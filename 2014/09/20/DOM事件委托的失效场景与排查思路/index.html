DOM 事件委托的失效场景与排查思路

事件委托的代码只有十几行，但要让它在一个真实项目里长期不出事，靠的是对三件事的判断：事件会不会冒泡到这个容器、冒泡路径上的节点是不是都”够格”参与匹配、以及委托绑定与直接绑定混在同一页里时谁先谁后。过去半年我写过三篇事件相关的文章：《jQuery 的 on、off 与事件委托》解决库 API 的选型与迁移，《DOM 事件移除与内存泄漏》解决绑定与解绑的生命周期，《DOM 事件对象与事件委托》解决事件对象的属性差异并给过一个二十多行的原生委托。它们各自把一条线讲完了，但线上问题从来不按我文章的章节出——这半年我处理过的委托故障里，没有一起是”委托代码本身写错”。本文换一个视角，把委托失效的场景逐类拆开，每一类给出排查方法和当时能落地的兼容结论。适合委托已经用起来、正准备把功能铺到 IE8 与老 Android 上的读者；读完你应该能在遇到”委托怎么没反应”时，按一条固定的路径在三分钟内定位到断点。

先对齐心智模型：委托的战场是一条路径

在拆解失效之前，先用三句话把委托的运作模型钉死，后文每一类事故都对应其中一句话被破坏：

第一，事件从 target 出发，沿祖先链一路向上走到根，这条路径才是委托的战场。容器不是被动等事件的”终点”，而是这条路径上的一个哨卡：事件只要冒不到哨卡，委托就形同不存在。第二，选择器匹配不是对”你想象中那个按钮”做的，而是对路径上的节点逐个做的，命中者是路径上最近的匹配节点——所以路径的第一环（target）如果压根不是个像样的节点，整个匹配链就从起点崩掉。第三，同一页里可以有多个哨卡（直接绑定、另一个容器上的委托、document 级的历史遗留 live），它们各自独立筛各自的，彼此不知道对方的存在，命中两次就是双触发。

这三句话没有一句是新知识——前两篇里都散落地讲过。但把失效归因到”哪句话被破坏了”，排查就从玄学变成了流程。下面按第一句、第二句、第三句被破坏的顺序展开。

路径断在半路：事件根本不会冒泡

最古老的一类失效，断的是第一句话：选的事件本身不冒泡，哨卡永远等不到人。这类事件在规范里是明确的，2014 年需要背下来的清单是：submit 与 reset（在 IE8 及更早完全不冒泡，标准浏览器里 IE9 起才冒泡）、change（IE8 不冒泡，而且它的触发时机各家本就不一致）、select（IE8 不冒泡）、focus 与 blur（所有浏览器都不冒泡，IE 另有私有的冒泡版 focusin / focusout，Firefox 到当前版本仍未实现）、以及 scroll（只在产生滚动的那个元素上派发，不冒泡也不捕获到 document 以外的祖先）。《DOM 事件对象与事件委托》的坑清单里给过 submit 与 change 的结论，这里只补两条它没写的：一是 reset 与 submit 同病，重置一个委托在容器上的表单一样收不到，而且 form.reset() 方法调用在老浏览器里干脆不派发 reset 事件，跟 form.submit() 不派发 submit 是一对孪生坑；二是 scroll 看似没有委托需求，真需求藏在滚动容器里——给一个可滚动的列表容器绑 scroll 做懒加载，这个容器本身必须稳定存在，容器一旦被模板重建，滚动监听跟着消失，这属于下文哨卡消失的同类事故，但它的症状是”滚到底不加载”而不是”点了没反应”，排查时很容易被归错类。

现象、诊断、对策在这个模型下都很干净：诊断用一行捕获探针（捕获阶段在任何 stopPropagation 之前执行，也早于冒泡；若捕获期都收不到，说明事件根本没派发或被更早的环节拦下，IE8 没有捕获阶段，探针要逐层绑到各祖先上笨办法二分）。对策照旧一句：不冒泡的事件，别委托，直接绑。

路径的第一环塌了：target 不一定是个能匹配的节点

委托代码里最常见的一行是 while 循环沿祖先链做选择器匹配，或者用 closest() 一步到位。麻烦在于循环的起点是 event.target，而 target 并不保证是元素节点。

现象有三种。第一种，委托代码在某些机器上抛异常，报错信息通常是”Object doesn’t support this property or method”或”querySelectorAll 选择器无效”之类——因为你在一个文本节点上调用了选择器方法。Firefox 在早期版本里曾把点击事件的 target 报成文本节点（后来修掉了），但 Android 2.x 自带浏览器的那套老 WebKit 把这个问题一直带到 2014 年的用户手机上；另外在富文本编辑场景里，凡是页面上有过通过 createTextRange 构造的选区（编辑器做关键词高亮的常规手段），IE 9 与 IE 10 的点击事件也被观察到返回文本节点 target。第二种，不抛异常，但静默不命中：文本节点没有 className 属性，用”正则匹配 className”做匹配的老式委托代码遇到它直接落空，表现为”偶尔点不动”。第三种最隐蔽：target 是元素但它是 SVG 元素（后文单独一节）或者 document 本身，匹配函数行为怪异。

原生 closest() 这一层也有自己的坑。它是 W3C 在 DOM4 草案里新加的方法，2014 年的支持现实是：IE9 及以上才有，IE8 完全没有，Android 2.x 与老 Firefox 也不可用；就算在支持它的浏览器里，文本节点上也没有 closest 方法，直接调用照样抛异常。所以”IE9 起才有 closest”的正确理解是：它是你代码里唯一需要特性检测的入口，而不是你可以直接用的入口。好消息是 jQuery 1.3 起就提供了同名方法 closest()，库内场景永远不必赌原生实现；但注意 jQuery 版同样在文本节点 target 面前会表现异常，而且它不会尊重你的委托边界——它会一路向上找过容器，这正是下一节要讲的越界问题。

路径上根本没有它：伪元素无法被委托命中

CSS 生成的 ::before / ::after 内容是 2014 年前后用得最飞起的装饰手段：关闭按钮的叉、必填星号、图标字体。但伪元素不存在于 DOM 树里，冒泡路径上没有它的节点身份，于是委托对它的命中永远是”宿主元素”。这带来两种相反方向的失效。

第一种，误触发。给面板标题的 ::after 画了个叉当作关闭按钮，点击它时 target 是整个标题元素——如果你的委托恰好绑了 .panel-title（比如用来折叠展开），点叉会触发的不是关闭而是折叠，用户觉得”按错地方了”，其实是按哪儿浏览器都当成同一个位置。第二种，漏触发。给删除链接加了个图标伪元素，用户偏要点图标那块视觉区域才觉得是”点按钮”，而那块区域的宿主是按钮本身还好，若伪元素定位偏出去了（绝对定位的角标常见），点它时 target 落到了再外一层的容器，选择器不匹配，静默失败，用户反复点，你反复查不到 bug。

另一条时间线的节点：SVG 与老 IE 的 VML

数据可视化在 2014 年的主流方案还是 SVG（Raphaël 2011 年就支持了 IE8 下的 VML 降级）。给图表节点做事件委托，会撞上普通 DOM 上不存在的一整套问题。

问题一，className 不是字符串。SVG DOM 里元素的 className 属性是 SVGAnimatedString 对象，target.className.indexOf('.bar') 这类代码在 SVG 节点上直接 TypeError 或静默失败——这是”委托在 HTML 列表里好好的、绑到图表上就失灵”的头号原因。判断类名请一律走 getAttribute('class')，或者用前文 closestSafe 里的选择器匹配函数，它们对 SVG 元素同样有效。

问题二，IE8 根本没有 SVG。用户点的”图形”在 IE8 里是 VML 节点，VML 走的是 IE 私有的行为（behavior）体系，它的节点不在标准 DOM 事件模型的语义里：没有 addEventListener，srcElement 偶尔给你 document 或者莫名其妙的包装节点。指望在 IE8 下对 VML 图形做委托，是拿项目开玩笑。

问题三，老浏览器的 SVG 选择器匹配不稳定。Chrome 30 之前的版本对 SVG 结构使用层级选择器（svg > g path 之类）行为不完全可靠，老 Firefox 亦有前缀历史包袱。

所以 2014 年关于”SVG 要不要委托”的实践结论很朴素：图形节点数量通常不过百，直接绑；Raphaël 本身提供每个图形对象的 click / mouseover 回调，用它，事件模型的问题让库去扛。需要委托的只有外层 HTML 容器——图例、工具条这些本来就是 HTML 节点的区域。把 SVG 内部当成”委托盲区”，是这一节真正的收获。

多个哨卡互不知情：双触发、绑定顺序与动态 class

断的是第三句话。委托的匹配发生在事件触发的那一刻，同一页里可能同时存在：新写的容器委托、历史遗留的 document 级委托、某个插件在按钮上的直接绑定、甚至 1.8 时代没人清理的 live。它们互不知情，各自命中，各自执行。

最典型的现场是删除按钮。列表委托 $('#list').on('click', '.del', del) 写着没问题，但某弹窗组件在它的关闭按钮上直接绑过 $('.del').on('click', close)——同一个类名，同一页，两套逻辑。用户点弹窗里的 .del，事件冒泡到 document 上那个历史遗留委托时，列表模块也认它，于是删除逻辑和关闭逻辑一起跑。这不是谁写错了，是两个哨卡各自都”正确”。治法分两层：代码层面，委托选择器必须带命名空间意识，至少加上模块前缀类名（.mod-list .del）或改用 data-action 属性选择器；排查层面，用 Chrome 控制台的 getEventListeners(document)（Firefox 与 IE 只能回到”逐层捕获打点”的笨办法）把绑在 document 与 body 上的处理器列一遍，2014 年的前端调试笔记里，这是比翻代码快得多的找到”隐形委托”的方式。

同容器多分支委托也有一个容易吃不准的细节。在同一个容器上绑 '.title' 和 '.title .del' 两条委托，点标题里的删除按钮时，title 分支会不会一起执行？会——两条 handleObj 各自从 target 沿路径匹配各自的 selector，各命中各的，互不干扰；委托没有”一个命中后其余分支跳过”的语义。如果你要的就是互斥分支（点了 .del 就只跑 .del），要么让处理器自己判断并提前 return，要么把两条合成一条逗号选择器再加 is() 分发：

焦点与表单：一套层层叠加的补丁机制里全是边界

《DOM 事件对象与事件委托》的坑清单已经给出结论：focus 不冒泡，委托焦点在标准浏览器走捕获，Firefox 不支持 focusin；change 与 submit 永远直接绑。这里把这张失效地图补完整，重点是 jQuery 委托焦点时那套补丁机制的边界在哪。

关键在于第三行与第四行之间那道缝：老 WebKit 支持 focusin，Firefox 到 31 仍然没有——而 jQuery 1.11 为了让你”放心用 focusin 委托”，在没有原生 focusin 的浏览器里走的是补绑路径：绑定时对匹配到的控件直接绑 focus / blur 并人工合成冒泡语义。补绑发生在绑定的那一刻，对动态插入的控件，jQuery 靠事件触发时的重查来补，于是留下几个可观察到的边界行为：其一是时机，Firefox 下焦点委托的合成派发与原生 focus 处理器有先后差，你的处理器若同时依赖”输入框已失焦”的状态，Chrome 下没事、Firefox 下读到旧值；其二是 relatedTarget，委托焦点逻辑里常用它判断”焦点是不是真的离开了容器”（从容器内一个输入框跳到另一个，focusout 的 relatedTarget 是下一个输入框，可以跳过收起校验），但焦点移出窗口、或聚焦元素被移出 DOM 时，relatedTarget 是 null——直接 relatedTarget 判空会误报”离开了容器”。2014 年可用的兜底是读 document.activeElement：relatedTarget 为空时，检查 activeElement 是否仍在容器内。

表单控件的动态生成问题也集中在这块。用 DocumentFragment 批量渲染一行行带输入框的表格，change 无法委托（前面说过），直接补绑又要遍历新控件，性能顾虑让人犹豫。实际测下来这个担心多半是多余的：表格行数在三位数量级时，渲染回调里给新控件逐个绑 change 的开销可以忽略——真正该警惕的是”忘了补绑”：补绑代码写在 append 之后，而另一处代码路径直接 innerHTML 重建却绕过了补绑函数，两类路径的委托行为不一致，用户报”有的输入框有校验有的没有”。解法是把”渲染 + 补绑”收成一个函数，杜绝裸的片段插入。至于重置，form.reset() 不触发 change 也不触发 reset（老浏览器），依赖值变化刷新界面的代码要在调用 reset() 后手动同步一次状态——这不是委托的坑，但委托 change 失败的项目十个有八个会顺手也栽在这里，一并记下来。

委托的隐藏账单：每次触发的匹配成本与 document 级委托

绑定成本那笔账——一千个直绑对一千个委托——前文测过，委托完胜。但委托的另一半成本发生在每次事件触发时：从 target 到容器的路径上，每个节点、对容器上每一条委托 handleObj，都要做一次选择器匹配。单次成本是路径深度与委托条数的乘积。

这意味着两种 2014 年踩得到的真实退化。第一种是 document 级委托的”广播税”。document 上的委托是路径最长的哨卡：页面上每一次点击，无论发生在哪个角落，都要走完整条祖先链并对 document 上挂的全部委托选择器各匹配一遍。零散点击无感，但给 mousemove 这类高频事件也挂上 document 委托时（做拖拽热区检测、做悬停菜单的公共逻辑），每帧几十次触发乘上几十条选择器，掉帧就是这么来的。判断方法很土但有效：

第二种是选择器本身写得深。委托选择器里层级越深，matchesSelector 的匹配越慢，而委托的匹配发生在每个路过的事件上，不只是”那个按钮被点时”。'#list li .item span .del' 这种写法，成本要乘上容器里每一层祖先。规范做法是把委托锚点提到列表根、选择器压到一层（'[data-action="del"]'），并用”容器尽量贴近业务根节点”的老纪律缩短路径——容器越近，路径越短，乘出来的总账越小。document 级委托在 2014 年的正确定位是：全局快捷键、埋点采集这类真全局逻辑；模块自己的交互，一律回到模块根节点。

容器选在哪：body、documentElement 与消失的哨卡

最后一个断点：哨卡自己没了。委托绑在容器上，容器若被重建，监听器跟着旧节点一起进回收站，新容器干干净净，功能整体失联——而你的代码里一行委托都没错。这在前面章节的绑定模型里没有位置，因为它坏的不是匹配，是哨卡本身。

比”容器被重建”更高频的是”绑定时机”的坑：脚本在 <head> 里执行时去找 #list 做委托，容器还不存在，addEventListener 直接报空。老手会条件反射地把委托挪进 $(function () { ... })，但这里藏着一个更细的选择：等到 ready 再绑，绑在 document 还是绑在 documentElement？2014 年不少自研框架的引导层喜欢用 documentElement——它在脚本执行的任何时刻都已存在（document.documentElement 从解析开始就可用），绑在它上面既不依赖 ready，又比 document 短一层路径。代价是它不在常见模板的替换范围内，比 body 更长寿：有些页面切换方案（整页过渡、打印前重排）真的会重建 body 内部结构甚至换掉 body 节点本身，绑在 body 上的全局委托会随之蒸发。选择顺序因此是：模块交互绑模块根节点；全局逻辑优先 documentElement；document 留给那些历史遗留、以及必须晚于一切 DOM 存在的运行时钩子。

还有一个与容器选择相关的移动端边界要记一笔：iOS 与 Android 老 WebKit 的合成点击机制对”可点击”有自己的判定——普通 div 在没有直接 onclick、不处于 cursor: pointer 样式下时，点击事件可能被系统改写目标（点到被禁用的按钮时，target 落到它的祖先上去），委托在这种合成点击面前命中的可能不是你写代码时想象的那个节点。触摸场景的事件模型自成一套体系，这里不展开，本文的委托结论到移动端要重新在真机上验一遍，机制细节另见《FastClick 解决点击延迟》。

一套固定的排查流程

把全文的断点串成一条排查路径，遇到委托失灵按顺序走，不要跳步：

flowchart TD
    A[委托没有反应] --> B{事件在冒泡清单里吗}
    B -->|submit change focus 等| Z1[改直绑或捕获或换事件名]
    B -->|在| C[容器上挂捕获探针]
    C --> D{探针收到事件吗}
    D -->|否| E[逐层上移探针找截胡者]
    E --> Z2[stopPropagation: 挪容器或谈插件]
    D -->|是| F{target 是什么节点}
    F -->|文本或 SVG 或伪元素宿主| Z3[扶正 target 或改真实元素]
    F -->|正常元素| G{选择器在路径上命中吗}
    G -->|class 被改写| Z4[迁到 data 属性]
    G -->|命中但没执行| H[查双触发与隐形委托 getEventListeners]
    G -->|正常执行| I[功能问题不在委托 回头查业务]

配套的自检清单，按被破坏的模型三句话分组：

组 检查项
冒泡 事件在不冒泡清单里；动态容器上的 scroll 类监听是否随容器重建而丢失
路径 target 是否为文本节点或 SVG；伪元素热区是否有真实节点；匹配是否越过委托边界
哨卡 容器在绑定时是否已存在且此后不会被替换；同页有无重复委托与直绑打架；选择器锚点是否被第三方改写；高频事件是否挂了 document 级委托

小结

委托的全部复杂度，不在”怎么写对”，在”它依赖的三个假设什么时候被悄悄破坏”：事件会冒泡到容器、路径上的节点能被正常匹配、每个哨卡互不知情地各自执行。失效排查就是把这三句话逐条证伪——先查事件类型在不冒泡清单里，再挂捕获探针看事件到没到、target 是什么，最后查容器与选择器锚点。写代码时的纪律同样从这三句话来：不冒泡的事件不碰委托、委托选择器用 data-action 而不是 class、匹配圈定容器边界、document 级委托只留给真全局逻辑、动态渲染与补绑收进同一个函数。把这些收住的团队，委托带来的收益是稳定的；收不住的，收益会在三个月后的某个弹窗上线日连本带利地还回去。
