localStorage 与 sessionStorage 本地存储实战

本文属于《HTML 与 CSS》第 53/62 篇
上一篇系列目录下一篇

2013 年底我们把一个内部系统的筛选条件从 cookie 迁到 localStorage，本以为只是换个 API，结果陆续炸出无痕模式白屏、读回字符串、脏数据清了三次、跨标签页登录态不同步四起事故，每一起的根因都不在”怎么调用”，而在”没搞清它到底是什么”。本文按现场、根因、修复的顺序把这四个坑复盘一遍，再把同源边界、真实容量、同步读写的代价和安全边界讲清楚，最后给一份可以直接抄进代码评审的接入检查清单。适合正在考虑用本地存储替代 cookie，或者已经被它坑过的前端。

先把底数摸清：它到底是什么

Web Storage 给每个 origin 挂了两张键值表，一张叫 localStorage，除非代码或用户清掉否则一直在；另一张叫 sessionStorage，挂在顶层浏览上下文上，标签页一关就没了。两张表都只能存字符串，接口是同步的，读写都跑在主线程上，这是后面所有坑的物理起点。

兼容性在 2014 年已经不必太担心：localStorage 与 sessionStorage 从 IE 8 起可用，IE 7 及更早要用微软私有的 userData 行为，那是另一套 XML 持久化写法，真要支持就单独立一个后端，别伪装成同一层。常见的坑恰恰是”能不能用”这件事不能靠判断对象是否存在来确定，原因见坑一。

至于更大规模的结构化存储，IndexedDB 与 Web SQL 是另一条线，选型取舍在《移动端离线存储与缓存》里讲过了；HTTP 缓存与 AppCache 那套也和客户端存储无关，本文都不重复。

坑一：无痕模式写入直接抛错

现场是这样的：桌面一切正常，测试同事拿 iPhone 4 打开无痕浏览，页面直接白屏，控制台停在 QUOTA_EXCEEDED_ERR。当时的代码写得很”标准”：

根因有两层。早期 WebKit（iOS 4 之前）在私有模式下干脆不给 window.localStorage，对象是 undefined，判存在是对的；但 iOS 5、6 的 Safari 换了做法，对象给你、读也返回 null，一写就抛 QUOTA_EXCEEDED_ERR——私有模式下配额被设成 0，而异常又不在 if 的判断范围内。IE 这边还有第三种情况：用户在 Internet 选项里勾掉了”启用 DOM Storage”，读写同样抛错。所以”存在性检测”这条路天生不可靠，只能真写一次才算数。

修复是把探测做成一次性动作，再给失败留一个行为一致的内存兜底，让上层代码感知不到差异。

还有一个业务层的决定：兜底之后要不要告诉用户。我们的做法是 memoryOnly 为真时在页脚提示一行”当前浏览模式下筛选条件不会保存”。无痕模式本来就不留痕，程序不该假装能存，但也别白屏。

坑二：存进去是对象，读回来是字符串

第二个事故更安静。有人把整个筛选条件数组直接 setItem("filter", condList) 写了进去，取出来用 length 判断条数，怎么都不对。原因是规范里存储区的值就是字符串，写对象时浏览器会先做一次隐式转字符串，数组变成逗号串、对象变成 [object Object]，信息当场丢掉。

于是大家改成 JSON.stringify，问题只解决了一半。第二次白屏是这么来的：某次写入时浏览器在序列化中途被杀掉，或者有人手贱在控制台里改了值，本地留下了一段残缺 JSON，而读取代码是这样的：

parse 抛出的异常没人接，初始化函数中断，整页空白。这坑的本质是：本地存储里的数据是不可信输入，它可能属于上一个版本的数据结构，可能被用户改过，可能只有一半。处理它的态度和处理接口返回一样，要有默认值和异常分支。

顺带两个细节：JSON.stringify 会丢掉值为 undefined 的键、把日期变成字符串、遇到循环引用直接抛错，序列化前最好只放纯数据；JSON.parse 的第二个参数在 2014 年只有少数浏览器实现，别指望它。

坑三：写进去的东西永不过期

第三个坑是慢性的。上线半年后用户抱怨”去年存的模板还在””早就下线的选项还挂在筛选面板上”。Web Storage 没有过期概念，条目一旦写下，除非代码显式删或用户清浏览器数据，它会一直待在那儿。当年 cookie 好歹还有 Expires，这一点常常被忘。

我们的修复是做一个带 TTL 的存储层：命名空间前缀隔开同域下不同项目的键，写入时统一包一层值、过期时间、最近访问时间，读取时判过期就地删除，配额逼近时按最近访问时间逐出最旧的条目。下面是生产里用的版本，只用 ES5 语法，枚举一律走后端自己的 keys，所以 IE 8 也能跑。

三个设计取舍值得说明。前缀是必须的：同域下所有页面共用一个存储池，不加前缀迟早和别人的键撞车。get 每次都要回写访问时间，热点键上这笔开销不小，我们后来改成在内存里记访问时刻、页面卸载前批量回写。逐出只在自己的命名空间里做，绝不动别人的键，这条是纪律。

localStorage.clear() 是这一节顺带要钉死的一条禁令：它清的是整个 origin 下所有页面的数据，包括同域下另一个团队的应用。排查问题时在控制台手滑一次，事故就出了。我们要求代码里不允许出现这个方法，删除只走 removeItem。

坑四：跨标签页同步与 storage 事件

最后一件事不是事故，是我们摸了几轮才搞清的机制。需求很朴素：A 标签页点了退出，开着的 B 标签页也要变成未登录。storage 事件就是为这个设计的——某个文档修改了存储，同源的其他文档会收到通知。但它有四条脾气，每一条都能坑一次。

第一，发起变更的那个文档自己不会收到事件，规范明确把它排除了。所以不能指望”写完自己也刷一遍”，B 靠事件、A 手动更新界面是两套代码。第二，事件只在不同文档之间派发，同源 iframe 与主页面算不同文档，能收到。第三，sessionStorage 按规范只在同一浏览会话的其他上下文里派发，2014 年各家实现基本不发，跨标签页同步只能靠 localStorage。第四，兼容性有洞：IE 8 就支持，但走的是只有 attachEvent 才认的私有事件名 onstorage，事件对象也从参数变成 window.event；Firefox 3.0 到 3.5 那一线早期版本压根没实现，之后才补齐。

还有一点关于 event.url：标准里这个字段标了废弃，Firefox 早期给的属性名是 uri，Chrome 给的是 url，两边拼写都不一样。既然只需要判断是不是自己的键，就干脆不要依赖它，用 key 的前缀自己判别。

事件对象上还给了 oldValue 与 newValue，判断是不是从登录变成未登录不必再回读一次存储。另外，标签页被系统回收或异常关闭时不会给你任何机会，登录态这类关键状态别只靠事件，页面重新获得焦点时主动校验一次更稳。

边界：同源口径和 5 MB 的真实含义

Web Storage 的作用域是 origin，而 origin 由协议、主机名、端口三者严格拼出来。所以 http://app.example.com 和 https://app.example.com 是两套表；app.example.com 和 app.example.com:8080 也是两套；m.example.com 与 www.example.com 同样不共享——这和 cookie 能用 domain 放宽到父域完全不同，也是”明明同一个站点，子域间数据不通”的唯一解释。顺带一提，document.domain 那套打通 DOM 的办法对存储不起作用。跨域怎么处理是另一篇文章的事，《AJAX 与跨域请求实践》讲过，本文不重复。

容量方面，各家从 2.5 MB 到 10 MB 不等，业界常用的保守口径是每个 origin 5 MB。这句话有两个坑。其一，配额是整个源共享而不是每个应用独占：同域下三个团队、后台管理页和营销活动页用的是同一个池子，谁写爆了大家一起报错，这就是必须加前缀、必须自己做预算和逐出的原因。其二，5 MB 按什么计各家并不统一：值在内存里是 UTF-16，一个汉字算一个码元，落盘按 UTF-8 一个汉字要三个字节，超出基本平面的字符是代理对、占两个码元。同样一份中文内容，在不同浏览器上吃掉的配额能差到两三倍。猜口径不如实测：

键名本身也占空间。见过把接口地址、时间戳、用户 ID 全拼进 key 的写法，一个条目光键名就上百字节。键名允许空格、冒号甚至中文，语法上不报错，但在控制台里手工读写很别扭，统一用小写字母加冒号比较省心。

性能：同步 API 与那笔 cookie 的带宽账

先做实测。读写都在主线程同步完成，浏览器可能还要落盘，所以耗时取决于数据体积，也取决于设备。别用一次采样下结论，第一次写入往往偏慢：

我们的实测数据是：桌面 Chrome 写 100 KB 字符串在几毫秒量级，可以忽略；同一份数据在 Android 2.3 原生浏览器上要几十毫秒，写 1 MB 时肉眼能看到滚动掉帧。结论是”体积越大越危险”，而不是”这个 API 慢”。规避手段按优先级排：第一是压根不存完整对象，只存 id 列表，需要详情时回接口取，这一条能解决八成问题；第二是分片，把大数组切成固定条目的若干键，逐片写、逐片读，避开单次大写入；第三是延迟合并写，连续变更在内存里攒着，用定时器或页面卸载前统一落一次，别在 mousemove 这种高频回调里同步写。

真正要强调的是别拿 cookie 存列表数据。三种手段摆在一起看就清楚了：

维度 cookie localStorage sessionStorage
单条容量 约 4 KB 整个源约 5 MB 上下 同左
随请求发送 是，同源每个请求都带 否 否
服务端能否读写 能 不能 不能
过期能力 Expires 或 Max-Age 原生 无，要自己实现 标签页关闭即失
脚本可读性 非 HttpOnly 时可读 始终可读 始终可读
作用域粒度 域加路径，可放宽到父域 严格 origin，含端口 origin 加标签页
跨标签页通知 无 storage 事件 实际不可用
合适用途 会话凭证、服务端要用的小标记 偏好、草稿、带 TTL 的小数据 一次性表单流程状态

那行”随请求发送”就是这笔账的关键：cookie 会附加到同源下的每一个请求上，包括 CSS、JS 和一堆图片，静态资源请求还会一路带到 CDN 域名。把 30 KB 的列表塞进 cookie，等于每次刷新都往上行里加 30 KB，何况它会被截到 4 KB，截断后的 JSON 直接坏掉，URL 编码还要让体积再涨三分之一。反过来，需要服务端识别身份的信息也不该搬进 localStorage，服务端根本看不见它。这两条边界一划清，大部分选型纠结自然消失。

sessionStorage 还有个容易被误会的语义：新开标签页不会继承，只有脚本 window.open 出来的同源新上下文会拷贝一份，这就是”刷新还在、新开就没了”的由来。另外 IE 8 和 9 里几个标签页共用一个浏览器进程，sessionStorage 的实际存活边界和进程绑在一起，测试时别想当然认为关掉标签页数据就没了。

安全：先判断存不存，再讨论怎么存

一句话前提：localStorage 里的东西页面脚本都能直接读走，没有 HttpOnly 保护。《表单元素操作与表单验证实战》里讲过前端校验只是体验层不是安全层，同一个道理放大到存储上就是客户端存的一切都不能当信任依据。而 XSS 落地后的第一个动作往往就是把整个存储 dump 一遍，《HTML5 contenteditable 富文本编辑入门》谈存储型 XSS 时提过这一点，也明确过真正的防线在服务端。

具体到存不存，判断标准是三问：这份数据被 XSS 读走会不会造成实际损失；用户换浏览器或清掉数据后功能是否退化；服务端是否会拿它做鉴权依据。只要有一问答”是”，就不放本地。梳理下来是这样：

可以放：界面主题、语言、字号、表格列宽这类偏好；折叠状态和上次浏览位置；带 TTL 的编辑器草稿，且界面上要明示内容保存在本机；不含隐私信息的短时接口数据。

不要放：会话令牌、刷新令牌、密码；身份证号、手机号、住址这类明文个人信息；任何权限判断的源数据——前端只可以用它加速展示，不可以用它决定是否渲染一个按钮；公用设备上的搜索历史。

移动端还有三个额外变量。第一，iOS 上 Safari 切到后台可能被系统直接杀掉进程，sessionStorage 随之消失，草稿类内容要么实时写 localStorage 要么认命；系统存储紧张时回收某个站点的全部本地存储也确实发生过，所以本地存储是缓存，不是数据库。第二，WebView 里 file:// 协议下的 origin 各家处理不一致，Chrome 系内核把本地文件当成不透明源，读 localStorage 会直接抛 SecurityError；Hybrid 场景要持久化就走原生通道，《移动端离线存储与缓存》和《JSBridge 设计与实现》里各写过一处，这里不展开。第三，Android 2.3 那批设备的原生浏览器配额比桌面小、私有模式下同样抛错、单次写入明显更慢，大对象写入的掉帧是能直接感觉到的。

小结与接入检查清单

回头看，四个坑指向同一条认知：Web Storage 是一个按 origin 划分、只能装字符串、没有过期机制、读写全部同步、脚本可以任意读的小盒子。把它当”更方便的 cookie”用会出事，把它当一个需要自己补齐 TTL、命名空间、异常分支和降级路径的迷你 KV 层来封装，才好用。

接入前照着这张单子过一遍：探测要用真写入而不是判对象存在，失败要有内存兜底；所有值过 JSON 封装，读取带默认值和版本号；写入包 TTL，页面加载时跑一次清扫；键一律带命名空间前缀，禁止调用 clear；配额自己设预算，逼近时只逐出本命名空间里最旧的条目；跨标签页同步只用 localStorage，兼容 IE 的 onstorage 与事件对象差异，并记住自己这一页收不到通知；只存 id 列表不存完整对象，大数组分片、连续变更合并延迟写；身份信息留在 HttpOnly cookie 里，本地不放任何服务端鉴权依据；移动端把被杀进程、file:// 下的隔离、低端机写入耗时三件事单独测一遍。

清单不长，但每一条背后都是一次线上排查。这几件事在封装层里一次做对，剩下的就只是按业务定 TTL 了。
