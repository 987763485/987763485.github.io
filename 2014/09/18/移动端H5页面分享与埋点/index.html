移动端 H5 页面分享与埋点

2014 年做移动端 H5 活动页，分享和埋点是一对难兄难弟：分享出去的内容收不回来，埋点发出去的数据半路会丢。本文讲清两件事——分享可控到什么程度，以及一条从入队到落库真正收得到数据的打点链路怎么设计，最后给一段能直接抄走的 ES5 SDK。

分享的三种形态，先看清各自可控多少

页面能调动起来的分享入口只有三类，可控性差别极大，做方案之前必须先把边界分清楚。

第一类是浏览器或客户端自带的菜单转发。 标题、描述、缩略图全由客户端抓取，页面能影响的通常只有 document.title 和一段 meta 描述。微信里可以用 JS-SDK 的分享接口把这三项固定下来，签名配置在《微信 JS-SDK 接入实践》里写过。要紧的是：这条路径拿不到成功回调，也拿不到转发之后的曝光量。

第二类是宿主 App 注入的分享面板。 容器注入的 bridge 对象能拉起原生面板，内容由页面给、动作由原生完成。协议在《JSBridge 设计与实现》里定过，本文只用两条结论：调用前做能力探测，老客户端回”不支持”时要有退路；不要把业务奖励挂在”分享成功”上。

第三类是页面自绘的引导蒙层。 iOS Safari 没有把网页转发给联系人的入口，用户只能复制链接或者退到系统浏览器再操作。当年活动页普遍的兜底做法是：点”分享给好友”就盖一层半透明蒙层，手绘箭头指向右上角，文案写”点右上按钮，选择在浏览器中打开后分享”。它不依赖任何客户端能力。

实现上有四个细节：环境判断先排除自家容器，免得和原生面板抢交互；提示频率要有上限，用一个 localStorage 键记时间戳；老 WebView 在隐私模式下读写它会抛错，必须包 try-catch；示例里的 toast 与 shareParams 由业务侧提供。

三种形态选完，链路大概是这样：

flowchart TD
    A[用户点击页面分享按钮] --> B{在微信内置浏览器}
    B -- 是 --> C[JS-SDK 配好的标题与图标]
    B -- 否 --> D{在自家客户端容器}
    D -- 是 --> E[bridge 调起原生分享面板]
    D -- 否 --> F[蒙层引导点右上角]
    C --> G[好友或朋友圈打开落地页]
    E --> G
    F --> G
    G --> H[落地页读来源参数并上报]

分享链接的构造：短链、参数命名与被丢掉的 hash

不管走哪条路径，最终都要落到一个能被统计的地址上。链接构造要提前定死三件事：参数命名规范、参数放在哪一段、短链由谁提供。

先说命名。当年我们吃过”每个活动各造一套参数名”的亏，数据组要写四五种解析逻辑，报表里同一个渠道三种写法。后来定了一份固定字段表写进构造函数，不许自造：

参数 含义 示例 约定
act 活动 id act=20140918a 与后台活动表一致
ch 一级渠道 ch=weixin weixin、weibo、qq、app、push
sub 二级投放位 sub=poster1 海报、公众号菜单、群发
from 来源形态 from=share share、banner、qrcode
lv 转发层级 lv=2 第几层转发，默认 1
suid 分享者标识 suid=8831 脱敏后的站内 id
ts 链接生成时间 ts=1411027200 秒级，服务端时间

另有四条硬约束：全部小写、值里不出现中文、单个值不超过 32 字符、总长不超过 120 字符。解析要处理重复键、空值和被二次转义的加号；decodeURIComponent 遇到残缺的 % 序列会抛异常，一个脏参数就能让整页脚本停摆，所以解码必须包 try-catch。

参数放 query 还是放 hash，是 2014 年移动端一个真实的分水岭。活动页习惯用 hash 做单页路由，于是写成 .../#/index?act=xxx&from=share。可这条地址经过两三个环节就可能变短：部分安卓 WebView 会把 hash 里的查询片段当路由参数处理掉；微博这类客户端做 URL 规范化时把 # 之后整段截掉过；短链生成码时只保留 # 之前的部分。落地页打开了，from 却读不到。对策只有一句：来源参数放 query，路由放 hash。页面加载时先解析 location.search，发现参数掉进了 hash 再兜一次：

短链能选就自建。自建映射表把长链存在服务端，跳转用 302 而不是 301，改了参数不会被浏览器缓存钉死，还能把短链点击与落地页带参访问对上，量化中间丢了多少。第三方短链对未编码的 & 处理不一致，有时会把后面的参数并成一个值；跳转接口要加 no-store，否则参数改版在真机上验不干净。

分享为什么只能间接度量

把话说透：H5 页面统计不到”分享次数”。系统菜单转发没有回调，原生面板的回调只告诉你点了哪个渠道，朋友圈曝光完全不可见。前端只有两个数——分享按钮的点击次数，和落地页带 from=share 的访问次数。

报表里只有一个正经口径：分享带来的访问，即 from=share 的会话首次 PV。要倒推分享次数，只能除以”单次分享的平均打开人数”，微博转发和微信群聊差别很大，我们当年按 2 到 3 估。K 值用带参访问除以总访问，不依赖那个系数，适合活动之间横向比较。

要写进数据字典的误差有五条：一条链接在群里被二十个人点开会计二十次；手动粘贴时参数常被截断，这部分流量掉进直连；二级转发改标题重发时 lv 不会自动递增；iOS 从聊天窗口返回活动页可能命中页面缓存，不算新的首访；广告拦截让分享来源系统性偏低。

结论：报表里不要出现”分享次数”这一栏，只写两个可观测口径。硬凑拿不到的数据，比承认统计不到更容易误导决策。

埋点的事件模型与字段规范

分享是流量入口，埋点是数据底座，底座这一侧才是本文的技术主线。事件模型不用贪多，一个活动页四类事件足够覆盖 90% 的分析需求。

事件 触发点 上报量级 说明
pv 页面或单页视图首次呈现 1 带来源参数与首屏耗时
expose 模块进入视口约四分之三 每模块每会话 1 次 去重靠模块 id 字典
click 可交互元素点击 不限 带模块 id 与序号
stay 离开时补发 1 停留秒数，不是心跳

字段规范比事件类型更容易出问题：前端各写各的字段名，落到同一张表里对不上，是埋点崩掉最常见的原因。最小字段集所有事件共用：

字段 含义 为什么必须有
pid 页面 id 活动页多版本并行，靠它区分
mid 模块 id 曝光与点击都挂它，空串表示页面级事件
a 动作类型 pv、expose、click、stay
s 会话内序号 从 1 自增，用来还原顺序与发现丢包
t 事件时间戳 毫秒，校准后的客户端时间
u 会话 id sid 页面级关联，比 Cookie 可靠
v SDK 版本号 字段改版后能按版本分段统计
ext 扩展 JSON 业务参数，长度截断

seq 值得单独说一句。批量发送时同一毫秒内多条事件的时间戳完全一样，服务端按时间排序就会乱序，”先点领券再点关闭”这类顺序分析直接失效。改成按 sid 加 s 排序，序号还能发现丢包：一次会话里 s 从 1 跳到 7，中间那几条就是没送到。

sid 靠 Cookie 存不住也靠不住：WebView 清 Cookie 频繁，活动页域名和业务主域常常不同源。做法是首次进入时在前端生成 sid，写一份 sessionStorage，连续页面靠 URL 传递；生成用 Math.random 拼时间戳的 36 进制，足够唯一：

三条传输通道：GIF 打点、跨域 XHR 与 JSONP

打点的通道只有三条，限制摆在一起就是一次明确的取舍。同源策略、withCredentials 与 CORS 的基础在《AJAX 与跨域请求实践》里讲透了，这里只比打点场景下的表现。

维度 1x1 GIF 跨域 XHR JSONP 脚本
跨域 天然可以 需服务端 CORS 头 需服务端支持回调
带 Cookie 可以，受第三方 Cookie 限制 需 withCredentials 不适用
老安卓内核 全部可用 2.3 不支持 CORS，4.0 至 4.3 行为不稳 全部可用
能读响应状态 只能靠 onload 与 onerror 能读状态码 能读数据
载荷上限 受 URL 长度限制 POST 体不受限 受 URL 长度限制
被拦截概率 高，域名易进黑名单 中 中，但会执行脚本

GIF 打点是移动端主选：不需要跨域能力、不解析响应、代码三行，服务端只要返回 200 加一张极小的图。有个坑必须写进代码——Image 对象要有引用持有。很多人写完 new Image().src = url 就不管了，回收时对象被清掉，请求在半路取消，日志时有时无。我们在 SDK 里维护一个数组，onload 或 onerror 之后才摘引用。

XHR 在同域收数时更体面，能 POST、能读状态码做重试判断、不受 URL 长度限制。但 2014 年的现实是老安卓 WebView 对 CORS 支持残缺：2.3 基本不认 Access-Control-Allow-Origin，4.0 到 4.3 带 withCredentials 偶发直接失败，预检在弱网下还多一拍延迟。所以跨域打点不用 XHR。

JSONP 只留给必须读响应数据的场景，比如拉打点配置、校准服务器时间。它本质是执行服务端返回的脚本，只对自家域使用并做超时兜底，安全约束在跨域那篇里写过。

结论：默认走 GIF，同域且载荷大或要状态码时走 XHR POST，需要读响应才用 JSONP。

发送时机与页面卸载的兜底

事件什么时候发出去，直接决定丢多少数据。

PV 的时机有两个候选。用 window.onload 会把图片耗时算进 PV，活动页首屏延迟三四秒的那段时间里用户已经划走，PV 凭空少一截；DOMContentLoaded 更贴近”页面开始呈现”，但它是脚本执行的时机而不是渲染完成的时机。我们选后者发 PV，渲染耗时另记一个字段。

批量发送是必要的：一屏十几个模块曝光加若干点击，逐条请求在 3G 上要抢十几个连接，还会挤占图片下载。策略是双条件——攒到 5 条立即发，或者第一条入队后 5 秒到点就发。

真正的问题是用户跳走时队列里还有数据。移动端可用的时机有三个，触发条件各不相同（老 WebKit 上还要听 webkitvisibilitychange、读 document.webkitHidden），必须都挂上做同一件事：

  • beforeunload：桌面浏览器可靠，iOS Safari 在关闭标签、切后台、点链接跳走时经常不触发，不能只指望它；
  • pagehide：iOS Safari 与 Android 4.x 支持，进入 bfcache 时也会触发，是最好的那个信号；
  • visibilitychange：切后台、跳到别的 App 时都会触发，适合提前结算停留时长。

在卸载回调里发请求的代价分两种。异步 GIF 最理想，但部分内核开始卸载后就不再等新请求，剩下的事件直接丢；同步 XHR 发得出去，代价是阻塞主线程，弱网下页面会卡一下才走。我们的折中是：普通事件放弃，关键事件同步发——关键事件用 important 标记，比如提交订单、领奖点击。

整条链路串起来是这样：

sequenceDiagram
    participant U as 用户
    participant P as H5 页面
    participant Q as 打点队列
    participant S as 日志服务器
    U->>P: 点击按钮或模块进入视口
    P->>Q: track 入队带 pid sid 与序号
    Q->>Q: 达到 5 条或定时器到 5 秒
    Q->>S: GET 请求一张 1x1 GIF
    S-->>Q: 200 与图片字节
    Q->>Q: 失败则延迟重试一次
    U->>P: 切后台或跳走
    P->>Q: 卸载事件里立即 flush
    Q->>S: 关键事件同步补发

上线之后才会暴露的四个坑

第一个：hash 切换的单页视图不算 PV。 切视图时 location.hash 变了但页面不重新加载，PV 少一整页。补发时要把新视图当一次首访，同时清掉已曝光字典：

第二个：iOS 上滚动中的曝光大面积漏统计。 这是真机行为，不是 bug：iOS Safari 在惯性滚动过程中基本不派发 scroll，要等手指抬起、滚动停下才补一次。用户快速划过一整屏，靠 scroll 做检测只在末尾扫一次，中间模块已经滚出视口，曝光全丢。解法只有轮询，定在 400 ms 一次，再密就影响滚动帧率；轮询的成本是读 offsetTop 会触发布局重算，曝光过的节点要立刻摘出检测列表。真机对比，纯 scroll 方案比轮询少三成以上。

第三个：GET 打点的 URL 长度上限。 批量事件拼进一条 URL，加上扩展字段很容易超过服务端的请求行限制，nginx 与 Apache 默认都在 8 KB 附近，超了直接 414，一批事件全丢。对策分三层：扩展字段截断到 512 字节、单次批量条数设上限、超过就走同域 POST。

第四个：打点域名被广告拦截。 log.、stat.、count.、analytics. 这些二级域是拦截列表的常客，UC 和 QQ 的加速模式也会过滤统计请求。把收数地址收到业务主域下的一个短路径后，被拦比例明显下降。更要紧的是当故障监控而不是幻想归零：拿服务端 PV 与前端 PV 对比，差异超过一成再排查，关键指标留一条不依赖打点的口径。

还有一个口径问题：客户端时间不可信。用户手改时间、低端机时钟漂移都会污染 t 字段。做法是差值类字段用校准后的时间算，绝对时间以服务端收到时刻为准。

小结

H5 活动页上，分享决定流量从哪来，埋点决定流量能不能被看见。分享这一侧的结论偏冷静：菜单转发不可控也不可测，原生面板要靠能力探测，iOS Safari 只能用引导蒙层，所以要做的不是提高分享成功率，而是把参数规范地放进 query、用自建短链、把带参访问当成唯一可信的指标。埋点这一侧是工程活：四类事件共用一份字段规范，序号解决乱序与丢包，传输默认走 GIF 并保住 Image 引用，批量加定时双条件发送，卸载时三个信号一起 flush。

上线前照着这份清单过一遍：

  • 来源参数放 query，act、ch、sub、from、lv 齐备，总长不超过 120 字符；
  • 短链服务在自家域下，跳转用 302 且加 no-store；
  • 引导蒙层在自家容器里不出现，微信里只做原生菜单引导，提示频率有上限；
  • localStorage 读写全部包 try-catch；
  • 埋点字段含 pid、mid、a、s、t、sid、v，缺字段的事件服务端直接丢弃；
  • 批量阈值与定时器双保险，卸载兜底已挂三个事件；
  • 曝光检测有轮询兜底，不单独依赖 scroll 事件；
  • 打点路径避开常见拦截域名，且有一条不依赖打点的对照口径；
  • 服务器时间校准生效，停留时长用差值而非绝对时间；
  • 抽样验证：两台真机各点十条，回后台核对 sid 与序号是否连续、来源参数是否完整。

十条里最容易漏的是最后一条。埋点写完不自测就等于没写——数据少了三分之一，往往要到活动复盘才被发现。
