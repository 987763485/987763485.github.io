事件委托减少事件绑定

上个月写的《DOM 事件委托的边界情况》把委托的原理、事件流走法和哪些事件接不了讲完了，那一篇的落点是”能不能用”。这篇只谈后半件事：”绑定策略怎么选”。读者留言问得最多的三个问题是：委托到底快多少、代价出在哪一步、IE8 还活着的项目里哪种写法可行。本文把逐个原生绑定、原生委托、jQuery 委托和 $.live 四种策略放进同一个测量口径里对比，给一张按场景查的选型表，最后专门写一节反面结论——什么时候不该用委托。至于为什么还要把 $.live 拉进来，因为存量项目里它还没清干净；而二月那篇《jQuery 的 on、off 与事件委托》已经测过 jQuery 内部两种绑法的差距，这次把原生写法和 live 补进同一个框架，只讲测量与选型，原理一律不重复。

四种候选策略

统一一个场景再谈选型：一个 1000 行的任务列表，每行一个删除按钮，只有 click 一类交互；容器 <ul id="list"> 稳定不销毁，行内容会被搜索、筛选整段重渲染。四种写法如下。

策略 A：逐个原生绑定

监听器数量等于节点数，1000 行就是 1000 个。IE8 只有 attachEvent：没有捕获阶段、事件对象挂在 window 上，所以上面这层十几行的包装就是为它准备的。这是所有账的起点。

策略 B：容器委托 + 手写上溯

监听器只有一个。成本从绑定端挪到了分发端：每次点击要从 event.target 沿祖先链上溯到容器，逐层做一次选择器匹配。在 IE8 上这条分支要换成 attachEvent、目标从 window.event.srcElement 取，兼容层的体量正是这个策略”代码复杂度高”的来源。

策略 C：jQuery 委托

一行，监听器同样只有一个，匹配和浏览器差异都交给库。on 的委托形态 2011 年底就在 1.7 里定下来了，到 1.11 参数形状没有任何变动，所以它可以当作 2014 年默认答案——前提是 jQuery 已经在页面里。

策略 D：$.live

版本事实要写清楚：live 是 1.3（2009 年）的旧物；1.7 引入 on 的同一年它被标记废弃，实现退化成”绑在 document 上的 on“；1.9（2013 年初）连人带机制一起删除。本文写作时手里是 jQuery 1.11，live 一行都跑不起来。它为什么慢：1.9 之前的实现里，每次点击都要从 target 一路走到 document，沿途靠挂在元素上的 dataEvents 处理器清单逐个试选择器；1.7 之后旧机制拆了，但”绑在最远处”这个结构没变，冒泡链依旧最长、候选清单是全页共享的。它和策略 C 的绑定数量相同，分发的账却明显更贵，还要额外背一笔迁移债——迁移成本不在改签名（一行搜索替换），而在容器从 document 上移到稳定祖先、die 换成带命名空间的 off、原来依赖”全页点击都被接住”的逻辑重新走查这三件事。清单在旧文里写过，这里只保留结论：live 是欠债写法，新项目禁用，存量项目按升级阻塞项处理。

这张表是定性的，数字在哪一档，下一节用测量说话。

计时方法与测量口径

先交代环境和量法，免得数字被当成权威基准引用。环境是当时在 Chrome 30（2014 年 7 月发布的版本）与一台装着 IE8 的 Windows 虚拟机上的手工计时，jQuery 版本 1.11.1，单台机器，跑十次去掉最高最低取中间值。所有结论只认量级，小数点后的数字没有意义。

绑定的量法：列表渲染完成到绑定语句返回之间的耗时，DOM 构造不计入。分发的量法：createEvent 造一个同步派发的 click，在处理器入口打点，与派发调用之间取差。毫秒级时钟量不出亚毫秒事件，所以分发一律循环派发一千次再除以一千；IE8 的 fireEvent 不保证沿链冒泡，这条路走不通，那一侧改成手工连点取差值，只和 Chrome 侧比量级、不比小数值。打点统一用 new Date().getTime()：console.time 在 Chrome 30 的工具里已经可用，但 IE8 的开发者工具没有，两边写同一份手工打点代码，避免工具差异混进结果。performance.now 在 IE8 上不存在，从头到尾没考虑过。

顺带交代这份测量的局限，免得数字被过度引用。虚拟机里的 IE8 计时受宿主调度影响，同一段代码两次结果差三成是常态；Chrome 首次执行的即时编译开销会污染第一轮，所以每组数据都跑满十轮再取中位；GC 暂停偶尔混进绑定阶段的尾部测量，处理办法是把明显离群的那一轮整轮作废。也正因为误差项这么多，笔者只把结果写成”哪个量级”，任何精确到小数点的表述在这套手工口径下都是假精确——表格里的区间是复测后仍然稳定的那部分，量级差在一倍以内的两栏，实际上应当视为”测不出差别”。

最后对齐旧账：二月那篇测得 jQuery 逐个绑定约 90 - 130 ms、容器委托 1 - 3 ms。这次把原生拉进同一框架，原生逐个绑定在 Chrome 30 上比 jQuery 版略快一些，但与委托仍是百倍量级的差距——旧结论扩大样本后依然成立。

三句话读这张表。第一，收益全部集中在绑定与重建阶段：IE8 上首绑 300 - 600 ms 对 10 ms 以内，是用户唯一感得到的差距；列表每被筛选重写一次，逐个绑定就要把这笔账再付一次，委托一次付清。第二，分发阶段委托是付钱的一方：多出来的是一次上溯加一次匹配，浅容器场景循环平均下来在亚毫秒量级，按用户一天几百次点击累计，也摸不到一秒——这点代价不值得为它放弃委托，但也不该被”委托全面更快”的说法掩盖。第三，”N 大且交互频繁时委托必赢”是常见高估：真正让分发的账变可观的是三件事——冒泡链很深、同容器挂的选择器种类多、高频事件参与委托。N 大只保证绑定端收益大，分发端好不好，取决于上面这三件事，和 N 无关。

B 与 C 的分发差异同样在量级内：手写上溯只做一条 selector 的判断，jQuery 沿链匹配还要过事件表筛选。但换到的是捕获开关、attachEvent 归一化、this 修正这些自己维护的代码，几百字节换几十行——项目里已有 jQuery 就没必要省，这一层的取舍是工程问题不是性能问题。

内存这一栏表格里没给数字，因为它只能定性观测：Chrome 30 的开发者工具 timeline 里能直接数出堆在页面上的监听器个数，策略 A 是一千，B、C、D 都是一个；IE8 侧没有这种面板，只能挂任务管理器看进程内存曲线，逐个绑定那一版从首绑起就抬高了一截，反复重建列表时台阶还在往上走。至于解绑之后曲线为什么不回落，那是《DOM 事件移除与内存泄漏》里讲过的引用链问题，本文不重复，只需要带走一个选型层面的事实：监听器个数直接决定这条内存账的厚度，这正是”减少事件绑定”这个标题在本篇语境下的全部含义。

场景选型表

把四种策略放回具体场景。推荐栏里 A 表示逐个直接绑，C 表示 jQuery 容器委托，B 表示无库时的原生委托。

千行列表，整表重渲染 C；无库则 B 一次绑定，重建免重绑，IE8 首屏差距最大

两条补充。没引 jQuery 的页面里只有 A、B 两个选项，B 的兼容层要自己写全套，节点不过百就别为难自己。移动端 Zepto 1.1.x 的 $(document).on(type, selector, fn) 与 jQuery 委托同形，上面这张表可以直接搬，结论不变。

反面结论：什么时候不要委托

选型表的反面单独拎出来讲，这节才是本文最容易踩空的地方。

其一，容器挪不近、链很深。每次点击都要从 target 上溯到委托容器，匹配代价与深度成正比。业务组件把一行数据包进七八层包装 div、容器又只能放在更外圈时，分发的账会反超绑定的账——此时要么重排结构把容器拉近，要么退回直接绑。委托省的是监听器个数，不是上溯层数。

其二，focus、blur 一族。冒泡问题旧文已经讲透，这里只留一句结论：焦点类事件和 change、submit 一样直接绑。IE8 没有捕获可走、Firefox 到 2014 年还不支持 focusin，两条兜底路各断一半，委托方案凑不齐跨浏览器。

其三，需要 mouseenter 语义的场景。原生层面这对事件不走传播链，委托无从谈起；库的模拟版靠 mouseover 加 relatedTarget 判断，容器内鼠标每跨一次元素边界就触发一次匹配。千行列表上用户按住滚动条来回扫，这份开销是实时支付的。行悬停先用 CSS :hover 解决，JS 是最后手段。

其四，一个容器混了很多 selector。三个模块各在同一条容器上挂五六个委托，每次点击处理器都要按绑定顺序把候选清单过一遍。委托的收益建立在”种类少”之上，种类一多，先变贵的是分发端。解法是按模块拆容器，让每条委托的归属清晰，而不是继续往上堆。

与分片渲染、虚拟滚动的分工

最后摆正位置：委托管的是”绑多少个监听器”，不管”渲染多少个 DOM 节点”。1000 个 li 的绑定从 1000 个降到 1 个之后，这 1000 个节点的创建、布局、绘制成本一分没少——那是分片渲染的账：定时器分批插入、按滚动位置做视口切片再补节点。2014 年还没有成熟的虚拟滚动库，自研前身在《大列表渲染优化思路》里整理过。三类手段的分工排一条线就清楚了：先控节点数量，再控监听器数量，最后控事件分发频率；它们解决的不是同一个问题，只做一个都别宣称列表优化完成。

小结

给三条可以直接抄进团队规约的结论。第一条，一锤子判据：容器内交互节点超过一百个，或内容会被渲染整段重建，就绑到最近的稳定容器上（有库用 jQuery 的 on，无库用原生双分支委托）；否则直接绑，不为可忽略的绑定收益去付分发的复杂度。第二条，范围限定：change、submit、焦点类事件，以及有掐冒泡习惯的第三方组件内部，一律直接绑；行 hover 先 CSS。委托只适用于 click 一族、容器挪得近、同容器 selector 种类在个位数的场景。第三条，先测再写规约：绑定耗时用手表式打点量首绑与重建，分发耗时用循环合成事件取平均，只认十倍数级的差异，亚毫秒的”提升”不进结论；存量 live 按升级阻塞项排期清掉，移动端 Zepto 的委托签名同形，规约直接复用。
