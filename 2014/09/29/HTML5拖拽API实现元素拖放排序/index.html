HTML5 拖拽 API 实现元素拖放排序

本文属于《HTML 与 CSS》第 14/62 篇
上一篇系列目录下一篇

浏览器原生那套拖放 API（Drag and Drop）写起来只有几个事件，真跑起来却很容易卡：拖动一次能触发上千次事件，跟着鼠标读一遍布局就是一次强制同步重排，落位时删了整块重建更是雪崩。本文不谈怎么用鼠标事件手工实现拖拽（那条路笔者另一篇旧文写过），只谈原生 API 本身：事件链每一步必须做什么、dataTransfer 有哪些硬限制、高频 dragover 下的布局读写怎么挪走、落位用哪种 DOM 操作最省，以及 2014 年这个时间点上移动端到底能不能用它。适合准备给后台加一个”拖一拖改顺序”、又不想拖完一下卡半秒的同学。

先把事件链跑通，再看它贵在哪

HTML5 拖放的核心是给元素加 draggable="true"，然后听一串事件。注意 li、div 默认都不可拖，只有 a 与 img 默认可拖，这一点漏掉的话后面所有事件都不会触发。完整时序是这样的：

sequenceDiagram
    participant U as 用户
    participant S as 被拖元素
    participant T as 目标容器
    participant W as 浏览器
    U->>S: 按下并移动
    S->>W: dragstart（写数据、设 effectAllowed）
    W->>S: drag（可选，极少用）
    U->>T: 拖到目标上方
    T->>W: dragenter（必须 preventDefault）
    loop 拖动过程，每帧多次
        T->>W: dragover（必须 preventDefault、设 dropEffect）
    end
    U->>T: 移出目标
    T->>W: dragleave
    U->>T: 松手
    T->>W: drop（此处才能 getData）
    W->>S: dragend（无论成败都会触发，收尾在这）

链条里有两件事是”必须做，否则整条链断掉”的。第一，dragenter 和 dragover 一定要调用 preventDefault()，它们的默认动作是”不接受放置”，不阻止就等于告诉浏览器这里不能放，drop 永远不会触发；在 addEventListener 的回调里 return false 是不生效的，别和 jQuery 的绑定搞混。第二，Firefox 在 dragstart 里若一次 setData 都没调用，拖拽干脆不会开始，而 IE 9 及更早版本连 setData 的类型都要挑着写。

effectAllowed 与 dropEffect 是一对，浏览器取它们的交集来决定光标旁边那个小符号，交集为空时光标直接变成禁止，用户会以为这里不能放：

属性 设在哪儿 可取值
effectAllowed dragstart 里，dataTransfer 上 none、copy、link、move、copyLink、copyMove、linkMove、all、uninitialized
dropEffect dragenter / dragover 里，同一个对象上 none、copy、link、move

排序场景两边都给 move 就行。这两个属性只影响光标的提示符号，不影响逻辑，别指望用它们限制谁能放。

2014 年的桌面现状是：Chrome、Firefox、Safari 都实现了完整链条，IE 9 与 IE 10 可用，IE 8 完全没有；setDragImage 前三家有，IE 全系列没有。看着一片大好，但这一套在手机上根本不存在，第 7 节单独说。

现在说”贵在哪”。上面那个 loop 是全文的题眼：dragover 不是”进入目标时触发一次”，而是拖动过程中持续派发——鼠标每动一下就有一批，鼠标不动只要按键还按着，WebKit 也会每隔十几毫秒补一次。实测一次两秒钟的拖动，dragover 触发 1500 次以上很常见；dragenter / dragleave 因为路径要穿过每一行的子节点，次数还要翻几倍。回调里任何一点开销都会被这个乘数放大几十倍，这就是原生拖放”写着简单、跑着卡”的根源。

坑一：dragenter 与 dragleave 的高亮闪烁

第一个坑在视觉反馈上。你想给”可以放在这里”的容器加个高亮边框，实现是 dragenter 加 class、dragleave 去掉 class。但这两个事件和 mouseover / mouseout 一样会穿透到子元素：鼠标从 li 移进它内部的 span，容器上就先收到一个 dragleave 再收到一个 dragenter，高亮闪一下。每行有图标、有文字、有删除按钮时，一次拖动能闪几十次，看着像坏了。

另一种看起来更优雅的做法是不监听 dragleave，只在 dragover 里判断 relatedTarget 还在不在容器内。思路可行，但 2014 年不推荐：部分内核在拖放事件里根本不填 relatedTarget，拿到的是 undefined 或 null；目标本身是子元素时还得自己写”向上找容器”的循环（IE 9 没有 closest）。判断错了表现为高亮该消不消，比闪烁更难查；计数器笨一点，但只依赖”事件成对”这一条，可靠性高得多。

坑二：dataTransfer 的读取时机被安全策略限制

第二个坑是设计约束层面的，也最容易踩：dataTransfer.getData() 只在 drop 里能读到值，在 dragstart、dragover、dragenter 里读回来一定是空字符串。这不是 bug，是规范里的安全限制——拖拽期间允许页面读被拖数据的类型清单（types 只读数组），但不允许在放置之前读到内容，防止页面偷听别的窗口正拖着什么。

这条限制对性能设计的直接影响是：拖动过程中要用的数据，必须自己存在闭包或模块变量里。排序需要知道”现在拖的是哪一行”，在 dragover 里调 getData 只会拿到空串，然后回头去查 DOM，白花一次开销还算错位置。正确写法是 dragstart 里把引用扣住：

性能主线：dragover 里的布局读写必须挪走

前面铺垫完，这里才是本文的正题。绝大多数”拖一下卡一下”的原生拖放，都栽在同一行代码上：在 dragover 回调里调 getBoundingClientRect() 或读 offsetTop 来判断该插在哪儿。

为什么贵？dragover 是每帧派发好几次的高频事件，而 getBoundingClientRect() 这类几何属性是”读取即要求布局是最新的”。只要上一次 dragover 改过样式或结构——比如把占位符插进了列表——这一次读矩形就强制浏览器同步跑一遍 layout，把本该攒到帧末的批量计算提前塞进事件循环。读写交替十几次，一帧就没了。Chrome 34 的 Timeline 打开看看，未优化的实现里 dragover 上挂着密密麻麻的 Layout 记录，括号里是整个容器的尺寸。

优化只有一句话：把布局的读从事件里搬走，事件里只做数组查表。具体两步。

第一步，矩形缓存。dragstart 时把所有行的矩形一次读完存进数组，之后 dragover 只在这个数组上二分。数组按 top 单调递增，天然有序，行高不等也不影响。前提必须说清：拖动过程中不能动任何影响布局的东西，所以被拖行只改 opacity（不触发重排），落点指示用一条脱离文档流的虚线，坐标直接从缓存来。这样缓存在整个拖拽期间都有效，一次 dragstart 读一遍，代替原来上千次读。

第二步，requestAnimationFrame 节流。事件只算出”落点应该是第几个位置”，改样式排到下一帧；这一帧内落点没变就一帧都不排。IE 9 没有 rAF，用 16 毫秒的 setTimeout 顶上即可。

这段代码里唯一剩下的”读”是 hit() 里的数组访问：dragover 回调里既不碰几何属性，也不写 DOM，Timeline 中的 Layout 记录会掉到接近零。

两个失效条件要交代。其一，缓存存的是视口坐标，position: fixed 的指示线正好也用视口坐标，两边对齐还省掉滚动量换算；可一旦列表放在可滚动容器里又做了”拖到边缘自动滚动”，滚动后缓存立刻作废，得在滚动回调里重新 measure()——自动滚动的次数比 dragover 少几个量级，重读不亏。其二，如果产品要的是”跟手插入”（拖动时真实节点马上让位），结构每帧都在变，缓存必须每帧重建，这时退一步：仍用 rAF 把”读全部矩形”和”改结构”分成两批做，绝不在同一个回调里读写交替，帧率照样能救回来不少。

落位方式的选择：移动节点远比重建便宜

拖完之后要把行放到新位置，这一步有三条路，代价差别比想象中大：

做法 代价 事件绑定 结论
insertBefore 移动已有节点 只有被移动的节点及其后续兄弟需要重新布局 完全保留 首选
拼 innerHTML 重建整块 整容器子树销毁重建，样式重算，图片与图标重新请求 全部丢失，只能靠委托或重绑 只在首次渲染时用
交换 class 或改序号属性 结构不变，只改属性 保留 视觉顺序并没有真的变，需要重绘才生效

insertBefore 便宜的关键在于它是”搬”不是”造”：节点对象还是同一个，绑在它上面的事件监听器、data-id、展开状态全都不动，浏览器只在兄弟链路上摘一次插一次，重排范围限制在容器内部，也不会让图片重新请求、不会让滚动位置跳动。相比之下 innerHTML 重建整块，行一多那种”叮”一下的停顿在 IE 10 上尤其明显。批量插入该怎么写，《DOM 增删改查与文档碎片 DocumentFragment》已经说透；改样式属性引起的大范围重排，见《DOM 操作性能：批量插入与重排优化》里的案例。

第三条路（不动结构，只给每行改 data-order）看着最省，实际只是把排序推迟到下一次渲染，屏幕上的顺序并不会变——2014 年想用 CSS 表达顺序，只有 IE 的 -ms-flex-order 和各家带前缀的 box 属性勉强可用，不值得依赖。合理搭配是”落位用 insertBefore，顺序数据从 DOM 现取”：

触屏上没有这套 API

本文最要紧的结论在这里：截至 2014 年 9 月，HTML5 拖放在手机浏览器里完全不存在。iOS Safari 上你在 div 写满 draggable="true"、绑好 dragstart，一个事件都不会触发；Android 原生浏览器（含 4.4 刚换上的那个 Chromium WebView）同样没实现。桌面主流内核都支持，移动两大平台一个都不支持——这个断层不是版本新旧问题，是压根没做。所以任何要覆盖手机和平板的产品，都不能把原生拖放当主路径；移动端只能用 touch 事件自己模拟，长按接管与页面滚动争夺那套细节，笔者的《DOM 拖拽排序的实现方案》写过，不再重复推导。

键盘与无障碍：别只给拖拽一条路

最后一个常被忽略的开销项是可访问性。原生拖放依赖”按住并移动指针”，纯键盘用户完全无法操作；2014 年的屏幕阅读器对 draggable 与拖放事件链的支持基本为零，规范里那几个 ARIA 拖放角色（grabbed、dropeffect）浏览器和读屏软件都还没跟上，写了也没人消费。所以务实的做法不是硬凑无障碍语义，而是并排提供一条键盘路径——它正好和触屏的按钮降级共用一套代码。

小结

原生拖放在 2014 年的可用性是一条明确的分岔：桌面 Chrome、Firefox、Safari、IE 9/10 能跑完整条事件链，iOS Safari 与 Android 原生浏览器一律不支持。四件事必须记住：draggable="true" 不能漏、dragenter 与 dragover 要 preventDefault 否则收不到 drop、dragenter / dragleave 用计数器兜住闪烁、getData 只能在 drop 里读所以拖动期间的数据得存闭包。性能上只有一条主线：dragover 每帧好几次，回调里绝不能再读几何属性——矩形在 dragstart 缓存好做二分，样式写入挪进 requestAnimationFrame，落位用 insertBefore 搬节点而不是 innerHTML 重建。

场景 是否适合用 HTML5 拖放 理由
公司内部后台的桌面排序（Chrome / Firefox / Safari / IE 9+） 适合 零依赖，六七十行搞定
需要跨浏览器窗口、跨页面、从桌面往页面里拖 只能用它 手工鼠标事件方案做不到跨文档
覆盖手机、平板的 C 端页面 不适合 移动内核没实现，只能 touch 模拟或按钮降级
要兼容 IE 8 不适合 IE 8 完全没做，只能走鼠标事件或 jQuery UI
需要精细跟随动效、惯性、动画落位 不适合 影像由浏览器绘制，只有一张图可换
跨 iframe 传结构化数据 谨慎 dataTransfer 类型受限，复杂数据走全局变量或服务端
纯键盘或依赖读屏的用户 必须给后备 屏幕阅读器对拖放支持接近零

一句话结论：把它当桌面后台的锦上添花，同时准备好按钮路径，性能和可用性都稳。
