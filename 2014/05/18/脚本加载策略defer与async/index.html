脚本加载策略：defer 与 async

<script> 标签上其实只有三个与加载有关的写法：什么都不加、加 defer、加 async，再加上一个不走标签的动态注入。看上去很简单，但执行时机、顺序保证、浏览器差异搅在一起，项目里”本地好好的、线上偶发报错”的脚本问题多半出在这里。本文把这四种写法各自的”什么时候开始下载、什么时候执行、和 DOMContentLoaded 谁先谁后”讲透，配一张时序对照表和一段可直接抄走的按序加载代码，最后给出一张决策表。适合被统计脚本坑过的入门同学，也适合想搞清楚 defer 到底能不能用的人。

默认脚本：解析器一停，全线等待

浏览器解析 HTML 时是边下载边构建 DOM 的：读到一个开始标签就建一个节点，正常情况下解析不会等任何东西。唯一例外是同步的 <script src>。解析器遇到它必须立刻停下来，发起下载，等文件到货并执行完毕，才继续解析后面的标签。为什么要这么霸道？因为脚本里一句 document.write() 就能往当前位置插入新标记，甚至可以 document.write('<sc' + 'ript src="b.js"></scr' + 'ipt>') 再拖一层依赖进来。解析器无法预知脚本会做什么，只能把整个世界暂停，等它执行完再恢复。

这就是把脚本挪到 </body> 之前的由来：让 HTML 先解析完、首屏先渲染出来，脚本排最后再加载。这是 HTML4 时代通行的做法，成本是页面底部的交互要等整页解析完才可用。另有一篇旧文《资源合并与压缩的收益分析》解决的是”把更少的字节送到浏览器”这一段，它管的是体积与请求数，管不了执行时机——合并得再好的脚本，堵在头部照样把整页解析拦停。本篇只谈时机，不谈字节。

defer：下载不挡路，执行排队到解析结束

defer 不是 HTML5 的新东西，HTML4 规范里就有它，语义是：这个脚本可以异步下载，不阻塞解析，但执行要推迟到文档解析完成之后、DOMContentLoaded 事件触发之前。多个带 defer 的脚本之间严格按文档书写顺序执行——先写先跑，哪怕它的网络响应到得更晚。这一点让它成为”有依赖关系的业务代码”的天然选择：jQuery 版在上、插件版在下，执行顺序就不会乱。

当年的支持矩阵比想象中碎：

  • IE 从 4.0 起就支持 defer，是各家浏览器里最”原生”的，但早期版本的实现在细节上有出入，IE9/10 对规范里”不保证相对 DOMContentLoaded 的顺序”还留了备注，实际观察都执行得很早。
  • Firefox 直到 3.0 都把 defer 当普通同步脚本处理，3.5（2010 年）才重写成符合规范的行为。
  • Safari 5、Opera 9.5 之后的版本陆续支持；Chrome 起步早，但早期版本对多个 defer 脚本的执行时机与规范有偏差，实践中要靠测试说话，不能写一句”所有浏览器都支持”就完事。

更麻烦的是动态注入场景：用 createElement('script') 插入的脚本，给它设 script.defer = true 在多数老浏览器里基本无效——动态脚本没有”文档顺序”可言，浏览器也不会在 DOMContentLoaded 前特意等它。IE 系对动态脚本的完成通知走的是另一套机制：script.readyState 从 loading 到 loaded 再到 complete，配合 onreadystatechange 判断 /loaded|complete/ 才能确认执行完毕，而且命中缓存时事件可能一次都不触发，这是 defer 在注入场景不可靠的根源，下一节动态加载的代码里会给出兜底写法。

async：下载不挡路，谁先到谁先跑

async 是 HTML5 新增的属性，语义只有半句话的区别：下载不阻塞解析，但下载完成立即执行，不等解析、不等别人。于是它有三个推论：执行时机完全由网络决定；多个 async 脚本之间不保证任何顺序；它可能在 DOMContentLoaded 之前跑，也可能在其后跑，甚至可能在文档还解析到一半时就把主线程抢走——脚本执行时 DOM 树建到哪一步，你无法预测。

支持面同样要泼冷水：async 在 Chrome、Safari 5、Firefox 3.6、Opera 10.5 就已可用，但 IE 系到 IE9 才支持，且 IE9 只认动态创建的 script 元素上设置的 script.async = true 属性，写在 HTML 标签里的 async 要到 IE10 才被识别。所以 2014 年写 async 的前提是：老 IE 用户会退化成同步加载，你的页面要能接受这个结果。

五种写法的时序对照

顺带说两个”注入不执行”的冷知识。第一种，innerHTML 里塞 <script> 不会执行：innerHTML 用的是片段解析器，这样造出来的 script 元素带着”已启动”标记，插进文档也不会触发执行，这是规范行为，别指望哪个浏览器放水。第二种，document.write 写入的 script 标签反而会执行——因为它把内容交回给真正的文档解析器，等于往正在解析的流里加料；但代价是同步阻塞、解析完之后再调用还会把整个文档重写一遍。这也是当年广告代码让人又爱又恨的原因。

与首屏的关系：先定位置，再定属性

<head> 里放阻塞脚本的代价在瀑布图上非常直观：HTML 才解析几 KB 就停住，白屏时间被脚本的下载加执行全程占满。旧文《首屏时间优化实战》实测过三个第三方同步脚本压住 CSS 和 HTML 的场景，挪走之后白屏时间大幅缩短；《首屏渲染优化手段汇总》也已经把”脚本放底部、defer/async“列进了手段清单。本篇的补充是：位置解决”尽早可见”，属性解决”尽早可交互与执行秩序”，两件事要分开决策。

据此可以定出三条实践规则：第一，同步脚本只留一个入口 bundle，放 </body> 之前——这个 bundle 里 jQuery 和业务代码合并保序，约束是它必须包含首屏交互所需的全部依赖；其余按页面位置能用 defer 的都标 defer，反正它保证顺序。第二，与首屏无关的独立库（分享按钮、富文本编辑器）不占标签，用动态注入按需触发，点击后再加载也行。第三，第三方统计用 async 或动态注入，但上线前必须确认它不依赖你的任何全局变量；依赖就用 readyState 判断加轮询做”依赖判定”，别赌顺序。

对了，SPDY 已经有些人在试，但主流仍是 HTTP/1.1，并发连接限制还在，”减少请求”和”控制时机”两条线一条都不能松。

坑与注意事项

  • IE9 以下的行为差异要单独回归：defer 在 Firefox 3.5 以前会被当同步脚本，async 在 IE8 及以下完全被忽略、IE9 只认属性写法，标签写法要等到 IE10。同一个页面在 IE8 里可能悄悄退回全同步。
  • defer 和 async 同时写在一个标签上时，支持 async 的浏览器以 async 优先——等于你写了个保序脚本但拿不到保序。这个组合只有一种正当用途：给支持 async 的新浏览器抢速度，其余浏览器退到 defer 再退到普通，前提是这个脚本本来就不依赖顺序。
  • async 脚本里没有 DOM 承诺，开头第一件事是读 document.readyState 判断现在能不能动手；被 defer 的脚本虽然执行时文档已解析完，但如果它依赖的节点是别的 async 或动态脚本注入的（评论框、分享按钮），仍需等待或重试，defer 管不了别人。关于 DOMContentLoaded 与 load 的语义，旧文《DOM contentloaded 与 load 的区别》已有完整推导，本文不再重复。
  • 第三方跨域脚本抛错时，window.onerror 只能拿到一句干巴巴的 Script error.，没有堆栈。想让监控看到详情，要么让对方给你的域名配 Access-Control-Allow-Origin 并在 script 标签上写 crossorigin（当年只有部分新浏览器支持），要么退而求其次把统计域和业务域做成主域相同的子域，脚本里设 document.domain 互通。
  • defer 只对外部 src 脚本有意义，内联 <script> 写 defer 直接被规范忽略；老 Firefox 会把带 defer 的文档脚本扔进执行队列尾部，多个 defer 之间的相对顺序要自己回归确认。

决策表：什么脚本用什么加载方式

脚本类型 推荐写法 理由
入口 bundle（jQuery + 业务，有依赖链） 同步，放 </body> 前，或全标 defer 需要保序且尽早可交互
依赖入口库的业务扩展模块 动态注入，走串行队列或加载器 不进首屏关键路径，依赖到位才能跑
非关键 UI 库（分享按钮、轮播增强） defer，或用户触发时再注入 不阻塞解析，不需要就永不加载
第三方统计 async（老 IE 接受退化），或动态注入 + 依赖判定 独立、无 DOM 依赖，越早开始发送越好
广告 iframe 隔离，或动态注入兜底超时 内部常含 document.write，必须切断阻塞与覆盖

小结

<script> 的三种标签写法加动态注入，对浏览器来说是四台不同的调度器：同步的停下一切，defer 下载插队、执行排队，async 先到先跑，动态注入是脚本自己发起的第二场下载。选型的依据只有一条：脚本之间有没有依赖、首屏等不等它。入口保序、独立放飞、注入要回调兜底 IE、async 前先查依赖——把这四条对上号，时序表上的格子就能直接填进项目。合并与压缩省的是字节，加载策略省的是等待，两件事都做到，首屏才算真的快。
