移动端点击 300ms 延迟与解决方案

去年年底那篇《移动端性能优化特殊点》把”触控响应”列为移动端优化的第一顺位，当时只给了结论没给数据。这半年做了两个移动专题页和一个 Hybrid 列表页，把点击延迟从量测、选型到上线验证完整跑了一遍。与今年三月那篇《FastClick 解决点击延迟》的源码与架构角度不同，本文是同一问题域的性能与调优角度：延迟给整条交互链路添了多少成本、几条解决路径各自的适用边界与代价、上线后怎么用打点证明收益。适合被”点了没反应”困扰，又需要在评审会上说清取舍依据的同学。

先把延迟量出来：真机时间戳打点

要谈优化，先得把数字摆上桌。测法很简单：在同一个元素上分别记录 touchstart 与 click 的时间戳，相减就是这个环境给你的手势等待成本。

两个细节值得提醒。其一，别用 alert 读数：alert 会堵住主线程，你观察到的是弹窗动画时间而不是事件时间，笔者的第一版测试就是这么废掉的；直接往 DOM 写文本，或用《移动端调试工具与实践》里的远程日志把数据发回桌面端。其二，event.timeStamp 各家基准点不一样（iOS 上它是相对页面起点的毫秒数，某些 Android WebView 里带自己的纪元），跨机型比较统一用 Date.now() 打墙钟时间戳更稳妥。

下面是真机测到的分布，每个环境连点 30 次取中位数，括号里是最差值。页面统一用 width=device-width 且允许缩放：

环境 touchstart 到 click 的中位间隔 双击缩放窗口 备注
iOS Safari 5.1（iPhone 4S） 318 ms（356 ms） 固定约 300 ms 数值最稳定，几乎无抖动
iOS Safari 6.1（iPhone 5） 312 ms（341 ms） 固定约 300 ms 与 5.1 无实质差别
iOS Safari 7.0（iPhone 5） 305 ms（338 ms） 固定约 300 ms 设 user-scalable=no 也不变
Android 2.3 原生浏览器（G7） 402 ms（689 ms） 各家 ROM 不同，偏大 长尾严重，惯性滚动未停时更差
Android 4.0 到 4.3 原生浏览器 306 ms（372 ms） 约 300 ms WebView 内数值与浏览器一致
Android 4.4 WebView（Chromium 33） 297 ms（330 ms） 约 300 ms 禁止缩放时这一档接近 0
Windows Phone 8（IE10） 310 ms（368 ms） 约 300 ms 声明 -ms-touch-action 后掉到 30 ms 内
Firefox OS 1.1 无等待 无双击缩放 不需要处理

从这张表能读出三件事。第一，”300ms”是典型值而不是定值，同一环境内 30 次就有 60 ms 上下的离散，跨 ROM 的 Android 2.x 能飘到 700 ms。第二，双击缩放的判定窗口各家实现不同，国产 ROM 上我们遇到过明显更长的等待，所以别把目标定成”消掉 300 ms”，要定成”把这条链路的 P95 压进 100 ms”。第三，同样是 300 ms，杀伤力取决于后面还有多少耗时——纯展示页无所谓，一个要跟网络请求的确认按钮就很难受，这也是后文要拆四段的原因。

延迟的根因，以及一个不该用的”快招”

根因一句话：触摸屏上要区分单击与双击缩放，浏览器在第一次 tap 结束后不敢立刻派发 click，必须留着判定窗口看用户会不会再来第二下。这个等待发生在原生层，网页代码拦不住；iOS Safari 与 Android 浏览器都有双击缩放，所以两边都得等。它与 viewport meta 的关系是：页面允许缩放，浏览器就认定这个手势有用途，老老实实等满；页面禁止缩放，手势失去意义，浏览器才有资格缩短或跳过等待。iOS 的问题恰恰在于它的等待和 viewport 设置脱钩，禁止缩放照样等满，三个版本我们都验证过。

于是有人会在 viewport 上做文章：

笔者明确不推荐这条路。收益只在部分环境成立（Android 4.4 之后新版 Chrome 对禁止缩放的页面确实跳过了等待，但当时这套内核装机覆盖面很有限，iOS 与大量 Android 4.3 以下机型完全无效），代价却是实打实的：双击缩放和双指缩放是低视力用户与老年用户读小字的主要手段，我们的用户反馈里就有”字号小、要点两下放大看”的诉求。禁掉缩放等于把一小部分人彻底挡在页面外面，与 WCAG 里”文本可放大到 200% 而不损失内容与功能”的精神相反。页面排版太碎，正确做法是改排版，而不是把用户的放大镜砸掉；maximum-scale=1 同样不该被当成性能手段。

解决路径清单：五条路各自的适用边界

这是本文的主线。摆得出来的选项有五个，逐个说清它们快在哪、代价是什么、什么场景别用。

直接用 touchstart 响应

理论最快：手指一落下就执行动作，手势等待整段被跳过，代价是误触。三个必踩的坑：滚动起始时手指按下就会触发（用户本想滑动列表，结果点了删除）；长按查词或复制之后抬手又触发一次；系统手势打断时 touchend 根本不会来，touchcancel 不处理就留下半截状态。所以”直接用 touchstart”落地形态应该是一套判定：touchstart 记录起点与时刻，touchmove 位移超阈值就放弃，touchend 才真正执行，并补上 touchcancel。

注意 preventDefault() 这一行。不拦的话一次按压会跑两遍 handler——我们的加购按钮就这么重复提交过一次订单。拦了之后又有新麻烦：:active 态与点击高亮受影响、原生表单控件的系统弹层叫不出来，所以这条路只适合自绘的按钮、卡片、菜单项，不适合 input、select、label、a。适用边界可以概括为：交互目标是可控的自绘元素，且你愿意为每个手势分支自己写判定。

Zepto 的 tap 事件

Zepto 自带 tap，内部同样在 touchend 上做判定，收益与风险都跟上面那套自制逻辑类似。坑在于滚动容器里它会静默失效（一次惯性滑动之后 tap 不触发），以及它合成的 click 与原生 click 打架——同一个 handler 绑两个事件名，就可能出现”点一次跑两遍”或”绑了不生效”。这些事故在《Zepto 移动端库实战》里逐个复盘过，此处不重复。工程上只记住一条：tap 与 click 不要在同一个元素上混用，团队里定死一个。

FastClick 类库

不重复源码，只讲工程侧。接入位置就一行 FastClick.attach(document.body)，放在 DOM ready 之后；靠冒泡覆盖动态插入的节点，脱离 body 的弹层要单独处理。它的影响面是整个 layer：所有 click 都要过它的手，业务代码一行不用改，这是相对自制方案最大的优点。代价是那张豁免名单归你维护——表单控件、日期选择器、iframe、video，以及任何你希望原生默认行为发生的元素都得加 needsclick，哪些必须放行、为什么放行，旧文里列得清楚。另外别和 Zepto 的 tap 叠用，同一区域也别和 -ms-touch-action 混配，两套机制互相踩脚很难查。

CSS 方案：touch-action

把声明写在 CSS 里让浏览器自己跳过手势判定，架构上最干净，可惜 2014 年这个时间点它只能用在一部分环境：

IE10 与 WP8 对 -ms-touch-action 支持完整，实测延迟从 310 ms 掉到 30 ms 以内，效果最好；Chrome for Android 当时只实现部分取值、还要开关，iOS Safari 完全不认。Android 4.4 之后新版 Chrome 对禁止缩放的页面会自动跳过等待，但那是 viewport 策略的副产品，不能当跨机型方案依赖。结论：它适合作为 IE 系与 WP 的专项补充叠加上去（没有副作用），不适合作为唯一手段。顺带一提，架构上更彻底的 Pointer Events 能统一 mouse 与 touch 两条链路，但那时只有 IE10 的私有 MSPointer 前缀实现，标准仍在候选推荐阶段，iOS 与 Android 均无实现，跨端代码指望不上。

单页容器：强交互界面交给原生

如果某个界面的交互密度高到要为每次点击抠这 300 ms，那它可能压根不该是 Web 页面。我们的详情页保留 H5，但把键盘、图片查看器和结算面板挪进原生壳走 JSBridge 调用，WebView 里的手势层整个绕开，延迟问题不复存在。这条路只在自家 App 容器内成立，通信与降级的设计在《JSBridge 设计与实现》里写过；代价是发版节奏被绑定、失去 URL 可分享性，属于产品形态决策而不是前端优化手段。

选型决策树

把上面的边界压缩成三个判据——是否需要双击缩放、触控目标是否在滚动容器里、目标机型分布怎么走：

判据里最容易被忽略的是第一个。图片查看器、地图、长文阅读页里，双击缩放本身就是功能，消掉延迟等于砍掉功能，这类页面只能往后三段去要收益。

300ms 之外：把”响应慢”拆成四段

用户说的”点击慢”从来不只是手势等待，完整链路是四段相加：

真实案例：去年一个”确认加入清单”的按钮，iOS 上从按下到界面变化要 700 ms 以上，最初所有人都以为是那 300 ms，接了类库后数字只降到 600 ms 左右——延迟根本不是主因。分段打点之后是这样：

分段 优化前 优化后 说明
手势等待 305 ms 40 ms 接入类库，唯一由浏览器决定的部分
事件处理 190 ms 22 ms handler 里对 40 个条目循环读写 offsetHeight
样式重排与绘制 90 ms 30 ms 改为先批量读、再切一个 class 批量写
网络与数据 120 ms（WiFi）/ 680 ms（3G） 同前，但界面先响应 原来是同步 AJAX，UI 被彻底冻住

第二行的问题最典型：handler 里为了算一个插入位置，每轮先读 offsetHeight 再改 className，读操作把待处理的样式改动强制结算成布局，循环 40 次就是 40 次同步重排，Android 4.1 实测 190 ms，改法即《减少重排与重绘的实践清单》里那条”先批量读再批量写”。第三行的同步 AJAX（xhr.open 第三个参数传了 false）更恶劣：请求没回来之前页面不响应任何输入，用户以为没点到会再点一次，于是又叠上 ghost click 与重复提交。改成异步、先给界面反馈，总耗时并没有减少，但用户感知完全变了。

结论直接决定优化优先级：先量四段，再决定要不要动 300 ms。事件处理段本身就有 200 ms 的话，接任何类库都是隔靴搔痒。

副作用清单与灰度回滚

提速的代价都藏在默认行为里，逐条过一遍我们项目里踩到的。

表单校验与焦点顺序。合成 click 让 blur 与 click 的相对顺序和原生不一致，依赖”失焦即校验”的逻辑偶发跑在校验之前，表现为报错文案闪一下又消失。处理办法：带校验的表单控件全部进豁免名单不提速，校验时机从 blur 改成显式的 submit，减少对顺序的依赖。

ghost click。合成 click 提前触发、原生 click 300 ms 后到货，如果 handler 里把当前元素从 DOM 移除，迟到的那一下会落到身后的元素上。机制与类库内部的防护，旧文《FastClick 解决点击延迟》已经讲透。工程侧只需记住一条产品规则：弹层关闭后不要立刻移除 DOM，先隐藏（visibility 或留一层遮罩），300 ms 之后再清理，这个习惯能挡掉绝大部分幽灵点击。

链接新窗口打开。target="_blank" 的 a 标签被合成 click 命中时，”打开新窗口”属于默认行为，而默认行为只对可信事件生效，结果就是点了没反应。把 a 标签进豁免名单，或显式跳转。

保留双击手势。图片查看器里我们自研了双击放大，加了提速层后两次 tap 被提前合成掉，自己的双击判定窗口随之失效。做法是在图片容器上不提速，自己实现监听：

灰度与回滚。机型差异太大，不可能一刀切。我们把开关做成远端配置下发、按 UA 分桶，本地缓存一份兜底：

收益怎么用数据证明

改造上线得有数字说话：把 touchstart 到 handler 首行的间隔当指标，采样上报，服务端算 P50/P95。

口径要说清楚，否则两组数字没法比：起点是 touchstart 触发时刻，终点是业务 handler 第一行执行；改造前后的采样窗口、机型分桶、过滤规则都得一致。别看均值，它会被长尾拉平；P50 说明典型手感，P95 说明最差体验，投诉基本都来自 P95。专题页上线两周后的结果：

机型分组 改造前 P50 改造前 P95 改造后 P50 改造后 P95
iOS 5/6/7 Safari 312 ms 402 ms 41 ms 96 ms
Android 2.3 到 4.3 335 ms 689 ms 52 ms 130 ms
Android 4.4 296 ms 380 ms 33 ms 78 ms
Windows Phone 8（CSS 方案） 310 ms 368 ms 28 ms 64 ms

同时必须看反向指标，只报延迟是耍流氓。我们盯三个：误触率（点击后 2 秒内返回或撤销的比例，改造后从 1.4% 涨到 1.9%，说明阈值偏灵敏，把容差从 8 px 调到 12 px 后回落到 1.5%）、表单校验失败率（持平）、加购提交重复率（同步 AJAX 改异步并加防抖后，从 0.7% 降到 0.2%）。数据来回调了两轮才稳住，这也是前面坚持做机型开关的原因——数字不对就关掉某个桶，不必回滚整个页面。

小结

300 ms 不是定值，它随环境在 300 到 700 ms 之间浮动，各家双击缩放窗口的实现也不一样，所以第一步永远是拿真机时间戳把四段耗时拆开量清楚，确认延迟在你这条链路里占多大比重。方案上，自制安全判定最可控但要自己兜住滚动、长按与 touchcancel；类库省事，代价是影响面铺满整层、豁免名单归你维护；-ms-touch-action 干净，但当时只在 IE 系与 WP8 成立；交互真正密集的界面应该交给原生容器。至于禁用缩放，收益只在部分环境成立，代价是老年用户与低视力用户失去放大手段，不该当成优化手段。选型看三个判据：是否需要双击缩放、目标是否在滚动容器里、机型分布怎么走。任何方案都会把成本换个地方落下——ghost click、默认行为偏差、焦点顺序变化，所以机型开关、URL 级回滚与 P50/P95 打点这三件套不是可选项，它们是这类改动能安全上线的前提。
