CSS3 animation 与 keyframes 动画实战

本文属于《HTML 与 CSS》第 47/62 篇
上一篇系列目录下一篇

上一篇文章《移动端页面切换动画》讲的是”切换”这个具体场景怎么用动画落地，那篇偏工程组合拳。这一篇换个角度：把 CSS3 的 animation 机制本身拆开看。我们不讨论”CSS 动画和 JS 动画谁更快”这种选型结论，那有另一篇专门写。本文要做的是讲清楚 @keyframes 这条时间轴是怎么被浏览器解析、插值、执行的，再顺着渲染管线推导出”哪些写法是安全的、哪些写法是在给主线程挖坑”。适合已经用过 transition、但一直没搞明白 animation-name 和 fill-mode 到底在干什么的同学。读完你应该能解释：为什么少写一个 duration 动画就不动，为什么 delay 期间元素会先跳到 from 状态，以及为什么当年移动端都拿 transform 而不是 top 做位移。

transition 的天花板在哪里

要理解 animation 为什么存在，得先把 transition 的模型讲透。transition 的本质是”两个已计算样式之间的一次插值”：你给某个属性设一个起始值，再通过 class 切换或 JS 改一个结束值，浏览器读取这两端的 computed value，在 animation-timing 规定的那条曲线（对 transition 来说是 transition-timing-function）上，把中间每一帧算出来。它的整个生命都依附在”属性值发生了变化”这件事上，没有变化就没有动画。

这个模型有三个绕不过去的天花板。第一，它只能表达”从 A 到 B”，无法表达 A 到 B 再到 C、回到 A 这种多关键帧的曲线。你想做一个”加载图标左右各摆两下再停”的效果，用 transition 就得靠 JS 串多个 setTimeout 分段设值，代码又脏又容易和真实帧率脱节。第二，它天然是一次性的，播完就结束，没有”循环”的概念，loading 那种要一直转的动画用 transition 做不了。第三，它没法在开始前就呈现起始状态，也没法在 delay 期间做点什么，因为 delay 对 transition 而言只是”延迟开始插值”，期间元素保持原样。

animation 做的事情，本质上就是把”时间轴”这件事从 JS 手里交回到 CSS。你不再描述”起点和终点”，而是直接在 @keyframes 里声明若干时间点上的样式，再交给 animation-* 这一组属性去决定播多长、怎么缓动、循环几次、正反交替、停在哪个状态。一旦动画跑起来，它的计算值不再依赖元素在 DOM 里”本来应该是什么样”，而是被关键帧接管。这是 transition 和 animation 最根本的分野：一个是”值驱动”，一个是”时间轴驱动”。

@keyframes 是怎么被解析的

@keyframes 是一条 at-rule，浏览器解析它的时候，会把里面每个关键帧选择器对应的声明收集起来，构造成一张”进度到样式”的表。

关于这套语法，有几个解析细节必须记牢。关键帧选择器可以是百分比，也可以是 from、to 这两个关键字，from 等价于 0%、to 等价于 100%；如果 0% 或 100% 缺失，浏览器会把元素在没有动画时的”底层值”当作那一端，也就是元素本该呈现的样子。同一份样式表里如果出现两个同名的 @keyframes，后声明的会整体覆盖先声明的，这和 CSS 层叠的”后来者胜”是一致的，别指望两个同名块能合并。最关键的一条容错行为：@keyframes 里的声明和普通规则一样要经过 CSS 解析器，任何非法声明会被单独丢弃而不影响同块内其它声明。比如你在关键帧里写 width: 100px 是合法的、会被采纳，但如果拼错成 wdith: 100px，这一行会被静默丢掉，动画里这个属性就当作没被关键帧控制，回到”底层值 + 插值”的处理。这种静默丢弃正是”动画效果不对劲但控制台什么都没报”的经典来源。

再说插值是怎么发生的。浏览器拿到当前动画时间进度（一个 0 到 1 之间的量），先定位它落在哪一段关键帧之间。上面 pulse 这条，如果进度是 25%，它落在 0% 和 50% 之间，于是浏览器把”这段的 timing-function”作用在这 25%→实际映射到 0→1 的局部进度上，然后对 scale(1) 和 scale(1.2) 之间做插值。注意”每一段用的是这一段自己的 timing-function”，你可以在关键帧里给某个 50% 单独写 animation-timing-function，让它前半段 ease、后半段 linear，这是 transition 完全没有的能力。至于插值本身，transform 列表按函数逐个对齐插值，颜色按 rgb 分量插值，长度按数值插值；如果一个属性的两端值”结构不匹配”（比如一端是 translateX(10px) 另一端是 rotate(10deg)），老浏览器无法对齐，会退化成离散切换（50% 之前显示起始、50% 之后直接跳到结束），而不是平滑过渡。这一点当年吃过亏：两端 transform 函数的种类和顺序要保持一致。

animation-name 与 @keyframes 靠标识符名字匹配。animation-name 写 none 或者写一个样式表里根本不存在的名字，动画就是不生效——它不会报错，只是安静地什么都不做。所以线上”动画没了”第一件事就是去核对 animation-name 拼写和 @keyframes 名字是否严格一致（区分大小写）。

animation-* 长写法逐个拆开

animation 的简写把一堆长写法打包了，但真正决定行为的永远是这些长写法。逐个说清楚。

animation-duration 是”跑完一次完整时间轴要多久”，默认 0s。这里埋着 2014 年最常见的一个 bug：只写了 animation-name 忘了写 duration，于是 duration 取默认 0，浏览器认为”动画瞬间完成”，结果就是你看到元素直接跳到最后状态或者根本没动，控制台无异常。排查动画不播，先看 duration 有没有给。

animation-timing-function 决定进度到插值系数的映射曲线，下面单独展开。

animation-delay 是”开始前的等待时间”，可以是负值。负 delay 的语义常被误解：它不会让动画”少等一会儿”，而是让动画在”过去的某个时间点就已经开始了”，等效于把时间轴向前跳过一段，直接从中途切入。做无缝循环或者错开相位时负 delay 非常好用。

animation-iteration-count 是循环次数，可以是小数（比如 2.5 就在半个周期处停住），也可以是 infinite，默认 1。

animation-direction 决定每次往返的方向，有 normal、reverse、alternate、alternate-reverse 四个值。normal 每次都从 0% 播到 100%；reverse 每次从 100% 播回 0%；alternate 是奇数次正常、偶数次反向（往返摆动的关键）；alternate-reverse 反过来。注意一个细节：换向的判定是”这一次是第几轮”，而 timing-function 在反向时也会被”镜像”，也就是 ease-in 反向后表现接近 ease-out，这点当年很多人调试来回摆动时觉得曲线”怎么变样了”就是它。

animation-fill-mode 是最容易被忽略却最容易出视觉 bug 的一条，它管的是”动画没在跑的时段里，元素借用的样式从哪来”。四种取值：none（默认，动画不作用时元素显示它本来该是什么样）；forwards（动画结束后，元素保持最后一帧计算出来的样式不回弹）；backwards（动画开始前的 delay 期间，元素就应用第一帧的样式）；both（两头都管）。这里要重点理解 backwards 和 delay 的配合：如果你写了 animation: pulse 1s ease 0.5s，在没加 fill-mode 时，前 0.5s delay 期间元素是”原样”的，delay 到点突然跳到 from，观感上”抖一下”。加上 backwards（或者 both）之后，delay 一开始元素就呈现 from 那帧的样式，过渡就顺了。入场动画几乎都应该用 both：进场前就藏在起始位置、结束后停在终态。

animation-play-state 只有 running 和 paused 两个值，默认 running，它是 JS 干预动画最轻量的开关——把 play-state 切成 paused，动画就在当前进度冻结，切回 running 就从冻结处继续。后面配合 loading 动画的暂停继续会用到。

简写的书写顺序是 name duration timing-function delay iteration-count direction fill-mode play-state，但真正会咬人的是”两个时间值”的区分规则：在简写里，第一个出现的 <time> 被当作 duration，第二个出现的 <time> 被当作 delay。也就是说 animation: spin 2s infinite linear 里 2s 是 duration 没问题，但如果你想加 delay，必须写成 animation: spin 2s linear 0.3s infinite，把 duration 放前面、delay 放后面，一旦你手滑写成 spin 0.3s 2s，duration 会变成 0.3s、delay 变成 2s，效果完全不对。这张顺序表建议贴在手边：

位置 含义 默认值 说明
1 animation-name none 匹配 @keyframes 名
2 animation-duration 0s 第一个时间值
3 animation-timing-function ease 曲线
4 animation-delay 0s 第二个时间值
5 animation-iteration-count 1 次数或 infinite
6 animation-direction normal 往返方式
7 animation-fill-mode none 前后态填充
8 animation-play-state running 暂停开关

缓动函数的原理与实现

animation-timing-function 的本质是一条”时间进度 → 数值进度”的映射。CSS 内置了几个关键字，linear 是恒等映射，ease 是 cubic-bezier(0.25, 0.1, 0.25, 1)，ease-in 是 cubic-bezier(0.42, 0, 1, 1)，ease-out 是 cubic-bezier(0, 0, 0.58, 1)，ease-in-out 是 cubic-bezier(0.42, 0, 0.58, 1)。真正值得讲的是 cubic-bezier 本身。

三次贝塞尔曲线在这条映射里有两个端点是固定的：起点 (0,0)、终点 (1,1)，横轴是”时间走过的比例”，纵轴是”数值变化的比例”。你能调的是两个控制点 P1(x1,y1)、P2(x2,y2)，写成 cubic-bezier(x1, y1, x2, y2)。控制点如何塑造速度，可以这样直觉地想：曲线在某处的斜率就是那一瞬的”数值/时间”变化率，也就是速度。P1 的 x1 偏大意味着开头要等很久才有变化（起步慢、加速后段），y 大于 x 的区域则代表”进度跑在时间前面”。四个点决定一条从 (0,0) 单调爬到 (1,1) 的曲线。

这里有一个约束必须理解清楚：贝塞尔作为时间函数，横轴（时间）必须单调递增，否则同一段时间对应多个进度，物理上说不通。CSS 因此强制 x1、x2 落在 [0, 1] 区间——一旦越界，整条 cubic-bezier() 非法，声明被丢弃。而纵轴 y 允许超出 [0, 1]，这正是”回弹/过冲”效果的来源：cubic-bezier(0.68, -0.55, 0.27, 1.55) 是合法的，因为两个 x 在 0 和 1 内，y 的负值和超过 1 只是让元素冲过头再收回来。但反过来，cubic-bezier(2, 0, -1, 1) 会因为 x 越界被整条丢掉。这也解释了一个 CSS 与 JS 动画的机制差异：JS 里每帧你可以调用任意计算函数，映射不必是单调贝塞尔，甚至可以是分段离散逻辑；而 CSS 的时间函数被规范锁死成单调函数，所以它天生无法用”一条函数”表达需要非单调进度映射的效果。

steps() 是另一类，它把连续的插值切成有限级数，正好适合”逐帧播放”。steps(n, end) 把动画分成 n 段，每段末尾跳变；单参数 steps(n) 等价于 steps(n, end)（当时双参数写法在部分浏览器上支持还不完整，稳妥起见按帧数单参数用）。最典型应用就是雪碧图逐帧动画——用 background-position 在一条长图上阶跃跳动：

浏览器是怎么跑一帧动画的

把动画讲成”插值”还只是 CSS 层的抽象，真正的成本在渲染管线。理解这条管线，才能推导出写法纪律。

flowchart TD
    A[样式重算 Recalculate Style] --> B[布局 Layout 回流]
    B --> C[图层化 Layerize]
    C --> D[绘制 Paint 重绘]
    D --> E[合成 Composite GPU]
    E --> F[屏幕显示]
    G[transform opacity 变化] --> C
    H[width top left margin 变化] --> B

一帧的常规路径是：样式重算 → 布局（回流）→ 图层化 → 绘制（重绘）→ 合成 → 上屏。越靠左边的阶段越贵，因为一次布局往往会牵动一片绘制和合成。关键区别在于：transform 和 opacity 这两个属性不需要走前面的布局和绘制。当一个元素被提升成独立的合成层之后，它的 transform、opacity 变化可以由合成器（Compositor）直接在 GPU 上搬运和混合已有纹理，主线程甚至不用参与——这就是为什么这两个属性在移动端动画里”便宜”。反过来，width、top、left、margin 这些改变几何的属性，每变一帧都要重算布局，再重新绘制受影响的像素，成本随页面复杂度上升，低端机上直接表现为掉帧。

具体代价分级，按当年的经验排一下：

属性 触发的最重阶段 代价 备注
width / height / top / left / margin / padding 布局 + 绘制 高 每帧回流
background-position / color / box-shadow 绘制 中 不回流但要重绘
background-color（局部） 绘制 中 大面积重绘更贵
transform 合成 低 有独立层时最省
opacity 合成 低 同上

既然 transform、opacity 走合成最省，那怎么保证它们真的被分到独立层？当年移动端的土办法是给元素加 translate3d(0, 0, 0) 或者 translateZ(0)：带 3D 的变换会促使浏览器把该元素提升为一个合成层，从此 transform 和 opacity 的变化留在 GPU。这个技巧在 iOS Safari 和 Android 4.x WebView 上确实能救活卡顿的动画。但它不是免费的——每多一个合成层，就要多占一份纹理内存，而且层的内容要能塞进 GPU 的纹理尺寸上限。iOS 上合成层总内存是有硬顶的，一旦你把太多元素都 translateZ(0)，或者堆了过多大尺寸层，超出预算后 WebKit 会直接放弃合成、页面白屏或者整屏重绘，反而更糟。所以正确的姿势是：只对”真正在做动画的少数元素”提层，动画结束后能不提就不提，把 translate3d 当成定位和救急的工具，而不是无脑默认加。顺带一提，规范草案里当时已经有 will-change 这个属性，本意是优雅地提示浏览器”我打算改 transform”，但 2014 年 5 月这个时间点浏览器实现面极窄，基本不能依赖，还是 translateZ(0) 这套土办法更普适。

重排与重绘的实测方法

上面是原理，落到工程要能测出来。同一个”把一个方块从左移到右 300px”的效果，分别用 top、transform、left+margin 三种写法，测在同一设备上的耗时差异。测量思路不依赖任何库：启动一个固定帧数（比如 60 帧）的循环，每帧用 requestAnimationFrame 触发一次样式改写，用 Date.now 打点统计总耗时和掉帧数；更严谨一点在 Chrome 34 上开 Timeline，看每一帧里有没有 Paint、Layout 事件冒出来。

把 step 换成三种实现，在一台 iPhone 5（iOS 7 Safari）、一台 Nexus 4（Android 4.4 Chrome 34）、以及当年还活着的 Android 4.0 WebView 上跑，得到的量级大致是这样（数值是笔者当时在真机上的典型区间，非精确基准，用来看趋势）：

实现 iOS 7 Safari Android 4.4 Chrome 34 Android 4.0 WebView
top 位移 约 12-18 ms/帧 约 9-14 ms/帧 约 22-40 ms/帧，明显掉帧
left + margin 补偿 约 13-19 ms/帧 约 10-15 ms/帧 约 25-45 ms/帧，最差
transform 位移 约 3-5 ms/帧 约 2-4 ms/帧 约 6-10 ms/帧

一帧的预算是 16.7ms（60fps），top 方案在 Android 4.0 上直接超预算、肉眼可见地卡顿；transform 在所有设备上都稳稳待在预算内。在 Chrome Timeline 里对比更直观：top 那一列几乎每帧都挂着 Layout 和 Paint 两个事件条，transform 那列则只有 Compositor 的轨迹、主线程基本是空的。这就是”能合成就不回流的写法纪律”的量化依据——它不是玄学，是每帧省下了一次布局计算。IE10 桌面版上 transform 也走硬件合成，表现和 Chrome 接近；反倒是 IE9 根本不支持 animation，谈不上测（下面兼容性一节展开）。

多元素与序列编排

真实页面里动画很少只有一个元素。列表入场要错峰、一串图标要接力，靠的是 animation-delay 的阶梯。思路很简单：给第 n 个元素设 delay = (n-1) * 步长，它们就会一个接一个进场。麻烦在于当年没有 CSS 自定义属性（var 那种 2014 年还不可用），元素一多，delay 得一个个手写，维护痛苦。当时普遍用预处理器把这套阶梯生成出来。

还有一个容易踩的语义坑：同一个元素、同一个属性上，animation 和 transition 会打架。规则是 animation 的优先级高于 transition——动画在跑的时候，它对该属性产生的计算值会盖住 transition 想要插的那个值。所以如果你给一个元素同时配了”hover 时 transition 变 opacity”和”一个持续改变 opacity 的 animation”，实际观感是 animation 说了算、transition 像是没生效。要么把两者分到不同属性上，要么就别混用，别指望它们和平共处。

与 JavaScript 协作：事件、暂停与换帧

animation 跑在 CSS 里，但结束时机往往要 JS 知道——比如入场动画播完再把元素从”动画态”切回”常态”以回收合成层。规范提供了 animationstart、animationiteration、animationend 三个事件。现实是前缀满地爬：WebKit 内核要监听 webkitAnimationStart / webkitAnimationIteration / webkitAnimationEnd，IE10 用 MSAnimationStart 这套带大写 M 的前缀，只有较新的 Chrome 才同时派发无前缀的标准名。稳妥做法是做一个跨内核的绑定小工具：

那个 done 标志很重要：在既派发标准名又派发带前缀名的内核上，同一次结束可能触发两个 handler，不加保护就会执行两遍清理逻辑。

transitionend 比 animationend 更不靠谱，坑有两处。其一是同样有前缀问题（webkitTransitionEnd / transitionend）。其二更隐蔽：只要动画”实际没有产生值的变化”，transitionend 根本不触发——比如目标值和起始值相同，或者中途元素被 display:none、或者 transition 被覆盖掉了，事件就丢了。你要是把”跳转下一步”的逻辑吊在 transitionend 上，一旦这条边界触发，流程就永久卡住。所以当时的通用做法是给监听补一个 setTimeout 兜底，超时时间取 duration 加一点余量，两者谁先到谁执行、另一个用标志位作废，保证流程不会因为事件丢失而饿死。

play-state 是做”暂停/继续”最轻的手段。一个一直在转的 loading 图标，想让用户点击暂停，JS 只要把它的 animation-play-state 在 paused 和 running 之间切，冻结和恢复都在当前进度上，不用记录角度：

无障碍与体验纪律

prefers-reduced-motion 这个媒体查询是 2014 年之后才逐步出现的，2014 年 5 月还指望不上，但”运动相关的可访问性与舒适度”当年就有成熟的经验纪律可以遵守。最重要的一条是光敏感安全：大面积、高对比的闪烁不要超过 3Hz（每秒明暗交替 3 次以上），否则对光敏性癫痫用户有风险。用 steps 或者高频 alternate 做”闪光/呼吸”类效果时，一定要把频率和覆盖面积压下来——小图标闪没事，整屏 3Hz 以上闪绝对不能上。实在要做强烈的进入提示，宁可加一个”点击停止动画”的开关，把控制权交给用户。

时长口径也值得定死：用于”用户操作的即时反馈”（点一下按钮的按压回弹、hover 高亮），动画应该在 100-300ms 之间，短于 100ms 人眼几乎无感、长于 300ms 会让人觉得界面”迟钝”；用于”位移/入场”这种需要传达空间关系的，可以到 300-500ms；任何超过 500ms 的动画都必须是可以被打断的——用户一旦再次交互，动画要么立即跳到终态、要么切到新状态，绝不能让一个自顾自播 800ms 的入场动画把用户锁在门外。移动端比桌面端更该取短，手指连续操作时慢半拍的动画叠加起来就是”卡”的观感。还有一条纪律：动画结束后如果那个元素不再需要独立合成层，尽量把触发 translateZ 的样式收回，别把一层层纹理永久留在 GPU 上，尤其在长列表里。

小结

transition 是”两个状态一次插值”，而 animation 把整条时间轴交到你手里，代价是它接管了对应属性的计算值、并盖过同属性的 transition。@keyframes 会被解析成”进度到样式”的表，同名覆盖、非法声明静默丢弃、缺 0%/100% 用底层值兜底，这些解析细节正是”动画没报错却不生效”的根源。animation-* 里最该记的是 duration 缺省为 0 会让动画不动，fill-mode 的 backwards/both 决定 delay 期间元素长什么样，以及简写里”第一个时间是 duration、第二个是 delay”这条顺序规则。缓动函数本质是被锁死为单调的三次贝塞尔，x 越界即非法、y 可越界做回弹，steps() 用来做逐帧雪碧图，easeOutBounce 只能靠多关键帧手工逼近。往渲染管线看，transform 与 opacity 走合成、几乎不回流，top/left/width/margin 每帧回流，这就是”动画只动 transform 和 opacity”这条纪律的量化依据；translateZ(0) 能提合成层救卡顿，但 iOS 合成层内存有上限，滥用会白屏。和 JS 协作要跨前缀监听 animationend、给 transitionend 补 setTimeout 兜底、用 play-state 做暂停、动态换 animation-name 前强制重排。兼容性上 IE9/Android 2.x 是死穴，用 Modernizr 的 cssanimations 类名分支做渐进增强，永远记住动画只是装饰、关掉动画功能照样可用。
