DOM 操作性能：批量插入与重排优化

本文复盘 2013 年底到 2014 年 4 月之间，笔者在项目里踩的三次重排（reflow）事故：报表表格的一次悬停卡全屏、IE 8 上六秒的搜索建议、一个 iframe 表单拖死父页面。每个事故都按”现象—排查—修复—回归”的完整过程写，重点是重排在 table、float 多列、绝对定位、iframe 这些复杂布局下的连锁代价，以及当年手上可用的定位手段。不是清单，也不是 Fragment 教程——批量插入的选型那篇旧文已经讲透，本文的案例恰恰说明：真正贵的往往不是插入本身。适合被”JS 没写几行但页面就是卡”困扰的同学。

事故一：报表页滚一下就白屏

那是一个费用报销的报表页，服务端一把吐 1200 行 × 14 列的 table，前端不做分页。需求里有一条”鼠标悬停整行高亮”，前任的实现是 mouseover 给 tr 加 row-hover 类、mouseout 移除，类里有 font-weight: bold 和左右各加 4px 的 padding——问题就出在这两个属性上，它们都是几何属性。

现象是鼠标从第 1 行扫到第 100 行，行高亮一卡一卡，IE 9 下整页发白，像白屏。在 Chrome 34 的 Timeline 里复现一次悬停，Layout 记录不是零条，而是每次悬停切换都有多条，单击一条展开，括号里写着整表的尺寸——也就是说每次重排都在重算 16800 个单元格。

这里必须讲清 table 布局的特殊性。table-layout: auto（默认值）下，列宽不是由某一列独立决定的，而是这一列所有行的内容共同参与计算：某个单元格的字体加粗、padding 变大，行盒宽度变了，浏览器要把整列重新测量，列与列之间还要互相争抢总宽度，最终波及整张表。所以在 table 上，任何单元格尺寸的小改动都近似于一次全表重排，代价与行数列数都成正比。这与 div 布局完全不同——div 里改一个盒子，通常只推动它后面的兄弟。

修复分三步，每步单独量化：

改成纯 CSS 并把加粗、padding 从悬停样式里拿掉之后，悬停只改 background-color，引擎跳过布局直接重绘，Timeline 里 Layout 归零。但如果业务确实想让悬停行加粗呢？第二步是 table-layout: fixed：列宽只由第一行（或显式 colgroup）决定，后续一万多行根本不再参与宽度计算，几何改动被限制在行内，重排从”整表测量”降为”局部”。报表列宽本来就是拍板定死的，改成 fixed 零视觉损失。

悬停切换一行（1200 行 × 14 列） Chrome 34 IE 9
JS 加类 + auto 布局（原始） 约 48 毫秒 约 130 毫秒
CSS :hover（只换背景）+ auto 0 次 Layout，绘制约 6 毫秒 约 20 毫秒
CSS :hover（保留加粗）+ fixed 约 4 毫秒 约 11 毫秒

第三步是给同类页面铺路：新建的报表直接用 div 模拟表格（一行一个 div，格子里放固定宽度的块），每行高度互不牵连列宽，重排范围就只剩该行以下的内容流。代价是失去自动列宽与表格语义，复制单元格到 Excel 的体验也差，所以只在列宽本来就固定的后台报表里用。回归测试用鼠标连扫 500 行，IE 9 全程无白屏。

事故二：IE 8 上插入 500 条搜索建议要 6 秒

搜索框下拉建议，聚合类目下会一次返回 500 条。原始代码是循环 insertAdjacentHTML 逐条追加进面板，而且每追加若干条就读一次面板的 offsetHeight，用来判断剩余空间不够时把面板向上翻转。IE 8 实测从回车到面板出现约 6100 毫秒。

排查过程值得细说，因为我一开始就抓错了凶手。第一步怀疑节点数量：把渲染拆成”造 500 个节点”和”逐个塞进面板”两段，用 +new Date() 分别计时（IE 8 没有 console.time，也没有可靠的性能工具），两段合起来只有约 1100 毫秒——批量插入本身没那么贵。真正的大头在第三段：500 次 offsetHeight 读取合计约 5000 毫秒，而且越读越慢。道理在于每次读取都是一次强制同步布局，而面板是绝对定位的、内部条目有 float 两栏排版——每次补算布局都要重新解决一遍所有已插入条目的浮动排列，再重算绝对定位的包含块，工作量随已插入条数增长。读写交错把一个线性过程放大成了近似平方级的账单，这就是本次事故的核心：贵在读写交错 + 复杂布局的每次重算都比你想象的重。

改法是把”装配车间”挪出渲染树：先建一个离屏容器，条目全部在里面拼装，装完读一次总高度、一次定好翻转方向，最后整体搬进面板。

为什么不干脆 display: none 装完再显示？那确实让插入完全不触发布局，但《DOM 尺寸与位置》那篇早给过结论：display: none 时 offset 全家都是 0，翻转判断要用的面板高度根本读不出来，所以必须离屏而不是隐藏。

版本（500 条建议，IE 8） 耗时
逐条插入 + 逐条读高度（原始） 约 6100 毫秒
只改”全部插完最后读一次” 约 1900 毫秒
离屏容器装配 + 整体搬入 + 读一次 约 260 毫秒

第二行是关键的对照实验：节点数量完全没变、插入方式没变，仅仅把读写分开就快了 3 倍；离屏方案再快一档，是因为装配期间面板本身还嵌在 float 多列的文档流里，在文档里每动一次它，周围栏目都得陪葬，离屏把这个陪葬也免了。Chrome 34 上三档分别是约 300 / 90 / 35 毫秒，趋势一致。

事故三：iframe 里的表单联动把父页面拖住

入驻流程页，第三步表单挂在同源 iframe 里，表单团队配了一段”自适应高度”脚本：iframe 内容每次 change、每次展开收起字段组，就通过 postMessage 把内容 scrollHeight 报给父页面，父页面把它写到 iframe 的 style.height 上。听起来贴心，实际是灾难。

现象：在 iframe 里每选一次省市级联，父页面冻结 400 毫秒上下。Timeline 一录，每次联动是成对的两条 Layout：一条属于父文档，一条属于 iframe 子文档。原因要回到 iframe 的渲染模型：iframe 有自己独立的渲染树，子文档内部再怎么改，正常情况下都波及不到父页面——唯一的例外就是这堵墙的几何尺寸本身。父页面是三栏 float 布局，iframe 坐在中栏流里，style.height 一变，父文档整页重排：中栏之后的内容被推下去，右栏要重新解决浮动挤压；紧接着子文档也全量重排（视口变了）；最后整块区域重绘。选一次下拉触发 6 到 8 次高度上报，等于把这条”跨文档连锁重排”跑 8 遍。

修复的取向不是”算得更快”，而是干脆不再频繁动这堵墙：iframe 改固定高度、内容超出靠内部 overflow: auto 滚动，这正是《iScroll 实现移动端滚动》里那条”容器尺寸钉死、滚动交给容器”纪律在桌面端的翻版。高度自适应脚本只在整表状态切换（比如展开附件区）时调用一次，输入联动一律不碰。双滚动条确实不雅，把 iframe 高度按最大表单留足余量后，实际很少滚到第二层。回归：级联选择全程 0 次父文档 Layout，卡顿消失；代价是短表单下方留白，业务方接受了。

通用排查手法沉淀

三个事故能收口，靠的是同一套笨办法，整理成四条：

  1. Chrome Timeline 看 Layout。重点看两个量：一次操作里 Layout 的条数（条数爆炸就是读写交错的形状）和单条耗时（条数不多但每条都肥，就是布局类型太重，去查 table、浮动、iframe）。点开 Layout 能带出触发它的脚本调用栈，比猜快得多。
  2. **IE 9/10 F12 的局限要认清。**它的分析器只对脚本采样，看不到布局记录本身；某函数自身耗时不大却把墙上时间吃光时，多半是在循环里读布局属性等布局返回，得回 Chrome 复现确认。IE 8 则什么都没有，只能手工埋点。
  3. 手工分段计时，一次只改一个变量。+new Date() 打点拆段，改一步跑一次，把嫌疑变量逐个剥掉——本文事故二里”只分离读写”那一档对照实验，就是把节点数量钉死、只动读写顺序，账才摊得开。
  4. **注释二分。**怀疑哪段就注释哪段，回 Timeline 看 Layout 条数是否锐减，减了就锁定，不减就换目标。

再给一个当年常用的小探针：布局脏账检测。思路是布局刷新成干净状态后，紧接着再读一次几乎免费；只有当引擎欠着布局时，这一次读才会变成真实的同步计算耗时。

flowchart TD
    A[页面卡顿] --> B[Timeline 复现这次操作]
    B --> C{Layout 多还是单条 Layout 肥}
    C -->|条数多| D[看调用栈定位那次读]
    D --> E[读写拆段或移入离屏容器]
    C -->|单条肥| F[查布局类型 table float iframe]
    F --> G[固定尺寸或脱离文档流]
    E --> H[再录 Timeline 回归]
    G --> H

修复之后的取舍：什么时候换实现

按上面的手法改到极限后，还有一道坎：有些需求的重排账单是布局类型决定的，缝缝补补省不掉，宁可换实现。两类最典型：

  • **图形密集的内容换 Canvas。**趋势图挂 5000 个 SVG/DOM 节点时，每帧的布局税跟节点数成正比；Canvas 把几何计算全部收到自己手里，浏览器只看见一张位图，reflow 归零，代价是命中检测、无障碍都得自己做。图表库当年主流（Highcharts 那一系）走的基本都是 SVG 路线，数据点上万时也该考虑切 canvas 自绘。
  • **超长列表手工做虚拟滚动。**DOM 规模钉死在”视口行数 + 上下缓冲”，滚动时只改写复用节点的文本。2014 年手工实现的注意点：行高必须固定，否则首行偏移与可视区间的换算无从谈起；视口用绝对定位加一个撑高的占位块造滚动条；scroll 回调里读 scrollTop 是只读操作、不欠布局，放心读，但回调之后改写节点时别顺手再去读复用节点的高度；IE 下 scroll 事件触发过密，要做 30 到 50 毫秒节流。丢焦点、丢选择这些副作用要评估。

原则是：测量驱动的微调没做完，不要跳到换实现；微调做完还不够，换实现也别硬扛。

复盘结论五条

  1. **先测再改。**三个事故里两个的第一嫌疑人（节点数量、JS 计算量）都是错的，靠分段计时和 Timeline 才抓到真凶；感觉不可靠。
  2. **读写分离永远是最大收益点。**事故二里光拆读写就快 3 倍，比任何插入技巧都值钱；循环里每读一次 offset 系列属性，就是在逼引擎当场交一次布局的税。
  3. **布局类型的影响远大于节点数量。**同为 500 节点，auto 的 table 与 fixed 的 table、孤立的离屏容器与嵌在 float 三栏里的面板，单次重排的账单差一个数量级。
  4. **复杂布局要钉死尺寸。**列宽写进 colgroup、容器高度给定值——让尺寸参与计算的地方越多，重排的爆炸半径越大。
  5. **跨文档边界要谨慎。**iframe 内外互不干扰的前提是这堵墙不动；一旦频繁改它的几何，就是同时给两棵渲染树各记一笔账。

小结

这三起事故的账本合起来其实只有一句话：重排的代价等于失效范围乘以触发次数，而复杂布局（auto 的 table、浮动、绝对定位、iframe）会把单次失效范围悄悄放大到整页。排查上不神秘——Timeline 数 Layout 条数、看单条耗时、二分注释、分段计时，四板斧足够把凶手按在代码行上。动手改的时候先分离读写、再固定尺寸、把装配挪出渲染树，实在省不掉的账就换 Canvas 或虚拟滚动的实现。下一个卡页面，先别急着优化循环，去看看布局欠了多少次税。
