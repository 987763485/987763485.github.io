DOM 节点类型与节点关系梳理

浏览器把一份 HTML 解析成一棵树，树上每个位置都是一个节点对象，节点之间靠一组属性相连。听起来很简单，但 childNodes.length 在不同浏览器上给出不同数字、children 里莫名混进注释、innerText 读出来的文本少了半段，这些都是原生节点模型本身的行为差异，跟 jQuery 和文档碎片无关。本文只谈这一层：节点有哪些类型、关系属性各自的兼容性、以及围绕这些差异最小的一套兼容封装。增删改查的接口与 DocumentFragment 的用法在《DOM 增删改查与文档碎片 DocumentFragment》里写过，jQuery 的遍历方法另有梳理，这里不重复。

结论只有一条：任何依赖”第 n 个子节点”的代码，都必须显式按 nodeType 过滤，不能假设浏览器给出的顺序和自己写源码时的视觉顺序一致。

nodeType 家族

节点类型是数字常量，Document 构造函数在老 IE 里读不到，所以判断时直接用数字，别写 node.nodeType === node.ELEMENT_NODE（IE 8 及以前没有这些常量属性）。完整对照如下：

nodeType 常量名 是什么 实际遇到的频率
1 ELEMENT_NODE 元素节点 天天遇到
2 ATTRIBUTE_NODE 属性节点，只有 getAttributeNode 之类才拿得到 偶尔，主要在 SVG
3 TEXT_NODE 文本节点，createTextNode 造的也是它 天天遇到
4 CDATA_SECTION_NODE CDATA 段 处理 XML 才会遇到
5 ENTITY_REFERENCE_NODE 实体引用 基本遇不到
6 ENTITY_NODE 实体声明 遇不到
7 PROCESSING_INSTRUCTION_NODE 处理指令 只在 XML
8 COMMENT_NODE 注释 常见
9 DOCUMENT_NODE 文档本身，document.nodeType 就是 9 常见
10 DOCUMENT_TYPE_NODE DOCTYPE 声明 极少
11 DocumentFragment 文档碎片 用碎片时
12 NOTATION_NODE 符号声明 遇不到

nodeName 和 tagName 经常被当成一回事，实际有三个差别。第一，tagName 只有元素节点才有，文本节点和注释节点上是 undefined，而 nodeName 所有节点都有。第二，非元素节点的 nodeName 是一串带 # 的固定名字：文本是 #text，注释是 #comment，碎片是 #document-fragment，document.nodeName 是 #document，CDATA 段是 #cdata-section。属性节点的 nodeName 就是属性名本身，所以 node.nodeName.toLowerCase() === 'class' 这种判断在混合遍历里会突然冒出来。第三，大小写：在 HTML 文档里元素的 nodeName 一律大写（DIV），tagName 在标准模式（Strict Mode）下是小写，而老 IE 在怪异模式（Quirks Mode）下返回大写；同一份代码在混排 SVG 时又是另一套规则，因为 XML 大小写敏感。所以当年判断标签名的稳妥写法是统一转小写再比较，并且优先用 tagName：

读写文本

textContent 与 innerText 读出来的字符串经常不一样，差异是规范层面的：

行为 textContent（DOM 标准，IE 9 起） innerText（IE 私有，Opera 与 WebKit 跟进）
display: none 的元素 照样读出来 剔除
<script> 与 <style> 里的文字 读出来 不读
<br> 与块级边界 原样拼接，没有换行 变成换行符
读取时的代价 只走 DOM 强制同步布局（layout）
写入时的语义 纯文本 纯文本，比 innerHTML 安全

normalize() 与相邻文本节点

normalize() 做两件事：把连续的兄弟文本节点合并成一个，删掉内容为空字符串的文本节点。它递归处理整棵子树，所以节点很少被主动调用。真正需要它的是富文本编辑器：contenteditable 的区域里，用户连续输入、程序插入 <span>、再撤销删除，很容易留下「一段文本被切成三个相邻文本节点」的状态。我们在做光标定位时，会把选中位置算成「某个文本节点内部的偏移量」，一旦节点被切开，同一个视觉位置的偏移量就完全变了，表现是光标莫名其妙跳到句子中间，或者插入的图片跑到半句话前面。

节点的工厂与归属

创建节点时，归属关系（ownerDocument）就已经确定了。document.createElement('div') 造的节点属于当前文档，把它插进 iframe 里的另一份文档时，规范上要先用 document.importNode(node, true) 复制一份，或者用 adoptNode(node) 把它的 ownerDocument 改过来。IE 8 上这两个都不可用（adoptNode 直到 IE 11 才补上，importNode 也只对 XML 文档生效），所以当年的绕法只有两种：cloneNode 之后再改，或者把内容序列化成字符串在目标文档里重建。

cloneNode 本身也有几个必须记住的语义。深复制（参数 true）复制的是节点和属性，不复制用 addEventListener 或 attachEvent 绑上去的监听器；表单控件的当前状态也不复制——<input value="a"> 被用户改成 b 之后克隆出来的节点读 value 又是 a，因为改动的只是属性对应的 DOM 属性而非默认值，checked、selected 同理。克隆还会把 id 一起复制，导致文档里出现两个同名 id，getElementById 的行为变得不可预测，所以克隆带 id 的模板节点后第一件事就是改 id。

跨 iframe 还有一处容易翻车的地方：用 instanceof HTMLElement 判断节点类型会失败，因为两个 window 各有自己的构造函数。判断节点一律用 nodeType。反过来拿一个节点要找它所在文档的 window，用 ownerDocument.defaultView，IE 8 上没有 defaultView，得退到私有属性 parentWindow：

属性节点、dataset 与自己的工具函数

读属性有两个入口：el.getAttribute('href') 拿到的是源码里写的那个字符串，el.href 拿到的是浏览器解析后的 DOM 属性值（对 a 元素是绝对 URL）。同理 input.value 是用户当前输入的值，getAttribute('value') 是初始值，两者在表单场景里含义完全不同。老 IE 还有几处专属的坑：input 元素插入文档后 type 改不动，只能在创建时用私有写法 document.createElement('<input type="checkbox">')；form 元素上如果有个子控件叫 name，form.name 会被它遮蔽，读到的不是字符串而是一个元素——凡是 form 上的内置属性名，都别直接用点号取。

属性本身也是节点（nodeType 2）。getAttributeNode / setAttributeNode / createAttribute 什么时候真的需要？两种场景。其一是把一组属性整批搬到另一个元素上，属性节点带着类型和顺序信息，比逐个字符串读写干净；其二是命名空间属性：SVG 里的 xlink:href 必须用 setAttributeNS，IE 甚至不支持命名空间属性，只能用私有写法绕。判断属性节点名字时注意它不带 xlink: 前缀的部分和带前缀的部分是 localName 与 nodeName 两个字段。

dataset 是把 data-foo-bar 映射成驼峰属性的糖，2014 年的支持情况大致如下：

环境 dataset 建议
桌面 Chrome / Firefox / Safari 新版本 支持 可以直接用
IE 8 / 9 / 10 不支持 用 getAttribute('data-x')
IE 11 支持 2013 年底才随系统铺开，覆盖率很低
Android 4.4 之前的 WebView 不支持 移动端一律手工读写
iOS Safari 新版本 支持 但低版本 iOS 仍有风险

也就是说桌面勉强能用、移动端不能用，加上驼峰转换在数字与连字符边界上还有歧义（data-list-id-2 这类名字读回去的键名各家不完全一致），所以当时绝大多数项目仍然统一走 getAttribute。属性命名与 jQuery.data() 的缓存陷阱在旧文《HTML5 自定义数据属性 data-* 的设计与读取》里写过，这里不重复。

小结

原生节点模型的核心差异集中在三处：解析阶段留下的空白与注释文本节点、nodeType 与 nodeName 的取值规则（尤其 nodeName 大写和属性节点的特殊名字）、以及关系属性在老 IE 上的缺失与偏差（children 混入注释、element 系列不存在、textContent 要到 IE 9）。childNodes 一类的活集合是遍历时最容易咬人的东西，规矩只有一条：先把节点拷进普通数组再动手。文本读写用 textContent 加 innerText 双分支，记住 innerText 会强制同步布局，innerHTML 则整棵子树重建。深究到底，这些差异不足以改变架构，但足够让一段在 Chrome 里正确的代码在 IE 8 上静默出错——所以按 nodeType 过滤、把兼容收敛到一小套自己的函数里，是我现在写原生 DOM 时的默认做法。
