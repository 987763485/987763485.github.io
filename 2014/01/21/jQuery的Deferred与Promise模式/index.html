jQuery 的 Deferred 与 Promise 模式

jQuery 1.5 在 2011 年初引入 $.Deferred 时，很多人以为它只是个”更好用的 AJAX 回调”。但这个对象真正改变的，是把异步流程从”往函数里传回调”翻转成”把返回值当成可等待的对象”。本文按 2014 年初的现状，把 $.Deferred、$.when、$.Callbacks 与 jQuery 1.7/1.8 的 then、pipe 一并讲清，重点剖析 jQuery 的 then 与后来 ES6 的 Promise 之间那些著名差异——尤其是 1.8 之前 then 的非标准行为这个坑。结论先放在前面：$.Deferred 是一套好用的工具，但它的 then 从来不是 Promise 的 then，混用两者心智模型必然出错。

三种状态与 Deferred 的构造

$.Deferred() 创建一个 deferred 对象，它内部维护三种状态：pending（等待中）、resolved（已完成）、rejected（已失败）。状态流转是单向的：一旦从 pending 变成 resolved 或 rejected，就永久固定，后续再调用 resolve/reject 没有任何效果。

这里有个重要细节：在 deferred 已经 resolved 之后注册的 done 回调会立即执行，带着当初 resolve 时传入的值。这个”迟到也能收到通知”的特性是 Deferred 价值的一半——它把”事件已经发生”和”我还没注册回调”这两个问题解耦了。

异常不会被自动捕获

标准 Promise 有一个重要的健壮性设计：then 回调里抛出的异常会被 Promise 捕获，并转换成新 Promise 的 rejected 状态，从而被下游的 .catch() 或 fail 处理。

jQuery 的 Deferred 完全没有这个机制。 done/fail/then/pipe 回调里抛出的异常会直接冒泡到全局，触发 window.onerror，Deferred 链就此中断，fail 回调不会被调用。

这个差异有深远的实践影响。写 Promise 风格代码时，习惯性地把可能出错的逻辑放进回调、依赖 .catch 兜底，在 jQuery 下会全部失效。jQuery 下的正确做法是显式 try/catch 并把异常转成 reject：

另一个相关的坑：jQuery 的回调队列不保证异常后继续执行。标准 Promise 的多个 then 中，前一个抛异常不会影响后一个（因为它们在不同的 Promise 上）。jQuery 的 done 回调如果第一个抛了异常，后面注册的 done 可能不会执行，具体行为取决于版本。所以不要把多个独立逻辑挂在同一个 done 上。

这个坑在真实项目里的典型表现是”某个功能坏了，另一个无关功能也不动了”，而两者看起来毫无联系。根因是它们挂在同一个 deferred 的同一个回调队列里，第一个回调的异常中断了队列遍历。解决办法有两个：一是把独立逻辑拆到不同的 deferred 或不同的 done 分支上；二是给每个回调包一层 try/catch。前者更干净，因为它同时解决了”一个功能的异常不应该影响另一个功能”这个设计问题。

done 可以被多次调用、每次注册一个回调，这本身就提供了拆分的手段。它与”一次 done 传多个回调”的区别在于：多个 done 调用之间的边界更清晰，出错时影响范围更小。

还有一点与异常相关的实现细节：jQuery 1.9 内部用 try/catch 包裹了回调调用，捕获到的异常会被缓存在 deferred 上，等到所有回调跑完再重新抛出。这意味着异常不会立刻冒泡到全局，但也不会被 fail 处理，最终仍然以未捕获异常的形式出现。所以”用 fail 兜住回调异常”这个直觉在 jQuery 下始终不成立，无论版本。

$.Callbacks 与 Deferred 的关系是：Deferred 内部就是三个 $.Callbacks 列表（resolve 队列、reject 队列、通知队列），resolve 就是 fire 第一个列表。理解这一点，就能理解为什么 done 回调的添加顺序就是执行顺序，以及为什么 memory 模式能让”迟到注册”的 done 立即执行。

实际项目里 $.Callbacks 常用于自建事件总线，尤其是”事件可能已经发生”的场景——例如资源加载完成后才注册的监听器。用 Deferred 的 promise 也能做到，但 $.Callbacks('memory') 语义更直白。

$.Callbacks 与 Deferred 的分工值得再说一句：Deferred 关心的是”一个异步操作的最终结果”，$.Callbacks 关心的是”一组可以被多次触发的观察者”。前者天然带有”一次性”的语义（状态只能变一次），后者则是可重复的事件列表。所以轮询式的场景（窗口 resize、滚动、消息到达）用 $.Callbacks，”加载完成”这类一次性事件用 Deferred。混用的典型错误是用 Deferred 做事件总线——第二次 resolve 不会触发任何回调，订阅者会以为事件只发生了一次。

$.Callbacks 还有两个查询方法：fired() 返回列表是否已触发过，locked() 在 once 标志下返回列表是否已锁定。它们可以用来做状态判断，避免重复触发。

与 CommonJS Promises/A 的关系

2013 年讨论 jQuery Deferred 时，必然会提到 CommonJS 的 Promises/A 规范。这份规范由 Kris Zyp 等人在 2009 年前后提出，核心内容只有一条：promise 是一个有 then 方法的对象，then(fulfilledHandler, errorHandler, progressHandler) 接受两个（或三个）回调，返回一个新的 promise。

Promises/A 与 Promises/B（另一个更早的提案）的分歧之一就是 then 的返回值。Promises/A 明确要求 then 返回新 promise，而 jQuery 1.7 的 then 没有做到——这正是它被指”不符合 Promises/A”的原因。jQuery 1.8 引入 pipe 之后才补齐了这部分语义，而 jQuery 团队当时的公开态度是：他们不打算完全遵循 Promises/A，因为 jQuery 的回调列表模型（支持多个回调、支持通知回调）与规范的单回调模型不同。

这个分歧的痕迹在 jQuery 的 API 上保留了很久。then 的进度回调参数（第三个参数）就是 Promises/A 里 progressHandler 的遗留，jQuery 用 notify 与 progress 实现：

在展开进度通知之前，值得先把 Promises/A 的规范条文本身摆出来，因为很多争论源于没读过原文。规范的核心只有三条：

  1. 一个 promise 对象上必须有名为 then 的方法。
  2. then 接受两个参数，第一个是完成回调，第二个是失败回调（Promises/A 的第三个进度参数是可选的，由实现自行决定是否支持）。
  3. then 必须返回一个新的 promise。

第 3 条是 jQuery 1.7 被批评的直接依据，第 2 条里”两个参数都是可选的”则解释了为什么标准 Promise 允许 .then(onSuccess) 而不传失败回调——失败状态会沿着链往下传，直到某个 then 处理它。jQuery 的 done/fail 分离式设计没有这个”穿透”特性：done 注册的回调只在成功时触发，失败时整个 done 链被跳过，这与标准 Promise 的链式语义又有细微差别。

规范还规定了”同一次 then 调用中，完成回调和失败回调至多只有一个被调用”，以及”回调的返回值决定新 promise 的状态”。jQuery 1.8 之后的 then/pipe 在第一条上是一致的（resolve 或 reject 只会触发一边），在第二条上也是通过采纳返回值实现的。所以可以这样说：jQuery 1.8 之后的 then 大体符合 Promises/A，1.7 的不符合，而 jQuery 独有的多回调队列和进度通知始终是规范之外的扩展。

理解这段规范史对读当年的技术讨论有帮助。jQuery 团队在邮件列表里的立场大致是：jQuery 的回调列表模型（done 可注册多个、resolve 触发全部）与 Promises/A 的单回调模型有本质冲突，完全遵循会破坏向后兼容。这个立场在社区引发了长期争论，也直接催生了 Q、when.js 这些”严格遵循规范”的库。2013 年选择技术方案时，这段历史决定了你的取舍：用 jQuery 生态就跟 jQuery 的语义走，要严格语义就引入独立库。

进度通知在标准 Promise 里被彻底去掉了，所以这也是 jQuery Deferred 与 ES6 Promise 之间不可调和的差异之一。它的实用价值在于上传进度、批量任务进度这类场景，jQuery 用户当年确实用得上。

notify 与 progress 的组合有一个容易忽略的细节：notify 可以带多个参数，progress 回调同样按注册顺序执行，与 done 的行为一致。另外，如果 deferred 已经 resolve 了，后续的 notify 不再触发任何回调——进度只在 pending 阶段有意义。这与 done 的”迟到也执行”不同，是 notify 与 resolve 在状态语义上的分工。

这个模式在标准 Promise 里完全没有对应物，用标准 Promise 做同样的事情只能在每个 then 里手动更新进度变量，代码结构反而更散。这也解释了为什么 jQuery 团队当年坚持不完全遵循 Promises/A——jQuery 的用户场景里，进度通知是硬需求。

至于 ES6 的 Promise，在 2014 年初还处于草案阶段，只有 Firefox 的实验性实现和少数 polyfill（如 Q、when.js）。本文提及它只是为了说明”jQuery 的 then 与未来的标准不是一回事”，读者不应在 2014 年的生产代码里使用原生 Promise 构造函数，那是当时不存在的语法。如果项目需要标准 Promise 行为，当年的方案是用 Q 或 when.js 这类库，而不是等浏览器。

维护老项目（jQuery 1.5 到 1.7）：链式转换用 pipe，不要用 then。异常处理全部显式 try/catch 转 reject。不要指望回调返回值传递。

新写代码（jQuery 1.9 或 2.0）：then 可用，但心里要清楚它与标准 Promise 仍有差异（异常不自动捕获、进度回调存在、不可取消）。跨库协作时（比如某个第三方库返回标准 Promise），用转换层桥接。

这个 duck typing 判断能同时识别 jQuery 的 promise、Q 的 promise 和未来的标准 Promise，是写通用工具函数的基础。

最后一条容易被忽略：Deferred 不可取消。状态一旦从 pending 变成 resolved 或 rejected，就无法回头。jQuery 没有提供取消机制，abort 只是让 jqXHR 进入 rejected，那个 deferred 依然”完成”了。设计任务流程时，如果业务需要”用户点了取消，整个流程停下来”，必须自己在每一层判断取消标志位，不能依赖 Deferred 本身。

这里要澄清一个常见的混淆：jQuery 的 jqXHR 有 abort()，所以很多人误以为 Deferred 可取消。实际上 abort 触发的是 jqXHR 的 fail 回调（状态文本为 abort），deferred 从 pending 变成 rejected，这是一个状态完成而不是状态撤销。下游的 done 不会执行，但 fail 和 always 都会。如果你的代码把 abort 当”什么都没发生”处理，就会看到 loading 消失、错误提示弹出这类不符合预期的表现。

正确的处理是在 fail 里区分 status === 'abort' 与真正的网络错误，前者静默或者走取消逻辑，后者走错误提示。这也是包装 withTimeout 时必须处理 abort 回调的原因。

小结

$.Deferred 从 jQuery 1.5 开始提供了 pending/resolved/rejected 三种状态和 done/fail/always/notify/progress 一套回调队列，$.ajax 返回的 jqXHR 本身就是 Deferred 的超集，这让异步代码从回调嵌套翻转为链式调用。但必须牢记它与标准 Promise 的差异：1.8 之前的 then 不返回新 Deferred、回调返回值被丢弃，与 CommonJS Promises/A 规范不符，链式转换要用 1.8 的 pipe；回调中抛出的异常不会被自动捕获转成 rejected，必须显式 try/catch 后 reject；进度通知是 jQuery 特有的扩展，标准 Promise 没有；整个机制不可取消，取消要靠业务层的标志位。$.when 适合并行等待但任一失败即整体失败，$.Callbacks 是底层回调列表，memory 标志能通知迟到的订阅者。ES6 Promise 在 2014 年初还是草案，生产中需要标准行为时应选择 Q 或 when.js。判断可等待对象用 typeof obj.then === 'function' 的 duck typing，而不是类型检测。
