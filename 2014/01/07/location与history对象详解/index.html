location 与 history 对象详解

location 和 history 是两个天天在用、却很少被系统看完的浏览器对象。一个管当前地址和跳转，一个管历史栈和前进后退。本文从工程实践出发，把两者的属性、方法和事件梳理清楚，重点说明 search 的手工解析、pushState 的兼容边界，以及 hash 与 path 两套路由的取舍。读完你应该能自己写出一个不依赖库的 URL 工具函数。

跳转与刷新：assign、replace 与 reload

location 的三个方法对应三种跳转语义。

replace 的典型用途是”不希望用户后退回到上一页”的场景：登录成功后的跳转、表单提交后的确认页、支付流程的中间步骤。如果这些页面留在历史栈里，用户点后退会看到过期状态，甚至重复提交。

reload(true) 强制刷新在 2014 年的兼容性已经开始分化，Firefox 早已忽略该参数，Chrome 后续也废弃。需要强制刷新的场景更可靠的做法是加一个随机查询参数让 URL 不同，或者用缓存控制响应头。

设置 location.href 与调用 assign 等价，都能跳转。但 location.href 还有一种”改部分”的能力——直接赋值给 location 的属性只会改那一部分，页面不会跳转：

这个特性是 hash 路由的基础：改 hash 不会触发页面重载，只会在地址栏变化并触发 hashchange 事件。而改 pathname 或 search 会导致浏览器真正导航到新地址。

history 对象的四个方法与 length

history 暴露的操作很有限，核心是 back、forward、go 和 length：

go(0) 与 location.reload() 效果相近，但在某些浏览器下 go(0) 会重新执行页面脚本而 reload() 可能命中缓存，行为有细微差别。

history.length 常被误用。它表示当前标签页历史栈的记录数，这个数字从 1 开始，且不同浏览器对初始记录的计算不一致。有的浏览器新开标签页就是 1，有的把 about:blank 也算进去得到 2。指望用它做”能否后退”的判断不可靠，因为规范没有定义清楚，而且出于隐私考虑浏览器也在限制它的可预测性。需要禁用后退的场景（如支付流程），正确做法是用 pushState 堆记录或者监听 popstate 反推，而不是读 length。

back/forward/go 都是异步的：调用后页面不会立即切换，浏览器要先出栈、可能要重新加载文档、再触发事件。所以不要在 go() 之后立刻访问依赖新页面的变量。

pushState、replaceState 与 popstate

HTML5 给 history 加了 pushState 和 replaceState，这是 History API 的核心，也是 hash 路由的现代替代品。完整用法已经在《HTML5 History API 打造无刷新单页应用》里展开，本文只补足与 location 相关的部分。

与 location 的关系需要特别澄清：pushState 会更新地址栏，也会更新 location 的各个属性，但不触发页面加载，也不清空 document。也就是说 pushState 之后 location.pathname 会立刻变成新值，而页面还是原来那个页面。这既是它的能力也是陷阱——代码里读 location.pathname 拿到的可能不是当前渲染内容对应的路径，而是最近一次 pushState 写进去的值。

小结

location 的九个属性覆盖 URL 的全部组成部分，其中 host 含端口、search 与 hash 含前导符号、origin 在 IE 上不可用，这三点是最常见的出错来源。跳转语义上 assign 留记录、replace 不留、reload 重载，选择依据是用户能否后退。history.length 不可靠，不要用它做后退判断；pushState 与 replaceState 从 IE10 起可用，且它们改地址栏但不加载页面，读取 location 属性时要意识到这个不同步。search 的解析必须自己实现，注意加号转空格与空值处理。hash 路由靠 hashchange 兼容到 IE8，两套方案通过能力检测加统一解析函数可以和平共存。
