jQuery 遍历节点的方法梳理

jQuery 的遍历 API 又多又像，find 与 children、filter 与 not、next 与 nextAll，用错一个就得到一堆意料之外的元素。本文从性能与调优的角度，把这些方法按”筛选已有集合”和”沿树移动”两类梳理清楚，并说明它们在 jQuery 1.9 中的内部实现差异。结论先给出：能用选择器一步到位的不要拆成多步链式调用，链式越长中间产生的 jQuery 对象越多。

两类遍历：筛选与移动

jQuery 的遍历方法看似几十个，实际分两类。

筛选类：输入是一个 jQuery 集合，输出还是集合（元素个数不增），作用是去掉或留下符合条件的元素。filter、not、has、is、eq、first、last、slice 属于这一类。

移动类：输入是一个 jQuery 集合，输出是集合中元素在树上的邻居或后代，元素个数通常变化。children、find、parent、parents、next、nextAll、prev、siblings、closest 属于这一类。

分清这两类很重要，因为它们决定了链式调用的语义。筛选类可以任意串联，移动类每一步都在换参照系。

筛选类方法的差异

filter 与 not 是一对反操作，参数形式完全相同：选择器字符串、DOM 元素、或者回调函数。

filter 的回调签名是 function (index, element)，与 .each() 一致。这里有个高频坑：在 filter 回调里写 return this.className === 'active' 而不是 return true/false，忘了返回值会让所有元素都被过滤掉。ES5 的数组方法同样要求显式返回，这个习惯要一致。

eq 与 first/last/slice 都是按下标取元素：

eq 支持负下标，eq(-1) 取最后一个。而 $('li')[0] 拿到的是原生 DOM 元素，$('li').get(0) 等价。这两者的区别在链式能力上：原生元素没有 jQuery 方法。

has 与 is 最容易被混用：

has 是筛选，输出仍是集合；is 是判断，输出是布尔值。is 的常见用途是在事件回调里做类型判断：

移动类方法的边界

children 与 find 的区别是深度：前者只找直接子元素，后者递归全部后代。

性能上 children 更快，因为它只遍历一层，内部用 childElements 而不是递归 DOM 树。能用 children 就不要用 find，这是最直接的优化。

parent、parents、closest 三个都往上走，但语义有细微差别：

closest 与 parents('.panel') 的差别有两处。第一，closest 从当前元素自身开始匹配，如果自己就带 .panel，会返回自身；parents 从父级开始，不可能返回自身。第二，closest 一旦命中就停止遍历并返回单个元素，parents 会遍历完整条链再返回全部匹配。事件委托里判断”点的是不是某个容器内的东西”，closest 是正解：

next、prev、nextAll、prevAll、siblings 都在兄弟维度：

next 与 prev 只取紧邻的一个，且默认只算元素节点，跳过文本节点和注释节点。这一点与原生 nextSibling 不同——nextSibling 会把空白文本节点算进去。如果混用 jQuery 和原生 DOM 遍历，这个差异会制造 bug。

nextAll/prevAll 可以带选择器参数，等价于先取全部再 filter。

性能差异的根源

jQuery 1.9 内部，不同遍历方法的实现路径差别很大，这直接影响了性能。

flowchart TD
  A[链式调用] --> B{每步产生新 jQuery 对象}
  B --> C[选择器用 Sizzle 查询]
  B --> D[DOM 方法直接遍历节点]
  C --> E[开销较高]
  D --> F[开销较低]
  E --> G[能用原生 DOM 方法的步骤优先]
  F --> G
  G --> H[最终才包装成 jQuery 对象]

核心原则是：jQuery 对象包装是有成本的，每个 jQuery 对象都带 length 属性和几十个方法引用。一条长链式调用中途会创建多个临时 jQuery 对象，这些对象虽然会被 GC 回收，但在热路径上仍有可见开销。

几个具体的优化点。

能用一步选择器就不要拆多步。 $('#list li.active') 比 $('#list').find('li').filter('.active') 快，因为 Sizzle 可以用 querySelectorAll 一次拿到结果，后者要走三次遍历加两次包装。

缩小初始集合再移动。 先 $('#list') 再 find 比全局 $('li') 再 filter 高效得多，因为查找范围小了。

children 优于 find，eq 优于 filter 加下标比较。 前者是单层遍历，后者可能递归。

缓存与去重

end() 与 addBack()（1.9 之前叫 andSelf()）用于回到上一个集合状态，是链式拆分的工具：

这个机制在 1.9 里的实现是维护一个栈。滥用 end() 会让链条难读，但合理使用能避免为了回到上一个状态而重新选择一次。

另一个值得注意的行为是去重。jQuery 内部用 jQuery.unique 保证集合内元素不重复，所以 $('li').add('li') 不会得到两份相同的元素。但跨方法组合时仍可能出现顺序不稳定的情况，依赖元素顺序的代码要显式处理。

$rows.get() 不带参数返回整个原生数组，这是 jQuery 集合与原生数组互通的入口。拿到原生数组后就能用 ES5 的数组方法，性能通常更好。

与原生选择器的配合

2013 年前后浏览器对 querySelectorAll 的支持已经相当普及，简单的遍历完全可以用原生 API 完成，只在需要批量操作或链式便利时才包装成 jQuery。混合使用的原则是：选择用原生，操作用 jQuery。

一个完整的选型速查

把上面的讨论压缩成一张表，实际开发时对照着用即可：

需求 推荐写法 说明
取直接子级 .children(sel) 单层遍历，快于 find
取所有后代 .find(sel) 递归，范围大时注意代价
按条件保留 .filter(sel) 回调需显式返回布尔值
排除符合条件的 .not(sel) filter 的反操作
取某个下标的元素 .eq(i) 支持负数，返回 jQuery 对象
取原生 DOM .get(i) 或 [i] 需要原生属性时使用
判断是否匹配 .is(sel) 返回布尔值，不是集合
含某后代 .has(sel) 筛选而非判断
向上找容器 .closest(sel) 从自身开始，命中即停
事件委托中定位 .closest(sel) 比 parents().eq(0) 高效
兄弟元素 .siblings() 不含自身
转换回原生数组 .get() 之后可用 ES5 数组方法

选型的通用顺序是：先限定查找范围（从最具体的容器出发），再选择深度最浅的遍历方法，最后才考虑链式长度。一条链超过四五步时，通常说明选择器可以重写。

第二个写法把筛选逻辑前移到选择器里，querySelectorAll 一次完成匹配，语义也更直白。它不总是等价于第一个写法（选择器无法表达所有判断），但绝大多数场景下够用。真正复杂到选择器写不出来的情况，再回到链式或者 .filter(function(){})。

小结

jQuery 遍历 API 分筛选类（filter/not/has/is/eq/slice）和移动类（children/find/parent/parents/closest/next/prev/siblings），前者输出集合或布尔值，后者沿树换参照系。关键差异要记牢：children 单层快于 find 递归，closest 从自身开始且命中即停、parents 从父级开始并返回全部，next 只算元素节点而原生 nextSibling 会命中文本节点。性能上每步链式都产生临时 jQuery 对象，能用单步选择器就不拆多步，循环里避免反复包装，热点路径上原生选择加 jQuery 操作的混合写法最快。end() 回到上一个集合状态，get() 转原生数组后即可使用 ES5 数组方法。
