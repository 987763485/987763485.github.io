JavaScript 函数式编程入门：map/filter/reduce

map、filter、reduce 是 ES5 给数组加的三个方法，也是 JavaScript 函数式编程最常用的入口。它们看起来只是”语法糖”，但真正改变的是代码的书写方式：从描述”怎么一步步改”变成描述”要什么结果”。本文从对比与选型的角度，讲清三个方法的回调签名、与命令式循环的等价关系，以及实战中的常见误用。结论先给出：三者适用于”从数组到新数组或单值”的转换，不适合需要中断或产生副作用的场景。

回调签名与 thisArg

三个方法的回调签名高度一致，掌握一个就等于掌握三个。

三个参数的含义相同：当前值、下标、原数组。map 的回调返回值构成新数组的元素；filter 的回调返回值必须是布尔值（实际是”真值/假值”），为真则保留该元素；reduce 的回调返回值是下一轮的 previous。

理解这三个方法最好的方式，是把熟悉的循环翻译一遍。

三者的语义边界可以这样记：map 是一对一变换，filter 是一对零或一，reduce 是多对一。任何从数组出发的转换，基本都能落到这三类里。

纯函数与不可变性

map/filter 的关键约定是：它们返回新数组，不修改原数组。这听起来是废话，但它带来一个重要的性质——回调函数如果是纯函数，整个变换过程就是无副作用的。

纯函数的定义是：同样的输入永远得到同样的输出，且不产生可观察的副作用。遵守这个约定的回调可以安全地复用、测试和缓存；违反它的回调会把数据流搅乱。

性能考量

2013 年前后的实测结论比较一致：三个方法的开销都比等价的 for 循环高，主要成本是回调函数调用。大致量级如下：

方式 相对开销
for 缓存长度 基准
forEach 约为 for 的 1.5 到 3 倍
map / filter 与 forEach 同量级，另加新数组分配
reduce 与 forEach 同量级

结论不是”别用”，而是”别在热路径上无脑用”。一万次以下的数据处理，三者的耗时在毫秒级，可读性收益远大于性能损失；十万次级的热点循环，差距会被放大到几十甚至上百毫秒，此时应回退到 for。

小结

map、filter、reduce 分别对应一对一变换、条件筛选和多对一折叠，回调签名统一为（值，下标，原数组），reduce 额外接受初始值且空数组无初始值会抛错。它们的真正价值不在语法简洁，而在把命令式的”步骤描述”转成声明式的”结果描述”，链式组合让数据处理管道一目了然。要守住纯函数约定：不修改原数组、不在回调里读写外部状态，sort 会原地修改所以链式里要先 slice()。常见误用集中在忘记 return、稀疏数组被跳过、push 与 concat 混淆。性能上三者均慢于 for，热点路径和大数据量场景应合并中间数组或直接回退到循环，小数据量场景优先可读性。
