大列表渲染优化思路

后台系统里动辄几千行的表格、信息流里滚动不完的列表，都会把浏览器拖垮。2014 年初还没有成熟的虚拟滚动库，大家靠的是一套朴素但有效的组合：分页、无限滚动、事件委托和节点复用。本文从源码与架构的角度，把大列表的性能瓶颈拆开，逐项给出可落地的优化手段，并说明它们的适用边界。先说结论：列表优化的第一性原则是控制同时存在的 DOM 节点数量，第二是把单次操作从 N 次降到 1 次。

问题定位：瓶颈到底在哪

遇到列表卡顿，第一反应常是”数据太多了”，但真正的原因需要拆开看。常见的有四类，定位方法各不相同。

flowchart TD
  A[列表卡顿] --> B{卡在哪个阶段}
  B -->|初始渲染慢| C[一次性插入节点过多]
  B -->|滚动掉帧| D[滚动回调频繁触发重排]
  B -->|交互响应慢| E[事件监听器过多]
  B -->|内存持续增长| F[节点未回收或监听器泄漏]
  C --> G[分页 分批插入]
  D --> H[节流 简化回调]
  E --> I[事件委托]
  F --> J[节点复用 及时解绑]

一次性插入过多节点。 三千个 li 用字符串拼接一次性 innerHTML 进容器，浏览器要解析 HTML、创建三千个 DOM 节点、计算样式和布局。这个过程可能就要几百毫秒到数秒，期间页面无响应。定位方法很简单：在插入前后打时间戳，看纯插入耗时占比。

滚动回调里的重排。 监听 scroll 事件并在回调里读取 offsetTop、scrollHeight 这类布局属性，每读一次就可能触发一次强制重排。滚动事件一秒触发几十次，重排被放大几十倍。

事件监听器过多。 每行绑三个监听器，三千行就是九千个。这不仅占内存，事件派发和垃圾回收都会被拖慢。低版本 IE 上尤其明显。

内存泄漏。 节点被删除了但监听器没解绑，或者闭包里持有对大数组的引用，导致整批数据无法回收。表现是切几次页面后浏览器越来越卡。

定位手段在 2014 年还很基础：Chrome 的 Timeline 面板看帧率与脚本执行，Heap Snapshot 对比内存，以及最朴素的 console.time 打点。

分页与无限滚动

最直接的优化是不渲染全部数据。分页是最传统的方案，每页 20 到 50 条，用户翻页才加载。

分页的优点是请求量可控、DOM 数量恒定、URL 可分享、后退键可用。缺点是打断浏览连续性，用户要等待下一页。

无限滚动体验更连贯，但它在 2013 年前后也暴露了不少问题：页脚永远到不了、滚动位置无法记录、内存随滚动无限增长、SEO 内容只在第一屏。实现上的核心不是”滚到底就加载”，而是加载之后要回收：

这个实现里有两个要点。第一是 documentFragment 批量插入，避免每加一行就触发一次布局；第二是 trimList，它把 DOM 节点数压在上限内，是无限滚动不失控的关键。代价是滚回顶部时要重新加载，滚动位置的处理要格外小心。

虚拟列表：只渲染可视区域

虚拟列表（也叫窗口化）是更彻底的方案：无论数据有多少条，DOM 里只保留可视区域加少量缓冲区的节点，滚动时动态替换内容。

  D --> E[滚动时重算区间]

虚拟列表的代价是实现复杂度。行高不固定时（文字可能换行），区间计算和节点复用都会变得很麻烦，这是当年很多自研虚拟列表折戟的地方。务实的分界线是：行高固定、数据量五千以上，值得上虚拟列表；行高不定、数据量几千以下，分批渲染加节点回收就够了。

小结

大列表优化的主线是控制 DOM 节点数量：分页和无限滚动从数据量入手，虚拟列表把节点数压到与数据量无关的常量级，节点复用避免反复创建销毁。第二主线是降低单次操作成本：documentFragment 批量插入、事件委托把 N 个监听器合成 1 个、滚动节流削减高频重排、图片懒加载削减请求与内存。2013 年前后没有成熟库，虚拟列表需要自研，其难点全在行高不固定的场景；行高固定、数据量大的列表才值得投入这份复杂度。定位卡顿先分清是初始渲染、滚动、交互还是内存，四类问题的解法几乎不重叠。
