正则表达式进阶：回溯与性能

本文从一次真实的线上事故出发，把 JavaScript 正则表达式的匹配原理、灾难性回溯的成因、量词与断言的回溯行为、分组与捕获的成本、exec/test/lastIndex 的坑、校验类正则的工程写法，以及 Node 服务端上的同类风险，系统地梳理一遍。适合已经会写基本正则、但在生产环境里被”页面突然卡死”困扰过的前端同学。读完之后，你应当能够一眼认出危险的正则写法，并知道怎么把它改写成线性时间的等价形式。

事后统计，线上有相当一批备注是”长数字串加一个中文标点”的形态，客服页面几乎天天有人误触发。把正则改成 /^[\w-]+(?:,[\w-]+)*$/ 之后，同样的输入在 IE8 里不到 50 毫秒就返回了 false，事故就此终结。

这次事故给笔者上了深刻的一课：正则不是黑盒，test 返回 false 的成本可能是天文本秒，也可能是十几年不返回。”尝试、失败、回退”的回溯机制，是所有基于回溯的正则引擎绕不开的对象。本文就把这个机制讲透，再给出工程上的避险纪律。文中耗时数据均为笔者在不同机器上的实测：部分对照表用当前开发机的 V8 内核跑的稳定数据，事故相关数字则来自当年那台老笔记本上的 Chrome 33 与 IE8，绝对值不可互相换算，但增长量级和曲线形态是一致的。

先把引擎模型讲清楚：NFA 与回溯

要理解性能问题，必须先搞清楚 JS 正则跑在什么引擎模型上。正则引擎大体分两类。第一类是 DFA（确定型有限自动机），它把正则编译成一张状态转移表，对输入串只扫描一遍，每个字符推进一次状态，时间复杂度严格线性，永远不会有”回去重试”的概念。grep 的某些快速通道就是 DFA。第二类是 NFA（非确定型有限自动机），它从正则的角度出发，拿着模式串在输入上”试探”：每遇到一个量词、一个分支，就产生一个不确定的选择，先把选择压进栈，沿着当前分支走下去，走不通再弹出上一个选择换一条路。这就是回溯。

JavaScript 的所有引擎——V8 的 IrRegex、IE8 的 JScript 正则、当时的 SpiderMonkey——全部是带回溯的 NFA，思路接近 Thompson 构造法加一个回溯栈。之所以不用纯 DFA，是因为 NFA 才能记录捕获组的位置、支持反向引用与环视，代价就是可能出现指数级的回溯。

flowchart TD
    A[从位置 0 进入循环组] --> B[分支 1 匹配单个 a 前进 1 格]
    B --> C{还能继续进组吗}
    C -->|能| B
    C -->|不能| D{尾部锚点匹配吗}
    D -->|匹配| E[返回成功]
    D -->|不匹配| F[回退到上一层组换分支 2 尝试 aa]
    F --> C

图里”回退换分支”的每一条路径都会被完整走完才宣告失败。我们用 /^(a|aa)+$/ 匹配 "aaa!" 来看一个完整的尝试表。(a|aa)+ 要求把一串 a 恰好铺满，引擎按”分支顺序优先、外层尽早结束”的策略枚举所有铺法：

序号 分组切割方式（长度序列） 推进到的位置 失败点 引擎动作
1 1+1+1 3 $ 处发现 ! 尝试再多进一组，! 不匹配，弹出
2 1+1+2 — 第 3 组取 aa 时字符不足 回退
3 1+2 3 $ 处发现 ! 回退
4 2+1 3 $ 处发现 ! 回退
5 2+2 — 第 2 组越界 枚举结束，整体失败

n 个 a 用 1 和 2 铺满的方案数正好是斐波那契数 F(n+1)，n=4 时是 5 种，n=10 时是 89 种，n=20 时是 10946 种，n=40 时是 1.66 亿种。输入每多一个 a，尝试次数约乘以 1.618。这就是回溯引擎的账单：它不会”聪明地”知道 1+2 和 2+1 在同一种字符上等价，它只认状态栈。

值得补充的一点是，NFA 引擎内部对”当前匹配位置、程序计数器”这样的状态并不做去重记录（没有记忆化），同一个位置配合同一个组进度会被反复重走。理论上把访问过的状态合并成集合去重，就接近 DFA 的线性表现，一些服务端正则库（比如 RE2）就是这么做的，但那样就放弃了捕获组与环视，JS 引擎不会走这条路。所以对我们来说，能做的只有一件事：写出回溯量可控的正则。

灾难性回溯的三种典型形态

“灾难性回溯”（Catastrophic Backtracking，这个概念以及后来总结出的 ReDoS 一词，早在 2002 年前后就被安全社区讨论了）不是玄学，它几乎总是来自三类可辨认的模式。下面每种形态都给出能复现的代码和实测耗时，输入统一是”n 个字符再加一个非法尾字符”——因为灾难几乎总是在失败路径上爆发，校验正则恰恰是最容易走到失败路径的场景。

形态一：嵌套量词，量词套着含量词的组

(a+)+ 里，外层 + 把整串 a 切成若干段，每一种切法在语法上都合法，切法总数是 2^(n-1)。实测（Chrome/V8）：

输入长度 n（后跟 !） ^(a+)+b$ ^(\w+)+b$ ^(.*)*b$
18 2 ms — —
20 5 ms 6 ms 23 ms
22 22 ms 26 ms —
24 87 ms 104 ms 380 ms
26 349 ms — —
28 约 9 s — 6092 ms

每加 2 个字符耗时约乘 4，即每加 1 个字符乘 2，标准的 2^n。对照实验：把正则改写成 ^a+b$，同样的模式输入 10 万个 a 再跟 !，耗时不到 1 毫秒。作为另一条对照，^(a*)*$ 在纯 a 输入上是”成功路径”，耗时随长度只有轻微增长——引擎对空匹配循环有局部防御。这提醒我们：危险的不是嵌套量词这个形状本身，而是”嵌套量词加失败路径”这个组合。

形态二：重叠交替，多个分支能匹配同一段文本

这就是上文讲过的斐波那契形态，实测（V8）：

n 30 35 40 45
耗时 11 ms 122 ms 1349 ms 14956 ms

每加 5 个字符耗时约乘 11，折合每个字符约 1.62 倍，与斐波那契比例 1.618 吻合到小数点。判断方法很简单：把各分支能匹配的字符串集合画出来，只要有交集（a 与 aa 共享 a，\w 与 \d 共享数字，. 与一切共享），并且外面套了量词，就在爆炸的候补名单上。

形态三：量词组配合反向引用，或分支前缀互相覆盖

反向引用 \1 的加入让引擎不但要枚举切分，还要在每种切分下比对两段捕获内容是否相等，回溯树的节点更贵；实测 ^(\d+)+\1$ 对 n 个 1 加非法尾字符：n=20 时 7 ms，n=22 时 27 ms，n=24 时 110 ms，仍然是每 2 字符乘 4 的指数曲线。^(ab|a)+b$ 则属于分支前缀覆盖：a 是 ab 的前缀，一个 ab 可以拆成”先走 a 分支再补一个 b“，铺法出现二义性，同样触发重叠交替的问题。

三种形态归纳成一句话：一个可以重复的结构，若其内部存在两种以上方式吃掉同一段输入，整个正则就埋了指数炸弹；输入尾部哪怕只有一个不匹配的字符，也足以让引擎把所有铺法枚举干净才回答”否”。

贪婪、惰性与”没有原子组”的现实：靠改写消除回溯

先复习量词的两种消耗策略。贪婪模式（+、*、?、{n,m} 默认）先尽量多吃，失败再一格一格吐出来；惰性模式（量词后加 ?，即 +?、*?、??、{n,m}?）先尽量少匹配，不够了再一格一格多吃。? 在 JS 里有双重身份：跟在量词后面是”惰性修饰符”，跟在普通原子后面是”出现 0 次或 1 次”，写在 (?! 或 (?= 里又是环视的一部分，读正则时要格外当心这三者的位置。

PCRE 和 Java 的 java.util.regex 支持原子组 (?>...) 与占有量词 a++：一旦匹配成功就拒绝交还字符，从而在结构上封死回溯。JS 没有这两个武器，ECMAScript 5.1 规范没有，笔者查了当时 ES6（Harmony）草案的进度，也没有任何要把它们补进来的动向。这意味着在 JS 里对抗灾难性回溯只有一条路：重写正则，让歧义从结构上消失。下面是笔者总结并逐条实测过的几种改写。

  1. 用”排除分隔符的字符类”替代点号。想匹配一个 HTML 标签，<.*?> 的 . 与 > 共享全部字符空间，一旦外层再套量词（如 (<.*?>)+ 匹配一串尖括号）就是灾难；改写为 <[^>]*> 或 <[^>]+>，[^>] 与 > 互斥，每个位置至多一种走法，回溯无从发生。注意：单独一个顶层的 <.*?> 并不会爆炸，惰性点号也只需要线性推进，真正危险的是它进入可重复结构的那一刻，所以从书写习惯上就杜绝 . 进循环体。
  2. 让分支两两互斥。(a|aa)+ 等价于 a+（长度 1 与长度 2 的铺法合起来就是”至少一个 a”），直接改写成 /^a+$/；(ab|ac|ad)+ 这类共享前缀的分支，把前缀提出来变成 a[bcd]，再考察是否还需要重复。凡是能一眼看出”分支并集等于某个字符类”的，都该合并。
  3. 给量词上界。{1,20} 代替 +，把最坏情况的回溯深度锁死在常数内。上界要来自真实业务（备注最长 200 字就写 200），不是为了好看乱加。
  4. 消灭空匹配歧义，把”分隔符结构”写进正则而不是靠通配。(a*)*、(\s*\w+\s*)+ 这类模式，段与段之间的空白归属有两种以上分法。/^(\s*\w+\s*)+$/ 对 28 个单词（空格分隔）后跟非法字符，笔者实测 15275 ms；改写成 /^\w+(?:\s+\w+)*$/——每个空格只属于唯一一个边界——同一输入耗时小于 1 ms。这是”展开”（unrolling）思想：先匹配必现的原子，再用 (?:(?:必现分隔符)(?:必现原子))* 描述重复，保证重复体内没有可空的部件。
  5. 把必匹配的前缀提到循环外。想匹配 key=value 序列，与其 (?:\w+=\w*;?)+，不如先要求第一段必然出现：\w+=\w*(?:;\w+=\w*)*，锚定住起点，失败时能极早退出。

这些改写的共同点不是”写得短”，而是让引擎在每个字符位置至多只有一种推进方式，把回溯次数从指数压回线性。

断言与回溯：零宽的另一面

环视断言 (?=...)、(?!...) 在 JS 里是零宽的：它们检查当前位置之后能否（或不能）匹配某个模式，但无论成败都不消耗字符，匹配结束的位置还是原来的位置。零宽有双重含义：一是能力，允许在同一位置叠加多个条件；二是陷阱，一个纯由断言组成的正则匹配长度为零。

断言本身不引入额外的回溯灾难——它们与普通子表达式一样走回溯流程，只是结果被取反或置空。工程上断言最常见的正当用途是”与”条件叠加，比如密码强度：

每个 (?=...) 从当前位置向后扫一遍，代价是常数次线性扫描，总复杂度仍是线性的。这里的关键在于主体 [a-z\d]{6,16} 自带互斥字符类与上界，断言只是门卫，不制造歧义。用 (?!...) 还能优雅地表达”排除某特征”：匹配不在数字前的 abc，写 /abc(?!\d)/；匹配双引号字符串并允许内部转义，经典写法 /\"[^\"\\\\]*(?:\\\\.[^\"\\\\]*)*\"/ 的每一段都靠字符类互斥保证线性。

麻烦在于后顾断言 (?<=...) 与 (?<!...)。按 ECMAScript 标准，JS 从来不支持后顾——当年所有遵循标准的实现（Chrome、Firefox、Safari、Node）都直接抛语法错误；讽刺的是 IE 的 JScript 很早就非标准地支持了 (?<=，但正因为只有它一家支持，业务代码里等于不可用。需要”前面是某字符”的语义时，笔者的两个替代方案：其一，把”前文”吸收进匹配再用捕获组取回，例如想取冒号后的文件名 (?<=:)\s*([^:]+)，改写为 /:\s*([^:]+)/ 然后读 $1；其二，用循环加前向断言手工扫描，或者干脆 split：匹配”最后一个逗号之后的内容”，与其纠结后顾，不如 s.slice(s.lastIndexOf(',') + 1)，一行代码，零回溯，谁都看得懂。另外切记断言的零宽特性会与全局标志组合出坑：纯断言正则在 g 下每次 exec 都匹配空串，lastIndex 不会自动前进，与下节要讲的死循环是同一颗雷。

分组与捕获的真实成本

分组是正则里少数”有内存账单”的构造。每多一个捕获组，引擎就必须在回溯栈的每个节点上多记录一对位置（起点、终点），失败弹栈时还要逐个回滚；匹配成功后还要为每个组创建字符串切片并组装数组。把同一个模式的捕获组全部换成非捕获组 (?:...)，V8 实测（20 万次匹配，模式含 5 个组）从 8 ms 降到 5 ms——差距存在，约三成，但远不是某些帖子宣扬的”快十倍”。非捕获组的主要收益是语义上的：它明确告诉读代码的人”这里不取内容”，同时少占一点内存、避免 arguments/数组下标被无关分组打乱。神化它的性能的人，多半从来没测过，建议写组时优先按语义决定捕获与否，再在热点路径上统一降级为非捕获。

反向引用 \1 的成本则完全不同量级。它要求引擎不但走到某处，还要把”某个捕获组当时吃进了什么文本”随身带着，回到引用点逐字符比对。这带来两个后果：一是每个回溯节点都多了捕获内容的拷贝，内存与时间同步上涨；二是反向引用让语言脱离了正规语言的范畴（a{n}b{n} 这类”计数匹配”正规表达式理论上无法描述），引擎为普通模式准备的快速通道——比如首字符位图过滤、字面量前缀跳转——大多被禁用。前文 ^(\d+)+\1$ 的实测表已经展示了”分组量词加反向引用”的叠加效果：指数依旧，常数更差。结论：反向引用只在真的需要”前后文本一致”（配对标签名、重复词检测）时使用，纯粹为了分组请用 (?:...)，而 (?<name>...) 这类命名捕获组在 ES5 里不存在，XRegExp 库用扩展语法模拟的命名组底层仍是编号捕获，成本一样。

锚定、预筛与预编译：把成本花在刀刃上

^ 与 $ 是免费的加速器，也是灾难的开关。作为加速器，锚点让引擎在错误起点上只花一步就放弃：^ 使引擎不必在每个起始位置展开回溯树，未命中首字符即返回；实测同一条含 (a+)+ 形态的正则，锚定版本在未命中的输入上毫秒内返回，非锚定版本则在每个偏移重复展开。作为开关，前文的事故也正是因为 $ 强制”全串匹配”，尾部一个非法字符把失败信号推到扫描终点才出现，回溯树已经全部展开完了。多行标志 m 会改变 ^/$ 的语义（行首行尾都算），JS 没有 \A/\z，校验整串时务必确认没有误开 m，否则”每行合法”会被当成”整体合法”。

预编译指的是别让引擎在循环里反复编译正则。规范上，new RegExp 每次调用都产生新对象并触发一次编译，而字面量是否共享编译结果是引擎的实现细节：V8 对同一处字面量只编译一次，但如果你每次循环都用字符串动态拼出 new RegExp('^' + key + '=\\d+$')，编译开销就要自己买单。实测 1 万次动态构造再匹配耗时 15 ms，加一张缓存表（cache[key] || (cache[key] = new RegExp(...))）降到 2 ms；同样的写法搬到 IE8 上差距还要放大一个量级，老 JScript 的编译路径明显更慢。纪律很简单：模式固定的正则提到函数外、模块顶层；模式按关键词拼的，建缓存表。

正则与字符串方法的取舍

能用 indexOf/slice/split 解决的，不要上正则，这不是教条而是账单。实测（V8）：在一条约 10 KB 的长文本里做”是否包含某字面子串”的判断，20 万次 indexOf 共 8 ms，等量 test 共 406 ms——快了五十倍，因为 indexOf 是专门为字面匹配优化的例程，而正则引擎即便匹配一个字面量也要走通用的字节码虚拟机。split(',') 与 split(/,/) 在 V8 里几乎打平（50 ms 对 53 ms，5 万次），但老 IE 上字符串分隔符的实现更朴素也更快。笔者的经验划分如下表：

需求 首选工具 备注
包含/前缀/后缀判断 indexOf、charAt 零回溯成本
按固定分隔符拆分 split（字符串形式） 别写成正则
截取已知结构片段 slice/substring 配合 lastIndexOf
模式化提取、批量替换 正则 按本文规则改写

由此延伸出两条解析纪律。其一，URL 参数解析别用正则硬啃，split('&') 加 split('=') 加 decodeURIComponent 的循环更稳，遇到畸形 URL 还能逐个参数容错。其二，绝不要用正则解析 HTML——标签可以嵌套、属性可以带引号嵌套引号、注释里可以出现伪标签，这些都不是正则能表达的结构；页面内解析请交给 document.createElement 与浏览器自己的解析器，这也是取 URL 各段的可靠办法：

常见校验类正则的写法复盘

前端日常最大量的正则使用是表单校验。复盘几条笔者现在会提交上线的写法。

URL 校验：上面 checkUrl 里那条已经够用——协议白名单开头、主机名按点分段、端口限定 2 到 5 位数字、路径排除空白。它不校验 punycode、不接受 IPv6 字面量、不区分查询与片段，但工程上”结构合理即可，语义交给请求去验证”。邮箱校验：RFC 5322 的合法地址集连规范作者都承认无法用一条常规正则完整表达（引号形式的本地部分、注释、域名字面量地址都不是字符类能描述的），所以目标应该是”拦住 99% 的手滑，放过所有真实地址”：

逐段解释：本地部分由”允许字符的一个串”经”点号加另一个串”重复构成，点号不可能出现在首尾或连续出现，因为它总在两个非空串之间；域名部分要求每个标签以字母数字开头、以字母数字结尾、中间容许连字符，末尾至少一个两级以上的完整后缀。这段没有一处嵌套量词：(?:\.[...]+)* 的循环体必然以一个点号开头、至少吃一个字符，起点唯一，线性。手机号当时这样写就够：/^1[3-9]\d{9}$/（三大运营商号段都落在 13 至 19，逐季再收紧白名单即可）。身份证号：正则只负责”15 位或 18 位的数字串加末位可能的 X”（/^\d{17}[\dXx]$/），真正的校验位必须用代码算——前三行是 17 位加权因子与校验字符表，加权求和后模 11 查表比对，这不是正则该干的活：

日期时间：/^\d{4}-\d{2}-\d{2}$/ 之后必须补数值检查，2013-02-30 能通过结构校验，通不过 new Date(2013, 1, 30) 回读比对；把年月日用捕获组取出转成数字再判断，比写一条八百字的”闰年正则”体面得多。这一节的总原则：正则管”形状”，代码管”含义”，可读性永远优先于炫技的一行流。

服务端视角：同一条正则能拖死 Node 进程

这类问题从来不是前端独占。后台用 Node 0.10 的服务里，事件循环是单线程的，一次 test 卡住十秒，这十秒里所有连接、所有请求全部停摆：

攻击者只需要用一条命令发一个带着 30 个字符加一个全角标点的头部请求，就能以每秒几个请求的节奏把服务器变成砖机——这就是 ReDoS（正则拒绝服务）在服务端的形态，原理与浏览器卡死完全一致，只是受害者从用户变成所有用户。当时的防御手段谈不上优雅但都有效：入口处先限制长度（超过 200 字符直接拒绝，指数炸弹的引信就被剪短了）；能用字符白名单就不要用会回溯的黑名单结构（先 /^[\w-,\s]*$/ 粗筛——单层字符类是线性的——再谈格式）；正则本身按前文四条改写，让危险形状根本不出现；实在需要跑用户可控模式的任务，放 child_process.fork 出子进程，主进程挂看门狗超时 kill，代价是延迟与架构复杂度。服务端的同事在评审表单校验逻辑时，请把”最坏输入长度乘以引擎复杂度”当成一条性能指标来对待。

引擎差异：IE8 的 JScript 与 IE9 之后的 Chakra

最后聊聊跨引擎的现实差异，尤其是万恶之源 IE8。IE8 及更早版本跑的是 JScript 5.8 的正则实现，与 V8 相比有两类差距。一是量级：同样的回溯次数，JScript 每次尝试的常数成本明显更高，事故里同一条正则同一条输入，Chrome 33 在老笔记本上表现为数秒卡死，IE8 则要十几秒，差出近一个数量级；即便是线性路径，老 IE 的 test 吞吐也普遍慢数倍。二是行为：JScript 非标准地支持后顾断言（前文已述），但它不支持 ES5 的若干字符串与正则细节，比如 String.prototype.trim 要在 JS 层补，split 对捕获组进结果数组这类 ES5 语义在老引擎里行为不一致，空匹配与 lastIndex 的交互在不同版本间偶有偏差，跨 IE 的正则循环务必带上下文提到的防御代码。IE9 起引擎换成重写的 Chakra（JScript 9），正则实现对齐标准并大幅提速，到 IE11 基本可以放心；写兼容代码时，性能预算请以 IE8 为下限做测试，因为灾难性回溯在哪个引擎都会发生，而 IE8 只是把账单放大十倍。字符类方面补充两个易错点：. 不匹配 \n、\r、\u2028、\u2029 是所有引擎一致的，想”匹配除换行外任意字符”就老老实实写 [^\n\r]；\d 在任何引擎里都只指 ASCII 的 0-9，全角数字与 Unicode 十进制数字一个都不匹配，\p{...} 那样的 Unicode 属性类直到今天的草案阶段也没轮到 JS，处理多语言字符请显式罗列码段，比如中日韩文字用 [\u4e00-\u9fa5]。顺带备忘：ES6 草案已经在讨论 u（Unicode 精确模式）与 y（sticky）两个标志，2014 年尚无引擎支持，本文所有代码都不依赖它们。

小结

这次事故之后，笔者给自己立下几条使用正则的纪律，抄在这里当作全文的收束：一，凡”可重复结构内部的部件可以吃同一段文本”，即嵌套量词、重叠交替、. 与定界符混写，一律视为 bug 而非风格问题，当场改写成互斥字符类或展开形式；二，所有接触用户输入的正则必须先锚定、再限长，校验函数入口带长度粗筛；三，test 不加 g，exec 循环必带零宽推进防御，replace 复杂逻辑一律函数回调；四，正则只描述形状，校验位、范围、语义交给代码，保证每个模式能被下一个接手的人读懂；五，写危险形状的正则之前先构造”超长加非法尾”的失败样例跑一遍计时，把它当成单元测试固化下来。回溯并不可怕，可怕的是不知道自己正在回溯。
