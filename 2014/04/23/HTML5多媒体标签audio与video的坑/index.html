HTML5 多媒体标签 audio 与 video 的坑

本文属于《HTML 与 CSS》第 10/62 篇
上一篇系列目录下一篇

<audio> 与 <video> 的写法早已不是问题：加个 src、加个 controls，视频就出来了。真正的问题是它今天能播、明天在某台机器上黑屏；在电脑上进度条正常、在 iPhone 上时间永远是 0；写了 autoplay 却没反应；想做页内小窗播放器却被浏览器整屏接管。本文假定你已经熟悉标签与属性，只谈机制与坑：编码与容器、全屏与页内播放、自动播放与 preload、事件与 readyState、缓冲与拖动、音频打断，以及 2014 年这套东西在内置浏览器与 Flash 回退下的现实处境。

编码与容器：一切都从这里开始

最常见的误解是把 video/mp4 当成一种视频格式。MP4 是容器（container），里面装什么编码才是关键：Web 上通常是 H.264（AVC）视频轨加 AAC-LC 音频轨；WebM 容器装 VP8 视频加 Vorbis 音频；Ogg 容器装 Theora 加 Vorbis。所以 canPlayType('video/mp4') 只能回答”这个盒子我打得开吗”，答不了”里面这条轨我解得了解”。要精确探测必须带 codec 串：

返回值只有三种：空串（肯定不行）、maybe（大概是行，没细看）、probably（很有把握）。注意 maybe 不等于能播，这是后面所有降级逻辑都要处理 error 事件的原因。

矩阵里两个”看机器”最要命。其一是 IE：它自己不带 H.264 解码器，直接调用操作系统的能力，所以 Windows 7 未打平台更新的机器、N/KN 版本、精简版系统上，同一个 MP4 就是黑屏。其二是 Android：硬件解码器的档位由 SoC 决定，Baseline/Main/High Profile、Level 上限、分辨率与帧率上限各不相同，同一份视频在某些机型上花屏、有声无画或干脆静默失败。

H.264 走 MPEG LA 专利池要收版税，Google 2010 年收购 On2 拿到 VP8 并承诺免版税，Mozilla 与 Google 都不愿为开放 Web 付这笔钱，所以 Firefox/Chrome 长期不实现 H.264（Chrome 官方发行版能播是 Google 自己买了分发授权，开源构建里没有）。Theora 免版税但同码率画质差一截。后果是一句实践结论：任何单一格式都覆盖不了全部浏览器，MP4 + WebM 是底线，稳妥点再加一份 Ogg。

另外 type 属性别省：不写 type 时浏览器只能发请求嗅探文件头才知道能不能播，白多一轮往返。

转码环节最容易翻车的是 iOS。只保证 Baseline Profile Level 3.0（约 640x480@30fps），High Profile 的 MP4 在 iPhone 上经常是黑屏但有声音。用 ffmpeg 出一份 iOS 友好的 MP4：

-pix_fmt yuv420p 不能省，非 420 的采样硬件解码器不认；+faststart 把 moov 索引盒从文件尾挪到文件头，否则浏览器要等整段下载完（或者发 Range 请求）才能开始播，”边下边播”变成”下完再播”。配套的服务器条件是必须支持 Range 请求、返回 Accept-Ranges: bytes——不支持的话 seek 完全失效，拖动进度条等于重新下载。

流媒体方面，2014 年的现状是四套并存：苹果的 HLS（.m3u8）是 iOS Safari 唯一原生支持的流格式，Safari 6 之后的 Mac 也支持；微软的 Smooth Streaming 靠 IE 加 Silverlight；Adobe 的 Dynamic Streaming 靠 Flash；MPEG-DASH（ISO/IEC 23009-1）年初刚定稿，浏览器一个都不原生支持。MediaSource Extensions 与 EME 当时都还是 W3C 工作草案，只有少数桌面浏览器的实验性实现，几乎没有产品在用。所以”在网页上切码率”在 2014 年的答案仍然是 Flash：非 iOS 平台的自适应流基本靠回退 Flash 播放器解决。

全屏 API 与前缀地狱

Fullscreen API 的前缀状况在当年堪称灾难，而且各家连”方法名末尾那个字母的大小写”都不统一：

CSS 侧同理，:-webkit-full-screen、:-moz-full-screen、:ms-fullscreen 三个写法都得写，::backdrop 只有 WebKit 系有。iOS Safari 完全没有 Fullscreen API；OS X 上的 Safari 只给 <video> 开了一个后门——用 video.webkitSupportsFullscreen 判断能力、video.webkitEnterFullscreen() 让视频自己全屏，任意元素的全屏不支持。也就是说 Mac 上做不到让整个播放器容器（含自定义控制条）全屏，只能让画面全屏。

移动端更没商量。iPhone 上点播放必然跳出原生全屏播放器，盖住整个页面，没有 API 能阻止，控制条是系统那套，想换掉只能放弃原生控件自己拼；而”用一个属性声明让视频留在页内播放”这件事，要到好几年后的 iOS 版本才成为可能。2014 年做”信息流里小窗自动播放”只剩一条路：尺寸伪装——把 video 做得远大于视口，进入系统全屏播放器后再用滚动与定位把需要的那一小块”漏”出来，配合页面背景制造页内小窗的错觉，社区里的 inlinePlayer.js 走的就是这条路。能跑通，代价是黑边、手势被系统吃掉、每次 iOS 小版本都要回归测试。

Android 上是另一种接管：不少厂商浏览器（以及 4.x 之前原生浏览器的部分实现）看到 <video> 的 src 就直接把 URL 丢给系统播放器 App 全屏播，页面里的元素原地不动，timeupdate 之类的事件全部失联。同一份代码在 Nexus 正常、在某国产 ROM 上点了没反应，就是这么来的；兼容性列表里 Android 不能只写一行。

自动播放几乎处处受限

autoplay 在 iPhone 上是彻底无效的，桌面浏览器却基本都听。iOS 的规则是：play() 必须由用户手势（click/touch）直接触发才生效，而且一次手势只解锁一个媒体元素——在同一个 touchend 回调里连调两个 audio.play()，第二个被静默忽略；先 pause() 再想 play()，还得再来一次手势。所以”点一下同时播三个音效”这种需求当年实现不了。桌面 Chrome 到 2014 年 4 月还没有任何自动播放策略，有声静音都能自动播；但 Android 版 Chrome 与各家 WebView 的限制接近 iOS，跨端产品要按最严的一方设计交互。

preload 取 none、metadata、auto 三档，用来控制要不要提前拉数据。iOS Safari 直接忽略它——首屏能拿到的只有 poster 图片，duration 和分辨率都是空的。这意味着 iOS 上”首屏显示视频时长”这个需求只能靠后端把时长渲染进 HTML，不要指望前端探测。

readyState 是 0 到 4 五个整数，理解了它才知道该监听哪个事件：

值 常量 含义
0 HAVE_NOTHING 什么都没确定
1 HAVE_METADATA 拿到时长、分辨率等元数据
2 HAVE_CURRENT_DATA 当前帧可用，但不足以继续播
3 HAVE_FUTURE_DATA 能继续播一小会儿
4 HAVE_ENOUGH_DATA 大概率能一路播完不打断

loadeddata 对应到 2、canplay 对应到 3、canplaythrough 对应到 4。为什么不能用 onload：媒体元素的加载语义和图片、script 完全不同，规范把加载过程拆成了上面这条 readyState 驱动的事件链，load 在媒体元素上是否触发各家实现并不一致，指望它等于把 UI 状态挂在一个不确定事件上。而 canplaythrough 本身也别太信：服务器不支持 Range、或者源是流的时候，Chrome/WebKit 很可能永远不触发它，把”播放按钮出现”绑死在它上面会做出一个永远不出现按钮的页面。稳妥组合是 loadedmetadata 出时长、canplay 出播放按钮、canplaythrough 只用来做提示优化。

事件模型的时序与各家差异

一条正常加载链的顺序大致是这样：

flowchart TD
  A[loadstart] --> B[progress 反复触发]
  B --> C[loadedmetadata]
  C --> D[durationchange]
  D --> E[loadeddata]
  E --> F[canplay]
  F --> G[canplaythrough]
  A --> H[error 加载失败]

逐个说当年的实际行为：

  • loadedmetadata：能拿到 videoWidth/duration 的最早时机，自适应布局该挂这里而不是 canplay。
  • durationchange：可能触发多次。iOS 不预载，第一次拿到的 duration 常常是 Infinity 或 NaN，要靠它修正（下节细说）；流式源的时长本来就会变，也必须监听。
  • timeupdate：规范只约束”平均不大于 250ms、不频繁于 15ms”，各家实际就在 250ms 附近浮动。只用它驱动进度动画会看到一秒四跳，正确做法是用 requestAnimationFrame 每帧读 currentTime 自己画，把它当粗略校正。2014 年 rAF 在 IE10+/Chrome/Firefox/iOS 6 都已可用，老 IE 退化成 setTimeout。
  • waiting 与 stalled：前者是”缓冲不足卡住”，后者是”预期该到的数据没到”。用户看到的转圈要同时监听这两个，只听 waiting 会漏掉慢速网络下的长时间无数据。
  • seeking / seeked：设 currentTime 立刻进 seeking，取到目标帧才 seeked；目标位置未缓冲时中间会夹一个 waiting，UI 上表现为进度条抖一下。
  • ended：播完触发。iOS 上 loop 在部分版本对 video 不生效（尤其进了原生全屏播放器后），要靠监听 ended 手动归零再 play()，而这个”自动重播”不算用户手势、有时会静默失败——当年”循环播放莫名断掉”多源于此。
  • error：MediaError.code 四个值：1 ABORTED、2 NETWORK、3 DECODE、4 SRC_NOT_SUPPORTED。坑在部分浏览器把错误报在 <source> 上而不是 <video> 上，而 source 的 error 不冒泡，所以每个 source 都得单独绑监听。
  • progress：本意是”缓冲区更新了”，用来画下载进度。Firefox 早年实现不完整，实测常常只触发一两次，别拿它当可靠的下载百分比。

时长拿不到与进度条缓冲

iOS 上拿不到 duration 有个流传很广的绕法：seek 到一个极大的时间点，逼解码器把容器读到末尾，duration 就会在 durationchange 里出现，然后再 seek 回 0。

代价是多一次 Range 请求（服务器不支持 Range 时这招直接无效），并且画面会闪一下末尾帧，得配合 poster 或临时遮住。更省事的方案是服务端转码时就把时长写进数据表、直接渲染到 HTML，前端不参与探测。

拖动进度条是另一处重灾区。mousedown/touchmove 每帧设一次 currentTime，浏览器就要 seek 一次，未缓冲的区域还得先发 Range 请求解码，结果就是疯狂抖动、音频爆音、甚至在 Android 上直接卡死。可行方案是拖动期间只更新 UI、不碰视频，松手再 seek；如果产品要求”拖动实时预览”，就把 seek 节流到 200ms 一次，并且只在 buffered 覆盖到的区间内允许实时 seek：

seek 之后要等 seeked 再恢复 UI，否则用户在 seeking 期间又拖一次，画面会停在错误位置。

音频的独占、打断与 Web Audio

<audio> 在 iOS 上播起来会直接打断系统音乐（Music App 被暂停），H5 页面无法申请”混音”或声明音频类别——原生开发里 AVAudioSession 的 category 那套控制，网页没有对应 API。产品侧的后果是背景音乐抢走用户的听歌，投诉落到前端头上，而前端能做的只有”提示用户当前会暂停系统音乐”和”给一个明显的停止按钮”。来电、闹钟响起时音频被系统暂停，pause 事件会触发，但通话结束后不会自动恢复，而且因为脱离了用户手势 play() 调不动，只能等用户再点一次。Android 上是音频焦点问题，2.3 时代暂停后不响应 play()、切后台就断的机型不少。而 <audio controls> 在 iPhone 上的控件条交互能力又很有限，实际项目几乎都是隐藏原生控件自己画。

如果需求是”多个短音效混音、音量包络、可视化”，2014 年可以考虑 Web Audio API：AudioContext 在 Chrome 35、Firefox 25、Safari 6 已可用，iOS 6 起 Safari 也支持（仍需用户手势，采样率固定、内存吃紧，别一次性解码太多大文件）。它用 GainNode 混音、AnalyserNode 拿频域数据画频谱，是”多音效同时响”在当年唯一不用 Flash 的答案，但不适合长音频背景音乐，也照样抢不到 iOS 的混音权。

微信与 QQ 内置浏览器的现实

腾讯系的内置浏览器是当年 H5 营销页的多媒体噩梦，因为媒体行为由容器而不是页面决定。iOS 上是 UIWebView：autoplay 无效、play() 必须在用户手势里、视频一播就被顶到全屏、切后台或锁屏立刻中断。Android 上内置内核会接管 video/audio，用自带的全屏播放器替换页面控件，自定义控制条形同虚设；时长、缓冲这些属性在这里常常拿不到，因为内核根本不预载。

“进入页面自动放背景音乐”这个营销页标配需求当年普遍失败，原因是叠了四层限制：iOS 的手势要求（没有手势就没有播放资格）、网页无法申请音频后台权限（锁屏即停）、容器接管导致控件与页面 UI 不一致、以及移动网络下加载时长造成的”点了没反应”。务实做法只有一种：放一个明确的”点击播放”按钮，借用户第一次点击解锁音频，文案告知可能打断当前音乐，不要偷偷 autoplay。排查时务必区分”iOS WebKit 本身的限制”与”容器额外加的限制”——前者有规范可依，后者只能实测。

降级策略：Flash、poster 与能力探测

2014 年 Flash 仍然是多媒体的兜底主力：它覆盖了 IE 缺系统解码器、Android 老机型、以及各种流格式（Dynamic Streaming/Smooth Streaming 靠 Flash/Silverlight 播）。成熟做法是用现成的播放器库做统一封装——Video.js 4.x 与 Flowplayer 5 都是 HTML5 优先、检测失败自动切 SWF。自己写的话，swfobject 做检测与嵌入：

小结

多媒体标签的坑几乎都不是标签写错了，而是模型理解偏了：容器不等于编码，必须 MP4 + WebM（再加一份 Ogg）多份输出，并记住 iOS 只保证 H.264 Baseline、IE 依赖系统解码器、Android 取决于硬件档位。source 的回退只在 canPlayType 探测阶段可靠，maybe 骗人时得靠 error 事件自己往后退。事件模型要以 readyState 的 0 到 4 为准：loadedmetadata 出尺寸、canplay 出播放按钮，别指望 load，也别把 UI 卡死在 canplaythrough；timeupdate 只有约 250ms 粒度，进度动画必须交给 requestAnimationFrame。移动端的核心矛盾是控制权不在页面上：iOS 强制全屏、忽略 preload、一次手势只解锁一个媒体、音频独占系统播放，Android 与微信/QQ 内置浏览器还会整个接管播放器。所以 2014 年的务实解法仍然是：能力探测而非 UA、自定义控制条而非原生控件、明确的播放按钮而非 autoplay、poster 与 Flash 兜底。
