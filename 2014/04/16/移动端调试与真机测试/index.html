移动端调试与真机测试

上一篇《移动端调试工具与实践》讲的是每个工具怎么用，前提是已经决定用哪个工具。但项目里真正反复争论的往往是前面两步：机型和内核这么多，到底要备哪几台才算安全；预算和排期有限，几种调试方案里哪条路对我们项目划算。本文就谈这两个选型问题，不再重复工具的操作步骤。适合刚开始负责移动 Web 项目测试方案的同学，读完能直接抄走一张最小覆盖矩阵和一份提测自查清单。

2014 年移动 Web 的碎片化现实

先说 iOS。很多人以为 iPhone 用户不用操心兼容，这是错觉。iOS 5 还占着不少份额，它和 iOS 7 之间隔了两代内核：iOS 5 对应 Safari 5.1 时代的 WebKit，CSS 前缀和一些 API 的行为明显更老；iOS 6 补上了远程调试能力；iOS 7 改版后状态栏透明、默认表单控件全部重绘，页头顶部的 fixed 元素会被状态栏压住 20 像素，老页面升级当天就出问题的案例一大把。同一个 Safari 名字下面藏着三代行为，这就是 iOS 的现状。

Android 这边更碎。关键节点是去年底发布的 Android 4.4：WebView 终于换成了 Chromium 30 内核，而且作为独立组件随应用商店升级；在此之前，从 2.3 到 4.3 用的都是老 WebKit 血统，4.0 到 4.3 基本停在 Chrome 18 的代码基线上。粗对照如下：

系统版本 WebView 内核 大约相当于桌面端
Android 2.3 老 WebKit 533 系 Safari 4/5 时代
Android 4.0 至 4.3 Android WebKit 534（Chrome 18 基线） Chrome 18
Android 4.4 Chromium 30（537.36） Chrome 30，可独立升级
iOS 5 / 6 / 7 WebKit 三代分支 各自对应 Safari 5.1/6/7

再往上还叠了两层魔改。一层是厂商 ROM：华为、三星、小米的自带浏览器都是拿 AOSP 源码自己改的，视频被劫持进系统播放器、UA 里塞自家标识、个别 CSS 属性处理不一致都是常事。另一层是第三方浏览器：UC 的 U3 内核、QQ 浏览器、百度浏览器各有各的加速代理，图片预压缩、请求合并，页面跑在里面时已经不完全按标准 WebView 的规则出牌了。所以”我在自己手机上测过了”这句话，严格讲只是宣告”矩阵里这一格没炸”。一台开发机测不完，不是抱怨，是事实。

调试方案横向对比

桌面端习惯了 DevTools 打开就有一切，移动端选型的目标其实是”每个排查场景至少有一条信息通道”。几种方案的能看与不能看，摊开对比：

方案 能看到 看不到 需要的设备与环境
weinre DOM 树、样式、控制台执行 JS 断点、Network 面板、布局渲染信息；所有指令要经服务器中转，有网络往返 一台起服务的开发机，任何能打开页面的手机
iOS 真机加 Safari Web Inspector DOM、样式、console、资源与时间线 调试不了 App 内嵌的 WebView，只有 Safari 页面可查 iPhone 加一台 Mac，数据线，系统 iOS 6 以上
Chrome 远程调试 Android WebView DOM、断点、Network、Timeline，信息量最全 4.0 以下没有通道；4.0 至 4.3 只能调试可调试包，4.4 才顺畅 对应 Android 真机，PC 装 Chrome 32 以上
WP8 模拟器 屏幕画面、布局冒烟 触摸手感、真实性能、JS 调试通道很弱，基本靠注入日志 一台 Windows 8 的 PC，不需要手机
自建日志回传 JS 报错、自定义埋点、真实 UA DOM、样式、网络瀑布什么都看不见，报错之外全靠你埋了什么 任意手机，加服务端一个收日志的接口

前四行的用法在上一篇都写过，这里只比选型。我的结论是分三档：能用系统级远程调试就用它，iOS 靠 Safari Web Inspector，Android 4.4 靠 Chrome 远程调试，信息量最大、零代码侵入；跨平台兜底靠 weinre，代价是看不到的东西比看得到的多；最后的保底是日志回传，它不挑内核、不挑浏览器，UC、QQ 里照样能把错传回来，缺点是只能看你自己打印过的东西。实际项目里三档通常都要，只是比重不同。日志回传贴一段当年在用的最小实现：

拿不到真机时怎么办

项目早期或者出差在外，手边只有一台电脑是常态。这时候要先想清楚哪些结论”模拟出来不算数”。

UA 伪装与 navigator 检测不可靠

测试报告里写”用户是 Chrome”没有任何意义，因为 UA 会说谎。国产浏览器为了不被网站挡在门外，UA 尾巴上挂着 AppleWebKit 和 Safari 是标配，个别 UC 与 QQ 浏览器的版本还直接自称 Chrome 18，把站点骗得团团转——它内核明明还是老 WebKit。伪装史在《navigator 与浏览器检测的取舍》里讲得很细，本文只取测试角度的结论：验证结果必须以”机型、系统、浏览器”三元组记录，不接受”这台手机 UA 显示 Chrome 所以等于 Chrome”这种推论；代码里靠 UA 分支的补丁逻辑，本身就是要重点测的风险点。

桌面模拟能给什么、给不了什么

Chrome 和 Safari 都有拖视口加模拟 touch 的设备模式，快速过布局、验证媒体查询完全够用，改一行 CSS 刷新十秒搞定，这是它划算的地方。但它模拟不了三样东西：内核行为差异（桌面 Chrome 再快也是 Chrome 30 级别的解析器，替 2.3 上的老 WebKit 说话没有效力）、真实的触摸手感（惯性滚动、双击缩放的时序都是另一套）、以及硬件资源上限。所以桌面模拟适合”改样式时提效”，不适合”出测试结论”。

只能真机复现的坑

下面这些，模拟环境测不出来，谁模拟谁上当：

  • 300ms 点击延迟：双击缩放判断发生在原生层，桌面拖视口永远等不出这一拍；
  • 软键盘顶起页面：键盘弹出时视口怎么变、window.innerHeight 变不变，各家行为不同，必须真机敲一遍表单；
  • position: fixed 抖动：iOS 上滚动时 fixed 元素跟着晃甚至跳位，纯渲染层问题；
  • video 自动播放：iOS Safari 要求用户手势才起播，且一播就被系统全屏播放器接管，桌面模拟里设置 autoplay 就会播，完全两回事；
  • 图片内存上限：低端 iPhone 上解码面积超限直接白图甚至整页重载，桌面内存管够，测不出来；
  • iOS 截图与滚动条：系统截图只截当前视口，长页效果要肉眼翻页验收；滚动条只在滚动瞬间出现，”内容还能不能滚”这类判断模拟环境里做不了。

真机从哪来

选型选到最后都是采购和制度问题。三条路各有适用面。

自建机型池

小团队预算有限，买机标准我建议按”份额乘以内核差异再除以价格”来排优先级：份额决定问题暴露量，内核差异决定它代表不代表一族机型，价格决定你能铺多宽。当年我们花三千多块凑了第一批：一台 iPhone 4S 守 iOS 6 老内核加低端内存，一台 iPhone 5 跑 iOS 7 主流，一台 HTC 老机器留着 2.3 的坑，一台三星 Galaxy S3 代表 4.1 加厂商定制浏览器，一台红米代表 MIUI 用户群。Nexus 5 是后来补的，专门看 Chromium 30 新内核的行为。每加一台新机，先问它覆盖了矩阵里哪一格空白，问不出来的不买。

轮流借用制度

自建池解决”常驻机型”，长尾机型靠制度。我们的做法是设一个共享设备架，同事手里的旧手机登记后统一贴标（型号、系统、可借周期），版本测试期由测试同学按清单签出，用完归位。成本几乎为零，两年里从同事手里”众筹”出了七八台不在矩阵主格但偶发问题集中的机型。

云真机与众测平台

2014 年 Testin、百度云测这类第三方云测试服务已经做起来了，平台上挂着几百款真机可以远程点选。要划清它们的适用边界：跑批量兼容性截图、装机与崩溃收集非常合适，版本发布前拉一份几百机型的兼容报告给产品和测试看，性价比高；但深度调试不行——没有稳定的调试通道，操作排队延迟大，弱网、键盘这些场景基本碰不到。Appium 这类开源自动化方案 2011 年就有了，今年 3 月刚发布 1.0，可以拿来做批量冒烟脚本，但别指望它替你判断”这个动画卡不卡”。一句话：云真机管广度，自有真机管深度。

测试矩阵与优先级

把前面的东西收拢成一张最小覆盖矩阵，按我们项目当时的用户份额（百度统计看系统版本分布，友盟和 GA 交叉验证机型集中度）填出是这样：

档位 机型与系统 浏览器 / WebView 网络 优先级
iOS 主流 iPhone 5，iOS 7 Safari，微信内 WebView WiFi P0
iOS 低端 iPhone 4S，iOS 6 Safari 3G 限速 P0
Android 老内核 HTC 2.3 自带机 自带浏览器，UC 2G / 3G P0
Android 主流 Galaxy S3（4.1），红米（4.2） 厂商自带浏览器，QQ，百度 3G 限速 P0
Android 新内核 Nexus 5，4.4 系统 WebView，Chrome WiFi P1
Windows Phone Lumia 520，WP8 IE10 WiFi P2，按份额决定投不投

份额数据每季度刷新一次，矩阵里哪个格子盖住的真实用户掉到 3% 以下，P0 就降 P1，有新机型冲进前列就补格子。网络维度别偷懒：手机挂上 Charles 代理，用 Throttle 的 3G 预设再手动把延迟调高，首屏真实秒数立刻现形，这一步在有真机通道的方案里成本最低、收益最大，建议直接固化进每次提测。

常见兼容问题的分类定位套路

把历史 bug 按类归档之后，每类都能总结出一条最短定位路径。

布局类

案例：iOS 7 升级当天，首页搜索条整体下移了 20 像素——系统状态栏变透明，页面默认顶到屏幕最上沿。定位路径：先确认问题只在 iOS 7 出现，再拿 Safari Web Inspector 看视口高度，发现 fixed 定位基准变了。补一条 meta 与顶部占位的分支逻辑解决。布局类的套路是：先分内核代际，再分视口基准，最后才怀疑具体 CSS。

事件类

案例：页面在 WP8 的 IE10 里按钮全部点不动。原因很简单，只绑了 touchstart，而 IE10 走 Pointer Events 那一系。定位路径：拿日志回传确认事件根本没进处理函数，再在点击入口统一走 click 加库兜住延迟，不再裸绑 touch。事件类的套路是：先判断”事件到底有没有派发”，再谈处理逻辑，别一上来就怀疑业务代码。

媒体类

案例：视频页在三星自带浏览器里一播放就被弹进全屏系统播放器，自制的进度条和封面全失效。定位路径：同一 URL 在 Chrome 和自带浏览器各放一遍，确认是厂商 ROM 劫持而非代码问题，最后按浏览器家族分别降级——劫持不可控的机型退回静态封面加跳转链接。媒体类基本是厂商定制的重灾区，套路是”同机型换浏览器对照”，两分钟就能把内核问题和 ROM 问题分开。

性能类

案例：Android 4.1 的老机器上列表滚动严重掉帧。定位路径：4.4 上先用 Chrome 远程调试的 Timeline 确认是每帧重绘面积太大，回头把 box-shadow 加大圆角的组合从滚动容器里拆出去。老内核拿不到 Timeline，就在滚动循环里打时间戳回传。性能套路的核心是先定瓶颈层——网络、脚本还是绘制——再优化，跨机型对比时间戳往往比盯着单机看更有信息量。

输入法类

案例：中文输入法下昵称字数校验疯狂误报超限。原因是部分 Android 浏览器在候选拼音阶段就开始连续触发 input，字数按拼音字母算了一遍。定位路径：真机上分别用系统英文键盘和中文键盘各录一遍事件序列，差异立刻暴露；处理上输入法组合期间的值不参与校验。这类坑模拟环境根本不存在，也再次说明为什么必须有一台装着中文输入法的真机常驻。

提测前自查清单

下面这份是我们组贴在工位上的版本，可以直接抄走改成自己项目的：

  • viewport 声明正确，页面在三个宽度档（320/375/480 逻辑像素）下无横向滚动；
  • 代码里没有靠 UA 猜内核的分支，特性判断全部改为能力检测；
  • Android 2.3 与 4.0 系自带浏览器各跑一遍主流程，UC 单独再跑一遍；
  • iOS 6 与 iOS 7 各过一遍带 fixed 顶底栏的页面；
  • UC、QQ、百度三款第三方浏览器覆盖核心路径；
  • 全表单页真实弹出软键盘，验证遮挡与页面回弹；
  • Charles 限速到 3G 预设，记录首屏完成时间；
  • 最大尺寸图片检查白图与整页重载，页面解码面积合计有数；
  • video、audio 在各机型确认手势起播与全屏行为符合产品预期；
  • 高频点击操作验证 300ms 感知，必要时接入 fastclick 并回归双击场景；
  • window.onerror 回传已开启，提测包里能看到自己的日志落库；
  • 横竖屏切换、iOS 7 后退缓存页各试一次。

小结

移动端的测试问题本质上是覆盖问题：碎片化的内核与 ROM 决定了不可能一台机测完，能做的是把”测哪几台、怎么调、信哪些结论”变成显式决策。调试方案按信息量分档，系统级远程调试优先，weinre 兜底，日志回传保底；桌面模拟只用于提效，涉及触摸、键盘、内存、媒体劫持的结论必须出自真机。机型来源上，自建池管常驻主力格，借用制度补长尾，云真机跑批量兼容性报告。矩阵按季度用真实份额刷新优先级，弱网限速固化进流程。最后，把自查清单贴在每次提测的入口，让同类坑只踩一次。
