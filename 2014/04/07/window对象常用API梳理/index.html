window 对象常用 API 梳理

window 是 JavaScript 里最大的那个对象：既是全局作用域的载体，又是脚本接触浏览器的一切入口。很多人天天用它，却只熟悉零星的几个属性。本文不做手册式的罗列，而是按性能与调优的视角，把每个常用 API 讲清楚三件事：开销在哪、坑在哪、2014 年的正确写法是什么。适合还在同时伺候 IE8 和 Chrome 33 的页面开发者。

window 的双重身份：全局对象与 BOM 入口

window 戴着两顶帽子。在语言层面，它是全局对象：顶层的 var 声明和未声明的直接赋值，最终都会变成挂在它身上的属性。在浏览器层面，它是 BOM 的入口，文档、事件和绝大部分浏览器能力都从这里出发。location 与 history 笔者上一篇《location 与 history 对象详解》已经专门讲过，navigator 也另有专文，本文只谈 window 自身。

先说”顶层 var 就是 window 属性”这件事的细节。用 var 声明的全局变量会成为 window 上不可删除的属性，delete window.foo 返回 false；而没有声明就赋值的”泄漏变量”生成的属性倒是可删的，但这不是优点，是事故。在没有严格模式的代码里，函数内部忘了写 var，变量就悄无声息地落到了 window 上。严格模式（'use strict'）会把这种赋值直接变成 ReferenceError，IE10 已经支持它，Chrome 与 Firefox 支持得更早，2014 年没有理由不用。

全局污染带来的第一类真实问题是命名冲突。笔者曾被第三方广告脚本坑过：页面顶层声明了一个 util，广告脚本也往 window 上挂了一个 util，我的工具方法瞬间蒸发，排查了半个下午。页面控制不了会加载哪些脚本，全局命名空间就是一片没有锁的公共草地。第二类问题是查找开销：标识符要沿作用域链一层层向上找，找不到才落到全局对象上问一次，函数嵌套越深、全局引用越多，这条路越长。做了个粗略计时，在 Chrome 33 的桌面上跑 1 亿次循环：

尺寸与滚动：三组容易搞混的数字

尺寸读数最容易混的是两组：window.innerWidth / innerHeight 是窗口内部尺寸，包含右侧滚动条占的那一条，IE9 才有；document.documentElement.clientWidth 是不含滚动条的布局视口宽度。差值约等于竖向滚动条宽度，Windows 桌面上一般 17 px 上下。做”是否放得下浮动条”这类判断用 innerWidth，想让数值和 CSS 里的长度对齐用 clientWidth，混用就会出浮动元素错位 17 px 的经典 bug。滚动位置的读取更碎：pageXOffset / pageYOffset 从 IE9 起可用；scrollX / scrollY 当时只有 Firefox 认得稳，Chrome 与 IE 上不要碰；IE8 及以下只能读 documentElement.scrollTop，且页面一旦是 quirks 模式，值会挪到 body.scrollTop 上：

定时器：setTimeout、setInterval 与 rAF 的隐藏开销

定时器的坑都在运行时层面，看文档是看不出来的。第一，最小延迟不是 0。HTML5 规定定时器嵌套层次超过 5 层后，延迟会被强制抬高到不小于 4 ms，参数写多小都没用；老 IE 的系统时钟粒度在 10 ms 上下，IE6/7 上这个下限更高。所以”用 setInterval(fn, 1) 做精确节拍器”这种需求根本不存在正解，定时器只能保证”不早于”，不能保证”恰好”。

第二，后台节流。Chrome 33 与 Firefox 28 都会把后台标签页的定时器夹到约 1 s 一跳，IE10/11 行为宽松些但也会收紧；移动端的 WebView 更干脆，应用退到后台往往直接冻结全部定时器甚至挂起整个页面。依赖 setInterval 数秒做倒计时或心跳的业务，切回前台时会发现数字全乱了，必须用时间戳重算而不是累加次数。

第三，两种必须禁掉的写法。一是给 setTimeout 传字符串，它等价于一次隐式 eval：拿不到当前闭包作用域、每次执行都重新解析、并且被 CSP 的 unsafe-eval 明令禁止，启用严格安全策略的站点上直接不执行。二是 this 的默认绑定：非严格模式下定时器回调里的 this 指向 window，严格模式下是 undefined，类方法里直接传 this.method 会丢上下文：

其它容易踩的零碎 API

alert / confirm / prompt 是同步阻塞渲染与脚本的，在移动端还有一层尴尬：不少 App 内嵌 WebView 会把当前页面 URL 直接印在弹窗上，微信内置浏览器就是这个做派，你藏了半天地址栏，一个 alert 全抖出来。提示和确认一律换自定义浮层，alert 只留给调试。

window.name 容量以 MB 计，远超 cookie 的 4 KB，而且跟着窗口跨页面、跨域导航存活。老 hack 用隐藏 iframe 加 window.name 当跨域数据桥，或者在多步表单之间传大参数。但它是明文，同一个窗口里后来加载的任何文档都读得到，敏感数据放进去就是事故。

scrollbars、statusbar、toolbar 这类 window.open 特性串，以及 window 上对应的同名遗留属性，属于浏览器定制时代的文物，当年主流浏览器已经基本无视，别再依赖也别再读。

性能与调优清单

把全文收拢成可执行的清单，新项目照着自查：

  • 不要在 window 上挂大对象或 DOM 引用。全局属性连同闭包会把整棵子树扣在内存里，页面切换后 GC 也带不走；大缓存一律放模块闭包内，配淘汰策略。
  • 监听器收进统一命名空间：绑定时把 target、类型、函数名三元组登记到 App.listeners，销毁视图时遍历解绑。匿名函数一绑就断了自己的退路。
  • setInterval 与 requestAnimationFrame 必须配对清理：clearInterval 对不上 start，cancelAnimationFrame 与 rAF 一起判断存在性，降级路径尤其容易漏。
  • resize、scroll 这类高频事件先过防抖或节流；scroll 处理器里只记账（存下当前位置），真正的重排操作攒到下一帧 rAF 里做。
  • postMessage 走 JSON 序列化，大载荷的序列化与反序列化都是同步开销，传增量不传全量，超过几十 KB 就该怀疑架构。
  • 定时器逻辑永远考虑后台节流与移动 WebView 挂起：用时间戳校准，不用累加计数。

小结

window 的双重身份决定了对它的两种态度：作为全局对象，要像管理公共资源一样管理它，IIFE 封装、只挂一个命名空间、热点路径缓存到局部；作为 BOM 入口，要清楚每个读数的边界——innerWidth 与 clientWidth 差一条滚动条，pageXOffset 止步 IE8，setInterval 有 4 ms 下限和后台 1 s 节流，弹窗拦截会让 window.open 返回 null，postMessage 两头都必须校验 origin。性能层面记住三条主线：高频事件防抖、定时器与动画帧配对清理、不给 window 留大对象与 DOM 引用。这些约束在 IE8 到 Chrome 33 之间都能同时成立，把它们写成工具函数，比背 API 列表值钱。
