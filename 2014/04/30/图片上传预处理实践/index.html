图片上传预处理实践

本文记录我们在移动 Web 项目里落地”图片上传前先在浏览器里处理一遍”的完整过程：链路怎么分层、每一层的 API 怎么选、EXIF 方向这种坑怎么绕、以及与后端的协议怎么设计。适合正在做移动端拍照上传、被弱网和大图折磨的前端同学，读完可以直接照着把链路搭起来。

为什么要在上传前做预处理

先算一笔账。iPhone 5 拍一张 800 万像素照片（3264 x 2448），原始 JPEG 大约 2-3 MB；2014 年国内 3G 上行普遍只有几百 KB/s，4G 刚起步且覆盖不稳，一张原图传上去动辄十几二十秒，进度条一动不动的场景下用户直接关掉页面的比例非常高。再叠加流量资费按 MB 计费这个现实，让用户替一个可以被压缩掉的文件掏钱，本身就是体验问题。

Android 侧更惨。我们在 Android 2.3 的自带浏览器上测试过把 dataURL 整段塞进表单字段提交，WebView 的 JS 堆直接撑爆，页面连同输入法一起卡死。结论很明确：大图不能原样进内存，更不能原样走网络。

于是目标定为四步闭环：”读进来 - 缩一遍 - 压一次 - 再传”。全部在浏览器里完成，服务端不参与预处理，只负责接收成品。下文按链路的层次展开，每一层给出实现代码与当时的实测取舍。

链路分层

整条链路我把它切成六层，每层只做一件事，层与层之间只传递明确的数据形态（File 对象、Image 对象、canvas、dataURL、Blob），这样单独替换任何一层都不影响其他层，比如把 FileReader 换成 createObjectURL 只动第一、二层。

flowchart TD
  A[选择文件 input type=file] --> B[读取层 FileReader 或 createObjectURL]
  B --> C[解码层 Image onload]
  C --> D[缩放层 canvas 逐步减半 drawImage]
  D --> E[编码层 toDataURL jpeg 0.7]
  E --> F[还原二进制层 dataURL 转 ArrayBuffer 转 Blob]
  F --> G[上传层 XHR2 FormData]
  G -->|失败| H[降级 iframe 表单提交]
  H --> G

分层带来的最大好处是失败可以精确定位。真机上排查问题时，只要在某一层打日志看数据形态是否还是预期的，就能判断是哪一层先崩的——iOS 白屏多半出在缩放层触碰了 canvas 面积上限，Android 2.3 假死多半出在还原二进制层之前的 base64 长字符串上。

读取与解码层：两条路线的内存差异

两条路的内存差异很大。FileReader 方案会让一张 3 MB 的照片在 JS 堆里同时存在两份膨胀副本（base64 字符串约 4 MB，加上转码开销），而 dataURL 是字符串，字符串在 WebKit 里是不可变的，后续 img.src = dataURL 解码时又会产生位图内存。createObjectURL 只是给文件句柄起了个 URL，Image 解码走的是浏览器内部的流式路径，JS 侧几乎不占堆。所以解码这一环优先用 createObjectURL，FileReader 留给两个场景：需要读原始字节做 EXIF 解析（后文重点），以及老 WebKit 上 createObjectURL 不可用的兜底。

revoke 时机上有个真机坑：iOS 6 Safari 在 img.onload 里立刻 revoke，个别情况下解码线程还没交还数据，drawImage 出来是空白。稳妥做法是 revoke 延迟到 onload 之后的下一个 tick，或者干脆把 revoke 放在 drawImage 完成之后。

缩放与编码层：canvas 尺寸上限与压缩率

缩放层用 canvas.drawImage 完成，但有两个必须先想清楚的问题：画布开多大、怎么缩才不糊。

canvas 尺寸上限是这条链路里最容易翻车的硬件约束。iOS Safari 对单个 canvas 的总像素数和内存占用都有红线，一张 3264 x 2448 的照片如果先建一个原尺寸画布再缩，RGBA 就是约 30 MB，iPhone 4S 上大概率直接白屏重载页面。所以第一步永远先把最大边长限制住（我们默认 1024，可被后端配置覆盖），而且第一步减半直接从 img 画到半尺寸画布，全程不出现原尺寸 canvas：

为什么逐步减半而不是 drawImage(img, 0, 0, fw, fh) 一步到位？当时各平台 canvas 缩放实现参差不齐，一步跨越大比例时 Android 自带浏览器会出现明显的锯齿和细节丢失，减半路径每一跳都是 2:1 采样，质量稳定得多。代价是多几次画布分配，用 width = height = 0 及时回收中间画布后，实测峰值内存只增加一档而不是线性增长。

编码层就是 canvas.toDataURL('image/jpeg', quality)。第二参数的压缩率我们用同一张 2.7 MB 样张（3264 x 2448，缩到 1024 边长后）在 iPhone 5 上实测：

质量参数 成品体积 主观质量（真机屏幕）
0.9 412 KB 与原缩图几乎无差别
0.8 268 KB 发丝级细节略软，可接受
0.7 181 KB 噪点开始可见，屏幕上看无碍
0.5 89 KB 天空渐变出现色带，文字边缘毛刺

结论是 0.7 是性价比拐点：体积已经不到原始数据的 7%，屏幕观看与 0.9 档拉不开差距。这里要特别提一句 toBlob——Chrome 与 Firefox 的新版本里已经有 canvas.toBlob()，能省掉 base64 中转，但当时 iOS Safari 和 Android 自带浏览器都没有，主流做法仍是手工把 dataURL 转回二进制，下一节讲。

EXIF 方向：本链路最大的坑

复盘一次线上事故。用户反馈”竖着拍的照片传到社区里全躺下了”，部分 Android 机型还旋转了 180 度。原因不在我们的代码，而在 JPEG 的 EXIF 元数据：iPhone 和部分 Android 相机并不旋转像素，而是写一个 Orientation 字段（1 到 8 值），由看图软件负责旋转。照片解码进 canvas 时，Safari 当时的 Image 解码会按 Orientation 自动摆正，Android 自带浏览器则原样解码——同一份 canvas 代码在两端表现相反。而 toDataURL 之后 Orientation 字段彻底丢失，躺倒就永久固化了。

当时可选的解法有三种：服务端处理（上传原图再旋转，流量问题一个没解决，否决）；强制用户横屏拍照（改变用户习惯，否决）；前端自己读 EXIF、自己旋转画布（采纳）。

读 Orientation 不需要完整 EXIF 库，字段就在 JPEG 头部 SOI 之后的 APP1 段里，取前 64 KB 足够：

拿到 orientation 后在缩放层里用 ctx 的 transform 旋转画布再 drawImage，常见的是 3（转 180 度）、6（顺时针转 90 度，iPhone 竖拍最常见）、8（逆时针 90 度），2/4/5/7 含镜像概率低可以只处理旋转：

还有一个两端行为不一致的收尾：既然 Android 上 Image 解码不带自动摆正，iOS 上带，那 orientation 是不是应该只在 Android 分支应用？我们最终的做法是不区分平台，统一读 EXIF 并显式旋转，但在 iOS 上先对比”带 rotate 与不带 rotate 的成品”确认解码器行为后再决定开关——把平台差异变成配置，而不是散在 if 分支里的经验直觉，这条原则后面救过我们一次（iOS 7 测试版改了自动摆正行为，改一个开关就发布了）。

还原二进制与上传层

dataURL 是 base64 字符串，base64 每 3 字节编成 4 字符，膨胀约 33%，再加上 dataURL 本身不能直接进 multipart。为什么不把 dataURL 整段丢给服务端？除了膨胀，还有三个理由：字符串进 JSON 会被转义再膨胀一轮；服务端要重新解码校验 MIME 前缀；网关对超长表单字段有截断风险。所以上传前把 dataURL 手工转回二进制：

坑在于：加了 capture=camera 的部分 Android 2.3 机型连相册入口一起消失，用户没法选已有照片；而 iOS 上该值并不强制只开相机，只是倾向。我们的结论是 accept 用 image/* 即可，capture 只作为提示不作为依赖，页面上把”拍照”和”从相册选”做成两个入口分别绑不同的 input，行为可控得多。另外 Android 4.0 以下自带浏览器读相册大图的 onload 有概率不触发，解码层要加一个 8 秒的看门狗定时器，超时即走降级。

踩坑清单

最后把散落各层、值得单独记住的坑列一遍：

  • GIF 动图不能走这条链路。canvas 只画第一帧，转 JPEG 后动图变成静图，检测 MIME 是 image/gif 直接跳过预处理传原文件。
  • 透明 PNG 转 JPEG 会变黑底。canvas 没有底色的区域按黑色合成，正确做法是填充时 ctx.fillStyle = '#fff' 先铺一层白再 drawImage，或者对 PNG 保留 image/png 编码。
  • iPhone 4S 的 canvas 内存红线明显低于 5，连续处理三张照片不释放中间画布就会白屏。每个临时 canvas 用完置 width = height = 0，比 delete 引用有效。
  • EXIF 里带 GPS 坐标。照片原样上传等于把用户拍摄位置公开，前端 toDataURL 之后像素归像素、元数据全部丢弃反而意外成了隐私保护；但凡走”原图直传”降级路径的，必须提醒服务端剥 EXIF。
  • HEIF 之类的新格式 2014 年还不存在，不用考虑；但 bmp 在个别 Android 浏览器能选不能解码，onerror 分支要接得住。
  • 看门狗、timeout、revoke 延迟这三件事都要配置化，浏览器内核的小版本行为差异比想象中频繁。

小结

移动端大图上传的问题，本质是把”网络成本”前移成”端上计算成本”，而 2014 年的手机处理一张图的解码缩放编码远快于弱网传 3 MB，这笔账是划算的。链路上六个层各自只依赖一种数据形态，FileReader 与 createObjectURL 按内存场景二选一，缩放务必先卡最大边长、逐步减半保质量，编码 0.7 是实测性价比拐点。EXIF 方向是这个领域最阴的坑，两端解码器行为不一致，统一读 Orientation 字段显式旋转、行为开关配置化才是正解。上传前把 base64 还原成二进制再走 XHR2 FormData，老设备用 iframe 表单兜底。参数协商交给服务端配置，前端只做执行者，链路才能不跟着发版跑。
