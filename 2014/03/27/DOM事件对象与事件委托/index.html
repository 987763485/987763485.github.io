DOM 事件对象与事件委托

上个月写了《jQuery 的 on、off 与事件委托》，讲的是库的 API 怎么选、老代码怎么迁。发出去后收到几条留言，问的其实是同一件事：抛开 jQuery，事件对象本身到底长什么样？我复盘一遍发现，jQuery 替我们抹平的那些差异，只有自己动手抹过一次才算真懂。所以本文只讲原生这一层：事件对象从哪来、怎么在树上走、有哪些属性、各家差在哪、怎么自己造一个，最后用三十行 ES5 写一个能上生产的委托。适合 jQuery 用得熟、但还没翻过 DOM Events 规范的读者。库的 API 与选型本文一律不重复。

顺带提一个安全隐患：老 IE 的 window.event 会一直指向页面上最后一个已派发的事件，而事件又通过 srcElement 拽着那个 DOM 节点。如果你在闭包里把 window.event 存了下来，就等于存了一条通往节点的引用链，节点从文档树上摘掉也回收不掉——结论同《DOM 事件移除与内存泄漏》：只要有一条可达路径，节点连同闭包引用的对象就全都留着。正确做法是进处理器先把需要的值取成局部变量，之后不再碰那个对象。

传播三阶段与第三个参数

一个点击不是”发生在某个元素上”，而是”沿着一棵树走一趟”。DOM Events 把这趟路切成三个阶段：从 window 一路向下走到目标元素的捕获（capturing，eventPhase === 1）、目标元素自身的处理（eventPhase === 2）、再一路向上回到 window 的冒泡（bubbling，eventPhase === 3）。

flowchart TD
    A[window 与 document] --> B[html]
    B --> C[body]
    C --> D[ul 列表容器]
    D --> E[li]
    E --> F[span 被真正点到的文字]
    F -.冒泡.-> E
    E -.冒泡.-> D
    D -.冒泡.-> C

addEventListener 的第三个参数就是这两条支路的选择开关：true 表示只在捕获阶段调用，false（默认）表示只在冒泡阶段和目标阶段调用。它就是个布尔值，传别的数字会被按真假处理，想同时要两个阶段只能绑两次。至于在这个参数里塞配置对象那套思路，2014 年还没有任何一个发布版本做到可用，规范本身也仍在反复，业务代码里不要指望它。

一趟路上谁先执行？同一元素、同一阶段内按绑定顺序执行；不同元素则由树的深度决定，越靠近目标越先跑。老 IE 的 attachEvent 完全没有捕获这条路，只有冒泡，而且顺序是后绑的先跑，这点和标准相反，跨浏览器排查执行顺序时是头号嫌疑人。

捕获阶段的价值常被低估，最常见的误用场景就是”上游有人 stopPropagation，我收不到事件”。看这句：

捕获阶段的监听器跑在目标元素之前，所以下游怎么掐都掐不到它；反过来，如果祖先在捕获阶段就 stopPropagation，事件根本到不了目标元素，目标自身的处理器一次都不会执行。这是当时统计埋点、以及给不冒泡的 focus 做委托（后文有坑）唯一靠得住的入口。

target、currentTarget 与 this

三个概念必须先分清：target 是被真正操作的那个节点，currentTarget 是当前这个处理器绑定在哪个元素上，eventPhase 决定这两者是否相等。在目标阶段它们相同，在捕获与冒泡阶段 currentTarget 一定比 target 更靠上。委托的全部机制都建立在”这两个不一样”之上。标准里处理器里的 this 等于 currentTarget，也就是绑定元素本身——注意这对委托意味着什么：监听器绑在容器上，this 就是容器，而不是被点的那个 li。jQuery 的委托处理器里 this 指向命中元素，那是库额外用 call 帮你改的，原生不会替你做到。同理，如果你把处理器当普通函数调用（handler(e)），this 就掉回 window；必须显式写 handler.call(hit, e)。

属性层面的差异更多，一张表过一遍：

标准属性/方法 老 IE（8 及以下） 备注
type type 无
target srcElement 值等价，名字不同，必须双写兜底
currentTarget 无 老 IE 里只能自己沿祖先链算
eventPhase 无 老 IE 分不清捕获与冒泡
relatedTarget fromElement / toElement mouseover 用 fromElement，mouseout 用 toElement；标准下两者统一成一个 relatedTarget

relatedTarget 值得多说一句：mouseout 时它表示鼠标即将移入的那个元素，判断”是不是真的离开了容器”就靠它——沿祖先链检查 relatedTarget 是否落在容器内，是则忽略。这是当年手写 hover 效果的标准解法，比 mouseover 计数可靠得多。

还有一个坑要单独拎出来：e.target 不保证是元素。某些浏览器（早期 Firefox 与 WebKit 都有过）会把文本节点当 target 抛出来，注释节点在老 IE 的部分 API 里还带着 #comment 这种假标签名。所以沿祖先链上溯匹配选择器的代码，第一件事是判 nodeType === 1，否则 querySelectorAll 匹配不到，还可能在一个没有 querySelector 方法的文本节点上取 className 直接报错。

取消默认行为与停止传播的三套写法

同一件事有三套 API，各自的规则不同，混用时最容易出错的是返回值。

规则分三条说清：

  • DOM2（addEventListener）：只认方法。preventDefault() 取消默认动作，stopPropagation() 掐断传播，stopImmediatePropagation() 连同一元素上后续绑定的同类型处理器一起跳过。处理器返回 false 在这里毫无意义，它既不会阻止默认动作，也不会阻止冒泡，浏览器根本不看返回值。
  • DOM0（el.onclick = fn 与内联 onclick="..."）：按 HTML/DOM 的约定，返回 false 表示取消默认动作，等价于调了一次 preventDefault()。注意它只管默认动作，不管传播——这是很多人写 el.onclick = function () { return false; } 之后发现事件还在冒泡的原因。
  • 老 IE（attachEvent）：不读处理器返回值，只读 window.event 上的两个属性，returnValue 与 cancelBubble。写 return false 在 attachEvent 里等于白写。

于是就有了那个经典误解：return false 之所以”看起来万能”，是因为 jQuery 在它的处理器包装层里把返回值 false 翻译成”调用 preventDefault 加 stopPropagation“。这个约定属于库，不属于浏览器。原生代码里请老老实实调方法，别依赖返回值——内联属性里除外，那里返回值真有作用。

鼠标与键盘的属性细节

先说顺序。在可聚焦元素上按下鼠标，派发序列是 mousedown → focus → mouseup → click；focus 夹在中间这一事实常被忽略，导致”点一下输入框，先跑了 blur 再跑 focus”这类逻辑排错排半天。双击的判定是两次 click 落在一个时间窗内，桌面端这个窗口由系统控制（约 500 ms），浏览器只是照报 dblclick；iOS Safari 为了分辨”这是单击还是要双击缩放”，会在第一次 touchend 之后再等约 300 ms 才合成 click，所以移动端点击有肉眼可见的延迟——这个坑单独记在《FastClick 解决点击延迟》里，触摸事件本身也不在本文范围（见《移动端长按与复制粘贴处理》）。

pageX / pageY 文档左上角，已含滚动量 老 IE 完全没有

一份 2014 年的坑清单

  • DOMContentLoaded 与 load 的区别不在本文范围，一句话带过：绑事件给 DOMContentLoaded，别等 load（详见《DOM contentloaded 与 load 的区别》）。
  • 老 IE 的 event 对象在处理器返回后即失效。setTimeout 里再去读 e.type 会报错，或者更糟——读到的是紧随其后的下一个事件。凡是异步处理，先把 target、坐标这些值取成局部变量。
  • focusin / focusout 是冒泡版的焦点事件，Chrome、IE、Opera 都支持，Firefox 到 2014 年还不支持。要委托焦点，用捕获：delegate(root, 'focus', 'input', fn, true)，focus 虽然不冒泡，但在标准浏览器里能捕获——这就是捕获阶段的实用价值。
  • submit 在老 IE 全系不冒泡，且通过 form.submit() 提交时任何浏览器都不派发 submit 事件。结论：表单提交永远直接绑在 <form> 上，别委托。
  • change 的时机在 IE 下不同：选择框（<select>）在点中选项的那一刻就派发 change，标准浏览器要等控件失焦、且失焦时的值与聚焦时不同才派发。多选框拖选、键盘改值的时机也各不相同，涉及表单校验的代码必须在 IE 8 虚拟机里单独验一遍，别信委托逻辑。
  • mouseenter / mouseleave 是 IE 私有事件转正的非标准货，本身不冒泡，原生层面委托不了；用 mouseover 加 relatedTarget 判断自己模拟。
  • 同一次快速鼠标移动中，老 IE 的 window.event 可能被下一个事件覆盖，异步读取尤其危险；e = e || window.event 之后不要再依赖全局那一份。

小结

原生事件对象只有两条来路（形参与 window.event），一次传播（捕获、目标、冒泡），两套属性命名（target 与 srcElement、relatedTarget 与 fromElement / toElement），以及三种取消语义（方法、返回值、returnValue / cancelBubble）。把这四组差异背下来，读 jQuery 源码时就不会再被”它到底替我做了什么”困扰——它无非是统一了对象命名、把 this 改成命中元素、把返回值 false 翻译成两个方法调用。手写委托可行且很轻，但要清楚自己放弃了命名空间、附加数据与特殊事件补齐；而 submit、change、焦点类事件的历史差异短期内不会消失，涉及表单就直接绑。日常写法上留两句：处理器第一行永远写 e = e || window.event，异步逻辑里绝不复用那个事件对象。
