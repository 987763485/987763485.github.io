JavaScript 中的浅拷贝与深拷贝

前两周处理表单重置的 bug 时，我把”拷贝”这件事从头到尾又梳理了一遍，发现团队里不少同事对赋值、浅拷贝、深拷贝三者的边界仍然含糊，写出来的”深拷贝”十个里有八个是 JSON.parse(JSON.stringify(obj))。本文从工程实践的角度把这三层语义一次讲清：什么时候浅拷贝就够了，JSON 这个偏方在哪些场景会失效，怎么写一个在 IE8 上也能跑的递归深拷贝，以及拷贝的边界该划在哪里。适合被脏数据折磨过的页面开发者阅读。

由”拷贝”引起的两个 bug

第一个 bug 出在表单页。页面上有一个”重置”按钮，思路很朴素：把默认值对象交给页面状态，用户随便改，改完想复原就拿默认值再渲染一次。

第二个 bug 在多组件共用的配置上。服务端返回一个配置对象，面板 A 图省事把运行时状态直接写在配置对象上，面板 B 后加载，读到的就是被 A 改过的值。

两个 bug 的病根相同：JavaScript 里对象变量持有的是引用而不是对象本身，var formState = defaults 只是给同一个对象起了第二个名字。要隔离改动，就必须真正制造副本——于是一个问题摆在面前：你要的是哪种副本？

先把概念定清楚：赋值、浅拷贝、深拷贝

笔者给出的操作性定义是：

  • 赋值复制引用。var a = source 之后，a 与 source 是同一个对象，任何一层属性的改动都互相可见。
  • 浅拷贝是顶层字段逐个复制。新建一个对象，把源对象第一层的属性值一个个搬过去；如果某个属性值本身是对象或数组，搬过去的仍是引用。改动副本的顶层字段不影响源，改动副本的嵌套对象依然会脏了源。
  • 深拷贝是把整个对象图复制成互不影响的新图。递归到底，新图里找不到任何一个与源图共享的引用（函数与原型对象除外，后面讨论）。

还要注意一点：拷贝只对”可变的引用类型”有意义。数值、字符串、布尔这些原始类型在语言层面天然不可变，任何操作都会在原地之外产生新值，所以哪怕浅拷贝把它们”共享”了也永远不会互相污染。这就是所有拷贝函数递归到原始类型即可停手的原因。

原型要不要保留。拷贝实例时我们不复制原型链——say 这类挂在 User.prototype 上的方法本就该所有实例共享，连着原型链一起复制既无必要也不可行；正确目标是让副本的 [[Prototype]] 仍指向同一个原型对象。Object.create(Object.getPrototypeOf(source)) 干的正是这件事，但这两个 API 都是 ES5 的，IE9 起才有；IE8 下如果源对象的构造函数 constructor 无副作用，可以退回 new source.constructor()，否则只能接受副本降级成普通对象。这一点与拙作《JavaScript 原型与原型链完全解析》里”原型是共享的方法仓库”的结论正好衔接。

循环引用：先记录，再递归

为什么”登记副本”必须发生在递归子属性之前？因为循环引用意味着对象图里有环，不记录”这个源对象已经拷过”，递归就会沿着环转圈，直到爆栈：

最干净的解法是以对象身份为键、且不阻止垃圾回收的映射——Harmony 草案里确实有 WeakMap，但截至目前只有极少数宿主在实验开关后支持，生产不可依赖。当时可行的做法有两种。

做法一：平行数组记录（上面 deepCopy 采用）。seenSrc 与 seenDst 两个数组按下标一一对应，查找用 indexOf。优点是对外无副作用，任何对象都能拷；缺点是 O(n) 查找，源图对象多时明显拖慢，需要的话可以换成一棵自建的树来索引。

随机键名加 enumerable: false，是为了标记期间别的代码 for-in 或序列化时不会撞见它。但缺点也明显：它在源对象上留了临时痕迹，多线程般的时序交错（比如递归途中触发第三方库遍历源对象）理论上有风险，而且冻结对象完全不可用。团队项目里笔者的选择是默认用平行数组，确认没有环的结构才允许打标记。

工程边界：DOM、jQuery 缓存、代价与约定

DOM 节点不是普通对象。cloneNode(true) 复制属性与子孙节点，但不复制 addEventListener 绑的事件处理函数，也不复制表单当前值（比如用户改过的 input 的 value 属性）。jQuery 的 .clone() 之所以看起来能带走事件，是它先把自己 data/events 缓存表里的记录存下来、克隆后再回放——这引出了下一条。

jQuery 的 data 与缓存。1.9 之后 jQuery 把事件与 $.data 存在按元素索引的内部缓存里。任何绕过 jQuery 的拷贝（包括你自己写的深拷贝递归）都搬不走这些隐藏状态，甚至可能把缓存表整个复制出一套幽灵数据。所以深拷贝的递归函数里应当显式拒绝 DOM 节点：nodeType === 1 就返回引用或者干脆抛错，别让它掉进 for-in。

超大结构的代价。递归深度受调用栈限制，几千层嵌套直接爆；副本让内存瞬时翻倍；大对象图拷完还给 GC 添一堆短命垃圾。列表类数据动辄上万条时，先问自己是不是只需要复制”会被改动的那条记录”。

有些场景要的不是拷贝，是约定。共享只读配置最常见的破坏方式，是某处”顺手改一下”。与其到处拷，不如入口处冻结并约定谁都不许改：

测试清单与当年的浏览器差异

这份实现进主干之前，笔者留着一条用例清单，每次改动跑一遍：

  • Date：副本是 Date 实例、getTime() 相等，且改副本不影响源（盯 instanceof 分支与 getTime 构造）。
  • 嵌套数组：list 里的元素是对象时，改 copy.list[0].x 不能漏回源；数组的自定义可枚举属性也不能丢。
  • 循环引用：a.b = a 的双节点环，验证副本里的环指向副本自己而不是源——这是”先登记再递归”那两行的回归测试。
  • 函数属性：对象上挂的 fn，期望是引用共享而不是报错；确认 typeof 分支放行。
  • 原型保持：copy instanceof User 与 typeof copy.say，分别在支持 Object.getPrototypeOf 与走 IE8 退路的浏览器上各验一次。
  • 不可枚举与访问器：Object.defineProperty 造的 getter 对象，验证副本调用 getter 行为一致、特性没被 for-in 版实现悄悄丢掉。

当年在 IE8 上跑出的差异主要有三处：没有 Object.create、getPrototypeOf、defineProperty 这些 ES5 API，原型保持与描述符搬运整段退化成普通对象拷贝；没有 Array.prototype.indexOf，必须用自带函数；兼容模式下连 JSON 都要 shim，”偏方”在测试机上直接不可用。这些分支留在实现里，比任何文档都诚实。

小结

赋值只复制引用，浅拷贝隔离顶层、共享嵌套，深拷贝复制整个对象图——动手前先想清楚要的是哪一种。$.extend(true) 与 JSON 往返各有适用前提，也都各有失效清单，把它们当”完整深拷贝”用迟早出事。真要自己写递归，顺序应当是：原始类型先返回，特殊类型各给各的构造法，先登记副本再递归子属性，最后才是原型、描述符这些精修。而拷贝不是万能药：DOM 节点、jQuery 缓存、超大结构都提醒我们，工程上更省心的答案常常是”只拷会被改的那一小块”，或者干脆冻结起来、用约定代替拷贝。
