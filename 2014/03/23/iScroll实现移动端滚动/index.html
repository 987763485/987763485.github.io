iScroll 实现移动端滚动

做全屏布局的移动 Web 页面时，”中间那块列表要能滚”这件小事，2014 年依然能纠结掉一个下午。本文不谈页面切换（去年那篇已经写过），只谈容器内滚动的选型：iOS 原生惯性滚动和 iScroll 这类 JS 模拟，各自的收益与代价在哪，什么时候必须上、什么时候上了反而亏。适合正在做 Hybrid 壳子里 H5 页面的同学，读完能拿到一张对比表、一组踩坑清单和一个下拉刷新的可运行例子。

问题背景：body 不动，中间那块要滚

先说清楚场景，因为选型完全由场景决定。

现在的项目大多不是”一整篇文档从上往下读”的形态，而是模仿原生 App 的全屏布局：顶部一条固定的导航头，底部一个固定的 tab 栏，中间剩下的一块矩形区域放列表。实现上通常是 html、body 都锁死 100% 高度加 overflow: hidden，头和脚用 position: absolute 钉在上下沿，中间那块也绝对定位，top 给头的高度、bottom 给脚的高度。

这么一来，整个文档是不滚动的——window.scrollTo 无处可使，因为 body 根本没有超出视口的内容。需要滚的是中间那个 div 里的内容。于是问题就落在：如何让一个固定尺寸的 div，滚动它内部超出的内容。

摆在我们面前的只有两条路。

一条是原生滚动：给这个 div 加 overflow: auto，让浏览器自己的滚动机制接管。iOS 5 起再加上 -webkit-overflow-scrolling: touch，就有了惯性和回弹。

另一条是JS 模拟滚动：容器加 overflow: hidden，用 JS 监听 touch 事件，手指移动时把内部那个 scroller 元素用 translate 位移，自己算惯性、自己算回弹。iScroll 就是这条路最成熟的实现。

两条路的差别不在”能不能滚”，而在谁在控制这帧画面。原生滚动由浏览器的合成过程负责，页面主线程不参与逐帧计算；JS 模拟则每一帧都要走一遍主线程。这个差别会带来手感、内存、事件行为与 fixed 元素共存方式上的一连串分歧，也正是本文要对比的全部内容。

两条路线：原生滚动与 JS 模拟

原生滚动这条路

最省心的写法：

它的优点很实在。第一是省内存，浏览器只为可视区附近的像素准备图层，往下滚的时候复用同一块合成内存，列表再长也不会线性膨胀。第二是手感，iOS 上带 touch 关键字的原生滚动，惯性曲线和系统列表是一模一样的，用户挑不出毛病。第三，也是最容易被忽略的：无障碍和键盘可达。原生滚动容器是真正可聚焦、可被读屏软件识别为滚动区域的，overflow: auto 在没有触屏的设备上还会给出滚动条。

坑同样明确，而且都是拦路级别的：

  • 容器内的 position: fixed 会跟着跑。 这是当年最疼的一条。iOS 上带 -webkit-overflow-scrolling: touch 的容器相当于给自己创建了一个新的坐标系，里面写的 fixed 元素不再相对视口，而是相对容器滚动，视觉上就是”吸顶的那一行跟着列表一起溜走了”，甚至被容器边界裁掉半截。
  • 和 transform 动画打架。 容器内元素做 translate 动画时，滚到某些位置会出现图层错位、闪烁、点击区域和画面分离。规避手法通常是动画期间临时把 touch 关键字去掉，做完再恢复，很脏。
  • 低版本 Android 基本没戏。 Android 2.3 的 WebView 不支持惯性，4.0 上 -webkit-overflow-scrolling 直接无效，表现是不跟手、没有回弹，很多机型连滚动条都不给；有的版本甚至出现容器能滚但 scrollTop 读数不动的情况，事件回调里想拿滚动位置都拿不到。

也就是说，原生滚动在 iOS 上体验好、在 Android 上一致性差，而且它和 fixed、transform 之间有一层没法商量的冲突。

JS 模拟这条路

2014 年能选的比想象的多一点。

iScroll 4 是过去两年里的绝对主力，用法简单、生态最大：下拉刷新组件、轮播、多级选择器，市面上大部分现成代码都建立在它上面。它的做法是监听 touch，把 scroller 用 translate 位移，用 setInterval 自己跑一个动画循环来模拟惯性。

iScroll 5 是 Matteo Spinelli 在 2013 年重写的版本，也是本文的重点。核心改动是两处：位移改走 translate3d 并配合 requestAnimationFrame，动画交给合成线程；事件层面新增了 preventDefault 选项和 probe 探针事件。这两处改动决定了它的性能特征和能力边界，下一节细说。

Sensible Touch Scroll 走的是极简路线，代码量很小，只解决”跟手 + 惯性 + 回弹”这一件事，不打算你做轮播和列表视图。DSScroll 属于同一档，体积优先。它们的共同好处是引入成本低、读懂容易，代价是什么都要自己接。

jQuery Mobile 自带的 scrollview widget 在 1.3 里还处于实验状态，需要和它整套 widget 一起用，除非项目已经全面 jQuery Mobile，否则单独为滚动引入它不划算，实测惯性调优空间也很有限。

一句话结论：必须上 iScroll 的三种情况是容器内要和 fixed 元素和平共处、要用 probe 事件驱动下拉刷新或视差位移、要覆盖低版本 Android 的一致行为。别上 iScroll 的三种情况是内容很长的纯列表页（合成层内存吃不消）、需要读屏或键盘操作的页面、以及本质上是文档流的资讯页——这类页面 overflow: auto 就是最优解，任何 JS 模拟都是倒退。

iScroll 的实现要点，也是它的代价

知道库在干什么很重要：它的实现方式，直接决定了你会踩哪些坑。

结构上只有一个合法姿势

iScroll 要求容器（wrapper）设置 position: relative 或 absolute，尺寸固定、overflow: hidden，并且只包一层直接子元素作为 scroller。这不是代码洁癖，而是实现约束：它只读 scroller.offsetHeight 来算内容高度，中间多插一层 div 会让这个值变成 0 或者变成那一层的高度，滚动范围立刻错掉。

maxScrollY 是一切的根

iScroll 的位移范围不是无限的，它预先算好边界，滚动时把 y 钳制在 [maxScrollY, 0] 之间。核心就这一行算术：

probe 的三档频率

probe 是 iScroll 5 相对 4 最有价值的增量：它让库主动往外发滚动位置，而不是让你去 bind('scrollMove') 或者读一个不保证更新的属性。三档差别很大，选错档就是性能事故：

probe 值 触发时机 典型用途 代价
0（默认） 不发送探针事件 单纯滚动 无
1 每帧动画时（惯性与回弹期间） 进度条、吸顶状态判断 与帧率同频，跟手拖动期间不触发
2 渲染新帧之前 视差、需要严格对齐画面的效果 每帧一次，最贵
3 手指每次移动时 下拉刷新 跟手期高频，回调必须极轻

下拉刷新要的是”手指正在往下拖了多远”，所以必须 probeType: 3。而 probeType: 3 意味着一次拖动可能触发上百次回调，回调里做任何一件重活都是在给自己挖坑。还要补一句：只有 bounce 为 true 时，顶部才允许被拖出越界的正偏移，探针才会读到大于 0 的 y，下拉刷新的判定才有素材。

几个必须显式表态的选项

bounce、momentum、mouseWheel 好理解。要强调的是 preventDefault：它为 true 时，iScroll 会在 touchstart/touchmove 上调用 preventDefault，好处是彻底干掉页面级滚动和橡皮筋，坏处是浏览器的原生 click 生成、focus、input 聚焦都会被它一起压掉——这就是后面几个坑的共同源头。

踩坑复盘

坑一：容器内点击失效

现象是滚动一切正常，但列表项的 tap、click 就是不触发，偶尔又灵一下。根因链是这样的：preventDefault: true 压掉了浏览器生成原生 click 的过程，而 click 选项默认是 false，iScroll 自己也刻意不伪造 click 事件（它会判断这是否算一次”拖动”）。当年很多人是在项目里同时挂了 FastClick，于是变成三方打架：FastClick 想合成一次 click，iScroll 阻止了默认行为，两者在 touchend 上互相试探，结果是点击要么丢失要么延迟到下一次。

解法按优先级：需要真 click 就显式 click: true；不想开这个就用 iScroll 自己的 onBeforeScrollStart/自定义 tap 判定，或者干脆监听 end 事件自己派发；FastClick 和 iScroll 不要同时管同一个区域，给 iScroll 的容器加上 FastClick 的 notNeedTouch 忽略标记。

坑二：嵌套滚动互相抢事件

纵向列表里放一个横向轮播，是最常见的嵌套。两套 touch 监听都会在 touchmove 里要控制权，表现是手指斜着划的时候两个方向同时动，或者轮播把纵向滚动锁死了。

坑三：动态内容之后忘调 refresh

maxScrollY 只在构造时算一次。列表是异步拉回来的，或者用户展开了某一项、图片加载完把内容撑高了，scrollerHeight 变了而 maxScrollY 还是老值，结果就是滚到底也看不到最后几条，而且回弹点出现在中途，看起来特别像 bug。

正确姿势是任何改变内容高度之后手动通知：

图片多的列表还要在每张图片 load 之后再 refresh 一次，否则首屏算到的是缺图高度。旋转屏幕也要 refresh，orientationchange 在 iOS 上触发时视口尺寸可能还没更新，稳妥做法是延迟 200ms 再调。

坑四：input 聚焦后坐标错乱

容器里有输入框时，键盘弹起会把整个 WebView 往上顶，而 iScroll 缓存的 wrapper 位置和它认定的可视高度都还是键盘弹起前的值。等键盘收起，页面回位，iScroll 手里的偏移量没跟着变，于是出现点击区域和画面错开一段距离、或者列表莫名往上跑一截。

当年的处理套路：输入框 focus 时先 scroller.blur() 停住（防止事件继续消耗），blur 之后延迟一次 window.scrollTo(0, 0) 把 WebView 顶回来，再 scroller.refresh() 重算。给 resize 也挂上同一个 refresh，能顺手解决一部分 Android 键盘不改变 resize 而是直接盖住画面的机型。

坑五：千级节点之后合成层爆内存

这是最贵的一条。translate3d 把整块 scroller 提升成合成层，节点多到一定量级，iOS 上会看到内存一路涨，到某一点直接白屏或者列表变成一片空白，只有回弹动画还在动——因为纹理内存申请失败了。实测经验是列表项节点总数（含每一行的 img、多层 div）超过千个就要当回事，超过三千个基本必炸。

思路是只渲染可见区，DOM 里的节点数量保持恒定，滚出视野的节点复用。手工做法不需要框架：

性能调优的几条纪律

第一，touchmove 里只做 transform，不碰任何会引起布局的东西。 不改 width、不改 top（用 translate3d 而不是 top）、不增删节点、不加 class 触发重排。iScroll 的位移之所以能稳在 60 帧，就是因为它的写路径只有 transform。

第二，自己写的动画用 rAF 节流，注意当年的前缀现实。 requestAnimationFrame 的标准写法在 2014 年还不能裸用，需要探测并回退：

这套节流对 probeType: 3 尤其重要：快速拖动时探针回调的频率远高于帧率，不节流就是每次回调都排一次活。

第三，探针回调里禁止读布局属性。 笔者在旧文《DOM 尺寸与位置：offset、client 与 scroll》里总结过一条结论：布局属性读一次，浏览器就得当场把布局重算一遍。offsetTop、clientHeight 这类值一旦出现在每帧回调里，就是”写完样式马上又读回来”的经典强制同步重排。要高度就在 refresh() 的时机读一次存成变量，回调里只用变量。

第四，切换页面或销毁视图时把监听器清干净。 这是内存泄漏的老巢，iScroll 实例会长期持有 wrapper 和 scroller 的引用，页面切走时不销毁，几个来回之后就是几十个活的 touch 监听在后台跑。

destroy() 之后 scroller 内部置空，但不会移除你自己 addEventListener 挂上去的东西，这部分必须自己配对。

第五，低端 Android 上把 bounce 和 HWAcceleration 关掉。 回弹动画在 2.3 上很容易掉帧，translate3d 提升的合成层在那批机器上反而拖慢渲染。probeType 能用 1 就不要用 3。

小结

容器内滚动在 2014 年依然是两条路：原生 overflow: auto 配 -webkit-overflow-scrolling: touch，和 iScroll 这类 JS 模拟。前者省内存、手感正、无障碍可用，代价是 iOS 上容器内 fixed 元素失效、和 transform 动画冲突、低版本 Android 行为不一致；后者用 translate3d 搬整块 scroller 换来了跨端一致的手感和 probeType 进度事件，代价是全量合成层的内存、被 preventDefault 压掉的点击与聚焦，以及一套必须自己维护的事件与边界。选型看三件事：有没有 fixed 元素共存、要不要滚动进度、要不要覆盖 Android 2.3 与 4.0；长列表和资讯页老老实实用原生。用了 iScroll 就把三条纪律刻在手上：内容变更后 refresh()、destroy() 和自己的监听器成对清理、探针回调里只写 transform 不读布局属性。列表过千个节点时，用”固定行数 + 复用节点”的虚拟渲染把 DOM 规模钉死，比任何调参都管用。
