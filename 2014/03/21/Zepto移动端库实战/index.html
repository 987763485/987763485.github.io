Zepto 移动端库实战

去年年底我们把移动端专题站从 jQuery 1.9 切到 Zepto，接下来的三个星期基本都在给这次切换补窟窿。笔者在《jQuery 与 Zepto 的差异》里已经把两边的 API 差异罗列过一遍，本文不重复那份清单，只讲项目里真实发生过的事故：动画为什么静默消失、tap 为什么又双触发又不触发、data 为什么读出来类型不对、内存为什么只涨不降。结论都来自线上页面和一堆真机调试，适合正准备迁到 Zepto、或者已经迁到一半正在深夜改 bug 的同学。本篇基于 Zepto 1.1.3 与 jQuery 1.9/1.10，官方仓库还在往前走，将来出到 1.1.6 也不是不可能，但本文只对本项目实际跑过的代码负责。

事故开场：动画没了，插件报错，size() 不见了

切换上线第一天，运营就反馈春节活动页的入场动画全没了。排查过程很有意思，三类症状指向三个不同的原因。

第一类，$('#intro').animate({...}) 所在的代码块整个不执行。控制台里 $ 和 $.fn.on 都好好的，唯独 $.fn.animate 是 undefined，而代码在 try-catch 的边缘被静默吞掉了。原因：我们为了控体积，从 Zepto 仓库根目录拿了那个最小的 zepto.js，只拼了 event、data、ajax，没有拼动画模块。函数不存在，调用直接抛 TypeError，这在 jQuery 全家桶里永远不会发生。

第二类，一个从 PC 站搬过来的轮播插件在初始化时报 $.fn.addProps is not a function 之类的怪错。这个插件内部魔改了 jQuery 的动画属性表，Zepto 的 fx 实现走的是 CSS transition，属性表根本不存在。插件生态不是白说的，涉及动画内核的 jQuery 插件在 Zepto 上基本没戏。

第三类最直接：老代码里有一句 $items.size()，在 Zepto 下抛”对象不支持该方法”。Zepto 的集合只有 length 属性，没有 size() 方法，类似的还有 .end()、:eq() 这些 jQuery 扩展，缺的东西是悄悄缺的，写到才知道。

这三次事故教会我一件事：Zepto 不是 jQuery 的完整替代品，它是”长得像 jQuery 的一组模块”。你拼进去几个模块，API 表面就有多完整，缺的部分不会在编译期提醒你，只会在用户的手指下爆出来。

模块拼接：默认包没有 fx，animate 会静默失败

Zepto 1.1.x 的发布方式决定了踩坑概率：仓库根目录的 zepto.js 只有核心（选择器封装、集合方法、$.each 这些），dist 下的完整包才是全量的。很多教程让你直接从 GitHub 拖文件，拖到的往往就是最小核心。可用的模块大致是这些：zepto.js、event、touch、data、fx、fx_methods、anim、ajax、deferred、callbacks、selector、detect、form。

依赖关系里有几条暗线要记住：fx 读写元素的动画状态走的是 data 模块的内部缓存，所以 data 必须在 fx 之前；fx_methods 提供 .animate()、.fadeIn()、.fadeOut() 这些快捷方法，它依赖 fx；anim 提供 .anim() 的 transition 封装，也依赖 fx；touch 提供手势事件，依赖 event；detect 提供 $.os 与 $.browser，谁依赖它都行，只要在业务代码之前；selector 是给核心打补丁支持 :first、:last 等伪类的，必须紧跟在 zepto.js 之后加载，晚于业务代码就白加载了。画成流程图如下：

tap 不是 click：手势事件的三起事故

tap、swipe、doubleTap、longTap 都由 touch 模块提供，看起来比绑 click 时髦，实际内部机制是：touchstart 记录起点，touchend 时算位移，位移超过阈值就当滑动、不触发 tap；没超阈值还要卡一个约 300ms 的窗口用来区分单击和双击；tap 触发后它会主动拦截随后赶来的原生 click，防止一次手势执行两遍回调。理解了这套机制，三起事故都能推演出来。

第一起，链接不跳转。有同事在 a 标签上绑 tap 做埋点，回调跑完了，页面没动——tap 是 Zepto 自己派发的事件，不携带浏览器默认行为，原生 click 又被它吞了，导航自然没发生。表单提交按钮同理。后来我们的规矩是：a 和 submit 按钮一律绑 click，tap 只用于 div 类的假按钮。

第二起，和 FastClick 混用后按钮时灵时不灵。FastClick 在 touchend 里手工合成一个 click，再拦截原生 click；Zepto 的 tap 也是”自己触发再吞 click”。两套拦截逻辑碰在一起，拦截标记互相识别不了，结果有的控件双击才生效，有的回调一次都不跑。结论写进团队规范：要么全站 click + FastClick，要么全站 Zepto 手势，不许混。

第三起，滚动中的 tap 失效。列表项绑了 tap，用户快速滑动时经常点不中，因为惯性滚动阶段浏览器派发的事件序列不完整，touchend 落在下一个手指动作上，位移判定全部失败。这个没有体面解法，只能减少”滚动容器内直接绑 tap”的场景，或者接受降回 click。

data 模块：类型不一致与不回收的缓存

Zepto 的 data 模块读取 data-* 属性时会尝试做一次 JSON 解析，写入则是只进内存缓存、不回写 DOM 属性，removeData 只删自家缓存的键。这套策略和 jQuery 的 expando 缓存形似而神不似，事故出在三个地方。

同一段 DOM 属性，两边读出来的类型可能对不上。比如 <li data-id="1024" data-conf='{"top":1}'>，.attr('data-id') 两边都返回字符串，但 .data('id') 会走类型推断。我们迁移时没清理混用的 attr/data 读取，有个判断写成 if ($(el).data('id') === '1024')，在一处按 jQuery 语义改的、另一处按 Zepto 语义跑的代码里，一个分支恒真一个分支恒假，选座页的座位状态显示错乱。排查那晚才想明白：同一个键，有人拿到字符串 '1024'，有人拿到数字 1024。纪律从此是：业务代码里 data 的读取出口统一封装一个函数，比较一律先 String()。

第二个坑是驼峰键名。data-conf-id 这种属性，jQuery 侧 .data('confId') 能读到，Zepto 对属性名到键名的转换处理不完全一致，有几种写法直接读出 undefined。我们的做法是 data 属性一律只用小写加连字符，读取时按原样传，不指望库帮你转换。

第三个坑最隐蔽：缓存不回收。1.1.x 上通过 .html('') 或 innerHTML 清空子树时，被移除节点在 Zepto 内部 data 缓存里留下的条目不保证被清掉。活动页是单页结构，列表来回刷新四十多次之后，Android 4.x 的 WebView 内存从 60MB 涨到 140MB 以上，直接被系统杀掉重开页面。最后两头堵：移除子树前显式 removeData；更重要的业务状态根本不挂 DOM，改用 JS 对象加 id 映射，data 属性只存静态配置。移动端 WebView 的内存红线就那一条，谁的项目里挂对象到节点上挂得爽，谁就先撞线。

选择器与性能：原生 QSA 不是免费的

Zepto 的选择器就是 querySelectorAll 加一层薄封装，能力与速度全押在宿主浏览器上。桌面 Safari 和 iOS 6 表现很好，但 Android 2.3 那代老 WebKit 对复杂选择器既支持得磕磕绊绊，优化也差，类链和属性选择器尤其慢。我们在 GT-I9300（Android 2.3.6）和 iPhone 4S（iOS 6）上对一个约 1200 节点的订单列表做了分段计时，每类选择器跑 50 次取平均：

选择器写法 Android 2.3 WebKit iOS 6 Safari
#order-list 0.3 ms 0.1 ms
.order-item 4.2 ms 1.1 ms
.order-list .item .price span 26 ms 3.4 ms
[data-status="paid"] 31 ms 2.7 ms
.order-list .item:nth-child(2n) 48 ms，部分机型返回空集 4.0 ms

数字本身不必较真，量级关系是稳定的：老 Android 上多级类链和属性选择器比单类慢一个数量级，nth-child 这类结构伪号还有正确性风险。改法也便宜：列表项直接挂 .item-price 这种扁平单类，少用后代链；查询结果缓存进变量，别在循环里重复查——这条正是笔者在《DOM 查询缓存与批量操作》里验证过的结论，查询引用提到循环外永远是性价比最高的优化。事件绑定统一走一层委托，container.on('tap', '.item', fn) 这种写法底下只查一次容器。

ajax：jsonp、类型推断与那个简化版 Deferred

Zepto 的 ajax 模块能用，但它给你的是骨架不是全屋装修，几处细节要提前知道。

jsonp 的实现是动态插一个 script 标签，回调名通过 jsonp 和 jsonpCallback 选项控制，这块和 jQuery 语义接近，跨域拿数据没问题。真正的坑在 dataType：Zepto 会先看 dataType，没写就按响应头 Content-Type 推断，服务端接口不给 application/json（2014 年了还有一大半后端返回 text/html 的），你拿到的 data 就是字符串，data.list 一访问就炸。我们的规矩变成两句：显式写 dataType: 'json'；回调里再 typeof data === 'string' 兜一次 JSON.parse。

全局配置方面，Zepto 也有 $.ajaxSetup，但它只是浅合并一组默认参数，jQuery 那套 ajaxStart/ajaxError 全局事件和按 URL 覆盖的精细控制都没有，公共拦截逻辑得自己包一层 request() 函数。

Deferred 要单独警告。Zepto 1.1.x 的 $.Deferred 是精简实现，.then() 不支持 jQuery 那种”链式返回新对象、前一个的返回值喂给下一个”的完整语义，多个异步步骤串起来还是要自己回调或计数。另外别把它和当时 ES6 草案里讲的 Promise 混为一谈，规范语义差着一截，照着 Promise 的直觉写链式调用是行不通的。超时也是自己动手，我们包的壳如下：

兼容与降级：那些库帮不了你的事

切 Zepto 省下的体积是明账，兼容性欠下的债是暗账，几笔必须记清楚。

Android 2.3 的老 WebKit 上，transform、transition、animation 不带 -webkit- 前缀会被整个忽略，这意味着 Zepto 的 fx/anim 模块在这批机器上直接退化——它生成的样式属性当时对前缀的处理不算周全，我们的做法是动画相关的 CSS 全部双写前缀属性，JS 动画只做有则加、无则跳的增强。iOS 7 上的 position:fixed 配合软键盘是另一个深渊：输入框聚焦、页面上推之后，fixed 的头部会漂移，键盘收起后页面还可能卡在半截滚不回底。这和 Zepto 毫无关系，但移动端项目一个都绕不过去，最后的方案是弹键盘时把头部从 fixed 切成 absolute、收起后 window.scrollTo 归位。-webkit-overflow-scrolling: touch 换来顺滑的惯性滚动，代价是橡皮筋回弹期间前面说的 tap 失效和 offset() 坐标滞后，吸顶和滚动定位逻辑都要在这个前提下写。

复盘下来，当年我们认定必须自研、不能指望库的能力清单是：下拉刷新、scroll 吸顶、图片懒加载与占位、键盘弹起布局适配、跨页面的滚动位置恢复。这些要么依赖原生事件的精确时序，要么依赖库不碰的渲染层特性。Zepto 帮你的是 DOM 查询、简单事件委托和 transition 动画这一层，越往交互深处走，库的边界越清楚。

小结

Zepto 在 2014 年的移动端项目里依然是好选择，但前提是你把它当”按模块装配的工具箱”而不是”小号 jQuery”：拼接清单加自检能挡掉大半静默故障；tap 手势与原生 click、FastClick 的语义冲突要靠统一规范避免混用；data 的类型推断和缓存不回收是内存事故的两大隐患；选择器性能完全押在宿主浏览器上，老 Android 上保持单类、缓存结果就够活。迁移前先跑一遍检查清单，命中插件生态、动画编排或 IE 回退任何一条，就坦率地留着 jQuery。库的能力边界越早摸清，深夜真机调试的机会就越少。
