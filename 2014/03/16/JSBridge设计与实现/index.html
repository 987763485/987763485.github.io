JSBridge 设计与实现

去年四月那篇 Hybrid 与 WebView 交互基础里，笔者把 WebView 与原生互通的基本原理过了一遍，那是入门角度，解决的是”能不能通”。本文解决的是”通了之后怎么用好”：把一套 JSBridge 的协议与骨架代码写出来，再量一遍调用链路上每一段的开销，看哪些地方值得省。适合正在做 Hybrid 容器、或者被一堆散乱调用搞得没法维护的前端同学看。文中的数据与结论来自 Android 4.x 的 WebKit WebView 与 iOS 6/7 的 UIWebView。

先把散乱的调用摊开看

这三段代码凑在一起，能归纳出四个老问题。第一是没有回调，回调写成硬编码的全局函数名，一个页面里两处同时调分享就互相覆盖。第二是没有超时，原生一旦异常或被用户取消，H5 这边的 loading 就永远转下去。第三是没有错误码，成功失败只剩一个”回来了”，业务层分不清是用户取消还是原生抛异常。第四是平台分支扩散，两套写法散落在每个业务文件里，换一次通道要全局搜几十处。

根源不在调用写得丑，而在于没有一层协议。所以我们做的第一件事不是优化性能，而是把散调用收进一个 bridge 对象。

通信通道：三条路怎么选

先回顾一下当时可用的三条通道。

URL Scheme 拦截。H5 侧造一个自定义协议的地址，靠隐藏 iframe 赋 src 或直接改 location.href 触发一次导航；原生侧在 Android 的 WebViewClient.shouldOverrideUrlLoading、iOS 的 shouldStartLoadWithRequest 里拦下来解析。这是唯一一套两端都不依赖私有 API、也不需要注入对象的做法，代价是单向——原生拿到消息后没法 return，只能反手再执行一段 JS，而且 URL 有限长，载荷大了会出事。

addJavascriptInterface。Android 官方注入接口，把 Java 对象挂到 window 上，H5 直接 window.nativeApi.xxx() 调用，同步、能拿返回值、写法最舒服。但它有个绕不过去的历史：2012 年 9 月公开的那个远程代码执行漏洞（CVE-2012-6636）——任何被注入的页面都能通过 getClass() 反射拿到任意 Java 对象，一路调到 Runtime.exec()。Google 直到 Android 4.2（API 17）才补上，要求方法显式加 @JavascriptInterface 注解才暴露。而 4.2 以下的机器在我们线上还占相当比例，页面混进一段远程脚本就等于交出整个沙盒。所以我们的容器从一开始就禁掉了这条通道，只在完全可控的本地 assets 页面里作为快速通道开放。iOS 的 UIWebView 没有公开的对应能力，私有 API 有审核风险，不考虑。

WebViewJavascriptBridge 那一类 iframe 注入 scheme 的做法。这是 iOS 上事实上的标准做法，思路还是 scheme 拦截，但把消息体当队列：H5 侧把待发送的消息 push 进一个全局数组，只发一个”来取消息”的信号 URL；原生拦到信号后，用 stringByEvaluatingJavaScriptFromString: 把数组序列化结果一次取回，处理完再执行一段 JS 把响应送回去。原因是 iOS 上 iframe 在同一个 tick 里连续赋 src 会丢消息，iOS 7 之后某些情况下 scheme 导航还会被直接吞掉，”信号 + 批量拉取”能把这两个问题一起解决，顺带摊薄了”一次一帧”的固定开销，代价是链路多一跳。

三条路放在一起对比：

维度 URL Scheme 拦截 addJavascriptInterface iframe 信号 + 队列拉取
可用平台 iOS、Android 通吃 仅 Android iOS、Android 通吃
方向 单向，需原生反调 JS 双向同步 双向，异步
单次载荷 几 KB 起就开始抖，见下文 不受 URL 限制 受 JS 求值字符串限制，宽松得多
安全性 好，不暴露原生对象 4.2 以下有远程代码执行风险 好
高频调用表现 差，每次走导航拦截 好 好，可批量
2014 年结论 兜底通道 关掉，或仅限本地页 主推

我们的最终选择是：iOS 走信号 + 队列拉取，Android 走 scheme 拦截但同样带发送队列，两端共用一份消息体格式。发送函数做成可替换的实现，业务层完全感知不到底下走的是哪条管子。

通道只是管子，真正决定可维护性的是管子里跑的东西。我们把每一帧定成五个字段：

序列化后拼成 jsbridge://invoke?<encodeURIComponent(JSON.stringify(frame))>。原生回帧的格式固定成四元组：(callbackId, errCode, errMsg, data)。

这里最关键的是 callbackId 为什么必须有，而且要 JS 侧自己维护一张注册表。原生回调 JS 时没有上下文，它只能对一个全局函数发起调用；如果 JS 侧不记住”这个 id 对应当初哪一次调用的哪个回调函数”，响应回来就是无主的数据。所以 bridge 内部维护一个字典，发帧前把回调函数按 id 存进去，收到响应时取出、执行、删除。这张表同时也是超时清理与泄漏排查的抓手。

错误码也定了枚举，免得每个模块自己乱造：0 成功，-1 参数不合法，-2 无权限或未授权，-3 原生内部异常，-4 用户主动取消，-5 原生不支持该模块或方法，-7 JS 侧超时。其中 -5 很重要：H5 领先于客户端版本时，调一个老客户端没有的能力，必须让原生明确回”不支持”，而不是让人靠超时去猜。默认超时 5000 ms，由 JS 侧 setTimeout 触发后回 -7。

调用链路上的开销与调优

JSBridge 慢，不是因为”跨语言调用”有多玄学，而是一次调用要走三次跳转，每跳都有实实在在的固定成本。

先看 URL 通道能装多少。这个数字在不同层差异极大，我们拿线上机器实测过一圈：

位置 实测可用上限 表现
iOS 6/7 UIWebView 拦 shouldStartLoadWithRequest 约 100 KB 内比较稳，超过几百 KB 偶发不回调 静默失败，只能靠超时发现
Android 4.x shouldOverrideUrlLoading 几 KB 起就有截断，接近 2 MB 必挂 拿到的是半截 URL，JSON 解析报错
Android loadUrl 本身 宽松，几十 MB 也进得去 但拦截回调那条路径不宽松
服务端（Apache、nginx 默认配置） 请求行 8 KB 超了直接 400 / 414

结论很清楚：URL 通道不能当数据通道用。再加上转义开销——中文与花括号、引号都要展开成三到六个字符，实测一个含中文的 payload 转义后膨胀到 1.8 至 2.4 倍，你以为发了 20 KB，落到拦截器里已经是 45 KB。所以定死一条规矩：单帧序列化后超过 8 KB 就不许走通道。超了只有两条路：分片（拆成 N 帧，每帧带分片序号与总数，原生拼装完再回一个总回调），或者干脆只传一个引用——H5 把数据放进原生的临时存储，通道里只跑一个 key。

再看一次完整往返的耗时量级。数据是在几台真机上循环 200 次取的中位数，原生侧只回一个常量、不含真实业务逻辑，所以这个数就是纯桥的固定成本：

阶段 低端 Android 4.0 机 Android 4.3 中端机 iPhone 4S / iOS 6 iPhone 5 / iOS 7
JSON.stringify + 转义 1.5 ms 0.6 ms 1.1 ms 0.5 ms
建帧 + iframe 赋值 2.0 ms 0.9 ms 1.4 ms 0.6 ms
原生拦截、解析、派发 4.5 ms 2.2 ms 3.0 ms 1.4 ms
原生回帧执行 JS 3.0 ms 1.6 ms 2.2 ms 1.1 ms
JS 侧查表、清定时器、执行回调 1.0 ms 0.5 ms 0.8 ms 0.4 ms
一次往返合计 约 12 ms 约 5.8 ms 约 8.5 ms 约 4 ms

这个表能说明三件事。第一，低端 Android 上一次空转往返就 12 ms，等于一帧预算（60 fps 下 16.7 ms）的绝大部分。第二，iframe 建了删、删了建在链路里占 1 到 2 ms，还带布局抖动——所以我们改成全局复用一个 iframe，靠发送队列保证一 tick 只发一帧。上线后列表页的内存曲线明显变平；每次新建 iframe 在高频场景下是会漏的，个别内核版本 remove 之后导航请求还挂在历史栈里。第三，Android 侧的回帧 JS 是排队执行的，如果那一刻 WebView 正在解析或渲染，回帧就被推迟，原生业务再快也没用——这就是同一套 H5 在 Android 上偶发几十毫秒回调抖动的原因。

有了固定成本，调优方向就是减少往返次数和减小每帧体积：

  • 批量接口合并。收益最大的一条。原来页面初始化要拿用户信息、城市、配置、红点数，四次调用在低端机上就是 48 ms 加四次抖动；合并成一个 batch 接口，让原生并发跑完四个模块再回一帧，实测从 47 ms 降到 15 ms。原则是：同一个渲染周期内需要的数据，一次拿完。
  • 结果缓存。用户信息、定位、设备等级这类”变化频率远低于调用频率”的数据，必须在 JS 侧留一层缓存并设 TTL。我们线上有一次埋点没做缓存，滚动时每个条目曝光都查一次用户等级，5 秒内打出 300 多次调用，把 WebView 的导航队列直接堵死。
  • 不要在滚动、resize、touchmove 里同步过桥。这类地方要的是节流，100 ms 一次；或者反过来让原生主动推，把坐标、滚动位置推进来，H5 只读本地变量。
  • 裁剪字段。一个 100 KB 的商品列表在 4.0 的机器上序列化加解析能吃掉 10 到 20 ms。列表接口只回渲染需要的字段，这一条对回帧尤其重要，因为原生往往不知道自己那一帧有多大。
  • 该不限超时的别限。低端机上 5 秒超时会误杀，我们把支付、扫码这类要用户操作的接口放进”不超时”名单，改由原生回用户取消来收尾；普通取数接口保持 5 秒。

体积与次数的关系大致是这样：单帧从 20 KB 降到 4 KB，一次往返在 iOS 7 上大概省下 1 ms 多一点；但调用从 4 次合并成 1 次，省的是 3 个完整的 4 到 12 ms。先合并次数，再抠体积，顺序别搞反。

五个反复出现的坑

  1. Android 4.4 之前的内核差异。4.4 之前是老的 Android WebKit，4.4 起换成 Chromium，注入与求值的时序行为不一样，console、localStorage 的可用性和若干 CSS 前缀也跟着变。同一份 bridge.js 在 4.3 与 4.4 上要分别回归，不能只测最新系统。
  2. 原生回调早于 JS 就绪。原生处理得太快，回调函数还没定义就发起了求值，Android 上抛错被静默吞掉，响应彻底丢失，H5 只能等到超时。修法是在协议里加一次握手：H5 起来先发一帧 ready，原生在收到它之前把所有响应暂存，收到后立刻重放。
  3. 页面刷新后注册表丢失。注册表是纯内存的，页面一 reload 全没了，而原生手里可能还攥着几个 callbackId。这类响应只能丢掉，但要同时上报埋点，把孤儿 callbackId 的数量与年龄报上去，用来发现原生侧该回收没回收的任务。真要跨刷新恢复，就把未决调用摘要写进 sessionStorage，重载后按业务语义重发。
  4. 同一 URL 连续赋值不生效。指向完全相同的地址时第二次不触发导航，连续改 location.href 同理——这是历史记录语义，不是 bug。修法两条：帧里带自增 msgId 让每帧 URL 天然唯一（我们用的这个），或者发送队列一 tick 只发一帧。别用”加时间戳后缀”这种把 URL 撑得更长的办法。
  5. iOS 后台挂起导致回调丢失。App 进后台后 WebView 不再执行 JS，原生算完了、求值却白跑一趟；用户切回来时，那个调用在 JS 侧早已超时清理。我们在原生侧对回帧做有限重放（最多 3 次、间隔递增），JS 侧配合超时兜底，同时给关键流程加幂等：原生留一份结果缓存，同一个 callbackId 重复回来也只执行一次。

和当时生态的关系：各家都有自己的 bridge

自己写归自己写，业务真正跑起来时页面不一定在我们的容器里。2014 年这个时间点上最值得打交道的是微信内置浏览器：它对外暴露一个私有对象 WeixinJSBridge，能直接调分享、隐藏右上角菜单之类的动作，页面侧要监听 WeixinJSBridgeReady 才能安全调用——注意这个 ready 事件，它和我们上面那套排队机制其实是同一个问题：JS 就绪与通道就绪谁先谁后。

至于支付宝钱包、手机淘宝这类容器，思路上完全是同一套——私有注入对象、带 callbackId 的异步回调、ready 时机要等——但协议各家都不一样，方法名、参数键、错误码字段没有一个对齐过。Cordova 那边早已有 cordova.exec 与 deviceready，插件写起来很舒服，可你要在微信里跑，插件系统帮不上忙。所以我们最后做的不是”再写一个 bridge”，而是在 bridge 之上加一层能力适配表：业务只声明要分享、支付、扫码这几个语义动作，适配层按 UA 与可用对象决定映射到自家 scheme 还是微信那个私有对象。这一层代码量不大，但把”渠道一变就得全局改”的死循环解掉了，是整套东西里性价比最高的部分。

顺带一句前瞻：iOS 8 的预览里出现了新一代 WebView，据说开放了一个正经的消息注入口子，不必再造 scheme URL。真到那天，通道这一层可以整个换掉，而消息体格式、注册表、超时与批量这些设计能原样保留——这也是我们坚持把协议和通道拆成两层的原因。

小结

JSBridge 的价值不在”能调通”，而在有一层稳定的协议：模块、方法、callbackId、参数加错误码，配合 JS 侧的回调注册表与超时清理，散乱的双平台分支就能收进一个文件。通道上，注入对象因为 CVE-2012-6636 不能用在会加载远程内容的页面上，scheme 拦截加发送队列是两端都稳的选择。性能方面，一次空转往返在低端 Android 上是十几毫秒的量级，占掉大半个帧预算，所以调优顺序是先合并次数、加缓存、把高频调用改成原生推送，再抠单帧体积；URL 通道几 KB 就开始不可靠，大 payload 得换成引用或走批量拉取。剩下的坑基本都是时序问题，靠握手、重放加幂等能覆盖大半。各家容器协议不统一是现实，值得为它多写一层适配表。
