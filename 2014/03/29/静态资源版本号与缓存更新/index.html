静态资源版本号与缓存更新

二月初那篇《HTTP 缓存机制与缓存策略》从工程落地角度把缓存头与 Nginx 配置讲完了，剩下的问题集中在另一侧：版本号到底怎么生成、引用怎么改、发布时机怎么卡。这篇不再谈响应头，专谈构建系统与发布流程的设计：版本号从哪来、HTML 与 CSS 里的引用如何被重写、多机房与 CDN 之下发布的原子性靠什么保证、更新失败又留哪几层兜底。适合正要搭静态资源构建流水线，或每次上线都在手工改版本号的同学们；强缓存与协商的区分假定你已读过旧文，本文只在必要处一句带过。

文件名为什么必须随内容变

静态资源与缓存的矛盾本质只有一组：HTML 不能强缓存，否则用户永远看不见新版；静态 js / css 却恨不得缓存到最久，2014 年的网络条件下省一次往返比省几 KB 值钱得多。一个要随时能刷新型，一个要求相反，唯一的调和办法是把”版本”做进 URL 里。URL 变了，浏览器缓存、各级代理、CDN 边缘节点都会把它当全新资源处理，旧内容再也不会被端上来；反过来，URL 没变，链路上每一环都有”权利”给你旧的——响应头写得再精巧，都是在赌别人实现的素质。

笔者第一次真切理解这句话，是 1 月底的一次事故。站点 js 分两块：common.js 对外挂全局对象 window.UIUtils，页面级 bundle 直接取用。那次重构把 UIUtils.formatDate 从 common.js 里删了，而发布流程还是老的”整目录 rsync、文件名不动”。有用户在发布前访问过页面，app.js 按旧配置落进了磁盘缓存；发布后一小时他回来，HTML 是新的，common.js 是新的，app.js 却还是旧的，里面照旧引用着已被删掉的 UIUtils.formatDate。详情页一开即报 undefined is not a function，前端错误上报的量半小时翻了一倍多，客服那边是”页面打不开”的工单。复盘最扎心的一点是：链路上没有任何一层做错事——浏览器按头缓存、CDN 按策略转发，是我们自己把”内容变了而文件名没变”的文件递到了它们手里。

从那天起我们定了底线：文件名必须随内容变，版本号由构建系统生成，不经人手。下面只讲这条底线怎么实现。

三种版本策略的机制对比

按时间顺序我们用过三种方案，差别在于版本信息放在 URL 的哪个部位。

策略 示例 刷新机制 关键风险与代价 评价
查询串 /js/a.js?v=20140329 换参数即新 URL 部分 CDN 生成缓存 key 时忽略 query，刷新整体失效 救急可用，不做主方案
目录版本 /20140329/js/a.js 换目录，整套一起生效 历史目录堆积，清理与回滚要人管 过渡期可用，维护烦
内容指纹 /js/a.3f2c1b9d.js 内容变则改名 需要构建脚本与引用重写机制 终态，现行

查询串的死穴在于缓存 key 不是你说了算。浏览器这端，URL 含不同参数视为不同条目，没问题；问题出在 CDN 与运营商网关那一层，不少服务对静态文件类型会截掉 query、只按路径做缓存 key——旧文坑三里我们为这个拿 curl 实测了一下午，结论不再重复。从设计角度看，它的意思是：同一个路径带两个参数，经忽略 query 的 CDN 拿到的是同一份内容，经保留 query 的拿到两份，行为一致性还不如没有缓存，这种方案就不能当主干。

目录版本把版本放进路径，一套请求天然分成两个完整版本集，切换即整套切换，原子性比查询串好。代价在磁盘和运维：每次发布留一个目录，得写清理脚本按保留数删；回滚干脆，HTML 指回旧目录即可，前提是旧目录没被清掉。但它有个粒度错位：动一个文件也要顶起整个目录的版本号，没变的文件同样换了 URL，白白丢掉命中；目录没传完就切 HTML 还会收获一批 404。

内容指纹给每个文件按自己的内容单独命名，这个粒度就是它的天然原子性——一个文件的版本只取决于它自己，改动只破坏它自己的引用，未改文件的 URL 恒定、旧缓存永远命中。代价是整个方案真正的工程量集中在两处：算指纹，以及让所有引用改口指向新名字。这是我们后来的主要工作所在，以下各节都围绕它们展开。

两个设计选择值得展开。

为什么不用文件时间戳？我们最早的讨论稿里就有人提 mtime 方案，它不稳定，原因有三。其一，git 不保存文件时间，每次全新 clone 之后所有 mtime 都是 checkout 那一刻，同样内容在不同构建机上得到不同”版本”；其二，rsync、解包、增量构建都会重写时间，动两分钟前的一个文件可能连带整个目录的时间戳刷新；其三，也是根本的——时间戳度量”文件何时被写”，不度量”内容是什么”，而我们要的对应关系恰恰是内容决定版本：内容不动则 URL 不动，这条性质时间戳给不了。

为什么取 8 位而不是整段 32 位？是 URL 预算。指纹名会出现在 HTML、CDN 日志、监控聚合和错误上报里，32 位 hash 让每一行都臃肿一截，日志是真金白银的资源。8 位十六进制即 32 bit，按生日界估算，千级文件规模下碰撞概率约万分之一，万级文件约百分之一，单站点静态目录够用；真到了文件数暴涨的站点就加大位数，脚本里留扩展点即可。另外 grunt-rev（当时 0.2.x）做的事本质相同，团队 Grunt 管线现成的话直接用插件更省维护成本；手写版本的价值在于映射格式自己定，下游重写不依赖任何插件。

重写引用：从 usemin 块到映射表

坑都在”顺序”上。块内引用顺序就是最终执行顺序，所以必须与依赖顺序一致；曾经有人在块内两个 script 之间内联了一段初始化，合并后执行次序一变，这种 bug 极难定位。

并发连接、合并与 combo

构建侧之外，浏览器侧还压着 HTTP/1.1 的老约束：同源并发连接数。RFC 2616 第 8.1.4 节建议客户端对同一服务器或代理不要维持超过 2 条连接，IE6/7 照做了 2 条；后来的浏览器都松了绑，Firefox 3 起、Chrome 起就是 6 条，IE8/9 也是 6，IE10 放到 8。并发预算按域名计，于是有了两个经典对策。

合并文件：把十几个 js 打成一个 bundle，多次请求换一次，连每个请求的头开销一起省。代价是缓存粒度——bundle 里任意一行改动，整个包对用户重下。所以合并单位要按”变更频率”切群：半年不动的库类打一包、每周在改的页面逻辑另打，而不是全站一把梭。指纹方案在这里恰好是互补的：合并粒度造成的重下载浪费，会以”整包换了新指纹名”的形式暴露，构建时对比新旧包体积就能量化，超标即说明进群切分不合理。

域名分片：资源摊到 g1 至 g4 几个域名，每片 6 条并发，预算翻倍。但 2014 年这招已接近收益尽头：每个新域名多一次 DNS 解析与 TCP 建连，无线网 RTT 动辄三百毫秒，成本不小；一般认为超过 4 个分片后 DNS 与建连的损耗就抵掉并发增益，我们封顶 4 个不再加。

combo 服务与版本号能共存得很优雅。当时常见的 http://g.tbcdn.cn/??kissy/k/1.3/kissy-min.js,app/lib.js 语法，把多文件拼进一次请求，文件列表本身就是 URL 的一部分：组内每个文件用指纹名，任何成员一改，整个 combo URL 自动变化，不需要额外版本参数。反过来想给 combo URL 挂查询串版本号基本不可行——多数 combo 服务不把 query 纳入缓存 key，又绕回第二节那个坑。至于 webpack，当时才出 0.x，用的人不多，按下不表。

发布的原子性：顺序、manifest 与回滚

旧文定了”资源先传、HTML 后切”的规矩，这里把它落成流程图，并讲清这套顺序能保到哪一步、哪里还差一口气。

flowchart TD
  A[构建: 指纹与重写产出完整版本集] --> B[资源上传: 全机器与CDN推送]
  B --> C[抽验: 新资源URL全部200]
  C --> D[切换HTML: 入口整套指向新版本集]
  D --> E[CDN刷新入口并预热新资源]
  E --> F{404与错误监控正常?}
  F -->|正常| G[保留旧版本资源一周后清理]
  F -->|异常| H[HTML切回旧版本集]

真正的敌人是不一致窗口。HTML 到达多机房与 CDN 成千上万节点的时间有早有晚，切换期间，甲用户拿到新 HTML、从尚未刷新的边缘节点被喂旧内容，乙用户反之。若资源是同名原地替换，这就是必出错版；而指纹方案下新旧版本本是不同 URL、各自强缓存互不干扰，窗口里真正漂移的只有”HTML 引用哪套 URL”一步——这也正是 HTML 必须协商缓存的原因之一。换句话说：指纹把”内容不一致”这个无界问题，收窄成了”引用不一致”这个有界问题，后者用顺序与刷新就能对付。

要让”HTML 与资源版本一一对应”可校验，我们把 manifest JSON 作为发布物的一部分打进包，并给每次发布一个版本 id，构建时写进 HTML 尾部注释。排查时先看页面里的版本 id，再核对引用指纹与该 manifest 是否同套，不同套即漏发。另有一种变体值得记一笔：入口 HTML 只引一个固定名的引导脚本，引导脚本先拉 manifest、再按映射动态加载真正的 js——“本次用哪套资源”由运行时决定，灰度与回滚只动 manifest 一处。代价是多一次往返加一层间接，我们的多页站点没有采用，纯 SPA 入口可以考虑。

回滚之所以便宜，靠的是旧指纹文件从不删除：HTML 切回旧版即完，剩下唯一动作是把 CDN 上的入口再刷一次。两个提醒。其一，刷新与预热权限要提前申请到位，事故当晚再找 purge 接口来不及；预热的作用也实际——切新版后第一波流量若全回源拉新资源，源站带宽弱就是自己制造高峰，热门 js / css 值得发布后立刻推。其二，清理要压着回滚窗口：旧版资源保留期至少覆盖”发现问题到完成回滚”的时长，我们定一周，且清理脚本只删 manifest 版本号早于保留线的文件，不碰目录整体。

缓存更新失败时的兜底

设计能减少错误，不能归零，兜底留了三层。

第一层是硬规矩：入口 HTML 一律 no-cache。这条底线保证哪怕其它层全失守，用户刷新一次就能回到正确版本，响应头细节旧文已讲透，不重复。

第二层是服务端改写。若用户手里的 HTML 引用了已被清理或不曾上传的指纹资源，与其抛 404，不如把入口重写到当前稳定版本：

要留意浏览器会缓存 302——不给重定向加 no-cache，兜底本身会变成新的错版来源。回滚场景同理：把新版入口 302 回旧版 URL，比干等 CDN 刷新全网生效快得多。

实践清单

最后是本项目的现行规则，逐条对着执行。

进指纹的：所有自建 js / css、站内固定字体与图标、被 CSS 引用的图片——文件名即内容，无一例外。手工版本号的：运营图，它们改动频繁但命名要可预期，统一规则是文件名带活动日期，内容与名字一起换；jQuery 等第三方库不改名，收进 /lib/jquery/1.11.0/ 这类自托管版本目录，升级是显式动作。HTML 头：入口页 no-cache，带登录态的页面 no-store，理由见旧文。

上线 checklist：

  1. 构建产出版本集与 manifest，CI 上 grep 产物，确认不存在未映射的原始文件名引用
  2. 资源先传全机器并推 CDN，curl 抽三个新文件确认 200
  3. 切 HTML，核对页面尾部的版本 id 与 manifest 一致
  4. 刷新 CDN 入口，预热头部流量的 js / css
  5. 盯 404 比例与前端错误上报曲线半小时，异常即切回旧版 HTML
  6. 上一版本资源标记为可清理，满一周才允许清理脚本动手

小结

缓存这件事的后一半在构建与发布：文件名随内容变，指纹的按文件粒度给出天然原子性，真正的工程量在引用重写与重写次序上。查询串不能当主方案，因为你赌不起 CDN 对 query 的行为；目录版本输在维护；指纹配 usemin 式的 build 块与一张 manifest，是目前的正解。HTTP/1.1 的并发预算下，合并要按变更频率切群、域名分片四个封顶，combo 与指纹天生一对。发布吃”资源先传、HTML 后切、刷新加预热”这套顺序，回滚吃旧文件不删加版本 id 对账。兜底留 no-cache 的 HTML、会失效的 302 和带防循环标记的 reload 三层。最后想说，清单里最后一项不是技术而是纪律：任何一次”内容变了文件名没变”都不许过——事故我们只买过一次单。
