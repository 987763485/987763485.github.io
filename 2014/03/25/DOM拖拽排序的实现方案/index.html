DOM 拖拽排序的实现方案

后台里”按住一行拖到别处，顺序就变了”这个功能，看着不起眼，真做起来坑一大堆：放下去位置算反、IE 8 里拖两下选中半屏文字、手机上根本点不动。本文把三条实现路径（HTML5 原生拖放、鼠标事件手工实现、jQuery UI Sortable）分别讲透，每条都给可以直接跑起来的 ES5 代码，再补上落位之后的数据计算、移动端的打法和笔者踩过的坑。适合没写过拖拽、正准备给后台加一个排序功能的前端同学，读完至少能挑对方案并把第一版跑起来。

需求描述：拖动列表行改变顺序

笔者的场景很典型：后台的首页模块配置页，一个列表（或者表格），每一行是一个模块，运营同学想把”公告栏”拖到”首页大图”上面去，松手之后新顺序提交服务端保存。服务端并不关心你怎么拖的，它只要一个 id 数组，例如 ["notice","banner","recommend"]。

把这个需求拆开，一个可用的拖拽排序至少要能做好 5 件事：

  1. 识别拖拽起点，也就是”按住的是哪一行”；
  2. 拖动过程中给出可见反馈：一个跟随鼠标的影像，加上一个表示”将要放在这里”的占位符；
  3. 松手时把这一行插入正确的位置（DOM 落位）；
  4. 落位后按 DOM 顺序算出新的索引数组并提交（数据落位）；
  5. 提交失败或用户中途取消时，能恢复原来的顺序。

整个流程可以用一张图概括，三条路径只是在这张图的每一步上换了不同的事件而已：

flowchart TD
    A[按住某一行] --> B[进入拖拽态: 显示跟随影像与占位符]
    B --> C[移动]
    C --> D{移动到了别的行上方}
    D -->|是| E[占位符换到新位置]
    E --> C
    D -->|否| C
    C --> F[松手]
    F --> G[真实落位到 DOM]
    G --> H[按 DOM 顺序生成索引数组]
    H --> I[提交服务端]
    I -->|失败| J[用备份顺序还原]

三条路径怎么选

动手之前先把路线定了，因为三条路径写出来的代码几乎不能复用。

对比项 HTML5 拖放 API 鼠标事件手工实现 jQuery UI 1.10.x Sortable
桌面兼容 IE 9+ / Firefox / Chrome，IE 8 不支持 桌面全线，含 IE 6 起 依赖 jQuery 1.6+，IE 7 起可用
移动端 不支持 换成 touch 事件即可 需要 touch punch 补丁
代码量 六七十行 一百多行 配置十几行
额外体积 0 0 完整包数百 KB，精简包约 20 KB
视觉控制 跟随影像由浏览器画，只能换一张图 完全自绘，想怎么动效都行 中等，helper 可返回自定义节点
上手难度 事件多，坑在细节 全部自己处理，坑在坐标 最低，但黑盒最深

选型思路：

  • HTML5 原生拖放是”浏览器帮你做了脏活”的路线，能拿到拖拽影像、能跨窗口拖拽，代价是各浏览器实现细节不一致，而且 IE 8 和手机浏览器直接出局。
  • 手工鼠标事件路线兼容性最好，代价是跟随元素、占位符、自动滚动、鼠标丢失全得自己写。
  • jQuery UI Sortable 是配置化路线，placeholder、helper、connectWith、forcePlaceholderSize 这些选项把常见需求都覆盖了，但是为了一个排序功能引一整套库，体积和”改不动”的问题会很现实。

顺带说一句指针事件：IE 10 上有带私有前缀的指针事件，想把 mouse 和 touch 合成一套代码，但生态还没跟上，2014 年基本没有库认真支持它，所以本文还是按鼠标事件与 touch 事件两套来写。

移动端怎么办

2014 年的移动浏览器基本没有实现 HTML5 拖放 API，iOS Safari 和 Android 原生浏览器里 dragstart 一次都不会触发（Android 4.4 里刚出现的那个 WebView 也别指望）。所以移动端只有一条路：touchstart / touchmove / touchend 自己实现一套跟随。

难点不在拖，而在和页面滚动的争夺。touchmove 里一调用 preventDefault()，浏览器就不滚了；可用户手指在屏幕上滑动，本来十有八九是想滚动页面。解决方案是”长按之后才接管”：按下时起一个定时器，如果 500 毫秒内手指有明显位移，说明用户在滚动，取消定时器把控制权交回浏览器；只有手指按住不动满 500 毫秒，才认定为拖拽意图，此后才允许 preventDefault。

三个细节：touchmove 建议绑在 document 上而不是行本身上，因为行一旦搬走就收不到后续事件；跟随位置读 e.touches[0].pageY，它是页面坐标，省掉自己加滚动量；iOS 上带 -webkit-overflow-scrolling: touch 的滚动容器有惯性，拖拽时若要自绘滚动，长按进入拖拽态顺手把这个属性关掉比较省事。最后别忘了解决”选中文字弹菜单”，-webkit-user-select: none 加上 -webkit-touch-callout: none。

另外，触屏设备往往既发 touch 又发 mouse（松开后还会补一发幽灵点击），两套事件都绑时要用一个标志位隔开，或者干脆按 ontouchstart in window 分流。

踩过的坑与选型建议

集中列一下上面没展开说、但真的会咬人的几点：

  • 文字被选中打断拖拽。除了 CSS 的 user-select，IE 8/9 还认元素上的 unselectable="on" 属性，CSS 不管用时要补这个；在 mousedown 里 preventDefault 也能挡掉，但副作用是输入框无法聚焦，别绑到整页。
  • a 和 img 默认可拖拽。列表里如果有封面图，按住图拖会把图片单独拖走，dragstart 里对它们 preventDefault，或者给它们加 draggable="false"。
  • 拖进 iframe 就回不来。拖拽经过 iframe 时事件被 iframe 吃掉，dragend 可能完全不触发，页面卡在拖拽态。兜底办法是监听 window 的 blur，或者在 dragstart 时给代理元素加一个透明遮罩层盖住 iframe；跨域 iframe 之间没法通信，只能靠遮罩。
  • 自定义拖拽影像的图片是空的。用外链图片做 setDragImage，如果对方开了防盗链（校验 Referer），影像就是一块白。要么用页面里已渲染的节点，要么把小图转成 Base64 内联。
  • 父容器有 transform 或层叠上下文。给代理用绝对定位跟随页面坐标时，如果它挂在带 transform 的祖先下，坐标系会跟着变成以该祖先为原点，跟随就整体偏移。最稳的做法永远是把代理挂到 body 下，并给足 zIndex。
  • 每帧读写交替导致掉帧。mousemove 一秒钟能触发上百次，在里面读 offsetHeight、getBoundingClientRect 又立刻改样式，会把 layout 反复刷新。像上面 movePlaceholder 那样先一次性读完所有 rect，再统一改 DOM，帧率差别很明显。
  • 拖拽期间不要改行内容。异步请求回填文字、图片加载完成导致行高变化，占位符位置瞬间就偏了，最好在拖拽态把这类刷新暂停。

至于怎么选，笔者的结论很朴素：

场景 建议
公司内部后台，只用桌面 Chrome 与 IE 9+ HTML5 原生拖放，零依赖、六七十行搞定
要兼容 IE 8 或 IE 9，项目已经引了 jQuery UI Sortable，但请打只含 core 加 sortable 的精简包
要同时覆盖手机和平板，或者需要精细的跟随动效 自研，鼠标与 touch 两套事件共用同一套落点计算逻辑
需要跨浏览器窗口/跨页面拖拽（比如从素材库拖进画布） 只有 HTML5 原生拖放能做到，手工方案没戏

小结

拖拽排序的三条路径，本质上只是”谁替你处理了跟随和落点”：HTML5 原生拖放替你处理，代价是 IE 8 和移动端出局；jQuery UI Sortable 用配置替你处理，代价是体积和黑盒；手工鼠标事件什么都不替你，换来完全的控制权。写的时候记住四件事：draggable="true" 不能少、dragover 必须 preventDefault、dragenter/dragleave 要用计数器、DOM 与数据之间只用 id 建立映射而不是按下标比对。移动端在 2014 年没有捷径，只能长按接管加 touch 跟随，并且要小心别把页面滚动一起杀掉了。先把结构和 id 定下来，三条路径的骨架其实是同一套，换的只是事件名。
