JavaScript switch 与 switch(true) 技巧

switch 大概是 JavaScript 里最容易被轻视、也最容易被用错的一个语句。刚工作一两年的同事往往把它当成”多个 if-else 的语法糖”，直到某天线上冒出一个诡异的 bug，才发现里面的门道比想象中多。本文从一次真实的排查经历讲起，把 switch 的比较规则、执行模型、结构细节讲透，再聊 switch(true) 这个小技巧的适用边界，最后给出对象分派表等替代写法和一套可以落地的团队规范。

从一个线上 bug 说起：switch 用的是严格相等

去年维护一个订单后台页面，订单状态由后端一个接口返回，前端用一个函数把状态码翻译成中文文案。代码大致长这样：

关键在于：switch 拿 case 值与表达式做比较时，用的是严格相等（===），而不是宽松相等（==）。这意味着类型必须一致，字符串 '2' 和数字 2 在它眼里就是两个东西，不会像 == 那样偷偷帮你做类型转换。想改宽松匹配的愿望是不存在的，这是语言层面的硬性规定。

switch 的执行模型：case 是入口，不是分支条件

理解了比较规则，再来看执行模型。很多人把 case 想成一串串”如果相等就执行这块”的独立分支，其实不对。switch 的执行过程是这样的：先计算表达式的值，从上到下逐个 case 用 === 比较，一旦命中，就从那一条 case 开始，一路往下执行所有语句，直到遇见 break 或者整个 switch 结束。

也就是说，case 只是一个”入口标签”，标记从哪里开始执行，而不是”进入后就只执行这一段的边界”。如果没有 break，程序会顺势”掉”进下一个 case 的语句里，这就是所谓的 fallthrough（贯穿）。

case 1 里没有 break，所以命中它之后继续执行 case 2 的语句，直到 case 2 末尾的 break 才停下。这个特性既是坑，也是一种有意为之的写法——处理键盘事件时，方向键常常要归到同一段逻辑：

用一张流程图把执行模型梳理清楚：

flowchart TD
    A[计算 switch 表达式] --> B[自上而下逐个用 === 比较 case]
    B --> C{有命中的 case 吗}
    C -- 没有 --> D[执行 default 分支]
    C -- 有 --> E[从命中的 case 入口开始执行]
    E --> F{遇到 break 了吗}
    F -- 遇到 --> G[跳出整个 switch]
    F -- 没遇到 --> H[继续执行下面的语句]
    H --> I{走到 default 或结束}
    I -- 到 default --> G
    I -- 语句块结束 --> G

再说 default 的位置。它只是”所有 case 都没命中时”的兜底入口，正常匹配时写在开头、中间还是结尾行为都一样。但一旦前面有 case 没写 break，执行顺序就跟着书写顺序走了——把 default 夹在一串会贯穿的 case 中间，它可能被上面漏了 break 的 case 顺带执行到。所以除非刻意为之，default 放结尾最符合直觉。

关于 fallthrough，还有一个协作层面的坑：漏写 break 是很隐蔽的 bug，肉眼很难发现。JSLint 和 JSHint 都对贯穿行为有告警。JSHint 的报错信息是 -W086: Expected a 'break' statement before 'case'，只要某个 case 结尾没有 break 也没有注释说明，它就会提醒你。团队里普遍的做法是：真正的、有意的贯穿，要在 case 结尾写一行约定注释：

结构细节：块作用域、花括号与 case 表达式

switch 语句本身带着一对 {}，构成一个单独的块。坑在于：所有 case 共享这一个块作用域，而不是每个 case 各有其作用域。

在 2014 年，JavaScript 还没有块级作用域的声明方式，变量只能用 var 声明，而 var 的作用域是函数级的、会被提升到函数顶部。于是你在 case 'a' 里写的 var msg，跟 case 'b' 里写的 var msg，其实是同一个变量。轻则值被意外覆盖，重则两个分支互相踩到对方的状态。而且同一块里重复 var 同名变量并不报错，问题会安静地活到线上。

规避办法很朴素：给每个 case 单独套一层花括号，把它当作一个独立的小块来写。虽然这并不能真正造出块级作用域（还是函数作用域），但它至少在视觉上把变量归属划清了边界，配合 JSHint 的 latedef、unused 检查，能在写的时候就发现命名冲突。

当某个 case 里的逻辑变长、需要自己的局部变量时，笔者的建议往往是：别在 case 里堆代码，直接抽成一个函数，case 里只留一行调用。这样作用域问题、贯穿问题一并消失。

再讲一个容易被忽略的点：case 后面跟的并不只能是字面量，它可以是任何常量表达式，运行时才求值，并且是自上而下算、一旦命中就停止往下算 case。

因为比较用的是 ===，case 表达式的求值结果类型要和 switch 表达式一致才能命中；而且由于”求值到第一个命中就停”，如果你的 case 表达式带有副作用（比如调用了一个会改变状态的函数），后面的 case 表达式根本不会被求值。所以稳妥的习惯是：case 值保持简单、无副作用。

switch(true)：把区间判断搬进 case

既然 case 可以是任意表达式、比较又是 ===，就引出一个很有意思的写法：把 switch 的表达式写成 true，然后让每个 case 是一个会返回布尔值的判断，只要哪个 case 结果为 true，就与 true === true 命中。这样就把一串”区间/条件判断”排成了类似枚举分派的样子：

不过它有明确的边界，用得不好反而添乱。第一，因为用的是 ===，每个 case 必须老老实实返回布尔 true 才命中，case 1 或 case 'yes' 这种 truthy 值永远命不中 true。稍有不慎就会重演本文开头那个类型坑：

第二，它把顺序敏感的逻辑藏进了 case 列表，读的人要时刻记住”自上而下第一个命中即停”，条件一多就容易看漏。第三，对不熟这个花式的同事，switch(true) 第一眼是有点费解的，团队协作时未必比 if-else 省心。

所以笔者的取舍是：当条件本身是”同一变量跟若干离散值相等”时，用普通 switch；当出现”三段以上互斥的区间判断、且判断两侧形式规整”时，可以考虑 switch(true)；一旦条件里混进了需要 Boolean() 显式转换的值，或者彼此有复杂依赖，老老实实写 if-else，别为了整齐牺牲可读性。

性能：跳转表是理论，可读性才是理由

很多人对 switch 有个朴素印象：它比 if-else 快，因为编译器能生成”跳转表”，直接按索引跳到对应分支，省去逐个比较。这个说法在 C 语言里、case 是密集连续整数时确实成立。但 JavaScript 是动态类型语言，switch 的表达式可以是字符串或任意值，case 也不必连续，多数场景根本构建不出紧凑的跳转表。

真实引擎的做法大致是这样：V8 和 SpiderMonkey 会视情况把 switch 编译成线性比较（还是一个一个 case 试）、二分查找，或者在 case 值恰好是密集整数时退化成一个基于哈希/跳转的分派。换句话说，switch 和 if-else 在 JIT 之后，运行期差别往往很小，甚至某些结构下 if-else 反而更快。为了验证，笔者在自己的笔记本上做过一组粗略计时（Chrome 稳定版，Node 0.10，取多次运行的大致中位数，仅供参考，别当基准测试看）：

分派场景 if-else 链 switch（case 离散值） 对象分派表
4 个分支命中平均位置 约 6 ns 约 5 ns 约 12 ns
8 个分支 约 11 ns 约 7 ns 约 13 ns
30 个分支（字符串） 约 40 ns 约 30 ns 约 11 ns

数字看个趋势就好：分支少时三者差距在个位数纳秒，实际测不出影响；分支很多且用字符串时，对象分派表走哈希查找，反而比 switch 的线性比较更占优。纳秒级的差别在真实浏览器交互里可以忽略——一次 DOM 操作或网络请求的成本是它的成千上万倍。

所以结论很干脆：选 switch 还是 if-else，理由应是”哪种写得更清楚”，而不是”哪个跑得快”。真要抠热点循环的性能，先 profiling 再优化，别凭”switch 一定快”的直觉改写代码，那样常常既徒劳又降低可读性。

替代模式：对象分派表、数组索引与策略函数

switch 用多了，会遇到两个天花板：分支无法跨文件扩展，以及 case 值必须是编译期能写出来的表达式。这时候换一种模式往往更顺手。

分派表相较 switch 的价值在于可扩展：别的模块可以往对象里挂新的处理器，而不必改动这一个大函数；也便于把处理逻辑拆成独立命名的函数，单元测试更好写。代价是多了哈希查找、以及要时刻提防原型链上的键。

老引擎的坑：JScript 与早期实现

写分派代码时，如果还要兼容老的 IE，得知道一些引擎差异会咬人。

先说重复的 case 值。ECMAScript 标准其实允许两个 case 写同一个值，命中时执行的是从上到下第一个匹配的 case，第二个就成了永远不会进入的死代码。但老版本 IE 的 JScript 引擎在处理重复 case 时表现并不稳定，某些构造下甚至会出现意料之外的跳转。所以稳妥的团队约定是：switch 里不要出现重复的 case 值。JSHint 对重复 case 会报 Duplicate case label，把它开在构建流程里，能在写代码阶段就拦住这类问题。

再说 switch 块里的函数声明。在老引擎上，把 function foo() {} 直接写在某个 case 分支里，其作用域归属各家实现不一：有的把它提升到整个函数，有的处理得更暧昧，配合贯穿控制流还可能触发怪异行为。ES5 严格模式下块内函数声明本就不被鼓励。规避办法跟前面”case 逻辑长了就抽函数”的建议一致：不要在 case 里声明函数，需要就放到 switch 外面，或由 case 调用一个独立命名函数。

团队规范：什么时候用 switch，什么时候用 map

把上面的经验收敛成几条可落地的团队规范，供刚入行的同事对照执行。

必须优先用 switch 的场景，是”对一个枚举变量的离散值做分派”，比如订单状态、键盘 event.keyCode、HTTP 状态码这类取值有限、彼此互斥、就近几个分支能写下的情况。它比一长串 if-else 整齐，且多个 case 共享同一段逻辑的贯穿能力，是 if-else 替代不了的。用 switch 时要守三条：进 switch 前先把表达式的类型规整到与 case 一致（这是本文开头那个 bug 的教训）；每个 case 要么 break 要么显式写 /* falls through */ 注释；有局部变量就给 case 套花括号，逻辑一长就抽函数。

优先用对象分派表的场景，是”映射需要扩展、或键是字符串、或分支多到 switch 已经难读”。跨模块挂处理器、按路由名分派、按类型选择策略函数，都更适合 map。用 map 时守两条：判断键存在一律用 hasOwnProperty.call，绝不写 if (map[key])；提供统一的默认兜底函数处理未知键。

至于 switch(true)，把它当作 if-else 链的可选替代而不是默认选择，条件不规整或含 truthy 值时改回 if-else。

Code Review 时，switch 是一段值得专门盯的语法，检查清单就几条：有没有哪个 case 结尾既没 break 也没 /* falls through */ 注释（漏 break 的头号来源）；有没有类型不一致导致永远命不中的 case；有没有重复的 case 值；default 是不是放在结尾；case 里有没有跨分支共享、可能互相覆盖的变量。这几条靠人眼容易看漏，但交给 JSHint 的 curly、forin、latedef 加 -W086 基本能在提交前自动逮住——把 linter 跑在 CI 里，比任何口头约定都靠谱。

小结

switch 的核心心智模型只有两条：比较用严格相等（===），case 是执行入口而非独立分支。前者提醒你分派前先统一类型，别踩字符串对不上数字的坑；后者提醒你 break 和 /* falls through */ 注释的重要性，以及 default 位置在贯穿情形下的影响。结构上所有 case 共享一个块作用域，在还没有块级声明的当下尤其容易撞名，套花括号、逻辑长了抽函数是稳妥习惯。switch(true) 是把区间判断排成 case 的小技巧，但受限于 === 对布尔值的严格要求，用错反而不如 if-else。性能上不必纠结，跳转表只是特定条件下的理论，选择应以可读性为准。当分支需要扩展或键是字符串时，对象分派表（记得 hasOwnProperty 与默认兜底）、数组索引、策略函数往往比 switch 更合适。把这些沉淀成规范、交给 JSHint 把关，比依赖个人记性可靠得多。
