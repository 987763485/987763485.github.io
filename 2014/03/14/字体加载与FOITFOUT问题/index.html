字体加载与 FOIT、FOUT 问题

前一阵子做站点首屏优化，性能清单上冒出一条奇怪的记录：”标题文字先空白一下，然后突然跳出来”。查下去发现这不是 bug，而是 @font-face 字体下载的固有时间差——浏览器在下载字体文件的窗口期里怎么渲染文本，各家实现完全不同。本文把这段时间踩的坑整理出来：FOIT 与 FOUT 到底是什么、2014 年各浏览器的真实行为、可控加载的检测代码怎么写，以及中文字体特有的体积现实。适合所有在项目里用过 webfont 的前端同学。

现象：文字先空白，或者先跳变

用 @font-face 引入的字体需要额外下载一个字体文件，而页面的渲染流水线并不会停下来等它。下载期间页面上本该用这个字体渲染的文本怎么办？实践中出现了两种截然相反的故障形态。

一种是 FOIT（Flash of Invisible Text，不可见文本闪烁）：字体没下载完，文本干脆不画，用户看到的是”文字位置一片空白”，字体到位后文字才突然出现。首屏有大标题的页面感受最明显——页面结构都在，唯独标题不见了，用户会怀疑是不是白屏卡住了。

另一种是 FOUT（Flash of Unstyled Text，无样式文本闪烁，这个叫法是 Paul Irish 在 2009 年提出的）：浏览器先用回退字体把文字渲染出来，字体下载完再替换成目标字体。问题是同一串文字在两种字体下的宽度、高度几乎不可能一致，替换瞬间文字会”跳”一下，行尾不齐、按钮里的文案变宽挤爆容器都算轻的，严重时整页内容上下抖动。

两者对用户感知的影响不对称。笔者认为 FOIT 更伤：空白意味着”内容不存在”，直接拉高跳出率；FOUT 至少信息是即时可读的，代价只是观感上的不稳定。但图标字体是例外——回退字体渲染私用区码位只会画出”豆腐块”或什么都不画，那种效果比晚出现更糟。

典型的时序大概是这样：

sequenceDiagram
    participant B as 浏览器
    participant S as 服务器
    B->>S: 请求 HTML
    B->>S: 请求 CSS
    S-->>B: CSS 中发现 @font-face
    B->>S: 请求字体文件
    Note over B: 下载窗口期：空白或回退字体
    S-->>B: 字体到位
    Note over B: 替换为目标字体

各家自己的行为：2014 年的浏览器矩阵

问题的根源在于：CSS Fonts Module Level 3 规范只定义了”怎么声明字体”，压根没有规定”字体下载期间怎么渲染”。Font Loading API 和 Font Load Events 都还只是 W3C 草案，传说中的 font-display 描述符连影子都没有。于是每个浏览器都自由发挥了：

浏览器 下载窗口期的表现 备注
IE 6-11 立即用回退字体渲染（类 FOUT） 但字体到位后不会主动重绘文本，常常要等一次 reflow 才替换
Firefox 4-27 约 200ms 隐形（短 FOIT），之后回退字体，下载完成再替换 行为最”折中”，也最容易被忽略
Chrome 25-33 全程隐形，直到字体下载完成（长 FOIT） 网络稍慢首屏标题就消失几秒
Android 原生浏览器 类似 Chrome 的 FOIT；CSS 跨域引用时字体直接不生效 老 bug，逼得人把字体转 base64 塞进同域 CSS
iOS Safari 5/6 FOIT，一直等字体 对慢网络极不友好

这张表是笔者在自己项目里拿虚拟机和真机逐个试出来的，结论只有一句话：不存在统一规范，你无法预测用户看到哪种故障。另外提醒一句，Chrome 早期实现过一套私有的 font events（document 上的 fontload 系列事件），新版已经移除，别再依赖它；Firefox 那个 200ms 隐形期也让”到底是 FOIT 还是 FOUT”的争论变得没有意义——取决于你测哪个浏览器。

@font-face 的写法守则与跨域坑

先把声明本身写对，能避开一半的加载失败。

src 列表按浏览器取第一个能解析的格式，所以顺序是策略本身：EOT 是给 IE9 以下的，不带 format() 单独放第一条；WOFF 作为绝对主力——它在 TTF 基础上加了压缩，体积一般是 TTF 的六到七成，且 IE9 以后的所有现代浏览器都支持；SVG 字体如今只值得为旧版 iOS Safari 兜底，新 iOS 不再支持，写在最后即可。规范里还有个 unicode-range 描述符，理论上可以按码位分段懒加载字体，但 2014 年只有 Chrome 和 IE 的部分版本支持，实践中指望不上。

服务端配置上有两个坑。第一是 MIME 类型：Nginx 要在 mime.types 里补上 woff application/font-woff（写 application/x-font-woff 也通用）、ttf application/x-font-ttf，类型不对 Firefox 会直接拒绝解析。第二是跨域：字体文件放上 CDN 后属于跨域资源，响应必须带 Access-Control-Allow-Origin。麻烦在 IE——IE10 及以下对 CORS 字体有额外限制，不仅要求字体响应带 ACAO 头，连声明 @font-face 的那份 CSS 也必须与页面同域，否则 IE 根本不发起下载；而且老 IE 发请求时不带 Origin 头，服务端没法按来源区分，只能无条件返回 Access-Control-Allow-Origin: *。nginx 里一行搞定：

中文的现实：体积与子集化

上面说的都是西文场景的从容——一套 OpenSans 的 woff 也就 20KB 上下。中文是另一个世界：覆盖 GB2312 七千多汉字的字体文件，TTF 普遍在 8-11MB，转成 WOFF 压缩后也要 4MB 上下。做个算术：2014 年国内 3G 实际下行按 2Mbps 算，4MB 意味着 16 秒起步，还没考虑信号波动和运营商劫持。结论很残酷，整包中文字体做正文 webfont 在今天就是不可用的。

可行的路子只有子集化：一个页面真正用到的汉字远少于七千个，用 fontsub、FontForge 这类工具把字体裁成”只包含用到的码位”，标题字体几十个字符可以压到几 KB，正文如果非要上，3500 常用字裁剪加压缩也要几百 KB 起，依然只在 WiFi 环境勉强可谈。

这个思路的极端成功用例就是图标字体——只打包十几个私用区字形，WOFF 压到 10-30KB。笔者在旧文《CSS 图标字体 iconfont 的使用与制作》里详细写过制作链路，这里不重复，只想指出一点：iconfont 本质是”中文 webfont 体积困境 + 子集化”这个等式的特解，而它付出的代价恰好就是本文主题的 FOIT/FOUT——图标位先空白或先出豆腐块。同一个矛盾，两个方向。

可控加载：先回退渲染，就绪再切换

既然浏览器行为不可控，就把控制权拿回自己手里。笔者的做法分三步：首屏 CSS 里完全不出现 @font-face，标题先用系统字体栈渲染；页面骨架就绪后再异步注入带 @font-face 的样式表；用 JS 检测字体真正可用后，给 body 加类名让规则生效。

布局抖动、缓存与体积的进一步压缩

即便做到了”就绪再切换”，替换瞬间的宽度变化仍会触发一次 reflow，这是无法消除只能减轻的。几条经验：

  • 标题和按钮的 font-size、line-height 用 px 显式写死，别用 em 或百分比——line-height 一旦是数值，换字体时行盒高度会跟着目标字体的度量跳变；写死 px 至少让纵向不动，抖动被限制在横向。
  • 回退字体尽量选和目标字体字宽接近的西文字体（比如 OpenSans 配 Helvetica/Arial），宽度差小，跳变就不明显。中文环境下这条基本失效，也是笔者主张正文不上 webfont 的又一个理由。
  • JS 里凡是”测量文本像素尺寸再定位”的逻辑（居中标签、canvas 文字排版），要么等 wf-active 之后再执行，要么重新测一遍。笔者的一个 tooltip 定位 bug 就是测量发生在字体替换前，上线后只在首次访问复现，查了很久。

缓存方面，字体文件几乎不变，务必 Cache-Control 长缓存加文件名指纹（我们的 Grunt 构建里接了个 rev 任务，输出 opensans.woff 变 opensans.a1b2c3.woff），改一个图标、换一个版本号都是安全操作。注意 ?#iefix 这种假查询串不影响缓存命中。传输层面，WOFF 内部已压缩，再开 gzip 收益很小（个位数百分比）；如果你还在发 TTF 或 SVG 字体，gzip 能再省三成左右。至于把几 KB 的子集字体转 base64 塞进 CSS 的 data URI 方案，要清楚两个代价：base64 本身膨胀约 33%，以及 iOS 4 的 Safari 有个著名 bug——行内 <style> 里的 data URI 字体不加载，必须把 @font-face 挪进外部 CSS 文件才生效。当年 Android 原生浏览器那个跨域 CSS 不吃字体的 bug，也正是靠这招绕过去的。

实践建议清单

把全文收拢成一份可执行的建议：

  1. 正文一律系统字体栈，任何 webfont 都不要碰大段文本，中文尤甚；
  2. 只有标题、品牌字、图标用 webfont，且中文必须子集化到页面实际用到的字符；
  3. 采用”回退先渲染、检测就绪再切类名”的渐进增强方案，并设置约 3 秒的超时兜底；
  4. 字体放 CDN 时配好 Access-Control-Allow-Origin: *、正确的 MIME 类型，声明字体的 CSS 保持与页面同域（为了 IE）；
  5. src 顺序固定为 EOT、WOFF、TTF，SVG 只给旧 iOS 兜底，unicode-range 当它不存在；
  6. 文件名指纹加长缓存，字体集随构建产出而不是手改；
  7. 移动端默认降级：弱网或小屏直接不注入字体，省流量也省一次 reflow。

小结

FOIT 和 FOUT 不是谁的 bug，而是规范缺位下各浏览器各自为政的产物——2014 年我们能做的只有把渲染时机攥在自己手里。工程套路总结成一句话：系统字体保证内容即时可读，异步注入触发下载，宽度轮询检测就绪，类名切换完成增强，超时兜底保证失败也有确定形态。中文项目在体积面前几乎没有第二条路：正文放弃 webfont，标题和图标走子集化。等 Font Loading 规范真正落地、浏览器行为统一的那一天，这篇文章里大半的 hack 都应该扔掉——但在那一天到来之前，它们就是我们手里仅有的工具。
