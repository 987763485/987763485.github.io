CSS3 @font-face 与网页字体优化

本文属于《HTML 与 CSS》第 41/62 篇
上一篇系列目录下一篇

上一篇写字体加载，把 FOIT、FOUT 和就绪检测讲完了，留下问得最多的一句话是：这个字体文件本身还能不能再小一点。本文只谈文件，不谈加载时机——描述符与 local() 的边界、同一份字体五种格式的体积差、中文怎么靠子集化从 MB 级打到 KB 级、多字重要不要下真文件、回退字体的度量怎么配、体积预算怎么钉进构建。至于下载窗口期浏览器怎么渲染、宽度轮询检测怎么写、CDN 上的跨域与 MIME 怎么配，旧文《字体加载与 FOIT、FOUT 问题》已经说过，这里不重复。

描述符的边界，以及 local() 埋过的坑

@font-face 的描述符就那么几个，2014 年真正把语义落实的只有一半：

描述符 作用 今年的实际状况
font-family 给这个文件起一个族名 必须与 CSS 里引用的名字逐字符一致，含空格要加引号
src 候选来源列表，local() 与 url() 混写 浏览器按顺序挑第一个能用的，local() 排前面会短路后面所有 url()
format() 声明后面那个 URL 的容器类型 embedded-opentype / woff / truetype / opentype / svg，认不出的跳过
unicode-range 声明这个文件负责哪些码位 只有 Chrome 和 IE 的部分版本实现，Firefox、Safari 直接忽略，指望不上
font-style 这个文件是正体还是斜体 正常可用
font-weight 这个文件的真实字重 正常可用，且必须和文件内 OS/2 表的 usWeightClass 对上
font-stretch 字面宽度（condensed / expanded） 除 IE 个别版本外基本无人实现，写了也白写
font-variant normal / small-caps 只有 Chrome、Opera 会拿它做族内选择，别当特性用

坑在 local()。它的语义是”先看用户机器上有没有这个字体，有就直接用，不发请求”，听起来省，实际是调试黑洞。上半年的品牌页就吃过一次：标题字体是买了 web 授权的方正兰亭黑，src 第一行写了 local('方正兰亭黑_GBK')，设计同学的开发机装过全套字库，页面一路正常，视觉走查也过了。子集化流程五月初上线，构建产物 296 KB，日志里那条字体 URL 的请求数连续两周是零——内网机器全部命中 local()，子集压根没被下载过，等于白做。问题是在外部用户反馈里暴露的：标题的”™”和后台动态注入的活动名变成了豆腐块。因为开发机上那份完整版覆盖两万余码位，我们的 296 KB 子集只有 940 余个。

三条经验：

  1. 品牌字体、子集字体一律不要写 local()：用户机器上那个同名家族是什么版本、什么字重你控制不了，命中与否会让线上表现和开发机完全不同。
  2. local() 只用来复用系统自带字体（local('Microsoft YaHei')、local('SimHei') 之类），而且要想清楚中文 Windows 上很多字体注册名是本地化的，名字对不上就是白写一行。
  3. 排查”我这好使、他那不好使”时，先把 local() 注释掉再比一次；确认可用性看 Network 面板的字体类型过滤。至于怎么判断字体真的换上了，旧文里有轮询检测的实现；最近 Bryan Jackson 放了个叫 FontFaceObserver 的新库，思路一样、做得更轻，作者还在完善，本项目暂时自研。

格式选型：同一份字体的五种容器

先给口径。WOFF 不是什么新字形格式，它就是一个带压缩的 sfnt 容器：把 TTF/OTF 内部的每张表单独做 zlib deflate，加一小段头部和校验，字形数据完全不变。所以同一份字体，WOFF 相对 TTF 的压缩率稳定落在 25%—40%，具体跟内容相关，汉字表（glyf）压得狠、cmap 基本压不动。EOT 是微软自己的压缩 sfnt，只 Windows/IE 认。SVG 字体是把轮廓写成路径文本，无压缩，体积最大。

下面是笔者手上两份字体 2014 年 6 月的实测（原始字节，未计服务端压缩）：

格式 容器本质 压缩 Open Sans Regular 方正兰亭黑 GBK（全量） 谁需要它
eot 微软压缩 sfnt 有，私有算法 68.9 KB 7.21 MB IE6—8 必须，IE9 也认
otf sfnt + CFF 轮廓 无 118.4 KB 12.86 MB 老 Safari、桌面软件更常见
ttf sfnt + TrueType 轮廓 无 96.4 KB 10.42 MB 老 Android 2.x/4.3 以下只认它
woff 压缩 sfnt 逐表 zlib 61.2 KB 6.98 MB 主力：IE9+、Chrome 6+、FF 3.6+、Safari 5.1+、Android 4.4+
svg 路径文本 无 121.7 KB 16.30 MB 只给 iOS 5 以下兜底，新 iOS 已停止支持

三点结论。第一，西文那份 WOFF 相对 TTF 省 36.5%，正落在 25%—40% 这个正常区间；中文那份 otf 到 woff 省 46%，汉字轮廓重复度高、deflate 收益格外好，别拿西文的经验去猜中文。这就是”WOFF 当主力”的全部理由。第二，EOT 绕不开：IE6—8 只吃这一种，而浏览器不会帮你导出，必须在构建里挂一次转换。微软放过 ttf2eot 这类命令行工具，Font Squirrel 的网页生成器也内置了，我们用的是前者。注意 ttf2eot 不吃 CFF 轮廓，OTF 直接转要么失败要么丢字形，得先用 FontForge 把曲线从 cubic 转成 quadratic（导出 TTF 时自动做这一步），再转 EOT。第三，WOFF 2.0 从 2013 年 8 月起仍是 W3C 工作草案，号称同字形下再省三成，但目前只有 Chromium 内核的实验性构建支持，覆盖率可以忽略不计，项目里不能依赖，也别为它预留管线。

子集化才是中文优化的主战场

上面那张表里中文那列，压成 WOFF 也还有 6.98 MB，按 2014 年国内 3G 有效下行 1.5—2 Mbps 算，光下载就要 28—37 秒。整包中文字体做 webfont 是死路，只能裁剪：留多少码位，就花多少体积。兰亭黑这份裁剪后摊下来每个汉字约 250—350 字节（WOFF 压缩后，共享表另计），所以”下多少字”几乎是”下多少 KB”的线性关系，可控性极强。

从 12.86 MB 到 27 KB，四百多倍，这就是中文 webfont 唯一可行的优化。

代价也必须写在脸上，别只吹收益：

  • 动态文案缺字。后台可配的运营标题、用户昵称、商品名，只要冒出一个不在子集里的字，前台就是豆腐块或者悄悄掉回退字体，走查看不出、线上炸得莫名其妙。兜底办法是把可能变的那部分（价格、倒计时、活动名）改成服务端出图或走系统字体栈，webfont 只覆盖设计稿里确定的静态文案；ASCII 与中日韩标点整段留作基线，别抠这几字节。
  • 多一条发布链路。文案一改就得重跑抽字符、重新裁剪、换指纹、刷 CDN，任何一环漏掉就是”新 HTML 配旧字体”的缺字。这条得进 Grunt 的 build 任务，产物跟 HTML 同一次发布，禁止手工替换字体文件。
  • 许可问题。中文商用字体的 web 嵌入授权多数按域名加 PV 计费，”能不能裁剪、能不能衍生再分发”要逐条看协议，有些明确禁止改动轮廓，兰亭黑这份我们单独签过 web 授权才敢进构建。文泉驿、Droid Sans Fallback 这类带字体例外许可的才能随便折腾；冬青黑体虽然常见，苹果授权并不覆盖 web 嵌入。法务红线往往比技术红线更早踩到。

多字重与多样式：一笔一笔算体积

每个字重都是一份独立文件、一次独立下载，体积账要按总和算，不按单个算。西文一个家族三档 WOFF 大约 61 + 62 + 64 = 187 KB；中文按上面那张表，三档页面级子集就是 3 × 428 = 1.28 MB，三档 GB2312 级子集是 3 × 1.07 = 3.2 MB——一个数字就能否掉这个设计。

那 bold 该不该下真字体？先看合成加粗：CSS 要 700 而族里只有 400 的文件时，浏览器可能把轮廓外扩（伪 bold），西文勉强能忍，中文 16 px 以下笔画直接糊成一团，32 px 的标题明显发肿。更麻烦的是各家支持并不一致：Chrome 与 Firefox 新版会对下载的 webfont 做合成，Safari 对伪斜的支持早于伪粗，老 IE 干脆不做合成，结果是不加粗——同一份 CSS 在三台机器上给出三种形态。别拿”浏览器会替我加粗”当方案，要拿它当风险。

我们的取舍表：

场景 做法 增量体积 理由
正文只用一档 只声明 font-weight:400 的页面级子集 428 KB 已经超预算，结论是正文干脆不上 webfont
首页大标题要 Bold，字号 28 px 以上、只用 62 字 单独做 62 字的 Bold 子集 +27 KB 字少时真字体便宜得发指
全站 Light / Regular / Bold 三档正文 三份 3,755 字子集 +2.1 MB 直接否掉，Light 那种细体改用图片
只有两三个按钮文字要粗 只下 Regular，接受合成或系统字体加粗 0 小字号合成还能看，测过才算

声明上有两个纪律。同一个家族的不同字重必须用同一个 font-family 名，靠 font-weight 描述符区分，写成两个族名会导致 CSS 无法做字重匹配；每个 @font-face 声明的字重要和文件里 OS/2.usWeightClass 一致，声明成 400 的文件实际是 500，浏览器会认为”还需要加权”而再做一次合成，得到双重加粗的糊字。

font-style: italic 同理，但中文不需要真斜体——汉字斜切之后不可读，我们的做法是子集里只保留正体，<em> 在中文语境改用颜色或下划线，西文引文若只有一两处，直接让它用系统字体的斜体，不为一个斜体付 60 KB。

度量匹配：性能之外的观感性能

先说一个反直觉的好消息：中文在这件事上天生占便宜。汉字的 advance width 几乎都严格等于 1 em，替换的瞬间 10 个汉字永远是 10 em 宽，换行位置一个字都不会变。抖动怎么减轻旧文讲过（写死 px 行高那一套），这里不重复，只补度量选型——中文真正会跳的是纵向行盒与视觉字面：

字体 16 px 时的默认行盒（Chrome/Win7 实测） 汉字字面占 em 观感
宋体 SimSun 约 18 px 0.83 字小、重心低、笔画细
微软雅黑 约 21 px 0.94 字撑满格、重心高
方正兰亭黑 约 22 px 0.93 与雅黑接近，但行盒再高一截
Helvetica Neue 约 18 px — 拉丁文参考基准
Arial 约 18 px — 与 Helvetica 几乎同度量
Verdana 约 21 px — x-height 与字宽都明显偏大

结论：中文标题的子集字体（黑体系，兰亭黑、雅黑一路都算）用微软雅黑兜回退是最稳的一对，宋体回退会让字瞬间”缩一圈”；西文则选 Arial 而不是 Verdana 或 Tahoma，因为 Arial 与 Helvetica 的 x-height（约 0.519 em）和 cap height（约 0.717 em）几乎相同，替换时行宽变化最小。西文才是度量匹配的主战场，量化标准是：回退字体与目标字体的 x-height 差不超过 0.03 em、小写平均字宽（OS/2 的 xAvgCharWidth）差不超过 3%，超过这个阈值，一段三行的正文就可能从三行变四行。

工具上，ttx -t OS/2 -t hhea 文件.woff 就能导出 sxHeight、sCapHeight、xAvgCharWidth、ascender/descender，FontForge 的 Font Info 里同一份数据更直观。度量对不上还能主动改：反正子集是我们自己裁的，把行盒对齐回退字体合法且有效，脚本十行就够——

体积预算与监控

优化没有预算就是玄学。我们给项目定的红线是：首屏一次加载的全部 webfont 之和不超过 100 KB，单个中文子集不超过 40 KB，单个西文 WOFF 不超过 65 KB，移动端弱网默认不注入字体。按 3G RTT 250 ms、有效下行 2 Mbps 估，100 KB 是 0.4 s 传输加一次 RTT，约 0.66 s，用户不会觉得页面坏了；400 KB 就是 1.9 s，标题那段空白期会直接反映到跳出率上。拿这把尺子回去量子集化那节的数据就清楚了：62 字的标题子集 27 KB，达标；1,379 码位的首页全量文案 428 KB，超线四倍——中文子集化省到最后，能负担的只有标题和品牌字，这是预算替我们做的决定。

与切图、iconfont 的取舍

图标不在本文范围：iconfont 只解决图标，制作链路旧文《CSS 图标字体 iconfont 的使用与制作》已经写完，不重复。真正要每次权衡的是小标题、艺术字这类装饰性文字——切图还是 webfont。

维度 切图（PNG，含 @2x） 子集 webfont
体积 一个中文艺术字标题 34—60 KB，且每处都要 62 字子集 27 KB，全站同一份可复用
清晰度 Retina 要出两倍图，放大即糊 矢量，任何倍率与字号都锐利
维护 改一个字要找设计重出图、重新切 只要新字在子集里，改 HTML 即可
SEO / 可访问性 文字变成图片，要靠 alt，不可选中 真文本，可搜索、可翻译、可选中
多语言 N 套图 每种语言重新裁一份子集，成本线性
动态文案 服务端出图可覆盖任意字 缺字即豆腐块，是硬伤
授权成本 一次买断或自制 商用中文字体按域名/PV 计费，可能很贵

判断标准很粗：同一款装饰字体全站不超过三处、文案铁定不变，切图省事；超过三处或文案每季度要改，做一份 62 字以内的子集更划算；带数字与用户输入的内容，两者都别当正文用。

小结

字体优化的杠杆全在文件本身：WOFF 当主力能省三到五成，EOT 是给老 IE 的固定税负，SVG 只留一条兜底，剩下的体积全靠子集化换出来——12.86 MB 的整包能裁成 27 KB，代价是缺字风险、一条发布链路和一份许可协议。字重要按总和算账，中文多一档 Light 就是几百 KB 起跳，能靠合成将就的只有小字号西文。度量上中文比西文幸运（汉字等宽，换行不动），要对齐的是行盒与视觉字面，实在对不上就用 fonttools 改度量。最后把 100 KB 的红线写成脚本卡进 CI，把字体 URL 的命中率打进日志，这套优化才不是一次性手艺。
