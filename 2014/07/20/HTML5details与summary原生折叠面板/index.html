HTML5 details 与 summary 原生折叠面板

本文属于《HTML 与 CSS》第 11/62 篇
上一篇系列目录下一篇

2014 年做一个折叠面板，多数同学的默认姿势还是三件套：div 装内容、click 切状态、状态类名控制显隐。但 HTML5 草案里其实有一对原生标签 details 与 summary，展开/收起这件事可以不写一行 JS 就完成，而且语义是浏览器直接给的。本文按”是什么、为什么、怎么写、坑在哪”的顺序把这对标签过一遍，重点放在 open 属性的事件口径、动画的折中做法，以及 IE 全车系不支持之下怎么降级。适合正在纠结”帮助中心那几十个 FAQ 要不要再包一层 jQuery”的同学。

这是什么：不写 JS 的展开与收起

details 表示”一段默认收起、用户可以展开的附加内容”，summary 是它的标题行，也就是那个可以点的东西。最小可运行的例子：

有一个容易忽略的点：summary 可以省略。省略时浏览器会自己补一个默认标题，但补什么完全看内核心情——有的显示一个光秃秃的三角，有的显示”详细信息”或”更多信息”之类的本地化文案，样式也不受你控制。所以实际项目请把 summary 写死，别赌默认值。

语义与可访问性

和 “div + click” 相比，details 的核心优势不是省了几行 JS，而是状态是原生语义：这个区域当前是展开还是收起，浏览器可访问性树里本来就有这个概念，不需要你亲手把 class 翻译成 ARIA 属性。上一篇文章《DOM 中 class 操作的几种封装》里我写过 div 手风琴必须手动同步 aria-expanded 与 aria-controls 的麻烦，用 details 的话那套约定整体可以扔掉——因为你压根没有自己维护的状态需要同步，漏写 ARIA 这种低级错误从结构上就不可能发生。

键盘方面，在支持这组标签的内核里，summary 本身可聚焦，回车与空格即可切换，不需要加 tabindex 和 keydown 处理。但请注意”支持的内核里”这个限定词，各实现对焦点与激活行为的细节并不完全一致，重要页面仍然要拿真键盘走一遍。

读屏软件方面不要乐观。2014 年年中的实际情况是：NVDA 配 Firefox 能把”可展开/可收起”报出来；JAWS 15 在 Chrome 里经常把 summary 读成一段普通文本，展开后新出现的内容不一定播报；iOS 7 的 VoiceOver 对这组标签基本无感。也就是说 details 目前的可访问性收益主要是”默认不犯错”，而不是”全平台体验最好”。如果你们的无障碍验收是硬指标，div 加手动 ARIA 仍是当下唯一可控的方案，details 适合用在验收范围外的内容页上。

支持矩阵与降级策略

2014 年 7 月的口径整理成表：

浏览器/环境 版本 支持情况
Chrome 6+ 支持，行为最完整，有 toggle 事件
Firefox 6+ 支持；marker 几何与 summary 的 list-item 渲染细节和 Webkit 有差异
Opera 15+ Blink 内核，同 Chrome；12.x 的 Presto 实现不完整，按不支持处理
Safari 桌面 6+ 基本可用，键盘与焦点细节需实测
IE 6-11 全系列不支持，含刚出半年的 IE11
Android WebView 4.0-4.3 部分支持，能渲染但事件不全；4.4（Chromium 33）良好
iOS Safari 各版本 部分版本不支持或有渲染无交互，必须真机验证

IE 全系不认识这两个标签，处理方式我们并不陌生：和当年 header、article 一样是未知元素，参考《HTML5 语义化标签的兼容性处理》里的思路，document.createElement('details') 注册一遍就能给它挂样式。注意关键性质：正因为 IE 不认识它，details 里的所有内容会原样平铺显示——这恰好就是我们要的降级形态。所以渐进增强的正确写法是：把内容做成”不折叠也能读”，折叠只是锦上添花；不要在语义上把正文藏进 details 再指望用户必须点开才能看懂。

为什么不直接上 polyfill？当时社区确实有几种把 details 翻译成 div 的方案，但它们的通用做法是运行时再造一层 DOM、接管事件、自己维护状态，等于为了省一个 click 处理器引入一整套私有实现，语义收益被抵消，还和你自己的 CSS 打架。一个纯内容折叠组件，犯不上。

适用与不适用的场景

适合用纯 details 的地方，共同特征是内容只读、状态只影响浏览舒适度：

  • FAQ 与帮助中心的问题列表；
  • 法律条款、规则说明的分组收纳；
  • 评论区”查看 N 条回复”式的折叠（回复内容本身放 details 里，点开展开）；
  • 商品页的参数表、配送说明这类次要信息块。

不适合的场景同样列清楚：

  • 折叠区里有表单控件。收起状态下内部 input 在部分内核里仍参与提交与校验，报错定位还落在看不见的内容上，表单页直接排除；
  • 需要跨页面记忆展开状态。open 不落存储，你得自己加 JS 写 cookie 或 localStorage，”无 JS”的优点当场破产；
  • 拿它做 SEO 的隐形衣。折叠内容仍在 DOM 里、搜索引擎仍会抓取，但 Google 对隐藏内容的权重口径在 2013 到 2014 年间反复过（移动端 tab 内容等价的表态之后，又放过桌面端折叠降权的说法，随后再改口），结论是别指望折叠内容与展开内容等价，更别把它当成分页工具，关键文案要么默认 open 要么直接铺开；
  • 复杂联动：多个面板之间、面板与外部筛选器之间互相驱动状态。open 与你的数据源之间要做双向同步，等于回到手动维护状态机，原生语义的好处所剩无几。

从 jQuery 手风琴迁移的成本评估

今年一季度我把帮助中心的 jQuery 手风琴换成了 details，按实际步骤给出成本评估顺序：

  1. 清点事件依赖。先全局搜绑在手风琴选择器上的 click 与委托处理器，确认除了”切换开合”之外没有别的逻辑挂在同一批事件上（埋点、懒加载、高度补偿都要搬家）；
  2. DOM 结构改造。div.accordion__title 换成 summary，内容 div 原样保留，同时把原来状态类名控制的显隐 CSS 全部删掉——这一步最容易删不干净，留着会和新行为打架；
  3. 事件清除与互斥。删状态机代码，只保留上文那份 toggle 门控的互斥逻辑，页面 JS 从百来行缩到三十行以内；
  4. 样式重写。marker 双内核重置、自定义图标、入场动画，工作量集中在这里，半天能收敛；
  5. IE 回退分支决策。两条路：接受 IE 里内容全部平铺（帮助中心完全可接受），或者用特性检测给 IE 保留一个最小 div 手风琴。我选了前者，因为该类页面 IE 流量当时已经不到百分之七，且平铺不影响阅读完成率。

最终决定”帮助中心用、表单页不用”，就是被上面清单里的第一条按住的：表单页的折叠区里有 input，校验插件和提交序列化都假设”隐藏的字段也要校验”，IE 与老内核的行为差异让我没法在回归测试里写死预期。帮助中心的 FAQ 则是纯只读内容、一次性浏览、低交互，恰好是 details 在 2014 年的甜点位。

小结

details 与 summary 是当下就能用的原生折叠方案：不写 JS 就有开合、键盘可达、状态语义原生，读屏支持虽不完整但”默认不犯错”已经好过大量手写的 div 面板。代价是四件事都要自己接住：toggle 事件不全、动画只能靠入场 animation 加拦截式退场、IE 全系不支持（但恰好可以当”不折叠也能读”的降级形态用）、有表单和联动需求的场景直接排除。实践建议按场景切割：帮助中心、FAQ、条款分组这类只读内容可以放心上，表单与复杂状态机维持 div 方案，迁移前先按”事件依赖、结构、样式、IE 分支”四步评估成本。
