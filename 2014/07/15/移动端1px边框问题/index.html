移动端 1px 边框问题

设计师给的分割线标注是 1px，切到 iPhone 5 真机上一看却”粗了一倍”，这是近两年移动端还原度工单里出现频率最高的一类问题。本文把 1px 边框在高分屏上变粗的原因讲透，然后逐一过一遍 2014 年手头可用的六种方案，给出对比表和选型流程，最后沉淀成可落地的 class 与 mixin 写法，并列出 scale 方案带来的一串副作用。适合正在做移动 Web 或 Hybrid 页面、被”细线调不调”折磨的前端同学。

现象与原因：1 CSS 像素到底是什么

先对齐三个视口概念。移动浏览器里有 layout viewport（布局视口）、visual viewport（可视视口）和 ideal viewport（理想视口）三层，width=device-width, initial-scale=1 的作用就是把布局视口钉在理想宽度上、初始缩放设为 1，此时 1 个 CSS 像素映射多少个物理像素，由设备像素比决定，也就是 window.devicePixelRatio：

iPhone 4/4S/5/5S 的屏幕是物理 640×1136、CSS 320×568，DPR 等于 2；当年部分 1080p 的 Android 高端机（如 GT-I9500 一类）DPR 在 2.7 到 3 之间，随着传闻中秋季要换屏的那款新 iPhone，DPR=3 的机型占比只会更高。结论很直接：你在 CSS 里写的 border: 1px，在 DPR=2 的设备上要占 2 个物理像素宽的横条，占 3 个物理像素行的位置，而设计稿上的”1px”指的是物理像素意义上的最细线，两边对不上，线就显得发虚、偏粗。《移动端性能优化特殊点》讲过 viewport 的设置套路，本文补上它没展开的”DPR 与像素映射”这一环。

先把目标定死：要的是 1 物理像素，不是 0.5 CSS px

这个区别不是咬文嚼字，它直接决定选型。如果目标是”写出 0.5px 让引擎去渲染”，那成败完全押在浏览器的取整行为上，而 2014 年各家的取整行为恰恰是最不可控的部分；如果把目标定成”最终在屏幕上只占 1 个物理像素行/列”，路就清晰了：要么让渲染层把 1 CSS px 画细（transform 压缩、渐变亚像素定位），要么让 1 CSS px 本身变细（改 viewport 缩放）。凡是不能满足”1 物理像素”这个验收口径的方案，无论写起来多顺手，都只能算缓解。

候选方案盘点

方案一：直接写 0.5px

桌面 Chrome 与 Android 全系 WebView 目前都会把它向上取整回 1px，等于白写；iOS 这边，iOS 8 beta 的 Safari 已经开始尊重小数边框，能在部分场景画出真半像素线，但 iOS 5/6/7 仍按 1px 取整。也就是说它只在”iOS 8 及以上”这一段有效，既覆盖不了存量，也覆盖不了 Android，当年只能当增强，不能当通用方案。

方案二：修改 viewport 整体缩小

把初始缩放设为 0.5，同时把布局宽度放大到 2 倍，此时 1 CSS px 恰好等于 1 物理像素，这是最早被验证可行的路子：

代价非常大。字号、间距、控件尺寸全部要按 2 倍重标，设计稿与代码的数值关系彻底失真；老 Android（尤其 2.3/4.0）在缩放 viewport 下位图插值算法粗糙，图片发虚、文字边缘毛糙；meta 必须写死像素宽，换机型就不对，用 JS 动态改写又赶不上首屏渲染；更麻烦的是与第三方嵌入组件（分享浮层、广告位）的样式互相打架，对方代码不会跟着你的缩放走。适用边界只剩”整页自主可控的独立站点”，且团队愿意接受全站尺寸翻倍的心智成本。

方案三：伪元素 + transform scale 压缩（本文主力）

思路是照常画 1px 边框，再用 scaleY(0.5) / scale(0.5) 把它压回物理 1 像素。三种典型写法：

配合要点有三处：box-sizing: border-box 保证伪元素盒子不越界；transform-origin 与边框所在边对齐，否则线会偏出半像素、颜色发灰；圆角场景半径必须乘 2（缩放对半径同样生效），这也是《CSS3 圆角阴影与边框新特性》里 border-radius 数值玩法的一个续集。兼容性：iOS 5 以上、Android 4.1 以上（Android 4.0 的 transform 支持已有但不稳）、WP8 的 IE10 桌面内核记得补 -ms- 前缀，Android 2.3 完全不支持，见后文兜底。

方案四：linear-gradient 画亚像素线，以及 box-shadow 的错觉

渐变 stop 的定位精度是亚像素的，可以在 1 CSS px 高的条带里只染下半个物理像素：

它不产生伪元素、不动布局，但只能画水平/垂直直线，圆角无能为力；background 槽位被占用，元素本身要背景时得再套一层；Android 2.3 连渐变都不支持。至于 box-shadow: 0 1px 0 #dcdcdc，不少团队把它当细线用——它的确不占布局、能随圆角走，但阴影的偏移与模糊仍按整数像素渲染，DPR=2 下实际还是 2 物理像素厚，严格说它没有解决物理像素问题，只是换了一条不重排的线。

方案五：媒体查询按 DPR 分叉

上面任何”缩”的方案都要回答 DPR=3 怎么办——scaleY(0.5) 在 3 倍屏上得到的是 1.5 个物理像素，要么灰要么粗。正解是把 scale 比例交给 DPR 媒体查询：DPR=2 用 0.5，DPR=3 用 0.33333：

Gecko 内核用 min-resolution: 2dppx 等价写法。这一条本身不产生细线，它是给方案三、四装上”按屏分档”的开关，代码量翻倍但换来确定性。

方案六：交给原生

Hybrid App 里列表分割线这类全局重复元素，最省事的是让原生画：Web 层彻底不做分割线样式，由容器统一绘制。具体通道设计见旧文《JSBridge 设计与实现》，这里只记一句：能走这条路就不要在 CSS 里硬拼。

选型决策流程

flowchart TD
  A[需要物理1像素细线] --> B{跑在App的WebView里吗}
  B -- 是 --> C{分割线可否由原生绘制}
  C -- 可 --> D[走JSBridge，Web不做线]
  C -- 不可 --> E{只有直线且无圆角}
  B -- 否 --> E
  E -- 是 --> F{元素已有背景图吗}
  F -- 无 --> G[linear-gradient细线]
  F -- 有 --> H[伪元素scaleY加DPR分档]
  E -- 否 --> I{需要四周边框或圆角}
  I -- 是 --> J[伪元素200尺寸scale乘0.5，半径乘2]
  I -- 否 --> H
  J --> K{最低要撑Android 2.3吗}
  K -- 是 --> L[无transform，退回普通1px]
  K -- 否 --> M[按DPR媒体查询输出scale档位]

判据归纳成四句话：只有一条直线且元素背景干净，渐变最轻；有圆角或四周描边，伪元素 scale；DPR=3 必须分档，否则 0.5 比例失去意义；除非全站可控且接受尺寸翻倍，否则不要动 viewport。

工程化：沉淀成 class 与 mixin

同时更新切图与联调规范两条纪律：第一，分割线不再用 1px 图片切——《CSS 精灵图与图文混排排版技巧》时代的”线也切图”在 2x 屏上会糊成灰带，图片只负责真正的图形内容；第二，UI 验收不再肉眼判断细线，一律按下一节的像素级口径走，避免”我觉得够细了”的扯皮。

副作用与坑

scale 方案好用，但 transform 是有牵连成本的，逐条记清：

  • 合成层与内存。伪元素一旦加了 transform 就有独立合成层，《CSS3 animation 与 keyframes 动画实战》里”每多一层就多占一份纹理内存、超预算反而白屏”的结论在长列表上同样成立：几百个 .list-item 每条挂一个 scale 伪元素时务必真机盯内存。
  • 可点击区域。伪元素是绝对定位盖在元素下沿的，pointer-events: none 在 iOS 5+ 可靠，个别 Android 4.0 机型不支持，稳妥做法是让伪元素只占 1~2px 高，别把交互区压在细线底下。
  • transform 干掉 fixed。这是真坑：带 transform 的祖先会让 position: fixed 后代的包含块变成该祖先，吸底按钮掉出屏幕外。细线 class 不要挂到含 fixed 元素的容器上。
  • 深色背景下线会消失。压缩后的线在合成时带灰度混合，深底上常与背景色融合到看不见，深色主题区域建议直接用 1px 实线或换高对比色。
  • Android 2.3。不支持 CSS transform，也不支持渐变，只能在 data-dpr=1 或媒体查询之外退回普通 1px，接受它粗一点。
  • 滚动容器里闪线。iOS 上开了 -webkit-overflow-scrolling: touch 的惯性滚动容器里，scale 细线在快速滚动经过合成栅格化时会出现断续闪烁（《移动端性能优化特殊点》提过该属性的滚动层副作用），对表现敏感的页面宁可给滚动区容器外的线单独提层，或局部关掉惯性滚动。

验收：确认真的只剩 1 物理像素

上线前按三个层次验：先用 Chrome 34 的 DevTools 设备模拟器，把 device scale factor 拨到 2 和 3 复现粗线与半粗线，回归媒体查询档位；再上真机截图导入 Mac，在预览或 Photoshop 里按原始像素 800% 放大，直接数线占几个像素行——占 1 行为过，2 行为不过（注意截图导出的尺寸本身是物理像素，不用担心缩放失真）；iOS 上还可用系统设置里的”缩放”辅助功能就地放大屏幕目检，配合《移动端调试与真机测试》里的 weinre 通道看 data-dpr 是否被正确写进 DOM。深色、浅色、滚动中三种状态各验一遍，才算过。

小结

1px 边框变粗的本质是 CSS 像素与物理像素的映射，目标必须定义成”物理 1 像素”才有选型依据。2014 年的现实排序是：伪元素加 transform scale 按 DPR 分档做主力，直线场景可用渐变取巧，0.5px 只作 iOS 8 的增强，box-shadow 不解决问题，改 viewport 除非全站可控否则别碰，Hybrid 里优先让原生画。把方案固化成 class 与 mixin、把”数像素行”写进验收规范，比记住某个具体数值重要得多——机型还会继续变，但”定义目标、列对比、定兜底”这套流程不会过期。
