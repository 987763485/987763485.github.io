DOM 中 dataset 与自定义属性

上一篇《HTML5 自定义数据属性 data- 的设计与读取》讲的是”为什么要用 data-*”以及三种基本读法，那些内容本文不再重复。这次往机制层再走一步：dataset 到底是个什么对象，属性名怎么映射成 JS 键，值的类型与缓存语义是什么，删除和遍历为什么不能按普通对象来写，以及它和 jQuery .data() 混用时会出什么事故。适合已经用惯 data-* 、正准备把自定义属性写进组件参数和埋点方案的同事，读完应当能自己定出一套团队规范。

dataset 只是同一条数据的另一张视图

先把两套 API 的关系钉死：它们不是两个存储。data-user-id 在 DOM 里只有一份，也就是 content attribute。getAttribute/setAttribute 直接操作它；dataset 是规范在 HTMLElement 上定义的一个只读访问器，返回 DOMStringMap 实例。这个实例是活的视图，每次取键都会现走一遍”把键名换算成属性名，再去 content attribute 里查”的流程，没有任何中间副本。

三处细节值得记：一是 dataset 本身只读，你不能 box.dataset = {} 去整体替换，只能逐键写；二是它只管 data- 这一片命名空间，box.dataset.class 读到的不是 class 而是 data-class（不存在就是 undefined）；三是缺值时一个给 null 一个给 undefined，用 === 做守卫时别把两条路的返回值混在一起判断。

还有一个老 IE 的历史包袱要提防。旧版 IE 会把标签上的属性顺带挂成 DOM 对象上的同名属性，于是 box['data-user-id'] 这种写法在 IE 里能拿到值，在 Chrome、Firefox 里却是 undefined。这属于非标准行为，和 dataset 没有半点关系，更和你往元素上赋的自定义 JS 属性混在一起（box.foo = 1 在 IE 里可能污染标签序列化）。结论是：业务代码里只允许 getAttribute/setAttribute/dataset 三条路，直接点元素属性的写法一律禁止。

命名映射规则与它的边界

dataset 的收益全在键名可读性上，而坑恰恰也在这里。把属性名转成键名的规则可以粗略记成：去掉 data- 前缀，每个”连字符 + ASCII 小写字母”的组合删掉连字符并把字母大写，其余字符原样保留。看起来简单，边界情况不少。

标签属性名 读到的键 备注
data-user-id dataset.userId 标准用法
data-id dataset.id 与 el.id 不冲突，dataset 是独立命名空间
data-x-abc dataset.xAbc 单段映射没问题，但反过来写会出问题，见下
data--x dataset['-X'] 或 dataset['X'] 连字符紧跟连字符，各家实现不一致
data-foo--bar dataset['foo-Bar']（Firefox）/ dataset.fooBar（Chrome） 双连字符是最典型的分歧点
data-ID dataset.id HTML 属性名不区分大小写，落到标签上就是 data-id
data-背景色 不可靠 非 ASCII，各家映射实现不统一

规范对属性名本身的要求只有三条：必须以 data- 开头、后面至少一个字符、名字里不能出现大写字母，且不能是 data-xml 这种形式（避让 XML 命名空间）。中文属性名并不违反”不能大写”这一条，理论上能写进文档，但 2013 年我们在 IE10、Firefox 22、Chrome 30 上交叉测过一轮，非 ASCII 名字的映射结果三种浏览器各不相同，有的直接读不到键，加上模板渲染时属性名的转义链路很长，这类写法一律当作非法处理。名字只允许小写字母、数字和连字符，连字符只用来分词。

大写字母这条限制在实践中是这样咬人的：setAttribute('data-Foo', '1') 在 HTML 文档里会被浏览器小写化，标签上最终存的是 data-foo，能读到的键只有 foo；IE 对小写化的处理又比别家更早更彻底。所以不要指望 dataset.Foo 和 dataset.foo 是两个键，它们只会是同一个属性。

数字段是第二张陷阱。data-x-abc 的键是 xAbc，但 data-x-1 的键是 x1（连字符后面不是字母，就没有大写动作，连字符却被吃掉了）。而反方向——写 dataset.x1 时——浏览器只是在字母前插连字符，x1 里没有大写字母，于是新属性名成了 data-x1。同一个键位下可能存在 data-x-1 与 data-x1 两个属性，读到哪一个取决于实现。这条不对称直接决定了后面兼容封装里的驼峰转连字符函数不可能完全可逆，因此我们团队后来的约定是：键名只用小写字母和连字符分词，段首段尾不放数字，禁止连续连字符。

值只有字符串这一种类型

dataset 的键类型是 DOMString，赋值时走的是标准的字符串转换，所以任何写入都会被拉平。

数字、布尔、JSON 三类都要自己转。数字用 parseInt(raw, 10)，注意基础进制参数不能省；布尔值不要指望字符串，要靠属性存在性来判断；JSON 得自己 parse，而且要处理好解析失败和属性缺失这两种不同情况。

布尔开关的正确写法是”存在即为真”，让属性名本身就是那个布尔变量，需要显式关闭时才写值。

in 和 hasOwnProperty 在 DOMStringMap 上是可以用的，但如果你的基线还要照顾到没有 dataset 的浏览器，就统一退到 hasAttribute，它的兼容性最好、语义也最直白。反过来说，data-async="false" 这种写法在纯存在性语义下等于”打开”，读代码的人极易搞反，开关型属性请干脆不要写值。

删除与遍历不能按普通对象来写

删除单个键用 delete el.dataset.foo，在 Chrome、Firefox、Safari、IE11 上都能正确地把 content attribute 从标签上摘掉。但在 IE9 及以下的兼容路径里根本没有可用的 dataset，早期实现里 delete 的语义也不完整（删了键、属性还挂在标签上）。所以真正跨浏览器的删除只有一条路：el.removeAttribute('data-foo')。同理，el.dataset.foo = undefined 不是删除，是写入字符串 'undefined'，这个误写在排查埋点数据时非常难查。

遍历更麻烦。DOMStringMap 是一个宿主对象（host object），不是普通的 JS 对象：它的键是靠内部枚举机制暴露出来的，Object.keys(el.dataset) 在当时的 Firefox 与 Safari 上要么抛 TypeError，要么返回一个空数组。即使能跑的浏览器上，枚举出来的键顺序也不保证和标签上的属性顺序一致。所以想把 data-* 整体转成普通对象拿来做参数合并，必须手工枚举并自己过滤原型链，或者干脆绕开 dataset，直接扫 el.attributes。

扫 attributes 这条路的好处是零依赖、IE6 起可用、还天然保留了属性的书写顺序；代价是它把驼峰转换自己做了一遍，因此必须遵守上一节那条命名约定，否则两条路径的键会对不上。另外，如果你指望”属性被改动时同步一份内部状态”，DOMStringMap 没有提供任何变更通知机制；2014 年能勉强做到这件事的只有 MutationObserver，而 IE9/IE10 并不支持它，所以不要把正确性押在监听 DOM 变更上，该重置的状态就在读取处重置。

与 jQuery data() 混用：一次真实的线上故障

这是本文最想提醒的一点。原生 dataset 每次读都是实时值，而 jQuery .data() 是”首次读取时把 data-* 扫进缓存并做类型推断，之后只认缓存”。两种语义放在同一个属性上，就是两份会分叉的状态。

维度 原生 dataset jQuery .data()
读取来源 每次读 content attribute，实时 先读缓存，未命中才读标签并建缓存
返回类型 永远是字符串 自动推断：'5'→5、'true'→true、合法 JSON→对象
写入影响标签 是 否，只写缓存
一次性读取全部 需自己枚举 无参调用直接给整个对象，含未写进标签的缓存值
长数字精度 无影响（字符串） 可能转成浮点数丢精度
缓存失效 不存在缓存 改属性后仍读到旧快照

规避方法只有纪律，没有技巧。我们的规范现在写进 CR 检查项里：第一，同一个 data-* 键，只允许一个通道负责，全项目统一。第二，如果项目依赖 jQuery 且数据是纯前端状态，那就全用 .data()，并且写入只用 .data()，绝不混 attr() 与 dataset；需要清理时显式 .removeData()。第三，如果数据要给 CSS、服务端渲染或原生代码读，那就以 dataset/getAttribute 为唯一真相源，jQuery 侧只允许 .attr('data-xxx')，禁止 .data() 读取这些键——因为 .attr() 不做缓存也不做类型转换，和原生语义一致。第四，任何”缓存快照”都不允许参与业务判断，必须每次读。这条纪律和旧文《jQuery 的 data 与 removeData》里关于缓存结构的结论是一致的：缓存是 jQuery 的内部实现，不是你的状态容器。

工程准则：什么该放，什么不该放

data-* 是”跟着节点走的少量私有参数”这个定位一旦偏离，就会变成另一种全局变量。我们的判断标准是这个值是否属于”节点的行为配置”，而不是”节点的业务数据”。

适合放的：组件的行为参数（延迟、触发方式、方向）、埋点标记（模块名、位置序号）、自动化测试选择器（data-testid）、服务端渲染时给前端的最小定位信息（行 id、权限位）。这些值生命周期和节点绑定、体积小、需要在 HTML 里可见。

不适合放的：成规模的业务数据（列表全量 JSON 请走接口或模板渲染）、任何敏感信息（DOM 里的内容对页面上所有脚本、任何装插件的用户都可见，还会被 innerHTML 复制到别处、被日志与埋点采集顺带带走）、可以推导出来的状态（能从别处算出来就别存，存了就要维护一致性）、样式钩子（这条留给 class）。

至于把整段 JSON 塞进 data-* 这种用法，代价有三层。体积上，JSON 里的引号在 HTML 属性值里必须转义，双引号变 &quot;、单引号变 &#39;、& 变 &amp;，一段稍大的配置膨胀三成以上；正确性上，只要服务端漏转一个引号，整段标签结构就崩了，而这类问题在测试环境里往往看不出来；可读性上，一个属性值里塞两行 JSON，code review 根本没法看。我们的分界线是：单个值不超过一屏、层数不超过两层才用 data-*；再大或再深，就把它挪出属性，放进一个独立的 JSON 块。

script 块里的内容是文本，浏览器不会解析，也不需要转义引号，还能被服务端模板原样输出，JSON.stringify 出来是什么就写什么。代价是它脱离了节点，得靠 id 或 data 属性建立”哪块数据属于哪个组件”的映射——这种情况下，在容器上留一个 data-source="order-init-data" 指过去，就正好是 data-* 该干的活。

属性选择器的代价与样式钩子的分工

data-* 在 CSS 里能直接选，是因为它就是 content attribute：[data-state="closed"] { display: none; } 完全合法，改一行 JS 状态样式就跟着变。这个”方便”是有账单的。属性选择器要比类选择器多做一次属性查找与值比较，在老内核（尤其 IE6/7，连 [attr] 都支持不全）上差距更明显；一条挂在高频重排容器上的 [data-*="…"] 规则，成本远高于同名 class。更要紧的是耦合：属性值一旦同时承担”数据”和”样式开关”两个职责，改动它的语义就可能意外改掉了样式，排查时要在 CSS 和 JS 之间来回跳。

我们的分工是：data-* 表达数据与行为参数，class 表达外观与状态开关，样式表只允许匹配 class，不允许匹配 data-*（结构性存在判断如 [data-tip] { cursor: help; } 例外，它不依赖值）。至于纯脚本用的选择器，继续沿用旧文《DOM 中 class 操作的几种封装》里定下的 js- 前缀约定——js-toggle 只作为结构钩子出现，样式表里禁止引用它，那是比 data-* 更省的一类”给 JS 留的门”。

小结

dataset 不是一个新存储，它是 content attribute 的实时视图：读写都直接落到标签上，值永远是字符串，键名是属性名经过连字符分词大写化之后的结果，而这套映射在双连字符、数字段、非 ASCII 和大写属性名四种情况下各家实现并不一致，所以键名只用”小写字母 + 连字符分词”这一条约定就能绕开所有坑。删除统一走 removeAttribute，遍历统一走 attributes 扫描，不要指望 Object.keys，也不要给 DOMStringMap 挂缓存。与 jQuery .data() 的混用是本文最贵的教训：.data() 的缓存快照和类型推断和原生语义天然冲突，同一个键必须只归一个通道管。至于工程定位，data-* 适合放节点的行为参数、埋点标记和测试钩子，不适合放大体积业务数据、敏感信息和可推导状态；数据一旦超过一屏就搬进独立的 script[type="application/json"]，样式钩子留给 class 与 js- 前缀，别拿 data-* 兼职。
