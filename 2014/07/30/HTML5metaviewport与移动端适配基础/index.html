HTML5 meta viewport 与移动端适配基础

本文属于《HTML 与 CSS》第 9/62 篇
上一篇系列目录下一篇

今年上半年经手的三个移动专题页里，有两个的”排版崩了”工单最后都落在同一行 meta 标签上，一个排查了两天、一个只用二十分钟，差别在于后者先把三个视口的模型建立起来了。本文讲清布局视口、视觉视口、理想视口，逐个拆 meta viewport 的参数语义，再复盘五个真踩过的坑：width=device-width 与 initial-scale=1 为什么不等价、横竖屏切换后缩放何时重算、禁缩放换来什么又赔上什么、像素密度私有参数怎么从救命稻草变成技术债、动态写入 viewport 造成的首屏闪烁。适合被”页面在某个机型上就是不对”折磨的前端同学，读完应该能自己判断问题出在视口层还是样式层。

复盘的起点：视口不是 CSS 的事

第一个案例是个签到活动页：iPhone 上正常，同事那台 Galaxy S 一代（Android 2.3）一打开就整体偏左、右边露出一条底色，双指捏合一次立刻恢复。我们按布局问题排查了两天，翻媒体查询、查浮动清除、怀疑固定宽度，全是白费劲。后来加了个每 100 ms 打印一次宽度的诊断块，才发现捏合之前布局视口读到的是 980，而 CSS 按 320 写的——问题不在样式层，在那台内核没按我们期待的方式处理 initial-scale。

第二个案例是横屏后右侧留白，iOS 与 Android 都复现，二十分钟就定位：要问的无非是布局视口宽度、初始缩放、方向变化后有没有重算。先确认这三个读数，再动 CSS。

三个视口：布局、视觉与理想

移动浏览器里同时存在三层视口，桌面端只有一个，从桌面转过来的人很容易把它们混成一个。布局视口（layout viewport）是 CSS 布局的包含块，即根元素算百分比、排浮动时参照的那个盒子。不写 viewport 元标签时，移动浏览器为了像桌面一样展示未适配的站点，会先给它 980 或 1024 这样的默认宽度再整体缩小塞进屏幕——这就是老页面在手机上整页可见、字却小如蚊的原因。

视觉视口（visual viewport）是用户此刻真正看到的那块区域，随缩放和平移变化：捏合放大后它在 CSS 像素意义上变小。理想视口（ideal viewport）不是第三种盒子，而是厂商为某款设备定下的一档”这块屏在 1 倍缩放下的最佳布局宽度”，width=device-width 取的就是它。三者关系可以这样串起来：

flowchart TD
    A[物理屏幕 例如 640 x 1136] --> B[理想视口 厂商定 例如 320 CSS 像素]
    B --> C{是否声明 meta viewport}
    C -->|未声明| D[布局视口 980 CSS 像素]
    C -->|width=device-width| E[布局视口 320 CSS 像素]
    D --> F[视觉视口 整体缩小后呈现 980 宽内容]
    E --> G[视觉视口 等于布局视口]
    G --> H[缩放比例 scale 决定每个 CSS 像素占多少物理像素]

换算上有两条实用关系：缩放比例大致等于布局视口宽度除以视觉视口宽度，放大之后 window.innerWidth 变小而布局视口宽度不变；1 个 CSS 像素占多少物理像素，由设备像素比（devicePixelRatio，下称 dpr）与缩放共同决定，width=device-width, initial-scale=1 只把布局钉在理想宽度上，并不保证 1 CSS 像素等于 1 物理像素。

下面是手上几台机器 2014 年年中的自报值，各家 ROM 有出入，但量级是真实的：

设备与内核 理想视口（竖屏） dpr 不写 meta 时的布局视口
iPhone 4S，iOS 5.1 Safari 320 2 980
iPhone 5，iOS 7 Safari 320（横屏 568） 2 980
iPad 2，iOS 6 Safari 768 1 980
Retina iPad，iOS 6 Safari 768 2 980
Nexus 7 一代，Android 4.2 601 1.33 800 左右
Galaxy S 一代，Android 2.3 320 1 320
某国产 480 x 800 机，Android 4.0 320 1.5 1024

注意 dpr 是小数的 Android 机型非常多，于是有了”同一套 CSS 在不同机器上线条粗细、图片清晰度不一致”的老问题；像素层面旧文《移动端 1px 边框问题》已经讲透，本文不重复。

meta viewport 参数逐项拆解

先看标准方向那六个键。viewport 元标签在 HTML 规范里长期是”各家实现加事实标准”，W3C 的 CSS Viewport Module 当时还是工作草案，所以语义与实测行为要分开记。

参数 语义 实测要点
width 直接给布局视口一个 CSS 像素宽度 数字写死会被机型绑死；device-width 取理想视口
height 直接给布局视口高度 极少单独用，和固定 width 搭配时最容易翻车
initial-scale 首次布局的缩放比例，1 表示不缩放 只改视觉视口，不改布局视口宽度
minimum-scale 允许捏合到的最小缩放 与 initial-scale 冲突时，各家钳制策略不同
maximum-scale 允许捏合到的最大缩放 设 1 等于变相禁掉放大，见坑三
user-scalable 是否允许用户手动缩放，取 1/0 或 yes/no 部分内核只认 1/0，写 yes 会被忽略

分隔符这件小事也有历史包袱。我们模板里曾有同事用分号分隔属性对，在某些老 Android 浏览器上解析器只认第一个键值对，后面整段被丢掉，页面于是按 980 布局。各家解析实现的差异，PPK 的 quirksmode 视口系列写得更细。保守做法：逗号分隔、不写空格、一行写完、全页只出现一个 viewport 标签。

下面三个私有键只为读老代码，都不该进新模板。target-densitydpi 是 Android WebKit 的私货，取值可以是 low-dpi、medium-dpi、high-dpi、device-dpi 或一个数字，用来把 CSS 像素密度对齐到某个 dpi 基准上，废弃过程见坑四。HandheldFriendly 主要出现在 BlackBerry 的老浏览器上，写 content="True" 才按设备宽度布局，OS 6 之后不再需要，在 iOS 与 Android 上毫无效果。format-detection 是 iOS Safari 的私有开关，content="telephone=no" 阻止 Safari 把文本里的数字自动识别成号码并生成 tel: 链接：我们一个订单号列表页里，纯数字串被识别成号码后套上链接样式，长按还弹出拨号确认，用户以为自己误触了打电话。

坑一：width=device-width 不等于 initial-scale=1

这两个键管的是不同的盒子：width 管布局视口，initial-scale 管视觉缩放。之所以常被当成一回事，是因为 iOS Safari 上只写 initial-scale=1 时浏览器会把布局视口一并收到理想宽度；Android 2.3 的原生浏览器不会，它的布局视口仍停在默认的 980，只按你给的算了一遍显示比例。于是出现那个经典现象：页面整体缩小呈现，用户捏一下手指触发布局重算，内容突然就”正常”了。反过来只写 width=device-width 不写 initial-scale 也不安全：iOS 会把初始缩放补成 1，观感正确；Android 2.3 却把 980 时代的”适配缩放比”保留下来，320 宽的内容被放大到两倍多显示，首屏只看到左上角一小块，同样要靠一次手动缩放才恢复。

结论很朴素：两个都写，一个都不能省。团队模板里固定 width=device-width, initial-scale=1.0，这也是《移动端性能优化特殊点》那行标准写法的由来。

dpr 带来的第二层误解更常见：有人以为 width=device-width 配上 initial-scale=1 之后，1 CSS 像素就是 1 物理像素。iPhone 5 的布局视口是 320、屏幕物理宽度是 640，1 CSS 像素实际吃掉 2 个物理像素。这套写法解决的是”不要横向拖动、不要整体缩小”，跟像素密度无关，密度问题只能走倍图与 dpr 媒体查询那一条路。同一套 320 的布局，在 dpr=1 的 480 x 800 机器上物理宽度就是 320，在 dpr=2 的 iPhone 5 上是 640：设计稿标的”44 高”点按区两边 CSS 意义都是 44，落到屏幕上的实际面积差一倍——这正是同一份 CSS 在 iOS 上显得精致、在某些低端 Android 上显得巨大的原因。

坑二：横竖屏切换后，缩放与布局视口重算的时机

旋转是 viewport 相关 bug 最密集的触发点：它同时要求浏览器重算布局视口宽度、重新套用缩放，还要处理地址栏高度变化。麻烦在于这些动作不是一次完成的，而且事件顺序各家不同。

iOS 上 orientationchange 先于 resize 触发，但在 orientationchange 回调里读 document.documentElement.clientWidth，拿到的经常还是旧方向的值，某些版本里 window.innerWidth 要再晚一两帧才刷新。Android 更散：4.0 到 4.3 的原生浏览器我们遇到过只发 resize 不发 orientationchange 的情况，2.3 上两个事件都常常迟到几百毫秒，个别 ROM 还会在一次旋转里连发两次 orientationchange。所以任何”旋转后重新算布局”的逻辑，只绑一个事件都靠不住。

还有个读数陷阱：screen.width 与 screen.height 在 iOS 上会随方向交换，在不少 Android 内核上始终保持出厂方向，用前者比大小来判横竖屏在 iOS 上正确、在 Android 上可能永远为假；方向判断要么用 window.orientation，要么比较两次读到的布局视口宽度。

我们的兜底策略分三层：优先用 window.matchMedia('(orientation: portrait)') 注册监听，这个 API 在 iOS 5 以上、Android 4.0 以上都可用，回调时机比 orientationchange 稳；不支持 matchMedia 的老内核退回 orientationchange 加 resize 双监听；无论走哪条，都再用 setTimeout 延后 200 ms 复核一次布局宽度，只有宽度真变了才修正，避免重复触发带来抖动。

修正动作本身也有讲究：当布局视口还是旧方向的值、或者缩放被钳在 maximum-scale 上时，重写一次 viewport 的 content 最有效——先写占位串紧接着改回目标串，强制内核重算，直接赋同一个字符串是无效的，内容没变化内核不会重新解析。另外横屏后字号莫名变大是另一条链路，Safari 的文本尺寸调整会在它认为”页面没按横屏重设布局”时放大若干文本节点，对策是给根元素补 -webkit-text-size-adjust: 100%，而不是改各处字号。

坑三：maximum-scale 与 user-scalable=no 的得与失

maximum-scale=1.0, user-scalable=no 这一行在 2013 年的模板里几乎是默认存在的，动机有两个：一是把双指缩放关掉，避免用户误捏之后布局错乱；二是让浏览器跳过双击缩放的判定。第二个动机我们已经在《移动端点击 300ms 延迟与解决方案》里量过数据了，收益只在部分环境成立，本文不重复论证，只谈剩下的那半。

双指缩放确实会带来真实故障：页面被捏到 1.5 倍后，position: fixed 的元素在旧版 iOS 上会跟着漂出屏幕外；自绘滚动容器（我们用的是 iScroll 那套，见《iScroll 实现移动端滚动》）的手势层与浏览器原生缩放互相打架，一次捏合之后所有触点坐标偏移，滚动开始”抓不住”。所以交互密集型的应用型页面禁缩放是有工程理由的。

代价同样清楚。一是可访问性：双击缩放与捏合放大是低视力用户读小字的主要手段，WCAG 2.0 里也早有文本可放大的条款，关掉它等于把一部分用户挡在页面外；我们的做法是把开关做成页面级配置，只有应用型页面（签到、抽奖、纯自绘交互）允许开，内容型页面一律不开。二是投诉成本：用户”看不清就放大”的习惯失效之后，会转成”这页面卡住了”的工单。

实现上还有个细节：user-scalable 的取值各家不一，iOS 认 no，部分老 Android 只认 0，但只要同时写了 maximum-scale=1.0，放大上限已被钳死，这个差异也就被掩盖了——这两个键要么一起用，要么都别用。

坑五：动态写入 viewport 与首屏闪烁

有一类老代码会在 head 顶部塞一段内联脚本，用 UA 判断机型，然后 document.write 出不同的 viewport。这在没有稳定标准的年代是有道理的：部分 Android 1.x 与早期定制浏览器对静态 meta 的解析时机不可靠，写在 HTML 里等于没写。

但它带来一个非常难看的问题：先渲染后缩放。浏览器的解析与样式计算不会等你的脚本，如果 viewport 的实际生效晚于首帧布局，用户会看到内容先按一个宽度铺开、紧接着整体跳变一次，Android 2.3 上这个跳变还常常停在错误状态，需要用户手动捏一下才恢复。我们做首屏时间打点时，这类页面的”首次可见”到”最终稳定”之间有 200 到 500 ms 的抖动，在弱网下更明显。

取舍是清楚的：今天（2014 年年中）的目标机型里静态 viewport 已经完全够用，优先级应当是模板里静态写死在第一行 meta，其次是极端兼容场景下用内联脚本在样式表之前 document.write，最末是在 DOMContentLoaded 之后动态插入。最后一种之所以危险，不只因为它触发重排，还因为不少内核里”运行时修改 viewport 的初始缩放”根本不生效，必须等下一次用户手势才有机会重算，等于把不确定性甩给交互。真要动态改（比如旋转修正），就遵守坑二那条：先写占位值再写目标值，只在读到的布局宽度和预期不符时才改。

小结

viewport 的本质是跟浏览器签一份关于三个宽度的契约：布局视口多宽、初始缩放多少、允许不允许用户改。width=device-width, initial-scale=1.0 只覆盖前两项，既不管像素密度，也不管旋转后的重算时机。团队实践四条：模板里统一一行静态 viewport，逗号分隔、不写空格、只出现一次，禁止各业务自行加键；user-scalable=no 与 maximum-scale 只在交互密集型的应用型页面开，且做成页面级开关，内容型页面一律保留缩放；旋转修正必须双事件监听加一次 setTimeout 复核，改 content 时用占位值强制重算，不要用 screen.width 判断方向；私有键不进公共模板，像素密度走 dpr 与倍图。最后仍要强调真机：模拟器和远程调试能看到读数，看不到跳变。
