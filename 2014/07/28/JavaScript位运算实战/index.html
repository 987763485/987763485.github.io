JavaScript 位运算实战

本文属于《算法与数据结构》第 4/13 篇
上一篇系列目录下一篇

位运算是 JavaScript 里最容易被当作”底层炫技”的部分，多数时候确实用不上；但在标志位管理、像素热循环和哈希索引这几类场景，它能带来语义和性能的双重收益。本文从 32 位模型讲起，把截断小数、位掩码、颜色打包、取模与环形索引逐一过一遍，并给出一份诚实的性能结论：哪里值得用位运算，哪里属于过早优化。适合被 canvas 逐像素处理、游戏实体状态或协议解析困扰的前端工程师。

先把模型立住：位运算走的是 32 位带符号整数

JS 里所有 number 都是 IEEE 754 双精度浮点数，而每一个位运算符都会先把两个操作数按规范 9.5 节的 ToInt32 语义转成 32 位带符号整数：先对 2 的 32 次方取模，再把结果映射到 [-2147483648, 2147483647]。这带来两个直接后果。第一，位运算的结果只可能落在这 32 位里，超出的部分无声回绕：

第二，小数在进入运算符之前就被截掉，这是后文所有”用位运算截断”用法的根源。

右移有两种：>> 是算术右移，高位补符号位，负数永远还是负数；>>> 是逻辑右移，高位补零，结果按无符号数理解，所以 x >>> 0 就是 JS 里表达 uint32 的标准写法：

~ 是按位取反，在补码表示下它恒等于 -x - 1，记住这个恒等式就不用掰手指了：~0 是 -1，~5 是 -6，~ -1 是 0。

优先级是位运算最大的坑。&、|、^ 的优先级全部低于 === 和各种比较，于是有了那个经典 bug：

按错误写法推导一遍：flags 只要含 READ（即任何奇数组合），flags & 1 得 1，条件恒为真，明明没有 WRITE 也判通过；反过来 flags 等于 2（只有 WRITE）时结果为 0，有权限却判没有。它和你真正想查的位完全无关。亲手推一次就终身难忘：位运算与比较混写，一律给位运算部分加括号，code review 里不设例外。

截断小数：~~x、x|0 与 Math.floor

对正数三者一致，对负数立刻分道扬镳。位截断是”向零取整”，Math.floor 是”向负无穷取整”：

最常见的翻车现场：速度向量、DOM 偏移、音频波形都可能是负数，本该 Math.floor(x) 的语义写成 x | 0，在 -1 到 0 之间就差了 1。用位截断前先确认值域非负，或者明确自己要的就是向零取整。ECMAScript 6 草案里已经给截断取了 Math.trunc 的名字，规范里还能看到 Math.clz32、Math.imul，但截至 2014 年 7 月各家引擎都尚未落地，眼下只有这两种写法可选。

性能实测。测试环境为 Chrome 35 与 IE 11、2012 年笔记本、未压缩脚本，同一小数累加 1000 万次，只取粗略量级：

截断 1000 万次 Chrome 35 IE 11
Math.floor(x) 约 40 ms 约 310 ms
Math.round(x) 约 45 ms 约 330 ms
~~x（x 或 0 同此） 约 30 ms 约 220 ms
parseInt(x, 10) 约 150 ms 约 800 ms

两个结论。其一，位截断确实快，但 Chrome 的 V8 早已把 Math.floor 内联，差距不到 2 倍，不在热点上就别为它牺牲可读性；IE 上差距放大到 1.5 倍左右，倒是位运算略占便宜。其二，parseInt 慢是因为它先把数字转成字符串再逐字符解析，它不是截断工具，并且永远别忘写基数 10：不写基数时 parseInt('0x10') 按十六进制得 16，而老 IE（8 及以下）会把 parseInt('08') 按八进制得 0，这个行为到 ES5 才被标准钉死为十进制。

所以我的取舍是：业务逻辑用 Math.floor 和 Math.round，把意图写明白；只有每帧几千次以上的热循环、且值域确认落在 32 位内非负时，才换位截断。

标志位用一个整数管理：本文收益最大的场景

用对象管理读写执行和各类开关是直觉做法，{ read: true, write: false, exec: true } 看着清楚，代价是每个实例都背着对象头和几个字符串键属性，内存、遍历（for-in 的枚举开销）、拷贝和传参都是整包操作。把标志打包进一个 32 位整数后，同样的状态就是一个数字，几十个字节的实体降到 4 字节；对游戏里”十万个实体乘以一组开关”或按位下发的权限系统，这个差距是实打实的。

性能结论与编码规范

值得用位运算的场景有共同特征：数据本身就是一个位域。标志位与权限、颜色与像素热循环、2 的幂哈希桶与环形索引、定长协议打包，这几处位运算是把”语义”直接写进运算，顺带快一点。不值得的场景：业务分支、字符串处理、每帧只算一次的表达式——全是过早优化，先上 console.time 或浏览器自带 profiler 找到热点再说，本文所有表格都只是量级参考，不是承诺。

review 检查点：&、|、^ 与比较混写处有没有括号；输入值域会不会越过 32 位带符号范围、该用 >>> 0 的地方用了没有；负数经过 %、>> 的行为与预期核对过没有；每个标志位是否进了常量表并且禁止魔数直用。

小结

JS 位运算的一切行为都来自同一个模型：double 先转 32 位带符号整数再运算，回绕、负数和符号位的怪事全部由它解释。优先级低于比较是第一大坑，位运算与比较混写必须加括号。~~x 与 Math.floor 在负数上语义不同，实测提速只有约两倍的粗略量级，热点再用，业务逻辑请留给可读的版本。位运算真正稳定的收益在标志位管理、像素与颜色热循环、2 的幂索引这三处；用常量表和封装小函数把它收进规范，就能既拿到性能，也不把可维护性输掉。
