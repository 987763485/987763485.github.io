JavaScript 错误处理 try/catch/finally

错误处理是每个前端项目都绕不开的一环，但很多团队的代码里 try/catch 只用来”兜底不让它报错”，catch 块常年是空的。这篇文章不打算把语法重抄一遍，而是站在工程实践的角度，先厘清 try catch finally 在语言层的几条容易踩坑的规则，再讲清楚哪些错误根本 catch 不到，最后把重心放在一套可在 2014 年落地的线上错误上报系统上：从去重指纹、采样限频到用 img 发送，给出能直接抄走改的 ES5 代码。适合写过几年 JS、正在被”线上报错看不见、复现不了”折磨的同学。

try / catch / finally 的语义与两个坑

先约定语义。try 块里的代码一旦抛出异常，剩余部分立即停止，控制流跳到匹配的 catch；如果没有 catch，只要有 finally 也会先执行 finally 再把异常继续往外抛。catch 和 finally 至少要有一个，光有 try 不写后两者是语法错误。

第一个坑是 finally 的”一定执行”以及它对返回值的覆盖。finally 在 try 正常返回、catch 处理完、甚至在 try 里 return 之后都会执行，唯一不执行的情况是进程被强制退出（浏览器里几乎碰不到，Node 里 process.exit 才会）。危险在于：如果 finally 里自己写了 return 或抛出新异常，它会吞掉前面 try/catch 准备返回的值或抛出的异常。

结论很简单：不要在 finally 里 return，也不要在 finally 里做可能抛异常的复杂逻辑，它只该用来做确定性的收尾（关文件、清定时器、复位标志位）。

第二个坑是 catch 的参数不是块级作用域。2014 年没有 let，catch (e) 里的 e 只在 catch 块内有效，出了块就没了；但很多新手会在 catch 块里再 var 一个同名变量，或者以为 catch 里 var 声明的变量只在块内——事实是 var 提升到函数作用域，块外的函数体内照样能读到。更麻烦的是老 IE：它把 catch 参数按函数作用域处理，catch (e) 结束后 e 仍然残留，甚至会把同名变量的值改掉。

对策是别给 catch 参数起和项目里全局变量重名的标识符，统一用一个短且不会撞车的名字（例如 catch (ex)），并且永远不要在 catch 块里 var 一个和参数同名的变量。

throw 抛出的是任意值，团队要收敛成 Error

JavaScript 的 throw 后面可以跟任意值：字符串、数字、对象、undefined 都行，catch 拿到的就是你抛的那个东西。这就带来一个问题——throw '出错了' 抛一个字符串，调用方根本分不清这是业务错误还是另一个字符串异常，也没法拿到出错位置。所以团队规范里最好写死一条：只 throw Error 的实例（或其子类），禁止裸字符串。

这些错误 catch 不到

try/catch 只能捕获同步执行流里、当前调用栈内的运行时异常，下面这几类它无能为力，是新手最容易误以为”我加了 try 就安全了”的地方。

语法错误发生在解析期。脚本在运行前会先被解析，解析不通过直接报错、整段代码一行都不执行，所以任何写在同一份脚本里的 try 都来不及包裹它——try 本身也还没跑起来。要兜住语法错误只能靠 <script> 的 onerror，而不是 try。

异步回调里抛出的异常，不在同一个调用栈上。setTimeout、事件监听、XHR 的 onload 回调里抛的错，try 是包不住的，因为 try 早在回调触发前就执行完了。老 IE 尤其明显：DOM 事件处理函数里抛出的异常根本不会走到你外层写的 try，直接冒泡到全局。

资源加载失败也不走 try：<img>、<script>、<link> 加载失败触发的是元素的 onerror 事件，需要单独监听，例如给图片 onerror 换成占位图。

最后是最坑的跨域脚本。当页面引用了不同域的 <script>，那段脚本里抛出的错误，window.onerror 只能收到一句干巴巴的 Script error.，没有 URL、没有行号、没有堆栈——这是浏览器的安全限制，防止跨域脚本的内部信息泄露。两种解法：一是让脚本服务端加上 CORS 响应头（Access-Control-Allow-Origin），并给 <script> 标签加 crossorigin="anonymous" 属性，2014 年主流新版浏览器逐步支持，但老 IE 无效，不能作为唯一依赖；二是干脆把报错脚本和页面部署到同域，从根上避免跨域。实践中当时更常见、也更稳妥的是后者。

用 window.onerror 搭一套线上错误上报

这是本文的主线。window.onerror 的回调签名是 (message, url, line, col, err)，其中 col（列号）和 err（错误对象）都是较新版本才补充的参数，老浏览器只能拿到前三项，写代码时要判空。回调返回 true 表示”我已经处理了，别再走默认行为”，可以抑制浏览器在控制台打印和弹脚本错误框。

老 IE 上抓不住堆栈怎么办

在缺 Error.stack 的老 IE 上，光靠 window.onerror 报回来的信息太稀。两个辅助手段值得做。

一是给事件处理入口统一包一层 wrap。既然异步错误进不了外层 try，那就在绑定的时候主动包：用 try/catch 包住业务函数，捕获到异常后补一个”业务语义位置”再上报，正好替代缺失的堆栈。

二是当时已有的调试辅助库，比如 traceKit、trace.js 这类，原理都是给全局函数套 wrapper、重写 addEventListener 之类来收集调用点，本地排查挺有用；但它们体积大、有兼容坑，线上更靠谱的还是自研上面这种轻量上报，别把宝押在第三方库上。

还有一点老生常谈：调用 console.error 前一定判空。IE 的控制台在未打开开发者工具时 console 是 undefined，直接 console.error(...) 会在 IE 上抛新异常，反而制造错误。旧文《window 对象常用 API 梳理》里提过类似的宿主差异，这里同理，包一层 if (window.console && console.error) 再调用。

工程规范：一份可执行的清单

把前面收敛成团队能落地的规矩：

  • 不要写空的 catch。最差也要 report(ex) 记一笔，把异常彻底吞掉比不 catch 更可怕。
  • 不要在最外层捕获用户可感知的错误。业务层该 catch 的让业务 catch 并给出提示，全局 onerror 只兜”没预料到”的错，两者职责分开。
  • 错误分层。网络层只 catch 请求失败与超时并归一化，数据层 catch 字段缺失与解析异常，UI 层 catch 渲染与交互异常；每层只处理自己语义范围内的错，别跨层抢。
  • 错误即状态，UI 上要有可见分支。接口失败不能只是控制台红字，要在界面上有对应态：
  • 灰度期间靠上报发现升级引入的新错误。同一套指纹分别统计旧版本和新版本的错误率，只看新增的、旧版本没有的指纹，避免把历史噪声当成回归。
  • 过滤误报。浏览器插件、注入的广告脚本抛的错，它的 url 往往是你页面域之外的地址，统计时按 url 域名过滤掉非本站来源；<noscript> 环境、被拦截的第三方脚本也一并排除，否则上报里一半是别人的锅。

性能与副作用要克制

早年 V8（大致 2012 年前后）对包含 try 块的函数优化很保守，会让函数难以内联，于是有人得出”能不用 try 就不用”的结论。这几年引擎进步很大，绝大多数场景已经不用为 try 本身的开销担心。真正要守住的是一条工程直觉：不要在热循环里靠 try/catch 做流程控制。抛异常要构造对象、要展开调用栈，比正常返回慢得多，把它当 if 用既难看又费性能。

更要紧的副作用是”误吞”：try 里塞一大段代码，你以为在防 A 出错，结果 B、C 的异常也被同一个 catch 静默接走，问题被埋得更深。原则是 try 块只包住真正可能抛异常的那几行，catch 里精确判断是不是预期的错，不是就重新 throw。

小结

try catch finally 语义不难，坑在细节：finally 里别 return，catch 参数在老 IE 里会泄漏，throw 要收敛成 Error 实例并带上下文，err.stack 不能假定要存在。要清醒认识到语法错误、异步回调、资源加载失败和跨域脚本的 Script error. 都 catch 不到，只能靠 window.onerror 和 onerror 事件兜底。线上问题看不见，就自己搭一套轻量上报：指纹去重、会话限频、img 发 gif、缺堆栈时用调用点标记补位，再用 wrap 给老 IE 补上业务语义位置。最后落到规矩上——不写空 catch、错误分层、UI 有失败态、灰度对比错误率并过滤插件噪声。把异常当状态、把上报当眼睛，前端才真正具备可观测性。
