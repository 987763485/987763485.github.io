DOM 动画与 requestAnimationFrame

本文要解决的问题是：当动画已经确定要交给 JS 来驱动时，怎么把它做对、做稳。我们不复述渲染管线，那在《CSS3 animation 与 keyframes 动画实战》里推过一遍；也不讨论什么场景该选 CSS 什么场景该选 JS，那是《CSS 动画与 JS 动画的性能取舍》的结论。本文只围绕 requestAnimationFrame 展开：它到底承诺了什么，polyfill 应该怎么写，一个页面里的动画循环应该组织成什么结构，时间轴和缓动怎么算才不跑偏。适合已经用 setTimeout 写过动画、但一直没搞明白”为什么偶尔会卡一下”的同学，读完你能拿到一套可直接落地的 ES5 动画循环代码和度量方法。

setTimeout 做动画的两个根本问题

第一个问题是计时精度与回调排队。HTML5 规范规定 setTimeout 的延迟只是”最短时间”，回调要等当前任务队列清空才有机会执行；更麻烦的是嵌套限制——同一来源的嵌套超过 5 层之后，最小延迟被强制抬到 4ms。做动画时我们通常这样写：

这个递归跑几层之后就会被 4ms 钳制规则罩住，它不是 16ms 的敌人，真正的问题在别处：回调的实际触发时间是”上一次回调结束后的 16ms 加主线程当前的忙碌程度”。渲染一帧、执行一段事件处理、跑一次 GC，都会把回调往后压，而 setTimeout 不会补偿，压多少就晚多少。

第二个问题是与重绘时机不对齐。浏览器的绘制由显示器的垂直同步信号（vsync）驱动，桌面屏绝大多数是 60Hz，也就是每 16.7ms 给出一次合成机会。setTimeout 的回调时刻和 vsync 之间没有任何约定，回调落在本帧窗口内就赶得上，落不进就得等下一帧。我们在桌面 Chrome 35 上用一个每 16ms 递归的 setTimeout 跑了五分钟，统计相邻回调间隔，分布如下：

回调间隔 占比 对应现象
15-17ms 约 45% 赶上本帧 vsync，正常
31-34ms 约 30% 错过一次合成，肉眼可见一顿
47-50ms 约 15% 连丢两帧
其余长尾 约 10% GC、事件风暴、样式重算挤占

将近一半的帧不是准时到的。这种抖动在位移速度快的动画上尤其明显，因为人眼对”匀速运动突然跳一下”极其敏感。用 mermaid 把时序关系画清楚：

flowchart TD
    A[setTimeout 到点] --> B[回调在帧内任意时刻执行]
    B --> C[写入样式]
    C --> D{是否赶在本次 vsync 前}
    D -->|赶上了| E[本帧合成，动作连续]
    D -->|没赶上| F[等下一次 vsync，掉帧]

requestAnimationFrame（下文简称 rAF）不是把 16 换成一个更准的数，而是干脆取消了”我们自己计时”这件事。

requestAnimationFrame 的语义与时间戳兼容

rAF 来自 W3C 的 Timing control for script-based animations 规范，语义可以拆成四条：

  1. 回调由浏览器调度，固定安排在同一次重绘之前，且同一帧内多次注册只合并执行一次。这意味着浏览器拿到一个”批量写样式”的窗口，写完紧接着就是它的布局与绘制阶段。
  2. 回调里只应该改样式。因为回调执行点就在布局之前，此时读几何属性触发的同步布局代价最高，这一点第六节单独讲。
  3. 标签页不可见时整个循环暂停。这既是省电——后台页面没有观众，不该消耗 CPU 和 GPU；也是正确行为——切回页面时动画从当前进度继续，而不是在后台空跑完之后发现早已结束。相比之下 setTimeout 在后台照常排队，只是被节流到 1s 一次，时间照烧。
  4. 回调参数是本次动画帧的时间戳，单位毫秒。

第四条是 2014 年的深坑，因为各家把玩的时间基准不一样。IE10 和较新的 Chrome（24 以后）传入的是高精度时间（performance.now 系），Firefox 传入的是 mozAnimationStartTime 体系的高精度值，而早期 Chrome 干脆传 undefined，Opera 12 之前的版本同样如此。所以回调开头必须做一次归一：

逐段说为什么这样写。前缀数组的顺序无所谓，但循环条件里带 !window.requestAnimationFrame 是关键：一旦命中就立即停止，避免后面的前缀赋值把已找到的实现覆盖成 undefined。取消 API 那一行是历史包袱最重的地方：早期 WebKit 遵循的是 setTimeout/clearTimeout 的命名对称，把取消函数叫 webkitCancelRequestAnimationFrame；Chrome 26 之后才改名为 webkitCancelAnimationFrame。也就是说同一台机器的不同浏览器版本可能只认识其中一个名字，所以两个都要探测，用 || 兜住。IE 是 ms 前缀、旧 Firefox 是 moz 前缀，各自的取消函数同样存在两套命名习惯的过渡期，这段代码对它们是同一个写法通吃的。

降级实现里最容易被误读的是 timeToCall 和 lastTime 这两行。它并不是简单地 setTimeout 16ms，而是维护了一个全局帧节拍：下一次回调预计发生在 lastTime + 16 时刻，本轮只需要等待两者的差值，用 Math.max(0, ...) 防止已经超时（主线程忙过 16ms）时传出负延迟。这样即使某一帧迟到了，后续帧会主动追赶回来，长时间看平均帧率仍然是约 16ms 一次。回调收到的参数是”预计触发时刻” currTime + timeToCall，让下游的时间轴代码在降级环境里也能拿到一个数字而不是 undefined。它伪造不了的对齐只有一处：无法与 vsync 同相，所以降级版本依然会有本文开头那种抖动分布——这是 polyfill 的天花板，用真机的 Timeline 一看便知。

动画循环的工程结构：全站只有一个 Ticker

rAF 是自我续订的：回调里再调一次 rAF 才进入下一帧。如果页面上 20 个组件各自维护一条”回调里再 rAF”的循环，就有 20 个独立回调排队等合成。这带来三个直接代价：每个组件的进度判断、边界检查、样式写入都要各跑一遍，函数调用与闭包分配的开销按组件数线性放大；各循环注册的时机不同，浏览器无法在一个批次里统一处理，写入被拆散；最要命的是预算问题——60Hz 下每帧总共只有约 16.7ms，2014 年的移动设备（Galaxy S II、iPhone 4S 这一档）JS 执行速度大约只有桌面机型的四分之一到三分之一，二十个散兵游勇的循环光回调调度本身就可能吃掉一半预算，更别提 GC 还会随机插入。

为什么基于帧计数的写法（”每帧 +4px”）不可靠？因为帧间隔从来不是常数。掉一帧，帧计数版本少走一步，动画整体变慢、结束时间漂移；如果哪天显示器不是 60Hz，同样的代码在 75Hz 面板上会提前结束。基于时间的版本里 p 只跟真实流逝的毫秒数有关，掉帧只是让物体跳过中间位置（视觉上略跳），但动画总时长恒定、终态确定。工程上我们要求所有动画遵守同一条纪律：进度 = 已过时间 / 声明时长，缓动只是对这个比值做非线性映射。

停止条件要特别处理。p 很可能永远不会恰好等于 1，回调间隔跳一下就从 0.98 直接越过 1，如果用 Math.min 之外的写法，元素会停在差 0.3px 的位置，transform 下的小数位移在低端屏上就是一根糊掉的边。所以务必在 p >= 1 时显式写入终点值再注销任务，上面代码里 opts.render(opts.to) 放在 remove 之前就是这个原因。

回调里的读写分离

第四节说过动画回调的执行点紧贴重绘之前，这个位置读几何属性（offsetHeight、getComputedStyle 的布局相关值）意味着：本帧刚写入的样式还没提交布局，浏览器必须立即同步把布局算出来才能回答你，代价是每帧一次强制布局。这与《DOM 操作性能：批量插入与重排优化》里反复出现的”读触发同步重排”是同一个机制，只是动画把它放大到每秒 60 次。正确姿势是把”量”和”用”分开：尺寸在初始化时量一次缓存起来，只在 resize 这类低频事件后重测，动画回调里只读缓存、只写样式：

与 CSS 动画的分工配合

《CSS 动画与 JS 动画的性能取舍》给过选型判据，这里只讲配合时的工程细节。我们常用的混合模式是：JS 负责算，CSS 负责补。JS 在交互事件里计算出目标位置和时长，把它们写成 CSS 变量的替代品——直接写到 transition-duration 和 transform 上，让浏览器去做插值，比如点击展开面板时 JS 算出内容高度，CSS transition 负责从 0 过渡过去。这样主线程只在起点出现一次，动画全程不占用帧预算。

配合的第一原则是所有权：一个属性同一时刻只能有一个主人。如果 CSS transition 还挂在元素上，而你的 rAF 循环每帧写 top，那么每次写入都会触发一条新过渡，动画会被搅成一锅粥。规则是 JS 接管前先把过渡类摘掉，JS 结束后再把类加回来。反过来也一样：CSS 动画在跑的元素不要同时用 JS 写 transform。

第二，长动画中途改目标值，现实里只能靠 JS。transition 被打断时浏览器虽然会从当前计算值继续，但你无法为”剩余路程”重新指定时长和缓动，观感就是速度突变；@keyframes 更是从头定义死的轨迹，中途重定向等于整个重放。凡是目标值会随用户输入连续变化的动画——拖拽回弹、图表数值追赶、跟手位移——都落在 JS 一侧，这也是本文这一整套循环结构存在的理由。

三个真实坑与度量验收

先复盘三个线上事故的成因与修法。

坑一：iOS 上滚动期间 rAF 降频甚至停摆。iOS Safari 在用户手指触摸滚动和惯性滚动期间几乎不给 rAF 回调发帧，页面滚动结束后动画”卡壳复活”。我们的跟手侧滑动画最初就是用 rAF 平滑 touchmove 坐标做的，实机上滑动期间动画完全冻结。修法是承认场景分层：触摸期间直接在 touchmove 回调里同步写 transform——那是浏览器本来就等着看结果的时机，多这一次写入摊不平；手指抬起后用 rAF 接管回弹收尾。

坑二：后台恢复后时间戳跳变，元素瞬移。rAF 暂停期间时间照常流逝，切回标签页的第一帧，ts - startTime 可能已经是几分钟，进度直接撞满，元素从起点一步跳到位。修法是在任务回调里记录上一帧时刻，发现 ts - lastTs 超过一个阈值（我们用 500ms）就判定为”从后台醒来”，保留当前进度、把 startTime 平移过去，让动画从冻结处继续跑完剩余路程。

坑三：cancel 时机不对导致泄漏。组件被 remove 掉 DOM 时，如果它的动画任务还挂在 Ticker 里，闭包持有已删节点的引用，节点永远回收不掉，而且回调每帧还在对一个不存在于文档的元素写样式。规则只有一条：组件的 destroy 必须先调用句柄的 remove（若组件自己直接持有 rAF 则先 cancelAnimationFrame），后断内部引用，顺序反了都不会漏，但漏一步必出问题。

度量方面，不要凭感觉判断流畅度。帧率与掉帧可以直接在 Ticker 里打点统计，方法是用 Date.now 或回调时间戳记录相邻帧间隔，跑够样本后算 P95：

小结

setTimeout 的问题不是 16 这个数不准，而是回调时刻与重绘时机之间没有约定；rAF 把调度权交还浏览器，换来与 vsync 对齐的节拍、后台自动暂停的能耗语义，以及一个各家基准不一的时间戳参数。工程上请记住四件事：polyfill 里 cancel 的双命名必须都探测；全页面维持一条 Ticker 循环，动画以任务身份进出；进度用时间除法而不是帧计数，终点值必须在最后一帧显式写入；回调内禁止读布局属性，尺寸靠缓存加 resize 重测。流畅度不靠肉眼裁决，用 P95 帧间隔和 Timeline 打点验收，并把 Android 4.0 的 30fps 当作现实基线。
