HTML5 contenteditable 富文本编辑入门

本文属于《HTML 与 CSS》第 13/62 篇
上一篇系列目录下一篇

去年秋天接到一个不算大的需求：给工单系统加一个”带加粗、链接、图片的备注编辑器”。我选了当时看起来最省事的 contenteditable，觉得一天就能上线，结果前前后后修了一个多月。本文按”现象—原因—解法”把坑复盘一遍，顺带讲清 textarea、同页 div、iframe + designMode 三种载体的取舍，适合准备自己撸轻量富文本的前端。全文 ES5，兼容底线是 IE 9，IE 8 单独说明。

一个备注编辑器引发的选型

需求很朴素：支持加粗、插链接、插图片，内容存进数据库、在列表页原样展示，上限两千字。我们评估了三条路。

第一条是 textarea 加标记语法，用户输入 **加粗** 这类符号再渲染预览。实现成本最可控，粘贴天然纯文本，maxlength 直接可用。但产品要求”点一下按钮文字就变粗”，不接受左源码右预览，谈了两轮只能放弃。

第二条是同页 div 加 contenteditable，原生所见即所得，DOM 里直接拿到 HTML，代码量最小。

第三条是老派 iframe + designMode，编辑区放进 iframe，样式与宿主彻底隔离，当年主流编辑器（FCKeditor 那一代）就走这条路。代价是维护两套文档、高度自己撑、样式再写一遍。

我选了第二条，理由是”HTML5 原生特性，浏览器都支持了，能有什么坑”。事实上坑不在属性本身，而在它背后那套各浏览器各自实现、没有互操作测试的编辑模型。第三条路我也实现了一半，同样要面对这些问题，只是多背一层 iframe 的债。

三种载体的实际差别

三种载体放在一起对比：

维度 textarea 同页 div + contenteditable iframe + designMode
能否承载格式 否，只有纯文本 是，直接产出 HTML 是，直接产出 HTML
样式隔离 不涉及 无，编辑区继承全站 CSS 彻底隔离，可单独喂一套样式
用户输入行为 高度一致 各浏览器生成的结构不同 与同页 div 一致，同样有差异
光标与选区 selectionStart / selectionEnd Range 或 textRange，两套 API 同左，但要跨 document 拿
取值 value innerHTML contentDocument.body.innerHTML
长度限制 maxlength 原生可用 不支持，要自己截断 不支持，要自己截断
粘贴 天然纯文本 任意 HTML 与内联样式进来 同样任意
XSS 面 小，转义即可 大，必须净化 大，必须净化
适合场景 评论、留言、备注纯文本 轻量富文本、单页内嵌 富文本 + 需要独立渲染样式

textarea 的最大优势不是简单，而是”它不碰渲染”。用户贴进来的东西不改变文档结构，光标位置能用一个数字表达，maxlength 由浏览器实现。这些微不足道的确定性，换到 contenteditable 就全消失。

iframe 那条路的代码留着，几个坑记在这儿：

没有 src 的 iframe 在 Firefox 上拿到的 about:blank 没有正常 baseURL，不先 open() 写一遍再 close()，designMode 设了也白设；IE 8 在 onload 之前拿到的 contentWindow.document 是个空壳，而更早的 IE 认 document.body.contentEditable 这个私有属性，和 designMode 混用时选区又落到宿主文档。iframe 高度不自适应，得从内部读 body.scrollHeight 回写宿主高度，中文换行时还会抖。样式隔离这个唯一优势，换来的是双份文档、双份事件、双份调试成本。

基本用法与 execCommand 的真实脾气

五个坑和它们的解法

坑一：粘贴带进来任意 HTML 与内联样式

现象：从 Word 复制一段带样式的文字贴进来，备注区立刻出现五号字、宋体、深蓝加下划线，夹着 <span class=MsoNormal> 和一堆 mso- 样式；从邮件客户端粘贴还会带进 <style> 块，把列表页字体全改了。

原因是默认粘贴行为会把剪贴板里的 HTML 片段原样插进 DOM，浏览器不做任何限制。解法是在 paste 里阻止默认行为，只取纯文本，自己转段落：

坦白一句：2014 年没有异步剪贴板接口，只能在 paste 的同步上下文里读，读不到就提示用户按 Ctrl+V 交给系统粘贴。

前端净化只是体验层，不是安全层。用户可以关 JS、直接改 DOM、拿 curl 往接口里 POST 任意 HTML。所以服务端入库前必须再净化一次，重点清掉 <script>、<iframe>、<object>、事件属性和 javascript: 协议。存储型 XSS 的触发点往往在列表页——备注被原样渲染进别人的浏览器，一个链接就够拿 cookie。我们用 PHP 的 HTMLPurifier 配白名单，前端管体验、后端才是防线。

坑二：每个浏览器都造自己的垃圾结构

现象：同一段”三行文字加一个列表”，四个浏览器存出来的 HTML 完全不一样。Chrome 用 <div> 包每一行，样式命令生成 <span style="font-weight: bold;">，粘贴网页时还会连 <font> 和成串内联 style 一起塞进来；Firefox 也用 <div>，但给空元素塞 _moz_dirty、末尾补 <br _moz_dirty="">，粘进来的块级元素标上 type="-moz-"；IE 9/10 用 <p>，颜色写成 <font color>，行尾空格变成一串 &nbsp;；从 WebKit 拷进 Firefox 还多出 class="Apple-style-span"。

这就是把 innerHTML 直接存库迟早出事的原因，三个后果我们全碰上了：换浏览器打开必然二次变形，渲染时当前浏览器还会再套一层自己的结构，越存越脏；内联样式和全站样式表打架，客服反馈”有些工单字号莫名其妙是 12px”；标签塞满无用属性，一条备注轻松破 8 KB，列表页拉 50 条就是几百 KB。

解法是入库前归一化一次：白名单外的标签拆壳留内容、属性只留 href/src/alt、<font> 换成 <b>/<i>、Chrome 的 <div> 行统一成 <p>。

坑三：换行、空行与塌陷的高度

三个现象。第一，回车产生的元素不一致：Chrome 与 Firefox 插 <div>，IE 9/10 插 <p>，IE 8 混着来；Shift+Enter 才是 <br>，IE 插的还是带 clear 的 br。Chrome 29 起有个 defaultParagraphSeparator 能指定，但只有它自己支持。第二，末尾空行存不住：文末敲两个回车，拿到的是空段落，展示时高度为 0，回车消失；反过来带 br 的段落展示正常，再写回时浏览器又会把它合并掉。第三，空编辑区点不进光标：内容为空时在 IE 里高度塌陷。

坑四：光标、选区与中文组字

先说 API 的分裂。IE 8 及以下只有 document.selection，给的是 TextRange，没有标准 Range 的起止节点；Firefox 4 和 Chrome 用 getSelection() 加 getRangeAt(0)，IE 9 才勉强实现标准 Range。跨块选区更麻烦：insertHTML 命令 IE 不支持，自己插入得走 deleteContents() 加 insertNode()，而后者只把片段插在选区起始位置，跨段落选择会留下一堆半截块元素。IE 反而简单，pasteHTML 什么片段都能吞。

保存光标我们第一版是算全文第几个字符的偏移再重放。这个思路要放弃：命令会把文本节点切成好几段，normalize() 再合并回来，存库重新渲染后结构又是另一副样子，同一个视觉位置的偏移每次都变，表现是光标跳到半句话前面、图片插进句子中间。存 Range（节点引用加节点内偏移）才靠得住——只要那两个节点还在，位置就准。注意 Range 不能序列化，刷新页面要重算。

中文输入法是统计字数的直接杀手。现象：输入”今天”先按 jin，keyup 一路触发，字数从 3 跳到 5，上屏后又变成 2，用户以为统计坏了。原因是组词期间 Chrome 把拼音串当内容写进 DOM 并派发 keyup，选词确认时才修正。解法用 compositionstart / compositionend 加标志位：

composition 事件在 2014 年的 Chrome 和 Firefox 上可用，IE 全系列不支持——但 IE 组词期间本来就不触发键盘事件，不监听反而对。必须写清楚的是：contenteditable 上的 input 当时完全不可信，Chrome 在连按退格、右键删除时漏报，IE 9/10 只在部分按键上触发，IE 8 干脆不支持。我们最终监听 keyup、paste、drop、compositionend 四路，再加每半秒读一次内容比字符串的定时器兜底。丑，但再没出现字数不刷新。本想用 MutationObserver，因 IE 全家不支持，一个循环就否了。

坑五：execCommand(‘undo’) 靠不住

现象：用户连打十个字，粘贴一大段，删掉三行，然后按 Ctrl+Z。第一次按，粘贴的整段全没；第二次按，十个字一起消失；有时按了没反应，或者重做后占位图变成破图。

原因是 execCommand('undo') 只覆盖浏览器自己记录的编辑历史，而我们的代码在改写 DOM——净化、插占位图、修空段落——每次赋值 innerHTML 都让历史栈断裂或合成一步；粘贴和输入法上屏在浏览器看来是一次操作，用户预期是若干次。IE 更特殊，失焦再聚焦历史就丢了。

结论：撤销自己做快照栈，存字符串，别存节点引用。

成本要说清：60 步乘上一条两千字带标签的内容，内存轻松几 MB，低端机要控上限；快照不保存表单元素状态，编辑区混了 input 得单独存。另有遗留：IE 下取消 Ctrl+Z 有时拦不住浏览器自己的撤销，两套历史交错会让内容闪一下。做法是每次 gotoStep 之后无条件再 push() 一次，强制拉平。

flowchart TD
    A[用户操作或事件] --> B[throttle 300ms]
    B --> C[push 一次 innerHTML 快照]
    C --> D{栈长超过上限}
    D -->|是| E[shift 丢掉最老一步]
    D -->|否| F[更新 index]
    E --> F
    F --> G[Ctrl+Z 用 index 回退并重建光标]

移动端就别折腾了

一句话结论：2014 年在 iOS 和 Android 浏览器里，contenteditable 做不到可控。键盘弹起遮挡编辑区、系统选区工具栏与自绘工具栏打架、Android 4.x 内置浏览器上 execCommand 部分命令静默失败、拖动光标调整选区直接卡住页面。移动端我们只做 textarea，加粗和链接改成标记语法，展示交给服务端渲染。

自研的边界在哪里

最后校准一次选型。CKEditor 4.4（2014 年 5 月发布）改成 GPL / LGPL / MPL 三重许可，含皮肤和常用插件压缩后 300 KB 量级、gzip 后 100 KB 出头；TinyMCE 4.x 是 LGPL，核心加主题加插件压缩后 400 KB 上下；KindEditor 4.1.x 是 GPL / MIT 双许可，压缩后 100 KB 出头，中文文档齐全。三者都自带表格、源码视图、多图上传，自研短期追不上。

所以边界要划清：需求真的是加粗、斜体、链接、一张图、一个列表，自研这三百行比引入编辑器再裁剪配置更省时间，体积也可控；一旦要表格、字号颜色、粘贴 Word 保格式、附件、源码编辑，直接上现成编辑器。这次要是开头就问清以后要不要表格，能少写两千行。

小结

contenteditable 只有一行属性，背后却是四套互不相同、没有互操作测试的编辑实现，这是所有坑的总根源。textarea 的价值在于确定性：粘贴不带格式、光标能用一个数字表达；要样式隔离才考虑 iframe，代价是双份文档和高度自适应。真要用 contenteditable，四件事必须先做：粘贴时阻止默认行为只取纯文本，白名单净化且服务端再净化一次，存 Range 而不是算偏移，撤销自己做快照栈。其余细节都指向同一条经验：浏览器的默认行为一个都不能信，凡是自动发生的事情都自己接管。移动端只做 textarea，需求超出”简单富文本”就上 CKEditor、KindEditor、TinyMCE。
