IIFE 立即执行函数表达式

立即执行函数是这两年写前端绕不开的一个小结构：一行括号，把一段代码从全局里摘出来。它足够轻，轻到很多人以为它只是”包一下”，直到合并脚本后莫名其妙报了个 xxx is not a function，或者 setTimeout 全打印同一个值，才发现里面有几条不那么直观的规则。本文把 IIFE 当作”作用域与模块化的最小方案”来讲：先把它几种语法形态的差异讲透，再把它和同期几种代码组织方式放在一起做选型对比，最后复盘几个真实踩过的坑并给出两个能直接抄的模板。适合已经会写 function 和 var、开始负责页面上脚本结构的读者。

IIFE 的语法形态与差异

先纠一个术语。按 ECMAScript 5 的文法，(function () {})() 里的 function () {} 是一个函数表达式（FunctionExpression），紧跟的 () 是一次调用，合起来读作”函数表达式 + 调用”。社区习惯叫它 Immediately Invoked Function Expression（IIFE），中文口语里常简称为”立即执行函数”。严格说”函数”二字是省略了”表达式”，但约定俗成，本文混用两者指同一件事，不再纠结。

关键问题是：为什么 function () {}() 会直接报语法错？因为在语句位置以 function 开头时，解析器把它当成函数声明（FunctionDeclaration），而声明不允许匿名、更不允许在名字缺失的情况下直接接一对调用括号。文法里调用表达式 CallExpression : MemberExpression Arguments 要求括号左边是一个成员表达式，函数声明不是表达式，于是整条语句无法归约，抛出 SyntaxError。解决办法就是把函数塞进一个”必须是表达式”的上下文里，让它从声明降级为表达式，最直白的是外面加一对圆括号，最省事的是前面加一个一元运算符。

一元运算符这一类写法能成立，是因为 !、+、~、void 后面必须跟一个表达式作操作数，于是 function 不再处于声明位置。它们各有代价：会消耗掉函数的返回值，! 返回布尔、+ 返回数值、~ 返回按位取反、void 恒为 undefined。把五种常见写法列个对比：

写法 是否产生表达式 返回值 可读性 是否需额外注意分号
(function () {})() 是 函数自身的返回值 最好，语义直白 需要，见下文 ASI
!function () {}() 是 !（返回值），布尔 差，符号无实义 前一行即使缺分号也难被拼接
+function () {}() 是 +（返回值），数值 差 同上
~function () {}() 是 ~（返回值），整数 差 同上
void function () {}() 是 恒为 undefined 中，能表意”丢弃结果” 同上

结论是：日常写 (function () {})()，因为它保留返回语义、可读性最好；!、void 一类主要出现在体积敏感的压缩产物里，省两三个字节，代价是把返回值语义搭了进去。需要返回值时（比如模块返回一个对象）就别用一元前缀，! 会把你的对象变成 false。

为什么需要 IIFE：作用域与闭包

讲完语法，回答”为什么要费劲包这一层”。最根本的一条是 var 没有块级作用域。在 2014 年，浏览器里能稳定用的只有函数作用域：if、for、try 里声明的 var 全部提升到所在函数顶部，共享同一个变量。语言层面正在讨论用块级作用域声明（当时草案里写作 let 与 const，尚未普及）来替代这一层，但那是后话，眼下能靠的只有”再造一个函数作用域”，而立即执行正好让这个函数不必留下名字、不占用外部标识。

第二是全局命名空间污染。脚本里随手一个 var temp、var config，就挂到了 window 上，和别的库、别的同事写的代码撞名。用 IIFE 把内部变量圈起来，临时值在执行完就随作用域销毁，不逃逸到全局。第三是循环里闭包捕获变量的经典问题——它几乎每个人都会踩一次，这里给 ES5 的正确写法：

五种代码组织方式的选型对比

真正想聊的是选型：把”组织一段前端代码”这件事拆开，2014 年手上其实有五张牌。IIFE 只是其中最小的一张，用不用得看场景。下面这张表是本文的主线，六列分别是隔离能力、依赖管理、可测试性、体积、加载方式与当时生态。

方式 隔离能力 依赖管理 可测试性 体积 加载方式 当时生态
全局函数 + 命名空间对象 无，仅分层命名 无，靠 script 顺序 差，全局状态难重置 零额外 <script> 顺序 人人都会
IIFE + 参数注入 函数级 手动实参注入 中，可换假依赖 零额外 <script> 顺序 jQuery 源码自身即此
IIFE + 模块返回 私有状态 + 公开 API 参数注入 良 零额外 <script> 单页/小部件主流
AMD（RequireJS） 模块级 声明式异步解析 良，依赖可 mock 需 r.js 打包 异步按需 大型项目主流（2.1.x）

它解决的是”别撞名”，不解决”别泄漏”——App 本身仍是全局可变对象，任何脚本都能往里塞东西，私有变量根本藏不住。

第二张牌是 IIFE 加参数注入，把外部依赖作为实参传进去。这是它相对命名空间最大的进步，收益有三重：一是拿到局部别名（内部 window、$ 都变成参数，改一个环境不影响内部引用）；二是压缩器能把短形参名改得更短，全局属性访问变成局部变量访问；三是可替换，测试时传一个假的 jQuery 进去即可。jQuery 官方源码本身就套在这层 IIFE 里，undefined 作形参等历史细节在旧文《jQuery 插件开发模式与实战》里已展开，这里不重讲。

第三张牌是 IIFE 加模块返回，也就是 Revealing Module 风格：函数内部藏私有变量，只 return 一个对象当作公开 API。

选型结论可以一句话收：单个页面、独立小部件、不想要任何运行时依赖的，IIFE 就够了；模块之间依赖关系多、需要异步按需加载的项目，上 AMD；团队已经在写 Node、想复用 npm 生态的，用 Browserify。三者不是替代关系，而是随协作规模升级的三段台阶。

真实踩过的坑与复盘

ASI 与脚本拼接。 这是最”玄学”也最常见的事故。两个文件合并后，前一个文件末尾如果漏了分号，后一个文件以 ( 开头，就会被解析成对前一个返回值的调用：

!、~、+、void 前缀之所以有时反而”更安全”，是因为它们无法接在一个值后面续写表达式，自动分号插入（ASI）会在它们前面补一个分号；而以 ( 开头的语句正好相反，会被 ASI 当成上一句的调用参数吃掉。工程上的铁律是：压缩合并前，保证每一段脚本都以分号结尾，别让语法结构依赖 ASI。合并压缩的收益与这类边界风险在旧文《资源合并与压缩的收益分析》里已有量化，此处不重复。

忘了包循环。 setTimeout 全输出 5 的复现与修复，上一节已经给过，这里只补一句：同样的坑在 for 里绑事件时一模一样，var i 是共享的，回调里读到的永远是最终值。

报错栈里只有匿名函数。 IIFE 匿名，一旦内部抛错，栈帧里只写着 anonymous，调试时很难找到是哪一块。给它起个内部名字就能显著改善可调试性，而且函数名在自身作用域内可见，不影响外部：

this 的指向。 IIFE 内部 this 在非严格模式下指向全局对象，在 'use strict' 下则是 undefined，两种都不是”外层那个 this“。别指望在 IIFE 里用 this 拿 window，显式把 window 作为实参传进来才靠得住：(function (window) { ... }(window))。

只执行一次，配置改不动。 IIFE 在定义时就跑完，内部的 defaults、count 之类要么被闭包冻结、要么只从参数进来一次。想让配置可变，不要在外部去改闭包里的私有变量（也改不到），而是从返回的 API 里提供一个 setOptions 之类的入口。至于用闭包缓存来加速的那些手法，旧文《JavaScript 惰性求值与缓存优化》已系统讲过，本文不展开。

闭包长期引用大对象。 IIFE 捕获的大数组、DOM 列表会随闭包一直存活，回收不掉。清理时机与事件解绑、$.cache 那条可达链是一回事，具体做法参考旧文《DOM 事件移除与内存泄漏》，此处一句带过。

小结

IIFE 本质是”函数表达式 + 调用”，加括号或加一元前缀只是为了把函数从声明位置降成表达式；五种写法里日常用 (function () {})() 保留返回语义，!、void 只是压缩场景省字节。它存在的理由是三件事：var 无块级作用域、全局命名空间易污染、循环闭包捕获共享变量。放到选型坐标里看，IIFE 是隔离成本最低的一张牌——小页面、独立小部件用它足够；依赖关系一多就升级 AMD；团队已在 Node 上则用 Browserify，三者是台阶不是对手。用的时候守住几条纪律：合并前每段以分号结尾别赌 ASI、给函数起个名方便看栈、this/window 显式传入、可变配置走返回的 API 别去戳闭包、闭包大对象记得随模块销毁解绑。把这几条刻进肌肉记忆，IIFE 就从一行括号变成了一套可靠的最小组织方式。
