selection 与 range 实现文本选区

要做「选中文字就高亮」或者「划词弹出释义」这类功能，绕不开浏览器的选区 API。2014 年的现实是两套模型并存：IE 9 以上和其余现代浏览器走标准的 Selection + Range，IE 8 及以下只有一套思路完全不同的 document.selection + TextRange，两者的数据结构、取文本方式、改 DOM 的手段全都不一样。本文以「选中即高亮 + 划词提示」这个组件为主线，把两套模型的概念差异、取选区、包高亮、算浮层坐标的完整 ES5 实现写一遍，并把当时踩过的坑列清楚。适合要动手写这类组件、或者接手过一坨 document.selection 老代码的前端。

两套模型：边界点与可移动的 TextRange

标准模型（IE 9+、Firefox、Chrome、Safari、Opera）的核心是「边界点」。一个 Range 由两个点定义：(startContainer, startOffset) 到 (endContainer, endOffset)。如果容器是文本节点，offset 就是字符下标；如果容器是元素，offset 是子节点索引——也就是说 setStart(p, 2) 的含义是「第 2 个和第 3 个子节点之间」，而不是「段落的第 2 个字符」。Selection 则是用户实际看到的那一团高亮，它记录锚点（anchor）与焦点（focus），内部持有一个或多个 Range。

老 IE（IE 8 及更早）的 TextRange 是另一种东西：它像一个可以被推动的游标对，不需要知道容器是谁，靠 moveStart('character', 3)、moveEnd('word', -1) 这类按语义单位（character、word、sentence、textedit）挪动端点的方式来描述范围，取内容直接读 .text，改内容用 .text = 'xxx' 或 pasteHTML()。它把字符边界和元素边界混在一个对象里，好处是简单，坏处是任何和结构相关的操作都得靠循环试探。

方向问题：先归一化再动手

标准 Range 的 start 与 end 由浏览器保证是文档序正序，用户从右往左拖选，range.startOffset 依然指向前面那个点；真正会「反」的是 Selection 的 anchor 与 focus。所以凡是绕过 getRangeAt(0)、自己拿 anchor 和 focus 拼 Range 的代码（保存恢复选区、或者按 anchor 插入元素时经常会这么写），反向选择时就会造出一段空 Range。稳妥做法有两个：能用 getRangeAt(0) 就别自己拼；必须比大小就用一个临时 Range 探边界点。

上面返回 0 的那一支要留个心眼：anchorNode 是 focusNode 的祖先（或者反过来）时，光比容器定不出先后，还得把祖先那一侧的偏移展开到子节点层级才能比。这种场景别硬推，直接退回 getRangeAt(0) 让浏览器替你归一化。

老 IE 的坑更直接：document.selection.createRange().startOffset 与 endOffset 在反向选择时会互换，拿这两个值去切字符串必须自己排序。Range.compareBoundaryPoints 虽然各家都在，但 Safari 与 Chrome 早期实现的 START_TO_START / END_TO_END 参数顺序和标准是反的（MDN 上有备注），所以本文只在「判断某个节点是否整体落在选区内」这一处依赖它，并且上线前在 Chrome、Safari、Firefox、IE 9 / 10 各测过一轮；凡涉及排序的地方，一律用上面这个不依赖它的写法。

取选区：getSelectedText 与 getSelectedRange

第一步是拿到「当前这一坨选中内容」，并且把它限制在组件自己的容器里，否则用户在页面别处划词也会触发你的逻辑。

调用方拿到 range 之后，第一件事应该是判断它是哪套模型：标准 Range 有 cloneRange 与 setStart，TextRange 有 duplicate 和 pasteHTML。用特性检测而不是浏览器嗅探，代码能少一大截分支。另外严格起见，纯文本要从那个已经按 root 过滤过的范围上取（range.toString()），getSelectedText() 里的 Selection.toString() 是省事的写法，选区越界时它会把别人家的文字一起带回来；老 IE 的 tr.text 天然等于该范围内容，反而没这个问题。

getRangeAt(0) 的取舍要说清楚。Firefox 当时支持按住 Ctrl 加选出不连续的多段选区，rangeCount 会大于 1，只取第 0 段意味着后两段被无声丢掉。我们的处理不是在组件里循环处理所有 Range——高亮可以循环，但划词提示要合并多个矩形，交互上根本说不清「你要查哪个词」。所以在 mousedown 时就把多余选区清掉，用单区语义把不确定性挡在外面：

高亮：从 surroundContents 到手工切分

把选中文本包成 <span class="mark"> 是本文的重头，有两种做法，差别很大。

做法一：surroundContents，一步到位但很脆

surroundContents() 的规则是：新节点必须是 Range 的公共祖先的合法子节点，且选区不能「部分跨越」任何非文本元素。从段落开头整段拖到段落结尾没问题；一旦选区从第一段末尾拖到第三段开头，中间那些 <p> 属于「只被选中了一半」，直接抛 INVALID_STATE_ERR（Firefox 上错误名略有不同，都是同一个异常）。所以它只能当快路径，跨元素必须走手工切分。IE 8 的对应手段是 pasteHTML，代价是它会打断当前选区：

htmlText 直接拼字符串在我们项目里只在纯文本段落用，一旦选区里带链接或图片就得先做转义，风险不小；老 IE 这条分支我们的底线是「不出错就行」，不做像素级还原。

做法二：切分边界文本节点后逐段包裹

思路是不搬任何节点，只在原位给每一段被选中的文本各自套一个 span。分三步：先快照出所有被覆盖的文本节点及其局部偏移，再用 splitText 把首尾两个节点切开让选中段变成完整节点，最后逐个包裹并合并相邻 span。

这里有个隐藏的好处：遍历的起点是 root 而不是 range.commonAncestorContainer，所以选区要是有一截跑到别人的区块里，跑不出 root 的那部分会被自动裁掉，高亮只发生在组件自己的地盘上。

还有两个必须点名的细节。其一，只有当 startContainer / endContainer 是文本节点时才会出现「部分覆盖」，容器是元素时边界落在子节点之间，遍历里的整体覆盖判定自然成立，所以 tn === range.startContainer 这一支就够用。其二，splitText 之后原 Range 的边界不能再用：规范上浏览器会自动调整活动 Range 的容器与偏移，但 IE 9 / 10 的实现并不完全可靠，更何况我们存在变量里的那份边界值一定是旧的。切分之后要重新构造选区，否则后面 getSelection() 拿到的是一个错位 Range：

划词提示：isCollapsed、矩形与三个坐标坑

交互链路很短：mouseup 之后判断有没有选中内容，有就取一个矩形把浮层贴上去。

三个坑逐个说。第一，坐标参照系不一致。getBoundingClientRect() 给的是视口坐标，offsetTop / offsetLeft 给的是相对 offsetParent 的文档流坐标，两者差了一个滚动量：把浮层挂在 body 上按页面坐标定位时，视口坐标要加上 document.documentElement.scrollLeft；挂在滚动容器里按容器坐标定位时，容器自身滚掉的那部分要加回来，反过来按页面坐标算就要减掉 scrollTop。方向搞混的表现是「一滚动浮层就飞」。第二，反向选择不影响矩形：前面说过 Range 已按文档序归一，getBoundingClientRect() 永远返回正向的外接框，不需要修正；要修正的是老 IE，那里得先归一 startOffset 与 endOffset 再取矩形。第三，选区跨多行时 getClientRects() 返回多个矩形，一个一行，而用户视线焦点在选区末尾那一行，所以取最后一个而不是合并成一个大框——合并框会把浮层甩到整块区域中间，很怪。

另外 IE 8 的 TextRange.getBoundingClientRect() 是非标准实现，返回的对象只有 left / top / right / bottom，没有 width 与 height，所以上面那条「宽高都是 0 就当空选区」的判断在老 IE 上要换成比 right - left；再往下兜底只能读 TextRange 自带的 boundingTop / boundingHeight / boundingLeft，或者先在选区里 pasteHTML 插一个占位元素、再读它的 offsetTop 与 offsetLeft 并累加 offsetParent 链——两种都是近似，老 IE 上浮层贴不准是常态，别在这里追求像素级。还有一点，「按点击坐标反推出光标位置」这件事当时没有跨浏览器办法：Firefox 有 document.caretPositionFromPoint()，WebKit 系有私有的 document.caretRangeFromPoint()，老 IE 只能靠 TextRange.moveToPoint(x, y) 做近似，三者都得当作各自浏览器的专属增强，不能进主流程。

设置选区：反过来的能力更麻烦

高亮之后常见需求是「点一下按钮把这段代码选中」，让用户直接 Ctrl + C。标准路径是 selectNodeContents 加 addRange，老 IE 是 document.body.createTextRange() 加 moveToElementText() 和 select()。

Selection.selectAllChildren(el) 当时也可用，它等价于上面那三行「清空再加 Range」，但对不可选的元素（表单控件、某些 <fieldset>）Firefox 与 Safari 的表现不一致，Safari 在 <input> 上尤其怪，所以照样得包 try/catch。iOS Safari 是这里的老大难：addRange 调用不报错，界面上就是不显示选区高亮；配合 document.execCommand('copy') 做一键复制时，在 iOS 4 与 iOS 7 上必须真机验证，我们当时的结论是「桌面和 Android 的 Chrome 可靠，iOS 不稳」，只能保留「长按手动复制」这条兜底路径。复制这件事在《移动端长按与复制粘贴处理》里写过，本文不重复展开——它的核心限制始终是「必须已存在选区且由用户手势直接触发」。

顺带说一句「查找并选中」：window.find(text, caseSensitive, wrap, wholeWord) 当时 Firefox 与 Chrome 有、IE 没有，IE 系走 document.body.createTextRange().findText(kw)，然后 select() 加 scrollIntoView(true)。两条路都会把选区设好，正好能复用前面的高亮函数。

事件时机与性能取舍

selectionchange 在 2014 年不能当主力。IE 9 / 10 的 document.onselectionchange 可用，WebKit 系部分支持，Firefox 有自己的 onselectionchange，但三家的事件对象、触发时机、冒泡行为全不一致，甚至同一浏览器里拖选过程中根本不发事件。所以「选区一变就重算」这件事只能靠 mouseup 加 keyup 组合驱动，再用去抖兜住手抖：

轮询里只调 getSelectedText()，因为它本身极轻——Selection.toString() 与 TextRange.text 只是读一个已经维护好的字符串，不涉及布局。真正重的是改 DOM：highlightBySplit 要遍历整棵 root，每个候选文本节点再建一个临时 Range 比边界，节点上千时耗时肉眼可见；splitText 与 insertNode 是写操作，脏掉布局缓存，紧接着读 getBoundingClientRect() 就强制一次同步重排。所以原则还是老规矩：高亮范围限制在正文容器而不是 document，一次事件只做一次批量处理，读矩形放到 setTimeout 之后与写入错开（bindSelectTip 里那个 200 毫秒延时顺带就满足了这一条）——这属于《减少重排与重绘的实践清单》里「先集中读再集中写」那条的具体应用，不重复推导。

一份坑清单

contenteditable 里改 DOM 会让编辑器失焦或光标乱跳。富文本里做高亮，必须先 sel.getRangeAt(0).cloneRange() 把 Range 存下来，改完 DOM 再 removeAllRanges() 加 addRange(savedRange) 恢复；富文本本身在《HTML5 contenteditable 富文本编辑入门》里写过，本文只提选区这一维。

表格单元格内跨节点选择会让矩形彻底错乱：getClientRects() 在 <td> 之间返回的矩形带有单元格的边框偏移，浮层贴上去会盖住线。当时的处理是判定 commonAncestorContainer 跨了 tr 就只显示工具条、不做贴字定位。

老 IE 的 tr.text 把换行返回成 \r，标准浏览器是 \n，拿去和 innerHTML 或后端存的数据做指纹比对时必然不等。别用等号，用长度加忽略空白的摘要。

<input> 与 <textarea> 有自己的选区 API：selectionStart、selectionEnd、setSelectionRange()，这套和页面 Selection 是两条平行线。Firefox 上尤其明显：输入框一聚焦，window.getSelection() 就被字段选区抢走，你在正文里刚做的高亮选区当场失效。两套 API 的边界要说清——字段内划词走 selectionStart 系，页面文本才走 Selection / Range，selectionchange 在字段上根本不可靠，实时输入监听那部分见《DOM 实时输入监听 input 事件》。

最后，IE 8 的 document.selection 是只读的全局对象，别写 document.selection = null；标准侧清空选区永远用 sel.removeAllRanges()，而不是 WebKit 私有的 sel.empty()。

小结

判断该用哪个 API，按这张表走基本不会错：

需求 标准浏览器写法 IE 8 及更早 备注
取选中文本 String(window.getSelection()) document.selection.createRange().text 换行符差异要处理
取选区范围 sel.getRangeAt(0) document.selection.createRange() 先判 rangeCount / type
包一层元素 surroundContents 试，失败走切分 pasteHTML(htmlText) 跨元素必抛 INVALID_STATE_ERR
定位浮层 range.getClientRects() 取末个 tr.getBoundingClientRect() 视口坐标要与滚动量换算
设置选区 range.setStart 加 sel.addRange createTextRange().moveToElementText().select() iOS 上不稳，需真机验证
取消选区 sel.removeAllRanges() document.selection.empty() 不要用 sel.empty()

封装上建议分四层，别把模型判断散在各个业务函数里：探测层只回答「现在哪套模型可用」，取选区层输出统一的范围对象加纯文本，改选区层负责切分、包裹、还原和矩形，交互层只管事件时机与去抖。这样业务代码里只出现 getSelectedText、getSelectedRange、highlightBySplit、getSelectionBox 这类动宾函数名，两套模型的脏活都被压在下面一层。

flowchart TD
  A[探测层: 判断 Selection / document.selection] --> B[取选区层: getSelectedText / getSelectedRange]
  B --> C[改选区层: 切分文本节点 / 包裹 span / 算矩形]
  C --> D[交互层: mouseup + keyup + 200ms 去抖]
  D --> E[业务: 高亮 / 划词提示 / 一键复制]

年代限制也要摆在明面上：2014 年做这件事，跨浏览器一致性没有保证，selectionchange 不可信、iOS 设不了选区、IE 8 只能近似回选，所以高亮这种「改了 DOM 就得能撤回来」的能力一定要配指纹校验和丢弃策略，而不是幻想把边界匹配做到完美。把上面这四层写干净，剩下的都是浏览器差异表上的具体条目。
