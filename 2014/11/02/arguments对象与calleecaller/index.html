arguments 对象与 callee、caller

arguments 是 JavaScript 里最容易被随手用错的对象：它长得像数组却不是数组，它的下标会和形参互相影响，它还能通过 callee、caller 摸到函数自身与调用关系。也正因为这些能力，内核为它单独实现了一套激活对象逻辑，你在函数里多写一句 arguments 就可能让这段代码失去优化。本文从性能与调优的角度讲三件事：arguments 的行为边界到底在哪，callee 与 caller 为什么必须尽快淘汰，以及在高频调用的函数里怎样改写才能不为”参数快照”买单。适合写过不定参数、正要把项目切到严格模式的同学。

arguments 到底是什么

类数组对象，不是数组

它有 length、有数字下标、可以 for 循环走完，但它的原型不是 Array.prototype，所以 push、slice、indexOf、join 一个都调不出来。老版本 Firefox 曾经让 arguments 挂在 Array.prototype 上，能直接写 arguments.forEach(...)，这种私有能力别的内核没有，跨浏览器代码不能指望。统一姿势是借数组的泛型方法，把 arguments 当”接收者”传进去：

arguments.callee.caller 这种链式写法曾经被当成”穷人版调用栈”，我劝你把它当反例看：它慢、严格模式下不可用、混淆后名字全丢。真要栈信息，抛个异常看 err.stack 就够，V8 与 Firefox 当时都给了这个私有属性，IE 基本拿不到。

为什么 callee、caller 必须淘汰

严格模式下访问就报错

'use strict' 里 arguments 没有可用的 callee，访问它是 TypeError，Chrome 当时的报错原话是 'caller', 'callee', and 'arguments' properties may not be accessed on strict mode functions or the arguments objects for calls to them。还有一个更隐蔽的语法层面的坑：在严格模式代码里把 caller 或 callee 用作变量名、形参名，解析阶段就是 SyntaxError，连运行都到不了。

两类错误要分开看，第一类在解析阶段就把整个函数拦下，同一段里先写了非法的 var callee，第二条的报错你根本走不到。

它们会关掉引擎的优化

callee 的语义是”当前执行的函数”，这意味着函数对象在运行期才能确定，调用者可能是任何一个借用了该方法的对象。对引擎来说，这直接破坏了内联与逃逸分析的前提：它没法把这个函数当作一个固定的调用点来处理，也没法把形参安全地放在栈槽里。所以当时的做法很粗暴——函数体里只要出现 arguments.callee 或 caller，这个函数就整个不进优化流程。这不是规范条文而是内核的实现选择：为了少写一个函数名，你可能牺牲掉整个函数的执行效率。

性能主线：arguments 要花的三笔钱

这三笔是我做参数处理优化时反复遇到的，都给出可以在自己机器上跑的片段。方向是确定的，具体倍数请以实测为准——我只认量级，不认小数点。

第一笔：把 arguments 传出函数

函数一进入就会创建激活对象，形参本来是引擎最容易处理的一组值——它们可以直接待在栈上。但只要 arguments 被”泄漏”出去，也就是被 return、被存进数组、被作为实参传给另一个函数，引擎就必须保证它离开栈帧之后仍然可用，于是整个激活对象被实体化到堆上，形参也得一份一份搬进这个对象里。

这三个函数做的事几乎一样，但第一个走的路径完全不同。我在自己的机器上跑过一个 20 万次调用的循环，泄漏版比显式版慢了两三倍、内存也明显涨，第二、第三种改写则基本追平不写 arguments 的版本。这类差距在小数据量下很容易被噪声淹没，所以我把它当成一个方向性结论：能不传出就绝不传出。如果你的改写需要”参数个数不定”这个前提，那也请立刻 slice 成数组，别把 arguments 本身交给别人。

顺带说一句，通用缓存包装器很难完全避免这笔开销——《JavaScript 惰性求值与缓存优化》里那个 memoize 就是把 arguments 直接传给了 keyMaker。这是通用工具的固有代价，我的建议是只把它用在低频函数上，或者给热路径单独写一个显式传 key 的版本。

第三笔：用了就付出代价，哪怕没用

这是最反直觉的一条。只要函数体里出现了对 arguments 的引用，引擎就得为它准备参数对象——即使这个引用在一个永远走不到的分支里，甚至即使你只是把它读出来又丢掉。当时读 V8 源码会看到 arguments 相关的处理被划成好几条路径（不同版本里内部标记名不一样），判断的关键就是”函数里到底有没有真的用、有没有逃逸”。对写代码的人来说，只需要记住一条简化规则：热路径函数里要么彻底不用 arguments，要么就老老实实承担它的开销，半用不用是最亏的。

小结

arguments 不是数组，它是一个会牵动形参的对象，一次引用就可能让函数走上一条开销更大的实现路径。callee 与 caller 在严格模式下不可访问，在实现层面又直接阻碍优化，它们的替代方案分别是具名函数（IE 下用内部函数声明避开重复创建的 bug）和异常对象的 stack。至于实践规则，我给团队定的是四条：默认不用 arguments，参数个数不定就改成配置对象；必须用时只读 length 和需要的下标，绝不给它赋值；永远不要把 arguments 对象本身 return、存进数组或者传给别的函数；递归一律用名字而不是 callee。测量时记得预热、多轮取中位数、让结果参与运算防止被优化掉，并且只认量级。这几条听起来都是”少写点东西”，真正的收益是让引擎按它最熟悉的那条路去编译你的函数。
