JavaScript 数据类型与类型转换详解

隐式类型转换是 JavaScript 里名声最差的知识点：面试年年考，代码里年年错，背了一堆“奇技淫巧”的结论，遇到没见过的组合还是不会推。其实 ES5 规范把这件事写成了一个不大的规则系统——四个抽象操作加几条运算符语义，全部的“怪结果”都能从里面机械地推导出来。本文就是要把这套推导链完整走一遍：先看清楚语言类型与内部类型这两层体系，再逐个拆解 ToPrimitive、ToNumber、ToString、ToBoolean，然后把 +、关系比较、== 的转换规则挂回抽象操作这条主线上，最后落到显式转换的坑与团队规约。适合被 [] == ![] 这类题目困扰过、想一次把根子弄清楚的读者。读完你手里会有一张 hint 对照表、四个抽象操作的完整规则和一套直接可用的判定工具；以后再遇到推不出来的转换结果，回到第三节从 ToPrimitive 起手即可。文中所有代码均为 ES5，输出都在 Node 里实际跑过。

类型系统的两层视角

ES5 规范第 8 章把值分成六种语言类型：Undefined、Null、Boolean、String、Number、Object。注意口径，ES5 就是这六种，Undefined 和 Null 虽然各只有一个值，但都被承认为独立的类型；Number 类型内部还要算上 +0、-0、NaN 和正负 Infinity 这几个特殊值，它们都是 Number 而不是什么“空”或“非数对象”。TC39 当时已经在讨论把 Symbol 作为第七种类型加进语言（ES6 草案阶段），但在 2014 年的今天它完全不可用，本文所有规则都以已定稿的 ECMA-262 第 5.1 版为准。

日常用来摸类型底细的第一个工具是 typeof。规范 11.4.3 的表 15 规定了它的返回值一共列了七种字符串："undefined"、"boolean"、"string"、"number"、"function"、"object"，以及一个今天几乎见不到、但白纸黑字写在规范里的 "xml"。最后这个不是笔误：它保留给“未被其他类别覆盖的宿主对象”，老版 IE 对 XMLDocument 对象就老老实实返回 "xml"，这是当时做特性分支时真实踩到的坑。同一时期还有两个老 IE 的坑值得记录：标准模式之外，typeof alert 这类宿主函数在 IE 早期返回 "object" 而不是 "function"，判断可调用性时并不总可靠。

typeof null === 'object' 是所有人都会背的一句，但成因值得说清楚。这不是规范故意刁人：最早的 JavaScript 实现（SpiderMonkey 那一代）里，值存在机器字里，低位标签标示类型，对象的标签恰好是 0，而 null 表示为空指针、机器字全零，低位同样是 0，于是类型判断函数把它认成了对象。后来引擎重写了内部表示，但这个结果被已有代码固化下来，规范干脆承认它是对的。同理，typeof 对未声明的变量不抛 ReferenceError 而返回 "undefined"，这是规范明确保证的行为，也正是“检测一个全局 API 是否存在时，用 typeof someHostApi === 'undefined' 比直接引用变量安全”的全部理由——引用未声明变量会抛错，typeof 不会。

typeof 的粒度到此为止：所有对象（函数除外）一律返回 "object"，数组、日期、正则、DOM 节点分不出来。要更细的粒度，得先补两句类型语义。Null 类型虽然也只有一个值，规范给它的定义却是“空的对象引用”——var node = null 表达的是“这个变量将来会装对象、当前有意留空”；Undefined 表示“未初始化、压根还没有值”。二者的工程语义不同，这也是规范坚持把两个单值类型分开列数的原因。另一个容易忽略的是 Number 类型的表示极限：ES5 规定数字一律为 64 位双精度，整数只在 ±2^53 范围内保证精确，超出去连 String(x) 都会变成带舍入的指数形式。后端把雪花订单号这类长整型直接丢给前端做 Number()，尾数就已经错了——这不是转换的锅，是类型本身的极限，规约里“长 ID 走字符串”就出自这里。想看对象层的细粒度，还得请出第二层类型视角。

Object.prototype.toString 与内部类别

每个 ECMAScript 对象都有一个叫 [[Class]] 的内部属性，是规范在第 8.12 节里规定的“实现定义的分类字符串”。它不是属性，读写不了，语言层面唯一窥探它的窗口就是 Object.prototype.toString：引擎按对象的 [[Class]] 拼出 [object 类别名] 这样的字符串。用 call 借来调用，就能拿到比 typeof 细一档的结果。

注意前两个：Undefined 和 Null 这两个语言类型的值，toString 特判返回 [object Undefined]、[object Null]，而不是直接报错——这正是它能当全类型判定器的原因（规范 15.2.4.2 专门处理了这两种输入）。

但这个方法不可全信，坑有三类。第一，宿主对象不受规范管辖：ES5 只要求实现给宿主对象的 [[Class]] 选一个“最贴切的字符串”，于是同一个 document，在 IE 8 里是 '[object Object]'，在 Chrome 里是 '[object HTMLDocument]'；IE 里部分 DOM 方法转成字符串甚至是 '[object Unknown]'。跨浏览器判定 DOM 节点不能靠它，老老实实退回 nodeType 加 tagName，或者先判标准浏览器支持的 instanceof Element 再兜底看 nodeType 属性。第二，老 IE 连内置对象的 [[Class]] 都不规矩，arguments 报的是 [object Object] 而非 [object Arguments]，想跨浏览器把“类数组”与“真数组”分开，还得配合 length 属性与 callee 的存在一起看。第三，[object Object] 的粒度仍然太粗——自定义构造函数的实例、Object.create(null) 的裸对象、字面量对象，全都返回同一字符串，想单独认出“字面量对象”必须再补一层原型链检查。实操经验是一句三分法：Array、Date、RegExp、Error、Function 这些内置具体类的结果跨浏览器可信；报 [object Object] 的要再过一道原型检查；宿主对象干脆别用它来判类型。jQuery 的 $.type 与 $.isPlainObject 正是“toString 打底、再对 Object 细分”这一思路的工业实现，笔者在《jQuery 的 extend 与工具方法扩展》里拆过 isPlainObject 的源码，此处不展开。顺带一句，instanceof 走的是原型链而不是 [[Class]]，判定数组时还有跨 frame 失灵的著名问题，机制上属于另一篇话题（new 与原型链那两篇旧文已详述），本文的判定工具一律以 toString 打底。

ToPrimitive：隐式转换的总闸门

从这一节开始进入本文的主线。四个抽象操作里，ToPrimitive 是绝大多数怪现象的第一现场，规范位置是 9.1 节加上对象内部方法 [[DefaultValue]]（8.12.8）。语义很简洁：输入不是对象，原样返回；输入是对象，就带着一个提示（hint）去调 [[DefaultValue]]，按下面的流程拿一个原始值出来。

flowchart TD
  A[ToPrimitive 输入值与 hint] --> B{输入是对象吗}
  B -->|不是| C[原样返回]
  B -->|是| D{hint 是什么}
  D -->|hint 为 string 或无 hint 的 Date| E[先调用 toString]
  D -->|hint 为 number 或无 hint 的其他对象| F[先调用 valueOf]
  E --> G{返回的是原始值吗}
  G -->|是| H[拿到结果]
  G -->|否| I[再调用 valueOf 兜底]
  I --> J{是原始值吗}
  J -->|否| K[抛 TypeError]
  J -->|是| H
  F --> L{返回的是原始值吗}
  L -->|是| H
  L -->|否| M[再调用 toString 兜底]
  M --> N{是原始值吗}
  N -->|否| K
  N -->|是| H

三个关键结论。第一，hint 决定调用顺序：string 提示先 toString 后 valueOf，number 提示先 valueOf 后 toString，每一步都要求返回值是原始值，两个方法都给不出原始值就抛 TypeError。第二，hint 缺省（规范里叫 default）时按 number 处理，唯一的内置例外是 Date：Date 对象在无 hint 时按 string 处理。第三，普通对象的 valueOf 继承自 Object.prototype，默认返回对象自己——不是原始值，所以按 number 方向转换时普通对象总会落到 toString 兜底那一步，得到 '[object Object]'；数组、日期的 valueOf 则各有定义。

ToNumber、ToString、ToBoolean 三条基础转换

ToPrimitive 出来的原始值，接下来要喂给三个基础转换。它们的规范定义（表 12、表 13、表 11）就是整个转换系统的全部秘密，值得逐条抄成表格再逐条验证。

ToNumber（9.3）的语言类型层规则：Undefined 转 NaN，Null 转 +0，Boolean 的 true 转 1、false 转 +0，Number 原样，String 走一套文法（9.3.1），Object 先 ToPrimitive(number) 再递归转。null 得 0、undefined 得 NaN 是最常背反的一对，务必记死方向：null 是“空但确定存在”，所以有数值 0；undefined 是“压根没有”，所以不可表达为数。字符串的转换规则是：允许前后空白，空串或纯空白串转 +0，可识别十进制（可带正负号、可带指数、允许 001 这样的前导零）与 0x 开头的十六进制，其余一律 NaN。数组的怪结果全部能两步推出：先 ToPrimitive(number)，数组的 valueOf 返回自己不是原始值，落到 join 语义的 toString，于是 [] 变空串、[1] 变 '1'、[1, 2] 变 '1,2'，再走字符串规则：

ToString（9.8）的特别之处是它对 null 和 undefined 直接返回字符串 "null"、"undefined" 而不抛错——这是它比 null.toString()（SyntaxError/TypeError 伺候）可靠的地方，也是工具函数里偏爱 String(x) 的原因。对象的转换走 ToPrimitive(string)，注意与 + 的无 hint 方向不同。数字的字符串化（9.8.1）按规范是“有效数字、小数点、指数三段决定格式”，落到可记忆的阈值上：绝对值大到需要超过 21 个整位数、或者小到 0.000001（1e-6）以下第一个有效位之前还有零，就切换成 e 记法：

顺带把两个更底层的近亲操作也交代清楚，后文的位运算取整会用到。ToInteger（9.4）是 ToNumber 之后向下取整，NaN 归 +0，服务于数组长度、重复次数这类“个数语义”；ToInt32/ToUint32 则是在 ToInteger 之后把数值模 2^32 折回 32 位区间，|、~、<< 这类位运算符两头用的就是它。负零也值得单独一提：0 * -1 会得到 -0，它的 ToBoolean 是 false，String(-0) 把负号直接丢掉写成 '0'，但 1 / -0 仍然是 -Infinity——Number 类型里“数学上的零”和“工程上的零”是两回事，这是后文 === 那处例外的伏笔。

ToBoolean（表 11）只有一句话：Undefined、Null 恒为 false；Number 里 +0、-0、NaN 为 false；String 里空串为 false；对象恒为 true。把假值集合数出来正好七个：false、+0、-0、NaN、''、null、undefined，其余全真——'false' 是真，[] 与 {} 是真，包装了 0 的 new Number(0) 也是真。真值判断在条件分支里的各种用法（|| 默认值的坑、!!、document.all 这个规范特例），笔者在《JavaScript 布尔值与真假判断》里已经展开过，本文不重复，只保留上面这张结论表，因为它就是 ToBoolean 的完整定义。补一句边界感：表 11 管辖的是语言值本身的转换，条件判断里遇到“对象却是假值”的灵异现象，要么是宿主特例（前文提过 document.all），要么就是拿到的根本不是对象——先查类型，再谈规则。

加号与关系运算符的转换规则

== 的完整推导与 === 的边界

宽松相等（11.9.3）的判定顺序是十条，值得逐条抄下来，因为所有“诡异等式”都能按图索骥：先看是不是同一类型（同类型时按 1.c 的数值语义、1.d 的字符串逐字符、1.f 的引用同一来比）；然后 null 与 undefined 互相等、且不与任何别的值等；数字遇字符串、字符串遇数字，把字符串 ToNumber；任何一边是 Boolean，先把它 ToNumber；对象遇 String 或 Number，对对象做不带 hint 的 ToPrimitive 再递归；剩下的跨类型组合一律 false。

按这十条把 [] == ![] 拆干净——该修正的是“它怎么可能是 true”的直觉，推导全程合法：

同一条链路上，[] == 0、[] == ''、['10'] == 10、new String('a') == 'a' 为真都不意外；意外的是它的非传递性：两个内容相同的 String 包装对象互不相等（各自是独立引用），却都等于那个原始字符串——规范 NOTE 里自己承认 == 不是等价关系。再叠加 Date 在无 hint 时按 string 的规则，就有了 d == +d 为 false。再用十条推三道三十秒就能解决的题：false == '0' 为 true，先 false 转 +0、再 ‘0’ 转 0，数字相等自然成立；null == undefined 为 true，但它俩各自再与 0、''、false 比较一律 false，因为第 2、3 条把 null 与 undefined 锁死在互相等这一档，后面的转换规则根本不给别的路径；[] == true 为 false——第 7 条把 true 转成 1，[] 压成 ''，'' 转 0，最后比的是 0 与 1，堂堂正正地 false。这四道连同 [] == ![] 正好拼齐面试常客的全部类型组合。工程结论干脆利落：== 的合法使用场景只有一种（见下文 == null），其余一律 ===。

严格相等（11.9.6）不做任何转换，类型不同直接 false，但规范仍给它留了两处“违反直觉”的例外，都在 Number 的语义里：+0 === -0 为 true（数学上的相等关系被保留），NaN === NaN 为 false（IEEE 754 规定 NaN 与任何值都不等）。前者意味着 x === 0 分不清正零负零，需要时得用 1 / x 的符号补判——检测写法是 x === 0 && 1 / x === -Infinity 的组合，这在处理坐标轴翻转方向、Math.atan2 这类带符号语义的场景里才真正用得上；后者意味着判 NaN 不能靠相等运算，ES5 时代的标准姿势是全局 isNaN，可它自带 ToNumber——isNaN('abc')、isNaN(undefined) 都是 true，会把“不能转成数字”误报成“是 NaN”。而且全局函数可以被覆盖污染，兜底方案要绕开它：

显式转换：每个坑的标准答案

显式转换函数是抽象操作的语言入口，但每一个都有自己的坑，逐个说清工程口径。判断的标准只有一条：显式转换应当是隐式规则的可预测写法，如果连它都要靠背特例，那说明这一族函数不适合当前场景，换一个并配合校验，而不是继续加技巧。

Number(x) 就是 ToNumber 本尊，行为完全符合上文表 12，用它做“字符串转数字”时注意空串与空白串会安静地变成 0，'1a' 这类脏数据返回 NaN 而不是报错——这反而是优点：拿到 NaN 说明数据不合法，可以集中校验。一元 +x 与 Number(x) 同源，x - 0 借减法触发 ToNumber，三者对数字字符串等价，但都不做“截断解析”。

parseInt 则是另一套语义：先把参数 ToString，跳过前导空白，贪心地吃“当前进制下的合法数字前缀”，吃不下就停。所以 parseInt('1.2.3') 得 1，parseFloat('1.2.3') 得 1.2（它能多吃一个小数点），而 parseInt('1px') 得 1、parseInt('px1') 得 NaN。它的头号坑是第二个参数：ES3 时代实现各异，ES5 规定缺省按十进制（带 0x 前缀识别十六进制），但老 IE（8 及以下）在当年仍按八进制处理前导零——parseInt('08') 在那些浏览器里返回 0，笔者在生产环境被这一行配置代码咬过。结论没有商量：基数永远显式写。

位运算取整（~~x、x | 0）的真相是 ToInt32：先 ToNumber，再向零取整，最后按 32 位回绕。它比 parseInt 快是当年流传的说法，但代价是溢出——~~2147483648 返回 -2147483648，4294967296 | 0 直接归 0。凡数字可能超出 32 位范围（时间戳、订单号），禁止用位运算取整。

Date 的显式转换是和 parseInt 并列的重灾区。规范把 Date.parse 与 new Date(字符串) 解析“非 ISO 8601 形式字符串”的分支定为实现相关行为，当年 '2014-11-16 18:17:33' 这种空格分隔的格式在 Safari 与老 IE 里得到 Invalid Date、在 Chrome 里却正常，就是这一条授权出来的。即便改用 ISO 形式，纯日期 YYYY-MM-DD 按 UTC 解析、带时间的形式按本地时区解析，跨时区的报表还是能翻出差错。可靠的工程做法是：接口传数字时间戳，或者把年月日拆成字段由前端逐字段 new Date(y, m, d) 重建（月份从零起算这个老坑照旧要防）。再补一对函数的行为差：Number(true) 得 1，而 parseInt(true) 得 NaN——后者先 ToString 成 'true' 再一个数字都吃不下。写参数转换函数时别把这两个函数当同义词混用。

String(x) 与 x + ''：null/undefined 都安全（得 'null'、'undefined'），差别只在对象走哪个 hint——String(o) 带 string 提示先 toString，o + '' 无 hint 先 valueOf，上文已验证两者结果可以不同。对象一律用前者。Boolean(x) 与 !!x 都是 ToBoolean，选一个统一风格即可。

实现细节有两处值得说明。其一，trim 手写成正则，是因为 String.prototype.trim 属于“语言层有、宿主层没有”——IE 8 及以下不支持它，当年 $.trim 替所有人背过这个锅。其二，toNumber 直接拒收对象与数组，正是为了堵死第三、四节反复演示的那条隐式通道：[] 变 0、[1] 变 1 这种“合法但荒谬”的结果，不该从数值转换函数里流出去——脏数据进不了算术，也就进不了线上事故。

有了这套工具，团队规约就是顺水推舟的十条，每条都有本文的推导做后盾：比较一律 ===/!==，唯一豁免是 == null；算术前先显式转换（Number 或一元 + 配 toNumber），禁止依赖 + 的隐式行为做数值运算；parseInt 必带基数；需要取整用 Math.round/round，禁止对可能超 32 位的数用 ~~；字符串输出统一 String(x)，禁止 x + '' 处理对象；格式化数字用 round 而非 toFixed 直接出数值，toFixed 只用于“接受其舍入行为”的展示场景；isNaN 必须搭配 typeof 或换用 isNaNValue；除法与数组下标前用 isInteger 校验；布尔上下文禁止 !! 之外的花招（!~、x * 1 这类技巧一律打回）；金额和坐标这类精度敏感值在传输层就用字符串或以分为单位的整数，不在 JS 浮点里裸奔。

== null 为什么是少数可以接受的例外？因为它的语义由规范 11.9.3 的第 2、3 条写死：只有 null 与 undefined 互相等，且规范保证二者不与任何其它值相等——x == null 精确等价于 x === null || x === undefined，不多不少，永远不会把 0、空串、false 卷进来；写长式反而容易漏掉一支。jQuery 源码里大面积使用它，前提是团队理解上述推导。豁免仅限 null 这一处，== undefined 同理成立，但 == true、== '' 一个都不许。

规约的落地也有条 2014 年可行的路径：把 == true、== '' 这类无豁免写法和不带基数的 parseInt 调用交给 jshint 的 eqeqeq 与 radix 规则先自动拦截，机器能查的机械项不要消耗人工评审；类型判定工具集沉到公共库里，让业务代码用它们比用自己写的判断更省事——要让正确的路恰好是最短的路，规约才能在评审压力下活下来。

最后用一次真实排查把全文串起来。某版报表页的“总金额”与明细行合计始终对不上，差的不是整数。回溯代码，累加语句写的是 total += data[key]，而某个接口字段改成了数字字符串，+ 在“一边是 String 即拼接”的规则下悄悄从加法换成了接龙——这是第五节的运算符分叉；第一版修复给两边都包上 Number()，加法是回来了，可平均值这栏数目不对：缺字段传回的 null 被无声转成 0 当成一个合法值参与运算，这正是第四节表 12 里“null 得 0、空串得 0、唯独 undefined 得 NaN”的那对方向感。最终用上面的 toNumber(v, null) 加 type 校验把脏数据挡回调用层，坏值直接拒绝而不是凑数。三处误判对应正文三条规则，可见这套“零散怪题”其实是同一条因果链：把链理顺，排查是推导，不是背题。

小结

本文把 ES5 的隐式转换还原成了一个可推导的规则系统，三条原则贯穿全部结论：第一，运算符决定 hint——+ 与 == 不带 hint，关系运算符与算术带 number hint，String() 带 string hint；第二，hint 与对象自身的类别决定 ToPrimitive 先调 valueOf 还是先调 toString，普通对象无 hint 按 number，Date 是唯一的例外按 string；第三，拿到原始值之后，才轮到“一边字符串即拼接、否则转数字、双字符串才字典序”这几条末端规则。真值表只有七个假值，=== 只有正零负零与 NaN 两处例外，parseInt 永远带基数，超过 32 位禁止 ~~。背下这十几行推导所需的前提，而不是背题目——下次遇到 [2] < [10] 是 false 这种事，你能在十秒内从规范里推出来，这比记住答案值钱得多。
