浏览器渲染流程详解

关于渲染，市面上已经有不少”优化清单”了，本文不想再来一份。它要做的事情是把浏览器内部的渲染流水线本身讲透——从字节流到屏幕上的像素，每一环是怎么运转的、引擎里对应什么代码结构——然后用今年项目里真实发生过的几次故障逐一复盘：白屏、整页重排、布局抖动、层爆炸、动画卡顿、主线程冻结。每一条故障背后都能精确指回流水线上的某一环。适合写过不少页面、却说不清”一帧到底是怎么来的”的同学；读完你应该能在 DevTools 的 Timeline 里看懂每根柱子属于哪一段，遇到渲染问题时有一套固定的排查顺序。

先把流水线摊开：从字节到像素

浏览器渲染不是一次性动作，而是一条可以流式推进的流水线。HTML 字节一边到达，解析器一边工作：先按 BOM、meta charset、响应头的顺序判定编码，解码成字符流；分词器（tokenizer）按 HTML5 规范定义的状态机把字符流切成标签与文本；树构造阶段再按同样的状态机把节点挂到 DOM 树上。这三步都是增量的，网络层送来一块字节就推进一段，所以”文档还没下完页面就出来了一部分”是正常现象。

解析过程中有两个关键的岔口。遇到 <link rel="stylesheet">，解析器自己不停，把下载任务派给网络层继续往下走；但渲染这条线会被它拖住——CSS 没有全部就绪之前，浏览器不会画第一帧，这是渲染阻塞。遇到没有 defer 或 async 的 <script>，解析器必须停下：脚本随时可能用 document.write 改写后面的文档流，不执行完就没法确定接下来怎么解析，这是解析阻塞。CSS 与 JS 卡的是流水线上不同的位置，后面两个白屏案例的根源都在这里。

CSS 的下载与 HTML 并行进行，下完即由 CSS 解析器构建成 CSSOM。CSS 解析是规则驱动的，可以整表处理，但层叠与继承决定了它必须”全部算完”才可信：同一元素被多条规则命中时按特异性与来源顺序定输赢，可继承属性的值要沿树往下传。浏览器不敢拿半截的 CSSOM 去渲染，否则后面的覆盖规则一来，前面的绘制就全错了。

DOM 与 CSSOM 就绪后合并成渲染树。以 WebKit 为例，这棵树上的节点是 RenderObject（Blink 从 Chrome 28 分叉后一路推进到今年的 38 版，内部把这套结构重构成了 LayoutObject，概念仍然对应），它只收”要画出来的东西”：display: none 的子树整个不进树，<head> 里的节点也不进树。渲染树往下是布局（layout）：从根开始递归算出每个盒子的坐标与尺寸；然后是绘制（paint）：按绘制顺序把背景、边框、文字、图片一笔一笔落到位图上，WebKit 里这一步走的是 GraphicsContext 抽象，Chrome 一线背后接的是 Skia，Safari 一线接的是 CoreGraphics；最后是合成（composite）：若干已经光栅化好的图层由合成器拼成屏幕上的最终画面。

这条线记住三件事就够了：解析与渲染是两条可以互相拖累的线；layout 与 paint 之间是严格先后关系；合成是”搬运现成位图”，本身不重新绘制内容。后文所有故障都是这三句话的推论。

再补一个让这条流水线”看起来快”的内部角色：预扫描。主解析器被同步脚本按住的这段时间里，WebKit 里紧跟其后的一个轻量扫描器（预解析器，Firefox 那边叫推测性解析）并没有闲着——它用简化状态机往后偷看文档，把沿途遇到的 <img>、<link>、<script> 的外部资源提前派发给网络层。所以 Timeline 里常见 HTML 只解析了一半、整页图片已经开始下载的景象。这个机制有两面：好的一面是脚本阻塞解析时，后面的资源大多已经在路上，等待链不至于串成纯串行；坏的一面是它只认 HTML 源码里的标签，用 document.createElement 动态插入的脚本、样式、图片在它眼里不存在，必须等 JS 真跑起来才第一次被网络层知道。今年排查”首屏图慢半拍”时发现运营同学把首屏大图挪进了一个动态加载的轮播组件里，等于主动把这张图从预扫描的视野里抹掉了——静态写在 HTML 里和动态插进 DOM 里，在流水线上是两个完全不同的起跑位。

还有一个值得单独点出来的对照：解析是流式的，但渲染是否”边解析边画”取决于渲染阻塞集合是否清空。head 里的 CSS 到齐后，已解析出的部分 DOM 完全可以先走一遍布局绘制摆上屏幕，解析器继续往下，后面内容再增量补画——桌面浏览器今年就是这么做的，这也是”页面先出现上半截再慢慢长出来”的机制来源。理解这一点，才明白白屏案例里”屏幕一片白”绝不是浏览器画不出来，而是它被规则摁住不敢画。

直觉诊断是”两个 CSS 阻塞渲染，合并一下”。但打开 Timeline 一看，白屏期间的问题比这复杂。Chrome 的 Timeline 面板（其前身即 Web Inspector 里那个）会把 Loading、Scripting、Layout、Recalc Styles、Paint、Paint Setup 这些事件画成一根根彩条，把时间轴拉开后能看到完整的因果链：两个 CSS 请求几乎同时发出、先后到达；jquery 的请求也早就派发了，可它的执行条一直等到第二个 CSS 落地才出现；紧接着是一条很长的 Recalc Styles 和一条粗的 Layout；再之后才是第一根 Paint 条。

这里的关键机制很多人没意识到：同步脚本必须等它前面的样式表全部加载完毕才能执行。原因很朴素——脚本运行起来随时可能调 getComputedStyle 或读 offsetHeight，浏览器必须保证这些读取的答案是”完整的 CSS 应用之后”的答案。于是这条等待链成立了：CSS 未就绪 → 脚本不能执行 → 解析器停在脚本上 → 后面的 DOM 建不出来 → 首帧绘制遥遥无期。外链 CSS 阻塞的是渲染，但样式后面的脚本把这份阻塞转嫁给了解析，白屏时间等于最慢那个 CSS 的下载时间加上脚本执行时间，而不是”CSS 下完就画”。

所以复盘结论有两条。其一，看 Timeline 判读白屏时，先找第一根 Paint 条，再看它左边最近的那根长条是 Network 等待、Recalc Styles 还是 Scripting——三者对应的病灶完全不同，分别是资源慢、样式规模失控、脚本卡解析。其二，样式与脚本在头部的相对顺序是要算账的：CSS 之间夹脚本，等于给每个 CSS 单独串行了一遍解析阻塞，脚本应当整体排在所有 CSS 之后，或者干脆后置加 defer。IE 10 以后的 performance.timing.msFirstPaint 可以拿来打真实用户的首绘点，和 loadEventEnd 一起上报，白屏问题才不再是”用户说慢”。至于 defer 与 async 的时序细节，旧文《脚本加载策略：defer 与 async》已经讲透，这里不重复。

把这次的时间账摊开看：两个 CSS 合计 190 KB（Gzip 后），慢的一方在宽带下约 700 毫秒到达；jquery 与 activity.js 本身下载各只用一百多毫秒，但它们的执行条全部压在 CSS 之后出现；内联的初始化逻辑加 Recalc Styles 又吃掉 300 多毫秒——首绘定格在一秒六。修法的优先级也是按这条链排的：先合并两个 CSS 减一次往返，再把两个脚本整体挪到 </body> 之前（不 defer 也先解掉”替 CSS 背锅”的问题），最后把 activity.js 里操作首屏 DOM 的部分改成 setTimeout(fn, 0) 推后一拍，让浏览器先交出第一帧再改样式。三招之后首绘回到 800 毫秒上下。这里没有用到任何”高级”手段，全部是把 Timeline 上的等待链一段一段剪短——白屏优化的功夫从来不在资源本身，而在它们互相等待的方式。

为什么同样是”移动一个元素”，left 与 transform 的代价差着数量级？要看失效范围怎么传播。left 是布局属性，一改它，该元素在布局树里的几何就变了，而布局是自上而下的递归：父容器的尺寸、后续兄弟节点的文档流位置、乃至整页的滚动高度都建立在”它占多大地方”这个前提上，所以浏览器必须从这个节点开始把受影响的整棵子树乃至整页重算一遍。transform 则发生在布局完成之后——它不改变”这个盒子占多大地方”，只改变”画到屏幕哪里”，对布局树而言元素纹丝不动，脏范围被天然关在这个元素自己身上。这就是为什么布局属性是”动了就牵全身”，而变换属性是”自己挪自己的”。绘制段也有同样的分档：改一个元素的颜色只让它自己的矩形重画，Timeline 里对应一小块脏矩形；给宽列表单元改 padding，脏矩形可能铺满整屏，重绘的像素量大到 paint 本身成为瓶颈——这类情况下连”只重绘”这一档都省不掉，只能往”纯合成”那一档逃。轮播后来还遇过一例次生问题：每张幻灯片都带了提层变换，七八层纹理叠着滑动时合成器自己反而变慢，最后是把静止帧的变换撤掉、退回普通绘制才稳住——提层是把账从主线程挪到显存和合成器，不是免单。

这次排查里还顺带挖出两个更隐蔽的”读”。一个是 getComputedStyle(el)：它名义上只是取样式，但只要取的属性跟几何有关（height、top 这类），效果与读 offsetHeight 完全等价，当场结算一次布局；当年团队里有人拿它在 hover 脚本里”判断当前状态”，等于每次鼠标移动都补一次布局，后来统一改成把状态记在 JS 变量里。另一个是 scroll 事件回调：滚动时事件每秒能打几十个，每个回调里只要有一次几何读，就是一次每帧强制布局——我们那个列表页修完循环之后仍然微卡，就是因为一个”滚动时显示回到顶部按钮”的小脚本在 onscroll 里读了 document.body.offsetHeight。把它换成 setTimeout 里节流加缓存值之后才干净。规律是：凡是高频路径（循环、动画回调、scroll 与 resize 监听、事件委托的回调），都该问一遍里面有没有读几何。这些读法本身没有错，错的是它们出现的频率和它们身后挂了多少笔未结算的写。

图层与合成：一帧画面在层里的旅行

上面三个复盘都发生在主线程的流水线里，接下来这段是本文的技术重心：paint 之后、屏幕之前的那一段——图层与合成。

浏览器并不总是把整页画进同一张位图。满足某些条件的元素会被”提升”成独立的合成层（compositing layer），有自己的位图、自己的坐标空间，合成线程最后把这些层按顺序叠成最终画面。以 2014 年的内核实现，提升条件大致是这几类：带 3D 变换的元素（translate3d、rotateX 这类，注意 2D translate 在 iOS 的老内核上并不提层）；opacity 做动画的元素；video、canvas、WebGL 这类”内容不是页面自己画的”元素；position: fixed 的元素；overflow: scroll 且（在 iOS 上）加了 -webkit-overflow-scrolling: touch 的滚动容器；以及一个容易被忽略的规则——与已提升层发生交叠的元素会被连带提升，否则遮挡关系在层与层之间会算错。顺带说一嘴，will-change 今年 5 月才出第一份草案、Chrome 36 刚有第一个实现，Safari 完全没有，所以当年强制提层仍然只能靠 3D 变换这个老办法。

提层为什么要给”特权”？因为层的价值在于隔离重绘范围。一个层的位图一旦光栅化好，层内只要几何与内容不变，挪动它、改它透明度都不需要重新 paint；页面其余部分再翻江倒海，也只影响各自的层。合成线程的工作因此极其便宜：贴几张纹理，发一条 draw 指令，它不在主线程上，主线程正忙着跑脚本也不拖累它——这是滚动和 transform 动画在别人卡顿时还能保持流畅的全部原因。代价是每层的位图都要真实地占内存，尺寸约为”层的边界盒乘设备像素比”，一张全屏层在 Retina 屏上就是 300 多万像素、12 MB 上下。

故障就出在这里。一个移动端长列表页，开发同学为了给每一项开滚动加速，给列表容器和每一个卡片都加了 translateZ(0)，本地测着挺顺，上线后 iPhone 5 上滚几十屏就白屏闪退。用 Timeline 旁的渲染调试选项一看便知病灶：勾选 Show layer borders 后屏幕上密密麻麻全是黄框——几百个卡片各成一层，每层都要一份纹理内存，加上光栅化任务的调度开销，iOS 的内存压力直接让页面被系统回收。”层爆炸”的可怕之处在于它的触发是渐进的：滚得越深、渲染过的层越多，内存水位越高，直到某一次申请纹理失败。当年我们定下的纪律很简单：层是给”内容不变、只有位移或透明度在变”的东西准备的，内容每次都要重画的东西提层只会更贵；列表项永远不该有层，该有层的只有滚动容器这一个。用 Show paint rectangles 看绘制区域也是同一思路——绿色代表该区域只画了一部分、被加速了，满屏黄色代表大面积重绘，两者配合基本能判断”这帧的钱花在了哪一段”。这些手段在移动滚动场景下的具体运用，《移动端滚动方案优化》里已经展开过，本文只补机制。

再把两个容易混淆的”层”分开。渲染树里其实有两套层结构：一套是 WebKit 里 RenderLayer 这类的绘制层，管的是元素画出来的前后顺序——背景、块、浮动、定位元素、z-index 形成的堆叠上下文，全都在这套层里排队，它决定遮挡关系但不决定内存；另一套才是合成层，是绘制层中少数被单独提出来、拥有独立位图的成员。一个元素提层之后，它的子树里凡是自己又满足提升条件的，会在合成层树上成为它的孩子；更微妙的是前面提过的连带提升——一个没资格提层的元素，只要和某个已提升的层发生交叠，为了不画错遮挡就得自己也被提上去。这就是为什么一个页面明明只写了三五个 translateZ(0)，DevTools 却报出几十层的另一个原因：透明视频浮层把整个头部分支”传染”上了。合成层的位图也不是整张无限大的：Chrome 桌面端的实现里，一个层的位图按瓦片（tile）切分管理，滚动时只有新进入视野的瓦片需要光栅化，旧瓦片可以平移复用，这就是”滚动便宜”的工程学真相；但瓦片是越滚存得越多，上限由纹理尺寸与内存预算管着，前面 iPhone 5 那起白屏就是预算顶破之后系统直接杀进程。所以层数要数得出来才算管住：每层边界盒面积乘设备像素比的平方，再乘份数（前后缓冲），这笔账在当年 512 MB 内存的手机上必须手动心算。

复盘四：rAF 与 setTimeout，差的不是那 16 毫秒

轮播改完 transform 后还剩最后一处不平：手动拖拽的跟手动画用的是 setTimeout 递归 16 毫秒，偶尔一顿。这就要说到 vsync。多数屏幕每秒给出 60 次垂直同步信号，浏览器通常在 vsync 到来时安排一次”帧的流水线”：处理输入、跑 requestAnimationFrame 回调、样式、布局、绘制、提交合成。setTimeout 的回调时刻跟这个节拍没有任何约定——它落在窗口前半段就赶上这帧，落在后半段就等下一帧，于是出现大量”两帧并作一帧”的抖动；rAF 则是把自己注册到流水线的那个固定工位上，回调写完样式紧跟着就是本帧的样式与布局计算，天然对齐。

两者的另一个实质差别在后台标签页：rAF 在页面不可见时整个停掉，setTimeout 只是被节流到每秒一次，时间照烧。对比代码可以这样写：

轮播那次改完 rAF 后还留了一条尾巴值得记录：动画在”看起来该流畅”的页面上仍然偶发跳帧，Timeline 展开后发现 rAF 回调本身没问题，是页面上另一处 setInterval 每 250 毫秒跑一次的轮询在捣乱——每次轮询都读一次几何，强制布局恰好插在两帧之间，把 rAF 攒好的节奏打断。这个案例把 rAF 的真实语义讲全了：rAF 只保证你自己的回调排在重绘前，不保证那一帧的预算不被别人花掉。换句话说，rAF 解决的是”对齐”，对齐之后每一帧还剩多少毫秒给样式、布局、绘制，取决于主线程上还有谁。当年我们给团队立的规矩是：动画页面上禁止任何带几何读取的轮询，全局定时器要么合并进统一的 rAF 循环按帧调度，要么只碰纯 JS 数据。帧层面的证据直接看 Timeline 底部的帧率标尺就够了：绿色帧是合成准时交付，出现黄色长条表示主线程超过一帧预算，红色表示这一帧直接丢了几张 vsync——把丢帧时刻和事件记录对齐，凶手通常一眼可辨。

复盘五：把主线程冻住的两个老伙计

第五起事故是一次”页面点不动”的报障，值得复盘是因为凶手藏在渲染流水线之外、却又影响流水线之内：JS 执行、样式计算、布局、绘制全部排在主线程这一条队上，前面任何一段不被让开，后面的渲染就寸步难行。

document.write 在解析期间插入的内容会真的进入文档流，但被写入的那个外链脚本又是同步脚本——于是解析器在这里停得更死了：先等这段内联执行，再等 track.js 下载，再执行它，然后才继续解析后面的 DOM。广告域名被运营商劫持慢了一秒，页面就多白一秒。更糟的情况是有人在 window.onload 回调里调 document.write：文档解析早已结束，这一写等于把整页 DOM 全部推倒重建，用户眼睁睁看着页面”闪回”成另一张白屏。复盘结论：解析期间的 document.write 每一次都在给等待链加一环，解析结束后的 document.write 是毁灭性的，两者都该被动态插入节点替代。

元凶之二是同步 XHR。一个后台页面在 DOMContentLoaded 里用 xhr.open('GET', url, false) 拉配置，内网测试一切正常，走代理的办公网里这个接口要三四秒。同步 XHR 把主线程整个占住，这期间样式算不了、布局走不动、paint 更无从谈起，Timeline 里是一根几秒长的 Scripting 条横在所有渲染事件前面。把它改成异步回调之后，”白屏后一次性跳出来”变成了”结构先出来、内容后补上”——流水线还是那条流水线，区别只是你不再堵住它。DOMContentLoaded 与 load 该挂哪个、迟到的脚本怎么补判状态，旧文《DOM contentloaded 与 load 的区别》讲过，本文不重讲；本文的教训是反过来的：事件挂得再准，也要看主线程当时腾不腾得出手。

这两起故障放在一起复盘，是因为它们暴露的是同一条规则的两个侧面：主线程的队上没有优先级，谁先排进来谁先执行，后面的样式、布局、绘制一律顺延。document.write 卡的是”队首还没排的解析”，所以症状是白屏加长；同步 XHR 卡的是”已经排好的第一次绘制或交互”，所以症状是内容出得来但点不动。Timeline 里两者同样好认：一根几秒长的 Scripting 条，底下挂着的堆栈指向 write 或指向 xhr 而已。顺带记录一个当年的土办法：怀疑某个第三方脚本是凶手时，把它用 setTimeout 包一层延迟注入——脚本从”解析同步路径”挪到”未来某个任务”里，解析与首绘立刻绕开它；虽然执行仍然占主线程，但至少不再卡解析器，白屏与不可交互被拆成了两个可以分别度量、分别处理的问题。治标不治本，但在对方代码你改不动的现实里，这是把等待链剪断的最短一刀。

一帧的排班表：主线程与合成线程

把前面所有机制装进一张时刻表，渲染流程才算真正讲完。输入事件、rAF 回调、样式计算、布局、绘制都在主线程上按固定次序串行走；合成线程拿到各层位图后独立工作，绘制记录（在 Chrome 内部表现为 paint op 列表）经提交、光栅化，最终随下一个 vsync 上屏。

sequenceDiagram
  participant V as vsync 信号
  participant M as 主线程
  participant C as 合成线程
  V->>M: 一帧开始
  M->>M: 派发输入事件 click touch
  M->>M: 执行 rAF 回调与脚本
  M->>M: Recalc Styles 样式计算
  M->>M: Layout 布局
  M->>M: Paint 生成绘制记录
  M->>C: 提交绘制记录 Commit
  C->>C: 各层光栅化 Raster
  C->>V: 等待下一个 vsync
  V->>V: 合成上屏
  M->>M: 期间 JS 若长跑 则下一帧全部顺延

几个由此推出的读图方法。脚本一长，后面所有渲染事件顺延，这就是”一个 200 毫秒的循环让整页卡住”的形态；输入事件永远排在 rAF 之前，所以 rAF 里再读几何属性读到的一定是”上一帧布局加本帧写入”混合后的最新结算；合成线程只在 Commit 之后登场，主线程忙得交不出新记录时，它能平移的只有已有图层——这正是滚动还能继续而动画停摆的原因。桌面 Chrome 今年仍以软件光栅化为主，GPU 光栅化刚在 canary 上以开关形式露面；iOS Safari 则把层直接交给 CoreAnimation 在 GPU 上合成，两家实现分歧很大，但”主线程排班、合成线程搬运”的骨架一致。关键渲染路径上各段的资源账怎么算、预算怎么分配，《网页性能优化全景：关键渲染路径》已经给过方法，本文只补了它没有展开的内部机制。

小结：遇到渲染问题的排查顺序

复盘完五个故障，把它们倒过来整理成一套排查动线。第一步，在 Timeline 里找第一根 Paint 条确定首绘位置，看它左边压着什么长条——Network 等待、Scripting、Recalc Styles 还是 Layout，四类长条分别指向资源、脚本、样式规模、布局代价四个病灶；第二步，分辨这笔账属于哪一档：只重合成、要重绘、还是要重排，档位决定修复手段的价值上限；第三步，找触发点，Layout 条点下去能看到触发它的脚本堆栈，一串紧密 Layout 基本就是读写交替；第四步，才轮到选降级手段——合并读写、属性换档、削减图层、脚本挪出解析路径。层的问题用 Show layer borders 与 Show paint rectangles 现场取证，量化的结论交给 Timeline 的帧数据而不是眼睛，真实用户侧用 performance.timing 加 msFirstPaint 打点兜底。渲染流程本身没有什么玄学：它就是一条可以被解析与脚本打断、可以被属性选择绕开、可以被图层切分的流水线，故障从来不是”浏览器画得慢”，而是我们让它重复画了不该它再画的段。
