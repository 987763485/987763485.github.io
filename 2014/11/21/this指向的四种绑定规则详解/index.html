this 指向的四种绑定规则详解

this 大概是 JavaScript 里最容易被背错的一个词。很多人把它记成”函数自带的属性”，于是每遇到回调、事件、构造函数就要重新猜一次，猜错的地方还往往安静地跑着不报错。本文换一个说法：this 是引擎在一次调用发生时绑定的执行上下文，规则完全确定，可以固化成一套算法。读完你应该能立刻判断任意一行代码里 this 指向什么，也能把组件里那些”莫名丢失”的引用修干净。全文只涉及 ES5，代码都在 Node 和浏览器控制台实测过。

this 不是函数自身的属性

先破一个误解：函数对象上并没有一个叫 this 的属性，this 也不参与原型链查找。引擎在每次调用函数时创建一个执行上下文，里面有一个隐式的 this 槽，它的值由调用点的语法形式决定，而不是由函数写在哪里决定。

上面三段说明一件事：函数对象只有一个，this 却有无数个候选。所以”这个函数的 this 是什么”是个不成立的问题，成立的问题是”这一次调用的 this 是什么”。判定只看调用点，这是全文的地基。

其二，ES5 里没有动态作用域，也没有 self、my 这类隐式关键字（Python 把 self 摊平成一个显式形参，JavaScript 把它做成引擎注入的槽）。函数内部能引用哪些变量，在定义时就沿作用域链定死了，调用点改不了它——这正是 var that = this 这种写法存在的根源：你能捕获的只有变量，捕获不了”上一层的 this”。往前看一句，当时 TC39 草案里已经有绑定函数 :: 与箭头函数两种试图改变这一局面的提案，但 2014 年 11 月的浏览器上没有可靠实现，本文一律不依赖。

四种绑定规则

引擎判定 this 的规则一共四条，下面按”写法 → 结果 → 引擎侧发生了什么”逐个过。

默认绑定：裸调用

调用点没有任何前缀，就是 foo()。非严格函数拿到全局对象（浏览器里是 window），严格函数拿到 undefined。归根到底，是这种调用形式没给引擎提供任何 thisArg，最后落到哪个值由函数自身的严格性决定。

有两个口径要说清楚。第一，”严格与否”看的是被调用函数自身，不是调用它的那段代码；第二，IE8 及以下的 JScript 对严格模式支持不完整，脚本级 this 仍可能落到全局，这类差异当年只能靠真机实测确认，别照规范想当然。严格模式自己的规则清单《JavaScript 严格模式 strict 的作用》已经列过，本文只取它影响 this 的那一条。

默认绑定最阴的地方是撞名。window 上挂着一堆历史属性，全局 var 也全都落在 window 上，于是 this.name、this.top、this.self、this.location 这类写法一旦掉进默认绑定，不会报错，而是安静地读到全局值。排查时与其盯着”值为什么不对”，不如先问”this 是不是根本没绑上”。

成员绑定：属性链最后一层

调用点写成”某个对象点出来的方法”时，this 就是属性链最后一层那个对象，只有它参与判定。

with 语句是个反例，也是它该被禁用的理由。在 V8 里实测，with (obj) { show() } 的 this 会变成 obj——因为 with 环境让调用点生成的引用把 base 指向了绑定对象，同时标识符解析也被劫持。一个语法结构能让 this 和变量来源同时漂移，等于把”看一眼调用点就知道答案”这条纪律废掉了，严格模式直接判它语法错误，老代码里遇到就重写。

getter / setter 里的 this 依然遵循成员绑定，指向访问属性时点出来的那个对象，而不是属性定义所在的原型对象。

做继承时如果把带 getter 的对象塞进原型链，child.amount 里 this 是 child 而不是原型上那个字面量——这是当年不少”getter 读到 undefined”的来源。

显式绑定：call、apply、bind

call / apply 让调用方当场指定 this，bind 则把 this 冻在函数外面，生成一个新函数。

三条实测过的要点：绑定是终身的，f.bind(a) 之后再 call(b) 或再 bind(c) 都改不动它；连续 bind 只有第一次生效；装箱规则只看被调用函数自己是否严格——严格函数原样接收 thisArg（f.call(null) 里 this 就是 null），非严格函数会把原始值 ToObject 装箱、null / undefined 换成全局对象。

new 绑定

new 的四步过程《new 操作符到底做了什么》已经完整推过，这里只取跟 this 有关的一句：构造函数被调用时，this 是刚建出来的那个新对象；构造函数返回对象时结果被该返回值替换，返回原始值则被忽略、this 白建一次。

不管是 new Foo()、new obj.Foo() 还是 new Foo.bind(ctx)()，最终 this 都是新对象。所以 new 绑定天然排在最前面，这不是约定，而是判定顺序本来就藏在调用语法里。

优先级与五步判定

四条规则同时”看起来都成立”时谁赢？结论一句话：new 绑定 > 显式绑定 > 成员绑定 > 默认绑定。

把它写成一段能背下来的伪流程：

  1. 调用表达式最前面有没有 new？有 → this 是新建对象，判定结束。
  2. 这次调用是不是 call / apply 直接触发的，或者函数本身是 bind 的产物？是 → this 是那个（第一次绑上的）对象，判定结束。
  3. 调用点是不是 x.y()、x.y.z() 这种带前缀的属性访问？是 → this 是最后一层的 x.y。
  4. 以上都不是，且函数自身是严格模式 → this 是 undefined。
  5. 以上都不是且非严格 → this 是 window（老 JScript 需实测）。
flowchart TD
  A[一次函数调用] --> B{前面有 new 吗}
  B -->|有| C[this 是新建对象]
  B -->|没有| D{是 call apply 触发或 bind 产物吗}
  D -->|是| E[this 是绑定的那个对象]
  D -->|否| F{调用点写成 obj.foo 吗}
  F -->|是| G[this 是属性链最后一层]
  F -->|否| H{函数自身是严格模式吗}
  H -->|是| I[this 是 undefined]
  H -->|否| J[this 是 window]

下面十道判断题，答案都实测过，建议先自己答再看解释。

  1. var fn = o.f; fn() —— 默认绑定。浏览器里 this 是 window，window.n 不存在就是 undefined，撞上全局同名属性反而”看起来正常”。
  2. o.inner.f() —— this 是 inner。属性链只有最后一层参与判定。
  3. (o.f)() —— this 还是 o。括号不改变引用的 base。
  4. (0, o.f)() —— 默认绑定。逗号表达式返回的是”无名”值，base 在这一步被丢掉，这是压缩代码里常见的 this 消音器。
  5. var a = [o.f]; a[0]() —— this 是那个数组。成员绑定不关心接收者是不是数组，只要写成点出来或下标取出来再调用。
  6. o.f.bind(x).call(y) —— this 是 x。bind 一旦生效，后面的 call 只能改参数。
  7. new o.Ctor.bind(ctx)() —— this 是新对象。new 压过显式绑定，ctx 只剩预置参数的作用。
  8. setTimeout(o.f, 100) —— 默认绑定。定时器保存的是函数对象，不是 o.f 这个带 base 的引用。
  9. strictF.call(null) 与 sloppyF.call(null) —— 前者 this 是 null，后者是 window。装箱与否看被调用函数是否严格。
  10. 把 getter 的函数取出来裸调用 —— 掉回默认绑定。box.self 与 descriptor.get() 是两次完全不同的调用。

组件里的 this：构造时绑一次

把规则落到架构上，我现在的做法是一句话：需要交给外界回调的公开方法，在构造函数里 bind 一次，把绑定版存到实例上，绑与摘复用同一个引用。方法本体仍然放原型（一份函数全实例共享），只有别名是每实例各一份。

要点有三：onClick 是实例上的绑定版、handleClick 是原型上的本体，职责一眼分清；destroy() 传回去的就是绑定时那个引用，所以能精确摘除而不牵连别的模块；处理函数内部一律从 e.currentTarget 拿元素，把”元素”和”组件”两件事彻底分开。代价是每个实例多出两个函数对象——相比漏掉一个组件的内存，这个代价可以忽略。

另一条路线是干脆不用 this：模块返回一个对象，内部状态全靠闭包共享。这条路 IIFE 那篇讲过，本文不重述。取舍上我的经验是”需要多实例、需要继承”就用构造函数加原型，”单例、纯工具、一次性初始化”就用模块对象，最糟的是一个文件里两种混着写，读的人得先猜这层的 this 是谁。

剩下的边界与坑

  • arguments 与 this 无关。arguments 记录的是本次调用的实参，跟着调用点走；this 是上下文，两者互不推导。Array.prototype.slice.call(arguments) 里那次 call 只是”把 slice 以 arguments 为接收者调起来”，跟业务对象的 this 毫无关系，别把它当成”绑定”的例子讲给新人。
  • 对象字面量里的方法用 this 引用同层属性，成败取决于调用方式。var o = { a: 1, b: function () { return this.a; } }; 写成 o.b() 得 1，写成 var g = o.b; g() 什么也拿不到。另外字面量初始化阶段根本没有 this 可用：{ a: 1, b: this.a } 里的 this 是外层上下文（在全局脚本里就是 window），实测拿到 undefined。想在字面量里引用兄弟属性，只能构造完再补一句赋值，或者改用工厂函数。
  • DOM 事件里 this === currentTarget 是标准约定，但 IE8 的 attachEvent 下 this 是 window。2014 年还要兼容时统一归一化，别依赖 this：
  • 链式 call / apply 的 this 归属。Function.prototype.call.apply(fn, [ctx]) 与 fn.call(ctx) 等价：外层 apply 把内层的 call 当普通函数调，它的第一个参数才是内层的 this。读原型方法借用技巧时按这个拆法看，一串点也不会看晕。
  • 严格模式下的表述口径。规范层面的说法是”引擎没有为这次调用传入 thisArg”，实现上落到 undefined，不是”this 被设成 null”。写团队文档时把这句话说准，能省掉同事一半的追问。

小结

速查表贴在显示器边上最省事：

写法 this 结果
new Foo() 新建对象（构造函数返回对象则被替换）
new Foo.bind(ctx)() 新建对象，ctx 被忽略，只留预置参数
foo.call(ctx) / foo.apply(ctx) ctx（严格函数可原样收到原始值）
foo.bind(ctx)() ctx，之后 call / bind 都改不动
obj.foo() / obj.p.foo() 属性链最后一层的对象
with (obj) { foo() } obj（严格模式禁用，别用）
foo() 严格函数是 undefined，非严格是 window
el.onclick = fn 触发时 元素本身（attachEvent 下是 window）
setTimeout(fn, 0)、arr.forEach(fn) 默认绑定，除非显式传上下文

三条团队规约：第一，回调一律显式绑定或传上下文，禁止裸传方法引用；第二，事件解绑必须复用绑定时那个函数引用，禁止现绑现摘；第三，判定不确定时就改成闭包捕获 that——它不优雅，但它是所有引擎上都不会变的行为。this 的规则其实很少，出问题的从来是我们把它和”这个函数属于谁”混为一谈的直觉。
