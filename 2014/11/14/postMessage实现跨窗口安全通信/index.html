postMessage 实现跨窗口安全通信

本文属于《HTML 与 CSS》第 55/62 篇
上一篇系列目录下一篇

页面里嵌一个不同源的第三方组件，或者弹一个对方域下的登录窗口，两边谁也没法直接读谁的东西。postMessage 是浏览器为这种情况留的正式通道：把一条消息投递到另一个窗口的 message 事件上，不经过服务器，也不进地址栏。本文按入门的顺序讲三件事：最少几行代码跑通收发、消息什么时候发才不会丢、以及怎么把这道门守住不让它变成漏洞。适合准备嵌入第三方内容或做跨窗口登录回传的同事读，代码全是 ES5，可以直接落到老项目里。

为什么需要 postMessage

同源策略规定协议、域名、端口三者全部相同才算同源，不同源的脚本不能读写对方的文档对象。落到 iframe 上，最直接的后果是父页拿不到子页的内部结构：

于是前端攒出了三条绕行路：JSONP 借 script 标签不受同源限制的特性，CORS 让服务端用响应头声明许可范围，document.domain 让同主域的两个子域互相认出来。三者的原理与配置在《AJAX 与跨域请求实践》里已经讲透，本文不重复推导。这里只分清定位差异：前两条解决的是”我向你取一份数据”，本质仍是请求与响应；第三条只在主域相同时可用，而且改完之后改不回去。

有一类需求这三条都覆盖不了——我要和另一个窗口双向说话。对方可能是我嵌入的第三方页面，也可能是我 window.open 弹出的登录窗口，两边除了一个 URL 之外什么都不共享。这种情况下用 URL 传参回传是很多人第一反应，但它明确不可取：敏感信息一旦进了 URL，就会留在地址栏、浏览器历史和服务端访问日志里，还可能被 Referer 请求头带到第三方站点；URL 长度有实际上限，表单快照或者富文本内容根本塞不下；传参就意味着导航，回传要把用户从一个页面甩到另一个页面，中间状态全部丢掉。

postMessage 正是为这类需求准备的：你持有目标窗口的引用，把消息体和期望的目标源交给它，浏览器负责校验和投递，目标窗口在自己的 message 事件里拿到数据。整个过程不进 URL、不进历史栈，也不需要两边变成同源。

最小可用：一条消息的收发

最小闭环只需要几行有效代码，但每个参数各有讲究。先约定场景：主站页面嵌入一个不同源的组件页。

第一个参数 data 是消息体，规范允许字符串也允许对象，实际项目里请按后面的结论统一成字符串。第二个参数 targetOrigin 是发送方对”投递给谁”的承诺，浏览器会拿目标窗口当前文档的源与之比对，不匹配就丢弃消息，连事件都不触发。接收端的事件对象 MessageEvent 比普通事件多三个属性，它们是本文全部内容的支点：

  • data：消息体，对方传什么就是什么，任何内容都不可信；
  • origin：发送方文档的源，形如 http://child.example.com，不含路径与查询串；
  • source：发送方窗口的引用，可以反过来对它调用 postMessage。

origin 回答”这条消息来自哪个站点”，source 回答”来自哪一个具体窗口”。少了前者，任何页面都能伪称自己是合作方；少了后者，你分不清消息出自自己嵌的那一个 iframe，还是被人偷偷塞进来的另一个。

安全：接收侧的两道校验

origin 必须走白名单，不能做子串判断

接收侧不校验源，等于把门敞开：任何页面只要拿到你窗口的引用就能发消息，而拿到引用并不难，window.open 出来的页面天然持有 opener，iframe 里的页面天然持有 parent。更常见的问题是”看起来在校验”：

除了 evil-example.com，http://example.com.evil.cn 这类把合法域放进中间子域的写法同样能骗过子串判断。允许的域确实多、又要支持任意子域时，只能换成锚定起止位置并转义点号的正则。origin 的取值本身也有坑：file:// 打开的页面、被 sandbox 限制且没给 allow-same-origin 的 iframe，origin 是字符串 "null"；IE8 在设置过 document.domain 的页面里给出的可能是主域形式，也可能与 URI 方案规定的写法不一致。所以校验第一步就排除 "null"，别把判断写成宽松的”非空即通过”。

比对 e.source，确认是”那一个”窗口

同一层校验还不够。同一个源下可能有多个窗口：页面上三个组件都来自 child.example.com，用户还可能在别的标签页打开了同域页面。处理逻辑一旦改动状态或者提交数据，就得多问一句”出自哪一个”。

这个比对把信任范围从”这个站点”缩小到”我亲手创建的那一个窗口”，冒充的成本陡然变高。两点提醒：老 IE 不一定完整给出 source，要先判断存在再比对，缺失时按业务风险决定放行还是丢弃；引用正确不等于内容安全，source 通过之后照样要做指令白名单和字段校验。用 jQuery 绑定消息事件时，自定义属性可能在原始事件对象上，取值写成 e.origin || e.originalEvent.origin 更稳，早期 Firefox 与 jQuery 的封装在这里并不一致。

安全：发送侧与协议设计

targetOrigin 不许偷懒写星号

发送侧这层保护最容易被”图省事”打掉：

写成 '*' 之后浏览器不做任何检查。典型事故是：你嵌的第三方 iframe 内部把用户跳去了广告页，或者被人引导到了钓鱼页，此时它的文档已不属于合作方域，但你后续发出的消息照旧送达，里面可能带着 token、用户标识或者内部配置。targetOrigin 写死之后，这类投递会被静默丢弃，这正是它的意义。两条边界要记住：第二参数只接受单个源或者 '*'，不能传数组，多目标就分别调用；IE8 会忽略这个参数，等于这层保护根本不存在，因此涉及敏感数据的通信不要把 IE8 算在支持范围内。

结构化数据走 JSON 字符串并校验字段

消息体建议统一为 JSON.stringify 之后的字符串。规范允许直接把对象交给 postMessage，底层走结构化克隆（structured clone），但它有两个当时的限制。一是只有可克隆的值过得去，函数、DOM 节点、window 这类宿主对象在克隆时会直接抛异常，别指望把一段逻辑”传”过去；二是 IE8 与 IE9 对非字符串的支持残缺，传对象常见属性丢失甚至整体失败。既然要跨窗口，就按最保守的公共子集来。

JSON.parse 包在 try/catch 里不是形式主义：对端页面的脚本错误、同一窗口里别人发的自定义消息，都会让接收函数拿到非本协议的字符串。字段校验要具体到业务含义，只写 if (!data) return; 挡不住类型合法但取值荒谬的输入。

就绪握手：消息别发早了

消息发早了会静默丢失，不报错，最难查。iframe 刚插进 DOM 时它的文档还是 about:blank，源和 targetOrigin 对不上，浏览器直接丢弃；即使 src 已经开始加载，子页的监听函数也还没执行。父页以为发了，子页从没收到，联调时两边都觉得自己没问题。可靠的办法是双向握手：

sequenceDiagram
  participant P as 父页
  participant F as 子 iframe
  P->>F: 创建 iframe 开始加载
  F->>F: DOMContentLoaded 后注册 message 监听
  F->>P: 发送 child-ready
  P->>P: 校验 origin 与 source 标记已就绪
  P->>F: 投递排队中的业务消息
  F->>P: 回 ACK 或结果数据
  P->>F: 超时未收到 ready 则发 ping 重问

要点有三条。第一，监听先于握手，子页必须注册好处理函数再发 ready，顺序反了就是死等。第二，ready 是子到父方向，父页此刻还不能确认子页可信，照旧要校验 origin。第三，ready 本身也可能丢，父页超时后主动发一次轻量的 ping，子页收到就再发一遍 ready，比只等一次健壮。子页若不确定父页的源，可以先收一条来自父页的合法消息，用事件里的 origin 学到父页源再定向回复。

下面这个 ES5 实现覆盖了三种失败情形：子页永远不 ready、ready 丢失、投递时窗口已关闭。

子页侧只需要几行：先注册处理函数，再在 DOM 就绪时把 ready 主动送出去。

实战一：第三方登录弹窗回传 token

场景是主站点击登录后弹出对方域下的授权页，用户完成验证，弹窗把一次性 token 回传主站，主站拿它换取本域会话。token 全程不进 URL，这是它比跳转回传干净的地方。

实战二：iframe 自适应高度

嵌入内容最常见的需求：组件页的高度由内容决定，父页跟着改 iframe 的高度。跨域时父页读不到子页的 contentDocument，没法轮询量高，只能由子页把自己量出来的值上报。

触发时机比想象中多：内容异步渲染完、图片加载完成、用户展开某一块都要调一次 requestResize，其中图片最容易被忘，图没加载完就上报，高度必然偏小。DOM 变化本身可以用 MutationObserver 监听，Chrome、Firefox 与 IE11 支持，更老的浏览器退化为在已知交互动作后手动调用。

父页侧只做一件事：设置高度。一条消息只做一件小事，出问题时才知道是哪一环。多个组件嵌在同一页时必须带上 id 并用 e.source 反查确认，否则同域多个 iframe 的消息会互相打错。

兼容性坑清单

把这些年踩过的坑集中列一下，接入前逐条对照。

  • IE8 的事件注册只能用 attachEvent('onmessage')，处理函数收不到事件参数，得从 window.event 上取；两条注册路径都写上，别只测 Chrome。
  • IE8 与 IE9 传对象容易丢属性，data 按字符串传最保险，两端各自 JSON.stringify 和 JSON.parse。
  • IE8 会忽略第二个参数 targetOrigin，且 origin 的取值形式可能是 document.domain 后的主域，跨域敏感通信不要把 IE8 纳入支持范围。
  • 目标窗口可能已经关闭。对 window.open 回来的引用发消息，先判 closed 再包 try/catch，判断不能替代捕获。
  • iframe 还处于 about:blank 时发消息必丢，不要在创建它的那一行之后立刻投递，这正是握手要解决的事。
  • 消息风暴会让页面卡住。高度上报、滚动同步这类高频消息必须在发送端合并、在接收端去抖，同值不发送。
  • 被人嵌入时 top !== self 可以判断，但跨域下读 top.location 会抛异常；真正阻止被别人嵌要靠响应头 X-Frame-Options，前端判断只是补救。
  • 嵌入完全不可信的内容时，iframe 的 sandbox 属性可以限制能力，当时 Chrome、Opera、Firefox 与 IE10 之后陆续支持；写了 allow-scripts 而不给 allow-same-origin，该文档的 origin 就是字符串 "null"，接收侧必须显式拒绝。
  • 标准里还有 MessageChannel 与 MessagePort，能做更隔离的点对点通道，SharedWorker 也能配合，但当时只有 Chrome 支持，不建议依赖。

小结

postMessage 的使用不难，难的是把它当成分界线而不是后门：消息另一端是一个你无法控制的文档，它可能正在被攻击。上线前照这份清单过一遍。

  1. 接收侧 origin 走白名单全等比对，禁止子串判断，显式拒绝 "null"；
  2. 比对 e.source 与自己保存的窗口引用，把信任范围收到具体窗口；
  3. 发送侧 targetOrigin 写死具体源，全项目不允许出现 '*'；
  4. 消息只携带”指令名加参数”，接收端用白名单分发表，严禁用数据字段去取函数或 eval；
  5. 数据统一 JSON 字符串，JSON.parse 包 try/catch，字段做类型、必填与上下界校验；
  6. 用 ready 与 ping 的双向握手解决就绪时机，未就绪的消息排队，超时有重试上限与降级；
  7. 高频消息在发送端合并、接收端去抖，投递处一律 try/catch 并判窗口 closed。

七条里最容易省的是第 3 条和第 6 条：前者写着方便，后果要到线上才暴露；后者在小 demo 里根本复现不了。笔者的经验是把源常量、白名单校验和 ReadyBridge 抽成公共模块，业务代码只写分发表里的处理函数——安全约束落在基础设施里，才不会被某次赶工绕过。
