Object.defineProperty 与数据劫持入门

本文要解决的是一个具体痛点：表单数据一变，预览区和”未保存”提示就得跟着变，而靠人在每个回调里补一句刷新函数，迟早会漏。我们把 ES5 的访问器属性拿出来做”赋值即通知”，也就是通常说的数据劫持。文中给出一个完整可运行的最小实现、三个绕不开的边界、一批当年真实会踩的坑，并把这条路线和轮询脏检查、setter 方法约定放在一起比较。适合写过表单联动、做过小状态管理，或者好奇”响应式”当年是怎么落地的读者。属性描述符本身的规则不再重述，只在本篇需要时指向旧文。

从一个漏掉刷新函数的表单说起

场景很普通：一个信息编辑页，左边是表单，右边是卡片预览，顶部还有一个”有未保存修改”的红条。最初的写法是把每个 input 的 change 回调写成三段式：

字段从 3 个涨到 15 个之后，问题就出现了。新增字段时忘记补第 2、3 行是小事，大事是数据开始从别的地方被改写：某个第三方校验插件直接改了 form.phone，或者一段异步回调从服务端回填了 form.city。这些地方根本没有”change 事件”这个概念，也就不会有人替你想起来调用刷新函数。笔者的实际 bug 是用户在预览区点了一下”重新生成”，页面显示的还是三个字段之前的旧值，查了半天发现是回填逻辑绕过了回调。

需求的本质是：把”数据被改了”这件事从”谁改了它”里解耦出来。写数据的地方不该关心有几处 UI 要刷新，UI 只应该订阅数据变更。要做到”赋值即通知”，语言层面必须能在属性被读写时插一段代码进去。2014 年的浏览器里，能插代码的现实路径有三条。

三条路径的对比：轮询、setter 约定、访问器劫持

第一条是轮询脏检查。把对象做一份快照，隔一小段时间逐属性比对，不一样就派发变更：

它的优点是简单粗暴且通用：不需要预知字段名，不需要改任何调用点，IE8 也能跑。缺点全在”比”这个动作上。浅比对只能发现顶层替换，form.user.city 被改就看不见；要看见就得深拷贝快照，而深拷贝每轮都跑一遍，属性多的时候明显吃 CPU，还会踩循环引用。另外它是异步的，同一轮里改两次只能看到最后一次结果，想拿到旧值得靠快照表自己存。

第二条是 setter 方法约定。给每个字段配一个显式写入口，谁改数据谁调它：

语义最清楚，调试时断点好下，也不依赖任何新 API。代价是它把”赋值”这个语言里最自然的动作变成了函数调用，所有调用点都得改写；更要命的是漏改的成本很高——只要有人图省事直接写 form._name = 'x'，通知就永远丢了，而这种代码在 review 里特别容易看漏。字段一多，getter 侧还得配一堆 getName，样板代码不少。

第三条就是本文的主角：用 Object.defineProperty 把已有属性换成访问器，读写都被我们拦下来。它的决定性优势是透明——调用点一个都不用改，form.name = 'x' 这种最普通的赋值语句就会自动派发通知。三个方案摆在一起：

维度 轮询脏检查 setter 方法约定 访问器劫持
是否要改调用点 不用 全改 不用
新增字段能否感知 能 不能 不能
数组下标与 push 能 能（走显式 API） 不能
变更时机 下一轮，合并后 立即 立即
拿到旧值 要自建快照 手写参数比较 set 里天然有旧值
性能风险 遍历比对的固定开销 几乎没有 通知风暴
IE8 可用性 可用 可用 不可用

结论不是”访问器最好”，而是三条路径各自的失效方式不同：脏检查丢时效和精度，setter 丢纪律，访问器丢新增属性。

最小实现：把自有属性逐个换成访问器

先明确一件事：defineProperty 的字段规则、默认值陷阱、configurable 单向门这些，笔者在《JavaScript 对象属性描述符与特性》里已经梳理过，这里直接用结论，只讲怎么把它组织成”数据劫持”这套结构。

整个实现分三块：一张订阅表、一个改写函数、一个递归遍历。

walk 里那行”先把原值读出来”是整个机制的命门。如果 get 写成 return obj[key]、set 写成 obj[key] = next，那么 getter 内部又触发同一个 getter，调用栈立刻爆掉。访问器属性不能再读写自己，值必须搬家——搬到闭包变量、或者搬到一个 enumerable: false 的备份字段上（后者要注意序列化时的行为，下面会说）。另一个细节是 set 里的同值短路：数组对象每次 push 之后引用没变，不短路的话会白刷一次；反过来这也意味着”对象内部被就地改动”是拦不住的，这正是数组问题的根源。

用 Object.keys 起步是有意的：它只给自有可枚举属性，原型上的方法不会被我们误伤成访问器，for in 遍历时也不会冒出一堆继承来的键。至于要不要把 configurable 留成 true，笔者的答案是必须——解观察、二次改写、调试时读描述符全靠它。

三个必须处理的边界

第一个是嵌套对象。最小实现里的 walk 带一个 depth 参数，因为只劫持一层明显不够用。但递归层数也不该无限放大：一个从服务端拿到的深层结构里可能挂着大数组，逐层全劫持的代价很实在。实践里我们按”订阅点决定深度”来定，只有会被 UI 订阅的路径才值得劫持到底。

第二个是数组，也是最容易骗过人的地方。defineProperty 拦的是命名属性的读写，list.push(x) 改的是 length 和下标，list[0] = x 是一次索引赋值。你可以给已有下标逐个装访问器，但新增的下标仍然是裸的，length 也照样看不见。所以 2014 年可行的办法只有两种：要么把数组方法包装一层，要么干脆走显式 API。

一次性代价与几个真实的坑

通知风暴。 上面的实现是立即派发：一次赋值同步调用所有订阅者。如果某个 getter 里读了别的被劫持对象，而订阅者又顺手写了别的字段，一次用户操作能引出几十次重渲染，DOM 被反复重排，页面直接卡住。解决办法是把派发推迟到本轮同步代码之后，同一路径只算一次：

setTimeout(fn, 0) 是这个年代最省事的合批手段，一个 tick 内多次赋值只触发一次渲染。要注意 scheduled 必须在遍历之前复位，否则 flush 里派生的写操作会被静默吞掉；如果确实需要禁止重入，就反过来加个 flushing 标记并在 publish 里抛错，把问题暴露到开发期。代价也要认：合并之后只剩最后一次新值和第一次旧值，中间过程丢失，依赖逐次时序的逻辑得另想办法。

劫持后的枚举与序列化差异。 for in 和 JSON.stringify 经过属性时都会真的调用 getter，所以 getter 里藏计数、藏日志的写法会变成”遍历一次等于读 N 遍”，副作用函数被反复执行。如果你把搬出来的值放进一个备份字段（比如 _name），它默认可枚举，序列化结果凭空多出一堆下划线键，或者因为互相引用直接抛循环引用错误。这个备份字段要不要设成不可枚举、值究竟存在闭包里还是存在对象上，本篇不重复论证：描述符规则决定枚举行为，细节见前面提到的那篇旧文。

遇到 freeze 过的对象直接抛错。 被 Object.freeze 处理的对象，属性 configurable 已是 false 且 setter 被置成 undefined，此时再 defineProperty 会抛 TypeError；即使不抛，seal 过的属性也不能从数据描述符转成访问器描述符。所以别把常量表或者上游库给的冻结对象塞进 walk。团队里定一条规矩：初始数据从服务端 JSON 解析出来就用，不做 freeze，需要只读的字段用 set 里加白名单来拒绝。

IE8 与降级。 IE8 的 defineProperty 只能作用在 DOM 对象上，对普通对象调用会抛错，而且访问器语义压根不支持，IE9 才是可用的起点。老 Android 自带浏览器上也别赌，一律以检测为准：

至于未来，草案阶段的 Proxy 能连新增属性、delete 和下标一起拦，但 2014 年没有任何可依赖的实现；Object.observe 也有人提并在实验通道里露过面，可它要求浏览器原生开启合批语义、需要手动开 flag、规范还在改，笔者对它的判断是”方向对但注定不好用”，工程上当它不存在。

jQuery 生态里的那半边通知丢在哪

页面不只有 JS 对象，还有 DOM。当时最常见的状态存放点是 $(el).data(...)，而它写的是 jQuery 内部那张 cache 表里的键值，不是元素上的属性赋值，我们的访问器自然一声不吭；插件通过自定义事件（$.event.special 那一套）广播出来的状态变化同理，压根没经过被劫持的对象。旧文《DOM 中 class 操作的几种封装》里讨论过 data 缓存导致的”两份状态”问题，本质是同一件事。

所以 2014 年最普遍的替代方案朴素得可以：在 jQuery 侧手工 trigger。

$(document).on('form:dirty', handler) 集中收口，预览区和提示条订阅它。这条路不需要 defineProperty、跨浏览器无痛，缺点是把”通知”重新变成了纪律问题：调用点照样分散，忘一次 trigger 就漏一处，而且传参全靠约定。可以说手工 trigger 和访问器劫持正好站在光谱的两端，前者透明性为零、兼容性满分。真正省事的做法是让 DOM 事件只负责”用户操作”，操作落到 form 对象上之后就只剩一条通知链路，不要把两个体系混着用。

框架对照：脏检查与访问器是两种取舍

只谈技术选择，不比优劣。AngularJS 1.2 走的是脏检查：$watch 注册表达式和上次的值，$digest 循环遍历监听列表逐个比对，有变化就执行回调并重新走一轮，直到稳定。它的取舍和上面那张表完全对应：不需要预知字段名，新增属性天然能被发现，数组和 push 也能看见，不依赖 defineProperty 所以 IE8 照跑。代价是所有变更都要等一轮 digest，监听数量线性影响开销，跨作用域的 $apply 引发级联检查后就成了大家熟悉的 digest 风暴——笔者的一个列表页在 watch 加到 600 多个之后，输入框打字开始有明显的滞后感。

Polymer 当时的 0.x 预览版本走的是另一条：通过 defineProperty 给声明过的属性装观察器，属性变化时把变更派发给模板绑定。注意这只是它 0.x 预览阶段的公开实现，拿来做参照是为了说明”访问器路线确实有人在认真走”，而不是断言它更先进。有意思的是它同样绕不开我们遇到的边界——被观察的属性要在声明里写清楚，数组元素变化需要显式的数组方法去做，这恰好说明那几个边界是机制本身带来的，不是谁实现得粗糙。

两条路线的分水岭是一句话：检测放在写的那一刻，还是放在固定的检查点上。前者精确及时，但要预知字段；后者通用，但要为每一次检查付遍历比对的开销，还要忍受时效。

实践结论

值不值得上访问器劫持，看三个条件是否同时满足。字段集合已知且相对封闭（有模板或 schema，服务端结构可控），变更点分散在多个模块、多个插件回填，需要精确到”哪个键从什么变成什么”的通知。三条都中，walk 加订阅表这套很划算，一次投入换掉几十个手工刷新调用。

只要字段不可预知、数据是服务端任意结构、或者需求里满是”往对象里追加键”，脏检查更划算：实现不到三十行，跨浏览器无痛，新增属性免费感知，代价只是时效和一次浅比对的开销。至于 setter 约定，笔者现在的态度是：把它当成访问器路线的补丁用——劫持覆盖不到的地方（数组下标、setPath、插件写入点）就用显式 API 明说，别为”全透明”这个执念去做包装数组方法那种脆弱的兼容。

最后一条经验：无论选哪条，通知出口只能有一个。同一个字段既能被劫持通知、又能被 trigger 通知、还能被轮询通知时，出问题时你不会知道 UI 是被谁刷新的。

小结

数据劫持做的事只有一件：把属性搬到闭包变量里，再用访问器换掉原属性，让赋值顺手派发通知。它的价值是透明，调用点一个字都不用改，旧值还是现成的。它的失效面同样清楚：新增属性感知不到、数组下标和 push 拦不住、冻结过的对象改写会抛错、IE8 及以下根本不支持，所以必须特性检测并准备好降级到脏检查的那条分支。真正让人却步的往往是通知风暴，用 setTimeout(fn, 0) 做同轮合批是当年够用且便宜的办法。和 AngularJS 的脏检查比起来，两条路线不是新旧之分，而是”预知字段换精确时效”与”放弃时效换通用性”的取舍，看清数据的字段是否封闭，选择基本就定了。
