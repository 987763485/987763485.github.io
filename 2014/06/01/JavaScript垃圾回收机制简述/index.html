JavaScript 垃圾回收机制简述

写页面的人大多有个错觉：内存是浏览器的事，JS 里有垃圾回收（GC），所以不会泄漏。真到了单页应用跑半小时内存翻倍、iPhone 上页面莫名其妙整页重载的时候，才发现 GC 不是保险箱。本文从回收算法讲起，落到 V8 分代对写代码的实际指导、几类能复现的泄漏模式和当年手头可用的排查手段。适合正在被”内存只涨不跌”困扰、想让页面长跑稳定的读者。

为什么前端要关心 GC

垃圾回收最大的麻烦在于它不由你控制。你无法命令浏览器”现在回收”，只能等引擎自己判断时机——通常分配内存超过某个阈值时才动手。而 JS 是单线程的，回收停顿和业务代码跑在同一个线程上，一次几百毫秒的 GC 意味着动画直接丢掉十几帧。桌面机上或许只是”卡一下”，在移动端就是体验事故。

更要命的是移动浏览器的内存红线。iOS Safari 对单个标签页有硬性的内存上限，超过之后 WebContent 进程直接被杀，用户看到的现象是页面原地重载——滚动位置没了、状态全丢，像见鬼一样。Android 2.3 及之前的系统浏览器（WebView 同源）GC 停顿明显，列表快速滚动时一遇到回收就整屏定住。这些都不是”逻辑写对了”能躲过去的，必须理解回收器怎么工作、内存去哪了，才有排查的入口。

引用计数与标记-清除：两种算法的本质差异

回收算法归根到底只回答一个问题：哪些对象再也不会被用到了？早期答案有两条路。

引用计数给每个对象挂一个计数器，被引用一次加一，引用失效减一，归零即回收。实现简单、回收即时，但有一个致命缺陷：循环引用无解。A 引用 B、B 引用 A，哪怕这两个对象对整个程序已经不可达，彼此的计数器永远到不了零。IE 6/7/8 时代的 JS 对象与 DOM/COM 对象各用引用计数管理、两套计数器互不相通，”DOM 节点 + 闭包”形成的环解不开，才成就历史上那批著名的泄漏（具体做法在旧文《DOM 事件移除与内存泄漏》里已详述，本文不重复）。

标记-清除反过来：从一组”根”出发，把所有能走到的对象标为存活，走不到的一律回收。环不环的根本不重要，重要的是”从根出发可达不可达”。Firefox、Chrome、Safari 以及 IE 9 之后的回收器都是这一路数的变体，可以说 2014 年主流引擎已经是标记-清除为主。写代码时纠结”有没有循环引用”意义不大，纠结”这条引用链能不能从 window 走到它”才有意义。

V8 的分代回收：对写代码的实际指导

V8 为了压低停顿做了分代：新对象先放在新生代，活下来的再晋升到老生代，两代用不同算法。

区域 算法 特点 对写代码的指导
新生代 Scavenge（复制） 把存活对象复制到半区，死对象零成本整片丢弃；存活越少越快 循环里的一次性临时对象其实便宜，但临时对象总量大会触发频繁复制
老生代 标记-清除 + 标记-整理 原地标记回收，碎片严重时要搬移压缩，停顿明显 长期存活的对象要少而精，大对象尽量别进老生代反复折腾

新生代的对象晋升条件大致是：经历过一次 Scavenge 仍存活，或复制时半区放不下。于是出现两个反直觉的结论。

其一，短命对象多并不贵。只要对象在新生代就死掉，复制算法根本不碰它，成本近似为零。真正贵的是”创建得又多又活过了第一轮”的对象。

其二，大数组反复扩容很贵。数组超过老生代大对象阈值后直接进老生代，来回 push/截断、大规模 splice 搬移元素都会搅动这片区域，每搅动一次都是在给标记-整理制造工作量。

同理，热路径上能复用的对象就复用（对象池思路），别每帧 new 一批”用完即弃”却侥幸活过第一轮扫描的东西。

什么算”根”：闭包不是泄漏，被过度捕获才是

标记-清除要从根出发，根就是那批天然的起点：全局对象 window、当前活动调用栈里的局部变量、以及被现存闭包捕获的环境。第三条最容易被忽略——函数返回了，但只要还有个函数对象活着，它当年捕获的那个作用域就一直可达。

所以”用了闭包就会泄漏”是个误传。闭包只是让捕获的对象延长了可达性，问题永远出在捕获了不该捕获的大对象上。看一组 ES5 的对比：

配套的三条纪律：组件销毁时把挂出去的对象引用显式置 null（尤其是挂在 DOM expando 或外部模块上的）；定时器用完立即 clearInterval，定时器的回调连同它的捕获环境在被清掉之前都是根可达的；事件监听器成对移除——这属于引用链没斩断的又一形态，做法见旧文《DOM 事件移除与内存泄漏》，本文只把它当作”根通过回调把整条链拽住”的案例之一。

六个常见泄漏模式，每一个都能复现

一：忘记清理的 setInterval 与事件。 弹窗开了绑定时器、关了不清理，开关一百次就攒一百个定时器，回调的捕获环境全部根可达。

二：把对象塞进全局数组当”缓存”，却从不淘汰。

三：console.log 持有对象。 这在 IE 下尤其阴险：控制台打开时被 log 过的对象会被控制台引用着，哪怕你把变量置 null，它在回收器眼里依然可达。

Chrome 上同样建议排查完就清空控制台再复测，别被”日志残留”干扰快照结论。

四：detach 下来的 DOM 节点仍被闭包引用。 节点从树上摘了，JS 里还留着引用，整棵子树都跟着。

五：闭包里的 this / arguments 意外留住大对象。 回调里一句 var self = this，如果 this 是组件根节点或包含大数据的对象，等于把它整个捕获了；arguments 会让调用者的整个参数列表在闭包存活期间一个都释放不掉。

六：IE 的循环引用与 expando。 往 DOM 节点上挂自定义 JS 属性（expando），属性对象又反向引用该节点，在 IE 9 之前引用计数解不开环。

实操排查：从曲线到快照

排查内存问题的正确姿势是先证明”涨”，再定位”谁涨”。

第一步，Chrome 任务管理器（菜单 → 工具 → 任务管理器，或快捷键 Shift+Esc），右键列头勾出”内存占用值”列。它显示的是每个标签页的真实占用，比系统任务管理器细。反复执行同一个操作 20 次，看这一列是否单调上涨——先圈定”哪个操作在泄漏”。

第二步，开发者工具 Timeline 面板，勾选 Tools 抽屉里的 “Memory”，操作一段后观察内存曲线。健康曲线是锯齿形：分配、回收、回落。只爬坡不回落，基本可以定罪。这里有个关键技巧：做前后对比时，先点面板上的垃圾回收按钮手动触发一次回收，再开始下一步，否则你对比的是”还没回收的垃圾”，全是假阳性。

第三步，Profiles 面板选 “Heap Snapshot”（Chrome 34 可用），”先手动 GC、再拍快照”同样适用。拍完在搜索框过滤 Detached，展开 Detached DOM tree 分类——游离节点成批出现就是铁证。点开单个节点看 Object retention 引用链，沿着”谁引用了它”一路向上，最后十有八九停在一个全局数组、一个未清理的定时器回调或一个绑在别处的函数上。

局限也要说清楚：这套手段只属于 Chrome。IE 9/10 没有堆快照，只能靠系统任务管理器盯进程内存，自己写一个对象计数器辅助定位——比如给关键类维护创建/销毁的计数，操作完对不上账的就是嫌疑对象。当年不少 IE 泄漏就是这么人肉排出来的。

顺带一提，window.performance.memory 能读到 JS 堆的 usedSize/totalSize，但那是 Chrome 私有 API、数据精度也有限，只在调试脚本里做趋势记录用，别拿来做线上监控。

治理：给缓存立规矩，给销毁留钩子

定位完泄漏，治本靠两件事：缓存有上限，销毁有纪律。

其一，SPA 里每个”页面”模块必须有自己的 destroy 钩子，路由切换时统一调用：清定时器、off 掉本模块命名空间的事件、把自己在全局缓存里的条目删掉。这套”无刷新切换”的骨架在旧文《HTML5 History API 打造无刷新单页应用》里已经搭好，本文的销毁纪律就是给那个骨架补上的另一半。

其二，图片与大数据缓存宁可”用完即释放 + 需要时重新请求”。HTTP 缓存（参见旧文《HTTP 缓存机制与缓存策略》）会让重新请求的代价远低于驻留内存的代价，JS 里的强引用缓存只在确有必要的热点上开，并且一律走 LRU。

其三，长列表不要越滚越多地堆节点，回收屏幕外的行、改写内容复用——做法与原因在旧文《DOM 操作性能：批量插入与重排优化》里讲过，对内存同样成立：DOM 节点减少一个，它的监听器、expando、关联 JS 对象都少一分滞留机会。

移动端的特别纪律

移动端的内存是”配额制”而不是”尽力而为”，必须自己算账。

iOS Safari 的标签页内存上限随设备与系统版本浮动，我们的取值标准是：正常页面控制在 200 MB 以内，富媒体页面顶到 250 MB 就该主动做淘汰，接近红线时用户的表现不是报错，而是上一节说的整页重载，排查时极难归因。Android 2.3 的系统浏览器 GC 停顿明显，大列表滚动场景要让出回收窗口——避免每帧大量分配，比事后优化回收更有效（requestIdleCallback 那套协作式调度还要等很多年，当年只能靠减少分配硬扛）。

图解内存是移动端的头号大户，估算公式必须刻在脑子里：解码后的内存约等于 宽 × 高 × 4 字节（RGBA 每像素 4 字节，与 JPEG/PNG 文件体积无关）。一张 2048×1536 的图解码后约 12 MB，屏幕上显示 300×225 也是 12 MB。所以：列表缩略图一定用服务端裁剪的小图；iPhone 4/4S 上别把多张大图同时摆进 DOM；轮播预加载最多预下 1 张。

小结

GC 不可控、时机不确定、停顿吃掉帧，这三件事决定了前端必须主动管内存。算法层面，标记-清除是主流，担心循环引用不如检查”从根出发的引用链”；V8 分代告诉我们短命对象便宜、老生代的大对象折腾不起，热路径少造临时对象、大数组避免反复扩容。泄漏的高发地永远是全局容器、未清理的定时器、console 引用和游离 DOM，排查靠”任务管理器圈定操作、Timeline 曲线定性、手动 GC 后对比快照、retention 链定位”这套流程，IE 只能人肉计数。治理的落点是 LRU 上限加 destroy 钩子的纪律，移动端则要多背一条内存红线和一张宽×高×4 的乘法表。
