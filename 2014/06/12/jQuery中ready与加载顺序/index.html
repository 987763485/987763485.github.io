jQuery 中 ready 与加载顺序

$(function () {...}) 大概是所有前端同学敲得最多的一行代码，但它常常被一句”等 DOM 好了再跑”就带过去了。实际上它至少有四层含义：写法上有一堆彼此等价的形式，语义上和等图片的 load 有一条清晰分界，实现上 jQuery 为了老 IE 准备了三条互相竞争的检测路径，工程上动态注入的脚本还会撞上”ready 早就过去了”这类静默失效。本文就讲 jQuery 这一层的 ready 本身：怎么写、源码里发生了什么、什么情况下会不执行，最后给一份不依赖 jQuery 的最小实现。适合已经把 jQuery 用进项目、但还没读过 core/ready.js 的同学。

边界先划清：DOMContentLoaded 与 load 各自的原生语义，旧文《DOM contentloaded 与 load 的区别》已经完整推导；defer 与 async 怎样改变脚本的执行时机，见《脚本加载策略 defer 与 async》。本文只在必要处各带一句。版本口径按 jQuery 1.9/1.10/1.11 与 2.1，浏览器考虑 IE6 到 IE11、Chrome 35、Firefox 30、Opera 12。

为什么需要 ready

问题的起点很朴素：脚本放在 head 里时，它执行的时刻文档才解析到最上面，正文里的元素一个都还不存在。

$("#nav") 返回的是一个空集合，jQuery 对空集合调用 find、bind 都不报错，于是这段代码”成功运行、什么都没做”。这是新手最难查的一类 bug：控制台干净，功能就是不出现。

把脚本挪到 </body> 之前能解决这一问题，但那是靠位置赌时序：将来有人为了合并脚本把它挪回头部，或者页面结构改由脚本渲染，绑定就再次失效。稳妥的做法是把两件事解耦——脚本什么时候执行，与 DOM 什么时候可用，本该由两个不同的机制说明。所有库都要解决这个问题，因为各家浏览器给出的是三种不同的通知方式：标准浏览器派发 DOMContentLoaded，老 IE 只有 readystatechange 且状态变化不止一次，再老的环境只能靠轮询探测。jQuery 把这三条路径收进一个 ready，让调用方只面对一个承诺：DOM 可以用之后，把你的回调执行一次。

执行时机与顺序

把顺序问题说清楚，调试时就能省掉一半猜测。

第一，多个 ready 处理器按注册顺序执行，不存在”谁快谁先”。回调队列就是 readyList 这个 Deferred 的 done 列表，先进先出。

第二，ready 在 DOMContentLoaded（或它的等价信号）之后触发，并且只触发一次。一次的意思是 isReady 置位后队列不再重开；但”只触发一次”不等于”只可能执行一次”——isReady 之后再调用 $(fn)，fn 会立即被执行，因为队列已经是完成状态。这正是动态注入场景的救命机制，下面走读源码时细说。

第三，ready 里异步注入的 DOM，ready 管不到。这一点很容易忽略：

针对新节点的操作必须放在注入回调之后。widget 若会被反复加载，就把这段绑定抽成函数、每次加载完成后调用一次，并留意别在同一节点上重复绑同一个 handler。

第四，ready 不等图片、不等 iframe 内容，通常也不等外部字体加载完成。要不要等图片，判断标准只有一条：你的逻辑是否依赖资源的实际尺寸或内容。轮播按图片高度定位、灯箱读原图尺寸，那是 load 的活；点按钮、读文本、渲染列表，一律 ready。两者的分界旧文已讲透。

第一，completed 里那个条件不是多余的。document.addEventListener 为真时直接认——标准浏览器只有 DOMContentLoaded 和 load 会走到这里；addEventListener 不存在的老 IE 走 attachEvent，而 onreadystatechange 在一次加载里会触发多次（loading、interactive、complete），必须只认 readyState === "complete" 那一次，否则 ready 会被提前 fire。这个能力判断区分的是”我此刻收到的是哪个事件模型的信号”。

第二，doScroll 轮询只在顶层文档启用。window.frameElement == null 包在 try/catch 里，因为跨域 iframe 上读 frameElement 会抛异常；而在 iframe 内部，document.documentElement 没有可滚动的视口，doScroll 探测不成立，所以 jQuery 不在 iframe 里轮询，退回 onreadystatechange 加 onload——源码注释那句 “maybe late but safe also for iframes” 说的就是这件事。

第三，关于 Opera。Presto 内核（Opera 12 及以前）在当年的实测记录里，DOMContentLoaded 与外部样式表应用的相对顺序不如其他内核稳定，容易出现”ready 已触发、样式还没生效”的窗口。有意思的是，jQuery 源码里没有任何 Opera 专属分支——1.4.4 里只剩一句 “Mozilla, Opera and webkit nightlies currently support this event” 的注释，1.9.1 里连浏览器名都搜不到，早期的 $.browser 嗅探在这个版本已被移除。它的策略是不给任何内核开后门，而是让三条路径互相竞争，谁先到算谁的，配合 detach() 保证只认第一个。这种”不做特判、只做兜底”的写法值得学：特判会随版本失效，兜底不会。

第四，绑定时机与”已经过期”的处理。readyState === "complete" 那条分支专门负责迟到场景：文档整体加载完了、事件早就过去，那就直接 fire。1.9 把这段判断放在 ready.promise() 内部，配合 Deferred 的完成记忆，迟到的 $(fn) 会同步执行。顺带说一个源码注释里公开的往事：官方在同一个位置写过”我们曾在这里试用 readyState 的 interactive，结果引出 ticket #12282 那一类问题”，最终只认 complete。老 IE 的 interactive 与标准浏览器的 interactive 并不同步，拿它当”DOM 已就绪”是不可靠的——这个细节下一节第一个坑会用到。

三个真实坑的复盘

坑一：动态注入的插件脚本里 $(function () {...}) 在老 IE 上时灵时不灵。

现象是这样的：主站用动态注入加载一个第三方组件，组件内部照着常见写法注册 ready。在 Chrome 和 Firefox 上一切正常，在 IE7/IE8 上有相当概率整块初始化不执行，页面少一个交互，控制台无报错。

原因在于”迟到”。动态注入的脚本开始执行时，DOMContentLoaded 很可能已经派发过、监听也已解绑；此时 ready 只能靠 readyList 的完成状态或 readyState === "complete" 那条兜底分支来救。老版本 jQuery（1.4 及以前）在这个位置只认 complete，而老 IE 的 readyState 在文档解析完毕、子资源仍在加载的漫长区间里停在 interactive，既不等于 complete，onreadystatechange 又不会再给你一次机会——回调被推进队列，然后永久躺在那里。后来版本加固了兜底（Deferred 的完成记忆加 complete 判断），这个坑才算被封住。但把脚本的正确性押在库的兜底演进上并不可靠，尤其你还得同时支持 IE6 到 IE11。

坑二：在 ready 里做 DOM 测量，拿到的是回退字体的宽度。

需求很常见：侧栏导航的宽度要按文字实际排布算，或者自适应的标签条要在 ready 时测量每个标签的偏移。问题是 ready 只承诺 DOM 结构可用，不承诺 @font-face 的 web 字体下载并应用完成。字体到达后，同一句 $("#nav").width() 的结果会变，于是布局错位、标签条溢出，Chrome 35 与 Firefox 30 上表现还不一致。当时的处理思路有两条：把测量推迟到 load（代价是晚很多，而且被图片拖慢），或者做字体检测轮询——先用隐藏元素以 serif 与 monospace 两种本地字体量出基准宽度，再不断用目标字体家族重测，两个基准都变了就说明字体到了。这套做法在旧文《字体加载与 FOIT、FOUT 问题》里有完整代码和各家浏览器的行为差异，这里不展开，只强调结论：任何依赖文字度量的代码都不该写在 ready 里，包括用 offsetWidth 判断换行、算居中偏移、给图表定刻度。

什么时候值得自己写？只有当入口代码确实只有一两行、且明确不需要跨浏览器事件绑定、选择器扩展和 Ajax 的时候。页面一旦有十几个交互点，维护这套兼容性代码的成本会迅速超过引入库的收益；何况它没有 holdReady、也没暴露 isReady，跨模块协作时你又会把它补成 jQuery 那个样子。

一些工程规范

把前面的内容收敛成可执行的项目约定：

  • 入口脚本里只做初始化调用，不做定义、不做计算。一个页面的头部脚本理想状态是 $(app.init) 一行。
  • 初始化与定义分离：模块导出 init，ready 只是它的调用时机之一。动态注入、单元测试、手动重试才能复用同一段代码。
  • 不写嵌套 ready：ready 里再套 $(function(){...}) 看着像”再等一次”，实际只是立即执行，还会掩盖真实的依赖关系。要串行就写回调或队列。
  • 等资源的放 load，等结构的放 ready，等数据的放请求回调——三者不要混在一个 ready 里靠延时凑。

小结

ready 只做一件事：把”脚本执行”和”DOM 可用”两条时间线解耦，把标准事件、老 IE 的 readystatechange 加 doScroll 轮询、load 安全网三条路径收敛成一次通知。写法上 $(fn)、$(document).ready(fn)、jQuery(fn) 走的是同一条通道，.on("ready") 只是源码里那句 trigger 留下的兼容口，参数不同、迟到即失效，新代码不必再用。实现上记住三点：readyList 是 jQuery 自己的 Deferred（不是浏览器原生对象，状态完成后同步执行新回调），jQuery.ready 靠 isReady 保证幂等，兜底判断只认 complete 而不是 interactive。真正要留神的是动态注入的脚本得自己判状态、依赖文字度量的代码不该写在 ready 里、holdReady 每次 hold 都要在失败路径上配对释放。位置决定时机，状态决定行为——把这两句对上，ready 相关的坑基本就绕开了。
