JavaScript 柯里化与偏函数应用

柯里化（currying）和偏函数应用（partial application）是前端圈里最容易被混着说的两个词：贴一段”把 f(a,b,c) 变成 f(a)(b)(c)“的代码，标题却写着”偏函数”；反过来也常见。本文先把两者的定义钉死，再给出可以直接抄进项目的 ES5 实现，然后用四个真实场景说明它在工程里到底怎么用、能省掉什么样的样板代码。最后必须泼一盆冷水：它的可读性代价、性能代价、以及会悄悄破坏 fn.length 这个很多库都在依赖的元信息。适合写过回调、正在纠结”要不要在团队里推函数式风格”的同学。

偏函数应用与柯里化：先把两个词分清

一句话版本：偏函数应用是”固定掉一部分参数，得到一个参数更少的函数”；柯里化是”把一个多参数函数改造成逐参数调用的嵌套一元函数”。两者的产物都是”参数更少的函数”，这就是它们被混用的原因，但改造规则完全不同。

柯里化的名字来自逻辑学家 Haskell Curry（函数式语言 Haskell 正是以他命名），它的理论动机是”所有函数都只接受一个参数”，多参数靠返回新函数来串联。偏函数应用没有这层洁癖，它的动机非常务实：某个参数在你的调用点上是常量，就别每次重复写了。

工程上我更看重这个区别：柯里化对参数顺序有强约束（必须从最左开始一个个收），而偏函数应用可以配占位符跳过前面的参数。所以实践里偏函数用的多、柯里化用的少，后面所有用例基本都落在 partial 上。

通用实现：partial 与 curry

支持占位符的 partial

arguments 转数组用 Array.prototype.slice.call，这是 ES5 时代唯一稳妥的写法（IE8 对非 Array 的 slice.call 有时要手写循环，DOM NodeList 场景里注意）。占位符我用一个唯一的空对象引用即可，不必依赖 Underscore 导出的 _。

三个细节值得注意。第一，this 用 apply(this, merged) 透传，否则当对象方法用就丢了上下文。第二，这个实现只做一次填充：占位符没等到实参时，P 会原样留在 merged 里传进原函数。我刻意不支持”分几步把占位符填完”，因为分步语义会让参数最终顺序更难推断（lodash 2.4 的 _.partial 在这方面支持得更完整）。稳妥做法是在调用原函数之前补一句 if ($.inArray(P, merged) >= 0) { throw new Error('参数未填满'); }，让它早失败而不是把空对象喂进业务逻辑。第三，也是最常见的坑：要固定的参数必须在形参列表最前面，否则你就得写一堆 P，此时更该改用配置对象。

基于 fn.length 递归的 curry

严格版柯里化每次只收一个参数，把 arguments.length !== 1 视为错误。上面这个宽松版更符合 JS 的习惯，也更实用——它不强迫你改变调用方式。arity 参数是刻意加的，原因见下一节。

arguments.length 与 fn.length 的坑

fn.length 是声明的形参个数，arguments.length 是实际传进来的个数，两者在 JS 里可以任意不一致。柯里化把 fn.length 当作”收满没有”的判据，于是踩到三个坑：

  1. 可选参数。function parse(s, strict, cb) { cb = cb || noop; } 声明了 3 个形参，curry(parse) 就会死等你传满 3 个才调用。这类函数必须显式给 arity：curry(parse, 1)。
  2. 参数适配器、arguments-only 函数（function sum() {}）的 length 是 0，递归版 curry 会立刻调用或无限返回函数，所以我在实现里加了 need <= 0 抛错，宁可早失败。
  3. 包装之后 length 丢失。partial 返回的是 function () {}，length 是 0；curry 同样。JS 里 fn.length 不可写（非 writable），但它是 configurable 的，可以用 Object.defineProperty 手动修正——这个细节在后文讲异步流程库时很关键。

顺带一个经典案例：['1', '2', '3'].map(parseInt) 得到 [1, NaN, NaN]，因为 map 传了 (val, index, array) 三个实参，而 parseInt 声明了两个形参、length 为 2。柯里化与 map/forEach 混用时同理：curry(fn) 遇到 map 多塞的 index 会提前满足 all.length >= need，然后把这些多余参数原样灌给 fn。习惯写 arr.map(partial(fmt, 'short')) 之前，先确认 fmt 不会因为多出第三参数而行为改变。

bind 与 $.proxy：偏函数应用的官方入口

Function.prototype.bind（ES5 2009 年定稿，浏览器侧 IE9+ 原生支持，IE8 需要 polyfill）本身就同时做了两件事：绑定 this，以及偏函数应用。

bind 和 partial 的差异值得记牢：

  • bind 会永久绑死 this，作为构造函数时（new Bound()）按规范忽略 thisArg，仍然创建新对象；partial 用 apply(this, merged) 透传，谁调就用谁的 this。这意味着 partial 更适合挂到原型方法上，bind 更适合回调。
  • bind 会正确计算包装函数的 length：Math.max(目标函数 length - 已绑定参数个数, 0)。这一点比多数手写 partial 优秀，也是我建议能用 bind 就别自己造轮子的理由之一。
  • bind 不支持占位符，只能绑头部参数；bind 出来的函数在 Chrome 调试栈里显示为 bound fn，比匿名包装函数可读。
  • 老引擎上 bind 的 polyfill 是 MDN/ES5-Shim 里那三十行，注意它修不了 length，也别在 IE8 上指望 boundFunction 的栈提示。

jQuery 侧要留意 $.proxy 与 bind 的分工：

$.proxy 在 jQuery 1.9 之后会把原函数的 guid 复制到包装函数上，这在实际项目里很关键：off('resize', handler) 时传同一个 handler 能正确解绑；而 bind/partial 出来的函数没有 guid，你必须自己保存引用，否则只能 off('resize') 全清，容易误伤其他监听。另外 $.proxy(target, name) 这种”按名字”的形式在方法被重新赋值后仍然指向当时取到的函数，做插件上下文切换时要心里有数。

代价：可读性、性能与被破坏的 length

必须诚实说明：上面那些改造都不是免费的。

可读性与调试。偏函数化的每个包装层都是栈里一个匿名函数。当 citySearch('杭州')('西湖区', '咖啡') 报错时，Chrome 调用栈会给你 memoize 内部函数 -> partial 内部函数 -> search，前两层的参数在 Console 里要手动展开 arguments 才知道到底是什么。团队里新人接手，光是”为什么这个函数少两个参数”就能问一下午。我的纪律是：任何 partial/curry 的产物必须落到具名变量（var info = ...），禁止 partial(log, 'info')(...) 这种就地嵌套两层的写法。

性能。包装意味着多一次函数调用、两次 slice.call 把 arguments 拷成数组、一次 concat。粗略计时（100 万次两参调用，取多次运行的中位数，数值只作数量级参考，不同机器不可换算）：

写法 Chrome 33 / V8 Node 0.10 IE8
直接 f(a, b) 约 5 ms 约 4 ms 约 260 ms
bind 一次后调用 约 9 ms 约 7 ms 不支持
手写 partial 后调用 约 16 ms 约 12 ms 约 480 ms
curry 三级链式 约 40 ms 约 30 ms 约 950 ms

结论很直白：V8 会把小包装内联掉，差距在 Chrome 里几乎可以忽略；但 IE8 上每层包装肉眼可见地加钱，而我们的老项目恰恰要支持 IE8。滚动、requestAnimationFrame 动画、长列表渲染这类每帧执行的路径，我一律不用 arguments 拷贝版本，直接手写具名闭包。

fn.length 被破坏的连锁反应。这个坑最隐蔽。很多库靠回调的形参个数来决定行为。Express 4（2014 年 4 月发布）的错误中间件识别就写死了 fn.length !== 4 直接放行到下一层——你把一个 (err, req, res, next) 中间件用 partial(mw, cfg) 包一层，length 变成 0，它会被当成普通中间件，错误分支静默失效，这是最难查的一类线上问题。async 0.1 时代的 auto 也曾根据 callback.length > 1 决定把前置结果作为数组传进来（这个特性后来被移除了，但”读形参个数”的思路在各家流程库里都还活着）。修法有两层：实现 partial 之后用 Object.defineProperty(wrapper, 'length', { value: Math.max(fn.length - 已填个数, 0), configurable: true, writable: false }) 显式修正（IE9+ 可用，lodash 2.4 内部也是这么处理的）；工程层面则是——在给 Express 中间件、异步流程库传任务的地方禁用偏函数。

最后一条是管理层面的：偏函数是一种”隐式约定”，它把参数含义从调用点挪到了定义点。团队里要用，先定规范：只允许固定字符串/枚举/上下文对象这类稳定前缀参数；禁止固定易变的业务值；curry 链式不超过两级；新工具函数一律进 utils/func.js 并配单元测试。没有这套约束，半年后你会在仓库里看到七种不同实现的 partial，以及一批”看起来少个参数其实少了个参数”的幽灵 bug。

什么时候不要偏函数化

我总结了几个明确的”不要”：

  1. 参数只有两个且调用点很少。partial(f, x) 换来的收益，抵不上读者去查 x 从哪来的一次上下文切换。三个以上调用点才值得动手。
  2. 函数依赖可变参数。任何 function () { var args = arguments; } 形态的函数（_.extend、自己写的 union）被 partial 之后语义就坏了，因为你无法表达”剩余参数从第 N 位开始”。
  3. 需要固定中间参数、而前后都还会变。写一堆 P 占位符等于给自己埋雷，这种需求应该用配置对象或高阶函数解决。
  4. 性能敏感的每帧路径，尤其是还要跑在 IE8 上的代码。
  5. 要传给依赖 fn.length 的流程库或第三方适配器。

反过来，值得偏函数化的三种信号：

  • 同一个实参在三个以上调用点重复出现（'info'、'GET'、'json'、locale），它是噪音而不是信息；
  • 形参列表存在”稳定前缀 + 易变后缀”的自然分层，稳定的是模式/目标/上下文，易变的是载荷；
  • 接口只接受无参回调（setTimeout、$.Deferred.done、事件 handler），但你手上是一个带参函数——这时 partial 是比手写 IIFE 更表达意图的写法。

组合子要求每个环节”一进一出”，柯里化恰好能把多参函数切成一元链——这才是 curry 在 JS 里最有价值的用法；partial 则负责在链条之外派生具名工具函数。两者是分工关系，不是替代关系。

库的现状（截至本文写作时）：Underscore 1.6.x 有 _.partial、_.bind、_.bindAll、_.compose，但没有 _.curry（社区多次拒绝加入，需要的话得引 underscore-contrib）；lodash 2.4.x 则提供 _.curry（可显式传 arity，内部会尽量修正包装函数的 length）、带占位符的 _.partial（占位符就是 Underscore/lodash 自己导出的 _）、_.flow、_.ary、_.once、_.wrap。所以现实建议是：项目里已经有 lodash 就别自己造 partial/curry，直接用 _.curry、_.partial，它们处理过的边界（length 修正、占位符、arity 覆盖）比你我二十行实现更周全。但要用得明白——_.partial(fn, _) 里的 _ 是模块引用而不是 lodash 的链式语法糖，一旦页面里 noConflict() 或者局部变量遮蔽了 _，你的占位符就静默失效。这个坑，我们今年三月踩过。

小结

偏函数应用是”固定一部分参数得到更少参数的函数”，柯里化是”逐参数嵌套调用”，两者产物相似但规则不同，工程上真正天天用的是前者。partial 适合的场景很集中：循环里绑定 index、从 log(level, msg)/ajax(method, url) 派生具名工具、适配 (err, data) 回调、配合 memoize 做分组缓存；curry 更多是给 compose/pipe 铺路，不要拿它替代普通多参调用。Function.prototype.bind 已经内置了偏函数能力并且能正确修正 length，jQuery 项目里 $.proxy 还额外解决了 guid 和解绑问题。代价同样真实：匿名包装层让调用栈变难读、arguments 拷贝在 IE8 上是可测量的开销、fn.length 被破坏会让异步流程库的行为悄悄翻转。所以要用就先定规范：只固定稳定的前缀参数，产物必须具名，每帧路径和流程库回调处不用它。
