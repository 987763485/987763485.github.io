CSS3 滤镜 filter 与混合模式 blend-mode

本文属于《HTML 与 CSS》第 42/62 篇
上一篇系列目录下一篇

2014 年做图片列表和运营页，多半碰到过”图要置灰””hover 要有阴影””水印不能被背景吃掉”这类需求。让切图师多切一套灰图、再切一套 hover 态是过去的常规解法；-webkit-filter 与混合模式出现后，一部分需求可以只在浏览器里做。但滤镜是逐像素的实时计算，手机上算不快、也算不起。本文不罗列效果，而是站在性能与调优的角度，把滤镜函数族、混合模式、支持面、降级写法与何时该退回服务端出图讲清楚。

同名陷阱：IE 的老 filter 不是 CSS 的 filter

这是本文最想先钉死的一件事，当年兼容代码里一半事故都来自它。

IE6 到 IE8 有一个私有属性也叫 filter，值是一串 progid: 开头的 COM 组件调用：

它工作在另一套机制之上：元素必须有 hasLayout（所以常见配套写 zoom: 1），滤镜由 IE 自己的渲染管线实现，只作用于元素盒子。IE9 改用 Direct2D 重写渲染层后，AlphaImageLoader、Gradient、Blur 这批滤镜绝大部分直接失效。而 filter: progid:... 对现代浏览器是非法声明，会被整条丢弃。

问题是两者共用同一个属性名。有人喜欢把所有兼容写法堆进一条规则：

按层叠规则，同一个声明块里后写的合法声明覆盖先写的。支持 filter 的浏览器里 progid 非法被忽略，看着”侥幸能用”；只认老 filter 的 IE8 里 blur(3px) 非法被忽略，剩下 progid 生效。真正出事的是另外两种情形：浏览器把 filter 认作合法属性却不实现滤镜函数，以及规则被拆到不同文件、合并后加载顺序变了。我们线上就有一次：样式合并后顺序颠倒，Chrome 里灰态失效、IE8 里的模糊变成一整块黑。

结论只有一条：老 filter 永远只放在 IE 条件注释引入的独立样式表里，绝不和 CSS 滤镜写进同一个声明块。

filter 函数族速查与两个重点

-webkit-filter 接一个函数列表，按书写顺序串联，前一个的输出就是后一个的输入。每个函数都对应到 SVG 滤镜规范里的一个原语（feGaussianBlur、feColorMatrix 等），这层对应关系决定了它的开销。

函数 取值 等价的 SVG 滤镜做法 性能提示
brightness(n) 0 起，1 原样 feComponentTransfer linear 一次乘算，最便宜
contrast(n) 0 起，1 原样 feComponentTransfer 近似 便宜，但会改变文本对比度
saturate(n) 0 起，1 原样 feColorMatrix saturate 便宜
grayscale(n) 0 到 1 feColorMatrix matrix 便宜，适合动画
sepia(n) 0 到 1 feColorMatrix matrix 便宜
hue-rotate(deg) 任意角度 feColorMatrix hueRotate 便宜
invert(n) 0 到 1 feComponentTransfer invert 便宜，别用于正文色板
blur(radius) 必须带单位 feGaussianBlur，stdDeviation 约为半径一半 全场最贵，随半径与面积线性增长
drop-shadow(x y blur color) 单个阴影 feOffset + feGaussianBlur + feMerge 比 box-shadow 明显贵
url(#id) SVG 滤镜引用 自定义滤镜链 复杂链是重灾区

两点值得单独说。

其一是 blur 的半径。它是高斯模糊，实现上一般拆成横向、纵向两趟卷积，代价约与”半径 × 像素面积”成正比，而不是很多人以为的与半径平方成正比。所以 6px 在桌面毫无压力，20px 开始吃帧，40px 以上在手机上基本属于”点了等半秒”。半径必须带单位，写 blur(10) 是非法声明、整条规则被丢掉。

其二是 drop-shadow 与 box-shadow 的差别。box-shadow 是盒子级的，永远画在外接矩形上，可以 inset、可以用 spread 扩张、可以逗号写多层，代价很低。drop-shadow 作用于元素最终渲染结果的 alpha 轮廓：PNG 抠出的不规则图标、clip 裁出的多边形、带透明通道的 logo，它的阴影才贴着真实形状走。代价是必须先有带 alpha 的位图再做模糊合成，比 box-shadow 贵不少，且没有 inset 与 spread；一条 filter 里串多个 drop-shadow 是叠加到上一步结果，不是并列多层。

混合模式：mix-blend-mode 与 background-blend-mode

混合模式解决的是”这一层怎么和它下面的层混色”，取值语义直接对应 Photoshop 的图层模式下拉：multiply（正片叠底，变暗）、screen（滤色，变亮）、overlay（叠加，加强对比）、lighten（变浅，逐通道取大）、darken（变深，逐通道取小），另有 color-dodge、hard-light、difference、hue、saturation、color、luminosity 一整套。

两个属性的区别只在作用对象：background-blend-mode 混的是同一元素内部的多个背景层（多层渐变、多张 background-image），不参与文档层叠；mix-blend-mode 混的是这个元素与它背后已绘制好的内容，是真正参与布局的元素级混合。

关键约束是混合范围。mix-blend-mode 只在同一个”隔离组”（isolated group）里混色，而元素一旦创建层叠上下文就自动成为隔离边界——定位元素、opacity 小于 1 的元素、带 -webkit-filter 的元素都会截断混合。想让混合只发生在预期的一小组元素内部，就用 isolation: isolate 显式造边界，比给父级塞 opacity: 0.999 的偏方干净。

下面这个需求很典型：图片置灰，右下角压一个白色文字水印，且水印不能被灰底吃掉（multiply 会把白字压成底色，screen 会把灰图提亮糊成一片）。

要点有三个。第一，.hero 因 isolation: isolate 成为隔离组，水印不会去和页面背景混。第二，-webkit-filter 的灰态让 .hero-img 自成一层，混色不会被上层渐变意外带走。第三，白字水印想稳定可见，靠的不是找”神奇的模式”，而是给它半透明深色底块、把 mix-blend-mode 显式设回 normal——要”融进画面”的质感时才用 overlay。

时间点上必须说清楚：2014 年 6 月实际能用的只有 WebKit/Blink 系。Safari 7 与 iOS 7 已可实现，Chrome 稳定版这条线刚把 mix-blend-mode 打开、background-blend-mode 更早一些，Android 4.4 的 WebView 可用、4.2 及以前不行，Firefox 还在测试渠道推进（background-blend-mode 年中正式版尚未全面可用，请按实测判定），IE 完全没有、也别指望降级。检测方式和滤镜同理：

性能与调优：滤镜贵在哪

先给结论：filter 是逐像素操作，写进 CSS 不等于免费。桌面 GPU 上大多数函数确实量不出来，移动端和老 WebKit 上是另一回事。

一张 1920 × 1080 的运营大图在不同滤镜下的实测（同一张 JPG，解码完成后触发重绘，取三次中位数；桌面机 Core i5 + HD 4000 + Chrome 34，手机为 Android 4.0 原生 WebView）：

场景 Chrome 34 桌面（单帧） Android 4.0 WebView（单帧） 滚动帧率表现
无滤镜 约 1 ms 约 6 ms 满帧
grayscale(1) 约 3 ms 约 24 ms 满帧，手指滑动轻微掉帧
blur(4px) 约 8 ms 约 62 ms 明显卡顿，约 15 fps
blur(10px) 约 17 ms 约 180 ms 严重掉帧，约 5 fps，有可见延迟
blur(20px) 约 41 ms 约 470 ms 基本不可交互
drop-shadow(0 0 10px #000) 约 13 ms 约 96 ms 列表滚动时逐帧掉帧
grayscale(1) blur(10px) 串联 约 22 ms 约 205 ms 两个函数的开销近似相加

几点值得记住。串联的开销近似相加，因为滤镜链要逐个跑完整个像素缓冲；blur 随半径与面积都近似线性，4.0 上 180 ms 意味着一次点击的反馈要等下一帧；drop-shadow 在手机上贵得不成比例，因为带 alpha 轮廓的模糊在那批实现里还有较多 CPU 参与。

为什么滤镜一定要独立合成层？浏览器要先把元素光栅化到一张纹理，再对纹理跑滤镜，最后交给合成器。这意味着三件事：纹理占显存与内存（1920 × 1080 的 RGBA 纹理约 8 MB，还没算中间缓冲）；元素从普通绘制变成”层”，出现层爆炸；重绘代价从局部脏矩形变成整张纹理重传。

由此推出动画的代价。-webkit-filter 一旦进了 transition 或 animation，每帧都要重跑像素链并上传纹理，它不是 transform/opacity 那种能交给合成器的动画。经验值是：单个元素 300 ms 内的灰度渐变在桌面尚可，同一屏超过 5 个元素同时做滤镜动画，Android 4.x 一定卡。替代方案按优先级排：

第一，预渲染多档图片。hover 变色、置灰、加深这类固定效果，让构建脚本或图片服务一次出多个变体，前端只切 src 或用 background-image 做 opacity 交叉淡入——opacity 动画合成器友好，代价远低于滤镜。

第二，静态 SVG 滤镜。效果不随时间变化时，把 feColorMatrix 定义好、只用 url() 引用，浏览器有机会走更省的路径，还顺带解决 Firefox 只认 url() 的问题。

第三，半透明渐变叠加模拟。”变暗””压色”这类需求，一条 linear-gradient(rgba(0,0,0,.35), rgba(0,0,0,.35)) 叠在背景层上，或一个绝对定位的遮罩 div，视觉上接近 brightness(0.7)，代价只是一次混合。

再说一个被反复问到的现象：hover 第一次触发灰度动画特别慢，第二次就顺了。这不是错觉。首次触发时浏览器要做的是：把元素提升为合成层、分配纹理、首次光栅化子树、初始化滤镜链与中间缓冲、跑第一遍着色；后面几次只是复用已有的层和链，图片自身的首次解码也常压在同一帧上。缓解有两个办法：时长放到 250 ms 以上并用 transition 而不是瞬间切换（瞬间切换会把首帧耗时暴露成闪烁）；或在元素临近屏幕时用一个 visibility: hidden、同样带滤镜的副本提前”预热”这条链。预热要放在 load 之后、只对屏幕内元素做，写进 scroll 回调记得节流：

最后一个案例是内存。有一次信息流首页给 30 多张封面图统一加了 -webkit-filter: grayscale(1)，iOS 6 Safari 一进列表页就白屏重载。原因是每张图独立成层，各自保留 RGBA 纹理和中间缓冲：30 张按 640 × 427 算是约 30 × 2.6 MB，页面内存从 120 MB 涨到 300 MB 出头，撞上系统水位被回收。修法三步：列表灰度改由图片服务出灰图，前端只留 hover 那一个元素的滤镜；同屏最多一个滤镜层；长列表做懒加载与离屏清理。此后我们定了条硬规矩——列表页不用滤镜做常态效果。

工程做法：能交给服务端的就别留给浏览器

职责边界很清楚：静态、可预期、大面积的效果归服务端；hover 高亮、按下反馈、拖拽预览这类瞬时交互态归前端滤镜。判断标准很简单——这个效果会不会同时出现在十几个元素上、会不会在滚动里持续重绘，只要答”是”，就回图。

2014 年各家图片服务已经足够便宜：阿里云图片服务的样式后缀（参数式写法如 ?x-oss-process=image/resize,m_lfit,w_300，更早是 @300w_200h 这类样式串）、又拍云的图片处理样式、自建 ImageMagick 批处理，都能把缩放、裁切、灰度、加水印一次做完：

渐进式占位是滤镜另一个正当用途，也最容易被滥用：把原图缩到 16 - 32 像素宽、压成极低质量、以 data URI 内联在 HTML 里当背景，先显示并 blur(20px) 遮住马赛克，真图加载完后交叉淡入并去掉模糊：

代价要认清：低清纹理是常驻的；从 blur(20px) 到 blur(0) 是每帧重跑的动画，等于把最贵的函数放在最需要流畅的时刻。我们的取舍是占位只用低清图放大 + opacity 淡入，不做模糊动画；非要保留就把半径压到 6px 以内，且只在首屏一张主图上做。

还有一类误用是拿滤镜给图标变色。图标换色该走 color，做法与坑在旧文《CSS 图标字体 iconfont 的使用与制作》里写过：字体图标的颜色天生由 CSS 控制，用 brightness()、invert() 改色会把抗锯齿边缘一起算糊，还白搭一个合成层。滤镜该管位图，不该管矢量。

无障碍与视觉纪律

滤镜改的是像素，不改语义，这正是它最危险的地方。

第一是对比度。WCAG 2.0 要求正文与背景对比度不低于 4.5:1，大字号（约 18pt 常规或 14pt 加粗）不低于 3:1。而 contrast(0.6)、brightness(1.2)、saturate(1.5) 都会让实际渲染色偏离你选的色板，invert 更是直接翻转关系。所以验收要在滤镜跑完之后取色核算，而不是看 CSS 里那两个 color 值。我们的做法是：带滤镜区域里的文字一律放到滤镜之外的层上。

第二是状态表达。灰态、已读、不可点、审核中，不能只靠 sepia() 或 grayscale() 传达——色觉障碍用户分不出”彩色”和”轻微泛黄的老照片”，屏幕阅读器更不知道。CSS 滤镜无法改动 DOM，辅助技术读到的还是原来的 alt 和结构，所以要保留真正的状态属性：

灰化用滤镜做视觉，disabled / aria-disabled 负责语义，再配一个不依赖颜色的线索（图标、文案”已下线”、边框样式），三者到位才算完整。同理，别用 blur 表示”不可用”——模糊对所有人都是不可读的，又什么都没告诉辅助技术。

小结

老 IE 的 filter 与 CSS 的 filter 只共用一个名字，两套机制毫无关系，写进同一个声明块是当年最容易翻车的地方，IE 兼容必须走独立样式表。函数族里除 blur 与 drop-shadow 都很便宜：blur 随半径与面积线性变贵，drop-shadow 只在要贴合 alpha 轮廓时才值得。2014 年的支持面还很碎：函数写法实际靠 WebKit/Blink，Firefox 只认 url()，IE9/10 什么都没有，混合模式只有 WebKit/Blink 可用，所以”检测 + 类名分支 + 静态图回退”三件套缺一不可。性能上的核心结论是滤镜强制独立合成层、一进动画就每帧重跑像素链，常态效果交给图片服务，前端只留交互态那一个元素。最后，滤镜只改像素不改语义：对比度要在滤镜之后取色，状态要留在 aria 与 DOM 属性里。
