jQuery 1.9 与 2.0 的差异及升级

本文是一次升级复盘：我们把几个在产项目从 jQuery 1.7/1.8 挪到 1.11 与 2.1，踩的坑大多不在业务代码里，而在”某段三年前的代码恰好依赖了 jQuery 的一层兼容垫片”。适合手上还背着 1.8 及更早版本的人看，读完能拿到一份 1.9 变更对照清单、一个双版本共存的做法，以及一份可抄的 checklist。

为什么是两条分支同时维护

jQuery 团队在 2013 年做了个大胆决定：把产品线劈成两条。1.9 发布于 2013 年 1 月，是 1.x 里第一个动刀删 API 的版本；2.0 在 2013 年年中跟上，只做了一件事但很彻底——不再支持 IE 6/7/8。此后两条分支保持 API 对齐：2.0 有什么能力，1.10 就有什么能力，只是 1.x 额外背着老 IE 的兼容层。到 2014 年上半年，官方口径已经是”1.11 与 2.1 并行发布”，选哪个由你的浏览器支持矩阵决定，而不是由”哪个更新”决定。

选型维度从”版本号大小”换成”有没有 IE 包袱”，很多争论自动消失。我们写进团队 wiki 的口径很短：公网移动端一律 2.1；需要 IE8 的内网与政企后台一律 1.11；既不要求老 IE、依赖树里也没硬骨头的历史页面，才允许从 1.8 直接评估 2.1。

1.9 的破坏性变更清单

1.9 值得单独拎出来，是因为它是”删除”而不是”废弃”：1.7/1.8 只是给某些 API 挂 deprecate 警告，1.9 是真删。下面每项都按变更、为什么、现象、修复来写。

移除 $.browser

变更：$.browser 这一整块没了。为什么：嗅探一旦进了代码就会被当成事实标准，而 UA 从来不可靠——当年的 Chrome 里写着 Safari，手机浏览器大量伪装成 PC 端。官方建议改用特性检测，配合 Modernizr（我们用的 2.8）给根元素打类名。

现象：最阴的一项，因为它不报错。内部日历组件里有 $.browser.msie 的版本分支，升 1.9 后条件恒假，IE8 下遮罩层整体错位。测试只跑了 Chrome，上线第二天运营来问”后台在财务那台 XP 机器上是不是坏了”。

移除 .live()/.die() 与 .selector

变更：.live()/.die() 删除，改用 .on()/.off() 的委托形式；.selector 在链式调用之后不再维护。为什么：.live() 只能挂在 document 一级，没有命名空间、没有事件数据、没法按容器缩小作用域；而 .selector 存在的意义本来就是给 .live() 反查选择器串。

现象：自研的表格插件用 $(this).selector 反解容器再拼子选择器，1.9 下这里拿到 undefined，拼出来就是 "undefined .row"，直接抛”未识别的表达式”。

修复：委托写全，容器作为配置项显式传入，绝不从选择器字符串反推。

attr 与 prop 彻底分家

变更：.attr() 只读写 HTML 特性，不再在取不到时回落到 DOM 属性——特性没写在标签上就返回 undefined。为什么：checked、value、type 这类东西，HTML 特性是”初始值”，DOM 属性是”当前状态”，语义完全不同。这层分离从 1.6 就开始，1.8 还留着 attr 回落，1.9 删干净。

现象：一个”必须勾选同意条款”的校验写成 if ($agree.attr("checked"))，1.8 下靠 attr 回落”看起来能用”；1.9 之后标签上没写 checked="checked"，attr 永远返回 undefined，用户不勾选也能提交。这是业务 bug 而不是脚本报错，而且错的方向是”该拦的没拦住”。

修复与对照：

想读什么 该用哪个 1.9 后的表现
勾选框当前状态 prop("checked") 或 is(":checked") attr("checked") 只反映标签上写没写
输入框当前内容 val() attr("value") 只反映 HTML 初始值
选择器 input[value=abc] —— 按特性匹配，用户改过的值不算
已插入文档的 input 改 type 重新建元素 jQuery 不再兜住，老 IE 自己报错

顺带说 type：老 IE 里 input 插入文档后不能改 type，1.8 及以前 jQuery 内部做了替换元素来兜住这个坑，1.9 去掉这段特殊逻辑，让浏览器按原生行为报错。我们的做法是建元素时就带上 type，之后再不改。

class 操作对拼接串的要求变严

变更：1.9 重写了 class 的读写路径，按空格把参数拆成类名逐个处理，空串和多余空白不再被宽容对待。为什么：老 IE 对 className 里的空白有问题。

现象：有一处把状态类名从数组拼成字符串一次性传入的代码，数组里偶尔混进空项，拼出来首尾就带空格。1.8 下看不出问题，1.9 之后在 IE9 上有概率残留一个空类名，靠 .filter(".state-del") 统计的角标少一个。

修复：拼之前先过滤空值。

$.ajax 的 dataType 与全局事件

变更：三条。其一，期望 JSON 或 JSONP 的响应若是空字符串，1.9 之前当成功并把 null 交给回调，1.9 之后按格式错误的 JSON 处理，直接进 error。其二，全局 ajax 事件只在 document 上触发，不再落到发起请求的元素上。其三，克隆已有 script 标签”重跑脚本”的做法失效，动态加载请用 $.getScript()。

现象：最疼的是第一条。后端当年的习惯是”没数据就返回空串”，一个”保存备注”的接口成功时返回空字符串，升到 1.9 后一律走 error，前端弹”保存失败”，数据其实已经写进库了。第二条更隐蔽：写在 #status 上的 ajaxStart 静默失效，加载提示再也不出现。

修复：短期在前端加一层 dataFilter 把空串补成合法 JSON，长期推动后端统一返回结构。

JSONP 补一句：1.9 对回调挂载与脚本清理更严格，jsonp 参数名别依赖默认值，接口只认 callback= 就显式写出来；把回调名写死在 URL 里的老写法，升级时最容易”看着能用、偶尔丢数据”。

trigger 与事件对象的属性

变更：合成点击对 checkbox/radio 的状态与真实点击一致（以前取到相反状态）；focus 与 blur 改为原生顺序；attrChange、attrName、relatedNode、srcElement 不再拷进处理器收到的事件对象；"hover" 不再是 "mouseenter mouseleave" 的同义词。

现象：e.srcElement 是 IE 系写法，一处老代码读它判断点击来源，1.9 后拿到 undefined，分支恒假；.bind("hover", fn) 那处更隐蔽，不报错也不触发。非标准属性能从 e.originalEvent 上拿。

修复：全局搜 srcElement 与 "hover" 做替换。

位置伪类从选择器引擎里搬走

变更：:eq()、:first、:last 这类按位置过滤结果集合的伪类，在 1.9 的引擎重构里不再是选择器引擎的一部分，改由 jQuery 层的过滤器实现。为什么：位置过滤是集合操作而不是元素匹配，留在引擎里会拖慢原生快路径。

现象：$("li:eq(2)") 在 jQuery 里仍然能用，所以很多人升完没感觉。出问题的是把选择器串绕过 jQuery 直接丢给原生接口的插件——querySelectorAll 与 matchesSelector 只认标准 CSS，遇到 :eq(2) 就抛语法错误。

修复：选择器只做标准 CSS 匹配，位置判断挪到方法链上。

$.fn.load 与 load 事件的同名冲突

变更：1.9 收掉一批未文档化的参数分支，.load() 这个既当”AJAX 载入片段”又当”绑定 load 事件”的方法，只能靠实参个数与类型猜意图，风险随之变高。

现象：一个轮播插件在自己的作用域里覆盖了 $.fn.load 来”顺便”做初始化，结果 $(window).load(fn) 不再绑事件、$("#box").load(url) 也不再发请求，两边一起中枪。

修复：事件一律 .on("load", fn)，片段加载写全 .load(url, data, callback)；不允许任何插件覆盖 $.fn.load，我们升级时加了断言把这条钉住。

被删掉的内部 API

变更：.andSelf() 改名 .addBack()（旧名只是废弃，不是立刻消失），jQuery.sub() 挪进 Migrate 插件，一批从未文档化但被插件广泛使用的内部成员被删：jQuery.attrFn、jQuery.clean()、jQuery.event.handle()、jQuery.uuid、jQuery.deletedIds、jQuery.offset.bodyOffset()；.data("events") 也不再支持。

现象：一个图片懒加载库内部调 jQuery.event.handle.apply(...)，1.9 下直接 TypeError；自研控件读 .data("events") 统计绑定数量，返回值变成 undefined，统计全零。

修复：内部 API 没有迁移方案，只能改插件源码，改完把 diff 和原因记进内网 wiki。

2.0 换了个引擎

2.0 的全部卖点就是”不管老 IE”。听着简单，落到实现上是把 jQuery 里最厚的一层兼容代码整块抽掉，收益和代价都因此变得可观。体积是最直观的一项：官方在 2.0 发布时给的口径是”比 1.9.1 小 12%”，我们把 CI 产物用 gzip -9 实测了一遍：

版本 未压缩 压缩后 压缩再 gzip
1.9.1 约 250 KB 约 91 KB 约 33.5 KB
1.10.2 约 253 KB 约 91 KB 约 33.4 KB
1.11.0 约 270 KB 约 96 KB 约 33.5 KB
2.0.3 约 221 KB 约 81 KB 约 29.5 KB
2.1.0 约 224 KB 约 83 KB 约 29.7 KB

数字四舍五入，以官方下载页为准。1.11 的 gzip 和 1.9.1 差不多，是因为 1.x 这条线还在补 bug；拉开差距的是 2.x 少掉的那一大块 IE 分支，而移动端这 4 KB 属于首屏阻塞资源。

选择器方面，2.x 把常规匹配交给原生 querySelectorAll，Sizzle 只在遇到扩展语法或浏览器缺能力时接管。我们在一个一千多行的订单表上试过：纯属性与类名选择器两条路径差不多，带扩展伪类的还得走 Sizzle。可见”把选择器写得更像标准 CSS”在 2.x 上第一次有了实打实的性能回报。

变快的是样式与尺寸的关键路径。1.x 读样式要在两套接口之间分岔，写透明度要给老 IE 拼滤镜，取偏移要为 body 与文档根元素的差异做补偿，这些分支在 2.x 里成块消失。$.css 因此只剩原生计算样式一条路；动画队列、step、stop 接口都在，只是不再维护为 IE 准备的降级值。代价是：习惯了”传个字符串 jQuery 总能抹平差异”之后你会发现，2.x 上这层抹平的范围明显变小。

与 1.x 行为不一致的地方，我们踩到的是偏移与 box-sizing。当年全局上了 border-box 重置，1.x 在老 IE 分支上对边框与内边距做过额外补偿，2.x 更接近原生，同一个 .offset() 两边能差出一个边框宽，表现是弹层错位 2 px。修法不是调 jQuery，而是别依赖绝对偏移：锚点改用 position() 加相对定位容器。

升级过程复盘

整个升级分四周走，顺序不能换。第一步是挂上 jQuery Migrate 收集警告。

Migrate 的作用是”把 1.9 删掉的东西原样补回来，每次用到打一条警告”。它既是脚手架也是麻醉剂：只要挂着，.live()、$.browser、attr 回落全都还能跑，页面看着完全正常。我们有个项目灰度两周一切安好，摘掉 Migrate 第二天就报了三个错。所以要定一条硬规矩：警告清零后立刻摘掉，不许活过下一个版本；上线包里也不该有它，压缩后还有七八 KB，而线上的 console.warn 没人看。

第二步是顺着警告定位第三方插件。我们把警告文案按插件归类，命中的老熟人不少：jQuery Validation 的老版本、Colorbox 1.3 那一代、jStorage 和自研的几个组件，全都依赖 $.browser——当年写”给 IE6 打个补丁”的人实在太多。处理按体量分档：单文件小插件直接改源码，把嗅探换成特性判断；有维护分支的升它自己的版本；改不动的先记下，让它和 1.x 待在同一页。

第四步是回归测试，按踩坑概率排序：表单（勾选、必填、val() 与 attr("value") 的差异、动态新增行上的委托事件）；动画（opacity 过渡、stop(true, true) 的中断语义、轮播连点下的队列）；ajax 错误分支（空响应、非 200、超时、JSONP 回调名不匹配、被 abort 的请求）；事件委托（多层动态插入、命名空间解绑、trigger 与真实点击的一致性）。四类里 ajax 错误分支最容易漏，因为平时没人专门去制造一个失败响应；我们后来在测试环境留了个必定返回空串的接口，就是给升级期用的。

从插件生态看版本依赖

当年插件声明依赖哪个 jQuery 版本，主要靠三种方式：文件头注释、包管理描述文件里的依赖项、少数插件里的运行时断言。

$.fn.jquery 不起眼但有用，拿到的是当前版本号字符串。升级前我们写的第一个脚本，就是把这个断言铺到每个依赖旧 API 的插件文件头上，让它们在 1.9 下主动报错——报错比静默走错分支好一万倍。

老插件在 2.x 上”静默失效”的原因，基本都是清单里那些分支型依赖：嗅探变恒假、attr 永远拿不到值、给老 IE 准备的滤镜字符串在标准分支里忘了配平。它们没调用任何被删的方法，所以不报 TypeError，只是那条补丁路径再也不执行；而作者多数早已不更新，Issue 沉在下面，只能自己判断。

处置分三档，标准写下来后省了很多讨论：改动量小于一百行且逻辑看得懂的，改源码并在 diff 里注明原版本；同类替代品已稳定支持 1.9+ 的，换库，别舍不得；体量大、逻辑晦涩、又只有 IE8 用户会碰到的，保留 1.x，认了。第三档不丢人——把共存当技术失败去强推统一，代价往往更大。

决策与结论

该选 1.x：有 IE6/7/8 用户或内网 IE8 硬要求，后台系统、政企对接、银行控件那一类；依赖树里有改不动也换不掉的插件；团队没精力做全量回归。能上 2.x：移动端 WebView（iOS Safari 与 Android 4.x 的 WebKit 都没有 IE 包袱）、面向公网且能接受老 IE 走降级的页面、从一开始就不写嗅探代码的新项目。

我现在的判断是：升级 jQuery 不是重构，是偿还运维债务。它不改变架构、不减少业务代码，只是把你依赖的一层兼容垫片往前挪一格，收益是体积、速度和行为一致性，成本是全量回归。定性想清楚后决策会冷静很多：不要为了”用最新版”升级，要为了”少背一层兼容包袱”或”某个新插件要求 1.9+”升级；一次只升一级，不要把跨版本跳跃和一个业务需求塞进同一次发布，否则出了问题你连回滚的边界都找不到。

下面是贴在 wiki 首页的 checklist，可以直接抄：

  1. 先定浏览器矩阵，决定走 1.x 还是 2.x，而不是决定装哪个版本。
  2. 全库搜一遍这些串：$.browser、.live(、.selector、srcElement、attr("checked")、attr("type")、.data("events")、.andSelf(。
  3. 按依赖深度给第三方插件排序：先升能升的，再改能改的，改不动的列清单。
  4. 测试环境挂 Migrate，警告清零之前不谈”升完了”。
  5. 准备一个返回空串的接口和一个必定失败的接口，专门跑 ajax 错误分支。
  6. 共存页面把 noConflict(true) 的引用关系写进头部注释，标明哪片 DOM 归哪个 jQuery。
  7. 上线包摘掉 Migrate，发布单里单独列一行——它是麻醉剂，不是依赖。
  8. 升级过的页面留下 $.fn.jquery 断言，给下一个人省一次排查。

小结

1.9 与 2.0 是两回事：前者是删兼容层带来的破坏性变更，后者是不支持老 IE 换来的体积与速度。升级真正的成本不在官方清单本身，而在那些把嗅探、attr 回落、事件对象私货当成正常 API 用的第三方代码上——它们大多不报错，只静默走错分支。三条经验：Migrate 只当脚手架且必须摘掉，双版本共存是合理策略而不是失败，回归重点压在表单、动画、ajax 错误分支与事件委托上。选型时用”有没有 IE 包袱”代替”版本号大小”，很多争论根本不必发生。
