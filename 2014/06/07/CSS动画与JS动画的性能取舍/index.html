CSS 动画与 JS 动画的性能取舍

动画用 CSS 写还是用 JS 写，是项目里隔三差五就要吵一次的话题。这篇文章不展开 CSS 动画的语法和浏览器内部的推进机制（那是《CSS3 animation 与 keyframes 动画实战》的任务），只解决一个问题：给定一个交互需求，怎么判断它属于 CSS 还是 JS，两者的边界在哪里，以及怎么把两者拼起来用。适合被”为什么一上低端 Android 就卡成幻灯片”折磨过的前端同学，读完你能得到一张选型判据表、一组实测数据和一套混合写法的落地规则。

先给结论：选型判据表

本文的判据可以压缩成一句话：动画的目标值如果在写代码时就确定，首选 CSS；如果只有运行时才知道，交给 JS。 按这条线把常见需求摆一遍：

动效需求 首选 判断依据
hover、focus、active 等状态过渡 CSS transition 起止值都是预设的，输入只有”状态”
入场、退场（落点已知） CSS transition/animation 目标位置写死在样式表里
循环 loading、spinner CSS animation infinite 循环，无需中途干预
可预告的位移、缩放、淡入淡出 CSS 属性在 transform/opacity 射程内
跟随指针的拖拽、滑动 JS 指针位置是逐帧刷新的输入源
惯性甩出、弹性回弹 JS（收尾可交回 CSS） 要按速度实时算落点，且随时被打断
依赖运行时测量的路径 JS 算值 元素位置、窗口尺寸要 getBoundingClientRect
中途改目标值、反向、暂停 JS CSS 没有读取中间状态的可靠手段
时间轴编排与多元素联动 JS 管节奏 靠 delay 硬编码不可维护
Canvas、WebGL 动画 JS 根本不经过 CSS 样式体系

表里”JS 算值””收尾交回 CSS”这两类其实是混合用法，占了我们项目里大多数动效，第 6 节展开。

CSS 动画的真实优势

CSS 路线的好处是真实的，但每一条都有适用边界，不必神化。

第一，不依赖 JS 的执行，也不吃定时器精度。CSS 动画的时间轴由浏览器自己推进，同页面上有同步请求、图片解码、别的脚本在死循环，都不会把它的节奏带乱。JS 路线反过来：靠 setInterval、setTimeout 驱动的话，最小间隔被钳到约 4ms，回调还会排队漂移，长时间跑下来时间和帧率都会漂。

第二，特定属性、特定浏览器上，动画能离开主线程推进。当时 Chrome 30 之后的若干版本上，transform 和 opacity 的动画可以由主线程之外的线程推进，iOS Safari 7 也有类似行为——脚本 momentarily 卡住时画面照移动。机制推导本文不做，这里只需要记住它的限制：这只是”属性白名单 + 浏览器白名单”都命中才成立的收益。当时 Firefox 29/30 的动画推进仍与主线程关系密切，Android 4.x 的 WebView 更没法指望，所以这条不能作为普适结论写进方案。

第三，声明式，对设计交付友好。动效稿上标的时长和贝塞尔曲线，可以原样落进一行 transition 简写，设计改动就是改一行样式，不需要读 JS 逻辑。

第四，不跑 JS 也能动。声明页、邮件模板、脚本出错概率高的老页面里，这一条有实际价值。

CSS 动画的真实短板

优势说完了，短板才是选型的决定性因素。以下这些是当年（2014 年）用 CSS 动画做交互时反复撞到的墙。

其一，读不到中间状态，也改不了目标值。CSS 动画的输入只有类名：动画一旦开播，起点终点就锁死在预设关键帧里。播放中途想根据接口数据换目标位置，唯一的土办法是用 CSSStyleSheet 的 deleteRule/insertRule 重写整条 @keyframes 规则，前缀差异大、还会牵动全页重算，实践中基本没人这么干。Web Animations 规范承诺解决这件事，但它的规范和实现都还很早，不能当选型依据。

其二，无法精确表达”跟随”的物理感。拖拽时元素位置是指针坐标的函数，每一帧都在变；transition 只会对两个端点插值。用 cubic-bezier 可以逼近 iOS 7 那种减速手感，但贝塞尔曲线只能描述”一次性”的变化，过冲之后再振荡回弹、或者用户中途反手拽回来，都表达不了。

其三，结束回调不可靠。animationend/transitionend 带前缀，会冒泡，还可能根本不触发——元素中途被 display:none、类名被覆盖、甚至个别版本的事件实现漏发。依赖它做状态机收尾，线上就会出现”卡在动画中途回不来”的事故。可靠的办法是加一个超时兜底：

其四，复杂编排靠 delay 硬编码，很难维护。八个元素依次入场，就是 JS 循环里给每个元素内联一行 delay（索引乘 60ms）。哪天把单段时长从 200ms 改成 260ms，或者要求”第二段等第一段真正结束再开始”，整套 delay 全部重算，改一处崩一片。

其五，老浏览器完全缺席。IE9 对 transition 和 animation 的支持是零，不是”效果打折”而是”属性被整个忽略”。只要页面初始态靠 from 关键帧维持，IE9 上元素就可能永远不可见，所以必须有 JS 兜底或直接无动画切换，这在第 8 节会落成规范。

JS 动画要付的代价

反过来，JS 路线也没有免费午餐，它的成本是三笔账。

第一笔，每帧都要走一遍样式计算。rAF 方案每一帧都在写 style，写的值还会参与布局与绘制；更隐蔽的是”写一次样式、读一次 offsetTop、再写一次”这种链条，每次读都会强制同步布局，掉帧往往不是算不动，而是读写交替把自己绊住了。这笔账在《DOM 操作性能批量插入与重排优化》里展开过，不再重复。

第二笔，计时器与前缀。setInterval 驱动动画有精度钳制、回调排队和漂移问题，标签页切到后台还在烧 CPU。requestAnimationFrame 是当时正确的答案：与刷新率对齐、后台自动暂停。但 2014 年它的现实是：Chrome 要挂 webkit 前缀（webkitRequestAnimationFrame），Firefox 挂 moz 前缀，IE10 起才无前缀，IE9 与部分 Android 4.0 的 WebView 干脆没有，必须带 polyfill 降级到 setTimeout：

第三笔，库的体积与授权。jQuery 1.11 的 animate 走自己的动画计时器（约 13ms 轮询），每一帧对每个 tween 元素做取值、插值、再经 css 管线写回样式，而且它当时并不能直接补间 transform——想用 animate 做位移还得回到 left/top，或者外挂 animate-enhanced 一类插件，合成收益也就谈不上了。几个当时流行的库放在一起看：

库 版本 体积（约） 授权 备注
jQuery 1.11.0 94KB min / 33KB gzip MIT 已随项目引入，animate 走 JS 补间
Transit 0.9.x 10KB min / 3KB gzip MIT 底层是 CSS transition，链式 API
GSAP (TweenMax) 1.11.x 90KB min / 30KB gzip 免费但核心闭源 Draggable 等高级插件需 Club GreenSock 会员
Tween.js 0.14.x 5KB min / 2KB gzip MIT 只做数值补间，配合 rAF 自己写渲染

实测：同一效果的三种实现

选一个最普通的场景：10 张卡片同时做”右移 320px 落位 + 淡入”，时长 400ms，分别用 jQuery.animate（补间 left 与 opacity）、手写 rAF（每帧写 transform 与 opacity）、CSS transition（transform 与 opacity）三种实现。测试机为桌面 Chrome 35、实体机 IE10、以及一部 Android 4.0.4 真机的系统 WebView。帧率用页面里挂 rAF 计数器统计主线程可用帧，CSS 方案以 Chrome Timeline 记录的实绘帧为准；总耗时取”从开始到最后一张卡片落位”的墙钟时间。结果取三次平均值：

实现 Chrome 35 桌面 IE10 Android 4.0 WebView
jQuery.animate 52 fps / 470ms 31 fps / 690ms 11 fps / 1600ms
手写 rAF 60 fps / 405ms 48 fps / 520ms 24 fps / 760ms
CSS transition 60 fps / 402ms 50 fps / 460ms 44 fps / 440ms

几个读数值得记住。jQuery.animate 的开销大头就在逐帧 JS 计算与样式写回：桌面 CPU 兜得住，掉得不多但总耗时已经因为计时器排队溢出约 70ms；到了 Android 4.0，10 个元素逐帧算 left 补间直接把主线程压垮，11 fps 的观感就是幻灯片。手写 rAF 在桌面上和 CSS 基本打平——反正都在 60fps 上限，差距在移动端拉开：rAF 回调毕竟跑在主线程，移动端 CPU 撑不起每帧十次样式重算。CSS 方案在移动端胜出，因为那段动画不依赖主线程脚本的每一帧参与。数字是我的机器的量级，不具备普适性，但”桌面三者可用、移动端 CSS 优先、jQuery.animate 别上大量元素”的方向反复验证都能复现。

混合策略与动画所有权

实践中最值得推荐的不是二选一，而是分工：JS 负责”值”，CSS 负责”时间”——JS 把只有运行时才知道的目标算出来，把插值推进交给 CSS。落地有三招。

第一招，CSS 做表现层过渡，JS 只切类与传参。设计稿给的时长和缓动不必写死在样式表里，JS 通过内联 style 下发，动画本体仍然是一段 transition：

第二招，跟手与物理归 JS，收尾交回 CSS。拖拽跟手阶段每帧写 transform 没得商量；松手时用当前速度预测落点（一段简单的摩擦模型），之后”滑到落点”的减速过程交给 transition 播，主线程立刻解放：

第三招，也是最容易被忽视的：动画所有权规则。同一个属性在同一时刻只能有一个写主。两类典型事故都源于违反这条：跟手阶段忘了把 transition 置成 none，CSS 在后台缓慢追 JS 每帧写的新值，手感像拉橡皮筋；或者 rAF 补间还没停，类名切换又触发了同一元素上 transform 的 transition，两边抢一个属性，画面直接跳变。规则定下来很简单：JS 接管期间禁过渡；交接时一次性设好 transition 与目标值，JS 从此不再写这个属性；谁写的属性谁负责收尾。

决策流程

把判据表蒸馏成四问，按顺序过：

  1. 目标值是否需要运行时计算（指针、测量、数据）？不需要，往下走；需要，但只算终点，走混合。
  2. 是否需要中途打断、反向、暂停？需要就是 JS 的活。
  3. 属性是否落在 transform/opacity 这类 CSS 舒适区，项目要求的目标浏览器是否支持 CSS 动画？有一个不成立就要 JS 兜底。
  4. 是否需要多元素编排与联动？需要的话时间轴归 JS（哪怕只是一串 setTimeout），每段动画本体仍尽量用 CSS 播。

团队落地与验收

选型判断不该每次靠个人现场拍脑袋，建议固化成三条团队规范。

动效清单里写死实现方式。每个动效条目登记：触发条件、动画属性、时长、缓动曲线、实现方式（CSS 类名还是 JS，混合要写清谁先把 transform 交给谁）、结束事件依赖与兜底超时。评审时逐条过所有权，杜绝两个模块同时驱动一个属性。

掉帧验收口径要承认 2014 年的现实：没有统一的自动化指标，我们能做的是固定环境与固定动作。约定两条：桌面用 Chrome 35 的 DevTools Timeline 录主演出动画，掉帧标红不能出现在验收版本里；低端机抽测用 Android 4.0 真机跑一遍全部动效清单，主观标准是”看得出完整过程、不幻灯片”，达不到就砍效果或者改成纯 CSS 收尾。

降级策略写进组件模板。特性检测只检测一次：

检测不到 animation/transition 支持时，直接切换最终状态、不做动画——注意初始”隐藏态”必须由 JS 确认支持后才补上（比如加 is-preparing 类），不要写在基础样式里，否则 IE9 上用户会看到一批永远淡不出来的元素。配合前文的超时兜底，保证动画链路在任何一端失效时，功能仍然可用。

小结

CSS 与 JS 做动画不是信仰之争，是输入源之争：输入只有”状态”、目标值写代码时就确定的动效，首选 CSS，它在移动端和主线程繁忙场景下的收益是真实且 JS 拿不到的；输入是”指针与测量”、需要打断和物理感的动效，归 JS，代价是每帧样式计算、计时器精度和库体积。两者拼接的工程解法是”JS 算值、CSS 播时间”，外加一条动画所有权规则避免抢写同一属性。jQuery.animate 只适合桌面、少量元素、且不涉及 transform 的简单补间，移动端的动效清单要优先安排给 CSS transition。最后把降级与验收口径写进团队规范，选型才算真正落地。
