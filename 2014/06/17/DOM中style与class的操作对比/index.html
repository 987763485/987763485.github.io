DOM 中 style 与 class 的操作对比

关于 class 的增删封装，我在《DOM 中 class 操作的几种封装》里给过一份完整实现；怎么读到一个元素的真实颜色，则记录在《DOM 样式操作与 getComputedStyle》。本文往上抽一层：把一个元素的样式拆成几个来源，讲清各自的存储位置与优先级机制，再给出一个能直接写进团队规范的判据——什么时候写 element.style，什么时候切 class，什么时候该动整张样式表。读完你应该能解释内联为什么压过类名、!important 约定为什么会烂掉，以及主题切换的几种做法分别卡在哪个浏览器上。

样式的三个来源与三套入口

先把模型建立起来。一个元素最终用上哪个值，是三层东西结算完的结果，而不是”样式表里最后一条”或者”脚本里最后一次赋值”。

flowchart TD
    A[样式表规则 按 media 与选择器优先级层叠] --> D[层叠结算]
    B[内联 style 属性] --> D
    C[动画关键帧与 !important 声明] --> D
    D --> E[元素真正生效的值]

第一层是级联的样式表规则，由 @media 决定是否适用，由选择器特异性与书写顺序决定谁覆盖谁。第二层是内联 style 属性，也就是标签上那段字符串、即 element.style 读写的那份声明块。第三层是两种”插队”的东西：CSS Animations 的关键帧，以及带 !important 的声明。按 CSS3 Cascading 草案的排序，动画的来源在作者正常声明之上，所以一段 animation 跑起来时，你用脚本写进内联的 left 会被关键帧盖掉；而 !important 则能把样式表里的值顶到内联之上。

在 CSSOM 里，这三层各有入口，彼此不通：

来源 存在哪 CSSOM 入口 能否写
样式表规则 document.styleSheets sheet.cssRules / IE 的 sheet.rules 可以，改的是规则
内联声明块 标签的 style 属性 element.style（CSSStyleDeclaration） 可以，只碰这一层
结算后的最终值 不存在 DOM 里 getComputedStyle / IE 的 currentStyle 只读

这里必须钉住一句话：getComputedStyle 读到的计算值不等于 element.style.color，前者是层叠结算后的结果、只读、有跨浏览器格式差异，后者只是内联那一层、看不到任何样式表规则。读取端的兼容与代价在旧文《DOM 样式操作与 getComputedStyle》里已写透，本文不重复，只讨论”往哪一层写”。

element.style 的读写规则

element.style 是一个活的 CSSStyleDeclaration 对象，它只包含内联那一条声明块，没有声明的属性读回来是空字符串。

第一条规则：写进去的是字符串，单位不能省。CSSStyleDeclaration 的每个属性 setter 接收的都是 DOMString，浏览器要重新解析一遍；解析不过就整条丢弃，而且不报错。

zIndex、opacity、fontWeight、lineHeight、zoom 这几个可以直接赋数字，因为它们本身接受无单位值。这也正是 jQuery .css() 要额外补一层”自动加 px”的原因——原生这层坑它替你填了。

第二条规则：点号访问只认驼峰，连字符必须走方法。box.style['background-color'] 在标准浏览器上只是给对象挂了个自定义属性，跟样式毫无关系；IE 8 及以下甚至会为它创建一个真属性而让 background-color 依然没设上。要按 CSS 原始名读写，得用 setProperty / getPropertyValue / getPropertyPriority：

float 是唯一被改名过的：标准是 cssFloat，IE 是 styleFloat，连字符名 style.float 反而谁都读不到（float 是保留字）。这套探测思路旧文里写过，此处不展开。

第三条规则：cssText 是整块覆盖，一次写完、一次失效，适合批量赋值；但它会清掉原有全部内联声明，包括别的脚本刚写进去的坐标。

第四条规则：删除一条内联声明用 removeProperty，参数是连字符名。IE 9 及以上有，IE 8 及以下完全没有。

至于 classList，字符串误匹配与 SVG 的坑已在《DOM 中 class 操作的几种封装》处理干净，本文直接调用 domClass.add/remove/toggle，不再重复代码。

优先级实战：内联压过类，以及 !important 军备竞赛

先解释一个常见线上困惑：为什么样式表里明明写了 .tab-panel { display: block }，脚本里一句 el.style.display = 'none' 就能压住它？因为内联声明属于作者样式层，且层叠时排在任何选择器组合之前——规范里的说法是把内联的特异性视作 1,0,0,0，比页面上能写出的最长选择器还高。反过来，样式表里只要加一个 !important，就能把同一条属性从内联手里抢回去。掌握这两条，你就掌握了”谁能盖住谁”的全部答案。

麻烦在于第三条：一旦团队发现”内联压不住”，就会约定 .show { display: block !important } 这类保险类名。这个约定在两三年内必然烂掉，原因有三。第一，它开启了军备竞赛，后来的人只能再加 !important 或更长的选择器来覆盖，优先级体系被彻底打平，最后没人敢删。第二，它盖不住脚本：el.style.display = 'block' 对一个带 !important 的类是无效的，写代码的人只能在控制台里看见”我明明设了值却没变化”。第三，它无法精确撤销，一个类名带 !important 等于让这个元素的相关属性永久失去表现层弹性。

于是”隐藏到底用 class 还是 style”这个问题要分开答。默认答案是用 class：.is-hidden { display: none }，状态互斥、可穷举、能被样式表其它规则协同（比如隐藏时顺手关掉 transition）。但确实存在内联更稳的场景——你的组件要嵌进不能控制的宿主页面（嵌入式小工具、第三方皮肤下的弹窗），你不知道对方的样式表里藏着多少 !important，这时把关键几何属性写进内联是合理的自卫。邮件 HTML 模板是另一个极端：所有声明必须内联，因为客户端根本不接受样式表。

主判据：算出来的值写 style，能表达状态就写 class

这一节是本文的核心判据，一句话：只有当这个值是运行时算出来的，才写 element.style；只要能用状态表达的，一律切 class。

前者包括拖拽后的坐标、滚动同步出来的 top、图表里由数据映射出的柱高、跟随鼠标指针的位置、用户自定义配色里的色值。这些东西在设计稿里不存在，样式表里也没地方写，只能落在内联。后者包括 is-active、is-open、has-error、is-loading 这些状态——取值是有限集合，写在样式表里天然可穷举。

理由有四条，按重要性排：

第一，表现与逻辑分离。设计师要把激活态从橙色改成蓝色，改样式表就行；如果颜色是 el.style.backgroundColor = '#f60' 散在五个文件里，这个改动就得发一次前端版本。第二，避免 !important 军备竞赛。状态类之间靠选择器和书写顺序正常层叠，永远可以在样式表里加一条更具体的规则来微调；而内联一旦需要覆盖，就只能上 !important。第三，状态可枚举、可测试。类名集合是有限的，能写成互斥的一组并配单测；style 上的值是连续量，没法断言”状态正确”。第四，批量切换时改一个类只触发一次样式失效，这在后文性能一节会展开。

批量与主题：切整张样式表的几种做法

页面级换肤在 2014 年有三种主流做法，最后还有一条兜底路子，各自的坑不一样。

第一种：切换 <link> 的 href。简单直接，但要重新走一次网络与解析，中间会出现样式真空期（页面短暂裸奔）。缓解办法是预加载：先创建一个隐藏 link 让浏览器把 CSS 下载进缓存，再换 href。

第二种：禁用样式表。这里有个必须说清的行为差异——不要去写 link.disabled，要去写 link.sheet.disabled。

link.disabled 只在 IE 里映射到样式表；Firefox 与 Chrome 会把它当成挂在 DOM 对象上的自定义属性，赋值成功、渲染毫无变化，这是最容易”本地 IE 正常、Chrome 无效”的一处。另外三个约束：link.sheet 在该张表加载完成前是 null；media="alternate" 的表默认不参与渲染；同源之外的外链表读 cssRules 会抛 SecurityError。

用 alternate 加 title 做主题是一套很省事的写法，浏览器（IE 与 Firefox 的”视图 > 样式”菜单）甚至会自带切换器：

注意遍历时不要缓存下标后又在循环里增删 link，那样索引会漂移；改规则本身不影响集合长度，但移除样式表会。IE 还有一个历史约束：@import 嵌套上限 31 条，主题表拆得太碎就踩线。

第三种（多数团队最终选择的）：把主题写到一个根类名上，用选择器覆盖。

它比切换样式表稳：不必等新资源、没有真空期、能只换部分属性，内联的几何值与主题状态也互不干扰。代价是选择器规模翻倍、规则数暴涨，以及”每加一个组件都要配一套主题规则”的维护成本。建议：色板、阴影、边框这类可枚举属性走根类名，需要整套排版换掉的（打印样式、活动页）才走整表切换。

最后一种是运行时插入 style 标签，用来承载”用户自定义配色”这类不可枚举的值。IE 8 在这里有个必知的坑：不能对已插入的 style 元素改 innerHTML，只能写它的 styleSheet.cssText。

插入的这张表会追加到 document.styleSheets 末尾，因此优先级高于所有外链样式表，正好适合”覆盖”。风险是 CSP：2014 年 CSP 1.0 还在 W3C 候选推荐阶段，Firefox 与 Chrome 都已实现，只要页面下发 style-src 'self' 而没有 'unsafe-inline'，这种动态内联 style 元素和标签上的 style 属性都会被拦掉。相对稳的替代方案是往一张已有的外链表里 insertRule（CSSOM 写操作不在 style-src 的管控范围内），或者把可配置项收敛成有限几个类名由后端下发。

直接改样式表规则：什么时候值得动

比插入整表更进一步的是改规则本身。先给命名差异，这是最容易写错的一处。

能力 标准（Chrome 35 / Firefox 30 / Safari 6 / Opera） IE 8 IE 9 IE 10 / 11
规则集合 sheet.cssRules（CSSRuleList） sheet.rules sheet.rules 两者都有
新增 insertRule(text, index) addRule(sel, css, index) addRule 为主 insertRule
删除 deleteRule(index) removeRule(index) removeRule deleteRule
读某条规则的声明 rules[i].style rules[i].style 同 同
写整条规则 rules[i].cssText = ... rules[i].cssText = ... 支持 支持
新建样式表 插入 link / style 元素 document.createStyleSheet() 同 IE 8 同
跨域外链读规则 抛 SecurityError 抛错或返回空 同 同

值得动规则的场景只有一类：大量同构元素要同时改同一个值。比如表格里 500 行要按数据换成两种色系。逐行写 style.color 是 500 次声明块变更，虽然浏览器会在同一帧合并失效，但 500 个元素都要重新做样式计算、内联属性还要参与序列化与 DOM 检查；改一条规则只需要一次失效，500 个元素的命中结果由这条规则统一给出。

但作用域风险必须提前想清楚：改规则影响的是所有引用这条规则的元素和所有引用这张表的文档。同源 iframe 共享同一份 document.styleSheets 语义、@import 进来的子表被多个页面复用——这些都会让”我只想改这一页”变成”整站都变了”。安全做法是只对运行时自己插入的那张表动规则（它逻辑上归你所有），或者把要改的选择器写得足够独特（加一个 js- 前缀类，样式表禁止依赖，正好用上旧文里定的约定）。还有一点：跨域外链表的 cssRules 读不出来，insertRule 前务必确认 sheet.href 同源或为 null。

性能对照：失效范围差在哪

不重复推导重排（旧文《DOM 操作性能：批量插入与重排优化》与《DOM 样式操作与 getComputedStyle》已经写清”读写交替”的代价），只对比 style 与 class 在失效范围上的差别。

改 element.style 只影响这一个元素的声明块，浏览器给它打上属性级失效标记，样式重算围绕它自己的一条命中链展开，代价与元素数量线性相关。改 class 则要求重新做选择器匹配：祖先链上的复合选择器可能要重新验证，如果新类名进入了一个后代选择器的左半部分，浏览器还得重查同一棵树里的其他候选。一句话，类名的成本挂在选择器结构上，style 的成本挂在元素数量上。

由此得到三条实用结论。第一，几百个同构元素换状态时，把类打在容器上让后代选择器去改，比逐元素切类更省（容器一次失效 vs 数百次选择器验证）；这也是前文”批量切换只改一个类”那条判据的技术理由。第二，style 上的多条属性尽量合并成一次 cssText，或在同一轮代码里连续写完再读布局属性，不要设一个读一个。第三，需要每帧改变的几何属性，优先用 transform: translate(...) 而不是 left/top——位移不触发布局，而 left 每次都要重新排位子；真正跑动画的属性最好落在 transform 与 opacity 上，配一个 translateZ(0) 把元素提到独立合成层，细节见旧文《CSS3 animation 与 keyframes 动画实战》。

小结

element.style 只是内联那一层，读不到样式表；写进去的是必须带单位的字符串，删除声明要用 removeProperty 而不是赋空串。内联的特异性高于任何选择器，但低于样式表里的 !important，也低于正在播放的动画关键帧。据此判断写法：运行时算出来的连续量（坐标、尺寸、跟随指针）只能写 style，能用状态表达的一律切 class，这样既保住了表现与逻辑分离，也从根上消掉了 !important 军备竞赛的必要。整页主题优先用根类名，真要整套排版换掉才去动样式表，且永远写 link.sheet.disabled 而不是 link.disabled；改样式表规则只用在”大量同构元素同步换值”这一种场景上，并先确认这张表归你所有、不是跨域外链。性能上的差别就是失效范围：style 按元素计价，class 按选择器复杂度计价。最实用的一条经验是——定位尺寸写 style、外观状态写 class，这条界限一旦糊掉，代码就再也理不清了。
