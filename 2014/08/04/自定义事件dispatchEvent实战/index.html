自定义事件 dispatchEvent 实战

上一篇文章《DOM 事件对象与事件委托》末尾给过一个跨浏览器派发函数，但代码评审时不断有人问我同一个问题：到底该用哪一种写法造这个自定义事件？HTMLEvents、initCustomEvent、构造函数、还是干脆 $el.trigger？这不是语法题，是选型题——四种能力在”能不能带数据、能不能冒泡、IE 怎么办、要不要背依赖”上各有退让。本文把这四种写法逐一摆开，给出各自的完整代码与适用场景，再补上事件命名规范、自研发布订阅器的取舍，以及几个只在派发环节才会暴露的坑。适合正在写组件、做多模块协作，或者被”IE 8 也要跑”困扰的读者。冒泡与捕获的原理、target 与 currentTarget 的区别前文已经讲透，本文不再展开，只在必要处一句话带过。

自定义事件要解决的三类问题

在动手对比 API 之前，先想清楚为什么需要自定义事件。把页面上真实发生过的需求摊开，大致是三类。

第一类是组件对外通知。以我们项目里在用的选项卡组件为例：宿主页面想知道”用户切到了第三个面板”，传统做法是往组件初始化参数里塞回调函数。回调可用，但一个组件只允许一个主人——第二个模块也想监听切换时，就得让第一个模块再转发一次，调用链越拉越长。组件在切换完成后向自己的根节点派发一个 tab.show 事件，任何模块绑上来监听都是平级关系，组件不必知道听众的存在。

第二类是跨模块解耦。页面分成地图模块和图层面板模块，面板上勾选”关闭商户图层”，地图要做出响应。若面板直接持有地图实例的引用再调方法，两个模块的构建顺序、命名空间就都拴死了，测试时谁也离不开谁。让面板只负责派发 layer.hide 事件带一个图层 id，地图模块在 document 上监听，两边互不引用，删掉任何一边页面都不该崩。

第三类是给原生事件补充语义。click 只是”点了一下”，它不区分”点的是删除按钮且二次确认已通过”；change 只管值变了，管不了”表单此刻已经校验通过、可以提交了”。在业务逻辑走完关键分支的那一刻派发一个带语义的事件，比让下游各自去猜测 DOM 状态可靠得多。

三类需求说到底是同一件事：把”发生了什么”广播出去，而不要让发生者认识每个消费者。

写法一：createEvent(‘HTMLEvents’) 加 initEvent

这是 DOM Level 2 Events 里的正规军，也是兼容面最广的原生写法：从 IE 9 到 Chrome、Firefox、Safari、Opera 全线可用。代价是它没有一个正经的数据通道——initEvent(type, canBubble, cancelable) 只有三个布尔与字符串参数，事件对象上不存在 detail 这个标准字段。

其二是更原始的做法：不发事件，直接调事先挂在节点上的回调属性。这已经不算事件了，本文不展开。

用私有属性传值有三个问题：属性会残留，下一次派发前若忘了更新就读到旧值；属性名要自己约定并防止和别人撞名——顺带说一句，属性传值与 dataset 方案的取舍我写在《DOM中dataset与自定义属性》里，那个方向是 HTML 声明数据，这里是脚本临时传值，场景并不重合；最要命的是它只对”事件路径上的节点”有效，派发到 document 上的全局事件你还得挑一个全页面都摸得到的节点当信箱，语义上很别扭。

所以 HTMLEvents 的适用场景被压缩得很窄：只需要通知、不需要携带任何数据的时候用它最划算，比如”面板打开了”这种无参数信号。一旦要传值，往下看。

写法二：createEvent(‘CustomEvent’) 加 initCustomEvent

DOM Level 3 Events（截至本文写作时仍是 W3C 工作草案）给事件对象加上了 detail 字段，专门放与事件相关的数据。草案时代的标准造法是 createEvent('CustomEvent') 配 initCustomEvent(type, canBubble, cancelable, detail)：

当年的支持情况要摸清楚：这条路径在 Chrome 与 Firefox 上是通的（Firefox 早期版本的 initCustomEvent 签名与草案有过出入，2014 年的发布版本已一致），Safari 大体跟随。但 IE 是断的：IE 9 与 10 虽然实现了 initCustomEvent，参数约定与草案文本有出入，detail 的读取时灵时不灵；IE 8 及以下连 createEvent 都没有，只剩 createEventObject 加 fireEvent 那一套——差异细节见《DOM事件对象与事件委托》，派发层的结论本文不重复。也就是说，这种写法在 PC 项目里没法单独扛起跨浏览器，它更像”给不需要管 IE 的场景少写两行”的选择。

顺带一个前瞻性提醒：initCustomEvent 与 createEvent 整族接口在更新的草案里已经被标记为废弃，规范的风向是收敛到构造函数写法。但迁移动力要等浏览器支持追上，2014 年还早。

写法三：new CustomEvent 构造函数加 ES5 polyfill

DOM View 规范一系的构造函数写法是最舒服的：一个对象字面量说清所有配置。

到本文写作时，Chrome、Firefox 与新一点的 Safari 已经原生支持构造函数；IE 全系不支持，连今年 Build 大会上的 11 预览版也没补，直接 new 会抛 TypeError。要用它就必须配 polyfill。常见的 polyfill 思路有两种：一种是转发给 initCustomEvent，等于把写法二的 IE 不确定性原样继承下来，不推荐；另一种是降级到通用的 createEvent 加 initEvent，再把 detail 手工挂成普通属性，我实际用的是后者：

两处细节值得说。第一，探测原生支持要用 try 包一次真实构造，而不是 typeof window.CustomEvent === 'function'——IE 9/10 里 window.CustomEvent 确实存在且是对象，typeof 检查会误判放行。第二，polyfill 出来的 detail 是可写的普通属性，原生实现里它是只读的；这个差异不是缺陷而是陷阱，别在业务代码里写 e.detail = x 这类依赖可写性的操作，否则换到原生环境就静默失效。至于 IE 8，它连 dispatchEvent 都没有，polyfill 只解决”造出事件对象”，派发仍需走 fireEvent 分支或在入口处直接放弃 IE 8 的原生自定义事件——这就是它进选型表时要付的兼容税。

trigger 相对原生 dispatchEvent 的强项说得出名道姓：数据想放哪就放哪（事件对象属性、附加参数、event.data 三种通道），不依赖 detail 规范字段；自定义事件在老 IE 里也能正常冒泡，因为 jQuery 是沿 DOM 树自己逐层调用处理器，根本不看浏览器的传播矩阵；除 jQuery 绑定的处理器外，它还会调用节点上的 onxxx 属性型处理器，监听端接入方式更宽；取消状态有现成的 isDefaultPrevented() 查询，不必读 defaultPrevented 那个 IE 不认识的属性。

弱项同样明确：一切以 jQuery 集合为前提，派发端和监听端都必须是包在库里的元素；document 上触发时它靠内部 all 标记手工模拟冒泡与默认行为，语义与原生有一层温差；离开这个页面用了什么库，你的事件就没了载体——组件若立志做零依赖，$.Event 不是选项。

五种能力的对比表与选型结论

把四种原生/库写法加上文末要讲的自研 Emitter 放进一张表：

方案 可传值 可否冒泡 可否 preventDefault IE 兼容 依赖 适合场景
HTMLEvents + initEvent 差，只能借 DOM 属性 原生支持 支持 IE 9 起可用 无 无参数的纯通知
CustomEvent + initCustomEvent detail 标准字段 原生支持 支持 IE 9/10 签名有出入，IE 8 无 无 不管 IE 的页面
new CustomEvent + polyfill detail 标准字段 原生支持 支持 IE 9/10 靠降级路径，IE 8 需另补 无 新浏览器为主、组件想零依赖
jQuery $.Event + trigger 任意属性加附加参数 库模拟，老 IE 也冒泡 支持，有 isDefaultPrevented 查询 全系（靠库） jQuery 页面已用 jQuery
自研 Emitter 任意对象参数 无 DOM 概念，自行转发 可自定义约定 全兼容 无 无 DOM 参与的模块总线

笔者给出的三条选型纪律。其一，看依赖：页面本身跑着 jQuery，组件间通知就优先 $.Event 加 trigger，上面那张兼容表它全绿，没必要为了”原生正统”多背一套 polyfill；反过来，组件要发布给不特定宿主用，就不能假设 jQuery 在场，走构造函数加 polyfill 这条路。其二，看数据：纯信号且要覆盖 IE 9 到 Chrome 全谱，HTMLEvents 三十秒写完最省事；一旦要带参数，HTMLEvents 的属性信箱就不要用作正经通道，宁可上 detail。其三，看 DOM：事件消费者与生产者之间没有真实的 DOM 节点关系时（典型如模块总线），不要硬造一个”信箱节点”，直接用下一节的 Emitter。

三十行自研 Emitter：什么时候宁可不碰 DOM

往 DOM 上派发事件有一个常被忽视的隐含成本：你的事件语义被 DOM 树结构绑架了。冒泡路径由节点位置决定，一旦组件被移动、克隆或临时摘下文档树（createDocumentFragment 场景），事件传播就悄悄变了；监听器还容易和原生事件混在同一张表里，调试时真假难分。下列场景笔者会果断放弃 DOM，改用发布订阅对象：生产者与消费者都不持有元素；事件频率高（每帧都发）；需要在 Node 或测试环境里跑；模块销毁必须一键清空所有监听。

事件命名规范：比 API 更早出问题的地方

自定义事件没有包管理器帮你查重名，命名是唯一防线。我们团队的纪律有三条。

第一，统一用”模块名.动作”的点分式，小写、动词化：tab.show、layer.hide、order.submit.done。点分式有个天然红利——它恰好撞上 jQuery 的命名空间语法，$('x').off('.layer') 能按模块整体摘除监听，原生端 e.type 也原样保留全名，两边不冲突。要注意的只在派发端：trigger('layer.hide') 时 jQuery 会把 hide 解析成命名空间、真实类型是 layer，跨模块派发请照表调用，别凭直觉。

第二，绝不与原生事件同名。click、change、load、focus 这些名字一旦占用，你的监听器会同时收到用户真实操作与程序派发，混在一起极难排查；带 CSS3 前缀的 transitionend、animationstart 和触摸系的 touchstart 同样在禁列。同理，DOM Level 3 草案里预留的未实现事件名（如 alert）也不要碰，等规范真落地就撞车了。

派发环节特有的三个坑

detail 里塞 DOM 引用，回收不掉。 detail: { node: bigElement } 看着方便，但事件对象会被所有还活着的监听器闭包引用；只要有一个监听器不卸载，detail 里那个节点就从内存里摘不干净——完整链路见《DOM事件移除与内存泄漏》。纪律：detail 只放 id、坐标、状态这类纯数据，消费方需要节点时自己按 id 去查。

dispatchEvent 是同步的，循环中派发会重入。 document.dispatchEvent 要到所有监听器都执行完毕才返回，这不是异步广播。若监听器会修改你正在遍历的集合，重入就会让数组边变短边往前跳，漏处理或死循环：

若确实需要”本轮结束后再消费”，用 setTimeout(fn, 0) 把派发排到下一个回合，别指望它自带异步。自研 Emitter 的实现里那行 slice() 就是为同一件事准备的。

自定义事件不会被 return false 拦住。 原生处理器里 return false 什么也不取消（前文《DOM事件对象与事件委托》讲过返回值的三套规则，这里只说结论应用）；默认行为对自定义事件本来就不存在，能否”被取消”取决于 cancelable，而取消只认显式的 e.preventDefault()，派发端用 dispatchEvent() 的返回值判断（监听器里调了 preventDefault 时，标准浏览器返回 false）。jQuery 这边处理器 return false 有效，是因为库替你翻译成了 preventDefault 加 stopPropagation，这是库约定不是浏览器行为；自研 Emitter 则按我们自己的约定返回 false。三套语义各是各的，跨层调用时必须显式询问取消状态：e.isDefaultPrevented() 或 e.defaultPrevented，别偷懒用返回值传递”我不同意”。

小结

自定义事件的四条路各有各的让渡：HTMLEvents 兼容性最好但传不了数据；initCustomEvent 守着草案语义，IE 一栏始终发虚；构造函数加 polyfill 是当下原生方案里手感最好的，代价是给 IE 9/10 维护一条降级通道；$.Event 加 trigger 功能全面，但你的事件从此姓了 jQuery。选型先看依赖，再看数据，最后看有没有真实的 DOM 传播需求——三者都不沾，就用三十行的 Emitter，别硬上 DOM。落地时守住三条纪律：命名用点分常量并与原生事件划清界限，detail 只放纯数据，循环中派发先复制集合。事件本身没有对错，只有”谁需要知道、以什么代价知道”，把它当成模块之间的接口去设计，后面的维护会轻松很多。
