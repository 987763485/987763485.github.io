移动端离线存储与缓存

2014 年做手机上的 Web 应用，”离线可用”很容易被当成一个纯 API 问题：页面挂个 manifest，数据塞进 IndexedDB，就完事了。笔者在两个混合 App 项目里把它真正落到线上之后，才发现难点几乎都不在接口本身，而在移动端的物理与生态约束——网是慢的、流量是花钱的、内核是碎的、存进去的东西是随时可能被系统收走的。本文不复述桌面端的机制，只讲三件事：移动场景给离线加了哪些约束、同一套能力在当年各家内核上缺哪一块、数据层怎么选型，并附一份可以直接抄的 IndexedDB 列表页代码。适合做过桌面端离线、正要往手机上落地的同学。

移动场景给离线加了四道约束

桌面端设计离线方案时，默认前提是”网络基本可用、存储基本无限、内核基本一致”。手机上这三条前提全部不成立。

弱网与流量成本

《移动端性能优化特殊点》里已经算过延迟这笔账，本文只补一句结论：离线在手机上省下来的不只是时间，更是请求本身。2G 与信号不稳的 3G 下，一次完整往返可能吃掉一秒以上，而用户的流量是按 MB 计费的。这意味着两件事：一是首屏能不能不上网就不上网，这是体验问题；二是重复下载的每一字节都在用户的话费单上，这是成本问题。桌面端那种”反正都有网”的从容，在这里要换成”重试一次就要用户等三秒并花掉三十 KB”的计较。

内核碎片化

桌面端测三个浏览器基本就够了。手机上，iOS 6 与 iOS 7 是同一支 Mobile Safari 的两个版本，但它们在存储能力上不是同一台机器；Android 2.3 跑的是老 WebKit，4.4 把 WebView 整个换成基于 Chromium 的实现，行为等于换了内核；剩下的市场散落在 Chrome 18 到 Chrome 30 之间的各种版本上。同一份离线代码在不同机型上的能力差集不一样，所以选型时不能只回答”这个 API 有没有”，要回答”在我必须覆盖的那几档机型上，它缺哪块”。

系统对存储的主动清理

手机是存储和内存都紧张的设备，操作系统会为了腾地方回收浏览器数据，而且清理时机对用户不可见。更直接的是，用户在设置里点一次”清除数据”，AppCache、localStorage、IndexedDB 会一起消失。桌面端”缓存能活很久”的假设必须改写成一条设计原则：任何一次读本地数据，都要按”可能读不到”来写。凡是初始化读一次就全程假设它还在的实现，在手机上都会变成偶发白屏。

WebView 与浏览器行为不一致

同一个 URL，跑在 Safari 里、跑在自家 App 的 WebView 里、跑在打包进安装包的本地页面上，能拿到的缓存策略与存储配额是三套不同答案。WebView 的缓存常常由宿主 App 的配置决定，前端一行代码都改不动。这决定了移动端的离线方案必须有一半写在原生侧。

离线其实分三层

把”离线”拆成三层，讨论才能收敛。

第一层是 HTTP 缓存，由响应头驱动、浏览器自动管理，规则细节在《浏览器缓存机制全景》里已完整讲过，本文不重复，只当它是地基。第二层是资源清单离线，靠 AppCache 的 manifest 把外壳钉在本地，断网时 HTML 与它的静态依赖还能打开。第三层是数据离线，靠 Storage、Web SQL、IndexedDB 把接口内容存起来，断网时页面不只是一张壳，还有内容可看。

flowchart TD
  A[离线能力] --> B[HTTP 缓存 减少重复请求]
  A --> C[AppCache 断网可打开外壳]
  A --> D[数据离线 断网仍有内容]
  B --> E[配置错了不影响能打开]
  C --> F[只管静态资源 管不了接口数据]
  D --> G[容量与内核差异都集中在这一层]

一句话概括分层的作用：第一层省往返，第二层保外壳，第三层保内容。本文主体是后两层。

AppCache 搬到手机上多出来的坑

它的机制、”首次访问不生效”、更新与清理那几类经典陷阱，在《Application Cache 离线缓存机制与陷阱》里已经逐条推导过，这里不再重复，只写换到手机上以后新增的部分。

更新要等下次访问，弱网把延迟放大成两个版本。 新缓存下载完不自动生效，这条桌面端也一样，但手机上后果更重：用户从地铁里出来重新打开页面，弱网让更新检查超时，他停在昨天那个版本上，而你收到的反馈是”改了没生效”。更麻烦的是整个缓存集的下载本身就可能中断，中断后浏览器不会保留半份缓存，只能下次从头再来。

任一资源下载失败，整个缓存集作废。 manifest 里列了三十个文件，第二十九个在移动网络的抖动里返回 500，这次更新就整体失败。而 FALLBACK 救不了接口——XHR 请求既不走 AppCache 的缓存集，也不受 FALLBACK 接管，这一点在桌面上是设计缺陷，在手机上直接变成方案性别的分界线：凡是想在 AppCache 里顺手缓存接口数据的想法，都要打消。

配额更小、会被系统清空，update() 也救不回来。 桌面上常说的 5 MB 量级在手机上往往拿不满，低端机写满之后是静默不再缓存，不报任何错。更致命的是缓存被系统回收后，页面里的 manifest 引用还在，浏览器会重新尝试建缓存集，但弱网下这一步大概率失败，于是页面退回完全在线状态，代码里那套”我已经离线可用了”的判断随之失效。

Android 2.3 的 WebView 里，原生不开关就没有 AppCache。 老 Android 的 WebView 默认不给你这些能力，必须让客户端同学显式打开：setAppCacheEnabled(true) 配上 setAppCachePath() 指定可写目录，DOM Storage 要 setDomStorageEnabled(true)，HTTP 缓存那一层由 setCacheMode() 决定。这些开关默认值在各家 ROM 上还不一致。这意味着混合 App 里”离线能不能用”这个问题，前端单方面答不了。

file:// 与 http:// 是两套彼此看不见的缓存。 打进安装包的本地页面和本地服务器上同一份线上页面，origin 完全不同，AppCache 缓存集互不相干，localStorage 也各存一份。混合 App 里最常见的事故是”本地页面读不到线上页面存的数据”，或者反过来，同一段代码在两种加载方式下表现不一致。

iOS Safari 的清理入口对用户不可见。 桌面浏览器还有开发者工具与 chrome://appcache-internals 可查，iOS 上用户能做的只有”清除历史记录与网站数据”这种一刀切操作，会把 Cookie、缓存、本地存储一并抹掉。线上出现”部分 iPhone 用户一直停在旧版”时，你几乎没有可观测手段，只能靠埋点上报当前版本号反推。

结论是清晰的：AppCache 在手机上只适合缓存静态壳，一切数据都要走接口再自己存。 把 manifest 里的 CACHE 段限制在 HTML、合并后的 CSS 与 JS、少量首屏图标，容量控制在两三 MB 以内，接口数据一律落到下面要谈的数据层。这样 AppCache 坏掉时，你损失的只是首屏速度，不是内容。

这张表读法有三点要说明。

第一，IndexedDB 在 2014 年有一个必须写进方案的真实缺口：iOS 7 的 Safari 至今没有实现它。iOS 8 的开发者预览版里补上了，但正式版今年秋天才发，线上等 iPhone 用户的这段时间里，这条路是断的。凡是”核心功能依赖 IndexedDB”的设计，在这个时间点都必须准备一条回退路径。

第二，Web SQL 已经被 W3C 明确废弃，Firefox 与 IE 从来没有实现过，Chrome 也把它标了废弃并计划移除，当年只剩 iOS Safari 与 Android 4.x 系统浏览器还完整内置。它现在的唯一正当用途是维护那些多年前用它的老项目——把数据读出来、迁走，而不是在上面继续加功能。

第三，localStorage 谁都有，但它是同步的，读一个大 JSON 会直接卡住主线程，而且没有过期机制。手机上它只配当”小状态”的容器，不要当缓存层。

于是当年的选型其实很朴素：能用 IndexedDB 就用 IndexedDB，探测不到就退回 localStorage 存一份小快照，快照只保证”有内容可看”，不保证容量与查询能力。下一节给出这套探测与回退的具体代码。

混合 App 的离线包才是真正的主力

在 2014 年的国内环境里，真正跑在 WebView 里的业务页面比跑在浏览器里的多。这类场景下最可靠的离线手段不是 AppCache，而是客户端预置的离线资源包，做法当年已经很成熟：安装包内置一份壳资源与一个初始版本号；启动时把预置包解压到应用私有目录；请求服务端一份 version.json；比对本地版本；只下载增量文件列表；逐个校验后原子替换；最后通过 JSBridge 通知 H5 侧重载页面。桥协议与调用时序在《JSBridge 设计与实现》里写过，这里不展开；版本号与强缓存怎么配合在《静态资源版本号与缓存更新》里讲过，同样不重复。

为什么它更可靠：不依赖任何浏览器特性，配额由 App 自己的沙盒决定，清理逻辑可控——用户可以清缓存，但壳资源不会被系统顺手收走；而且能灰度、能回滚、能强制更新，这些都是 AppCache 给不了的确定性。代价是要原生配合，还要自己管版本与校验。

这里有两个 API 边界要说清。FileSystem 当时只有 Chrome 有私有实现，需要 requestFileSystem 并申请持久化配额，iOS 与多数 Android 浏览器根本没有，以它为前提的设计都不可依赖。File API 与 FileReader 普遍可用，但它们解决的是”读用户选中的文件”（比如上传前压缩预览），不是”存离线包”，两者不要混。

至于 rel="manifest" 那份应用清单规范，2014 年 8 月它还是草案状态，没有任何主流浏览器给出稳定实现，只能作为前瞻记在这里，不能作为选型依据。

一条列表页的离线策略

把上面几层拼成一个具体页面的决策流程，就是我们当年画在需求评审文档上的那张图。

flowchart TD
  A[进入列表页] --> B[用本地壳渲染骨架 立刻上屏]
  B --> C[请求列表接口]
  C --> D{接口是否成功}
  D -->|成功| E[渲染新数据]
  E --> F[写入快照并记下时间戳]
  D -->|失败| G{本地有没有快照}
  G -->|有且未过期| H[读快照渲染]
  G -->|有但已过期| I[渲染快照并标注缓存时间]
  G -->|没有| J[显示离线空态与重试入口]

四个要点。首屏骨架走本地，让结构与样式不依赖任何一次网络往返，这是”打开就有东西”的底线。数据一律走接口，接口成功才更新快照，失败才读快照，方向不能反。快照必须带写入时间戳，并给一个业务决定的失效阈值：新闻列表半小时可以接受，订单状态五分钟就嫌长了。过期仍然要渲染，但必须把时间明确写在页面上——让用户看到标注过的旧内容，远好于让他盯住一片空白；把旧内容伪装成新内容，是最快失去信任的方式。

小结

移动端的离线难点不在 API，在约束：延迟主导的弱网与按 MB 计费的流量、碎成十几档的内核能力差集、系统随时可能执行的存储回收、以及 WebView 与浏览器两套互不一致的行为。方案上要分层——HTTP 缓存当地基，AppCache 只圈定静态壳并把容量压到两三 MB，接口数据一律走数据层，混合 App 里真正的主力是原生离线包。数据层在 2014 年的现实是 IndexedDB 与 localStorage 两套并行：iOS 7 没有 IndexedDB 这个缺口必须写进代码，探测决定走哪条路、运行时异常再兜一层，而不是探测完就假设稳定。

值得离线的东西有三类：首屏壳与骨架、少量必需的静态资源、最近一次列表快照与用户没提交完的草稿队列。不值得的也有三类：价格库存未读数这类实时性数据，大体积图片与视频（它们该走 CDN 强缓存，不该塞进本地配额），以及任何形式的身份凭据与隐私字段——手机会丢，本地存储会被提取，这些内容存进客户端就是事故储备。最后一句心法：不要把离线设计成”存进去就有”，要设计成”每次读都可能读不到，读到了也必须注明它是几点的数据”。
