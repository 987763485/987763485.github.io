移动端适配方案：流式与弹性

做了大半年移动页面，我把适配方式归成了三条路线：固定宽度、流式（fluid）、弹性（elastic）。前两条谁都会写，第三条去年还只是零散技巧，今年 iOS 4.1 以上与 Android 2.1 以上基本都能解析 rem，才真正能用在一个正式项目里。这篇文章不做概念科普，直接把我这套适配层的源码摊开：流式的百分比栅格怎么写、弹性的根字号脚本怎么写、构建期的 px 到 rem 换算任务怎么写、这四个模块为什么必须收成一个独立的适配层而不是散落在各页面，以及真机上一定会踩的五个坑。适合已经在写移动页面、正准备定团队适配规范的前端同学，读完可以直接把源码抄走改基准值。

三条路线的边界

先把定义钉死，避免后面讨论时互相错位。

固定宽度是定宽设计的平移：页面按某个宽度（当年常见 640 或 980）写死像素，交给 viewport 去缩放，用户想看细节只能双指放大。三种视口与 meta 参数的取舍我在《HTML5 meta viewport 与移动端适配基础》里已经讲透，本文只把它当作适配层的一个输入，也就是布局视口宽度，不再重复。

流式（fluid）是不写死宽度、改用百分比，让容器的宽度跟着视口等比走，但高度、字号、边框、图片本身的尺寸都不跟着缩放；需要换结构时靠媒体查询切一两个断点。它的本质是”宽度自适应，内容不自适应”。

弹性（elastic）是把整页的度量基准挂到 html 的 font-size 上，所有尺寸用 rem 表达，于是 JS 只要改一个数字，全页的宽高、间距、字号、行高一起等比放缩。它的本质是”用根字号模拟设计稿的缩放系数”，等比程度最高，代价是对浏览器单位实现细节最敏感。

路线 等比缩放程度 字体是否随视口缩放 实现成本 iOS 风险 Android 2.3 风险 Android 4.x 风险 适合业务
固定宽度 无，全靠 viewport 缩放 否 最低，桌面稿直搬 缩放后位图发虚 缩放插值粗糙、字体毛糙 机型 CSS 宽不匹配时左右留白 营销长图、桌面内容平移

选型判据其实很朴素：设计稿是”一套尺寸通吃”还是”每档屏幕另出一稿”。前者必上弹性，后者流式加断点足够；而只要页面里有需要保持物理尺寸的像素级元素（细线、图标、可点区域的最小高度），就不能全页弹性，得把那些值钉在 px 上。这就是我最后走向混合方案的原因。

流式方案：百分比栅格与断点纪律

流式的核心算式只有一条：target / context = result，目标值除以上下文值，得到百分比。上下文是父容器的宽度，不是屏幕宽度，这一点写栅格时最容易搞混——列宽是相对 .row 的，而 .row 自己是 100%。

断点是流式方案唯一容易写坏的地方。我见过的项目从 320 一路写到 1024，堆十几个 @media，每个断点复制一份布局。问题在于每多一个断点就多一份完整分支，测试矩阵是断点数乘以页面数，而 2014 年市面 CSS 宽度是一条连续分布（320、360、375、384、400、412、480、540、600、640 都在跑），你永远补不完。合理的做法是让断点只负责结构切换（两栏变一栏、侧栏上移），尺寸缩放交给流式或弹性去管，于是三档封顶：

还有一个必须记进规范的兼容事实：Android 2.x 的系统浏览器原生不支持 Media Queries Level 3（2012 年才成为推荐标准，老内核没跟上），断点在这些机器上完全不生效。要么补一份 matchMedia 的 polyfill（Paul Irish 2012 年放出来的那版只补 API，不会让 CSS 里的 @media 生效，还得配合脚本切换样式表），要么直接把这批机器归进”最小档样式”，不做结构切换。我选后者，因为它的存量下滑得比预期快，而前者会让首屏多一次重排。

弹性方案：动态根字号

弹性方案的全部秘密只有一个函数：把根字号算准。JS 必须停在 ES5，只用 var、function 和回调，这条限制反而让代码短得像伪码。

这段脚本要放在 head 里内联执行，而不是打包到页面底部——根字号晚一帧写入，用户就看到一次字号跳变的闪烁（先按默认的 16px 排版、再重排成 15.36px，长页面尤其明显）。基准值可以按团队设计稿换成 640 一档：DESIGN_WIDTH = 640、BASE_FONT = 100，此时 1rem 在设计稿上等于 100px，换算只是把小数点左移两位，写 CSS 时心算最快；代价是 CSS 里那条兜底的 html { font-size: 16px } 也要跟着改成 100px，否则 JS 执行前的首帧会按 16px 排版，弹性值全部按 16 折算，闪一下就重来，比不换基准更难看。

构建期换算：一个 Grunt 0.4 任务

设计稿上标的是 px，代码里要写 rem，靠人手除基准值一定会出错，而且 review 时看不出除错了。把换算挪到构建期是更稳的做法：设计师给的标注数字直接抄进 CSS，构建任务负责改成 rem。

三条纪律要写进 README。第一，输入必须是编译产出的 CSS，不能直接改源码，否则源码里出现 rem 之后新人读设计稿标注要来回换算，标注与代码脱钩更难查错。第二，src 只圈定移动端目录，桌面端 CSS 混进来越算越乱。第三，keep 阈值是给 1px 这类物理尺寸留的后门，阈值取几要和基准字号一起定，别随手写。同样的逻辑搬到 gulp 3.x 只是换了流接口：

适配层的架构：四个模块一个数据源

把上面这几段代码合起来看，它其实是一个小型框架，模块边界很清楚：

flowchart TD
  CFG[适配配置 单一数据源 设计稿宽 基准字号 断点表 上下限]
  CFG --> VIEW[viewport 注入模块]
  CFG --> CALC[根字号计算模块]
  CFG --> CONV[构建期单位换算任务]
  CFG --> BP[断点配置模块]
  VIEW --> LV[布局视口宽度]
  LV --> CALC
  CALC --> ROOT[html 的 font size]
  CALC --> FALL[降级开关 data rem]
  ROOT --> BIZ[业务样式 rem 排版]
  CONV --> BIZ
  BP --> BIZ
  FALL --> BIZ
  EV[事件层 DOMContentLoaded orientationchange pageshow resize] --> CALC

四个模块各有各的坑，但共享同一份配置。这里”集中成一层”是本文真正想说的架构结论，理由有四条。

第一，基准值一旦被复制成两份就一定会漂移。运行时脚本里的 DESIGN_WIDTH、BASE_FONT 和构建任务里的 base 必须是同一个数，否则 CSS 写的是按 16 除出来的 rem，JS 把根字号算成 18，整页字号静默放大 12.5%，这种 bug 在 UI 上只表现为”字好像有点大”，排查成本极高。我现在的做法是把配置抽成一个 JSON，Grunt 里 require 它，同时用 grunt.template 在构建时把同一个对象注入到 root-font.js 头部。

第二，降级策略只能有一处。Android 2.3 走不走 rem、data-rem 标记怎么挂、哪些值永远保持 px，如果散在各页面里，每页都要重写一遍判断，漏一页就崩一页。收进适配层后，业务 CSS 只管写值。

第三，首屏阻塞要能被量化。根字号脚本内联在 head，是同步阻塞的，集中成一层才能明确它的体积与执行时机预算；散落各处就变成了”每个页面都不知道谁先跑完”。

第四，断点属于结构切换，属于设计约束而非页面细节，它应该和栅格的上下文宽度放在一起看。适配层把断点表暴露成一个 JS 常量，页面里要按屏幕宽度切换行为时读它，而不是各自写一遍 600。

运行时时序

架构上唯一需要画出来的部分是时机，因为适配层是首屏渲染的前置条件：根字号没写进 DOM 之前，任何用 rem 的盒子都按浏览器默认的 16px 计算。

flowchart TD
  A[HTML 到达] --> B[head 内联脚本同步执行]
  B --> C[读 clientWidth 算根字号]
  C --> D[写入 html 的 font size 与 data 标记]
  D --> E[首次布局与绘制]
  E --> F{orientationchange 或 pageshow}
  F --> G[立即重算一次避免长时间错版]
  G --> H[延时 300ms 再算一次拿真实尺寸]
  H --> I[两次数值不同才触发第二次重排]

三条时序纪律：脚本内联且放在样式表之前，让第一次布局就用上正确字号；监听 DOMContentLoaded 而不是 load，因为图片还在下载时字号就该定了；pageshow 必须有，从后退缓存回来的页面不会重新执行 head 里的脚本，只有这个事件能兜住。整段脚本压到 1KB 以内、不做任何 DOM 查询以外的活，才能放心内联——这也是把它收成一个独立小文件、不并进业务 JS 的原因。

五个一定会踩的坑

iOS 横屏时 innerWidth 不是布局视口

iOS Safari 的 window.innerWidth 反映的是可视视口，用户双指缩放之后它会跟着变，横屏切换的一瞬还可能报出与 screen.width 不一致的值。而我们要缩放的是布局视口，唯一可靠的读数是 document.documentElement.clientWidth。所以上面那段代码把 clientWidth 排在第一，innerWidth 只做它读数为 0 时的兜底。另一个表现是横屏后根字号算错半档，页面右边留一条空白，八成就是取了 innerWidth。

Android 2.3 认得 rem 但算错

这是弹性方案最大的坑，而且它骗过特性检测：2.3 的内核接受 rem 这个单位写法（所以 probe.style.fontSize === '1rem' 返回真），但计算时永远按初始字号（约 16px）折算，你改了 html 的 font-size 它不跟。结果是整页尺寸固定不动，流式部分照缩放，页面错位。做法是 UA 判断单独立一条，命中就在根元素挂 data-rem="off"，CSS 侧对关键尺寸保留一份 px 声明：

属性选择器 html[data-rem="off"] 的权重高于单类，能保证 2.3 上一定命中兜底。

orientationchange 触发时尺寸还没更新

方向事件的回调里立刻读 clientWidth，拿到的常常是旋转前的宽度，iOS 与部分 Android 4.x 都有这个行为。可靠组合是”立即算一次 + setTimeout 300ms 再算一次”：第一次保证不出现长时间错版，第二次拿到真实尺寸。副作用是页面会有肉眼可见的一次重排，所以别把这段逻辑挂到 resize 上再去滚动联动，resize 只做节流重算。顺带说，字号整体缩放之后，1px 边框在高分屏上的观感会更突出，那是《移动端 1px 边框问题》里已经处理过的老问题，本文不重复。

缩放后边框与图标失真

弹性放大的不只是文字：border: 2px 变粗、精灵图图标被拉伸发虚、border-radius 变成大圆角。原则是把不该缩放的物理尺寸钉在 px：细线、图标实际宽高、输入控件的可点高度。图标另外要用倍图，DPR=2 的机器上给 2x 素材，用 background-size 缩回逻辑尺寸，这样它被字号缩放影响时仍有足够像素密度。

大屏 iPad 上字号失控

viewportWidth / DESIGN_WIDTH * BASE_FONT 是一条直线，视口宽 768 时根字号正好撞到上限，再宽就靠 MAX_FONT 截断。截断之后页面等比性没了，会出现”两边大片留白”或”字小到不像 iPad”。三种策略选一种写进规范：提高上限并放宽容器最大宽度（内容居中，两侧留白，适合资讯类）；超过阈值直接切到桌面样式表走多栏（适合有桌面版的项目）；保持上限但把栅格从两栏升三栏（适合后台类）。我的选择是第二种，refresh() 里顺手加一条：视口宽度超过 700 就给根元素挂 data-mode="tablet"，CSS 里按属性分叉。

小结：流式为骨，弹性为肌

结论是混合方案：结构与图片走流式，排版度量走弹性，物理尺寸钉 px。两段片段就是最终落地形态。

-webkit-text-size-adjust: 100% 这一行不能省。iOS Safari 在横屏时会自作主张把字号放大一档，它放大的是计算后的值，于是我们的根字号被二次缩放，整页比例失衡；把它锁成 100% 之后，屏幕上只有 JS 一个字号来源。

收一下本文的结论。这套适配层的价值不在于”用了 rem”，而在于它把适配变成了一件可配置的事：换设计稿基准只改一份配置 JSON，换最低支持机型只改一条 UA 判断和一处 keep 阈值，业务 CSS 里没有一处需要跟着改。三条路线的分工要说清楚——流式管结构与图片的宽度，弹性管字号、间距这些需要整体等比的度量，px 只管那些一旦缩放就错的物理尺寸（细线、图标、可点高度），三者不要互相越界。基准值必须在运行时脚本与构建任务之间保持单一来源，这是整套方案里最容易腐坏的一环，也是它值得被收成一个独立层级的根本原因。机型还会继续变，屏幕宽度分布还会继续散，但”定基准、算根字号、构建期换算、集中降级”这四步不会过期。
