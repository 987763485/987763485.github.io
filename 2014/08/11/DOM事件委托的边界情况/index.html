DOM 事件委托的边界情况

事件委托的原理并不复杂：容器上绑一个监听器，事件冒泡上来，从 event.target 沿祖先链找命中者。可一旦把它从教程示例搬进真实项目，就会遇到一连串”明明按套路写的，怎么就不生效”的现场：点按钮没反应、老 IE 下焦点委托失灵、嵌了第三方日历的区块整块哑掉。《DOM 事件对象与事件委托》讲过事件对象与事件流本身，《jQuery 的 on、off 与事件委托》讲过库的委托 API，这两块基础本文不再重复；本文只做一件事——把 2014 年真实环境下（支持范围含 IE8，移动端正被 Android 2.3 与 4.x 并存折磨）委托会失效的边界情况逐一列清楚，每种都给出现象、原因、对策与可运行的 ES5 代码。适合刚把委托用进项目、开始在兼容性上吃亏的读者，读完你应该能回答：哪些事件天生不能委托，哪些要换个事件名才能委托，哪些看着能委托其实随时会断。

最小委托例子：先弄清命中是谁

先把最小的可运行例子摆出来，后面所有边界都从这里长出来。

target 与 currentTarget 的准确定义、以及捕获与冒泡的三阶段模型，前篇已经系统讲过（见《DOM 事件对象与事件委托》），这里只讲它们在”命中判定”里的分工：用户真正点到的是 span.title 还是 button.del，由 target 说了算；而我们的监听器永远只挂在 list 上，所以判定逻辑只有一句话——从 target 出发沿祖先链向上走，走到容器为止，第一个匹配选择器的节点就是业务上的”被点击项”。

麻烦在于”沿祖先链匹配”这一步没有现成的统一 API 可用。Element.prototype.closest 要 IE9 起才有，2014 年做 IE8 兼容的项目用不上它；选择器匹配函数各家前缀也还没收敛：Firefox 3.6 起是 mozMatchesSelector，WebKit 系（Chrome、Safari、Android 2.3/4.x 的自带浏览器）是 webkitMatchesSelector，IE9 起是 msMatchesSelector，IE 与 Firefox 的发布版当时都还没有去前缀的 matches——它到 2014 年年中也只在最新 Chrome 与 Firefox 的夜间通道里出现，生产代码一律不能裸用。所以人手一份的 polyfill 是这样的：

这里最容易犯的第一个边界错误，是把”上溯”写成”无限上溯”。closestFrom 的循环条件是 node !== root.parentNode，意思是过容器即停；少了这个闸，点击会”穿过”委托容器命中到外层同名结构的处理器上，造成跨模块误触发——这在多个组件都往 document 上绑委托的老页面里非常常见。第二个错误是用 className 字符串比对代替选择器匹配，看着省事，下一节会看到它碰到 SVG 就当场失效。

event.target 不一定是你期待的元素

委托的第一根支柱是”从 target 上溯”，可 target 本身未必是个元素节点。至少有三类情况要把住。

第一类是文本节点。 Firefox 3.6 及更早的版本与早期 WebKit 曾经在某些点击里把文本节点作为 target 抛出（如今的主流版本已基本修好，但 Android 2.3 那批残留 WebKit 里仍能见到）；老 IE 还有一条独立路径——页面上凡是用 createTextRange 做过自定义文本选区（富文本编辑器的关键词高亮当年常用这招），点击落在选区附近时 srcElement 可能给出文本节点。同理，contenteditable 编辑区的选词双击与拖动选字操作，在老 WebKit 与老 IE 上都报告过把文本节点塞进 mousedown、dblclick 的 target 的情况，编辑区和委托列表共存在同一页面的项目要格外小心。文本节点没有 className，拿它调 matchesSelector 会直接抛错，所以命中循环第一步必须先过 nodeType === 1，上面代码里已经带了这道闸。同理，注释节点、甚至 document 本身都可能出现在祖先链上，nodeType 过滤是零成本保险。

第二类是 SVG 内部元素。svg 标签里的 path、circle、use 被点击时，target 就是这些 SVG 元素，它们的命名空间与普通 HTML 不同，最阴的坑在属性形态上：HTML 元素的 className 是字符串，SVG 元素的 className 是 SVGAnimatedString 对象。凡是写成 node.className.indexOf('icon') !== -1 的老代码，点在 SVG 图标上时 indexOf 根本不存在，整段委托无声失败。对策有两条：坚持选择器匹配（各家前缀版对 SVG 元素都可用），或者至少把 className 读取改成 getAttribute('class')。另外老 Android 2.x 对页内 SVG 的事件派发本就残缺，图标类可点击区域在 2014 年的实践结论仍然是：用 HTML 容器包住 SVG，把委托绑在容器上，别绑进 SVG 内部。

第三类是伪元素。用 ::before 给按钮加了一个图标、给单元格加了一个”删除”字样的装饰块，用户点它，target 是宿主元素而不是伪元素——因为伪元素压根不在 DOM 树里，没有节点身份，自然谈不上命中。想用委托响应”那块区域”，就得把区域变成真实节点：要么直接生成子元素，要么在宿主的 data- 属性上记录状态、由处理器换算。指望”匹配到伪元素”在可预见的几年内都不会成为 DOM Events 的能力，遇到这类设计稿需求，正确动作是回去和产品讨论把装饰做成真实元素。

不能冒泡因而不能委托的事件清单

这是本文的核心一张表。委托的前提是事件会沿树往上走，不冒泡的事件在原生层面委托不了——不是”难”，是监听器根本收不到。2014 年需要盯住的是这些：

事件 冒泡情况（以 2014 年支持面为准） 可行的委托写法
focus / blur 一律不冒泡 标准浏览器用捕获；IE 系原生有 focusin / focusout 可用；Firefox 尚无 focusin
change IE8 及以下不冒泡，老 Opera 行为混乱 别委托，直接绑控件；控件动态生成则渲染后补绑
submit / reset IE8 及以下不冒泡；form.submit() 触发时任何浏览器都不派发 永远直接绑在 form 上
select IE8 及以下不冒泡 直接绑；或退而监听 keyup 加值变化轮询
mouseenter / mouseleave 原生不冒泡（IE 私有转正的非标准货） 委托 mouseover / mouseout，用 relatedTarget 自判进出
scroll 不冒泡 绑在真正产生滚动的那个容器上，别无他想
load / error（资源） 不冒泡 标准浏览器可在 document 上用捕获阶段监听；IE8 只能逐个元素绑
resize 不冒泡，只在 window 派发 全局一个监听器统一分发，不需要委托
click / mousedown / mouseup / mousemove / keydown / keyup / input / contextmenu / dblclick 冒泡 放心委托

几个需要展开说清的部分。

焦点类。focus 与 blur 不冒泡是规范写死的行为，但浏览器给出了两条补救路。其一，IE 从 IE6 起就私有提供了冒泡版焦点事件 focusin / focusout，attachEvent('onfocusin', fn) 在老 IE 上真实可用，这是 2014 年 IE8 环境委托焦点的唯一直路。其二，标准浏览器没有 focusin 也不影响：Firefox 直到 2014 年 8 月仍未实现 focusin / focusout，但 Firefox、Chrome、Safari、Opera 都能捕获不冒泡的 focus，第三参数传 true 即可（下一节展开）。也就是说，同一份”委托输入框聚焦”的代码，在 IE8 要走 focusin、在 Firefox 要走 focus 捕获、在 Chrome 两条都行，这正是后文封装里”自动降级”要处理的核心。顺带一句，jQuery 1.11 的委托 focusin 已经帮你把 Firefox 用直接绑 focus 的方式模拟补齐了，所以在 jQuery 项目里感觉不到这组分裂；原生与 Zepto 1.1.x 都不会替你做，Zepto 的 focusin 委托在未支持它的浏览器上就是静默失效。

change 一族。表单值变更事件在 IE8 及以下不冒泡，老 Opera（Presto 内核 11 之前）对 change 与 submit 的冒泡时机也时有时无，再加上各家对触发时机的定义都不一致（《DOM 事件对象与事件委托》里提过 select 下拉的 IE 提前派发问题），结论只有一条：表单状态类事件不碰委托。我知道很多项目想偷懒——列表里一行渲染几十个输入框，逐个绑太烦——正确思路是绑定层做增量：渲染后用 getElementsByTagName('input') 给新控件补绑，而不是把不冒泡的事件硬塞进委托管道。

load 与 error。图片加载失败上报是典型需求：想在一个容器上监听全部 img 的 error。这两个事件不冒泡，但标准浏览器里它们会走捕获阶段——在 document 上以捕获方式监听，就能收到任意深度处图片的加载结果，处理器里从 e.target 拿到那张图：

至于触摸与指针类：touchstart 等触摸事件冒泡，委托照常工作；Pointer Events（pointerdown 一族）到 2014 年只有 IE10 有正式发布实现，W3C 规范还在草案阶段，Chrome 与 Firefox 均未默认开启，属于前瞻内容——好消息是它的冒泡行为设计上是照着鼠标事件来的，未来的委托结论可以直接套用，但本文的工程代码不为它单独展开。

传播的两条岔路：捕获委托与中途截胡

既然焦点类事件不冒泡，那把监听器绑到捕获阶段行不行？行，但要清楚代价。addEventListener(type, fn, true) 之后，事件还没走到 target 就会自顶向下路过你的容器，容器上的处理器照样拿到 e.target，照常可以沿祖先链做命中判定——捕获委托在逻辑上完全成立。语义上有两处变化要留意：其一，你在容器上收到事件的时机比冒泡版早，此时 currentTarget 是容器、target 是被点元素，两者关系与冒泡阶段一致，判定代码不用改，但如果你在处理器里同步修改了 DOM（比如展开折叠面板），目标元素可能在事件到达它自己之前就被移出了文档，后续依赖”目标还活着”的逻辑要三思；其二，preventDefault 与 stopPropagation 的效力不变，但你的捕获处理器先跑，下游组件看到的已是被你处理过的现场，写埋点无妨，写交互逻辑要谨慎。

真正让捕获阶段不可替代的场景是：链路中间有人调用了 stopPropagation。这是委托最常见的”隐形断线”——你的委托容器好好地挂在 document 或列表根上，代码一行没错，事件就是不上来。谁掐的？2014 年的项目里通常是三类：第三方日历 / 下拉选择控件（它们在自己的根元素上掐掉 click 防止点穿）、富文本编辑器（KindEditor、Ueditor 们在工具条区域大量阻止默认与传播）、以及某些弹窗遮罩组件。定位方法不用猜，在 window 上加一个捕获阶段的”打点哨兵”：

哨兵在捕获阶段位于最顶端，任何事件只要真的派发了，它必先看到。如果哨兵打印了而你的委托容器没反应，说明事件在两者之间被 stopPropagation 掐断，把容器上逐层加同样的哨兵二分一次，就能定位到是哪一层、进而定位到是哪个组件干的。对策按优先级排三条：第一，把委托容器挪到截胡组件的下层或旁路，让它不再经过对方之手——这往往也顺便缩短了冒泡链，是正解；第二，改用捕获阶段监听，截胡发生在你之后，收得到；第三，实在改不动组件，退化为渲染后对目标元素逐个直绑。第三条是下策，但表单类事件本来就该走它。

还有一个半路截胡的变种要提防：stopImmediatePropagation。它不掐传播，只掐同一元素上后绑的同类型处理器，症状是”绑在先的能收到、绑在后的收不到”，且重新绑定顺序就能复现或消失。IE8 及以下没有这个方法，老 Firefox 与 Chrome 有，排查时注意只有新版浏览器出问题就要想到它。

CSS 与层叠也会改写命中结果

委托假设”点在哪里，target 就是哪里”，而 target 到底是谁，是渲染层在命中测试（hit testing）时算出来的，CSS 有权插手。两种干预方式各配一个坑。

第一种是 pointer-events: none。加上它，元素对鼠标事件彻底透明，点击会”穿”到它下面的元素上去。设计侧用它禁用按钮是常见做法，但事件侧要清楚后果：委托的 target 变成下层元素，沿祖先链上溯时那个”被禁用的按钮”作为 target 的机会没有了——若它仍是按钮的祖先（比如按钮包在 li 里），你的委托照样命中 li，用户就会看到”明明禁用了删除按钮，点它所在的行却触发了删除”。对策是在判定函数里补一条穿透检查：命中之后，再看事件坐标处最顶部的真实元素是不是处于禁用样式的节点。

支持面要讲清楚：pointer-events 作为作用于 HTML 元素的 CSS 属性，Firefox 3.6 起、Chrome 与 Safari 早已可用，但 IE 要到 11 才完整支持，IE10 只在 SVG 内认识它——也就是说在 2014 年，指望 CSS 声明本身在所有目标浏览器里禁用点击是幻想，老 IE 上被”禁用”的按钮照常派发 click，上面的 JS 检查反而成了必须项。

顺带把命中测试的几个 CSS 近亲一次说清，它们在委托现场经常被混用：display: none 的元素整个从渲染树消失，自然不参与命中；visibility: hidden 保留布局占位但不接收事件；opacity: 0 视觉上完全隐形，却照样是”最顶部元素”，照样把点击接走——委托现场那些”点不到下面按钮”的悬案，元凶十有八九是某个透明度归零却没被摘掉的热区层。判定标准只有一条：参与不参与命中，看的是渲染几何与 pointer-events / visibility，跟”看不看得见”无关。

第二种是遮挡。弹窗遮罩、浮动提示、z-index 错乱的绝对定位层，都会把本该落到按钮上的点击接走。这不是委托特有的问题，但委托会让它更难查：用户报”点删除没反应”，你查委托逻辑怎么都查不出错，因为事件压根没进你那棵子树。排查利器还是 elementFromPoint：把出问题的坐标喂给它，看浏览器认定的最顶层元素是谁，十有八九是一个看不见却占着层的节点（opacity: 0 的元素依然参与命中，visibility: hidden 才不参与）。修法是收敛层叠上下文，而不是在 JS 里继续加补丁。顺带一提，透明 GIF 撑出来的”隐形关闭按钮”当年很多组件在用作点击热区，这类节点正是遮挡误命中的高发源头。

委托把监听器绑在容器上，于是容器的”身份”成了单点依赖。两类操作会让监听器无声丢失，一类操作则完全无害，分清楚：

无害的是换内容。list.innerHTML = html 重建所有子节点，监听器还绑在那个 ul 身上，ul 没动，委托照常工作——这正是委托对付动态列表的本钱。子节点批量插入时若想避免逐条重排，用 DocumentFragment 收拢后一次 appendChild，细节与性能账在《DOM 增删改查与文档碎片 DocumentFragment》里算过，本文不重复；只提醒一句与委托相关的边界：fragment 里的节点脱离文档时，上面那段 matchesSelector 的 querySelectorAll 兜底分支查不到它们，所以事件派发前节点必须已经在文档树里，好在浏览器本来也只会对已插入的节点派发用户事件，这条纪律多数时候自动满足。

致命的是换容器本身。两条常见路径：parent.replaceChild(newList, list) 用新 ul 顶掉旧的；或者模板引擎整段重渲染，把包裹列表的那块 DOM 连根换掉（2014 年人手一个的模板工具大多是 outerHTML 式的整体替换）。容器节点一旦被摘走或替换，绑在它身上的监听器跟着留在孤儿节点上，新容器一身干净、一个监听器都没有，症状是”功能今天还好好的，刷新前突然全灭”——只要页面里有任何一处重绘了那块区域。更隐蔽的变种是”摘下来改完再插回去”：list.parentNode.removeChild(list) 改完再 appendChild 回来，监听器其实还在（它跟着节点走，不会掉），很多人误以为会丢，在插回去后又补绑一次，于是双触发。测试方法很简单，出问题的容器上把事件对象与绑定记录打印出来：

委托管不了的两件事：hover 状态与键盘可达性

委托只处理离散事件，连续状态不归它管。先说 hover。

CSS 的 :hover 伪类不需要 JS，够用；但一旦要做”悬停高亮整行 + 显示操作按钮”这类需要 class 参与的状态，JS 就要接管进出判定，而能冒泡的只有 mouseover / mouseout，它们跨越容器内任意元素边界都会派发，直接用它们切 class，鼠标从 li 移到它内部的 span 时就会先灭后亮、闪个不停。手工模拟 enter / leave 语义的标准写法是查 relatedTarget（老 IE 对应 fromElement / toElement，前篇的属性表已列过名字，这里只给委托用法）：

这套模拟与原生 mouseenter / mouseleave 语义并不完全等义：高频移动下每个跨边界动作都要跑一遍祖先链判定，开销实打实；relatedTarget 在某些边缘现场（从浏览器 chrome 外进入页面、老 Android 触摸转合成事件）会是 null，代码里已经把它按”进入”处理，但体验上会有毛边。jQuery 委托版的 mouseenter 内部走的是同一思路，所以用库也别指望语义是免费午餐——节点上千的列表加委托版 hover，先测一遍鼠标平移的帧率再上线。

再说键盘与无障碍，这是委托最容易被顺手引入缺陷的地方。委托绑的是 click，而 click 的合成派发规则是：链接与原生按钮上，回车键会合成 click；换成 div 或 li 做的”可点行”，回车与空格在哪个浏览器里都不会给你凭空变出一个 click——触屏用户点得到、键盘用户按不到，功能对一半人直接不存在。老 Firefox 还有一条额外的历史行为：光标落在按钮上按空格只派发 click 不派发 keyup 的顺序各家不一致，涉及空格快捷键的要在真机上各试一遍。对策分两层。上层是根治：可点的东西就该是 a 或 button，语义化标签的选型在《section、article、nav、aside 语义化标签的合理使用》里谈过，此处只说事件后果——用了原生控件，键盘合成 click 由浏览器负责，委托直接收到。下层是补救：样式确实改不动、非 div 不可的存量代码，在委托层补一个 keydown 通道，把回车与空格换算成对命中元素的操作：

空格键务必 preventDefault，否则在页面可滚动时它会顺手把页面往下翻一屏。动态显示的操作按钮（藏在 hover 里那种）键盘用户永远聚焦不到，要么常驻，要么配合 tabindex 与 aria-hidden 管理，别把”只有 hover 才出现”当成唯一入口。

工程化封装：一个处理边界的 ES5 delegate

把前面所有边界收拢，落成一个可以直接抄进项目的函数。与《DOM 事件对象与事件委托》末尾那份”够用版”相比，这一版多干的是边界活：焦点类自动选路（IE 走 focusin、其余走捕获）、事件对象归一化到 IE8、返回带元信息的卸载句柄、上溯过容器即停。仍不含命名空间与 event.data——那是库的领地。

三个设计决定说明白。其一，focus 的降级链用 'onfocusin' in document 探测：这句在 IE8 上为真、在 2014 年的 Firefox 上为假、在 Chrome 与 Safari 上为真，一个探测覆盖三种现实；注意 IE8 没有捕获阶段，所以绝不能给 IE8 留”focus 加捕获”这条路，它只能走 focusin。其二，resolveType 对 blur 的处理里 focusout 同源探测，逻辑对称。其三，对外暴露的归一化事件对象是按需最小集——只放委托边界需要的字段，坐标、which 这些完整归一化请参照前篇的补偿函数，避免重复造 jQuery。

手工验证清单（当单元测试用，每条都对应上文的一个边界），建议在一台真机 VM 阵列上跑：Chrome（当时通道）、Firefox 最新版、IE8 / IE9 / IE10、Android 2.3 自带浏览器与 Android 4.x：

  1. 点 li 内层 span，确认 this 是被委托的 li、target 是 span——最小例子回归。
  2. 把 target 换成 SVG 图标（页内内联），确认不抛 fn.call 错误——nodeType 与选择器匹配在 SVG 上也过。
  3. 输入框上委托 focus：IE8 走 focusin 分支触发、Firefox 走捕获分支触发、Chrome 两分支任一均可，三处行为一致才算过。
  4. 在 li 内嵌一个会在自己处理器里 stopPropagation 的模拟组件（临时写一个），确认委托失效且捕获哨兵可见——记录为已知限制，或把该组件的委托容器改到其下。
  5. 用 replaceChild 换掉容器本体，再点新列表，确认功能随容器一起消失——这是预期行为，借此演练”绑稳定祖先”的修复动作。
  6. 全程 keydown 回车与空格走 div 补救通道，Firefox、Chrome、IE8 三处都触发且页面不因空格滚动。
  7. 调用卸载函数后重放以上触发点，确认零残留；对照 console 里事件计数，排除双绑。

这份封装不到一百行，但它把”什么事件能进委托管道”的问题从口口相传的军规固化成了代码路径。值得再强调一次的是它没解决的：不冒泡清单里的 change / submit 一族，它不会也不能替你兜住。

小结：能委托、不能委托、有条件委托

最后把全文收成三档判断清单，供评审代码时对照。

能委托（冒泡有规范保证、各家行为多年稳定）：click、dblclick、mousedown、mouseup、mousemove、mouseover、mouseout、contextmenu、keydown、keyup、keypress、input。这些事件的委托代码在 IE8 到新版 Chrome 的整个光谱上走同一条逻辑，放心绑定。

不能委托（原生层面收不到，任何写法都是自欺）：change、submit、reset、select 在需要覆盖 IE8 与老 Opera 时一律直绑控件本身；scroll 只能绑滚动容器；resize 只有 window 收得到；资源 load / error 在 IE8 上只能逐元素绑；伪元素、被 pointer-events 穿透掉的节点、被替换或摘除的容器，属于”物理上不存在事件”，不在委托讨论范围，属于代码结构问题。

有条件委托（换事件名、换阶段、或接受语义偏差后才成立）：焦点类——IE 系走 focusin / focusout，Firefox 走 focus 捕获，Chrome 双路皆可；进出悬停态——委托 mouseover / mouseout 并用 relatedTarget 自判，接受与原生 mouseenter / mouseleave 的语义偏差与性能开销；资源加载——标准浏览器可在 document 上捕获，IE8 除外；自定义事件——IE8 下 fireEvent 冒泡不可靠（前篇已论证），要跨 IE8 就自己沿 parentNode 手动派发。

一条心法收尾：委托失效的排查永远从三问开始——事件冒不冒泡、容器还是不是当年那个容器、链路上有没有人截胡。三问都排除掉，再回头看 target 的节点类型与 CSS 命中。还有一点要说清：上面这些边界不是”原生才有的问题”，而是”被 jQuery 遮住了的问题”。jQuery 1.11 用特殊事件机制补了 focusin、模拟了 mouseenter 委托、给 change 做了补绑兜底，所以在 jQuery 项目里这些坑多数表现为”时机不对”而不是”完全失灵”；换到 Zepto 1.1.x 或纯原生页面，同一份代码的失效立刻、静默、不打招呼。混合工程（桌面 jQuery、移动 Zepto、公共组件两边跑）里，这份清单要按最严格的那一档执行。把清单贴在工位上，比背十篇教程有用。
