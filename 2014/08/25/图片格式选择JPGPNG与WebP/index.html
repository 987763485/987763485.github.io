图片格式选择：JPG、PNG 与 WebP

同一张图，选对格式能省掉三成以上的体积，选错则白白多传几百 KB。这件事和懒加载、上传前压缩、构建合并都不是一回事——那几样分别在旧文《图片懒加载与预加载实现》《图片上传预处理实践》《资源合并与压缩的收益分析》里谈过了，本文只聚焦一点：图片格式本身怎么选，以及在 2014 年这套工具链和兼容性现实下，怎么把选择落到构建脚本与服务端配置里。适合正在给站点做图片瘦身、又被 WebP 兼容性搞得犹豫不定的前端同学。读完你能得到一张决策表、一套 Grunt 构建片段、一份服务端协商配置，还有一串我们真踩过的坑。

先把结论摆在前面：2014 年做图片优化，主格式仍然要押在 JPEG 和 PNG 上，WebP 只能当作渐进增强去”锦上添花”——因为它当时的浏览器支持面太窄，把它当默认格式必然破图。

从编码原理看四种格式的差别

选型不是背口诀，得知道每个格式为什么在这些场景下占优。往下讲原理，都是为了后面那张决策表服务。

JPEG：有损、色度二次采样、基线与渐进式

JPEG 是有损格式，核心是把图像切成 8x8 的块做离散余弦变换（DCT），丢掉人眼不敏感的高频信息，再量化编码。它没有透明通道，也不适合大面积纯色和锐利文字——色块边缘会出现振铃效应（ringing），文字边缘会发毛。

影响体积的另一个旋钮是色度二次采样。人眼对亮度敏感、对色度迟钝，于是编码时把色彩空间从 RGB 转成 YCbCr 后，对两个色度分量降采样。常见有 4:4:4（不降采样，最费）、4:2:2、4:2:0（色度横竖都减半，最省）。照片用 4:2:0 基本看不出差别，却能再省一截；但带细密彩色线条或文字的图，4:2:0 会让线条发虚，这类就该回到 4:4:4 甚至换 PNG。质量参数和采样要一起调，光调质量不调采样，等于漏掉一半可省的字节。

JPEG 还分基线（baseline）和渐进式（progressive）。基线是一行行从上往下解码，下载多少显示多少的上半部分；渐进式是先糊后清，弱网下体验明显更好——用户先看到一张模糊的整图轮廓，再逐步变清晰，比”上半截清楚、下半截空白”舒服得多。代价是同画质下渐进式体积略大一点，而且有个当年绕不过去的坑：IE6 到 IE8 无法边下边显示渐进式 JPEG，要么什么都不显示、要么出现黑块，直到整个文件下载完才渲染。也就是说 progressive 这个”弱网利器”，恰好在我们最需要兼容的老 IE 上失效。要不要用，取决于你的用户里老 IE 占比，别默认打开。

PNG：无损、调色板模式与透明的两副面孔

PNG 是无损的，用 deflate 压缩像素，适合纯色块、插画、需要透明、以及带文字的界面截图——这些地方它比 JPEG 又小又清晰。反过来，一张照片硬塞进 PNG，体积能比 JPEG 大好几倍。

关键在透明怎么存。PNG 有两条路：真彩色加完整 alpha 通道（常见叫 PNG24/PNG32），每个像素独立记录透明度，灵活但费——RGB 加 alpha 就是每像素 4 字节打底；调色板模式（PNG8）只保留一张不超过 256 色的色表，每像素只存一个索引，配合 tRNS 段还能给”某个索引”标记透明。这里要分两种 tRNS：一种是单色透明（1-bit），色表里只有一个颜色是全透明，其余全不透明，效果和 GIF 的透明一样，省到极致但只能”要么全透要么不透”；另一种是每个色表项各带一个 alpha 值，能表达半透明，pngquant 这类工具做的正是这种带 alpha 的 PNG8。带 alpha 的 PNG8 能把一张真彩透明图砍到三分之一甚至更小，是图标类图片的降本主力。

但 PNG8 加 alpha 在 IE6 上有退化表现：IE6 根本不认 PNG 的 alpha 通道，只支持 GIF/PNG 的单色透明。你用 pngquant 做的半透明 PNG8，在 IE6 里那些半透明像素会被铺在黑底上，边缘发黑、一团脏。所以凡是 IE6 还得伺候的透明图标，稳妥选择是单色透明的 GIF，或者干脆接受纯色不透明；带 alpha 的 PNG8 只发给能正确渲染的浏览器。

GIF：只留给小图标和动图

GIF 是 256 色的 LZW 无损，色深是它最大的短板，照片类几乎不能用。它在 2014 年只剩两个正当用途：一是单色透明的极小图标，兼容性最好、IE6 也没问题；二是动图——GIF 动画是最广谱的动图格式，各家浏览器、各代 IE 都能放。除了这两点，能不用就不用。

WebP：更强的压缩，和很窄的支持面

WebP 是 Google 在 2010 年发布的格式，基于 VP8 帧内编码，0.2 版本又补齐了无损、透明通道和动图三种能力，一个格式覆盖了 JPEG、PNG、GIF 各自的地盘。有损 WebP 走的是预测加块编码，无损 WebP 用的是类似但更聪明的颜色变换加 Huffman。按 Google 官方的说法和我们自测的量级，同画质下有损 WebP 比 JPEG 普遍小约两成到三成，无损 WebP 比 PNG 也常常小这一档甚至更多。要强调这是 2014 年的公开数据与自测的量级，不是逐张图保证的精确百分比，具体收益得对着自己的样张跑。

收益诱人，但 2014 年 8 月这个时间点，WebP 的原生支持只有 Chrome 和 Opera。Safari、iOS 上的 Safari、桌面 IE（11 及以下）、以及相当多 Android 自带浏览器统统不支持。这就是全文最核心的一条现实：WebP 只能是增强，不能是默认。<picture> 元素当时还只是提案草案，srcset 也才在 Chrome 30 以上和 Safari 7 上开始出现，同样尚未成为标准。所以想用 WebP 又不能让不支持的浏览器看到破图，只能自己做协商——这正好是本文后半段要落地的东西。

构建期：Grunt 加 imagemin 把体积压到位

选型定了，接着靠构建脚本把每张图按目标格式做一次到位的优化。2014 年我们的管线是 Grunt 0.4 配 grunt-contrib-imagemin，背后调用的是 mozjpeg、optipng、pngquant 这些命令行工具。mozjpeg 在 2014 年 3 月发布了 2.0，同画质下比老 libjpeg 小一到两成，值得在构建里指定；pngquant 当时是 2.x，能把真彩透明转成带 alpha 的 PNG8，效果很好，但要注意它的商业授权是要购买许可的，别在闭源交付里当成免费组件随手打包。

这段要交代插件当时的局限。grunt-contrib-imagemin 0.4 那会儿，它对 pngquant、mozjpeg 的支持要靠额外的 imagemin-pngquant、imagemin-mozjpeg 这些 transform 插件挂上去，版本对不齐就静默降级回默认 optipng，你以为压过了其实没动。更坑的是它不会帮你改格式：把一张真彩 PNG 交给它，它不会自动转成 JPEG 或 WebP，格式转换是前面决策表里人来定的事。所以构建脚本只负责”把已选格式压到该格式的极限”，选格式这一步别指望工具替你做。批量场景也可以用 ImageMagick 的 mogrify 先做格式与采样转换，再交给 imagemin 收尾；追求一键可视化的同事会用 ImageOptim，那是个 Mac 上的图形壳，底层同样调 mozjpeg、pngquant、optipng，适合设计稿交付前的手动过一遍，但进不了 CI。

服务端：WebP 协商与回退

构建产物里同一张逻辑图往往存两份，比如 banner.jpg 和 banner.webp。谁用哪份，交给服务端按客户端能力决定。难点有两个：判断要准，缓存不能被判断搞乱。

先说判断。最天真的是看 UA，但 UA 判断不可靠——不少国产浏览器把自己伪装成 Chrome，UA 里明明白白写着 Chrome，实际内核却不支持 WebP，你据此返回 WebP，用户看到的就是破图。相对可靠的是看请求头：支持的浏览器在请求图片时 Accept 头里会带 image/webp。但页面主文档的 Accept 和图片子资源的 Accept 不完全是一回事，光靠 Accept 也会误判。我们当时的做法是前端做一次真正的能力探测，把结果写进一个 cookie，服务端读这个 cookie 来决定——判断落在浏览器自己的解码能力上，UA 伪装骗不了它。

小图标：合并与内联的边界

单个几 KB 的小图标，请求数开销往往比图片本身还大。这类优先合并成 CSS sprite，靠 background-position 定位，一次请求换掉几十次；图标要多色、要跟字体一样缩放控制的，走 iconfont，这套取舍旧文《CSS图标字体iconfont的使用与制作》讲过了，这里不展开。剩下的极小图，可以考虑直接 base64 内联进 CSS，连请求都省掉。

但内联有门槛，不能一把梭。Base64 编码本身会把体积撑大约三分之一，且内联图跟着 CSS 一起走、没法单独缓存。真正划算的是那些小到”省一个请求的收益盖过编码膨胀”的图。2014 年我们用的经验阈值在 4KB 上下——单张原始字节小于约 4KB 才内联，否则老老实实做成 sprite 或独立文件。判断逻辑写起来很简单：

那些年踩过的坑

再精巧的方案也是坑换来的，按代价从大到小列一遍。

UA 判断 WebP 导致破图。 前面反复讲过：国产浏览器伪装 Chrome UA 却不支持 WebP，你信了 UA 就返回 WebP，页面一片空白。教训是别信 UA，用 canvas 能力探测写 cookie，让浏览器自己证明。

协商和缓存耦合，切了格式还是旧图。 加了 WebP 协商却没发 Vary，或者 CDN 把带 cookie 与不带的响应混在一起缓存，用户明明换了支持 WebP 的浏览器，拿到的还是缓存里的旧 JPEG，反过来也错。改协商逻辑一定要连带把 Vary 和 CDN 的缓存 key 一起核对。

透明 PNG 强行减色导致锯齿。 为了省体积把带渐变的透明 PNG 用 pngquant 猛减到几十个色，半透明边缘会出现明显色带和毛刺。要么调高质量区间、加大误差扩散，要么这种图就不硬转 PNG8，留真彩再叠 WebP。

iOS 老设备的大图内存上限。 早期 iPhone（如 4S）的 Safari 对单张解码进内存的位图有红线，一张几千乘几千的大图，哪怕文件只有几百 KB，解码成 RGBA 后也能轻松上几十 MB，直接触发页面重载或白屏。老设备上的头图要按显示尺寸给合适像素，别把 5000 像素的原图甩给手机浏览器去降采样，降采样这件事在构建期就替它做完。

老 IE 的透明方案。 需要兼容 IE6/8 又必须用 PNG 半透明时，当年靠 filter: progid:DXImageTransform.Microsoft.AlphaImageLoader(src='x.png') 这类滤镜顶一下，但它只对老 IE 有意义、且会屏蔽背景、不支持定位平铺，别当成通用方案到处用——新浏览器一律走原生 alpha，老 IE 才单独喂这个滤镜或退成 GIF。

小结

格式选择是图片优化的地基，工具链和协商是把地基变成收益的脚手架。回到原理：JPEG 靠 DCT 加色度采样吃照片，渐进式弱网体验好却在老 IE 上翻车；PNG 无损、靠 PNG8 加 alpha 给透明图降本，却在 IE6 上退化；GIF 只剩小图标与动图；WebP 三套模式压缩最强、能省两到三成，可惜 2014 年只有 Chrome 和 Opera 认，<picture> 还只是草案。据此给团队定三条可直接执行的规约。其一，默认格式押 JPEG 加 PNG，按决策表选，WebP 只作为协商增强，绝不让不支持的浏览器看到破图。其二，构建期用 Grunt 加 imagemin 把每种格式压到极限，pngquant 商用记得买授权、imagemin 不做格式转换这层人来兜。其三，服务端协商必须配 Vary 并核对 CDN 缓存 key，判断用 canvas 探测写 cookie 而不是信 UA。图片这摊事，省下的字节是看得见的，选错格式带来的破图和错版缓存是看不见的债——把三条规约钉进流程，才能少还一次债。
