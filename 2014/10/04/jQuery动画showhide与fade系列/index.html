jQuery 动画 show、hide 与 fade 系列

先把三个易混概念理清

show() / hide()、fadeIn() 系列、slideDown() 系列这三组方法，看起来都是”让东西出现或消失”，改的却是完全不同的属性，出问题的时候症状也各不一样。项目里大量”点一下没反应””展开后错位””关不干净又漏出来”的毛病，根子都在没把它们分清。这一节先把地基打好，后面每个坑都对应回到这张差异表上。

先说结论式的分工。show() / hide() 改的是 display：不带时长参数时是瞬间切换 display 与 none，一旦传了 duration（比如 show(400)），它会走动画队列，同时补间 width、height、opacity 把元素撑开或收掉，结束再把 display 落到某个具体值。fadeIn() / fadeOut() / fadeTo() 改的是 opacity：fadeIn 先把 display 恢复成可见再让透明度从 0 走到 1，fadeOut 相反，透明度归 0 之后在动画结束时补一个 display: none；fadeTo(300, 0.5) 只把透明度补间到指定值，不碰 display，元素该占位还占位。slideDown() / slideUp() / slideToggle() 改的是高度相关属性：它内部其实就是 animate({ height: "show" }) 这类内置关键字的形式，先把 overflow 设成 hidden，从 0 补间到测量出来的自然高度，动画结束再把内联高度还原掉。

把最容易踩的几列整理成一张表：

方法 改哪个属性 结束是否留下内联 style 并发行为 老 IE 注意
show() / hide() 无时长 display 写死一个 display 值 不入队，瞬间完成 视图标默认值判断有差异
show(400) / hide(400) display 加宽高与透明度 留 display 及还原值 排进 fx 队列，串行 宽高补间会踩 hasLayout
fadeIn() / fadeOut() opacity，结束附带 display fadeOut 留 display: none 同一队列串行 依赖 filter: alpha
fadeTo() 仅 opacity 不改 display 同一队列串行 残留 filter 会一直半透明
slideDown() / slideUp() 高度与 overflow 结束还原高度 同一队列串行 高度测量受布局抖动影响

再补一个判定上的坑：:hidden 与 :visible 的判定依据是 display 或盒子的宽高，而不是透明度。也就是说 fadeOut 结束后的元素因为带上了 display: none，会被算作 :hidden；但你用 fadeTo 把它压到 opacity: 0，它仍然是 :visible，visibility: hidden 也一样算可见。凡是靠 $('.x:visible') 去做状态判断的地方，都要想清楚用的是哪一组方法。

顺带交代动画系统的两个全局开关，后面会反复用到。$.fx.interval 是 jQuery 内部驱动所有补间的定时器周期，默认约 13 毫秒一次 tick，页面上同时在动的元素越多，每个 tick 要重算和写回的样式就越多。$.fx.off 置为 true 时，所有动画会被立刻跳到终值、等于关闭动画，这是给低端设备留的降级口。至于 jQuery 版本：本文所有写法基于 1.11，$.browser 早在 1.9 就被移除了，别再去检测它；2.1 虽然当时已经发布，但它不支持 IE8，只要项目还要兼容 IE8，就还得留在 1.x，两套别混用。至于 CSS 动画与 JS 动画到底谁更省帧的实测结论，我在《CSS 动画与 JS 动画的性能取舍》里量过，这里不再重复。

坑一：show() 把 display 改掉，顺手破坏了布局

最常见的翻车来自一个想不到的副作用：show() 会把元素原本内联的 display: none 换成它认为合适的 display 值，而这个值经常是 block。对 <div> 无所谓，但对我们原本应该是 inline、inline-block 甚至表格里的 table-cell 元素，就是灾难——行内图标突然独占一行、表格单元格脱离了表格流，页面结构整个乱掉。

问题的机理在第一节已经埋好：当一个元素是靠标记里的 style="display:none" 或样式表规则隐藏的，而它又没有被 jQuery 亲手 hide() 过（也就是没有存下”上一次的 display”），show() 只能退回按标签名去猜一个默认值。老内核里这个默认值判断经常不准，<span> 给成 block、<td> 丢掉 table-cell 都是我们线上真实见过的。

坑二：动画队列堆积与 .stop() 的四种组合

jQuery 把每个元素的动画排进它自己的 fx 队列里，默认是串行执行——上一个没跑完，下一个就在队列里干等。这带来一个非常典型的”反应慢半拍”：用户手快点了几下折叠面板，最后一次点击界面却迟迟不动，等它终于动了，又是好几段动画噼里啪啦连着放完。因为每一次点击都往队列尾部追加了一段完整动画，点了五次就欠着五段债。

治这个的武器是 .stop(clearQueue, jumpToEnd) 两个布尔参数，四种组合差别很大，别只会裸调 .stop()：

写法 当前这段动画 队列里后续动画 当前动画是否跳到终值
.stop() 立即停 保留，继续跑 否，停在中间值
.stop(true) 立即停 清空 否
.stop(false, true) 立即停 保留 是，跳到终点
.stop(true, true) 立即停 清空 是

实践规则我给自己定成一句话：每次要起一个新动画之前，先 stop(true, true)。clearQueue 清掉那些还没跑的欠债，jumpToEnd 把正在中间态的元素一次性推到终点，这样紧接着的新动画是从一个干净、确定的状态出发的，不会出现”关到一半又展开”的鬼畜画面。裸 .stop() 或只 stop(true) 会把元素丢在一个不上不下的中间值上，对 slideDown 这类依赖起点高度的动画尤其致命。

但有两个必须记住的边界。第一，.stop() 管的是队列里的动画，不天经地义地管 .delay()。如果你排的是 $("x").delay(1000).fadeOut()，那个 delay 和它后面挂着的 fadeOut 是排在队列里的后续项，只调不带 clearQueue 的 .stop() 掐不掉它们，稍后照样会执行；要清干净得靠 .stop(true, ...)。第二，也是坑三要接的话题：.stop() 打断动画时，不会触发这段动画的 complete 回调。它只是把补间停了，然后接着走队列，那个绑在动画对象上的完成函数被直接跳过。

顺带一条通用的：热路径里反复 $('.x') 这种查询开销，靠缓存 jQuery 对象就能省掉，具体在《jQuery 性能优化实践》里讲过，动画代码里同样适用，这里不铺开。

坑三：回调只在动画结束触发，状态标志会卡住

很多人以为 hide(400, fn) 里的 fn 是逐帧回调，其实它只在整段动画正常跑到终点时执行一次。麻烦就出在”跑不到终点”：只要这段动画被 .stop() 打断、元素被移除、或者中途又触发了新的 hide，fn 就不会执行。于是那种把状态标志位塞进回调的写法迟早出事。

状态标志卡在 true，后面所有分支逻辑就都走错了，这种 bug 最难查，因为它只在”用户快速操作打断动画”时复现。两种更稳的写法。

坑四：slideDown 遇到异步变高就失准

slideDown 的做法是先测出元素”自然高度”，再从 0 补间过去。测高的那一刻，如果内容还没就位——最典型是里面有异步加载的图片——测出来的是一个偏小的值，动画老老实实只展开到那个小高度就停了，随后图片到位、真实内容撑高，就把下边裁掉了一截。

flowchart TD
    A["点击展开触发 slideDown"] --> B["读取当前自然高度"]
    B --> C["图片此时尚未加载完"]
    C --> D["算出的目标高度偏小"]
    D --> E["动画只展开到一半"]
    E --> F["图片到位后底部内容被裁切"]

解法按成本从低到高有三种。最稳的是等内容就绪再滑：把展开拆成”先确保图片加载完，再 slideDown“，用 $(img).on("load", ...) 或者在 window 的加载之后触发。给容器预留一个固定的高度、用 max-height 兜住展开态，也是一种务实做法，代价是要提前知道内容上界。至于 animate({ height: "show" }) 与 slideDown 的差别，其实 slideDown 就是它的封装，差别只在于 slideDown 帮你把起止值和 overflow 都处理好了，测量时机同样是”开始那一刻”，所以它并不能自动规避异步变高——真要精细控制，得自己在正确时机把动画踢起来。

slideUp 这边还有个残留问题：正常收起结束后元素是 display: none，但动画中途被 .stop() 打断过，内联高度可能停在某个非零值上，下次再用别的方式（比如直接加类把它显示出来）展开时，那截残留的 height 会把内容压扁，看起来”展开只显示了一半”。稳妥做法是再次展开之前 stop(true, true) 之后把内联高度清一下：

坑五：老 IE 上 opacity 动画与 filter 的连带毛病

2014 年做 PC 页，IE8 仍然躲不掉，而透明度动画恰恰是老 IE 上最容易出岔子的一类。IE9 以下不认 CSS 的 opacity，jQuery 只能退而去写 filter: alpha(opacity=...)。这个滤镜有两个副作用：一是它会触发 hasLayout，让原本靠 position: absolute 定位的元素跟着偏移，出现”淡入进去却站错位置”；二是滤镜作用在整个元素上，子元素会跟着一起半透明，文字还常常丢掉 ClearType 变成发虚的锯齿。jQuery 内部对 opacity 做了特殊处理，会在补间时同时维护 filter，并试图在透明度回到 1 时把 filter 清掉，以躲开这些副作用。

坑就在这”试图”上：如果淡入动画还没跑到 1 就被 .stop() 打断，或者你半路 fadeTo(x, 0.5) 之后再没管它，那个 filter: alpha(opacity=..) 就可能残留下来，元素永远半透明、或者定位一直不对。所以老 IE 上凡是能被打断的淡入淡出，收尾一定要把状态推到底再收：

性能与降级：interval、并发数与 $.fx.off

回到 $.fx.interval 这个默认 13 毫秒的周期。把它调大，比如设成 30 甚至 60，最直接的收益是每个 tick 之间触发的样式重算变少、CPU 占用下来；代价是帧率随之掉下去，动画看着一顿一顿。这是个纯权衡，不是调大就更好，低端机上用它换流畅度、高端机上保持默认，才合理。真正决定卡不卡的还有”同时在动的元素数量”：因为所有补间共用这一个全局定时器，每多一个在跑的元素，每个 tick 就多一份取值、插值、写回的工作，几十个元素齐动时主线程很容易顶不住。这也是移动端不建议拿 jQuery 动画去做大面积入场效果的原因，移动端的切页动画我另在《移动端页面切换动画》里用 CSS 处理。至于”到底该 CSS 还是 JS”的分寸，前面《CSS 动画与 JS 动画的性能取舍》已经量过，一句带过。

$.fx.off = true 是给低端设备留的总开关，打开后所有 show/hide/fade/slide 都会瞬间跳到终值、不再逐帧跑，功能照常、只是没有过程。要不要开，我一般用”已知低端 UA 直接关，其余用一次真实淡入的耗时来判定”这套组合：

小结与使用检查清单

这几组 API 的复杂度不在语法，而在”改了哪个属性、排在哪个队列、由谁触发回调”这三条隐线。把它们踩过的坑收拢成一份动手前的检查清单：一是队列，起新动画前先 stop(true, true)，记住 .stop() 不触发 complete、也不清 .delay() 后面的项；二是回调，关键状态不要塞进动画完成回调，用 .queue() 插逻辑一定补 next()，更稳的是让状态跟着点击意图当场更新；三是 display 污染，能用 class 切换就别用 show()/hide()，非用不可就准备回调把 inline-block/table-cell 按回去；四是测高时机，异步内容没就位前别 slideDown，展开前顺手清一下残留的 height；五是老 IE 兼容，opacity 动画会落到 filter: alpha，收尾要 fadeTo(0, 1) 清残留、必要时补 zoom: 1，且这一切只在 jQuery 1.11、且需要 IE8 时才成立，切到 2.1 就没有 IE8 了；六是降级，低端 UA 或探针超时就把 $.fx.off 打开，把动画整体关掉保功能。把这份清单贴在页面上线前过一遍，绝大多数”点一下没反应、展开闪烁、关不干净”的老毛病都能提前挡掉。
