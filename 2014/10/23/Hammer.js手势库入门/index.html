Hammer.js 手势库入门

移动端页面里”捏合缩放、滑动切换、长按保存”这些交互，用裸 touch 事件手写一遍并不轻松。Hammer.js 是 2014 年做移动 Web 时很受欢迎的一个人势库，1.0.x 版本压缩后只有 3.5KB 左右（gzip 前约 12KB，MIT 协议），却把多指、方向、互斥这些脏活全包了。本文不满足于会调用 API，而是把它内部的分层架构和识别器机制拆开讲一遍，再回到用法、配置与坑，适合准备把它引入项目的同学。

它要解决的问题

裸的 touchstart / touchmove / touchend 只是”手指接触屏幕”这一物理事件的原始信号，把它变成一个”手势”至少要自己处理四件事：多点触摸时区分几根手指并跟踪每根手指的位移；把斜向滑动归一化成上下左右某个方向；协调 tap 与拖动的互斥（手指按下后移动了就不能再算点击）；以及 iOS 与 Android 在 touchcancel、默认滚动行为上的差异。这些识别器逻辑我在旧文《移动端 touch 事件与手势基础》里手写演示过，这里不再重复。

Hammer 的思路是在原始 touch 之上加一层”语义化事件”：你在 touchstart 里写的那个匿名回调不该关心三角函数，它只想知道”用户向左滑了”还是”用户捏合放大了 1.4 倍”。库内部把判定做完，命中后派发 tap、swipe、transform 这类带业务含义的事件，并把结构化结果挂在 ev.gesture 上交给回调。

架构总览：从 touch 到语义事件的数据流

Hammer 1.x 的整体结构是一条单向流水线，可以拆成四层来看：

flowchart TD
    A[touch 或 mouse 原始事件] --> B[采集层: 维护 pointers 数组]
    B --> C[实例状态机: first / stop / 计时器]
    C --> D1[tap 识别器]
    C --> D2[hold 识别器]
    C --> D3[drag 与 swipe 识别器]
    C --> D4[transform 识别器]
    C --> D5[release 收尾识别器]
    D1 --> E[trigger 派发语义事件]
    D2 --> E
    D3 --> E
    D4 --> E
    D5 --> E
    E --> F[业务回调 on tap 等]
    G[配置项 options] --> C
    G --> D1

采集层负责把每一刻的接触点快照下来，状态机（即 Hammer(element) 返回的那个实例）维护全局的 first（是否触摸后的首个 move）、stop（是否已判定手势终止）和计时器，识别器组则各自回答一个独立问题：这是点击吗？这是长按吗？拖动够格触发 swipe 吗？transform 需要几个点？prevent_default 与 stop_event 两个配置项作用在派发环节：前者决定要不要对原始 touch 事件调用 preventDefault（从而压制浏览器默认的滚动与点击），后者决定语义事件要不要停止冒泡。

识别器之间的互斥是这套架构最有价值的设计。以 drag 与 tap 为例：一旦位移超过阈值，drag 识别器把实例标记为”已在拖动”，touchend 时 tap 的判定条件（位移必须很小）自然不成立，两者不需要显式通信就互斥了。transform 则硬性要求 pointers.length 等于 2，单指时直接短路。方向不是布尔值而是位掩码常量，Hammer.DIRECTION_UP / RIGHT / DOWN / LEFT 各占一个二进制位，DIRECTION_ALL 是它们的按位或，判断时再做按位与，所以一个配置项可以同时表达”只允许水平方向”这样的组合。

回调侧拿到的事件对象只有一个约定：除标准的 type 与 target 外，所有几何信息都挂在 ev.gesture 上。常用字段的含义如下表，写业务时基本不用回头翻源码：

字段 含义 典型用途
deltaX / deltaY 相对按下起点的位移 拖拽跟手、计算落点
direction 八方向掩码常量 swipe 区分左右翻页
scale 双指距离相对起始值的比例 缩放
rotation 双指连线相对起始角的角度增量 旋转
center 当前接触点的几何中心 围绕双指中点做变换
srcEvent 原始 touch 事件 需要 preventDefault 或读 target 时

源码级拆解几个关键机制

pointers 数组：一切判定的地基

实例里最核心的状态就是这个数组，它不是原始 touch 列表的引用，而是每帧重建的快照：

单指还是双指，看的就是 instance.pointers.length：drag、tap、hold 只认长度为 1，transform 只认长度为 2。手指离开屏幕后浏览器不再报告它的位置，这个数组配合 identifier 的匹配逻辑，就解决了”多指先后按下、各自跟踪”的难题。

distance 与 angle：方向和 deltaX 从哪来

ev.gesture.deltaX / deltaY 是起点与当前点的坐标差，而 direction 是把两点连线与水平轴的夹角归类到固定方向桶里得到的：

用掩码而不是字符串的好处是配置能表达集合：水平方向就是 LEFT 与 RIGHT 两个位的组合，判定处一次按位与即可，不需要写一堆 or。

tap 与 hold：阈值、定时器和取消

tap 的判定发生在 touchend 时刻，条件有三个：全程只有一根手指、首尾距离小于位移阈值、按下到抬起的时长没超过 hold 的计时线。hold 反过来：touchstart 时挂一个默认 250ms 的定时器，到点仍未释放且没发生明显位移就触发；一旦 touchmove 位移超阈值或手指提前抬起，立即 clearTimeout 取消：

同一段代码里 tap 与 hold 天然互斥：要么定时器先到点，要么手指先抬起，一个手势一次触摸只会有一个赢家。doubletap 则是 tap 之后再开一个约 300ms 的窗口，等第二下。

swipe：为什么看速度而不只看距离

swipe 与 drag 的区别不在距离，在”甩”的意图。库里的判定是位移超过阈值、且总耗时短、且距离除以时间得到的速度超过阈值（默认约每毫秒 0.7 像素）三者同时成立：

如果只要求距离，用户慢慢拖 200 像素也会被当成滑动切换，而这明显不是”翻页”的意图。速度门槛把”拖”与”甩”分开了，这是很多手写实现容易漏掉的一点。

release 与一次手势生命周期的收尾

识别器列表里最容易被人忽略的是 release，它其实是整套状态机的收尾动作：手指全部离开屏幕后，实例把这次手势的起止数据打包派发一个 release 事件，随后把 pointers 清空、first 重新置为 true、清掉所有计时器。这个”归零”步骤看起来很不起眼，却是连续操作正确性的来源——没有它，下一次 touchstart 会读到上一轮残留的接触点或脏标志位，表现为”第二下点击没反应”或”拖动突然从一个奇怪的位置开始”。所以调试手势丢失问题时，先确认 release 有没有正常触发，再怀疑自己的业务逻辑。双指变换后先抬起一根手指也会走类似的归零路径，此时 transform 直接结束而不会拖到单指继续误判。

集成、体积与销毁

按需关闭识别器是第一步：只用滑动切换就关掉 drag、transform、hold。核心代码本来就小，这一步省的主要不是字节，而是判定分支与手势冲突——tap 与 drag 在同一段位移区间里抢判定的机会少了，误触也少了。官方还有 Draggable、Droppable 这类扩展插件（以及汇总入口 Hammer.Gestures），注意它们是独立文件、按需引入的官方扩展，不在 3.5KB 的核心里。1.x 常用的配置项汇总如下，全部是下划线风格，直接赋值给实例的 options 即可：

配置项 默认 作用
tap / doubletap / hold true 三个基础识别器开关
drag / transform / swipe true 三个连续手势识别器开关
prevent_default false 对原始 touch 统一 preventDefault
stop_event false 语义事件是否停止冒泡
hold_timeout 250 hold 定时器的毫秒数
swipe_velocity 0.7 swipe 的速度门槛
drag_block_vertical false 拖动时锁死纵向，留给页面滚动

prevent_default: true 的副作用必须心里有数：它对原始 touch 事件统一 preventDefault，后果是同一元素上的 input 可能无法聚焦、-webkit-overflow-scrolling 容器滚不动。页面里同时跑 iScroll 这类模拟滚动方案时，两个库都会抢 touch 事件，边界怎么划分建议先读旧文《iScroll 实现移动端滚动》的坑复盘再决定。若只想屏蔽纵向干扰，可用 drag_block_vertical 让水平拖拽不吞掉纵向滚动。

最后一个容易漏的点：Hammer 是”一个元素绑一个实例”，实例内部对 element 挂了 touch 监听并闭包持有它。单页式交互里容器复用、删除节点时，必须先调用 hammer.remove() 把整套监听解掉，否则残留的监听会让旧 DOM 永远回收不掉，这正是旧文《DOM 事件移除与内存泄漏》反复强调的那类泄漏。

坑与选型判断

兼容性方面的账要提前算：Hammer 1.x 在没有 touch 的桌面浏览器会退化到 mouse 事件，手势能跑，但单根鼠标指针做不出双指 transform，桌面与移动端的体验分支得自己判断；tap 在部分内核上仍会被浏览器补发一个 click，同一个处理函数可能执行两次，要用标志位或自行拦截 click 兜底；Android 2.3 上缺 touchcancel 导致 pointers 数组偶发脏数据，getBoundingClientRect 也有抖动，要求高的页面建议加 try 恢复逻辑；跨 iframe 的拖拽完全不可用，touch 事件不会穿过框架边界，这类需求只能把拖拽层做在同一个文档里。

要不要引库，可以按下面的表权衡：

方案 体积 多指手势 方向判定 维护成本 适用场景
自己写 ES5 识别器 约 1KB 要手写两指跟踪 要手写掩码 高，坑要自己踩 只有一两个手势
Hammer 1.x 3.5KB gzip 开箱即用 内置常量 低，社区活跃 两种以上手势
jQuery Mobile 全家桶 数百 KB 依赖整套框架 内置 低但绑定重 本来就要整套 UI

只有一个 tap 的页面，引库确实不划算；但一旦同时需要 swipe 加 transform 再加 hold，手写代码量会迅速超过 Hammer 本身。

小结

Hammer.js 1.x 值得选的理由是架构干净：采集层、状态机、识别器、派发四层单向流动，识别器靠共享 pointers 与阈值配置实现互斥，方向用位掩码表达集合。实践上给三条结论：其一，按需只开用到的识别器，既省判定开销又减少误触；其二，transform 的 scale 与 rotation 都是相对起始值的增量，务必在 transformstart 里记基准；其三，库解决不了的事件模型之外的坑——click 双触发、无 touch 环境的鼠标退化、实例销毁时的监听残留——必须自己在集成层补兜底。把这三条守住，3.5KB 花得很值。
