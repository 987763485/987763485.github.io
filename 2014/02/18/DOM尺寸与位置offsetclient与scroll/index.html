DOM 尺寸与位置：offset、client 与 scroll

去年年底处理过一个下拉菜单在 IE8 上偏出屏幕的 bug，前前后后排查了两天，最后发现根因是把 offset、client、scroll 这三组属性的口径混用了。这三组属性是原生 JS 里做定位与滚动计算的全部家当，但它们各自的”尺子”从哪量到哪、含不含边框和滚动条，很多文章语焉不详。本文把三组属性一次讲清，再补上 offsetParent 规则、quirks 模式下的读数差异、视口与滚动位置的兼容取值函数，以及一个不依赖库的浮层定位实战。适合被”差 8 像素””差 17 像素”困扰过的同学。

从一次下拉菜单偏出屏幕说起

那套后台页面用的是一个老模板，<!DOCTYPE> 声明漏了，整页跑进了 quirks 模式。菜单的显隐逻辑是纯手写的：取触发按钮的 offsetLeft 沿 offsetParent 链累加算出页面坐标，再用 window.innerWidth 判断右边是否放得下、放不下就向左翻转。在 Chrome 和 IE9 上都正常，唯独 IE8 上菜单经常整个飞出可视区。

复盘时发现了三处叠在一起的错。第一，window.innerWidth 在 IE8 上是 undefined，参与运算后 left 变成了 NaNpx，浏览器直接忽略这次赋值，菜单落在样式表给的默认位置上。第二，quirks 模式下滚动位置和 clientWidth 的宿主从 documentElement 挪到了 body，我却还在读 document.documentElement.clientWidth，拿到的是 0 或者半截值。第三，按钮所在的一个 <td> 上有 1px 边框，而我把 offsetTop 的基准当成了边框外沿，实际规范是从 offsetParent 的内边距盒（padding box）起算，再加上 body 默认 8px 外边距没扣，几处误差累起来快 30px，翻转判定因此经常误触发。三个错单独看都不致命，串起来就是”菜单偏出屏幕”。下面把三组属性逐个钉死。

三组属性的口径对照

先给一张汇总表，这是全文的核心，后面所有坑都可以回到这张表上查。

属性 含 border 含 padding 含滚动条区域 参照/说明
offsetWidth / offsetHeight 含 含 含 布局完成后的实际外框尺寸，取整
offsetTop / offsetLeft 不含自身 — — 自身外边框沿到 offsetParent 内边距盒上沿的距离
offsetParent — — — 最近定位祖先，见下一节
clientWidth / clientHeight 不含 含 不含（要减掉） 可视区尺寸，即内边距盒去掉滚动条
clientTop / clientLeft 含 — 含 约等于上/左 border 宽加滚动条宽
scrollTop / scrollLeft — — — 元素内容当前卷走了多少，可读可写
scrollWidth / scrollHeight 不含 含 不含 含溢出内容的完整尺寸

用一个 1px 边框、10px 内边距、右侧出现 17px 纵向滚动条、内容宽 200px 的 div 来校准口径：

要点有三个。第一，offsetWidth 永远是你看到的”整个盒子的外壳宽度”，跟 CSS 里 width 写多少没有直接换算关系，要按盒模型推。第二，clientWidth 比 offsetWidth 少了两条 border 和滚动条，所以一个 width:200px 的滚动容器，offsetWidth 是 222，clientWidth 是 203，查”差 17px”的 bug 多半就是滚动条算在哪一侧的问题。第三，scrollTop 是相对内边距盒左上角的卷动量，不含 border，这也是为什么 clientTop 会被设计成”border 加滚动条”——它是把你从边框外沿拉回内容坐标系的那把补偿尺。顺带一提，IE 旧版在 quirks 模式下 clientTop、clientLeft 有可能恒为 0，不要拿它当业务依据。

offsetParent 的四条规则

offsetTop 的坐标系完全取决于 offsetParent，而 offsetParent 本身有四条容易翻车的规则，我们逐条过：

flowchart TD
    A[取某个元素的 offsetParent] --> B{自身 display 为 none 或 body 或 fixed?}
    B -- 是 --> C[返回 null 且四件套全为 0]
    B -- 否 --> D{最近的定位祖先 position 不为 static?}
    D -- 有 --> E[返回该定位祖先]
    D -- 没有 --> F{祖先里有 table / td / th?}
    F -- 有 --> G[部分浏览器返回该表格元素]
    F -- 没有 --> H[返回 body 或 html]
  1. 最近的定位祖先是锚点。 只要某祖先的 position 是 relative、absolute 或 fixed，它就是这一列元素的 offsetParent；一个都找不到时落到 body（个别浏览器是 html，所以要判空）。
  2. 表格元素会截胡。 按 HTML 规范，即使没有定位，td、th、table 也可以作为 offsetParent。IE 和部分老浏览器确实这么实现。上面那个菜单偏位 bug 的第三处错就在这里——按钮在单元格里，累加 offsetTop 时以为能一路加到 body，实际上链条在 td 就断了。
  3. display:none 时全家都是 0。 元素自身和它的所有后代，offsetWidth、offsetHeight、offsetTop、offsetLeft 全为 0，offsetParent 为 null。想测量隐藏元素的尺寸，要么临时给它挂 visibility:hidden; position:absolute; left:-9999px，要么像 jQuery 那样先 display:block 再量完还原。visibility:hidden 的元素则是另一路：offsetWidth 有值，offsetTop 也有值，因为它还占着布局。
  4. position:fixed 的元素在多数浏览器里 offsetParent 是 null，IE6/7 干脆不支持 fixed。别指望沿 fixed 元素的 offset 链累加出什么稳定结果，给 fixed 元素算坐标请直接使用下一节的 getBoundingClientRect。

还有一条实践建议：与其手写”累加 offsetParent 链”，不如改用 getBoundingClientRect，或者只在 offsetParent 就是定位容器时局部使用 offset 值，避免跨坐标系运算。

box-sizing 与 quirks 模式的读数差异

笔者在 2013 年 7 月那篇《IE 盒模型与 W3C 标准盒模型的区别与切换》里给过结论：IE5 时代缺 doctype 触发 quirks 后才会退回 IE 盒模型，标准模式下各家浏览器都按 W3C 盒模型渲染。本文不重复推导，只把那个结论接到 offsetWidth 的读数上。

offsetWidth 反映的是布局结果，不是 CSS 声明值。在标准模式（content-box）下，width:200px 加 10px 内边距加 1px 边框，布局出来的外框是 222px，offsetWidth 就是 222。一旦元素或祖先被重置成 box-sizing:border-box（很多全局重置样式表真这么干），外框被压回 200px，offsetWidth 也随之变成 200。而在 quirks 模式的旧 IE 里，所有盒模型都是 IE 那套，offsetWidth 恒等于声明的 width。也就是说：

对照 jQuery 1.9 的行为：$(el).width() 取的是内容区宽度（内部用计算样式），$(el).outerWidth() 才约等于 offsetWidth，$(el).outerWidth(true) 再加 margin。自己手写代码时如果想对齐 jQuery 的语义，用 getComputedStyle 拿声明值、把 offsetWidth 只当”外壳尺寸”用，两条路不要交叉。另外注意旧版 Firefox 在盒模型判定上也有自己的脾气，跨浏览器组件最好在 quirks 与标准两种 doctype 下各测一遍——我们那个模板后来补了 <!DOCTYPE html>，IE8 的菜单误差立刻少了 20 多像素。

视口尺寸与滚动位置的兼容取值

视口、文档、屏幕是三个尺寸概念，2014 年的支持矩阵如下（对勾表示可用，叉号表示拿不到值）：

取值途径 IE6-8 IE9 Firefox Chrome Safari
window.innerWidth / innerHeight 叉 对 对 对 对
documentElement.clientWidth 对（标准模式） 对 对 对 对
body.clientWidth（quirks 宿主） 对（quirks） 对 对 对 对
window.pageYOffset 叉 叉 对 新版对 对
screen.width / availWidth 对 对 对 对 对

两个怪癖必须记住。其一，window.innerWidth 含滚动条、且是浮点数（受页面缩放影响），documentElement.clientWidth 不含滚动条，两者永远差着一个滚动条的宽度。其二，滚动位置的宿主互斥：标准模式下 IE9+/Firefox/新版 Chrome 把页面滚动量挂在 documentElement.scrollTop 上；quirks 模式的旧 IE 挂在 body.scrollTop；而在更早的 Chrome 里 documentElement.scrollTop 恒为 0，只认 body.scrollTop。你在错误的那个宿主上读，永远读到 0，这就是”明明滚了页面上拉加载却不触发”的经典成因。当年通行的兼容取值函数是这样的，ES5，随取随用：

screen.width 与 window.screen.availWidth 描述的是显示器本身，跟页面布局无关，只在”判断用户设备大概是什么分辨率”这种粗粒度场景用；iPhone 4 之后有了 devicePixelRatio，逻辑像素与物理像素再也不能直接对等，这是另一个话题了。

getBoundingClientRect：相对视口的那把尺

getBoundingClientRect 在 IE9 起行为符合规范（IE 更早版本有私有实现，但只给 top/left/right/bottom，缺宽高，别指望它），Firefox、Chrome、Safari 全线可用。它返回元素相对视口的八个值，与 offset 家族相对文档、相对 offsetParent 的坐标系截然不同，差异集中在这几点：

  • 它是浮点数。页面缩放、高分屏、带 transform 的元素，读出来都可能带小数，用之前先 Math.round 或干脆别比较整数值。
  • 它包含 transform 之后的实际渲染位置。旋转、位移、缩放后的元素，offsetTop 给你的是变换前的布局坐标，rect 给你的是用户眼里真正看到的那块区域。
  • 它跟 offsetParent 链完全无关，不用关心定位祖先、表格截胡、body 外边距这些破事，一个调用直达视口坐标系。

jQuery 1.4 之后 .offset() 的源码走的就是这条路——rect 加滚动量加 clientTop 补偿，这也是它比手写 offset 链准的原因。在滚动容器里做吸顶判定或者弹层跟随更见它的价值：元素在容器内被卷走多少，rect.top 直接就是可见位置，不像 offset 系要逐层把容器的 scrollTop 加回来。

踩坑清单

把散在各节的问题钉成一张排查清单，下次哪个页面不对劲，按单核对：

  • 滚动条宽度算在哪： offsetWidth 含滚动条占位，clientWidth 不含；Windows 经典滚动条约 17px，Mac 上滚动条悬浮不占位，同一页面两端读数天然不同，别拿 Mac 调出来的 17px 去修 Windows 的 bug。
  • clientTop/clientLeft 不是 0： 它是 border 宽加滚动条宽，把 rect 坐标换算回文档系时漏了它，就会差出一个边框。
  • 给不可滚动元素写 scrollTop： 规范要求这个操作沿祖先链找最近的可滚动祖先执行下去，2014 年的浏览器基本都照办——你的”设置无效”其实是”滚了别人”。
  • 负值 scrollTop： 带弹性回弹的触控设备上，过滚动瞬间可能读到负数，阈值判断要用 <= 容差而不是等号。
  • display:none 四件套全 0： 隐藏时测量必为空，先临时显示或用占位写法，再量再还原。
  • 字体加载后重算： 中文页面挂了 Web 字体时，文字宽高在字体就位前后会变，浮层定位与等高布局要监听加载完成再算一遍；当年没有标准事件，常规做法是用一个挂了字体的隐藏 span 轮询 offsetWidth，变化即视为就绪。
  • offsetTop 基准是 padding box： 带边框、有滚动条的定位祖先都会让”目测值”与读出值差一个 clientTop，表格里的元素先确认 offsetParent 有没有被 td 截胡。

小结

offset 系量”外壳”，client 系量”可视区”，scroll 系量”卷走了多少”，三组口径的边界就是 border 与滚动条的去向，一张汇总表能省两天排查。定位链累加不如 getBoundingClientRect 一步到位，换算文档坐标时记得补滚动量与 clientTop。页面滚动位置的宿主在 documentElement 与 body 之间互斥，取值函数必须多路探测；quirks 模式的 doctype 会同时改变盒模型语义和这几个属性的宿主。写定位与滚动代码时先问三件事：参照系是谁、滚动条算哪边、doctype 什么模式——2014 年的浏览器江湖，答案还是得自己给。
