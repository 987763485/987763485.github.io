jQuery 的 on、off 与事件委托

年前接手一个老项目，事件层还混着 bind、live、delegate 三代写法，升级 jQuery 到 1.9 之后 live 直接报错，只好把全量事件代码翻出来重了一遍。这个过程让我把 jQuery 事件 API 的演进脉络重新梳理了一遍：on / off 不是凭空多出来的两个方法，而是把过去三套入口合并成一套。本文从演进历史、签名设计、委托边界、命名空间、事件对象包装、性能实测几个角度做一次完整的选型梳理，适合还在维护老代码、写公共组件或插件的读者。至于事件移除与内存泄漏的原理，笔者在《DOM 事件移除与内存泄漏》里已经写过，本文不再重复，只在必要处一句话带过。

三代 API：从 bind、live、delegate 到 on、off

jQuery 事件绑定的演进大致分三步。1.3（2009 年初）加入 live 和 die，思路是把处理器统一挂到 document 上，靠冒泡匹配选择器，解决”动态插入的节点绑不上事件”的老问题；1.4.2 加入 delegate / undelegate，把同样的匹配逻辑从 document 下移到指定容器；到 1.7（2011 年底），on / off 出现，bind、live、delegate 全部改成内部转发到 on 的薄包装；1.9（2013 年初）则干脆删掉了 live 及其背后的整套特殊事件机制。

live 被删不是历史包袱不清，而是这套设计有先天缺陷：

  • 所有处理器都挂在 document，任何一个点击都要一路冒泡到根才被处理，链路上任何人调用了 stopPropagation，live 处理器就收不到；反过来，页面滚动区域深层的点击也会被迫走完整条冒泡链。
  • 无法绑定最近的稳定容器，匹配范围失控，同页挂了几十个 live 处理器时，每次事件都要对全部选择器做一遍匹配。
  • focus、blur、submit、change 这类不冒泡或部分浏览器不冒泡的事件，要靠 jQuery 内部 hack 才能”模拟”委托，实现复杂且坑多。
  • 移除只能按 live 自己的粒度来，die() 一不小心就把别的模块的事件一起带走。

jQuery 团队在 1.9 的升级笔记里说得很直白：事件模块瘦身的最大受益者就是删掉 live。1.7 之后 live 本来就是 on 绑定到 document 的特例，留着只多一份实现要维护。

三代写法与 on / off 的迁移对照如下，这也是当年升级时笔者手边贴着的一张表：

旧写法（1.3 - 1.8） on / off 等价写法 语义
$el.bind('click', fn) $el.on('click', fn) 直接绑定，不委托
$el.bind('click', data, fn) $el.on('click', data, fn) 直接绑定并传递 event.data
$el.one('click', fn) $el.one('click', fn) 触发一次后自动移除
$parent.delegate('li', 'click', fn) $parent.on('click', 'li', fn) 在父容器上委托
$('li').live('click', fn) $(document).on('click', 'li', fn) document 级委托，建议换成更近的稳定容器
$('li').live('click', data, fn) $(document).on('click', 'li', data, fn) 委托加 data
$el.unbind('click', fn) $el.off('click', fn) 移除
$parent.undelegate('li', 'click') $parent.off('click', 'li') 按选择器移除委托
$('li').die('click') $(document).off('click', 'li') 移除 document 级委托

注意表中第五行：机械地把 live 翻译到 document 上只是”能跑”，正确做法是把容器换成最近的稳定祖先，这正是 live 做不到、on 才给你的自由度。

on 的统一签名：合并而不是新增

on 的完整签名是 on(events, [selector], [data], handler)，selector 与 data 都可省略。位置参数可以省略，靠的是 jQuery 内部的参数嗅探：若第二个参数不是字符串，它就被当成 data；若第三个也不是函数，则再往后顺。理解这一点之后，四种常见组合其实只对应两件事——绑不绑委托（有没有 selector）、传不传数据（有没有 data）：

为什么说它是”合并”而不是”新增”？因为 1.7 之后你翻 jQuery 源码会发现，bind、delegate、live 的方法体里都只剩一行转发：return this.on(...) 加上参数换位。绑定入口、handle 调度器、特殊事件处理这套核心机制整个仓库只有一份，on 只是把过去散落在三个方法名上的参数形状收敛到一个签名里。所以”on 比 bind 更高级”是误解——直接绑定时两者走的是同一条内部路径，区别只在 API 的统一性与后来的去留。理解了这一点，选型问题就只剩下一个问题：要不要给第二个参数 selector。

事件委托的正确姿势与边界

委托的匹配规则是：事件从 event.target 出发，沿祖先链向上走到绑定了 selector 的那个元素（delegateTarget）为止，沿途第一个匹配 selector 的元素即处理器里的 this。也就是说 selector 匹配的是”路径上最近的祖先”，而不是你的业务对象——点击 li 里的 span，this 仍是那个 li，e.target 才是 span。

sequenceDiagram
    participant T as 触发节点
    participant C as 委托容器
    participant Q as jQuery 分发
    participant H as 业务回调
    T->>C: 事件沿 DOM 树向上冒泡
    C->>Q: 容器上的原生监听器接管
    Q->>Q: 从 target 沿祖先链匹配 selector
    Q->>H: 命中则调用 this 指向命中元素

几个必须记住的边界：

hover 与 mouseenter / mouseleave。 这对事件本身不冒泡（它们是 IE 私有事件转正的非标准货），原生层面无法委托。jQuery 用绑定在容器上的 mouseover / mouseout 加 relatedTarget 判断模拟出委托效果，所以 $('#list').on('mouseenter', 'li', fn) 能正常工作；但 hover() 方法本身不接受 selector 参数，要委托只能拆成两个 on 写。另外这份模拟意味着容器内每次鼠标跨越元素边界都会触发一次匹配，高频页面上开销不小，别对 li 数量上千的列表随手加委托版 hover。

focus / blur 不冒泡。 委托场景要改写成 focusin / focusout，它们冒泡且 jQuery 的 selector 匹配照常工作：$('#form').on('focusin', 'input', onFocus)。老版 IE 不认识 focusin，jQuery 1.4.3 起通过内部机制补齐，1.9 之后新浏览器全部原生支持，2014 年的今天可以放心用。

change / submit 的委托坑。 这两个表单事件的冒泡行为在老浏览器里一团糟：IE 8 及以下的 change 不冒泡，jQuery 靠给每个匹配元素补绑来兜底，代价是动态插入的元素要用键盘改值时，委托的 change 要等焦点离开该元素才触发；submit 历史上在多数浏览器根本不冒泡，靠委托去捕获提交极不可靠。笔者的实践结论很干脆：change 和 submit 永远直接绑在表单或具体控件上，不要委托。

委托容器要稳定且尽量近。 绑到 document 等于重回 live 的老路；绑到业务模块自己的根节点，既少冒泡一段路，销毁时清理范围也清晰。

命名空间、one 与两个常见误解

on 的事件名支持 .ns 后缀，off('.myapp') 可以不区分事件类型，把该节点上所有带 .myapp 命名空间的处理器一次摘除；多级命名空间 click.dialog.ok 按包含关系匹配，off('.dialog') 能摘掉它。命名空间只服务于管理，不影响事件本身的匹配与触发。

写插件和公共组件时命名空间不是可选项而是义务。理由笔者在上一篇文章里论证过：模块销毁时必须精确清理自己的事件，又绝不能误伤同节点上别人的处理器，不泄漏的前提是”绑定与移除成对且边界清晰”。一个合格的 jQuery 插件应该有对称的两段：

第一个常见误解与 one 有关：one 是”触发一次后自动摘除”，不是”只允许存在一次”，它本质是 on 加一个执行完就 off 自己的包装，没触发过的那个处理器一直挂在事件表里。所以一次性引导逻辑如果中途模块被销毁，仍要按命名空间补一刀 off('.guide')，否则闭包链还在。

第二个误解是把 on 的返回值当处理器引用。有人写：

on 返回的是 jQuery 集合（为了链式调用），不是那个匿名函数。off(type, handler) 的移除靠的是函数引用相等（内部还会比对 guid 编号），匿名函数没有引用可传，自然摘不掉。想精确移除就自己把函数存进变量，或者用命名空间整体摘——没有第三种选择。同样地，带 selector 的委托绑定，off 时三个参数要对齐，off('click', 'li') 传不回正确的选择器就白摘，这些在迁移老代码时最容易漏。

jQuery 包装后的事件对象

进入处理器的 event 不是原生对象，而是 jQuery.Event 的实例。原生对象挂在其 originalEvent 属性上，未被 jQuery 认识的属性也可以透过它访问。jQuery 在构造时做了一件重要的事：抹平浏览器差异并补齐派生字段。

常被使用的属性有这么一批：type、target（IE 老模型的 srcElement 被归一化）、currentTarget、relatedTarget（IE 的 fromElement / toElement 被归一化，mouseover / focusout 场景很好用）、which（把 keyCode、charCode、鼠标按键三套体系归一成一个数）、metaKey、timeStamp，以及派生出来的 pageX / pageY——IE 原生不提供 page 坐标，jQuery 用 clientX 加滚动量补出来。委托场景还有两个专属字段：delegateTarget 指向绑定该处理器的容器元素，namespace 记录命名空间串，data 则是绑定时传入的附加数据。

方法侧，preventDefault、stopPropagation、stopImmediatePropagation 被包了一层，同时提供查询用的 isDefaultPrevented()、isPropagationStopped()，这在委托链路里判断”下游有没有人处理过”比原生标志位方便。手工派发可以用 $.Event('myapp.open', { detail: 1 }) 造事件对象再 trigger，自定义事件天然支持冒泡与命名空间，这也是 jQuery 事件系统比原生”多出来”实用的一块。要注意的是 stopImmediatePropagation 是 jQuery 帮你实现的：它在自己的 handle 调度循环里按绑定顺序逐个调用并检查标志，原生 IE 8 并没有这个 API——换句话说，同元素同类型多个处理器的执行顺序，jQuery 保证了”绑定序”，这在依赖处理器先后关系的旧代码里既是被依赖的特性，也是迁移时要留意的点。

性能实测：一千个处理器 vs 一个委托

拿一个典型场景做实验：一个 1000 行的任务列表，每行有一个删除按钮。用 jQuery 1.10.2，在 Chrome 31 与保留 IE 8 的虚拟机上各测一轮，绑定与解绑取 10 次平均。

实测数量级大致如下（笔者机器，仅作量级参考）：

指标 逐个绑定 1000 个 委托 1 个
绑定耗时（Chrome 31） 约 90 - 130 ms 约 1 - 3 ms
绑定耗时（IE 8） 约 300 - 500 ms 约 5 - 10 ms
解绑耗时（off 命名空间） 约 60 - 90 ms 不足 1 ms
列表重渲染后 必须重新全量绑定 零成本
单次点击分发 直接命中 冒泡到容器加一次选择器匹配，约 0.1 - 0.3 ms

为什么差距这么大，得看 jQuery 内部记的账。1.9 之后事件统一存进 jQuery.cache，每个挂过事件的元素有一个内部 id，$._data(el, 'events') 里是一条 type 到 handleObj 数组的表。逐个绑定 1000 次，就是 1000 个元素进缓存、1000 份 handle 闭包、1000 个原生监听器；委托只给容器记一条带 selector 的 handleObj，原生监听器只有一个，堆快照里两者相差可达 MB 量级（泄漏原理本文不展开）。而委托的代价发生在分发时：jQuery.event.handlers 收到事件后，要从 target 沿 DOM 树向上走到容器，沿途对 selector 做匹配，路径越深、同容器上委托的选择器越多，每个事件的固定开销越大。所以委托不是无脑更优——点击每天几千次无所谓，但对 mousemove、mouseover 这类高频事件在大列表上做委托，就是自己给自己制造每帧微卡。

结论一句话：绑定的量级成本在”个数”，委托的摊薄成本在”每次触发匹配”。节点多、触发少选委托；节点少、触发多选直绑。

选型与迁移

什么时候干脆不用 jQuery

如果一个页面的交互只有零星几处事件，或者你在写一个不想拖 jQuery 依赖的组件，原生 addEventListener 加十几行手写委托完全够。2014 年的现实约束是 IE 8 还要伺候（没有标准事件 API，只有 attachEvent），以及 Element.prototype.closest 还没进入主流浏览器的支持列表，所以匹配要自己沿祖先链走。一个 ES5 的最小可用实现：

这个版本没有事件对象归一化、没有命名空间、没有特殊事件补齐，要自己维护移除句柄就得再多一层注册表。如果你的页面本来就靠 jQuery 做 AJAX 和 DOM 操作，手写这套的边际收益很低；反过来，为几个事件引 90 KB 的 jQuery 才是选型失误。边界画在这里：jQuery 已进场就用 on，没进场且只支持新浏览器就用上面二十行，需要兼容老 IE 又没有 jQuery 的项目——2014 年还不少，老老实实把 jQuery 装上更划算。

移动端的 Zepto

Zepto 1.1.x 是移动端常见的轻量替代，它的 on / off / one 委托签名与 jQuery 有意保持一致，迁移心智成本很低。差异在实现策略上：Zepto 没有老 IE 兼容层，focusin / focusout 直接依赖原生支持，change / submit 的委托也不做 jQuery 那套补绑兜底，所以前文那条”表单事件别委托”的纪律在 Zepto 下同样成立甚至更严。此外 trigger 自定义事件默认不冒泡，要显式传 { bubbles: true }；tap、swipe 等触摸扩展是独立模块，按需加载。内存层面 Zepto 同样用元素缓存，绑定策略的取舍与本文结论一致。

从 live 迁移的 checklist

最后给一份笔者踩过坑之后整理的迁移清单，适用于把 live / die 老代码收敛到 on / off：

  1. 全局搜索 live(、die(、delegate(、undelegate(，列出清单再动手，别散弹式改。
  2. 每条 live 翻译时先找最近的稳定容器，找不到再退到 document，并在代码注释里标注原因。
  3. die() 无参调用是危险信号（历史上它清过别人的事件），迁移时一律换成带命名空间的 off('.mod')，绑定处同步补上命名空间。
  4. focus / blur 委托改 focusin / focusout；change / submit 拆出来直绑。
  5. 检查同一 selector 是否既在容器又在 document 绑过——委托后每层各自命中一次，会出现双触发，这是迁移后最常见的回归 bug。
  6. 依赖冒泡顺序、中途有 stopPropagation 的链路要重新走查：容器变近之后，原来先执行的处理器可能换到后执行。
  7. 回归测试至少覆盖：动态插入的节点触发一次、删除后不残留（$._data(container, 'events') 检查）、IE 8 下键盘改 change 的时机、弹窗反复开关的内存对比。
  8. 用 bind / unbind 的旧代码 2014 年仍可运行，但新代码不要再写，on / off 是唯一的推荐入口。

小结

on 的价值不在功能更多，而在把三代 API 收敛成一套心智模型：一条签名区分直绑与委托，一个命名空间解决批量摘除，一份事件表统一记账。选型上记住四条纪律——委托容器选最近的稳定祖先、不冒泡的事件换专用事件名、表单事件永远直绑、高频触发的事件慎用委托。老项目迁移按 checklist 走，改完用事件表和堆快照验证。jQuery 事件系统从 1.3 到 1.9 走了五年才把这条路铺平，我们没理由再把代码写回旧入口。
