JavaScript 对象属性描述符与特性

前阵子读 ES5 shim 库的源码，发现里面有大量 Object.defineProperty 调用，而且几乎每次都要把 enumerable: false、configurable: true 写全，起初觉得啰嗦，后来才明白这不是风格问题，而是这个 API 的默认值会咬人。属性描述符（Property Descriptor）是 ES5 引入的一套机制，它把引擎内部才可见的属性特性第一次暴露给了 JavaScript 代码。本文不打算逐个罗列 API 签名，而是从机制和设计意图出发，讲清楚这套东西为什么长成这样、默认值坑在哪、几条硬性约束背后的道理，以及它在 seal、freeze 这些上层封装里扮演的角色。适合写过插件、做过 polyfill、或者被”属性明明在却读不到”折磨过的读者。

为什么 ES5 要把属性拆成描述符

在 ES3 时代，一个属性在语言层面只有”名字和值”，赋值即创建，读取即访问，所有属性对脚本而言一视同仁。但引擎内部并不是这么实现的——规范草案里早有 [[Value]]、[[ReadOnly]]、[[DontEnum]]、[[DontDelete]] 这类内部槽（internal slots），只是脚本碰不到它们。于是内置属性和普通属性行为不同（比如你删不掉 Function.prototype 上的东西），却没有任何 API 能让你声明”我的这个属性也是这种性质”。

这对库作者是件很痛苦的事。假设你写一个插件，需要在传入的对象上挂一个内部缓存。你区分不了”内部状态”和”用户数据”：用户用 for in 遍历自己的配置项时，会把你挂的缓存键一并枚举出来；用户调用 JSON.stringify 时，你的缓存可能被序列化进去，一旦形成循环引用还会直接抛错。jQuery 1.x 时代的做法是绕开这个语言缺陷：不在元素上直接存数据，而是生成一个带随机数的 expando 字符串（形如 jQuery 加版本号再加 Math.random()），把真实数据放进全局的 cache 表里。名字取得再怪，本质上只是命名约定，约定管不住遍历。

ES5 的思路是：既然引擎内部本来就有这些特性，不如把它们提升为语言的一等公民。每个自有属性背后对应一个属性描述符对象，脚本可以读它、也可以写它。设计意图从”属性是个黑盒”变成”属性的行为本身也是可编程的”，上面那些问题才有了解决的语言级工具。

两种描述符与四个 API 的分工

描述符分两个变体（variant），一个属性只能属于其中一种：

flowchart TD
    D[属性描述符] --> A[数据描述符]
    D --> B[访问器描述符]
    A --> A1[value 与 writable]
    B --> B1[get 与 set]
    D --> C[公共字段: enumerable 与 configurable]

数据描述符描述”值存储”，字段是 value 和 writable；访问器描述符描述”存取函数”，字段是 get 和 set。两种变体都带 enumerable（是否参与枚举）和 configurable（描述符自身是否可再改）两个公共字段。ES5.1 规范（2011 年定稿）里校验逻辑就是按这两个变体分支写的，value/writable 与 get/set 互斥，混用直接抛 TypeError。

默认值陷阱：defineProperty 不是赋值

这是新手最容易踩的坑，也是我在 shim 源码里看到那些”啰嗦”写法的根源。字面量赋值创建属性时，四个特性全部默认为 true；而 defineProperty 对没写出来的字段一律取 false 或 undefined，哪怕这个属性已经存在，它也会把你没提到的字段改掉：

一次”只改值”的操作，把属性变成不可写、不可枚举、不可配置。更要命的是，在非严格模式下这一切都静默发生，错误会延迟到很远的地方才爆出来。正确做法要么是创建新属性时只写需要的字段（此时其余字段取默认值，符合预期），要么修改已有属性时先用 getOwnPropertyDescriptor 把原描述符读出来、改完再整体写回去。

几条硬性约束

除了上面 value/writable 与 get/set 互斥之外，还有两条约束值得单独说。

第一条是 configurable: false 是一扇单向门。规范这么设计是有原因的：只有当属性从此不可撤销地定型，引擎才能放心地把它内联优化、让引用它的代码跳过校验。代价是你自己再也退不回去。一旦 configurable 为 false：属性不能 delete；不能再转成另一种变体（数据改访问器）；enumerable 和 configurable 本身不能再改；writable 只允许从 true 改成 false 这一次，反向永远不行：

第二条是访问器与原型链组合出的”赋值静默失败”。给对象属性赋值时，引擎如果发现原型链上某个位置有一个 set 为 undefined 的访问器属性，这次赋值直接无效——注意，此时并不会在实例上创建遮蔽属性（数据属性才会被遮蔽），因为在设计者眼里，”原型声明了这个属性只能读”是一个明确的意图，赋值不该绕过它。这在当年做浏览器兼容时很常见，比如某些宿主对象上的只读属性：

enumerable 的真实影响面

enumerable 控制的是”可发现性”，不是”可访问性”——不可枚举的属性照样能正常读写，只是不会出现在三个地方：for in（含原型链）、Object.keys、JSON.stringify。Object.getOwnPropertyNames 则不受它约束，照样能拿到。

seal、freeze、preventExtensions 只是批量改描述符

这三个方法常被当成神秘的”对象保护等级”，但翻开任何一份 polyfill 源码都会看到，它们的实现全部是对描述符的批量操作，没有引入新的内部状态：

  • Object.preventExtensions：不碰任何描述符，只把对象的扩展开关关掉，之后不能加新属性；
  • Object.seal：先 preventExtensions，再把所有自有属性的 configurable 置为 false——属性删不掉、变不了身，但 writable 为 true 的数据属性值仍然可改；
  • Object.freeze：在 seal 的基础上，再把所有数据属性的 writable 置 false、所有访问器的 set 置 undefined。

工程实践：打补丁、严格模式与调试

写 shim 的第一步是特性检测，而且要检测行为而不是检测存在。IE8 的 Object.defineProperty 只能作用于 DOM 对象，对普通对象调用会抛错，所以只判断 typeof Object.defineProperty === 'function' 是不够的：

给宿主对象或第三方对象打补丁前，先 getOwnPropertyDescriptor 看一眼目标键的现状。如果你用赋值方式覆盖一个访问器属性，会把原生行为整个吃掉；反过来，如果现状是 configurable: false，你的 defineProperty 会抛 TypeError。先读后写，是目前 IE9+ 及 Chrome、Firefox 混跑环境里最稳的补丁流程。

严格模式对描述符相关操作的影响要记牢：非严格模式下，给不可写属性赋值、给不可扩展对象加属性、delete 一个 configurable: false 的属性，全部静默失败；严格模式下三者都抛 TypeError。行为差异只在”报错时机”，约束本身两个模式完全一样，别指望严格模式能解锁什么。

小结

属性描述符是 ES5 把引擎内部槽提升为语言能力的典型设计：数据描述符与访问器描述符二选一，四个 API 各管读写与枚举的一个切面。用 defineProperty 修改已有属性时，未写出的字段会被重置为 false 或 undefined，这是默认值陷阱的根源。configurable: false 是不可撤销的单向门，原型链上的只读访问器会让赋值静默失败，enumerable 则决定了内部状态会不会混进 for in、Object.keys 和 JSON.stringify。seal、freeze、preventExtensions 本质都是批量降级描述符。写库和打补丁时养成”先 getOwnPropertyDescriptor 读现状、再整体写回”的习惯，并用特性检测而非存在检测来做兼容，能避开这一机制九成以上的坑。
