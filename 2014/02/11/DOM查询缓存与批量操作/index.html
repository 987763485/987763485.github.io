DOM 查询缓存与批量操作

前面两篇聊过 DocumentFragment 的 API 和减少重排重绘的规则清单，这一篇只谈性能与调优层面笔者最近真正花时间琢磨的部分：查询结果怎么缓存、读写怎么分离、批量写入按什么场景选型。主线案例是管理后台那张确实很慢的千行订单表格，把测量数据、踩过的坑和改法都写全。适合维护列表类页面的前端同学。

一次卡顿的开始：千行表格

管理后台的订单列表是纯前端渲染的表格：1000 行、8 列，搜索框在前端按关键字过滤行。开发机上 Chrome 31 每敲一个字符只花几十毫秒，我以为没事。换到一台旧办公本、IE 8 里，每敲一个字符页面卡死半秒以上；首屏灌 5000 行时总耗时超过 2 秒，IE 8 直接弹出”此页面上的脚本造成 Web 浏览器运行速度减慢，是否停止”的对话框。

最初我认定是”渲染慢”，换了两种模板写法，几乎没改善。后来在搜索回调的头尾各埋一个 new Date()，再把循环拆成几段分别计时，结果很清醒：单次按键约 1.2 秒的耗时里，字符串比较这种纯 JS 计算只占 30 毫秒上下；剩下的钱，一处花在循环里反复执行的选择器查询（一千多次），另一处花在写入循环里读 offsetHeight，逼着浏览器重算了上千轮布局。真正的主因是”重复查询 + 读写交错”，而不是浏览器画像素这件事本身。

两轮优化下来，IE 8 上的总体账目大致是：

测量项 优化前 优化后
搜索每按键一次（1000 行） 约 1200 毫秒 约 210 毫秒
首屏渲染 5000 行 约 2400 毫秒，弹停止脚本对话框 约 1600 毫秒，全程不冻结

下面按环节拆开讲每一刀怎么改、各自贡献了多少。

查询缓存的三层做法

最便宜的查询是不做的查询。循环里不变的查询要提到循环外，这条原则早就是常识，这里说笔者项目里实际用的三层做法。

**第一层：局部变量缓存引用。**一次需求里同一批节点往往被多处代码碰，每碰一次就重新查一遍。jQuery 的每一次 $() 都要走一遍选择器解析加 Sizzle 匹配，一千行的页面里这样浪费几十次就是几十毫秒起步。

各种查询方式的成本有阶梯，粗测的数量级大致如下（1000 行规模、IE 8、每次调用取十次平均）：

查询方式 单次大约耗时 说明
getElementById 约 0.01 毫秒 浏览器内置哈希，最便宜
querySelectorAll 简单类选择器 约 0.2 毫秒 IE 8 支持但只认 CSS 2.1 语法，实现也慢
jQuery 属性选择器 [data-id=...] 约 1.5 毫秒 Sizzle 要扫候选集逐个匹配

数字不必较真，结论只有一条：离”原生 id 查找”越远，查询越贵，越值得缓存。

**第二层：手动索引，字典映射。**我们的需求是”给定订单 id，找到对应那一行”。属性选择器版本每次查询都要全表扫一遍，是 O(n)；笔者改成普通对象做 id 到元素的索引，建索引一次 O(n)，之后每次查询 O(1)：

代价是索引会失效，规则要自己定：批量增删之后整体重建一次，单条增删就同步维护一个键。配合后面要讲的静态快照使用，效果最好。

第三层：在节点上挂引用，以及 IE 的内存坑。data-* 属性只能存字符串，适合存 id、再配合第二层的索引回查。直接在 DOM 节点上挂 JS 对象（所谓 expando 属性）在 IE 8 及以下是经典内存泄漏：DOM 节点指向 JS 对象，JS 对象里的闭包又指回节点，形成循环引用，IE 的 GC 对这一对处理不干净，反复增删列表的页面内存会一路涨。

这也是 $.data() 比手写 el.myProp = obj 安全的原因。Zepto 1.x 同样是”数据集中挂、删除时统一清理”的思路，不过它只打现代移动浏览器，循环引用泄漏在它的设计里不是问题。

活集合与静态快照：漏删和死循环

getElementsBy* 返回的是 HTMLCollection，一个”活”的查询代理：每次读写它都在反映文档的实时状态。querySelectorAll 返回的 NodeList 是查询瞬间的快照，之后文档怎么变它都不动。上一篇讲过用活集合边遍历边删会漏掉一半元素，本文这边踩到的是更干脆的变体：死循环。

性能上还有一笔账：活集合不缓存结果，每次按下标取值，一些引擎都要从集合起点重新数一遍，单次下标访问接近 O(n)，整个循环就是 O(n²)。笔者用 1000 个节点对比过完整遍历一遍活集合和静态数组，IE 8 上前者比后者慢了近一个数量级。所以规则固化成两条：循环体里会动文档的，先拿快照；循环较长的，把快照再手工拷成普通数组（IE 8 下 HTMLCollection 不能直接 Array.prototype.slice，只能逐项 push）并缓存 length。

版本 IE 8 Chrome 31
交错读写 约 980 毫秒 约 160 毫秒
分离读写 + 行高常量化 约 230 毫秒 约 40 毫秒

策略上归结为三点：测量能集中就集中成一段；能由数据推算的值（行高固定时总高就是行数乘行高）干脆不要读布局；两头都占不了的算法——比如必须知道上一行改完的高度才能决定下一行——要么接受多次布局，要么先在写入前把所有要读的批量读进数组，再开始写。

批量重写的三种写法怎么选

首屏和”清空重新加载”这类整块重写，可选路子就三条。粗测的绝对值与上一篇基本对得上（量级参考，环境不同请自己量）：

写法 IE 8 渲染 1000 行 Chrome 31
innerHTML 整块重写 约 110 毫秒 约 25 毫秒
createElement + DocumentFragment 约 150 毫秒 约 30 毫秒
cloneNode 模板 + DocumentFragment 约 120 毫秒 约 22 毫秒

  • 数据来自接口就必须转义，否则一个带 HTML 的备注字段就是一次现成的 XSS：
  • cloneNode 的坑在事件：原生 cloneNode(true) 按规范不复制 JS 绑定事件，但 IE 8 会把 attachEvent 挂上的处理器一起克隆，导致同一个处理函数绑了两份。模板行上干脆不绑事件，配合后文的事件委托即可。另外深拷贝会把模板里的 id 一起复制，造成文档里重复 id，所以模板只用 class。

还有一个不算坑但必须考虑的差异：innerHTML 整块重写意味着旧节点全销毁，滚动位置和焦点都丢了。用户在一千行里滚到半途，一过滤表格跳回顶部，体验比慢 100 毫秒更糟。所以我们的最终分工是：过滤用”显隐切换 + 读写分离”（节点原地不动），首屏和重新加载才整块重写。

flowchart TD
    A[需要批量写入] --> B{节点要绑事件或逐行操作吗}
    B -->|否| C[innerHTML 整块重写 注意转义]
    B -->|是| D{行结构统一吗}
    D -->|是| E[cloneNode 模板 + Fragment]
    D -->|否| F[createElement + Fragment]
    C --> G{用户正在滚动或输入?}
    G -->|是| H[改用显隐切换]
    G -->|否| I[完成]

长任务切帧：setTimeout 与 requestAnimationFrame

切帧解决的是另一类问题：总耗时降不动了，但主线程被一口气占住，页面点不动、弹”脚本运行缓慢”。5000 行首屏在 IE 8 上无论怎么优化都要一秒多，笔者的做法是分片，每批插一小段就把执行权交还给浏览器：

rAF 比 setTimeout 好在两处：回调贴着浏览器的绘制节奏走，不会出现一批插完还没画又插一批的白工；后台标签页里会被暂停，省掉无谓的消耗。

每批插多少行不该拍脑袋，可以按帧预算算：60 帧一秒，一帧约 16.7 毫秒，扣掉布局与绘制，给脚本的预算大约 8 毫秒。先粗测单行插入成本，再在每批内计时超限就提前收工，并用上一批的实际耗时反馈调整下一批的批量：

实测 5000 行：不分片时 IE 8 一次跑满约 2400 毫秒并触发脚本对话框；分片后总墙钟时间反而涨到约 1600 毫秒到 1800 毫秒（分片不减少总工作量，只改变节奏），但全程可滚动、可点击，对话框不再出现。Chrome 31 上不分片本来只要 90 毫秒左右，分片纯属多余——切帧是给慢引擎准备的，别为了”看起来专业”把快路径也切碎。

    B --> C[Fragment 内拼装 预算 8 毫秒]
    C --> D[一次插入 tbody]
    D --> E{全部插完}
    E -->|否| B
    E -->|是| F[结束]

事件委托收个尾，度量工具说一下

批量写法再多，事件绑定方式不对就全白搭：1000 行逐行绑定，首屏光绑定就要几十毫秒，innerHTML 重写一次还得全部重绑。挂到容器上做委托，监听器从 1000 个变 1 个，重写之后也不用重绑——事件是听着容器派的：

jQuery 1.9 和 Zepto 1.x 的 .on 都支持这种委托写法，底层帮你抹平了 addEventListener 与 attachEvent 的差别。再展开就是事件系统教程了，本文收住。

改的每一刀都要有数据背书，笔者用的工具组合：

  • Chrome 31 的 DevTools：Timeline 面板看每一帧里紫色 Layout 块的次数，读写分离做对了，一次过滤从上千个 Layout 缩成一两个；Profiles 面板的 CPU 抽样能直接看到 Sizzle 的调用条有多肥，那是查询没缓存干净的证据。
  • IE 9 及以上：F12 开发者工具自带分析器，能采样 JS 耗时，粒度不如 Chrome，定位到函数级够用。
  • IE 8：没有任何内置工具，只能用 new Date() 手工分段埋点，像本文开头那样把循环拆成几截分别计时，笨但诚实。
  • jsPerf 适合对比查询写法的微基准，但要注意：它的预热和循环会让 JIT 把代码优化到热态，测出来的是引擎满负荷的相对量级，不代表真实页面里冷启动的第一次执行；各测试用例之间的 DOM 残留也会互相污染。结论最后一定要回到页面内分段计时复核一遍。

小结

回头看，那张表格的卡顿里没有一行代码是”写错了”的，全部是”多做了”的：查询多做了一千遍，布局多算了一千轮。查询侧的纪律是三层——引用提到循环外、id 到元素建字典、数据挂节点走 jQuery 的 expando 加 cache 而不是自己挂对象；遍历侧的纪律是认清活集合与静态快照，会改动文档的循环一律先拿快照；写入侧的纪律是读写分段、批量写法按”是否需要逐行操作”选型，慢引擎上再按帧预算切片。所有数字请用你自己目标浏览器上的分段计时和 Timeline 说话，感觉不可靠，帧时间才可靠。
