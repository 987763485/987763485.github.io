HTTP 缓存机制与缓存策略

上一篇文章把强缓存与协商缓存的机制推导了一遍，留言里问得最多的却是另一些事：Nginx 到底怎么改、发布顺序怎样才安全、上线前拿什么验证。本文不再重复那些原理，只谈工程落地：给出笔者团队在 2013 年几次改版里沉淀下来的策略表、配置片段、发布流程与 checklist，以及三个付出过真实代价的事故复盘。适合正要给站点做缓存改造、或者被”改了不生效”折磨过的同学，配置片段基本可以直接抄走改域名用。

缓存策略总表：先分层，再谈参数

我们的做法是按资源类型定策略，先回答”这类响应允不允许被谁存、存多久”，再去写具体的头。下表是 2014 年初我们站点的现行配置：

资源类型 响应头组合 取舍理由
HTML 入口页 Cache-Control: no-cache，引用的静态资源全部上指纹 HTML 必须随时能换引用，多一次 304 往返比一次错版事故便宜得多
带指纹的 js/css expires 1y，public 文件名变了就是新 URL，旧文件永远没人再问，可以放心给满一年
图片与字体 带目录版本号的给一年；文件名固定的最多七天 运营改图频繁且不改名，给一年迟早出事
需要登录态的接口 Cache-Control: no-store 共享缓存存中一次数据就是一起事故，宁可没有缓存收益
公共字典类接口 public, max-age=600 类目树、行政区划这类数据，十分钟内旧值可接受

这张表背后的取舍，和 2014 年国内的链路条件是绑死的。我们 1 月的统计里无线访问已占三成，绝大部分还在联通 WCDMA 和电信 EVDO 上，实测 RTT 普遍在 300 ms 以上，地铁里能冲到 1 秒。在这种链路上，贵的不是字节而是往返：一个 304 省下了带宽，省不掉那一次完整的请求往返。所以目标分层很明确——第一优先用强缓存把请求消灭掉，第二优先只让 HTML 和少数必须协商的资源去吃 304，第三是不能容忍错版的地方宁可不缓存。反过来说，”带宽紧张所以给没版本号的资源也塞一年 max-age”是最危险的省钱思路，它只是把问题从发布日推迟到事故日。另外一句题外话：SPDY 我们今年在内网做了些试验，但当时离普及还远，本文所有结论都按 HTTP/1.1 的链路来谈。

FileETag MTime Size 这一行是被事故逼出来的：Apache 2.2 的 FileETag 默认是 All，里面含 INode。我们两台 web 机器用 rsync 同步文件，同一个文件在两边的 inode 不同，用户请求被负载到不同机器时，If-None-Match 带来的 ETag 几乎永远对不上，304 退化成完整 200，带宽账单肉眼可见地涨。当时我们查了一下午才把”换了台机器 ETag 就变”和负载轮询对上号。修复二选一：像上面那样把 ETag 收敛到 MTime 加 Size，或者干脆 Header unset ETag 禁掉它只留 Last-Modified——发布受控、内容不会悄悄变的站点，后者完全够用。Nginx 的 ETag 由大小与修改时间组成，默认不吃 inode，所以没这个问题，但从 Apache 迁过来的配置最好显式检查一遍 etag 指令。

顺序问题与「改了不生效」的三类成因

max-age 与 Last-Modified 同时给出时，浏览器的先后次序上一篇已经讲透，这里只补配置落地时观察到的两点。其一，新鲜期内浏览器根本不发请求，条件头也就不会出现，所以 Last-Modified 救不了一个过长的 max-age——新鲜期内它连跟你说话的机会都没有，服务器日志里自然是零记录。其二，IE8/IE9 的”自动”检查级别下有一套自己的节奏：我们 2013 年 11 月那次改版，HTML 明明下发了 no-cache，用一台按旧说明装的 IE8 虚拟机验证，上午开过页面之后中午从链接再进仍是旧版，按 F5 才拉到新的；对比同一台真机上的 Chrome，每次都会带条件请求。当时我们没有把 IE 的实现细节全部复现，只记下结论：给 HTML 定发布生效时间时，要把 IE 用户的”自动检查”窗口算进去，重要变更宁可写进运营公告也别指望用户自然刷新到。同理，IE 下 Ctrl+F5 会把整个临时 internet 文件区连别的站一起清掉，测试时请开新的用户配置档，别用强刷当验证手段。

“改了文件用户端不生效”的成因，我们踩下来全部落进这三类：

成因 典型场景 判定证据 修复手段
强缓存没过期 无指纹资源配了长 max-age access_log 里 grep 不到这个 URL，用户端根本没发请求 换指纹文件名；或缩短 max-age 改走协商
新鲜期过了但浏览器不重校验 HTML、IE”自动”级别 日志里没有带条件头的请求，用户 F5 立刻见到新版 HTML 显式 no-cache，验证时区分刷新方式
中间层按自己的策略缓存 CDN、公司或家庭网关 curl 直连源站是新响应头，经 CDN 拿到旧内容 改 CDN 控制台策略或走 purge，源站头只是前提

排查心法一句话：先确认请求有没有发出去，再确认是谁应答的。Network 面板里状态码、Size 列、请求头这三样看一遍，九成的现场当场定性。

动态接口我们的默认值就是 no-store，一行配置：

理由很实际：接口响应里普遍拼着登录态、价格和库存，共享缓存里存中一次就不是性能问题而是事故；浏览器后退按钮从本地恢复页面的行为又和缓存头搅在一起，no-store 是唯一不用解释的配置。需要缓存收益的公共字典类接口，单独放一个前缀，给短 max-age 加 public，和 no-store 的默认块物理隔开。

Vary 配错会串味，我们交过一次学费。2013 年 9 月，页面主体和一个弹层复用同一个接口 URL，后端按 X-Requested-With 判断身份，给普通请求返回 HTML 片段、给 XHR 返回 JSON，却忘了声明 Vary。结果公司内网代理把 JSON 那份存了下来，另一拨同事打开弹层，页面上直接贴出一串生 JSON。修法有两条路：老老实实写 Vary: Accept-Encoding, X-Requested-With，但当年我们对接的 CDN 和部分内网代理对这种非标 Vary 字段支持很差，有的干脆把响应头整个丢掉，等于没声明；所以我们最后改成按 URL 拆分——/api/comment 归页面、/api/comment.json 归 XHR，一个 URL 只有一种表示，Vary 里只留 Accept-Encoding。接口串味的问题从根上消失，不用再赌中间代理的素质。还有一类脏数据来自你自己够不着的网络：一次活动接口被运营商侧内网代理缓存了两天的响应，对方反馈”我这边看是旧的”，直连一切正常——结论依然是别指望”不配置就不缓存”，接口必须显式 no-store。

发布流程：先传资源，后切 HTML

发布顺序我们只认一条：静态资源先就位，入口 HTML 最后切。流程图如下：

flowchart TD
  A[Grunt 构建输出带 hash 的 js 与 css] --> B[静态资源全量上传源站与 CDN]
  B --> C[curl 抽验新资源 URL 返回 200]
  C --> D[发布新 HTML 切到引用新文件名]
  D --> E[观察 404 比例与源站带宽曲线]
  E -->|异常| F[HTML 切回旧版本, 旧资源仍在]
  E -->|正常| G[保留最近三个版本资源, 一周后清理]

顺序反过来的代价是具体的：先切 HTML 时，新引用的指纹资源还没传完，用户拿到新页面去请求不存在的文件，CDN 边缘节点会把这批 404 按自己的策略存一阵子——哪怕资源两分钟后就位，已经吃过 404 的节点还要继续错下去。一次顺序搞反的发布，故障面积比正确顺序大出一倍不止。反过来，回滚之所以便宜，正是因为旧资源从未删除，HTML 单文件切回去就完事。构建侧我们用 Grunt 0.4 加 rev 类插件把 js/css 改成内容哈希名，改动文件名有困难的存量资源，退一步用 ?v=20140206 这种 query 串刷新——但要小心，当时有些国内 CDN 默认对图片类忽略 query 串缓存（带不带参数视为同一 URL），这样缓存刷新等于白做，务必拿 curl 带不同参数实测，别信手册。

灰度期两版本并存是另一个雷区。危险动作是”文件名不变、直接替换内容”：灰度机器已经是新文件、老实机器还是旧文件，同一个 URL 两种内容，用户在两台机器之间来回，一会儿 200 拿到新版、一会儿被老实机器按旧的 Last-Modified 判成 304，样式在新旧之间反复跳。我们的规矩是灰度只发生在 HTML 入口与接口网关层，静态资源永远先全机器同步新文件再放量，同一 URL 在任何一台机器上内容必须一致。

笔者现在的发布 checklist 是这几条，缺一项不点发布：

  • 构建产物全部带指纹文件名，HTML 引用清单核对无误
  • 静态资源先传完，抽三个文件 curl 确认 200 与响应头
  • HTML、新资源、图片、接口四类各抽一条响应头抽查
  • CDN 刷新队列清空，purge 入口和权限就位
  • 干净 profile 访问预发域名，记录 304 次数与强缓存命中情况
  • 回滚脚本在预发演练过一次，确认旧资源未删

坑与复盘

坑一：响应里出现两个 Cache-Control。 Nginx 的 expires 本身就会生成一条 Cache-Control，再画蛇添足写一句 add_header Cache-Control "public"，响应里就是两条同名头。Chrome 取哪条看不准，IE8 的行为更是随机，我们一次弹层 CSS 的版本错乱最后查到这儿，Charles 重放数了数头才发现。修复原则：要纯时长就只用 expires，要附加 public、must-revalidate 这类指令就关掉 expires、手写完整的一条，二者永远二选一。

坑二：$.ajaxSetup({ cache: false }) 干掉全部强缓存。 jQuery 会给 GET 请求追加 _=<毫秒时间戳>，全局一设，连静态 JSON 配置都被拖成每次回源。当年一个同事为调试 IE 的接口缓存把这句合进了主干，两个月里没人注意：字典类接口全部穿透，源站带宽涨了六倍，nginx 日志里 200 占比从 8% 爬到 46%，直到账单预警才暴露。这种参数禁止全局设置，代码评审单里加一条检查项。

坑三：CDN 丢响应头，图片缓存三十天。 接国内一家 CDN 时，文档写着”跟随源站”，实际默认策略是按后缀写死的 TTL——图片三十天，且源站的 Cache-Control 在边缘节点被直接丢弃。一次跨年活动，运营换了 banner 图的内容没换文件名，切换次日全国用户看到的还是旧图，客服工单暴涨，最后把旧图回滚传回去、同时提交全网手动刷新，purge 生效花了二十来分钟。复盘后立了两条铁规：图片文件名必须带日期或哈希，改内容必改 URL；CDN 侧把策略显式改成强制跟随源站，并拿 curl 到边缘节点逐类型实测——源站头只是承诺，中间层生效才算数，这条是三个坑共同的教训。

小结

本文按落地视角把缓存这件事重新过了一遍：先按资源类型定策略表，2014 年的移动网络下消灭往返比节省字节更重要；Nginx 与 Apache 的配置片段里，location 分块顺序、FileETag 的 inode、双 Cache-Control 头都是真金白银换来的细节；”改了不生效”的三类成因各有一条可判定的日志证据；接口默认 no-store，表示不同的数据拆 URL 而不是赌 Vary；验证靠固定的 curl 与抓包动作，发布靠”先传资源后切 HTML”的顺序和一份不打折的 checklist。缓存配置从来不是写完响应头就结束，它是一份横跨浏览器、CDN 与各级代理的契约，链条上每一环都要有人拿工具去验真。
