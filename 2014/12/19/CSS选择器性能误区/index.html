CSS 选择器性能误区

本文属于《HTML 与 CSS》第 23/62 篇
上一篇系列目录下一篇

聊 CSS 选择器性能，最常见的说法是”少用后代层级、只用类、禁用通配符”，但这些经验规则很少有人拿到真实页面里量一遍。本文先把浏览器匹配样式的过程搭一个最小模型，再按这个模型逐条纠正六个流行误区，最后给出四件真正值得做的事。适合已经能正常写选择器、打算在页面变重之后做取舍的读者。选择器的语法与用法我在旧文《CSS3 选择器进阶：属性、伪类与结构选择器》里已经梳理过，本文不再重复，建议先读完那篇再来看这里；那篇里我当时也列了几条经验规则，写了一年半再回头看，有几条需要修正。

先搭一个匹配过程的最小模型

很多人想象中的样式匹配是”每个元素把整张样式表从头到尾扫一遍”，实际过程分三步。第一步发生在样式表加载解析之后：浏览器会把所有规则预先按选择器的关键部分（最右边的简单选择器）分桶建索引——关键部分是 #nav 的进 id 桶，是 .btn 的进 class 桶，是 li 的进标签桶。第二步，当某个元素需要计算样式时，引擎先按它自身的 id、class、标签名从对应的桶里摘出少量候选规则。第三步才是命中判断：从选择器的最右端开始，逐段向左验证祖先是否满足条件。

flowchart TD
  A[样式表加载解析] --> B[步骤一 规则预处理 按关键部分分桶建索引]
  B --> C[某元素需要计算样式]
  C --> D[步骤二 按 id class 标签从桶中摘出候选规则]
  D --> E[步骤三 命中判断 从最右段向左验证祖先]
  E --> F[命中的规则进入层叠 得出最终值]

到 2014 年 12 月，这个”从右向左”的命中方向在 WebKit、Blink、Gecko 三个主流引擎上是一致的；但各家怎么分桶、缓存结构如何、对命中路径做了哪些 JIT 优化，差别相当大。所以网上流传的经验数值——“属性选择器比类慢几倍”这类——本质是某个具体版本某个具体引擎上的测量结果，可以参考，别当定律。

理解了这个模型就能明白：”从右向左”只是第三步的命中方向，不等于每条规则都要扫一遍文档树。真正的开销通常取决于两件事：这张样式表的规则总量（影响步骤一和失效标记），以及一次 DOM 或 class 变动之后哪些元素的样式重算被触发、范围多大。后面六个误区的病根，几乎都是把”选择器字符串”当成了”重算范围”。

误区一：选择器写得长就一定慢

说法：选择器越长，引擎要处理的字符越多，就越慢。

真相：分桶建索引之后，选择器字符串本身并不是被逐个字符”读”出来的。div.foo.bar > span 会被放进 span 桶，只有 span 插入、删除、改 class，或者它的祖先链发生相关变化时，这条规则才被拿出来做一次命中判断；左边的 div.foo.bar 只验证特定的父级，成本近乎恒定。真正贵的是触发重算的频率和范围：如果代码每秒给一个大容器切换一次 class，容器整棵子树都被标成需要重算，每个元素都要把可能命中的候选规则走一遍——这时候选择器被剪得再短也省不了多少。

怎么做：页面慢先查”谁被重算了”，再查”选择器长不长”。用 DevTools 的 Timeline 看 Recalculate Style 的记录占多少帧时间、由哪次 DOM 操作触发，比盯选择器字符串有用得多。一条从不参与变动的长选择器，首屏渲染完基本不产生持续成本；一条很短但每秒被切几十次的 class，才是要治理的对象。

误区二：为了性能只能全部用类选择器

说法：性能要求下整个项目只能写 class 选择器，标签选择器和结构选择器一律禁掉。

真相：”id 直接进哈希表最快”是早年的流行说法，id 作为关键部分时查找成本确实低，但拿 id 当样式锚点，等于把样式表绑死在一个 DOM 实例上：同一块结构需要出现第二个实例时样式不跟过去，而且 id 的特指性很高，想覆盖就得写更长选择器或者动用 !important。反过来，普通类与标签在重算成本上的差距常常落在噪声范围内，不至于为它立规矩；真正会咬人的是 ul li 这类纯结构性约束把样式绑死在特定层级上，结构一演进样式就莫名失效。

怎么做：给一条务实规则——结构性选择器可以保留给”语义稳定”的局部关系，状态与主题一律用 class。禁用、激活、加宽这类是状态而不是位置，状态就该由 class 表达，不该依赖容器里数得出几个子元素。不必为了含糊的”性能收益”把样式表强行压平。

误区三：通配符与属性选择器是性能杀手

说法：* 和 [attr] 匹配范围太大，是性能杀手，绝对不能用。

真相：* 只有当它处在最右关键部分时才贵——它对应的桶是”所有元素”，每次元素重算这条规则都要被考虑一遍。像 Reset 里 * { margin: 0 } 这种写法，主要参与首屏那一次批量匹配，页面稳定运行后几乎不产生持续成本，不值得为它专门绕开；旧文《CSS3 box-sizing 与全局重置样式》里的全局重置就是这一类，一次性、静态、可以接受。真正的坑是运行期活跃的 .container * { } 式写法：container 下每个后代的插入、删除、改 class，这条规则都会进入候选并被应用一遍。属性选择器也不是天生慢，贵的是”属性选择器加深层后代”的组合——每向上验证一层都要顺手读祖先的属性值。

怎么做：Reset 里的 * 保留；运行期样式宁可给容器里的子元素统一挂 class，用明确的命名换取”改了谁只重算谁”；属性选择器用在静态内容与一次性状态判断上，别把它放进频繁变动的深层嵌套里当条件。

误区四：后代层级越多越慢，必须压平

说法：每一层后代都要向上走一遍，五层必然比一层慢好几倍，必须全部压平。

真相：祖先验证通常找到最近的匹配就停下，层级并不线性放大成本；引擎的失效策略主要影响”哪些元素被标成要重算”，跟层级深度关系不大。这话空说无凭，我做了个小实验：造一个 5000 个条目的列表，准备两条规则——一条单层 class，一条三层后代，命中的是同一个元素，反复改 class 名并强制重算来计时。

我这台机器上两组单次均值都在零点几毫秒上下，差别基本淹没在噪声里；反倒是另外两个变量一动数字就跳一个量级：把规则的效果从颜色换成会影响布局的属性，或者把循环里的强制读取去掉让浏览器攒着批量处理。测量方法沿用《jQuery 与原生 DOM 的性能对比》里那两条纪律——先预热、多次取均值、只认量级。结论很直白：三层后代与单层类的差别，远小于一次强制同步布局带来的差别。

怎么做：三层以内的层级不必为”性能”主动压平；样式表里出现六七层长的后代链当然该治理，但理由是特指性失控和耦合（下面嵌套一节细说），不是”它慢”。

误区五：结构性伪类很慢所以禁用

说法：:nth-child 要数兄弟、:not 要反向验证，都很慢，项目里直接禁用。

真相：结构性伪类单次命中判断的成本并不高，贵的是元素增删时的失效标记——:nth-child 的匹配结果依赖兄弟序号，插入或删除一行，后面所有兄弟的序号全部作废，引擎得把这一片兄弟重算一遍。一次性渲染完就不动的表格，这笔账只在首屏结一次，近乎免费；每秒都在插行的列表，它就变成持续征收的税。:not 的成本与普通 class 条件差不多，没有必要株连。

怎么做：选型建议——静态或低频变动的内容（表格、文章排版、导航）放心用结构性伪类；高频插入的列表，把斑马纹之类的状态在拼装数据时用 JS 打好类名，让重算不再依赖兄弟序号。顺带一提，这个做法同时解决了老浏览器不支持结构伪类的兼容问题，兜底思路旧文里已经讲过。

误区六：!important 能提升性能

说法：!important 能让引擎短路层叠、直接返回结果，所以有性能优势。

真相：!important 只改变声明参与层叠时的优先次序，规则匹配与元素重算一步都没有少，加与不加在速度上测不出差别。它真正毁掉的是可维护性：要覆盖一个 important 就得用更重的覆盖手段，几轮下来样式表变成升级竞赛，谁也不敢删。

怎么做：正当用途只有两类——工具类覆盖（比如 .hidden 这类就是声明”任何情况下都要压过别人”的规则），以及第三方样式隔离（改不动对方规则时，用自己带 important 的规则保证输出稳定）。除此之外，尤其是业务样式，不要用。想防止误覆盖，正确的工具是控制特指性与结构，不是加 important。

真正值得优化的四件事

把六个误区拆开，指向的是同一个结论：值得花力气的不是选择器字符串，而是重算触发、耦合关系和交付体积。按收益排四件事。

一、少动”触发重算范围大”的属性

改 width、top、font-size 这类几何属性要重新布局，改 transform 与 opacity 可以绕开布局；多个属性总是一起变时，用一次 class 切换合并成一次失效。

性能结论的完整清单在旧文《减少重排与重绘的实践清单》里，这里不重复。

二、压缩阻塞渲染的 CSS

head 里的样式表要下载并解析完才允许首屏渲染，它的体积与请求数直接决定首屏出现的时间——这一项的量级通常远大于选择器层面的微差。拆文件、按需加载与合并压缩在旧文《资源合并与压缩的收益分析》里算过账，这里只补一句：首屏必需的样式随页面走，其余部分拆出去延迟加载。

三、预处理器嵌套不超过三层

嵌套的真实风险不是慢，而是展开后特指性过高、结构与样式意外耦合。看一个 Less 例子：

展开产物是 .page .sidebar .widget .title span。它要求 DOM 严格凑齐这条五层结构，少挂任何一层 class 样式就静默失效；特指性堆到四个 class 加一个标签，日后想覆盖要么写一样长的选择器要么上 important，又绕回误区六。写 Less 或 Stylus 时自查：嵌套超过三层，先问这个元素是不是真的需要外面那几层限定。

四、用命名规范把复杂度挪进 class

BEM 风格的命名（块、元素、修饰符）能把绝大多数规则压到”单类加状态类”的级别：.card、.card__title、.card__title--muted。布局关系靠少量标签与结构表达，状态一律用修饰符类。注意选择器平展不是目标本身，”谁依赖谁”才是——命名规范的价值在于把依赖变成可读的词汇表，顺便让引擎的失效范围更容易预测，而不是它本身省了多少毫秒。

小结

读完这一篇，值得带走的是三条可执行规约。第一，先测再说：用固定口径的量级测量替代经验值，先查谁被重算、重算了多少次、多久一次，再轮到选择器字符串。第二，层级与耦合优先：选择器层级控制在三层以内，状态依赖 class 而不是 DOM 结构——这决定的是半年后改版要返工多少，比省下的毫秒实在。第三，把复杂度放在 class 上，不要放在 DOM 结构上：无论是让 JS 打类名还是靠命名规范，本质都是同一件事——把匹配期的成本挪到拼装期，把运行时的重算变成构建时的清晰。至于引擎的分桶策略与 JIT 优化，每年都在变，本文说的从右向左与分桶是 2014 年三个内核的切面，具体结论过一两年可能要修，但”先建模型、再破认知、最后让数据说话”这条路径不会跟着版本过期。
