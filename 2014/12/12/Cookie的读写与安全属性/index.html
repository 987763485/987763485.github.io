Cookie 的读写与安全属性

cookie 是最容易被误解的一枚老工具：会话标识刷新还在，换个子域就读不到，明明删了记录仍挂着。本文只讲 cookie 自身——读写语义、六个属性的匹配规则，以及属性组合怎么选。

先把口径立住：能用的只有六个属性

依据是 RFC 6265（2011 年 6 月发布，取代 RFC 2109）：服务端用 Set-Cookie 写、Cookie 头带回，页面脚本用 document.cookie 读写，而一条记录能被谁读、活多久全由属性决定。可用的只有六个：

  • expires：绝对过期时间，必须是 GMT 格式的日期串。
  • max-age：相对秒数，与 expires 同时出现时它优先；IE 8 及更早完全不认。
  • domain：允许读取这条记录的域范围。
  • path：允许读取它的路径前缀。
  • secure：只在 https 请求里发送。
  • HttpOnly：不允许脚本读取，只能由服务端 Set-Cookie 设置。

属性名不区分大小写，这六个之外没有可配项。document.cookie 设不了 HttpOnly，写了也不生效，不少”读不到 cookie”的排查就从这里跑偏；前端赋值等价于一条只含名字、值和可选属性的 Set-Cookie，谁能写谁能读是第一道判断。cookie 不属于 HTTP 缓存体系，这条边界《浏览器缓存机制全景》讲过，不重复。

读写语义：赋值只提交一条，读取只给可见部分

误解在于把它当普通字符串属性：有人写 document.cookie = '' 想清空，有人以为 document.cookie = 'a=1' 会连带抹掉另外十几条。实际这个 setter 不读左侧的完整串，整条赋值只提交一个 cookie——同名同域同路径的旧记录被覆盖，其余一动不动。

读取相反：只有当前域与路径匹配到、且没有 HttpOnly 标记的记录才出现在返回值里。所以”读不到”有三种解释——没写、作用域不匹配、被 HttpOnly 挡住。

解析要按分号切，两端必须去空白

主流内核在分号后补一个空格，split('; ') 看着够用，但个别老版本只用分号，所以按分号切再两端去空白最稳；取等号用 indexOf 而不是 split('=')，后者会被值里的等号截断。

同名不同路径的两条会同时出现在这个串里：写入只是新增，读取拿到先出现的那条，服务端 Cookie 头里的顺序则由浏览器决定——这是”改了值、接口读到旧值”最隐蔽的来源，排查时打印整个 document.cookie 数一下名字出现几次就够了。

4 KB 是单条上限，各家口径还要实测

主流内核普遍按 name 加 value 计算，约 4096 字节，属性串不计入；超出后有的拒绝整条写入，有的截断保存。条数上限更要命：老 IE 每个域名只留几十条，整个浏览器另有总量限制。最坑的是超限不抛异常、静默失败，只能写回再读出来验证。

所以”要实测”不是客套：同一份数据在 Chrome、Safari 与 Android 2.3 原生浏览器上能写的长度确实不同。

删除是最容易失败的操作

删不掉的原因几乎只有一个：作用域没对上。必须用同名、同 domain、同 path 的组合再写一次，并把过期时间设到过去。

最高频的坑是省略 path：不写时浏览器取当前 URL 的目录部分作默认路径，页面在 /app/user/list.html 默认就是 /app/user/；删除代码往往写在另一个页面，目录不同，两者根本不是同一条记录。所以任何写入都显式带 path=/。另外老 IE 对超出 1970 到 2038 区间的时间串处理不一致，expires=0 是无效串，会被整段忽略。

作用域三属性的匹配规则

domain：写了就含子域，不写就锁死当前主机

规则只有两条：不写 domain，cookie 只属于当前主机名，精确匹配；写了 domain=example.com，example.com 本身和它的所有子域都能收到。

页面主机 写入时的 domain 谁能读到
www.example.com 省略 只有 www.example.com
www.example.com example.com 裸域加全部子域
example.com 省略 只有裸域，带 www 前缀的读不到
www.example.com other.org 跨注册域的写入被整段忽略
m.example.com co.uk 这类公共后缀 拒绝写入

三个结论：www.example.com 与 example.com 是两个不同主机，裸域写的记录带前缀的页面读不到，反向也一样，这是后文第一起故障的根因；domain 只能往更泛的方向写，且必须是当前主机自己或它的父域，写别的域不报错但完全无效；公共后缀不允许当 domain。

至于 document.domain，设成父域之后脚本写出的记录归属主机跟着变成父域，几个同名值的子域就能共享，代价是同源边界被削弱——同域下任何能把脚本注进来的 iframe 都能读写别人的记录。新代码我更倾向显式写 domain。

path：前缀匹配，而且要求斜杠边界

path 不是简单的字符串前缀包含。规范要求的匹配是：请求路径与 path 完全相同；或者 path 是请求路径的前缀，且前缀之后的第一个字符是斜杠，或者 path 自身以斜杠结尾。

cookie 的 path 请求路径 是否携带 原因
/foo /foo 是 完全相同
/foo /foo/ 是 前缀之后是斜杠
/foo /foo/bar 是 前缀之后是斜杠
/foo /foobar 否 缺斜杠边界
/foo/ /foo 否 path 不是请求路径的前缀
/ 任意路径 是 根路径匹配全部

最后两行解释了一类玄学问题：写成 /foo/，/foo 入口页收不到；写成 /foo，/foobar 那类活动页又带上本该隔离的记录。默认值是当前 URL 的目录部分并带结尾斜杠，空 path 不等于 /。

secure：只在 https 请求里出现

secure 让记录只在 https 请求里出现，http 页面既发不出也读不到。还没全站 https 的现实里，典型故障来自混用协议：登录接口在 https 上写了带 secure 的会话，页面却跳回 http 的活动页，会话发不出去，用户被踢回登录页。反过来，非 secure 的记录在两种协议下共享同一个存储桶，明文链路里会被中间人一览无余。

生命周期选型：会话、expires 与 max-age

三种活法：会话 cookie 不带过期属性，浏览器关闭即消失；expires 给绝对时间点；max-age 给相对秒数，两者同时出现时 max-age 胜出。会话 cookie 的前提本身就不牢靠——主流浏览器默认恢复上次会话，进程重启后记录还在，别当短期存储；退出时若只清了服务端状态、本地留的是会话 cookie，就会出现”退出后刷新又登录了”的错觉。

绝对时间的致命弱点是按客户端时钟判定：服务端算出”三十天后”转成 GMT 串，用户把日期改到两年前，这条记录写入瞬间就已过期被丢弃；时钟慢半小时，”三十分钟不再提示”就多半小时，这是后文第二起故障的机制。相对时间从写入起算不受影响，可惜 IE 8 及更早完全不认、只认 expires，所以真实项目要双写。

双写要注意两点：两个值必须表达同一时长；expires 不要写到 2038 年之外，超出后老 IE 静默丢弃，看着像压根没写进去。

HttpOnly 与 secure：安全属性各挡什么

HttpOnly 只解决一件事：让页面脚本读不到这条记录。它从 document.cookie 的返回值里消失，改不了也删不了，挡住的是 XSS 落地后偷走会话凭证这条路——评论区、富文本这类原样渲染用户输入的地方，一个链接就够把可读 cookie 全 dump 一遍，这个面在《HTML5 contenteditable 富文本编辑入门》里谈过。但它挡不住 CSRF：伪造请求不需要读 cookie，浏览器自己会把记录带上，那条防线在同源校验与一次性 token 上，两者不能混为一谈。

想要 HttpOnly 只能由服务端写：

划分如下：

数据 谁写 前端可读 HttpOnly Secure 补充建议
会话标识 sid 服务端 Set-Cookie 否 必须 有 https 就必须 path=/，跟会话同生死
长期登录凭证 服务端 否 必须 必须 max-age 与 expires 双写
CSRF token 服务端下发 是，要回填表单 不加 跟随页面协议 短 max-age
灰度标识、A/B 分桶 前端或服务端 是 不加 不必 显式 domain 与 path=/
界面偏好 前端 是 不加 不必 长期 max-age，值控制在几十字节
统计访客 id 服务端或前端 是 不加 不必 domain 放宽到主域

由此推出一条纪律：前端不要把任何身份凭证手写进可读 cookie。用一句 document.cookie 把接口返回的令牌存起来，等于主动放弃 HttpOnly 唯一的保护，还把它塞进了每一个请求头；真要让服务端认身份，就交给登录接口的 Set-Cookie。

https 尚未普及，secure 要不要一刀切？我的结论是不必，但登录态必须：站点只要有一处能走 http，中间人就能改写非 secure 的记录，给会话标识加 secure 是下限；对偏好类、统计类数据，加它只会带来混用协议的故障。

编码、命名与值的设计

value 里的分号、逗号、等号、空格都会破坏解析，中文在老浏览器上更麻烦，所以写入前必须 encodeURIComponent，读取后 decodeURIComponent。encodeURI 不够用：它按设计保留 : / ? # [ ] @ & = + $ , ; 这些有语法含义的字符，正好把最危险的留下。escape 要淘汰：它不在标准里，ES5 只在附录 B 当遗留兼容项标着，遇到汉字输出 %u4F60 这种私有形式，服务端按 UTF-8 百分号解码根本认不出来——同一段中文在老 IE 里是 %uXXXX、在 Chrome 里是 %E4%BD%A0，两套形态混在同一字段，后端只能两种都试一次。

三条原则。别把 JSON 大对象塞进去：中文经编码膨胀到三倍，超限又是静默失败，坏数据比没数据更难查。宁可拆成几条小的，也不攒成一条大的：拆开之后作用域和过期时间能独立设置，一项变更不连带整块失效，调试还能单条删除。命名带前缀和版本，形如 app1_theme_v1，换结构时递增版本号而不是原地改语义。

调用与验证：

已经有 jQuery 的项目，当时常用 jquery.cookie.js 1.4.1，接口 $.cookie(name, value, options)，options 支持 expires（天数或 Date）、path、domain、secure、raw。两点留意：它默认 path 就是 /，比手写安全；默认对值编码，而 raw: true 同时跳过编码和解码，后端按原样取值两边就分叉。它没有 max-age 支持，双写策略得自己补。

该不该用 cookie：与 Web Storage 的分工

先问”要不要参与 HTTP 请求”，再问”用哪些属性”。三种存储摆开：

存储手段 随请求发送 容量口径 服务端读写 过期能力 HttpOnly 保护 跨子域 WebView 的 file:// 场景 适合存什么
cookie 是，匹配到的每个请求都带 单条约 4 KB 能写能读 原生支持 expires 与 max-age 有，唯一的选项 能，靠 domain 放宽 各家不一致，读写不保证 会话凭证、灰度标识、A/B 分桶
localStorage 否 每个源约几 MB 看不见 无，要自己实现 TTL 无 不能，origin 严格划分 常被当成不透明源，读取抛错 偏好、草稿等不出门的缓存
sessionStorage 否 同上量级 看不见 上下文结束即清 无 不能 同上 一次性表单流程状态

localStorage 的封装、配额与私有模式抛错，《localStorage 与 sessionStorage 本地存储实战》写过一遍；跨域带 cookie 是另一套规则，withCredentials 配合 Access-Control-Allow-Credentials 在《AJAX 与跨域请求实践》里讲过；Hybrid 里 file:// 页面干脆走原生通道，属于《JSBridge 设计与实现》。三处都不重复。

flowchart TD
    A[这份数据要不要参与 HTTP 请求] -->|不需要| B[localStorage 或 sessionStorage]
    A -->|需要| C{是身份或会话数据吗}
    C -->|是| D[服务端 Set-Cookie 加 HttpOnly 与 Secure]
    C -->|否| E[前端 document.cookie 显式 path 与 domain]
    D --> F[max-age 与 expires 双写，避开本机时钟]
    E --> F

结论很硬：cookie 唯一不可替代的场景就是”要参与 HTTP 请求”——会话标识、灰度分流、A/B 分桶，以及服务端渲染时要读的首选项，其余数据都不该放 cookie。

带宽账算一次就够：主站域名挂着 2 KB 左右的记录，一个活动页有 80 个静态资源请求，就是 160 KB 纯上行头开销，全部落在首屏关键路径上。解法不是把 cookie 写小，而是静态资源走独立域名、那个域名一条 cookie 都不写——域名隔离的论证在《CDN 加速原理与接入实践》，引用规范在《静态资源版本号与缓存更新》。

两个故障复盘

子域写的状态主域读不到

现场：引导流程写在 m.example.com，用户跳到 www.example.com 的落地页，引导又从零开始。根因是写入没带 domain，记录被锁在 m.example.com 这个主机上；排查时还发现第二个问题——引导页路径 /guide/step2.html 让默认 path 成了 /guide/，连 /guide/help 也读不到。修复是显式统一作用域并在写入后校验，免得跨注册域这类被静默拒绝的写法混进来：

跨子域共享是 domain 唯一的价值，但一旦放宽，这个域下所有子站都能读写同一份数据，所以共享记录必须带前缀和版本号。

客户端时间倒退让”下次自动登录”当场作废

现场：个别用户每次登录都得重勾”下次自动登录”，同批其他人正常。根因：登录接口按服务端时间算出三十天后的绝对时间下发 expires，而这些用户把机器日期改到两年前，浏览器一比本机时间就判定记录已过期，写入即刻被丢弃。修复分三层：max-age 与 expires 双写；把”记住我”的时长语义放回服务端，浏览器只保存凭证；本机时间与服务端响应头 Date 偏差超过一天时，把绝对时间逻辑退化成相对时间并提示校时。教训一句话：任何按绝对时间的客户端逻辑，都要假设用户时钟是错的。

小结：一张属性配置决策表

先问三个问题：要不要参与 HTTP 请求；是不是身份或会话；作用域要多大。按这三问铺开：

要存什么 谁写 HttpOnly Secure 生命周期 domain 与 path
会话标识 服务端 加 有 https 就加 会话级，退出即清 显式 path=/，不跨子域就别写 domain
长期登录凭证 服务端 加 必加 max-age 双写 expires，别超 2038 主域加 path=/
CSRF token 服务端 不加，要回填 跟随页面协议 十几分钟 path 收窄到表单页
灰度标识、A/B 分桶 前端或服务端 不加 不加 跟实验周期，max-age 为主 要跨子域统计就放宽到主域
界面偏好 前端 不加 不加 长期 path=/，别按目录散着写
统计访客 id 服务端 不加 不加 一年量级 主域共享，便于跨子域归因
一次性表单流程 前端 不适用 不适用 用 sessionStorage 不该出现在 cookie 里

属性之外还有三条纪律：写入永远显式带 path，需要共享时才加 domain，值一律编码；写完立刻读回校验，4 KB 超限和非法 domain 都是静默失败；删除必须同名同域同路径，HttpOnly 只能由服务端清。这几件事一次做对，剩下的只是按时长填参数。
