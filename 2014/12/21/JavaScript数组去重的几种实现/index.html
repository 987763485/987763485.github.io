JavaScript 数组去重的几种实现

数组去重看着不用思考：建个对象当哈希表，或一句 filter 就写完。可放进真实业务，第一天就会遇到“少了两条”和“多了两条”：接口的 1 与 '1' 被合成一个，埋点里的 undefined 与 'undefined' 互相吞掉，列表因为重复 id 撞了渲染 key。本文先定清“什么算同一个值”的比较口径，再给出 ES5 里能跑的八种实现与边界，最后落到选型表、计时脚手架和三个场景。代码全是 ES5，输出均在 Node 实跑核对。

先把比较口径定下来

去重要回答的第一个问题不是“怎么实现”，而是“判重依据是什么”。最常用的口径是以 === 为基础、只把“多个 NaN 视为同一个值”这一条改掉——NaN 永远不等于自己，可没有业务希望列表里出现五个同样的 NaN 行。写成判定函数，后文所有实现都调它：

这个口径放弃了什么也要清楚。=== 不做转换，所以 1 与 '1'、true 与 'true'、[] 与 '' 都是不同的值；松散相等下 [] == false、[1] == 1 却统统成立。抽象操作怎么推，笔者在《JavaScript 数据类型与类型转换详解》里已写透，这里只引结论：== 不满足传递性，绝不能拿 == 当去重判据——两个各自与第三个值相等的元素可能互相不等，哈希结构无法自洽。

边界还有两条。正零与负零：+0 === -0 为 true，视为同一个值；但同一个值不等于同一个表示，[-0, 0] 去重后留下的仍是先出现的 -0；真要区分得自己补符号位，Object.is 当时还没有。对象：本口径比的是引用，两个内容一样的 {a: 1} 是两个值，值级比较是 deep-equal 的范畴，得由业务指定比哪个字段。

五：借字符串当容器

另一种思路：把所有键拼进一个长字符串，用 indexOf 判存在，靠逗号夹住边界。

卖点很实在：字符串 indexOf 是原生的，在老 IE 上比反复读写对象属性更可控，早期脚本里很常见。但它的脆弱是双重的。其一是分隔符冲突，元素自身含逗号就判错：实测 ['a', 'b', 'a,b'] 得 ['a', 'b']，而 ['a,b', 'a', 'b'] 反过来只剩 ['a,b']——换个顺序丢的就是不同的东西，这种顺序敏感的丢失最难查。其二是同样有键类型退化，实测 [1, '1', '10', 10] 只剩两项。真要用至少拼上 hashKey，那时它相对字典版已无优势，只留作极端兼容场合的备选。

八：分桶与分批——把收益边界说清楚

到了十万条量级，常见建议是“先分桶再桶内去重”。说实话：单线程里按首字符或长度分桶不改变总复杂度，该做的哈希判断一次不少，桶只是把大字典拆小。收益只有两条：一是每个桶的对象小、冲突少，不至于撑出巨型对象把 GC 拖出来；二是桶天然可分段处理与渲染。前者很难测出来，后者才实在：

小结

数组去重写起来只有几行，坑全埋在两处。一处是比较口径：NaN !== NaN、+0 === -0、== 不传递，这三条决定“什么算重复”必须先被定义而不是被继承。另一处是键类型退化：对象键会被强制字符串化，不同类型之间、所有对象与 [object Object] 之间全部互相吞并，toString、__proto__、hasOwnProperty 这些原型属性名还会造成漏判甚至抛错；hashKey 用 typeof 前缀加身份号把类型信息补回来，是本文唯一建议全局复用的实现。规模上，几千条用前缀哈希，十万条也不用怕，真卡住界面的是同步处理与渲染而不是去重本身；O(n²) 那几种超过五千就该换。最后重申顺序：先定比较口径，再按规模选实现，最后写单测覆盖 NaN、零值、对象与字符串数字混排——顺序颠倒，出来的就是那种“平时不报错、一上线少数据”的 bug。
