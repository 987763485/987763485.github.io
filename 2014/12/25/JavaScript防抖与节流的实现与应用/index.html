JavaScript 防抖与节流的实现与应用

输入、滚动、resize 这类连续事件的处理函数，是页面性能问题最集中的一处。防抖（debounce）和节流（throttle）是标准解法，但流传最广的版本大多只给了一个十行小函数：既没讲清”到底在哪一刻执行”，也没讲解绑时定时器怎么收、事件对象能不能延迟读、多个元素能不能共用一个包装函数。本文按工程实践的路线走一遍：先钉死时序语义，再给四套可直接投产的 ES5 实现并对比行为差异，然后用六个场景说明参数怎么选，最后收一份副作用清单。适合已经在写页面交互、准备把这些函数抽进公共库的读者。

先把时序语义钉死

一句话定义：防抖是”事件停止 N 毫秒后才执行一次，中途再来就把计时器重置”；节流是”N 毫秒内最多执行一次”。两者都在削减执行次数，削减的对象却不同——防抖等的是用户闭嘴，节流管的是节拍。

维度 防抖 节流
执行时刻 最后一次触发之后 + wait 每个 wait 窗口一次
连续触发 20 次 执行 1 次 执行约 20 次除以窗口数，按窗口切分
中途又来一下 重置计时，推迟执行 不影响窗口，按原节奏走
最坏情况 用户一直输入就永远不执行 停手前最后一下可能延迟一个窗口
适合的直觉 等用户”把话说完” 按固定节拍采样

时间轴对比如下（wait 取 100 毫秒，t0 到 t3 连续触发后静默）：

flowchart TD
    A["t0 触发"] --> B["t1 触发"]
    B --> C["t2 触发"]
    C --> D["t3 停止触发"]
    D --> E["防抖 trailing 在 t3 加 wait 执行 1 次"]
    A --> F["防抖 immediate 在 t0 执行 1 次 其余只重置定时器"]
    A --> G["节流 leading 在 t0 执行 窗口内丢弃 停手后补 1 次"]
    A --> H["标记式节流 只在窗口起点执行 末尾丢掉"]

真正决定选型的是执行时点，而执行时点由两个开关组合出来，一共四种，这一步最容易写错：

leading（窗口起点执行） trailing（窗口末尾执行） 实际行为 典型用途
是 是 立即一次，停手后再补一次 滚动加载、resize 重排
是 否 只在窗口起点执行，末尾丢弃 采样类、只要即时反馈
否 是 首次也要等，末尾保证执行 自动保存、坐标归位
否 否 永远不执行 没有意义，但很多人写出来过

防抖这边对应的开关是 immediate：immediate 为真等于只有 leading，为假等于只有 trailing，两者不可能同时开。节流要凑出四种组合，就得把 leading 与 trailing 做成两个独立选项。

函数包装那层骨架（存 this、拷 arguments、用 apply 调用）不是本文重点，《JavaScript 柯里化与偏函数应用》已经把透传讲透了，下面代码只保留必要的一行注释，篇幅全部留给时序行为与工程副作用。

三点必须记住的行为细节。

第一，immediate 为真时，第二次触发要等到”停止之后”才可能再执行，这不是 bug 而是定义：callNow 只在 timeout 为空时成立，而 timeout 只有等 later 跑完才会被置空。所以 300 毫秒内点四下提交，只有第一下发出请求，后三下只是在往后推静默窗口，要连续静默满 300 毫秒才可能再放行。

第二，args 与 context 在每次执行完都要置空。很多版本省掉这两行，结果防抖函数长期挂着最后一个事件对象和它引用的 DOM 节点，列表页来回切几次，内存曲线只涨不跌。这里存的也是 slice 出来的数组而不是 arguments 对象本身，因为 arguments 会连带激活对象一起留在闭包里。

第三，return result 返回的是上一次执行的结果而不是本次的，拿它当同步函数取值必然拿到旧值，抽成公共工具前要把这条写进注释。

clear 和 flush 是我自己加的。Underscore 1.7.0（2014 年 10 月发布）的 _.debounce(func, wait, immediate) 只给了 immediate 这一个开关，返回值上没有主动取消的入口；lodash 2.4.1 的 debounce 是带 cancel 与 flush 的。下面场景里会看到，这两个入口在真实项目里不是奢侈品。

节流变体一：时间戳加剩余时间定时器

这套写法是 leading 加 trailing：第一次立刻执行，窗口内的调用丢弃，但只要还剩一点时间就挂一个定时器在停手后补一次。这”多出来的最后一次”往往正是我们要的——没人补的话，用户停止拖拽时最终宽度对应的布局就永远不算了。

真实坑在 Date.now() 上：它是墙上时钟而非单调时钟，改系统时间、虚拟机同步时间、某些 Android ROM 的时钟跳变，都会让 Date.now() - last 突然极大或极小。回拨时 remaining 大于 wait，节流器长时间不放行；超前后 remaining 为负，攒下的事件一瞬间全部执行。下面完整实现里那条 remaining > wait 分支就是兜底。

节流变体二：是否已排队的标记

标记版只有 leading、没有 trailing：窗口起点立刻执行，末尾那一下丢掉。好处是不因定时器排队而多出一次执行，也不额外持有 args 与 context，没有内存驻留问题、不需要 clear；坏处是”最后一次状态”会丢，拖完窗口发现布局停在旧宽度就是它的锅。适用判断很简单：只关心”这段时间里更新过”就用标记版，关心”最终值一定要落到”就必须带 trailing。

补一句时间精度：两个版本的实际间隔都不严格等于 wait，setTimeout 排在主线程队列里，页面正在渲染或跑长脚本时就会延后。所以别把节流当计时器用，它是下限保护，不是节拍器。

完整实现：带 leading 与 trailing 选项、支持 cancel 与 flush

这段的选项语义我是照着 Underscore 的实现口径来写的：1.7.0 起 _.throttle(func, wait, options) 支持 {leading, trailing}，行为与上面一致（trailing 为假时不排末尾那次，leading 为假时窗口起点不执行）；cancel 与 flush 这两个入口 Underscore 1.7.0 没有、lodash 2.4.1 有，我按同样的语义补齐，因为场景六离不开 flush。四个组合的行为差异用一句话记：trailing 决定”停手后要不要补”，leading 决定”第一下要不要等”。

rAFThrottle：把重绘类工作合并到每帧一次

它本质是”窗口长度等于一帧、且永远 trailing”的节流，节拍由浏览器给，因此在 60Hz 与 144Hz、高端机与低端机之间都自适应，比手写 wait: 16 稳。但它有两个硬边界：一是只在浏览器里对视觉更新有效；二是不能拿它限制网络请求——帧率跟网络无关，而且后台标签页里 requestAnimationFrame 会被降频甚至暂停，用它做自动保存，用户切走标签页后保存就饿死了。兼容性上 2014 年仍需前缀，IE9 完全没有、IE10 起才有原生实现，所以上面留了 setTimeout 退路。

六个场景的参数选择

场景一：搜索框输入发请求

用防抖，wait 取 200 到 300 毫秒，同时要处理两个容易被漏掉的分支：清空后不该发请求，以及上一次请求还没回来时的竞态。

jqXHR.abort() 与序列号丢弃是互补的两招：abort 省流量但消不掉竞态，序列号才是正确性的保证。另外中文输入法下 keyup 在拼音候选阶段就会触发，250 毫秒的窗口正好跨过一次候选确认，事件更碎时改用 on('input')（IE9 起支持，jQuery 1.9 已归一）比继续拉长 wait 好。

场景二：窗口 resize 重算布局

用防抖。这里要的是”用户拖完边框后重排一次”，中间过程的重排全是浪费，trailing 语义天然对口。

如果用节流，用户拖拽边框时会一路重排到底，而每次重排都是强制布局，卡顿就来自这里。另外 Android 键盘弹出会改变视口高度从而误触发 resize，做弹层适配时要防一手。

场景三：滚动加载下一页

用节流加阈值判断，{leading: true, trailing: true}。滚动是持续事件，防抖会让用户”一直滚就永远不加载”，这是新手最常犯的反向错误。

阈值取 300 像素，是让下一页在用户滚到底之前就开始请求。另一个细节是别在滚动回调里读 offsetTop、scrollHeight 这类几何量，它们会强制浏览器同步算一次布局、把一帧预算吃光，所以上面用缓存的文档高度，只在 resize 里刷新。

场景四：提交按钮防重复点击

这里用首次立即执行的防抖（immediate: true），绝不能用 trailing 版本。

原因是体验和责任都指向第一次：trailing 版把”那一次点击”推迟到停止点击 1.2 秒之后，界面看起来像卡死，用户因为没反馈会更用力地多按几下，反而把提交时间一路往后推。immediate 版第一下就发请求，静默窗口内的重复点击被直接吞掉，语义正好是”只提交第一次”。当然前端防抖只挡得住双击，按钮 disabled 加接口幂等号才是完整解法。

场景五：拖拽与绘图时更新坐标

鼠标事件一秒内上百次，浏览器一帧只画一次，多出来的写入全是白做功；参数取最新，拖动结束时残影正好停在最终位置，不需要 trailing 补偿。

只写防抖会留下一个明确的数据丢失窗口：用户改完最后一句就关页面，那 1.5 秒的定时器随文档一起消失，草稿丢了，flush 补的正是这一笔。要注意 beforeunload 里发异步请求并不保证送达，当年项目里普遍退化成 async: false 的同步请求，体验差但可靠。

那些上线后才会暴露的问题

第一，解绑时忘了清理定时器。 防抖函数里那个 timeout 是一条实实在在的引用链：它挂着 context 与 args，而 args 里往往有 DOM 节点。组件销毁时只 off() 不解定时器，会有两种事故——回调在已经离开的页面里执行，以及整棵子树被闭包留住回收不掉。规范做法是解绑前先 clear：

摘掉监听器本身为什么会引发泄漏，闭包与 $.cache 那条可达链在《DOM 事件移除与内存泄漏》里已经推导过，本文不重复，只补一句：那篇的清理清单要加上”防抖与节流的定时器”。

第二，this 与 arguments 只能靠 apply 现场传，不能在定义时捕获。 把实现写成 var that = this; 再在回调里用 that，等于把上下文冻在”创建这个防抖函数的时刻”：在构造函数里创建恰好是对的，在原型方法里创建、或被复用到多个元素时就是错的，而且错得很安静。参数同理，延迟执行时拿不到调用现场，只能提前拷贝。每次绑定时现调 Function.prototype.bind 也是坑，它产生新引用导致摘不掉监听器，这层取舍《this 指向的四种绑定规则详解》谈过，本文只补一句：防抖函数自己也要”创建一次、存成引用”。

第三，事件对象在延迟执行时可能已经不可靠。 防抖把执行推到几百毫秒之后，那时再读事件对象常是过期信息：IE 的 window.event 在处理器返回后就被重置，延迟读到的是”下一次事件”；relatedTarget、pageX 在 jQuery 的包装层里同样可能失效。纪律是在触发现场把需要的字段取成普通值再传进去，像场景五那样传 e.pageX、e.pageY；把 e 整个交给防抖函数，还会顺带把 target 那棵子树留在闭包里。

第四，一个防抖函数不能给多个元素共用。 因为 context 与 args 只有一份，后一次调用会覆盖前一次：

共用实例的表现是”看起来偶尔生效”，比完全不生效更难查。每元素一份的代价是 N 个定时器，输入框场景无所谓，上千项的列表要改成事件委托加一份节流表。

第五，wait 的数值是团队调出来的经验值，不是定律。 我们当时用的量级：

场景 wait 量级 依据
输入联想 200 到 300 毫秒 跨过一次输入法候选确认
自动保存 1000 到 2000 毫秒 请求成本换编辑连续性，必须有 flush 兜底
resize 重排 150 到 250 毫秒 拖拽边框期间的自然静默
滚动采样 60 到 150 毫秒或一帧 视觉连续性减掉脚本预算
提交防重复 800 到 1500 毫秒 接口 P95 加上双击容差

请求类的 wait 应该看接口 P95 而不是拍脑袋：如果接口平均 400 毫秒返回，250 毫秒的防抖窗口照样会攒出并发请求，这时候该加的是序列号丢弃而不是继续拉长窗口。

引库还是自己写

需要 {leading, trailing} 与 cancel/flush 这套完整语义时，我倾向直接用库：Underscore 1.7.0 单文件、零依赖、体积十几 KB，_.debounce(func, wait, immediate) 与 _.throttle(func, wait, options) 的边界情况（时钟跳变、args 释放、返回值透传）都被社区磨过；lodash 2.4.1 面更广、整包体积也上一个量级，但节流函数上现成的 cancel 与 flush 很实用。反过来两种情况自己写：活动页这类为一个函数背整个库不划算的处境，以及需要库当时没有的行为，比如我给防抖补的 clear。自己写就要配单测，至少覆盖四种选项组合、时钟跳变、卸载取消这三类。放进公共模块后的依赖组织方式，旧文《IIFE 立即执行函数表达式》谈过，此处不展开。

小结

选型时用三问走一遍。第一问：我关心的是”最后一次”还是”每一次”？要最后一次就防抖，要每一次的均匀采样就节流；滚动加载、高频上报属于后者，输入联想、重算布局属于前者。第二问：我能容忍多长的延迟，以及能不能容忍”永远不执行”？用户一直操作时防抖可能一次都不跑，凡是不能接受这一点的（提交、保存），要么开 immediate，要么配 flush。第三问：执行成本是计算还是网络？计算类可以靠 rAF 合并到每帧，网络类必须用时间窗口的节流或防抖，帧率对网络毫无约束力。

再守住三条纪律：执行完把 context 与 args 置空；解绑前先 clear，卸载前 flush；每个元素各自一份实例，事件字段在触发现场取成普通值。防抖和节流的代码都不长，但把”哪一刻执行”想清楚，比抄一个十行函数重要得多。
