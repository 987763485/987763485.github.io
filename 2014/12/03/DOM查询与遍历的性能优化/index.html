DOM 查询与遍历的性能优化

查询与遍历是脚本碰 DOM 的两个最基本动作，也是最容易藏进热路径的两个：一次按键触发几百次全表扫描、一段递归把调用栈吃穿，事故现场往往就出在这两件“看起来不花钱”的事上。《DOM 查询缓存与批量操作》和《DOM 节点类型与节点关系梳理》已经把“查询结果要缓存”“活集合边删边遍历会漏”讲过，本文不重复这些结论，而是把主线换成成本模型与集合语义：一次查询的开销由哪几段构成、live 与静态集合在规范层面差在哪、老 IE 缺失的 Element 系列怎么补、深树遍历在调用栈与显式栈之间怎么选，最后用一张后台表格页的热路径重构把全部方法走一遍。适合维护列表、表格、树类页面的同学，也适合被“IE6-8 到底缺了什么 API”困扰、准备手写兼容层的读者。文中所有数字都按同一把手工计时口径测得，只给相对量级，不编权威数据。

一次查询，开销花在哪

先把一件小事拆开。无论你调的是 getElementById 还是 querySelectorAll，引擎收到的账单都由三段组成：选择器解析、树遍历匹配、结果集合构造。三段各自的比例，才是决定“这次查询贵不贵”的东西。

解析段最简单也最容易被忽略。getElementById 根本没有“选择器”这个概念，参数就是一个键名，解析近似为零；getElementsByTagName 与 getElementsByClassName 只解析一个 token；而 querySelectorAll 必须把整条选择器串喂给选择器解析器，匹配时多数内核采用自右向左的策略——先按最右侧的简单选择器抓出候选节点，再逐个沿祖先链回溯验证左侧条件。这意味着把 #panel td 写成 #panel .detail 之类更深的链式条件，候选集与回溯次数都会变，选择器写得“聪明”通常等于跑得慢。

遍历段决定第二笔账。id 家族是文档级哈希命中；标签与类名家族在有新式索引的内核里走索引，老 IE 更多是裸扫描子树；querySelectorAll 的遍历代价与查询范围（从哪个节点起算）和命中数成正比，这也是后文反复强调“限定容器”的底层理由。另外 querySelector 与全量版的差别在命中第一个就短路返回，“只判断存不存在”的需求用它省掉物化整段，不过判断存在性用活集合的 length 同样不落结果，两种办法的账要到下一次访问才算得清。

但真正的分水岭在第三段：返回集合是 live（动态）还是静态。活集合的构造几乎免费——引擎只交给你一个“查询代理”，不落任何结果；代价是把物化推迟到了每一次访问上，你每读一个下标、每取一次 length，它都要对着当前文档重新核算。静态集合反过来，查询的当下把命中全部物化成一个快照，先付一笔 O(命中数) 的钱，之后每次访问都是数组级的常数开销。所以只取一次结果（判断容器空不空、拿第一个节点），活集合往往更便宜；要完整遍历或者边遍历边改文档，静态集合才是省钱的那个。API 之间“快一个数量级还是差不多”的差别，大半能由这个模型解释，剩下的小半留给内核实现的年代差异。

快照化自己的账单

别把修法一当成免费午餐，它有三笔账。时间账：拷贝是 O(n) 的，每一项还伴随一次跨 JS/DOM 边界的包装对象生成，几千个节点的集合拷一次并不便宜。内存账：快照数组持着全部节点的引用，就算文档早已把它们移走，只要数组还活着，这一棵枯树就回收不掉；在 IE8 上再叠上节点挂着闭包的循环引用问题（expando 的坑旧文讲过），驻留会被放大。正确姿势是“短命快照”：函数作用域里拷、用完即弃，绝不把快照挂到长生命周期的对象属性上。也别忘了反面情形：集合只访问一次、循环体不碰文档，快照就是纯多付的一笔拷贝钱，此时活集合的“按需计算”反而占优——第 1 节那句“只取一次用活集合”说的就是它。最后一笔是失效账：快照与文档脱钩的另一面是快照会过期，重渲染之后再朝旧快照写，操作全部静默落在一个脱离文档的枯枝上，不报错。纪律一句话：快照的存活周期不要超过一次渲染。

自己掐表：本文数字的口径

后文所有“快一个数量级/差不多”都不是抄来的，是下面这个口径测的。先把 2014 年能用的计时工具交代完：performance.now() 在 Chrome 26 起、IE10 起可用，Date.now() 也要 IE9，但目标里既然有 IE8，就只能退化到 +new Date()——毫秒整数，粒度粗，所以每次测量要在一个 trial 里跑内圈若干次再摊平。

几个讲究。为什么取中位数而不是平均数：后台标签页的定时器、GC、系统里别的进程都会把个别轮次拉出长尾，21 轮的中位数比平均值抗噪。为什么要防死代码消除：查询结果如果没有任何消费，新一点的内核真能把 querySelectorAll 整个调用优化掉，测出来“快得离谱”是假象，所以让函数返回一个数值并累加进 sink。为什么预热：第一轮的计时包含了解析与首次求值，跟稳态完全不是一个量级，直接拿首轮说事会高估所有 API。

测量环境三档：物理机 Chrome 39（今年 11 月中旬刚发布的稳定版）、虚拟机里的 IE8、Android 2.3 系统自带浏览器真机。三者对同一份遍历代码的绝对耗时大致差着数量级——Chrome 39 与 IE8 虚拟机之间是一档，Android 2.3 真机上 DOM 对象包装与脚本执行都更贵，又是另一档。正因如此，本文通篇只给相对结论：一个改法只有在最慢那档上快出至少一档量级、同时在 Chrome 上“差不多”，才算立得住；拿最快环境的数字替最慢环境背书，是微基准最常见的骗术。顺带一个环境注脚：Array.prototype.forEach、map 这些方法是 ES5 才有的，IE8 原生没有，bench 的内圈和热路径埋点一律手写 for；为了“测得优雅”先给原型补 forEach 再计时，等于把一层函数调用开销垫进了每一次迭代，数字会被自己污染。jsPerf 这类站内微基准与页面内计时口径的差异、测试间 DOM 残留的污染，旧文交代过，不展开。

查询策略的七个动作

以下每条都是“在什么条件下值一测”的动作，不是背公式。缓存查询结果这件事旧文已经讲透，这里只谈它的边界与更细的选择。

**一、把查询范围从 document 收窄到容器。**同一条 .item，在 #panel 上查和在 document 上查，候选树小了几十倍，成本大致按比例缩。补两个旧文没说的细节：装配中的 detached 子树上查询同样有效，把容器引用作参数传进去，拼装的每个阶段都能就地窄查；另外收窄要收得稳定，容器本身如果被重渲染替换，引用要跟着换，否则查在半截枯树上。

**二、缓存的范围是“一次渲染周期”。**重复查询提到循环外谁都会讲，真正出事的是长期缓存：页面局部重渲染之后，模块级变量里存着的容器还是旧的，后续一切查询都发生在脱离文档的子树上，静默失效。我的做法是把查询结果都挂在“本次渲染的闭包”里，跨周期一律重查，把缓存的生命管理和快照对齐。

三、别在循环里做属性选择器匹配。

[data-x] 这类属性选择器没有任何索引可走，每次都是全范围遍历加逐个比对，放在循环里就是 N 次全表扫描的叠乘。正确姿势见第五条：查一次、自己分组。

四、id 查询最快，但别靠拼接 id 字符串去查。getElementById 的常数成本无可挑剔，坏的用法是把它当索引系统使：'row_' + id 的拼法把正确性押在三件事上——HTML 里 id 命名规范永远不变、数据里的特殊字符不撞上 id 的合法字符集、目标节点此刻就在文档里。任何一条断了，查询返回 null，后链 .cells[0] 当场抛错或者静默跳过。id 查询只配用于页面上那一两个固定锚点（容器、表头）；行与数据的对应，用文末表格页复盘里的行索引缓存来承担。

遍历发生在引擎内部时

nodeType 过滤的成本在哪

childNodes 遍历的开销大头不是判断本身，而是“读出来再扔掉”：每一次按下标取节点，引擎都要为那个节点生成一个跨语言边界的包装对象，你为每个空白文本节点付了完整的价格，只为把它 continue 掉。空白与注释节点的数量取决于 HTML 源码的书写格式——缩进排版的标签间全是文本节点，这在《DOM 节点类型与节点关系梳理》里已经用 tabs 组件实证过。有意思的推论是：线上把 HTML 空白压掉，除了省字节，还实打实削减了 DOM 节点总量，同一套遍历代码在压缩版页面和未压缩版上能测出肉眼可感的差距。判断纪律照旧是 node.nodeType === 1（常量数字，别碰 Node.ELEMENT_NODE，老 IE 读不到），但更省的做法是让查询只命中元素：能走 getElementsByTagName 或 querySelectorAll 拿到的集合，天然不含文本节点。

查询不是纯读。最疼的一类副作用在读写交替：循环里读一次 offsetTop 就逼引擎当场把欠着的布局算干净，原理《浏览器渲染流程详解》讲透了，同型的改造在《DOM 查询缓存与批量操作》里也做过，这里只留最小例子说明“查询侧”该负的那部分责任：

第二个问题问的人多：querySelectorAll 会不会触发样式重算？规范口径上选择器匹配看的是文档与属性层面的信息，不该逼布局同步；但实现口径（我在 IE8 与老 WebKit 上的观察，未读源码不敢咬死）是：连续改 className 之后再立刻查类名选择器，比“改完、隔一拍再查”明显贵，现象上像是查询前把攒着的样式变更先算了账。同一类隐形账还有 innerHTML 的读取——序列化整棵子树，在统计文本的循环里读它，每一轮都是一笔不比布局便宜的开销，能用 textContent 就换掉。保守的工程结论只有一条：写样式、读几何、再查询这三种动作别在同一个循环体里握手，分段排布。

第三个是 matchesSelector 系。事件委托里从 event.target 上溯、逐层做选择器匹配，每次匹配都是一回完整的解析加比对，这份成本在《事件委托减少事件绑定》里测过，不重复。站在查询侧只补一条：上溯循环里先用 nodeType === 1 与 tagName/className 做廉价预筛，把前缀版 matches 留到确权的最后一步，委托的分发账能再薄一层。

最后一个常被忘：遍历里读文本用 textContent（IE9 起）而不是 innerText。innerText 是 IE 与老 WebKit 的私有货，Firefox 到本文时点还没有；它的读取行为要看渲染结果，等于每次读都附带一笔布局税，在“逐格取文本拼接摘要”的循环里这是隐形的大额支出，IE8 上退路是手工沿 nodeType === 3 拼 nodeValue。

复盘：一张表格页的热路径重构

场景：商品管理表格，300 行 × 10 列，行内编辑（改价、改库存）加每 30 秒一次的轮询刷新部分字段。渲染由服务端模板一次吐整表，脚本负责后续更新。翻车的实现是“按绝对下标取单元格”：

行内编辑的实时校验每次 keyup 调一次 refreshCell，轮询一轮则是成百次。按键一下、先做一次三千格的物化，再取一个——Chrome 39 上输入仍算流畅，虚拟机 IE8 上每个按键都卡出肉眼可感的迟滞，Android 2.3 真机开输入法后整页假死。按 bench 的口径拆开计时，瓶颈明确落在 querySelectorAll('td') 这一次构造上：解析与遍历只占小头，三千个包装对象的生成才是主账。

重构分三步，正好把本文的三件套用齐：行索引缓存把“行”从下标计算变成引用命中，行内局部查询把范围从三千格缩到十格，差量更新把写入次数砍到真正变化的格子。

按行找下标用构建时同步写好的普通对象，绝不用 'row_' + id 拼串去 getElementById（动作四的实战位）。需要按字段定位而列序不定时，就在 tr 上做行内查询：tr.querySelector('td[data-field="price"]')，范围十个格子，成本与全表扫描差两个量级的候选集。索引这套东西还有一条维护纪律：rows 与 lastValues 的生命周期必须绑定在同一处——buildRowIndex 重建引用表时顺带展开比对表，轮询写入后即时刷新比对值，整表重渲染则一起作废重建。引用缓存与差量状态分给两拨人各管各的，是这类优化“改完引入新 bug”的头号来源。

改造后的账：编辑每敲一键的开销从“物化三千格”降到“十个格子的比较”，IE8 虚拟机上从肉眼可感的迟滞变成基本无感——快出的不止一个档位；轮询一轮的写入从全表重写缩到变化单元格，Chrome 上本来就差不多，但发热与耗电肉眼可见地收敛。tr.parentNode 那次防御不是白写的：有一回轮询响应早于重渲染完成，旧 rows 还指着被模板引擎换掉的枯 tr，写进去全部静默消失，从此这条防御固定保留——正是“快照过期账”的现场催收。

flowchart TD
    A["每次按键"] --> B["旧 全表查询物化三千格"]
    B --> C["老内核输入迟滞"]
    A --> D["新 行索引取到 tr"]
    D --> E["行内十格差量比较"]
    E --> F["只重写变化的单元格"]

复盘里还有一笔只可意会的账。给单元格文本做拼接摘要时，我用两种走法各测过一轮：tr.children[i] 按下标取第 i 个 td，与从 tr.firstChild 沿 nextSibling 链走到第 i 个，后者在 IE8 上快出一个档位，Chrome 39 上差不多。猜测的方向是老 IE 的 HTMLCollection 下标访问每次重新数位置、而兄弟指针就躺在节点上，但这是未读源码的猜想。写成经验：这是老内核上的实测现象，新内核的下标访问早已是常数成本，别把 firstChild 链照搬进现代代码——那一档优化只在你的慢目标机器上存在。

决策表与三条纪律

按“最低要伺候到哪款浏览器”分三档，把全文收进一张表。先说清这张表的用法：它假设你正坐在 2014 年 12 月的浏览器堆前，IE11 已经铺了一年、Chrome 与 Firefox 仍以月为单位见新；表里的“同左”意思是该 API 的行为在三档之间没有年代包袱，可以直接照抄，凡是写了两种写法的格子，差的正是集合语义或实现完整度，而不是个人口味：

需求 底线 IE8 底线 IE9 仅现代内核
固定锚点取单节点 getElementById 同左 同左
整行取单元格 tr.cells 或行内 querySelectorAll 同左 同左
按类名批量取 querySelectorAll（只 CSS 2.1，防实现 bug） getElementsByClassName（live，想好语义）或 querySelectorAll 同左，边改文档选 querySelectorAll
遍历兄弟元素 childNodes + nodeType === 1，或自写 childrenOf() firstElementChild / nextElementSibling children 快照化后用
节点匹配选择器 自写 tagName/className 比较 msMatchesSelector（IE11 竟又不支持，留手写退路） matches（仍带前缀壳）
树游标遍历 手工栈迭代 TreeWalker 可用，性能按自测 同左
读节点文本 nodeValue 手工拼 textContent textContent

三句话的纪律。第一，先认清集合语义再写循环：活集合配“只读一次”的需求，静态快照配“遍历加改文档”的需求，边改边遍历要么快照要么倒序，快照则管好过期与驻留。第二，热路径的数字只认最慢目标机：中位数、相对档位、预热与防死代码消除三件套一个都不能少，快机器上的“没问题”不是结论，是噪声。第三，老 IE 的 API 缺口用自己那 20 行 ES5 函数补：函数版返回数组、语义可控、不碰 DOM 原型、不引第三方 polyfill 库，出问题断点一下就到底。

小结

把一次查询拆成“解析、遍历、构造”三段之后，绝大多数选择器玄学都消失了：贵的一般不是解析，而是范围没收窄、构造走了错误的语义、或者循环把一次性开销乘成了 N 倍。live 与静态的分别是本文最重的一锤：它决定你的遍历安不安全、快照要不要拷、拷贝的钱和驻留的账怎么摊。计时方法决定其余一切的可信度，中位数加相对档位比任何绝对数字都诚实。最后记住表格页的教训：输入卡顿的账单里，最贵的常常是“顺手查了全表”——行索引、局部查询、差量更新三板斧下去，老内核和新内核第一次得出了同一个结论。
