CSS 层叠、优先级与特异度计算实战

本文属于《HTML 与 CSS》第 20/62 篇
上一篇系列目录下一篇

特异度（specificity）是 CSS 里少数几条能被算出来的规则，但大多数团队只在样式覆盖吵架的时候才想起它。本文想把三件事讲透：层叠到底按什么顺序判定、特异度怎么变成可以进代码审查的数字、以及优先级失控会以什么形式出现在构建产物的字节、加载顺序和线上 bug 里。适合写过两年样式、正在被”我明明改了 CSS 页面没反应”反复消耗的人。读完应该能带走一个能跑的度量脚本、一份 Grunt 门禁配置和七条团队规约。规范口径按 CSS 2.1 第 6 章 Cascading and Inheritance 与 Selectors Level 3 来说，文中所有实测数字都是我们自己样例文件量出来的，别处不要拿去当权威结论。

层叠判定：五个问题与三个高频误解

一条声明能不能最终落到元素上，取决于五个依次追问的问题，顺序不能颠倒。第一问：媒体条件匹配吗？CSS 2.1 在层叠之前先做一次媒体过滤，@media 不匹配的声明直接出局，它连参与比较的资格都没有。第二问：来源与重要级是哪一档？把命中的声明按来源和 !important 排成六档，从低到高依次是 UA 表普通声明、读者表普通声明、作者表普通声明、行内 style 属性、作者表 !important、读者表 !important。第三问：同档里谁的特异度更高？第四问：特异度完全相同时谁写在后面？第五问：元素自己身上有没有任何声明？一条都没有，才轮到继承值；父元素传下来的值不参与上面所有比较。

flowchart TD
  A[收集命中该元素该属性的所有声明] --> B{媒体条件是否匹配}
  B -->|否| Z[声明直接出局]
  B -->|是| C{按来源与重要级分档}
  C -->|只有高档命中| W[该声明胜出]
  C -->|同档多条竞争| D[比特异度 先比 a 再比 b 再比 c]
  D -->|分出高低| W
  D -->|完全相同| E[按声明顺序 后来者胜]
  E --> W
  W --> F[写入该元素的计算值]
  A -->|一条都没有| G[沿树继承 继承值不参与上面的比较]

三个高频误解就埋在这五问里。

误解一：特异度高就一定赢。 错，特异度是第四问，它排在来源与重要级之后。.btn { color: red !important } 与 #nav .btn { color: blue } 打架，赢的是红色，哪怕后者 (1,1,0) 压过前者 (0,1,0)。同理，UA 表的默认样式特异度是零档，随便一条作者规则都能盖掉它，但读者表里的 !important 又能盖掉作者的 !important——无障碍样式表能强制改字号，靠的就是这一条。

误解二：同特异度时”更贴近元素的选择器”赢。 没有这回事。CSS 2.1 在这一层只看声明在样式表里出现的先后，与 DOM 距离、选择器写在哪一个文件里都无关（文件的先后由加载顺序决定，这是下一节的主题）。.a .b 与 .c .d 同为 (0,2,0)，谁在后面谁赢；把它们拆进两个文件、调换两个 <link> 的顺序，胜负就翻转。这个误解的杀伤力在于它让人觉得”我再加一层容器限定就能稳赢”，实际上加的那层只是把特异度堆高，真正的胜负手一直是顺序。

误解三：继承值也参与特异度计算。 不参与。继承的优先级低于元素自身任何一条声明，哪怕那条声明来自 p 这种 (0,0,1) 的类型选择器。父元素 .wrap { color: red } 想把红色传给孩子，只要样式表里存在一条 p { color: green }，段落就是绿的。这条规则解释了为什么”给容器设个颜色想让整块都跟着变”经常失效：容器里每一个元素类型都被基础样式表显式设过颜色，继承一步都走不进去。

顺带补一句 UA 表的位置：链接默认是蓝色，来自 UA 样式表的 a { color: blue }（实际写法常带 :link 与 :visited），它是最低档，所以任何一条作者普通声明都能盖掉它——这就是”给 a 设了颜色立刻就变”的原因，也是为什么很多基础样式表要显式重写链接色。第三问在同档里比：#content .active .link 是 (1,2,0) 最高，.list a.link 是 (0,2,1)，.list li a 是 (0,1,2)，逐位比下来顺序很清楚。第四问在这个例子里用不上，因为没有并列；真正要靠顺序决胜的场景，通常是我们把两个主题写成同分，例如 .skin-blue .list__link--active 与 .is-event .list__link--active 都是 (0,2,0)，谁生效只看谁在文件后面。第五问最简单：这个元素自己身上就有声明，继承通道直接关闭。

顺带把 @import 的位置规则也说清楚：被导入表的声明，整体按”位于导入它的那张表之前”参与层叠。也就是说同特异度时，导入方的规则赢；而 @import 里嵌的那条规则本身必须写在样式表最前面（@charset 之后），否则整条无效。

特异度的计数口径与几个历史怪癖

CSS 2.1 把特异度定义成一个三元组 (a,b,c)，逐位比较，先比 a、再比 b、再比 c。

  • a 位：ID 选择器的个数，#hd 计 1；
  • b 位：类选择器、属性选择器、伪类的个数；
  • c 位：类型选择器（元素名）与伪元素的个数；
  • 不计分的东西：组合符（空格、>、+、~）与通配符 *。

Selectors Level 3 补了两条常被写错的细则。第一，:not() 自身不计分，但它括号里的选择器照常计分——所以 p:not(.a) 是 (0,1,1)，和 p.a 完全同分，胜负只能由顺序决定。第二，双冒号写法是 CSS3 为了区分伪类与伪元素引入的，计分位置没变，伪元素进 c 位；:before 与 ::before 在特异度上是同一回事，IE8 只认单冒号那件事属于匹配层面的兼容问题，旧文《CSS3 伪元素实战技巧》里讲透了，本文不重复。

还有一条不在计数规则里但常被忽略：行内 style 属性不是 (1,0,0) 而是”作者源里高于任何选择器”。CSS 2.1 明确它压过任何作者表规则，但压不过作者表的 !important。这一条是下一节那个线上事故的根源。

旧 IE 上的几笔账

这些写法在 2014 年仍然要背着，因为它们会改变”谁赢”的结论。

属性选择器与类同档。 IE7 及更早的实现把 [attr] 和 .class 一起计入 b 位，这点和标准一致；坑在匹配层——不带类型前缀的 [title] 在 IE6 上根本不识别，写成 *[title] 或 div[title] 才有行为，而 IE7 对部分属性值的大小写处理又不一致。于是”靠一条属性选择器压过类”的覆盖链，在 IE 上不是输在特异度，而是整条规则直接不参与竞争。

IE6 的 !important 双写 hack。 IE6 在同一条规则里遇到重复声明时，会忽略 !important 直接让后写的那条赢，于是当年流传这样一个 hack：

今天回头看，它把一个规范层的优先级问题变成了浏览器 bug 的利用，读代码的人只要不知道这个 bug 就会得出”我的 !important 失效了”的错误结论。同类写法还有 *width（IE7 及以下）与 _width（IE6）的属性前缀 hack，以及 filter: progid:DXImageTransform.Microsoft.gradient(startColorstr='#fff', endColorstr='#ccc')。最后这个要单独说明：filter 和 -webkit-filter 是两个不同的属性，标准内核读到 filter: progid:... 会按”无法识别的值”把整条声明丢掉，所以它们之间不存在覆盖关系——这一点和下一节 overflow 的判断题有关。作为历史坑记录，不要当最佳实践用。

IE6 的多 class 匹配 bug。 div.a.b 在 IE6 里只按最后一个类名匹配，等价于把它降级成 (0,1,0) 的单类；我们项目里出现过”同一份 CSS 在 IE6 上命中范围比预期大一圈”的怪事，最后追到这里。当时靠把两个类拆成后代关系绕过，代价是多一层结构耦合。

这套正则法会算错什么

诚实地列出四类已知错误，用之前要心里有数。第一，:not(:nth-child(2)) 这种括号嵌套，[^)]* 会在第一个右括号处截断，内部少计一层。第二，:not(.a, .b) 这种多参数写法在 Selectors Level 3 里本来非法，多参数属于 Level 4 草案的讨论范围，而我的正则会把两个类都累加成 (0,2,0)，比任何一种实现都高。第三，属性值里带右括号（[title="a]b"]）会把规则劈成两半。第四，命名空间写法（svg|rect）恰好能对上，但它依赖的是巧合而不是解析。

更要紧的是 score 这个数值本身有系统性偏差：十进制加权会串档。(0,11,0) 算出 110，(1,0,0) 算出 100，于是”十一个类”在数值上压过了”一个 id”，而规范判定恰好相反。所以 score 只能用来给全项目的规则分桶排序、看分布是否畸形，任何胜负判定必须回到三元组逐位比较。2014 年这个时间点，我没有找到可以放心依赖的选择器解析库——GitHub 上能搜到的同类实现（比如 Keegan Street 那个 specificity 仓库）走的也是正则路线，同样有这些边界。真需要确定答案时，最朴素也最可靠的做法是造两条规则让浏览器自己裁决：

代价二：加载顺序与第三方组件

层叠的第四问是”谁写在后面”，而”后面”由资源的加载顺序决定，于是优先级治理里有一半是构建与模板的问题。

第一个坑是 @import。它把本可以并行的样式表变成一条串行瀑布：引擎必须先拿到外层表、解析到那条 @import，才知道要请求内层表。按我们项目 2014 年 11 月那批 CDN 日志的均值口径（单个 CSS 请求约 180 ms 网络时间、解析约 20 ms），三级 @import 链要 600 ms 出头，而三张平铺的 <link> 并行下来约 200 ms；更要命的是渲染阻塞要等整条链解析完才解除。

  participant BR as 浏览器
  participant A as 主样式表
  participant B as 被导入表
  participant C as 二级被导入表
  BR->>A: 请求并下载
  A->>B: 解析到 import 才发起请求

第二个坑是顺序本身。很多项目把 reset.css 放最前面，觉得”我压在所有样式之下”是它在兜底，实际上这句话反过来才成立：只要两条规则的特异度相同，后加载那一张表里的声明就赢，而 reset 里的规则大多是最浅的形状。当页面引入第三方组件（当时最常见的是日历与富文本编辑器）且它的样式表由 CMS 插在你的业务表之后，它的 .title、.btn 就会覆盖你的同名类——这类”页面上一小块样式莫名变了”的事故，根因通常不是特异度算错，是顺序。所以第一条纪律是顺序即优先级：reset、基础组件、业务、第三方、主题覆盖，按这个次序排 <link>；能合并成一张表就用构建工具合并，别再靠 @import 表达分层。

当第三方必须在先（脚本注入的样式表位置你控制不了）时，不要靠 !important 筑墙——对方升级改一条规则，你就得跟着加一条更重的墙。正确工具是命名隔离：自己的类统一加项目前缀（我们当时用 .pn-），把同名冲突从”顺序问题”降级成”选择器根本不相交”。全局重置该怎么写，旧文《CSS3 box-sizing 与全局重置样式》里给过完整方案，这里不展开。

治理：一层 class 与命名约定

前面把病说完了，这一节给药。核心策略是把状态从结构里拿出来，做成同档位的类，让它们根本不竞争。BEM 那套 block__elem--modifier 命名在我们项目已经落地半年，它的价值在特异度上非常好解释：所有名字都只有一层类，全部落在 b 位，彼此之间靠”是否命中”区分而不是靠数值压制。

原来是三条覆盖规则，靠顺序和特异度硬拼：

状态挂在哪、主题挂在哪

一层 class 策略要成立，还差一条容易漏的约定：状态类挂在被着色的那个元素上，主题类挂在最近的稳定容器上。这两个落点定下来，is-active 与 skin-blue 才不会出现”我要覆盖它，但它的类在兄弟节点上”的僵局。我们当时给列表类组件定下的矩阵是这样：

变化来源 类名形状 落点 特异度
组件基态 list__link 链接自身 (0,1,0)
交互状态 is-active、is-disabled 元素自身 (0,1,0)
组件变体 list__link--compact 元素自身 (0,1,0)
页面主题 skin-blue、is-event body 或页面容器 (0,2,0)
断点差异 同名类写进 @media 不变 同基态

只有”页面主题”这一行因为带上祖先类而升到 (0,2,0)，其余全部同档，靠命中与否决胜。这张表同时充当 review 的判断依据：看到 (0,3,0) 以上的规则，基本可以断定有人把状态挂到了祖先节点上；看到 (1,x,y)，就直接进上面那个门禁的告警清单。

兜底：什么时候允许提高特异度

只承认三类例外，其余一律走类名与顺序。第一，覆盖第三方组件：对方的类名你改不动、顺序也可能在你之前，这时允许写更深的选择器，但必须写在专门的 override-vendor.css 里，并在文件头注释对方组件与版本号——对方升级时这个文件是第一波回归测试对象。第二，邮件模板：2014 年的邮件客户端里，<style> 标签与类选择器被支持的面积太小，正文样式基本只能靠行内 style 属性写死，这是行内样式唯一该由”人手写”的场景；同时不要指望 !important，我们当时实测以 Word 为渲染引擎的 Outlook 2007/2010 会把它丢掉。这个方向上还有一条类似的”规则不站你这边”的窄场景，见旧文《CSS 打印样式表 print 实践》。第三，常驻工具类：.hidden、.is-loading 这类声明”任何条件下都要生效”的规则，可以带 !important，但必须进上面的白名单登记，未登记的一律当失败处理。

两笔分开的账：特异度与重算范围

层叠与继承发生在样式重算阶段（流水线上那一环在旧文《浏览器渲染流程详解》里讲过，这里不重讲 CSSOM 构建）。必须把两笔账分开：特异度决定”谁赢”，重算范围决定”有多少元素要重新问一遍”。前者是可维护性成本，后者才是每帧的毫秒成本；把两者混在一起谈，是这类讨论最常犯的错。至于选择器的匹配方向、长度与速度之间那些流传很广的说法，我十一天前在《CSS 选择器性能误区》里已经逐条量过，本文不再重复。

定性结论（不给具体毫秒，这台机器上的量级差异太小、也不稳定）：几个属性总是一起变时，写法 B 明显更划算——一次改动只让该元素及其相关子树被标记一次，而且这些规则全部在样式表里、能被上面那个门禁审到。写法 A 的真实问题不止是多次失效：行内声明游离在所有静态审查之外，构建产物里看不到它，特异度检查脚本也扫不到它，半年后没人知道这个颜色是谁写的。反过来，如果只改一个一次性属性、且这个值确实由运行时数据算出（比如拖拽后的坐标），直接写行内是合理的，不必为了”统一”把它塞进一个动态生成的 <style> 里。

两笔账在排查时也有各自的入口，别用错工具。查”谁赢”这件事，用 Elements 面板看 Styles 列表就够：被层叠掉的声明会显示成划掉的样式，鼠标悬停能看到胜出规则的选择器与它来自哪一个文件第几行，绝大多数”改了没反应”的工单在这一步就能定位到是顺序还是档位。查”重算了多少”就必须换到 Timeline，看一次交互里 Recalculate Style 与 Layout 各出现几根柱子、分别由哪一行脚本触发。前者是样式表的问题，后者是代码的问题；把 Timeline 的数据拿去论证”应该把选择器剪短”，或者拿 Styles 面板的截图去论证”页面卡”，都是走错了门。

十道判断题

下面十组片段，先自己想答案再看解释。除特别说明外，都按 CSS 2.1 与 Selectors Level 3 判定。

一、.a 同时带 id 容器时是什么颜色？红色。!important 在分档上就赢，特异度根本没轮到。

二、这两条会不会打架？不会。p:not(.x) 与 p.x 确实同分（都是 (0,1,1)，:not 自身不计分、括号里的类照计），但同一个元素不可能同时满足两者——:not(.x) 的语义正好排掉带 .x 的那个。这题的陷阱在选择器语义不在计数。

三、绿色。作者表的 !important 在档位上高于行内，行内又高于任何作者选择器；只有在没有 !important 参与时，行内才是不可战胜的那一个。

四、背景变图片，红色没了。简写属性会把没写的组成分量重置为初值，background 里的 background-color 初值是 transparent。把两条顺序调换则红色保住——这就是”同特异度只看顺序”最直观的例子。

五、段落是绿的。继承不参与特异度比较，p 这种最低限度的声明也压得过从父元素传下来的值；想让继承生效，得先把基础样式表里那条 p 的颜色限定改掉。

六、(0,3,3)：b 位三个（.nav、:first-child、:hover），c 位三个（li、a、::after）。伪元素只进 c 位，不进 b 位；写成单冒号的 :after 结果一样，双冒号只是 CSS3 的语义区分。

七、标准浏览器里蓝色还是红色？红色。input[type="text"] 是 b=1（属性选择器）加 c=1（类型选择器），得 (0,1,1)；.field 只有 b=1，得 (0,1,0)。别把”属性选择器和类同档”记成”属性选择器等于类”，前者多带的那个类型选择器仍在 c 位上。IE6 里答案翻成蓝色——那条属性选择器在 IE6 要么不匹配、要么匹配范围与预期不符，整条规则不参与竞争，特异度再高也没有意义。IE7 则更微妙：它把 [attr] 与 .class 记在同一档（这一点和标准一致），可它对属性值的匹配本身有缺陷，于是只看计数的人会以为两条”打平、由顺序决定”，实际结果却由浏览器的匹配 bug 决定。稳妥的写法是给输入框补一个类名，让规则同分同形、由顺序决胜，这样所有引擎给出同一个答案。

八、四条全部”和平共处”：overflow 与 -webkit-overflow-scrolling、filter 与 -webkit-filter 都是不同的属性名，属性名不同就不存在覆盖，各自被认得的引擎收走。带前缀的私有属性在别的引擎里按无法识别的属性整条丢弃，这是 CSS 前向兼容解析的规定。

九、蓝色。ul li 是 (0,0,2)，.list li 是 (0,1,1)，比到 b 位就分出胜负，两条的先后顺序在这里完全不参与。这一题是给”层级写得深看起来更具体”的直觉泼冷水的：两个类型选择器加起来也换不到一个类。把 .list li 挪到文件最前面，结果仍然是蓝色。

十、#hd li:first-child a 与 #hd .list a.link 谁赢？前者 (1,1,2)，后者 (1,2,1)，a 位打平之后比 b 位，后者赢——前者 c 位更多却毫无用处，逐位比较不会因为低位堆得多就翻盘。给第一条加一个 :hover，变成 (1,2,2)，b 位打平、轮到 c 位，第一条反过来赢；给第二条加 :hover 则变 (1,3,1)，它赢得更干脆。同一处改动落到 a、b、c 三个位上的效果完全不同，这正是”手数容易看走眼、要么用脚本要么用浏览器”的原因：审查时真正要问的不是”这条比那条长”，而是”哪一位先分出高低”。

小结

给一份能直接抄进团队 wiki 的 CSS 优先级规约，共七条。第一，默认单层类名，状态用 modifier 类表达，不允许出现三层以上后代链。第二，覆盖必须注释原因，写下”覆盖哪条规则、为什么只能这样覆盖”，评审时只看这一行就够。第三，!important 只用于第三方隔离与常驻工具类，且要登记白名单，未登记的构建失败。第四，行内样式只由 JS 写，人手写的行内样式一律 review 不过（邮件模板是唯一例外，写进模板规范）。第五，@import 禁用于首屏样式，分层用构建合并而不是导入表达，顺序由 <link> 显式控制。第六，特异度检查脚本入门禁，盯两个指标：>=100 档的条数与未登记 !important 条数，前者归零、后者为空才算干净。第七，命名带状态前缀 is-，让”这是状态”在代码里可读，比任何约定都省事。

再往前看一句：层叠与特异度的规则本身这几年变化不多，CSS Cascading Level 3 的草案今年才把来源与重要级这套判定重新写成更明确的文字，等它落地，本文的分档口径可能要修一次；但”把优先级当成本、把度量进门禁”这条思路不会跟着规范版本过期。所有结论都要在自己的页面上量一遍——包括本文这些数字。
