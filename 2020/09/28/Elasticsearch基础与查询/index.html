Elasticsearch 基础与查询

很多团队第一次接触 Elasticsearch 是从日志检索开始的：把 JSON 丢进去，写几个查询就能全文搜索。但真正用起来之后，问题往往出在基础概念上——为什么刚写入的数据查不到，为什么 term 查询匹配不上，为什么翻到很深的页码就报错。本文从存储模型、分词与 Mapping 讲起，再落到 Query DSL、分页与聚合，最后用一个订单索引的例子把常用写法串起来，适合已经能启动集群、但还没系统理解查询语义的读者。

从 Lucene 到 Elasticsearch

Elasticsearch（下文简称 ES）是一个基于 Lucene 构建的分布式搜索与分析引擎，对外提供 RESTful 接口，用 JSON 文档描述数据。Lucene 本身只是一个 Java 搜索库，擅长倒排索引与打分，但不负责分布式、副本与故障转移；ES 在它之上补上了分片、副本、集群状态管理和聚合框架，才成为一个可以横向扩展的服务。截至 2020 年，7.x 是主流版本，本文示例基于 7.8 与 7.9。

几个概念需要先分清。索引（index）是逻辑上的文档集合，类似关系库中的表；文档（document）是一条 JSON 记录，类似一行；字段（field）是文档中的键值。索引在物理上被切成若干分片（shard），每个分片是一个完整的 Lucene 索引；每个分片还可以有副本（replica）。主分片数量在创建时就固定，副本数可以随时调整，这是后面做容量规划时绕不开的约束（分片与副本的调优在另一篇展开）。

ES 的写入是近实时的。文档写入后先进入内存缓冲与 translog，默认每秒执行一次 refresh，把缓冲生成新的 Lucene segment 并打开供搜索，所以从写入到可被搜索通常有约 1 秒的延迟。refresh 不等于持久化：真正保证不丢数据的是 translog 的落盘与之后的 flush。这一点直接影响使用方式——写完立刻按条件查询可能查不到，但按 _id 的 GET 是实时的，因为它直接读 translog。

还有一句常被忽略的话：ES 不是主数据库。它没有跨文档事务，不支持 join，副本之间的可见性存在延迟，mapping 一旦写错，修改成本很高。合理的定位是“可重建的检索与统计副本”，原始数据仍应落在 MySQL 或对象存储里。

倒排索引与分词

传统数据库为每行建 B+ 树，按主键或索引列查找；全文搜索要回答的是“哪些文档包含这个词”，正排结构只能逐条扫描。倒排索引反过来记录“词项 → 文档列表”：每个词项对应一条 posting list，里面是文档编号，通常还带词频与位置信息，位置用于短语查询和高亮。查询时先分词得到词项，再在 posting list 上求交并，代价与命中数量相关，而不是与文档总量线性相关。

写入时文档要经过分析链（analysis）才会进入倒排索引，大致是字符过滤、分词器（tokenizer）、词项过滤（token filter）三步。以标准分析器为例，它按 Unicode 规则切词、转小写、去掉标点，"Elasticsearch 7.9" 会被切成 elasticsearch 与 7.9。中文是难点：标准分析器把中文按单字切分，“订单查询”变成“订”“单”“查”“询”四个词项，召回尚可但精度很差。社区常用 IK 分词插件，提供 ik_smart 与 ik_max_word 两种分析器，前者粗粒度、后者细粒度；插件需要装在所有节点上并重启，版本必须与 ES 严格对应，否则节点无法启动。如果不方便装插件，也可以退一步：用 keyword 存原文，在应用层切词后写入一个额外的字段。

分析结果决定查询能否命中，因此要区分 text 与 keyword。text 会被分析，适合全文检索，但它保存的是词项，不能直接用来排序或聚合；keyword 不做分析，整串原样存储，适合精确匹配、排序、聚合，例如状态码、用户名、URL。常见做法是给同一个字段配多字段（multi-fields）：

另外两个字段容易被误解。_source 保存写入时的原始 JSON，默认开启，取文档、reindex、局部更新都依赖它；关掉能省磁盘，但会失去这些能力。doc_values 是磁盘上的列式存储，keyword、数值、日期类型默认开启，排序和聚合靠它完成；text 字段默认不开，因为需要 fielddata 把词项加载进堆内存，代价太大，所以对 text 排序通常是个错误。

Mapping：字段类型与索引管理

mapping 是索引的“表结构”，决定字段如何被分析、索引和存储。不写 mapping 时 ES 会动态推断：字符串默认映射成 text 并附带一个 keyword 子字段，整数按数值范围猜成 long 或 integer，能被日期格式解析的字符串猜成 date。动态 mapping 上手快，风险在于“第一条文档决定结构”——同一个字段先来了数字、后来了带单位的字符串，后续写入就会抛 mapper_parsing_exception，只能重建索引。

因此生产环境建议显式声明 mapping，只让确认过的字段进入索引。常用类型有 text（分词，用于全文检索）、keyword（精确值，用于排序聚合）、date（可指定 format）、integer 与 long、boolean、object、nested。object 的内部字段会被“拍平”，对象数组里各元素的字段对应关系会丢失；需要保留元素内部关联时用 nested，代价是查询要写成 nested 子查询，写入也更重。

这段定义里有几处细节。index: false 表示字段仍保存在 _source 中、可以取回，但不建索引、不能搜索，适合内部备注、手机号这类只展示不检索的字段；ignore_above 让超长值不被索引，避免个别异常字符串撑大索引；scaled_float 用整数存小数，比 double 省空间。上面的 items 只写了类型，实际使用还应展开成 properties。

另一个风险是 mapping 爆炸：若把用户自定义属性直接当字段名写入（例如 tags 下挂成千上万个键），字段总数会暴涨，集群状态随之变大，写入与恢复都会变慢。7.x 默认 index.mapping.total_fields.limit 为 1000，超出后新字段会被拒绝。对策是用 dynamic templates 规定“匹配某命名模式的字段一律映射成 keyword”，或者对不需要检索的子树用 enabled: false 整体跳过。

索引管理的核心约束是：主分片数创建后不能改（改只能 reindex 或 shrink），所以通常给物理索引起带日期的名字（如 orders-2020.09），再建一个别名 orders 指向它。需要调整 mapping 时，新建索引、用 _reindex 灌数据、再原子地把别名切过去，应用侧无需改配置。日常巡检靠 _cat 系列接口：_cat/indices?v 看文档数与存储大小，_cat/shards?v 看分片分布，_cat/aliases?v 看别名指向。

Query DSL：查询与过滤

ES 的查询用 JSON 表达，分叶子查询（match、term、range 等）与复合查询（bool 等）。最需要建立的条件反射是：这个查询条件会不会经过分析器。

match 把输入交给字段的分析器，再与倒排索引里的词项匹配，所以用 match 搜“退款 订单”能命中备注中只含“退款”的文档，默认是 or 关系，可用 operator 改成 and。term 不做分析，拿原值直接查词项，只适合 keyword、数值、日期这类未被分析的字段；对 text 字段用 term 查一个词组，除非它恰好被切成同一个词项，否则永远查不到。

range 支持数值与日期，日期可写 now-7d/d 这类表达式；exists 判断字段是否存在；match_phrase 要求词项按顺序相邻出现，slop 允许中间隔几个词；multi_match 把一个关键词同时打到多个字段，默认 best_fields 取最高分，cross_fields 则把多个字段视为一个整体，适合姓名、地址这类被拆开的字段。bool 是组合的主力：must 与 should 参与打分，filter 只过滤不算分，must_not 排除。有个细节常被忽略：只含 filter 与 must_not 的 bool，默认 minimum_should_match 为 0；一旦出现 must 或 filter，should 就退化为加分项，需要时得显式指定。

filter 上下文与 query 上下文的区别值得单独记住：query 上下文计算 _score，用于相关性排序；filter 上下文只回答“是否命中”，不计算分数，结果还能被缓存成位图，重复执行很快。实践原则是——影响“像不像”的条件放 must，纯粹的是非条件放 filter。状态、时间范围、租户 ID 这类条件都应放进 filter。

排序、分页与相关性

不指定排序时，ES 按 _score 倒序返回。7.x 默认的 BM25 取代了早期的 TF-IDF，核心仍是词频、逆文档频率与字段长度归一化：词出现得越多、在整个索引里越罕见、字段越短，得分越高。想让某个字段更重要，可以在查询里用 boost 加权；想弄清分数从哪来，加 "explain": true 看每个子查询的贡献。更复杂的排序（按销量、按时间衰减、随机加权）用 function_score 组合，但多数场景下先用 filter 缩小范围、再按字段排序更简单可靠。

按字段排序依赖 doc_values，keyword、数值、日期都没问题；对 text 排序会报 fielddata 错误，正确做法是排 字段.raw。按字段排序后分数通常不再参与比较，可以加 track_scores: false 省掉打分开销。分页用 from 与 size，深分页的代价却很高：协调节点要把每个分片上的 from+size 条结果取回再归并，from 越大，被丢弃的文档越多，内存与网络开销随之上升；index.max_result_window 默认 10000，超过直接报错。

遍历全量数据用 scroll：它生成快照上下文、按批返回，适合后台导出，不适合交互式翻页，因为快照期间新写入不可见，上下文也占资源。面向用户的“下一页”更适合 search_after：传入上一页最后一条的排序值，从该位置继续取，不依赖偏移量，代价稳定；排序里必须带一个唯一字段作为决胜条件。

聚合：把检索结果当数据分析

聚合在 query 筛出的文档集上执行：先过滤，再统计。常用的是指标聚合（avg、sum、min、max、cardinality）、桶聚合（terms、date_histogram、range），以及桶里再套桶的嵌套聚合。size: 0 表示不要命中文档、只要聚合结果，能省掉取 _source 的开销。

几个限制要记住。terms 默认只返回前 10 个桶，调大 size 能多取，但协调节点要合并各分片的前 N 名，N 越大越贵；桶默认按文档数排序，也可按子聚合排序。聚合字段必须是 keyword 或数值，对 text 聚合会直接报错。cardinality 是近似去重，底层用 HyperLogLog，调高 precision_threshold 能提升精度，但仍不是精确值。date_histogram 在 7.x 用 calendar_interval 与 fixed_interval 取代旧的 interval，按天、按月统计应使用前者。管道聚合在桶结果上再计算，例如 derivative 求环比、bucket_script 做自定义运算，适合把趋势直接算在 ES 侧。

几个反复出现的坑

  • text 与 keyword 混用：对 text 做 term 查询会查不到，做排序或聚合则报 fielddata 错误，应改用 .raw 子字段。
  • 动态 mapping 冲突：同一字段先写入数字、后写入字符串，或同名索引间类型不一致，后续写入失败。上线前固定 mapping 并保持跨索引一致。
  • 深分页：from 很大时开销骤增，超过 max_result_window 直接报错，应换用 search_after。
  • 前导通配：*keyword 这类查询无法利用倒排索引，只能扫描词项，应改成前缀查询或提前做 ngram 分词。
  • 刷新预期：写完立刻查不到属于正常现象，测试脚本要么等待 refresh，要么用 refresh=wait_for。
  • 把 ES 当唯一数据源：索引可能被误删、mapping 可能重建，原始数据必须在关系库或对象存储留底。

小结

ES 的能力来自倒排索引，理解它的前提是理解分析与 mapping：字段是 text 还是 keyword，决定了你能用 match 还是 term、能不能排序和聚合。查询时把精确条件放进 filter，把真正影响相关性的条件放进 must，既能拿到合理分数，也能享受过滤缓存。分页要避开深 from，遍历用 scroll、连续翻页用 search_after；聚合时记得 size: 0，并优先在 keyword 子字段上做桶。最后，把 ES 当作可重建的检索副本，原始数据留在主库，很多“玄学问题”都会消失。
