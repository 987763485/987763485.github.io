数据库设计三范式与反范式

很多团队的第一版表结构，都是把页面上的字段直接摞进一张宽表；上线三个月后，才开始出现“改一个客户地址要更新几十行”这类问题。本文先说明函数依赖与候选键，再依次拆解第一范式到第三范式以及 BCNF，最后讨论什么时候该主动反范式。

范式要解决的问题

先看一张典型的“订单宽表”，它把订单、客户、商品、分类四类信息塞进了同一张表：

一个订单买三件商品就有三行，客户资料、订单状态在每行里重复一遍。重复本身不算错，错在把“客户是谁”和“这一单买了什么”绑在了一起。

更新异常：客户换手机号，要把该客户所有历史行都改一遍。只要有一条路径漏掉（批量导入、手工修数据、只更新当前订单的接口），同一个客户在不同订单里就会出现两个号码。

插入异常：刚签约、还没下单的客户没有 order_id，资料无处安放，常见的妥协是造一条金额为零的占位订单。

删除异常：客户只下过一单，订单取消后删掉这行，客户档案、联系人一起消失。删一条业务记录，顺带销毁了另一条无关的事实。

三类异常背后是同一件事：一个事实被存放在多行里，行的存亡却由另一个实体决定。范式就是把“一个事实只存一处”翻译成可检查的规则；它约束的不是表的数量，而是函数依赖的摆放位置。

函数依赖与候选键

判断一张表处在第几范式，先要说清两件事：谁能唯一确定一行，哪些列由哪些列决定。

函数依赖的定义很朴素：如果任意两行在属性集 X 上取值相同，它们在 Y 上也必然相同，就说 X 函数决定 Y，记作 X → Y。换成大白话，“知道 X 就能唯一确定 Y”。订单明细上成立的关系大致是：

  • order_id, line_no → product_id, qty, unit_price：订单号加行号确定一行明细
  • order_id → customer_id, status, created_at：订单号确定下单人与状态
  • customer_id → customer_name, customer_phone：客户编号确定客户资料
  • product_id → product_name, category_id，category_id → category_name：商品与分类各归各的键

候选键是能唯一确定一行、且不含多余属性的属性集。明细表的候选键是 (order_id, line_no)：order_id 单独不行，一单有多行；加上 product_id 也能唯一确定，但多余，不满足最小性。主键是挑一个候选键，不属于任何候选键的属性叫非主属性。

在此基础上，两种“坏形状”可以精确描述。若 X → Y，而 X 只是复合候选键的真子集，称 Y 部分依赖于候选键；若 X → Y 且 Y → Z，而 Y 不是候选键，称 Z 传递依赖于 X。前者的典型是明细表里塞了商品名称，后者的典型是商品表里塞了分类名称。

这里有个前提容易被忽略：函数依赖来自业务规则，不是从数据样本里“发现”的。表里恰好没有重名，不代表姓名能决定工号。设计阶段应拿依赖清单去和业务确认，而不是 SELECT 一遍看看有没有重复；规则错了，后面拆得再干净也是白拆。

第一范式：原子值与重复组

第一范式（1NF）的要求只有一句：每个字段都是原子值，不可再分，也不允许出现重复组。

落到日常设计里就是三件事：一个字段不存多个值，比如 phone 里写 13800000000,13900000000；不把结构编码进字符串，比如 product_ids 里写 1001,1002,1003；不用列名做下标，比如 item1_name、item2_name 一路排到 item9_name。后两种是同一个毛病：用分隔符或列的位置模拟“多行”。

为什么这是坏味道？

  • 无法按单个值查询。找买过商品 1001 的订单只能 LIKE '%1001%'，会把 10010、21001 一起捞出来；改成 LIKE '%,1001,%' 又会漏掉首尾。
  • 无法建有效索引，B+Tree 对整个字符串起作用，查中间某个 ID 必然全表扫描；外键与唯一约束也无从谈起，写一个不存在的 ID 照样能存进去。
  • 更新一个值要读整串、拆分、改一个元素、再拼回去，并发改同一行时后写的会整串覆盖前一个。
  • 统计口径全靠应用代码，“每个商品被多少订单购买”在 SQL 里写不出来。

正确做法是把多值拆成多行：订单商品放进 order_items，一个商品一行；客户有多个电话就建 customer_phones(customer_id, phone_type, phone)，用 phone_type 区分手机与座机。这样每个值都能被索引、约束、聚合，写入也只影响一行。

MySQL 5.7 起提供了 JSON 类型，有人据此认为 1NF 过时了。这个理解是反的：JSON 列适合整体读写的扩展属性，一旦你要按其中字段过滤、排序、加唯一约束，它就已经是一个实体，应该建表。

第二范式：复合主键上的部分依赖

第二范式（2NF）在 1NF 的基础上，要求所有非主属性都完全依赖于候选键，不能只依赖复合键的一部分。

单列主键的表天然满足 2NF，问题几乎总出现在复合主键的关联表上，订单明细最典型：

主键是 (order_id, product_id)。qty 与 unit_price 需要两个键一起才能确定，属于完全依赖；product_name、category_name 只由 product_id 就能确定，与 order_id 无关，这就是部分依赖。

后果和上一节的三类异常一一对应：名称在每行重复，改名要更新全表，中途失败还会留下半新半旧的值；新品没人下单就没地方存；删掉最后一条明细，商品档案随之消失；也没有约束能阻止两行出现不同的商品名。

注意 unit_price 留在了明细表，没有跟着商品走。这不是漏拆，而是业务事实不同：商品表的 price 是“现在卖多少钱”，明细里的 unit_price 是“当时成交多少钱”。混为一谈，订单一改价，历史金额全部跟着变，财务对账立刻出问题。判断部分依赖不能只看列名，要看它描述的是哪个实体的事实。

第三范式与 BCNF

第三范式（3NF）：非主属性不能传递依赖于候选键，只能直接依赖键。

假如商品表长成 products(product_id, product_name, category_id, category_name)，product_id 决定 category_id，后者又决定 category_name，分类名就传递依赖于主键。同一分类下的两万个商品，分类名重复两万次；改名要批量更新，中途失败还会同时留下新旧两个名字。拆出 categories(category_id, category_name, parent_id)，商品表只留 category_id。

状态字段同理。orders.status 直接存 'paid'、'shipped' 这样的字符串，改一句文案就得改数据。常见做法有三种：建 order_status 查表最规范；TINYINT 加应用层常量最轻量，代价是改状态要发版；ENUM 看着省事，增删值却要 ALTER TABLE。选哪种取决于状态是否要运营配置，但别让状态值散落在代码各处。

BCNF 更严：所有决定因素都必须是候选键，针对的是 3NF 的盲区，即主属性之间的依赖。经典例子是选课表 (student_id, course_id, teacher_id)，规则为“一个学生的一门课只由一位老师教”且“一位老师只教一门课”，于是 teacher_id 决定 course_id。候选键是 (student_id, course_id) 与 (student_id, teacher_id)，teacher_id 不是候选键，所以它满足 3NF 却不满足 BCNF。拆开可解，代价是多一次连接，而且这条规则未必稳定。

所以多数团队做到 3NF 就停手：BCNF 的分解不保证保持函数依赖，规则一变就要重拆，多出的连接在 OLTP 里是实打实的开销。范式是分析工具，不是必须打满的关卡。

一次完整的拆分：从宽表到五张表

把前面的规则串起来，对 orders_wide 做一次完整拆分：沿用上一节的依赖清单，按“源头”归并实体，得到五张表：

flowchart LR
  C[categories] --> P[products]
  CU[customers] --> O[orders]
  O --> I[order_items]
  P --> I

拆分前后的差别，按异常逐条对照：

场景 宽表 五张表
客户换手机号 更新该客户所有订单行，易漏改 只改 customers 一行
新增未下单客户 无处存放，需造假订单 直接插 customers
删除最后一个订单 客户资料一并消失 customers 不受影响
商品改名 扫描并更新所有历史订单行 只改 products 一行

表里有两处有意为之的冗余：order_items.product_name 与 orders 的收货信息。它们不是抄过来忘了删，而是下单那一刻的事实快照：商品后来改名、客户后来搬家，都不该改变历史订单的展示内容。判断冗余该不该留，标准是它记录当前状态还是当时状态，而不是能不能推导。

orders.total_amount 属于另一类，记录当前状态，可由明细求和。留着它是为了列表页不必每次聚合，但必须同步维护，否则会出现“明细加起来 199，订单显示 189”的事故。

反范式：拿一致性换什么

反范式不是“不设计”，而是在明确知道代价的前提下，主动把某条依赖复制一份。常见动机有四类。

其一是读写比失衡。商品详情页读多写少，关联几乎不变，把分类名冗余进读表能省一次连接。其二是列表页的批量关联。订单列表要显示客户昵称，逐行查客户表就是 N+1，20 行数据 21 次查询，不如一次 IN 批量取回。其三是计数与汇总。帖子列表显示评论数，每次 COUNT(*) 都扫一遍评论表，改成维护 comment_count 就只读一行。其四是历史快照与报表宽表。

冗余一旦落地，一致性问题就跟着来。常见有四条路：

手段 一致性 代价
同一事务内写两处 强一致 锁范围变大、写放大，热点行容易冲突
触发器维护 强一致，对应用透明 逻辑隐式，排查困难，容易和批量操作打架
应用层异步更新 最终一致 消息丢失或重复就漂移，需要幂等与重试
定时对账修复 最终一致，兜底 有延迟，且要先能写出正确的对账 SQL

选哪一种，取决于读错的后果有多严重。商品销量少统计一次，用户几乎无感，异步加对账就够了；账户余额多算一分钱，就必须放进同一个事务。无论选哪种，都要能回答三个问题：谁负责写、失败时怎么补偿、怎么发现它已经不一致。

反范式要有度量：先用慢查询日志和执行计划证明连接或聚合确实是瓶颈，再动手冗余；没有测量数据的“优化”，多半只是把复杂度提前预支了。

从 OLTP 到 OLAP

事务库和分析场景对表结构的要求几乎相反。OLTP 按主键取一行、按订单号取一单，事务短、并发高，连接成本可靠索引压下去。OLAP 要扫三个月订单按分类汇总，连接反而是负担，宽表与预聚合才合适。

所以成熟架构通常分两层：业务库保持 3NF 内核，负责写入与一致性；分析侧通过 binlog、ETL 或定时抽数，构建反范式的读模型或宽表。报表不要直接压在主库上。CQRS 说的就是这件事：写侧维护规范化的命令模型，读侧维护为查询优化的投影，两者通过变更事件同步，接受一个短暂的一致窗口；代价是同步链路本身要监控和补偿。

实践准则与常见误区

规范化到“痛”为止，再反范式。所谓痛，是有具体的慢查询、N+1 或锁竞争，而不是“感觉连接太多”。每加一个冗余列，都在文档或表注释里写清来源、维护方和刷新时机；全库只保留一个事实来源；对派生字段定期跑对账 SQL，把差异当故障处理。

几个反复出现的坑：

  • 过度规范化导致 N+1。表拆得干净，却在应用层逐行查字典表，20 行数据 21 次往返。该用连接或批量查询。
  • 过早反范式。上线前就担心性能，把该拆的字段全塞回主表，量还没起来，一致性债先背上了。
  • 存了派生字段却不修复。total_amount、comment_count 只在部分写入路径更新，后台脚本和手工修数据全绕过了它。
  • 用 JSON 列逃避建模。订单明细、收货地址全塞进一个字段，查询只能全表扫描加应用层过滤。
  • 没有任何约束。只有应用层校验，缺唯一索引、非空、外键，脏数据写进去就永久存在。互联网团队常因性能或分库分表禁用外键，但那是用应用层校验加定期校验任务换来的，不是免费取消。

小结

范式解决的是“一个事实存几处”：1NF 保证值原子，2NF 消除部分依赖，3NF 消除传递依赖，BCNF 要求决定因素都是候选键。实践中做到 3NF 通常足够，拆表要跟着业务规则走。

反范式是在读写比、连接成本、历史快照等压力下做的权衡，前提是有测量、有单一事实来源、有对账手段。设计时多问一句“这个字段描述的是谁的事实、由谁维护”，比背定义有用得多。
