PostgreSQL 主从与备份

“主从复制”和“备份”经常被当成同一件事，但前者只能在一台机器故障时顶上，后者才决定误删数据之后还能不能回来。本文从 WAL 讲起，依次拆解逻辑备份、物理备份、流复制、同步复制与 PITR 的原理和命令，并给出一套可以落地的备份策略与演练清单。文中示例基于 PostgreSQL 12，配置与命令都可以直接照抄到测试环境验证。

备份与复制：两件常被混淆的事

复制保证可用性

流复制的本质，是主库把产生的 WAL 记录持续发送给备库，备库按顺序重放。它解决的问题是“主库所在的那台机器挂了，服务还能不能继续”：备库随时处于可以接管的接近最新状态，切换之后业务只丢失很少的数据。很多团队还会让备库承担只读查询、报表和备份源，从而分担主库压力。

但复制是“忠实”的：主库上一条没有条件的 DELETE、一次错误的表结构变更，都会作为 WAL 原样传到备库并被重放。复制会把逻辑错误一起复制过去，保护不了数据本身。

备份保证可回溯

备份是某一时刻的数据副本，配合归档 WAL，可以回到过去任意时间点。误删表、批量更新写错条件、程序写入脏数据，只能靠备份加 PITR 解决；机房断电、阵列损坏，同样需要一份放在别处的副本。

两者保护的目标不同，可用下表概括。表中 RPO（允许丢失的数据窗口）与 RTO（恢复耗时）都是设计目标，须由业务方确认并通过演练验证。

维度 流复制 备份 + WAL 归档
保护对象 主机、实例级故障 逻辑错误、误操作、灾难
数据回退 不能回退，只能向前重放 可以回到任意时间点
RPO 目标 同步模式下接近零 取决于归档与基础备份周期
RTO 目标 分钟级，取决于切换流程 小时级，取决于数据量与演练
典型用途 高可用、读写分离 合规、误操作恢复、迁移

WAL：复制与备份共同的底座

预写日志的基本原理

PostgreSQL 修改数据时，并不会立刻把数据页写回磁盘，而是先把“改了什么”追加到 WAL（Write-Ahead Log）中，等事务提交时确保 WAL 已经落盘，数据页则可以延迟到检查点时再刷写。这样做有两个好处：提交只需要顺序写日志，性能远好于随机写数据页；崩溃之后可以用 WAL 把没来得及刷盘的数据页重放出来，保证已提交事务不丢。

这条规则被称为“先写日志、再写数据”，也是复制与 PITR 的基础：拿到完整的 WAL 序列，就能在另一台机器重建出一致的数据状态。WAL 在磁盘上被切分成固定大小的段文件，默认每个 16 MB，放在数据目录的 pg_wal 子目录中（PostgreSQL 10 之前叫 pg_xlog）。每条 WAL 记录都有一个 LSN（Log Sequence Number），可以理解为“日志中的字节偏移”，它是判断复制进度、指定恢复目标的通用坐标。

wal_level：决定 WAL 里有多少信息

wal_level 控制 WAL 记录的信息量，直接决定了这个实例能做什么：

  • minimal：只记录崩溃恢复必需的信息，无法用于归档恢复，也无法支撑复制。
  • replica：默认值，额外记录足够让备库重放的信息，流复制、pg_basebackup、WAL 归档都需要至少这一级别。
  • logical：在 replica 基础上增加逻辑解码所需的信息，供逻辑复制或变更捕获使用，WAL 体积也最大。

换句话说，只要打算做主从或者 PITR，就不能停留在 minimal。修改 wal_level 需要重启实例；而 max_wal_senders、wal_keep_segments 这类参数虽然可以动态调整，也建议在配置文件中固化下来。

归档：把 WAL 从“临时文件”变成“历史”

WAL 段在正常情况下会被循环复用，旧段一旦不再需要就会被删除。如果不做归档，那么基础备份之后产生的 WAL 迟早会被覆盖，PITR 就成了空谈。archive_mode = on 让 PostgreSQL 在切换 WAL 段时调用 archive_command，把完成的段文件复制到归档目录；restore_command 则在恢复时从归档目录把需要的段取回来。

archive_command 的约定很简单：把 %p 指定的文件放到目标位置，成功返回 0，失败返回非 0。返回非 0 时 PostgreSQL 会不断重试，并保留该段不删除，直到归档成功。上面那条命令用 test ! -f 做了幂等保护，避免重复拷贝同一个文件时报错。

归档必须被监控，原因在于它是“静默失败”的典型：archive_command 失败不会让主库停止写入，业务毫无感知，但归档目录里已经出现空洞。等真正需要恢复时才发现缺了某一段 WAL，恢复只能停在那里。因此 pg_stat_archiver 中的失败计数、最后一次成功归档的文件名与时间，应当纳入日常巡检；归档目录所在磁盘的剩余空间也要设置告警。

还有一个容易被忘记的细节：归档只在 WAL 段写满并切换时触发。业务写入很少的库，一个 16 MB 的段可能几小时都写不满，归档也就迟迟不推进，RPO 被悄悄拉长。此时应设置 archive_timeout，比如 300 秒，强制周期性切换，代价是会归档一些只写了一半的段文件。

两种备份路线：逻辑与物理

PostgreSQL 提供两条完全不同的备份路线，理解它们的差别，比记住命令更重要。逻辑备份导出的是“数据与结构的描述”，物理备份复制的是“数据目录的字节”。前者像导出一份 SQL 脚本，后者像给整个实例拍一张快照。

逻辑备份：pg_dump 与 pg_dumpall

pg_dump 针对单个数据库工作。它在一个事务里取到一致性快照（可重复读级别），因此即使备份期间业务仍在写入，导出的数据也对应同一个时间点，不会出现“订单表是十点的、明细表是十点零五的”这种撕裂。备份过程只持有 ACCESS SHARE 锁，普通的增删改不会被阻塞，但 ALTER TABLE、DROP TABLE 这类需要排他锁的 DDL 会被挡住，所以大库导出应避开变更窗口。

它的输出格式值得仔细选择：

  • -Fp（plain）：纯 SQL 文本，可以用 psql 直接灌入，便于人工查看和局部修改，但不支持并行恢复。
  • -Fc（custom）：自定义归档，压缩、支持 pg_restore 选择性恢复，是单库备份的常用选择。
  • -Fd（directory）：目录格式，每个表一个文件，配合 -j 可以并行导出与并行恢复，大库首选。
  • -Ft（tar）：打包成 tar，便于传输，但灵活性不如目录格式。

pg_dump 不负责全局对象：角色、表空间这些跨数据库的对象由 pg_dumpall 导出。pg_dumpall 本质上是对每个库轮流调用 pg_dump，再加上全局对象的导出，因此它不能并行，库多时很慢。实践中通常用 --globals-only 单独备份角色与表空间定义，再对各库分别做目录格式导出。

逻辑备份的局限也很明确：数据量大时导出与恢复都以小时计，恢复要重建索引与约束，耗时是导出的数倍；它只能回到导出那一刻，无法做时间点恢复；导出期间若有长事务，快照被拖住，WAL 也无法回收。因此它适合作为第二道防线与迁移手段，而非唯一手段。

物理基础备份：pg_basebackup

物理备份复制整个数据目录，外加备份期间产生的 WAL，得到一个“解压即可启动”的实例副本。pg_basebackup 是最常用的工具，它通过复制协议连接主库，不需要登录主机拷文件。

使用它有几个前提：主库 wal_level 至少为 replica，max_wal_senders 大于零，连接账号具备 REPLICATION 权限（或为超级用户），并且 pg_hba.conf 中放行了 replication 类型的连接。少了任何一条，备份都会在第一步失败。

这里每个参数都有理由。-Ft -z 输出 base.tar.gz 与 pg_wal.tar.gz，便于归档和校验；-P 打印进度，长备份没有进度会让人怀疑是不是卡死了；--checkpoint=fast 立即触发检查点，而不是等待下一个周期，能显著缩短备份窗口；--wal-method=stream 在备份同时另开一条连接流式接收 WAL，保证备份期间产生的日志不缺失；-S 指定复制槽，让主库在备份期间保留所需 WAL。最后一点尤其关键：一次几百 GB 的备份可能跑上一小时，如果没有复制槽，主库在此期间切换掉的 WAL 段可能已被删除，备份就会在结束时失败。

物理备份的恢复很简单：解包到数据目录，修正属主与权限，启动实例。目录权限必须严格，数据目录通常为 0700，属主为运行 PostgreSQL 的系统用户，否则实例会拒绝启动。这也是备份文件需要加密的原因之一：base.tar.gz 里就是全部数据，谁拿到谁就能读。

两条路线怎么配合

逻辑备份解决“拿回一张表、迁到另一个版本”，物理备份解决“整个实例快速回来、配合 WAL 做 PITR”。成熟做法是两者都用：日常以物理基础备份加 WAL 归档为主，周期性补一份逻辑导出，用于对抗物理文件损坏与误删表。只做逻辑备份，TB 级数据库的恢复时间不可接受；只做物理备份，找回一张表也要恢复整个实例。

同步复制与它的代价

默认的流复制是异步的：主库把 WAL 写进本地日志就向客户端返回提交成功，至于备库有没有收到，主库并不等待。这样做性能最好，但主库突然断电时，那些“已提交但还没传到备库”的事务就丢了。同步复制要解决的正是这个窗口。

两个参数的分工

配置同步复制只涉及两个参数，但它们的作用点不同：

synchronous_standby_names 决定“等谁”，synchronous_commit 决定“等到什么程度”。备库是否同步，是按 application_name 匹配的，名字写错是最常见的配置失效原因——主库会安静地退回异步，pg_stat_replication 里 sync_state 显示 async，一切看起来都正常。

sync_state 有几个取值：sync 表示当前同步备库，potential 表示在候选列表中但尚未成为同步备库，quorum 表示按法定人数计入，async 表示完全不参与同步。用 ANY 1 (standby1, standby2) 时，两台都会显示 quorum，任意一台确认即可。

synchronous_commit 的五个级别

这个参数控制提交返回前必须完成的工作，级别越高越安全，延迟也越大：

取值 提交返回前保证 典型场景
off 只写入本地 WAL 缓冲区，不等落盘 批量导入、可重跑的任务
local 本地 WAL 已落盘 只保证本地持久化
remote_write 备库已写入其操作系统缓存 折中方案，备库崩溃仍可能丢
on 备库已把 WAL 刷到磁盘 默认值，多数同步复制场景
remote_apply 备库已重放，只读查询可见 要求读己之写的一致性场景

on 是默认值，但只有配置了同步备库才真正产生等待效果；没有同步备库时它与 local 等价。remote_apply 还要等备库重放完成，遇到长查询时延迟明显上升。

为什么同步复制会拖住主库

同步复制的本质是把“提交”的完成条件外包给了另一台机器。如果 synchronous_standby_names = 'standby1'，而 standby1 恰好宕机、网络中断或者重放卡住，主库上所有写事务都会停在提交点等待，连接池很快被占满，业务表现为“数据库没挂，但什么都写不进去”。这不是 bug，而是同步复制用可用性换一致性的必然结果。

缓解手段有三条。第一，配置两个同步候选并用 ANY 1，只要一台健康就能提交，相当于“法定人数”模式。第二，为等待设置上限，用 statement_timeout 或应用侧超时尽早暴露问题，并准备好把 synchronous_standby_names 置空、降级为异步的预案——这是明确的取舍，须由业务方拍板。第三，监控 sync_state 与延迟，备库掉线立即告警。

还要澄清一个常见误解：同步复制不等于绝对不丢数据。它保证的是“至少一台备库确认”，如果主备同时故障、备库磁盘缓存撒谎，或者运维在故障时误操作，数据仍可能丢失。它把窗口缩到很小，但不能替代备份。

PITR：把数据库倒回某个时刻

PITR（Point-In-Time Recovery，时间点恢复）是备份体系的皇冠：以基础备份为起点，用归档 WAL 一路重放，可在任意时刻停下。它对付的不是硬件故障，而是“数据被改坏、实例还活着”这类事故。

原理与前提

恢复过程可以分成两段：先把基础备份解包，得到一个“备份结束那一刻”的实例；然后从归档中依次取 WAL 段重放，直到达到指定的目标。目标可以是一个时间点、一个 LSN、一个事务 ID，或者一个命名还原点。

flowchart LR
  B[基础备份 T0] --> R[重放归档 WAL]
  R --> T1[目标时刻 T1]
  T1 --> P[提升为主库]
  E[误操作时刻 T2] -.->|不回放| X[丢弃]

这套机制成立有三个硬前提：基础备份必须早于目标时刻；从备份结束到目标时刻之间的 WAL 必须完整归档、没有缺口；恢复使用的程序版本与系统架构要和备份时一致。缺任何一条，恢复都会停在半路。

一次完整的恢复演练

假设 9 月 23 日 14:05，有人误执行了一条没有条件的删除，13:00 之前的数据是好的。基础备份是当天凌晨 2 点做的，WAL 一直正常归档。恢复步骤如下。

第一步，停库并保护现场。不要直接删除旧数据目录，把它改名保留，万一恢复目标选错还有退路。

第二步，配置恢复参数并放置 recovery.signal。这个信号文件告诉实例“启动时进入归档恢复”，与备库使用的 standby.signal 是两回事，两者不能同时存在。

第三步，启动并观察日志。恢复期间会看到大量 restored log file 与 redo done 之类的输出，最后出现 recovery stopping before commit of transaction ... 或 recovery stopping at ...，说明已经到达目标。

第四步，验证。检查 pg_is_in_recovery() 是否为 f（promote 模式会自动提升），核对关键表的行数、最大时间戳，确认误删的数据还在、后续的脏数据没有进来。

目标参数与两个易错点

recovery_target_time 最直观，但它是按服务器 TimeZone 解释的。如果主机时区、配置文件时区、运维人员心里的时区三者不一致，目标就会整体偏移几个小时，恢复出来的数据“看起来对，其实不对”。因此务必在配置里显式写死 timezone，并在工单里记录带时区偏移的时间字符串。

第二个易错点是 recovery_target_action。它有三个取值：pause（到达目标后暂停，默认）、promote（自动提升）、shutdown（停止实例）。pause 最适合不确信目标是否正确的场景：实例停在目标点，可以连上去查数据，确认无误后再执行 pg_promote() 或 SELECT pg_wal_replay_resume()。若目标时刻之后还有可用 WAL，暂停状态也可以继续往前重放。

除时间外，还可用 recovery_target_lsn 精确到字节、recovery_target_xid 指定事务，或用 recovery_target_name 配合 pg_create_restore_point() 埋点。计划内变更先建还原点，出问题按名字恢复，比推算时间可靠。

最后要接受一个现实：PITR 只能恢复到归档 WAL 存在的地方。如果归档在 13:40 断了，目标定在 14:00 也没用，恢复会在 13:40 处停下并报错。这正是前文强调“归档必须被监控”的原因——它决定了你的恢复上限。

切换、脑裂与旧主回归

复制搭起来只是开始，真正考验运维的是“什么时候可以把备库提上来”以及“提上来之后旧主怎么办”。这两个问题处理不好，复制反而会制造更大的事故。

计划内切换

计划内切换（switchover）是有准备的角色互换，目标是不丢数据、尽量少中断。流程可以固定为五步。

故障转移与 fencing

非计划故障转移（failover）没有准备时间，最大风险是脑裂：旧主还活着，只是监控误判或网络分区，新主提升后两边同时接受写入，产生两条分叉的时间线。网络恢复后两份数据无法合并，只能弃其一。

因此提升之前必须先 fencing，也就是确保旧主不会再接受任何写入。手段包括通过带外管理断电、交换机端口关闭、存储卷摘除、收回虚拟 IP 并在防火墙上封掉数据库端口。只有确认旧主“确实死了或确实写不了”，才执行提升。这条规则听起来保守，但它是唯一能从根本上避免双主写入的办法。

提升之后，新主库的时间线 ID 会加一，WAL 归档目录里会多出 .history 文件，记录时间线分叉的历史。旧主即使恢复，也不能直接改成备库跟随——它的 WAL 已经和新主分叉。此时 pg_rewind 可以把旧主的数据目录“倒回”分叉点，再作为备库接入：

自动化工具的位置

手工切换可以写成 runbook，但“该不该切”和“旧主是否已隔离”很难靠人保证。Patroni、repmgr 这类工具把选主、fencing、配置改写与 VIP 漂移串成自动流程，Patroni 依赖 etcd、Consul 或 ZooKeeper 做一致性仲裁。它们能缩短 RTO，却不会替你决定 RPO 取舍；引入前先把手工流程跑通、监控补齐。

监控、备份策略与常见坑

复制和备份都属于“平时感觉不到、出事时决定生死”的基础设施。它们最大的敌人不是技术难点，而是长期无人验证的假设。

复制与归档监控

复制延迟有两个视角：字节差与时间差。字节差用 LSN 相减，直观且不依赖时钟；时间差看 replay_lag，更贴近业务感受，但要求备库处于活跃状态，且受主备时钟偏差影响。

归档健康度看 pg_stat_archiver：重点不是成功次数，而是 failed_count 是否增长、last_archived_time 是否停滞。若当前时间减去最后成功归档时间超过 archive_timeout 的两倍，就应告警。

磁盘方面要盯三个位置：数据目录、pg_wal、归档目录。pg_wal 异常膨胀通常有两个原因——归档卡住导致旧段无法删除，或者复制槽持有 restart_lsn 不放。后者可以用下面的查询定位：

一套可执行的备份策略

下面这套策略适合中小规模的生产库，参数是示例目标，不是行业标准，实施时应按数据量、变更频率和合规要求调整。

项目 频率 保留 说明
物理基础备份 每日一次 14 天 pg_basebackup 到独立备份主机
WAL 归档 持续 覆盖最老基础备份再留余量 支撑 PITR 到任意时刻
逻辑导出 每周一次 4 周 目录格式，含全局对象
异地副本 每日同步 与本地一致 对象存储或异地机房

落地细节决定成败：备份文件离开主机前算校验和、传输后对比，避免“成功但损坏”；归档与备份应加密，物理备份等同于全部数据；备份账号只给复制权限；备份目录记录起始 LSN 与时间，恢复前确认归档覆盖该区间。

演练是整套策略里最容易被跳过、也最不能跳过的一环。演练要覆盖三种场景：从最近的基础备份完整恢复、按时间点恢复到误操作之前、以及模拟主库丢失后从备份重建备库。每次记录实际耗时，与 RTO 目标对比；记录恢复后的校验方式，比如关键表行数、金额汇总、抽样比对。没有演练过的备份，只能算“可能可用”。

常见坑清单

  • 只做主从、不做 WAL 归档。复制再健康也无法回到过去，一次误删就是终局。
  • 复制槽建了不监控。备库长期离线，槽位保留的 WAL 会把磁盘吃满。
  • 备份文件放在主库同一台机器、同一个存储卷。主机或阵列故障时主备与备份一起消失。
  • 从未验证恢复。备份命令退出码为 0，不代表文件可解包、可启动、数据完整。
  • PITR 时区混乱。目标时间按服务器时区解释，配置里不写死时区就可能偏移数小时。
  • 未 fencing 就提升。旧主仍在写，形成双主，后续只能弃数据。
  • 只备份数据库、不备份角色与表空间。恢复后权限全丢，应用连不上。
  • 归档命令使用会覆盖目标的写法，或目录权限不足，失败后静默重试，没人发现。
  • 长期不检查 pg_wal 与归档目录容量，磁盘写满导致主库停机。
  • 把备库当备份，在备库上执行 DROP 之后才想起没有归档。

小结

复制与备份保护的是两类完全不同的风险：前者用冗余换可用性，后者用历史副本换可回溯性，任何一方都不能替代另一方。WAL 是二者的共同底座，wal_level、archive_mode、archive_command 决定了你能否做复制与 PITR，也决定了事故当天的恢复上限。日常最值得投入的三件事是：让归档持续且被监控、让复制延迟可见、让恢复演练成为固定日程。配置层面记住 PostgreSQL 12 的变化——recovery.conf 已消失，备库用 standby.signal，归档恢复用 recovery.signal。最后，所有 RPO 与 RTO 都应以演练实测为准，而不是写在文档里的愿望。
