ELK 日志平台搭建实践

日志散落在几十台机器的 /var/log 目录下时，排查一次线上问题往往要先 ssh 登录、再 grep 半小时。本文从“能落地”的角度讲一遍 ELK 日志平台的搭建：先定架构与容量，再装 Elasticsearch、设计索引，然后补上 Filebeat 采集、Logstash 解析、ILM 生命周期和快照备份。示例基于 2020 年 8 月发布的 7.9 版本，单机实验与三节点小集群都能照着做。

架构与选型：一条日志的旅程

ELK 这个名字包含四件东西：采集端的 Beats（最常用的是 Filebeat）、负责解析与缓冲的 Logstash、负责存储与检索的 Elasticsearch，以及负责展示的 Kibana。一条应用日志的典型路径是：程序写本地文件，Filebeat 逐行读取并推送，Logstash 解析成结构化事件，Elasticsearch 写入索引，Kibana 提供检索界面。

flowchart LR
  A[应用日志文件] --> B[Filebeat]
  B -->|"Beats 协议 5044"| C[Logstash]
  B -.->|"可选：直接写入"| D[Elasticsearch]
  C -->|"HTTP 9200"| D
  D --> E[Kibana]

从方向上看，日志采集是“推”模型：Filebeat 主动 tail 文件并把事件推给下游，这与 Prometheus 定时“拉”指标正好相反。推送的好处是采集端不用暴露端口，坏处是下游一慢，压力会沿着链路往回顶。

这就引出背压（backpressure）问题：下游处理不过来时，上游应当减速而不是丢数据。Filebeat 用内存队列暂存事件，并用磁盘上的 registry 文件记录每个文件读到哪一行，输出阻塞时读取会停下来；Logstash 默认用内存队列，也可以开启持久化队列（queue.type: persisted）把事件先落盘；Elasticsearch 写入压力大时返回 429，Logstash 的 bulk 请求会自动重试。把链路上每一段的缓冲能力想清楚，比背下一堆参数更有用。

那要不要让 Filebeat 直接写 Elasticsearch？如果日志本身就是 JSON、不需要复杂解析、量也不大，直接配置 output.elasticsearch 最省事，少一层组件就少一个故障点。一旦需要 grok 解析非结构化文本、做 geoip 之类的字段富化、按内容路由到不同索引，或者想在 ES 前面加一道缓冲，就该让 Logstash 上场。笔者的经验是：能不经过 Logstash 就不经过，但需要“解析加多路输出”时不要硬省。

容量规划与集群拓扑

装之前先算三笔账：每天产生多少日志、要保留多久、能接受多长的故障恢复时间。单机足够应付实验和小团队：4 核 8 GB、一块 SSD，堆内存给 4 GB，日增量几个 GB、保留两周完全跑得动。生产环境的最小可用形态是三节点，三个节点都承担 master 与 data 角色，任一节点宕机时集群仍能选主、副本仍能顶上。日志量继续增长后，再把 master 拆成三个专用的小节点，data 节点按需横向扩展；ingest 角色只有在让 ES 承担解析时才需要单独规划，解析放在 Logstash 时可以直接省掉。

flowchart TD
  K[Kibana] --> M1[es01 master+data]
  K --> M2[es02 master+data]
  K --> M3[es03 master+data]
  L[Logstash x2] --> M1
  L --> M2
  L --> M3

堆内存是最容易犯错的地方。Elasticsearch 依赖操作系统的 page cache 缓存索引文件，堆给得越大，留给文件缓存的内存越少。两条硬约束：不超过物理内存的 50%，以及不超过 31 GB 左右——超过这个值，JVM 就用不了压缩普通对象指针（compressed oops），同样的对象占用更多内存，堆大了反而更慢。剩下的内存留给 Lucene。

磁盘按“日增量 × 保留天数 ×（1 + 副本数）× 1.1”估算，并让使用率长期低于 75%，给段合并和副本恢复留空间。系统层面还有四项必做：把 vm.max_map_count 调到 262144，文件描述符上限调到 65535，关闭 swap 或用 bootstrap.memory_lock 锁住内存，以及用 chrony 保证所有节点时间同步——日志时间错乱时，跨节点排序会完全失效。

安装与安全基线：把 7.9 跑起来

用官方 RPM 或 DEB 包安装，目录结构是固定的：配置在 /etc/elasticsearch，数据在 /var/lib/elasticsearch，日志在 /var/log/elasticsearch，systemd 单元由包自动注册。

配置文件里至少改这几项：

node.roles 是 7.9 引入的写法，比旧的 node.master 与 node.data 布尔组合更清晰。cluster.initial_master_nodes 只在集群第一次启动、还没有集群状态时用于选举，集群成型后不该依赖它，更不要每次重启都改这个列表，否则容易引发选主异常。防火墙要放行 9200（HTTP）和 9300（节点间传输），Logstash 所在机器还要放行 5044。

堆大小写在 /etc/elasticsearch/jvm.options.d/heap.options 里，7.x 支持这个 drop-in 目录，不必直接编辑主文件。把 -Xms 与 -Xmx 设为相等（例如都是 4g），避免运行期反复扩缩堆。7.9 自带 JDK，不需要为它单独安装 Java，也不要让系统里的老 JDK 顶替。

从 6.8 起，默认发行版的基础许可（basic）就包含 TLS 与基础认证，不需要购买订阅。做法是先在 elasticsearch.yml 里打开 xpack.security.enabled，用 elasticsearch-certutil 生成 CA 和节点证书，配置 xpack.security.http.ssl 与 xpack.security.transport.ssl 两段，再执行 elasticsearch-setup-passwords interactive 为内置用户设置密码。需要说明的是，审计日志以及文档级、字段级权限属于更高订阅，基础许可里没有，规划合规需求时不要把它们算进来。

索引设计：模板、映射与分片

日志索引最常见的是按天分，例如 app-2020.09.16。按天切分的好处是删除过期数据只需删掉整个索引，代价是索引数量随服务数和天数线性增长。按天建索引时，单个索引 1 个主分片、1 个副本通常就够，因为单日单服务的数据量有限。

用索引模板统一 settings 与 mappings，避免每个索引各写一份：

keyword 与 text 的区别要记牢：keyword 整串不分词，适合精确过滤、聚合和排序；text 会分词，适合全文检索，但不能直接拿来聚合。像 trace_id、uri 这种既要过滤又可能很长的字段，用 keyword 加 ignore_above，超长部分不建索引，避免把索引撑大。dynamic 为 true 时新字段自动推断类型，方便但危险：一个把异常堆栈当字段名的程序就能制造上千个字段，这就是字段爆炸。对结构不确定的日志，宁可显式列出字段，或者把 dynamic 设为 false。

分片不是越多越好。每个分片都是一个 Lucene 索引，占用堆内存和文件句柄，还要参与集群状态同步；集群状态变大后，主节点发布变更会变慢，节点重启时也要逐个分片恢复。经验值是单个分片控制在 10 到 50 GB，每 1 GB 堆内存对应的分片数不超过 20。小集群可以按“每服务每天 1 个主分片”起步，等单分片接近几十 GB 再考虑 rollover 或调整模板。

别名让使用方不感知索引的物理名字：给 app-* 建一个读别名 app-logs，Kibana 的索引模式指向别名，之后换索引、做 rollover 都不用改使用方。

这里有个取舍要说明：按天建索引简单直观，但每天一个索引乘以服务数，一年下来就是上万个小索引；rollover 用“大小或天数先到者触发”的写法，让索引体积更均匀，也让 ILM 的 warm 与 delete 阶段有统一的判断基准。数据量不大时不必追求 rollover，两种方式选一种并坚持到底，最怕的是两套规则混用。

采集与解析：Filebeat 与 Logstash 管道

Filebeat 的配置分成三段：输入、处理器、输出。真正需要花心思的是多行日志，Java 的异常堆栈如果一行一条发出去，检索时几乎没法看。

多行的思路是“以时间戳开头的是新事件，不匹配的算上一条的续行”，negate 与 match 配合后，堆栈就被合并进同一条。registry 文件记录每个文件读到哪一行，删掉它等于让 Filebeat 从头再读一遍，线上重复数据大多是这么来的。容器环境可以用 autodiscover 配合 Pod 注解，Pod 启动时自动套用对应的多行规则和字段。

Logstash 的管道由 input、filter、output 三段加条件判断组成。

几个细节值得单独说。@metadata 里的字段只在管道内部可见，不会写进文档，用它来拼索引名最合适；条件判断既可以按级别打标签，也可以写多个 output 做分流。grok 解析失败的事件会被打上 _grokparsefailure 标签，写完规则先搜这个标签，能快速发现漏配的格式。调试 grok 不必反复重启 Logstash，Kibana 的 Dev Tools 里自带 Grok Debugger，粘一行样本和模式就能看到拆分结果。格式完全固定时，用 dissect 比正则快得多；需要按 IP 补充地理位置时再加 geoip 过滤器。

性能上，pipeline.workers 默认等于 CPU 核数，batch.size 默认 125、batch.delay 默认 50 毫秒。日志量大而 CPU 有余时，先调大 batch；CPU 打满则说明 grok 写得太重，优先简化正则，而不是盲目加节点。最后在 Kibana 里按别名建索引模式、时间字段选 @timestamp，一条从文件到可检索的链路就通了。

Filebeat 一侧也有类似的旋钮：output.logstash 下的 bulk_max_size 控制每次发送的事件数，worker 数量影响并发连接。Logstash 暂时不可用时，Filebeat 会在内存里重试并停止读取新行，这就是它的背压表现；如果停机时间可能很长，宁可让 Logstash 开持久化队列，也不要指望采集端无限缓冲。

生命周期管理：用 ILM 代替定时删索引

按天建索引再配一个 cron 删旧索引，短期能用，长期一定会出问题：删除脚本和写入逻辑分散在两处，某天索引名变了就会漏删；删索引的瞬间没有过渡，无法先降温再清理；出事时也没人知道到底删了哪些。7.x 的 ILM（索引生命周期管理）把这些动作变成策略的一部分。

ILM 把索引的一生分成 hot、warm、cold、delete 四个阶段：hot 阶段滚动写入，warm 阶段不再写入并做段合并，cold 阶段可以冻结以省资源，delete 阶段到期删除。

如果单个索引有多个主分片，warm 阶段还可以加 shrink 动作合并成单分片，降低后续查询与恢复的开销；单分片索引不要写这一条，否则会因为无法再缩小而报错。

策略要配一个 rollover 别名才能生效：模板里写上 index.lifecycle.name 和 index.lifecycle.rollover_alias，并手工创建第一个带 is_write_index 的索引作为起点。

之后的滚动由 ILM 自己完成：写别名始终指向最新索引，查询别名覆盖全部索引。保留期只有一处定义，改策略即可，不需要再维护脚本。上线后可以用 GET app-logs/_ilm/explain 确认每个索引当前处于哪个阶段、下一步动作在什么时候触发。

安全加固、快照与排错清单

内置用户各有分工：elastic 是超级用户，只用于初始化；kibana_system 给 Kibana 连接 ES 用；logstash_system 只能写监控数据，写不了业务索引。因此要让 Logstash 写日志，必须自建一个 logstash_writer 角色：集群权限给 manage_index_templates、monitor、manage_ilm，索引权限给 write、create、create_index、manage，再把这个角色绑定到专用用户上。

密码不要写进明文配置文件。Kibana 用 kibana-keystore 保存 elasticsearch.password，Logstash 用环境变量或 keystore 注入。给 Filebeat 这类采集器发 API key 比共用一个账号更好：既能按采集器粒度吊销，也能把权限限制在 app-* 上。

备份用快照，不要直接 cp 数据目录。先在 elasticsearch.yml 里配置 path.repo 并重启，再注册文件系统仓库；跨机房或云上用官方 repository-s3 模块。恢复前先确认目标集群版本不低于快照版本，索引名冲突时用 rename_pattern 改名。

日常监控看三处：集群健康状态、各节点磁盘使用率、以及写入是否出现 429。打开 xpack.monitoring.collection.enabled 后，可以在 Kibana 的 Stack Monitoring 里看到节点与索引的概况，不必自己搭一套采集。

快照本身也要验证：定期在测试集群恢复一次，确认索引和文档数对得上，否则真出事时才发现仓库路径早已不可写。7.x 提供 SLM（快照生命周期管理），可以把“每天一次、保留 14 天”写成策略，和 ILM 一样免去自建定时任务。

最后列一份上线后最容易踩的坑：

  • 时区错位：容器里日志按 UTC 写、人按东八区看，date 过滤器又没有指定时区，结果所有事件整体偏移 8 小时。统一在 date 过滤器里显式写时区。
  • 映射冲突：同一个字段在 A 索引是 text、在 B 索引是 keyword，跨索引查询就会报错。靠模板统一，不要每个服务各写一套。
  • 字段爆炸：把整段 JSON 或异常信息当字段名，分片元数据迅速膨胀。控制 dynamic，必要时显式列字段。
  • 堆给太大：超过 31 GB 反而更慢，还挤压了 page cache。
  • 磁盘水位：默认 85% 低水位、90% 高水位、95% 洪泛水位，触及洪泛水位后索引会被置为只读。清理或扩容后还要手动解除只读。
  • 没有保留策略：只建索引不删索引，几个月后磁盘先满。用 ILM，不要靠 cron。
  • Logstash 解析瓶颈：grok 写得过于贪婪，CPU 打满而队列堆积。先简化正则或改用 dissect，再考虑扩容。

小结

搭建 ELK 的顺序应当是先架构后安装、先容量后参数：采集端用 Filebeat 负责搬运与背压，需要解析和多路输出时才引入 Logstash；Elasticsearch 按三节点起步，堆内存守住“不超过内存一半、不超过 31 GB”两条线；索引用模板统一 mapping，用别名隔离物理索引名；过期数据交给 ILM，备份交给快照。把这几个边界定清楚，平台才能在日志量增长时仍然可控，而不是靠加机器和删索引维持。
