数据库慢查询治理流程

慢查询治理最常见的失败，不是某条 SQL 没优化好，而是没有人对它负责：告警响了临时救火，风波过去一切照旧。本文以 MySQL 5.7 和 8.0 为例，把慢查询当作一项需要长期运营的工程来讨论，从指标基线、发现管线、分诊归因，一直讲到发布门禁、索引治理、故障闭环与九十天落地计划。文中不展开单条 SQL 的排查细节与执行计划逐列解读，这些内容留给同系列的其他篇目，这里只回答一个问题：一个团队如何把慢查询管住，并让它持续变好。

慢查询是治理缺位的症状

先看一个很多团队都经历过的场景。凌晨两点，核心接口 P99 从 200 ms 涨到 3 s，数据库 CPU 打满，连接数逼近上限，值班同学从慢日志里揪出一条没有走索引的查询，紧急加索引、重启应用，故障恢复。两周后，另一条 SQL 以几乎相同的方式再次把系统拖垮。每一次都被当作独立事故处理，每一次都“解决”了，但问题总量并没有下降。这说明我们修的是症状，不是病因。

单条 SQL 慢，通常能在几分钟内定位；一批 SQL 反复慢，背后往往是组织问题：这条 SQL 属于哪个服务、谁负责、上线前有没有人看过、变慢之后有没有人跟踪，这些问题的答案都是“不清楚”。没有归属，就没有人对访问路径负责；没有门禁，新问题就会源源不断进入生产；没有基线，讨论“慢不慢”只能靠感觉；没有复盘，同一个坑会被不同的人踩很多次。

慢查询的外在表现并不只有“查询变慢”一种。本文把它们归为五类信号：延迟 SLO 被击穿，用户可感知；CPU 或磁盘 IO 持续饱和，挤占其他查询；锁等待升高，事务互相拖拽；连接堆积，应用侧线程池被耗尽；以及最容易被忽视的故障疲劳，值班同学对告警逐渐麻木，真正的事故反而被漏掉。这五类信号指向同一个事实：数据库是共享资源，任何一条失控的查询都会外溢成团队问题。

因此，本文所说的“治理”，不是一次优化运动，而是一套把发现、归因、修复、防回归变成日常动作的机制。它至少包含四样东西：可度量的指标基线，固定的发现与分诊流程，发布前的审核门禁，以及明确到人和服务的责任划分。工具只是载体，流程和角色才是骨架。判断治理是否有效，不看这个季度优化了多少条 SQL，而看三件事：新的慢 SQL 是否更难进入生产，存量问题是否有人认领并有期限，整体指标是否在持续下降。

指标基线：平均值会掩盖长尾

治理的第一步不是优化，而是把“慢”变成可比较的数字。没有基线，团队会在两件事上反复消耗：一是争论某条 SQL 到底算不算慢，二是无法证明治理是否有效。基线不需要复杂，一页纸足够，但要覆盖四个层面：业务体验、SQL 行为、资源水位和变更影响。

层面 指标 口径 采集来源 示例目标（假设）
业务 接口 P99 按路由统计，排除健康检查 APM 与网关日志 核心读接口低于 200 ms
吞吐 QPS 与慢查询占比 实例与接口分别统计 监控与慢日志 慢查询占比低于 0.1%

关于平均值，有一个简单的算术例子。假设某接口在一分钟内处理 1000 次请求，其中 980 次耗时 5 ms，20 次因为锁等待耗时 2 s。平均耗时约为 45 ms，看起来仍然健康；但 P99 是 2 s，最慢的 2% 用户经历了完整的两秒卡顿。请求量越大，长尾越容易被平均掉，而线上事故恰恰由长尾触发。这就是本文坚持用 P95、P99 而不是平均值作为主指标的原因。

百分位本身也有陷阱。第一，不能对多个实例的 P99 再求平均，正确的做法是合并直方图或原始分桶后重新计算；第二，样本量太小时百分位没有意义，一分钟只有几十次调用的接口，应看更长窗口；第三，P99 只描述尾部的位置，不描述尾部有多长，必要时补充 P999 或“超过 1 s 的请求数”。使用 Prometheus 的 histogram 指标时，桶边界要覆盖业务关心的阈值，否则 histogram_quantile 只能在粗粒度的桶之间插值。

除了延迟，还有几个更能提前预警的指标。扫描行数与返回行数的比值，能在查询还没慢到触发阈值时就暴露访问路径问题；锁等待时间上升，往往先于业务超时出现；缓冲池命中率下降，说明热数据已经放不进内存；活跃连接数持续贴近上限，意味着应用侧很快就会出现获取连接超时。把这些指标和发布记录放在同一张图上，还能快速判断某次变慢是否由变更引起。

指标目标必须结合业务设定，不能照搬。本文在表格中给出的数值只是示例假设，用于说明量级：核心读接口 P99 控制在 200 ms 以内，热路径单次扫描行数不超过 100 行，锁等待 P99 低于 10 ms，实例 CPU 峰值不超过 70%。这些目标应该在治理启动时由后端、DBA 和业务方共同确认，并每个季度复核一次。目标一旦确定，就写进监控和评审清单，而不是停留在文档里。

发现管线：慢日志、性能表与采样

发现管线的目标不是抓到每一条慢查询，而是以可接受的成本稳定回答三个问题：哪些 SQL 指纹在变慢、变慢发生在什么时间、它与哪次变更或哪类业务有关。单一数据源都有盲区，实践中通常把慢日志、performance_schema、连接列表采样和 APM 链路组合起来使用，再以指纹作为关联键。

慢日志是最稳定的历史记录，按执行时间阈值落盘，适合做日、周维度的趋势分析。它的配置需要权衡：阈值太低会把大量正常查询写进磁盘，阈值太高又会漏掉“单次不慢但调用极频繁”的查询。本文建议在线库从 0.2 s 起步，报表库单独设为 1 s，并根据写入量调整。

log_queries_not_using_indexes 默认关闭是有意的：小表全扫也会被记录，噪音会淹没真正的问题；min_examined_row_limit 则过滤掉那些扫描行数很少的语句。两害相权，宁可漏掉一些轻微问题，也要保证慢日志本身可读。

performance_schema 的语句汇总表按指纹聚合，常驻内存，开销可控，适合实时排序。MySQL 5.7 与 8.0 都提供 events_statements_summary_by_digest，它的统计自实例启动或上次清空时开始，重启后归零，因此不能替代慢日志做长期趋势。

慢日志的可读性差，需要聚合工具。Percona Toolkit 3.x 的 pt-query-digest 会把字面量归一化成指纹，输出执行次数、总耗时、平均耗时、扫描行数和样本语句，正好对应分诊需要的字段。

连接列表（SHOW PROCESSLIST 或 information_schema.PROCESSLIST）采样补的是另一个维度：某一刻数据库正在做什么。它对短查询不敏感，却很容易抓到锁等待和连接堆积。故障期间每秒采样一次、持续一分钟，往往比翻慢日志更快定位“谁把谁堵住了”。

APM 链路提供业务视角：同一条 SQL 由哪个接口、哪类用户触发，影响面有多大。它的采样会漏掉低频慢请求，但非常适合回答“这条 SQL 值不值得优先修”。四类数据各有所长，用指纹拼在一起，才能既看到趋势，又看到现场，还能对应到业务。

需要提醒的是开销。慢日志的写入量取决于阈值和流量，阈值过低时 IO 影响不可忽略；performance_schema 常驻内存，实例规格小时要关注内存占用；连接采样本身很轻，但不要在高峰期对主库做全表扫描式的统计查询。采样的第一条原则是不要用观测手段制造新的故障。

分诊矩阵：先修哪一条

慢查询清单往往一次就有上百条，全部修复既不现实，也会让团队失去焦点。分诊要回答两个问题：先修哪一条，以及它属于哪一类问题。第一个问题决定优先级，第二个问题决定交给谁、用什么手段。

先纠正一个直觉。工程师容易被“单次最慢”的查询吸引，因为它最刺眼；但系统容量是被总耗时吃掉的。假设某查询每天执行 20 万次、平均 80 ms，总耗时约 4.4 小时；另一条每天执行 20 次、每次 30 s，总耗时只有 10 分钟。后者更值得写进周报，前者对数据库的消耗却是后者的二十多倍。因此排序的主键应该是总耗时，单次最大值只用于识别雪崩型问题。

分诊矩阵把频率、单次代价和业务重要性放在一起看。下表中的阈值同样是示例假设，团队应根据自己的流量规模调整。

频率 单次代价 业务重要性 优先级 处置方式
高频 中高 核心链路 P0 一周内修复，复盘为何漏过门禁
高频 低 核心链路 P1 减少调用次数、批量化或缓存
低频 高 核心链路 P1 限流、异步化、迁到只读副本
低频 高 非核心 P3 登记并限制并发，不占用主线资源

矩阵里最容易被误判的是“一次性报表查询”。它单次耗时很长，但频率低、可延迟，正确做法通常不是加索引，而是把它从在线库挪走：放到只读副本、限定时间范围、改为异步导出。反过来，一条平均只有 30 ms 却每秒执行上千次的查询，才更应该被当作在线链路问题处理。判断依据是调用来源、执行计划和业务时段，而不是单看耗时。

第二个问题是归因。归因不是重新做一遍单条 SQL 诊断，而是把问题放进有限的几个抽屉，交给对应的责任方。抽屉分得越清楚，修复动作越可复制，复盘时也越容易发现系统性缺口。

这张表只用于路由，不展开每一类的诊断细节。比如“索引缺失”背后可能是联合索引顺序不对，也可能是选择性判断错误，具体分析属于单条 SQL 优化的范畴；治理流程关心的是它有没有被分到正确的人手里，以及修复后有没有指标验证。每条进入清单的问题都应该带上四个字段：指纹、责任服务、负责人、期望改善的指标。没有负责人的条目，不进入排期。

SQL 审核门禁：把问题挡在发布前

治理性价比最高的环节是发布前。一条慢 SQL 在生产上运行一天消耗的资源，往往超过评审它所需的十分钟。门禁的目标不是让所有 SQL 都完美，而是让高风险 SQL 必须经过有经验的人看一眼。

门禁分三层。第一层是开发自检，提交前按清单过一遍；第二层是代码评审，评审人必须能看到最终执行的 SQL，而不是只看到 ORM 的链式调用；第三层是 DBA 会签，只针对大表 DDL、新索引、批量任务和核心链路的新查询。三层各司其职，既不把所有压力压给 DBA，也不让门禁流于形式。

检查项 要求 级别
执行计划 新查询附 EXPLAIN 结果与预估扫描行数 必须
条件列 WHERE 与 JOIN 列类型一致，有可用索引 必须
字段选择 禁止 SELECT *，覆盖索引场景需注明 必须
模糊匹配 禁止前导通配 LIKE '%关键词' 必须
列上运算 索引列禁止套函数或表达式，函数索引需评审 必须

几条禁令值得单独说明。SELECT * 的问题不只是多传字段，它会让原本可以走覆盖索引的查询被迫回表；前导通配的 LIKE '%关键词' 无法使用普通 B-Tree 索引；在索引列上套函数或运算会让索引失效，MySQL 8.0.13 起虽然支持函数索引，但需要单独评审，不能当作默认解法；超长 IN 列表则会让解析和执行付出额外代价。禁令的目的不是禁止，而是要求例外必须说明理由。

ORM 是门禁最容易漏掉的地方。框架生成的 SQL 往往带多余字段、隐式类型转换，或者在一个循环里逐条查询。评审时要求开发在测试环境打开 SQL 日志，把一次请求实际执行的语句贴出来；对核心接口还要统计单次请求的 SQL 条数，超过阈值就视为 N+1 嫌疑。测试数据同样要讲究，几十行的测试表上所有查询都很快，只有接近生产量级的数据才能暴露扫描和排序问题；无法复制生产数据时，至少保证数据量和分布同数量级。

门禁要有例外通道。线上故障需要紧急修复时，允许先上线后补审，但必须在四十八小时内补齐记录，并说明为什么绕过。例外不可怕，可怕的是例外没有记录，下次复盘时说不清哪些问题是门禁放进来的。

索引治理与容量边界

从加索引到管索引

很多团队对索引的态度是只加不减。查询慢了加一个，报表慢了再加一个，几年之后单表十几个索引，写入越来越慢，缓冲池被大量索引页占满，却没有人说得清每个索引服务哪条查询。索引治理要把“加”变成“管”：有清单、有责任人、有准入和退出机制。

清单至少包含四类信息：索引所属的表与服务、建立的日期与原因、当前的读写使用次数、占用的空间。MySQL 的 sys 库提供了两个现成视图，可以先做一轮盘点。

这两个视图只能作为线索，不能直接作为删除依据。未使用统计自实例重启后重新计数，季节性查询可能刚好没跑；唯一索引和主键即使“未使用”也不能删；冗余索引的判断基于最左前缀，实际执行计划仍可能依赖它。MySQL 8.0 提供不可见索引，可以先把候选索引设为不可见，观察一个完整业务周期，确认没有性能回退后再删除；5.7 没有这个能力，只能用低峰期试删加快速回滚的方式。

索引不是免费的。每个二级索引都意味着写入时要多维护一棵树，更新越频繁的表，写放大越明显；索引页还会挤占缓冲池，间接影响读性能。治理时应给单表索引数量设一个预算，例如不超过五个，超过就要说明理由。新增索引的申请必须附带目标查询、当前执行计划和预期收益，不能只说“加个索引试试”。

变更执行同样需要流程。大表加索引优先使用在线 DDL，并在语句中显式声明算法与锁策略：

ALGORITHM=INPLACE 表示尽量原地完成，LOCK=NONE 表示允许并发读写；并非所有操作都支持这两个选项，执行前要查官方文档确认，先在同等数据量的从库或影子表上演练。即使支持在线变更，大表操作仍会产生大量 IO 并可能导致主从延迟，应该放在低峰窗口，并准备好中止与回滚方案。删除索引尤其要谨慎：删错了再建回来，代价可能比当初加索引更大。

不要用分库分表掩盖慢查询

索引治理解决的是访问路径，容量规划解决的是资源是否够用，两者不能互相替代。容量规划从增长曲线出发：统计过去六到十二个月的数据量、QPS 和峰值倍数，按业务计划推算未来半年的需求，再留出三到五成的余量。没有增长数据时，宁可先做一次压测，也不要用“感觉还行”做判断。

当单机接近瓶颈时，手段是有顺序的。先做读写分离，把报表和只读流量迁走；再加缓存，挡住热点读；然后归档冷数据、按时间分区，把单表规模控制住；最后才考虑分库分表。这个顺序背后的逻辑是复杂度：读写分离只增加路由和一致性取舍，缓存要处理失效与穿透，归档和分区改变数据生命周期，而分库分表会引入跨库查询、分布式事务、全局 ID 和扩容迁移，运维成本是数量级的跃升。

分库分表最危险的用法，是拿来掩盖糟糕的查询。一个全表扫描的查询，拆到十个库之后会变成十次全表扫描；一个没有边界的导出，拆库之后会变成跨十个库的聚合，问题只会更复杂。分片之前应先确认：现有慢查询已经清理到可接受水平，单表数据量确实超出单机舒适区，并且业务能接受分片键带来的查询限制。否则，分片只是把技术债搬到了更贵的地方。

故障闭环：从告警到复盘

治理流程必须能处理“已经慢了”的时刻。一个完整的闭环包括告警、分诊、止血、定位、修复、回归和复盘，任何一环缺失，问题都会以另一种形式回来。

flowchart TD
  A[症状告警] --> B[确认影响面]
  B --> C[止血：限流、终止查询、回滚]
  C --> D[定位根因]
  D --> E[修复并验证]
  E --> F[补充回归用例]
  F --> G[复盘与行动项]
  G --> A

告警要基于症状而不是单条 SQL：P99 抬升、慢查询总耗时、锁等待、连接池等待，比“某条 SQL 超过一秒”更能反映用户受影响的程度。告警触发后先确认影响面：是单条指纹、单个实例，还是一次发布带来的普遍退化。止血手段按风险从低到高排列：终止异常查询、对入口限流、把报表切到只读副本、回滚最近的发布。KILL QUERY 只终止语句并保留连接，通常比 KILL CONNECTION 安全；执行前要核对连接 ID 和发起用户，避免误杀。

值班手册要把这些动作写成可执行的步骤：如何查当前排在前面的指纹，如何判断锁等待的持有者，哪些操作需要升级给 DBA，回滚命令是什么，对外如何同步。手册不必长，但必须在没有上下文的情况下也能照做。事后复盘只谈系统和流程，不追究个人；每个行动项要有负责人和截止日期，并在下一次周会上验收。

组织上，每条 SQL 都应该有归属的服务和团队。DBA 负责平台、规范与高风险变更的会签，不负责替所有业务修 SQL；后端团队对自己服务的访问路径负责。每周用三十分钟过一遍按总耗时排序的前十条，逐条确认负责人和进展，比每月开一次大会更有效。监控面板要对开发可见，而不是只挂在 DBA 的屏幕上。延迟 SLO 和错误预算可以把“要不要现在修”变成可讨论的数字：预算充足时按计划排期，预算快速消耗时自动升级优先级。衡量治理效果至少看四个数：慢查询条数、总耗时、P99 和重复发生率。

自动化与九十天落地

流程稳定之后，再用自动化减少重复劳动。每天定时把前二十条指纹和环比变化发到团队频道；在 CI 中对新增或修改的 SQL 做静态检查，缺少执行计划或命中禁令时阻止合并；对症状设置带持续时间的告警，避免抖动误报；在慢查询超过阈值时自动抓取执行计划存档，方便事后对比；把核心查询放进基准测试集，索引或结构变更后跑一遍。自动化的边界要清楚：自动终止查询、自动创建索引这类动作风险很高，必须保留人工确认。

落地不要铺得太开。下面的九十天计划把治理拆成六个阶段，每个阶段都有可验收的交付物。表中的数字是目标假设，不是承诺。

阶段 时间 交付物 成功标准（示例）
基线 第 1 至 2 周 指标看板、慢查询清单、服务归属 核心服务全部有负责人
清理 第 3 至 4 周 按总耗时排序的前二十条修复 总耗时下降三成
门禁 第 5 至 6 周 评审清单、CI 检查、例外流程 新查询评审全覆盖
索引 第 7 至 8 周 索引清单、冗余与未使用索引处置 单表索引数达标
运营 第 9 至 10 周 周会机制、值班手册、回归集 周会连续四周按时召开
复盘 第 11 至 13 周 季度报告与下一轮计划 P99 与重复率有基线对比

最常见的失败模式有六种：把治理当成一次性运动，风头过去就没人管；把问题甩给 DBA，业务团队始终不掌握自己的访问路径；没有发布门禁，一边清理一边新增；只靠加索引解决所有问题，最后承受写放大和索引膨胀；忽视 ORM 生成的 SQL，评审看到的和实际执行的不是一回事；没有回归测试，同一条 SQL 换个写法又回来了。避开这六种，治理就成功了一半。

小结

慢查询治理的本质，是把偶发的救火变成可重复的日常：用指标基线定义什么是慢，用发现管线持续看见问题，用分诊矩阵决定先修什么，用发布门禁和索引治理阻止新问题，用故障闭环与组织机制保证问题不反弹。它不追求一次性清零，而追求总量持续下降、重复问题越来越少。九十天计划只是起点，真正起作用的是每周三十分钟的评审，以及每条 SQL 背后那个明确的责任人。
