Kibana 日志分析实践

日志平台搭好之后，真正决定排障效率的往往不是集群规模，而是查询入口是否顺手。本文以 Kibana 7.9 为例，从索引模式讲起，依次介绍 Discover、KQL、可视化与仪表盘，并给出一条可复用的日志分析路径。读者不需要事先熟悉 Elasticsearch 查询 DSL，只要日志已经进入索引，就可以跟着本文把日常排障跑通。

Kibana 的定位与索引模式

Kibana 不存日志

在 ELK 组合里，三个组件各管一段：Elasticsearch 负责存储与检索，Logstash 与 Beats 负责采集和加工，Kibana 则是面向人的查询与展示层。Kibana 的服务端是一个 Node.js 进程，浏览器里的页面通过它向 Elasticsearch 发 REST 请求，再把结果画成表格和图表。日志始终躺在 Elasticsearch 的索引里，Kibana 既不复制也不持久化日志，停掉 Kibana 只会失去界面，不会丢数据。

不过 Kibana 并非完全无状态。索引模式、保存的搜索、可视化与仪表盘都以“保存对象”的形式存在 Elasticsearch 的 .kibana 索引中，因此重启 Kibana 后这些配置仍在。理解这一点很重要：排障时看到的每一张图，背后都是一次真实的查询，图的快慢取决于 Elasticsearch 的响应，而不是 Kibana 的渲染。

版本方面，Kibana 与 Elasticsearch 应保持同一版本线，本文约定两者都是 7.9；跨大版本混搭往往在启动阶段就报错。

索引模式：给查询划定范围

索引模式（index pattern）是 Kibana 里最基础的对象。它不复制数据，只记录三件事：匹配哪些索引、用哪个字段做时间过滤，以及字段列表的缓存。所有搜索、可视化和仪表盘都必须挂在一个索引模式上。

创建入口在 Management 的 Index Patterns 页面。第一步填写名称，可以直接写索引通配符，例如 filebeat-* 或 logs-2020.10.*，也可以写一个指向多个索引的别名。第二步选择时间字段，通常是 @timestamp；只有映射为 date 类型的字段才会出现在下拉框里。保存之后，Kibana 会读取索引的映射，生成字段列表。

这里有两个容易忽略的细节。其一，索引模式只做名称匹配，logs-* 会把同名前缀下所有索引都纳入查询，包括测试环境或已经不再写入的历史索引；范围越宽，查询越慢，结果也越容易被污染，因此生产环境更推荐使用语义明确的别名。其二，映射发生变化后，新字段不会自动出现，需要在索引模式页面点击刷新字段，否则字段列表里始终看不到它。

如果 Elasticsearch 配置了跨集群搜索，索引模式里也可以写远程集群前缀，例如 remote1:logs-*。Kibana 只是把这个名字原样交给 Elasticsearch，真正的网络连通与权限仍在集群侧配置，这一点在混合云环境里很常见。

时间字段的选择决定了后面一切。没有时间字段的索引模式只能关闭时间过滤，Discover 里也不会出现直方图，日志分析基本无从谈起。因此接入新日志时，先确认时间字段的映射和取值，再谈图表。

Discover：从时间轴到单条文档

Discover 是使用频率最高的页面，它回答两个问题：这段时间里发生了什么，以及某一条日志长什么样。页面从上到下大致分为时间选择器与查询栏、时间直方图、字段列表、文档表格四块。

时间选择器支持相对时间（最近 15 分钟、最近 24 小时）和绝对时间两种输入方式。排障时建议先用相对时间快速扫一眼，锁定异常区间后立刻切成绝对时间，避免页面自动刷新把现场冲掉。直方图按时间分桶展示文档数量，桶的粒度由 Kibana 根据时间范围自动推算；在图上拖选一段区间，时间过滤器会同步收窄，这是缩小范围最快的方式。柱子的缺口同样有信息量：完全没有柱子，说明那段时间没有日志写入，问题可能出在采集端而不是应用端。

左侧字段列表分为已选字段与可用字段两部分。把字段加到表格里，相当于在查询时显式指定要取的列；列可以拖动排序，点击列头可以排序，点开行首的展开按钮则能看到这条文档的全部字段。展开视图里通常还能查看原始 _source、单独查看这一条文档，以及按索引顺序加载它前后的若干条日志。按时间前后串联上下文，比盯着一条孤立的错误信息更有用，很多超时问题在前一条日志里就写着原因。

这里需要区分 _source 与字段值。_source 是写入时保存的原始 JSON，字段值则可能来自 doc values，也就是为聚合和排序准备的列式存储。Kibana 可以通过 docvalue_fields 只取这些列值。对于分词后的 text 字段，doc values 里存的是词项而不是原文；如果采集管道在写入前删掉了某个字段，它不会出现在 _source 里，但只要建立了 doc values，仍可能作为列显示。反过来，_source 里有而映射中没有的字段，无法用于查询和聚合。遇到表格里的值和原始日志对不上，先想想这两套数据来源的差别。

还有一个常见误解是命中总数。Elasticsearch 默认只精确统计到一万条，超过之后 Kibana 显示的数字只是下限，只能用来判断量级。

KQL 与过滤器：把范围收窄

Kibana 7.x 的查询栏默认使用 KQL（Kibana Query Language），它比 Lucene 语法更接近自然表达。直接输入关键词，Kibana 会在索引模式的全部字段中查找；写成“字段:值”则只匹配指定字段。例如：

双引号表示短语，and、or、not 组合条件，比较运算符用于数值和日期，* 与 ? 是通配符。判断字段是否存在，可以写 trace_id:*，取反就是缺失。混合逻辑时用括号分组，别依赖运算符优先级。

KQL 能覆盖日常大部分查询，遇到正则、模糊匹配或邻近搜索才需要切到 Lucene 语法：正则写作 message:/.*timeout.*/，模糊匹配在词后加 ~，邻近搜索写成 "connection refused"~3。切换入口在查询栏左侧的下拉框，两种语法不能混写，切换后原语句会按另一种规则重新解析。以 * 开头的通配符会扫描大量词项，能不用就不用。

查询栏之外还有过滤器。过滤器以结构化标签出现，字段、运算符、值分栏填写，可以取反、临时禁用，也可以固定到所有应用。它和查询语句是“与”的关系，两者同时生效。笔者习惯把服务名、环境、主机这类稳定维度放进过滤器，把临时的错误文本放进查询栏。过滤器不依赖语法，交接时别人一眼能看懂；调整查询文字时，也不会误删范围条件。

保存、分享与复现

一次有效的排查值得保存。Discover 右上角的 Save 会把当前查询、过滤器、列与排序存成保存的搜索，下次直接从已保存对象打开。命名时写清服务和现象，例如“checkout 5xx 按主机”，比默认名称有用得多。

分享有三条路径。短链接把当前状态（含时间范围）冻结成短地址，适合贴进工单；CSV 导出按当前列生成文件，数据量大时会转成后台任务；嵌入代码给出一段 iframe，可放进内部门户。三者都受登录态与权限约束，链接并不是免登录通行证。需要跨环境复现时，用 Management 的 Saved Objects 导出与导入，把索引模式、搜索、图表和仪表盘打成一个文件；导入方版本不宜相差太大，否则面板可能空白。

可视化：用聚合回答问题

可视化的本质是聚合。每个图表先选索引模式与时间范围，再决定怎么分桶、算什么指标。桶聚合负责切分数据：date histogram 按时间切，terms 按字段取值切，filters 按自定义条件切；指标聚合负责计算：count 数条数，average 求均值，percentiles 求分位值。字段类型选错，图就画不出来，这是新手最常见的卡点。

折线与面积图适合看趋势，通常以 date histogram 为横轴、count 为纵轴；把间隔固定为一分钟或五分钟，多个面板之间才容易对齐。柱状图适合比较离散的类别，饼图适合看份额，但切片超过六七个就难辨认。数据表可以同时放多个指标并按列排序，是做 Top N 的主力；Metric 只显示一个数字，适合放在仪表盘顶部；热力图用两个桶维度加颜色深浅，观察延迟分布随时间的变化很直观；TSVB 能在一个面板里放多条序列、做数学运算或加发布标注，代价是配置项更多。

日志分析常用的图不过几种：错误率随时间的变化、按服务拆分的日志量、Top N 请求路径、状态码分布、耗时的 p95 与 p99。错误率可以用 filters 桶分别统计错误数与总数，再在数据表里算比例；Top N 必须用 keyword 字段，text 字段无法直接聚合；状态码分布用 terms 桶最直接，排序方式则要按需求指定。

Split series 能把一条曲线拆成多条，例如按 service.name 拆分，一眼看出是哪个服务把错误量拉高。但拆分的基数不可控，字段取值一多，桶的数量成倍增长，图不可读，集群也更吃力。拆之前先想清楚要回答什么问题。

仪表盘与排障流程

仪表盘把若干可视化和保存的搜索拼在一页。新建 Dashboard 后从已保存对象添加面板，拖动调整大小与位置，顶部的时间范围和过滤器对所有面板生效，因此各面板要使用兼容的时间字段。面板可以配置跳转链接，把概览引向明细或外部系统；夜间值班切到深色模式，长时间盯屏会舒服一些。设计上最重要的原则是一块仪表盘只回答一个问题：顶部放核心指标，中间放趋势，底部放 Top N 与明细搜索。面板控制在十个以内，标题写清单位和过滤条件，比堆满整屏更有用。

排障时，可以按下面的顺序走：

flowchart TD
    A[明确症状与时间窗] --> B[选索引模式]
    B --> C[看总量与错误量直方图]
    C --> D[按服务与主机过滤]
    D --> E[用 KQL 找错误模式]
    E --> F[展开日志取 trace_id]
    F --> G[用 trace_id 串起全链路]
    G --> H[对照指标与发布记录]
    H --> I[保存搜索与短链接]

先定时间窗。用户说“两点零五分开始报错”，就把范围设为两点前后各十五分钟，而不是默认的最近二十四小时。接着选对索引模式，先看总量与错误量的直方图，确认异常是突增、归零还是缓慢爬升。然后用过滤器收窄到具体服务、环境和主机，再用 KQL 找错误文本。展开一条错误日志，取出 trace_id 或 request_id，用它搜索所有服务的日志并按时间排序，就能重建这次请求经过的每一个环节。最后把日志时间线与指标、发布记录对照，确认根因。过程中产生的搜索和短链接要随手保存，它们既是工单证据，也是复盘材料。

权限、成本与常见坑

空间（Space）用于多租户隔离：每个空间有独立的保存对象，团队 A 的仪表盘不会出现在团队 B 的列表里。角色决定读写边界，只读用户给 Kibana 的 read 权限，再加索引层面的 read 与 view_index_metadata 即可，不要图省事授予通配符索引的全部权限。

性能的大头在查询范围。先收窄时间，再谈其他；聚合走 keyword 字段；避免前导通配符；Discover 默认只取五百条样本，需要更多时再调大。聚合桶数量受 search.max_buckets 限制，默认一万，terms 基数过高会直接报错；Kibana 的请求超时可调，但盲目调大只会让慢查询拖得更久。

常见坑集中在几处：时间字段选错或时区理解错，日志整体偏移；同名字段在不同索引里类型不一致，Kibana 标记为冲突后无法使用；对 text 字段做聚合；索引模式写成星号，把无关索引一起查；仪表盘面板过多，打开一次就打出几十个查询；没有保留策略，磁盘被历史日志占满。这些问题大多在接入阶段埋下，提前约定字段与命名比事后救火便宜。

小结

Kibana 是 Elasticsearch 之上的查询与展示层，索引模式决定了查询范围与时间语义。日常排障先用 Discover 定位时间窗和异常日志，再用 KQL 与过滤器收窄，随后用聚合图表验证判断，最后把结论沉淀为仪表盘和保存的搜索。把握住时间字段、keyword 字段与查询范围这三件事，大多数“Kibana 很慢”的问题都会消失。
