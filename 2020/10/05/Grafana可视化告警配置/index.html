Grafana 可视化告警配置

很多团队已有 Prometheus 或 Elasticsearch，却仍靠命令行和临时查询判断系统是否健康。Grafana 补上的正是这一层：把分散在各处的指标画成图，并在图上直接配置告警。本文以 Grafana 7.x 为背景，从数据源、面板、变量讲到告警规则与通知渠道，最后讨论告警设计、权限与 GitOps 落地中的取舍。读完后，你应能为一个节点集群搭出可维护的看板与告警。

Grafana 在可观测性中的位置

Grafana 是一个可视化与告警前端，自己既不抓取指标，也不长期存储。打开看板时，浏览器把面板查询发给 Grafana 服务端，服务端再按数据源配置请求 Prometheus、Elasticsearch、MySQL 或 Loki，拿到结果后变换与渲染。因此面板多、刷新快，压力最终落在数据源上，而不是 Grafana 页面上。

正因为它只做“查询与展示”，Grafana 才能把不同来源的数据放进同一块屏幕：指标来自 Prometheus，日志来自 Loki，业务报表来自 MySQL，三者可以并排且时间轴对齐。这也是很多团队选择它的原因：不必为每类数据单独做一个查询界面。

数据源接入之后，查询编辑器是每天都要打交道的部分。以 Prometheus 为例，查询由指标名、标签选择器和区间组成，Legend 一栏写 即可显示实例名；Min step 控制返回点的密度，留空则跟随看板的时间范围计算。MySQL 数据源直接写 SQL，用 $__timeFilter(created_at) 注入时间条件，用 $__timeGroup(created_at, ‘5m’) 做分桶。Elasticsearch 数据源则是聚合式的：先选指标聚合，再选桶聚合，最后按字段分组。三者形态不同，思路一致——先定时间范围，再定聚合粒度，最后定分组维度。

需要提醒的是，Grafana 也不是监控系统的“大脑”：采集与长期存储仍由数据源负责，没有的数据既画不出来，也告不出来。

安装与配置

安装有两种常见方式：包管理器适合长期运行的虚拟机，容器适合快速试用与 Kubernetes 环境。下面以 7.1 系列为例固定版本号，避免无意升级的差异。

配置文件 grafana.ini 分为若干段。[server] 决定监听端口与外部访问地址；[database] 默认是 SQLite，单机足够，多副本或需要备份时换成 MySQL 或 PostgreSQL；[security] 的 secret_key 用于加密数据源密码，上线前必须替换并妥善保存，轮换它会导致已保存的密钥无法解密；[smtp] 决定邮件能否发出；[alerting] 控制告警评估的总开关与最小间隔。所有配置都能用 GF_ 前缀的环境变量覆盖，例如 GF_SECURITY_ADMIN_PASSWORD，容器部署时更常用，避免把密码写进镜像。

面板：查询、变换与显示

面板是最小展示单元，由查询、可视化类型和字段选项三部分组成。7.0 之后的面板编辑器把它们放在右侧的 Query、Transform、Alert 与 Panel、Field、Overrides 标签页里，比旧版统一。

选图先看数据形态。随时间变化的量用 Time series；只需要一个当前值、并且要与阈值比较时用 Stat 或 Gauge；多个对象的同一指标横向比较用 Bar gauge；明细与多维聚合结果用 Table；分布类数据用 Heatmap。

一个面板可以挂多条查询，命名为 A、B、C，每条都能单独隐藏。Transform 标签页在渲染前加工结果：Merge 把多条查询合并到一张表，Organize fields 隐藏或重排列，Reduce 把序列压成单值，Labels to fields 把标签提升为列。很多“图做不出来”的问题其实是缺一步变换，而不是查询写错。

Overrides 解决“同一面板里不同字段需要不同规则”的问题，典型场景是一块面板同时画磁盘使用率与剩余空间，前者用百分比、后者用字节，或者给某条序列单独设置颜色。单位、小数位、最大最小值、阈值与配色都属于 Standard options，既能作为默认值，也能按字段覆盖。

阈值有绝对值和百分比两种模式。CPU 使用率这类天然是百分比的指标，直接把阈值设成 85 与 95；字节类指标用百分比模式，避免写死随机器规格变化的数字。坐标轴要标明单位，否则图在别人眼里只是一条曲线；图例用 、 这类模板生成，换机器时就不必改图。

变量：让一张看板适配多个对象

一台机器一块看板不可持续，变量（Variable）让同一块看板适配不同实例、环境与聚合粒度。

最常用的是 Query 与 Custom 两类。Query 变量从数据源取候选值，Prometheus 数据源可以直接写 label_values(node_uname_info, instance)，得到所有上报的实例；Custom 变量是手写的逗号分隔列表，例如 prod,staging，适合不来自指标的环境选择。Interval 变量给出 1m,5m,10m 这样的时间粒度选项，配合查询里的 $interval 使用；Constant 与 Text box 用于固定值或临时输入。

变量定义好之后，在查询里用 $instance 或 ${instance} 引用。多选变量在 Prometheus 查询里要写成正则匹配：instance=~”$instance”，并在变量设置里配置 All 选项对应的值，通常是 .*。不配的话，选“All”时查询会拿到字面量 All，结果为空，这是最常见的变量坑。

链式变量让第二个变量的候选值依赖第一个。例如先选 job，再选 instance，后者的查询写成 label_values(node_uname_info{job=~”$job”}, instance)，Grafana 会在上游变量变化时刷新下游候选值。变量层数不宜超过两层，否则很难判断当前看到的是哪个组合。

看板拥挤时用 Repeat：给面板设置 Repeat by 变量并勾选 Horizontal，面板会按变量的每个取值复制一份，标题带上 $instance。它适合“每个实例一张小图”的场景；实例超过二十个时，更合适的是筛选后看一张聚合图，而不是让浏览器渲染几十个查询。

Grafana 7.x 的面板告警

7.x 的告警规则挂在面板上，而不是独立的规则列表里。规则继承面板的查询，由 Grafana 服务端按固定间隔评估；只要进程在跑，即使没人打开看板，告警也会评估。这是它与“图上那条红线”的本质区别。

一条规则需要填清楚五件事：评估间隔（Evaluate every）、持续时长（For）、条件（Conditions）、无数据与出错时的状态、通知渠道。条件由三部分组成：对哪条查询、取哪个聚合值、与阈值如何比较。聚合值可选 avg、max、min、sum、count、last，时间范围通常写 5m 或 now；比较方式有 above、below、outside range、within range。例如 WHEN avg() OF query(A, 5m, now) IS ABOVE 85，含义是“查询 A 在过去五分钟的平均值大于 85”。

持续时长决定“连续满足多久才算真的告警”。设为 10m 时，条件首次满足后规则进入 pending，十分钟内只要有一次评估不满足就回到 ok。没有 for 的规则把每次瞬时抖动都当成故障，这是通知风暴的头号来源。

无数据（No data）与执行出错（Execution error）要显式设置。默认的 No data 不一定发通知，而“采集器挂了”恰恰是最需要知道的故障。对关键指标，把 No data 设为 Alerting；对本来就稀疏的业务指标，保持 No data 更合理。执行出错通常是查询语法或数据源超时，设成 Alerting 可以暴露配置问题，但要有对应的处理流程。

通知渠道（Notification channel）决定告警发到哪里。邮件依赖 [smtp] 配置；Webhook 把 JSON POST 到指定地址，适合接入内部值班系统或聊天机器人；Slack 用 Incoming Webhook 地址即可。渠道可以按严重级别拆分：critical 发邮件加电话，warning 只发群。发送前用 Test 按钮验证，能省掉“告警响了但没人收到”的排查。静默（Silence）用于计划内维护，按标签匹配一段时间内的告警，避免维护窗口刷屏。

告警设计：症状、抖动与路由

告警要区分症状与原因。症状是用户能感知的：错误率上升、延迟变大、可用性下降；CPU 高、连接数多、磁盘将满属于原因或容量信号。值班时先看症状告警，能直接回答“现在有没有故障”，原因类指标更适合放在看板上做定位。原因指标全都做成告警，结果是手机一直在响，却没人知道业务是否真的受影响。

阈值要带一点回滞的思路。7.x 的单个条件没有“恢复阈值”参数，只有比较符号与阈值，同一规则里做不出 85 触发、75 恢复的双阈值。替代办法是用 for 拉长判定窗口、用较长聚合区间平滑毛刺；确需双阈值时，把判定放到 Prometheus 的 recording rule 里。评估间隔与聚合窗口也要匹配：15s 采集、1m 评估、5m 平均是常见组合。

防抖动主要靠三件事：给所有规则加 for；让聚合窗口覆盖至少两三个采集周期；避免用 last 只看最后一个点，它在数据断点或补点时最容易误报。

告警疲劳是组织问题，不是配置问题。每条告警都应可执行：收到后知道看哪块看板、执行哪段排查、找谁确认；做不到的应删掉或降级为看板上的红线。每周花十分钟清理长期不触发或误触发的规则，比一次大重构更有效。分级按影响面而不是按指标名：critical 走电话或值班轮询，warning 进群或工单，info 只留在看板上。消息里带上看板链接、当前值、阈值与 runbook 地址，并写明负责团队。

与 Alertmanager 的分工也值得说明。Grafana 的告警胜在“看图即配”，适合以看板为中心、规则不多的小团队。Alertmanager 提供分组、抑制、路由树、静默与多副本去重，适合服务多、告警量大、需按团队分流的场景，规则进 Git 还能评审。两者不是替代关系：核心告警走 Prometheus 规则加 Alertmanager，Grafana 保留少量与看板强相关的临时规则。规则写法与 for、absent 等细节见 619 篇。

常见的坑：看板选“最近 6 小时”而告警窗口是 5 分钟，图表与判定对不上；对 gauge 套 rate()，得到无意义的斜率；规则没加 for，抓取抖动就触发；每个面板单独配渠道，同一故障产生十几条消息；看板只增不减，命名逐渐失控；告警历史只留在注解与数据库里，跨月复盘时找不到。

权限、Provisioning 与 GitOps

多人协作先分清三个层次：组织（Org）是租户边界，数据源与看板在组织间隔离；团队（Team）是组织内的分组，用于批量授权；文件夹（Folder）是看板目录，也是常用的授权单位。角色只有三档：Viewer 只能看，Editor 能改看板与告警，Admin 还能管理用户与数据源。给业务方 Viewer，给值班同学 Editor，管理员控制在个位数。

看板自带版本历史：每次保存可写说明，之后能对比差异并回滚。排查“昨天还好好的”这类问题，先看版本记录往往比看指标更快。快照（Snapshot）保存某一刻的渲染结果，适合在复盘里固定证据，但它不是备份，也不会随数据源更新。

真正让看板可持续的是 provisioning。数据源与看板的 YAML 放在 provisioning 目录下，Grafana 启动时加载并监听变化。Provisioned 的看板在界面上只读，正好阻止了“线上随手改一版”的漂移。看板 JSON 从界面导出后，去掉 id 与 version、给定稳定的 uid，再提交到 Git，变更走合并请求。

纯点击式管理的问题不在于点，而在于没有记录：谁把阈值从 85 改成 95、为什么改、出问题怎么回滚，都无从查起。把看板与数据源纳入版本控制，配合 CI 校验 JSON，成本很低，收益是每次变更都可追溯。

小结

Grafana 的价值在于把查询、展示与告警放在同一处，让看板成为团队共同的语言。用好它需要分清三层：数据源负责采集与存储，Grafana 负责查询与呈现，告警规则负责判定与通知。面板与变量解决“看得清”，for 与分级路由解决“叫得准”，provisioning 与版本控制解决“改得稳”。先把少量关键看板和少量高质量告警做扎实，再逐步扩展，比一上来铺满屏幕更有效。
