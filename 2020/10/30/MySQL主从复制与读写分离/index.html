MySQL 主从复制与读写分离

单机 MySQL 迟早会遇到读请求压满 CPU、备份把磁盘 IO 打满、主库维护只能停服这几类问题，主从复制是最常见的第一层解法。本文从复制到底解决了什么讲起，依次拆解 binlog 格式、GTID、半同步与延迟成因，再落到读写分离的几种实现与读一致性的补偿手段。读完你应该能独立搭起一主两从，并清楚哪些问题复制本身答不了。

复制能做什么，不能做什么

先说清楚动机。复制最常见的用途是扩展读能力：写仍然只落在主库一台机器上，但可以把列表页、详情页、报表这些读请求分到多台从库，用加机器的方式顶住 QPS 增长。只要业务读多写少，这个收益就非常直接。

第二类用途是把从库当成备份与容灾的落点。在从库上执行备份，不会和主库争抢锁与 IO；跨机房的从库意味着主库所在机房整体故障时，数据还有另一份。第三类是隔离分析负载，把 ETL、对账、看板指向专用从库，避免一条没走索引的统计 SQL 拖慢交易。第四类是让维护变得可控：主库换机型、改表、升级小版本时，可以先把变更放到从库验证，再安排切换。

但复制不是万能药。它不提供自动故障切换，主库挂掉后由谁接任、客户端怎么重连、如何避免两个节点同时可写，属于切换器与高可用架构的问题。它也不提供强一致：异步复制下从库始终可能落后，读到旧数据是常态而不是故障。它更不能防误操作，主库上一条没有条件的 DELETE 或 DROP TABLE 会原样传到所有从库，复制在这里只是忠实的放大器。复制同样不提升写吞吐，也不解决单表过大，那是分库分表的范畴。

记住这几条边界，后面的参数选择才有依据：我们是在用“多一份数据加多一份读能力”换复杂度，而不是买一份自动化的保险。

复制链路：线程、日志与状态字段

复制的数据源只有一个，就是主库的二进制日志。主库把每个改变数据的事务按选定格式写进 binlog，从库再照着重放一遍。整条链路上有三类线程，理解分工，排障时才知道该看哪里。

主库一侧是 binlog dump 线程，每个从库连接对应一个，负责从指定位置开始读出 binlog 事件并发给从库。从库一侧有两个线程：IO 线程负责连接主库、接收事件并顺序写入本地 relay log；SQL 线程负责读出 relay log 并在从库上执行，也就是常说的回放。因此从库上有两份日志，relay log 是“收到的”，本地 binlog 是“执行过的”，后者只有在开启 log_bin 与 log_slave_updates 时才会写。

sequenceDiagram
    participant C as 客户端
    participant M as 主库
    participant D as dump 线程
    participant IO as 从库 IO 线程
    participant S as 从库 SQL 线程
    C->>M: 提交事务
    M->>M: 写 binlog 并提交
    M->>D: 唤醒 dump 线程
    D->>IO: 推送 binlog 事件
    IO->>IO: 写入 relay log
    S->>S: 回放 relay log
    M-->>C: 返回提交成功

这张图也说明了异步复制的本质：客户端收到提交成功时，从库可能连事件都还没收到。主库上的 sync_binlog 与 innodb_flush_log_at_trx_commit 决定的是主库自己掉电会不会丢事务，和从库是否追上没有关系，两者常被混为一谈。

binlog 格式与 GTID

三种格式的取舍

binlog_format 决定 binlog 里究竟写了什么，也决定了复制能否保证一致。

STATEMENT 记录 SQL 原文，体积最小，一条影响百万行的 UPDATE 也只占几十字节。代价是回放依赖执行环境：语句里带 NOW()、RAND()、UUID()，或者 UPDATE ... LIMIT 没有配 ORDER BY，主库和从库可能选出不同的行，出问题时表现为零星的数据对不上。

ROW 记录每一行变更前后的镜像，从库按行定位、按行修改，不重新执行 SQL，因此结果确定。代价是体积：一条批量更新十万行的语句会产生十万条行事件，binlog 膨胀、传输变慢、回放压力同步上升。MIXED 试图折中，默认用 STATEMENT，遇到它认为不确定的函数再自动切到 ROW。但“哪些语句算不确定”由服务器判断，边界不直观，排查时还要先确认语句最终用了哪种格式，反而增加心智负担。

本文的建议很直接：生产环境统一用 ROW。MySQL 5.7.7 起默认值已经是 ROW，8.0 延续了这一选择。担心膨胀可以用 binlog_row_image 控制镜像：FULL 记录所有列，MINIMAL 只记录主键与被修改列，NOBLOB 跳过未改的 BLOB 与 TEXT。MINIMAL 明显减小日志，但依赖完整行镜像的订阅与闪回工具会受影响。

GTID：把位点变成集合

传统复制用“文件名加偏移量”描述进度，主库上的 mysql-bin.000017: 48213 只在这一台机器、这一份日志里有意义。主库一换，位点就失去参照，切换时人工比对 Master_Log_File 和 Read_Master_Log_Pos 既慢又容易错。

GTID 换了一种描述方式：每个事务在主库提交时分配一个全局唯一编号，形如 3E11FA47-71CA-11E1-9E33-C80AA9429562:23，冒号前是服务器 UUID，冒号后是事务序号。从库记住的不再是位置，而是一个已执行事务集合。配好开关后，从库只声明按 GTID 自动定位，主库会把缺少的事务补给它。

enforce_gtid_consistency 必须一起打开，它禁止无法用单个 GTID 表达的写法，例如在事务里更新非事务引擎的表。线上从关闭切到 ON 要按 OFF、OFF_PERMISSIVE、ON_PERMISSIVE、ON 分四步推进，每一步观察一段时间。

GTID 最实用的场景是运维：切换时只要新主库的 gtid_executed 覆盖从库，从库改一下 MASTER_HOST 就能续上，不用算偏移量。代价是空洞问题：某个事务回放失败被人为跳过，或者新从库拿到的备份里 gtid_purged 已经越过它缺失的事务，已执行集合里就会出现不连续的区间。诊断时用内置函数算差集即可：

半同步复制与延迟治理

半同步到底保证了什么

异步复制下，主库提交成功只代表自己写完了 binlog，从库收没收到完全不知道。半同步在提交路径上加了一次确认：主库等待至少一个从库回复“我已收到”，然后才向客户端返回成功。启用方式是装载插件并打开两侧开关：

这里的“收到”指事务已写入从库的 relay log 并回复确认，是否刷盘取决于 sync_relay_log；它也不是执行完成，所以从库上的查询仍可能看不到它。它保证的是至少一个副本拿到日志，而不是零丢失：那个从库若随即损坏，事务依然会丢；rpl_semi_sync_master_timeout 到期后主库会自动退化为异步，没有告警就等于系统已在裸奔。监控要看 Rpl_semi_sync_master_status 与 Rpl_semi_sync_master_no_tx，后者持续增长说明超时退化在反复发生。

性能代价是每次提交多一个网络往返，跨机房时 RTT 会直接叠加到提交延迟上。是否启用取决于业务能否接受故障时丢掉最后若干事务。

延迟从哪里来

Seconds_Behind_Master 最容易被误读：它用从库当前时间减去正在回放事件的时间戳，空闲时可能显示 0，IO 线程未运行时则是 NULL；并行复制下它只反映某个 worker 的进度，可能长期显示 0 而实际落后很多。判断真实延迟应当用 pt-heartbeat 写心跳读时间差，或者比较 GTID 集合的差集。

延迟的成因可以归成几类。架构性原因是历史上 SQL 线程只能单线程回放，主库并发写入、从库串行执行，高峰期必然堆积。事务性原因是大事务，一次删除几百万行或大批量导入，在从库上就是长时间无法中断的回放单元。对象性原因是从库表缺少主键，ROW 格式下每行变更都要全表扫描定位。此外还有 DDL 需要元数据锁且无法并行、网络带宽不足、从库磁盘 IOPS 偏低。

治理要从两头下手。源头是拆小事务、给表补主键、错峰执行 DDL 与批量导入；回放侧是打开并行复制：

LOGICAL_CLOCK 依据主库组提交的信息，把可以并行的事务分到同一组交给多个 worker，比只在多库写入时有效的 DATABASE 模式适用面广得多；slave_preserve_commit_order 保证从库提交顺序与主库一致。worker 数量不是越大越好，超过 CPU 核数后收益迅速衰减。

最后是给延迟设一个界。读写分离系统必须能回答“延迟超过多少秒就把这台从库摘掉”，这个阈值来自业务对陈旧数据的容忍度，而不是拍脑袋。没有阈值的读写分离，等于把不可控的旧数据直接暴露给用户。

读写分离：从应用到中间件

主从搭好之后，读流量不会自动分流，还需要一层路由：判断一条 SQL 发往主库还是某个从库，以及从库不可用时如何降级。

最朴素的做法是在应用层实现。数据源里配置一个主库和若干从库，用 ThreadLocal 标记当前请求是否强制走主，Spring 的 AbstractRoutingDataSource 就是常见载体，再配合注解把只读方法标出来。它链路短、透明，但每个服务都要复制一遍逻辑，扩缩容与摘库都得改配置重启。

另一种是中间件。ProxySQL、MyCat、ShardingSphere 4.x 都可以挡在应用与 MySQL 之间，集中处理路由、健康检查、权重与故障摘除，应用只连一个地址。代价是多一跳网络和多一个要运维的组件，SQL 兼容性要逐条验证。已经在用 ShardingSphere 分片的团队，复用它的读写分离最自然；只需要读写分离时，ProxySQL 的规则更轻。

无论哪种实现，几条规则不能省：事务内的读一律走主库，否则读不到本事务刚写的行；写后立即读强制走主，通常用请求级标记实现；读偏好按业务配置，报表绑定专用从库，主库留少量读兜底；从库延迟超过阈值自动摘除。中间件能摘掉不健康的从库，但提升新主、客户端重连与防脑裂属于切换器的职责，这里只点一句。

读一致性：别让用户看到旧数据

读写分离最先暴露的问题往往不是性能，而是“我刚改的东西不见了”。用户提交订单后跳转详情页，请求落到还没回放的从库，页面提示不存在；改完昵称刷新，看到的还是旧名字。压测时不易复现，高峰时几乎必然出现。

常见补偿有四种。按用户 pin 主库：写后几秒内该用户的读都走主库，实现简单，代价是这部分读不再分摊。按 GTID 等待：在从库执行 SELECT WAIT_FOR_EXECUTED_GTID_SET('...', 1)，等指定事务集合回放完再查，超时降级到主库，它精确但占用连接，不适合高 QPS 路径。关键读强制主库：订单详情、支付结果直接指定主库。缓存与前端配合：把刚写入的对象放进本地缓存供后续读命中，写成功后用返回值渲染，必要时提示数据同步中，而不是让用户以为操作丢了。

没有方案能同时做到零延迟、零成本与全局一致，可行的做法是按业务分级：资金与订单强一致，动态允许秒级陈旧，报表允许分钟级陈旧。

拓扑、配置与常见坑

最后落到一套最小可用拓扑：一台主库加两台从库，同机房那台承接线上读，另一台单独给报表，互不干扰。

server_id 必须全局唯一，重复会直接报错；log_bin 与 gtid_mode 决定主库能否被订阅；从库要同时开 read_only 与 super_read_only，前者挡不住有 SUPER 权限的账号。复制账号只给 REPLICATION SLAVE，不要图省事授 ALL。

常见的坑集中在六处：把 Seconds_Behind_Master 当成真实延迟；从库表没有主键，行回放退化为全表扫描；以为 read_only 能挡住所有写入；在从库手工改数据导致主从漂移；只监控线程状态而不设延迟告警；把重分析查询丢给线上从库却不做隔离。

小结

主从复制用一份 binlog 换来读扩展、备份源与容灾，代价是延迟与复杂度。格式选 ROW，位点用 GTID，按需上半同步，延迟靠并行复制与阈值治理；读写分离则要明确路由规则与一致性补偿。
