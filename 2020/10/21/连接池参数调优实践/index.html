连接池参数调优实践

连接池几乎是每个后端服务的标配，但参数常是从上一个项目复制来的：最大连接数拍一个 50，超时随手填 30 秒，直到数据库报 Too many connections 才回头排查。本文从建连的真实成本讲起，用排队论推导池大小的估算方法，再说明 HikariCP、Go 标准库 database/sql 与 PgBouncer 中关键参数的职责，以及泄漏与监控的排查方法。读完后，读者应能为自己的服务算出一组有依据的初始参数，并知道上线后该看哪些指标。

连接池不只是缓存

不少人把连接池理解成一个缓存：连接建立一次，之后反复使用，省掉握手成本。这个理解只对了一半。连接池至少承担三件事：摊薄建连成本、限制并发、统一管理连接的生命周期。

先看建连成本。一次 MySQL 连接要完成 TCP 三次握手，至少一个网络往返；然后是认证，MySQL 8.0 默认的 caching_sha2_password 在首次认证时可能多一次往返；如果启用了 TLS，还要叠加 TLS 握手。即便在同机内网，数据库也要为这条连接创建服务端线程、分配网络缓冲区。按请求建连意味着每秒成百上千次线程创建与销毁，max_connections 很容易被打满。

连接池把这些成本摊到启动时和少量扩容时。更重要的是限流：池的大小就是应用同时访问数据库的上限。超过上限的请求在池内排队，排队超时则快速失败，数据库承受的并发因此可预期。

连接还是有状态的资源：上面可能残留未提交的事务、会话变量或临时表，归还时必须保证事务已经结束，否则下一个借用者会继承脏会话。连接池管理的是有界资源、排队策略与生命周期，缓存只是最表面的功能。

用 Little 定律估算池大小

不要急着抄参数，先算数量级。Little 定律指出，系统内的平均并发数等于到达速率乘以平均停留时间。对应到连接池，所需连接数约等于目标 QPS 乘以单次数据库操作的平均耗时（秒）。

例如某服务单实例峰值 200 QPS，每个请求平均执行 2 条 SQL，单条 SQL 平均往返 10 ms，那么数据库侧的平均并发约为 200 × 2 × 0.01 = 4。它回答的是平均需求，不是上限。池要吸收突发流量和长尾延迟，通常留 1.5 到 2 倍余量，得到 6 到 8。用峰值 QPS 和 p95 延迟代替均值会更保守。

池变大并不总是更快。每条连接在数据库端都是一个工作线程，并发执行时要争抢 CPU、行锁、缓冲池的内部闩锁。连接数超过数据库的真实处理能力后，线程切换与缓存失效让单条 SQL 更慢，吞吐不再上升，延迟则沿排队曲线陡增。判断依据是：数据库 CPU 已满而池内等待时间不长，说明瓶颈在数据库，加大池只是把队列从应用搬到数据库。

HikariCP 文档给过一个经验公式：连接数 = CPU 核数 × 2 + 有效 spindle 数。它的成立前提是单库、查询短小、事务内没有远程调用。SSD 上 spindle 可近似按 1 计，4 核机器得到 9。它给出的是数量级而非定律：查询都在毫秒级时，16 核机器也不需要 33 条连接。

最后要把池放进全局看。20 个实例、每实例 20 条连接合计 400 条，而 max_connections 若是 500，还要给备份、迁移、监控留出余量，滚动发布时实例数还会短暂翻倍。单实例池大小应由（数据库上限 − 预留）÷ 峰值实例数倒推，再与 Little 定律的结果对照取较小者。

关键参数与超时配合

各语言生态的参数名不同，职责却相近。下面以 HikariCP 的命名为线索，把参数分成容量、时间、健康检查三类。

容量类包括 maximumPoolSize 与 minimumIdle。前者是硬上限，既保护数据库，也保护应用自己；设置过小会让请求在池内排队直至超时，过大则失去限流意义。后者决定常驻连接数，minimumIdle 越大，突发到来时越少经历建连；代价是每个实例都长期占着数据库线程。HikariCP 默认让 minimumIdle 等于 maximumPoolSize，官方认为固定大小池的性能和响应性最好，但前提是池大小本身已经算对。几十个实例各自固定 50 条连接，空闲时数据库背着上千个 Sleep 线程，这时把它调小更合理。

时间类有 connectionTimeout、validationTimeout、idleTimeout、maxLifetime。connectionTimeout 是从池中取连接的等待上限，决定系统过载时多久失败，必须明显小于上游 RPC 或 HTTP 超时，否则调用方已经放弃，后端还在排队。HikariCP 的默认值是 30 秒，对面向用户的接口偏长，几百毫秒到两三秒更常见。validationTimeout 限制一次探活的时间，避免坏连接拖住借用流程。

idleTimeout 回收长时间空闲的连接，maxLifetime 给连接设一个绝对寿命。前者应对流量回落，后者应对连接老化，例如 NAT 表项被中间设备丢弃、数据库端超时关闭。HikariCP 的默认值分别是 10 分钟和 30 分钟，且 maxLifetime 应当比数据库的 wait_timeout 短。

健康检查类包括 connectionTestQuery、leakDetectionThreshold。JDBC 4 之后驱动普遍支持 isValid，无需测试语句；只有老驱动才需要 connectionTestQuery，且应使用 SELECT 1 这类极轻的语句，不要用 COUNT(*)。leakDetectionThreshold 在连接被借出超过阈值时打印借用者的堆栈，它是诊断工具而非常规配置，阈值应高于正常业务的最长占用时间。

参数之外，数据库一侧的超时同样决定连接能否被安全复用。MySQL 的 wait_timeout 控制非交互连接空闲多久后被服务端关闭，默认 28800 秒，也就是 8 小时；interactive_timeout 对交互式客户端生效，mysql 命令行登录看到的是后者。很多人把它们理解为“连接最长存活时间”，其实计的是空闲时间：持续有查询的连接不会被关闭，夜里闲置的连接才会消失。

如果池的 maxLifetime 大于 wait_timeout，顺序就反了：数据库先动手，池还以为连接可用，把它借给下一个请求，于是出现 Communications link failure 或 MySQL server has gone away。这类故障有迷惑性，往往在低峰后的第一个请求爆发，高峰期反而正常。正确做法是让 maxLifetime 比 wait_timeout 小几十秒，idleTimeout 也小于它，给池留出主动淘汰的窗口。HikariCP 会在借出时检查连接是否仍然存活，但这多一次往返，只能兜底。

另一个诱因是 wait_timeout 被调小却没有同步池参数：数据库几十秒就关闭空闲连接，应用侧仍是默认的 30 分钟 maxLifetime，于是每隔一会儿就有一批请求失败。改数据库参数时必须同步检查所有客户端的池配置，包括定时任务和报表工具。

JDBC URL 上的 autoReconnect=true 是一个陷阱。它让驱动在断连后自动重连，但重连后会话状态全部丢失：临时表没了，会话变量回到默认值，未提交事务已经回滚，而应用代码对此一无所知。故障被掩盖后，问题会以数据不一致的形式在别处出现。池本身会重建连接，正确的策略是让坏连接快速失败，在幂等的业务边界重试。

连接泄漏与事务边界

连接泄漏指借出的连接没有归还，可用连接越来越少。轻度泄漏的表现是活跃连接数缓慢爬升、空闲连接趋近于零、获取连接的平均等待时间变长；重度泄漏则直接抛获取超时，数据库端 Threads_connected 只增不减，最终撞上 max_connections。它和慢查询占满池不同：后者在查询结束后连接会回来，前者不会。

定位的第一步是打开 leakDetectionThreshold，让池在超时后打印借用者堆栈，通常能指出哪一行借了没还。第二步看池指标，active 长期等于上限而 idle 为 0，基本可以确认；再对照数据库的 SHOW PROCESSLIST，如果同一来源地址上挂着大量 Sleep 连接，而应用侧没有活跃请求，说明连接被应用遗忘了。第三步是代码审计，重点看所有带 return、continue 和异常捕获的分支。

常见原因有几类。最常见的是忘记关闭：连接、Statement、ResultSet 没有放在 finally 或 try-with-resources 中，异常路径直接跳过关闭。其次是在持有连接时做远程调用、读文件、sleep，连接被占用几秒甚至几十秒，池很快被拖干。第三是嵌套借用：一个方法借了连接又调用另一个也需要连接的方法，外层迟迟不还。第四是手工事务只写了 commit，没有在异常时 rollback，连接带着未提交事务回到池中。

事务边界直接决定连接占用时长。原则很简单：进入事务后只做数据库操作，尽快 commit 或 rollback，然后立即归还连接。事务里调用 HTTP 接口尤其危险，对方的超时时间会成为你持有行锁和连接的时间，一旦对方卡住，连接池和锁等待会同时恶化。所有退出路径都要覆盖，包括参数校验失败和业务异常。

配置示例与中间件池

把结论落成配置。假设单实例池大小算得 16，数据库 wait_timeout 保持默认的 8 小时，但连接寿命仍设为 29 分钟，便于在滚动变更和中间设备维护之前淘汰旧连接。

Go 标准库的 database/sql 没有独立池对象，参数挂在 *sql.DB 上。Go 1.15 起新增 SetConnMaxIdleTime，可把空闲寿命与总寿命分开设置；此前只有 SetConnMaxLifetime。注意 sql.Open 只解析参数，不会真正建连。

如果中间还有 PgBouncer，池就变成了两层。PgBouncer 1.13 支持 session、transaction、statement 三种 pool_mode，生产上常用 transaction 模式：一个客户端事务结束后，服务端连接就被收回给其他客户端。代价是会话状态无法保留，SET 的会话变量、临时表、advisory lock、LISTEN/NOTIFY、WITH HOLD 游标都会在事务边界失效，服务端预处理语句也不能跨事务复用。依赖这些特性时应改用 session 模式，或把使用限制在单个事务内。两层的池大小要一起算：应用实例数乘以应用池大小是 PgBouncer 的客户端上限，PgBouncer 到数据库的 default_pool_size 才是数据库看到的并发。

监控与压测

池的监控要回答三个问题：多少连接在用、多少在等、等多久。活跃数、空闲数、等待线程数、获取连接的 p99 耗时与超时率，足以覆盖大部分故障。HikariCP 通过 Micrometer 暴露 hikaricp_connections_active、hikaricp_connections_idle、hikaricp_connections_pending 等指标；Go 侧可以用 sql.DBStats 把 OpenConnections、InUse、Idle、WaitCount、WaitDuration 导出到 Prometheus。数据库侧看 Threads_connected、Threads_running 和 max_used_connections，必要时用 SHOW PROCESSLIST 区分 Sleep 与 Query。

压测是验证池大小的可靠手段：每隔一段时间提高一档 QPS，记录获取连接的等待时间、p99 延迟、数据库 CPU 与 Threads_running，画出曲线找拐点。健康的形态是等待时间接近零、数据库 CPU 随流量平稳上升；等待时间先抬头而数据库还有余量，说明池偏小；数据库 CPU 先饱和、等待时间随后飙升，说明瓶颈在数据库，加连接只会更糟。单次基准的绝对值意义有限，网络延迟、数据量与缓存命中率都会改变结果，要用同构环境的数据对照。

常见误区

第一个误区是把 max_connections 当成池大小。它是服务端资源约束，不是应用该用多少，单实例池大小必须按实例数分摊。第二个误区是不设获取超时，过载时请求无限排队，应用线程池被拖死，故障扩散到整个服务。第三个误区是把报表、批处理与在线交易混在一个池里，一条跑几分钟的统计 SQL 会占住连接，在线请求只能干等，正确做法是拆分数据源或走只读副本。

第四个误区是各环境复制同一份参数：测试两个实例、生产四十个实例，同样的池大小含义完全不同。第五个误区是分库分表后所有分片共用一个池，查询可能落到错误的分片，每个物理库应有独立的池，键是数据源而不是逻辑库名。最后是重启风暴：发布时几十个实例同时启动，各自按 maximumPoolSize 建连，数据库瞬间收到大量认证请求；缓解办法是错峰发布、限制启动建连速率，或让 minimumIdle 从小值按需增长。

小结

连接池的本质是有界并发加生命周期管理，缓存只是副产品。池大小先用 Little 定律按峰值 QPS 与 p95 延迟估算，再用核数经验公式和数据库总连接预算校正，不要超过（max_connections − 预留）÷ 峰值实例数。让 maxLifetime 明显小于 wait_timeout，为获取连接设置短而明确的超时，用泄漏检测定位忘记归还的代码。事务要短，网络调用不要放进事务。最后用阶梯压测找拐点，以活跃数、等待时间和数据库线程数持续验证。
