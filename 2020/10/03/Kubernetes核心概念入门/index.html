Kubernetes 核心概念入门

本文属于《Docker 与 Kubernetes》第 19/51 篇
上一篇系列目录下一篇

很多人第一次接触 Kubernetes，会被一堆对象名和 YAML 淹没：Pod、Deployment、Service、ConfigMap 到底各管什么，什么时候该用哪一个？本文从声明式模型讲起，把日常最常用的核心对象串成一条线，最后给出一个可以直接提交的例子和一套排障思路。读完你应该能看懂一份普通的 Kubernetes 清单，并知道出问题时先看哪里。本文面向已经会用 Docker、但还没有系统用过 Kubernetes 的读者。

声明式模型：描述你想要的最终状态

Kubernetes 的核心不是“怎么启动容器”，而是“集群应该长什么样”。用户把期望状态写进 YAML 清单提交给集群，集群里的控制器不断比对实际状态与期望状态，发现差异就采取动作，这个过程称为调谐（reconciliation）。理解这一点，后面所有对象都会好理解很多。

声明式的命令可以反复执行，结果一致；命令式则依赖你记得上一步做过什么。生产环境几乎都用清单文件，因为它能进版本库、能 review、也能整体回滚。

一份清单至少包含四个顶层字段：apiVersion 声明对象所属的 API 组与版本，kind 声明对象类型，metadata 放名字、命名空间与标签，spec 才是具体规格。清单里没写的字段会由 apiserver 按默认值补齐，所以同一份清单在不同版本上可能得到略有差异的对象。同一个 kind 在不同 apiVersion 下字段也可能不同，例如 Deployment 在早期的 extensions/v1beta1 与 apps/v1 中，selector 的默认行为就不一样。新版本一律使用 apps/v1。

flowchart LR
  A[提交 YAML] --> B[apiserver 写入 etcd]
  B --> C[控制器比对期望与实际]
  C --> D{两者一致?}
  D -- 否 --> E[创建或删除 Pod]
  E --> C
  D -- 是 --> F[保持不动]

kubectl apply 与 kubectl create 的区别值得记住：apply 是“不存在则创建，存在则按清单更新”，并把上次提交的内容记录在对象的 kubectl.kubernetes.io/last-applied-configuration 注解里，用于计算差异；create 遇到同名对象会直接报错。日常部署用 apply。

Pod：最小的调度单元

Pod 是 Kubernetes 中最小的调度单位，也是最小的部署单位。一个 Pod 里可以只有一个容器，也可以有多个；这些容器共享同一个网络命名空间，也就是同一个 IP，彼此可以用 localhost 通信，还可以挂载同一批卷。这个设计让“主容器 + 辅助容器”成为一种常规模式，例如主容器写日志、sidecar 容器负责收集并转发。

Pod 有五个阶段（phase）。Pending 表示对象已创建但还没跑起来，可能是调度没完成，也可能是镜像还在拉取；Running 表示至少有一个容器在运行；Succeeded 表示所有容器都正常退出且不会再启动；Failed 表示有容器以失败状态退出；Unknown 通常是节点失联，apiserver 拿不到最新状态。

restartPolicy 决定容器退出后怎么办，取值有 Always、OnFailure、Never，默认是 Always。要注意重启的是容器而不是 Pod：Pod 本身不会“重启”，只是容器在原地被重新拉起，重启间隔会指数退避。

既然 Pod 这么基础，为什么我们很少直接创建 Pod？因为裸 Pod 没有自愈能力：节点故障时它不会被迁移，容器反复崩溃也只能一次次重启，想扩容就得手工再写一个。实际工作中 Pod 几乎总是由控制器创建和管理，我们只写控制器对象。kubectl run 在 1.18 之后也只创建单个 Pod，适合临时验证镜像，不适合长期使用。

工作负载控制器：从 ReplicaSet 到 CronJob

控制器解决的是“维持多少个 Pod、以什么方式更新”的问题。它靠两样东西工作：selector 选出自己负责的 Pod，template 描述该生成什么样的 Pod。于是标签不是装饰，而是控制器与 Pod 之间的契约。

ReplicaSet 只做一件事：保证符合 selector 的 Pod 数量等于 replicas。它很少被直接使用，因为滚动更新和版本管理由 Deployment 负责。Deployment 管理若干 ReplicaSet，每次修改 Pod 模板就产生一个新 ReplicaSet，然后按 maxSurge 与 maxUnavailable（默认都是 25%）逐步替换旧副本。历史版本保留多少由 revisionHistoryLimit 控制，默认 10 个，kubectl rollout history 能看到，kubectl rollout undo 能退回。

StatefulSet 面向有状态服务。它给每个副本固定名字（如 db-0、db-1），配合无头 Service 提供稳定的网络标识，创建和删除按序号顺序进行，还可以用 volumeClaimTemplates 为每个副本申请独立的存储。数据库、消息队列这类需要稳定身份的应用才需要它。

DaemonSet 保证每个节点上跑一份 Pod，典型用途是日志采集、监控代理和网络插件。Job 用于运行到完成的任务，通过 completions 和 parallelism 控制总任务数与并发数，失败重试次数由 backoffLimit 限制。CronJob 按 cron 表达式周期性创建 Job，其 API 在 1.19 中仍是 batch/v1beta1；它还要考虑上一次任务没跑完时怎么办，concurrencyPolicy 可以设为 Allow、Forbid 或 Replace。

对象 关心的数量 典型场景
ReplicaSet 固定副本数 被 Deployment 管理
Deployment 副本数 + 版本 无状态 Web 服务
StatefulSet 固定身份 + 顺序 数据库、消息队列
DaemonSet 每节点一份 日志、监控、网络
Job / CronJob 运行到完成 批处理、定时任务

标签（label）是键值对，用于识别和选择对象，常见约定是 app.kubernetes.io/name、app.kubernetes.io/version、app.kubernetes.io/managed-by 这一组推荐标签。选择器有等值式和集合式两种，后者写作 matchExpressions，支持 In、NotIn、Exists、DoesNotExist。注意 Deployment 的 selector 在 apps/v1 中创建后不可修改，改标签前先想清楚。

注解（annotation）同样是键值对，但不参与选择，用来放非标识性信息，例如构建号、负责人、Ingress 控制器的参数。判断标准很简单：需要被选中就用标签，只是给人或工具看就用注解。选择器的匹配是实时的，Pod 一旦被改了标签，可能立刻被原控制器放弃、被另一个控制器接管，这类问题在排障时很容易被忽略。

Service 与 Ingress：给 Pod 一个稳定入口

Pod 的 IP 随重建而变化，副本又不止一个，调用方不能直连 Pod IP。Service 用 selector 选出一组 Pod，为它们提供一个稳定的虚拟 IP 和 DNS 名，访问 web 这个 Service 时，流量会被分发到后端任意一个就绪的 Pod。集群内的完整域名形如 web.default.svc.cluster.local。

Service 有几种类型。ClusterIP 是默认值，只在集群内可达；NodePort 在每个节点上开一个端口（默认范围 30000 至 32767）把流量转进来；LoadBalancer 在此基础上向云厂商申请负载均衡器；ExternalName 则是把名字映射到集群外的域名。它们各自的转发细节和排查方法，后续文章会专门展开。

Ingress 工作在七层，按域名和路径把 HTTP 请求路由到不同的 Service，还能顺带做 TLS 终止。它不是 Service 的替代品，而是入口规则的集合，必须部署对应的 Ingress 控制器（如 ingress-nginx）才会生效。Kubernetes 1.19 起，Ingress 的稳定 API 是 networking.k8s.io/v1，字段结构与之前的 v1beta1 有差异，升级时要留意。

配置与存储：ConfigMap、Secret 与卷

把配置写进镜像是最常见的坏习惯，改一个端口就要重新构建。ConfigMap 用来存放非敏感的配置，例如配置文件、命令行参数、环境变量；Secret 用来存放密码、令牌、证书。两者用法几乎一样，区别在于用途和访问控制。

使用方式主要有两种。一种是通过 env 或 envFrom 注入环境变量，适合少量简单配置；另一种是挂载成卷里的文件，适合整份配置文件。两者在更新行为上不同：修改 ConfigMap 后，已经注入的环境变量不会变，必须重建 Pod；挂载为卷的文件会由 kubelet 定期同步，通常有几十秒延迟。如果用了 subPath 挂载单个文件，则不会更新。

Secret 的 data 字段里，每个值都是 base64 编码，这只是编码而不是加密，任何人都能解开。真正的保护来自三处：用 RBAC 限制谁能读 Secret、开启 etcd 的静态加密、不要把 Secret 清单提交到公开仓库。清单里也可以用 stringData 直接写明文，apiserver 会帮你编码。

较新的版本还提供了不可变配置：给 ConfigMap 或 Secret 设置 immutable: true 后不能再修改，只能删除重建，好处是减少 apiserver 的 watch 压力。该字段在 1.18 引入、1.19 中仍处于 beta，使用前确认集群版本。

卷（volume）解决的是容器文件系统随容器重启而丢失的问题。常用的有 emptyDir，生命周期与 Pod 相同，适合缓存和容器间共享临时文件；configMap 与 secret 卷；hostPath 直接挂节点目录，适合读取节点信息，但它读写的是 Pod 所在节点的本地目录，换节点后数据就不在了，还带来安全风险。

需要持久化时用 PV 与 PVC。PV 是集群管理员视角的存储资源，PVC 是用户提出的申请，两者按容量和访问模式一对绑定。StorageClass 让绑定过程自动化：PVC 声明 storageClassName 后，供给器会按需创建 PV，也就是动态供给。PVC 删除后，PV 按回收策略处理，常见的是 Delete 与 Retain，后者会把数据留下等待人工确认。访问模式中 RWO 表示单节点读写，RWX 表示多节点读写，具体支持哪些取决于存储后端。这部分内容较多，后续文章会单独讲。

命名空间、资源约束与健康检查

Namespace 用来做逻辑隔离，把开发、测试、生产的对象分开，也方便按团队做配额和权限。默认有 default、kube-system、kube-public 和 kube-node-lease 四个。要提醒的是，Namespace 不是网络隔离，不同命名空间的 Pod 默认可以互相访问；网络层面的隔离要靠 NetworkPolicy。

每个容器都应该声明 requests 与 limits。requests 是调度依据，调度器据此判断节点还剩多少资源；limits 是运行时的上限，CPU 超过会被节流，内存超过会被杀死，Pod 状态显示 OOMKilled，退出码通常是 137。两者都不设，Pod 在节点资源紧张时最容易被驱逐。

requests 与 limits 的设置方式决定了 QoS 等级：每个容器都设了 requests 和 limits 且对应值相等，是 Guaranteed；部分设置，是 Burstable；完全没设，是 BestEffort。节点内存不足时，驱逐顺序大致是 BestEffort、Burstable、Guaranteed，所以关键服务至少要给 requests。命名空间层面还可以用 ResourceQuota 限制资源总量，用 LimitRange 为没写 requests 的容器补上默认值，两者配合配额才真正落地。

探针要区分两件事：容器是否活着，以及容器是否能接流量。liveness 探针失败会重启容器；readiness 探针失败会把 Pod 从 Service 的后端列表中摘除，但不重启；startup 探针用于启动很慢的应用，它成功之前，另外两个探针不会生效，该探针在 1.19 中为 beta。常用参数是 initialDelaySeconds、periodSeconds（默认 10 秒）、timeoutSeconds 和 failureThreshold。

调度方面，nodeSelector 做最简单的节点标签匹配；nodeAffinity 支持更复杂的表达式；podAntiAffinity 可以把同一服务的副本打散到不同节点。节点侧则用污点（taint）拒绝 Pod，Pod 用容忍（toleration）表示自己能接受哪种污点，效果有 NoSchedule、PreferNoSchedule 和 NoExecute 三档。

动手：一个可用的 Deployment

把前面的对象拼起来，就是一个能跑的最小应用：ConfigMap 提供配置，Deployment 管理两个副本并做就绪检查，Service 提供集群内入口。示例直接用 nginx 的首页做检查路径。

出问题时先看哪里

kubectl describe 输出末尾的 Events 是最有价值的信息，大多数问题在那里都有答案。怀疑问题在节点或调度层面时，可以先用 kubectl get events --sort-by=.lastTimestamp 看最近发生的集群事件，再回到具体 Pod。四个高频状态值得记住：Pending 通常是资源不足、节点亲和性不满足或节点带了 Pod 不能容忍的污点；ImagePullBackOff 是镜像名写错、tag 不存在或私有仓库凭据缺失；CrashLoopBackOff 是容器启动后反复退出，先看 kubectl logs <pod> --previous 拿上一次崩溃的日志；Pod 显示 Running 但 READY 是 0/1，说明 readiness 探针没通过，此时 Service 的后端列表是空的，请求自然打不进来。

几个常见陷阱

第一，标签与选择器不一致。Deployment 和 Service 的 selector 写错一个字母，Pod 照样能跑，但 Service 找不到后端，表现为“容器正常、访问不通”。第二，不写 requests，调度器只能按零资源计算，节点超卖后最先被驱逐的就是它。第三，liveness 探针设得太激进，应用启动慢于 initialDelaySeconds 就被反复杀死，启动慢的服务应该用 startup 探针兜底。第四，把明文密码写进 YAML 并提交到仓库。第五，生产环境使用 latest 标签，导致每次拉取行为不可预期。第六，用 kubectl edit 直接改线上对象，集群状态与仓库里的清单逐渐漂移，下次 apply 时又被打回原形。

小结

Kubernetes 的用法可以概括成一句话：用清单描述期望状态，让控制器去逼近它。Pod 是最小调度单位，通常由 Deployment、StatefulSet、DaemonSet 这类控制器代管；标签与选择器把控制器、Service 和 Pod 连在一起；ConfigMap 与 Secret 分离配置，PV 与 PVC 分离存储；requests、探针和命名空间决定了服务能否稳定运行。学习时建议从一份最小的 Deployment 加 Service 开始，反复 apply、describe、看 Events，比背概念有效得多。等这些对象用顺了，再去读调度器、网络和存储的实现细节，会轻松很多。
