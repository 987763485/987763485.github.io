MySQL InnoDB 索引与 B+ 树

很多开发者能背出“B+ 树、聚簇索引、最左前缀”这些词，却说不清一次查询究竟读了几次页、页里到底长什么样。本文从 InnoDB 的 16 KB 页和行记录格式讲起，逐层拆开聚簇索引、二级索引、页分裂、缓冲池与统计信息，并用一张订单表把一次查询的完整路径走一遍。读者应已会写基本 SQL，读完后能根据数据分布和写入模式判断索引为何这样设计、又为何在某些场景下失效。

为什么是 B+ 树：页、扇出与树高

InnoDB 以页为单位与磁盘交互，默认页大小 16 KB。一次随机 I/O 的成本远高于页内比较，因此索引结构的第一目标不是“比较次数最少”，而是“让一次查询走过的页数最少”。这解释了为什么二叉树不适合做磁盘索引：百万行数据会形成二十层左右，最坏情况下每层一次 I/O。

哈希表能把等值查询降到接近 O(1)，但哈希值本身没有顺序，范围查询、排序、前缀匹配都无从谈起。InnoDB 的自适应哈希索引只是热点页的辅助结构，并不是可选的索引类型；MEMORY 引擎的哈希索引也只适合等值访问。B 树把数据放在所有节点上，范围扫描需要在节点之间回溯；B+ 树把真实记录全部下沉到叶子节点，内部节点只保存键和子页指针，叶子节点之间再用双向链表串联。于是等值查询走一条从根到叶的路径，范围查询先定位起点，再沿着叶子链表顺序读取。

扇出（fan-out）是 B+ 树矮胖的关键。一个 16 KB 的内部页，去掉页头、槽位等开销后，若每个目录项是 8 字节主键加 4 字节子页号，再算上记录头，一页可以放下上千个目录项。按千级扇出估算，三层树可以覆盖千万到亿级记录。根页通常常驻缓冲池，实际点查往往只需两到三次物理读。

页大小并非越大越好。页越大，树越矮，但单次 I/O 的数据量、页内维护成本和分裂时的复制量也越大；页越小则相反。16 KB 是 InnoDB 在常见磁盘和内存环境下的折中，innodb_page_size 只能在初始化实例时设定，已有实例要改就得重建。

页与行：InnoDB 存储单元的解剖

页里的几个区域

一个索引页并不是“一堆记录”，而是由固定头尾和若干可变区域拼起来的。按从前往后的顺序，可以粗略分成这样几块：

区域 大致大小 作用
File Header 38 字节 页号、页类型、前后页指针、校验和、LSN
Page Header 56 字节 记录数、堆顶、空闲链表、页层级、索引 ID
Infimum 与 Supremum 26 字节 两条虚拟记录，分别表示页内下界和上界
User Records 不定 真正存放的行记录，向空闲区方向增长
Free Space 不定 尚未分配的页内空间
Page Directory 不定 稀疏槽位，记录每组的起始偏移
File Trailer 8 字节 校验和与 LSN 的低位，用于发现半写页

File Header 里的前后页指针把同一层的页串成链，Page Header 里的 PAGE_LEVEL 标明当前页在树中的层级，叶子页为 0；PAGE_INDEX_ID 则说明这页属于哪棵索引。

页内的记录按主键或索引键升序排成一条单向链表，插入时不一定移动已有记录，而是调整链表指针和槽位。删除记录时，InnoDB 先设置记录头里的删除标记，把空间挂到页内空闲链表，等 purge 线程确认没有事务再访问时才真正回收。Page Directory 是这条链表之上的“索引”：每个槽位指向一组记录的第一条，一组通常包含 4 到 8 条记录，查找时先对槽位做二分，再在组内顺序比较。

行格式：变长字段、NULL 位图与溢出页

InnoDB 5.7 起（5.7.9 之后）默认行格式是 DYNAMIC，更早的表常见 COMPACT。以 COMPACT 为例，一条聚簇索引记录从前往后大致是：变长字段长度列表、NULL 位图、5 字节记录头、隐藏列、各列的值。变长字段长度列表按列定义的逆序写入，每个字段用 1 字节还是 2 字节，取决于该列的最大字节长度是否超过 255；NULL 位图则为每个可空列保留 1 位，NULL 值本身不再占用字段空间。

5 字节记录头里包含删除标记、记录在页内的堆号、记录类型，以及指向下一条记录的相对偏移。聚簇索引记录还会带上 6 字节事务 ID 和 7 字节回滚指针，用于 MVCC；如果没有显式主键，还会多出一个 6 字节的隐藏行 ID。二级索引记录不承担版本信息，它只保存索引列和主键列，这也是二级索引通常比聚簇索引“薄”的原因。

当一行中的变长列太长，页内放不下时，就会发生行溢出。DYNAMIC 会把整段长值放到单独的溢出页，聚簇索引记录里只留一个 20 字节的指针；COMPACT 则会在记录内保留 768 字节的前缀，再跟一个指针。溢出页不在 B+ 树的叶子里，读取它意味着额外的页访问，所以 SELECT * 碰上大 TEXT 或 BLOB 时，代价往往不在索引本身，而在这些被连带读出的溢出页。InnoDB 单行长度也有上限，16 KB 页下大约是一半页大小，超过这个限制的列必须走溢出存储。

聚簇索引：主键即数据

InnoDB 的表就是一棵以主键为键的 B+ 树，称为聚簇索引。它的叶子页存放完整行，内部页只存放主键值和子页号；因此“按主键查一行”不是先查索引再查表，而是直接在树上走到包含这行的叶子页。若表没有主键，InnoDB 会选择第一个所有列都非空的唯一索引作为聚簇键；如果连这样的索引也没有，就生成一个 6 字节的隐藏行 ID。隐藏行 ID 不可见、顺序不可控，二级索引还要额外保存它，所以生产表应显式定义主键。

主键的顺序直接影响写入。自增主键总是落在最右侧的叶子页，页写满后申请新页，分裂点靠近页尾，已有页保持很高的填充率，写入也接近顺序 I/O。随机主键则相反：新记录可能落到任意叶子页，目标页满了就从中间劈开，两个页各留一半空间；大量随机插入会制造大量半满页。UUID 作为主键时，除了随机性，还有长度问题：36 字符的文本 UUID 比 8 字节的 BIGINT 宽得多，而每个二级索引的叶子都要保存主键，主键变长会让所有二级索引一起变胖，扇出下降，树高和页数上升。

主键还应尽量短、不可变。更新主键时，InnoDB 需要把整行搬到新的位置，并更新所有二级索引里的主键副本。

二级索引：回表、覆盖与条件下推

二级索引是一棵独立的 B+ 树，键是索引列，叶子记录里保存索引列和主键。以 KEY idx_user_status_time (user_id, status, created_at) 为例，叶子记录按 (user_id, status, created_at) 排序，每条记录后面跟着主键 id。查询先在这棵树里定位，拿到一批主键，再逐个回到聚簇索引取整行，这个过程就是回表。

    R --> B["二级索引分支页"]
    B --> L["叶子页：42, 1, 时间, id"]
    L --> C["聚簇索引根页"]

如果 amount 也放进索引，例如改成 (user_id, status, created_at, amount)，第三步就可以省略：查询需要的 id、amount 都在二级索引叶子里，id 还是隐式包含的主键。这种索引叫覆盖索引，执行计划里会显示 Using index，省掉的是每行一次、共 20 次随机回表。覆盖索引的代价是索引更宽，写入要维护更多字节，缓冲池能容纳的索引页也更少；它适合少量高频查询，不适合把所有列都复制一遍。

回表之前先过滤：索引条件下推

回表次数取决于索引扫描出的候选行数，而不是最终返回的行数。假设索引是 (user_id, created_at, status)，查询条件是 user_id = 42 AND created_at >= '2020-10-01' AND status = 1。status 排在范围列 created_at 之后，无法参与定位，但它仍在索引里。MySQL 5.6 引入的索引条件下推（Index Condition Pushdown，ICP）允许存储引擎在读出索引记录后、回表之前，先用索引里的 status 做过滤，只把真正可能匹配的行交给服务器层回表。执行计划里对应的是 Using index condition，它减少的是回表次数，不是索引页的扫描量。

ICP 只对二级索引有意义，聚簇索引的叶子已是整行，没有“先过滤再回表”这一步；它也不能下推不在索引里的列。若过滤列不在索引中，优化器只能先回表再过滤，减少回表就只能靠覆盖索引或调整列顺序。

联合索引：最左前缀的物理依据

联合索引 (a, b, c) 的键是三元组，B+ 树按字典序排序：先比 a，a 相同再比 b，b 相同再比 c。这个物理顺序决定了一条查询能不能用索引定位：只有从最左列开始、连续匹配的前缀，才能让目标记录聚集在一个连续的区间里。WHERE a = 1 可以定位到 a = 1 的一段；WHERE a = 1 AND b = 2 可以进一步缩到更小的一段；WHERE b = 2 则不行，因为 b = 2 的记录分散在所有 a 值下面，只能全索引扫描。

下表列出常见条件与可用前缀的关系：

查询条件 可用于定位的前缀 说明
a = 1 a 定位到 a = 1 的连续区间
a = 1 AND b = 2 a, b 两列都参与定位
a = 1 AND b > 2 AND c = 3 a, b c 在范围列之后，只能靠 ICP 过滤
a = 1 AND c = 3 a c 不能跳过 b 单独定位
b = 2 无 最左列缺失，无法形成连续区间

列顺序没有放之四海而皆准的答案，但有几条稳定的原则：等值条件多的列放前面，范围条件放后面，排序和分组常用的列放在能延续顺序的位置；同时要考虑单列查询的频率，因为 (a, b) 天然覆盖 a 的单列查询，反过来则不成立。列顺序也不必只按选择性排：查询总带 tenant_id 时，把它放最前更利于缩小范围。

key_len 可以用来判断联合索引实际用到了第几列。它报告的是索引键中被使用的字节数，例如 BIGINT 占 8 字节，DATETIME 占 5 字节，utf8mb4 的 VARCHAR(20) 可空列约占 20 × 4 + 2 + 1 = 83 字节。看到 key_len 只有 8，通常意味着只用到了第一个 BIGINT 列；看到 13，则可能是 BIGINT 加 DATETIME。字符集、可空性和变长前缀都会影响这个数字，所以它只适合粗判。

MySQL 5.7 没有索引跳跃扫描（index skip scan）。如果查询只带 b 和 c，优化器不能跳过 a 直接利用后面的有序性，只能选择全索引扫描、全表扫描，或者走其他索引；这一点与部分商业数据库不同。遇到这种查询，通常应补一个以 b 开头的索引，或者改写查询带上 a 的条件。

当一条查询涉及多个单列索引时，优化器还可能做索引合并：对两个索引分别扫描，再按主键求交集或并集。索引合并能避免全表扫描，但它要额外维护主键集合，代价常常高于一个合适的联合索引；执行计划里出现索引合并，往往提示缺一个联合索引。

页分裂、碎片与索引维护

B+ 树的叶子页不会永远留有空位，插入总会把某些页写满。当一条记录要插入的叶子页已经满了，InnoDB 会分配一个新页，把原页的一部分记录搬过去，再在父页里加入指向新页的目录项，这就是页分裂。分裂点取决于插入位置：如果新记录落在最右侧，InnoDB 可以让左页保持很满，只把末尾少量记录搬到新页；如果落在中间，通常会把记录大致对半分，两页各留一半空闲。父页也可能因此变满而继续分裂，极端情况下树高会增加一层。

顺序主键和随机主键的差别，在页分裂上体现得最明显。自增主键的插入永远发生在最右叶，页分裂少，页填充率高，写入是顺序的；随机主键的插入均匀落在整棵树里，每次分裂都把页劈成两半，留下大量半满页。半满页意味着同样的行数需要更多页，缓冲池要缓存更多页，范围扫描要读更多页，随机 I/O 也更多。下面用一个假设的实验说明量级：一张每行约 200 字节的表，16 KB 页大约能放 70 行；顺序插入一百万行，叶子页大多接近满页；随机插入同样多的行，若分裂后平均只有一半填充，页数可能接近顺序插入的两倍。

innodb_fill_factor 控制的是索引构建或重建时每页预留多少空间，默认 100，表示不额外预留；设成 70，则在索引页上留下约三成空间，给后续插入用。它不影响普通 INSERT 的分裂行为，也不会让已经碎片的表自动变紧凑；它主要用在批量导入或重建索引时，减少重建后立刻发生分裂的概率。

删除也会产生空洞。InnoDB 先给记录打删除标记，purge 之后再回收空间；当页的填充率低于合并阈值时，InnoDB 可能尝试与相邻页合并，但合并需要加锁，也可能带来额外的记录移动，所以它不会无条件发生。长期增删之后，表会出现页内空洞和页间不连续，SHOW TABLE STATUS 里的 Data_free 可以粗略看出可回收空间，information_schema.tables 也有对应字段，但这些都是估算值。

要整理碎片，常用 OPTIMIZE TABLE 或 ALTER TABLE ... FORCE。对 InnoDB 来说，前者通常被映射为一次表重建，会重建聚簇索引和所有二级索引，并重新统计索引信息；重建期间一般允许并发 DML，但开始和结束需要短暂的元数据锁，还要额外占用接近表加索引大小的磁盘空间。大表重建可能持续很久，带来主从延迟和缓冲池抖动；如果实例没有开启 innodb_file_per_table，重建也未必把空间还给操作系统。更根本的办法是从主键和插入模式入手，而不是反复重建。

缓冲池、Change Buffer 与自适应哈希

缓冲池与 LRU 的中点插入

InnoDB 读写磁盘的最小单位是页，但真正决定性能的是这些页能不能留在内存里。缓冲池（buffer pool）就是一块按页管理的内存区域，数据页、索引页、undo 页、插入缓冲等都在其中；查询命中缓冲池时，不需要读磁盘，没命中时才发起一次页读取。innodb_buffer_pool_size 是最重要的内存参数之一，专用数据库服务器上通常设置为物理内存的 50% 到 75%。

缓冲池用 LRU 链表管理页的冷热，但不是普通的 LRU。新读入的页不会直接放到链表头部，而是插入到中点，也就是“老年代”的头部；链表前 5/8 左右是“年轻代”，后 3/8 是“老年代”。页被访问后，只有在老年代停留超过 innodb_old_blocks_time（默认 1000 毫秒）才会被提升到年轻代。这个设计是为了防止一次全表扫描把真正的热页全部挤出去：扫描读到的页即使被访问两次，只要间隔太短，仍会留在老年代，很快被后续扫描页替换掉。

判断缓冲池是否够用，可以看命中率，即 1 - Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests，但命中率高不代表没有问题：一次冷页读取可能抵得上很多次内存访问。更有意义的是看业务查询的响应时间、磁盘读吞吐，以及热点表的大小是否明显超过缓冲池。实例重启后，缓冲池是空的，InnoDB 可以在正常关闭时把热页列表 dump 到磁盘，启动时再 load 回来，相关参数是 innodb_buffer_pool_dump_at_shutdown 和 innodb_buffer_pool_load_at_startup；加载完成前，前几批查询会明显偏慢。

缓冲池可以拆成多个实例，每个实例有自己的 LRU 和锁，减少高并发争用；innodb_buffer_pool_instances 较大时通常设为 8 左右，每个实例不小于 1 GB。

Change Buffer：把随机写攒起来

二级索引的写入有一个天然的麻烦：一条 INSERT 要更新聚簇索引，还要更新每个二级索引，而这些索引页大概率不在缓冲池里。如果每次都把页读进来再改，写入就会变成大量随机读。Change Buffer（早期叫 insert buffer）解决的就是这个问题：当非唯一二级索引的页不在内存中时，InnoDB 先把变更记录在 change buffer 里，等这个页因为查询被读入缓冲池时，再把变更合并进去；后台线程也会定期做合并。

change buffer 对写多读少、二级索引多的表特别有价值：它把“每写一行就随机读若干索引页”变成“先顺序记录变更，之后再合并”，减少了随机 I/O。它的限制也很明确：唯一二级索引不能用，因为插入前必须读页检查唯一性；聚簇索引本身也不走 change buffer；如果索引页本来就在缓冲池里，直接修改更快，change buffer 反而多了一步。innodb_change_buffering 控制缓冲哪些操作，默认是 all，也可以设为 none、inserts、deletes、changes 或 purges；innodb_change_buffer_max_size 默认是缓冲池的 25%，写压力很大时可以适当调高，但不要挤占正常的页缓存。

自适应哈希索引：热点页的快捷方式

自适应哈希索引（Adaptive Hash Index，AHI）是 InnoDB 在运行时自动建立的内存哈希表。它针对频繁访问的索引页，把“从根走到叶、再在页内二分”的路径缩短成一次哈希查找；它会根据访问模式自动决定为哪些页建索引，不需要用户声明。等值查询、重复访问同一批热点的场景最容易受益；范围扫描、前缀模糊匹配、访问分布很散的查询则基本用不上。

AHI 由 innodb_adaptive_hash_index 控制，默认开启；innodb_adaptive_hash_index_parts 把哈希表分成多个分区，减少争用。它在高并发下可能成为瓶颈：所有对该结构的访问都要争用 btr_search_latch，当热点非常集中、并发又很高时，等待会抵消哈希带来的收益。SHOW ENGINE INNODB STATUS 的 “INSERT BUFFER AND ADAPTIVE HASH INDEX” 段会给出哈希查询和非哈希查询的速率，可以作为判断依据；如果关闭 AHI 后吞吐反而上升，就说明争用大于收益。AHI 只优化访问路径，不改变数据的物理顺序。

统计信息、代价与常见陷阱

基数、采样与索引潜水

优化器选择索引，靠的不是“哪个索引看起来更相关”，而是一套代价估算：预估扫描多少行、读多少页、要不要回表、要不要排序，再挑总代价最低的方案。估算的起点是统计信息。InnoDB 默认把统计信息持久化到 mysql.innodb_index_stats 等系统表，innodb_stats_persistent 默认为开；innodb_stats_auto_recalc 也默认为开，当表大约有 10% 的行发生变化时，后台会重新采样。采样页数由 innodb_stats_persistent_sample_pages 控制，默认只有 20 页，所以“基数”（cardinality）只是一个估计值，数据分布倾斜或有列间相关性时，误差可能很大。

对于等值条件和范围条件，优化器还会做“索引潜水”（index dive）：真的沿着 B+ 树走一遍，估算这个条件能命中多少行。索引潜水比采样准确，但每个条件都要走树，条件很多时开销可观。eq_range_index_dive_limit 默认是 200：当等值条件的个数达到这个值，优化器会放弃逐条潜水，改用统计信息估算；一个包含几百个值的 IN 列表，执行计划可能因此突然变差。

统计信息不准时，最直接的补救是 ANALYZE TABLE，它会重新采样并更新索引基数；对刚做完大批量导入的表，手动执行一次往往比等自动重算更稳妥。

优化器为什么会选错

选错索引通常不是优化器“坏了”，而是它拿到的信息或假设不成立。常见原因有四类：统计信息过期，例如批量导入后基数还停留在旧值；数据分布倾斜，平均值掩盖了热点值；列之间的相关性没有被建模，优化器按独立事件相乘，低估或高估结果集；以及代价模型对缓冲池状态的假设与真实情况不同，冷缓存下的随机读比估算更贵。LIMIT 和 ORDER BY 还会让估算更复杂：优化器可能为了避免排序而选择一个扫描行数更多的索引，实际执行时却因为回表太多而更慢。

排查时，可以先用 ANALYZE TABLE 排除统计过期，再用 EXPLAIN 看预估行数和实际行数的差距；需要更细的线索时，optimizer_trace 会记录每个候选索引的代价。临时用 FORCE INDEX 验证可以，但不要长期依赖：数据分布会变，强制索引会让优化器失去应变能力，正确做法通常是调整索引或改写查询。计划里的 rows 是估算值，不是实际扫描行数。

从存储结构看常见陷阱

第一类是过度索引。每个二级索引都是一棵独立的 B+ 树，写入时要维护、要占缓冲池、要参与 change buffer 合并；一张表建十几个索引，写入放大和内存压力会同时出现。索引是否值得，要看它服务的查询频率和行数，而不是列出现在 WHERE 里就建。

第二类是冗余索引。已有 (a, b) 时，单独的 (a) 通常是多余的，因为最左前缀已经覆盖；但 (b, a) 不是冗余，它服务的是以 b 开头的查询。MySQL 5.7 和 8.0 的 sys.schema_redundant_indexes 视图可以帮助发现这类问题，清理前仍要确认没有查询依赖被删索引的 key_len 或覆盖能力。

第三类是低选择性列当前导列。比如 status 只有几个取值，(status, created_at) 在 status 上的过滤能力很弱，但若查询总是带 status 并按 created_at 排序，这个索引仍可能是有价值的：它把排序变成了顺序扫描。

第四类是在索引列上做函数运算或隐式类型转换。B+ 树的有序性建立在列的原始值上，一旦写成 DATE(created_at) = '2020-10-01'，或者用字符串列去比较数字，索引上的顺序就无法直接用于定位，优化器只能逐行计算或退化为全表扫描。MySQL 8.0.13 起支持函数索引，可以把表达式的结果建成索引；5.7 则可以用生成列加索引来模拟，但都要额外占用空间，不能滥用。

第五类是大主键。前面已经说过，二级索引的叶子要保存主键；主键从 8 字节的 BIGINT 换成 36 字节的字符串 UUID，每个二级索引的每条记录都要多出 28 字节，页数、树高、缓冲池占用和写入量都会跟着上涨。对写入密集的表，这个代价比一次查询慢更值得警惕。

小结

本文从 16 KB 页出发，说明 B+ 树靠高扇出把树高压到三到四层。聚簇索引的叶子就是数据，二级索引的叶子保存索引列和主键，回表、覆盖索引与 ICP 都是围绕这一结构做的取舍。联合索引的有序性来自字典序，最左前缀、列顺序与 key_len 都能从页内顺序推出；页分裂、缓冲池、change buffer 和 AHI 则决定了这些结构在真实写入下的表现。索引设计没有孤立的最优解，先看查询模式，再看数据分布与写入比例，最后用统计信息和执行计划验证。
