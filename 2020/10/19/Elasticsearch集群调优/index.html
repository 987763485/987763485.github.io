Elasticsearch 集群调优

调优 Elasticsearch 集群时，最容易犯的错误是先抄一组参数，再回头寻找证据。本文以 7.x 版本为背景，从负载类型与瓶颈定位讲起，依次讨论分片、写入链路、段合并、内存与线程池、查询执行和分片分配。读完之后，你应当能按“测量、假设、验证”的顺序处理大多数性能问题，而不是依赖零散的经验值。

从负载出发：先测量，再动参数

同一个参数在不同负载下的效果可能完全相反。把 refresh_interval 调大，对批量写入是明显的吞吐优化，对“写入后立刻搜索”的场景却是可见性倒退；把堆调大，对聚合查询可能减少磁盘读取，对写入型节点却可能换来更长的 GC 停顿。因此调优的第一步不是改配置，而是给集群归类：它到底在为什么样的请求服务。

负载类型 主要开销 优先观察的指标 常见症状
写入型（日志、指标） 分词与倒排、段合并、磁盘顺序写 写入速率、merge 耗时、write 队列拒绝数 bulk 返回 429、段数量持续上涨、磁盘写满
查询型（站内搜索） 打分、页缓存命中、段数量 查询 P95/P99、慢日志、缓存命中率 慢查询集中在少数索引、GC 随查询量抖动
聚合型（报表、分析） 全局序号、fielddata、CPU 聚合耗时、熔断次数、堆占用 节点发热、circuit breaker 异常、长停顿

现实中的集群往往是混合负载：白天查询、夜间跑批，或者同一个集群既有日志索引又有业务索引。这时比调参更有效的手段是按索引拆分职责，把写入密集的索引与查询密集的索引放到不同节点上，再用分片分配规则隔离。先分清负载，后面的每个决定才有判断依据。

瓶颈对照表

现象 更可能的瓶颈 下一步动作
CPU 长期偏高，hot_threads 多落在 index 或 merge 线程 分词、合并或刷新过频 检查 mapping 与 refresh_interval，评估 merge 限流
old GC 次数上升、单次停顿变长 堆过大、对象分配率高或 fielddata 膨胀 看 GC 日志与堆内大对象，缩小 bulk、移除 text 聚合
iowait 高，merge 长期落后 磁盘带宽不足或 merge 线程过多 换 SSD、降低 merge 并发、减少小段

改参数时坚持一次只动一个变量，并保留一个可回滚的窗口。比如先把 refresh_interval 从 1s 调到 30s，观察一天的写入拒绝数与查询可见性，再决定是否继续调整 translog。若同时改五个参数，出现问题时无法判断是哪一个起了作用。

分片策略：数量、大小与路由

分片是调优中代价最高的决定。number_of_shards 在索引创建后不能直接修改，只能通过 shrink、split 或 reindex 重建，因此它必须在建索引之前想清楚。分片数量既影响写入并行度，也影响集群状态大小、恢复速度和查询的扇出成本。

目标大小与数量约束

业界比较稳妥的经验是：单个分片的大小控制在 10 GB 到 50 GB 之间，每个节点的分片数不超过“堆内存 GB 数乘以 20”。后一条约束来自集群状态与段元数据的开销：分片越多，主节点维护的集群状态越大，数据节点上打开的 Lucene 文件也越多，恢复时要重放的 translog 越多。

分片过多与过少各有代价：

  • 分片过多：每个分片都有固定的内存与文件句柄开销，集群状态更新变慢，一次查询要访问更多分片，协调节点合并结果的成本上升；恢复时并发重放大量小分片，反而拖长恢复时间。
  • 分片过少：单个分片过大，恢复与迁移都以整个分片为单位，时间长且占用带宽；写入无法分散到更多节点；一次 merge 可能长时间占满磁盘。

可以用一个简单的算式估算主分片数：用实测的单日主分片存储量除以目标分片大小，再向上取整。例如某日志索引每天的主分片数据约 180 GB，目标分片 30 GB，则主分片取 6；保留 30 天就是 180 个主分片，分布在 3 个节点上每节点 60 个，若堆为 16 GB，按每 GB 堆 20 个分片的上限是 320 个，仍在安全范围内。注意这里的 180 GB 应来自 pri.store.size 的实测值，而不是原始日志量，压缩比因数据而异，不能拍脑袋。

路由与副本

默认路由是对文档 _id 做哈希，数据分布通常足够均匀。自定义 routing 能把同一业务键的文档放到同一分片，便于按用户或租户查询，但如果某个路由值对应的数据量远大于其他值，就会形成热点分片，写入和查询都压在一个节点上。使用自定义路由前，先确认键的基数足够大、分布足够均匀。

副本的作用有两个：故障时接管主分片，以及分摊查询。增加副本会成倍增加存储与写入放大，因为每个副本都要执行同样的索引操作。对写入型集群，副本从 1 降到 0 能显著减少写入压力，但此时节点故障会丢数据，只适合可重建的数据且在维护窗口内短期使用；对查询型集群，增加副本往往比升级 CPU 更直接。这个取舍要写进容量规划，而不是临时改设置。

分配、水位与热点节点

节点磁盘使用率由三个水位控制，7.x 的默认值是低水位 85%、高水位 90%、洪泛水位 95%。超过低水位后新分片不再分配进来，超过高水位会尝试迁走分片，超过洪泛水位则相关索引被加上只读块，写入直接失败。可以用下面的命令确认某个分片为什么没有分配：

写入链路：refresh、translog 与 flush

一次写入并不是“落盘即完成”，它要经过内存缓冲、translog 与 Lucene 段三个环节。很多看似矛盾的调优建议，其实是在这条链路上选择不同的持久化点。

flowchart TD
    A[客户端 bulk 请求] --> B[写入内存缓冲]
    A --> C[追加 translog]
    C --> D{durability}
    D -->|request| E[每次请求 fsync]
    D -->|async| F[按 sync_interval fsync]
    B --> G[refresh 生成 segment]
    G --> H[文档可被搜索]
    B --> I[flush 提交 Lucene]
    I --> J[清理旧 translog]

refresh_interval：搜索可见性的代价

refresh_interval 的默认值是 1s，意思是每秒把内存缓冲里的文档写成一个小段并重新打开搜索器，让新文档可以被搜到。刷新的代价不只是写磁盘：每次刷新都会产生新段，增加后续合并压力，并使查询缓存部分失效。写入量越大，1s 的刷新越像一台不停制造小文件的机器。

批量导入或重建索引时，通常把刷新间隔调大甚至设为 -1：

设为 -1 表示关闭周期性刷新，文档仍会写入缓冲和 translog，但在手动 refresh 之前不可搜索。导入完成后务必恢复，例如改成 30s，既降低刷新频率，又保证秒级可见性。如果业务在写入后必须立刻查到，可以使用 ?refresh=wait_for 让请求等待下一次刷新，而不是对每条文档使用 refresh=true，后者会让每次写入都强制生成段。

translog 的两种持久化模式

translog 是写入后的预写日志。index.translog.durability 有两个取值：

取值 行为 故障时可能丢失 适用场景
request（默认） 每个索引、删除、bulk 请求返回前执行 fsync 已确认的请求不会丢 订单、账务、审计等不可重建数据
async 写入页缓存，按 index.translog.sync_interval 周期 fsync，默认 5s 操作系统崩溃或断电时可能丢最近一个周期 日志、指标等可重放数据

async 并不等于“不写磁盘”，进程崩溃时页缓存仍在，通常不会丢数据；它防范的是机器断电或内核崩溃。把 durability 关掉换取吞吐，本质上是用一个明确的数据丢失窗口换更少的 fsync。这个决定应该由数据 owner 做出并写进文档，而不是运维为了压测好看随手改掉。

另一个相关参数是 index.translog.flush_threshold_size，默认 512 MB。translog 超过阈值会触发 flush，把内存中的段提交为 Lucene 提交点并开启新的 translog 世代。阈值调大能减少 flush 次数，但节点重启后需要重放的日志更多，恢复时间更长。

flush 不等于 refresh

refresh 让文档可搜索，flush 则负责持久化提交点并清理旧 translog，两者解决的是不同问题。_flush 不是控制搜索可见性的手段，_refresh 也不负责清理 translog。排障时把这两个概念混为一谈，很容易得出“刷新了为什么还丢数据”的错误结论。

对写入型集群，合理的组合通常是：刷新间隔 30s 左右、durability 按数据价值选择、bulk 请求批量提交。真正的吞吐提升来自“减少每次写入的固定开销”，而不是把每个开关都推到极端。

写入吞吐：bulk、mapping 与 pipeline

bulk 的大小与并发

官方给出的起点是每批 5 MB 到 15 MB，但这不是固定答案。批量太小，请求解析、网络往返与 translog fsync 的固定成本占比过高；批量太大，协调节点要缓存整个请求，堆压力上升，单个请求失败后的重试成本也更高。实践方法是从 5 MB 开始，在观察写入速率与 GC 的前提下逐步加大，直到速率不再上升或拒绝开始出现。

并发度同样需要试探。一个 bulk 请求会按目标分片拆成多个子请求并行执行，所以单批已经具备一定并行性；再叠加大量客户端并发，只会让 write 队列堆积、段数量暴涨。比较稳妥的做法是：控制客户端并发在“节点数乘以每节点少量请求”的量级，遇到 es_rejected_execution_exception 时按指数退避重试，而不是立刻加大队列。

mapping 决定写入成本

写入成本很大一部分在 mapping 上。默认的动态映射会把字符串同时映射为 text 和 keyword 子字段，前者分词建倒排，后者建 doc values；如果日志里不断出现新字段，还会持续更新集群状态，最终触发字段数上限。7.x 的 index.mapping.total_fields.limit 默认是 1000，超过后新字段会被拒绝，这类故障往往在运行数月后才暴露。

控制字段膨胀有三种常用手段：

  • 把索引的 dynamic 设为 strict，遇到未定义字段直接报错，迫使上游收敛结构；设为 false 则忽略新字段，文档仍可写入但字段不可搜索。
  • 用 dynamic_templates 按字段名或类型匹配，把字符串统一映射为 keyword，避免无意义的分词。
  • 对确定不需要检索的字段使用 index: false，对不需要排序和聚合的字段使用 doc_values: false，对只用于过滤的字段关闭 norms。

上面把 trace_id 设为不可搜索、不建 doc values，是因为它只用于展示，不参与过滤和聚合。每关掉一个倒排或列存结构，都节省一份磁盘和写入 CPU，但也要确认没有查询依赖它。

pipeline 的隐性成本

ingest pipeline 在每个文档上依次执行处理器。grok 的正则匹配、date 的多格式解析、脚本处理器都属于 CPU 密集操作，放在高吞吐写入路径上会被放大。使用前先用 _simulate 接口验证模式和输出，尽量把解析工作前移到采集端；确需在集群内处理时，控制正则复杂度，避免回溯失控，并注意处理器失败会导致文档被拒绝或进入失败索引。

pipeline 还会影响 bulk 的错误定位：一批中某条文档处理失败，返回结果里会带对应的条目，客户端应逐条检查 errors 字段，而不是只看 HTTP 状态码。批量写入的可靠性，往往取决于客户端有没有正确处理部分失败。

段合并、force_merge 与磁盘 IO

每次 refresh 都会产生新的 Lucene 段，段一旦写出就不再修改。删除和更新只是标记，真正的空间回收与查询加速依赖后台合并：把若干小段合成更大的段，同时丢弃被删除的文档。合并是顺序读写大文件，代价是磁盘带宽与 CPU，收益是更少的段、更小的索引和更快的查询。

看段的数量，而不是只看索引大小

_cat/segments 能列出每个分片的段数与大小。持续写入的索引，段数在几十到上百之间波动是正常的，因为后台合并一直在追赶；但如果段数长期只增不减，或单个分片有数百个小段，查询就要在每个段上执行过滤和打分，延迟会明显上升。refresh 越频繁、merge 越跟不上，这个数字越难看。

force_merge 只对只读索引有意义

_forcemerge 可以强制把分片合并到指定段数，常见用法是 max_num_segments=1。它适合历史索引、冷数据或刚重建完不再写入的索引：段数降到 1 后，查询只需要打开一个段，磁盘占用也会因清理删除标记而下降。

对仍在写入的索引执行 force merge 通常是反效果：合并刚完成，新的 refresh 又产生小段，后台合并还得再做一遍，期间磁盘被长时间占满，写入和查询一起变慢。需要回收删除空间时，可以用 only_expunge_deletes=true，它只合并含删除文档的段，代价比全量合并小。

限流与磁盘保护

合并会与查询、写入争抢磁盘。网上常见的建议是调 indices.store.throttle.max_bytes_per_sec 给合并限速，但这个设置从 6.0 起已废弃，7.x 不再支持；合并改由 ConcurrentMergeScheduler 自动节流，真正可调的是 index.merge.scheduler.max_thread_count，机械盘建议设为 1，SSD 保留默认即可。调整前先看 _cat/segments 的段数、merge 耗时与 iowait，确认瓶颈确实在合并，而不是照搬旧版本的参数。

磁盘写满会让整个索引变成只读，恢复过程远比提前限流麻烦。监控上应同时看 _cat/allocation 的使用率、merge 的耗时与 iowait，不要等洪泛水位触发才处理。

JVM、内存与线程池

堆不是越大越好

Elasticsearch 的堆建议不超过物理内存的 50%，剩余内存留给操作系统页缓存。Lucene 读取段文件时依赖页缓存，如果堆把内存吃光，查询会退化为频繁的磁盘读，延迟成倍上升。单节点给堆留出余量，比把所有内存都塞进 JVM 更划算。

另一个硬约束是压缩指针。HotSpot 在堆小于约 32 GB 时可以用 32 位压缩对象指针，超过这个界限后退化为 64 位指针，同样的对象占用更多内存，堆从 31 GB 加到 40 GB 实际可用对象数可能没有增加，GC 停顿反而更长。因此常见做法是把堆控制在 30 GB 上下；确实需要更大内存时，优先增加节点而不是无限加大单堆。

7.x 自带 JDK 默认使用 G1 GC，暂停目标默认在 200ms 量级。对大多数集群，保留默认并观察 GC 日志即可，不必手写一堆调优参数。要关注的是 old GC 的频率与单次停顿：如果 old GC 每隔几分钟就出现且停顿持续上升，通常说明堆内有长期存活的大对象，例如 fielddata、聚合中间结果或过大的批量请求，应先找对象来源，而不是换 GC 算法。

内存锁定与系统参数

bootstrap.memory_lock: true 让 JVM 锁定堆内存，避免被换出到 swap。swap 对 Elasticsearch 的伤害很大：一次换入换出可能造成数秒停顿，还会让节点被主节点误判为失联。启用内存锁定需要在 systemd 中放开 LimitMEMLOCK=infinity，否则启动会失败。与之配套的是把 vm.swappiness 调低，并在监控中确认没有 swap 使用。

vm.max_map_count 必须至少为 262144，否则 Lucene 打开大量段文件时会触发 max virtual memory areas vm.max_map_count is too low。这是部署检查项，不是性能参数，但它在分片多、段多时最容易暴露。

页缓存与磁盘

堆之外的内存主要给页缓存。判断页缓存是否充足，可以看 _nodes/stats/fs 中的可用空间与读写量，以及查询延迟是否随索引增长而恶化。若磁盘读频繁、页缓存命中低，增加内存或减少节点上的分片数，往往比调 JVM 参数更有效。

线程池与拒绝

Elasticsearch 用固定大小的线程池隔离不同类型的请求。7.x 中，search 线程数约为处理器核数的 1.5 倍加 1，队列默认 1000；write 线程数约等于处理器核数，队列默认 10000；get 也有独立线程池。队列满时请求被拒绝，客户端收到 es_rejected_execution_exception。

拒绝不是故障，而是背压信号：集群在告诉你“到达速率超过了处理能力”。把队列调大通常只会把拒绝推迟，请求在队列里等待的时间变长，客户端超时后重试，反而制造更多流量。正确的顺序是：先确认拒绝集中在哪个池、哪个节点，再看该池对应的操作是否真的需要这么多并发，最后才考虑调整队列或增加节点。

批量写入客户端应在收到 429 时指数退避，并限制重试次数；把重试放在应用层，配合幂等的文档 ID，比在集群侧堆队列更可控。

查询性能：上下文、缓存与分页

filter 与 query 的差别

查询上下文计算相关度分数，过滤上下文只回答“是否匹配”，结果可以缓存。把不参与打分的条件放进 filter，既省 CPU，也让缓存有机会生效：

判断标准很简单：这个条件是否影响“谁更相关”。服务名、时间范围、状态码通常只做筛选，放在 filter；全文关键词才需要打分。

doc_values、fielddata 与序号

排序和聚合依赖列式存储 doc values，keyword、数值、日期字段默认开启，text 字段没有 doc values。对 text 字段打开 fielddata 再聚合，会把分词结果全部加载进堆，基数一高就可能 OOM，这是生产环境最常见的查询事故之一。正确做法是为需要聚合的字段增加 keyword 子字段，或直接使用 keyword 类型。

对频繁做 terms 聚合的字段，可以打开 eager_global_ordinals，把构建全局序号的成本前移到 refresh 阶段，避免每次查询都付出这份开销。它适合“写入不频繁、聚合很频繁”的维度字段，不适合高基数且持续变化的字段。

总数、分页与缓存

7.x 中 track_total_hits 默认只精确统计到 10000 条。如果页面只需要展示“约多少结果”，保留默认或设为 false 即可；只有确实需要精确总数时才设为 true，代价是要遍历所有匹配文档。

from 加 size 的深分页会让协调节点先取出 from + size 条再丢弃前面的部分，翻到几千页时开销惊人，且受 index.max_result_window 限制。遍历大量结果应使用 scroll，它保留一份搜索上下文，适合导出；用户交互式的“下一页”更适合 search_after，用上一页最后一条的排序值作为游标，并带一个唯一字段作为决胜条件，避免翻页时重复或遗漏。scroll 上下文会占用资源，用完必须清理，不能无限期保留。

请求缓存只对 size: 0 的聚合类请求生效，默认开启；普通查询依赖的是段级查询缓存，段合并后缓存自然失效。判断一条查询慢在哪里，用 profile 比猜更可靠：

调优复盘与常见误区

下面用一个写入型集群的排查过程串起前面的内容。场景是日志集群在业务高峰出现大量 429，节点 CPU 偏高，GC 停顿变长。这里只描述诊断顺序与判断逻辑，不虚构具体数字。

一次写入型集群的排查

  1. 确认症状边界。查看客户端错误分布，确认 429 来自 bulk 而非查询；用 _cat/thread_pool 确认拒绝集中在 write 池且分布在多个数据节点，而不是单节点异常。
  2. 看写入路径。_nodes/stats/indices 显示 indexing 与 merge 耗时占比高，_cat/segments 显示单分片段数偏多，索引按天创建且单索引分片偏小。
  3. 看资源。GC 日志显示 old GC 次数上升但单次停顿尚可，_cat/allocation 显示磁盘接近高水位，iowait 偏高。此时瓶颈更可能是“小段过多、合并与写入争抢磁盘”，而不是 CPU 不足。
  4. 先改成本最低的项。把写入索引的 refresh_interval 从 1s 调到 30s，减少刷新产生的小段；客户端把 bulk 控制在 5 MB 到 15 MB，限制并发并在 429 时退避；确认 mapping 没有把无用字段建成 text。
  5. 再改结构性项。把按天索引改为按大小 rollover，让分片规模稳定；对已不再写入的历史索引在低峰执行 force merge；结合数据价值评估 translog durability，日志类数据可以接受 async 的丢失窗口。
  6. 验证与回滚。保持流量窗口可比，观察拒绝数、写入 P99、merge 耗时与 GC 停顿是否同时改善。若某一项没有改善，回滚该项再继续，避免多个变更互相掩盖。

常见误区

误区 后果 更合理的做法
把堆加到 32 GB 以上 压缩指针失效，停顿更长 控制在 30 GB 上下，增加节点
为“以后数据会多”预建大量分片 集群状态膨胀，恢复变慢 按实测数据量与 rollover 扩展
对活跃索引 force merge 合并完又被新段填满，磁盘被打满 只对只读索引执行
生产环境长期关闭 translog 持久化 断电丢数据，且难以追溯 按数据价值选择，明确记录取舍
只盯 CPU 或只盯 QPS 忽略拒绝、GC 与磁盘，调错方向 建立一组基线指标
先调参后测量 无法归因，问题反复 先采样，一次只改一个变量

这些问题有一个共同点：把局部指标当成整体健康。调优的目标不是让某个数字好看，而是让集群在目标延迟内稳定处理预期负载。

小结

集群调优的起点是负载判断，而不是参数表：先分清写入、查询与聚合各占多少，再用线程池拒绝、GC、磁盘与段数定位瓶颈。分片要在建索引前规划，控制单分片大小与每 GB 堆的分片数，按 rollover 而不是按天切分。写入侧理解 refresh、translog 与 flush 各自的职责，按数据价值选择持久化；合并只对只读索引做，force merge 不是日常操作。内存上给页缓存留空间，堆控制在压缩指针边界以内，把拒绝当作背压而不是敌人。最后，一次只改一个变量并保留回滚窗口，这比任何“最佳实践参数”都更可靠。
