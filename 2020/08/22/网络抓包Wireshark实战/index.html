网络抓包：Wireshark 实战

线上接口变慢时，应用日志往往只留下一行耗时数字，看不出时间花在了 DNS、握手还是服务端处理上。把流量抓下来逐包观察，是少数能直接看到协议行为的手段。本文从抓包点的选择讲起，介绍 Wireshark 3.2 的过滤器、流跟踪、统计与导出，最后给出一份可复用的排障清单。读者需要了解 TCP 与 HTTP 的基本概念，读完后应能独立完成一次受控的抓包分析。

抓包点：先想清楚能看见什么

抓包的第一件事不是打开软件，而是确定观察点。观察点决定了你能看到哪些包、看不到哪些包，也决定了结论的边界。

常见的抓包位置有以下几类：

  • 本机网卡：最方便，Wireshark 启动后直接列出接口。它只能看到本机进出的流量，适合排查客户端或服务端自身的连接问题。
  • 交换机端口镜像（SPAN）：在交换机上把目标端口或 VLAN 的流量复制到观察口。适合分析两台服务器之间的通信，但镜像口带宽容易过载，且镜像策略通常只覆盖单播，广播与组播要看具体配置。
  • 网络 TAP：分光或聚合设备串在链路中间，不改变转发行为，是最可靠的旁路方式，代价是需要停机接线。
  • 容器网络命名空间：容器有独立的 netns，宿主机默认抓不到 Pod 内部的回环流量。可以进入对应命名空间执行抓包，或让临时容器共享目标容器的网络栈。
  • 远程抓包：服务器上没有图形界面，先在远端用 tcpdump 落盘再取回，或者用 Wireshark 的 sshdump 通过 SSH 调用远端 dumpcap 实时回传。后者省去搬运文件，但受限于 SSH 带宽。

需要提前接受两个可见性限制。其一，交换网络中你不在转发路径上，就抓不到别人的流量，端口镜像和 TAP 解决的是“位置”问题，不是“权限”问题。其二，TLS 1.3 的应用数据只有密文，没有会话密钥时，能读到的只有握手字段、SNI、证书和包长时序。看到加密流量时，应把分析目标调整为连接行为，而不是猜测明文内容。

捕获过滤器与显示过滤器

Wireshark 有两套过滤语法，初学者最容易混淆。捕获过滤器使用 BPF 语法，在抓包开始前生效，由 libpcap 编译后交给内核或驱动执行，不匹配的包根本不会进入缓冲区。显示过滤器在抓包之后对已记录的数据做筛选，语法更丰富，可以引用任意协议字段。

两者的差别可以概括为：

维度 捕获过滤器 显示过滤器
生效时机 抓包前，丢包在驱动层 抓包后，只影响展示
语法来源 BPF（tcpdump 同款） Wireshark 自有语法
能力 地址、端口、协议、长度 任意字段、比较、正则
代价 写错会漏掉关键包 写错只是看不到，数据还在

ip.addr 与 tcp.port 都匹配源和目的两个方向，要限定方向得写 ip.src、tcp.dstport。判断“只有 SYN”的握手首包，必须同时约束 SYN 为 1、ACK 为 0，否则会把 SYN/ACK 也算进去。tcp.analysis.* 是 Wireshark 的分析字段，它根据前后包推断出重传、乱序、零窗口等事件，是排查传输问题的入口。

还有一个常见错误：在捕获过滤器里写 tcp.port == 443。BPF 不认识 == 和点号字段，正确写法是 tcp port 443。反过来，把 host 10.0.0.5 填进显示过滤器也会报语法错误。记住一条经验：捕获过滤器只认地址、端口和协议，显示过滤器才认字段。

复盘一个慢 HTTP 请求

假设用户反馈某个页面偶尔要等三秒，我们已经在客户端和 Web 服务器两侧各抓了一份包。下面按时间顺序走一遍。

第一步，定位会话。用 http.request 过滤出所有请求，按时间找到耗时异常的那一条。选中它，右键选择 Follow → TCP Stream，先看应用层全貌：请求行、Host、状态码、响应体大小。

第二步，固定这条流。关闭流窗口，在包列表里用 tcp.stream eq N 过滤，之后所有观察都基于这一条连接。先确认前面有没有 DNS 交互，查询与响应之间隔了多久、有没有重试；然后看 TCP 三次握手，SYN、SYN/ACK、ACK 三个包的时间差就是建连 RTT。

第三步，看 TLS 握手。Client Hello、Server Hello、证书、Finished 依次出现，可以读到 SNI、ALPN 和证书链。TLS 1.3 把证书也加密了，能看到的字段更少，此时只需记录握手总耗时，不必纠结内容。

第四步，看请求与响应。从发出 HTTP 请求到收到第一个响应字节的间隔，是服务端处理时间加上网络单程延迟。如果响应体很大，还要看它被分成多少个段、段之间是否出现停顿。

第五步，看连接如何结束。正常的四次挥手是 FIN、ACK、FIN、ACK；如果看到 RST，通常是某一端异常关闭、超时后被中间设备重置，或者应用层直接断连。

把这几段时间摆在一起，问题大致能归位：

  • SYN 发出后 SYN/ACK 迟迟不来，说明服务端不可达、SYN 队列满或被安全设备拦截。
  • 握手很快但首字节很慢，瓶颈在服务端处理或后端依赖，不在网络。
  • 出现大量 tcp.analysis.retransmission，说明路径丢包；如果同时 RTT 陡增，多半是拥塞。
  • 出现 tcp.analysis.zero_window，说明接收端应用来不及读数据，窗口被填满，发送方被迫停等。
  • 出现 tcp.analysis.out_of_order，多为多路径转发导致，少量可以忽略。

所有这些时间都来自抓包机的本地时钟。跨主机比较之前，先确认两台机器都同步了 NTP，否则几秒的时钟偏差足以让结论完全反过来。

统计视图与导出证据

单条流看完了，还需要回答“整体哪里不对”。Wireshark 的统计菜单提供了几个互补的视角。

Conversations 按地址对汇总字节数、包数和持续时间，勾选 Limit to display filter 可以先圈定范围再排序。它最适合回答“谁在占带宽”，比如某台主机在对外传输大文件，或者某个地址对之间有大量短连接。

Protocol Hierarchy 用百分比展示协议构成。DNS 占比异常高，可能是解析失败后的重试风暴；TCP 里重传比例高，则指向链路质量。这个视图不定位具体连接，但能快速排除方向。

IO Graph 把吞吐画成曲线，每个图可以绑定一个显示过滤器。把故障前后的两个时间段画在一起，尖刺和凹陷往往对应重传、超时或应用的批量请求。

TCP Stream Graphs 针对单条流，包含 Time Sequence（Stevens）、Throughput、Round Trip Time 和 Window Scaling 四种。RTT 图突然抬升，说明路径拥塞或发生了线路切换；窗口图长期贴近零，说明接收端处理不过来；吞吐图的阶梯形状，通常对应拥塞窗口的增长与回退。

Expert Information 把重传、零窗口、乱序、校验和错误按严重程度汇总。它是排查的起点而不是终点：校验和错误在开启了网卡卸载的机器上非常常见，出站包的校验和根本还没计算，这类告警可以直接忽略。

需要把证据交给别人时，优先导出最小集合。File → Export Objects → HTTP 可以把响应体单独落盘；Follow Stream 窗口里的 Save as 能保存原始字节；File → Export Specified Packets 选择 Displayed，只写出当前过滤结果，得到几十 KB 的小文件，比几百 MB 的全量包好用得多。分享前必须脱敏：用 editcap -s 96 截断载荷，去掉 Cookie、Authorization 头，替换内网地址与主机名。即便流量是加密的，SNI、IP 和时间戳同样可能暴露业务结构，不能直接外发。

生产环境抓包：性能、权限与合规

在办公机上抓包和在产线服务器上抓包是两件事。前者写错过滤器大不了重来，后者可能影响业务。

先估算数据量。千兆链路满负荷约 125 MB/s，几分钟就能写出几十 GB，磁盘和 inode 都会吃不消。所以第一步永远是缩小范围：用捕获过滤器限定主机和端口，把无关流量挡在驱动层。

其次是截断长度。只关心协议头时，把 snaplen 设为 96 字节，dumpcap -s 96 或 Wireshark 捕获选项里的 Snapshot length 都可以。载荷被截断后，统计、握手、重传分析仍然可用，写盘量却下降一个数量级。

第三是用环形缓冲兜底：

这组参数让文件按 100 MB 滚动，最多保留 20 个，总占用不超过 2 GB。即使忘了停止抓包，也不会把根分区写满。

第四是盯住丢包。dumpcap 退出时会打印 dropped 计数，抓包过程中也可以用 -q 查看实时统计。一旦出现丢包，说明缓冲区或磁盘跟不上，“没有看到重传”就不能作为结论，因为丢包可能发生在抓包程序自己身上。

第五是不要在产线机上开图形界面。Wireshark 的解析和重组很吃 CPU 与内存，几百 MB 的包足以让一台繁忙的服务器卡顿。正确做法是用 dumpcap 或 tshark 落盘，取回办公机再分析。

权限方面，Linux 上不必用 root 长期运行。给 dumpcap 授予 cap_net_raw 与 cap_net_admin 能力，再把分析账号加入 wireshark 组即可；macOS 安装时勾选 ChmodBPF，把 /dev/bpf* 的权限交给专用组。Windows 依赖 Npcap，安装时同样可以选择限制普通用户抓包。

最后是合规。抓包会完整记录通信内容，属于敏感操作。只抓自己有管理权限的资产，事先取得书面授权，明确范围、目的与保留期限，抓完及时删除。涉及用户数据的包，应按最小必要原则处理，不能因为“技术上抓得到”就默认可以抓。

命令行搭档与常见误区

服务器上更常见的组合是 tcpdump 加 tshark。tcpdump 负责采集，参数值得背下来：

-i any 抓所有接口，-nn 不做名字解析以避免额外的 DNS 查询，-s0 保留完整包，最后的表达式就是 BPF 捕获过滤器。

tshark 适合批量提取字段，把几十万条包变成可以排序的表格：

-Y 是显示过滤器，-e 指定字段，输出可以直接交给 awk 或表格软件。排查“哪些 URI 最慢”这类问题时，比在 GUI 里逐条点开高效得多。

处理已有文件时，editcap 与 mergecap 是两把剪刀。editcap -A 与 -B 按时间裁剪，editcap -c 10000 按包数切分，mergecap -a 把客户端和服务端的抓包按时间合并成一份。两端抓包合并后，同一段交互会以两个方向的时间线并列呈现，判断丢包发生在哪一侧会容易很多。

实践中最容易踩的坑有这几个：

  • 抓错接口。容器、VPN、bond 和 loopback 都可能承载真正的流量，ip addr 与 ip route 能帮你确认出口。
  • 被校验和告警误导。网卡校验和卸载会让出站包显示 bad checksum，这并不代表包坏了。
  • 忽略时钟。两台机器没有对时，时间线无法直接比较。
  • 把密文当明文分析。没有密钥就是读不懂，不要根据包长臆测内容。
  • 被重组掩盖问题。Follow Stream 展示的是拼接后的应用数据，重传和乱序在视图里被抹平了；查传输问题要回到包列表，必要时关掉 TCP 重组。
  • 只抓一端。单侧看到的“重传”可能只是抓包点丢了包，两端对比才能确定方向。

排障清单

把上面的内容压缩成一张检查表，遇到慢请求时可以按顺序过一遍：

  1. 最近改了什么。发布、证书更换、DNS 变更、负载均衡调整、安全组收紧，逐项确认时间点是否吻合。
  2. 影响范围。一个客户端、一个服务端还是全体用户。全体更像基础设施问题，单点更像客户端环境或单个实例。
  3. 分层定位。DNS 解析、TCP 建连、TLS 握手、首字节、数据传输，分别记下耗时，找出最大的那一段。
  4. 两端对比。在客户端和服务端同时抓包，比较同一请求在各阶段的时间差，差值就是网络段的成本。
  5. 看传输指标。重传率、RTT 变化、零窗口、乱序，重传超过 1% 就值得继续追。
  6. 复核结论。每条结论都要有包级别的证据支撑，不能只凭一条吞吐曲线下判断。

小结

抓包不是打开软件就开始录，而是先确定观察点，再用捕获过滤器缩小范围，用显示过滤器与流跟踪还原会话，用统计与专家信息定位异常，最后只导出必要证据并脱敏。生产环境优先使用 dumpcap 与 tshark，控制 snaplen 和环形缓冲，注意权限与授权边界。加密流量只能看元数据，传输层的问题要回到包级别判断，别被重组后的流视图迷惑。把抓包点、时间线和两端对比固定成习惯，多数“偶发变慢”都能在一次抓包里找到答案。
