零信任网络架构入门

很多团队把“零信任”当成一句口号，或者当成一台可以采购的设备。本文从边界模型的失效讲起，借用 2020 年 8 月刚刚发布的 NIST SP 800-207，把零信任拆成可以画出来、可以实施的概念和组件。读完后你应该能说清一条访问请求要经过哪些判定环节，以及下一步该做什么，而不是先纠结买什么。

边界模型的失效

过去二十多年，企业网络的默认假设很朴素：内网可信，外网不可信。于是防火墙上开一个口子，让远程用户通过 VPN 进来，进来后就和办公区同事处于同一个“内网”，访问服务器、数据库一路畅通。这就是边界模型，也叫“城堡加护城河”。

边界模型成立需要三个前提：用户坐在办公室里、终端由 IT 部门统一配发、应用跑在自建机房里。这三个前提在今天都已经松动。

第一，VPN 只回答“你是谁”，不回答“你能访问什么”。用户通过一次认证之后，拿到的是一个网段地址，而不是某个应用的权限。安全边界被压缩成了一道门，门后面的走廊却是相通的。攻击者只要拿到一个普通员工的账号，或者利用一台被钓鱼的笔记本电脑，就能以这台机器为跳板在内部横向移动，扫描网段、寻找弱口令、连接数据库。

第二，办公场景变了。员工在家里、在咖啡馆、在出差途中办公，用的是家庭宽带和个人设备，IP 每天都在变，“来自公司出口 IP”不再是可信凭据。

第三，应用的位置变了。业务迁到公有云，协作工具变成 SaaS，用户访问时流量根本不经过企业边界，护城河外面已经没有城堡。

第四，第三方接入让边界更模糊。外包、运维服务商、并购团队都要访问部分系统，常见做法是开一个 VPN 账号，而这个账号看到的往往比工作需要多得多。

把这些问题放在一起看：网络位置不再等价于信任等级。真正需要验证的，是“谁、用什么设备、在什么情况下、访问哪个应用”。

零信任的核心原则

零信任并不是“不信任任何人”，也不是把 VPN 换一个名字。它是一组设计原则，核心可以概括为四条。

永不隐式信任。 不因为请求来自内网、来自办公网段、来自已经登录的会话，就默认它是安全的。每一次访问都要重新判断，判断依据是身份、设备状态和上下文，而不是网络位置。

显式验证。 认证与授权要基于尽可能多的可用信号：用户身份是否经过多因素认证、终端是否纳管、补丁与磁盘加密是否合规、登录地点与时间是否异常、目标应用的敏感级别如何。

最小权限。 授权粒度要细到单个应用甚至单个操作，并且带有时间限制。员工不需要访问财务系统的数据库，运维人员也不需要常驻的生产环境管理员权限。权限按需申请、到期回收，比“一次授予、长期有效”安全得多。

假定失陷。 设计时假设攻击者已经在内部，或者某个账号已经被盗。由此有两个要求：默认拒绝，只有明确允许的流量才能通过；东西向流量也要管控，不能因为两台服务器在同一个机房就互相放行。

这四条原则推导出一个共同的落点：身份成为新的边界。过去的边界是 IP 和网段，现在的边界是“这个身份加上这台设备”。网络隔离与安全域划分解决的是“把网络切成块”，零信任解决的是“在块内部再按身份和应用切一次”，两者叠加而非替代。安全域、VLAN 与 ACL 的具体做法可参考网络隔离相关的文章。

NIST SP 800-207 的词汇表

2020 年 8 月，NIST 发布了 SP 800-207《Zero Trust Architecture》。它的价值不在于提出新概念，而在于把业界零散的实践整理成一套公共词汇。需要说明的是，它是一份参考性指南，发布时采纳还处在早期，本文引用它是为了借用术语，而不是暗示它已经是行业标准配置。

文档把零信任架构抽象成两个角色：策略决策点（Policy Decision Point，PDP）和策略执行点（Policy Enforcement Point，PEP）。PDP 负责“算”，依据身份、设备与上下文给出允许或拒绝的结论；PEP 负责“拦”，守在资源前面把结论变成实际的连接放行或阻断。所有访问都必须经过这一对角色，没有例外通道，这是零信任与“加一层 VPN”最本质的区别。

对于具体怎么实现，文档归纳了三条常见路径，它们可以单独使用，也可以组合。

一是增强身份治理。以身份提供方（IdP）为中心，把多因素认证、单点登录、权限审批、定期复核做扎实，让每个请求都带着可信的身份断言。这条路径改动最小，适合作为起点。

二是微隔离。在数据中心内部按应用或环境分组，组间默认拒绝，只放行声明的调用关系。它主要解决东西向流量，典型实现是主机防火墙、安全组或容器网络策略。

三是基于网络的隔离。用软件定义边界一类的网关把应用藏在后面，用户先与网关建立经过认证的通道，再由网关代理到应用。应用不直接暴露，也不向用户网络分配可路由的地址。

三条路径的共同点是：判定依据从“网络位置”换成了“身份与上下文”，执行点从“边界防火墙”前移到了“每个资源门口”。

文档还描述了 PDP 的判定输入，即信任算法。它不是固定公式，而是加权判断：身份是否可信、设备是否合规、行为是否异常、目标资源有多敏感，各项汇总成信任评分，再与阈值比较。描述刻意留得抽象，因为不同组织的权重完全不同。入门阶段重要的不是把算法做精确，而是先把信号采集起来。

策略输入与持续评估

把上面的抽象落到工程上，一条访问请求通常要看六类信号。

用户身份。 账号是否真实存在、是否通过多因素认证、属于哪个组、是否有该应用的授权。身份是判定的起点，身份系统的质量直接决定零信任的上限；账号还在共用、离职清理靠人工，后面的策略再精细也没有意义。

设备健康状态。 终端是否由公司纳管、补丁是否及时、磁盘是否加密、是否装了杀毒软件、是否越狱或 root。设备姿态（posture）最容易被忽略，也最能体现差异：同一个账号在公司笔记本和来源不明的个人电脑上，应该得到不同授权。

位置与时间。 登录地点是否在常驻地、是否来自高风险地区、IP 是否属于已知的代理或 Tor 出口；凌晨三点访问财务系统与工作日上午访问，风险显然不同。位置只是信号之一，不能单独放行，否则又退化成“按 IP 信任”；时间更适合做告警和二次认证的触发条件，直接拒绝会制造大量误报。

应用敏感度。 公开的文档系统、内部 Wiki、财务结算系统、生产数据库，应该对应不同的策略等级。分级不是为了好看，而是把有限的管控成本放在高价值资产上。

行为信号。 单位时间内的访问频次、下载量、是否在短时间内访问大量无关应用、是否出现典型的横向探测行为。这类信号需要基线，而基线需要时间积累，所以通常放在项目后期。

这六个输入说明：判定是持续的。登录成功只代表“这一刻验证通过”，不代表之后几小时的每个请求都可以放行。设备掉出合规状态、地点突变、权限被回收，都应触发重新评估。常见做法是给会话设置较短的授权有效期，到期由 PEP 静默向 PDP 重新确认，用户无感知，风险却持续收敛。

执行点该放在哪里

PDP 只做决策，真正拦住流量的是 PEP。PEP 的位置决定了架构的形态，常见有四类。

客户端代理：装在终端上的小程序，拦截发往受保护应用的流量，并采集设备姿态。优点是终端信息最丰富，缺点是只覆盖装了代理的设备。

网关：所有访问先到网关，认证后由网关代理到后端应用。终端无需安装，适合 BYOD，是替代 VPN 最常见的形式。

应用代理：反向代理部署在应用前面，按路径或域名做细粒度控制，对应用透明，但需要逐个接入。

服务网格边舱：在 Kubernetes 这类环境里，每个服务实例旁跑一个边舱代理，服务间每次调用都经过它做身份校验。它管的是东西向流量。

四类执行点有一个共同要求：尽量靠近资源。如果 PEP 离资源很远，只在网络入口放一台设备，那么它后面的网络仍然连通，攻击者绕过它就又能横向移动。反之，PEP 贴着应用部署，即使某台主机失守，能看到的也只是一个应用。

微隔离、应用级访问与 ZTNA

传统访问控制的单位是“网络可达”：两台机器能 ping 通，就默认可以连端口。零信任把它换成“应用授权”：A 服务的某个接口，允许 B 服务以某个身份调用，其余一律拒绝。按应用分组、组间默认拒绝，就是微隔离。难点不在技术，而在梳理调用关系，多数团队并不清楚自己有多少条隐式的跨服务连接。

面向人的访问同理。用户不再获得一段网络，而是获得某个应用的入口。2020 年前后，业界把用应用级代理替代 VPN 的做法称为 ZTNA（Zero Trust Network Access），把网络与安全能力打包成云服务交付的模式称为 SASE。两个词都带着浓重的厂商营销色彩，同一套网关会被贴上不同标签。读者需要分清：零信任是架构原则，ZTNA 与 SASE 是产品形态，买了后者不等于实现了前者。

一个参考实现蓝图

一个最小可用的参考实现包含六部分：身份提供方（含多因素认证）、终端管理、策略引擎（PDP）、网关或应用代理（PEP）、应用，以及统一日志与 SIEM。请求路径如下。

flowchart TD
    U[用户与终端] -->|1 发起访问| P[PEP 网关或应用代理]
    P -->|2 请求判定| D[PDP 策略引擎]
    D --> I[IdP 与多因素认证]
    D --> M[终端管理与姿态]
    D --> S[风险与行为信号]
    D --> Q{信任评估}
    Q -->|3a 允许| P
    Q -->|3b 拒绝| X[返回错误并提示修复]
    P -->|4 仅放行单个应用| R[业务应用]
    P --> L[日志与 SIEM]
    D --> L

图中两条分支对应两种结论：允许时 PEP 只建立到目标应用的单条连接，拒绝时直接返回错误并提示修复设备或补充认证。两条路径都要把判定依据写入日志，否则事后无法解释“为什么放行”。

迁移路径、运维与常见误区

零信任不适合“大爆炸”式改造。稳妥的顺序是：先盘点资产和访问关系；再按敏感度给应用分级；从高价值、低干扰的应用开始接入网关，比如远程运维入口和财务系统；接着叠加设备姿态；最后逐步收缩 VPN 授权范围，只保留少数遗留系统。每步都要有回退方案。

上线后运维重心从“配策略”转向“看日志、调策略”。拒绝日志要抽查，误报率高会逼业务绕过管控，比不做还糟。务必保留 break-glass 账号，用硬件令牌封存并单独告警；策略要像代码一样评审和测试，避免越加越多。用户体验同样要算进成本：多一步认证、错误提示含糊，用户就会绕道私人网盘。

常见的误区有六个：买了产品就宣称实现了零信任；内网仍然默认放行；只验证身份不看设备；策略膨胀到没人能解释某条规则；判定不留日志；以及忽视老协议，把只支持 IP 白名单的遗留系统硬塞进新架构。

小结

零信任的起点是承认“内网可信”已经失效，落点是把每次访问都变成一次有依据的判定。骨架是 PDP 与 PEP 的分离，输入是身份、设备与上下文，输出是应用级的最小授权，而且判定要持续进行。落地时先盘点、再分级、从少量应用起步，把日志和误报当成一等公民。NIST SP 800-207 给的是词汇与思路，不是验收清单；真正的验收标准，是你能否回答“这次访问为什么被允许”。
