Wireshark 分析 HTTPS 流量

HTTPS 把内容藏进了 TLS 记录，却在链路上留下大量可观察的结构性信息。本文以 Wireshark 3.2 为工具，先梳理握手阶段哪些字段可见，再讨论在什么条件下才能合法解密，以及解密后如何阅读 HTTP/2 流量。读者需要具备 TCP 与抓包的基础知识，读完应能独立完成一次有授权的 HTTPS 会话分析，并在拿不到密钥时给出有边界的判断。

链路上究竟还能看到什么

HTTPS 的防护目标是机密性、完整性与身份认证，它并不隐藏通信双方的存在、时间与大致体量。把一次页面访问拆成 TCP、TLS、HTTP 三层来看，TCP 头部完全明文，TLS 记录头同样明文（内容类型、记录版本、长度），真正被加密的只是记录负载。因此即使手里没有密钥，我们仍能拿到五元组、连接起止时间、双向字节数、每条 TLS 记录的边界与长度。

这些看似琐碎的字段，在排障时往往比内容更有用。下面这张表按“在哪一层、是否加密、能回答什么问题”整理了一次 HTTPS 会话中常见的可见信息。

SNI 值得单独说明。它位于 ClientHello 的 server_name 扩展中，目的是让同一 IP 上的虚拟主机在握手开始时就选对证书，因此必须明文传输。2020 年，加密 SNI 的方案还停留在草案阶段，常见的叫法是 ESNI，后来演进为 ECH，实际部署范围很小。所以本文所讨论的抓包里，SNI 基本总是可见的，这也是判断“用户访问了哪个域名”最直接的线索。

ALPN 同样明文，它决定了握手之后跑 HTTP/1.1 还是 HTTP/2。若客户端声明了 h2 而服务端只回 http/1.1，多数浏览器会接受降级继续通信，但性能特征会明显变化，这类问题在抓包里一眼就能看出来。

证书的位置则随版本而变。TLS 1.2 的 Certificate 消息在 ServerHello 之后明文发送，Wireshark 可以直接展开证书链、读取主题、SAN 与有效期。TLS 1.3 把 Certificate、CertificateVerify 与 Finished 一起放进了加密的握手阶段，没有密钥就只能看到几个长度不同的 Application Data 记录。很多人在升级到 TLS 1.3 后抱怨“看不到证书了”，原因就在这里，并不是抓包方法出了问题。

包长能提供的信息有限。TLS 1.3 允许记录填充，HTTP/2 有 9 字节帧头与 HPACK 头部压缩，TCP 还会合并、拆分与重传，这些因素叠加后，包长只能给出量级判断。我们可以说“这是一次以下载为主、突发集中在 0.8 秒内的传输”，却不能据此断言“下载的是一张 200 KB 的图片”。443 端口也不证明流量一定是 HTTPS，判定协议要看握手特征。

理解握手是读懂 HTTPS 抓包的前提。TLS 1.3 在 TLS 1.2 的基础上把握手压缩到一轮往返，并把大量字段挪进了加密区域。下图是一次完整的 TLS 1.3 握手，兼顾了会话恢复的场景。

先看 ClientHello。它的 legacy_version 字段固定写成 0x0303，也就是 TLS 1.2，这并非客户端只支持 1.2，而是为了穿过那些不认识新版本号的中间设备；真实版本在 supported_versions 扩展里，通常列出 1.3 与 1.2。legacy_session_id 在 TLS 1.3 中也被复用，非空值用于触发中间盒兼容模式。cipher suites 列表的顺序表达了客户端偏好，TLS 1.3 的套件只剩下 AEAD 组合，例如 TLS_AES_128_GCM_SHA256 与 TLS_CHACHA20_POLY1305_SHA256。key_share 扩展则直接带上客户端为某个椭圆曲线组生成的公钥，这是 1-RTT 握手能成立的关键。

ServerHello 只做三件事：确认版本、选定套件、回送服务端的 key_share。若服务端启用了会话恢复，还会带上 pre_shared_key 扩展，此时握手可以走 PSK 路径，省掉证书与密钥交换。紧随其后的 ChangeCipherSpec 是一条“假装还在用 1.2”的兼容记录，Wireshark 会标注它是 Ignored Unknown Record 或 CCS，不必紧张，这是正常现象。

TLS 1.2 的握手则长得多，也更“透明”。ServerHello 之后是明文 Certificate，可以直接看到整条证书链；ServerKeyExchange 携带 ECDHE 的曲线参数与服务端签名；ServerHelloDone 表示服务端发言结束；客户端回 ClientKeyExchange，双方再各发 ChangeCipherSpec 与 Finished。因为证书明文，TLS 1.2 的抓包非常适合排查证书链与主机名问题，这一点在 TLS 1.3 普及之后反而成了“旧版本的便利”。

握手包也是排障的第一现场。服务端若直接回 Alert 70，说明它不接受客户端提出的版本；Alert 40 或 71 多半指向套件或安全强度不满足；Alert 120 是 ALPN 协商失败，常见于服务端只允许 h2 而客户端只提供 http/1.1 的反向配置。Wireshark 的显示过滤器可以把这些包单独筛出来：

第一条筛出所有 ClientHello，用来统计有多少次独立连接；第二条按 SNI 过滤，适合在一堆并发连接里锁定目标站点；第三条把告警单独列出，握手失败的现场往往只有一两个 Alert 包。需要提醒的是，TLS 1.3 下证书与告警都可能落在加密记录里，过滤器能筛到包，却未必能读出原因，这时要结合客户端侧的错误提示与服务端日志一起看。

为什么默认解不开：前向保密与会话密钥

几乎每个刚接触抓包的人都会问同一个问题：既然我能在服务器上拿到私钥，为什么 Wireshark 还是解不开？答案在于现代 TLS 交换的不是“用公钥加密的会话密钥”，而是一组双方各自算出来的临时秘密。

TLS 1.3 的密钥交换基本只剩 ECDHE，恢复会话时走 PSK；TLS 1.2 也早已把 ECDHE 套件作为默认选项。以常用的 x25519 为例，客户端与服务端在握手时各自生成一对临时的椭圆曲线密钥，只把公钥放进 key_share 或 ServerKeyExchange 发出去。双方用自己的私钥和对方的公钥做一次 Diffie-Hellman 运算，得到同一个共享秘密，再经过 HKDF（TLS 1.3）或 PRF（TLS 1.2）逐层派生出握手密钥与应用密钥。整个过程里，会话密钥从来没有以任何形式出现在链路上，临时私钥也在握手结束后被丢弃。

这就是前向保密的含义：即使攻击者在若干年后拿到了服务端的长期私钥，也无法回溯解密当时录下的流量，因为那对临时私钥早已不存在。反过来说，这也决定了抓包分析的边界：没有会话密钥，任何人都无法从密文还原明文，这不是工具能力问题，而是密码学保证。

与 ECDHE 相对的是静态 RSA 密钥交换，也就是 TLS_RSA_WITH_* 系列套件。客户端用服务端证书里的公钥直接加密一个预主密钥发过去，服务端用私钥解开，双方再据此派生会话密钥。在这种模式下，长期私钥确实足以解密历史流量，但它不具备前向保密，一旦私钥泄露，此前录下的所有会话都会暴露。也正因如此，主流浏览器从 2018 年起陆续移除了对静态 RSA 密钥交换的支持，2020 年的公网服务基本只剩下 ECDHE 一种选择。

可以用一棵简单的判断树来概括“能不能解”：

flowchart TD
    A[拿到一段 HTTPS 抓包] --> B{有会话密钥吗}
    B -->|有 key log| C[可以解密 与套件无关]
    B -->|没有| D{是静态 RSA 套件吗}
    D -->|是 且有服务器私钥| E[可以解密 仅限该会话]
    D -->|否 ECDHE| F[无法解密 只能看元数据]
    C --> G[继续分析 HTTP 层]
    E --> G
    F --> H[转向元数据推断]

判断套件类型并不难。在 TLS 1.2 的 ServerHello 里看 Cipher Suite 字段，名字以 TLS_ECDHE_ 开头的就是临时密钥交换，以 TLS_RSA_WITH_ 开头的才是静态 RSA。TLS 1.3 的套件名统一是 TLS_AES_* 或 TLS_CHACHA20_*，不再体现密钥交换方式，因为它只允许 ECDHE 与 PSK，看到 1.3 就可以直接判定“无私钥路径”。

还有一个常被忽略的点：会话恢复。TLS 1.2 的 Session ID 与 Session Ticket、TLS 1.3 的 PSK，都是把上一次握手的密钥材料保存下来复用，抓包里表现为握手包数量骤减。恢复会话同样不会把密钥放到链路上，因此“三个包完成握手”并不奇怪，也不意味着加密变弱。

获准解密：从 key log 到服务器私钥

在明确了“必须有密钥”之后，接下来的问题就是密钥从哪里来。工程上只有三类正当来源：自己客户端导出的会话密钥、自己服务器持有的静态 RSA 私钥、以及完全受控的测试环境。三者都建立在一个前提上：你对这段流量拥有所有权或明确授权。

最常用的是 SSLKEYLOGFILE。它的原理很朴素：浏览器在完成密钥派生后，把会话密钥按固定格式追加写入一个文本文件，Wireshark 读取该文件，就能在不解密握手的情况下直接拿到密钥。Chrome 与 Firefox 都支持这一机制，格式由 NSS 定义，每行形如“标签 客户端随机数 密钥”，TLS 1.2 常见的是 CLIENT_RANDOM，TLS 1.3 则会写入 CLIENT_HANDSHAKE_TRAFFIC_SECRET、SERVER_HANDSHAKE_TRAFFIC_SECRET、CLIENT_TRAFFIC_SECRET_0 等多条记录。

Chrome 在 Linux 与 macOS 上同样识别这个变量，但需要从命令行启动，已经运行的实例不会重新读取。写完密钥文件后，在 Wireshark 中依次打开 Preferences、Protocols、TLS，把“(Pre)-Master-Secret log filename”指向该文件。重新载入抓包，原本显示 Application Data 的记录就会变成可展开的 HTTP/2 或 HTTP/1.1。

第二种来源是服务器私钥，但它的适用范围被严格限制在静态 RSA 密钥交换。配置位置在同一个 TLS 协议首选项页的 RSA keys list，需要填写服务器 IP、端口、协议与私钥文件路径。很多人照着教程配了私钥却毫无效果，原因通常是抓包用的是 ECDHE 套件，此时 Wireshark 会明确提示“无法用该私钥解密”，这不是配置错误，而是数学上不可能。

第三种是受控测试环境。自己搭一套 Nginx 与自签 CA，客户端也由自己控制，此时既可以用 key log，也可以在测试构建里给服务端接入 keylog 回调。需要说明的是，Nginx 本身并不读取 SSLKEYLOGFILE，服务端导出密钥通常要改代码或使用带调试接口的构建，因此这只适合实验环境，不适合直接搬到生产。

最后必须把边界说清楚。对自有流量、经授权的渗透测试目标、或本机实验环境做解密，是合法的技术分析；未经授权截获并解密他人的 HTTPS 流量，无论在技术上是否可行，都是不可接受的行为，也可能触犯法律。抓包本身就会接触到账号、Cookie 与个人信息，解密只是把风险放大，权限与目的必须事先明确。

解密之后：HTTP/2 帧、流与一次慢请求定位

有了密钥，Wireshark 会把 TLS 记录里的明文交给上层解析器。若 ALPN 协商结果是 h2，协议列会显示 HTTP2，原本连续的 Application Data 被还原成一个个帧。理解帧结构是读懂这类抓包的关键：每个帧有 9 字节头，包含长度、类型、标志与流标识符，负载则按类型解释。

常见的帧类型不多。HEADERS 携带请求或响应的头部字段，经过 HPACK 压缩；DATA 携带实体内容；SETTINGS 用于交换连接级参数；WINDOW_UPDATE 做流量控制；RST_STREAM 终止单个流；GOAWAY 表示连接即将关闭；PING 用于探活。客户端发起的流使用奇数编号，服务端发起的是偶数，同一个连接上可以同时存在多个流，这正是 HTTP/2 多路复用的由来。

下面用一次示意图性质的会话来串起整个流程。场景是浏览器访问由 Nginx 提供服务的测试站点，已通过 SSLKEYLOGFILE 提供密钥，抓包在客户端侧完成。所有数值仅用于说明分析方法，并非真实业务数据。

第一步，定位连接。用 tls.handshake.type == 1 找到 ClientHello，确认 SNI 为被测域名，supported_versions 中包含 0x0304，说明客户端优先尝试 TLS 1.3；ServerHello 回选了 0x0304 与 TLS_AES_128_GCM_SHA256，ALPN 在 Encrypted Extensions 中确认为 h2。到这里可以确认没有降级，也没有套件不匹配。

第二步，确认解密生效。在 Protocol 列看到 HTTP2，说明密钥文件匹配成功；若仍是 Application Data，先检查客户端随机数是否与 key log 中的记录对应，再确认抓包是否在设置环境变量之前开始。

第三步，找到目标请求。用 http2.streamid 逐条查看，或直接在过滤框输入 http2.headers.authority contains “example.test”，展开 HEADERS 帧可以看到 :method、:path、:authority 与 user-agent。假设关注的是 /api/report 这条请求，记下它所在的流号，例如 5。

第四步，测量耗时。给抓包加上时间列，或者用 frame.time_delta_displayed 观察相邻帧间隔。把该流第一个 HEADERS 帧的时间记为 t0，第一个 DATA 帧记为 t1，最后一个 DATA 帧记为 t2。t1 减 t0 近似等于服务端处理时间加上一个单程网络时延，t2 减 t1 是响应体的传输时间。如果 t1 减 t0 达到 1.8 秒，而握手阶段的 RTT 只有 20 毫秒，那么瓶颈大概率在应用侧，而不是网络。

第五步，交叉验证。Nginx 的访问日志里记录了 $request_time 与 $upstream_response_time，若二者与 t1 减 t0 吻合，就可以把结论落到具体上游服务；若日志显示很快而抓包很慢，则要怀疑客户端侧排队、TLS 记录分片或中间设备缓冲。抓包只能证明“链路上发生了什么”，不能单独证明“服务端内部为什么慢”，这一步的交叉验证不能省。

拿不到密钥时：从元数据做有限推断

绝大多数生产抓包是没有密钥的，这时分析目标要从“读内容”切换为“读行为”。可行的推断集中在连接、时间、体量、命名与错误五个维度，每一条都要配上“能得出什么、不能得出什么”的边界。

连接维度看复用。同一个五元组上如果只出现一次 ClientHello，之后长时间有双向数据，说明客户端在复用连接；如果每隔几百毫秒就新建一条连接，可能是连接池配置过小，也可能是服务端主动关闭。TLS 1.3 的会话恢复表现为 ServerHello 带 pre_shared_key、证书阶段消失，包数明显减少。

时间维度看节奏。TCP 三次握手的完成时间给出一个 RTT 基线，ClientHello 到 ServerHello 的间隔反映服务端与网络的总延迟，请求之间的空闲间隔则接近用户思考时间。把这些时间画成时序，能区分“页面本身慢”和“用户在等待时没有发起请求”。

体量维度看方向与突发。统计某条连接上客户端到服务端、服务端到客户端的字节数，可以判断这是一次上传还是下载；观察突发是否集中在握手后极短时间内，可以推测是否为静态资源批量加载。这里的结论只能是量级，不能精确到文件类型。

命名维度看 SNI 与证书。SNI 暴露了用户访问的域名，TLS 1.2 的明文证书还能给出 SAN 列表、签发者与有效期，足以判断服务是否用了 CDN、是否走了内部域名。即使是 TLS 1.3，SNI 依然可见，因此“加密后域名也保密”的说法并不成立。

错误维度看 TCP 与告警。RST 出现在握手后不久，可能是服务端拒绝了该请求或中间设备拦截；大量重传与零窗口说明链路质量或接收端处理能力有问题；握手阶段的 Alert 则直接指向版本、套件或证书。把这些信号与时间线对齐，往往比猜测内容更有价值。

必须强调一点：元数据能支持“这是一次约 300 KB 的下载，服务端在 1.2 秒后才开始回数据”，但不能支持“用户下载了某份报表”。在没有密钥的情况下，任何关于具体内容的断言都是过度解读，写进报告会削弱整份分析的可信度。

排障案例矩阵：从证书链到 TLS 1.3 中间盒

HTTPS 的故障大多集中在握手阶段，而且症状相似、原因各异。下表把常见现象、抓包特征与定位手段放在一起，便于按图索骥。表中结论基于 TLS 1.2 与 1.3 的标准行为，具体环境仍需结合客户端与服务端日志。

现象 抓包特征 常见原因 定位手段
浏览器报证书不受信任 TLS 1.2 可见不完整链，或客户端发 Alert 48 服务端只发叶子证书，缺中间 CA 展开 Certificate 看链长度，用 openssl s_client 复核
浏览器报名称不匹配 证书 SAN 与 SNI 不一致 虚拟主机配错证书或 SNI 分流错误 对比 ClientHello 的 SNI 与证书 SAN
协商结果总是 TLS 1.2 ClientHello 含 1.3，ServerHello 回 1.2 服务端未开 1.3，或中间盒拦截 看 supported_versions 与 ServerHello 选定值
握手在 ClientHello 后停滞 无 ServerHello，多次重传 ClientHello 中间设备丢弃带新扩展的包 对比不同网络路径，检查 MTU 与设备策略
直接 handshake_failure Alert 40 或 71 套件不匹配、密钥长度不足 比对双方套件列表与安全级别配置
ALPN 协商失败 Alert 120 或退化到 http/1.1 服务端只允许 h2，客户端未提供 查 ClientHello 与 Encrypted Extensions 的 ALPN
首屏明显变慢 握手后出现额外的 OCSP 请求 未启用 OCSP stapling 看 ClientHello 是否带 status_request，服务端是否回装订响应
频繁完整握手 每次请求都有 Certificate 与密钥交换 会话恢复未生效 检查 ticket 下发与负载均衡是否一致

证书链问题是出现频率最高的一类。TLS 1.2 下可以直接在 Certificate 消息里数证书张数，只有一张叶子证书而缺少中间 CA 时，桌面浏览器可能因为缓存过中间证书而正常，移动端或新环境却直接失败。这类“同一站点在不同设备表现不同”的现象，用抓包对比两端最有效。

主机名不匹配则要看 SNI 与 SAN 的对应关系。常见于 Nginx 上多个 server 块共用 443，默认 server 的证书被错误地返回给其他域名。抓包里 ClientHello 的 SNI 是 A，证书 SAN 却只有 B，问题一目了然。TLS 1.3 下证书被加密，只能借助客户端错误码、服务端日志或在本机用 openssl s_client 复现。

协议降级需要区分“正常回退”与“被中间盒压低”。前者是服务端确实没开 1.3，ServerHello 的 supported_versions 明确回 0x0303；后者常见于某些老旧的负载均衡或安全设备，它们对 ClientHello 里的新扩展处理不当，导致握手卡住或被迫重试。TLS 1.3 定义了降级哨兵值，支持 1.3 的服务端在最终协商为 1.2 时，会把特定字节写入 ServerHello 随机数的末尾，客户端据此判断自己是否被降级，Wireshark 也会在解析时给出提示，这是判断是否存在中间人干预的重要线索。

TLS 1.3 与中间盒的兼容问题在 2020 年仍不少见。为了照顾只认 TLS 1.2 结构的设备，客户端会在 ClientHello 中带上非空的 legacy_session_id，并在握手中插入 ChangeCipherSpec 记录，服务端也会照做。若抓包里看到 CCS 出现在 ServerHello 之后、且被标记为忽略，这是兼容机制在起作用；若看到 ClientHello 发出后长时间没有响应、随后客户端重试，则要怀疑路径上有设备直接丢弃了这些包。

OCSP stapling 影响的是首屏时间而非连通性。启用装订后，服务端在握手时一并送上 OCSP 响应，客户端不必再单独查询 CA。TLS 1.2 下表现为 Certificate 之后的 CertificateStatus 消息；TLS 1.3 下该信息被放进加密的证书条目扩展，抓包里看不到明文，只能通过“握手后是否还有发往 OCSP 域名的请求”间接判断。若看到握手完成后紧接着一条到 CA 的查询，基本可以认定装订没有生效。

会话恢复的问题往往表现为“性能忽然变差”。正常情况下，TLS 1.2 的恢复握手只有 ServerHello、CCS、Finished 几个包，TLS 1.3 则直接走 PSK。如果每次请求都完整走一遍证书与密钥交换，需要检查服务端是否下发 ticket、多台后端之间的 ticket 密钥是否一致。TLS 1.3 的 0-RTT 还能进一步省掉一次往返，但它有重放风险，只应允许幂等请求使用，这一点在分析抓包时也要留意，看到 early data 不等于配置正确。

抓包卫生、QUIC 边界与收尾建议

HTTPS 抓包天然携带敏感信息，解密之后更是如此。key log 文件等同于一段时间内的全部会话密钥，必须按密钥材料管理：目录权限收紧到仅本人可读，文件名带日期，分析结束立即删除，绝不提交到代码仓库，也不要与抓包文件放在同一台共享机器上。团队协作时，密钥应由抓包者本人在本地加载，而不是随 pcap 一起传递。

pcap 的共享同样需要处理。即使没有解密，包里也有 IP、SNI、证书、DNS 查询与时间规律，足以勾勒出用户行为。对外提供样本前，应截断负载、移除与本问题无关的会话，必要时替换地址。Wireshark 自带的 editcap 可以按条件裁剪或限制快照长度，例如只保留目标端口并截去应用层负载：

第一条按显示过滤器保留 443 流量，第二条把每个包截断到 96 字节，TLS 记录头与部分握手字段仍在，应用层内容被丢弃。更彻底的做法是使用专门的匿名化工具替换 IP 与 MAC，但无论用哪种方式，发布前都要人工抽查，确认没有残留的账号、Cookie 或内部域名。留存时间遵循最小必要原则，分析完成后按组织要求归档或销毁，并记录访问者与时间。

QUIC 是另一个必须交代的边界。QUIC 把传输层搬到 UDP 之上，默认使用 443 端口，握手内嵌 TLS 1.3，因此抓包里看到的是 UDP 而非 TCP。2020 年，HTTP/3 仍处于草案阶段，IETF 的 QUIC 草案版本迭代频繁，Wireshark 3.2 能按草案版本解析 Initial、Handshake 与 Short Header 包，但字段名与支持程度随版本变化，遇到不认识的长包头版本时会直接退化为 Data，这是工具成熟度的限制，不是抓包失败。

QUIC 的可见性比 TLS over TCP 更低。Initial 包的头部受一轮由连接 ID 派生的密钥保护，抓包工具可以解开头部以读取版本与连接 ID，但握手之后的负载全部加密。用 key log 解密 QUIC 在 Wireshark 3.2 中已经可用，前提是客户端同样导出密钥，而且版本与解析器匹配；实践中成功率不如 TCP 上的 TLS 稳定。因此排查 HTTP/3 问题时，浏览器导出的 netlog、服务端的 qlog 往往比 pcap 更有信息量。

回到方法层面，HTTPS 流量分析可以归纳为三步：先判断有没有密钥，有则直接读 HTTP 层，没有则退到元数据；再用握手包确认版本、套件、SNI 与 ALPN，把“连不上”和“连上了但慢”分开；最后把抓包时间线与客户端、服务端日志对齐，让结论落在可验证的证据上。工具只是放大器，边界意识才决定分析是否可信。

小结

HTTPS 并不隐藏通信的存在，IP、端口、时间、包长、SNI、ALPN 始终可见，TLS 1.2 的证书也明文，TLS 1.3 则把证书与告警一起加密。能否解密取决于密钥而非工具：ECDHE 提供前向保密，会话密钥从不上链路，只有静态 RSA 套件才可能用服务器私钥解密。工程上可行的路径是自己客户端的 SSLKEYLOGFILE、受控测试环境，以及在明确授权前提下对自有流量的分析，未经授权解密他人流量不可接受。解密之后，重点转向 HTTP/2 的流与帧，用流号、HEADERS 与 DATA 的时间差定位慢请求，并用服务端日志交叉验证。没有密钥时，应把结论限制在连接复用、时序、体量与错误特征上，避免对内容做过度断言。最后，key log 与 pcap 都应按敏感数据管理，QUIC 场景则要接受可见性更低的现实。
