Redis 持久化与高可用方案

Redis 把数据放在内存里，读写快得让人放心，可一旦进程退出或者机器断电，这些数据就只剩下最后一次落盘的样子。本文要回答两个相邻但不同的问题：数据怎么安全地落到磁盘，以及单台机器倒下时服务怎么继续。读者需要已经熟悉 Redis 的基本命令与配置，读完之后应当能为一套业务选出合适的持久化组合、设计出可演练的恢复流程，并且知道哪些“高可用”其实只是心理安慰。

持久化与高可用：两个问题，两套答案

很多人第一次给 Redis 做运维方案时，会把“开了持久化”和“做了高可用”当成同一件事。这两件事的目标、失败模式与验证方法都不一样，混在一起谈，最后往往两头都不到位。

持久化解决的是“重启之后还在不在”

持久化（persistence）把内存中的数据结构写到磁盘，回答的是：进程崩溃、机器重启后，数据能恢复到哪个时刻。它衡量的指标是 RPO（Recovery Point Objective，恢复点目标），即业务最多能接受丢多长时间的数据。RDB 十分钟落一次盘，RPO 就是十分钟；AOF 每秒刷一次，RPO 约一秒。但它保护不了机器本身：磁盘坏了、断电超过 UPS 支撑时间，落盘的文件一样读不出来。

高可用解决的是“节点倒下之后服务还能不能连上”

高可用（high availability）关心的是服务的连续性：主节点挂掉之后，有没有别的节点接替它，客户端多久能重新连上。它衡量的指标是 RTO（Recovery Time Objective，恢复时间目标），也就是业务能容忍多长的不可用时间。

复制、Sentinel、Cluster 都属于这一类，它们把数据放在多台机器上，并在主节点失联时提升某个副本。但复制是异步的，主节点确认写入后还没同步就宕机，这部分写入就永久丢了；更糟的是，误删一条 key 也会被毫秒级同步到所有副本，高可用会把错误一起高可用。

用 RPO 与 RTO 给业务分类

选型之前，先给数据分类，比背配置项有用得多。下表是笔者常用的起点，具体数字是设计目标，需要按业务实际压测和评审。

数据角色 丢失的后果 目标 RPO 目标 RTO 推荐组合
纯缓存 回源重建，只是数据库压力上升 全量可丢 秒级到分钟级 可不开持久化，主从或 Cluster
会话与验证码 用户重新登录 分钟级 秒级 RDB 加主从，或交给外部存储
排行榜、计数器 可以重算，但要花时间 秒级 秒级 AOF everysec 加主从
队列、去重标记 任务丢失、重复投递 接近 0 秒级 AOF everysec 加 Sentinel
主存储（无其他副本） 业务数据永久丢失 接近 0 分钟级 AOF everysec 或混合持久化，加副本与异地备份

一个常见的误判是“我们只是缓存，丢了没关系”，但缓存里往往混着分布式锁、限流计数、幂等标记，这些数据丢了直接变成正确性问题。

RDB：时间点快照与 fork 的代价

RDB 是 Redis 最早、也最直观的持久化方式：把某一时刻的整个数据集序列化成一个二进制文件，默认叫 dump.rdb。它保存的是数据本身，不是操作过程，所以文件紧凑、加载快，非常适合做备份和跨环境搬运。

快照是怎么产生的

触发一次快照有三条路径：配置里的 save 规则、客户端显式执行 BGSAVE、以及主从复制时主节点为全量同步生成 RDB。SAVE 命令也能生成快照，但它在前台执行，会阻塞整个事件循环，生产环境基本只用于调试和关机前。

save 规则的语义是“N 秒内至少有 M 个 key 变化，就触发一次后台保存”。Redis 不为每条规则起定时器，而是用每 100 毫秒执行一次的定时任务，检查距上次保存的时间与脏 key 计数是否同时满足某条规则。

规则之间是“或”的关系，最细的一档决定了最坏情况下的 RPO：写入安静时最多丢十五分钟，写得很热闹时最多丢一分钟。想让 RPO 更小，就把 save 60 10000 调得更激进，代价是更频繁的 fork。

fork 与写时复制

BGSAVE 的核心是 fork()。子进程拿到一份和父进程几乎一样的内存页表，然后从这份“冻结”的视图里把数据写进临时文件，写完再原子地重命名为 dump.rdb。与此同时，父进程继续处理客户端请求，不做任何阻塞式等待。

父子进程共享物理内存页，父进程一旦要修改某一页，内核必须先把这一页复制给子进程，这就是写时复制（copy-on-write，COW）。于是快照期间的内存开销与“被修改的数据量”成正比：写得越猛、快照拖得越久，复制的页越多；极端情况下父子各占一份完整数据集，瞬时内存接近翻倍。

flowchart TD
    A[父进程收到 BGSAVE] --> B[fork 子进程]
    B --> C[父子共享内存页, 页表只读]
    C --> D[子进程顺序写临时 RDB 文件]
    C --> E[父进程继续处理写请求]
    E --> F{写入的页是否共享}
    F -->|是| G[内核复制该页, 父进程改副本]
    F -->|否| H[直接写入]
    D --> I[写完 rename 为 dump.rdb]
    G --> D
    H --> D

所以“内存用了 60%，机器还剩 40% 余量”这种估算会翻车：真正要算的是 used_memory 加上快照期间可能被复制的页，再留出碎片余量。

fork 的延迟从哪来

fork() 本身不复制数据，但要复制页表，耗时与进程的虚拟内存规模成正比，而不是与当前数据量成正比。几十 GB 的实例，fork 花掉几百毫秒并不稀奇，这段时间主线程被挂起，客户端命令排队，表现为明显的延迟毛刺。几个可以动手的缓解手段：

  • 控制单实例内存，别把一台机器堆到上百 GB，宁可多分几个实例。
  • 确认 vm.overcommit_memory = 1，否则内存紧张时 fork 可能直接失败，日志里会出现 Can't save in background: fork: Cannot allocate memory。
  • 关闭透明大页（THP）。THP 会让 COW 的复制单位从 4 KB 变成 2 MB，放大延迟和内存开销，官方文档明确建议关闭。
  • 把 save 规则调稀疏一些，或者把快照时间点错开到业务低峰。

stop-writes-on-bgsave-error 的两难

这个选项默认为 yes：最近一次后台保存失败后，主节点拒绝所有写命令，返回 MISCONF Redis is configured to save RDB snapshots, but it is currently not able to persist on disk。理由很直接：磁盘写不进去了，继续接受写入只会让内存与磁盘的差距越来越大。

但对纯缓存来说这是个陷阱：磁盘满了，Redis 拒绝写入，业务把所有请求打到数据库，一次磁盘告警演变成一次全站故障。笔者的做法是按角色分开：主存储保持 yes，纯缓存改成 no，同时把 rdb_last_bgsave_status 接入告警。

RDB 的优缺点

优点是文件紧凑，体积通常远小于 AOF；加载时按序反序列化，恢复速度快；单个文件便于归档和异地拷贝；日常只在 fork 与 COW 时才有抖动。缺点是两次快照之间的数据全部丢失；fork 的延迟毛刺随实例变大而变严重；没法只备份某几个 key；文件格式与版本相关，低版本 Redis 读不了高版本生成的 RDB。

AOF：把每条写命令记下来

RDB 记的是“结果”，AOF（append only file）记的是“过程”：每一条会修改数据的命令，执行完之后按 RESP 协议追加到文件末尾。恢复时把文件里的命令从头重放一遍，就能得到和崩溃前一致的数据集。

写入路径与三种 fsync 策略

一次写请求在 AOF 模式下的路径是：命令在内存中执行，结果追加到 aof_buf 缓冲区；事件循环在进入休眠前把缓冲区 write() 到文件；最后按 appendfsync 决定何时调用 fsync() 把页缓存刷到磁盘。

write() 只是把数据交给操作系统，断电后仍在页缓存里的部分会丢；fsync() 才是真正的落盘点，而它很贵。三档策略就是在这个成本上做取舍：

取值 行为 崩溃时最多丢 代价
always 每条命令都 fsync 后才回复客户端 一条命令 吞吐下降明显，延迟受磁盘摆布
everysec 后台线程每秒 fsync 一次 约 1 秒 默认值，绝大多数场景的平衡点
no 交给操作系统自己刷 数十秒，取决于内核 最快，但不可控

everysec 的 fsync 由后台线程执行，正常情况下不阻塞主线程。但如果某次 fsync 卡住超过一秒（磁盘抖动、云盘限流、快照任务抢 I/O），主线程为了不超过“最多丢两秒”的承诺，会主动等待上一次 fsync 完成，这段时间写请求一起排队。这种毛刺在监控上表现为周期性的延迟尖峰，排查时要看磁盘写延迟而不是 Redis 本身。no-appendfsync-on-rewrite 可以在重写期间暂停 fsync，代价是重写持续多久，丢失窗口就有多久，对主存储通常不划算。

文件为什么会无限增长

AOF 记录的是操作，不是状态。对一个计数器连续执行一百万次 INCR，文件里就有一百万条命令，而数据集里只有一个整数；DEL 同样会被追加，旧数据不会因此从文件里消失。

所以 AOF 必须定期重写（rewrite）。重写不是压缩原文件，而是按当前数据集重新生成最小命令集：一个有一万条记录的 hash，重写后是几条 HSET，而不是它历史上经历过的所有 HSET 与 HDEL。

sequenceDiagram
    participant P as 主进程
    participant C as 子进程
    participant O as 旧 AOF
    participant N as 新 AOF 临时文件
    P->>C: fork
    C->>N: 按 fork 时刻的数据集写最小命令集
    P->>O: 继续追加新命令
    P->>P: 同时缓存到重写缓冲区
    C-->>P: 写完并退出
    P->>N: 追加缓冲区中的增量命令
    P->>N: rename 覆盖旧 AOF
    P->>N: 后续命令直接追加

重写期间旧 AOF 仍在正常追加，所以子进程中途失败也不影响恢复能力；只有 rename 成功，新旧文件才完成交接。

自动重写阈值与手工触发

需要立刻整理时可以手工执行 BGREWRITEAOF。如果已有子进程在重写，命令不会失败，而是被排进队列；运维脚本里循环调用它，只会排出一长串任务，每个都要 fork 一次。

文件损坏与修复

AOF 最常见的损坏是尾部截断：写到一半机器断电，最后一条命令不完整。启动时读到不完整命令，aof-load-truncated yes 会截掉尾部继续启动并打印警告，设为 no 则直接拒绝启动。更麻烦的是文件中间出现无法解析的内容，比如磁盘坏块或人为编辑，这时需要 redis-check-aof：

--fix 的策略是从头扫描，遇到第一条读不通的命令就把后面全部截掉，不会猜测那条命令原本是什么，所以修复点之后的数据确定丢失。这也是为什么修复前必须备份：截断位置可能比预期早，届时还能改用更早的 RDB 拼接 AOF。

AOF 的优缺点

AOF 的最大价值是把 RPO 从分钟级压到秒级，而且不依赖数据量：一百万个 key 和一百个 key，everysec 下丢的都是最近一秒。追加写对磁盘友好，文件是文本协议，出问题时能直接看见命令序列。

代价是文件更大、加载更慢、fsync 有固定开销，重写同样要 fork。还有一个教训：重写逻辑出 bug 时可能生成“看起来正常但语义错误”的文件，任何方案都不能只靠“文件存在”证明数据完好。

混合持久化与策略选型

RDB 快但丢得多，AOF 丢得少但加载慢，两者的短板恰好互补。Redis 4.0 起提供了把二者拼起来的做法，到 5.0 之后成为默认行为。

RDB 做底、AOF 做增量

开启 aof-use-rdb-preamble yes 后，AOF 重写生成的文件不再全是命令，而是“前半段是 RDB 快照，后半段是重写期间的增量命令”。文件仍叫 appendonly.aof，Redis 通过文件头判断前半段是 RDB 还是纯命令，加载时先反序列化快照，再重放尾部。这让加载速度回到 RDB 的量级，而 RPO 仍是秒级：几十 GB 的实例，纯 AOF 重放可能要几分钟，混合模式通常能压到十几秒到几十秒，具体取决于尾部增量，需要在目标环境实测。

代价是文件不再是纯文本，人工排查命令序列的能力没了；低于 4.0 的 Redis 读不了这种文件，回滚时要先关闭该选项并触发重写。混合模式也不改变写入路径，appendfsync 的取舍依然存在。

按数据角色选组合

把前面的分析落到具体业务上，笔者推荐这几组搭配：

  • 纯缓存：可以完全关闭持久化，也可以只留 RDB 做冷启动加速。重点不在磁盘，而在主从或 Cluster 提供读扩展与故障转移。maxmemory 与淘汰策略要配好，否则重启后缓存为空的瞬间会把数据库打穿。
  • 会话存储：RDB 加主从即可。丢一分钟的会话，用户重新登录一次就能接受；不想让用户感知，就把会话放到带持久化的外部存储。
  • 计数器、排行榜、队列标记：AOF everysec 或混合持久化。这类数据贵在准确，丢一秒的计数可能意味着对账差异。
  • 事实上的主存储：混合持久化加副本，加 Sentinel 或 Cluster，再加异地备份。前提是业务能容忍秒级丢失，并且有独立的对账或补偿机制。

磁盘怎么估

估算分三块。数据文件本身：RDB 通常比内存小；AOF 在两次重写之间持续增长，稳态大小近似于重写后大小乘以增长阈值。重写临时文件：重写在同目录写新文件再 rename，峰值时新旧两份并存，保守按数据集的两倍预留。最后是日志与系统本身，量不大，但磁盘打满时它就是最后一根稻草。持久化目录应放在独立数据盘，与日志盘分开。

备份不等于持久化

持久化保证“本机重启能起来”，备份保证“本机彻底没了还能重建”。这两件事经常被合成一句话，然后在机房搬迁或者误删实例时一起失效。

一个可执行的策略：每天低峰期在主节点执行 BGSAVE，等 rdb_bgsave_in_progress 回到 0 后把 dump.rdb 拷到对象存储或另一台机器；保留 7 天日备份与 4 周周备份，需要精确回滚时额外保留 AOF。拷完必须用 redis-check-rdb 验证可读，否则备份的可能只是一个大小正确的空壳。从节点的 RDB 也能用来备份，前提是 replica-read-only 没被改成可写、偏移量确实追上了主节点。

主从复制：把数据多放几份

持久化解决单机重启，复制解决单机消失。Redis 的复制是异步的、基于命令流重放：从节点连上主节点，先拿一份全量数据，之后持续接收转发的写命令。

从 replicaof 到 PSYNC

在从节点配置 replicaof 10.0.0.12 6379 即可建立复制关系。这个名字在 5.0 之前叫 slaveof，旧命令仍可用，但新配置一律建议用 replicaof。主节点开了密码时，从节点要配 masterauth；6.0 引入 ACL 后，多用户场景用 masteruser 指定用户名。

第一次同步由从节点发起 PSYNC ? -1，意思是“我没有历史，请给我全量”。主节点在后台生成 RDB，同时攒下这段时间的新写入，等传完再补发。从节点收到 RDB 会先清空自己的数据集再加载，这是很多人第一次做主从时被吓到的地方。

断线重连与部分同步

网络抖一下就要全量重传，代价太大。所以从节点会记住主节点的复制 ID（40 位十六进制串）和自己已处理的偏移量，重连时发 PSYNC <replid> <offset>。主节点检查偏移量是否还在复制积压缓冲区（repl backlog）里：在，就回 +CONTINUE 补发缺失命令；不在，就退化成全量同步。积压缓冲区是固定大小的环形缓冲，由 repl-backlog-size 控制，默认只有 1 MB，按写入速率算可能只够覆盖几秒的断线。经验做法是按“平均写入速率乘以期望容忍的断线时长”设置，几个 MB 到几十 MB 都常见。

sequenceDiagram
    participant R as 从节点
    participant M as 主节点
    R->>M: PSYNC replid offset
    alt offset 在积压缓冲区内
        M-->>R: +CONTINUE
        M->>R: 补发缺失命令
    else offset 已被覆盖或 replid 不匹配
        M-->>R: +FULLRESYNC 新 replid offset
        M->>M: BGSAVE 生成 RDB
        M->>R: 传输 RDB
        M->>R: 补发期间累积的写入
    end

Redis 4.0 起还引入了第二个复制 ID（replid2），记录上一次主节点变更前的 ID。这样在 Sentinel 完成切换后，尚未被重新配置的从节点仍有机会和新主节点做部分同步，而不是全部推倒重来。

异步复制的丢数据窗口

复制是异步的：主节点执行完写命令、回复客户端成功，之后才把命令发给从节点。从“主节点确认”到“从节点收到”之间存在一个窗口，主节点在这个窗口内宕机，这部分写入就永远丢了。窗口大小等于复制延迟，业务写得越猛、网络越差、从节点越忙，窗口越大。

WAIT numreplicas timeout 可以阻塞当前连接，直到指定数量的副本确认收到之前的写入，或者超时。它能把窗口压小，但不是强一致：返回成功只代表那一刻副本收到了，主节点随后崩溃，新主节点仍可能没有这条数据。真正的一致性需要 Raft 这类共识协议，Redis 的定位不是那个方向。

全量同步的两种传输方式

主节点生成 RDB 后，可以写到磁盘再传给从节点，也可以把字节流直接通过 socket 发出去，后者叫无盘复制。repl-diskless-sync yes 在磁盘慢或者容器里没有持久卷时很有用，省掉一次落盘和一次读盘，代价是传输期间网络中断就得从头再来；它配合 repl-diskless-sync-delay 把同时来请求的多个从节点合并到同一次传输，避免为每个从节点各 fork 一次。从节点仍然要在内存里加载 RDB，省掉的只是主节点的磁盘 I/O。

几个必须想清楚的配置

replica-read-only yes 是默认值，几乎不该改：从节点可写不会与主节点冲突，但数据会分叉，切换时不知道该信谁。

min-replicas-to-write 与 min-replicas-max-lag 是一对组合，作用是在副本都不健康时让主节点主动拒绝写入：副本全挂时业务写不进来，但也不会产生一批注定要丢的数据。主存储建议开启，纯缓存不要开。

Sentinel 与 Cluster：概览与边界

复制只解决了“数据有几份”，没解决“谁来宣布主节点死了、谁来接替”。Redis 生态里有两条路线：Sentinel 负责对主从结构做自动故障转移，Cluster 负责分片加故障转移。

Sentinel 做的事情

Sentinel 是一组独立进程，定期 ping 主从节点，按 down-after-milliseconds 判定主观下线；足够多的 Sentinel 都认为某节点下线，才升级为客观下线，这个数量就是 quorum。随后 Sentinel 之间选出领导者，由它从副本里挑数据最新的一个提升为主节点，其余副本改挂过去。

客户端不直接连 Sentinel，而是先问当前主节点地址，再连真正的 Redis；切换发生时，Sentinel 通过 +switch-master 频道发布消息，客户端收到后刷新连接。这套机制要求客户端库支持 Sentinel 协议，这是选型时要确认的第一件事。

部署有两条硬要求：数量取奇数且至少三个，分布在不同故障域；quorum 不超过总数的一半。三个 Sentinel 挂掉两个，剩下的一个既形不成多数，也完不成切换。切换耗时写进预案并在演练中测量，不要凭空写一个数字。

选举细节、failover-timeout 的各个阶段与脑裂的完整处理属于另一篇的主题，这里只强调一点：自动切换会放大异步复制丢数据的问题，min-replicas-to-write 是目前最直接的缓解手段。

Cluster 做的事情

Cluster 把数据按 16384 个槽位分片到多个主节点，每个主节点可以带副本。客户端按 key 计算槽位，算错了收到 MOVED 重定向，槽位迁移过程中还会出现 ASK 临时重定向。主节点失联且其副本获得多数主节点认可后，副本被提升，槽位随之转移。

它的约束比 Sentinel 强：多 key 命令要求 key 落在同一个槽（可用 hash tag 强制），事务与 Lua 脚本同样受限，客户端必须支持 Cluster 协议。分片、Gossip、迁移与扩容的细节留给集群专题，这里只记定位：需要横向扩容写能力时选 Cluster，只想要自动切换时 Sentinel 更简单。

恢复演练：备份只有恢复成功才算数

持久化和备份的最终验收标准只有一个：真的能从文件里把数据读回来。这一步没法靠读文档获得信心，只能靠演练。

启动时到底加载了哪个文件

启动时的加载顺序是固定的：appendonly yes 且 AOF 文件存在就加载 AOF，混合模式下先读 RDB 前导再重放尾部；否则才读 dump.rdb。两个文件都不存在，实例以空数据集启动，日志里只有一句轻描淡写的提示。

这里有个很常见的坑：原本只开 RDB 的实例，磁盘上留着几天前的 dump.rdb；某次把 appendonly 打开却没有触发重写，重启后 AOF 文件不存在，Redis 仍会回退读 RDB，看起来一切正常，实际数据停在几天前。判断依据不要靠猜，看启动日志里是 DB loaded from append only file 还是 DB loaded from disk。

flowchart TD
    A[实例启动] --> B{appendonly 是否为 yes}
    B -->|是| C{AOF 文件是否存在}
    C -->|是| D[加载 AOF, 混合模式先读 RDB 前导]
    C -->|否| E[回退读 dump.rdb]
    B -->|否| E
    E --> F{RDB 是否存在}
    F -->|是| G[加载 RDB]
    F -->|否| H[空数据集启动并打印警告]

一次完整的恢复流程

假设主节点磁盘损坏，要从昨天的备份重建，可以按下面的顺序操作，每一步都留出验证点：

  1. 确认目标时间点与 RPO 预期，避免恢复完才发现少了一天数据却没人说清。
  2. 停掉故障实例，把原数据目录整体改名保留。现场不要删，AOF 尾部有时还能抢救出最后几秒的数据。
  3. 在干净目录里放入选定的文件，并确认配置与类型匹配：放 RDB 就要确保 appendonly no，否则 Redis 会忽略它。
  4. 启动实例，检查日志里的加载来源、耗时，以及有没有 Bad file format 之类的报错。
  5. 校验数据：DBSIZE 与备份记录对比，INFO keyspace 看各库 key 数量，再抽查几个关键 key，对不上就别急着切流量。
  6. 用 DEBUG RELOAD 把当前数据集重新落盘再加载回来，提前暴露文件层面的问题。
  7. 重新挂载副本，等全量同步完成、偏移量追平，再逐步放量。

演练要演练到什么程度

建议至少每季度做一次，随机抽一份备份，在隔离环境里完整走一遍上面的流程，记录实际耗时。演练的价值不在“能不能起来”，而在暴露文档里没写的依赖：备份放在哪、谁有权限取、恢复后连接串怎么改、Sentinel 要不要重新配置。

如果用了 Sentinel，演练还要包含一次真实切换：手动 SHUTDOWN 主节点，观察切换是否在预期时间内完成、客户端是否自动重连、切换后丢了哪些写入。把“切换会丢最后若干条写入”变成团队共识，比在故障当天争论要不要接受丢失有用得多。

监控、决策矩阵与常见坑

该盯哪些指标

INFO persistence 是最直接的一屏：rdb_last_bgsave_status 与 aof_last_write_status 一旦不是 ok，说明落盘已经出问题；rdb_last_bgsave_time_sec 与 rdb_last_cow_size 反映快照成本；aof_current_size 与 aof_base_size 的比值能看出重写是否跟得上。INFO stats 里的 latest_fork_usec 是预测下一次延迟毛刺的最好依据。

复制侧看 INFO replication 的 master_link_status、master_last_io_seconds_ago，以及主从 master_repl_offset 的差值。延迟持续增大通常不是网络问题，而是从节点在跑慢命令或者磁盘在排队。

延迟本身用 latency-monitor-threshold 打开内置监控，再用 LATENCY HISTORY 与 LATENCY DOCTOR 看事件分布。它记录的是超过阈值的阻塞事件，比客户端侧的平均延迟更能定位 fork、fsync、过期键删除这类内部抖动。

一张选型矩阵

下表按业务形态给出对照，数字是设计目标，不是承诺。

业务形态 持久化 拓扑 必须配套的动作
纯缓存，可回源 可关闭，或只留 RDB 主从或 Cluster 淘汰策略、回源限流、缓存预热
会话、验证码 RDB 主从加 Sentinel 客户端支持 Sentinel、登录态可重建
计数、排行榜、队列标记 AOF everysec 或混合 主从加 Sentinel 对账任务、幂等消费、积压监控
事实上的主存储 混合持久化 Cluster 或主从加 Sentinel 异地备份、恢复演练、写入端补偿

六个反复出现的坑

  • 把复制当备份。副本上的数据是主节点写坏的、误删的，复制只会让错误多几份。
  • 主存储不开持久化。理由通常是“反正是内存数据库”，等重启后面对空实例才发现没有第二条路。
  • 忽略 fork 的内存峰值。快照期间 COW 把内存推到上限，触发 OOM Killer 杀掉 Redis。
  • 放任 AOF 增长。重写阈值调得过高，或者重写一直失败没人看，最后磁盘先满。
  • 以为切换不会丢数据。异步复制的窗口永远存在，切换只是把窗口内的写入变成永久丢失。
  • 从没做过恢复演练。文件大小正常、checksum 正常，却没人验证过它能不能加载，也没人量过恢复要多久。

小结

持久化与高可用是两道不同的题：前者用 RDB、AOF 或混合持久化把 RPO 压到业务能接受的范围，后者用复制、Sentinel、Cluster 把 RTO 压到业务能接受的范围，任何一道题都不能替另一道题作答。RDB 适合备份与冷启动，AOF 适合把丢失窗口压到秒级，混合持久化在两者之间取得工程上最实用的平衡。选型时先给数据分角色，再定持久化方式与拓扑，最后用备份、监控和定期演练把承诺变成可验证的事实。
