HTTP/1.1 与 HTTP/2 对比

HTTP/2 在 2015 年成为 RFC 7540，到 2020 年已被主流浏览器与 CDN 广泛支持，但不少团队对它的理解仍停留在“比 HTTP/1.1 快”。本文从 HTTP/1.1 的连接模型讲起，说明域名分片、资源合并为何出现，再逐项对比 HTTP/2 的分帧、多路复用、HPACK 与 Server Push，并重点讨论它没有解决的问题。读完后，读者应能判断站点是否值得迁移，以及如何确认协议版本。

一、HTTP/1.1 的连接模型

HTTP/1.1 相对 HTTP/1.0 最直接的变化，是默认启用持久连接。一个 TCP 连接可以依次承载多个请求与响应，响应通过 Content-Length 或分块传输编码划定边界。RFC 7230 将其定为默认，客户端只有显式写上 Connection: close 才关闭连接。持久连接省掉了每个资源一次握手与慢启动，是 HTTP/1.1 最重要的性能改进之一。

问题出在“依次”二字。HTTP/1.1 的响应没有请求编号，客户端只能依靠“响应顺序与请求顺序一致”来配对，服务器因此必须按序返回，前一个响应没有写完，后一个就不能开始。这条规则把并发责任推给了连接数。

管道化为什么没有普及

管道化（pipelining）本来是对上述限制的补救：客户端不必等前一个响应，就可以连续写出多个请求。但服务器仍要按序回复，只要第一个请求处理得慢，后面已发出的请求都被堵在它身后，这就是请求层面的队头阻塞（head-of-line blocking）。它没有引入乱序返回，只是把等待挪到服务端缓冲区。

工程上的阻力更大。早期代理对管道化的支持参差不齐，有的会打乱请求顺序，有的在连接复用上出错；非幂等请求失败后能否重发，语义也不清楚。多重因素叠加，浏览器最终默认关闭了管道化。

连接数上限与握手成本

既然一条连接一次只能跑一个请求，浏览器只好对同一个源多开几条连接，Chrome 与 Firefox 长期把每源并发连接数限制在 6 条左右。一个页面若有 60 个同源资源，平均要排十轮；资源都很小时，排队与协议开销反而成了主要成本。

HTTPS 让代价更高。每条新连接都要完成 TCP 三次握手，再做一次 TLS 握手，通常需要两到三个往返才能开始传数据，之后还要经历慢启动。在高延迟链路上，这些往返被放大，用户感知到的就是白屏时间变长。后续优化几乎都在围绕“少建连接、少排队、少往返”做文章。

二、为绕开限制而生的工程手段

第一类手段是域名分片（domain sharding）。既然浏览器限制的是“每个源 6 条连接”，就把静态资源分散到 static1.example.com、static2.example.com 等子域，让浏览器按源分别计数，从而成倍提高并发。这一招曾经非常有效，代价是额外的 DNS 查询、更多握手与更复杂的证书配置。分片数量也不是越多越好，通常控制在两到四个子域，否则握手成本会吃掉并发收益。

第二类是减少请求数量。把多个 CSS 或 JavaScript 文件合并成一个大文件，把小图标拼成雪碧图（CSS sprite），用 data URI 把极小图片内联进样式表，思路相同：请求本身很贵，那就少发请求。这些做法确实降低了排队轮次，但副作用同样明显。合并后的文件粒度变粗，改动一行代码就会让整个包的缓存失效；雪碧图让图标失去独立缓存，维护时还要重新计算坐标；base64 内联会让体积增大约三分之一，而且无法被单独缓存。它们是为协议缺陷付出的“税”，而非免费的优化。

三、HTTP/2 的核心机制

二进制分帧与多路复用

HTTP/2 没有改动 HTTP 的语义：方法、状态码、首部字段、缓存规则都沿用 HTTP/1.1，RFC 7540 改的是这些语义在线路上如何编码。它把报文拆成二进制帧，在 TCP 连接之上定义了一条分帧层。帧头固定为 9 个字节，包含 24 位的长度、8 位的类型、8 位的标志位，以及 1 位保留位和 31 位的流标识符。常见帧类型有 HEADERS、DATA、SETTINGS、WINDOW_UPDATE 等。

HTTP/2 用四个层次组织数据：连接、流（stream）、消息（message）和帧。一条 TCP 连接上可以同时存在多条流，每条流有独立编号，承载一次请求与响应的往返；一个消息由若干帧组成，例如 HEADERS 帧加多个 DATA 帧，最后一帧带 END_STREAM 标志表示结束。客户端发起的流使用奇数编号，服务端使用偶数编号。

flowchart TD
    C[一条 TCP 连接] --> S1[流 1 请求 index.html]
    C --> S3[流 3 请求 app.css]
    C --> S5[流 5 请求 logo.png]
    S1 --> F1[HEADERS 帧]
    S1 --> F2[DATA 帧]

关键在于，来自不同流的帧可以交错发送。接收端按流标识符重新组装，再交给上层的请求处理逻辑。流 1 的响应还在传输时，流 3 和流 5 可以插进来，HTTP 层面的队头阻塞就此消失。

多路复用还带来两个间接收益。页面通常只需对每个源建立一条连接，省掉大量握手；所有请求共享同一条连接的拥塞窗口，不必让每条新连接都从慢启动重新开始。代价是连接更“重要”：一旦出问题，上面的所有流都会受影响。

头部压缩与伪首部

HTTP/1.1 的请求头是纯文本，且每次请求都要重复发送。一个带 Cookie 与 User-Agent 的请求，头部达到几百字节很常见，而响应体可能只有几十字节。HTTP/2 用 HPACK（RFC 7541）解决这个问题，思路是“索引加压缩”。

HPACK 维护两张表。静态表有 61 个条目，把 :method: GET、:status: 200、accept-encoding 等常见字段与取值预先编号；动态表在连接内增删，记录出现过的字段组合，先进先出。编码时能查表就只发索引号，否则发字面量；字段名与值还会经过 Huffman 编码。重复请求的头部开销因此大幅下降，对 Cookie 多、请求密集的 API 尤其明显。

HTTP/2 还引入伪首部字段，如 :method、:path、:scheme、:authority，它们代替请求行，并与普通首部一起参与压缩。Connection、Keep-Alive、Transfer-Encoding 等逐跳字段则不允许出现，连接管理改由协议自身负责。

优先级与流控

优先级通过依赖树表达。每个流可以声明依赖哪个流、权重是多少（1 到 256），还可以用独占标志调整树结构，浏览器据此告诉服务器“先给 CSS，再给图片”。不过优先级只是建议，服务端可以忽略，不同实现差异很大，不应把关键路径完全押在它上面。

流控是另一套机制。HTTP/2 在连接级和流级各维护一个窗口，默认 65535 字节，接收方通过 WINDOW_UPDATE 帧补充额度。它的目的是防止一个流把接收端内存吃光，属于流量控制而非拥塞控制；真正的拥塞控制仍由 TCP 负责。两者混淆是理解 HTTP/2 性能的常见误区。

Server Push

Server Push 允许服务端在客户端请求之前，用 PUSH_PROMISE 帧预告并推送资源，例如请求 HTML 时顺便推送关键 CSS。实践却有边界：资源必须同源、可缓存，浏览器还要判断本地是否已有副本，判断不准就会浪费带宽；与缓存、Service Worker 的配合也要额外设计。因此在 2020 年，Push 更适合当作可选手段，而非“开了就一定更快”的开关。

需要提醒的是，“每源一条连接”是协议鼓励的方向，不是硬性规定；浏览器在丢包严重时仍可能对同一源建立多条连接。

五、HTTP/2 没有解决什么

最重要的一条是 TCP 层的队头阻塞。HTTP/2 的所有流共享一条 TCP 连接，而 TCP 保证字节按序交付。一旦某个报文段丢失，内核会等待重传，后续已到达的字节只能暂存在接收缓冲区，无法交给应用层，反映到 HTTP/2 上就是所有流一起停顿。连接越“粗”，影响越明显：HTTP/1.1 一条连接丢包只影响一个请求，HTTP/2 可能让几十个流同时等待。这也是 QUIC 把可靠传输搬到 UDP 之上的动机。

第二，HTTP/2 不会让服务端算得更快。多路复用解决的是“请求排不上队”，不是“请求处理得慢”。后端一个查询要两秒，十个流并发过去只会得到十个一起变慢的请求，甚至把数据库拖垮。服务端仍需限制连接级与流级的并发。

第三，它不会自动优化资源本身。未压缩的文本、没有按需加载的脚本、过大的首屏图片，换任何协议都还是慢。压缩、缓存、代码分割的价值不因 HTTP/2 而消失。至于缓冲膨胀（bufferbloat）与单个大资源，更不在它的能力范围内：前者是链路队列过长导致往返时间抖动，后者是下载几百 MB 文件时多路复用没有用武之地，收益接近于零。

六、TLS、ALPN、收益与调试

RFC 7540 定义了跑在 TLS 之上的 h2，以及明文升级的 h2c。浏览器实践中只通过 ALPN（RFC 7301）协商 h2，并要求 TLS 1.2 及以上、禁用重协商与压缩；2018 年发布的 TLS 1.3 进一步减少了握手往返。服务端在证书正确的前提下，于 ALPN 扩展中选中 h2，连接才进入 HTTP/2；协商失败则回退到 HTTP/1.1，用户通常无感。这也是“证书链不完整”经常表现为“HTTP/2 没生效”的原因：握手先失败，根本轮不到协议协商。

收益取决于负载形态，不能一概而论。资源数量多、单个资源小、往返延迟高、头部字段重的站点，收益通常明显；反过来，只有几个大文件下载、用户集中在低延迟内网、静态资源早已合并的站点，提升可能很有限。本文不给出具体百分比，因为脱离测量环境的数字不可靠，应以自己站点的真实采样为准。

调试与常见回退

开发者工具的 Network 面板有一列 Protocol，Chrome 需右键表头手动勾选。看到 h2 说明走了 HTTP/2，看到 http/1.1 就要查原因。命令行侧，curl --http2 -I https://example.com 可以看响应首行是否为 HTTP/2 200；curl -v 会打印 ALPN 协商结果，前提是 curl 编译时带了 nghttp2。压测可用 nghttp2 项目提供的 h2load，例如 h2load -n 1000 -c 10 https://example.com/，它能给出连接数、流数与每秒请求数。

回退的常见原因包括：证书链不完整或域名不匹配；链路上的代理、负载均衡器不支持 h2 或没有开启 ALPN；源站启用了 HTTP/2，但 CDN 回源仍用 HTTP/1.1；服务端与某些老模块冲突。排查时先在边缘用 openssl s_client -alpn h2 -connect example.com:443 看协商结果，再逐跳确认。

七、HTTP/3 草案与迁移

HTTP/3 与 QUIC：2020 年的草案

TCP 层队头阻塞无法在 HTTP/2 内部解决，IETF 的做法是把可靠传输整体搬到 UDP 之上，这就是 QUIC。QUIC 在用户态实现流控、重传与拥塞控制，每条流独立排序，一个流丢包不会阻塞其他流；它把 TLS 1.3 集成进握手，并支持连接迁移。HTTP/3 则是跑在 QUIC 上的 HTTP 映射。

必须强调，2020 年 HTTP/3 与 QUIC 仍处于 IETF 草案阶段，尚未成为正式标准，只有部分浏览器与 CDN 实验性开启，部署面远不能与 HTTP/2 相比。本文把它当作演进方向，而不是可以立刻替换的方案。另外，UDP 在部分企业网络中被防火墙拦截，也会让 QUIC 回退到 TCP。

迁移建议

迁移应从边缘开始：先在 CDN 或反向代理上开启 HTTP/2，保留 HTTP/1.1 作为回退，观察协议分布、首字节时间与错误率，稳定后再考虑源站。不要在开启当天就拆掉域名分片和资源合并，这些优化在 HTTP/2 下常不再必要，但拆掉会改变缓存粒度与并发形态，应先测量再逐步下线。同时留意服务端的流并发上限与单连接内存占用，避免“省连接”变成“单点过载”。

小结

HTTP/1.1 的瓶颈不在语义，而在“一条连接一次一个请求”的传输模型；管道化因顺序约束与生态兼容性未能救场，域名分片、合并与雪碧图都是为此付出的代价。HTTP/2 用分帧、多路复用与 HPACK 把并发搬进单条连接，解决了请求级队头阻塞，却没有解决 TCP 级队头阻塞、服务端处理慢与资源本身的问题。迁移应以测量为准，保留回退路径，理性看待 Server Push 与优先级，并把 HTTP/3 视为草案中的下一站。
