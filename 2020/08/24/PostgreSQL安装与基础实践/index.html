PostgreSQL 安装与基础实践

PostgreSQL 功能完整、扩展性强，但对刚接手它的后端同学来说，第一道门槛往往不是 SQL，而是安装、认证与日常运维这一整套“外围工作”。本文以 PostgreSQL 12 为例，从版本选择讲到安装、配置、权限、psql 操作、备份与监控，目标是让读者能在一台干净的 Linux 服务器上独立搭起可用的实例，并知道哪些默认值必须改。索引优化与复制细节另有专文讨论，本文只在相关处给出指向。

版本选择与安装方式

动手之前先明确版本。PostgreSQL 的版本号由主版本与次版本组成，如 12.3，12 是主版本、3 是次版本。主版本每年秋季发布一次；本文写作时 12 是当前稳定主线，社区路线图上的 13 要到 2020 年 9 月下旬才发布，因此生产环境应以 12 为准。次版本只修缺陷与安全问题，不改变目录结构，替换二进制即可完成升级。

安装方式有三种，选择取决于你对可控性的要求。

第一种是发行版自带的仓库包，例如 Ubuntu 的 postgresql、CentOS 的 postgresql-server。优点是省事、与系统集成好；缺点是版本偏旧，常见仍是 9.x 或 10，补丁节奏也跟随发行版，不由数据库团队掌握。

第二种是 PostgreSQL 官方维护的 PGDG 仓库（PostgreSQL Global Development Group）。它支持多个主版本并行安装，升级与回退都方便，是生产环境最常见的选择，本文也以它为主。

第三种是从源码编译。只有需要自定义编译选项（如特定 SSL 库、非默认安装路径）时才值得，代价是每次次版本更新都要自己重编。

还有一个易被忽略的问题：客户端与服务端的主版本要匹配。psql 一般能连接比自己新或旧一两个主版本的服务端，但 pg_dump 有条硬规则——备份工具的版本必须不低于服务端版本，用 11 的 pg_dump 导 12 的库会直接报错。建议在同一条运维链路上统一主版本，避免备份脚本到生产机才失效。

安装、初始化与首次连接

先添加 PGDG 仓库。Debian 与 Ubuntu 上需要先导入签名密钥，再写入软件源；CentOS 8 还要先禁用系统自带的 postgresql 模块，否则仓库里的包会被模块过滤掉。

包管理器会顺带创建操作系统用户 postgres、生成数据目录并注册 systemd 服务。Debian 系的数据目录在 /var/lib/postgresql/12/main，配置文件却放在 /etc/postgresql/12/main；Red Hat 系则把两者都放在 /var/lib/pgsql/12/data。这个差异在写备份脚本时很容易踩坑，动手前先确认布局。

--auth-local=peer 表示本机 Unix socket 连接使用 peer 认证，即由内核校验操作系统用户名；--auth-host=scram-sha-256 表示 TCP 连接使用 SCRAM 口令认证。这两个参数决定了初始 pg_hba.conf 的内容，比事后手改更不容易漏项。

数据目录里几个子目录值得记住：base 存放各数据库的实际文件，每个库对应一个以 OID 命名的子目录；global 存放跨库共享的系统表；pg_wal 是预写日志；pg_xact 记录事务提交状态。PG_VERSION 文件标明主版本，不要手工修改。

配置文件与客户端认证

PostgreSQL 的配置分两处：postgresql.conf 管实例行为，pg_hba.conf 管谁能从哪个地址、用什么方式连进来。前者改错通常只是行为不符预期，后者改错会直接把人锁在门外。

postgresql.conf 里有几个参数值得一开始就关注。listen_addresses 决定监听哪些网卡，默认 localhost 只允许本机连接，要让应用服务器连进来就得改成具体的内网地址，而不是图省事写 '*'。port 默认 5432，同机多实例必须改。shared_buffers 是共享缓冲池，经验值取物理内存的 25% 左右，太小造成读放大，太大会挤压操作系统页缓存。work_mem 是每个排序或哈希操作的上限而非全局内存，一个查询可能同时开好几个，要看并发而非单条语句。maintenance_work_mem 供 VACUUM、CREATE INDEX 使用，可以比 work_mem 大方。wal_level 在 12 中默认即 replica。max_connections 要结合连接池设定，盲目调到几百只会让每个连接各占一份内存。

pg_hba.conf 按顺序匹配，每条记录含连接类型、库、用户、来源与认证方法，命中第一条即生效，因此“先松后紧”会让后面的限制形同虚设。local 行对应 Unix socket，host 行对应 TCP；peer 依赖操作系统用户，md5 与 scram-sha-256 走口令认证，trust 则无条件放行。

认证方法与口令存储方式要配套。PostgreSQL 10 起支持 scram-sha-256，它比 md5 多了盐值与迭代，能抵御离线彩虹表；但 12 的 password_encryption 默认仍是 md5，即便 pg_hba.conf 写了 scram-sha-256，以 MD5 存储口令的用户仍会认证失败。正确做法是先设 password_encryption = 'scram-sha-256' 并重载，再让用户重设口令。

pg_ident.conf 处理“操作系统用户与数据库角色不同名”的映射，只有 peer、ident、gss 这类认证会用到。例如让系统账号 deploy 以 app_user 身份连库，就在其中加一行映射，并在 pg_hba.conf 对应记录里写上映射名。

改完配置要分清重载与重启。listen_addresses、port、shared_buffers、wal_level、max_connections 需要重启才生效，而 work_mem、log_min_duration_statement、password_encryption 与 pg_hba.conf 只需重载：

角色与权限管理

PostgreSQL 把用户统一抽象为“角色”，带 LOGIN 属性才等同于通常意义上的用户，不带则用于归组授权。安装时创建的 postgres 是超级用户，只留给运维与迁移，应用连接一律另建普通角色。

这里有两个容易忽略的点。第一，GRANT SELECT ON ALL TABLES 只作用于已有表，之后新建的表不会自动继承权限，必须配合 ALTER DEFAULT PRIVILEGES，否则“昨天还能查、今天新表就报权限不足”。第二，权限检查沿 search_path 展开，若应用账号的路径含 public 且 public 留有建表权限，就等于给了它凭空造对象的空间。较稳妥的做法是为应用单独建 schema，把 search_path 固定为 app, pg_catalog。

数据库属主拥有库内 schema 的创建权与对象处置权，OWNER 不要随手给业务账号；DDL 交给专门的迁移角色，应用角色只持有 SELECT/INSERT/UPDATE/DELETE 与必要的序列使用权。最小权限的实际收益在于：一旦应用被注入，攻击者拿到的也只是一个连 DROP TABLE 都做不到的账号。

psql 常用操作

psql 是随服务端一起安装的交互式客户端，元命令以反斜杠开头，与 SQL 走两套解析逻辑，因此不必加分号。日常排查掌握十来个就够用。

\l 列出所有数据库，\c appdb 切换连接，切换时可以顺带指定用户；\dn 看 schema，\dt 看当前 search_path 下的表，\d+ 表名 看字段、索引、约束与存储参数，\du 与 \dg 看角色及其属性。列太多挤成一团时，用 \x 打开纵向显示，宽表会按“字段名 | 值”逐行展开。\timing 打开后每条语句都会回报耗时，适合临时摸底，真正的分析要靠执行计划，属于另一篇文章。

\e 把上一条语句或缓冲区内容送进编辑器，保存即执行，写多行 SQL 比在提示符里挪光标舒服。\i script.sql 执行外部脚本，\copy 是客户端侧的导入导出，与 COPY 的关键差别在于它读写运行 psql 那台机器上的文件，不需要超级用户权限，也不要求文件位于服务端路径。

ON_ERROR_STOP 与 --single-transaction 在自动化场景里几乎必配：前者避免脚本报错后继续往下跑，留下半截状态；后者让整个脚本要么全成、要么全不成，代价是 CREATE INDEX CONCURRENTLY 这类语句不能在事务块内执行，要拆开处理。

写入侧最实用的是 ON CONFLICT（9.5 起）与 RETURNING：前者把“先查再插”合并成一条语句，后者让写入与读取一次往返完成：

要注意 ON CONFLICT 依赖唯一约束或唯一索引，冲突目标写错列名会直接报错；它只处理唯一性冲突，外键或 CHECK 失败仍会抛异常并中止事务。

事务用 BEGIN 与 COMMIT 包裹，出错时 ROLLBACK。PostgreSQL 基于 MVCC：更新不原地覆盖，而是写入新版本，旧版本由元组头的事务号标记为过期，读操作依据快照判断该看见哪个版本，因此读写互不阻塞。代价是旧版本要等 VACUUM 回收，长事务会拖住清理进度，表体积随之膨胀，所以不要在业务库上长期挂着不提交的事务。

备份、监控与安全基线

逻辑备份的主力是 pg_dump。默认的纯文本格式便于人读，但恢复时无法选择性重放；生产上更推荐自定义格式，它压缩、可并行恢复，也支持只恢复某些表：

pg_dump 只导一个库，角色、表空间等全局对象要靠 pg_dumpall --globals-only 单独保存，否则新机器上恢复完会发现账号全没了。pg_basebackup 复制整个数据目录，要求版本一致、布局清楚，通常作为复制与时间点恢复的起点，细节留给讲复制的文章。这里只强调两点：没做过恢复演练的备份不算备份；副本要推到另一台机器，本地放三份同样的 dump 抵御不了磁盘损坏。

监控方面，pg_stat_activity 是排查的第一站，能看每条连接的来源、状态、当前语句与等待事件；pg_locks 配合 pg_blocking_pids() 能定位锁等待的阻塞源；pg_stat_database 给出各库的事务提交与回滚数。日志里打开 log_min_duration_statement 记下慢语句。健康检查可固化成几条查询：连接数是否逼近上限、有无长事务、复制延迟、磁盘余量与最近一次备份时间。

安全基线按“网络、认证、传输、账号”四层来收。网络层只监听内网地址，用防火墙限定应用网段；认证层在 pg_hba.conf 中显式拒绝其余来源，绝不允许 trust 出现在任何一行，也不要图方便写 0.0.0.0/0 加口令认证；传输层开启 ssl = on 并配置证书；账号层为每个应用建独立角色，禁止共用 postgres。审计需求强的场景可打开 log_connections、log_statement 或用 pgaudit，但要留意日志量增长。

升级维护与常见坑

次版本升级几乎没有悬念：停服务、替换二进制、启动，数据目录不用动，PGDG 仓库下一次 apt upgrade 就能完成。主版本升级则必须走 pg_upgrade，它用新旧两套二进制分别读写各自的数据目录并搬迁系统表与用户数据，比导出再导入快得多，但仍需事先完整备份、核对扩展与排序规则，并用 --check 演练。升级前不备份，是这类操作里最不可原谅的错误。

日常维护主要围绕 VACUUM。autovacuum 默认开启并按阈值触发，但大批量删除或频繁更新的表往往需要单独调参。必要时才手工执行 VACUUM (VERBOSE, ANALYZE)，而 VACUUM FULL 会持有排他锁并重写整表，只能安排在维护窗口。扩展用 CREATE EXTENSION 安装，pg_stat_statements、pgcrypto 是常见选择，其中前者要加进 shared_preload_libraries 并重启。时间与区域设置要在建库时定好：--locale 决定排序与大小写行为，事后修改会牵动索引排序。

最后列几个新手常踩的坑。其一，部分发行版的 pg_hba.conf 默认对本机是 trust，装完就能免密进入，必须先改再上线。其二，shared_buffers 拍脑袋设成物理内存的 80%，操作系统没有余量做页缓存，整体反而更慢。其三，用 root 直接跑 psql 或 initdb，被拦下后去改属主，正确姿势始终是 sudo -u postgres。其四，改完 pg_hba.conf 忘了重载。其五，客户端与服务端编码不一致导致中文乱码，建库时统一 UTF8 可避免大半问题。其六，把 postgres 的口令写进应用配置文件，等于把整个实例交出去。

小结

PostgreSQL 的安装并不复杂，复杂的是围绕它的一圈约定：主版本要对齐，目录与配置文件位置随发行版而变，认证方式要与口令存储方式配套。配置上优先关注监听地址、共享缓冲与连接数，改动后分清哪些需要重载、哪些必须重启。权限上坚持一个应用一个角色、最小授权与 scram-sha-256 存储口令。日常靠 pg_dump 加异地副本守住数据，靠 pg_stat_activity 与慢日志守住可观测性，这些基础打牢之后再读索引与复制，才不会迷失。
