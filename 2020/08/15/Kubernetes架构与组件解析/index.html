Kubernetes 架构与组件解析

本文属于《Docker 与 Kubernetes》第 20/51 篇
上一篇系列目录下一篇

很多读者会用 kubectl 创建 Deployment，也能把服务跑起来，但一旦 Pod 一直 Pending、节点变成 NotReady，就不知道应该去看哪个组件。本文以 Kubernetes 1.18 为基准，沿着“请求如何被接收、状态存在哪里、谁来做决定、谁来执行”这条线索，把控制面与节点上的组件逐个拆开。读完本文，你应当能在脑海里画出一张组件交互图，并在故障发生时迅速定位到责任组件，而不是盲目重启。

声明式控制面与调谐循环

如果只用一句话概括 Kubernetes 与其他容器编排工具的差别，笔者会选这一句：用户只描述期望状态，系统负责把实际状态拉回来。用户提交的 YAML 不是一串“请创建容器”的命令，而是一份持续有效的声明；集群里有一批常驻进程，不断地把这份声明与现实对齐。理解这一点，后面所有组件的职责都会变得顺理成章。

这套机制通常被称为调谐循环（reconciliation loop）。它的输入有两个：期望状态，存放在 etcd 中，由用户通过 API Server 写入；实际状态，由各节点上的 kubelet 与控制器观察并上报。循环的每一步都很朴素：读取期望状态，读取实际状态，比较两者，执行动作，然后写回新的状态。写回本身又会产生新的事件，触发下一轮比较，直到两者一致，循环进入等待。

这个循环是电平触发的，而不是边沿触发的：控制器每次决策都基于当前完整的状态快照，而不是依赖“某条事件曾经发生过”。事件丢失、控制器重启、处理顺序颠倒，都不会让系统永久偏离，只要下一轮还能读到真实状态就能补上。代价是每个控制器都必须幂等，同一个动作执行多次与执行一次的结果相同，这也是为什么 Kubernetes 里几乎没有“创建一次”的语义，而是“确保存在”。

    A -->|持久化| E[(etcd)]
    E -->|watch 事件| C[kube-controller-manager]
    E -->|watch 事件| S[kube-scheduler]
    C -->|更新 status / 创建子对象| A

    A -->|watch 事件| K[kubelet]

    K -->|上报状态| A

图中还有一个容易被忽略的划分：控制面与数据面。API Server、etcd、调度器、控制器管理器决定“应该发生什么”；kubelet、运行时、kube-proxy 与网络插件让“事情真的发生”。控制面整体宕机时，已运行的 Pod 不会消失，Service 规则还在内核里，现有流量可以继续；但新的调度、扩缩容与自愈都会停摆。这既是 Kubernetes 的韧性来源，也是很多人误判故障影响范围的根源。

那么组件之间如何感知变化？答案是 list-watch。客户端先 list 拿到全量对象与 resourceVersion，再带着这个版本号 watch，服务端有变更就推送事件。kubelet、调度器与控制器都维护本地缓存，事件更新缓存后进入工作队列。版本过旧时 watch 返回 410，客户端重新 list 即可，周期性 resync 只是兜底。

API Server：所有请求的闸门

集群里几乎所有读写都要经过 kube-apiserver：kubectl 自不必说，kubelet 上报节点与 Pod 状态、kube-proxy 监听 Service 变化、调度器读取待调度 Pod、控制器写回 status，走的都是同一个入口。它对外表现为一个 REST 服务，资源路径遵循固定规律，例如 /api/v1/namespaces/default/pods 属于核心组，/apis/apps/v1/namespaces/default/deployments 属于 apps 组。group、version、resource 三级结构，最终都落在这条 URL 上。

一个请求进入 API Server 后，要依次穿过若干道关卡，顺序不能颠倒。第一道是认证，回答“你是谁”，支持客户端证书、Bearer Token、ServiceAccount 的 JWT、OpenID Connect 以及认证 webhook。第二道是鉴权，回答“你能做什么”，1.18 中默认推荐 Node,RBAC 组合：普通用户与控制器走 RBAC，kubelet 走 Node 授权器，后者只允许它读写与自己节点相关的对象。第三道是变更型准入，负责补默认值、注入 sidecar、套用 LimitRange。之后才做对象结构校验，再进入校验型准入，检查配额、PodSecurityPolicy 以及外部 webhook 定义的规则。

这套顺序有一个实际后果：被拒绝的请求在准入阶段就被挡下，不会写进 etcd，也不会产生 watch 事件；而认证失败与鉴权失败返回的状态码不同，排障时可以通过 kubectl -v=8 观察请求在哪一层被拒。RBAC 的模型很小，只有 Role、ClusterRole、RoleBinding、ClusterRoleBinding 四种对象，规则由 apiGroups、resources、verbs 三元组描述，非资源 URL 则用 nonResourceURLs 单独授权。它把“谁能改什么”集中到了 API Server 一处。

准入控制是 Kubernetes 最容易被低估的扩展点。内置插件解决的是平台自身的约束，例如 NamespaceLifecycle 阻止向正在删除的命名空间写入对象，ServiceAccount 自动为 Pod 挂载令牌，ResourceQuota 在写入前统计用量。外部 webhook 则把策略判断外移，让企业可以接入自己的合规检查。需要提醒的是，webhook 位于关键路径上，failurePolicy 设为 Fail 时，一个不可用的 webhook 会直接让整个集群无法创建对象；timeoutSeconds 也有上限，超时同样按失败处理。生产环境里给 webhook 配好副本与独立命名空间，比事后追查“为什么所有 Deployment 都创建不了”划算。

读操作的核心是 watch。客户端带上 resourceVersion 与 watch=1，服务端保持长连接，用分块的 JSON 流持续推送 ADDED、MODIFIED、DELETED 事件。为了让客户端能确认自己读到的最新版本，API Server 会周期性发送 bookmark 事件。缓存过期的客户端会收到 410 Gone，此时唯一的正确做法是重新 list，而不是重试原来的版本号。很多“控制器看起来很忙却什么都不做”的问题，根源就是客户端没有正确处理 410 而陷入无效重试。

最后是聚合层。API Server 可以把 /apis/<group>/<version> 的请求转发给外部 API Server，目标由 APIService 对象描述，metrics-server 就是这样把指标暴露给 HPA 的，认证与鉴权仍由主 API Server 统一完成。聚合层与 CRD 的区别在于，前者可以自定义存储与子资源语义，后者只是把对象存进 etcd。这也解释了为什么“所有组件都只和 API Server 说话”不是偷懒：策略、审计与事件分发只需要实现一次。

扩展的边界：CRD、Webhook 与聚合 API

Kubernetes 提供三种扩展方式，代价依次上升。最轻的是 CRD，声明一个自定义资源类型，API Server 就会为它提供增删改查与 watch，再配合一个自定义控制器读取对象、调谐外部系统，就构成了 Operator 模式。CRD 的局限是存储与语义都由 API Server 决定，无法实现自定义子资源或特殊存储。

中间一层是准入 webhook，能在对象落盘前修改或拒绝请求，适合默认值注入、标签规范与安全策略。最重的是聚合 API Server，它接管某个 API 组的全部请求，可以自定义存储、子资源与转换逻辑，metrics-server 与很多企业内部的资源抽象都走这条路，代价是要自己处理认证委托、可用性与版本兼容。

判断是否值得扩展，可以先问三个问题：原生对象加标签能否表达，控制器能否放在集群外，扩展失败会不会阻塞所有写入。三个答案都偏向否定时，再考虑写 CRD 与控制器；为了少写几个字段而引入 webhook，往往是运维负担的开始。

etcd：集群状态的事实来源

etcd 是一个分布式的键值存储，Kubernetes 只用到它很小的一部分能力：带版本号的读写、前缀扫描和 watch。对象的键遵循固定前缀，例如 Pod 存在 /registry/pods/<namespace>/<name>，Deployment 存在 /registry/deployments/<namespace>/<name>。值并不是人类可读的 YAML，而是序列化后的对象，因此直接用 etcdctl 查看通常只能看到二进制乱码；想读内容，应该通过 API Server。

写入路径决定了 etcd 的性能特征。一次写请求先追加到 Raft 日志，落盘 fsync 之后才被确认为已提交，然后应用到状态机并更新内存索引。也就是说，每一次 kubectl apply 的延迟里，都包含了一次磁盘同步的时间。这正是官方反复强调 etcd 要使用低延迟本地盘的原因：网络盘或共享云盘的 fsync 抖动，会直接表现为 API Server 的写请求变慢，进而让控制器、kubelet 的状态上报排队。读请求可以走本地状态机，压力小得多，但 watch 的建立与事件分发仍然依赖同一份数据。

Raft 要求多数派存活才能推进提交，所以成员数量必须是奇数。三个成员可以容忍一个故障，五个成员可以容忍两个，但五个成员的写延迟通常高于三个，因为 leader 需要把日志复制到更多节点。两个成员没有任何好处，反而让可用性下降。集群失去多数派时，etcd 会拒绝写入，API Server 随之只能提供读服务，这时新建 Pod、更新 Deployment 都会失败，但已有工作负载不受影响。理解这个边界，才能在“控制面挂了”时判断业务是否真的中断。

etcd 使用多版本并发控制保存键的历史版本，每次修改都会产生新的 revision。watch 正是基于 revision 实现的：客户端告诉服务端“从某个版本之后开始推送”，服务端就能精确补发期间的变化。历史版本不能无限保留，因此需要压缩（compaction），把旧 revision 之前的数据丢弃。压缩只释放逻辑空间，boltdb 文件并不会因此变小，碎片需要通过 defrag 整理，而 defrag 会阻塞该成员的读写，必须逐个成员执行并错开时间。

运维上有三件事必须形成习惯。第一是备份，使用 etcdctl snapshot save 定期导出快照，并真正演练过恢复流程；恢复时用 snapshot restore 生成新的数据目录，再以新的集群配置启动。第二是容量，后端数据库有配额限制，写满会触发 NOSPACE 告警并只允许读和删除，必须先清理或扩容并解除告警，写入才能恢复。第三是延迟，持续观察 WAL fsync 与后端提交的耗时，一旦明显劣化，先查磁盘与 IO 争用，而不是加大 API Server 的内存。

调度器：把 Pod 放到合适的节点

kube-scheduler 只做一件事：为尚未绑定节点的 Pod 选择一个节点。它 watch 到 spec.nodeName 为空的 Pod 后放入队列，取出时先做过滤（Filter），筛掉不满足硬性条件的节点，再对剩余节点打分（Score），选出得分最高者，最后通过绑定接口把决定写回 API Server。绑定不是一个普通的 Pod 更新，而是向 pods/binding 子资源发起的请求，这样可以避免与 kubelet 的状态更新互相覆盖。

过滤阶段考察的是硬约束。节点必须有足够的可分配资源，这里的可分配量是节点容量减去系统保留与驱逐阈值后的结果；Pod 的 nodeSelector 与节点标签必须匹配；nodeAffinity 的 required 规则必须满足；节点上的污点必须被 Pod 的容忍度覆盖；Pod 之间如果声明了反亲和，同一拓扑域内不能已有冲突的 Pod。任何一条不满足，节点就被排除，调度器会把原因写进 Pod 的 Condition 与事件，例如 0/3 nodes are available: 3 Insufficient cpu。这条事件是排查 Pending 的第一手材料。

打分阶段处理的是偏好。nodeAffinity 的 preferred 规则、Pod 亲和、节点资源均衡、镜像本地性都会影响得分，权重由调度器配置决定。这里有一个常见误区：打分只影响“更愿意放在哪”，不会否决节点；如果所有节点都通过了过滤，Pod 一定能被调度，只是位置未必理想。真正导致 Pod 永远 Pending 的，几乎都是过滤阶段全军覆没。

污点与容忍度值得单独强调，因为它是节点主动拒绝 Pod 的机制。NoSchedule 阻止新 Pod 调度但不管已运行的 Pod，PreferNoSchedule 只是降低得分，NoExecute 还会驱逐不容忍的现有 Pod。节点出问题时，节点控制器会自动打上 node.kubernetes.io/not-ready 或 unreachable 污点，而 Pod 默认带有对这些污点的容忍，只是容忍时间有限，超过之后才会被驱逐。很多“节点恢复后 Pod 被赶到别处”的现象，就是这套机制在起作用。

资源请求是调度的货币。调度器只看 requests，不看 limits，因此 requests 写小了会导致节点超卖，写大了会浪费容量。拓扑分布约束（TopologySpreadConstraints）在 1.18 中处于 beta，用来把 Pod 均匀分散到不同的可用区或节点上，比简单的反亲和更灵活，也是提升可用性的实用手段：把副本打散到多个故障域，单点故障才不会带走整个服务。当高优先级 Pod 无处可放时，调度器会尝试抢占低优先级 Pod 的节点，被选中的受害者会被优雅终止，但 PodDisruptionBudget 只能被参考，不能绝对阻止抢占。

从架构上看，调度器是可替换的。1.15 引入的调度框架把过程拆成 QueueSort、PreFilter、Filter、Score、Reserve、Permit、Bind 等扩展点，自定义逻辑以插件形式接入，不必 fork 整个调度器。多数团队并不需要自己写插件，但理解这些扩展点，能帮助判断一个陌生的调度行为来自哪里。

控制器管理器与云控制器

控制面里真正干活的是 kube-controller-manager，一个进程内运行着几十个控制器，共享同一套 API Server 连接与本地缓存。它们的骨架几乎一样：informer 监听某类对象，把变化的对象键丢进工作队列，worker 取出键后重新从缓存读取最新状态，计算差额并写回。注意这里传递的是键而不是对象本身，因为事件可能合并、乱序，只有重新读取才能保证决策基于最新状态。

Deployment 控制器负责版本管理。它不直接管理 Pod，而是为每个 Pod 模板计算一个哈希，创建对应版本的 ReplicaSet，并在模板变化时新建 ReplicaSet、按 maxSurge 与 maxUnavailable 调整新旧副本数。回滚之所以可行，是因为旧 ReplicaSet 被保留下来，revisionHistoryLimit 决定保留多少个。ReplicaSet 控制器则只做数量对齐：按标签选出 Pod，少则创建，多则删除，并通过 expectations 机制避免在缓存尚未更新时重复创建。

其他工作负载控制器各有侧重。StatefulSet 为每个副本分配稳定的序号与网络标识，配合 Headless Service 提供固定 DNS 名，缩容时按序号从大到小删除并保留 PVC。DaemonSet 通过节点亲和让每个节点（或符合条件的节点）运行一个副本，因此必须容忍控制面节点上的污点，否则关键代理类组件会漏装。Job 控制器统计成功完成的 Pod 数量，用 completions 与 parallelism 控制规模，用 backoffLimit 限制重试。

还有几个容易被忽视但很关键的控制器。节点控制器周期检查 kubelet 的心跳，超时后把节点标记为 NotReady 并打上污点，再等待容忍时间后驱逐其上的 Pod。Endpoints 控制器监听 Service 与 Pod，把就绪的 Pod IP 填入 Endpoints，未就绪的放入 notReadyAddresses；EndpointSlice 在 1.17 进入 beta，用分片方式缓解大集群下单对象过大的问题。ServiceAccount 控制器保证每个命名空间都有 default 账号，命名空间控制器则在删除命名空间时清理其中的所有对象。

对象之间的从属关系由 ownerReferences 表达。ReplicaSet 的 owner 是 Deployment，Pod 的 owner 是 ReplicaSet，删除时垃圾回收控制器沿着引用链处理，支持后台删除、前台删除与孤儿保留三种策略。这里有个约束：owner 与 dependent 必须同属一个命名空间，跨命名空间的引用不被认可。理解引用链，就能解释为什么删除 Deployment 会连带删掉 Pod，而直接删除 ReplicaSet 留下的 Pod 又会被新的 ReplicaSet 接管。

云厂商相关的逻辑曾经混在主控制器里，后来被拆到 cloud-controller-manager。它接管三件事：初始化节点时补充云上的元数据与标签、维护云路由、以及为 LoadBalancer 类型的 Service 创建和删除云负载均衡器。启用外部云控制器后，kube-controller-manager 以 --cloud-provider=external 启动，不再直接调用云 API。拆分的意义不只是解耦，更在于让 Kubernetes 核心不必内置每一家云的 SDK，云厂商可以独立发版。

节点侧：kubelet、kube-proxy 与三类接口

kubelet 与 Pod 生命周期

kubelet 是运行在每个节点上的代理，也是唯一能直接操作容器运行时与网络的组件。它启动后向 API Server 注册 Node 对象，随后周期性上报容量、可分配资源、Conditions 与心跳。1.17 起心跳默认通过 Lease 对象完成，Node 对象本身的状态更新频率可以更低，从而减轻大规模集群下 API Server 的写压力。

kubelet 管理的 Pod 有两个来源：API Server 上的 Pod，以及本地清单目录中的静态 Pod。静态 Pod 不经过调度器，由 kubelet 直接创建，API Server 上看到的是一个镜像对象，带有 kubernetes.io/config.mirror 注解，只能观察不能修改。kubeadm 部署的控制面组件正是以静态 Pod 形式运行，这也是为什么控制面 Pod 在 API Server 尚未就绪时就能起来。

同步循环是 kubelet 的核心。PLEG 负责发现容器状态变化，变化触发 syncLoop，syncLoop 再为每个 Pod 计算期望动作：需要新建沙箱就调用 CRI 的 RunPodSandbox，需要网络就交给 CNI 插件，镜像不存在就拉取，容器该启动就启动，该重启就重启。每一步都要把结果写回 Pod 的 status，因此 kubectl describe pod 里的容器状态、重启次数、事件，本质上都是 kubelet 观察结果的转述。

探针由 kubelet 执行，而不是容器自己判断。liveness 失败会重启容器，readiness 失败只是把 Pod 从 Endpoints 中摘除，startup 探针在 1.16 引入、1.18 进入 beta，用来保护启动慢的应用不被误杀。三种探针都支持 exec、httpGet 与 tcpSocket，参数里的 failureThreshold 与 periodSeconds 共同决定判定时间，配置不当会造成“应用还在启动就被反复重启”的典型故障。

资源观测依赖内嵌的 cAdvisor。它从 cgroup 读取容器与节点的 CPU、内存、文件系统用量，通过 Summary API 暴露给 metrics-server，后者再以聚合 API 的形式供 HPA 使用。kubelet 同时负责执行驱逐：当节点内存或磁盘触及硬阈值时，按 QoS 等级与“超出 requests 的用量”排序，依次终止 Pod；软阈值则给出一段宽限期。驱逐发生在节点本地，不经过调度器，这也是为什么节点压力大时 Pod 会莫名其妙消失，而事件里只留下 Evicted 字样。

配置同步有一个常被误解的细节。挂载为卷的 ConfigMap 与 Secret 最终会被更新，但依赖 kubelet 的定期同步，存在分钟级延迟；通过 env 注入的值永远不会更新，只能重建 Pod；使用 subPath 挂载的文件同样不会收到更新。很多“改了配置为什么没生效”的疑问，答案都在这三条里。

kube-proxy 与 Service 转发

Service 只是一个虚拟地址，真正让它工作的是每个节点上的 kube-proxy。它监听 Service 与 Endpoints，把“某个 ClusterIP 的某个端口应转发到哪些 Pod IP”翻译成节点本地的转发规则。iptables 模式下，它为每个 Service 建一条 KUBE-SVC 链，为每个后端建 KUBE-SEP 链，用 statistic 模块做随机分流；连接建立后由 conntrack 记住选择，因此同一条 TCP 连接的后续报文不会跳到别的后端。IPVS 模式把规则交给内核的 IPVS 虚拟服务器，支持轮询、最少连接等调度算法，后端数量很大时查找效率更好，是当时大规模集群常见的选项。

有一个细节常被忽略：kube-proxy 不做健康检查，它只相信 Endpoints 里的就绪状态，而就绪状态由 kubelet 的 readiness 探针决定，再由 Endpoints 控制器汇总。这条链路解释了“Pod 明明活着却不接流量”的多数原因。externalTrafficPolicy 设为 Local 时可以保留客户端源 IP，但流量只会落到本节点确有后端的 Pod 上，节点没有后端时连接会被丢弃，必须配合负载均衡器的健康检查使用。EndpointSlice 在 1.17 进入 beta，把一个大 Endpoints 对象切成多片，减少了每次变更推送给所有节点的数据量。

CNI 与 kube-proxy 是两件不同的事：前者负责给 Pod 分配 IP 并打通 Pod 之间的网络，后者只负责 Service 虚拟 IP 的转发。Pod 之间不通时查 CNI，Service 不通时查 kube-proxy 与 Endpoints，这个划分能省下大量排查时间。

CRI、CNI 与 CSI

容器运行时、网络、存储这三块能力，Kubernetes 都用接口解耦，分别是 CRI、CNI 与 CSI。CRI 是 kubelet 与运行时之间的 gRPC 接口，分为运行时服务与镜像服务；CNI 是 kubelet 经由运行时调用的网络插件规范，负责沙箱网络的创建与拆除；CSI 定义存储的挂载、附着与扩容。接口化让核心代码不必认识 Docker、Calico 或某一家存储阵列。

在 1.18 这个时间点，dockershim 仍是很多集群的默认路径：kubelet 内置一个 shim，把 CRI 请求翻译成 Docker API，再由 dockerd 调用 containerd。直接使用 containerd 的 CRI 插件则少了一层，链路更短，是当时逐渐流行的选择。需要说明的是，dockershim 此时仍是受支持的正式组件，并未被标记废弃，社区对其长期维护成本的讨论要到更晚才成为定论。

一次请求的完整生命周期

把上面这些组件串起来，最好的方式是跟踪一次 kubectl apply。客户端先做服务端发现，确认资源类型与版本，把 YAML 转换成请求体，再向 API Server 发起创建或更新。API Server 完成认证、鉴权、变更准入与校验之后，把对象写入 etcd，写成功才返回响应。此刻用户的请求已经结束，但集群的工作才刚刚开始。

    A->>E: 写入对象
    E-->>A: 提交成功
    A-->>U: 201 Created

    C->>A: 创建 ReplicaSet 与 Pod
    A-->>S: watch 到未绑定 Pod
    S->>A: 绑定到节点
    A-->>K: watch 到本节点 Pod
    K->>R: 创建沙箱与容器
    K->>A: 上报 Ready

接下来是控制器的连锁反应。Deployment 控制器发现新对象，创建 ReplicaSet；ReplicaSet 控制器发现副本数不足，创建 Pod，此时 Pod 的 spec.nodeName 为空。调度器把它取走，过滤打分之后写入绑定结果。kubelet 通过 watch 看到“分配给自己且尚未运行”的 Pod，调用运行时创建沙箱，CNI 插件为沙箱配置网络，随后拉镜像、启动容器。探针通过后，kubelet 把 Pod 标记为 Ready，Endpoints 控制器把它加入后端列表，kube-proxy 在各节点更新转发规则，流量才真正可达。

Service 的访问路径可以与之对照。客户端访问 ClusterIP，报文进入节点后被 iptables 或 IPVS 规则改写目的地址，DNAT 到某个 Pod IP，回程报文再由 conntrack 做反向转换。整个过程客户端无感知，Pod 也不知道自己被负载均衡过。正因为转发发生在内核，Service 的吞吐不依赖用户态进程，kube-proxy 只负责维护规则，不参与数据搬运。

沿着这条链路，故障定位就有了坐标系。API Server 变慢，先看 etcd 的写延迟与请求量，再看是否有 webhook 超时；Pod 一直 Pending，看调度器事件里的过滤原因，常见的是资源不足、污点不匹配、亲和规则过严或 PVC 未绑定；Pod 一直 ContainerCreating，多半卡在镜像拉取或 CNI 分配 IP；Pod Running 但不 Ready，则是探针失败或就绪门禁未通过；节点 NotReady，检查 kubelet 日志、运行时状态与磁盘压力。把“对象现在处于哪个阶段”映射到“哪个组件负责这个阶段”，比逐个重启组件有效得多。

控制面高可用

控制面的高可用可以拆成三个独立问题：状态、入口与决策权。状态指 etcd，必须部署奇数个成员，跨故障域放置，使用低延迟本地盘。成员之间靠 Raft 选举 leader，多数派存活才能写入，因此三节点集群挂掉两个、五节点挂掉三个，都会进入只读状态。把成员平均分散到两个机房并不明智，任何一边故障都可能失去多数派。

入口指 API Server。它本身无状态，可以横向扩展多个实例，前面放四层负载均衡或 VIP，kubelet 与客户端统一指向这个地址。证书的 SAN 必须包含该地址，否则客户端会报证书不匹配；用 kubeadm 搭建时通过 --control-plane-endpoint 指定，后续增加控制面节点才不用返工。

决策权指控制器管理器与调度器。它们支持多副本，但同一时刻只有一个实例真正工作，靠 Lease 对象选举 leader，其余实例待命。原因在于这些控制器并非为并发协调而设计，两个实例同时调谐会重复创建、互相覆盖。选举切换通常在十几秒内完成，期间不影响已运行的工作负载。

还有两件常被忽视的事。一是证书有效期，kubeadm 生成的工作证书默认一年到期，到期当天 API Server 会拒绝连接，必须提前续期并重启静态 Pod。二是聚合组件的可用性，metrics-server 之类的 APIService 后端不可用时，相关 API 直接报错，若被 HPA 依赖，会连带影响扩缩容。高可用的目标不是永不出错，而是让单点故障不放大为全局故障。

小结

Kubernetes 的架构可以概括为一条链路与几类角色：API Server 是唯一入口，etcd 保存期望状态，控制器负责调谐，调度器负责放置，kubelet 与运行时负责执行。理解调谐循环，就理解了组件为何能随时重启而不丢状态；理解 list-watch，就理解了状态变化如何传播。实践中建议先保证 etcd 的磁盘与多数派，再保证 API Server 的入口与证书，最后才是控制器与调度器的副本，这个顺序与故障影响面一致。
