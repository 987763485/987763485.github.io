SonarQube 代码质量平台

单元测试能覆盖某条路径，却挡不住空指针、拼接出来的 SQL 和复制粘贴的重复代码；代码评审能发现一部分，但人的注意力有限，标准也难以保持一致。SonarQube 把这些判断固化成可重复的静态分析：每次提交按同一套规则扫一遍，再由质量门禁决定这次改动能否合入。本文以 2020 年底的 8.x 版本为背景，从部署、扫描、门禁讲到规则配置、CI 接入与日常维护，读者需要会用 Docker 与 Maven 或 Gradle，读完后应能在一个真实仓库里把这条链路跑通。

SonarQube 的定位与质量模型

SonarQube 是一个自托管的代码质量平台。它不编译、不运行、也不测试被测项目，而是读取源码，按语言插件中的规则逐条匹配，把命中的位置、规则说明和修复建议写入数据库。Java 项目会额外读取字节码与测试报告，多数其他语言只看源码。一次分析结束后，我们得到的不是一堆散落的告警，而是一组可比较的指标：缺陷、漏洞、代码异味、重复率、覆盖率，以及由它们汇总出的可靠性、安全性、可维护性评级。

三个评级都用 A 到 E 表示。8.x 把问题分成 Bug、Vulnerability、Code Smell 三种类型，每种再带一个从 Info 到 Blocker 的严重级别；评级取该维度下最严重的那条问题，只要存在一个 Blocker，可靠性就是 E。这种“一票定级”很粗糙，却能让团队一眼看出代码现在能不能碰。覆盖率与重复率是独立指标：覆盖率来自外部测试报告，重复率由平台按 token 序列自行比对。

需要强调它替代不了什么。Linter 更贴近编辑器，反馈以毫秒计，规则偏重风格与局部错误；SonarQube 的价值在于跨文件、跨语言的统一规则集，以及历史趋势和门禁。二者并不冲突，实际项目里常见 ESLint、Checkstyle 继续在本地和 CI 中运行，SonarQube 在合并前做兜底。它也不是运行时安全工具：不做流量分析，不拦截攻击，报出的漏洞是对代码模式的推断，必须人工确认。

部署一个 8.x 服务

2020 年底最新的是 8.6，8.5 与它部署方式相同。官方提供 zip 包与 Docker 镜像，社区版免费并以 LGPL 发布；分支分析、合并请求装饰、组合管理等能力属于商业版，选型时应先确认自己需要哪一档，不要用社区版的预期去规划流程。

小团队最省事的是 Docker Compose：一个 PostgreSQL，一个 SonarQube，卷分开挂载。

镜像内置的 Elasticsearch 对内存映射数量有要求。Linux 宿主机要先执行 sysctl -w vm.max_map_count=262144，并写入 /etc/sysctl.d/ 持久化，否则容器会在启动几十秒后退出，日志里只留下一句关于 bootstrap checks 的报错。SonarQube 不能以 root 运行，官方镜像已处理，自建镜像时别改回去。

数据库只推荐 PostgreSQL。内嵌的 H2 仅用于评估：数据存在本地文件里，升级要清空重来。老资料里的 MySQL 方案在 8.x 已经过时，不要照抄。

日常还有两件小事：housekeeping 配置保留天数、定期清理旧快照，否则数据库迟早撑爆；账号用组和权限模板管理，分析账号只给 Execute Analysis，接 LDAP 时通过 sonar.security.realm=LDAP 与 ldap.* 参数对接，先小范围验证再全量切换。

扫描器与项目配置

SonarQube 的分析是“扫描器干活、服务端记账”。扫描器启动时先向服务端拉取当前项目生效的质量配置与规则参数，再在本地解析源码、执行规则、生成分析报告，最后通过 HTTP 提交；服务端只负责计算指标、判定门禁和保存历史，它不读源码，也不执行规则。这个分工解释了两个常见现象：扫描器版本太旧可能不认识新参数；规则更新后必须重新分析，结果才会变化。

flowchart LR
  A[Scanner 拉取质量配置] --> B[本地解析源码并执行规则]
  B --> C[提交分析报告]
  C --> D[Server 计算指标]
  D --> E[质量门禁判定]
  E --> F[CI 通过或失败]

认证用 token，而不是账号密码。登录后在个人账号的 Security 页生成，名字写清用途，明文只显示一次。8.x 里通过 sonar.login 传入，放在 CI 的密钥变量中，这个账号只需要分析权限。

质量门禁与新代码

质量门禁（Quality Gate）是一组条件的集合，分析完成后由服务端判定，结果只有通过和不通过。关键在于条件作用在哪个范围：作用在全体代码上，一个历史包袱沉重的仓库永远红着，团队很快会学会无视它；作用在新代码上，门禁只对本次改动负责，才可能长期执行。

这就是 SonarQube 反复讲的 Clean as You Code：不要求一次清理完存量，只要求新写和修改的代码是干净的，让债务不再增加，存量再按计划慢慢还。8.x 的默认门禁 Sonar way 就是这种思路，典型条件包括新代码覆盖率不低于 80%、新代码重复率不高于 3%、新代码的可靠性、安全性、可维护性评级均为 A，以及安全热点全部审阅。数值可以按团队情况调整，但方向不要变。

新代码的边界由项目设置里的 New Code 定义决定，有三种口径：上一个版本、最近若干天、参考分支。按版本适合发版节奏清晰的团队，按天数适合持续交付，参考分支则依赖分支分析能力，社区版用不了。选一种并保持稳定，频繁切换会让趋势图失去意义。

配置入口在 Quality Gates 页面：复制 Sonar way，改阈值，设为默认或只绑到某个项目。初次落地建议从宽到严：先把覆盖率定在 60%，稳定两个月再提到 80%；一上来就 80%，只会逼着大家写无意义的断言来凑数。

还有两个细节。覆盖率是导入的，测试没跑或报告路径不对，新代码覆盖率就是 0，先确认报告文件存在再怀疑规则。其次，门禁失败时应说明是哪条条件不满足，页面和 API 都能拿到这些信息，贴到合并请求里，比一句“门禁未通过”有用得多。

规则、质量配置与误报

规则按语言组织，每种语言有一份内置的 Sonar way 配置，是官方推荐的起点。8.x 已把主流语言的分析器打包进发行版，Java、JavaScript、TypeScript、Python 等开箱可用；额外插件要谨慎，第三方插件常跟不上服务端升级。

质量配置可以复制 Sonar way 后修改，也可以继承父配置，只覆盖差异。项目能单独绑定配置，适合历史项目暂时放宽。启用或停用规则会影响下次分析，已存在的问题不会消失，只是不再新产生。

严重级别值得单独说。8.x 的评级不看问题数量，只看该维度最严重的一条：一个 Blocker 就把评级拉到 E。调整规则级别等于调整它对评级的影响，比批量关闭更精细。团队应约定：改级别要写理由，且只改有争议的规则。

误报处理是平台能否被信任的分水岭。确认是误报后，在问题上标记 False Positive；确认不该修但接受风险，标记 Won’t Fix，并写清原因和负责人。两种标记都会让该问题退出评级计算，但记录仍在，审计时查得到。反过来，如果没人处理误报，开发者看到满屏假问题，就会连真问题一起忽略，这比不接入还糟。

安全热点是另一类对象：它不一定是漏洞，而是需要人判断的敏感写法，例如关闭证书校验、使用弱随机数。审阅后标记为安全或已修复，门禁里的热点审阅率才有意义。

接入 CI 与分支分析

典型流水线是：编译、跑测试并生成覆盖率报告、执行扫描、等待门禁、决定是否部署。扫描必须在测试之后，否则覆盖率没有数据；放在打包之前更合理。

让流水线因门禁失败而中断，用 sonar.qualitygate.wait=true。扫描器提交报告后会轮询服务端，直到分析处理完成并返回门禁状态，再决定退出码：

不加这个参数时，扫描器提交完就成功退出，门禁结果要回页面看，CI 永远是绿的，等于没有门禁。

分支能力要按版本区分。社区版只维护一条主分支的历史，用 sonar.branch.name 分析其他分支不会得到独立的分支视图；分支分析和合并请求装饰从 Developer Edition 起提供，会在合并请求里逐行评论新增问题。社区版有一种变通做法是给每个分支拼一个不同的 projectKey，但历史会被切成互不相干的项目，指标和门禁都失去连续性，只适合短期过渡。

Webhook 用来把结果推给外部系统：在管理页面配置回调地址，分析完成且门禁判定后触发，负载里有项目、任务和分析状态。常见用法是通知群聊、触发部署系统，或在自建平台里记录发布前的质量状态。

指标、技术债与落地路线

平台上的指标很多，真正用于排期的就几个。技术债比率是修复代码异味所需时间与开发成本的比值，SonarQube 按每行 30 分钟估算开发成本，评级 A 大致对应 5% 以内，适合看趋势而不适合当 KPI。认知复杂度把嵌套与打断线性流程的结构计入分值，比圈复杂度更贴近人的感受，适合找最该拆的函数；重复率按 token 比对，能发现被复制多遍的工具类。指标一旦成为考核目标就会被优化，空断言、为降复杂度硬拆方法、用 // NOSONAR 压告警都是常见做法，最终还是要回到“是否降低了真实风险”。

落地不要从全公司推广开始。选一个活跃、有测试基础、团队愿意配合的仓库试点：先只开默认规则，门禁只卡新代码的 Blocker 与 Critical；稳定两周后接入覆盖率，再逐步加严。试点期收集的误报与规则争议整理成团队约定，再复制到下一个仓库。

几个坑值得提前避开：生成代码、依赖目录、编译产物没有排除，一次分析能产出上万条无意义问题；覆盖率报告没生成或路径写错，门禁以“覆盖率 0”失败；条件配在全体代码上，老项目永远失败；扫描器与服务端版本差太多，会出现参数不识别或解析失败；分析历史不清理，数据库一年后会变成运维事故。归属同样重要：每条问题都该有人负责，按目录映射到团队，由提交者在合并请求阶段处理新增问题。

小结

SonarQube 是静态分析平台，既不是 linter 的替代品，也不是运行时防护。部署优先 Docker 加 PostgreSQL，把备份与升级路径当成硬约束；扫描器在本地分析，服务端负责指标、历史与门禁，token 只给分析权限。质量门禁应压在新代码上，用 Clean as You Code 控制增量，规则与误报要持续经营，指标用于排期而非考核。接入 CI 时别忘打开门禁等待，并清楚社区版在分支与 PR 上的边界。
