证书自动化：ACME 与 Let's Encrypt

手工维护 TLS 证书的日子并不遥远：申请、下载、粘贴、改配置、重启，每一步都靠人记。本文从这套流程的失效模式讲起，沿着 RFC 8555 的对象模型拆解 ACME 协议，再用 certbot 与 acme.sh 两条工具链把签发、续期、部署和监控串成一条可无人值守的流水线。读完本文，你应该能为一个多域名、含泛域名、跨多台负载均衡的站点设计出可审计的证书自动化方案，并知道它会在哪些地方出错。

从手工运维到协议：ACME 要解决的问题

证书申请本身并不复杂，复杂的是把它当作长期运行的基础设施来管理。手工流程通常是这样的：年初列一张表，记下域名、到期日、负责人；到期前两周有人想起，登录 CA 控制台，填 CSR，做域名验证，下载压缩包，解压出证书和中间证书，scp 到几台服务器，改 Nginx 配置，重启。这个流程在域名少于五个、人员稳定、机器只有两台的时候可以运转，一旦规模上去，它就会以几种非常典型的方式失效。

第一种是到期事故。日历提醒依赖某个人的邮箱和记忆，人员离职、项目交接、提醒被当作噪音忽略，都会让提醒失效。证书过期的故障形态又特别隐蔽：服务进程健康、端口通、监控的 TCP 探活全绿，只有真实用户看到浏览器的全站警告。很多团队是在客服工单涌进来之后才知道证书已经过期两天。

第二种是链不完整。CA 下发的压缩包里通常有叶子证书、中间证书，甚至根证书。有人只把叶子证书贴进配置，桌面浏览器因为缓存了中间证书或者会去抓 AIA 地址，看起来一切正常；而移动端、Java 客户端、某些 API 网关没有这些兜底手段，握手直接失败。同一份配置在不同客户端上表现不一致，排查成本极高。

第三种是版本漂移。证书被复制到十台机器，续期时只换了其中八台，剩下两台因为没重启或者被跳过，继续提供旧证书。负载均衡把请求轮流打到新旧两组后端，用户遇到的是随机出现的证书错误，复现困难。

第四种是私钥管理失控：私钥被放进代码仓库、被设置成 644、被复制到开发机。证书是公开信息，私钥才是资产，但手工流程里很少有人认真对待这一点。

传统商业证书一年一签，把人的记忆周期拉长到一年，问题被稀释，却没有消失。Let’s Encrypt 在 2015 年之后把免费证书的有效期定为 90 天，逻辑正好相反：缩短有效期可以降低吊销的压力，让泄露的证书更快自然失效，但代价是续期频率提高到每季度一次，有些团队甚至每周都在续。这样的频率下人不可能可靠，只有自动化才可行。

ACME 就是为这件事设计的协议，全称 Automatic Certificate Management Environment，2019 年 3 月发布的 RFC 8555 是它的第二个版本，也是本文讨论的唯一版本。它把“证明域名控制权”这件事协议化：客户端向 CA 提交订单，CA 下发挑战，客户端完成挑战，CA 签发证书，整个过程都是 HTTPS 上的 JSON 请求。它的价值不在于免费，而在于把签发变成可编程、可重试、可审计的 API 调用。证书链为什么必须完整、根证书与中间证书如何校验，属于 PKI 的基础理论，本文不展开；手工执行 OpenSSL 命令的细节也有专门的文章，这里只关心如何让机器替我们完成这些动作。

RFC 8555 的对象模型与 JWS 请求

理解 ACME 的第一步是分清它定义的几个对象。RFC 8555 用资源（resource）的方式组织协议，客户端拿到的不是一纸证书，而是一组有 URL、有状态、可以轮询的 JSON 文档。

生产环境与测试环境的目录地址不同，这一点后文还会反复提到：生产是 https://acme-v02.api.letsencrypt.org/directory，测试环境是 https://acme-staging-v02.api.letsencrypt.org/directory。两者协议完全一致，只是签发的证书不受信任、配额宽松。

账户（account）代表一个长期身份。客户端用账户私钥对请求签名，首次调用 newAccount 时在 JWS 的保护头里放公钥（jwk），CA 返回 201 和一个账户 URL；之后的请求改用 kid 字段引用这个 URL。这里必须强调账户密钥与证书密钥是两把完全不同的钥匙：账户密钥只用于向 CA 证明“我是同一个客户端”，证书密钥才是配置在 Web 服务器上、用于 TLS 握手的那把。账户密钥一旦泄露，攻击者可以在授权仍然有效的前提下替你申请证书，所以它和网站私钥一样需要保护。

订单（order）是一次签发请求。客户端向 newOrder POST 一个标识符列表，CA 返回订单对象，里面有 status、authorizations、finalize 和最终的 certificate 字段。每个标识符对应一个授权（authorization），授权里列出可选的挑战（challenge），每个挑战带类型、令牌（token）和状态。客户端选一个挑战，POST 一个空对象表示“我开始验证了”，然后轮询授权状态，直到变成 valid 或 invalid。

这些对象构成一条状态链：订单从 pending 开始，所有授权通过后变成 ready，客户端提交 CSR 后进入 processing，签发完成变成 valid；授权从 pending 到 valid 或 invalid；挑战从 pending 经 processing 到 valid 或 invalid。客户端本质上是一个状态机驱动器，它不需要理解密码学细节，只需要按顺序推进状态、处理错误、在超时后重试。

flowchart LR
  A[newOrder 创建订单] --> B[pending 待授权]
  B --> C[逐个完成挑战]
  C --> D{授权全部 valid}
  D -->|是| E[ready 可提交 CSR]
  D -->|否| F[invalid 订单失败]
  E --> G[finalize 提交 CSR]
  G --> H[processing 签发中]
  H --> I[valid 下载证书]

协议层还有两个容易忽略的细节。其一是 nonce：每个响应都带一个 Replay-Nonce 头，客户端下次签名必须把它放进保护头，CA 用过即废，这是防重放的核心机制。客户端应当缓存并并发获取 nonce，遇到 urn:ietf:params:acme:error:badNonce 时重试，而不是把它当成致命错误。其二是 POST-as-GET：RFC 8555 不允许用普通 GET 读取订单、授权这类资源，必须发一个 payload 为空的 JWS POST，这样请求本身也是签名的，避免了资源 URL 被第三方拿去探测。自己实现客户端时这两点最容易踩坑；用现成工具不必操心，但排错时要看懂日志里的 badNonce 与签名错误。

三种挑战类型与网络可达性

挑战是 ACME 里唯一需要“外部世界配合”的环节，也是绝大多数失败发生的地方。RFC 8555 定义了三种挑战，它们回答的是同一个问题——你能否控制这个域名——但验证的通道完全不同，因此对网络拓扑的要求也完全不同。

HTTP-01 是最常用的一种。CA 从多个网络位置发起请求，访问 http://<域名>/.well-known/acme-challenge/<token>，期望得到一段纯文本，内容是把挑战令牌和账户密钥指纹拼起来的 key authorization。客户端要做的事情很朴素：把这段文本写进网站根目录下的对应路径。用 webroot 模式时，工具只负责往指定目录写文件，Web 服务器照常提供服务。它的限制也同样朴素：80 端口必须从公网可达，域名必须解析到这台机器，中间不能有强制跳转到非标准端口、Basic 认证或者 WAF 拦截。RFC 允许 CA 跟随 301 与 302 跳转，但跳转目标仍受端口限制，跳到 8443 这类端口就会失败。另一个高频陷阱是 AAAA 记录：域名同时有 A 和 AAAA，而机器只监听了 IPv4，CA 从 IPv6 地址连过来就是 connection refused，日志里只会写一句验证失败。

DNS-01 换了一条通道：在 _acme-challenge.<域名> 下写一条 TXT 记录，值为 key authorization 的 SHA-256 摘要的 Base64URL 编码。CA 通过递归解析器查询这条记录，因此不需要站点开放任何端口，也不要求域名指向某台具体机器。它最大的优势是支持泛域名：申请 *.example.com 时，授权对象的 wildcard 字段为真，验证的是 example.com 的 _acme-challenge，而不是某个具体子域。代价是必须能改 DNS，要么手工加记录，要么把 DNS 服务商的 API 凭证交给客户端。DNS 记录的传播不是瞬时的，客户端必须等待权威服务器返回新值再触发验证，这段等待时间是 DNS-01 最主要的失败来源。

TLS-ALPN-01 最少见。客户端在 443 端口上临时起一个 TLS 服务，ALPN 只协商 acme-tls/1，返回一张带特殊扩展的自签证书，扩展里放着 key authorization 的摘要，CA 完成握手即视为验证通过。它适合 80 端口被封、又不方便改 DNS 的环境，但要求客户端独占 443，Nginx 正在运行时无法使用，工具链的支持也最弱。

挑战类型 验证通道 泛域名 端口要求 典型场景
HTTP-01 80 端口 HTTP 请求 不支持 80 入站 单域名站点、webroot
DNS-01 _acme-challenge TXT 支持 无 泛域名、内网源站、无公网 80
TLS-ALPN-01 443 端口 TLS 握手 不支持 443 独占 只有 443 的环境

选择挑战类型时，先问三个问题：证书里要不要泛域名，源站能不能被公网访问，DNS 能不能通过 API 修改。要泛域名就只能选 DNS-01；源站藏在 CDN 或内网后面，HTTP-01 往往也不可行；两者都受限时，DNS-01 的 CNAME 委派是常用出路，后文会专门讲。还有一个容易被忽视的细节：泛域名证书只覆盖一级子域，*.example.com 既不覆盖 example.com 本身，也不覆盖 a.b.example.com，申请时通常要同时写上根域。

Let’s Encrypt 的配额、staging 与 90 天生命周期

Let’s Encrypt 是 ACME 协议最广泛的应用，也是很多人唯一接触过的 CA。它的服务条款、配额和证书策略直接决定了自动化方案的设计，必须在动手之前弄清楚。

第一是速率限制。它按类别设置，而不是一个总数：每个注册域名每周可签发的证书数量有上限（长期公开的数字是 50），这里的“注册域名”指 example.com 这一级，所有子域共享同一份额度；完全相同的域名集合重复签发有单独的配额（每周 5 张），所以反复调试同一张证书会很快撞墙；验证失败按账户、按主机名、按小时计数，失败的尝试同样消耗配额；账户创建按来源 IP 限制；订单创建也有按账户的速率约束。配额的设计意图是防止滥用，而不是惩罚正常使用，绝大多数事故来自“调试时反复重试”和“脚本把同一组域名签了十几遍”。遇到 too many certificates already issued 或 too many failed authorizations recently 时，正确的反应是停下查原因，而不是换台机器继续试。

第二是测试环境。Let’s Encrypt 提供一套完全独立的 staging 端点，协议行为与生产一致，配额宽松得多，签发的证书由一张不受信任的测试根签发。它的用途只有一个：验证自动化流程本身是否走得通。所有上线前联调都应指向 staging，生产配置必须确认没有残留 staging 地址。certbot 的 --dry-run 就是自动切到 staging 跑一遍完整流程，这个参数应当成为每次修改续期配置后的固定动作。

第三是有效期。2020 年时 Let’s Encrypt 证书的有效期是 90 天，官方建议在剩余约 30 天时续期，而不是按固定日历周期。90 天意味着一年至少四次续期，任何一次失败都必须在下一个 30 天窗口内被发现，这也解释了为什么监控是方案的一部分而不是可选项。

第四是证书透明。Let’s Encrypt 会把签发的每一张证书提交到 CT 日志，证书因此进入公开可查的账本。这对审计是好事，对内部域名则是坏事：任何拿到日志的人都能枚举你签发过哪些域名。所以测试域名、内部系统域名不应使用公共 CA，这不是技术限制，而是信息暴露问题。

最后是服务条款。首次注册账户时需要同意当时的用户协议，客户端会把这个动作做成一个显式参数。自动化脚本里应当显式接受条款；无人值守的 cron 任务最怕遇到等待输入的提示符。

--manual 完全靠人完成挑战，默认交互式地让你去 DNS 添加记录。它可以配合 --manual-auth-hook 与 --manual-cleanup-hook 调用外部脚本，从而间接实现自动化，但证书续期时仍然要求这些钩子可靠执行，否则就会卡住。把纯 --manual 放进 cron 是一个典型的反模式，后文还会展开。

部署：链文件、权限与原子替换

签发成功只是完成了一半，证书要真正生效，还得经过“放到正确路径、给对权限、让进程重新加载”这三步。每一步都有坑，而且坑的表现形式都是“看起来成功了”。

先看文件。certbot 在 /etc/letsencrypt/live/<证书名>/ 下提供四个符号链接：cert.pem 是叶子证书，chain.pem 是中间证书，fullchain.pem 是两者拼接，privkey.pem 是私钥。Web 服务器应当使用 fullchain.pem 与 privkey.pem，而不是 cert.pem。链文件的顺序必须是叶子在前、中间在后，顺序反了，部分客户端会直接握手失败；根证书通常不需要也不应该放进链里，客户端本地已有信任锚。

改完配置先做语法检查再重载。Nginx 的 reload 是平滑的，旧 worker 会把手上的连接处理完再退出，不会中断请求：

不要用 restart 代替 reload。restart 会断开监听套接字，在流量高峰表现为一批连接被重置；而 reload 只是在主进程里重新读配置、拉起新 worker。

再看权限。/etc/letsencrypt/live 与 archive 的目录权限是 700，属主是 root，privkey.pem 是 600。这意味着只有 root 能读私钥，Web 服务器主进程以 root 启动、再降权到 worker，所以能读到；但如果你把证书路径指向一个由普通用户运行的服务，就会遇到 permission denied。正确做法不是把私钥改成 644，而是让部署脚本用 root 把文件复制到服务专用目录，属主设为服务账号，权限 600。HAProxy 这类需要把证书和私钥合并成一个文件的场景，尤其要注意复制后的属主，否则 reload 时才会报错。

最后是原子替换。部署脚本的典型错误是“先删旧文件、再拷新文件”，中间有一个窗口期文件不存在，此时 reload 必然失败，服务可能带着旧配置继续跑或者直接起不来。正确顺序是：在同一文件系统内写临时文件、设好权限、用 mv 覆盖（同一文件系统内的 rename 是原子的），最后 reload。certbot 自己的 live/ 符号链接切换就是原子操作，所以直接引用 live/ 路径通常比自己复制更安全。

多服务场景要把“部署”抽象成一份服务清单，逐个重载并逐个校验。Nginx、HAProxy、API 网关读取证书的方式不同，但流程一致：复制、检查配置、重载、探测。任何一个服务失败，都应当停止后续步骤并告警，而不是继续把错误扩散到全部节点。重载后的健康检查不要只看进程状态，要用真实握手验证：openssl s_client -connect 127.0.0.1:443 -servername example.com 看返回的证书主题与有效期，或者用 curl --resolve example.com:443:127.0.0.1 https://example.com/ 确认证书链能被正常校验。只有握手通过，才算部署成功；失败则恢复上一份文件、再次 reload，并保留现场日志。

参考架构与故障排查

把前面几节拼起来，一个可运维的证书自动化架构包含四段：管理主机上的客户端与定时任务、CA 的 ACME 端点、验证通道（80 端口或 DNS API）、以及证书落盘后的分发与重载。管理主机不必是 Web 服务器，它可以只负责签发和分发，这样证书的生命周期与业务机器的扩缩容解耦。

flowchart TD
  A[管理主机 cron/timer] --> B[certbot 或 acme.sh]
  B --> C[ACME 目录与账户]
  C --> D{验证通道}
  D -->|HTTP-01| E[站点 80 端口]
  D -->|DNS-01| F[DNS API 写入 TXT]
  E --> G[CA 校验域名控制权]
  F --> G
  G --> H[签发证书]
  H --> I[证书存储 live/ 或 ssl/]
  I --> J[部署脚本: 原子替换]
  J --> K[Nginx]
  J --> L[HAProxy]
  J --> M[API 网关]
  I --> N[外部到期探测]
  K --> O[握手健康检查]
  L --> O
  M --> O
  O -->|失败| P[回滚并告警]

续期流程的失败处理要分层次。签发失败时，旧证书还在，服务不受影响，此时应当重试有限次数后告警，绝不能在脚本里删掉现有证书“重新来过”。部署失败时，同样保留旧文件，重载失败就不要继续操作其他节点。监控失败时，不要自动重签，因为重签很可能撞上速率限制，正确的动作是通知人。把“能自动修复的”和“必须人判断的”分开，是这套架构能不能长期稳定运行的关键。

排错时按“挑战类型、错误码、发生位置”三条线索定位，比盲目重试有效得多。下表列出最常见的几类现象：

现象 常见原因 检查手段
HTTP-01 返回 404 webroot 路径与站点根不一致；重写规则拦截 .well-known；文件权限不可读 手工在站点根放测试文件，用公网地址访问同一路径
HTTP-01 连接被拒或超时 安全组未放行 80；AAAA 记录指向未监听的主机；CDN 回源未配置 从外部网络 curl -v http://域名/.well-known/acme-challenge/测试值，并检查 A/AAAA
DNS-01 提示记录不正确 传播未完成；写到了错误的 zone；存在多条冲突 TXT dig +short TXT _acme-challenge.域名 @权威服务器，确认权威侧已生效

监控要覆盖三个层面。最外层是外部探测：从公网定期连接 443，读取证书的 notAfter，在剩余 30 天、14 天、7 天分别升级告警级别。这一层不依赖任何内部脚本是否跑成功，是最可靠的兜底。中间层是续期任务本身：检查 cron 或 timer 是否执行、退出码是否为零、日志里有没有 failed 与 error。最内层是部署结果：握手探测、证书指纹是否变化、链是否完整。三层都绿，才能说这条流水线是健康的。

值得单独提的是证书透明监控。既然证书会进入 CT 日志，就可以反过来利用它：定期查询 CT 日志中出现的自家域名，如果发现一张自己没申请过的证书，说明有人可能通过其他途径完成了域名验证，这属于安全事件而不是运维故障。同样地，内部域名出现在公共 CT 日志里，也应当被当作信息泄露来处理。

安全边界上有几条硬规则。账户私钥与证书私钥都按敏感文件对待，目录 700、私钥 600、属主专用账号；DNS API 令牌限定到单个 zone、只给 DNS 编辑权限，并且不落进 shell 历史（用环境变量文件或密钥管理服务注入）；不要在无人值守的任务里使用交互式 --manual，它会在等待输入时挂起，把一次普通续期拖成到期事故；部署钩子只做复制与重载，不在里面执行来源不明的脚本。最后定期审计续期日志与钩子内容，确认没人留下 --staging 或跳过验证的临时改动。

小结

证书自动化的核心不是某个命令，而是一条从签发、验证、落盘、部署到监控的闭环，任何一环缺失都会在 90 天的周期里暴露出来。理解 ACME 的账户、订单、授权与挑战模型，才能在工具报错时判断问题出在协议层还是网络层。选型上，单机小站点用 certbot 的 webroot 加 timer 最省事，跨云、多域名、要泛域名时 acme.sh 配合 DNS API 更灵活，但无论选哪个，都要用 staging 演练、用原子替换部署、用外部探测兜底。把“续期成功但没重载”和“只部署叶子证书”这两个最常见的坑堵住，证书这件事基本就不会再半夜叫醒你。
