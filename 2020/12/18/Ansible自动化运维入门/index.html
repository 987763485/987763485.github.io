Ansible 自动化运维入门

第一次接触配置管理，很容易被 Puppet 的 manifest、Chef 的 cookbook、Salt 的 master 与 minion 绕晕。Ansible 的思路恰好相反：目标机上什么都不用装，只要有 SSH 和 Python，就能从一台控制机把配置推过去。本文从无代理模型讲起，依次说明 inventory、ad-hoc、playbook、变量与 facts、循环模板、role，最后落到幂等、密钥和灰度发布。读者需要会用 ssh 和基本的 Linux 命令，不需要任何 Ansible 经验。

为什么 Ansible 不需要 Agent

配置管理工具的谱系里，Puppet 和 Chef 走的是拉取模型：每台机器装一个 agent，定期向 master 拉配置并上报状态，Salt 的 minion 也类似。这套结构适合几千台机器的规模，代价是每台机器都要先完成 agent 安装、证书签发和版本对齐，而这恰恰是运维最不愿意重复的体力活。

Ansible 反过来做。控制机装一份 Ansible，通过 SSH 连到目标机，把模块代码临时拷过去，用目标机上的 Python 执行，再把 JSON 结果收回来。目标机不需要常驻进程，不需要开放 22 之外的端口，也不需要跟着 Ansible 升级而升级。一条 ssh 能通，Ansible 就能管；撤销同样干净，删掉控制机上的目录即可。

flowchart LR
  A[控制机 ansible-playbook] -->|SSH| B[web01]
  A -->|SSH| C[web02]
  A -->|SSH| D[db01]
  B --> E[执行模块并返回 JSON]
  C --> E
  D --> E

这套“推送 + 无代理”的模型决定了使用方式：目标机先登记进 inventory（清单），inventory 是唯一事实源，哪台机器属于哪个组、用什么账号登录、有哪些变量，都写在里面；之后所有操作都以 inventory 为起点从控制机推下去。临时动作用 ad-hoc 命令，成体系的操作用 playbook。即便机器上跑的是容器，装 Docker、写 daemon.json、挂数据盘这些主机层的事仍然要逐台落地，Ansible 管的正是这一层。

无代理也不是没有代价。每个任务都要建立 SSH 连接，Ansible 默认开启连接复用（ControlPersist）来摊薄开销，但几百台以上时并发数、连接数和单机 fork 仍会成为瓶颈，这时要么调大 forks，要么按组分批。Windows 目标要走 WinRM，网络设备走对应的 collection 或连接插件，这些边界在选型时就该想清楚。

安装、配置与 inventory

2020 年底有两条并行的版本线。2.9 是最后一个“大而全”的版本，模块全打在同一个包里；2.10 把模块拆进 collections，核心交给 ansible-base，pip install ansible 装到的是社区合集。两者在本文涉及的用法上一致，存量环境跑 2.9 的更多，新项目可以直接上 2.10。

控制机需要 Python 2.7 或 3.5 以上。安装有两种常见方式：发行版仓库，EPEL 里的 ansible 包通常是 2.9；或者用 pip 装到用户目录，版本更可控。装完先看 ansible --version，输出里会列出生效的配置文件路径，排查“为什么配置没生效”时这一行最有用。

Ansible 按固定顺序查找配置：环境变量 ANSIBLE_CONFIG、当前目录的 ansible.cfg、家目录的 ~/.ansible.cfg、最后是 /etc/ansible/ansible.cfg。推荐把 ansible.cfg 和 inventory 一起放进项目仓库，在项目根目录执行命令，配置就天然生效。

host_key_checking = False 只适合内网首次批量接入，正式环境应把主机指纹维护进 known_hosts；interpreter_python = auto_silent 让 Ansible 自己找可用的解释器，省掉目标机上没有 /usr/bin/python 的报错。

连接依赖 SSH 密钥。控制机上 ssh-keygen -t ed25519 生成密钥，ssh-copy-id deploy@web01 把公钥送到目标机，之后 ansible all -m ping 能通就说明链路没问题。检查清单解析结果用 ansible-inventory --graph，它会按组把主机树打印出来，比翻 INI 快得多。日常操作大多需要 root，但不要直接用 root 登录：用普通账号登录，在 playbook 里写 become: true（命令行是 -b），必要时用 --ask-become-pass 输入 sudo 密码，或者在 sudoers 里给这个账号配置免密执行。

从 ad-hoc 到 playbook

ad-hoc：一次执行一个模块

装好之后第一件事是连通性检查。ansible all -m ping 里的 ping 不是 ICMP，而是 Ansible 的 ping 模块：它验证 SSH 能登录、目标机的 Python 能执行，返回 pong 才算真的通。

ad-hoc 的本质是“一次执行一个模块”，格式为 ansible <主机模式> -m <模块> -a <参数>：

command 不经过 shell，管道、重定向、通配符都不生效，需要这些特性时才用 shell。--limit web01 把范围收窄到单台；--check 只报告将要做什么，--diff 顺带打印文件差异，两者搭配是改动前的第一道保险。

ad-hoc 适合查状态、临时重启、批量拷一个文件这类几句话能说清的事。输出是逐台的，失败主机会在末尾单独列出，加 -o 可以压成一行一台，巡检时扫一眼就够。一旦出现“先装包、再改配置、最后重启”这种有顺序的步骤，或者需要反复执行、需要别人也能复现，就该写 playbook：ad-hoc 没有先后保证，也无法把变更结果串起来。

playbook：把步骤写成文件

Playbook 是 YAML 文件，顶层是一个列表，每个元素称为一个 play，描述“在哪批主机上、以什么身份、按什么顺序做哪些事”。play 里的 tasks 也是列表，每个任务至少要有 name 和一个模块。下面的例子在 web 组上装 Nginx、下发站点配置，并保证服务处于运行状态：

执行命令是 ansible-playbook -i inventories/prod/hosts.ini site.yml。末尾的汇总行会给出 ok、changed、unreachable、failed 四个计数，判断一次执行是否正常，看 changed 和 failed 就够了。

变量、facts 与条件判断

变量有三种常见来源。写在 play 里的 vars 只作用于当前 play；放在 inventory 同级的 group_vars/ 和 host_vars/ 目录里，会按组名或主机名自动加载，适合按环境区分的配置；命令行传入的 -e 优先级最高，适合临时覆盖。

优先级记一条经验就够：越具体越优先，命令行最高。role 的 defaults 最低，可被任何来源覆盖；inventory 的组变量低于主机变量；play 的 vars 又高于 inventory；-e 压过一切。实践中把“可调参数”放进 defaults，把“环境差异”放进 group_vars，很少需要和优先级搏斗。

facts 是 Ansible 自动采集的目标机信息，包括发行版、内核、CPU 数、内存、网卡和挂载点。单独查看用 ansible web -m setup -a "filter=ansible_distribution*"；在模板和 when 里通过 ansible_facts 字典访问，2.10 推荐 ansible_facts['distribution'] 这种写法，旧的 ansible_distribution 仍可用，但属于兼容层。

变量不生效时，先别急着改 playbook，在任务里加一个 debug: var=site_name 把值打出来；想看目标机上报了哪些 facts，用 ansible web -m setup -a "filter=ansible_os_family" 单独查一台。如果发现值不是预期的那份，多半是优先级问题——比如同名变量同时写在 group_vars/all.yml 和 play 的 vars 里，后者会赢。set_fact 则在运行时给主机挂一个新变量，作用范围限于当前这次执行，适合存放“前一步查出来的结果”，不要拿它当持久配置。

过滤器写在变量后面：default 处理变量未定义的情况，join 把列表拼成字符串，upper、int、length 各管一摊。一个常见的组合是 {{ upstreams | default(['127.0.0.1:8080']) | join(' ') }}，既能给默认值，又能适配不同长度的列表。

2.10 引入的 collections 把 role 和模块一起打包，解决了模块命名冲突和分发问题。ansible-galaxy collection install community.general 安装，requirements.yml 固化版本，调用时写全限定名如 community.general.ufw。2.10 的 ansible 包已经内置了一批常用 collection，从 2.9 升级时大部分 playbook 不用改。

role 之间也有依赖关系，写在 meta/main.yml 的 dependencies 里，执行时会先跑被依赖的 role，且同一个 role 只跑一次。跨项目复用时，把 role 推到 git 仓库，在 requirements.yml 里写清 src 和 version，一条 ansible-galaxy install -r requirements.yml -p roles/ 就能把依赖装齐，比复制粘贴目录可靠得多。

幂等性、密钥与上线纪律

幂等性

幂等指同一个 playbook 执行一次和执行十次，最终状态一致，且第二次开始不再产生变更。Ansible 的模块大多按“声明目标状态”设计：service: state=started 在服务已运行时返回 ok，file: state=directory 在目录已存在时什么都不做。shell 和 command 是例外，它们只负责执行，永远返回 changed。

所以能用模块就别用 shell。确实要跑脚本时，用 creates、removes 给它加一个判断条件：

只读命令用 changed_when: false 声明“它不会改变系统”，预期内的失败用 failed_when 兜住，避免把正常的返回码当成故障。--check 能提前看到变更，但它有边界：command、shell 在检查模式下默认跳过，不支持检查模式的模块会显示 skipped，所以 --check 通过不等于真实执行一定安全。

几个常见的替换关系值得记住：shell: useradd -m deploy 第二次执行会报用户已存在，改成 user: name=deploy state=present 就自然幂等；mkdir -p 换成 file: state=directory，sed -i 换成 lineinfile 或 template。也有例外，service: state=restarted 每次都会真的重启，需要“仅在配置变更时重启”时，正确做法是让配置任务 notify 一个 reload handler，而不是把重启写死在任务列表里。

验证幂等性的方法很朴素：连续跑两次，第二次的 changed 应该是 0。这条可以写进发布检查单。

加固与灰度

下面这段是日常最典型的用途：改 sshd_config、下发 Nginx 主配置、按需重启服务，全部带上校验和回滚点。

改动生产前，先 --check --diff 看一遍将要发生什么，再用 --limit web01 拿一台机器试水。批量更新用 serial 分片，serial: 1 逐台、serial: 25% 按比例，配合 any_errors_fatal: true，一台失败就整体停下，不要带着一半新一半旧继续跑。

ansible.cfg 里打开 log_path，每次执行的输出留档；playbook 和 inventory 全部进版本库；提交前跑一遍 ansible-lint，它能发现“该用模块却用了 shell”“任务没有 name”这类问题。copy、template、lineinfile 都支持 backup: true，改动前留一份带时间戳的副本，出问题时不必靠记忆回滚。

最后列几个最常见的坑：把 shell 当万能工具，playbook 越写越不可重复；密码写在 group_vars 里跟着仓库一起泄露；不管需不需要都 become: true；跳过 --check 直接上生产；inventory 长期不更新，机器下线了清单里还在；改了任务却没触发 handler，服务仍在跑旧配置；目标机只有 Python 3 而 inventory 里还写着 /usr/bin/python。这些问题的共同点是几分钟内就能发现，代价却往往是一次线上事故。

小结

Ansible 的价值不在功能多，而在入口低：一台控制机、一份 inventory、一条 SSH 通道，就能把几百台机器的配置收敛到同一状态。本文从无代理模型讲起，覆盖了 inventory、ad-hoc、playbook、变量与 facts、循环模板、role 与 collection，最后落到幂等、vault 和灰度发布。学完这些，装包、改配置、重启服务已经可以全部脚本化。下一步值得投入的是把常用配置沉淀成 role，并把 --check、serial、vault 变成团队的默认动作，而不是出事之后才想起的补救手段。
