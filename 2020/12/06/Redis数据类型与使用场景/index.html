Redis 数据类型与使用场景

很多团队把 Redis 当作一个简单的键值缓存，只用到 GET 和 SET，遇到排队、排行榜、去重、计数时又去引入新的组件。本文从 Redis 的基础类型与扩展类型出发，说明每种结构的语义、常用命令、适用场景和边界，并结合 2020 年的 Redis 6.0 给出选型建议。读完本文，你应该能为一个具体需求挑出合适的数据结构，并避开几个最常见的误用。

Redis 不只是缓存：单线程与命令复杂度

很多人第一次接触 Redis 是从 SET 和 GET 开始的，于是把它理解成一个放在内存里的哈希表。这个印象只对了一半。Redis 官方把自己定位为数据结构服务器（data structure server）：除了字符串，它还提供列表、哈希、集合、有序集合、位图、HyperLogLog、Stream 和地理索引。每一种结构都对应一组原子命令，客户端不必把整个值取回本地再计算，就能在服务端完成追加、计数、求交集、按分数排序等操作。理解这一点，是从“会用缓存”走向“会做建模”的分水岭。

版本方面，本文以 2020 年 5 月正式发布的 Redis 6.0 为基准。6.0 引入了多线程 I/O，但默认关闭，而且多线程只负责网络读写，命令执行仍然由单线程串行完成。

单线程带来两个直接后果。第一，所有命令排队执行，一条慢命令会阻塞后面所有请求，所以命令的时间复杂度不是学术问题，而是线上延迟问题。第二，既然没有锁竞争，单条命令天然原子，INCR、SADD、ZADD 这类操作不需要额外加锁；但多条命令组合出的逻辑并不原子，需要 Lua 脚本或事务来保证。

flowchart LR
    A[客户端命令] --> B[连接读取]
    B --> C[命令队列]
    C --> D[单线程执行]
    D --> E[返回结果]

因此，看到 KEYS *、对百万元素的集合执行 SMEMBERS、或者直接 DEL 一个存了几十万字段的哈希时，要先算一算这条命令要跑多久。后文在介绍每种类型时，都会标注关键命令的复杂度，并在最后集中讨论大 key 的发现与拆分。

String：计数器、锁与位操作

String 是唯一一种可以被其他结构复用的底层类型，也是使用率最高的类型。它的值按字节存储，是二进制安全的，因此可以放 JSON、序列化后的对象、图片缩略图，单个值上限 512 MB。常见命令是 SET、GET、MSET、MGET、APPEND、STRLEN，复杂度都是 O(1)（MGET 为 O(N)，N 是 key 个数）。

计数器是最典型的用法。INCR、INCRBY、DECRBY 把值当作 64 位有符号整数做原子加减，文章阅读数、接口调用量、库存扣减都能直接映射。值必须是整数格式，否则报错，这也意味着不要用字符串拼接的方式去改计数。

分布式锁依赖的是 SET 的扩展参数。SET key value NX EX seconds 把“不存在才设置”和“设置过期时间”合并成一条原子命令，避免了 SETNX 之后再 EXPIRE 之间进程崩溃导致死锁。值建议使用随机 token，释放时用 Lua 比对 token 再删除，防止误删别人的锁。

GETRANGE 和 SETRANGE 按字节下标读写片段，适合存放定长编码的数据。位操作 SETBIT、GETBIT、BITCOUNT、BITOP 则把一个 String 当成 bit 数组，第五节会展开。

使用场景可以归纳为五类：缓存序列化后的对象（整存整取）、会话数据、计数器、分布式锁的持有标记，以及以位图形式存在的布尔状态。需要注意，String 存 JSON 时每次更新都要读出、反序列化、改字段、再写回，字段多且更新频繁时应考虑 Hash。

List 与 Hash：队列、时间线与对象存储

List 是按插入顺序排列的字符串序列，底层在 6.0 中是 quicklist，即由多个 ziplist 节点串成的双向链表。这个结构决定了两端操作快、按下标随机访问慢：LPUSH、RPUSH、LPOP、RPOP 都是 O(1)，LINDEX、LRANGE 是 O(N)，其中 N 是从表头走到起始下标的步数加上返回元素个数。

用两端的不同组合，可以得到两种语义。LPUSH 加 RPOP 是先进先出的队列，LPUSH 加 LPOP 是后进先出的栈。消费者侧通常用阻塞版本 BRPOP key timeout，timeout 为 0 表示一直等到有数据，比轮询节省连接和 CPU。阻塞命令会占住一个连接，连接池要留出余量。

时间线是另一个常见用法：写入时 LPUSH 最新动态，再用 LTRIM 只保留最近若干条，读取时 LRANGE key 0 9 取第一页。这样列表长度有上界，内存可控。反过来，如果没有 LTRIM，列表会无限增长，这是 List 最常见的生产事故。

还要清楚 List 作为队列的局限：它没有确认机制，RPOP 之后消费者崩溃，消息就丢了，也没有消费组。对可靠性有要求时应使用 Stream。

Hash 是字段到值的映射，适合表达对象。HSET、HGET、HDEL、HINCRBY 都是 O(1)，HMGET 一次取多个字段，HGETALL 是 O(N)。字段很多时不要用 HGETALL 全量拉取，用 HSCAN 游标分批遍历。

Hash 相对 JSON 字符串的优势在于部分更新与部分读取：改一个字段只发一条 HSET，不必把整个对象读回应用层。字段数量少时，Hash 使用 ziplist 编码，内存比每个字段单独存一个 String 更省。Redis 6.0 的默认阈值是 hash-max-ziplist-entries 128、hash-max-ziplist-value 64，超过后转为 hashtable，内存会明显上升。

Hash 的坑在于巨型哈希：把所有用户塞进一个 key，几十万字段之后，HGETALL 会阻塞主线程，过期时间只能加在整个 key 上，无法按字段淘汰。合理做法是按业务或 ID 区间分桶，例如 user:bucket:07。

Set 与 Sorted Set：去重、关系与排行榜

Set 是无序且元素唯一的字符串集合。SADD、SREM、SISMEMBER、SCARD 都是 O(1)，SMEMBERS 是 O(N)。集合运算 SINTER、SUNION、SDIFF 分别是交集、并集、差集，结果很大时可以用带 STORE 的版本写回另一个 key，避免把大结果传到客户端。

SRANDMEMBER 和 SPOP 都用于随机取元素，区别是前者不删除、后者删除。SRANDMEMBER key count 的 count 为正数时返回不重复元素，为负数时允许重复，这个细节在抽奖场景里很有用。

典型场景有四类：标签系统（一个标签一个 Set，交集求共同标签）、去重（SADD 返回 1 表示新增、0 表示已存在）、关系集合（关注列表、共同关注）、抽奖（SPOP 保证不重复中奖）。当元素全是整数且数量不大时，Set 使用 intset 编码，内存非常紧凑，默认上限是 set-max-intset-entries 512。

Sorted Set 在 Set 的基础上给每个元素绑定一个分数，按分数排序，元素仍然唯一。ZADD、ZINCRBY 是 O(log N)，ZRANGEBYSCORE、ZREVRANGE 是 O(log N + M)，ZRANK、ZREVRANK 是 O(log N)。底层是跳表加字典：字典保证按成员查分数是 O(1)，跳表保证按分数范围查询和排名是对数级。

排行榜是最直观的用法。延迟队列则把执行时间戳当分数，到期任务用 ZRANGEBYSCORE key 0 now LIMIT 0 1 取出，取到后必须删除，取和删要放在 Lua 里保证原子，否则多实例会重复消费。滑动窗口限流也常用它：每次请求 ZADD 一个“时间戳加随机后缀”的成员，再用 ZREMRANGEBYSCORE 清掉窗口外的记录，ZCARD 就是窗口内请求数。

两个细节容易出错。第一，分数是双精度浮点数，超过 2^53 的整数无法精确表示，用毫秒时间戳没问题，用纳秒或超长 ID 就会丢精度。第二，分数相同时按成员字典序排列，所以并列第一的顺序是确定的，但可能不符合业务预期，必要时把序号拼进成员名。

Bitmap 与 HyperLogLog：把内存压到极限

Bitmap 不是独立类型，而是把 String 当 bit 数组用。SETBIT key offset 1 把第 offset 位置 1，GETBIT 读某一位，BITCOUNT 统计 1 的个数，BITOP AND|OR|XOR|NOT 在多个位图之间做运算，结果写入新 key。offset 从 0 开始，上限是 2^32-1，也就是单个位图最大 512 MB。

日活统计是很典型的例子：以日期为 key，用户 ID 为 offset，登录时 SETBIT，统计时 BITCOUNT。前提是用户 ID 是紧凑的整数；如果 ID 是雪花算法生成的 19 位数字，offset 会直接把位图撑到几百 MB，这时应先做一层映射或改用 HyperLogLog。按 1 亿用户估算，一天一个位图约 12.5 MB，一个月三十天就是数百 MB 量级，这个数字只是量级估算，实际取决于最大 offset。

签到、功能开关、布尔型标记都适合同一套思路：一个用户一天一位，或者一个功能一位。

HyperLogLog 解决的是另一个问题：只需要基数（有多少个不同的值），不关心具体是哪些值。PFADD 添加元素，PFCOUNT 返回估算值，PFMERGE 合并多个 key。官方文档给出的标准误差是 0.81%，每个 key 在稠密编码下约 12 KB，这两个数字都来自文档，不是精确保证。它的优点是内存与元素数量无关，一亿个 UV 和一万个 UV 占用一样。

代价也很明确：结果有误差，无法判断某个元素是否存在，也无法取回元素。因此计费、对账这类要求精确的场景不能用它，统计 UV、搜索词去重、独立访客趋势这类允许近似的地方才合适。按天建 key，再用 PFMERGE 汇总周活、月活，是常见的组合。

Stream 与 Geo：日志流与附近的人

Stream 是 Redis 5.0 引入的追加日志类型。每条消息有一个“毫秒时间戳-序号”形式的 ID，XADD 追加，XLEN 取长度，XRANGE 按 ID 区间读取。和 List 相比，它多了消费组和确认机制：XGROUP CREATE 建组，XREADGROUP GROUP g c COUNT 10 BLOCK 5000 STREAMS s > 让消费者 c 读取新消息，处理成功后 XACK 确认。

未确认的消息会进入每个消费者的待处理列表（pending entries list，PEL），可以用 XPENDING 查看积压，用 XCLAIM 把超时未确认的消息转给其他消费者重新处理。这正是 List 做队列缺少的能力：消息不会因为消费者崩溃而凭空消失。

它的语义接近 Kafka 的简化版：有主题、有消费组、有偏移量，但没有分区，也没有跨节点的分区再均衡，规模上去之后仍要靠外部消息队列。把它当作轻量级事件日志、站内通知、任务分发是合适的。

Geo 建立在有序集合之上，把经纬度编码成 geohash 存进 score。GEOADD 写入，GEODIST 算两点距离，GEORADIUS 按圆心和半径查询，GEORADIUSBYMEMBER 以某个成员为圆心查询。

注意参数顺序是先经度后纬度，写反了不会报错，只会查到错误的结果。国内业务还要注意坐标系：GPS 拿到的是 WGS-84，地图展示常用 GCJ-02，入库前应统一转换。另外，本文写作时 Redis 6.2 尚未发布，按半径查询只能用 GEORADIUS 系列，6.2 才提供的 GEOSEARCH 在这里不可用。

编码、复杂度与选型

同一份逻辑数据，不同编码的内存差距可能达到数倍。用 OBJECT ENCODING key 可以查看当前编码：String 有 int、embstr、raw 三种，能解析为整数的值用 int，短字符串用 embstr，长字符串用 raw；List 是 quicklist；Hash 和 Sorted Set 在小规模时用 ziplist，超过阈值转为 hashtable 和 skiplist；Set 在纯整数且规模小时用 intset。前面提到的几个 hash-max-ziplist-*、set-max-intset-entries 配置就是阈值。

编码转换基本是单向的：元素数量或单个值长度超过阈值后，结构会转成更通用的编码，即使之后删掉元素也不会转回去。这解释了为什么一个曾经很大的 Hash 即使清空了大半，内存也没有降下来。调整阈值要在写入前规划，而不是事后补救。

命令复杂度要按数据规模来读。GET、SET、HSET、SADD、LPUSH 是 O(1)；ZADD、ZRANK 是 O(log N)；LRANGE、HGETALL、SMEMBERS、SINTER 是 O(N) 或更高；KEYS 是 O(N) 且会遍历整个库。生产环境禁止 KEYS，用 SCAN cursor MATCH pattern COUNT 100 渐进遍历，代价是可能返回重复元素，需要客户端去重。

大 key 是单线程模型下最危险的东西。redis-cli --bigkeys 基于 SCAN 采样，能列出各类型中最大的 key；MEMORY USAGE key 可以看单个 key 的字节数；删除大 key 用 UNLINK 把释放内存的工作交给后台线程，避免 DEL 卡住主线程。

按需求选型可以参照下表：

需求 推荐结构 关键命令 注意事项
缓存对象、计数器 String SET、INCR 整体读写，注意值上限
队列、时间线 List LPUSH、BRPOP 无确认机制，必须限长
对象字段更新 Hash HSET、HSCAN 避免单个巨型哈希
标签、去重、关系 Set SADD、SINTER 大集合求交注意复杂度
排行榜、延迟队列 Sorted Set ZADD、ZRANGEBYSCORE 分数精度与并列顺序
布尔标记、签到 Bitmap SETBIT、BITCOUNT offset 不能过于稀疏
UV 估算 HyperLogLog PFADD、PFCOUNT 有误差，不能取元素
事件流 Stream XADD、XREADGROUP 规模有限，复杂场景用消息队列
地理位置 Geo GEOADD、GEORADIUS 先经度后纬度，注意坐标系

最后集中说几个误区。把 List 当无界队列用，写多读少时内存会一路涨到 maxmemory；在生产环境执行 KEYS，几百万个 key 足以让主线程停顿；把所有对象塞进一个 Hash，导致无法分片、无法按字段过期；从不检查 OBJECT ENCODING，以为删了元素内存就会降；以及用 HyperLogLog 做计费统计，误差会在对账时暴露。

小结

Redis 的价值不只是快，更在于它把常用数据结构做成了服务端原语，让计数、去重、排序、范围查询都能用一条命令完成。本文按 String、List、Hash、Set、Sorted Set、Bitmap、HyperLogLog、Stream、Geo 的顺序梳理了各自的语义、常用命令与典型场景，并给出了一张选型表。真正要记住的是三点：命令复杂度要与数据规模一起看，因为执行是单线程的；编码决定内存，阈值要在建模时就想清楚；每种结构都有边界，List 没有确认、HyperLogLog 不精确、Geo 参数顺序反直觉。把这些边界写进设计文档，比事后调优更省事。
