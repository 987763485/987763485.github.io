TCP 流量控制与拥塞控制

排查“网络慢”时，我们常会同时遇到两个词：流量控制与拥塞控制。它们的表现都是发送方主动减速，但保护的对象完全不同：一个怕接收方被压垮，一个怕网络被压垮。本文从滑动窗口讲起，说明接收窗口与拥塞窗口如何共同决定发送速率，再讨论 CUBIC 与 BBR 的取舍、SACK 与缓冲区膨胀，最后给出用 ss、tc 和 Wireshark 观察与调优的方法。

两个问题：一个保接收方，一个保网络

先看两个容易混淆的场景。接收端磁盘繁忙、应用读取缓慢，接收缓冲区被填满，它希望发送方少发一点，这是流量控制（flow control）要解决的问题；接收端很空闲，但中间路由器的出口队列排满了，继续加速只会丢更多报文，这是拥塞控制（congestion control）要解决的问题。前者保护端系统，后者保护网络。

两者的反馈机制也不同。流量控制有显式的协议字段：TCP 首部里的 16 位窗口字段就是接收方通告的接收窗口 rwnd（receive window），含义是“从确认号开始，我还能接收多少字节”。拥塞控制没有对应字段，发送方只能根据 ACK 的到达节奏、丢包与 RTT 的变化来推断路径的承载能力，并在本地维护一个拥塞窗口 cwnd（congestion window）。

真正决定“还能发多少”的是两者的较小值：有效窗口 = min(rwnd, cwnd)。可以用一个比喻记住分工：rwnd 是收件人告诉你“我桌上还能放几箱”，cwnd 是快递公司根据路况估计“这条线还能塞几辆车”。作为发送方，两个限制都必须遵守，因此“带宽跑不满”既可能出在接收端，也可能出在路径上，排查时不能只盯着带宽一个数字。

滑动窗口与带宽时延积

序列空间与通告窗口

TCP 把字节流编号，序列号是 32 位、按字节递增的。所谓滑动窗口，是指在序列空间上开一个可移动的区间：区间内的字节已获准发送，左边界随 ACK 前移，右边界随窗口变大而扩张。它同时解决两个问题——用累积确认减少 ACK 数量，用窗口大小限制在途数据量。

发送方通常维护几个变量：SND.UNA 是最早未确认的序号，SND.NXT 是下一个要发送的序号，SND.WND 是当前发送窗口；SND.UNA 到 SND.NXT 之间是已发未确认的数据，SND.NXT 到窗口右边界之间是还可以发但尚未发出的数据。接收方对应维护 RCV.NXT 与 RCV.WND，RCV.WND 就是它写进首部通告出去的 rwnd。

窗口是区间而不是一个数字：乱序报文可先缓存，等空缺补齐再交付，这也是 SACK 能发挥作用的基础。

16 位窗口字段最大只能表示 65535 字节。在早期低速链路上这足够，但在长肥管道（long fat network）上远远不够，于是有了窗口缩放（window scaling）选项：双方在握手时协商一个 0 到 14 的移位值，实际窗口等于首部字段左移该位数，上限可到约 1 GB。注意它只能在 SYN 中协商，连接建立后再改无效；中间设备若改写或丢弃该选项，就会出现“带宽足够但吞吐上不去”的怪现象。

当接收缓冲区满时，接收方通告零窗口，发送方停止发送并启动坚持定时器（persist timer），定期发送窗口探测报文，避免双方互相等待造成死锁；窗口重新打开后，接收方再发窗口更新。另一类细节是糊涂窗口综合征（silly window syndrome）：接收方每次只腾出几十字节就通告，或发送方每次只发几十字节的小段，都会让首部开销占比飙升。前者的对策是等窗口涨到缓冲区一半或一个 MSS 再通告；后者的对策之一是 Nagle 算法，即在还有未确认数据时不发小段。Nagle 与延迟确认叠加会引入额外时延，对时延敏感的业务通常用 TCP_NODELAY 关闭它。

带宽时延积：窗口到底要多大

链路上能容纳的“在途数据”有一个物理上限，等于带宽乘以往返时延，这个量叫带宽时延积（bandwidth-delay product，BDP）。发送方必须让足够多的字节同时在路上，链路才不会空转；如果窗口小于 BDP，吞吐就被窗口卡住，与带宽无关。

举个示意性的例子。假设一条 1 Gbps 的链路，往返时延 100 ms，则 BDP 约为 1 Gbps ÷ 8 × 0.1 s ≈ 12.5 MB。若窗口只有未缩放的 64 KB，理论吞吐上限约为 64 KB ÷ 0.1 s ≈ 5 Mbps。把窗口放大到 12.5 MB 以上，才可能跑满带宽。这说明跨地域传输慢，很多时候不是带宽不够，而是窗口与 RTT 不匹配。

由此得到估算式：吞吐 ≈ min(rwnd, cwnd) ÷ RTT。只扩容带宽而不处理 RTT 和窗口，收益往往有限。

拥塞控制：四个阶段与丢包恢复

经典实现把拥塞控制分成慢启动、拥塞避免、快重传、快恢复四个阶段，核心状态变量是慢启动阈值 ssthresh。

慢启动并不慢，只是起点低：连接初期 cwnd 从较小的初始窗口开始（Linux 3.0 之后为 10 个 MSS），每收到一个 ACK 增加一个 MSS，效果是每个 RTT 翻一倍，即指数增长。当 cwnd 达到 ssthresh 时转入拥塞避免，改为每个 RTT 增加约一个 MSS 的线性增长，也就是常说的加性增、乘性减（AIMD）。

丢包的发现方式决定了代价。若是超时重传，说明 ACK 长时间断流，发送方把 ssthresh 降为当前在途数据量的一半，cwnd 回落到一个 MSS 并重新慢启动，代价很大。若是收到三个重复 ACK，说明后续报文仍在到达，只是中间缺了一段，此时执行快重传：立即重传丢失的报文而不等超时；随后进入快恢复，把 ssthresh 设为在途量的一半，cwnd 设为 ssthresh 加三个 MSS，每多一个重复 ACK 再临时加一个 MSS，直到新的 ACK 到来再回落到 ssthresh。

flowchart TD
    A[慢启动: cwnd 每 RTT 翻倍] --> B{cwnd 达到 ssthresh}
    B --> C[拥塞避免: 每 RTT 加一个 MSS]
    C --> D{收到三个重复 ACK}
    D --> E[快重传: 立即重传丢失段]
    E --> F[快恢复: ssthresh 减半, cwnd 临时膨胀]
    F --> C
    C --> G{超时}
    G --> H[cwnd 降为一个 MSS, 重新慢启动]
    H --> A

同样丢一个包，快重传只让窗口减半，超时却让窗口归零重来。因此减少超时、让重复 ACK 尽早出现（例如不乱序、不关闭 SACK），对吞吐的影响可能比换算法更大。

SACK、DSACK 与 RTT 测量

累积确认只告诉发送方“第 N 字节之前都收到了”，中间缺一段时无法判断后面是否已到达，只能保守地重传一大片。SACK（selective acknowledgment，RFC 2018）让接收方在选项中列出已经收到的非连续块，发送方据此只补空洞，一个窗口丢多个包时尤其有效。它需要双方在握手时都声明支持，任一端或中间设备不认，协商就不生效，这也是不要随手关闭它的原因。

DSACK（RFC 2883）让接收方把重复收到的块也报出来，发送方据此判断某次重传是多余的，可能是超时过早或路径乱序，从而减少误判。

RTT 的测量依赖时间戳选项（RFC 1323）。没有它，一次采样要绑定一个被确认的报文，重传还会带来“ACK 确认的是哪次发送”的歧义；有了时间戳回显，几乎每个 ACK 都能提供采样，RTO 估计更及时，还能防止序列号回绕。

算法演进：从 Reno 到 CUBIC 与 BBR

Reno 是 1990 年代的经典实现，也就是前面四阶段的来源。它把丢包一律视为拥塞信号，靠 AIMD 收敛。问题在于高 BDP 链路上窗口减半后要很多个 RTT 才能恢复，且一个窗口丢多个包时，标准快恢复只能处理第一个。

NewReno 用部分确认（partial ACK）判断一次恢复是否结束，一个窗口内连续丢包时能逐个重传，不必退回慢启动，这一思路写进了 RFC 6582。

Vegas 属于时延型算法：它比较实际速率与期望速率，把差值换算成排队报文数，发现 RTT 变大就提前减速，努力只保留少量排队。但当链路上还有 Reno 这类丢包型算法时，它总是先退让，带宽被挤占，因此部署很少。

CUBIC 是目前最常见的选择。它不按 RTT 计数线性增长，而把窗口表示成距上次拥塞事件的时间的三次函数：远离拥塞点时增长快，接近时变缓。由于增长只与时间有关、与 RTT 无关，不同 RTT 的流之间更公平，也更容易跑满高 BDP 链路。CUBIC 自 Linux 2.6.19 起成为默认算法，2018 年形成 RFC 8312，到 2020 年仍是主流发行版的默认值，但本质上仍以丢包为主要信号。

BBR 则换了模型。它在 2016 年由 Google 公开，通过持续测量瓶颈带宽和最小 RTT 估计路径容量，再按两者乘积做 pacing 发送，尽量填满管道而不制造排队。它对随机丢包不敏感，在有丢包的长链路上优势明显。但要说清楚：BBR 自 Linux 4.9 起可以选用，2020 年已被 Google 与部分 CDN 使用，却并非各发行版的默认算法，与 CUBIC 共存时的公平性也仍在讨论。把它当成“万能加速器”并不准确。

缓冲区膨胀：更多缓冲不等于更好

路由器出口队列是吸收突发的必需品，但队列太长会把拥塞信号从丢包变成时延。缓冲区长期被填满时，所有流都要排上几百毫秒，交互式应用明显卡顿，吞吐测试却显示带宽正常，这就是缓冲区膨胀（bufferbloat）。家庭网关与廉价交换机常见这种配置：缓冲很大，却没有任何队列管理。

解决方向是主动队列管理（AQM）。CoDel 不配置队列长度，而是观察报文在队列中的停留时间，超过目标值就主动丢弃或标记；FQ-CoDel 先按流散列成多条子队列再分别执行 CoDel，既隔离了占用大量缓冲的流，又让时延保持低位。不少发行版已把 fq_codel 设为默认规则，可用 tc 查看。判断这类问题要比较空闲时与满载时的 RTT 差值，而不是只看平均时延。

观察、调优与一次排查

排查窗口与拥塞问题，第一步是看内核已有的统计，而不是先改参数。

Wireshark 里可以用 tcp.analysis.retransmission、tcp.analysis.duplicate_ack、tcp.analysis.zero_window、tcp.analysis.window_full 等显示过滤器快速定位异常，再用 tcp.options.wscale.shift 确认窗口缩放是否协商成功。

区分丢包与排队并不难：有重传和重复 ACK，多半是丢包；没有重传但 RTT 持续抬升，多半是队列堆积；通告窗口归零，瓶颈在接收端；cwnd 很小又没有丢包，可能是应用限速。把这几点与吞吐估算式对照，基本能判断卡在哪一环。

调优主要围绕几个参数：tcp_rmem 与 tcp_wmem 的三个值是下限、默认值和上限，上限过小会直接压住窗口；tcp_window_scaling、tcp_sack 应保持开启；tcp_congestion_control 选择 cubic 或 bbr；tcp_notsent_lowat 从 Linux 3.12 起可用，设小可限制内核里尚未发送的数据，降低大传输对时延的干扰。缓冲区应按 BDP 估算，而非越大越好——过大的接收缓冲同样会制造缓冲区膨胀。内核自动调优已覆盖大多数场景，照搬网上的“万能参数”往往是负优化。

一次跨地域传输的排查

假设一条跨地域链路带宽充足，但单个连接的吞吐远低于预期，而且时延越大越慢。按前面的公式，先怀疑窗口而不是带宽。

第一步用 ss 看连接：cwnd 停在很小的值且重传不为零，说明丢包在压制窗口；cwnd 正常而 rwnd 很小、wscale 为 0，说明接收窗口成了瓶颈。第二步核对两端缓冲上限，低于 BDP 时窗口根本涨不上去。第三步看应用是否写得慢：cwnd 已达 BDP、又没有重传，却仍传不满，多半是发送端供给不足。

对应处理是：修复链路质量，或换成对丢包不敏感的算法并配合 fq 队列；开启窗口缩放、按 BDP 调大接收缓冲；优化应用写入或增加并发。这样每次只验证一个假设，而不是同时改十个参数。

常见误区

把流量控制与拥塞控制混为一谈，是最常见的起点错误：窗口问题去换算法，丢包问题去加缓冲，方向一开始就错了。其次是默认带宽不足，忽略 RTT 与窗口的乘积。第三，为了所谓稳定关闭 SACK 或窗口缩放，反而让多包丢失的恢复更慢。第四，不测量就照搬参数，尤其把缓冲调到极大。第五，认为 BBR 一定更快，忽略它与 CUBIC 共存时的公平性以及自身的排队行为。

小结

流量控制与拥塞控制共同决定发送窗口：前者由接收方的 rwnd 表达，后者由发送方的 cwnd 估计，实际速率受两者较小值约束，并与 RTT 成反比。滑动窗口、窗口缩放与 BDP 解释了长肥管道为何需要大窗口；慢启动、拥塞避免、快重传与快恢复构成丢包型算法的骨架，CUBIC 是当今 Linux 的默认选择，BBR 则改用带宽与 RTT 建模。SACK 与时间戳让恢复更精确，AQM 抑制缓冲区膨胀。排查时先测量再调参，按窗口、丢包、时延逐层排除。
