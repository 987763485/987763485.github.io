RabbitMQ 与 Kafka 的对比

消息中间件选型时，RabbitMQ 与 Kafka 常被放进同一张对比表，但两者其实不是同一类东西：一个是从 AMQP 规范长出来的路由型消息代理，一个是从日志聚合场景长出来的分布式提交日志。本文不重复讲 Kafka 的安装与收发，而是把两者的数据模型、投递语义、吞吐与延迟、顺序与积压、运维成本逐项摆开，说明差异的根源，最后给出一份可以直接拿去开会的选型清单。

两种出身，两条路线

RabbitMQ 在 2007 年发布，实现的是 AMQP 0-9-1 模型。它的核心抽象是交换机与队列：生产者不直接把消息塞进队列，而是投给交换机，再由绑定规则决定消息进入哪些队列。这个设计的目标是灵活路由，让同一份消息按不同规则分发给多个用途不同的消费者。

Kafka 出自 LinkedIn 的日志聚合需求，2011 年开源。它把消息组织成只追加的日志，主题在物理上切成若干分区，每个分区就是一条独立的日志。消费不是取走并删除，而是按偏移量读取。这个设计的目标是高吞吐的持久化流转：数据落盘保留一段时间，多个下游按各自进度消费，需要时还能重放。

两条路线决定了后面几乎所有差异。RabbitMQ 关心的是“这条消息该送到哪里、由谁确认”，Kafka 关心的是“这份日志写到哪个分区、谁读到了第几条”。理解了这一点，很多“哪个更快”的争论，其实最终会变成“你要的是哪一种语义”的选择。

RabbitMQ 的模型：交换机是路由中枢

一条消息从生产者到消费者，要经过交换机、绑定、队列三个环节：

flowchart LR
    P[生产者] --> E{交换机}
    E -->|routing key: order.created| Q1[队列: 订单]
    E -->|routing key: order.*| Q2[队列: 审计]
    Q1 --> C1[消费者 A]
    Q2 --> C2[消费者 B]

交换机有四种常用类型。direct 按路由键精确匹配；fanout 忽略路由键，广播到所有绑定队列；topic 支持 *（匹配一个词）与 #（匹配零到多个词）的通配；headers 按消息头匹配，实际使用较少。绑定就是把交换机与队列连起来的那条规则，一个队列可以绑定多个交换机，一个交换机也可以绑定多个队列。

队列侧的能力是 RabbitMQ 最实用的部分。消费者默认自动确认，改成手动确认后，只有业务处理成功才发 basic.ack，失败可以 basic.nack 并选择是否重新入队。预取数量（prefetch，即 basic.qos）限制每个消费者手上未确认的消息条数，避免一个消费者一次被塞进上千条。队列可以配置死信交换机，把被拒绝、过期或超出长度的消息转到另一个队列统一处理；可以设置消息级与队列级的 TTL；可以开启优先级队列，让紧急任务排在前面；社区插件 rabbitmq_delayed_message_exchange 还能实现延时投递，不必用死信队列加 TTL 的土办法模拟。

这些能力共同指向一个定位：RabbitMQ 是一台会按规则分拣、能逐条追踪状态的路由器。

Kafka 的模型：分区日志与消费进度

Kafka 的层级只有三层：主题、分区、偏移量。生产者把消息追加到某个分区的末尾，broker 顺序写盘；消费者主动拉取，自己记录读到哪个偏移量，并把进度提交到内部主题。同一个消费组内，一个分区同时只能被一个消费者占用，因此组的最大并行度等于分区数。

这里只强调与对比有关的三个性质。第一，消息不因消费而删除，保留期由时间或容量决定，所以同一份数据可以被多个消费组各读一遍，也可以把偏移量重置回去重放。第二，顺序只在分区内成立，跨分区没有全局顺序。第三，分区是并行与顺序的折中单位：分区越多吞吐越高，但单分区内的顺序保证越容易被“按 key 分区”绑架。

投递语义与端到端一致性

RabbitMQ 的语义取决于确认方式。消费者自动确认时，消息一发出就从队列删除，进程崩溃就丢，这是至多一次。改用手动确认并配合发布者确认（publisher confirms），生产者在消息被交换机接收并落到队列后收到 broker 的确认，失败可重发，就得到至少一次；代价是网络超时这类不确定场景会产生重复消息。更麻烦的是超时：broker 其实已经收下，只是确认没回来，生产者重发就会多出一条，所以消费端最好按消息 ID 做一次去重，把重复挡在入库之前。

Kafka 默认也是至少一次：生产者设置 acks=all 并开启重试，消费者处理完再提交偏移量，中途崩溃就会重复消费。Kafka 在 0.11 引入幂等生产者，用生产者 ID 与序列号在 broker 侧去重，解决重试造成的重复；再配合事务与 isolation.level=read_committed，可以把“消费—处理—再生产”这条链路做成 Kafka 内部的精确一次。

但要注意边界：Kafka 的精确一次只覆盖 Kafka 自身的读写。如果消费者要把结果写进 MySQL、调用外部接口或发短信，这一步仍然可能重复执行。所谓端到端精确一次，最终还是要靠消费端幂等来兜底，比如业务唯一键、去重表或带过期时间的去重标记。把“开了事务”当成“业务不会重复”，是这两套系统上最常见的误解。

吞吐、延迟与顺序保证

从设计取向上看，Kafka 把吞吐放在第一位。追加写避免了随机写，操作系统页缓存承担了大部分读写，发送端把消息攒成批（batch.size、linger.ms）并压缩，broker 用零拷贝把数据直接送给网络。批越大、压缩比越高，单位时间处理的消息越多，但单条消息的端到端延迟也被攒批时间拉长。吞吐还可以靠增加分区横向扩展。

RabbitMQ 把低延迟和逐条控制放在第一位。消息到达交换机后立刻按绑定关系路由，通过推模型尽快送到消费者；代价是每条消息都要经历路由、入队、确认的完整流程，单位开销比批量追加高。它的吞吐可以靠增加队列与消费者提升，但更擅长的是“消息不多、每条都很重要、需要精细控制”的场景。换句话说，Kafka 优化的是每字节的搬运成本，RabbitMQ 优化的是每条消息的决策成本。

顺序方面，RabbitMQ 在单个队列内保持先进先出，但一旦多个消费者竞争同一个队列，处理顺序就无法保证；basic.nack 重新入队还会把消息放回队首附近，进一步打乱顺序。要在 RabbitMQ 上严格有序，通常得让一个队列只有一个消费者，或者用 3.8 引入的单活跃消费者（single active consumer）在组内只选一个成员消费，再按业务键拆多个队列来换取并行。

Kafka 的顺序单位是分区。同一个 key 经默认分区器散列后总是进入同一分区，从而获得分区内顺序；代价是热点 key 会把压力集中到一个分区，消费端也只能由组内一个成员处理这个分区。分区数变更后，key 到分区的映射会变，依赖顺序的消费方要做好兼容。

积压、重放与数据生命周期

这是两者差别最容易被低估的地方。

RabbitMQ 的队列是销毁性的：消息被确认后即删除，积压只存在于尚未消费的部分。积压过多时，消息会从内存换出到磁盘，吞吐明显下降；再叠加上内存与磁盘告警，broker 会阻塞生产者，形成背压。队列可以设置最大长度，超出后按策略丢弃队首或拒绝新消息。换句话说，RabbitMQ 的队列是一段管道，不是一份档案；想让已经消费过的消息重来一遍，只能提前把消息另存一份，或者从上游重新生成。

Kafka 天然保留：只要没到保留期，偏移量可以往回拨，用 kafka-consumer-groups.sh 重置到最早或指定位置，也可以用一个新的消费组从头读。重置只改变消费进度，不动日志本身，多个消费组互不干扰，但重复处理也因此成为常态，补算任务要按幂等来写。对于按键更新的场景，还可以开启日志压缩，只保留每个 key 的最新值，把主题当成一张可回放的变更表。

因此判断标准很清楚：如果消息是一次性的任务指令，处理完就该消失，RabbitMQ 的模型更贴合；如果消息是对事实的记录，需要被多个下游反复读取、回放、补算，Kafka 的日志模型才站得住。事件溯源、CDC 同步、审计与指标管道属于后者，订单派发、邮件发送、工单流转属于前者。

运维、选型与常见误区

RabbitMQ 以集群方式部署，队列在 3.8 之后推荐使用基于 Raft 的仲裁队列（quorum queue）做副本，早期的经典镜像队列在高负载下问题较多。它的管理界面相当完整，队列深度、消费者数量、投递速率、连接与通道都能直接看到；内存或磁盘超过水位会触发告警并阻塞生产者，这是保护，也是故障时最容易被误判为“服务挂了”的现象。

Kafka 的运维重心在 broker 与分区。2020 年前后仍依赖 ZooKeeper 存放元数据与选主，通常单独部署三节点；每个分区有一主多从，靠 ISR 与 min.insync.replicas 保证写入安全，分区重分配是重操作，消费积压要看 lag 而不是队列长度。它的可观测性更多依赖 JMX 指标与外部工具，管理界面不是标配。

维度 RabbitMQ Kafka
核心模型 交换机、绑定、队列 主题、分区、偏移量
路由能力 强，四种交换机加消息头匹配 弱，按 key 选分区
投递语义 至多一次或至少一次，靠手动确认 默认至少一次，可做 Kafka 内部精确一次
顺序 单队列内有序，竞争消费会打乱 单分区内有序，按 key 保证
保留与重放 确认即删除，重放需另行设计 按时间或容量保留，可重置偏移量
吞吐与延迟 低延迟、逐条控制，吞吐中等 高吞吐、批量顺序写，延迟受攒批影响
运维复杂度 集群与队列治理，界面友好 分区、副本与积压治理，工具偏底层
典型场景 任务分发、复杂路由、RPC 式调用 日志聚合、事件流、CDC、分析管道

选型时可以先问三个问题：消息处理完是否还需要再读一遍；路由规则是否复杂到需要交换机和绑定来表达；吞吐量级是否已经超出单条确认模型的经济区间。前两个答“是”偏向 RabbitMQ，后一个答“是”偏向 Kafka。

常见的误区有这几个。把 Kafka 当任务队列用，却没设计好消费组与 key，结果重平衡时整组停摆，单条失败也无处安放；期待 RabbitMQ 提供重放，直到发现确认即删除才回头改架构；只在生产者侧开启确认，却忘了消费端幂等，重试一次就多扣一笔款；队列或主题都不设上限，积压时先把内存或磁盘打满；分区只用默认散列，热点 key 把单个分区打成瓶颈；没有死信队列，失败消息要么无限重投要么悄悄消失；不监控消费积压，直到业务方投诉才发现消费者早已停摆。

至于“一套消息系统包打天下”，在多数团队里都是坏味道。同一家公司完全可能既用 RabbitMQ 跑订单与通知，又用 Kafka 做日志与数据管道，两者之间用桥接程序或双写隔离，各自承担自己擅长的语义。真正需要避免的不是多一套组件，而是用错误的语义去硬凑场景。

小结

RabbitMQ 与 Kafka 的差异不是性能参数的高低，而是模型的不同：前者是带路由的消息代理，后者是可重放的分布式日志。选型时先看语义，消息是一次性任务还是可回放的事实；再看路由复杂度、顺序要求与吞吐量级。无论选哪一个，消费端幂等、死信处理、积压监控都是必须补上的功课，缺了它们，换任何中间件都会在故障当天暴露问题。
