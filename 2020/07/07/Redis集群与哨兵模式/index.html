Redis 集群与哨兵模式

单机 Redis 一旦承载核心业务，内存上限、故障恢复与扩容就会同时变成问题。本文从复制协议讲起，依次拆解 Sentinel 的仲裁与故障转移、Cluster 的槽位与重定向，再落到客户端、运维与安全配置。读完本文，你应当能为自己的业务选出一条可落地的高可用路径，并知道每条路径的失效边界。

单机 Redis 的四个天花板

很多团队引入 Redis 时，只把它当作“比数据库快的内存缓存”。当它开始承载会话、计数器、排行榜甚至库存扣减时，单机形态就会在四个维度同时露出上限。

第一是内存。一台机器的物理内存总有边界，Redis 的 maxmemory 只能在这个边界内做淘汰；更麻烦的是持久化与主从全量同步都会 fork 子进程，页表复制和写时复制（copy-on-write）会放大内存占用。数据量越大，fork 的停顿越明显，单机就越难同时兼顾容量与延迟。

第二是故障恢复。进程崩溃、宿主机宕机、磁盘损坏，任何一种故障都意味着要人工从 RDB 或 AOF 恢复，再重建服务。恢复时间取决于数据量和备份方式，业务只能被动等待；这还没有计算 DNS 切换、连接重建和缓存预热。

第三是写入扩展。Redis 6.0 于 2020 年 5 月正式发布，引入了可选的多线程 I/O，但命令执行仍然由单线程完成，单个主节点的写入能力有明确上限。增加副本只能扩展读，不能分摊写；把同一个 key 拆到多个实例又会把分片逻辑推给应用。

第四是维护窗口。升级版本、打内核补丁、迁移机房，都需要停机或至少一次主从切换；单机没有可用的切换对象，只能接受停机。

这四件事指向两个不同的答案：如果数据能放进一台机器，缺的是“故障时自动顶上”的能力，Sentinel 就够了；如果数据或写入已经超过单机，才需要 Cluster 这样的分片方案。两者都不是凭空实现的，它们共享同一套复制地基。

复制：两种方案共同的地基

Sentinel 和 Cluster 都把“主从复制”当作原料：Sentinel 负责在主节点挂掉后换一个副本上来，Cluster 负责把槽位分配给多个主节点，并在主节点挂掉后让它的副本接管。理解复制的异步本质，后面所有“会不会丢数据”的问题才有答案。

全量同步与部分同步

副本启动时执行 REPLICAOF（旧命令是 SLAVEOF）指向主节点，然后发送 PSYNC ? -1，表示“我没有复制历史，请给我一份全量数据”。主节点执行 BGSAVE 生成 RDB，同时把这段时间的写命令缓存在内存里；RDB 传完后，再把缓冲区里的命令发给副本。副本清空旧数据、加载 RDB、回放缓冲命令，复制就此建立。

复制建立后，双方维护两个关键量：复制 ID（replication ID）和复制偏移量（offset）。主节点把写命令发给副本的同时，也写进一个固定大小的环形缓冲区，称为复制积压缓冲区（replication backlog）。副本断线重连时发送 PSYNC <replid> <offset>；如果 offset 仍在 backlog 覆盖范围内，主节点只补发缺失的部分，这叫部分重同步；否则退回全量同步。

backlog 默认只有 1 MB，写入量大或断线时间长时很容易被覆盖，部分同步就会失败。生产上可以按“平均写入速率 × 预计最长断线时间”估算 repl-backlog-size，例如写入 2 MB/s、希望容忍 60 秒断线，至少要留 120 MB 以上。这个数字是设计目标，不是固定推荐值。

异步复制意味着什么

主节点处理完写命令就返回客户端，并不等待副本确认。副本可能落后几毫秒，也可能落后几分钟；replica-serve-stale-data 默认为 yes，副本在失去主连接后仍会返回旧数据。复制延迟可以用 INFO replication 里的 lag 观察，但 lag 只表示最后一次 ACK 的时间差，不等于某条具体命令的延迟。

这带来一个必须接受的事实：主节点在故障前最后一段写入，可能还没到副本。Sentinel 切换和 Cluster 晋升都以“把某个副本提升为主”收尾，因此都可能丢掉这段数据。后文会分别讨论如何用 min-replicas-to-write 和 WAIT 缩小窗口，但不会有零损失的银弹。

复制还支持级联：副本可以再挂副本，用来分担全量同步的压力。代价是链路更长、延迟更大，故障转移时可选的晋升对象也更多，需要靠优先级和偏移量来约束。

Sentinel：监控、仲裁与故障转移

它解决什么问题

Sentinel 是一个独立进程，不存业务数据，只做三件事：持续监控主从节点、在主观认为主节点失联后与其他 Sentinel 交换意见、在达成共识后选出一个副本提升为主，并通知客户端。它不负责分片，所有数据仍在一个主节点上，因此适合“数据量能装进单机、但不能再接受人工切换”的场景。

监控、主观下线与客观下线

每个 Sentinel 每秒向主节点、副本和其他 Sentinel 发送 PING，每 10 秒发送 INFO，每 2 秒通过 __sentinel__:hello 频道交换对主节点的看法。当某个 Sentinel 在 down-after-milliseconds 内收不到主节点的有效响应，它把主节点标记为主观下线（SDOWN）；这只代表它自己的判断。

当足够多的 Sentinel（达到 quorum）都报告 SDOWN，主节点被标记为客观下线（ODOWN）。注意 quorum 只用于“确认故障”，不等于“授权切换”。真正发起故障转移的 Sentinel 还必须赢得多数票，也就是获得包括自己在内的多数 Sentinel 支持。3 个 Sentinel 的 quorum 通常设为 2，5 个设为 3；quorum 设得过高会让故障无法被确认，设得过低则容易因单个网络抖动触发切换。

领导选举与故障转移

ODOWN 之后，Sentinel 之间要进行一次类似 Raft 的选举。发现故障的 Sentinel 向其他 Sentinel 请求投票，每个 Sentinel 在每个配置纪元（configuration epoch）只能投一票；拿到多数票的 Sentinel 成为 leader，获得执行故障转移的授权。配置纪元是一个单调递增的编号，用来给“哪一版主从拓扑更新”排序，旧主节点带着旧纪元回来时，会被识别为过时配置并降级为副本。

故障转移的步骤可以概括为：

  1. 在副本中挑选晋升对象：先看 replica-priority，数值越小优先级越高，0 表示永不晋升；优先级相同再看复制偏移量，偏移量大的数据更新；仍相同则比较 runid。
  2. 向选中的副本发送 REPLICAOF NO ONE，让它停止复制并成为主节点。
  3. 向其余副本发送 REPLICAOF 新主节点地址，让它们改挂新主。
  4. 把旧主节点记录为“待降级”，等它恢复后发送 REPLICAOF，让它成为新主的副本。
  5. 通过 +switch-master 事件把新地址广播给订阅的客户端。

    S1->>R: 记录为新主节点
    S1->>S2: 广播 +switch-master

整个过程受 failover-timeout 约束，超时后会重新尝试。parallel-syncs 控制同时有多少个副本去与新主做全量同步，设得太大可能在新主上造成一波 fork 和网络压力。

客户端如何发现新主

客户端不应该把主节点 IP 写死。常见做法是连接 Sentinel 集合，启动时用 SENTINEL get-master-addr-by-name mymaster 拿到当前主地址，之后订阅 +switch-master 事件；也可以用客户端库提供的 Sentinel 连接池（例如 Jedis 的 JedisSentinelPool、Lettuce 的 Sentinel 支持），由库负责在切换后重建连接。

这里有一个容易被忽略的细节：客户端缓存的地址有“保质期”。如果客户端只在启动时查一次，切换后它会一直向旧主写，直到重启或连接报错。稳妥的做法是同时具备事件订阅、连接失败重查和短 TTL 缓存，三者互为兜底。

部署上的几条硬规矩

Sentinel 的数量应为奇数且不少于 3 个，否则无法形成稳定的多数；它们应分布在不同的物理机、机架或可用区，避免一次断电全军覆没；不要和 Redis 主节点部署在同一台机器上，否则主节点故障会连带带走仲裁能力；在 Docker 或 NAT 环境中要配置 sentinel announce-ip 和 announce-port，否则 Sentinel 之间会交换容器内地址，导致互相不可达；Sentinel 端口同样要设置 bind、protected-mode 和密码，不能裸露在公网。

故障场景与防护

Sentinel 能处理“进程崩溃”这类干净故障，但对网络分区和客户端行为要更小心。

网络分区与旧主写入

假设主节点所在机房与 Sentinel 集群之间的网络中断，但主节点与部分客户端仍然连通。Sentinel 侧看到的是主节点失联，达到 quorum 后发起切换，把副本提升为新主；旧主并不知道自己已经被替换，仍然接受客户端写入。等网络恢复，Sentinel 会把旧主降级为副本，旧主上那段未被复制的写入会被清空。这就是 Sentinel 场景下最典型的脑裂风险。

要彻底消除它，需要分布式共识和 fencing，Redis 的异步复制给不了。工程上能做的是缩小窗口：在主节点上设置 min-replicas-to-write 和 min-replicas-max-lag，让它在“健康副本不足”时拒绝写入。

这两个参数不是万能的：副本可能只是网络慢，主节点会因此拒绝写入，可用性下降；参数只在主节点生效，切换后新主也要有同样的配置；它降低的是“旧主继续接受写入”的概率，不是严格保证。是否启用，要在“丢数据”和“短时不可写”之间做业务判断。

切换抖动与故障转移循环

网络不稳定时，主节点可能反复在“可达”和“不可达”之间摆动，Sentinel 跟着反复切换。down-after-milliseconds 设得太短会放大这个问题，设得太长又会让真实故障的恢复变慢。failover-timeout 则决定一次失败的切换多久后重试，太小会叠加压力，太大则恢复缓慢。实践上要结合业务能接受的恢复时间设定，并用监控观察 +failover-end、+switch-master 的频率；如果一天内多次切换，应先查网络和主节点负载，而不是继续调小超时。

replica-priority 也常被用来做人工干预：给性能弱或跨机房的副本设 0，禁止它被提升；给主推副本设较小值，让 Sentinel 优先选它。但优先级只在副本之间比较，不能替代容量规划。

客户端缓存过期

切换完成后，最危险的不是新主，而是“还连着旧主”的客户端。旧主被降级后，写入会收到 READONLY 错误，这其实是保护；更隐蔽的是客户端缓存了旧拓扑，持续重试旧地址，形成错误风暴。客户端应当把 READONLY 错误视为“拓扑已变”的信号，立即重新查询 Sentinel，而不是原地重试。对于使用连接池的应用，还要确保池中的旧连接被清理，避免一半请求打到新主、一半打到旧主。

适用边界

Sentinel 不解决容量问题。所有写仍然落在一个主节点，内存上限就是单机上限；增加副本只能分担读，且副本默认只读、可能返回旧数据。当数据量或写入量超过单机，继续堆 Sentinel 没有意义，应该考虑 Cluster。

Redis Cluster：槽位、重定向与扩缩容

16384 个槽与键的路由

Cluster 把整个键空间切成 16384 个哈希槽，每个主节点负责一部分槽。键属于哪个槽由 CRC16(key) mod 16384 决定，Cluster 只负责把槽分配给节点，不负责记录每个键的位置。这样路由表很小，节点之间交换的是槽位归属，而不是键列表。

为什么是 16384 而不是 65536？一个常被引用的解释是心跳包要携带槽位位图：16384 个槽对应 2 KB 位图，65536 个槽则是 8 KB，而 Cluster 的设计规模通常在几百到一千个节点，16384 个槽已经够分。这个数字是协议常量，客户端和集群必须一致，不能自行修改。

MOVED 与 ASK：两种重定向

当客户端把命令发到不负责该槽的节点，节点不会代为转发，而是返回重定向。MOVED <slot> <ip:port> 表示这个槽永久归目标节点，客户端应更新本地槽位缓存，以后直接发往新地址；ASK <slot> <ip:port> 表示这个槽正在迁移，目标节点只是临时接管这个键，客户端应先发送 ASKING，再发送原命令，但不要更新槽位缓存，因为迁移完成后归属还会变。

flowchart TD
    A[客户端计算 CRC16 key mod 16384] --> B{本地槽位表命中?}
    B -- 是 --> C[发送到对应节点]
    B -- 否 --> D[任选节点发送]
    D --> E{节点负责该槽?}
    E -- 是 --> F[正常执行]
    E -- 否，已迁移 --> G[返回 MOVED]
    E -- 否，迁移中 --> H[返回 ASK]
    G --> I[更新槽位表并重试]
    H --> J[发送 ASKING 后重试目标节点]

MOVED 是稳定的拓扑变更，ASK 是迁移过程中的临时状态。客户端如果对 ASK 也更新缓存，会在迁移未完成时把请求固定到临时节点，随后收到更多重定向；如果对 MOVED 不更新缓存，则会每次多一跳。成熟的集群客户端会区分两者，并设置最大重定向次数，防止异常情况下无限循环。

集群总线、故障检测与副本晋升

Cluster 节点之间通过集群总线通信，端口是客户端端口 + 10000（例如 6379 对应 16379）。总线使用二进制协议和 gossip，交换节点状态、槽位归属和故障判断。节点之间定期 PING/PONG，超过 cluster-node-timeout 未响应会被标记为 PFAIL；当多数主节点都认为某个主节点 PFAIL，它才被标记为 FAIL，其副本开始竞选。

副本晋升需要多数主节点投票，且会等待一段与排名相关的延迟，避免多个副本同时竞选。晋升成功后，新主接管原主的槽位，旧主恢复后自动成为副本。cluster-require-full-coverage 默认为 yes，意味着只要有一个槽没有节点负责，整个集群就拒绝服务；把它设为 no 可以让集群在部分槽不可用时继续服务其余槽，但客户端会看到部分键报错。这是一个可用性与完整性的取舍，不能当成“万能开关”。

手动切换用 CLUSTER FAILOVER，在副本上执行，默认会先与主节点协调、等待复制追上，再完成切换；FORCE 用于主节点不可达时强制切换，TAKEOVER 则完全不协商，只适合极端故障场景。

多键操作与 hash tag

Cluster 不支持跨槽的多键命令。MGET、MSET、SUNIONSTORE、事务、Lua 脚本中的键都必须落在同一个槽，否则会报 CROSSSLOT 错误。解决办法是 hash tag：用花括号包住键的一部分，Cluster 只对花括号内的内容做哈希。

花括号只认第一个配对，且不能嵌套；{} 空标签等于没有标签。设计键名时要把“需要原子操作的数据”放进同一个 tag，但不要把过多数据塞进同一个 tag，否则所有压力会集中到一个槽、一个节点，形成热点。

Lua 脚本同样受槽位约束：脚本里访问的所有键必须同槽，EVAL 的第一个参数是键的数量，客户端库通常要求显式传入键列表。Cluster 也不支持 SELECT 切换数据库，只能使用 0 号库，依赖多库隔离的应用需要改造。

客户端、代理与一致性边界

集群感知客户端

Cluster 客户端通常内置槽位表，并在收到 MOVED 时刷新。Jedis 的 JedisCluster、Lettuce 的 RedisClusterClient、redis-py 的 RedisCluster、go-redis 的 ClusterClient 都属于这一类。选型时要关注四个行为：是否区分 MOVED 与 ASK、最大重定向次数、拓扑刷新策略（定时还是仅在重定向时）、以及失败重试是否只针对幂等命令。

重试尤其容易出错。GET、SET 这类命令重复执行结果相同，可以安全重试；INCR、LPUSH、SETNX 之类重复执行会改变结果，盲目重试可能多扣一次库存或多发一条消息。正确做法是在业务层引入请求 ID 做去重，或者只对读操作自动重试，写操作交给上层决定。网络超时并不等于命令没有执行，这一点在故障转移期间尤其明显。

如果业务需要从副本读，Cluster 副本默认不服务读请求，客户端必须先发送 READONLY 才能读，发送 READWRITE 恢复。副本读同样可能读到旧数据，一致性要求高的场景应读主。

代理方案

另一条路是在客户端和 Redis 之间放代理，由代理维护路由，客户端像访问单机一样访问代理。Twemproxy、Codis 以及后来的 Envoy Redis 代理都属于这个思路。代理的好处是兼容旧客户端、集中治理、可以在代理层做限流和审计；代价是多一跳网络、代理本身要解决高可用、跨槽操作仍然受限，而且扩容时往往需要迁移数据。

代理不是高可用的替代品：它解决的是“客户端不会说集群协议”，不解决“主节点挂了怎么办”。实际架构里，代理后面仍然需要 Sentinel 或 Cluster 提供故障转移。

一致性与持久化边界

无论 Sentinel 还是 Cluster，故障转移都是“提升一个副本”，而复制是异步的，所以切换点之前未同步的写入会丢。WAIT 可以让客户端等待指定数量的副本确认：

WAIT 返回的是“确认的副本数”，不是“数据已持久化”。副本确认只说明命令到了副本的内存，不说明它写进了 RDB 或 AOF；如果副本随后也崩溃，仍可能丢。WAIT 还会阻塞当前客户端，超时返回 0 并不代表命令失败。它适合对少量关键写入加一道保险，不适合当成强一致方案。

持久化的细节（RDB、AOF、混合持久化、fsync 策略）属于另一篇的主题，这里只强调交集：每个节点各自持久化自己的数据，集群不会做跨节点的一致性快照；备份时要分别对每个主节点执行 BGSAVE，并记录当时的槽位分布，否则恢复出来的数据可能对不上。

运维实践：建集群、升级与容量陷阱

创建完成后，先用 redis-cli –cluster check 做一次体检，再用 CLUSTER INFO 和 CLUSTER NODES 确认状态：

CLUSTER INFO 里要重点看 cluster_state 是否为 ok、cluster_slots_assigned 是否为 16384、cluster_known_nodes 是否符合预期。CLUSTER NODES 每行是一个节点，字段依次是节点 ID、地址与总线端口、标志位、主节点 ID、最后 ping/pong 时间、配置纪元、连接状态和负责的槽位。标志位里出现 fail、fail?、handshake 都要追查；槽位出现 [slot->-nodeid] 说明正在迁移。

扩容时先加节点、再迁槽，迁完后用 –cluster rebalance 调整均衡；缩容时先迁走槽、再删节点。每次只动一个节点，动完观察 cluster_state 和客户端错误率，再继续。

升级的顺序与复制方向相反：先升级副本，再在副本上执行 CLUSTER FAILOVER，把主角色切到已升级的副本，然后升级旧主（此时它是副本）。这样任何时刻至少有一个节点在提供服务，且新版本先以副本身份验证兼容性。Sentinel 架构同理：先升级副本，手动切换主，再升级旧主，最后逐个升级 Sentinel；升级 Sentinel 期间要保持多数派在线，不要一次全部重启。

备份需要对每个主节点执行 BGSAVE，收集 RDB、redis.conf、ACL 文件和 CLUSTER NODES 输出；使用 AOF 时还要保证各节点文件完整。恢复时先在隔离环境按原槽位分布重建集群，再导入数据，最后用 –cluster check 校验。没有经过恢复演练的备份，等于没有备份。

容量与常见坑可以列成一张清单：

  • 槽位不均：扩容后新节点只拿到少量槽，老节点仍承载大部分请求，用 –cluster rebalance 或按权重调整。
  • 热点 key：槽按 key 哈希，单个热点 key 一定落在单个节点，加节点无效，需要在业务层拆键或加本地缓存。
  • 大 key：迁移时 MIGRATE 同步执行，大 key 会阻塞源节点；删除大 key 也可能造成延迟尖刺，上线前应抽样排查。
  • 跨槽事务与 Lua：设计阶段就要把相关键放进同一个 hash tag，事后改造代价很高。
  • MOVED 风暴：客户端拓扑陈旧或频繁迁槽时会放大重定向流量，迁移应安排在低峰，客户端要开启拓扑刷新并设置重定向上限。
  • 脑裂与切换时间：故障检测依赖 cluster-node-timeout 和多数主节点，网络分区时可能出现双主写入；切换时间是设计目标，必须在自己的环境里做故障演练测量，不能照搬别人的秒数。

选型：Sentinel、Cluster、代理与托管服务

把几种形态放在一起比较，决策会清楚很多。

维度 Sentinel Cluster 代理 托管服务
数据容量 单机内存 多主分片 取决于后端 取决于套餐
写扩展 单主 多主 取决于后端 视产品而定
故障转移 自动 自动 依赖后端 平台负责
多键与事务 无限制 必须同槽 仍受后端限制 视产品而定
客户端改造 小 需要集群客户端 小 小
运维复杂度 中 高 中高 低
适用场景 中小数据量、多键操作多 大数据量、要写扩展 遗留客户端 小团队、合规允许

如果数据能放进单机、业务大量使用多键操作和事务，Sentinel 是更简单的选择；它的复杂度主要在仲裁和客户端发现，不涉及槽迁移。如果数据或写入已经超过单机，或者可以接受按 key 设计分片，Cluster 才是答案，但要接受跨槽限制、运维复杂度上升和迁移成本。代理适合“客户端改不动”的过渡期，不应作为长期架构的核心。托管服务把运维转移给平台，代价是成本、可控性和某些命令与配置的限制，选型前要确认网络延迟、备份策略和扩容方式。

一个常见的误区是“为了高可用上 Cluster”。Cluster 的高可用并不比 Sentinel 更强，它额外提供的是分片；如果容量不是问题，Cluster 只会增加约束。反过来，数据已经超过单机却继续用 Sentinel，也只是把问题推迟到下一次扩容。

安全加固要点

Redis 的默认配置面向本机开发，直接暴露在公网是事故的起点。加固按网络、认证、加密、命令四层推进。

网络层：bind 只监听内网地址，安全组只放行应用网段，protected-mode 保持 yes；Cluster 总线端口（客户端端口 + 10000）和 Sentinel 的 26379 同样不能暴露，更不要把 Redis 绑定到公网负载均衡。

认证层：requirepass 只是第一步，Redis 6.0 的 ACL 可以按用户授权。先配置 aclfile，再建最小权限账号：

生产上建议在 aclfile 里关闭 default 用户（user default off），每个应用独立账号，用 +@read、-@write、-@dangerous 收口，再按需放开命令；ACL LOG 查看拒绝记录，ACL WHOAMI 确认身份。键模式是 glob，~* 等于不限制，等于没隔离。

加密层：Redis 6.0 内置 TLS，可配置 tls-port、tls-cert-file、tls-key-file、tls-ca-cert-file 并关闭明文端口；Cluster 总线可用 tls-cluster 打开加密。Sentinel 的 TLS 配置项更多，启用前要逐项对照文档验证，不要假设开了端口就全链路加密。

命令层：FLUSHALL、FLUSHDB、KEYS、CONFIG、DEBUG、SHUTDOWN 等命令在生产环境应通过 ACL 或 rename-command 禁用，确需使用时走堡垒机。慢查询、连接数和拒绝命令数要纳入监控，管理端口与业务流量分开。

小结

单机 Redis 的瓶颈不只是内存，还包括故障恢复、写入扩展与维护窗口。Sentinel 用监控、quorum、领导选举和配置纪元解决自动切换，适合数据能装进单机且多键操作频繁的场景；Cluster 用 16384 个槽、MOVED/ASK 重定向和 gossip 总线解决分片与故障转移，代价是跨槽限制和更高的运维复杂度。两者都建立在异步复制之上，故障切换可能丢失最后一段写入，WAIT 与 min-replicas-to-write 只能缩小窗口，不能消除。落地时先判断容量是否需要分片，再选择拓扑；把客户端重试、备份恢复、升级顺序和安全加固一起设计，才算真正的高可用。
