MongoDB 入门与实践

很多团队从 MySQL 起步，等到表结构三天两头改、一个页面要拼七八张表时才想到 MongoDB，却又容易走到另一个极端：把关系模型原样搬进文档，或者把没有索引的集合直接放上生产。本文从文档模型讲起，依次覆盖适用边界、安装配置、CRUD、索引、建模、副本集与一个 Node.js 订单服务示例，最后落到运维、安全与常见坑。读者不需要事先用过 MongoDB，但应当熟悉一种关系型数据库和基本的 JavaScript 语法。

一、文档模型与 BSON

关系型建模先定结构：建表、声明列与类型、加约束，再往里写数据。MongoDB 反过来，从一次读写需要哪些数据出发，把经常一起访问的字段放进同一个文档，让一次查询取回整块内容。这个顺序差异，会传导到后面几乎所有的设计取舍。

MongoDB 分三层：数据库、集合、文档。文档是 BSON 键值结构，值可以是字符串、数字、日期、二进制、ObjectId，也可以是嵌套文档或数组。嵌套与数组不是附加能力，而是建模的一等公民：订单文档可以直接带收货地址与商品明细，不必再建两张表再 JOIN。

BSON 是 JSON 的二进制扩展，带长度前缀，跳读字段比解析文本快，也支持日期等 JSON 没有的类型。代价是可读性，shell 里看到的只是渲染结果，存储层并不是文本。

每个文档都有 _id，未指定时生成 ObjectId。它占 12 字节，前 4 字节是秒级时间戳，按 _id 排序近似按插入时间排序；但它是标识符而非业务主键，订单号这类编号仍需单独设计字段。

动态 schema 指同一集合的文档字段可以不同，新增字段不用改表，老文档缺字段就当作不存在。迭代变快，约束责任交给了应用；3.6 之后可以用 $jsonSchema 做集合校验，但它只覆盖写入路径。

关注点 关系模型 文档模型
订单与明细 主表加子表，查询时 JOIN 明细数组内嵌在订单文档里
新增可选字段 改表结构或预留列 直接写入，读取时判空
读取一个聚合 多表关联后拼装 一次查询取回整棵文档
跨实体一致性 外键与事务 多文档事务或应用补偿

二、适用边界：什么时候用它，什么时候别用

判断是否适合 MongoDB，可以看三件事：结构是否稳定、读取是否以文档为中心、是否需要水平扩展。三者占了两条以上，通常就是好选择。

第一类是结构快速演化的业务。内容管理、商品属性、表单收集这类场景，字段随运营需求变化，关系库里加列会让表越来越宽，塞进文本字段又要在应用里解析。文档模型允许不同商品有不同属性，代价是应用侧要做字段兼容。

第二类是文档为中心的读取。文章带标签、评论摘要与作者信息，一次查询就返回渲染所需数据，省掉多次往返与 JOIN，此时嵌入是自然的选择。

第三类是高写入、弱关联的数据，例如日志、埋点，以及需要按分片键扩容的场景。分片集群的组成与扩容步骤另文讨论。

不适合的情况同样明确：跨多个实体强一致的事务、以复杂报表和即席关联为主的系统、已高度规范化且实体频繁互相更新的模型，用关系库更省心。MongoDB 4.0 起支持多文档事务，4.2 起支持分片集群上的分布式事务，但要显式开启会话、依附副本集，长事务还会放大锁与存储压力。它解决的是少数必须原子完成的跨文档操作，而不是把 MongoDB 用成关系库的理由。

四、CRUD：插入、查询、更新与批量写

写操作以文档为单位。insertOne 返回新文档的 _id；insertMany 默认按顺序写入，任一条失败就停止，传 { ordered: false } 可以跳过失败项继续写，insertedIds 按位置对应。批量导入日志这类允许部分失败的场景，适合无序写入。

查询条件是文档。等值直接写字段，范围与逻辑用 $gt、$gte、$lt、$lte、$ne、$in、$nin、$exists，组合用 $and、$or、$not。数组字段中 { tags: "book" } 匹配包含该元素，$all 要求全部包含，按下标条件筛选用 $elemMatch。嵌套文档必须整体匹配，只匹配某个字段要写点路径。

投影是第二参数，1 取、0 不取，除 _id 外不能混用；只取必要字段既省带宽，也是覆盖查询的前提。

更新靠操作符：$set 改字段，$unset 删字段，$inc 原子自增，$push 追加，$addToSet 去重追加，$pull 按条件移除。updateOne 只改第一条，updateMany 改全部，{ upsert: true } 在无匹配时插入。替换式更新会整文档覆盖，误用会丢字段。

删除用 deleteOne 与 deleteMany；线上执行前先用同样条件跑一次 countDocuments，是成本最低的习惯。

一批不同类型的写操作可以用 bulkWrite 打包，减少往返；ordered: false 时个别失败不影响其余，结果按位置返回。

写结果看 matchedCount、modifiedCount、upsertedCount。命中大于零而修改为零，说明条件对了但值没变，这是排查“更新没生效”的第一现场。

五、索引：单字段、复合与几种特殊索引

没有索引的查询就是集合扫描。几万文档时感觉不出来，几百万时一次扫描足以拖慢整个实例，索引应当和集合一起设计。

单字段索引适合按时间取列表。复合索引按字段顺序生效：{ userId: 1, createdAt: -1 } 服务“某用户最近的订单”，也能单独服务只带 userId 的查询，只查 createdAt 时用不上，这就是最左前缀。字段顺序按等值条件在前、范围与排序在后安排。

唯一索引把约束交给数据库，重复写入报 11000；稀疏索引只收录存在该字段的文档；TTL 索引定期删除过期文档，适合会话与验证码；文本索引支持 $text，但分词能力有限，复杂搜索仍应交给搜索引擎。

验证靠 explain("executionStats")：winningPlan 是 IXSCAN 还是 COLLSCAN，totalDocsExamined 与 nReturned 的比值是否接近 1。hint() 可以强制指定索引做对比，但长期依赖 hint，通常说明索引本身该改。

覆盖查询指条件与返回字段都在同一索引里、投影又排除 _id，服务端只读索引，totalDocsExamined 为 0；代价是索引变宽、写入变慢。索引也不是越多越好，每个索引都要占存储并在每次写入时维护，一个集合维持在五个以内通常够用。

六、Schema 设计：嵌入、引用与 16 MB 上限

建模先问嵌入还是引用，依据两条：数据是否总被一起读写，数组会不会无限增长。

一对少量适合嵌入，例如订单里的商品明细，读写都在一个文档内，原子性天然保证。一对多要分情况：用户有几千条订单，订单还要单独查询、单独改状态，就在订单文档里放 userId 引用；引用分散了增长压力，代价是二次查询或 $lookup。

多对多有两种存法：中间集合存两端 _id，适合关系本身带属性；双方各存引用数组，适合读多写少且数量可控。

硬约束是 16 MB 的文档上限。无界数组是最常见的坑：评论、日志直接 $push 进主文档，几个月后要么写失败，要么每次更新都在搬动整个文档。应另建集合按 parentId 存，主文档只留计数或最近几条。

原子性只在文档级别保证，跨文档要么用事务，要么在应用层做补偿与幂等；必须一起原子修改的数据，应尽量放进同一文档。

七、副本集基础：生产环境不要单机

单机 mongod 没有冗余，磁盘坏、进程崩都是停机；多文档事务与多数派写关注也依赖副本集，生产环境从第一天就该按副本集部署。

副本集是一组保存同一份数据的进程，primary 接受写，secondary 通过 oplog 持续拉取并重放。primary 失联时，剩余成员投票选出新 primary，驱动自动发现并重连，切换通常在数秒到数十秒之间。

flowchart LR
  A[应用与驱动] --> P[primary 接受写]
  P -->|oplog 复制| S1[secondary]
  P -->|oplog 复制| S2[secondary]
  A -.->|读偏好| S1

三个数据节点最常见。仲裁节点省机器但不存数据，能投票不能顶替，不建议作主力。内部认证用 keyFile，跨机房访问要启用 TLS。上线前应做一次手工切换演练，确认应用能在切换窗口内自动重连，而不是等真出事才发现驱动配置写错了。

读偏好决定查询发给谁：primary 保证读到最新写入，secondary 分摊读流量但可能读到旧数据，nearest 按网络延迟选择。写关注决定何时确认：w: 1 只等 primary，w: "majority" 要多数节点确认，加 j: true 才要求落 journal。订单类数据用多数派加 journal，日志类可以放宽。

九、运维、安全与常见坑

备份与导入导出

mongodump 做逻辑备份，配合 oplog 可以恢复到某个时间点；对生产实例执行时应连 secondary 并控制并发，避免把磁盘与网络打满。mongorestore 负责恢复，--gzip 能显著缩小体积。mongoexport 与 mongoimport 处理 JSON 或 CSV，适合数据交换，但不保存类型与索引，不能当备份用。

备份的价值在于能恢复，定期在独立环境跑一次恢复演练，比多存几份更有意义。

监控与慢查询

日常先看 db.serverStatus()：连接数是否逼近上限、opcounters 的读写曲线、WiredTiger 缓存是否吃紧。怀疑有长操作时用 db.currentOp() 过滤 secs_running。慢查询用 db.setProfilingLevel(1, { slowms: 100 }) 采集到 system.profile，分析时优先看是否 COLLSCAN、扫描量与返回量是否悬殊；profiler 有开销，排障后应调回 0。

安全

四件事按顺序做：启用认证并按角色授权，业务账号只给所需库的读写权限；节点间启用 keyFile，对外启用 TLS；bindIp 收紧到内网，防火墙只放行应用服务器；27017 绝不暴露公网。云主机安全组误开 27017 导致数据被清空的事故，几乎每年都有。

常见坑

  • 无界数组：评论、日志持续追加进主文档，最终撞上 16 MB 上限。
  • 缺索引：开发环境数据少，上线后全表扫描拖垮实例；索引过多同样拖慢写入。
  • 按关系模型建模：三张表原样搬成三个集合，再用应用层循环拼装。
  • 忽略写关注：单机 w: 1 就认为数据安全，切换时丢掉最近写入。
  • 没有备份演练：备份文件存在，但从没验证过能否恢复。
  • 深分页用大 skip：越翻越慢，应改用上一页最后一条的排序值做游标。

小结

MongoDB 的建模起点是“一次读写需要哪些数据”，嵌入与引用的取舍、文档大小与原子性边界都由此展开。它适合结构演化快、读取以文档为中心、需要水平扩展的场景，复杂事务与报表仍应留给关系库。落地时先把副本集、认证、备份和索引做对，再谈性能优化；聚合管道与分片集群分别涉及执行模型与数据分布，值得单独深入。
