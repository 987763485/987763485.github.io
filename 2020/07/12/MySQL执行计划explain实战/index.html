MySQL 执行计划 explain 实战

一条 SQL 变慢了，很多人的第一反应是加索引，但真正需要回答的问题是：优化器现在选了什么路径，为什么没有选另一条。EXPLAIN 就是回答这两个问题的入口。本文从各输出列的含义讲起，再过渡到 EXPLAIN ANALYZE 与优化器追踪，最后给出一套可以照着走的读计划顺序。示例基于 MySQL 5.7 与 8.0 共有的行为，涉及 8.0 专属功能时会单独标注。

EXPLAIN 报告的是计划，不是执行结果

很多人把 EXPLAIN 当成一张体检报告，看到 type 是 ALL 就断定语句有问题。严格说，它输出的只是优化器在当下统计信息基础上选定的一份执行计划，并没有真正执行 SQL，因此 rows 和 filtered 都是估算值。

优化器的工作可以粗略理解为：枚举可用的访问路径，包括走哪条索引、按什么顺序连接、是否使用临时表，然后用代价模型给每条路径打分，取分数最低的那条。代价主要由两部分构成，读取数据页的 IO 代价和处理行的 CPU 代价。统计信息来自对索引页的采样，采样本身有误差，数据分布一旦倾斜，估算就会偏离现实。

这带来两个实践结论。第一，读计划时要分清哪些字段是确定的，比如用了哪条索引、是否排序、连接顺序，哪些是估算的，比如行数和过滤比例。第二，怀疑估算失真时不能只盯着 EXPLAIN，还要用 EXPLAIN ANALYZE 拿到实际行数与耗时，两者对照才能定位问题。

输出列的骨架：id、select_type、table 与 partitions

EXPLAIN 的输出有十二列，初看很密，其实可以分成四组：定位查询块的 id、select_type、table、partitions，描述访问方式的 type、possible_keys、key、key_len、ref，给出规模估算的 rows、filtered，以及补充说明 Extra。

id 是查询块的编号。同一条语句里，id 相同表示属于同一个 SELECT 块，数字越大越先执行；子查询和派生表会分配新的 id。UNION 的汇总行比较特殊，id 显示为 NULL，table 列写成 <union1,2> 这样的形式，表示它合并的是 id 为 1 和 2 的两个块。

select_type 说明这个块的身份。SIMPLE 表示既没有子查询也没有 UNION；PRIMARY 是最外层；SUBQUERY 是子查询里的第一个 SELECT 且与外层无关；DEPENDENT SUBQUERY 则相关，外层每取一行它都要重新执行一次；DERIVED 是 FROM 子句里的派生表，通常会被物化成临时表；此外还有 UNION 和 UNION RESULT。排查时 DEPENDENT SUBQUERY 和 DERIVED 值得多看一眼，前者容易放大执行次数，后者意味着额外的物化开销。

table 列给出表名或别名，派生表显示为 <derived2>，尖括号里的数字指向生成它的 id。partitions 列只在分区表上有意义，显示本次实际访问的分区，未分区时为 NULL。

type：访问类型从好到差

type 描述单张表的访问方式，是整份计划里最常被引用的列。按通常的性能排序，从好到差大致是 system、const、eq_ref、ref、range、index、ALL，中间还可能插入 ref_or_null、index_merge，以及用于子查询的 unique_subquery 和 index_subquery。

system 表示表里只有一行，可以看作 const 的特例。const 表示通过主键或唯一索引最多命中一行，而且这一行在优化阶段就能确定，典型写法是按主键查单条记录。eq_ref 出现在连接中，被驱动表通过主键或唯一非空索引与驱动表逐行匹配，每行至多一条。ref 则是用普通索引或联合索引的最左前缀匹配，可能返回多行，这是业务查询里最常见也最健康的一种。

range 表示按索引做范围扫描，条件形如 BETWEEN、>、IN 或者前缀匹配的 LIKE。index 表示扫完整棵索引树，它虽然用到了索引，但读取量等于索引里的全部条目；如果索引不是覆盖索引，还要逐条回表，代价常常高于 range。ALL 是全表扫描，按聚簇索引的顺序把整张表读一遍。

需要强调的是，这个排序只在同等条件下成立。index 有时反而比 range 更好，因为它天然有序，可以省掉一次排序；ALL 在小表或者本来就要读取大部分数据时也完全合理。判断访问方式好坏，最终要结合 rows 和 filtered 一起看。

key 与 key_len：联合索引用到了第几列

possible_keys 列出优化器认为可能用上的索引，key 则是最终选中的那一条，两者不一致是常态，因为候选可以有很多，代价最低的只有一个。如果 possible_keys 为 NULL 而 key 不为 NULL，通常说明语句里没有可用的过滤条件，优化器为了走覆盖索引而挑了一条索引来扫。

key_len 是最容易被忽略、也最能说明问题的一列。它表示本次访问在索引里用掉的字节数，对联合索引而言，由此可以反推出用到了前几列。下面这张订单表有一个三列联合索引：

rows、filtered 与 Extra 里的信号

rows 是优化器估算的需要扫描的行数，注意是估算而不是实际值。它来自索引统计信息，InnoDB 默认只采样少量索引页，数据分布倾斜时误差可能很大。filtered 是百分比，表示这一层的条件过滤之后剩余行数的比例。两者相乘，才是传递给下一张表的行数估算，所以看到 rows 很大不必立刻慌张，真正要看的是 rows 乘以 filtered 之后的绝对值。

Extra 装的是补充信息，其中几项直接影响结论。Using index 表示查询涉及的列都在索引里，不需要回表，也就是覆盖索引；它和 type 为 index 是两回事，后者只说明扫了整棵索引。Using where 表示存储引擎返回行之后，Server 层还要再过滤一遍，说明索引没能承担全部过滤。Using index condition 是索引条件下推（ICP），部分 WHERE 条件下沉到存储引擎，在索引上先筛一遍再回表，能明显减少回表次数。

剩下的几项与排序、连接相关。Using filesort 表示需要额外排序，它不一定落盘，数据量小于排序缓冲区时在内存里完成，超出之后才归并到磁盘。Using temporary 表示使用了内部临时表，常见于 GROUP BY、DISTINCT 和 UNION，同样先走内存，超过上限才落盘。Using join buffer 表示被驱动表没有可用索引，只能用连接缓冲做块嵌套循环，8.0.18 起这里可能显示为 hash join。此外还有 Using MRR、Using union、Using intersect，分别对应多范围读和索引合并的不同形态。

从 JSON 到 ANALYZE：把估算变成实测

普通 EXPLAIN 是表格，信息有限。加上 FORMAT=JSON 能看到更多细节，包括每个访问路径的代价拆分、实际使用的索引列 used_key_parts，以及下推到存储引擎的条件 attached_condition。当需要确认联合索引到底用了几列时，used_key_parts 比推算 key_len 更直观。

8.0.16 起还支持 FORMAT=TREE，输出是一棵缩进的运算符树，读起来更接近执行流程，代价和估算行数也直接标在节点上。

需要提醒的是，EXPLAIN ANALYZE 会真实执行 SQL，用在 UPDATE 或 DELETE 上要格外谨慎，最好放在事务里回滚，或者先改写成等价的 SELECT 再分析。

优化器追踪：索引为什么被放弃

计划里最让人困惑的情形，是明明有索引却走了全表扫描。这时候需要看优化器的推理过程，MySQL 提供的 optimizer trace 就是干这个的：打开开关，执行语句，再把追踪结果读出来。

追踪结果是一段 JSON，重点看两块。rows_estimation 里的 potential_range_indexes 会列出每个索引是否可用以及估算行数，usable 为 false 时通常会在 cause 里写明原因，比如条件里对列用了函数、发生了隐式类型转换，或者最左前缀缺失。considered_execution_plans 则给出各个候选计划的代价，能看出优化器在几条路径之间如何取舍。

代价模型本身不复杂：一个计划的代价约等于读取数据页的 IO 代价加上处理行的 CPU 代价。走二级索引要先读索引页，再按主键回表读聚簇索引页，随机 IO 的单价更高；全表扫描按顺序读，页数虽多但单价低。当过滤后剩余的行占比很高时，回表的随机 IO 足以抵消索引带来的收益，优化器选择全表扫描就是理性的。这也是本文要强调的一点：全表扫描不一定是失误，可能只是当前数据分布下的最优解。追踪本身有开销，只在会话级别临时开启，排查完记得关闭。

实战：连接顺序、排序与 OR

连接查询的关键是驱动顺序。执行 SELECT o.id, u.name FROM t_order o JOIN t_user u ON o.user_id = u.id WHERE o.status = 1 时，如果 t_user 一侧是 eq_ref、t_order 一侧是 ref 或 ALL，说明优化器先扫 t_order 再逐行查 t_user。连接顺序不由书写顺序决定，而是按估算行数从小到大排列。若发现大表被选为驱动表，先检查统计信息是否过期，再考虑调整索引。

排序能否借力索引，看 Extra 里有没有 Using filesort。联合索引本身有序，当 WHERE 用等值条件固定了前面的列、ORDER BY 又恰好是索引的下一列时，可以直接按索引顺序读出。比如按 user_id 和 status 等值过滤、再按 created_at 排序，不会出现 filesort；一旦 ORDER BY 换成 amount，排序就无法避免。还有一个细节：排序方向必须一致，8.0 之前无法利用降序索引，混用升序和降序同样会触发 filesort。

OR 条件容易引发索引合并。执行 SELECT * FROM t_order WHERE user_id = 100 OR amount = 10.00 时，如果两列上各有一条索引，计划里的 type 会显示 index_merge，key 列出两条索引，Extra 显示 Using union。它的做法是分别用两条索引取出主键集合再求并集，代价可能低于全表扫描，也可能因为两次扫描加去重而更慢。若 OR 的一侧没有索引，整个条件通常退化为全表扫描，这时拆成两条语句再 UNION 往往更可控。

常见误读与读计划的顺序

几个反复出现的误读值得单独说明。rows 是估算值，不能拿来精确计算 IO；filtered 是百分比，不是行数；type 的排序只是经验法则，index 并不总优于 range，ALL 也不总代表错误；Using filesort 不等于磁盘排序，Using temporary 也不等于一定落盘；key 为 NULL 有时是合理选择，比如结果集很小，或者优化器判断走索引反而更贵。

落到操作上，可以按下面的顺序读一份计划。第一步看过滤条件有没有落到索引上，核对 key、key_len 与 Extra 里的 Using where；第二步看每张表的访问类型，确认没有意料之外的 ALL 或 index 全扫；第三步看排序与分组，确认 filesort 和临时表是否必要；第四步看连接顺序，确认驱动表足够小；第五步用 EXPLAIN ANALYZE 验证估算，估算与实际相差一个数量级时，先更新统计信息再谈改 SQL。

这个顺序背后的逻辑是一致的：先确认数据从哪里来、来了多少，再判断这些数据怎么被处理。跳过前面的步骤直接调索引，往往只是把问题挪到了下一个环节。

小结

EXPLAIN 展示的是优化器基于统计信息选出的计划，rows 和 filtered 都是估算，这决定了读计划必须与实测结合。各列可以分组记忆：id 与 select_type 定位查询块，type、key、key_len 描述访问路径，rows 与 filtered 描述规模，Extra 指出排序、临时表和条件下推等额外动作。5.7 上可以用 FORMAT=JSON，8.0 上还多了 TREE 与 ANALYZE，索引被放弃时则用 optimizer trace 找原因。把读计划固化成固定顺序，比记住某个 type 的好坏更有用。
