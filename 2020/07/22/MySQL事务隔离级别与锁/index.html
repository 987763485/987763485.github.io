MySQL 事务隔离级别与锁

同一条记录，在两个会话里可能读出不同的值；一条看起来只影响一行的 UPDATE，却可能把整段索引区间锁住，让别人的插入排队等待。本文从 ACID 出发，依次梳理四种隔离级别、MVCC 的可见性判断、快照读与当前读的区别，以及 InnoDB 的记录锁、间隙锁和临键锁，最后用两个会话的实操示例演示阻塞与死锁。示例基于 MySQL 5.7 与 8.0，两者在语法和监控表上有差异，文中会分别标注。

从 ACID 到四种隔离级别

ACID 是四个单词的缩写：原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability）。InnoDB 用 undo log 保证原子性，回滚时把已经做的修改逐条撤销；用 redo log 保证持久性，事务提交前先顺序写日志，崩溃重启后按日志重放。一致性是业务约束、唯一索引、外键共同达成的结果，数据库本身只能提供工具。真正可以调节的那个旋钮，是隔离性。

为什么隔离性需要取舍？因为数据库要同时服务很多事务。如果完全串行执行，隔离性最好，但吞吐量会跌到无法接受；如果完全放开，一个事务就能读到别人写到一半、最终还会回滚的中间状态，业务判断随之出错。隔离级别就是在这两端之间选一个位置，级别越高，一致性越强，并发度越低。

SQL 标准定义了三种典型的并发异常。第一是脏读：事务 B 读到了事务 A 尚未提交的修改，而 A 随后回滚，这个值等于从未存在过。第二是不可重复读：同一事务内两次读取同一行，结果不一样，因为期间别的事务修改并提交了。第三是幻读：同一事务内两次按相同条件查询，第二次多出或少了行，因为期间别的事务插入或删除了满足条件的记录。注意不可重复读针对的是同一行的值，幻读针对的是结果集的行数，这是两者最容易混淆的地方。

四种隔离级别对异常的处理如下表所示。

隔离级别 脏读 不可重复读 幻读
READ UNCOMMITTED 可能 可能 可能
READ COMMITTED 不可能 可能 可能
REPEATABLE READ 不可能 不可能 标准允许可能
SERIALIZABLE 不可能 不可能 不可能

READ UNCOMMITTED 基本只是理论存在，它的实现方式是读最新版本、完全不加判断，几乎没有业务会用它。SERIALIZABLE 会给普通 SELECT 隐式加上共享锁，让读也参与锁竞争，等价于把事务串行化，正确性最好但并发最差。工程上绝大多数系统在 READ COMMITTED（下称 RC）和 REPEATABLE READ（下称 RR）之间做选择。需要特别记住的是，MySQL 的默认级别是 RR，而 Oracle 与 PostgreSQL 的默认级别是 RC，从这两种数据库迁移过来的团队，经常因为这一处默认值差异遇到“本地好好的，线上却锁等待”的问题。

MySQL 的默认 REPEATABLE READ 与一致性快照

SQL 标准只要求 RR 禁止不可重复读，对幻读的态度是“允许发生”。InnoDB 的实现比标准更严格：普通 SELECT 走的是一致性快照读（consistent snapshot read），整个事务看到的是第一次读时建立的那份视图，别的事务后来插入的行根本不会进入这份视图，幻读也就无从发生。这就是很多人说“MySQL 的 RR 已经解决了幻读”的由来。

但这个说法只对了一半，需要加两个限定。第一，快照是在事务内第一次快照读时建立的，不是执行 BEGIN 的时刻。如果先 BEGIN，隔了很久才执行第一条 SELECT，那么这期间别人提交的数据仍然会出现在第一次查询里。第二，快照读不幻读，不等于 RR 完全消灭幻读。一旦事务里出现当前读，比如 UPDATE、DELETE 或加锁读，它会读到最新提交的数据并且给区间加锁；此后本事务再执行普通 SELECT，就可能看到刚刚被自己更新过的、原本由别的事务插入的行，因为这些行的版本已经属于本事务，对快照可见。

经典复现步骤是这样的：事务 A 执行 SELECT 得到空集；事务 B 插入一行并提交；事务 A 执行 UPDATE 该条件，当前读命中了 B 插入的行并把它改成自己的版本；事务 A 再执行一次 SELECT，这一行就出现了。第一次没有、第二次有，形式上就是幻读。所以更准确的说法是：InnoDB 在 RR 下用一致性快照消除了“快照读的幻读”，用间隙锁消除了“当前读的幻读”，但两者的组合仍可能暴露新的行。理解这一点，比记住一句结论更有用。

MVCC：undo 版本链与 Read View

一致性快照读能成立，靠的是多版本并发控制（Multi-Version Concurrency Control，MVCC）。它让“读”和“写”不必互相阻塞：写操作生成新版本，读操作按照自己的视图去挑一个旧版本，双方各走各的路。

先看行记录的物理结构。InnoDB 的每一行除了业务字段，还有几个隐藏列：DB_TRX_ID 记录最后一次修改该行的事务 ID，DB_ROLL_PTR 指向 undo log 中上一个版本的地址，DB_ROW_ID 在没有主键时生成的行号。更新一行时，InnoDB 不会原地覆盖旧值，而是把旧版本写入 undo log，再让新版本的 ROLL_PTR 指向它。多次更新就串成一条版本链，链头是最新版本，链尾是最老的版本。删除也类似，只是给记录打一个删除标记，真正的物理清理交给后台线程。

有了版本链，还需要一套规则来决定“我现在应该看哪个版本”，这套规则的数据结构就是 Read View。它包含四个关键字段：

  • m_ids：创建视图时仍在活跃、尚未提交的读写事务 ID 列表；
  • min_trx_id：m_ids 中的最小值，比它小的事务一定已经提交；
  • max_trx_id：创建视图时系统即将分配的下一个事务 ID，不小于它的事务在视图创建之后才开始；
  • creator_trx_id：创建这个视图的事务自己的 ID。

判断某个版本是否可见，按下面的顺序走：如果版本的 trx_id 等于 creator_trx_id，说明是自己改的，可见；如果小于 min_trx_id，说明在视图创建前就已经提交，可见；如果大于等于 max_trx_id，说明这个事务在视图创建后才开始，不可见；如果落在两者之间，就看它是否出现在 m_ids 里，在说明当时还活跃，不可见，不在说明已经提交，可见。遇到不可见的版本，就顺着 ROLL_PTR 往链尾找，对下一个版本重复同样的判断，直到找到可见版本，或者走到链尾仍没有合适版本。这个过程可以概括为下图。

flowchart TD
  A[取版本链上的版本] --> B{trx_id 等于 creator_trx_id}
  B -->|是| V[可见]
  B -->|否| C{trx_id 小于 min_trx_id}
  C -->|是| V
  C -->|否| D{trx_id 大于等于 max_trx_id}
  D -->|是| N[不可见]
  D -->|否| E{trx_id 在 m_ids 中}
  E -->|是| N
  E -->|否| V
  N --> F[沿 ROLL_PTR 取下一个版本]
  F --> A

RC 和 RR 在 MVCC 上的唯一差别，就是 Read View 的创建时机。RC 下每一条 SELECT 都会新建一个视图，所以同一事务里两次查询能看到别人在这期间新提交的数据，不可重复读因此发生；RR 下只在事务内第一次快照读时建一个视图，之后一直复用，所以两次查询结果一致。这也解释了一个常见现象：在 RR 的事务里执行 UPDATE 之后，再 SELECT 能看到自己刚才的修改，因为被改过的版本 trx_id 等于 creator_trx_id，规则第一条就放行了。

版本链不会无限增长。delete 只是打标记，purge 线程负责在合适的时机把已删除的记录和不再需要的 undo 日志真正清理掉。判断“不再需要”的依据是：没有任何活跃的 Read View 还需要看到那些旧版本。反过来说，一个开了很久却没有提交的事务，会一直拖住 purge，undo 表空间持续膨胀，History list length 只涨不降，最终拖慢整个实例。这是“事务要尽量短”最硬的技术理由，比任何编码规范都更有说服力。

快照读与当前读

不是所有的读都走 MVCC。MySQL 把读分成两类，分清这两类，很多“同样的 SQL 结果不一样”的疑惑就解开了。

快照读（snapshot read）指普通的 SELECT，它根据 Read View 去版本链上挑一个历史版本，不加任何锁，因此不会阻塞别人，也不会被别人阻塞。当前读（current read）指读取最新提交的版本，并且必须加锁，保证读到的行在事务结束前不被人改掉。属于当前读的语句有：

  • SELECT … FOR UPDATE：加排他锁，常用于“先查出来再修改”的场景；
  • SELECT … LOCK IN SHARE MODE：加共享锁，8.0 增加了等价写法 FOR SHARE，旧写法仍然可用但已不推荐；
  • UPDATE 与 DELETE：先按条件定位行，这一步本身就是当前读，然后再修改；
  • INSERT：插入也要读索引判断唯一性冲突，同样属于当前读语义。

两类读混用会带来一个典型陷阱。事务里先执行普通 SELECT 做业务检查，再执行 SELECT … FOR UPDATE 去锁定并更新，两次结果可能不一样：前者是快照，后者是最新数据。如果检查依据的是快照，而更新依据的是最新数据，那么“检查通过”这个结论在更新时可能已经不成立。正确的做法是让检查本身就用加锁读，把检查和修改放进同一把锁的保护范围，消除中间窗口。这就是常说的 check-then-act 竞态，在库存扣减、余额判断这类场景里尤其常见。

InnoDB 的锁：从记录锁到临键锁

InnoDB 的行锁加在索引记录上，不是加在物理行上。这是理解后面所有锁现象的前提：WHERE 条件没有走索引时，InnoDB 只能全表扫描，扫到的每条记录都要加锁，效果接近锁表。

  • 记录锁（Record Lock）：锁住单条索引记录。
  • 间隙锁（Gap Lock）：锁住两条记录之间的开区间，只阻止插入；间隙锁之间互相兼容。
  • 临键锁（Next-Key Lock）：记录锁加上它前面的间隙，区间左开右闭，是 RR 下的默认加锁单位。
  • 插入意向锁（Insert Intention Lock）：INSERT 前在目标间隙设置的标记，与被占用的间隙锁冲突，插入因此等待。
  • 意向锁（Intention Lock）：表级 IS/IX，表示事务打算在行上加共享锁或排他锁，让表锁不必逐行检查；意向锁之间不冲突。

RR 与 RC 的差别集中在间隙：RC 下除外键检查和唯一键冲突检查，间隙锁关闭，临键锁退化为记录锁，锁范围小、并发高，代价是幻读。唯一索引等值命中时，RR 下的临键锁也退化为记录锁，不必锁间隙；记录不存在时则锁住它所在的间隙。非唯一索引没有这个优化，命中记录和它前面的间隙都要锁，还会向右延伸到第一个不满足条件的记录，防止区间内被插入。

InnoDB 默认开启 innodb_deadlock_detect，检测到环后回滚代价较小的事务，报 ERROR 1213；关闭检测时只能等 innodb_lock_wait_timeout（默认 50 秒）超时，报 ERROR 1205。SHOW ENGINE INNODB STATUS 的 LATEST DETECTED DEADLOCK 段会列出两个事务各持有什么、等待什么，以及最终回滚了谁。预防无非三条：固定加锁顺序、事务写短、补齐索引；高并发下检测本身耗 CPU，可以关闭检测并让应用捕获 1213 重试。

监控

8.0 用 performance_schema.data_locks 与 data_lock_waits 查看锁和等待关系；5.7 没有这两张表，只能用 information_schema.INNODB_LOCKS 与 INNODB_LOCK_WAITS（8.0 已移除），且仅在发生等待时才有数据。INNODB_TRX 看 trx_started 与 trx_state，SHOW PROCESSLIST 看连接在做什么，两者配合即可定位谁锁了谁。

常见坑

长事务拖住 purge 造成 undo 膨胀；DDL 等语句隐式提交切断事务；缺索引让行锁扩散成表锁；该用 RC 却守着 RR；热点行等待占满连接池，表现为整站变慢。

小结

隔离级别决定可见性，锁决定并发行为，两者在 InnoDB 里由 MVCC 与索引锁协同完成。RR 用一个 Read View 保证可重复读，用间隙锁压制当前读的幻读；RC 放弃间隙锁换取并发，代价是幻读。排查锁问题，先分清快照读与当前读，再看锁加在哪个索引上，最后用 INNODB_TRX 与锁等待视图找到持有者。事务尽量短、访问顺序固定、条件走索引，这三条能消掉大部分死锁。
