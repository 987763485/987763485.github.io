Kafka 消息队列入门实战

Kafka 常被归到“消息队列”里，但它的内核是一条可分割、可复制的追加日志，很多参数与坑都源于这个设计。本文从数据模型讲起，依次说明集群副本、生产者的批处理与确认、消费者的位移与再均衡，再落到投递语义和分区规划，最后用 Docker 单机环境和 Spring Boot 示例走一遍收发流程。读者读完应当能独立搭起实验环境，看懂 acks、min.insync.replicas、max.poll.interval.ms 这些配置在保护什么，并知道分区数该怎么估。

从一条追加日志说起

Kafka 把消息存成日志：新消息只会追加到文件末尾，已有位置不会被改写。日志在物理上被切成若干个分区（partition），每个分区内部按写入顺序编号，这个编号就是偏移量（offset）。offset 只在单个分区内单调递增，跨分区没有可比性。

分区之上是主题（topic），它只是一个逻辑名字，用来把同一类消息归在一起。创建一个 3 分区的主题，实际上是在集群里建了 3 条独立的日志，它们可以落在不同的 broker 上，从而并行写入、并行读取。因此我们说 Kafka 的并行度单位是分区，不是主题。

flowchart LR

    T1 --> PA[partition 0]
    T1 --> PB[partition 1]
    T1 --> PC[partition 2]

    PB --> C2[消费者 B]
    PC --> C2

消费不会删除消息。消息能留多久由保留策略决定：retention.ms 默认 7 天，retention.bytes 默认不限；只要没到期，同一个 offset 可以被反复读取，也可以被另一个消费组从头读。这与“出队即删除”的传统队列有本质区别——队列的语义是任务分发，Kafka 的语义是一份可重放的日志，下游按自己的进度取用。

取用方式是拉（pull）。broker 不记录“谁读到了哪里”，消费者自己维护进度并定期提交。拉模型让消费者可以按处理能力控制节奏，代价是空闲时会有少量空转请求，Kafka 用 fetch.max.wait.ms 把空转请求挂起一会儿来缓解。

集群解剖：broker、副本与 ISR

一个 broker 就是一个 Kafka 进程，通常一台机器跑一个。客户端配置 bootstrap.servers 只是用来获取元数据，连上任意一个节点后，它会被告知每个分区的 leader 在哪，之后直接和 leader 通信。所以 bootstrap 列表不必写全，但写两三个可以避免单点。

集群里有一个 broker 兼任控制器（controller），负责分区 leader 的选举和副本分配。2020 年前后这一角色依赖 ZooKeeper 完成选主和元数据存储，运维上通常把 ZooKeeper 独立成 3 节点的小集群。

每个分区有 1 个 leader 和若干 follower，副本总数即副本因子（replication factor）。生产和消费都只与 leader 交互，follower 主动向 leader 拉取数据做备份。副本因子为 3 时，任意一台 broker 宕机，分区仍有 2 份数据。

与 leader 保持同步的副本集合叫 ISR（in-sync replicas）。落后太多或长时间不联系的副本会被踢出 ISR，判断依据是 replica.lag.time.max.ms。leader 故障时，控制器只从 ISR 中选新 leader，这样不会丢失已确认的消息；如果 ISR 空了又允许非同步副本当选，就会丢数据，所以 unclean.leader.election.enable 默认是 false。

写入确认由两个参数共同决定。生产者的 acks=all 表示 leader 要等 ISR 中所有副本写完才回确认；broker 的 min.insync.replicas=2 表示 ISR 少于 2 个时直接拒绝写入，抛出 NotEnoughReplicasException。两者配合的含义是：宁可写失败，也不接受只有一份的数据。副本因子 3、min.insync.replicas=2、acks=all 是常见组合，它允许坏一台 broker 而不丢数据，也允许坏两台时停止写入而不是降级。

生产者：分区、批量与确认

生产者发送一条消息，要回答三个问题：去哪个分区、什么时候真正发出去、发出去算不算成功。

分区选择由分区器完成。指定了 key 时，默认分区器对 key 做 murmur2 哈希后对分区数取模，相同 key 永远落在同一分区；key 为空时，早期版本是轮询，2.4 之后改成粘性分区——先随机挑一个分区，把批次攒满再换下一个，牺牲一点均衡换取更大的批。

批量与压缩是吞吐的主要来源。batch.size 控制单个批次的上限（默认 16 KB），linger.ms 控制“没攒满也等一会儿”的时间（默认 0，即立刻发）。把 linger.ms 调到 20 毫秒、batch.size 调到 64 KB，通常能显著提高压缩率和网络利用率，代价是最多 20 毫秒的额外延迟。压缩算法可选 gzip、snappy、lz4、zstd，其中 lz4 在压缩比和 CPU 开销之间比较均衡。

acks 决定确认的含义：0 表示发出去就不管，断开连接也无从得知；1 表示 leader 落盘即返回，leader 在复制完成前宕机可能丢；all 表示等 ISR 全部确认。2.5 版本的默认值是 1，这在生产环境是不够的，需要显式改成 all，并配上前面说的 min.insync.replicas。

重试会带来重复，也会带来乱序：一批消息重试时，后面的批次可能已经写进去了。Kafka 2.5 的幂等生产者用 producer id 加分区级序列号在 broker 侧去重，可以解决单分区、单会话内的重复与乱序，但它默认关闭，需要显式设置 enable.idempotence=true。开启后客户端会强制要求 acks=all、retries>0，且 max.in.flight.requests.per.connection 不超过 5；这几项冲突时会直接报配置错误，算是把约束前置了。

异步发送加回调是常规写法，回调里拿到分区和 offset 便于排查。注意 send 返回的 Future 如果一直不取，异常只会出现在回调里，不会抛到主线程，因此日志和告警要落在回调中。进程退出前必须 flush() 再 close()，否则缓冲区里的批次会丢。

消费者：消费组、位移与再均衡

消费者用 group.id 标识自己属于哪个消费组。同一条消息在同一个组内只会被一个消费者处理，不同组各自独立消费全量。

组内的分区分配由组协调者负责。一个分区在同一时刻只能属于组内一个消费者，所以消费者数量超过分区数时，多出来的实例会空闲。分配策略有 Range、RoundRobin、Sticky 几种，2.4 起还引入了协作式再均衡（cooperative rebalance），可以把一次全量停顿拆成几轮增量调整；示例仍用默认策略，行为更好预期。

位移提交是最容易出事的地方。enable.auto.commit 默认是 true，客户端每 auto.commit.interval.ms（默认 5 秒）在 poll 时顺手提交一次。问题在于提交的时机与业务处理无关：消息刚拉下来就提交了位移，处理到一半进程崩溃，重启后从新位移继续，那批消息就永远丢了。手动提交把顺序反过来——先处理成功，再 commitSync，进程崩溃最多重复处理，不会丢。

max.poll.records 与 max.poll.interval.ms 是一对。消费者两次 poll 的间隔超过后者（默认 5 分钟），就会被认为失联并踢出组，触发再均衡，这一批没提交的位移全部作废，消息会被重新投递。单条处理耗时 1 秒、一轮拉 500 条，就是 500 秒，必然超时——这是“消费变慢后疯狂再均衡”的典型成因。要么调小 max.poll.records，要么把耗时操作异步化，但要自己保证位移在处理完成后再提交。

再均衡期间分区会在实例间迁移，消费基本停摆。session.timeout.ms（默认 10 秒）决定失联判定，heartbeat.interval.ms（默认 3 秒）是心跳频率，心跳由独立线程发送，所以业务线程卡住时心跳仍在，真正触发踢出的是 max.poll.interval.ms 而不是心跳超时。

投递语义、幂等消费与分区规划

三种语义的边界

把提交位移与业务处理的先后顺序组合起来，就得到两种常见语义：先处理再提交是至少一次（at-least-once），先提交再处理是至多一次（at-most-once）。绝大多数业务选前者，重复由下游消化。想更进一步，生产侧可以开启事务：设置 transactional.id，用 initTransactions、beginTransaction、sendOffsetsToTransaction、commitTransaction 把“读 Kafka、写 Kafka、提交消费位移”打包成一个原子操作，实现读-处理-写的恰好一次。

但必须说清楚边界：这套事务只在 Kafka 内部闭环，一旦处理过程中要写 MySQL，事务就管不到了。所谓“恰好一次”从来不是打开一个开关，而是端到端设计出来的。

幂等消费：去重键与 outbox

工程上的做法是让重复投递无害。给每条消息一个业务上唯一的键，比如订单号加事件类型，消费端建一张去重表或在业务表上建唯一索引，处理与写库放在同一个本地事务里，重复消息会在唯一约束上失败并被直接丢弃。这要求事件的标识在重试、重放时保持不变，所以不要用随机 UUID 充当业务键。

如果还要保证“数据库写成功”和“消息发出去”同时成立，可以用 outbox：在同一个本地事务里写业务表和一张 outbox 表，再由独立的投递线程扫描 outbox 发往 Kafka，发送成功才标记。数据库事务保证了这两行同生共死，消息最多重发，靠上面的去重键兜底。这个模式不依赖 Kafka 事务，跨库场景更实用。

顺序与热点分区

顺序只在分区内成立，这是设计时最先要接受的约束。需要按订单有序，就把订单号作为 key；需要全局有序，只能用一个分区，吞吐也就锁死了。按用户维度有序是常见折中：key 用用户 ID，用户内部有序，用户之间并行。

key 分布不均是另一个问题。如果按城市做 key，一线城市的流量会把某个分区打满，其他分区闲着，这就是热点分区。缓解手段是给 key 加后缀拆成多个子 key（牺牲该维度内的顺序），或者把大 key 拆成独立主题单独扩容。

分区数只能增不能减，扩容时 key 到分区的映射会整体变化，原本同 key 的消息可能落到新分区，顺序保证随之失效，所以宁可一开始估足。估算方式是目标写入吞吐除以单分区能力，再留一倍余量。假设单分区能稳定写入 10 MB/s，目标峰值 100 MB/s，至少需要 10 个分区；这些数字只是示例假设，实际要压测。反过来说，分区也不是越多越好：每个分区在 broker 上是一组文件句柄，分区越多，leader 选举与再均衡越慢，端到端延迟也会上升，副本同步的负担同样按分区数放大。

实战：Docker 单机环境与 Spring Boot 收发

本地实验用 Docker 19.03 起一个 ZooKeeper 加一个 broker 就够了。镜像选 Confluent 的 5.5.0 版本，它对应 Kafka 2.5。

advertised.listeners 是新手最容易踩的坑。broker 启动时会把自己注册到 ZooKeeper，客户端连上 bootstrap 地址后，拿到的就是这个注册地址。如果写成容器内的 kafka:9092，宿主机上的客户端能完成第一次握手，随后一直连不上 leader，表现为超时而不是明确的连接拒绝。单机环境下写 localhost:9092，跨机部署则要写对外可达的域名或 IP。

主题建议显式创建，不要依赖自动建主题，因为自动创建的分区数和副本因子由 broker 默认值决定，往往是 1 分区 1 副本。

运维监控与常见坑

日常盯三个指标就够了。消费者延迟（lag）等于分区末端位移减去已提交位移，用 kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group order-worker 能看到每个分区的差值，持续上涨说明消费能力跟不上写入。副本同步情况用 kafka-topics.sh --describe --under-replicated-partitions 查看，ISR 缩水通常意味着 broker 负载过高、网络抖动或磁盘写满。磁盘则看 retention.ms 与 retention.bytes 是否被撑爆，注意保留策略按日志段（segment）删除，segment.bytes 默认 1 GB，清理线程默认每 5 分钟跑一次，所以空间释放会有延迟，磁盘水位要留出余量。

备份这件事要纠正一个直觉：Kafka 的可靠性来自副本，不是文件备份。直接拷贝 log.dirs 得不到一致快照，恢复时 offset 与索引也可能对不上。跨机房容灾的正确做法是副本跨机架放置，或使用 2.4 引入的 MirrorMaker 2 做集群间复制。

常见的坑可以归成几条：分区数按“够用就好”来给，事后扩容会破坏 key 的映射；key 选得太粗导致热点；开着自动提交却在处理失败时抛异常，消息静默丢失；单轮处理时间过长引发反复再均衡；积压没有告警，等发现时已经追不上；以及毒消息在某分区反复重投，卡死整个分区——这类消息应当限制重试次数后转入死信主题，而不是无限重试。

小结

Kafka 的本质是可分区、可复制的追加日志，offset 与保留策略共同决定了它“可重放”的性格。生产端要同时管好分区键、攒批参数和 acks=all 加幂等，消费端要管好手动提交与 max.poll.interval.ms。顺序性只在分区内成立，分区数在创建时就该估足。所谓恰好一次不是配置项，而是去重键、唯一约束与 outbox 这类端到端设计的结果。最后，副本给的是可用性，监控 lag 与 ISR 才能提前发现问题。
