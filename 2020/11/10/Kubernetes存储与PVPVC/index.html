Kubernetes 存储与 PV/PVC

本文属于《Docker 与 Kubernetes》第 23/51 篇
上一篇系列目录下一篇

容器里写的文件，容器一重启就没了，这是很多团队第一次在 Kubernetes 上跑有状态服务时遇到的第一个问题。本文从容器文件系统的生命周期讲起，先梳理 emptyDir、hostPath、网络存储这些常用卷，再重点解释 PV、PVC 与 StorageClass 之间的绑定关系，最后给出一份可以落地的清单和一套排障顺序。阅读本文需要了解 Pod 与 Deployment 的基本用法。

容器的文件系统与 Volume 类型

可写层跟着容器一起消失

镜像由若干只读层叠加而成，容器启动时在最上面加一个可写层，进程所有的写操作都落在这里。这个可写层与容器同生命周期：进程退出、kubelet 重建容器，可写层被丢弃；Pod 被删除或漂移到其他节点，数据同样不复存在。所以容器适合跑无状态进程，任何需要跨重启保留的东西都要放到容器之外。

Kubernetes 用卷（Volume）解决这个问题。卷声明在 Pod 级别，由容器挂载，生命周期可以比容器长，也可以比 Pod 长。按“数据能活多久”分三档：跟容器走的是可写层，跟 Pod 走的是 emptyDir，独立于 Pod 存在的是 hostPath、网络存储和 PV。

emptyDir 与 hostPath

emptyDir 在 Pod 调度到节点时创建，Pod 离开节点时删除；期间容器重启多少次，数据都还在。它有三种典型用法：当临时目录（编译中间产物、上传缓冲），当可重建的本地缓存，以及在多个容器之间交换文件，例如主容器写日志、sidecar 读取后转发。把 emptyDir.medium 设为 Memory，卷落在 tmpfs 上，读写快但占内存，节点重启即失；配合 sizeLimit 能防止临时文件写满节点磁盘。要记住它仍然不是持久存储，Pod 一删就没了。

hostPath 直接把节点上的路径挂进容器，数据留在节点磁盘，Pod 重建后还在。问题在于数据与节点绑定：Pod 换节点就读不到；容器往往对宿主目录有写权限，等于绕过隔离；不同节点的目录内容还可能不一致。合理的用途是读取节点自身的信息，例如 /var/log、/proc 或设备文件，配合 DaemonSet 做日志采集与监控代理；拿它存业务数据，等于把持久化交给了调度器的随机性。

配置卷与网络存储

配置类卷有 configMap 与 secret，把键值对以文件形式挂进容器，适合配置文件、证书和密钥。kubelet 会周期性同步更新，通常有几十秒延迟；挂载时用了 subPath 的文件不会跟着更新，只能重建 Pod。数据库的数据文件显然不属于这一类。

持久化的主力是网络存储。NFS 是最常见的自建方案：多节点可同时挂载，天然支持多 Pod 读写，运维也简单；代价是性能和可用性都压在 NFS 服务器上，它一停，所有挂载它的 Pod 都会卡住。云厂商的块存储只能挂到一台主机，适合数据库这类单写场景，而且盘与可用区绑定，跨区调度会失败；文件存储提供共享语义，适合多副本读写同一目录。这些实现如今基本通过 CSI 驱动接入，驱动的注册与调用属于架构篇的话题，从使用者角度只需知道 StorageClass 的 provisioner 指向某个驱动。

类型 典型用途 多节点共享 数据位置
emptyDir 临时文件、缓存、容器间交换 否 节点本地
hostPath 读取节点日志、设备文件 否 节点本地
configMap/secret 配置文件、证书 是（只读） etcd 与节点缓存
NFS 共享文件、多副本读写 是 网络存储
云盘 数据库等单写场景 否 云存储

选型可以先简化成一句话：能无状态就无状态；必须落盘且只被一个 Pod 使用的用块存储；多个 Pod 要共享同一份文件的用文件存储或 NFS；只是临时中转的用 emptyDir。

PV 与 PVC：把供给与申请分开

emptyDir 和 hostPath 都是“随 Pod 定义”的卷：用户自己写卷类型，也自己承担后果。集群规模一大，这种方式就难以管理：管理员不知道谁在用哪块盘，开发者也不该关心后端是 NFS 还是云盘。PV 与 PVC 就是把这两种角色分开的抽象。

PV（PersistentVolume）是集群级别的资源，描述一块具体的存储：容量、访问模式、后端类型、回收策略。它不属于任何命名空间，由管理员创建，或者由 StorageClass 自动创建。PVC（PersistentVolumeClaim）是命名空间级别的申请，用户只写“我要多大、怎么挂”，不写后端细节。两者按规则配对绑定，绑定关系是一对一的：一块 PV 在同一时间只能被一个 PVC 占用。

一个 PVC 的核心字段不多：

storage 是申请量而不是配额上限，PV 的容量大于等于它即可；文件系统层面并不会因此限制写入，超用仍可能写满后端。

访问模式描述的是挂载语义，不是文件系统权限：ReadWriteOnce（RWO）允许被单个节点以读写方式挂载；ReadOnlyMany（ROX）允许多个节点只读挂载；ReadWriteMany（RWX）允许多个节点读写挂载。RWO 的“单节点”常被误解成“单 Pod”：同一节点上的多个 Pod 挂同一个 RWO 卷通常没问题，跨节点就会冲突。社区还在讨论粒度更细的 ReadWriteOncePod（RWOP），语义是只允许一个 Pod 挂载，截至 1.19 尚无可用实现，选型时不要依赖它。某个卷到底支持哪几种模式，取决于后端：NFS 通常三种都行，云盘一般只有 RWO。

回收策略决定 PVC 释放后 PV 怎么处理。Retain 保留 PV 与数据，PV 进入 Released 状态，需要管理员手动清理后才能再次使用；Delete 让供给器连后端存储一起删除；Recycle 只做简单的清除，早已废弃，不要在新集群里使用。状态方面，PV 有 Available、Bound、Released、Failed 四个阶段，PVC 有 Pending、Bound、Lost 三个阶段，排障时先看这两个字段，比翻日志快得多。

静态供给：绑定是怎么发生的

静态供给指管理员预先创建 PV，PVC 提交后由控制面挑一块合适的绑上去。匹配要同时满足几个条件：容量不小于申请量，访问模式覆盖 PVC 的要求，两者的 storageClassName 相同，volumeMode 一致；如果 PVC 写了 selector，PV 的标签还要匹配。满足条件的有多块时，控制器选容量最小的一块，避免浪费大卷。

对应的 PVC 把 storageClassName 写成 manual；要限定具体某块盘，可以加 selector.matchLabels；也可以用 PV 的 claimRef 预先指定它只服务某个命名空间里的某个 PVC，迁移和保留盘时很有用。

PVC 一直 Pending，常见原因有四类：集群里没有满足条件的 PV；指定的 StorageClass 不存在；PVC 的 storageClassName 为空而集群又没有无类的 PV；selector 没有匹配到任何标签。执行 kubectl describe pvc 看 Events，通常会直接写出 no persistent volumes available 或 storageclass not found。还有一类 Pending 与调度有关，下一节讲。

动态供给：StorageClass 与 provisioner

手工建 PV 在云上不现实：每次申请都要管理员介入，盘的类型与区域也难以预先枚举。动态供给让 PVC 提交时自动创建 PV，靠的是 StorageClass。provisioner 指定由哪个插件造卷，parameters 传给它（磁盘类型、副本数、文件系统等），reclaimPolicy 决定新建 PV 的回收策略，默认是 Delete。

有两个字段值得单独说。volumeBindingMode 控制何时真正创建并绑定卷：Immediate 是默认值，PVC 一创建就分配 PV，不等 Pod，对 NFS 没问题，但对云盘和本地盘可能出事——先绑定的盘在 A 可用区，Pod 后来被调度到 B 区，就永远起不来。WaitForFirstConsumer 把绑定推迟到有 Pod 使用这个 PVC 时，调度器先选节点，再在节点所在区域创建卷。它在 1.17 进入 beta，1.19 可以放心使用，用本地盘时基本是必选项。

allowVolumeExpansion 打开后，改大 PVC 的 requests.storage 就能触发扩容。它只能增不能减，底层驱动必须支持，部分场景要重启 Pod 才能完成文件系统扩展。

默认 StorageClass 用注解 storageclass.kubernetes.io/is-default-class: "true" 标记，集群里最好只设一个。PVC 不写 storageClassName 会被填入默认类；显式写空字符串则表示只要无类 PV，两种写法效果完全不同，是常见的踩坑点。

在 Pod 中使用 PVC 与 StatefulSet

PVC 绑定成功后，Pod 通过 persistentVolumeClaim 类型的卷引用它，readOnly 只影响这一次挂载，不会改变 PVC 的访问模式：

多个 Pod 引用同一个 PVC 时，调度器不会因为卷是 RWO 就把它们放到同一个节点：两个副本分到不同节点，挂的却是 RWO 云盘，第二个就会因为 multi-attach 卡在 ContainerCreating。Deployment 尤其容易撞上，因为副本本来就要分散。要么改用支持 RWX 的后端，要么让每个副本有自己的 PVC。local 类型的 PV 还有一层约束：卷绑定了节点，Pod 必须调度到那个节点，PV 上的 nodeAffinity 会变成调度约束，配合 WaitForFirstConsumer 才能正常工作；如果 PVC 已经 Immediate 绑定而节点资源又不够，Pod 就会一直 Pending。

StatefulSet 的做法是给每个副本固定的名字（如 web-0、web-1），并用 volumeClaimTemplates 为每个副本生成独立的 PVC，命名规则是“模板名-StatefulSet 名-序号”。副本重建或被重新调度后仍挂回自己那块盘，这是稳定身份在存储上的体现。

StatefulSet 默认按序号从 0 到 N-1 依次创建，前一个 Ready 才创建下一个，删除时倒序；一个副本卡住会拖住后面所有副本，必要时可用 podManagementPolicy: Parallel 放宽。配套的无头 Service 提供稳定 DNS 名称，这部分在概念篇已经讲过。需要强调：StatefulSet 只解决身份与存储的稳定，不解决数据库本身的高可用，主从切换、脑裂与备份仍要靠数据库自身的机制。

运维、排障与常见坑

扩容是最常用的操作：改大 PVC 的 requests.storage 后，PVC 会进入 Resizing 状态，供给器扩后端卷，文件系统随后扩展；前提是 StorageClass 开了 allowVolumeExpansion，缩小请求会被 apiserver 直接拒绝。如果状态停在 FileSystemResizePending，通常重启一次 Pod 就能触发文件系统扩容，之后再看容量是否生效。

备份不能只靠 PV。Retain 只表示不删，不代表数据可恢复，误删文件、逻辑损坏同样会发生。常见做法是用 Velero 这类工具把命名空间内的对象与卷内容定期备份到对象存储，并做恢复演练；数据库还应叠加自身的逻辑备份与 binlog。卷快照在 1.19 仍是 beta，由 VolumeSnapshotClass、VolumeSnapshot、VolumeSnapshotContent 三个 CRD 组成，需要驱动支持，恢复时在 PVC 里用 dataSource 指向快照；它适合快速回滚，不能替代跨集群备份。

排障可以按一条固定顺序走：

  1. 看 PVC：kubectl describe pvc，Pending 多半是没有匹配的 PV、StorageClass 名字写错，或者 WaitForFirstConsumer 在等 Pod。
  2. 看 Pod：Pending 且 Events 提到 node affinity 或 volume node affinity conflict，说明卷被绑在了别的节点或可用区。
  3. 看挂载：长时间 ContainerCreating，describe pod 里常见 multi-attach error（RWO 卷被两个节点同时挂）或 mount failed（NFS 不可达、路径不存在）。
  4. 看权限：容器以非 root 运行而卷目录属主是 root，会报 Permission denied，用 fsGroup 或初始化容器改属主。
  5. 看回收：PV 处于 Released 后新 PVC 仍然 Pending，是因为 claimRef 还占着，需要手工清理。

几个反复出现的坑值得单独列出：生产环境用 hostPath 存业务数据；把重要数据的回收策略设成 Delete，删 PVC 时连盘一起没了；以为所有后端都支持 RWX，结果多副本挂不上；驱动不支持扩容却直接改 PVC；没有备份就删命名空间，而命名空间删除会连带删 PVC，PVC 删除又触发回收策略，一条命令可能带走全部数据。迁移数据时，先建新 PV 与新 PVC，用临时 Pod 把数据拷过去，确认无误后再切换工作负载；要保留旧卷，先把 PV 的回收策略改成 Retain 再删 PVC。删除顺序上，先确认备份，再删工作负载，最后删 PVC；只删 PVC 时，PV 会按回收策略进入 Released 或被直接删除，这一点务必提前确认。另外，正在被 Pod 使用的 PVC 会被 pvc-protection 终结器挡住，执行删除后会长时间停在 Terminating，需要先删掉使用它的工作负载。

小结

容器的可写层随容器消失，emptyDir 随 Pod 消失，只有 PV 这类独立于 Pod 的资源能跨重启、跨节点保留数据。PV 是管理员视角的存储资源，PVC 是用户视角的申请，二者按容量、访问模式、StorageClass 与标签绑定；StorageClass 把绑定自动化，WaitForFirstConsumer 解决了拓扑受限存储的调度错配。StatefulSet 用 volumeClaimTemplates 给每个副本独立的盘，但它只保证身份稳定，不等于数据库高可用。落地时建议默认打开 allowVolumeExpansion，重要数据一律 Retain 并配好备份，排障从 PVC 的 Events 看起。
