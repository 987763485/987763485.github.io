常见加密算法对比：AES、RSA、ECC

项目里要选一个加密方案时，摆在面前的往往就是 AES、RSA、ECC 这三个名字，可它们并不是互相替代的关系：一个负责批量数据，一个擅长签名和兼容旧系统，一个用短密钥换取同等强度。本文不重复推导数学原理，而是把三者放到同一组维度上对比，给出安全强度的换算参考、混合加密的拼装方式以及一份可以直接照着走的选型清单。读完本文，你应该能判断某个场景该用哪种算法、密钥该开多长，以及哪些坑一旦踩了就等于没加密。

比较之前，先确定用哪把尺子

把 AES、RSA、ECC 放在一起比较，最常见的错误是直接比密钥长度：看到 AES 只有 256 位、RSA 动辄 2048 位，就以为 RSA 更安全。这两种长度的含义完全不同。AES 的 256 位是密钥本身的全部信息量；RSA 的 2048 位是一个大合数的位长，真正决定强度的是把它分解成两个素数的难度。拿 2048 和 256 相比，就像拿一个人的体重和身高相比，数字大小说明不了问题。

要让比较有意义，至少要看六个维度：

  • 安全强度：折算到统一的“位”数，而不是原始密钥长度。
  • 运算速度：处理同样多的数据要花多少时间，是否依赖硬件加速。
  • 体积开销：密文、签名、公钥各占多少字节，这在证书链、移动网络和智能卡里很敏感。
  • 能力边界：能加密、能签名，还是只能做其中一件。
  • 密钥分发：双方是否需要事先共享秘密，公钥又靠什么证明身份。
  • 硬件支持：CPU 指令、密码卡、安全芯片是否提供加速或密钥保护。

前三个维度可以测量，后三个更多是工程约束。现实中选型失败，多数不是算错了速度，而是忽略了能力边界和密钥分发：用 RSA 加密业务数据，单次能处理的字节数很少，只能切块，既慢又容易写出漏洞；只加密不认证，密文被篡改了解密端也发现不了。下文对每种算法的讨论都围绕这六个维度展开，数学只讲到够用为止。

AES：快是它的立身之本

AES 是对称分组密码，分组长度固定为 128 位，也就是 16 字节；密钥长度可以是 128、192 或 256 位，分别对应 10、12、14 轮运算。它的设计目标是软硬件都容易实现，这一点在工程上比“理论强度最高”更有价值：同样一台服务器，AES 的吞吐比 RSA 高出几个数量级。

分组密码只规定了“16 字节怎么算”，要加密任意长度的消息，必须选一种分组模式。模式选错，算法再强也没用。

  • ECB（电子密码本）：每个分组独立加密，相同明文块必然得到相同密文块。它不隐藏任何数据模式，加密一张图片仍能看出轮廓，新系统不应使用。
  • CBC（密码分组链接）：每个明文块先与前一块密文异或再加密，需要一个初始化向量（IV）。IV 不必保密，但必须随机且每条消息都不同，否则相同前缀会产生相同密文前缀。CBC 还需要填充，解密端如果把“填充错误”和“数据错误”区分开来报告，就可能被填充预言攻击逐字节解出明文。
  • CTR（计数器模式）：把分组密码当流密码用，用递增计数器生成密钥流。它不需要填充，可以并行计算，代价是同一密钥下计数器绝不能重复，否则两段密文异或就能还原明文。
  • GCM（Galois/Counter Mode）：在 CTR 之上叠加 GHASH，输出一个 16 字节的认证标签，属于带关联数据的认证加密（AEAD）。解密时先校验标签再交出明文，密文改动一个比特就会失败。GCM 的 nonce 通常取 12 字节，同一密钥下必须唯一；随机生成 96 位 nonce 时，按照生日界，一条密钥处理大约 2^32 条消息后就该更换，高吞吐系统更稳妥的做法是用固定前缀加计数器构造 nonce。

AES 之所以在实际系统里几乎无处不在，很大程度要归功于硬件支持。Intel 从 2010 年的 Westmere 架构起提供 AES-NI 指令，ARMv8 也有对应的密码扩展，OpenSSL 这类库会自动检测并选用，把轮运算从软件查表变成一条指令。这带来的不只是速度，还有安全性：软件查表实现容易受到缓存时序攻击，硬件指令则天然更接近常数时间。

因此 AES 的适用面很清楚：磁盘与对象存储加密、数据库字段加密、TLS 记录层、备份归档，凡是“数据量大、需要反复读写”的场合都归它。它做不到的事情也同样清楚：AES 无法在双方没有共享密钥的前提下工作，也不能用于签名。密钥怎么安全地送到对方手里，仍然要靠非对称算法或带外通道解决。

RSA：能力最全，代价是体积和速度

RSA 的安全性建立在大整数分解困难之上：两个大素数相乘很容易，从乘积反推这两个素数却极难。工程上模长通常取 2048 位，3072 位用于需要更长期保护的数据，4096 位则多见于根证书，代价是密钥生成和每次运算都明显更慢。

RSA 的独特之处在于“一对密钥、两种用法”，但两种用法的填充方案并不相同，不能混为一谈。加密使用 OAEP 填充，签名使用 PKCS#1 v1.5 或 PSS。PSS 带有随机盐，安全性证明更完整，新系统应优先选择；PKCS#1 v1.5 签名虽然仍广泛部署，但历史上出现过 Bleichenbacher 一类针对填充的攻击，实现稍有疏漏就会出问题。签名的哈希函数也要选 SHA-256 及以上，SHA-1 早已不该出现在新方案里。

体积是 RSA 最直观的短板。密文长度恒等于模长：2048 位模长下，无论明文多短，密文都是 256 字节，签名也是 256 字节。单次能加密的明文更少，2048 位配 OAEP-SHA256 最多约 190 字节，3072 位约 318 字节。这意味着它天生不适合加密业务数据，只适合封装一把会话密钥或签名一段摘要。反过来说，RSA 的兼容性是三者中最好的：老系统、老证书、多数硬件模块和代码库都支持它，这也是它在迁移期难以被彻底替换的原因。

ECC：用短密钥换同等强度

ECC 基于椭圆曲线上的离散对数问题。它不分解大整数，而是在一条定义好的曲线上做点乘，已知起点和终点反推乘数同样困难，但所需的密钥短得多。常见曲线有 NIST P-256 与 P-384，也有 Curve25519 这一族：X25519 用于密钥交换，Ed25519 用于签名。

短密钥带来的好处是连锁的。256 位曲线大致相当于 3072 位 RSA 的强度，公钥只有 32 字节量级，P-256 的原始签名约 64 字节，DER 编码后 70 字节出头，而 RSA-3072 的签名是 384 字节。证书更小、握手报文更短、智能卡里能存下更多密钥，这些在移动网络和物联网场景里都是实打实的收益。ECC 的两大用途也很固定：ECDH 协商共享秘密，ECDSA 或 EdDSA 做签名，它很少被用来直接加密数据。

但 ECC 把复杂度从数学转移到了实现上，这是最容易低估的部分。第一，ECDSA 每次签名需要一个一次性的随机数 k，一旦两次签名用了同一个 k，私钥就能被直接解出方程。2010 年索尼 PlayStation 3 的签名漏洞源于常数 k，2013 年部分 Android 钱包因随机数生成器缺陷重复了 k，两次都是私钥泄露而非“强度不够”。第二，如果实现不校验对方送来的点是否真在这条曲线上，攻击者可以构造无效曲线攻击，逐步推出私钥。第三，曲线参数本身必须可信，NIST 曲线的参数生成过程长期存在争议，这也是 Curve25519 在开源社区受欢迎的原因之一。结论很朴素：选成熟的库、选公开审计过的曲线，不要自己实现点运算。

安全强度换算与混合加密

大致安全强度 对称算法 RSA 模长 ECC 曲线
约 112 位 — 2048 位 P-224
约 128 位 AES-128 3072 位 P-256
约 192 位 AES-192 7680 位 P-384
约 256 位 AES-256 15360 位 P-521

这张表给出的是业界广泛使用的等效强度参考（NIST SP 800-57 一类文档中的对应关系），用途是让不同算法落到同一档位，既不是压测结果，也不意味着可以互换。不同标准可能相差半档，项目若受合规清单约束，应以清单为准。可以记住两个锚点：AES-128 约等于 RSA-3072，约等于 ECC-256；RSA-2048 与 P-224 落在 112 位档，今天仍然可用，但新设计的长期系统应直接选 128 位档。

真实系统很少单独使用其中一种，而是拼成混合加密：用 ECDHE 协商出共享秘密，用 HKDF 派生出会话密钥，再用 AES-GCM 加密数据。

flowchart TD
    A[客户端生成临时密钥对] --> B[与服务端交换公钥并做 ECDH]
    B --> C[双方得到同一共享秘密]
    C --> D[HKDF 派生会话密钥]
    D --> E[AES-GCM 加密应用数据]
    E --> F[接收方解密并校验认证标签]

这样组合是在扬长避短：非对称算法解决密钥分发但速度慢，对称算法快却要求双方先有同一把密钥。TLS 是这条路线最典型的落地，握手阶段用证书认证身份、用 ECDHE 协商密钥，记录层用 AEAD 加密；TLS 1.3 已经删掉了 RSA 密钥传输，只保留能提供前向保密的（EC）DHE 方案。握手的字段与密钥派生步骤不在本文展开。

签名、加密与密钥管理

三种能力要分开看：保密、完整性、不可否认。AES 只能保密，GCM 顺带提供完整性，但它无法签名；RSA 两件事都能做，然而加密与签名必须使用不同的密钥和不同的填充，共用一把密钥会在不同协议之间制造交叉攻击的切面；ECC 通常只承担密钥交换与签名，不用于直接加密数据。还有一个常被遗忘的工具是 HMAC：它用共享密钥对消息做认证，速度接近对称算法，适合接口签名与消息完整性校验，但通信双方都能算出同样的值，所以它不具备不可否认性。

密钥管理的重要性高于算法选择。生成密钥要用操作系统提供的密码学安全随机数，OpenSSL 的 rand 子命令就够用；存储应交给 KMS 或 HSM，业务系统只持有密钥标识，让明文密钥尽量不落到磁盘和内存里；加密密钥与签名密钥、不同环境、不同租户的密钥都要分开；轮换要有周期和版本号，让旧数据仍可解密；关键操作要分离职责并留下审计日志；还要准备备份与恢复流程，否则 HSM 故障会直接变成数据永久丢失。

算法选错了还能平滑替换，密钥泄露了却无法把已经流出的数据收回来。这也是为什么成熟团队会把更多精力放在密钥生命周期上，而不是反复比较两个都够用的算法。

选型清单与常见误区

按场景对照即可：

  • 批量数据：AES-256-GCM，nonce 用固定前缀加计数器构造，密钥随数据版本轮换。
  • 密钥交换：ECDHE，优先 X25519 或 P-256；需要前向保密就不要用 RSA 密钥传输。
  • 签名：ECDSA P-256 或 Ed25519；必须兼容旧系统时用 RSA-3072 配 PSS。
  • 老系统与专用硬件：RSA-2048 加 SHA-256，强度在 112 位档，但兼容性最好。
  • 资源受限：ECC 证书配 AES 硬件指令，能同时减少握手字节数与 CPU 开销。
  • 合规场景：按适用的标准清单执行，不要用本文的换算表替代合规要求。

2020 年还必须提一句后量子风险。RSA 与 ECC 分别依赖大整数分解和椭圆曲线离散对数，Shor 算法在理论上可以在足够大的量子计算机上解决这两类问题。NIST 从 2016 年起推进后量子密码标准化，2020 年 7 月公布了第三轮候选算法，但到本文写作时仍没有最终标准，也没有成熟的替换方案。务实的做法不是马上换算法，而是保持加密敏捷性：把算法与密钥长度做成可配置项，梳理需要长期保密的数据，等标准落地再迁移。

常见误区可当检查表：直接比较密钥长度；使用 ECB；在 GCM 下复用 nonce；用时间戳或 rand() 充当随机数；继续使用 MD5 与 SHA-1；自己发明加密协议；只加密不认证；用 RSA 直接加密大文件；跳过证书链校验；把密钥写进代码或配置文件。

小结

三种算法不是竞争关系，而是分工关系：AES 处理数据，RSA 负责兼容与通用场景，ECC 在有限资源下提供同等强度。选型时先看能力边界和密钥分发，再看速度与体积；强度按档位对齐，不要直接比较长度。真正决定系统安全的是密钥管理与实现细节：成熟的库、正确的模式、唯一的 nonce、可信的随机数。最后，为后量子迁移留出可配置的余地，比追新更有价值。
