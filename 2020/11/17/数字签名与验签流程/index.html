数字签名与验签流程

接口报文被中间人改了一个金额字段，客户端却照样接受；升级包在传输途中被替换，安装器仍然放行。这类问题的共同解法是数字签名：发送方用自己的私钥对消息“盖章”，接收方用公钥验证这枚章。本文从签名要保证的三件事讲起，完整走一遍签名与验签流程，再用 Go 写出可运行的例子，最后把工程上最常见的失败原因和落地清单列出来。

签名到底保证了什么

很多人第一次接触签名，会把它和加密混在一起。二者的目标正好相反：加密关心“别人看不见”，签名关心“别人改不了、也赖不掉”。具体来说，一个可用的数字签名要同时提供三个性质。

第一是完整性。消息哪怕只改动一个字节，验签就会失败。注意这里的前提是摘要算法抗碰撞，若用 MD5 或 SHA-1，攻击者可以构造出摘要相同的另一份消息，完整性就名存实亡。

第二是身份真实性。签名只能用私钥生成，而私钥只在签名方手里，所以验签通过意味着“持有该私钥的一方签过这份消息”。这里有一个容易被忽略的环节：公钥本身也要可信，否则攻击者可以把自己的公钥塞给接收方。这正是证书要解决的问题。

第三是不可否认性。因为私钥是签名方独占的，签名方事后很难否认自己签过。这一点在对称密钥的 MAC 上做不到：双方共享同一个密钥，谁都能算出 MAC，出了纠纷无法判断是谁生成的。

理解了这三个性质，就能明白为什么签名之前必须先做摘要。RSA 的模运算一次只能处理一个小于模数的整数，2048 位密钥扣除填充结构后，可承载的数据只有两百多字节，几十兆的安装包根本塞不进去。把任意长度的消息压缩成 32 字节的 SHA-256 摘要，再对摘要签名，既绕开了长度限制，也把昂贵的非对称运算控制在一次。验签方重新计算摘要，再用公钥还原签名中的摘要值做比对。

需要强调的是，摘要本身是公开可算的，单独使用只能发现偶然损坏，挡不住蓄意篡改，因为攻击者改完消息可以顺手重算摘要。摘要必须被私钥“封”住，才具备认证能力。

一次完整的签名与验签流程

把上面的思路串起来，一次签名交互包含三样东西：原始消息、签名值、签名方的证书。少了证书，接收方不知道该用哪把公钥；少了消息，无法重算摘要。

sequenceDiagram
    participant S as 签名方
    participant R as 验签方
    S->>S: 对消息字节计算 SHA-256 摘要
    S->>S: 用私钥对摘要签名
    S->>R: 消息 + 签名 + 证书
    R->>R: 对收到的消息字节重算摘要
    R->>R: 校验证书链、有效期与用途
    R->>R: 用证书中的公钥验签
    R-->>S: 接受或拒绝

签名方的工作可以概括为三步。先确定要签的字节序列，然后用 SHA-256 算出 32 字节摘要，最后调用签名算法，用私钥对摘要运算，得到签名值。RSA 的签名长度恒等于模长，ECDSA 则随 r、s 的取值浮动，DER 编码后通常在 70 到 72 字节之间。

验签方的工作是逆过程，但顺序有讲究。先校验证书：链是否完整、是否在有效期内、密钥用途是否包含数字签名。再用证书里的公钥验签。如果先验签再校验证书，攻击者用一张自签证书也能让验签通过，等于白做。验签通过只能说明“消息与证书公钥匹配”，证书可信与否是另一个独立判断。

证书承担了什么

裸公钥没法回答“这把公钥属于谁”。证书把公钥和主体身份绑在一起，由 CA 用自己的私钥签名背书，同时附带有效期、序列号、密钥用途等元数据。验签方看到证书上的 digitalSignature 用途位，才知道这把钥匙被允许用于签名，而不是只能用于密钥交换。证书链如何逐级校验属于 PKI 的内容，这里只需记住：验签之前先把证书验一遍，且必须校验到受信任的根。

签名值放在哪里

实际系统里，签名很少和消息裸拼。常见做法是随消息放一个签名字段，并带上密钥标识 kid，让接收方快速定位公钥。JSON Web Signature 把头部和载荷分别做 base64url 编码，再对编码后的文本签名，拼成三段式字符串。无论哪种封装，签名的对象始终是字节序列，而不是抽象对象。

算法：RSA、ECDSA 与 Ed25519

2020 年做选型绕不开这三类算法，差别在参数、签名长度与工程兼容性。

算法 典型参数 签名长度 特征
RSASSA-PKCS1-v1_5 RSA-2048 + SHA-256 256 字节 确定性填充，兼容性最好
RSASSA-PSS RSA-2048 + SHA-256 256 字节 随机盐，安全性证明更完整
ECDSA P-256 + SHA-256 DER 约 70 至 72 字节，裸拼接 64 字节 密钥与签名都短，签名随机
EdDSA Ed25519 64 字节 无需选曲线和填充参数，实现简单

RSA 的两个填充方案值得单独说明。PKCS#1 v1.5 把摘要和算法标识打包成一个固定结构，再补零到模长，同样的消息和密钥每次算出的签名完全一样，副产物是相同消息必然产生相同签名，会泄露相等性。PSS 则引入随机盐，同一份消息两次签名结果不同，安全性论证也更接近“可证明安全”。新协议优先选 PSS，但老系统与不少签名设备只认 v1.5，互通时以对方为准。

ECDSA 在 P-256 曲线上配 SHA-256，签名短、运算快，是移动端和物联网场景的常见选择。必须警惕的是，签名随机数 k 绝不能复用，两次签名若用了同一个 k，联立方程就能解出私钥。历史上游戏主机和部分钱包都栽在这上面，生产环境应使用经过审计的库。

Ed25519 属于 Edwards 曲线上的 EdDSA，2015 年前后进入主流密码库，2017 年由 RFC 8032 标准化，TLS 1.3 和 JWT 都已经有对应支持，签名固定 64 字节，用起来比 ECDSA 省心。但要清楚它的现状：2020 年并非所有网关、HSM 和老版本 SDK 都支持 Ed25519，跨组织对接时经常要退回 RSA。

无论选哪种，协议里都要把算法套件写死，而不是让报文自己声明。JWT 的 alg 字段被改成 none 的经典漏洞，根源就是验签方信任了报文里的算法声明。做法是接收方持有允许列表，只接受约定算法，其他一律拒绝。

ECDSA 还有一个跨语言问题：签名用 DER 还是裸的 r、s 拼接。Java 与 OpenSSL 默认输出 DER，JOSE 的 ES256 规定用 64 字节裸拼接。两种格式混用必然失败；转换时每段要补齐到曲线字节长度，而不是简单去掉前导零。

被签的是字节，不是对象

签名算法只认字节，不认语义。同一份逻辑上相同的 JSON，经过不同语言的序列化器，字节可能完全不同：键的顺序不同，空格与换行不同，浮点数 99.0 与 99.00 不同，非 ASCII 字符可能被转义成 \u00e9 也可能保留原字符，末尾有没有换行也不同。签名方对 A 签名，接收方解析后重新序列化得到 B，内容等价，摘要却不同。

链路上还常经过网关与消息队列，任何一次美化输出或字段重排都会让签名失效。典型的一例是：签名服务对紧凑 JSON 签名，网关开启格式化输出，下游再压缩回去，键序已变，所有请求全部验签失败。

解决思路有三条。第一，定义规范化规则：键按字典序排列、固定分隔符、数字统一用字符串表示、统一 UTF-8 且不带 BOM、去掉末尾换行；XML 领域的 C14N 就是这类标准的代表。第二，直接对编码后的文本签名，签名覆盖 base64url(header) + "." + base64url(payload) 的确切字节，验签时使用收到的原始字符串，绝不重新编码。第三，实现上把报文当字节数组，HTTP 直接读原始 body，而不是从框架对象重建。

编码细节同样会坏事。标准 base64 含 + 和 /，URL-safe 变体用 - 和 _，结尾的 = 还可能被省略。解码必须严格匹配变体，否则得到的字节不同，验签自然失败；比较也应在解码后的字节上做。文本模式读取会把 CRLF 转成 LF，二进制场景必须显式按字节读取。

时间戳与重放：签名不证明新鲜

签名证明“谁签的”，不证明“什么时候签的”。攻击者截获一条合法请求原样重发，签名依然有效。用在转账、下单、改密码上则是灾难。

防御要把时间信息放进被签的载荷内部，否则攻击者改掉时间戳再重放即可。服务端检查时间偏差，例如正负五分钟；窗口越大对时钟漂移越宽容，可重放区间也越大。再配一次性随机数，用缓存记录已用过的值，过期时间不短于时间窗，写入必须是“不存在才写入”的原子操作，否则并发下同一个随机数可能两次通过。时钟依赖 NTP 同步，容器漂移会造成大量签名过期的误报，需要监控偏移量。

代码签名与文档签名的差别也在这里。代码签名对二进制摘要签名，常附 RFC 3161 时间戳，证明签名发生在证书有效期内，证书到期后旧软件仍可安装；文档签名嵌在文件里，覆盖特定字节范围，后续编辑都会破坏签名。两者签的都是摘要，差别在封装、时间戳与验证时机。

验签失败排查与落地清单

验签失败时不要只抛一句“签名错误”，要定位到具体环节。下面几类原因覆盖了绝大多数线上问题。

现象 常见原因
本地通过、线上全挂 网关重新序列化、换行或编码被改动
换环境后全挂 公钥错配，或填充方式、摘要算法不一致
升级后开始失败 证书过期或未生效，链上缺中间 CA
偶发失败 ECDSA 的 DER 与裸拼接混用，PSS 盐长不同，时钟漂移
报用途错误 证书的 KeyUsage 不含 digitalSignature

排查顺序建议从字节开始：先确认两端摘要算法一致，再比对解码后的签名长度，最后看证书。长度往往能直接暴露格式问题，P-256 的 DER 签名不会是 64 字节。若对已算好的摘要又哈希了一次，等价于签了另一份数据，这种错误只能靠打印中间值发现。

落到 API 实现，可以按这份清单逐项确认。算法套件写进协议文档，算法、曲线、摘要、填充、盐长度、编码全部显式约定，不依赖库的默认值。私钥交给 KMS 或 HSM 托管，不进代码库和环境变量，按租户与环境隔离。待签字节由签名服务统一生成，业务方只提交结构化数据。错误对外返回 401 和稳定错误码，对内记录 kid、算法、摘要前缀与请求 ID，绝不记录私钥或完整报文。轮换用 kid 路由，新旧公钥并存一个过渡期，提前发布 JWKS，等旧密钥调用量归零再下线。

还有一组反复出现的错误做法：用 MD5 或 SHA-1 做摘要、多个系统共用一把私钥、只验签名不验证书链、把 base64 当成加密、自研密码算法。它们在测试环境往往能跑通，上线后才暴露。

小结

数字签名的骨架只有三步：算摘要、私钥签摘要、公钥验摘要。它保证完整性与不可否认性，但不提供保密性，也不证明消息新鲜。工程上真正难的从来不是调用签名接口，而是让两端对待签字节、算法参数和编码格式的理解完全一致。选型优先 PSS 或 Ed25519，老系统退回 PKCS#1 v1.5；协议里写死算法套件，密钥交给 KMS，验签失败按字节、格式、证书的顺序排查。
