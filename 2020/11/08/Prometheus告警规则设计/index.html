Prometheus 告警规则设计

告警规则是把指标翻译成行动的最后一公里：表达式写错、阈值拍错、通知发错人，前面的采集与存储都白费。本文从告警价值观、指标与标签、PromQL 表达式、阈值与 for、规则组织、延迟与 SLO 燃烧率，一直讲到 Alertmanager 的分组、抑制与路由，并给出可以直接落地的规则与测试样例。读者应已了解 Prometheus 的基本抓取模型与 PromQL 语法，读完后能为一个真实服务设计出噪声可控、责任清晰、可被测试的告警体系。

告警的价值观：症状、因果与可执行性

很多团队把告警理解为“指标加阈值”，于是规则文件里堆满了几百条 xxx > 80。上线三个月后，值班同学开始凭标题判断哪条要处理，真正的事故反而被淹没。本文认为，告警是一条产品线：输入是时间序列，输出是人的注意力，中间每一步设计失误都会以误报、漏报或疲劳的形式还回来。

症状优先，原因其次

用户能感知的是“下单失败”“页面一直转圈”“搜索结果不对”。CPU 使用率 92%、磁盘剩余 8%、GC 暂停变长，这些是原因层的信号。只对原因告警会遇到两个方向的错误：一是原因出现但症状没有出现（批处理任务把 CPU 打满，接口延迟仍在 SLO 内），二是症状出现却没有对应的原因指标（依赖方超时、配置推送错误、证书过期）。

因此 page 级别的告警应当绑定症状：错误率、延迟、可用性、数据正确性。原因信号有两个去处：放进看板与诊断信息，或者作为“可预测的症状”提前 page。例如磁盘按当前写入速度 4 小时内会写满，这已经不是“使用率 80%”这种静态阈值，而是“未来必然影响写入”的预测，值得叫醒人。

因果链的例子很常见：数据库连接池耗尽导致 API 返回 5xx。只对连接池使用率告警，阈值既难定又滞后，因为不同负载下安全水位不同；对 5xx 比例告警，直接对应用户影响。反过来，连接池等待时间适合放进 annotation，帮助值班同学在两分钟内定位到根因。

每条告警都要有主人和手册

一条告警上线前要回答三个问题：收到的人要做什么？不做会怎样？出了事找谁？答不上来的规则不该 page，最多挂到看板上。由此引出两个必备字段：owner（通常是 team 标签，对应到值班表）与 runbook（一段可执行的处置说明，包含确认命令、常见原因、缓解手段、升级路径）。

runbook 不是写给审计看的文档。它应该让一个不熟悉该服务的值班同学在五分钟内完成三件事：确认影响范围、执行一个已知有效的缓解动作、找到能继续处理的人。缺少 runbook 的告警，实际上是把诊断成本转嫁给了被叫醒的人。

page 与 ticket 的分界线

page 用于“用户影响正在发生或即将发生，需要在几分钟内由人介入”的情况，例如错误率快速燃烧、核心接口不可用、数据写入停滞。ticket 用于可以异步处理的事情：证书还有 30 天到期、磁盘增长趋势、单实例冗余丢失、容量水位缓慢上升。把 ticket 当 page 发，是告警疲劳最主要的来源；反过来把 page 降级成群消息，则会让故障在聊天记录里过期。

疲劳本身就是可靠性风险，而不是“体验问题”。报警密度超过人的处理能力后，值班同学会开始扫标题、凭直觉忽略、把确认当成处理。真正的事故通知混在几十条噪声里，MTTR 被拉长，事后复盘还会发现“其实早就报过”。可以用几个数字观察：每个班次的 page 数量、可执行告警占比、重复告警占比、从通知到确认的时延。它们不需要绝对精确，但需要被周期性看到。

最后是分级。severity 至少区分 critical、warning、info 三档，分别对应立即 page、工作时间处理、只看板。分级不是为了好看，而是路由的依据：不同级别走不同的通知渠道、不同的响应时限、不同的升级策略。

Prometheus 负责“算”，Alertmanager 负责“发”。职责分离的好处是规则可以单独测试，通知策略可以独立调整；把路由逻辑写进 PromQL 或者用脚本拼接通知，最终都会变成无法维护的泥团。

指标与标签：让规则有稳定的地基

告警表达式的好坏，很大程度上在指标设计阶段就决定了。名字混乱、标签爆炸、口径不一致，后面无论怎么调阈值都救不回来。

命名与单位

指标名应当自解释：<namespace>_<subsystem>_<name>_<unit>。counter 以 _total 结尾，时间统一用秒，大小统一用字节。http_request_duration_seconds 比 http_request_time_ms 更好，因为 PromQL 里的 rate 默认按秒计算，单位混用会让阈值的含义变得可疑。同一个含义不要有两个名字，例如既有 errors_total 又有 request_errors_total，不同的看板各取一个，告警结果自然对不上。

标签命名同样需要约定：小写字母、下划线分隔，environment 与 env 只能留一个。团队里常见的“历史遗留”是同一类指标在不同服务里用了 status、code、status_code 三种写法，写规则时只能用正则把三种都兜住，既难读又容易漏。

标签基数：最贵的资源

一条时间序列由指标名与一组标签唯一确定。标签不是越多越好，每增加一个取值丰富的标签，序列数量按乘法增长。一个服务有 50 个实例、20 个路径、5 种状态码，http_requests_total{instance, path, code} 就有 5000 条序列；如果 path 里带上订单号，基数直接失控。

告警规则尤其要避免把高基数标签带进来：user_id、request_id、session_id、完整 URL、错误消息文本都不应该出现在指标标签里。它们带来的问题不只是存储膨胀，还包括查询变慢、规则评估周期被拉长，以及 Alertmanager 里每条告警都因为标签不同而无法分组。需要定位具体请求时，用日志与链路追踪，不要用指标。

另一些标签则应当被保留，因为它们是路由和聚合的抓手：service 标识业务服务，team 标识负责人，environment 区分生产与预发，severity 由告警规则注入而不是写进原始指标。job 与 instance 由抓取配置自动生成，job 表示一类目标，instance 是具体地址；在告警表达式里通常按 service 聚合，把 instance 留给排障。

稳定的标签集合

同一个指标的所有样本，标签集合应当尽量一致。Prometheus 允许不同样本带不同标签，但一旦出现“有的样本有 region、有的没有”，sum by (region) 就会多出一个空值分组，on() 匹配也会出现意外。新增标签属于破坏性变更，需要同步修改所有规则与看板，最好在指标评审时就想清楚。

告警规则产出的标签同样要稳定。severity、team、service 是路由依赖的维度，不能时有时无；runbook_url 更适合放在 annotation，因为它是给人看的文本，放进标签会让同一告警因 URL 不同而分裂成多条。

用 Recording Rules 分担成本

当一段表达式被多条告警或看板反复使用时，预计算是值得的。Recording Rule 把结果写成新的时间序列，查询时只做一次简单的过滤。命名沿用社区习惯 level:metric:operations，例如 service:http_requests:rate5m，冒号不是合法指标名字符，因此不会与原始指标混淆。

Recording Rule 也有代价：它多了一次评估与一份存储，且结果同样受 staleness 影响。源序列消失后，后续评估会把它标记为失效，但已写入的样本仍可被回看；如果整组规则停止评估，带 for 的告警可能基于旧值误判为持续，后文的误区一节会展开。

指标与标签定好之后，才轮到表达式与阈值。

表达式与阈值：rate 家族、窗口、迟滞与 for

告警表达式最常见的事故不是语法错误，而是“看起来有值、语义却不对”。这一节把几个高频函数与边界条件拆开讲。

rate、increase 与 irate 的分工

rate() 只能用于 counter。它取区间内首尾样本的增量，除以区间秒数，并在区间边界做外推，得到“每秒增长速率”。counter 重置会被自动识别，不会出现负数。increase() 是同一套逻辑乘以区间秒数，回答“这个区间里大概增加了多少”。两者都带外推，结果是估计值而非精确计数。

irate() 只看区间内最后两个样本，反应快、抖动也大。它适合看板上的即时趋势，不适合告警：一次瞬时的尖峰就能让 irate 冲高，下一分钟又恢复，配合 for 反而产生“时有时无”的 pending 状态。告警应当关注一段时间的总体水平，用 rate 配合足够长的窗口更稳。

对 gauge 用 rate 是另一个常见错误。内存使用量、队列长度、连接数都是可增可减的瞬时值，rate 会把“上下波动”误读成“持续增长”。需要 gauge 的变化趋势时，用 delta() 看区间首尾差值，或用 deriv() 看每秒斜率，并且要接受它们同样受采样影响。

窗口不能短于抓取间隔

区间向量的窗口必须覆盖足够多的样本，否则 rate 在样本不足时返回空值。社区经验是窗口至少为抓取间隔的四倍：15 秒抓取对应 1 分钟以上的窗口，30 秒抓取对应 2 分钟以上。实践中 5 分钟窗口配合 15 到 30 秒抓取最常用，既能平滑抖动，又不会让告警迟钝太多。

窗口还需要与评估间隔配合。规则每 30 秒评估一次，窗口却写成 [45s]，相邻两次评估看到的样本集合会来回跳，曲线呈锯齿状。让窗口是评估间隔的整数倍，结果更稳定，也更容易解释。

空值、除零与 absent 的陷阱

比例型告警最常见的静默失败是分母为空。sum(rate(errors[5m])) / sum(rate(total[5m])) 在计数器尚未建立、或目标已经下线时，两侧都为空，向量匹配得不到任何结果，表达式返回空集，告警永远不触发。表达式没报错，规则显示正常，问题却漏掉了。

分母为 0 时按浮点语义会得到 Inf 或 NaN，比较运算随之失真；分母缺失则让整条结果消失。工程上的处理有三种。第一种是给分母兜底：当分母存在但为 0 时，clamp_min(分母, 0.001) 让比例有定义，但它补不出完全缺失的序列。第二种是显式检测缺失：用 absent() 在指标整体消失时单独告警，例如 absent(up{job="order-api"} == 1)，它会在目标消失或全部不可用时返回 1。第三种是给结果补零：... or on() vector(0)，但要清楚补出来的样本没有业务标签，只能用于“是否为零”的判断，不能用于路由。

absent() 的匹配是精确的：标签写多了，指标只是部分缺失时它不会触发；写少了，只要同组还有别的实例在上报，它就认为数据没丢。对关键指标，通常还要再加一条“无数据”告警，用 absent() 配合 for: 10m，防止监控链路自己坏掉却无人知晓。

unless 用来做排除，例如灰度实例不参与告警：expr unless on(instance) (label_replace(...))。它适合静态、可枚举的排除；按时间窗维护的排除应该交给 Alertmanager 的静默，否则规则里会积累大量一次性的 unless 条件。

阈值、迟滞与 for

阈值不该拍脑袋。可行的做法是取过去四周同类时段的分位数作为基线，再留出余量。例如接口 P99 在正常工作日的高峰约为 280 ms，SLO 目标是 300 ms，那么告警阈值可以定在“错误预算燃烧速度”上，而不是直接卡 300 ms；如果一定要用静态阈值，至少要保证正常流量的日内波动不会触发它。

迟滞用于解决“阈值附近来回跳”的问题：触发线设在 90%，恢复线设在 80%，进入告警后只有降到 80% 以下才恢复。Prometheus 的告警规则没有原生的恢复阈值，只有 for 要求的“持续满足”。一种绕法是在表达式里引用上一轮评估写入的 ALERTS 序列：

for 是抑制抖动最直接的工具。它的语义是“表达式连续为真达到指定时长才从 pending 转为 firing”，中途只要有一次评估为假就重新计时。for 的长度要大于抓取间隔与评估间隔之和，否则可能在样本还没稳定时就开始计时；另一方面，for 越长，真正的故障被延迟通知越久。经验上，用户可感知的错误率告警用 5 到 10 分钟，容量与趋势类告警可以用 30 分钟以上。

季节性同样影响阈值。面向办公人群的服务在夜间流量低，固定错误数阈值会在低流量时过度敏感；用比例而不是绝对数可以缓解，但仍应比较“上周同一时刻”的基线。对多服务共用一套规则的情况，按服务覆盖阈值比全局一个数字更现实：批处理服务与在线 API 的 CPU 水位本来就不该使用同一条线。

规则文件的解剖、组织与测试

一条规则写对，和一套规则能长期维护，是两件事。前者靠 PromQL 功底，后者靠文件结构、命名约定与测试。

一条告警规则的完整字段

alert 是告警名，也是 ALERTS 序列里 alertname 标签的值，应当在全局范围内保持唯一且语义明确。expr 返回的每条序列都会生成一条独立告警，因此表达式的聚合维度直接决定告警条数。for 决定持续多久才 firing。labels 会附加到告警上，供 Alertmanager 路由与抑制匹配；annotations 只用于展示，不会参与匹配。

模板变量是经常被忽略的细节：$labels 可以取到告警序列上的任意标签，$value 是表达式结果，$externalLabels 是全局外部标签。展示比例时用 humanizePercentage，展示时长用 humanizeDuration，比直接打印一长串小数可读得多。summary 要短，它是通知标题；description 写清现象、范围和已经持续的时间，让值班同学不用打开看板就能判断严重程度。

record 规则没有 for 与 annotations，但可以附加 labels，用来标记数据来源或聚合层级。录制规则的命名要能看出聚合层级、指标与运算，例如 service:http_error_ratio:rate5m。录制规则不是越多越好：每一条都会增加评估开销，且会让“指标从哪里来”变得难查；只把被复用三次以上、或明显昂贵的表达式下沉。

文件怎么放

按团队或按服务拆文件，比按告警级别拆更可持续：rules/order-api.yml、rules/payment.yml，在 prometheus.yml 里用 rule_files: ["rules/*.yml"] 一次加载。每个文件内部再用 groups 按 SLO 或主题分组，并给组设置独立的 interval：SLO 燃烧率需要 30 秒级评估，容量趋势一分钟一次就够。

同一个 alertname 不要在不同文件里表达不同含义，否则抑制与路由都会出错。改名时要同步更新 runbook、看板链接与测试用例，这也是把告警当成代码管理的一部分。

延迟与错误：直方图分位数、RED 与饱和度

平均值会骗人

100 个请求里 99 个耗时 50 ms，1 个耗时 10 s，平均约 150 ms，看上去“还好”；但对那个用户来说，这是一次超时。延迟分布是长尾的，均值被大量快请求拉低，尾部才决定体验。因此延迟告警要看分位数，而不是用 _sum 除以 _count 算平均。

直方图与 histogram_quantile

客户端直方图把观测值计入 le 桶，桶是累积计数。PromQL 用 histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m]))) 估算分位数，桶内按均匀分布插值，所以桶边界直接决定精度。桶要围绕 SLO 边界设计：目标 300 ms，就在 0.1、0.25、0.3、0.5、1、2.5、5 秒设桶，不要让默认的指数桶恰好跨过 300 ms。

聚合时必须保留 le，先 sum by (le) 再算分位数；也不能把各实例的 P99 求平均，分位数不可平均。正确顺序永远是先合并桶，再计算。

用达标比例替代分位数告警

延迟告警常看 P95 与 P99，但分位数本身没有业务含义，低流量时噪声还大：5 分钟只有 100 个请求，P99 基本等于最大值。更稳的 SLI 是“快请求占比”：

它直接回答“有多少比例的用户在 300 ms 内完成”，可以跨实例相加，也能直接对接 SLO。

错误、流量与饱和度

RED 方法给出三个维度：Rate、Errors、Duration。错误率用 5xx 与总请求之比，注意排除客户端 4xx，除非业务上 4xx 也算失败；流量用 sum(rate(...))，突降同样值得告警，可能是上游断流或发布回滚。USE 面向资源：利用率、饱和度、错误。饱和度往往比利用率更接近症状：CPU 90% 不一定慢，CPU throttling 时间持续增长通常意味着真的在排队。

容量余量用预测而不是静态水位：

它表示按最近六小时的趋势，四小时内磁盘会写满。预测对突发写入不敏感，适合作为工单或低级别提醒，不适合作为唯一的 page 依据。

SLO 与多窗口燃烧率

SLI、SLO 与错误预算

SLI 是测量，SLO 是目标，错误预算是允许的失败量。以 99.9% 的 30 天可用性目标为例（这是示例值，不是通用标准），失败预算为 0.1%，约 43 分 12 秒。错误预算把稳定性变成可消耗的资源：发布激进就多花预算，预算见底就冻结变更。

燃烧率与多窗口

燃烧率等于实际错误率除以预算速率：

99.9% 的目标下，错误率 0.1% 时燃烧率为 1，30 天刚好用完；错误率 1.44% 时燃烧率为 14.4，一小时就烧掉 2% 的预算。Google SRE Workbook 给出的多窗口组合是：1 小时窗口配 5 分钟窗口、阈值 14.4；6 小时配 30 分钟、阈值 6；3 天配 6 小时、阈值 1。短窗口约为长窗口的十二分之一。

这种组合降低噪声的原因很直接：瞬时抖动只能满足短窗口，长窗口不满足；持续故障两个窗口同时满足，几分钟内就能 page，不需要很长的 for。恢复时短窗口先掉下去，告警迅速解除，不会出现“故障已经恢复、通知还在继续”的尴尬。

预算策略

燃烧率告警要配策略才有意义：预算消耗过半时限制发布，耗尽时只允许修复类变更。策略需要服务 owner 与业务方共同确认，不能由监控团队单方面设定。低流量服务还要拉长窗口，否则几分钟没有请求就会触发除零或假阳性。

Alertmanager：分组、抑制、路由与静默

Prometheus 只负责产生 ALERTS 序列，去重、聚合、决定发给谁由 Alertmanager 完成。

分组与三个时间参数

group_by 决定哪些告警合并成一条通知。常用组合是 [alertname, service, cluster]：同一服务、同一类告警合并，不同服务分开。维度过粗会把无关故障塞进同一条消息，过细则等于没有分组。

group_wait 是新分组首次通知前的等待，默认 30 秒，用来收拢同一批告警；group_interval 是同一分组出现新告警时的最小发送间隔；repeat_interval 是未恢复告警的重复提醒周期，4 小时是常见取值。三者共同决定通知密度，调参要一起看。

抑制：用上游故障压住下游噪声

抑制规则由 source、target 与 equal 组成：source 触发时，target 被压制。典型场景是服务宕机后，依赖它的延迟、错误率、连接池告警会一起响；用 ServiceDown 抑制同一服务的派生告警，值班同学只需要面对根因。

equal 中的标签必须在两侧都存在，少一个就匹配不上。抑制也不同于静默：source 恢复后 target 会重新参与评估，不需要人工解除。

路由树与接收人

route 是一棵树，子路由按顺序匹配，第一个命中的兄弟节点生效；设置 continue: true 可以继续匹配后面的兄弟。利用这个机制可以做到“生产环境的 critical 全部进 Pager，同时订单团队的 critical 额外进自己的值班群”。

空的 blackhole 接收人常被用来吞掉预发环境告警，比在每个 team 的规则里写排除条件更干净。send_resolved 建议开启，否则恢复信息只能靠人去看板确认。

静默与高可用

计划内维护用静默，不要改规则：amtool silence add alertname=~"OrderApi.*" --duration=2h --comment="release 2020.11"，静默带创建人、备注与到期时间，到期自动失效，事后可审计。临时把阈值调高再忘记改回来，是更常见的二次事故来源。

Alertmanager 自身要成对部署：至少两个实例通过 gossip 组成集群，Prometheus 同时向两者发送告警，通知日志负责去重。Prometheus 也可以跑双副本，规则完全一致，重复的 ALERTS 会在 Alertmanager 侧被合并。只部署一个 Alertmanager，等于把整条通知链路变成单点。

完整案例：错误率、延迟、抑制与路由

把前面的零件装成一套可运行的配置。场景是订单服务 order-api，可用性目标 99.9%（示例），延迟目标是 99% 的请求在 300 ms 内完成。

规则文件

错误率告警用 1 小时与 5 分钟双窗口，for 只留 2 分钟，因为持续条件已经由窗口表达；延迟告警是症状型 warning，走群消息与工单，不 page。两条告警分别带 team 与 slo 标签，Alertmanager 可以按团队路由，事后也能按 SLO 统计告警量。

抑制与路由沿用前面的配置：ServiceDown 出现时压制所有 OrderApi.* 告警；critical 进 Pager，warning 进团队群。测试文件应覆盖三个场景：错误率 9% 持续一小时必须触发、短暂尖峰不触发、无流量时不触发。

上线前检查与常见误区

规则与测试都通过之后，先在预发环境跑一周，观察告警量与误报率，再切生产。上线后每季度做一次告警评审，结合值班反馈把没人处理的规则删掉，比新增规则更重要。以下问题在评审中出现频率最高。

  1. 对原因告警：CPU、内存一高就叫醒人，而用户没有任何感知。
  2. 缺少 for 或 for 短于评估间隔，一次采样抖动就直接 page。
  3. 高基数标签进入告警，一个故障裂成上百条通知。
  4. 多副本 Prometheus 与重复规则产生同义告警，未在 Alertmanager 去重。
  5. 维护窗口靠改阈值，忘记改回，之后一直漏报。
  6. 告警没有 owner 与 runbook，值班同学收到后只能转发。
  7. 录制规则断流后旧样本仍在回看窗口内，带 for 的规则误判为持续。
  8. 阈值从不复评，规则只增不减，最后没人再看告警列表。

小结

告警设计的核心不是把阈值调准，而是决定“什么值得叫醒人”。症状优先、每条告警有 owner 与 runbook、page 与 ticket 分流，是三条不可妥协的原则。表达式层面，counter 用 rate、窗口不短于抓取间隔、聚合时保住路由标签、对空值与除零做兜底，能消除大部分静默失败。延迟用直方图桶聚合后的达标比例，可用性用 SLO 燃烧率，比单点阈值更接近用户感受。规则要像代码一样组织、测试与评审，Alertmanager 的分组、抑制、路由与静默则负责把正确的信息送到正确的人。最后，控制告警数量本身就是可靠性工作，噪声越少，真正的事故越容易被看见。
