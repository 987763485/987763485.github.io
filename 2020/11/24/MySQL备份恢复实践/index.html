MySQL 备份恢复实践

备份是数据库运维中最容易被拖延的一件事：平时它只是磁盘上的几个文件，真出事时它却是唯一的退路。本文以 MySQL 5.7 与 8.0 为背景，梳理逻辑备份与物理备份的取舍、binlog 与时间点恢复的配合方式，并给出一套可以落地的备份策略与恢复流程。文中的容量与耗时为说明用的假设值，读者需要按自己的数据量和硬件重新估算。

先回答几个问题

在挑工具之前，先把需求写成文字。没有目标的备份，往往只是把数据换了个地方存放。

RPO 与 RTO

恢复点目标（RPO）回答“最多能丢多少数据”，恢复时间目标（RTO）回答“多久必须恢复服务”。这两个数字直接决定技术选型：如果 RPO 是以分钟计，光靠每天一次全备不够，必须持续归档 binlog 或者使用延迟从库；如果 RTO 要求在一小时内，那么一个需要导入数小时的逻辑备份显然不合格。很多团队直到演练时才发现，自己实际能做到的 RPO 与对外承诺的相差一个数量级。

备份的几种形态

按内容分，逻辑备份导出的是 SQL 语句或文本数据，物理备份复制的是数据文件与日志文件；按范围分，有全量、增量与差异；按时间维度看，还有 binlog 这种“记录变化”的流水账。三者的关系可以用一句话概括：全量备份给你一个起点，增量备份减少重复拷贝，binlog 把起点推进到任意时刻。此外还有异地副本、加密、保留周期与恢复演练，这些属于非功能性要求，却决定了备份在关键时刻是否真的可用。

一个常见的误解是把“有备份”等同于“能恢复”。备份文件损坏、版本不匹配、权限缺失、磁盘写满，任何一种情况都会让恢复失败。因此本文把“验证”和“演练”放在与备份同等重要的位置。

逻辑备份：mysqldump 的用法与边界

mysqldump 随 MySQL 一起发布，不需要额外安装，导出的 SQL 文本可读、可编辑、可跨小版本迁移，是最常见的入门方案。

一致性从哪来

InnoDB 支持事务，mysqldump 借助 --single-transaction 在一个可重复读事务里完成导出，整个过程中不需要锁表，业务写入不受影响。这条参数是逻辑备份的生命线：不加它，导出期间其他会话的写入会导致各表之间的数据处于不同时间点，恢复后可能出现外键断裂或金额对不上。

几个参数值得单独说明：

  • --single-transaction：开启一致性快照，只对 InnoDB 有效，MyISAM 表仍会被锁住。
  • --master-data=2：把备份时刻的 binlog 文件名与位置以注释形式写进文件，恢复后可据此重放后续 binlog。GTID 环境中再配合 --set-gtid-purged=ON（默认开启），文件里会额外记录 GTID 集合。
  • --routines --triggers --events：默认不导出存储过程、函数、触发器和事件调度器，漏掉这三项是恢复后“功能莫名失效”的典型原因。
  • --quick：逐行读取并写出，避免把整张表缓冲进内存，对大表几乎是必需的。
  • --databases 与直接跟库名的区别在于前者会在导出文件里写入 CREATE DATABASE 与 USE 语句。

恢复前应确认目标实例上没有同名库，或明确接受覆盖；导入时建议设置 sql_log_bin=0 关闭 binlog，否则这批写入会被当作业务变更记录，既浪费空间，也污染后续的时间点恢复。

逻辑备份的短板同样明显。恢复时需要逐条执行 SQL、重建索引，数据量到百 GB 级别后，导出可能要数小时，导入更慢；文本文件无法直接增量；mysqldump 对单表超大、并发写入极高的场景也不友好。因此在生产环境中，它更适合中小库、单表导出和跨版本迁移，而不是 TB 级实例的主力方案。

物理备份：XtraBackup 的热备与增量

物理备份直接复制 InnoDB 的数据文件，恢复时省去了解析 SQL 和重建索引的开销，因此在数据量大、RTO 要求紧的场景里几乎是标准答案。Percona XtraBackup 是使用最广的开源实现，它通过备份期间持续拷贝 redo 日志来保证文件的一致性，整个过程不阻塞写入。

版本对应关系必须先弄清楚：MySQL 5.7 配 XtraBackup 2.4，MySQL 8.0 配 XtraBackup 8.0，两者互不兼容。用 2.4 去备份 8.0 实例会直接报错退出，反过来同样不行。

--backup 结束时目录里会生成 xtrabackup_binlog_info，记录备份对应的 binlog 文件名与位置（开启 GTID 时还包含 GTID 集合），这个文件是全量备份与 binlog 衔接的桥梁，务必随备份一起归档。--prepare 的作用是让 redo 日志中的未提交事务回滚、已提交事务落盘，没有这一步，备份目录里的文件处于“崩溃恢复前”的状态，直接启动实例可能失败。--copy-back 只是复制，不会修改 my.cnf，也不会自动创建数据目录。

增量备份

XtraBackup 的增量基于 InnoDB 页的 LSN：只拷贝 LSN 大于上次备份的页，因此增量备份的体积通常远小于全量。用法上先做一次全备，之后每次指定基准目录：

恢复增量链时，顺序和参数都不能错：先对全备执行 --prepare --apply-log-only，再依次合并每个增量，最后一个增量不加 --apply-log-only。前几步加上该参数是为了跳过回滚阶段，否则中间态的未提交事务会被提前回滚，后续增量就无法正确合并。

合并完成后，/backup/full 就是包含全部增量的完整备份，再走 --copy-back 即可。增量链越长，任何一环损坏都会导致整条链失效，因此实践中通常采用“每周全备 + 每天增量”，而不是无限叠加。

binlog 与时间点恢复

全量备份只能把你带回备份开始的那一刻，之后的数据要靠 binlog 补回来。这套组合就是常说的 PITR（Point-In-Time Recovery）。

前提配置

首先要确认 log_bin 已开启，并且 binlog_format 为 ROW。ROW 格式记录每一行的前后镜像，重放结果确定，不受 SQL 执行计划或函数取值影响，是恢复场景下唯一可靠的选择。binlog_row_image 保持默认的 FULL，否则更新语句可能缺少完整的前镜像。

还需要注意 server_id 唯一、sync_binlog=1（每次提交刷盘），否则崩溃时可能丢失最后一段事务。GTID 模式下建议同时开启 gtid_mode=ON 与 enforce_gtid_consistency=ON，恢复时用 GTID 定位比用文件名加偏移量更不容易出错。

用 mysqlbinlog 重放到指定时刻

假设误操作发生在 2020-11-24 14:30 左右，而当天凌晨 02:00 做过全备，恢复流程是：先还原全备，再把 02:00 到 14:29 之间的 binlog 重放一遍。

也可以按位置截断：--start-position 与 --stop-position 适合已知具体事务偏移的场景。开启 GTID 后，--skip-gtids 常与 --include-gtids 配合使用，目的是把重放产生的事务换上新 GTID，避免与已有 GTID 集合冲突而跳过。

时间点恢复的核心难点不在命令，而在“停在哪里”。误删往往是在发现之后才被定位的，所以第一步永远是把 binlog 解析成可读文本，找到误操作事务的起始位置，向前截断。直接按“大约几点”重放，很容易把误操作再执行一遍。此外，重放前务必确认目标实例的 sql_log_bin 已关闭，否则这段历史会被再次写入 binlog，形成循环。

备份策略与恢复流程

工具只是零件，真正决定可靠性的是一套有节奏、有验证、有文档的流程。

分层与节奏

对大多数中小型业务，下面这套组合足够覆盖绝大多数故障：每天凌晨做一次全量备份（物理或逻辑，按数据量选择），全天持续归档 binlog，每周把一份全备同步到异地或对象存储，每月保留一份归档到冷存储。保留周期按合规要求和恢复需求取交集，常见做法是本地保留 7 到 14 天、异地保留 30 到 90 天。

flowchart TD
    A[每日全备] --> B[校验 checksum]
    B --> C[上传本地备份池]
    A --> D[归档 binlog]
    D --> E[每周同步异地]
    C --> F[季度恢复演练]
    E --> F
    F --> G[记录 RPO/RTO 实测值]

每次备份完成后计算校验和并记录，恢复前比对，能挡住传输截断与磁盘静默损坏，成本极低。

恢复的步骤

恢复不是一条命令，而是一串动作，建议提前写成可执行的清单：

  1. 准备一台干净实例，MySQL 版本与备份源一致，my.cnf 中的字符集、innodb_page_size、sql_mode 尽量对齐。
  2. 恢复期间关闭 binlog，避免恢复数据被写入日志。
  3. 还原全备，按需重放 binlog 到目标时刻。
  4. 恢复账号与授权。mysqldump 不加 --all-databases 时不会包含 mysql 库，物理备份虽然包含，但账号密码与应用连接配置仍需核对。
  5. 校验：关键表行数、金额汇总、自增起点、CHECKSUM TABLE 结果，与源端比对。
  6. 把应用指向新实例。连接串、DNS 或 VIP 的切换属于变更操作，应先在低峰期演练，切换后观察错误率与延迟。

核心思路是先在隔离环境恢复成功，再谈切换；直接在原实例上覆盖，中途失败就没有回退余地。

部分恢复：单表与误删

整库恢复代价高，很多故障其实只需要找回一小部分数据。

如果使用逻辑备份，可以用 --tables 只导出指定表，恢复到临时库后再按主键回填：

物理备份则有“可传输表空间”的思路：--export 导出单表的 .cfg 与 .ibd，在目标实例上 DISCARD TABLESPACE 后用 IMPORT TABLESPACE 导入。这条路径要求表结构与页格式完全兼容，操作门槛高，不适合作为日常手段。

对误 DELETE 或误 UPDATE，更好的做法是不做整库恢复，而是把 binlog 解析出来，反向生成补偿语句。mysqlbinlog 配合 --base64-output=DECODE-ROWS -v 可以打印出行级前后镜像，再据此构造 INSERT 或还原字段。这个过程必须人工确认，脚本自动生成的反向 SQL 一旦条件写错，会把问题扩大。操作前先在从库或临时实例上演练，确认影响行数与预期一致再执行。

监控、自动化与安全

备份失败往往悄无声息，等到需要时才被发现，所以监控要覆盖“有没有成功”和“是否健康”两个层面。

最基础的检查是任务退出码与产物大小：备份脚本失败要立即告警，产物大小相对上周同期骤降超过一定比例也要告警，后者常常意味着导出的库选错了或表被误删。再往上一层看趋势：备份耗时、压缩后体积、binlog 增长速度。耗时持续上升说明数据量或 IO 出了问题，binlog 增长过快则可能预示批量写入或异常循环。

binlog 的磁盘管理要单独说。SHOW BINARY LOGS 查看现存文件，PURGE BINARY LOGS TO 'mysql-bin.000020' 或 PURGE BINARY LOGS BEFORE '2020-11-01 00:00:00' 手动清理。自动清理在 5.7 中由 expire_logs_days 控制，单位为天；MySQL 8.0 保留该参数但已标记为废弃，改用 binlog_expire_logs_seconds，精度到秒，默认值约 30 天。升级到 8.0 后如果只改旧参数，可能发现行为与预期不一致。清理前务必确认没有从库仍依赖这些文件，删掉正在被复制的 binlog 会让从库直接报错中断。

安全方面有三条底线：备份文件落盘加密，传输走 SSH 或 TLS，访问备份的账号与业务账号分离且只读。备份里包含全量用户数据，敏感程度不低于生产库，备份服务器的权限、审计日志、恢复记录都应纳入管理。谁在什么时候恢复了哪个库，这类信息在事故复盘时非常关键。

常见误区

把前面内容里反复出现的坑集中列一下，便于对照自查：

  • 逻辑备份不加 --single-transaction，导出结果跨时间点，恢复后数据自相矛盾。
  • 只做全备不开 binlog，故障后只能回到昨天，RPO 直接以天计。
  • 备份与数据库放在同一块盘或同一台机器，磁盘故障时一起消失。
  • 从不做恢复演练，直到真出事才发现备份文件根本导不进去。
  • 备份与恢复的 MySQL 版本不一致，物理备份尤其敏感，直接无法启动。
  • 导出时漏掉 --routines --triggers --events，恢复后存储过程与定时任务全部丢失。
  • 恢复时没有关闭 binlog，恢复数据被记录为新事务，后续 PITR 出现重复写入。
  • 用 --all-databases 恢复时把 mysql 库的系统表一起覆盖，账号与权限被旧数据冲掉。

小结

备份的本质不是复制文件，而是“在限定时间内把数据恢复到某个确定时刻”的能力。选型上，中小库用 mysqldump 配合 --single-transaction 足够，大库与紧 RTO 场景应上 XtraBackup，并理清全备、增量与 binlog 的衔接关系。策略上，全备加 binlog 归档加异地副本是基本盘，校验和与恢复演练决定了这套基本盘是否可信。最后，把 RPO、RTO、恢复步骤和责任人写成文档，按季度实测一次，比任何工具参数都更能提升安全感。
