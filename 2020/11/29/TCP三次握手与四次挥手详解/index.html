TCP 三次握手与四次挥手详解

几乎每一次网络故障排查，最后都会落到“连接是怎么建立、又是怎么断开的”这两个问题上。本文从 TCP 头部字段出发，逐段拆解三次握手与四次挥手，说明序列号同步、选项协商、服务端队列与 TIME_WAIT 的真实作用，并给出抓包观察与排障的思路。读者不需要事先熟悉内核源码，但应当写过至少一个 socket 程序。

先认清 TCP 头部里参与握手的字段

TCP 报文段的头部由固定部分和可变选项组成，RFC 793 规定的固定部分为 20 字节，选项最长 40 字节。理解握手与挥手只需要盯住其中少数字段，但它们各自的语义必须分清。

端口与序号是最基础的几项。源端口和目的端口各占 16 位，与源 IP、目的 IP 一起构成四元组，内核正是靠它把报文分发到对应的 socket。序列号占 32 位，标识本报文段第一个数据字节在整个字节流中的位置；确认号同样 32 位，含义是“这个序号之前的字节我都收到了，下一个期望收到的是它”。序列号会回绕，比较时必须按模 2 的 32 次方处理。

六个标志位各管一件事：SYN 用于建立连接并同步初始序列号，ACK 表示确认号有效，FIN 表示发送方没有数据要发了，RST 用于立即复位连接，PSH 提示接收方尽快把数据交给应用，URG 与紧急指针配合表示带外数据，实际几乎不用。窗口字段 16 位，是对端在未收到确认时允许发送的字节数上限，后面的窗口缩放选项会把它放大；校验和覆盖头部与数据，用于发现传输错误。

最后一个容易忽略的规则是序号消耗：SYN 和 FIN 各消耗一个序列号，纯 ACK 不消耗。所以客户端发出 seq=x 的 SYN 之后，服务端的确认号是 x+1 而不是 x。很多“确认号为什么多了一”的疑问，都来自这条规则。

三次握手：从 SYN 到 ACK

三次握手的每一步都在做两件事：交换初始序列号，以及确认对方既能收也能发。下面的时序图按 RFC 793 的状态名标注。

sequenceDiagram
    participant C as 客户端
    participant S as 服务端
    Note over S: LISTEN
    C->>S: SYN, seq=x
    Note over C: SYN_SENT
    S->>C: SYN + ACK, seq=y, ack=x+1
    Note over S: SYN_RCVD
    C->>S: ACK, seq=x+1, ack=y+1
    Note over C,S: ESTABLISHED

第一步，客户端调用 connect，内核选出一个初始序列号 x，发送 SYN 置位、ACK 未置位的报文段，随后进入 SYN_SENT。第二步，服务端从 LISTEN 收到 SYN，分配一个半连接结构记录对端信息，回复 SYN 与 ACK 同时置位、seq=y、ack=x+1 的报文段，进入 SYN_RCVD。第三步，客户端回复 seq=x+1、ack=y+1 的纯 ACK，进入 ESTABLISHED；服务端收到这条 ACK 后，把半连接结构升级为完整 socket 并放入 accept 队列，自己也进入 ESTABLISHED。此时连接对内核而言已经建立，但应用有没有调用 accept 并开始处理，是另一回事。

重传行为值得记住。客户端每发一次 SYN 就等待回应，超时后指数退避重发，Linux 的 tcp_syn_retries 默认为 6，最坏要约 127 秒才放弃；服务端的 SYN+ACK 由 tcp_synack_retries 控制，默认重发 5 次。所以“连不上”常常表现为几十秒到两分钟的卡顿，而不是立刻报错，这通常说明 SYN 被丢弃了；真正被拒绝时对端会回 RST，connect 立即返回 ECONNREFUSED。二者的区别是排障时第一件要分清的事。

为什么是三次，而不是两次

两次握手不够，原因有两层。第一层是能力确认：TCP 是全双工的，双方都得确认“我的发送能到达你”和“你的发送能到达我”。只有两次时，客户端能确认自己的发送能力，服务端却无法知道自己发出的 SYN+ACK 是否被客户端收到。

第二层是序列号同步，这层更隐蔽也更关键。序列号不只是编号，它划定了接收窗口的边界，也决定了哪些重复报文会被丢弃。客户端通过 SYN 告知 x，服务端通过 SYN+ACK 告知 y 并确认 x+1，客户端再用 ack=y+1 确认收到 y。至此两个方向的初始序列号都得到了对方的书面确认，任何一方都不会拿着一个对方根本不知道的起点开始发数据。

一个经典的反例能说明缺少第三次握手的后果。假设客户端一个早已失效的 SYN 在网络中滞留，很久之后才抵达服务端。服务端照常回复 SYN+ACK 并分配资源，如果没有第三次握手，它会单方面认为连接已经建立，然后一直空等永远不会到来的数据，资源被白白占用。有了第三次握手，客户端对这个来历不明的 SYN+ACK 会回一个 RST，服务端立刻回收资源。三次握手的本质，是让“陈旧报文”有机会在真正分配资源之前被识别出来。

握手同时还是一次选项协商的机会。MSS 选项告诉对方“我这个方向单个报文段最多能收多少字节载荷”，以太网环境下通常是 1460；不携带时默认按 536 处理，跨运营商链路时这个默认值会明显拖慢速度。窗口缩放选项把 16 位窗口左移若干位，最大放大到 2 的 14 次方，否则高带宽时延积的链路上窗口很快成为瓶颈。SACK permitted 允许接收方只确认收到的区间，一处丢包不必重传其后所有数据。时间戳选项既用于更精确的 RTT 测量，也提供防回绕的 PAWS 机制。这些选项只在 SYN 段中出现，且需要双方都支持才生效；如果中间设备把它们剥掉，连接仍然能建立，只是性能会悄悄退化。用 ss -ti 查看已建立连接的 mss 与 wscale，是确认协商结果的快捷方式。

服务端的两条队列与 backlog

服务端并不是收到 SYN 就立刻创建完整连接，中间隔着一层队列，这也是很多“握手成功但业务无响应”问题的根源。Linux 为每个监听 socket 维护两条队列：SYN 队列存放收到 SYN、尚未完成三次握手的半连接，长度受 net.ipv4.tcp_max_syn_backlog 约束；accept 队列存放已经完成握手、等待应用调用 accept 取走的完整连接，长度取 listen 传入的 backlog 与 net.core.somaxconn 中的较小值。

应用侧的 backlog 常被写成随意的数字，而 Nginx 默认为 511。这个值决定了内核最多替你排多少队，超过之后新的握手无法落地。accept 队列满时的默认行为是丢弃第三步的 ACK，客户端会认为连接已建立并开始发数据，服务端却在重传 SYN+ACK，双方认知不一致，表现为请求发出后长时间无响应；只有把 net.ipv4.tcp_abort_on_overflow 设为 1，内核才会改回 RST，让客户端立刻失败。生产环境通常保持默认值，转而把队列调大并保证应用及时 accept。

观察队列占用最直接的办法是 ss -lnt：监听态的 Recv-Q 就是当前 accept 队列长度，Send-Q 是上限。netstat -s 中的 listen queue overflow 计数则记录了历史溢出次数，它增长就说明应用消费得太慢，而不是网络有问题。

四次挥手、半关闭与 TIME_WAIT

关闭连接之所以需要四次，是因为 TCP 是全双工的：两个方向的数据流各自独立，一方说“我没数据要发了”，并不意味着它不再接收对方的数据。于是关闭被拆成两个方向各一次，加上各自的确认，共四段。

sequenceDiagram
    participant C as 主动关闭方
    participant S as 被动关闭方
    C->>S: FIN, seq=u
    Note over C: FIN_WAIT_1
    S->>C: ACK, ack=u+1
    Note over S: CLOSE_WAIT
    Note over C: FIN_WAIT_2
    S->>C: FIN, seq=v
    Note over S: LAST_ACK
    C->>S: ACK, ack=v+1
    Note over C: TIME_WAIT
    Note over C,S: 2MSL 后关闭

主动关闭方发送 FIN 后进入 FIN_WAIT_1，收到对方的 ACK 进入 FIN_WAIT_2，此时它这一侧的发送通道已经关闭，但仍能接收数据，这就是半关闭。被动关闭方收到 FIN 后进入 CLOSE_WAIT，这个状态的含义非常明确：内核已经把对端的关闭请求交给了应用，正等应用调用 close。如果大量连接长期停在 CLOSE_WAIT，问题一定在应用代码里，通常是忘了关闭 socket 或者关闭前阻塞在某个操作上，与网络无关。应用关闭后发出自己的 FIN，进入 LAST_ACK，收到最后的 ACK 才真正释放。

TIME_WAIT 只出现在主动关闭的一方，且要持续 2MSL，Linux 上约为 60 秒。它有两个不可省略的理由：一是保证最后那个 ACK 能到达对方，如果 ACK 丢了，对方会重传 FIN，处于 TIME_WAIT 的一方还能再回一次 ACK，否则对方会一直卡在 LAST_ACK；二是让这条连接上的旧报文在网络中自然消亡，避免它们被随后复用同一四元组的新连接误收。所以 TIME_WAIT 是协议正确性的一部分，不是内核的缺陷。

代价则集中在端口上。客户端每次主动关闭都占用一个本地端口约一分钟，作为反向代理或压测工具时很容易把临时端口耗尽，表现为 Cannot assign requested address。net.ipv4.tcp_tw_reuse 允许在时间戳递增的前提下复用 TIME_WAIT 的端口发起新连接，只对主动发起方有效，相对安全；而曾经流行的 tcp_tw_recycle 依赖对端时间戳的单调性，在 NAT 后面大量主机共享源 IP 时会误丢报文，从 Linux 4.12 起已被移除，不应再作为调优项。服务端的 SO_REUSEADDR 解决的是另一个问题：让监听 socket 在重启时能绑定仍处于 TIME_WAIT 的端口，避免 Address already in use。

RST 与 SYN flood 的防御视角

RST 是 TCP 里的急刹车，收到它的连接立即释放，不进入 TIME_WAIT，在途数据可能直接丢失。常见来源有四类：目标端口没有监听，内核直接回 RST；应用崩溃或被 kill -9，内核代为复位它持有的连接；防火墙配置为 reject 而非 drop，由设备伪造 RST；以及设置了 SO_LINGER 且超时为 0，close 时直接发 RST 丢弃发送缓冲区。此外，一端重启后收到对端数据也会回 RST，这是半开连接被发现的常见方式。

RST 也是拒绝服务的工具。SYN flood 的做法是大量伪造源地址的 SYN，让服务端的 SYN 队列被半连接填满，真正的客户端 SYN 无处安放，SYN+ACK 又都发往不存在的地址，于是正常用户看到的是连接超时。防御手段有几层：开启 net.ipv4.tcp_syncookies=1，队列溢出时内核不再保存半连接状态，而是把必要信息编码进 SYN+ACK 的序列号，收到合法 ACK 再重建；适度调大 tcp_max_syn_backlog 并降低 tcp_synack_retries，缩短资源占用时间；在边界设备上对新建 SYN 做速率限制，例如用 iptables 的 limit 模块对每秒新建连接设阈值；规模较大的站点还可以把清洗放到上游 CDN 或专用抗 D 设备。SYN cookies 会牺牲部分选项协商能力，属于应急手段而非日常配置。

把结果放进 Wireshark 后，显示过滤器的写法类似：tcp.flags.syn == 1 && tcp.flags.ack == 0 只看第一个 SYN，tcp.flags.reset == 1 只看复位，tcp.analysis.flags 则会标出重传、乱序与零窗口。访问一个正常监听的端口，抓到的前三段应是 SYN、SYN+ACK、ACK，之后才是数据；访问一个没有监听的端口，则是 SYN 之后紧跟一个 RST+ACK，curl 立刻报 connection refused。

全局视角可以看计数器。ss -s 给出各状态连接的总量，TIME_WAIT 数量是否异常一目了然；netstat -s 里的连接复位次数、因队列满而丢弃的 SYN 数量、重传段数，分别对应拒绝、丢弃与链路质量问题。常见现象可以按下表对号入座。

现象 可能原因 失败环节
立即返回 connection refused 端口未监听，或防火墙配置为 reject SYN 之后收到 RST
卡住数十秒后超时 SYN 被 drop、SYN 队列溢出、路由不通 第三步之前就断了
连接成功但请求无响应 accept 队列满，应用未 accept 或处理慢 握手完成，应用未就绪
传输中被 reset 应用崩溃、中间设备空闲超时、SO_LINGER 为 0 已建立连接被复位

最后是几个常见误区。其一，把第三步的 ACK 当成数据确认：它的确认号指向的是对方的 SYN，x+1 与 y+1 都不是数据边界。其二，把 TIME_WAIT 当故障，动手改参数之前先确认端口是否真的耗尽。其三，只看 CPU 与带宽，不看 accept 队列，于是握手成功而请求超时的问题被误判成网络故障。其四，在 NAT 环境沿用 tcp_tw_recycle，造成间歇性丢包且极难复现。其五，认为三次握手成功就代表应用就绪，实际上内核完成握手时，应用可能还没开始监听业务逻辑。

小结

三次握手的核心是双向能力确认与初始序列号同步，缺一次就会留下陈旧报文与半开连接的隐患。四次挥手源于全双工的两个方向各自关闭，TIME_WAIT 是保证可靠关闭的必要状态，应当管理而不是消灭。把 SYN 队列与 accept 队列区分开，能解释大部分“握手成功但请求无响应”的问题。抓包时先用标志位过滤确认握手是否完整，再结合 ss 与 netstat -s 的计数定位是拒绝、丢弃还是应用消费过慢。调优参数要结合内核版本，已经被移除的选项不要再照抄旧文章。
