Redis 缓存穿透、击穿与雪崩

缓存是大多数系统抵御数据库压力的第一道堤坝，穿透、击穿、雪崩是这道堤坝最常见的三种溃口。三者都表现为数据库流量陡增，但触发条件、影响范围与处置手段不同。本文沿 cache-aside 读取路径拆解三种故障，给出防御手段与取舍，并用一段 Go 代码把空值缓存、互斥重建与 TTL 打散组装起来。读者应已用 Redis 做过业务缓存，希望把“能挡住”变成“知道为什么能挡住”。

三种故障，一条读取路径

先固定读取路径。cache-aside 是绝大多数业务缓存的写法：读请求先查 Redis，命中就直接返回；未命中再查数据库，把结果写回缓存并设置过期时间。写请求绕过缓存直接落库，再让对应的缓存失效。

flowchart TD
    A["读请求到达"] --> B["查询 Redis"]
    B -->|命中| C["返回缓存值"]
    B -->|未命中| D["查询数据库"]
    D -->|有数据| E["写回缓存并设置 TTL"]
    D -->|无数据| F["穿透：每次请求都落到数据库"]
    B -->|热点 key 刚过期| G["击穿：同一 key 并发回源"]
    B -->|大批 key 同时失效| H["雪崩：回源流量整体放大"]

正常的未命中并不可怕：回源一次、写回缓存，下一次就命中了。真正的问题是回源的规模与时机失控。穿透是“这个 key 根本不存在”，没有可写回的东西，于是每次都穿过去；击穿是“这个 key 存在，但缓存刚过期”，并发请求一起回源；雪崩是“大片 key 同时不可用”，回源流量整体放大。三者分别是内容、时间与范围的问题。

故障 触发条件 典型特征
穿透 key 在缓存和数据库中都不存在 大量不同的 key，缓存命中率极低
击穿 单个热点 key 过期 同一个 key 的并发请求同时回源
雪崩 大批 key 同时失效，或 Redis 整体不可用 回源流量整体上涨，波及所有 key

排查时先问两个问题：不存在的 key 占比是否异常高？失效是否集中在同一时刻或同一台实例？答案决定先上布隆过滤器，还是先做互斥重建与 TTL 打散。

缓存穿透：查不到的键

穿透指请求查询一个在缓存和数据库里都不存在的 key。缓存不命中，数据库也查不到，没有结果可以写回，每次请求都要完整查库。正常 miss 回源一次就会被缓存接住，穿透的 key 没有可缓存的值，下一次仍然 miss，请求仿佛穿过了缓存层。

成因有三类。第一类是恶意构造，攻击者用自增 ID、随机字符串遍历接口，查询不存在的记录；第二类是业务遗留，数据已删除，旧链接、爬虫仍在反复请求；第三类是参数没有校验，id=-1、超长字符串等非法标识都能进入查询逻辑。三类共同点是查询目标为空，防御思路也统一：入口挡住，或让缓存记住“不存在”。

最便宜的一层是入口校验与限流。在网关或接口层校验 ID 的格式、长度与取值范围，非法请求直接返回；再按 IP 或用户限流，把遍历式请求压在边缘。它不能替代后面的方案，但能减少进入核心链路的无效流量。

第二层是空值缓存。数据库查不到时，不直接返回，而是往 Redis 写一个占位值，并设置较短的 TTL，例如 30 到 120 秒。这样同一个不存在的 key 在 TTL 内只会回源一次。要点有三个：占位值要与正常值可区分，不能把空字符串当合法数据；TTL 必须设置，否则一次误查会永久占用内存；数据被创建时要能删除占位，或接受 TTL 内的短暂不一致。空值缓存也有反作用：海量随机 key 会各写一个占位，迅速放大内存，因此要配合限流或布隆过滤器。

第三层是布隆过滤器。它用位数组和若干哈希函数表示“哪些 key 可能存在”：请求先经过过滤器，判定不存在就直接返回。单机可以用 Guava 的 BloomFilter；多实例共享可以用 RedisBloom，先 BF.RESERVE 声明容量与误判率，再用 BF.ADD、BF.EXISTS 读写。它的误判方向是安全的：只会把不存在的 key 误判为存在，不会丢数据；前提是数据新增时同步写入过滤器。

代价是位数组随容量增长，容量估小会抬高误判率；标准布隆过滤器不支持删除，删除数据后只能定期重建，或改用计数布隆、布谷鸟过滤器。它需要全量预热，扩容时还要考虑重建窗口。

缓存击穿：一个热点键的过期

击穿指某个被高并发访问的 key 在某一刻过期，重建完成前的窗口里，请求同时发现缓存未命中，于是一起回源。数据本身存在，只是缓存暂时为空，这一点与穿透不同；影响通常只有一个 key，但它往往承载很大流量，后果未必比大面积失效轻。首页商品、活动配置、榜单首位，都是典型对象。

sequenceDiagram
    participant C as 客户端
    participant R as Redis
    participant D as 数据库
    C->>R: 读取热点 key
    R-->>C: 未命中，刚过期
    C->>D: 并发查询同一条记录
    D-->>C: 连接池耗尽，响应变慢
    Note over R,D: 重建完成前形成正反馈

从过期到回填之间有一个重建窗口。假设窗口是 200 毫秒，期间有数千个请求到达（示例值），它们同时查库，连接池很快见底，排队又拉长恢复时间，故障因此被放大。

第一种方案是互斥重建，也叫 single-flight。缓存未命中时先抢一把锁，抢到的请求负责查库并回填，没抢到的短暂等待后重读缓存。跨实例用 SET lock NX PX，释放时用 Lua 比对持有者再删除；单实例用进程内互斥或请求合并。等待必须有上限：超时后返回旧值、降级或快速失败，不能无限自旋。

第二种方案是逻辑过期。缓存值里带上一个 expireAt 字段，Redis 的物理 TTL 设得更长甚至不设；读到逻辑过期时先返回旧值，同时异步触发一次刷新，刷新同样用锁保证只有一个执行者。它用短暂的不一致换稳定延迟，适合能容忍几十秒旧数据的场景；代价是调用方要接受旧值，刷新失败要有报警。

第三种方案是热点不过期。对确认的热点 key 不设置 TTL，由后台任务或数据变更事件主动刷新。它最稳定，也最依赖运维：刷新任务失效后数据会永远陈旧，必须配套陈旧检测和手动重建入口。三种方案并不互斥，实践中常常是热点不过期加异步刷新，普通 key 用互斥重建。

锁释放的瞬间，等待中的请求会同时醒来再次未命中，形成第二波回源；客户端自动重试还会把一次失败放大成多次。等待方应加随机退避，服务端限制单 key 的重建并发，客户端只对幂等读重试。

缓存雪崩：大面积同时失效

雪崩有两种成因。第一种是批量写入的 key 用了相同 TTL，例如凌晨统一预热、统一设置 24 小时过期，到期时刻高度集中；第二种是缓存层整体不可用，包括单点宕机、主从切换、网络分区、内存打满导致大量淘汰，以及重启后的冷缓存。前者是时间集中，后者是容量塌陷，结果都是请求绕过缓存压向数据库。

击穿是点，雪崩是面。雪崩时互斥锁救不了场：要重建的 key 太多，锁只会把请求排更长的队，占满连接和线程。因此防御重点不在单个 key，而在削峰、分流和兜底。

TTL 打散最简单：给基础过期时间加随机偏移，例如 30 分钟加减 5 分钟（示例），并把计算封装进统一写入函数，禁止业务代码写死。同一批数据同时写入，失效时刻也会被摊开。

错峰预热与分级加载是第二条。启动或重建时不要瞬间加载全量数据，按优先级分批进行并控制回源并发，低优先级数据可以延迟加载。冷缓存直接承接全量流量，本身就是一次自制的雪崩。

第三条是多级缓存。进程内保留一份容量和 TTL 都有上限的本地缓存，Redis 不可用时它还能挡住一部分读请求；代价是一致性变弱，需要短 TTL 或失效广播来收敛。本地缓存要有容量上限，否则会把内存问题搬进应用进程。

第四条是熔断与降级。监测数据库 QPS、连接池等待、Redis 错误率，超过阈值就切换降级路径：默认值、旧值、排队页，或关闭非核心功能。开关要能人工触发，也能在流量回落后自动恢复，否则一次误判会长期影响业务。

最后是数据库保护与高可用。回源加信号量，把并发限制在数据库能承受的范围内，排队超时就快速失败；Redis 侧用哨兵或集群做故障转移，用持久化缩短恢复时间。故障转移本身也有不可用窗口，应用要把它当成常态。

热点键、一致性与容量边界

热点键的识别有三条路：业务侧按页面或商品埋点采样；代理层按 key 统计转发次数；Redis 侧用 redis-cli --hotkeys，但它要求 LFU 策略（allkeys-lfu 或 volatile-lfu），结果是采样值，只能作参考。

处置思路是“分散”与“就近”：给 key 加后缀拆到多个实例，读时聚合；把最热的一小批放进有容量上限的本地缓存；或增加只读副本分担读流量。拆分让统计和更新变复杂，本地缓存引入不一致，取舍取决于能接受多旧的数据。

一致性只划边界。cache-aside 推荐先更新数据库、再删除缓存：并发读最多把旧值回填一次，后续删除会修正；反过来先删缓存再更新库，删除与更新之间到达的读请求会把旧值写回。更新缓存则要面对并发写乱序与无效写。延迟双删、binlog 订阅都是补偿手段，只保证最终一致，完整方案另文讨论。

容量也会制造雪崩。maxmemory 必须设置并留出碎片空间，maxmemory-policy 按场景选择：纯缓存通常用 allkeys-lru，只淘汰带 TTL 的 key 可用 volatile-lru，但可淘汰 key 不足时会返回 OOM；noeviction 适合需要感知写入失败的场景。内存贴着上限会出现淘汰风暴，命中率骤降、回源放大，应把水位控制在七成（经验值）并监控 evicted_keys。连接池与各类超时也要有上限，缓存调用单独隔离，超时快速失败，别让缓存抖动占满业务线程。

用 Go 写一层缓存保护

下面用 Go 1.15 与 go-redis v8 把空值缓存、互斥重建与 TTL 打散串起来。代码省略了日志与指标，但保留了失败分支。

失败路径需要单独说明。Redis 超时返回的不是 redis.Nil，此时直接受限回源，不要在原地重试三次；数据库报错时不要把错误写进缓存，否则一次故障会被固化一整个 TTL；持锁进程崩溃后锁在 3 秒后过期，所以锁的 TTL 必须大于回源耗时上限；释放锁用 token 比对，避免删掉别人的锁。等待方只等 50 毫秒，没等到就返回 ErrBusy，由上层退避重试，这比所有等待方一起查库安全。singleflight 只合并单进程请求，多实例间仍靠 Redis 锁，两层各司其职。

监控、演练与常见坑

指标要连起来看：缓存命中率（总体与按 key 前缀）、未命中次数、数据库 QPS 与连接池等待、锁等待时长与 ErrBusy 比例、Redis 的 p99 延迟、evicted_keys、拒绝连接数与超时错误。命中率从基线掉下来、数据库 QPS 同时抬升，基本可以判定回源放大；淘汰计数持续增长说明内存水位过高。阈值应来自压测与历史分位数，不要照搬别人的数字。

演练比告警更能暴露问题：在预发环境杀掉 Redis 进程，观察服务是否在超时内降级、恢复后是否出现回源尖峰；手动删除热点 key，确认只有一个请求回源；给一批 key 设置同一秒过期，验证打散是否生效；用 tc 注入延迟，检查超时与熔断。演练要记录恢复时间，而不只是“没挂”。

常见坑列在这里：空值缓存忘记设 TTL；锁没有过期时间；用 DEL 裸删锁；所有 key 在同一秒过期；把 Redis 当成一定可用的存储，代码里没有降级分支；失败后立刻递归重试，把流量放大。每条都对应前面的一节。

小结

穿透是 key 不存在，击穿是热点 key 恰好过期，雪崩是成片缓存同时失效，结果都是回源放大。穿透靠入口校验、空值缓存与布隆过滤器；击穿靠互斥重建、逻辑过期与热点不过期；雪崩靠 TTL 打散、多级缓存与降级。所有手段都有代价，选型前先明确能接受多旧的数据、多大的误判与多少额外内存。缓存不是数据库的替代品，最后的闸门仍是数据库侧的并发保护与可观测性。
