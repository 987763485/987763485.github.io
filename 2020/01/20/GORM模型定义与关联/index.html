GORM 模型定义与关联

本文属于《Go 语言与工程》第 73/78 篇
上一篇系列目录下一篇

服务上线半年后，表结构往往比代码更难改：字段类型、索引、外键都沉在数据库里，模型结构体是它们唯一的文字说明。本文从 GORM 1.x 的导入路径讲起，依次说明模型约定、字段 tag、时间与软删除、主键与索引，再把 has one、belongs to、has many、many to many 四种关联的 1.x 写法逐个写全，最后落到 AutoMigrate 的边界与常见坑。查询与预加载留给《GORM 关联查询与预加载》，事务与钩子另有一篇，本文只关心表长什么样、关系怎么声明。

先确认版本：GORM 1.x 的导入路径

GORM 1.x 的包路径是 github.com/jinzhu/gorm，MySQL 驱动单独放在 github.com/jinzhu/gorm/dialects/mysql，以匿名导入的方式注册方言。打开连接用 gorm.Open("mysql", dsn)，第一个参数是方言名，第二个是 DSN，返回 *gorm.DB 与 error 两个值。本文所有示例都基于它。

DSN 里 parseTime=True 不能省，否则 time.Time 字段扫描会失败；loc 决定时间如何解释，charset=utf8mb4 保证四字节字符可以写入。连接池通过 db.DB() 取到底层 *sql.DB 再设置。

需要提前说明一点：GORM 的下一代版本已经在开发中，导入路径将换成 gorm.io/gorm，Open 也改为接收 Dialector，两代 API 不兼容。本文全部基于 1.x，看到 gorm.io 开头的示例请先放下，混用会得到一堆编译错误。

模型约定：gorm.Model、表名与主键

gorm.Model 是 1.x 提供的一个可嵌入结构体，包含四个字段：ID uint、CreatedAt time.Time、UpdatedAt time.Time、DeletedAt *time.Time。嵌入它等于拿到自增主键、两个自动时间戳和软删除能力，大多数业务表都可以从它开始。如果主键要叫别的名字，或者时间字段要换列名，就不要嵌入，自己声明并按需加 tag。

表名默认由结构体名复数化得到：User 对应 users，Order 对应 orders，Company 对应 companies，Person 对应 people。规则来自英文屈折变化，遇到不规则名词或遗留表名时，最稳妥的做法是实现 TableName() 方法。它返回空字符串时 GORM 仍会退回默认规则，所以不要用返回值来“条件化”表名。若整个项目都想关闭复数化，可以在初始化时调用 db.SingularTable(true)，但同一项目里不要两种风格并存。

主键的默认约定是名为 ID 的字段。主键叫 UID 或 ArticleID 时，必须显式写 gorm:"primary_key"，否则 GORM 会认为这张表没有主键，First、Update 之类依赖主键的方法都会表现异常。1.x 只支持单列主键，复合主键要用联合唯一索引模拟，不能靠两个 primary_key tag 实现。

字段 tag：把 Go 类型翻译成 MySQL 类型

GORM 1.x 的字段 tag 写在 gorm:"..." 里，多个设置用分号分隔。常用键有 column（列名）、type（完整列类型）、size（长度）、not null、default、index、unique_index、primary_key、auto_increment。其中 type 优先级最高，写了它就不再走默认映射；size 是 type 的简写，只对字符串和字节切片有意义。

默认映射值得背下来：string 是 varchar(255)，int 是 int，int64 是 bigint，uint 是无符号整型，bool 是 tinyint(1)，time.Time 是 datetime，[]byte 是 blob。比如邮箱要建唯一索引，varchar(255) 在 utf8mb4 下可能超过旧行格式的索引长度限制，应主动收窄到 191；正文要存长文本，应写 type:mediumtext，而不是把 size 调到几万。

字符串的 default 值要带引号，写成 default:'' 或 default:'draft'；数字和布尔值直接写。not null 与 Go 的零值并不等价：没有 not null 时，零值字符串会以空串写入，而不是 NULL，想让“未填写”落成 NULL，字段类型本身就得是指针。

时间字段与软删除

嵌入 gorm.Model 后，CreatedAt 与 UpdatedAt 由 GORM 自动维护：Create 时两者都填当前时间，Save 与 Update 时刷新 UpdatedAt。绕过这一步的 API 是 UpdateColumn 与 UpdateColumns，它们既不触发 Hook 也不更新时间戳。

DeletedAt *time.Time 是软删除开关。字段存在时，db.Delete 不再发 DELETE，而是发 UPDATE ... SET deleted_at = NOW()；此后所有查询自动补上 deleted_at IS NULL，First 查不到，列表里也不会出现。要看已删除的数据，用 Unscoped() 摘掉默认作用域；要真正删行，用 Unscoped().Delete。注意 Unscoped 是全有或全无的开关，它连关联上的软删除条件一起关掉。

时间语义还有两个配置点。DSN 的 loc 决定驱动如何解释数据库返回的时间，MySQL 会话的 time_zone 决定 NOW() 按哪个时区计算，两者不一致时，同一条记录在写入和读出时会平移几个小时。笔者的习惯是数据库统一存 UTC，展示层再转本地时区，并在 DSN 里固定 loc=UTC。另外，time.Time 的零值是 0001-01-01，MySQL 的 datetime 不接受这个值，严格模式下会直接报错；可空时间一律用 *time.Time。

主键与索引：少而准

整型主键默认自增，不需要额外 tag。字符串主键则要自己生成值，并在 Create 之前赋好，否则插入的是空串，第二行就会撞主键。UUID 去掉横线是 32 位，适合 char(32)；带横线用 char(36)。字符串主键的代价是索引更大、插入更随机。

索引通过 tag 声明。index 生成普通索引，unique_index 生成唯一索引；带名字时，多个字段使用同一个名字就会合成复合索引，字段顺序就是索引列顺序。命名建议统一成 idx_表名_列名 与 uk_表名_列名，排查慢查询时容易对上。复合索引遵循最左前缀，(city, status) 能服务按城市查、按城市加状态查，却服务不了只按状态查。

索引不是越多越好。每个二级索引都要在写入时同步维护，数据量大时插入性能会下降；优化器面对过多索引也可能选错。唯一索引还承担业务约束，比在代码里先查后插可靠，但要注意 MySQL 把多个 NULL 视为互不相同，可空列上的唯一索引并不会阻止多行 NULL。

四种关联：外键到底放在哪张表

GORM 1.x 的关联只有一条判断依据：外键字段在哪张表上。belongs to 的外键在本方，has one 与 has many 的外键在对方，many to many 两边都不放，靠中间表连接。默认外键名是“关联类型名 + 主键名”，例如 UserID、CompanyID；默认被引用的列是对方主键。遵守约定时这些 tag 可以省略，偏离约定时才必须写出来。

has one 表示“一个用户有一个档案”，档案表持有 user_id。结构体里写值类型 Profile，不要写指针。belongs to 表示“一张订单属于一个用户”，外键 UserID 在订单表上，结构体里同时保留外键与关联字段，名字要能对应上。

has many 与 has one 的外键位置相同，区别只在字段是切片。切片里的元素不会随普通查询自动带出，需要预加载或关联写入时才会填充，这一点常被误解为“关联失效”。

多对多用一个 tag 声明中间表，两边结构体都不出现外键字段。tag 的值就是中间表名，1.x 不会根据模型名自动推导，写错一个字母就会多出一张表。

外键与引用：1.x 的 foreignkey 系列

真实项目很少完全符合约定。老订单表可能用 buyer_no 关联用户，用户表用 member_number 做业务键。这时要改两处：子表用哪个字段做外键，父表用哪个字段被引用。前者写 foreignkey，后者写 association_foreignkey，两个值都写结构体字段名，不是数据库列名。字段改名后 tag 忘了同步，是关联查不到数据的最常见原因。

belongs to 的 foreignkey 指本方字段，association_foreignkey 指对方字段；has one 与 has many 的写法相同，但两侧角色互换：foreignkey 指对方（子表）字段，association_foreignkey 指本方（父表）字段。这个对称关系容易绕晕，记忆方法是“foreignkey 永远指向存外键的表”。

1.x 没有 references，也没有 uniqueIndex、constraint 这类 GORM 2 的 tag 键。写了不认识的键不会报错，只会被静默忽略，结果是索引没建、外键没按预期对应，排查时非常费时间。

三个 association_* 开关控制写入时的连带行为。association_autocreate 决定 Create 主记录时是否顺带创建关联记录，默认 true；association_autoupdate 决定 Save 时是否更新关联记录，默认 true；association_save_reference 决定保存关联后是否把关联的主键回写到本方的外键字段，默认也是 true。从请求体直接绑定模型时，前两个开关尤其危险：客户端多传一个嵌套对象，就可能凭空插入一行公司数据。业务代码里通常显式关掉，改为在 service 层按字段赋值。

多对多：连接表也是一张表

many2many:user_roles 会在数据库里建一张 user_roles，两列默认叫 user_id 与 role_id，它们分别指向两张表的主键。这张表没有对应的 Go 结构体，但它是实打实的表，需要联合唯一索引来防止重复：同一对用户与角色被追加两次，Preload 出来就会有重复项，ORM 不会替你去重。

AutoMigrate 会创建连接表，但不要假设它替你补好了所有约束。上线前用 SQL 确认主键或唯一索引存在，是最省事的办法。连接表还需要两个方向都能查，两列上都要有索引，联合唯一索引的最左前缀只能服务一个查询方向。

连接表一旦需要额外字段，比如授权时间、授权人、授权来源，它就不再是纯连接表。1.x 的 many2many 无法给中间表映射字段，正确做法是建独立模型 UserRole，用两个 has many 分别从用户和角色出发，写入时直接操作这个模型。不要一边保留 many2many，一边手写 SQL 往同一张表插数据。

AutoMigrate：能做什么，不能做什么

AutoMigrate 接收一组模型指针，按模型定义补建表、补列、补索引，并创建缺失的连接表。它不会删除模型里已经不存在的列，这是保护数据的默认策略；类型变更也只覆盖长度、精度、可空性这类有限场景，不能当成完整的 schema 迁移工具。自动生成的外键约束未必带得上你想要的更新、删除策略，需要明确控制时仍要单独调用 AddForeignKey。

生产环境直接跑 AutoMigrate 有几个现实风险。DDL 会拿元数据锁，长事务未提交时，一条 ALTER TABLE 可能把整张表的读写都堵住；它没有版本记录，也没有回滚脚本，出问题只能靠备份。笔者的做法是：开发和测试环境用它快速对齐结构，生产环境用带版本号的 SQL 迁移脚本，AutoMigrate 最多在启动时对空库执行一次。迁移工具的选择不在本文范围。

模型与 DTO 分离：数据库结构不等于接口契约

把模型直接序列化成 API 响应，短期省事，长期一定出问题。模型里有密码哈希、内部状态、软删除时间，还有可能被预加载进来的关联对象；响应体会跟着膨胀，客户端还会把内部字段当成稳定契约。正确做法是为接口定义独立响应结构体，只放需要暴露的字段，转换在 handler 层完成。

两个 tag 经常被混淆。json:"-" 只影响 JSON 序列化，字段照常建列、照常读写；gorm:"-" 只影响 GORM，字段不建列、不参与查询，但会被 JSON 序列化。像登录后临时计算的 Token，应该同时写 gorm:"-" json:"token,omitempty"；像密码哈希，写 json:"-" 就够，数据库里仍要保留。

命名与组织：一个文件一个模型

模型放在独立包里，通常叫 model 或 domain，一个文件一个聚合根，文件名与结构体同名的小写下划线形式。TableName() 紧挨着结构体写，改表名时不用满项目搜索。

依赖方向要单向：model 不 import service，也不 import repository；service 依赖 model 与 repository；handler 依赖 service 与 DTO。模型方法只放与自身状态有关的纯逻辑，比如 DisplayName()、CanCancel()，不要在里面查库。需要多条记录或跨表协作的逻辑放进 service，否则模型会逐渐变成什么都干的上帝对象。包之间出现循环引用，多半是某人把查询塞进了模型方法，先把这层拆开，比调整目录结构有效。

常见坑清单

  • tag 拼写用了 2.x 的键，例如 uniqueIndex、references、constraint。1.x 不报错，直接忽略，结果是索引缺失、关联按默认规则走。
  • 表名不符合预期。先确认复数化结果，再检查有没有 TableName()；person、category 这类词最容易翻车。
  • 关联查不到数据。检查 foreignkey 写的是不是结构体字段名，以及字段改名后 tag 是否同步。
  • AutoMigrate 静默失败。多因没取 .Error，或没有建表权限、索引超过长度限制。启动阶段必须判错并退出。
  • 软删除后唯一索引冲突。已删除的行仍占着 email，同一邮箱不能重新注册。可选方案是删除时改写唯一列、改用 is_deleted 标志位，或把已删除记录归档到历史表。
  • 时间字段零值。time.Time 的零值写入严格模式会报错，可空时间用 *time.Time，并确认 DSN 的 parseTime 与 loc。
  • 把模型直接返回。密码哈希、内部状态、软删除时间都会泄漏，接口契约也会被数据库结构绑架。

小结

模型定义是把数据库结构写成 Go 代码，关联声明则是在代码里重复一遍外键的位置。先把版本钉在 GORM 1.x，记住 foreignkey 与 association_foreignkey 指向字段名、many2many 的中间表也是实体；再用 tag 精确控制列类型与索引，用 TableName() 处理遗留表名，用 DTO 隔离接口契约。AutoMigrate 适合开发环境快速对齐，生产环境交给带版本的迁移脚本。把这些约定写进项目模板，比每次评审时口头提醒更可靠。
