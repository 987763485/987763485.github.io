Go 垃圾回收机制解析

本文属于《Go 语言与工程》第 42/78 篇
上一篇系列目录下一篇

Go 服务跑得久了，总会遇到与内存有关的问题：堆为什么涨得比预期快，GC 为什么在高峰期变频繁，调大 GOGC 到底换来了什么。本文以 Go 1.13 的实现为准，从堆与对象分配讲起，依次拆开三色标记、写屏障、辅助标记与 pacer，再落到 gctrace、MemStats 和调优手段。读者应当已经能写 Go 服务，但还说不清运行时在背后做了什么。

一、为什么 Go 需要垃圾回收

手动管理留下的三笔账

在 C 和 C++ 里，malloc 与 free 成对出现，释放时机由程序员决定。这套模型给了极致的控制力，也把三笔账留给了人：忘记释放造成泄漏，提前释放造成悬垂指针，重复释放直接破坏堆。单线程小程序尚可靠纪律维持，到了高并发的服务端，对象的生命周期跨越请求、跨 goroutine、跨缓存层，“谁该在什么时候释放”很快变成一张没人能完整维护的所有权图。

RAII 与智能指针缓解了问题，却没有消除问题。引用计数要付出每次拷贝的原子操作，环状引用仍然需要人工打破；更根本的是，一旦语言允许共享可变状态，编译器和运行时都很难静态证明某块内存已经无人使用。

Go 的选择

Go 选择了带垃圾回收的静态语言，但它没有把所有对象都推给 GC。值类型、栈分配与逃逸分析让大量临时对象留在 goroutine 栈上，函数返回时随栈帧一起消失，不需要 GC 介入；只有逃逸到堆上的对象才进入回收流程。这个设计很关键：GC 的成本与堆上对象的数量、存活率直接相关，而编译器在前面已经替运行时挡掉了一部分工作。

吞吐、延迟与内存的三角

评价一个 GC，通常看三个维度。吞吐是用户代码拿到 CPU 的比例，GC 占得越多，吞吐越低；延迟是单次停顿与尾延迟，STW 越长、辅助标记越重，长尾越难看；内存占用则是堆目标与归还策略的结果，GC 越懒，堆越大。三者互相拉扯：想让 GC 少跑，就放宽堆目标，代价是内存；想省内存，就提高频率，代价是 CPU 与延迟。

Go 1.13 的取舍是并发标记加两次短暂的 STW，后台标记默认最多占用四分之一的 P，把大部分标记工作与用户代码重叠。它的停顿目标是亚毫秒级，但这是工程目标而非硬实时承诺：goroutine 数量、栈深度、分配速率和机器负载都会让实际停顿偏离目标。理解这一点，才不会把“Go 的 GC 很快”当成可以随意分配的借口。

二、堆、span 与对象分配

页、span 与 size class

Go 的堆按页管理，64 位平台上每页 8 KB。连续的若干页组成一个 mspan，每个 span 只服务一种尺寸等级（size class），内部被切成等大的槽位。1.13 一共定义了 67 个尺寸档位，覆盖 8 字节到 32 KB；超过 32 KB 的对象被视为大对象，不再走尺寸分级，而是直接按页数分配。

尺寸分级的意义在于降低碎片：如果所有小对象都按实际大小切分，堆里会充满难以复用的缝隙；把尺寸归并成有限档位后，一个槽位释放后很容易被同尺寸的下一个对象复用。代价是内部碎片，比如申请 20 字节会落到 24 字节的档位，多出的 4 字节无法被别的对象使用。

mcache、mcentral 与 mheap

分配路径是一条三级缓存。每个 P 有一份 mcache，里面缓存了各个尺寸档位的当前 span，小对象分配直接在这里完成，不需要加锁。mcache 用完当前 span 后，向 mcentral 申请；mcentral 每个尺寸档位一个，维护两个链表：还有空槽位的 nonempty 与已满的 empty。mcentral 也没有可用 span 时，才向全局的 mheap 要。mheap 管理按 64 MB 划分的 arena、空闲 span 与位图，真正向操作系统申请内存的是它。

这条路径的设计目的很明确：绝大多数分配走无锁的 mcache，把锁竞争压到 mcentral 与 mheap。代价是内存驻留：mcache 与 mcentral 会缓存暂时用不到的 span，HeapSys 因此高于当前存活对象所需。

小对象、tiny 对象与大对象

小于 16 字节且不含指针的对象走 tiny 分配器：它们被合并进同一个 16 字节块，多个小对象共享一块内存，进一步减少碎片与分配次数。普通小对象（不超过 32 KB）走上面的 mcache 路径。大对象直接由 mheap 按页分配，不经过尺寸分级，也不缓存到 mcache。

对象是否含指针，同样影响 GC。运行时把对象分为 scan 与 noscan 两类：不含指针的对象在标记时不需要继续扫描其内部，标记工作量小得多。tiny 分配器只合并 noscan 对象，正是这个原因。写代码时，减少结构体里的指针数量、把一组小对象合并成切片，往往比调 GC 参数更有效。

分配就是 GC 的燃料

每次堆分配都在消耗一份预算。运行时维护一个“距离目标堆还有多少”的计数，分配推进这个计数，达到阈值就触发下一轮 GC；标记期间分配过快，则会触发辅助标记。换句话说，GC 的频率不是定时器决定的，而是由分配速率和存活堆共同决定的。理解这一点，“为什么高峰期 GC 变频繁”就不再需要神秘解释。

三、三色标记与写屏障

颜色描述的是处理进度

三色标记把堆上的对象分成三种状态。白色表示还没有被 GC 访问到，理论上可能是垃圾；灰色表示已经发现，但它的引用还没有扫描完；黑色表示自身和它的直接引用都已经处理完。标记从根集合出发：全局变量、各个 goroutine 的栈、寄存器里的指针都算根。根对象先被染灰放进队列，标记线程不断取出灰色对象，扫描它的每个指针字段，把指向的白色对象染灰入队，自己转为黑色。队列空了，剩下的白色对象就是不可达的。

实际实现里，灰色对象放在每个 P 的工作缓冲中，缓冲满了就转移到全局队列，后台标记线程通过 work stealing 从别的 P 那里取活，避免某个 P 闲着而另一个 P 排队。颜色并不存储在对象头里，而是通过堆位图与 span 的状态推导出来，这样不需要在对象里额外留几位。

并发标记为什么会漏

如果标记期间用户代码不动，三色标记很简单。麻烦在于标记与赋值器（mutator，也就是用户 goroutine）同时运行，指针关系随时变化。考虑一个黑色对象 B，它已经扫描完毕；此时用户代码让 B 指向白色对象 W，同时删除了从灰色对象 G 到 W 的唯一边。标记线程不会再扫描 B，W 又是白色，于是 W 被当成垃圾回收，而 B 还握着它的指针，程序随后就会访问到已释放内存。

漏标需要同时满足两个条件：一个白色对象的所有可达路径都被破坏，同时有一条新的边从黑色对象指向它。只要破坏其中任意一个条件，就能保证正确性：要么在新增边时把白色对象保护起来，要么在删除边时把旧目标保护起来。前者对应插入屏障，后者对应删除屏障。

flowchart LR
    G[灰色对象 G] -->|删除指向 W 的引用| W[白色对象 W]
    B[黑色对象 B] -->|扫描后新增引用| W
    R[根] --> B
    R --> G

图里黑色对象在扫描后新增的边，正是强三色不变式禁止的情况；灰色对象到 W 的路径一旦被删除，W 就失去了保护。

强三色不变式与插入屏障

强三色不变式要求：黑色对象不能指向白色对象。Dijkstra 插入屏障的做法是，在指针写入之前，把新写入的对象染灰。这样黑色对象一旦指向某个白色对象，后者立刻变灰，不会再被当作垃圾；不变式始终成立。

插入屏障的代价在栈上。栈上的指针写入极其频繁，如果每次写栈都执行屏障，性能无法接受，所以运行时只在堆写入时开启屏障，栈不开启。这样栈上可能出现“扫描之后又新增了指向白色对象的指针”，只能在标记终止时暂停世界，重扫所有栈。Go 1.7 及更早的版本正是这么做的，第二次 STW 的耗时因此与 goroutine 数量强相关。

弱三色不变式与删除屏障

弱三色不变式放宽了条件：黑色对象可以指向白色对象，但这个白色对象必须还能通过一条从灰色对象出发的路径到达，也就是仍然被“灰色保护”着。Yuasa 删除屏障在指针被覆盖之前，把旧值染灰。删除一条边时，旧目标多了一次被标记的机会，即使它从原来的路径上掉下来，也不会立刻失去保护。

删除屏障是保守的：它可能把一些实际上已经不可达的对象重新标活，产生浮动垃圾，本轮不回收，留到下一轮。它的好处是栈只需要扫描一次，不必在标记终止时重扫。

混合写屏障

Go 1.8 起采用混合写屏障，把两者合在一起：写入时既把旧值染灰，也把新值染灰。删除的部分维持弱三色不变式，插入的部分让新指针立即受到保护；两者结合后，栈只需要扫描一次即可，标记终止不需要再重扫所有栈，第二次 STW 的耗时不再随 goroutine 数量线性增长。

混合屏障还有一个配套规则：标记期间新分配的对象直接标黑。这样即使新对象的指针只存在于栈上，也不会因为栈已经扫描过而漏标。代价是每次堆上的指针写都要多几条指令和一次位图访问，标记阶段所有写指针的代码都会略微变慢；同时删除屏障带来的浮动垃圾依然存在。

写屏障只在标记阶段开启。GC 空闲时，写指针与普通赋值没有区别，长时间运行的服务不会因此永久损失写性能。

四、一个 GC 周期做了什么

Go 的 GC 不是一次完成的动作，而是一个有状态机的周期：标记准备、并发标记、标记终止、并发清扫。两次 STW 分别夹在标记的两端，中间大段工作与用户代码并发。

flowchart TD
    A[标记准备 STW] --> B[并发标记]
    B --> C[标记终止 STW]
    C --> D[并发清扫]
    D --> E[等待堆增长到目标]
    E --> A

标记准备：第一次 STW

标记准备要停下来做几件事：暂停所有 P，开启写屏障，把根标记任务准备好，启动后台标记线程，然后恢复用户代码。这里的“暂停所有 P”就是第一次 STW。它本身很短，主要成本是让所有 P 停下来、完成清扫终止与状态切换；真正的根扫描，包括全局变量与各个 goroutine 的栈，主要由后台标记线程在并发阶段完成，其中扫描某个栈时需要短暂停住对应的 goroutine。因此 goroutine 很多会拉长整个标记阶段，却不一定直接体现在第一次停顿的时长上。

并发标记

恢复用户代码后，后台标记线程与用户 goroutine 一起运行。默认情况下，后台标记最多使用四分之一的 P，剩下的 P 继续跑用户代码；如果分配速度超过标记速度，运行时会拉用户 goroutine 来做辅助标记。写屏障在整个阶段开启，所有堆上的指针写入都要经过它。这个阶段最长，也最容易被误解：它不暂停程序，但会抢走一部分 CPU，并通过辅助标记直接拖慢分配密集的请求。

标记终止：第二次 STW

当灰色队列基本清空，周期进入标记终止。这一次 STW 要处理收尾工作：暂停用户代码，完成剩余的标记任务，等待后台标记线程退出，关闭写屏障，统计本轮结束时的存活堆大小，计算下一轮的堆目标，最后唤醒清扫。存活堆的统计决定了 GOGC 的基数，因此这一步不只是“停一下”，它直接决定下一轮 GC 何时到来。

并发清扫

清扫同样与用户代码并发。运行时以 span 为单位，把没有存活对象的 span 标记为空闲，归还给 mcache、mcentral 或 mheap；清扫是惰性的，分配时发现 span 未清扫会先清扫再用。清扫不移动对象，所以指针地址稳定，栈上的指针不需要修正；代价是堆会碎片化，长期运行后可能出现“总空闲够用但没有连续大块”的情况。大对象按页分配，对碎片更敏感，这也是大切片频繁创建删除时内存看起来降不下去的原因之一。

两次停顿的分工

第一次停顿负责“开始”：开屏障、准备根任务、启动标记；第二次停顿负责“收口”：补完标记、关屏障、算目标。前者与 P 的数量和状态切换关系大，后者与剩余标记工作、后台线程的收尾关系大。

五、辅助标记与 pacer

分配者买单：mutator assist

后台标记可能追不上分配速度。若放任不管，堆会在标记完成前撞破目标。Go 的解法是让分配者承担一部分标记工作，也就是辅助标记（mutator assist）。运行时给每个 goroutine 维护一个 gcAssistBytes 计数，可以把它理解为分配额度：每次分配按比例扣减，额度为负就停下来扫描对象，用扫描工作量把额度补回来。分配越多，欠债越多，被拉去扫描的时间越长，堆增长与标记进度因此被绑在一起。

代价是延迟的分摊。一个分配密集的服务在 GC 期间会出现请求整体变慢、P99 抖动，而 STW 指标可能完全正常。只盯 PauseNs 找不到原因时，要想到辅助标记。

pacer：把标记安排在预算内

pacer 决定下一轮何时开始、标记跑多快，目标是在堆达到目标前完成标记，同时不过早占用 CPU。目标堆的基线是上一轮标记结束时的存活堆按 GOGC 放大：GOGC 为 100 时是两倍，50 时是一点五倍，200 时是三倍。pacer 还会根据上一轮提前或延后完成来微调触发比例，并按最近的分配速率估算启动时机，所以 gctrace 里的 goal 每轮都在变。

要注意 GOGC 的基数只含堆上的存活对象，不含 goroutine 栈、runtime 元数据和 mcache 缓存的 span。goroutine 很多的服务，RSS 可能明显高于 HeapAlloc 的两倍，却仍符合 GOGC 的设定；拿 HeapAlloc 估算容器内存上限，经常会低估。

GOGC 的取舍

GOGC 调大，GC 次数变少，CPU 占比下降，但单轮要标记的堆更大、内存峰值更高；调小则相反。没有通用最优值，只有与内存预算、延迟目标匹配的取值。GOGC=off 会关闭自动 GC，适合生命周期短、内存充足的批处理；对常驻服务，等于把内存交给分配速率，最终大概率被 OOM kill。Go 1.13 的运行时不会因为接近容器上限而主动降级，内存策略只能靠 GOGC 与代码本身控制。

MemStats：把指标拿进程序

需要在监控里看趋势时，用 runtime.ReadMemStats：

HeapAlloc 是当前存活对象占用的字节数，最接近业务真正持有的内存；HeapInuse 是已分配给 span 的页，包含尚未使用的槽位；HeapSys 是向操作系统申请的总量；HeapIdle 是可以归还但还没归还的空闲页；NextGC 是下一轮目标；NumGC 是完成轮数；PauseNs 是长度 256 的环形缓冲，取模才能拿到最新一条；GCCPUFraction 给出 GC 占用的 CPU 比例。

这些指标要成组看。HeapAlloc 与 HeapSys 都高，是真实的堆占用；HeapAlloc 低而 HeapSys 高，多半是归还滞后或碎片；HeapAlloc 锯齿的谷底持续抬高，才更像存活对象在增长。还要记住 ReadMemStats 会暂停世界，遍历 span 统计内存，堆越大耗时越长；把它放进高频请求路径，本身就会制造延迟，甚至让采集变成新的抖动源。

七、调优：先定位，再动参数

先分清三种症状

GC 相关的抱怨通常分三类。CPU 高，看 GCCPUFraction 与 gctrace 频率，判断是 GC 抢了 CPU 还是业务吃满；延迟抖动，看 PauseNs 分布，同时看辅助标记时间，区分停顿与分摊；内存高，看 HeapAlloc、HeapInuse、HeapSys 的关系，判断是存活对象多、碎片多，还是归还慢。症状不同，手段完全不同。

GOGC 与 SetGCPercent

调整 GOGC 是最容易想到的手段：提高它，用内存换 CPU；降低它，用 CPU 换内存。debug.SetGCPercent 可以在运行时修改并返回旧值，适合按阶段调整：批处理开始前放宽，结束后恢复；内存紧张的容器里收紧，给栈和 runtime 留出余量。

容器场景要额外小心。Go 1.13 的运行时并不感知 cgroup 的内存上限，GOGC 只按堆的存活量计算目标。一个限制 512 MB 的容器，如果堆目标算到 400 MB，加上栈与 runtime 元数据，峰值很容易被 OOM kill。做法是压低 GOGC，并用压测确认峰值 RSS 留有余量。

FreeOSMemory 的边界

debug.FreeOSMemory 会强制触发一次 GC，并把空闲内存归还操作系统。它不释放存活对象，也不能解决泄漏；它带来一次完整周期的 CPU 开销与停顿。合理的用法是在明确的阶段边界调用一次，比如批量导入结束之后；放进定时任务每分钟跑一次，只会让 GC 更忙。Linux 上 Go 1.12 起默认用 MADV_FREE 归还页，内核可能延迟回收，RSS 不会立刻下降；要确认归还，可临时设置 GODEBUG=madvdontneed=1 观察。

减少分配才是主线

多数时候，减少分配比调参数有效。预分配切片与 map 的容量，避免反复扩容；用 sync.Pool 复用临时缓冲，注意池里的对象在 GC 后可能被清理，它适合短生命周期对象，不适合当缓存；合并小对象，降低指针密度；避免热路径上不必要的 []byte 与 string 转换、接口装箱和闭包捕获，逃逸分析的细节另文展开。这些改动直接减少标记与清扫的工作量。调 GOGC 只是挪动工作量的位置，减少分配才是把总量降下来。

八、GC 与延迟：停顿之外还有分摊

讨论 GC 延迟，很多人只盯着两次 STW。实际上延迟有两个来源。第一是停顿：标记准备要暂停所有 P，标记终止要暂停去收尾，这两段时间里所有 goroutine 都不推进。第二是分摊：辅助标记把标记工作塞进用户 goroutine，请求没有停，但变慢了，表现为 P99 上升而 STW 指标正常。

停顿的长短取决于 P 的数量、状态切换与收尾工作量。堆越大、存活对象越多，并发标记跑得越久，辅助标记介入的机会也越多；存活率高则每轮标记都要把大部分对象走一遍，回收出来的却很少，堆很快又回到目标，GC 频率随之上升。

所以“减少分配”通常比“调 GOGC”更有效：它同时降低标记工作量、辅助标记概率和清扫压力，而调大 GOGC 只是把触发点往后推，单轮成本还在。只有在分配已经很难再降、内存又相对宽裕时，放宽 GOGC 才是合理选择。

Go 的停顿目标是亚毫秒级，这个目标靠并发标记与混合写屏障支撑，但它不是硬保证。宿主机 CPU 被其他进程抢走、容器配额被限流、单次分配触发大量清扫，都会让实际停顿偏离预期。评估延迟要把 GC 指标与应用的分位延迟放在同一时间轴上对照，而不是孤立地看某一次停顿。

九、几个常见误解

GC 会立刻把内存还给操作系统

不会。对象被回收后，span 先变成空闲，回到 mcache、mcentral 或 mheap 的空闲列表，HeapAlloc 下降，HeapSys 不变。运行时的 scavenger 会在后台逐步归还长时间不用的页，Linux 上还可能因为 MADV_FREE 而延迟体现为 RSS 下降。看到 HeapAlloc 降了、RSS 没降，先查 HeapIdle 与归还策略，不要急着认定内存泄漏。

定期调用 runtime.GC() 是好习惯

runtime.GC 会强制启动一轮完整的 GC，包含两次 STW 与全堆标记。定期调用它，相当于人为制造周期性的 CPU 开销与停顿；如果目的是防止泄漏，它还会掩盖真正的增长趋势，让问题更晚暴露。它适合测试、基准与明确的阶段边界，不适合当成定时任务。

GOGC=off 一定更快

关闭 GC 确实省掉了标记与清扫的 CPU，短期吞吐可能上升。但堆从此只增不减，分配速率决定内存曲线，长期运行的服务迟早撞上容器上限。它适合短生命周期、内存充足的批处理，而不是常驻服务。即便在批处理里，也要估算峰值内存。

HeapAlloc 下降就代表没有泄漏

HeapAlloc 是锯齿形的：刚跑完 GC 的谷底低，接近下一轮目标时高。判断泄漏要看多个周期之后的谷底是否持续抬高，而不是看某一时刻的下降。更可靠的做法是对比两个时间点的 heap profile，看 inuse_space 的顶部对象是否单调增长；只看 HeapAlloc 曲线，既容易把缓存增长当成正常波动，也容易把正常波动当成泄漏。

十、一次内存持续上涨的排查

有一个订单服务，上线一周后 RSS 从几百 MB 涨到上 GB，重启后恢复，一周后又涨回去。GC 次数没有明显异常，接口延迟也稳定，但容器的内存告警越来越频繁。这类现象要先回答一个问题：是存活对象在增长，还是堆没有归还。

第一步看 gctrace。如果每轮存活堆都在抬高、goal 跟着抬高，说明确实有对象被长期持有；如果存活堆稳定，HeapSys 高而 HeapAlloc 低，问题在归还与碎片，不在泄漏。

第二步把 MemStats 打点。按分钟记录 HeapAlloc、HeapObjects、HeapSys，画成趋势。HeapAlloc 的谷底持续抬高，HeapObjects 也在涨，说明是对象数量在增加，而不是少数大对象。

第三步采 heap profile，在两个时间点各采一次，比较 inuse_space 的顶部。第一次顶部是请求上下文与序列化缓冲，第二次多了一个业务 map，且它的 inuse_space 与时间正相关；alloc_space 则显示写入集中在少数几个接口。第四步确认语义：这个 map 是本地缓存，key 是商品 ID，只增不删，没有容量上限也没有过期时间。商品总量在涨，缓存就跟着涨。结论不是 GC 失效，而是缓存没有边界；加上容量上限与 TTL 后，RSS 稳定在可接受的范围。

如果 heap profile 的顶部是 goroutine 相关结构，还要看 goroutine 数量是否持续增长；如果是大量小对象，考虑对象池与批处理。pprof 的采集细节留待另文，这里只强调判断顺序：先分清存活增长与归还滞后，再看对象类型，最后才谈参数。

小结

Go 的 GC 是一套组合：三色标记保证正确性，混合写屏障让标记与用户代码并发，辅助标记把成本分摊给分配者，pacer 决定何时开始与跑多快，两次短暂的 STW 负责开始与收口。它的停顿目标是亚毫秒级，但延迟不只来自停顿，也来自辅助标记带来的分摊。

理解这些机制的目的，不是背参数，而是写出分配友好的代码：控制对象数量与存活率，复用临时缓冲，避免无谓的指针与拷贝，让存活堆保持稳定，GC 周期自然拉长。观察用 gctrace 与 MemStats，判断用趋势与 profile，调 GOGC 是最后一步，而不是第一步。
