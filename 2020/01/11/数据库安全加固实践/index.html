数据库安全加固实践

数据库往往是系统里价值最高的资产，也最容易被“顺手”暴露：为远程连接把监听改成 0.0.0.0，为省事给应用授 ALL，多个应用共用一个账号。这些问题单看都不算漏洞，叠在一起却足以让一次弱口令猜解演变成数据泄露。本文以 MySQL 5.7 为主、兼顾 8.0，并覆盖 Redis 5.0 与 MongoDB 3.6/4.0，按“先收敛暴露面、再收紧身份、最后补齐审计与恢复”的顺序，说明每项配置防什么、怎么做、怎么验。

数据库安全的层次

数据库加固是一条按暴露面排序的处置链：网络暴露、认证授权、传输加密、审计、备份、补丁。一台监听公网、允许 root 远程登录的实例，先收回端口，收益远大于调 sql_mode；只改参数不动网络和账号，加固只是表面功夫。

换到攻击者视角：先扫端口，再试登录，登录后看能读哪些库。防守动作一一对应：收敛监听、收紧账号、最小权限、留痕、可恢复。等保 2.0 已于 2019-12-01 实施；本文不逐条对照控制项，只讲工程上怎么改、怎么验。

flowchart LR
    A[网络暴露] --> B[认证与授权]
    B --> C[传输加密]
    C --> D[审计]
    D --> E[备份与恢复]
    E --> F[补丁与版本]

先收敛暴露面：网络与监听

事故起点常常不是漏洞，而是本该只在内网监听的端口被放到了公网。MySQL 的默认监听、MongoDB 的旧配置，以及不少 Redis 部署，都出现过 0.0.0.0。监听地址本身不等于可访问，但只要安全组或防火墙有一条宽松规则，数据库就会直接面对扫描器。

做法分三步：改监听地址，只绑定回环与内网网卡；在主机防火墙做白名单，只允许应用网段和运维网段；把管理入口收到堡垒机后面，禁止公网直连。

改完不要只看配置文件，要用 ss -lntp 确认实际监听地址，再从另一台机器用 nc -zv 10.0.2.15 3306 验证白名单是否生效。云上的安全组只能当作一类边界控制，不能替代主机防火墙。

运维通道同样要收。DBA 通过堡垒机登录跳板机，再从跳板机连数据库；临时排障用 SSH 端口转发，用完即关。只被本机进程访问的实例，直接 skip-networking，前提是确认没有远程备份和监控依赖 TCP。

盘点之后按四件事处理。第一，删除匿名用户，它可能匹配任意用户名，必须清干净；DROP USER 会同步刷新权限表，不需要再执行 FLUSH PRIVILEGES。第二，root 只保留本机来源；需要远程管理时另建具名账号并限定主机。第三，按应用建独立账号，Host 限定到具体地址，读写账号分开。第四，只授完成工作必需的权限。

应用账号不应拥有 ALL、WITH GRANT OPTION、FILE、PROCESS、SUPER。FILE 能读写服务器文件，配合 LOAD DATA 或 INTO OUTFILE 可绕过库表权限；PROCESS 能看到所有会话的明文参数。

权限要定期审计。除了 SHOW GRANTS，还可以查 mysql.db 与 mysql.tables_priv，把结果与 CMDB 的应用清单比对，发现离职项目遗留的账号与长期未使用的授权。

口令策略用 validate_password 兜底。MySQL 5.7 通过插件安装，8.0 改为组件，变量名也从下划线风格变成点号风格，迁移时不要照抄配置。

MEDIUM 要求口令同时包含数字、大小写字母和特殊字符，长度至少 12 位。策略只约束新口令的强度，管不住口令被写进代码，后者要靠配置中心和代码扫描解决。

MySQL 配置加固

MySQL 的一组关键参数大多需要重启才能生效。

local_infile 关闭后，批量导入改为把文件先传到服务器目录，再用服务端 LOAD DATA。secure_file_priv 为空表示不限制，为 NULL 表示禁止导入导出，生产应指向专用目录。skip_symbolic_links（配置项写作 symbolic-links = 0）避免攻击者用符号链接把读写引到系统文件。max_connections 过高会在连接风暴中耗尽内存，过低会让应用连接池拿不到连接；wait_timeout 要大于连接池的空闲回收时间。

sql_mode 建议开启严格模式。非严格模式下，超长字符串会被截断、非法日期会被写成零值，应用以为写入成功，数据却已经失真；严格模式让这类写入直接报错。老系统可能依赖宽松行为，切换前要在预发跑完整回归。MySQL 8.0 默认还包含 ONLY_FULL_GROUP_BY，升级时需逐条确认。

慢查询日志既是性能工具，也是行为基线。long_query_time 设为 1 秒；log_queries_not_using_indexes 只在排查期短期开启。错误日志要单独落盘并纳入采集，登录失败、表损坏、复制中断都会留下线索。

配置改完要两边对照：

静态参数改完要重启，并确认错误日志没有因为未知参数而启动失败；SET GLOBAL 只影响当前实例，不能当作持久化配置。配置文件也应设为 600 权限。

传输与存储：让链路和落盘都不裸奔

数据库端口收回内网，只解决了“谁能连”，没有解决“链路上会不会被看见”。MySQL 5.7 首次初始化时会生成自签名证书，但自签名证书无法证明服务器身份，正规做法是用内部 CA 签发，客户端配置 CA 并校验。

很多驱动默认的 PREFERRED 模式只协商加密，不校验对端证书。JDBC 连接串应显式写上 useSSL=true&requireSSL=true&verifyServerCertificate=true。服务端在确认所有客户端都支持 TLS 后，再开启 require_secure_transport=ON；要先验证复制、监控、备份账号，否则它们会集体断连。

当前会话若返回非空 cipher，说明链路已加密；返回空则仍是明文。Redis 5.0 没有原生 TLS，只能依赖内网隔离或用 stunnel 做本地加密转发；MongoDB 3.6/4.0 支持 TLS，配置 net.tls.mode: requireTLS 后客户端必须带 CA 连接。

磁盘加密的边界要说清楚。TDE 或 LUKS 能防的是“磁盘、备份磁带被整块拿走”，防不了在线注入、越权查询，也防不了拥有合法账号的人拖库。密钥要与数据分开存放。备份文件同样要加密，密钥不能和备份放在同一台主机上，加密之后一定要做一次真实恢复。

审计：留下能查的痕迹

审计要回答四个问题：谁、从哪来、什么时候、做了什么。MySQL 企业版提供审计插件，可按用户与操作类型过滤；社区版没有同等能力，通常用 general log 与慢查询日志拼出大致轮廓。

general log 记录所有到达服务器的语句，包括账号口令与业务 SQL 里的身份证号，开销大、敏感信息多，不能在生产长期开启。正确的用法是排障时开一个短窗口：先确认 log_output=FILE，开启 general_log，复现问题后立即关闭，把日志转走并按留存要求处理。慢查询日志的记录面窄一些，适合作为长期的行为基线，但同样包含参数值，不能随意开放读取权限。

登录失败不在 general log 里，要去错误日志找 Access denied 与 Aborted connection。日志应通过 rsyslog 或 Filebeat 外送到独立主机；《网络安全法》要求网络日志留存不少于六个月。审计日志本身就是高敏感数据，外送后要限制索引的访问权限。

Redis：别让缓存变成入口

Redis 事故常见同一个模板：监听 0.0.0.0、没有口令、CONFIG 可用，攻击者改持久化目录写入文件，再借 Web 目录或定时任务执行。加固从网络、认证与危险命令三条线入手。

网络层，bind 只写回环与内网地址，保持 protected-mode yes；后者只在没有 bind 且没有口令时生效，不能当唯一防线。防火墙只放行应用网段。

认证层，requirepass 使用长随机串，按实例、按环境区分；Redis 5.0 没有 ACL，ACL 是 6.0 才引入的能力，当时 6.0 还在候选阶段，因此只能靠“一实例一口令 + 网络隔离 + 命令重命名”控制权限。

rename-command 必须在配置文件里写，不能通过 CONFIG SET 生效，改完要重启。重命名 CONFIG 会影响依赖它的运维工具；KEYS 在大库上会阻塞，生产应改用 SCAN。

持久化目录属主为 redis 用户，权限设为 700，文件 600，绝不能放在 Web 根目录；maxmemory 与淘汰策略要设置，避免被 OOM 杀掉。Redis 5 没有原生 TLS，跨网访问用 stunnel 或专线。

MongoDB：认证、绑定与审计

MongoDB 3.6/4.0 的默认配置已经比早期版本收敛，但仍有几件事必须手动做。先建管理员再开认证：在 admin 库创建 userAdminAnyDatabase 与 clusterAdmin 账号，然后在配置文件写 security.authorization: enabled 并重启。开启后按库授权，应用只拿 readWrite 或 read，不拿 root；账号建在对应业务库中，不要都堆在 admin。

net.bindIp 只写 127.0.0.1 和内网地址。更早的版本可用 nohttpinterface 或 net.http.enabled 关闭 HTTP 接口，3.6 起该接口已移除，但仍要确认没有遗留的 28017 端口暴露。传输用 net.tls.mode: requireTLS，配置 certificateKeyFile 与 CAFile；需要双向认证时关闭 allowConnectionsWithoutCertificates。4.0 默认使用 SCRAM-SHA-256，3.6 是 SCRAM-SHA-1。

审计方面，auditLog 是企业版能力，可输出到文件或 syslog 并按操作过滤；社区版没有内置审计，只能用 profiler（db.setProfilingLevel）加慢日志、currentOp 和日志外送做替代，profiler 级别 2 开销大，排障后要关。不需要服务端 JavaScript 时可关闭 security.javascriptEnabled。

注入与查询安全

注入的根治在代码层：所有外部输入走参数化查询或预编译语句，不拼字符串；表名、列名、排序方向无法参数化，用白名单映射；ORM 的 raw SQL、字符串插值、order by 拼接要逐处审查。数据库侧的最小权限是兜底：应用账号只有单库 DML，没有 FILE 与跨库读，注入成功也拿不到更多数据。错误信息不要原样返回给前端，避免泄露库表结构。注入原理与检测另有文章，这里不展开。

备份与恢复：备份不等于可恢复

备份要同时满足可恢复与不可篡改，通常全量与增量结合。MySQL 小库用 mysqldump --single-transaction --master-data=2 --routines --triggers，大库用 XtraBackup 做物理备份；无论哪种，都要持续归档 binlog，才能做到时间点恢复。备份账号只授 SELECT、SHOW VIEW、TRIGGER、LOCK TABLES，按需加 RELOAD，不授写权限。

备份文件加密后传到异地或对象存储，保留多份与不同介质；存放目录 700，文件 600，不能放在 Web 根目录，也不能与数据库同盘。每季度至少做一次恢复演练：在隔离环境还原全量、重放 binlog、跑校验与应用冒烟，记录 RTO 与 RPO。没有演练过的备份，只能算“可能可恢复”。Redis 与 MongoDB 的备份同样纳入这套流程。

补丁与版本管理

补丁管理要有固定节奏：资产清单里记录版本，订阅官方安全公告，按影响面分级；紧急漏洞走应急窗口，常规更新按季度。补丁先在测试环境验证，再在从库或灰度实例观察，最后才动主库。大版本升级（如 5.7 到 8.0）要先读升级说明，重点关注默认认证插件、字符集、被移除的特性与保留字，用升级检查工具跑一遍兼容性，再安排回滚方案。本文不列具体 CVE 编号，版本问题以官方公告为准。

监控与告警

监控要覆盖五类信号：失败登录（错误日志中的 Access denied、Aborted connection）、异常连接（新来源 IP、连接数突增）、慢查询与锁等待、磁盘与 binlog 增长、复制延迟（SHOW SLAVE STATUS 的 Seconds_Behind_Master）。阈值要结合基线设定，告警必须配处置手册，否则值班人员会习惯性忽略。

日志外送前要脱敏：慢日志与 general log 常带手机号、身份证号、口令，SIEM 中应做字段掩码，并限制查询权限。

基线检查清单

把上面的动作压成可勾选清单，交付前逐项确认：

类别 检查项
网络 监听地址非 0.0.0.0；防火墙仅放行应用与运维网段；无公网直连
账号 匿名用户已删；root 仅本机；应用独立账号；无 ALL 与 GRANT OPTION
配置 local_infile 关闭；secure_file_priv 指定目录；sql_mode 严格；日志已开
审计 失败登录可查；日志外送；留存不少于六个月；敏感字段脱敏
备份 全量加增量与 binlog；异地加密；权限 600；季度恢复演练

清单不是一次性验收材料。新实例上线、应用改版、账号新增，都可能让某项回退；把清单写成核查脚本，每周跑一次并与基线比对。

常见坑

应用账号给 ALL：一次注入就能 DROP 表或读其他库。多个应用共用账号：出问题无法定位来源，也无法按应用收回权限。备份文件放 Web 目录：等于把整库打包供人下载。Redis 无口令：6379 暴露在公网，几小时内就会被写入异常文件。只加固主库忘了从库：从库同样保存全量数据，却常被忽略。改配置没重启验证：以为生效，实际仍是旧值；或者只改了运行时变量，重启后失效。把安全组当防火墙：规则由多人维护，默认放行 0.0.0.0/0 的临时规则最容易遗留。

小结

数据库加固没有一步到位，只有持续收敛。先收网络与账号，再补 TLS、审计和备份，最后用监控与基线检查防止回退；每一条变更都要能验证、能回滚、能追责，才算真正落地。
