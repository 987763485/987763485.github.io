MongoDB 聚合管道实战

find() 能取回文档，却很难在服务端完成分组、关联与统计。本文从执行模型讲起，把聚合管道拆成可以单独验证的小步骤，再用一个订单与订单明细的案例串起常用阶段、索引配合与排错方法。读者需要写过基本的 find 查询，读完后应当能为一个统计需求独立写出可解释、可优化的管道。

一、聚合管道适合放在哪一层

先看一个常见需求：从订单集合里筛出已支付的订单，按用户汇总消费金额，再取金额最高的十个人。用 find() 也能做，但只能把符合条件的文档整批取回应用，再在进程里用哈希表累加、排序、截断。数据量小的时候这种做法没有问题，数据量一大，三个代价就同时出现：网络上传输的是明细而不是结果，应用内存要装下全部中间数据，分页与并发也很难做得干净。

聚合管道把这段逻辑放回服务端。文档在 mongod 进程内依次经过若干阶段，只有最终结果通过网络返回。它适合三类场景：需要分组统计，例如求和、计数、去重、取首尾；需要把两个集合按字段拼在一起，例如订单与明细、文章与作者；需要在一轮扫描里产出多个口径的报表。

反过来说，如果只是按条件取几十条文档、做一点字段裁剪，find() 配合投影更直接，也更容易命中索引；把简单查询改写成管道，除了增加阅读成本，不会有额外收益。判断标准可以概括成一句话：中间结果明显大于最终结果时，才值得把计算搬到服务端。

二、管道的心智模型：文档流与阻塞阶段

理解管道的关键，是把每个阶段看成“输入一串文档、输出另一串文档”的转换器，而不是一条 SQL 子句。$match 过滤，$project 重塑字段，$group 把多串并成一串，$unwind 把一条拆成多条。所有阶段首尾相接，前一阶段的输出就是后一阶段的输入。

flowchart LR
  A[orders 集合] --> B[$match 过滤]
  B --> C[$lookup 关联明细]
  C --> D[$unwind 展开]
  D --> E[$group 汇总]
  E --> F[$sort 排序]
  F --> G[$limit 截断]

阶段分为两类。流式阶段处理一条就向下游交付一条，$match、$project、$addFields、$unwind、$limit 都属于这一类；阻塞阶段必须读完全部输入才能产出第一条输出，$group、$sort、$bucket、$facet 是典型代表。区分两者的意义在于定位瓶颈：阻塞阶段前面挂着的 $limit 并不能减少它要读的数据，只有把过滤条件放到更前面，才能真正缩小输入。

另一个推论是顺序即语义。$sort 后接 $limit 是“取前 N 条”，$limit 后接 $sort 是“先随便取 N 条再排序”，结果完全不同。写管道时应当把每个阶段读成一句自然语言，确认它表达的正是业务意图。

三、核心阶段与表达式

最常用的阶段可以按职责归成四组。过滤与裁剪是 $match、$project、$addFields；聚合与计数是 $group、$bucket、$facet；排序与分页是 $sort、$limit、$skip；结构变换是 $unwind 与 $lookup。$group 的 _id 决定分组键，累加器决定每组保留什么，$sum、$avg、$min、$max 做数值汇总，$push 保留全部值，$addToSet 去重，$first 与 $last 依赖输入顺序。

表达式让字段可以在阶段内被计算出来。$cond 做二选一，$map 逐元素变换数组，$filter 保留满足条件的元素，$reduce 把数组折叠成一个值，日期与字符串算子负责格式化与拆分。它们都写在 $project、$addFields 或 $group 的表达式位置，不能单独成为一个阶段。

$expr 是另一类入口：它允许在 $match 里比较同一文档的两个字段，例如筛出成交价低于标价的订单。这类条件用普通查询语法写不出来，只能借助 $expr，代价是它通常无法使用普通索引，需要配合其他高选择性条件一起缩小范围。

$facet 与 $bucket 解决“一次扫描、多份结果”。$facet 把同一批输入分发给几条子管道，各自输出独立结果；$bucket 按边界把数值分到区间里。两者都只能出现在管道的特定位置，子管道里不能再用 $out 之类的写出阶段。

$lookup 有两种形态。简写形式只给出 from、localField、foreignField 与 as，语义是“把右侧所有匹配文档放进数组”；从 3.6 起还可以写成 let 加 pipeline 的形式，在关联的同时带上过滤与投影，只取需要的字段。后者更灵活，但子管道里引用左表字段必须通过 let 声明的变量，不能直接写字段名，这是初学者最常遇到的语法错误。

$addFields 适合在管道中间暂存计算结果。它保留原有字段、只覆盖同名项，比 $project 更适合“加一点东西”的场景；但如果把大数组反复塞进文档，后续每个阶段都要搬运这些数据，能裁掉就尽早裁掉。

四、让索引配合管道

聚合管道不会自动变快，它只是把计算搬到了数据旁边。真正决定耗时的仍然是扫描了多少文档、读取了多少索引项。

第一条规则是把过滤与排序尽量前置。$match 写在最前面，$sort 紧随其后，MongoDB 才有机会用同一个复合索引同时满足两者。索引字段顺序大体遵循等值、排序、范围的次序：查询条件是 status 等值、结果按 createdAt 倒序，那么 { status: 1, createdAt: -1 } 是合适的；反过来写成 { createdAt: -1, status: 1 }，排序仍可借助索引顺序，但过滤要在遍历中逐条判断，读的索引项会多出不少。

优化器会做一定程度的阶段重排，例如把 $match 前移、把 $sort 与 $limit 合并，但这种能力有边界：跨 $group、跨 $unwind 的重排通常不会发生。把管道按最优顺序写好，比指望优化器更可靠。

第二条规则是给 $lookup 的外键建索引。$lookup 对左侧每一条输入，都要到右侧按 foreignField 查找匹配文档；这个字段没有索引时，这一步退化为一次集合扫描。假定左侧有一万条订单，右侧有十万条明细，每条订单都全表扫一遍，量级就是十亿次文档比较。这种管道在开发库上跑得通，上线后往往直接拖垮实例。

第三条是学会看 explain。聚合的计划结构与查询类似，executionStats 会给出各阶段的扫描量与返回量。

输出里重点看三处：winningPlan 中是否出现 IXSCAN 而不是 COLLSCAN，totalDocsExamined 与 nReturned 的比值是否接近，$sort 阶段有没有内存溢出的提示。如果扫描量是返回量的几十倍，说明索引没吃上，或者 $match 的选择性太低。带 $out、$merge 的管道不适合用 explain 观察写出效果，它只给计划，不会替你验证目标集合的最终状态。

还有一处容易混淆的限制：find() 的排序在没有索引时受 32 MB 内存约束，而聚合管道中单个阶段的上限是 100 MB。前者报错时提示你建索引，后者报错时提示你加 allowDiskUse，两者不是一回事。

最后一点常被忽略：管道里每个阶段都会产生新的文档副本，$lookup 出来的数组如果一直带到后面，$sort 与 $group 就要为这些副本付出内存。关联完成、字段取到之后，应当用 $project 收窄文档，让后面的阶段只处理必要的字段。

五、实战：按分类统计热销商品

假设有三份数据：orders 保存订单头，字段是 _id、status、createdAt；order_items 保存订单行，字段是 orderId、productId、qty、price；products 保存商品与分类。需求是统计最近一个月每个分类销量前三的商品。

这类需求不能先取订单再逐条查明细，那是典型的 N+1。管道的思路是：先过滤订单，把明细关联进来并展开，再关联商品拿到分类，按分类与商品汇总，排序后按分类分组取前三。

这里有一个值得记住的技巧：第一个 $group 之后先按分类升序、销量降序 $sort，第二个 $group 用 $push 把文档按到达顺序收进数组，$slice 取前三个，就得到了每个分类的榜单。$push 保留输入顺序，这个性质是整段逻辑成立的前提；如果中间再插入会改变顺序的阶段，结果就不再可靠。

这段管道有两个代价需要提前评估。其一，order_items.orderId 与 products._id 都必须有索引，否则两次 $lookup 会分别退化为逐条扫描。其二，$push 会把每个分类下的全部商品装进一个数组，分类商品数很多时可能逼近 16 MB 的文档上限，也会撑大 $group 的内存占用。商品基数大的场景，更稳妥的做法是先按分类与商品聚合，把中间结果落到一张汇总集合，再对汇总集合做第二次分组。

六、调试、写出与常见坑

分段执行与内存上限

管道写错时，报错信息往往只指向最后一行，真正的问题在前面几个阶段。有效的办法是分段执行：先只保留 $match 和 $limit 5，确认过滤条件符合预期；再逐步往上加阶段，每加一个就看几条样本。把 $limit 放在可疑阶段之前，可以避免调试过程本身触发一次大排序。

内存方面，聚合管道每个阶段默认可用 100 MB，$group、$sort、$bucket、$facet 这类阻塞阶段一旦超出就会报错。加上 allowDiskUse: true 之后，超出部分会写到临时文件，代价是额外的磁盘读写与更长的耗时。它不是性能优化开关，只是让本来会失败的管道能够跑完；真正该做的仍是先用 $match 缩小输入、用 $project 尽早裁掉大字段。

写出阶段的副作用

需要把结果留存时，用 $out 或 $merge 作为最后一个阶段。$out 会整体替换目标集合，集合上原有的索引不会被复制过去，需要重新创建；$merge 按 _id 合并，可以保留目标集合的结构与索引，更适合增量场景。两者都有副作用，重复执行会改写数据，放在可能被重试的定时任务里时必须自己保证幂等。权限上，aggregate 要求源集合的 find 权限，$lookup 要求外部集合的 find 权限，$out 与 $merge 还分别要求目标集合的写入权限，只读账号执行带写出的管道会直接报未授权。

顺带一提，视图本质上保存的就是一条管道，查询视图时会展开执行。把常用统计封装成视图可以减少重复代码，但视图不存储结果，每次查询仍然实时计算，也不能包含 $out 这类写出阶段。

五个高频问题

第一，$unwind 默认丢弃空数组与缺失字段。订单没有明细时，整条订单会在展开时消失，后续统计自然偏小，而且不会报错。需要保留时加上 preserveNullAndEmptyArrays: true，并在下游用 $ifNull 处理缺失值。

第二，$lookup 没有匹配时，as 字段是空数组而不是 null，紧接着的 $unwind 又会把这条文档丢掉。关联不上通常意味着脏数据，统计前应当先单独数一数这类文档有多少，而不是让它默默消失。

第三，分组键的类型不一致会把同一实体拆成两组。字符串 "1001" 与数字 1001 是两个不同的 _id，从不同数据源导入的数据尤其常见。可以先用 $convert 或 $toString 统一类型再分组，也可以在建模阶段就固定字段类型。

第四，在 $group 之前 $sort 基本没有意义：分组不保证输出顺序，排序消耗的内存也白花了。想要有序结果，$sort 必须放在 $group 之后；$first、$last 这类累加器依赖顺序时是例外，但那时排序是为了给累加器定序，而不是给最终输出定序。

第五，$skip 很大时，被跳过的文档仍然要被处理，深分页在聚合里同样昂贵。用上一页最后一条记录的排序键做范围条件，比不断增大 $skip 更稳，也更容易命中索引。

小结

聚合管道是一套以文档流为中心的变换工具：流式阶段逐条转发，阻塞阶段读完再算，阶段的顺序本身就是语义。写管道时先想清楚输入如何被缩小、输出需要什么形状，再挑选阶段；把 $match 与 $sort 放在前面，给 $lookup 的外键建索引，用 explain 验证扫描量。遇到内存告警先优化输入，再考虑 allowDiskUse；需要落结果时优先 $merge，并接受它的副作用。掌握这些，绝大多数统计需求都不必再搬回应用层用循环实现。判断一条管道写得好不好，先看它在前几个阶段把输入缩小了多少；索引没有命中时，再漂亮的阶段组合也只是把扫描换了个位置。
