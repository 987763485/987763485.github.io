慢 SQL 定位与优化流程

慢 SQL 是后端团队绕不开的问题，但“慢”常常被当成感觉，而不是可以度量、复现和改进的指标。本文从判定阈值讲起，依次梳理采集、聚合、单条分析、锁等待、改写与验证，最后给出一套可以落地的防回归机制。文中以 MySQL 5.7 为主，涉及 8.0 的差异会单独说明；索引原理只点到为止，留待另一篇展开。

一、先把“慢”定义清楚

讨论优化之前，必须先回答：多慢算慢。MySQL 用 long_query_time 定义慢查询，5.7 的默认值是 10 秒，并支持微秒级设置。这个默认值只是“不要漏掉明显异常”的兜底，不能直接当作业务标准。面向用户的接口，一次查询超过 100 毫秒就值得关注；后台报表几秒钟可能仍可接受。更合理的做法是按场景分别设阈值，例如在线查询 200 毫秒、批量任务 5 秒，并写进监控规则。

还要区分数据库视角与业务视角。慢日志记录的是服务器端执行时间，不含网络传输、连接池排队和应用层序列化；一条在库里只跑 20 毫秒的 SQL，如果被调用 500 次，同样会把接口拖慢。因此定位时要同时看单次耗时、调用次数和总耗时，先有阈值与基线，再谈优化，否则永远不知道何时可以收手。

二、开启与采集：先可控，再收集

慢查询日志由 slow_query_log 控制，路径由 slow_query_log_file 指定。log_output 可选 FILE、TABLE 或两者，写入表便于直接用 SQL 查询，但表使用 CSV 引擎，频繁写入有额外开销，生产环境通常还是落文件。long_query_time 可以在会话级临时调小，用来抓取某条可疑 SQL，而不影响全局。

log_queries_not_using_indexes 常被误用。它会把所有未走索引的语句记下来，包括小表扫描和本来就走全表的统计查询，日志很快膨胀。5.7 提供 log_throttle_queries_not_using_indexes 限制同类语句每分钟的写入次数，但它只是减噪，不是分类。生产上更稳妥的做法是默认关闭，专项排查时短时间开启，查完立即恢复。

日志轮转也要提前设计。直接删除文件不会释放句柄，应配合 FLUSH LOGS 或 mysqladmin flush-logs 让 MySQL 重新打开文件，再由 logrotate 压缩归档。采集的目标是“有足够样本且不影响主库”，可以在从库开启慢日志并打开 log_slow_slave_statements 做采样，但要确认从库负载与复制延迟仍有余量。

三、聚合分析：从日志到问题清单

单条日志价值有限，先要聚合成按“指纹”归并的清单。mysqldumpslow 是官方自带工具，-s t 按总耗时排序，-s c 按次数，-s at 按平均耗时，配合 -t 20 只看前 20 条。它会把字面量归一化成 N，适合快速浏览。

更细的分析通常用 Percona Toolkit 的 pt-query-digest。它能给出每条指纹的调用次数、总响应时间、平均耗时、95 分位和执行计划样本，还支持按时间窗口过滤。排序时建议先看总耗时，因为总耗时等于次数乘以平均，最能反映整体影响；再看单次最大耗时，避免漏掉偶发的长事务。

要注意样本偏差：阈值以下“次数多、单次略慢”的查询不会进慢日志，却可能才是接口延迟的主因；低峰期采集到的计划也不代表高峰期的数据分布。聚合结果应与业务监控、performance_schema 的语句统计互相印证，而不是当作唯一真相。

四、单条 SQL：读懂执行计划

EXPLAIN 输出中，type 表示访问方式，常见顺序是 const、eq_ref、ref、range、index、ALL，越靠后通常扫描越多；key 是实际选择的索引，key_len 反映联合索引用到了哪几列；rows 是优化器估算的扫描行数，filtered 是过滤后剩余比例的估算；Extra 给出 Using index、Using where、Using temporary、Using filesort 等关键信息。

不要只看 type。type 为 ref 但 rows 是几十万，仍然可能很慢；小表上的 ALL 反而无所谓。真正要合起来看的是“预计扫描多少行、是否回表、是否排序、是否建临时表”。需要更细的代价信息时，用 EXPLAIN FORMAT=JSON，其中的 cost_info、used_columns、attached_condition 能帮助判断条件下推与列裁剪是否发生。5.7 已支持该格式，8.0 还增加了 EXPLAIN ANALYZE，可以拿到实际执行时间，但那是 8.0.18 之后才有的能力。

五、常见问题：把现象映射到原因

全表扫描通常表现为 type=ALL 且 rows 接近表行数，原因可能是缺少可用索引、条件选择性太低，或者查询本身就要读全表。回表次数多表现为 Using where 加大量随机读，常见于二级索引过滤后仍要回聚簇索引取剩余字段。临时表与排序看 Extra 里的 Using temporary、Using filesort，多出现在 GROUP BY、DISTINCT 和无法利用索引顺序的 ORDER BY 上。

join 顺序由优化器决定，驱动表选择不当会让中间结果膨胀，可以用 STRAIGHT_JOIN 做对照实验，但不要把它当成长期方案。子查询在 5.7 中可能被改写为半连接或物化，执行计划与直觉不同，需要单独 EXPLAIN。隐式类型转换最隐蔽：字符串列与数字比较时，MySQL 会把列转成数字，索引随之失效。函数作用在索引列上同样如此，WHERE DATE(created_at) = '2020-04-01' 无法使用 created_at 上的索引，应改成范围条件。

六、锁等待：SQL 慢，还是被堵住

有些“慢”与执行计划无关，而是锁等待。先用 SHOW ENGINE INNODB STATUS 看 TRANSACTIONS 段，关注 TRX STATE、TRX STARTED 和 LOCK WAIT；存在阻塞时，段里会列出等待的锁与持锁事务。5.7 可以查询 information_schema.innodb_trx、innodb_locks、innodb_lock_waits，更省事的是 sys.innodb_lock_waits 视图，它已经把等待方与阻塞方拼在一起；8.0 则改用 performance_schema 的 data_locks 与 data_lock_waits，字段更完整。

长事务是锁等待的常见源头：事务里做远程调用、批量更新，或者开启事务却忘记提交，都会让行锁长期不释放。需要澄清一个说法：InnoDB 一般不会把行锁“升级”为表锁，锁数量增加带来的是内存与检测开销；真正会让范围突然扩大的是间隙锁、next-key lock，以及 DDL 引发的元数据锁。死锁则看 LATEST DETECTED DEADLOCK 段，它会给出两个事务各自持有和等待的锁，以及最后被回滚的事务，按这个顺序还原加锁次序，才能找到修复点。

七、改写策略：先减少工作量

优化的第一优先级不是加索引，而是让查询少做无用功。只取需要的列，避免 SELECT *，既减少网络传输，也给覆盖索引创造条件。深翻页是典型场景，LIMIT 100000, 20 会先读出前十万行再丢弃，可以改成延迟关联：先用覆盖索引取出主键，再回表取整行。

更彻底的是游标分页，把“第几页”换成“上一页最后一条的排序值”，让每次查询都从索引的某个位置继续。它要求排序键稳定，通常用 (created_at, id) 组合并加唯一性兜底。大查询可以拆成多次小查询，减少单次锁持有时间与内存占用；OR 改 UNION ALL 只在两个分支都能走索引且不需要去重时更优，否则可能持平甚至更差。循环里逐条查询应改成批量 IN，把 N 次往返压缩成一次。

八、索引调整：只讲怎么验证有效

索引怎么设计属于另一篇的主题，这里只保留验证方法。加索引后，EXPLAIN 里应看到 key 变成目标索引、rows 明显下降；如果查询列都在索引中，Extra 会出现 Using index，也就是覆盖索引，回表消失。联合索引的顺序要与查询条件对齐：等值条件在前，排序列在后，范围条件尽量靠后，key_len 可以告诉实际用到了几列。

如果优化器没有选目标索引，可以打开 optimizer_trace 查看代价计算，确认是统计信息过期，还是代价模型判断不同；统计信息长期不更新，估算就会偏离真实分布。验证时还要看写代价。索引会增加插入与更新的维护成本，重复索引、低选择性索引要清理。用 pt-index-usage 之类工具核对索引是否被使用，比凭感觉删索引安全。索引不是越多越好，能用一个联合索引覆盖多个查询，通常比堆多个单列索引更划算。

九、验证：用同一把尺子量前后

优化是否有效，不能靠“看起来更快”。至少做三组对比：优化前后的 EXPLAIN，重点看访问方式、扫描行数与 Extra；同一数据集上的实际执行时间，多跑几次取稳定值；以及扫描行数，可以用 SHOW SESSION STATUS LIKE 'Handler_read%' 观察 Handler_read_next、Handler_read_rnd_next 的变化。

测试数据要接近生产分布，否则选择性判断会失真；还要考虑缓存，第一次执行与缓存命中后的耗时差异很大，比较时应统一预热条件。上线前做压测回归，观察 QPS、P99 与数据库 CPU，确认优化没有把压力转移到别处。若在从库或影子库验证，要注明隔离级别、数据版本与参数差异，避免结论不可迁移。

十、业务层：数据库不是唯一答案

不是所有慢查询都该在数据库里解决。读多写少且容忍短暂不一致的数据，可以加缓存，但要设计失效与穿透保护；报表类查询可以走只读从库，做读写分离，同时接受复制延迟；历史数据按时间归档到冷表或离线存储，能让热表保持较小规模；通知、导出、统计这类非实时任务可以异步化，把长查询从请求链路里移走。

这些手段都有代价：缓存带来一致性复杂度，读写分离带来延迟与路由问题，归档需要迁移方案与回滚预案。判断标准仍然是业务能接受多旧的数据、多长的延迟，而不是哪个方案听起来更高级。

十一、防回归：把优化变成机制

一次优化只能解决一条 SQL，机制才能防止问题反复出现。慢查询监控要设告警，按指纹聚合而不是按单条日志，阈值与业务分级对应；SQL 审核要覆盖上线流程，至少检查是否走索引、是否深分页、是否有隐式转换；上线前的 EXPLAIN 检查应作为清单项，而不是可选项；定期巡检则关注新增的慢查询指纹、索引使用率、长事务与锁等待趋势。

监控指标要能回答“哪类查询在变慢”，而不只是“数据库 CPU 很高”。把慢日志、performance_schema 与业务链路追踪关联起来，才能在下一次故障前发现问题。

十三、常见误区

只加索引不改写法，是最常见的无效优化：索引列上套了函数、发生了隐式转换，索引依然用不上。用 LIKE '%关键词%' 做前缀模糊匹配，普通 B+Tree 索引无能为力，应评估全文检索或外部搜索。忽略数据分布也会误判，status 只有两种取值时，优化器可能认为全表扫描更便宜，rows 与 filtered 要结合基数一起看。

优化后不复测，等于没有优化；把 EXPLAIN 的 rows 当成精确值，也会导致错误结论，它只是估算，实际扫描行数要用 Handler 计数器或 performance_schema 验证。还有一种误区是只盯数据库：连接池过小、应用层 N+1 查询、序列化过大，都会表现为“SQL 慢”。定位时先把链路上的每一段拆开，再决定改哪一层。

小结

慢 SQL 的治理是一条闭环：先按业务定义阈值，再用慢日志与聚合工具找到高影响查询，接着用 EXPLAIN、锁等待视图和实际扫描行数定位原因，最后通过改写、索引与业务层手段解决，并用同一套指标验证效果。索引原理与设计细节值得单独研究，但流程本身并不复杂，难的是把它变成团队习惯。把采集、告警、审核和复测固化下来，下一次出现慢查询时，我们面对的就是一个已知问题，而不是一场临时的救火。
