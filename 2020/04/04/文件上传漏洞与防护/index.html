文件上传漏洞与防护

文件上传把外部字节写入服务器并可能再次解析，是高风险入口。本文梳理文件上传的风险面、校验原理、存储隔离与检测修复，面向在授权范围内做安全测试与整改的工程师。文中只讨论原理与无害验证，不给出可执行脚本或绕过样例。

一、上传功能的风险面

上传把外部字节带入服务端，经历临时落盘、校验、改名、存储、对外访问五个环节。风险面有四类：上传目录可执行，Web 服务器按扩展名把文件交给脚本引擎；路径可控，文件名或子目录直接取自请求；类型校验缺失，可执行文件、伪造图片和超大文件进入存储；解析漏洞，服务器对路径的处理与校验逻辑不一致。这些问题会叠加，目录可执行放大类型校验缺失的后果。上传点应按高风险入口对待。

二、校验层次与绕过原理

浏览器里的 JavaScript 校验只能改善体验，不能构成安全边界。攻击者可以不走页面，直接构造 HTTP 请求；服务端必须在文件受控落盘之后、对外可见之前独立校验。

multipart 请求里的 Content-Type 由客户端填写，只能当作提示。“Content-Type 是 image/jpeg 就放行”等于没有校验。

扩展名黑名单的枚举永远不完整。不同运行时和服务器对同一文件是否可执行判断不同，大小写变形、双扩展名、末尾点号或空格、历史上的空字节截断，都可能让校验与实际解析产生偏差。黑名单还容易漏掉备份、模板和默认映射后缀，漏掉一个就失效。

文件头魔数同样可以伪造，只能作为辅助信号。基于“排除坏东西”的校验不可靠，应改成“只允许已知的好东西”。

三、扩展名与解析：白名单优于黑名单

白名单先列出业务真正需要的类型，再为每种类型规定唯一的存储扩展名，例如头像只允许 JPEG 和 PNG。原始文件名只作展示，存储扩展名由服务端映射表决定，不能取自用户输入。

可执行扩展名远不止一种。PHP 有 php、php3、php5、phtml 等历史后缀，Java 容器有 jsp、jspx，ASP.NET 有 asp、aspx，此外还有 cgi、pl、py、sh 等。防护要把当前环境可能交给解释器的后缀全部拒绝。

解析配置同样关键。Apache 的 AddHandler、SetHandler、多后缀处理和 .htaccess 覆盖，Nginx 的 location 正则与 PATH_INFO 处理，都可能让图片文件进入脚本分支。稳妥做法是让上传目录根本不具备脚本执行能力：独立域名、独立目录、不配置脚本处理器。

四、内容校验：从文件头到重编码

内容校验的第一层是检查文件头。JPEG、PNG、GIF、PDF 都有相对固定的起始字节，可过滤明显不符的文件。但文件头很短、容易伪造，适合快速拒绝，不适合最终放行。

第二层是交给真正的解析器解码。以图片为例，服务端用图像库打开文件，确认格式、宽高、色彩模式都能正常解析；解析失败、尺寸异常、像素总数过大的文件直接拒绝。可以先校验结构，再重新解码并保存为新文件：

重新编码的意义在于输出文件由服务端重新生成，原始文件附加的脚本片段、异常元数据、畸形分块不会原样进入存储。多义文件经过解码和重写后也只剩像素数据，这一步通常称为二次渲染。

但重编码不是万能的。PDF、Office 文档、音视频、压缩包无法简单解码成像素再写回。对这类文件应依赖类型白名单、病毒扫描、隔离存储和安全响应头。

五、路径穿越与文件名

路径穿越的本质是让服务端把用户提供的路径片段拼进真实路径，从而跳出预期目录。常见变形包括上一级目录、绝对路径，以及编码或 Unicode 归一化导致的解释差异。只检查文件名里有没有某几个字符并不可靠。

更稳妥的原则是根本不使用用户提供的路径。存储目录由服务端按业务和用户标识生成，文件名使用 UUID 或足够长的随机串，扩展名从白名单映射表中取。原始文件名只写入数据库作为展示字段。

如果业务需要保留目录结构，必须对最终路径做规范化，确认它仍位于允许的根目录之内。存储路径与访问 URL 也要分离：数据库保存相对标识，下载接口根据标识查询记录并鉴权，而不是把磁盘路径拼进 URL。

六、存储隔离

上传目录与 Web 根目录分离是最有价值的一项改造。文件落在 Web 根目录之外，Web 服务器默认无法直接访问，即使出现可执行内容也不会被解析。对外访问时，可以由应用鉴权后通过内部重定向把文件流式返回，或者放到独立域名、独立对象存储上。

独立域名可以隔离同源权限。即使文件被浏览器当作 HTML 打开，它也运行在另一个源上，拿不到主站 Cookie。配合 Content-Disposition 强制下载、X-Content-Type-Options 禁止嗅探，可以降低误解析概率。

权限方面，上传进程只应拥有写入权限，不应拥有执行权限；存放目录可以挂载为不可执行；上传服务账户与主站应用账户尽量分离。对象存储通过私有桶、临时签名 URL 和后端代理下载控制访问。

七、大小与资源限制

上传接口必须限制请求体大小。Web 服务器层设置请求体上限，应用层再按业务设置单文件大小、文件数量、文件名长度和字段数量。两层都需要，因为请求体在进入应用前已占用连接和临时磁盘，而不同接口的业务上限不同。

分片上传要把边界想清楚。每个分片都应携带上传会话标识，服务端确认会话属于当前用户、分片序号在允许范围内、累计大小没有超限。合并阶段仍要重新校验总大小和文件数量，不能假设前面的分片都通过检查。分片标识和临时目录不能由客户端任意指定。

压缩包要防范解压炸弹：极小的文件可以解出极大内容，或者通过嵌套和海量小文件耗尽资源。防护要点是限制压缩比、解压后总字节数、嵌套层数和文件数量，并在解压过程中持续计数，超过阈值立即终止。图片则限制像素总数和解码时间。

八、鉴权与业务

上传接口首先是业务接口，必须经过身份认证和权限判断。匿名上传会让存储、审核和追溯失控：无法确认归属、做配额和追责。确需匿名提交的场景，应使用一次性令牌、验证码、频率限制和人工审核，并把文件放入隔离区，审核通过后才对外可见。

登录用户之间也要隔离。每个文件记录所有者、业务对象、创建时间、来源 IP 和校验结果；查询和下载按所有者或业务权限过滤，不能只凭一个可猜测的标识就返回文件。上传、删除、审核、下载等动作写入审计日志，日志记录文件标识而不是完整路径。

公开图片也应区分存储标识和公开地址，公开地址使用不可预测的随机串，删除或封禁时让标识失效。

九、检测方法：在授权环境里验证

检测上传问题的第一步是梳理上传点：表单、富文本、头像、附件、导入接口和移动端接口，记录请求方法、鉴权方式、返回结构和文件最终地址。

第二步是观察响应与回显。上传无害的纯文本文件或测试图片，观察服务端是否返回存储路径、大小、哈希或预览地址；对比成功与失败的状态码、错误信息和响应时间。错误信息如果暴露磁盘路径、框架版本或校验规则，也需要整改。

第三步是在授权范围内访问上传结果，确认文件能否通过返回地址直接访问、是否需要鉴权、响应头是否允许浏览器嗅探或内联执行。不要上传可执行内容来证明漏洞；可以用无害文件配合配置检查、日志和隔离策略说明风险。解析行为的验证只在隔离测试环境进行，并事先取得书面授权，明确目标、时间窗口和禁止动作。检测产出应是可复现步骤、影响说明、证据和修复建议。

十、修复清单

把要点收敛成一份可执行清单：

  1. 类型白名单：只允许业务必需的类型，维护扩展名与 MIME 映射，拒绝表外组合。
  2. 内容校验：检查文件头并解码；图片限制尺寸和像素，必要时二次渲染。
  3. 服务端改名：使用随机标识，扩展名由服务端决定，原名只作展示。
  4. 隔离存储：上传目录移出 Web 根目录，使用独立域名或私有存储，下载走鉴权代理。
  5. 禁止执行：目录不配置脚本处理器，必要时以不可执行方式挂载。
  6. 访问控制：上传、下载、删除都鉴权，按用户隔离并设置配额。
  7. 资源限制：请求体、单文件、文件数量、解压总量、图片像素都有上限。
  8. 审计与复测：记录关键动作，修复后用无害用例回归，确认旧路径已失效。

纵深防御的含义是任何一层都可能出错：白名单挡住大多数错误类型，内容校验处理伪造，重命名和隔离降低影响，禁止执行兜住解析风险。

十一、Nginx 配置示例

下面给出一个偏保守的 Nginx 片段，让上传文件所在域名只提供静态读取，不配置脚本处理器，并用正则显式拒绝可执行后缀。实际部署还要结合应用的上传接口和鉴权逻辑调整。

这个 server 块没有 fastcgi_pass 或其他脚本处理器，即使正则漏掉某个后缀，文件也不会被执行。autoindex off 防止目录被列出，避免文件名被批量枚举。Content-Disposition 让浏览器按下载处理，降低 HTML 或 SVG 被内联渲染的风险；如需在线预览图片，应单独设置可信类型。internal 位置只能由应用通过内部重定向访问，适合鉴权下载。client_max_body_size 只是第一道限制，应用层仍要按业务校验。如果上传接口和静态文件在同一域名，至少要把上传目录放在 Web 根目录之外，通过应用代理读取。

十二、常见误区

只做前端校验是第一个误区。浏览器检查可以被跳过，服务端必须独立判断。第二个误区是只查 Content-Type；这个字段由客户端提供，伪造成本极低，只能作为辅助信息。

第三个误区是把文件存进 Web 根目录并沿用原始文件名。前者让文件天然可访问，后者让路径和类型都受用户控制。第四个误区是认为改了扩展名就安全。解析行为由服务器配置决定，扩展名只是一环；如果目录仍可执行，或者存在多后缀解析，改名并不能兜底。

第五个误区是上传目录允许列目录。目录列表会把私有文件变成可枚举资源。第六个误区是修复后不复测。旧 URL、缓存、备份目录和测试接口都可能仍可用，必须用无害用例回归。防护没有单点银弹，它是一组彼此独立的约束：类型、内容、名称、路径、存储、权限、鉴权、限额和日志。

小结

文件上传的风险来自外部字节进入服务端并被再次解析，单靠某一层校验无法可靠解决。实践上应以白名单为起点，用内容解码和重编码处理伪造，用服务端随机命名和路径规范化消除路径问题，再把文件放到不可执行、需鉴权的隔离存储中。检测应在书面授权和隔离环境内进行，只做无害验证。最后把限额、日志和复测纳入日常流程。
