MySQL 索引原理与优化

索引几乎是每张业务表都会写的语句，但“加了索引为什么还是慢”却经常说不清。本文从 InnoDB 的数据组织方式讲起，依次拆解 B+Tree、聚簇索引与二级索引、覆盖索引、最左前缀和索引条件下推，最后给出联合索引设计、索引失效排查与日常维护的流程。读者应已能编写基本 SQL，读完后可以独立判断一条查询该不该建索引、该建什么索引。

索引是什么

索引本质上是一种排好序的数据结构，用额外的存储空间换取更少的扫描行数。没有索引时，查询只能从第一页读到最后一页，代价随表的大小线性增长；有了索引，数据库可以先在树上定位到少量候选记录，再把 I/O 次数压到树高这个量级。

InnoDB 的特殊之处在于，索引不只是加速手段，它就是数据本身。表按主键组织成一棵 B+Tree，叶子节点存放完整行，这种表也被称为索引组织表。因此讨论 InnoDB 的索引，实际上是在讨论“数据怎么排、页怎么连、一次查询要读几个页”。

B+Tree：为磁盘而生的结构

为什么是 B+Tree？二叉树每个节点只有两个分叉，百万行数据会形成二十多层，每下探一层都可能是一次磁盘 I/O；哈希索引虽然等值查询是 O(1)，却不支持范围扫描和排序，也无法满足 ORDER BY。B+Tree 把这两类需求折中得最好。

InnoDB 以 16 KB 的页为读写单位，B+Tree 的阶数（一个节点最多容纳的子节点数）由页大小和键长共同决定。非叶子节点只保存键和子页指针，不保存整行，所以一页能容纳数百甚至上千个键，扇出非常大；叶子节点按键有序排列，并用双向链表连接。这样范围查询只需定位起点，再顺着叶子链表读取。一棵三层左右的树就能容纳千万级记录，点查通常只需两到三次页访问，而且根节点往往常驻缓冲池。

    R --> B["内部页：13 | 17"]
    R --> C["内部页：23 | 27"]

图中非叶子页只承担导航，真正的记录都在叶子页；页内有序、页间成链，范围扫描才不必回到根节点反复查找。树高由阶数和记录总量共同决定，这也是主键不宜过长的原因之一。

聚簇索引与主键选择

聚簇索引的叶子节点就是数据页，主键值决定了一行记录在磁盘上的大致位置。这个设计让主键查询非常快，但也把主键选择的影响放大了。

自增主键总是追加到最右侧的叶子页，页写满后再申请新页，空间利用率高，写入也基本是顺序 I/O。UUID 这类随机主键则相反：新记录会落到树的中间，目标页已满时触发页分裂，一半数据被搬到新页，留下空洞和碎片；同时每个二级索引的叶子都要保存主键，主键越长，所有二级索引越臃肿。若没有显式主键，InnoDB 会选择第一个非空唯一索引，否则生成 6 字节的隐藏 row ID，这更说明主键应当由设计者显式给出。

二级索引与回表

二级索引的叶子只保存索引列和主键值，不保存整行。通过二级索引找到主键后，再拿主键去聚簇索引取整行，这个过程叫回表。一次回表就是一次按主键的查找，虽然可能命中缓冲池，但行数多时仍是可观的随机 I/O。

回表的次数取决于索引扫描出的候选行数，而不是最终返回的行数。例如给 status 建了单列索引，查询 WHERE status = 'paid' 命中十万行，就要回表十万次；如果这些行在表中分布很散，优化器很可能放弃索引，直接全表扫描。LIMIT 10 也未必能救场：若还需要排序，服务器可能要先取出大量行再排序，最后才截断。二级索引查询比想象中慢，原因通常就在这里。

覆盖索引：不回表的查询

如果一条查询需要的列全部能在二级索引里找到，就不需要回表，这就是覆盖索引。例如联合索引 (user_id, status, created_at) 上的查询只取这三列，EXPLAIN 的 Extra 会显示 Using index。这里的 index 指“只读索引”，不是“用到了索引”；后者对应的是 key 列有值。

覆盖索引的收益是把“索引扫描 + N 次回表”变成一次顺序的索引扫描，对高频查询非常有效。代价同样明显：索引要额外保存这些列，页数变多，缓冲池命中率下降，插入和更新也要维护更多内容。把十几个列塞进一个索引来覆盖所有查询，往往得不偿失；覆盖索引应当服务于少数核心查询，而不是成为默认做法。

最左前缀：联合索引的使用边界

在 MySQL 5.7 中，联合索引 (a, b, c) 先按 a 排序，a 相同再按 b，b 相同再按 c，因此只能从最左列开始连续使用。a = 1、a = 1 AND b = 2、三列都带等值条件，都可以用满索引；a = 1 AND c = 2 只用到 a，因为缺少 b 时，c 在索引中并不是整体有序的。

范围条件会截断后续列。a = 1 AND b > 2 AND c = 3 中，b 已经变成范围扫描，c 无法继续用于缩小扫描区间；MySQL 5.6 之后可以把 c 条件下推到索引层做过滤，减少回表，但它仍然不是定位条件。EXPLAIN 的 key_len 能反映实际用到的前缀长度：只带 a 时约为 8 字节，带上 b 后增加，c 不再增长就说明它没参与定位。另外，WHERE 中条件的书写顺序不影响结果，优化器会自动把等值条件排到前面。

联合索引的列顺序

联合索引的列顺序没有放之四海皆准的公式，但有一条稳定的原则：等值过滤列在前，范围列和排序列在后。等值列之间的先后，通常把区分度高的放在前面，这样只带第一列的查询也能有较好的过滤效果；但这不是铁律。若业务最常见的查询只带 status，而 status 的取值很少，把 (status, created_at) 作为前缀反而更实用。

排序和分组会改变结论。WHERE user_id = ? ORDER BY created_at 适合 (user_id, created_at)，因为 user_id 固定后，索引天然按 created_at 有序，可以省掉 filesort；若建成 (created_at, user_id)，则无法同时满足过滤和排序。设计时应先按“查询模板”分组，再为每组选一个能兼顾过滤、排序和覆盖的索引，而不是为每条 SQL 单独建索引。

索引条件下推

索引条件下推（Index Condition Pushdown，ICP）是 MySQL 5.6 引入的能力，5.7 默认开启。它的作用是：当索引中存在无法用于定位、但仍能判断的条件时，先把条件下推到索引页上过滤，只把真正符合条件的行回表。

例如索引 (user_id, status, created_at)，查询 user_id = 42 AND status > 1 AND created_at >= '2020-04-01'。status 是范围条件，created_at 不能继续用于定位，但可以在索引层判断日期，从而减少回表。EXPLAIN 的 Extra 出现 Using index condition 就表示发生了 ICP。它和覆盖索引不同：ICP 仍然要回表，只是回表更少；覆盖索引完全不回表，Extra 是 Using index。看到前者不要误以为查询已经被索引完全覆盖。

选择性与前缀索引

选择性衡量一列“区分行”的能力，常用 COUNT(DISTINCT col) / COUNT(*) 估算，越接近 1 越好。一般可把 10% 以上视为尚可，但阈值要结合数据分布：status 只有几个值，整体选择性很低，可如果 99% 的订单都是“已完成”，查询那 1% 的“异常”订单时，索引反而非常有效。

低选择性列单独建索引，常常是扫描索引再大量回表，不如全表扫描；它更适合放在联合索引的后置列，或作为覆盖索引的一部分。字符串列可以考虑前缀索引：

索引失效的常见场景

索引失效并不是一个非黑即白的判断，更准确的说法是“用不上索引的定位能力”。常见情形有几类。

对索引列做函数或运算，例如 WHERE DATE(created_at) = '2020-04-01'，应改写成范围：created_at >= '2020-04-01' AND created_at < '2020-04-02'。隐式类型转换同样致命：phone 是 VARCHAR，却写成 WHERE phone = 13800138000，MySQL 会把列转成数字再比较，索引随之失效；参数类型应与列类型一致。

LIKE '%张' 这种前导通配无法利用有序性，LIKE '张%' 可以。OR 两侧只要有一侧没有可用索引，整个条件就可能退化为全表扫描，能改 UNION ALL 时优先改写。!=、NOT IN 并非绝对失效，而是通常扫描范围过大、回表太多，优化器会主动放弃；在覆盖索引或小表场景仍可能使用。多表 JOIN 时还要保证关联列字符集与排序规则一致，utf8 与 utf8mb4 混用会引入转换，让索引形同虚设。

索引维护与写放大

索引不是免费的。每个二级索引都是一棵独立的 B+Tree，写入时要同步维护，更新越频繁、索引越多，写放大越明显。日常至少应清理三类索引：完全重复的索引；被更长联合索引前缀覆盖的冗余索引，例如已有 (a, b) 时，单列 (a) 通常可以删除；以及长期没有访问的索引。

MySQL 5.7 可以用 sys.schema_unused_indexes 查看未被使用的索引，但它统计的是实例启动以来的数据，重启后会清零，不能仅凭一次查询就删除，最好观察一个完整的业务周期。加索引的在线 DDL 在 5.7 中可以做到 ALGORITHM=INPLACE, LOCK=NONE，但仍要重建索引、消耗 I/O，大表上还可能拖慢主从复制；低峰期执行、控制并发、提前评估磁盘空间，比记住语法更重要。8.0 提供的不可见索引可以先“隐藏”再观察，适合作为删除前的缓冲。

从查询出发设计索引

索引设计应当从查询出发，而不是从表结构出发。可行的流程如下。

先收集高频 SQL 和核心业务 SQL，可以从慢查询日志、业务代码和接口清单中整理，按表归类。然后为每条 SQL 标出过滤列、排序/分组列、返回列，判断哪些查询值得优化。接着设计联合索引：等值列在前，范围列在后，尽量让核心查询走到覆盖索引；同一张表的多个索引要合并审视，避免前缀重复。

设计完必须用 EXPLAIN 验证，重点看 key 是否命中、key_len 是否用满、rows 的估算量级和 Extra 是否出现 filesort、temporary。不要只看 type：ref 也可能扫描很多行，ALL 在小表上未必慢。最后用接近生产的数据量和分布做压测回归，观察 QPS、延迟以及写入性能的变化。上线后定期复查未使用索引和慢查询，索引方案是迭代出来的，不是一次建完就结束。

常见误区

最后列出几个反复出现的误区。其一是索引越多越好：索引只对特定查询模式有效，多余的索引只会增加写入和存储成本。其二是用 UUID 做主键并随机插入：读取方便了，写入却付出页分裂和碎片的代价。其三是只看 EXPLAIN 的 type：range 可能扫百万行，ALL 可能只扫几千行，rows 和 Extra 同样重要。

其四是忽略数据分布：同一张索引在测试库很快，在生产库可能因为某个值占绝大多数而失效。其五是用覆盖索引掩盖慢查询：覆盖索引只消除了回表，如果过滤条件本身扫描了大量索引条目，查询依旧慢，此时应先改查询条件或调整索引顺序，而不是继续往索引里加列。判断索引好坏的标准始终是“这条查询读了多少页”，而不是“有没有用到索引”。

小结

索引的核心是用有序结构减少页访问：B+Tree 提供稳定的树高和范围扫描能力，聚簇索引决定行的物理组织，二级索引通过主键回表，覆盖索引和 ICP 则分别从“不回表”和“少回表”两个方向降低成本。联合索引要遵守最左前缀，等值列在前、范围列在后，并结合排序与分组需求确定顺序。设计时从高频查询出发，用 EXPLAIN 和真实数据验证，再持续清理冗余与未使用索引。记住，索引是写放大与读性能之间的交易，不是越多越好。
