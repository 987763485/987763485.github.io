MySQL 分库分表方案

单机 MySQL 能支撑的业务规模，往往比很多人想象的大；它触顶的过程，又比很多人想象的更突然。本文从“单库为什么会长成瓶颈”讲起，依次讨论垂直与水平拆分、分片键选择、路由实现、跨分片查询、分布式事务、全局唯一 ID 与在线扩容，重点说清每一步的代价。示例以 MySQL 5.7 与 ShardingSphere 4.x 的写法为主，这套方案在 8.0 上同样适用。

单库的边界在哪里

单机的容量不是一个固定数字，而是一组指标先后触顶的过程。有人看到表里有三千万行就急着拆，也有人等到主库 CPU 长期打满才动手，两种做法都不够稳妥。比较可靠的方式，是分别观察下面几类信号，判断瓶颈究竟落在哪一层。

连接数与线程开销

MySQL 的连接模型是“一连接一线程”，max_connections 在 5.7 与 8.0 中的默认值都是 151。每个连接除了线程栈，还会在需要时分配排序缓冲、连接缓冲等内存，参数调得越大，几百个活跃连接就可能吃掉可观的物理内存。连接数打到上千之后，即使 CPU 占用尚未饱和，吞吐也会因为线程切换和锁竞争而下降。这类问题应当先用连接池收敛、缩短事务持有时间来解决，而不是直接分库。

单表体量与维护窗口

单表行数进入千万级、数据文件涨到几十 GB 之后，B+ 树要多一层才能定位到叶节点，一次查询就多一次随机 I/O；缓存命中率下降，缓冲池里能装下的热数据页变少。更麻烦的是维护动作：加索引、改字段、清理历史数据都要消耗 I/O 与复制延迟预算，备份与恢复的耗时随数据量近似线性增长。MySQL 5.7 的 online DDL 能减少锁表时间，但并不能让大表的 DDL 变成免费操作。

写入吞吐与故障域

单个主库的写入能力受 redo log 刷盘、binlog 落盘、半同步复制确认共同约束，上限由最慢的一环决定。当业务需要每秒数千次写事务时，纵向扩硬件的边际收益很快耗尽。此外，单库同时是故障域：一次误删、一次磁盘损坏、一次机房抖动，影响的是全部业务。拆分的一个隐性收益，是把故障与慢查询的影响限制在部分用户身上。

垂直拆分与水平拆分

拆分有两个正交的方向：一个是把一张宽表或一个库按业务切开，另一个是把同一张表按规则分散到多个物理节点。前者改变结构，后者改变分布，实践中常常组合使用。

垂直拆分：先让边界清晰

垂直分库按业务域切分，例如把用户、商品、订单放进独立实例，各自拥有独立的连接池、备份策略与扩容节奏。垂直分表则是把大字段与访问频率低的字段挪到扩展表，让主表变窄，一行能放下更多记录，缓冲池效率随之提升。

垂直拆分的收益是边界清晰、单表变窄、故障隔离；代价是原本在一个事务里的操作被拆到两个库，跨库关联只能靠应用层拼装。它适合业务边界本来就清楚的系统，如果边界还模糊，贸然分库只会把耦合从 SQL 里搬到代码里。

水平拆分：按规则分散数据

水平拆分保持表结构不变，按分片键把数据分布到多张表或多个库。只分表不分库，能缓解单表体量，但仍在同一个实例上争抢连接与 I/O；只分库不分表，能分散连接与写入，但单表依然会继续长大。常见做法是先分库再分表，例如 4 个库、每个库 8 张表，共 32 个分片。

分片数量要一次规划到位。分片数偏少，很快就需要二次拆分；分片数偏多，每个分片的数据量小，跨分片查询的组合数却成倍增加。经验上按三到五年的数据增长预估，并给单分片留出可观的余量。

拆分的先后顺序

合理的顺序是：先加索引、消除慢查询，再加缓存挡住读流量，然后做读写分离与冷数据归档，最后才考虑拆分。判断是否该拆，看的是“单库写入能力或单表体量是否已经成为确定性瓶颈”，而不是“某几条 SQL 很慢”。前者只能靠分布解决，后者往往只需要一条合适的索引。

分片键与路由

分片键决定了数据如何分布，也决定了以后有多少查询会变成跨分片查询。它一旦上线就很难更改，选型阶段的讨论再多都不算多。

分片键的四个判断标准

第一是基数，取值要足够多，避免大量数据挤在少数分片上。第二是写入均匀，不能出现某个取值天然占据大部分流量。第三是查询亲和，核心链路的查询应当自带分片键，例如订单表按 user_id 分片，用户查自己的订单就能一次定位。第四是跨分片概率，如果大量后台查询按订单号、按时间范围检索，那么分片键的选择就要为这些场景留出退路。

一个常见的补救手段是基因法：订单号生成时把用户 ID 的低若干位编码进去，于是按订单号也能反推出分片位置。代价是 ID 生成逻辑与分片规则耦合，分片数变化时需要重新设计编码位数。

热点分片从哪来

按 merchant_id 分片时，头部商户可能贡献三成流量，这个分片就会持续过热。按时间范围分片时，最新的分片永远承受全部写入，历史分片则几乎只读。解决办法不是加大分片数，而是换维度：写多读少的场景优先用哈希分片打散写入，再对超大商户做二级拆分或独立部署；时间维度则只作为分区或冷热归档的依据。

客户端模式与代理模式

路由逻辑放在哪里，是选型的第二个问题。客户端模式把分片能力做成 jar 包，应用直连数据库；代理模式则伪装成一个 MySQL 服务，应用连代理，由代理转发。

客户端模式的代表是 ShardingSphere 4.x 的 JDBC 版本，SQL 解析、改写、路由、结果归并在进程内完成，少一次网络往返，性能更好；缺点是只对 Java 友好，规则变更要跟着应用发版。代理模式的代表是 MyCat 1.6 与 ShardingSphere-Proxy，语言无关、规则集中管理，但多了一跳转发，代理自身必须做主备，否则它就是新的单点。分片很少、SQL 很简单的系统，也可以在最上层手写路由，把分片规则收敛到 DAO 层，代价是所有业务代码都要感知分片。

跨分片查询的妥协

拆分之后，SQL 的自由度会明显下降。与其在中间件上追求“透明”，不如提前承认哪些查询必须改写。

JOIN 与聚合

同一分片键的订单与订单明细可以绑定，路由到同一个库表后做本地 JOIN。不同维度的关联，只能在应用层拆成两次查询再拼装，或者把常用字段冗余成一张宽表。聚合函数同理：SUM、COUNT 由各分片算出局部结果后归并，COUNT(DISTINCT) 则要把各分片的去重结果拉回内存再合并，分片越多代价越大，能改成预聚合统计表就不要实时算。

分页与全局排序

LIMIT offset, size 在分片下必须改写成 LIMIT 0, offset + size 发往每个分片，再归并排序取中间一段，代价随分片数线性放大。深分页因此成为拆分后最典型的性能问题。可行的做法是只允许“下一页”，用上一页最后一条记录的排序键做游标；或者先在各分片查出边界值，再发起第二轮精确查询。全局 ORDER BY 非分片键字段时，归并需要内存缓冲，数据量大时要限制参与排序的行数，不能指望中间件无上限地兜底。

这些限制并不优雅，但它们把成本摆在了明处：要么改查询，要么改模型，要么接受有限的功能降级。

分布式事务与全局唯一 ID

跨库写入把本地事务变成了分布式问题，全局 ID 则是拆分后最先撞上的工程细节，两者都要在动手之前想清楚。

三种一致性方案

XA 与 2PC：InnoDB 支持 XA 事务，ShardingSphere 4.x 也提供 XA 事务类型，由协调者分两阶段提交。它的语义最强，但 prepare 阶段长时间持有锁，协调者宕机会让参与者悬而未决，吞吐明显低于本地事务，只适合短小且并发不高的操作。

TCC：业务自己实现 Try、Confirm、Cancel 三个阶段，先预留资源再确认或释放。它不长时间占用数据库锁，性能较好，但要处理空回滚、幂等与悬挂三种异常，开发成本最高，通常只用在资金与库存这类不能出错的环节。

可靠消息与本地消息表：在同一个本地事务里写业务数据与一条消息记录，再由后台任务投递，下游幂等消费。它把强一致换成最终一致，实现简单、可观测，适合下单后发积分、发通知这类场景。

先改边界，再谈事务

相当一部分分布式事务，是拆分边界画错造成的：订单与订单明细本可以按同一个 order_id 落在同一分片，却被拆进了两个库。能通过重新划分片键放进同一库的操作，就不要交给分布式事务；只有真正跨业务域的写入，才值得付出协调成本。

全局唯一 ID

自增主键在分片后不再全局唯一，常见方案有三种。Snowflake 用 41 位毫秒时间、10 位机器标识与 12 位序列拼成 64 位整数，趋势递增且不依赖数据库，但要处理时钟回拨：可以短暂等待、直接报错，或换用备用机器标识；容器化部署时机器标识的分配也要有统一来源。号段模式在数据库里维护 max_id 与步长，一次取一批缓存在内存并预取下一段，数据库压力很小，代价是重启会浪费一段 ID。Redis 的 INCR 最简单，但要保证持久化与主从切换时不回退，否则可能发出重复 ID。

在线扩容与运维坑

双写与影子表迁移

扩容或调整分片数时，停机迁移几乎不可接受。稳妥的流程是：先建好新分片并开启双写，让新数据同时写入新旧两侧；再按分片全量搬迁历史数据；然后追平迁移期间产生的增量，通常按更新时间或 binlog 位点补齐；接着做一致性校验，逐分片比对行数与抽样字段；确认无误后切读、停双写，旧库保留只读一段时间作为回滚退路。

其中任何一步断裂都会导致数据不一致，所以每一步都要能单独重跑，双写失败也要留下补偿记录。

运维中最容易忽略的几件事

跨分片事务的可见性：A 分片已提交、B 分片回滚时，其他请求可能读到中间状态，业务要能容忍，或用状态机兜底。热点与倾斜：分片键的分布要定期出直方图，头部取值单独治理。分片数规划：改分片数等于一次全量迁移，初期宁可多留余量。监控：按分片采集 QPS、连接数、慢查询、主从延迟与磁盘增速，单个分片异常应独立告警，而不是只看集群总量。

小结

分库分表是容量治理的最后手段，而不是性能优化的起点。先确认瓶颈确实在单库写入或单表体量，再用垂直拆分理清边界、用水平拆分分散数据；分片键要同时满足分布均匀与查询亲和，路由方式则按团队技术栈在客户端与代理之间取舍。跨分片 JOIN、聚合与深分页没有免费方案，分布式事务能避免就避免，全局 ID 要提前处理时钟与分配问题。扩容方案应当在上线前就设计好，双写、校验与回滚缺一不可。
