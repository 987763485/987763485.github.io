Kubernetes 集群部署实践

本文属于《Docker 与 Kubernetes》第 21/51 篇
上一篇系列目录下一篇

本文记录一次小规模生产集群的搭建过程：三台控制面、若干工作节点，操作系统为 Ubuntu 18.04，目标版本 Kubernetes 1.18。文章从规划、运行时选择讲到 kubeadm 初始化、控制面高可用、节点加入和安装后加固，重点解释每一步为什么这样做，以及出错时先查什么。读者需要具备 Linux 命令行与 Docker 的基本使用经验，读完后应能独立完成一套可用的测试或小生产集群。

一、规划阶段先定六件事

部署事故很少是某条命令敲错，更多是规划时留下空白：Pod 网段和公司 VPN 撞车、节点时间不同步导致证书校验失败、防火墙只放行 6443 却忘了 kubelet 的 10250。本文建议在装系统之前，把节点、系统、网段、端口和证书写成一张清单。

节点角色与数量。控制面承担 apiserver、scheduler、controller-manager 与 etcd，生产环境至少 3 台，且尽量分布在不同物理机或可用区。工作节点按业务域分池，例如通用池与内存密集型池，后续靠标签和污点调度。控制面默认带 node-role.kubernetes.io/master:NoSchedule 污点，业务 Pod 不会落上去；测试环境若只有一台机器可以临时去掉，生产环境不要这么做。

节点规格要按 Pod 密度倒推。生产节点建议预留 10% 到 20% 的资源给系统组件，并在 kubelet 配置中设置 --system-reserved 与 --kube-reserved，否则业务把节点压满后，kubelet 自己会先被 OOM。磁盘同样要留余量，镜像与容器日志默认写在 /var/lib/docker 或 /var/lib/containerd，单独挂一块数据盘能避免根分区被日志写满。

操作系统基线。Ubuntu 18.04 与 CentOS 7 都可以，关键是四件事：关闭 swap 并注释 /etc/fstab 中的交换分区，因为 kubelet 的资源计算与调度假设不依赖交换；加载 overlay 与 br_netfilter 模块，设置 net.bridge.bridge-nf-call-iptables=1 与 net.ipv4.ip_forward=1，否则跨节点 Pod 通信和 Service 转发都会出问题；用 chrony 指向同一组 NTP 源，时间漂移会让证书校验和 token 有效期判断出错；主机名唯一并写入所有节点的 /etc/hosts，避免 DNS 反查超时拖慢启动。

网段规划。Service 网段常用 10.96.0.0/12，Pod 网段常用 10.244.0.0/16（Flannel 默认）或 192.168.0.0/16（Calico 默认）。这两个网段不能与办公网、VPC、VPN 重叠，否则会出现“集群内能通、集群外访问随机失败”的怪问题。节点 IP 建议单独划分管理网段，并与 Pod、Service 网段错开。

端口矩阵。控制面之间放行 6443（apiserver）、2379 与 2380（etcd）；控制面到所有节点放行 10250（kubelet）；30000 到 32767 留给 NodePort，按需对负载均衡开放；CNI 还要额外端口，Flannel 的 VXLAN 用 8472/UDP，Calico 的 BGP 用 179/TCP。云上还要同步安全组，很多“节点加入失败”最后都查到这里。

证书计划。kubeadm 会自动生成一套 CA 和叶子证书，叶子证书默认有效期 1 年，CA 为 10 年。初始化时把 CA 证书与 key 单独备份；controlPlaneEndpoint 使用的域名或 VIP 必须写进 apiserver 证书的 SAN，否则 kubectl 会报 x509: certificate is valid for ...。如果计划用外部负载均衡，域名要在初始化前确定，事后改 SAN 需要重新签发证书。

二、容器运行时与 cgroup driver

Kubernetes 1.18 支持 Docker 19.03 与 containerd 1.3 两条常见路径。Docker 通过 kubelet 内置的 dockershim 接入，优势是镜像构建、调试习惯和生态成熟；containerd 自带 CRI 插件，少一层 dockerd，资源占用与故障面更小。团队已有 Docker 流水线时选 Docker 最省事；追求精简或已经用 containerd 跑其他负载时，选 containerd 也完全可行。一个集群只选一种，不要在同一批节点上混装。

选择 containerd 时，kubelet 的 --container-runtime-endpoint 要指向 unix:///run/containerd/containerd.sock；Docker 则保持默认的 dockershim 套接字。这个地址写错时 kubelet 会直接报连接失败，节点自然无法注册，排查时先看这一项。

真正容易出事的是 cgroup driver。Linux 上有 cgroupfs 与 systemd 两套管理方式，Docker 默认 cgroupfs，containerd 1.3 默认也是 cgroupfs，而 systemd 发行版上的 kubelet 推荐使用 systemd。两者不一致时，kubelet 以为容器挂在 systemd 层级，运行时却把容器创建在 cgroupfs 层级，资源统计和 Pod 沙箱创建都会失败，节点表现为反复 NotReady 或 kubelet 不断重启。

多网卡节点还要注意 CNI 的网卡选择。Calico 默认自动探测，可能选中没有到其他节点路由的网卡，表现为同节点 Pod 能通、跨节点不通；此时通过 IP_AUTODETECTION_METHOD 或 kubelet 的 --node-ip 明确指定地址。Flannel 同理，启动参数里的 --iface 要指向管理网卡。

四、控制面高可用：三节点 stacked etcd

单台控制面是明显的单点。生产环境通常用三台控制面，每台同时运行 apiserver 与 etcd，这种布局叫 stacked etcd；它的部署简单，但控制面节点故障会同时损失一个 etcd 成员，因此三台要尽量分散在不同宿主机上。

flowchart TD
  LB["VIP 10.0.0.100:8443"] --> M1["master-01 apiserver + etcd"]
  LB --> M2["master-02 apiserver + etcd"]
  LB --> M3["master-03 apiserver + etcd"]
  W1["worker-01 kubelet"] --> LB
  W2["worker-02 kubelet"] --> LB

负载均衡可以用 HAProxy 加 keepalived 提供 VIP，后端指向三台控制面的 6443，健康检查走 /healthz。所有节点、kubectl 以及后续加入的机器都只认这个 VIP，不直连某一台 apiserver。第一台初始化时 VIP 可能只有它一个健康后端，这没有问题，但要保证 VIP 本身已经可访问。

上线前做一次故障演练：在负载均衡上摘掉一台后端，确认 kubectl 仍然可用；再停掉一台 etcd，确认 kubectl get nodes 仍能返回。演练通过才说明高可用成立，只看三台同时健康并没有意义。

stacked etcd 的代价是故障域耦合：控制面节点宕机，既少一个 apiserver，也少一个 etcd 成员。如果团队已经有独立维护的 etcd 集群，可以改用 external etcd 模式，让 etcd 与 apiserver 分开部署；代价是节点更多、证书与连接参数更复杂，小团队通常不值得。

etcd 的成员数必须是奇数。quorum 为多数派，3 个成员允许坏 1 个，5 个允许坏 2 个；2 个成员需要两个都在线才能写入，故障容忍度反而是 0，4 个成员与 3 个一样只能坏 1 个，却增加了需要协调的成员数量和分裂风险。因此要么 3 台，要么 5 台，不要为了“对称”凑成偶数。etcd 对磁盘延迟非常敏感，数据目录尽量放在 SSD 上，并监控 fsync 耗时。

五、加入工作节点与安装后必做

工作节点加入靠 bootstrap token，默认有效期 24 小时。token 过期后不必重新初始化，在控制面执行 kubeadm token create --print-join-command 会直接打印一条可用的 join 命令。把命令拿到工作节点执行，成功后回控制面确认：

然后按用途打标签，例如 kubectl label node k8s-worker-01 node-role.kubernetes.io/worker=，再补上机房、机型等自定义标签。控制面的 NoSchedule 污点保持不动，除非确实要让控制面也承载业务。

验证 CoreDNS 时，启动一个临时 Pod 执行 nslookup kubernetes.default，返回 ClusterIP 即正常；验证 metrics-server 用 kubectl top nodes，能显示 CPU 与内存说明采集链路已经通了。这两个命令比只看 Pod 状态更接近真实可用性。

集群可用之后，还有六件事需要收尾。第一是 CoreDNS：默认两个副本，节点较多或 DNS 查询量大时按比例扩容，并用临时 Pod 验证解析。第二是 kube-proxy 模式：默认 iptables 在几百个 Service 以内足够，规模上来后可切 IPVS，修改 kube-system/kube-proxy ConfigMap 的 mode 后删除 kube-proxy Pod 让其重建，同时确认内核加载了 ip_vs 系列模块与 ipset。第三是 metrics-server 0.3.6，kubectl top 依赖它；自签证书环境要给启动参数加 --kubelet-insecure-tls，否则一直拿不到指标。

第四是存储。新集群没有默认 StorageClass，PVC 会一直 Pending。先决定后端是 NFS、Ceph 还是云盘，再安装对应 provisioner，并用注解 storageclass.kubernetes.io/is-default-class: "true" 标记唯一的默认类。第五是 RBAC：给每个业务建 Namespace，CI 使用独立的 ServiceAccount 与 RoleBinding，只授予目标 Namespace 内的 Deployment 和 Pod 权限，不要图省事发 cluster-admin：

第六是审计日志。在 ClusterConfiguration 的 apiServer.extraArgs 中配置 audit-policy-file 与 audit-log-path，通过 extraVolumes 把策略文件挂进静态 Pod，并设置轮转参数，避免日志撑满磁盘。审计策略至少记录写操作与 Secret 读取，否则出了问题没有追溯依据。

六、常见故障与升级维护

部署期的问题大多集中在几张网卡和几个端口上，先按现象归类，再逐项排查，比盲目重装有效：

现象 常见原因 处理
kubelet 启动即退出 swap 未关闭 swapoff -a 并清理 fstab
join 超时 安全组未放行 6443 放行控制面入站
kubectl logs 失败 10250 被拦截 控制面到节点放行
etcd 成员频繁失联 2379/2380 不通或磁盘慢 查网络与 fsync
证书过期或 not yet valid 节点时间漂移 chrony 重新同步
节点反复 NotReady cgroup driver 不一致 三处对齐为 systemd
Pod 一直 ImagePullBackOff 私库认证或离线缺镜像 imagePullSecrets、预导入
CoreDNS Pending CNI 未就绪或网段不匹配 查 CNI 日志与 CIDR

节点 NotReady 时，先在节点上执行 systemctl status kubelet 与 journalctl -u kubelet -n 100，确认它能否连上 apiserver；Pod 起不来则按 kubectl describe pod 的 Events、kubectl logs 的上一条容器日志、节点上的 crictl ps -a 三层往下查。多数问题在 Events 里已有明确原因，不要一上来就删 Pod 重建。

升级要遵守“一次一个小版本”的原则，1.17 升 1.18 可以，直接跨到 1.19 不行，因为 kubelet 与 apiserver 的 skew 有限制，跳版会留下无法自动迁移的字段。升级前先备份 etcd，快照文件放到集群之外：

然后升级控制面，再逐台处理工作节点。控制面升级时先在第一台执行 kubeadm upgrade apply，其余控制面执行 kubeadm upgrade node，每台完成后再处理下一台，保证任意时刻至少有两台 apiserver 可用。工作节点先 kubectl drain --ignore-daemonsets --delete-local-data，升级 kubeadm、kubelet、kubectl 后执行 kubeadm upgrade node，重启 kubelet，最后 kubectl uncordon 恢复调度。顺序反过来会让新版本 kubelet 连不上旧 apiserver，排查成本更高。

备份文件只有真正恢复过一次才算备份。建议在测试环境用 etcdctl snapshot restore 恢复到临时目录，再启动一个单节点 etcd 验证数据完整；同时检查快照时间与大小，避免定时任务早已失败却无人发现。

证书也要纳入例行检查。kubeadm alpha certs check-expiration 会列出各证书剩余时间，临近一年时用 kubeadm alpha certs renew all 续期，再重启 kubelet 与静态 Pod 让新证书生效。把这条检查和 etcd 快照一起写进季度运维清单，能避免“一年后集群突然连不上”的经典事故。

小结

Kubernetes 集群部署的难点不在命令本身，而在前置约束：网段不冲突、时间同步、端口放行、cgroup driver 一致，这四项决定了后面是否顺利。控制面至少三台并保持 etcd 成员为奇数，所有客户端统一走负载均衡 VIP；工作节点通过 token 加入后，及时补齐 CoreDNS、metrics-server、存储、RBAC 与审计。升级时一次只走一个小版本，先备份 etcd、再升级控制面、最后逐台 drain 工作节点。把这套清单固化成文档，下一次扩容或重建时，集群就是可重复交付的，而不是一次性的手工产物。
