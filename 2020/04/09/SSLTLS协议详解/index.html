SSL/TLS 协议详解

当我们访问以 https 开头的站点时，浏览器地址栏会出现一把锁。这把锁背后是 SSL/TLS 协议族在完成密钥协商、身份认证与数据加密。本文从协议分层讲起，逐一拆解 TLS 1.2 与 TLS 1.3 的握手过程，再讨论证书、SNI、密码套件、前向保密、会话恢复与 HSTS，最后给出配置与检测建议。读者读完后应能看懂一次握手的抓包，并判断常见 TLS 故障出在哪一层。

TLS 要解决的问题

HTTP 本身是明文协议。链路上的任何一跳都能读到请求与响应，也能悄悄改写内容，还能冒充服务端与客户端通信。TLS 把这三类威胁拆成三个目标：机密性、完整性、身份认证。

机密性靠对称加密实现，双方协商出只有彼此知道的会话密钥。完整性靠消息认证码或带关联数据的认证加密（AEAD）保证，任何比特被改动都会被发现。身份认证靠证书与数字签名完成，客户端据此确认对面确实持有该域名对应的私钥。

SSL 是 TLS 的前身。SSL 3.0 在 2014 年因 POODLE 漏洞被主流浏览器禁用，RFC 7568 随后在 2015 年将其正式弃用，TLS 1.0 与 TLS 1.1 也陆续被停止支持。因此今天说“SSL 证书”“SSL 握手”，实际指的都是 TLS；协议版本应写作 TLS 1.2 或 TLS 1.3。

记录层与握手层

TLS 在结构上分为记录层与上层协议。记录层负责分片、压缩（已不推荐）、加密与完整性保护；上层包括握手协议、告警协议、变更密码规格协议与应用数据协议。

每条记录由内容类型、版本、长度与载荷组成，明文载荷上限为 16384 字节。加密之后还要加上 MAC 或 AEAD 认证标签，以及可能的填充。

握手协议携带 ClientHello、ServerHello、Certificate、Finished 等消息。告警协议只有两级：warning 与 fatal，常见的有 close_notify、handshake_failure、bad_record_mac、certificate_unknown。收到 fatal 告警后连接立即终止。应用数据协议只是把上层字节流装进记录，TLS 不关心里面是 HTTP 还是别的协议。

握手消息本身也会被切成多条记录，一条记录里也可以放多条握手消息，记录层不必理解握手语义。

TLS 1.2 握手

TLS 1.2 的完整握手需要两个往返。下面以 ECDHE 密钥交换为例，时序如下。

sequenceDiagram
    participant C as 客户端
    participant S as 服务端
    C->>S: ClientHello（版本、随机数、套件、扩展）
    S->>C: ServerHello（选定套件、随机数）
    S->>C: Certificate
    S->>C: ServerKeyExchange（ECDHE 参数与签名）
    S->>C: ServerHelloDone
    C->>S: ClientKeyExchange（客户端 ECDHE 公钥）
    C->>S: ChangeCipherSpec
    C->>S: Finished
    S->>C: ChangeCipherSpec
    S->>C: Finished

ClientHello 携带客户端支持的最高版本、32 字节随机数、会话 ID、密码套件列表、压缩方法与扩展。ServerHello 从中选定一套参数并回送自己的随机数。随后服务端发送证书链；若使用 ECDHE，还要发送 ServerKeyExchange，其中包含临时公钥与对握手转录的签名，证明这些参数确实来自证书持有者。

客户端验证证书与签名后，生成自己的临时公钥发给服务端，双方各自算出预主密钥，再结合两个随机数派生出主密钥与记录层密钥。ChangeCipherSpec 是一条分界消息，之后发送的 Finished 已经受新密钥保护。Finished 中的 verify_data 是对此前所有握手消息的摘要，任何消息被篡改都会导致校验失败。

RSA 密钥交换则不同：客户端直接用证书公钥加密预主密钥，服务端用私钥解密，不需要 ServerKeyExchange。它的代价是服务端长期私钥一旦泄露，攻击者可以解密此前录下的全部流量，这正是后面前向保密要解决的问题。

TLS 1.3 握手

TLS 1.3 把完整握手压缩到一个往返。客户端在 ClientHello 里直接带上密钥共享（key_share），服务端选定参数后，可以在同一趟里发出 ServerHello、EncryptedExtensions、Certificate、CertificateVerify 与 Finished。客户端验证完即可发送加密的应用数据，延迟明显下降。

sequenceDiagram
    participant C as 客户端
    participant S as 服务端
    C->>S: ClientHello（key_share、签名算法、套件）
    S->>C: ServerHello（选定 key_share）
    S->>C: EncryptedExtensions、Certificate、CertificateVerify
    S->>C: Finished（此后全部加密）
    C->>S: Finished
    C->>S: 应用数据

TLS 1.3 只保留 ECDHE 与 DHE 密钥交换，移除了 RSA 密钥交换与静态 DH。所有握手消息在 ServerHello 之后都受加密保护，证书不再明文可见。密钥派生改用 HKDF，按早期密钥、握手密钥、主密钥逐层分离，不同阶段使用不同密钥，某一阶段的密钥泄露不会波及其他阶段。同时被移除的还有 CBC 模式、RC4、压缩与重协商。

当客户端 key_share 中的群与服务端支持的交集为空时，服务端回一条 HelloRetryRequest，要求客户端换一个群重发 ClientHello，这多花一个往返。

0-RTT 是 TLS 1.3 的另一项能力：客户端用上次会话恢复的 PSK，在第一个飞行里就发送早期数据。问题在于这些数据没有新鲜随机数参与，攻击者可以截获并重放。因此只有幂等请求才适合走 0-RTT，服务端也应对早期数据做限流与去重，涉及下单、转账的接口必须禁用。

证书与证书链

证书是 TLS 身份认证的载体，格式由 X.509 定义。一张证书包含版本、序列号、签名算法、颁发者、有效期、主体、主体公钥，以及若干扩展。扩展里最关键的是主体备用名称（SAN），现代客户端主要以 SAN 为准，通用名称（CN）早已退居其次。此外还有基本约束、密钥用途、扩展密钥用途、CRL 分发点与颁发机构信息访问等字段。

证书链通常分三层：站点证书（叶证书）、一个或多个中间 CA、根 CA。根证书预置在操作系统或浏览器的信任库中，中间证书由上层签发，叶证书由中间证书签发。验证时客户端从叶证书一路向上验签，直到命中受信任的根。中间证书一般随握手一起下发，根证书不下发。

主机名校验要求证书 SAN 中存在与访问域名匹配的条目。通配符只能覆盖最左一级，例如 *.example.com 匹配 www.example.com，却不匹配 a.b.example.com。有效期校验依赖本机时钟，时钟漂移会让证书看似“尚未生效”。

吊销有两条路径：下载 CRL 列表，或通过 OCSP 实时查询。CRL 体积大且更新滞后，OCSP 又带来隐私与可用性问题，很多实现采用软失败，查询不到就放行。OCSP stapling 由服务端代取响应并随握手附上，兼顾性能与隐私，但仍不是所有部署都开启。证书透明度（CT）把证书写入公开日志，域名所有者可借此发现误签，本文只作概念介绍。

最常见的证书故障是链不完整：服务端只发叶证书，漏掉中间证书。桌面浏览器会尝试按 AIA 地址补全，所以看起来正常；而 Java、curl 或移动端往往直接报错。排查时应直接查看服务端下发的证书列表，而不是只看浏览器是否显示锁。

SNI

一个 IP 地址常常承载多个 HTTPS 站点，服务端必须在握手早期就知道客户端要访问哪个域名，才能选出对应证书。TLS 的解决办法是 SNI 扩展：客户端在 ClientHello 中带上目标主机名，服务端据此选择证书与虚拟主机。若不支持或未携带 SNI，服务端只能返回默认证书，客户端便会遇到主机名不匹配。

SNI 的代价是明文传输。ClientHello 尚未加密，路径上的观察者可以直接看到用户访问的域名，这在一定程度上削弱了 HTTPS 的隐私属性。加密 SNI 的后续提案当时仍处于讨论阶段，本文不展开。

密码套件

TLS 1.2 的套件名称把算法组合写在一起，例如 TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256，依次表示密钥交换用 ECDHE、认证用 RSA 签名、对称加密用 128 位 AES-GCM、PRF 用 SHA-256。TLS 1.3 的命名简化为 TLS_AES_128_GCM_SHA256，只描述 AEAD 与哈希，密钥交换与签名算法改在扩展中单独协商。

AEAD 把加密与认证合成一个原语，密文与认证标签一起产生，接收方一次校验。相比先加密再算 MAC 的组合，AEAD 不易误用，也避开了填充预言一类攻击。AES-GCM 在有硬件指令时吞吐很好，ChaCha20-Poly1305 则在缺少 AES 加速的移动设备上更有优势。两者都是当前推荐选择，CBC 模式、RC4、3DES 与导出级套件应尽早淘汰。

套件优先级通常由服务端决定，思路是先限定 AEAD，再要求 ECDHE，最后按密钥长度与性能排序。把弱套件留在列表末尾并不安全，因为客户端可以只提供弱套件，服务端仍会接受。

前向保密

前向保密指长期密钥泄露后，攻击者仍然无法解密此前录制的会话。静态 RSA 密钥交换做不到这一点：预主密钥被证书公钥加密后送上链路，谁拿到服务端私钥，谁就能把历史流量逐一解开。

ECDHE 每次连接都生成一对临时密钥，长期私钥只用于对临时参数签名，不参与密钥派生。会话结束临时私钥即被丢弃，因此事后拿到证书私钥也无济于事。部署时应确认整条链路都启用了 ECDHE 套件，同时别忘了轮换会话票据的加密密钥，否则攻击者仍可能从票据入手恢复会话。

会话恢复

完整握手开销不小。TLS 1.2 提供两种恢复方式：Session ID 由服务端保存会话状态，客户端在 ClientHello 中带上 ID，命中则走简短的恢复握手，缺点是占用内存且多机部署需要共享状态；Session Ticket 把状态加密后交给客户端保管（RFC 5077），服务端只保存票据密钥，扩展性更好，但密钥轮换同样不能省。

TLS 1.3 统一使用 PSK：服务端在握手后下发 NewSessionTicket，客户端下次用票据派生的 PSK 恢复。推荐同时携带 key_share，把 PSK 与 ECDHE 结合，兼顾效率与前向保密。恢复省去了证书验证，风险边界也随之变化：票据被盗即可冒充会话，0-RTT 还额外引入重放，因此票据应设置较短有效期并支持吊销。

HSTS

HSTS 通过响应头 Strict-Transport-Security 告诉浏览器：在 max-age 秒内访问本站一律使用 HTTPS。常见取值是一年，加上 includeSubDomains 后对所有子域生效。浏览器收到后会把域名记入本地列表，之后即使用户输入 http，也会在发请求前改写为 https，避免后续明文请求被劫持。

该响应头只在 HTTPS 响应中生效，HTTP 响应里的声明会被忽略。max-age 可以逐步调大，设为 0 表示撤销。preload 是把域名写进浏览器内置列表，让首次访问也受保护，但申请容易、移除缓慢，子域若还有纯 HTTP 服务会立刻不可用。

HSTS 不能替代正确证书。它只负责把请求导向 HTTPS，证书无效时浏览器仍会拦截；配置之前必须确保证书链、主机名与有效期都没有问题。

常见错误配置

第一类是协议版本过旧，TLS 1.0 与 1.1 仍在监听，给降级攻击留下空间。第二类是弱套件，RC4、3DES、CBC 甚至空加密没有关闭，扫描器一抓就是一片。第三类是证书过期或链不完整，前者多为续期流程缺失，后者常因只部署了叶证书。

主机名不匹配多发生在证书更换或新增域名之后。混合内容包括页面里的 http 图片、脚本与样式，主动内容会被拦截，被动内容只给警告，容易在测试环境被忽略。HSTS 配置过早也是典型事故：子域尚未全量支持 HTTPS 就加了 includeSubDomains，用户会被锁在打不开的站点之外。此外，重协商、TLS 压缩与票据密钥轮换也常被遗忘。

检测与验证

命令行最直接的入口是 openssl s_client。加上 -servername 才会触发 SNI，加上 -showcerts 能看到服务端实际下发的整条链，-tls1_2 或 -tls1_3 可以限定版本。

在线评估工具能汇总协议版本、套件、证书链与 HSTS 配置，适合上线前自查。使用时要注意隐私：工具会看到域名与证书，内部系统与未公开域名不应提交。协议与套件扫描只应在授权范围内进行，nmap 的 ssl-enum-ciphers 脚本或 testssl.sh 都能完成这类检查。

选型建议

新部署应优先启用 TLS 1.3，同时保留 TLS 1.2 作为兼容回退，并只保留 ECDHE 加 AEAD 的套件。默认关闭重协商、TLS 压缩与 0-RTT，按业务需要逐项放开。证书尽量自动化签发与续期，缩短有效期，配合到期监控，避免人工遗漏。

对外服务还应统一跳转、补齐中间证书、开启 OCSP stapling，并在确认全站支持后再上 HSTS 与 preload。把这些检查写进发布流程，比事后排查便宜得多。

小结

TLS 用记录层承载加密与完整性，用握手层完成认证与密钥协商。TLS 1.2 靠两个往返与显式套件组合工作，TLS 1.3 把它压缩到一个往返，移除了静态密钥交换并强化了密钥分离。证书链、SNI、前向保密、会话恢复与 HSTS 各自解决一个具体问题，也各有边界与风险。配置时优先新版本、强套件与完整证书链，再用工具定期验证，才能让那把锁真正可靠。
