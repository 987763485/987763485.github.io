Go 内存模型与 happens-before

本文属于《Go 语言与工程》第 43/78 篇
上一篇系列目录下一篇

并发程序最难的部分不是把任务拆开，而是判断一个 goroutine 写入的值，另一个 goroutine 什么时候一定能看到。本文以 Go 1.13 的内存模型为准，讲清楚 happens-before 这套推理工具，逐条拆解 goroutine、channel、锁、Once 与 atomic 的同步语义，再讨论 data race 与 -race 检测器的能力边界，最后用几道推理题把规则实际用一遍。适合已经能写 goroutine 和 channel、但对自己写的并发代码心里没底的读者。

为什么需要内存模型

直觉上，代码按从上到下的顺序执行，写在前面的赋值一定先发生。单 goroutine 里这个直觉基本够用，一旦引入并发就不成立了。编译器可能把两个互不相关的赋值调换顺序，CPU 可能把写操作放进 store buffer 延迟提交，每个核的缓存也可能让另一个核迟迟看不到更新。源码里的先后顺序，和另一个 goroutine 观察到的顺序，是两件事。

不同硬件的宽松程度并不一样。x86 是较强的内存模型，普通读写基本保持顺序，但 store buffer 仍会让写延迟可见；ARM 与 POWER 允许更多重排。Go 要在这两类机器上给出一致的行为，就不能把某一种硬件的细节写进语言规范，于是有了内存模型：它不描述硬件怎么做，只规定程序员在什么条件下可以依赖什么。

Go 1.13 的内存模型文档开头有一句著名的劝告：如果你必须读完这份文档才能理解程序的行为，那你想得太多了，不要耍小聪明。这句话的意思是，内存模型是最后的裁判，不是日常写代码的常用工具。绝大多数并发代码应该用少数几种清晰的同步方式组织，让可见性成为结构自带的性质，而不是靠背规则拼出来。

所以内存模型解决的不是性能问题，而是正确性问题。它回答的是：这段代码在任何符合规范的实现上，是否都只有一个可接受的结果。后面所有规则，都是围绕这个问题展开的。

happens-before：一种偏序关系

Go 的内存模型用 happens-before 描述可见性。它的定义并不神秘，只有两个来源：同一 goroutine 内按程序顺序，以及若干条同步规则给出的边；再把这两类边做传递闭包，就得到完整的 happens-before 关系。

记作 e1 → e2，读作 e1 happens-before e2。它的含义是：如果 e1 排在 e2 之前，那么 e2 以及 e2 之后的操作，一定能看到 e1 的效果。注意这里的“看到”是针对内存的，并不是说 e1 的机器指令一定先执行完。

这个关系是偏序，不是全序。任意两个事件，可能 e1 排在 e2 之前，可能 e2 排在 e1 之前，也可能两者都不成立。第三种情况称为并发。并发在这里不代表同时执行，只代表没有先后保证。两个 goroutine 各写一个变量，这两次写多半就是并发的，哪怕实际执行时间相差几毫秒。

happens-before 也不是墙上时钟的先后。先 sleep 一秒钟再执行 B，只能说明 B 开始得晚，不能说明之前的写对 B 可见；反过来，两个事件在物理时间上相隔很远，只要没有同步边，它们仍然是并发的。这一点是理解后面所有例子的前提。

那么，怎样用这套关系推理“读到的值是否一定可见”？要保证读 r 一定看到写 w 写入的值，需要两条：w happens-before r；其他所有对同一变量的写，要么 happens-before w，要么排在 r 之后。换句话说，w 必须是 r 唯一被允许观察到的写。只要存在一个既不在 w 之前、也不在 r 之后的写，r 读到哪个值就没有保证，程序里也就出现了 data race。反过来说，非原子读即使读到了某个写的新值，也不能凭这一点认定两者之间建立了 happens-before；同步边必须由同步操作建立，而不能由“我看到了结果”倒推。原子操作是例外，后文会讲。

初始化与 goroutine 生命周期

在同一个 goroutine 内，程序顺序就是 happens-before。编译器可以重排指令，但必须保证单线程语义不变，所以从内存模型的角度，前一条语句的写对后一条语句的读永远可见。这条规则看似平凡，却是所有推理的起点：先在一个 goroutine 内建立局部顺序，再通过同步点把它和别的 goroutine 连起来。

包初始化

包初始化提供了程序启动阶段的一组顺序保证。Go 1.13 的规则是：如果包 p 导入了包 q，q 的所有 init 函数完成后，p 的 init 才开始；包级变量按依赖关系初始化，全部变量初始化完成后才执行 init 函数；所有 init 结束后，main.main 才开始。把这些串起来，任何 init 函数以及 main 的第一条语句，都能看到此前所有初始化写入的值。

这解释了一个常见做法为什么安全：把只读配置放在包级变量里，在 init 中加载，之后所有 goroutine 直接读，不需要加锁。前提是这些变量在初始化完成后不再被修改。一旦有人在运行期改写它们，读的一方就必须用同步手段，初始化阶段建立的顺序帮不上忙。

还有一个容易被忽略的边界：init 里启动的 goroutine 不会被自动等待。go 语句只保证新 goroutine 的开始排在语句之后，不保证它在 init 返回前完成。如果这个后台 goroutine 负责填充某个全局缓存，main 里直接使用就可能读到零值。要么在 init 里同步等待它完成第一轮初始化，要么把初始化挪到 sync.Once 里按需执行。

还要区分“等待完成”和“传递结果”。Wait 保证你能看到结果，但如果多个 goroutine 同时往一个 slice 里 append，即使最后 Wait 了，append 之间的竞争依然存在。WaitGroup 只负责结束点的同步，不负责结果汇总过程中的互斥。

channel：通信即同步

channel 是 Go 内存模型里规则最完整的一部分。Go 1.13 的文档给出四条：

  1. 对 channel 的发送，happens-before 对应的接收完成。
  2. channel 关闭，happens-before 因关闭而读到零值的接收。
  3. 无缓冲 channel 的接收，happens-before 对应的发送完成。
  4. 容量为 C 的缓冲 channel，第 k 次接收 happens-before 第 k + C 次发送完成。

第一条是最常用的。所谓“接收完成”，指接收操作真正拿到值并返回，而不是开始等待。发送可能阻塞，但一旦对应的接收完成，发送方在发送之前的所有写，对接收方后续代码都可见：

无缓冲 channel 多一条反向规则：接收 happens-before 发送完成。因为无缓冲发送必须等到接收方接手才能返回，两者在 channel 上会合，两个方向都成立。这也是“交接”语义的来源：发送返回时，值已经在对方手里。

关闭的规则常被用来做广播。关闭一个 channel 后，接收方会先把缓冲区里剩下的值取完，之后再接收就会立即得到零值；因关闭而返回零值的那次接收，能看到 close 之前的写：

channel 的价值在于它同时承担通信和同步。哪怕传的是一个空结构体，接收方也知道发送方在发送之前的准备工作已经完成。很多信号 channel 正是利用这一点：值是什么不重要，同步边才是重点。

但不要过度延伸。channel 只对“对应的发送与接收”建立顺序，不负责给整个程序排一个全局顺序。两个 goroutine 各自往同一个 channel 发送，谁先谁后没有保证；跨多个 channel 的操作，也不会自动串成一条链。

锁：Unlock 与后续 Lock 之间

sync.Mutex 的规则很简洁：对同一个锁 l，若 n 小于 m，则第 n 次 Unlock happens-before 第 m 次 Lock 返回。注意是 Lock 返回，不是 Lock 调用。Lock 可能阻塞，返回时说明前一个临界区已经结束。

这条规则把临界区串成了链：临界区 A 里的写，在 Unlock 时发布；下一个 Lock 返回的 goroutine 拿到锁，也就拿到了这些写。临界区之间互斥，前一个临界区的所有效果对后一个临界区可见。

RWMutex 有两条对应的规则。写锁的 Unlock happens-before 后续 Lock 或 RLock 返回；每一次 RLock 返回，都排在此前某次 Unlock 之后，而本次 RUnlock 又排在后续 Lock 之前。读锁之间可以并发，所以两个读者之间没有先后保证，它们看到的都是写者释放锁时的状态。

更重要的是理解锁保护的对象。锁保护的是一段访问约定，不是变量本身。变量不会因为曾经在锁里被写过就自动获得保护；如果另一个 goroutine 在锁外读它，照样是 data race。下面这段代码的读操作看起来“在锁的保护范围内”，其实保护的字段和读的字段并不是同一组：

还有两个工程细节。第一，Mutex 一旦使用就不能复制，复制会把锁的状态拆成两份，两个副本互不排斥；go vet 的 copylocks 检查能发现大部分这类问题。第二，锁的粒度要覆盖不变量。如果两个字段必须一起变化，就必须在同一临界区里改完，否则别人可能看到只改了一半的中间状态。

Once 与 atomic：轻量同步

sync.Once：一次执行，所有等待者可见

sync.Once 的同步规则是：某次 Do(f) 中 f 的完成，happens-before 任意一次 Do 的返回。这里说的是任意一次，包括没有执行 f、只是在门口等待的那次。因此第一个调用者初始化出来的数据，后续所有调用者返回后都能看到。

这条规则让 Once 成为并发初始化的标准工具：懒加载配置、注册回调、建立连接池，都可以放在 f 里，调用方不必再加锁，也不必判断“有没有初始化好”。f 内部如果发生 panic，第一次调用会把 panic 抛给调用者，Once 则把这次执行视为已结束，后续调用不再执行 f，这个行为在写库代码时要想清楚。

用法在《Go 单例模式与 sync.Once》里已经拆过，这里只强调它与内存模型的关系：Once 不只是“只执行一次”的计数器，它还是一道发布屏障。f 里的写通过 Once 的内部状态发布给所有等待者，这正是单例可以安全共享的原因。

sync/atomic：单字操作的可见性

Go 1.13 的 sync/atomic 提供的是一组函数：AddInt64、LoadInt64、StoreInt64、CompareAndSwapInt64，以及对应的 32 位和指针版本。内存模型对它们的说法是：如果原子操作 A 的效果被原子操作 B 观察到，那么 A happens-before B；并且程序中所有原子操作，表现得像是按某个顺序一致的全序执行。

这句话有两层意思。第一层是可见性：一个 goroutine 用 StoreInt64 写入，另一个 goroutine 用 LoadInt64 读到了这个值，那么 Store 之前的普通写对 Load 之后的代码可见。这就是所谓的发布与订阅，Load 与 Store 必须配对使用，缺一不可。

第二层是顺序：原子操作之间不会出现部分可见的中间状态，所有 goroutine 对同一批原子操作看到的顺序是一致的。这让 atomic 适合做计数器、标志位和轻量的状态机。

但 atomic 只保证单个操作的原子性，不保证复合操作。两次 AddInt64 之间，别的 goroutine 可以插进来；一个 Load 加一个 Store 更不是事务。用两个 atomic 变量分别表示“余额”和“流水”，读者可能看到余额已扣、流水未记的中间态。遇到需要一起变化的字段，应该用一把锁把整组更新包起来，而不是给每个字段配一个原子变量。

还有一个 32 位平台上的坑：对 int64 的原子操作要求地址 64 位对齐。在 ARM、x86-32 等平台上，如果 int64 字段排在结构体中间，可能只有 4 字节对齐，原子操作会 panic 或失去原子性。把字段放在结构体第一个，或者显式补足对齐，是当年的常见做法。

data race 与 -race

data race：定义与后果

data race 的定义有三个条件：两个 goroutine 访问同一个变量；至少有一次是写；两次访问之间没有 happens-before 关系。三个条件同时满足才算，缺一不可。全是读的并发访问是安全的，有同步边的读写也是安全的。原子操作是另一条例外：如果所有访问都是原子操作，就不构成 data race；不过，原子访问与非原子访问混用，仍然构成竞争。

注意“并发”在这里是内存模型意义下的并发，即两次访问不可比较，而不是物理时间上重叠。两个 goroutine 分别在不同核上同时执行固然是并发，一个先执行完、另一个后执行但两者之间没有同步边，同样是并发。

data race 和逻辑上的 race condition 不是一回事。前者是内存安全问题，后者是业务语义问题。一个程序可以没有任何 data race，却仍然有 race condition：比如“先查库存再扣减”分成两个临界区，每次访问都加了锁，但两个请求之间仍然可能超卖。反过来，有 data race 的程序不一定立刻表现出错误，它可能在你演示时一切正常，在生产环境的高并发下崩溃。

后果为什么要说得这么重？因为 Go 的内存模型没有为有竞争的访问规定任何行为。实践中可能读到旧值，可能读到写了一半的值，32 位平台上的 int64 可能出现高低位来自两次写的撕裂，map 的并发读写会触发运行时的 fatal error，interface 的两个字段也可能来自不同的赋值。运行时能检测到的只是其中一部分，检测不到的部分不会给你任何提示。

所以正确的态度不是“跑起来没坏就算对”，而是“有竞争就是错”，哪怕它今天恰好工作。

-race：动态检测器的能与不能

Go 的 race detector 基于 ThreadSanitizer，是一个动态分析工具。它在编译时插入检查代码，运行时为每个内存位置维护影子状态，并用向量时钟记录访问之间的先后关系。当两次访问满足 data race 的三个条件时，它打印报告，指出两处访问的调用栈。

使用成本要先说清楚。官方文档给出的经验值是内存占用增加 5 到 10 倍，执行时间增加 2 到 20 倍，所以它适合测试和预发环境，不适合长期开着跑生产。常用命令是 go test -race ./...、go run -race main.go、go build -race；在 CI 里应该作为独立的任务，而不是本地偶尔想起来才跑一次。

几个配置项值得记住。GORACE 环境变量可以传参，halt_on_error=1 让检测到竞争时立即退出，方便 CI 快速失败；log_path 把报告写到文件；history_size 影响能回溯多长的历史。另外，race detector 依赖 cgo，CI 镜像里如果设了 CGO_ENABLED=0，-race 会直接构建失败，这是流水线上常见的第一道坎。

它的边界同样重要。第一，动态检测只看这次运行真正发生的访问；没走到的分支、没调度的交错，它看不见。第二，它不理解自定义的同步方式，比如汇编、cgo 回调、mmap 共享内存，这些场景可能报出看起来像误报的竞争，实际是检测器缺少语义信息。第三，它只找 data race，不找死锁、goroutine 泄漏、逻辑竞态。因此，-race 通过只能说明这次运行没有发现内存竞争，不能证明程序没有并发 bug。

实践中的组合是：用 -race 跑单元测试和集成测试，用压力测试制造更多交错，用代码评审检查同步约定，三者缺一不可。

错误模式与正确模式

常见错误

第一类是用 time.Sleep 代替同步。sleep 只改变时间，不建立 happens-before。它在测试里常常“有效”，因为调度恰好按预期发生；一旦机器负载变化、GOMAXPROCS 调整，问题就复现。凡是需要等待另一个 goroutine 的结果，就应该用 channel、WaitGroup 或显式的条件变量，而不是猜一个足够长的睡眠时间。

第二类是共享 map 不加锁。map 的并发读写是未定义行为，运行时会检测到并抛出 fatal error，但这个检测不是语言保证，不能当成安全网。多个 goroutine 读写同一个 map，必须用 Mutex 或 RWMutex 保护；如果读多写少，也可以用 sync.Map，但要先确认它的适用场景。

第三类是双重检查锁定写错。很多人从其他语言搬来这个模式：

外层的读没有同步，和 loadConfig 之后的写构成 data race；即使侥幸读到非 nil，也不能保证 loadConfig 里对其他字段的写已经可见。Go 里的正解是 sync.Once，或者干脆在 init 里初始化。不要为了省一次锁去挑战内存模型，那点开销通常不值得。

第四类是在 goroutine 里捕获循环变量。for range 的循环变量在 Go 1.13 中只有一份，多个闭包共享它，goroutine 真正执行时循环往往已经结束。这个问题在《Go 中 for range 的变量语义》里有完整分析，修法是循环体内 v := v 或把值作为参数传入。

第五类是用 atomic 标志位传递多个字段。比如写者先改 a、再改 b，最后把 flag 置 1；读者看到 flag 为 1 就认为 a、b 都就绪。如果只有一个写者，且写者之后不再修改 a、b，这个发布模式是成立的；但只要有第二个写者，或者写者在置位后继续修改字段，读者就可能读到新旧混合的状态。标志位只能表达一个比特的信息，表达不了“这一组字段是一个整体”。

正确模式：让可见性由结构保证

第一种是 channel 传递所有权。数据在一个时刻只归一个 goroutine 所有，交接通过 channel 完成，交接之后发送方不再碰它。这样根本不需要锁，也不存在并发访问：

这段代码里，r 的字段在 worker 中被改写，但同一时刻只有一个 goroutine 持有它，所以没有竞争。发送之后，worker 不再引用 r，所有权转移给下游。

第二种是 mutex 保护临界区。把不变量涉及的字段放在同一把锁下，进入临界区先 Lock，离开时 Unlock，所有访问路径无一例外。临界区尽量短，但不要短到破坏不变量；把 I/O、远程调用放在锁外，避免锁被慢操作拖住。

第三种是 Once 做初始化。凡是“只做一次、之后只读”的构造，都适合放进 Once；它同时解决重复执行和发布可见性两个问题。第四种是 WaitGroup 等待完成。主 goroutine 负责 Add，工作 goroutine 负责 Done，Wait 返回后统一读取结果。需要注意的是，Add 要在启动 goroutine 之前完成，结果汇总如果涉及并发写，仍要另加锁或改用 channel 收集。

这四种模式的共同点是：同步方式与数据流一致。所有权转移用 channel，共享状态用锁，一次性构造用 Once，生命周期用 WaitGroup。选对了结构，内存模型的规则就不需要逐条背，它们已经隐含在结构里。

推理练习

规则讲完了，最重要的是会用。下面三道题，建议先自己判断，再看分析。

第一题：

第二题：

这里 x 一定有保证，y 没有。x = 1 在发送之前，发送 happens-before 接收完成，接收又在打印之前，传递起来就是 x = 1 happens-before 打印，所以 x 一定输出 1。y = 2 排在发送之后，它与接收、与打印之间都没有同步边，打印时可能看到 2，也可能看到 0，并且这是一处 data race。同一段 goroutine 里的两次写，命运的差别只在于它们位于同步点的哪一侧。

第三题：

write 对 data 的写在锁内，read 对 data 的读也在锁内，这部分是安全的。但 count++ 在锁外，read 却在锁内读 count，锁并没有覆盖 count 的写，所以仍然存在 data race。这个例子说明：锁保护的不是“临界区里的所有变量”，而是“所有访问都遵守同一把锁的变量”。只要有一条访问路径漏掉锁，保护就失效。修法是把 count++ 移进临界区，或者给 count 单独设计一条同步路径。

如果三道题都能不假思索地答对，说明已经开始用 happens-before 而不是用运行结果来判断并发代码了。

小结

内存模型是一套推理工具，不是运行时开关。它用 happens-before 把“我看到了你的写”变成可以证明的命题：同一 goroutine 内按程序顺序，跨 goroutine 靠 go 语句、channel、锁、Once 和 atomic 建立同步边，再沿传递闭包推导。没有同步边的访问就是并发的，并发的读写就是 data race。

工程上的建议可以归结为几条：优先用 channel 传递所有权，用 Mutex 保护共享状态，用 Once 做一次性初始化，用 WaitGroup 管理生命周期；不要用 sleep 猜时序，不要让锁的保护范围出现缺口，不要用 atomic 拼接多个字段。把 -race 放进 CI，把它当作发现问题的探照灯，而不是证明正确的证书。真正让并发程序可靠的，是清晰的同步结构，加上对每一条可见性边界的自觉。
