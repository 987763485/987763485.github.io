GORM 事务与钩子实践

本文属于《Go 语言与工程》第 75/78 篇
上一篇系列目录下一篇

事务边界画错，代码平时能跑，一出错就留下半条数据；Hook 写得顺手，排查时却常常忘了它也在事务里。本文基于 GORM 1.x（github.com/jinzhu/gorm），从业务用例的事务边界讲到手动事务、回调事务、保存点、隔离级别与死锁重试，再拆开 Hook 的生命周期、批量行为、与事务的关系，最后讨论提交后动作、幂等、测试和常见坑。读者应已能用 GORM 完成基本 CRUD，本文不重复模型与关联查询。

事务边界：一个用例，一个事务

事务的边界应当由业务用例决定，而不是由单条 SQL 或整个 HTTP 请求决定。下单要同时写订单、扣库存、记流水，这三步必须同生共死，就把它们放进一个事务；下单之前的参数校验、之后的发短信，都不该在事务里。边界过大，锁持有时间长、连接被占；边界过小，两次写之间失败，数据只改一半。

边界应该放在 service 层。repository 只负责“用给定的连接执行一条语句”，不自己调用 Begin。若每个 repository 方法各自开事务，service 组合两个方法时就是两个独立事务，前一个已经提交，后一个失败也回滚不了前者。正确做法是 service 开启事务，把 tx 作为参数传给 repository，让它们在同一条连接上工作。

事务要尽量短。开事务之前把能准备的都准备好：参数、价格、风控结果；事务里只留必须原子化的写。不要在事务里调用外部 HTTP 接口、发消息、渲染模板或等待用户输入。长事务除了锁住行，还会让 InnoDB 的 undo 日志膨胀，拖慢 purge。读操作能提前就提前，只有“读到之后必须立刻锁住”的校验才放进事务。

手动事务：Begin、Commit、Rollback

最直白的写法是手动控制三个动作。db.Begin() 返回一个新的 *gorm.DB，开启失败时错误放在 tx.Error 里，此时不能继续使用。之后每条语句都要检查错误并决定回滚。Commit 与 Rollback 本身也返回 *gorm.DB，提交失败同样要处理。

这段辅助函数把回滚收进 defer：正常返回但没提交、执行中出错、发生 panic，三条路径都会回滚。committed 标志是为了避免对已提交的事务再调 Rollback；1.x 虽会忽略 sql.ErrTxDone，显式区分仍更清楚。panic 分支先回滚再把 panic 抛回去，不能让 recover 吞掉它。若不想自己维护标志，1.x 提供了 RollbackUnlessCommitted，直接 defer tx.RollbackUnlessCommitted() 也能覆盖大多数场景。

Begin 失败后不要再执行语句；Commit 失败要按失败处理并记录日志。

db.Transaction：把提交与回滚交给回调

更推荐的是回调形式。把事务体写成一个返回 error 的函数，返回 nil 就提交，返回非 nil 就回滚。省掉了每条错误分支上的 Rollback，也避免了漏写。

1.x 的实现里，回调返回错误后不会再提交；如果 Commit 本身失败，延迟函数仍会尝试回滚。回调里发生 panic 时，它不会替你 recover：延迟函数先回滚，panic 继续向上抛，最终由中间件或任务框架的恢复逻辑接住。所以 panic 不会留下悬挂事务，但会让当前请求失败，日志里要能看到堆栈。

嵌套调用要特别小心。1.x 没有真正的嵌套事务：在事务上再调用 Transaction，内层 Begin 拿不到新事务，只会记下错误。内层无论提交还是回滚，作用到的都是外层连接：回调吞掉错误，外层就被提前提交；回调把错误抛出来，外层则被一起回滚。若外层再提交，往往得到“事务已完成”的错误，看起来像提交失败，实际早已落库或回滚。解决办法很简单：事务只在外层开一次，内层函数一律接收 tx；确实需要分段回滚，用下一节的保存点。

SavePoint：部分回滚，不是独立事务

保存点是 SQL 标准里的概念，MySQL InnoDB 支持。它在一个已经开启的事务里打一个标记，之后可以只撤销标记之后的语句，事务本身仍然存活。GORM 1.x 没有封装 SavePoint 与 RollbackTo 方法，直接写 tx.SavePoint("sp1") 会编译失败，要用 Exec 执行原生 SQL。

保存点适合“主流程必须成功，附加动作失败可以降级”的场景，比如下单送赠品：订单写入失败要整体回滚，赠品库存不足只撤销赠品，订单照常提交。要注意三点。第一，ROLLBACK TO SAVEPOINT 之后事务还在，必须继续走到 Commit 或 Rollback，否则连接一直被占着。第二，它不释放保存点之后拿到的行锁，锁要等整个事务结束才归还，别指望靠它缩短锁持有时间。第三，保存点不是独立事务，不能跨连接，也不能在保存点里再开一个事务。

隔离级别与锁：从 REPEATABLE READ 说起

MySQL InnoDB 的默认隔离级别是 REPEATABLE READ。事务里第一次一致性读会建立快照，之后的普通查询都读这个快照，所以同一事务内多次查询结果一致。FOR UPDATE 属于当前读，读最新已提交的数据并加排他锁；在 REPEATABLE READ 下，范围条件还会加间隙锁，用来看住不存在的行。间隙锁减少幻读，也让并发插入更容易互相等待。

GORM 1.x 的 Begin() 使用数据库默认级别。要显式指定，可以用 BeginTx 传入 *sql.TxOptions，database/sql 会在该连接上设置隔离级别，再开启事务。不要在连接池上执行全局 SET，它只影响当前连接。

行锁用 Set("gorm:query_option", "FOR UPDATE") 加在查询上，且必须在事务内，否则语句执行完锁就释放了。多行加锁要按固定顺序，比如永远先锁订单再锁库存；顺序不一致，两个事务就会各持一把锁等对方。InnoDB 检测到死锁会回滚其中一个事务并返回错误码 1213，这类错误可以重试整个事务；锁等待超时返回 1205，通常说明有长事务或锁范围过大，重试往往无济于事。

重试的前提是事务体可重复执行：闭包里的参数要重新读，不能沿用上次已修改的内存对象；有副作用的操作要放在提交之后。两三次足够，频繁死锁说明锁顺序或事务太长。

BeforeSave 排在 BeforeCreate 与 BeforeUpdate 之前，适合放两种场景都要做的校验；AfterCreate 排在 AfterSave 之前，不要误以为它已经是最后一步。任何一步返回 error，后续步骤都不再执行；错误交给调用方决定提交还是回滚。Hook 里 panic 时，框架先回滚当前事务，再抛出 panic，日志里能看到 SQL 失败与业务堆栈。

删除只有 BeforeDelete 与 AfterDelete，没有 BeforeSave。软删除在 SQL 层面是 UPDATE，但走的是删除回调，同样不会触发 BeforeSave。另外，UpdateColumn 与 UpdateColumns 不触发任何 Hook，也不会自动更新 UpdatedAt，它们本来就是给“明确知道要改哪一列”的场景准备的。

Hook 里该做什么，不该做什么

Hook 适合做机械、轻量、与当前行强相关的事情：生成业务单号或 UUID、填充审计字段、计算派生字段、在同一条连接上写审计日志。这些操作要么只碰内存，要么只写当前库，失败时随业务一起回滚。

不适合放进 Hook 的是远程调用和重 IO：请求风控服务、发短信、上传对象存储、跑大查询、等待锁。Hook 在事务内执行，这些动作会把事务拉长到数百毫秒甚至数秒，连接和行锁都被占着；远程服务抖动还会让本来能成功的业务回滚。Hook 里也不要用全局 db 再发语句，那会从池里取另一条连接，看不到当前事务未提交的数据，更新同一行时还会自己等自己。

派生字段在创建时最可靠，因为 INSERT 的列值在 Hook 之后才读取。更新要小心：待更新的列在 Hook 之前就已经算好，BeforeUpdate 里再改结构体字段，未必会进入最终的 UPDATE 语句。需要强制写入时用 UpdateColumn 明确指定，或者在 service 里先算好再调用 Updates。

Hook 与批量操作

GORM 1.x 的 Create 按单个结构体拼 INSERT，传切片不会被当成批量插入。批量写入要在事务里循环调用 tx.Create(&item)，此时 Hook 对每条记录各触发一次，单号、时间戳、审计字段都能逐条填好。循环要控制批次大小，几千条一个事务同样会长时间持锁。

批量更新是另一种情况。db.Model(&Order{}).Where("status = ?", "created").Updates(map[string]interface{}{"status": "closed"}) 只会在传入的 Model 实例上触发一次 Hook，而且拿不到每一行的旧值；如果 Hook 里根据旧状态做判断，读到的是零值。UpdateColumn 与 UpdateColumns 直接跳过 Hook 和 UpdatedAt，适合“把一批数据推到某个确定状态”的运维操作，代价是审计字段要自己补。

取舍的标准是：需要逐行不变式、逐行审计，就循环加 Hook，并接受更大的事务；只是批量改状态，就用 UpdateColumn 配一条单独的审计记录，再用 RowsAffected 核对影响行数。不要一边用批量更新追求速度，一边指望 Hook 像单行更新那样工作。

Hook 与事务：提交后动作的边界

Hook 和业务 SQL 跑在同一条连接、同一个事务里。AfterCreate 执行时，INSERT 已经发出，但事务还没有提交；此时用 scope.DB() 写一条流水，流水与订单同生共死，这是 Hook 的正确用法。反过来，Hook 返回错误后调用方必须把错误继续往上抛，不能记个日志就返回 nil，否则外层事务会带着一条失败的记录提交。

把发消息、写缓存放在 AfterCreate 或 AfterSave 里，是更隐蔽的错误。消息发出时数据尚未提交，消费者可能立刻回查却查不到；提交阶段失败，消息已经发出去，成了没有对应数据的孤儿；进程在提交前崩溃，消息则彻底丢失。缓存同理，提交前写入的数据可能永远不会存在。

所以“提交后动作”要放在 Transaction 返回 nil 之后，由 service 显式执行。但仍有双写问题：数据库提交成功、消息发送失败，两边就不一致。可靠的做法是让消息与业务数据同事务落库，再由后台任务投递，也就是下一节的 outbox。

提交后动作：outbox 与幂等

outbox 的思路是把“要发什么”当成一条业务数据，和订单写在同一个事务里。表里至少有主题、载荷、状态、重试次数与下次重试时间。业务提交，消息一定在表里；业务回滚，消息一起消失。它是事务消息的朴素做法。

投递由独立进程轮询：按状态与时间取一批，锁住，逐条发送，成功后标记完成，失败则推后重试时间。MySQL 8.0 可以用 SKIP LOCKED 让多个投递者错开，5.7 没有这个语法，常用单实例加状态条件更新。投递语义是至少一次，重复不可避免。

消费端必须幂等。最省事的是唯一键：消息 ID 或业务单号建唯一索引，重复插入捕获冲突后直接返回成功；也可以用幂等表记录已处理的 ID，或用状态机做条件更新，只有状态从待支付变成已支付的那一次才算数。接口层同理：客户端带请求号，服务端在唯一索引上落库，冲突时返回已有结果；支付回调要验签、核对金额，再用条件更新推进状态，不能假设回调只来一次。

测试与常见坑

事务与 Hook 有一半行为在数据库内部，只 mock 测不出来。准备真实 MySQL，至少覆盖：提交后可见、回滚后无残留、保存点只撤销后半段、Hook 顺序、Hook 报错回滚、UpdateColumn 不触发 Hook、唯一键挡住重复请求。SQLite 启动快，适合跑 CRUD 与 Hook 顺序，但它没有 InnoDB 的行锁与间隙锁，隔离与死锁必须放到 MySQL 上测。用例之间用 TRUNCATE 清理，不要包在测试事务里：1.x 没有嵌套事务，被测代码自己 Begin 时，外层回滚撤销不了内层已提交的数据。

常见坑 后果
忘记 Rollback 连接被占住，连接池耗尽
长事务或事务里做远程调用 锁等待，undo 膨胀
事务里继续用 db 读到旧数据，或等待自己持有的锁
Hook 里用全局 db 另开连接，自我死锁
Hook 里 panic 事务回滚，请求失败
批量 Updates 指望逐行 Hook 只触发一次，且拿到零值
UpdateColumn 跳过 Hook 审计字段与更新时间丢失
嵌套 Transaction 外层被提前提交

小结

事务边界放在 service 层，一个用例一个事务，事务内只认 tx。手动事务用 defer 兜底，能写成回调就用 db.Transaction；1.x 没有嵌套事务，部分回滚要用保存点。锁的范围要小、顺序要固定，死锁只重试可重复执行的事务体。Hook 只做轻量且同库的操作，批量更新别指望逐行触发；提交后动作交给 outbox，消费端与接口都做幂等。守住边界，ORM 的便利才不会变成半夜的故障。
