Go 实现接口限流

本文属于《Go 语言与工程》第 76/78 篇
上一篇系列目录下一篇

接口处理能力总有上限。流量超过上限又不加约束，结果往往不是“慢一点”，而是协程堆积、连接耗尽、数据库被打满，整条链路可能不可用。本文从要解决的问题出发，比较常见算法，再落到 Go 1.13 的单机实现与 Redis 5.0 的分布式实现，最后讨论响应约定、可观测性与常见坑。读者需了解 HTTP 与 Redis 基础。

为什么需要限流

限流首先保护自身。服务的 CPU、内存、连接和下游配额都有限，入口不设闸门，异常流量会迅速吃光资源，正常请求跟着遭殃。第二是公平：多租户系统里，单个租户的批量任务不应挤占他人份额；公众接口也要防止单个用户占满额度。第三是成本，数据库、短信、第三方 API 按量计费，限流能避免故障变成账单。

限流常和熔断、降级一起出现，但三者不同。限流在入口主动约束速率，是事前动作；熔断在调用下游连续失败时快速失败，是事中保护；降级是在资源不足时关掉非核心功能或返回兜底数据，是功能取舍。误区是过载后才想起限流，此时请求已进入进程，只能减少后续压力。合理做法是入口限流、依赖处熔断、预先写好降级。

四种常用算法

限流控制单位时间通过的请求数。算法各有侧重，选择看两点：能否容忍突发，以及实现与运维成本。

算法 核心思路 突发流量 实现复杂度 典型场景
固定窗口 每个时间窗口独立计数，超过阈值拒绝 窗口边界可能出现双倍突刺 低 简单配额
滑动窗口 统计最近一个窗口内的请求，可用时间戳日志或分桶近似 较平滑，边界突刺小 中 精确配额
令牌桶 按固定速率补令牌，桶容量决定可积累的突发量 允许不超过桶容量的突发 低到中 对外 API
漏桶 请求先入队，再以固定速率流出 削平突发，输出恒定 中 流量整形

固定窗口最易实现，一个计数器加过期时间即可，缺点是窗口切换时可能放过近两倍流量。滑动窗口用时间戳日志最准，但每个请求都要存记录，内存随量增长；分桶计数按小格加权，精度与内存平衡。令牌桶允许一定突发，适合面向用户的接口。漏桶输出平滑，通常要队列和排队超时，更适合保护怕抖动的下游。多数场景选令牌桶，Go 扩展库已提供。

令牌桶与 x/time/rate

golang.org/x/time/rate 实现的是令牌桶。rate.Limit 是 float64 类型，表示每秒补充的令牌数；Burst 是桶容量，也是单次最多能取走的令牌数。rate.NewLimiter(rate.Limit(10), 20) 表示平均每秒 10 个令牌，单次最多突发 20 个。也可用 rate.Every(200 * time.Millisecond) 表达间隔。Limit 是速率而非间隔，Burst 为 0 时任何请求都拿不到令牌。

Allow 是非阻塞判断：桶里有足够令牌就扣减并返回 true，否则立即返回 false，请求不会排队。AllowN(now, n) 用于一次消耗多个令牌的场景，例如批量接口按条数计费，Allow 等价于 AllowN(time.Now(), 1)。它适合请求路径，代价可控，不会挂起 goroutine；缺点是无法告诉调用方还要等多久，只能配合 Retry-After 或直接拒绝。被拒绝时不会扣减令牌，这在批量场景下很重要。

速率和容量要分开设定。速率对应长期平均负载，容量对应可以容忍的瞬时突发。容量过大，保护效果会被突发穿透；容量过小，正常并发加载会被误伤。常见错误是只调速率不看容量，或者把容量设成 1，把令牌桶退化成严格的间隔控制。容量应来自压测和业务峰值特征，而不是照抄配置。

Wait、Reserve 与 context

Wait 会阻塞到取到令牌或 context 结束，适合后台任务、消息消费等可排队的场景。在 HTTP 处理函数里必须给它带超时的 context，不能让请求无限等待。

Wait 的错误来源要分清：context 先结束返回 ctx.Err()；若按当前速率等到期限也拿不到令牌，会返回无法满足等待的错误。不要把错误字符串当成协议，统一按“没拿到令牌”处理，返回 429 或 503。更不要在请求路径无期限等待：Wait(r.Context()) 在客户端不断开时会一直排队，过载时只是把拒绝变成堆积，延迟飙升后仍会超时。

Reserve 和 ReserveN 适合需要自己决策的场景：返回的 Reservation 中，Delay() 表示还要等多久，OK() 表示能否在期限内满足，不想等时调用 Cancel() 归还预占令牌。例如希望“最多等 100 毫秒，否则拒绝”，用 Reserve 比 Wait 更直接。WaitN 与 AllowN 同理，按令牌数计费时不能只判断一个。

单机限流中间件

单机限流按 key 维护 limiter，key 决定限流粒度和内存开销。按 IP 用 ip: 前缀，按登录用户用 user:，按接口用路由模板而非原始 URL，避免查询参数进入 key 造成无限增长。除非策略需要联合判断，不要把多个维度拼成一个巨大的 key，分开更利于观测和调整。

map 必须加锁。rate.Limiter 自身并发安全，但“查 map、创建 limiter、更新最后访问时间”是复合操作，需要同一把锁。清理协程和请求处理也共用这把锁，删除前判断最后访问时间，避免删掉刚被访问的 limiter。

清理周期要小于业务能容忍的误差，过期阈值至少大于一次正常会话间隔。实例多、key 分散时，单个 map 的锁会成为热点，可按 key 哈希分片，各自加锁。限流应放在鉴权之后、业务之前：用户维度需要身份信息，静态资源和健康检查应放行。拒绝时写入统一的 JSON 错误体并带上 Retry-After，不要只返回空响应。

分布式限流与 Redis

单机限流只能约束一个进程。多实例部署时，每个实例各自计数，集群总速率随实例数放大，要表达全局配额必须把计数放到共享存储。Redis 5.0 是常见选择，最简单的是固定窗口计数器：INCR 原子加一，超过上限拒绝，首次计数设置过期。

INCR 和 EXPIRE 是两条命令。若进程在两者之间崩溃，key 没有 TTL，会永久累积，之后请求全被拒。把两条命令放进 Lua，Redis 单线程执行，中间不会插入其他命令，原子性就有保证。

固定窗口仍有边界问题：每分钟 100 次的配额，若在窗口末尾和下一窗口开头各用掉 100 次，跨边界短时间内实际通过 200 次，对下游就是双倍突刺。要平滑可用滑动窗口：有序集合保存时间戳，脚本先删窗口外成员，再统计并添加当前请求；它精确，但每个请求一条记录，内存与请求数成正比。分桶计数把窗口切格加权，内存固定、精度略差，是常见折中。

还要考虑 Redis 不可用的策略。限流器不能成为新故障点：调用要设超时，失败时明确放行还是拒绝。放行保护可用性，但可能把压力传给下游；拒绝更安全，却会把 Redis 抖动放大成业务不可用。读接口多选择短时放行并记录指标，支付等写接口倾向拒绝。

用 Redis 实现令牌桶

固定窗口无法表达突发容量，令牌桶可以把“令牌数 + 上次刷新时间”存成一个 Hash，脚本内按时间差补令牌、判断、扣减、写回。所有读写都在脚本里完成，避免“读、算、写”之间被并发插入。

调用方式同固定窗口：用 redis.NewScript 加载，再用 Run 传入 key 与参数。脚本用 TIME 取 Redis 时间，避免实例间时钟偏差；时钟回拨时 now < ts，把时间戳拉回当前且不补令牌，宁可短暂少发也不超发。回拨期间不补令牌，之后按正常速率继续补充，靠 NTP 纠正即可。更常见的是应用侧用本地时间限流，实例间几秒偏差就会让配额漂移。

每个请求执行 Lua 都有网络往返成本，热点 key 会成瓶颈。可在单机再做一层小配额，或预取令牌本地分配，减少 Redis 调用；代价是实例崩溃浪费预取令牌。脚本里不要做复杂计算或遍历大集合，执行期间其他命令都要等。

限流维度与分层

限流维度按业务目标选择。全局配额保护总容量；租户配额保证多租户公平；用户配额防止单人滥用；IP 配额覆盖未登录流量；接口配额保护导出、搜索、短信等高价端点。维度越多，key 基数与 Redis 成本越高，通常选两三个关键维度即可。

多层限流要明确分工。网关做粗粒度控制，如总连接数、总速率、恶意来源；服务内部做细粒度控制，如按用户、接口、业务配额。两层限制同一维度时，生效的是更严格的一层，用户可能比预期更早被拒，排查要看两层指标。配置应写清“总配额由谁负责”，避免两层各配一半却都以为对方兜底。也不要把所有维度塞进一个 key，策略无法独立调整，也看不出哪层触发；分开 key、分别判断，错误里带上维度，排障更快。

响应约定与可观测性

被限流时返回 429 Too Many Requests，这是 RFC 6585 定义的状态码。配合 Retry-After 告诉客户端多久后可重试，值可以是秒数或 HTTP 日期。限流响应还应带上 X-RateLimit-Limit、X-RateLimit-Remaining、X-RateLimit-Reset，分别表示配额、剩余量和重置时间；Reset 用 Unix 时间戳还是剩余秒数要在文档里写清。成功响应也建议带剩余量，客户端可主动减速。

剩余量可以取自 limiter 的瞬时令牌数，但它只是估计，不要承诺精确值。错误体要和全局格式统一，包含业务码、消息和请求标识，避免返回纯文本或 HTML。内部服务用 503 加 Retry-After 也可以，但同一接口要保持一致。

可观测性方面，至少记录被限流次数、按路由和维度类型的分布、限流比例、limiter 数量及 Redis 脚本延迟与错误率。按 key 做 TopN 很有用，但不要把用户 ID 直接作为监控标签，否则基数爆炸；可先在本地聚合，再上报有限分组。告警不要只看单次尖峰，而要看持续一段时间的限流比例是否超过容忍度。limiter map 的大小和堆内存也要监控，异常增长通常意味着 key 设计或清理有问题。

公平性、压测与常见坑

按 IP 限流会遇到 NAT：公司、学校、移动网络的出口 IP 后可能有大量真实用户，阈值过严会误伤整片。登录用户以用户维度为主，IP 只做宽松兜底；匿名接口可结合设备标识等信号。X-Forwarded-For 只有请求来自可信代理时才能采信，并从右往左取第一个不可信地址；服务直接暴露在公网时，该头可随意伪造，不能作为依据。登录、短信等接口还要按手机号、设备、IP 限制，配合验证码和冷却。

压测是验证限流是否生效的主要手段。用固定并发持续一段时间，统计总请求数、成功数和 429 数量，与配置的速率、容量对照；再单独测突发：先空闲让桶充满，然后瞬间打出一批请求，观察通过数量是否接近 Burst。持续速率和突发容量是两件事，只测其中一个容易得出错误结论。调参先测出下游配额内服务能承受的速率，再留余量，不要照搬网上的 QPS 数字。

常见坑还有这些：每个请求新建 limiter，等于没有限流；limiter map 只增不减，内存泄漏；调用 Wait 不处理错误，超时后继续处理；Redis key 忘记设 TTL；只限流不返回明确错误；网关和服务重复限流导致配额减半；在反向代理后用 RemoteAddr 拿到的是代理地址；把 limiter 按值复制，内部互斥锁被复制，go vet 会报 copylocks；Burst 设为 0 导致永远拒绝；Redis 调用没有超时，限流器拖垮请求链路。

小结

限流是入口处的主动保护，和熔断、降级各司其职。单机优先用 x/time/rate 的令牌桶，按 IP、用户或接口拆 key，并清理不活跃的 limiter。需要全局配额时，把计数或令牌状态放进 Redis，用 Lua 保证原子性，并处理固定窗口的边界突刺与 Redis 故障取舍。响应返回 429、Retry-After 和配额头，指标要能回答“谁被限、限了多少”。参数来自压测与业务容量，不靠拍脑袋。
