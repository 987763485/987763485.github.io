Go 实现简单爬虫

本文属于《Go 语言与工程》第 74/78 篇
上一篇系列目录下一篇

爬虫是很多人学 Go 之后写的第一个“能干点实事”的程序：几十行代码就能把网页标题抓下来。但真正决定一个爬虫是否合格的，不是它跑得多快，而是它有没有给别人添麻烦。本文用一个只采集公开内容的示例，把种子 URL、抓取、解析、去重、限速、重试和存储串成一条完整链路，代码基于 Go 1.13 与 goquery。读完后你应当能写出一个跑得住、停得下、出了问题查得到的采集程序，也知道哪些事情不该做。

六个部件与一条底线

一个爬虫拆开看只有六个部件：种子 URL 是入口；调度器决定下一个抓谁；抓取器发请求；解析器把 HTML 变成字段；去重器拦住重复地址；存储负责落盘。六者围着一个队列转，缺一个就会表现成“跑着跑着就乱了”。

flowchart TD
    A[种子 URL] --> B[去重与规范化]
    B --> C[调度队列]
    C --> D[等待限速]
    D --> E[HTTP 请求]
    E --> F[解析 HTML]
    F --> G[存储]
    F --> B
    E -->|失败| H[重试或放弃记录]

动手之前先回答两个问题：要哪几个字段，这些内容是否允许被采集。只采集公开页面，也就是不需要登录就能看到的那部分；先读网站的服务条款，明确禁止采集的就不碰；涉及个人信息、付费内容、明确声明版权限制的，一律绕开。技术上能做到，不等于可以去做，这条线要先画好。

具体一点：只抓列表页和公开详情页，不碰个人主页、联系方式、订单类页面；文章只存标题、摘要、链接和必要字段，不整站转载正文；对方在条款里写明禁止转载或禁止自动访问的，直接放弃。频率上宁慢勿快，白天高峰可以暂停，放到夜间再跑，这不是技术妥协，而是最基本的礼貌。

robots.txt 是站点留给爬虫的说明书，放在根路径下，用 User-agent、Disallow、Crawl-delay 这几个字段说明谁能抓什么。约定俗成的处理是：按 host 取一次并缓存；4xx 视为没有限制；5xx 视为暂时不允许，宁可少抓；匹配时用自己 UA 里的产品名。

把这段判断放在入队之前，而不是抓完再检查，能省下大量无用请求。Crawl-delay 不一定存在，取到 0 就用自己的默认间隔，两者取较大值。

HTTP 客户端：标识身份，划好边界

http.Client 的零值可用，但不适合爬虫：它没有超时，一个卡住的连接会把 worker 永久占住。Client.Timeout 覆盖从建连到读完 body 的全过程，必须设；再给 Transport 加 ResponseHeaderTimeout，把“连上了但不回话”的情况也圈进来。

Header 里最重要的是 User-Agent。写清楚程序名、版本和联系方式，让对方运维一眼知道这是谁、怎么联系。有人喜欢把 UA 改成浏览器，指望不被拦，这既是对服务条款的规避，也会让排障变得困难：对方看到的是一个“浏览器”在异常高频地请求。我们不做这件事。

gzip 有个容易踩的点：Transport 会在没手动设置 Accept-Encoding 时自动加上并透明解压；一旦你自己写了这个头，解压就没人管了，读到的是一堆二进制。要么交给标准库，要么自己包一层 gzip.Reader。

重定向用 CheckRedirect 限制跳数，超过就报错；Go 在跨域跳转时会自动去掉 Authorization、Cookie 这类敏感头，不用自己处理。

解析：把页面变成结构

解析交给 goquery。它在 x/net/html 之上做了一层 jQuery 风格的选择器，容错好：标签没闭合、属性没加引号，它都能建出树来。这也是不要用 encoding/xml 去解析 HTML 的原因：真实页面几乎都不是良构 XML，一遇到 <br> 就报错。

选择器从稳到脆依次是：id、带语义的 class、标签加属性、纯层级。写的时候尽量选前两种，并把选择器集中在一个函数里，站点改版时只改一处。

提取时统一做 TrimSpace，链接用 Attr 取原始值，再用 ResolveReference 转成绝对地址；文本里常有换行和不间断空格，落库前要清一遍。

编码是中文站点绕不开的：老页面用 GBK，Content-Type 里未必写对，可以看 meta charset，或者用 x/text 的 htmlindex 猜。转码用 transform.NewReader 套 simplifiedchinese.GBK.NewDecoder，读出来就是 UTF-8。

返回空结果时不要当成功，记一条告警再去人工看页面，否则站点改版后程序会安静地抓上几个小时的零条数据。

并发、限速与调度

并发不是越高越好。对同一个域名，礼貌的做法是串行或极低并发；只有面对多个域名时才值得并行。全局并发用 worker pool 控住，思路与 509 那篇一致，这里只关心它如何与限速配合。

真正容易写错的是限速器的粒度：每个 host 一个 rate.Limiter，用 mutex 保护这张 map。rate.Every(d) 表示每隔 d 放行一个令牌，burst 设为 1，两次请求就至少间隔 d。等待要用 Wait(ctx)，把 main 里的 context 一路传下来，收到中断信号时整体退出，卡在等待里的 goroutine 也能立刻返回。

调度用广度优先：种子入队，弹出后抓取、解析，把新链接的深度加一，放回队尾。深度上限和总页数上限都必须有。翻页链接最容易被无限展开，下一页永远存在，只是内容为空；判断依据可以是连续若干页没有新条目，也可以是“下一页”的 href 与当前页相同。

单域名串行加间隔，多域名各起一个队列并行，是这套结构里最稳的组合。别为了跑满带宽去堆并发，对方响应变慢时，你的重试又会放大压力。

还有两个参数值得单独留出来：时段与缓存。把抓取窗口限制在凌晨到清晨，白天不跑，对多数内容站点都更友好；已经抓过的页面在有效期内直接读本地副本，不重复请求，等于把礼貌做进了缓存层。小站尤其要保守，一台个人服务器经不起几十个并发轮番问候。

去重：从 URL 规范化开始

去重的第一道关是 URL 规范化。同一个页面可能有十几种写法：带不带 fragment、查询参数顺序不同、末尾多一个斜杠、显式写了默认端口、主机名大小写不一、被加上 utm 参数。不统一，队列里就会混进大量“新”地址，抓十遍还是同一页。

规范化之后用 map[string]struct{} 记录已见地址，读写加锁；集合只增不减，十万级规模内存完全扛得住。到百万级再换布隆过滤器：k 个哈希映射到一条位数组，空间小一个数量级，代价是假阳性，可能漏掉少量页面，对采集来说可以接受。要注意布隆过滤器不支持删除，也不该当唯一依据，通常是前面挡一层，命中后再查持久化集合。

持久化最简单的方式是追加写文件：每抓完一个 URL 追加一行，启动时读回内存。崩溃最多丢最后几行，重启会重复抓少量页面，配合幂等写入问题不大。

内存集合的容量要提前估算：一个 URL 平均一百字节，一百万条大约一百兆，加上 map 的额外开销还要再翻倍；超过这个量级就该考虑布隆过滤器加磁盘索引，而不是硬扛。

出错是常态：分类、退避、记录

一次抓取会以很多方式失败：DNS 解析不了、TLS 握手超时、对方限流、返回 502、页面结构变化、body 读到一半断掉。第一步是分类，而不是统一重试。

可以重试的是：连接超时、临时性网络错误、429、502/503/504。不该重试的是：400、401、403、404、410，以及解析失败，因为同样的页面再抓一遍也不会变。把这两类分开，重试次数才不会被浪费在注定失败的地址上。

429 和 503 常带 Retry-After，值可能是秒数，也可能是 HTTP 日期。先按整数解析，失败再试 http.ParseTime。这个头的意思是“多久以后再来”，照做即可，比任何自研算法都准。

没有这个头时用指数退避：1 秒、2 秒、4 秒，上限 30 秒，再加随机抖动，避免所有 worker 在同一秒一起重试。每个 URL 最多 3 次，超过就落一条失败记录，带上 URL、状态码、错误和时间，留给人工判断。

还要看域名级的信号：连续多个请求都失败，往往说明对方在维护，或者已经把你这台机器拦了。这时应该暂停整个域名一段时间，而不是逐个 URL 硬试。失败记录按 host 聚合，趋势比单条错误更有信息量。

本文只发 GET，所以重放是安全的；如果将来要提交表单或调用写接口，必须先确认对方幂等，再决定要不要重试。

存储与增量

存什么取决于要回答的问题。除了业务字段，至少保留 url、抓取时间、HTTP 状态码和原始文件路径。有了原始 HTML，字段抽错了还能离线重解析，不必再打扰对方一次。

小规模用 JSONL：一行一条，追加写，坏也只坏一行，grep 就能查。要交给别人用再导出 CSV，注意 Excel 直接打开 UTF-8 的 CSV 会乱码，加 BOM，或者直接给 xlsx 文件。上量之后进数据库，用规范化 URL 的哈希做唯一键，配合 INSERT IGNORE 或 ON DUPLICATE KEY UPDATE，重复抓取天然幂等。

增量抓取靠时间或 ID：列表按发布时间倒序时，记下最大的 ID，下次只取更新的；单页更新用 ETag 或 Last-Modified，304 直接跳过解析。两者都没有，就只能保存正文哈希做比对。

原始页面建议按日期分目录存，文件名用 URL 哈希，既避免非法字符，也方便和记录表对上。

可观测性与测试

至少要埋四个数：已抓取、成功、失败、限速等待累计时长。前三个用 sync/atomic 计数，最后一个在 Wait 前后取时间差累加。每 30 秒打一行汇总，配合日志就能回答“现在卡在哪”。

日志一行一个请求，带 host、URL、状态码、耗时、重试次数。量大了控制台看不过来，按 host 聚合再看：某个域名错误率突然升高，通常不是代码坏了，而是对方改了规则或开始限流。等待时间占比过高，说明瓶颈在限速而不是网络，此时加 worker 没有意义，只会让更多 goroutine 排在队列里。

测试不要打真实站点。用 httptest.NewServer 起一个本地站点，返回固定 HTML，把 robots、重定向、429 都模拟出来；解析函数直接用字符串测，完全不经过网络。

至少覆盖三种情况：正常页面能抽出字段；结构变化时返回错误而不是 panic；robots 禁止的路径不会发出请求。测试加 -race，worker 和计数器的问题最容易在这里暴露。

再养成一个习惯：把真实页面脱敏后存成 testdata 样本，解析器的回归测试都跑它，比手搓 HTML 更接近真实。上线前先单线程抓 20 页，人眼看一遍字段，再放并发，这个动作花不了十分钟，能挡掉大部分选择器写错的低级问题。

几个常见的坑

最后列几个几乎人人都踩过的坑，按出现频率排序。

  • 重定向成环。甲跳乙、乙跳甲，没设上限就会一直跳，CheckRedirect 限 5 次即可。
  • 忘记关闭 body。defer resp.Body.Close() 要写在错误判断之后；读不完也要关，否则连接无法复用。
  • 并发开太大。对方响应一慢，几百个连接同时压过去，轻则 429，重则整段 IP 被拒。
  • 规范化不一致。列表页写相对地址、详情页写绝对地址，同一篇被抓两次；统一在入队口规范化一次。
  • 拿 XML 解析器读 HTML。遇到 <br>、<img> 直接报错，改用 goquery 或 x/net/html。
  • 忽略编码。GBK 页面按 UTF-8 读，标题全是乱码，还以为是选择器写错了。
  • 只记录成功。失败了什么都不留，第二天发现少了一半数据，无从查起。
  • 把抓取速度当性能指标。抓得快只说明你给对方添的麻烦多。

这些坑的共同点是：出问题时程序不报错，只是安静地少抓或重复抓。所以日志和计数不是可选项，而是爬虫的一部分。

小结

爬虫的难点不在发请求，而在克制与可维护：先确认允许采集，再读 robots 与服务条款；给客户端设超时，给自己设并发上限，给每个域名设间隔；URL 先规范化再去重，失败先分类再退避；原始页面留档，指标和日志留痕；测试用本地站点，不打真实站点。

代码量不大，但每一条都对应一次线上事故。把限速、去重、重试、留档这四件事做扎实，一个几百行的爬虫就足够稳定地跑上几个月，也不会成为别人运维日志里的噪音。
