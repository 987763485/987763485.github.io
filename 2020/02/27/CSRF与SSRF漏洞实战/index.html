CSRF 与 SSRF 漏洞实战

CSRF 借用户的浏览器发请求，SSRF 借服务器的网络位置发请求，共同点是请求本身“合法”，发起请求的主体却被冒用。本文按原理、检测、修复与复测的顺序展开，代码和请求均来自本地实验环境。所有验证都应在书面授权和明确范围内进行。

一、CSRF 的本质与成立条件

CSRF 的全称是跨站请求伪造。它不依赖窃取 Cookie，而依赖浏览器的一条默认行为：向某个站点发起请求时，只要目标域名匹配，浏览器就会自动附上该站点的 Cookie，不管这个请求由哪个页面发起。攻击者要做的只是让受害者的浏览器发出一个请求，请求内容由攻击者决定，身份由浏览器补齐。

同源策略限制的是脚本读取响应，并不限制请求发出。因此攻击者看不到结果，却能让服务端执行动作。这种“有身份、无回显”的能力，正好对应转账、改邮箱、加管理员一类不需要读取返回值的操作。

与 XSS 的区别常被混淆。XSS 把脚本注入目标源，脚本继承该源权限，能读页面、读非 HttpOnly 的 Cookie、读页面中的令牌；CSRF 站在另一个源，借浏览器自动附加的凭证发请求，读不到响应。XSS 能绕过多数 CSRF 防护，CSRF 防护也挡不住 XSS：前者利用对同源脚本的信任，后者利用浏览器对 Cookie 的自动携带。

图中第三步是关键：请求由攻击者页面发起，凭证却由浏览器自动附加。

把上述过程拆开，CSRF 成立需要三个条件。第一个条件是鉴权依赖浏览器自动提交的凭证，通常是 Cookie 或 Session；如果接口要求 Authorization 头，跨站表单无法设置该头，风险会显著降低。第二个条件是攻击者能预测请求的全部参数，不需要知道当前值。第三个条件是服务端没有二次校验，不验证令牌、不验证来源、不要求重新输入密码。

三个条件缺一不可，修复只需打断其中一环。

GET 执行写操作是另一类放大器。浏览器允许图片、脚本、样式表、链接预取以 GET 发起跨站请求，不需要表单，也不需要用户点击。把“退出登录”“取消订单”“绑定邮箱”做成 GET，等于把这些动作暴露给任何能插入图片的页面。方法语义应当严格：GET 只读，写操作使用 POST/PUT/DELETE，并对所有不安全方法做同等防护。

POST 的 Content-Type 也不是防线。跨站表单只能发送三种简单类型，但服务端若接受 text/plain 后自行解析，攻击者仍可构造请求。

二、CSRF 防护：令牌、SameSite 与来源校验

同步令牌是最直接的方案：服务端为会话生成随机令牌，嵌入表单或由前端读取，提交时比对。要点有四条：令牌足够随机，使用密码学安全的随机源；令牌与会话绑定，不能跨用户使用；比较使用常量时间函数，避免时序侧信道；校验失败必须拒绝请求，而不是记录日志后继续。

令牌粒度需要权衡。每会话一个令牌实现简单，多标签页友好，但泄露后可重复使用；每请求一个令牌更安全，却要处理并发请求、页面回退、AJAX 取新令牌等问题。多数业务采用每会话令牌，敏感操作再要求二次验证。

双重提交 Cookie 是另一种思路：令牌同时放入 Cookie 与请求参数，服务端只比较两者是否一致，不保存会话状态。它适合无状态服务，但前提是攻击者不能向目标域写入 Cookie。子域较多时应使用签名令牌，把会话标识签进去，防止子域注入覆盖。

SameSite 让浏览器决定跨站请求是否携带 Cookie。Strict 最严，从外站跳转进来也不带；Lax 允许顶级导航的 GET 携带，跨站 POST 不带；None 显式允许跨站携带，且必须同时设置 Secure。Lax 因此能挡住绝大多数跨站表单提交，是性价比很高的默认值。

浏览器支持情况需要谨慎表述。Chrome 从 2020 年初开始逐步把未声明 SameSite 的 Cookie 视为 Lax，但推送是分阶段的；Firefox 与 Safari 的实现和拦截策略也不一致，旧版本仍可能按旧规则行事。因此 SameSite 只是纵深防御的一层，不能替代令牌；子域互发请求仍算 same-site，站内 XSS 也可能被用来发起同站请求。

Origin 与 Referer 校验适合作为补充。对 POST/PUT/DELETE 检查 Origin 是否在白名单，缺失时回退到 Referer，两者都没有则拒绝。隐私策略可能剥离 Referer，跨域重定向可能让 Origin 变成 null，判断逻辑要写清“缺失即拒绝”。

自定义请求头是前后端分离项目常用的轻量方案：要求请求带 X-Requested-With 或自定义令牌头。跨站表单无法设置自定义头，跨域 XHR 会先发预检，服务端不放行 CORS 即可拦截；但它对非浏览器客户端无效，仍需与令牌配合。

三、CSRF 检测：去令牌重放与跨站验证

检测的第一步是梳理写操作。用代理抓取登录后的完整流量，筛出 POST/PUT/DELETE/PATCH，以及所有会改变状态的 GET，包括退出、绑定、支付、授权、导入。为每个接口记录鉴权方式、参数、令牌位置、Content-Type 与来源校验情况。

第二步做去令牌重放：保留会话 Cookie，删除令牌参数或请求头，原样重放。若仍返回成功，说明令牌只是摆设；若返回 403，再把令牌替换为过期值、另一测试账号的令牌、空字符串，观察是否被正确拒绝。注意只修改自己账号的请求，不触碰他人数据。

第三步确认是否依赖 Cookie。去掉 Cookie 重放，若返回 401，说明鉴权基于 Cookie，具备 CSRF 的前提；若仍成功，说明鉴权基于其他可预测因素，问题更严重。

第四步是在本地实验环境构造跨站请求，观察浏览器是否自动携带 Cookie、服务端是否执行。构造只针对自身系统，不制作钓鱼页面。判断时要排除前端拦截：用 curl 直接请求后端，确认防护落在哪一层。

常见误判有三类：令牌存在但未校验；令牌未绑定会话，A 的令牌可用于 B；只校验主接口，批量与旧版本接口仍然裸奔。报告应写明接口、方法、复现条件与证据。

四、SSRF 的本质、入口与危害

SSRF 是服务端请求伪造。业务替用户取回远程资源时，服务端会按参数中的 URL 发起请求；若 URL 完全由用户控制，攻击者就能让服务器访问它本不该到达的位置。服务器比浏览器更有价值：它能直达内网、网络权限更高，内网设备也更愿意信任来自服务器的流量。

常见入口都与抓取有关：头像与图片下载、Webhook 回调验证、链接预览、文件导入、网页转 PDF、RSS 订阅、下载代理，共同特征是接收地址并立即请求。按结果分为回显型与盲型，后者只能靠延时或带外行为推断，危害未必更小。

危害取决于服务器能到达哪里。第一层是内网探测：借响应差异判断主机与端口，发现未授权访问的管理后台、缓存与数据库接口。第二层是云上凭证：云主机通常在链路本地地址提供元数据服务，如 169.254.169.254，可返回实例信息与临时凭证，一旦被读取，权限便从实例扩展到云账号。2019 年公开的某金融机构数据泄露事件，就与 SSRF 结合元数据服务有关。

第三层是协议滥用。除 HTTP 外，部分运行时支持 file、gopher、dict：file 读本地文件，gopher 向内网服务发送任意 TCP 数据，dict 探测服务信息。风险取决于请求库是否允许用户指定协议。本文不给出地址路径与利用脚本。

五、SSRF 防护：白名单与解析后校验

第一原则是不相信 URL，第二原则是不只相信字符串。

协议与端口：只允许 http 与 https、80 与 443，禁用 file、gopher、dict 等协议和非标准端口。域名：只放行业务确需的域名或后缀，匹配前统一小写并去掉末尾的点，防止后缀伪装。IP：域名通过后逐一检查解析结果，拒绝环回、私网、链路本地、保留、组播与 IPv6 唯一本地地址；元数据地址显式封禁，不能只靠私网判断。

重定向：默认不跟随；必须跟随时逐跳重做校验并限制跳数。出网：通过正向代理统一出口，代理侧维护白名单；网络层默认拒绝出站，只放行必要目标，元数据网段单独封禁。再配合超时、响应大小上限，且不向用户回显内部错误。

六、DNS 重绑定与连接时校验

只做“先解析、再按域名连接”仍留有时间窗。攻击者控制域名并将 TTL 设为 0，第一次解析返回公网地址，校验通过；真正连接时 DNS 返回内网地址，请求便落到内网。这就是 DNS 重绑定，本质是检查与使用之间的 TOCTOU。

正确做法是把校验放进建立连接的一刻：自定义 Dialer 解析域名、校验 IP，再直接连接该 IP，不让底层二次解析。连接池按 host:port 复用，复用本身不重新解析；风险不在复用，而在把校验放在连接之外，换出口或代理时校验要在代理侧完成。TLS 的 SNI 仍用原域名。

七、SSRF 检测：回显、延时与带外

检测从参数梳理开始：列出所有接收 URL 的字段，包括显式参数、JSON 字段、Webhook 配置、导入来源、图片代理与隐藏参数，确认是否由服务端发起请求、是否回显、是否限制协议与目标。

判断有三条思路。回显型看响应是否出现内网页面特征或文件头。延时型看不同目标的响应时间是否有稳定差异，排除抖动与重试。带外型让目标访问自己控制的域名，观察是否产生解析或连接记录；本文不提供平台搭建与脚本。验证使用自建靶机与模拟元数据服务，不扫描真实内网，不读取真实凭证。

八、修复优先级与安全实现

修复优先级按影响面排序。先做网络层最小出网：默认拒绝、按需放行、封禁元数据网段，这层能兜住应用层遗漏。再做应用层白名单：协议、端口、域名逐项收窄。然后是请求行为限制：禁重定向、限超时、限大小。最后补日志与告警，记录被拒绝的目标与频次。任何单点都可能被绕过，纵深防御才是目标。

九、报告与复测

报告先说影响，再说证据。影响面要回答：漏洞在哪个功能、需要什么权限、能到达哪类网络、能否读到数据或凭证、是回显还是盲型。证据保留最小可复现请求、响应片段、时间与授权编号，隐去真实凭据。

修复建议对应到具体控制项。复测逐项执行：协议与端口、域名伪装、重定向、DNS 重绑定、IPv6、大小写与尾点、错误回显。未修复前不公开细节，按约定时间协调披露，通过后保留监控。

小结

CSRF 的核心是浏览器自动带凭证，修复靠令牌、SameSite 与来源校验的组合；SSRF 的核心是服务端替用户发起请求，修复靠出网白名单与连接时的地址校验。两者都必须把校验放在真正执行动作的那一层，测试的意义在于推动修复而不是收集入口。
