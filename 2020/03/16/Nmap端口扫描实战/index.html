Nmap 端口扫描实战

端口扫描是资产梳理中最基础的一步，也最容易被做成“打开工具就扫”。本文以 Nmap 7.80 为例，讲清授权、主机发现、端口状态、扫描类型、服务识别、NSE、时序和输出归档，并总结常见坑。

Nmap 的定位：资产发现，而不是漏洞利用

Nmap 全称 Network Mapper，1997 年发布，核心能力是三件事：发现存活主机，列出开放端口，判断端口后面的服务与版本。围绕这三件事，后来又长出了 NSE 脚本引擎和操作系统识别。

先摆正定位：Nmap 不是漏洞利用工具，它不验证 CVE 能否利用，也不会自动拿到权限。即使运行 vuln 类脚本，得到的也只是“可能存在”的线索。

它和 Nessus 的分工也在这里。Nmap 轻、快、覆盖广，先回答“有什么、开了什么、跑什么版本”；Nessus 在清单上做插件比对、凭据审计和合规检查，回答“可能缺哪个补丁”。合理顺序是 Nmap 发现、Nessus 深扫、人工复核。

授权、范围与时间窗口

端口扫描会主动发包，流量特征和攻击没有区别，所以第一件事不是敲命令，而是拿到书面授权。授权材料至少要说清：委托方与授权人、目标清单、排除项、时间窗口、速率约定、应急联系人，以及业务异常时的中止流程。口头同意不足以作为依据。

排除项和包含项同样重要。云主机 IP 可能属于共享设施，CDN 和 WAF 的回源地址往往不在授权范围，托管系统、外包系统和 SaaS 域名也要单独确认。打印机、摄像头、门禁和工控设备对扫描非常敏感，宁可先排除。扫到第三方资产，轻则被投诉，重则涉及法律责任。

还要评估扫描噪声。端口探测会占用连接表，老旧设备在并发稍高时可能变慢甚至重启；IDS/IPS 会产生大量告警。窗口应放在业务低谷，避开批处理、备份和发布；开始前通知值班人员，准备好中止命令。对公网陌生目标做扫描，不在本文讨论范围内。授权书、目标清单和扫描记录要一起归档，保留到项目审计周期结束。

主机发现：先知道谁在线

Nmap 默认在端口扫描前先做主机发现，只有存活主机才进入后续扫描。-sn 表示只做发现、不扫端口。

发现手段不止一种。同一以太网段内优先用 ARP，它不跨路由，但本地响应可靠、速度快，也不容易被主机防火墙挡住。ARP 只对本地网段有效，跨网段必须依赖三层探测。跨网段时，默认组合通常是 ICMP echo、发往 443 的 TCP SYN、发往 80 的 TCP ACK 以及 ICMP timestamp。

“ping 不通”不等于主机不在线。很多服务器丢弃 ICMP，却正常提供 Web 服务；有的设备对 ICMP 限速；有的地址在另一个 VLAN，ARP 根本到不了。反过来，防火墙或负载均衡可能代替后端回应。因此发现结果要结合台账和端口结果交叉判断。

确认目标在线、只是不回应探测时，可以用 -Pn 跳过发现。代价是所有地址都被当作在线，扫描时间和流量都会上升。

端口状态：读数而不是事实

Nmap 把端口分成几种状态，理解推断过程比背定义更重要。

open 表示有服务监听并做出预期响应。closed 表示主机可达但端口没有监听，通常以 RST 回应。filtered 表示探测被丢弃或拒绝，收不到有效回应，可能是防火墙或 ACL 所致。unfiltered 出现在 ACK 扫描中，表示端口可达，但无法判断开还是关。open|filtered 常见于 UDP：没有回应时，既可能是开放服务不回复，也可能是被过滤。

这些状态都是推断，不是目标的“真实配置”。防火墙静默丢包会让开放端口显示为 filtered；负载均衡可能替后端回应，让关闭的端口看起来开放。关键结论应该用 --reason 查看依据，再低速复扫确认。--reason 会列出收到或未收到的包，是解释报告结论的好材料。

把 filtered 当成 closed 是危险的：前者意味着“不知道”，后者才是“确认没有服务”。

扫描类型：按权限和目的选

最常见的三类是 TCP connect、TCP SYN 和 UDP，它们解决不同条件下的问题，而不是“谁更高级”。

TCP connect（-sT）调用操作系统的 connect，完整走完三次握手。它不需要特殊权限，普通用户就能用；缺点是每个端口都建立连接，应用日志和连接表都会留下记录，速度也受超时限制。适合没有 root 权限、或需要让目标侧看到完整连接的场景。

TCP SYN（-sS）是有权限时的默认方式。它发送 SYN，收到 SYN/ACK 后直接发 RST，不完成握手。因为不建立完整连接，速度快、应用层日志少，但网络层和 IDS 仍然看得到，需要 root 或管理员权限。要强调：SYN 扫描并不是“隐蔽扫描”，它只是减少了应用层痕迹，不能用来规避检测，本文也不讨论规避手法。

UDP（-sU）面对无连接协议。端口关闭时通常返回 ICMP port unreachable，没有回应则记为 open|filtered。UDP 不保证回应，Nmap 需要重试和等待，速度远慢于 TCP，全端口 UDP 扫描在生产环境基本不可接受。实践中只挑 DNS、SNMP、NTP、TFTP 等可能使用的端口。

端口范围也影响效率。--top-ports 100 按 nmap-services 的频率取前 100 个；-p- 扫全部 65535 个端口，耗时和噪声都显著上升，只建议在维护窗口内对少量主机使用。-F 是常见的 100 个端口，-p 22,80,443 用于已知业务端口，--open 只输出开放端口，让报告更干净。

服务与版本识别

端口号只是约定，80 端口不一定跑 HTTP，2222 也可能是 SSH。-sV 向开放端口发送探针，把响应与 nmap-service-probes 的签名比对，给出服务名、产品、版本和额外信息。

强度由 --version-intensity 控制，范围 0 到 9，默认 7。数值越高，探针越多，结果越细，耗时也越长。--version-light 相当于 2，适合大范围初筛；--version-all 相当于 9，适合少量关键主机。

识别错误很常见。中间设备可能改写 banner；端口映射和负载均衡会把请求转给另一台机器；服务跑在非标准端口上，签名匹配不到；TLS 包裹的协议需要先握手才能看见内容。版本结论通常带置信度，遇到“疑似”应该用浏览器、openssl 或主机侧包管理信息交叉验证。必要时用 --version-trace 查看探针交互，但输出量大，只适合单机排查。

操作系统识别：参考，不是结论

-O 通过分析目标 TCP/IP 协议栈的指纹来猜测操作系统：TCP 选项的顺序和内容、初始窗口大小、TTL、DF 位、IP ID 的生长方式、时间戳等。不同系统、不同版本的实现有差异，Nmap 把这些特征与内置指纹库比对。

限制很硬。目标至少需要一个开放端口和一个关闭端口；一台主机只能给出一个猜测，而虚拟化、容器、NAT 和负载均衡会让多个系统共享一个 IP；防火墙会改写或丢弃特征包。即使加上 --osscan-guess，结果也只能作为参考。

资产梳理中，操作系统更适合用带凭据的清单或虚拟化平台台账确认。-O 的价值在于区分服务器、网络设备和嵌入式系统的大致类别，而不是给出精确答案。扫描前应确认目标确实承载操作系统，而不是交换机或打印机，否则指纹匹配会偏离。

NSE 脚本：能力越大，越要约束

NSE 是 Nmap 的脚本引擎，脚本用 Lua 编写，按用途分成 discovery、auth、default、version、vuln、brute、dos、exploit、intrusive、malware、fuzzer、external 等类别。类别本身就是风险提示：intrusive、dos、exploit、brute 不适合在生产环境随手运行。-sC 等价于 --script default，适合初次接触时补充常见信息。

--script 可以写脚本名、类别名或通配符，例如 --script safe 只跑安全类。--script-args 传入键值参数，--script-args-file 从文件读取，避免在命令行暴露凭据。执行前先用 --script-help 看清脚本会做什么。

脚本更新也要走变更流程。--script-updatedb 只更新数据库；第三方仓库的脚本本质是可执行代码，必须审查后再用。生产资产优先选择 safe 和 discovery，vuln 类只挑与资产匹配的少数脚本，并确认授权范围覆盖脚本发出的请求。

时序与性能：生产环境要保守

Nmap 用 -T0 到 -T5 六个模板控制节奏，从 paranoid 到 insane。模板会同时调整超时、重试、探测间隔和并行度。-T3 是默认值，-T4 更快，常用于实验环境或网络良好的内网；-T5 过于激进，容易丢包、误判，也可能压垮老旧设备。生产环境更稳妥的是 -T2 或 -T3。

更细的控制是速率和超时。--min-rate 与 --max-rate 以每秒发包数计，--max-retries 控制重传，--host-timeout 给单台主机设上限，--scan-delay 控制探测间隔。对连接表较小的交换机、嵌入式设备、打印机和工控设备，应主动降低并行度和速率。虚拟化环境里，同一宿主机上的多台虚拟机可能同时被扫，资源争抢会更明显。

高时序会让目标 CPU 和连接表瞬时升高，让 IDS 产生大量告警，也可能触发安全设备自动封禁。目标应是稳定拿到可信结果，而不是把扫描器推到极限。窗口内要有人盯着业务指标，发现异常立即停止。

输出、归档与比对

Nmap 支持三种主要输出：-oN 是普通文本，-oX 是 XML，-oG 便于 grep，-oA 一次性生成三种。日常执行建议用 -oA，文件名带上日期、区域和任务名，避免几个月后无法对应。

XML 是后续自动化的入口。它可以被解析成资产表，也可以导入支持 Nmap 格式的工具；比较两次扫描时，Nmap 套件里的 ndiff 能按主机和端口列出新增、消失和状态变化。保留原始 XML，比只留截图可靠。

一份可复核的记录至少包含：授权编号与范围、执行人与时间窗口、Nmap 版本与完整命令行、目标清单与排除项、主机状态、开放端口、服务与版本、判定依据、异常与中止情况。字段不必多，但每一项都要能被下一位同事复核，只留截图无法作为后续比对的基线。

从端口到台账：把结果接进流程

扫描的价值在于把结果变成可执行的下一步。基本链路是：端口对应服务，服务对应版本，版本再结合授权范围内的验证手段判断是否存在已知问题。看到旧版本不等于存在漏洞，看到漏洞标题也不等于可以利用。验证应在授权范围内、在测试环境或经批准的时间窗口进行。

结果还要回写资产台账，至少补齐 IP、主机名、业务与负责人、操作系统、开放端口、服务与版本、首次发现时间、最近确认时间和授权批次。对比两次扫描的差异，新增端口往往意味着变更没有走流程，或者出现了影子资产；端口消失则可以用来确认加固或下线是否完成。台账里的端口变化还可以触发告警，帮助发现未登记的暴露面。

常见坑

第一是未授权扫描。范围、窗口、速率没有落到书面文件，或者顺手扫了同网段的其他地址，都会让整个工作失去合法性。第二是全端口加高时序。-p- 配合 -T4 打老旧设备，轻则超时，重则设备重启。

第三是低估 UDP。超时和重试会让任务从分钟级变成小时级，没设 --host-timeout 就可能挂一整夜。第四是把 filtered 当 closed，报告里写“端口未开放”，实际只是被防火墙挡住。

第五是版本识别误判。banner 可以伪造，端口可以转发，负载均衡可以代答，看到“Apache 2.2”就判定存在某个漏洞，往往经不起复核。第六是结果不复核、不归档。没有原始 XML、命令行和时间戳，出了问题无法回溯。

小结

Nmap 的定位是资产发现与端口、服务梳理，它给出的是线索，不是漏洞结论。前提是授权、范围和窗口清楚；执行时按权限与目的选择 connect、SYN 或 UDP，按资产敏感度控制时序，最后把 XML 与命令行完整归档。

对生产环境，保守的速率、明确的排除项和可中止的流程，比多扫几个端口更重要。把结果接进台账并持续比对差异，端口扫描才会成为日常能力。
