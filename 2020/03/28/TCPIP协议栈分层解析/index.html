TCP/IP 协议栈分层解析

排查线上问题时，我们常在“网络不通”四个字上打转：是网线松了，是路由没通，是端口没开，还是应用自己卡住了？本文以 TCP/IP 四层为主线，把封装、寻址、连接与排障工具串成一条线，帮助会写代码但对协议细节一知半解的读者建立可复用的分析框架。读完你应该能看着一次抓包说出每层在做什么，也能按现象快速缩小范围。

分层：把复杂问题切成可替换的几块

网络通信要解决的问题很多：怎么找到对方、怎么在不可靠的链路上传数据、怎么让多个程序共用一条线路。揉在一起，任何一处改动都会牵连全局。分层的基本思路是职责隔离：每层只依赖下层提供的服务，只向上层暴露约定的接口。链路从以太网换成 Wi-Fi，上面的 IP 与 TCP 几乎不用改；应用协议换了，传输层也无需知情。封装则让每层把控制信息加在数据前面，接收端逐层剥掉；同一层换实现，只要接口语义不变。

OSI 七层是参考模型，TCP/IP 四层是工程模型，对应关系如下表。

OSI 七层 TCP/IP 四层 典型协议 关注点
应用层 应用层 HTTP、DNS、SSH 报文语义
表示层 应用层 TLS 常归入此处 编码与加密
会话层 应用层 会话管理 连接生命周期
传输层 传输层 TCP、UDP 端到端可靠与复用
网络层 网络层 IP、ICMP 寻址与路由
数据链路层 链路层 以太网、ARP 同一链路上的交付
物理层 链路层 双绞线、光纤 比特传输

TLS 介于应用与传输之间，ARP 也横跨链路层与网络层。

封装与解封装：数据如何穿过协议栈

浏览器要发一段 HTTP 请求，应用层把报文交给传输层，TCP 加上端口、序列号、确认号、标志位、窗口与校验和，形成 TCP 段；IP 加上地址、TTL、协议号与分片信息，形成 IP 包；链路层加上目的 MAC、源 MAC 与类型字段，末尾附上校验序列，形成以太网帧交给网卡。

flowchart TD
    A[应用数据 HTTP 报文] --> B[TCP 段 加端口与序列号]
    B --> C[IP 包 加地址与 TTL]
    C --> D[以太网帧 加 MAC 与校验]
    D --> E[网卡发送]

接收端顺序相反：网卡校验帧、剥掉链路层首部，按类型交给网络层；IP 确认目的地址后按协议号交给 TCP；TCP 按四元组找到连接，剥掉首部，把字节流交给监听端口的应用，这就是解封装。抓包工具看到的不是网页，而是链路上的一个个帧，Wireshark 只是逐层解析后拼接展示。

两个尺寸容易混淆。MTU 是链路层能承载的最大载荷，以太网常见 1500 字节；MSS 是 TCP 数据的最大长度，等于 MTU 减去 IP 与 TCP 首部，IPv4 下通常是 1460 字节。MSS 在握手时协商。超过 MTU 的包要么分片，要么在 DF 置位时被丢弃并返回 ICMP 差错，这就是“大包不通、小包正常”的根源。

链路层与网络层：从 MAC 到 IP

链路层负责同一段链路上的交付。以太网帧用 48 位 MAC 地址标识网卡，交换机按目的 MAC 查转发表，查不到就泛洪到整个广播域。广播域越大，无效流量越多，生产中常用 VLAN 划小。

IP 与 MAC 的分工靠 ARP 衔接。主机发给同子网的 IP，先查 ARP 缓存；没有就广播请求“谁是这个地址”，目标主机单播回应，双方缓存一段时间。跨子网时，ARP 解析的是网关的 MAC，而不是最终目的地。ARP 没有认证，任何人都能声称某个 IP 对应自己的 MAC，这就是 ARP 欺骗的来源，流量会被引到错误主机进而被窃听或篡改；防护靠端口安全、动态 ARP 检测与静态绑定。

网络层的关键是寻址与路由。IPv4 地址配合掩码划分网络号与主机号，CIDR 用前缀长度表示。主机先判断目的地址是否同子网：同子网直接 ARP，否则交给默认网关。路由器查路由表做最长前缀匹配，选出下一跳与出接口。TTL 每经过一台路由器减一，减到零就丢弃并回送 ICMP 超时，既避免包在环路里打转，也成了 traceroute 的原理。

包大于出接口 MTU 且 DF 未置位时，路由器会分片：标识相同、片偏移标出位置，到目的主机再重组。任一片丢失整个包都要重传，所以实现更希望由源端按路径 MTU 发送。

绕不开的中间盒是 NAT。家用路由器把内网地址与端口映射成公网地址与端口，靠转换表维护会话；外部只能看到公网地址，无法主动连接内网。NAT 缓解了地址短缺，也削弱了端到端原则：应用不能再假设自己全局可达，P2P 与语音需要打洞或中继，空闲后映射还会被回收。

传输层 TCP：连接、可靠传输与拥塞控制

TCP 提供面向连接、可靠的字节流服务。建立连接是三次握手：客户端发 SYN 与初始序列号，服务端回 SYN 与自己的初始序列号并确认对方，客户端再确认。三次而非两次，是为了双方都确认对方的收发能力并同步初始序列号，避免旧报文被误认。

断开是四次挥手：主动方发 FIN 表示没有数据要发；对方先回 ACK，连接处于半关闭，仍可继续发送；发完再发 FIN，主动方确认后进入 TIME_WAIT。TIME_WAIT 等 2 倍 MSL 才消失，一是最后一个 ACK 丢失时还能确认对方重发的 FIN，二是让旧报文在网络中彻底消散，避免干扰相同四元组的新连接。

可靠性靠序列号与确认号。发送方给每个字节编号，接收方用累计确认表示“这个序号之前都收到了”。超时未确认就重传，RTO 按往返时延估算；连续收到三个重复 ACK，说明中间某段丢了，不等超时直接快速重传。流量控制靠滑动窗口：接收方通告还能缓冲多少字节，窗口为零时发送方停发并定期探测，慢的接收方不会被淹没。

拥塞控制则关心网络本身。发送方维护拥塞窗口 cwnd，可发送量取 cwnd 与接收窗口的较小值。慢启动每收到一个确认就把 cwnd 加一，指数增长；到慢启动阈值后进入拥塞避免，每个往返只加一个 MSS，线性增长；超时就把阈值减半、cwnd 回到一个 MSS 重新慢启动；收到重复 ACK 则快重传与快恢复，cwnd 减半后直接进入拥塞避免。这套 Reno 系算法在 2020 年仍是主流实现的基础。

传输层 UDP：轻量的代价

UDP 只做两件事：用端口区分应用，用校验和发现差错。首部只有 8 字节：源端口、目的端口、长度、校验和。没有连接状态、重传、排序与拥塞控制，并且保留消息边界，一次发送对应一次接收。

这些“缺失”在有些场景是优点。DNS 一问一答，重发一次比建连接划算；音视频与游戏宁可丢几帧也不愿等重传；监控指标丢一个点无关紧要。代价是可靠性要应用层自己补：序号、确认、超时重传、去重与重排，还要自己控速，否则会把别人和自己一起拖慢。所以“UDP 一定比 TCP 快”是误解，它只是少了协议栈的保证，快不快取决于应用怎么写。当时基于 UDP 的 QUIC 仍是草案，尚未成为主流。

应用层与一次完整访问

应用层协议定义报文格式与交互语义。DNS 解析分递归与迭代：客户端问本地递归服务器，递归服务器扛下全部工作；先查缓存，未命中就从根问到顶级域，再问权威，逐级拿到授权与记录。每级记录都带 TTL，到期就要重查，这是“刚改了解析为什么不生效”的常见原因。DNS 默认走 UDP 53，响应较大时改用 TCP。结果没有完整性保护，链路被劫持就可能返回错误地址，防护靠可信解析、DNSSEC 与终端侧的加密解析。

HTTP 是请求响应模型：客户端发方法、路径、首部与可选主体，服务端回状态码、首部与主体。HTTP/1.1 默认持久连接，一个 TCP 连接承载多次请求；当时浏览器对同一域名通常并发 6 个左右连接，这是静态资源分域名部署的由来。HTTPS 在 TCP 之上加 TLS，完成证书校验与密钥协商后再传报文。常见端口要记住：HTTP 80、HTTPS 443、DNS 53、SSH 22、SMTP 25、MySQL 3306。

sequenceDiagram
    participant B as 浏览器
    participant R as 本地 DNS
    participant A as 权威 DNS
    participant S as 服务器
    B->>R: 查询域名
    R->>A: 迭代查询
    A-->>R: 返回记录与 TTL
    R-->>B: 返回地址并缓存
    B->>S: TCP 三次握手
    B->>S: TLS 握手与证书校验
    B->>S: HTTP 请求
    S-->>B: HTTP 响应
    B->>S: 四次挥手

串起来就是一次完整访问：输入域名，浏览器查缓存并问本地 DNS；拿到地址后建立 TCP 连接；HTTPS 还要完成 TLS 握手与证书校验；随后发 HTTP 请求，服务端处理并返回。任何一步慢或失败，用户看到的都是“网站打不开”，分层视角却能把它拆成 DNS、连接、TLS、应用四个阶段。

排障：工具的能力边界与分层定位

排障的核心不是记住命令，而是知道每个命令证明了什么、没证明什么。

工具 主要用途 边界
ping 验证 IP 可达与往返时延 只到网络层；ICMP 可能被禁
traceroute 观察逐跳路径与断点 中间设备可能不回应
ss 查看监听端口、连接状态与队列 只能看本机
tcpdump 抓取并过滤真实报文 只能看到经过本机的流量
dig 查询 DNS 记录与 TTL 不代表应用一定可访问

按分层定位能少走弯路。先看链路：网线、Wi-Fi、交换机端口、ARP 表里有没有网关；再看路由：ping 网关与外部地址，traceroute 看断点；然后看端口：ss 确认监听地址与防火墙；最后看应用：curl -v 看状态码与响应头，翻日志。把“网络不通”拆成这四问，多数问题十分钟内能定位。

常见现象与误区

能 ping 通但端口不通，说明网络层可达，问题在传输层以上：服务没启动、只监听回环地址、防火墙丢弃了该端口。连接超时与拒绝是两种信号：超时通常是包被丢弃，可能是防火墙 DROP 或路由黑洞；拒绝是对方回了 RST，说明主机可达但端口没监听。

能解析但打开慢，要区分 DNS 慢还是连接慢：dig 看查询耗时与 TTL，curl 看各阶段时间。MTU 不一致的典型表现是小包正常、大包卡住：路径上某段 MTU 更小，而 ICMP 差错被防火墙拦掉，源端无法完成路径 MTU 发现；处理办法是调小接口 MTU 或在网关上做 MSS 钳制。TIME_WAIT 过多常出现在主动关闭的短连接服务上，先看是不是频繁建连，再考虑连接复用，直接改内核参数往往只是把问题挪走。

几个误区值得点出。TCP 是字节流，不保留消息边界，所谓“粘包”是应用层没有定义分帧规则，正确做法是长度前缀或分隔符。UDP 不一定快，缺少拥塞控制反而可能在丢包时更差。ping 通只证明 ICMP 可达，不代表服务正常。忽视 DNS 缓存则会让人反复怀疑代码，其实只是 TTL 没到期。

安全视角：明文、中间人与 SYN flood

分层决定了风险落在哪一层。HTTP、Telnet、FTP 等明文协议在链路上可被直接读取，账号、Cookie 与业务数据都暴露在同一个出口；这也是推动全站 HTTPS 的直接原因。中间人常从链路层入手：ARP 欺骗把流量引到攻击者主机，若应用又不校验证书，攻击者就能透明转发并篡改内容。防护要双向：链路侧做端口安全与动态 ARP 检测，应用侧强制 HTTPS 并校验证书链与主机名。

SYN flood 利用握手的不对称：攻击者伪造大量源地址发 SYN，服务端为每个半连接分配资源并等待最后的 ACK，半连接队列占满后正常用户无法建立连接。防护包括启用 SYN cookies，队列满时把状态编码进序列号；调大半连接队列；边界设备做新建连接限速与源地址校验；再配合清洗与流量分析。伪造源地址之所以可行，很大程度上是网络缺少入口过滤，运营商与企业边界按源地址范围做 ingress/egress 过滤，能从源头减少这类流量。

小结

分层不是口号，而是排障时能用的坐标系：链路层看 MAC 与 ARP，网络层看地址、路由与 TTL，传输层看端口、握手与窗口，应用层看报文语义。封装让每层只关心自己的首部，解封装让接收端逐层还原；MTU 与 MSS 决定包的尺寸边界，NAT 与中间盒留下例外。TCP 用序列号、窗口与拥塞控制换取可靠，代价是握手、状态与 TIME_WAIT；UDP 把选择权交回应用。遇到问题先问“哪一层能证明，哪一层还没证明”，比反复重启服务有效得多。
