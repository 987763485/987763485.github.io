中间件安全：Nginx 加固

把 Nginx 放在公网入口，等于把系统的第一道门交给它。很多团队装完就上线，默认站点、版本号、旧协议、宽松的上传目录都原样保留，等到等保测评或渗透测试时才被发现。本文从配置层面梳理一套可以落地的加固顺序：先收敛暴露面，再处理 TLS 与响应头，最后补上请求限制、日志与变更流程。读完之后，读者应能整理出一份可执行基线，并理解每条指令的副作用。

加固思路

Nginx 加固不是把网上流传的配置片段整段粘贴，而是围绕五个目标做取舍。第一是减少暴露面：不需要的站点、模块、目录和 HTTP 方法都不要对外。第二是最小权限：worker 进程、静态目录、配置与私钥各自只拿到完成工作所需的权限。第三是正确的 TLS：协议、套件、证书链和会话策略要经得起工具检查。第四是限制资源：让单个客户端无法用大包、慢连接或高频请求拖垮服务。第五是可审计、可回滚：每次变更都有记录，出问题能在几分钟内退回上一版。

这五个目标之间存在冲突。比如为兼容旧客户端保留 TLS 1.0 会削弱传输安全，为防刷把阈值压得过低又可能误伤正常用户。加固是在明确业务边界后做选择，而不是把所有选项开到最严。

版本与信息泄露

默认安装的 Nginx 会在响应头里带上版本号，默认站点会展示欢迎页，目录没有索引文件时还可能列出全部文件。这些信息单独看危害有限，组合起来却足以让攻击者判断中间件类型、版本与后端结构。

关闭版本号使用 server_tokens off，它放在 http、server 或 location 块中都可以，通常写在 http 块里统一生效。需要注意，它只去掉版本号，响应头仍然会显示 Server: nginx，若要完全隐藏服务器标识，需要额外模块或在上层代理统一改写。

return 444 是 Nginx 的非标准状态码，表示直接关闭连接，不返回响应体。它适合吸收扫描流量，但排障时没有任何提示，只建议放在默认站点。

错误页同样会泄露信息。Nginx 默认的 404、500 页面带有版本和签名，后端返回的堆栈也可能被原样透出。应当准备静态错误页，并用 error_page 接管；对 502、503、504 这类上游错误，只给用户一个统一的提示，详细原因写进错误日志。目录列表用 autoindex off 关闭；它本是默认值，却常被“优化配置”打开，交接时要重点检查。

最后清理默认内容：发行版自带的 default.conf、/usr/share/nginx/html 下的示例页、安装生成的测试站点都应删除或移出配置目录。默认站点若必须保留，就只做拒绝，不留下可访问文件。

运行身份与文件权限

Nginx 采用 master-worker 模型。master 进程以 root 启动，负责绑定 80、443 等特权端口、读取配置和派生 worker；worker 进程则应当降权到普通用户，真正处理请求的是它们。user 指令只能在 main 上下文使用，常见写法是 user nginx nginx; 或 user www-data www-data;。如果 worker 以 root 运行，一旦出现文件解析或模块漏洞，攻击者直接获得的就是 root 权限。

静态目录的权限按“目录 755、文件 644、属主为部署账号”把握。worker 只需要读取和进入目录，不需要写权限；需要上传的目录对应用账号放开写权限，目录保留进入权限，其中的文件去掉执行位，并且不能让 Nginx 把它当作脚本目录。配置文件与私钥的权限更要收紧：站点配置通常 644 即可，包含凭据的配置和私钥应当是 600，属主为 root，避免普通账号读取。

还要注意，worker 数量与文件描述符也属于运行面。worker_processes auto; 让 Nginx 按 CPU 核数派生进程，worker_rlimit_nofile 和 worker_connections 决定单进程能同时处理多少连接。数值不是越大越好，超过系统 ulimit 和内存承受能力之后，反而会在高峰期出现难以定位的错误。

TLS 配置

TLS 是入口加固中最容易“看起来配了、实际没生效”的部分。先定协议：只保留 TLS 1.2 和 TLS 1.3。TLS 1.0 与 1.1 已被主流浏览器陆续停止支持；等保 2.0 已于 2019 年 12 月 1 日实施，测评通常也要求关闭。若仍有只支持旧协议的客户端，应单列兼容入口并登记例外，而不是在主站长期放开。

套件选择以 ECDHE 前向保密和 AEAD 为主，禁用 CBC、3DES、RC4。TLS 1.3 的套件由 OpenSSL 管理，ssl_ciphers 主要作用于 TLS 1.2。证书必须部署完整链：站点证书加中间证书。缺中间证书时桌面浏览器可能正常，移动端和 Java 客户端却会报错，这类问题在灰度阶段很难靠肉眼发现。OCSP stapling 让 Nginx 代客户端查询吊销状态，既减少握手延迟，也避免客户端查询泄露访问行为；证书未带 OCSP 地址时该功能会被跳过。

HSTS 要谨慎。先从小 max-age 开始，确认全站 HTTPS 和子域都准备好了，再逐步加大；preload 一旦提交，浏览器内置列表的移除周期很长，子域中任何一台只支持 HTTP 的设备都会立刻不可用。会话复用使用共享缓存，关闭会话票据可以规避票据密钥轮换带来的前向保密问题，但会增加跨机房复用的成本。

配置完成后不要只看浏览器地址栏的小锁。用 openssl s_client 分别指定协议版本，确认旧协议握手失败、新协议能拿到完整链；再用 curl -I 检查 HSTS 是否出现在 HTTPS 响应中。

安全响应头

安全响应头应当统一放在一个 include 文件里，避免各站点各写一套。X-Content-Type-Options: nosniff 阻止浏览器猜测资源类型；X-Frame-Options: SAMEORIGIN 与 CSP 的 frame-ancestors 'self' 一起防点击劫持；Referrer-Policy 控制跨站时携带多少来源信息。CSP 只给方向：先以 default-src 'self' 收集违规报告，再按业务逐项放开，不要直接抄一份复杂策略上线。Permissions-Policy 由 Feature-Policy 演进而来，仍处在过渡期，浏览器支持并不整齐，它的目标是限制页面调用摄像头、麦克风、定位等能力，但不能替代服务端鉴权。

add_header 有一个常见陷阱：子块一旦出现自己的 add_header，父块的响应头不会继承。因此要么在每个 server、location 重复 include，要么用 always 参数确保错误响应也带上头。

请求限制

请求限制要分两层：连接层和请求层。client_max_body_size 限制请求体，超出返回 413；上传接口单独放宽，其余接口保持较小值。client_body_timeout、client_header_timeout 防止慢速发送拖住连接，send_timeout 控制响应写出的等待时间。keepalive_timeout 不宜过长，长连接会占用 worker 连接数，公网入口通常取 30 到 65 秒。

limit_req 基于漏桶，按 IP 或用户维度限速；limit_conn 限制并发连接。两者都要配合业务：登录、短信、下单接口阈值应更严，静态资源可以放宽；NAT 出口下大量用户共享 IP，阈值过低会误伤正常用户。限流状态码用 429，配合监控观察命中量，再调整 burst 与 nodelay。

代理安全

Nginx 前面有负载均衡时，真实 IP 须显式传递。边缘节点应把客户端地址写入 X-Forwarded-For，内部每一跳再追加；应用只信任来自已知代理网段的头，否则客户端可以自己伪造。Nginx 侧用 set_real_ip_from 限定可信来源，再用 real_ip_header 取地址。

上游超时必须设置，否则卡住的请求会长期占用连接：连接、读、写分别由 proxy_connect_timeout、proxy_read_timeout、proxy_send_timeout 控制。缓冲默认开启，能吸收上游的慢响应，但大文件下载要单独关闭。上游错误页和 X-Powered-By 要隐藏，502 统一换成静态页，避免暴露内部地址与框架版本。

还要注意 XFF 的边界：边缘用 $remote_addr 覆盖，内部用 $proxy_add_x_forwarded_for 追加。若两处都追加，第一个值就是攻击者伪造的，后续日志与限流都会失真。

动静分离与路径

location 的匹配顺序决定了哪条规则生效：先精确匹配 =；没有命中时找最长前缀，若它带 ^~ 就直接使用，否则按顺序尝试正则，最后回退到最长前缀。静态资源可以单独用 ^~ 命中，避免被后面的正则抢走；脚本路径则不应出现在纯静态站点里。

隐藏文件和敏感文件必须显式拒绝，包括 .git、.env、备份文件与编辑器临时文件；但 ACME 验证需要访问 /.well-known/，正则里要留出例外。上传目录只允许读取，不允许执行：不要给上传目录配置 FastCGI 或任何脚本处理器，并对可执行扩展名直接返回 403。

alias 是最容易出路径穿越的地方。若 location 前缀没有结尾斜杠，而 alias 指向的目录有斜杠，请求 /static../etc/passwd 可能被拼成预期之外的路径。要么两边都带斜杠，要么改用 root，让路径拼接由 Nginx 按固定规则完成。

访问控制

allow 与 deny 按出现顺序匹配，第一条命中即生效，因此 deny all 必须放在最后。管理后台、监控页、内部接口只允许办公网或跳板机网段访问，公网入口直接拒绝；对外只需要知道“不存在”的接口，返回 404 比 403 更少泄露信息。

Basic Auth 适合给临时入口加一道门槛，但不能当作唯一防线：密码随每个请求发送，必须走 HTTPS；没有服务端会话，退出登录通常只能依赖关闭浏览器；账号共享后无法追责。它应当和来源限制、强密码、失败计数一起使用。stub_status 这类状态页要用 internal 或来源限制，绝不能直接暴露在公网。

日志

访问日志至少要能回答谁在什么时候访问了什么、结果如何。$request 会带上完整查询串，可能包含手机号、令牌，建议拆成 $request_method 与 $uri，或对参数做脱敏；不要记录 Authorization 与 Cookie，这两类凭据一旦进日志，能读日志的人就获得了账号。加上 $request_time 与 $upstream_response_time，才能区分是入口慢还是后端慢。

错误日志级别在生产环境用 warn 或 error，debug 只在排障时短时开启。日志要按天轮转并压缩，用 nginx -s reopen 或 kill -USR1 让 Nginx 重新打开文件；集中外送时优先走 syslog 或日志采集器，避免本地磁盘被写满。按《网络安全法》的要求，网络日志留存不少于六个月。

配置检查与灰度

任何配置改动都要先执行 nginx -t，它只检查语法和文件可达性，不代表业务正确；配合 nginx -T 导出完整配置做 diff，能发现 include 顺序和变量展开的问题。nginx -s reload 是平滑重载，旧 worker 会处理完存量连接再退出，但仍要观察错误日志与 5xx。

生产变更至少经过一个灰度实例：先应用到权重很低的节点，验证 TLS 握手、关键接口、限流与日志，再逐步扩大。TLS 变更前先用工具验证协议和证书链，确认无误后再切流量。回滚方案要具体到文件和命令，不能只写一句“恢复备份”。

基线检查清单

  • 信息泄露：server_tokens off、autoindex off、默认站点已清理、错误页已定制。
  • 信息泄露：.git、.env、备份文件不可访问，.well-known 例外可用。
  • TLS：仅启用 TLS 1.2/1.3，弱套件已禁用，证书链完整。
  • TLS：OCSP stapling 生效，HSTS 的 max-age 与子域范围经过确认。
  • 响应头：nosniff、X-Frame-Options、Referrer-Policy、CSP 基线已覆盖。
  • 限制：请求体、超时、limit_req、limit_conn 已按接口配置并观察误伤。
  • 限制：代理只信任已知网段，上游超时、缓冲与错误页已配置。
  • 权限：worker 非 root，静态目录不可写，配置与私钥为 600。
  • 权限：上传目录不解析脚本，管理接口仅限可信来源。
  • 日志：不记录 Authorization/Cookie，轮转、外送与六个月留存已落实。

小结

Nginx 加固的核心不是记住多少指令，而是把入口当成需要持续维护的边界：默认内容清理干净，worker 降权，TLS 只留现代协议并验证证书链，响应头与请求限制按业务调整，代理只信任可信来源，日志既便于排障又不泄露凭据。每项变更都经过检查、灰度与回滚演练，基线才不会停留在文档里。
