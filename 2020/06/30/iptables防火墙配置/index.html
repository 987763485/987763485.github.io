iptables 防火墙配置

在 Linux 服务器上，iptables 常常是最容易被“抄一段规则就跑”、却最少被真正理解的一层。本文从数据包进入内核后的走向讲起，说明四张表与五条内置链各自负责什么，再逐步落到一台 Web 服务器的基线规则、NAT、持久化与排错。读者读完应当能独立写出一份可审计、可回滚的主机防火墙配置，并知道每条规则为什么排在那个位置。

四张表与五条链：数据包到底经过谁

Linux 的包过滤框架叫 Netfilter，iptables 只是操作它的命令行工具。内核在协议栈的关键位置埋了五个钩子（hook），每个钩子对应一条内置链：PREROUTING 在路由判断之前，INPUT 送往本机，FORWARD 转发给其他主机，OUTPUT 由本机发出，POSTROUTING 在数据包离开网卡之前。

表则按功能划分，一张表可以挂在多条链上：

  • filter：默认表，负责放行与拒绝，内置链是 INPUT、FORWARD、OUTPUT。
  • nat：负责地址与端口转换，主要出现在 PREROUTING、POSTROUTING，OUTPUT 也常用。
  • mangle：修改 IP 头字段，例如 TTL、TOS、MARK，五条链上都有。
  • raw：在连接跟踪之前打标记，只有 PREROUTING 与 OUTPUT，常配合 NOTRACK 使用。

同一钩子上，表的执行顺序是 raw → mangle → nat → filter。因此一个从外网进入、发往本机 80 端口的包，会先经过 PREROUTING 上的 raw、mangle、nat，完成路由判断后进入 INPUT 链的 mangle 与 filter；如果是转发流量，则走 FORWARD，最后在 POSTROUTING 上做 nat。

flowchart TD
    A[数据包到达网卡] --> B[PREROUTING: raw, mangle, nat]
    B --> C{路由判断}
    C -->|目的为本机| D[INPUT: mangle, filter]
    C -->|需要转发| E[FORWARD: mangle, filter]
    D --> F[本地进程]
    F --> G[OUTPUT: raw, mangle, nat, filter]
    E --> H[POSTROUTING: mangle, nat]
    G --> H
    H --> I[离开网卡]

日常配置九成只动 filter 表，涉及地址转换才进 nat 表，mangle 与 raw 属于特殊场景。需要提醒的是，2020 年前后的发行版里，iptables 命令背后可能已经是 nftables 兼容层，表名和链名保持不变，但规则的存储与查看方式不同，后文会单独说明。

规则的解剖：匹配、目标与顺序

一条规则由“在哪个表、哪条链、匹配什么、命中后做什么”四部分组成。下面这条规则放行来自管理网段、新建的 SSH 连接：

-t filter 指定表，-A INPUT 把规则追加到链尾；若希望插到最前面，用 -I INPUT 1。匹配部分可以组合多个条件，条件之间是逻辑与的关系：

  • -p tcp 指定协议，-s 与 -d 指定源、目的地址，支持 CIDR 与 ! 取反。
  • -i eth0 限制入接口，-o 限制出接口。INPUT、FORWARD、PREROUTING 有入接口，OUTPUT、POSTROUTING 有出接口，用错会被直接拒绝。
  • --dport 指定目的端口，必须与 -p tcp 或 -p udp 一起使用；多个端口写成 -m multiport --dports 80,443。
  • -m conntrack --ctstate 匹配连接状态，-m limit 做速率限制，-m recent 记录来源地址，这些扩展模块让规则从“看五元组”升级为“看行为”。

目标是命中后的动作。ACCEPT 放行，DROP 静默丢弃，REJECT 则回一个错误报文，可以用 --reject-with tcp-reset 让客户端立刻收到重置，而不是等到超时。LOG 只写日志、不终止匹配，规则会继续往下走，这一点决定了它必须放在 DROP 之前。SNAT、DNAT、MASQUERADE 只能出现在 nat 表。RETURN 表示返回调用链；如果当前是内置链，则相当于跳到默认策略。

规则是逐条匹配、命中即执行的，所以顺序本身就是策略。宽泛的 ACCEPT 放在前面，后面的细化规则永远不会生效。规则较多时可以用自定义链分组，例如 -N WEB 建链，再在 INPUT 里用 -j WEB 跳转，既方便复用，也让 iptables -L 的输出更可读。老资料里的 -m state --state 是 conntrack 的前身，语义基本相同，新写的配置统一用 conntrack 即可。

有状态过滤：conntrack 才是分水岭

如果只按“端口加方向”放行，就必须为返回流量开放一大段高位端口，规则会迅速失控。Netfilter 的解法是连接跟踪：内核的 nf_conntrack 模块维护一张表，按五元组记录每条连接及其状态，规则只需描述“允许什么样的新连接”，返回流量自动归入已有连接。

四个状态足够日常使用：NEW 是连接的第一个包；ESTABLISHED 表示这条连接已经见到双向流量；RELATED 表示与某条已有连接相关联的新连接，例如 FTP 的数据通道、ICMP 的差错报文；INVALID 则是无法归入任何连接、或状态异常的包。

最容易踩的坑是漏掉 ESTABLISHED。以 Web 服务器为例，客户端的 SYN 是 NEW，服务器回的 SYN-ACK 在这条连接里已经属于 ESTABLISHED。如果只写了“允许 NEW 且目的端口 80”，握手包能进来，回包却被默认策略丢掉，表现为浏览器一直转圈，抓包只看到单向的 SYN。正确的骨架是三条：先放行 ESTABLISHED,RELATED，再按端口放行 NEW，最后丢弃 INVALID。

容量同样要关心。nf_conntrack_max 是表项上限，默认常见为 65536；nf_conntrack_count 是当前用量。打满后内核会打印“nf_conntrack: table full, dropping packet”，新连接被直接丢弃，而旧连接看起来一切正常，这类故障很容易被误判为网络抖动。超时方面，nf_conntrack_tcp_timeout_established 默认 432000 秒，也就是 5 天，UDP 与 ICMP 则是 30 秒；高并发短连接的服务应适当调大上限、缩短 established 超时。

一台 Web 服务器的基线规则

下面这份规则集适合只对外提供 SSH 与 HTTP/HTTPS 的单机。它假设管理访问来自 203.0.113.0/28，业务网卡是 eth0；实际使用时把地址与网卡换成自己的。规则按“先放行必要流量、最后兜底拒绝”的顺序排列，默认策略放在脚本末尾设置，避免中途把自己关在门外。

几条规则值得单独解释。回环接口的放行不能省，数据库、缓存、应用之间的本地连接都走 lo，漏掉它会出现“服务在跑但连不上”的怪现象。SSH 的两条 recent 规则先记录来源，再判断 60 秒内是否超过 5 次新建连接，超过就丢弃，这能挡住大部分口令爆破，又不影响正常登录。ICMP 不能一刀切封死，路径 MTU 发现依赖 type 3 code 4 的差错报文，封掉后大包会莫名卡住。FORWARD 链虽然这台机器不做路由器，也要设为 DROP，防止误开转发后被当作跳板。

OUTPUT 保留 ACCEPT 是一种务实取舍。主机角色单一之后，可以进一步只放行 DNS、NTP、软件源与业务下游端口，出站收紧能明显削弱主机被植入后的外联能力；但收口要结合监控逐步进行，避免把正常的升级与回调一起断掉。

NAT：SNAT、DNAT 与“它不是安全边界”

NAT 解决的是地址可达性，不是访问控制。nat 表只在连接的第一个包上生效，后续包依靠 conntrack 的记录自动改写，因此 NAT 规则永远不需要为返回流量再写一条。理解这一点，很多“只加了一条规则怎么就通了”的疑惑自然消失。

出方向共享公网地址用 SNAT，规则挂在 POSTROUTING：iptables -t nat -A POSTROUTING -s 192.168.10.0/24 -o eth0 -j SNAT --to-source 203.0.113.10。如果公网地址来自拨号或 DHCP、随时会变，就改用 MASQUERADE，它每次新建连接都去查出口网卡的当前地址，代价是略高的开销，适合地址不固定的场景。

入方向把公网端口映射到内网主机用 DNAT，规则挂在 PREROUTING：iptables -t nat -A PREROUTING -d 203.0.113.10 -p tcp --dport 8080 -j DNAT --to-destination 192.168.10.20:80。这条规则只改了目的地址，包还要经过路由判断与 FORWARD 链，所以必须打开 net.ipv4.ip_forward，并在 FORWARD 中放行该流量，否则会出现“NAT 规则计数在涨、连接却建不起来”的现象。

为什么说 NAT 不是安全边界？因为它只做地址改写，不判断该不该放行。端口映射一旦建立，公网就能直达内网主机的那一个端口，conntrack 还会为返回流量自动开门。真正的边界仍然是 filter 表里的规则：只映射必需的端口，在 FORWARD 链里按源地址收紧，内网主机自身也要配置主机防火墙。把“内网地址外网看不到”当作安全假设，是很多事故的起点。此外，内网主机通过公网地址访问自己的映射端口时，还需要一条额外的 SNAT，也就是常说的 hairpin NAT，否则服务器会把回包直接发给内网客户端，源地址对不上，连接表现为单向可达。

比持久化更危险的是把自己关在门外。远程改防火墙时，默认策略一旦切到 DROP 而 SSH 规则又写错，当前会话断开后就再也进不去。稳妥的流程是：先在本地或带外控制台验证；保留一个已登录的 SSH 会话不要退出；用 iptables-apply 或自己安排定时回滚，例如通过 at 在 5 分钟后恢复备份规则，确认新规则无误后再取消；默认策略放在脚本最后设置。规则文件纳入版本管理，每次变更留下 diff。

关于“规则不见了”，2020 年前后最常见的原因有三个。其一，firewalld 正在运行，它作为前端管理 nftables 或 iptables，reload 时会重写规则集，此时应使用 firewall-cmd --permanent 或 rich rule，而不是直接调用 iptables。其二，命令实际走的是 nftables 兼容层，iptables -V 会显示 (nf_tables) 或 (legacy)，用 nft list ruleset 才能看到全貌。其三，看错了表，NAT 规则本来就不在默认的 filter 表里。排查前先执行 firewall-cmd --state 与 iptables -V，确认当前是哪套后端在管事，比盲目加规则有效得多。

排错：从计数器到抓包

规则写完不生效时，第一步不是改规则，而是看计数器。iptables -L -n -v --line-numbers 会列出每条规则的包数与字节数，编号可用于 -I 与 -D；加上 -n 避免反解域名造成的长时间等待。某个计数器为 0，说明包根本没走到这条规则，常见原因是前面已有规则命中，或者包走的是另一条链。链的默认策略那一行也带计数，policy 的数字持续增长，说明有流量没被任何规则接住，正是需要确认预期的地方。iptables -S INPUT 用命令形式打印规则，比表格视图更容易看清顺序；-Z 可以清零计数，便于做一次干净的复现。

几种高频错误值得对照自查。默认策略是 ACCEPT 又没写任何规则，防火墙等于没有；只放行 NEW 却忘了 ESTABLISHED，表现为握手到一半卡住；LOG 写在 DROP 后面，日志永远是空的；只配 IPv4，IPv6 仍然全开；为了省事把 22 端口或数据库端口对 0.0.0.0/0 开放，等于把管理面交给互联网；规则调通却没持久化，重启后回到原点。

治理层面，防火墙应遵循最小权限：只开业务必需的端口，管理入口限定在跳板机或管理网段，能用密钥登录就不开密码。每次变更走评审并保留 diff，规则文件与变更记录一起入库；丢弃与拒绝的日志接入集中日志系统并设置告警，定期审计规则，删除临时放行的条目。防火墙不是配一次就结束的东西，它需要和资产清单一起维护。

小结

本文从 Netfilter 的钩子讲起，说明了四张表与五条链的分工，以及规则“匹配加目标、顺序即策略”的本质。有状态过滤是关键：先放行 ESTABLISHED,RELATED，再按端口放行 NEW，最后兜底 DROP，同时关注 conntrack 的容量与超时。落地时 IPv4 与 IPv6 要一起配，NAT 只当可达性手段而不当安全边界。上线务必解决持久化与锁死风险，并用计数器、日志、conntrack 与抓包形成排错闭环。
