MySQL 慢查询优化案例

慢查询优化最容易走两个极端：一上来就加索引，或者把 SQL 改得面目全非却说不清为什么。本文不复述排查流程，也不逐列讲执行计划，而是挑出七个来自工单的案例，每个都按“症状—怀疑—证据—修复—验证—教训”走一遍。文中表结构、执行计划与耗时均为示例数据，只用于说明量级。读完之后，你面对一条慢 SQL 时应该能先判断它属于哪一类问题，再决定动哪里。

教训：联合索引是照着查询形状建的，不是照着表建的。点查加时间排序用 (user_id, created_at)，按状态跑批用 (status, created_at)，两个形状就该两条索引，硬塞进一条只会两头都不讨好。

案例二：隐式类型转换让索引失效

症状：用户中心按手机号查账号，大部分请求十几毫秒，个别时段却要两秒以上。phone 是 varchar(20)，上面有普通索引。

怀疑：索引损坏或统计信息过期。

证据：EXPLAIN 显示 type 为 ALL、key 为 NULL，扫描行数约等于全表；再执行 SHOW WARNINGS，能看到优化器改写后的条件：

括号里的 cast 就是答案。字符串列与数字比较时，MySQL 把字符串转成双精度浮点数再比，转换发生在列这一侧，索引按原始字符串排序，无法复用，于是退化成全表扫描。更麻烦的是它会带来错误结果：'13800138000abc' 转成 double 同样是 13800138000，也会被命中。

修复分两层。SQL 层把常量改回字符串，应用层则统一用参数化查询并按字符串绑定，别让框架把手机号当数字传：

改完 type 变为 ref，key 为 idx_phone，rows 为 1。

这里有个方向问题值得记住：同样是“类型不一致”，谁被转换决定了后果。WHERE status = '1' 是 tinyint 列比字符串常量，被转的是常量，索引照用，属于无害的隐式转换；WHERE phone = 13800138000 是把列转成数字，索引必然失效。判断办法很简单，看 SHOW WARNINGS 里 cast 包住的是常量还是列。

字符集与排序规则不一致是同一家族的另一支。它通常不会悄悄变慢，而是直接抛 Illegal mix of collations，反倒好定位。真正的坑在于有人为了消掉这个报错，在 SQL 里写 CONVERT(u.phone USING utf8mb4) = o.phone，把列包进函数，报错没了，索引也没了。正确做法是建表统一 utf8mb4，历史表用 ALTER TABLE ... CONVERT TO CHARACTER SET 收敛，而不是在查询里打补丁。

教训：索引失效的投诉里，类型不匹配占了很大比例。看到“明明有索引却全表扫描”，第一步就该查两边的类型与字符集，而不是先怀疑优化器。

案例三：函数包住了索引列

症状：运营后台的“昨日新增”看板，凌晨跑批要十几秒。

怀疑：这么简单的 COUNT，索引也在，不该慢。于是看执行计划，发现 key 一列并非 NULL，而是遗留的单列索引 idx_created，type 是 index，rows 接近全表。这里容易被误导：key 有值不等于走了范围扫描，type 为 index 表示把整棵索引扫了一遍，只是扫的是索引页而非数据页，量级一样。

证据要再补一层：DATE(created_at) 的结果并不存在于索引中。索引按 created_at 的原值有序，优化器没有能力从 DATE(x) = '2020-05-20' 反推出 x 的区间，只能逐行取值、套函数、再比较。即便在 8.0 上也是如此，函数索引（8.0.13 起）是另一条路，不是自动优化。

修复是把运算搬到常量一侧，写成半开区间：

改完 type 为 range，rows 变成一天的量。用半开区间而不是 BETWEEN '2020-05-20' AND '2020-05-20 23:59:59'，是为了兼容带小数秒的列：若列是 DATETIME(3)，23:59:59 之后那 999 毫秒的数据会被漏掉，这类错误往往几个月后才被对账发现。

同样的思路适用于一切“列上做运算”的写法：WHERE amount * 2 > 100 改成 amount > 50，WHERE LEFT(order_no, 8) = '20200520' 改成 order_no LIKE '20200520%'。后者的前提是前缀匹配，LIKE 以通配符开头时同样用不上索引。

教训：函数、运算、类型转换只要作用在列上，索引就基本失效。改写方向永远是“让列保持裸奔，把计算交给常量”。

案例四：深分页，越翻越慢

症状：后台文章列表前几页几十毫秒，翻到几万页之后要七八秒，且耗时随页码线性增长。

怀疑：(status, created_at) 索引是现成的，排序也走了索引，为什么还慢。

证据在 EXPLAIN 的 rows 一列：估算值约 100 万，正好等于 offset 加 limit。这说明优化器很清楚自己要读多少行。LIMIT 的语义不是“跳过前 N 行”，而是“先按顺序取出前 N+M 行，丢掉前 N 行”。被丢掉的 100 万行同样要沿二级索引逐条回表、取出整行、再丢弃，成本全花在无用功上。加索引解决不了这个问题，因为索引本身没有“第 100 万条在哪里”的快捷入口。

第一条路是延迟关联，把回表次数从百万级压到 20 次：

内层只取 id。因为二级索引的叶子节点带着主键，(status, created_at) 上就能完成覆盖扫描，无需回表；外层再用 20 个主键做点查。示例中这条改写把 8 秒降到 0.6 秒——收益全部来自“少回表 100 万次”，内层依旧扫了 100 万条索引项，所以它只是缓解，不是根治。

第二条路是游标分页，让每次查询都从“上一页最后一条”开始：

用行构造器把 created_at 与 id 组成一个游标，id 作为决胜列，避免同一秒内多条记录被跳过或重复。这条语句能在 (status, created_at, id) 上做范围扫描，无论翻到多深都是常量级开销。代价是不能跳页，只能上一页/下一页，前端得改成滚动加载或“加载更多”；产品上还要接受“第 N 页”这个入口消失。

验证时除了看耗时，还要逐行比对改造前后的两页数据，确认没有重复与遗漏，尤其是同一秒内写入的批量数据。

教训：深分页的根因是 offset 的线性成本，属于接口设计问题而非索引问题。能改接口就上游标分页，改不动就用延迟关联兜底，同时把“最多翻多少页”写进产品约束。

案例五：OR 跨列，索引合并未必是好事

症状：消息中心要查询“某个用户发出的”或“提到某个用户的”消息，列表接口偶尔超过一秒。

两列各有一条单列索引，直觉上应该很快。

证据：EXPLAIN 的 Extra 里出现了 Using union(idx_sender, idx_mention)，type 为 index_merge。这说明优化器没有放弃索引，而是分别从两条索引取出行号、求并集、再去重，最后为满足 ORDER BY 做一次 filesort。问题就出在最后一步：合并后的结果并不按 created_at 有序，排序必须等所有行到齐，LIMIT 20 起不到提前收敛的作用，扫描量随命中行数增长。示例中两列各命中数万行，光是排序就花掉了大部分时间。

还有一条更常见的坑：只要 OR 的任意一个分支用不上索引，整个条件就退化为全表扫描。因为 OR 要求并集，优化器只能老实逐行判断。所以“我给其中一个字段加了索引，为什么还是全扫”，答案往往就在另一个分支上。

修复是手工拆分，把并集写成两条独立查询：

每个分支各自用索引、各自排序、各自取 20 行，外层只对最多 40 行排序，成本被彻底压平。结果正确的前提是“全局前 20 一定落在两个分支的前 20 之内”，这对任何按同一键排序的 TOP-N 合并都成立。

UNION ALL 不去重，所以第二个分支必须加上 sender_id <> 10086 保证互斥，否则同一条消息会重复出现。如果两列都可能为 NULL，这个不等式会把 NULL 行过滤掉，此时用 NOT (sender_id <=> 10086) 或干脆退回 UNION 去重，但要接受临时表的开销。

验证时对比两版的返回条数与首尾行，再确认两个分支的执行计划都是 ref、rows 均为 20 上下。示例中总耗时从约 1.2 秒降到 15 毫秒。

教训：OR 是并集语义，天然不友好于 B+Tree 的单向有序扫描。索引合并是优化器的补救，不是免费的午餐；能改写成 UNION ALL 就改，改的时候务必把重复行处理干净。

案例六：慢的不是 SQL，是锁

症状：一批按主键更新的语句，平时 5 毫秒，某个下午集体变成 8 秒，应用侧连接池很快被打满，而 CPU 与磁盘指标都很平静。

怀疑：索引失效？但条件是主键，扫描行数必然是 1。

证据要连成一条链。第一环来自慢日志：Query_time 为 8.02 秒，Rows_examined 为 1，Rows_sent 为 0。只碰了一行却花了 8 秒，时间显然不在“找行”上，这一条就足以把索引问题排除掉。第二环是 SHOW PROCESSLIST：能看到若干 State 为 updating 的会话，还有一个 State 为 Waiting for table metadata lock 的 ALTER TABLE。第三环查事务表：

结果里有一个十分钟前开启、状态为 RUNNING 的事务，trx_query 为 NULL——它已经执行完语句却没有提交。再往下用 performance_schema.data_lock_waits 关联 data_locks，就能拿到“谁挡住了谁”的线程号。这里要注意版本差异：5.7 里 INNODB_LOCKS、INNODB_LOCK_WAITS 已标记废弃，8.0 直接移除，统一用 performance_schema 的两张表更稳。

真相是连锁反应：批处理脚本关掉了 autocommit，跑完一条 SELECT 就去做别的事，事务一直悬着，元数据锁不释放；运维的 ALTER TABLE 排在它后面；后续所有访问这张表的语句又排在 ALTER 后面。一条只读的 SELECT 拖住了一条 DDL，DDL 再拖住整张表。

用一张图概括分流思路：

flowchart TD
    A[慢日志里一条语句很慢] --> B{Rows_examined 是否远小于耗时对应量级}
    B -- 是 --> C[怀疑锁等待或元数据锁]
    B -- 否 --> D{是否扫描了大量行}
    D -- 是 --> E[索引失效或最左前缀不匹配]
    D -- 否 --> F[排序 临时表 网络或应用侧]
    C --> G[查 innodb_trx 与 data_lock_waits]

修复分三步：先 kill 掉悬挂事务的会话，让 ALTER 通过；再给 DDL 设置合理的 lock_wait_timeout，避免它无限期排队；最后约束批处理，事务里不做无关操作，长事务纳入监控。

验证的标准不是“SQL 变快了”，而是“阻塞链消失”：SHOW PROCESSLIST 里不再有长时间 updating，innodb_trx 中最老事务的存活时间回到秒级。

教训：慢日志记录的是语句从进入到返回的总时长，锁等待也算在内。先看 Rows_examined 与耗时是否匹配，就能把“查得慢”和“等得久”分开，这一步能省掉大量无效的索引调整。

案例七：filesort 与 NOT IN 子查询

这一类问题不在“扫了多少行”，而在“扫完之后还要做什么”。

第一个是排序。WHERE author_id = 7 ORDER BY created_at DESC LIMIT 20，若索引只有 author_id，取出的行按主键顺序排列，必须整体排序后才能取前 20，Extra 里会出现 Using filesort，而且参与排序的是该作者的全部文章。把索引扩成 (author_id, created_at)，顺序由索引直接给出，LIMIT 20 读满即停。判断标准很直接：等值列在前、排序列在后，Extra 里的 filesort 才会消失。

第二个是 NOT IN。下面这条语句在 refunds.order_id 允许 NULL 时，无法被改写成反连接，只能对 orders 每取一行就执行一次子查询：

原因是三值逻辑：子查询里只要出现一个 NULL，NOT IN 的结果就整体为 UNKNOWN，优化器不敢做等价变换。把列改成 NOT NULL，或改写成 LEFT JOIN refunds r ON r.order_id = orders.id AND r.status = 1 WHERE r.order_id IS NULL，执行计划才会变成一次连接。这类改写不改变语义，却常带来数量级的差异。

教训：看到 filesort 先问“能不能让索引提供顺序”，看到子查询先问“优化器为什么不敢重写”，答案通常藏在可空性与排序键里。

小结

这七个案例可以归成四类：索引与查询形状不匹配（案例一、三、七），类型与字符集不一致（案例二），访问模式本身有缺陷（案例四、五），以及根本不是查询问题（案例六）。排查时先看 Rows_examined 与耗时的关系，能最快把“等锁”从“扫描”里摘出来；再看 possible_keys 与 key 是否为空，判断是没索引还是没用上；最后才去调索引顺序与 SQL 写法。每次改完都用同一份数据、同一会话验证，并把结论写回工单——积累下来的应是“这类形状配什么索引”的判断力，而不是某一条 SQL 的最终版本。
