PostgreSQL 索引类型与查询优化

索引是 PostgreSQL 性能调优里投入产出比最高的一环，但“建了索引”并不等于“查询变快”：选错访问方法、排错列顺序，或者让统计信息过期，都可能让一条本该毫秒返回的 SQL 退化成全表扫描。本文以 PostgreSQL 12 为基准，先梳理各类索引的适用边界，再按查询形态给出选型建议，然后讲清楚规划器的成本模型与执行计划的读法，最后用一个订单表的例子把单列索引、复合索引和部分索引放在一起对比。读完本文，你应该能判断一条 SQL 该建什么索引，以及规划器为什么有时偏偏不用它。

索引家族：六种访问方法

PostgreSQL 与 MySQL 有一个显著区别：索引不是只有 B+ 树一种实现，而是可插拔的访问方法（access method）。建索引时用 USING 指定，不写就默认 B-tree。理解每种方法的数据结构，才能理解它能回答哪一类谓词。

B-tree 是最常用的一种，平衡多路搜索树，支持 =、<、<=、>、>=、BETWEEN、IN 和 IS NULL，还能直接提供排序顺序，让 ORDER BY 省掉一次 Sort 节点。绝大多数业务查询都可以先用 B-tree 保底，真正需要斟酌的是“列怎么排”而不是“用不用它”。

Hash 只支持等值比较。从 PostgreSQL 10 起 Hash 索引写入了 WAL、具备崩溃安全性，可以放心用在生产环境。它的索引体积通常小于 B-tree，单点等值查找也略快，但只支持单列、不支持范围和排序，因此实际出现频率并不高。

GIN 是广义倒排索引（Generalized Inverted Index），一个键指向多行，天生适合“包含”类查询：数组的 @>、JSONB 的 @>、全文检索的 @@，以及 pg_trgm 提供的模糊匹配。它的写入代价偏高，因为每个元素都要拆成键，PostgreSQL 用 pending list 做缓冲来摊平这部分开销。

GiST 是广义搜索树，把数据抽象成可比较的“范围”或“外接矩形”，适合几何类型、范围类型和最近邻查询（<-> 运算符），PostGIS 的空间索引就建立在它之上，排除约束也依赖它。

BRIN 是块级索引（Block Range Index），每 N 个数据页只记录一个 min/max 摘要。一个 BRIN 索引可能只有几十 KB，非常适合按时间追加、且列值与物理顺序强相关的大表；代价是查询时要把命中区间内的页全部读出来再过滤。

SP-GiST 是空间分区树，适合点数据、前缀树这类非平衡结构，日常业务里用得不多，知道它的存在即可。

按查询形态选索引

选索引的第一步不是看表结构，而是看 WHERE 子句的形状。同样的列，换个写法就可能换一种索引。

等值与范围。WHERE status = 'paid'、WHERE created_at >= now() - interval '7 days'、WHERE id IN (1, 2, 3) 都交给 B-tree。若一条 SQL 同时含等值列和范围列，等值列应放在前面，原因在下一节展开。

前缀匹配。LIKE 'abc%' 看起来天然适合 B-tree，但在非 C 排序规则下默认用不上：索引按 locale 排序，前缀不再对应连续的键区间。解决办法是给列指定 text_pattern_ops 操作符类。

任意位置匹配。LIKE '%abc%' 和 ILIKE '%abc%' 无法走 B-tree。启用 pg_trgm 扩展后，把字符串切成三元组建 GIN 索引，就能支持包含、相似和大小写不敏感的匹配。

JSONB 包含。@> 是 JSONB 最常用的操作符，用 GIN 索引。默认的 jsonb_ops 通用性最好；如果只做包含查询，jsonb_path_ops 的索引更小、查找更快，但不支持键存在性判断。

全文检索。把文档转成 tsvector 后用 GIN 存储，查询侧用 @@ 匹配 tsquery。PostgreSQL 12 支持生成列，可以把分词结果落成真实列，避免每次查询重复计算。

多列索引、列顺序与覆盖索引

B-tree 的键是复合的：先按第一列排序，第一列相同再按第二列排序。这个物理事实决定了三件事。

第一，最左前缀原则。只有约束了前导列，索引才能被用来定位。对 (status, created_at) 来说，WHERE created_at > now() - interval '1 day' 几乎得不到帮助，因为 PostgreSQL 12 没有索引跳跃扫描，无法跳过未约束的前导列。

第二，等值列放前、范围列放后。(status, created_at) 可以先按 status = 'pending' 定位到一段连续区间，再在这段区间里按时间做范围扫描；如果反过来建成 (created_at, status)，时间范围会把索引切成很多碎片，status 只能退化成过滤条件。列顺序不取决于哪一列“更独特”，而取决于查询里谓词的形态。

第三，覆盖索引可以减少回表。从 PostgreSQL 11 起，B-tree 支持 INCLUDE 子句，附加列只存放在叶子节点，不参与比较与排序，因此既能带上查询需要的字段，又不会让上层键变得臃肿。

想让 INCLUDE 真正发挥作用，查询必须只访问索引里有的列，从而走 Index Only Scan。这里还有一个容易被忽略的前提：索引对应堆页在可见性映射（visibility map）中必须是 all-visible，否则执行器仍要回表确认元组可见性。EXPLAIN 输出里的 Heap Fetches 就是这件事的计数器；批量导入后立刻测试，常常看不到理想的 Index Only Scan，跑一次 VACUUM 之后才会好转。

部分索引、表达式索引与并发创建

部分索引（partial index）只索引满足 WHERE 条件的行。当某一状态的数据占比很小、或者表做了软删除时，部分索引可以把体积压到全量索引的零头，写入维护成本也随之下降。

使用部分索引的关键是谓词蕴含：查询里的条件必须能推出索引的 WHERE 条件，规划器才敢用。WHERE status = 'pending' 的索引服务不了 WHERE status <> 'cancelled'，哪怕结果集看起来差不多。谓词里也不能出现易变函数。

表达式索引（expression index）索引的是函数计算结果，适合对列做了固定变换的查询。建索引时函数必须标记为 IMMUTABLE，查询里也必须写出完全相同的表达式，否则规划器无法把两者对上。

最后是上线方式。普通的 CREATE INDEX 会持有 SHARE 锁，期间该表的写入全部阻塞，大表上可能持续几分钟。CREATE INDEX CONCURRENTLY 不阻塞写入，但代价不小：不能在事务块中执行，需要扫描两遍表，还要等待所有可能看到旧快照的事务结束；中途失败会留下一个标记为 invalid 的索引，必须删掉重建。因此并发建索引要放在事务之外单独执行，建完再查 pg_index.indisvalid 确认状态。

规划器的成本模型与执行计划

PostgreSQL 的规划器是代价驱动的：它为每个候选路径估算 I/O 与 CPU 成本，挑出最低的那个。估算的依据是统计信息，所以“索引没被用上”往往不是索引坏了，而是规划器算出来它更贵。

统计信息从哪里来

ANALYZE 会采样表数据，把结果写进 pg_statistic，日常通过 pg_stats 视图查看。三个字段最值得关注：n_distinct 表示某列有多少个不同值，决定等值条件大致能过滤掉多少行；most_common_vals 与 most_common_freqs 记录高频值及其占比，status 这类分布倾斜的列全靠它估准；correlation 描述列值的物理顺序与逻辑顺序有多一致，接近 1 时索引扫描近似顺序读，接近 0 时就是大量随机 I/O。

统计信息是采样得来的。批量导入或大批更新之后不跑 ANALYZE，规划器就会拿着旧分布做决策，这正是“昨天还好好的 SQL 今天突然全表扫”的常见原因。

成本参数与全表扫描

几个关键参数值得记住：seq_page_cost 默认 1.0，random_page_cost 默认 4.0，cpu_tuple_cost 为 0.01，cpu_index_tuple_cost 为 0.005，effective_cache_size 则告诉规划器操作系统和共享缓冲区大概能缓存多少数据。

random_page_cost 是最常被调整的一个。4.0 来自机械硬盘时代，SSD 上随机读与顺序读的差距没有那么大，不少团队把它调到 1.1 左右，规划器随即更愿意选择索引。但也要接受另一种情况：表只有几个数据页，或者条件过滤后仍要返回大部分行，这时顺序扫描本来就是更便宜的路径。用 enable_seqscan = off 强行“纠正”规划器，通常只是把代价转移到了别处。

读计划

EXPLAIN 只估算、不执行；EXPLAIN (ANALYZE, BUFFERS) 会真正执行，给出实际耗时、实际行数和缓冲区访问情况。读计划时从内层往外层看，重点关注三件事：节点类型（Seq Scan、Index Scan、Bitmap Heap Scan、Index Only Scan、Nested Loop、Hash Join、Merge Join）、估算行数与实际行数的差距、以及 BUFFERS 里的 shared hit 与 read 比例。

估算与实际相差一个数量级，通常说明统计信息不准，或者列与列之间的相关性没有被建模；loops 大于 1 时，节点上显示的时间是单次循环的平均值，估算总耗时要乘上循环次数。至于连接方式，嵌套循环适合外表小、内表有高效索引的场景，哈希连接适合大表等值连接且内存足够，归并连接则要求两侧都有序，常用于已经排好序或走索引扫描的结果。

实战：订单表的三种索引方案

假设有一张一千万行的订单表，status 只有四种取值，其中 pending 约占 1%，最近一天的订单约占全表的 0.3%。业务上最热的查询是“取最近一天的待处理订单，按时间倒序取前 50 条”。

没有任何索引时，计划是 Seq Scan 加 Sort，再把结果截断到 50 行。全表一千万行都要读一遍、逐行判断两个条件，成本随表增长线性上升。

只给 status 建单列索引，计划会变成 Bitmap Index Scan 加 Bitmap Heap Scan。位图扫描先把满足 status = 'pending' 的十万个元组位置收集起来，再按物理顺序回表，回表之后仍要过滤时间条件，最后还要排序。索引本身用上了，但过滤效果太差，回表量依然巨大。

正确的做法是建复合索引，让两个条件都参与定位，同时顺带提供排序：

由于 status 是等值条件，索引在 status = 'pending' 这一段内部已经按 created_at DESC 有序，执行器顺着索引读，取满 50 行就停，既不用排序也不用扫描全部候选行。INCLUDE 里的两列让查询只访问索引即可完成，若堆页已是 all-visible，就能看到 Index Only Scan。

如果确认这张表上九成以上的查询都只关心待处理订单，还可以进一步换成部分索引：CREATE INDEX idx_orders_pending ON orders (created_at DESC) WHERE status = 'pending'。它不存储其他状态的条目，体积更小、缓存命中率更高。代价是通用性：将来出现按 status = 'paid' 查询的需求，这个索引帮不上忙，还得再建一个。这也是选型时的取舍——部分索引换取体积和写性能，复合索引换取适用范围。

维护与常见误区

膨胀、VACUUM 与 REINDEX

MVCC 之下，一次 UPDATE 会写入新版本并把旧版本留在堆里，索引也要为旧版本保留条目，直到清理。autovacuum 默认的触发阈值是 autovacuum_vacuum_scale_factor = 0.2，在一张千万行的表上意味着两百万行变动才动手，往往太迟。对大表可以单独调低这个比例，让清理更及时。

VACUUM 只把空间标记为可复用，并不归还给操作系统；要真正缩小文件，得用会持排他锁的 VACUUM FULL，或者社区工具 pg_repack。索引自身也可以重建，PostgreSQL 12 起支持 REINDEX CONCURRENTLY，重建期间不阻塞写入。

索引使用统计与写放大

pg_stat_user_indexes 的 idx_scan 能回答“这个索引到底有没有人用”。长期为 0 的索引值得审视，但要注意统计是从上次重置开始累计的，季度报表、年度对账这类低频查询可能几个月才跑一次，不能贸然删除。另一个方向是成本：每多一个索引，每次 INSERT 和 UPDATE 都要多维护一棵树、多写一份 WAL、多占一份缓冲，这就是写放大。索引数量应当与写入吞吐一起权衡。

常见误区

  • 过度索引：把每个出现在 WHERE 里的列都建一遍，结果写变慢、规划器选择变多、缓存被挤占。
  • 列顺序凭直觉：把选择性最高的列放最前，却忽略了查询里它并不是等值条件。
  • 依赖 OR、!=、NOT IN：OR 尚可拆成 BitmapOr，但两侧选择性都差时不如全表扫；!= 与 NOT IN 几乎注定要读大部分行。
  • 类型不匹配：在 PostgreSQL 里字面量一般会按列类型解析，id = '123' 仍能走索引；真正麻烦的是 JOIN 两侧类型不同，或者比较时套了隐式转换。
  • 在列上套函数：WHERE date(created_at) = '2020-06-01' 用不上普通索引，应改写成范围条件，或建表达式索引。
  • 统计信息过期：大批量导入、批量更新后没有 ANALYZE，规划器仍按旧分布估算。

小结

PostgreSQL 的索引是可插拔的访问方法：B-tree 覆盖等值、范围与排序，GIN 处理数组、JSONB 与全文检索，GiST 面向几何与范围，BRIN 服务按序追加的大表，Hash 只做等值。选型时先看查询形态，再定列顺序；等值列在前、范围列在后，必要时用 INCLUDE 换取 Index Only Scan。部分索引与表达式索引能显著压缩体积，但要保证查询谓词与索引定义对得上。索引能否被用上最终由规划器按成本决定，读懂 EXPLAIN (ANALYZE, BUFFERS) 里估算与实际行数的差距，比反复猜测有效得多。最后别忘了维护：及时 VACUUM、定期审视 pg_stat_user_indexes 中从未被使用的索引，控制写放大。
