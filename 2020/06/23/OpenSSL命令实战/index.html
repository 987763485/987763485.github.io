OpenSSL 命令实战

证书过期、证书链不完整、私钥与证书不匹配，这些线上事故的最后一步排查往往落在同一条命令上。本文把 OpenSSL 1.1.1 中与证书、密钥相关的子命令串成一条可操作的路径，从生成私钥、制作 CSR，到签发自签证书、检查与校验，再到用 s_client 探测线上服务。读完之后，你应该能独立完成一套内部证书的签发与部署，并在遇到 TLS 报错时知道先敲哪一条命令。

版本与密钥：先确认工具链，再生成私钥

OpenSSL 的命令行工具在 1.1.1 与 1.0.2 之间有不少差异，而两者的报错常常只差一行 unknown option，很容易把时间浪费在排查语法上。截至本文写作时，OpenSSL 1.1.1 是官方维护的长期支持分支，1.0.2 已经在 2019 年 12 月 31 日结束支持，仍在使用它的多半是随老发行版一起安装的版本，例如 CentOS 7 自带的 1.0.2k。OpenSSL 3.0 仍在开发之中，尚未发布，它的 provider 体系会改变算法加载方式，本文不涉及；如果你在某个环境里看到 3.0 的文档，请先确认它是否真的安装在那台机器上。

生成私钥：genpkey 是统一入口

genpkey 是 1.0.0 之后引入的通用密钥生成命令，算法由 algorithm 参数指定，算法细节用 pkeyopt 传入。它输出的私钥默认是 PKCS#8 格式，文本头部为 BEGIN PRIVATE KEY，比老的 genrsa 输出的 PKCS#1 格式更通用，也方便在不同工具之间迁移。

第一条命令先把当前 shell 的默认权限掩码设为 077，之后新建的文件只有属主可读写，避免私钥在生成的瞬间被同组用户读到。第二条生成 3072 位 RSA 私钥；第三条用 aes-256-cbc 给私钥加口令保护，执行时会提示输入口令。密钥长度上，2048 位是当下的底线，3072 位在安全性和握手开销之间比较均衡；4096 位并非不能用，但每次握手都要多做大数运算，在高并发入口上并不划算。

CSR：配置文件、SAN 与 addext

CSR 是申请者交给 CA 的申请表，里面包含公钥和主题信息，并用对应的私钥签名，以此证明申请者确实持有这把私钥。CA 只读取其中的公钥与主题，最终签发的证书内容由 CA 决定，因此 CSR 里写的扩展只能算请求，不保证被原样采纳。理解这一点，就不会在证书签发后才发现 CA 丢掉了自己精心写好的 SAN。

最直接的做法是用 subj 一行给出主题：

new 表示生成新的 CSR，key 指定已有私钥，工具会用其中的公钥填充 CSR 并签名，subj 则用斜杠分隔的字符串给出主题。这种写法适合脚本和一次性操作，但它有一个明显短板：无法携带扩展，尤其是 SAN。主题里的 CN 曾经是浏览器匹配域名的依据，但在 RFC 5280 的语境下，主机名校验应当以 SAN 为准，主流浏览器在 2017 年前后已经不再回退到 CN。换句话说，一张只有 CN、没有 SAN 的证书，在现代浏览器里会直接报证书错误，生产环境务必显式写入 SAN。

CSR 生成之后，先自检再提交给 CA：

subject 只打印主题，适合快速核对；text 打印完整结构，重点看公钥算法、签名算法和 Requested Extensions 里的 SAN 是否齐全；verify 用 CSR 中的公钥验证其签名，输出 verify OK 说明私钥匹配、内容未被篡改。若这一步就失败，说明 CSR 与私钥对不上，后面无论怎么签发都不会得到正确结果。提交前还要确认 CSR 里的公钥来自将要部署的私钥，否则证书装上服务器时会立刻报密钥不匹配。

自签证书与证书检查：req x509 与 x509 的读法

自签证书是用同一把私钥既当申请者又当签发者，省去 CA 环节。它适合内网、实验环境和受控的客户端，比如客户端已经预置了这张证书或它的指纹；但它不适合任何需要陌生浏览器无条件信任的站点，因为客户端没有理由相信一个自己从未见过的签发者。

x509 参数表示直接产出证书而不是 CSR，days 给出有效期，sha256 指定签名摘要，1.1.1 的默认值已经是 SHA-256，显式写出只是为了便于审阅。三段 addext 分别在声明：这不是一张 CA 证书、这把钥匙允许做什么、这张证书允许用于服务端认证。

basicConstraints 必须带 critical，告诉校验方这是一张终端证书，不能拿去签别的证书；keyUsage 里的 keyEncipherment 只在 RSA 密钥交换的套件里有意义，如果用的是 EC 私钥，应当改成只有 digitalSignature；extendedKeyUsage 限定用途，一张只标了 serverAuth 的证书拿去当客户端证书会被拒绝。这几个扩展不是可选项，缺了它们，很多客户端会以一句含糊的握手失败结束，排查起来非常费劲。

有效期方面，公有 CA 签发的证书受浏览器策略约束，2018 年起单张证书的上限是 825 天，而浏览器厂商已经宣布要在 2020 年下半年把上限压缩到 398 天。自签证书不受这条策略约束，但仍建议控制在一年以内，配合定期轮换，缩短私钥泄露后的暴露窗口。若省略 addext，1.1.1 会套用配置文件里的默认扩展，很容易生成一张既没有 SAN、又缺 keyUsage 的裸证书，在浏览器里表现为名称无效的错误，这是自签场景最常见的翻车点。

确认私钥与证书是否配对

证书与私钥不匹配是 Nginx 启动失败最常见的原因，报错通常是 SSL_CTX_use_PrivateKey 失败或 key values mismatch。原理很简单：证书里嵌着公钥，私钥必须与这把公钥成对。命令行下不必真的做一次握手，比较两者的公钥摘要即可：

校验与链：verify 的正确用法

verify 做的是路径校验：从一张终端证书出发，沿着签发关系一路向上，直到命中一个被信任的根。它的输入只有两类：待验证的证书，以及信任锚；中间证书不在信任锚里，需要另外提供。这也是它能用来判断服务器配置是否完整的原因，把服务器发来的证书原样喂给它，缺什么一目了然。

CAfile 是信任锚集合，可以放多张根证书；untrusted 提供候选中间证书，可以给一个包含多张证书的文件，OpenSSL 会自己挑选，所以文件内部的顺序不影响结果；purpose 检查扩展用途，一张只标了 clientAuth 的证书会在这里被拒；verify_hostname 校验 SAN，必要时回退到 CN，这正是浏览器所做的事。加上 show_chain 还能看到实际构建出的链：

输出里的 untrusted 标记表示这张证书来自命令行提供而非系统信任库，不代表它有问题。看这条链就能判断中间证书是否被正确选中，尤其当手里有多个中间证书时非常有用。

四类典型失败

第一类是 unable to get local issuer certificate。含义是校验器在信任锚里找不到能签发当前证书的那一级，原因有两种：根证书没放进 CAfile，或者中间证书没通过 untrusted 提供。服务端场景下后者更常见，服务器只发了叶子证书，客户端又没有缓存中间证书，链就在这里断掉。

第二类是 certificate has expired。先看 dates 的输出，再注意比较的是 UTC 时间，服务器时钟漂移也会造成同样的报错。第三类是 certificate is not yet valid，多出现在刚签发的证书上，原因是签发机的时钟比校验机快，或者容器里的时间没有同步。

第四类是 Hostname mismatch，只有加上 verify_hostname 才会出现。先确认 SAN 里是否包含访问时使用的名字，再确认测试时是否带了正确的 SNI，后者在下一节展开。错误输出里还有一个 error 加编号、at depth 加层级的前缀，depth 表示出错的那一级在链中的位置，0 是叶子，1 是中间。这个数字直接告诉你该检查哪张证书，比错误文本本身更有价值。

Nginx 要求证书文件里叶子证书在前、中间证书在后，根证书通常不放进去，因为客户端本来就有：

顺序不能颠倒。把根证书一并塞进去虽然多数客户端能容忍，但会多传输几 KB，也让链的构建过程多一次无谓的匹配。打包完成后，用 verify 把整包当作中间证书来源验证叶子，能提前发现中间证书拿错版本的问题；如果中间证书与叶子不是同一条链上的，verify 会直接报找不到签发者。

摘要、签名、对称加密与随机数

证书之外，OpenSSL 还有几个每天都在用的子命令：算摘要、做签名、跑对称加密、取随机数。它们的共同点是参数简单，但误用之后的后果不容易察觉，所以值得单独过一遍。

摘要、签名与 HMAC

第一条只算摘要，输出一行十六进制值，用途是校验文件完整性，但它只能发现传输损坏，挡不住有意的替换，因为攻击者可以连带改掉摘要。第二条用私钥对文件签名，工具内部会先做摘要再对摘要签名，你不需要提前手动算一次；第三条用公钥验签，成功时输出 Verified OK。这里有个常见误区：如果先用 sha256sum 算出摘要，再对摘要文件签名，验签方必须知道这是对摘要的签名，否则会再哈希一次导致失败。大文件分发的正确做法是把原文和签名一起发布，让接收方自己算摘要并验签。

hmac 后面的字符串会出现在 shell 历史和进程列表里，多人共用的机器上等于把密钥写在墙上。需要稍微隐蔽一点时可以改用 mac 与 macopt 从十六进制传入，但这仍然只是遮掩，真正的生产实现应当把密钥放进配置中心或环境变量，在应用进程内计算。

对称加密：enc 的能与不能

pbkdf2 表示用 PBKDF2 从口令派生密钥与初始向量，替代了更早的、基于摘要迭代的派生方式；iter 指定迭代次数，默认是一万，口令强度一般时应当显式调高到十万量级。salt 在 1.1.1 里已经是默认行为，写出来只是让脚本读者明确知道每次加密会使用随机盐，同样的口令不会得到同样的密文。解密时必须提供完全一致的参数，否则只会得到一段乱码或者填充错误。

有两个模式要避开。第一是 ECB，用 aes-256-ecb 时相同的明文块会产生相同的密文块，图片和结构化文本的结构会直接泄露，它唯一的用途是处理固定长度的随机数据。第二是 GCM，1.1.1 的命令行 enc 对 AEAD 模式会直接报错，提示该工具不支持认证加密，所以不要指望用一条命令拿到机密性与完整性；CBC 加口令只保证机密性，密文被篡改时往往要到解密后才发现，需要完整性时应当在应用层使用 AEAD 实现，或者在密文之外再附一个独立的 HMAC 并先验后解。

直接用 K 与 iv 传入十六进制密钥和初始向量看起来很方便，但固定的初始向量会破坏 CBC 的安全性，这类参数只应在核对测试向量时使用。需要走文本通道时加 base64，体积会增加约三分之一，换来的是不再依赖二进制传输。

随机数：不要自己发明

rand 读取操作系统的密码学随机源，Linux 上最终来自内核的随机数接口，适合生成密钥、盐、会话令牌和初始化向量。第一个命令输出 64 个十六进制字符，即 256 位；第二个输出 24 字节的 Base64，去掉填充后是 32 个字符，适合放进 URL 或头部。

反面例子必须点名：shell 的 RANDOM 只有十五位，而且可以被预测；用日期加进程号拼一个字符串再取 MD5，得到的值看起来随机，实际熵极低。生成密钥这类事情，交给 rand 就够了。

把前面几节的命令组合起来，就得到一张故障对照表。遇到问题时先定位，再决定改配置还是重签证书，不要一上来就重新申请。

表格之外还有两种容易被忽略的情况。一是中间设备替换证书，比如企业网关做 TLS 检查，客户端看到的是网关自签的证书，这时无论怎么改源站都没用，需要把网关的根证书装进客户端信任库。二是时钟漂移，宿主机没有开启时间同步，证书明明有效却被判定为未生效，这类问题只能靠统一的时间同步解决。

一份可用的 Nginx 配置

证书路径指向 fullchain 而不是单张叶子证书，这是链完整的关键；私钥与证书放在同一目录但权限不同，前者 600，后者 644。协议只留 1.2 与 1.3，加密套件只留前向安全的 ECDHE 组合，prefer_server_ciphers 关掉是为了让客户端选择，这在移动端兼容性上更好。会话缓存与 stapling 是性能与隐私的加分项，stapling 需要 chain 文件作为验证 OCSP 响应的辅助链，配错时 Nginx 会静默降级，所以要回到 s_client 的 status 输出确认。

续期与轮换清单

到期前三十天启动续期，把到期时间写进监控，不要依赖日历提醒。新证书先在一台机器上验证，确认链完整、主机名匹配、私钥配对、OCSP 响应正常，再滚动到其余节点。reload 之前跑一遍配置测试，保留旧证书至少一周以便回滚。私钥建议每年轮换一次，人员变动时立即轮换；轮换后同步更新所有引用它的配置与密钥库，避免出现一半新一半旧的中间状态。

安全上有几条底线：私钥不进工单、不进聊天工具、不进版本库，一旦确认泄露就当作作废处理，重新签发并吊销旧证书；私钥权限 600、目录 700，备份也要加密；内部服务用一套私有 CA 统一签发，而不是每个服务各签一张自签证书，私有 CA 的私钥离线保存，根证书的扩展里写明它是 CA 并限制路径长度；跟随 1.1.1 的小版本更新，关注安全公告，已经结束支持的 1.0.2 不应再用于新部署。

小结

OpenSSL 的命令行本身并不复杂，难的是知道自己要什么。先确认版本与工具链，再按私钥、CSR、证书、链、探测的顺序推进，每一步都用对应的子命令把结果读回来验证，而不是签完就直接上线。证书问题九成可以归到四类：过期、链不完整、名字不匹配、私钥不配对；先用 x509 读，再用 verify 验，最后用 s_client 从客户端视角看一遍，基本不会走偏。把常用命令固化成脚本，把到期时间放进监控，比任何一次临时救火都可靠。
