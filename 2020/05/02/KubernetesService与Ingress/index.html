Kubernetes Service 与 Ingress

本文属于《Docker 与 Kubernetes》第 22/51 篇
上一篇系列目录下一篇

在 Kubernetes 里，Pod 是最小的调度单位，也是最不稳定的一个：它会被重建、被迁移、被扩缩容。本文从这个问题出发，讲清楚 Service 如何为一组 Pod 提供稳定入口，kube-proxy 如何把虚拟 IP 变成真实连接，Ingress 又如何在此之上完成七层路由与 TLS 终止。示例基于 Kubernetes 1.18 与 nginx-ingress 0.34，读完之后你应该能独立写出可用的 Service 与 Ingress，并在访问不通时按顺序定位问题。

Pod IP 为什么不能当接口用

每个 Pod 启动时由 CNI 插件分配一个 IP，这个地址只在 Pod 的生命周期内有效，出了这个边界就不可靠。原因大致有三类。

其一是重建。Deployment 滚动更新时，旧的 ReplicaSet 缩容、新的 ReplicaSet 扩容，Pod 名字和 IP 全部换掉；节点故障、容器 OOM、探针失败也都会触发重建。任何把这些 IP 写进配置文件、写进上游白名单、写进 DNS 记录的做法，都会在下一次发布时失效。

其二是调度。Pod 落在哪台节点由 scheduler 决定，而节点常常属于不同网段。同一个 Deployment 的副本可能分散在多个节点上，IP 前缀各不相同，调用方无法据此做任何稳定的假设。

其三是规模。副本数随负载变化，HPA 可以在几分钟内把两个副本扩到十个。让每个调用方自己去服务发现、自己维护后端列表、自己做健康检查，既不现实也不安全。

于是需求变得清晰：需要一个不随 Pod 生灭而变化的地址，一个能自动跟踪后端集合变化的机制，以及一个只把流量交给健康副本的过滤层。这三件事恰好对应 Service 的三个组成部分：虚拟 IP、选择器驱动的 Endpoints、就绪探针。

Service 的基本模型：选择器、Endpoints 与 ClusterIP

Service 是一层四层抽象，spec 中最重要的是 selector、ports 和 type。selector 是一组 label 匹配规则，endpoints controller 持续 watch Pod 与 Service，把匹配且处于 Ready 状态的 Pod IP 与端口写进同名的 Endpoints 对象。这里的 Ready 是关键：readinessProbe 没有通过的 Pod 不会出现在 Endpoints 里，这正是滚动更新期间流量不会打到半启动实例上的原因。

Service 的 selector 选中的 Pod，其 IP 应当与 Endpoints 的地址列表一一对应；如果 Endpoints 是空的，问题通常就出在这条链路上，而不是网络。

ClusterIP 是分配在 service CIDR 里的虚拟地址，它不配置在任何网卡上，也不响应 ARP 与 ICMP。所以 ping 一个 ClusterIP 不通，并不代表 Service 坏了；只要本机的 iptables 或 IPVS 规则存在，TCP 连接依然会被 DNAT 到后端 Pod。理解这一点，能省掉很多“ping 不通就以为服务挂了”的误判。

端口有三个层次，初学者最容易混淆：port 是 Service 对外暴露的端口，targetPort 是容器实际监听的端口，containerPort 只是 Pod 模板里的声明性信息，并不改变容器行为。targetPort 可以写数字，也可以写容器端口名；写名字时，Pod 的 ports[].name 必须与之对应，否则 Endpoints 里不会出现该端口。如果 Service 干脆不写 selector，controller 就不会为它生成 Endpoints，需要手工创建同名 Endpoints 指向外部地址；这种写法能把集群外服务纳入统一入口，代价是失去了自动健康检查。

当后端规模很大时，单个 Endpoints 对象会变得非常庞大，任何变更都要把整个对象推给所有节点上的 kube-proxy。从 1.17 起进入 beta 的 EndpointSlice 把地址按每片 100 个切开，1.18 的集群里已经能看到 endpointslice 对象；不过日常排障时，大家还是习惯先看 Endpoints。

还有一种特殊写法：clusterIP: None，也就是 headless Service。它不分配虚拟 IP，DNS 直接返回所有后端 Pod 的 A 记录，由客户端自己做负载均衡或连接复用。StatefulSet 依赖它为每个副本提供固定域名，例如 web-0.web.default.svc.cluster.local。无状态服务一般用不到它，但需要直连每个实例做分片或主从识别的场景离不开它。

数据包如何到达 Pod：kube-proxy 与四种类型

ClusterIP 之所以能被访问，靠的是每台节点上的 kube-proxy。它 watch Service 与 Endpoints 的变化，把转发规则写进内核；真正处理数据包的是 netfilter 或 IPVS，kube-proxy 自己不在数据路径上。这是理解 Service 性能与排障方式的前提。

iptables 模式下，kube-proxy 会建立 KUBE-SERVICES、KUBE-SVC-xxx、KUBE-SEP-xxx 这样一组链。请求进入后先匹配目的地址，命中某个 Service 就跳转到对应的 KUBE-SVC 链，再按概率在各后端之间选择一条 KUBE-SEP 链，执行 DNAT 改写目的地址。选择结果被 conntrack 记住，同一连接的后续报文不会再重新选择，所以它不是严格意义上的负载均衡器，而是按连接分发。规则数量随 Service 与 Endpoints 的乘积增长，几千个 Service 的集群里，规则同步会明显变慢。

IPVS 模式用内核里的哈希表代替线性链，查找复杂度与规模基本无关，还支持 rr、lc、sh 等调度算法，可以通过 kube-proxy 配置里的 ipvs.scheduler 指定。它需要节点加载 ipvs 相关内核模块并安装 ipset，NodePort 与 SNAT 部分仍然借助 iptables 完成。规模上到数百个 Service 之后，IPVS 的优势就比较明显了。

按暴露范围，Service 分为四种类型。ClusterIP 只供集群内部访问；NodePort 在每个节点上打开同一个高端口，默认范围 30000 到 32767，外部用节点 IP 加端口即可访问；LoadBalancer 在 NodePort 之上向云厂商申请一个外部负载均衡器，地址回填到 status.loadBalancer 里；ExternalName 则不做任何代理，只在 DNS 层返回一条 CNAME，适合把集群外的数据库之类资源伪装成集群内服务。

一次典型的集群内访问是这样的：客户端 Pod 先向 CoreDNS 查询 web.default.svc.cluster.local，拿到 ClusterIP；然后向这个虚拟地址发起连接，报文进入本节点的规则链，被 DNAT 成某个 Pod 的 IP 与 targetPort；最后由 CNI 负责的路由把包送到目标节点或本机 veth。回包沿着 conntrack 记录反向改写，客户端始终以为自己只在和那个虚拟 IP 通信。

flowchart LR
  A[客户端 Pod] --> B[DNS 解析服务名]
  B --> C[ClusterIP 虚拟地址]
  C --> D[kube-proxy 规则 DNAT]
  D --> E[后端 Pod]
  E --> F[回包按 conntrack 改写]

从集群外经 NodePort 进来时，默认策略下除了 DNAT 还会做一次 SNAT，后端 Pod 看到的源地址是节点 IP，真实客户端 IP 就丢了。把 Service 的 externalTrafficPolicy 设为 Local 可以保留源 IP，代价是流量只会转给本节点上的 Pod，节点间不再二次转发；配合 healthCheckNodePort，外部负载均衡器只会把节点标记为健康当且仅当该节点上有可用后端，从而避免请求打到没有副本的节点。需要做基于 IP 的限流或审计时，这个选项几乎是必须的。

如果业务依赖会话粘性，可以设置 sessionAffinity: ClientIP，默认超时 10800 秒。它按源 IP 做哈希，在 NAT 后面大量客户端共享出口 IP 时会严重倾斜，所以更常见的做法是在 Ingress 层用 cookie 做会话保持，或者在应用侧把状态外置到 Redis。

Service 不通时，按这个顺序排查

Service 访问失败的原因大多集中在一个很小的范围内，按层排查比乱试有效得多。

第一步看 Service 与 Endpoints 是否对得上。kubectl describe svc web 能看到 Selector 与 Endpoints 两栏，Endpoints 为空时先跑 kubectl get pods –show-labels，确认标签拼写、命名空间、以及 Pod 是否真的 Ready。探针失败、镜像拉不起来、副本数为零，都会让 Endpoints 保持为空，而 Service 本身看起来一切正常。

第二步看端口。Service 的 port、targetPort 与容器的实际监听端口必须能串起来。targetPort 写成名字时，Pod 的 containerPort 名称要一致；容器里监听 127.0.0.1 而不是 0.0.0.0 也是一个高频错误，此时从 Pod 内部 curl 自己通，从别的 Pod 访问就不通。

第三步区分 DNS 与连通性。在业务 Pod 里执行 nslookup web.default.svc.cluster.local，如果解析失败，检查 /etc/resolv.conf 里的 search 域与 ndots 设置，以及 CoreDNS 是否正常；如果解析成功但连接超时，问题就在转发或后端。此时可以在 Pod 内直接 curl Pod IP 与端口，绕过 Service，快速判断是应用没起来还是规则没生效。

第四步看节点上的规则。确认 kube-proxy 的运行模式，再用 iptables-save 过滤 KUBE-SERVICES，或用 ipvsadm -Ln 查看虚拟服务与真实服务器列表，比对是否有对应的条目。规则缺失通常意味着 kube-proxy 异常或它连不上 apiserver，规则存在但计数不增长，则更像 conntrack 表满或后端确实不可达。

还有一个很适合做分界的工具是 kubectl port-forward。它绕过 Service，把本地端口直接映射到某个 Pod 的端口：转发之后应用正常，说明问题在 Service 或其后的规则；转发也不通，问题就在容器本身。它不能替代全链路验证，但能把排查范围迅速砍掉一半。

最后才考虑网络策略与 CNI。如果集群启用了 NetworkPolicy，一条默认拒绝就可能把来自其他命名空间的流量全部挡掉，这类问题的现象是 DNS 正常、TCP 超时，和规则缺失很像，需要用策略对象与 CNI 的日志来区分。网络插件本身的行为差异不在本文范围内，排查时把它放到确认策略之后的最后一步即可。

Ingress：七层路由与 TLS 终止

Service 只认 IP 和端口，属于四层。要在同一个入口上按域名和路径分流、集中配置证书、做路径重写与限流，就需要 Ingress。它描述的是“什么样的请求应该转到哪个 Service”，本身并不是代理进程，真正干活的是 Ingress controller。以 nginx-ingress 0.34 为例，它 watch Ingress、Service、Secret 等对象，渲染出 nginx.conf 并触发 reload，数据面仍然是普通的 Nginx。

API 版本必须先说清楚，这是 2020 年最容易踩的坑。Kubernetes 1.18 里 Ingress 的正式入口是 networking.k8s.io/v1beta1，extensions/v1beta1 仍被 apiserver 提供但已标记弃用；networking.k8s.io/v1 要到 1.19 才可用，按官方计划随 2020 年 8 月的 1.19 发布，届时 pathType 变为必填，backend 的结构也会调整。本文的清单全部按 v1beta1 书写，迁移留到集群升级时再做。

路由规则由 host 与 path 两部分组成。host 精确匹配域名；path 在 v1beta1 中没有 pathType 字段，匹配语义由控制器决定，nginx-ingress 默认按前缀匹配，并且更长的路径优先，因此 /api 会先于 / 命中。多个 Ingress 声明同一个 host 时，控制器会把它们的路径合并到同一个 server 块里。

TLS 通过 Secret 提供。spec.tls 中声明 hosts 与 secretName，Secret 必须是 kubernetes.io/tls 类型且包含 tls.crt 与 tls.key。controller 用它完成 443 上的握手，随后把请求以明文 HTTP 转发给后端 Service；如果后端自己也说 HTTPS，需要把 backend-protocol 注解设为 HTTPS。证书轮换只需更新 Secret，控制器会自动重载。

关于控制器选择，0.32 与 0.34 这一代主要靠注解 kubernetes.io/ingress.class: nginx 声明归属，集群里装了多个控制器时，这个注解决定了谁来处理。1.18 引入了 IngressClass 资源以及 spec.ingressClassName 字段，方向是让注解退场；两种写法在这一代可以共存，但同一个 Ingress 不要给出互相矛盾的声明。

注解是 nginx-ingress 表达能力的来源：rewrite-target 配合正则改写路径，ssl-redirect 与 force-ssl-redirect 控制跳转，proxy-body-size 调整上传大小上限（默认 1m），proxy-read-timeout 调整长连接与慢接口的超时。需要 WAF、限流、灰度时，可以在这一层用 ModSecurity、limit_req 或 canary 注解实现；但入口层通常是无状态多副本的，计数器不共享，真正严格的限流更适合放在最外层的负载均衡或网关上，Ingress 承担粗粒度的第一道拦截即可。

部署之后，如果 ADDRESS 长期为空，几乎可以断定控制器没装，或者注解里的 class 与控制器不匹配；地址有了但返回 503，多半是 Service 名字或端口写错，控制器在后端找不到可用的 Endpoints；返回 404 则是 host 或 path 没有命中规则，注意 v1beta1 下路径结尾是否带斜杠会影响前缀匹配结果。滚动更新期间偶发 502，通常是 readinessProbe 缺失或阈值过松，旧 Pod 已停止监听却仍留在 Endpoints 里。

混合协议是另一个常见坑：Ingress 终止 TLS 后以 HTTP 访问后端，应用若依据 X-Forwarded-Proto 生成跳转链接，需要控制器正确传递该请求头；而应用自身再强制跳转 HTTPS，就可能与入口的 ssl-redirect 叠加成重定向循环。把跳转统一放在一处，是更省事的选择。

小结

Service 解决的是“后端会变、地址不能变”的问题，核心是选择器、Endpoints 与虚拟 IP 三件套；数据面由 kube-proxy 写入的 iptables 或 IPVS 规则完成，按连接而不是按请求分发。Ingress 在此之上补足七层能力，按 host 与 path 路由并终止 TLS，但它必须依赖一个实际安装的控制器，版本上要记住 1.18 仍然是 v1beta1。排障的顺序应当是标签与 Endpoints、端口映射、DNS 与直连、节点规则，最后才是网络策略与插件。写清单时把 readinessProbe、命名端口和路径结尾斜杠处理好，大部分问题在上线前就能避免。
