MySQL 高可用架构

“主从配好了”和“高可用”之间，隔着检测、决策、切换、回切这一整条链路。本文从 RPO 与 RTO 这些可度量的目标讲起，依次分析常见拓扑、异步与半同步的取舍、MHA 与 Orchestrator 两代切换器、MGR 与 ProxySQL 的分工，以及 VIP 漂移背后的脑裂风险，最后给出一套可落地的架构与故障复盘清单。读者应已了解主从复制的基本用法，读完后能够判断自己的系统在故障时会丢多少数据、多久能恢复，以及哪些环节其实从未被验证过。

高可用到底要保证什么

很多团队说“我们的 MySQL 是高可用的”，依据是配了一主一从、装了 MHA。但只要追问三句就会露馅：主库挂掉后多久能恢复写入？会丢多少事务？切换过程中会不会出现两个主库？高可用不是一组组件的堆叠，而是一串可以被度量、可以被演练的承诺。

本文把这串承诺拆成六个指标。第一是 RPO（Recovery Point Objective，恢复点目标），指故障发生时允许丢失的数据量。异步复制下，RPO 大致等于故障瞬间的复制延迟；半同步复制下，只要至少有一个从库确认过事务，RPO 就可以逼近 0，但前提是切换时选中了那个已确认的从库，而不是一个落后的从库。可见 RPO 不是某个参数，而是复制模式与选主策略共同决定的结果。

第二是 RTO（Recovery Time Objective，恢复时间目标），即从故障发生到业务恢复写入的总时长。第三是故障检测时间，它虽然包含在 RTO 里，却值得单独拿出来看，因为绝大多数“切换很慢”的真实原因是“发现得很晚”。第四是切换耗时，包含选主、提升、改写路由、应用重连这一串动作。第五是数据一致性，即提升后的新主库与旧主库之间差了多少事务，差的那部分是丢弃还是补齐。第六是脑裂防护，系统能否保证任意时刻只有一个节点在接受写入。

还有一个常被忽略的维度是计划内维护。主库升级、换机型、加索引、扩容都该走一次可控切换；如果日常维护只能靠停服加手工操作，计划外故障时的表现只会更差。本文建议把目标写成一句可执行的话，例如“交易库 RPO 为 0、RTO 不超过 60 秒、每月演练一次计划内切换”。要注意这里的数字是设计目标，而不是任何产品的承诺值，具体取值必须按业务能忍受的损失来定：一年 99.99% 的可用性约等于 52 分钟停机，99.999% 只剩 5 分钟，而一次包含人工确认的切换，光是沟通成本就可能吃掉其中大半。

把 RTO 拆成四段

RTO 若只当成一个数字，就无法定位瓶颈，本文把它拆成检测、决策、执行、业务恢复四段。

检测段是从真实故障到监控系统确认故障，取决于探测间隔与重试次数。探测太敏感会误判，一次网络抖动就触发切换；太迟钝则白白拉长停机。常见的折中是心跳间隔 1 秒、连续失败 3 次判定，也就是 3 秒左右的检测窗口。决策段是选择哪个从库接任，需要比较复制位点、机房位置、硬件规格，必要时还要人工确认。执行段是提升从库、把其他从库指向新主、摘除旧主、迁移 VIP 或更新入口配置。业务恢复段最容易被低估：连接池里全是失效连接，DNS 缓存还没过期，重连风暴把新主库的连接数打满，这些都不在数据库的掌控之内。

四段各有超时与责任人，任何一段缺了兜底，整体目标就只是纸面数字。下一节回到复制本身，因为选主逻辑都建立在“位点可比较”这个前提上。

复制地基与拓扑形态

复制的最小模型

异步复制的链路很短：主库的 binlog dump 线程把二进制日志推给从库，从库的 IO 线程写入本地 relay log，再由 SQL 线程回放。位点以文件名加偏移量表示，开启 GTID 后则表现为一个已执行事务集合。这两套坐标决定了从库“追到了哪里”。

GTID 的价值在于切换。传统位点切换要求人工比对 Master_Log_File 与 Read_Master_Log_Pos，一旦某个从库执行过额外事务，补齐就非常麻烦；GTID 下从库只需声明 MASTER_AUTO_POSITION=1，主库会自动补发它缺少的事务。半同步复制则在提交路径上加了一道确认：主库等待至少 N 个从库回复收到 relay log 后才向客户端返回成功，MySQL 5.7 起默认的 AFTER_SYNC 模式让确认发生在存储引擎提交之前。

复制的线程模型、日志格式与延迟成因属于另一个话题，本文不再展开。这里只需要记住两个事实：第一，位点是可比较的，因此能判断谁更“新”；第二，relay log 里的事务可能尚未执行，因此“收到了”不等于“应用了”。后文所有选主逻辑，都是在这两个事实上做文章。

四种拓扑

一主一从最简单：主库一挂，从库就是唯一候选，没有选择困难，但也没有冗余，从库本身出问题同样意味着停服。

一主多从在生产中更常见。多个从库分担读流量，切换时有候选可选，代价是要比较位点：谁的 Executed_Gtid_Set 更完整，谁就更有资格接任。如果从库分布在多个机房，还要在“位点最新”和“同机房延迟最低”之间做取舍，这正是 Orchestrator 那类工具存在的理由。

双主加 VIP 曾经非常流行。两台机器互为主从，VIP 挂在其中一台，应用只连 VIP。切换时把 VIP 漂到另一台，再确认它的复制已经追平，看起来只需几秒钟。这种形态把“谁可写”的判定交给了网络层，而网络层并不理解数据库：VIP 漂移失败、或者旧主库的网络还活着却已经脱离集群，都会立刻产生两个可写节点。双主还需用 auto_increment_increment 与 offset 错开自增，即便如此，唯一键冲突和更新覆盖依然可能发生。因此双主的关键不在于“双向复制怎么配”，而在于 fencing，即如何确保被放弃的那一方真的不能再写。

    VIP --> A["db-a 可写"]
    VIP -. "故障后漂移" .-> B["db-b 只读"]
    A -- "复制" --> B
    B -- "复制" --> A

级联复制把从库再挂到从库下面，用于降低主库的 dump 线程数与跨机房带宽压力。代价是延迟逐层叠加，中间节点故障会让整条下游链路失联，而且级联节点通常不是好的切换候选。多源复制自 5.7 起支持多 channel，常用于把多个业务库汇总到报表库或灾备库，但它引入了写冲突与多套位点，一般不作为在线交易系统的高可用形态。

拓扑没有绝对优劣，只有与故障域是否匹配。真正需要提前回答的是：主库所在的机柜、交换机、云可用区整体失效时，剩下的节点还能不能凑出一个完整的主库。

一致性谱系：异步、半同步与组复制

讨论数据丢失前，先把“提交成功”的含义说清楚。客户端收到提交成功，只代表主库认为事务完成了，不代表从库也拿到了它。不同复制模式的区别，就在于主库在返回成功之前，愿意等谁、等多久。

异步复制不等任何人。主库写 binlog、提交、返回，dump 线程随后把日志推出去。因此异步复制的丢失窗口等于故障瞬间的复制延迟：主库在 14:00:00 崩溃，从库最后应用的事务停在 13:59:57，那么这三秒内提交的事务全部消失。它的优点是主库提交延迟不受从库影响，从库宕机或网络抖动都不会拖慢写入，这也是它仍是默认选择的原因。

半同步复制在主库返回前插入一次等待：至少 N 个从库确认收到 relay log 之后，事务才算提交成功。MySQL 5.7 默认的 AFTER_SYNC 语义把等待放在存储引擎提交之前，因此客户端看到成功的事务，至少已经落在某个从库的 relay log 里；如果主库在等待期间崩溃，客户端收到的是失败而不是“成功但丢失”。相关参数是 rpl_semi_sync_master_enabled、rpl_semi_sync_master_timeout（默认 10000 毫秒）与 rpl_semi_sync_master_wait_for_slave_count。要注意两件事：一是从库确认的是“收到日志”，不是“执行完毕”，切换后新主仍需回放 relay log 中的事务；二是超时之后主库会自动退化为异步，Rpl_semi_sync_master_status 变成 OFF，此时丢失窗口重新打开，必须有告警盯着这个状态。

半同步的代价是每次提交多一次网络往返：跨机房时就是几毫秒，高并发小事务的吞吐会明显下降；组提交能合并等待，但消除不了 RTT 的物理下限。因此半同步通常只在同城机房开启，跨城节点用异步。

组复制把确认对象从“某个从库”换成了“组内多数派”。事务在主库执行后，把写集广播给组内成员，多数派认证通过才提交；只要多数派存活，已经提交的事务就不会因为单点故障而丢失。代价是写路径上多了组通信，对网络延迟和稳定性非常敏感，组内任何一个慢节点都可能通过流控拖慢整体。

模式 提交条件 典型丢失窗口 主库延迟影响
异步复制 本地提交 等于复制延迟 几乎无
半同步 至少 N 个从库确认收到日志 超时退化为异步后重新出现 增加一次 RTT
组复制 组内多数派认证通过 多数派存活时接近 0 受最慢成员与流控影响

还需要区分“数据库已提交”和“从库可读”。读写分离下，刚写入的数据立刻去从库读，很可能读不到。若业务不能接受，可以让从库在会话开始时阻塞等待特定 GTID：客户端带上主库返回的 gtid_executed，在从库执行 SELECT WAIT_FOR_EXECUTED_GTID_SET('...', 1)，最多等 1 秒。这是 5.7 就提供的原语，代价是把复制延迟转嫁成了读请求的等待时间。

切换器的两代：MHA 与 Orchestrator

模式决定了丢多少数据，切换器决定了多久能恢复、以及会不会切错。MHA 与 Orchestrator 代表了两代思路：前者以配置文件和 SSH 为中心，后者把拓扑当成一份持续演化的状态。

MHA 0.58 的工作方式

MHA 由 manager 节点和部署在每台 MySQL 主机上的 node 包组成。manager 通过 SSH 免密登录各节点，用复制账号读取状态，不需要在数据库里装任何插件。配置写在 app1.cnf 里，每个 [serverN] 段落声明一台机器的地址、端口以及是否可作为候选主库：

上线前用 masterha_check_ssh 验证 SSH 互通，用 masterha_check_repl 验证复制链路、账号权限与 master_binlog_dir 是否配置正确。后者是排障时最有用的命令，它会把每台从库的 SHOW SLAVE STATUS 汇总并给出判断，失败原因通常写得很直白。日常用 masterha_check_status 确认 manager 在跑，用 masterha_master_switch --master_state=alive 做计划内切换。

故障切换的流程大体如下：manager 以 ping_interval 探测主库，连续失败判定为宕机；随后尝试 SSH 到旧主，把尚未发送的 binlog 抢救出来；同时在候选从库中比较 relay log 的位点，选出最接近旧主的那台，把抢救到的差异日志应用到它上面；然后提升为新主、关闭只读、让其余从库指向新主；最后调用 master_ip_failover 脚本完成 VIP 迁移。旧主恢复后不会自动回归，需要人工把它重建为从库。

这套流程在 5.6/5.7 时代支撑了大量生产系统，但局限也很清楚。manager 自身是单点，通常要再用 keepalived 给它做一层主备；拓扑信息来自静态配置，新增从库必须改配置文件；VIP 迁移依赖自定义脚本，脚本写错就等于没有切换；最关键的是它没有 fencing 能力，当旧主只是网络分区、SSH 也连不上时，manager 既救不出日志，也无法确保旧主停止写入。此外，MHA 0.58 之后基本停止演进，对 MySQL 8.0 的适配并不完整，这也是它在 8.0 普及后逐渐退场的原因。

Orchestrator 3.x：把拓扑当成状态

Orchestrator 的思路与 MHA 相反：不维护一份手写配置，而是让工具自己去发现问题。每台 MySQL 主机上运行一个 agent，orchestrator 进程周期性拉取 SHOW SLAVE STATUS 与 SHOW MASTER STATUS，据此拼出一张有向无环图。谁是谁的从库、复制是否中断、位点是否一致，全部实时可见，新增从库不需要改任何配置。

自动切换分为检测、分析、恢复三步。检测既看 agent 上报，也看主库心跳；分析阶段把故障归类，例如 DeadMaster、DeadMasterAndSomeSlaves，不同类别对应不同的恢复策略；恢复阶段选出候选从库，优先同机房、位点最靠前、且没有被标记为不可提升的节点，然后提升、改写其余从库的复制关系，并把旧主登记为待修复状态。每一步都写进审计表，事后可以完整回放“为什么选了这台”。

它的可定制点集中在钩子上：PreFailoverProcesses、PostFailoverProcesses、PostUnsuccessfulFailoverProcesses 等，用外部脚本完成 VIP 迁移、DNS 更新、通知和工单。计划内维护则用 graceful-master-takeover，先让候选从库追平 GTID，再切换，比直接漂 VIP 安全得多。

Orchestrator 自身也可能成为单点，因此 3.x 引入了基于 raft 的多节点部署：多个 orchestrator 组成共识组，同一时刻只有一个 leader 执行恢复动作，配置存在 raft 里而不依赖共享数据库。它的短板是拓扑学习依赖网络可达，跨机房分区时两个分区可能各自认为掌握真相，因此仍需配合 fencing 与单一写入入口。

Group Replication：把共识写进数据库

前面所有方案都在数据库外面做决策：谁活着、谁该当主、日志够不够。MySQL 5.7.17 起提供的组复制（Group Replication，MGR）把这件事挪进了数据库内部，用组通信与认证机制替代外部脚本。它在 8.0 上被进一步完善，是官方主推的原生高可用方案。

一个组由若干成员组成，成员间通过组通信端口互连，事务提交前把写集广播出去，由所有成员做冲突认证。组的可用性取决于多数派：5 个成员能容忍 2 台故障，3 个成员只能容忍 1 台。当存活成员少于多数派时，剩余节点会进入 ERROR 状态并拒绝写入，宁可停服也不产生分叉，这正是 MGR 相对双主的最大优势。

单主模式是默认形态，组内选出一个主节点接受写入，其余成员只读；主节点故障后由组内重新选举，8.0 可以通过成员权重影响优先级。多主模式允许所有成员同时写入，靠认证机制检测冲突，适合分片写入或跨地域低延迟写入的场景，但应用要能接受冲突事务被回滚，运维复杂度也明显更高。

一致性级别是 MGR 最容易被误解的部分。默认的 EVENTUAL 不等待，读请求可能读到旧数据；BEFORE_ON_PRIMARY_FAILOVER 只在新主接管时等待积压事务应用完，避免切换后立刻读到“倒退”的数据；BEFORE 与 AFTER 分别要求事务在执行前或提交后等待组内同步，BEFORE_AND_AFTER 最严格也最慢（这几个级别从 8.0.14 起提供）。级别越高，一致性越强，吞吐越低，这条曲线没有免费的午餐。

MGR 的运维门槛不低：只支持 InnoDB，表必须有主键，必须开启 GTID 与 ROW 格式，大事务会触发流控甚至被拒绝，跨城部署时网络抖动会直接表现为提交变慢。更重要的是，MGR 只保证组内的数据一致，不解决客户端连哪里：主节点换了，应用的连接串并不会自动跟着变，仍然需要 ProxySQL、MySQL Router 或 VIP 来做入口切换。

ProxySQL：把入口与拓扑解耦

无论后端是 MHA、Orchestrator 还是 MGR，应用都不应该知道主库的 IP。让应用连一个稳定的中间层，由中间层根据后端状态决定把语句发到哪里，这就是 ProxySQL 2.x 解决的问题。它监听两个端口：6033 提供 MySQL 协议给业务，6032 是管理接口，用 MySQL 客户端就能操作。

mysql_replication_hostgroups 是关键：ProxySQL 定期检查每台后端的 read_only 值，为 0 的放进写组，为 1 的放进读组。主库切走、新主执行 SET GLOBAL read_only=0 之后，流量会自动迁移，中间层的配置不需要改。如果后端是 MGR，则改用 mysql_group_replication_hostgroups，它额外跟踪成员状态，还能通过 max_writers 限制写组只允许一个成员。

健康检查决定故障感知的速度：mysql-monitor_ping_interval 控制连通性探测，mysql-monitor_read_only_interval 控制 read_only 轮询，两者默认都是 10 秒量级，要更短的 RTO 就得调小，同时接受更多探测流量。weight 用于加权读流量，status 可置为 OFFLINE_SOFT 做优雅下线。

ProxySQL 只能感知“后端是否可写”，不能替你做选主。主库真的宕机时，从库的 read_only 仍是 1，写组会变空，此时写请求应当直接报错而不是回退到读组。这条规则必须写死，否则一次主库故障就会变成一次大规模写错节点事故。

VIP、fencing 与脑裂

VIP 是最古老的入口方案。keepalived 通过 VRRP 协议在主备之间竞选，持有 VIP 的节点定时发送通告，备节点收不到通告就认为对方已死，接管 VIP 并发送免费 ARP 刷新交换机与主机的 ARP 缓存。

问题在于 VRRP 只判断“网络与进程是否活着”，不理解数据库状态。主库的 mysqld 还在跑、复制却已断开，健康检查照样通过，VIP 不会漂移；反过来，一次交换机抖动让备节点收不到通告，备节点就会认为主库已死，抢走 VIP 并开始接受写入，而旧主仍然活着、仍然可写。两个主库同时接受写入，自增 ID 交叉、更新互相覆盖，事后几乎无法合并，这就是脑裂。

因此双主加 VIP 的核心不是怎么漂移，而是 fencing：在允许新主写入之前，必须确保旧主绝对写不了。常见手段分三层。基础设施层用电源管理接口强制关机，或者调用云 API 停止实例，这被称为 STONITH；网络层关闭交换机端口或用 iptables 丢弃 3306 入站；数据库层执行 SET GLOBAL super_read_only=1、撤销写权限、KILL 掉所有连接。顺序必须是先隔离、再提升：如果隔离失败，宁可不切换，让业务短暂不可写，也好过产生两个分叉的数据库。

super_read_only 是 5.7 起提供的开关，它比 read_only 更彻底，连具备 SUPER 权限的账号也无法写入，因此适合作为降级动作。配合 ProxySQL 按 read_only 分组的策略，效果会更好：任何没有被明确提升的节点都保持 read_only=1，即使它还活着、还能被连上，也拿不到写流量。单一可写端点加上强制的只读默认值，比任何自动切换脚本都更能防住脑裂。

监控、演练与故障复盘

架构搭好只是开始：切换能否在 60 秒内完成，取决于监控是否早发现、预案是否演练过、旧主回归时是否有人知道怎么处理。

观测什么

SHOW SLAVE STATUS 是最基础的观测入口，但只有几个字段真正有用：Slave_IO_Running 与 Slave_SQL_Running 是否都是 Yes，Retrieved_Gtid_Set 与 Executed_Gtid_Set 的差集有多大，以及 Seconds_Behind_Master 是否在增长。最后一个字段要谨慎对待：它由从库当前时间与正在执行事件的时间戳相减得到，主库长时间无写入时显示 0，大事务回放时又长时间不更新，因此既可能低估也可能高估真实延迟。

更可靠的做法是心跳表。Percona Toolkit 的 pt-heartbeat 在主库上按固定间隔更新一行时间戳，从库读出这行再与本地时间比较，得到的延迟与主库写入节奏无关：

告警要分层：复制线程中断超过 60 秒、心跳延迟超过业务阈值、半同步状态掉成 OFF、切换器进程消失（MHA 的 manager、Orchestrator 的 leader），这四类都应直达值班。切换器自身失活是最隐蔽的一类，数据库一切正常，直到真正需要切换的那一刻才发现没人干活。

演练与切换后校验

计划内切换是最好的演练：低峰期把入口指向从库，记录检测、决策、执行、应用恢复各段耗时，并核对应用日志的报错数量。演练要覆盖“切换后立刻回切”，因为回切往往比切换更容易出错。

切换完成后必须校验一致性。pt-table-checksum 以块为单位计算主从两侧的校验和，结果写入一张结果表，再用 pt-table-sync --print 查看差异语句而不是直接执行：

这条命令对主库有实际压力，--chunk-time 与 --max-load 是必须设置的刹车。校验发现的差异要区分类型：切换瞬间丢失的少量事务可以接受，结构性的分叉则说明曾经发生过双写。

六类常见故障

网络分区最危险：机房之间链路断了，各自内部都正常，双主结构下备节点会抢走 VIP，旧主仍在服务，双写就此产生。处置原则是先确认隔离，再决定是否切换。

relay log 损坏通常表现为 SQL 线程报 1594 或校验失败，多见于磁盘写满、非正常关机。不要用 sql_slave_skip_counter 跳过，那会在 GTID 模式下留下空洞；正确做法是 RESET SLAVE ALL 之后以 MASTER_AUTO_POSITION=1 重新建立复制，让主库补齐缺失事务，实在补不齐就从备份重建。

GTID 空洞与多余事务经常一起出现。旧主在分区期间执行过本地事务，带着一组新主没有的 GTID 回归，此时它既不能直接当从库，也绝不能提升为主库。判断方法是比较两边的 gtid_executed：如果旧主包含新主没有的事务，唯一安全的路径是重建。

切换循环指的是主库恢复后又被选为主、随后再次故障，来回抖动。需要在切换器里设置冷却时间、降低故障节点的提升优先级，并提供“禁止自动切换”的开关。

旧主回归要当成一次数据迁移来处理：先以只读方式挂载、比对校验和、决定是补齐还是重建，确认无误后再加入读组。

连接风暴则发生在应用侧。主库切换的瞬间，成千上万个连接同时失效并重连，新主库的 max_connections 被打满，健康检查随之失败，触发第二次切换。缓解手段包括连接池的指数退避与随机抖动、提高 max_connect_errors、切换前预热连接，以及让应用在重连失败时快速失败而不是无限重试。

一套可落地的架构

把前面的零件拼起来，一套中等规模、可运维的架构大致如下：应用只连 ProxySQL 的 6033 端口，ProxySQL 后面是同城三节点，一主两从，跨城一个异步从库只做灾备；切换由 Orchestrator 决策，VIP 只用于运维通道而不承载业务写入。

flowchart TD
    APP["应用集群"] --> PX["ProxySQL 6033"]
    PX -->|"写：hostgroup 10"| M["db-a 主库 同城"]
    PX -->|"读：hostgroup 20"| S1["db-b 从库 同城"]
    PX -->|"读：hostgroup 20"| S2["db-c 从库 同城"]
    M -->|"半同步"| S1
    M -->|"半同步"| S2
    S1 -->|"异步 级联"| DR["db-d 灾备 跨城"]
    O["Orchestrator raft 三节点"] -.->|"拉取拓扑"| M
    O -.-> S1
    O -.-> S2
    O -->|"钩子：改 hostgroup 与通知"| PX

故障发生时的决策路径是固定的：Orchestrator 在 10 秒内判定主库不可达；若属于网络分区且无法隔离旧主，则不自动切换，只告警；确认可切换后，在 db-b 与 db-c 中选位点更靠前的一台，先对旧主执行 super_read_only=1，再提升新主并关闭其只读；随后改写另一台的复制指向，由钩子通知 ProxySQL；应用侧连接池在退避后重连，写流量落到新主。跨城 db-d 是异步且延迟较大，只作为最后手段，不参与自动选主。

这套架构里没有双主，也没有让 VIP 决定谁可写：任何时刻只有一个节点具备写权限，脑裂从架构上被排除，而不是靠脚本祈祷。

小结

高可用是一组可度量的承诺，而不是组件的堆叠。RPO 由复制模式与选主策略共同决定，RTO 则要拆成检测、决策、执行、业务恢复四段分别优化。拓扑选择要与故障域匹配，双主加 VIP 看似简单，却把“谁可写”交给了不理解数据库的网络层。MHA 适合 5.7 时代的小规模部署，Orchestrator 用拓扑发现与钩子把切换做成了可审计的流程，MGR 把一致性交给组协议，ProxySQL 则负责让应用与拓扑解耦。无论选哪一套，判断标准只有三条：是否只有一个可写端点、旧主能否被真正隔离、以及这套流程最近一次演练是什么时候。
