HTTP/2 部署实践

HTTP/2 在 2015 年就成为 RFC，但真正让它普及的，是近几年浏览器与 CDN 的普遍支持，以及 gRPC 在微服务里的落地。本文不从协议史讲起，而是从一次“配置里明明写了 http2、DevTools 里却还是 http/1.1”的排查出发，把 Nginx 上的部署、ALPN 与证书、gRPC 回源、Server Push 的取舍、调优参数和测量方法串成一条可执行的路径。读完本文，你应该能独立完成一次灰度上线，并且知道出问题时先看哪几个地方。

HTTP/2 改了什么，以及它没改什么

HTTP/2 由 RFC 7540 定义，2015 年 5 月发布，配套的头部压缩规范是 RFC 7541（HPACK）。它没有改动 HTTP 的语义：方法、状态码、缓存规则、Cookie 都还是原来的样子，改的是这些语义在一条连接上的表达方式。笔者把它概括为“四个变化、一个减法”。

第一个变化是二进制分帧。HTTP/1.1 的报文是纯文本，靠首行、空行和 Content-Length 或分块编码划定边界；HTTP/2 把一切切成帧，每帧带 9 字节头，包含长度、类型、标志位和 31 位的流标识符。常见的帧类型有 HEADERS、DATA、SETTINGS、WINDOW_UPDATE、RST_STREAM、GOAWAY、PRIORITY 与 PUSH_PROMISE。文本协议便于人读，却让解析器要处理空白、大小写和歧义；定长帧头把边界判断变成读几个字节的事，这是后面所有特性的前提。

第二个变化是流与多路复用。一条 TCP 连接上可以并存许多条流，每条流是一次独立的请求—响应交换，用一个整数标识；不同流的帧可以交错发送，接收端按流标识重新组装。于是“一个页面几十个资源，要么排队、要么多开连接”的约束消失了。

第三个变化是头部压缩。HPACK 维护一张 61 项的静态表和一张随连接演进的动态表，重复出现的头部（:method、:path、user-agent、大段 Cookie）第二次只需发一个索引，字面量再用哈夫曼编码压缩。一个典型页面能省下可观的头部字节，这在移动网络下比在机房内更明显。

第四个变化是流量控制与优先级。流量控制有连接级和流级两个窗口，接收方通过 WINDOW_UPDATE 发放信用，和 TCP 的滑动窗口叠加生效；优先级用依赖树加权重描述“谁先发”，但各家实现差异很大，Chrome 与 Nginx 都没有完整实现 RFC 里的优先级树，实际效果不要期待过高。

所谓减法，是指域名分片、雪碧图、把十几个 JS 合并成一个大文件这些“绕过并发连接数限制”的手段不再必要。合并文件还会牺牲缓存粒度：改一行代码就让整个 bundle 失效。当然，减法不等于立刻拆掉，历史包袱要按缓存策略逐步处理。

需要强调的是，HTTP/2 没有解决 TCP 层面的队头阻塞，也没有让 TLS 变得可有可无。主流浏览器只在 TLS 上启用 h2，明文 h2c 基本只出现在内网。这两点决定了后文的配置与排障思路。

ALPN、h2 与 h2c：协议是怎么谈成的

浏览器不会“猜”服务器支持什么。TLS 之上靠 ALPN（Application-Layer Protocol Negotiation，RFC 7301）：客户端在 ClientHello 里带一个协议列表，服务器在 ServerHello 里选一个，双方就此确定用 h2 还是 http/1.1。用 OpenSSL 可以直接观察这次协商：

h2 与 h2c 的区别只在传输层：h2 跑在 TLS 上，h2c 跑在明文 TCP 上。h2c 有两种建立方式。其一是 HTTP/1.1 的 Upgrade，请求带 Connection: Upgrade, HTTP2-Settings 与一个 base64 编码的 SETTINGS 帧，服务器回 101 后切换；它要多一个往返，且不少代理对 101 的处理并不可靠。其二是 prior knowledge，客户端直接发送连接前言 PRI * HTTP/2.0，不做任何协商，只适合自己完全掌控的两端。curl 对应 --http2 与 --http2-prior-knowledge 两个参数，后者在公网场景几乎用不上。

TLS 版本方面，TLS 1.3（RFC 8446，2018 年 8 月）把完整握手压到一个往返，且只保留 AEAD 套件，对 h2 是纯粹的利好；但 2020 年仍有大量客户端停留在 TLS 1.2，配置必须两者都开。RFC 7540 附录 A 列出了一批“禁止用于 HTTP/2”的密码套件，包括 NULL 加密、EXPORT 级密钥、静态 RSA 密钥交换、基于 CBC 的套件以及使用弱 DH 参数的套件。原因并不神秘：静态 RSA 没有前向保密，EXPORT 级密钥可被暴力破解，CBC 套件在实现里反复出现填充预言类问题，而 h2 的多路复用会把这类 timing 差异放大成可观测的信号。所以实践上不必逐条背诵，只要守住“ECDHE + AEAD”这一条线：

第二件事是证书链。ssl_certificate 指向的文件必须是“叶子证书加中间 CA”的完整链，顺序为先叶子后中间，Nginx 不会自动补链。缺中间证书时，桌面浏览器常因为缓存过中间证书或支持 AIA 抓取而蒙混过关，移动端、curl、Java 客户端则直接握手失败，表现为“有的用户能打开、有的不能”，极难复现。验证方法是看握手结果里的校验码：

第三件事是 OCSP Stapling。开启后由 Nginx 代客户端去 CA 查询吊销状态并缓存，客户端在握手中直接拿到结果，省去一次对外请求，也避免把用户访问的域名泄露给 CA。

ssl_trusted_certificate 要指向签发链，通常是中间 CA 加根；resolver 必须配置，否则 Nginx 无法解析 OCSP 响应地址，stapling 会静默失败。验证同样用 s_client，加上 -status 参数，看到 OCSP Response Status: successful 才算生效。注意首次握手时缓存还是空的，Nginx 可能先不 stapling，多连几次再看。

第五件事是 h2c 的边界。listen 80 http2; 这样的写法确实能让 Nginx 接受明文 h2，但它没有 ALPN，中间设备也可能改写，公网不要开。只有在完全可控的内网链路、或者服务网格的 sidecar 之间，才考虑 h2c，并且要配合网络策略限制来源。

还有一处容易忽略的是会话复用。h2 的一条连接要服务很多请求，ssl_session_cache 命中时能省掉完整的密钥协商，对首屏体感影响不小；多台边缘共享会话时需要统一 ticket 密钥，否则用户会在节点之间反复完整握手，看起来就像“h2 没有加速”。

gRPC：HTTP/2 最实在的落地场景

如果说网页端上 h2 的收益常常被 TLS 握手和 CDN 稀释，那么 gRPC 是真正“非 h2 不可”的场景。它把四件事直接建在协议上。

一是分帧的消息体。gRPC 的请求仍是 POST，content-type 为 application/grpc，body 由一条条消息组成，每条消息前有 5 字节前缀：1 字节压缩标志加 4 字节大端长度。这层长度前缀让一条流上可以承载多条消息，而不必依赖 HTTP 的分块边界。

二是四种调用形态。一元调用、服务端流、客户端流、双向流，后三者都跑在一条长期存活的 h2 流上，可能持续几分钟甚至几小时。HTTP/1.1 下这样的长连接要么被中间设备按空闲超时切断，要么独占一条 TCP 连接，成本很高。

三是状态放在 trailers 里。gRPC 的响应头在 body 之前就发出，此时服务端还不知道最终结果，grpc-status、grpc-message 只能放在 trailers 中。HTTP/1.1 名义上支持分块编码的 trailer，但大量代理会直接丢弃它，这正是 gRPC 无法降级到 1.1 的根本原因，也是选型代理时最容易忽略的一条。

四是多路复用带来的连接模型。同一条连接上可以并发成百上千个 RPC，客户端不再需要维护复杂的连接池，服务端也不会因为几千个空闲连接耗尽文件描述符。

这些特性对中间的代理和负载均衡器提出了一份硬性清单：

  • 端到端使用 h2，而不是在入口终止 h2、再用 1.1 转发；
  • 透传 trailers，不能把 trailer 折叠进 header 或直接丢掉；
  • 不缓冲整个响应，流式场景下缓冲等于把实时性杀死；
  • 正确处理 PING 帧与 RST_STREAM，不能把 PING 当异常流量拦截；
  • 空闲超时大于客户端的 keepalive 间隔，否则连接会被反复重建。

如果链路更长，Envoy 往往是更合适的选择：它原生理解 h2、trailers 与 gRPC 的健康检查，能按 RPC 方法做路由和限流。2020 年的常见拓扑是浏览器到边缘走 Nginx，服务之间走 Envoy 或直连。

还有两个容易忽略的参数：gRPC 默认的接收消息上限是 4 MB，超过会返回 RESOURCE_EXHAUSTED，大对象应当走分页或流式；大消息还会被 h2 的流控窗口卡住，带宽时延积大的链路上需要更大的初始窗口，否则吞吐上不去，表现为 CPU 不忙、带宽不满、延迟却很高。

keepalive 也要单独说。gRPC 各语言实现的默认值偏保守，有的默认根本不发 PING。连接穿过 NAT 网关或云负载均衡时，空闲映射可能被静默回收，表现是“闲置几分钟后第一个请求必失败”。解决办法是客户端开启 keepalive，把间隔设得比链路上最短的空闲超时更小，同时服务端设置最小允许间隔，防止客户端用高频 PING 放大攻击面。

Server Push：期望与现实

推送的机制并不复杂：服务器在已建立的响应流上发一个 PUSH_PROMISE 帧，里面带上被推资源的请求头，随后在一条新的偶数编号流上发送响应。客户端可以接受，也可以用 RST_STREAM 拒绝；被推的资源进入浏览器缓存，之后页面再请求时直接命中。Nginx 提供两种写法，http2_push 指定具体路径，http2_push_preload on 则读取上游响应里的 Link: </x>; rel=preload 头并自动转成推送，两者都从 1.13.9 起可用：

看起来很美：HTML 一到达，CSS 与 JS 已经在路上，省掉了“解析 HTML 才发现资源”的那一轮等待。但真实收益受五个因素制约。

第一，服务器不知道客户端缓存里有没有。推一个已缓存的资源，白白占用带宽；在移动网络下，这可能比省下的一个 RTT 更贵。

第二，推送与优先级会打架。被推资源与页面自身的请求竞争带宽，如果推的是不关键的大图，反而拖慢首屏。PUSH_PROMISE 可以携带优先级，但浏览器对推送流的调度并不统一。

第三，CDN 与多层缓存会放大问题。边缘节点按源站指令推送，缓存命中率低时仍要回源，链路成本反而上升；多级 CDN 下行为更难预测。

第四，统计困难。DevTools 里推送的请求标为 Push，但“是否被真正使用”要看后续是否命中，工具链支持有限，优化缺少反馈闭环。

第五，浏览器厂商的态度在变化。过去两年 Chrome 团队多次在公开讨论中提出弱化甚至移除 Server Push，理由是使用率低、实现复杂、收益不明显。截至本文写作时该特性仍然可用，但把 push 作为长期依赖并不明智，基于它的构建管线要留退路。

调优：流、头部与 upstream 连接

先说结论：大多数站点的 h2 调优只需要动三五个参数，其余交给默认值。参数改得越多，出问题时越难定位。

http2_max_concurrent_streams 默认 128，对应 SETTINGS_MAX_CONCURRENT_STREAMS，限制的是每条连接上同时活跃的流数，不是请求总数。它像一道闸门：调小可以让单条连接上的排队更可控，避免少量客户端用几百条流把 worker 压满；调大对下行带宽的利用帮助有限，因为瓶颈通常在带宽和 RTT，而不在流数。面向公众的站点保持默认或适度收紧到 64，内部网关可以调大。

http2_body_preread_size 默认 64 KB，决定 Nginx 在把请求交给上游之前预读多少 body。上传小文件、gRPC 一元调用时，预读完可以一次转发，减少上游的等待；body 很大时预读没有意义，反而多占内存，此时应配合 proxy_request_buffering off 让数据流式转发。

client_header_buffer_size 默认只有 1 KB，large_client_header_buffers 默认 4 个 8 KB。别被“h2 压缩了头部”误导：Nginx 的限制作用在解压之后的头部上，一个塞满 Cookie 和 JWT 的请求照样会得到 400 或 431。调大之前先算内存账，这部分缓冲按连接分配，高并发下放大的倍数很可观。更根本的做法是给静态资源用独立域名、剥掉无关 Cookie，把 JWT 里的大字段挪走。

另外两个与安全直接相关的上限是 http2_max_field_size（单个字段，默认 4 KB）与 http2_max_header_size（整个头部块，默认 16 KB）。它们比调大缓冲区更值得关注：超限的请求会被直接拒绝，这既是防护也是故障源，调整前要确认业务侧最大的 Cookie 与令牌尺寸。

keepalive_timeout 默认 75 秒，h2 连接的空闲回收还受 http2_idle_timeout 影响。原则是“服务器要比它前面的负载均衡器更耐心”：如果 LB 60 秒就断开空闲连接，而 Nginx 75 秒才回收，用户侧会偶尔看到连接被重置；反过来，Nginx 先关、客户端还在写，就会产生看似随机的 502。

测量：怎么证明它真的更快

上线 h2 最常见的误区是“改完觉得快了”。要证明收益，得先定义指标：首字节时间（TTFB）、首屏或加载完成时间、页面加载期间的连接数、并发流峰值、错误率。其中 TTFB 和连接数最能反映协议本身的作用，加载时间则容易被图片体积、第三方脚本干扰。

第二条是 DevTools。Network 面板默认不显示协议列，右键表头勾选 Protocol 即可。整页刷新后看每个请求是 h2 还是 http/1.1，以及 Connection ID 有几条。如果几十个请求只落在一条连接上，说明多路复用生效；如果仍是一堆 http/1.1，先回去查 ALPN。

第三条是 h2load，nghttp2 自带的压测工具，是少数真正会说 h2 的压测客户端：

-n 是总请求数，-c 是并发连接数，-m 是每条连接的最大并发流。输出包含每秒请求数、TTFB 的最小值/最大值/均值/标准差，以及各状态码的计数。标准差往往比均值更有信息量：h2 在丢包链路上容易出现长尾，均值好看而 P99 很差是常见现象。

wrk 也常被拿来用，但它只支持 HTTP/1.1，压 h2 站点时会退回 1.1，数字不能与 h2load 直接比较。合理的用法是用 wrk 压上游、h2load 压边缘，分别看两段的容量。

想看帧级行为，可以用 nghttp2 自带的客户端 nghttp -nv https://www.example.com/，它会把 SETTINGS 交换、HEADERS、DATA、WINDOW_UPDATE 逐帧打印出来。TLS 之下的明文抓不到，除非客户端设置了 SSLKEYLOGFILE 并用 Wireshark 导入密钥；生产环境不要为了排障长期开着这个开关。

实验室数据只能说明协议差异，真实收益要看真实用户监控。在页面里读取 performance.getEntriesByType('navigation')[0].nextHopProtocol，就能按协议分桶统计 TTFB 与加载时间，Chromium 内核的浏览器已支持该字段。分桶之后如果 h2 用户的 TTFB 没有优势，通常说明瓶颈在服务端或链路上，而不是协议本身。

还有一个常被忽略的维度是连接复用率。h2 的收益来自“一次握手、多次请求”，如果页面每次跳转都重新建连，收益就退化为 TLS 握手的优化。用 DevTools 的 Connection ID，或者用服务端日志里新建连接数除以请求数，就能估算复用率；站内跳转场景下这个值应当很高，偏低通常意味着证书、域名或中间设备在捣乱。

至于“h2 到底快多少”，没有通用答案，它取决于资源数量、RTT、丢包率和 TLS 版本。下表只用于说明记录格式，数值是示意值，不代表任何真实环境：

指标 HTTP/1.1（6 连接） HTTP/2（单连接） 采集方式
TTFB 中位数 示意值 示意值 curl time_starttransfer
页面连接数 6 1 DevTools Connection ID
并发流峰值 不适用 示意值 h2load 或服务端日志
5xx 比例 示意值 示意值 访问日志

真正有价值的比较，是在同一网络条件、同一份资源、同一台机器上做 A/B，并且至少跑三轮取中位数。把测试机放在与用户相近的网络里，比在机房内网测出来的数字有意义得多。

坑、安全与上线节奏

第一个坑是 TCP 层队头阻塞。所有流共享一条 TCP 连接，任何一个包丢失，整条连接上所有流都要等重传。无线网络丢包率到 1% 时，h2 的单连接可能反而不如 6 条并行连接。这也是 QUIC 与 HTTP/3 要解决的问题，2020 年它们仍是 IETF 草案，生产环境只适合小流量试验。缓解手段有限：启用 BBR 拥塞控制、合理设置初始拥塞窗口、在丢包严重的链路上不要把 h2 当成唯一通道。

第二个坑是 bufferbloat。边缘网卡或中间设备的队列过长时，h2 会更快把拥塞窗口撑满，排队延迟被放大，表现为“带宽没跑满但 RTT 很高”。用 ss -ti 观察 cwnd 与 rtt 的变化，必要时在边缘做流量整形，比继续加机器有效。

第三个坑是过大的头部。Cookie 膨胀、把整个 JWT 塞进 Authorization、自定义追踪头层层叠加，解压后轻易超过缓冲区上限。对策前面已经说过：静态资源独立域名、精简令牌、按需提高缓冲但要算内存。

第四个坑是第三方资源。主站上了 h2，页面里的统计、广告、字体仍走 1.1，甚至来自没有优化过的域名，收益会被这些请求吃掉。更常见的情况是第三方脚本阻塞主线程，这时候协议再怎么优化也没用，先量一下主线程的忙碌时间。

第五个坑是链路中途的协议终止。典型拓扑是浏览器到 CDN 用 h2，CDN 回源用 1.1，负载均衡器再终止一次。多路复用只存在于第一跳，后面每一跳的队头阻塞都还在：

flowchart LR
    A[浏览器] -->|h2| B[CDN 边缘]
    B -->|HTTP/1.1 回源| C[负载均衡]
    C -->|HTTP/1.1| D[源站 Nginx]
    D -->|HTTP/1.1 keepalive| E[应用]

排查时先确认“在哪一跳终止”，用 curl -sv 看 ALPN 结果，再看响应头里有没有中间设备添加的标识。很多“h2 没生效”的工单，最终都落在某一层没有透传协议上。

第六个坑是负载不均与限流失真。四层负载均衡按连接分发，而 h2 客户端往往只建一条连接，结果一个用户的所有请求都压在同一台后端上；同理，按连接数或源 IP 做的限流在 h2 下会严重低估真实请求量。上 h2 之前要确认负载均衡是七层、能按请求分发，限流规则改成按请求或按流计数。

安全方面，h2 本身消除了 HTTP/1.1 里 Content-Length 与 Transfer-Encoding 的歧义，因为长度写在帧头里；但风险转移到了“h2 降级为 1.1”的那一层。如果代理在重写请求时对这两个头的处理与后端不一致，就可能被构造出请求走私。防御思路是收敛而不是打补丁：只保留一层负责规范化的入口代理，拒绝同时携带 Content-Length 与 Transfer-Encoding 的请求，关闭不需要的 h2c Upgrade，保持代理与后端对头部的解析一致，并且不要让内网服务直接暴露给客户端。

可观测性上，至少要在访问日志里加上协议与 TLS 版本：

$http2 的取值是 h2、h2c 或空字符串，用它做聚合就能得到协议占比曲线。监控面板上建议放四张图：h2 请求占比、TLS 版本分布、握手失败率、5xx 与上游超时。上线后如果 h2 占比没有上升，先查 ALPN 与中间设备，而不是怀疑统计。

灰度与回滚要提前设计。可行的节奏是：预发环境全量开启，跑一遍核心链路与压测；生产先在一个次要域名或一组 upstream 上开，观察一天；再按 10%、50%、100% 放量。保留一个不带 http2 的对照端口，出问题时只需去掉 listen 里的 http2 并 reload。注意 reload 是优雅退出，旧的 h2 长连接可能存活很久，必要时用 worker_shutdown_timeout 给一个上限。

迁移清单可以压缩成六步：

  1. 盘点客户端：Java 8 默认不支持 ALPN，gRPC 客户端需要额外依赖；Windows 7 上的 IE11 不支持 h2；老版本 Android 也会回落。确认这些用户能接受 1.1。
  2. 预发开启，用 openssl s_client 与 curl 确认 ALPN、证书链、OCSP 三项都正常。
  3. 对比指标：TTFB、连接数、错误率、上游超时，至少观察一个完整业务周期。
  4. 关注错误率而不是平均值，尤其是 502、连接重置和 gRPC 的 UNAVAILABLE。
  5. 按域名或 upstream 逐步放量，每一步都保留回滚开关。
  6. 上线后复盘协议占比曲线，把 h2 相关配置纳入变更管理，避免被后续模板覆盖。

小结

HTTP/2 的部署难点不在协议，而在链路上每一跳是否真的说 h2。本文的结论可以带走：用 ALPN 验证协商，用完整证书链与 OCSP 保证握手，用 listen 443 ssl http2 三个参数一次到位；上游继续用 HTTP/1.1 并开启 keepalive，不必为此纠结；Server Push 收益有限，优先用 preload；调优只动少数参数，测量看 TTFB、连接数与错误率；上线按域名灰度，随时可以回滚。最后要记住，h2 解决的是应用层的队头阻塞，TCP 层的丢包与排队依旧存在，这正是 HTTP/3 在 2020 年仍是草案却值得关注的原因。
