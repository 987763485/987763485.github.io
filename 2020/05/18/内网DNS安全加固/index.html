内网 DNS 安全加固

内网 DNS 常常是最早建成、最晚重构的一套基础设施：它承载办公网的上网解析、内部系统的服务发现，也往往是安全设备做域名策略的唯一抓手。一旦它被投毒、被当成隧道出口，或者仅仅因为一条过期记录返回了错误地址，影响面就会覆盖整个组织。本文从威胁模型讲起，逐步落到 BIND 9.16 的基线配置、视图与 ACL、DNSSEC 与 RPZ、日志与主机加固，最后给出变更与应急的做法，目标是让读者能对照自家环境做一次可执行的加固。

威胁模型：内网 DNS 站在哪几条信任链上

内网 DNS 通常同时承担三种角色：为终端解析公网域名、为内部系统提供地址与服务记录、以及作为出网流量的第一道策略点。角色叠加意味着它既是攻击入口，也是调查时最重要的证据来源。做加固之前，先要把对手的位置摆清楚。

能伪造响应的对手

同一广播域内的攻击者可以做 ARP 欺骗，把终端的 DNS 请求引到自己身上；也可以伪造 DHCP 响应，直接下发一个恶意的解析器地址。DNS 查询默认走明文 UDP，协议本身不认证响应来源，客户端只靠事务 ID、源端口和问题字段做匹配。2008 年 Kaminsky 攻击之后，主流解析器都引入了源端口随机化，但熵依然有限，攻击者还可以用大量并发查询提高猜中的概率。更现实的问题是转发器：如果内网解析器把查询转发给一个不可信的上游，上游返回什么，内网就缓存什么，一次投毒会影响所有走这台解析器的客户端。

未授权递归与反射放大

把递归查询的许可范围配成 any，或者干脆没有显式配置、依赖默认值，是内网解析器最常见的问题。这样的服务器一旦能被外部或访客网段访问，就成了开放递归解析器。攻击者可以用它放大响应：查询大体积记录，源地址伪造后，受害者收到的就是来自你司 IP 的洪流。开放递归还会被当作隐蔽信道，攻击者不需要自己的域名，就能借你的解析器完成隧道通信，日志里留下的也只是正常查询。

隧道与外泄

很多企业只允许 53 端口出网，这恰好给了恶意软件一条稳定通道。DNS 隧道把数据编码进子域名，通过 TXT、NULL、CNAME 或 A 记录带出，服务端由攻击者控制，客户端只需要持续发查询。它的特点是流量看起来像正常解析、单条报文很小，但域名标签长、信息熵高、唯一子域数量大。若终端可以直连外部 53 端口，内网的 RPZ 与日志就完全看不到这些请求。

区域传送泄漏

没有限制区域传送时，任何人执行一次完整的区域传送就能拿到内网区域的全部记录，相当于一份资产清单：数据库地址、跳板机、测试环境、打印机全在里面。这类泄漏不产生告警，也不影响业务，往往在渗透复盘时才被发现。

可用性威胁

还有一类不来自攻击者的风险同样致命：过期记录指向已下线的主机、转发器单点故障、TTL 过长导致切换缓慢、DNSSEC 签名过期导致整域解析失败。对多数组织来说，这类事故的发生频率远高于真正的攻击，因此加固方案必须同时覆盖“被攻击”和“被自己改坏”两种情况。

架构：先把解析路径画清楚

很多加固失败不是配置写错，而是没弄清一台服务器同时扮演了什么角色。内网常见的组件有四类：终端上的 stub resolver、缓存递归解析器、只做转发的 forwarder、以及内部权威服务器。四者的安全要求完全不同，混部在一台机器上就必须用 view 把策略拆开。

递归与转发的取舍

完全递归的解析器需要自己访问根和各级权威，出网策略必须放开 53 端口，攻击面更大，但信任链最短；只做转发的解析器把所有查询交给上游，出网只需放行少数目的地址，便于集中审计和做策略，代价是上游成为信任与容量的单点，上游缓存被投毒会直接传导到内网。折中的做法是设一层“出网解析器”：只有它能访问外网，办公解析器向它转发，两层都做 ACL。无论选哪种，都要在配置里显式写出递归开关和许可范围，不要依赖默认值，因为不同发行版的默认值并不一致。

分离视图

分离视图解决的是同名区域内外返回不同地址的问题。BIND 用 view 加 match-clients 实现，判断顺序是“第一个匹配生效”，因此兜底 view 必须放在最后。match-clients 要写具体网段，不要依赖 localnets，在多网卡、容器和 NAT 环境里，localnets 的含义经常超出预期。另一个容易被忽略的点是缓存：每个 view 有独立的缓存，内存要按 view 数量估算，否则高峰期会出现缓存挤占。视图之间还会共享同一份配置文件，任何一条 zone 语句写错位置都会让 named 启动失败，所以改动后先用 named-checkconf 校验。

隐形主服务器

内部权威建议采用“隐形主服务器加多台从服务器”的结构：主服务器不出现在 NS 记录里，只接受从服务器的 TSIG 传送；从服务器对外提供查询。这样主服务器可以放在管理网段，升级和改配置不影响在线查询，也减少了被直接攻击的面。主服务器与从服务器之间要监控序列号差异，传送失败往往在 TTL 到期后才暴露成解析错误。

放置与高可用

解析器放在管理区或独立的 DNS 网段，只对内网客户端开放；权威服务器按需放在 DMZ。不要把对外权威和对内递归放在同一个进程里，否则一条针对权威的放大攻击会同时拖垮递归服务。高可用至少两台，客户端配置两个地址；但 glibc 的 resolver 默认按顺序尝试、超时后才切换，实际切换时间可能达到数秒，关键系统应通过 VIP 或本地缓存代理缩短故障感知。多站点可以用 anycast 把同一地址宣告到不同机房，注意 UDP 无连接而 TCP 需要会话一致，anycast 路径切换时可能出现短暂重传。

BIND 9.16 基线：先关掉不该开的口子

BIND 9.16 在 2020 年初发布，是当时新部署的默认选择，配置结构和 9.11 基本兼容，但默认值和可用选项有变化。基线配置的原则很简单：只监听必要的地址、只服务必要的客户端、只返回必要的数据，然后把校验能力打开。下面这份片段可以作为递归解析器的起点，各项取舍在后文逐条展开。

监听面与查询面

listen-on 只写业务地址和回环地址，不要图省事监听所有网卡。多网卡服务器上，一块临时挂上的测试网卡就可能把解析器暴露到不该到的网段。allow-query 控制谁能提问，allow-recursion 控制谁能要求递归，allow-query-cache 控制谁能读取缓存。三者语义不同，只配其中一个会留下缝隙：比如把递归限制在内网，却让缓存对所有人开放，攻击者仍能通过缓存窥探内网访问过哪些域名，这种手法通常称为缓存窥探。

响应最小化与分片

minimal-responses yes 让服务器在回答时省略不必要的权威段和附加段，既减小报文体积，也降低被用于放大的价值。max-udp-size 和 edns-udp-size 设成 1232 是 2020 年社区推荐的做法，目的是避开中间设备对 IP 分片的处理差异；代价是部分大响应会改走 TCP，需要确认防火墙放行 53 端口的 TCP。

递归侧的限流

响应速率限制主要用在权威服务器上，用来抑制伪造源地址的查询洪流，配置在解析器上反而容易误伤正常的高频客户端。递归侧更合适的旋钮是 clients-per-query、max-clients-per-query 和 fetches-per-zone：它们限制的是同一域名被大量客户端同时查询、以及向同一区域发起过多取数请求的情况，能在上游变慢时保护自身。是否调低这些值要结合业务峰值，建议先在旁路实例上观察一周。

这组参数的含义是：同一网段每秒最多获得 20 个正常响应，超出的请求按比例返回截断响应，让合法客户端改用 TCP 重试，而伪造源地址的攻击者收不到完整答案。前缀长度决定聚合粒度，设得太细会让限流失效，设得太粗会误伤整栋楼。

不要依赖默认值

BIND 的多数默认值是为“能跑起来”设计的，不是为“安全”设计的。查询许可默认对所有人开放，递归默认开启，只有在显式写了 ACL 之后行为才符合内网预期。很多事故的根因是一份从教程抄来的最小配置：只写了 recursion yes，没有写任何许可范围，服务器在测试网段跑得很正常，接入办公网后立刻变成开放递归。每次上线前应把 named-checkconf -p 展开后的完整配置导出复核，确认每一个 allow 语句都指向预期网段，而不是停留在“我记得配过”。

版本信息与校验

隐藏版本号只能减少指纹识别，不能替代补丁，version "not disclosed" 之外还应关闭不必要的 CHAOS 查询。dnssec-validation auto 让解析器用内置根信任锚做校验，是 9.16 的推荐值；如果内网存在自建的信任岛，还需要额外的信任锚配置，这部分放在 DNSSEC 一节展开。

ACL、view 与 TSIG：把递归和传送关进笼子

ACL 是 BIND 里所有访问控制的基石，写法比其他厂商的地址组灵活，也更容易写错。一条 ACL 可以嵌套引用另一条 ACL，可以用感叹号做排除，匹配顺序是从左到右、首个命中生效。把“办公网段减去测试网段”这种需求直接表达出来，比在上层反复叠加规则更不容易出错。

视图的边界

上面的结构把内网视图放在前面，外网视图用 any 兜底。要注意两点：第一，一旦使用 view，所有 zone 都必须写在某个 view 里，写在 options 同级会直接报错；第二，外网视图必须显式关闭递归并禁止传送，否则兜底视图会变成新的开放递归入口。如果同一台机器用不同地址服务内外网，可以用 match-destinations 按目的地址区分，比按来源地址更可靠。

用 TSIG 约束传送

区域传送使用 TSIG 做共享密钥认证，算法选 hmac-sha256，密钥用 tsig-keygen 生成，不要手工拼字符串。密钥文件权限应设为仅 named 可读，并且每个传送方向使用独立密钥，便于单独轮换和吊销。从服务器上同样要写 allow-transfer { none; }，避免从服务器又被别人当作传送源。验证时，从未授权主机发起传送应当被拒绝，从授权从服务器发起应当成功；注意不要把密钥直接写在命令行参数里，那会留在 shell 历史和进程列表中。

还有一个容易误解的地方是继承关系：写在 options 里的 allow-transfer 会被所有 zone 继承，某个 zone 里再写一条就会整体覆盖，而不是合并。因此推荐的做法是全局默认拒绝，只在确实需要传送的 zone 上显式写出密钥，这样新增区域时不会因为忘记收口而意外开放。

动态更新的最小授权

如果地址由 DHCP 分配，需要允许 DHCP 服务更新正向和反向区域，这时不要开放整个区域，而是用 update-policy 精确到记录类型和子域，例如只允许某个密钥更新指定子域的 A、AAAA 和 PTR 记录。动态更新与区域传送使用不同的密钥，避免一把钥匙开所有门。

DNSSEC：内网签名值不值得

DNSSEC 解决的是“收到的记录是否真的来自该区域的权威服务器、且没有被篡改”。它用签名链把信任从信任锚逐级传到叶子记录，能防住缓存投毒中“伪造一个看起来合理的响应”这一类攻击。需要先明确它的边界：DNSSEC 保护的是解析器到权威之间的数据完整性，不保护终端到解析器这一段，也不提供机密性。终端与解析器之间仍要靠加密传输或网络层隔离，这一点在后面的加密 DNS 一节再谈。

内网签名的方式

内网域名通常不在公共 DNSSEC 树里，做法是建立一个“信任岛”：用一个内网信任锚签根区域或企业顶级域，解析器把这个锚配置为静态信任锚。BIND 9.16 提供了 dnssec-policy，把密钥生成、签名、轮换交给 KASP 自动管理，比过去手工执行 dnssec-keygen 和 dnssec-signzone 可靠得多。

校验器的配置陷阱

解析器侧需要同时拥有公共根锚和内部信任锚：公共部分用自动根锚，内部部分用静态锚指向企业域的 DNSKEY。只配内部锚会让所有公网域名校验失败，只配根锚则会让内部域名失败。最常见的坑是分离视图与 DNSSEC 叠加：内网视图返回的地址与公网签名记录不一致，解析器按公网链验证就会得到 SERVFAIL；如果内部区域根本没有签名，而父域在公网存在且已签名，否定证明同样对不上。这类故障的表现是“只有开了校验的解析器出问题”，排查时应先用 delv 指定信任锚逐级验证，确认断点在哪一层。

密钥管理与轮换

轮换的关键不是算法，而是时间参数。新密钥要先发布、等旧缓存过期，再开始使用，最后才删除旧密钥；max-zone-ttl 必须小于签名有效期，否则会出现“记录还在缓存里、签名已过期”的窗口。ZSK 按季度轮换、KSK 按年轮换是常见节奏，私钥应离线备份并限制读取权限，条件允许时放入 HSM。轮换前后要监控签名有效期和区域传送状态，避免主从之间只同步了记录、没同步到新密钥。

算法选择上，ecdsap256sha256 的签名体积小、校验开销低，适合查询量大的内网区域；如果还有只支持 RSA 的老设备，可以退到 2048 位的 rsasha256，但不要继续使用已被主流实现淘汰的 SHA-1 系列算法。自动策略并不意味着可以完全不看：至少要定期检查密钥的发布时间、激活时间和签名剩余有效期，确认 KASP 没有因为时钟漂移或权限问题卡在中间状态。

RPZ：把威胁情报变成策略

RPZ 是一种特殊的区域，里面写的不是真实数据，而是“遇到某个名字时应该怎么做”的策略。递归解析器在回答时会把查询名与 RPZ 比对，命中后按策略返回 NXDOMAIN、空答案、伪造地址，或者直接丢弃。它的价值在于响应速度快：情报更新只需要刷新一个区域，不用改防火墙，也不用等终端重启。

区域文件的写法有固定约定：CNAME . 表示返回 NXDOMAIN，CNAME *. 表示返回空答案，CNAME rpz-passthru. 表示放行，CNAME rpz-drop. 表示直接丢弃。白名单区域放在前面，先匹配先生效，这样即使情报源误判，也能用一条本地记录纠正。TTL 建议设得很短，便于紧急撤回。

情报源与变更

外部情报不能直接加载，通常要经过格式转换、去重、剔除自家域名和关键合作方域名，再用 named-checkzone 校验后替换文件。更新过程应该是“下载到临时目录、校验、原子替换、reload”，任何一步失败都保留旧版本。每次更新记录版本号、条数和校验和，出问题时能回答“是哪一版规则导致的”。

误报与 DNSSEC

RPZ 改写了答案，会破坏原有签名，因此对已签名的区域启用改写策略时，需要接受校验失败或显式配置 break-dnssec，这会削弱 DNSSEC 的意义，应在策略上明确取舍。另一个常见问题是误报：把整个二级域拉黑，可能连带阻断同一域名下的邮件、更新和登录服务。建议先在小范围解析器上以放行加日志的方式观察命中情况，确认没有业务依赖后再切换为阻断，并保留一键回滚的开关。

可观测性：日志、指标与隧道识别

DNS 是少数能同时看到“谁在访问什么”的协议，因此日志既是安全能力，也是隐私负担。BIND 的查询日志可以用 category queries 单独输出，建议限制文件数量和大小、只保留必要字段，并把它与其他日志分开存放，避免磁盘被写满导致解析服务不可用。高流量环境应关闭全量查询日志，改用 dnstap：它以二进制格式记录查询与响应元数据，开销远低于文本日志，也便于后续做结构化分析。

指标与基线

除了查询量，至少应采集缓存命中率、SERVFAIL 比例、NXDOMAIN 比例、按查询类型的分布、响应时延和前若干名客户端。statistics-channels 暴露的统计可以被监控系统定时抓取，形成按小时和按天的基线。没有基线，告警就只能靠拍脑袋设阈值；有了基线，才能判断“今天 NXDOMAIN 涨了三倍”是解析器故障还是有人在扫描。

开启全量查询日志前，应先按峰值查询量乘以单条日志的平均长度估算日增量，再决定是否采样。一个每天数亿次查询的解析器，全量文本日志很容易在几小时内吃掉上百 GB，磁盘写满后 named 会直接停止服务。更稳妥的顺序是：先用 dnstap 或统计接口摸清流量结构，确认确有调查需求后再对特定网段或特定查询类型开启文本日志，并把 query-errors 单独收集，用来看拒绝、超时和格式错误，而不是把它们混进正常查询里。

隧道识别的启发式

DNS 隧道的信号不在单条查询上，而在统计特征上：标签特别长、子域随机、唯一子域数量与查询量接近、TXT 和 NULL 查询占比异常、同一客户端持续以固定间隔发起请求、响应字节数远大于请求。实际检测通常组合多个特征打分，再人工确认，而不是指望某一条规则。发现可疑终端后，第一步是保留 dnstap 与解析日志、确认它是否绕过了内网解析器，第二步才是封禁域名或隔离主机，顺序反了就会丢掉证据。

隐私与留存

查询日志会暴露内部系统名称、员工访问习惯和业务节奏，属于敏感数据。留存期建议按调查需要设定，常见做法是热存 7 到 30 天、聚合统计长期保留；访问日志需要审批和审计，导出时对客户端地址做截断或哈希。日志服务器本身也要加固，不能成为新的泄漏点。

主机加固、加密 DNS 与应急响应

配置正确只是第一步，运行 named 的那台机器同样需要按安全基线治理。BIND 应以专用用户运行，能用 chroot 就用 chroot，区域文件和密钥目录的权限要收到最小：公钥文件可读，私钥文件仅属主可读，密钥目录不可被其他用户遍历。发行版自带的 systemd 单元通常已经包含沙箱选项，自建单元时至少要限制文件系统写入范围、关闭提权、只保留绑定 53 端口所需的能力。

启用 SELinux 的发行版还要确认区域文件的上下文正确，动态更新目录需要相应的布尔开关，否则表现为“权限明明对、就是写不进去”。控制通道 rndc 只监听回环并启用密钥认证，不要为了方便绑到管理地址却不设 ACL。补丁节奏上，BIND 的稳定分支会持续发布安全修复，应订阅上游的安全公告，把“评估、测试、灰度、全量”做成固定流程，而不是等出事再升级。

加密 DNS 在 2020 年的位置

DoT 与 DoH 在 2020 年已经可用：DoT 有 RFC 7858，DoH 有 RFC 8484，Firefox 开始在美国逐步默认启用 DoH，Android 9 以上支持私有的 DoT，Unbound 1.9 也能直接提供 DoT 监听。但在内网，它们不是万能药。加密只保护终端到解析器这一段，防的是同网段嗅探和中间人篡改；如果终端本身已被控制，加密没有意义。更大的风险在 DoH：客户端直连公共 DoH 服务后，会绕过分离视图、RPZ 和查询日志，内网域名解析失败，安全策略也同时失效。务实的做法是允许内网 DoT、通过终端策略和 DoH 探测域名约束公共 DoH，并把“为什么不能随便开 DoH”写进终端基线，而不是简单封端口。

变更管理与应急

记录变更最容易出问题的是 TTL 和序列号。计划切换地址时，提前一个旧 TTL 周期把 TTL 调低，切换完成并观察稳定后再调回；序列号采用日期加序号，保证从服务器能判断新旧。变更前用 named-checkzone 校验语法和语义，先灰度一台解析器，再全量 reload，最后用查询验证关键域名。应急场景下，RPZ 是最快的阻断手段，把恶意域名写入短 TTL 的阻断区并 reload，通常比改防火墙更快；如果故障来自 DNSSEC 签名，可以临时对该域设置负信任锚，但要记录原因和到期时间，避免长期遗留。回滚依赖两样东西：上一版区域文件和可重复的发布步骤。

落地清单

  • 递归只对内部网段开放，缓存查询同样受限
  • 权威与递归分离，隐形主服务器只接受 TSIG 传送
  • 区域传送默认拒绝，按需授权到具体从服务器
  • 版本号隐藏，控制通道仅回环并启用密钥
  • 关键区域启用 DNSSEC，信任锚与轮换计划明确
  • 解析器开启校验，并用内部信任锚覆盖企业域
  • RPZ 有白名单、有版本记录、有回滚开关
  • 查询日志或 dnstap 可用，留存期与访问权限明确
  • 隧道检测有基线，异常能关联到终端
  • 主机使用专用用户、最小权限与沙箱
  • 补丁订阅与灰度流程固定
  • 变更前降 TTL，变更后验证，保留上一版文件
  • 加密 DNS 有明确边界，不绕过内网策略
  • 应急手册包含 RPZ 阻断、负信任锚和证据保全

小结

内网 DNS 的安全问题可以归为两类：一类是协议与配置留下的缺口，比如开放递归、未限制的传送、不可信的上游；另一类是运维过程留下的隐患，比如过期记录、过期签名、单点转发。前一类靠基线配置、ACL、TSIG、DNSSEC 和 RPZ 解决，后一类靠变更流程、监控基线和应急演练解决。加固不必一次做完，建议先收紧递归与传送这两个高风险项，再补齐日志与 DNSSEC，最后处理加密 DNS 与终端策略的边界。任何时候都要记住，DNS 的高可用和它的安全性一样重要，一次错误的加固同样能让整个组织断网。
