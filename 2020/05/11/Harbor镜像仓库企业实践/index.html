Harbor 镜像仓库企业实践

本文属于《Docker 与 Kubernetes》第 16/51 篇
上一篇系列目录下一篇

团队规模小的时候，镜像靠一台构建机上的 docker save 加共享目录就能传递；一旦有几十个人、几个机房、若干条流水线，这种方式就会在权限、带宽和追溯上同时失控。本文以 Harbor 1.10 为基准，讲清楚一个企业私有镜像仓库从部署到日常治理的完整链路：项目与角色怎么划、跨站点复制怎么做、漏洞扫描与保留策略怎么落地、备份和 CI 接入又该注意什么。读者需要熟悉 Docker 的基本命令，读完后应当能够独立规划一套可供几十人团队长期使用的镜像仓库。

为什么要自建镜像仓库

Harbor 由 VMware 开源，2018 年进入 CNCF，至今仍是孵化项目，1.10 是 2020 年初的稳定版本。它并不是“界面更好看的 Registry”，而是在 Docker Registry 之上补齐了企业真正关心的几件事：镜像存在哪里、谁能推、谁能拉、出了问题能否追溯。

  • 私有镜像不外流。业务镜像常带内网地址、证书和初始化脚本，推到公有仓库等于公开部署细节。
  • 权限要分级。开发、测试、运维对同一镜像的需求不同，靠构建机上的 htpasswd 管不过来。
  • 多站点分发。总部构建、分部运行，跨公网拉取大镜像既慢又费钱。
  • 安全与合规。基础镜像的漏洞要有清单，出事时要能回答“镜像何时、被谁推上来”。

只做存储的话，官方 registry:2 也能用，但它是“哑”存储：没有项目、没有界面、没有扫描和复制，认证只能外挂。Harbor 把这些能力做进同一个产品，代价是要多维护数据库、Redis 和一组容器。

能力 registry:2 Harbor 1.10
多租户与权限 仅基础认证 项目隔离，五种角色
漏洞扫描 无 集成 Clair，可拦截拉取
跨站点复制 无 推、拉两种模式
标签保留与回收 无 保留策略加垃圾回收
操作审计 无 全量操作日志

部署 Harbor 1.10：主机、证书与外部依赖

主机与目录规划

官方最低配置是 2 核 CPU、4 GB 内存、40 GB 磁盘，生产建议 4 核 8 GB 起步，数据目录放在独立数据盘上，因为镜像层会持续增长，和系统盘抢空间是最常见的故障。宿主机的 Docker 需 17.06 以上，docker-compose 需 1.18 以上。解压安装包后，持久化数据默认落在 /data 下：

路径 内容 说明
/data/registry 镜像层与 manifest 通常最大
/data/database 内置 PostgreSQL 数据 可改用外部库
/data/redis 会话与任务队列 可重建
/data/secret Token 私钥与加密密钥 丢失后机器人账号全部失效

外部数据库与邮件

单机演示可以用内置 PostgreSQL 和 Redis，但要多副本或规范备份，就应换成外部实例：在 database 段填地址、账号和 sslmode，在 redis 段填地址与密码。换成外部库后，备份方式也要从拷贝目录改成 pg_dump。邮件不在配置文件里，而在管理界面的“配置”页填写 SMTP，用于密码重置和扫描通知，装好后就该配好并测试发信。

项目、角色与机器人账号

项目是权限的边界

Harbor 里的镜像都属于某个项目，项目是权限、配额、扫描策略和保留策略的最小单位。按团队或业务域划分比按环境划分更稳：payment、base-images 各自独立，环境差异交给角色和流水线控制。公开项目允许匿名拉取，适合放基础镜像；业务镜像一律私有，只给明确的人授权。

五种项目角色

Harbor 1.10 的项目角色较细：访客只读；受限访客只能读指定仓库；开发者可推可拉；维护人员额外能管部分配置；项目管理员拥有全部权限。要点是“推”和“管”分离，研发给开发者即可，扫描阈值、保留策略这类批量生效的配置应当留在平台团队。

机器人账号与 CI 接入

流水线不能用人账号：人一走账号就废，改密码还会打断构建。项目级机器人账号的用户名形如 robot$payment+ci，只勾选需要的 push、pull 权限并设置过期时间；系统级机器人账号用于跨项目拉取，适合部署平台。

用提交号做标签、用 digest 部署，能避免“标签被覆盖后行为变了”的问题。发布类仓库还可以在项目配置里开启标签不可变，推送同名标签会被直接拒绝，把覆盖式发版挡在仓库这一层。

对接 LDAP 与 AD

企业通常已有目录服务，在“系统管理 → 配置 → 认证模式”里改为 LDAP，填地址、基准 DN、绑定账号和过滤器，用户属性用 uid 或 sAMAccountName。开启组同步后，把目录组映射到项目角色，入离职只改目录一处。要注意切换后登录优先走 LDAP，管理员密码必须单独保住，否则目录故障时无人能进。

镜像复制与多站点分发

分部跨公网直拉总部仓库，结果是拉取慢、出口带宽被占满，专线一抖连发布都做不了。复制把镜像异步同步到另一个仓库，让每个站点就近拉取。

端点、方向与触发方式

复制由端点、规则、任务三部分组成。端点是目标仓库的地址与凭据，可以是 Harbor、标准 Registry 或公有仓库。推送模式把本地镜像推给对方，适合总部向分部同步；拉取模式由本地主动去远端取，适合隔离区仓库从内网拉，因为受控网络通常只允许单向发起连接。触发方式有手动和定时两种，定时用 cron 表达式。复制是异步的，任务由 Jobservice 执行，“点了复制”不等于“复制完成”，发布流程若依赖结果，应当查任务状态而不是空等。

过滤器与失败处理

规则可按仓库名和标签过滤，常见写法是只同步 release/* 或 v*，把每天数百个临时构建挡在外面。过滤太宽会让队列堆积，太窄又会在发布时才发现镜像没同步。

失败原因多集中在三处：目标端证书不被信任、机器人账号权限不足、目标项目不存在。任务详情能看到具体错误，修好后重试即可；Harbor 不会补跑历史失败任务，需要定时任务兜底。1.10 不提供复制限速，只能靠错峰或代理层限速。另外，复制的是镜像内容，扫描结果一般不会随之带过去，各站点仍需自行扫描。

漏洞扫描与拉取门禁

Clair 在 Harbor 1.x 中的位置

Harbor 1.10 的扫描能力来自 Clair：它作为独立容器运行，自带 PostgreSQL 存放漏洞库，clair.updaters_interval 控制更新周期，默认 12 小时。链路是 Harbor 把镜像 manifest 交给 Clair，Clair 解析出系统包和部分语言依赖，与漏洞库比对后把报告写回 Harbor。

两个前提容易忽略：扫描识别的是包管理器装了哪些包，从源码编译进镜像的二进制基本扫不出来，报告干净不等于没有漏洞；离线环境里更新器需要访问上游漏洞源，没有出口就得配代理，否则漏洞库停更，界面上的“无漏洞”只是假象。

扫描时机与拉取门禁

扫描可以设为推送时自动执行，也能在详情页手动触发，项目维度还支持批量扫描存量镜像。“推送即扫”加“定期全量扫”比较稳妥：前者尽早暴露问题，后者覆盖漏洞库更新后才被标记出来的旧镜像。

真正有约束力的是拉取门禁：项目可开启“阻止运行有漏洞的镜像”并设定严重级别阈值。它作用于 pull 而不影响 push，构建不会因此失败，部署侧会收到明确的拒绝。阈值定得太低会拦住几乎所有镜像，团队很快就会把门禁关掉，通常从高危起步；误报靠项目级 CVE 白名单豁免，但白名单要有审批和过期；紧急回滚时还要给管理员留临时放行的通道。

基础镜像的责任边界

报告里多数漏洞来自基础镜像而非业务代码，责任应当划给平台团队：维护几个固定的基础镜像，定期重建和扫描，业务镜像只从它们派生。镜像越薄，扫描越快，误报也越少。

运维治理：保留、回收、备份与升级

标签保留策略

流水线每天产生几十个提交号标签，几个月后一个仓库就有上千个。保留策略按规则清理标签，1.10 的规则由作用范围、标签筛选条件和执行计划组成。

筛选维度包括保留最近推送的 N 个、最近被拉取的 N 个、最近 N 天，或按正则匹配标签名。例如对 release/* 只留最近 10 个且永不清理 latest，对普通标签保留 30 天。规则写错会删掉还在用的镜像，第一次务必用试运行核对命中清单，再改成实际删除。

垃圾回收与配额

删除标签只删了引用，镜像层仍在存储里，释放空间要靠垃圾回收。回收会扫描 Registry 中不被任何 manifest 引用的 blob 并删除，执行期间不能让新推送插进来，否则刚上传的层可能被误判。标准做法是切到只读模式，触发回收，确认日志完成后恢复读写；频率按推送量定，通常每周一次，放在低峰期，前后对比存储用量就能判断策略是否生效。

配额是另一道闸门：给项目设存储上限，超过后推送被拒绝。它适合约束“什么都往里塞”的项目，但基础镜像项目要放宽，否则一次基础镜像更新就会卡死。告警应早于硬限制触发，让人有时间清理。

审计日志

Harbor 记录登录、推送、删除、改配置、创建机器人账号等写操作，可按项目、用户、类型和时间过滤，能回答“这个镜像为什么没了”。建议把日志定期导出到统一日志平台，避免本地轮转冲掉关键记录，并对删除项目、修改扫描策略这类高危操作设置告警。

多副本与共享存储

Harbor 的多数组件无状态，有状态的是数据库、Redis 和镜像存储。做高可用先把这三样外置：镜像存储用对象存储或共享文件系统，数据库和 Redis 用外部实例，再部署多个实例挂到负载均衡后面。所有实例必须共享同一份 /data/secret，因为 Token 的签发与校验依赖同一把私钥；Jobservice 负责定时调度，实践上只让一个实例承担，避免复制和保留任务被重复触发。

备份与恢复演练

备份清单不长：数据库每天用 pg_dump 导出，镜像存储交给对象存储的版本或快照，harbor.yml、证书和 secret 目录纳入版本管理。恢复演练建议每季度一次：新装同版本 Harbor，导入数据库，挂载同一份存储，再用机器人账号推拉一个测试镜像，确认权限、标签和 digest 都对得上。没演练过的备份只能算心理安慰。

签名与升级

Notary 是可选的内容信任层，安装时加 --with-notary，客户端设置 DOCKER_CONTENT_TRUST=1 后，未签名的镜像会被拒绝拉取。它和扫描互补，但会增加发布复杂度，中小团队可先用 digest 固定版本。升级前先读 release notes 再备份，按版本路径逐级升级；升级脚本会重建代理配置，自行改过的 TLS 参数会被覆盖，主机名和证书路径也不要变，否则 token 与客户端配置都要跟着改。Harbor 2.0 预计 5 月中旬发布，但此刻生产仍应以 1.10 为准。

小结

自建镜像仓库的价值不在“能推能拉”，而在把权限、复制、扫描和保留变成可执行的规定。落地顺序建议是：先按业务域划项目、用机器人账号接 CI，再补复制和扫描门禁，最后用保留策略与垃圾回收控制成本。高可用和备份要在业务真正依赖它之前做好，升级则永远先备份、再读发布说明。
