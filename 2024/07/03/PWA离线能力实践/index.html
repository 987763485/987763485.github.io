PWA 离线能力实践

“离线”在需求文档里常常只是一行字，实现时却牵扯三套彼此独立的机制。本文不谈 PWA 的功能清单，只谈离线能力的设计：哪些请求必须在无网络时成功、哪些数据允许陈旧到什么程度、写操作该不该被接受，以及这些选择在 Chrome、Safari、Firefox 上分别能做到哪一步。适合已经把 Service Worker 接进构建流程的同学。

离线能力的三个独立问题

把”支持离线”当成一个开关，是绝大多数失败案例的共同起点。它实际上是三个问题，判定标准、技术手段与失败模式各不相同。

第一个问题：静态资源可用性

问题是”用户在没有网络时点开首页或某个已访问过的页面，能不能渲染出可用的界面”。不确定性来自构建产物：一次发布会产生一批新的 hash 文件名，也会删掉一批旧文件。这一层的目标是”界面结构可用、功能降级明确”；手段是 precache 与运行时缓存，衡量口径是”无连接冷启动能不能进应用外壳”。

第二个问题：数据可用性

问题是”页面渲染出来了，但列表、详情、看板里的业务数据从哪来”。这里最关键的概念是陈旧度预算：某个数据离线时展示 5 分钟前的快照可以接受，展示上周的就不可以。要回答的不是”缓存什么”，而是”每份数据最长可接受多久没更新、由谁刷新、超期后展示什么”。手段是运行时缓存策略加 IndexedDB 里的结构化副本，衡量口径是”离线打开列表页时，看到的是标注了时间的旧数据，还是一屏空白加转圈图标”。

第三个问题：写操作可用性

问题是”离线时用户点了保存、提交、发送，系统该怎么办”。这一层与前两层有本质差别：前两层是”读取的降级”，这一层是”承诺的兑现”。一旦接受离线写，就等于承诺”这条数据最终会到达服务端”，而要兑现就必须处理排队、重放、幂等、冲突与失败告知。这是个产品层面的决策：接受离线写会把复杂度抬升一个数量级，并引入”用户以为保存了、实际没保存”的信任风险。

混为一谈的典型症状有几种：只做了静态资源缓存，应用能打开、界面能渲染，但所有区块都是”加载失败，请重试”，用户仍评价”完全不能用”，因为他感知的”能用”就是看到内容；只做数据缓存却没处理导航回退，首页能离线打开、深层路由却是浏览器错误页；或者把三层验收写成同一条”断网可用”，测试点一下飞行模式就给出通过结论，结果没有一条边界真正被覆盖过。正确做法是每层单独写进验收清单并给出可判定的条件，例如”无连接重启后访问首页与最近 20 个已访问路由，均能渲染外壳且无白屏”。

一点历史边界

在 Service Worker 之前，浏览器给出过 Application Cache，它在规范与浏览器中早已被废弃并移除，今天只作为”为什么需要一个可编程拦截层”的反面教材：问题核心不是 bug 多，而是把三个问题揉进了一个声明式清单与一套应用无法控制的更新时序里。具体陷阱在本仓库 2013 年的旧文中有专门讨论，本文不复述。Service Worker 的缓存与 HTTP 缓存是分层协作的，浏览器缓存仍在生效，前者只是站在它前面的一个可编程拦截点。

manifest：与离线相关的字段与注册边界

Web App Manifest 常被当成”安装用的配置文件”，但它对离线能力的影响是前置性的：它决定了什么算”你的应用”，也就决定了离线的边界。

name 与 short_name 是应用名，display 决定窗口形态，orientation 约束屏幕方向，theme_color 影响系统着色，icons 提供多尺寸图标——都不参与离线逻辑。真正与离线相关的是 start_url 与 scope。

start_url 是无界面启动时进入的地址；scope 是路径边界：落在其内的链接被视为”还在应用里”，复用同一个应用实例，跳出的则交给普通标签页。离线的边界正在这里——只有 scope 内的导航请求才会被当作应用内导航处理。

这里要区分两个容易混淆的 scope。manifest 的 scope 描述应用边界，注册时的 scope 描述 fetch 拦截边界，后者是硬性约束：传入的 scope 不能超出脚本自身所在目录，脚本放在 /app/sw.js，最大可拦截范围就是 /app/。工程上让两者取同一路径并在同一处常量里定义。

两个边界不一致会产生很难排查的现象：某个路由被拦截并给出离线回退页，却不在 manifest 的 scope 内，从桌面入口进来时又变成一次全新导航；或者反过来，scope 覆盖了而拦截没覆盖，离线时那个路由直接白屏。

id、share_target、shortcuts 是当时已进入规范与部分浏览器实现的可选扩展，与离线可用性没有直接关系，不要为了”字段更全”而引入。

另一个易漏点：start_url 带查询参数时，要确认这个 URL 本身也进了 precache 清单。外壳缓存在 /app/、启动地址是 /app/?source=pwa，两者是不同 URL，若拦截按 URL 精确匹配就会漏掉，恰好让无网络启动回退失败。

Service Worker 生命周期与接管风险

Service Worker 是独立于页面生命周期的工作线程，它的状态迁移决定了”哪一份代码在拦截请求”。理解这套状态，是理解离线能力为什么”有时生效有时不生效”的前提。

flowchart TD
  A["下载并解析脚本"] --> B["installing"]
  B -->|"install 事件成功"| C["installed"]
  C -->|"旧 SW 全部关闭后"| D["activating"]
  C -->|"skipWaiting"| D
  D -->|"activate 事件成功"| E["activated"]
  E --> F["fetch 等事件开始工作"]
  B -->|"安装失败"| G["redundant"]
  D -->|"激活失败"| G

三个事件职责要分清。install 把 precache 清单里的资源下载进缓存桶，这一步要求”要么全部成功、要么整个安装失败”，因为半份缓存比没有缓存更麻烦；activate 清理上一版本遗留的桶，此时旧 worker 已不再控制页面；fetch 是拦截点，正确性依赖前两阶段留下的缓存状态。

一个容易忽略的细节：install 成功后，新 worker 默认停在 installed 等待，直到所有关联页面关闭才激活，这就是 waiting worker。原因是版本一致性——新脚本若已改变资源命名，而运行中的页面仍按旧产物 URL 请求，立刻接管会让同一页面混用两次构建的结果。

skipWaiting 加 clients.claim 用来跳过这个等待：前者让等待中的 worker 立刻进入激活，后者让它在激活后立即接管已打开的页面。

代价必须写在同一张评审单里。风险正是”正在运行的页面被接管”：页面在旧构建产物下启动，接管后它的请求由新 worker 拦截，而新桶里可能没有旧版资源的完整副本。典型症状是用户停在长会话页面，切走再切回来时行为变化，或页面状态与新版本接口约定不匹配，出现难以复现的报错。对表单填写、播放、协作编辑这类长生命周期页面，skipWaiting 的断裂感往往比多等一轮刷新更糟。

取舍建议：默认不启用 skipWaiting，把更新时机交给用户（下一节的做法）；只有确认没有长会话页面、或新版本不含破坏性接口变更时才启用。一定要自动更新的话，至少把 clients.claim 与 skipWaiting 分开考虑，前者风险远小于后者。

版本与更新：把”发现新版本”变成一个可点击的动作

更新判定的粒度很粗也很严格：浏览器重新下载 sw.js，与已安装脚本做逐字节比较，任一字节不同即视为新版本并触发安装。这带来两个反直觉结果。其一是”改了业务代码但 sw.js 没变，用户拿不到更新”：手写的脚本没被构建工具注入内容，无论发多少版都保持字节一致。其二是反向问题：把构建时间戳注入脚本，每次发布都产生新版本，包括什么都没改的发布。折中是注入本次发布产物清单的指纹而不是构建时间，让”内容有变化”与”字节有变化”尽量对齐。

时序是这样的：注册或页面访问时触发检查，发现新版本后安装；安装成功时 registration.installing 经历 installed，registration.waiting 出现新 worker，registration 派发 updatefound。此时旧 worker 仍在控制页面，直到 skipWaiting 或所有页面关闭。

由此得到一条应当作为团队契约的 UI 流程：发现新版本 → 用不阻断操作的方式提示用户 → 用户点击 → 通知新 worker 跳过等待 → 接管后刷新。

上面是 React 写法，Vue 3 里把 useState/useEffect 换成 ref 与 onMounted 即可。三点实现约定：controllerchange 只挂一次、且只在用户点击之后挂，否则开发环境里热更新触发的接管会把页面刷个不停；提示控件放在不影响操作的角落而不是模态弹窗，因为”有更新”几乎从不紧急；用户正在填写表单时把”立即更新”改成”稍后提醒”。

还有一个边界：如果新版本改动的是接口约定而服务端已切换，旧页面即使不更新也会坏。这类版本要绕过”用户选择”直接强制刷新，并在刷新前把未提交草稿写入 IndexedDB、刷新后恢复；这个动作要提前告知用户，不要做成静默。

缓存策略四式与判定依据

策略选择不需要灵感，需要判定依据。四式的标准都可以写成一句话：这个资源会变吗、变了能忍多久、拿不到时能不能降级。

cache-first：不可变静态资源

适用对象是带 fingerprint 的构建产物：JS、CSS、字体、图标。判定依据是”同一 URL 的内容永不改变”，因此命中即正确，网络只是冗余开销。

不要在以下场景用它：HTML 外壳，以及任何”URL 不变但内容会变”的接口。对 /api/* 用 cache-first，等于把一次响应用到了所有用户身上——缓存桶按 origin 共享，一个用户的私有响应会被另一个用户读到。凡带鉴权语义的响应，都不允许进入 cache-first。

network-first：会变的 API 响应

适用对象是”新鲜比可用性重要”的数据：未读数、权限配置、库存状态。网络优先，失败或超时才回落到缓存。

不要在以下场景用它：静态资源，以及任何”离线必须能打开”的关键内容——network-first 在无网络时必然先失败一次再回落，等待就是纯代价。另外 4xx/5xx 不要写入缓存，否则一次服务端故障会被固化成”永久错误”，恢复之后仍读到坏响应。

stale-while-revalidate：可容忍短暂陈旧、但要快

适用对象是列表页、详情页的次级数据、头像与缩略图。判定依据是”先给用户看到点什么，后台再把它更新成新的”。

不要把 SWR 用于需要明确时点的数据，例如支付结果、审批流当前状态。SWR 的语义是”给你的可能是旧的，而且我不告诉你”，用在需要精确性的数据上会产生用户与客服都说不清的问题；一定要用，就必须在界面展示数据获取时间，把陈旧度显式交回用户视野。

precache 与 runtime cache 的分工

两者角色不同，不要混用一个桶。precache 是构建期已知清单、安装期主动下载，保证”无连接冷启动能渲染外壳”，是确定性集合；runtime cache 是运行期按需收集，保证”访问过的内容下次能复用”，是会被淘汰的集合。常见错误有两个方向：把外壳放进 runtime cache，冷启动时它还没被写过，离线直接失败；把大量接口响应塞进 precache，清单不可控，安装期下载变慢甚至失败，新版本迟迟装不上。

一句话记忆：precache 管”一定能打开”，runtime cache 管”打开得快”，IndexedDB 管”内容是真的”。

缓存版本管理：precache 清单、清理与配额

清单在构建期生成，不在运行期猜

现代前端构建会把每个模块输出成带内容指纹的文件名，内容变则文件名变、URL 随之变化。这个性质正是 cache-first 可以”永久有效”的根据：URL 唯一标识了内容，命中缓存就不存在陈旧问题；反过来，产物名里没有指纹时，cache-first 就等价于”永不更新”。构建期要做的只是把最终产物列成清单，写进 Service Worker 能读到的模块：

activate 阶段清旧桶

缓存桶按版本命名是最低成本的管理办法：precache-<buildId>、runtime-v1、api-v1。新版本激活时把所有不属于当前版本的桶删掉，容量就能收敛在一到两个版本之间。

配额与持久化：只能定性依赖

navigator.storage.estimate() 给出浏览器愿意告知的用量与配额上限，navigator.storage.persist() 请求把 origin 标记为持久化以减少被自动驱逐。局限有三条：其一，返回值不精确，多数实现给的是与总磁盘空间挂钩的粗略估算，只能做趋势观察，不能拿来做业务判断；其二，persist() 的授予条件由浏览器策略决定，桌面端相对宽松、移动端更严，不能假定成功，必须检查返回的布尔值；其三，即使持久化成功，用户清除站点数据或磁盘紧张时的驱逐仍会发生。因此任何”离线时依赖这份数据”的功能，都要设计成数据可能整份消失后仍可恢复的形态。不要用配额数字回答”能存多少条离线工单”，可落地的表述是：本地观察给保守值、实现里做条数上限、超限时明确拒绝新的离线写而不是静默丢弃。

导航请求与离线回退页

导航请求是离线的分水岭。普通资源请求失败，界面只是缺一块；导航请求失败，用户看到的是浏览器错误页，前面所有缓存都等于白做，因此”离线可用”的验收必须单独覆盖它。

识别方式很直接：request.mode === 'navigate'。处理思路是三级回落——先试缓存里对应 URL 的文档，再回落到缓存的应用外壳（shell），最后才给离线专用页。shell 回落是”离线时深层路由也要能进”的关键：单页应用的深层路径（如 /app/orders/12345）通常不会作为独立文档被 precache，离线时命中不了任何缓存；此时返回外壳 HTML，路由初始化去读 IndexedDB 的数据，把界面渲染成”离线快照”。副作用也要看清：地址栏仍是原始深层 URL，外壳初始化逻辑若依赖服务端注入的数据，这条路径必须在无注入时也能跑。

几个实践约束：跨域且不可信的请求不要接管，接管了就等于把别人的故障变成你的白屏；ignoreSearch 对导航有用（能兜住带来源参数的启动地址），但用在接口上会让不同查询结果互相覆盖，两者要分开配置；离线页本身必须进 precache，且不引用任何未缓存资源，否则回退页也会渲染成残缺页面。

数据的离线读写：IndexedDB 与写操作排队

Cache Storage 是”请求到响应的映射”，没有索引、查询和事务。把大量业务数据塞进去会失去按条件取数、局部更新与迁移能力：它适合存 Response 原件，不适合当数据库。结构化数据的正确归属是 IndexedDB——一个事务型的浏览器数据库，按 object store 组织、可按 key 或索引取数，读写在 transaction 内完成；同 store 的写串行、读可并发，事务在浏览器认为空闲时会提前提交，不要假设”微任务里事务一定还活着”。

有了这层，”离线读”的做法是：请求成功后把结构化数据写入 IndexedDB 并记录获取时间，离线时取快照渲染，并在界面上明确展示”数据截至 10:24”，而不是把旧数据伪装成新数据。这比让 Cache Storage 兜接口响应更可控，因为你能决定存哪些字段、存多久、怎么清。”离线写”的骨架就是 outbox：把写操作先落成本地一条待办记录，界面立刻给出”已保存，待同步”，网络恢复后按顺序重放。

冲突处理只有三条现实路线，必须提前选定。最后写入优先靠时间戳覆盖，实现最简单，但多人协作时会静默吞掉别人的修改，只适合”数据只有本人会改”的草稿场景。服务端裁决是默认推荐：客户端提交本地副本与基线版本号，服务端返回冲突与最新版本，客户端再把修改合并上去。提示用户用于业务上不能自动决定的场合，例如金额与状态流转，把两个版本并列让用户选。本质上是在”自动化程度”与”用户预期”之间选边。

这也是为什么笔者反复强调：离线写是产品决策，不是技术默认项。outbox 的代码不难，难的是它改变了用户对”保存”的预期。动手前必须先回答四个问题：如何区分”已保存到设备”与”已保存到服务端”；重放失败几次后放弃、内容如何找回；服务端如何拒绝过期版本；重复提交如何幂等。

后台同步与推送的真实边界

sync 事件与 Background Sync 的意图很有吸引力：页面关掉了，仍由浏览器在合适时机把 outbox 里的操作补发出去；Periodic Background Sync 面向”定期把内容更新到本地”。但截至本文写作时，这两项主要只在 Chromium 系浏览器（桌面与安卓）可用，Safari 与 Firefox 的支持有限或不支持。也就是说，如果离线方案的正确性依赖 sync 被派发，那么在相当一部分设备上队列会一直躺着不动——这是静默失败，不报错，只让”已保存，待同步”永远停在待同步。

正确的架构是：Background Sync 只当加速通道，不做唯一通道。保底重放必须挂在页面自身可用的事件上：

sync 本身也要写成”有则更好”的形态：在 Service Worker 里监听它、调用同一个 flushOutbox()，只有清空队列才结束重试。这样 Chromium 上享受后台补发，Safari 与 Firefox 上退化为”下次打开页面时补发”，语义仍是完整闭环。

Web Push 的边界同样要写清。Android 侧（Chrome 及依赖其推送通道的浏览器）可用性成熟。iOS 侧需要较新的系统版本，且必须把应用添加到主屏幕之后才具备注册推送的条件——它服务的是已安装到主屏的 PWA，而不是任意 Safari 标签页，因此推送不能作为普适的离线唤醒手段；顺带一提常被误当成离线能力的 File System Access API：它在 Safari 与 Firefox 上不支持，涉及本地文件读写的功能要么走下载与上传的传统路径，要么明确标注为受限浏览器的增强体验。

可观测性与离线验证

Service Worker 的可观测性先天很差：它没有所属页面的控制台上下文，未捕获异常默认不会出现在开发者眼前，离线时的失败更没人看见。最常见的事故形态是”某台设备上一直读到很久以前的缓存”，而监控里一个错误都没有。对策是把它当成一个独立客户端接入上报：给一个专属 tag（例如 client: sw）和版本号字段，在 install、activate、fetch 的 catch 分支与 error 监听里显式上报。

要上报的关键事件有四类：安装失败、激活失败（多半是清理旧桶抛错）、拦截异常（策略函数抛错会被吞掉）、回落到离线页的次数——最后一项是判断离线体验最直接的代理指标。分母与比例都应标注为示意值；没有全量口径时，不要给出”缓存命中率 92%”这类数字。

离线测试要按矩阵做，而不是点一下飞行模式。四个维度组合起来才算覆盖：

  • 触发方式：DevTools 的 offline 复选框；throttling 断网但保留 DNS（能测出超时分支）；真机飞行模式；真机断 Wi-Fi 且关蜂窝。
  • 进入路径：先联网访问、断网后再访问（测 runtime cache）；直接无连接冷启动（测 precache 与外壳回落，最容易失败的一条）；断网点深层路由；断网从通知或桌面图标启动。
  • 版本状态：存在 waiting worker 时断网；清掉站点数据后断网；用户手动清除数据后断网。
  • 平台：Chrome 桌面、Chrome 安卓、Safari 桌面、Safari iOS、Firefox 桌面，各跑一遍冷启动。

灰度是最后一道保险。可行做法是按 URL 分桶：sw.js 这个稳定入口只读一个灰度开关（服务端注入或按用户 ID 取模），据此注册稳定版或金丝雀版脚本，新版本因此只对一小部分用户安装，出问题时关掉开关即可回退，不必等用户清缓存。回退路径要提前验证——只要旧 worker 还在控制页面，它就会继续按旧策略服务。

小结

离线能力是三件事：静态资源可用性、数据可用性、写操作可用性。分开设计，验收标准才写得出来；混为一谈，就会做出”能打开但没内容”或”有内容但不敢点保存”的应用。技术分配并不复杂——precache 保证一定能打开，运行时策略保证打开得快，IndexedDB 保证内容是真的，outbox 保证写出去的东西最终到服务端。

代价同样要如实写进方案。第一是内容陈旧：任何 cache-first 都在赌”这个 URL 的内容不会变”，赌错一次就是线上事故，所以指纹文件名不是可选项而是前提。第二是隐私与合规：缓存里的用户数据是一份真实存在、可被提取、会被下一个接触这台设备的人读到的副本，因此个人信息的离线保留要有明确范围、期限与清理路径，退出登录时必须连带清空对应缓存桶与 IndexedDB 数据。这在共享设备场景下尤其重要。第三是排查成本：Service Worker 让”为什么用户看到的和别人不一样”变成长期问题，没有独立上报与测试矩阵时，这类问题定位明显慢于普通前端缺陷。

因此建议的实施顺序是：先做静态资源层并把更新提示做扎实，再按需给少数接口加 network-first，最后才考虑离线写。每往下一层收益递减、复杂度递增，平台差异带来的不确定性也递增；把这三步拆成三次发布，比一次上齐稳妥得多。
