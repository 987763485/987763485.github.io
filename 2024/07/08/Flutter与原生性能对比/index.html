Flutter 与原生性能对比

“Flutter 性能到底好不好”这个问题在 2024 年仍然每天被问一遍，但它的形状是错的：自绘渲染与平台控件根本不是同一件事，脱离 UI 需求、测量口径和设备档位谈快慢，得到的只能是大话。本文把一次可复现的对比拆开写：哪些维度值得测、两侧各自的机制是什么、测量时哪些坑会让结论失真。读者应熟悉 Flutter 工程结构与至少一种原生 UI 栈；读完能拿到一套可直接套用的对比维度清单、一张“维度 → 机制 → 坑 → 结论形态”的对照表和一份分层的适用边界。文中所有具体数值一律是示意值，只说明本文的实验口径，不构成任何“谁更快”的结论。

一、先把问法改对：三个前提

常见的错误形状是把两个框架当成两个可互换的“运行时”，然后问哪个开销小。Flutter 的自绘渲染与 Android/iOS 的平台控件路线差异不在同一个轴上：前者把布局与绘制收进自己的引擎，向平台索取一块可绘制区域；后者把控件交给平台 UI 框架，由系统测量、绘制、合成，并顺带享受系统级行为（滚动链、文本排版缓存、系统控件的复用与状态动画）。拿这两条路线直接比“快慢”，就像拿开车与坐地铁比谁更快——答案取决于起点、终点和是否堵车。一次有意义的对比必须先钉死三个前提。

第一个前提是同一个 UI 需求。不是“做一个列表页”，而是把需求写到能约束两侧实现的程度：视觉规格（字体、行高、阴影、圆角、模糊）、交互规格（回弹曲线、下拉刷新、惯性滚动、转场语义）、内容规格（图片数量与尺寸、文本是否可变长、是否嵌入地图或视频）、数据规格（分页大小、接口延迟、首屏是否等待网络）。如果 Flutter 侧写了毛玻璃而原生侧只画了半透明矩形，后面测到的一切差异都会归因错误。

第二个前提是同一套测量口径：指标定义、采样方式、统计方式。冷启动从哪一刻算起、掉帧按次数还是按时长占比、内存看 PSS 还是总驻留，都要在动手前写成两侧共用的文档。同批服务端跨语言对比一文也遵循同样纪律，本文不复述“选型不等于跑分”这段论述，只强调结论必须写成“在某口径下观察到某趋势”。

第三个前提是同一设备档位与同一环境。本文示例档位写成 A/B 两档：A 档是当前旗舰，B 档是三四年前的中端机，这只是本轮实验口径，不代表任何市场结论。Flutter 侧以 3.19 与 3.22 两条线为参照，平台侧以 Android 14 与 iOS 17 为参照。换一个档位或系统小版本，趋势很可能变化——尤其那些与 GPU 驱动、字体回退、合成路径相关的维度，本就不该指望跨设备可移植。

钉死这三条之后，问题就从“Flutter 快还是原生快”变成几个可回答的小问题：在这个需求、这个口径、这台机器上，哪个维度出现了差距，差距来源是渲染速度、桥接层、编译产物形态，还是测量本身的误差。

二、结构性差异落在哪四个位置

后文每个对比维度几乎都能回溯到这四点之一。这里只做铺垫：三棵树与逐帧流水线在《Flutter 渲染引擎原理》一文已经展开，本文不重述。

布局与绘制的执行位置

Flutter 应用在平台上通常只呈现为一个 Surface（Android 侧常见是 FlutterView 一类载体，iOS 侧是引擎的 Metal 载体），Dart 代码在引擎内完成布局，再把绘制指令交给 Skia 或 Impeller 栅格化，最后由系统合成。布局与绘制的耗时都发生在应用进程内、由应用自己承担：好处是双端一致、可控；代价是拿不到系统为原生控件准备的那些优化（控件级裁剪、系统滚动优化、合成器的免绘制路径）。原生路线把界面交给平台框架：测量与布局在平台代码里跑，最终由 SurfaceFlinger 或 Core Animation 组装。同一个“列表滚动”在不同系统上的手感与耗时，很大一部分来自这一层，而不是来自语言执行速度。

文本渲染与字体

这是最容易被忽略、又最容易造成真实差距的一点。Flutter 自己排版与绘制文本：字号、行高、字距、字体回退、连字、双向文本、emoji 序列都要引擎处理，排版耗时是每帧布局的一部分，长段落与频繁换行尤其明显。原生路线直接用平台文本系统，回退链、字体度量与字形缓存由平台提供。两侧差异经常不是“谁算得慢”，而是字体回退命中了不同字形来源——同一句中文在两个实现里行高不同、换行点不同，看上去就像“性能不一样”。

无障碍桥接

屏幕阅读器不认识像素，只认识平台无障碍服务暴露的语义节点。原生控件天然带语义；Flutter 要在引擎里维护一棵语义树再映射、同步到平台无障碍 API。这层额外桥接是第八节的主线。

平台视图嵌入

地图、视频、WebView、广告、系统相机预览不可能由 Flutter 画出来，必须把真正的原生视图嵌进来。画面于是从“一块自绘 Surface”变成“多块内容要跨边界合成”，带来纹理化、额外拷贝与输入事件路由的复杂度，这是第七节的主线。

这四点决定了性能差异不会均匀分布在所有屏幕上，而是集中在文本、无障碍、平台内容嵌入与启动形态这几个结构性位置上。设计对比维度时就该沿这些位置去切，而不是笼统地“跑一个 demo 看帧率”。

三、对比维度设计与测量手段配对

本节是全文的核心。维度选错了，后面所有数字都是噪声；维度选对了，即使一次也不跑分，也能把“差距会出现在哪里”讲清楚。九个维度的两侧机制与测量坑集中在文末对照表里，这里只写测什么、为什么要单开一栏。

九个对比维度

首帧与冷启动。测点击图标到第一帧上屏、到内容可交互。这一栏跨设备最不稳，也最容易把系统闪屏算错。

滚动帧时间与丢帧。测每帧耗时分布与超预算帧占比。Flutter 的布局、绘制与栅格化全在应用进程内完成，原生侧交给平台框架并享有系统滚动优化；差异更可能来自画了什么，而不是用了什么语言。

复杂动画。测转场、多层变换与并行动画数量。它必须与滚动分开：滚动卡在内容供给，动画更多卡在合成与栅格化；原生侧不少转场与惯性由系统驱动，主线程卡顿也停不住它——这常被误读成“原生动画更快”，实际是责任线程不同。

长列表复用。测内容异构、高度可变的长列表被快速滑动时的稳定性。ListView.builder 按需构建，RecyclerView 与 UITableView 走复用池，两种模型的成本浮现位置不同，同一个滑动速度未必压到同一段成本（第六节展开）。

内存与 GPU 内存。测稳定态驻留、进出页面后的回落、长时间滑动后的增长趋势。两侧都要拆口径分别记，只测一个总数会让比较失去意义（第九节展开）。

包体。测分发口径的体积而非磁盘占用，并写明取的是 AAB 下载量、APK 还是产物文件之和、是否拆分 ABI。Flutter 有一块与业务代码无关的引擎与快照，两侧减体积的手段完全不同。

图片解码。测首屏图片从读取到上屏的时间与解码后位图占用。差异常常不在解码速度，而在默认是否做了向下采样——那是实现选择而非框架属性，算到框架头上是典型的归因错误。

平台通道往返。测发起调用到取回结果的时间，重点在负载大小与调用频率。跨语言要走编解码与线程切换，原生侧是同进程调用；这里即便有差距也是边界问题而非渲染问题。机制见同批混合开发一文，单侧优化见同批 Flutter 性能优化一文。

启动后的 JIT/AOT 差异。测同一界面第 1 次与第 20 次进入的耗时是否收敛。Dart 的移动发布形态是 AOT，Android 侧 ART 的安装期编译与运行期 JIT 并存，前几次不同是预期行为；debug 模式是 JIT 且带大量断言，绝不能进对比。

两侧测量手段要对齐

维度定了，还要保证两侧工具强度对等。Flutter 侧的骨干是 timeline 事件：DevTools 的 timeline 面板按 UI 线程与 Raster 线程分段展示，能把耗时归到构建布局绘制还是栅格化；业务区间可以用 dart:developer 的时间线接口打点，让两侧产物对齐同一份时间轴。

编译模式对齐比工具本身更关键，这是最容易翻车的地方。debug 带 JIT、断言与调试通信，帧时间与启动时间完全不具代表性；Profile 保留符号与采集、又去掉 debug 开销，才是用于对比的档位；release 最接近线上但可采集细节少。原生侧同理，Android 的 debug 构建与 iOS 的 Debug 配置都不能进对比。两侧必须同时停在“为采集而构建”那一档：

四、冷启动与首帧

冷启动是最容易被做坏的维度，因为“首帧”至少有三种定义：进程创建到系统显示闪屏、进程创建到应用自己画的第一帧、以及到内容真正可交互。Flutter 的启动链比原生多几步：装载引擎动态库、映射 AOT 快照、初始化引擎与 isolate、加载字体与资源、跑完第一帧再提交给系统合成；原生侧是进程与运行时初始化、平台应用组件创建、首个界面控制器与布局。两侧的“第一帧”并不自动对齐，要么统一到“图标点击到第一帧上屏”，要么把系统闪屏单独列一栏，否则数字看着像结论其实是定义差。

系统闪屏在 2024 年特别容易造成误会。Android 12 之后启动画面由系统统一提供，原生与 Flutter 应用都会被覆盖一层；把这段算进冷启动，两侧差距会被显著“抹平”，因为大家共同多了一段与框架无关的时间。合理做法是拆成“闪屏结束到首帧”与“点击到可交互”两段记录，iOS 侧的启动图与首屏资源加载同理。

首屏之后的热身效应也要单列一栏：Dart 的 AOT 发布产物意味着业务代码不需运行期编译，而 Android 侧 ART 的 JIT 与配置文件引导编译会让前几次进入同一界面的耗时不同。把第 1 次与第 20 次都记下来，比只报第一个数字负责得多。

五、帧预算：滚动、动画与每帧的分工

谈掉帧先要谈预算，而预算由刷新率决定：60 Hz 下每帧约 16.7 ms，90 Hz 约 11.1 ms，120 Hz 约 8.3 ms——这些是按刷新率折算的口径数字，不是实测结果。把 60 Hz 当默认事实是最常见的错误，2024 年的中高端 Android 机大量默认 90 或 120 Hz，不少还会自适应切换。所以测量前要锁定刷新率或在结论里写明锁定值，并把“超预算”定义成随刷新率变化的阈值而不是固定毫秒数。同一份代码在 60 Hz 上顺畅、在 120 Hz 上出现可感知抖动是正常观察，不是“高刷下崩了”。

每帧内部分工要能归因，否则“掉帧”没有信息量。Flutter 一帧里发生构建、布局、绘制指令生成，再交栅格化；细节见《Flutter 渲染引擎原理》一文，这里只用它的结论：UI 线程段与 Raster 线程段是两条独立的预算消耗，前者超预算表现为手指跟随迟、内容供给不上，后者表现为画面本身一顿一顿，阴影、模糊、大面积裁剪尤其明显。原生侧同样要分清主线程的测量布局、渲染线程的提交与合成器的组装，Choreographer、dumpsys gfxinfo 与 Instruments 各给一层。

滚动掉帧与动画掉帧成因不同：滚动成本来自每帧要供给多少新内容（条目数量、文本排版量、图片是否就绪、高度是否可变），动画成本来自每帧要重画多大面积、多少层。两者在同一页面里可以各自超标，所以脚本要分出“纯滚动段”与“纯动画段”，各取一段分布。

最后是数字纪律：本文不给“Flutter 帧率多少、原生多少”这类结论，只给“在示意负载（例如 200 条含图片与富文本的条目）与示意设备上，两侧超预算帧占比呈现某种趋势，且换负载方向后趋势可能反转”这样的表达——负载与设备一起交出去，结论才可复核。

六、长列表：两种复用模型，不是一快一慢

Flutter 的 ListView.builder 与 Android 的 RecyclerView、iOS 的 UITableView 代表两种模型。前者按需构建：可见区域加一点点近邻范围才会创建对象，滚出去的部分不复存在；后者是复用池：视图被回收、绑定新数据再挂上去，视图层级本身反复使用。

差别在成本的形状。按需构建把成本摊在“每帧要新建多少东西”上，条目越复杂、文本越长、图片越多，浮现得越明显；复用池把成本挪到绑定与回收这一步，视图创建只发生在池子还没热的阶段。用同一个固定滑动速度压两侧，未必压到同一段成本：速度很低时构建侧几乎看不出来，速度很高时两侧都掉帧。所以这个维度可复现的测法是同时记录两个量——单位时间内新建了多少视图对象，以及超预算帧的分布——只看帧时间会得出误导结论。

各自的坑也要摆在同一张桌子上。Flutter 侧：条目高度不确定时，构建与布局会分两次到来（先按估算再按真实内容重排），滚动条位置与惯性行为显得“不干净”；给定高可以让布局跳过测量，但那是单侧优化，见同批 Flutter 性能优化一文。原生侧：复用池的坑集中在“绑定的东西没清干净”（异步图片回填到已经滚走的条目上）、回收时机与可变高度的相互作用、缓存范围与内存占用的取舍。两边共通的难点是异步高度——数据决定高度、高度影响可见范围、可见范围又决定要不要请求数据，这个环在两个框架里都得人工切断。

结论形态因此只能是“两种模型在不同负载形状下各有优势区间”：条目定高、内容轻、速度快时，复用池的摊薄效果很容易体现；类型高度异构、进入退出频繁、需要动态插入大段富文本时，按需构建的简单性更容易守住帧预算。“谁一定更快”在这个维度上没有答案。

七、混合内容的代价：平台视图与文本输入

平台视图嵌入

地图、视频、WebView、广告与系统相机预览只能由原生视图提供，嵌进 Flutter 有两条路：把原生视图内容渲染进纹理、再让它参与 Flutter 自己的合成；或者走混合合成，让系统合成器同时参与 Flutter 层与原生层。前者便于统一做变换与裁剪，代价是多一次内容落进纹理的开销与额外 GPU 内存；后者保留原生行为特性，代价是层叠顺序、变换能力与输入事件路由都变复杂。要强调：到 2024 年为止，Android 上这条路线仍在演进，几种方案在不同系统版本、不同视图类型上的表现并不一致，某个 demo 上的观察不能当成普遍结论，只能逐项验证。iOS 侧路径与 Android 不同，问题更多集中在层顺序、手势竞争与视频类视图的坐标系上。

测量上这一维度要单独开一页：同一份需求分别测“纯 Flutter 页”与“含平台视图页”，否则平台视图的开销会被算到自绘渲染头上；视频还要另记解码与内存这笔账，它与 UI 帧时间是两件事；落在平台视图上的触摸要单独验证响应，因为它走另一条事件路径。本文不给具体百分比损耗——那个数字与视图类型、尺寸、是否常驻强相关，写出来只会误导。

文本输入与输入法

Flutter 的文本框是自绘的，但输入交互必须与平台输入法连接：虚拟键盘、候选词窗口、组合中（composing）区间的更新、选区与光标拖拽。原生输入控件的这些都由系统直接负责，所以这一维度的差异往往同时混合性能与行为两部分。谨慎的表述是：到本文口径为止，中文输入法的组合区间回填、光标与选区处理、剪贴板与富文本粘贴仍在持续改进中，不宜断言“完全等同原生”。

测量时要把输入法固定成同一个（系统自带与第三方输入法行为差别很大，换输入法等于换实验条件），分别记录按键到字符出现的响应趋势、组合区间更新时一帧的重绘面积、粘贴长文本后的排版耗时。多数情况下真正的问题不是帧率而是行为缺陷，因此这一栏的结论形态建议写成“同一份人工用例清单上的通过情况加响应时间趋势”。

八、无障碍桥接：差距最容易出现的维度

屏幕阅读器（Android 的 TalkBack、iOS 的 VoiceOver）读的是平台无障碍服务暴露的语义节点，它不认识像素。Flutter 因此在引擎内维护一棵语义树，再由桥接层映射、同步到平台 API。这条链决定了与原生对比里最容易出差距的往往不是渲染速度，而是语义覆盖与同步时机：原生控件天然带语义与状态，Flutter 侧要求开发者为自定义控件显式声明角色、标签、值与提示；一旦某个交互控件没被标注，它在无障碍视角里就是“不存在”，而帧率一切正常。同步本身也有代价——语义树更新要节流、要跟随界面变化，滚动中的动态内容与焦点顺序最容易出问题，但把这类问题归因成“自绘渲染慢”是错的，根源在桥接层。

检查做法是从语义视角而不是视觉视角过一遍界面：用 showSemanticsDebugger 把语义框叠在界面上，确认每个可交互元素都有框、文本与角色对得上；再用 debugDumpApp() 与渲染树调试输出把 Widget 与语义节点一一对上，找出漏标与错标；DevTools 里也有让语义树常开的入口，便于没有真机阅读器时先做静态核对。验收口径应与同团队原生应用共用同一份人工清单，在 TalkBack 与 VoiceOver 上各过一遍、逐条记录而不是打总分。

小结

对比两类技术栈的性能，结论的可靠性取决于实验设计而不是立场。先固定设备、系统版本、构建模式与网络条件，再把指标定义成能操作的时间段（首帧、稳定滚动帧时间、冷启动到可交互、内存平台值、安装后包体），然后按”自绘一致性、启动、渲染、平台通道往返、内存与包体”逐维度看成因。诚实的写法是把优势与劣势一起写：自绘带来跨端一致与动画可控，代价是包体、内存、桥接与无障碍这类系统红利需要自己补。任何数字都应标注为同一台机器上的示意值，团队自己的设备与业务形态才是最终依据。
