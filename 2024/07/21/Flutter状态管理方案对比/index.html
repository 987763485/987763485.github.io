Flutter 状态管理方案对比

Flutter 项目里关于状态管理的争论几乎每年都要吵一遍，但很多争论从提问方式上就偏了：它们在比“哪个库更好”，却没有先问“这段状态属于哪一层”。本文不给任何跑分，先把 setState、ValueNotifier、InheritedWidget 这些语言层手段讲透，再从可测试性、依赖注入、与 BuildContext 的耦合、编译期安全、样板量、心智模型、上手成本与可调试性这些结构性维度，比较 Provider、Riverpod、Bloc/Cubit 及其他方案的适用边界。读完你应该能为自己的项目定出一条“默认方案加例外条件”的规则，并知道万一选错，退出代价由什么决定。

状态的二分：先把问题问对

Flutter 语境下的“状态”混着两类东西。第一类是 ephemeral state，即页面内状态：只属于某个 Widget 内部，页面销毁就消失，不跨页面共享也不需要持久化，典型如 TextField 正在输入的文本、TabBar 选中第几页、卡片展开还是收起、列表滚动偏移、表单当下的校验提示、一段动画的进度。第二类是 app state，即应用级状态：登录态、购物车、用户偏好与配置、待同步到服务端的操作队列、多页面共享的筛选条件，特征是跨页面可见、生命周期比创建它的 Widget 长、往往还要落盘。

区分两者有个可操作的问法：这段状态被谁读。一个 Widget 自己或它的直接子树读完就够，放 Widget 内部；两个互不嵌套的 Widget 都要读，才考虑往树的上层提一层；跨页面都要读，或应用重启后还得存在，才是 app state。三档分清，方案选择通常自己就收敛了。

本文的基本判断是：绝大多数方案之争，根源是没先做这个二分（经验判断，不是统计结论）。把 Tab 索引塞进全局 store，等于让局部状态背上全局通知的成本，还把读它的页面统统拖进重建列表；把登录态藏在某个 StatefulWidget 里靠回调往上抛，就会引出“这库不好用”的抱怨。两种情况下真正的问题都在分层，不在库。State 与 Widget 体系基础见同批环境搭建一文。

由此得到第一条纪律：能用 setState 解决就不要引库。setState 的重建范围天然被 State 所在子树框住，没有第三方生命周期要理解，测试时挂载 Widget 就能断言；引入一个库等于给全项目加一条“所有人都得遵守”的规则，收益必须大于学习与维护成本才划算。反向含义同样成立：状态确实要跨页面共享时，硬用 setState 加回调链去凑也是债。

顺带划界：Web 侧状态库的范式差异见同批 Pinia 一文，单向数据流的思想源头另有旧文，本文不以它们的结论替代 Flutter 侧分析；渲染流水线、三棵树与重建的优化手段都不在这里重讲，本文只把“方案如何影响重建范围”当判断入口。

语言层面的原生手段

先把 Dart 与 Flutter 自带的三件东西讲清楚，它们既是很多场景的完整答案，也是所有第三方库的地基。

setState：标记脏，重建当前 State 的子树

setState 的语义不是“修补视图数据”，而是两件事：把当前 State 标脏，并安排一次调度，让框架下次构建时重新执行这个 State 的 build。所以它的重建范围就是“当前 State 的整棵子树”，兄弟与父节点不受影响。两个常见误解值得点出来：它只在 Widget 仍挂在树上时合法，异步回调里对象已销毁再调用会报错；在 build 过程中调用会立刻触发同一帧再次构建，等于自找重入，任何“构建时改状态”都应视为设计信号而不是技巧。

ValueNotifier 与 ValueListenableBuilder：把监听下沉到叶子

ValueNotifier 是带单一值的通知源，给 value 赋值就通知监听者；ValueListenableBuilder 在它下面单独开一个构建点，只有这个构建点的子树随通知重建。价值在于监听粒度可选：状态不必属于当前 State，兄弟节点也能共享同一个 notifier，外层 build 完全不参与。页面内多个控件共享一段状态时，把它挂在页面 State 上就比引库轻、比回调链清楚。代价是 notifier 由谁创建、谁释放全凭约定，没有编译期检查；它只表示一个值，派生状态要么手算要么再挂一个 notifier，链条一长就成了手写的响应式系统。

InheritedWidget：所有方案的共同地基

InheritedWidget 做的是“沿 Widget 树向下传递一个值，并让读取者自动订阅”。dependOnInheritedWidgetOfExactType 一次完成两件事：向上找最近的同类型实例取值，同时把当前 Element 登记为该实例的依赖者。当祖先位置换上新实例，框架按 updateShouldNotify 的返回值决定是否通知，返回 true 时所有依赖它的 Element 被标脏重建。这就是它能替代外部库的原因：跨层共享加变更通知这两个需求，框架已经给出最小完备机制，库的工作大多只是把它包装得更好用。

限制也来自机制方向：只能向上找、只能向下通知。兄弟节点要互通，必须让共同祖先持有；想在树之外读写这个值，就得另建一个持有者对象。手写成本也不低，Scope Widget、of 静态方法、updateShouldNotify 判断这套三件套，每类共享状态都要重复一遍。Provider 受欢迎正是因为它替你写完了这遍样板，Bloc 的 provider 包与 Riverpod 的 ProviderScope 也都在树上放一个继承性节点，把外部容器接进依赖系统。所以“要不要引库”的实质问题是：要不要让别人替你维护这层 InheritedWidget。

重建范围：评价任何方案的入口

有一个说法比“哪个库更快”有意义得多：状态放得越高，重建越多。读取者会登记为依赖者，值一变，所有登记过的 Element 都要重建；把状态放到树根附近意味着潜在读取者覆盖面极大，你很难保证某个中间层的 build 没跟着做无用功。这不是某个库的缺陷，而是依赖订阅模型的固有代价，所以它成了横向比较各方案最好的入口。

判据只有一条：同一份状态，两种写法谁更容易把重建范围写小。收窄重建有三条通用手法。一是让不依赖状态的部分成为 const 构造，参数全为编译期常量时实例可复用，框架发现实例未变就不必重建对应子树。二是把监听下沉到叶子：外层只管布局，真正读状态的那个小组件单独包一层构建点。三是派生选择：不订阅整个对象，只订阅比较出来的标量或不可变片段，值没变就不通知。Provider 的 context.select、Riverpod 的选择器式读法、Bloc 里按状态字段做 buildWhen 之类的判断，本质都是第三条。

于是本文对“性能”的态度很明确：不比库之间的跑分，也不给基准数字，差异主要由“你写出的重建范围”决定——一个把全部页面状态塞进全局 store 的项目，用哪个库都会卡。看方案时该问的是：这套 API 鼓励我把监听下沉、把状态切片，还是诱导我反手取整个 store。至于把重建当头号成本之后怎么优化，同批性能优化一文已经承担。

Provider：官方封装的能力与边界

Provider 的定位要先说准：它不是新的状态模型，而是 InheritedWidget 的官方推荐封装，加上对 ChangeNotifier 这类通知源的订阅管理。它解决的具体问题就三个：手写 Scope 的样板、类型查找的繁琐、通知源生命周期没人管。这三点做得干净，是它长期成为默认选择的原因。

创建方式按用途分四类。Provider 只往树里放一个对象、不负责通知，适合 Repository 这类“放进去就够了”的依赖。ChangeNotifierProvider 放一个 ChangeNotifier，负责在子树移除时释放它，并在 notifyListeners 时通知订阅者。FutureProvider 把异步计算结果放进树，读到的是进行中、成功、失败的统一表示。ProxyProvider 声明“我的值依赖树上其他 provider”，依赖变化时重算，是把多个来源合成一个视图的正规做法，风险是链子一长就成了看不见的依赖图。

读取方式三种，误用后果不同。context.read 只取一次值、不登记依赖，在 build 里用它改状态就是构建期副作用。context.watch 登记依赖、值变则重建，是 build 里表达依赖的正规写法；一处 build 里 watch 多个对象，等于把这些对象的变化全部算进当前子树的重建成本。context.select 只订阅派生值，是收窄重建的首选。Consumer 与 Selector 只在 build 整体很大、你只想让一小块响应时才需要，日常用得比文档暗示的少，因为 context.select 更直接。

缺点要如实写。第一，ChangeNotifier 是运行时通知：谁订阅了什么、变更波及哪里，编译期没有任何信息。第二，它通知全部订阅者，Provider 自身不做值比较，改一个字段就让订阅整块的人全部重建，除非自己切片。第三，忘记 dispose 是常见隐性泄漏，特别是自己创建却未交给 ChangeNotifierProvider 管理的对象。第四，最容易走偏的是把它当完整的依赖注入容器，逐层叠十几个节点成一座塔，读一次值要穿过很长的链。第五，可达性由树位置决定，动态插入子树时容易遇到“找不到 provider”的运行时报错。

Riverpod：把依赖关系前移到声明里

先给定位，这点容易被讲错：Riverpod 是 Provider 作者对同一问题的重新设计，不是 Flutter 官方内置能力。差异有两条。一是 provider 不依赖 BuildContext：它是顶层的普通声明，谁依赖谁写在声明里，而不是看它在树上的位置，于是读一个不存在的 provider 成了编译期就能暴露的错误，也不会因放置位置不同而表现不同。二是 provider 本身就是依赖声明：构造里用 ref.watch 写明自己读谁，整张依赖图由库掌握。

StateNotifier 与较新的 Notifier 都承担“状态转换写在这个对象里”，后者不必自己构造持有者、更像普通类，两者对外都只给一个不可变状态值。真正的价值在派生链：totalProvider 不需要知道购物车怎么通知它，只声明读 cartProvider，变化由库顺着依赖图传播，这类派生恰是 Provider 里最难干净表达的部分。

生命周期是第三个卖点。默认 provider 只在被监听时存在，最后一个监听者消失就可以回收（autoDispose 语义），正好对上“页面关掉这块状态就该消失”的直觉；要跨页面存活时用 keepAlive 常驻。它把忘记释放那类问题从靠纪律变成靠机制。

测试能力最被称道。ProviderScope 接受一组覆盖项，测试时只把数据源 provider 换成假实现，其余代码一行不改；不挂 Widget 时还能直接构造一个根容器，让纯逻辑状态在没有树的情况下跑测试。两种覆盖的差别在作用域：挂在某个 ProviderScope 上只影响这棵树的读取，落在根容器上则影响该容器的全部读取。集成测试里选错作用域，会出现“这个用例生效、那个不生效”的怪事。

代价也必须写清。第一是概念量：family（按参数生成 provider 实例）、autoDispose 与 keepAlive（生命周期策略）、override（覆盖机制）三层各自不难，但要一起理解才能预测行为，新人第一周常问的是“为什么这个 provider 又重建了”。第二是口径变化：它在当前这一代里把写法从函数式 StateNotifier 逐步挪向 Notifier 与代码生成方向，教程里新旧混着，搜到的例子未必适合当前主线，团队需要一份内部写法约定。第三，上手曲线确实比 Provider 陡。第四，它的依赖图仍是运行时传播，编译期安全主要体现在引用是否声明存在、读取时机是否合法，别误解成类型层面的依赖检查。

Bloc 与 Cubit：显式状态机的回报和代价

Bloc 的定位不是状态容器，而是把业务状态做成显式状态机：外界投递事件，状态机消化事件产出新状态，Widget 只渲染状态。链上每个环节都显式——事件是类型，状态是不可变类，转换是集中一处的逻辑，输入输出可以一一对应地测。Cubit 是同一套东西的简化档：不定义事件类型，直接在对象上暴露方法，方法内部 emit 新状态；省掉事件这层仪式，保留状态转移集中一处、对外只发不可变状态这两个核心。

BlocBuilder 与 BlocListener 的分工要讲准。前者管“状态变了要重画什么”，可以带一个条件在新旧状态上决定是否重建，这正好对上派生选择；后者管“状态变了要做的一次性动作”，比如弹提示、关闭键盘，回调不参与构建树。把副作用放进 listener 而不是 builder，是 Bloc 项目在纪律上容易守住的结构性原因：API 形状本身在提醒你构建里别做事。

为什么业务流程复杂、状态转移要审计的项目里显式性有回报？因为这类项目的难点不是显示值，而是回答“现在为什么是这个界面、上一步是什么、还有没有请求在飞”。显式事件流让这些都有唯一去处：变更入口是事件类型，可逐个列出逐个测；出问题时看事件序列就能复盘；“不许在 Widget 里直接改状态”是硬约束而不是约定。示意地讲，一个有确认、校验、支付、重试四段的下单流程，用事件枚举写出来本身就是一份可评审的流程文档。

缺点同样明确。一是样板量：简单开关页也要状态类、事件类、bloc 类、挂载四件套，行数远超裸 ValueNotifier。二是简单页面被仪式化：Tab 索引这类局部状态一旦顺手搬进 bloc，就是拿状态机做布尔变量。三是团队接受度：不接受事件流范式的团队会把 bloc 写成 setter，反而比 Provider 更难读。四是它同样是运行时通知，依赖靠构造传入（比全局单例干净），但谁在读这个 bloc，编译期不知道。

本文不把 Bloc 当成最推荐的架构：它的收益取决于状态转移是否真的复杂、团队是否愿意把纪律写成结构，流程薄的后台硬套它，只会得到一堆除了一处赋值什么都没做的空壳事件。

其他方案的诚实定位

mobx_flutter 走响应式模型：状态字段声明为可观察量，逻辑写在 action 里，界面包一层 Observer，读时自动建立依赖、写时自动通知。好处是代码形态自然，接近“直接赋值、界面跟着变”，样板比 Bloc 少很多。代价来自依赖追踪是隐式的：界面到底读了哪些可观察量要运行时才知道，重建范围比显式订阅的方案更难预测，调试“这一帧为什么重建”要顺着隐式依赖反查；这类追踪与需要脱离 Widget 环境的场景（服务端渲染、纯隔离单元测试）配合也更麻烦。

get_x 提供的是“控制器加全局依赖加响应式变量”的一体化方案：控制器基类承载页面状态，靠全局注册表按需取实例，配一套 obs 风格的响应式变量与局部重建 Widget，还带自己的路由与消息机制。优点是快，建页面到能跑几乎不用铺垫，赶工期的原型、单人维护的工具类 App 里很有效。缺点也直说：与框架强绑定，路由、依赖、状态三件事都被约定接管，脱离约定就讲不清状态从哪来；全局单例式取依赖让可测试性变差；实例创建与释放由注册表决定，忘记删除就长驻，跨页面复用同名控制器还需额外规范。把它定位成“高效率的框架化方案”最准确，而不是通用状态管理库。

信号（signal）一类的细粒度响应式范式，在 2024 年年中仍属社区探索：核心是“读时订阅单个信号、写时只通知这个信号”，把重建粒度推到比整个状态对象更细的一层，思路对收窄重建确实直接。但当时它在 Flutter 侧只是若干实验性包的形态，没有稳定的公开 API，没有成规模的生产案例，也没进入官方口径，选型不该把项目押在仍在验证范式的方案上。

依赖注入维度：可测试性的差异从哪来

各方案在“外部依赖怎么进来”上差别很大，而这一条几乎决定了可测试性的高低。

方案 依赖注入方式 测试时替换数据源
Provider 沿 Widget 树注入 测试顶层套一层替换数据源
Riverpod 声明即依赖图 覆盖数据源或直接建根容器
Bloc 与 Cubit 构造函数注入 直接 new，无需 Widget 树
mobx_flutter 自建 Store 配定位器 手换依赖再挂观察器
get_x 全局注册表取实例 先清全局实例防互串
裸 ValueNotifier 没有注入机制 靠构造参数手工传

分层与模块化的工程结论

不管选哪个库，能长期维持的项目基本都是同三层。Repository 层负责数据来源：网络、磁盘、缓存、字段合并，只吐数据模型，不知道 Widget 存在。状态转换层（Notifier、Cubit、Bloc 都算）把数据与用户动作合成一份可渲染的不可变状态，是唯一允许改状态的地方。Widget 层只读状态、只发意图，不做业务判断。三层边界守住，换库成本可控；守不住，用哪个库都会烂。

最典型的反模式是“巨型全局状态”：一个 store 装着登录信息、购物车、主题、草稿、埋点开关，所有页面都从根上取整个对象，新人问“这个字段谁在改”没人答得上来。后果有三条：任何页面都要知道整个 store 的形状，改一处要全库搜引用；变更判定只能比较整个对象，字段级切片形同虚设，重建范围被迫放大；测一个只读主题的小组件也得把整个 store 搭起来。重构路径也是三步：按功能切片，把 cart、session、settings 拆成独立提供者；在切片上加派生选择，组件只订阅算出来的小值；最后把 app state 降格成若干 feature state，跨功能交换交给 Repository 层而不是状态层互读。

迁移与共存

从 Provider 迁到 Riverpod 的步骤是四步，而不是一次重写。第一步只做读取层抽象：把状态对象与业务逻辑从 Widget 里抽出来，让它们不依赖 context，这一步不动任何库。第二步建桥：用一层 provider 包住既有的通知源，新代码读桥，旧代码按原方式读。第三步按 feature 迁：一次只换一个模块的读取入口，模块内全走新写法，模块外一律不动，并给迁移期定一条门禁（团队约定示例：新写的共享状态不许再用旧方式接入）。第四步收尾，桥上的引用清零后删掉旧挂载点。之所以禁止一次性重写，是因为状态层是全局骨架，同时改骨架和业务逻辑，出问题时无从归因。

共存边界同样要说清。Provider 与 Bloc 并存可以解释：页面内流程状态交给 Bloc，跨页面注入的东西用 Provider 传，但注入的应当是数据来源而不是可变状态，否则会出现这页的 Bloc 在改同一个对象、那页又在 watch 它的局面，两条通知链互相覆盖，谁先到达没有语义保证。跨页面共享登录态时，让 Repository 持有唯一的会话对象，各页面状态机各自监听这个来源同步自己，比让两个状态层互写安全。硬规则是：并存方案超过两种就是债（团队约定示例），因为新人要学两套纪律，状态流向要在两张图上追。

选型决策树

把前面的判断串成一棵树，顺序很关键：先问是不是跨页面共享，再问状态转移是否需要审计与可回溯，再问团队是否接受响应式范式，再问是否要求编译期依赖安全，最后才看新人上手窗口。

flowchart TD
  A[这段状态要跨页面共享吗] -->|不要| B[能否用 setState 或 ValueNotifier]
  B -->|能| C[就用它，不引库]
  B -->|不能| D[Provider 挂到合适层级]
  A -->|要| E[状态转移要审计与复盘吗]
  E -->|要| F[Bloc 或 Cubit]
  E -->|不要| G[团队接受响应式写法吗]
  G -->|接受且测试要求高| H[Riverpod]
  G -->|不接受| I[Provider 加内部约定]
  H --> J[要求编译期依赖安全吗]
  J -->|要求| K[以声明式 provider 为准并统一写法]
  J -->|不要求| L[按上手窗口收口]

落到默认建议：小项目、以页面内共享为主，用 ValueNotifier 或 Provider；中大型且流程复杂、需要看得见状态转移轨迹，用 Bloc 或 Cubit；中大型但状态以派生与缓存为主、测试要求高，用 Riverpod；只有局部状态这种需求的原型，就停在 setState。至于选错会不会推倒重来，判断依据不在库而在分层：三层边界守住，替换实现只是逐模块重构；三层混成一团，哪怕不换库，第一次需求变更就已经在重写了。

五条反模式与修法

第一条，把 UI 局部状态提到全局。Tab 索引、折叠开关进了全局 store，代价是所有相关页面一起参与重建，收益为零。修法回到二分：出现两个互不嵌套的读取者才往上提一层，能挂在页面 State 上就别往容器里放。

第二条，在 build 里写副作用改状态。构建过程中调用会改状态的方法，轻则同一帧重复构建，重则死循环。修法是把副作用挪到明确的事件回调，或挪到库里“只做事不构建”的监听入口。

第三条，状态里塞不可序列化的对象，例如 BuildContext、滚动控制器、动画控制器。后果是这份状态无法复制、无法持久化、无法在 Widget 销毁后安全持有。修法是状态里只放数据，控制器留在 State 层持有并在销毁时释放。

第四条，用状态库当事件总线。往 store 里塞一次性消息，通知语义就被当成消息队列用，测试要构造整个状态才能触发一次动作。修法是分清值与事：值放状态，一次性动作显式表达、消费完就消失。

第五条，任何改动都触发根重建。原因是订阅了整块状态、外层 Widget 太大、构造里缺 const。修法是三条通用手法轮着上：派生选择、监听下沉到叶子、常量构造。

小结

状态管理的第一步不是选库，而是把 ephemeral state 与 app state 分开：能用 setState 解决就不要引库。所有方案的共同地基是 InheritedWidget 那套沿树传递并通知订阅者的机制，库之间的差别在样板、生命周期、依赖表达与可测试性，不在谁更快。评价时该问三个问题：谁更容易把重建范围写小，谁的外部依赖在测试里换得掉，谁的状态转移在半年后还看得见。Provider 胜在概念量低，Riverpod 胜在依赖声明与可覆盖，Bloc 胜在显式与可复盘，get_x 胜在快，代价都写在各自强项的背面。最后仍回到分层：三层守住，选型只是工程偏好；三层不守，换哪个库都只是暂时的。
