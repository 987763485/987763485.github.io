Spring Cloud 微服务实战

本文假设你能用 Spring Boot 把单个服务写完跑起来，现在要把若干服务装配成一套能上线的系统。Spring Cloud 不是引入一个依赖就拥有微服务，它是一组规范加一份版本编排，重点因此全在装配与排查：注册发现配哪几项、超时怎么分层、网关边界在哪、配置刷新会丢什么、容错组件的叠加顺序为何比阈值更要紧。拆分边界不在本文范围。

定位：Spring Cloud 是规范与版本编排

最容易产生的误解是把它当成与 Spring Boot 平级的框架。它实际是一份契约加一份目录：定义服务如何自我描述、如何被发现、失败时如何自保，再把每条能力交给可替换的实现项目。你要决策的是每条能力选哪个实现、用什么版本组合。

本文口径是 2023.0.x 这条发布列车，对应 Spring Boot 3.2；Boot 3.3 已于 2024-05-09 发布并过了一个月线，纳入考虑前仍要按官方兼容矩阵核对。这一代最关键的变化有两条：一是命名空间统一到 jakarta.*，沿用旧命名空间的教程代码直接编译不过；二是 Spring Cloud Sleuth 已被 Micrometer Tracing 取代，仍按 Sleuth 搜配置项属于旧口径。

组件选型地图

注册发现的原理、CAP 与心跳机制已有旧文覆盖，本文只写怎么配、怎么查。

版本对齐：BOM 是唯一可信的耦合点

痛点先在依赖树：Boot 版本与发布列车强绑定，列车的兼容区间决定哪些 starter 能被加载；越过区间后先出问题的是自动配置类找不到、配置键被改名、第三方 starter 仍在引用旧命名空间。

做法是只在一处声明版本：Maven 的 dependencyManagement 导入官方 BOM，业务依赖一律不写版本。

Java 侧按 17 起步，21 可用；两者混用时 CI 必须锁一个。

为什么只升一个组件会炸：BOM 把列车验证过的版本定成基准，子模块里手写一个新小版本等于绕开验证集，把冲突留到运行时，典型症状是启动期抛 NoClassDefFoundError，或某个自动配置静默不生效。纪律三句话：升级以列车为单位整体升；升之前用 mvn dependency:tree 出一份前后差异；任何手写版本都要在评审里写明理由与退出时间。

注册与发现：配哪几项、僵尸实例怎么查

决定线上行为的只有三类：我是谁、怎么被判定健康、多久报一次。实例 ID 默认带主机名与端口，容器里每次重启都变，要显式指定成稳定形式；元数据挂区域、权重、灰度标，消费端的负载均衡读的就是它们；健康检查要指向真正的活性端点，而不是进程还在就返回正常的地址。

注册中心整体不可用时客户端不会立刻瞎：本地缓存着上一次拉到的注册表，有效期内继续可路由，所以短时故障多表现为新实例上不了线，而非全站雪崩。危险的是缓存刚过期又恰逢实例下线，调用方拿着过期视图连向死进程。排查按四步走：注册中心里该实例的状态与最后续租时间、调用方缓存刷新周期、实例下线的动作序列、探针与优雅关闭是否对齐。

僵尸实例多半是下线动作做了一半。正确序列是：先转不可服务，等一个完整的”续租加摘除”周期，再停止接收新请求并等在途请求返回，最后关连接池。应用侧要开启容器与生命周期的优雅停机，等待时长长于在途请求的最大耗时；编排侧要让就绪探针的失败能被服务发现读到，否则注册中心摘除与入口摘除之间留有空窗，那段时间的报错就是典型的间歇性连接被重置。

OpenFeign：超时是两层的，重试会叠乘

接口定义没有悬念：带客户端注解的接口加一组 Spring Web 注解。值得花时间的是契约与编解码——接口包被上下游共享时，会把超时配置甚至领域模型一起传播出去，这是后面反模式第三条的根源；编解码器在客户端级配置类里替换，让 4xx 与 5xx 落到不同异常类型。

超时最常被配错。Feign 层的连接超时与读超时，和底层 HTTP 客户端的连接池等待，是两套参数，必须分开设定：前者管这次调用允许多久，后者管从池里拿到一条连接允许等多久。只配 Feign 层而底层等待更长时，连接池被慢调用占满，请求先堵在获取连接这一步，上层超时形同虚设。

日志级别单独提醒一次：完整级别会把请求体与响应体全部打进日志，高并发下性能代价明显，更会顺手把令牌、手机号写进采集链路。生产只用最简级别或关闭。

重试的坑在于叠乘：Feign 自带重试器，负载均衡层可能配置了换实例重试，网关可以再重试一次，应用层还能套一层 Resilience4j 的重试——四层各两次就是十六倍调用量（示意推演），正好撞在下游最脆弱的时刻。纪律是只保留一层重试，通常留在容错组件那一层，其余全部关掉；开启重试的路径必须幂等。

换掉默认客户端的动机很实际：要连接池复用，要更细的连接获取超时，要把池占用作为指标暴露给 Micrometer。换成 JDK HttpClient 或 OkHttp 之后，池上限与每路由上限要一起配。

Spring Cloud Gateway：三段模型与一条纪律

模型只有三段：路由是容器，决定匹配到什么、转给谁、经过哪些处理；断言负责匹配，路径、方法、请求头都能作为维度；过滤器负责改写请求与响应。

鉴权放网关合理，但边界要认清：网关判的是凭证是否有效、请求能否进入，不是这个用户能不能改这条订单。授权语义属于业务服务，网关一旦开始判业务权限，就等于复制了一份领域规则，两边必然漂移。全局过滤器对所有路由生效，是排查时最容易被忽略的一环。

限流按调用方维度做，KeyResolver 取租户或客户端标识，它保护的是入口不被冲垮；服务自身的并发保护交给容错组件，两层不能互相替代。最后一条纪律：网关不要做业务编排——不在网关里聚合多个服务，不在过滤器里写业务分支，不用路由条件表达业务规则。

配置中心：加载顺序、刷新与密钥红线

加载是有先后的：本地配置文件、环境变量与命令行参数、远端配置源按优先级合并；远端再按应用名、profile、命名空间或分组分层，通用在上、应用居中、环境最具体。这套顺序的意义只有可预测：同一个键出现在两层时，谁覆盖谁必须能由文档回答。

刷新的坑几乎都一样：刷新让带刷新作用域的代理指向一个新的 Bean，字段被重新注入，实例里保存的运行态随之清零。计数窗口、本地缓存、正在累积的批处理、注册在实例上的监听器，都属于刷新一次就蒸发的状态。纪律是把状态放到进程外，或把这类 Bean 排除在可刷新范围之外，并给刷新事件本身留一条日志。

密钥红线三条：不明文进配置文件、不进任何会被打包或推送的存储、读取动作要留审计。示例值一律用占位符，例如 ${DB_PASSWORD_PLACEHOLDER}；传输与落盘要加密，权限按应用与命名空间隔离，撤销要能追到人和时间。配置中心是配置仓库，不是密钥仓库。

Resilience4j：组合顺序比阈值更关键

状态机原理见旧文，这里只谈装配。配置项的语义要清楚：滑动窗口的类型与大小决定统计分母，失败率与慢调用率阈值决定何时跳闸，最小调用次数避免样本不足时误判，打开后的等待时长与 half-open 期间放行的探测调用数决定恢复有多保守。下面的数值全是团队约定示例，评审要问的是依据是什么。

函数式包装的顺序才是真正说了算的地方，因为注解决定不了你手工组合时的嵌套关系。

把重试包在熔断外面是最典型的放大事故：熔断已经打开，失败以毫秒计，重试器却把它当成可以再试一次，于是一次逻辑调用在短时间内对着已经拒绝的下游打满全部尝试量。确实要让重试在外时，两件事必须同时做到：重试显式忽略熔断拒绝类异常，退避带随机抖动。TimeLimiter 只作用于返回异步结果的调用，同步方法上加它不产生效果；Bulkhead 放在重试之内限的是并发尝试数，放在之外限的是并发逻辑调用数。

链路与指标：一个 traceId 对上一条曲线

接入差异只有一处：追踪实现换成了 Micrometer Tracing，日志通过 MDC 拿到 traceId 与 spanId，跨进程靠 W3C 上下文头传播，网关、调用方、被调方三段日志能被同一个 traceId 串起来。采样率是唯一直接影响成本的开关，策略按错误全采、正常按概率来配，数值由团队按流量规模约定。

指标用 RED 三件：请求率、错误率、时延分布，命名按服务、调用方向、依赖名组织，让网关侧耗时与调用侧耗时能对上。两侧都带上对端服务名与自身 span 标识：网关看到的是端到端时间，客户端看到的是含连接等待的时间，两者之差就是入口与取连接的开销，别拿它们互相验证绝对值。

迁移与灰度：拆出来的服务怎么挂上

拆出来的服务按这个顺序挂上：先注册但不接流量，把只读接口打通，验证发现与调用链；再按最小范围放开写接口；灰度靠请求头驱动，网关按头部把流量切到带灰度元数据的实例，注册中心侧用权重把新实例的接收比例从小往上抬；最后把老路径下的同名实现改成代理，观察一个完整周期后删除。回滚路径必须在灰度前就写好。

组件存量要单列一句：Zuul 1、Ribbon 与 Hystrix 都已处于维护或退役状态，Hystrix 的模式本仓库旧文已有讲解，本文不复述，新项目一律走 Spring Cloud Gateway、内置负载均衡与 Resilience4j。存量迁移不必一次换完，但要停止在旧组件上增加新功能。

五条反模式

  1. 把注册中心当配置存储：元数据塞满业务开关，没人知道哪个值生效，重启顺序决定行为。
  2. 在网关写业务逻辑：聚合、分支、权限判定进了共享基础设施，一次改动变成全站发布。
  3. Feign 接口与领域模型双向耦合：共享包让上游字段变更逼着所有下游一起发布。
  4. 超时层层放大：上游给 5 秒预算，下游是三次两秒的重试，预算早就不够。
  5. 熔断阈值调到”永不熔断”图省事：保护逻辑从没被验证，第一次真跳闸时没人敢信。

小结

三件事再强调一遍：版本只能成组演进，BOM 是唯一可信的耦合点；超时与重试必须在各层之间分层设定，否则叠乘的雪崩一定发生；保护机制的价值来自可观测的失败信号，静默成功的降级等于没有降级。把上面这张表贴进评审模板，逐条确认谁配了、依据是什么、怎么回滚，比多读十篇教程有效。单服务内部的开发口径见同批的 Spring Boot 一文。
