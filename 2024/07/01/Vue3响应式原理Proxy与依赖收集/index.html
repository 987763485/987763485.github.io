Vue 3 响应式原理：Proxy 与依赖收集

Vue 3 把响应式的底层从 Object.defineProperty 换成 Proxy，改的不只是一套 API，而是”系统何时才知道数据变了”这个模型。本文写给已经会用 reactive 与 ref、却被”这样写为什么丢了响应性”困扰的读者：先说清 Proxy 拦住了哪些操作，再用一份手写实现拆开依赖收集与触发，解释懒代理、effect 栈、调度器为何把两次赋值合并成一次渲染。全篇以 Vue 3.4 为口径。

为什么 Vue 3 换用 Proxy

Vue 2 用 Object.defineProperty 把 data 的每个属性改造成 getter 与 setter，并在初始化时递归遍历整棵对象；那套 observer 与 Dep、Watcher 的配对细节已有专文拆解，本文只回答”这条路走到了哪里走不动”。

属性级的 getter 与 setter 有三个结构性缺口。第一，它感知不到属性的新增与删除——这个键上从未挂过拦截器，写一个不存在的键就是普通赋值。第二，数组索引赋值与 length 变化难以自然覆盖，只能给数组打补丁、重写原型方法。第三，Map 与 Set 的读写发生在内部槽位而非可拦截的属性上。还有一条常被忽略的成本：为了拦截任意深度，初始化时必须遍历所有层级，而渲染往往只用到其中一小部分。

reactive 的懒代理与三层缓存

reactive 不在启动时遍历整棵对象，只在 get 里判断取出的值是否需要代理，需要就地创建并缓存。深层属性的响应式是被”访问”出来的：没读过的嵌套对象连代理都不存在。初始化成本因此换成了按需成本——代价从”遍历全量”变成”每次读取都穿一层 Proxy”。

去重靠一个 WeakMap：键是原始对象，值是代理对象，保证同一原始对象在同一代理类型下永远拿回同一份代理，否则每次读取都新建 Proxy，缓存与依赖都会乱。选 WeakMap 而非 Map，是为了让被丢弃的原始对象能正常回收。

这里有三个容易踩的点。其一，reactive 的返回值与原始对象判等永远为 false，别拿 state === raw 做分支。其二，把代理对象当作 Map 的键、再拿原始对象去取值会取不到，它们是两条不同的哈希路径。其三，在 toRaw 的结果上读写都绕过 trap，既不触发也不收集。

ref：Proxy 拦不住基本类型

Proxy 只能代理对象。let count = 0 这类基本类型，赋值发生在变量绑定上，外部没有可拦截的对象入口，于是 Vue 3 提供 ref：把值装进对象的 value 属性，再用 getter 与 setter 拦截这个属性。可以说 ref 是”给基本类型补一个可被 trap 的属性”的容器，代价是所有读写都要显式写 .value。

依赖收集的数据结构

依赖关系不是一张”谁用了谁”的全局大表，而是三层索引加一组双向引用：最外层仍是 WeakMap，从原始对象索引到一张属性表；属性表是 Map，键是属性名，值是 Dep；Dep 是”一个属性一个收集器”，持有当前正在读这个属性的那批副作用。副作用这边叫 ReactiveEffect，反过来记录自己依赖了哪些 Dep。

flowchart TD
    A[原始对象 state] --> B[WeakMap 索引到属性表]
    B --> C[属性 count 对应的 Dep]
    C --> D[渲染 ReactiveEffect]
    C --> E[computed ReactiveEffect]
    D --> F[effect 的 deps 列表]
    F --> C
    G[set count] --> C
    C --> H[通知订阅者 走 run 或 scheduler]

双向关系有两个用途。正向的 Dep 到 effect 集合用于触发：写入时取到 Dep，把订阅者逐个调度。反向的 effect 到 Dep 列表用于清理：effect 重新执行前，它依赖的属性可能已经变了（渲染分支切换、computed 换了依赖组），必须把自己从旧的 Dep 集合里摘出去，否则一个不再被读取的属性会永久把组件吊在更新队列里。3.4 的实现中 ReactiveEffect 与 Dep 是两个互相持有的类，effect 停止时沿 deps 反向断开。

effectStack 应对的是嵌套：渲染 effect 跑到一半，模板读了某个 computed，它的 effect 随即开始跑。若只有一个 activeEffect 变量，内层跑完外层就成了 null，之后的读取全不被收集，组件对这些属性永久失感。栈的做法是入栈、指向自己、执行、出栈、指回上一层，嵌套再深也能还原，内层只记自己那次读取，与外层互不串味。computed 的求值同样在自己的 effect 里进行，因此记下一组独立依赖并在变化时重新收集。

这份代码也交代了调用时机：track 只可能发生在副作用同步执行期间。事件回调、定时器、await 之后的读取都在 effect 之外，activeEffect 为 null，读什么都不建立依赖——这是后文失效场景里最常见的一条根因。

迭代依赖、触发范围与调度

键集合本身也是可读的东西，却没有属性名可用，Vue 3 用内部哨兵值 ITERATE_KEY 顶替：for in、Object.keys、展开运算符收集到的依赖都挂在它上面。Map 的 get 与 has 依赖具体那个键，size 与遍历依赖 ITERATE_KEY。只有增删键才改变”有哪些键”，所以改已有键的值不必通知遍历类依赖，删除一个键必须通知，否则列表不会重跑；数组长度走的是 length。

触发时先定范围：set 一个属性通知同 key 的 Dep，本次是新增就补上 ITERATE_KEY，数组额外带上 length。范围内还要过一次值比较，hasChanged 的语义与 Object.is 一致，新旧值相同直接返回；NaN 是个细节，朴素全等会因 NaN !== NaN 把”又写一次 NaN”判成变化，Object.is(NaN, NaN) 为 true，正好堵住这个口子。

被通知的 effect 怎么跑是第三件事。裸 effect 同步执行，组件的渲染 effect 带调度器：把自己压进按组件去重的队列，在微任务检查点统一冲刷。下面这段只会渲染一次：

computed 与 watch 家族

computed 的 getter 只在被读取时执行，这就是惰性。内部一个脏标记加一份缓存：依赖变化时不重算，只置脏；下次访问发现脏才求值，求值在自己的 effect 里跑，顺带重新收集一遍依赖；没人访问，这次变化就永远不产生计算。多处读同一个 computed 拿到同一份缓存，这是它与”写个函数每次调用”的实质区别。

取舍也就明确了：派生一个要被模板或多处读取的值，用 computed；要在状态变化后做一件外部的事（发请求、写日志、操作非响应式对象），用 watch 家族。computed 里不该写副作用，因为执行时机由访问决定——这次变化可能根本不触发，可能多次变化合并成一次求值，也可能在你看不见的地方被访问两遍。副作用的归宿是 watch，它的执行次数与依赖变化有确定的对应关系。

依赖来源与两种正确写法

watch 的依赖来自你显式给出的源：一个 ref、一个 getter，或一个响应式对象。watchEffect 的依赖来自回调运行期间读到的所有响应式属性，不需要声明。差别决定可读性：源多又碎时 watchEffect 省事，但你多加一行读取就会悄悄扩大触发范围；只关心某个属性时，watch 加 getter 更稳。

三种 flush 各有用途：pre 是默认值，在组件更新前执行，适合改状态；post 在更新后执行，适合读已渲染的 DOM；sync 同步执行，只在需要”写完立刻可见”时用，代价是放弃批处理。deep 是一次递归 traverse，把所有属性都读一遍，开销随规模线性增长，大列表与深层结构别随手加，能精确到 getter 就精确到 getter。一次性监听用 once，配合返回的 stop 与 effectScope 管理成批副作用。状态管理库那一层不在本文范围，另见专文。

shallow 系列与性能边界

深度代理的成本分两段。一是创建：懒代理只在属性被读到时才为嵌套对象建 Proxy，没访问过的子树不花钱，一旦整棵读完，创建量就与规模成正比。二是访问：处于深度代理下的对象，每次属性读取都要穿一层 trap，这笔成本不在初始化时，而在运行期反复支付。深拷贝的代价则一次性落在初始化时，且不产生后续拦截，两者不要混为一谈；本文的对比都是定性的，自测数字请标注为示意值。

图表实例、富文本引擎的内部模型这类对象最适合交给 shallow 系列：它们内部有大量互相引用的 getter，被深度代理后不但读取全程穿 trap，还可能因为内部引用被代理替换而行为异常。shallowReactive 只代理第一层属性，shallowRef 不代理装进去的值、只在引用变化时触发，markRaw 给对象打上永不代理的标记；引用没变而内部状态变了时，用 triggerRef 手动通知。

失效场景与 API 对照

序号 场景 修法
1 const { count } = state 解构后改值不更新 用 toRefs(state) 解构，或把 count 单独声明为 ref
2 state = reactive({ ...state }) 整体重绑 组件内改成逐属性赋值或 Object.assign(state, patch)
3 在 toRaw(state) 的结果上读写 需要绕过代理就用普通变量，别混在同一份数据上
4 setInterval 回调里读 state.x 却不再触发 在 effect 外读取不收集依赖，改为 watch 驱动或在回调外先取值
5 模板里对装在普通对象中的 ref 漏写 .value 只有顶层 ref 与 reactive 属性上的 ref 才自动解包

第 2 条的根因是被替换的引用脱离了模板原先收集到的那个 Dep；第 3 条不是偶尔不生效，而是永远不生效。

小结

Proxy 把拦截粒度从属性提升到操作，换来对增删、数组与集合的覆盖，也把成本模型改成了懒代理。依赖收集的结构是三层索引加 Dep 与 ReactiveEffect 的双向引用，以及一个被 effectStack 保护的 activeEffect。写了不触发，多半是 hasChanged 拦下同值；渲染不重复，是调度器把更新合并进了微任务。ref 与 shallow 系列不是语法糖，而是”Proxy 管不到”与”代理代价高于收益”这两条边界上的补丁。排查失效时先问一句：这次读取有没有发生在某个副作用的同步执行期间。
