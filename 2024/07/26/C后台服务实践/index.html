C# 后台服务实践

本文讨论不接收请求的那部分代码怎么写：消费消息、清理数据、跑批、对账。难点不在语法，而在生命周期——宿主何时启动你、何时要求你停下、你悄悄死掉谁来发现。阈值类数字一律标注为示意值或团队约定示例。

后台服务的三种形态

后台服务指不由外部请求驱动、自己决定何时干活的代码，.NET 里常见三种形态。进程内伴随任务与 Web 宿主同进程，比如请求处理完往通道塞一条审计记录、每隔几分钟清一次本地缓存；好处是共享连接池、不必独立发布，代价是故障域重合——线程池饥饿或内存压力时接口和任务一起难受，伸缩永远跟着请求量走。Web 侧写法见同系列 .NET 一文。独立 Worker 服务是没有 HTTP 入口的宿主进程，Console 程序加通用主机，自己订阅队列、自己连库，发布、伸缩、告警全独立。平台调度任务不常驻，由 cron 或流水线定时按点拉起，跑完退出；cron 语法不在本文范围，同系列已有专文。

选哪种，判据是任务失败会不会影响用户请求：一挂接口就变慢、超时报错的，与请求同生共死，该跟 Web 一起部署；报表晚几分钟不影响在线用户的，没理由占用 Web 的进程和发布窗口，拆成独立 Worker 或交给平台调度。辅助判据是伸缩节奏：请求随流量波动，任务只看积压量，两者不一致时拆开更划算。

IHostedService 的真实契约

IHostedService 只有两个方法：StartAsync(CancellationToken) 与 StopAsync(CancellationToken)。宿主在启动阶段按注册顺序调用各实现的 StartAsync，全部返回才认为应用启动完成；关闭阶段按相反顺序调用 StopAsync。这两个时机决定两条纪律。

第一条：StartAsync 里不能直接跑长任务。它没返回，宿主就认为应用尚未启动完毕，就绪判断和后续步骤全卡在它后面；在这里 await 一个三分钟的批处理，进程启动时间就被拉长三分钟。托管为 Windows 服务时更糟，服务控制管理器等待启动确认的时间窗远短于批处理耗时，会直接判定启动失败。StartAsync 的职责是点火：建资源、登记回调、把工作交给另一个任务，立刻返回。

第二条关于超时预算。StopAsync 的令牌由宿主构造，取消时机来自 HostOptions.ShutdownTimeout，.NET 8 默认 5 秒（这是默认值，不是官方推荐值），而且这一份预算由全部后台服务共用，不是每个各分 5 秒：前面的收尾慢一点，后面的可用时间就被吃掉。

BackgroundService 的简化

BackgroundService 不是另一套机制，它就是 IHostedService 的一层模板方法：StartAsync 调用你重写的 ExecuteAsync，拿到返回的任务便让启动立刻完成；StopAsync 取消 stoppingToken，再等那个任务收尾，最多等到预算用完。你只填循环体。标准骨架是循环、延时、停止令牌三件套：

两处容易写错。OperationCanceledException 要用 when 条件包起来，才分得清正常收工和真出事，外部取消与内部故障都会抛它。Task.Delay 是结束之后再等，不是每 30 秒一次，一轮耗时算不进周期；不传 stoppingToken 则是后台服务关得慢的头号原因。

一个宿主注册多个 BackgroundService 时，StartAsync 按注册顺序串行点火，但每个都立刻返回，所以各 ExecuteAsync 实际并发。别把注册顺序当执行顺序：先注册不代表数据先就绪，有依赖要靠显式握手——通道、状态表、就绪标志。关闭按相反顺序进行且共用超时预算，这也是别往一个宿主塞太多长任务的理由。

为什么不直接用 ConcurrentQueue 加轮询？因为那要你自己重造通道已提供的四件事：容量上限（没有上限就没有背压，只有 OOM）、等待唤醒（空转烧 CPU 或 Sleep 引入固定延迟，而先判空再睡必然有丢唤醒的竞态）、取消语义、完成通知。忙等轮询写起来简单，查起来最难。

幂等与多副本协调

多副本之后，”每天凌晨跑一次”会变成每个副本各跑一次。协调手段按可靠性排队。数据库唯一约束与去重表：处理前先插一条带任务标识和轮次标识的记录，靠唯一索引让先到者赢；失败模式是键的粒度——太粗误判重复，太细挡不住重复，且表要清理。乐观锁版本号：更新时带版本或状态条件，影响行数为 0 说明别人已做完；失败模式是只保护单行，跨表动作仍靠前者。

分布式锁与租约续期：锁只保证多数时候只有一个，它不是幂等。最凶的失败模式是持锁副本经历一次长停顿——大 GC、网络分区、节点被驱逐——租约到期，另一个副本拿到锁，而前一个还在写。所以续期失败必须立刻放弃本轮，而不是再试一次。专门的调度系统（Quartz 集群、Hangfire、分布式调度平台这类定位）由调度器把一次触发只分给一个执行者，代价是调度器自己成为要运维的单点，错过触发的补偿策略得显式配置。

结论请写在 README 上：幂等靠存储层的唯一键最可靠，锁只是减少浪费。

与消息队列对接

Worker 最常干的活儿是消费。各产品 SDK 方法名不同，我们只按订阅、确认、拒绝这套语义谈，三条必须落到代码里。第一，处理成功再确认：拉取即确认等于把投递语义降级成最多一次，队列说消息处理完了、库里却没有那行记录，这类事故事后无从追溯；失败时拒绝让它重投，重投到上限进死信，死信必须有告警，否则它是个静默的数据坟场。第二，并发消费者数量要和下游容量匹配而不是和积压量匹配：下游是数据库时活跃消费者数不能超过连接池供给量，否则人人攥着一个连接等另一个，直接死锁在池上；下游是外部接口时先问限流配额，上调并发的前提永远是下游先扩容。第三，关闭顺序不能反：先停止拉取，再等在途消息完成并确认或拒绝，最后退出。先退订再收尾，最坏只是多等一会儿；先退出再退订，得到的是一批被强杀的处理和一批反复重投的消息。

sequenceDiagram
    participant H as 宿主
    participant S as 消费者服务
    participant Q as 消息代理
    H->>S: 关闭信号，取消 stoppingToken
    S->>Q: 停止拉取，取消订阅
    S->>S: 等待在途消息处理完成
    S->>Q: 逐条确认或拒绝
    S-->>H: ExecuteAsync 返回

在途消息要显式记账：一个计数器加一个可等待的结束事件，收到关闭信号后把新消息的门关掉，再等计数归零；等不到的那些必须走拒绝路径，把归还交给队列的可见性超时机制，而不是假设它们会自己完成。

定时与周期任务

固定间隔的活儿首选 PeriodicTimer。老的 Timer 回调是同步方法，往里写 async void 会让异常击穿线程池，套一层任务派发又丢了”这轮做完没有”的通知；PeriodicTimer 是 await 语义，到点返回真值、取消时抛 OperationCanceledException，且天然串行——上一轮没做完，下一轮不会插进来。

但周期不等于时长保证。一轮跑 45 秒、间隔设 30 秒，不会有两个循环并行，也不会补跑两票，本轮结束后立刻拿到下一个 tick，”每 30 秒一次”就退化成连续不断地跑。按”每天固定次数”做的容量估算会被这类漂移算错。

至于”每天凌晨三点”这类日历需求，通用主机不提供 cron 表达式解析，这是现实：要么引入第三方调度库（Quartz.NET、NCrontab、Hangfire、Coravel 均属此类定位，版本与接口以项目实测为准），要么把准时性交给平台调度，进程只负责被拉起来干活。

异常与重启策略

ExecuteAsync 抛出未处理异常不会只影响这一轮：异常会上报给宿主，由 HostOptions.BackgroundServiceExceptionBehavior 决定处置——默认的停宿主在容器里表现为进程退出、被平台重新拉起，在 Windows 服务里表现为服务停止；配成忽略则只剩一条日志，任务从此悄悄不再运行，比崩溃更难发现。所以重启要自己写在任务级：宿主级重启牵连同进程的其它任务、丢弃所有在途、重建连接，多副本还容易同时重启形成启动风暴。退避节奏属于任务本身——指数增长、上限封顶、每步加抖动，连续失败到阈值必须发出告警，而不是静默重试到天亮。

优雅关闭与超时落地

关闭阶段可以拆成三步：停止接收新工作、等待在途收尾、放弃等待继续释放。HostOptions.ShutdownTimeout 约束中间那一步，默认 5 秒，这是框架默认值而不是官方推荐值，对单轮可能跑几分钟的批量任务几乎肯定不够；要按任务实际时长设定，让它略大于可接受的最长一轮，例如团队约定示例里的 3 分钟，同时确认部署平台的关停等待与它匹配——设得过长会拖慢滚动发布。

flowchart TD
    A["收到停止请求"] --> B["按相反顺序调用各 StopAsync"]
    B --> C["stoppingToken 被取消"]
    C --> D{"ExecuteAsync 在预算内返回?"}
    D -->|是| E["正常释放容器，进程退出"]
    D -->|否| F["放弃等待，继续释放"]
    F --> G["在途工作被强杀"]

容器里 SIGTERM 由宿主的生命周期组件接住，转成同一个取消令牌，所以 stoppingToken 上等到的就是这次信号；若进程没接住信号，或者作为子进程运行而父进程不转发，再合理的收尾代码也等不到执行。托管为 Windows 服务时触发源换成服务控制管理器的停止请求，代码里看到的仍然是取消令牌，把进程注册为服务这类能力由平台扩展提供；两边真正的差别是关停窗口由平台各自决定，预算耗尽后一律强制结束。

小结

后台服务的可靠性来自把四类职责分开：启动时把配置、依赖与健康检查一次校验清楚，运行期用宿主承载单例与调度，出错时用重试策略表达”哪些故障值得再试一次”，关闭时用一个取消令牌贯穿所有等待点。最容易踩的三个坑都出在边界上——配置缺失要在启动时就失败而不是运行到一半抛异常，异常处理要让宿主知道服务的真实状态，收尾逻辑要在关停预算内完成否则等于没做。把这些写成模板并让新服务复用，比每次重写一遍启动代码可靠得多。
