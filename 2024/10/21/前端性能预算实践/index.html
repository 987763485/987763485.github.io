前端性能预算实践

导读：本文不谈怎样把某个指标改好，只谈怎样让已经改好的结果不被下一个需求吃掉：预算管什么、基线从哪里取、新功能如何申请额度、超限由谁负责、检查点挂在哪条流水线上。口径先说清：INP 已在 2024 年 3 月取代 FID 成为 Core Web Vitals 指标，FID 自 2024 年 9 月起不再在报告中展示，本文以 INP 为交互维度主线；文中所有体积、耗时与阈值均为示意值或团队约定示例阈值，不代表任何真实站点或行业分位数据。

为什么”优化过”不等于”守得住”

性能曲线常常是锯齿形的：立专项把首屏从很难用改到能用，三个月后回到原样，半年后更差。问题不在不会优化，而在优化产出的余量没有被制度保护，成了一块谁都可以来占的无主地。压缩、分割、预加载这些手法，既有的优化清单与体积治理文章已经写得很细，本文只主张一件事：这些成果需要被预算约束。

退化的三种来源

新功能。活动页加一块轮播、列表页加实时预览、结算流程加一次风控校验，单个需求都无害，落地时却常附带新的图表库、日期库、动画依赖和几张未压缩的运营图；它最隐蔽，因为提需求的人并不认为自己做了性能决策。

第三方脚本。营销、客服、埋点、A/B 实验、社交登录多由非前端角色申请，直接在模板里插一个标签。它们不进构建产物，因此不被构建期检查看见；它们阻塞解析、抢占主线程、把 LCP 推后，更新节奏还不受我们控制。

依赖升级。框架小版本、组件库、polyfill 集合、打包器插件的升级由补漏洞或拿语法支持触发，评审者关心兼容与 API 变更，很少有人把体积差当作阻断条件：组件库从按需引入退化为全量引入、某个 loader 改动让 tree-shaking 失效，都能在 CI 全绿时让首屏 JS 涨几十 KB（示意值）。

三者共同点：都是一次增量决策。增量决策的审查标准里若没有性能这一项，退化就是必然结果。

一次性专项为什么必然失效

三个结构性缺陷。产出物不可持续：专项留下的是”当前状态很好”这个事实，不是”当前状态必须这样”这个约束，人一走约束就没了。反馈滞后：解散后看板还在但没有值班人，等下个专项立项，数据已经坏了两个季度。归因失真：专项成果常被说成”某项改动带来多少提升”，同期却还伴随 CDN 更换、页面改版、流量结构变化；没有对照的观察不足以支撑因果结论，团队因此高估某些手法的收益，把预算建立在错误经验上。

预算制度换了什么

把性能从目标改写成预算，是把愿景句改造成可执行契约。目标句”首屏要快”无法判定谁做错了；预算句”首页首屏 JS 压缩后不超过 180 KB，其中框架层 60 KB、业务组件层 80 KB、页面内联逻辑 40 KB，超出即阻断，责任人是模块 owner”（数值均为团队约定示例阈值）可以判定、可以追责、可以复审。四个部件：对象要落到文件或请求；分配要让工程师写代码前查得到自己额度；门禁要规定检查环节与阻断或告警；责任要规定谁审批、债务记在哪、多久复审。

预算对象：先能落到文件与请求

“LCP 不超过 2.5 秒”是结果指标，它没告诉工程师该做什么决策：影响因素有十个，手里只有一行代码。把预算写成一组指标数字是最常见的失败形态，它必须同时给出结果指标与手段指标，而手段指标要落到文件名与请求 URL 上；指标定义与单项改善手法属于指标优化专题，本文不重复。

包体：以首屏实际加载集合为口径

全量产物总大小对性能没有解释力，因为代码分割之后很多产物首屏并不下发；合理口径是”首屏关键路径上会下载的 JS 与 CSS，按压缩后字节计”（示意值：首页 JS 180 KB、CSS 45 KB），并且压缩按生产环境实际编码测量、vendor 与业务代码分账，否则依赖升级的增长会被业务代码变化掩盖。

关键是能指到文件。给每个 chunk 建归属映射——属于哪个模块、哪个团队、哪个 owner——是预算能执行的前提：没有映射时超限信息只能写成”产物超出预算”，有映射时可以写成”chart 相关 chunk 较基线增长 32 KB，基线 18 KB，本次 50 KB，负责人 @xxx”（数值为示意值）。

请求数与关键路径

请求数预算管要建多少条连接、要串行多少轮往返，可拆成几个可数的量：首屏 HTML 之后的关键脚本数、关键 CSS 数、首屏接口调用数、字体文件数、首屏图片数。串行深度比总数量更值得管：并发十个请求未必慢，但”取配置 → 取用户信息 → 取列表 → 取详情”这种四段串行会把四个 RTT 串到 LCP 前面。

图片、字体与主线程

图片口径用总量加单张上限两条一起写（示意值：首屏图片总量 400 KB，单张不超过 120 KB），字体口径用文件数、压缩后字节与是否阻塞文本可见（示意值：中文字体不超过 2 个文件、总量 300 KB）。

交互维度同时管总量与最坏样本：总量口径是首屏任务执行总时长与长任务数量（示意值：长任务不超过 4 个、单任务不超过 150 ms），最坏口径用 INP 的真实流量分位。一次偶发但在场的长任务能把部分用户的 INP 推到很差，所以预算里要有一条”禁止在首屏关键路径上同步执行超过某时长的任务”（团队约定示例阈值）。CLS 的对象最具体：未声明尺寸的图片与视频、后插入的 banner 与提示条、字体加载导致的文本重排；预算给它的是允许偏移的动态插入点数量（示意值：每页 1 处，且必须预留高度）。

基线与分配：把总额度切下去

基线取自真实流量分位，而不是取自愿望

指标类预算的基线应来自真实数据的某个分位。常用 p75 口径（取该页面真实样本第 75 百分位）：p50 会让”一半用户仍然很慢”变成合规状态，p95 又常被弱网与低端设备主导，两端都不好用（这里只谈口径逻辑，不给具体数值）。窗口一般取滚动 28 天，按页面与设备形态分别计算，不要把整站混成一池。

而包体类基线有两个候选：当前构建实际值，与团队曾稳定维持的最优值。当前值已被污染时用历史最优作目标、当前值作对照，写成”先回收到最优、再按新基线守住”的两阶段计划；当前值健康时加一条极小容差（示意值：+2%）。基线必须版本化：连同取值时间、样本量、页面标识存进仓库文件，改动走提交记录。

分配：按页面切，再按模块切

三种分法：按页面分，首页、列表页、详情页各一条线，适合流量差异大的站点；按模块分，把首屏额度拆给框架层、公共组件层、业务组件层、页面内联逻辑，适合多人共用的设计系统；混合分法最常见，页面维度验收结果、模块维度定位责任。

三条经验写进约定：不要让每个模块都在当前基础上再加一点，否则总额必然破线，要先做一次全量清账、把额度重新分完，此后任何新增都要有对应腾挪；留一笔机动额度（示意值：总额的 8%）由性能值班人掌管；vendor 层单独设线且默认不动，升级的体积差由发起者消化。

新功能如何申请预算

这是制度的核心：让”我需要一个新图表库”变成有成本、有期限的显式动作，而不是默认可做的技术选择。流程要轻，越轻越有人走。

flowchart TD
  A[需求评审提出新增资源] --> B{该模块是否有剩余额度}
  B -- 有 --> C[记入模块账本,合入后看板观察]
  B -- 无 --> D[提交预算申请单:对象/预估增量/收益说明/退出条件]
  D --> E{性能值班人初审}
  E -- 材料不足 --> D
  E -- 通过 --> F[额度腾挪:等量置换或动用机动额度]
  F --> G[更新基线文件并合入]
  G --> H[CI 按新基线拦截]
  E -- 拒绝 --> I[降级方案:异步加载/延后加载/等额度释放]

申请单四栏：对象（哪个 chunk、哪个页面、哪类请求）、预估增量（字节或毫秒，按本地构建与实验室估算）、收益说明（要解决的具体问题，不接受”体验更好”这类无法验证的表述）、退出条件（何时归还额度，例如活动下线后一周内删除代码）。等量置换是最有力的约束：想让图表库进首屏，就要说清首屏里哪一块可以出去。

把预算写进 CI

只存在于文档站的预算仍然是愿望。让它成为约束的最小成本，是一份基线文件加一条流水线规则。

构建期检查体积与数量

先由打包插件导出逐文件体积清单，再由脚本按归属映射汇总首屏加载集合、逐项比对基线，超限时以非零码退出并把差额打到标准输出。

失败信息的写法决定这套东西能不能用：”总包体超出预算”只会让工程师去调高基线数字，有效信息要包含对象名、基线值、当前值、差额、归属与可疑文件（示意输出）。

逐文件差异按差额排序取前几项，就能把嫌疑范围缩到两三个文件，评审者据此提问。

阻断还是告警

按对象成熟度切：新引入的检查项先只告警，跑一到两个发布周期把误报处理掉再升级为阻断；已有对象越线直接阻断，因为规则早已被验证。按分支切：主干与发布分支阻断，功能分支与预览环境只告警并在评论里给出差额。

第三条规则：区分新增超限与存量超限。存量超限时，若本次改动让体积下降或持平就应当放行，否则预算会反过来惩罚做清理的人；这需要脚本带基线对比维度，也是基线要逐对象存的原因。

实验室回归与 PR 模板

包体检查管下了多少字节，管不了因此慢了多少，所以在 PR 上补一次 Lighthouse 实验室跑分，把指标当回归测试。三点必须注意：噪声大，取多次运行的中位数并写容差（示意值：LCP 容差 300 ms）；环境锁死，设备档位、网络档位、降速倍率与冷热缓存固定；看构成不看总分，逐项比 LCP、INP、CLS 与关键资源耗时。实验室的 INP 覆盖取决于脚本点击了什么，只用于拦截明显退化，交互验收仍以真实分位为准。

再补一道软约束：PR 模板加两问——本 PR 是否新增首屏资源、第三方脚本或字体，如有则申请单编号是什么；本 PR 可能影响哪个页面的哪个指标，发布后如何观察。同时把基线文件所在目录设为需要性能值班人评审的路径，额度改动都要一次显式批准。

图片与字体的预算执行

这两类最容易在无人察觉时膨胀，因为决策权在设计与运营侧，不走前端代码评审。

格式与尺寸协商

格式不要在页面里写死一组候选，而是把”支持什么格式”交给 CDN 或图片服务按请求头协商，页面只声明逻辑尺寸：约定一组尺寸档位（示意值：宽度 320、640、960、1280），运营上传原图、服务端按档位派生并选编码，前端只写响应式尺寸属性。这样预算能按”每张派生图上限 + 首屏图片总量”两条线检查，也避免同一张图被复制成十份命名不同的静态文件塞进仓库。声明宽度要写准，它决定浏览器在解析阶段选哪一档资源，评审时把声明宽度与布局实际渲染宽度对一遍即可。

懒加载与优先加载要成对出现

懒加载管”不要提前下”，优先加载管”该提前的一点都别晚”，只写前者会把首屏最大内容元素一起推迟。

fetchpriority 在 2024 年已是可用属性，把它给到候选 LCP 元素（通常是首屏主图）是”首屏关键图片数”这条线的配套要求：既然允许放 N 张首屏图，就要指明哪一张优先。延迟加载要与视口占位一起写，显式宽高让浏览器预留布局空间，这一条同时是 CLS 预算的执行手段。

字体子集化与显示策略的代价

中文字体的执行手段是子集化：抽取实际用到的字形再分片加载。代价是后续文案变更可能超出子集、出现回退字形，所以字体预算要连同文案约束一起写：哪些区块用受限字体、字符集变更需重新出包、出包后跑一次覆盖检查（示意值：覆盖率 99%）。

font-display 在文本可见时间与避免重排之间取舍：block 让首屏文本短暂不可见，把 LCP 推后；swap 先用系统字体绘制、到位后替换，会出现字形跳动，对 CLS 有压力；optional 最省，但很可能整次会话都用不上目标字体。合理分配是影响 LCP 的主标题用 swap 并预留度量相近的本地回退（配合 size-adjust 压小跳动），次要字体用 swap 或系统字体栈，装饰性字体用 optional。这张决策表放在设计系统文档里，预算检查只确认每个字体文件有归属与策略。

图标要单独列条目：用字体承载图标会强制下载一份含大量无关字形的文件，迁到内联 SVG 通常显著降低图标字节（定性判断，取决于图标数量与字体文件是否被复用）。条目写成图标资产总量与每页图标请求数，新增图标才不会牵动整份字体预算。

第三方脚本治理

这是最难管的一块：使用者不是前端，成本却记在用户主线程上。治理路径是把接入变成有登记、有期限、有隔离的显式动作。

准入清单与归属

任何脚本进生产页面前先登记一条记录，字段就是制度的全部依托。

owner 与 sponsor 分开：前者负责出问题时响应，后者负责到期时决定续期或删除。expires 最重要，它把永久接入变成”需要重新证明一次才能继续”；到期复审必须带上一观察窗口的实测数据（体积、执行时长、对 LCP 与 INP 的影响），无数据默认不续期。清单放在仓库里由 CI 校验：页面上出现的第三方域名必须能找到对应条目，找不到就阻断。

异步与延迟的取舍

同步脚本阻塞解析，把后续内容与 LCP 一起推后，除非它决定首屏结构否则不该出现在头部。async 不阻塞下载但执行时机不确定，可能在主线程忙碌时插入一段执行，对 INP 不友好。defer 把执行排到解析之后，仍占首屏之后的主线程时间。隔离到首屏渲染之后再加空闲时机，代价是功能可用时间明显推后，需要提前与业务方对齐计时口径。所以决策不是选最好的方式，而是明确”这个脚本什么时候必须可用”，把它翻译成 placement 字段。

单独计量与看板隔离

三方脚本必须能单独算账，否则它们会藏在”页面变慢了”这句话里。两层做法：RUM 侧用资源计时按域名聚合每个脚本的下载字节与耗时；主线程侧用 PerformanceObserver 观察长任务并按容器类型汇总。

看板把第三方域名单独列一栏，让”我们的代码达标了”与”页面整体达标了”能被分开陈述，这是要求脚本整改时的谈判材料。长任务归因粒度很粗，不足以指认具体脚本，因此这段代码得到的是总量，适合设阈值而不适合追责；要彻底分开，把可隔离的三方能力放进 iframe 沙箱单独计量，或标注这是估计值、需双方复现。

删不掉的时候怎么办

很多脚本删不掉，因为背后有合同或跨部门诉求。这时预算提供的不是否决权而是降级手段：代理收口，把页面直连改为服务端代理转发，从而控制下发时机、加超时、异常时返回占位；开关与灰度，把加载入口收敛成一个可远程关闭的开关，退化时先关再查，而不是等对方发版；兜底呈现，为脚本失效准备静态替代内容，这样关掉它不会引起业务方反对——而关掉后无人投诉这一事实，恰恰是到期复审时最有力的删除依据。

RUM 与实验室数据的分工

两类数据解决的问题不同。合成监控环境可控、可重复、能在合入前跑，适合回归拦截，回答”这次改动相对上一版有没有让页面变差”；真实用户监控受设备、网络、地区与行为差异污染，但它是唯一能回答”用户实际体验如何”的数据，用于验收与分位观察。把实验室的 LCP 写成用户 LCP，或用真实流量波动解释一次没有对照的合入，都是越界使用。落到操作上：门禁看实验室数据，基线与告警阈值看真实分位，同一条预算线在两边的口径并不完全一致。

采集侧有两条底线。字段最小必要：性能归因需要页面标识、组件标识、导航计时与交互类别，不需要用户身份，也不需要任何能定位个人的内容字段；不得采集手机号、精确地理位置、输入内容与业务敏感标识，必要的关联只用脱敏后加盐哈希得到的不可逆标识，并写明盐值轮换周期。隐私口径写进采集封装：明确留存期限、明确哪些维度不进明细表、明确用户拒绝统计时如何降级为本地聚合。错误上报体系与无障碍度量各自决定自己的字段与分级，本文只借用同一套上报通道。

度量看板与告警

看板要分层，否则读数的人会自己发明解释路径。分层至少三档：按页面（整站均值会把一个坏页面稀释掉）、按版本或构建号（把退化定位到具体一次上线）、按网络形态与设备档位（至少把弱网与低端设备分开，否则分位数被优质设备样本掩盖）。

观察窗口与回滚判据要提前写进发布单，而不是发布后临时讨论。一种可执行形态：发布后连续观察一段时间（示意值：2 小时至 24 小时，视流量而定），定时与前一版本同时段的 p75 比对；若 LCP 或 INP 分位劣化超过约定幅度且样本量达到下限，先回滚再定位；若只有关键资源耗时波动而体验指标平稳，转观察队列、不触发回滚（阈值均为团队约定示例）。

告警要分派到人并带预算归属：包体告警指向模块 owner，指标告警指向性能值班人，三方脚本告警指向 sponsor；文案直接引用对象名与差额，避免出现”首页变慢了”这类无法接手的消息。

与业务指标的联动

预算争取排期时最有说服力的论据是它与业务结果有关，而最容易毁掉这套制度的就是把关联说过头。原则是：相关不等于因果。转化好的页面往往也性能更好，但它们同时受价格、素材、位置、人群与活动周期影响，把转化差直接归因于 LCP 差会得出错误整改清单；把优化后的转化上升归功于本次改动，也常常只是把同期其他变化算在了性能头上。

要可用结论只有两条路。实验：同一页面同一入口分流，让性能差异成为主要变量，人群、时段、素材保持一致，样本量不足时宁可承认看不出差异，不要用一次短期波动讲长期收益。分段观察：用页面自然分段或版本前后做时间切片，同时记录未优化的对照页面，把”可能的影响范围”而不是”确定的提升值”作为结论口径。因此本文不给出任何”性能提升带动转化提升若干百分比”的数字。

制度落地：责任人、债务与复审

责任人最小配置：一名性能值班人（掌管机动额度、主持复审、解释口径），每个页面一名 owner，每个公共模块一名 owner，每个第三方脚本一名 sponsor。不必设全职角色，但要把职责写进例行机制，否则人力一紧张它就被放弃。

超期债务要登记而不是遗忘。任何”这次先放行、下版本处理”的决定，都得在台账留下一条：对象、当前值与基线值、差额、原因、承诺消减的迭代、复核人。登记让豁免变得昂贵（要留下名字），也让复审能看到哪些豁免长期没兑现。

复审一季一次，输入四份材料：各对象的余量曲线、CI 拦截与豁免记录、第三方清单到期情况、真实分位趋势。产出三件事：重新分配额度、把已验证稳定的检查项从告警升级为阻断、把已下线但未删除的资源一次性清账。复审也要允许调高某条预算线，只要理由与数据成立。

最后一张表把退化场景与拦截点对齐，它是整套制度的检查清单。

小结

性能守不住多半不是能力问题，而是制度缺位：新功能的增量决策、第三方脚本的默认可用、依赖升级的体积差异，都发生在没人审查性能的环节。预算把”首屏要快”翻译成能落到文件名与请求 URL 上的额度，让它在构建期被检查、在评审时被引用、在发布后被观察。基线从真实流量分位取并且版本化；分配先清账再切，新增走等量置换与申请单；门禁区分检查项成熟度与存量豁免；三方脚本靠准入清单与单独计量治理。实验室数据用于回归拦截、真实数据用于验收，采集守住最小必要与脱敏底线。最后把责任人、债务台账与季度复审固定成节奏，制度才能在人力紧张时活下来。
