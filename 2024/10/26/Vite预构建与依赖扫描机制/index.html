Vite 预构建与依赖扫描机制

npm 依赖在浏览器里不能直接用，这是 Vite 开发服务器必须解决的第一件事。本文沿着“依赖从哪来、被怎么处理、缓存在哪、什么时候失效”这条线索，讲清 Vite 5 的依赖预构建与扫描机制，适合被“页面突然整页重载”“React 出现两份实例”“本地能跑构建就坏”困扰过的前端工程师。

开发服务器为什么需要预构建

Vite 的开发服务器把“打包”从请求路径上移走了，源码模块直接以原生 ESM 发给浏览器。执行方式是按需解析：浏览器拿到 /src/main.tsx，读到 import ... from "react"，再发一次请求去取 react，取回来继续解析它内部的 import，如此层层递归。这对源码不是问题，模块图规模可控；可一旦把视角挪到 node_modules，三个老问题会同时冒出来。

第一个问题是请求数量。以中等规模的后台项目为例，index.html 引出 /src/main.tsx，后者再引出路由库、状态库、组件库与图表库。组件库里一句 import debounce from "lodash-es/debounce"，在浏览器端会展开成 lodash-es 内部成百上千个模块的请求——它们彼此还在继续互相引用。第一屏 Network 面板出现上千条请求并不夸张，每条哪怕只有 1 毫秒的处理与一次往返，累加起来也是肉眼可见的白屏；若本地 dev server 走的是不支持 HTTP/2 的代理链路，还要撞上并发上限与队头阻塞。

第二个问题是模块格式。浏览器不会执行 CommonJS，而 npm 上至今仍有大量包只提供 CJS 产物，或者只提供 UMD，或者 package.json 里既没有 exports 也没有 module 字段。require 是同步函数、module.exports 是可以随时改写的普通对象、__dirname 依赖真实文件系统路径，这些语义在浏览器里没有对应物，必须有人在中间做一次翻译。UMD 还默认运行在有全局对象、可能有 AMD 加载器的环境里，浏览器直接加载多半什么都取不到。

第三个问题是定位。裸模块名 react 对浏览器不是合法说明符，开发服务器必须把它解析到 node_modules/react/index.js 这种真实可达路径，还要处理 react/jsx-runtime 这类子路径与条件导出；这套规则比浏览器的复杂得多，每个模块都做一次也是开销。

于是预构建要做的三件事就清楚了：把散落成百个文件的依赖打包成少量 ESM 模块，把 CJS/UMD 翻译成 ESM，把裸模块名固化成一组稳定 URL。它针对的是“开发服务器启动慢”与“首屏请求太多”，而不是“生产包体积”。

需要先划清边界：Vite 整体的模块解析、HMR 链路与插件钩子时序在《Vite构建工具原理与插件开发》里已经展开，本文只谈依赖这一层；esbuild 本身为什么快则由《esbuild与SWC编译加速》负责，本文只谈它在预构建里的角色。

格式转换是 esbuild 在这里干的活。一个只提供 CJS 的包，输入是 module.exports = { x: 1 } 这样的赋值语句，输出必须是一个能被 import 的 ESM 文件。Vite 让 esbuild 以 ESM 格式产出，再对检测到的 CJS 入口补一层互操作包装：默认导出被合成为整个 module.exports 对象，命名导出则靠静态分析尽量还原。_metadata.json 里的 needsInterop 标记描述的就是这件事：为真时，默认导入需要经过一次“取默认导出”的适配。

产物之间的引用关系是刻意保留的。预构建不把所有依赖塞进一个巨型文件，而是维持“入口 chunk 加共享 chunk”的形状：react 与 react/jsx-runtime 都依赖同一份内部调度代码，如果每个入口自带拷贝，同一模块会在页面里执行两次；可拆得过碎，请求数又回来了，所以这个粒度是权衡出来的。

依赖是怎么被发现的

预构建的前提是知道要构建谁，这件事分两步：先找入口，再从入口爬出依赖集合。Vite 把第一步叫扫描、第二步叫优化，两者都跑在 esbuild 上但用的能力不同：扫描只用解析器，优化才用打包器。

入口的确定是保守的。默认 Vite 在项目根目录（root，不是系统根）下寻找 HTML 作为入口，node_modules 与构建输出目录被排除，随后读取 <script type="module"> 的 src 当作扫描起点。项目若根本没有 HTML——开发组件库、入口由后端模板渲染——就找不到入口，扫描只能退化成“几乎什么都没发现”。

从入口出发，扫描器沿静态 ESM 图往下爬：遇到 import、export ... from、require 与字面量形式的 import()，就取出说明符判断它是相对路径还是裸模块名。相对路径指向源码，继续递归读文件；裸模块名解析到 node_modules 的入口，入口若是 ESM 就继续往里爬、把它内部的裸依赖收进来，若是 CJS 就停止深入——CJS 的内部依赖交给打包阶段让 esbuild 自己解析，扫描器不去模拟 require 语义。爬完得到一份“哪些依赖需要在浏览器里可用”的清单。

漏扫的根本原因是扫描器只看静态可见的字符串。变量拼接的动态导入；只在条件分支或 try/catch 里出现的依赖；被一层没被入口用到的自研适配包间接引用的依赖；只在测试文件里出现却同时被浏览器代码引用的依赖——这几类它都发现不了。

一旦漏扫，就会出现那个让人困惑的现象：点进某个页面，整页突然重新加载一次。

机制是这样：开发服务器处理模块请求时遇到没有预构建过的依赖，就把它追加进待优化集合重跑一次优化；新产物哈希变了、v 参数变了，客户端收到“optimized dependencies changed. reloading”并做一次全量刷新，在此之前控制台已经打出一行“new dependencies optimized”。这不是错误，而是按需优化的兜底路径，代价是丢掉页面状态；连续点进多个新页面反复重载，损耗就很明显。把依赖提前写进 optimizeDeps.include，等于把兜底路径变成一次到位的启动路径。

缓存目录与失效条件

node_modules/.vite 里要分清两层缓存：磁盘产物缓存决定开发服务器要不要重跑 esbuild，浏览器对产物 URL 的 HTTP 缓存决定优化结果能被复用多久。两者失效条件不同，排查时不能混为一谈。

产物是否命中缓存，由一次优化的输入算出的哈希决定。进入这个哈希的输入包括：项目锁文件（package-lock.json、pnpm-lock.yaml 或 yarn.lock）的内容指纹；配置中与依赖解析相关的部分，包括 optimizeDeps.include、exclude、entries、esbuildOptions 与 resolve 下的别名、条件、去重；被优化依赖自身的版本与入口路径；还有运行目标——浏览器侧与 SSR 侧外部化策略不同，产物分目录存放，SSR 结果落在 deps_ssr，不与 deps 混用。

因此这些动作会自然让缓存失效并触发重新优化：安装或升级依赖；切换分支导致 package.json 与锁文件同时变化；修改上述配置字段；删除 node_modules 重装。反过来，改业务源码不会让预构建缓存失效——这正是预构建的设计目的，源码与依赖的失效粒度必须解耦。

同样要说清楚，清缓存不是万能药。如果症状源自解析配置写错——别名指错了包、exclude 把一个只提供 CJS 的包排除掉了——清缓存只会让这套错误配置被完整重放一遍，现象一模一样。判断是否真该清缓存，看第二次启动的日志：如果重新优化花了可观时间而问题立刻复现，成因就在配置或依赖本身。

CI 里有个细节容易被忽略：npm ci 会重写锁文件与工作区文件的时间戳，即便内容没变也可能让指纹变化，于是“把 node_modules/.vite 塞进 CI 缓存”的收益并不稳定——产物里写入了相对路径与哈希，换一棵 node_modules 树未必对得上。真正能省时间的是让依赖安装本身可复用。

本地并发是另一类问题。同一项目同时起两个开发服务器（两个终端、不同端口），默认共享同一个缓存目录。Vite 先在一个临时目录里构建完整产物、成功后再替换正式目录，避免读到半成品；但两个进程同时判定“缓存过期”仍可能重复跑两次优化，表现为启动时互相等待、日志里优化出现两遍，偶发的请求 500 也常出现在这里。解法很朴素：一个项目一个端口只留一个实例，切分支后重启而不是再起一个。

最典型的一条报错来自 React：

排查到最后，页面里存在两份 React。原因不在 hooks 的用法，而在模块身份：ESM 的模块注册表以 URL 为键，URL 不同就是两个互不相干的实例。一旦有两份 react，useState 读到的是当前执行那份里的全局 dispatcher，而渲染流程由另一份驱动，两者对不上，hooks 调用立刻失败。同类问题在别的库里也有对应表现：状态库的 store 是按模块作用域建的单例，两份实例意味着写进 A 的 state 在 B 里读到初始值；Pinia 会抱怨 store 装在了另一份实例上。

出现两份通常有三种形态差异。其一是格式差异：同一个包同时提供 CJS 与 ESM 入口，一条链路解析到 index.js，另一条解析到 index.mjs。其二是版本与路径差异：直接依赖装在根 node_modules，某个间接依赖带着自己的嵌套副本，在 pnpm 那种“每个包只看得见自己声明的依赖”的严格布局下尤其常见。其三是外部化差异：某个包被 exclude 之后不再进入预构建，它内部的裸依赖由开发服务器逐条解析，走的是与预构建产物完全不同的 URL 路径。

optimizeDeps.include 解决的是“一起打包就能共享”。把有问题的包和被它引用的依赖放进同一轮优化，esbuild 只为同一份依赖生成一个 chunk，两条引用路径在产物里汇合，实例天然唯一：

include 支持 父依赖 > 子依赖 这种嵌套写法，专门用于“子依赖只有被父依赖引用时才出现、静态扫描抓不到”的情况。

exclude 则相反，把包留在未预构建状态、由开发服务器逐文件转换。合理场景是直接发布源码级 ESM 的 workspace 包，或需要改动即时生效的调试；代价是它同时让这个包的裸依赖脱离了预构建集合，容易触发上一节描述的二次优化与整页重载。

CommonJS 与 ESM 的互操作边界

先看默认导出。按规范，import foo from "cjs-pkg" 拿到的是 CommonJS 模块的 module.exports 整体——只要它没有 exports.default，宿主就把整个导出对象合成给 default。经 esbuild 转换之后这件事同样成立，但多了一层历史约定：如果 CJS 代码显式设置了 exports.__esModule = true，转换会认为那才是真正的默认导出语义，把 exports.default 交给 default。同一语法形式在两个写法不同的包上得到不同结果，这是第一层困惑来源。

再看命名导出。ESM 的具名导入是静态契约：模块必须有那个名字的导出，否则加载期就报错。

esbuild 做 CJS 转 ESM 时靠静态识别 exports.foo = ... 与 Object.defineProperty(exports, "foo", ...) 这类字面量赋值形态。一旦导出是运行期构造的——循环批量赋值、从别的对象展开拷贝、用 Object.assign(exports, ...) 合并——它就探测不到。这时 default 导入依然可用（那是整个对象），具名导入却是空的。绕开写法有两种：整体默认导入再取属性，或者让这个包在预构建阶段被彻底展开，后者正是 include 的价值所在。

require 侧还有几条硬边界：路径拼接的动态 require 在打包期无法解析；__dirname、__filename 在 ESM 里不存在，转换后靠注入的兼容变量，指向的是产物所在目录而不是原始包目录，任何“运行时按目录读文件”的逻辑在浏览器里都会落空；webpack 特有的 require.context 没有对应物，在 Vite 侧要换成 import.meta.glob。顶层 await 是另一条线，它只在真实的 ESM 模块里合法；若一个包的入口是 CJS，被包装成 ESM 之后内部再出现顶层 await，转换本身不成立，esbuild 会直接报错而不是产出可疑产物。这也是“某个包在别的构建工具里能用、在 Vite 里进不去预构建”的一种成因。

至于为什么有些包必须强制 include：这些包把 ESM 与 CJS 混在同一棵目录树里，或者 exports 的浏览器条件指向 CJS 产物。逐文件外部化意味着开发服务器要在浏览器每次请求时重新做一次格式判定，稍不留神就让同一份代码以两种形态出现在页面上；集中预构建把整棵依赖树拍平成产物，内部 require 都变成产物里的局部引用，浏览器根本看不到这些中间文件。

monorepo 冷启动与 workspace 包

在 pnpm 或 npm workspace 里，本地包通常以符号链接出现在应用的 node_modules 下。Vite 对这类被链接的包采取和第三方包不同的默认策略：不做预构建，把它当源码对待。理由很直接——本地包是你正在改的东西，每改一次都重跑一轮 esbuild 的话热更新就废了。

这个默认选择带来两个后果。一是本地包自身依赖的第三方包仍需预构建，扫描器会顺着本地包的入口继续收集裸依赖，但入口一旦找不到，收集就漏——entries 在这里必须覆盖到本地包的示例入口，而不只是应用的 index.html。二是依赖的物理布局影响解析结果：pnpm 下每个 workspace 包有自己私有的 node_modules，同一份第三方库可能在磁盘上存在多个位置，双实例风险更容易出现，resolve.dedupe 几乎是标配。

resolve.preserveSymlinks 决定符号链接要不要在解析阶段展开成真实路径。默认 false，即解析到真实路径，所有应用与本地包对同一第三方库的引用汇聚到同一份物理文件；设为 true 时保留链接路径，每个 workspace 包只看得见自己那份依赖：

在单例性质的库上开 preserveSymlinks 是双实例的经典成因，除非确实需要“每个包锁自己的版本”这种隔离语义，否则保持默认。

冷启动的优化空间基本都在把首屏依赖收敛上，可做的动作有三类。第一类是拆 barrel 文件：很多组件库的入口 index.ts 把几百个组件全部重导出，静态扫描沿着这张大网把所有东西收进预构建集合，产物随之膨胀；改成从具体子路径导入，扫描到的依赖面明显收窄。第二类是把重量级依赖挪出首屏静态图：编辑器、图表、PDF 预览放进真正的动态 import() 分支，同时把依赖名补进 include，让它们仍被预先优化但不在首屏加载——关键在于预构建与运行时加载是两件事，提前打包不等于提前请求。第三类是把 entries 写全，避免进入页面之后连续触发二次优化。这三件事的收益体现在启动阶段 esbuild 的输入规模、产物 chunk 数量与首屏请求数上，具体能省多少要看依赖构成，不宜给统一数字。

SSR 场景下的依赖处理

SSR 下依赖的处理方向恰好相反：默认外部化。服务端跑在 Node 里，Node 自己能加载包，把 dependencies 留成外部引用既快又避免把 Node 原生能力打进产物。代价是解析权交给了 Node，而 Node 的加载规则与浏览器端预构建之后的行为并不等价。

ssr.noExternal 就是把某些依赖从外部化名单里捞回来的开关：

需要用它的情形几乎都是 Node 侧 ESM/CJS 解析差异造成的“只在 SSR 复现”。几种典型报错各有来历。

require() of ES Module ... not supported——某个 CommonJS 包在运行期 require 了一个只提供 ESM 的依赖。Node 的 require 不能加载 ESM，这一限制在当时是硬约束；而浏览器端这条路早已被 esbuild 在预构建时拍平，根本执行不到 require。于是同一个包，客户端正常、服务端整条请求挂掉。

ERR_MODULE_NOT_FOUND 与找不到子路径——Node 的 ESM 加载器严格按 exports 字段匹配，不做目录 index 回落、不补扩展名；而预构建用的是 Vite 那套更宽松的解析规则，会把 pkg/sub 补成 pkg/sub/index.js。产物能跑而 Node 不能跑，就是这一层差异。

默认导出多包一层——具名导出探测在浏览器端由 esbuild 完成，Node 侧由它自己的 CJS 词法分析器完成，两者算法与能力不同：同一个包在一侧能拿到 createStore，另一侧只能拿到 default。把包放进 noExternal 之后服务端也走 Vite 的转换链路，两侧口径才统一。

另外，SSR 侧的预构建产物独立落在 deps_ssr，不与浏览器侧共用目录，因为外部化名单、格式目标与 exports 条件都不同；如果浏览器侧缓存正常而服务端仍报旧行为，两个目录要一起清。原则是：只在确认某个依赖让 Node 自己解析会出问题时才加进 noExternal，把整棵依赖树塞进去会让 SSR 的启动与重建明显变慢。

生产构建为什么换用 Rollup

预构建只作用于开发服务器。执行生产构建时 node_modules/.vite 里的产物完全不参与，依赖重新作为源码进入模块图，由 Rollup 一次性处理。动机不是换个工具更快，而是两个阶段目标根本不同：开发期要启动快、请求少、改动即时，生产期要体积与结构。Rollup 建立在静态 ESM 契约上做变量级死代码消除，能按动态导入边界切分 chunk，能让 sideEffects 字段真正生效，也能通过 rollupOptions 控制外部化与输出格式。CJS 依赖照样要转换，但由 Rollup 侧的 CommonJS 插件在构建期对整棵树做一次，转换时机与判定口径都和 esbuild 那一轮不同。

正因为两侧走的是不同实现，“开发能跑、构建后坏”有固定的几类成因。

其一是条件依赖。开发期整包被 esbuild 拍平进产物，运行期拼出来的路径只要文件真在树里就可能拿得到；Rollup 在构建期只看静态说明符，动态拼接的位置要么留成运行期错误，要么在告警里出现“没有这个导出”。其二是外部化差异。开发服务器把所有能解析到的依赖都变成本地 URL，而生产构建里被 rollupOptions.external 留成外部引用的包在最终运行环境是否存在是另一件事——库模式下产物发给一个装着不同版本的宿主，行为取决于对方的解析规则。其三是格式差异。dev 侧的默认导出合成来自 esbuild，生产侧来自 Rollup 的 CommonJS 插件，两者对 __esModule 与命名导出探测并不严格等价，构建后常见症状是默认导入多了一层 default，或某个具名导入变成 undefined。再加上 optimizeDeps.esbuildOptions.target 与 build.target 是两个独立配置，语法降级不一致也属同类陷阱。结论很朴素：开发服务器起得来不代表构建能过，CI 里必须真跑一次构建与 vite preview。

排查手册

先看启动日志：ready in 之前没有出现依赖优化日志，说明命中了磁盘缓存；出现了则记下它跑了几次，第二遍几乎一定是漏扫。再看浏览器 Network 面板里依赖请求的实际 URL，命中预构建的长这样 /node_modules/.vite/deps/react.js?v=哈希；如果某个包以散文件路径返回（/node_modules/some-pkg/lib/index.js），它没有被优化，要么被 exclude 了，要么扫描器没发现它。接着确认是否触发过二次优化：控制台的“new dependencies optimized”与紧随的整页重载就是证据，处理动作是补 entries 或把依赖名写进 include，而不是关掉热更新。然后查外部化，浏览器侧核对 exclude 有无误伤，SSR 侧核对 noExternal 有无漏写，两份名单要分别检查。再查身份唯一性：在 Sources 面板按包名搜模块，同名模块出现两份、或 URL 前缀一个是 deps 一个是真实路径，就回到去重那部分处理。最后一步才是删 node_modules/.vite 重跑——把它当确认手段而不是第一步，否则你永远不知道修好的是配置还是缓存。

最小复现的构造方法是：新建一个空目录，只留一份 vite.config.js、一份 HTML 与一个入口，只写两行 import，一行指向可疑依赖、一行指向 React 或状态库。问题复现，成因就在包本身或这两项配置的交互；不复现，就把原项目的 resolve 与 optimizeDeps 字段逐组注释回迁，二分定位。复现仓库要重装依赖而不是拷贝 node_modules，否则锁文件指纹的差异会把排查带偏。

小结

预构建是开发服务器在依赖层做的一件事：把散碎的第三方包压成少量 ESM 产物，减少首屏请求，并把 CJS/UMD 翻译成浏览器能执行的形态，它不参与生产体积优化。它的输入是扫描出来的依赖清单，所以静态看不见的写法一定会漏，漏了就用 entries 与 include 补回来。产物缓存在 node_modules/.vite，命中与否由锁文件、配置与依赖版本共同决定，需要手动介入时删目录即可，Vite 5 没有强制重新优化的配置项。双实例要从 URL 即身份这个视角理解，include、exclude、resolve.dedupe 分别管打包轮次、外部化与解析归一，不能互相替代。SSR 默认外部化、按需 noExternal；生产走 Rollup，两侧实现不一致正是“开发能跑、构建后坏”的根源，所以构建必须在 CI 里真跑一次。
