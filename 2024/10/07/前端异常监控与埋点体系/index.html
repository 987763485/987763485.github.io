前端异常监控与埋点体系

线上页面的报错，往往在用户已经流失之后才被发现。本文把前端异常监控拆成采集、传输、聚合、告警、治理五个层次，逐层说明职责、手段与失败模式，并给出字段规范与采样策略。适合已经接过全局错误监听、却还没形成闭环的团队。

体系分层：五个层次与各自的失败模式

最基础的 window.onerror 接入示例在错误监控入门篇已给过，本文从分层与字段规范讲起。

五个层次各有不同的失败模式：采集漏了，聚合再漂亮也没用；聚合没做好，看板数字就会骗人。

flowchart TD
  A[采集层：全局钩子与框架错误处理] --> B[传输层：队列、批量与卸载发送]
  B --> C[聚合层：去重、指纹与会话归并]
  C --> D[看板与告警：阈值、分级与静默窗口]
  D --> E[治理闭环：定级、归属与回归验证]
  E --> A
  • 采集层求不漏与不炸：钩子要接住一切会终结体验的异常，采集代码自身不能抛异常。失败模式是在监听器里序列化循环引用对象，监控自己成了新错误源。
  • 传输层求不丢与不冲：关键错误带幂等标识重试，其余按窗口合并。失败模式是跳转时请求被取消，那一次报错永远收不到。
  • 聚合层求不重复计数：一个会话里报错一百次，影响面只算一个用户。失败模式是聚合键不统一，看板被少数循环用户拉偏。
  • 看板与告警层求可定位可分级：告警要能回答版本、指纹与影响面。失败模式是所有未处理拒绝一律推群。
  • 治理闭环层让错误有人认领、有验证动作，决定前四层的价值。

埋点事件的设计与表格另有专文，本文只讲共用通道与治理；无障碍度量另有专文，这里只保证同一套上报口径；性能预算与门禁不展开。

错误分类与采集点

把错误分成六类，是因为它们的采集点、可信度与误报率完全不同；若一律以 type: 'error' 上传，后面的告警与归因都拆不开。

运行时同步异常与未处理的 Promise 拒绝

前者用 window.onerror，后者用 unhandledrejection：同步异常在具备 crossorigin 时能拿到 error.stack；未处理拒绝只有一个 reason，很多库传的是字符串甚至响应体，所以要先归一化：

不要把整个 reason 序列化进 payload，响应体里可能含用户数据。被主动 catch 的 reject 不会进入 unhandledrejection，所以要么不捕获，要么捕获后显式上报。

资源加载失败与跨域脚本的裁剪

error 事件在捕获阶段能拿到资源加载失败。真实机制是：同源脚本能拿到完整堆栈，跨域脚本若没有 crossorigin 属性，浏览器出于安全会把详情裁成一句 Script error.，行列号归零。要拿到可读堆栈得同时满足两个条件——脚本带 crossorigin="anonymous"，服务端返回正确的 Access-Control-Allow-Origin。

网络请求失败：超时、取消与失败是三件事

请求层靠包装 XMLHttpRequest 或 fetch 采集，关键是把超时、取消（用户离开或被 AbortController 中断）与真失败（5xx、DNS 错误、断网）分开。把取消算成失败是最常见的误报来源；超时阈值只是团队约定示例值。

接口业务错误码：最难对齐的一类

HTTP 200、响应体里 code 非 0，既可能是系统故障，也可能是预期业务分支。难点不在采集而在契约：没有契约会把正常分支当异常上报，又会漏掉真正的降级。可行做法是响应码分三段写进接口文档：网关段与服务段一律视为异常；业务段要求每个 code 声明是否用户可感知、是否代表系统故障。前端只在未按契约返回（缺字段、类型不符、code 不在注册表）时上报异常，其余走埋点通道。

白屏与渲染失败

React 18 的错误边界捕获子树渲染异常，Vue 3 的应用级 app.config.errorHandler 收敛组件树内错误，两者都不覆盖“组件正常渲染但页面上什么都没有”。白屏要靠主动探测：关键节点挂载后检查根容器是否有预期子节点或可见内容，结果作为独立一类上报并附路由与版本。

采集 SDK 的设计要点

初始化时机与框架接入

SDK 要在业务脚本之前加载，否则首屏异常落在监听器之外；把完整 SDK 放进 <head> 又太重。务实做法是先内联一段极小的占位钩子，把早期错误暂存到全局数组，主包就绪后回放并接管监听，而“SDK 加载失败”本身也该单独采集。

框架侧接入保持薄：React 18 用包裹根节点的错误边界把子树异常转成上报并渲染降级 UI，Vue 3 用 app.config.errorHandler 收敛组件树错误；两者只补组件名、路由与出错阶段这类上下文便转交统一通道，不要在钩子里实现重试、采样或聚合。

上下文注入

SDK 暴露两类写入接口：会话级不变项（应用版本、发布标识、随机会话标识、匿名用户标识）在初始化时一次写入，随操作变化项（当前路由、面包屑、最后一次接口 traceId）由路由与请求层写入。用户标识必须在写入前完成加盐哈希或换成服务端下发的随机化名，明文标识与任何令牌都不得进入队列、日志、缓存键与堆转储。

去重与聚合键：栈指纹还是归一化消息

只用栈指纹有两个坑：产物文件名带 hash，每次发布指纹就变，同一问题被切成无数个“新错误”；压缩后的行列号经 SourceMap 还原会漂移。只用归一化消息又会过度合并。可行做法是两级键：合并键取归一化消息加栈顶若干帧函数名，不含行号与 hash，用于看板归组；实例键保留完整指纹，只在会话内去重。

队列、批量与卸载时的发送

队列要有硬上限与丢弃策略：超限时优先保留未处理拒绝与白屏。发送按条数或时间窗触发；重试有上限并遵守服务端限流语义，被限流时先退避。

页面卸载用 navigator.sendBeacon，它能在跳转与关闭后继续投递，适合小 payload 的收尾数据。限制要清楚：payload 有大小上限（规范给出约 64 KB 的约束，浏览器还会自行收紧），不能携带自定义请求头，鉴权只能用一次性票据；触发配合 pagehide 而非 visibilitychange，后者在往返缓存时也会触发，容易把切后台误判成离开。beacon 不保证送达，关键统计仍需服务端按会话超时补齐。

SourceMap 管理

构建产物与版本的对应

堆栈里的位置属于发布产物，能还原的前提是拿到同一份 map，所以 map 与产物必须共享一个不可变的发布标识：构建时写入、上报时携带、服务端按标识索引。上传要在灰度放量之前，否则正被观察的那批用户堆栈全部不可读。

映射文件不得公开到公网：它们等于把源码结构与内部路径交给任何访问者，接口路径与内部域名也会随之泄露。

还原放在服务端还是客户端

客户端还原只在本地调试时值得考虑，代价是把 map 下发到浏览器，等于放弃源码保护。还原应放在服务端：原始堆栈加发布标识送到内网服务查表。隐私上服务端要多做一件事——原始堆栈里的 URL 可能带查询参数中的用户数据，还原服务应只读 map、不留原始输入，并让访问可审计。

映射缺失本身要能被监控

map 丢失、上传延迟、标识写错，症状都是“堆栈不可读”，而这类错误依旧正常计数，很容易被忽略。做法是聚合后给每条事件打还原状态标记，把不可还原条数单列成指标并纳入告警；它衡量的是监控体系自身的健康度，阈值由团队按发布节奏约定。

上下文字段与面包屑

上下文决定了一条错误能不能被复现。面包屑是环形缓冲：交互点击、路由变化、接口摘要与自定义打点先进本地缓冲区，出错时才把最近若干条随快照上报。缓冲区只记元素的语义名称，不记输入内容；设备信息取 UA、视口与网络类型即可，精确地理位置与手机号不在采集范围。下表是字段规范示例，可据此建立字典，并把“是否可上报”作为评审项。

字段（示例） 来源 是否可上报 脱敏方式 留存期
route_path 前端路由 可 去 query 与动态段 30 天
breadcrumb 交互监听 可 只记语义名 7 天
session_id 随机生成 可 每会话随机 90 天
user_key 服务端下发 可 加盐哈希 90 天
ua、viewport 浏览器接口 可 原样不含标识 30 天
api_trace_id 响应头 可 原样 7 天
input_value 表单节点 不可 一律丢弃 不留存
geo_precise 定位接口 不可 不采集 不适用

采样、限流与降噪

采样要分维度：致命类与白屏不采样，可重复计数的资源失败低比例采样；灰度中的新版本提高比例，稳定旧版本降低比例；同一匿名用户按标识稳定分桶，避免体验忽采忽不采。

限流的核心是熔断循环报错：同一合并键在约定窗口内超过约定次数后只累加计数、不再上报实例，窗口长度与次数由团队约定，属内部阈值而非行业数字。同源突发也要合并：一次接口失败会连锁触发组件、全局与错误页三处报错，应在极短窗口内按合并键折叠成一条并保留首次堆栈。

灰度期看新版本与基线版本的相对差而不是绝对阈值；旧版本长尾单独归档、设过期时间，不再混进主看板。

告警、值班与治理闭环

阈值只能由团队约定，不引用外部行业数字。可用口径有三条：新版本相对基线的增量、同一合并键的历史中位数、按会话去重后的受影响用户数。告警分三级：白屏、SDK 自身失效与 map 不可还原这类让体系失明的算 P0，影响多个会话的新增合并键算 P1，其余进日报。静默窗口同样必要，发布后十分钟内的错误不告警，夜间只推 P0。每条告警要自带版本与发布标识、堆栈指纹、影响面口径与查询入口，缺一项就得回看板重查。

闭环的抓手是把错误当需求入口：新增合并键定级后指派模块负责人，旧版本长尾归入技术债队列，修复要验证该合并键在最新版本的会话数确实下降。发布后 24 小时的观察是固定清单：先看不可还原堆栈占比，再看新增合并键，最后比对灰度与基线的相对差。一次改动引入了此前不存在的合并键就应视为回归，而不是解释成环境问题。

隐私与合规

最小必要是第一规则：只采能用于定位问题的字段。用户标识走加盐哈希或随机化会话标识，明文标识、密钥与令牌不得进入上报内容、日志、缓存键与堆转储；表单输入值与精确地理位置不进面包屑，手机号不作为检索键。同意状态要在采集前判定：未同意时只保留不含用户标识的运行时报错，撤回同意后停止写入新数据。留存期按字段设定并配删除任务，原始事件与聚合统计分开过期。上报一律走 HTTPS，跨境传输只在必要范围内发生，具体条款以法务口径为准，本文不列条目编号。

错误类型与采集手段对照

浏览器侧可观测数据的标准化当时仍在推进，字段留出扩展位即可，不必假定已经成熟。下表是前文分类的速查表。

类型 采集手段 还原堆栈 常见误报
同步异常 window.onerror 能 三方库重复触发
未处理拒绝 unhandledrejection 视 reason 已捕获仍上报
资源失败 捕获阶段 error 否 拦截器与弱网
请求失败 包装请求层 否 取消当失败

小结

体系的价值不在于接住多少条错误，而在于每一条都能被定位、被归组、被指派。聚合键决定看板是否可信，字段规范与脱敏决定能不能长期运行，采样与静默窗口决定值班同学会不会把它关掉。落地顺序建议是：先定分类与字段，再做去重与采样，最后才谈阈值与告警。
