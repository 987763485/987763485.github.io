Micro Frontends 微前端架构

微前端这个词已经被用滥了：它既被当成架构升级的勋章，也被当成组织问题的止痛药。本文不论证它先进，而是把它放回工程语境，比较六类集成方式各能解决什么、又引入什么新问题，并讲清外壳、样式隔离、共享依赖、通信契约与发布回滚这些落地环节。适合正在评估要不要上的负责人，也适合被两个团队协作同一个页面卡住的开发者。

先判断该不该拆

微前端站得住的动因只有两个。其一是多个团队要对同一段体验负责，却不愿共享同一条发布列车：报表团队按周发版，交易团队被合规流程绑住，并进一条流水线后慢的一方一定拖住快的一方。其二是技术栈共存：仓库里有一批只能维护、没人敢重写的旧页面，新页面又要用 React 18 或 Vue 3 写，强行统一的成本远高于让两者并存。至于“后端在拆微服务，所以前端也该拆”，这个推理并不成立，服务端的边界划分是另一个话题，本文只借用它的同一个动因：按团队边界拆，不按技术时髦度拆。

动手之前，用三个问题打分。

团队数：稳定贡献团队是否在三个及以上，且协作成本已经体现在交付周期上；单个团队上微前端，等于把跨进程调试和网络延迟引进自己的仓库。

发布频率：各部分是否真的节奏不同；所有页面每周都由同一批人发布时，独立部署的收益接近于零。

耦合度：页面之间共享了多少数据与交互；拆开一个共用八个全局状态、互相靠私有事件驱动的页面，只会得到分布式单体。

三条都弱，结论就是不需要微前端，需要的是把模块边界划清楚：构建慢、包体大、依赖冲突属于工程化症状，monorepo 的组织方式在《Turborepo 与 pnpm monorepo 实践》里已经写透，本文不讨论包管理。

六种集成方式的谱系与代价

方式 能解决 代价
构建时聚合（npm 包） 能力复用、统一视觉 不能独立发布，消费方重新构建
iframe 硬隔离，与技术栈彻底解耦 尺寸同步、弹层裁剪、路由与登录态
Web Components 框架无关元素，样式边界清晰 Shadow DOM 限制、服务端渲染
路由接管式集成 统一 URL 与导航权限 靠生命周期约定，隔离最弱
共享依赖式集成 公共依赖只加载一次 版本协商、与构建工具耦合
后端模板拼装 复用服务端区块与缓存 交互状态难共享，仍是多页

构建时聚合最被低估：把按钮、表格、埋点封装成包，团队边界照样清晰，且不引入运行时复杂度，代价是每次改动都要消费方重新构建上线——很多号称“微前端”的项目做的正是这件事，也确实够用。iframe 反过来把隔离做到最彻底，浏览器天然替你做了样式与全局对象的沙箱，遗留区块整块嵌进来往往最省事，代价是内容高度要回传父页、浮层被裁在框架内、URL 不再反映内部状态。

路由接管式集成（single-spa 与 qiankun 这一路）由外壳按前缀决定挂载哪个应用，应用导出挂载与卸载生命周期；它换来统一的地址、菜单与权限判断，代价是隔离最弱：全局样式、全局变量和事件名共享同一个 window，约定不写清楚就互相污染。

共享依赖式集成（Webpack 5 的模块联邦，Vite 5 下为插件形态）让多个应用共用同一份 React 与工具库，其配置字段与机制细节留给《前端微服务与模块联邦》，本文只在谱系里给它定位。import maps 能把裸模块名解析成具体 URL，但主流内核近两年才陆续支持，起点版本差异大，存量浏览器仍要靠垫片，目前宜作补充手段而非地基；SystemJS 已退到历史位置，它在前两者之前承担运行时加载，如今主要作为兼容层存在。

公共外壳要薄到什么程度

外壳（shell）承载导航、权限、布局和子应用装载，最容易犯的错误是越做越厚。健康的分工是：外壳只管与业务无关的骨架——地址归属、菜单、登录态、错误兜底、主题变量；页面内的状态与接口调用留在子应用。判断标准很实际：外壳的发布频率应明显低于任何子应用，每周都要改就说明业务逻辑漏了进去。

路由归属必须唯一。地址由外壳解析并派发，子应用只声明自己的前缀和内部路由，不允许两个应用争同一段前缀。菜单与权限同理：可见性由外壳按角色裁剪，能进哪个前缀、能调哪类接口随会话下发，子应用拿到的是只读清单而不是判定规则。

加载与降级要当常态而非异常：入口脚本 404、版本不存在、远端超时、应用内部抛错，四种情况都要有确定行为。默认是局部降级——单个应用失败时保留外壳与其他应用，只在出问题的区域给出重试入口；只有外壳自身起不来才整页兜底。

flowchart TD
  URL[地址变化] --> Shell[公共外壳]

样式隔离与主题下发

Shadow DOM 的隔离最强，也最容易被误判：任何渲染到 document.body 的内容都跑出了 shadow 根，浮层类组件会失去作用域，依赖全局类名的第三方库也会失效。所以只有子应用完全自控 DOM 时才值得用它。

更常用的是构建期作用域方案：CSS Modules 把类名哈希化，天然避免冲突；全局栈用 BEM 加团队前缀。真正难处理的是加载顺序——两个应用都引入同一种 reset，谁后加载谁覆盖，表现为进入某个页面后另一个页面的按钮变了颜色。这要靠约定解决：全局 reset 只由外壳出一份。

共享依赖与版本冲突

有些依赖必须全局单例，React 最典型。同一页面出现两份 React，轻则 Invalid hook call，重则 Context 跨实例失效、ref 转发链断裂。路由库有两份就各维护一份历史状态，地址栏与应用视图错位；状态库有两份，两个组件订阅同名 store 却读到不同数据，看着像偶发的数据不同步，实为多实例。

约定要分两处落。构建期把 React、渲染器、路由外部化，由外壳或统一装载器提供，子应用声明为同行依赖，并在流水线里校验实际解析到的版本。运行期靠按模块名解析的装载层兜底，让所有应用指向同一份实例；启动时做显式校验，不一致就拒绝挂载并上报，而不是带病运行。

兼容窗口同样要约定：外壳同时支持子应用的一前一后两个版本，超出范围就拒绝装配并给出可读原因。

通信与状态：把契约写成显式的东西

三类手段按稳定性排序是 URL、只读状态下发、事件总线。

URL 是最被低估的跨应用契约，天然可分享、可前进后退：把在编辑哪条记录放进地址，各应用解析同一份信息。只读状态下发指外壳把用户、租户、主题、权限清单作为属性交给子应用，只读不回写；要改就走显式的意图回调，由外壳决定副作用。

事件总线最容易写也最容易烂：问题在于名字不受约束，一处发出订单已变更这类通用事件，别处遗留的监听就会接住它。我们见过两个应用除私有事件外还共用挂在 window 上的全局对象，A 提交后 B 的旧监听触发同一次请求，页面重复写入，排查要跨三个源映射，一天定不到根因。

约束办法很朴素：事件清单像接口一样纳入评审，名字带前缀，载荷由共享类型包约束，每个跨应用事件都能被 grep 到唯一发布方。

路由归属与深链

前缀是公共 API。给每个应用一段稳定前缀，一段前缀只归一个应用，不要用通配兜底把未知路径随便派出去；将来迁移或改名，必须在保留期内挂显式重定向，否则收藏的深链会静默变 404。

切换时的加载与卸载要写清策略。首次进入前缀再拉入口并配骨架屏，避免外壳启动就把所有应用请求一遍；保活换来返回时的即时感，代价是内存、定时器与订阅全在跑，页面一多就失控。卸载不是把容器清空：挂在 body 的浮层节点、全局监听、轮询任务都要回收，否则第二次进入同一个应用会看到双份行为。

404 归属要唯一：匹配不到前缀的地址由外壳渲染兜底页，应用内部的 404 只出现在自己的视图区域，不改写整体地址语义。历史操作统一由外壳封装一层，禁止子应用直接改整页地址——那会退化成一次全量刷新，共享依赖白加载——并且要记住滚动位置。

部署、灰度与回滚

独立发布的前提是信任有边界。契约测试是第一道：前缀、跨应用事件名、下发属性的结构各写一组自动化冒烟，跑在发布流水线上，任何一方破坏契约就先在 CI 里红。第二道是版本兼容窗口——外壳支持范围内的子应用版本，子应用也假定外壳可能是上一版，双方都不做同时上线的假设。

灰度与回滚的控制点最好集中在外壳。应用清单按用户或租户分桶，不同桶指向不同版本入口；回滚就是把某个桶的条目改回上一个已验证版本，不必重新发布任何子应用。这要求清单能秒级生效。

产物与 CDN 的关系要分清：带内容哈希的静态资源可以长缓存，不带哈希的清单与入口必须短缓存或不缓存，否则回滚之后浏览器仍拿到旧引用，出现改了但线上没变这种最难查的现象。

什么时候不该用

一句话判据：拆开的收益主要体现在组织而不是技术上时可以做，只想解决构建慢或代码乱，做了只会更糟。

团队规模 页面耦合度 技术栈统一度 建议形态
一到两个团队 高，页面共享大量状态 已统一 单体加清晰模块边界，必要时配 monorepo
三个以上团队 中，以页面为单位弱耦合 部分需要共存 路由接管式或共享依赖式运行时集成
多个外部团队 低，区块级拼装 完全不约束 iframe 或 Web Components 做硬隔离
一个团队但遗留栈 高 旧栈无法重写 外壳包住旧区块，新页面统一技术栈

常见反效果要提前写进评审材料：依赖被打成多份，体积不降反升；体验割裂，导航、加载态与错误提示在不同区域风格不一；调试链路变长，一次点击要跨三个应用与两套框架的源映射；首屏要先等外壳再等子应用。这些能靠约定压制，却压不掉组织本身的问题——只有一个团队时，复杂度没有任何收益去对冲。

小结

微前端的正当动因是团队独立交付与遗留栈共存，不是架构审美。先按团队数、发布频率、耦合度决定要不要做，再从六类方式里选最保守的那一种：能用构建时聚合解决的不上运行时，能用路由接管的不上自定义元素，iframe 留给不打算统一的区块。真正要花力气的是四件乏味的事：把外壳做薄，把单例依赖约定成全局，把跨应用通信写成可 grep 的契约，把清单与入口的缓存策略调对。回滚能力要比发布能力先到位——装配失败影响的是整个页面，不是某个组件。
