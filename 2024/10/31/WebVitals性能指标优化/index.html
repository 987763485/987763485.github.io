Web Vitals 性能指标优化

页面加载快不快、点下去有没有反应、内容会不会突然跳动，分别对应 LCP、INP 与 CLS。本文把三个指标的口径逐个拆开，说明分数由哪几段构成、被什么拖坏，再给出采集代码与优化手段，适合已经接了性能看板、改一轮却发现指标纹丝不动的前端同学。

三个指标各自在测什么

LCP（Largest Contentful Paint，最大内容绘制）测视口内最大内容完成渲染的时刻。最大元素指图片（含 CSS 背景图）、video 首帧海报、image 类型的 canvas，或块级文本里字体渲染面积最大的节点。它不等于页面可用，只看单个元素：最大元素若是懒加载的封面图，即便框架早已可交互，LCP 仍被这张图的下载与解码推到很后；若是首屏标题，则要等字体绘制才落表。不同视口选中的元素可能不同，移动端与桌面端手段不能直接复用。

INP（Interaction to Next Paint，交互到下一次绘制）于 2024 年 3 月 12 日取代 FID 成为 Core Web Vitals，FID 自 2024 年 9 月起不再展示。它覆盖整个生命周期的所有交互，取最差一次作为页面分，聚合接近 p98 分位而非平均。一次交互拆三段：输入延迟，事件已排队而主线程仍在忙；处理时长，处理器与同步任务执行；呈现延迟，更新提交渲染管线到下一帧绘制。FID 被替换，正因为它只看首次交互、只看回调能否及时开始，不含渲染段。三段对应三种手段：切长任务治输入延迟，减同步计算治处理时长，缩小 DOM 更新治呈现延迟。

CLS（Cumulative Layout Shift，累积布局偏移）测可见元素在无用户输入时发生意外位移的程度。单次分数等于距离分数（位移相对视口对角线的比例）乘以影响分数（偏移前后区域并集占视口的比例）。会话级结果不取最大那一次，而按时间窗口累加：每 500 毫秒一个窗口、总跨度上限 25 秒，取累加值最大的窗口。因为连续小偏移往往比一次孤立跳动更扰人——不断刷新的推荐位单帧都算轻微，累计起来却把阅读位置持续推走。反过来，纯用 transform 的动画不计入偏移，这成了常见认知陷阱。

本文数字与阈值一律是团队约定示例阈值或示意值。

实验室数据与真实数据为什么必然不同

合成监控（Lighthouse）与真实用户监控（RUM）之间是相关，不是相等。实验室把每个变量取成保守常数：冷缓存、无其他标签页、CPU 降频倍率固定（常见默认 4 倍 slowdown）、网络用协议层节流按固定 RTT 与带宽模拟，于是同一次改动跑三遍，LCP 方差就可能盖掉你优化下来的差值。真实用户带宽抖动、缓存常热、设备性能长尾，还有相当比例页面在后台打开，可见性计时随之改变。所以实验室适合归因（哪个资源阻塞、哪个任务过长），不适合下结论。

真实数据看 p75，即 75% 的访问比这个值好，而不是均值：均值被大量极快回访拉低，p50 又让最慢的四分之一用户失去声音。团队约定示例阈值可定为 p75 达标即视为该路由健康，同时保留 p95 观察尾部。真实数据里 Android 中低端机占比远高于自测用的旗舰机，本地流畅而线上复现不成立是常态；采集有开销，多数实现按会话或页面抽样，抽样率是配置项而非常数，跨版本比较前必须确认口径一致。

最后是分层。页面级按路由模板聚合，回答这个页面体验如何，却会把首页与长尾页混在一起；业务级按关键用户旅程（从列表进详情、提交订单）聚合，才回答这条链路是否真的慢。先用页面级发现异常，再用业务级定位责任模块。预算如何制定、指标如何进 CI 门禁，是《前端性能预算实践》的内容，本文只讲单项指标本身。

采集实现

三个指标都能用 PerformanceObserver 直接拿到，不必依赖库：

buffered: true 解决观察器注册太晚造成的丢失。埋点脚本常被打进异步 chunk 或由标签管理器二次注入，等它跑起来时 LCP 元素早绘制完了；打开 buffered 才能读回注册前缓冲区里的历史条目。event 缓冲区有容量上限，交互密集时会丢早期条目，这也是建议直接引 web-vitals 库的理由之一，它还处理了最终值判定与浏览器实现差异。

SPA 场景要小心语义变化。单页内导航不重置文档，LCP 条目只在首次加载产生一次，切路由后新页面那张最大的封面图不会再更新 LCP，你上报的永远只是落地页；CLS 相反，它跨路由持续累加，会把整段会话的偏移算到最后一个页面。常见处理是切路由时以旧路由名结算上一段、再重新开始统计，并明确 SPA 的 LCP 只是入口体验指标。INP 覆盖整个生命周期，相对安全。

上报时机不要放在 unload。可靠做法是监听 visibilitychange 到 hidden 与 pagehide，两者在页面进 bfcache 时也会触发；发送用 navigator.sendBeacon 或带 keepalive: true 的 fetch。三项指标合并成一条事件，带上路由、版本、设备等级与抽样标记，通道与隐私口径沿用《前端异常监控与埋点体系》，本文不重复。

LCP 的成因链与优化

LCP 的时间轴是一条串行链，任何一环慢都会原样体现在指标上。

flowchart TD
  A[请求发出] --> B[TTFB 首字节]
  B --> C[解析 HTML 与首屏 CSS]
  C --> D{LCP 元素类型}
  D -->|图片| E[发现资源、下载、解码、绘制]
  D -->|文本| F[字体就绪后绘制文本]
  E --> G[LCP 落表]
  F --> G

链首是 TTFB，HTML 慢则后面所有事都往后推；前端能做的是把首屏内容放进服务端返回的 HTML，而不是等脚本执行完才画。其次是渲染阻塞资源：过大的首屏 CSS 与 head 里的同步脚本会推迟布局与绘制，也让 LCP 元素的发现时间变晚——浏览器要先解析到那个节点才知道该下载什么。图片类 LCP 要走发现、下载、解码三步，最容易吃亏的是发现：loading="lazy" 用在对首屏封面图上，等于把发现推到滚动之后，它只该给折以下图片使用。fetchpriority="high" 适合首屏封面这类确定性元素（当时在主流 Chromium 可用，跨浏览器需检查状态）；rel="preload" 能提前发现，但会抢关键资源带宽，预加载一堆没用上的东西反而拖慢 LCP，只在无法调整 HTML 结构或资源由脚本决定时少量使用。图片给与显示尺寸匹配的分辨率、优先现代格式并写 srcset 兜底。

文本类 LCP 的成因是字体，三种 font-display 各有观感代价：block 期间完全不显示文本（最长约 3 秒不可见期，观感是白屏，最容易同时伤到 LCP）、swap 先用系统字体占位再替换（代价是一次字形跳变，并带来 CLS 偏移）、optional 尽量不等（首帧稳定，代价是首屏很可能用不上目标字体）。LCP 元素是文本就配 swap 并控制子集，更看重一致性就配 block 加短超时。

INP 的成因链与优化

三段里多数劣化不出在处理时长本身，而出在交互到来之前主线程已被占满。规范把超过 50 毫秒的任务定义为长任务，一次首屏 hydration 常由几个几百毫秒的长任务串成（示意值），这期间点下的每次按钮都要排队，输入延迟直接变成几十到上百毫秒。原则是缩短单个任务的执行时间，而不是减少任务数量。

setTimeout 让出是粗粒度方案，代价是整体完成时间变长，分片太细则被调度开销反噬。其余三条来源：一是处理器里的同步计算与强制同步布局，点击回调中先读几何属性再写样式会触发强制重排，把处理时长与呈现延迟同时拉长，做法是读写分离、把统计与序列化挪到让出之后。二是渲染开销，React 与 Vue 里在交互回调中更新大状态对象会让整棵子树重渲染，把状态收窄、列表虚拟化只渲染视口内节点，收益直接落在呈现延迟段。三是第三方脚本抢占，埋点、广告、客服浮窗同样在主线程执行且不受你审查，可控手段只剩加载时机（延后初始化、按需加载、别在关键路径同步插入 script）与隔离（能用 worker 的计算不放主线程）。

CLS 的成因链与优化

成因可以归成一句：视口内的可见内容被后来的东西挤走了。最常见三类是图片与视频没预留尺寸（加载前占位高度为 0，加载后突然撑开）、广告与推荐位异步插入、字体替换与动态插入内容。

对应手段：给媒体元素写显式 width/height 或用 CSS 的 aspect-ratio，让占位在资源到达前就是正确高度；给广告位与异步模块预留固定尺寸容器，宁可留白也不要让高度随返回内容变化，但预留要按真实返回概率校准，长期空置本身是体验损失；字体替换的偏移来自两套字体的度量差异，手段是控制子集体积、对 fallback 用 size-adjust 一类度量覆盖参数（当时主要在 Chromium 支持）；动态内容优先插到视口下方，必须插到上方时滚动锚定能缓解一部分，但不能指望它覆盖全部场景；sticky 吸顶后自身移动不计入偏移，可一旦展开菜单把下方整页推走，偏移照样计算。

最容易误判的是用 transform 做位移补偿：纯 transform 动画不产生布局偏移，分数上很干净，但用户看到的仍然是一块内容在跳动。它适合预期内的动效，不适合抹平预期外的跳动，否则看板上得到好消息，用户那里什么都没变。

验证与防回归

改完要回答两件事：是否生效、会不会退化。

本地对比只用于归因与验证方向：固定设备与网络，清缓存、不清缓存各跑一组，每个变体跑若干次取中位数，并盯住同一个 LCP 候选元素（上报带上元素选择器，否则分不清是优化生效还是最大元素换了）。INP 的本地验证更直接：录一段交互，看三段各自时长是否缩短。真实数据一侧要用观察窗口，团队约定示例做法是变更前后各取 28 天，并排除三类干扰：新版本带来的用户结构变化、季节性流量、抽样率调整；窗口内再按设备等级分层，否则低端机占比一变就能伪造一次劣化。防回归最省事的是把 p75 与 p95 做成日级趋势并配阈值提醒，阈值取团队约定示例值；通用优化技巧见关键渲染路径与移动端性能那几篇旧文。

小结

三个指标各测一件事：LCP 是单个最大元素的完成渲染时刻，受发现、下载、解码与字体串行影响；INP 是生命周期里最差一次交互的三段之和，主要对手是长任务；CLS 是时间窗口内意外偏移的累加，靠预留尺寸而非事后补偿。实验室数据看成因，真实数据看尾部，两者隔着环境、缓存、节流与分位口径。上线前先在本地确认方向，再用分层观察窗口确认 p75 与 p95 真的动了，并把元素选择器、事件类型、版本与抽样率一起上报。本文数字都是团队约定示例阈值或示意值：指标是手段，用户感知才是目的。
