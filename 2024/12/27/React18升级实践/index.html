React 18 升级实践

2024 年下半年，我们把团队里几个还停在 React 17 上的业务仓库陆续推到了 18.x。这篇是这轮升级的经验复盘：渲染入口怎么切、双调用暴露出哪些真问题、批量更新改了语义之后如何排查，以及灰度和回滚的开关怎么设计。React 19 在 2024 年 12 月 5 日刚发布，本文只把它当作下一步的预告，不展开任何未经生产验证的细节。本仓库早前那篇讲工程化与 TypeScript 早期实践的文章处理的是另一个年代的问题，这里不复述。

升级前的体检：先把不兼容的东西挖出来

升级 React 大版本最容易犯的错误，是直接改 package.json 里的版本号然后开始修编译错误。更靠谱的顺序是先做一次静态体检，把“机械可替换”和“语义会变”两类问题分开，因为前者可以交给脚本，后者必须人来读代码。

入口是最先要动的地方。18 之后推荐的挂载方式是 createRoot，它同时是并发特性的开关：只用老的 ReactDOM.render，即便装了 18 也拿不到并发渲染，只会拿到行为差异带来的麻烦。

水合入口要单独列出来核对。我们第一个仓库就漏了一个服务端渲染的模板页，构建通过、本地跑得也好好的，直到灰度环境报出 hydration mismatch 才被发现。把入口文件收敛到一个模块（例如 src/entrypoints/ 下），再要求所有新增入口走这条约定，是比“全仓搜索一次”更长期有效的做法。

第二类等生命周期。componentWillMount、componentWillReceiveProps、componentWillUpdate 这几个在 18 的 StrictMode 下会明确给出弃用警告，它们的问题在于依赖“这段代码只跑一次”。迁移方向是把它们各自搬到语义更确定的位置：初始化逻辑进 constructor 或 componentDidMount，派生状态进静态的 getDerivedStateFromProps 加 getSnapshotBeforeUpdate，卸载清理留在 componentWillUnmount。类组件不多时，我们倾向于顺手把带旧生命周期的组件重写成函数组件，而不是原样保留类形态再改生命周期。

第三类是 findDOMNode。它在并发渲染下语义不稳定，迁移方式很机械：给目标元素加 ref，从 ref.current 取值。真正麻烦的是那些把 DOM 节点当参数传给第三方库的地方（弹窗定位、图表挂载、拖拽库），需要确认库的 API 是否接受节点引用，以及节点在 React 重渲染后被替换时库会不会缓存住旧的引用。

体检的第四类是第三方库对并发模式的兼容。这里的关键判断是：18 的 render 阶段可能被中断后重放，所以“在渲染阶段做一次性副作用”的库会出问题——在渲染函数里注册全局监听、往单例 map 里写状态、依赖模块级变量做去重，这类写法在并发下都会漏。我们整理的办法很朴素，全仓搜一遍在组件函数体顶层出现的非纯操作，逐个确认；依赖列表里渲染阶段有副作用的库，先降级为同步渲染或把它从并发路径里排除。

StrictMode 的双调用：把藏着的副作用问题照出来

升到 18 之后，很多人第一次遇到的“惊吓”来自 StrictMode：开发环境下组件的函数体、初始化函数、render 阶段的方法会被调用两次，效果看起来像重复请求、重复打点、状态莫名错乱。这里要说清楚一件事，双调用只在开发模式发生，它是 React 有意为之的探针，为的是让“以后可能重放”的代码现在就暴露出来，而不是等到并发场景下才炸。线上不会有这个行为，所以它的定位是“提前告诉你这段代码不幂等”。

我们的排查顺序是先给每个双调用现场做一次定性，问一个问题：这个副作用重复执行一次，用户会看到什么？

第一个版本不是“因为双调用才有 bug”，它本身在并发渲染下就会重复发请求，双调用只是把一个已经存在的缺陷提前放到你眼前。区分“开发期噪声”和“真 bug”的标准也在这里：如果这段代码在 render 阶段之外、并且有配对的清理，双调用带来的只是控制台日志和一次额外的开销，属于噪声；如果它在 render 阶段有外部写入（请求、埋点、改全局对象、改 DOM 但不归 React 管），那它就是真 bug，必须改。

副作用的幂等写法，我们沉淀出几条约定。第一，一切外部交互进 effect，并且清理函数要能真正撤销这一步做的事：解绑监听、abort 请求、清定时器、取消订阅。第二， effect 的依赖数组要按语义写，不要为了让“只跑一次”的旧直觉满意就留空数组，双调用下这只会让状态停留在第一次的结果上。第三，对“只能发生一次”的动作（写本地存储的一次性引导标记、上报会话开始），把判断依据放在模块级或 ref 上，而不是组件的渲染次数上。第四，订阅类要返回退订，且要处理“先退订再重订”的时序。

埋点是这个机制下最容易误判的一类。双调用会让开发环境的埋点条数翻倍，如果在联调时按开发环境的数字核对，就会得出“上报逻辑有 bug”的错误结论。我们的做法是在埋点层加一个开发环境的标记字段，把这类数据从统计口径里天然隔离出去，同时约定所有埋点核对只看测试环境和灰度环境。

还有一个心理层面的收益值得记录。第一次把 StrictMode 打开并且清空所有警告之后，后续几轮功能迭代的返工率明显下降，因为“渲染阶段做副作用”这个习惯一旦在团队里被清除，并发相关的疑难杂症基本就没有土壤了。这也是我们把“仓库必须处于 StrictMode 且无警告”写进升级验收标准的原因。

Automatic Batching：批量边界变了，排查思路也要变

17 及更早版本的批量更新只覆盖 React 事件处理函数内部。在 setTimeout 回调、Promise 的 then、原生事件监听或第三方库回调里连续调用两次 setState，会触发两次渲染。18 把批量范围扩展到了所有场景，无论更新发生在哪一层，同一批微任务里的状态更新都会被合并成一次渲染。

这个变化本身是性能收益，但它在升级过程中制造了一类非常难查的现象：升级前“能正常显示”的代码，升级后偶发地显示不出最新值。我们复盘下来，成因几乎都不是 React 丢了更新，而是老代码在无意中依赖了“渲染是同步分两次发生”这个前提。

排查这类问题我们按三步走。第一步确认是不是“读到旧值”：把连续两个更新的中间值打印出来，如果第二次读到的仍是第一次之前的值，基本可以定位。第二步找依赖点，重点看三类位置——更新后紧接着读取 state 的函数、把 state 作为参数传给命令式 API 的地方、以及在回调里靠多次更新来“推动”渲染次数的手动写法。第三步改语义而不是改时序：正确做法是让数据流变成“事件产生新值，新值同时用于更新 state 和后续逻辑”，而不是先更新 state 再从 state 里读回来。

有一个反例值得警惕：不要在业务代码里用 flushSync 去“恢复升级前的行为”。它能解燃眉之急，但它把渲染强行变成同步，在并发路径上会放大卡顿，而且一旦散落各处就变成新的隐性约定。我们的规则是 flushSync 只允许出现在与第三方库命令式 API 对接的适配层，出现一次就要写一次注释说明为什么必须同步。

同理，unstable_batchedUpdates 在新版本里已经没有存在必要，可以随升级一起清掉；清理时记得把那些位置加进回归测试列表，因为那里本来就是时序敏感区。

并发特性：transition 与 deferred 各自解决什么

把入口换成 createRoot 之后，并发能力才算真正可用。但并发特性不是“打开就变快”，它解决的是“高优先级输入不被长任务阻塞”这一类体验问题，选错工具反而会增加复杂度。我们把两把常用的工具按“谁被打断”来区分。

useTransition 与 startTransition 标记的是“这次更新引起的渲染可以被别的更新打断”。它适合输入联想、切换筛选条件后重新计算大列表这类场景：用户继续在输入框打字时，为上一次按键产生的列表渲染可以被放弃重来。两者的差别在使用方式上：useTransition 返回一个 isPending 用于在界面上表达“正在更新”，适合需要加载态反馈的组件；startTransition 没有 isPending，适合在组件外、事件处理器里或非组件模块中把某次更新降级为可中断。

useDeferredValue 解决的是另一半问题：拿到的值本身延迟更新，从而让慢的那部分渲染“落后”于快的那部分。当被延迟的值不是由你自己的 setState 产生，而是父组件传下来的一段数据、或者你没法改写产生它的那段逻辑时，用它更顺手；反过来，如果你能控制更新的产生位置，startTransition 表达意图更清楚。我们团队的约定是：能在事件处理器里显式区分两次更新的，用 startTransition；只能对已有值做延迟处理的，用 useDeferredValue。两者都别同时套在同一个状态上，那只会让排查时看不清到底哪一层在动。

Suspense 在 18 里的定位是让“等待中的这部分树先渲染兜底内容”，配合数据流时它把加载态从每个组件里的 if (loading) 收敛到边界上。但要清楚它的收益边界：在客户端从接口拿数据这件事上，光把请求放进组件里然后靠 Suspense 兜底，是拿不到预期效果的，因为组件每次重渲染都会重新发起请求，真正可用的形态是“能被挂起的数据源”这一类机制。我们的做法是把数据获取仍放在 effect 或集中的 hooks 层，只在“整块内容依赖异步资源”的位置上划 Suspense 边界，并给边界设置合理的粒度，避免一个大边界把整个页面的骨架都吞掉。边界粒度太粗会让加载态覆盖已有内容，太细会引发闪烁，我们从页面级开始，再按体验反馈往下拆。

外部状态库的“撕裂”问题在并发渲染下更容易暴露：一次渲染跨越了两个更新周期，同一次渲染里从 store 读到的两个值可能来自不同时刻。官方给出的答案是 useSyncExternalStore，用统一的订阅与快照读取方式保证一致性。这块我们仓库里另有一篇专文展开，此处只说明它与升级的关系：迁移前依赖手写的 subscribe 加 forceUpdate 的适配层，是升级后出现“列表某几行显示旧数据”这类反馈时最先要检查的地方。

回到本次升级的节奏：这些特性都属于“升级之后才能开始用”的增量工作，不要把新特性的落地和版本迁移混在同一次发布里。我们的顺序是先完成迁移并把警告清零，观察一到两个迭代，再按场景挑一到两处引入 transition。

升级策略：按包灰度、批次顺序、回滚点

多仓库或单仓多包的形态下，“一口气全升”带来的最大问题不是技术难度，而是出问题时无法定位是哪一批变更导致的。我们最终采用的策略是按包灰度：以业务包为单位分批，每批只包含一个包的依赖升级加上该包内的适配改造，让“版本变更”和“业务变更”在发布单元上一一绑定。跨包共用的组件库先出兼容 18 的版本，业务包再逐个把它装上，这样任何一批都能单独回滚而不牵连其他批。

批次内部有两处顺序决策需要说清楚。第一，渲染入口先切还是组件先改。我们的选择是先改组件、后切入口：入口切换到 createRoot 会把双调用和批量语义一起打开，此时如果组件里还残留大量 render 阶段副作用，出问题时很难判断是入口变更还是组件变更引起的。反过来先做机械替换与生命周期迁移，在这期间老入口仍然工作，改动带来的风险是可控的；最后单独一次发布切入口，切完只观察一类信号，定位面窄。第二，StrictMode 的打开时机。我们把它放在切入口的同一次发布里，因为两者都属于“改变渲染行为”的变更，放在一起只需一次集中回归；但前提是这一批改动的文件清单要短。

回归测试的设计是这次升级里投入产出比最高的环节，也是我们踩坑最多的地方。先说快照测试的局限：升级后快照会大面积失败，其中绝大多数只是渲染结构里的注释节点、包裹层或 key 表达形式变了。如果靠“全部更新快照”来通过测试，等于把一次真正的回归掩盖在几百行无意义的 diff 里。我们的处理是把快照测试暂时降级为参考，改为先看 diff 内容再决定是否需要更新，并把快照数量在升级后主动收窄。

行为测试优先。判断标准很简单：这条测试是否绑定了用户能感知的结果。我们补的重点是三类——输入到列表更新这条链路（用来抓批量语义变化）、弹窗打开后焦点与 DOM 是否挂载成功（用来抓 findDOMNode 迁移）、路由切换后清理是否执行（用来抓 effect 配对）。这些用例在旧版本上跑过一遍确认全绿，再在升级分支上跑，才有对照意义。

开关与回滚点是必须提前设计而不是事后补的东西。我们把入口选择做成一个构建期可读到的配置项：同一个包能产出走老入口和走新入口的两份产物，灰度平台按比例下发，出问题只需要把配置切回旧入口再重新发布，不用回滚代码。这个开关的生命周期要写进计划——我们在升级完成一个迭代后就把它连同分支代码一起删除了，长期留着的双入口路径会变成团队的认知负担。

指标方面，我们盯三组数：首屏可交互相关的时间指标、长任务与卡顿次数的分布、以及 React 相关的错误上报量。要点有三。第一，切入口前后各留至少一个完整业务周期的数据，避开大促和发版当天的噪声；第二，升级本身不等于性能优化，所以首屏数字大概率不会有明显变化，真正变化的是卡顿分布的长尾，如果只盯平均值会得出“没收益”的结论；第三，本文不给出具体百分比结论，你们仓库里的数值必然不同，写进汇报的数字都应标注为示意值。

迁移中的坑清单

这一节把升级过程中真实遇到的坑列成一圈清单，每条后面附上我们的判断依据，方便你在自己的仓库里快速对照。

第一个坑是 ref 转发相关的行为变化。当函数组件需要接收 ref，仍然必须显式使用 forwardRef；升级过程中如果同时调整了组件包装层，很容易出现“ref 传下去变成 undefined”的情况，表现为定位库拿不到节点、弹窗位置错乱。排查方式是沿着包装链一层层打印 ref.current，中断的那一层通常就是新加的包装组件。凡是给组件加了高阶函数包装的地方，都要重新确认 ref 是否被透传，这类改动在升级期间经常伴随出现。

第二个坑是 defaultProps 搬到参数默认值之后的差别。对 undefined 两者表现一致，但生效时机不同：defaultProps 由 React 在元素创建时补齐，包装层与透传出去的 props 拿到的是补过的值；参数默认值只在组件自己解构的那一层生效，如果 props 被原样转交给别的组件，兜底就丢了。这类差异不会报错，只在特定调用形态下显示异常，要靠覆盖包装与透传的用例才能发现。

第三个坑是类型层面的变化。升级到 18 的类型定义后，编译器的报错数量会增加，这些报错大部分是好事，说明以前被宽松类型掩盖的问题暴露了。具体表现包括函数组件类型不再默认携带 children，需要显式声明；以及若干与 JSX 命名空间解析相关的写法在新版本下不再隐式可用。这里我刻意不列出具体类型名和签名细节，因为不同 @types/react 小版本之间有过调整，编一张对照表容易出错也不好在你们的版本上复用。可靠的做法是把 typecheck 的报错逐条当作待办清单，看编译器给的提示和官方迁移说明，而不是从别人的博客抄一段类型补丁贴进项目。原则是：不用 any 压制报错，也不用一行全局声明换掉一批真实问题。

第四个坑是测试环境的 act 警告。升级后单测里会集中出现这类提示，它的含义是“有状态更新发生在测试控制的时机之外”。它有两类完全不同的原因，要分开处理。一类是测试写法问题：断言前没有把异步更新等待完成，正确做法是用异步的 act 包住触发与等待，让更新跑完再断言。另一类是生产代码问题：组件在渲染阶段就发起了会影响状态的副作用，这恰好是前面 StrictMode 那节说的缺陷，测试只是把它提前告诉你了。把 act 警告一律靠配置忽略掉的后果是，测试跑得很干净，但它测的已经不是真实的时序。

第五个坑与服务端渲染的模板有关。水合入口切换之后，模板里如果还残留早期版本的挂载脚本引用，会出现“页面无报错但不交互”的情况，因为新的 root 从未被创建。这类问题在 CI 上抓不到，必须靠灰度环境真实访问一次。我们的检查项是把所有服务端模板与静态 HTML 列成清单，逐条核对脚本引用与挂载节点 id。

第六个坑是第三方弹层的挂载节点。有些库把内容渲染到 document.body 下，升级后如果入口的挂载结构或挂载时机变了，会出现样式丢失或弹层错位。定位关键是“节点有没有被创建”：先确认 DOM 结构，再确认 CSS 作用域是否覆盖到它，不要一上来就怀疑 React 的渲染。

清单最后加一条经验性的：每解决一个坑，把它写成一条能在体检阶段自动发现的检查项（一条搜索命令，或者一个 lint 规则），下一批灰度就能直接挡住同类问题，不用第二次靠人肉发现。

性能与包体：别把升级本身当成优化

需要把一个容易被误传的因果讲清楚：从 17 升到 18 不会自动让页面变快，包体积也不会因为换版本就明显下降。升级带来的是能力和更一致的更新语义，性能收益来自你在这之后使用了并发特性、把渲染工作量拆成了可打断的部分，或者顺手做了路由与组件级的分包。把这两件事写进同一份汇报，短期好看，长期会让团队对“版本升级”形成错误的收益预期，下一次迁移就很难申请到排期。

真正影响包体的通常是伴随升级一起清理的东西：为绕过旧批量行为而引入的工具代码、已经废弃的生命周期与兼容层、以及被 forwardRef 改造后不再需要的包装组件。这些删除是实打实的体积减少，可以在升级完成后单独统计一次。至于新增的并发 API，它们本身在运行时里，不需要为“以后可能用”而在每个包提前引入。

下一步：React 19 刚刚发布

这篇写于 2024 年 12 月 27 日，React 19 在 12 月 5 日刚发布。我们生产上跑的是 18.x，19 目前只在个人项目里试过，所以下面只列官方在发布说明里点出的方向，不写迁移步骤，也不给 API 层面的结论：编译方向的工具想减少手写记忆化，资源相关的用法想把异步数据写得更直接，表单与动作想收敛提交状态。这些都还需要生态跟上，尤其是组件库、路由与状态管理库的类型与运行时兼容，等它们跟上再评估。本仓库那篇服务端组件探索的文章处理的是渲染边界另一侧的问题，这里也不重复。我们的计划是等 19 的兼容矩阵明确后，用同一套体检加灰度流程再走一遍。

升级前中后检查清单

阶段 检查项 通过标准
升级前 统计旧生命周期、findDOMNode、手动批量的数量 数量级已知，排期按批划分
升级前 梳理全部挂载与水合入口，收敛到约定目录 入口清单完整，无模板遗漏
升级前 第三方库并发兼容评估与组件库先发兼容版本 每批依赖可单独回滚
升级前 建立双入口开关与埋点基线 旧入口可一键切回
改造中 codemod 处理机械替换，语义变更人工复核 编译通过且无新增 any
改造中 render 阶段副作用清零，effect 清理成对 StrictMode 无警告
改造中 行为测试补齐输入链路、弹窗、路由三场景 旧版本全绿后再对照
切换后 同次发布切 createRoot 并打开 StrictMode 变更文件清单短且集中
切换后 观察首屏、长任务分布、错误上报一个周期 错误量不升，长尾可解释
切换后 按场景引入 transition 或 deferred 与迁移不同批发版
收尾 删除双入口开关与冗余批量代码 开关生命周期有明确终点

小结

这轮升级最值得留下的经验，是“把版本变更和行为变更分开”这件事。入口切换、StrictMode、批量语义都属于行为变更，它们才是风险的来源；组件改造和依赖升级都属于可静态核对的部分，交给脚本和清单。顺序上先清副作用、再切入口，测试上先降级快照、再补行为用例，指标上多看错误量与长尾而不是平均值。并发特性是这次迁移的真正回报，但要等迁移稳定之后再按场景引入。19 已经发布，方向清楚，只是我们还需要等生态一步。
