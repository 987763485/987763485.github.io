Vue 3 项目性能优化

性能优化在 Vue 3 项目里经常被简化成”加一个 computed、拆一个组件”，但收益来自一条因果链：先确定成本发生在哪一层，再选那一层的工具。本文按编译层、响应式层、组件层、列表层与产物层拆开这些手段，说明各自的收益来源与副作用；响应式系统与浏览器指标的定义另文已有，这里只用它们解释优化为什么有效。

先测量：把”感觉慢”拆成可归因的成本

拿到”页面卡顿”的反馈，第一件事不是改代码，而是确认成本落在哪一层。Vue 3 项目的性能问题大致两类：一类是编译层与产物层的成本，表现为下载与解析的体积、首屏可交互前主线程被占用；另一类是运行时成本，表现为状态变化后视图响应的延迟、滚动或输入时的掉帧。两类的定位、修复与验收指标完全不同，混在一起谈优化，很容易做出看不出收益的改动。

编译层的收益主要落在更新阶段，要靠渲染耗时数据判断；产物层的收益主要落在首屏，要靠构建体积与网络瀑布判断。把它们统称为”性能优化”，是很多团队做完之后无法归因的根源。

Vue Devtools 的 Components 面板可以打开渲染耗时统计，给每个组件标出上一次渲染耗时与本次会话内的渲染次数。这两个数字要分开看：耗时高说明渲染函数本身昂贵，次数多说明它被过度触发；一个耗时零点几毫秒却每次按键渲染上百次的组件，总成本高于耗时几毫秒但只渲染一次的组件。面板里的更新高亮选项在排查”不知道是谁在重渲染”时特别有效，它能把更新归因到具体模板位置，而不是靠猜。

组件级计时用 performance.mark 与 performance.measure，它能留下可导出、可被脚本读取的记录。标记要打在状态变更前后而不是渲染函数里——前者度量用户感知延迟，后者只度量 Vue 自己花了多少时间。

还有一层容易被忽略：Vue 的更新被批量调度到微任务里，一次状态变更引发的多个组件更新会合并进同一个任务；当这个任务超过 50 毫秒，它就成为一个浏览器长任务，输入响应被卡在它后面。用 PerformanceObserver 监听 longtask 条目并与操作时间点关联，就能回答”卡顿是不是 Vue 更新造成的”。但长任务接口只给耗时与归因，给不出是哪个组件贡献的，所以它适合监控告警，精确定位仍要靠组件级计时。

测量的纪律是建立基线：固定数据规模、设备与网络条件，改动前后各跑若干次取中位数。本文不给”从 800 毫秒降到 120 毫秒”这类数字，脱离测量条件它们没有可比性；下文出现的数值一律是示意值或团队约定示例。

编译层：让模板里的静态信息真正被用上

Vue 3 的模板编译器会把模板中可确定的信息固化成运行时可用的提示，理解它才知道哪些写法能享受收益、哪些会把它绕开。静态提升把纯静态节点及其子树移到渲染函数之外，只创建一次并复用同一批虚拟 DOM 对象；补丁标记用按位组合的方式标出一个元素哪些部分会变化，比如只有文本变、只有类名变、只有普通属性变；块级树把动态节点收集进所属的块，更新时只比较块内登记的动态节点，而不是从根开始逐层递归比较整棵子树。响应式系统的内部依赖收集另文已述，这里只需要接受它的结论：标记越精确，需要比较与读取的响应式依赖就越少。

这套机制的收益是少做工作，不是把工作做得更快：静态多、动态局部化的模板，编译产物本身就把比较范围收窄了，而几乎全动态的模板本来可省的部分就不多。两个常见反模式能说明这条边界。

第一个反模式是在模板里创建新的对象、数组或行内函数，让本可以静态的节点变成动态节点。:style="{ color: state.color }" 每次渲染都新建一个对象，比较时因为引用不同而无法快速判定相等；:class="[...]" 里的数组、@click="() => doIt(item)" 里的箭头函数同理。换成 computed 的结果或稳定的方法引用，节点就能落回较便宜的比较路径。编译器的静态分析只看模板本身，无法穿透一个每次返回新对象的函数，所以把复杂表达式挪出模板在两层同时有效。

第二个反模式是对 v-once 与 v-memo 的过度使用。v-once 让子树只渲染一次并永久跳过后续更新，只适合真正的死内容；放进需要更新的区域，症状是视图永远停在初始值，而这种错误在开发期不一定报错，很容易带到线上。v-memo="[deps]" 缓存整棵子树，依赖变了才重新渲染，配合 v-for 写在同一元素上可以做逐项跳过，例如只有被点击那一行的 selected 变化，其余行用 v-memo="[item.id, item.selected]" 略过。风险在于依赖数组是手写契约：漏掉一个影响渲染的字段，视图就静默不更新，这等于把自动的依赖追踪变成脆弱的手工维护。它适合两类场景——虚拟滚动里被反复回收复用的行，以及父组件被迫重渲染但子树输入确实稳定；其余情况优先考虑 computed 与组件拆分。

真正要掌握的是判断方法：改动之后渲染次数没有下降、渲染耗时没有变化，它就没有收益，只是增加了噪音。

一次更新的真实路径

把上面两层串起来，看一次状态写入到 DOM 补丁之间发生了什么，就能理解各种手段分别切在哪一段上。

flowchart TD
  A[状态写入] --> B[依赖的副作用进入调度队列]
  B --> C[微任务批次合并后统一执行]
  C --> D[组件渲染函数生成新的虚拟节点]
  D --> E[进入块级差异比较]
  E --> F[只遍历块内登记的动态节点]
  F --> G[按补丁标记比较会变化的属性]
  G --> H[执行真实 DOM 补丁]
  E --> I[节点类型或位置不匹配则重建子树]
  I --> H

调度合并解释了为什么连续写入只引发一次渲染，也解释了把写入拆进不同任务会增加更新次数；块级比较解释了为什么局部化的动态内容比散布整棵树的动态内容便宜。隐藏成本最高的是重建子树那条分支：一旦节点判别不一致，Vue 只能卸载旧的再挂载新的，此时子组件的状态、副作用与 DOM 创建成本全部重来。后面提到的 key 选择、条件渲染与组件定义位置，本质上都在这条分支上做文章。

响应式层：只让该响应的数据响应

reactive 与 ref 对复杂类型做的是深层代理：数据被访问到哪一层，代理就创建到哪一层，而代理创建与依赖记录的成本和数据规模、访问广度成正比。一个一万条记录、每条多层嵌套的数组被放进 reactive，每次更新又遍历全部字段时，光是让数据变得响应就已经足够昂贵。

Vue 3 提供了一组缩小响应范围的工具。shallowRef 只对 .value 的替换做响应，内部对象的字段变化不会触发更新；shallowReactive 只代理顶层属性；markRaw 给对象打上跳过标记，使它永远不会被转换成代理；toRaw 则相反，从代理对象取回原始对象。3.5 版本起响应式的内存占用做了改进，依赖存储更紧凑，但那是同样用法更省，不是深层响应式可以随便用的理由。

该用哪种方式取决于数据的更新语义。如果合理的更新方式是整体替换——图表实例、几何点集、编辑器文档对象、接口一次性拿回的大结构——就放进 shallowRef 并按不可变思路重新赋值；如果必须原地改又需要视图跟上，就用 triggerRef 显式通知，但要意识到这等于把更新时机交回自己手里，漏通知就出现数据变了视图不动。

toRaw 的边界要说清楚：它适合读取与比较，比如判断两个对象是否底层同一份数据、把数据交给会深度遍历的库；不适合写入，因为绕过代理改原始对象不会被依赖通知，视图不更新，这类问题比报错更难查。同理，markRaw 只能用在确定不需要响应的对象上，包住了驱动视图的数据，症状同样是视图不动。

另一类零成本收益是把不需要响应的数据移出响应式容器。模块作用域的常量表、枚举映射、正则、格式化函数、静态配置项写在外层即可，不需要 ref，也不必 readonly 包一层：它们本就不会变，放进容器只会让编译器判定为动态依赖、让运行时多一次代理与一次追踪。这类改动只在大数据量与高频更新场景才看得出差别，但它是纯收益。

也要警惕反方向的过度优化。把 shallowRef 用在表单对象上，发现输入不生效，再在每个事件里补一次 triggerRef，等于用更贵的手工契约换回本该自动的事情。判断标准只有两条：变更是否真的需要驱动视图，数据是否大到让代理成本可被观察。

组件层：控制重渲染半径与加载时机

Vue 的更新以组件为最小调度单元：每个实例有自己的副作用，模板读取了哪些依赖，就决定它被哪些写入唤醒。于是重渲染半径成为组件设计里最值得量化的指标——一次状态变更会带动多少组件重新执行渲染函数。降低半径最直接的办法是把高频状态往下推：只在叶子节点使用的输入、hover、拖动中间值放进叶子组件的局部状态，而不是提到父组件用 props 下发；父组件只保留确实需要跨子树共享的数据。常见的失控形态，是某个页面把输入框的每个按键都写进共享 store，结果整棵页面树跟着渲染。

但拆分本身不是收益，组件是有成本的：实例创建、props 校验、插槽编译、生命周期钩子都要花时间。把纯展示的静态内容拆成十几个小组件，只是把一次渲染换成十几次，半径没变而总耗时上升。有意义的拆分要么有独立且低频的更新触发源，要么需要在父组件重渲染时被跳过；除此之外，拆分首先是可读性决策，不该拿性能当理由。

有一种静默错误必须写进团队规范：在渲染路径上重新产生组件类型。把组件定义写在另一个组件的函数体内、把内联对象传给 <component :is>、每次渲染新建一个包装组件，都会让新旧节点的组件类型不同，Vue 只能卸载重建，子树里所有状态丢失、DOM 全部重来。它的典型表现是”我只改了一个字段，整个列表闪了一下”。修法是组件定义留在模块顶层，:is 只传稳定引用或已注册的名字。

加载时机是组件层的另一半收益。路由级代码分割用动态 import，让首屏只下载当前路由需要的部分；路由之外的大块低频内容（图表详情、导出面板、复杂弹框的表单）用 defineAsyncComponent 按需拉起，配合骨架屏把等待变成可见的结构。异步组件不是免费的：它把下载与编译成本从首屏挪到交互时刻，如果用户下一跳就要用到它，感知总延迟反而变长，判断标准是该内容在当前路径上被真正用到的概率。Suspense 可以把多个异步依赖的加载态收敛成一个统一边界，做整页级骨架比逐个写加载态省心，但它仍属于需要留意行为变化的实验能力，重要流程上先验证再依赖。

列表层：key、虚拟化与模板里的隐形计算

key 是列表比较里唯一的身份依据。用数组下标做 key，在只追加不删除的静态列表上看不出问题；一旦头部插入或删除中间项，位置与内容的对应关系整体错位：Vue 会认为第 i 个位置上的旧节点就是新的第 i 项，于是把每个节点的属性重新比较甚至重新渲染，本该只是移动的操作变成整片重写。更糟的是有内部状态的子组件会跟着错位——输入框里残留上一项的内容、勾选状态跑到别的行上。在纯展示列表里这只是浪费，在可编辑列表里就是功能缺陷。结论是 key 用稳定且唯一的业务标识，数据本身没有 id 时就在拿到数据时补齐一个，也不要图省事用随机值，那会让每次渲染都判定为全新节点。

长列表的成本上限来自同时存在的 DOM 节点数量，虚拟滚动只渲染可视区加少量缓冲。通用做法有四个环节：容器固定高度并监听滚动位置；根据滚动偏移与行高算出起始索引与结束索引；只渲染这段区间，并用一个占位元素撑起总高度；再通过 transform 或绝对定位把渲染出来的行推到正确的视觉位置。固定行高是这套算法的前提，行高随内容变化就必须维护已测量高度的缓存，成本与出错率都会上升。不依赖特定组件库也能做对，关键是三件事：滚动事件做节流或合并到帧、总高度与缓冲条数显式配置、被回收复用的行正好是 v-memo 的适用场景。

列表模板里最容易积累的是隐形计算。第一类是在 v-for 的表达式里做过滤、排序或查找：v-for="item in list.filter(...)" 每次渲染都重新执行，条目上千就是一笔完全没必要的重复工作，挪进 computed 后依赖不变就直接命中缓存。这也是计算属性缓存与函数调用式渲染的区别——methods 里的函数写进模板表达式没有缓存，每次渲染都调用；computed 是有依赖追踪的惰性求值，只在依赖变化后算一次。第二类是在列表项上做格式化与单位换算，能在数据进入时算好就提前算，别把每次渲染都变成一次数据清洗。第三类是把 v-if 与 v-for 写在同一元素上：Vue 3 中同一元素上 v-if 的优先级高于 v-for，此时 v-if 访问不到循环变量，通常直接报错；正确做法是用 computed 先过滤出要展示的集合，或在外层包一个 <template> 承载其中一个指令，前者还能避免为了隐藏若干项而渲染全部节点。

如果只是想限制显示数量，分页或加载更多永远比一次性渲染几万节点可靠；虚拟化是为用户确实要连续浏览大量条目准备的，不是为接口一次返回太多兜底的。

写法层：派生、观察与条件渲染的代价

先给一句划界：Composition API 的组织方式另文已有，这里只比较几种写法在运行时的成本差别。

派生值用 computed，副作用用 watch，需要参数或明确要求每次执行才用方法——这条规则的依据是缓存与触发次数。computed 惰性求值、依赖不变不重算、结果被下游共享；模板里的行内表达式每次渲染都重新执行一遍，也无法被别的消费者复用；methods 写进模板同样没有缓存。当表达式出现在 v-for 里，成本还要乘上条目数，这是最常见的”看着没问题、数据一多就崩”。

watch 的成本不在回调本身，而在触发时机与订阅范围。flush 默认在组件更新前，改成 post 会等到更新之后再跑，适合依赖最终 DOM 的读取；sync 让回调在写入的同一刻同步执行，等于把批量合并绕过去了——一次写入触发一轮完整更新，连续写入不再共享同一批次，除非必须立刻读到新值，否则不要用。深层观察会为遍历到的每一层建立依赖，只关心两个字段就改成观察这两个字段的选择器。watchEffect 的依赖是运行时收集的，函数体里多读一个无关字段就多订阅一个字段，这是它便利的代价。卸载时的清理要显式做，onCleanup 里漏掉一个定时器或事件监听，就留下一份持续的隐形开销。

条件渲染的两个指令成本结构不同。v-if 是真正的条件渲染，切换时子树被挂载或卸载，组件实例创建或销毁、DOM 节点增删、生命周期重新走一遍；v-show 只是改变样式，节点始终存在，切换成本几乎恒定。因此频繁来回切换且内容较重的区域用 v-show；初始不展示且渲染昂贵的区域用 v-if；一次会话中只显示一次的提示类内容也用 v-if，连初始渲染都省掉。反过来把只在极端条件下出现的重内容写成 v-show，等于每次进页面都白渲染一次。

nextTick 常被误当作性能工具。它只是让你拿到批次执行完之后的时机，因为更新是异步批量的、DOM 在那之前还是旧的；正确用途是紧接着读取或操作刚更新过的 DOM，比如聚焦、测量、滚动。两种用法是错的：用 setTimeout 或空 nextTick 等一等以规避时序问题，不缩短任何耗时，只是把缺陷延后；在 nextTick 回调里继续写状态，会启动新一轮批次，让一次交互变成两轮渲染。真要合并写入，就在同一段同步代码里把状态写完。

产物层：让首屏只下载它需要的东西

分包的第一来源是动态 import：路由组件与按需拉起的内容天然成为独立块，浏览器只在需要时请求。构建阶段还能对第三方依赖做进一步分组，把体积大、变化频率低的库单独成块，让业务代码更新时用户不必重新下载它们——这是缓存命中率意义上的收益，不是变小。要警惕反向操作：切得过细会产生大量小请求，模块图初始化与串行等待会吃掉一部分收益，粒度应参考真实访问路径而不是文件数量。依赖预构建处理的是开发期的格式转换与请求瀑布，它属于构建链路调优，专篇另有论述。

组件库的引入方式是体积问题的常见来源。整包引入会绕过 Tree-shaking，把没用的组件、指令、样式一起打进产物。正确方向是按需引入：只导入实际使用的组件，并确认样式同样按需，否则只是把 JS 的浪费换成 CSS 的浪费。其他高频的隐性全量引入包括整个图标库、整个时间处理库、整个工具库只用到一两个函数，或在共享模块里为了一个小图导入整个图表库。这些不必读源码，构建后的模块分析报告里就能看到排名。

CSS 的体积同样要归因：全局基础样式是否有必要覆盖全部页面、组件级作用域样式是否会因大量重复规则膨胀；动画与阴影这类成本主要落在渲染线程而不是体积上。

最后一类是看起来像优化的优化。defineOptions、产物里为 <script setup> 生成的 _export_sfc 辅助调用之类不影响运行时性能的东西，为了性能去改写或规避它们只是噪音。判断任何配置改动是否值得，标准都是同一条：能不能指出它改变了哪一段成本。

SSR 与 Nuxt：多出来的一本账

服务端渲染把首屏内容的成本从浏览器挪到服务器，同时新增三笔开销。第一笔是状态序列化体积：服务端把数据写进 HTML 交给客户端恢复，列表数据、字典、鉴权信息很容易整包塞进去，而多出来的 HTML 要下载、解析与恢复三项成本一起付；原则是只放页面真正需要的数据，展示用的派生结果在客户端重算。第二笔是水合时间：客户端要遍历组件树把事件与实例接上真实 DOM，节点数量直接决定它有多贵，整页一次性水合常常比纯客户端渲染更慢；可行方向是关键区域先完成、其余延后，把非关键内容改成异步组件或客户端渲染，或用 Suspense 边界把水合拆成多段。第三笔是水合后的二次更新浪费：水合期间服务端数据又被客户端请求覆盖，或初始状态与服务端输出不一致触发额外渲染，等于白做两轮。水合阶段的卡顿常常来自树上绑定的大量事件与初始化状态，而不是网络。

观测与回归防护

一次性的优化容易，守住成果难。Vue 项目的性能回归有几种明确形态：新增一次深层响应式包裹，把不需要驱动视图的大对象塞进 reactive；在渲染路径上重新产生组件类型；在 v-for 表达式里做过滤排序；组件库里新增一次全量引入。这四种形态在评审里可识别、在产物与渲染计数里可测量，值得写进检查清单。

落地分两层。构建侧把关键块大小与首屏资源量做阈值告警，超出的合入要显式说明理由；运行侧把组件渲染次数、批次耗时与长任务数量采样上报，而不是全量上报。阈值没有普适标准，本文数值都是团队约定示例，重要的是同一项目内口径固定、随版本记录趋势，让”变差了”成为能被自动发现的问题。浏览器指标的统一口径不在本文展开，Vue 项目还要补一条：把长任务次数与峰值耗时绑定到具体交互路径，比盯一个综合分数更有指导意义。

小结

Vue 3 的性能优化有一条主线：让编译器与运行时掌握的信息恰好等于真实变化的信息。编译层的静态提升、补丁标记与块级比较已经把能自动省的部分省掉了，你要做的是别让模板破坏这些条件；响应式层围绕缩小被代理与被追踪的数据范围；组件层看重渲染半径与加载时机；列表层看 key 的正确性与同时存在的节点数；产物层只解决下载与解析。各层手段互不替代，用错层就看不到收益。顺序永远一样：测量、建立基线、改一处、复测，再把它写成回归防护；做不到这一点的优化，只是换了个写法。
