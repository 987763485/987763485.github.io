前端微服务与模块联邦

组件库想给十条业务线共用一套按钮，发版之后每条业务都得重新构建才能用上，这件事烦了很多人。模块联邦把复用的单位从”发布时的源码”换成了”运行时的模块”：远程产物在浏览器里被现场加载、现场消费，提供方升级一次，消费方下次打开就是新的。本文只谈这一种机制的落地细节，微前端整体怎么拆分另有一文。

模块联邦要解决的问题

传统复用走的是 npm 包：把公共组件抽成包、发版本、业务装包，构建时被打进各自的 bundle。这条链路的痛点不在代码组织，而在”升级”这个动作上——提供方发布了 1.2.0，消费方那边有八个人不会立刻重新构建，线上于是同时跑着三四个版本，一个安全修复要等完整的一轮构建发布才能生效。复用的粒度也停在源码层：能共享的是包，不是正在运行的那份实例。

模块联邦换掉的正是这个单位。一个已经构建好的产物可以对外声明”我允许别人直接拿”（exposes），另一个产物声明”我要从别人那里拿”（remotes），两边在运行时才第一次相遇。提供方替换远程产物，消费方不需要重新构建自己就能拿到新版本。代价是共享这件事变成了一等公民：shared 里声明的依赖（React、Vue、路由库）必须由两边协商出用哪一份，协商不好就出双实例故障。

webpack 时代偏构建配置的那套讨论与本文是两条线，这里只谈运行时的这一半。

核心概念：容器、exposes、remotes 与 shared

每个启用联邦的产物都会额外产出一个容器（container）：挂在 window 上的入口对象，暴露 init 与 get 两个方法。消费方加载远程的 remoteEntry.js，调用 get('./Button') 拿到一个异步函数，执行后才得到真正的模块。filename 决定这个入口文件叫什么，library 决定容器挂在哪个全局变量名下，两者合起来构成远程方在 URL 上的坐标。

name 是容器对象的全局名，ui_kit@https://... 冒号前那一段必须和它完全一致，写错就找不到入口。exposes 的键是对外契约，值是实现路径：路径随时能改，键名不能轻易改，改了就是破坏性变更。消费方拿到模块后用 <React.lazy> 包一层即可：

版本协商：shared 里最容易出事的一段

shared 的几个字段各有各的脾气。version 是产物自己被打进去的依赖版本，用来回答”我这儿有什么”；requiredVersion 是消费方对共享依赖提出的版本范围，写成 semver 字符串；singleton: true 要求整个运行时里这类依赖只留一份，谁先加载谁提供；strictVersion: true 要求实际拿到的那份必须落在 requiredVersion 范围内，否则直接抛错而不是悄悄降级。

冲突的表现比配置本身更好认。React 项目里最常见的样子是 Invalid hook call 那句报错，紧跟一句版本不一致的提示——两份 React 各自维护自己的 dispatcher，hooks 在 A 的渲染上下文里读到了 B 的当前实例。路由库双实例更隐蔽：两个 router 各自订阅 history，一次 URL 变化触发两次渲染，或者页签之间跳不回去。Vue 那边表现为插件注册失效、provide 跨不过去，因为两套运行时互不认识。

排查顺序建议固定下来：先看容器加载顺序，谁先完成 init 谁就决定了共享依赖拿到的版本；再核对两边 requiredVersion 与 singleton 的组合是否自相矛盾；实在协调不了，就关掉 singleton 接受双实例，同时把有状态的那部分依赖收回宿主一侧，只让远程消费无状态组件。

运行时加载与部署

远程入口的解析发生在运行时：宿主 bundle 里只留下远程地址字符串，页面执行到那行动态 import 时才插入 script 标签，等容器挂到全局对象上再取模块。好处是远程可以按需延后加载，坏处是网络抖动会直接进入渲染路径。

地址由 remotes 的字符串拼出，域名和路径默认在构建期就被写死，多环境于是成了麻烦事。稳妥些的做法是把 remote 列表从构建配置里拿出来，启动时读一份 JSON 或由服务端注入到页面上，再喂给容器；如果一定要固化在产物里，就用环境变量替换域名。这里 publicPath: 'auto' 很关键——远程自己的 chunk 是相对 remoteEntry.js 解析的，一旦继承宿主的 publicPath，就会跨域名去要文件而 404。

产物指纹和长期缓存要分开对待：remoteEntry.js 这个名字必须保持稳定，因为消费方手里只有它；它内部引用的 chunk 才可以带 contenthash。所以 CDN 上入口文件的缓存要短、回源要可靠，带 hash 的 chunk 可以放心设成长期 immutable。所谓版本切换，本质就是把地址指向另一个目录；回滚也只是把地址指回去，这条杠杆很快，但跳过消费方构建这件事本身也意味着少了一道关卡。

还有一处容易被漏：远程加载失败要有看得见的降级。动态 import 被拒绝后，如果外面既没有 Suspense 也没有错误边界，整棵组件树会跟着崩；合理做法是给远程组件包一层占位与有限重试，并把失败原因上报到监控，而不是只在控制台留一行警告。

手写的问题在于要靠人维持同步：提供方改了 props，宿主的声明还是旧的，直到运行时才炸。稍好一些的办法是让提供方在构建后从源码生成一份声明文件，连同 remoteEntry.js 一起发布，宿主拉下来放进 include。生成链路必须覆盖 exposes 的每一个键，漏一个就等于对外宣告这个模块没有类型。

本地联调远程模块靠的是把 remote 地址临时指向提供方的 dev server，写成 ui_kit@http://localhost:3001/remoteEntry.js，提供方起本地服务，改代码即时生效。此时提供方必须允许跨域，共享依赖版本也要和宿主对齐，否则一进页面就撞上前面说的双实例。调试时 source map 的归属容易看错：断点落在远程模块里，堆栈显示的是提供方的源文件路径，报错指向的 map 也可能来自另一个域名，控制台那行文件名并不代表它属于当前工程。

样式与隔离

联邦把样式从构建期推到了运行时，加载顺序不再完全由入口的 import 顺序决定：远程组件的 CSS 可能晚于宿主的全局重置到达，同名选择器的胜负就变了。公共重置样式若放进 shared，两边各自注入会产生重复规则；若不共享，宿主改了按钮内边距而远程没收到，视觉立刻错位。

隔离程度建议做成团队约定，而不是指望自动机制。一档是远程只输出组件内部的 scoped 样式，比如 CSS Modules 或带前缀的 BEM 类名，完全不碰标签选择器和全局变量；另一档是允许远程消费宿主下发的设计 token，由宿主在根元素上维护一组 CSS 自定义属性，主题切换只改变量。第二档好用但脆弱：token 名一旦变动，所有远程产物得跟着发一轮，而且这种破坏是静默的——页面不报错，只是颜色不对。

组件库自身的样式最容易重复注入。如果远程已经把按钮样式带进来，宿主就不要再装一份同名 npm 包，否则同一套类名对应两种规则。这类冲突肉眼难查，最好在流水线里比对两边产物中重复的选择器。

编排与治理

远程列表不该散落在各业务的构建配置里。常见的收敛做法是维护一份模块注册表：由平台侧发布一段 JSON，列出每个远程的名字、入口地址、可用模块键、负责团队和当前版本，宿主启动时读它并据此生成 remotes。这样”哪些模块可用”从代码问题变成数据问题，权限、审批和下线都能挂在注册表上。至于路由接管、公共外壳这些做法，另有一文，这里不重复。

灰度几乎是注册表带来的最大红利：先给 5% 的用户返回指向新目录的地址，看一轮指标再全量。杠杆大，风险也同样集中——一次错误发布不再只影响一个应用，而是所有拉这个远程的宿主同时出问题；消费方因为没有重新构建，连”回滚自己的 bundle”都做不到，只能等平台把地址指回去。所以远程产物要保留历史目录、禁止覆盖同名文件，发布脚本最好加一条校验：新版本必须与当前线上版本共享同一份 React 主版本。

契约变更建议走”加而不改”。exposes 的键和组件 props 一旦发布就当公开 API 看待，要动就先加新键，把旧的标为废弃并给出保留期限；破坏性变更必须和所有已知消费方一起排期。监控至少看三类指标：远程入口加载失败率、入口加载耗时、共享依赖协商失败的报错量。以失败率为例，正常应压在 1% 以下（示意值），若某次灰度后跳到 3%（示意值）而页面本身没有报错，多半是部分用户命中的 CDN 缓存还没刷新。

局限与不适合的场景

模块联邦常被顺口叫作”前端的微服务”，但它没有免费的那部分：后端服务能独立部署、独立扩缩、语言互不相干；远程模块与宿主共享同一个运行时、同一份 React、同一个页面进程，一个远程抛出的未捕获错误可以把宿主一起带下去。拆分带来的独立性远低于名字给人的期待，治理成本却是真的。

时序问题也躲不掉。首屏要展示远程内容，就得等入口文件下载、执行、协商完，这段耗时全部落在用户眼前；提前 preload 能缓解，代价是拉一堆可能用不到的代码。服务端渲染更棘手：渲染阶段拿不到浏览器运行时，通常要为远程模块准备一份可在 Node 侧解析的替代实现，或把相关区块降级成客户端渲染。

安全边界值得单独说一句。把远程地址配进宿主，等于授权那个 URL 背后的产物在你的页面里以你的权限执行代码——它能读 cookie、调接口、改 DOM。所以域名必须收敛到受控 CDN 并强制 HTTPS，产物发布要有来源审计或校验手段；任何”能写这个目录”的人，实际上都能改你的前端。

工具绑定是最现实的门槛。模块联邦在 2024 年的位置仍然是 webpack 5 的一项能力，其他工具链上有各自的兼容实现与社区方案，生态还在跟进，但配置字段和行为并不完全等价，全量推广前建议先跑通一个最小的远程模块。至于值不值得用，标准其实朴素：如果共享组件只有一个团队在用、升级靠重新构建完全来得及、依赖版本能靠人工对齐，那引入联邦只是把复杂度换成了一张流程图——小团队大概率不划算。

小结

模块联邦要解决的问题比”微前端”这个标签窄，也具体得多：它把复用单位从构建期的源码包换成运行时的模块，让提供方升级不必惊动所有消费方的构建。代价集中在三处——shared 的版本协商、加载链路直接进入用户视野、远程代码拿到宿主的执行权限。

落地顺序我建议这样：先只共享一个低风险组件，把 singleton 与 requiredVersion 的组合调通，确认不再出现多实例报错；再把 remote 地址从构建配置挪进模块注册表，拿到灰度和回滚能力；最后补上类型声明的生成链路与加载失败率监控，把契约变更写进发布流程。走完这三步仍然觉得顺手，再考虑把核心页面交给远程模块；如果其中任何一步只能靠某个人记住规则来维持，那就先停在这里。
