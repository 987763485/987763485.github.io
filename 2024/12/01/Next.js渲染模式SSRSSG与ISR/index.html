Next.js 渲染模式：SSR、SSG 与 ISR

同样一个商品详情页，可以做到毫秒级首字节，也可以做到每次请求都反映最新库存。差别不在业务代码，而在渲染发生的位置与数据被确定的时机。本文把 Next.js 里几种主流渲染模式放到同一条谱系上，梳理 Pages Router 与 App Router 在数据获取上的差异，拆解增量静态再生成的粒度与失效路径，并给出一张可以直接照着做取舍的选型矩阵。文中的性能相关数字均为示意值，实际要以自身业务压测为准。

渲染位置与数据时机的谱系

讨论渲染模式时，“在服务器渲染还是浏览器渲染”这个二分法过于粗糙，真正有解释力的是两个正交的问题：数据在什么时刻被确定，由哪个进程来确定。把这两个问题画在一张图上，几种模式的位置就很清楚了。

flowchart TD
  A[一次访问请求] --> B{数据何时确定}
  B -->|构建时| C[SSG 静态生成]
  B -->|构建后按周期| D[ISR 增量再生成]
  B -->|请求时| E[SSR 服务端渲染]
  B -->|浏览器运行后| F[CSR 客户端渲染]
  C --> G[产物是 HTML 文件]
  D --> G
  E --> H[产物是每次响应]
  F --> I[产物是首屏骨架加数据]

SSG（Static Site Generation）把决策提前到 next build 那一刻：组件被渲染、HTML 被写成文件，后续访问只是把这份文件交给请求者。收益非常直接——没有数据库查询、没有服务端计算，内容可被 CDN 缓存在离用户最近的节点，首字节时间几乎等于网络往返。代价是内容从生成到消亡这段时间里是冻结的。

ISR（Incremental Static Regeneration）保留了 SSG 的产物形态，但给它加了过期时间。首个请求命中旧文件，响应照常返回；同时后台触发一次重新生成，新版本落盘后被后续请求使用。用户始终拿到可以直接服务的内容，从不会阻塞在渲染上。这正是 stale-while-revalidate 语义在页面层的体现：先给旧的，后台换新的。

SSR（Server-Side Rendering）把决策推迟到请求发生时，每个请求执行一次服务端渲染。它换来强实时性与按请求个性化（登录态、地区、A/B 分组），代价是每次响应都承担服务端计算与上游延迟，缓存友好度显著下降。

CSR 把决策彻底交给浏览器：服务端只返回一个几乎空的壳，真正的取数与渲染发生在 hydration 之后。壳可静态缓存因此首字节很快，但可交互时间被推后，且首屏内容对搜索引擎不友好——这个问题在现代爬虫实践中被部分缓解，不能当成已解决。

App Router 引入了第三个维度：组件运行在哪个环境。Server Components 在服务端执行，代码不进入客户端 bundle；Client Components 才需要 hydration。RSC（React Server Components）不是第四种渲染模式，而是组件运行位置与序列化协议，可与静态生成、请求时渲染、流式输出组合。PPR（Partial Prerendering）在本文写作时仍是实验特性，目标是让同一页面里静态壳与动态内容共存：静态部分构建期落盘，动态部分请求期流式补齐，可用边界以官方文档为准。判断模式时我习惯问三个问题：数据多久变一次、能否允许短暂陈旧、内容是否对所有访客相同。

Pages Router 与 App Router 的数据获取差异

Pages Router 的数据获取是“约定式的钩子”：页面导出一个特殊命名的异步函数，框架在正确的时机调用它，把返回值作为 props 注入页面。三个钩子决定了页面的生命周期形态。

getServerSideProps 每个请求执行一次，返回 { props }、{ redirect } 或 { notFound } 三种形态之一。它只能拿到浏览器请求携带的信息，因此鉴权逻辑写在里面是安全的；但它的返回值必须是可 JSON 序列化的，不能带 Class 实例。

getStaticProps 在构建期执行，导出时多一个可选的 revalidate 秒数，就把它从纯 SSG 变成 ISR。getStaticPaths 则回答“构建期为哪些动态路径生成页面”：

fallback 的三种取值容易被误用。false 表示未列出的路径直接 404，全站路径必须在构建期穷举完毕。true 表示未列出的路径先返回空壳（router.isFallback() 为真），客户端接管后再拉数据，页面在首次访问后由后台生成——构建快，但首次访问体验差且首屏 HTML 不含内容。'blocking' 是折中：服务端阻塞等待生成完成后返回完整 HTML 并缓存这份结果。新项目里 true 已很少用，多数场景 blocking 更合适。

App Router 换了一套思路：数据获取不再是页面级钩子，而是组件内部的普通 await。

控制渲染形态的不再是“用哪个钩子”，而是 fetch 缓存选项、dynamic 段与路由是否触达请求期数据。export const dynamic 可取 force-static、force-dynamic、auto、error；export const revalidate 给出页面级默认重验证周期；fetchCache 与 runtime 进一步细化。一个关键因果是：只要渲染路径读取了 cookies()、headers()、searchParams 或请求体，这段 UI 必然进入请求期渲染、无法静态化——这是很多“以为会走 SSG，结果每次都在跑函数”的根因。

两套 Router 的差异还体现在数据一致性上：Pages Router 的 props 是一次成型的整块快照，App Router 允许一棵树里混合静态段与动态段、页面分批抵达浏览器，因此缓存与失效的心智模型要从“一份 HTML 文件”升级为“若干段可独立失效的载荷”。

ISR 的粒度、按需失效与语义细节

revalidate 表面上只是一个数字，实际有两层完全不同的含义，把它们混为一谈是很多线上问题的起点。

页面级重验证（Pages Router 中 getStaticProps 返回的 revalidate，App Router 中的 export const revalidate）控制这个路由段最多陈旧多少秒：到期后的第一个请求触发后台再生成，期间其他请求仍拿到旧版本。

数据级重验证（App Router 中单个 fetch 上的 next: { revalidate: n }）控制这条上游数据的缓存时长，让一次渲染能混合不同新鲜度——标题缓存一天、价格缓存一分钟、库存缓存五秒。页面是否静态由这些选项共同决定，排查时不要只盯着页面导出。

还有一个反直觉的事实：ISR 的失效以页面或路由段为单位呈现给请求者，而不是以字段为单位。数据级缓存到期不等于用户能看到新内容，除非页面本身也重新渲染。常见做法是把页面级 revalidate 取所有数据段中最短的那个值，或者干脆把强实时的部分拆成 Client Component 在挂载后单独请求。

按需失效（on-demand revalidation）在本文写作时仍属实验能力，官方文档中以 unstable_revalidate 一类命名出现，具体函数名、参数结构与支持范围随版本变化，请以所用版本的官方文档为准，不要在未核对文档时照抄字段。它的价值是把失效时机从“时间到期”变成“事件发生”：CMS 发布、商品改价、文章被编辑，Webhook 打到一个小接口，服务端按路径或标签把对应静态资源标记为过期，下一个请求即拿到新版本。

自建 Node 服务上，按需失效依赖 Next.js 维护的缓存存储；多实例水平扩展时，一个实例上的失效不会自动传播到其他实例的内存缓存，需要额外机制对齐，平台托管通常内置了这层广播，自建部署要显式核对。构建后失效（invalidate after build）指产物已分发到边缘后让特定路径的旧内容立即失效：它是“丢掉旧的、下次重建”，而按需失效更接近“立刻重建”，前者对上游压力小，代价是首个请求要等待生成。

最后把 stale-while-revalidate 讲透，它有三个必须同时成立的性质：请求不会被再生成阻塞；返回的是已过期旧内容而不是骨架屏；同一时刻对同一 key 的并发再生成会被合并。ISR 承诺的是有界陈旧而不是实时——若业务无法容忍任何旧数据（比如支付金额），它就是错误选择。

缓存层次与失效路径

一次 Next.js 请求从浏览器打到应用，中间穿过至少四层缓存，每层的键、生命周期与失效方式都不同。

最外层是 CDN 与边缘缓存。纯静态产物（SSG 页面、JS、CSS、图片资源）天然可被 CDN 长缓存，键是 URL；带 fingerprint 的构建资源用 immutable 长期缓存是标准做法。HTML 页面要谨慎：一旦在 CDN 上给页面设了长 max-age，ISR 与 SSR 都会失效，因为请求根本到不了应用。应用侧逻辑完全正确、用户却永远看到旧页面，属于典型的配置性事故。

第二层是构建产物层。next build 生成的 .next 目录里，静态页面以文件形式存在，动态页面对应可执行的服务端模块。这一层没有过期概念，只有重新部署，因此把内容更新寄托在重新构建上，等于把发布频率当成 CMS 的保存频率，通常不可持续。

第三层是服务端数据缓存，App Router 里表现为 fetch 缓存与不透明缓存。它缓存的是上游响应及其派生的渲染段而不是最终 HTML，因此对“多个页面共享同一数据”的场景命中率很高。要警惕它的作用域：多实例部署下若缓存是进程内的，实例之间彼此独立，同一份数据会被重复拉取、陈旧程度也可能不一致。本文写作时 Next.js 15 对 fetch 的默认缓存行为做了调整，具体默认值与迁移注意事项请在升级前逐条核对官方升级指南，不要按记忆推断。

第四层是客户端 Router Cache。它会缓存访问过的路由段载荷，使浏览器前进后退时不必重新请求，代价是路由段可能在客户端停留而与服务器不一致。它的行为在版本间被反复调整，是升级 Next 时最容易被静默改变行为的部分。同类的还有完整路由缓存（Full Route Cache），它承载构建期与 ISR 生成的静态输出；页面是否进入这一层，取决于渲染路径是否含请求期数据。

把这几层串起来，两类常见故障就浮现了。一类是集中到期造成的请求放大：高频页面的数据级缓存同时过期，后台再生成一起打向数据库，形成周期性尖峰。缓解手段是把不同页面的 revalidate 错开取值、给上游加一层真正的分布式缓存、或改用事件驱动失效。另一类是时间戳不一致：页面 HTML 来自较旧的生成，客户端组件挂载后拿到最新数据，同一屏里出现“更新时间晚于正文版本”的矛盾。这往往不是 bug 而是混合渲染的必然结果，需要用产品展示规则来收敛。

预览模式与草稿内容是这条链路的特殊分支。它的本质是在浏览器 Cookie 里打标记，让携带标记的请求绕过静态缓存走请求时渲染，从而在编辑器里看到未发布内容。共享 CDN 缓存不能接受同一个 URL 两种响应，因此预览请求必然不能被共享缓存，代价是额外响应头与略高延迟。发布动作应同时触发一次按需失效，否则预览里看到的新内容仍会在正式链接上陈旧一段时间。

流式渲染、Suspense 与各自的稳定度

传统 SSR 的输出是原子的：服务端把整棵树的 HTML 攒完才发首字节，页面里最慢的那个查询决定了用户看到任何东西的时刻。流式渲染改变了这个契约——服务端先发已准备好的部分，浏览器立刻开始绘制，剩下的在同一条连接里陆续抵达。

在 App Router 里这条路径由几个部件组合而成。loading.tsx 为一个路由段提供即时反馈内容，它在框架层面与 Suspense 边界配合，使用户导航到新路由时先看到占位而不是白屏。<Suspense fallback={...}> 把粒度下沉到组件级：被包裹的异步组件在等待数据时展示 fallback，数据就绪后服务端把真实 HTML 以流的方式推送，客户端脚本把它替换进 DOM。

这个结构值得反复体会：外层是同步的静态段，内层是异步的动态段。当动态段是请求期数据时，整页不再可能被完整静态化，但静态段的 HTML 依然可以早早在字节流中出现。PPR 想要的正是把这种“静态部分落盘、动态部分请求期补齐”提前到构建期产物中，它在本文写作时仍属于实验特性，不应作为生产架构的前提。

关于稳定度要给一句诚实的划分：App Router 的路由、布局、Server Components、loading.tsx 与 Suspense 流式输出在主版本线里属于稳定能力；按需重验证与 PPR 属实验范围（命名带 unstable 前缀即为此信号）；Turbopack 在生产构建中的覆盖度仍在扩展，本文写作时把它视为开发模式可用的构建器更稳妥，而不是已经全面替代 webpack。React 19 在本文写作时仍处于 RC 阶段、正式版尚未发布，涉及它的行为差异请以 RC 文档自测，不要按已发布版本写进架构假设。

流式还有个实操问题：响应已经开始输出后再出错，无法返回错误状态码，Next.js 只能在客户端侧用错误边界兜住，监控上要留意 HTTP 200 却包含错误 UI 的响应。流式也与压缩、反向代理的缓冲配置相互作用——若代理把响应整体缓冲到结束才转发，流式收益直接归零，而这不会报错。

动态路由与站点生成规模

内容型站点的典型形态是动态路由：文章以 slug 为参数，商品以 id 为参数。getStaticPaths（Pages）与 generateStaticParams（App）负责回答“构建期为哪些参数组合生成页面”。

第一个决策是穷举还是采样。全站穷举意味着构建时间随内容量线性增长，一万篇文章与一百万篇文章的构建成本差别巨大（这只是量级示意，并非实测数据），而且每次部署都要重来。工程上更常见的做法是只预生成长尾头部——最近发布的、流量最高的、被站内链接指向的那些，其余交给按需生成与到期重验证覆盖。App Router 中对应的能力是 dynamicParams：保持默认时未预生成的路径在首次请求被渲染并缓存；设为 false 则直接 404。它与 fallback 语义同源，但控制点从“返回什么壳”变成了“允不允许生成”。

分页是第二个难点。列表页天然带 ?page=n 这类请求期输入，一旦读取搜索参数就退出静态输出。可行处理有三种：把分页做成路径段（/blog/2）从而可被参数枚举预生成；列表页整体转为请求时渲染并配短缓存；首屏静态化、翻页由客户端向接口发请求。

大规模站点最终都会遇到构建时间治理，可用手段按性价比排序大致是：减少预生成数量，把长尾交给按需生成；把逐页 N 次查询改成批量取回后在生成函数内共享；在生成函数里加一层跨页缓存，避免每个页面重复拉取同一份导航或站点配置；把生成过程按内容分区拆成多个构建任务并行推进；把不参与内容的重活（图片处理、外链检查）挪出构建关键路径。这些不是框架特性而是流水线工程。

ISR 与后台任务的配合是这套治理里最优雅的一环。后台任务负责昂贵产物（生成摘要、构建搜索索引、渲染分享图），完成后调用按需失效或把结果写入页面读取的存储；页面保持静态形态，只在数据真正就绪后被重新生成。昂贵计算由此离开请求路径，用户永远不需要为它等待。

内容型站点（文档、博客、营销落地页）首选 SSG，把长尾交给按需生成。理由很直接：这类内容更新频率远低于访问频率，用一次构建换千万次零成本命中是划算的；同时它们对搜索索引与分享预览有硬需求，静态 HTML 是唯一稳妥的形态。若编辑每天多次发布且要求保存即上线，用 ISR 加事件驱动失效，而不是把 revalidate 调小。

电商需要混合。商品详情、类目列表、政策页适合 ISR：描述与价格允许分钟级陈旧，访问高度集中，缓存收益巨大。购物车、结算、库存临界提示、优惠券试算必须走请求时渲染或客户端请求：这些内容每个访客都不同，一旦静态化就是数据串号事故。搜索列表页通常走请求时渲染加短缓存。

后台管理系统首选 CSR（或 SSR 但禁用共享缓存）。决定性因素不是性能而是没有可缓存的东西：每个用户看到的数据不同，首屏之后是长时间交互，SEO 完全不相关。用 App Router 时可以把这类路由整体做成 Client Component 加接口请求，结构简单、错误处理清晰；把 SSR 强加上去只会增加服务端渲染成本与 hydration 风险。

SaaS 官网是典型的营销静态、应用动态结构：市场页、定价页、帮助中心走 SSG 或 ISR，登录后的产品界面走独立路径的客户端渲染。两者放进同一个项目没问题，但要用路由段划分清缓存期望，别让门户的实时性要求污染营销页的缓存策略。

常见坑与排查

服务端模块级状态被复用。 模块顶层声明的变量在开发时随热更新重建，在生产的服务端进程里却长期存在，多个请求共享同一份。于是出现“第一个请求正常、后面请求数据越来越多”这种诡异现象，通常就是一个没被清理的数组或 Map。真正需要跨请求状态时应显式使用外部存储，并把它当作有并发访问的共享资源对待。

fetch 缓存造成数据陈旧。 这是最经典的一类，表现为部署后页面里的数字停留在构建那一刻，或多实例部署下不同实例返回不同版本。排查顺序建议固定：先看响应头与 HTML 内容，判断走的是静态产物还是请求时渲染；再看该数据的 fetch 选项是否带了重验证或 no-store；最后确认是否有边缘或代理层缓存在替你回答请求。

中间件与重定向的意外组合。 中间件运行在渲染之前，matcher 按路径匹配，很容易误伤静态资源、API 路由与预览接口。请求期重定向与静态产物也有天然张力：被静态化的页面里的 redirect 会被固化进产物，而基于 Cookie 或 Header 的重定向无法出现在静态输出里，于是看起来配置正确的规则在部分路径上静默失效。

图片优化与外部域。 next/image 的远程域名需要显式白名单，缺失时表现为图片直接 404 或退化为原图。图片优化接口本身是服务端动态端点，若上游域名响应慢或返回非预期类型，会拖慢整个端点，需要按服务而非静态资源对待。

环境变量泄漏到客户端。 约束只有前缀这一条：以 NEXT_PUBLIC_ 开头的变量会在构建期被内联进浏览器 bundle，任何人可在源码里读到，因此密钥必须没有这个前缀。反向的坑是在 Client Component 里 import 了含敏感逻辑的模块，代码照样进了浏览器。

hydration 不匹配。 服务端 HTML 与客户端首次渲染结果不一致，React 会回退到整棵子树重新渲染，控制台出现 hydrate 告警。常见诱因是时间格式化（服务端 UTC、浏览器本地时区）、Math.random、依赖 window 的分支、浏览器插件改写 DOM，以及静态段与动态段各自取数造成的同一接口在一次生命周期里被打两次。定位办法是把可疑表达式挪到仅客户端路径（在 effect 或事件里赋值）或改用显式的挂载后状态，不要用 suppressHydrationWarning 掩盖结构性不一致。

部署形态决定了模式能不能用

渲染模式不是纯前端决策，它与你能提供的运行时强绑定，这一点要在选型阶段确认，否则会在上线前才发现“设计好的 ISR 落不了地”。

最完整的是 Node 服务器形态：next start 或自建进程承载 SSR、ISR 的后台再生成、按需失效、图片优化与中间件。代价是常驻进程、并发与内存治理、多实例缓存一致性。

standalone 输出把服务端运行所需文件收敛成一个自包含目录，配合极小的基础镜像就能得到体积可控的容器，是自建部署最常见的落点。但它只解决打包，不解决多实例下的数据缓存与静态产物共享：默认实现里每个容器持有自己的缓存视图，水平扩展时同一 URL 可能返回不同陈旧程度的内容。要对齐，需要共享存储、会话粘连或改用事件驱动失效，这是架构层面的决策。

静态导出（output: 'export'）产出纯 HTML 与资源，可以放到任何对象存储加 CDN 上，成本与运维几乎为零。但必须清楚换来了什么：没有 Node 服务、没有请求期渲染、没有中间件、没有按需失效，ISR 在这条路径上根本不可用，因为没有进程去执行再生成。它只适合内容更新可以容忍“重新构建并上传”的场景。很多团队在这里翻车：先按 ISR 设计好更新流程，最后发现部署形态不支持，只能整体回退。

Edge runtime 提供靠近用户的轻量执行环境，冷启动低、分布广，适合按地域分流、鉴权、A/B 与个性化片段。约束来自运行时本身：并非所有 Node 能力都在（文件系统、部分原生依赖、需要连接池的数据库客户端通常不合适），执行时长与体积也有限制。务实分工是把路由段与鉴权类逻辑放 Edge，重数据访问与长计算的渲染留在 Node。同时要注意 Server Components 的运行环境与路由的 runtime 设置互相影响——一个静态化的路由若含只能在 Node 下执行的代码，构建期就会报错，这属于把环境约束提前暴露出来的良性失败。

小结

本文把 Next.js 的渲染模式还原成两个正交问题：数据何时确定、由谁确定。SSG 把时机推到构建期，换来最好的 TTFB 与缓存友好度；ISR 在静态产物上叠加有界陈旧与后台再生成，用 stale-while-revalidate 语义保证请求不被阻塞；SSR 把时机推到请求期，用计算换实时与个性化；CSR 把时机交给浏览器，适合无缓存价值、重交互的界面；RSC 是组件运行位置的维度，与上述模式正交，PPR 仍是实验特性。

数据获取的形态在两套 Router 之间发生了迁移：Pages Router 用 getStaticProps、getServerSideProps、getStaticPaths 三个钩子加 fallback 的三种取值定义页面生命周期；App Router 用组件内 await、fetch 选项、generateStaticParams 与 dynamic、revalidate 段共同决定渲染形态，其中“渲染路径触达请求期数据即退出静态”是绝大多数困惑的来源。

选型时先按业务定新鲜度容忍度，再按部署形态确认可用性——静态导出与 ISR 天然冲突，多实例自建部署需要额外的缓存一致性设计。Next.js 15 对 fetch 缓存默认行为做了调整，升级前请逐条核对官方迁移说明；React 19 在本文写作时仍在 RC，尚未正式发布。
