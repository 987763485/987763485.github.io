React Server Components 探索

React Server Components（下称 RSC）是近几年 React 运行模型里改动最深的一项：它第一次让”这段代码运行在哪一侧”成为逐个组件都能做出的选择。本文只梳理它的问题域、边界规则与落地时的坑，作为一次探索记录。写作时点，它的配套接口与缓存口径仍在演进，把它当作刚走出实验阶段的工具、而非成熟的默认方案，更符合实际。

它到底解决什么问题

把 RSC 想解决的问题摊开，是三个互相纠缠的老毛病：浏览器要下载的脚本太多、数据访问路径太长、客户端代码复杂度太高。传统模式下，一个组件无论逻辑多简单，只要被渲染树引用，它的代码就进入包体；组件在接口里取回一大坨原始数据再于浏览器里拼装过滤，这些实现细节全部运行在用户设备上，还顺带把日期库、解析器一类依赖拖进包。

RSC 给出的答案是新加了一个维度：组件可以声明自己只在服务器运行。它的产物不是 JavaScript，而是一段渲染后的描述，代码本身一行都不进包。靠近数据的校验、权限过滤、模板拼装都可以留在服务器一侧，浏览器只接手真正要交互的部分。

人们习惯把它和服务端渲染放在一起比较，但两者不是一回事。服务端渲染是一种渲染方式：组件从头到尾仍然是客户端组件，服务器只是提前把它画成 HTML，浏览器随后还是要下载同一套脚本、执行注水、把控制权交回去。RSC 则是一种组件类型，改变的是代码归属与责任边界，产物不需要在浏览器里”复活”。两者也不冲突，App Router 这类框架基本叠着用：RSC 负责削减包体与取数，服务端渲染负责首屏 HTML。真正新的东西是提问方式：哪些代码该运行在离数据更近的一侧，现在可以精确到单个组件来回答。

边界是怎么划出来的

RSC 最具体的一样东西，是文件顶部那句 ‘use client’。别把它理解成”这个组件在客户端渲染”，它真正的语义是客户端模块图的入口标记：这个文件往下 import 的模块都会被打包进发往浏览器的脚本；反过来，一个没有标记的服务器组件，它的模块不会进入包体，浏览器拿到的只是它渲染出的描述。边界两侧产物形态不同，能力也就不同。

由此产生一条单向规则：服务器组件可以自由渲染客户端组件，客户端组件却不能把服务器组件 import 进来当普通子节点使用。一旦越过边界就是黑盒：只接受可序列化的 props，只能原样显示 children，没法递函数过去、也没法共享模块级可变状态。对应地，所有依赖”函数运行在浏览器里”的能力只能落在客户端组件一侧：onClick 这类事件处理、useState 与 useEffect 这类状态钩子、window 与 document 这类浏览器 API，以及大量直接摸 DOM 的第三方库。

划分边界的心法，官方文档反复强调”把客户端边界尽量往下推”：页面九成内容是静态展示、只有一小块要交互时，不要把整页裹进 ‘use client’，而应把交互部分——评论框、按钮组——切出来做成客户端组件，其余留在服务器侧。这句话平淡，做起来却反直觉：它要求先拆掉 SPA 时代”组件默认都在客户端”的假设，再按交互密度给每个组件重新定位。每往服务器侧多留一个组件，就意味着少分发包体里的一段脚本、少一次注水成本，这笔账在内容型站点上尤其划算。

组合模式：把客户端组件当 children 传入

开始写服务器组件后，很快会撞上这个限制：客户端组件像被冻在边界上的快照，拿到的 props 必须可序列化。如果既想让某个客户端组件持有服务端算好的数据，又想让它自由接收函数与状态，直接”传值”的方式很容易把整条数据链路拖进客户端模块图，边界就白划了。

官方文档反复推荐的组合模式正是解药：把一个客户端组件作为 React 元素——最常见的是 children，也可以是任意具名插槽——传给服务器组件。这个元素在服务器侧被渲染成描述、进入序列化路径，但组件本身仍保留在客户端模块图里，挂载后照常保有交互能力。妙处在于服务器组件不需要知道这个客户端组件需要什么数据，后者自顾自取上下文、拉状态，两者的数据流彻底解耦，props 里也就无需出现任何函数。

上下文是另一类高频坑。客户端组件里定义的 Context 提供器，没法直接把值透传给服务器组件，因为服务器组件渲染时根本不在浏览器那棵树上；服务器侧的值要进入某组客户端组件，也得显式经提供器中转一次。可行的姿势是把提供器摆在客户端模块图的上层，服务器组件把数据作为可序列化 props 一路递到它身上。总之把边界当成分布式系统的模块边界：一切传输显式、可序列化，不依赖隐式通道。这个约束起初让人烦躁，却顺带把许多”反正能传”的糊弄式架构逼问清楚了。

序列化与能跨边界的数据类型

服务器与浏览器之间传递的不是 HTML，而是一种中间表示，社区常叫它 RSC 载荷：描述哪个组件出现在什么位置、带着哪些 props。既然要过这条序列化管道，跨边界 props 就有一条硬规矩——必须能转成线上格式。普通对象、数组、字符串、数字、布尔值、空值天然过关；函数、类实例、符号不行，客户端组件的方法当 props 递给服务器组件更不行，违反时立刻报错。事件处理这类行为只能在客户端组件内部定义并使用，服务器一侧提供数据、不提供动作。

稍反直觉的是，Promise 是个被特批的类型，可以跨边界：服务器组件可以把一个”在途请求”直接当 prop 交给客户端组件，客户端一侧等它落地再取值；配上 Suspense，就形成一套很自然的流式模式——服务器先吐出页面骨架，慢数据的位置留空，结果一返回就把缺口补上，用户不必为整页最慢的那个接口干等。这套组合是 RSC 体验提升最直观的部分，值得优先在列表与详情页尝试。某些特殊值能否安全过界，各框架支持进度不一，以实际报错与所用框架文档为准，不要靠记忆猜。

数据获取与缓存：便利背后有坑

多数团队认真评估 RSC，都是冲着取数方式来的。服务器组件里可以直接连数据库、读文件、调用内部服务，凭据全程留在服务端，浏览器拿到的只是查询结果；取回数据的清洗、聚合、权限过滤都在同一侧完成，不用为同一份逻辑维护接口层与客户端层两套实现。对内容密集、数据敏感的页面，这条链路的缩短是看得见的收益。

坑在缓存这一环。框架层为了让一次请求里重复的取数合并去重，会把结果缓存起来，于是出现很难解释的现象：改了数据源，页面却像”忘不掉旧值”，重新部署之后看到的仍可能是旧内容。当时的默认缓存行为就属于易踩坑的设计，而且这些缓存开关与口径在 RSC 演进过程中被反复调整过，本文不背统一口径：唯一可靠的做法是按你正在使用的框架版本文档逐条核对，把每个请求的缓存意图写成显式声明。

失效手段大体围绕三类展开：按时间做按需再验证，在业务写入之后按路径或按标签主动失效，以及在请求本身做显式的旁路与开关。选型时一个朴素原则够用：让缓存策略出现在代码评审能看见的地方，把”为什么这里可以旧一点”写清楚，比记住某个开关的名字重要得多。

生态现状与局限：诚实一点

坦率地说，截至写作时点，RSC 仍处在演进期，体验和生态都谈不上稳。先看库兼容性：并非所有库都能跨边界工作——部分 CSS-in-JS 方案的出码方式与服务器渲染合不来，依赖浏览器全局环境的组件库在导入阶段就会炸，一些状态管理库只能整体留在客户端模块图里、隔着边界协作。实际后果是：适配成本落在你依赖的第三方库上而不是自己的代码上，评估时必须先盘这份清单。

再看人的成本。”这个组件运行在哪一侧”是一条全新的思路线，团队要从零建立”默认服务器、按需客户端”的直觉，代码评审里也要多问一句边界划得对不对；调试体验也更直接：跨边界的报错常离根因隔了几层，两侧没法同时下断点，新人挫败感不低。还有部署形态：RSC 深度依赖框架层的构建、路由与渲染服务，当时 Next.js 是主要落地方式，其他框架还在跟进，不打算把项目交给这类框架的团队几乎无法独立使用它。

时间线也要说清：React 19 于 2024 年 12 月 5 日刚发布，官方已放出把服务端组件纳入核心接口、配套 Actions 等能力的信号，值得跟进；但刚发布不等于已成默认工具链，库的适配与存量项目的升级都需要时间。至于只以实验形式放出的 React Compiler，现阶段不必纳入任何落地计划。

团队落地建议：什么场景值得，什么场景先别用

值不值得上手，本文的建议是分场景看。值得先试的：列表、详情、资讯这类内容与数据都重的展示型页面，包体收益最直接；权限敏感的数据，在服务器侧过滤完再下发、只让可见字段到达浏览器，比全量下发再在前端隐藏安全得多；接口偏慢的页面，配合 Suspense 的流式补洞对体验改善明显。可以先不用的：接近编辑器、几乎每寸区域都交互的界面，客户端模块图本来就躲不掉，边界划得再细也省不出多少；重度依赖未适配库的站点，改造成本会失控；还在消化 Hooks 与渲染心智的团队，不建议再叠加新维度。

引入节奏上倾向灰度：挑一两条与核心业务无关的边缘路由，先做成服务器组件优先，交互点仍用熟悉的客户端组件实现，观察一个迭代周期里包体变化（拿构建产物对比示意值即可，不必急着要结论）、报错形态与开发体感，再决定推广面。回退路径也留好了：边界内的客户端组件保持纯客户端写法，真要回退时把那条路由降级回客户端渲染即可。留这个后手的理由很直白——它自己的规范还在变。

小结

RSC 给 React 补上了”组件运行位置”这个维度：用 ‘use client’ 划出客户端模块图，以序列化开销为跨界的通行费，把取数与过滤挪到离数据近的一侧，把包体瘦成只剩真正要交互的部分；Promise 跨边界加 Suspense，又让流式渲染变得顺手。同时必须承认，库生态、调试体验与缓存口径都未定型，落地形态高度依赖框架层支持，React 19 刚发布也仍是信号而非现实。本文的立场是探索而非结论：先理解边界，再小范围试用，跟着演进口径核对文档，既不必全盘拥抱，也没必要一概拒绝。等工具链稳定下来，”这段代码该放在哪一侧”大概会成为和我们考虑组件拆分一样自然的问题。
