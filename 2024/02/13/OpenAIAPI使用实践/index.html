OpenAI API 使用实践

OpenAI 的接口调通一次并不难，难的是把它变成能长期运行的生产链路：超时该不该重试、限流怎么退避、日志里能不能留下密钥、这个月的钱花在哪里。本文面向已经用 Python 或 TypeScript 调用过 Chat Completions 的读者，按接口选型、请求结构、流式、工具调用、JSON mode、向量、错误处理、可靠性、成本与合规的顺序，讲清每个环节的实践口径。读完你应当能写出带超时、带退避、带用量日志的客户端骨架。

接口全景与选型

OpenAI 的文本入口有两个：更早的 completions 只接受一整段提示字符串，返回一整段续写，角色语义要靠提示词自己约定；Chat Completions 把输入抽象成 messages 数组，每个元素带 role 与 content，服务端按对话形式生成答复。二者背后是不同的模型系列，指令跟随能力差距明显，因此本批示例统一走 Chat Completions：它的消息结构能直接承载系统指令、历史轮次与工具调用结果，应用侧不必再拼接模板。该接口自 2023 年 11 月起还支持携带图像输入，本文不涉及。

SDK 进入 1.x 后，调用形态有两处实质变化。其一是命名空间化：过去是 openai.ChatCompletion.create(...) 这类模块级函数，现在先实例化客户端再走属性链，密钥、超时、重试次数、代理都能按实例覆盖，便于在同一进程里区分环境与模型池。其二是返回体与异常被类型化：响应是结构化对象，字段缺失在属性访问时即报错，错误也不再是一条通用 Exception，而是分成状态码、连接、超时与限流等分支，重试策略可按类型判断。同一套类型定义也让 TypeScript 侧能在编译期查出 messages 与 tools 的结构错误。

应用与接口之间还有一层职责边界：本文只讲客户端如何调用模型服务，整体分层与层间契约不在此展开；另一家的消息接口在角色与计费字段上有差异，思路可对照，代码不可混用。

请求结构逐项拆解

messages 的角色共有四类。system 放长期有效的指令与约束，如输出语言、身份、拒答边界；user 是本轮输入；assistant 既可以是历史答复，也可以是模型刚返回的调用意图；tool 承载某个工具的执行结果，必须与调用编号配对。角色写错不会立即报错，但会让模型把上下文当成用户话语，行为漂移很难排查，建议在客户端校验角色白名单。

采样参数中最常被误用的是 temperature 与 top_p。temperature 控制概率分布的陡峭程度，取值 0 到 2，抽取与分类任务取低值，创意写作取高值；top_p 是核采样阈值，按累计概率截断候选词。两者是同一件事的两个侧面，实践里只调其一，同时压低会让输出既呆板又难以复现。max_tokens 是本次生成的长度上限，也是单次费用天花板。stop 是停止序列列表，命中即结束生成，数量与长度都有限制，写入前先确认分隔符不会被模型自然生成。n 指定一次返回多少个候选，费用按倍数计，多数业务用 n 等于 1 加客户端多次采样更划算。

流式输出与增量拼接

流式解决的是首字延迟：不等整段生成完，边产出边下发。传输层上服务端以 SSE 分块推送，每个事件体是一行 data: 加一段 JSON，最后以 data: [DONE] 作为结束标记；客户端断开重连、背压与前端渲染口径另有专文，本文只讲接口层的消费方式。

SDK 1.x 把分块解析藏在迭代器里，stream=True 后拿到的是逐块对象而不是完整响应。工程上有三个细节容易踩。第一，首个块常常只有角色而没有内容，某些块 choices 是空数组，直接按下标取 delta 会抛索引错误，要先判空。第二，增量字段是 delta 里的 content 片段，要自己拼接缓冲区，同时保留 finish_reason 用于区分正常结束、长度截断与内容审核中止，三者对用户的提示文案应当不同。第三，客户端主动中断时要关闭流，否则底层连接一直被占用，在并发较高的服务里表现为连接池饥饿。自研客户端时还要留意分块边界不保证落在 JSON 结尾，不完整的行留在缓冲区等下一块。

工具调用的一轮完整交互

函数调用能力自 2023 年 6 月引入，后来收敛成更通用的 tools 形式：把可用能力写成带 JSON Schema 的声明，模型不执行任何操作，只输出“打算调用哪个函数、参数是什么”的结构化意图，执行权始终在客户端。

一轮完整交互要走两次请求。第一次带 messages 与 tools，模型返回的 assistant 消息里含 tool_calls 数组，每项有编号、函数名与 JSON 字符串形式的参数；客户端按名字派发到本地实现，再把执行结果以 role 等于 tool 的消息回传，用 tool_call_id 与调用编号配对；第二次请求时模型基于结果生成自然语言答复。多个调用可以并行出现，回传必须一一对齐，漏掉任何一个编号都会在下一轮直接报错。

sequenceDiagram
    participant A as 应用侧
    participant M as Chat Completions
    participant F as 本地函数
    A->>M: messages 加 tools 声明
    M-->>A: 返回 tool_calls 调用意图
    A->>F: 校验参数后按名派发
    F-->>A: 返回结构化执行结果
    A->>M: 追加 assistant 与 tool 消息
    M-->>A: 生成面向用户的最终答复

这里最容易犯的错是把模型给出的参数当成可信输入。它可能出现缺字段、类型不符、编造标识等情况，派发前必须按 Schema 校验；校验失败时把错误原文作为 tool 消息回传，让模型自行修正，而不是抛异常终止会话。

JSON mode 的能与不能

2023 年 11 月起，Chat Completions 支持通过 response_format 声明 json_object，让输出保证是一段语法合法的 JSON。它解决的是解析异常与括号不配对，而不是字段正确性：接口只承诺能 parse，不承诺符合你的业务 Schema。键名拼错、枚举值自创、该填数字却填了字符串，这些情况在 JSON mode 下照样会出现，因此自己那一层的校验不能省。

使用上有三点约束。第一，提示词里必须明确告诉模型输出 JSON，否则声明生效而内容可能只是一个空对象。第二，顶层建议约定成对象而不是数组，把列表放进固定键下，追加字段时兼容性更好。第三，它与工具调用一次调用只选一种：需要可执行意图就用 tools，需要落库的结构体就用 JSON mode。

还要注意 max_tokens 与 JSON mode 的相互作用：生成被截断时末尾括号不闭合，此时合法 JSON 的承诺同样落空，上限要按最坏结构预留。至于解析器实现、Schema 校验与失败后的修复重试链路，属于结构化解析专文的内容，本文不再展开。

Embeddings 与批量入库

向量化走独立的 embeddings 接口，当时稳定的通用文本模型是 text-embedding-ada-002，输出 1536 维浮点向量。input 可以直接传字符串数组，一次请求拿到多条结果，这是控制速率与成本的主要手段；单条文本按 token 计有长度上限，超长的一条会让整批请求失败，所以切块逻辑要在客户端完成。

维度一旦确定就写进了向量库的表结构，换模型等于换向量空间：不同模型的向量不能混在同一索引里检索。迁移的正确做法是新建集合并全量重算，再按流量切换，而不是原地覆盖。若检索用余弦相似度，入库前做一次 L2 归一化，之后用内积即可等价。

批量写入环节的真实痛点在于一致性而不是算法。以业务主键或文档加版本键作为 upsert 键，不要用自增 id，否则重试会产生重复向量；每个分片附带内容哈希，未变化则跳过重算；向量与元数据放在同一批或同一事务里，避免出现有向量无元数据的孤儿记录；失败分片只重投未确认的部分，不要整批重来。

新发布的 embedding 系列刚公布、落地不足一月，尚无广泛的使用数据，本文不写它的具体参数与取舍。

错误分流：可重试与不可重试

速率限制表现为 429，触发原因可能是每分钟请求数或每分钟 token 数超限，两者处置不同：请求数超限靠退避即可缓解，token 超限要减小批次或压低并发，单纯等待帮助有限。若响应头给出建议等待时长，优先按它等待。5xx、连接错误与读取超时属于可重试类别，重发大概率能成，但要假定“可能已经计费”，这与幂等处理直接相关。

上下文超长、参数结构非法、密钥无效、权限不足都是 4xx，重试只会重复失败。上下文超长应当在客户端做长度预算，超限时丢弃最旧轮次或先把历史摘要成一段再重发。内容审核拒绝同样不可重试，它有两种表现：请求阶段返回错误，或正常返回但 finish_reason 标记为内容过滤，后者要在客户端单独判定并走兜底文案，不能当成“生成不完整”去补发。

可靠性工程骨架

退避用指数加抖动，避免多个实例在同一时刻集体重发形成二次洪峰，等待上限也要设边界，累计耗时不能超出用户耐心。超时按请求级设定，连接超时与读取超时分开设，前者短、后者按最慢的正常生成时间给。重试次数可以交给 SDK 的 max_retries，流式与有副作用的调用则关掉自动重试、自己控制。

有副作用的链路还要有幂等键：把会话号与轮次号拼成请求标识写入调用记录，重试前先查该标识是否已有结果，重复投递时直接复用。再往外一层是熔断与降级：连续失败达到阈值就短路一段时间，期间把请求切到备用模型或返回缓存答复，避免整个会话被一个上游拖死。

备用模型与主模型行为并不完全一致，长度上限与工具能力都有差异，降级路径必须在测试环境里真实跑过，否则线上第一次触发就是故障现场。

成本、用量与数据合规

成本的计量单位是 token，它不等于字数，用量以响应里 usage 给出的三个字段为准；发送前则用官方分词库在本地估算，才能提前判断是否会撞上限：

按字符数粗估的比例随文本形态变化很大，本文不列换算系数，预算以 usage 为准。真正有效的控制是三件事：请求前把 messages 全量估算一遍做上下文体检，超预算就裁剪旧轮次或压缩历史；响应后把 prompt_tokens 与 completion_tokens 按会话、租户、功能点聚合入库；把 max_tokens 与 n 作为硬闸门写进配置，而不是依赖提示词自觉。单价乘以用量的成本模型与分摊方法另文讨论，本文只谈用量本身。

数据侧的底线同样要在客户端完成。日志不写原文，只留内容哈希、长度与结论字段；密钥不进代码、不进镜像、不进前端，只从环境变量或密钥管理服务读取，并按环境隔离；多团队协作时把调用集中到一层网关，由它统一鉴权、限流、脱敏与审计，把上游模型地址收敛为唯一出口。生成式服务相关管理办法自 2023 年 8 月施行，接入前按自身业务确认备案与内容留存义务，这属于管理口径而非技术选型。

小结

本文沿着一次调用的生命周期走了一遍，从消息结构、流式消费、工具调用到向量入库、错误分流与用量控制。接口的难点从来不在请求本身，而在于把不确定的生成结果放进确定的工程约束里，为此要始终保留自己的一层校验与预算。常见情形的处置口径整理如下，用户侧表现指最终呈现给使用者的内容。
