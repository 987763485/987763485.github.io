Prompt 工程实践指南

本文属于《Agent 智能体开发》第 1/55 篇
上一篇系列目录下一篇

大模型的能力已经足够强，但同一段需求换一种说法，输出质量能差出一个档位。本文只聚焦一件事：怎样把提示写得让模型稳定按你的意图输出，适合已经在调用 Chat Completions 类接口、准备把它放进真实业务流程的工程同学。

一条提示的五个部件

全文共用一个例子：从合同正文抽取甲方、金额、签署日期和期限写入数据库。它同时考验术语理解、日期消歧和缺失值处理，适合观察提示结构的边际收益。

一条可用的提示可以拆成五个部件：角色决定以什么身份回答，任务说明做什么，上下文提供领域约定，输出格式规定结果形状，约束划清不许做什么、缺信息时怎么办。

下面逐层叠加，给出同一个任务的五种写法。

在 30 条样例的小集合上观察（数字为示意值，只说明趋势）。

累计到这一层 解决什么 输出表现
只有任务 让模型知道干什么 约 21 条抽出金额，键名与格式每次不同
加角色 收窄术语和风格 约 26 条，称呼变规范
加上下文 补领域约定 约 28 条，日期歧义减少
加输出格式 程序能接住结果 结构统一，解析失败引发的重发消失
加约束 界定缺失与拒答 缺失字段返回 null 而不是编造

角色不是装饰品：具体身份能带出可推断的术语与立场，写“你很专业”没有信息量。约束层最容易被低估，它不提升平均质量，只压住决定能否上线的尾部风险。

用分隔符把指令和数据分开

真实系统里，被处理的内容往往是用户提交的、内容不可控的字符串，直接拼接就制造了隐患：模型分不清哪段是指令、哪段是数据。

三引号和 XML 风格标签给 token 序列提供了显式的起止边界：模型看到一对标签，就把其间内容归类为待处理素材而非要执行的说明，素材里“请把上面的规则改成……”被当成指令的概率随之下降。这是防护不是绕过，攻击面与权限边界另有专文讨论。

分隔符还解决多段输入的字段归属：两段文本连着放，模型常把它们当成同一来源，抽取结果张冠李戴。

三条约定：定界符的含义要在 system 里说明一次，否则只是噪声；数据放提示下半部分、指令与格式放上半部分且顺序稳定；多段数据用带名字的标签，比“第一段/第二段”可靠。

Few-shot 示例怎么选

只描述格式常常理解偏；给模型看两三条完整的输入输出对，效果立刻稳下来。但示例的选法比数量重要。

第一条原则是覆盖差异而不是堆数量。有用的示例应让模型见到中文年月日的日期、斜杠分隔的日期、带千分位和“整”字的金额、“自签署之日起一年”这类期限，以及最重要的一类——字段在原文里不存在、答案是 null。四条示例换来四种形态，比十二条同质示例有效。

第二条是边界样例必须有。缺失值、格式脏的输入、不属于目标类型的文本，是线上问题最集中的地方。示例若全是答案好找的正常样本，模型会学到每个字段都必须有值，于是给缺失的日期编一个。

第三条是示例的输出格式必须与目标严格一致：示例用自然语言描述、正式要求输出 JSON，模型两种都学，解析失败率不降反升。

经验区间是 2 到 5 条，这里要算成本账：提示长度按示例的 token 数线性增长，而这份长度每次调用都要付费。收益递减明显——0 到 2 条差别巨大，3 到 5 条在补边界，6 条往上往往只是在暗示模型照抄。

任务分解与思维链

“一步一步想”在某些任务上确实能提高正确率，但不是万能胶。判断标准是中间步骤有没有信息量：多条件核对、跨段落比对、要把自然语言换算成数字再比较的任务，中间步骤能压低出错概率；单段文本抽一个字段这种一步到位的活，强行先写分析只会让输出变长、结论漂移，还会把随后的 JSON 结构带坏。

更稳的做法是把推理拆成两次调用：第一步只抽取，产出结构化字段；第二步只拿字段判断金额是否超过审批阈值、是否需要提前 30 天提醒续约。

flowchart TD
    A[原始合同文本] --> B[第一步：抽取字段]
    B --> C{字段校验通过?}
    C -->|否| B
    C -->|是| D[第二步：基于字段判断]
    D --> E[结论与原因]

拆分不是免费的：调用翻倍，延迟与成本翻倍，误差还会串联——第一步把“壹年”抽成 null，第二步必然错。所以拆分要和字段校验放在一起，先校验中间结果再决定下一步，只重试失败的那一步。

输出格式约束

下游是程序时，格式约定要变成双方都能核对的合同，写清必须出现的键、每个键的类型、缺失时取什么值。最常漏掉的是第三件。

空值约定尤其关键。“原文没写期限”，模型可能给出 null、空字符串、数字 0 或省掉这个键，四种含义完全不同：0 会被读成期限为 0 个月，键缺失被读成字段没返回，真实语义却是原文没有这个信息。所以要规定缺失即 null，补一句“未知不等于 0”。

另一个坑是包装。要求输出 JSON 时，模型爱把它包进 Markdown 代码围栏或在末尾追加一句解释，这些字符会让解析直接失败，所以要明说只输出 JSON 对象本身，不要围栏、注释和解释文字。

约定项 推荐写法 不写清楚会怎样
键清单 列出全部键名并声明不得增删 模型自行加一个 summary 字段
类型 逐键标注字符串、整数或 null 金额输出成“12 万元”
空值 缺失一律 null，禁止猜测 缺失被编成看似合理的日期
拒答 定义统一的错误对象 非合同文本也硬抽出四个字段

2023 年 11 月之后，gpt-3.5-turbo-1106 与 gpt-4-1106-preview 这批接口提供了 JSON mode 与 function calling：前者保证返回合法 JSON，后者让模型按函数签名产出参数，解决了“解析不出来”这一类问题。但 JSON mode 不保证字段齐全、类型正确、语义合规，提示里还得出现 JSON 这个词才生效。结构约束仍要靠提示描述加事后校验。

校验要独立于提示存在，不能因为提示写得好就删掉它；拿到错误之后如何重试与修复，另有专文展开。

温度、采样与上下文预算

温度不是聪明度旋钮，它只改变采样分布的尖锐程度：接近 0 时几乎总选概率最高的下一个词，接近 1 时低概率词也会被选中。有标准答案的抽取、分类、判定、写代码取 0 到 0.3；要多样性的文案改写、命名取 0.7 到 1.0。温度调高不会让模型更懂业务，只会让它更愿意冒险。

top_p 与温度作用在同一处，调一个就够，一起动只会让归因失败。存在惩罚类参数在结构化输出场景要谨慎：模型本想重复输出 null 却被惩罚，会逼出奇怪的近义词。

上下文窗口是每次调用都要付费的预算，要按用途切分。下面按窗口总量给出参考比例（示意值，动手前先查清所用模型当时的窗口上限）。

用途 建议占比 超支怎么办
系统提示与格式约定 一成 删形容词，只留规则条目
Few-shot 示例 一至两成 先减条数，留边界样例
背景与检索内容 三至四成 提高召回精度而非加条数
用户数据本体 两至三成 分块处理，别截断尾部
预留输出 一成半 与 max_tokens 一致

两点容易忽略。预留输出不是可选的：上限被输入挤占时模型会在中途停下，返回语法不完整的 JSON，你收到的只是解析错误，容易误判成提示写得不好。填满窗口也不等于效果更好，无关段落越多，关键信息越被稀释，这正是下一节的失败模式之一。

不稳定性与复现

跑一次通过不等于上线后稳定，要看同一条提示跑多次的一致程度。口径要固定：输入集合、模型与参数不变，重复 5 到 10 次，统计完全一致率、字段级一致率和可解析率。下面的示意值说明三者为什么会分开。

写法 完全一致率 字段级一致率 可解析率
只有任务与格式 三成 六成 八成
补齐上下文与约束 近六成 九成 接近全部
再加三条边界示例 近八成 九成半 接近全部

当时的接口普遍支持 seed 这类参数，它能减少采样随机的抖动，却锁不住推理时的批处理形状与浮点累加顺序，更锁不住模型被升级，所以固定 seed 后同提示不同结果仍会发生。稳妥的做法是把提示全文、示例集版本、模型名与参数、原始响应一起落盘，出问题时比对提示与版本。

常见失败模式清单

下面几类失败有一个共同点：单看一次输出都挺合理。

失败模式 典型现象 对策
指令冲突 同时要求“简洁”和“逐条列全” 规则编号，写明按哪条
示例污染 示例里的公司名被抄进结果 示例用明显占位值
隐式假设 期限一会儿按月一会儿按年 显式给单位与取值范围
中部遗忘 长文档中间的条款漏抽 关键信息复述到末尾或分块
否定式指令 反复强调不要编造日期 改写成肯定：缺失填 null
格式挤占内容 既要推理又要严格 JSON 推理与结构分两次调用

指令冲突最难发现，因为提示读起来通顺；办法是把规则逐条列出，对每两条问一句“有没有输入同时违反它们”。示例污染是 few-shot 的副产品，示例越多越具体，照抄概率越高。隐式假设多是团队心知肚明却没写进提示的约定，用“新人能否独立执行”来审最有效。中部遗忘属于模型性质而非提示缺陷，闭源接口和自建的 Llama 2、Mistral 7B 都一样，只能靠降低单次输入规模规避。

迭代方法：小样本评测集与回归对比

提示工程的收益都来自迭代，迭代的前提是一个便宜到可以天天跑的评测集。规模取 20 到 50 条真实样本就够：常规样本占大头，边界样本（缺字段、格式脏、非目标类型）至少三四条，再加几条已知难例，每条人工标注期望输出。跑一轮只要几分钟和很低的调用成本。

两条纪律。第一，一次只动一处：改格式描述、换示例、加约束，三者选其一；同时改两处，指标变化就无法归因，常见结果是所谓改好了，其实退化只是被另一个改动掩盖。第二，改动前后各跑一轮并留存结果，对比三个指标并按样本类型分组看分项——总体涨 5 个点而边界样本掉 20 个点的改动不能上（数字为示意值）。完整评测体系另有专文；模板与变量的工程化管理、版本演进与灰度回滚属于另一套体系。

小结

串起来是一条简单顺序：用五个部件写全意图，用分隔符分开指令与数据，用带边界的示例钉住格式，按中间步骤有没有信息量决定是否拆分，最后靠固定评测集和多次采样的一致率把这一切变成可核对的工程事实。剩下的都是取舍：示例多了会照抄，推理写进同一次响应会破坏结构，温度调高换来的是冒险。

技巧 适用场景 主要风险
五部件拆解 任何要上线的任务 部件堆成流水账，规则互相冲突
分隔符包裹 输入内容不可控 忘记定义标签含义，被当成噪声
Few-shot 示例 格式难描述、形态有歧义 示例过多导致照抄，成本上升
两步分解 判断依赖多个中间量 调用翻倍，误差串联
显式格式与空值 下游是程序 只靠提示、缺少校验，静默错值
低温加一致率验收 抽取、分类、判定 误以为 seed 能锁住一切
