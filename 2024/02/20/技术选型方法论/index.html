技术选型方法论

技术选型每个团队都会反复做，但多数讨论停在”要看场景”这句话上，没有把场景展开成结论的过程。本文把它拆成约束收集、候选池、评分维度、证据采集、决策记录与复评退出六个环节，每一环给出可直接套用的清单、判定表或模板，适合即将引入新框架、新语言运行时的同学，以及需要在评审会上解释”为什么是它”的负责人。文中时限、人数与阈值一律是团队约定示例，不代表任何厂商或社区统计。

选型的三种失败形态

要设计流程，先要看清失败长什么样。选型事故几乎都能归入三类，成因不同，预防手段也不同；把它们混成同一种”选错了”，开出的药方就只能是一句”下次多调研”。

形态一：选完就后悔

典型说法是”早知道就不换它了”。技术本身往往没有明显缺陷，缺的是决策时没把约束写成文字：输入信号只有”最近讨论得多””维护者很有名””演示跑得很顺”，而没人回答”招不招到会它的人””出问题时谁半夜排查””现有构建脚本要不要重写”。半年后炸出来的问题，通常在决策那天已经确定。

更深的成因是把候选池当成结论：方案排第一，只说明它在评估者构造的维度上得分最高，不意味着它与团队的组织现实相容。

形态二：半年后迁移

这类失败是选完之后走了一半又退回来，或者干脆换掉。成因有三个：评估只覆盖”能不能写出第一个接口”，没覆盖演进，一个只做增删改查的验证项目能跑，不代表它两年后撑得住多租户、灰度发布与合规审计；PoC 代码被直接当成生产骨架，早期妥协变成长期债务，迁移成本最后都记在”这个技术不行”的账上；决策时没写复评触发条件，注意力要等线上事故才回到选型问题上。

它多发生在多端项目里：服务端语言与跨端界面方案由两个小组分别评估，各看各的文档，最后发现可观测口径接不上——链路标识无法贯穿，构建产物版本对不上，只能重做一端。接界处没人负责，就是典型的单点都对、整体不可用。

形态三：只有跑分没有结论

第三类最隐蔽：材料里全是数字，却没有决策。有人跑了一轮微基准，得出两个方案在某细分操作上相差若干倍，会议室于是陷入两种极端——要么”数据都在这，还用讨论吗”，要么”这数据不说明问题”，然后什么都没定。

成因是跑分与决策之间缺两层转换。一是负载形态：微基准测单个操作的极限，端到端关心真实请求里 IO、序列化、连接池与调度共同决定的分位延迟与稳定性，两者结论可以相反。二是表述形式：基准结论必须以区间加条件的形式给出，条件要写清硬件、并发档位、预热方式与配置水平，否则它没法参与权衡。

三类失败合起来指向同一句话：选型的产物不是赢家，而是一份把约束、证据、决定与代价绑在一起的记录。后面几个环节都是为了产出这份记录。

先定约束再找候选

流程总览

选型可以画成一条带门禁的流水线，关键在三处：候选池在硬约束之后，PoC 在评分之后，复评条件与决定写在同一份文档里。

flowchart TD
    A[收集约束条件] --> B{硬约束门禁}
    B -->|不满足| C[直接淘汰并记录原因]
    B -->|满足| D[候选池收敛到 3-5 个]
    D --> E[按维度评分]
    E --> F{分数接近}
    F -->|是| G[做 PoC 与证据采集]
    F -->|否| H[写出 ADR 决策记录]
    G --> H
    H --> I[设定复评触发条件]
    I --> J[到期或触发时重评]
    J --> A

两处门禁最容易被省略，也最省时间：硬约束淘汰能在一小时内清掉半个池子，复评触发条件则决定你会不会跌进形态二。

六类约束

约束要写成可判定真假的句子，不能是”性能要好””生态要活跃”这类无法核对的愿望。下面这份清单把最容易漏的六类约束落成问句，评审时逐条回答并写下出处；答案要由团队自己填，本文不代填。

清单里最常被跳过的是运维与招聘、退出成本两类，因为它们不表现为技术缺陷，而表现为团队持续付出额外时间；合规与许可证两类相反，跳过的代价集中爆发，通常是临近上线时整个方案作废。本文不做状态管理库、向量数据库这类具体候选的逐项对比，那是专篇内容。

约束之间会冲突

六类约束经常互相矛盾，交付时间一紧，团队技能与退出成本就会被挤压。可操作的办法只有一个：在文件顶部写一行显式排序，例如”合规 > 交付时间 > 运维与招聘 > 团队技能 > 退出成本 > 许可证细节”，并记录理由。有了排序，冲突发生时不必重新争吵；没有排序，同一个冲突每周都会以新形式出现一次。

排序之后把约束分成两档：硬门禁不满足直接淘汰并记录，软约束进入评分维度按权重体现。分档本身要是一次显式决定，而不是评审现场的即兴判断；至于协作规范如何落到日常流程，属于团队协作类文章的范围。

候选池的构建与收敛

来源要刻意分散

池子最常见的毛病是来源单一：某位成员在读一个项目，于是一半候选是它的变体。渠道应当互相独立，至少四类：自家存量，翻依赖清单与构建脚本，看哪些方案已在某个角落跑着且没人抱怨，它的运维经验与排查手册都在手里；官方生态位，框架给出的受支持集成清单与兼容性矩阵，例如 Spring 的项目列表、Kotlin 的官方库索引、Flutter 的插件市场与 .NET 的包目录；包仓库的客观记录，包括发布历史、支持声明与许可证字段；外部实践描述，只用来发现候选，因为它天然带幸存者偏差。

先排除，再加权

第一步不是打分而是排除。拿约束清单逐条核对，四类情况应当在评分之前出局：硬约束不满足；目标平台或运行时不受支持，或只在预览状态下支持；许可证与商用条款同产品形态冲突；没有可核对的维护信号，例如长期没有发布、没有安全响应渠道、官方已声明进入维护或废弃状态。

排除要留一行记录，写清因哪条约束出局。它的价值在半年后：有人重提这个方案时，一句”已因合规约束排除，原因见约束清单第 4 条”就能避免整场讨论重来一遍。

为什么是 3-5 个

池子要压到三到五个，这不是审美，而是两种失效之间的平衡点。只有两个候选时，评审几乎必然退化成立场之争：新证据只被用来攻击对方，否决一个之后团队失去选项，只能退回重做。三到五个提供了中间地带——可以得出”两个都不合适，用第三个”，也可以把两个候选合并成同一个决定，例如服务端沿用现有语言、只在客户端引入新方案，而合并往往就是最优解。超过五个则成本失控：评分表要有人独立填写，PoC 预算按候选数线性增长，且第五个之后往往是某个方案的另一个变体，差异不足以支撑决策。

压缩的做法是按实现路径分组，同组只保留一个代表，判断标准是替代它们所需付出的工程动作是否相同：若两个候选要求相同的部署形态、技能栈与运维接入方式，它们在决策上就是同一个选项。示例：后端候选里若若干项都属于”沿用 JVM 生态、只是语言不同”，例如在 Java 17 与 21 这两个 LTS 版本之上用 Kotlin 1.9.x 编写服务层，那就是一组；”更换运行时并更换构建与镜像产物”的候选自成一组。分组只解决评审成本，不构成优劣判断。

把”不引入”放进池子

最后一步容易漏：把”不做改动、在现有栈内解决”作为正式候选列入并给完整评分。这是防追新的机制，也是防个别人偏好决定的机制：很多选型的真实需求只是”某个模块难维护”，而现有栈里的重构、拆分或升级同样能满足它；这个选项不在表上，决策就变成”引入什么”的单选题。

评分维度设计

维度要能被独立填写

评分维度的设计标准只有一条：一个没有参与讨论的成员，看完维度定义和证据来源后，能填出一个和别人可比较的分。”生态好””性能强””社区活跃”没有判据，做不到这一点，最终只能变成嗓门大小的比拼。每个维度写清三件事：问什么、看什么证据、怎么给分，其中分档优于连续分值，后者会制造假精确。

性能是否够用。关键在”够用”而不是”最优”。先写下目标：某类接口在预期峰值并发下的分位延迟上限、单实例承载流量下限、内存预算、启动时间要求，再判断候选落在”满足并留有余量””处在边界需专门优化””无法满足”哪一档。多数候选都在第一档，此时这个维度对决策没有贡献，应当把权重让出去；落到第三档则是硬问题，不能靠”以后优化”含糊。完整的负载对比属于性能类文章。

可观测性与排障难度。这是最被低估的维度。问三句：日志、指标、链路能否接进现有平台；出问题时能否用现有工具看到内部状态；是否有可用的追踪与剖析集成。判据建议写成”不加新组件就能定位一次人为构造的超时故障”。它决定凌晨值班的体验，却几乎不出现在对比材料里，因为跑分不需要值班。

回到版本口径：以 2024 年 2 月为时点，可核对的基线是 JVM 侧 Java 17 与 21 这两个 LTS 版本配合 Spring Boot 3.2，.NET 侧是 .NET 8，跨端方案取当时的稳定通道版本，Kotlin 服务层按 1.9.x 口径评估，前端工具链按 Node.js 20 LTS 口径，Go 侧则是刚发布不足一个月的 1.22。依据不是热度，而是各自的升级路径能否被官方文档验证。

权重从约束排序里来

权重的合法性来自上一节的约束优先级，而不是评审现场的兴趣。做法很机械：把约束清单里的排序直接映射成维度权重，排在前面的约束对应的维度拿高分值，归一化之后把映射结果写进表头。这样当有人质疑”为什么可观测性权重这么高”，答案指向约束文件而不是某个人的偏好。反过来，如果换一组合理权重就翻转结论，这本身就是重要信息：说明决策由权重而非证据决定，应当回到约束层确认优先级。

加权法的四个失效场景

第一种是分数接近。此时打分已经失去区分能力，该看的是可逆性与执行侧条件：哪个方案改错了能退回、哪套产物能复用现有流水线、谁愿意承担内部负责人角色、值班时谁能看懂告警。这几项塞不进加权表，却常常是真正的决定因素。

第二种是权重被结果反推，先在心里定了赢家再回去调权重。防法有三条：权重在任何分数填写之前锁定并写入文件；填分与算分由不参与讨论的人执行；调整权重必须提交变更说明，同 ADR 一起存档。

第三种是维度重复计权。功能匹配度与生态演进、性能够用与构建一致性明显正相关，同时给高权重等于把同一个判断算两遍，会把某方向的优势放大成决定性优势。检查方法是问：这个候选的高分，是否完全由另一维带来？

第四种是打分掩盖否决项。加权表天生倾向于”总分高就赢”，而许可证、托管依赖这类问题不能被别的维度补回来，所以否决检查必须在计分之前执行；顺序错了，表再漂亮也没有意义。

PoC 怎么设计才不走过场

PoC 是一次有预算的实验，不是一次演示，四件事要在开工前写进文档。第一是可证伪的假设，写成”若某能力在不自建组件的前提下能接进现有平台，则此候选可用”，并明确什么结果算它不成立；写不出失败条件的 PoC 只是给已有结论找证据。第二是人日预算，建议单人两到五日，团队约定示例可取四日为上限，超了就停——它是唯一能防住”再试一天就通了”这种膨胀的手段。第三是有代表性的负载，选真实场景里最麻烦的那条路径，至少包含一次带测试的业务改造、一次故障排查演练、一次完整构建与发布，跨端项目再加一次原生能力调用。第四是失败退出条件，写清”若未达成则本候选出局，代码删除或归档，不做二次利用”。

一个真实感很强的反例：某团队让方案的最大推荐者独自做 PoC，题目由他自定，只演示成功路径，没有失败条件，时限从三天延到三周，最后把 PoC 代码整理两遍直接上线。这场 PoC 的唯一功能是证明推荐者是对的。破解只有三条：出题人、执行人、判分人分开；时限与失败条件写进文档；PoC 产物与生产代码隔离。

决策记录与复评退出

ADR 是选型的交付物

评审会结束时的口头共识不是选型的产物，能被后来的人读到、核对与推翻的记录才是。架构决策记录（ADR）把一次决定的背景、选项、结论与代价固化成带时间戳的文件，与代码同仓、编号递增，状态可以变更但内容不改写：新的认识用新记录表达，旧记录标为已被取代。三年后想知道当年为什么这么定，不需要找人问，也不需要靠猜。

示例：网关服务的语言边界怎么记

以一个常见场景填一遍：一个已有 JVM 服务群的产品线，需要为新增的网关型服务决定实现边界，候选包括沿用现有栈与引入另一套运行时。这里用 Java 与 Go 举例，只演示记录方法，不比较优劣。

这份记录的重点不在选项本身，而在于它把结论钉在场景里：标题写的是”新增网关型服务”，不是”服务端语言选择”；后果一栏明写负面代价与未解决问题；复评条件让决定可以在几个月后被合理推翻。一份填得完整的 ADR 不会给出”谁更好”这类跨场景结论。

什么时候必须重评

复评不是仪式，触发条件要具体到能被非当事人核对。常见的有五类：依赖的版本或平台跳代，例如运行时从当前 LTS 迁移到下一代；团队结构变化，能承担内部负责人角色的人数低于阈值；外部约束变化，合规要求或分发形态调整；运维信号，同类故障重复出现或排查耗时上升；约定到期，即使没有异常也在上线后固定月份强制重看。第五条最重要，因为前四条都依赖有人愿意先承认问题。

降低沉没成本偏差

选型一旦落地，团队就会不自觉地为它辩护。三个机制能缓解：决策人与执行人分离，评审组轮值，避免同一批人反复为自己的选择背书；PoC 与迁移的预算上限预先写死，超支要走正式追加审批；每季度做一次零基线重问——假设今天什么都没建，只看现在的需求与团队，是否还会选它。它的作用是把”要不要维持”与”当初要不要选”分开。

迁移路径预案

选型的代价不在决定那一刻，而在需要改变它的时候，所以预案属于决策记录的一部分。做法是优先选择可逆的接入方式：把新方案限制在一层适配代码里，让领域模型与接口契约不依赖它的具体类型；渐进替换而不是一次切换，先承接只读流量；保留双跑与影子流量，使回滚只需改一次路由配置。这些约束会让早期开发不够爽快，而正是这点不爽快，在事后省下整场重写。

三个反复出现的反模式

追新：把”最近热门”当作证据，把”我们还在用旧版本”当作问题本身，破解是把”不引入”列入评分表并认真填一次证据列。由个别人偏好决定：候选池由某个方案的变体组成、维度按它的强项设计、PoC 由它的推荐者独自完成；这条最难自察，因为它看起来完全像专业判断，唯一可靠的检查是出题人、执行人、判分人是否分离。把选型当技术站队：反对方案等于否定人，于是要么用跑分压人，要么用”数据不说明问题”回避数据；一旦出现站队迹象，停止口头讨论，把分歧写成表里的分差与各自一句理由。

小结

方法论的全部内容其实是一句话：把”我们觉得它行”变成”在写明的约束与条件下，证据支持这个决定，代价是这些，重看的条件在这里”。约束清单与否决门禁把池子变小，评分维度与检查单把差别说清楚，PoC 把印象换成观察，ADR 与复评条件让决定可以被诚实地推翻。权重和分数替代不了判断：一旦分差小到需要解释，起作用的就是可逆性、值班体验和谁愿意当内部负责人。
