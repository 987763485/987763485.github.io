模型量化与 GGUF 格式

本地跑大模型的第一道门槛往往不是算法，而是内存与带宽。本文从一条估算公式出发，说明权重为何要从 16 位浮点压到 4 位整数，解释分组量化如何压住误差，再拆开 GGUF 的字节布局，梳理 2024 年年初可用的量化档位。适合准备在本地部署 Llama 2 或 Mistral 7B、却在档位表前犹豫的读者。

量化的出发点：容量与带宽

自回归解码每产出一个 token，都要把整份权重从头到尾读一遍。批量不大时，浮点单元大部分时间在等数据，真正的约束是内存带宽而不是算力。于是“每个参数占多少字节”这个静态数字，同时决定模型能不能装下、跑得多快：容量决定可行性，带宽决定速度上限。

权重量化要做的事很直接：把浮点张量换成低位宽整数，再加一点用于恢复量级的旁信息。代价从每参数 2 字节降到 0.6 至 1.2 字节，收益是同样显存装下更大的模型，或为上下文腾出空间。

但总量不止权重。注意力会为序列中每个位置缓存一对 K 与 V，这段内存随序列长度线性增长，量化权重时动不了它。两者放在一起看，才看得见档位的真实边界。

重点不在输出，而在三者的相对比例。fp16 时 KV Cache 只是零头；把权重降到 4 位之后，它的占比迅速升到三成上下，此时继续压权重的收益开始不如缩短上下文。量化档位与上下文长度必须一起决定，分开调是常见的错误来源。

量化的两种切法

第一个分野是量化对象。只量权重、激活保持浮点；两者一起量，则整条链路都能用低位宽内核。

权重是静态的：训练结束就固定了，可以离线慢慢算每组的比例因子，甚至多试几种分组再挑最好的。激活是动态的，同一层在不同输入下范围差别很大，必须运行时先统计再量化，既有额外开销，也依赖后端有对应的融合内核。本地推理批量小、以矩阵乘向量为主，权重读取才是瓶颈，所以仅权重量化收益最直接，也最容易跨硬件落地。

第二个分野是量化处于训练的哪个阶段。

量化感知训练（QAT）在训练回路里插入一个“假装量化”的环节：前向时把权重与激活投影到目标格点再算损失，反向时用近似梯度绕过取整的不可导点。上限确实高，但要付出完整训练流程、数据与算力，而且每换一次目标位宽往往要重跑。为本地部署去重训一个几百亿参数的基座模型，这份成本没人愿意付。

训练后量化（PTQ）相反：模型已经训练完毕，量化只是对已有权重做一次离线压缩，最多用一小批校准数据统计各层数值范围。门槛低、产物确定，同一个权重文件能在不同机器上反复使用，天然适合“一次转换、到处分发”的开源生态。这就是当时的大模型本地部署几乎全走 PTQ 的原因——不是 QAT 不好，而是它的收益结构与分发场景不匹配。

分组量化与 per-channel

PTQ 的核心困难在于：同一层内权重范围差异极大，少数离群值就把整体跨度撑开。整层共用一个比例因子时，多数正常权重被挤到极少几个格点上，信息大面积丢失。

均匀量化把一段实数区间等分成 2 的位宽次方个格点，权重就近落点：

scale 与量化值一起存下来，恢复时只需一次乘法。误差上界大致是 scale 的一半，而 scale 由组内极差除以格点数决定：极差越小，误差越小。于是“分组”成了必然选择——把张量切成小块，每块自带比例因子，只覆盖自己那一小段数值范围。

非对称量化再多存一个零点（或最小值），把区间下沿对齐到实际分布，代价是每组多花一点旁信息。Q4_0 只有 scale，属对称方案；Q4_1 带第二个附加量，属非对称方案，两者体积差正好是一份旁信息。

分组量化与 per-channel 在这里是同一条思路：粒度越细误差越小，但旁信息越多。块太小会让比例因子的开销反噬压缩收益，块太大则分组形同虚设。把这件事做两层，就是后文 K-系列的原型。

运行它会看到一条单调下降的曲线：块从整层缩到 32，误差迅速收敛；再缩到 16 或 8，收益平缓而旁信息仍在增加。这就是实践中常用 32 这个块长的原因。

GGUF：从 GGML 到自描述容器

2023 年 3 月开源的那套 C 与 C++ 推理代码，早期直接读取自家 GGML 的二进制权重。那种格式信息不全：张量叫什么、有多少层、隐藏维多大、词表如何还原，都由转换脚本与加载器约定死，元数据事实上硬编码在源码里。于是每支持一个新架构，就得同时改转换程序、加载器和量化脚本，而文件本身几乎不携带自我说明。

2023 年 8 月起启用的 GGUF 就是为这件事准备的：让单个文件自包含。结构参数、张量清单、分词器词表与合并规则、对话模板、适配所需的提示信息，全部以键值对写进文件。加载器只要会读这套键值，就能判断该用哪种网络形状实例化，不必再猜。

这同时缓解了多语言绑定的问题：权重格式不再依附某个特定 Python 库的对象布局，也不必为每种宿主语言重复一份模型定义，约定从“写在代码里”变成“写在文件里”。v1 到 v3 的演进也沿着这条路：v1 基本延续 GGML 的结构，v2 把元数据独立成与张量数据分离的键值区，v3 进一步统一字符串与张量信息段的读法并收紧对齐要求。本文按 v3 口径拆解。

GGUF 文件结构拆解

flowchart TD
  A[文件头：魔数与版本] --> B[计数区：张量个数与 KV 个数]
  B --> C[KV 元数据区：结构参数、词表、对话模板]
  C --> D[张量信息表：名称、维度、类型、偏移]
  D --> E[对齐填充]
  E --> F[张量数据段：按块存放的量化权重]

几个细节值得单独说明。字符串一律带长度前缀，先取长度再取内容，不需要零字节作终止符，词表里的特殊符号也能安全存放。张量偏移相对数据段起点计算，而数据段起点由对齐值向上取整得到，内核因此能直接按边界访问量化块。最关键是类型字段挂在每个张量上而非整个文件上——同一个 GGUF 里可以混放不同档位的张量，这正是混合量化在格式层面成立的前提。读完张量信息表就能算出每个张量的起止地址，不必扫描数据段。

遍历 KV 区还需要一张类型表：标量按各自宽度读，字符串与数组是“长度前缀加元素类型”的嵌套结构，必须递归跳过。只读键名已足够体检，后文的自检就靠它。

当时可用的量化档位

Q 系列与 K 系列解决同一个问题，区别在分组粒度。

Q4_0、Q4_1、Q5_0、Q5_1、Q8_0 是单级定长块：每 32 个权重一组，组前放一个 fp32 比例因子，带 1 后缀的再多放一个最小值。规则整齐，内核简单。把旁信息摊入每参数开销后：Q4_0 约 5 比特，Q4_1 与 Q5_0 约 6 比特，Q5_1 约 7 比特，Q8_0 约 9 比特——体积差主要来自旁信息而非名义位宽。

Q2_K 到 Q8_K 走两级分组：大块里嵌若干小块，小块各自带比例因子与最小值，而这些小块参数本身又被粗量化一次，大块再记录一组基准。省下的是旁信息空间，同一名义位宽下能腾出更多档位，不必让每组都付一份 fp32。代价是块结构更绕，某些档位在小批量时反而不比整齐的 Q4_0 快。

敏感度并不均匀。普遍经验是：Transformer 的首尾几层、注意力里负责输出汇聚的投影，以及 FFN 中承担降维的那块权重更敏感，同样位宽降在它们身上损失明显更大。混合量化工具因此能按张量名单独指定档位，这也是 K-系列把粒度做细的理由之一。

症状对照与选择流程

换档位前先确认症状属于哪一类，否则会调错方向。

症状 先检查什么 调整方向
装不下 上下文长度、并行请求数、是否两份模型常驻 缩短上下文，降一档，其次换更小模型
跑得慢 首 token 慢还是逐 token 慢、磁盘是否仍在读 优先改档位形态而非猛降位宽，减小批次
质量差 输出是否复读、角色错乱、长文跑题 升一档，或给敏感层单独保留高比特

顺序上建议从上界往下试：先跑到装得下的最大档位，再逐步下压，每压一次自检一次，不要一步跳到最低位宽再解释效果为什么差。首 token 慢通常是预填充受限，逐 token 慢才是带宽问题，两者处方不同。

转换与自检

从 Hugging Face 权重出发的流程分三步：把 fp16 张量按统一命名写入 GGUF，并带上结构参数与分词器信息；按目标档位逐张量做分块量化，输出新文件；加载验证。第一步最容易被忽略，却决定成败。

坑集中在两处。其一是分词器与对话模板必须与模型训练使用时一致：词表、特殊 token 的编号、模板里的角色标记任一不对，表现不是报错而是安静地胡说——复读、角色混乱、把模板原样吐回来。模板在 KV 区里是一个字符串字段，转出来务必逐字核对。其二是量化脚本的张量名匹配：名字对不上就退化成整层共用一个比例因子，文件照样生成、体积正常，只是质量塌了。

至于阈值，本文刻意不给具体数字：困惑度的绝对值与语料语种、领域、分词强相关，抄来的数字只会误导。有意义的是同一批条件下基线与各档位的相对变化趋势，以及定性探针是否出现新的失败模式。明显退化时先怀疑转换环节，而不是急着降上下文。

适用边界

云端接口不必自己持有权重，容量与批量由服务商决定，代价是数据出口、长尾延迟与单位成本不可控；本地量化则用一次性投入换可控性与离线能力。两者不是替代关系。

与同期方案相比，定位差异比性能差异更值得记。bitsandbytes 的 int8 与 NF4 服务于 Python 加 PyTorch 的训练与微调生态，权重格式贴近张量库，方便与参数高效微调组件搭配，但不解决跨语言分发；GGUF 面向的是把模型作为单个文件投递给各种宿主环境。GPTQ 与 AWQ 依赖校准数据与逐层误差补偿，需要配套的反量化内核与显卡；分组量化把力气花在块结构与旁信息压缩上，用通用内核换可移植性。

边界之外不展开：llama.cpp 的源码结构、批处理与内核调度另有专文；应用侧的分层职责在《大模型应用架构分层》里已讲清，这里只涉及最底层的权重存放形态；检索增强的数据管道属于《RAG 工程化落地》，量化只影响该管道末端模型节点的内存占用；vLLM 的 PagedAttention 与连续批处理同样另有专文。

小结

量化不是把位宽调小这么简单：分组决定误差，块结构决定速度，文件格式决定元数据是否完整。GGUF 的价值在于把约定从代码搬进文件，让同一张档位表能被不同语言的环境共同遵守。选档位先确定容量上界，再按症状单向下探，每一步用相对变化而非绝对数字自检。

档位 相对体积直觉（fp16 为 1） 适用场景 已知风险
fp16 1 作校验转换正确性的参照 本地容量往往先不够
Q8_0 约 0.56 容量宽裕、要贴近基线 省下的空间与带宽收益都有限
Q5_0 与 Q5_1 约 0.38 与 0.44 质量与体积的稳妥折中 与 Q4 档的差距常小于预期
Q4_0 与 Q4_1 约 0.31 与 0.38 消费级显卡与内存受限机器 损失集中在敏感层，长文先退化
Q4_K 至 Q6_K 约 0.26 至 0.43 想同时保住质量与体积 块结构复杂，速度未必占优
Q2_K 与 Q3_K 约 0.16 与 0.22 只让大模型装得进去 复述与数值任务最先失守
