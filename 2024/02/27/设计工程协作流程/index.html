设计工程协作流程

设计与前端之间最常见的摩擦，不是某人画错或某人写错，而是双方对”同一件东西”的叫法、状态数和验收口径各说各话。本文站在前端工程视角，把设计到实现拆成一条有准入准出条件的流水线：设计令牌层、组件命名与映射契约、评审与走查节点、变更通知纪律，以及能用来自检的度量口径。读完你会得到一套可以直接抄进团队章程的清单与示例。它适合已经做过若干需求、但每次上线都要靠”肉眼比对稿子”来兜底的设计与前端同学。

设计为什么会与实现漂移

先把问题定义清楚。漂移（design drift）指的是设计意图与线上实现之间的差异随时间累积，而不是某一次明显的 bug。它的根子在于交付物与协作方式本身。设计与实现之间漂移的第一个原因是交付物是静态图：一张设计稿呈现的是一种”正确答案的样子”，但界面在真实世界里有一整套状态——加载中、空数据、部分失败、禁用、悬停、焦点、错误提示，静态图默认只画了”有数据且成功”的那一格，剩下的状态靠实现时临场脑补。

第二个原因是口头约定占主导。”这个间距和那个一样””这个按钮复用了””红色就是危险操作”这类判断散落在聊天窗口和会议口头里，没有落成可读、可检索、可对比的记录。人员一轮换，约定就丢失，实现只能凭感觉重做。

第三个原因是缺少共同词汇。设计师说”卡片”，前端说的可能是 Panel、Card、Tile、Block 中的某一个；设计师改了一个圆角，前端不知道这个圆角到底属于”某组件私有”还是”全局令牌”，于是要么不敢动、要么动了一大片。

下面三个具体漂移现象值得对照自查。其一是”同款不同值”：设计稿里有五处主按钮，颜色本应同一个语义令牌，实现时因为复制粘贴出现了 3 种略有差异的十六进制值，肉眼难辨但截图对比能抓出来。其二是”状态漏配”：设计只给了下拉框收起与展开两态，实现上线后才发现选中态、键盘焦点态、禁用态、报错态全靠前端自行发挥，走查时又发现与另一处组件不一致。其三是”令牌孤岛”：前端已经有一套 CSS 变量，设计工具里另有一套色板，两套各改各的，谁都不是事实源，改一次全站配色要人肉对齐两份。

需要说明的是，本文只谈设计与前端之间的协作流程与契约，不重复 2016 年那篇《Photoshop 切图与标注协作流程》里的切图与标注单点实现，也不展开《Web 组件化设计系统实践》所讲的组件 API、Shadow DOM 与版本发布机制——那些属于工程实现，本篇只在”契约”层面握手。

协作流程总览

把设计与前端之间的一次完整交付画成一条流水线，每个节点都带准入（进入这一格之前必须满足什么）与准出（离开这一格必须交出什么）。下面的 flowchart TD 是本文其余小节的路标：需求评审 → 设计探索 → 设计交付 → 实现 → 走查 → 上线 → 复盘。

flowchart TD
    A[需求评审] --> B[设计探索]
    B --> C[设计交付]
    C --> D[前端实现]
    D --> E[设计走查]
    E --> F[上线]
    F --> G[复盘]
    G -.-> A
    E -.->|缺陷回退| D

各节点的准入与准出条件如下（数值口径均为团队约定示例，可按团队实际调整）。

节点 准入条件 准出产物
需求评审 需求说明、验收目标就绪 前端五类问题清单已回答
设计探索 评审结论、可用令牌已确认 关键流程状态草稿
设计交付 状态齐全、命名对上登记表 可开发设计稿 + 令牌变更说明
前端实现 收到可开发稿、契约无歧义 组件 Story 与实现自检通过
设计走查 实现部署到走查环境 分级缺陷记录闭合或挂账
上线 走查阻断级缺陷清零 灰度放量、监控看板就绪
复盘 上线后一个迭代周期 度量数据、流程修订项

这张图里有两条回退线是流程的关键：走查发现阻断级缺陷时回退到实现，而不是”先上线再说”；复盘产出的流程修订项回流到下一次需求评审。一条没有回退线的流程图只是排期表，画不出协作的真实成本。

设计令牌层：把视觉决策变成可消费的契约

漂移的很大一部分来自”值”没有归属。设计令牌（design token）就是把颜色、间距、圆角、字号、阴影这些视觉决策，命名成有层级、可被代码消费的数据对象，让设计和前端共享同一份命名后的取值，而不是各自抄十六进制。

令牌要分语义层级，最常见的是三级。原始层（primitive）是”不带语义的原料”，如 color.blue.500；语义层（semantic）是”带用途的意图”，如 color.action.primary 指向 color.blue.500；组件层（component）是”某组件当前用哪个语义”，如 button.background.default 指向 color.action.primary。前端绝大多数只应消费语义层与组件层，原始层留给设计内部与主题切换。这样改一个主色只动语义层一处映射，全站随令牌更新，而不是全站的蓝都被替换——这正是”令牌孤岛”的解法。

两种消费形态各有取舍，不是非此即彼。运行时 CSS 自定义属性的好处是主题切换、深色模式可以在不重新构建的前提下整站换值，代价是编译期拿不到”令牌名写错了”这类错误。构建时 TypeScript 常量的好处是类型检查能把住关，代价是换肤要重新出包。成熟做法是两者叠加：以令牌 JSON 为源，构建时同时产出 CSS 变量表与类型安全的 TS 映射，组件样式走 CSS 变量、逻辑判断（如”这个令牌是不是语义上的危险色”）走 TS 常量。

前端与设计的协作到此落到一个可检查的口径上：任何未被登记表收录的令牌名，都算变更，都走下一节的流程。

组件命名与映射契约

令牌管”值”，命名与映射契约管”东西叫什么、状态怎么对应到代码”。这一节只讲协作契约，组件 API 的实现细节留给工程实现篇，本篇不展开。

契约的核心是一张登记表：设计稿里的组件名与代码里的组件名一一对应，且变体（variant）与状态（state）有明确的落点——变体映射为一个枚举型属性，状态映射为布尔型属性或属性组合。登记表至少包含列：设计组件名、代码组件名、变体枚举、状态清单、对应 Story 链接。下面是一份示例登记表的文字形态：

设计组件名 代码组件名 变体 variant 状态 state
主按钮 <Button> primary / secondary / ghost disabled / loading
下拉选择 <Select> default / inline error / open
信息卡片 <Card> elevated / outlined selectable / selected

命名纪律有三条。其一，登记表是唯一命名源，设计工具里的组件命名与代码里的导出名必须逐字一致；发现不一致，先改设计稿或先改代码要由最近改动的一方负责。其二，”变体”回答”这是同一种东西的哪一款”，”状态”回答”它此刻处于什么情形”；把”选中”当成变体还是状态要全团队统一，否则会出现同一个组件在不同人手里落点不同。其三，状态里的 disabled 与 loading 是互斥还是可叠加，要在契约里写死，不要留给实现临场决定。

“这到底是变体还是状态”是登记表里最容易吵架的地方，值得给一条可判定的规则，而不是各凭理解。判据是：如果这个差异由调用方在使用时就固定选定、运行中不会因用户操作而切换，它是变体；如果这个差异由运行时数据或用户交互驱动、同一实例会在不同取值间来回切换，它是状态。据此列一张对照表（示例为团队约定口径）：

场景 归类 理由
按钮是 primary 还是 ghost 变体 调用方在写代码时就定死
输入框是否处于报错 状态 校验结果在运行时改变
卡片是否可选 变体 由业务场景决定它可否被选
卡片当前是否被选中 状态 用户点击在运行时切换
表格是紧凑还是舒适密度 变体 全局设置一次选定

有了这张表，评审时遇到分歧可以照判据归类，不必争”我觉得”。归错类的代价很实际：把一个本应是状态的”选中”实现成变体，就等于逼调用方为同一份数据维护两个组件实例，交互逻辑随之分裂；反过来把变体当状态，会让枚举值膨胀、Story 目录爆炸。

评审节点与交付物标准

流程里最省钱的一步是需求评审，因为此时改动的代价还只是改一张草图。前端在这个阶段的价值不是”听懂需求”，而是把设计稿里没有明说的状态与边界问题提前问出来。下面五类问题是前端在评审阶段必须提出的清单，缺一项就意味着后面某个节点要补。

第一类是状态数。每一个交互组件都要问全：默认态、悬停态、按下态、焦点态、禁用态、加载中态、错误态、空数据态，一共几种，是否互斥。状态数不问清，实现就会自己发明，走查就会来回返工。

第二类是边界数据。文案长度极端时（一个超长的按钮标签、一段超长的用户名）组件是截断、换行还是撑破容器？数字为 0、为负、为超大值时怎么显示？列表只有 1 条和铺满 50 条时的滚动行为是否一致？这些不是”实现细节”，而是设计必须在稿子里表态的内容。

第三类是空、错、加载。这是最常被整块遗漏的一组：数据还没回来时放骨架屏还是 spinner？请求失败时是整页报错还是局部重试？完全无数据时的插画与文案由谁给？设计稿里如果只有”成功”那一态，就等于把三种状态甩给了实现。

第四类是响应式断点。同一张稿在窄屏、平板、宽屏下布局如何重排，哪些组件在窄屏下折叠、哪些换方向、哪些直接隐藏，断点阈值是否复用全局令牌。断点不是”缩放”，重排规则要逐组件写明。

第五类是动效与可访问性。过渡时长、缓动曲线、进入与退出是否成对；动效要能响应”减少动态效果”的系统偏好，键盘焦点路径要可视。此处只对动效与可访问性检查点一句带过，可访问性的工程化门禁属于另一篇《前端可访问性工程化》，本文不展开。

评审之后，进入”设计交付”节点，交付物的验收口径是：什么才算一份”可开发的设计稿”。可开发不等于好看，而是满足下面这份检查清单——逐项打勾，缺项即视为未交付。

把清单套到一个具体组件上，能看出它如何把”含糊”逼成”明确”。以”筛选区下拉选择”为例，过一遍清单会得到这样一组结论：状态至少有默认、悬停、焦点、展开、选中、禁用、报错七种，不是设计稿里画的两态；选项列表为空时显示”暂无可选项”而非空白，加载中显示占位骨架而非转圈；当搜索关键词超长时输入区省略号截断、下拉面板不换行；窄屏下面板从触发器下方展开改为底部抽屉；选中一项后面板收起、失焦时未选中则恢复默认。这七条里任何一条没在稿子上写明，都会在走查时以”实现自作主张”的形式回来。清单的作用就是让这些决定发生在评审与交付阶段，而不是实现之后。

其中”交互转移条件”是最容易被忽略的一栏。静态图能画出”展开的下拉框”，却画不出”点击选项后收起并把选中值写回、失焦时取消”这条转移。转移条件要么写进稿子的说明层，要么在评审会上口头确认后补记，否则实现只能猜，走查时又各说各话。

走查机制与变更纪律

走查（design QA，设计验收）是实现完成后、上线之前的一次系统比对，它不是”设计师打开页面随便看看”，而是一次有发起人、有环境、有记录、有分级的验收动作。先把机制约定清楚，走查才不会退化成情绪化的挑刺。

发起人默认是设计侧，但触发条件是”实现已部署到走查环境”，而不是”前端说做完了”。走查环境必须是一个数据可控、能复现空/错/加载三态的环境——在一个永远返回成功数据的本地热更新服务上走查，等于放弃了对一半状态的验收。走查按登记表逐组件、逐状态核对，核对对象就是上一节那份检查清单里的每一项。

缺陷要分级，且级别决定修复优先级与是否阻塞上线。下面是一套分级口径（阈值均为团队约定示例）：

级别 定义 修复时限示例 是否阻塞上线
阻断 状态缺失、令牌用错致对比度不达标、核心流程走不通 上线前必须闭合 是
严重 变体渲染错误、边界数据下布局撑破、转移条件不符 当前迭代内 否，但需挂账
一般 间距/圆角与稿有肉眼可见偏差、文案截断策略不一致 排入后续待办 否
建议 主观审美偏好、非规范性的微调 可选 否

分级的关键在”是否阻塞”这一列要提前对齐，而不是走查会上临时争。一条可执行的判定规则是：凡是让某个状态无法达成、或让语义令牌被绕过成硬编码的缺陷，一律至少判严重；能一眼看出与稿不一致但不影响功能与可访问性的，判一般。

走完走查不等于流程结束，变更纪律是防漂移的另一半。设计令牌的改动必须走和代码一样的评审通道：令牌变更以一次 PR 的形式提交，PR 里说清楚改了哪个语义令牌、影响哪些组件、是否包含破坏性变更。最危险的是”静默改全局”——有人为了某一个页面把 action.primary 的十六进制改了，结果全站主按钮跟着变。避免它的机制有两条：一是原始层与语义层分离，改语义要显式提交并触发受影响 Story 的视觉回归；二是把”谁动了全局令牌”纳入 PR 审查清单，评审者据此重点看。

破坏性变更要有提前量与迁移提示。当一个语义令牌被拆分或重命名（例如把 action.primary 拆成 action.primary.bg 与 action.primary.text），要给使用方留出一个迭代周期的窗口（提前量为团队约定示例），期间旧名保留并标注废弃、输出告警，PR 描述里附上从旧名到新名的迁移对照，让两端（React 与 Vue）有时间为自己仓库补迁移。这条纪律和跨团队协作里”接口先加后删”的思路一致，但本文只把它用在令牌这一层。

单一事实源、度量与反模式

组件文档——通常是 Storybook 7.x 这类工具——在协作里的角色，是把设计稿从”静态图”升级为”可交互验证物”。设计不再只交付一张图，而是和前端约定：每个登记在册的组件，都在文档里有对应每一状态的 Story，设计师的验收可以对着 Story 而不是对着还在开发中的业务页面。这样”状态齐全”这件事就从口头承诺变成了看得见的目录项。

落地方式是把 Story 当作状态的合同。契约里的每个变体与状态，对应文档里一个可点开的条目；设计走查时逐条点开核对，缺一个 Story 就是缺一个状态。可访问性检查也能挂在这层：焦点态、减少动效降级在 Story 里各给一个条目，验收时一并看。这里只讲协作机制——文档如何承担”设计可交互验证”的角色；组件 API 本身的实现、Shadow DOM 与发布机制仍归工程实现篇，本文不展开。

把 Story 挂进 CI 还能反过来强化变更纪律：以 Story 目录为基线跑视觉回归，一旦某个全局令牌被误改，受影响组件的 Story 截图会集体偏移，流水线立刻把它拦在合并之前。这正是”静默改全局”最难防、也最值得用自动化去堵的地方——人工走查能抓显眼的偏差，抓不动”三处主按钮蓝值差了 2 个色阶”这种细节，而基线截图可以。于是设计交付、走查、变更三条线在同一份 Story 目录上交汇，单一事实源才名副其实。

度量不是为了考核人，而是为了让”流程到底哪里在漏”变得可见。下面几个指标的定义与采集口径值得团队约定（所有数值目标都是团队约定示例，不是行业基准，不可横向比较）：

指标 定义 采集口径示例
返工率 因设计/契约歧义导致的返工提交数 ÷ 迭代总提交数 提交信息打 rework: 前缀，脚本计数
走查缺陷密度 一次走查记录的有效缺陷数 ÷ 走查覆盖组件数 走查记录表逐条落表后统计
需求变更次数 进入实现后设计/需求回改的次数 每次回改在工单上留一条变更记录
静默令牌变更 未经 PR 评审的全局令牌改动次数 令牌构建钩子比对来源 PR

这些指标要盯趋势，不盯个人。用返工率去考核某个前端”是不是手艺差”，只会逼人把问题藏起来——数据一旦变成绩效考核的输入，采集就会失真，度量就失去意义。正确的用法是在复盘会上看”这一迭代走查缺陷密度为什么升高”，把答案指向流程（是不是评审阶段状态数没问全），而不是指向某个人。

最后是四类反复出现的反模式及其修复，它们和本文前面每一节都对应。

其一，”设计稿即最终答案”：把一张成功态静态图当成全部真相，实现被迫脑补其余状态。修复是交付前用检查清单把状态、边界、转移条件补齐，静态图降级为”意图示意”。其二，”前端被动接稿”：前端只在收到终稿后才参与，问题积累到走查才暴露。修复是把前端拉进需求评审，用五类问题清单在最早期发言。其三，”令牌与代码两套真相”：设计工具一套色板、代码里另一套变量，谁都不是源。修复是建立三级令牌层，让构建产物成为唯一被消费的一方。其四，”把协作问题当技术问题”：明明是命名没对齐、状态没约定，却归咎于”前端没还原好”或”设计师不懂实现”。修复是用登记表与走查分级把分歧落到可核对的口径上，让讨论针对”哪一格的哪个状态”，而不是针对人。

阶段、产出与责任

把整条流水线收束成一张表，方便直接抄进团队章程。阶段对应输入与产出，责任人指”对这一格准出负责的人”，准出条件是离开该阶段的硬门槛。责任人角色名称为示例，按团队实际映射。

阶段 输入 产出 责任人 准出条件
需求评审 需求说明、验收目标 五类问题已回答 前端 状态/边界/断点无悬空问题
设计探索 评审结论、可用令牌 关键流程状态草稿 设计 覆盖成功/空/错/加载四态
设计交付 状态草稿、登记表 可开发稿 + 令牌变更说明 设计 检查清单逐项打勾
前端实现 可开发稿、契约 组件 Story + 自检 前端 每状态 Story 可点开
设计走查 走查环境实现 分级缺陷记录 设计 阻断级清零、严重级挂账
上线 走查通过产物 灰度放量与看板 前端 令牌变更均经 PR
复盘 上线后一个迭代 度量与流程修订项 全体 修订项回流评审清单

这张表的价值在于每一格都能被追问”你准出了吗”。漂移往往不是某格做错了，而是某格根本没有准出条件，于是可以悄悄跳过。

小结

设计与前端的漂移，本质是”共同词汇”和”验收口径”的缺失，而不是手艺问题。本文给的解法可以归纳为四件事：用三级设计令牌把视觉决策变成有归属、可消费的数据；用组件命名与映射契约让设计叫法和代码叫法一一对应，并把状态固化成同一份两端实现都遵守的规则；用带准入准出的流水线（评审、交付、走查、变更、复盘）替代口头约定；用只盯趋势、不考核个人的度量让流程的漏洞可见。落地时不必一次全上，建议先从”评审五类问题清单”和”交付检查清单”两张表起步，这两张表成本最低、见效最快，也最能暴露真正的问题在哪个环节。
