Java 性能调优实战

Java 服务的性能问题，多数不是参数不够多，而是顺序不对：没建基线就改配置，没看业务指标就下结论，没做可复现测量就汇报数字。本文给出一套可复用的方法与工具链口径：指标定义、基准测试、火焰图阅读、工具选择，再收束到三类高频优化与调优登记表。

调优顺序与指标口径

先建基线，再谈改进

第一步不是打开参数列表，而是确定当前行为。缺了基线，改完参数得到的只是变化，不是改进。基线由四件事组成：

顺序上先量业务指标再看进程指标：前者决定值不值得优化，后者只回答卡在哪一段。P99 本来就达标时，CPU 曲线再难看也不该动线上配置；P99 抖动则常同时指向分配速率、外部依赖延迟、线程排队、容器限流等多个因素。一句划界：GC 与内存机制见《Java JVM 内存模型与 GC》，事故定位见《Java 服务线上问题排查》，本篇只讲方法与工具链。

吞吐、平均延迟与百分位延迟

吞吐是单位时间完成的请求数，延迟是单个请求的耗时分布，两者不能互相代替。平均值只刻画重心，会把长尾抹平：99 个请求耗时 5 ms、1 个耗时 500 ms，平均值依然很小，但那 1 个用户确实在等，所以 SLA 通常约定 P99 与 P999。

关键口径是：分位数不能跨窗口做算术平均。P99 不是线性可加的统计量，把十个小窗口的 P99 取平均，等于先把每窗口的长尾压成一个标量再平均，偶发尖峰被稀释，真实整体长尾通常更高。正确做法是合并原始样本后再算，或者合并可加的直方图桶计数。线性插值的实现如下：

为什么用 JUnit 跑性能测试不成立

缺的不是更仔细的写法，而是控制手段：预热轮次、独立进程、重复迭代与统计、结果消费、参数扫描。

JMH 的四个关键设计

JMH 的思路是四点。先预热再测量：预热迭代让分层编译把热点稳定下来，测量迭代才开始计数。用 fork 隔离：每轮起新 JVM，基准之间不互相污染，也拿到独立的 JIT 与堆状态。强制消费结果：返回值写进 Blackhole，编译器无法把它当无用计算删掉。参数外置：用 @Param 把输入规模变成运行时才知道的值，防止常量折叠。骨架只写注解与结构，不预设跑分：

-prof gc 把分配速率与 GC 次数附在结果里，很多“算法变慢了”其实是每轮多分配了一个数组。三条纪律：基准不在生产机器或共享集群上跑；一次只改一个变量；报告写清负载形态与并发档位，绝对数值一律标注为示意值。

火焰图怎么读，以及它的偏差从哪来

采样式剖析在做什么

插桩式剖析给每次方法调用加计数，精确但开销大，只在隔离环境针对少数方法开；本文讲的是采样式——按周期抓当前线程栈，用统计近似热点，开销低到能在生产短暂开启，JFR 的执行采样事件与常见火焰图工具都属于这一类。

它有两个固有偏差。其一是安全点偏差：传统方式只能在安全点读到真实栈，而安全点位置由字节码布局决定，某些循环出口更容易停住，于是这些行被过度表示、真正耗时的区间反而被低估；缓解办法是用基于信号、靠帧指针或栈表重建栈的采样器。其二是采样间隔：太短，信号处理与栈展开本身开始影响被测程序；太长，短方法采不到，只剩大块结构。做法是先粗后细：粗粒度定方向，再对单个方法缩短间隔复采。

读图的四步

横轴不是时间轴，而是同层兄弟节点按宽度排序后的位置，纵轴是栈深度。色块宽度代表连同子树占采样总数的比例，即耗时或分配量占比，与调用次数无关：被调用百万次、每次极快的方法可能只有很窄一条。

读图分四步。一看最宽的平顶，叶子帧自身宽度大的地方才是消耗点，被厚叶子顶着的小帧只是路过。二看形状，一根通天的柱子说明串行瓶颈集中，一层矮胖块说明成本分散在许多调用方，此时优化被调方收益有限。三分模式对比，CPU 图里宽的方法未必在分配图里宽，分配图对“GC 压力大”指向性极强。四区分自身宽度与子树总宽度，别把调用方的宽当成它贵。图给的是方向不是结论，判断要回到可重复测量。

工具链：什么时候用哪一件

进程与 GC 计数：jps、jstat

jps 把主类名映射成 pid，脚本里比手动记 pid 可靠。jstat 看计数器与区域用量的时间序列，要点是看趋势不看单帧：连续十几帧，看老年代占比是否阶梯式上升、回收次数与耗时是否同向增长。GC 机制见《Java JVM 内存模型与 GC》。

线程快照：jstack 与 jcmd Thread.print

jstack 抓瞬间线程栈，回答此刻谁在等谁。单次快照只能作参考，正确做法是十几秒内连抓三份：同一段等待三次都在同一行才算嫌疑。栈里自带死锁检测，遇到 Found one Java-level deadlock 直接读环上的持锁与等锁关系；定位 CPU 高的线程时，把操作系统线程号转成十六进制再匹配 nid。线程池与锁的实现见《Java 并发编程：JUC 核心》，本篇只把线程当待排查因素。

堆：直方图、转储与支配树

先粗后细：类直方图便宜，用来判断哪类对象占大头；堆转储是完整现场，代价是进程停顿加接近堆用量的文件，导之前先想清楚要看什么，之后离线分析。MAT 的价值在支配树与保留大小：Shallow Size 只是对象自身占用，Retained Size 是“回收它能连带释放多少”，只有后者衡量一个引用的真实代价；支配树回答谁把它钉住了，配合泄漏嫌疑报表能快速锁定可疑集合与类加载器。几 GB 的转储还是交给批处理工具稳。

持续记录：JFR、jcmd 与 Arthas

JFR 是适合生产的那一件：事件在 JVM 内以极低开销写入环形缓冲区，可长期滚动记录，出问题时只导出最近窗口，不必为抓一次现象提前重启加参数。它覆盖分配、CPU 采样、锁等待、GC 周期、安全点停留、编译活动与方法级事件，正好对应本篇各节要看的证据；jcmd 是配套入口。不便重启又只想看某个方法的入参与返回耗时时，Arthas 这类在线诊断工具可做方法级观察，代价是自身占用资源，窗口结束务必清理增强的类。

堆外、方法区与容器内存口径

堆外内存容易被漏掉，因为堆转储看不见它。直接内存（ByteBuffer.allocateDirect 那一类）受 -XX:MaxDirectMemorySize 约束，用量只在缓冲区池里可见：

方法区方向的口径是类与类加载器：看元空间已用容量与已加载类数量是否只增不减，来源是 jstat -gcmetacapacity、jcmd GC.heap_info 或 JFR 的类加载事件，分区机制见《Java JVM 内存模型与 GC》。

容器里的关键是 -Xmx 只约束堆，不等于进程占用：常驻内存还要加元空间、代码缓存、线程栈、直接内存、GC 与 JIT 的内部结构以及分配器碎片。所以要给堆外留预算——团队约定示例是 -Xmx 取容器 limit 的 60%75%，堆外与页缓存占剩余 25%40%，再按最大线程数预留栈；这是约定不是事实，落地前用自己的常驻内存曲线校准。

三类高频优化的正确做法

字符串与拼接

编译器会把常量之间的 + 合成，单表达式里用 + 完全正常，可读性还更好；问题在循环里逐轮 +，每轮都产生新构建器与新字符串，代价随长度平方级增长，这时换 StringBuilder 并给出初值容量。跨线程不要共享同一个构建器；日志消息先按级别短路再拼接，否则字符串在被丢弃之前就已经分配完。

装箱与热路径容器选型

判断口径只有一条：这段代码每请求跑多少次、每次产生多少临时对象。热路径上以 Integer、Long 作键值会同时带来装箱对象与额外比较，量大时先看分配火焰图再决定换不换；键是基本类型且规模固定时，数组往往比任何映射都合适。Stream 与 Optional 在低频调用里买到清晰度，在每请求上万次的循环里就变成每轮的临时对象。集合内部实现见《Java 集合框架与源码解析》，本篇只做选型判断。

日志

同步 appender 的开销有两段：取锁与落盘 IO，两者都会进入 P99，磁盘抖动时尤其明显。异步 appender 把这两段挪到后台线程，代价是三件事：队列有上限，写满后要么阻塞要么丢弃，丢掉的往往是异常时刻最需要的行；上下文（如 MDC）必须在提交任务时快照，否则后台线程打出的行会串号；进程被强杀时缓冲区可能来不及刷盘。所以先做降噪（级别、采样、单行长度）再谈异步，异步上线前演练一次强杀，确认团队能接受多大的丢失窗口。

GC 与运行时参数：从目标倒推

先写目标再选收集器，机制见《Java JVM 内存模型与 GC》，这里只讲决策顺序。目标要成对给出：停顿预算，即单次回收最长能接受多久；吞吐下限，即允许多少 CPU 用于回收。停顿敏感且存活集偏大的在线服务朝低停顿选，吞吐优先的批处理朝吞吐取向选；只写“要低延迟”而没有数字，任何参数都无法验证。

JIT 与预热：前几分钟为什么慢

代码先由解释器执行，达到热度阈值后进 C1（编译快、优化轻），热点再进 C2（激进内联与假设性优化）。分层编译意味着同一个方法在进程生命期内速度会变，假设失败还会去优化、退回解释执行。于是新实例天然慢，启动后前几分钟的 P99 明显高于稳态（示意值）；滚动发布同时推上多个冷实例，冷 JIT 叠加类加载与建连，形成一段可预期的劣化。应对办法是把它当成发布流程的一部分：

小结

本篇没有给出“应该设成多少”的答案，因为可复用的只有流程：先定基线与指标口径，再用 JMH 与火焰图拿到可重复证据，然后一次改一个变量，最后把结论写进登记表。工具按问题形状而非熟悉度选择：计数看 jstat，快照看 jstack，现场看转储与 MAT，长期观察看 JFR 与 jcmd。
