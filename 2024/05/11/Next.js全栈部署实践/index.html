Next.js 全栈部署实践

一个 Next.js 项目在开发机上跑通，只完成了工作量的三分之一；把它变成能被网关、容器编排、CDN 和告警系统长期照料的服务，才是全栈框架真正难的部分。本文面向要把 Next.js 14 应用放到自有服务器或容器平台上的同学，聚焦构建产物、镜像瘦身、环境变量与密钥、进程与并发、缓存与 CDN 协作、发布回滚、观测告警这些部署侧议题；框架本身的组件与路由写法不在这里展开。

部署形态要先厘清

部署一个 Next.js 应用，第一步不是写 Dockerfile，而是确认这个应用需要哪些运行期能力，因为能力清单直接决定形态，形态决定运维成本。按承载方式划分，常见形态有四种：纯静态导出、常驻 Node 服务器、容器化的 Node 服务器、Serverless 或边缘函数。前两种与第三种并不是同一维度的对比——容器只是交付封装方式，里面跑的仍然是 Node 服务器；而第四种把长驻进程切成按请求启动的函数实例，是真正改变了运行模型。

纯静态导出把路由在构建期全部渲染成 HTML 与 JSON 文件，产物可以直接扔进对象存储加 CDN，不需要任何服务器。它的代价是运行期没有任何 Node 进程，因此所有依赖服务端执行的能力都会失效：API 路由、中间件、Server Actions、按请求动态渲染的页面、增量再生的后台重渲染任务都不存在。能用的是预渲染页面、客户端交互与静态资源长缓存。需要动态能力的路由会让构建直接报错，不会把问题留到线上。

常驻 Node 服务器是能力最完整的形态：动态渲染、流式响应、API 路由、Server Actions、中间件、缓存失效调度都由一个 next start 进程承担。代价是这个有状态进程要管 CPU 与内存、要处理优雅关闭、要保证多副本行为一致。把同一份产物打进镜像就是第三种形态，运维模型与跑在虚拟机上没有本质区别，只是把依赖锁定与升级节奏交给了镜像层。

Serverless 与边缘形态按路由把应用切成独立函数，扩容由平台负责，账单按调用计费。它的运维负担最轻，约束却最多：单次执行有时长上限，请求体大小受网关限制，Node 标准库只能使用子集，冷启动直接抬高首字节时间，实例之间不共享内存所以进程内缓存一律不生效。边缘运行时比函数更窄，可用接口与连接数都受限，渲染位置如何选择、边缘能承担哪些逻辑属于另一篇讨论的主题，本文只取它对部署的一条硬约束：源站与边缘的缓存要分开设置，且边缘实例上的密钥必须是运行期注入的短生命周期凭据。

把四种形态放在一起对照，能力边界一目了然：

纯静态导出 不支持 不支持 不支持 不支持 不支持
Node 服务器 支持 支持 支持 支持 支持

本文后续配置与脚本都以容器化 Node 服务器为主形态展开，它既保留全部服务端能力，又能被编排系统标准化托管。至于 SSR、SSG、ISR 之间怎么取舍、revalidate 的语义细节，属于渲染模式专篇的内容，本文只在缓存头与失效策略这一层与它衔接。

看清构建产物再谈瘦身

next build 的输出集中在 .next 目录，部署侧要理解三类内容各自的职责。第一类是服务端运行代码，包含按路由切分的服务器端包、中间件产物与若干份清单文件；清单描述请求路径到处理方式的映射、预渲染页面的位置、服务端引用之间的关系，运行期靠它们在进入渲染前完成路由决策与重写。第二类是静态资源，包含带指纹的脚本、样式、字体和图片，不需要服务器参与，可直接由 CDN 长期缓存。第三类是构建期缓存，存放增量构建与渲染产物的中间结果，只服务于下一次构建，不应出现在生产镜像里。

全量拷贝 .next 会让镜像混入构建缓存、source map 与未被任何路由引用的模块，体积动辄数百兆。standalone 模式正是为此存在：开启后，构建结束时做一次依赖追踪，把当前入口真正 require 到的模块收集到一个自包含目录，附带一个可直接启动的入口脚本。产物只含服务端代码与最小依赖集，镜像里的依赖层能缩小一个数量级，也省掉了容器内重装依赖的时间与不确定性。

standalone 目录有一个容易被忽略的性质：它按入口裁剪，只含服务端运行需要的依赖，客户端资源仍靠构建期落盘的静态目录，因此拷贝动作至少要三段。下面是一份可直接使用的多阶段 Dockerfile，基于 Node 20 主线。

三段拷贝各有理由。standalone 目录提供入口脚本与裁剪后的服务端依赖；.next/static 不在 standalone 内，不补齐就会出现脚本 404；public 同理，运行期不会从项目根读它。运行阶段不需要再拷一份完整的 node_modules，这正是 standalone 的价值；只有未被追踪的原生模块才要补拷贝，并把它显式加入外部包清单。

compress: false 的取舍要说明：前面已有反向代理或网关做 gzip 时，应用在进程内再压缩一次就是重复的 CPU 开销，只有源站直连用户才保留应用侧压缩。外部包清单在这里的作用是告诉构建器不要打包原生模块与带动态 require 的库，否则依赖追踪会把它们漏掉，表现为运行期找不到模块的启动失败。

依赖层与源码层分离，是为了让镜像构建复用层缓存：只要锁文件不变，安装依赖这一层就命中缓存，源码改动不会触发重装。构建缓存则不同，.next/cache 属于构建器缓存，与镜像层是两套机制。BuildKit 的 cache 挂载能明显缩短重复构建，但它不随镜像导出，跨任务复用要把该目录显式落到 CI 的缓存存储。CI 侧常见做法是两级缓存：依赖目录按锁文件哈希作 key，构建缓存按分支名作 key，分支内增量复用、跨分支不复用，避免把不相关的旧产物带进新构建。至于在多个包之间共享产物的 monorepo 远端缓存，属于构建编排范畴，本文不展开。

环境变量、密钥与版本基线

Next.js 的环境变量有一个必须写进团队规范的性质：只有带 NEXT_PUBLIC_ 前缀的变量会被替换进客户端代码，而这个替换发生在构建期。构建器在打包客户端 bundle 时把 process.env.NEXT_PUBLIC_* 按字面量内联，值在产物生成的那一刻就被固化，运行期再怎么改容器环境变量都不会生效，想让前端读到新值只能重新构建。由此得出两条结论：希望运行期可调的配置绝不能加这个前缀，也不要在客户端读它，服务端渲染阶段读的变量才是每次请求现取运行期环境；任何带前缀的变量都应按公开信息对待，它已经躺在下载的脚本里。

密钥的正确处理方式是只让它出现在服务端进程的环境里。数据源凭据、内部服务令牌、签名私钥统一放在无前缀变量中，由部署平台的密钥管理能力在容器启动时注入，不写进镜像层，不进版本库。.env 系列文件同理：next build 会读取 .env.production 等本地文件，把它们拷进镜像等于把构建期秘密与运行期配置混在一起，dockerignore 要显式排除。构建期只注入公开配置，例如站点地址、埋点开关，这类值一变就要重新构建，因此应列入构建参数而非运行参数。

健康检查接口要满足三点：不走缓存、不做鉴权、不依赖下游服务。就绪探测与存活探测可以共用这个路径，但存活探测不应因数据库抖动而返回失败，否则一次下游故障会引发整批副本重启，把可用性问题放大成雪崩。

监听地址与端口是容器化部署里最常见的启动失败原因。standalone 产物里的入口脚本按 HOSTNAME 与 PORT 两个环境变量决定监听位置，默认只接受本机连接，在容器里表现为端口映射正常但外部一律连不上。因此镜像里必须显式设置 HOSTNAME=0.0.0.0，端口交给平台注入的 PORT 覆盖，别把 3000 硬编码进启动命令。

版本基线上，2024 年年中的稳妥选择是 Node 20 主线：它在 2023 年 10 月底转入长期支持，App Router 的构建与运行都在其上验证过。Node 18 仍在维护窗口内，属于存量项目的现实基线，新部署没有理由选它。Node 22 于 2024 年 4 月发布，当前是 Current 线而不是 LTS，按官方节奏要到当年 10 月才转入长期支持，此时把它放进生产镜像只适合作为预验证。镜像标签要写具体，node:20-alpine 优于 node:alpine，固定补丁版本或镜像摘要优于浮动大版本，否则基础镜像的静默升级会把小版本变化带进所有副本。

工程一致性靠三处对齐：package.json 的 engines 字段声明允许的主版本范围，本地版本管理文件写入同一主版本，锁文件与镜像的 Node 主版本一致并且用 npm ci 安装。语言侧按 TypeScript 5.4 主线配置，target 与 lib 要和实际运行环境匹配——构建目标写得比运行环境新，编译期不报错，运行期才出现语法不支持。

进程模型、资源限额与优雅关闭

一个 next start 进程是单进程的：一个 Node 实例承载全部路由的渲染、API 处理与中间件。好处是模型简单、状态集中，坏处是事件循环上任何一段长任务都会拖慢同进程内所有请求。服务端渲染本身就是 CPU 工作——序列化组件树、拼装 HTML、执行流式写入都在这一个线程里；再叠加同步的大 JSON 解析、图片处理或正则回溯，就形成排队放大：一个慢请求让同时段所有请求的首字节变差。这类问题的特征是副本 CPU 并不饱和但延迟明显升高，瓶颈在排队而非算力，判断依据是事件循环延迟而不是 CPU 使用率。结论是把重活搬出请求路径，交给独立的工作服务或队列，Web 进程只做渲染与轻量数据组装。

资源限额要区分内存与 CPU。内存给硬上限，用来保护节点；容器内存上限与进程堆上限之间要留余量，因为 Node 的常驻内存不止 V8 堆，还包括外部缓冲与原生模块占用，只按堆设置推断会低估。CPU 上限要谨慎：过紧的配额让进程被周期性节流，而渲染恰好对时间片的连续性敏感，节流表现为尾延迟毛刺。更稳的做法是内存设硬限、CPU 只设宽松上限、把副本数当作主要容量调节手段。数值必须来自压测与线上观察，本文给出的都是示意值：单副本 1 至 2 核、1 GiB 至 2 GiB 内存起步。

副本数与自动扩缩的判定依据有三条。第一条是延迟分位：高百分位首字节时间随并发明显劣化，说明单副本已进入排队区。第二条是事件循环延迟与内存水位，它们比 CPU 使用率更能反映 Node 进程的压力。第三条是下游连接预算：副本数乘以单副本连接池上限不能超过数据库允许的最大连接数，否则扩容本身成为故障源。基于 CPU 的比例扩缩是简单可用的默认（示意值：目标 60%），但要给渲染型服务设最小副本数，避免低谷期缩到无法吸收突发。

优雅关闭决定发布是否平滑。收到终止信号后的正确顺序是：先从负载均衡摘掉本副本、停止接受新连接、等在途请求完成、最后释放数据库连接再退出。编排系统要给足排水窗口，默认的 30 秒对包含流式响应与长查询的页面可能不够；同时要知道信号不会自动送达应用：容器里以 1 号进程运行的入口如果不是 init 程序，可能收不到终止信号，副本只能被强制杀死，在途请求全部失败。用轻量 init 程序做信号转发是必须补上的一步。

这段代码的适用边界要讲清：只有自定义入口才需要自己写排水，next start 的进程与信号行为属于框架内建，部署侧能做的是把排水时间窗与摘流量顺序配置正确。另外，任何把连接状态存在进程内存里的做法都会在多副本下失效，会话与限流计数需要外置到共享存储。

缓存分层与 CDN 协作

部署侧的缓存设计要从“哪些产物可变”开始。构建输出的脚本、样式与字体文件名里带内容哈希，同一份文件永远对应同一个地址，可以放心给最长缓存；public 下的文件不带哈希，改内容不改地址，必须用较短缓存或自行在地址上附加版本参数。把静态前缀指向 CDN 域名、源站只负责 HTML 与接口，是带宽与首字节都受益的第一步，前提是这个地址在构建期就确定。

HTML 与数据响应要分层设置 Cache-Control。动态渲染的文档不应在边缘缓存，否则会把与请求上下文绑定的内容串给别人；预渲染与增量再生的文档则要尽量让边缘承担重复访问，每个请求都回源等于放弃这类页面的性能优势。可行的分层是文档给 public, max-age=0, s-maxage=60, stale-while-revalidate=300, stale-if-error=600 这一类组合：浏览器不缓存而边缘可复用，过期后先返回旧副本并后台回源，源站出错时继续用旧内容兜底。接口侧按数据是否含用户态区分，公开数据给长缓存，用户态数据只允许 private, no-store。再验证时间的语义与写法属于渲染模式专篇，本文只强调一条部署侧结论：源站再生完成后，边缘那份旧文档也必须失效，否则用户可见的更新时效由边缘的 s-maxage 决定，而不是由源站的再生节奏决定。这是排障时最常被误判的地方——日志显示再生成功，用户看到的仍是昨日内容。

图片优化端点对部署有三条硬要求。第一，它是运行期的服务端接口，网关必须完整透传带查询串的请求，边缘缓存的键要包含源地址与宽度等参数，否则不同尺寸互相污染或每次都回源。第二，生产镜像里要安装原生图像处理库并把它列入外部包清单，否则优化能力在容器里退化，表现为大图直出与内存上涨。第三，远程图片必须走域名与路径模式白名单；允许任意地址，这个端点就变成可对内网发起请求的开放代理，安全评审不会放过它。

未列入白名单的地址会被直接拒绝，表现为优化接口返回失败而非降级显示。这类问题只在生产出现、本地不复现，务必把白名单变更纳入发布检查。

API 路由与上传的部署侧约束

接口与表单动作把应用变成了真正的后端服务，也就把数据库连接、请求体大小和临时文件这些传统服务端问题一并带进来。最先到来的容量问题是连接数：每个副本都有自己的连接池，总连接数等于副本数乘以单副本池上限，从 2 个副本扩到 12 个的过程就是数据库连接被打满的过程，而最大连接数是固定预算。部署侧要把三者写在同一张容量表里：先确定数据库允许的连接总量，再倒推单副本池大小，最后才决定最大副本数；并发不够而连接预算也不够时，在应用与数据库之间加连接池代理，让等待发生在池层而不是让数据库拒绝连接。函数化部署会放大这个问题：实例可以瞬间扩出上百个且每个都尝试建连，此时外部连接池是前提而非优化项。

冷启动的影响不止是首次响应慢。新副本在接流量之前要建立到数据库的传输层连接、完成凭据拉取、加载较大的原生模块；如果这些动作写在模块顶层，进程启动会被外部依赖拖住，就绪探测随之超时，编排系统判定副本不健康并反复重启，形成启动与依赖互相拖垮的循环。可执行的做法是延迟建立、复用连接、把凭据随环境注入而不是首次请求时去远端拉取，再配合最小副本数或预热请求，让突发流量落在已经准备好的进程上。

超时必须沿链路单调递减。网关等待时间、应用处理时间、数据库语句时间若反过来设置，就会出现用户早已收到错误、应用仍在原地等数据库的场面，连接与进程被无意义的请求占住，尾延迟随并发恶化。示意值可以这样取：网关 30 秒，应用给单次请求 25 秒预算，数据库语句上限 10 秒，并把 keep-alive 空闲时间对齐到网关之下，避免边缘复用一个源站已关掉的连接。体大小限制来自三个位置：接口体解析有默认上限，表单动作的体上限独立配置，反代与网关还各自有一道，其中最小的那个决定用户能上传多大文件。只调网关不调应用，表现为服务端拿到被截断的请求体并报出难定位的解析错误；只调应用不调网关，表现为明确的体过大状态码。

上传请求以 multipart 编码到达，网关与应用都要按边界解析它；关闭请求缓冲、让请求体流式抵达应用，是大文件场景减少内存峰值的关键开关。无状态多副本还要处理临时文件：不要把上传内容先写进容器本地磁盘再交给后续任务，副本随时可能被销毁、任务也可能落在另一个副本上，读写本地磁盘等于制造只在单实例成立的状态。正确路径是在请求内把字节流直接写入对象存储，只把对象键与元数据交给后台任务；文件很大时让客户端用带签名的地址直传存储，应用只签发凭据与校验规则。表单动作写入完成后要顺带失效相关页面的边缘缓存，否则用户提交成功却看不到变化。

发布、灰度与回滚

发布的前提是产物可辨识。把版本标识在构建期注入进程环境，再让健康检查、错误日志与响应头都携带同一个标识，运维才可能在故障时回答“这个副本跑的是哪一版”。注入用构建参数，它是编译期内联的，正好与运行期可调的配置互补。

不可变性有实际收益：同一个标签的镜像永远对应同一份字节，回滚就是把流量切回旧标签，不需要重新构建，也就不会引入“回滚时构建失败”这种二次故障。灰度按两种方式做：按流量比例，让网关把小百分比的新请求定向到新版本副本；按请求头，把内部工具或测试账号固定路由到新版本，便于验证而不影响真实用户。两种方式的前提都是新旧副本同时在线，因此数据库结构变更必须向后兼容，顺序固定为先做迁移、再灰度代码、最后清理旧字段。反过来做，旧副本在流量回切时会面对不认识的结构，回滚能力当场失效。

阶段 检查项
构建 锁文件与镜像 Node 版本一致；standalone 产物启动自检通过
预发布 健康检查返回新版本标识；关键页面渲染状态码与耗时对比基线
灰度 1% 到 10% 递增，观察 5xx 比例与首字节分位；边缘缓存键无污染
全量 保留旧版本镜像至回滚窗口结束；迁移脚本可重入

构建加速方面，14 主线里的 turbo 仍是实验性开关，不作为发布流水线依赖项，流水线只信任当时稳定的构建路径。

观测与告警

请求日志最少要包含这些字段：链路标识 traceId、路由、渲染类型、状态码、总耗时与首字节耗时、副本标识与版本标识、体大小。链路标识由网关生成并透传，服务端日志与前端错误上报共用同一个值，才能把一个会话里的多次请求串起来。渲染类型字段的价值在于分流告警：增量再生路径上的偶发慢请求与动态路径上的持续慢请求，处理方式完全不同。

错误上报在生产上还要处理源映射文件。客户端报错的堆栈指向打包后的名字，没有映射就无法定位；而把映射文件随产物发布等于公开源码结构，正确做法是在构建期上传到内部错误平台，再从镜像与静态目录里剔除。

指标至少三条：首字节分位、渲染耗时、5xx 比例（示意值：首字节 P75 不超过 800 毫秒、P95 不超过 2 秒，5xx 比例超过 1% 触发告警）。阈值不要照抄，应按服务自身的历史基线设定；对服务端渲染而言，事件循环延迟与内存水位要单独看，它们先于用户可见指标劣化，是提前的信号。告警要按期分开设：构建期告警关注产物大小、构建时长、依赖与镜像扫描结果，通知研发；运行期告警关注可用性、延迟与副本重启次数，通知值班。两类混在一个群里会互相掩盖，最终结果是没人响应。

小结

部署形态决定能力上限，能力上限决定运维成本，这个顺序不能颠倒。先列出应用必须保留的服务端能力，再决定是静态导出、常驻进程还是函数化；然后把产物压到最小、把配置按编译期与运行期切开、把连接与超时沿链路排布、把版本与回滚做成可执行的动作，最后用日志与指标把这一切变成可观察的系统。本文数字均为示意值，落地时按自身基线重估。四种形态的能力与成本对照如下，可作为选型收尾：

部署形态 支持的能力 运维成本 适用场景
纯静态导出 预渲染页面与纯客户端交互 最低，无需进程与容量管理 文档站、营销页、内容变更少
Node 服务器 全部服务端能力 中，需自管进程与扩容 内部系统、中小流量业务
容器化 Node 服务器 全部服务端能力 中高，涉及镜像、编排与信号处理 多环境交付、需要灰度与回滚
Serverless 与边缘 服务端能力受限，冷启动与体大小受限 低到中，平台托管 流量起伏大、地域分散
