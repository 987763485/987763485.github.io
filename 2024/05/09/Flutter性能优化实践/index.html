Flutter 性能优化实践

这是一篇浅要篇，只谈 Flutter 里上手就能用的性能手段，不进渲染引擎的内部机制，也不与其他技术栈对比，适合有半年以上 Flutter 业务开发经验、正被掉帧、白屏或启动慢困扰的读者。读完应该能按症状判断该看哪条曲线、先改哪类代码，并用可复现的对比实验验收效果。

先定义症状，再决定动手

第一步不是改代码，而是把”慢”翻译成可观察的信号。五类症状各有各的看法：掉帧看每帧的构建时间与栅格化时间是否稳定落在帧预算线内，抖动比平均值更能说明问题；卡顿通常是某次交互里冒出一两个长帧，要关联到具体手势或路由；白屏是首帧迟迟不上屏，往往和启动流程、首屏依赖与资源解码有关；启动慢要拆成引擎启动、Dart isolate 引导与首屏数据请求三段分别计时；内存增长看反复进出同一页面之后常驻内存是否单调上升，而不是单页峰值。

模式选择决定结论是否成立。profile 保留了时间线、热重载与调试接入，便于定位方向，但帧时间不等于设备上的真实表现；release 才是交付出去的产物。本文口径是：用 profile 复现问题，写进汇报的数字必须在 release 包上重测，不要拿 profile 数据下结论。

重建是头号成本

多数能感知到的卡顿，最后都能归到”build 被调用的次数太多”。build 是个纯函数，但对象创建与比对的开销并不为零；长列表和动画里每帧重建十几层子树，是最常见的劣化来源。所以第一条手段是把不变的子树变成编译期常量。const 构造函数最直接：字段都是 final、构造参数能在编译期确定，就可以声明 const 构造；调用处加上 const，相同参数的实例被复用，这一子树也就跳过重建。前提是参数在编译期可求值，因此要把样式、尺寸、间距、固定文案抽成顶层常量或 static const，而不是每次在 build 里写字面量。

对照来看，改动没有引入任何缓存框架，只是把能在编译期确定的东西挪到了编译期。另一个习惯是不要在 build 里做计算：格式化日期、排序列表、拼接 EdgeInsets 与 TextStyle、给每个子项新建回调闭包，都会让子树失去常量化资格，这类代码在列表里还会执行成百上千次。把计算挪到构造函数或状态字段里，收益通常比事后加缓存更直接。

收紧状态范围，重建范围才会小

重建范围常常不是写出来的，而是被状态位置决定的。setState 写在最外层的 StatefulWidget 上，整页就要重新 build，哪怕变化的只是一个红点数字。做法是把状态往下挪、把监听做成局部：用 ValueNotifier 承载会变的值，只在需要它的那一小块子树外包 ValueListenableBuilder，重建就只发生在那里；AnimatedBuilder 是同一思路，它把动画刷新限制在自己包裹的子树内。

这段代码有三个要点：ProductList 是 const 的，父级重建不会波及它；builder 只重建角标那一小片；child 把不变部分传进 builder，避免每次重建图标。同理，计时器、进度条这类高频刷新源要单独抽成组件。至于用 setState、InheritedWidget 还是第三方状态管理库，属于方案选型，另有专文讨论；本文只关心结果：状态离 UI 越近，重建范围越小。

列表与长内容的取数与复用

长列表是问题高发区。先确认有没有在构建全部子项：ListView 直接给 children 时所有子项都参与构建，几百条数据就是一次几百个 widget；改成 ListView.builder 后，只有进入视口与缓存区的条目会被构建。两个参数值得调：itemExtent 告知框架每一项的固定高度或宽度，不必每帧为可见项单独测量，滚动抖动会明显减少；cacheExtent 控制视口外预构建的距离，调大减少快速滚动时的空白，代价是存活子项变多、内存上升，两者要一起权衡而不是无脑拉满。

另一个常见坑是在 itemBuilder 里做重计算：解析 JSON 片段、对整份数据排序、逐条算相对时间，这些每帧都会重做，列表越长越明显。正确做法是数据到手时一次性预处理成展示就绪的结构，itemBuilder 只负责读取。分页与占位也属于这一节：首屏只取少量数据保证快速上屏，接近底部再请求下一页，并给未到的数据留固定高度占位，避免高度突变引起视觉跳动。

RepaintBoundary 与动画的每帧成本

RepaintBoundary 把一颗子树划进独立的重绘边界，让它内部的重绘不连带波及同层其他内容。适合包在外面的是持续播放的动画组件、视频或大面积自定义绘制的组件，以及长列表里的每个条目。静态页面加它没有意义，边界要占额外的图层与显存，加多了反而抬高合成成本，它的用法是隔离重绘源，不是全局装饰。判断加错了也很直接：包上之后时间线里重绘那条曲线没有变化，说明瓶颈不在重绘，而在构建与布局阶段，或者主 isolate 被同步任务占住了，这时该回头查前面几节。

这段写法对应三条经验：动画刷新只落在 builder 那一小片，父页面不参与重建；把 animation 的值用在变换与透明度上，改的是已有图层属性，不触发重新布局，若每帧去改宽高与边距，等于把合成成本换成布局成本；被包裹的子树是 const 的，每帧只重建最外层。最要避免的写法是把动画值塞进页面 setState，让整页每帧重新 build。时长与曲线同样有成本：单个动效压在两百到四百毫秒这个量级（示意值，按自家观感校准），过长会让人更容易注意到帧率不足；曲线用系统默认缓动即可，过强的弹性回弹会拉长重绘窗口。转场与 Hero 属于另一类：转场期间两个页面同时参与合成，Hero 飞越的大图若没解码完成，会在转场末尾出现一次明显掉帧，要提前触发解码或改用缩略图。动画 API 与手势冲突另有专文，本文只强调每帧开销。

图片与字体的解码成本

图片是内存与时间开销的主要来源之一。位图解码之后占用的是像素级内存，和文件体积不成正比，把高分辨率原图铺在列表的小图标位置上，等于同时付出解码时间与内存两份代价。思路是让解码尺寸贴近显示尺寸：加载时指定 cacheWidth、cacheHeight，按目标尺寸解码，列表缩略图与详情页大图分别请求，同一张图不要在两个位置各自解码。

除了单张尺寸，还要看整体驻留量：图片缓存有容量上限，超过就不再保留，快速滚动时表现为反复回源解码，这时要么缩调解码尺寸，要么让服务端给更小的缩略图规格。分级策略的落点是列表页只要缩略图，点开才加载原图，二者在数据里就该是两个字段，而不是同一个 URL 靠客户端缩放。字体侧的成本集中在首屏：字体文件动辄几兆，全量打包推高包体并拖慢首次文本排版，按实际用到的字符区间做子集裁剪，保留数字、常用汉字与业务必需标点即可（裁剪比例属于示意值）；首屏关键文案尽量不依赖网络字体，先让本地兜底字体上屏，到位后再切换。

耗时任务、启动与包体

把计算挪出 UI isolate

解析大 JSON、加解密、大数组排序、图片重编码，只要出现在 UI isolate 里就会顶出一个长帧，表现为点下去之后半秒没有反应。做法是交给隔离区去算，算完只把结果回传再赋值。

这里划一句边界：隔离区承载 CPU 密集的计算型后台任务，不替代 Future 与 Stream 那类 IO 异步；插件里的线程调度属于插件工程范畴，本篇不写。

启动与首屏依赖

启动慢的空间通常不在引擎本身，而在首屏依赖。非首屏必需的模块、动画资源、大图标延后再加载，首帧要构造的子树越小越好；对需要早点进入的页面可以提前创建引擎并预热首屏数据，但不要把预热塞进首帧关键路径。包体手段如下，效果请按自家项目实测：

--split-per-abi 按 CPU 架构分别出包，避免把几套原生库都打进同一个通用产物；资源侧要清理从未被引用的图片与多档重复位图，把大图压成显示需要的规格。这几项叠加的体积差属于示意值，汇报以自家产物的前后对比为准。

渲染后端状态与 Shader 编译卡顿

这一节口径要写准，因为 2024 年 5 月这个时间点上两端状态并不相同：Impeller 在 iOS 已是默认渲染后端，在 Android 上仍是预览、可选启用，不存在两端都已默认，排查手段要按平台分别描述。iOS 走新后端，shader 在构建期就已完成编译，首次出现某个视觉效果时的运行时编译卡顿基本不再是主要矛盾，剩下的抖动更多来自构建与布局；Android 上若仍运行在 Skia 路径，首帧之后第一次渐变、阴影、模糊、复杂路径绘制会伴随一次运行时 shader 编译，用户看到的是第一次点开这个页面卡一下、之后就顺了。

预热的前提是预热的效果与业务用的是同一组参数：渐变端点、模糊半径一变，编译出的变体就不同，所以采集场景要覆盖真实页面，而不是随手画一个。若预热之后第一次出现仍然卡顿，另一条思路是降低复杂度，用贴图或渐变色带替代实时模糊。

观测与验证闭环

优化的最后一步是让结论可复现。DevTools 的性能视图主要看两条轨道：一条是 UI 线程上的构建与布局耗时，一条是栅格化线程上的重绘与合成耗时，哪条先碰到预算线，就往对应章节找原因；时间线里明显凸出的高帧要逐个点开，关联到当时的操作。辅助开关方面，debugProfileBuildsEnabled 用来确认某个组件是不是在被反复重建，它属于诊断手段，定位完就该关掉，不要留在代码里当常驻配置；拿不准的开关名不要瞎写，宁可用 Stopwatch 分段计时。对比实验至少固定五个条件：同一台机器与同一系统版本、同样的冷启动（杀进程重进）、同一份数据（条数与内容固定）、同一种构建模式（release，profile 只用于定位）、同一套操作路径（固定速度滑动或录屏回放），每种跑五次取中位数。

汇报口径建议写成四段：症状与影响范围、定位到的瓶颈、改动点、同条件下的前后对比。前后对比要给观察口径而不是绝对倍数，例如”同一列表滚动时高帧数量明显减少（本机 release 包观察，示意值）”；只报没有条件的百分比数字，复测时通常会被打回来。

症状 首选排查手段 常见成因 修复方向
持续掉帧 性能视图两条轨道对比 每帧重建子树、build 内计算 const 化、缩小重建范围
偶发长帧 时间线定位到具体操作 同步解析、大图解码 挪进 isolate、按尺寸解码
白屏或首帧慢 三段分段计时 首屏依赖过多、资源过大 裁剪首屏、延后加载
启动慢 引擎与数据分别计时 预热挤占关键路径 预热与首帧解耦
内存单调上升 反复进出同页看常驻量 图片驻留、监听未释放 缩调解码尺寸、dispose
首次交互卡顿 先区分平台与渲染后端 Skia 下运行时编译 shader 采集并打包预热产物

小结

本文把 Flutter 的性能问题拆成三件事：用症状确定该看哪条曲线，按重建范围、列表复用、重绘边界、图片字体、计算位置逐个动手，最后在 release 包上用可复现实验验收。多数卡顿来自不必要的重建和 build 里的计算，改这两处的收益大于任何花哨技巧；渲染后端的状态要按平台分别描述，数字一律以自家实测为准。
