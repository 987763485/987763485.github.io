Java 并发编程：JUC 核心

本文面向已经写过 synchronized、也调过线程池参数，但在代码评审里说不清”这里为什么不能换成 HashMap“的读者。我们把 java.util.concurrent（下文简称 JUC）按”约束—能力—误用”三段式过一遍：先立起内存模型与 happens-before 这块地基，再看锁与 AQS、同步工具类、线程池、并发容器与阻塞队列、CompletableFuture，最后落到 Java 21 的虚拟线程上。读完你应该能对着一段并发代码指出它依赖哪一条保证，以及它在什么并发度下失效。

并发问题的三个来源与本篇地图

多个线程访问同一份数据时，结果与”按某种顺序单线程执行”的直觉不一致，这类偏差几乎都可以归到三个来源：可见性、原子性、有序性。把它们分开，是选择工具的第一步。

可见性指一个线程对共享变量的写入，另一个线程不一定立刻看到：硬件层面有 store buffer 与各级缓存，JIT 也可能把变量长期留在寄存器里。Java 内存模型（JMM）不承诺”写入即刻全局可见”，它只承诺存在 happens-before 关系的两个操作之间，前者的结果对后者可见。少了这条链，”我在日志里明明看到赋值先执行了”在语义上毫无意义。

原子性指一组动作不能被其他线程插入。count++ 在源码里是一条语句，执行上是”读旧值—加一—写回”三步，两个线程交错就丢失更新。判断一段代码是否原子，只能看它是否整体落在某个同步动作内：一把锁、一次 CAS、或某个并发容器的具名方法。

有序性指编译器与处理器会在”不改变单线程语义”的前提下重排指令，多线程下这个前提消失，重排就被外部观察到。双重检查锁定的单例漏写 volatile，问题就出在”分配内存—初始化对象—赋引用”这三步被重排，别的线程拿到一个还没构造完的对象。

三个来源对应三层工具：可见性与有序性由内存模型规定的同步动作保证，原子性由锁与原子类保证，这两层之上才是业务代码直接接触的线程池、并发容器与异步编排。

本文只讨论单个 JVM 进程内的并发；跨进程的正确性属于分布式一致性范畴，不由 JUC 提供任何保证，把 ConcurrentHashMap 当作”集群共享的缓存”是常见的架构错觉。

happens-before：可判定的规则，不是时间先后

很多人把 happens-before 读成”在这之前发生”，于是认为只要我先写、你先读，你就一定读得到。这恰恰是错的：它是 JMM 定义的一种保证关系，刻画”一个操作的结果对另一个可见、且不会被重排到它之后”，与墙上时钟无关。两个操作若不在同一条链上，无论实际早晚，都不构成任何可见性承诺。

好消息是，这套关系可以用一组小规则判定，日常代码里用到的基本就是下面这几条：

  1. 程序内顺序：同一线程中，代码顺序靠前的操作 happens-before 靠后的操作。
  2. 监视器锁：对同一把锁的 unlock happens-before 后续对这把锁的 lock。锁不只是互斥，它还是可见性通道。
  3. volatile 字段：对同一个 volatile 字段的写 happens-before 后续对它的读。
  4. 线程启动：Thread.start() happens-before 被启动线程里执行的任何操作。
  5. 线程终止：一个线程里的所有操作 happens-before 其他线程成功从它的 join() 返回。
  6. 传递性：A happens-before B，且 B happens-before C，则 A happens-before C。

判定套路很固定：先确认两个访问是否在同一线程，不在就找它们共同经过的”桥”——同一把锁、同一个 volatile 字段，或一对 start/join；找到就顺着传递性串链，找不到就有竞态。

volatile：两个正确用法与一个典型误用

volatile 只参与上面两条链的构建：它解决可见性与局部的有序性，不解决原子性。

用法之一：状态标志位。 一个线程置位、若干线程轮询退出，这是 volatile 最合适的场景。判据是”这个字段的值不依赖旧值”。

用法之二：双重检查锁定的单例。 这里 volatile 的作用是禁止”引用赋值”被重排到”对象初始化”之前。

去掉 volatile 会怎样？new Singleton() 在字节码层面是”分配内存—执行构造—把地址赋给字段”三步，后两步可能被重排。线程 A 先赋了引用、还没跑完构造，线程 B 在第一次检查处看到非 null，直接返回一个半成品对象。这个 bug 与线程数、机器负载相关，几乎无法在开发机上稳定复现。

典型误用：volatile int count 做自增。

count++ 展开是”读、加一、写回”。volatile 让每次读都拿到最新值，却在读与写之间不提供任何独占：两个线程都读到 5、各自加一、都写回 6，结果少了一次。volatile 修的是”看不见新值”，这里是”基于旧值算完再覆盖”，属于原子性问题。修复按竞争强度选路：

从 synchronized 到 ReentrantLock

synchronized 至今仍是默认选择，理由很硬：语法上不可能忘记释放，异常路径自动解锁，能与 wait/notify 直接配套，JVM 也能围绕它做锁消除、锁粗化等优化。写代码时该关心的是这些契约：可重入、同时提供互斥与可见性、异常时一定退出临界区。

至于”偏向锁—轻量级锁—重量级锁”的升级过程、对象头位布局与各种阈值，属于 HotSpot 的实现细节，随版本一直在变，某些机制在新版本里已被调整或移除，不要背成固定口诀——背来的口诀会引导你去”优化”一个并不存在的机制。这类问题应该用测量回答。

需要超出 synchronized 契约的能力时，才换 ReentrantLock。它的四个卖点是：公平性可选、可中断获取、超时获取、多个等待条件队列。

AQS：state、等待队列与模板方法

ReentrantLock、Semaphore、CountDownLatch 这些类看起来功能各异，骨架却完全一样，这个共同骨架就是抽象队列同步器（下文简称 AQS）。理解它不需要读源码，只需要接受三个部件：一个整数状态、一条等待队列、一组留给子类的模板方法。

state 是一个整数值，语义完全由子类定义：独占锁里它是重入次数，0 代表无人持有；Semaphore 里是剩余许可数；CountDownLatch 里是还要倒数几次；读写锁里被劈成两半，分别记读线程数与写重入数。对它的争抢靠 CAS 完成，这是”谁赢”的裁判。

赢不了的线程进队列。队列是一条双向链表，节点记录线程、等待状态与前驱后继，新节点追加到尾部，队首节点表示已持有资源的线程。拿不到资源的线程不会自转，而是把前驱标记为”需要唤醒我”后挂起自己；释放方负责唤醒队首方向的等待者，被唤醒者从挂起点继续，再试一次 CAS。要注意线程是先入队、再挂起，唤醒后也先竞争、再出队，所以队列顺序不等于授予顺序，这正是非公平模式的来源。

模板方法是子类与骨架的接口：独占形态实现 tryAcquire、tryRelease，共享形态实现 tryAcquireShared、tryReleaseShared。排队、挂起、唤醒、超时与中断这些容易写错的机械部分由骨架负责，子类只回答两个问题：”此刻能不能拿到？””拿到之后 state 怎么变？”同一个框架因此既能表达互斥也能表达配额：独占形态一次只有一个赢家，共享形态允许一批赢家同时通过，并且要把”还有余量”的信号继续往后传播，否则队列会卡在无人持有的状态上。

同步工具类：按场景选型

四个常见工具对应四种完全不同的需求，选型时先问”要等的是什么”。

CountDownLatch 等的是一个数归零。 一个线程等若干子任务回报，或若干线程等一个统一发令。它一次性，倒数到 0 之后不能重置，想再来一轮只能新建对象；它也不接受”提前失败”，子任务异常退出时必须自己保证 countDown() 被调用，否则等待方永久挂死。不该用的场景：需要每轮重置的汇合点（那是 CyclicBarrier），或限制并发数量（Semaphore 的许可可以归还，它不行）。

CyclicBarrier 等的是最后一批同伴到齐。 party 数固定，全员到齐后执行可选的屏障动作再一起放行，可复用。破屏障是它的关键语义：任一等待者被中断或超时，屏障进入 broken 状态，其余等待者同时收到 BrokenBarrierException，一个线程的取消会传染整组，等待方必须处理异常并决定 reset() 还是整批失败。不该用的场景：参与者数量不固定（动态注册退出用 Phaser），或只需”一对多放行”。

Semaphore 等的是一个配额。 acquire 消耗许可，release 归还；许可数就是同时在途的任务数。它必须 finally release，而且不能 release 一个没有对应 acquire 的许可——那会凭空放大配额，比忘记 release 更难查。不该用的场景：需要”同一线程重入同一份配额”（默认实现不可重入，除非自己基于 AQS 重写），也别拿它替代连接池（它管数量，不管资源是否健康可用）。

Phaser 是 CyclicBarrier 的动态版：参与者可以运行时 register/deregister，一轮叫一个 phase，还能只注册到某个阶段。适合”任务数随数据分片变化”的多阶段流水。不该用的场景：单轮一次性等待，用 CountDownLatch 更直观。

Exchanger 是成对交换。 两个线程各持一个缓冲区，在交换点互相把引用递过去，天生适合”一个填、一个清空”的双缓冲。不该用的场景：线程数多于两个（它只按对配对，多余线程要等新对手），或生产者与消费者数量不对称（那种情况该用阻塞队列承担缓冲与解耦）。

这些工具解决的是线程之间的等待结构，不是数据保护：它们不承诺共享可变字段的可见性，业务数据仍要走锁、原子类或并发容器。

线程池：参数、执行流程、拒绝策略与池大小

生产代码请直接 new ThreadPoolExecutor(...)，别用 Executors 的快捷工厂。七个参数之间存在明确的制约关系。

corePoolSize 是常驻线程数，空闲也不回收（除非开启 allowCoreThreadTimeOut）。maximumPoolSize 是总上限，只有队列塞满后才会用到，它常被误解为”并发上限”。keepAliveTime 与单位决定非核心线程闲置多久被回收。workQueue 是等待区，它的容量决定”先排队还是先扩容”。threadFactory 决定线程怎么创建，handler 决定装不下时怎么办。

执行流程是一条固定的判断链，理解了它就能预测任何配置的行为：

flowchart TD
    A[提交任务] --> B{运行中线程数 < core?}
    B -->|是| C[新建核心线程执行]
    B -->|否| D{队列未满?}
    D -->|是| E[入队等待]
    D -->|否| F{线程数 < max?}
    F -->|是| G[新建非核心线程执行]
    F -->|否| H[拒绝策略]

关键点是队列优先于扩容：无界队列配上很大的 maximumPoolSize，后者永远不生效；容量很小的队列会把池子迅速推到上限。另外线程是 lazy 创建的，prestartAllCoreThreads 值得显式调用。

四种内置拒绝策略的差别只在”丢什么”。AbortPolicy 是默认，直接抛 RejectedExecutionException，让调用方立刻知道容量不够。CallerRunsPolicy 让提交任务的线程自己去跑，效果是天然回压，代价是提交方被阻塞——如果提交方本身是池内线程或事件循环，这会拖垮上游。DiscardPolicy 静默丢掉新任务，DiscardOldestPolicy 丢掉队头最老的任务再重试提交，只适合”新数据比旧数据有价值”的场景，比如行情快照。自定义 RejectedExecutionHandler 该做的事通常是：打点与告警（拒绝次数是最该被看见的指标）、把任务落到磁盘或备份队列、区分可重试与不可重试、给调用方明确的失败语义而不是吞掉；最不该做的事是在处理器里同步把任务再塞回同一个池。

threadFactory 不是可选项，它至少要做三件事：给线程起可识别的名字（jstack、线程 dump 与日志都靠它定位归属）、明确 daemon 属性、设置 UncaughtExceptionHandler。任务经 execute 提交时，未捕获异常会让线程终止并由工厂新建线程顶替，异常只打到默认错误流；经 submit 提交时异常被吞进 Future，不 get 就永远看不见——这是线上”任务静默失败”的头号原因。

Executors.newFixedThreadPool 与 newCachedThreadPool 在生产里危险，方向各不相同。前者用无界的 LinkedBlockingQueue，任务堆积不受上限约束，最终在队列里耗尽内存；后者上限是 Integer.MAX_VALUE、队列是 SynchronousQueue，来一个任务开一个线程，下游一慢就线程爆炸，光线程栈就能压垮进程。newScheduledThreadPool 同样用无界队列，两个坑一起占。

池大小只能给估算起点，不能给最优值。 CPU 密集任务从一个核一个线程起步，即 core = max = 可用核数，而”可用核数”要读容器的 CPU 限额，不是宿主机的 availableProcessors()。IO 密集任务按等待与计算的比例放大，常用形式是 核数 × (1 + 平均等待时间 / 平均计算时间)，或从下游能扛住多少并发（连接池上限、数据库可接受的查询数）倒推，取较小者。两个公式都只用来定第一次压测的档位，必须压测校准：真实瓶颈往往在下游连接池或锁竞争上，而不在线程数。调大池子前先问上游有没有回压，否则只是把队列从进程内挪到进程外。

并发容器：ConcurrentHashMap 与阻塞队列

ConcurrentHashMap 从早期的分段锁演进为”CAS 加上对桶头节点 synchronized“，这段历史一句带过即可，今天写代码关心的是它提供的口径。

第一，计数是近似的。size() 的值由一个基础值加上若干分散计数单元累加而来，思路与 LongAdder 相同，代价是并发修改下它只是瞬时估计。容量规划与监控请用返回 long 的 mappingCount()，它同时避开了元素数超过 int 的溢出。凡是”先看 size 再决定要不要清理”的逻辑都要按估计值处理。

第二，单键的复合操作是原子的，跨键的不是。computeIfAbsent、merge、putIfAbsent、replace(key, old, new) 都可以当契约读：同一个 key 上只有一个线程的映射函数会被执行。两个禁忌由此而来——映射函数里不要做阻塞 IO，它持有的是那个桶，慢查询会拖住同桶的其他 key、并长时间占住容量与线程；也不要修改同一张表，递归更新属于未定义行为。”读一下再决定写”应该放进 compute 或 merge，写成 get 加 put 就在两次调用之间留下了竞态。

第三，批量遍历不是快照。迭代器、forEach、keySet、values 与并行归约都是弱一致的：不抛 ConcurrentModificationException，既不保证看到创建迭代器之前的全部写入，也不保证遍历期间没有新元素进来。”边 forEach 边统计数量”得到两个对不上的数字，是设计如此。

阻塞队列家族的区别全在容量语义上。ArrayBlockingQueue 有界、数组实现、入队与出队共用一把锁。LinkedBlockingQueue 把 put 与 take 拆成两把锁，但默认容量是 Integer.MAX_VALUE——不显式传容量就等于无界队列，这是它最危险的默认值。SynchronousQueue 容量为零、只做交接，要求双方同时在场，newCachedThreadPool 靠它实现”来任务就开线程”，因此不适合当缓冲。PriorityBlockingQueue 无界、按比较器从堆顶出队，出队顺序不等于并发顺序，元素不可比较时直接失败。DelayQueue 只允许取出已到期的元素，它是队列不是调度器，别指望定时精度。

关停是这类代码最容易写错的一段，两条正规路子：毒丸，或者 shutdown 加 awaitTermination。

毒丸的纪律是”人数与毒丸数相等”，且毒丸必须是队列里最后一个进入的元素，所以生产者要在自己确定不再投入之后才放。shutdownNow 的可靠性完全取决于任务是否响应中断，不检查中断标志的任务它拿没办法。

CompletableFuture：编排异步链路

Future 只能做三件事：阻塞 get、轮询 isDone、取消。”拿到 A 的结果再去调 B””A 与 B 都回来再合并”这类需求用它就得自己开线程去等，等待本身就是浪费。CompletableFuture 补上的是编排：结果到达时由回调链驱动下一步，它可以被外部 complete，异常也在链上传递。

方法选择有个判断依据：回调返回普通值用 thenApply，回调本身还是异步的用 thenCompose，后者相当于扁平化，写成 thenApply 会得到套了两层的对象。两条独立结果合流用 thenCombine，多路汇聚用 allOf，只要一路先完成用 anyOf。坑在于 allOf 的完成结果是 Void，仍要逐个 join 取值；anyOf 只说”有一路完成了”，不告诉你失败的那几路去哪了。

异常处理走 exceptionally（只在异常分支上补一个值）、handle（成功失败都走一遍）、whenComplete（只旁路记录、不改结果）。三个要点：链上的异常被包成 CompletionException，get 与 join 抛出的包装类型不同，别只抓其中一个；一个 stage 失败后正常分支会被跳过，一路滑到最近的异常处理器；处理器返回的值会重新变成”成功结果”，所以兜底该放在链末端。

默认执行器是风险最大的地方。不带 Executor 参数的异步方法都跑在公共池上，并行度按可用核数减一确定，而且整个 JVM 共享一份。往里丢阻塞调用（RPC、数据库、文件 IO）会把这个池占满，进而拖慢同一进程里所有用默认池的任务与并行流。规则很简单：任务会阻塞就显式传自己的执行器，并按上一节的方法给它定容量与队列。超时方面 Java 9 起提供了 orTimeout 与 completeOnTimeout，更早只能靠外部调度器兜；即便有了 orTimeout，它也只是让结果”以超时异常完成”，底层那次阻塞调用不会被打断，取消与中断是两件事。

顺带划一条界：挂起函数与阻塞调用的关系另有专文，本文不展开。

虚拟线程：Java 21 的吞吐工具

虚拟线程在 Java 21（2023-09-19 发布的 LTS 版本）转正。它要解决的问题必须说准：提高阻塞式代码的吞吐，而不是提高 CPU 并行度。虚拟线程遇到阻塞调用时把续体交还调度器、让出所在线的载体线程，于是几万个”大部分时间在等 IO”的任务只需少量载体线程。CPU 仍在算的活儿不会因为换成虚拟线程而变快，并行度依然由载体线程数量决定。它与 goroutine 的机制差异与性能对比不在本文范围。

适合的形状是”每请求一线程”的阻塞式代码：Servlet 处理链、JDBC 调用、同步 RPC，不需要改写为异步风格。不适合的有两类：CPU 密集任务（没有阻塞可让出，只多了调度开销），以及依赖 ThreadLocal 缓存重对象的代码（线程数从几百涨到几万，缓存会按比例放大内存）。

池化的旧理由里，”线程创建贵、要复用”这一条在虚拟线程上不再成立；”限制对稀缺资源的并发访问”完全成立。所以别写”虚拟线程取代线程池”，准确的说法是执行器换了语义：newVirtualThreadPerTaskExecutor 每次提交都新建一个虚拟线程，不排队也不限并发，等于把无界并发的责任交回给你。要限流就在上层用信号量控制”在途任务数”，保护连接池与下游服务。两者正交——每任务一个线程是结构，信号量是配额。

关于固定（pinning）要用观察口径而不是记忆：Java 21 的实现里，虚拟线程在 synchronized 块内阻塞、或停在某些本地方法调用上时，可能被固定在载体线程上不让出，从而削弱吞吐。判断有没有发生请开 JFR 看对应的事件计数，别靠”我记得这里有问题”去改代码结构。另外，本文日期下结构化并发与作用域值仍是预览或孵化阶段的 API，尚未稳定，生产代码不要把它们当可用能力依赖。

小结

四句可执行的判断。第一，先问这段代码依赖哪条 happens-before 链，链断了就谈不上正确性，压测通过也不算证据。第二，volatile 管可见性与有序性，原子类与锁管原子性，两者不能互相顶替，锁升级这类实现细节不要背口诀。第三，线程池与队列的危险默认值指向同一件事：无界的等待区会让上限参数失效，池大小只能当压测起点。第四，虚拟线程改变的是阻塞式代码的吞吐上限，不改变稀缺资源需要配额这一事实。
