Java 与 Go 性能对比实测

“Java 和 Go 到底谁更快”是我在技术评审里被问过最多、也最难回答的问题。本文把它拆开重做一遍：固定被测运行时版本，设计三类互不覆盖的负载，把指标口径、环境一致性、预热窗口、压测脚本骨架和结果解读框架逐条落实，给出一个既可复现也可被推翻的实验设计。需要提前声明：文中所有数字都是本轮实验口径下的示意值，用来说明”数据长什么样才算讲清楚”，而不是说明”某语言应该有多快”。

从”谁更快”到”在哪种负载下谁更快”

这个问题为什么问错了形状

这个问题难答，不是因为答案藏在细节里，而是问题本身缺了三个必要条件：负载形态、指标口径、资源约束。同一对运行时在这三个条件变动时会给出互相矛盾的排名。CPU 密集的素数筛在 1 个 CPU 配额上可能让 Go 领先，同样负载放到 8 个配额并给足预热后，被 JIT 充分编译过的 Java 热点循环反而更省 CPU 时间；而一个下游容量有限的扇出服务，两者吞吐几乎全由下游决定，运行时差异被压成噪声。把这种必然发生的名次互换压缩成一句”某语言更快”，结论没有行动价值。

更麻烦的是”快”没有单位。启动快、吞吐高、尾延迟低、每请求 CPU 少、内存占用小是五个不同目标，且经常冲突：为吞吐调大堆，冷启动和内存水位变差；为尾延迟把回收调激进，吞吐和 CPU 开销上升。所以本文不使用”快”这个模糊词，只说”某负载下某指标的观测结果”。

对比要成立的三个”同”

本文的实验设计遵循三条纪律，缺一条结果就没有解释力。第一，同一负载形态：两类应用使用同一份请求生成逻辑、同一组请求分布、同一份数据集，业务代码写得等价，而不是各自”惯用写法”的极限优化版本。第二，同一指标口径：要么都看服务端记录的单请求 CPU 时间，要么都看压测端算出的 RPS，不能一边取服务端日志分位、另一边取压测工具的墙钟估计。第三，同一资源约束：两边放进完全相同的容器规格，CPU 限额、内存限额、副本数与网络策略一致。资源约束不等价时，测的是配置而不是语言。

本篇的范围边界

有三件事本文不做，以避免与其他专文重复：单一语言内部的调优流程与剖析工具有专文；把既有服务改写为另一语言的迁移决策与步骤不在本文范围，这里只给性能层面的判断；跨语言对比的通用方法论另有专文。goroutine 调度模型的内部机制同样属于并发专文，本文只使用其栈开销与调度粒度的可观测后果。

被测口径与实验边界

两侧的版本选择

Java 侧本轮并行跑两个基线：Java 17 LTS 与 Java 21 LTS。选这两个而不是只取最新，是因为 17 仍是大量存量服务的生产版本，21 LTS 于 2023-09-19 发布，是当时最新的老版本支持线，且虚拟线程在这一版正式可用；把两者放进同一轮，也能直接看到同一种负载在新老 LTS 之间的差别。回收器两侧保持一致，都用当时默认的分区式回收器，ZGC 只在补充实验里单独标注，不与主结论混排。

Go 侧取 1.22，发布于 2024-02-06，是本文写作当时的稳定版本。1.22 对 for 循环变量语义的变更会影响并发代码，这属于正确性范畴、不改变性能口径，但编写压测客户端时不能沿用旧的闭包捕获写法。两侧都用官方稳定版，不引入预发布构建，也不引入本文日期之后才发布的版本，避免把版本迭代收益误读成语言差异。

编译与构建口径

Java 侧用当时主流构建工具产出可执行 jar，启动参数固定后不再调整；Go 侧用标准工具链静态编译为单一二进制，编译目标与基础镜像架构一致。两侧都关闭与实验无关的后台任务：自动扩缩容、链路采样上报、热重载与高频指标打点。

判定”同一负载”要看请求语义、数据分布与失败语义三件事是否一致，而不是看代码行数是否接近：三件都对齐之后，差异才有资格被归因到运行时，否则一侧仅因重试更激进就显得”吞吐更高”，那属于配置差异。

负载设计：三类负载各自考验什么

CPU 密集：考验稳态计算效率

第一类负载做纯粹的计算，取三小项：一定区间内的素数筛选、小规模矩阵乘法、把固定结构的对象图序列化成 JSON 再反序列化回来。三项各有用意：素数筛循环体极简、几乎不产生垃圾，考验热点代码编译后的机器码质量；矩阵乘法有可观的数组访问压力，考验内存层次与边界检查开销；JSON 序列化同时考验对象布局访问、字符串处理与临时对象分配，是业务服务里最常见的 CPU 消耗形态。

这一类负载上，结构性差异集中在编译模型：Java 的解释执行与分层编译意味着同一段代码在进程生命周期内的效率是变化的，未预热的数据不能代表稳态；Go 在构建期就产出机器码，进程一启动就是最终形态。第二个差异是分配与回收压力：Java 侧短命对象回收成本很低，Go 侧取决于逃逸分析结果，同样写法在两侧可能有不同量级的分配压力。

IO 密集：考验并发成本与排队

第二类负载自己几乎不计算，收到请求后向一个受控下游发起一到两次调用，把结果简单聚合后输出。下游用同语言的桩服务模拟，延迟分布固定，并明确限制总容量，使瓶颈可以按设计出现在下游、也可能出现在被测服务。这一类考验并发连接的代价与排队行为：每个进行中的请求占多少内存、多少句柄、调度上要等多久。

结构性差异在这里最直观。Go 的并发单元起步栈很小、按需增长，创建与销毁成本低，高并发下能把大量进行中的请求保持在内存里而不让资源曲线急剧上升。Java 17 这条线上每个进行中的请求通常对应一个平台线程，线程栈是固定成本，常见做法是线程池加异步非阻塞客户端，把”并发度”与”线程数”解耦；Java 21 的虚拟线程提供了另一种解法，后面单独讨论。

混合负载：考验真实服务的耦合效应

第三类负载是带本地缓存的 HTTP 服务：命中缓存时走一段真实的序列化与少量计算，未命中时查数据库并写回缓存。它把前两类揉在一起，也最接近一般业务服务。设计目的是观察 CPU 压力、内存水位与 IO 等待互相掩盖的能力：命中率从示意值区间高端滑向低端时，两个运行时的吞吐曲线都会变形，但变形的位置和形状不一定相同。

指标口径：把”快”拆成可测量的量

六个必须同时记录的指标

本轮实验固定采集六项，缺一不可。吞吐用压测端统计的每秒完成请求数 RPS，只在采样窗口内统计，并按并发档位分别记录。延迟记录 P50、P99 与 P99.9 三个分位，来源是服务端为每个请求记录的处理耗时，而不是压测端看到的响应时间，两者只在没有排队时近似相等。单请求 CPU 时间由进程累计 CPU 时间除以完成请求数得到，这是最容易解释、也最不容易被机器抖动污染的一项。内存记录常驻内存 RSS 峰值，并同时记录它与容器限额的比值。冷启动与预热时间取进程启动到首次达到稳定吞吐的中点。错误率按请求记录，分成超时、连接类错误与被下游限流三类。

为什么 P99 不能取多次采样的平均值

这是评审里最常见的一个方法错误：跑三轮压测，把三轮的 P99 相加除以三，报告”平均 P99”。分位数不是可加的量，它依赖整个样本集合的排序位置。三轮各有各的样本分布，取平均等于预设三次的尾部分布同形，而这恰恰是要检验的东西。更要命的是，尾部对极端值的出现次数极为敏感，平均会把”偶尔出现的尾巴”抹平成看起来稳定的数字。

正确做法是把同一档位所有轮次的原始单请求耗时合并成一个样本池，在池上计算分位；至少也要按轮次分别报告，并说明轮次间的离散程度。P99.9 更极端，样本量不足时它没有统计意义，所以采样窗口必须保证尾部有足够事件数，且不要用只支持平均与最大值的直方图粗桶去推算尾分位。此外，单请求 CPU 时间乘上目标吞吐得到的所需总 CPU 量才是决定副本数的依据，RSS 只有除以容器限额之后才有意义，换算过程要写进报告，避免读者拿孤立数字做判断。

环境一致性：把噪声压到可解释的范围

硬件与调度层面

同一对负载必须在同一台物理机器上跑，而不是两台”配置相同”的云主机：宿主负载、云盘性能与网络抖动都会进入结果。能绑核就绑核，被测服务限制在固定核集合，压测进程使用另一组核，两者不重叠。CPU 频率调节要么显式关闭，要么把调节策略记进报告，因为它会让前后段采样处在不同频率上。

运行时参数与容器限额必须对齐

这是最容易失真的地方：给 Java 一个大内存容器却不设堆上限，或给 Go 一个 CPU 限额却不让可用并行度与之匹配。本轮把两侧都对齐到同一个容器规格，规格数值是团队约定示例，不是推荐值。

Java 侧对应的做法是把堆上限设为容器限额减去元空间、线程栈、直接缓冲区与运行时自身开销之后的值，两侧都在启动脚本里断言实际读到的限额，不一致就拒绝启动，避免配置漂移污染整轮数据。

压测端自耗与其他干扰

压测端与被测服务同机时，压测进程自己消耗 CPU 与页缓存，档位越高污染越重，尾延迟里会混入压测线程被抢占的时间。本轮把压测端放在同机另一组核上，并在高档位单独记录其 CPU 占用作为质量检查项。此外还要固定日志级别与输出目标（调试级日志足以改变结果）、指标导出频率、时钟同步方式、是否开启透明大页、宿主监控代理，以及数据集是否已进过页缓存。

预热与采样窗口：先约定时间线再谈数据

两类预热的不平等

Java 的分层编译意味着同一段字节码在运行初期被解释执行、随后逐层编译为优化机器码，还要经过反优化与重新编译，启动后的前一段时间里吞吐与单请求 CPU 时间都在爬升。Go 没有编译带来的爬升，但依然有自己的预热：到下游与数据库的连接池要建立，DNS 与路由缓存要生效，页缓存里要有数据集，回收器也要按实际分配速率扩缩到工作堆大小。所以”预热”不是对 Java 的照顾，而是对两侧的公平：两侧使用同样的预热时长与预热流量，期间数据一律丢弃，不参与统计。

时间线设计

flowchart LR
    A[启动与配置断言] --> B[预热流量 固定时长]
    B --> C[稳态确认 吞吐斜率趋平]
    C --> D[采样窗口 每档位固定时长]
    D --> E[冷却间隔]
    E --> F[下一并发档位]

判定”可以开始采样”要有客观条件，而不是靠人眼看曲线顺眼。本轮做法是：连续若干个小时间片内吞吐的相对变化都落在阈值以内才算进入稳态，阈值按团队约定示例给出。采样窗口要覆盖足够多请求，让 P99.9 有样本支撑；档位之间插入冷却间隔，避免上一档位遗留的排队与回收压力渗进下一档。每个档位至少重复三轮，且每轮重新部署进程，而不是在同一进程上连续换档。

压测脚本骨架与并发档位扫描

压力生成思路

压测器选一个能固定并发连接数、又能逐请求记录耗时的工具即可。常见思路有两类：wrk 这类常驻连接加固定并发的模式，适合找拐点；vegeta 这类按目标速率投递的模式，适合验容量。本轮三类负载都用前者，因为它直接对应选型时关心的问题：给定资源约束，这个服务能吃下多少并发。

关键是不能只拿工具汇总的平均值，必须保留逐请求耗时。工具汇总常有两个坑：把连接建立与排队算进延迟却不区分；存在协调遗漏，即慢响应期间该发的请求没有发出，导致尾部被系统性低估。缓解方式是按固定节奏发起，把未发出的时刻记为错过的事件，或者在服务端独立记录到达时间。

档位的设置与扫描

本轮使用 8、32、128、512 四个示意档位：8 观察低并发下的单请求成本，此时差异更接近运行时固有开销；32 观察线程池或调度器开始承载并发的时刻；128 让 IO 型负载进入下游受限区间；512 暴露高并发下的每请求并发成本，而且常常是内存水位先出问题。扫描顺序从低到高、每档重新部署，并补一次反向扫描检查顺序偏差：正反差异明显说明采样窗口有问题，应该回到时间线而不是修改数据。

停顿与垃圾回收：只写观察口径

观察入口两侧不同，但要换算到同一口径

Java 侧入口是回收日志：记下每次回收的暂停时间与时间戳，与同时间轴的单请求耗时对齐，看尾部抬升能否落到回收事件上、哪一类回收事件与尾延迟相关。Go 侧没有同形态日志，本轮通过运行时暴露的指标接口读取回收周期的暂停分布与堆增长趋势。两侧最终换算成同一个问题：尾延迟里有多大比例能与回收事件建立时间对应关系。

有个说法需要纠正：Go 的回收并不是没有停顿。它用三色标记并发推进，大部分标记工作与用户代码同时进行，但标记起止阶段需要所有正在执行的并发单元参与协调，这段时间极短，仍然是对全部并发单元的协助式停顿。说成”零停顿”或断言某个具体毫秒数都不准确；能说的是它被设计成把单次停顿压得很短，代价由并发单元协助承担。Java 侧同样是并发阶段与短暂停顿的组合，两侧比较必须建立在如何测量一致之上，而不是宣传口径上。

调参数是为了看敏感度，不是为了找最优值

本轮刻意做参数敏感度实验：Java 侧改堆大小，Go 侧改回收触发阈值与内存上限提示，看同一负载下尾延迟与吞吐如何移动。目的不是挑一个最好看的配置，而是回答这个结论离最优配置有多远——名次在参数小幅移动后就反转，它就不该被写成结论。单语言内部如何系统调优有专门文章，本文不重复那套流程。

内存与部署形态：三条常见结论各自的反例

三条常见说法与它们的翻转条件

第一条，Go 的产物是单一二进制、镜像小、冷启动快：这在形态上成立、不必实测，但启动时要加载大数据集或预热大量连接时，进程时间被数据加载与依赖握手主导，Java 侧若已提前加载，两者启动时间可能拉平。第二条，Java 启动慢但稳态吞吐高：若流量是短时突发后长期空闲，进程进不了充分编译的稳态；容器内存限额逼得紧时，稳态吞吐也会被回收频率拉下来。第三条，Go 的常驻内存通常更低：工作集很大且大量长期存活时，紧凑对象布局的优势被分配器与元数据开销抵掉，RSS 差距缩小甚至反转。

这一节真正能说的是：部署形态的差异是结构性的、可按定义确认；内存与启动的差距是条件性的、必须按负载重测，把两者混进同一条结论是这类对比最常犯的错误。

虚拟线程：改了成本模型，不是免费并发

Java 21 的虚拟线程削弱了 IO 密集并发里”每个等待中的请求占一个平台线程”这项固定成本：阻塞不再长期霸占载体线程，同一份资源约束下能同时挂起的请求数显著提高。这在本次扇出负载上可观察，但它改的是成本模型而不是计算速度——CPU 密集负载里几乎没有等待可摊薄，虚拟线程基本不带来收益。

更要紧的是，把档位从 128 推到 512 时，若下游容量本身就那么大，多出的并发只会变成下游队列与自身超时，吞吐不再上升、错误率反而抬升。所以本轮把三项保护与虚拟线程同时开启：到每个下游的并发上限、每请求超时预算、入口侧速率控制。缺一项，测到的就是”把压力转移给下游之后的假高吞吐”。同样基于这个理由，本报告拒绝给出”虚拟线程让 Java 与 Go 在并发上等价”这类结论：机制相似，但依赖治理与既有代码的阻塞习惯差别很大，只能按具体服务测。

选型判断与结论边界

情形 倾向 判断依据（非性能结论）
已有大量服务端代码、治理体系与中间件围绕既有框架构建 Java 线 迁移成本与治理资产的价值远大于运行时差异
团队长期以该语言招聘与培养，代码评审与规范成熟 保持原语言 组织熟练度是性能之外的第一变量
新建轻量网关、代理、边车、CLI 与短生命周期进程 Go 线 产物形态、启动与内存结构更契合这类进程
稳态高吞吐的复杂计算或重度依赖成熟生态的服务 Java 线 预热后的稳态表现与生态成熟度
瓶颈在慢查询、下游容量或数据访问路径的服务 都别换语言 换语言不会移动真正的瓶颈

最后一条是本篇最重要的反直觉结论：多数业务服务的性能问题出在依赖与数据访问上——一个缺索引的查询、一次未合并的循环调用、一个容量不足的下游，代价远超两种运行时在同一负载上的差距。本轮实验中 IO 密集负载在高并发档位下两侧吞吐趋同，瓶颈已经落到下游容量上，这就是”换语言解决不了排队”的直接体现。反过来，若测出的差异能被一行索引或一处批量调用抹平，它就不该作为选型理由。换负载、换硬件、换依赖拓扑，结论都会变，这是本篇所有示意值的共同限定。

对比实验自查清单

  • 两侧是否同机、同容器规格、同核集合且与压测端不重叠？
  • Java 堆与 Go 的内存上限提示是否都按同一容器限额推导？
  • 请求语义、数据分布与失败语义三项是否逐条对齐？
  • 预热窗口是否两侧等长，预热数据是否全部丢弃？
  • P99 与 P99.9 是否在合并后的原始样本池上计算？
  • 是否保留逐请求耗时并检查了协调遗漏与压测端自耗？
  • 每个名次是否附带负载、档位、预热与硬件四个限定条件？
  • 是否至少做过一次参数敏感度与一次反向档位扫描？

小结

本文把”Java 还是 Go 快”改写成可复现的实验设计：固定版本口径，三类负载分别考验稳态计算、并发等待与混合耦合，六个指标代替模糊的”快”，再用环境一致性清单、预热时间线、档位扫描与汇总表把结果约束在可解释范围内。停顿与内存两节给出的是观察入口和翻转条件，不构成数字结论；虚拟线程一节强调的是它改了成本模型而非计算速度，且必须与限流、超时一起评估。真正该带走的是方法论：多数服务瓶颈在依赖与数据访问上，别把跨语言改写当性能方案。换负载与换硬件，结论会变——这句话不是免责，而是本篇唯一希望读者记住的东西。
