Java JVM 内存模型与 GC

本文讲 HotSpot 的内存划分与垃圾回收：运行时数据区怎么分、对象一生走过哪些阶段、GC 凭什么判定对象不再可达、收集器如何取舍。适合写过 Java 业务代码、但还没理清”内存去了哪里”与”一次停顿由什么组成”的读者，读完应能解释一段 GC 日志的字段，也能说清某个收集器适合哪类服务。

先划边界：本篇只讲机制层的”内存怎么分、垃圾怎么收”，线上事故定位与工具链调参分别由同批《Java 服务线上问题排查》《Java 性能调优实战》承担。阈值数字都是团队约定示例，性能数字标注为示意值；版本口径统一为 Java 17 与 Java 21（21 于 2023-09-19 发布，是当时最新的 LTS）。

运行时数据区：谁共享、谁私有

Java 进程占用的内存并不等于堆，HotSpot 的运行时内存按”线程私有”与”线程共享”两类切分最好理解。

线程私有区域有三块。程序计数器记录线程正在执行的字节码行号，分支、循环与异常跳转靠它恢复位置。虚拟机栈以栈帧为单位，存放局部变量表、操作数栈、动态链接与返回信息，StackOverflowError 来自这里。本地方法栈服务于 native 方法，HotSpot 与虚拟机栈合并实现。

线程共享区域有两块。堆存放对象实例与数组，是垃圾回收的主战场，物理上可以不连续。方法区是规范里的概念，存类元信息、运行时常量池、静态变量与 JIT 后的代码缓存；Java 8 起它由位于本地内存的元空间（Metaspace）实现，替换了此前的永久代（PermGen）——类元数据规模难预估，放在堆内固定区域既容易撑爆，也不利于多个类加载器共享。

堆之外还有直接内存。ByteBuffer.allocateDirect 分配的是堆外内存，不受 -Xmx 约束，只受 -XX:MaxDirectMemorySize 约束；未显式设置时由 JVM 内部默认值兜底。它要等堆内包装对象被回收才释放，这个依赖是后文误区的来源。

flowchart TD
    A[JVM 进程占用的内存] --> B[堆: 对象实例与数组]
    A --> C[线程私有区域]
    A --> D[本地内存]
    C --> E[虚拟机栈与本地方法栈]
    C --> F[程序计数器]
    D --> G[元空间: 类元数据]
    D --> H[直接内存: NIO 缓冲区]

栈与元空间都在本地内存，所以容器里进程常驻内存高于 -Xmx 是正常现象，不是”配置没生效”。

对象的一生：从 TLAB 到晋升

一条 new 指令大致经历类加载检查、分配内存、初始化零值、设置对象头、执行构造方法。堆是否规整决定用指针碰撞还是查空闲列表。并发分配靠 CAS 加重试，更常见的做法是本地线程分配缓冲（TLAB）：线程提前在 Eden 切出一段私有区域，小对象在自己 TLAB 里移动指针即可，不必抢锁；对象大于剩余空间时退化到共享 Eden 分配，旧 TLAB 尾部作废。

逃逸分析决定对象是否一定落在堆上，这段最容易写错。JIT 在内联之后判断引用会不会逃出方法或线程：不逃逸时可能做标量替换，把字段拆散放进寄存器与栈槽，也可能消除锁或改为栈上分配。但这是”发生条件”而非”一定发生”：它在 Java 17/21 的服务端编译路径上默认开启，只有方法被内联、逃逸路径简单、对象不超过内部阈值时才真的生效；引用进了静态字段或集合、逃逸到别的线程、对象过大，都退回堆分配。

年龄与晋升：对象每熬过一次 Young 回收年龄加一，达到阈值进入老年代。阈值由 -XX:MaxTenuringThreshold 设置，动态年龄判定却会让它更低——Survivor 中从最老往回累加超过该区域容量一半时，就取那个年龄作实际阈值。分配速率突增时，这套机制把对象更早推向老年代，形成”看起来像泄漏、其实是压力”的曲线。大对象绕过 Young 区：部分收集器用 -XX:PretenureSizeThreshold 让超长数组直接分配在老年代，G1 用 Humongous Region 承载超过单个 Region 一半的对象。

对象内存布局与压缩指针

普通对象在堆上分四段：标记头（mark word）、元数据指针、实例数据、对齐填充。标记头存哈希值、分代年龄、锁状态标志与 GC 标记位；元数据指针指向类元数据，虚方法分发靠它；实例数据是字段本身，父类字段排在子类字段之前；对齐填充不承载语义，只把总大小补齐到 8 字节的整数倍。

-XX:+UseCompressedOops 把引用从 8 字节压成 4 字节，前提有三条：64 位虚拟机、堆不超过 32GB、对象对齐粒度保持默认。原理是对象起始地址必然对齐到 8 字节，低 3 位恒为零，只需存右移 3 位后的值，32 位指针左移 3 位就覆盖 4G×8=32GB。堆超过 32GB 后指针退回 8 字节，可用对象数因头部膨胀缩水，常说的”31GB 比 33GB 装得多”就是这个塌陷效应（经验口径，需按自己的负载验证）。类元数据指针由 -XX:+UseCompressedClassPointers 控制。

可达性判定与四种引用

Java 用可达性分析判定存活：从一组必须存活的根遍历引用图，走不到的对象就是垃圾。GC Roots 包括：线程栈上正在使用的局部变量与操作数栈引用、类的静态字段、运行时常量池里的引用、JNI 代码持有的引用、活跃线程对象本身、被锁持有的对象，以及分代回收里作为跨区引用入口的卡表与记忆集根。引用链上只要有一个节点被无用的集合抓住，整串对象都回收不掉。

引用强度分四级，各对应一类用途。

软引用适合”可被内存压力牺牲的缓存”，但回收时机由 JVM 决定，命中率不可控；弱引用适合”键或值不该因引用而续命”的场景，典型是以对象为键的附属信息表；虚引用必须配合 ReferenceQueue 使用，拿不到对象本体，只在对象被回收后通知一次，适合清理堆外资源。四种引用都要在回收时被处理，这部分耗时就是后文的 Ref Proc 阶段。

分代假设与两种收集算法

分代是把经验写成结构。弱分代假设说绝大多数对象朝生夕灭，强分代假设说熬过越多轮回收的对象越难死。于是堆切成 Young 与 Old：新对象在 Young 出生，短命对象就地消亡，少数活下来的搬去 Old，每次回收只需扫描很小的区域。

三种算法的取舍很直白。复制把存活对象从一个区域拷到另一个，原区域整体清空：实现简单、天然紧凑、停顿只与存活对象数量相关，代价是必须预留一块空着的 to-space，可用容量打折。标记-清除先标记再清除，空间利用率最高，但留下碎片，后续大对象可能因找不到连续空间而提前触发回收。标记-整理在标记后把存活对象向一端移动并更新引用，不浪费空间也不留碎片，代价是移动引用最费工。

为什么老年代不用复制？复制成本正比于存活对象数量，而老年代正是存活对象聚集地，把大半堆拷一遍纯属浪费；老年代又占堆的主要容量，旁边再留一块等大空闲区域不可接受。Region 化换的是粒度而不是算法：G1 仍用复制，却把”整代”拆成”每次挑若干 Region”，存活多的区域这轮不选，一次回收的代价就能被目标约束。

三个收集器的定位

Serial Old 是单线程收集器，回收时应用线程全部暂停。它的价值不是快，而是简单可靠、内存开销小、不额外吃 CPU：小堆、限成一个 CPU 的容器、本地单元测试，用它反而更稳定。切换用 -XX:+UseSerialGC。

G1 是 Java 17/21 的默认收集器，定位是大堆上的”可控停顿”。它把堆划成大小相等的 Region，扮演 Eden、Survivor、Old 或 Humongous 角色；每个 Region 维护记忆集（RSet），记录”哪些外部区域指向我”，于是扫一个 Region 的根不必遍历整堆。回收分三种：Young GC 只处理 Eden 与 Survivor；Mixed GC 再挑若干回收价值高的老年代 Region；Full GC 是兜底路径，频繁出现说明选区策略已失效。停顿预测模型按每个 Region 的历史代价排优先级，-XX:MaxGCPauseMillis 是目标而非保证：设得过小，可选区域变少，回收更频繁、吞吐下降。

ZGC 的定位是低停顿，机制有两点：一是着色指针，把标记与重定位状态编码进指针本身，让引用能携带”处于哪一轮回收”；二是读屏障，线程读引用时经过一小段检查代码，对象若已被并发搬走就顺手修正。搬移能与业务线程同时进行，暂停只剩根扫描等固定开销，停顿量级与堆大小基本无关。开启方式是 -XX:+UseZGC。

Shenandoah 走并发整理路线，用转发指针配合读屏障，让对象在业务线程运行时被移动并更新引用，把停顿与堆规模解耦。它从 Java 15 起进入 OpenJDK 主线，需要显式开启，在 Java 17/21 里不是默认选择。

Java 21 的分代 ZGC 要单独交代：本批口径下它仍是预览或试验性质，需靠额外参数显式启用，生产默认仍选 G1。它解决的是短命对象也要扫全堆的效率问题，并不改变对堆外内存与类卸载的要求。

停顿从哪里来

GC 不能想停就停，应用线程只能在安全点（safepoint）停下——那是字节码里标记为可安全暂停的位置，线程检查标志位后挂起。收集器设标志后要等所有线程到达，这一步就可能被拖长：在超大数组里循环的线程、持有锁的 native 调用、刚被反优化的解释帧，都会推迟到达安全点，表现为业务线程等待比日志里的阶段耗时更长。此后的根扫描、更新记忆集、复制对象、处理引用属于暂停；并发标记、重定位、清理大多能与业务线程同时跑。

由此能解释一个反直觉结论：堆更大，停顿不一定更长。暂停时间正比于本次要处理的存活对象数量与根集合规模，而不是堆总容量。G1 每次只选若干 Region，堆更大只是有更多区域可以分开偿还；ZGC 的重定位是并发的，堆大小影响并发周期跑多久、要不要多占 CPU，而不是暂停本身。

五个常见误区

  1. 元空间不设上限。只配 -Xmx 不管 -XX:MaxMetaspaceSize，类加载器泄漏会让元空间持续膨胀；容器终止进程时，堆内指标可能全程健康。
  2. 直接内存不受 -Xmx 约束。NIO 缓冲与堆外缓存都算进进程常驻内存，堆内余量充足而容器已接近限额，调 -Xmx 没有帮助。
  3. “Full GC 就是出问题”。晋升阈值压低、元空间到阈值时尝试类卸载、显式调用都会带来老年代回收；该看的是频率与效果，不是它出现过。
  4. System.gc() 只是建议虚拟机回收一次，默认实现触发 Full GC；加 -XX:+DisableExplicitGC 后它近似空操作，代价是直接内存的回收时机失去提示。
  5. 把软引用当缓存。软引用只在内存紧张时按内部策略清除，容量、命中率、失效时间都不由你控制；业务缓存要靠显式容量与过期规则。

小结

内存模型回答”东西放在哪”，GC 回答”什么时候能拿走”，中间那条线是可达性；收集器没有普适答案，只有场景匹配。

收集器 适用场景 本批（Java 17/21）状态
Serial Old 小堆、单核容器、本地测试 可用，需显式开启
G1 大堆、有停顿目标的服务 默认
ZGC（非分代） 停顿极敏感的大堆服务 可用，需显式开启
分代 ZGC 同上，回收效率更高 预览/试验，生产默认仍选 G1
Shenandoah 需要并发整理、可接受非默认 可用（Java 15 起进主线），非默认

实践建议三条：默认先信 G1，没测量前别换收集器；GC 日志与容器内存水位要同时留着，只看堆内会漏掉一半事实；所有阈值都是待验证假设。
