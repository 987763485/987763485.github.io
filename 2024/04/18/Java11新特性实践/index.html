Java 11 新特性实践

Java 11 是 2018 年 9 月发布的长期支持版本，如今已进入维护后期，主线 LTS 推进到 17 与 21。但企业里真实跑着的 JVM 仍有相当比例停在 8 与 11：授权与内部基线要走审批和合规窗口，容器镜像与监控探针常绑定固定 JDK，金融、政企类系统的大版本升级按年度排期。本文整理 Java 11 当时带来的能力，并逐项写清版本归属：哪些是 11 新增，哪些来自 9 或 10，哪些属于 14 到 21 的后继特性。读完应当能判断两件事：仍在 11 上的系统可以直接用哪些写法，升级到 17 或 21 前要先补哪些功课。

为什么今天仍要面对 Java 11

把 11 当作“历史版本”来写，并不是要回到过去，而是因为遗留 LTS 才是很多团队的现状。Java 的发布节奏从 9 开始变成每半年一个特性版本，LTS 则是每两年一个（11、17、21），厂商的免费更新窗口和商业订阅周期各自不同。一次升级要同时评估编译产物能否在旧 JDK 上运行、依赖是否提供支持新 JDK 的版本、运行时参数是否被移除或改名，这三项成本往往高于代码改动本身，于是 11 被长期保留下来。

需要注意口径：Java 22 在 2024 年 3 月刚发布，它只是特性版本，半年后即停止更新，不能当作主线；企业主线仍然是 17 与 21。因此本文对每个特性都标注当时的状态——实验、预览，还是正式可用，这个标签比功能本身更容易被误传。同样要说清楚的是，本文不会把 record、密封类、文本块、虚拟线程写成 Java 11 特性，它们分属 14 到 21，混写会让升级评估建立在错误前提上。

var 与类型推断的使用边界

var 在 Java 10 引入，用于局部变量；Java 11 把同样的写法扩展到 Lambda 参数。它做的是编译期类型推断，不是动态类型：变量的实际类型在字节码里完全确定，只是源码不再重复书写。因此 var 只能用在带初始化的声明上，例如局部变量、传统 for 与增强 for 的索引变量、try-with-resources 的资源；不能用在字段、方法参数、返回类型上，也不能单独声明一个稍后赋值的变量。

Java 11 在 Lambda 参数上的增量只有一处：允许给参数写 var，从而可以带注解。

反过来说，var 会降低可读性的场景也很明确。右侧是方法调用且返回类型不自明时，var result = service.process(input) 迫使读者跳转定义；右侧是菱形泛型构造时，var map = new HashMap<>() 会推断成 HashMap<Object, Object>，比显式类型更糟；同一方法里连续多个 var 会让数据流失去类型锚点。实践建议是：右侧类型一眼可见就用 var，否则保留显式类型，团队统一一条规则即可。语言层面之外，List、Map 的底层结构与扩容在《Java 集合框架与源码解析》里已有专文。

String 与集合 API 的增量

Java 11 没有引入新的集合框架，但对字符串和常用 API 做了一批“补齐型”改动。

String 上新增了 strip、stripLeading、stripTrailing、isBlank、lines、repeat。要区分 trim 与 strip：前者只裁掉码点不大于 0x20 的 ASCII 空白，遇到全角空格等 Unicode 空白无能为力；后者按 Unicode 空白判定，处理中文文本、Excel 导出、配置解析时更可靠。lines 返回按行切分的流，同时识别多种换行组合，省掉手工分割与空串过滤。

Predicate.not 让取反条件可读，配合方法引用尤其明显。

不可变集合要写准归属：List.of、Set.of、Map.of 由 Java 9 引入，Java 11 只是沿用，但它们是这一代代码里替换老写法的主力。三种写法语义并不相同。

要注意的是，List.of 返回的实例连 set 也抛异常，把它赋给期望可变的形参是常见的线上故障来源；常量表、默认配置、枚举映射最适合交给它。

一行式文件读写与单文件源码运行

Files.readString、Files.writeString 与 Path.of 都在 Java 11 落地，把过去要写七八行的文本读写压缩成一行。

适用边界必须写清：这两个方法把整个文件一次读进字符串，或把整个字符串一次写出，只适合配置、模板、脚本这类体积可控的文本。几百兆的日志、CSV 或导出文件不应这样处理，前者要用 Files.lines 配合流式消费，后者要用 Files.newBufferedWriter 或分片通道，否则堆内存会被直接压满。涉及字节而非字符时仍走 Files.readAllBytes 与 Files.write，它们出现得更早。

单文件源码运行同样是 Java 11 的能力，也是它对教学与排障最实用的改动。

它的限制是“一个源文件、一个主类、只能使用 JDK 平台类与类路径上已编译的类”，适合脚本化任务、复现问题和接口验证，不适合替代工程构建。与之配合的是 jshell，它在 Java 9 就已提供，11 上是标准的小段验证工具。

把新 API 的行为差异放在 jshell 里跑一遍再写进代码评审，比在工程里加临时测试类快得多，也是排查本机 JDK 版本差异的首选手段。

标准 HttpClient 的用法与坑

java.net.http 下的 HttpClient 是 Java 11 最受关注的增量。在它之前，标准库只有语义粗糙的 HttpURLConnection，于是大量项目引入第三方客户端，只为拿到连接复用、超时控制和异步回调。11 之后，简单的外部调用完全可以走标准 API。

send 阻塞当前线程，sendAsync 返回可组合的异步结果，两者共用同一套请求构造。响应体处理器决定内存形态：ofString 全量读入，ofByteArray 用于二进制，ofLines 返回按行消费的流、适合大响应，ofFile 直接落盘，discarding 只要状态码与头部；请求体侧有对应的发布器，可来自字符串、文件与输入流。

要记住的坑有三个。第一，HttpClient 要作为长生命周期对象复用，它内部维护连接，每个请求都新建实例会把优势全部抵消；第二，11 里它不实现可关闭接口，实例要靠宿主生命周期回收，这一点到 21 才改变；第三，HTTP/2 依赖 TLS 的 ALPN 协商，部分平台上实际跑在 HTTP/1.1 而日志里没有提示，验收时要看响应携带的版本字段而不是配置值。框架里应当注入哪个客户端属于工程选型，Spring Boot 的默认装配在《Spring Boot 快速开发实践》中已有说明。

Optional 与流式 API：把版本归属写准

Optional 常被归到 Java 11 名下，其实多数成员来自更早版本。ifPresentOrElse、or、stream 属于 Java 9，11 为它新增的只有 isEmpty。这个区分不是学究气：把 or 当成 11 特性写进升级评估，会得出“从 8 升到 11 才可用”的错误结论，而它其实要求至少跨到 9。

流式 API 同理：takeWhile、dropWhile、带种子与步进参数的 iterate 来自 Java 9，Collectors.toUnmodifiableList 等不可变收集器来自 Java 10，Stream.toList 则要等到 Java 16。在仍运行 11 的工程里，能直接组合出的是这样的形态。

这类写法在 11 上完全可用，也不依赖第三方库，是存量代码里最容易落地的改造。至于 CompletableFuture 的编排与并发原语的选择，《Java 并发编程：JUC 核心》专门处理。

低开销诊断：飞行记录器

对遗留版本而言，Java 11 最有运维价值的改动是飞行记录器（JFR）进入了 OpenJDK 并开放了事件定义接口。在此之前它随商业版本提供，多数团队只能在事后用 jstack 和 GC 日志拼图。JFR 的思路不同：事件写入进程内的二进制环形缓冲，采集动作贴近现有执行路径，因此可以常态开启而不是“出事才打开”。

jfr summary 的输出按事件类型列出条数，这是最有信息量的第一屏：分配类事件占比高说明对象产生速率是压力源，锁等待与阻塞事件集中说明瓶颈在同步而不是算力，编译事件密集则要考虑预热是否完成。要看具体维度就按事件名过滤，例如分配、方法执行采样、GC 停顿原因、安全点参与线程数与类加载。这些维度给出的是分布与频次，正确用法是判断哪个维度异常突出，而不是从单条记录读绝对性能结论。需要图形化时，用 JDK Mission Control 打开同一份文件即可。

边界要说清：本文只讲怎么用记录器拿数据，堆的分代与 Region 结构、各收集器的取舍与 GC 日志解读见《Java JVM 内存模型与 GC》，先测量后优化的流程与火焰图见《Java 性能调优实战》，GC 原理与调优另有专文，这里不比较停顿长短。

实验性垃圾收集器：ZGC 与 Epsilon 的当时状态

Java 11 收录了 ZGC 与 Epsilon 两个收集器，但两者的状态标签都是实验性。这不是一句免责声明，而是当时的硬约束：实验性意味着必须显式解锁、参数与行为在后续版本可能变动、出现问题不在支持范围内。

Epsilon 的用途容易被误读：它不回收，堆用满即退出，适合生命周期极短的批处理任务，也适合验证一段代码的分配上界，放在常驻服务上必然失败。ZGC 在 11 的定位是大堆低停顿方向的探索，实验性标签决定了当时不该把它放进生产；它后来才转为正式产品，而 17 与 21 的默认收集器仍是 G1，把今天“某场景可选 ZGC”的经验倒回 11 是常见误判。在 11 上做收集器选型，稳妥结论只有一条：从默认配置起步，改参数前先有基线数据，实验性开关只用于对照验证。

面向 17 与 21 的升级判断

留在 11 的时间越长，越要把“11 里没有的东西”点名归位，否则需求评审会把它当成已有能力。record 在 14 预览、16 转正；switch 表达式在 14 转正；文本块在 15 转正；密封类在 17 转正；instanceof 模式匹配在 16 转正，switch 的模式匹配要到 21 才稳定；虚拟线程在 21 转正，结构化并发在 21 仍是预览。这些都不能写进 Java 11 的验收清单。

升级本身还要处理模块化的历史遗留。Java 9 把 Java EE 与 CORBA 相关模块标记为废弃，Java 11 正式移除，其中影响最广的是 java.xml.bind（JAXB）与激活框架、注解模块，以及 java.xml.ws（JAX-WS）。移除意味着编译期不再报错、运行期抛 NoClassDefFoundError，必须在依赖里补上对应实现包，或者改造代码路径。其他常见的适配点还有反射深度限制带来的 --add-opens、内部 API 不可见、安全策略文件被废弃，以及旧版本字节码增强与监控探针需要跟着升级。

推进顺序建议按四步走。第一步静态盘点，用依赖树与构建脚本确认哪些库提供了支持新 JDK 的版本。第二步隔离编译目标，用 --release 或构建工具里的等价参数保证产物同时跑在 11 与新版本上，避免升级与业务改动混在同一个变更里。第三步在预发以新 JDK 跑全链路回归，重点看序列化、反射、时区与字符集差异。第四步按实例灰度，让 11 与新版本在同一集群并行，用同一份流量比较错误率与资源占用，异常即回切。

flowchart TD
    A[盘点依赖与运行参数] --> B[用 release 参数隔离编译目标]
    B --> C[预发全链路回归]
    C --> D[实例灰度并行观察]
    D --> E[全量切换 17 或 21]
    D -->|指标异常| C

小结

Java 11 的价值不在某个惊艳特性，而在一批把样板代码压掉的小改动：var 简化局部声明、String 与 Predicate.not 补齐表达力、Files.readString 让文本读写变成一行、标准 HttpClient 替代了大量第三方依赖、单文件运行与 jshell 降低验证成本、JFR 让生产诊断可以常开。使用时最要紧的是把版本归属写准：不可变集合工厂、Optional 的 or 与 ifPresentOrElse、takeWhile 来自 9 与 10，record、文本块、密封类、虚拟线程属于 14 到 21，混用会让遗留系统的评估失真。对仍运行 8 或 11 的团队，建议先把这批标准 API 落地，把第三方工具类的重复实现删掉，再按盘点、隔离、回归、灰度四步推进到 17 或 21，一次只解决一个问题。
