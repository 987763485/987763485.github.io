esbuild 与 SWC 编译加速

改一行代码要等好几秒才看到编译结果，这个痛点在 2024 年已有务实解法：把翻译代码这件事交给原生语言编写的编译器，而不是用 JavaScript 写的工具去翻译 JavaScript。本文介绍 esbuild 与 SWC 各自解决什么问题、快在哪里、哪些地方必须把活交回 Babel 与 webpack。适合被构建耗时困扰或准备换工具的读者，读完能得到接入姿势、迁移检查表和度量方法。

传统构建工具慢在哪里

要理解新工具为什么快，得先看清老工具的时间花在了哪里。以 webpack 加 Babel 的组合为例，一个模块从进入构建到产出代码，要经历读取源文件、按 loader 依次转换、解析成语法树、插件做依赖分析、生成代码、压缩。问题不在步骤多，而在步骤之间传递的是字符串。

第一个开销是解析与生成的多次往返：Babel 把源码解析成语法树、转换完打印回字符串，链上若还有第二个转换器，又要重新解析再打印一次。每多一个环节就多一次往返，同一段 JSX 可能被解析三遍，位置信息与注释也在交接中丢失。

第二个开销来自中间语法树的形态：JavaScript 写的编译器里，语法树是堆上散布的大量小对象，节点靠引用连接，遍历就是密集分配与指针跳转，用完留下成批短命对象，规模上去后内存涨得快、GC 停顿频繁。

第三个开销是执行模型：解析与转换在主线程串行推进，文件之间本无强依赖却排队等待，改用多进程或线程池时又要跨线程传递依赖状态与插件上下文，改造代价高、收益打折。第四个开销是磁盘往返：中间产物序列化进缓存目录、命中时再反序列化回来，”缓存命中”并不等于免费。

下图对比两条路线：上半段反复展开再折叠语法树，下半段一次解析、一次生成。

flowchart TD
    A[源文件] --> B[解析为语法树]
    B --> C[打印为代码字符串]
    C --> D[下一个转换器重新解析]
    D --> E[再打印一次]
    E --> F[依赖分析与合并]
    F --> G[独立工具压缩]
    G --> H[产物落盘]
    I[源文件] --> J[解析为内部语法树]
    J --> K[同一棵树上有符号链接与依赖收集]
    K --> L[多文件并行转换]
    L --> M[内置压缩后一次写出]

看清这四类开销，就能理解加速工具的设计动机：减少往返、紧凑的语法树结构、文件级并行、少落盘。语言选择只是手段，不是原因。

esbuild 的设计选择与能力边界

为什么它快

esbuild 用 Go 语言重写，发布形态是平台相关的可执行文件，构建时不再依赖 Node 运行时的解释与垃圾回收。它的加速点逐条对应上一节的四个开销：同一份语法树完成解析与生成，词法分析、符号链接、转换与打印共用一套紧凑结构，环节之间不再打印成字符串重新解析；跨文件并行，扫描、解析、转换按文件推进，与依赖图构建重叠，单个慢文件不拖住流水线，这是最主要的收益来源；内置压缩，在同一进程完成，省掉交给独立工具再读回来的往返；少落盘，输入到输出尽量留在内存，一次写出。

边界在哪里

快是有前提的，把边界写清楚比只讲优点有用。

它不做类型检查。 esbuild 处理 TypeScript 的方式是”擦除类型”：解析时容忍类型标注，输出时去掉，仅此而已。类型错误、不兼容赋值、缺失导出它一概不管。因此迁移后 tsc 仍要在流水线里跑，只是不再负责产出代码：

这条分工要和团队讲明白：构建变快不等于类型检查消失，否则 CI 会出现”编译通过但类型是错的”。类型检查自身的优化是另一个话题，本文不展开。它也不生成 .d.ts，声明文件仍要 tsc 或专门工具产出。

语法与特性支持有具体限制。 以 0.20 前后的版本口径来看，迁移前用自己的版本逐项实测：

  • const enum：跨文件常量枚举内联在当时的版本里支持有限，isolatedModules 下容易退化成普通枚举；
  • 装饰器：主流形态仍是旧版实验性装饰器，标准装饰器当时刚开始对齐；
  • emitDecoratorMetadata：不输出装饰器元数据，依赖 reflect-metadata 的注入写法不能直接替换；
  • 有运行时语义的构造：namespace 值合并、参数属性、import = require 要逐个确认；
  • 不做 polyfill 注入：target 只降级语法，运行时补齐不归它管。

这些限制不构成否决，但决定了 esbuild 在流水线里的正确位置：负责快，不负责全。

esbuild 的四种常见接入姿势

接法不对同样拿不到收益。下面四种姿势覆盖大多数项目。

第一种：只做转译，不做打包。 风险最低的切入点：把 ts-loader 或 Babel 的语法降级交给 esbuild，打包仍归 webpack 负责，产物结构与插件生态不变。

这种模式要额外对齐影响单文件语义的选项：JSX 工厂、useDefineForClassFields、装饰器开关；依赖路径解析的 paths 不会被完整尊重。

第二种：单文件打包。 小工具与内部脚本适合一条命令产出可运行文件，连依赖一起打进去。

第三种：作为库的构建器。 要点是多格式输出、外部依赖声明与源码映射。

硬约束是 esbuild 不产出 .d.ts：声明仍要 tsc --emitDeclarationOnly 补一步，在同一任务里串联。库产物开 minify 要谨慎，局部名字失去意义、堆栈可读性下降，很多团队选择不压缩、留给使用方去压。

第四种：开发与生产两套配置。 开发要反馈速度：监听、增量重建、不全量压缩；生产要产物质量：压缩、分片、目标降级。

混用一套配置的后果很常见：开发时被压缩拖慢，生产时漏掉压缩。

顺带说明一句边界：esbuild 在 Vite 中承担依赖预构建一类的角色，但那套机制的细节不在本文范围内，此处不展开。

SWC 的定位与基本用法

SWC 是另一个方向的解法：用 Rust 编写的编译工具。它与 esbuild 的关键差别不在语言而在定位——主战场是转换，即把一份源码按目标语法改写成另一份源码；打包、最小化、解析只是配套能力，转译才是第一公民。

生态位置只述事实：Next.js 在 2024 年已经把 SWC 作为默认的编译与打包路径，这说明它的转译正确性在大规模真实项目上被反复验证过；Next.js 侧的配置取舍属于框架篇目，本文不展开。

SWC 插件机制与 Babel 生态的迁移现实

Babel 的护城河不是语法转换而是插件生态。换掉它之前先回答一个问题：我们的插件能不能换。

SWC 的插件用 Rust 编写、编译成 Wasm，在编译期直接操作 SWC 的语法树，配置里通过 jsc.experimental.plugins 声明。速度远超 JavaScript 插件，代价也明确：作者要会 Rust，要跟随 SWC 的语法树定义，调试手段更少。

迁移现实因此分成三类：

  • 可直接替换的：TS 与 JSX 语法转换、常见 ES 提案降级、import 形态转换、自动运行时，都是 jsc.transform 的内置能力。
  • 移植后才能替换的：埋点注入、编译期常量替换、日志织入等自定义插件，要重写为 Wasm 插件，成本取决于原插件对 Babel 工具函数与访问者状态的依赖深度。
  • 当时替换不掉的：依赖 Babel 运行时机制的宏类方案、依赖转换上下文的复杂改写、输出装饰器元数据的插件、与框架约定绑定的调试插件；这类项目就让 Babel 继续处理它们。

转译与打包是两条路线

把两者理解成”更快的 webpack”是最常见的误判：它们替代的是不同环节。

flowchart LR
    S[源码] --> T[转译层: esbuild 或 SWC]
    T --> R{产物形态}
    R -->|单文件与应用| B[简单打包: esbuild/SWC]
    R -->|库与精细分片| P[精细打包: Rollup 或 webpack]
    P --> O[产物与运行时]
    B --> O

转译层只处理单个文件，输入输出都是文件粒度，天然可并行，快工具在这里收益最大。打包层要解析依赖图、决定模块进哪个分片、处理循环依赖、生成加载运行时代码，这些工作彼此耦合，很难靠并行解决。

于是合理的分工出现：esbuild 或 SWC 负责快，Rollup 或 webpack 负责细。 各自擅长的产物形态也不同。

  • esbuild：应用的单文件或少分片产物、内部工具、Node 服务端脚本、库的双格式产出；tree-shaking 有效，但副作用边界与分片命名的控制不如专用打包器精细。
  • SWC：TS 与 JSX 的转译本身、作为框架的编译后端；它的打包能力在 2024 年仍在补齐，多数项目不用它做最终打包。
  • Rollup：以 ESM 形态发布的库，副作用标注与摇树精度成熟，产物接近手写。
  • webpack：资源种类多、需要复杂分片策略与运行时能力（模块联邦、按分片加载）的大型应用。

记法：转译换工具，打包看诉求；多数项目最优解是新工具做转译、老打包器做产物。

最后一项最容易被低估：内置 loader 能处理常见资源类型，但单文件组件要先拆开模板与脚本，样式模块化与预处理也各有链路，这些不在默认能力内，仍要靠专用插件完成。

如何度量收益

“快了好几倍”无法复现，也没有价值。度量要固定输入、分轮次、按阶段拆开。

对照组要同一份输入、同一台机器、同一依赖版本；冷启动与重复构建分开记录，并行收益在这两种场景下并不一致。再按解析、转译、打包、压缩分别计时，才知道慢在哪一步、该换掉哪一段。

结论要写成条件区间而不是单点：文件多、单文件小、核数多的项目并行收益明显，只有几个巨型文件时收益有限。本文不给统一倍数，具体数字都只在特定机器上成立，属于示意值。

什么时候仍该用 Babel 或 webpack

以下情形保留原方案更划算。

  • 构建依赖成体系的自定义插件，且深植于 Babel 的访问者机制：重写成本高于省下的时间。
  • 需要精细的分包与产物控制：命名分片、按路由切分、共享依赖协商。
  • 转换不止语法一层：样式抽取、文档注入、编译期写死变量、覆盖率统计。
  • 浏览器基线很低，需要构建层统一承担运行时补齐的责任。
  • 团队更看重可预测性：换工具的收益盖不住回归验证的成本。

判断口径是一句话：转译瓶颈就换，语义与生态瓶颈先估迁移成本。

小结

esbuild 与 SWC 的价值来自结构性选择：一次解析一次生成、文件级并行、转译与压缩在同一进程，而不是把循环换快。它们的边界同样清楚：不做类型检查、不生成声明文件、对需要运行时语义的语法支持有限。让它们做流水线里最快的那一段，把类型与精细产物留在原处，是风险最低的用法；收益自己测，结论写成条件区间。
