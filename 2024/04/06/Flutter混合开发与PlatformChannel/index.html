Flutter 混合开发与 Platform Channel

很多团队的 App 并非从零开始：原生代码跑了多年，埋点、推送、账号体系都长在原有架构上，而 Flutter 的价值常常只需要在两三个高频迭代的活动页上兑现。本文讲这种局部引入的做法——原生侧怎么承载引擎、怎么预热、页面栈怎么对齐，以及三条通道各自适合干什么、坑在哪。

为什么要把 Flutter 放进原生工程

混合开发（add-to-app）的动因大致三类。

第一类是存量原生 App 的局部引入。首页与交易链路被自定义容器、路由中间件等原生基建包裹，一次重写风险太高。稳妥做法是把 Flutter 当作一种页面实现方式，在原生栈里挂一个容器，先替换一两个低风险页面。

第二类是团队技能与组件复用。同一套券卡片、富文本组件要在手机与平板上呈现，写一次比两套技术栈各维护一份划算；Flutter 的 UI 是自绘的，跨机型一致性问题也更少。

第三类是需要频繁发版的业务页面。原生改动要走商店审核，周期不可控；这类页面放进 Flutter 产物，迭代节奏明显加快。

但有些场景不该混。性能敏感的先排除：相机预览、直播推流、地图拖拽、长列表密集交互，native 侧优化路径更直接，多一层通道只增加往返成本。手势与输入法密集的表单页也要谨慎，键盘升降、焦点切换、滑动返回都得额外同步。渲染方面，2024 年 4 月的 3.19 口径下 Impeller 只在 iOS 是默认后端，Android 仍属预览或可选，两端首帧不能套同一结论。

接入形态与工程结构

混合接入有两种形态，取舍核心是构建速度与版本对齐成本谁更痛。

源码依赖把 Flutter 模块以工程形式被原生构建系统引用。改一行 Dart 就能跑起来，适合小团队验证；代价是每次原生构建都触发 Flutter 编译，CI 变慢，开发机还得装齐 Flutter SDK、JDK 与 CocoaPods。

产物依赖把模块编译成 AAR 或 Framework，原生只依赖二进制。构建几乎不变慢，两侧可由不同流水线出包，版本以产物号锁定；代价是需要一条发布流程与一张版本对应表。中大型团队通常选后者，把模块当内部 SDK 管。

引擎预热与首帧成本

用户点开第一个 Flutter 页面时感觉慢半拍，原因是几件事挤在同一次点击里：引擎初始化、起线程、创建并加载 Dart isolate、执行入口、布局与合成首帧，最后才轮到页面请求数据。这些成本只在第一次付，所以首屏慢，之后 Flutter 页之间跳转很快。

debug 构建更慢一截，它是 JIT 口径，代码边跑边编译；profile 与 release 走 AOT。用 debug 包判断混合页首帧，结论基本会错。

预热就是把那串初始化从点击里挪出来，常见三档。启动即预热：在启动空闲时机建引擎放进缓存，收益最大，代价是启动阶段多占内存与一点 CPU。入口曝光时预热：在用户大概率点开的入口出现时建引擎，浪费更小，但需要埋点。不预热：只在页内做骨架屏与占位，把慢变成看起来不慢。

内存代价按引擎数量算。一个引擎一份 isolate 加一份 Dart 堆，示意值在十几 MB 到几十 MB，取决于产物与图片持有量；用组时共享部分不再重复，但 isolate 增量仍线性增长。常见约定是全局一个常驻引擎，确需多个页面并行时才引入组，并给组容量设上限、退出时显式回收。帧率与耗时数字由性能专文测量，本文不下结论。

路由与导航同步

混合开发里同时存在两套导航栈：原生的 Activity 栈或导航控制器，以及 Dart 侧 Navigator 的路由栈。它们各自合法，用户却只有一份心智：按下返回要回到上一个页面，不关心是谁渲染的。

所以必须有一张统一路由表：原生侧维护路径到承载方式的映射，命中 Flutter 路径就启动容器并把路径与参数交给引擎，命中原生路径走原有分发。深链也要过这张表，否则外部链接会绕过容器落到默认页，参数丢失。

参数与结果回传最容易出错。原生打开 Flutter 页时把参数随初始路由传进去，页面完成后要把结果还给原生再关闭。正确做法是 Dart 侧通过通道发一条关闭并回传的消息，由原生执行关闭，而不是让原生猜 Dart 的栈何时空了。若原生销毁容器而 Dart 路由没清理，缓存引擎里会留下悬挂页面，下次进入看到上次残留。

同一容器里装了多个 Flutter 页时，原生只有一层、Dart 有三层，原生返回要转成 Dart 出栈请求，只有 Dart 栈见底才真正关容器；这套协议写死在容器基类里。Dart 侧路由方案本身——命名路由、参数解析、转场与守卫——另有专文，本文只处理它与原生栈的边界。

三类通道：语义差别与选型

平台通道的三条通道差别不在性能而在语义模型，选错会写出难维护的代码。一次典型的混合页调用链如下：

flowchart TD
    A[原生路由表] --> B[混合容器]
    B --> C[缓存引擎与 FlutterView]
    C --> D[Dart 页面]
    D --> E[MethodChannel 请求]
    E --> F[原生 handler]
    F --> G[后台线程取数]
    G --> E

MethodChannel 是一次请求一次响应，适合做一件事并要结果：调原生登录、取定位、读设备信息。

EventChannel 是单向流：原生持续产出、Dart 只消费，适合传感器、进度这类没有终点的数据。

BasicMessageChannel 是双向消息通道，编解码器可替换，适合大块字节或高频小消息：图片二进制、协议报文原样递过去。

选型口诀：要结果用 MethodChannel，要流水用 EventChannel，要字节或高频小包用 BasicMessageChannel。

编解码器：类型映射与字节缓冲

通道两端的对象必须先过一层编解码器。默认的 StandardMessageCodec 使用紧凑的二进制格式，两端支持的类型如下（Android 为 Kotlin/Java 类型，iOS 对应 Foundation 类型）：

Dart Java/Kotlin 备注
null null
bool Boolean
int Int/Long 超 32 位用长整型
double Double
String String UTF-8
Uint8List ByteArray 原始字节
ByteData ByteBuffer 定长缓冲
List List 元素须在表内
Map Map 键值须在表内
BigInt BigInteger 谨慎用

表外类型不会被自动序列化，只会抛出难以定位的编解码异常。第一条纪律因此是：通道参数只允许表内类型，业务对象在两端各做一次显式转换。

第二条关于大数据。字典每次拆装都要遍历结构并逐个编码，几 MB 的图片塞进 Map，两端都在做无谓的分配与拷贝。字节缓冲不同：Uint8List 到 ByteBuffer 基本是一次内存搬运，Dart 按视图读取，不产生副本。图片、音视频帧、协议体都该以字节形式过通道。

第三条关于线程。原生 handler 默认跑在平台主线程，网络、磁盘、加解密都要切到线程池，结果回来再用主线程交付 result，在子线程直接回调是错的。Dart 侧同理：通道回调进入主 isolate，把解析大 JSON、遍历长列表留在回调里就会掉帧，耗时计算应交给 compute 或后台 isolate。这与渲染管线无关，帧率分析见性能专文。

契约、兼容与排障灰度

通道名与方法名是接口，要像接口一样管。三个做法几乎必需：通道名与入参出参集中写进 Dart 与原生两侧的常量文件，让改一个字段要动几处在评审时看得见；方法语义只加不改，废弃方法保留兼容期并打日志；每个通道配一个协议版本号，原生按版本分支，避免老 App 收到新产物后错乱。

缺实现时必须有降级。同一份 Dart 代码在三端上跑，方法可能只在其中一端实现，Dart 侧抓到 MissingPluginException 就要走兜底，而不是让页面卡在加载态。浏览器没有原生 handler，依赖通道的功能要在 Web 分支给出替代实现或屏蔽入口。

另一个坑是同名不同义：Android 的长整型与 iOS 的数字对象落到 Dart 都可能变成 int，溢出与精度行为却不一致。金额与时间戳要在协议里写死单位与量级，再用一份契约测试比对各端返回值形状，纳入构建流程。

混合页最难的是出问题说不清在哪一侧。最省事的办法是一条链路标识：原生打开容器时生成 traceId 带进 Dart，每次通道调用再带回原生，日志里分发、请求、响应三段用同一条 id 串起来。通道至少打四类点：发起、进入 handler、耗时超阈值、失败降级。

观测口径要把容器拆开：内存按原生容器、引擎、Dart 堆三段统计，只看进程总内存会得出 Flutter 页无所谓的错觉；引擎数量与缓存是否回收是判断内存问题的第一入口。卡顿要分清是主 isolate 被回调占住还是渲染本身重，两者修法相反。

灰度时保留原生页实现：开关按用户维度下发，命中实验走混合容器，未命中走原生页。此外要有失败即回退的硬保护——容器初始化异常、首屏超时、通道连续失败达阈值时直接关闭入口并上报。

小结

混合开发的价值只在于把 Flutter 用在它擅长的页面上，而不是换掉整个 App。产物形态上，中大型团队用产物依赖并把模块当内部 SDK 管版本；容器先用最简承载，只有需要跨页面存活与预热时才自己持有引擎；预热把首帧成本从点击里挪出来，代价是常驻内存；路由要有统一映射表，返回栈只在一个地方同步。三条通道的边界见下表。

通道类型 语义 典型用途 常见坑
MethodChannel 一次请求一次响应 原生登录、设备信息 主线程做耗时任务；方法名无契约
EventChannel 原生到 Dart 的单向流 传感器、连接状态、进度 onCancel 未停推送致泄漏；手搓轮询
BasicMessageChannel 双向消息，编解码器可换 图片字节、协议报文 大对象塞进 Map 反复拷贝
降级回退 缺实现时走兜底 灰度与老版本 缺实现未兜底，页面永久加载
