Kotlin 与 Java 互操作

Kotlin 落地到真实项目里，绝大多数情况不是把 Java 全部换掉，而是两种语言在同一个模块里长期共存。本文要处理的是这种共存带来的语义变形：一段代码单独看都没错，跨过语言边界之后行为却和预期不一致。读者是准备在存量 Java 工程里引入 Kotlin、或已把 Kotlin 写成对外接口的开发者。口径是 Kotlin 1.9.x 与 Java 17/21。

混编才是常态

实践里 Kotlin 很少独占一个仓库。常见的是三种位置：其一，存量 Java 模块继续存在，新写的 Kotlin 调用它的类和工具方法；其二，框架提供的回调接口、注解、SPI 约定由 Java 定义，Kotlin 只是实现方；其三，你写出的公共 API 要交给还在用 Java 的下游团队消费。三者指向同一个事实：Kotlin 和 Java 之间没有字节码屏障，编译产物就是普通 class 文件，任何 JVM 语言都能加载。

真正的障碍在语言层。Kotlin 的可空类型、属性、默认参数、扩展函数、不强制受检异常，在 Java 那边没有一一对应的概念。于是互操作的问题从来不是能不能调用，而是调用过去之后语义会不会变形：拦住空值的类型检查消失了，属性变成了两个方法，默认参数在 Java 侧看不见。这些变形不会让编译失败，只在运行期或者同事的调用点上暴露。

涉及空值语法本身和扩展函数原理的部分不再展开，本文只谈边界。

平台类型与可空性注解

为什么既不报编译错也不保证安全

Java 代码通常不带可空性信息，Kotlin 编译器读到 Java 的方法签名时，无法判断返回值和参数允不允许为 null。它既不假设可空也不假设非空，而是给这种类型一个特殊地位：平台类型。写代码时它看起来像普通类型，赋值传参都不受限制，但编译器不会在解引用前插入任何检查。下面是最典型的一条爆雷路径。

编译过程完全正常，返回值被当成可以直接使用的东西。NPE 发生在运行期，堆栈落在 Kotlin 文件里，看起来像类型系统失守，实际失守的是信息：null 的可能性在 Java 那侧就已经无法表达了。参数方向同理——Kotlin 把一个可能为 null 的值传给 Java 方法，编译器也不拦。

三种修法

第一种是尽早转成显式可空，把不确定性收敛在离 Java 最近的接收点上。

第二种是加注解，让 Java 侧把信息补回来。Java 一旦标注，Kotlin 推断出的就是真正的可空类型，不必在每个调用点重复处理。

第三种是集中校验，适合那种”按约定这里不该为空，一旦为空说明环境坏了”的场景。

选择有规律：能改 Java 就加注解，收益全局；改不了别人发布的 jar 就在接收点标注可空；校验函数只用于确认不该为空的关键路径。

注解只是提示

Kotlin 能识别的可空性注解不止一套：JetBrains、Android、Spring 各自提供的那几组，以及 JSR-305 定义的那一族，都能参与编译期推断。Kotlin 对 JSR-305 的处理严格程度还可以用编译选项调整，例如打开 -Xjsr305=strict 之后，连类型参数里的可空性也会生效。

但要记住：注解只是编译期的提示，运行期并不保证。Java 方法标了非空注解却返回 null，Kotlin 侧照样接得住，因为注解不会在字节码里生成任何校验逻辑。可空性信息的可信程度取决于写注解的那个人，而不是编译器。反过来，你给 Kotlin 函数加的注解，Java 侧工具未必认识。

Java 侧看 Kotlin：三个注解

Kotlin 的属性、伴生对象和默认参数在字节码里有 Java 不认识的形式，三个 @Jvm 开头的注解就是把形式修正回 Java 习惯的样子。

@JvmStatic 解决”必须绕过实例”的问题。Kotlin 的 object 和伴生对象都会生成一个实例字段，不加注解时 Java 只能写成 Ids.INSTANCE.next("u-")，工具类看起来非常古怪。

@JvmOverloads 解决 Java 看不见默认值的问题。带默认参数的方法编译后是一个全参数方法加一个合成方法，Java 侧调用必须把所有参数写全。加上注解后，编译器按默认参数从右往左依次裁剪，为每个组合生成真正的重载。

@JvmField 把属性变成字段，代价要清楚：Java 侧可以直接给字段赋值，你写在访问器里的校验全部失效；对按 bean 规范反射读属性的序列化框架来说，没有 getter 意味着这个属性可能不被识别。除非是常量，或者纯粹想给 Java 一个字段视图，否则不要轻易用。

fun interface 与 SAM 转换的边界

Kotlin 侧调用 Java 的函数式接口时，lambda 会自动完成 SAM 转换，这一点和 Java 体验一致。反方向就有讲究：Kotlin 里声明的普通接口，历史上不接受 lambda；要让两边都能用 lambda 实现它，就显式写成 fun interface，它只允许有一个抽象方法。

真正的边界在函数类型上。参数写成 Kotlin 的函数类型时，Java 侧看到的是 Function0 那类接口，名字生硬，还连带要求消费方依赖 stdlib。结论很直接：给 Java 消费的 API，参数位置用 fun interface；只在 Kotlin 内部流转的高阶函数才用函数类型，它更灵活，能带接收者。另外，SAM 转换只作用于接口，抽象类不在范围内。

属性与 JavaBean 的相互识别

Kotlin 的 var name: String 编译后是一个私有字段加一对 getName/setName，val 只生成 getter。Kotlin 没有引入新的运行时概念，只是把方法对折叠成更简洁的书写；Java 侧看不到属性，只看到方法。

反过来，Kotlin 会主动识别 bean 规范。getFoo() 被看成名为 foo 的属性，isFoo() 被看成名为 isFoo 的属性——注意保留 is 前缀，不会变成 foo。Kotlin 侧也遵守同一条约定：属性名以 is 开头时 getter 就叫 isXxx，不会叠成 isIsXxx。

隐患在可变性和副作用上。

属性语法掩盖了每次访问都是一次方法调用这件事，getter 里可能有耗时计算、可能返回不同对象、可能有副作用，写法上看不出来。更要紧的是可变性：getter 与 setter 不成对时属性就消失了——可见性不同，或者返回类型不一致，Kotlin 都无法合成自洽的属性，只能退回方法调用。

集合与数组

List<T> 和 MutableList<T> 运行时都是同一个 java.util.List，区别只存在于 Kotlin 的类型检查里：只读视图不给调 add，可变视图给。结论必须记牢——只读是编译期约束，不是运行期不可变。

readOnly 不能调 add，但任何持有 shared 的人都能往同一个对象里塞元素，readOnly 立刻跟着变。真要不可变，得交给 Collections.unmodifiableList 这类运行期包装，或者传副本。

还有一处容易被忽略：Kotlin 把 List<T> 用作参数类型时，字节码里生成的是 List<? extends T>，而 MutableList<T> 生成的是 List<T>。这个通配符在 Kotlin 侧看不见，Java 侧接手你的 API 时却会变成”只能读不能写”的麻烦参数。抹掉它用 @JvmSuppressWildcards，想反向加回用 @JvmWildcard。

数组是另一套映射。Array<T> 就是 T[]，IntArray/LongArray/BooleanArray 等对应 int[] 等基本类型数组，不带装箱。Java 的 int[] 在 Kotlin 里就是 IntArray，反过来 Array<Int> 编译成 Integer[]，性能敏感的循环要避开后者，需要时用 toIntArray()/toTypedArray() 转换。

默认参数、可变参数与重载歧义

默认参数的底细要先说清：不带 @JvmOverloads 时，Kotlin 生成全参数方法加一个 $default 合成方法，后者只供语言内部使用，Java 侧调不到，等于默认值不存在。同一个函数在 Kotlin 里可以按名字跳着传参，Java 侧只能严格对齐位置。

vararg 编译成数组参数，Java 侧照常传数组或者逐个列出；Kotlin 侧多一个展开操作符，用星号把已有数组摊进参数位置。要留心 vararg 不在最后一位的签名——Java 调用者必须先传完数组再按位置补后面的参数，跨语言的 API 应避免这种形状。

异常与异步的边界

Kotlin 不区分受检与非受检异常，所有异常都按非受检处理，函数签名上也不写 throws。差异由此产生：Java 调用会抛 IO 异常的 Kotlin 函数时，编译器不提示也不强制捕获，调用方很容易什么都不处理。补救办法是 @Throws：把异常写回方法的异常表，Java 侧重新看到 throws 声明、重新被要求处理。

反方向也成立：实现 Java 声明了受检异常的接口时，Kotlin 不必把异常重新抛出去，但捕获它们是合法的。跨语言边界的包装策略建议收敛成三类：原样透传、包成领域异常并保留原因链、或者返回结果对象让调用方被迫检查。

异步部分只谈接口形态。挂起函数编译后会多出一个 Continuation 参数，Java 侧看到的是 Object search(Continuation<? super String>)，基本没法直接调用，桥接要显式写门面。

门面层把 suspend 留在 Kotlin 内部，让 Java 只看到自己熟悉的类型。Flow 与 Reactive Streams 的 Publisher 之间有专门的适配模块可互转，同样由门面解决，这里不展开。

混编工程实践

源码目录上，Kotlin JVM 插件同时接受 src/main/java 与 src/main/kotlin。文件放进 java 目录也能编译，但两边分开约定更省事。

编译顺序是 Kotlin 先、Java 后：Kotlin 编译器会解析同模块的 Java 源码，产出 class 文件，再由 javac 消费。所以两个方向都能互相引用，不需要预先抽取接口。代价是增量构建变慢——改动一个被广泛引用的 Java 文件往往连带触发两步编译。

有个坑只在混编时出现：Kotlin 接口里带实现的方法仍会生成一个内部的默认实现类，Java 实现类不会自动获得实现，得手写转发。当时可以用编译开关让 Kotlin 生成 Java 8 的默认方法，但那仍是要显式打开的非默认行为，跨语言接口最好保持纯抽象。

-Xexplicit-api 强制公共声明显式写出可见性和返回类型，漏写就报警告或错误。它适合库作者：模块被别的团队当 API 消费时，隐式公开的东西迟早变成维护负担。当时这是一个默认关闭的可选模式，应用模块不必打开。

迁移节奏建议四步。先挑一个不对外暴露的叶子包试写，把编译链路跑通；跨语言的公共接口保持 Java 形状，需要的注解一次配齐；由内向外扩展，不要顺手重写别人正在消费的签名；最后留好回退预案——真要退回 Java，工作量集中在缺少注解而改动的调用点上，所以每个新写的 Kotlin 公共 API 都该配一个 Java 侧冒烟调用测试，既是文档也是最便宜的兼容校验。

小结

互操作的麻烦可以归结为一句：Java 的语言层信息比 Kotlin 少，缺的那些不会自动补齐，只会以变形的样子出现。平台类型补可空性、三个注解补形式、@Throws 补异常声明、门面补异步形态，本质是同一件事——把缺失的信息显式写回去。下表按需求整理。
