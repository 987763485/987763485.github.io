Kotlin 空安全与扩展函数

Kotlin 的类型系统把 null 变成编译期必须处理的信息，但工程里炸出来的 NullPointerException 仍然来自三个缺口：平台类型、集合元素，以及绕过构造器的赋值。扩展函数是另一件事，它看着像给类型补了方法，实际按声明类型静态分派，误解它就撞上“覆盖不生效”的怪现象。本文从会出错的代码讲起，落到可以照着做的写法约定。

空指针的真实来源

非空类型不接受 null：val name: String = null 直接编译失败，容纳 null 必须写成 String?，可空类型也不会隐式变回非空。真正的风险不在规则本身，而在三个管不到的缺口。

第一个缺口是平台类型。Java 的编译产物里没有可空性信息（要补充可空性注解才有，注解体系与互操作细节另篇专讲），Kotlin 只能把 String 理解成“既可能非空也可能为 null”的未知状态，记作 String!，不强制你判空。

显式写成 val name: String = api.nickName(id) 时，编译器会在赋值处插入一次空检查，异常至少在边界抛出；省略类型标注时这次检查根本不发生，栈顶那行离真正返回 null 的调用可以隔好几层：查不查取决于你怎么写。标准库对 JDK 常见方法做了可空性映射，BufferedReader.readLine()、Map.get() 直接是可空返回，替调用者提示“这里确实可能没有值”。

第二个缺口是集合与泛型。Java 的 List<String> 进入 Kotlin 后元素可空性未知，泛型又在运行期被擦除，list.forEach { it.length } 照样能炸。第三方库尤其明显：作者允许 null 的边界未必和你的声明一致。

第三个缺口是绕过构造器的赋值。序列化、反射填充这类机制会在对象构造完成之后往字段写值甚至写 null，此时非空声明没有执行者。结论是空安全只在数据全程待在这套类型系统里时才成立，外部进来的数据应当在边界处收敛，别带着未知状态穿过业务逻辑。

可空类型与调用姿势

String? 是“要么是 String，要么是 null”的联合，用之前必须处理这个分支，常用姿势有四种。

安全调用 ?. 在接收者为 null 时短路并返回 null，适合“取一路属性，中间断掉就算了”，代价是结果类型一路可空。Elvis 操作符 ?: 提供兜底值，右侧只在左侧为 null 时求值，因此可以写成 ?: return、?: throw IllegalStateException(...) 这样的卫语句。

?.let { } 把非空值传给一段代码，用于“非空才做这件事”。它的返回值由 lambda 决定，于是 x?.let { println(it) } ?: println("没有值") 在 x 为 null 时照样会打印出点什么，而本意只是“没值就别说话”，这种场景用 also 或 if 更贴合意图。

!! 把可空断言成非空，失败时抛出没有业务信息的 NullPointerException。可接受的场景只有一种：此处为 null 说明前置条件已被破坏，你希望它尽早炸。即便如此也更推荐 checkNotNull(value) { "缺少必要配置" } 与 requireNotNull(value)：异常类型可控、能带消息，标准库还给它们声明了契约，调用后编译器会认账该变量非空。纪律上，!! 不该出现在库的公开路径上，评审时它是一个需要解释的记号。

收敛集合用 filterNotNull() 与 mapNotNull { }；可空成员用局部快照 val addr = user.address ?: return，一次把不稳定引用变成非空局部值。

智能转换及其失效条件

编译器会沿控制流把可空值收窄，这叫智能转换：if (name != null) 之后直接用 name.length 合法，再写 name!! 就是噪音，if (value is String) 同理。成立前提只有一个：从检查点到使用点，这个值没被别人改过。凡是改得了的地方，收窄失效。

原因是 token 是可变成员属性：两次读取之间可能被别的线程或本类其他方法改掉，编译器无法保证第二次读到的还是非空。失效条件大致四类：一是 var 成员属性；二是带自定义 getter 的属性与 open 的 val，getter 可能在子类返回不同结果，跨模块声明时更是看不见实现；三是被 lambda 捕获的局部 var，闭包内的写入时机不可控；四是泛型的可空性推断冲突，is 只能确定容器类型，元素那一层收窄不到。

修法是把不稳定变成稳定。

局部 val 不可变，编译器乐意一路推断到底；确需保留可变性时，可以用契约把“返回真就代表非空”这条知识补给编译器，下一节讲。看到报错就顺手补 !! 是错的方向：它把数据流该承担的责任挪到了运行期。

lateinit、by lazy 与构造期不可用

有些值无法在声明时给出：它依赖构造完成之后的赋值，或者代价高、可能永远用不到。两个出口的失败表现完全不同。

lateinit 是对编译器的承诺：使用前我一定赋值。它只能用在非空、非基本类型的 var 上，Int、Long 没有空引用可言。破坏承诺的代价是读取时抛 UninitializedPropertyAccessException，抛出点通常离真正的写入时机很远。::header.isInitialized 能探测，但那只是把运行期检查搬回代码，不该当常规防御；更稳的做法是写入方赋值完成后再暴露对象，或者把该值放进构造参数。

by lazy 把初始化推迟到首次访问，默认加锁保证只计算一次。它的失败不是读到未初始化，而是初始化表达式自己抛异常，异常传播给调用方且不会被缓存，访问越频繁、依赖越不稳，代价越大。

构造期是这两个工具的边界：by lazy 属性在构造函数里被读取，延迟立刻失效；若表达式又依赖尚未写入的 lateinit 字段就当场抛异常。选择依据是值由谁产生、时机是否受自己控制，而当两者都在掩盖“构造参数没给全”时，先回去调整构造函数。

契约式编程

智能转换失效，本质是编译器缺一条它推不出来的知识，契约就是补这条知识的语法。requireNotNull 与 checkNotNull 比普通断言好用，正因为标准库给它们写了契约：调用之后编译器知道参数非空，下游不用再取快照。

另一类是 callsInPlace，声明高阶函数参数里的 lambda 会被执行几次；returnsNotNull() 则承诺返回值非空。它换来的是“块内赋值一定会发生”，调用点之后就能把变量当已初始化的值使用。

用契约要记住三点：它必须是函数体的第一条语句，写进分支或循环不生效；它只是作者与编译器之间的约定，运行时不校验，实现与承诺不一致时，错误的收窄会安静地送到每个调用点，比一次空指针更难定位；契约随元数据导出，改实现必须同步改契约。

返回可空还是抛异常，看缺失算不算正常业务分支。找不到记录、选填项没填，本来就有两种状态，返回可空最诚实；违反前置条件、走下去只会写坏数据，就抛异常，或者用带契约的断言函数把这件事变成编译器的推力。

扩展函数的本质：静态解析

扩展函数不改变目标类型，也不往对象里塞字段。它编译成一个普通静态方法，接收者作为第一个参数，value.ext() 只是把这层传递写得好看些。由此产生一条容易被忽略的规则：扩展按声明类型分派，而不是运行期类型。

同一个 Dog 实例，成员函数走了覆盖，扩展函数没有：shout 里的 a 声明为 Animal，编译器在这行就选定了 Animal.describe()。同理，扩展不能盖过成员，已有同名同签名成员时成员永远优先，你的扩展要么不可达，要么让调用者困惑；它也无法被 override，因为没有可占的分派位置。

所以扩展适合只读取公开成员、给调用点加可读性的操作；需要多态就回到成员函数与接口。扩展属性不能带初始化器，它没有存放状态的地方，每次访问都在执行 getter。

可空接收者扩展与集合扩展

接收者也可以声明为可空类型，这时 null 同样能调用它，函数体里 this 仍是可空值，必须自己处理。判空因此从每个调用点搬进一处定义。

nullOrBlank() 把空串、全空白和 null 三种“没有内容”归成一个结果，比在业务代码里写三遍 isNullOrBlank() 干净。它与 ?. 的分工是：x?.trim() 表达“没有就什么都不做”，x.orFallback("-") 表达“没有也是一种答案”，后者让链继续走得下去。

集合扩展要注意两件事：别重造标准库已有的 getOrNull、firstOrNull、filterNotNull，上面的 secondOrNull 只是命名示范，真要补的能力请用 OrNull、OrEmpty 后缀明示失败语义；接收者类型选最小够用的一档，只读元素写 Collection<T>，要按下标才写 List<T>。

作用域函数的选型

五个作用域函数的差别只有两点：接收者在块内是 this 还是 it，返回值是对象本身还是 lambda 的结果。按意图选即可。

我想做什么 用哪个
把可空值转换成一个结果 x?.let { }
配置刚创建的对象，仍要拿到它本身 apply
对已有对象做检查、打日志，不参与结果 also
连续使用一个非空对象的多个成员，只要结果 with(obj) { }
需要一段带返回值的语句块，没有接收者 run { }
条件不成立时把值变成 null takeIf / takeUnless

apply 与 also 返回接收者，适合放在链中间；let、run、with 返回 lambda 结果，适合收尾。with 的接收者是普通参数，user?.with { } 并不能判空，只是把可能为 null 的值传进函数，正确形式是 with(user ?: return) { }。

代价出在嵌套上：两层 let 就有两个 it 要读者重命名，return 从哪返回也需要判断；最直接的坑是最后一行决定整块类型，本该返回对象的链会因为最后一句是 println 而变成 Unit。约定是同一个表达式里作用域函数不超过一层，需要两层就说明该抽成一个有名字的函数。

库作者视角：扩展可见性与类型别名

public 扩展一旦发布就是隐式 API：import 了接收者类型就可能把它当方法用上，改名与删除都是破坏性变更。两个库给同一类型加了同名同签名的扩展时，显式 import 胜过通配 import，读者未必看得出名字来自哪里，所以扩展名要带足语义，trimToNull 好于 clean。internal 扩展只在本模块可见，编译产物却是可被反射与其他 JVM 语言看到的静态方法，别把可见性当安全边界；文件顶部的 @file:JvmName 只是给 Java 侧一个体面的门面类名。

typealias 的正当用途是让难读的签名自己说明意图，典型对象是函数类型（如 (Event) -> Unit）和嵌套泛型。局限在于它不创建新类型：别名与底层类型双向兼容，typealias UserId = String 配 typealias OrderId = String，传错时编译器一声不响，约束只存在于命名里，这就是障眼法。判断标准：改名只为读懂，用别名；要让错误传不进去，用只包一个字段的新类型。

反模式清单与实践对照

  • 满屏 !!：把编译期检查换成运行期赌博。回到边界收敛、局部快照或带契约的断言函数。
  • 扩展函数当工具类垃圾桶：零碎逻辑全挂在 String、Collection 上，得到一堆按声明类型分派、又无法覆盖与测试的多态幻想。
  • 可空类型一路透传：同一个 null 在十层调用里各判一次，说明第一层就没做决定。
  • 作用域函数嵌套：let 套 also 再套 run，看着像回调地狱，其实只缺几个命名函数。
  • 相信平台类型：给 Java 返回值写上非空类型就当安全。
  • 契约与实现不符：错误不再崩溃，而是静默传播。
  • 用 typealias 假装类型隔离：见上一节。

两个主题是同一条经验：语言工具给的是编译期的推力，不是保证。可空类型只在数据没离开类型系统时成立，扩展函数只在你想清楚它静态分派时才好用；把 null 的处理集中在边界、把分派期望放在成员上，写法就不会大错。

小结

把本篇收束成四条可执行的做法：可空性在入口判定、在内部保持非空；!! 只留给”这里为 null 就是程序 bug”的位置；平台类型进入 Kotlin 时立刻转成明确的可空类型；扩展函数只放薄逻辑，抽象能力交给接口或类层级。作用域函数按”这次调用返回什么”来选，而不是按哪个字母更短。守住这几条，空安全与扩展带来的收益才会大于它给读代码的人制造的疑问。
