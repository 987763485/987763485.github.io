Tauri 应用打包与更新

桌面应用的难点从来不在“跑起来”，而在“把跑起来的东西变成用户敢双击的那个文件”。本文聚焦 Tauri 1.x 这一条从源码到安装包、从安装包到下一次更新的完整链路：配置文件里哪些段管哪件事、三种平台各自的产物形态与凭证要求、更新为什么必须签名、签名之后的清单文件长什么样、以及发布之后如何停投与回滚。适合已经用 Tauri 起过项目、正准备第一次正式发版的开发者。写作当天 Tauri 2.0 仍处于 RC/预览阶段、尚未正式发布，因此全文以 1.x 的稳定行为为准，涉及 2.0 的部分只作迁移预告，不复述其配置字段。

打包链路全貌

理解 Tauri 的打包，最好的心智模型是把三个独立产物合成：前端构建产物、Rust 编译出的可执行文件、平台原生 bundle 工具生成的安装包外壳。前端部分由项目自己的构建工具负责，Vite 或 webpack 都可以，Tauri 只问它要一个静态目录；Rust 部分由 src-tauri 这个 crate 负责，它把窗口、命令、权限逻辑与嵌入资源编译成一个本地二进制；bundle 部分由 Tauri CLI 调用系统上已有的工具完成——Windows 上调用 WiX 与 NSIS，macOS 上用 create-dmg 之类的机制把 .app 目录包成 .dmg，Linux 上按目标分别产出 .deb、.rpm 与 .AppImage。

这张图里有三个容易被忽略的落点。其一，配置不只喂给打包器，它还参与 Rust 编译期的代码生成，图标、资源与窗口初始化都在编译时固化，改完必须重新编译才生效。其二，bundle 步骤完全依赖宿主机上已有的工具链，Linux 机器产不出可分发的 .app，这正是 CI 要用矩阵的原因。其三，签名发生在安装包生成之后，只增加文件而不改变包体，可一旦私钥或清单出错，前面所有构建都白做。

配置分层

Tauri 1.x 的应用配置集中在 src-tauri/tauri.conf.json 一个文件里，看起来很长，实际职责只有四层：包元信息、构建行为、窗口与安全、bundle 产物。把它们当成四个不同的抽屉来维护，排查问题会快很多。

包元信息层管“这个应用叫什么、第几版”。productName 会同时出现在安装目录、开始菜单项、.app 包名与卸载列表里，改名意味着用户看到两个不同应用；version 是更新机制唯一承认的比较依据，语义化版本号写错一位就会让灰度策略全盘失效。

构建层管“开发时从哪加载、发布时从哪加载”。devPath 可以是本地端口，也可以是一个已经部署好的地址，开发模式下窗口加载的是这个地址；distDir 则指向构建工具的输出目录，发布产物里的前端资源全部来自它。beforeBuildCommand 让 Tauri 在编译 Rust 之前替你跑一次前端构建，把这条命令接进 CI 时要注意它继承的是打包机的工作目录与 Node 环境。这一层最常见的事故是 distDir 指向了一个陈旧目录：前端改了但没重新构建，或构建输出被 .gitignore 之外的规则误删，Rust 侧编译照样成功，运行起来界面还是旧版。

窗口与安全层管运行时表现，包括初始尺寸、标题、能否缩放与内容安全策略。窗口与菜单、命令与权限这类运行时 API 不在本文展开，另有专文，本文只看它们对产物的影响：窗口配置在编译期固化，同一安装包在所有机器上初始行为一致；csp 一旦设置就写进产物并约束脚本与远端资源加载，配错表现为白屏而不是报错，排查时要优先怀疑它。

bundle 层管“产出什么、以什么身份产出”。active 决定是否执行打包，targets 决定产出哪些形态，identifier 决定应用身份，icon 列出参与打包的图标文件。此外还有资源文件、外部二进制与平台专属子段，它们共同决定了安装包的内容边界。需要注意 2.0 已处于 RC 阶段，其配置结构对这几层做了重排与拆分，但从 1.x 迁移时判断“这个字段属于哪一层”的思路不变，具体字段名以当期迁移文档为准。

前端产物如何进包

前端构建出来的静态目录要怎么进入安装包，Tauri 1.x 给了两条路：编译期内嵌，或者作为外部资源随包分发。默认且推荐的是前者。tauri::generate_context! 在编译时会把 distDir 指向的 HTML、JS、CSS 与其他静态文件写进可执行文件，运行时由内置的资源协议把它们喂给 WebView。用户在磁盘上看到的是一个单文件二进制，看不见里面的 index.html，也没法随手改。

内嵌的代价是耦合：前端资源属于 Rust 编译产物的一部分，只改一行样式也要重新执行完整构建。另一个代价来自体积，字体、图片与 sourcemap 这类大文件一旦误带进 distDir，就永久占据二进制体积；发版前检查构建输出目录，比事后压缩更有效。

外部目录方式是把前端资产作为随包资源发布，安装后放在应用目录里、运行时从磁盘读取。价值是灵活：同一份二进制可配不同前端包，皮肤化部署或灰度期只换前端而不动 Rust 逻辑都能做到。风险也很直白——磁盘上的文件归用户所有，校验与防篡改要自己设计，卸载时还得别误删用户数据。配置里声明随包资源的字段就是为此准备的，写法以当期文档为准。

bundle 目标逐个看

targets 决定要为哪些平台产出哪些形态。它可以写成一次性产出当前平台所有可行形态的聚合值，也可以显式列出目标名。CI 里强烈建议后者，因为聚合值在不同 runner 上产出的集合并不相同，会让“这次发版到底上传了哪几个文件”变成玄学。

Windows 上有 msi 与 nsis 两种。NSIS 产物是常见的 .exe 安装器，体积小、界面可定制，支持按当前用户安装而不需要管理员权限，静默安装与卸载参数清晰；升级时按同一产品标识原地覆盖，用户数据留在应用数据目录里不动，这是它作为个人分发主力的原因。MSI 由 WiX 工具链生成，价值在企业环境：组策略软件分发、设备管理推送、标准安装上下文，以及 IT 部门习惯的静默参数。代价是它对升级语义更严格，产品标识与升级码一旦写错，表现就是同一应用装出两份、旧版卸载不干净。另外 Windows 的 WebView 依赖运行时，配置里 webviewInstallMode 提供下载引导、内嵌引导、离线安装与静态依赖等几种模式，面向内网或离线机器分发时应选内嵌或离线，而不是让用户第一次启动时去联网下载。

macOS 的产物是 .app 目录与包裹它的 .dmg。.dmg 只是投递外壳，真正被安装的是拖进“应用程序”目录的那个 bundle，所以签名与公证都发生在 bundle 层面。架构是这一平台最容易翻车的地方：Apple Silicon 与 Intel 是两种机器码，只编 arm64 的包在老 Intel 机器上无法启动，只编 x86_64 的包靠转译能跑但性能与体积都吃亏。需要一份包通吃时，构建命令显式指定通用二进制目标，让产物同时包含两套架构的切片；对应地，验证也必须两种机器各跑一遍，只用一台 Apple Silicon 验证通用包等于没验证。

Linux 的三种形态服务三类用户。deb 服务 Debian 与 Ubuntu 系，rpm 服务 Fedora、RHEL 与 openSUSE 系，二者都能向系统包管理器声明依赖，把 webkit2gtk 与 GTK 相关库缺失变成安装期报错而不是运行期白屏，适合交给发行版惯例去管理升级。AppImage 是单文件免安装形态，加执行权限后双击即开，适合临时使用与容器环境；但它不声明依赖，缺库只能用户自己解决，且多数实现依赖 FUSE，在精简发行版或容器里还得补一个兼容库。三种产物同时提供是常见做法，代价是三条链路各验证一次。

标识符与单实例

identifier 是整个发版体系里最不该随手改的值。它是一个反向域名形式的应用身份，会被写进 macOS 应用 bundle 的标识、Windows 的安装与注册信息，以及应用数据目录的路径。系统判断“这是不是同一个应用”靠的就是它，而不是显示名或安装包文件名。一旦改动，操作系统会把它当成一个全新应用：桌面与启动项出现两个图标，用户数据目录重新生成一份空的，旧版本收不到新版本的更新，卸载时旧的那份还留在机器上。这类问题在测试阶段几乎不可见，只有拿同一台装过旧版的机器做升级验证才会暴露。

因此实践中要把它当成不可变主键来管理。展示名想改就改 productName，文案与品牌升级都不影响身份；反向域名建议用真实持有的域名倒写，全小写、只用点与字母数字，避免中文、空格与连字符带来的平台差异。若确实因品牌迁移必须换标识，不要指望升级链路自动完成，只能准备迁移方案：旧标识继续发布并在应用内提示，新标识首包内置从旧数据目录导入的逻辑，并行到覆盖率足够高再停掉旧的。

单实例行为不由打包配置决定，而由应用启动时在 Rust 侧注册的逻辑决定。1.x 通过官方提供的单实例插件，或自行实现的进程间通信来完成，互斥所依据的名字同样由应用身份派生。它的语义是“第二个实例启动时把已有窗口唤起并让自己退出”，配置得当还能把第二次的启动参数（比如被双击的文件路径）转交给第一个进程。这里有三条边界要清楚：单实例只在同一登录会话内有效，两个用户各自登录会各跑一份；调试构建与正式发布构建如果共用同一标识会互相抢占，表现为开发时窗口莫名跳到另一个进程；卸载残留或多形态混发会让“这台机器上到底装了几个”从一开始就说不清。

生成物要一并纳入版本管理，否则打包机在缺少图形工具的环境里会失败。两个常见坑：只换源图不重新生成，产物里还是旧图标；macOS 上换了图标却发现程序坞没变，那是系统缓存。

除图标外，每个平台还有一份“必须改对否则审核或权限异常”的清单。macOS 是 bundle 内的属性列表文件，里面除了标识、显示名与版本，还要为每一次敏感资源访问写清楚用途文案——缺失时系统的表现不是弹窗询问，而是直接拒绝甚至进程被终止；用途文案与签名时附带的权限声明不匹配，公证环节同样会打回。Windows 是嵌入可执行文件的应用清单，涉及显示缩放感知、是否需要提权运行、文件关联这类声明，写错表现为高分屏下界面发虚，或双击关联文件时行为异常。Linux 是桌面入口文件与图标安装路径，决定应用出现在哪个分类、能处理哪些 MIME 类型，配置缺失时应用能启动但系统层面认不出它。具体键名各平台文档写得很细，本文只强调一点：它们不是装饰，而是应用与操作系统之间的合同。

平台清单之外还有两类内容也要参与签名：随包资源与外部二进制。把一个用其他语言写的命令行工具带进安装包时，它是按目标架构三元组命名并作为可执行文件放进产物里的，macOS 上如果忘了把它一起签名，公证会失败而不是仅仅警告。同理，任何在构建后才塞进 bundle 的文件都会破坏签名完整性，所以“打完包再手工改个文件”这条路必须堵死。

代码签名与公证

签名解决的是两个问题：用户能否确认这个包出自你，以及操作系统是否愿意让它顺利跑起来。这两件事在 Windows 与 macOS 上的成本结构完全不同，必须分开规划。

Windows 侧需要一张代码签名证书，签名后安装器的“发布者”才会显示为经过验证的组织名而不是“未知”。现实约束有三条：证书按年购买且要通过组织验证；信誉需要积累，即使签了名，下载量很少的新文件仍可能触发 SmartScreen 蓝色拦截页，只有持续以同一证书发布才逐渐消失；签名必须带时间戳，否则证书过期后历史产物会被判为无效签名。企业环境还常见硬件密钥或云端签名服务，签名要在 CI 里受控完成，私钥不能落盘。

macOS 侧要一张 Developer ID 类型证书，流程比 Windows 多一步公证。先用系统的 codesign 对整个 bundle 签名并启用较严格的运行时保护，若应用需要越出默认能力还得同时提供权限声明文件；随后用 notarytool 提交公证，等扫描通过后用装订命令把票据写进文件，离线机器因此也能通过检查。签名与公证都作用在 .app 上，所以顺序必须是构建、签名、打成 .dmg、公证装订、上传，一步不能颠倒。

没有这些凭证时用户体验到什么，要提前想清楚。macOS 上未签名或未装订公证的应用会被 Gatekeeper 拦下，提示“无法打开，因为无法验证开发者”，甚至在某些来源上直接报“已损坏”，用户需要右键选择打开，或用命令清除下载时打上的隔离属性——这两条路都不可能指望普通用户走完。Windows 上未签名包会显示未知发布者并触发 SmartScreen 警告，企业设备管理策略可能直接禁止执行，浏览器也会把下载文件标记为高风险。所以“先出包再补证书”这种安排，实际上是把成本转嫁给了用户支持与口碑。

更新机制：密钥、清单与失败路径

自动更新是应用给自己开的后门，因此必须签名。客户端会去一个网络地址下载可执行内容并替换自身，如果这条链路不校验来源，任何能劫持响应的人都能在用户机器上以用户权限执行代码。1.x 的做法是用 ed25519 密钥对给每个安装包签一份分离签名，客户端内置公钥，只接受能被该公钥验证通过的更新包。

    C->>C: 用内置公钥校验签名
    C->>C: 校验通过后安装并重启

失败路径要逐条设计，因为自动更新的默认策略是“失败也要安静”。常见的有：端点超时或返回 404；CDN 把一个 JSON 请求变成拦截页导致解析失败；清单里的地址与签名不匹配，校验直接不过；下载中途磁盘不足或被安全软件掐断；Windows 安装器需要提权而静默失败；macOS 上应用仍在运行时替换 bundle，留下半新半旧的目录；Linux 下包管理器形态的产物不提权就无法自动完成。至少要保证三件事：更新失败不能破坏当前可用版本、错误要上报服务端而不是只写本地日志、确认对话框与重启策略要显式决定。

最后是灰度与强制更新。上游更新机制只负责“清单里有更高版本就提示安装”，不提供按比例放量，也不提供“低于某版本禁止使用”的强制语义，这两件事只能由服务端策略与自建校验完成。灰度靠端点按当前版本、渠道或用户标识决定返回什么清单，给小流量返回新版、其余返回旧版，随时可以收回。强制更新靠应用自身的版本检查：启动时判断当前版本是否仍在支持列表内，不在就阻断进入主界面并给出全量安装包链接——这条路必须留好离线兜底，否则断网用户会被自己的策略锁在门外。

更新流水线与回滚运维

发布应当是一条任何成员都能按下开关的流水线，而不是某个人电脑上的手工仪式。典型做法是在 CI 里按平台开矩阵：Windows runner 产 msi 与 NSIS 包，macOS runner 产两种架构与通用包并完成签名公证，Linux runner 产 deb、rpm 与 AppImage，各条 job 上传产物与 .sig，最后由汇总 job 组装清单并推送。

上游用于产出更新签名的开关名在不同版本上变动过，1.x 里它随更新器启用状态自动生成，是否显式开启请以当期文档为准，别把记忆里的字段名抄进新仓库。真正稳定的是三条纪律：私钥只存在于加密变量或临时文件、构建完立刻销毁；产物路径按版本号不可变，同一版本永不覆盖；清单里每个平台的地址都要能实际下载成功。

运维上最被低估的能力是“停投”。线上版本出问题时，要能在几分钟内让尚未升级的用户不再收到这条更新，做法是从清单里撤回该版本，或把端点指回旧版本；因此清单必须短缓存或可主动刷新——一个被 CDN 缓存两天的 latest 清单，会让停投指令迟到两天。至于已经升级的用户，回滚几乎不可能自动完成：更新器不提供退回旧版本的通道，旧版数据格式还可能已被新版改写。可行的补偿只有两种，发一个版本号更高的修复版，或者在应用内提供导出到旧格式的兜底路径。这也解释了版本号为什么只能单调递增，以及数据迁移为什么要写成向后兼容。

安装失败后的现场同样要处理。下载残留占用户磁盘，半完成的安装会留下无法启动的快捷方式，注册表与桌面入口里的残项让下一次安装行为异常。清理要么靠安装器覆盖式修复，要么给一份明确的手动重装说明，别让支持同学只能远程协助。

体积、产物形态与平台对照

与 Electron 的对照只谈定性结论：Tauri 安装包小，根本原因是不自带浏览器内核与 Node 运行时，渲染交给系统 WebView，二进制里主要是 Rust 编译出的应用逻辑。于是空壳应用的安装器通常落在个位数到二十几兆的量级，同类 Electron 应用则从几十兆起步（均为示意值，不构成实测依据）。内存差距同样来自少了一整套自带内核的进程树，但示意值不能替代实测。

代价是责任的转移，这点必须写清楚。系统 WebView 的版本不由你决定：Windows 上取决于运行时是否安装及其更新程度，macOS 取决于系统版本，Linux 取决于发行版打包的 webkit2gtk，同一份前端代码在三套内核上可能表现不同。字体渲染、CSS 特性支持、剪贴板与文件对话框行为都可能出差异，回归测试要覆盖最低支持版本而不是只测开发机。Linux 还额外依赖 GUI 系统库，容器里跑不起来通常是缺库而非应用有 bug。说白了，Tauri 用体积换来的责任是把内核兼容性揽到自己身上。

三个平台的准备事项可以收敛成一张表：

平台 需要提前准备的凭证或产物 最常踩的坑
Windows 代码签名证书与时间戳、更新私钥、WebView 运行时分发策略 首次发布仍被 SmartScreen 拦截；MSI 升级标识写错导致装成两份
macOS Developer ID 证书、权限声明文件、公证所需账号与专用口令、双架构或通用包 只验证了本机架构；随包外部二进制未一起签名导致公证失败
Linux 目标包格式清单、桌面入口与图标、依赖声明 缺 FUSE 或图形库导致打不开；未给执行权限被当成损坏文件

小结

打包与更新本质上是把“应用身份”与“发布责任”固定下来。身份由标识符、产品名、版本号与图标共同构成，一旦发布出去就不能再随意改动，尤其是标识符——改了就等于换了一个应用，旧用户既升不上来也卸不干净。责任则落在两份合同上：一份是跟操作系统的合同，包括各平台清单里那些权限与元信息字段、代码签名与公证；另一份是跟用户的合同，即更新链路能不能安全、可停、可解释地失败。密钥管理是这两份合同的交点，公钥进了客户端就再也换不了，所以私钥的保管与备份要当成基础设施来做。体积上的收益确实存在且可观，但它换来的是把内核兼容性的判断权交给系统，回归测试必须覆盖最低支持环境。按配置分层、产物目标、签名公证、清单发布与停投演练这个顺序走通一遍，第一次发版就不会手忙脚乱。需要说明的是，Tauri 2.0 在写作当天（2024-09-30）仍未正式发布，仍处于 RC 阶段，其配置字段与插件形态请以正式发布后的文档为准。
