跨语言序列化协议对比

本文要解决一个具体的决策问题：当 Java 服务、Go 网关、Kotlin 客户端、Flutter 页面和 C# 后台要在同一条链路上交换数据时，序列化方案怎么选、为什么这么选、选完要还哪些债。笔者不按特性清单罗列，而是先用“是否自描述”这一条轴把 JSON、MessagePack、Protobuf、Avro、Thrift、FlatBuffers 分开，再逐个讨论体积从哪来、schema 怎么演进、跨语言语义在哪崩、工具链要付多少。读完你应该能对某条具体链路给出可辩护的选择，而不是继续沿用“默认就 JSON 吧”。

序列化要回答的三个问题

选型混乱的根源，多半是团队把“用什么格式”当成纯技术问题，而它首先是组织问题。动手之前先回答三个问题。

第一，给谁读。同进程传对象不需要序列化协议，直接传引用即可，转成 JSON 再解析回来只是给自己制造一次拷贝。跨服务调用需要两端都能稳定生成访问代码的格式，因为类型对不上会变成每天几百万次的日志噪音。落盘归档（事件日志、数仓快照、合规备份）要的是“十年后还有一个陌生人能读出来”，这时自描述性与元数据可发现性压倒体积。三种角色诉求互相矛盾，用一个统一格式覆盖它们是全栈项目最常见的设计债来源。

第二，读多久，也就是版本共存期。同进程是 0；服务到服务只是发布窗口那几十分钟；对外 HTTP API 里，浏览器缓存的老页面和不会自动升级的移动 App 会让一个字段的存在性拖上好几个季度；数仓里的老分区文件可能比写它的服务活得更久。共存期越长，“新增字段能被老代码忽略、删除字段能被新代码容忍”这类演进规则越值钱，而这恰好是自描述格式与带编号格式分野的地方。

第三，谁演进。生产者和消费者同属一个团队时，IDL 变更和业务代码在同一个 PR 里，纪律靠 code review 就能维持。契约跨团队时（Java 后端定义、Flutter 前端消费），它必须独立于任何一方仓库存在，并有自动化检查拦住单方面破坏，否则每次联调都在赌对方看到了那行注释。

三个答案组合起来就能推出具体结论：内部高频链路可以给强 schema 的二进制；对外公开 API 通常停在 JSON 加一份机器可读的接口描述；事件流落盘必须把 schema 版本当一等公民。顺带划界：本文只比数据交换格式，不比语言本身，Java 与 Go、C 与 Go 的服务端性能与工程写法差异由同批对比类篇目负责。

两种世界：文本自描述与二进制带 schema

真正有解释力的分类轴不是“文本还是二进制”，而是“这串字节自己知道自己是什么类型吗”。

自描述一侧，JSON 把字段名和类型线索都放进载荷：引号是字符串，裸字面量是数字与 true、false、null，方括号是数组，花括号是对象；MessagePack 也是自描述的二进制，每个值前有一个类型字节说明它属于哪个 family（fixint、str、bin、array、map、ext）。好处是决定性的：读者只要有解析器，不需要外部信息就能恢复出一个通用对象，随手打印、随手改字段发回去。代价是每个值都要带上“我叫什么、我是什么类型”的税：字段名每条记录重复一次，数字用十进制文本往往比定宽二进制更占空间。

带 schema 一侧，Protobuf 的二进制流里只有字段编号和 wire type：它只说明这个字段是变长整数还是 length-delimited 块，不说明它是 int32、枚举还是嵌套 message，字段名完全不在流里。Avro 更极端，连字段编号都不写，只按 schema 中字段顺序依次写值，脱离 schema 就是一串无法归因的字节。FlatBuffers 需要 schema 才能生成访问器；Thrift 的二进制协议写字段 ID 与类型，但不写字段名，且它的服务调用帧本身就是 IDL 的一部分。这里只做结论级引用：varint 每字节携带 7 位有效位、zigzag 如何折负数、tag 如何由编号与 wire type 拼成，位级推导已有专文讲透，本文只用它的结论——小整数便宜、字段名零成本、类型信息全靠外部约定。

这张图的重点不在格式列表，而在三条债务出口：走自描述，欠的是契约漂移，文档与线上字节的真实形状迟早不一致，直到某次前端把可选字段当必填读；走强类型生成，欠的是构建链，IDL、运行时、生成器三者版本要一起对齐，Flutter 侧还多一层产物提交纪律；走动态读取，欠的是 schema 存储，谁能找到某批历史文件对应的 schema，谁才读得懂它。自描述也不等于跨语言一致：JSON 在各语言里先落到通用类型（Java 的 Map、Dart 的 Map<String, dynamic>、C# 的 JsonElement），类型信息在这一刻就丢了；带 schema 生成静态类型看似解决了问题，但空值三态、整数位宽、时间语义在各生成器里的映射不同，反而制造另一种不一致。

JSON：成为默认的理由与代价

JSON 的默认地位不是靠性能挣来的，而是靠三件事：浏览器原生有解析器、几乎所有语言都有事实标准库、任何人在终端里肉眼就能读——对外 API、Webhook、第三方接入这三类链路里，它们几乎总是压倒其他考虑。成本结构也符合直觉：逐字符扫描，数字要从小数文本转成浮点，字段名要参与哈希与比较，CPU 主要花在词法扫描与字符串处理上；体积上是字段名重复与十进制文本两座山。量级只能给口径明确的示意观察：本地构造的 10 万条含 4 个短字段（id、名称、金额、时间戳）的简单对象里，同一条记录的 JSON 文本长度约为 Protobuf 编码后的两到三倍——这是示意值（本地构造的 10 万条简单对象的观察口径，非权威 benchmark），字段越少、名字越长比例越难看，任何场景都不应拿它当决策依据。

真正的坑在类型语义上，一共四个。

第一个坑是数字精度。JSON 的 number 在规范层面就允许实现丢失范围和精度，主流解析器按 IEEE-754 double 读，超过 2 的 53 次方减 1 后整数开始悄悄失真。JavaScript 的安全整数上限正是这个数，所以“64 位 id 一律用字符串传”不是风格偏好而是兼容性要求，Protobuf 到 JSON 的官方映射把 int64 与 uint64 编码成字符串同理。Java 与 Kotlin 侧要保精度得显式指定用 BigDecimal 读，默认行为不保护你。

第二个坑是日期时间。JSON 没有日期类型，只有字符串，于是“2024-09-11T11:53:40”究竟是本地时间、UTC 还是带偏移的时刻，取决于发送方用了哪门语言的哪个类库：Java 的 Instant、OffsetDateTime、LocalDateTime 映射出三种形状，C# 的 DateTime 与 DateTimeOffset 处理偏移的方式不同，Dart 的 DateTime.parse 把不带偏移的字符串按本地时区解释。契约上要么写死 RFC 3339 带偏移，要么传 epoch 秒并明确单位。

第三个坑是 null 与字段缺省。“字段不存在”和“字段值为 null”是两个不同的事实，而模型类常把它们折叠成同一个 null，于是“用户没填地址”和“用户清空了地址”再也分不开。要么在契约里规定不许写 null 只许删字段，要么显式加一个标记字段，别指望解析器默认行为替你保持一致。

第四个坑是松散契约。JSON 的接口文档本身就是它的 schema，而文档不是可执行约束：字段有没有、类型对不对、枚举新增了什么，消费者代码里那个非空断言都不会报错，事故通常以“某字段某天突然变成字符串形式的数字”的面目出现（反序列化打爆内存这类排查路径另有专文讲线上问题定位）。用 JSON 做跨团队长期契约时必须补一层机器可读的 schema（JSON Schema 或 OpenAPI 文档）并在 CI 里检查契约变更，否则它就是一份不断漂移的口头约定。

MessagePack：没有 schema 的二进制

MessagePack 的定位一句话说清：把 JSON 的形状换成二进制编码，语义保持不变。它仍然自描述，仍然不需要外部 schema，解析结果仍然是通用对象；但它省掉了字段名的引号、冒号、逗号，短整数用一个字节表示，字符串长度前置。它解决的正是“我想要 JSON 的灵活性，但不想要 JSON 的体积和解析开销”这类问题。

典型适用面有三个。缓存值最常见：往 Redis 写一个会话对象或一段计算结果，读写双方是自己人，没有跨团队契约压力，格式纯属内部实现细节，换成 MessagePack 往往只是一层编解码封装的改动量。消息总线载荷是第二个：事件 payload 用 MessagePack，broker 不需要理解内容，消费者按自己的模型取字段。第三个是资源受限的客户端把结构化日志批量压缩上行。

它的表达力边界来自同一套设计。类型映射是一张固定表：字符串和二进制分属 str 与 bin 两个 family，数组对应 list、对象对应 map，扩展类型 ext 留给自定义语义（规范把时间戳定义为扩展类型，用一个负编号的 type id 标识，各家库支持程度参差不齐）。字段名仍是每条记录里重复的字符串，所以体积优势在“结构少、值小、重复度高”的场景里明显，在字段名很长、每条记录字段很多的场景里不如带编号方案。它没有字段编号这个概念，因此也没有“删除字段后老编号不许复用”这类演进规则可言。

为什么它不适合当跨团队长期契约，理由有三层。第一，没有 IDL，就没有可评审的契约文件，前后端各自维护一份手写模型，谁也不能证明两份模型描述的是同一个东西。第二，没有 schema 注册表或生成器，就没有“不兼容变更被机器拦下”的机会，字段改名只能靠全局搜索加运气。第三，跨语言的类型映射细节多且不一致：无符号整数在只有 64 位有符号整型的语言里怎么还原、ext 类型是否被某个库识别、二进制在 Java 侧还原成字节数组还是字符串，实现差异真实存在，一旦放进跨团队契约，这些差异就会变成排期。结论是把它定位成内部实现细节：缓存、日志、进程内队列、同团队服务之间的临时载荷都能用；一旦这条链路要写进对外文档、要留给别的团队或下个季度才上线的客户端读，就应当升到 Protobuf 或 Avro，或者老老实实用加 schema 校验的 JSON。

Protobuf：字段编号就是契约

Protobuf 的 IDL 里最关键的符号不是类型名，而是等号后面那个数字。它一旦被写进代码并发了出去，就是这条链路上不可回收的资产。

演进规则由编号推导出来，三条最要紧。第一，编号不可复用：灰度期间老客户端还会发出带旧语义的字节流，如果新字段抢用了同一个编号，新代码会把它当新字段解析，数据在静默中错位，没有任何错误抛出——这是这类契约里唯一一类“错了也不报”的事故，所以删除字段必须同时写 reserved。第二，改名通常安全、改编号和改类型不是：名字不在二进制流里，只影响 JSON 映射和生成代码的 API。第三，wire type 兼容才算真兼容，int32、int64、uint32、uint64、sint32、sint64、bool、enum 之间在二进制层可互换（除值域与符号截断风险），改到 string 或 bytes 就直接断裂。

proto3 的存在性语义要单独说清：标量字段默认没有 presence，未设置时不写进流、读出来是该类型的零值，于是 0、false、空串和“没填”在编码层完全同一个样子。要区分就得三选一：用 optional 关键字（生成代码里给出显式的有没有设置过的判断能力）、用 message 包装标量（如 Int32Value，代价是多一层嵌套）、或者把它塞进 oneof（副作用是设置任一分支都会清空其他分支，且字段不能再加 repeated）。字段本身是 message 类型时天然有 presence，这也是“把可选标量包一层消息”这个老技巧的来源。

oneof、Any 与 Well-Known Types 是三件最常踩到的工具。oneof 表达同一时刻只有一个分支有值，它是互斥约束不是可选集合，该用来表达业务上真正的多选一（支付方式、地址类型），而不是给字段随手分组。Any 把一个消息连同类型 URL 一起塞进 value 字段，适合插件式配置和多态载荷，但它把契约从编译期推到运行期：解包要求对应消息类型已被链接进当前程序，Go 侧要靠类型注册、Java 侧要求类可见、Dart 侧往往要手工提供解包代码，“线上解不出来”多数是这个原因而不是数据坏了。Well-Known Types 里 Timestamp 用 int64 秒加 int32 纳秒表示绝对时刻、其 JSON 映射是 RFC 3339 字符串，Duration 同理表示时长，NullValue 是给“必须能表达 JSON 的 null”这类场景准备的枚举值，Struct 与 Value 承载半结构化对象。要跨语言传时间与空值三态就用这几个，别自己发明一套 long 加单位约定，收益是各家生成器的映射规则一致。

生成代码的一致性不是自动的：protoc 版本、各语言运行时版本、插件版本三者要一起管，产物要么提交进版本库、要么在 CI 里每次生成并缓存，Flutter 侧还要把 build_runner 的时机和输出目录固定。本文只讲载荷格式，gRPC 的服务定义、拦截器与流式调用不在这里展开，那部分另有专文；需要留意的是同一个 proto 文件既当 RPC 契约又当消息契约时演进压力会叠加，服务方法签名的变更半径远大于消息字段的新增。

Avro 与 Thrift：schema 存储与 IDL 生成的两条老路

Avro 的特别之处是它的 schema 就是 JSON，而数据是二进制——这种组合让它天然适合 schema 与数据分离存放的架构。

Avro 二进制里既不写字段名也不写字段编号，只按 schema 中字段的声明顺序依次写值，所以一条记录脱离 schema 完全不可读，而这正是它的优势：不必为每条记录重复付字段名的税，同一批数据共享一份 schema。Object Container File 把 schema 写在文件头一次，一个几 GB 的文件只有一份 schema 开销；事件流里常见做法是消息前只放一个 schema id，真正的 schema 存在 Confluent Schema Registry 这样的注册表里，读者按 id 取回再解析。两种形态都指向同一个结论：Avro 是为写一次、读很多次、批次跨越多个版本设计的，这恰好是离线数仓和事件日志的形状。

它的解析机制是读者用写者的 schema 做解析：解析器拿到写者 schema，按名字把字段对应到读者 schema 上，写者有而读者没有的字段被丢弃，读者有而写者没有的字段取默认值。所以每个字段都应当带默认值——这在别的格式里是风格，在 Avro 里是演进能力的前提。代价是它没有字段编号，标识字段的是名字，于是重命名默认就是破坏性变更（规范提供的 aliases 机制能在读者侧补一条映射，但这要求所有读者都升级，起不到灰度作用）；字段顺序的调整在按名解析下能被容忍，但依赖位置把记录映射到列存或 CSV 的那类转换器会悄悄错位，这是真实事故源。可空性用 union 表达，形如 null 与某类型的二元 union，读侧必须先判分支再取值，忘记判分支就在运行时抛异常，在 Java 生成代码里表现为拿到 Object 而不是具体类型。

Thrift 走的是另一条路：它的 IDL 不只描述类型，还描述服务和异常，编译器一次性生成各语言的数据结构与调用桩，这在多语言服务化早期是很强的卖点。

Thrift 和 Protobuf 一样给字段编号，因此同样有“删除字段要留位”的纪律，未识别字段会被跳过；它的类型系统里 i64 是主整数类型，这给 JavaScript 一类语言留下精度陷阱。协议层要区分清楚：TBinaryProtocol 结构直白、每个字段带类型和 ID，compact 协议用变长整数和字段 ID 增量编码把体积压下来，两者互不兼容，跨语言联调时先确认协议一致再谈其他。历史上 Thrift 流行是因为它比 Protobuf 早、语言覆盖极广、且服务桩生成能省掉一层手写 HTTP 接口；今天的现实是它的社区活跃度与新特性推进明显不如 Protobuf 与 Avro 生态，生成代码风格偏旧，required 修饰符被普遍视为设计失误（新代码只该用 optional）。新项目选 Thrift，理由通常是存量 IDL 资产或某个冷门语言的生成器只有它有，而不是它更先进。

FlatBuffers：把解析从读路径上挪走

FlatBuffers 的 schema 文件在形态上接近 Protobuf：字段有编号、支持新增与默认值、按号兼容。真正的差别在物理布局——它写出的缓冲区里，嵌套表用偏移量互相指向，每张表前面有一张 vtable 描述各字段的位置与存在性，于是读取端拿到缓冲区后不需要解析出中间对象，生成的访问器直接沿偏移取标量。Protobuf 的 parseFrom 会把整条消息变成语言层的对象图，这部分开销在 FlatBuffers 里被省掉了，换来的是构造端的不友好：创建顺序必须自底向上（先建字符串和 vector，再建引用它们的表）、要显式开始与结束对象，API 比直觉绕得多。

还有一个安全前提不能省略：它的读取建立在信任缓冲区结构的基础上，来自不可信来源的数据必须先走一遍校验函数，否则损坏或恶意的偏移会让访问器越界。这一层校验本身有成本，而且不是所有语言的运行时都提供同样强度的实现，选型时要确认。

为什么游戏、嵌入式和低延迟链路愿意接受更复杂的构建流程：这些场景读路径极热、数据量大而生命周期短，读到即用、不建中间对象能直接省掉一次分配与遍历，地图瓦片、行情快照、渲染资源包、移动端离线数据都在这类形状里。它与 Protobuf 的取舍可以这样记：Protobuf 把复杂度放在“编码简单、读取要解析”，FlatBuffers 把复杂度放在“编码要小心、读取零解析”；如果读写两侧都是热路径，或者还需要第三方工具能读写你的文件，Protobuf 的生态优势通常压过零拷贝的收益。

跨语言一致性：五个反复出事的类型

前面讲的都是格式内部，真正吃掉排期的是同一份契约在 Java、Go、Kotlin、Dart、C# 里映射成不同的东西。

整数范围。Java 至今没有原生无符号整型，Java 8 只提供把 int、long 当无符号处理的方法，类型本身仍是有符号，于是 Protobuf 的 uint64 落到 Java 只能塞进 long 并自行处理回绕，最大值附近的表现取决于运行时是截断多余位还是直接丢弃。JavaScript 与 Dart 的 Number 是双精度浮点，安全整数上限是 2 的 53 次方减 1，超过就丢精度，要保完整 64 位得改用 BigInt 或字符串。Go 的 uint64 与线上语义对得上。结论是：契约里所有用作标识符的 64 位整数，要么统一写成字符串，要么在 IDL 里用有符号类型并禁止负值。

时间与时区。绝对时刻用 Timestamp 或 RFC 3339 带偏移的字符串，单位（秒、毫秒、微秒）必须写进契约；“门店营业时间”“生日”这类没有时刻含义的值是本地日期语义，不该被硬塞成 UTC 时间戳，那正是所有时区同一天生日变成不同日期的原因。Kotlin 的 Instant、Java 的 OffsetDateTime 与 LocalDateTime、C# 的 DateTime 与 DateTimeOffset 之间，任何一个默认行为都能把偏移吃掉。

空值三态。“字段不存在”“显式为 null”“值等于零”是三个事实，只有少数格式能同时表达。Protobuf 要靠 optional、包装类型或 oneof；Avro 用含 null 的 union；Dart 的空安全让缺席必须显式声明；C# 在 .NET 8 上开了可空引用类型注解也仍只是编译期提示；Go 没有可选值概念，值类型的零无法表达缺席，只能上指针或专门的包装结构——“没填”被读成“0”多半出在这里（Go 的 encoding/json 那套 tag 的用法细节已有专文，这里只借它的结论）。

二进制字段。bytes 在 Protobuf 的 JSON 映射里是 base64 字符串，MessagePack 把 str 与 bin 分成两个 family，Java 侧还原成字节数组、Dart 侧是 Uint8List、C# 侧是 byte 数组且需要显式转 base64。图片缩略图、加密摘要、压缩块这类字段一旦进了 JSON 链路，最容易出的事故是某一层多做了一次字符编码。

枚举与未知值。生产者加一个枚举值是新增行为，消费者怎么处理它是另一个问题。Protobuf 的做法宽容：未识别字段在 3.x 的 proto3 运行时里被保留，重新序列化能带回，未知枚举数值也保留原始整数（Java 侧枚举 getter 给 UNRECOGNIZED，但取编号的方法仍返回原值）。JSON 的字符串枚举默认严格，新值直接让解析或校验失败；Thrift 把枚举当 i32，数字比较层面宽容但语义上更容易漏判。结论只有一条：枚举在任何跨语言契约里都是开放集合，消费端必须写默认分支，发布顺序是先让所有消费者上线容忍逻辑，再让生产者发新值。

演进的工程化：发布顺序、版本矩阵与调试成本

有了 schema 不等于有演进能力，让链路真正稳定的是三件工程实践。

第一是发布顺序。加字段看似安全，仍然有顺序：先让所有读者容忍缺失与新增，再让生产者开始写，观察满一个共存期之后才在业务逻辑里依赖它。删字段是反向的两步：先让生产者停写、保留字段声明，等共存期里再没有老生产者，才从 IDL 移除并写 reserved。生产者与消费者的版本矩阵要提前画出来：仍在灰度中的几种生产者版本，乘以线上共存期内的几种消费者版本，每个格子要么被双读覆盖、要么被明确判为不可能出现——多数事故来自“这个格子不会有流量”这类没被验证过的假设。灰度期最常见的落地形式是双写加转换层。

sequenceDiagram
    participant P as 生产者
    participant R as 老消费者
    participant N as 新消费者
    P->>R: 同时写 old_field 与 new_field
    P->>N: 同一份载荷, new_field 生效
    N-->>N: 双读比对, 记录不一致计数
    R->>R: 全量升级到读 new_field
    P->>P: 共存期结束, 停写 old_field
    P->>P: IDL 移除 old_field 并 reserved 编号

双写的转换层必须有截止时间，否则会永久留下来变成一层看不见的契约。第二是注册表与 CI。Confluent Schema Registry 这类组件把 schema 版本化，并在注册时按兼容模式（向后、向前、完全，以及各自的传递性变体）拒绝不兼容的新 schema，Avro 与 Protobuf 都能接；但它管不到没有 schema 的链路，也拦不住“编号没变而语义变了”这类变更，后者只能靠 IDL 的评审人机制、契约测试和 buf 这类工具在 CI 里比对 proto 目录的破坏性变更来兜。

第三是调试与可观测。Protobuf 流用 hexdump 只能看到编号和长度，应急手段是 protoc 那个不依赖 schema 的解码方式，它能把字节流还原成“编号到值”的树，够用来判断字段是否错位；需要精确解读时再拿 .proto 文件做文本格式转换。Avro 的容器文件有配套命令行工具能转成 JSON，MessagePack 各家库都有 dump 能力。工程上稳的做法是在系统边界留一层转换：内部走二进制，出口日志与排查接口转成 JSON 或文本格式并按采样落盘，避免日志里塞满 base64。指标上要把解析失败和业务校验失败分开计数，两类混在一起时，灰度期的 schema 不兼容看起来就像下游业务异常。

代码生成接入构建链的成本要提前预算：protoc 与各语言运行时的版本要锁，插件版本要锁，生成产物要么提交进版本库要么在 CI 每次重建并缓存，IDL 要独立成仓并打版本标签供多仓引用。语言覆盖度也在这一步决定：Protobuf 与 Avro 的主流语言支持成熟，Dart 与 C# 要挑生成器，Kotlin 侧要区分 kotlinx.serialization 自带的 Protobuf 支持与 protoc 生成的 Java 代码这两条路线，冷门语言先看生成器质量再定协议——协议选了、语言侧只能手写结构体，是最糟糕的组合。

场景选型

下表是笔者会用的默认答案，每一行的代价都是要真实承担的债。

场景 推荐方案 理由 要还的债
内部高频 RPC Protobuf（proto3） 载荷紧凑，强类型生成，不兼容变更可被机器检查 protoc 与运行时版本要一起管，调试要靠工具
对外公开 API JSON 加机器可读接口描述 浏览器与第三方接入零门槛，排障直观 数字精度、时间格式、空值语义要在文档里钉死
事件流与数仓落盘 Avro 加 schema 注册表 schema 与数据分离，读者按名解析跨版本批次 字段重命名即破坏性变更，schema 要有 owner
缓存值 MessagePack 无 IDL、改动小，与 JSON 心智模型一致 不能当跨团队契约，类型映射细节随库而异
移动端与弱网 Protobuf，读路径极热时 FlatBuffers 体积与解析开销直接映射成流量与耗电 客户端版本共存期长，演进纪律必须严格遵守
前端与浏览器 JSON；确需二进制时用 Protobuf 的 JS 运行时 原生解析器免费，64 位整数需按字符串处理 契约漂移快，要靠契约测试守住接口描述

小结

跨语言序列化的选择顺序应该是：先用“给谁读、读多久、谁演进”确定需不需要显式 schema，再在自描述与带 schema 两支里按体积、演进规则、语言覆盖度和调试成本挑一个，最后把选它要还的债写进排期。JSON 的价值是零门槛，风险是契约只活在文档里；MessagePack 是同心智模型的二进制替身，适合当内部实现细节而不是长期契约；Protobuf 用字段编号换来紧凑与可机器检查的演进，代价是构建链和 presence 语义；Avro 让 schema 与数据分离，是落盘与事件流的答案，代价是名字即标识符带来的重命名困境；Thrift 的多语言服务桩仍有存量价值，但新项目要评估社区活跃度；FlatBuffers 用更绕的写路径换零解析，只在读路径极热时才划算。最难的部分从来不是格式本身，而是同一份契约在五种语言里的类型映射：64 位整数、时间与时区、空值三态、二进制字段和开放枚举。把这五件事在 IDL 或接口文档里逐个写死，比多比较一种格式更能减少事故。
