Vite 构建工具原理与插件开发

浏览器早就具备模块加载能力，工程代码却不可能原样跑起来：TypeScript、JSX、单文件组件、裸模块标识都要一层处理。本文要回答的问题是，Vite 把打包从开发循环里拿走之后，编译、缓存、热更新是怎么组织的，以及使用者如何写出真正能用的插件。适合已经在用 Vite、但没读过插件钩子的前端工程师，读完应能说清开发服务与生产构建的分工，并独立写一个带虚拟模块的插件。

开发环境为什么不需要先打包

传统构建工具的开发循环是先打包、再看效果：从入口递归解析模块图，把上千个文件合并成几个 bundle 写入磁盘，再启动监听，文件一变就重算受影响的部分重新打包。代价有两处：冷启动要付全量初始化的账，项目越大越明显；改一小段代码时，编译范围仍由依赖图决定，而不是由你编辑了哪个文件决定。

Vite 把打包从开发循环里去掉。浏览器本身就是模块加载器：能解析 import 语句、按 URL 拉取模块、对同一 URL 去重并缓存执行结果。既然工程代码最终要变成浏览器能懂的东西，就不如让浏览器决定需要哪些模块，服务端只在被请求时编译那一个。启动成本于是从与项目规模相关，变成只与首屏请求到的模块数相关。

过程是这样的：请求根路径时 dev server 读取 index.html，保留模块脚本标签并补上客户端入口；浏览器接着请求 /src/main.ts，服务端读文件、用 esbuild 剥掉类型与 JSX、补一段导入分析，返回 JS 与 source map；返回值里的相对导入又被解析成新请求，如此递归。模块图不在磁盘上的 bundle 里，它在浏览器已加载的模块集合中，服务端只维护一份对应的反向依赖记录。

这个模式换来秒级启动，也带来两类新问题。一是请求数量：中型应用首屏可能请求数百个模块，本地回环上单次往返虽小，串起来仍可感。二是 URL 到磁盘路径的映射：裸标识符浏览器无法解析，根之外的文件不能用相对路径访问，依赖里大量 CommonJS 包更没有模块语义。前者靠 URL 约定解决，根外文件走 /@fs/，需要额外处理的裸模块走 /@id/；后者只能靠预构建，第三节展开。被改过的模块会在 URL 上追加时间戳，预构建产物带内容哈希，用来绕开浏览器与磁盘缓存。

dev server 的三层职责

Vite 的开发服务器不是一台静态文件服务器，它是三层结构叠出来的。

中间件层

最外层是一条 connect 风格的请求处理链，configureServer 能直接拿到它。顺序大致是内部中间件（/@fs/、/@id/、HMR 的 WebSocket 升级）、插件注册的中间件、模块转换中间件、单页应用回退。插逻辑要先懂顺序：钩子里调用 server.middlewares.use() 注册的处理器排在内部中间件之后，要在 Vite 之前把请求拦下，就得从钩子返回一个函数，让它在内部中间件装配完之后执行。这一层还负责 server.proxy（把接口请求转给后端，绕开跨域）、server.host（默认只监听本机）与 server.fs.allow（声明根外哪些文件可访问）。

转换管线

中间件把 URL 解析成模块标识之后，就进入与生产构建共用的那条插件管线：别名匹配、解析、加载、转换链、导入分析。TypeScript 与 JSX 的剥离由 esbuild 负责，它只按单文件工作、不做跨文件类型检查，跨文件的枚举内联与纯类型导入要按 isolatedModules 的约束来写。Vue 单文件组件、Sass、CSS Modules 由各自的插件补在这条链上。esbuild 与 SWC 自身的原理见《esbuild 与 SWC 编译加速》，本文只讲它们在 Vite 里的位置。

源码映射

管线里每一个 transform 都可以返回代码与映射对象，Vite 会把链路上的映射串起来随响应给浏览器，这就是断点能打在源文件的行上而不是编译产物上的原因。写插件时改了代码结构却忘记返回映射，报错行号会漂到转换后的位置，这是最常见的失分项。

依赖预构建为什么必须存在

node_modules 里的包是按需安装的，浏览器却把它们当作一堆无法解析的裸标识符，而其中一个包可能有几百个小文件。Vite 在开发启动阶段用 esbuild 把要用的依赖单独编译一次，产物落在 node_modules/.vite/deps 下，源码里的 react 从此指向一个产物的 URL。这一步存在的理由有三个，缺一不可。

第一是模块语义。CommonJS 与 UMD 包没有静态的导出声明，浏览器无法从中挑出具名导出，esbuild 在预构建时插入 interop 层，把 require 与 exports 翻译成 ESM 导出，并保证默认导出的取值时机正确。跳过它的代价是运行期抛错，而不是构建期报错。

第二是请求数量。一个像 lodash 这样的包由上千个小文件组成，逐个请求会把首屏变成串行往返的灾难，预构建把整个包合成一个文件，一次拿完。

第三是缓存与稳定性。预构建结果以锁文件哈希与相关配置为键，依赖没变时重启直接复用磁盘产物。它也保证同一个依赖在整张模块图里只有一个 URL：React 这类自带模块级状态的包被解析成两份时，Hook 会报无效调用，而起因看上去与依赖无关。

预构建只是开发阶段的机制，生产构建的 CommonJS 互操作交给 Rollup 生态的插件。扫描器如何决定要预构建哪些包、optimizeDeps 的配置项与缓存失效链路，另见《Vite 预构建与依赖扫描机制》，本文只在原理层停这一次。

HMR 的链路与失效传播

热更新不是把新代码塞进运行中的页面这么简单，它是一次带依赖图的定向传播：起点是文件系统事件，终点要么某个模块被替换，要么整页重载。

flowchart TD
  A[文件变更触发监听] --> B[服务端查模块图]
  B --> C[算出受影响模块集合]
  C --> D[WebSocket 推送 update 消息]
  D --> E[客户端拿到新模块地址]
  E --> F{被改模块自身接受更新}
  F -->|是| G[执行 dispose 清理旧副作用]
  G --> H[导入新模块并替换导出]
  F -->|否| I[沿反向依赖向上冒泡]
  I --> J{入口之前有人接受}
  J -->|是| H
  J -->|否| K[推送 full-reload 整页刷新]
  H --> L[重新执行依赖它的父模块]

服务端算传播范围：它维护模块间的反向依赖，变更命中哪个模块、被谁导入、再往上有谁接受，都由这张图推出最小集合。客户端是注入到 HTML 的 @vite/client，与 dev server 保持一条 WebSocket 连接（默认端口 5173），收到的消息有类型区分：update 带变更模块的路径与时间戳，full-reload 表示放弃热更新。

接受更新的入口是 import.meta.hot，它只在开发环境存在，构建时相关分支会被整体去掉。

accept 的三种形态覆盖自接受、指定依赖接受与回调接受；dispose 在旧模块被替换前卸载定时器、事件监听这类副作用；prune 在模块不再被引用时兜底。更常见的写法是把接受做成条件式：能就地处理的自己接住，处理不了就调用 import.meta.hot.invalidate()，把变更交给父级判断。传播链上没人接受时，更新一路冒泡到入口退化成整页刷新；改到预构建命中的依赖、需要重新打包时同样如此。

框架插件各补了一段。Vue 的插件把单文件组件的模板、脚本、样式切成带查询参数的子模块，切分粒度决定热更新粒度：改样式只替换样式标签，改模板则重新生成渲染函数并替换运行时 HMR 记录里的定义，组件实例与响应式状态不变；它还实现 handleHotUpdate，把不该进传播集合的文件剔除。React 的插件为 JSX 文件注入 Fast Refresh 的包装代码与前置脚本，把组件注册进刷新表，变更时按导出组件的签名比对决定重新执行还是保住 state，比对失败就退回整页刷新。差别不在实现水平，而在组件模型：Vue 的组件定义可以被安全替换，React 要靠约定留住 Hook 状态。

生产构建为什么交给 Rollup

esbuild 的单文件转换在开发里占尽便宜，打包要的却是另一套能力：跨模块的 tree-shaking 需要静态分析导出的使用关系，代码分割要把共享模块切成公共 chunk，产物还要兼顾命名、副作用标记与成熟的插件生态。Rollup 在这三点上更稳，Vite 5 的事实是开发用 esbuild 做预构建与转换、生产用 Rollup 打包，两者各在其位。webpack 的插件模型本文不重复，只对照一句：loader 按文件类型串行转换，plugin 订阅整个编译生命周期，与 Vite 以模块为单位的钩子不是一回事。

base 决定注入到 HTML 的资源前缀，也决定 import.meta.env.BASE_URL，子路径部署忘记改它是白屏的第一原因。构建产物没有 HMR 这条退路，vite preview 只是把 dist 起成静态服务。

插件开发从一个虚拟模块开始

Vite 插件是一个带 name 的对象，钩子签名沿用 Rollup，再叠上 enforce、apply 这些自有字段。虚拟模块最能体现这套模型：磁盘上没有这个文件，却要在客户端 import 到一份运行期才知道的内容。约定是用一个带前缀的裸标识符作为请求名，resolveId 把它解析成以 \0 开头的 id，load 只为这个 id 返回源码。

使用它只需要一句 import { version } from 'virtual:app-config'。\0 是 Rollup 侧的约定，表示这个 id 不存在于文件系统，能阻止其他插件或打包器再对它做一次路径解析；到了浏览器侧它被换成带 /@id/ 前缀的请求。前缀只是命名纪律，要避开真实包名，并给 TypeScript 补一句模块声明，否则 import 会报类型错误。

钩子时序、enforce 与 apply

一次模块请求的顺序是 alias、resolveId、load、transform 链：transform 收到解析后的绝对路径与上一个插件的输出，返回值串成流水线，排在后面的必须兼容前面的产物。enforce: 'pre' 排在 Vite 核心插件之前，'post' 排在构建相关插件之后，不写就落在中间；要在 esbuild 剥类型之前处理源码，只能是 'pre'。apply 限定生效范围，'build' 表示只在打包时参与，适合生成清单、注入埋点这类不该出现在 dev 的活儿。配置类钩子更早：config 在合并阶段改配置，configResolved 拿到只读的最终配置，buildStart 在构建开始时收集信息。

环境变量、模式与四个坑

.env 家族按固定顺序加载，后面的覆盖前面的：.env、.env.local、.env.[mode]、.env.[mode].local，带 .local 的默认不入库。开发时 mode 是 development，打包是 production；--mode staging 换掉的是加载哪个文件与 import.meta.env.MODE 的值，DEV 与 PROD 跟着命令走。只有 VITE_ 开头的变量注入客户端，其余留在 Node 侧，配置里要读它们就用 loadEnv。这条规则的实用含义是密钥绝不放进 VITE_ 变量，它会原样出现在产物里。

坑有四类。resolve.alias 只改写匹配到的说明符，不动相对路径，别名指向的目录里再用相对导入，同一文件可能被解析成两个 URL，模块级状态各自一份。依赖没进预构建时浏览器拿到的是 CommonJS，报错在运行期且信息模糊，补进 optimizeDeps.include 是标准解法。动态 import() 的说明符必须是字面量或由 import.meta.glob 在构建期展开，否则无法确定要保留哪些文件，产物会缺模块。define 是纯文本替换，值要自己 JSON.stringify；它与 import.meta.env 的区别是前者能出现在任何代码里、构建后直接消失，后者只暴露带前缀的变量。

需求与钩子对照表

需求落地时先定位钩子，再定作用范围；工具间的编年史式对比另见《前端构建工具链演进》，本文不写演进史。

需求 该用的钩子 为什么是它
造一个磁盘上不存在的模块 resolveId 配 load 前者给出稳定 id，后者补源码，浏览器不必知道文件在哪
兜住别名覆盖不到的裸标识符 resolveId 解析早于加载，失败前还有机会改写
转译自有语法或宏 transform 配 enforce: 'pre' 拿到原始源码，产出仍是标准 JS 与映射
往 HTML 里塞脚本或 meta transformIndexHtml 入口是 HTML，钩子能直接改标签
只在打包时产出清单 buildStart 配 apply: 'build' 开发阶段无需落盘，省掉无谓开销
加接口或调整中间件顺序 configureServer 直接拿到请求处理链与内部模块图
按最终配置决定行为 configResolved 配置已合并且只读，可判断命令与模式
控制热更新粒度 handleHotUpdate 传播之前能改受影响的模块集合

小结

Vite 的开发体验来自一个决定：把打包从循环里拿出来，让浏览器按请求驱动编译，代价用预构建与 URL 约定补回去；生产构建交给 Rollup，换的是完整的 tree-shaking 与分割粒度。插件模型沿袭 Rollup，虚拟模块是理解 resolveId 与 load 分工的最短路径，enforce 与 apply 决定你在时序里的位置。动手之前先确认改的文件类型与浏览器最终请求的 URL 是否一致，多数坑都出在这两者对不上。
