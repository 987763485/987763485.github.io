C# 异步编程 async await

async/await 写起来是同步的形状，跑起来是另一套机制。本文面向会敲 await 但没弄清背后机制的同学，按 .NET 8 与 C# 12 口径讲清状态机、任务、线程池与上下文，再落到取消、超时、异常传播、并发度控制这些线上真正咬人的纪律。读完应该能回答三个问题：为什么 await 不占线程，为什么一句 .Result 能把服务锁死，库代码里 ConfigureAwait(false) 到底该不该写。

机制：编译器把方法改写成了状态机

async 不是“给代码找一根线程”的开关，它是编译器改写语法的约定。凡是带 async 且返回 Task、Task<T>、ValueTask<T>、IAsyncEnumerable<T> 一类结果的方法，编译器都会生成一个实现 IAsyncStateMachine 的私有结构体，把方法里的局部变量提升成它的字段，把方法体沿着每个 await 切成若干段，再用一个整数状态字段决定从哪一段续跑。原方法本身只剩下“启动状态机、返回任务句柄”这一件事。

第一个 await 之前的代码，是在调用者所在线程上同步跑完的。到了 await，如果被等的任务尚未完成，方法立即返回一个未完成的 Task，剩余代码连同 json 这类被提升的字段一起留在状态机里，注册成续体。任务真正完成时——可能来自完成端口回调，也可能来自线程池工作项——运行时在捕获好的上下文上执行续体，状态机从下一个分支接着跑，最后由 AsyncTaskMethodBuilder<T> 把结果或者异常写进任务。调用方 await 它才取得到值；没人 await，异常就一直躺在任务里，一声不响。

想到这一层，三个常见误解就自行瓦解。第一，await 不等于新线程，绝大多数异步 IO 在整个等待期间不占用任何工作线程，只是把“等谁回来叫我”这件事交给了系统。第二，方法不是“跑完才返回”，而是“第一段跑完就返回”。第三，返回的任务是热任务：LoadAsync 被调用的那一瞬间请求已经发出，无法延后启动；真需要延后，就传 Func<Task> 工厂而不是任务本身。

线程池与同步上下文：await 之后你在哪一根线程上

续体不是随机投递的。await 会先捕获当前执行上下文，再据此决定恢复位置。承担这件事的是 SynchronizationContext，它的职责很朴素：把一段工作交给谁去跑。Windows 窗体和 WPF 装了 UI 上下文，续体被送回消息队列，最终在 UI 线程执行；ASP.NET Core 从设计上就没有“这个请求属于这根线程”的概念，请求管道里几乎没有需要还原的上下文，于是 await 之后的续体落回线程池，线程编号可以随便变。这就是同一句 ConfigureAwait(false) 在桌面端有明显收益、在 Web 端差别不大的原因。

上下文里除了同步上下文，还有 TaskScheduler.Current：在一个任务内部继续创建任务时，续体可能被留在同一个调度器上。平时感觉不到这层机制，一旦引入自定义调度器它就会显形。

真正决定吞吐的是线程池本身。它是一组共享的工作线程，从队列取任务、按压力增长，而增长速度相当克制，示意值大致是每秒新增一两个线程，线上表现为“第一波并发请求先排队，稍后才跟上”。于是有两类操作特别危险：在异步管道里调用阻塞 API，把等待期间那根线程整个占住；在池内线程上调用 .Result 或 .Wait()，而 await 之后的续体同样需要池内线程才能跑，两边互等，形成线程池饥饿乃至全局卡死。判据记一句就够了：只要可能在池内执行，就不要阻塞。

CPU 密集的活儿也是同一个道理。异步的意义是把线程让出去，计算没有可让的东西，给它套一层 async 只是装样子。真要并行算，就把循环显式交给 Task.Run 挪出当前请求线程，或者用并行库。

ConfigureAwait：库代码里的默认选择

ConfigureAwait(false) 只做一件事：告诉续体不必回到捕获的上下文，直接在线程池上恢复。代价是续体里不能再碰上下文保护的东西——UI 对象、请求上下文这类环境状态；AsyncLocal<T> 的值仍然正常流动，这一层不受影响，也最容易被误解。收益是省掉每次捕获与投递，在高频调用路径和桌面端相当可观。

选择规则按代码所在的位置划分，而不是按“这次要不要顺手优化”：

  • 应用层入口，事件处理器、控制器动作这类需要回到原上下文的代码，保持默认写法。
  • 库与可复用组件，数据访问、SDK、内部工具包，默认逐处写 ConfigureAwait(false)，因为你无法预知调用方是桌面端、Windows 服务还是 Web；把恢复位置的控制权交给最外层。
  • ASP.NET Core 里写与不写差别很小，但包可能被别的宿主引用，仍建议写。

纪律是一句话：不要在应用层把 ConfigureAwait(false) 贴得到处都是，也不要在库里只贴第一处——恢复位置是按 await 逐个决定的，漏一处就还一处。换到其他栈看，虚拟线程与挂起函数回答的是同一个问题，但它们各自的调度模型另有文章负责，这里不展开。

正确等待与死锁

await 是等待的正确形态，.Result、.Wait()、GetAwaiter().GetResult() 是三个常见事故源。它们的危险不在于“阻塞了一下”，而在于被阻塞的那根线程往往正是恢复续体所需的线程。最经典的死锁形状长这样：UI 线程调用 .Result，被调方法的第一段在 UI 线程上同步跑完，续体被排进 UI 队列，而 UI 线程此刻正忙着等结果，队列永远轮不到它——界面冻死，任务永远不会完成。线程池上的版本更隐蔽：并发一上来，池内线程全在等结果，续体排在队列里等不到线程，表现为整个服务无响应而 CPU 占用很低。

所以“异步贯穿到底”是原则而不是口号：底层返回 Task，中层透传 Task，直到最外层由 await 收尾。确实必须在同步位置等结果的场景是有的——进程启动的组合根、控制台入口、某些只能同步的接口实现——三条降低伤害的路子依次是：把入口本身做成异步，例如 Main 返回 Task<int>；把等待挪进 Task.Run，这只是把死锁换成饥饿风险，只在启动阶段可接受；最稳的做法依然是让边界异步，别把 Task 拆成阻塞调用。

“发出去不管”是另一类等待事故。_ = DoAsync(); 这种丢弃任务写法，异常既不进任何被观察的任务也没人 await，业务失败静默无声；.NET 里未观察的任务异常不会终结进程，但会在线程池回收该任务时经 TaskScheduler.UnobservedTaskException 上报，把它接起来打日志，是排障时少有的线索来源。要么 await，要么明确地记录并处理，别留悬空任务。

取消与超时：协作式的边界

取消是协作式的。CancellationToken 只是一个信号载体，它不会中断任何正在执行的操作；只有当代码把令牌一路传下去、并在合适的地方检查它，取消才会真的发生。令牌要作为参数一路传下去，循环里定期 ThrowIfCancellationRequested。一个不接收令牌的同步阻塞调用，唯一的取消办法是等它自己跑完，这正是把接口换成异步版本的价值。

超时是同一机制上的另一个触发源。CancelAfter 让令牌在若干时间后自动被取消，CreateLinkedTokenSource 能把上游取消与本地超时合并成一个令牌，两种来源在方法内部靠 ct.IsCancellationRequested 分辨，抛出的都是 OperationCanceledException。这里要特别区分 WaitAsync：它只让调用方不再等，底层操作照旧跑完并继续占着连接与线程，属于“放弃等待”，不等于“取消工作”。

最后一条容易漏：CancellationTokenSource 是 IDisposable，注册过回调或定时器的更要及时释放，否则在长生命周期服务里会攒出一条注册链，表现为托管内存缓慢上涨。ct.Register 的回调在哪根线程上执行不保证，别在 UI 上下文相关的方法里直接改 UI。

异常传播：AggregateException 什么时候才出现

异步方法的异常不会顺着调用栈立刻回到调用方，它被装进返回的任务里，等到有人 await 或者读取结果时才在这一点重新抛出。好消息是 await 抛的是原始异常类型，堆栈经过 Exception.DispatchInfo 保留了异步入口那一段，日志里看到的仍是 SqlException 这类具体类型，排查体验和同步代码一致。

AggregateException 只在“批量或阻塞式取结果”时才浮出水面，具体是四种场合：调用 .Wait() 与 .Result；访问 Task.Exception 属性；Parallel 系列方法；以及任务未被观察而由终结器上报时的 TaskScheduler.UnobservedTaskException。要注意的是 await Task.WhenAll(...) 只抛第一个异常，剩下的藏在各个任务的 Exception 里，需要自己遍历收集——批处理场景漏掉这一步，往往只看到一个失败，其余失败静默。

try/catch 跨过 await 是完全有效的，状态机的分段不改变语义；但 finally 里不要再 await 一个可能永远不完成的任务。IAsyncEnumerable<T> 的异常在 MoveNextAsync 处抛出，所以 await foreach 外面套 try 才捕得到，写在迭代体内部只覆盖了一部分。异常不该当控制流用，尤其别在深循环里靠它退出。

ValueTask 与 IAsyncEnumerable

Task<T> 是堆对象，一次异步调用至少分配一个。热路径上如果多数调用其实同步就能返回结果——命中缓存、流里已有缓冲数据——这个分配就成了纯粹的垃圾压力。ValueTask<T> 就是为这种情况准备的：同步完成时它把结果直接装在这个栈上的结构里，不产生对象；真要等待时再退化为内部的 Task。代价是它的使用约束比 Task 严格得多：只能被 await 一次，不能存进字段等以后重复等待，也不能并发等同一个实例，因为没有可重放的语义。需要多次等待或者跨方法保存，就 AsTask() 换回 Task<T>，或者干脆一开始就返回 Task<T>。判断标准是调用方是否由你掌控：库内部高频接口可以用，对外公开的异步 API 通常不值得。

IAsyncEnumerable<T> 解决的是另一件事：把“流”变成异步的。await foreach 逐项取数据，消费方不取，生产方就不推进，天然带背压；配合 await using 还能保证游标被释放。数据库大结果集、服务器推送、消息流都适合它。注意两点：接收令牌要用 [EnumeratorCancellation] 标注参数，否则枚举器收不到取消信号；需要还原上下文或附加令牌时，用 ConfigureAwait 与 WithCancellation 这两个扩展方法写在序列上，而不是在迭代体里手工兜。

并发度控制与实用清单

一段 Task.WhenAll 把一千个下游请求同时打出去，最可能的结果是下游被压垮、本进程内存被响应缓冲挤爆，最后连日志都写不出去。控制并发度最省心的工具是 SemaphoreSlim：先异步拿到许可，再在 finally 里归还，同时在飞的任务数就被钉在上限。

不要用 while (running >= 8) await Task.Delay(50); 这类轮询替代它，既浪费唤醒又容易漏归还许可。批处理还可以直接上 Parallel.ForEachAsync，它自带 MaxDegreeOfParallelism 与取消支持；生产者消费者结构则交给 System.Threading.Channels，比手写信号量清楚得多。

把剩下的纪律收成一份清单：异步方法以 Async 结尾并返回 Task 系列类型；async void 只允许出现在事件处理器里，且内部必须自己捕获异常；不要在异步方法内部用 .Result 或 .Wait()；不要把已经是异步的调用再包一层 Task.Run，那只是多占一根池线程；只有 CPU 密集工作才值得 Task.Run；每一个可等待调用都传令牌；库代码逐处写 ConfigureAwait(false)；ValueTask 只 await 一次；批量任务收集全部异常而不是只看第一个。

小结

机制只有一句话：await 把方法切成状态机的分段，等待期间线程被归还，恢复位置由捕获的上下文决定；其余全是工程纪律。别在可能进池的位置阻塞，别把任务扔掉不管，别把超时当成取消，别让 ValueTask 被等两次。进程级的 IHostedService 与优雅关闭、与其他语言生态和 Go 写法的横向对照，各自另有专文，本文只把 .NET 内部的这条异步链讲完。

写法 后果
.Result、.Wait() 死锁或线程池饥饿
async void（事件处理器除外） 异常无法捕获
_ = DoAsync() 失败静默无痕迹
Task.Run 包已是异步的调用 白占一根池线程
方法不接收 CancellationToken 无法取消，请求越堆越多
ValueTask 被 await 两次 未定义行为
库代码省略 ConfigureAwait(false) 桌面端续体多一次投递
一路 await 到底 等待期间不占线程
