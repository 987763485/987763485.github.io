前端可访问性工程化

可访问性（常写作 a11y，取自首尾两个字母之间有 11 个字母）最容易做成的样子，是需求评审里被提一句、上线前被补一堆 ARIA 属性、然后在下一轮迭代里被无声改掉。本文关心的是另一件事：怎样把它变成一套长期可维护的工程机制，让缺陷在编码期就被拦下、在流水线里被卡住、在验收时有人对着屏幕阅读器真的听一遍。适合负责组件库、前端基建或某个业务线的同学读，读完你应该能拿到一条可落地的检查链路、一组门禁分级策略，以及一份能直接抄走的人工验收清单。年代口径说明一下：本文以 WCAG 2.2 为参照（它在 2023 年 10 月成为 W3C 推荐标准），同时兼容大量团队仍在承诺的 WCAG 2.1 AA；欧盟 EAA 的适用期限还没到，美国的 DOJ Title II 规则刚发布、合规压力在未来两三年，本文只在必要处点到为止。

为什么”过检查”不等于”能用”

先把一个误解拆开：绿色分数、零告警、审计通过，都是”我们检查过了”的证据，不是”它能用”的证据。可访问性的障碍至少分四类，每类都有很典型的真实故障。

第一类是视觉障碍，包含全盲、低视力、色觉差异，也包括强光下屏幕看不清这类临时状态。典型故障不是”没做暗色模式”这么简单，而是信息只存在于视觉通道里：一个状态标签用红色表示失败、绿色表示成功，屏幕上是两个词，读屏软件念出来只有一句”成功”或者干脆什么都不念；再比如表单校验只在输入框右侧画了一个红点，没有任何文字。焦点环被全局重置语句抹掉（把 outline 设为 none 却忘了补自定义样式）也归这一类，它同时伤害键盘用户。

第二类是键盘与动作障碍，包含运动功能受限、使用开关设备或语音控制、以及手部临时受伤。典型故障有三件：只用鼠标事件驱动的交互（只绑了 mousedown 或只监听 hover 展开的下拉菜单）；自定义控件抢焦点导致 Tab 走不通或走一遍要按八十次；拖拽排序没有等价的键盘替代路径。WCAG 2.2 专门补了拖拽动作与目标尺寸相关的条目，正是因为这类”看着能点、实际很难点”的问题太多。

第三类是听觉与认知障碍。视频没有字幕是最表面的一层，更深的一层在界面语言上：错误提示写成”错误码 E4021”，用户不知道该做什么；页面每次聚焦新元素就自动触发动画或跳转；同一个操作在三个页面里有三种叫法。这一类问题几乎全部无法用机器检测，因为它检验的是内容与交互设计，而不是标记。

第四类是辅助技术兼容问题，这也是最容易”过了检查却不能用”的一类。举例：某弹层用 div 加事件模拟按钮，补了 role 等于 button，却没补 tabindex，读屏能读到却按不了；某个自动补全列表把选项渲染在 body 末尾的 portal 里，却没有用 aria-activedescendant 或焦点移动把关系接回去，于是键盘能选、读屏不知道选了什么；再比如把整个卡片包在 a 标签里、里面又放了一个 button，形成非法嵌套，结果部分辅助技术直接吞掉内层按钮。这些结构在 Lighthouse 的可访问性面板里可能一条都不报错。

所以工程上的第一原则是：把”能用”定义成可复现的行为，而不是把”检查”定义成可勾选的任务。后面所有机制都围绕这个定义展开——机器负责拦住结构与属性层面的确定性问题，人负责验证行为层面的不确定性问题，两者之间用清晰的分工表和缺陷流程连起来。

语义优先，ARIA 只是补丁

ARIA 常被当成可访问性的起点，实际应该是最后一步。正确的递进有三层，优先级从高到低。

第一层是选对原生元素。HTML 的 button、a、input、label、select、textarea、table、nav、main、h1 到 h6、ul 与 ol、fieldset 与 legend，这些标签自带角色、状态、键盘行为和焦点语义，浏览器实现了几十年，比任何库都稳定。一个原生 button 免费给你的是：可聚焦、Enter 与空格都能触发、role 为 button、disabled 时读屏会播报不可用、表单提交行为正确。

第二层是依赖隐式语义，不要重复声明。给原生 button 再加一个 role 等于 button，给原生 nav 再加 role 等于 navigation，都是噪音；只有在原生语义被样式或结构覆盖时才需要显式声明。同样，能靠 DOM 顺序表达的阅读顺序就不要用 aria-flowto，能用 label 关联解决的就不要用 aria-labelledby。

第三层才是 ARIA 的角色、状态与属性，用来填补原生 HTML 表达不了的组合：复杂栅格表格、树形控件、标签页、组合框、进度提示、动态区域。这一层的成本很高，因为 ARIA 只改变”被说出来的是什么”，不会改变任何键盘与焦点行为。声明了 role 等于 tab，就得自己实现左右方向键切换、Home 与 End 跳转、tabindex 的 roving 管理。这也是为什么组件库要统一实现这些行为，而不是让每个业务页面各写一遍。

ARIA 的边界与常见误用

ARIA 写错比不写更糟，因为它会覆盖浏览器原本做对的事情。边界要先讲清楚：它是给辅助技术的一层”旁白”，不改变焦点、不改变键盘、不改变可见文本，而且它的属性值会被缓存——节点内容改了但引用没改，读屏念的还是旧文案。

第一类误用是 role 与 aria-label 覆盖原生语义。给 a 标签加 role 等于 button，读屏会按按钮预期处理，但中键新开、复制链接、长按菜单等原生链接能力仍在，行为与预期错位；反过来给 button 加 role 等于 link 也一样糟。更常见的是 aria-label 把可见文本替换掉：按钮上写着”查看详情”，aria-label 写成”点击这里”，视力用户与读屏用户拿到两套名字，语音控制用户念”查看详情”就找不到目标。规则应该是：可见文本永远优先，label 要么不写，要么与可见文本一致或是它的超集。同理，一个已经写对 label 关联的 input 上再叠一个 aria-label，等于用旁白盖掉真正的说明，读屏只会念前者。

第二类误用是 aria-hidden 与焦点仍可达的矛盾。把整个背景层设为 aria-hidden 等于 true，只能让辅助技术”听不见”，挡不住 Tab 键。于是出现最难受的组合：读屏用户跳过了内容，键盘用户却陷在里面；或者装饰图标被隐藏了，但它外面包着的按钮还能聚焦，读屏念出来是一片空白。正确做法是隐藏就隐藏彻底——视觉隐藏与交互不可达要同时做到，禁用交互用 disabled 或 inert，而不是只贴一个 aria-hidden。反过来也成立：只给元素设 tabindex 等于 -1 不代表它从辅助技术里消失了，那只是移出 Tab 序列。

第三类误用是 aria-live 区域滥用。把整个容器标成 aria-live 等于 polite，容器里每一次数据更新都会被打断播报，用户点一下筛选，读屏就连环念出表格每一格。要点有三条：live 区域要小且稳定（提前存在于 DOM，之后只改它的文本，不要在插入节点的同时才加 live 属性，很多辅助技术不会回读已存在节点的属性变化）；播报内容只写结论，不写过程，”已加载 12 条结果”胜过重排整个列表；优先级要克制，polite 用于状态提示，assertive 只留给真正会丢失数据的告警。同理，role 等于 alert 的容器天然带 assertive 语义，不需要再叠一层 aria-live。

第四类是”属性拼盘”：把 ARIA 里所有看着相关的属性都加上。role 声明了却缺必要属主（checkbox 没有 aria-checked，combobox 没有 aria-expanded 与控件指向），aria-labelledby 指向不存在的 id，aria-describedby 指向被条件渲染掉的节点。这类问题机器能查，应该交给静态检查，不该靠人肉评审。一条实用约定是：新增 ARIA 属性必须同时写清它服务的键盘行为，评审时只见属性不见行为一律退回。

键盘可达与焦点管理

焦点顺序与 tabindex 的三档取值

理想情况下不需要动 tabindex：DOM 顺序就等于阅读与操作顺序，这是最省心也最不容易腐坏的结构。真要动，只有三档合法取值，各自用途很窄。取值 0 把本来不可聚焦的自定义元素放进自然 Tab 序列（比如可展开的表格行、自绘的滑块把手）；取值 -1 表示”不能靠 Tab 到达，但程序可以聚焦它”，这是模态框初始焦点、错误汇总区、跳过链接目标的标准做法；正数会把元素强插到序列最前面，多个正数之间还会因为取值不同产生谁先谁后的坑，并且几乎一定会与页面后来者冲突。工程上应该直接禁止正数：ESLint 的 jsx-a11y 插件与 Vue 的可访问性插件都有对应规则，配成告警或阻断都行，再加一条代码评审约定，比解释”这里为什么用 3”便宜得多。

跳过链接（Skip link）是给键盘用户的省时机制，做法是在 body 最前面放一个指向主内容区的链接，平时用视觉隐藏样式藏起来，聚焦时才显示。注意它必须真的能聚焦，用 display 为 none 隐藏会导致链接从 Tab 序列里消失。

自定义组件的键位不要自创，照 ARIA 授权设计实践里的既有习惯来。列表与下拉：上下键移动高亮，Enter 或空格确认，Esc 关闭并把焦点还给触发者，输入首字母做前缀匹配。组合框与自动补全：上下键在展开态选择，Esc 只关面板不清已选值，Focus 与 expanded 状态要分开维护。标签页：Tab 进出标签列表，左右键在标签之间切换，Home 与 End 到首尾，选中态变化后 panel 的显示与 aria-selected 必须同步。可展开区域：Enter 与空格都能展开，aria-expanded 挂在触发按钮上而不是容器上。实现这些时，roving tabindex（同一组里只有一个成员是 0，其余为 -1）比给全部成员设 0 更好，因为它把”组内移动”交给方向键，让 Tab 只负责进出组。

焦点陷阱、模态框与归位

模态框是键盘缺陷的重灾区，一个合格的模态框要同时做到六件事：打开时焦点进入对话框内部（通常是最先有意义的可操作元素或标题）；Tab 在边界处绕回，形成焦点陷阱；Esc 能关闭（除非它真的不可取消，那就明确不做）；背后内容既不可交互也不被读屏读到；关闭后焦点回到打开它的那个触发元素；标题与描述通过 aria-labelledby 与 aria-describedby 关联，对话框用 role 等于 dialog 或 aria-modal 为 true 的语义。

背景内容的处理值得单说。inert 属性能同时移出焦点可达性与读屏可达性，是当时最干净的方案，但兼容性口径要写清楚：2024 年这一版浏览器格局里，Chromium 与 WebKit 系已经支持了一段时间，Firefox 到 2023 年才落地，所以面向老旧 Firefox 的产品仍需要焦点陷阱加手工屏蔽兜底。用 aria-hidden 加 tabindex 改写来”手工实现 inert”是很常见的过渡方案，代价是要遍历子节点并在卸载时还原，很容易漏，因此这类逻辑应该沉到组件库而不是散落在业务里。

路由切换后的焦点归位是另一件事。单页应用换页面时浏览器不会自动把焦点放到新内容开头，读屏用户会以为自己还在旧页面上，焦点停在已经被卸载的元素上。约定是：每次主路由变化后，把焦点移到主内容容器（它带 tabindex 等于 -1 与更新后的 aria-label 或标题），同时滚动位置与文档标题一起更新。这一步要区分”路由变化”与”筛选变化”：筛选只更新局部内容，走 aria-live 播报，绝不能抢焦点，否则用户每改一次条件就被扔到页首。

异步内容导致焦点丢失的排查手法很机械但有效：在开发环境里挂一个全局监听，记录 activeElement 的变化与被移除节点的关系。

看到这条告警，修法是三种之一：保持节点存在只改内容、在替换前把焦点交给新的等价元素、或者把焦点显式交给容器并配合 live 区域播报。三种都别用 window 的 blur 去”消音”。

颜色与文本：把对比度落到设计令牌

颜色是可访问性里最容易”一次做对、长期跑偏”的部分，因为它由设计与前端共同持有，改动频率远高于结构。工程解法是把阈值写进令牌体系，而不是写进文档。

对比度的落地口径是两条：正文文本与图标的对比度不低于 4.5 比 1，大字号文本（通常按约 18 点常规字重或 14 点加粗为界，各团队按自己字体系统定一个明确的像素门槛）不低于 3 比 1；界面部件与聚焦环这类非文本元素不低于 3 比 1。关键不在数字，而在”这些判断由谁在什么时刻执行”。如果设计稿里的颜色是自由取值，前端只能靠肉眼和取色器，那么每次新增色板都在赌。令牌化的做法是给颜色分层：底层是色阶，中间层是语义令牌（文本主色、文本次要色、危险色、禁用态、聚焦环），上层才是组件引用。校验只发生在中间层，成本一下就降下来了。

落地时值得注意三处。第一，对比度要在真实背景上算，不是在白纸上算：半透明遮罩、渐变、带纹理的卡片、图片上叠字，都要按最坏背景取。第二，暗色模式不是把色阶反转，很多团队的做法是同一套语义令牌换一组值，然后让校验脚本对两组分别计算，避免出现”浅色达标、深色不达标”的静默回归。第三，聚焦环的可见性要单独验证：仅靠浏览器默认 outline 在深色背景上常常看不清，自定义样式要保证它与相邻内容之间达到非文本对比度门槛，且不依赖 outline 一种手段（再叠一层背景色或阴影更稳）。

不能只靠颜色传递信息这条约束，实操上等于要求”任何颜色都配一个非颜色通道”。错误状态配文字与图标、图表除颜色外还加图案或直接标数值、链接除变色外还加下划线、表格里状态列除色点外必须有文字。工程上可以用一个便宜的检查项来固化：搜索代码里的颜色相关类名（表示成功、失败、警告的语义类）附近是否出现文本节点或 title 之外的可读标签，这类检查做成脚本或 stylelint 规则都行，不必追求全覆盖，能拦住新增的就够了。

还有文本本身的可调性：相对单位比固定像素更抗缩放，用户放大浏览器字号后布局不应遮挡或截断；行长与行距属于令牌范围，换行与断词要有兜底，避免长链接撑破容器。把”放大到两倍字号截图”放进设计走查清单，比写一堆原则有用。

表单：从标签绑定到错误汇总

表单的语义靠关联维持：关联一断，页面看起来完全正常，读屏里却是一堆匿名输入框。

绑定只有两种可靠写法：label 的 for 与控件 id 对应，或者 label 直接包裹控件；绝对定位摆一个看起来像标签的 span 不算绑定。组件库里这件事要由契约保证：输入组件必须要求调用方提供标签，缺了就报错或至少在构建期告警，而不是允许 placeholder 顶替——placeholder 会在输入后消失、对比度通常偏低、部分辅助技术根本不念它。

几个细节值得展开。错误提示要用 aria-describedby 关联到控件本身，这样读屏聚焦输入框时就把错误一起念出来；只把红字放在右边，视觉用户看得到、读屏用户听不到。aria-invalid 为 true 要跟着真实状态走，别常驻。必填的标记：星号是视觉符号，需要 aria-hidden 加文字或 aria-required 承担语义；原生 required 属性会带来浏览器自带的校验提示，与自定义提示混用时容易重复播报，团队应选一种并写进组件文档。分组用 fieldset 加 legend，特别是单选组与复选组——没有 legend 时，读屏用户只知道按了哪个选项，不知道在回答什么问题。

格式提示要在提交前给，不要在出错后给。”请输入 11 位手机号”这种说明，比”格式不正确”有用一个数量级；能用 input 的 type、inputmode、autocomplete 就用，它们同时改善键盘用户的输入体验（弹出合适的数字键盘、自动填充减少打字量）。这里要提一句合规边界：自动填充涉及个人敏感字段，是否启用应遵循最小必要原则，并由用户在明确知情下选择，不要把”填得快”当成压倒性的理由。

验证码是经典的可访问性断点。图片验证码同时挡住了视觉障碍与部分认知障碍用户，工程上必须提供等价替代路径：短信或邮件验证码、语音验证码、支持读屏的算术题、或者在风险允许时改用无需用户解题的风险判定。团队约定可以是”任何主流程不得只有一条验证码通道”，把它写进验收清单里，比写在需求文档里更容易被执行。

错误汇总与焦点策略是最后一环，也是自动化完全查不出来的部分。提交后存在多个错误时，推荐的做法是在表单顶部渲染一个汇总区，它带 tabindex 等于 -1 与合适的标题，列出每一条错误并提供指向对应控件的锚点链接；提交失败时把焦点移到汇总区，读屏用户立刻知道自己卡在哪。这里有两个反效果要避免：一是给每个字段单独设 live 区域，一次提交引发十几条播报；二是把焦点直接扔进第一个输入框，用户不知道被扔到哪里、为什么。汇总区与字段内提示同时存在是可以的，但汇总区只出现一次、内容用简短的行动句（”手机号未填写”而不是”字段校验失败”）。

组件库把可访问性写进契约

前面几节的规则，如果只存在于文档和评审意见里，就一定会在第三次迭代后被改掉。可维护性的关键是把它们变成组件的接口——业务方拿不到不合规的用法，或者拿到了就编译不过、测试不过。

具体是三件事。第一，必填 props 表达语义要求：输入类组件的 label 必填、弹层组件的标题与关闭回调必填、图标类组件必须显式声明自己是装饰（走 aria-hidden）还是有文本含义（提供可读文本）。第二，默认角色与可组合的标签槽位：组件内部把 role、aria-expanded、aria-selected 这些状态收敛到自己身上，对外只暴露受控属性；描述与错误由组件负责生成 id 关联，业务方永远不需要手写 aria-describedby。第三，行为内聚：焦点陷阱、roving tabindex、方向键处理、归位逻辑放在组件或一个可复用的 hook 里，而不是每个页面抄一遍。

Storybook 是这套契约最便宜的验证场。给每个交互组件配一组可访问性 story，把状态矩阵铺开：默认、聚焦、禁用、加载中、校验失败、展开、只读、窄容器。矩阵里每一格都应该能用键盘走一遍、能开读屏听一遍，而不是只看视觉截图。把 axe-core 作为 Storybook 插件跑起来，每个 story 自动扫一次，新增 story 就自动多一道检查；但要清楚它的局限，插件报绿只说明结构层没撞规则，”禁用却仍可聚焦””展开却不播报”这类状态问题它一概不管。

设计走查清单是同一件事的另一半。条目不要写成”是否可访问”这种无法回答的话，要写成走查现场能执行的动作：这组颜色在暗色模式下对比度够不够；只用键盘能不能完成这次提交；错误提示有没有文字；聚焦环在真实背景上看不看得见；放大两倍字号后按钮文字有没有被挤掉。清单进设计评审模板，每次评审固定念一遍，比一次性大审计更能维持水位。

自动化能覆盖多少，门禁怎么分级

自动化检查的价值是拦截确定性错误，不是给出”通过”的结论。链路上分四个时机，越靠前越便宜。

编码期靠编辑器里的 ESLint 插件：React 侧用 eslint-plugin-jsx-a11y，Vue 侧用 eslint-plugin-vuejs-accessibility。它们能在你写下 div 加 onclick、空链接、缺标签关联的 input、role 与属主不匹配的那一刻报出来。规则里真正干活的是锚点有效性、非交互元素上的交互、点击事件缺键盘等价、ARIA 属性拼写、必需属主这几类，值得从一开始就设为阻断而不是告警。

PR 与 CI 阶段做运行时扫描：在集成测试里注入 axe-core（Playwright 用官方集成包，Cypress 用 cypress-axe），对每条关键路由或每个 story 跑一次，输出违规规则标识、影响节点与修复指引。Lighthouse 的可访问性面板适合做趋势观察和版本对比，不适合当门禁——它是加权分数，一处严重缺陷和十处小问题可能给出同样的分。

axe-core 这类工具的能力边界要讲给团队听：属性拼写、必需属主、名称可读性、对比度、非法嵌套这类结构性问题判得准；而焦点顺序是否合逻辑、播报是否打断、拖拽有没有键盘替代、错误文案能不能执行，多数状态类与语义类问题机器查不出来。所以门禁的作用域要写清：它管新增的确定性违规，其余交给人工验收。把这句写进 CI 说明，可以避免团队把绿灯当成上线许可。

  C --> D[CI 门禁: 阻断级规则失败即红灯]

门禁分级的建议是两层：阻断层只放”确定是缺陷、修复成本低、误报极少”的规则（非法嵌套、缺必需属主、名称为空、交互无可键盘等价）；告警层放需要人判断的（对比度临界、landmark 结构、重复 id）。存量债务用 baseline 或豁免清单渐进消化——把当前违规按规则与页面快照记录下来，门禁只检查”是否比快照更差”，同时给豁免项挂负责人与到期时间。这一步很关键：一上来就全量阻断，团队的理性反应是关掉规则或者在文件头加一行忽略注释，可访问性检查就此报废。豁免清单要出现在 PR 的 diff 里、要在周报里能被看见，让”加豁免”变成有成本的动作。同样重要的失败信息给到谁：CI 红灯要把可读的失败摘要写回 PR 评论，指明文件、规则、复现步骤，而不是只留一行退出码，否则没人会去看工具输出的原始 JSON。

人工验收与真实辅助技术

人工验收不该是”有空试一下”，它要有固定脚本、固定环境和固定产出。环境口径就三套：Windows 上的 NVDA 配 Firefox，macOS 与 iOS 上的 VoiceOver，Android 上的 TalkBack；键盘单独一档，不装任何辅助技术也要走。每套都要真听真按，看别人演示不算验收。

度量与埋点：把无障碍缺陷当缺陷管理

工程机制要能被跟踪，否则永远是”尽力而为”。做法是把无障碍问题纳入既有缺陷流程：同一个模板、同一套分级、同一个看板，回归走同一套用例库。分级按影响而不是按规则名定级：主流程完全无法完成为一级，能完成但要绕很远或需要他人帮忙为二级，播报冗余、焦点顺序别扭但目标可达为三级。一级二级不豁免到下个迭代，三级可以进豁免清单但要挂到期时间。

指标建议只留四个，阈值一律是团队约定示例，不要跨团队照抄：新增阻断级违规数（来自门禁扫描，示例口径为每次发布不高于上一版）、验收脚本覆盖率（关键路径页面被人工验过的比例，示例口径为主流程全量、其余按季度三成）、缺陷平均修复时长（按分级分别看）、回归复发率（同类问题在同一页面二次出现的比例，示例口径为不高于团队约定的低位）。这四个数合起来才说明趋势，任何单一分数都不行。

埋点这块要格外克制。若确实需要观察使用情况以便改进，原则是最小必要采集：不采集可标识个人的信息，不采集手机号、精确地理位置这类敏感字段，也不尝试推断具体个人的身体状况——辅助技术类型这类标签本身就敏感，除非有明确用途并取得用户同意，否则不要采。可行的替代是把无障碍相关的失败信号汇聚到服务端可观察的层面（表单放弃率、错误汇总触发次数、键盘路径长度这类匿名化聚合指标），字段脱敏后聚合存储，明示留存期限并按期删除，同时在隐私说明里写清采集范围与目的。度量的是界面，不是人。

小结

可访问性工程化的实质，是把”这类问题由谁、在什么时刻、以什么成本被发现”定下来：语义与属性层面的确定性错误交给编码期插件与 CI 门禁，状态与行为层面的问题交给组件库契约和固定的人工验收脚本，趋势与存量债务交给有负责人、有到期时间的豁免清单。下面这张对照表可以直接当分工模板用。

机制建成后，日常动作其实很少：新增组件补 story 与状态矩阵，改交互跑一次键盘脚本，发布前看门禁是否比快照更差，季度清一次豁免清单。把可访问性从”补一堆属性”变成”补一条链路”，它才能在不被特别惦记的迭代里也不退化。
