Web 组件化设计系统实践

设计系统落地时，最容易的错觉是“组件库发上了 npm，设计系统就建成了”。本文从工程实现的角度拆解这条路上真正的难点：组件 API 如何设计得既稳定又好用，自定义元素与 Shadow DOM 的边界能承担什么、不能承担什么，设计令牌如何穿透样式隔离下发到组件内部，以及文档、版本、治理与测试这四件事如何协同。

我们把载体选定为 Web Components，因为它天然跨框架，也因为它把许多平时被框架封装掩盖的问题暴露了出来。以下口径基于 Custom Elements v1 与 Shadow DOM v1 这层规范，涉及支持面的地方会明确标注“当时”的状态。

设计系统的构成：组件库不等于设计系统

一个可运行的设计系统至少包含四条线。第一条是设计令牌，把颜色、间距、字号、圆角、阴影、层级、动效时长这些决策抽成有名字的常量，它们是设计与工程之间唯一的“合同文本”。第二条是组件，令牌在这里被实现为可交互的行为单元，包含视觉、状态机、键盘与语义。第三条是文档，文档不是网站的附属品，它是设计系统真正的交付面——用不出来的规范等于没有规范。第四条是治理，决定谁能提需求、谁来评审、破坏性变更走什么流程、废弃什么时候真正删除。

组件库只是第二条线的产物。把它单独交付给业务团队，通常会得到视觉各改各的、令牌被绕过、深色主题上线才发现没人做对比度检查的结果。缺的是另外三条线。

需要说明的是，协作流程本身属于设计工程协作流程这一独立议题，本文只讨论工程实现；微前端解决的是应用级组合与独立部署，设计系统与它配合时只需保证令牌与组件在所有子应用里来自同一份来源。

选择 Web Components 作为载体，理由有三点。跨框架复用不需要为每个框架写一层适配壳；Shadow DOM 提供真实的作用域隔离，业务侧的全局样式不会意外染红我们的按钮；组件是有 DOM 身份的元素，能被非框架代码与静态 HTML 直接使用。代价也必须摆到桌面上：SSR 需要额外方案、表单集成要用相对新的规范、样式定制要走显式公共接口。

组件 API 设计：把边界写清楚

组件 API 是长期承诺，写错一个属性名要背着它活过三个大版本。第一原则是命名一致性：同一概念在所有组件里用同一个词，布尔属性用现在时状态形容词，事件用现在时动词，避免 on-click 这类把监听器前缀写进契约的名字。

属性要区分 attribute 与 property 这两种写入路径，这是自定义元素最容易踩的坑。attribute 是 HTML 上的字符串，kebab-case，只能在标签里写；property 是 JS 对象上的字段，camelCase，能承载任意类型。规范要求的做法是“反射”：把 this.disabled = true 同步反映到 setAttribute('disabled', '')，反过来属性变化也要更新 attribute，否则用户从 DOM 上读到的是旧值。

事件的约定要写进文档而不是靠猜。CustomEvent 默认既不冒泡也不跨越 Shadow 边界，不显式设置 bubbles: true, composed: true，写在宿主外的监听器永远收不到——这是 Shadow DOM 组件最常见的“事件丢了”疑问。开启 composed 后事件穿过边界，但到达宿主之外时 event.target 已被重定向为宿主元素，真实来源要看 event.composedPath()。所以负载要自带语义：detail 定成稳定的对象形状，让消费方不必读内部节点。内部实现事件与对外公共事件要分开，公共事件必须带组件前缀，例如 app-button:submit，避免与原生事件或第三方组件撞名。

插槽是组件 API 里最容易被低估的部分。默认插槽承接“用户写进来的一切”，具名插槽承接结构化的位置，两者语义完全不同：默认插槽允许自由内容，具名插槽一旦出现在文档里就成了契约。slotchange 事件用来感知插槽内容变化，从而决定“没有内容时隐藏这个区域”这类行为，注意它只在节点列表整体变化时触发，子树内部的修改不会触发，需要 MutationObserver 补齐。

受控与非受控的取舍在这里没有框架那层糖衣。原生输入天然非受控，想让属性真正控制视图，就要在 attributeChangedCallback 里回写 DOM 值并小心光标位置；纯非受控则把状态留在内部，只通过事件对外报告。一个务实的组合是：值属性只在变化时“覆盖一次”，用户输入走事件通道，文档里明确写出这个差异，别让读者以为它和 React 的 value 语义相同。

枚举属性的校验建议做成通用工具：非法值回落到默认值并告警。直接抛错在库代码里代价太高，静默忽略又让人无从排查。布尔属性用 toggleAttribute，数值属性做范围裁剪，字符串属性先 toString 再处理空值——文档里要有一节“输入容错”。

自定义元素与 Shadow DOM 的边界

customElements.define 把标签名与类关联起来，命名必须包含小写字母和至少一个连字符，这是规范硬性要求，也是设计系统前缀（比如 app-）天然的落点。注册是全局单例行为：同一个标签名注册第二次会抛 DOMException，因此库代码要写成“查过再注册”的幂等模式，业务侧混合加载两个版本时也不会因为重复注册白屏。

三个生命周期回调各有明确职责。connectedCallback 可能在属性解析前就被调用，也会因元素移动而多次触发，所以监听器要成对注册、渲染要幂等；disconnectedCallback 用来摘除事件、定时器与观察器，漏掉就会在长会话里累积泄漏；attributeChangedCallback 只对 observedAttributes 声明的属性生效，第一次调用可能在 connectedCallback 之前，两者都要按“可能发生两次”来写。

attachShadow({ mode: 'open' | 'closed' }) 的选择常被简化成“安全与否”。closed 模式只是让 element.shadowRoot 从外部读到 null，构造时保存的引用依然在内存里，它挡不住有心人，只挡得住无意中的调试和第三方脚本乱改内部节点。代价是排查线上问题时自己也读不到，工具链、测试框架与部分无障碍检查器同样受阻。多数团队的做法是：默认 open，把“不许改内部 DOM”作为文档约定而不是靠 closed 强制。

样式隔离是 Shadow DOM 最有价值的部分，也最容易被误解。它隔离的是选择器作用域，不是继承：color、font、line-height 这些可继承属性依然从宿主流进来，CSS 自定义属性同样会继承——这一点在后面令牌下发那节会反复用到。它也不隔离全局资源，@font-face、关键帧动画与文档级变量的行为都要单独验证。

表单集成是边界上最实的一处缺口。原生表单只认识标准表单控件，自定义元素默认不参与提交、不参与校验、不进 FormData。formAssociated: true 加上 attachInternals() 返回的 ElementInternals 可以补上：设置值、报告有效性、实现约束校验 API、参与表单重置。到 2024 年底这套接口已在多数现代浏览器落地，但各家实现仍在补齐细节，要写出对旧环境的降级路径，尤其是内部需要提交到传统 <form action> 的场景，稳妥方案还是在 Shadow 外放置一个隐藏的原生输入承接值。

SSR 与声明式模板是另一处限制。Shadow DOM 无法把内部结构以纯 HTML 属性携带在静态标记里，服务端渲染首屏要么输出“宿主加一份等价静态结构”，要么接受水合前的空白。2024 年的稳妥口径是：声明式 Shadow DOM 在部分浏览器已可用，其他环境仍需 polyfill 或服务端方案，跨浏览器全面支持还不能当作既定事实；用 CSS Modules 给 Web Components 做样式作用域这类思路当时仍在早期阶段，不宜作为架构前提。

在 React 与 Vue 中使用自定义元素

框架对未知标签的处理方式决定了组件库的使用体验，这里写通用注意点，不绑定具体版本。

React 把 JSX 的属性透传为 DOM attribute，而不是给宿主元素设置 property。这意味着两件事：一是复杂值（数组、对象、函数）无法通过 attribute 表达，必须走 ref 拿到元素实例后赋给 property；二是 className 之类的框架约定名不会自动映射到组件的 class 语义，自定义元素自己要保证 attribute 名是 kebab-case 的合法入口。事件方面，React 的合成事件建立在原生事件冒泡机制上，组件的 CustomEvent 必须同时开启 bubbles 与 composed 才可能被宿主外的监听器收到；同时 onChange 这类框架惯用名与原生 change 语义并不总是一致，文档里要给出“该监听哪个事件名、detail 是什么形状”的明确表格。更可靠的路径是用 useRef 保存元素实例后手动 addEventListener，这条写法应该进示例代码。

Vue 在模板编译阶段会对未知标签产生告警，甚至把属性当成 attribute 处理。正确的思路是在编译器配置里声明“带 - 的标签或匹配某个前缀的标签视为自定义元素”，让编译器跳过解析、不再警告，并把属性透传行为固定在 attribute 层面。把这个配置项写进设计系统的接入文档，作为“三行配置完成接入”的一部分，比让每个业务团队自己摸索要有效得多。若组件同时提供 property 入口，示例里应演示 ref 赋值或 .prop 修饰符这类显式写法。

TypeScript 需要单独扩声明，否则 <app-button> 在 JSX 与模板里都是类型错误。自定义元素标签名含连字符，无法直接作为接口属性名，必须用引号形式声明。

这份声明文件是公共 API 的一部分，要跟着组件一起发布、一起进变更日志。手工维护迟早会漂移，可行做法是从组件类的元数据生成，或者至少用一条测试断言“attribute 名单与 observedAttributes 完全一致”。事件契约同样要生成类型，让 detail 的形状由组件源码而不是文档示例决定。

设计令牌下发：从常量到 Shadow DOM 内部

令牌要分层，否则改名会拖垮整个系统。原始层是事实（blue-500 的色值），语义层是意图（color-action-primary、space-md），组件层是局部决策（button-padding-inline）。组件只允许引用语义层与组件层，禁止直接读原始层，这条规则要在构建期用 lint 强制。分层最大的好处是换肤：主题切换只需把语义层重映射到新的原始值，组件源码一行不动。

下发路径是：令牌源文件经构建脚本产出 CSS 自定义属性表并挂到文档根节点，同时产出类型化常量供组件内部逻辑取值。两个产物必须来自同一次构建，手工同步一份 CSS 是事故来源。

CSS 自定义属性会继承进 Shadow DOM，这是令牌穿透隔离墙的唯一正道，也是它最大的优点：变量名就是公共 API，值由使用方决定，组件不需要为每个可定制点提供 prop。但要小心“继承不到”的场景——组件被 portal 到文档其他位置、被放进另一个 shadowRoot、或者在 iframe 里渲染时，根节点上的变量表可能不在作用域链上。健壮做法是给每个变量都带兜底值（var(--x, fallback)），并且允许组件接受一个“令牌命名空间前缀”属性。

把令牌注入 Shadow DOM 内部有几种做法，各有适用面。第一种完全依赖继承，根节点定义、内部消费，最简洁，但处理不了跨作用域渲染。第二种在组件的 shadow 样式表里声明 :host { --x: ... }，把令牌作为默认值打包进组件，宿主上的同名变量可以覆盖它，形成“组件自带主题、外部可改写”的关系；这份内部变量表最好由构建生成。第三种用构造样式表：把令牌表编译成 CSSStyleSheet 实例，通过 adoptedStyleSheets 赋给 shadowRoot，多个组件共享同一份对象引用而不是各自复制文本。要注意 adoptedStyleSheets 在 shadowRoot 上的可用面曾比在 document 上更窄，增量更新还需要“可构造且可变更”的样式表，落地前先确认目标浏览器矩阵；不支持的环境回退到在 shadow 内插入 <style> 文本。

明暗主题与品牌皮肤不要靠多份 CSS 拷贝。主题只是变量表的一次重赋值，切换时改文档根节点的 data-theme，组件不重新渲染。若品牌有 N 套，就让构建产出 N 份变量表加一个运行时注入器，而不是 N 份组件样式。同时把主题解析失败当成错误暴露出来：主题名不存在时应告警并回落到默认主题，而不是静默留下一堆未定义的变量导致视觉塌陷。

样式与主题的工程细节

公共样式 API 要显式设计，否则使用方一定会去攻击内部结构。可用手段只有三种是干净的：CSS 自定义属性、::part、以及属性驱动的变体。三者定位不同——变量用于“改一个值”，part 用于“改一个节点的样式包”，变体用于“切换到另一种被设计过的形态”。::part 需要在 shadow 内给节点标注 part=“label”，外部用 app-button::part(label) { ... } 命中；它跨不过第二层 Shadow 边界，除非中间层用 exportparts 显式导出，组合式组件里这很容易漏，所以要在文档里列出每个组件暴露的 part 名单，并把“名单外的节点都算私有”写成规则。

要避免深度覆盖。业务侧一旦习惯用 !important 和极端选择器去压样式，组件的可预测性就消失了。治理方式是提供足够多的显式出口（变体加变量加 part），同时在验收清单里检查“是否存在对内部节点的覆盖”。当发现某类覆盖反复出现，正确响应是把它升级成公共 API，而不是教用户使用更狠的选择器。

样式复用方面，把跨组件共享的基础规则（重置、排版、焦点环）放进少量构造样式表实例，让所有 shadowRoot 引用同一批对象，焦点环这类全局一致性修改只需改一处。动画关键帧与 @font-face 在 Shadow 作用域内的可见性并不总符合直觉，涉及这些资源时优先在文档层定义、在组件层引用名称，并用真实浏览器的集成测试覆盖。

字体与图标在 Shadow DOM 内的引用有两个细节。@font-face 的 src 在样式表被解析时必须仍然有效：样式表内联进 JS 后写相对路径，基准会被解析到文档而不是包目录，应在构建期把资源转成可内联数据或输出绝对 URL。图标更推荐内联 SVG 而非字体图标，可控、可着色、能被辅助技术识别；装饰性图标加 aria-hidden，有含义的图标要带可访问名称，外链图标还要考虑 CSP 与离线场景。

可访问性：组件必须自带，不能指望使用方补

自定义元素让无障碍责任从“每个业务页面”转移到“组件内部”，这是好事，前提是组件真的做完了。原生元素能给的语义，自定义元素默认给不了：一个 <app-button> 不是按钮，它只是一个未知元素。要么用 Shadow DOM 内部的真实原生元素承载交互，要么在宿主上补齐 role 与 tabindex 并自己实现键盘行为。前者优先，因为浏览器原生行为（表单提交、空格激活、辅助技术播报）几乎不可能被手工实现完整。

键盘导航要看清焦点所在的位置。焦点在宿主上时，Shadow 内部节点无法被 Tab 单独到达；焦点进入内部后，Tab 顺序由内部 DOM 决定，离开组件时又要正确回到文档流。复合组件（标签页、菜单、表格、对话框）应实现方向键在内部项之间移动、Home/End 跳转、Esc 关闭并把焦点还给触发元素，对话框还要做焦点陷阱与背景滚动状态还原，这些都归组件负责。

焦点可见性属于设计令牌而不是组件细节。全局定义一套 :focus-visible 环，Shadow 内每个可交互节点都引用它，并保证与所有主题背景的对比都满足要求；不要因为“视觉稿没画焦点态”就把它删掉。WCAG 2.1 与 2.2 都可以作为依据，2.2 从 2023 年 10 月起已成为 W3C 推荐标准，其中针对焦点外观与目标尺寸的增量要求，对触屏与高密度工具栏组件有直接影响，验收时按 2.2 的口径检查更稳。色彩对比度要在令牌层校验：语义色对语义背景的对比比值由构建脚本算出来，不达标就不让这次令牌变更合入，而不是等人工抽查。

动态内容更新要能被告知。异步完成的列表、校验失败的提示、加载状态切换，都该通过 aria-live 区域播报；实时程度按内容重要性与时间敏感性选择礼貌级别，不要把每个状态变化都设成断言式播报，那会让屏幕阅读器用户反而错过真正重要的信息。校验错误的组件要把错误消息与字段用 aria-describedby 关联起来，并在宿主上维护 aria-invalid 状态。

组件级 a11y 测试要写进单测而不是只挂在 CI 扫描任务上：断言默认 role、断言键盘序列后的焦点位置、断言隐藏状态下不可聚焦（inert 可用时优先用它，否则要在隐藏时摘掉 tabindex 并禁用内部控件）。这些断言比任何自动扫描器都更早发现问题。

文档与交付：把组件当成产品发布

文档站建议直接用 Storybook 这类组件工作区：一个组件一份 stories 文件，同时充当示例、手工测试用例与视觉回归的输入源。文档页必须给出可复制的完整示例，覆盖安装、变量前缀设置、事件监听与 detail 结构，示例代码由构建从 stories 提取，避免手写文档与真实用法漂移。除示例外还要有“属性表、事件表、part 表、CSS 变量表、可访问性说明、已知限制”六个固定区块，最后一项要写在显眼处，否则使用者会把限制当成 bug 提交工单。

设计令牌与代码要双向同步。设计工具里的令牌修改应能生成令牌源文件，源文件变更触发构建产出 CSS 变量与类型常量，同时让文档站显示“这个语义值当前指向哪个原始值、被哪些组件引用”。反向也要通：组件里出现未被令牌覆盖的硬编码值，构建就该失败。做到这两条，令牌才是活的资产。

交付物不止 npm 包，还应包含类型声明、令牌包、接入用的编译器配置片段、变更日志、每个破坏性变更的迁移指南与可执行 codemod。迁移指南要写清“改前怎么写、改后怎么写、为什么必须改”，只有“不兼容变更”四个字的日志会让人直接停止升级。变更日志由提交时的约定式变更说明聚合生成，人工只做归类与排序。

验收清单是治理落到实处的地方。组件上线前逐项确认：API 三表齐全、键盘与屏幕阅读器手工走查通过、对比度自动校验通过、深浅两套主题截图确认、非法属性值有回落与告警、SSR 场景有说明、无内部节点被外部覆盖、体积增量在预算内、废弃项有告警与移除计划。这份清单本身就是文档站的一页。

版本与破坏性变更：让升级是可计算的决策

组件库用语义化版本不是为了好看，是为了让业务团队能算出成本：修订号是修 bug，次版本号是新增能力且向后兼容，主版本号意味着有人要改代码。这个承诺一旦被破坏（比如次版本里悄悄改了默认值），整个版本号体系就失去意义。所以发布前要跑公共 API 快照比对：属性名、事件名、part 名单、CSS 变量名单四类都在快照里，任何删除或改名都必须走主版本。

废弃策略要留出足够长的缓冲：先在同一主版本里发告警（控制台加文档站标记），保留旧行为至少一个次版本周期，再在下个主版本移除，并在迁移指南里给出可执行 codemod。移除时把告警文案写死成“迁移到哪一行文档”，让人能自查。

多版本并存是 Web Components 特有的坑。同一次运行加载了两份组件包，注册表冲突会以“标签名已被占用”的形式抛错；即便做了幂等保护，先注册的那份实现会赢，行为静默回退到旧版，排查成本极高。可行手段是把标签名与前缀纳入版本契约、让打包工具对同一标签名做去重检查，并在浏览器端输出“当前生效实现来自哪个包”的诊断信息。令牌包与组件包版本错配更隐蔽：组件引用了不存在的变量，视觉直接塌陷，因此两者的兼容矩阵必须写进发布说明。按需引入与体积要一起看——注册即引入，一个包导出全部组件会让首屏付出所有类的代价，构建时应支持子路径导入，并把每个组件的体积做成预算门禁。私有 registry 与内部发布流程要区分预览与正式通道，正式版本不可覆盖，包名统一加组织作用域，避免与公网包撞名。

跨框架复用与治理

跨框架复用不是“框架都能用”就结束，它需要有人长期为兼容性负责。治理的最小结构是：一个维护小组负责公共 API 与令牌，业务团队的需求走设计系统 backlog，提需求要写清使用场景而不是实现方式；每季度看一次采纳度，口径例如“接入组件的业务页面占比”“绕过令牌写的硬编码颜色数量”“升级停留的主版本数”（均为示意值口径，不用于个人绩效）。组件合入有质量门禁：视觉回归通过、a11y 自动扫描无严重项、单测覆盖率达到团队约定示例阈值，缺一条就不进主干。

作为设计系统载体，三种技术的取舍差异很直接：

维度 Web Components React 组件 Vue 组件
跨框架复用 原生标签，任意框架与静态页通用 需与宿主框架同栈 需与宿主框架同栈
SSR 首屏 标签可输出，Shadow 内容需额外方案 框架生态成熟 框架生态成熟
样式隔离 浏览器内置作用域 依赖构建工具约定 依赖单文件组件约定
生态成本 类型与文档需自建声明 组件生态与工具链最大 模板与编译器配置友好

测试策略：四层各司其职

单元测试跑在 DOM 环境里，覆盖生命周期与契约：observedAttributes 是否真的触发回调、属性回落是否符合文档、断开连接后监听器是否摘干净、插槽为空时区域是否隐藏。第二层是事件契约测试，把每个公共事件的 bubbles、composed 与 detail 形状写成断言——这三项最容易在一次重构后悄悄变化。第三层视觉回归以 stories 为用例源，覆盖深浅主题、各变体、禁用与加载态、窄视口。第四层是 a11y：自动扫描负责机器可判定的部分（role 合法性、对比度、标签关联），键盘走查必须人工执行，因为“顺序对不对”“焦点是否回到触发元素”这类判断扫描器给不出结论。四层放在同一条 CI 流水线上，任何一层失败都不发版。

小结

把设计系统交付到工程里，靠的不是一个组件包，而是四条线同时成立：令牌有分层且能穿透 Shadow 边界，组件 API 把 attribute、property、事件、插槽的边界写清并有类型兜底，文档把示例与限制一起交付，治理让破坏性变更有代价、废弃有期限。Web Components 的价值在跨框架与真隔离，代价在 SSR、表单集成与自建工具链，而这些都能靠明确约定消化。剩下的长期动作只有一件：把支持面确认当成常规，而不是假设。
