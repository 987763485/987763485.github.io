Service Worker 离线缓存实战

本文只解决一件事：把 Service Worker 的缓存与更新写成能直接抄进项目的代码，适合已经会注册 worker、却常被“旧包”和“断网白屏”折磨的前端同学。manifest、安装条件与推送的平台差异归《PWA 渐进式 Web 应用实践》，本文不碰安装与推送；最小注册示例见更早的《Service Worker 与 Web Push 实战》，本篇按可落地的成熟度重写。

注册与生效时机

最容易误判的一点是：注册成功不等于已经生效。register() 是异步的，浏览器要下载 sw.js、求值、跑完 install 再进入 activate，之后才接管请求；而首次访问的 HTML、脚本、样式早在这次导航中发出并完成，Service Worker 根本来不及插手。判据不是注册返回的 Promise，而是 navigator.serviceWorker.controller 是否为 null：为空说明当前页面完全没被控制过。要验证离线能力，必须做一次新导航或者另开标签页，而不是在当前页勾选 DevTools 的 Offline。

controllerchange 只在控制者真的换人时触发，是“提示刷新”的正确挂载点；用 notified 兜住重复触发，否则多标签页会把用户淹在弹窗里。注册还有个硬前提：只在安全上下文可用，即 HTTPS 或 localhost，用局域网 IP 走 http 调试时 navigator.serviceWorker 直接是 undefined，此时排查代码毫无意义。

有团队喜欢用 skipWaiting() 加 clients.claim() 让首访立刻接管：首屏确实能命中缓存，代价是页面里已执行的 JS 与新 worker 提供的资源可能来自两个版本，接口字段或 chunk 名一旦不匹配，就出现只在灰度当天复现的怪错。纯静态站可以放心用，带接口协议的 SPA 只在无版本跳变的补丁发布里用。

生命周期代码骨架

sw.js 的三个事件是全部策略的落点。install 必须把预缓存放进 event.waitUntil()，否则 worker 可能在下载完成前被终止，桶里只剩半截文件；activate 负责清旧桶与接管页面；fetch 只处理同源请求，跨域直接放手。

三个细节值得强调。第一，fetch 里对跨域请求直接 return 是刻意的：一旦 respondWith 了跨域请求，你拿到的是 opaque 响应，response.ok 恒为假、状态码与长度都被抹平，策略瞬间失去判断依据，确实需要缓存第三方 CDN 的除外。第二，install 只做“下载并落桶”这一件事，把清理留给 activate，职责混在一起时旧桶删不干净很难定位。第三，逐项 cache.add(url).catch() 取代 addAll，失败能精确上报到某个 URL，缺的那一项会在运行时走网络回落，不致命。

版本与缓存命名

桶名必须能代表一次构建，我用 precache-<构建号前八位>，构建号由打包工具在编译期注入 sw.js。不要用 v1、v2 这类手工自增：并行流水线和回滚会把语义搅乱；也不要用日期，同一天多次发布会撞名。前八位提交号既唯一，又能在排障时直接反查代码。

上一节的 KEEP 只是形态校验，能挡住别的库写进 CacheStorage 的桶，却挡不住同形态的历史版本桶，所以真正的清理要显式列白名单，把当前桶和上一个桶留下：

留一个旧桶的原因很实际：正在运行的页面还引用旧构建资源，旧桶全删会让它在下次请求时集体落到网络；而它一旦被新导航替换，那个桶就在下一次 activate 被回收。

为什么按 key 逐个删除不如整桶删除可靠？四个理由。第一，逐 key 要枚举旧版本的清单，而清单只是构建时快照，资源改名、下线或加 query 之后，cache.delete('/static/app.js') 就找不到对应条目，且 Cache.delete() 只返回 false 不抛异常，静默留下孤儿。第二，缓存 key 是写入时那个完整 URL，query 顺序或尾斜杠不同就是不同条目，手拼字符串必然删不对齐。第三，配额按桶回收：残留条目持续占用存储配额（示意值：单桶 8 MB），caches.delete(name) 一次把整桶空间释放干净。第四，逐 key 是 N 次异步调用，activate 的时间有预算上限（示意值：几十秒），中途被终止就留下半删状态；整桶删除是 CacheStorage 层的一次操作，没有删到一半。

预缓存桶与运行时桶要分开命名。runtime-api-、runtime-img- 这类桶不能靠版本切换清理，得自己限量：条目数与存活时间各设阈值（示意值：200 条、7 天）。注意 Cache 不记录写入时间，想按时间淘汰就得自己留痕——写回时把时间戳做成响应头塞进重建的 Response，读取时再解析它，这份留痕在下一节还会用来判断新鲜度。

三种策略的实现与适用面

cache-first：只给指纹资源

命中即返回，不发一个网络字节，这是断网下最稳的策略，适用对象是文件名带内容指纹的 js、css、字体和图片。它害你的方式很直接：把没有指纹的 index.html 或 /static/app.js 放进 cache-first，桶名不变用户就永远拿旧包，怎么刷新都没用；命中即返回还意味着放弃 ETag 与 Last-Modified 协商，服务端紧急下线某个资源也不会生效。带 Set-Cookie 或有 Vary 敏感字段的响应同样不适合。写回前判 res.ok && res.status === 200，是为了别把 3xx、404 和 opaque 响应固化进桶里。

network-first：需要新鲜度的接口

要点有三处。超时必须用 AbortController 主动掐断，否则离线时首字节要等到浏览器自己的连接超时才失败；回落查找用 ignoreSearch: true 才能覆盖 query 有轻微差异的同一接口；超时和真正的服务端错误要分开处理，5xx 不该被吞掉，让页面拿到真实状态码比“看起来有数据”重要。害你的方式：阈值定太长（示意值：8 秒）时，弱网下每个请求都要先等满再读缓存，比 cache-first 慢一个数量级；ignoreSearch: true 会把分页、筛选参数不同的请求当同一条目，列表类接口要慎用。回落到缓存的请求事后要补传，但 sync 事件与 Periodic Background Sync 目前主要只在 Chromium 系可用，Safari 与 Firefox 不支持，只能当渐进增强，主路径仍得在页面可见时自己重试。

stale-while-revalidate：返回旧的，后台换新的

首字节永远最快，网络只在后台把桶刷新。它害你的地方是“永远差一拍”：资源已经下线，桶里那份还会被无限次返回，用户看到的是最后一次成功版本，只有整桶被清才结束；它也不能用在写请求或有幂等语义的接口上。更隐蔽的是页面无法知道内容有多旧，所以返回旧内容时必须带上 sw-resp-at 这样的时间戳头，让上层判断是否可接受——至于陈旧到什么程度该拒绝、离线写队列与冲突怎么合，那是《PWA 离线能力实践》已经展开的设计层，本文只补缓存代码。

导航请求与离线回退

导航请求要单独分支，因为它的失败不是“某个资源没了”而是“整个页面打不开”。回退链我固定三级：真实文档、可渲染的外壳、离线提示页。

flowchart TD
  A[导航请求] --> B{网络可用}
  B -- 是 --> C[返回真实文档并顺手刷新外壳]
  B -- 否 --> D{缓存里有同路径文档}
  D -- 是 --> E[返回该文档]
  D -- 否 --> F{有外壳}
  F -- 是 --> G[返回外壳并带上原始路径]
  F -- 否 --> H[返回离线页或 503]

返回外壳不等于页面能正常显示。SPA 拿到的是空壳，路由要靠 sw-original-path 或者信任 location.pathname 解析；数据层必须只吃本地副本：详情 ID 在 IndexedDB 里有副本就渲染副本，没有就渲染“离线不可用”的占位卡片，而不是让整页停在骨架屏。代价要说清楚——离线回落时 title、meta 与首屏数据都不可靠，分享卡片和 SEO 都会退化，这是能力边界。

Workbox 把这条链拆成两块配置：NavigationRoute 用预缓存好的 URL 当外壳并配合白名单，setCatchHandler 兜住所有回落失败的导航请求，NetworkOnly 与 NetworkFirst 还支持 fallbacks 直接给候选 URL 列表；手写的好处是判定顺序完全可见、不引入构建期插件，适合回退逻辑要和自家路由深度耦合的场景。

与 HTTP 缓存的关系

Service Worker 不是浏览器缓存的替代品。CacheStorage 是显式 API，写什么、留多久、什么时候清全是你自己的代码；HTTP 缓存由响应头驱动，Cache-Control 与 ETag 照常工作。新加的一层坐在 HTTP 缓存前面：策略未命中而调用 fetch() 时，网络那一段仍然会用 disk 或 memory 缓存、仍然会发 304 协商。理解这点才明白，“请求变少了”与“缓存被管好了”是两件不同的事。

“用户看到旧内容”是双缓存叠加后的典型症状，排查顺序必须是先确认命中的是哪一层：

  1. 看 Network 面板的 Size 列。标了 (from ServiceWorker) 说明请求被 worker 用自己的缓存解决了，问题在桶与 key；没有这个标记而请求真到了网络，才轮到看 HTTP 缓存。
  2. SW 命中时，去 Application 面板的 Cache Storage 里核对桶名与条目 key，重点看 key 里 query 的顺序和尾斜杠——绝大多数“改了不生效”其实是命中了另一个形态的旧条目。
  3. 走到网络时，区分 200 与 304、读 Cache-Control 的 max-age，确认入口 HTML 没被长时间缓存；指纹资源可以长缓存。
  4. 三层都排除了，再看 Service Workers 面板里 worker 的状态。旧 worker 还在跑旧的 fetch 逻辑时，你改的一切策略都不生效。

清理也要两层一起：强制刷新不会清空 CacheStorage，也不会等 worker 停用完成。可靠做法是 Unregister 后勾选 Clear site data，再开一次新导航；线上急救用下一节的 passthrough 显式关掉缓存层，而不是指望用户手动清数据。

调试与灰度

DevTools 的三个开关各会误导一件事，用错比不用更糟。

  • Offline：断网后已命中 Cache 的请求照常成功，容易让你把“页面正常”当成“策略正确”，其实网络分支一次都没走到；同时 sw.js 也拉不到新版本，你以为在测离线，实际在测旧 worker。
  • Bypass：请求绕过 respondWith 直连网络与 HTTP 缓存，但 install 与 activate 照常发生。挂着它验证 cache-first，你会得出“策略没生效”的错误结论；忘记关掉是本地复现不了线上问题的头号来源。
  • update on reload：每次刷新都重拉脚本并立即接管。它最危险，因为“真实用户不会主动刷新”被从视野里删掉了：本地永远最新版，waiting 与更新提示链路触发不了，线上旧 worker 却可能驻留好几天。

这三项默认全关，验证时一次只开一项，并把“新开标签页做第二次导航”固定成验收动作。

旧 worker 卡住是高频事故，多数卡在 waiting：新 worker 已经 installed，但旧页面还占着控制权。按顺序救，别一上来就反注册：

灰度按 URL 分桶：开关放在服务端渲染的入口 HTML 里，命中桶的用户才注册，预缓存前缀带上桶号就能分桶观察命中率。回退路径要提前定：停投时把 sw.js 换成一个 passthrough worker——不预缓存、fetch 里一律不 respondWith，activate 里清掉自家桶并 claim()。它比 unregister() 好用，因为反注册要等下一次导航才生效，也覆盖不了已装好 worker 的用户，而 passthrough 是一次正常更新，走你验证过的链路。

上线纪律

三条硬要求。更新必须能停投：sw.js 不参与任何缓存策略，它由浏览器按自身的更新检查规则拉取，所以停投只需替换脚本内容，别把它列进预缓存清单，也别用 HTTP 头去调它；passthrough 脚本要随包发布并预先验证过。缓存必须能清理：所有桶名带统一前缀，caches.keys() 的结果能与远端配置比对，把不该留的桶一次删空，且清理动作要能被上面那个 SKIP_WAITING 通道远程触发。失败必须能上报：worker 里抛出的异常不会被页面错误监控捕获，必须在 sw.js 内部把注册失败、预缓存缺项、策略异常、回退命中这四类事件发到采集端点并带上桶名与构建号，否则线上问题只存在于用户口述里；采集与采样口径归同批的监控篇，此处不展开。

症状 可能命中的层 处理动作
首访空白，第二次打开才有内容 生效时机，controller 仍为空 用新导航验收，或加 controllerchange 刷新提示
改了样式，用户仍是旧包 SW cache-first 命中旧桶条目 确认资源带指纹，检查 activate 是否删掉旧桶
接口偶发返回几天前数据 network-first 超时或回退分支 复核超时阈值，慎用 ignoreSearch
深层路由离线白屏 回退链缺外壳或缺离线页 补齐并预缓存 /app-shell.html 与 /offline.html
强制刷新也无效 HTTP 缓存与 SW 双层同时命中 Unregister 加 Clear site data 后重新导航
本地正常，线上异常 update on reload 掩盖了 waiting 关闭该开关复现，检查 worker 状态
大面积报错需要止血 旧 worker 仍在接管请求 下发 passthrough 并远程触发清桶

小结

Service Worker 的可靠性来自几条朴素纪律：注册后以 controller 判断是否真的接管；install 只管下载落桶，activate 只管清桶与接管，fetch 只管同源；桶名按构建号，清理按整桶删除；cache-first 只给指纹资源，接口用带 AbortController 超时的 network-first，静态内容用 stale-while-revalidate 并自带时间戳头；导航请求必须有文档、外壳、离线页三级回落。上线前确认能停投、能清桶、能上报这三件事都有代码。把调试开关关好、用第二次导航做验收，缓存问题就会从玄学变成可复现的分支判断。
