PWA 渐进式 Web 应用实践

本文把 PWA 拆成三件可各自验收的事——可安装、可离线、可推送，重点是把它做成一款可发布的产品形态，覆盖 manifest 字段、安装条件、平台差异、更新与通知边界、配额现实与发布验收清单。适合站点已跑起来、评估要不要走 PWA 路线的前端与产品读者。读完能得到一份在 iOS/Android/桌面上能逐条打勾的发布清单；离线能力详细设计不在本文。

PWA 的三件事各自解决什么

“是不是 PWA” 这个问句在产品讨论里几乎没有信息量——装了 manifest 但没写 Service Worker、写了 Service Worker 但没做推送的站点，算不算？答案取决于对方手里那张清单。本文把这条争论拆成三件具体的事：可安装、可离线、可推送，分别讲它们解决什么、边界在哪里、2024 年在移动与桌面上如何落地。

可安装解决的是”入口”问题。用户不必每次在地址栏搜索、不必在标签页里被工具栏干扰。它只需要 manifest 加浏览器的安装条件判断，不需要 Service Worker 也能触发——这一点常被误解为”没 SW 就不能装”。可安装不等于值得装，收益在哪里见第三节。

可离线解决”网络抖动下的可用性”，由 Service Worker 与缓存策略承担。本文只把它当安装与发布的前置依赖：装了 Service Worker 才进入部分浏览器的安装条件、才有版本更新可以谈、才有推送的接收端。三层验收、陈旧度预算与 outbox 在《PWA 离线能力实践》已经展开；缓存策略实现代码留给《Service Worker 离线缓存实战》，本文不重复。

可推送解决”冷启动召回”：把用户从通知直接送回某条深链。它受平台约束最强——iOS 需要较新版本且必须安装到主屏幕才具备接收条件，普通浏览器标签页里做不到；Android 与桌面 Chrome/Edge/Firefox 各家条件不同。推送不是普适手段。

历史上的 Application Cache 早已废弃并从浏览器移除，本文只在对照里提一次，不要按它还活着做设计。

manifest 逐段讲

manifest 不是”配齐字段就会弹安装提示”，它是浏览器判断的输入，也是产品形态的声明。下面挑真正影响发布决策的字段。

display 决定窗口形态

display 是产品形态开关。standalone 让页面在独立窗口里打开、不显示浏览器工具栏；minimal-ui 保留极简控件；fullscreen 主要给媒体或游戏；缺省 browser 表示安装前后都留在标签页。选 standalone 就要为”没有后退键”负责——顶部要自己提供返回上一级与”回到首页”的入口，深链落点要有兜底。

start_url 与 scope 的关系

start_url 是冷启动落点，scope 是”在这个范围内不算离开应用”。两者要写成子集关系，start_url 不在 scope 之内会被浏览器拒绝安装：

start_url 上拼的 source=pwa 会保留到冷启动与推送落地页判断里，方便把安装入口的转化拆开统计；它同时写入历史记录，后退一步还是同一个 URL。

图标与主题色

图标至少一张 192、一张 512；512 建议同时给 maskable 版本，Android 自适应图标会做安全区裁剪，没做 maskable 的位图在圆/方蒙版下会被切掉边缘。theme_color 决定状态栏与顶栏染色，background_color 只在启动画面用一次——两色先在视觉稿里定下来再写进 manifest，不要反过来。

shortcuts 与 share_target 只作可选说明

shortcuts 是桌面长按或右键图标时弹出的快捷入口；share_target 让系统”分享”面板把内容送到本站某条 URL。两者技术上都能用，但价值取决于用户是否真的走这条路，上线时先做能验证的子集。

安装条件在不同浏览器上的差异

Android 侧 Chrome/Edge 在满足”manifest 关键字段 + 可用图标 + Service Worker + 一定的用户参与度”之后触发 beforeinstallprompt，前端可自绘安装按钮、监听事件、调用 prompt()。iOS 的 Safari 没有这个事件——只在”分享 → 添加到主屏幕”里提供入口，不主动提示、也不自动安装。”能不能显示安装提示”要在两个平台上分开问、分开答；”一键安装到桌面”这种文案在 iOS 上不成立，属于平台差异。

安装之后的行为变化

安装本身不带来收益，收益来自装完之后被改变的行为。设计期至少吃下三处变化。

独立窗口。standalone 下页面在独立应用窗口里运行，不再共享标签页会话，window.opener 与”新标签页打开”的直觉要重新设计。跳外站切回浏览器，Android 给出”正在离开应用”的提示；window.close 不一定生效，要在 scope 内留”回到首页”的入口。

生命周期。独立窗口切到后台或被最小化时，页面被冻结的概率高于标签页。长任务、音频、计时器都要按 Page Lifecycle 处理，不要假定 visibilitychange 时机与标签页一致。iOS 上主屏安装过的站点在后台被杀更激进，内存压力回来时不给优雅关机的机会。

深链与应用切换器。安装后 start_url 上的查询参数、scope 内的路径会被切换器与”最近使用”记住；推送与外链落到 scope 内是”回到应用”，落到 scope 外是”跳到浏览器”。分界要在验收里单独跑一次。

一句话：“安装”解决的是入口成本，不是收益。留存、召回、离线可用才是收益，一个桌面图标不会让任何一个指标自然上涨——把”装完数据就涨”当默认预期是最常见的错觉。

更新策略的两种产品形态

Service Worker 让”何时更新”变成产品决策，而不是部署副作用。两种形态各有代价：

默认静默更新。新版本 Service Worker 安装完成后立即进入 activate。配合 skipWaiting 与 clientsClaim，新 SW 接管尚未刷新但仍在线的旧客户端——对刚打开的读多写少页面安全，对表单未提交、长会话或 outbox 还在写会撕碎状态。适合内容型站点。

发现新版本请刷新。不主动 skipWaiting，waiting 阶段通过 postMessage 通知页面，UI 弹一条”发现新版本，点击刷新”的提示，把时机交还用户。适合工具型、写多、长会话、有离线队列的产品。实现细节——waiting 消息、按钮触发 controllerchange 后 reload 的写法——留给《Service Worker 离线缓存实战》，本文不写策略代码。

UI 两点要把握：提示放在不打断输入的位置；刷新前对未提交内容做暂存，否则”点击刷新”本身就是一次事故。也可以把切换按钮做成”稍后提醒”，一次部署不强推用户。

flowchart TD
  A[新版本 SW install] --> B{策略}
  B -->|静默| C[skipWaiting + clientsClaim]
  B -->|交还用户| D[等待 controllerchange]
  C --> E[旧客户端被接管]
  D --> F[UI 提示 点击刷新]
  F --> E

通知与推送的现实边界

推送是最容易被过度承诺的能力。真正值得用的场景只有三类：订单与交易状态（发货、退款、支付回执）、协作与消息（评论、@、指派）、用户主动订阅的提醒（日程、抢票、降价）。除此之外，营销推送授权率与点击率都很低、卸载成本很高——示意值层面常见授权率不到三成、七日点击率个位数；具体数字看自家数据，不要照搬别人家的。

iOS 的约束必须写清。Web Push 在 iOS 上需要 16.4/17.4 之后的版本、且必须”添加到主屏幕”安装之后才具备接收条件——普通 Safari 标签页里不存在这条路径。Android 与桌面 Chrome/Edge 走 Notification.requestPermission() 与 push manager；Firefox 桌面支持、Android Firefox 支持有限。不能把”我们能推送”当普适手段，产品上要接受”推送只对一部分安装用户有效”，把这条现实写进指标口径与召回预算。

打扰成本。授权之后不代表用户希望被推。通知要分级：交易与协作即时推送，其余默认合并或每日一次；每条通知能在应用内单独关掉，不要埋在设置里四层深。iOS 上主屏安装的通知入口在系统设置里，应用内要教用户去哪里找。

通知点击的落地页与深链。通知 data 字段里带一个 scope 内的相对路径，Service Worker 在 notificationclick 里打开对应窗口。冷启动落点要与 start_url 查询参数一起考虑，否则用户从通知进来却回不到自己会话。验收时把”通知点击 → 落到具体订单/评论/日程”跑一次，比”能不能收到通知”更有意义。

存储与配额：把”数据可能整份消失”当成默认前提

navigator.storage.estimate() 返回 usage 与 quota，看上去精确，实际是浏览器基于全局磁盘压力给出的粗略估算：同一台机器不同时间测出的 quota 可能大幅波动，同一份缓存写入前后 usage 也会跳。适合做诊断日志，不适合做”还剩多少所以再存一点”这类判断。

想稳一点可以调 navigator.storage.persist() 申请持久化授权，但是否给、给多大完全由浏览器策略决定：Chrome 系在用户参与度或站点被”以应用形式使用”时可能自动给，Safari/Firefox 策略不同，不给是常态。不要假定申请一定拿到，也不要拿到后写死更大的缓存预算。

现实是三条每天都在发生的路径：用户清站点数据、系统磁盘压力驱逐缓存、iOS 长期不用把主屏站点当普通网页重新处理——三条都会让 IndexedDB、Cache Storage、Service Worker 注册一起消失。所以离线数据必须设计成”可整份消失”：未提交草稿要本地文件与后端双写；关键设置在服务端要有一份可回放；缓存里只放能重建的东西。配额不足时降级到”骨架 + 首屏关键资源”是可接受策略，硬撑到被驱逐才是事故。

发布验收清单

验收条件必须可判定，不要写”体验良好”。下面每一条都能在真机或干净环境跑出一个通过/失败：

  1. 可安装路径：Android Chrome/Edge 走 beforeinstallprompt → 安装 → 冷启动落点 = start_url 加 source=pwa；iOS Safari 走”分享 → 添加到主屏幕” → 冷启动进入 standalone；桌面 Chrome/Edge 地址栏出现安装图标。三条路径各跑一次。
  2. 无网络首屏：飞行模式下再次打开应用能进入首屏骨架与静态资源；关键路由显示”离线状态”，不出现白屏。
  3. 更新提示：以”交还用户”策略发一次新版本，UI 出现”发现新版本”；不点击时旧客户端行为不变，点击后刷新到新版本，未提交内容仍在。
  4. 通知开关：交易、协作、营销三类通知能分别关闭；系统层关闭后应用内显示对应状态，不再弹。
  5. 配额不足降级：手工把缓存撑大或模拟低磁盘，观察降级路径是”骨架 + 首屏关键资源”，不出现写入失败导致的路由白屏。
  6. iOS/Android/桌面各过一遍第 1、2、3 项：三项在每个平台上都有独立行为，不接受”Android 跑通就算通过”。
  7. scope 内/外跳转：scope 内链接留在应用；scope 外链接明确切回浏览器并可返回。
  8. 返回入口：standalone 下每个页面都能通过 UI 回到首页；深链落点在无会话时有兜底。
  9. 清除站点数据后重开：手工清除后再次进入不出现无法启动的死循环；未提交草稿按上节所述有双写来源。
  10. manifest 校验：devtools 的 Manifest 面板检查图标尺寸、maskable、theme_color 与 background_color 与视觉稿一致。

任何一条不通过都不算发布完成。示意值层面一次发布至少留一天做真机回归，窗口按团队实际调整。

小结

PWA 不是一句”是不是”，而是三件可各自验收的事：可安装解决入口、可离线解决抖动、可推送解决召回；三件事各有边界，边界由平台决定，不由产品愿景决定。manifest 与安装条件要按 Android/iOS/桌面分开谈；更新时机是产品决策，静默与”点击刷新”各有代价；推送不是普适手段，iOS 约束要写清；存储与配额是粗略估算，离线数据必须按”可整份消失”设计。把上节清单一条条跑通，才谈得上把 PWA 做成可发布的产品形态——离线能力验收看《PWA 离线能力实践》，缓存策略代码看《Service Worker 离线缓存实战》。
