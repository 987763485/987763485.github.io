SSR 与边缘渲染实践

这篇文章讨论的不是”用哪个框架”，而是”渲染这件事发生在哪一台机器上”。同一个页面，渲染放在浏览器里、放在机房里的 Node 服务上、放在离用户更近的边缘运行时里、或者干脆放在构建期做完，四者的成本结构、失败模式和补救手段完全不同。适合用过 SSR 却说不清”慢在哪一段”的同学，读完应能回答三个问题：首屏的三段时间各被什么吃掉、哪些代码搬不到边缘、一次未命中的边缘请求最终把压力转嫁给谁。框架内的模式选型与部署运维不在本文范围。

渲染位置谱系：谁在为什么付钱

一段网页从字节变成可交互的界面，中间要发生四件事：取到渲染所需的数据、把数据变成 HTML 字符串、把 HTML 送到用户、把事件与状态接回已有 DOM。这四件事可以在四个不同位置上完成，而位置一旦选定，延迟和成本的分布就基本固定了，后面的工程手段只是在同一条曲线上挪动。

先看四个位置分别把代价放在哪里。纯客户端渲染把取数和拼装都交给浏览器：服务端只需要吐一份体积很小但内容为空的 HTML，第一段响应几乎只受网络往返和静态文件服务支配，源站压力最低；代价是首屏可见时间被 JavaScript 下载、执行和一轮轮数据请求推后，内容可见性还得看爬虫是否执行脚本。源站 SSR 把取数和拼装集中到自己的机房：HTML 到达时内容已经完整，爬虫和低速设备都受益；代价是”每个请求都要跑一遍渲染函数”必须由一台有状态、要扩缩容、要缓存的长驻服务承担，而且源站通常只在少数几个地域，网络距离本身成了新的延迟项。边缘渲染把渲染函数搬到全球多个节点，把网络距离压回去；代价是执行环境从一台随时可扩容的 Linux 机器换成了一套受限沙箱，能用什么 API、能跑多久、能连谁都被平台写死。构建期静态（SSG 与带再渲染语义的 ISR，本文只作定位）把代价推到构建阶段和新鲜度上：分发几乎免费，但要用明确的过期策略换实时性。

选型上我倾向用一个粗暴但好用的判据：内容是否需要知道”你是谁”，以及多久变一次。不需要身份、变化不快，就往构建期和边缘缓存推；需要身份，就把静态外壳留在边缘、个性化交给客户端；两者都不满足，才做源站 SSR，并配好缓存与降级。

首屏到底在等什么

把”首屏慢”当成一个整体来优化几乎一定失败，因为从输入 URL 到能点按钮，中间是三段时间的接力，而 SSR 与边缘渲染对这三段的影响方向并不一致。

第一段是 TTFB，即请求发出到收到第一个字节，由网络往返、连接建立、服务端排队与响应开始之前的一切同步工作构成。这一段是纯粹的服务端账：源站 SSR 把取数和拼装放在这里，边缘渲染把渲染函数放在离用户更近的地方，两者都在压缩它。第二段是 HTML 到达，也就是文档剩余字节传完、解析器把工作交给脚本的时刻，它由 HTML 体积与带宽决定，与水合无关。第三段是水合完成，浏览器要下载并执行框架运行时与页面组件，在已有 DOM 上重建组件树、绑定事件、把服务端状态灌进客户端 store，直到交互真正可用。

关键结论是：SSR 降低第一段，却很可能抬高第三段。服务端为了”内容可见”已经把组件树渲染了一遍，客户端为了接管交互还要再构建一遍，代码体积和依赖都没少，只是多了一轮与 DOM 的协调。数据量大的页面还会把序列化后的状态内联进 HTML，这段 JSON 直接挤进第二段让文档更肥，而水合期间的长任务则把”看起来早就好了、点下去没反应”的观感集中引爆。边缘渲染也没有魔法：它缩短的只是第一段里的网络分量，渲染若要等一个跨地域的私有数据库，边缘只是把等待换了地点。

因此打点要按段拆开：至少把首字节时刻、文档 DOMContentLoaded 时刻和自己埋的”根组件已接管交互”时刻放到同一条时间轴上。看到三段的比例，才知道”首屏慢”该找边缘、找体积还是找主线程。至于预算制度本身怎么定，前端性能预算实践一文已经讲过，本文不重复。

源站 SSR 的真实工程负担

源站 SSR 的难点不是”能不能把组件渲染成字符串”——React 18 的 renderToString 与 renderToPipeableStream、Vue 3.4 的服务端渲染器都已经足够稳，传统 Node SSR 的最小实现我在更早那篇 React 服务端渲染初探里写过。难点在于：渲染一旦进入请求路径，这台机器就变成了在线系统，要有超时、降级和缓存，还要回答”挂了怎么办”。

第一层负担是内存与并发。渲染是 CPU 密集的同步工作：构造组件树、执行生命周期、拼接字符串，全跑在事件循环上，单进程的并发约等于”一次只能认真渲染一个页面”，其余请求只能排队。于是 QPS 上去之后最先恶化的指标恰恰是我们想改善的 TTFB——用户等的是排队而不是渲染。每请求临时对象、模块级缓存状态、误挂在 globalThis 上的请求上下文都会推高常驻内存，接近上限时垃圾回收的停顿进一步放大延迟，形成典型的”越忙越慢”。扩容能解决吞吐，解决不了单请求时长和状态共享的正确性。

第二层是超时与降级，这是最容易被跳过的一环。必须给渲染路径设一个每请求时间预算，超了就放弃完整渲染，改发一个仍然可用的响应：旧缓存 HTML、只含外壳的骨架、或者直接退回纯客户端渲染。三者都比”等到用户关掉页面”好。

第三层是缓存一致性。源站 SSR 通常有两级缓存：整页 HTML 缓存和依赖数据缓存，失效顺序必须固定——先失效依赖、再失效 HTML，否则会出现”新数据配旧 HTML”，或更糟的”旧数据配新 HTML 又被缓存住”。

第四层是对下游的放大，这是最昂贵的一课。”每个请求跑一次渲染”意味着页面里有多少次取数，数据库就承受多少倍于静态站点的压力：一个首屏串行发起八个查询、还带 N+1 的页面，在五千 QPS 下就是四万次查询每秒，而其中绝大部分在算同一件事。缓解手段按性价比排序：串行取数改并行或批量合并、给渲染路径加短 TTL 缓存、给慢查询设熔断并在超时时走降级而不是走等待。要不要上源站 SSR，最实用的判据是”能不能给出这一页在峰值 QPS 下的每请求查询次数”。

边缘运行时的能力与限制

边缘渲染的吸引力来自距离：把渲染函数部署到靠近用户的节点，用短往返替代跨洲际往返。要理解限制，得先理解执行模型。主流边缘平台跑的是 V8 隔离而不是容器或虚拟机：一个底层进程同时承载大量互相隔离的执行上下文。这带来两个直接后果。其一，冷启动的语义变了——没有虚拟机启动和进程 fork，但模块实例化、顶层代码求值和闭包构建仍是真实开销，一个上下文刚被回收，下一个请求就要重付这笔账，量级通常在几十到上百毫秒（示意值，各平台差异极大，不要照抄博客里的数字）。其二，进程内缓存不可靠——全局对象上的 Map 不保证跨请求、跨上下文命中，把它当分布式缓存用一定会出错，真正可依赖的是平台提供的键值或对象存储。至于容量，隔离上下文数量受宿主资源约束，峰值时新上下文要现建，冷启动比例会随流量上升。

什么代码能跑到边缘

我用的判据只有一条：只依赖 Web 标准 API 的纯计算，加上边缘可访问的数据源。前半句是能力问题，后半句是网络拓扑问题，很多人只检查前半句，结果代码在边缘跑起来了、却在每次取数时超时。

常见失败清单值得背下来。Buffer 不是全局对象，除非平台提供 polyfill，要改成 Uint8Array 加 TextEncoder 与 TextDecoder；fs、child_process、net、dns、worker_threads 一律不可用；node: 前缀的说明符即使有实现也不保证同名；原生 addon 与需要 node-gyp 编译的依赖进不去，纯 JavaScript 或 WebAssembly 实现才有资格；process.env 通常只保证模块顶层被静态读取的键有值，运行时动态下标可能拿到 undefined，正确写法是在模块作用域一次性解构并在构建期内联。

还有一类更麻烦的失败：依赖内部做运行时探测，探测不到 Node 就抛错，这类问题在构建期常常只是一条警告，所以值得把”边缘入口能否导入每个页面模块”做成构建期冒烟检查。

框架里哪些代码天然满足这个判据，Next.js 的 App Router 与 runtime 边界在 Next.js 全栈框架实战一文里已经讲清，本文不重讲框架 API；框架内 SSR、SSG 与 ISR 该怎么选，见下一篇专门讲渲染模式选型的文章；而怎么把边缘函数部署上线、灰度与回滚，属于 Next.js 全栈部署实践的范围。

数据获取的分层与缓存键

确定渲染位置之后，下一个决定是”在哪一层取哪一份数据”。我建议把首屏数据按”是否与身份相关”切成两堆：匿名可缓存的公共数据，以及只有登录用户才有的个性化数据。前者进边缘，后者干脆不进渲染路径——边缘只输出含占位符的外壳，个性化由客户端补齐。这不是偷懒，而是把不可缓存的东西移出缓存路径的唯一干净做法，它的实质就是 stale-while-revalidate 的精神：先返回一份略旧但完整可用的公共内容，再由后台或客户端补上新数据。

难点集中在缓存键。键里只要含 cookie、Authorization 头或任何用户标识，缓存就退化成”每用户一份”，命中率断崖式下跌，等于花了边缘的成本却什么都没缓存住。正确做法是把身份信息排除在键外并显式降级：命中公共缓存时返回匿名外壳，个性化由客户端补；确实要按身份区分时，宁可放弃边缘缓存回源。

另一条常被误用的捷径是”边缘直连主库”，我认为它几乎总是错的，原因不是安全而是物理：边缘到源站数据库要跨地域，往返常常比查询本身高一个数量级；数据库要为每个边缘节点维持一批连接，而边缘的连接并发本来就受限；最要命的是主库失去了”请求只从少数几个源站来”这个拓扑前提，一次缓存失效就变成全球数百个节点同时回源。真要边缘取数，应该走一层可缓存的 HTTP 接口或平台自带的边缘可读存储。

流式与分块：外壳先到、慢模块后补

分块传输让”等待”可以被重新安排。服务端不再攒齐整个 HTML 才响应，而是一段段地推：先发送头部、关键样式和首屏外壳，慢模块的数据到齐后再追加。浏览器在第一段到达时就能开始解析和绘制，用户看到的不再是白屏而是一个逐步长出来的页面。React 18 的 renderToPipeableStream 把这套语义做成了显式阶段：外壳就绪时通过 onShellReady 开始响应，被 Suspense 边界包裹的慢内容在数据到齐后作为替换片段流出；Vue 3.4 与 3.5 的服务端渲染在这个年代仍是一次性整树输出，要分块得靠手工拼接。

好处要说准，坏处也要说准。好处是 TTFB 和首次绘制都提前了，用户在等待期间获得视觉反馈。坏处有三。第一，如果最大内容元素恰好落在被推迟的慢模块里，真正的首屏指标可能反而变差——外壳来得快但主体来得晚，指标不会替用户撒谎。第二，分块输出的 HTML 在任意时刻都是不完整的文档，而水合要求服务端 DOM 与客户端组件树一致，因此每个片段必须自带边界标识和替换协议。第三，对爬虫是真实风险：搜索引擎的渲染通常发生在抓取之后的队列里，但抓取时看到的内容仍然算数，title、规范链接、结构化数据和主导航必须出现在外壳里。我的实践边界是：延迟块只放推荐位、评论和个性化模块，正文与导航永远在外壳里。

缓存与失效：三层各自的抓手

边缘渲染的成败最终由命中率决定，而命中率横跨三层，每层的控制手段和生命周期都不同。

第一层是浏览器缓存，由响应头支配，作用域只有当前用户，省得下二次访问、省不下首访。动态 HTML 在这里寿命很短，真正长寿的是带内容哈希的资源，用 public, max-age=31536000, immutable 让浏览器一年不再问。第二层是 CDN 与边缘缓存，它的键决定命中率上限，失效必须能按 URL 之外的维度做，否则改一条文案就要等 TTL 过期。第三层是应用内缓存，也就是渲染函数自己的数据缓存，它能被业务语义精确控制，也最容易写脏。

失效的通用武器只有 TTL。tag 失效——“把打了 product:42 标签的页面一次清掉”——依赖平台是否提供接口，不是 HTTP 标准能力，不要在架构里假设它普遍存在；用了它就要接受与平台绑定，并留一条 TTL 兜底路径，防止失效接口失败时内容永久停在旧版本。

个性化与命中率的冲突无法两全，只能靠切分缓解：可缓存外壳加不可缓存尾部是标准解法，代价是首屏必须留一块”待填充”区域，而且布局要提前占好，否则内容补上时的位移会同时伤害体验与布局稳定性。

两个失败模式要有成文的防护。一是穿透：不存在的资源被大量请求，每次都绕过缓存打到渲染路径，做法是让缓存层存住 404 与空结果，并对同一键的并发回源做单飞。二是惊群：热点内容 TTL 到期的瞬间成批请求同时重渲染，做法是让它们复用同一次渲染，或用随机抖动把过期时间打散。

SEO 与可访问性：SSR 换来什么、又要小心的坑

先说清收益的形状。SSR 或边缘渲染让内容在文档到达时就已存在于 DOM 里，爬虫即使不执行脚本也能读到文本、拿到链接。对内容型站点，这既是收录保险，也是内链被发现速度的保障——只在客户端渲染后才出现的列表项，它的链接在抓取时并不存在。CSR 并非一定不被收录，但爬虫执行脚本要排队、要开销、结果不保证；把确定性拿到自己手里，才是做 SSR 的正当理由。

代价藏在两个坑里。第一个是重复内容与闪烁：关键 CSS 没在头部就绪时，浏览器会先画一版无样式文本再重画；更常见的是服务端渲染默认状态、客户端 store 灌入真实状态后立刻覆盖，用户看到内容跳一下。根治办法是让服务端渲染的状态与客户端首次读取的状态严格一致，并把它内联成唯一来源。第二个是 hydration mismatch：服务端只要用了当前时间、随机数或依赖语言头的判断，两端就会算出不同结果，React 的恢复策略会重渲染整棵子树，把 SSR 的收益原地销毁。

meta 与结构化数据的落位只有一条原则：必须出现在外壳的首块里，且只出现一次。title、meta name="description"、link rel="canonical"、Open Graph 与 Twitter 卡片标签都要在 head 内完成，因为爬虫和社交抓取器读 head 时不会等你后续分块；JSON-LD 也要在一次输出里给全，半截的脚本块比没有更糟。一条诚实边界：不要为了爬虫而放隐藏文本，也不要按 user agent 输出显著不同的内容。

可访问性常被漏掉，但它对水合特别敏感。三条实操：占位区域要有明确的忙碌语义（例如容器上标注 aria-busy 并在补齐后去掉）；水合不要重排 DOM 顺序，两端必须产出同一棵树，否则屏幕阅读器的焦点会莫名跳跃；水合失败时页面仍应可读，只要别把关键交互做成”不水合就完全不可用”。

成本模型与可观测性

成本上，边缘和源站是两种不同的账。源站按实例付费：容量必须按峰值预留，闲时也烧钱，好处是重计算和长连接都在预算内。边缘按调用付费：账单由请求数与每次调用的执行时间相加，闲时几乎为零，坏处是每次调用的 CPU 时间既是账单单位又是硬上限，而且对命中率极度敏感——命中时你付的是一个静态文件的钱，未命中时付的是一次完整渲染的钱。

于是分水岭其实是命中率与流量形态。低频但地理分散的站点（海外用户为主、企业官网、长尾内容页）在边缘获益最直接，它同时省下源站预留和往返延迟。每次响应都依赖身份或私有数据的高吞吐站点不适合边缘：缓存留不住，等于用更高单价买同样的工作，还不如让源站的进程内缓存摊薄。重计算的页面也不适合，执行时间既是钱又是超时风险。最麻烦的是”两边都养着”——上了边缘却给源站缩不了容，既付按请求的账单又付按实例的账单。

失败模式里最贵的是回源放大：边缘未命中时请求要跨地域回源，一次全球范围的热 key 同时过期就可能把源站队列打满，而源站的预留本来就是按”边缘挡住大部分流量”设计的。应对是过期时间加抖动、回源做单飞、给回源路径设并发上限并在超时时返回旧内容。其次是雪崩：数据源抖动推高失败率，失败响应无法被缓存，全部落到重试上形成正反馈——所以让短 TTL 的错误响应也被缓存一会儿，比失败就永远穿透安全。

可观测性必须按渲染位置分段。核心是每条响应都带上”这份 HTML 从哪来”的标记，并在浏览器侧把三段时间一起上报。

示例字段 含义 用途
render_layer edge 或 origin 或 build 分层看延迟与错误率
cache_state hit 或 miss 或 stale 或 bypass 命中率与回源放大的分子
render_ms 渲染函数自身耗时 与总耗时相减即排队与网络
fetch_count 本请求发起的取数次数 下游放大的直接指标
deadline_hit 是否触达渲染超时预算 降级率，最该告警的一项

采集口径要注意三件事。第一，边缘命中率以边缘日志为准而不是 CDN 面板，两者对”命中”的定义经常不一致。第二，源站要分开统计”来自边缘的回源”和”直达源站”的请求，否则回源放大看不出来。第三，浏览器侧上报的三段时间要带渲染位置标记，才能回答”同一个页面，命中与未命中差多少”。告警只盯两个比例：触达预算的降级占比，和命中率的绝对下跌。

需求、渲染位置与代价：一张选型表

把前面的判断收敛成一张能贴进评审文档的表，它的作用是把代价显式化，避免”别人都用边缘所以我们也用”。

需求形态 建议渲染位置 要付的代价
全站公开、更新以天为单位 构建期静态进 CDN 实时性最差，改动要等重建或过期
公开但更新频繁 边缘渲染加短 TTL 公共缓存 成本随命中率波动，要防惊群与穿透
首屏公开、登录后才个性化 边缘出外壳，客户端补个性化 需要预留占位，接受位移与二次请求
每请求都依赖私有数据 源站 SSR 要为峰值预留容量并配齐超时降级
重计算或依赖原生库、文件系统 源站 SSR，或构建期预生成 渲染时长直接进入 TTFB
用户地域分散、源站只在单一地域 外壳与静态部分搬边缘 私有数据仍要回源，收益被抵消
内部系统、用户集中、并发可控 源站 SSR 甚至纯客户端 上边缘换不来延迟收益只添复杂度
强依赖收录、内容又高度动态 SSR 且正文永远在外壳 延迟块只能放非正文模块

读表方式是横向而不是纵向：先确认内容是否需要身份、多久变一次、渲染要吃多少 CPU、依赖能不能进边缘，四个答案就能把行缩小到一到两行。任何一行都要连同代价一起汇报给业务方——构建期用新鲜度换吞吐，边缘用平台绑定换距离，源站用预留容量换自由度。

小结

本文的核心判断是：渲染位置决定延迟与成本的形状，框架只是在这个形状上做优化。首屏要拆成 TTFB、HTML 到达与水合完成三段时间分别归因，SSR 压第一段而可能抬第三段。源站 SSR 的负担是内存与并发、超时与降级、两级缓存一致性、以及对下游数据库的放大，缺一项都不算上线完成。边缘的判据是”只依赖 Web API 的纯计算加边缘可访问的数据源”，个性化留给客户端，主库永远不要直连边缘。流式能改善观感，但 head 里的元信息与正文必须在首块给全。最后，命中率同时决定成本与账单，按渲染位置分段打点、盯住降级率与命中率，比任何单次调优都可靠。
