Claude API 与工具调用实践

本文属于《Agent 智能体开发》第 6/55 篇
上一篇系列目录下一篇

本文面向准备把大模型接口接入生产系统的工程师，梳理 Claude 这套消息式 API 在写作时的使用形态：请求结构、返回长度控制、鉴权与密钥管理、错误重试、流式消费，以及工具调用如何落进一个可控的客户端循环。Claude API 于 2023 年 3 月对外提供，工具调用则随 Claude 2.1 在 2023 年 11 月以较新的能力形态接入。文中的端点、字段名与取值沿用当时的公开形态，落地前请以官方文档核对。

消息式 API 的基本形态

Claude 的对话接口采用 messages 形态：客户端把一次对话显式写成一组带角色的消息随请求提交，服务端不保存会话状态。工程上的许多约束都从这里派生。

system 与多轮消息

请求体里有两个层次的指令。system 是一段独立于对话历史的整体设定，用来固定角色、输出风格与边界条件；messages 是本轮及此前的对话内容，按角色交替排列。一个最小可用的 Python 请求大致长这样：

显式对话结构带来的责任

因为没有会话状态，多轮对话的成本由客户端承担：每一轮都要把此前的消息重新组织并提交。这带来三个直接影响。第一，历史不断增长，而上下文总量有上限，超限直接报错，所以要裁剪——常见做法是保留 system 与最近若干轮，更早的内容压成摘要塞回去。第二，预算要在输入与输出之间分配，输入挤满后留给返回的空间就很有限。第三，同一角色的消息连续出现时部分实现会拒绝，构造历史时最好在客户端先合并一次。规则要集中在 system，不要在最后一轮用户消息里复述。

把返回控制在预期之内

三个旋钮决定了一次返回的形态：长度上限、停止序列、采样参数。它们各自解决不同的问题，混用会掩盖真实原因。

最大返回长度与截断

max_tokens 是返回内容的预算上限。关键认知是：触顶截断通常不算错误，HTTP 状态仍是成功，只是内容在半句话处停住。不检查结束原因就把文本落库或展示给用户，就会得到一条残缺记录，而且它随机出现，测试环境里很难复现。

正确做法是把结束原因当成业务字段。命中上限时，要么把已生成内容接回历史再请求续写，要么把这次调用判为失败重来。前者适合长文本，后者适合结构化输出——半截 JSON 续写往往比重新生成更麻烦。

停止序列

stop_sequences 是一组字符串，生成过程中一旦命中任意一个就立即停止，且标记本身不会出现在返回内容里。它的价值在于把“从哪里该停下来”交给客户端决定。

典型用法有两类。一类是给自由文本约定收尾标记：正文生成完输出一个固定字符串，客户端把它配成停止序列，就不必再用正则切尾部。另一类是配合工具循环，用约定边界把解释文本和调用意图分开。注意停止序列必须是正文里绝对不会出现的字符串，撞车就会得到一条被莫名掐断的回复。

温度与采样参数

温度控制候选分布的陡峭程度，值越低输出越确定、越贴近模型首选，值越高越发散。除温度外通常还能配 top-p 与 top-k，它们分别从累计概率和候选集质量上截断。三者不必同时调，日常只动温度就够了，一起拧到底会让线上变化无法归因。

选型按任务类型：抽取、分类、改写这类有标准答案的任务用低温，并把温度作为常量在配置里显式声明；创意类用较高温度。温度的允许范围随版本调整过，上下界以官方文档为准。

鉴权与密钥管理

调用凭证放在请求头里随请求发出，争议全在密钥该存在哪、谁能看见。值得守住的边界只有一条：密钥只能出现在服务端进程的环境里，绝不出现在浏览器包体、移动端配置、日志与错误堆栈中。

前端需要调用时，正确形态是自建一层代理：请求先打到自己的服务，服务端补上鉴权再转发上游；这一层除了藏密钥，还能顺手做用户级配额与审计。把密钥配进前端环境变量，等于把它发布给所有能打开控制台的人。

存放上，开发机用本地环境变量文件并确认它已被版本控制忽略，正式环境交给部署平台的密文配置或密钥管理服务注入。轮换要有告警，告警内容是“检测到旧密钥仍在使用”。代码里不要打印密钥；不同环境与业务线用不同密钥，用量才能归因。

错误处理与重试

上游错误分成两类，处理方式完全不同。可重试的是容量与瞬时故障：限流、超时、服务端临时不可用；不可重试的是请求本身的问题：鉴权失败、参数不合法、上下文超限。把不可重试的错误丢进重试循环，是线上雪崩的常见制造方式。

限流要单独对待。先看响应头有没有建议的等待时间，有就按它等，没有再退到本地策略。等待不能无序：固定间隔会让一批失败请求同时对齐，形成二次洪峰，所以需要指数退避加随机抖动，并同时设三个上限——重试次数、单次等待天花板、总时间预算。任一触顶就抛异常，由上层决定降级。

重试还带来副作用重复。一次任务可能已经扣了配额、写了数据库，只是最后没拿到响应，重试会把前置动作再做一遍。办法是给一次业务意图分配幂等键，随请求与落库记录一起保存，消费端按键查重。这里的幂等指副作用不重复：采样打开时两次生成的文本本来就不会逐字相同，对一致性敏感的流程应把首次成功生成的文本落库，重放时直接读库。

流式返回的消费方式

流式开关打开后，一次调用不再一次性返回完整 JSON，而是持续推送事件，每个事件带自己的类型与增量负载。消费端的心智模型要跟着换：不是拿到响应再解析，而是维护一个累加状态机。

要点有三。第一，增量要按内容块归属分别累加，不能拼成一根字符串——文本块与调用意图块可能交替出现，混拼后展示层会看到错位片段。第二，结束事件仍带着停止原因，流式下同样必须做截断检测。第三，工具调用的参数以片段形式陆续到达，中途拼出来的往往不是合法 JSON，等该块结束再一次性解析。

超时语义也跟着变了：连接建立后长时间没有新事件，应按空闲超时判定而不是总时长超时。流一旦中断，已推送的增量既可能已经计费又无法续传，稳妥做法是整次判失败重来，不要接着半截生成——那会让模型看到一份自己没写过的历史。

工具调用：从定义到执行回传

Claude 2.1 在 2023 年 11 月提供了工具调用能力，在当时属于较新的形态，接入方式与开关以官方文档为准。机制并不神秘：客户端先把工具清单交给模型，模型在回复里表达“要调用哪个工具、参数是什么”，真正的执行仍然发生在客户端。模型从不碰你的系统，它只把调用意图交给可信的一方。

工具定义怎么写

每个工具通常要提供三部分信息：一个稳定的名称、一段给模型看的说明、一份输入参数的结构描述。名称是模型引用工具的唯一句柄，改名等于换工具。说明不是写给人看的接口文档，而是模型做选择的依据，要讲清这个工具做什么、什么时候该用、什么情况下不该用、返回什么形态的内容。参数结构用类型、必填项和字段含义来表达，模型只能依赖这些文字理解约束，所以字段说明要具体，能带取值范围与示例就带上。

字段拼写沿用当时的公开形态，接入前请核对。另外工具清单不是越多越好：名称近似、职责重叠的工具会让模型的选择变得不稳定，超过约十个（示意值）就该先做一层分组，宁可少而精确。

请求、执行与回传

模型如果决定调用工具，返回的停止原因会指向“需要调用工具”，内容里出现一个带调用标识、工具名与参数对象的调用块。客户端按顺序做四件事：解析参数、校验参数、执行工具、把结果作为新一轮内容回传。回传的关键约束是结果必须与对应的调用标识绑定，让模型知道哪份结果回应的是哪次调用。

sequenceDiagram
    participant C as 客户端
    participant M as 模型
    C->>M: 用户问题 + 工具清单
    M-->>C: 调用请求（工具名 + 参数）
    C->>C: 校验参数、执行工具、记录审计
    C->>M: 调用结果作为新一轮内容回传
    M-->>C: 给出最终回答或再次请求调用

循环控制与终止条件

请求调用、执行、回传之后，模型可能再次请求调用，于是形成循环。循环必须由客户端掌握上限与退出条件。至少要设四道闸门：轮数上限，比如 8 轮（示意值），触顶就停止并把已有信息整理成回答，同时标注任务未完成；停止原因不再是工具调用，这是最正常的退出路径；重复检测，连续几轮出现完全相同的工具名与参数，说明模型没从结果里得到新信息，继续问只会重复消费配额；整条链路的总时间与总预算。

并行调用

一次返回里可能出现多个调用块，客户端可以并行执行它们来压缩时延。三个注意点：结果回传时每个都要带上自己的调用标识，绑定不能错；有副作用或争抢同一资源的工具要串行化；并行批次里只要有一个失败，要提前决定是整体失败还是单独回传，默认取后者更稳。

权限确认与最小权限

模型请求调用工具，不等于这个调用有权发生。工具侧要做三件事：收窄可用集合、给敏感动作加人工确认、给执行留痕。可用工具按会话或按用户配置，只交出当前任务真正需要的那些。写操作、外发操作、产生费用的操作要走人工确认，且确认必须由客户端实现：命中这类工具时挂起循环，把待确认内容交给界面或工单，批准后再继续。不要指望模型在文本里自己“提醒用户注意”，那是文案，不是控制。

把错误回传给模型

工具执行失败时，既不要静默跳过，也不要抛异常终止整个会话。把失败本身作为这一轮的结果内容回传，写清失败类别与可读原因，模型才有机会改参数重试或改用别的工具。回传的应当是原因摘要而不是整段堆栈：堆栈可能带文件路径、连接串等敏感信息，长文本还挤占上下文预算。同理，参数校验不通过时，回传“哪个字段不符合要求、期望是什么”比让模型盲猜有效得多。

小结

这套接口工程化的关键，是把每一处默认行为变成显式约定：历史由客户端组织并裁剪，返回预算与停止序列由客户端设定，结束原因必须被检查，错误按可否重试分类，密钥只活在服务端，流式被当作状态机而非一次性响应。工具调用又把执行权留在客户端，于是循环上限、参数校验、人工确认、错误回传这些老派的服务端功夫一个都不能少。
