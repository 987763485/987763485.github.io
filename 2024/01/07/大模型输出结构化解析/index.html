大模型输出结构化解析

本文属于《Agent 智能体开发》第 5/55 篇
上一篇系列目录下一篇

大模型最擅长产出的是自然语言，而工程系统最需要的是能直接进数据库、能当函数参数、能参与事务提交的结构化数据。这两者之间隔着一层解析，而这一层恰恰是 LLM 应用里最容易出问题也最少被认真讨论的地方。本文把“如何从模型输出里稳定地拿到结构化数据”这件事拆开：有哪几条获取路径、各自的保证强度与代价、拿到字符串之后如何校验与重试、遇到截断和类型漂移怎么收尾，以及如何用一套指标衡量整条链路。

下游是代码，不是人

要理解结构化解析为什么值得单独讨论，先要看清消费模型输出的到底是谁。

在传统聊天场景里，模型输出的终点是人的眼睛。模型回一段排版整齐的表格，人读完自己去填系统表单。这条链路里“解析”这一步是由人脑完成的：人能容忍错别字、容忍字段顺序变化、容忍模型多说两句客套话，并在理解之后自动纠正。这种容错能力极强，强到我们很少意识到它的存在。

一旦把这一步交给程序，情况完全不同。程序的解析逻辑是刚性的：它期望某个字段存在、类型正确、日期符合某种格式、枚举值落在给定集合里，它没有“猜你大概是想说这个”的能力，最多靠默认值把问题藏起来。更关键的是自然语言输出天然不稳定：同一个提示跑两次，模型可能一次给“到期日：2024 年 3 月”，另一次给“有效期至 2024-03-31”，两句人都能读对，解析代码往往只认其中一种。本文的核心矛盾是一句话：模型的输出分布是连续的、多样的，而下游程序的输入契约是离散的、严格的。

工程上会撞上这堵墙的场景大致三类。第一类是信息抽取：输入是合同、邮件、客服对话、图片 OCR 结果这类非结构化文本，输出一组字段，特点是字段多、类型杂，而且经常出现“文本里没提到”的情况，必须能表达缺失这个语义。第二类是分类与判定：结构往往就是几个枚举字段，但对格式一致性要求最高，因为下游要用它做路由，一个多余空格或大小写差异就能让路由失败。第三类是参数生成：把自然语言诉求翻译成接口调用参数，常涉及嵌套与可选参数，一旦解释错误，后果不是解析失败而是执行了错误的操作。

错误的沉默性

结构化解析最棘手的地方不在于它会失败，而在于它失败时往往不报错。

设想一段用“取字段并给默认值”写法把模型 JSON 转成业务对象的代码。模型漏掉币种字段，代码填了默认值 CNY，业务系统就收到一笔金额正确但币种错误的记录；模型把日期写成 2024-3-5 而转换函数只接受补零格式，异常被上层吞掉记了一行日志，接口对外返回的还是成功。这类错误在测试环境里几乎不可见，发现时已经污染了几个星期的数据。

自然语言答案错了人一眼能看出来，结构化数据错了只有对账时才知道。这就是为什么这条链路必须配套校验、失败率指标和原始输出留档：没有经过校验的模型输出不可以直接落库。

让提示约束更有效的一些手法

在只能靠提示的阶段，有几类做法对格式稳定性确实有效。给出具体的输出示例而不是只描述规则：说“日期用 ISO 格式”会被理解成 2024-3-5、2024-03-05 或“2024 年 3 月 5 日”中的任一种，示例能把分布收窄到一个模式。把不要做什么说具体：只说“请输出 JSON”往往得到一段话加一个代码块，要显式说明首字符必须是左花括号、末字符必须是右花括号。单独强调易错字段：金额、日期、布尔这三类漂移最多。控制单次要求的字段数量：一次抽 30 个字段的失败率明显高于分两批各抽 15 个。

服务商提供的两种结构化能力

到本文写作的时间点（2024 年 1 月），主流闭源 API 提供两种官方能力来缓解上述问题：JSON 模式和函数调用（function calling）。它们解决的问题不同，保证强度也不同，混淆二者是线上事故的常见来源。

JSON 模式：只保证合法，不保证合规

JSON 模式在 2023 年 11 月随新一代模型接口一起提供，用法是在请求里把响应格式选项设置为 JSON 对象模式，服务端会在解码阶段约束输出，使返回内容是一段可被标准解析器接受的 JSON。

这里必须把它的保证讲准确：它保证的是语法合法，不是符合你的 schema。它能消除尾随逗号、注释、单引号、夹带解释文字这类让解析器直接报错的问题；但不能保证字段齐全（要求六个可以只给四个）、类型正确（要求数字可以给字符串）、枚举取值（给四个候选能造出第五个）、嵌套形状（要对象数组，可能给字符串数组）。

另外两点容易被忽略。一是这个模式对提示有实际要求：请求内容里需要明确出现对 JSON 格式的指称，否则请求会被拒绝——这条约束很容易在提示模板与请求参数分开维护时被忘记，线上就会突然开始返回 400 类错误。二是 JSON 模式下输出仍然是一段要闭合所有括号才算结束的文本，生成预算用完时返回的依然是不完整的 JSON，截断问题不会因为切了模式而消失。

对封装层来说，JSON 模式的价值在于把“解析器报错”这一类失败压掉，让失败集中到“解析成功但内容不合规”这一类。

函数调用：把输出当作函数入参

函数调用能力在 2023 年 6 月提供，最初的设计目的是让模型选择调用哪个外部函数并生成参数。用法是把字段定义写成一份函数签名——用 JSON Schema 描述参数列表，模型返回的不是文本正文，而是一个函数名加上以 JSON 字符串形式给出的参数对象。

很多团队把它用作纯粹的结构化输出通道：定义一个描述写清用途的函数，要求本次必须调用它，再把返回的参数对象直接当作业务数据。这个用法有效，是因为模型对“生成函数调用”这个行为有更强的格式倾向：输出落在专门的返回字段里，正文不再承载数据，模型顺手说两句的可能性显著下降。

但同样要讲准确它的边界：在本文时间点，函数调用的参数不保证严格符合你给的 schema。官方文档对此有明确提示：模型可能调用不存在的函数、可能填入你未定义的参数、可能在应该用字符串的地方给出数字。工程上还有三个注意点：

第一，参数字段本身也是一段 JSON 字符串，需要二次解析；函数调用被截断时该字符串同样不闭合，处理方式与正文截断一致。第二，必须调用某个函数这类强制能保证返回结构一定是函数调用，但不能提升字段正确率，真正提升正确率的是 schema 写得好：参数描述写清、枚举值用 enum 列全、必填与可选区分开。第三，把函数调用当纯结构化通道在语义上是借用，若系统里同时存在真正的工具调用逻辑，两类用法要靠函数名区分，所以我们给这类函数加固定前缀，解析侧只接受该前缀开头的返回。

受限解码：自研场景下的思路

如果是自建推理服务，或者能拿到模型权重与解码过程，就可以做一件闭源 API 当时还做不到的事：把格式约束从“请求模型这样做”变成“只能生成这样的 token”。

核心思路是在采样阶段做筛选。解码每一步都会得到整个词表上的分数分布，正常做法是按温度或 top-p 抽样；受限解码在抽样前先过滤——维护一个描述目标格式的自动机（对 JSON 通常需要栈，因为嵌套深度不定），根据已生成内容判断当前状态，把不允许的 token 分数置为负无穷，再在剩下的候选里抽样。语法正确性由此变成解码过程的强制属性。

代码只讲原理，真实实现还要处理分词问题：一个 token 可能对应多个字符，所以约束要在字节层面或对整个词表预分类，否则会出现“每个 token 单独看都合法、拼起来不合法”。常见做法是离线算好各状态下每个 token 的合法性并缓存。

这条路径的收益与代价都很明确。收益是硬保证：语法不会错，字段名不会拼错，枚举值不会跑偏（把枚举写进语法即可）。代价是三项：需要能改解码过程；需要为每个 schema 编译约束，冷启动有开销；以及最重要的——语法约束不能保证语义正确。你可以强制模型给 urgency 填 1 到 5 的整数，但填哪个数字仍然可能是错的。约束解决格式，不解决理解。

兜底解析：正则、分隔符与宽容解析器

无论用哪条获取路径，生产系统都应该保留一层兜底解析：模型返回的文本形态会随提示修改、模型版本升级而漂移，只认完美 JSON 的解析器在半年内几乎必然出问题。

一种常见策略是分隔符约定加逐行提取：让模型按行输出 key 与 value，用正则逐字段抓取。

它的价值在于字段之间互相独立：JSON 整体不闭合时全部字段都拿不到，而逐行正则只丢失出问题的那一行，适合“部分成功也好过全部失败”的批量场景。缺点是要求输出扁平，嵌套结构很难用行式约定表达，而且正则本身脆弱，多一个空格或换种大小写就可能失配。

另一种兜底是宽容解析器：选择或自写一个能容忍缺陷的解析器，允许尾随逗号、允许注释、遇到不闭合时把已解析部分作为结果返回。组织方式是先试标准库，失败后试容忍缺陷的解析器，再失败就走逐字段提取。TypeScript 侧不要把对象文本当表达式求值，更稳妥的是自写一个截断容忍的递归下降解析器。

第二个返回值很重要：必须知道数据是哪条路径救回来的。走 strict 可以直接用；走 salvage 意味着有字段缺失风险，下游要么补默认值要么走人工。这类样本占比是格式健康度的核心监控指标，缓慢上升通常就是模型侧行为变了的信号。

schema 校验与一次错误反馈重试

解析成功不等于数据可用，中间必须插一层校验，把“能 parse”提升到“符合契约”。

校验有两条常见实现路径：一条是直接用 JSON Schema 描述契约并用校验库检查，好处是契约与语言无关、报错信息天然机器可读；另一条是用类型系统的运行时模型（Python 侧的 pydantic、TypeScript 侧的 zod 这类），好处是校验之后直接得到带类型的对象。两者覆盖的检查项一样：必填字段是否存在、类型是否对、枚举是否合法、数字是否在范围内、日期能否归一、字符串是否长到离谱（这常常是模型在编内容的信号）。

校验失败之后要不要重试、重试几次，才是这一节真正要回答的问题。我们的结论是：把校验错误原样反馈给模型，只重试一次，再失败就退出自动链路。反馈的不是一句“请重新输出”，而是校验器给出的具体错误连同 schema 一起给回去，让模型只修改出错的部分。

限制为一次的原因有三方面。成本上，一次重试等于把输入 token 重新付一遍，而抽取任务的输入常含长文本；延迟上，在线场景里重试直接把响应时间翻倍；最重要的是收益衰减很快：失败原因是模型没理解指令时，把错误清单喂回去通常能修好；失败原因是原文里确实没有这个信息时，重试只是在同一个错误附近抖动。所以重试是修复格式类错误的手段，不是提高正确率的手段。

实践里还有几个细节决定这套机制是否可用。重试请求要包含上次的输出，只给错误清单模型不知道要改什么，带上那段 JSON 它才能做局部修改。要区分可修复与不可修复的错误类型，枚举值写错、数字带单位属于格式类，重试有意义；必填字段整体缺失、返回完全无关的结构属于理解类，直接判失败更快。校验错误要归一化后再统计，否则监控面板只剩噪声。原始输出必须留档，它是唯一能用来复盘和补充评测集的材料。

三类脏数据的收尾

前面处理的是“能不能拿到对象”，这一节处理“拿到之后哪些字段不能信”。

截断：先识别，再决定怎么补

截断在结构化输出里有特殊之处：它不是少了后半句话，而是整个结构不闭合，标准解析器会直接失败，前面已完整生成的字段也一起丢掉。识别它有两个信号：响应里的结束原因标记，以及括号平衡检查——不闭合的 JSON 未必是截断，但截断的 JSON 一定不闭合。

这里的原则是宁可少几个字段，也不要拿被猜测的内容去补全：字符串值被切断时应丢弃该字段，而不是补一个引号当作完整值，否则一条截断的摘要看起来就像正常数据。补全成功的数据要打上去截断修复的标记，走不同的下游策略。修复动作的优先级是：先确认生成预算够不够（去掉缩进、把长摘要砍短常比调大预算更有效），再把大输出拆成多次小输出，最后才是提高预算重试。

字段缺失：区分“没有”和“没抽到”

缺失有三种形态，混在一起处理一定出错：键根本不存在、键存在值为 null、键存在值是空字符串。前者通常是模型没遵守指令，后两者是模型表示原文里没有这个信息。工程约定是：schema 里所有业务字段显式声明是否可空，提示里要求“文本中没有则填 null，不要省略键”，解析侧把三种形态统一成“无值”判定，但打点时要分开记录——大面积出现键不存在说明格式指令出了问题，大面积出现 null 说明原文确实不含该信息。

类型漂移：在边界归一化，不要往下传

最常见的漂移都是“语义对但表示不对”，应该在解析边界一次性处理掉，而不是让每个下游模块各自兼容。

强转要守两条纪律。只允许白名单形式的强转：把字符串形式的 true 转成布尔是安全的，把“大约一千二”转成 1200 不是——那是模型在含糊其辞，替它做决定等于制造假数据。每次强转都要记录：某类强转占比升高，说明那个字段的表达有歧义，这是改进的输入，而不是可以长期存在的兼容代码。

日期是最麻烦的一类，格式空间几乎是开的：2024-03-05、2024/3/5、“2024 年 3 月 5 日”、“上周三”。做法是维护候选格式列表逐个尝试，全部失败就判字段无效，并在提示里要求“无法确定绝对日期时返回 null”——相对时间表达要由带时区和当前日期的上下文解析，不该交给模型口算。

嵌套结构：分而治之

当任务要求两层以上嵌套、或者长度不定的数组时，一次性抽全会同时撞上三个问题：输出太长容易截断、字段互相干扰导致漏填、一个字段出错就要整体重试。

更稳的做法是拆成多步：第一步只让模型输出骨架，一个 ID 列表或浅层对象数组，元素数量可控；第二步对每个元素单独发起抽取，只填这个元素的细节；第三步在应用侧按 ID 关联拼装。

拆法的收益是每一项都简单：单次输出短，截断风险低；schema 小，字段错配概率低；失败只影响一个元素。代价是调用次数变成 1 加 N，成本和延迟要重新算，而且跨步一致性要你在应用侧保证——关联键要在第二步的提示里给出并要求模型不要自己造 ID，还要准备容错匹配。

是否值得拆看三点：数组长度不定且可能超过三五项、嵌套超过两层、字段总数接近模型能稳定输出的规模；结构扁平、字段数在十个以内不值得。

流式输出下的增量解析

如果响应是逐块到达的（传输层细节属于流式输出那篇文章的范围，这里只谈解析），你会拿到一段还不闭合的 JSON，要不要做增量解析取决于拿它做什么。

增量解析的正确用途是展示进度，不是落库。 可行做法是维护一个手写的解析状态：一个括号栈加上“是否在字符串内、值是否读完”这几个标记，每收到一块文本就推进状态，遇到完整的字段值就发一个事件出去，前端据此显示“已识别到订单号……已识别到金额……”。

几个坑要提前知道。不能假设字段出现顺序，模型可能先给 summary 再给 order_id，增量逻辑必须对顺序无感。不要对部分 JSON 用正则，它看到的是不完整上下文，容易把值的一部分误认成另一个字段。最要紧的是：流结束时必须对完整文本做一次标准解析加校验，增量结果只能用于展示；如果流结束但顶层括号没闭合，那是截断，要走截断路径。

评测、成本与延迟

指标要分层：准确率、字段级召回与失败率

这条链路必须能被量化，否则无法判断一次提示修改或模型切换是变好还是变坏。指标要分层，不要只报一个总数。

最粗的一层是任务级结果，按结局分桶统计：解析成功且校验通过、解析失败、解析成功但校验失败、重试后成功、兜底救回、最终失败。各桶指向不同的修复动作——解析失败桶涨了就去看格式约束和截断，校验失败桶涨了就去看 schema 与提示描述，兜底救回桶涨了说明输出稳定性正在变差，只是被兼容代码掩盖着。

细的一层是字段级，在带人工标注的样本集上按字段计算。要区分两个概念：字段级召回回答该抽的字段有没有抽到，反映格式遵守度；字段值正确率回答抽到的值对不对，反映理解能力。

把两者混成一个指标，就会出现“格式很完美但数据全错”的假象；反过来只看格式成功率，会掩盖模型在编字段值的事实。样本集要覆盖三类困难：原文里字段确实缺失的、表述非标准的、结构复杂的长文本，它们分别考验 null 策略、归一化层和截断处理。上线后评测还要和线上打点对齐：同一套错误分类既用于离线也用于线上。

成本与延迟的代价

结构化解析的开销分布和普通对话不一样，容易低估的有四处。输入侧的 schema 描述是固定税：无论写进提示的字段说明还是函数调用的参数定义，每次请求都要重发，缓解手段是压缩描述、只保留业务约束（枚举取值、可空规则、单位）、示例给精简版。输出侧的结构比散文费 token：要求紧凑 JSON、去掉缩进，是少数立刻见效的优化。重试和拆分是放大器：一次重试意味着输入 token 重付，1 加 N 的多步抽取意味着 N 次输入，拆分要基于失败率而不是“看起来更稳”。流式改善感知延迟而不改善完成延迟：数据完整可用的时刻并没有提前。

还要特别注意尾延迟：链路加了重试，超时就该按最坏情况（两次调用）来设，否则重试请求会被上层网关掐掉，变成失败却没记录的隐藏问题。

小结

回头看，结构化解析真正的设计决策只有一个：在哪一层承担格式保证，在哪一层承担正确性保证。提示词、JSON 模式、函数调用、受限解码这四条路径提供的保证依次增强，也依次更依赖模型侧或推理侧的能力，但它们只覆盖格式这一半；符合契约这一半必须由客户端的校验来承担；内容对不对这一半，任何解析技巧都帮不上忙。

可以直接落地的建议是：把兜底解析当作必备层而不是临时补丁，并记录每条数据走的解析路径；重试只做一次，且只用于格式类错误；截断优先靠压缩输出结构预防；强转走白名单并留痕；指标按结局分桶、按字段区分召回与值正确率。最后提醒一次最容易忘的纪律：模型原文要留档。
