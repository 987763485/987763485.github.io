大模型应用架构分层

大模型应用的初版往往是一个几百行的脚本：拼 prompt、调接口、查数据库、把结果打印出来看效果。它跑得很好，直到要上线——换一家模型供应商要改五处，加一路召回要动主流程，评测只能靠人工抽查。本文把这套代码拆成接入层、编排层、能力层、模型层、数据层与观测评测层六层，逐层写清职责边界、输入输出契约与不该做什么，并给出层间契约、降级分支与成本归属的可运行示例。适合已经写过 demo、正准备把它变成线上服务的工程师，读完能拿到一张分层职责表和一组可落地的契约字段。

单体脚本上云时暴露的四类耦合

先还原一个典型形态。下面这段代码来自一个内部问答助手的第一个版本，它把「拼提示词、调模型、查向量库、解析结果、判断好坏」全部写在同一个函数里。

上线阶段它必然暴露四类耦合，每一类都有非常具体的疼痛表现。

第一类是模型供应商耦合。model="gpt-3.5-turbo-1106"、temperature、max_tokens、响应结构、错误码语义，全部直接写在业务函数里。当要把主模型换成自托管的 Llama 2 13B 或 Mistral 7B，或者把便宜模型换贵模型时，改动会扩散到每一个调用点。更要命的是重试策略：供应商侧的 429 限流、超长的首 token 延迟、上下文超限报错，都被同一个 except Exception 吞掉了，看不出是哪一类问题。

第二类是编排逻辑耦合。什么时候先检索、什么时候调工具、检索不到就拒答还是继续追问、多路召回结果如何合并、任务复杂时是否换更大的模型，这些控制流本来是最该被测试的确定性代码，却和字符串拼接搅在一起，只能用「改一行跑十次看看」的方式验证。

第三类是数据访问耦合。向量检索、原文回表、用户权限过滤都写在主流程里，意味着同一个检索逻辑要复制到「问答」「工单摘要」「周报生成」三个入口，权限过滤漏写一处就是事故。数据管道与索引更新本身的工程细节另有一篇《RAG 工程化落地》专门讲，本文不重复展开，只关心检索能力对外暴露什么契约。

第四类是评测耦合。判断回答好坏的方式是 print 出来人眼看。没有可复现的输入快照，就没有离线评测集；没有离线评测集，任何一次模型替换、提示词修改、检索参数调整都等于蒙眼上线。至于是不是被提示注入攻破、工具权限是否过度，属于应用安全的范畴，本文只在契约里留出 permission 字段，具体攻防由《大模型应用安全》那篇覆盖。

拆分的顺序建议是自内向外：先把模型层抽出来（改动面最小、收益立现），再抽能力层，最后把编排层的控制流写成显式的图，评测层可以并行起步——先攒 50 条标注样本，就能拦住大部分明显退化的变更。至于服务网格与网关高可用这些通用套路，是高并发微服务的老话题，本文只讨论大模型应用特有的分层理由：概率性输出、上下文组装成本，以及按 token 计费的资源模型。

六层划分与职责边界

分层不是给架构图凑格子，每一层必须能回答三个问题：对上提供什么契约，对下依赖什么，明确拒绝做什么。本文采用的划分如下。

flowchart TD
    A[接入层：会话与请求形态] --> B[编排层：控制流与路由]
    B --> C[能力层：检索、工具、记忆]
    C --> D[模型层：推理入口与缓存]
    B --> D
    D --> E[数据层：向量索引与对象存储]
    C --> E
    F[观测与评测层：贯穿各层的埋点与回归门禁]
    A --> F
    B --> F
    C --> F
    D --> F

接入层

职责是把外部世界五花八门的请求形态收敛成一个内部请求对象：Web 会话、移动端、开放接口、定时任务、批量导入，都要在这一层被翻译为统一的「一次生成请求」。它负责鉴权后的身份注入、会话归属、限流配额、输入长度预检与多模态附件的接收登记，同时负责把内部产出的事件流翻译成客户端协议。

输入输出契约：对外接收 HTTP 或 WebSocket 报文，对内产出一个不可变的请求上下文对象；下行返回事件流或完整响应体。它不该理解业务语义——不知道这个问题需不需要检索，不知道该用哪个模型，不该出现 if len(question) > 3000 这种和模型上下文窗口相关的判断，因为窗口大小属于模型层的知识。

流式输出的分帧、断线重连与增量渲染实现细节，本文不展开，那是《流式输出实现》的主题；接入层在这里只需要保证一件事：取消信号必须能向下游传播，客户端断开时不要把整条链路跑完。

编排层

职责是决定这次请求走哪条路：是否需要检索、检索几路、是否需要工具、工具结果要不要回填、失败之后降级到哪条路径、最终答案怎么合成。它是唯一允许持有「控制流」的层，也是唯一允许调用多个能力并组合其结果的层。

契约：上行接收请求上下文，下行只调用能力层与模型层的接口，产出结构化的中间产物（步骤记录、候选上下文、工具调用记录）与最终响应对象。它不该拼 system prompt 的具体文案（属于提示模板），不该直接写 SQL 或 HTTP 调向量库（属于能力层），不该 import openai（属于模型层），更不该在循环里sleep 重试——重试与额度控制是模型层的职责。

能力层

职责是把「模型之外的、可被编排复用的能力」实现为确定性的服务：检索服务、工具注册与执行、会话记忆读写。这一层的每个能力都必须可单独测试、可单独降级、可单独度量。

契约：每个能力暴露「输入受约束的参数对象，输出带来源与置信信息的结构化结果」。检索返回片段列表加命中统计，不返回拼好的字符串；工具返回原始执行结果加错误码，不返回让模型读的自然语言描述（把结果转成文本是编排层的事）。它不该调用大模型做决策——能力层是「被调用者」，一旦它内部开始调模型判断「要不要检索」，层级就塌了。

模型层

职责是提供统一的推理入口：把标准化的消息序列与采样参数交给某个后端（云端 API 或自托管服务），拿回文本或增量片段，并把 token 用量、耗时、缓存命中、错误分类如实上报。它还要负责额度、并发、重试、超时与成本归因。

契约：上行是 GenerationRequest（消息、工具 schema、采样参数、超时预算），下行是 GenerationResult（文本或事件流、用量、停止原因、后端标识）。它不该决定提示词内容，不该知道用户是谁，不该把供应商的差异泄漏到上层（finish_reason 之类的字段要归一化）。推理内核与算子优化不属本层，模型层关心的是「入口抽象」，具体的解码与量化内核实现由《llama.cpp 源码与推理优化》那篇承担。

数据层

职责是持久化与索引：向量索引、全文索引、对象存储里的原文、会话与记忆的落库、结构化业务数据。它提供读写与权限过滤原语，并负责数据生命周期。

契约：上行是带租户与权限标签的读写请求，下行是记录流。它不该计算 embedding（那是模型层或能力层的写路径）、不该决定召回策略、不该在返回前对文本做语义裁剪。

观测与评测层

职责是让上面五层的每次交互都可回溯、可归因、可回归：埋点字段规范、trace 聚合、离线评测集、在线指标与回归门禁。它是横切层，不参与控制流，也不向任何层返回业务数据。

契约：只消费各层上报的事件，产出指标、看板与门禁结论。它不该在生产链路上同步执行评测调用——把评测塞进请求路径会同时污染延迟和预算。

层间契约与一次请求的完整往返

分层之后，跨层调用需要一份共同契约。经验上四个东西必须贯穿：请求上下文对象、超时与取消传播、幂等键、trace 字段。

超时与取消用绝对截止时刻而不是每层各配一个相对超时，原因很实际：每层重新计时会把总预算悄悄放大成「上游超时两倍」，而下游并不知道上游已经放弃了。约定是每一层进入时先算剩余预算，剩余不足就直接返回降级结果，不再发起调用。

幂等键解决的是「重试产生两条回答、两次扣费、两次写库」。request_id 由接入层生成或由客户端携带，编排层与模型层都以它为缓存键与去重键；工具执行必须显式声明是否幂等，非幂等工具在重试时要带上同一 request_id 让下游自己去重，而不是简单地重放。

一次带检索与工具调用的请求，在六层之间的完整往返如下。

降级分支需要显式定义，不能散落在 except 块里。本文采用的口径是：检索失败或召回为空时降级为无依据回答或直接拒答，由业务风险等级决定，不阻塞主链路；工具超时则把「工具不可用」作为事实写进上下文让模型说明限制，而不是重试到用户离开；模型层主后端不可用时切备用后端，切换要记入 trace 并在响应里标出，便于评测层把降级样本单独统计。

编排层：把控制流写成可测试的代码

编排层最常见的两种形态是链式与图式。链式（顺序组合若干步骤，前一步输出接后一步输入）写起来省力，适合流程线性、分支少的任务；一旦需要条件分支、并行扇出、循环回退，链式就开始用「把分支藏进回调」的方式变形，可测试性迅速下降。图式（显式声明节点与边，状态沿边流动）把分支变成数据结构，代价是要引入状态与终止条件的概念。取舍判据很简单：分支数小于二且无环，用链式；出现并行汇合、循环或需要中途恢复，用图式。

LangChain 在 0.1 前后正处于抽象迁移期，链与 Agent 的组织方式换了口径，直接把它的内部抽象当架构分层会踩到版本动荡，所以本文只把它当可选工具而不是架构主干——路由、扇出与降级这三件事建议自己写清楚。

路由是编排层最有价值的一段代码：按任务复杂度选模型，能把成本压下来一大截。

并发与扇出：一次问题拆成子问题并行检索、多路召回、多家后端同跑取最优，都属于扇出。要点是并发上限必须与模型层的额度联动，而不是编排层自己写一个数——扇出到 8 路而额度只允许 3 路并发，多出来的 5 路只会换来一堆 429。扇出的汇聚要有部分成功语义：等到全部完成再返回，会让整个请求被最慢的一路拖死。

失败重试的边界要分三层写清，避免同一个错误在两层各重试两次：编排层只对「幂等且语义上有替代路径」的失败做重路由（换后端、去掉检索），不重试同一个后端；模型层对网络类与限流类错误做带抖动的指数退避，退避必须落在剩余预算内；数据层对写入冲突做有限重试。任何一层重试都要在 step 记录里留下次数，否则评测层看到的延迟波动无从归因。

能力层：检索、工具与记忆

检索服务是能力层里最容易被编排层越权的一块。正确形态是暴露一个带类型契约的接口：入参是查询文本、租户、权限标签、top_k 与过滤条件，出参是片段列表，每段带来源标识、得分与原文定位，便于终答引用与事后核对。空召回必须返回空列表而不是抛异常，让编排层显式决定降级方式。

工具注册与权限校验是这一层的核心工程。注册表把「模型能看到的描述」与「运行时真正执行的实现」分开，模型只看到名字、参数 schema 与一句说明（function calling 的参数约束在 2023 年 6 月之后已经够用，把返回值整理成自然语言是编排层的事）。

三个细节值得单独强调。参数校验发生在执行之前而不是让下游报错，因为模型生成的参数是半可信输入；权限校验用「暴露即授权」的思路，无权工具连 schema 都不给模型，能显著减少无效调用与探测；request_id 透传给非幂等工具，把去重责任交给下游而不是靠重试运气。

会话记忆的存储形态有三种，各自的失效策略不同：

形态 内容 适合场景 失效策略
原始轮次窗口 最近 N 轮对话 连续追问、指代消解 按轮数截断加 token 上限双约束
摘要压缩 早期对话的结构化摘要 长会话、跨天延续 摘要重生成时旧版本直接替换，保留版本号
显式事实记忆 用户偏好、稳定设定 个性化 按条目更新，带时间戳与来源，可人工撤销

要点是记忆的写入必须可解释、可撤销，不要把「模型说过的一切」都当事实存下来。摘要与原始窗口之间要有一致的定位信息，否则引用会串。记忆读写属于能力层，落库属于数据层，两者通过带 tenant 与 session_id 的窄接口隔离。

模型层：推理入口抽象与其资源边界

模型层的价值全在「上层只看见一种形状」这一件事上。无论后端是云端 API 还是自托管服务，接口只有一对数据结构：进去的是消息序列加采样参数加预算，出来的是文本或事件流加用量加停止原因加后端标识。响应里的 finish_reason 语义要归一化——长度截断、命中停止词、被过滤、正常结束这四类在上层要能一分支处理，而各家字面量并不一致。至于把模型输出解析成结构化对象的具体做法是《输出解析》的主题，本层只负责把原始文本与错误分类交上去。

流式与非流式是同一个入口的两种下行形态，不该拆成两套契约：stream=True 时返回事件流，最后一个事件必须携带完整用量与停止原因，否则成本归因和评测采样都会缺一块。选择原则是「用户在等的用流式，机器在等的用非流式」——面向人的答案用流式压首字延迟；工具规划、结构化抽取、离线批量生成用非流式，因为要的是完整结果而不是渐进显示。

缓存要分两级看待。第一级是应用级的完整响应缓存，键由后端标识、提示模板版本、渲染后的消息序列哈希、采样参数与租户共同决定，任何一项变化都会失配；它命中时直接跳过模型调用，最适合高频重复的客服问答与摘要类任务，但要清楚它对「上下文里带用户身份或实时数据」的请求基本无效。第二级是提示前缀缓存，即把每条请求里逐字节相同的长前缀（静态 system prompt、few-shot 示例、共享的说明段）放在最前面，让后端复用前缀的计算。它的适用边界比听起来窄：前缀必须真正稳定，任何动态字段（时间戳、用户名、会话号）混进前缀就退化成永不命中；云端 API 在这一年的一月还没有普遍提供可控的前缀缓存能力，自托管侧则依赖推理引擎的 KV 复用与实例亲和——请求被负载均衡打散到不同实例，前缀缓存等于零。所以工程上先守住「前缀稳定化」这条书写纪律，再把它作为模型层的可选优化上报命中情况，而不是当作既成的降本手段。

批处理与并发额度是一对需要显式分配的约束。离线任务（评测集重跑、全量重建索引的摘要生成、历史工单聚类）不该和在线请求抢同一份额度，正确做法是给它们独立的队列与独立的额度池，在低峰期限速消费，并把它们归到不同的成本桶。自托管同理：在线实例要保延迟，离线跑批独占一批实例，两者按部署单元隔离而不是靠运行时优先级。

量化部署与云端 API 的分工，判据只有四条：数据能否出域、延迟要求、稳定 QPS、团队是否具备 GPU 运维能力。敏感语料与受监管场景落在自托管，用 Llama 2 13B 或 Mistral 7B 这类开源模型，配 PyTorch 2.1 与 transformers 4.3x 系列的加载路径，推理服务用 vLLM 0.x 提供的 PagedAttention 与连续批处理；需要更强推理能力的长链路任务再上云端旗舰模型。量化模型（K-系列权重与 GGUF）的取舍不是架构问题，属部署细节，本文不展开，只要求一件事：自托管后端在模型层必须与云端后端一样暴露统一的用量与错误分类，否则观测层的数据不可比。

数据层与观测评测层

数据层要处理的第一个问题是派生数据与原文的权限边界。一份原文被切成片段、算上 embedding、生成摘要、打上标签之后，会产生四类新的泄露面：片段进索引时把原文里的敏感字段一起写了进去；摘要比原文更「像答案」，容易被当成可公开内容；embedding 本身在部分场景可被反推；标签暴露了原文的分类逻辑。可执行的约定是三条：派生数据的可见范围永远不宽于其来源原文，写入时继承 tenant 与密级标签并让检索路径强制过滤；索引只存被允许召回的字段，展示所需的其他字段回原文取；原文删除或密级提升时派生数据必须级联清理，删除沿数据层一条带来源标识的写路径完成，不留孤儿片段。索引更新与数据管道本身的实现细节归《RAG 工程化落地》，本层只对上层承诺一件事：读到的一定是版本一致的数据。

版本一致性靠「别名切换」而不是原地更新：新片段与重算的 embedding 写到一批新的分片里，校验通过后把查询别名指过去，旧分片保留一个回滚窗口。这让「一次索引坏了」从数据事故降级为一次别名回滚。

观测与评测层是让前五层可治理的唯一手段。埋点字段要一次定全，事后补不上历史数据：

离线评测集是变更的安全网。起步规模不必大，50 到 300 条按任务类型分层抽样的样本就足够拦住大部分明显退化，但必须满足三个条件：输入快照完整（包含当时的检索结果，否则无法复现）、每条评价标准写死（正确性、是否该拒答、引用是否到位、格式是否合规）、样本会随线上失败案例滚动更新。评测本身是一次批量的模型调用，因此要放到模型层的离线额度池里跑，并把结果与 prompt_version 一起入库。

在线指标与离线指标分工不同：离线看「答得对不对」，在线看「用户是否真的省事」。值得长期盯的是赞踩比与追问率、人工接管率、降级率、单位请求成本、首 token 延迟分布。在线指标要能按 backend、prompt_version、experiment 三个维度切分，否则一次模型切换的影响会被平均掉。埋点的采集口径遵循最小必要与脱敏，留存期限由业务与合规要求确定。

成本与容量的分层归属

成本归属不写清，最后一定变成「模型层背锅」。合理的分配是：接入层负责限流与配额（每用户每分钟请求数、单次输入长度上限），因为它知道谁在调用；编排层负责预算分配与扇出规模（一次请求最多调几次模型、几路检索、允许几次重路由），因为控制流在它手里；能力层负责召回规模（top_k、重排候选数直接决定进入上下文的 token 数）；模型层负责额度、重试、缓存命中与后端选择；数据层负责索引容量与存储；观测层负责核算与归因。

数字口径全部是示意值，需要用自家单价与真实流量替换：一次问答请求的输入约 2000 到 4000 token，其中上下文资料通常占七成以上，因此「少召回两段但更准」往往比「换个便宜模型」更省；检索一次的耗时约几十到几百毫秒，模型一次生成约一到五秒，容量规划时模型层是瓶颈而不是数据层；自托管小模型的单位成本明显低于云端旗舰，但要按 GPU 折旧与运维人力折算成同口径才能比较。

什么时候不需要六层？三种情形明确不需要。第一种是内部一次性工具：跑一次的报告生成、给团队自己用的批处理脚本，一个文件加一个配置就够，分层只增加阅读成本。第二种是任务本身极窄：单轮抽取、分类、格式转换，没有检索也没有工具，那能力层与编排层都是空的，正确形态是接入层加模型层加一个轻量的观测埋点。第三种是流量与人力都不足：一个人维护、日均几百次调用，把时间花在评测集上比花在分层重构上划算。分层的收益来自「变更频繁且变更点分布在不同层」，如果只有 prompt 在变，分层就是负担。一个务实的判据是：改一处降级策略要同时动三个文件，换一次模型要在十处改参数，说明耦合成本已经超过分层的维护成本，该抽层了。

小结

六层不是六个进程，也不是六个仓库；它是六份契约，可以在一个进程里以模块形式存在，也可以在规模到位后逐层拆成服务。真正需要固化的东西只有四件：贯穿的 trace 与幂等键、绝对截止时刻驱动的预算传播、每层明确的「不该做什么」、把变更分类到不同层的评测门禁。把职责表贴在墙上，比画出漂亮的架构图有用。

层级 核心职责 典型故障表现 归属团队
接入层 请求形态收敛、鉴权限流、下行分帧 客户端断开后链路仍在跑；超长输入直达模型层报上下文超限 前端与网关
编排层 控制流、路由、扇出、降级与重路由 一次请求调了七次模型；分支只能靠改代码验证 应用与业务
能力层 检索、工具注册与权限校验、会话记忆 无权工具被模型看见；记忆写脏且无法撤销；召回为空时整链卡死 算法与业务共建
模型层 统一推理入口、用量归一、额度与重试、缓存 429 与真故障混在一起；换后端要改上层十处；延迟毛刺无从归因 平台与推理服务
数据层 向量索引、原文对象存储、派生数据权限与版本一致 索引与原文不一致；删原文后片段仍可召回；跨租户串数据 数据平台
观测与评测层 埋点字段、离线评测集、在线指标、回归门禁 说不清这次版本变好还是变坏；成本无法按功能归因 质量与平台
