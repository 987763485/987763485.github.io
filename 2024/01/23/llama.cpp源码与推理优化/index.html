llama.cpp 源码与推理优化

llama.cpp 于 2023 年 3 月开源，它想解决的问题很直接：让大模型推理脱离对高端显卡与重型框架的依赖，在消费级硬件和多种后端上跑起来。本文沿着源码的组织方式，看一次推理如何在模型加载、图计算、分词、采样与服务层之间流转，并讨论 GGUF、量化、KV Cache、批处理与后端卸载的动机与代价。读完你应能回答两个问题：请求的耗时与内存分别花在哪里，怎样在自己的机器上做出可信测量。

项目要解决的问题

主流推理栈默认把 GPU 当作前提：权重以 fp32 或 fp16 存放，框架还要带上一整套运行时与算子库。这套组合在数据中心里合理，搬到个人电脑、入门级显卡的服务器，或者没有 CUDA 的平台，就会同时撞上两堵墙。

第一堵墙是容量：参数量决定权重体积，注意力缓存决定上下文能开多长，两者相加往往超过消费级显卡的显存。第二堵墙是依赖：跑一次推理要装配深度学习框架、Python 环境与一堆二进制库，嵌入已有程序尤其困难。llama.cpp 的答案是相反方向的收敛——核心用 C/C++ 实现，依赖压到标准库加可选的线性代数后端；用量化把权重压到 4 至 8 比特，让模型体积落进内存；用一层薄薄的张量库，把同一份计算描述分发到不同后端。

这个立场换来广覆盖与低门槛，代价是它并不为超大 batch 的极限吞吐而设计；当成高并发在线服务的支柱，还得自己补上调度与监控。

代码组织：从模型加载到服务层

阅读源码的好入口是按职责切成五段：模型加载、图计算、分词、采样与服务层，它们串成从磁盘到文本的链路。

flowchart TD
    A[GGUF 模型文件] --> B[模型加载与张量装配]
    B --> C[图计算引擎]
    D[分词模块] --> C
    C --> E[后端执行 CPU 或 GPU]
    E --> F[采样模块]
    F --> G[服务层与命令行工具]
    G --> D
    F --> G

五段职责

模型加载读出文件里的元信息与张量数据，按声明的维度、类型和偏移把权重组织成可用形态，同时接住词表与架构超参。图计算层不关心语言模型语义，只把一次前向拆成矩阵乘、加法、归一化、注意力这类算子的有向图，交给底层张量库构建与执行，这一层是与硬件后端解耦的关键。分词模块把文本切成 token 序列。采样层拿到最后一个位置的 logits，按温度、top-k、top-p、重复惩罚这类策略选出一个 token。服务层把这些能力包装成命令行工具与 HTTP 服务，并管理各自的会话状态。

薄 API 的价值

对外头文件只暴露少数入口：加载模型、创建上下文、执行一次前向、拿回 logits。薄 API 的意义在于可嵌入——数据库扩展、其他语言的绑定、体积受限的宿主程序都能只链接这一层；把上下文对象与模型对象分开这类设计，正是为在服务场景里复用模型、隔离会话。

GGUF 的设计要点

2023 年 8 月起，项目改用 GGUF 作为模型文件格式。这不是改个后缀，而是把权重文件重新定义成自描述的模型容器。

文件头部先写清身份：魔数与版本号让加载器能够拒绝一个并不兼容的文件，而不是读出乱码。其后是键值元数据区，用带类型的键值对存放层数、隐藏维度、上下文上限、词表与特殊标记等架构信息；这套键值可扩展，新特性能先以元数据形式落进文件。再往后是张量信息表与数据体，每个张量登记自己的名称、维度、元素类型与文件内偏移。

多量化等级共存

张量信息表按张量记录类型，这意味着同一个模型里不同张量可以采用不同量化等级，不必全表统一。常见做法是把对数值损失更敏感的权重留在较高精度，把体积占大头的压到更低精度；这种混合等级在旧格式里做不到。也因为每个张量自带元信息，加载器不再靠硬编码的名字顺序猜结构，数据体按固定字节数对齐的排布，则为后面的内存映射做好铺垫。

量化思路与取舍

量化是收益最直观的一环，但很多人把它当成“数字越小越好”，这就走偏了。这里只讲原理与取舍，不给具体分数结论。

块状量化在做什么

权重量化的本质，是用更少的比特表示原本 16 位或 32 位的浮点数值。对整张量做线性映射的问题是，少数极大值会把量化区间拉宽，多数正常值挤在几个刻度上，误差迅速放大。块状量化把张量切成小块，每块单独求缩放系数（有的格式再附带偏移或最小值），块内数值用整数刻度表示：块越小，对局部分布贴合越好，元数据占比也越高。

按每参数平均比特数看，4 比特附近通常是最实用的折中，5 到 8 比特用于更在意质量的场合，2 到 3 比特只在内存极度紧张时才考虑。下面的表格是思路对照，不是评测结论。

比特量级 思路 适用场景
2 至 3 比特 压到极小，误差最大 容量勉强够、只做粗探
4 比特 主流折中，体积约为原权重的一小半 内存受限但要求可用质量
5 至 8 比特 同族格式里偏保守的选择 容量略宽裕，重视稳定

量化不是免费午餐

两点代价要记住。第一，权重只是内存占用的一部分：推理时还要为 KV Cache、激活与运行时结构留空间，量化省下的容量很容易被长上下文吃掉。第二，解码时要先把整数刻度还原成可参与运算的数值，这带来额外计算；好在此时瓶颈通常在内存带宽而非算力，少读一半数据往往是净收益。是否更快要按阶段看，预填充算力密集，收益通常不如解码阶段明显。选等级的合理顺序是拿自己的提示集，在候选等级上各跑一轮，看质量能否接受。

KV Cache 与上下文占用

自回归解码每生成一个新 token，都要让它在注意力里看到前面所有位置。每步重算历史的代价不可接受，于是把每个历史位置算出的键与值缓存下来，这就是 KV Cache。它的容量由模型结构与上下文长度决定，与参数量无关，权重量化得再狠也动不了这块开销。

这段公式能读出几条结论。上下文长度是线性因子：上限翻四倍，缓存就翻四倍，哪怕实际只跑短对话，容量也常按上限预留；多轮与并发会话会让占用继续叠加。所以上下文能开多长，取决于权重之外还剩多少内存，而不是模型文件有多大。真要长上下文，稳妥顺序是先确认缓存开销可承受，再减小并发数、限制生成长度、复用会话前缀。

批处理与预填充阶段

一次请求在时间上分成两段，瓶颈完全不同，混在一起谈吞吐会得出错误结论。

预填充（prefill）处理输入提示，一次把整段 prompt 的每个位置都算出来，它是算力密集的：矩阵乘的行数与提示长度成正比，能把硬件并行度喂饱。解码（decode）阶段每步只有一个新位置要算，却要把全部权重和缓存读一遍，于是变成内存带宽密集。同一块硬件上两段的每秒 token 数能差出一个量级，报告数据必须说清是哪一段。

sequenceDiagram
    participant C as 客户端
    participant S as 服务层
    participant G as 图计算
    C->>S: 提交提示
    S->>G: 一次性预填充整段 prompt
    G-->>S: 首批 logits
    S-->>C: 第一个 token
    loop 逐个生成
        S->>G: 单 token 解码并写入 KV Cache
        G-->>S: logits
        S-->>C: 增量文本
    end

批处理把多个请求的同阶段工作合并成一次前向：几条序列的解码步拼成一个批次，权重读取从每 token 一次摊薄成每批次一次，带宽利用率立刻上来。代价是调度变复杂——序列长度不齐、到达时间分散，需要按槽位管理各自的上下文区间。批次大小与上下文占用互相争夺内存，增大批次能提吞吐，却推高首 token 延迟与峰值内存。另一个省掉重复预填充的办法，是在多轮对话中复用已有前缀的缓存、只重算追加部分；前缀一旦被改动，缓存就必须作废。

计算后端与内存映射

覆盖多种硬件靠的是把描述计算与执行计算分开。CPU 侧为同一批算子准备多套实现：一份可移植的标量基线，加上面向 x86 各代向量指令集与 ARM NEON 的优化版本，按本机能力选择路径。量化格式下向量化尤其划算——整数刻度与缩放系数的乘加适合用 SIMD 一次处理多个元素，瓶颈也随之从算力转向内存带宽。

GPU 卸载的实用粒度是层而非单个算子：按剩余显存决定卸载到第几层，其余留在主机侧；采样这类开销小但频繁的步骤，没必要来回搬运。判断标准是单层数据放不放得下、拷贝开销能否被计算收益盖住，把卸载层数拉满通常并不最优。

内存映射则直接影响加载表现。权重以 mmap 进入进程，省掉一次完整读入，多个进程还能共享同一份页缓存。代价是访问变成缺页驱动：被回收的页要重新从磁盘读回，只跑很短时间的进程可能还没读完就退出，此时磁盘带宽才是瓶颈。

服务化接口与编译

仓库自带一个本地 HTTP 服务，既能直接验证推理链路，也能被上层应用当引擎调用。能力概览是：补全端点接收提示与生成参数，支持以增量方式把 token 陆续推给客户端；嵌入端点把文本转成向量；另有健康检查与模型信息两类只读端点。请求参数集中在采样策略、最大生成长度与超时，服务端按会话维护上下文槽位。它是进程内单模型的形态，扩容靠多实例与前置调度。

构建走 CMake，仍遵循最小依赖：运行期不需要 Python 或深度学习框架，Python 只出现在把第三方权重转换成 GGUF 的脚本里；后端与并行能力用构建开关选择，例如某个 GPU 后端、厂商 BLAS 库，以及是否启用 OpenMP 做多线程。

跨机器分发时，指令集开关要按部署机而不是编译机设置，否则典型症状是构建成功、运行时报非法指令。

测量自己的机器

三个指标覆盖大多数判断：首 token 延迟（由排队、加载与预填充共同决定）、解码吞吐、峰值内存与显存占用，三者不能互相替代。程序本身会输出分阶段的耗时统计，配合外部观测就够用：

让结果可信靠的是约束：固定模型文件与量化等级、固定提示集与生成长度、先跑一轮丢弃预热、多次取中位数而非最好的一次、把输入长度一并记录。别人的数字只能当线索——硬件、指令集、内存通道、批大小任一项不同，曲线就不可比。

坑也集中在几处。上下文上限设得过大最常见：它按上限预留，直接换算成内存占用，还没生成就吃光余量，表现为加载失败或频繁换页。其次是量化等级一味图小，体积满意了质量却撑不住业务，合理顺序是先定质量底线，再在可接受范围内挑最省的等级。第三是线程数开得比物理核多，带宽已经饱和时只会增加调度抖动，平均吞吐可能略升而尾延迟变差，稳妥做法是从物理核数起步再看曲线。

小结

这个项目的价值不在某个单点最快，而在把“能不能跑”变成“怎么跑得更合适”：薄 API 加一层张量库，让同一份计算描述落到多种后端；GGUF 用自描述的元信息换掉旧格式，让混合量化与内存映射成为可能；量化决定权重体积，KV Cache 决定上下文余量，两者要一起算；预填充与解码的瓶颈不同，批处理改善的是后者，代价落在首 token 延迟上。所有结论都应在自己的机器上、用自己的提示集测出来。
