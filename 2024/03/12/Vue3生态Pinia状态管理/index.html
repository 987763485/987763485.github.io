Vue 3 生态：Pinia 状态管理

当一个 Vue 3 项目的页面涨到十几个，组件之间就开始互相“借”数据：父组件往下传、兄弟绕道公共父组件、登录态塞进每一层路由。本文在 Vue 3.4 与 Pinia 2.x 主线的口径下，说明为什么需要独立的状态库、store 怎么写、坑埋在哪里，适合已经会写 <script setup> 组件、准备引入全局状态的读者。读完你应该能定义并组合 store、写出持久化插件。

为什么还需要独立的状态库

组件树传参的成本先是层级。一个“当前用户昵称”要出现在右上角、评论区与订单详情里，就得从根组件一路 props 下钻，中间每一层都接收着自己并不消费的字段，改名时这些中转层全得跟着改。其次是反向传递：子组件改动只能沿 emit 链往上抛，抛到第三层已经很难说清起点与终点。

跨路由共享是第二个压力。<router-view> 切换时旧组件实例被销毁，写在组件里的 ref 随之消失。购物车列表、筛选条件这类返回后仍需存在的状态，靠组件自己保管就得再做一层“离开页面前存起来”的手工搬运。

可回溯的变更是第三个收益。全局状态只有一份可变来源，每次修改都经过 store 的方法，于是有了天然的挂载点：记日志、报埋点、存档某次会话的快照。

但收益只在真正共享的状态上成立。这几类不要放进全局：只在单个组件内消费的界面态，如弹窗开关、hover 高亮、表单草稿；能从 props 或已有状态推导的值，就地计算；只被一个页面使用的一次请求结果；变化极频繁的中间量，如拖拽坐标，交给局部 ref，让变化只影响一小片模板。

与 Vuex 的差别

Pinia 之前，Vue 生态的默认答案是 Vuex，《Vue Router 与 Vuex 实战》一篇已介绍过它的 API，这里只做定位对比。差别有四点。

第一是去掉 mutation。Vuex 把“声明改动意图”和“真正改状态”分成两步，同步写在 mutation、异步编排在 action；Pinia 只有 state、getter、action 三层，action 里直接给状态属性赋值即可。少掉的不只是几行代码，而是“这段逻辑该放哪一层”的纠结。

第二是写法天然组合式。store 定义本身就是函数与响应式变量的组合，与抽取组合函数的手感一致；this 不再无处不在，测试一个函数比测试依赖上下文的对象方法容易。

第三是类型推断来源变了。Vuex 里状态、mutation 名与 payload 要靠联合类型和 helper 手工对齐，改一处漏一处。Pinia 的类型直接从 store 定义的返回值推出，编辑器在 store. 之后能列出全部字段，getter 的返回类型由表达式决定。

第四是没有模块注册负担。Vuex 用 modules 与命名空间组织状态树，新增一块状态要写模块文件、注册进根 store、决定命名空间。Pinia 里“模块”就是“另一个 store”：定义一个函数，谁用谁 import，没有中心注册表，也就没有拼错命名空间这种失败方式。

集中式提交换来过可审计的变更记录，只是这份保证在调试面板与订阅机制到位后显得冗余。存量项目可以让两者并存，按业务块迁移。

定义 store 的两种方式

安装只有一处：把 createPinia() 交给根应用，之后任何组件里调用 useXxxStore() 都拿到同一个实例。

第一种是 Options Store，把 state、getters、actions 写成三个配置块，形态接近 Vue 2 时代的选项式组件。

第二种是 Setup Store，把 store 的定义写成一个函数，形态与组合式 API 的 setup 一致。

两种定义在使用方式上完全一致，互换不影响调用点。选择直觉有两条：store 基本就是“若干字段加若干改名函数”时用 Options，配置块的名字本身就是分类；需要不对外暴露的中间变量、需要在多个 action 之间共享私有逻辑，或要把已有组合函数原样放进 store 时用 Setup——它最后那行 return 相当于一次显式的接口声明。

state、getter 与 action

getter 就是 computed

理解 getter 的关键是把它当作 computed：它惰性求值，没有组件读取就不会计算；它带缓存，依赖没变时反复读取返回同一结果。因此 getter 里不能放副作用。把埋点或请求写进 getter，可能一次都不执行；即使执行了，后续读取拿的是缓存值，副作用不会再来一遍。副作用应当放在 action 里，由明确的调用时机驱动。

Options Store 里的 this 是个类型坑。箭头函数形式的 getter 拿不到 this，只能接收 state 参数；一旦要通过 this 读别的 getter，就必须改写成方法形式并显式标注返回类型，否则 TypeScript 推断 this 要依赖 getter 的返回类型，后者又依赖 this，形成循环推断。上面的 totalQuantity(): number 就是为这个约束服务的。Setup Store 没有该问题，依赖同处一个闭包；在 getter 里调用别的 store 会形成隐式耦合，后文讨论组合时再展开。

action 的同步、异步与错误处理

action 不区分同步与异步，异步就是 async 函数，返回值是 Promise，调用方可以直接 await。

组件里先 const store = useSearchStore()，再调用 store.fetchList(kw)。一个容易忽略的细节：action 挂在 store 的响应式代理上，代理会把方法绑定到自身，因此解构出来单独调用的 action 读写的仍是同一份状态；解构 state 字段不在这份保护范围内。

错误处理的取舍是：能在界面内消化并继续展示的，转成 error 这类状态字段；必须让上层感知的，继续抛出。最不该做的是 catch 之后返回空数组，那会把故障伪装成“确实没有数据”。

loading 的归属按数据块划分，不按按钮划分。同一段数据可能被三个组件同时展示，它们都想知道是不是正在加载，这时 loading 属于 store；按钮自己的禁用状态属于那个组件的局部 ref。给每个 action 复制一个专属 loading 会让状态数量线性膨胀，出现界面还在转圈而请求早已结束的漂移。

解构失响应与 storeToRefs

先看一段常见错误写法。

点按钮后数量确实变了，但界面上 totalQuantity 停在 0。因为 store 是代理：读 store.coupon 取出当前值，读 store.totalQuantity 执行一次 computed 求值再交出结果。解构只是把当前属性值复制到局部变量，复制完就断开联系，两个变量于是成了普通字符串和普通数字。它的底层是响应式系统，而解构恰好绕开了这条依赖。

更隐蔽的是数组或对象字段：const { items } = cart 拿到的是被代理过的引用，对它 push 仍会触发更新；但一旦用 $patch 整体替换 items，局部变量仍指向旧数组，界面就静止不动。

正确写法交给 storeToRefs，它把 state 与 getter 逐字段转成引用，同时刻意不包含 action。

省心的约定是：解构只走 storeToRefs，需要方法就保留 cart. 前缀。整块修改优先用 cart.$patch，把多处改动合并成一次可回溯的变更。另外 $reset 只在 Options Store 上自带，Setup Store 要自己写恢复逻辑。

store 之间的组合与循环依赖

store 之间互相引用是常态：结算要读购物车，也要读当前用户。做法朴素，在需要的地方调用对方的组合函数。

循环依赖要提前认识。若 cart 用到 user、user 又用到 cart，模块级互相 import 会让某一方的组合函数在自身模块求值完成前被访问，调用时拿到未定义的值；更麻烦的是 getter 求值时机不定，可能在还没有活跃 pinia 实例的阶段创建对方 store，初始化时报出与实例未安装相关的错误。报错行号往往指向一个看起来完全正确的 import。

规避手段排三条。第一，把跨 store 的读取放进 action，让依赖在运行期才解析。第二，给依赖定方向：数据型 store 不反向依赖业务型 store，需要通知时用 $subscribe 或参数回传。第三，两个 store 只是共用一段算法时，抽成组合式函数。

抽取时要注意：组合函数的局部状态每个调用点各一份。这个例子只接收参数、只返回派生值；若函数里写了 const loading = ref(false)，那份 loading 并不共享，把它当“共享逻辑”引进 store 会让两边各转各的圈。

订阅与持久化插件

订阅是独立状态库换来的收益之一。$subscribe 在每次状态变更后触发，回调能拿到变更描述：$patch 传对象时 payload 是那份对象，传函数时是 undefined，因此适合落盘与变更计数，不适合精确回放。$onAction 挂在方法调用上，可以注册成功与失败之后的钩子，适合统一埋点、耗时统计与错误上报。

持久化是最常见的插件：给 store 挂上落盘与恢复逻辑，业务代码不感知。下面的实现用版本号处理结构变更，只对白名单内的 store 生效。

注册时按业务挑 store，写成 pinia.use(createPersistPlugin(['cart', 'preference']))。令牌与手机号这类字段不要落盘，若它们和偏好写在同一个 store 里，说明划分得不对。结构升级时先升 VERSION，旧结构的迁移写成一次性读取分支，读完即删。

SSR 与水合、组件测试

服务端渲染的第一原则是每个请求一套实例：createPinia() 要写在应用工厂内部随请求调用，否则两个用户的状态会互相串。渲染结束时实例上的 state.value 是普通可序列化对象，JSON 化注入 HTML；客户端新建实例后，在水合开始前把这份数据写回 state.value，首个 useXxxStore() 就能拿到一致的内容。

按需创建也有代价。只有服务端渲染路径上真正用过的 store 才出现在序列化结果里；只在客户端出现的组件所依赖的 store，状态不在 HTML 中，客户端会退回定义时的初值。若组件在初值下渲染出不同结构，水合阶段就会不匹配。稳妥做法是让参与首屏的 store 在服务端被调用一次，或给初值设定不改变渲染分支的保守默认。state 里也不要存放无法 JSON 化的值。

测试组件时不要 mock 整个 store 模块：它只是返回固定值的壳子，内部字段一改名，测试仍然通过却不再检验任何东西。更好的方式是装上真实 pinia 再预置状态：挂载选项传入 global.plugins: [createPinia()]，挂载前调用 useUserStore() 把 vipLevel 设成用例关心的值，再断言界面分支。测 store 自身不需要组件环境，用 setActivePinia(pinia) 激活后即可直接调用 action，beforeEach 里重建实例就能隔离用例。只想隔离网络请求时，把请求层抽成可注入的函数。

需要避开的反模式

  • 巨型 store。一个文件塞着四十个字段，服务五个互不相关的页面，每次改动都要确认其余页面没被牵连。切分依据是“会一起变化的数据”，不是“同一个页面用到的数据”。
  • 把服务器数据当唯一真相。返回结构、分页游标、缓存时间戳原样进 state，全局状态变成第二层数据库。缓存交给数据访问层，全局状态只留界面需要的最小投影。
  • 在 store 里直接操作 DOM。action 里滚动元素、给节点加类名，就把状态层和页面结构绑死了；在没有 DOM 的测试与渲染环境里会直接失败。视图细节交给监听状态的组件自行处理。
  • action 之间隐式依赖。一个 action 默认“前面有人调用过另一个”留下了中间变量，调用顺序一变就静默出错。前置数据要么显式传入，要么在 action 内检查并补齐。

小结

Pinia 用三层概念覆盖全局状态的常见需求：state 提供唯一可变来源，getter 承担派生计算，action 承担有副作用的编排。它把两步提交换成一步赋值，把模块注册换成显式 import，把类型对齐从手工声明换成从返回值推断。两条纪律要记住：解构 state 与 getter 必须经过 storeToRefs，跨 store 的依赖尽量放进 action 里解析。边界判断始终是共享范围与生命周期，而不是数据看起来重不重要。

场景 推荐做法 注意事项
单个弹窗的开关 组件内局部 ref 别为以后可能用到而提前放全局
登录态与用户偏好 独立 store，字段精简 敏感字段不进持久化白名单
列表请求与分页 action 拉取，状态含加载标记 只留界面需要的最小投影
深层组件读同一字段 storeToRefs 后解构 直接解构失响应
两个 store 共用算法 抽成组合式函数 函数内 ref 不跨调用点
结算依赖购物车与用户 在 action 内解析依赖 避免模块级循环引用
埋点与变更审计 $subscribe 与 $onAction 上报字段需脱敏
服务端渲染首屏 序列化状态后客户端回填 每请求新建实例，水合前完成
