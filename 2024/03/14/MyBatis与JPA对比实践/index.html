MyBatis 与 JPA 对比实践

本文把 MyBatis 与 JPA 放在同一个需求下对比：同一条订单查询，两边第一版怎么写、坑在哪、改动量落在谁身上。读完能得到一套按场景选型的判断依据，以及两套框架共存时的落地方式与代价，适合正在选型或同时维护两套数据访问层的读者。口径是 Spring Boot 3.2、Jakarta EE 命名空间（jakarta.persistence.*）、Hibernate 6.x、MyBatis 3.5.x 与 mybatis-spring-boot-starter 3.x，运行时按 Java 17 或 21 考虑。

两种定位：SQL 优先与对象优先

差异不在语法，而在控制权交给谁。MyBatis 是 SQL 优先：你把 SQL 写清楚，框架把结果集装进对象，执行计划的每处细节都在掌控里，代价是表与对象的关系要靠映射文件维护。JPA 是对象优先：你把模型说清楚，声明实体、字段与关联，SQL 由 Hibernate 在调用查询或提交事务时生成，代价是你要理解它什么时候生成、生成什么。

需求基准很常见：按用户、一组订单状态与时间范围查订单列表，并带出订单明细行。

差别立刻显形：MyBatis 侧已经在处理 join、列别名与分页参数，一次把列表和明细取全；JPA 侧的 Page<Order> 只返回订单根，明细要么走懒加载，要么显式加图查询。反过来，JPA 的模型是常驻的，写订单、改状态能直接复用实体，MyBatis 每类写操作仍要一条语句。复杂度走向由此确定：一边堆在 SQL 与映射文件里，一边堆在实体图与刷新时机里。

分页、排序与深分页

分页是方言差异最集中的地方，MySQL、PostgreSQL、Oracle 与 SQL Server 的写法各不相同。MyBatis 里这一层要么按目标库写死，要么交给插件改写，后者发生在你看不见的位置，连 count 语句也是改写出来的。JPA 侧 Pageable 只描述页码与排序，方言由 Hibernate 按 Dialect 处理，换库不动代码。代价同样真实：count 由框架生成，遇到 join 或分组时会套一层包裹，开销一点不比手写小；列表要排序而 count 不需要时，必须显式提供 countQuery。

join fetch 与分页放在一起是经典陷阱：一条订单十行明细时，limit 20 截的是 join 后的行，不是 20 个订单。要么拆两次查询，先分页取主键再批量取明细。深分页两边都无解：limit 1000000, 20 与 PageRequest.of(50000, 20) 都要先读过前面的行，JPA 还多一次全量 count。可行的做法是游标式分页，用上次的排序键做边界：

N+1 与懒加载的真实代价

N+1 不是某一方的毛病，而是按根取子这种加载方式的必然结果，两边只是触发时机不同。

JPA 的关联默认懒加载，order.getItems() 返回代理，第一次访问集合才发 SELECT。列表 50 个订单、循环里各访问一次，就是 1 条主查询加 50 条子查询。三种解法各有边界：

join fetch 适合确定一次取全；@EntityGraph 适合同一方法服务多种加载需求；@BatchSize 是侵入最小的兜底，它承认二次查询存在，只是让它变便宜。

再说序列化为什么炸。控制器直接返回实体时，Jackson 写 JSON 会调用所有 getter，代理的 getter 一被调用就触发加载；持久化上下文若已关闭，抛的就是 LazyInitializationException。更糟的是它有时不抛异常而是真的去查库：spring.jpa.open-in-view 默认打开，请求线程全程持有会话，序列化阶段能悄悄补发几百条查询，只表现为接口慢。做法是把它设为 none，让加载留在服务层，出参改用 DTO 或投影。

MyBatis 的两种写法对应两种风险。嵌套结果一条 SQL 搞定，没有 N+1，但行数是笛卡儿积，父表字段随子行数重复传输；更隐蔽的是它依赖 <id> 声明，漏写时相同父行会被拆成多个对象。嵌套查询把 N+1 摆到明面上：

它默认不发二次查询：只有开启 lazyLoadingEnabled 并配合字节码增强才是懒的，否则嵌套查询就是明晃晃的 N+1。方向与 JPA 相反，JPA 默认懒、要显式提速，MyBatis 默认逐条查、要显式改成 join。

缓存的粒度与失效陷阱

MyBatis 一级缓存挂在 SqlSession 上，同会话内相同语句加相同参数直接复用对象。看着免费，实际最容易踩：Web 层每请求新开会话，命中不了；事务内同一会话，UPDATE 之后再读，只要语句与参数一致拿到的仍是旧对象，它更像会话内的对象一致性保证。

二级缓存以 namespace 为单位，用 <cache/> 开启：

三个失效陷阱要单独点出。第一，失效范围是整个 namespace：本 namespace 里任何一条写语句都会清空该 mapper 的全部条目，粒度粗得超乎预期。第二，跨表不失效：更新 t_order_item 不会惊动 t_order 的汇总缓存，因为后者属于另一个 namespace。第三，同一批数据被两条语句查询时，缓存里是两份互不知情的条目。

分布式部署下，二级缓存是每个 JVM 进程一份的本地状态。节点 A 写、节点 B 不会失效，读到的仍是旧数据，只能靠 flushInterval 给一个最长陈旧窗口的上限。正确预期是：它只适合变更极少、允许短暂陈旧的字典与配置类读场景，且要么单实例、要么接受不一致窗口。把它当性能加速器的项目，最后多半改用 Redis 显式读写。

JPA 侧同名但含义不同。一级缓存就是 PersistenceContext：事务内同一主键只加载一次，价值在对象身份一致与脏检查，不在命中率。二级缓存是实体级（@Cacheable 加集合域），要显式接 provider 并配 region factory，按主键失效，粒度天然比 namespace 细。查询缓存只缓存主键列表、对 SQL 文本敏感、失效面大，多数团队直接跳过。现实定位是：Hibernate 6.x 的二级缓存收益集中在热点实体按主键反复读这类窄场景，跨节点共享要靠应用层显式管理。

也可以用 Tuple 或 @SqlResultSetMapping，但都是在为绕过对象的缺失写胶水。MyBatis 在这一带是天然优势：SQL 怎么写就怎么执行，动态列用 <if> 拼，列不固定时直接返回 Map。

报表走 MyBatis、CRUD 走 JPA 是能落地的，方式是两套数据访问层共存：同一个数据源、同一个 PlatformTransactionManager，实体与仓库和 mapper 分包放置。代价要写进设计文档。其一，JPA 的一级缓存看不见 MyBatis 的写，Hibernate 尚未 flush 的写 MyBatis 也看不见，同一事务里混用要先 flush 再查报表。其二，同一张表的列信息在实体注解与映射文件里各存一份，改名容易漏。其三，两套动态查询机制并存，新人不知道该写哪一种。顺带说明，连接池调优另有专文。

测试与结构演进成本

JPA 能把实体当作 schema 的来源，开发期确实省时间，但生产必须切到 none 让迁移工具按脚本走，否则一次实体改动的隐式 DDL 就可能锁表。MyBatis 没有这个幻觉：schema 与映射文件是两份独立资产，前者归迁移工具，后者归代码评审。

结构变更时的改动量差异明显。给 t_order 加一列：JPA 侧改实体加一个字段一个注解，查询与写路径自动跟随；MyBatis 侧要动 resultMap、动 select 的列清单，可能还要动 insert。反过来，把过滤条件从 status 改成 status 加 channel：MyBatis 改一条 SQL，影响面就是这条 SQL；JPA 侧要确认所有复用该实体的派生查询与 Specification，改动是模型级别的。删列、改类型这类破坏性变更两边都得把全部语句过一遍，只是 JPA 有一半语句是生成的。

测试策略上 JPA 的优势是可分层：Specification 与领域方法做纯单元测试，映射与查询用 @DataJpaTest 起切片上下文，再配容器化数据库跑集成测试。MyBatis 侧语句逻辑靠 Provider 可以单测，XML 里的 <if> 分支只能起会话跑，常见做法是给它单独的测试切片连同一个测试库，为每条动态 SQL 的分支各写一条断言。混用时测试基线必须统一：同一套容器数据库、同一套迁移脚本、同一份种子数据。

团队因素与选型判定

技术差异之外，决定长期成本的是团队条件。有 DBA 审查文化、要求每条上线 SQL 逐条评审的团队里，MyBatis 的映射文件本身就是审查材料，JPA 生成的 SQL 要先抓出来才能审，流程上天然别扭。领域模型复杂——聚合根多、不变式严格、状态迁移依赖级联语义——JPA 的对象图与脏检查能省掉大量手工维护。反过来，遗留库表不规整（联合主键、无主键表、一列塞多值、宽表列数上百）时，实体建模要先付一大笔。

判定维度 选 MyBatis 的信号 选 JPA 的信号 需要注意的混合方式
SQL 控制权 要逐条审查与手工调优 接受框架定执行计划 报表走 mapper，别再用实体查一遍
动态查询 分支贴近 SQL 语义 条件可按属性组合 只留一套动态机制
关联加载 关联只在个别查询需要 对象图多处复用 懒加载靠 DTO 收口
写入批量 自己管执行器与 flush 主键策略允许攒批 IDENTITY 会让批量退化
结构演进 变更集中在少数查询 字段频繁增减 迁移脚本统一
缓存 接受 namespace 粒度 要按主键粒度缓存 跨节点一致性另做
团队条件 有 DBA 与 SQL 文化 建模能力强 分包与事务边界入规范

小结

本文的对比可以收成一句话：MyBatis 让 SQL 成为一等公民，复杂度堆在映射文件与语句维护上；JPA 让模型成为一等公民，复杂度堆在加载策略、刷新时机与主键策略上。选型按场景走：报表密集、需要逐条审查 SQL，MyBatis 收益直接；写模型复杂、字段频繁增减、团队擅长建模，JPA 省下的样板代码实在。混合是常态，但要付三笔账——映射重复、flush 与缓存的可见性、新人不知道该写哪种。最容易翻车的两处：被 getter 唤醒的懒加载，以及 IDENTITY 主键下形同虚设的批处理。
