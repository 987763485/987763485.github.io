Kotlin 协程源码解析

挂起函数写起来像顺序代码，跑起来却几乎不占用线程，这中间的落差全靠编译器改写和库里的调度机制补齐。本文不做 launch、async 的用法教学（选型与 API 用法已在另一篇协程入门里写过），而是从实现机制往回看：编译器把一个 suspend 函数变成了什么，调度器在哪个方法上接进来，Job 如何用一个字段表达五六个状态，取消、异常、背压又分别落在这套机制的哪一层。读完之后，你应该能在一次协程 dump 或一段挂起栈里，认出每一帧对应的实现意图。口径是 Kotlin 1.9.x 与 kotlinx.coroutines 的 1.7/1.8 线；凡是涉及内部类名、字段名的地方，都以当时的公开源码为准，命名可能随版本变化，思路不变。

挂起到底挂起了什么

先厘清一个容易混淆的层次：调用栈属于线程，不属于协程。一个线程一条调用栈，栈帧里存着这个调用的局部变量、操作数栈和返回地址。当一个函数阻塞时，真正被占住的是线程本身、它那按兆预留的栈空间，以及它在线程池里那个不可分割的槽位。这就是阻塞式线程模型贵的原因：并发数由线程数决定，而线程数是操作系统资源，扩不动。

挂起做的事，是把”还没执行完的那半截”从栈上搬到堆上，然后让栈直接展开。函数返回，线程被归还给调度器；剩下的状态变成堆上一个普通对象，等别人来恢复它。所谓 Continuation，就是”剩余工作”这个对象的标准形式，它只有两个成员：一个 context 说明这次恢复该带什么上下文（其中就包含调度器），一个 resumeWith 接收结果或异常并继续往下跑。

三个点值得停一下。第一，挂起函数的返回类型在字节码层面是 Any?，因为一次调用要么给出真实结果、要么给出 COROUTINE_SUSPENDED 这个哨兵；基本类型因此会被装箱，这是状态机方案的固有成本之一。第二，拿到哨兵之后，调用方不能碰返回值，它不是结果，而是”请等回调”的信号。第三，resumeWith 可以在任何线程上被调用，协程本身对”谁叫我”没有要求，这个自由后面会变成取消迟到和栈溢出的源头。日常代码不该手写这些，suspendCoroutine 之类的封装只是把这套协议收拢成安全形状；见过裸协议，才知道包装在保护什么。

于是”每个挂起点变成一次跳转”这句话有了具体所指：label 是唯一需要持久化的程序计数器，局部变量提升成字段是为了在栈销毁后继续存活，挂起函数的每次调用都被改写成”传入 this、检查哨兵、决定 fallthrough 还是返回”。这里有个常被忽略的优化：如果被调用的挂起函数实际上同步就算完了（没有真正挂起），label 分支直接往下走，一次调度都不会发生，整段代码在同一个线程同一个栈上跑完。快路径与慢路径性能差别不小，也是”挂起不等于一定切换线程”的根据。

理解到这层，几个现象就顺了：协程对象是堆分配，上万数量也只是普通小对象；suspend 传染性的根因是 CPS 改写必须在编译期知道续体往哪传，不是风格洁癖。

调度器如何接上协程

两个方法就是全部接入点

ContinuationInterceptor 同时是 CoroutineContext.Element，有自己的键，所以一个协程上下文里最多只有一个调度器；Job、CoroutineName、CoroutineExceptionHandler、自定义的线程上下文元素与它并列成一条小链表。调度动作被压缩在两个方法上：interceptContinuation 在协程开始前把裸续体包一层，返回的包装对象知道”恢复我该往哪个队列投”；dispatch 才真的把任务交出去。恢复路径因此是：外部线程调用包装类的 resumeWith，它先看 isDispatchNeeded，需要就 dispatch 把任务排进队列，工作线程稍后取出执行，最终才落到 invokeSuspend；不需要就同线程直接继续。用完后包装对象通过 releaseInterceptedContinuation 归还，内部有对象复用以削掉每轮恢复的分配。

把这条链画出来，”协程在哪个线程上跑”就有了确定答案：不是 launch 时一次定死的，而是每次恢复重新走一遍判断。

flowchart TD
    A[外部线程调用 resumeWith] --> B{isDispatchNeeded}
    B -->|是| C[dispatch 投递到调度器队列]
    C --> D[工作线程取出任务执行]
    D --> E[调用 invokeSuspend 按 label 继续]
    B -->|否| E
    E --> F{是否遇到挂起点}
    F -->|是| G[返回 COROUTINE_SUSPENDED]
    F -->|否| H[产出结果并结束]

调度器族谱与各自的取向

Dispatchers.Default 面向 CPU 密集型短任务：一组数量与处理器规模挂钩的工作线程，本地队列加全局队列，配合窃取式的取任务策略，线程复用充分，切换少。Dispatchers.IO 复用的是同一个调度器的实现骨架，但它额外管着一份”阻塞型任务”的额度，允许在等数据库、等网络的时候开出远多于处理器数的线程，靠可回收的线程上限兜住不失控。两者分开的原因不是历史包袱，而是取向冲突：让”什么也不干只在等”的线程去挤 CPU 任务的调度名额，或者让计算任务把等待额度吃光，都是坏事。Dispatchers.Main 是薄封装，只把任务交给平台的事件循环（Android 上落到 Handler），本身不提供并发，这也解释了主线程上挂起密集的循环为何会卡界面。Dispatchers.Unconfined 不做投递，谁调用 resumeWith 就在谁的线程和调用栈上继续跑，还带着当前线程的上下文，属于”我知道我在做什么”级别的选项。

社区常提到的 trampoline 调度器在公开 API 里其实没有对应物，真正承担这个语义的是 runBlocking 自带的事件循环（当前线程自己消化恢复，不外抛）以及 Unconfined 那条非投递路径；Main.immediate 则在主线程匹配时省掉一次重投递。顺带一句，当时仍标着实验性质的协程标识元素 CoroutineId 只影响线程名与 dump 输出，不改变投递目标，不要把它当调度器来做选型。

启动方式决定第一次谁来调用 invokeSuspend

CoroutineStart 四个枚举值的差别，全部体现在”是否生成一个待执行任务””是否立刻在当前线程进入状态机””取消能不能阻止它开始”这三件事上。

启动方式 是否投递任务 第一次执行位置 开始前被取消 典型语义
DEFAULT 是 调度器的工作线程 不启动，直接终止 常规写法
LAZY 否 显式 start() 或 join() 时决定 不启动 攒着批处理
UNDISPATCHED 否 调用者线程，立即跑到第一个真挂起点 不启动 想省一次投递
ATOMIC 开始后再投递 调用者线程，立即开始 仍会启动 不让取消抹掉这一步

未启动的协程在实现里并不特殊：状态机对象已经建好、挂在 Job 上，只是调度队列里没有对应任务，Job 停留在新建状态。所以在 dump 里它以 NEW 形态出现，而不是”不存在的协程”。dump 里一堆 NEW，多半是协程创建了没启动，或在启动前就被取消。

作用域与作业的内部结构

CoroutineScope 这个接口在实现上轻得出奇：它只有一个 coroutineContext 属性。它不调度，不持有线程，也不管队列，它唯一的贡献是回答”从这里启动的协程，父作业是谁”。把作用域当成生命周期容器来理解是对的，但要清楚这个容器由 Job 撑起，而不是由 CoroutineScope 本身撑起。

真正的实现集中在 JobSupport 上。它用一个引用字段承载全部状态，靠不同的取值形态编码不同的状态：字段为空表示刚创建、尚未启动；字段指向一个不可变节点链表表示正在运行，链表里挂着子作业引用和完成后的回调节点；链表中出现取消标记表示正在取消；字段指向一个完成状态对象表示已经进入终态，对象里存着失败原因或”正常完成”这个事实。所有迁移都在一个 CAS 循环里完成，没有锁，因此读 isActive 便宜、并发创建子协程也不会有明显的争用放大。代价是可读性差，抓住”一个字段、四种形态”这条线就够了。

父子关系就存在那个节点链表里。子协程挂到父作业的链表上，父作业记着所有孩子；孩子只记一个父引用，方向是单向的。由此产生两条确定行为：父进入取消时，遍历链表逐个通知孩子，一层层往下级联；孩子在异常完成时，把失败原因交给父去裁决。同时，一个作业只有自己这段逻辑跑完、并且所有子作业都进入终态之后，才算真正完成，中间那个”自己完了但还在等孩子”的状态在实现里是独立存在的，它保证 join 的语义不会在孩子还没收尾时就返回。

flowchart TD
    N[新建] -->|启动并投递| A[活跃]
    N -->|启动前被取消| X[已取消]
    A -->|自身逻辑结束| C[完成中]
    A -->|调用 cancel| G[取消中]
    C -->|全部子作业进入终态| D[已完成]
    G -->|子作业继续级联| G
    G -->|全部子作业进入终态| X

这张迁移图解释了两类常见困惑。第一类是”我明明 cancel 了，join 却没返回”：取消中这个中间态会一直等到最后一个孙作业落定，只要有一个孩子卡在不可中断的调用上，父就停在中间态。第二类是”join 返回不代表成功”：join 只等终态，不区分已完成与已取消，真正判断成败要用带结果等待的方式。把状态迁移记牢，这类现象就不需要靠猜。

取消是如何传播的

调用 cancel() 时实现做的事情很朴素：把取消原因写进状态字段，CAS 把链表换成带取消标记的形态，然后遍历子节点通知下去，最后把已经挂起的续体用 CancellationException 恢复。注意它没有做的事：它不打断线程，不回滚调用栈，也不撤回已经投递出去的任务。取消纯粹是”改写一个状态，然后在合适的地方让状态被看见”，这就是协作式取消的全部含义。

那个”合适的地方”就是取消检查点。显式检查点是你自己写的 ensureActive()，它读一次状态、发现取消就抛异常；隐式检查点是挂起本身，协程在恢复时会先看作业状态，如果已经取消，这次恢复的结果会被替换成 CancellationException，状态机因此直接走向异常出口而不是继续执行 label 后面的分支。一个循环里如果既没有挂起点也没有显式检查，它就永远不会注意到世界已经变了。

于是”取消迟到”就有了准确的解释。如果你的挂起函数中间夹了一段不可取消的阻塞调用，同步 socket 读、老式 JDBC、JNI 里的等待，那么在它返回之前不存在任何检查点，取消原因只能静静躺在状态字段里；它一旦返回，检查点才第一次被踩到，协程才退出。更要紧的是，这段期间线程被真实占用，你以为已经释放掉的并发额度还在消耗。实现上能给的补救有限：把阻塞调用交给 Dispatchers.IO 并给它自己的超时，让取消至少不是唯一的止损手段；对于本身响应中断的调用（线程睡眠、可中断的 NIO 读），用 runInterruptible 这一类桥接，把中断翻译成 CancellationException，让检查点在阻塞结束的第一时间生效；至于既不响应中断也没有超时的第三方同步客户端，协程层面无解，只能在它自己内部配超时。

还有一个反复出现的坑值得从实现角度说清：CancellationException 在协程里是控制流信号，不是业务错误。粗心地写 catch (e: Exception) 把它吞掉，后果是这次协程以”正常完成”的形态落进父作业，取消级联在这一层被截断，其他兄弟协程继续运行，资源回收和 join 全部对不上账。要么别捕获异常，要么捕获后原样重新抛出取消。

withContext 的切换与回传

withContext 常被念成”切线程”，实现上它做的是另一件事：让同一个协程带着新上下文继续。它被编译成一个普通挂起点，动作拆开是三步。第一步，把当前续体按目标调度器做 interceptContinuation 包装，然后 dispatch 一次，于是块体从目标线程开始执行；第二步，块体内所有挂起调用继承这个新上下文，包括其中的 Job（仍是同一个作业，父子结构没变）；第三步，块返回时结果沿另一个包装续体投回原上下文，调用点之后的代码回到原来的调度器上。切换的开销因此只在边界那两次投递，块内的挂起不会来回穿越。

快路径值得单独说。如果目标调度器和当前调度器是同一个，或者它表明不需要调度，实现会走一条不投递的分支，直接在当前线程当前栈上把块跑完，省掉排队与唤醒。同一条规则还管着线程本地状态：上下文里实现了线程上下文搬运接口的元素（典型是把 ThreadLocal 装进去的那些）会在恢复前后各搬一次，这解释了为什么切到别的线程后 MDC、上下文 ClassLoader 这类东西会丢，也解释了为什么把它们做成上下文元素比手写 try/finally 可靠。

取消与异常的传播在 withContext 上是双向的，这一点和 async 有实质区别。块体内抛出的异常会作为失败结果恢复外层协程，父作业看到的仍然是一个协程的失败；反过来，外层协程被取消时，withContext 会把取消直接送进块体，它构成一个可取消的边界，块体不会变成孤儿。async 则新建一个孩子作业，取消父作业会级联到孩子，但孩子的失败默认要等 await 才在外层显现，两者的传播形状不同。这也是为什么”包一段阻塞调用然后能取消”的正确写法是 withContext(Dispatchers.IO)，而不是随手起一个 async 再等它。

Channel 的缓冲与挂起队列

Channel 的骨架可以记成三张表：一块缓冲、一串等待发送的续体节点、一串等待接收的续体节点。send 的判定顺序是：如果接收侧有人排队，直接把值交给队首那个等待者并唤醒它，这次发送连缓冲都不进；如果没人等但缓冲有空位，值入缓冲，发送方立刻返回；两者都不成立，发送方把自己的续体连同这个值一起包成节点排进等待队列，返回 COROUTINE_SUSPENDED。receive 对称：缓冲里有值就取，没有就把自己排队。所谓缓冲区大小，实现上就是”第二条表和第三条表允许同时为空到什么程度”。

由此能推出两个不那么直观的行为。其一，rendezvous 类型的 Channel 每次交接都要两侧同时在场，生产与消费被天然串起来，吞吐受配对速度限制；加了缓冲后，交接发生在”写入”与”读出”两个时刻，代价是值在内存里多待一会儿。其二，把缓冲配成满时丢弃而不是挂起，实现只是把判定从”排队等待”换成”覆盖某一端”，溢出策略之间并没有多出新的同步点。

还有一个容易看漏的细节：挂起的 send 被唤醒不代表发送成功，原因可能是对端取走了值，也可能是通道被关闭。所以实现里 send 在恢复之后会重新检查一遍状态，不成功就再走一轮挂起，而不是假定”醒了就是成了”。挂起的 receive 同理。

onSend 与 onReceive 这两个钩子解释的是另一层：真正传输成功的那一刻，实现允许你把”登记这次成功”这件事做成一个可能挂起的步骤。有了这两个插槽，多路等待才能被组合起来，因为每个分支都清楚”我这一路成功后需要补做什么”。反过来，把 onSend 写得阻塞或抛异常，会让一次已完成的交接在语义上变形：这类钩子该做记账，不该做业务。

顺带一句和 Mutex 的关系，它的实现形状和 Channel 高度相似：一个状态字段表达”锁在谁手上、有没有人排队”，加锁失败就把续体排进等待队列，解锁时不是”释放后大家重新竞争”，而是把所有权直接交给队首。因此它是公平且不可重入的，配合 withLock 时取消处理也更干净。把它当成”缓冲区大小为零、元素是许可凭证的通道”来理解，实现层面基本不会错。

Flow 的上下文约束与背压实现

Flow 的接口面窄到只有一个挂起方法：FlowCollector 的 emit。这个形状决定了整套实现。flow { ... } 构建出来的对象里没有任何队列、没有后台生产者，它装的是”一段可以被反复调用的挂起逻辑”；collect 每次被调用，就把这次传进来的 collector 交给那段逻辑，从头执行一遍。冷流不是设计偏好，而是这个结构的必然结果：没有人在你不调用的时候替你生产数据，同一段逻辑对不同的 collector 就是不同的执行现场。

也正因为 emit 的实质是”直接调用下游”，跨上下文转流会破坏整套语义，所以实现里放了一道检查。收集开始时记住当前的收集现场，emit 时发现调用者不是那个现场就报错，报错大意是”Flow 的实现被限制在同一个收集上下文中使用”。它防的是这几类写法：在 launch 里往外 emit、用回调式 API 包装却把 emit 丢到别的线程、在 flowOn 之后的下游又反向发射。这些写法真正的危害在于：取消信号、异常归属和背压原本都靠这条同栈调用链传递，一旦中间换成队列，链就断了，而编译器不会提醒你。调试模式下抛出的是可识别的专用异常类型，便于在日志里看出根因在收集现场而不在下游。

背压在这套结构里是免费的，而且是”零缓冲”意义上的免费：emit 挂起多久，生产者就等多久，消费者的慢会原样顶回去。所谓 buffer 和 flowOn 的实现效果，是把这条同栈链换成一段通道：它们构建的是通道型流，内部起一个生产者协程去 collect 上游，把取到的值塞进一个通道，下游从通道另一头取。于是 buffer(n) 就是那个通道的容量，flowOn(dispatcher) 就是”生产者协程换成目标上下文，并默认带一格缓冲”。几个现象因此不奇怪：缓冲把生产与消费在时间上解耦，代价是多占内存、异常与取消需要跨通道搬运；flowOn 之后上游不再能借用下游线程；try/finally 在这种带通道的流里守护的是生产者协程的生命周期，和纯 flow 里的顺序语义并不等价。

异常为什么要交给父作业

一个子协程里抛出的未捕获异常，在实现上不会被就地处理，而是被写进它的作业状态，然后交给父作业裁决。这不是偷懒，而是唯一一个在并发结构里说得通的位置：只有父知道这个孩子还有哪几个兄弟、这段逻辑整体算不算失败、要不要一起收掉。于是标准行为是固定的三步：孩子以异常原因终止，父把失败转成对整个子树的取消，取消按前面讲的级联机制铺到其他孩子，最后这个原因继续沿树往上走。

handleCoroutineException 站在这条链的终点。当异常上行到没有父作业可交的那个协程时，它才开始工作：先在协程上下文里找 CoroutineExceptionHandler 元素，找到就交给它；找不到就退回平台的未处理异常路径，在 JVM 上是线程的未捕获异常钩子，在 Android 上会经由主线程分发出去。这条规则解释了一个每天都在重复的现象：把 handler 放进独立的顶层协程能兜住异常，放进某个有父作业的孩子里却根本不触发，因为异常在上一层就被父作业消化成取消了。想让孩子失败可见，要么父作业是监督型的，要么在那个孩子的上下文里就有能消费异常的东西。

supervisorScope 在实现上的差别只有一处判定，但效果很大：监督型作业对”孩子的失败要不要我接管”这个问题回答否定，失败因此不向上回传，父不取消，兄弟不受影响。被切断的只是上行的失败传播，下行的取消一如往常，父作用域被取消时所有孩子照样收到取消。还有一点容易忘：监督型作用域在自己完成之前，仍然要等所有孩子进入终态，无论成败。代价是失败孩子抛出的异常只能靠它自己的上下文里的 handler 或平台日志暴露，所以在监督结构里，每个孩子的错误处理不是可选项而是必选项，否则线上只剩一行无人认领的堆栈。

调试能力、实现代价与速查

开启 kotlinx.coroutines.debug 这个 JVM 属性之后，实现额外做三件事：给协程分配可打印的标识，把线程名写成”调度器名加协程编号”的样子，并在异常日志后面附一段这个协程经历过的挂起调用序列。那段序列不是真实的 Java 调用栈，它是从续体链上一路读上下文与栈帧拼出来的，因此能看到”这个协程在哪一行 launch、当前卡在哪个挂起函数”，但看不到中间已经返回的帧。一段典型挂起栈的形态大致如下（帧名以当时版本为准）：

把这篇的内容收束成一句话：协程没有让调用栈消失，它只是把”等待”表达成了堆上的对象和队列里的任务，把”取消”表达成了一个状态位，把”父子”表达成了一条节点链表。机制都摆在明处，剩下的只是你愿不愿意在排查时去读它们。

小结

读完实现层，有三个判断可以带走。第一，挂起不是阻塞：线程被释放、续体进堆，这是所有”协程省线程”说法的真正来源，也是它排查更难的来源。第二，取消是协作式的：状态位置上了，还要有人在下一次挂起点检查它，不可中断的阻塞调用只能靠超时兜底。第三，结构化并发把异常与生命周期绑在父节点上，父在子才在，父败子先停。把这三条记住，读别人写的挂起函数时就不会被语法糖迷惑。
