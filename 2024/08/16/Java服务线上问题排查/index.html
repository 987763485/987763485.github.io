Java 服务线上问题排查

线上出问题的时候，最缺的往往不是知识，而是一套能照着走的流程。本文不谈 JVM 内存结构与回收器原理（见同批 JVM 内存模型与 GC 一文），也不做基准测试与参数实验设计（见同批性能调优一文），只解决一件事：告警响了，人按什么顺序动手、先留什么证据、在分岔口走哪条路、怎么把一次事故变成一条不复发的规则。适合值班同学与带值班的技术负责人读完就整理出自己团队的 runbook。

排查主线：四问与止血判据

固定顺序的四问

排查最有效率的姿态，是把问题压进四个按固定顺序回答的问题，而不是凭直觉翻日志。第一问是现象是什么，要求得到一个可证伪的指标变化：”订单创建接口的 P99 从基线抬到明显更高的位置””某台实例的用户态 CPU 持续超过阈值”，这类说法能被数据反驳；而”感觉变慢了”不是现象，必须先翻译成指标。第二问是时间窗：何时开始，是阶跃式起点（几乎一定有对应事件）还是缓慢爬升（多为累积型问题），是持续还是周期性——周期性抖动会把嫌疑直接推向定时任务、缓存批量过期、监控采集与备份窗口。第三问是变更：发布、配置中心推送、流量结构变化、上下游依赖的版本与容量，每一项都要有据可查，把变更单号与发布时间点写进排查记录，”我记得没改过”不算答案。第四问是指标哪一层先动：入口错误率、应用层延迟、中间件排队、数据库耗时、操作系统资源，最早偏离基线的那一层通常最接近根因。

顺序之所以固定，是因为前两问决定后两问的搜索空间。跳过时间窗直接看指标，会在几十条同时恶化的曲线里打转；跳过变更直接下结论，最常见的代价是把一个回滚就能收住的问题排查上很久。

先止血还是先定位

取舍要显式判断，判据是影响面与定位收益的比较。影响面大且不可控（核心链路持续失败、错误率还在上走、容量见底），先止血：摘掉异常实例流量、回滚最近发布、降级非核心功能、必要时限流保住主要路径。影响面小且稳定（单机、灰度批次内、无用户可感知失败），先定位：把现场固定住再动，否则重启之后没有第二次机会。

有一条硬规则值得写进值班手册：止血前必须留证据。摘流量、回滚、重启都会破坏现场，而动手前采到线程栈与关键指标截图，事后定位成本会下降一个数量级。下面这张决策流把这段判断固化下来。

flowchart TD
    A[告警或用户反馈触发] --> B{影响面是否覆盖核心链路且持续扩大}
    B -- 是 --> C[进入止血优先]
    C --> D[采四件套证据并留时间戳]
    D --> E[摘流量或回滚或降级或限流]
    E --> F[确认指标回到基线]
    F --> G[恢复后再做定位与根因]
    B -- 否 --> H[进入定位优先]
    H --> I[固定现场并记录当前参数]
    I --> J[四问依次作答]
    J --> K{能否形成可证伪假设}
    K -- 能 --> L[用最小代价验证单一变量]
    K -- 不能 --> M[升级到二线并保留现场]
    L --> N{假设被数据反驳}
    N -- 是 --> J
    N -- 否 --> O[修复并写入复盘]

开工前的现场准备

证据先于动作

规范的开工动作是把”四件套”一次性采齐并对齐时间戳：线程 dump、堆直方图、GC 日志片段、核心指标截图（入口 QPS、错误率、P99、CPU、内存、连接池）。四件套的价值全在”同一时刻”这个前提上，时间戳差开几十秒，后面就会出现线程栈里看不到阻塞、指标却显示延迟飙升的矛盾。建议在排查记录第一行写明基准时刻，之后每条证据都记它相对基准的偏移。

能不能 dump，要先确认三件事

堆转储是代价最高的手段，动手前逐项确认三件事。第一是暂停：把整个堆写成文件会带来明显的进程停顿，堆越大停得越久，对内有状态请求、对外挂着心跳与租约的服务，这个停顿可能直接触发连锁超时。第二是磁盘：dump 体积与存活对象量相关，量级上可到 GiB，写进容器可写层或宿主机关键分区很容易把磁盘打满，造成二次事故，落盘位置要提前确认剩余空间。第三是生命周期与可 attach 性：容器随时可能被驱逐重建，dump 留在容器文件系统里等于随容器消失；需要 attach 目标进程的转储方式在容器里还可能因权限、ptrace 限制或用户 ID 不匹配而失败，此时改用 jcmd 的堆转储能力或让 JVM 在错误发生时自行落盘更稳。

默认次序因此是：先 jstack 与堆直方图（代价小、信息密度高），再判断是否真的需要完整堆转储；需要时优先用 -XX:+HeapDumpOnOutOfMemoryError 配合 -XX:HeapDumpPath，把”人为决定 dump 时机”变成预先安排好的自动动作。

容器环境里的取证与安全边界

容器里拿 dump，要点是限量、落到受控位置、尽快搬离易失层：用挂载卷或宿主目录承接，别写进镜像层与临时可写层，确认路径的容量上限与权限，生成后立刻搬到团队自有的受控存储并按数量做保留。这里有一条必须写进流程的红线：堆转储含内存中的明文对象，包括口令、令牌、会话标识与用户数据。把 dump 上传到不受控的外部服务（在线分析工具、第三方网盘、公开对象存储桶、外部客服通道）属于数据合规事故，与故障本身同级甚至更严重，无论多急都不能做。MAT 这类分析工具应在内网本地运行，需要的样本走内部审批脱敏。

改环境前先记录当前参数

“先改一个参数看看”是最容易造成现场污染的动作。任何改动之前，把当前生效的参数原样留档：JVM 参数、环境变量、配置中心版本号、容器资源限额与副本数、连接池配置。一旦改过，就再也无法回答”故障发生时进程按什么配置运行”，而这个问题往往决定假设能否被验证；留档同时给回滚提供了准确基准。

CPU 打高的处置链

从进程定位到线程，再对齐到栈

CPU 高的标准链路是四步。第一步确认是哪个进程：用 top 或 ps 按 CPU 排序，确定是目标 Java 进程还是别的进程。第二步下钻到线程：top -H -p <pid> 列出该进程内线程的 CPU 占用（也可用 pidstat -t 观察每线程趋势），记下占用最高的线程号。第三步把十进制线程号转成十六进制，因为 jstack 输出里的 nid 用十六进制本地线程 ID，转错了就找不到对应栈帧。第四步取栈：jstack <pid>（或 jcmd <pid> Thread.print）后按 nid 搜索，看这些线程此刻在做什么。

拿到栈后按栈顶所在区域分四类判断。业务热点：栈落在自己应用的方法上且多次 dump 停在同一处，说明真在算东西；要连续采两三次栈（间隔几秒）再下结论，单次快照容易抓到偶然样本。正则与序列化：栈顶是正则匹配、JSON 序列化、加解密、压缩一类调用，往往是输入规模失控或模式回溯放大，处置方向是限制输入长度、把昂贵解析挪到异步或缓存。JIT 编译线程：栈属于编译线程且发生在启动观察窗内，这是预热，通常正常，不该朝业务方向查。GC 线程：高 CPU 来自回收线程，转入下一条分支。

整台机器 CPU 高但进程不高

这种形态说明消耗不来自这个 Java 进程的可见线程，方向要往外挪。先在同机其他进程里找：别的应用、监控与日志采集代理、安全扫描、备份或压缩任务、容器运行时自身。再看是不是被限额了：容器的 CPU 配额会让进程视角的占用看起来”不高”（被限流后调度延迟上升），此时指标形态是延迟抬升、错误率不变或轻微上升，CPU 曲线像封顶在一个平台值上，判据要看被限流的时间占比而不是利用率百分比。操作系统与网络侧工具见同批 Linux 网络诊断工具一文，这里只确认一件事：CPU 的消耗主体到底是不是我们那个进程。如果不是，就不要在应用代码里空转，把嫌疑交给同机或同集群的责任方。

GC 线程占用高就走回收分支

当高 CPU 线程集中在垃圾回收线程，或用户态 CPU 高同时伴随吞吐下降与延迟毛刺，就不要再找业务热点，直接转入内存这条线：先看堆各代占用趋势是否呈”回收后仍然很高”，再看是否短期内大量 Full GC。这一分支的判据见下文 GC 停顿一节。工具层面补一句：Arthas 这类在线诊断工具提供了按 CPU 占用取前若干个线程的用法（thread -n 这类形态）与 dashboard 总览，能在不写文件的情况下快速看线程状态分布，适合影响面大、不希望 dump 代价的场合先做一轮粗看；火焰图在这里只用于确认热点位置，采样与调优的方法论见同批性能调优一文。

线程阻塞与死锁

先学会读状态，再谈锁

线程问题的信息几乎全在线程栈里，但要按状态分类读。RUNNABLE 表示线程正在跑或在本机方法调用内部，包括阻塞在 socket read 上的网络等待——大量 RUNNABLE 且栈顶是 socket 读，本质是在等下游，不是 CPU 问题，这是最容易误判的一点。BLOCKED 是在等进入同步块。WAITING (on object monitor) 是线程在某对象上等待被唤醒，典型是等条件成立；TIMED_WAITING (parking to wait for ...) 是带超时的等待，多来自线程池取任务超时、锁的超时获取、超时控制的同步等待。两者含义不同：大量 WAITING (on object monitor) 而唤醒方永远不来，往往是通知逻辑缺失或丢失；大量 TIMED_WAITING (parking) 分散在各池的工作线程上，多数只是空闲线程等活，属于噪声，不该当故障证据。

大量 BLOCKED 指向锁内 IO，这是最有价值的判据之一：如果几十上百个线程卡在同一个监视器上，而持有该锁的那个线程栈顶是数据库调用、远程调用或文件读写，那就是”把慢操作放进了临界区”。这种形态的特征是：等待方数量随流量线性增长，持锁方的耗时决定了所有人的排队时长，止血方向是熔断降级与把 IO 移出锁，加线程数只会把排队挪个地方。顺带留意栈的附带症状：Too many open files、Cannot create new thread、栈行数异常稀少或 dump 被截断，分别指向文件描述符耗尽、线程数或内存不足导致创建失败、采证时进程已经不健康。

死锁段落怎么读

真死锁很好认：jstack 输出末尾会出现一段专门的死锁说明，写明 Found one Java-level deadlock，并给出互相持有与等待对方锁的线程以及所等待对象的地址。读这段不要只看它点名的线程，还要顺着栈往上确认它们被哪条业务链路调进来，才知道影响面。死锁要求成环，两个线程交叉持有两把锁是最小形态，下面这段可复现代码专门用来在预发环境验证告警能否真的识别出死锁。

怎么安全地在线上确认与上线

定位不能靠”等到出现为止”。安全上线的顺序是先有告警再取证据：给线程数、队列积压、接口超时率设团队约定示例级别的阈值（用相对基线的偏离比例而不是绝对数），告警触发后自动或手动采一份线程栈，把 BLOCKED 聚集情况与死锁段落归档。这样即使这一次没找到根因，也留下了”发生时刻的栈”这一决定性证据；反过来靠猜锁的顺序改代码，风险是把正确路径也改掉。本文只从”栈与状态怎么读”的角度使用并发工具，线程池参数与锁的 API 语义见同批 JUC 核心一文。

GC 停顿与频繁 Full GC：只走分支

GC 相关的排查，本篇只处理”看到什么形态、走哪条分支”，回收器机制与日志字段含义见同批 JVM 内存模型与 GC 一文。

起点是把两条时间线对齐：GC 日志的时间戳序列，与用户请求延迟（或错误率）的时间序列放在同一张图上看。只有当延迟毛刺与回收事件在时间上重合，才有资格把原因归给 GC；不重合就立刻回到线程、下游与 SQL 那几条分支。这一步要用观察口径描述，不要写”停顿多少毫秒”这类具体数值当作事实——不同堆大小、不同回收器、不同容器限额下的量级差别极大，把某个数字抄进结论里会误导下一个值班的人。判断标准是形态：延迟毛刺是否与回收事件一一对应、毛刺期间吞吐是否塌陷、恢复是否跟随回收结束。

趋势用 jstat -gcutil 看：以固定间隔采样若干个周期，观察年轻代、老年代、元空间各区的占用比例与年轻代、Full GC 的次数与累计耗时增长速率。两条分支很清楚：如果老年代在一次完整回收之后占用明显回落、而年轻代回收次数与晋升速率异常高，形态是”晋升过快”，方向是分配风暴、大对象直接进老年代、缓存批量写入、批量任务把短期对象推过了年轻代；如果老年代回收后仍维持高位甚至逐次抬升，形态是”回收不掉”，就必须走内存泄漏分支，继续调 GC 参数只是拖延时间。

周期性 Full GC 先查非代码因素：曲线呈现规整间隔时，优先核对定时任务与批处理的执行计划、缓存集中过期时间点、监控与指标采集的抓取周期、日志压缩与备份窗口、外部依赖的批量重连。这类问题用”事件时间叠加图”十分钟就能确认，比在 JVM 参数里试错便宜得多。若确认是堆内存在持续抬升，转入下一节。

内存泄漏：先证明，再定位

怎么证明”在泄漏”

泄漏的判断不靠某一刻的内存高，而靠三条曲线的形态。第一，老年代或堆已用内存的”底噪”逐级抬升：每次完整回收之后的最低点一次比一次高，这是最可靠的堆内泄漏信号；只看峰值会把正常的业务波动误判成泄漏。第二，进程 RSS 与堆使用量分离：堆曲线平稳而 RSS 持续上涨，说明增长在堆外（直接缓冲、元空间与类加载、线程栈、本地库、压缩与映射文件），继续在堆里找是浪费时间。第三，与流量无关：把 QPS 归零或压低之后内存不回落（且已排除正常的缓存保留策略），累积型证据就成立了。三条里至少满足一条再讨论”泄漏在哪”，否则很可能是容量不足或缓存设计问题。

堆转储的正确姿势

-XX:+HeapDumpOnOutOfMemoryError 与手工 jmap 的取舍在于时机与代价。自动落盘的好处是抓到失败瞬间的真实状态，不需要人在场，也不引入人为延迟；代价是只在 OOM 时触发，而许多慢泄漏长期不 OOM，只表现为延迟抖动与频繁完整回收。手工转储可选时机，但要接受明显停顿，堆越大越久，且要提前确认落盘路径的空间与权限。容器里限量有三个办法：堆上限与实际内存限额之间留出自有余量，避免转储过程中容器被限额杀掉；转储路径指向受控挂载卷而不是可写层；大堆场景先用堆直方图与对象计数缩小范围（jmap -histo:live 与 jcmd 的类直方图能力会触发一次完整回收，这一点要预判），确认嫌疑类别之后再付一次完整转储的代价。

MAT 里读什么

拿到 hprof 之后，先看支配树（dominator tree）确认”谁独占最多”，再按保留大小（retained size）排序。retained size 才是判据，对象自身大小（shallow size）只是那几个字节的开销；一个持有大集合的注册表对象自身很小，但它保留的整棵引用图可能占掉堆的相当比例，这种”体积在下游”的形态只能靠保留大小识别。定位到嫌疑对象后，用”到 GC Roots 的最短路径（排除弱、软、虚引用）”看它为什么活着：排除这一步很关键，因为很多缓存条目本身被软引用或弱引用包着，不排除时路径会绕到引用队列上，看起来像正常缓存机制持有，掩盖真正的强引用链条。

五类高频形态

一、无界本地缓存。成因：以对象实例或含可变字段的类型作 key，而 key 未正确覆盖 equals 与 hashCode，相同的逻辑键产生不同键实例，命中率极低、条目只增不减。确认：堆直方图里 key 类型的实例数与业务基数明显不匹配，缓存 Map 的条目数只涨不降。二、ThreadLocal 未 remove 且线程池复用。成因：线程不随请求结束而死，条目留在该线程的线程本地表里被一直持有。确认：保留大小的持有者是 Thread 与线程本地映射，数量与工作线程数成正比。三、监听器与回调注册未注销（服务端形态，与浏览器端 DOM 事件无关）。成因：每次初始化新对象都注册一次而从不反注册，注册表按事件类型累积。确认：监听器集合大小与请求数或对象创建数同向增长。四、静态集合当注册表。成因：用静态 Map 或 List 保存”所有实例”做协调或统计，生命周期与类加载器一致。确认：支配树上该静态字段独占大量内存，到 GC Roots 的路径经过类的静态字段。五、堆外泄漏，如直接字节缓冲、本地库分配与未关闭的流。成因：分配了不受堆上限约束的内存，却在异常路径上漏掉释放或关闭。确认：堆曲线平稳、RSS 上升而元空间不涨，此时看原生内存跟踪的汇总或缓冲池计数。

正确的写法是把 remove() 放在 finally 里由切面统一执行；只要线程存活，ThreadLocal 的值就不会因为不再被业务引用而自动回收。

堆外与元空间先看哪三块数据

先分清是哪一块在涨。三条数据源：堆内使用量（jstat -gcutil 的老年代列与 jcmd 的堆信息能力）、元空间占用（同一输出的元空间列，配合原生内存信息）、以及 RSS 减去堆的差值。差值持续增大而堆平稳，重点看直接缓冲、线程数量与栈大小、内存映射与本地库分配。-XX:MaxDirectMemorySize 要与容器内存限额一起看：直接内存不受堆上限约束，只设堆上限等于给容器留了一个不计入的缺口，形态是堆一切正常而容器被限额杀掉——这种”重启原因写在容器事件里而不是应用日志里”的现象容易被误判成基础设施问题。Netty 这类网络缓冲的泄漏表现也是堆稳、RSS 涨、连接数正常，确认办法是把它的泄漏检测采样调到更密集的档位，让框架自己打印分配站点，而不是靠猜哪段代码忘了释放。元空间增长多与动态类生成有关：反射代理、字节码增强、脚本编译结果、每次新建而不复用的类加载器都会持续产生类；确认方式是看已加载类计数是否与元空间同步上升，再按类加载器维度看统计，找出实例数异常膨胀的类型或反复出现的类加载器。

没有异常的那一类：慢请求与外部依赖

线上一半以上的”卡顿”报告里找不到异常，因为每一层都认为自己正常。这类问题的判据是耗时的分布形态而不是平均值：把入口接口的响应时间按百分位拆开，如果 P50 正常、P99 拖长，通常是外部依赖的尾部延迟；如果整条曲线一起抬高，才是自身容量或 GC 的问题。

分诊顺序建议固定下来。第一步确认慢在等还是在算：等待型问题的线程状态集中在 WAITING 与 TIMED_WAITING，且栈里能看到 socket 读或连接池获取；计算型问题则线程长时间 RUNNABLE 且栈顶在自己的代码里。第二步确认是否与流量同形：把慢请求的时间轴和入口 QPS、下游提供方的指标叠在一起看，同涨说明是容量或依赖，不同涨说明是某个定时任务、缓存过期或连接池回收在起作用。第三步确认是否有隐性串行：连接池上限低于并发量、超时值大于上游重试间隔、同步锁跨网络调用，这三种都会让”单请求很快、并发起来很慢”。

这一类现场最值钱的证据是带时间戳的线程栈序列，而不是单份快照。同一处等待在三份快照里都出现，才算锁定；只在一份里出现的大概率是采样噪声。若已经接入了链路追踪，先按 span 的时长排序定位到具体依赖，再回到线程栈确认是等待还是计算，通常能把排查时间从小时级压到分钟级。

处置完之后：复盘、演练与登记

止血动作结束后，还有三件事必须做，否则同一个故障一定会再来。

第一件是留下结论。登记的字段不必多：现象、判据、根因、止血动作、修复项、验证方式、遗留风险。其中”判据”最容易被省掉，而它恰恰是下次能复用这条记录的唯一原因——只写”重启后恢复”的文档，等于把经验变成了运气。涉及堆转储、日志片段的附件要按团队约定的留存期限归档，注意这些文件常含用户数据，存放位置与访问权限要和敏感数据同等级管理，不得上传到不受控的外部服务。

第二件是把这次用到的能力补全。常见的缺口有三项：某个关键指标没有采集、某条链路的超时参数无人负责、容器内的采证工具在镜像里不存在。把它们作为修复项排期，比承诺”下次会更快定位”有效。

第三件是演练。把故障处置当成可训练的动作：在预发环境构造一次可控的慢依赖，让值班同学按脚本走一遍采证、判据、止血、升级的流程，记录每一步耗时和卡点。演练的价值在于暴露”文档里有但没人会用”的工具，以及权限、审批这类非技术阻塞。团队约定的示例阈值——例如从告警到确认现场不超过若干分钟、导堆前必须双人确认——只有跑过才算存在。

小结

线上排查的确定性来自顺序：先按业务影响决定止血还是定位，再按固定顺序采证（进程、线程、GC、内存、参数留档），然后用判据而不是直觉缩小范围——CPU 高看栈顶在算还是在等，堆稳而 RSS 涨看直接内存与本地分配，间歇性失败看优雅停机与摘除顺序。整个过程里，”不破坏现场”和”不扩大影响”这两条纪律，优先级永远高于”尽快找到原因”。机制层面的解释属于另几篇文章的范围，本篇只给动作与判据：把每一步写成能被下一个人复述的脚本，才是团队真正的资产。
