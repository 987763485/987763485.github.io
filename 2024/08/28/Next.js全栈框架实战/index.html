Next.js 全栈框架实战

本文要解决的是一个很具体的问题：手上有一个 Next.js 14 的项目，怎么用 App Router 把路由、组件边界和数据获取这三层各自安顿好。适合已经写过 React 函数组件、但一碰到 app/ 目录就犯迷糊的读者。读完你应该能回答三个问题：这段代码跑在服务端还是浏览器、这个请求的结果会被缓存几次、交互逻辑该切到哪一层去写。

为什么需要全栈框架

纯客户端渲染的站点有两个绕不开的代价：首屏必须先把 JS 包下载、解析、执行完才能看到内容；数据获取逻辑散落在各个组件的 useEffect 里，拿不到就渲染空态。更麻烦的是“从哪取数、取到之后放在哪、什么时候该重新取”这三件事没有统一归属，最后全变成组件内部的私有约定，页面一多就再也对不齐。

App Router 改变的正是这个分工。组件可以直接写成异步函数，在服务端把数据取好再交付渲染结果；路由层的文件结构同时承担“URL 到组件的映射”和“数据获取时机”两件事；写操作通过 Server Actions 收敛到服务端。本文的心智模型可以压成一句话：文件位置决定了这段代码由谁执行、执行几次、结果什么时候过期。

边界说明：部署与运维不在本文范围，《Next.js 全栈部署实践》已经讲透构建产物、平台适配与流水线；渲染模式选型与服务端组件协议留给后续文章。这里只谈框架内部的路由、组件边界与数据获取。

起步：脚手架、目录与文件式路由

从零建项目

--app 生成 App Router 结构，--src-dir 把源码收进 src/，根目录就能安心放配置文件；去掉它的话 middleware.ts 会从 src/ 挪到根目录，这是两者的实质差异。需要 Tailwind 加 --tailwind，本文示例按 TypeScript 5.x 写。

两套目录技术上可以共存，但同一个 URL 只能由一套负责，出现相同路径时 pages 优先命中，排查很费时间。新项目要么整个走 app/，要么按路由逐个搬，别长期混着留。

三段路由讲透，其余带过

动态段 app/posts/[slug]/page.tsx 的组件会收到 params 属性，类型上就是一个 { slug: string } 对象，直接解构即可：

两个坑：params 与 searchParams 只传给页面和布局，普通组件拿不到，别指望层层往下传 props；读取 searchParams 会把这一段变成按需渲染，静态产物就没了，这一点下一节还会回来。

分组路由用圆括号目录名 (marketing)，它对 URL 完全透明，只把共享同一套布局的一批页面归置在一起。判据很朴素：需要独立页头页脚、独立权限域或者独立团队维护才开分组；纯粹为了目录好看而拆的，两年后会变成迷宫。

拦截路由的写法是 (.)、(..)、(...) 三级前缀，配合 Modal 与 Link 实现“点开列表项浮出详情、刷新后又变成完整页面”的动效。它的适用边界是可选的详情视图：评论详情、图片预览这一类。内容本身就是用户要看的正文，别用拦截路由，两套渲染路径的维护成本很高。

可选 catch-all [[...slug]] 用于可省略的深层路径，平行路由 @account 配 default.tsx 用于抽屉式登录，本文不展开。

布局嵌套与约定文件

布局会跨路由复用，这是特性也是陷阱

app/posts/layout.tsx 只在其覆盖的路由段被激活时渲染一次，在同一段内部跳转到子路由时不会重新挂载。这个复用带来两个直接收益：侧边栏、页头这些外壳不会闪烁，布局里 useState 保存的折叠状态和滚动位置也还在。代价也在这里：布局内的服务端取数在同段内切子页时不会自动刷新，得靠下一节的失效手段主动处理。需要“每次跳转都重来一遍”的场景（进入页面重放动画、重置搜索输入框），用 template.tsx 替代同名 layout.tsx：模板在每次导航时创建新实例并重新挂载，代价是子树状态全部丢失。另一个差别是模板不接收属性，拿不到 params。

四个约定文件各自的边界

loading.tsx 把该段包进一个 Suspense 边界，提供导航期间的回退 UI；它只影响本段与更深的子树，上层布局照常保持。error.tsx 必须是客户端组件——它是 React 错误边界的封装，而错误边界只在客户端组件里存在。not-found.tsx 由未匹配路由自动渲染，也可以在代码里显式调用 next/navigation 导出的 notFound() 触发，常用于“按 id 查不到记录”。

error.tsx 的覆盖范围包含它所在段以及所有下级段，因此放在足够高的位置一次就够；loading.tsx 与 error.tsx 不会互相顶替，前者管挂起、后者管抛错。也不要试图把 app 目录里的 error.tsx 当普通组件导入复用，可复用的 UI 抽到 components/ 下。

服务端组件与客户端组件的边界

什么时候必须写 use client

一个组件默认是服务端组件。只要出现下面四种情况之一，它就必须落在带 'use client' 的模块里：绑定了事件处理函数；用了 useState、useEffect、useRef 之类的 Hook；直接访问 window、document、localStorage；使用了只在浏览器可用的第三方库。这个指令的作用范围是模块边界，不是函数边界：一个文件顶部写了 'use client'，它以及它静态导入的所有本地组件都会进入客户端包。

服务端组件不能挂事件的原因值得说清楚：它的产物是一棵可序列化的 UI 树，网络上传的是这棵树的描述而不是可执行闭包。函数没法被序列化过去，所以“点击时调用哪个函数”这个信息在服务端组件里根本无处安放。唯一例外是 Server Action 的引用，那是框架生成的远程调用占位符。

服务端组件传给客户端组件的只有可序列化值：字符串、数字、布尔、数组、普通对象。函数、类实例、Symbol 都传不过去；日期一类的值拿不准就转成字符串或时间戳，别赌隐式行为。

把交互面收窄

反面写法是为了一个“加载更多”按钮把整个列表页写成客户端组件，于是这一页的取数、过滤全被推回浏览器执行，首屏只能等 JS。正确做法是把客户端边界推到叶子上，只给真正需要交互的最小单元标 'use client'：

需要跨页面保持的客户端状态（主题、登录弹窗开关）另有一招：让布局成为客户端组件，把服务端组件通过 children 属性塞进去。children 是一个已经渲染完的 UI 引用，不会被序列化进客户端包，所以子页面的取数逻辑照常留在服务端执行。这是 App Router 里最常见的结构。

数据获取与缓存层次

在组件里直接取数

服务端组件可以是异步函数，取数就是函数体里的一行 await，不需要额外包装。注意并排的两个 await 会串行等待，接口延迟直接相加；彼此没有依赖的数据应该同时发出再统一等待：

取数放在哪一层，判据是“谁需要它、谁能容忍它旧”。全站都要的放根布局，整页都要的放页面，只有某个块要的放那个叶子组件——放得越高越容易被上层缓存住，也就越难保证这一页是最新的。

三种缓存与两种失效手段

一个请求经过的层次大致如下：

flowchart TD
  A[浏览器请求] --> B[middleware 重写或放行]
  B --> C{该路由段有产物?}
  C -->|有且未过期| D[直接交付缓存的 UI 树]
  C -->|没有| E[服务端组件渲染]
  E --> F[组件内 fetch 取数]
  F --> G{同一份数据的 fetch 缓存命中?}
  G -->|命中| F
  G -->|未命中| H[真实请求数据源]
  D --> I[客户端路由器缓存：跳转时复用]

框架内同时存在三份东西：单次数据请求的结果缓存、整段路由产物的缓存、浏览器内存里为跳转提速留下的路由器缓存。控制第一层的开关是标准 fetch 的 cache 选项（force-cache 允许长期复用、no-store 每次真实请求）和 next 扩展里的 revalidate 秒数与 tags 标签数组。这一层不缓存非 fetch 的调用（比如直连数据库），默认取值在不同版本上调整过，本文不写死，落地前以官方文档为准；实践上建议每个 fetch 都显式写出 cache，把意图留在代码里。

主动失效用 next/cache 导出的两个函数：revalidatePath('/posts/[slug]', 'layout') 让某个路径的产物过期，revalidateTag('posts') 让所有打了这个标签的数据请求一起过期——写操作之后调一次标签失效，比逐个清理路径省事。另外，读取 cookies()、headers() 或者用了 no-store，都会把这一段变成按需渲染，静态产物就没有了；想固定某段的刷新周期，可以用路由段配置导出 revalidate 这个数值。

原生 form 加 action 的写法自带渐进增强：JS 还没加载完时浏览器仍会提交这个表单，服务端动作照样执行。提交中状态用 react-dom 提供的 useFormStatus 读取，注意它只反映“外层 form”的状态，必须写在子组件里而不是同一个组件里，这是最常见的踩点。所有写操作集中放进 actions.ts 一类文件，好处是权限校验、失效调用、审计日志能收在一处处理。

中间件与路由处理器能做什么

middleware.ts 是一个跑在真实渲染之前的函数，导出 middleware 和一个 config.matcher 数组来限定生效路径，典型用法是未登录时 NextResponse.redirect 到登录页、给灰度流量 rewrite 到另一个段、按语言头重写前缀。它的定位是“轻量的请求分流”：默认执行环境不是完整的 Node，读不到本地文件系统、不适合放数据库查询或几十毫秒以上的逻辑，超时就会退化成直接放行。需要为重写后的请求补信息，用 NextRequest 的 headers.set 生成新请求，别指望修改原请求对象就生效。

app/**/route.ts 导出以 HTTP 方法命名的大写函数，返回 NextResponse.json(...)，适合做 webhook 接收、给第三方回调的窄接口、少量字段的读写。边界也要讲清楚：不要在导出里塞长任务，同步执行到一半就可能撞上请求时限，应该只落一条待办然后交给外部 worker；不要在处理器里直连大查询，把访问收进数据层，页面组件和接口共用同一份实现；不要用它承担鉴权中枢——中间件的前置检查只是第一道门，真正判权必须在动作和处理器里各做一次。

样式、图片与迁移清单

样式的额外成本

CSS Modules 是内置能力，文件名以 .module.css 结尾即可按模块使用，全局样式表只在根布局里导入一次，别散落到叶子组件。麻烦的是运行时 CSS-in-JS：styled-components 与 emotion 要把生成的样式注入服务端渲染的输出流，官方示例的做法是自写一个客户端注册器组件配合 useServerInsertedHTML 完成注入，配置不便宜，写法也随版本变动。新建项目没有强需求就优先选 CSS Modules 或原子化 CSS，把运行时样式引擎留给旧项目。

图片与字体

next/image 会生成多尺寸与现代格式、按视口挑选合适的图，并预留占位尺寸，收益主要落在首屏加载与布局抖动上；本文不给具体数字，示意值也该以自己的站点实测为准。两个用法要点：sizes 要按真实布局写，写错反而会下载过大的尺寸；首屏最大内容元素那张图补上 priority。远端地址必须进入 next.config.js 里 images 的白名单，domains 只按主机名放行，协议、端口、路径一概不限，remotePatterns 能把协议、端口、路径前缀一起收紧，新代码一律用后者。next/font 在构建期把字体文件自托管，省掉一次跨域请求和一段空白期，variable 选项把它暴露成 CSS 变量给样式表使用。

从 Pages Router 过来的清单

  1. _app.tsx 的全局外壳搬进 app/layout.tsx；_document.tsx 直接删掉，原来 <head> 里的标签改用元数据导出。
  2. 路径改成目录：pages/posts/[slug].tsx 变成 app/posts/[slug]/page.tsx，每个页面必须有默认导出。
  3. getStaticPaths 换成 generateStaticParams，getStaticProps 与 getServerSideProps 换成组件函数体里的 await。
  4. next/router 换成 next/navigation，查询串读取换 useSearchParams，跳转方法的参数形式也不同。
  5. Link 去掉 legacyBehavior 与 passHref，直接包裹文本或组件。
  6. pages/api/* 的 req、res 风格换成 route.ts 里的标准 Request 与 NextResponse。
  7. pages/_middleware.ts 挪到根目录或 src/ 下的 middleware.ts，改写为返回 NextResponse。
  8. 全局样式集中导入一次；images.domains 迁成 remotePatterns。
  9. 每搬完一段就跑一次生产构建，确认这一段的静态产物仍然生成——迁移期最容易悄悄把整站变成按需渲染。

小结

用法层面可以归成三条纪律。第一，位置即语义：文件在 app/ 里的位置和它的约定文件名，共同决定了这段代码在哪执行、结果缓存到哪一层、什么时候失效。第二，'use client' 是边界而不是开关，把它推到叶子上，让外壳客户端化、内容服务端化，首屏才守得住。第三，取数与写操作各归其位：读放在需要它的最上层，写收进动作文件并在成功后按标签失效，接口层只做必须走 HTTP 的窄口子。

Server Actions 与实验性的构建加速在当时都还在演进，用之前先确认版本与开关状态。渲染模式怎么挑、服务端组件协议如何工作，那是更深一层的题目，本文刻意没有展开；部署与运行则去看《Next.js 全栈部署实践》。把这三件事分开记，项目的结构会清楚很多。
