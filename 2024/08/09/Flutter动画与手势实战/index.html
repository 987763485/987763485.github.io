Flutter 动画与手势实战

Flutter 里同一个视觉效果往往有两种完全不同的写法，选错路径正是动画代码迅速膨胀的首要原因。本文依次讲隐式动画、显式动画三件套、曲线分段与交错、跨页动画、物理模拟，以及手势识别与手势竞技场。

两条路径：隐式还是显式

框架层面看，Flutter 的动画只做一件事：某个值随时间从 A 走到 B，每一帧把界面重画一遍。差别只在交给谁做。

第一条路径是隐式动画：把要变化的属性写成控件的构造参数，再换成带 Animated 前缀的同类，插值由框架完成，你只提供目标状态和时长。第二条路径是显式动画：你持有一个 0 到 1 的进度值，通常是 AnimationController，把它映射成想要的东西，再在 build 里按进度构造子树，于是可以倒放、可以在半途改方向，也能让好几段动画共享同一条时间轴。

代价并不对称。该用显式时用了隐式，你会发现“属性到属性”表达不出序列、打断和联动，只好再塞延时回调或者第二个 controller；该用隐式时用了显式，则是为一个淡入写二十行样板。判据只有一句：需不需要在中途被人为打断，需不需要和另一段动画共用时间轴。StatefulWidget 与 build 的基础本文不重讲，见同批《Flutter 环境搭建与 Widget 体系》。

隐式动画：把变化交给控件

最常用的四个成员是 AnimatedContainer（尺寸、内边距、颜色、圆角一起插值）、AnimatedOpacity、AnimatedDefaultTextStyle 与 AnimatedAlign（对齐位置）。它们共享同一组关键参数：duration 决定这次过渡走多久，curve 决定用什么节奏走；duration 不写就退化成瞬间切换，这是“怎么没有动画”的头号原因。它们还都提供一个过渡结束时触发的回调，名称以你 SDK 里的类文档为准。

好处与坏处来自同一处：属性写在 Widget 上，声明性强；但也因此它只能表达“某个属性从一个值变到另一个值”。它无法描述序列，也就是先移位置再变颜色；它对打断的处理是被动的，用户途中再点一次，控件会从当前插值位置重新起一段；它更不能把一个进度值同时喂给两个互不相关的子树。这三点就是显式动画存在的全部理由。

显式动画三件套

三个角色职责分清，代码自然就顺。

AnimationController 就是那条时间轴：内部一个 ticker 每帧把进度向前推，并按 duration 归一化成 0 到 1；常用操作是 forward、reverse、toggle、stop、reset、repeat；它本身还是一个 Listenable。它必须在 dispose 里显式释放，忘了释放是 Flutter 动画最典型的泄漏点。

Tween 只负责值域映射，例如把 0 到 1 映射成 48 到 120，完全不关心时间；animate 把 controller 的进度经过一条曲线和这个映射，变成一个“带状态的目标值”。常见类型都有现成的 ColorTween、SizeTween、RectTween，自定义类型可以继承 Tween 并提供自己的插值逻辑。

AnimatedBuilder 与 ListenableBuilder 负责“什么时候只重建局部”。前者监听 Animation，只在收到通知时执行 builder，并通过 child 参数把不随动画改变的重型子树提出来，避免整棵子树陪跑；后者监听任意 Listenable。手上是 Animation 对象就用前者，只有 ValueNotifier 就用后者。

需要多个互不相干的动画时，把 mixin 换成 TickerProviderStateMixin。

vsync 不是可以省掉的样板参数。它把 ticker 挂到一个“可见性”上：页面被推到后台时 ticker 自动停摆，不再每帧回调。少了这层保护，一个已经离开屏幕的页面仍在按帧推进进度、触发局部重建，白白吃掉本该属于当前页面的帧预算，这种浪费还会随页面栈变深而叠加。正因如此，不提供 vsync 时框架会直接抛断言，而不是给一个默认值。

曲线、分段与交错

曲线决定观感，影响常常大于时长。Curves.easeOutBack 收尾时会轻微冲过头再拉回，很适合“落位”类动作；easeOutCubic 起手快收尾慢，接近手指松开后的减速；linear 几乎只该用在进度条上。

多段动画不要串多个 controller，而要用 Interval 在同一条时间轴上切窗口：时间轴只有一条时，暂停、倒放、变速都只操作一处；多个 controller 衔接时，你得处理每一段的启动时机和被打断后另一段怎么办，维护成本会失控。

0.45 到 0.55 的重叠是为了让两段接得不突兀，数字都是示意值。若只想在一小段进度里换几种节奏，可以用 CurveChain 把若干曲线串起来依次生效，注意它串联的是曲线而不是 Tween。

交错动画是 Interval 最典型的用法：一个 controller，每一项拿到一个沿时间轴向后平移的窗口，就形成波浪式入场。

项数很多时别用过长的总时长，否则末项要等很久才动。

动画对象是“运行中不断插入和删除的列表项”时，AnimatedList 与 SliverAnimatedList 比手写交错更合适。关键认知是：数据变化和动画变化是两步。你先改数据源，再显式通知它某个下标插入了或者即将移除，并在构建回调里返回带过渡效果的 Widget；删除时旧 Widget 会在动画播完之前继续留在树上，所以构建回调要能区分正常显示与正在退场。最常见的失败是只改了数据、忘了发通知，列表瞬间跳变，看起来像动画没生效。这两个类的参数名各版本有差异，本文只描述语义。

Hero：让一个 Widget 飞到另一个页面

Hero 做的是跨页动画：路由切换时，框架把起点页面上那个 Hero 摘下来，沿一条轨迹移动到目标页面上 tag 相同的 Hero，两端不需要自己写 controller。

唯一的硬约束就是 tag：同一次飞行两端必须一致，而同一时刻只能对应一对起点与终点。三类失败最常见。一是 tag 重复，源与目标写死同一个字符串，或者列表里每项都用了同一个 tag，框架无从判断该让哪个 Widget 起飞，表现就是有时不动或从错误的项动过去，列表场景要把下标或业务 id 拼进 tag。二是页面并不是用路由方式覆盖的：Hero 依赖转场时机，如果“切页”其实是同一页面里用层叠、显隐或自绘换内容，它根本不会被触发。三是两端外观不一致，飞行结束后会有一次明显的尺寸或圆角跳变；正确做法是让两端渲染同一个外观，或者利用它自定义飞行中 Widget 的能力，在途中换成专门画给这段轨迹的 Widget，该能力的参数形式各版本略有差异。

至于 Navigator 与页面转场构建器属于路由体系，本文不展开，只需知道它们与 Hero 是两套机制。

物理模拟：把时长换成方程

前面的动画都建立在“固定时长”上：给一个 duration，进度按它归一化。物理模型不给时长，而给初速度、刚度、阻尼这类状态量，位移由方程逐帧解出，因此每次结果的时长都可能不一样。

SpringSimulation 是这个思路最纯粹的入口：它需要质量、刚度、阻尼与初始位置、初速度，而松手那一刻的初速度直接来自手指。AnimationController 也支持不吃曲线而直接接受一个模拟对象，弹簧结果仍旧接在原来的 Listenable 链路上，下游不用改。

滚动物理是更日常的入口：ClampingScrollPhysics 到边界就硬停，BouncingScrollPhysics 允许把内容拉出边界再弹回去；GravityScrollPhysics 由后续版本引入，2024-08 时请核对你所在 SDK 是否已包含，不能当作既有能力来推荐。

分歧只在一处：动作终点是不是由手指给的速度决定。甩动后的惯性滑动、拖拽松手后的回弹、面板落到最近停靠位都该用物理；若退化成固定 duration 的 Tween，那么无论轻推还是用力甩，动画都用同样时间走完，跟手感当场断裂。反过来，由程序触发的明确切换，固定时长更可控。

时长、曲线与物理模型是同一问题的三层：多长、怎么变、由谁决定终点。

手势识别与手势竞技场

家族与配对回调

GestureDetector 能识别的家族大致是：onTap 单击、onDoubleTap 双击、onLongPress 长按、onVerticalDrag 与 onHorizontalDrag 单轴拖拽、onPan 任意方向拖拽、onScale 多指缩放与旋转。它们不是一堆独立开关，而是会彼此竞争的识别器。

每个家族都把回调分成一组，这是刻意的：Start 表示识别刚刚胜出、手势正式开始；Update 逐帧给出增量；End 表示手指正常离开；Cancel 表示中途被抢走或者被系统打断。只写 Update 不写 Cancel 的后果很具体——卡片被拖到一半时父级列表开始滚动，你的偏移量就永久停在错误位置上。

d.delta 是这一帧相对上一帧的位移，累加它比累加屏幕坐标可靠，因为父级被滚走时绝对坐标会突变。缩放与旋转取 onScaleUpdate 里的缩放因子和转角，乘进一个 Transform，或者用 FittedBox 让内容按新尺寸重新适配，好处是内容本身不需要知道自己在被放大。

框架内部还存在若干阈值常量，例如把按下抖动与真的想拖区分开的 kTouchSlop。它们的作用是不让手势在第一个像素上就误触发；数值与平台、版本有关，代码里请直接引用常量，不要写死数字。

竞技场：谁赢了这次触摸

指针事件在到达 Widget 之前先做命中测试，路径上所有候选手势识别器被注册进同一个竞技场，再由竞技场决定唯一胜出者，其余的收到取消。这解释了两件日常困惑：单击为什么往往在松手之后还要再等一小会儿——点击识别者必须等双击和长按的判定窗口过去才敢认领；长按和拖拽为什么会互抢——两者都在等位移，先超过阈值的那个立刻宣告胜出，于是“长按后再拖动”要么丢掉长按、要么丢掉拖拽。

  participant T as 点击识别器
  participant D as 拖拽识别器

  T-->>A: 等待松手与双击窗口

  A->>T: 判定失败，派发取消
  A->>D: 逐帧派发更新直到松手

当框架提供的开关在你的版本上不可用或粒度不对时，例如把某个子树整体排除在命中测试之外这类能力，别靠堆 IgnorePointer 绕，改用 RawGestureDetector：它允许你显式声明这份 Widget 需要哪几种识别器、以什么组合注册，从而把默认那套竞争关系换成你真正想要的一套，比如只留拖拽、彻底不给上层点击机会。

最难缠的是“父滚子也滚”：外层是纵向列表，内层有横向可拖拽区，一拖就带着整页跑。两种解法：一是内层用手势状态做闸门，外层用 NotificationListener 接住滚动通知、在横向手势期间阻止它继续向上冒泡，并把父级临时换成不可滚动的物理；二是从结构上让横轴归子级、纵轴归父级，内层只声明横向拖拽的识别器，两个方向各属一个手势，冲突自然消失。能选第二种就别选第一种。

Listener 与原始指针事件

Listener 和 GestureDetector 不在同一层。前者把原始 PointerEvent 交给你，不做语义解释：你能拿到按下位置、事件类型、当时按下的按钮，也能看出是手指还是鼠标；它不进竞技场，来一个事件回调一次，因此完全没有识别等待。后者做语义识别，代价就是要等竞技场裁决。

这个差别解释了一类真实体验：既能单击又能双击的按钮，单击永远慢半拍，因为识别器必须等双击窗口结束才敢把这次按下判给单击。如果界面其实不需要双击，就可以在最外层挂一个 Listener，自己按按下事件与抬起事件的配对判定点击，立刻生效，代价是要自己处理阈值与手指移出边界的取消。同理，Listener 也是最好用的手势调试工具：把它的回调打在控制台，就能看清这次触摸在哪一步被谁抢走。

动画性能的几条提示

这里只列动画与手势特有的五条，完整优化口径见同批《Flutter 性能优化实践》。

  • 把动画下沉到最小的那个 Widget：AnimatedBuilder 包在哪一层，重建就只发生在哪一层，包在页面根部等于每帧重跑整棵子树（完整优化口径见同批《Flutter 性能优化实践》）。
  • 不在 build 里创建 AnimationController 或 Tween：build 会被反复调用，对象每帧重建，进度和释放时机同时失控（完整优化口径见同批《Flutter 性能优化实践》）。
  • 逐帧 setState 的代价是把整个 State 的 build 重跑一遍，进度类更新应当走 Listenable（完整优化口径见同批《Flutter 性能优化实践》）。
  • RepaintBoundary 用来把频繁重绘的一块区域与周围切开，使重绘不再牵连兄弟节点，典型对象是飞行中的 Hero（完整优化口径见同批《Flutter 性能优化实践》）。
  • 构建跟踪类调试开关只回答“这帧重建了哪些子树”，不要把它当成帧率测量工具（完整优化口径见同批《Flutter 性能优化实践》）。

小结

最后把效果、机制与坑整理成一张对照表。

想要的效果 该用的机制 最容易错的地方
单个属性渐变 隐式动画 AnimatedContainer 一族 忘了给 duration
先变 A 再变 B 一个 controller 配多个 Interval 串多个 controller，打断逻辑写不完
逐项波浪入场 交错：平移的时间窗口 总时长太长，末项等太久
运行中增删列表项 AnimatedList、SliverAnimatedList 只改数据没发通知，列表跳变
卡片飞进详情页 Hero tag 重复，或页面不是路由覆盖
拖拽要跟手 onPan 加 Transform.translate 只写 Update，漏掉 Cancel
松手后自然回弹 物理模拟与滚动物理 用固定时长代替物理
双指缩放旋转 onScaleUpdate 配 FittedBox 缩放因子累乘没有上下限
父滚子也滚 方向独占，或拦通知加临时物理 只拦通知不改物理，父级照样在滚

本文的主线只有一个判断：变化交给 Widget 自己插值，还是由你握住那条 0 到 1 的进度。前者省心，但表达不了序列、打断与共享时间轴；后者一旦上手，交错、跨页飞行、物理回弹都只是同一条时间轴的不同用法。手势这一侧也一样，GestureDetector 给你语义、竞技场给你唯一胜出者、Listener 给你原始事件与零延迟，知道自己在哪一层，冲突就不再靠试错解决。落地时守住三条：时长与曲线由团队统一约定并写进常量表；每个 controller 都能在 dispose 里找到对应释放；凡涉及跟手与惯性，先考虑物理模型再考虑固定时长。
