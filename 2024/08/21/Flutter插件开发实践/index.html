Flutter 插件开发实践

这篇文章聊的是”造插件”：把一段只能在工作台之外才能完成的活儿，封装成一个可以被别的工程 dart pub add 走的包。用插件、把 Flutter 塞进已有原生 App、宿主与 Flutter 之间的双向通信工程取舍，是《Flutter 混合开发与 Platform Channel》那一类话题，这里只做最小必要引用；渲染性能相关的话题归《Flutter 性能优化实践》，SDK 与 channel 的安装归《Flutter 环境搭建与 Widget 体系》。本篇的版本口径是 2024 年 8 月这条时间线：Flutter 3.22 稳定线是当前主力，3.24 刚进入发布节奏，Dart 是 3.x，dart pub 是默认入口，null safety 早已是常态。拿不准具体从哪个版本引入的细节，我会不写版本号，只描述行为。

从需求到形态：先判断要不要做插件

一个包该长成什么形状，取决于它要不要碰平台。我把常见形态排成三档。

第一档是纯 Dart 包。pubspec.yaml 里没有 flutter: plugin: 这一段，目录里只有 lib/。工具函数、算法、数据模型校验、一套通用 UI 组件、依赖 dart:io 或 package:http 就能完成的事情，都属于这一档。它的收益很实在：不需要懂 Kotlin 和 Swift，不需要处理引擎注册，不需要在真机上跑集成测试，dart test 几秒出结果。代价是它对平台一无所知——读不到 Android 的 NotificationManager，碰不到 iOS 的 AVAudioSession，也调不动 Windows 的 Win32 API。很多”我以为要写插件”的需求，其实把平台差异留给调用方就好，硬塞一个通道反而增加一层序列化开销。

第二档是单平台插件，也就是一个包内直接放 android/、ios/ 目录，Dart 门面和平台实现住在一起。flutter create --template=plugin 给的默认骨架就是这一档。它的路径最短：一个仓库、一条发布流水线、一次版本决策。适合三种情况——需求只覆盖一个平台；平台差异极小，参数与返回几乎同构；或者你自己就是唯一实现方，不打算让别人替换。它的代价要在半年后才显现：目录越来越厚，lib/ 里开始长出 if (Platform.isAndroid) 这样的分支，返回的 Map 里字段含义随平台漂移，想给某个平台换一个实现方只能连整个包 fork 走。

第三档是 federated plugin（联合插件），把一个”能力”拆成若干包：面向应用的门面包、平台接口包、各平台的实现包。url_launcher、shared_preferences 这一族就是这种形状。它的收益是能力与实现解耦：接口包定义契约，实现包各自遵守，第三方可以提供一个同名接口的替代实现（比如给某个国产硬件写一个实现包），调用方只改一行依赖。代价也很直白：仓库数量、版本联动、发布顺序（先实现包后接口包再门面包）、跨包联调时 pubspec_overrides.yaml 满天飞。团队第一次做的时候容易被这套工序劝退，所以我倾向于按”是否会有第二个实现方”来判断，而不是按”看起来是否正规”。

判断顺序可以固定下来：先问要不要平台 API，不要就停在纯 Dart 包；要平台 API，再问要不要覆盖两个以上平台且行为可能不同；要，就把接口包先写出来，哪怕暂时只有一个实现。最后一条经验值得单独强调——接口包的成本很低，但它决定了 API 的形状会不会被某个平台绑架。等三个平台的代码都写完再回头抽接口，通常要动门面签名，那是 breaking change。

字段名以工具链文档为准，别自己发明；写错不会在 flutter pub get 时报错，而是在运行时以 MissingPluginException 的形式出现，非常难查。写完这一段，先看一眼 example/ 里自动生成的注册文件（Android 侧是 Java/Kotlin 的 FlutterActivity 注册逻辑，iOS 是 AppDelegate 里的 GeneratedPluginRegistrant），确认插件类真的被注册进去了，再开始写业务代码。这一步能提前发现八成声明错误。

federated 插件的五件套与自动装配

federated 形态把一个能力拆成五类角色，角色之间存在单向依赖。

第一件是 app-facing package，也就是用户 import 的那个包（volume_player）。它只做三件事：定义面向用户的 API、在 pubspec.yaml 里为每个平台写 default_package、不包含任何平台代码。用户只应该看见这一层的类型，接口层的类型不要泄漏到函数签名里。

第二件是 platform interface package（volume_player_platform_interface）。它定义抽象契约，并把”实现必须继承我”这件事变成运行时检查：

PlatformInterface 的 token 机制看起来繁琐，但它挡住的是一类真实事故：有人实现了同名方法却漏了某个语义细节，编译器不报错、运行时行为错乱。用 token 校验后，非继承实现会在赋值那一行立刻抛异常。UnimplementedError 而不是 abstract 方法，是为了让实现包只覆盖自己关心的方法，同时保证加新方法时不破坏下游编译（这一点在接口的次要实现上很关键）。

第三、四件是各平台的实现包（volume_player_android、volume_player_ios），每个包里同时有 Dart 侧实现和原生代码。Dart 侧通常继承接口包自带的 MethodChannelVolumePlayer，只覆盖与平台特性相关的方法；原生侧则照普通单平台插件写。第五件是社区或你为特定设备写的替代实现包，形状与平台实现包完全一样——这正是 federated 的意义所在。

通道选型、编解码与 Dart 侧门面

三条通道的选择判据其实是”交互形状”。

MethodChannel 适合请求-响应：一次调用、一个结果、可有错误。它也能发不带期待结果的单向消息（Dart 侧不 await 即可），但语义上仍是方法调用。EventChannel 适合订阅：一次建立、持续推送、由 Stream 承接，传感器读数、播放进度、连接状态这类”来源在平台侧”的数据用它。BasicMessageChannel 适合对等双向通信与自定义编码——你要传一个二进制帧、想让两端共享同一个 MessageCodec、或者两端都可能主动发起，就用它。至于它放在网络层还是存储层的工程取舍，属于混合开发里宿主与 Flutter 通信的话题，这里不展开。

MethodChannel 与 EventChannel 默认都用 StandardMessageCodec，它认得的下表这些类型（BigUint64List 与其余定长列表同理）：

Dart Kotlin / Java Swift / Objective-C
null null nil / NSNull
bool Boolean NSNumber（bool）
int Integer 或 Long Int32 / Int64
double Double NSNumber（double）
String String NSString
Uint8List ByteArray FlutterStandardTypedData
Int32List / Int64List / Float64List 对应数组 FlutterStandardTypedData
List ArrayList NSArray
Map HashMap NSDictionary
BigInt BigInteger 需自行映射

表里没有的东西就是坑：自定义对象、DateTime、Duration、闭包、任何带行为的类型都不能直接过通道。原因不是”麻烦”，而是编码器的类型表是固定的、按 type id 编号的——序列化出来的字节只携带”值”，不携带类信息与生命周期。对端拿到的是一个 Map，方法、私有字段、定时器句柄、原生资源指针全都不在里面。更危险的是版本漂移：如果两端各自依赖同一份 Dart 模型代码，通道字节格式一变就会出现静默错位；而显式的 Map 契约能被测试覆盖。

错误语义要分清楚，否则排查方向会错。MissingPluginException 意味着通道另一侧根本没有 handler——典型原因是插件没被注册、pluginClass 写错、刚做完 hot restart 而原生侧没重启，或者平台没在你的构建目标上启用；它不是业务错误，重试没有意义。PlatformException 是原生侧显式 result.error(...) 送回来的业务失败，code 是稳定标识、message 给人看、details 放结构化数据。设计 code 时把它当 API 的一部分：用蛇形小写常量、只增不改不删，把异常堆栈留在原生日志里而不是塞进 message（message 可能被界面直接展示）。iOS 侧对无法识别的方法要返回 FlutterMethodNotImplemented，Android 侧调用 result.notImplemented()，Dart 侧收到的是 MissingPluginException——这正好用来发现”方法名两端打错了”这类低级但常见的 bug。还有一个容易踩的坑：invokeMethod<int> 在原生返回 null 时会得到 int?，如果直接赋给 int 变量，热重载后表现为 TypeError；跨通道的返回值一律先当可空处理。

ApplicationContext 与 Activity 的区别决定了插件能不能被安全复用。binding.applicationContext 在插件整个 attach 周期内稳定，适合存缓存、拿 SharedPreferences、注册 ContentResolver 观察者、读系统设置。Activity 则随时会变：旋转屏幕是销毁重建，跳转页面是 detach 再 attach，进后台可能没有前台 Activity。所有需要界面或Activity 生命周期的操作——弹权限框、ActivityResultLauncher、分享、调起系统面板——都必须显式向 ActivityAware 要前台 Activity，而且要处理”拿不到”的分支：

链路上有三个断点：对话框期间 Activity 被重建，listener 挂在旧 binding 上收不到回调；用户在系统设置里改完权限直接返回，onRequestPermissionsResult 根本不触发，需要靠 onResume 补一次检查；回调线程与 result 的调用线程不一致。稳妥做法是把”等待结果”这件事建模成一个带超时的挂起表（方法名加 arguments 作为 key），onResume 与超时都能收尾，且每个 key 至多 reply 一次——重复 reply 会被引擎识别为”结果已提交”并记录错误，第二次的数据静默丢失。

iOS 与 macOS 侧实现要点

iOS/macOS 侧的注册是类方法 register(with:)，由 GeneratedPluginRegistrant 在 AppDelegate 里调用：

macOS 侧取 messenger 的方式完全相同，区别在视图：registrar.view 返回 NSView?，窗口关闭后就是 nil，凡是要把内容挂到界面上的分支都要判空并准备好回退路径。registrar.publish(_:) 用来把对象（例如纹理注册器）暴露给别的插件，避免插件之间通过全局单例互相耦合。

引用关系是 iOS 侧最大的坑。插件对象被 registrar 持有，生命周期跟着引擎走；但插件里如果强引用了 FlutterViewController 或 FlutterEngine，就会形成引擎 → 插件 → 引擎的环，表现为页面关闭后引擎不释放。原则是：需要往 Flutter 回发消息时，保存 FlutterMethodChannel（它内部对 messenger 是弱引用语义）而不是保存引擎；需要监听 App 生命周期时用 registrar.addApplicationDelegate(self) 接 applicationDidBecomeActive 这类回调，而不是去访问控制器。

线程、耗时任务与生命周期

onMethodCall（以及 iOS 的 handle(_:result:)）默认跑在平台主线程上。这条规则带来的后果比想象中大：主线程一旦被同步 IO 占住，通道上后续所有消息都要排队，权限回调、生命周期事件、平台 UI 刷新一起卡住；iOS 上主线程长时间无响应还会触发系统看门狗。Flutter 自己的绘制在引擎线程上，所以界面不一定立刻掉帧——渲染侧的表现归《Flutter 性能优化实践》，本篇只谈插件这一侧的规矩。

正确写法是把任务交给后台线程，并在任务真正结束、且切回主线程之后再 reply：

Dart 侧要配合做超时兜底，否则一个忘记 reply 的 handler 会让 await 永久悬挂，界面上表现为按钮卡死：

超时值要按”最慢的合法情况”给，别写 5 秒这种凭感觉的数字。真要覆盖大文件，比超时更有效的是把一次性调用改成 EventChannel 推进度：Dart 侧拿到 Stream，平台侧每完成一段就 eventSink?.invoke(进度)，结束时再推送一个终态。

数据量大时还有编解码成本。一次 invokeMethod 的返回值会在两端各解一次码，Uint8List 这种定长列表尽量原样传，不要 base64 成 String——后者在通道之外多了一次编码、一次解码和一次内存膨胀，传一个几兆的缩略图（示意量级，不是实测）时差别非常明显。同理，不要把整份 JSON 字符串扔过去让 Dart 侧 jsonDecode，直接传 Map 更省。

生命周期是插件内存问题的主战场。规则很朴素：谁注册谁解绑，且解绑要和注册成对出现在 attach/detach 两侧。

  • Android：context.registerReceiver 必须有配对的 unregisterReceiver；ContentResolver.registerContentObserver 要 unregisterContentObserver；ActivityPluginBinding 上 addRequestPermissionsResultListener 加进去的 listener 要在 detach 时移除（binding 会随 Activity 重建，旧 listener 留在旧 binding 上就是无效引用）。
  • iOS/macOS：NotificationCenter.addObserver 与 KVO 要在 onCancel、插件释放或引擎销毁路径上撤销；Timer 记得 invalidate，它对被调用目标的引用在失效前一直存在。
  • 不要在 companion object 或 Swift 的静态属性里缓存 Activity/UIViewController，引擎重建后这些引用会把上一世的界面留在堆上。

引擎销毁再重建（Android 上 Activity 被系统回收后重启、add-to-app 场景里的引擎复用与释放）时，插件实例是全新的，所有状态要从 Dart 侧重新下发。把插件设计成”无持久状态、配置由 Dart 每次传入”比”缓存一份配置在原生”更容易活过重建；如果确实要缓存，就缓存到 ApplicationContext 级别的存储里，而不是内存字段。示例应用要能把这些路径演示出来：dispose 里取消订阅、页面 pop 后检查是否还在推送、开发者选项里打开”不保留活动”跑一遍权限流程。

至于引擎在多页面间复用、后台 Service 主动向 Flutter 推消息时如何拿到 messenger，属于混合开发与引擎生命周期的范围，本篇按”插件不假设自己永远处于 attach 状态”这一条纪律处理。

测试：把平台差异挡在单测之外

插件最难测的地方不在 Dart，而在”原生那半边跑不起来”。federated 结构本身给出了答案：把可替换的边界放在 platform interface 上，测试就能分层。

最外层是纯 Dart 单测，速度最快、能在 CI 里跑几百次。做法是让门面依赖 interface 而不是某个具体平台实现，测试时用假实现顶替：假实现记录被调用过哪些方法、参数是什么、按脚本返回结果或抛错。这一层的价值在于验证门面的逻辑——参数校验、错误码翻译、事件流的订阅与取消、超时与重试的边界，全部与设备无关。写这一层时有个常见误区：把假实现写成”什么都不做也返回成功”，于是断言退化成”没抛异常”，等于没测。假实现应该显式断言调用次数与参数，并且至少有一条用例让它失败一次，确认门面确实把错误传上来了。

中间一层是通道级测试。Flutter 的测试框架允许在测试环境里给某个 MethodChannel 装上模拟的处理器，从而检验”门面发出的方法名、参数结构、返回类型解码”这三件事是否真的对得上。这一层最容易被漏掉，而它恰好是跨语言问题的高发区：Dart 侧写的是 Map<String, Object>，Kotlin 侧按具体类型强转，单测全绿、真机崩溃。把编解码放进通道级测试，能在没有设备的情况下抓住类型不匹配与 null 语义错误。

最里层是真机集成测试，用 integration_test 那一套。只有这一层能覆盖权限弹窗、真实文件系统、后台状态、传感器与平台 UI；它的代价是慢、环境依赖重、失败原因常常是模拟器状态脏。工程上的分配方式是：门面的行为契约由 Dart 单测守住，编解码由通道级测试守住，只有”平台确实能做到”这类断言交给真机。反过来说，如果一条用例真机上时好时坏，先怀疑它是否在验证平台行为而不是插件逻辑。

example/ 目录不是装饰。它是 pub.dev 上唯一会被多数使用者打开的东西，也是回归基线：每个公开 API 至少要有一条可点按路径，包括错误路径——故意传非法参数、故意在没有权限时调用。示例越接近真实用法，别人替你踩坑的概率越高。

Web 与桌面端：能力缺失要显式报错

一个常见事故是这样的：插件只在 iOS 与 Android 上实现过，桌面端编译能过、运行不崩，只是调用永远返回空结果。原因往往是把”没有平台实现”处理成了静默的默认返回。

正确的做法是把”不支持”变成契约的一部分。三种形态可以选：在 Dart 门面里显式声明当前平台会抛 UnsupportedError，并在文档写清；由 platform interface 提供一份”能力查询”方法，让调用方先问再做；或者给出降级实现（例如桌面端把系统通知转成应用内提示），但要明确标注降级语义。三者都比”返回空集合”好，因为空集合看起来像成功。

依赖方向也要留意。pubspec.yaml 的 plugin 段里声明了哪些平台，才装配哪些平台的实现包；只写了 iOS 与 Android 的插件在 macOS 上不会自动可用，需要单独增加对应实现包并在声明里列出。Web 侧是另一套机制，与 dart:io 相关的文件与网络能力在浏览器里没有对应物，需要走浏览器 API 重新实现，且必须接受权限、跨域与用户手势这些浏览器约束；能力不确定时，宁可先声明不支持，不要在运行时猜测。

桌面端还有一个容易忽略的实现细节：Windows 与 Linux 的传统插件实现分别落在 C++ 与 C 这一类原生工程里，构建脚本参与编译，这与 iOS、Android 用 Swift、Objective-C 或 Kotlin 的体验差别很大。若团队没有维护原生构建的经验，把桌面端列为”暂不支持”比硬撑着支持更负责——前提是能力查询与文档要写清楚。

发布与维护：把兼容性写成人能读的句子

发布前的清单不复杂，但每一条都会在未来某天咬人：公开 API 是否都有文档注释与示例；错误码是否稳定（调用方可能按字符串分支，改名就是破坏性变更）；README 里是否写清支持哪些平台、哪些平台是降级实现；CHANGELOG 是否说明了”这次升级需要改调用代码吗”。

版本要成组考虑。federated 结构下至少有三类包：接口包、各平台实现包、面向应用的门面包。接口包发生破坏性变更时，所有实现包必须同步升级并在描述里写明依赖的接口版本范围，否则应用侧出现的是”门面是新版、某个平台实现是旧版”的组合，报错信息通常很难懂。发布新版本前先确认一件事：老版本组合是否会静默工作。若会，就要在接口包里做版本协商或显式拒绝。

维护的边界也要提前想好。插件一旦被依赖，Issue 里就会出现”在别人设备上能用、在我这里不行”的报告，而这类问题的分辨率取决于你有没有把诊断信息做进返回值与错误码里。工程上值得长期开着的只有三件事：静态分析、格式化检查、测试。把这三步放进 CI，比在发布说明里写”已自测”更有说服力。至于打分与推荐标记，那是平台侧的算法结果，随规则变化，不应作为设计目标。

形态选择对照表

形态 适用场景 开发成本 测试成本 主要风险
纯 Dart 包 只依赖已有插件或浏览器、dart: 能力 低 低，单测即可 被误认为能访问平台 API
单平台插件 只服务一个平台，如某厂商 SDK 中 中，需真机 其他平台装配不到实现
federated 插件 多平台且实现差异大 高 高，分三层 版本组合错配
应用内私有插件 只在本仓库用，不对外发布 中 中 后来被误当公共 API

小结

写插件的难点从来不在通道 API 有几行，而在边界：哪些事属于 Dart 侧契约，哪些事必须由平台实现负责，哪些能力应当公开声明为不支持。federated 结构把这三件事拆成可以独立版本化的包，代价是多一层依赖关系要维护。测试按”门面逻辑—编解码—平台真实行为”三层分配，能避免把真机当成唯一验证手段。落地时守住四条纪律就够了：编解码只走约定的类型、能力缺失显式报错、长任务不占平台主线程、引擎重建后不残留状态。
