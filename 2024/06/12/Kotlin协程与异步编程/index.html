Kotlin 协程与异步编程

本文面向已经会写 Kotlin、但还没把协程放进真实工程的读者，只讲用法与工程实践：该用哪个 API、代码骨架长什么样、哪些写法迟早变成线上问题。主线口径是 Kotlin 1.9.x 与 kotlinx-coroutines 1.7/1.8 线；实现机制不在本文展开，需要追问“为什么”时，实现原理见同批《Kotlin 协程源码解析》。读完你应能判断一段异步代码该不该协程化、作用域从哪来、超时与异常放在哪一层。

为什么需要协程

协程要替换掉的是两种写法，痛点不同。第一种是阻塞线程：线程不免费，一条线程要预留栈空间（1 MB 量级，示意值），创建与切换也有成本；更要命的是容量，等待期间线程被占住，线程池大小就成了并发上限——CPU 空闲、请求全在排队。

第二种是回调，它不占线程，代价是控制流被切碎：

难处理的不是缩进，而是三件事：中途加一步串行就得再挖一层；想随用户退出而停止就得给每个回调存可撤销句柄；想整体 catch 就得手写转发链路。

协程的目标就一句话：看起来同步的代码，加上不占线程的等待。

还有一个必须先钉住的误解：协程不是并行工具。开 100 个协程不等于用 100 个核：协程管“等待怎么组织”，并行度来自线程数，线程数由调度器给、被核数封顶。计算要真并行靠多核线程池，等待要省钱才轮到协程。

挂起函数的写法与读法

挂起函数就是标了 suspend 的函数，读法比写法重要。

第一层语义是调用位置的限制：suspend 表示“这里可能等待”，因此只能在协程或另一个 suspend 函数里调用，编译器会直接拦下来。

于是出现“染色”：调用链上游都得能提供作用域，但返回类型不用变，不像 Deferred<Double> 或 Publisher<Double> 那样污染签名。

第二层语义是与“返回 Deferred 的函数”的区别，这是最容易选错的一处：

规则很直白：结果接下来就要用，写 suspend；只有要把两件互不依赖的事同时发出去，才换成 Deferred。它是延迟结果的句柄，一旦当参数或字段传来传去，“谁等它、谁取消它、谁管它的异常”就没人认领，症状是跑完没人取结果、页面销毁后请求还在发。可组合性同理：suspend 函数能层层复用，Deferred 只能在外层手工拼装；挂起本身怎么实现，见同批《Kotlin 协程源码解析》。

启动方式与作用域从哪里来

三个启动方式的选择，只回答两个问题：要不要结果，要不要等。

方式 适用场景 返回什么 最常见的错误
runBlocking main 函数、单元测试、把同步接口桥到协程 最终结果 在协程里、在 Android 主线程里随手用它
launch 不要结果，只要副作用（发请求、写日志、更新状态） Job，只能用来取消 拿它当“后台线程”，任务失败没人管
async 要结果，且需要先把多个任务同时发出去 Deferred，配合 await 起了 async 却忘了 await，异常与耗时都被推后

runBlocking 的定位要背下来：它是边界，不是工具。它把当前线程钉住直到内部协程树跑完，所以在协程里随手写它，等于把承载自己的线程变回同步阻塞，前面省下的成本一次还清。主线程上更糟：主线程被占住，内部那个 withContext(Dispatchers.Main) 出不来也回不去，界面直接卡死；服务端请求路径上写它，等于自己造一个线程瓶颈。确需在同步方法里等一次结果时，写成显式适配层，别散落在业务方法中间。

作用域回答的是“这批任务属于谁、谁负责收尾”。获取方式只有三种，按优先级排：

第一种，用生命周期对象自带的 scope。Android 的 lifecycleScope、viewModelScope 取消时机由组件状态决定，最省心；先问“有没有现成的 scope”，再考虑自己造。

第二种，自己造并明确寿命：一个长寿命的容器级 scope，加每条请求或每个作业临时的子 scope：

第三种是两个构建器。共同点是开一个“等完所有子任务才返回”的窗口；区别只在失败处理：coroutineScope 里一个子任务失败会连带取消兄弟并上抛异常，supervisorScope 里兄弟互不牵连。还有命名坑：coroutineScope 是构建器，CoroutineScope() 是工厂函数，后者造出来的作用域没人等，写错就变成“任务发出去就失联”。

GlobalScope 请在团队里明确禁用。它不属于任何一棵有寿命的协程树：页面关了、请求超时了、服务下线了，任务照样跑，异常也没有父级接收，“什么时候该停”彻底失去答案。

调度器选型与 withContext 的边界

只讲用法与判断；内部线程怎么排、队列怎么长，实现原理见同批《Kotlin 协程源码解析》。

调度器 适合的调用 不适合的调用
Dispatchers.Main 更新界面、读视图状态、和框架的回调线程打交道 任何耗时的读写与计算
Dispatchers.IO 磁盘读写、网络请求、数据库、下游 RPC 等以等待为主的调用 CPU 密集的计算
Dispatchers.Default 解析大 JSON、加解密、排序、图片解码等吃 CPU 的调用 大量长时间的阻塞等待
Dispatchers.Unconfined 极窄的调试场景；注意库里并没有 Unbounded 这个名字 任何业务代码

规则只有一句：按这段代码是在等什么、还是在算什么来选调度器。把 IO 放 Default 是最常见的错误——Default 线程数按核数配置，几条等待中的任务就把它占满，真正要 CPU 的任务反而排队，表现为吞吐下降而 CPU 利用率不高。Main 上做任何耗时操作，等于自己制造一次 ANR。

两个误解要拆掉。第一，切调度器不是“开了一个线程池”，IO 与 Default 是共享线程资源，切过去只是把任务提交到那一侧队列。第二，切调度器不提升并行度：withContext(Dispatchers.IO) { … } 依然串行；并行度由同时跑多少个任务决定，跟调度器名字无关。

withContext 的正确用法就两件事：把一段代码整体挪到合适的调度器，再把结果带回调用方的上下文。

两种典型误用：

误用一，拿它当超时用。withContext 没有超时语义，只保证块执行完才返回；里面的调用若不响应取消，它就一直等下去。超时是取消机制，要用 withTimeout 从外面包住，两者正交。

误用二，拿它包裹 CPU 密集代码当并行。嵌套几层依然顺序执行，只是每层换一次线程；要真并行就写四次 async 再 await。

结构化并发的工程含义

结构化并发落到代码上就一句话：子任务不会比父作用域活得久。coroutineScope { } 一返回，里面的任务就全部结束了。它治的是最难查的一类 bug——任务泄漏：只要作用域来自生命周期对象，忘记取消这件事就不会发生。

代价要一起接受：同一个 coroutineScope 里一个子任务抛异常会取消所有兄弟，异常再上抛给调用者，它保证不留半成功的状态。但兄弟本来互不依赖时它就成问题：批处理里第 3 条失败不该让另外 50 条回滚，头像加载失败不该让订单列表一起空白，这时必须换成 supervisorScope。

作用域写法 是否等子任务跑完 失败怎么传播
runBlocking { } 等 整棵树取消，异常抛到调用线程
coroutineScope { } 等 取消所有兄弟，异常上抛给调用者
supervisorScope { } 等 不牵连兄弟，异常由该子任务自己处理
CoroutineScope(SupervisorJob() + …) 不等，需要外部显式取消 交给 CoroutineExceptionHandler
GlobalScope.launch 不等，也没人负责取消 只能靠全局未捕获处理

团队约定：默认写 coroutineScope，确认任务彼此独立才升级为 supervisorScope，并在注释里写明理由；共享数据或事务边界的任务保持连带取消。

取消、超时与异常处理

取消的入口是 Job.cancel()：Job 进入不可逆的“取消中”状态，isActive 变假，等待中的挂起调用抛 CancellationException 收尾。关键认知是取消只在挂起点生效，不挂起的循环与第三方阻塞调用不会因一次 cancel() 停下。

超时有两个入口：withTimeout 抛 TimeoutCancellationException，withTimeoutOrNull 返回 null，按调用方要“感知异常”还是“走分支”来选。别在业务代码里 catch (e: Throwable)，那会把超时和取消一起吞掉，让上层以为任务正常结束；顺手 catch (e: CancellationException) 更糟，它直接破坏取消传播。要处理超时，只捕获 TimeoutCancellationException 并当成正常分支。

异常处理的坑都和“谁接管”有关：

第一段说明 CoroutineExceptionHandler 的边界：只有异常走到“没有父协程接管”的顶层时它才生效；在 coroutineScope 里父作用域接管并上抛，handler 一次也不会被调用。第二段是最常见的误读：以为 try 框住 launch 就能拿到它的异常，其实 launch 立刻返回，异常发生时那行早已执行完——想拿异常只有两条路，async 配 await 处捕获，或按作用域规则交给上层。runBlocking 则把异常原样抛到调用线程，所以测试里栈最完整。

兜底按平台分开：Android 让任务挂在 lifecycleScope、viewModelScope 上，界面层集中一处捕获展示；服务端固定一个容器级 SupervisorJob + CoroutineExceptionHandler 统一记日志与指标，请求路径上的异常仍交给 coroutineScope 上抛。

Flow 的使用面

Flow 首先是冷流：flow { } 构建出来时什么都不会发生，只有 collect 才真正开始，而且每 collect 一次就重新执行一遍。所以别把“创建了 Flow”当成“已经在拉数据”；要一次执行、多处消费，就得显式把它变热。

一对一改名用 map；一条变多条且要保序用 flatMapConcat；多路并发再合并用 flattenMerge，它的并发度直接放大下游压力，团队约定示例是 4 以内。StateFlow 管“现在是什么样”，有初始值、会去重、新订阅者立刻拿到当前值；SharedFlow 管“刚刚发生了什么”，replay 与 extraBufferCapacity 要显式设定，否则事件要么丢要么被重放。WhileSubscribed(5_000) 解决的就是“没人看就别再拉数据”。

背压只有三种策略，选错代价完全不同：

策略 什么时候用 代价
buffer 一条都不能丢，下游偶尔慢 用内存换时间，容量要设上限
conflate 只要最新值：进度、位置、行情 中间值被丢弃，有业务含义时别用
collectLatest 处理新值前先取消上一条的处理 上一条半途而废，有副作用时谨慎

与既有异步方案的对照与迁移

从 RxJava 迁过来，概念能一一对上：AndroidSchedulers.mainThread 对应 Dispatchers.Main，Schedulers.io 对应 Dispatchers.IO，Schedulers.computation 对应 Dispatchers.Default；Observable/Flowable 对应 Flow，Single 对应返回一次结果的 suspend 函数，Subject 对应 MutableSharedFlow，publish().refCount() 对应 sharedIn 加 WhileSubscribed。迁移别做大爆炸重写：新旧代码只在边界处互转，新模块直接写协程。C# 的 async/await 没有作用域树这层约束，Dart 的 Stream 与 Flow 形似但计算并行要靠 Isolate。

团队约定与场景速查

  1. 异步语义进类型，不进名字：suspend 说明“会等待”，xxxAsync 只留给真返回 Deferred 的函数。
  2. 挂起函数里不许阻塞：Thread.sleep、同步 socket 一律评审打回；躲不开就挪 Dispatchers.IO 并插 ensureActive()。
  3. scope 来源写死：界面用组件自带的，服务端用容器级的，禁止新建顶层作用域。
  4. 超时是默认项：对外调用一律带超时（团队约定示例：连接 3 秒、整体 10 秒）。
  5. 测试用 runTest：虚拟时间快进 delay，几小时的轮询几毫秒验完；推进用 advanceTimeBy。

顺序拿结果 直接调 suspend 函数 async 后立刻 await
两件事同时做 async 配 await 忘了 await

同步入口等结果 runBlocking 在协程或主线程里用
换线程跑一段 withContext 当成超时或并行
到点必须停 withTimeout、withTimeoutOrNull 顺手吞掉取消异常

小结

协程改变的是等待的组织方式，不是算力：它让顺序可读的代码不再占着线程，又用作用域把取消、异常和收尾变成结构约束。要立的规矩只有四条：作用域有来源、调度器按在等什么还是在算什么选、每处对外调用带超时、异常按接管关系找归宿；Flow 再补两条，冷流靠 collect 触发，背压按能不能丢选。Kotlin 2.0 与 K2 编译器在 2024-05-21 刚进入稳定版，当时尚未成为默认口径，升级需评估编译器兼容；本文这套用法在 1.9.x 与 1.7/1.8 线上稳定。
