Turborepo 与 pnpm monorepo 实践

本文记录一套前端 monorepo 的工程化口径：用 pnpm 9 管依赖与 workspace，用 Turborepo 1.x 管任务编排与缓存。适合正把多个包收拢进同一仓库、或者已经被慢构建和依赖漂移缠住的团队。

monorepo 解决什么问题，代价在哪

monorepo 的收益可以压缩成两件事：跨包复用与原子变更。

跨包复用指组件库、工具函数、类型定义这些代码能被多个应用共享。多仓库形态下，共享意味着发一次 npm 包、改一次版本号、在消费方升一次依赖，一次小改动要走完整条发布链路；收进同一仓库后，它变成一条 import 语句加一行 workspace 声明，代价从”发布协调”降为”路径协调”。原子变更则指一个意图能在一个 PR 里表达完：改一个组件的 props 要同时动实现、类型、两个消费方应用和它们的测试，多仓库下得拆成三四个互相阻塞的 PR，还得临时发 beta 版本串起来。

收益不是白拿的。仓库变大之后，会浮现三类原本不存在的成本：

  • 依赖解析成本：谁依赖谁、用仓库内还是仓库外的版本、同一个第三方包能不能只有一份，要显式表达并有工具兜底。
  • 构建编排成本：任务之间的先后顺序、并行度、失败传播，以及”这次改动到底要重跑哪些任务”，需要一层调度器。
  • 发布与权限成本：版本号从哪来、变更日志谁写、包作用域与 2FA/OTP 权限如何分配，需要流程与门禁。

也要先说清楚：并不是所有团队都该上 monorepo。只有一个两个应用、没有横向共享、协作人数也不多时，上面三类成本是净付出。判断标准不是”包多不多”，而是”跨包改动频不频繁”。

pnpm 侧的地基

安装模型：最小回顾

pnpm 把包实体放在按完整性哈希寻址的全局存储里，node_modules 只放符号链接指过去，同一版本的依赖在一台机器上只落盘一份。这个模型天生适配 monorepo：几十个包引用同一个依赖时实体仍是一份，新增包主要是本地链接，磁盘与安装时间都能压住（本文不给具体数字）。

严格安装与幽灵依赖

npm 与 Yarn 的经典安装会把依赖树扁平地铺在 node_modules 顶层。坏处是每个包都能顺手拿到别人的依赖：上游把 lodash 提到顶层后，下游没在自己 package.json 里声明也能 import 成功。这就是幽灵依赖，它不被察觉，直到上游升级或移除那个包，构建在你没动过的地方炸掉。

pnpm 的默认结构是严格隔离的：顶层只放直接声明过的依赖，其余按声明关系链接到指向存储的隐藏目录。没声明的模块解析不到，幽灵依赖在本地就报错，不会潜伏到上线之后。

public-hoist-pattern 解决的是插件发现问题：ESLint、Stylelint 这类工具运行时会按名字去顶层找插件包，严格结构让它们找不到，只提升这一小撮比全仓提升安全。only-built-dependencies 不是提升开关，而是安装脚本白名单——pnpm 9 默认不为所有依赖跑 preinstall/postinstall，需要原生编译或下载二进制的包必须显式列出。

至于壳层提升（shamefully-hoist=true），笔者的口径是当迁移期的止痛药、不当架构：它装出近似 npm 的扁平目录，代价是隔离性全部退回，收益是某些年久失修的工具链立刻能用。合理场景是从 npm/Yarn 批量搬迁的头几周，不合理场景是新仓库图省事；长期开着，等于承认依赖图的可信度不再由工具保证。

peer 依赖与多副本

React 报 Invalid hook call、Vue 报注入不到当前应用实例，在 monorepo 里多数不是代码问题，而是同一个运行时被装了两份：组件库把 react 声明成 peerDependency 期望由应用提供，可它自己在 devDependencies 里也写了 react，或者某个中间包用固定版本依赖了另一个大版本，严格安装就会在各自子树链出两份实体，两份各有独立的 hooks 调度状态与响应式作用域。

Turborepo 的任务图

pnpm 管住”依赖长什么样”，还要一层管”活儿怎么排”。Turborepo 把每个包里的脚本当作任务，任务间用依赖连成有向无环图，由它决定执行顺序、并行度和缓存边界。

要先说明：pipeline 是 2024 年上半年 1.x 的字段口径，配置结构一直在演进，把它当永恒 API 抄是踩坑的源头；落地时以所装版本文档为准。

三个语义要吃透。dependsOn 列的是同包内该任务开始前必须完成的任务；前缀 ^ 把依赖挪到拓扑方向，"^build" 读作”我依赖的 workspace 包的 build 先跑完，我的 build 再开始”，这是 monorepo 里最常见的正确形状；不写 ^ 就只在同包内找任务，漏了会得”下游先跑、上游还没编译”的错序。

拓扑约束外的节点彼此独立，执行器在它们之间并发，同时受全局上限约束（这个上限在 CI 容器里要显式收紧，团队约定示例：与 CPU 核数挂钩并给内存留余量）。cache: false 给 dev 这类不该缓存的任务，persistent 标记常驻任务。

任务图可以画得很朴素：

flowchart TD
  cfgA["config:build"] --> uiA["ui:build"]
  cfgA --> utilsA["utils:build"]
  utilsA --> webA["web:build"]
  uiA --> webA
  webA --> webTest["web:test"]
  uiA --> uiTest["ui:test"]

缓存：命中从哪来

缓存才是这套工具的价值来源。一次任务的缓存键大致由四类输入算出：本包参与哈希的文件内容、上游任务的哈希（上游产物变了，下游必须重算）、声明纳入的环境变量、包与配置的版本。指纹相同就复用上次归档的产物，任务本身根本不执行。

inputs 与 outputs 是这套机制的两个旋钮，也是最常出错的地方。outputs 声明哪些路径会被归档：写宽了把无关文件塞进归档，写漏了缓存到残缺产物。inputs 声明哪些文件参与哈希：写漏了改动感知不到，写宽了任何一个文件变动都会击穿缓存。两类症状要能反向定位：

  • 改一行代码却不重跑：多半是 inputs 收窄过头、产物路径不在监视范围，或改动落在被排除的目录里；先跑一次带详细日志的任务，看它给出的输入集合是否符合预期。
  • 每次全量重跑：通常是缓存键混进了不稳定输入——时间戳、随机目录名、绝对路径、构建时写入的版本号，或者 outputs 与实际产物对不上；定位靠逐个把可疑输入从哈希集合里摘掉再试。

远端缓存把指纹从”每台机器各自一份”变成”团队共享一份”：CI 跑完任务，产物按指纹上传；别人第一次构建时拿同一个指纹命中，直接下载而不必重跑。读写权限要分开看待——只有主干分支的流水线有写权限，PR 与本地开发默认只读。

红线是不要把密钥本身放进参与哈希的环境变量列表：把敏感值编进可被下载的缓存标识才是真问题。参与哈希的应当是影响产物、本身不敏感的值，比如 Node 版本、构建目标、特性开关的名字。缓存保留多久、命中率多少算合格，都是各团队自定的约定示例，本文不给行业数字，也不比较托管服务的定价与配额。

只跑受影响的部分

日常 PR 应该只跑被这次改动影响到的包，全量跑只在主干发布时合理。Turborepo 提供按变更范围过滤的能力：给定一个比较基准（通常是远端主干分支），它沿依赖图算出哪些包的文件变了、它们的下游有哪些包，把任务集收窄到这批包上。

按变更范围过滤的参数写法在 1.x 期间调整过，写进 CI 之前先跑一次 dry-run，确认过滤集合符合预期。

版本与发布

monorepo 里版本号要由流程产生，不能靠人在 PR 里手改。changesets 把”这次改动影响哪些包、属于哪种语义级别”写成变更文件，发布时再统一算版本：

version 与 publish 都发生在主干流水线上，平时只产生变更文件，合并与发版因此解耦。预发布通道的价值在长周期的破坏性改动：团队能在同一个候选版本线上联调，版本号带固定标签，不污染正式序列。

同仓的多个包要不要一起跳版本，是 fixed（锁定步长）与 independent（独立版本）之争：

维度 independent fixed 同组
版本含义 只反映该包自身的改动 组内一起跳，接口对齐优先
发布噪声 有改动才发，较低 任一次改动带动整组发版
使用者心智 需自行核对兼容矩阵 一句”整组同版本”即可
适用对象 可按需升级的工具库 一起成套使用的框架层套件

取舍看耦合面：一起演进、外部总是一起装的成套包用 fixed 组，被独立引用的库保持 independent。

CI 落地

CI 里有两类缓存要分工：依赖安装的缓存加速 pnpm install，任务产物缓存加速构建本身，两者不能互相替代。

要点有四个：并发上限按 runner 规格显式设；--frozen-lockfile 保证依赖图与提交里的锁文件一致；lint、typecheck、test 拆成独立任务，PR 才只跑需要的那部分，失败也能定位到具体包；CI 的命令与环境变量要能在本地原样跑通，失败才可复现。

五条反模式

  • 把整个仓库当一个包：依赖都写在根 package.json，包边界消失，变更范围与缓存一起退化成全量。
  • 在根装业务依赖：根依赖被所有包隐式共享，等于把幽灵依赖制度化，根只该装工具链。
  • 用 postinstall 做跨包复制或软链：这条边不在依赖图里，任务排序和缓存都看不见它。
  • 缓存键里塞时间戳或随机值：每次都是新指纹，命中率归零，要写构建时间就挪到发布步骤里。
  • 为了”统一”把所有配置抽成 shared 包：只有一个使用者的抽象没有收益，只有跨包发版的代价。

问题与配置对照

我要解决的问题 pnpm 侧配置 Turborepo 侧配置

运行时双实例 overrides 与 peer 纪律 typecheck 拆独立任务

发版漏包 publish 时替换 workspace 协议 changesets 的 version 步骤

小结

pnpm 与 Turborepo 的分工是一句话：前者保证依赖图可信，后者按这张图调度任务与缓存。配置项要能对应到症状——幽灵依赖找严格安装，双实例找 overrides，错序找 ^ 前缀，命中率找 inputs 与 outputs，发布混乱找 changesets。若仓库里只有一两个应用、跨包改动很少，这套机制的收益覆盖不了学习成本。真要上，顺序是先跑通 workspace 与严格安装，再引入任务图，最后谈远端缓存与发布流程。
