C# 与 Go 服务端编程对比

本文处理一个具体问题：同样做一个对外提供 HTTP 接口、对内读写数据库的后端服务，用 C# 写和用 Go 写，差别落在哪里。适合正在给新服务定语言、或者手上同时维护两套代码的读者。读完你应该能说清两件事：表达同一需求时谁要写的样板更少，工程约束把自由度放在哪一边。口径取写作时的稳定版本：C# 侧是 .NET 8 与 C# 12，Go 侧是 1.22。

对比口径与写作范围

先把范围钉住：假设两边需求完全相同，一个 REST 服务，若干领域对象，一个数据库，若干下游调用，跑在容器里。只比四件事：写代码时的心智负担、可用的表达手段、语言与运行时施加的工程约束、交付的部署形态。

不比速度。跨语言性能比较要固定负载、并发档位、机器与统计口径，还要处理运行时预热，条件不具备时得出的数字没有意义；本文不给吞吐或耗时结论，那部分属于同系列的实测篇目。与 Java 的对照另有专文，迁移方案也不在范围内：那是流程问题，不是语言问题。

类型系统与建模

建模：多态是怎么取得的

C# 的实现关系写在类型声明上，继承层次是显式的、可导航的。

Go 没有继承，也没有 implements 子句。类型之间的关系靠结构体组合与隐式满足接口建立，接口通常定义在调用方一边。

两段代码放在一起，组织差异就露出来了。C# 里“谁实现了这个抽象”是类型的固有属性，编译器与 IDE 能列出全部派生类，改抽象成员时影响范围一目了然，建模自上而下。Go 里“谁满足接口”要到赋值那一刻才被推导出来，包通常只暴露一两个方法的小接口，建模自下而上。代价也对称：C# 容易提前抽象出三层基类，Go 改方法名时报错点离定义较远，重构导航不如前者直接。

值语义的控制权也不同。C# 用 struct 与 record 显式区分值类型，record 还提供按值相等比较，写领域事件的快照很省事；Go 的结构体本来就是值类型，复制与否取决于你用值接收者还是指针接收者。

泛型：能用与不能用的边界

C# 的泛型在运行时也可用：闭合类型保留类型参数，因此能按具体接口注册依赖、用类型做缓存键。

Go 从 1.18 起有类型参数泛型，1.22 口径下成熟可用，但约束是类型集合而不是能力声明：类型参数上不能用运算符，不能在运行时反查具体实例化类型再分派，方法也不能带自己的额外类型参数。

判断标准因此很实用：排序、去重、查找这些 slices、maps 已覆盖的操作，Go 的泛型够用；需要运算符、通用数值算法或对类型参数做运行时分支的场景，只能逐类型手写、退化成 interface{ } 加类型 switch、或者生成代码。C# 没有这些限制，但闭合类型怎么注册、可空怎么区分，也要团队统一约定。

空值与错误处理：两条完全不同的路

错误传播的位置不同，直接把代码形状拉成了两样，这是日常写起来差别最大的一处。

C# 走异常。可空引用类型注解解决的是“这个引用可能为 null 吗”的表达问题，编译期做流分析、把信息写进注解，运行时并不强制，来自外部边界的空引用还要自己防。真正的错误传播不写在调用点旁边，而在调用栈上。

Go 走 error 值。可能的失败是函数返回值的一部分，传播要逐层手写，用 %w 保留原因，由上层用 errors.Is、errors.As 判定语义而不是匹配字符串。

两种形状的代价很清楚。C# 的正常路径干净，代价是要靠文档与约定说明“这个方法会抛什么”；一旦有人把异常当成控制流，成本就同时转到运行时和读者的注意力上。Go 没有隐藏的跳转，每次调用都得当场决定错误怎么处理，好处是评审时一眼看出哪条分支没管，坏处是每个函数尾部都有形状相同的判错样板。panic 只留给不变量被破坏、初始化无法继续这类不可恢复的情况，业务校验失败与下游超时不属于它；入口层的恢复机制是最后一道防线，不是错误通道。

并发模型：Task 异步与 goroutine

两边都把“等下游”这件事做得很轻，但抽象的粒度与失效模式完全不同。

C# 的写法是 async/await 加 Task。一个异步方法编译成状态机，await 处挂起、续体回到线程池继续；Task 是“进行中的工作”的句柄，可以存储、组合、等待。两条约定要写进团队规范：耗时方法把 CancellationToken 放在最后一个参数并在循环里检查；不要用 .Result 或 .Wait() 同步等待异步方法，那会占住线程池线程，高并发下演化成排队甚至死锁。

Go 的写法是 goroutine 加 channel 加 context.Context。启动一个并发任务几乎不增加语法成本；channel 用来传结果、信号或所有权；上下文只承担取消、超时与请求域元数据，不拿来传业务参数。本节只讲怎么用，不讲调度器内部。

同一个扇出聚合需求——收到请求后并发调多个下游，全部返回后汇总——两边各写一遍。

flowchart TD
    A[请求进入] --> B[扇出多个下游调用]
    B --> C1[调用一]
    B --> C2[调用二]
    C1 --> D[汇总]
    C2 --> D
    D --> E[返回响应]
    B -.取消或超时信号.-> C1
    B -.取消或超时信号.-> C2

失效模式最值得对比。C# 这边，一个没被 await 的 Task 是静默的：异常不会冒到调用方，只在收尾阶段以未观察异常的形式露一次面；Task.WhenAll 只把第一个异常交给你。Go 这边常见事故是泄漏而不是丢异常：忘了取消、无人接收的 channel 发送、不做取消检查的等待组，都会让 goroutine 一直活着。前者症状是“错误不见了”，后者是“内存和连接一直涨”，两边都靠评审加静态检查兜住。

依赖注入与项目组织

.NET 把容器做进了运行时与模板：注册三行，作用域语义由框架保证，Scoped 实例在请求结束时释放，日志、选项、认证、健康检查这些横切关注都以服务形式挂到同一条流水线上。

Go 语言与标准库都不提供容器，事实上的惯例是显式构造函数注入：依赖写在参数列表里，装配集中写在一个入口文件里，包边界承担组织职责。

差别不在谁更高级，而在谁替你做了事。C# 里容器替你管生命周期与释放、把横切能力串起来，代价是依赖关系有一部分要到运行时才定：服务注册在什么作用域、会不会把请求级实例带进单例，都得靠约定与检查。Go 里依赖图完全静态，读入口文件就知道程序怎么拼起来，代价是装配代码全部手写。规模变大时，前者的复杂度落在容器规则上，后者落在装配长度与分包上。

数据访问、配置与日志

数据访问：SQL 的控制权在哪里

C# 侧两个主流库的定位一句话能说清：EF Core 管对象与表之间的同步，你写 LINQ、它生成 SQL 并跟踪变更；Dapper 只把手写 SQL 的结果集绑到类型上。选哪个，实质是决定 SQL 的生成权交给谁。

Go 侧的基线是 database/sql：它抽象了连接、语句、行游标和事务，但不做对象建模，绑到结构体要在 Scan 里手写循环。在此之上，映射增强类库站在“还是你写 SQL，只是少些样板”这一端，带关联与钩子的 ORM 类库则接近 EF Core 的思路。这里不比性能，只比心智：EF Core 的建模落点是类型与导航属性，表结构是模型的产物；Go 的建模落点是行结构与列名，查询是你写出来的事实。迁移也要做：前者由模型变动驱动生成，后者多是有序脚本，排查路径不同。

配置与日志

.NET 的配置是层叠的：默认值、appsettings.json、按环境区分的文件、环境变量、命令行依次覆盖，最后绑定成强类型选项类，容器负责在解析时给你。

Go 的标准库没有配置层叠这件事，现实做法是环境变量加 flag，复杂时引入第三方配置库；结构化日志则已经不需要外部依赖，log/slog 在 Go 1.21 进入标准库，1.22 口径下直接可用。

两边在日志上的取向接近：都认可结构化字段，而不是把上下文拼进消息文本。差别在谁来接——C# 的 ILogger 是抽象，由注入提供；Go 的 *slog.Logger 是具体值，随构造函数往下传，换实现就在装配处换。

部署形态与团队生态

交付产物

Go 编译出的是一个静态可执行文件，交叉编译只是把目标平台写进环境变量；镜像里可以只放这一个文件，运行时依赖为零，交付面通常更薄。

.NET 的两种发布方式区别只在运行时归谁带：框架依赖的产物小，但镜像要选对基础镜像并跟补丁；自包含把运行时带在产物里，跨环境一致，代价是每次发布都绑定一个运行时版本。启动与配置注入也不同：Go 一般执行二进制、从环境变量读配置、自己处理退出信号；.NET 由主机层加载配置层叠与中间件，再把停止信号转成宿主的关闭流程。本文不给镜像体积与启动耗时的数字。

团队与生态

存量资产决定成本。Windows 服务、企业内网集成与既有 .NET 代码库是 C# 一侧的顺势；云原生工具链、命令行工具、需要单文件交付的平台组件是 Go 一侧的母语区。上手成本也不对称：C# 新人要先吃下容器作用域、选项绑定位置、中间件顺序等框架约定；Go 的语法几天能读完，但按 Go 的方式切包、把接口放在调用方，往往要更久才顺手。风格统一上，Go 同一个需求几乎没有第二种写法，新旧代码看起来一样；C# 是多范式，不把约定写进评审清单，几种写法会在同一个仓库里长期并存。

三条反例结论

对比要给结论，就得先说它什么时候不成立。

  • 复杂领域模型加多依赖装配时，C# 明显更省事：值对象、不变量、按类型注册的抽象与成体系的配置都有现成表达位置；换成 Go，同样的规则会变成结构体加方法集加手写装配，样板量容易失控。
  • 平台工具、小团队、部署规范严格时，Go 明显更省事：服务多但都不大、要交叉编译给多种环境、运维只面对一个二进制文件，这些诉求与 Go 的语言取向和交付形态天然对齐。
  • 两种情况下这个对比没有意义。一是瓶颈不在应用进程：响应时间由数据库查询和下游决定时，换语言不改变曲线。二是团队已深度绑定某栈：组件库、监控接入、发布流水线与人员经验是真实成本，表达差异不足以抵消。

把前几节压缩成一张评审时能直接摊开的表。最后一列是判断依据，不是结论。

小结

两种语言的分工不在能力而在取向：C# 把表达能力与运行时信息当作资产，代价是要用团队约定把多范式收敛成一种写法；Go 把写法统一与交付简单当作资产，代价是要手写别人替你生成的部分。建模时，C# 的多态沿显式声明的层次组织，Go 的接口沿调用方的需要拼装；错误传播时，C# 放在栈上，Go 放在每个调用点旁边；并发时，C# 要小心没人等的 Task，Go 要小心没人收的 goroutine。所以先问领域模型与配置有多复杂，再问交付环境与团队存量在哪一侧——这两组答案通常就给出结论，速度问题留给实测。
