MobX 与 Redux 的对比

同一段业务逻辑，Redux 团队写出来是 action type 常量、action creator 与 reducer 三件套，MobX 团队可能只有一个带 @observable 的类。两者都能让 React 应用的状态变得可维护，但背后的心智模型几乎相反。本文不比较 API 的数量，而是从心智模型、更新方式、响应粒度、调试手段与团队协作成本几个角度拆开看，帮助你在真实项目里做出有依据的选择。

一个共同的出发点

React 本身是视图库，setState 只管组件内部状态。多个页面、多个层级共享同一份数据时，把状态逐层下传（当时常说的 prop drilling）会让中间层被迫接收无关的 props，数据结构一调整就引发连锁修改。于是社区形成共识：把共享状态提到组件树之外，组件只负责读取与触发变更。

Redux 与 MobX 都建立在这个共识上：状态集中、变更入口收敛、组件靠订阅而非父组件重传感知变化。真正的分歧在于——状态变化该由开发者显式描述，还是由框架自动推导。Redux 选前者，把每次变更变成可序列化、可重放的事件；MobX 选后者，让状态自己携带「谁在观察我」的信息。

版本上，Redux 4.0 本月刚发布，公开 API 基本没变，从 3.7 升级几乎不用改业务代码，配套 react-redux 仍是 5.x。MobX 处在 3.x 与 4.x 并存阶段，4.x 依赖 Proxy 拦截属性，不再支持 IE 11，要兼容老浏览器就得停在 3.x。

Redux 的心智模型：用事件描述变化

Redux 的核心约束只有三条：单一 store、状态只读、变更必须由纯函数完成。三者合在一起，把应用变成一台状态机——给定旧状态和一条 action，必然得到同一个新状态。

这里的 Object.assign({}, todo, { done: !todo.done }) 是当时最常见的不可变写法，成本不高，但每一次嵌套更新都要手动展开路径上的每一层；状态层级一深，代码就啰嗦，这也是 immutable.js 与各类 helper 流行的原因。

数据流单向闭合：dispatch(action)、reducer 汇总新状态、store 通知订阅者、react-redux 映射回组件，任何状态都能追溯到「哪条 action 造成的」。收益是确定性：action 可序列化，能记录、比较、重放；代价是表达成本，改一个布尔值也要定义常量、写 creator 与分支。Redux 没有隐藏成本，而是把它前置。

MobX 的心智模型：让状态自己会说话

MobX 把问题换了一个提法：如果每个被观察的属性都知道谁在读它，那么属性一变，通知就能精确送达，开发者不必手写「怎么通知」。

它的概念分四类：可观察状态（observable） 是被追踪的数据；派生值（computed） 由状态算出并缓存，依赖不变就不重算；动作（action） 修改状态并把多次赋值合并成一次通知；反应（reaction / autorun） 是变化后执行的副作用，渲染组件就是一种反应。

add 里直接 push，toggle 里直接赋值。MobX 不要求构造新对象，而是拦截属性读写来感知变化；读代码的人看到的只是普通的面向对象写法。不用装饰器时，也能用 observable({...}) 写成函数式：

更新方式与样板代码的对照

把差别落到「改一个字段」这件小事上最容易看清：Redux 重建路径，MobX 就地修改。

前者冗长，但每次变更都产生新对象，旧引用不会被意外影响；后者简洁，代价是引用共享——把 store.a.b 缓存到不参与追踪的地方，它会在你不知情时变化。

样板代码的差距同样明显：Redux 侧完成「新增待办」要常量、creator、reducer 分支、mapDispatchToProps 四段；MobX 侧是一个 @action 加一个 @observer 组件。这也是 MobX 最常被引用的卖点——同样功能，行数往往只有一半。

但行数少不等于维护成本低。Redux 的样板是约束的载体：常量集中一处，一眼看到系统支持哪些操作；reducer 是纯函数，天然可测；action 是数据，天然可存。MobX 用装饰器压缩了这些约定，约定就得改由团队规范承载。

维度 Redux MobX
状态存放 单一 store，一棵不可变树 一个或多个 observable 对象
变更方式 dispatch action，reducer 返回新状态 在 action 中直接赋值
变更来源 显式，集中在一处 分散在各 store 的方法里
响应机制 订阅 store，connect 比较映射结果 渲染时收集依赖，属性级通知
派生数据 reselect 手动缓存 @computed 自动缓存
调试核心 action 日志、时间旅行 依赖图、action 边界
学习曲线 概念多但规则少，边界清晰 概念少但语义隐式，容易踩坑

响应粒度：浅比较与依赖追踪

React 的重渲染成本，让「状态变了要更新哪些组件」成为真问题。Redux 侧由 react-redux 承担：connect 在每次通知时调用 mapStateToProps，把返回对象与上次浅比较，相等就跳过更新。由此有两个隐含要求：更新必须不可变，否则引用不变、比较恒等，组件不会刷新；映射结果要小，否则无关字段变化也会重渲染。派生数据多了，映射函数里的计算会重复执行，这时用 reselect 缓存：

MobX 侧不需要这层缓存。@observer 组件渲染时记录自己读过哪些 observable，渲染结束即建立依赖；某属性变化，只有读过它的组件被标记更新。粒度是属性级而非组件级，computed 也只在依赖变化时重算。

这套机制很强，但有三个失效点：组件忘了 @observer，依赖不会被收集；在渲染函数外读取 observable 并解构成普通对象，依赖被记在错误的函数上；渲染时整体遍历大数组，组件就依赖了整个数组。

换句话说，Redux 把「何时重渲染」交给纯函数与比较控制，规则明确但要手工优化；MobX 把它自动化了，前提是遵守使用姿势。规模变大后，差别往往不在性能，而在排查不更新问题时手上是日志还是依赖图。

调试与异步：账本、地图与流程归属

Redux 最有力的调试能力来自 action 的可序列化：把 action 记下来，就能逐条回放、跳到任意历史节点、对比前后状态。Redux DevTools 提供的正是这套体验，配合 redux-logger 还能直接看到 action 名与 payload。它有前提：reducer 必须是纯的、状态必须可序列化，一旦在 reducer 里改参数或塞入 Date、类实例，时间旅行就会错乱；带副作用的流程回放时也只重放结果，不会重发请求。

MobX 没有等价的时间旅行，状态是可变对象，快照要自己实现。mobx-react-devtools 侧重另一件事：可视化组件的重渲染次数与依赖关系，能看出组件依赖了哪些 observable、一次变更触发了谁，排查「改一个字段为何整页重渲染」时比日志有效。spy 则暴露内部事件流，配合 useStrict(true) 把「修改必须走 action」变成运行时检查：

放进五人团队看，差异更具体。Redux 概念多：store、action、creator、reducer、中间件、connect、不可变更新；新人前两周痛苦，但职责清晰，看一份目录和两个例子就能上手，阅读路径也固定——顺着 action type 全局搜索即能找到唯一分支，评审容易达成一致。MobX 概念少，新人第一天就能写出能跑的代码，隐患是规则隐式：忘了 @observer、赋值落在 action 外、observable 被提前解构，都不会在编译期暴露，往往表现为偶发的不更新。团队若不把「统一 store 写法、修改走 action、组件加 observer」写成规范并配 lint，半年后风格容易分裂。装饰器还带来环境成本：要配 babel-plugin-transform-decorators-legacy 与 class properties 插件，TypeScript 项目打开 experimentalDecorators，叠加 Babel 6 生态与测试转译，是新人搭环境的第一道坎。

还有一点：Redux 的约束迫使团队提前回答状态设计问题——哪些数据进 store、实体如何按 id 归一化；MobX 因为改起来方便，容易演变成「哪里需要就加一个 observable」，半年后引用关系难以梳理。工具给了自由，架构责任就回到人身上。

常见误区与选型建议

误区一：MobX 不需要架构。 它只省了样板，没省分层。domain store 与 UI store 如何划分、跨 store 依赖谁持有、服务端数据与本地状态如何区分，一样要回答；少了 action 常量这层显式目录，更得靠目录与命名表达边界。

误区二：Redux 一定要上 redux-saga。 多数后台的表单与列表用 thunk 足够，只在需要取消、竞态处理与复杂编排时才值得引入 saga。为「架构完整」先上 saga，等于让新人同时学两套模型。

误区三：两者能解决所有状态问题。 服务端缓存、请求去重、分页游标，手写都要不少代码，当时社区已在用 Apollo 这类专门方案；另一个共同坑是把派生数据也塞进状态，同一事实存两份，同步逻辑到处漏。

至于选型，笔者建议按下面的顺序判断，而不是先比代码行数：

  1. 团队经验与调试需求。有人熟练其中一套就优先用它；线上排查严重依赖状态回放时，Redux 的账本很难被替代。
  2. 状态结构与变更频率。表单、拖拽、实时联动这类「读得多、改得碎」的界面，MobX 的细粒度追踪能让代码明显变短；流程长、参与人多、迁移需要审计的系统，Redux 的显式事件更稳。
  3. 协作规模。多人并行、评审标准要统一时，Redux 的单一写法省沟通；两三个人的小团队快速迭代，MobX 更划算。
  4. 环境约束。兼容 IE 11 只能用 MobX 3.x；不想引入装饰器就写函数式，或干脆选 Redux。
  5. 迁移成本。已有 Redux 项目不必为少写几行样板而重写；新项目也不必因「大厂都在用」放弃更贴合场景的方案。

多方案矩阵与迁移步骤是另一个话题。需要强调的是：两者在 2018 年都经过大量生产验证，选错的代价通常不是「跑不起来」，而是「半年后维护得很难受」，依据应是团队与场景，而不是 GitHub 星数。

小结

Redux 与 MobX 解决的是同一个问题——把共享状态从组件树里抽出来，但对「状态如何变化」给出了相反的答案。Redux 要求把每次变更写成可序列化的事件，用纯函数推导新状态，换来确定性与可回放；MobX 让状态自带依赖信息，用赋值触发精确通知，换来简洁与开发速度。前者的成本在样板与不可变更新，后者的成本在隐式规则与架构自律。选型先看团队经验与调试需求，再看状态结构与变更频率，最后才比较代码量；两者都不是银弹，派生状态与服务端缓存仍需单独设计。
