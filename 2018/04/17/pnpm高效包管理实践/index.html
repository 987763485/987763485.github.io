pnpm 高效包管理实践

npm 与 yarn 把 node_modules 铺成一片平坦的草原，装得快，却把依赖之间原本的层级关系抹掉了。pnpm 换个方向回答同一个问题：用全局内容寻址仓库加硬链接，让每个包在磁盘上只留一份，同时把 node_modules 恢复成严格的树。本文从 node_modules 的老毛病讲起，依次说明 pnpm 的存储机制、严格结构、日常命令、锁文件、迁移与常见坑，适合已经用着 npm 或 yarn、想把包管理再往前推一步的团队。读完你应该能判断项目值不值得换，也能独立完成一次迁移。

node_modules 的三个老问题

先把问题摆清楚，才能理解 pnpm 为什么长成这个样子。当时 Node 8 LTS、npm 5.6、yarn 1.x 是主流，绝大多数项目的 node_modules 都来自同一种策略：扁平化提升。

所谓提升，是指安装器为减少重复，把依赖尽量往顶层挪。项目声明了 A，A 依赖 B，B 依赖 C，最终顶层往往同时躺着 A、B、C。好处是路径短、同一版本只出现一次；代价是目录结构和 package.json 说的不是一回事。

第一个麻烦是幽灵依赖。代码里写 require('B') 能跑通，可 package.json 里根本没有 B。它能跑，纯粹是因为 A 把 B 提到了顶层，Node 顺着目录往上找就找到了。这种依赖没有任何声明，升级 A 时如果 A 换掉了 B，或者换了版本，构建就会在毫无预兆的地方断掉。这类代码看上去完全合法，问题只在运行时才暴露。

第二个麻烦是版本冲突被掩盖。两个依赖各自需要不同大版本的同一个包时，提升只能满足其中一个，另一个被塞进父包的 node_modules 里。谁被提升、谁被嵌套，取决于安装顺序与依赖树形状，不同机器上偶尔会算出不同结果，而且在 package.json 与锁文件里都看不出来。

第三个麻烦是重复安装。提升只在单个项目内部生效，项目之间互不相干。同一份 lodash 在十个仓库里就有十份拷贝，磁盘和带宽都在为同一批字节反复付费。

pnpm 的思路不是继续优化提升算法，而是换掉存储方式：包只在全局仓库里存一份，项目通过硬链接引用，层级按真实依赖重建。三件事一起做，才同时解决了重复、幽灵依赖和版本覆盖。

内容寻址仓库与硬链接

pnpm 在用户目录下维护一个仓库，通常叫 store。它的组织方式叫内容寻址：文件按内容哈希命名与分目录，内容相同就必然落到同一个位置。这样一来，同一个包的同一个版本无论被多少个项目引用，磁盘上都只有一份实体。

项目安装时，pnpm 不复制文件，而是创建硬链接。硬链接是文件系统层面的概念：同一个文件可以有多个名字，多个路径指向同一份数据，删除其中一个名字不影响其余。项目里的 node_modules/lodash/index.js 与 store 里那份是同一个 inode。

这带来两个直接结果。第一，安装的磁盘开销从「项目数乘以依赖体积」降到「所有项目用到的不同内容之和」，第二个项目装同样的依赖几乎是瞬间完成，因为链接比复制便宜。第二，store 必须被当作只读区域：项目和仓库共享同一份数据，任何一处写入都会同时改到另一处。手工编辑 node_modules 里的文件，改的其实是全局那份。

硬链接只在同一个文件系统内有效，所以 store 与项目的位置很关键。默认 store 在用户主目录下，同一块盘时一切正常；项目放在另一块磁盘、移动硬盘、虚拟机共享目录或者网络盘上时，硬链接建不出来，pnpm 退化成复制：安装仍然成功，但磁盘收益消失，速度也回到与 npm 相近的水平。遇到时把 store 指到项目所在的同一分区即可。

仓库里的内容不会自动回收。删掉一个项目只是删掉它那一侧的硬链接，store 里的数据还在，因为可能还有别的项目在用。团队共用一台机器、或者频繁切换分支时，隔一段时间清一次比较稳妥。

严格的 node_modules

pnpm 装完之后，node_modules 顶层只有 package.json 里明确写下的那些包，外加 .bin 一类的辅助目录。每个包自己的依赖不会往顶层挪，而是留在它自己该在的位置，具体实现上是通过一个隐藏的虚拟目录配合符号链接完成的。站在 Node 的解析规则看，只有声明过的包能被找到。

严格结构还顺带解决了版本覆盖。两个依赖需要不同大版本的同一个包时，pnpm 不挑选、不提升，各自在自己的位置上取到各自需要的版本，互不干扰。这比 npm 的混合策略更容易预测：目录结构就是依赖关系本身，不必在脑子里模拟安装器的决策。

凡事有代价。严格结构要求每个包的依赖声明完整，而生态里总有一些包没做到：它们在自己的代码里 require 了一个只在开发时存在的包，或者依赖某个被提升上来的间接依赖。这类包在 npm 与 yarn 下能跑，在 pnpm 下会失败。遇到时先确认是不是自己的项目漏了声明；确认是上游包的问题后，可行的办法是在项目里把它缺的包显式装成直接依赖，作为兼容补丁，并写清楚原因。不要为了绕过一个包就把 node_modules 拉平，那等于关掉了 pnpm 最有价值的部分。当时也提供过这类强行展开的兼容开关，只适合做对照实验，不要留在配置里。

安装与日常命令

当时的安装方式很朴素，pnpm 还没有随 Node 分发，需要用 npm 全局装一次；它本身也是 JavaScript 写的，Node 8 LTS 足够。

进入项目后，第一条命令就是安装依赖：读取 package.json，把缺的包从仓库链接进来，同时生成或更新锁文件。

新增与删除依赖的写法接近 yarn，-D 是开发依赖，可选依赖也有对应参数。当时 pnpm 的命令行还在演进，pnpm install <pkg> 与 pnpm add <pkg> 在不同小版本里都出现过，团队统一一种写法即可。

与 npm、yarn 的对照见表，三者对 dependencies、devDependencies、scripts 的理解一致，差别只在命令拼写与安装策略。

操作 npm yarn pnpm
安装全部依赖 npm install yarn pnpm install
新增依赖 npm install pkg yarn add pkg pnpm add pkg
新增开发依赖 npm i -D pkg yarn add -D pkg pnpm add -D pkg
移除依赖 npm uninstall pkg yarn remove pkg pnpm remove pkg
执行脚本 npm run build yarn build pnpm run build
升级依赖 npm update yarn upgrade pnpm upgrade

锁文件与团队协作

锁文件记录「这次安装究竟解析出了哪些版本」，让不同机器、不同时间装出来的树尽可能一致。npm 用 package-lock.json，yarn 用 yarn.lock，pnpm 用自己的格式：当时 1.x/2.x 一代写在 shrinkwrap.yaml 里，之后改名为 pnpm-lock.yaml，本文按后者称呼，具体文件名以文档为准。

三种锁文件的语义相似，都记录解析版本、下载地址与完整性校验值，但格式互不兼容，也没有工具会去读另外两个的文件。混用的后果很直接：仓库里同时存在两种锁文件时，用不同工具的人会得到两棵不同的树，CI 的结果取决于 CI 用了哪个工具。

规则很简单：一个仓库只保留一种锁文件，并提交进版本库。迁移时删掉旧锁文件，让 pnpm 重新解析；担心回退就从 git 历史里取回。

锁文件也要进代码评审。依赖升级、间接依赖变动、校验值变化都会体现在 diff 里，一个不起眼的间接依赖换了版本，可能带来行为差异。锁文件与 store 是两件事：前者决定装哪些版本，后者决定字节从哪里来。

从 npm 或 yarn 迁移

迁移会同时改变磁盘布局和依赖可见性，所以要按顺序做，每一步都能回退。建议先在一个中等规模、测试覆盖尚可的仓库上试点。

第一步，清理现场。删掉 node_modules，删掉现有的锁文件，确认 package.json 里的依赖声明是完整的。这一步不要图省事跳过，残留的 node_modules 会让后面的问题变得难以判断。

第二步，把安装、构建、测试、lint 全部跑一遍。安装阶段的报错多半是网络或仓库位置问题；构建与测试阶段的报错才有价值，通常指向两类原因：某个依赖没声明却被使用，或者某个包的安装脚本没按预期执行。逐条记下来，不要急着改配置。

第三步，处理幽灵依赖，这是迁移中最常见的返工点。表现是构建时报 Cannot find module，而那个包在 npm 下明明存在。办法就是前面说的补声明，版本选与调用方兼容的范围；补完重新安装，再跑测试。

第四步，确认工具链。TypeScript、ESLint、Jest 和打包工具通常会顺着符号链接读文件，多数情况无需配置；少数插件自己拼路径，解析不到时先看它是否支持符号链接。验收标准是 CI 通过，而不是本机能跑。

第五步，切换 CI 并提交锁文件。CI 使用锁定文件模式，要求锁文件与 package.json 一致，不允许在 CI 上静默更新。参数名以当时文档为准。切换后观察一段时间，确认没有偶发的安装失败。

第六步，保留回退路径。合并前确认主干仍能用旧方式构建一次；合并后若出现无法定位的问题，回退成本应该只是一次 revert。团队人多时同步一句「本仓库从今天起用 pnpm」，并写进 README。

monorepo 与 workspace

多包仓库是 pnpm 比较舒服的场景。根目录放一个 pnpm-workspace.yaml，声明包的分布，然后在根上执行一次安装，所有子包的依赖会一起装好。

子包互相引用时不需要先发版。pnpm 把工作区的包以符号链接放进引用方的 node_modules，改完源码立刻生效。整个仓库只有根目录一份锁文件，所有子包的解析结果记录在一起。

与 yarn workspaces 的差别在于布局。yarn 习惯把公共依赖提升到根 node_modules，子包共享一份，省空间、配置简单，但子包也能看到自己没声明的包。pnpm 保持每个子包独立的 node_modules，内部包用链接串起来，隔离性与单仓库一致；代价是老 monorepo 里靠提升才能跑的脚本会暴露出来，需要逐个补声明。

常见坑与 CI 实践

第一个坑是混用。同一个仓库里今天 npm install、明天 pnpm install，会得到两套结构不同的 node_modules，锁文件也会互相覆盖。约定一种工具，并在 README 与 CI 脚本里写死，比任何口头约定都可靠。

第二个坑是安装脚本与原生模块。node-sass、phantomjs 这类包安装时要下载二进制或执行 postinstall 脚本（常常调用 node-gyp），失败时先看编译环境，再跑一次重建命令，不要直接删锁文件重装。

第三个坑是符号链接带来的路径问题。Node 默认把符号链接解析成真实路径，某些工具读到的位置会落在 store 里，打包配置里可以用 resolve.symlinks 一类的选项调整；编辑器索引不到依赖时优先怀疑这一点。

第四个坑是跨文件系统。前面说过硬链接的边界，容器、共享目录、外接盘都属于这一类，表现是安装变慢、磁盘占用没有下降。

CI 的做法相对固定：缓存 store 目录，key 用锁文件的哈希；安装使用锁定文件模式，锁文件与 package.json 不一致就失败，绝不允许 CI 顺手更新。缓存命中时几乎不需要网络，缓存失效时也能保证版本与开发机一致。

小结

pnpm 的价值不在「又一个包管理器」，而在它换了一种存储与布局方式：内容寻址仓库让同一份内容只存一次，硬链接让项目引用而不复制，严格结构让依赖关系回到 package.json 里。收益是磁盘占用下降、跨项目安装变快、幽灵依赖无处藏身；成本是工具链兼容性要验证、团队要改掉混用的习惯。它适合依赖与仓库都多、对安装一致性有要求的团队；只有一两个小项目时，收益不足以抵消迁移成本。真要动手，就从删掉 node_modules 与旧锁文件、跑一遍完整测试开始，遇到找不到的包先补声明，而不是关掉严格模式。
