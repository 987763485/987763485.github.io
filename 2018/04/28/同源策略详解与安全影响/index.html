同源策略详解与安全影响

同源策略是浏览器最基础的安全边界，却也是最容易被含糊带过的概念。本文从“什么是源”讲起，逐层解释它限制了什么、没有限制什么，再落到 CORS、JSONP、document.domain 与 postMessage 的实际写法，最后讨论配置过宽带来的安全影响，并给出一份自查清单。适合已经写过前后端分离项目、却被跨域报错反复困扰的开发者阅读。

一、什么是源：scheme、host 与 port 的三元组

浏览器判断两个页面是否“同源”，只看三样东西：协议（scheme）、主机名（host）、端口（port）。三者完全一致才算同源，任何一项不同都算跨源。注意这里说的是“完全一致”，不是“看起来差不多”。

第一种是协议不同。http://www.example.com 与 https://www.example.com 是两个源。很多人在本地用 HTTP 调试，上线换成 HTTPS，接口地址却没改，浏览器立刻报跨域。这不是服务端坏了，而是源变了。

第二种是端口不同。http://www.example.com 默认端口是 80，http://www.example.com:8080 则是另一个源。前端开发服务器常跑在 8080 或 3000，后端跑在 8000，两边即使主机名一样，也天然跨源。端口省略时按协议补默认值：HTTP 补 80，HTTPS 补 443，所以 https://example.com 与 https://example.com:443 是同源的。

第三种是子域不同。https://a.example.com 与 https://b.example.com 不同源，https://example.com 与 https://www.example.com 也不同源。子域之间可以共享 Cookie（取决于 Cookie 的 Domain 属性），但这与同源判断是两回事，后文会专门说明。

源只比较这三项，路径、查询参数、片段标识都不参与，所以同一个域名下的不同应用仍然同源。浏览器在发出 CORS 请求时会带上 Origin 请求头，值就是当前页面的源，形如 https://www.example.com，不带路径。这个头由浏览器自动添加，页面脚本无法伪造，这也是后面 CORS 校验能够成立的前提。

二、同源策略到底限制什么

很多人把同源策略理解成“不能跨域发请求”，这是不准确的。它限制的核心是“读取”和“操作”，而不是“发出”。具体来说，主要限制以下几类行为。

第一，DOM 访问。不同源的窗口之间不能随意读取对方的 DOM。比如父页面里嵌了一个跨源 iframe，父页面拿不到 iframe 内部文档的节点，iframe.contentDocument 会返回 null，访问 contentWindow.document 则会抛出安全异常。这样做的目的是防止恶意页面通过 iframe 嵌入银行或邮箱页面，再读取用户输入的内容。

第二，window 对象的访问。跨源窗口之间只能访问极少数属性和方法，比如 window.postMessage、window.close、window.location 的写操作（赋值跳转），而 location.href 的读取、document、localStorage 等一律被拦截。这种“有限放行”的设计，是为了在隔离的同时保留必要的通信能力。

第三，XHR 与 fetch 的响应读取。用 XMLHttpRequest 向另一个源发请求，请求本身可以发出去，但响应会被浏览器拦下，脚本读不到 responseText，控制台会给出跨域提示。fetch 同理，它返回的 Promise 会 reject。这里的关键词是“读不到”，而不是“发不出”，下一节会展开这个区别。

第四，Canvas 像素读取。跨源图片画进 canvas 后会被标记为“被污染”，getImageData 与 toDataURL 都会抛异常，防止把别的站点的图片内容偷出来做识别。

需要特别澄清的是 Cookie。Cookie 的发送规则由 Domain、Path、Secure、HttpOnly、Expires 等属性决定，与“是否同源”是两套机制。一个请求即使跨源，只要目标域匹配 Cookie 的 Domain，浏览器仍会带上它。反过来，同源请求也未必带 Cookie，比如 Cookie 的 Path 不匹配；而 HttpOnly 只限制脚本读取，不影响 Cookie 随请求发送。把“同源”当成“Cookie 一定发送”或“跨源一定不带 Cookie”，都是常见误解。

用一张图概括同源策略的放行与拦截关系：

flowchart TD
    A[页面发起跨源操作] --> B{操作类型}
    B -->|加载资源| C[允许: script img link iframe]
    B -->|发送请求| D[允许: 请求到达服务端]
    B -->|读取响应| E[拦截: 需 CORS 授权]
    B -->|访问 DOM| F[拦截: 跨源窗口隔离]
    C --> G[但无法读取内容或像素]
    D --> H[副作用已发生]

这张图想说明一件事：拦截点往往在“读”这一侧，而“写”和“加载”通常已经放行。理解这一点，才能理解后面 CSRF 为什么成立，以及 CORS 为什么需要在服务端配合。

三、不受同源限制的加载：JSONP 的由来与局限

同源策略从不阻止页面引用外部资源。<script src> 可以指向任意域名，<img> 可以加载任意站点的图片，<link rel="stylesheet"> 可以引入外部样式表，<iframe> 也可以嵌入别的站点。浏览器允许这些标签发起请求，因为它们是 Web 的基本组成方式，如果连图片和脚本都不能跨站引用，页面就没法正常工作了。

但“能加载”不等于“能读取”。脚本会被执行，可页面拿不到脚本文件的文本内容；图片会显示，可 canvas 读不到像素；iframe 会渲染，可父页面进不去它的文档。这个“执行但不暴露内容”的特性，恰好被早期开发者利用，于是有了 JSONP。

JSONP 的思路很直接：既然 <script> 能跨域加载并执行 JavaScript，那就让服务端返回一段“调用某个函数的代码”，而不是纯数据。页面先定义一个全局函数，再把函数名通过查询参数传给服务端，服务端拼出 callback({...}) 返回，脚本一加载，函数就被调用了。

JSONP 在 jQuery 时代非常普遍，$.ajax({ dataType: 'jsonp' }) 一行就能用。它的局限也很明显：只能发 GET，无法设置自定义请求头，无法读取真实的 HTTP 状态码，超时和错误处理只能靠定时器兜底。更麻烦的是安全模型——服务端返回的内容会被当作脚本执行，一旦接口被劫持或参数校验不严，等于把任意脚本请进了页面。2018 年新项目基本不再选它，CORS 已经足够成熟；只有在维护老接口、对接不肯改服务端的第三方时，才会偶尔见到。

四、跨域写与读的区别：请求已经到达服务端

理解了“加载不受限”，就能理解跨源请求的真正边界。用 XMLHttpRequest 或表单向另一个源提交数据时，请求会正常发出，服务端会正常收到、正常处理，数据库该写还是写。浏览器拦截的是响应回到页面之后的读取环节，控制台那句跨域报错，描述的是“你无权看结果”，不是“请求没发出去”。

这个区别的安全含义很大。攻击者做一个页面，让受害者浏览器向银行站点提交转账表单，请求会带上受害者的 Cookie，银行照常执行；攻击者读不到响应没关系，钱已经转出去了。这就是 CSRF 能够成立的根本原因：攻击者利用的是“写”的放行，而不是“读”的绕过。防护手段另有专文讨论，这里只强调一句：不要因为“前端读不到响应”就认为接口是安全的。

反过来，如果业务只关心“对方有没有收到”，比如打点上报、日志收集，那么一个 img 请求或 navigator.sendBeacon 就够了，根本不需要 CORS。设计接口时先问自己：这次跨域，是真的要读数据，还是只要把数据送出去？答案不同，方案完全不同。

五、CORS 的基本流程

CORS（Cross-Origin Resource Sharing）是一套由浏览器执行、服务端配合的授权机制。浏览器在跨源请求里自动带上 Origin，服务端如果愿意开放，就在响应里回一个 Access-Control-Allow-Origin（下称 ACAO），值可以是具体的源，也可以是 *。浏览器拿到响应后比对两者，匹配才把内容交给脚本。

请求分两类。简单的 GET、HEAD、POST，且 Content-Type 限于 application/x-www-form-urlencoded、multipart/form-data、text/plain 时，浏览器直接发出，不预检，服务端回 ACAO 即可。一旦用到 PUT、DELETE，或者自定义请求头、application/json，浏览器会先发一个 OPTIONS 预检，问清楚“能不能用这个方法、能不能带这些头”。服务端要用 Access-Control-Allow-Methods、Access-Control-Allow-Headers 明确回答，预检通过后才发真实请求。

flowchart TD
    A[脚本发起跨源请求] --> B{是否简单请求}
    B -->|是| C[直接发送并带 Origin]
    B -->|否| D[先发 OPTIONS 预检]
    D --> E{服务端允许方法与头}
    E -->|否| F[浏览器拦截]
    E -->|是| G[发送真实请求]
    C --> H[检查 ACAO]
    G --> H
    H -->|匹配| I[脚本读到响应]
    H -->|不匹配| F

Access-Control-Max-Age 用来缓存预检结果，单位是秒。设得太短会多一次往返；设得太长，调整允许头后客户端仍按旧规则走，容易误以为配置没生效。

六、带凭据的跨域请求

默认情况下，跨源 XHR 与 fetch 不带 Cookie，也不带 HTTP 认证信息。要让浏览器带上它们，前端必须显式开启：XMLHttpRequest 设置 xhr.withCredentials = true，fetch 传 credentials: 'include'。需要提醒的是，IE 11 不支持 fetch，项目中若还要兼容它，得引入 polyfill，或者继续用 XHR。

前端开启之后，服务端的配合更严格：ACAO 必须是具体的源，不能是 *；同时要返回 Access-Control-Allow-Credentials: true。这两个条件缺一不可。测试环境若没带 Cookie，通配符的问题就不会暴露；一旦带上凭据，浏览器直接拒绝，报错却往往只说跨域。

还有一个容易被忽略的头：Vary: Origin。当服务端按请求的 Origin 动态回写 ACAO 时，响应内容就随 Origin 变化。如果中间有 CDN 或反向代理缓存，没有 Vary: Origin 就可能把 A 站点拿到的 ACAO 缓存下来，再发给 B 站点。轻则 B 站点跨域失败，重则把授权信息错配给不该拿的源。只要 ACAO 是按 Origin 动态回写的，就应当加上这个头。

Cookie 本身是否发送，仍由 Cookie 的 Domain、Path、SameSite 等属性决定，CORS 只负责“允不允许脚本读响应”。两者别混为一谈：CORS 配好了，Cookie 也可能因 SameSite 或 Path 不匹配而没带上。

七、document.domain 与 postMessage

在 CORS 普及之前，同主域不同子域之间有一个“土办法”：两个页面都执行 document.domain = 'example.com'，浏览器就把它们当成同源，可以互相读取 DOM。这段代码必须两边都写，只写一边不生效；而且只能向上放宽到当前域的后缀，不能设成完全无关的域名。

它的风险在于“放宽”的粒度太粗。a.example.com 与 b.example.com 一旦都降到 example.com，其中任何一个子域只要出现 XSS，或者子域本身托管了用户内容，攻击者就能借这个被放宽的源去读主站的页面数据。2018 年这段 API 仍然可用，但已经是明确的遗留方案，新项目应当用 postMessage 或 CORS 替代。

postMessage 是更可控的跨窗口通信方式。发送方调用 otherWindow.postMessage(data, targetOrigin)，第二个参数指定“只把消息交给哪个源”，必须写成具体的源。接收方监听 message 事件，并同时校验 event.origin 与 event.source，确认消息来自预期的页面，再做后续处理。

八、常见误区排查

第一，把“同站”当成“同源”。a.example.com 与 b.example.com 在 Cookie 语境下可能算同一个站（可注册域名相同），但在同源判断里是两个源。讨论 Cookie 的 SameSite 时说的是“站”，讨论 XHR 和 DOM 时说的是“源”，两者不能互相替代。

第二，端口和协议写错。ACAO 里必须带端口（默认端口可省略），https://example.com 与 https://example.com:8443 不匹配。页面从 HTTPS 调 HTTP 接口，还会先被混合内容策略拦下，根本到不了 CORS 这一步。

第三，预检结果被缓存。改了允许头却“没生效”，先看 Access-Control-Max-Age，再清缓存或换时间戳重试。

第四，开发环境的 proxy 掩盖了问题。webpack-dev-server 的 proxy 是让开发服务器转发请求，浏览器看到的是同源，自然不会触发 CORS。这套配置只解决本地开发，不能证明生产环境的 ACAO、Cookie、预检都正确。上线前要用真实域名做一次跨域验证。

九、安全影响与自查清单

CORS 配置过宽，本质上是把接口开放给任意站点。最常见的是直接回写请求里的 Origin，再配上允许凭据，这等于任何页面都能以用户身份读取数据；其次是长期使用通配符，或者连 null 源也一并放行。攻击者不需要攻破服务器，只要诱导用户打开一个页面，就能借用户的浏览器完成读取。

内网与本地服务更容易被忽视。很多团队认为“只有内网能访问”，于是接口不做鉴权、跨域全开；但用户的浏览器就处在内网中，恶意页面可以借它去访问这些地址。本机调试端口同理，宽松配置会成为现成的突破口。

上线前可以按下面几条自查：

  • ACAO 使用明确白名单，不反射任意 Origin，也不允许 null 源
  • 带凭据时 ACAO 精确匹配，Access-Control-Allow-Credentials 只对可信站点开启
  • 方法与请求头按需放开，不直接复制一套“全允许”配置
  • 动态回写 ACAO 的响应加上 Vary: Origin
  • 不把 Origin 当身份凭证，服务端仍要做会话与权限校验
  • 测试、预发、内网服务的跨域配置与生产环境同等审查

小结

同源策略的核心是 scheme、host、port 三元组，它限制的是读取与 DOM 操作，而不是请求的发出。跨源加载一直可行，JSONP 正是利用这一点，但只支持 GET、缺乏错误处理，已不适合新项目。CORS 通过 Origin 与 ACAO 完成授权，非简单请求还要经过预检；带凭据时不能用通配符，并要注意 Vary: Origin。document.domain 仍可用但粒度过粗，跨窗口通信应优先用 postMessage 并校验来源。最后，跨域配置是安全边界的一部分，过宽等于把接口交给整个互联网，务必按清单定期复查。
