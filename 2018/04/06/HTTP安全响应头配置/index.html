HTTP 安全响应头配置

很多团队把 HTTPS 证书装好就认为传输层已经安全了，但浏览器还有一半的防线藏在响应头里：能不能降级到 HTTP、能不能被别的站点用 iframe 套住、脚本能从哪些源加载、Referer 会不会把内网地址带出去，全都由几个几十字节的头部决定。本文按“先讲语义、再给配置、最后排顺序”的方式，把 2018 年主流浏览器已经支持的安全响应头过一遍，重点是它们之间的组合关系与 Nginx 上的落法。

先划清作用边界

安全响应头是浏览器侧的策略声明。服务端在响应里写下这些字段，浏览器收到后据此收紧自己的行为：把 http 请求自动升级为 https、不再猜测资源类型、拒绝把页面放进别人的框架、限制脚本与表单的目标。它防的是“用户浏览器被诱导着做错事”，属于纵深防御里的一层。

它防不了的事情同样要清楚。第一，攻击者用 curl 或脚本直接打 API，根本不经过浏览器，响应头一点作用都没有，参数校验、鉴权、限流仍然必须在服务端做。第二，未知的响应头会被浏览器安静地忽略，老版本 IE 与部分国产双核浏览器对内联脚本的限制、对 frame-ancestors 的支持都不完整，不能把它当成硬性保证。第三，头配错会直接造成业务故障：一个过严的 CSP 能让整站脚本失效，一个 includeSubDomains 能把没上证书的子域打到不可访问。

不配置也是一种配置，而且是最不安全的默认值：浏览器会按内容嗅探 MIME、跨站请求会带上完整 Referer、任何站点都能用 iframe 嵌入你的登录页。安全头不是锦上添花，而是把默认行为改回可预期状态。

Strict-Transport-Security：先短后长，最后才谈 preload

Strict-Transport-Security（下文简称 HSTS）只在 HTTPS 响应里才有意义。浏览器收到后会把域名和 max-age 记进本地存储，在这段时间内，凡是访问该域名的 http 请求，都会在发出前被改写成 https，证书报错时也不允许用户点“继续访问”。它挡的是降级跳转与 SSL stripping，却挡不住首次访问就被劫持的请求；证书链与 301 迁移步骤本文不展开。

三个参数有明确的递进关系，配错顺序的代价很大：

  • max-age：单位是秒。第一次上线建议先给一个很小的值，例如 300 或 86400，观察一两天，确认所有子路径、所有客户端都不会因为强制 HTTPS 出问题，再提高到 31536000。写下去之后，在到期前无法通过删掉响应头来撤销，只能靠浏览器缓存到期。
  • includeSubDomains：把策略扩展到所有子域。这一条要求你对子域有完整掌控，任何一个只提供 HTTP 的内部系统、测试域名、第三方托管页面，都会在策略生效后直接不可访问。
  • preload：表示愿意被收录进浏览器内置的 HSTS 列表。提交有硬性门槛，通常要求 max-age 不少于一年、带 includeSubDomains、且所有子域都能正常提供 HTTPS；而撤销要等下一次浏览器版本更新才生效，周期以月计。除非域名长期稳定，否则本文不建议一开始就加。

内容类型与框架：nosniff 和 X-Frame-Options

X-Content-Type-Options: nosniff 的作用是禁止浏览器做 MIME 嗅探。没有它时，一个被声明为 text/plain 的文件如果内容像 HTML，IE 与部分 Chrome 场景仍会按 HTML 解析；用户上传的图片、文本、日志文件就可能变成存储型 XSS 的载体。加上之后，浏览器严格按 Content-Type 处理：script 与 style 标签的资源类型不匹配就直接拒绝执行。

效果完全依赖服务端把类型写对。静态资源由 Nginx 的 types 决定，接口返回 JSON 必须显式写 application/json；如果 JS 文件被错误地标成 text/plain，nosniff 会让整站脚本加载失败，页面看起来“什么都没坏，就是不能点”。上线前用 curl 抽查几类资源的类型，比事后排查便宜得多。

X-Frame-Options 用来拒绝被其他页面嵌入，取值只有 DENY 与 SAMEORIGIN 两个可靠选项。规范里还有 ALLOW-FROM uri，但 Chrome 一直没实现，Safari 与 IE 的行为也不一致，不要用它来做“只允许某合作方嵌入”的需求。需要白名单时应该用 CSP 的 frame-ancestors，它能写多个源和通配符，是同一个问题的更新答案。两者可以同时发送：老浏览器认 XFO，新浏览器看到 frame-ancestors 就以它为准。点击劫持的攻击手法与验证方式另有专文，这里只强调配置层面的两个坑：一是同一响应里出现两个不同取值的 XFO，不同浏览器的处理不一致，有的直接整页拒绝；二是只给首页加了头，登录后的业务页漏配，等于没防。

Referrer-Policy：按用途收缩来源信息

浏览器默认的 Referer 策略是 no-referrer-when-downgrade：https 页面跳到 https 页面时，把完整的来源 URL 带上，包括查询串；只有跳到 http 时才不发。这意味着一张外链图片、一个第三方统计脚本，都能拿到你后台地址里的订单号或用户标识。Referrer-Policy 就是用来改写这个默认值的。

几种常用取值可以按“信息量从少到多”来理解：

  • no-referrer：一个字节都不发。最干净，但会打断依赖 Referer 的统计归因、防盗链和部分第三方登录回跳校验，适合后台管理界面，不适合对外站点全量使用。
  • same-origin：同源请求发完整 URL，跨源请求完全不发。适合内部系统与 API 站点。
  • strict-origin-when-cross-origin：同源发完整 URL，跨源只发源（协议加域名加端口），协议降级时不发。它在可用性与隐私之间最平衡，是多数业务站点的推荐值。
  • origin：所有请求都只发源。适合前端完全独立部署、又需要保留粗粒度来源信息的场景。
  • unsafe-url：任何情况下都发完整 URL，包括 https 降级到 http。不要用。

CSP 与 Feature-Policy：限制资源与限制能力

Content-Security-Policy 是这批头里能力最强、也最容易配坏的一个。它的定位是给页面加一份白名单：脚本、样式、图片、字体、表单提交目标、可嵌入的框架来源，都能逐项声明。配上之后，即使某处输出转义漏了，注入的脚本也会因为不在白名单里而无法执行，XSS 从“可以执行任意代码”降级为“控制台里一串报错”。Level 2 的 nonce-、sha256- 与 report-uri 在 2018 年已经可用，足够支撑常规落地。一个能作为起点的最小配置：

Expect-CT 与安全头的上线顺序

Expect-CT 是这批头里最新的一个，Chrome 从 61 版开始支持。它对接的是证书透明度（Certificate Transparency）机制：CA 签发的每张证书都会提交到公开日志，站点通过在响应里声明策略，要求浏览器检查自己拿到的证书是否带了合法的 SCT 记录。写法如下：

上线顺序按“配错之后能否快速回滚”来排：

  1. 先摸底：用 curl 抽查首页、登录页、API、静态资源、错误页，把现状记下来，确认反向代理与 CDN 有没有自己加头。
  2. 上无害项：X-Content-Type-Options、X-Frame-Options、Referrer-Policy。配错最多是某个页面嵌不进来或统计口径变化，回滚只需删一行。
  3. 上报告类：CSP 先用 Content-Security-Policy-Report-Only 收集违规，Expect-CT 先不要 enforce。这一步不改行为，只产生日志。
  4. 收紧：根据报告修完内联脚本与第三方源，再把 CSP 切成强制模式，同时加 Feature-Policy。
  5. 最后动 HSTS：从很小的 max-age 起步，稳定后加长，includeSubDomains 单独作为一次变更，preload 另议。

逻辑很简单：前四步出问题只是局部功能异常，改得回；HSTS 出问题是整站访问不了，在 max-age 到期前无法撤销。

Nginx 的 add_header 继承陷阱

配置安全头最常踩的坑不在头的语义，而在 Nginx 的继承规则：add_header 只在当前层级没有同类指令时才继承上层，一旦某个 location 里写了任意一条 add_header，父级 server 里的全部 add_header 都会失效，而不只是同名的那个。

缓存、CDN 与验证方法

安全头是响应的一部分，会被一起缓存。给静态资源设了 Cache-Control: public, max-age=31536000，就意味着旧的头也要在原缓存里待上一年；改完配置不刷新 CDN，一部分用户拿到的仍是旧策略。做法是 HTML 用 no-cache 走协商缓存，让新头尽快生效；静态资源维持长缓存，发版时按目录刷新。CDN 还有两个高频问题：一是边缘节点缓存了 HTML，回源一次之后头就固化了；二是控制台里另配了一份安全头，与源站的头叠加成重复值，或者把 Expect-CT、Feature-Policy 这类新头直接丢掉。上线前一定在边缘节点上验证，而不是只看源站。

验证本身不复杂。浏览器 DevTools 的 Network 面板选中请求，看 Response Headers，顺手确认 Content-Type 与预期一致；命令行用 curl -s -D - -o /dev/null https://example.com/ 打印响应头，比 curl -I 可靠，因为 -I 发的是 HEAD 请求，部分应用对 HEAD 与 GET 返回的头并不相同。抽查范围要覆盖首页、登录页、带参数的详情页、API、404 页和一条 301 跳转，301 响应同样需要 HSTS，否则跳转链上会留一个空档。在线扫描工具可以快速给个总览，但它们通常只抓首页，评分高不代表每个路径都配全了。最后提醒一句：开发与测试环境的 Nginx 往往没有这段配置，等上线才发现 CSP 挡住了内联脚本，所以配置要跟站点配置一起进版本库，环境之间只差参数，不差结构。

小结

安全响应头是浏览器侧的策略声明，能收紧降级、嗅探、嵌入、来源泄露与脚本执行这些默认行为，但替代不了服务端的校验与鉴权。落地时按风险排序：先上 nosniff、X-Frame-Options、Referrer-Policy 这类可随时回滚的头，再用 Report-Only 收集 CSP 与 Expect-CT 的违规，稳定后收紧，HSTS 放在最后并从短 max-age 起步。Nginx 上要特别小心 add_header 的层级继承与状态码范围，公共头抽成片段显式 include，避免某个 location 一行缓存配置把整组安全头冲掉。配置进版本库、在边缘节点验证、覆盖错误页与跳转响应，才算真正配完。
