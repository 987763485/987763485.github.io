前端安全之 XSS 攻击与防护

把用户输入原样拼进页面，是前端最古老也最顽固的错误。XSS（Cross-Site Scripting，跨站脚本）并不依赖某个框架漏洞，它利用的是浏览器对 HTML 与 JavaScript 的解析规则：只要不可信数据落在了本该写代码的位置，浏览器就会把它当代码执行。本文从 XSS 的本质讲起，依次梳理三类攻击的数据流、几种常见上下文的编码方式，以及富文本、框架转义和 Cookie 属性的边界，最后给出一份可以照着做的排查清单。读者不需要安全背景，但需要写过表单回显和 DOM 操作。

XSS 的本质：数据被当成了代码

先看一个最小场景：页面上有一个搜索框，提交后服务端把关键词回显在标题里：

如果 keyword 的值是“前端安全”，浏览器渲染出“搜索结果：前端安全”，一切正常。如果它的值是 <img src=x onerror=alert(1)>，模板引擎原样输出后，浏览器看到的不再是一段文字，而是一个合法的 img 标签；图片加载失败，onerror 里的脚本被执行。同一份数据，在文本的位置是数据，在标签的位置就是代码。

关键不是输入里有没有 script，而是这段数据落在 HTML 的哪个语法位置。浏览器不会因为数据来自用户输入就降低信任，它只认语法。安全领域把这类问题拆成三个要素：

  • Source（来源）：不可信数据的入口，如查询参数、表单字段、location.hash、第三方接口返回、document.referrer。
  • Sink（汇点）：数据最终进入的位置，如 HTML 字符串拼接、innerHTML、模板输出、eval。
  • Context（上下文）：汇点所处的语法环境，HTML 正文、属性值、URL、JavaScript 字符串，各自需要不同的编码。

一次成功的 XSS，就是一条从 Source 到 Sink、中间缺少正确编码的路径。防护因此可以归结为一句话：数据进入汇点之前，按它所在的上下文做编码。

XSS 的危害常被低估。脚本运行在目标站点的源下，能读取页面内容、以受害者身份发请求、篡改界面做钓鱼；存储型漏洞还能借转发自动扩散，最终指向账号接管。

三类 XSS 与它们的数据流

按数据停留的位置，XSS 分为反射型、存储型和 DOM 型，三者的差异在数据从哪来、经过谁、最终落在哪里。

反射型 XSS 的数据不落库，服务端把当前请求里的参数直接写回响应。典型入口是搜索页、错误提示页和跳转提示页：

服务端把 q 解码后拼进 HTML，脚本便在受害者浏览器里执行。攻击者需诱导用户点击构造好的链接，所以叫“反射”；单次影响有限，但等于给钓鱼邮件提供了一个可信域名的落地页。

存储型 XSS 的数据先入库，再随页面渲染输出，评论区、昵称、站内信都是高发区。攻击者提交一次，所有打开该页面的用户都会中招；它也稳定地出现在页面源码里，因而常被扫描器发现。

DOM 型 XSS 的特殊之处在于：服务端响应完全正常，脚本是在浏览器端拼出来的，数据可能来自 location.hash、location.search 或 localStorage。看一段典型的错误写法：

三者的防护手段相同，都是按上下文编码；分类的价值在于排查时知道往哪看。

HTML 上下文转义：五个字符与它们的边界

最常见也最基础的防护，是把数据在插入 HTML 正文之前做实体编码。HTML 中有五个字符具有语法意义，需要分别处理：

字符 实体 不转义的后果
& &amp; 可能构成实体，改变后续解析
< &lt; 开启新标签
> &gt; 闭合标签，破坏结构
" &quot; 逃出双引号属性值
' &#x27; 逃出单引号属性值

一个可靠的实现要注意顺序：& 必须最先替换，否则后续替换产生的 &lt; 会被二次编码成 &amp;lt;，页面上就会出现字面量。

很多事故来自“只过滤 <script>”。XSS 不只有 script，<img onerror>、<svg onload> 都能执行脚本；HTML 解析器还会把大小写混写、多余空格的畸形输入纠正成可执行结构；过滤器作用在字符串而非语法位置上，换个属性上下文就失效。黑名单永远在追赶新标签，白名单式的“把危险字符变成文本”才是封闭的。

还要明确转义的适用边界：它只对 HTML 正文和带引号的属性值有效。把转义结果放进 <script> 或 href，问题依然存在，因为那已经是另一种语法环境。

DOM 型 XSS：认识危险的汇点

DOM 型 XSS 的入口几乎都在前端，因此识别“哪些 API 会把字符串当成 HTML 解析”比记住 payload 更重要。下面这些汇点需要重点盯防：

  • element.innerHTML、element.outerHTML：把字符串当 HTML 解析。
  • element.insertAdjacentHTML(position, html)：同样走 HTML 解析器。
  • document.write()、document.writeln()：写入即解析，还会破坏文档结构。
  • jQuery 的 .html()、.append()、.prepend()、.before()，传入字符串时同样会解析标签。
  • 框架提供的“原始 HTML”入口，如 React 的 dangerouslySetInnerHTML、Vue 的 v-html。

富文本：白名单净化而不是黑名单

评论区、邮件正文、CMS 编辑器都要保留一部分 HTML，不能把所有标签都转义成文本。这类场景必须做净化（sanitize）：解析 HTML，按白名单保留标签与属性，其余丢弃。

为什么不能用正则做黑名单？HTML 不是正则友好的语言：标签可嵌套、可带任意属性、可大小写混写，浏览器还会容错修复残缺标签。一段看起来“没有 script”的字符串，解析后可能就带上了可执行节点。白名单只放行明确需要的东西，黑名单只能追着已知形态跑。

净化应该做两次：服务端入库前净化，防止脏数据影响导出报表、App 端 WebView 等读取方；前端渲染前再净化，防止历史脏数据和接口篡改。两次共用一套白名单，存入与显示才一致。只在前端做，等于把防线交给每个调用方；只在后端做，覆盖不了前端二次拼接。

纵深防御：Cookie、CSP 与排查习惯

Cookie 属性的作用边界

HttpOnly 让脚本读不到会话 Cookie，XSS 便无法直接带走凭证，但它只提高成本：脚本仍能以受害者身份发请求、读取页面、篡改 DOM。Secure 要求 Cookie 只在 HTTPS 下发送，防的是链路嗅探。SameSite 在 Chrome 51 之后可用，Lax 与 Strict 减少跨站请求携带 Cookie 的机会，主要面向 CSRF，此处不展开。三者都是减损手段，不能替代输出编码。

CSP 是最后一道网

CSP 通过响应头限制脚本来源，禁掉内联脚本与 eval，再用 nonce 或 hash 放行必要的内联块，能拦住“注入成功但执行不了”的场景。上线时先用 Content-Security-Policy-Report-Only 收集报告，再逐步收紧。指令与灰度方法在 CSP 专文中展开。

输入校验与输出编码的分工

输出编码必须是主防线：同一份数据在不同上下文需要不同编码；输入校验无法预知数据落在哪个汇点；数据还可能来自第三方接口和历史库存，根本不经过表单。输入校验仍有价值，限制长度、类型与字符集能缩小攻击面，但它是补充。倒过来做，就会得到“校验很严、渲染照样出事”的系统。

排查清单与常见坑

手工验证很朴素：在每个输入点填入带唯一标记的字符串，提交后在 Elements 面板看它最终以文本还是节点出现；DOM 型问题在“查看源代码”里看不到。代码审计先搜关键词：innerHTML、outerHTML、insertAdjacentHTML、document.write、dangerouslySetInnerHTML、v-html、eval、new Function、location.hash，再逐个确认来源与编码。

常见坑集中在几处：只在前端转义，直接调接口就绕过去了；只在后端转义，前端二次拼接又引入风险；富文本入库时净化，展示时却换一套规则重新渲染；URL 参数不经判断就进 DOM；把 escape 或 encodeURIComponent 当万能编码，两者都面向 URL，前者早已废弃，后者连单引号都不编码，放进 HTML 正文毫无作用；以为加了 HttpOnly 就万事大吉。

小结

XSS 的本质是不可信数据进入了代码位置，防范的核心是按上下文编码。三类攻击数据流不同，排查时要从 Source 追到 Sink。HTML 正文、属性、URL、JavaScript 各有编码规则，HTML 转义不能跨界。富文本要用白名单净化，框架转义只覆盖它自己渲染的那一层。HttpOnly、SameSite 与 CSP 是减损和兜底，主防线始终是输出编码。
