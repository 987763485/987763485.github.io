Token 认证机制设计

做过几个前后端分离的项目之后，很多人都会遇到同一组问题：登录状态到底放在服务端还是客户端？把 JWT 塞进 localStorage 行不行？用户点了退出，服务端怎么让那张还没过期的凭证立刻失效？本文从会话 Cookie 与 Token 的差别讲起，逐层拆开 JWT 的结构、签名、载荷、刷新与存储，最后给出一份可以直接照着实现的校验清单。读完你应该能为一个中小型系统画出完整的 Token 生命周期，并知道每一步的取舍在哪里。

从会话 Cookie 说起：状态放在哪一边

传统的登录方案依赖服务端会话。用户提交账号密码，服务端验证通过后在内存或 Redis 里生成一条记录，把随机生成的 session id 写进 Cookie，浏览器之后每次请求自动带上它。服务端拿到 id 去查存储，查到记录就知道这是谁。整个方案的核心是：凭证本身没有含义，含义存在服务端。

Token 认证把这件事反过来。服务端签发一张自包含的凭证，里面直接写明用户标识、签发时间、过期时间，再用密钥签名。之后服务端不再查会话表，只要验证签名和几个字段，就能确认这张凭证没有被篡改、也没过期。状态从服务端搬到了凭证本身。

两者没有绝对的优劣，差别体现在几个具体的工程问题上。会话方案注销很干脆，删掉那条记录即可，但每次请求都要访问一次会话存储，多实例部署时还得把存储做成共享的。Token 方案省掉了这次查询，横向扩展很自然，代价是“让一张已签发的凭证提前作废”变得麻烦。另外，会话 Cookie 由浏览器自动携带，天然带着 CSRF 风险；Token 放在请求头里则由前端代码显式附加，CSRF 面变小，但对 XSS 更敏感。

顺带澄清一个常见的混淆：OAuth 2.0（RFC 6749）用 access token 表示授权结果，JWT（RFC 7519）定义了 token 的一种编码格式，一个是授权框架，一个是凭证格式。本文只讨论后者在登录场景里的用法。

这里有个必须说清楚的误解：Base64URL 是编码，不是加密。它只是把二进制换成 URL 安全的字符集（把 + 换成 -、/ 换成 _，并去掉末尾的 =），任何人都能解开，不需要密钥。所以载荷里写什么，等于把什么公开写在明信片上。签名的意义只在于防篡改：别人可以读，可以改，但改完之后算不出正确的签名，服务端一验就知道。

这也解释了 JWT 为什么容易变长：每多一个字段，字符串就长一截，而它要出现在每个请求头里。把头像 URL、权限列表、部门树全塞进去，请求头会超过某些代理默认的缓冲区大小。载荷要克制。

RS256 是非对称签名，私钥签发、公钥验证。好处是公钥可以随便分发，多个服务共享一把公钥做校验，谁也不需要持有能签发的私钥；代价是签发慢一个数量级，密钥管理更麻烦。

选择哪一种，取决于信任边界。单体应用里所有代码都在同一台机器上，HS256 足够；一旦验证方和签发方不在同一个信任域内，比如网关、多个微服务、第三方合作方，就该用 RS256，否则每个验证方都握有伪造凭证的能力。

历史上最出名的 JWT 漏洞就出在算法字段上。有些实现会读头部的 alg，照着它选验证逻辑。攻击者把 alg 改成 none 并删掉签名段，库如果放行，一张伪造凭证就通过了。另一种是算法混淆：服务端用 RS256，公钥公开，攻击者把 alg 改成 HS256，用公钥当 HMAC 密钥重新签名，校验方跟着头部走就正好对上。

载荷设计：标准声明与不该放的东西

RFC 7519 定义了一组注册声明，名字短、含义固定，常用的有：

声明 含义 说明
sub 主体 用户或资源的唯一标识，不要用可变的昵称
iss 签发者 谁签的，验证方据此决定用哪把钥匙
aud 受众 这张凭证是给谁用的，防止拿 A 服务的 token 调 B 服务
exp 过期时间 必须校验
nbf 生效时间 早于这个时刻不接受，可选
iat 签发时间 可用于判断凭证年龄、配合改密时间做失效
jti 唯一编号 撤销名单、防重放时需要

exp、nbf、iat 都是 NumericDate，单位是秒，不是毫秒。这是一个高频错误：前端拿 Date.now() 直接比对 exp，结果相差一千倍，写出来的判断永远成立。

判断标准只有一条：凭证会经过浏览器、日志、代理和监控系统，凡不能公开的内容都不要放。密码、身份证号、手机号、内部接口地址都不该出现。要展示用户信息时，用 sub 再查一次用户服务，多一次内网请求换来可控的暴露面。

另一个误区是把权限列表塞进载荷，指望“改了数据库权限就立刻生效”。不会。用户被降权后，旧 token 里的 roles 仍是他原来的角色。权限要实时就得在服务端查，或者用后文的版本号机制整体作废。载荷里适合放凭证寿命内不变的东西，比如租户 id。

有效期与刷新：短寿命凭证与轮换

JWT 签发后无法收回，寿命就应短到“即使泄露，损失也有限”。通行做法是双凭证：访问凭证（access token）活十几分钟到一小时，刷新凭证（refresh token）活几天到几周，只用来换新的访问凭证。

expires_in 是相对秒数，前端据此提前续期。不要等 401 才刷新，否则用户在过期瞬间会看到一次失败请求；稳妥的做法是提前一到两分钟主动换新，并对并发刷新去重。

刷新凭证本身是服务端状态，不该是 JWT，而是一个不透明的随机串，服务端在 Redis 里存记录，关联用户、签发时间、设备和状态，既能单独撤销，也能审计。

更重要的是轮换与重放检测。每次刷新时同时签发新的刷新凭证，并把旧的标记为已使用。有人拿用过的刷新凭证再来一次，说明凭证泄露了：合法用户和攻击者各有一份，谁先用谁就把另一份挤掉。这时不应只拒绝这一次请求，而要把这条会话链上的凭证全部作废，强制重登。实现起来不过是 Redis 里多存一个状态位。

公共客户端（纯前端、移动端 App）没有能力保管密钥，授权码可能被拦截。RFC 7636 定义的 PKCE 用一次性的 code_verifier 和它的哈希 code_challenge 把链路绑死，成本很低。它不是 JWT 的一部分，但只要出现“第三方登录”就该加上。

存哪里：localStorage、sessionStorage 与 HttpOnly Cookie

前端拿到 token 后放哪里，争论了很多年，三种位置各有代价。

localStorage 最简单，读写同步，刷新不丢，跨标签页共享。问题是它没有任何隔离：同源下任何脚本都能读，一次 XSS 就等于 token 泄露。sessionStorage 的 API 一样，只活在当前标签页，但 XSS 面前同样不设防。

HttpOnly Cookie 相反：JavaScript 读不到，XSS 拿不到明文。代价是浏览器自动携带，CSRF 的窗口重新打开；跨域时还要配 SameSite、Secure、Domain，稍不留神就“本地正常、线上丢登录态”。

SameSite=Lax 在 Chrome 51 之后可用，它让 Cookie 在跨站 POST、iframe、XMLHttpRequest 里不被发送，只在顶层导航的 GET 上带上，既保住了“点链接进来仍然登录”，也挡掉大部分跨站表单提交；如果有跨站 POST 跳转，就要重新评估。

怎么选取决于你更怕哪种攻击，以及团队能不能守住对应防线。token 放在请求头（内存变量或 localStorage）时，CSRF 基本不成立，因为表单提交带不上自定义头；但 XSS 一旦发生，token 就是现成的。放在 HttpOnly Cookie 里，XSS 偷不到，但必须补 CSRF 防护，比如同步令牌或校验 Origin。

笔者偏向折中：刷新凭证放 HttpOnly + Secure + SameSite 的 Cookie，路径限制在刷新接口；访问凭证放内存变量，页面刷新时再换一张。这样 XSS 能偷到的只是短命凭证，CSRF 的目标接口也只有一个。无论选哪种，传输必须走 TLS。

注销与撤销：无状态凭证的代价

用户点“退出登录”，前端删掉本地存储只是清掉自己那一份，凭证仍在有效期内，谁拿着都能继续访问。这是无状态设计必须偿还的债，有三种还法。

最省事的是只靠短过期。访问凭证活十五分钟，退出后最多再被用十五分钟。多数业务能接受这个窗口，但它防不住“刚被解雇的员工”这类场景。

第二种是黑名单。签发时给每张凭证一个 jti，退出时把 jti 写进 Redis，过期时间设成与 exp 一致，让记录随凭证一起自然消失。校验时多查一次 Redis。它精确，但把无状态又变回了有状态，查询量和会话方案差不多，只是键更短。

第三种是版本号。用户表上放一个 token_version，签发时写进载荷；校验时比对，不一致就拒绝。改密码、强制下线时把版本号加一，该用户所有旧凭证同时失效。它只需缓存一个整数，但每次校验仍要读一次用户状态，可以放在网关本地缓存里，用较短的 TTL 兜住一致性。

选择取决于失效粒度：单设备退出用黑名单，全端下线用版本号，都不做就接受过期窗口。三者混用也很常见。

校验清单与网关实践

校验应按固定顺序做，任何一步失败都直接返回 401，不要拼凑错误信息。清单如下：

  1. 从 Authorization 头取凭证，格式是 Bearer <token>，方案名大小写不敏感，但中间必须是一个空格；缺失或格式不对就拒绝。
  2. 用固定的算法列表验签，拒绝 none，拒绝头部指定的算法。
  3. 校验 exp 与 nbf，允许六十秒左右的时钟偏差，服务器之间做一次 NTP 同步。
  4. 校验 iss 与 aud，确认这张凭证确实由自己信任的签发者发出、确实是发给当前服务的。
  5. 业务侧再查一次撤销状态或版本号，然后才把 sub 交给后续逻辑。

微服务场景下，校验通常收敛到网关：验签通过后，网关把 sub、租户 id 放进内部请求头传给下游，下游不再重复解析。有两处容易忽略。一是受众：给 Web 前端签发的 token 不该能调内部管理接口，靠 aud 分开。二是密钥轮换：签发方在头部放 kid，验证方通过公开的 JWKS 地址按 kid 取公钥，轮换时新旧公钥并存，等服务刷新完缓存再下掉旧的；没有 kid，只能同时接受两把钥匙，灰度期间容易出现零星验签失败。

最后列几个反复出现的坑：把 JWT 当加密，以为前端看不到内容；把密码或完整手机号写进载荷；把 exp 当成毫秒；前端自己解析角色渲染管理菜单，服务端却不校验。前三个是认知问题，最后一个最危险，它把“界面看不到”误当成了“接口调不通”。

小结

Token 认证的本质是把会话状态从服务端搬到一张自包含的签名凭证上，换来的是横向扩展的便利，付出的是撤销困难。JWT 只是这种凭证的一种编码格式，Base64URL 谁都能解码，签名只保证不被篡改，所以载荷里不能放任何秘密。算法要在服务端固定，alg: none 与算法混淆都是不检查头部的代价。访问凭证短命、刷新凭证可撤销并轮换，是让泄露的损失可控的基本组合。存储位置没有完美答案，放在请求头里躲开 CSRF、放在 HttpOnly Cookie 里躲开 XSS，选一边就要把另一边的防线补齐。最后，注销、受众校验与密钥轮换这三件事，最好在系统设计的第一天就留好位置。
