前端模块化方案演进总结

模块化并不是新话题，但把它讲清楚的文章不多：从 IIFE 到 AMD、CMD，再到 CommonJS 与 ES Module，每一套方案都在收拾上一套留下的残局。本文按时间顺序走一遍这条路线，说明每种规范的写法、执行时机与适用场景，再落到 2018 年做选型的判断依据。读完你应当能看懂老项目里的 define 与 require，也能说清为什么打包器至今仍是生产主力。

从一段失控的脚本说起

2010 年前后，一个稍具规模的页面往往要在模板底部排上十几个 <script>：

这种写法能跑，但代价是四个问题同时压在页面作者身上。

第一是全局污染。每个脚本都在 window 上挂东西，util.js 里的 format 很可能与某个库撞名，后加载的直接覆盖先加载的。第二是依赖顺序。dialog.js 用到 underscore，就必须排在它后面；一旦有人在中间插入脚本，或把公共部分挪到 CDN 上异步加载，运行时就会报 undefined is not a function。第三是复用。想在新页面复用它，得把依赖一个个抄过来，抄漏一个就是线上事故。第四是加载。十几个同步脚本会卡住首屏，改成 async 之后执行顺序又彻底不可控。

于是有了最朴素的补救手段：立即执行函数加命名空间。

IIFE 解决了污染和一部分复用：内部状态私有，对外只留一个名字，依赖靠参数显式传入（(function ($) { ... })(jQuery) 是当年的标准写法）。但它没有解决依赖声明和加载，window.Dialog 仍是约定俗成的字符串名字，谁依赖谁全靠注释和人工排序。命名空间只是把全局变量收进一个对象，问题的性质没变。

AMD 与 CMD：浏览器端的两种异步流派

真正的第一次系统性回答来自 AMD。AMD 是 Asynchronous Module Definition 的缩写，核心 API 只有两个：

AMD 的三个设计点值得记住。其一，依赖前置：加载器解析出整张依赖图，并行发出请求，全部就绪后才执行工厂函数。其二，异步加载：<script> 由加载器动态插入，不阻塞渲染，这在当年是刚需。其三，返回值即导出：工厂函数 return 什么就导出什么。

RequireJS 是 AMD 最主流的实现：页面里只留一个入口脚本，其余模块按需拉取，配合 r.js 还能把多个模块合并成一个文件做生产构建，这套做法在 2011 到 2014 年的单页应用里非常普遍。

CMD 则是国内社区给出的另一份答案，代表性实现是阿里的 SeaJS，规范由玉伯提出。它的写法看起来和 AMD 很像，但气质不同：

两者的差异集中在写法与执行时机上。AMD 依赖前置、提前执行：依赖数组先声明，加载完立刻执行工厂，哪怕这次只用到其中一个方法。CMD 依赖就近、延迟执行：require 写在用到它的地方，SeaJS 解析时依然提前下载，但执行推迟到真正 require 的那一刻。导出方式也不同，AMD 靠 return，CMD 更接近 CommonJS，用 exports 与 module.exports。争论的落点是可分析性：AMD 的静态依赖数组更容易被工具处理，CMD 更贴近服务端开发者的直觉。

不过两者的局限相同：模块信息写在函数体里，靠加载器在运行时解析字符串、拼 URL、插入脚本，于是每个模块都是一次请求，加载器自身的体积与解析开销也要算进首屏预算。

CommonJS 与 UMD：从服务端到通用包装

AMD 与 CMD 都在为浏览器做妥协，而服务端并不需要这些妥协。2009 年，从 ServerJS 改名而来的 CommonJS 规范给出了另一种模型，Node.js 把它变成了事实标准：

CommonJS 的设计建立在一个假设上：加载是同步且廉价的。Node 里模块是磁盘文件，require 读到内容后把代码包进一个函数壳执行：

这个函数壳解释了很多细节：模块里的 var 为何不泄漏到全局，exports 为何只是 module.exports 的初始引用，__filename 为何可以直接用。它也解释了那个经典陷阱——一旦写了 module.exports = something，exports 就与真正的导出对象脱钩，之后再 exports.foo = 1 不会生效。

同步加载在服务端成立，在浏览器里则不成立：一次网络往返动辄几十毫秒，同步等待会冻结页面。2017 年发布的 webpack 3 与更早的 Browserify，价值正在于构建阶段把 require 改写、把模块按图拼进一个文件，让浏览器也能运行这类代码——同步只是假象，因为执行时所有模块都已在内存里。

于是库作者面对一个现实：同一个 dialog.js，AMD 用户想 define，Node 用户想 module.exports，直接 <script> 引入的老用户想拿到全局变量。UMD（Universal Module Definition）就是为这三种场景准备的包装模板：

这段模板在 lodash、jQuery 插件、各类 UI 组件里反复出现。它是工程上的妥协：包装样板让可读性变差，三个分支意味着三条测试路径，typeof self !== 'undefined' ? self : this 这类写法在严格模式或 ES Module 下还会失效（此时顶层 this 是 undefined）。所以后来的做法是源码用 ES Module 写，构建时分别产出 CommonJS 与 UMD 产物，把兼容性交给脚本。

ES Module：从运行时走向编译时

ES Module 是 ECMAScript 2015 正式纳入语言层面的模块系统。它与前面所有方案最根本的区别在于：模块关系是静态的。

所谓静态，指 import 与 export 只能出现在模块顶层，模块名必须是字符串字面量，不能是运行时拼出的表达式，也不能写在条件分支里。这条限制换来的是编译期就能确定的模块图：工具不必执行代码，就知道 app.js 依赖 math.js。相比之下，CommonJS 的 require 是普通函数调用，require('./' + name) 只在运行时成立，静态分析只能猜。

静态结构还带来两个容易忽略的语义差异。第一，导出的是绑定而非值的拷贝：export var count 之后模块内部改动 count，导入方看到的值同步变化；CommonJS 的 exports.count = 1 复制的是当时的数值。第二，模块默认运行在严格模式下，顶层 this 是 undefined。

这些特性正是 tree shaking 的前提。打包器沿静态的 import/export 边做标记，把没人引用、也没有副作用的导出整段删掉；CommonJS 做不到，因为无法确定 require 是否发生在某个分支里，也无法确定顶层有没有副作用。所以当年常见的困惑是：明明写了 ES Module 语法，体积却没降——多半是中间某一层被 Babel 转成了 CommonJS，静态信息在进打包器前就丢了。

浏览器原生 ESM：条件与回退

规范定稿之后，浏览器用了一年多才陆续把它落地。到 2018 年 4 月，Safari 10.1、Chrome 61、Edge 16 都已支持，Firefox 60 即将发布，写法就是换一个 type：

type="module" 带来几条与普通脚本不同的规则，每一条都对应着真实的坑。

其一，模块脚本默认是 defer 行为：下载不阻塞解析，执行推到文档解析完成之后并保持顺序，写 document.write 不会生效。其二，模块脚本自动处于严格模式，每个模块只执行一次，多个入口 import 同一文件不会重复初始化。其三，跨域加载模块必须满足 CORS：请求会带上 Origin，服务端要返回 Access-Control-Allow-Origin，CDN 上没配这个头的脚本，用普通 <script> 能跑，改成 type="module" 就直接失败。其四，响应头里的 MIME 必须是 JavaScript 类型，text/plain 或空的 Content-Type 会被严格 MIME 检查拦下，控制台报 “Failed to load module script”。此外，用 file:// 双击打开页面也加载不了模块，因为此时源是 null。

nomodule 是给不支持 ESM 的浏览器准备的：支持模块的浏览器忽略带 nomodule 的脚本，不支持的浏览器不认识 type="module"，会跳过模块脚本、执行 nomodule 脚本，于是”新浏览器跑 ESM，IE 11 跑打包产物”。要注意：Safari 10.1 尚不识别 nomodule，要到 Safari 11 才补齐；内联模块没有 src 可降级，逻辑只能放进外部文件。

原生 ESM 还有性能问题：入口 import 三个模块，浏览器要先下载入口、解析依赖、再发请求，形成请求瀑布；模块一多，往返次数就成了瓶颈。所以 2018 年的普遍说法是”可以用了，但生产环境还在打包”，它更适合内部工具、文档站点与渐进增强的页面，而不是几十个路由的单页应用。

打包器如何消费模块

打包器的工作可以概括成三步：从入口出发遍历依赖，得到模块图；把每个模块包进一个函数，登记到模块表；生成运行时代码，按需调用并缓存结果。以 2017 年的 webpack 3 为例，产物里到处是 __webpack_require__，本质就是一个带缓存的同步 require，只不过模块早就在同一个文件里了。

理解了这层映射，很多现象就顺了：打包后调试要看 source map，因为源码被套进了函数壳；循环依赖有时拿到 undefined，因为工厂函数执行到一半，另一方读到的还是未完成的 exports。

webpack 3 的 Scope Hoisting（ModuleConcatenationPlugin）是这条路线上的转折：它利用 ES Module 的静态结构，把层层嵌套的模块函数尽量合并进同一作用域，减少包装开销。2018 年 2 月发布的 webpack 4 又把 mode 与副作用标记变成默认配置的一部分，产物体积的默认值比上一代更合理。

Rollup 走的是另一条路：它面向库打包，尽量输出扁平的 ES Module，把多个源文件合成一个模块，而不是一堆工厂函数。库作者喜欢它，是因为产物干净、tree shaking 效果好；应用作者仍然倾向打包器，因为它对 CSS、图片、代码分割的支持更完整。

模块解析：一行 import 背后的查找

写 import x from 'foo' 时，真正花时间的是解析。规则分两类。

相对路径必须带前缀：./math、../lib/math 从当前文件目录算起，/static/js/math 从站点根目录算起。裸模块名（foo、lodash/fp）交给查找算法：从当前目录向上逐级找 node_modules/foo，直到文件系统根目录；找到后读它的 package.json，按字段决定入口。main 是 CommonJS 时代的约定，Node 与打包器都认；module 是社区为推动 tree shaking 加的非标准字段，Rollup 与主流打包器优先读它；browser 用于在浏览器端替换 Node 专用实现。三个字段并存时，打包器按自己的优先级挑一个，这也是同一个库在两端行为不一致的常见来源。

没有命中就是补全：省略扩展名时按 .js、.json 依次尝试，目录则找 index.js。打包器把这些行为做成了配置项，resolve.extensions 决定尝试顺序，resolve.alias 让 @/utils 这类别名指向真实目录——好处是路径短、重构只改一处，代价是编辑器与 TypeScript 要各自再配一遍，否则跳转和类型检查会失效。

互操作陷阱与选型建议

ESM 与 CommonJS 共存的那几年，坑几乎都出在”看起来能跑”上。

最典型的是具名导入。CommonJS 只有一个整体导出对象，理论上 import { add } from './math' 拿不到具名；但在 Babel 转译的代码里，这句被改写成属性访问，于是运行正常，换成原生 ESM 或另一个打包器就报错。默认导出同理：module.exports = function () {} 被 import fn from 引入时，Babel 会用一层 interop 包装，把整体当成 default；按规范解析时，CommonJS 并没有 default 这个键。这类差异不会在开发阶段暴露，只会在换构建方案时集中爆发。

循环依赖的表现也不同。CommonJS 在模块执行到一半时就把 exports 交出去，另一方拿到半成品，属性可能还是 undefined；ES Module 导出的是活的绑定，但初始化完成前访问会直接抛引用错误，问题从”值不对”变成”直接崩”，反而好排查。

选型按项目类型分：新项目直接用 ES Module 写源码，交给打包器输出，不要为兼容去写 UMD；老项目不要推倒重来，先划清 require 与 import 的边界，按目录逐个迁移，保证每步都能单独发布；库项目输出多份产物，main 指向 CommonJS、module 指向 ESM，再附一份 UMD 供 CDN 引用，让使用者自己挑。

小结

每一步演进都是在上一步约束下做的取舍：IIFE 换来作用域隔离，AMD 与 CMD 换来异步加载，CommonJS 换来简洁的同步模型，UMD 换来一份代码跑三个环境。ES Module 的不同在于把模块关系提前到编译期，让静态分析、tree shaking 和更聪明的打包成为可能，而不只是换一种语法。原生 ESM 在 2018 年已经可用，但请求瀑布与兼容回退让它暂时替代不了打包产物。理解这些规范的执行时机与解析规则，比记住某个 API 更有价值——换构建工具时，你判断的仍是同一件事：模块在哪一步被解析，又在哪一步被执行。
