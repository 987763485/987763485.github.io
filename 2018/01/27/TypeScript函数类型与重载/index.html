TypeScript 函数类型与重载

本文属于《TypeScript 学习路线》第 6/74 篇
上一篇系列目录下一篇

函数是 JavaScript 里最灵活的东西：可以被赋值、被传递、被返回，还能带一串可选参数和默认值。TypeScript 要给这样的东西建一套类型描述，于是有了函数类型、重载和 this 参数这些工具。本文从函数类型的两种写法讲起，一路走到重载的声明规则与常见陷阱，适合已经会写 JavaScript、正准备把项目迁到 TypeScript 的读者。

两种写法：类型字面量与调用签名

在 JavaScript 里，函数是一等公民，变量、对象属性、数组元素都可以装函数。到了 TypeScript，描述一个函数的类型有两种等价写法：

两种写法描述的是同一个类型：接收一个 number 和一个可选的 number，返回 string。差别只在书写位置。类型字面量通常直接写在变量、参数或返回值的位置，用完即走；调用签名必须挂在接口或对象类型里，适合需要命名、需要反复引用、或者需要往函数上再挂属性的场景。参数名 value 和 digits 只是给人看的文档，不参与兼容性判断，这一点和对象类型里属性名必须一致刚好相反。

还有一点值得强调：函数类型的核心是“形状”。只要参数个数、类型和返回值对得上，两个来自完全不同地方的函数就能互相赋值，名字和来源都不重要。这是 TypeScript 结构类型系统在函数上的直接体现。

默认参数在声明处直接给值：

带默认值的参数，在调用方看来就是可选的：greet() 与 greet(undefined) 都合法，效果和把参数标成 name?: string 相同。区别落在函数体内：有默认值时编译器认为参数一定有值，不需要先判 undefined，因为不传或者传 undefined 都会走默认值。但默认值只是运行时的兜底，不会改变参数的静态类型——不写标注时类型由默认值推断，一旦写了标注，默认值就救不回标错的类型。

剩余参数用 ... 收集成一个数组：

剩余参数必须是参数列表的最后一个，类型必须是数组；写成 (...nums: number) 会报错，因为它的本质就是一串值装进数组。三种修饰可以组合，顺序固定：必选、可选或默认、剩余。把可选参数挪到必选参数前面会直接报错 TS1016，这是初学者最常撞的一堵墙。

真正的重点在回调位置：

(value: number) => number 可以赋给 (value: number) => void，反过来不行。原因很直白：声明成 void 的调用方已经表明自己不使用返回值，被调函数多返回一个值无所谓；反过来，调用方指望拿到 number，实际签名却给不出值，就必须拒绝。这条规则解释了为什么 arr.forEach(item => list.push(item)) 能通过检查——push 返回新长度，而 forEach 的回调只要求 void。

需要分清的是，void 不等于“函数里绝对不能写 return”。带 return; 的函数仍然是 void；返回具体值的函数也能赋给 void 回调，只是那个值会被丢弃。

赋值兼容：参数与返回值方向相反

把函数赋给另一个函数类型时，参数和返回值的方向感是不一样的。先看返回值，它遵循协变：子类型可以替代父类型。

参数方向正好相反，直觉上是逆变：参数类型更宽的函数，可以替代参数类型更窄的函数。

反方向 handleAnimal = handleDog 在类型上并不安全，调用方可能递进来一只猫。不过在 TypeScript 2.6 的默认配置下，编译器对函数参数采用的是双变检查，这个反方向也能通过。它这样选择，是为了照顾 JavaScript 里大量“运行时再判断类型”的既有写法，代价是把一部分判断交给了开发者。所以看到函数赋值时，与其背术语，不如问一句“参数方向对不对”。

回调的参数可以少写：声明要求三个参数，实参只写 n => n * 2 完全合法。反方向则不允许，回调声明了比调用方提供的更多的必选参数就会报错。这与前面的赋值规则是同一个道理：调用方按声明传参，被调方不能反过来提更多要求。

最后是一个经典的坑：['1', '2', '3'].map(parseInt)。parseInt 的签名是 (s: string, radix?: number) => number，恰好能匹配 map 回调的前两个参数，于是数组下标被当成进制传了进去，结果是 [1, NaN, NaN]。类型系统在这里帮不上忙，形状兼容不代表语义兼容。

重载：一组签名，一个实现

实际项目里，函数经常需要根据参数的不同返回不同的类型。联合类型描述不了这种“输入决定输出”的关系，于是有了重载。重载的写法是一组声明加一个实现：

前两个是重载签名，只有类型没有函数体，用分号结尾；最后一个是实现签名，带函数体。调用方看到的是重载签名，实现签名对它不可见。调用 query('id', 'app') 时，编译器从上到下逐个比对，找到第一个匹配的签名就停下，返回值确定为 HTMLElement | null。所以顺序至关重要：具体的签名必须写在宽泛的签名前面。如果把 (selector: string, value: string) 放到最上面，后面两条永远轮不到，返回值也退化成 any。

实现签名则要兼容每一条重载：参数要够宽，能接住每种重载的实参；返回类型要能和重载的返回要求对上。对不上的时候，编译器会直接提示“This overload signature is not compatible with its implementation signature”。也正因为检查是按可赋值关系做的，很多人图省事把实现签名写成 (selector: string, value: string): any。这样做本身没问题，但要守住一条底线：any 只能待在实现签名里，不能让它在重载签名里露头，否则调用方拿到的是 any，重载就白写了。

另外，重载签名只能挂在函数声明或对象方法上，箭头函数没法直接写重载。

重载的取舍、坑与替代方案

重载最适合两类场景。第一类是参数组合有限且互斥，用联合类型会放过非法调用：

第二类是返回类型随参数变化，也就是上一节的 query。联合类型做不到这一点，它只能把所有可能的返回值堆在一起，调用方拿到一个大联合，还得自己收窄。

代价是签名变长、维护成本变高。如果参数之间只是“要么都传、要么都不传”这种弱约束，可选参数加联合类型就够了，没必要上重载。

三个坑要特别注意。

第一个坑是实现签名不兼容。重载签名说参数是 number，实现签名却只收 string，编译器会报错；实现签名过窄时，某个重载的参数组合根本接不住，错误会指向那条重载签名，初学者容易看错位置。

第二个坑是调用方看不到实现签名。实现签名里写的参数、默认值、可选性，对调用方一律无效：

实现签名里的默认值和 timeout 参数，都不会让三参数调用变合法。想让调用方享受默认值，就得把可选性写进重载签名本身。

第三个坑是顺序导致错误匹配，前面已经提过一次。典型的翻车现场是把 (value: string) 写在 (value: 'a') 前面，或者干脆写一条 (value: any) 收尾，结果所有调用都被第一条吸走，精确类型全部失效。

最后是重载爆炸。三个可选参数就是八种组合，如果每种组合都要返回不同类型，重载数量会失控。经验上，重载超过三四个就该停下来问一句：是不是接口设计得太“聪明”了。把参数收成配置对象，或拆成两个函数，通常更清楚。

常见坑速查

把上面几节的边界条件集中列一遍，写代码时可以直接对照：

  • 可选参数和带默认值的参数都不能出现在必选参数之前，编译器会报 TS1016。
  • 默认值只影响运行时和函数体内的判断，不会把已标注的参数类型变宽。
  • void 的语义是“忽略返回值”，不是“禁止返回”；把它写在回调上时尤其要记住这一点。
  • 回调的参数宁少勿多，多声明一个必选参数就会和调用方的签名对不上。
  • 重载从上到下匹配，具体签名在前、宽泛签名在后，any 收尾等于放弃检查。
  • 实现签名对调用方不可见，别把重要约束、默认值只写在实现签名里。
  • 想表达“输入类型决定输出类型”的关系，先看泛型能不能写出来，写不出来再上重载。

小结

函数类型看着只是“参数加箭头加返回值”，真正要想清楚的是参数方向、返回值方向和可选性。类型字面量与接口调用签名语义等价，区别在于是否需要命名、是否需要附加属性。void 在回调位置的含义是忽略返回值，这条规则解释了为什么 forEach 乐意接受有返回值的回调。重载处理参数组合有限、返回类型随之变化的情况，代价是调用方与实现签名看到的世界不一致，顺序和兼容性都要自己把关。能用泛型表达的关系优先用泛型，需要按具体值分派时再写重载；一旦重载超过三四个，多半该回头检查接口设计，而不是继续堆签名。
