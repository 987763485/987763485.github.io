Go 函数、多返回值与错误处理

本文属于《Go 语言与工程》第 4/78 篇
上一篇系列目录下一篇

Go 的函数签名把类型写在名字之后，又能一次返回多个值，于是“结果加错误”成了最自然的返回形式。本文从函数声明讲起，依次梳理多返回值、命名返回值、defer、闭包与 panic 的用法，再落到错误处理的通行惯例。读完后，你应该能写出参数清晰、错误不被吞掉、边界行为可预期的 Go 函数。

小对象优先按值返回：复制成本低，调用方拿到副本，怎么改都不影响函数内部状态；time.Time 这类小结构体在标准库里就是按值传递的。

大结构体、需要表达“可能不存在”的语义、或者确实要在多处共享同一份可变数据时，才返回指针。这里有个常见误解：切片、map、channel 本身已经是包含指针的描述符，按值返回并不会复制底层数组或哈希表，不必为了“避免复制”再套一层指针。

五、defer：顺序、参数求值与资源释放

六、panic 与 recover 的边界

panic 表示程序进入了不该出现的状态，例如数组越界、向 nil map 写入、类型断言失败。它会沿调用栈向上展开，沿途的 defer 依次执行，直到被 recover 拦下，或者进程直接退出。

是否该主动 panic，判断标准是“这个错误是否属于调用方能够合理处理的预期情况”。配置文件缺字段、用户输入非法、下游接口超时，都是可预期错误，应当通过返回值交给调用方决定怎么办；而“数据库驱动没有注册”“启动时模板语法错误”这类问题，说明程序本身有缺陷或部署不完整，继续运行没有意义，用 panic 尽早暴露反而更好。标准库的 regexp.MustCompile、template.Must 就是这种思路：把错误检查前移到初始化阶段。

recover 只有在 defer 的函数中直接调用才有效，并且只能捕获当前 goroutine 的 panic。恢复之后，发生 panic 的函数不会回到原来的调用点，而是直接返回。库或框架的边界是合理位置，比如给 HTTP 服务加一层保护：

八、函数设计：让签名自己说话

函数是阅读代码时最小的理解单元。一个函数只做一件事，名字能准确说出这件事，比任何注释都有效。参数个数是最直观的信号：超过三四个，调用点就会出现一长串难以对应的实参，此时应当把参数收进配置结构体。

结构体让每个字段在调用点都有名字，新增字段也不会破坏已有调用。布尔参数尤其要避免，start(true, false) 没人看得懂；实在需要，就定义具名类型或拆成两个函数。返回值同理，超过三个就该合并成小结构体。

小结

Go 用多返回值把错误变成普通数据，换来的是显式的控制流：每个可能失败的地方都得写下判断，也因此很难悄悄漏掉。写函数时，优先选择值返回和提前返回，命名返回值只在短函数或 defer 收尾时使用，并警惕 := 的遮蔽。defer 负责释放资源，但要记住参数在注册时求值、循环里会堆积。闭包捕获的是变量而不是快照，循环变量该复制就复制。panic 留给真正的程序错误，可预期失败一律走 error；把这几条变成习惯，函数的边界行为就基本可控了。
