TypeScript 工程配置模板

本文属于《TypeScript 学习路线》第 16/74 篇
上一篇系列目录下一篇

新建一个 TypeScript 项目，最耗神的往往不是写第一行业务代码，而是把编译、检查、测试、发布这几件事配到能用。本文给出一套可以直接复制的工程模板：目录怎么分、tsconfig 与 package.json 怎么写、lint 与测试怎么接，以及从零落地时要避开的坑。读完之后，你应该能在十分钟内让一个新仓库跑起来，并让团队里每个人的配置长得一样。

模板要解决什么问题

配置模板不是脚手架，也不是框架。它只回答三个问题：新仓库能不能在十分钟内跑起来；两个人拉下同一份代码，行为是否一致；半年后接手的人能不能看懂每个选项为什么在这里。脚手架习惯替我们做决定，业务一变就要拆；模板反过来，只放约定和必要的配置，业务代码从空目录开始长。

很多团队的 tsconfig 是手抄来的。第一个项目开了 strict，第二个项目为了赶进度关掉，第三个项目又抄了第二个。等到升级 TypeScript 2.6 时，没人说得清哪些选项是必须的、哪些是历史遗留。模板的价值，就是把“哪些选项必须有”固定下来，把“为什么”写进注释，让项目之间的差异只发生在业务代码里。

笔者给自己的模板定了四条规矩：配置项只保留当前项目真的用得上的；同一类配置只出现一处；每个非默认选项旁边写一行注释；所有约定都能用一条命令验证。最后一条最重要，模板不是文档，而是一组能跑的命令。只要 build、lint、test 三条命令在空仓库里全部通过，模板就算立住了。

目录模板

先定目录，再谈配置。模板的目录只有五个业务目录加若干根文件：

src 只放会被编译进产物的源码，入口固定为 src/index.ts。库的对外导出全部经过这个文件，消费者不需要知道内部目录怎么分，将来重构目录也不会破坏引用路径。入口放在别处、或者允许从 dist 深处直接引文件，都会把内部结构变成公开契约。

test 与 src 保持镜像结构：src/user/service.ts 对应 test/user/service.spec.ts。镜像不是形式主义，代码评审时看一眼目录，就能发现哪个模块根本没有测试。测试文件不参与正式编译，但仍在 tslint 的检查范围内，测试代码同样要遵守命名与类型规则。

types 放 ambient 声明，比如全局变量、没有自带类型的第三方模块的补丁。模块自己的类型跟着源码走，写在与实现相邻的 .ts 文件里，不要集中堆到 types，否则改一个接口要跨三个目录。scripts 放用 Node 写的小工具，例如清理产物、同步版本号，它们不参与 tsc 编译，因此不在 include 里。dist 是产物目录，git 忽略，npm 发布时通过白名单带出去，这一点后面再展开。

根目录只留配置。配置超过五六个文件时，可以建一个 config/ 目录集中存放，再在脚本里指路；但模板阶段没有必要，路径越短，新人越容易找到。

输出组里，rootDir 与 outDir 一起决定了目录结构：src/user/service.ts 会编译成 dist/user/service.js，不会在 dist 里多套一层 src。sourceMap 打开，线上报错能映射回源码；库项目打开 declaration，应用项目可以关掉。

语言组里，target 选 es2017 是因为 Node 8 原生支持 async/await，降到 es5 只会多出一层 __awaiter 辅助函数，调试时平添噪音。lib 只写 es2017，不写 dom：Node 项目里编译不出 window 和 document 是优点，而不是限制。module 必须是 commonjs，Node 的 require 和 Jest 的加载方式都按 CommonJS 走；库项目若在这里写 es2015，第一个报错的往往是测试。

include 只写 src/**/*.ts，这是从源头堵住“把 dist 编进去”的问题；exclude 里的两项更多是保险。检查组的五个开关都不改变产物，只让问题提前暴露，noUnusedParameters 允许以下划线开头的参数豁免，专门留给接口实现里用不到的形参。

严格模式：一次开，还是分步开

strict 从 2.3 起就是一个总开关，2.6 起又把函数参数的逆变检查纳入进来。模板默认给新项目开全套，原因很实际：严格检查的成本主要来自存量代码，新项目没有存量，越早开越便宜。等代码长到几万行再补 strictNullChecks，修错的工作量会翻好几倍，而且那时候没人敢动。

存量项目则相反，建议按 noImplicitAny、strictNullChecks、strictFunctionTypes 的顺序分批打开，每批修完再进下一批，中间允许把尚未清理的目录排除在外。模板服务的是新项目，所以只保留一个总开关，不提供“半严格”的中间档——中间档一旦存在，就会永远留在那里，最后没人记得还差哪几项。

prepare 在 npm install 与发布前触发，保证 dist 总是最新；如果嫌本地安装时也编译，可以换成更精确的 prepublishOnly，但那样从 git 地址安装的依赖就不会被构建。模板选择前者，用一点安装时间换“装完即可用”。main 与 types 必须指向 dist 里真实存在的文件，两个字段同时写全，否则 JavaScript 使用者能跑、TypeScript 使用者只能看到 any。files 只写 dist，是发布白名单，细节在讲发布边界时展开。

devDependencies 按用途分三组，顺序也按这三组排：编译器与类型（typescript、@types/node）、检查与格式（tslint、tslint-config-prettier、prettier）、测试（jest、ts-jest、@types/jest）。分组不是 npm 的要求，是给人看的，新人加依赖时一眼就知道该插在哪一行。dependencies 只放运行时真正 require 的包；把类型包和测试工具塞进去，安装体积会转嫁给每一个使用者。

库项目与 Web 项目：两份模板的差异

目录与脚本可以共用，tsconfig 则要按项目形态分叉。关键差异集中在四个选项：

选项 库模板 Web 模板
declaration true，发布 .d.ts false，产物不需要类型文件
module commonjs，Node 与 Jest 直接加载 es2015，交给 webpack 3 做 tree shaking
target es2017，对齐 Node 8 LTS es5，照顾 IE 11
outDir dist，由 tsc 直接产出 可选，输出由打包器决定

库项目的消费者是别的代码，所以类型声明和入口一样重要。declaration 打开，types 指向 dist/index.d.ts，files 只带 dist；target 与运行时对齐即可，Node 8 上没有必要降到 es5。如果这个库还要在浏览器里用，可以再加一份 rollup 配置输出 es5 的 UMD 包，但模板的默认形态是 Node 库，浏览器构建作为可选项，不放进主配置。

Web 项目的产物由 webpack 3 负责，tsconfig 的角色退化为“告诉 loader 怎么转译、告诉编辑器怎么检查”。target 用 es5，lib 加上 dom，module 用 es2015 让 tree shaking 有据可依，declaration 关掉。此时 outDir 只作为单独跑 tsc 做全量类型检查时的临时目录，或者干脆省略，避免和打包器的输出目录打架。jsx 只在 React 项目里出现，归属具体项目，不属于通用模板。

两份模板共享的部分比差异多：目录、脚本名、lint 与测试配置、发布流程全部一致。分叉只发生在编译目标上，这样团队里换项目时，需要重新理解的只有四个选项。

ts-jest 与 babel-jest 的取舍，本质是“类型检查放在哪一步”。ts-jest 复用 tsconfig，测试文件也走类型检查，测试里的类型错误会直接让 CI 失败，代价是启动慢；babel-jest 只擦除类型，启动快，但测试代码里的类型错误要另跑一次 tsc --noEmit 才能发现。模板默认 ts-jest，因为小项目更怕漏错误，而不是怕慢。

testMatch 固定到 test/**/*.spec.ts，避免 Jest 的默认规则把 dist 里的旧文件也当成测试；collectCoverageFrom 只统计 src，声明文件排除在外。覆盖率阈值从 70 起步，稳定后每次加 5，只升不降。阈值不是 KPI，而是防止回退的闸门：新代码可以暂时不完美，但不能把整体拉低。

git 忽略什么、npm 发布什么，是两套独立的规则，模板要用两个文件分别表达：

dist 不进 git，但必须进 npm 包；node_modules 和 coverage 两边都不要。npm 的规则是 files 白名单优先于 .npmignore，所以模板只维护 files: ["dist"]，不再写 .npmignore——两份清单迟早会不一致。README、LICENSE、package.json 永远会被打包，不用列。发布前先 npm pack 打出 tarball，再用 tar -tzf 看一眼内容，比发错版本之后再补一个补丁版本便宜得多。

编辑器与运行时版本也需要模板化。.editorconfig 管文件层面的基础格式，和 Prettier 不冲突：前者负责编码、换行符、末行空行，后者负责代码排版。.nvmrc 里只写一个 8，本地 nvm use 自动切到 Node 8 LTS，CI 也读同一个文件，省掉“我本地是 10”的争论。

落地步骤与常见坑

从空目录开始，顺序不要颠倒：

npx tsc --init 这一步容易被跳过，但它很关键：生成的默认配置跟随当前安装的 TypeScript 版本，比从半年前的仓库整包复制更不容易带上过期选项。生成之后，对照本文的模板删改，把注释保留下来，再把 package.json 的 scripts 逐条补齐。接着写一个空的 src/index.ts 和一条冒烟测试，先让三条命令跑通，再往里搬业务代码。模板文件本身放在独立仓库里，升级时集中改一次再同步到各项目，这才是“模板”和“复制粘贴”的区别。

配置跑通之后，仍然有几个坑会反复出现。第一个是路径别名：paths 只影响类型解析，tsc 不会重写 import 路径，Node 运行时需要额外的注册工具，webpack 也要在 resolve.alias 里再写一遍。三处配置对不上时，编辑器不报错、测试却挂掉。模板默认不开别名，需要时再一次性配齐三处。

第二个是 include 太宽。写成 "**/*" 会把 dist 里已有的 .d.ts 再当作输入编一遍，轻则重复标识符，重则产物套产物。只写 src/**/*.ts 就能避免，exclude 不能替代 include，它只是减法。第三个是依赖放错位置：@types/*、typescript、jest 进了 dependencies，体积转嫁给使用者；运行时库放进了 devDependencies，线上 npm install --production 之后直接模块找不到。判断标准很简单：代码运行时会 require 的放前者，只在开发、构建、测试时用的放后者。

第四个是入口字段指错。main 写成 src/index.ts，本地靠 ts-node 能跑，发布后 JavaScript 使用者却加载失败；types 漏写，TypeScript 使用者只能看到隐式 any。第五个是测试与编译目标不一致：tsconfig 的 module 若是 es2015，ts-jest 转出的代码 Jest 无法加载。解决办法要么让库项目坚持 commonjs，要么给测试单独一份 tsconfig，不要指望测试加载器猜。

最后一个坑在发布清单上：只写 .npmignore 而忘了 files，或者两份清单各写一半，都会把 test、源码甚至覆盖率报告带进包里。模板只认 files 白名单，发布前用 npm pack 检查，这条习惯比任何配置都可靠。

小结

TypeScript 工程模板的价值不在选项多，而在约定少且能被命令验证：五个目录各司其职，根配置只保留必须做决定的选项，脚本名统一为 build、lint、test。新项目默认打开 strict，把成本放在代码还少的时候；存量项目则按检查项分批推进。库与 Web 两份模板共享目录和流程，只在 declaration、module、target、outDir 上分叉。配置跑通只是开始，路径别名、include 范围、依赖归属和发布清单才是长期维护中最容易出错的地方。把模板放进独立仓库统一升级，比在每个项目里手抄一份更省心。
