TypeScript 工程化实践

本文属于《TypeScript 学习路线》第 15/74 篇
上一篇系列目录下一篇

2018 年初，把 JavaScript 项目迁到 TypeScript 的成本已经不高：装依赖、写一份 tsconfig.json、改后缀、补类型，tsc 跑通，很多人就认为迁移结束了。但接下来几周，问题会以另一种形式冒出来：新人 clone 后不知道先跑哪条命令，测试文件被编进产物，类型错误要等合并之后才由别人发现。本文讨论这些与类型语法无关、却决定项目能否长期协作的部分，适合准备把 TypeScript 项目交给团队维护的读者。

从能编译到能协作

TypeScript 解决的是“这段代码的类型对不对”，工程化解决的是“一群人能不能稳定地修改这段代码”。项目可以编译零错误，却依然难以协作：没有统一入口，没有检查门禁，产物里混着调试代码。笔者把工程化拆成五个问题：代码放在哪、用什么命令跑、谁来把关、怎么验证行为、怎么交付产物。

判断是否跨过这条线，有两个朴素标准。第一，新机器 clone 后照着 README 跑三条命令就能启动开发与测试；第二，CI 失败时，红色标记能指向 lint、类型、测试或构建中的某一环，而不是笼统的一句“构建失败”。

本文只讲组织方式与脚本。tsconfig 字段语义、打包器原理、完整模板都有专文讨论，配置片段保持最小。

目录分层：每个目录回答一个问题

目录结构是工程化的第一层表达。它不需要复杂，但每个目录都应该能回答“这个文件为什么在这里”。本文以一个既包含浏览器端代码、又有少量 Node 脚本的项目为例，使用五个目录：

  • src：唯一的源码目录，也是唯一会进入产物的目录。内部再按领域划分 api、utils、components。
  • test：测试代码，结构与 src 镜像，src/utils/date.ts 对应 test/utils/date.spec.ts。
  • types：手写的声明文件，用于两类情况：第三方库没有类型，或需要给全局对象补充类型。
  • scripts：构建、发布、代码生成等辅助脚本，同样用 TypeScript 编写，由 ts-node 直接执行。
  • dist：生成物，随时可以删掉重建，永远不提交。

为什么 test 不放进 src？构建通常以 src 为根，测试会被打进产物；发布 npm 包时，files 也难只排除测试；Jest 的 roots 指向 test，收集范围反而更清晰。

types 单独放是同样的道理。声明文件不产生 JavaScript，散落在 src 里会让 declaration 产物出现只有类型的空模块。集中到 types，再在 include 中显式加入，边界最清楚。

scripts 用 TypeScript 写常被忽略。发布脚本要读 package.json、拼版本号、调用 git，最容易写错；用 ts-node 执行，可以共享 src 的类型，也能被 tsc 检查。它不进入打包入口，不影响产物。

tsconfig 的工程视角：只管边界

从工程角度看，tsconfig 只需回答三个问题：编译器读哪些文件、模块名怎么解析、产物写到哪里。选项的完整语义有专文讨论，这里只看与组织相关的部分。

include 与 exclude 的边界应与“人会编辑的文件”一致。本文的 include 是 src、test、types，exclude 只写 node_modules 与 dist 兜底。常见错误是写 include: ["**/*"] 再用 exclude 去补：dist 里的旧产物被再次读入，编译器同时看到源码和编译结果，报出重复声明；每次新增目录还要维护排除列表，迟早漏掉。从窄到宽更安全。

baseUrl 与 paths 解决模块名解析。baseUrl 设为项目根，paths 写 "@/*": ["src/*"]，深层目录就不必写一串 ../../../。但要记住：paths 只是编译期映射，不改变运行时的 require，浏览器和 Node 都不认识 @。

rootDir 与 outDir 只在 tsc 真正输出文件时才有意义。typecheck 用 --noEmit，不产生文件，也就不需要 outDir。但若同一份配置既 include 了 test，又设置 "rootDir": "src"，tsc 会报 TS6059：测试文件不在 rootDir 之下，无法确定它在输出目录中的位置。这正是把检查与产出拆成两份配置的原因。

npm scripts：把动作固化成命令

目录定好之后，所有动作都要收敛成命令。团队成员不必记住 tsc 的参数，CI 也不必维护另一套命令，两边共用 package.json 里的 scripts。

本文把动作分成六个：clean、typecheck、lint、format、test、build，再加一个 dev。每个命令只做一件事，失败信息才能指向具体环节。其中 typecheck 只检查、不产出：tsc 按文件转译，不做模块合并，也不处理样式与静态资源，用它产出浏览器代码并不合适。检查交给 tsc --noEmit，产物交给 2017 年的 webpack 3；若是给别的项目引用的库，产物交给 Rollup。

webpack 3 在 2017 年是主流的构建工具，它的 ts-loader 默认每次编译都做完整类型检查，开发时改一行要等几秒，错误还会显示成浏览器遮罩。常见的取舍是给 ts-loader 开 transpileOnly，配合 fork-ts-checker-webpack-plugin 把类型错误放到终端提示，而 CI 里始终保留一次全量 tsc --noEmit。注意 transpileOnly 只是把检查挪走，不是取消；若 CI 也没有 typecheck，整条链路都不校验类型。

build 之前必须先 clean。打包器只写它认识的入口产物，源码里删掉的文件不会自动从 dist 消失；tsc 输出声明文件时同理。留下的旧文件最典型的后果，是发布物里带着废弃模块，引用方还能 import 成功，运行时才报错。

verify 是本地预演：提交前跑一遍，相当于把 CI 的顺序在本地走一遍。命令之间用 && 连接，任何一步失败就停下，不会出现“lint 失败、build 成功，最后只看到一句成功”的错觉。

TSLint 与 Prettier：两类规则，两种职责

代码检查与格式化常被混为一谈，实际是两类规则。语义类回答“这段代码是否可能出错”，比如未使用的变量、浮动的 Promise、滥用 any；排版类回答“代码长什么样”，比如行宽、引号、缩进。TSLint 两样都管，Prettier 只管后者，但管得更彻底。

二者冲突的典型表现是：Prettier 把一行拆成多行，TSLint 的行宽规则立刻报错；保存时两个 fixer 轮流执行，光标位置跟着跳。解决思路不是二选一，而是分工：格式化交给 Prettier，语义规则留给 TSLint，再用 tslint-config-prettier 关掉 TSLint 中与排版有关的规则。同一时期 JS 项目里的 eslint-config-prettier 扮演同一角色，只是宿主是 ESLint。

配置建议分三层。第一层继承 tslint:recommended，它覆盖了大部分常见问题，是团队共识的起点；第二层写团队自己的规则，例如生产代码禁止 console.log、要求 no-floating-promises；第三层把 tslint-config-prettier 放在 extends 数组的最后，它只做一件事，把冲突规则关掉。顺序很重要，后面的会覆盖前面的。

有一个细节值得提醒：带类型信息的规则（如 no-floating-promises）需要 TSLint 拿到完整的 Program，所以命令里必须带 -p tsconfig.json。只传文件通配符时，这类规则会静默失效，看起来像“规则没生效”。

编辑器里装 TSLint 与 Prettier 两个插件即可，但不要让两个 fixer 同时工作。笔者的习惯是保存时只让 Prettier 格式化，TSLint 的问题以波浪线呈现，或在提交前统一跑一次 tslint --fix。CI 里的格式检查用 prettier --list-different 而不是 --write：流水线只报告差异，不替人改代码。

测试：Jest 22 与两条转译路线

测试是唯一能验证“行为仍然正确”的环节，类型检查替代不了。Jest 22 配置少，内置断言、mock、快照与覆盖率；接入 TypeScript 时，第一个决定是转译路线。

路线一用 ts-jest。它作为 Jest 的 transform，调用 TypeScript 编译测试与源码，读取同一份 tsconfig。优点是一次运行同时得到转译与类型检查，测试里的类型错误会直接让用例失败；缺点是启动与增量都慢，且与 TypeScript 版本需要对齐，跨大版本升级容易遇到语言服务报错。

路线二用 babel-jest，只剥类型、不做检查。速度快，但 2018 年初 Babel 7 还在 beta，配套的 TypeScript 处理尚不成熟；更重要的是，类型错误不会再被发现，必须依赖 CI 里单独的 typecheck 兜底。

本文建议默认用 ts-jest。多数项目的测试规模还没大到需要为启动时间付出双编译器的维护成本；等测试集到了分钟级，再评估第二条路线，并且先确认 typecheck 是独立门禁。另外，Jest 22 默认环境是 jsdom，纯 Node 的库要显式写 testEnvironment: 'node'，否则 Buffer、setImmediate 的表现会与线上不同。

覆盖率只统计 src，排除声明文件与入口；阈值先定团队当前能达到的数字，再逐步提高。一上来就设 90% 的结果，通常是有人写一堆没有断言的测试来凑数。

测试目录镜像 src 的好处在这里再次体现：roots 指向 test，moduleNameMapper 把 @ 还原成 src。检查应该保护行为，而不是保护实现。

一份别名，三处同步

路径别名提升可读性，也最容易“只做一半”。同一个 @/utils/date 需要三处认识它：tsconfig 的 paths 负责编辑器与 tsc 的类型解析，2017 年主流的 webpack 3 用 resolve.alias 负责打包，Jest 的 moduleNameMapper 负责测试运行时。少一处，症状很明确：tsc 通过但页面白屏，或测试报 Cannot find module。

类型声明：三种来源，三种处理

类型声明决定“别人用你的包时能不能通过编译”。来源有三类，处理方式不同。

第一类是内部手写的声明，放在 types/ 下，典型场景是没有类型的旧库，或挂在 window 上的全局对象。写一个 legacy-sdk.d.ts，用 declare module 'legacy-sdk' 列出实际用到的函数即可，不必追求完整。这类文件必须被 include，否则不会生效。

第二类是外部 @types 包，放在 devDependencies，版本尽量跟随被声明库的主版本；不要手改 node_modules 里的声明，也不要复制进 types/ 冒充自己的。版本错位时优先升降 @types，而不是用 skipLibCheck 掩盖：它关掉的是全部声明文件的检查，只能临时止血。

这里没有把根目录的 types/ 包含进来，原因仍是 rootDir：它必须覆盖所有输入文件，一旦 types/ 被读入，TS6059 又会出现。所以项目从“应用”变成“要发声明文件的库”时，源码依赖的环境声明要挪到 src/typings/；根目录的 types/ 只留给不参与构建的辅助声明。

还要让 package.json 的三个字段对齐：main 指向 dist/index.js，types 指向 dist/index.d.ts，files 只写 dist。任一错位，引用方要么找不到 JS，要么找不到类型。发布前用 npm pack 看一眼清单，比本地 link 可靠。

typeRoots 与 types 只在需要收窄自动加载范围时使用。默认会加载 node_modules 下 @types 的所有包，包多了容易让错误的全局声明污染整个程序，这时才显式列出需要的集合。

CI 门禁与反复出现的坑

CI 的价值不在于多跑一遍，而在于用固定的顺序替代“我这能跑”的口头保证。建议顺序是 install → lint → typecheck → test → build：越靠前越快、越容易定位，失败成本越低；前面失败就不用等后面的构建。

安装阶段用锁文件固定依赖。yarn 用 yarn install --frozen-lockfile；npm 5 用 npm install，并确保 package-lock.json 已提交。此时 npm ci 尚未出现，它要到 2018 年 2 月的 5.7 版本才提供，CI 配置里不要照搬后来的写法。

最后列出几个反复出现的坑，它们都不难修，难的是第一次遇到时不知道往哪看。

第一，dist 被再次编译。include 太宽，产物被当成源码，报重复声明。收窄 include，并保证构建前 clean。

第二，类型文件没进包。files 只写了 dist，但 declaration 输出到了别处，或 types 字段指向不存在的路径。用 npm pack 检查。

第三，Node 版本不一致。本地 8.9、CI 8.0，或有人用 9.x 尝鲜，原生模块重编译失败。用 .nvmrc 与 package.json 的 engines 固定版本。

第四，两份锁文件。一半人用 npm、一半人用 yarn，安装结果逐渐分叉。选一个，删掉另一个，在 README 写清楚。

第五，CI 安装时跳过 devDependencies，导致 lint、test 命令不存在；或 CI 与本地 TypeScript 版本不同，出现“只有 CI 才有”的类型错误。安装时显式包含开发依赖，并用锁文件与统一的 Node 镜像解决。

小结

TypeScript 工程化的核心不是更多配置，而是把“检查什么、在哪检查、什么时候拦住”说清楚。目录按职责划分，src 是唯一的产品目录；tsconfig 只管边界，检查配置不产出；脚本把动作固化成命令，typecheck 与 build 分开；lint 与 format 分工；测试守住行为；别名三处同步；CI 由快到慢串联，失败即停。做到这些，类型系统才真正为团队工作，而不只是让编辑器少画几条红波浪线。
