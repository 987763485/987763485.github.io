Go 服务日志规范

本文属于《Go 语言与工程》第 21/78 篇
上一篇系列目录下一篇

服务上线之后，我们对它的了解几乎全部来自日志。一条合格的日志能回答：谁在什么时候对什么做了什么、结果如何；一条不合格的日志只会留下一句“出错了”。本文面向已经能把 Go 服务跑起来、准备或刚刚上线的读者，从字段设计、级别约定、库的选型一直讲到输出与切割，尝试整理出一份团队可以直接执行的日志规范。

日志要回答的五个问题

在讨论用什么库之前，先明确日志为谁而写。笔者把它拆成五个问题：谁、何时、在哪、做了什么、结果如何。它们分别对应五类字段，缺一项，排障时就多问一个人。

  • 谁：发起操作的用户或调用方，例如 user_id、client_id、来源 IP。
  • 何时：事件发生的时间，统一使用 UTC，格式固定为 RFC 3339。
  • 在哪：服务名、实例标识、模块或文件行号，用于定位是哪台机器、哪段代码。
  • 做了什么：动作名称与关键资源，例如创建订单、订单号、request_id。
  • 结果如何：成功还是失败、耗时多少、错误是什么。

结构化不等于把一切都塞进字段，字段太多、命名随意同样会让查询变难。实践中的做法是维护字段字典：时间、级别、服务名、实例、request_id、user_id、error 为公共字段，业务模块只追加少量专属字段，并在文档里登记含义。

日志级别的边界与级别通胀

级别的作用是让读者快速判断“这条日志要不要管”。如果级别用乱了，过滤和告警都会失效。笔者推荐的边界如下：

  • Debug：开发与联调时的诊断信息，例如完整的请求参数、缓存命中情况。生产环境默认关闭，或只对特定用户、特定接口打开。
  • Info：业务上的关键节点与状态变化，例如服务启动、配置加载完成、订单创建成功。它记录“发生了什么”，不记录“每一步”。
  • Warn：出现了异常但已经被处理，例如重试一次后成功、降级到本地缓存、依赖接口变慢。它提示隐患，但不需要半夜叫人。
  • Error：请求最终失败，或数据可能不一致，需要人介入排查。每一条 Error 都应该能被解释为“谁该做什么”。
  • Fatal：进程无法继续运行，例如端口被占用、必要配置缺失。它只应出现在 main 函数或初始化代码里。

最常见的问题是“级别通胀”：为了省事，所有异常都打 Error。短时间看似乎信息更全，实际带来三个后果：告警被淹没，真正要处理的错误混在大量“重试成功”里；日志量成倍增长，存储与检索成本上升；团队逐渐不再相信 Error，看到也不处理。

判断一条日志该用什么级别，可以问自己一个问题：如果这条日志在凌晨触发告警，我会起床处理吗？答案是否定的，就不要用 Error。另一个实用规则是：同一类事件在整条链路上只应有一个最终级别，中间层记录重试与降级用 Warn，最终失败才由边界统一记为 Error。

zap：把结构化做成默认

zap 的定位与 logrus 不同：它从设计之初就把“结构化”和“低分配”放在一起考虑。字段通过 zap.String、zap.Int64、zap.Error 这类构造函数生成，类型在编译期就确定，编码时直接写入缓冲区，不需要先构造一个 map[string]interface{}。对于每秒要处理大量请求、又必须保留结构化日志的服务，这个差异值得认真对待。

关于 context.Context，有一条边界必须守住：它适合携带请求范围内的元数据，例如 request_id、调用方身份、超时与取消信号；不适合携带业务参数。把 order_id、sku 这类本该显式传参的值塞进 context，会让函数签名失去信息，调用方也不知道自己依赖了什么。另外，key 要用未导出的自定义类型，避免不同包使用字符串 key 时互相覆盖。

内容规范、脱敏与采样

字段与上下文准备好后，每条日志写什么同样需要约定。

第一，错误必须带 error 字段，不要拼进消息。logger.Errorf("create order failed: %v", err) 把错误变成了消息的一部分，采集端无法按错误类型聚合；logger.WithError(err).Error("create order failed") 则保留了独立的 error 键，消息保持稳定。

第二，同一个错误只记录一次。常见的情况是 DAO 层记一次、Service 层记一次、Handler 层再记一次，一次失败留下三份堆栈。合理的做法是中间层只补充上下文并向上返回，由最外层统一记录。

第三，消息要稳定，变量放字段。fmt.Sprintf("user %d created order %s", uid, oid) 每个订单都不同，按消息聚合会得到海量分组；写成固定的 create order，两个值放进字段，才能统计事件本身。

第四，敏感信息一律脱敏。密码、令牌、会话 Cookie、完整的身份证号与银行卡号不应进入日志；手机号保留前三位与后四位，中间用星号代替：

还要注意 URL 查询串与请求头，?token=... 和 Authorization 经常在“打印完整请求”时被顺手带进日志。脱敏应该做在写入日志的入口，而不是指望事后清洗。

第五，对高频日志采样。健康检查、轮询接口、重试循环这类日志量大且重复，可以按比例采样或限制每个请求的最大条数；Error 级别的日志通常不采样，但要有总量上限，避免故障期间日志把磁盘写满。采样规则要写在配置里，而不是散落在代码中。

输出、切割、聚合与落地细节

日志写到哪里取决于部署方式。容器里的 Go 服务应写 stdout 与 stderr，交给运行时收集和轮转；在容器内写文件，会随容器销毁而丢失，也让采集链路多绕一层。systemd 托管的二进制服务同理，stderr 进入 journald。只有虚拟机上的传统部署，或需要独立审计文件时，才考虑自己写文件。

文件日志的核心问题是切割，标准库与 logrus 都不提供轮转。社区常用 lumberjack.v2，它实现了 io.Writer，可以直接接到 logger 上：

lumberjack 只按大小轮转，不按日期命名；它假设一个文件只有一个写入者，多实例部署时每个实例写自己的路径，不要让两个进程共享文件。MaxBackups 与 MaxAge 必须设置，否则旧日志只是换了名字，磁盘照样会满。

多服务聚合的前提是格式一致：一行一个 JSON 对象，不要输出多行缩进的 JSON；时间统一为 UTC 的 RFC 3339（容器里可设 TZ=UTC），字段名使用下划线风格；service、instance、request_id 每行都要有。机器时间用 NTP 校准，否则跨服务对比时间线会出现“结果早于请求”的怪事。格式统一后，采集端按行读取、按字段建索引即可。

几个反复出现的坑

第一，在库代码里调用 log.Fatal。Fatal 内部是 os.Exit，不会执行 defer，logger 的 Sync 和缓冲区都没有机会落盘，调用方也失去了处理错误的机会。库函数只返回 error，是否退出由 main 决定。

第二，在 goroutine 里使用全局 logger。请求处理中启动的异步任务，如果拿的是包级 logger，request_id、user_id 全部丢失，出问题时无法与主链路关联。正确做法是把带字段的 entry 或 context.Context 作为参数传进去。

第三，日志过多拖慢服务。JSON 编码、锁与写设备都在请求路径上，量级上来后延迟会明显上升。不要打印大对象和完整响应体，高频路径先采样，上线前压测确认开销。

第四，异常堆栈重复。每层都用 %+v 打印同一次错误，只会放大日志量，掩盖真正的首发现场；错误只在边界记录一次即可。

小结

日志规范的目标不是写出漂亮的日志，而是让故障发生时能在几分钟内定位问题。先确定“谁、何时、在哪、做了什么、结果如何”对应的字段，再选择工具：标准库 log 够用就用它，需要级别与字段选 logrus，热点路径在意分配开销选 zap。让 request_id 贯穿整条调用链，错误只记录一次并保留独立的 error 字段，敏感信息在写入入口完成脱敏。容器场景写 stdout，文件场景用 lumberjack 切割，多服务统一为 UTC 的 JSON 行。规范写下来只是开始，落到字段字典与代码评审里才算真正执行。
