Go 错误封装与 unwrap

本文属于《Go 语言与工程》第 23/78 篇
上一篇系列目录下一篇

在多层结构的 Go 服务里，错误通常从仓储层一路返回到 HTTP 处理函数。如果每一层都只是 return err，日志里就只剩一句干巴巴的失败信息，既看不出发生在哪一步，调用方也无法按错误种类做分支。本文从 error 接口讲起，依次介绍哨兵错误、自定义错误类型，以及当时社区里常用的 github.com/pkg/errors 包装手法与取根因的思路。读完本文，你应该能为自己的项目设计一条既能补充上下文、又保留可检查身份的错误链。

为什么需要错误封装

先看一个常见的场景。处理函数收到请求，调用服务层查询订单，服务层再调用仓储层访问数据库。数据库返回 sql.ErrNoRows，如果三层都原样返回，最终日志只会打印 “sql: no rows in result set”。这条消息在技术上没错，但它没有回答排障最关心的问题：查的是哪张表、哪个订单号、由哪个用户触发。

封装错误的第一价值是补充上下文。每一层把自己知道、而上层不知道的信息附加到错误上，例如资源标识、操作名、关键参数。这样错误从底层向上传递时，信息是累加的，而不是被替换的。

第二个价值是保留错误的身份。调用方常常需要根据错误种类决定行为：记录不存在返回 404，参数校验失败返回 400，数据库超时则可能重试。如果封装把原始错误吃掉，只留下一个字符串，这些分支就无从写起。

第三个价值是让判断摆脱字符串。错误消息是给人读的，措辞会随着文案调整；把 err.Error() == "record not found" 写进代码，相当于把展示文本变成了接口协议，任何一次改字都可能让分支失效。正确的做法是围绕类型和哨兵值做判断，消息只负责可读性。

需要强调的是，封装不是层数越多越好。每一层只应补充该层独有的信息，并保留原始错误供检查；无意义的重复包装只会让日志变长、根因变远。后面介绍的 Wrap 与 Cause，正是围绕这两个目标设计的。

error 接口与哨兵错误的局限

Go 的 error 是一个内建接口，只规定了一个方法：Error() string。任何类型只要实现它，就能被当作错误使用。errors.New 返回标准库内部的错误实现，fmt.Errorf 返回格式化后的错误，二者都满足这个接口。

最传统的定义方式是哨兵错误：在包级导出一个变量，调用方用 == 比较。标准库的 io.EOF、sql.ErrNoRows 都是这个模式。

哨兵错误简单、可比较，适合表达少量稳定的失败种类。但它也有明显短板。其一，它不携带上下文，同一个 ErrNotFound 无法说明查的是用户还是订单，也带不上主键。其二，一旦用 fmt.Errorf 补充信息，身份就丢了。

上面这行是很多项目的默认写法。问题不在消息，而在于 fmt.Errorf 只做字符串拼接，返回的错误与 ErrNotFound 没有任何关系，调用方再也不能用 == 判断。要同时拿到上下文和身份，就需要一种能包住原始错误的结构。

自定义错误类型：把细节带在身上

当错误需要携带结构化信息时，自定义类型通常比哨兵值更合适。例如参数校验失败，调用方不仅要知道失败，还想知道哪个字段、违反了哪条规则。

注意 Error() 定义在指针接收者上，因此只有 *ValidationError 实现了 error。返回错误时应统一用指针，避免有时能断言、有时不能的困惑。

类型断言让调用方拿到完整字段，而不必解析消息。这里同样有个前提：错误在向上传递时没有被 fmt.Errorf 替换掉。只要中间任何一层用字符串拼接重新造了错误，断言就会失败。这正是包装库要解决的问题：补充消息的同时，把原始错误留在链上。

用 pkg/errors 包装错误

在 Go 1.9 时代，标准库没有提供带链的包装。社区里使用最广的是 github.com/pkg/errors。它通过 Wrap、Wrapf、WithMessage 等函数，在错误外面附加消息和调用栈，同时保留原始错误，供 Cause 取回。

包装后的错误用 %v 打印，会得到类似 “read config app.yaml: open app.yaml: no such file or directory” 的链式消息，外层在前、根因在后。用 %+v 打印则会额外输出每次 Wrap 时记录的调用栈，这对定位错误从哪一层开始非常有用。

需要区分消息和栈。消息回答发生了什么，栈回答在哪里发生。Wrap 两者都记录，适合放在错误第一次被补充业务语义的位置；如果同一层反复 Wrap，栈会越积越多，日志也会变得嘈杂。

WithMessage 与 Wrap 的区别

pkg/errors 还提供 WithMessage 和 WithMessagef。它们与 Wrap 的共同点是：都返回一个包住原始错误的新错误，Cause 仍然可以一路取到根因；区别在于 WithMessage 不记录调用栈。

因此选择标准可以简化为：需要栈就用 Wrap，只需要一句补充说明就用 WithMessage。例如在已经很靠近日志边界的地方，栈信息没有额外价值，用 WithMessage 可以少一些开销，也让 %+v 的输出更干净。

另一个函数 WithStack 只记录栈、不附加消息，适合原样保留错误但想标记发生位置的情况。三者都不修改原始错误，而是返回新的包装值，所以同一个底层错误可以被不同分支分别包装，互不影响。

这里要澄清一个常见误解：WithMessage 并不会吃掉原始错误，它和 Wrap 一样保留错误链。真正会丢失链的是 fmt.Errorf 的字符串拼接，或者自定义结构体时只存了 err.Error() 而没有存 err 本身。判断一个包装是否合格，标准不是看它有没有消息，而是看它能否把原始错误交还出来。

另外，Cause 返回的仍是一个 error 接口。如果包装类型在构造时把 typed nil 塞进接口，循环可能拿到一个看起来非 nil、实际为 nil 的值。写包装类型时，构造函数应拒绝 nil 内部错误，取链的代码也要在每一步判空。

在边界层统一记录

错误链让日志更适合只写一次。底层只管包装和返回，不打印；到了 HTTP 中间件、任务调度入口或 main 这类边界层，再用 %+v 把消息和栈一起记下来。每层都打印再返回，同一个故障会出现多条重复日志，反而掩盖真正的根因。

记录时把请求标识、用户标识等放到结构化字段里，消息部分保留错误链即可。日志库的选择与字段规范是另一个话题，这里只强调边界：包装负责补充语义，记录负责落地输出，两者不要混在同一层。

让库返回可检查的错误

库代码的职责是返回调用方能够检查的错误，而不是替调用方决定如何展示。导出的哨兵错误、错误类型以及 IsXxx 辅助函数，都是 API 的一部分，一旦发布就要考虑兼容性。应用层则负责把错误映射成 HTTP 状态码、用户提示和告警级别。

对外响应不要直接拼接底层错误消息，尤其是数据库和网络错误，其中可能包含表名、地址等内部信息。把详细错误写进日志，把稳定、友好的消息返回给客户端，这是库与应用之间最基本的分工。

至于 panic 和 recover，它们处理的是程序无法继续的异常，不应当替代普通的错误返回。只有在进程初始化失败，或者框架边界需要把 panic 转成 500 时，才值得使用；日常业务失败仍然走 error 链。

标准库错误链的展望

标题里的 unwrap 指的是沿错误链解包、取出内层错误这个动作，而不是一个现成的标准库函数。截至本文写作时，Go 1.9 的标准库只有 errors.New 和 fmt.Errorf 这两种常见的错误构造方式，没有统一的解包接口，也没有能在格式化时保留错误链的动词。社区所说的 unwrap，实际依赖的是 pkg/errors 的 Cause 约定，或者项目自己定义的 Cause() error 接口。

Go 团队和社区一直在讨论改进错误检查与错误值的方案，方向包括让包装后的错误可以被程序检查、让标准库提供统一的解包入口等。但这些讨论仍处于提案阶段，尚未发布，也没有确定的时间表。本文不预测具体版本，也不建议在生产代码里依赖尚未落地的 API。

在过渡期，比较稳妥的做法是：项目内部统一使用一种包装库，约定根因接口；对外暴露哨兵错误或错误类型，并用辅助函数隐藏链的细节；日志只在边界层记录。这样即使未来标准库提供了新的机制，迁移也主要集中在包装与判断的少数几处，而不是散落在所有业务代码里。

选择包装库时还要看团队现状。pkg/errors 的 API 很小，学习成本低，和标准库错误可以混用；如果项目已经有一套自己的错误码体系，也可以只借用 Cause 接口，把包装类型换成内部实现。关键不是选哪个库，而是全项目遵守同一套约定：包装时保留原始错误，判断时走链，展示时再转成文案。

最后提醒一句：错误链是给程序和排障用的，不是给最终用户看的。链越长，日志越完整，但用户看到的仍然应该是一句可理解的话。把这两类信息分开，错误封装才算真正落地。

小结

错误封装的目的不是把调用栈堆高，而是在补充上下文的同时保留错误的身份。pkg/errors 的 Wrap 负责消息与栈，WithMessage 只补消息，二者都保留原始错误，Cause 则沿链取回根因。判断错误应依赖哨兵值、类型断言或根因比较，不要比较消息字符串。日志在边界层统一记录一次，库代码只返回可检查的错误。标准库的统一解包能力在当时尚未发布，跨版本迁移时要预留替换包装层的空间。
