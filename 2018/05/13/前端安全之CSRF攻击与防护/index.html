前端安全之 CSRF 攻击与防护

跨站请求伪造（CSRF）大概是前后端都容易低估的一类漏洞：页面没有 XSS，接口也做了登录校验，攻击者却能让受害者在不知情的情况下完成转账、改密码这类操作。本文从攻击成立的条件讲起，依次介绍同步令牌、双提交 Cookie、SameSite、Origin 校验等防护手段，并给出可以直接落地的自查方法。读者需要具备基本的 HTTP 与 Cookie 知识，读完后应能为自己的项目搭起一套完整的 CSRF 防线。

CSRF 是什么

CSRF（Cross-Site Request Forgery，跨站请求伪造）的核心是“借”：攻击者不需要窃取用户的密码，也不需要读到 Cookie 的值，只需要让受害者的浏览器向目标站点发出一个请求。浏览器会自动附上目标站点的 Cookie，服务端看到有效的会话，就把它当成用户本人的操作。

这与 XSS 的思路正好相反。XSS 利用的是站点对用户输入的信任，攻击者把脚本注入页面，从而读取数据、冒充用户；CSRF 利用的是站点对浏览器自动携带凭据这一机制的信任，攻击者躲在第三方页面里，借用户的登录态完成一次请求。用一句话概括：XSS 偷的是数据，CSRF 借的是权限。也正因为如此，CSRF 通常读不到响应内容，同源策略挡在中间，但这并不妨碍请求生效——转账、改邮箱、发消息，一次就够。

攻击成立的三个条件

一个 CSRF 攻击要成立，通常需要同时满足三个条件。第一，目标站点用 Cookie 识别登录态，浏览器会在跨站请求里自动携带；第二，请求参数可预测，攻击者知道接口地址和字段名，不需要用户输入验证码或随机数；第三，服务端只检查 Cookie 是否有效，既不校验请求来源，也不校验额外的令牌。

    participant E as 恶意站点

    U->>E: 访问被诱导的页面
    E->>E: 渲染隐藏表单并自动提交

    B->>B: 校验 Cookie 通过，执行转账
    B-->>U: 返回结果页，攻击者读不到响应

这也是 CSRF 最迷惑人的地方：请求的每一个字节都来自受害者自己的浏览器，访问日志里看不出异常，只有结合来源和业务上下文才能发现。

常见攻击载体

CSRF 的载体不止表单一种，凡是浏览器会自动发起、又能带上目标站点 Cookie 的请求，都值得警惕。

表单 POST 最经典，也最可靠。字段全部设为 hidden，页面加载后调用 submit()，或者诱导用户点击按钮；表单提交属于简单请求，不受跨域脚本限制。

img 标签只能发 GET，攻击者读不到响应，但写操作若用 GET 就已经生效，图片能否加载并不重要。a 标签同理，把链接伪装成“点此查看”，用户一点就完成一次请求。

JSONP 通过 script 标签加载，天然跨站。如果接口有副作用，直接中招；即使没有，JSONP 也常被用来读取数据，那属于另一个话题。

历史上 Flash 的 crossdomain.xml 配置不当也曾是绕过同源策略、发起跨站请求的通道。随着 Flash 逐步退场，这条路径已不主流，但老系统里仍可能残留。

真正的教训是写操作不要用 GET。浏览器预取、爬虫、缓存、img 标签都可能触发 GET；换成 POST 只是提高了门槛，并不等于安全。

同步令牌

同步令牌（Synchronizer Token）是目前最可靠的方案，思路是把一个攻击者猜不到的随机值同时放在两处：服务端的会话里，以及表单或请求头里。

生成时用密码学安全的随机数生成器，比如 Node.js 的 crypto.randomBytes 或 Java 的 SecureRandom，长度至少 128 位。令牌与会话绑定，存放在服务端 session 中，不要只放在 Cookie 里，否则又回到“浏览器自动携带”的老问题。

双提交 Cookie

双提交 Cookie（Double Submit Cookie）是一种无状态方案：服务端不保存令牌，而是让同一个随机值出现在两个位置，一个是可以被脚本读取的 Cookie，另一个是请求参数或自定义头。服务端只比较两者是否一致。

攻击者能让浏览器带上目标站点的 Cookie，却读不到它的值，同源策略挡住了脚本读取，自然无法把同样的值放进参数里，请求于是被拒绝。

这个方案有个前提：Cookie 不能被第三方写入。如果 example.com 下存在可被攻击者控制的子域，或者发生子域接管，攻击者就能从那个子域设置 Domain=.example.com 的同名 Cookie，把自己的值“种”进父域，双提交随即失效。带 __Host- 前缀的 Cookie 要求必须来自当前主机且不设置 Domain，能在支持的浏览器里缓解这类注入，但清理子域资产才是根本。

双提交也防不住同站 XSS：脚本能读 document.cookie，也能直接发请求，令牌在它面前没有秘密。同步令牌同样如此。

SameSite Cookie

SameSite 是 Cookie 的一个属性，用来告诉浏览器“这个 Cookie 在跨站请求里要不要带上”。它由 2016 年前后的草案引入，Chrome 从 51 版开始支持；Firefox 60 在 2018 年 5 月才跟上，Safari 当时尚未支持，因此只能作为纵深防御。

Lax 的规则是：跨站的 POST、PUT 等请求不带 Cookie，但从其他站点点击链接跳转过来的顶层 GET 导航会带上。对多数网站来说，这是体验与安全的折中，用户从搜索引擎或邮件里点进来，仍然是登录状态。

Strict 更严格：任何跨站请求都不带 Cookie，包括顶层导航。安全强度更高，但用户从外部链接进入时会显示未登录，需要再点一次或重新登录，对依赖外链引流的产品不太友好。

不设置 SameSite 时，浏览器不会做额外限制，跨站请求照常携带 Cookie，这是 2018 年大多数站点的现状。

使用时注意两点。Lax 放行顶层 GET，所以用 GET 完成的写操作在 Lax 下依然危险；SameSite 只约束 Cookie，不能替代令牌，老浏览器和部分 WebView 的行为也不可靠。合理的位置是默认都加上 Lax，敏感操作再用令牌兜底。

Origin 与 Referer 校验

Origin 与 Referer 是浏览器自动附加的来源信息，服务端可以据此判断请求是不是从自己的页面发出的。

Origin 头在跨站请求中通常会带上，只包含协议、主机和端口，信息量小，适合做白名单判断。Referer 包含完整路径，可能泄露隐私，也可能被 Referrer-Policy 裁剪。

Referer 缺失很常见：页面设置了 Referrer-Policy: no-referrer，从 HTTPS 页面请求 HTTP 接口，用户通过书签或直接输入地址访问，某些隐私插件或企业代理也会剥掉它。服务端要有明确策略：优先看 Origin，缺失时再看 Referer，两者都没有时拒绝写请求，或至少降级处理并记录日志。

前后端分离与 JSON API

前后端分离的项目里，接口大多返回 JSON，这带来了一些额外的防护空间，也带来一些误解。

跨站表单只能发送三种 Content-Type：application/x-www-form-urlencoded、multipart/form-data 和 text/plain。如果接口只接受 application/json 并严格检查请求头，普通表单就发不出合法请求。攻击者若用 XMLHttpRequest 设置 JSON 头，就会触发 CORS 预检，而预检需要服务端明确放行他的域名，通常不会成功。

自定义请求头也是同样的道理：给 AJAX 加上 X-Requested-With: XMLHttpRequest 或 X-CSRF-Token，跨站请求必须先过预检。这是 2018 年很多团队的常见做法。

但这条防线比想象中脆弱。有些框架会把 text/plain 的请求体也当 JSON 解析；有些接口为了兼容客户端，对 Content-Type 并不严格；更危险的是 CORS 配置错误，把 Access-Control-Allow-Origin 反射成请求的 Origin 并允许携带凭据，等于向所有站点开放了接口。

所以自定义头和 Content-Type 检查只能提高攻击门槛，真正要保护写操作，仍然要回到令牌或 SameSite。

容易被忽略的场景

除了转账，还有一些场景容易被忽略。

登录 CSRF：攻击者用自己的账号在受害者的浏览器里完成登录，此后受害者在该站点上的操作都落在攻击者账号下，用户随后输入的收货地址、绑定的支付信息就可能被攻击者看到。登录表单同样要带令牌，登录成功后轮换 session id。

登出 CSRF：一个指向 /logout 的 img 标签就能让用户退出登录。危害有限，但常被用来配合钓鱼或制造混乱，登出也应该是 POST 加令牌。

文件上传：multipart/form-data 属于简单请求，跨站表单可以直接提交。上传接口同样要校验令牌，并对文件类型、大小和存储位置做限制。

GraphQL 单端点：所有操作都发往同一个 /graphql 地址，传统按 URL 区分写接口的豁免规则不再适用。令牌要在统一的中间件里校验，同时禁止用 GET 执行 mutation。

最后要强调：XSS 可以让以上所有令牌防护失效。攻击者一旦能在页面里执行脚本，就能读到令牌并带着它发请求，CSRF 防护替代不了 XSS 防护。

自查清单与测试方法

下面这份清单可以用来检查一个站点是否具备基本的 CSRF 防护。

  • 所有改变状态的接口都使用 POST、PUT、DELETE，GET 只读。
  • 每个写接口都校验同步令牌或双提交 Cookie，登录、登出、改邮箱、改密码一个不漏。
  • 会话 Cookie 设置 HttpOnly、Secure，并按兼容性加上 SameSite=Lax。
  • 服务端校验 Origin 与 Referer，白名单精确到 host，来源缺失时拒绝写请求。
  • CORS 不反射任意 Origin，不允许通配符与凭据同时出现。
  • 令牌不出现在 URL、日志和错误页里。

测试可以分三步。先看 Cookie：用浏览器开发者工具或 curl -i 查看 Set-Cookie，确认属性齐全。再重放请求：抓一个正常的写请求，去掉令牌、改掉 Origin 再发一次，预期返回 403。

最后做跨站验证：在本地起一个静态页面，放一个 action 指向目标站点的表单，登录后从另一个端口访问它，观察请求是否被执行。页面最好放在与目标站点不同 host 的环境里，才能真正模拟跨站。如果返回 403 且日志里能查到拦截记录，说明防护链路是通的。

小结

CSRF 的本质是借用用户浏览器自动携带的凭据，攻击者既不需要密码，也不需要读到 Cookie。防御的核心是让请求带上攻击者拿不到的东西：同步令牌最可靠，双提交 Cookie 适合无状态场景，SameSite 与 Origin 校验则是必要的纵深防御。没有哪一种手段能单独解决所有问题，写接口的令牌校验、Cookie 属性、来源检查要一起上。最后别忘了 XSS，脚本一旦能在页面里执行，所有令牌都会失去意义。
