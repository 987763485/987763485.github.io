Babel 6 转译与 polyfill 策略

ES2015 之后，JavaScript 的新语法与新 API 越来越多，浏览器跟进的速度却参差不齐。很多项目一边用 async/await 写业务，一边还要保证 IE 11 能正常运行，这时只靠 Babel 转译并不够。本文从 Babel 6 的处理流程讲起，说明 preset-env、babel-polyfill 与 transform-runtime 各自解决什么问题，并给出应用与库两套可落地的配置。读完之后，你应该能判断 polyfill 该在哪里引入，以及怎样验证编译产物是否真的覆盖了目标浏览器。

语法转译与 polyfill 是两件事

Babel 最容易被误解的地方，是把它当成“让旧浏览器支持新 JavaScript”的万能开关。实际上它只做一半工作：改变代码的形态，不改变运行环境的能力。前者叫语法转译，后者靠 polyfill 补齐。

async/await 是语法。Babel 6 会把它改写成 generator 配合状态机，再包一层 _asyncToGenerator helper。产物里已经看不到 async 关键字，只要执行环境里有 regeneratorRuntime，ES5 引擎也能跑。Array.prototype.includes 不一样，它是对内置对象原型的方法调用，源码里就是 list.includes(2)，没有可供改写的语法结构。Babel 原样保留这行，IE 11 执行时照样报“对象不支持 includes 属性或方法”。

全局对象也是同理。Promise、Symbol、Map、Object.assign 在旧浏览器里根本不存在，转译器不会凭空变出一个实现。你得在代码运行之前，用 core-js 2 这样的库把缺失的 API 安装到全局或局部命名空间里，这一步才是 polyfill。

可以看到 async 没了，但 regeneratorRuntime 和 includes 都还在。前者要运行时提供，后者要 polyfill 提供，这就是两条不同的供应链。

有些特性同时踩在两条线上，for...of 就是例子。语法上它要降级成迭代器调用，运行时又要有 Symbol.iterator 和对应的迭代器实现。只做语法转换，IE 11 会在取迭代器时失败；只装 polyfill，旧引擎又可能不认识 for...of 这种写法。判断一个特性属于哪一类，最直接的方法是看它有没有引入新的语法形式，这类特性也最容易被误判成“Babel 没生效”。

Babel 6 的处理流程

Babel 6 的核心是 babel-core，一次编译大致分三步：parse、transform、generate。parse 用 Babylon 把源码读成 AST；transform 让 plugin 按 visitor 规则改写 AST；generate 由 babel-generator 把 AST 打印回字符串。plugin 是真正干活的最小单位，preset 只是一组 plugin 的集合，外加一些共享配置。

顺序规则值得记牢：plugin 先于 preset 执行，preset 之间按声明顺序倒序执行。也就是说，presets: ["es2015", "stage-2"] 会先跑 stage-2，再跑 es2015。实际效果是让更激进的提案转换先接触原始语法，再交给稳定的 preset 收尾。plugin 之间则按数组顺序从前到后执行。理解这一点，遇到“两个转换互相打架”时才有排查方向。

flowchart TD
  A[ES2015+ 源码] --> B[parse：Babylon 解析为 AST]
  B --> C[transform：plugin 依次改写节点]
  C --> D[generate：babel-generator 输出 ES5]
  D --> E[业务产物]
  F[babel-polyfill 或 core-js 2] --> E

图中最后一步的注入并不由 Babel 的转译流程自动完成，而是靠入口处的 import 或 transform-runtime 的模块改写，这也是后文要展开的重点。顺带一句，Babel 7 在 2018 年上半年仍处于 beta/RC 阶段，包名改成了 @babel/core 这类 scope 形式，但尚未正式发布，本文的配置都按 Babel 6 写。

useBuiltIns：false、entry 与 usage

useBuiltIns 决定 preset-env 要不要碰 polyfill，以及怎么碰。它有三个取值，行为差别很大。

false 是默认值，Babel 完全不注入 polyfill。你写了 Promise 就还是 Promise，需要自己 import 'babel-polyfill'，而且通常是全量引入。这种方式最可控，也最容易引入多余代码。

"entry" 要求入口文件里保留 import 'babel-polyfill'。Babel 会把这一行替换成当前 targets 真正需要的一组 core-js 2 模块，不需要的就不引入。产物比全量小，但仍然是一次性把目标环境缺的能力全部装上，而且这行 import 不能少，少了就完全不生效。entry 模式通常只识别 babel-polyfill 这一条入口 import，换成单独引入 core-js 或 regenerator-runtime，就不会享受按目标裁剪。

"usage" 更进一步，不需要手动 import。Babel 扫描每个文件里用到的内置对象和方法，按需插入 core-js 模块。产物通常最小，适合浏览器清单明确的应用。它的局限也很明显：只能识别静态写法。window['Promise']、把方法名拼成字符串再调用、第三方依赖内部的用法，都可能漏掉。它仍然会污染全局，而且不同 1.x 小版本的实现有差异，usage 是较新版本才加入的，升级前要确认 babel-preset-env 的版本，别拿旧版的文档套新配置。

三者按产物大小排，在 false 下手动全量引入时最大，"entry" 次之，"usage" 最小；按可预测性排则相反。团队里如果不想承担漏检测的风险，"entry" 是更稳的折中。

babel-polyfill 的代价

babel-polyfill 是 Babel 6 时代的官方入口包，内部依赖 core-js 2 和 regenerator-runtime。它的工作方式很直接：被 import 时立即执行 core-js 的 shim，把 ES2015+ 的标准库能力装到全局对象上，同时提供 regeneratorRuntime。Promise、Symbol、Map、Set、WeakMap、Array.from、Object.assign、String.prototype.padStart，都靠它补齐。

代价有三点。第一是全量。哪怕页面只用了 Promise，它也会把整套 shim 带上，体积明显偏大，gzip 之后通常仍有几十 KB。第二是全局污染。它改写的是 window 上的构造器和原型，多个副本同时存在会互相覆盖，babel-polyfill 自己就会直接抛错。第三是版本绑定。应用锁定的是 babel-polyfill 的版本，库如果也依赖它，消费者很难判断最终装进去的是哪一份。

如果只缺 regeneratorRuntime，也可以单独引入 regenerator-runtime/runtime，不必把整套 core-js 带上；反过来，只用 core-js 的 shim 而不引 regenerator，async 仍然跑不起来。拆开引入更灵活，但要把依赖关系记清楚，否则很容易在某个入口漏掉一环。

因此，它适合放在应用入口，且全项目只引一次；不适合放在库里。库里 import 一次 babel-polyfill，等于替所有使用方做了决定，还会让“到底谁该负责 polyfill”变得模糊。库的边界应该止于自己的代码，把运行环境的准备留给应用。

transform-runtime：复用 helper、按需取 core-js

Babel 的语法转换会往每个文件里塞 helper。一个文件用到 class 就有 _classCallCheck，用到 async 就有 _asyncToGenerator，用到展开就有 _extends。文件一多，这些 helper 就重复了几十份。babel-plugin-transform-runtime 的第一个作用，是把它们改写成对 babel-runtime/helpers/* 的引用，让打包工具只保留一份。

第二个作用是改写内置对象引用。开启 polyfill: true 后，代码里的 Promise、Symbol、Object.assign 会被改写成 babel-runtime/core-js/* 下的模块，用的是 core-js 2 的 library 版本，不往全局挂东西。第三个作用是 regenerator: true，把 regeneratorRuntime 变成从 babel-runtime/regenerator 导入，不再依赖全局变量。

这里要区分依赖类型：插件只在编译时用，放 devDependencies；babel-runtime 会被产物 import，必须放 dependencies。版本上，Babel 6 对应 babel-runtime 6.x，不要和 Babel 7 beta 的 @babel/runtime 混用。

polyfill: true 不是没有代价。它只能改写对内置对象及其静态方法的引用，改不了原型上的实例方法。[1, 2, 3].includes(2) 里的 includes 没有独立标识符可供替换，transform-runtime 无能为力，仍然需要应用层 polyfill。另外，每个包各自带一份 babel-runtime 时，core-js 模块也可能重复。对库来说，它最大的价值是“不污染全局、不假设消费者已经装了什么”，但这不意味着库可以把所有运行时能力都包办。

还要注意，transform-runtime 只改运行时引用，不负责语法降级。箭头函数、class、async 的语法转换仍然由 preset-env 完成，两者是配合关系，不是替代关系。

常见坑与排查思路

引入顺序。polyfill 必须在业务代码之前执行。ES module 的 import 会被提升，写在文件后面的 import 也可能先执行，所以入口里要把 import 'babel-polyfill' 放在第一行；用打包工具的 entry 数组时，也要把 polyfill 放在第一项。顺序错了，业务模块顶层就可能先访问尚未定义的 Promise。

IE 11 的报错很隐晦。缺少 Promise 时通常是“Promise 未定义”；缺少 Symbol 时，for...of、迭代器或某些第三方库会报“对象不支持此属性或方法”；includes、Object.assign、Array.from 则直接提示方法不存在。看到这类错误，先确认 polyfill 有没有加载，而不是怀疑语法转换。

polyfill 重复引入。babel-polyfill 内部有单例检查，重复执行会抛出“only one instance of babel-polyfill is allowed”。常见来源是某个依赖自己 import 了它，或者多入口各自引入。应用应保证只有一处入口引入，库则完全不要引入。

stage preset 不稳定。babel-preset-stage-0、stage-1、stage-2 装的是尚未定稿的提案，装饰器、class properties 的语义在不同版本间改过。业务代码临时用可以，库和长期维护的项目要谨慎，至少锁死版本并记录升级风险。

targets 与实际用户不符。targets 写得过窄，构建会少转语法、少装 polyfill，老用户直接白屏；写得过宽，又会把现代浏览器不需要的代码带进来。上线前用访问日志核对浏览器分布，再决定清单。

regeneratorRuntime is not defined。这是 async/await 或 generator 编译后最常见的问题。原因通常是只做了语法转换，却没有提供运行时：没有引入 babel-polyfill、引入顺序不对，或者 transform-runtime 把 regenerator 设成了 false。排查时直接在产物里搜 regeneratorRuntime，看它从哪来。

usage 模式漏检测。动态属性访问、字符串拼接调用、依赖包内部用法，都可能让 "usage" 少装模块。若选择 usage，就要在目标浏览器把所有主流程跑一遍，不能只看构建成功。

如何验证产物

编译通过不等于兼容达标。至少要做三件事：看单文件产物、看打包产物、在目标浏览器里跑。

打开产物，重点搜几个标记：async 是否变成 regeneratorRuntime.mark，class 是否出现 _classCallCheck，helper 是内联还是 babel-runtime/helpers 的 import，entry 模式下 babel-polyfill 是否被替换成多条 core-js/modules/*。如果搜不到 core-js 的痕迹，说明 polyfill 根本没接上；如果 regeneratorRuntime 只有使用、没有来源，运行时一定会报错。

再看打包产物。用未压缩的开发构建，搜索 core-js/modules、regenerator-runtime、babel-runtime/helpers，确认这些模块真的进了 bundle，而不是被 tree shaking 或配置误删。还要确认入口顺序：polyfill 模块应排在业务模块之前，source map 可以帮助定位。压缩后的文件里模块路径可能被抹掉，不适合做这项检查。

最后在目标浏览器跑。准备一台 IE 11 虚拟机，或者用 BrowserStack 这类设备云，打开一个包含 Promise、Array.prototype.includes、Symbol.iterator、async 函数的测试页。控制台里执行 typeof Promise、typeof Symbol、[1, 2].includes(1)，再走一遍登录、列表加载等主流程。只有这里通过，polyfill 策略才算真正生效。

还可以做一次“反证”：临时去掉 polyfill，看测试页是否按预期报错，以确认测试确实覆盖了相关能力，而不是碰巧没有执行到。

小结

转译与 polyfill 是两条独立的供应链：前者改变语法形态，后者补齐运行时能力，不能互相替代。应用通常在入口引入 babel-polyfill，用 entry 模式按目标裁剪；库则应使用 transform-runtime 复用 helper、避免污染全局，并谨慎对待 polyfill 选项。useBuiltIns 的 usage 能进一步减小体积，但存在静态分析盲区，且依赖 preset-env 的版本。最终的判断标准不是构建是否成功，而是目标浏览器里的真实行为。
