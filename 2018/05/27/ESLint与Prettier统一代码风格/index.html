ESLint 与 Prettier 统一代码风格

多人协作的前端项目里，代码风格的分歧往往比逻辑错误更早暴露出来：有人用两个空格，有人用四个；有人坚持单引号，有人偏爱双引号；一次提交的 diff 里有一半只是空白变化。本文从 ESLint 与 Prettier 的职责划分讲起，依次拆解配置结构、规则优先级、冲突处理、编辑器保存时格式化与提交前检查，最后给出一套可以在存量项目中渐进落地的方案。读者对象是已经能独立维护一个前端项目、准备把团队规范固化下来的工程师。

两类问题：格式与语义

代码检查要解决的问题其实有两类，混在一起谈就很容易失焦。

第一类是格式问题：缩进几个空格、字符串用单引号还是双引号、语句末尾要不要分号、单行最长多少字符、对象字面量末尾是否保留逗号。这类问题完全由解析结果决定，不涉及运行时行为，改与不改对程序没有任何影响，只影响人读代码的观感与 diff 的可读性。也正因为“没有对错，只有统一”，它最容易在评审里被反复争论，而争论的收益几乎为零。

第二类是语义问题：声明了却没有使用的变量、引用了未定义的全局、条件里误用赋值、== 与 === 混用、React 组件的 propTypes 缺失、列表渲染时用下标当 key、正则里多余的转义。这类问题指向真实的缺陷或维护风险，需要结合上下文判断，改法也不唯一。

用 ESLint 同时处理两类问题，在早期是可行的：它自带的 indent、quotes、semi 确实能检查格式。问题在于这些规则是“检查后报告”，每条规则各自实现一套启发式判断，彼此还会牵制。例如 indent 对多行三元表达式的理解，和 operator-linebreak 可能并不一致；max-len 与 object-curly-newline 也会互相要求对方让步。规则开得越多，配置越像在打补丁。

Prettier 的思路完全不同：它把源码解析成 AST，丢掉全部原始空白，再按固定算法重新打印。它是“重写”而不是“检查”，因此天然不会自相矛盾。两者放在一起，如果职责不划清，就会出现“Prettier 改成 A，ESLint 要求 B，保存一次又改回来”的死循环。后文的所有配置，本质上都在回答同一个问题：谁是格式的最终权威。

ESLint 4 的配置结构

当时稳定的版本是 ESLint 4.x，配置仍以 .eslintrc 系列文件为核心，其中 .eslintrc.js 因为可以写表达式、能按目录切换规则，是工程里最常用的形式。它的字段不多，但职责要分清。

  • root：告诉 ESLint 到此为止，不再向上级目录查找配置。单仓库项目务必打开，否则可能继承到用户主目录下意料之外的配置。
  • parser：把源码转成 AST 的工具，默认是 espree。需要 JSX、实验语法或 Flow 类型标注时，换成 babel-eslint。
  • parserOptions：传给 parser 的参数。ecmaVersion 决定能识别哪一年的语法，sourceType: 'module' 打开 import 与 export，ecmaFeatures.jsx 打开 JSX。
  • env：声明运行环境，决定哪些全局变量合法。环境不等于语法版本，browser 与 es6 要分开设，测试目录再加 jest。
  • extends：复用写好的规则集合，可以是官方预设、插件导出的配置，或一个 npm 包。
  • plugins：声明使用哪些插件。插件只“提供规则”，规则默认全部关闭，必须在 rules 或 extends 里显式打开，这是新手最容易漏的一步。
  • rules：逐条设置级别，off、warn、error 或 0、1、2，需要参数时写成数组。
  • overrides：按文件 glob 覆写以上任何字段，是处理测试目录、构建脚本与历史代码的主要手段。

extends 的优先级与共享配置

extends 的优先级是理解整套配置的钥匙：数组从右往左应用，越靠左的配置越后加载、优先级越高；rules 字段则在所有 extends 之后应用，所以总能覆盖继承来的同一条规则。这与 CSS 的层叠习惯相反，顺序写反就会出现“明明关了却还在报”的困惑。排查时用 eslint --print-config src/main.js 打印某个文件最终生效的完整配置，比凭记忆猜顺序可靠。

eslint:recommended 是官方给的底线集合，只包含可能导致错误的规则，几乎不碰风格，适合当作第一个 extends。真正决定团队风格的是 airbnb 这类完整预设：eslint-config-airbnb 有两百条上下的规则，约定很细，两空格、必须分号、优先单引号、函数括号前不加空格都已替你定好。它的好处是不用开会讨论，成本有三点：与 Prettier 冲突的规则偏多，后面要专门处理；规则过严会让新人第一天面对满屏错误，转而用 /* eslint-disable */ 一关了之；它还捎带了 React 与无障碍规则，非 React 项目应当改用 airbnb-base。

团队超过三五人后，建议把共识沉淀成自己的 eslint-config-xxx 包：内部继承 airbnb-base，逐条调整有争议的规则，发布到私有 npm 源。各项目只写一行 extends，规则演进交给包版本，而不是在每个仓库里各改各的。

Prettier 的定位：只做格式化

Prettier 1.x 的自我定位非常克制：只做格式化，不做任何语义检查。你写 var 还是 const、变量有没有用到、propTypes 全不全，它一概不管，甚至不会替你排序 import。它只做一件事，读入源码、解析成 AST、再用固定规则打印出来。

解析器由扩展名或 parser 选项决定：JavaScript 用 babylon，TypeScript 用 typescript，Vue 单文件组件用 vue，样式用 css、less、scss，此外还有 json、graphql 与 markdown。因此一个 Prettier 就能把 JS、样式、模板与文档的风格一起统一。

常用配置项不多，放在 .prettierrc 里即可：

选项 默认值 说明
printWidth 80 超过就尝试换行，不是硬性截断
tabWidth 2 缩进宽度，与 useTabs 一起决定整体观感
singleQuote false 是否优先单引号，JSX 属性不受影响
semi true 语句末尾是否加分号
trailingComma none 可选 es5，让多行对象与数组的 diff 更干净

团队的常见取舍是把 printWidth 调到 100 或 120，宽屏下 80 列会把表达式切得太碎；trailingComma 选 es5 而不是 all，因为函数参数尾逗号属于 ES2017 语法，老浏览器还需要转译。tabWidth 与 useTabs 一旦定下就不要再动，它决定了整个仓库的 diff 形态。

.prettierignore 的语法与 .gitignore 相同，dist、coverage、package-lock.json、压缩产物与自动生成的接口代码都应排除。判据很简单：不会有人手动编辑的文件，就不该被格式化，否则每次构建都会产生无意义的改动。

冲突从哪来，怎么解

两套工具同时存在，冲突是必然的。Prettier 按 printWidth 拆行，max-len 可能仍然报超长；Prettier 输出 function foo() {，space-before-function-paren 却要求匿名函数前留空格；对象字面量怎么换行，Prettier 与 object-curly-newline、object-property-newline 各有判断。这些规则在 airbnb 里全是打开的，装上 Prettier 之后立刻开始互相拆台。

官方的解法是 eslint-config-prettier：它本身不含任何检查，只是一份把与 Prettier 冲突的规则统统设为 off 的配置，因此必须放在 extends 数组最后一位。

这样 ESLint 只剩语义规则，Prettier 单独负责格式，两边井水不犯河水。代价是格式问题不再出现在 eslint 的输出里，CI 需要补一条 prettier --list-different。

另一种方案是 eslint-plugin-prettier：把 Prettier 包装成名为 prettier/prettier 的 ESLint 规则，格式不一致就报 lint 错误。官方给的组合写法是一个预设，等价于继承 prettier 配置再打开插件规则：

笔者的建议是：团队小、以新项目为主，用方案 B 图省事；代码量大、多人并行、在 CI 时间敏感的团队，用方案 A，把格式检查拆成独立命令，错误来源更清晰。两者不要混用，更不要在方案 A 的基础上又手动打开 prettier/prettier。

编辑器集成：保存时到底做了什么

把整条链路画出来，一共五道关卡：

flowchart TD
  A[编辑器保存文件] --> B[Prettier 格式化当前文件]
  B --> C[ESLint 显示语义问题]
  C --> D[git commit]
  D --> E[lint-staged 对暂存文件执行 eslint --fix]
  E --> F[CI 全量 lint 与格式检查]
  F --> G[合并]

关于保存时自动修复，边界要划清：formatOnSave 交给 Prettier 是安全的，只改空白与引号；eslint.autoFixOnSave 会把所有可修复的规则一起跑，其中少数会实质改写代码，例如合并重复分支、调整 case 缩进。语义规则大多没有 fixer，因此不会被自动改，但“能自动改”不等于“该自动改”。稳妥的做法是日常只开 formatOnSave，把 ESLint 的修复留给提交钩子，让改动集中在一个可回滚的时刻，而不是散落在每次保存。

提交门禁：lint-staged 与 husky

编辑器配置只能约束愿意配置的人，真正兜底的是 git 钩子。当时的标配是 husky 0.14 加 lint-staged。

husky 0.14 的用法很朴素：安装之后，它会为 package.json 里所有以钩子命名的脚本自动安装 hook，所以只要写一个叫 precommit 的脚本即可，不需要额外的配置文件，也不用去 hooks 目录里放 shell 脚本。

几点说明。precommit 只处理暂存区里的文件，改一个文件不会牵连整个仓库，速度快，也不会把同事没写完的代码卷进来。命令末尾的 git add 在 6.x 之后默认会自动执行，保留它是为了兼容旧版本，写上不影响结果。若采用方案 B，eslint --fix 已顺带格式化，第二个命令可以省掉。

钩子失败时先看输出里的文件名与规则名，修不掉的会列在终端，改完重新 git add 再提交。git commit --no-verify 可以跳过，但应作为例外：跳过只是把问题推给 CI。钩子本身挡不住图形客户端和直接 push，所以 CI 必须再跑全量，并把 eslint 加上 --max-warnings 0。

存量项目怎么渐进落地

在几万行历史代码上直接开 airbnb，结果是几千条错误，没人看得完，最后往往整体 disable 收场。合理的顺序与直觉相反：先减少规则，再自动修复。

第一步，盘基线。用 eslint . -f json -o report.json 跑一遍并按规则统计数量，排在前面的通常是 indent、quotes、semi、comma-dangle，正好都是该交给 Prettier 的格式规则。第二步，接入 eslint-config-prettier 关掉格式规则，再对 no-console、no-plusplus 这类争议规则做减法。第三步，用 overrides 分目录放宽：历史目录给一条低线，新目录按严格标准走，新代码从第一天就干净。

第四步，warning 先行。先不设 --max-warnings，让 CI 通过，观察一两周再把 warn 逐批改成 error。第五步，单独做一次格式化提交：prettier --write 会让所有文件产生空白改动，和业务改动混在一起 review 就废了，正确做法是冻结合并、单独提交，并在后续追溯时用 git blame -w 跳过空白改动。

常见坑

行尾符。Windows 的 core.autocrlf 默认值会让同一文件在不同机器上行尾不同，两边工具都可能报错。仓库根目录放 .gitattributes 写 * text=auto eol=lf，编辑器设 files.eol，一次解决；Prettier 1.x 还没有 endOfLine 选项，只能靠这两处约束。

parserOptions。写了 import 却报 Parsing error，多半是漏了 sourceType: 'module'；在 ESLint 4 上把 ecmaVersion 写成 2018 会得到无效值，当时只认到 2017，对象展开这类 ES2018 语法要交给 babel-eslint。

Vue 单文件组件。用 eslint --ext .js,.vue src 扫描，并确认 eslint-plugin-vue 已装、plugins 里有 vue；模板规则与脚本规则是两套，v-for 缺 :key 只在模板里报。

反复改同一行。保存后 Prettier 改成两格，indent 立刻要四格，光标来回跳。这不是 bug，是两套格式主张在抢方向盘，按上一节接入 eslint-config-prettier 即可。

依赖目录被扫。显式写 .eslintignore，列出 node_modules、dist、coverage，不要依赖默认行为。另外别让规则级别依赖 process.env，本地与 CI 环境不同会让同一份代码得出两种结论，规则应当只由文件路径决定。

小结

格式与语义是两类不同性质的问题，混在一套规则里必然互相拆台。ESLint 负责“代码是否可能出错”，Prettier 负责“代码长什么样”，eslint-config-prettier 把中间的冲突规则关掉，是这套分工的关键。配置上用 extends 继承共识、用 rules 覆盖个别条目、用 overrides 区分新旧目录。流程上让编辑器只做安全的事，ESLint 的修复交给提交钩子，全量检查留给 CI。存量项目先从关闭格式规则开始，再单独提交一次格式化，最后把 warning 收紧成 error。规范的目的不是让人背下两百条规则，而是让格式从讨论中消失。
