Vue 2 源码结构解析

读 Vue 2 的源码，最容易迷路的地方不是代码量，而是模块之间的调用关系：一次数据改动如何一路走到 DOM，编译产物与运行时又如何分工。本文以 2.5.x 的仓库为线索，从目录结构、实例初始化、响应式、异步更新一路讲到虚拟 DOM 与编译器，并在最后给出几个可以在控制台复现的误读。适合已经会写 Vue 组件、想弄清“为什么这样写才生效”的读者。

一、仓库目录：先建立模块地图

读源码之前，先要知道每个目录负责哪一类问题。Vue 2 的仓库根目录下，和阅读源码有关的主要是 build 与 src：build 目录里的 config.js 定义 Rollup 的入口、别名与产物名，src 才是运行时本体。测试与类型声明可以暂时放到一边，它们不影响主干流程。

  • src/shared：最底层的工具箱。util.js 里的 hasOwn、def、isObject、camelize 被几乎所有模块引用，constants.js 则集中放置生命周期名与 SSR 相关常量。它不依赖上层模块，适合作为阅读起点。
  • src/core：与宿主环境无关的运行时。observer 负责把数据变成响应式，vdom 负责 VNode 与 patch，instance 负责实例的初始化、生命周期、事件和渲染，global-api 提供 Vue.use、Vue.extend、Vue.component 等静态方法，components 里放着 KeepAlive 等内置组件，util 则包含 nextTick 与错误处理。
  • src/compiler：模板编译器。parser 把模板字符串解析成 AST，optimizer 标记静态节点，codegen 把 AST 生成 render 函数代码，directives 负责 v-model、v-text 等指令的代码生成。
  • src/platforms：平台适配层。web 目录提供浏览器入口、$mount、DOM 更新模块和 web 平台指令；weex 目录面向 Weex，复用 core 的抽象，只替换宿主相关部分。
  • src/server：服务端渲染。复用 core 的组件与 VNode，但把 patch 换成字符串拼接，最终输出 HTML。
  • src/sfc：单文件组件解析器，主要给 vue-template-compiler 使用，读运行时主线时可以先跳过。
flowchart TD
  Shared[shared 工具与常量] --> Core[core 平台无关运行时]
  Core --> Web[platforms web 浏览器适配]
  Core --> Weex[platforms weex 原生适配]
  Compiler[compiler 模板编译器] --> Web
  Core --> Server[server 服务端渲染]
  Web --> Dist[dist 构建产物]

几条依赖方向值得记住：shared 在最底层；core 只依赖 shared，不知道浏览器 API；platforms 包住 core，把 DOM 操作和编译能力接进来；server 复用 core，并借用 web 平台的服务端模块；compiler 相对独立，由 web 的完整版入口消费。这个分层解释了后面一个反复出现的现象：同一份响应式代码，既能跑在浏览器里，也能跑在 Node 的服务端渲染里。

二、入口与构建产物：full 与 runtime-only 的分界

很多教程从 src/index.js 讲起，但 2.5 的仓库里并没有一个包打天下的入口，真正的入口在 platforms 下按构建目标拆分。理解这一点，才能解释为什么有的项目可以直接写 template，有的项目必须配 vue-loader。

先看 src/platforms/web/entry-runtime.js。它从 runtime/index.js 拿到已经装好 DOM 工具、平台指令和 patch 的 Vue 构造函数并导出。runtime/index.js 里定义了最原始的 $mount：拿到 el 后转成真实节点，然后交给 mountComponent 完成渲染。此时构造函数还不认识 template 字符串。

完整版入口 entry-runtime-with-compiler.js 做了两件事：先保存上一步的 $mount，再用同名函数覆盖它。覆盖后的逻辑是：如果 options 上没有 render，就依次从 options.template 和 el.outerHTML 取模板，调用 compileToFunctions 得到 render 与 staticRenderFns，写回 options，最后调用保存下来的原始 $mount。源码大致如下，省略了开发环境的警告分支：

于是 full 与 runtime-only 的差别就落在这一层：full 版本把 compiler 打进包里，dist/vue.js 与 dist/vue.min.js 属于这一类，可以直接在浏览器里写 template 或挂载带模板的 el；runtime-only 版本只有运行时，dist/vue.runtime.js 属于这一类，体积更小，但不认识 template，遇到 template 选项只会给出警告。单文件组件项目通常用 runtime-only，因为 vue-loader 在构建阶段已经用 vue-template-compiler 把 template 编译成了 render 函数，浏览器拿到的组件对象里本来就有 render。

还有一个常被忽略的差别是 CSP。full 版本编译模板时要用 new Function 生成函数，在禁止 eval 的严格 CSP 下会失败；runtime-only 不碰这段逻辑，因此在安全要求高的页面里更稳妥。这也解释了为什么生产项目更愿意把编译工作前移到构建期。

构建脚本 build/config.js 用别名把不同入口映射成不同产物：web-runtime、web-full、weex、server-renderer 等，再通过 Rollup 的 UMD 或 CommonJS 输出到 dist。读源码时不必背产物名，只要记住：入口决定能力，编译能力是可选的插件式一层。

三、实例初始化：_init 里的顺序不是随意的

无论是 new Vue 还是组件实例，最终都会走到 src/core/instance/init.js 的 _init。它先合并选项，再按固定顺序调用一组初始化函数，最后视情况挂载。顺序是理解很多“为什么这里拿不到值”的钥匙。

mergeOptions 不是简单拷贝：data、methods 会合并成函数，生命周期钩子会合并成数组，props、computed 各有自己的合并策略。组件实例走 initInternalComponent，直接复用父级准备好的配置，避免重复合并。

接下来逐个看这些函数做了什么：

  • initLifecycle 建立父子关系，初始化 $parent、$root、$children、$refs，以及 _watcher、_isMounted 等内部标记。
  • initEvents 把父组件写在模板上的监听器挂到子实例的 _events 上，供 $emit 触发。这里只处理组件自定义事件，DOM 事件不在这里。
  • initRender 准备 $slots 与 $scopedSlots，绑定 _c 和 $createElement，并在 2.5 里用 defineReactive 定义 $attrs 与 $listeners。beforeCreate 在这之后触发，所以此时拿不到 data、computed 和 methods。
  • initInjections 放在 initState 之前，保证 props 与 data 里可以使用 inject 注入的值。
  • initState 依次处理 props、methods、data、computed、watch。源码里先 props 再 methods 再 data，因此 data 能读 props，也能调用 methods；data 返回的对象会被 observe，并代理到 vm 上，this.msg 实际访问的是 this._data.msg。
  • initProvide 放在 state 之后，保证 provide 可以引用 data 与 computed。
  • created 触发时，数据、计算属性、监听器都已就绪，但 DOM 还不存在。需要操作 DOM 的逻辑应放到 mounted。

最后判断 $options.el：根实例通常有 el，于是进入 $mount；组件实例没有 el，由 patch 阶段在创建组件时手动挂载。记住这条依赖顺序：inject 先于 state，provide 后于 state，DOM 永远最后。

四、响应式核心：Observer、Dep 与 Watcher

Vue 2.5 的响应式完全建立在 Object.defineProperty 上。它没有能力监听属性的新增与删除，也不能直接监听数组下标，这个前提决定了后面许多设计。核心只有三个角色：Observer 把普通对象改造成带 getter 与 setter 的对象；Dep 充当依赖收集器；Watcher 代表一个需要被通知的订阅者。

Observer 的职责很单纯：给对象打一个不可枚举的 ob 标记，创建一个 dep，然后递归处理每个属性。遇到对象就 walk，对每个 key 调用 defineReactive；遇到数组则替换原型方法，下一节展开。相关代码可以在 src/core/observer/index.js 找到。

defineReactive 为每个属性闭包创建一个 Dep。读取时，如果当前存在 Dep.target，就让这个 watcher 订阅当前 dep；如果属性值本身是对象，还要让子 Observer 的 dep 也收集依赖，这样数组或嵌套对象被整体替换时也能通知。写入时先比较新旧值，相等就返回；否则更新闭包里的值，重新 observe 新值，最后 dep.notify 通知所有订阅者。

update 并不直接重新渲染，而是把 watcher 交给调度器，这就是下一节异步队列的入口。setter 只负责“通知有变化”，至于什么时候真正执行更新，由调度器统一安排。

五、数组的特殊处理：为什么下标赋值不生效

数组没有属性名可供 defineReactive 拦截。给每个索引安装 getter 与 setter 并非不能做，但数组长度可变，索引会动态增加，逐一拦截既笨重又容易漏；更关键的是 push、splice 等方法会一次性改变多个索引。Vue 选择拦截能改变数组的七个方法，而不是拦截下标。

src/core/observer/array.js 里先以 Array.prototype 为原型创建 arrayMethods，再对 push、pop、shift、unshift、splice、sort、reverse 逐个包装。包装函数先用原方法执行并拿到结果；如果是 push、unshift 或 splice，把新增的元素取出来，交给 ob.observeArray 递归 observe；最后调用 ob.dep.notify 通知订阅者。

这段代码依赖两个前提：一是数组本身已被 Observer 处理，带有 ob；二是数组的原型被替换成 arrayMethods。支持 proto 的浏览器走 protoAugment，直接把原型指过去；不支持的浏览器则用 copyAugment 把七个方法逐个 def 到数组实例上。因此 vm.items.push 会触发更新，而 vm.items[0] = ‘x’ 不会：前者经过被包装的方法，后者只是普通赋值，没有任何人调用 dep.notify。

ob 除了用来拿 dep，还兼作“已观察”的标记。observe 函数看到 value.ob 就直接返回已有的 Observer，避免重复递归；Vue.set 与 Vue.delete 也靠它判断目标是不是响应式对象。

对象新增属性不响应式的原因同样简单：defineReactive 在初始化时把已有的 key 逐个转成访问器属性，后来才加的 key 根本没有 getter 与 setter，读取时不会收集依赖，写入时也不会通知。delete 则把整个属性描述符删掉，原来的 setter 随之消失。Vue.set 的处理分三种情况：数组走 splice；对象上已存在的 key 直接赋值；对象上不存在且对象带有 ob，则调用 defineReactive 安装访问器，再手动执行 ob.dep.notify。Vue.delete 对数组用 splice，对对象用 delete 后同样 notify。这就是文档要求用 Vue.set 而不是直接赋值的源码依据。

六、依赖收集的时机：三种 watcher 的分工

同一个 Dep 可以被多种 watcher 订阅，这是 Vue 能同时支持渲染、计算属性与 watch 的关键。三者的创建时机与 update 行为都不同，混在一起看就很容易误解“为什么改数据没有重新渲染”。

render watcher 在 mountComponent 里创建，getter 是 updateComponent。它负责当前组件的渲染，收集的是 render 过程中实际访问到的属性，模板里没用到的数据不会建立依赖。它的 id 通常小于子组件 watcher，因此父组件先于子组件更新；不过同一组件内的用户 watcher 是在 initState 阶段创建的，id 反而更小，会先于 render watcher 执行。

computed watcher 在 initComputed 里创建，构造时传入 lazy: true，因此不会立刻求值，dirty 初始也为 true。真正的求值发生在渲染读取这个计算属性时：createComputedGetter 发现 dirty 为真，调用 watcher.evaluate，evaluate 内部调用 get 收集依赖，然后把 dirty 置回 false，返回值缓存到 watcher.value。依赖变化时，computed watcher 的 update 只把 dirty 置为 true，不立即计算，也不加入渲染队列；下一次有人读取时才重新求值。

这里有一个容易忽略的细节：createComputedGetter 在求值后会调用 watcher.depend()，让当前渲染 watcher 也订阅 computed watcher 所依赖的那些 dep。这样一来，数据变化时会同时通知 computed watcher 置脏和 render watcher 排队重渲染，计算属性既保持惰性，又能驱动视图更新。若计算属性只被 watch 使用、没有出现在模板里，它就不会触发渲染。

user watcher 由 initWatch 创建，对应选项里的 watch 或实例方法 $watch。它默认不是 lazy，getter 返回被观察的值；deep 为真时，getter 里会调用 traverse 递归读取所有嵌套属性，从而把深层依赖也收集进来。用户 watcher 的 update 走同样的调度队列，回调在 watcher.run 里执行，因此同一 tick 内多次修改也只会回调一次。immediate 为真时，创建阶段会立即执行一次回调。

计算属性默认只有 getter；传入对象时可以同时提供 get 与 set，但 setter 不会自动更新依赖，需要你在 setter 里修改源数据。理解这一点，就不会把 computed 当成“带缓存的 method”来用：method 每次渲染都会重新执行，computed 只在依赖变化且被读取时重新执行。

七、异步更新队列：同一 tick 只渲染一次

理解了 watcher 的 update 只入队，就能回答一个常见问题：为什么在同一个事件处理函数里连续修改三次 msg，页面只更新一次？答案在 src/core/observer/scheduler.js 与 src/core/util/next-tick.js。

queueWatcher 用 has 这个 id 映射做去重：同一个 watcher 在一次刷新里只入队一次，这是“多次修改只渲染一次”的第一层保证。waiting 标记保证 flushSchedulerQueue 只注册一次，不会每来一个 watcher 就排一个微任务。如果当前已经在 flushing，新 watcher 会按 id 插入队列的合适位置，而不是简单追加。

flushSchedulerQueue 先按 watcher.id 升序排序，再依次执行。排序保证父组件先于子组件；同一组件内，用户 watcher 因为创建更早而先于 render watcher 执行；执行前把 has[id] 置空，允许运行过程中再次入队，比如 watcher 回调又改了数据，同时用循环计数防止无限更新。每个 watcher 的 run 会调用 get 重新求值，render watcher 走 updateComponent，用户 watcher 则把新旧值传给回调。全部执行完后重置队列状态，并触发 updated 钩子。

nextTick 本身是一个回调队列。调用时把回调 push 进 callbacks，如果当前没有等待中的刷新，就根据环境选择 timerFunc：优先 Promise.then，把 flushCallbacks 放到微任务；不支持 Promise 时用 MutationObserver 监听文本节点变化，同样落在微任务；再退到 setImmediate 或 setTimeout 0，进入宏任务。2.5 的源码里还能看到 isIE 的判断，因为旧版 IE 的 MutationObserver 行为不可靠。

微任务的意义在于：同一轮同步代码结束后立刻执行，早于浏览器渲染与用户的下一次交互，既能把同一 tick 的多次修改合并，又不会让界面明显延迟。setTimeout 回退则保证老浏览器也能工作，只是时机会晚一些。框架在这里做了一个取舍：优先保证“批量”，其次才是“最早可执行”。

还有两个容易混淆的点。第一，nextTick 从 2.1 起在不传回调时返回 Promise，但内部调度仍然使用回调数组，Promise 只是对外的便利封装；不要据此认为整个更新机制都建立在 Promise 上。第二，用户写的 this.$nextTick 与调度器用的 nextTick 是同一个队列，谁先注册谁先执行。因此要先改数据，再调用 $nextTick，回调才能看到更新后的 DOM；顺序反过来，回调可能先于 flushSchedulerQueue 执行。

八、虚拟 DOM 与 patch：从 VNode 到真实节点

VNode 是一个普通对象，不是 DOM。src/core/vdom/vnode.js 的构造函数记录 tag、data、children、text、elm、ns、context、key、componentOptions、componentInstance、parent 等字段。data 里放 attrs、props、on、nativeOn、directives、scopedSlots 等描述信息；elm 则要等 patch 时才指向真实节点。

createElement 在 src/core/vdom/create-element.js，负责把 render 函数收到的参数规范化：children 可以是字符串、数组或嵌套数组，最终被摊平并转成 VNode；文本节点用 createTextVNode；如果 tag 是组件，则交给 createComponent 生成占位节点。它总是返回 VNode，不会在这里创建 DOM。

patch 在 src/core/vdom/patch.js。它先判断 oldVnode 是否存在：不存在就 createElm 新建；存在且 sameVnode(oldVnode, vnode) 为真，就 patchVnode 就地更新；否则创建新节点、插入到旧节点前面，再销毁旧节点。sameVnode 比较 key、tag、是否为注释、data 是否同时有定义，以及 input 的 type，任何一项不同都视为不同节点。这个判断看似保守，却避免了大量“看起来一样、实际不能复用”的错误。

patchVnode 是就地更新的核心：新旧 vnode 相同则直接返回，被 _m 缓存的静态子树通常走的就是这一步；v-for 中克隆出来的静态节点还会比较 key，命中后复用 elm。有新文本就写 textContent；否则对比 children，双方都有子节点时调用 updateChildren，只有新节点有子节点则创建，只有旧节点有子节点则移除。属性、class、style、事件等由各个模块的钩子更新。

updateChildren 采用双端比较，维护 oldStart、oldEnd、newStart、newEnd 四个指针，每轮依次尝试四种匹配：旧头对新头、旧尾对新尾、旧头对新尾、旧尾对新头。命中就 patchVnode 并移动指针；如果旧尾对新头命中，还要把旧尾对应的真实节点移动到旧头之前。四种都不中时，用旧子节点的 key 建索引，拿 newStart 的 key 去查；查到且 sameVnode 为真就移动，否则创建新节点插入。循环结束后，旧节点有剩余就删除，新节点有剩余就追加。

举个具体例子。旧子节点是 a、b、c、d，新子节点是 d、a、b、c，key 稳定。第一轮：旧头 a 对新头 d 不匹配，旧尾 d 对新尾 c 不匹配，旧头 a 对新尾 c 不匹配，旧尾 d 对新头 d 匹配第四种。于是把 d 的真实 DOM 移到 a 之前，oldEnd 左移到 c，newStart 右移到 a。第二轮旧头 a 与新头 a 匹配，patch 后两个头指针同时右移；第三轮 b 对 b，第四轮 c 对 c。循环结束时两列都走完，整个过程只移动了一次 DOM。

如果没有 key，sameVnode 仍然可能因为 tag 相同而命中，但复用位置会按索引走，列表中间插入时容易把内容错配到旧节点上；key 的作用是告诉 patch“谁是同一个节点”，让移动而不是重建发生。这也是列表渲染要写稳定 key 的底层原因。

九、组件化：占位节点如何变成实例

在模板里写 <my-card> 时，编译器不会为它生成 DOM 标签，而是生成 _c 调用。createElement 发现 tag 不是保留标签，就调用 createComponent，返回一个占位 VNode。这个 VNode 的 data 上挂着 init、prepatch、insert、destroy 四个钩子，componentOptions 里保存 Ctor、propsData、listeners、children 等信息。真正的实例化被推迟到 patch。

createComponent 先通过 Vue.extend 把普通选项对象转成构造函数并缓存，再处理 v-model、props、事件等 data，最后返回 vnode。patch 执行到该节点时调用 init 钩子，initComponent 里用 createComponentInstanceForVnode 新建实例，传入 _isComponent: true，然后手动调用 $mount。组件实例因此没有 el，挂载目标由 patch 决定。

更新阶段走 prepatch：updateChildComponent 更新 props、listeners、$attrs、$listeners 和插槽，并触发生命周期。2.5 新增的 $attrs 与 $listeners 就是在这里维护的：$attrs 收集未声明为 props 的 attribute，class 与 style 除外；$listeners 收集父级事件监听器，配合 inheritAttrs: false，可以干净地把它们透传给内部元素。这两个对象用 defineReactive 定义，因此父级传入新值时会通知依赖了它们的子组件重新渲染。写高阶组件或二次封装时，这比逐个声明 props 省事得多。

插槽在 VNode 层面有两套表现。普通插槽的 VNode 作为组件占位节点的 children 传入，在子组件渲染时由 resolveSlots 按 name 分到 $slots，再通过 _t 渲染。它们是在父组件作用域里编译的，所以能访问父组件的数据，但拿不到子组件的数据。

作用域插槽在 2.5 里用 slot-scope 声明，编译结果是 data.scopedSlots 上的一个函数。子组件调用这个函数并把自身数据作为参数传入，函数返回 VNode。它仍然闭包着父组件作用域，同时多了一层“由子组件决定何时调用、传什么参数”的能力。普通插槽是父组件给什么就渲染什么，作用域插槽是父组件给模板、子组件给数据。理解了这一点，再看列表组件把 item 通过 slot-scope 暴露出去，就不会觉得那是某种特殊语法糖。

组件化还有一个收益常被忽略：每个组件实例都有自己的 render watcher。父组件重新渲染时，只要子组件的 props 没变，子组件未必需要重新渲染；这为后续的性能优化留下了空间，但也意味着“数据变了视图没变”的问题要沿着组件边界去查。

十、事件系统：组件事件不是 DOM 事件

Vue 实例上的 $on、$emit、$off、$once 是一套独立的事件总线，和 addEventListener 没有关系。initEvents 在实例上创建 _events 对象，$on 把回调按事件名存进数组，$emit 取到数组后依次 apply，$off 支持移除全部、按事件移除或按回调移除，$once 则包一层，执行前先把自己移除。

on.fn 这个标记不是多余的：$off 在按回调移除时，会同时比较 cb 与 cb.fn，否则用户拿原始 fn 来注销时找不到包装后的 on。

与 DOM 事件的区别有三点。第一，组件事件不会冒泡，子组件 $emit 只有直接父级模板上的 v-on 能收到；要跨层通信用事件总线或状态管理。第二，事件名不会自动做大小写转换，DOM 模板里通常写 kebab-case，单文件组件里则按原样匹配。第三，原生事件要加 .native 修饰符，它会被编译到 nativeOn 而不是 on，最终由 patch 用 addEventListener 绑定到组件根元素上。

v-model 在组件上不是魔法。编译器遇到组件上的 v-model，会生成 data.model：value 是被绑定的表达式，callback 是赋值函数，expression 是表达式的字符串形式。createComponent 里的 transformModel 再把它转换成 props.value 与 on.input；如果组件声明了 model 选项，就改用指定的 prop 与 event。

原生 input 上的 v-model 则生成 domProps.value 加 input 事件处理，并处理输入法组合态，避免中文输入过程中被强行改写。这也解释了自定义组件为什么默认接收 value、抛出 input；想改成 checked 与 change，就要在组件里写 model: { prop: ‘checked’, event: ‘change’ }。事件系统与 v-model 的编译结果合在一起看，组件间的数据流就清楚了：父级传 props 下去，子级用事件把意图传上来。

十一、编译器：parse、optimize 与 generate

编译器在 src/compiler 下，入口是 index.js 的 compileToFunctions。它先把模板交给 parse 得到 AST，再 optimize 标记静态节点，最后 generate 生成 render 代码字符串，并通过 new Function 转成函数。三步各有明确分工，读的时候可以分开看。

parse 基于 html-parser 与 text-parser。元素节点会记录 tag、attrsList、attrsMap、parent、children；文本节点区分纯文本与带插值表达式的文本；注释节点也会保留。解析过程中，v-for、v-if、v-once 等指令被转换成 AST 上的属性，例如 v-for 会生成 for 与 alias，v-if 会生成 ifConditions。此时还没有任何 DOM 操作，AST 只是对模板结构的描述。

optimize 遍历 AST，判断每个节点是否静态：没有动态绑定、没有插值、不是 v-for 或 v-if、不是组件、不是 slot 等，就标记 static。若一棵静态子树的根满足 staticRoot 条件，会单独标记，generate 时用 _m 把这些静态树渲染成缓存的 VNode。静态节点在 patch 时可以直接复用，省掉整棵子树的 diff；这就是静态标记提升 patch 性能的含义，它省掉的是后续更新，而不是首次渲染。

generate 递归生成代码：元素生成 _c，文本生成 _v，插值生成 _v(_s(expr))，v-for 生成 _l，静态根生成 _m，组件生成 _c 并带上 props、on、scopedSlots 等 data。生成的 render 函数依赖运行时注入的 _c、_v、_s、_m 等 helper，所以编译产物不能脱离 Vue 运行时单独执行。

runtime-only 为什么需要 vue-loader 预编译，到这里就顺理成章了：浏览器里的 runtime-only 包不包含 parse、optimize、generate，只有 render 函数才能工作。vue-loader 在构建阶段用 vue-template-compiler 处理单文件组件的 template，把编译结果写进组件对象；如果没有这一步，运行时看到 template 只能警告。编译器与运行时之间其实是一份约定：编译器负责把模板翻译成调用 helper 的代码，运行时负责提供 helper 与 patch 能力。

顺带一提，compileToFunctions 会按模板字符串做缓存，同一模板重复编译只发生一次；开发环境下还会把 errors 与 tips 收集起来，通过 warn 输出。读编译器源码时，先抓住 AST 的三种节点类型与 generate 的输出形状，比逐行读正则更容易建立整体感。

十二、常见误读与调试：把原理用起来

最后把几个高频误区放在一起，配上可以在控制台验证的例子。例子用完整版构建，直接写 template，方便观察 DOM 的变化。

第一类误读是“数组下标赋值应该触发更新”。由前面的 array.js 可知，只有七个变异方法会 notify；下标赋值不经过任何拦截。同理，直接修改数组 length 也不会触发。需要整体替换时用 vm.items = newArray，需要改某一项时用 Vue.set 或 splice。

第二类误读是“给对象加属性应该自动响应”。defineReactive 只在初始化时给已有 key 安装访问器；新 key 没有 setter，Vue 无从得知。Vue.set 会补装访问器并手动 notify，所以能生效。删除属性同理，要用 Vue.delete，否则视图与数据会脱节。

第三类误读是“deep watch 没成本”。deep: true 会触发 traverse，递归读取对象的所有嵌套属性，收集大量依赖；对象越大，首次收集与每次变更的遍历成本越高。更稳妥的做法是 watch 具体路径，或者用 computed 派生需要的那部分数据。若确实要监听大对象，至少确认它不会在高频事件里变化。

第四类误读是“$nextTick 一定在 DOM 更新后”。它只保证回调在队列里排到自己时执行；如果先调用 $nextTick 再改数据，回调可能排在 flushSchedulerQueue 之前。正确顺序是改数据，再 $nextTick。需要拿子组件引用时，也在 mounted 或 $nextTick 里取，不要在 created 里取。

调试时可以借助几个入口：vm._watcher 是 render watcher，vm._data 是原始数据，vm._data.ob 能拿到根 Observer，Vue.config.devtools 控制 devtools 集成。生产环境不要依赖这些下划线属性，但读源码和排查“为什么没更新”时，它们能快速告诉你依赖有没有收集上。真正要改代码时，优先用公开 API：Vue.set、Vue.delete、$nextTick 与 key，它们背后对应的正是本文拆开的几段源码。

小结

把整条链路串起来：Observer 把数据改成响应式，getter 让 Dep 收集 Watcher，setter 通知 Watcher 入队，调度器借 nextTick 在微任务里批量 flush，render watcher 重新生成 VNode，patch 再用 sameVnode 与双端比较把差异落到 DOM。编译器在构建期或 full 版本里把模板翻译成 render，静态标记与稳定 key 让这份差异计算尽量小。数组方法拦截与 Vue.set 是对 Object.defineProperty 能力边界的补丁，而不是额外的魔法。读源码时沿着这条链走，遇到单个函数再展开，比从目录逐文件硬啃更有效。
