前端组件库设计实践

组件库不是把几个按钮封装成 npm 包：它要在多个项目之间长期复用，API 一旦发布就很难收回，样式、主题、无障碍和发布流程都会反过来约束设计。本文从零讨论一套组件库的设计方法与治理手段，覆盖 API 约定、样式隔离、主题变量、构建产物、文档测试与版本发布。读者应已熟悉 2017 年之后的 Vue 2 与 React 16 组件写法，正在负责或准备启动团队内部的组件库。读完后你应当能画出组件分层、定下 API 规范，并给出可执行的发布清单。

组件库与业务组件：先分清边界

很多团队把抽出来的组件都叫组件库，其实两者的生命周期完全不同。业务组件服务于一个产品，可以随页面改版调整；组件库被多个项目引用，API 一旦发布，修改就要考虑全部调用方。复用的范围决定抽象的力度：只在一个页面用的东西，抽成组件只是整理代码；被三个以上项目引用，才值得进入组件库。

稳定性承诺是组件库最贵的部分。业务代码升级失败，影响一个页面；组件库发布一个破坏性变更，可能让十几个仓库同时构建失败。可以用一个粗略的公式衡量成本：调用点数量乘以单点迁移时间，再加上团队对库的信任损失。前两项可以估算，最后一项常被忽略，却决定团队还愿不愿意继续用这套库。

因此通用库适合分三层：基础组件只负责交互与视觉原语，例如按钮、输入框、弹层，不含业务词汇；复合组件由基础组件组合而成，例如日期范围选择、表格工具栏，仍然保持领域中立；带业务语义的组件，例如订单状态标签、商品选择器，留在业务仓库。判断标准很直接：如果 props 里出现订单、商品这类词，它就不该被跨项目复用。

组件库还是一项产品。需要有明确的维护者、issue 模板、变更记录和路线图，否则半年后就会变成没人敢动的遗留代码。本文后面的讨论都建立在这个前提上：每一次设计决策，都要为未来两三年的兼容性负责。

API 设计：让调用方少记规则

API 是组件库与使用者的唯一契约。好的 API 读一遍文档就能猜出用法，坏的 API 每次都要翻源码。命名是第一关：props 用完整的英文单词，布尔值用 disabled、loading 这类形容词或动名词，避免把主语和动词混在一起；同一含义在全库用同一个词，例如控制显隐统一叫 visible，而不是有的叫 show、有的叫 open。

语义比取值重要。type 表示视觉语义，取 primary、success、danger 等值；size 表示尺寸，取 small、default、large。不要把具体颜色透传给组件，例如 color=”#ff0000”：颜色属于主题层，组件只消费语义。否则换主题时，业务代码里的硬编码颜色会成为最大的阻力。

受控与非受控要明确边界。Vue 2.5 的约定是 value 加 input 事件，v-model 只是语法糖；React 的受控组件由 value 与 onChange 组成，非受控则用 defaultValue 并在内部保存状态。两者共同的坑是：组件内部既维护状态又接收外部值，最后谁覆盖谁说不清。经验法则是：传了 value 就完全受控，组件内部不再改动状态；没传才使用内部状态。

事件命名要贴合框架惯例，而不是照搬原生 DOM。Vue 里 input 表示值变化，用来支撑 v-model，change 表示用户确认提交；React 的 onChange 在文本框上等价于原生 input，每次按键都触发，不要以为它和原生 change 一样。自定义事件按对象加动作命名：Vue 模板里写 visible-change，React 里写 onVisibleChange，避免 click2、onOkClick 这类含糊名字。

插槽与 render props 解决结构可变的问题。Vue 用具名插槽，Vue 2.6（2018 年 2 月发布）已支持 v-slot 新语法，但 2.5 项目仍以 slot 属性为主；React 用 children 函数或 render prop，把渲染权交给调用方。不要在 props 里直接传 VNode 或 JSX 片段，那会把组件和框架的渲染细节绑死，文档也难以描述。

最后一条是克制：不要做万能组件。一个组件如果有八个布尔 props，就有 256 种组合，测试和文档都无法覆盖。遇到这种情况，应该拆成可组合的小组件，让调用方自己拼，而不是继续加开关。

尺寸与状态：把组合收敛成枚举

尺寸和类型是最容易被低估的设计点。尺寸建议只保留三档：small、default、large；超过三档，设计侧难以维护，业务侧也记不住。类型按语义划分，主色、成功、警告、危险各一档，默认档不加修饰符。所有枚举都要有默认值，并且由组件自身给出，而不是要求调用方每次显式传入。

状态组合才是真正的麻烦。disabled、loading、readonly、active、focus 两两组合，很容易写出矛盾的界面：按钮在 loading 却仍可点击，输入框 disabled 却还能聚焦。解决办法不是加更多判断，而是先定义优先级：disabled 高于 loading，loading 高于普通；互斥状态用一个枚举 prop 表达，而不是多个布尔值并存。

默认值还涉及全局配置。业务项目往往希望所有按钮统一尺寸，如果每个调用点都写 size="small"，改一次规范要改几百处。可以在库的根组件通过 provide/inject（Vue）或 2018 年 3 月发布的 React 16.3 新 Context 下发默认配置，组件按就近配置、全局配置、组件默认值的顺序取值。这也是后续主题系统的基础。

还要约束非法组合。例如 danger 与 ghost 同时出现时，到底是描边危险按钮还是实心危险按钮？如果设计稿没有定义，代码里也不应允许：开发环境打印警告，生产环境回退到默认组合。组件库不怕规则多，怕的是规则只存在于某位作者的脑子里。

样式隔离：三条路线与各自的坑

组件库的样式要做到引入即用、互不污染：组件内部不泄漏到外部，外部全局样式也不能轻易改变组件外观。2018 年主流有三条路线：BEM 命名加前缀、CSS Modules、Vue 单文件组件的 scoped CSS。三者并不互斥，不少库会组合使用。

BEM 最朴素也最可控。块名带统一前缀，例如 ui-；元素用双下划线；修饰符用双连字符；状态类用 is- 开头。前缀降低冲突概率，也让人一眼看出类来自组件库。BEM 的缺点是类名冗长，好处是不依赖构建工具，调试时在浏览器里看得清清楚楚。

CSS Modules 在构建时把类名哈希化，天然隔离，配合 composes 还能复用样式片段。它的问题是调试体验：开发者工具里看到的是带哈希的名字，需要 sourcemap 才能定位；业务方想覆盖内部元素时没有稳定类名，只能依赖结构选择器，反而更脆弱。若采用 CSS Modules，建议保留一两个稳定的全局类作为覆盖入口。

Vue 的 scoped CSS 通过给元素加 data-v 属性实现隔离，写起来最省心，但有两个坑。第一，父组件的 scoped 样式作用不到子组件内部，需要深度选择器：纯 CSS 用三个大于号，Sass、Less 等预处理器用 /deep/。第二，深度选择器用多了，隔离名存实亡，组件内部结构一变，外部样式立刻失效。约定是：只有布局微调允许穿透，颜色和字号一律走主题变量。

全局污染往往来自 reset。组件库不应自带完整 reset，那会和业务已有样式打架；只做最小必要的盒模型与字体继承，并限定在组件根节点内。不要在组件里写通配选择器，也不要用标签选择器给 div、span 设样式，这类规则一旦进入业务页面，很难追查来源。

第三方样式覆盖要讲顺序。组件库样式应在业务样式之前引入，让业务方用同等权重就能覆盖；浮层的 z-index 要预留分层区间，例如基础内容 0 到 100，固定栏 100 到 500，弹层从 1000 起，避免业务随手写 9999。覆盖时优先使用组件暴露的类名或主题变量，把 !important 留到真正的最后手段。

主题与设计变量：先有 token，再谈换肤

主题系统的本质，是把决定外观的值从样式规则里抽出来。常用的三层结构是：基础色板，例如 blue-500 这类原始值；语义变量，例如 color-primary、color-danger；组件变量，例如 button-primary-bg。业务与组件只消费后两层，基础色板由设计团队维护。换品牌色时只改一处，而不是全局搜索替换。

2018 年的现实是：CSS 自定义属性在 Chrome、Firefox、Safari 上都能用，但 IE 11 不支持。产品若要兼容 IE 11，不能直接写 var() 了事。可行做法是构建时生成静态回退：用 PostCSS 插件把 var() 替换为计算后的值，同时保留变量声明，让现代浏览器继续使用运行时变量。一份源码，两种浏览器都能得到正确结果。

postcss-custom-properties 开启 preserve 后，会同时输出静态值与 var() 声明：静态值在前，变量在后，旧浏览器忽略后者，新浏览器用后者覆盖。变量要定义在根节点或组件根元素上，避免循环引用。构建时解析失败往往不报错，而是静默产出错误颜色，所以 CI 里要加一条样式产物冒烟检查。

暗色主题在 2018 年是一件昂贵的事。系统级偏好媒体查询 prefers-color-scheme 还没有可用实现，无法跟随系统切换，只能让用户手动选择；暗色也不只是反色，阴影、边框、图片、图表配色都要重新设计；切换主题意味着大量样式重算，低端机上会明显卡顿。务实的选择是先做品牌色主题，把暗色留到设计资源充足时立项。

主题还要保证组件内部一致。禁用态通常在主色上叠加透明度，如果主题色本身很浅，禁用态就看不清；正确做法是为禁用态单独定义变量，而不是用 opacity 一把梭。焦点环颜色也要与背景有足够对比，不能简单复用主色。

无障碍：组件库最容易被忽略的契约

无障碍不是附加功能，而是组件库的基本质量。按钮用 div 实现、只绑 click，鼠标用户一切正常，键盘用户却完全无法操作；弹窗打开后焦点仍留在背后页面，读屏用户会以为什么都没发生。组件库把这些坑集中解决一次，业务方就不必在每个页面重复踩。

键盘可达是底线。所有交互元素都应能通过 Tab 到达，用 Enter 或 Space 触发，用 Esc 取消；自定义控件要实现对应键盘行为，例如下拉菜单用方向键移动、Home 与 End 跳到首尾。能用原生 button、input 解决的，不要用 div 加 role 模拟，原生元素自带焦点、禁用和表单语义，省下的工作量远超样式定制成本。

焦点管理是弹层类组件的核心。打开对话框时把焦点移入，关闭时还给打开它的元素；焦点在内部循环，不能 Tab 到背景。实现分三步：记录来源焦点、设置初始焦点、拦截 Tab 键在首尾元素之间回绕。下面的最小实现只是骨架，真实组件还要处理动态内容与多层弹层叠加。

ARIA 属性够用就好。对话框加 role=”dialog” 与 aria-modal=”true”，用 aria-labelledby 指向标题；折叠面板的触发器加 aria-expanded 与 aria-controls；异步提示区域用 aria-live=”polite”。不要给所有元素加 role，错误的 ARIA 比没有 ARIA 更糟，读屏软件会读出混乱的结构。

颜色对比度有明确门槛：正文与背景至少 4.5 比 1，大字号可放宽到 3 比 1。颜色不能是唯一的信息载体，错误状态除了变红，还要有图标或文字。表单最容易出问题：每个输入框都要有 label，用 for 与 id 关联；错误信息用 aria-describedby 关联并设置 aria-invalid；placeholder 不能替代 label，输入后它就消失了。

目录与包结构：单包、多包与按需引入

组件超过二十个之后，包结构会直接影响使用体验。最常见的是单包多入口：一个 npm 包，源码按组件分目录，构建后每个组件保留独立入口，使用者通过 @acme/ui/lib/button 这样的子路径引入。优点是发布简单、版本统一；缺点是路径冗长，安装时整个包都会进入 node_modules，即使打包只用到一部分。

另一种是 monorepo，每个组件一个包，用 lerna 统一管理版本与发布。它能做到真正的按包安装，依赖关系清晰，适合规模大、有独立维护者的团队。代价是构建发布链路更复杂：改一个基础组件，可能要联动发布五六个包；CI 需要缓存与增量构建。中小团队没有专职基建时，单包多入口通常更划算。

按需引入的本质是只打包用到的模块。ES module 的静态结构让 tree shaking 成为可能，前提是模块没有副作用。组件库常见的副作用是样式：import 组件时顺带引入 CSS，打包器无法判断能否删除。解决办法是把样式拆成独立文件，或提供 babel-plugin-import 这类插件，在编译时把整包引入改写成按目录引入。插件只负责改写语句，真正的收益仍来自模块拆分本身；它的具体配置属于使用文档的范畴，本文不展开。

peerDependencies 是组件库与框架的关系声明。Vue 或 React 不应被打进依赖树，否则业务项目里会出现两份框架实例，事件总线、Context、mixin 全部失效。正确写法是把框架放进 peerDependencies，版本范围写宽一些，例如 ^2.5.0，同时在 devDependencies 里锁定开发用版本。2018 年主流的 npm 5 不会自动安装 peer 依赖，文档里要写清楚请自行安装。

目录约定要同时服务开发、构建与文档。推荐每个组件一个目录，内含源码、样式、测试、示例和 API 元数据；主题、工具函数、图标各自独立目录；构建脚本只做扫描，不硬编码组件清单。新增组件时不需要改构建配置，这是判断目录设计是否合理的一个实用标准。

构建产物：三份格式与边界

组件库的产物要满足三类使用者：用打包工具的业务项目、Node 环境下的测试与服务端渲染、通过 script 标签直接引入的页面。对应三种格式：ES module 供现代打包器做 tree shaking，CommonJS 供 Node 与旧工具链，UMD 供浏览器直接使用。三份产物共用一份源码，构建时只改变模块格式与压缩策略。

Rollup 比应用打包器更适合库，因为它默认把代码视为模块图，输出更干净，也更容易保留 ES module 结构。配置的关键点有三个：external 声明框架依赖不打进产物；output 数组一次产出三种格式；sourcemap 单独输出，便于排查但不内联源码。若团队已有 webpack 3（2017 年发布）的链路，也可以复用，但要额外处理 externals 与多格式输出。

样式是否单独抽出，取决于使用方式。整包引入时，一个 dist/ui.css 最省事；按需引入时，每个组件应有自己的 CSS，业务方引入哪个组件就引哪个样式。不要把样式内联进 JS，那会让主题覆盖和缓存都变难。若用 CSS 自定义属性做主题，样式文件本身可以很小，主题变量单独一个文件，切换时只换主题文件。

externals 的映射要写全。以 Vue 为例，external 里写 vue，UMD 的 globals 里写 Vue，两者缺一不可，否则要么框架被打进包，要么浏览器里找不到全局变量。React 的 UMD 场景还要考虑 react-dom，通常组件库只依赖 react，示例页才依赖 react-dom。peerDependencies 与 external 应保持一致，这是一条容易在重构中失守的规则。

sourcemap 与类型声明属于发布质量。sourcemap 建议发布，但不要内联源码内容，避免把完整源码暴露在产物里；TypeScript 项目可以用 2.8 提供的 emitDeclarationOnly 只生成 .d.ts，类型文件与 JS 产物分目录存放。最后做一次产物冒烟：用 UMD 版本在空白页挂载一个按钮，用 ESM 版本在最小工程里 import 一次。

文档与示例：让 demo 成为唯一事实

文档最怕两套代码：文档里一份示例，仓库里一份 demo，时间一长必然不一致。正确做法是 demo 与文档同源：每个组件目录下放示例文件，文档站构建时扫描，既渲染成可交互示例，也展示源码。示例本身还能作为视觉验收与回归测试的输入，一份代码承担三种用途。

props 表格应该自动生成。组件的 props 定义、默认值、类型、说明都在源码或独立的元数据文件里，构建文档时读取并生成表格。Vue 的 props 对象自带类型与默认值，但默认值可能是函数、类型可能是构造函数，需要一层归一化；React 没有运行时 props 声明，通常维护 propTypes 加注释的元数据。原则是改代码就能改文档。

在线 playground 要谨慎。它确实方便试错，但成本不低：需要沙箱运行环境，需要跟随库版本更新，需要处理依赖加载失败；示例往往和真实业务差距很大，使用者复制回去仍要改。取舍是：静态示例覆盖全部组件，playground 只给三五个高频复杂组件，例如表格、日期选择、表单校验，并明确标注示例版本。

文档还要写不该怎么用。反面示例比正面示例更能减少误用，例如不要在 v-for 里用 index 作为 key 传给可排序列表，不要用两个按钮模拟单选。每个组件页面还应有变更记录入口与无障碍说明，前者帮助升级，后者帮助业务方判断能否直接使用。

测试：单元、快照与视觉回归的边界

组件库的测试分三层，成本递增、收益递减。单元测试验证行为：点击是否触发事件、loading 时是否阻止提交、props 变化是否更新类名。快照测试验证结构：渲染结果是否意外改变。视觉回归验证像素：样式是否走样。三层都要有，但投入比例应反过来，单元测试最多，视觉回归只覆盖核心组件。

单元测试用 Jest 22 加框架适配层。Vue 侧用 @vue/test-utils，当时仍在 1.0 beta；React 侧用 Enzyme 3 加官方 adapter。测试要断言对外行为，而不是内部实现：断言触发的事件、渲染出的文本与类名，不要断言组件内部的 data 或 state 名称，否则一次重构就要改一半测试。

快照测试的边界要划清。适合快照的是小而稳定的结构，例如类名组合函数、图标 SVG、简单渲染输出；不适合整个页面级组件，那种快照几百行，没人会认真 review，更新时一律按确认通过，等于没有测试。快照更新必须进 code review，diff 里出现意外变化要追查原因。

视觉回归的成本主要在基线维护。2018 年 PhantomJS 停止维护后，团队转向 headless Chrome 截图加像素比对；不同系统的字体渲染、抗锯齿、滚动条宽度都会造成差异，CI 容器要固定镜像与字体。可行策略是只对按钮、表单、弹层截图，阈值放宽，把截图当作发现大问题的警报，而不是像素级验收。

覆盖率不要当 KPI。更有价值的指标是：关键交互路径是否都有用例，每个破坏性变更是否有回归用例，issue 里复现的 bug 是否补了测试。做好这三件事，比追求百分之九十的行覆盖率更有意义。

版本与发布：把变更变成可预期的节奏

组件库必须严格遵循 semver：修 bug 升 patch，新增兼容功能升 minor，任何破坏性变更升 major。0.x 阶段可以声明 minor 也可能破坏，但一旦有外部使用者，就应尽快进入 1.0，否则使用者无法用版本号判断风险。预发布用 1.0.0-beta.1 这样的格式，不要覆盖正式版本号。

changelog 要写为什么，而不只是改了什么。从 commit 自动生成能保证完整性，但机器生成的条目往往只有标题；发布前应人工补一段背景，说明变更解决什么问题、有没有替代方案。破坏性变更必须附迁移指南，给出改前改后的代码对比，能提供 codemod 更好。

npm dist-tag 是灰度发布的工具。默认发布到 latest，预发布用 npm publish --tag next，使用者通过安装 next 标签试用；验证一段时间后，再把同一版本提升为 latest。这样既能收集反馈，又不会让普通使用者误装未稳定版本。dist-tag 与版本号是两回事，提升标签不需要重新发布。

发布前检查清单应固化到脚本，而不是靠记忆。至少包括：测试与构建通过、changelog 已更新、peerDependencies 范围正确、文档站已同步、UMD 产物冒烟通过、回滚方案明确。发布流程本身也值得画成图，让每个人知道自己在哪一步、失败了怎么退。

flowchart TD
    A[提交变更] --> B[CI 测试与构建]
    B --> C{是否破坏性变更}
    C -->|是| D[升 major 并写迁移指南]
    C -->|否| E[升 minor 或 patch]
    D --> F[发布到 next 标签]
    E --> F
    F --> G[试用与灰度]
    G --> H[提升为 latest]

发布之后要有观察窗口。组件库的问题往往不是构建失败，而是运行时行为变化：某个边界条件下弹层不关闭、某个浏览器下焦点丢失。保留上一个版本的标签，出问题时引导使用者回退，比紧急发补丁更稳妥。

团队协作：设计、评审与废弃

组件库是设计与工程共同的产品。设计侧先产出 token，即颜色、字号、间距、圆角、阴影，再产出组件规范；工程侧按 token 实现样式，而不是照着标注图逐个写死数值。对接时用标注工具确认间距与状态，把悬停什么颜色、禁用能否点击这类问题在评审阶段问清楚，不要留到提测。

组件评审要有清单：API 是否有歧义、命名是否与既有组件一致、是否支持键盘操作、主题变量是否覆盖、空数据与超长文本等边界是否定义、是否有测试与示例。评审不通过的原因要写进 issue，而不是口头说再改改，半年后同样的争议还会出现。

废弃流程体现团队成熟度。要删除一个 prop 或事件，正确顺序是：文档标记 deprecated 并给出替代；开发环境输出一次警告，生产环境静默；保留至少一个大版本；到期后在 changelog 说明并移除。警告要包含组件名、旧用法、新用法和文档链接，让使用者在控制台就能完成迁移。

协作还需要度量。统计每个组件被多少项目引用、issue 平均响应时间、破坏性变更的影响面，这些数据能帮助团队决定下个版本做什么、哪些组件该合并或废弃。组件库不是写完就结束的项目，它更像一条需要持续维护的产品线。

小结

组件库的难点不在写组件，而在做承诺：承诺 API 稳定、样式可控、主题可换、键盘可用、升级可预期。本文给出的顺序是先分边界，再定 API，然后处理样式、主题与无障碍，最后用包结构、构建、文档、测试与发布流程把承诺固化下来。对大多数团队来说，最值得先做的三件事是：统一 token、建立组件评审清单、把破坏性变更写进迁移指南。剩下的工作可以随着组件数量增长逐步补齐，但边界与发布纪律最好在第一天就确定。
