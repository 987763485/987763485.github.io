前端状态管理方案选型

状态管理几乎是每个中型前端项目都会遇到的问题。2018 年上半年，Redux 4.0 刚刚发布，MobX 在 3.x 与 4.x 之间过渡，Vuex 3 随 Vue 2.5 稳定下来，React 16.3（2018 年 3 月发布）又把新的 Context API 推到台前，可选项比两年前更多，争论却没有变少。本文不再教某个库的 API，而是回到更靠前的问题：状态应当怎样分类，什么情况下根本不需要库，几种方案的心智模型与团队成本差在哪里，以及一个已经在跑的项目如何低成本迁移。读完之后，你应当能为自己的项目写出一页纸的选型理由，而不是凭“大家都在用”做决定。

一、先把状态分类，再谈方案

很多关于状态管理的争论，其实在讨论不同的东西。一个人说“我们项目状态很乱”，可能指的是接口数据没有缓存；另一个人说的可能是弹窗开关散落在十几个组件里。不先把状态分类，选型就会变成拿锤子找钉子。

笔者习惯按“生命周期”和“共享范围”两个维度切分，得到五类状态。

五类状态

第一类是组件局部状态。输入框的当前值、下拉菜单是否展开、鼠标是否悬停，这些状态只服务一个组件，随组件挂载而生、卸载而灭。它们不需要被序列化，也不需要被其他组件读取。

第二类是跨组件共享状态。当前登录用户、权限列表、主题、购物车条目，这些数据被多个页面或相隔很远的组件使用，生命周期比任何一个组件都长。

第三类是服务端数据缓存。列表页的数据、详情页的数据、分页游标，本质上是服务端数据库的一份副本。它有失效时间，会过期，需要重新拉取。

第四类是 URL 与路由状态。当前页码、筛选条件、标签页、搜索关键词。这类状态的特殊之处在于，它应当可以被收藏、分享，刷新后还能还原。

第五类是表单状态。草稿值、校验错误、是否被修改过、是否正在提交。它变化频繁，且往往只在一次编辑会话内有效。

分类决定载体

把五类状态分开之后，很多问题会自动消失。服务端数据不该和 UI 状态混在一个 store 里，因为它们的失效策略完全不同；URL 状态不该只存在内存里，否则用户刷新页面就丢了筛选条件；表单草稿也不该进全局 store，否则一次未提交的编辑会污染整个应用。

可以用一张表把判断固定下来。

这张表不是教条，而是一组提问的顺序。当你想把某类状态放进 Redux 之前，先问一句它属于哪一类。如果答案是服务端数据，那么真正需要的是缓存与失效策略，而不是 action 与 reducer；如果答案是 URL 状态，那么先看看路由能不能承担。分类做对了，后面的选型会简单很多。

二、什么时候不需要状态管理库

三个判断信号

在引入任何库之前，可以先看三个信号：共享状态是否超过五个，组件层级是否超过三层，是否存在跨路由保持状态的需求。三个答案都是否，组件 state 加 props 就够了。

React 的组件组合本身是一种被低估的方案。把子组件作为 children 传下去，中间层不必知道这些 props 的存在，也就避免了逐层透传。很多“需要全局状态”的场景，用组合重写之后就不需要了。

过早引入的代价

过早引入状态管理库的代价，往往在半年后才显现。

第一是概念税。团队里每个人都要理解 action、reducer、dispatch、middleware、selector 这一套词汇，新人的第一个需求还没写完，先要读三篇文档。

第二是改动成本。改一个字段，要在 types、actions、reducers、组件四处跳转；一个简单的布尔开关，被拆成四个文件里的五处修改。

第三是抽象泄漏。当库的约定没有覆盖某个场景，开发者会在 store 之外再放一份状态，于是同一份数据有了两个来源，这比一开始不用库更糟。

第四是调试路径变长。出问题时，你首先要判断是组件状态不对，还是 store 里的状态不对，还是两者之间的同步逻辑没跑。

Context 的边界

React 16.3（2018 年 3 月发布）提供了新的 Context API，React.createContext 返回 Provider 与 Consumer，跨层级注入变得正式而简单。它足以承担“低频变化的全局配置”，例如主题、当前语言、登录用户。

但 Context 不是 store。Provider 的 value 一旦变化，所有消费者都会重新渲染；它没有选择器，也没有按字段订阅的机制。把高频变化的状态放进 Context，会让整棵子树跟着抖动。常见的做法是按关注点拆成多个 Provider，或者把 value 做成稳定的对象，只在内部字段变化时通过订阅通知。

笔者的经验是：Context 适合“读多写少”的共享状态，不适合“写多读多”的交互状态。越过这条线，就该考虑真正的 store 了。

三、候选方案全景

2018 年年中，React 生态里能上台面的选择大致有四种，Vue 生态则基本由 Vuex 统一。把它们放在一张桌子上，先看各自的位置，再看细节。

Redux 3.7 与 4.0

Redux 3.7 仍是大量项目的实际版本，4.0 在 2018 年 4 月发布，主要变化是用 TypeScript 重写了类型定义、清理了废弃 API、缩小了包体，核心 API 没有大的改动。它把状态放进单一 store，只允许通过 dispatch action 修改，reducer 必须是纯函数。中间件机制让异步、日志、持久化都可以插拔。

MobX 3 与 4

MobX 3.x 与 4.x 在 2018 年交替存在。4.x 在有 Proxy 的环境使用 Proxy，没有时退回 ES5 的 defineProperty 实现，因此 IE11 仍可用。它的核心是 observable、computed、action、reaction 四个概念：状态是可变的，依赖由运行时自动追踪，读取即订阅。

Vuex 3

Vuex 3 是 Vue 2 的官方方案，state、getters、mutations、actions、modules 的分工很清晰，和 Vue 的响应式系统天然贴合。它的适用范围基本被 Vue 生态限定，跨框架复用不是它的目标。

Context 加手写 reducer

不引入任何库也能得到一个迷你 store：容器组件持有 state，写一个纯 reducer 函数，dispatch 时先算出新状态再 setState，最后通过 Context 把 state 与 dispatch 下发。它没有中间件、没有 devtools、没有选择器缓存，但对中小型页面已经够用。需要说明的是，这种写法通常落在一个类组件容器里，函数组件此时只负责展示。

把服务端数据交给请求层

还有一条常被忽略的路线：根本不把服务端数据放进全局 store，而是让请求层负责缓存、去重、失效与重试。组件按需请求，请求层返回缓存或发起新请求。2018 年已经有不少团队这样做，GraphQL 场景下的 Apollo Client 把这条路走得最完整。它的好处是服务端数据的生命周期由请求层统一管理，UI 状态与服务端状态不再互相牵连。

MobX 可观察对象、自动追踪 工具链较轻 交互复杂、交付要快

四、心智模型对比：纯 reducer 与可观察对象

选型时最值得比较的不是 API，而是心智模型。同样一个购物车，两种方案写出来的代码，暴露的是两种世界观。

Redux：把“发生了什么”变成数据

Redux 的出发点是：UI 是状态的函数，状态只能由 action 描述的变化推导出来。所有修改都经过 reducer，reducer 是纯函数，输入旧状态与 action，输出新状态。

注意总价没有被存进 state。它是从 items 推导出来的，放在 selector 里按需计算，这是 Redux 社区反复强调的一条纪律。

MobX：描述状态是什么，修改就是方法调用

MobX 的出发点是：状态是一个可观察的对象，任何读取它的地方都会被自动记录，修改之后相关方自动更新。开发者写的是“业务对象”，不是“状态转换”。

同一个需求，MobX 版本没有 action type，没有不可变更新，也没有独立的 selector 文件。合并逻辑就是几行普通的命令式代码，读起来接近业务描述。

差别在哪里

Redux 用约束换可预测性：所有变化都有名字、都可序列化、都可重放。MobX 用自由换表达力：代码短、贴近业务，但变化的路径是隐式的。

这也解释了两者在团队里的表现。Redux 项目里，任何人看 action 日志就能还原一次操作；MobX 项目里，改动一个属性可能触发五处更新，只有理解依赖图的人才说得清。选哪一种，取决于你更怕“状态不可预测”，还是更怕“代码写不动”。

五、可调试性：时间旅行与依赖追踪

调试体验是选型中最容易被低估的一项，却往往是项目上线后最需要的。

Redux 的优势在可回放

Redux DevTools 可以把每一次 dispatch 记录下来，展示 action 名称、payload 与前后状态差异，并支持时间旅行：拖动滑块回到任意一步，界面随之还原。要做到这一点，前提是 reducer 纯、action 可序列化、状态不可变。异步请求通过 middleware 把“开始、成功、失败”拆成三个 action，日志里能完整看到一次请求的生命周期。

这套能力在排查“用户点了三下按钮之后页面为什么变成这样”时非常有效。代价是纪律：一旦有人在 reducer 里写了 Date.now()，或者直接修改了 state，时间旅行就会失真。

MobX 的优势在看清依赖

MobX 的调试思路不同。它不记录变化序列，而是回答“这个值为什么变了”。trace 可以打印出某个 computed 被谁读取、又被谁修改；spy 可以监听所有 action 与 reaction；mobx-react-devtools 能在页面上高亮正在渲染的组件，并列出本次渲染读取了哪些 observable。

它的短板是回放。因为状态是原地修改的，没有历史快照，时间旅行无从谈起。需要撤销重做时，通常要引入 mobx-state-tree，用它的快照与 action 记录补上这一块。MST 在 2018 年已经是可用方案，但学习成本不低，且会把写法重新拉回“动作 + 快照”的范式。

调试诉求如何影响选择

如果项目对可审计、可回放、可复现有硬要求，例如涉及金额、权限、审批流，Redux 的日志模型几乎是天然匹配。如果项目的主要难点是交互复杂、状态变化频繁，开发者更需要知道“谁触发了更新”，MobX 的追踪工具反而更顺手。

六、样板代码与团队成本

Redux 的三件套

一个字段的改动，在 Redux 里通常要碰三处：action type 常量、action creator、reducer。社区为此提出 ducks 模式，把同一个模块的 type、creator、reducer 收进一个文件，减少目录跳转。ducks 改善了组织方式，但没有消除概念数量。

样板代码的真正成本不在字数，而在“改一处要理解四处”。对熟悉的人，这是清晰的分层；对新人，这是一条必须走完的流程。

MobX 的装饰器与严格模式

MobX 的代码量明显少，但有两处需要提前约定。

一是装饰器。2018 年，Babel 6 需要 babel-plugin-transform-decorators-legacy，TypeScript 需要开启 experimentalDecorators，两者对装饰器的实现细节并不完全一致。团队最好在项目模板里统一，而不是让每个人自己配。

二是严格模式。useStrict(true) 之后，所有修改必须发生在 action 里，否则直接报错。不开严格模式，任何组件都能随手改 store，短期很省事，长期会出现“不知道谁改的”的问题。笔者的建议是：新项目一律开严格模式，老项目在补 action 的过程中逐步打开。

新人上手曲线

Redux 的曲线是“先陡后平”：概念多，但路径固定，照着模式写不容易出错。MobX 的曲线是“先平后陡”：半天就能改出东西，但要过一两个月才明白什么时候该用 computed、什么时候该拆 store。

团队人数少、流动低，MobX 的效率优势明显；团队人数多、外包多、交接频繁，Redux 的约束更像一种保险。

七、TypeScript 友好度

2018 年上半年，TypeScript 2.8 已经带来条件类型，2.9 在 5 月中旬发布，类型表达能力比一年前强了不少。三个方案在类型上的体验差异，主要来自它们的 API 形状。

Redux：联合类型是天然契合

Redux 的 action 是一个个普通对象，最适合用可辨识联合（discriminated union）描述。reducer 的 switch 在收窄之后，payload 的类型会自动确定。

痛点也有：connect 的泛型参数需要手写，mapStateToProps 与 mapDispatchToProps 的类型推导在 react-redux 5 里并不总是准确，通常要显式标注组件的 props。另一个坑是 combineReducers 推导出的根状态类型，早期写法里需要手动声明一个 RootState 别名，否则选择器拿不到完整类型。

MobX：装饰器能推断，但边界要标清

@observable 修饰的属性，类型由初始值或显式标注决定，读取处的推断基本顺畅。麻烦集中在三处：@computed 的返回类型在复杂表达式下需要显式写出；observer 包裹之后，组件的 props 类型要单独声明；装饰器与严格属性初始化同时开启时，属性初始化顺序会带来额外的断言。

Vuex：类型是短板

Vuex 的 store 是一个普通对象，组件里的 this.$store.state 几乎拿不到精确类型。2018 年常见的补救办法是用 vuex-class 之类的装饰器封装，或者为每个 module 手写接口再在组件里断言。Vue 2.5 改善了与 TypeScript 的集成，但 Vuex 这一层仍然需要额外约定。

结论很直接：以 TypeScript 为主的项目，Redux 的类型路径最顺；MobX 次之，需要团队自己补类型工具；Vuex 需要接受一定程度的类型损耗。

八、性能：重渲染范围与依赖粒度

性能讨论最容易变成阵营之争。这里只谈机制，不给没有出处的数字。

React 的渲染前提

React 的更新从 setState 的组件开始，向下协调整棵子树。是否真正操作 DOM 由 diff 决定，但 render 函数会执行。所以“重渲染”不等于“慢”，可当组件树很大、render 里有昂贵计算时，重复执行就是浪费。

优化的手段是让不该更新的子树提前停下：PureComponent 与 shouldComponentUpdate 做浅比较，或者用一个只比较 props 的高阶组件包住函数组件。浅比较要生效，状态更新必须是不可变的：返回新对象，旧对象不动。这正是 Redux 与不可变数据契合的地方。

选择器与 computed

Redux 侧常用 reselect 创建记忆化的选择器，输入不变时直接返回上次结果，避免在 mapStateToProps 里每次生成新数组导致无谓渲染。Vuex 侧的 getters 与 Vue 的 computed 由框架缓存，依赖不变就不会重算。MobX 的 computed 也是缓存加自动失效，区别在于依赖是运行时收集的，不需要手写输入声明。

MobX 的细粒度依赖

MobX 的 observer 组件只在自己读取过的 observable 变化时重渲染。一个列表里改了一行的数量，理论上只有读了这个字段的单元格会更新。这种粒度在复杂交互界面里很有吸引力。

但它有两个前提：组件要正确使用 observer，读取要发生在 render 期间。把 observable 的值提前解构到普通变量，或者在 observer 外层读取，都会让依赖追踪失效，更新就不再发生。这类 bug 往往表现为“数据变了界面没变”，排查起来比性能问题更费时间。

一句提醒

无论选哪种方案，先测量再优化。用 React DevTools 观察组件更新次数，或者直接在 render 里打点，比争论“谁更快”有用得多。多数项目的性能问题来自一次渲染上万行列表，或者在选择器里做了重计算，而不是 dispatch 本身的开销。

三个典型场景

后台管理系统。页面多、表单多、权限与路由耦合紧，状态数量中等但要求可追溯。团队规模超过十人时，Redux 配中间件处理审批流与批量操作更稳；小团队可以用 MobX 加快交付，但要提前约定严格模式与目录结构。这里的判断依据不是页面数量，而是“一次错误操作的代价有多大”。

内容型站点。大部分数据来自服务端，页面以展示为主，交互集中在筛选与分页。这类项目通常不需要全局 store：筛选条件放进 URL，数据交给请求层缓存，登录用户用 Context 注入即可。引入 Redux 往往只会增加一层转发，收益接近于零。

复杂交互编辑器。画布、图层、属性面板之间存在高频双向联动，还要支持撤销重做。MobX 的细粒度更新在这里很舒服，但撤销需要额外设计；Redux 的 action 日志天然适合实现 undo/redo，代价是每个操作都要写完整的 action 与 reducer。折中的选择是 mobx-state-tree，用快照换回放能力。

十、渐进式迁移

迁移比选型更容易出事。常见的失败模式是“一次性重构”：改了两周，功能冻结，最后回滚，团队从此对状态管理心存恐惧。

三个阶段

第一阶段，把散落的组件状态收拢。同一份数据被多个组件读取时，先提升到最近的公共父组件，用 props 传递。这一步不引入任何库，却能消掉大量重复状态。

第二阶段，用 Context 处理跨层级注入。登录用户、主题、权限这类低频数据先走 Context，配合手写 reducer 管好写入路径。

第三阶段，当共享状态超过一定数量、或者需要中间件与时间旅行时，再引入 Redux 或 MobX。此时状态清单已经清楚，迁移只是换载体，而不是重新设计应用。

flowchart TD
    A[组件内部 state] --> B[提升到公共父组件]
    B --> C{跨三层以上或跨路由}
    C -- 否 --> B
    C -- 是 --> D[Context 加手写 reducer]
    D --> E{需要中间件、时间旅行或多人协作}
    E -- 否 --> D
    E -- 是 --> F[Redux 或 MobX]
    F --> G[按模块迁移写入路径]
    G --> H[删除旧同步代码]

避免“半套 Redux”

半套 Redux 指的是一种中间状态：一部分数据在 store 里，一部分在组件里，两边靠 componentWillReceiveProps 里的 setState 同步。它的危害比纯组件状态大得多，因为数据有了两个写入点，任何一次遗漏都会造成界面与数据不一致。

避免的方法是一条规则：同一份状态只有一个写入点。迁移期间，可以先让组件从 store 读，但写入仍旧走老路径；等读的路径稳定，再把写入切过去，最后删掉老代码。顺序不能反，反了就会出现两套状态互相覆盖。

旧项目的迁移步骤

第一步，列状态清单。把每个状态的名字、读取方、写入方、生命周期写在一张表里，标出重复项与派生项。这张表通常能暴露三成的问题，也能让后续的争论有据可依。

第二步，建立只读通道。引入 Provider 与选择器，让组件从新通道读数据，但写操作保持不变。此时两套数据同时存在，必须确保新通道是旧状态的投影，而不是另起一份。

第三步，逐个模块切换写入。一次只改一个模块，改完跑一遍该模块的回归用例。切换时保留旧实现一个迭代，用配置开关控制，出问题能立刻切回。

第四步，清理与加固。删除同步代码，补上 action 日志或 MobX 的严格模式，给关键选择器加单元测试。清理这一步最容易被跳过，也最容易留下隐患。

回滚策略

回滚的关键是让新旧路径可以共存。按路由或按模块做开关，出问题时切回旧实现；后端接口不做配合改动；每个迁移提交保持可独立回退。最忌讳的是在一个提交里同时改状态结构、组件结构与接口协议，一旦出问题，根本不知道该回退哪一层。

十一、五个常见反模式

把所有状态塞进全局

store 变成一个没有边界的垃圾桶：弹窗开关、临时输入、滚动位置全在里面。后果是命名冲突、清理困难、任何改动都可能影响别处。判断标准很简单：这个状态在组件卸载之后还有意义吗？没有，就不该进全局。

用 store 代替组件通信

两个兄弟组件要传一个值，正确的做法是提升到父组件；跨三层才考虑 Context 或 store。把 store 当事件总线用，会让组件之间产生隐式耦合，删掉一个组件时不知道还有谁在依赖它写入的状态。

在 reducer 里做副作用

在 reducer 里发请求、读 localStorage、调用 Math.random 或 Date.now，都会破坏纯函数的前提。表现是时间旅行失真、测试需要 mock 全局对象、同一个 action 重放得到不同结果。副作用应当放在 action creator、middleware 或 MobX 的 action 之后的 reaction 里。

派生状态重复存储

把总价、过滤后的列表、未读数量存进 state，再写一段逻辑去同步，是 bug 的高发区。派生状态应当由选择器、getter 或 computed 现算，必要时加缓存。判断标准：这个值能否由其他状态完全推导出来？能，就不要存。

把服务端数据原样塞进 store

把服务端返回的整个对象原样塞进 store，不做规范化，也不设失效时间。列表页和详情页各存一份，改了一处另一处不同步。服务端数据应当由请求层统一管理，或者在进入 store 之前完成规范化，并标记失效条件。

十二、一页纸决策清单

把上面的内容压缩成一份可以直接贴进团队文档的清单。

  1. 先列状态清单，按五类归档，标出重复项与派生项。
  2. 共享状态少于五个、层级不超过三层，不引入库。
  3. 跨层级但低频，用 Context；按关注点拆分 Provider。
  4. 服务端数据交给请求层缓存，设定失效与重试策略。
  5. 可分享的状态放进 URL，保证刷新后能还原。
  6. 表单草稿留在表单内部，提交成功后再写入全局。
  7. 需要审计、回放、多人协作，选 Redux，并坚持纯 reducer。
  8. 交互密集、状态图复杂、团队小，选 MobX，并开启严格模式。
  9. Vue 技术栈直接用 Vuex，跨框架复用不在考虑范围内。
  10. 迁移按模块进行，保持单一写入点，保留一个迭代的回滚窗口。

如果只能记住一句：状态管理的第一原则是分类，第二原则是克制。库是最后一步，不是第一步。

小结

状态管理没有唯一正确答案，只有与团队、场景匹配的答案。先把状态分成局部、共享、服务端缓存、URL、表单五类，大部分“需要全局状态”的冲动会自然消退；确实需要时，再按约束强度、调试诉求、类型支持与团队规模，在 Redux、MobX、Vuex、Context 之间选择。Redux 用样板换可回放，MobX 用自由换表达力，Vuex 与 Vue 生态绑定，Context 适合低频注入。迁移要渐进，守住单一写入点，给回滚留出窗口。把这些判断写成团队约定，比在技术群里争论哪个库更好更有价值。
