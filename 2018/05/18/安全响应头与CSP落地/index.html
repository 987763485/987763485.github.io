安全响应头与 CSP 落地

给站点加安全响应头，听起来只是改几行 Nginx 配置：加一个 Strict-Transport-Security，再补一条 Content-Security-Policy，收工。真正做过一轮上线的人都知道，难点不在写头，而在顺序、灰度和回滚：哪个头先上、每一步观察什么指标、CSP 报错时怎么判断是攻击还是误杀。本文面向已经了解 CSP 基本语法、准备在真实业务上落地的工程师，把一套可执行的安全头上线流程讲清楚；指令语义与 nonce、hash 的基础用法已在《CSP 入门》中展开，这里不再重复指令表。

为什么“加一个头”不够

安全响应头有一个容易被忽略的特点：策略由服务器下发，执行却发生在浏览器里。服务端看不到“这条策略挡住了哪个脚本”，只能通过用户的报错、空白页面和客服工单间接感知。把响应头当成一次普通的配置变更，风险正来自这里。

第一层风险是浏览器差异。同一份 Content-Security-Policy，Chrome 与 Firefox 大体按 CSP2 执行，Safari 对部分指令的支持要晚一些，IE 11 基本不执行现代 CSP，只认 X-Frame-Options 这类老机制。一份在 Chrome 里“没问题”的策略，可能在 Safari 里放行了不该放行的资源，也可能在 IE 11 里完全没有生效，让人误以为已经安全。

第二层风险是业务中断。CSP 的默认动作是“阻止”，不是“警告”。script-src 'self' 会让页面里所有内联脚本失效，包括埋点初始化、服务端渲染注入的初始状态、第三方客服挂件；style-src 收得太紧会让组件样式整体错位。这类问题往往只在特定页面、特定浏览器、特定登录状态下出现，测试用例很难覆盖全。

第三层风险来自头与头之间的相互作用。多条 CSP 响应头会同时生效，浏览器取的是它们的交集，而不是后一条覆盖前一条；CDN 可能自己追加一条策略；X-Frame-Options 与 frame-ancestors 表述不一致时，新老浏览器会得到不同结论。单看每一条都“正确”，叠在一起却可能互相拆台。

所以落地的核心不是“写一条完美的策略”，而是把它拆成若干步，每一步都有明确的观察指标和回退手段。下面先从整体顺序说起。

上线顺序：从低风险到高风险

一个实用的排序原则是：先上“只收紧边缘行为、几乎不影响主流程”的头，再上“会影响页面渲染”的头，最后上“一旦生效就很难撤回”的头。按这个原则，可以分成七个阶段。

flowchart TD
    A[盘点资源与现有响应头] --> B[阶段一 nosniff 与 Referrer-Policy]
    B --> C[阶段二 X-Frame-Options 与 frame-ancestors]
    C --> D[阶段三 HSTS 小 max-age]
    D --> E[阶段四 CSP Report-Only]
    E --> F{报告是否收敛}
    F -- 否 --> E
    F -- 是 --> G[阶段五 nonce 与 strict-dynamic 收紧]
    G --> H[阶段六 enforce 按比例灰度]
    H --> I[阶段七 HSTS 加长与 preload 评估]

第一阶段是 X-Content-Type-Options 与 Referrer-Policy。它们不阻止页面执行任何东西，最坏情况是少数静态资源因 MIME 类型不正确而加载失败，或者第三方统计拿不到完整来源路径。第二阶段是 X-Frame-Options 与 frame-ancestors，影响的是“页面能不能被别的站点嵌进 iframe”，对自有页面几乎没有影响。第三阶段是 HSTS，只对 HTTPS 站点生效，风险集中在子域与回退窗口。第四阶段开始才是 CSP，而且必须先跑 Report-Only；第五阶段在 Report-Only 里补上 nonce 与 strict-dynamic，第六阶段才是 enforce 灰度。第七阶段回到 HSTS，把 max-age 加长并评估 preload。

阶段之间不是严格的串行关系。低风险头可以一次性上线；CSP 的 Report-Only 也可以提前与 HSTS 并行，它不阻断请求，越早收集越有数据。真正需要排队的是会阻断资源的动作：CSP enforce、frame-ancestors 收紧、HSTS 的 includeSubDomains。

每个阶段都要有观察指标，而不是“发布后看有没有人反馈”。低风险头看静态资源的 4xx/5xx 比例、前端 JS 错误率、来源流量结构；框架防护看重点页面的 iframe 嵌入方是否正常；HSTS 看 HTTPS 请求占比、跳转次数、子域可用性；CSP 看报告量、被拦截资源清单、核心页面的转化与错误率。指标要在上线前就有基线，否则出了问题无法判断是不是这次变更导致的。

第一步：两个几乎零风险的头

X-Content-Type-Options

这个头只有一个有效值 nosniff，作用是让浏览器不再“猜”资源类型。没有它时，一个 Content-Type: text/plain 的文件如果内容看起来像 JavaScript，部分浏览器仍会把它当脚本执行；加上之后，浏览器会严格按响应头声明的类型处理，类型不对就直接拒绝。

它几乎是所有响应头里最安全的一个，但也有前提：站点的静态资源必须返回正确的 Content-Type。常见踩坑是静态服务器没有加载 mime.types，.js 被返回成 application/octet-stream，或者某些老接口用 text/html 返回 JSONP。上线前可以抽几个代表性资源确认：

Referrer-Policy

Referrer-Policy 控制页面在发起请求时携带多少来源信息。它的取值不是“开或关”，而是一组粒度不同的策略：no-referrer 完全不带；no-referrer-when-downgrade 是 2018 年多数浏览器的默认值，HTTPS 跳 HTTPS 带完整地址，降级到 HTTP 时不带；origin 只带协议、域名和端口；strict-origin-when-cross-origin 在同源请求带完整路径，跨域只带 origin，降级时不带；same-origin 只在同源时携带。

选择哪一个，取决于第三方依赖。统计系统、广告平台、CDN 防盗链、部分支付回调都可能读取 Referer。把策略直接收紧到 no-referrer，最常见的后果是统计后台的落地页归因全部丢失，CDN 防盗链把正常请求判为盗链。比较稳妥的做法是先盘点所有会读取来源的第三方，再从 strict-origin-when-cross-origin 开始：跨域只暴露站点级别信息，同源行为不变，多数统计仍能拿到来源域名，只是丢了具体路径。

不支持这个头的旧浏览器会退回默认策略，所以它的效果是“新浏览器更严、旧浏览器维持原状”，属于渐进式收紧，不会造成硬性中断。观察指标是统计后台的来源结构、CDN 的 403 比例，以及合作方是否反馈回调校验失败。

第二步：框架防护的新旧并存

X-Frame-Options 是防点击劫持的老方案，常用取值是 DENY 与 SAMEORIGIN，以及一直没能统一的 ALLOW-FROM。前两个语义清晰，ALLOW-FROM 则是半成品：Chrome 与 Safari 从未支持，只有 Firefox 认，跨浏览器行为并不一致。只要业务需要“被指定的少数合作方嵌入”，XFO 就表达不了。

CSP2 的 frame-ancestors 解决了这个问题，它接受一个来源列表，语义与 XFO 对应但更灵活：'none' 等价于 DENY，'self' 等价于 SAMEORIGIN，也可以列出具体域名。在同时支持两者的浏览器里，frame-ancestors 的优先级高于 XFO；在不支持 CSP 的旧浏览器里，只有 XFO 起作用。

因此并存策略很明确：两个头都发，语义保持一致；需要多域名白名单时，frame-ancestors 写完整列表，XFO 退化为 SAMEORIGIN 作为旧浏览器的保守兜底。不要出现 XFO 写 DENY、frame-ancestors 却允许某个域名的情况，那会让新老浏览器给出相反的结论，排查起来非常费劲。

后续还要上完整 CSP 时，不要把 frame-ancestors 留在独立策略里。多条 CSP 同时生效，维护两处策略迟早会改漏一处；更稳妥的做法是维护一个策略模板，按阶段往同一条策略里加指令。

验证方法：用本地 HTML 的 iframe 嵌入目标页面，分别在 Chrome、Firefox、IE 11 里打开，确认白名单域名能加载、其他域名被拒绝。点击劫持的攻击手法与更多测试细节在《点击劫持》一篇中已有展开，这里只讨论头的配置方式。

第三步：HSTS 的灰度

Strict-Transport-Security 的语义是：浏览器在收到这个头之后的一段时间内，对该域名只走 HTTPS，用户输入 http:// 或者点击明文链接时，浏览器会在本地直接把请求改写成 HTTPS，不经过网络。它只在 HTTPS 响应里生效，通过 HTTP 下发的 HSTS 头会被忽略，这也意味着“先上 HSTS 再修证书”的顺序行不通。

灰度的手段是 max-age。可以从 300 秒开始，确认没有异常后逐步加到一天、一周、一个月、一年。这样做的原因是 HSTS 有一个不可撤销的窗口：浏览器已经记住的策略，不会因为你把响应头改小或删掉而立即消失，必须等原来的 max-age 到期。初期用 300 秒，最坏情况下五分钟就能恢复；直接写一年，出事就要等一年。

第二个开关是 includeSubDomains。它会把策略应用到所有子域，包括测试环境、内部系统、第三方托管的 CNAME 记录。上线前必须把 DNS 里所有子域过一遍，确认每一个都能正常响应 HTTPS，包括内网系统与很久没人维护的域名。常见事故是主站上了 includeSubDomains，某个子域的证书过期或根本不支持 HTTPS，导致该子域对所有用户不可达，而修复只能等 max-age 到期。

第三个开关是 preload。它表示站点愿意被写进浏览器内置的 HSTS 列表，从而在用户第一次访问之前就强制 HTTPS。门槛不低：max-age 至少一年、带 includeSubDomains、响应里带 preload 指令，然后到维护列表的站点提交。它的不可逆性比前两个开关都强，从列表里移除需要漫长的版本周期。合理的节奏是：主域与所有子域稳定跑满一年 HTTPS，再考虑提交。

需要说明的是，证书申请、301 跳转与混合内容治理属于《HTTPS 迁移实践》的范围，本文只讨论 HSTS 本身的上线节奏。另外，早年固定证书公钥的 HPKP 已被主流浏览器放弃，不要在新项目启用；2018 年出现的 Expect-CT 要求浏览器校验证书透明度日志，Chrome 已支持上报模式，可写成 Expect-CT: max-age=86400, report-uri="..."，但只有 Chrome 系浏览器认，属可选加固，不能替代 HSTS。

观察指标包括：HTTPS 请求占比是否按预期上升、301 跳转次数是否异常、各子域的可用性监控、证书到期告警。HSTS 生效后，任何证书问题都会直接变成“整站打不开”，所以证书监控必须比 HSTS 更早到位。

第四步：CSP 从 Report-Only 开始

CSP 的正确起点不是 enforce，而是 Content-Security-Policy-Report-Only。这个响应头里的策略不会阻止任何资源，只会在发生违规时向 report-uri 指定的地址发送一份 JSON 报告。它让我们在不影响用户的前提下，拿到“如果现在 enforce，会挡住什么”的完整清单。

去噪与聚合

原始报告里有大量噪音：浏览器扩展注入的脚本（blocked-uri 以 chrome-extension://、moz-extension:// 开头）、运营商或安全软件注入的代码、翻译插件、书签工具、about:blank 页面，以及老页面上遗留的内联脚本。聚合时建议按“页面路径 + 指令 + blocked-uri 主机 + script-sample 指纹”分组，再按浏览器与时间段统计。

判断“能不能转 enforce”，可以用几条相对客观的标准：核心页面与长尾页面都有报告覆盖；连续一周没有出现“自家域名被拦”的记录；剩余违规可以逐条归类为攻击、扩展或已知的历史代码；报告总量稳定，没有随发布出现突增；产品与测试负责人确认关键流程在 enforce 下不受影响。任何一条不满足，就继续留在 Report-Only。

还要注意 report-uri 的可用性。报告端点挂掉不影响用户，但 enforce 之后会失去唯一的观察窗口。收集服务要独立部署、限流、带磁盘缓冲，与业务应用解耦。CSP3 草案里的 report-to 与 Reporting API 在 2018 年仍是早期实验，只有部分 Chrome 支持，主方案仍应使用 report-uri。

nonce：每个请求一把钥匙

nonce 的思路是：服务器在每次响应里生成一个随机值，同时写进 CSP 头的 script-src 'nonce-...' 和页面里每一个需要执行的内联 <script nonce="...">。浏览器只执行 nonce 匹配的脚本，攻击者注入的脚本猜不到这个值，也就无法执行。

关键是“每次响应”。nonce 一旦被复用，安全性就打折扣；如果它还出现在共享缓存里，等于把钥匙公开挂在门上。

与 CDN 缓存的冲突

nonce 方案最容易出事的地方是缓存。假设页面 HTML 被 CDN 缓存了五分钟：这五分钟内所有用户拿到的是同一份 HTML，里面的 nonce 完全相同。攻击者只要自己访问一次页面，就能读到这个 nonce，再构造带同样 nonce 的注入脚本，CSP 形同虚设。更常见的故障是另一种：CDN 缓存了 HTML，但 CSP 头由边缘节点按请求重新生成，头里的 nonce 与 HTML 里的对不上，结果是所有内联脚本被拦截，页面白屏。

结论是：生成 nonce 的层，必须是渲染 HTML 的层，并且这份 HTML 不能被共享缓存。实践中有三种处理方式：

  1. 应用层渲染并设置头，CDN 对 HTML 不缓存或按用户区分缓存，静态资源照常缓存。
  2. 页面本身是静态的，把内联脚本抽成外部文件，用 hash 或 'self' 放行，绕开 nonce。
  3. 由边缘节点同时改写 HTML 与头，保证两者一致，且该响应不进入共享缓存。

hash 与 strict-dynamic：内联脚本多时的取舍

如果站点的内联脚本不多且内容稳定，hash 是比 nonce 更省事的选择。把每段内联脚本的 SHA-256 摘要写进 script-src 'sha256-...'，浏览器计算脚本内容的摘要，匹配才执行。它不需要改模板，也不怕缓存，适合构建期就能确定内容的场景，比如一段固定的初始化代码或错误页脚本。

hash 的局限也很明显：脚本内容改一个字符，摘要就失效；页面里动态注入的初始状态（每个用户不同）根本无法预先计算；内联事件处理器与 javascript: 链接不能被 hash 覆盖。所以它通常只作为 nonce 的补充，用于少数无法注入 nonce 的静态页面。

当内联脚本很多、又不想逐个维护 hash 时，strict-dynamic 是更现实的选择。它的规则是：只要一个脚本是通过“已经被信任的脚本”动态创建的，它就自动被信任，不再看它的来源域名。配合 nonce 使用，页面只需要给入口脚本加 nonce，入口脚本再去加载的 chunk、第三方挂件、AMD 模块都会被放行。

这条策略看起来矛盾，其实是兼容性写法。支持 strict-dynamic 的浏览器（Chrome 52 起、Firefox 52 起）会忽略后面的 https: 与 'unsafe-inline'，只认 nonce 与信任传播；不支持它的旧浏览器会忽略 strict-dynamic 与 nonce，退回到 https: 白名单，至少保证页面能运行。Safari 对 strict-dynamic 的支持明显滞后，如果流量里 Safari 占比高，必须单独验证，不能只看 Chrome 的结果。

strict-dynamic 的代价是“信任会传染”。入口脚本一旦被攻破，它动态插入的任何脚本都会被放行，白名单形同虚设。因此它适合配合严格的入口治理：入口脚本数量少、来源可控、有 SRI 或版本锁定；而不是给十几个来路不明的第三方脚本都发 nonce。

另外要记住 CSP 的一个老规则：只要策略里出现了 nonce 或 hash，'unsafe-inline' 在支持 CSP2 的浏览器里就会被忽略。这不是缺陷，而是规范行为。很多“加了 nonce 结果内联脚本全挂”的案例，都是因为误以为 'unsafe-inline' 还能兜底。

第三方脚本：白名单是最难写对的部分

CSP 白名单的直觉是“把信任的域名列进去”，但域名级别的信任粒度太粗。一个 CDN 域名下可能托管着成千上万个包，一个统计服务可能提供 JSONP 接口，一个广告平台允许上传任意创意脚本。把这样的域名放进 script-src，等于信任该域名上的所有内容，包括别人上传的与重定向跳转过去的。Google 的研究团队在 2016 年系统分析过当时流行的白名单策略，结论是这类策略很难写对，这也是业界后来转向 nonce 与 strict-dynamic 的原因。

落地时先做资产盘点，按类型列出每一段第三方代码，再映射到指令：

类型 常见指令 注意点
统计与埋点 script-src、img-src、connect-src 上报接口常与脚本不同域
客服与反馈挂件 script-src、frame-src 挂件内部还会再开 iframe
支付与登录 SDK script-src、frame-src、connect-src 回调域名要单独确认
广告与联盟 script-src、img-src、frame-src 创意脚本变化频繁，最难收紧
字体与图标 font-src、style-src 图标字体常被内联样式引用

frame-src 经常被漏掉：主文档的 script-src 收得再紧，一个允许任意来源的 iframe 依然可以把不受控的页面嵌进来。connect-src 则决定了 XMLHttpRequest、fetch 与 WebSocket 能连到哪里，接口域名、埋点上报域名、WebSocket 地址都要列全，否则表现是“页面能打开，但数据加载不出来”。

更现实的做法是让 Report-Only 报告替你列清单：先在策略里写一个较宽的白名单，收集一两周，把 blocked-uri 里出现的域名按频次排序，再逐个确认是否必要。对于通过信任脚本动态加载的第三方代码，优先用 strict-dynamic 的信任传播，而不是把它的下游域名一个个加进白名单。对于必须静态引入的第三方脚本，尽量要求对方提供带版本号的固定地址，并评估 SRI 的可行性；统计类脚本因为经常更新，通常无法锁版本，这时至少要做到变更通知与上线后报告对比。

与 CDN、SPA、内联样式的冲突

多层代理与重复的头

CSP 经过 CDN 时，最容易出问题的是“头被改写”和“头被叠加”。有的 CDN 会在边缘追加自己的安全策略，浏览器收到两条 CSP 后取交集，结果可能挡住业务资源；有的 CDN 默认不透传自定义头，Report-Only 阶段的报告会莫名其妙地少。验证时不能只看源站，必须带上 CDN 域名用 curl -sI 对比：

Nginx 的 add_header 还有一个继承规则：只要 location 里出现了任何一条 add_header，父级的头就全部不再继承。很多“某个路径突然没有安全头”的问题都源于此。把公共头写进单独的 include 文件，在每个需要的 location 里显式包含，比依赖继承可靠。

SPA 的运行时注入

单页应用的入口 HTML 只有一份，但运行时还会加载路由 chunk、异步组件和样式文件。使用 nonce 时，入口脚本带 nonce，构建工具动态插入的 chunk 默认不带；2018 年的 webpack 3 提供了 __webpack_nonce__，在入口里赋值为页面上的 nonce，后续插入的脚本与样式就会自动带上。没有这个机制时，要么退回 'self' 加 strict-dynamic 的组合，要么接受 chunk 被拦截。

开发环境与生产环境的策略要分开。开发模式下构建工具常用 eval 做 source map，需要 'unsafe-eval'；把这套策略带到生产，等于给 CSP 开了个大口子。Vue 2 还有一个常被忽略的点：带编译器的完整版会在运行时把模板编译成函数，用到 new Function，在 CSP 下需要 'unsafe-eval'；使用预编译模板的 runtime-only 构建则没有这个问题。

内联样式的妥协

样式是 CSP 落地中最容易妥协的部分。style-src 默认会拦截 <style> 标签和内联 style 属性，而组件库、动画库以及 React 的 style 属性都会大量产生内联样式。hash 与 nonce 对内联 style 属性无效，能覆盖它们的只有 'unsafe-inline'。

比较务实的策略是“脚本从严、样式从宽”：script-src 用 nonce 加 strict-dynamic，style-src 保留 'unsafe-inline'，并在文档里记录这是一项已知妥协。样式注入的风险主要是界面伪装与部分信息泄露，低于脚本执行，但并不是零风险。使用 CSS-in-JS 的团队可以检查库是否支持 nonce，2018 年主流实现已能通过 __webpack_nonce__ 给动态样式加 nonce；CSP3 草案里针对样式属性的指令还不能通用。

监控与回滚：把 CSP 当发布来管

enforce 之后，CSP 才真正开始影响用户，监控要围绕“报告”和“业务指标”两条线。报告线看三个数：单位时间报告量、blocked-uri 的 Top 域名、以及新出现的域名。业务线看核心页面的 JS 错误率、白屏率、下单转化。两条线要能按版本、按灰度分组对比，否则无法区分“这次发布引入的问题”和“用户环境本来的问题”。

报告量突增通常有三种原因：新版本引入了违规代码、第三方脚本更新了加载方式，或者真的遭遇了注入攻击。区分方法是看 blocked-uri：指向自家域名或已知第三方的新地址，多半是误杀；指向陌生域名、且 script-sample 里出现可疑代码，才更像攻击。

灰度在应用层做最灵活：按用户 ID 或设备标识哈希取模，决定这个请求返回 enforce 还是 Report-Only。同一条策略只能放进一个头：放 enforce 头就执行，放 Report-Only 头就只上报。灰度时按用户决定返回哪一个：

回滚就是把开关拨回 Report-Only，保留 report-uri 继续收集，修好问题后再按同样的比例放开。回滚不需要发版，而 CSP 问题往往在发版后几分钟内暴露，等流水线跑完再回滚就晚了。HSTS 没有这种回滚能力，这也是它必须单独灰度、单独评估的原因。

一份可执行的落地清单

把前面的阶段压缩成一张表，可以直接当作上线检查单使用。每一行的验证都要在预发环境做过一遍，再到生产按比例执行。

阶段 动作 验证方法 主要风险
0 盘点响应头、静态资源类型、第三方脚本 抓包与报告 清单遗漏
1 nosniff 与 Referrer-Policy 控制台 MIME 报错、统计来源 资源类型错误、归因丢失
2 X-Frame-Options 与 frame-ancestors 多浏览器 iframe 测试 合作方嵌入失败
3 HSTS max-age=300，不带子域 HTTPS 占比、子域可用性 回退窗口
4 CSP Report-Only，先宽后紧 报告覆盖与去噪 报告量过大
5 nonce 与 strict-dynamic 进 Report-Only 内联脚本覆盖 缓存导致 nonce 失效
6 enforce 从 5% 放到 100% 错误率、转化、报告量 误杀核心流程
7 HSTS 加长到一年，评估 preload 全年 HTTPS 稳定 难以撤销
8 Expect-CT、Feature-Policy 可选 Chrome 专项验证 覆盖面有限

几个跨阶段的注意事项：所有环境共用一份策略模板，避免测试与生产“看起来一样、实际不同”；CDN 与反向代理配置纳入版本管理，响应头也是代码；每次策略变更先在 Report-Only 里跑够一个发布周期；把策略、报告端点、灰度开关写进值班手册。

小结

安全响应头的落地是一个排序问题，而不是配置问题。先上不影响业务执行的 nosniff 与 Referrer-Policy，再处理框架防护与 HSTS，最后用 CSP 收口；CSP 必须先经过 Report-Only 的收集与去噪，再用 nonce 或 hash 配合 strict-dynamic 逐步收紧。nonce 的有效性依赖“每次响应生成、不被共享缓存”，而这个环节比策略本身更容易出错。灰度与回滚要在应用层留好开关，HSTS 则要按不可逆的节奏谨慎推进。把这些步骤固化成清单，安全头才能从一次性的上线动作变成可持续的工程实践。
