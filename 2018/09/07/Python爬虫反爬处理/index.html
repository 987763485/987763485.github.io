Python 爬虫反爬处理

本文属于《Python 学习路线》第 24/29 篇
上一篇系列目录下一篇

抓取公开数据在工程上并不难，难的是在被站点拒绝时不把项目做成一场对抗。本文从 robots 协议、服务条款与数据用途讲起，说明站点通常从哪些维度识别一个客户端，再给出限速、会话、退避、动态渲染、分布式调度与监控的合规做法，最后用一个每秒 1 次请求的文档站抓取项目把要点串起来。适合已经会写 requests 与 Scrapy、准备把脚本放到服务器上长期运行的后端开发者。

一、边界先于技术

在写第一行代码之前，先回答五个问题：这个站点允许自动访问吗，数据是公开的吗，其中是否含个人信息，准备抓多少，抓来做什么、保存多久。这五个问题决定了项目能不能做，而技术选型只决定做得好不好。很多“反爬”问题的根源不在代码，而在需求本身越过了边界：想要的数据需要登录才能看，或者站点已经明确禁止自动采集，此时正确的动作是停下来，而不是升级工具。

robots 协议是第一道需要尊重的约定。它放在站点根路径下，用简单的字段声明哪些路径可以被哪些 User-Agent 访问，Disallow 表示不希望被抓取，Crawl-delay 表示建议的请求间隔。需要说明的是，在 2018 年它仍然是一份 IETF 草案，而不是正式标准，不同站点与不同解析器对通配符、优先级、Crawl-delay 的支持并不一致。Python 标准库的 urllib.robotparser 只实现了最基本的部分，遇到 * 与 $ 通配符时判断可能偏保守。保守在这里不是缺点：它倾向于少抓，而不是多抓。

robots 不是法律，它表达的是一种技术约定；服务条款才是具有约束力的文本。有的站点在条款里明确禁止“使用自动化程序批量获取内容”，有的站点只禁止对特定接口的采集，还有的站点把公开浏览与登录后使用区分开来。判断时要看具体条款，而不是只看 robots 是否放行。版权同样需要区分：事实性数据（比如公开的统计数字）与受版权保护的表达（比如整篇译文、图片、数据库编排）适用不同的规则，转载与再分发前应当确认授权。

个人信息是另一条硬边界。公开可见不等于可以随意收集，姓名、邮箱、电话、头像、发言记录组合起来就可能识别到具体个人。合规的做法是最小化：只取业务真正需要的字段，不做跨站拼接，不建立个人画像，设定保留期限并支持删除请求。若数据用途涉及对外提供或分析个人行为，应当先做评估，而不是先抓下来再说。

出现以下情况时应当停止抓取，转而申请 API 或与站点沟通：robots 对目标路径全部禁止；服务条款明确禁止自动访问；内容位于登录或付费之后；站点已经提供官方 API；页面结构频繁变化且对方明显在增加成本；以及收到了站点的停止通知。申请 API 往往比维护一套抓取系统更便宜：接口有文档、有配额、有稳定性承诺，出问题时有联系人。本文后续讨论的所有手段，都以“这次抓取是被允许的”为前提。

二、站点如何识别一个客户端

要降低请求风险，先要知道对方在看什么。站点通常没有单一的“反爬开关”，而是把多个信号汇总成一个风险评分，再决定是正常返回、插入校验、限速还是直接拒绝。

第一是 IP 维度的频率。同一个出口 IP 在短时间内的请求数、请求间隔的方差、访问路径的分布，都是明显的特征。公司出口常常是多人共享的 NAT 地址，一个人的脚本可能让整个办公室访问变慢，这一点在排期时就要考虑。

第二是请求头。User-Agent 是否为空、是否自称一个不存在的浏览器版本、Accept 与 Accept-Language 是否与 UA 矛盾、缺少浏览器通常会带的字段，都会让请求显得异常。第三是 Referer：从列表页进入详情页时带上来源是自然的，凭空直接请求详情页却不带任何来源，反而不像正常浏览。

第四是 Cookie 与会话。一个从不携带 Cookie、每次都像第一次访问的客户端，与一个保持会话、偶尔回访的客户端，行为模式完全不同。第五是请求头的顺序与大小写。不同 HTTP 库拼接头字段的顺序有固定特征，这一层很难在 requests 里精细控制，属于投入产出比很低的对抗方向。第六是 TLS 握手的特征，密码套件顺序、扩展字段的组合会形成指纹，普通 HTTP 库很难完全伪装成某个具体浏览器。最后是行为节奏：固定每 1.000 秒一次、整夜不停、严格按广度优先遍历，这些规律比任何请求头都更能说明“这是程序”。

理解这些维度的目的不是逐个伪装，而是让抓取行为变得可解释、可预测、可联系。一个自报身份、频率稳定、遵守 robots、出错会退出的爬虫，被容忍的概率远高于一个努力假装成浏览器的爬虫。

三、合规基线：限速、并发与缓存

限速是成本最低、效果最好的“反反爬”手段。它同时保护对方和自己：对方不会被突发流量打到，自己的任务也不会因为被封而前功尽弃。工程上通常分三层控制：全局每秒请求数、单个域名每秒请求数、并发连接数。前两层用令牌桶实现，第三层用信号量或连接池大小约束。

令牌桶的核心是“按固定速率补充，最多攒到容量上限”。容量决定了允许的突发量，把容量设为 1 就意味着严格串行、不允许突发。

间隔要不要随机？适度随机可以避免“整点齐射”，但不必追求像人。把间隔设为一个区间，比如 0.8 到 1.5 秒，既打散了请求，又保持整体速率可控。真正需要避免的是两种极端：固定到毫秒的机械节奏，以及为了“更像人”而引入不可解释的长随机停顿，后者会让任务时长无法预估。

失败退避也属于基线的一部分。任何一次失败都不应该立刻重试，而应该等待一段时间，并且等待时间随失败次数增长。离线缓存则是另一个容易被忽略的手段：对支持条件请求的资源，带上 If-None-Match 与 If-Modified-Since，服务端返回 304 时既省流量也省解析。把“抓取”做成“同步”，请求量往往能降一个数量级。

限速参数不该凭感觉拍定。先看 robots 里的 Crawl-delay，没有就参考站点的 API 配额或公开说明；都没有时，从每秒 1 次、单域名并发 1 开始，观察响应时间与错误率再决定是否放宽。运行中要记录实际速率，因为令牌桶只能约束发起请求的节奏，重试、重定向与静态资源请求都会额外增加真实请求数。一个常见的偏差是：配置里写着 1 QPS，日志里却是 3 QPS，多出来的部分来自自动重试和页面内嵌资源。把“实际发出的请求数”作为监控指标，而不是把配置值当作事实，限速才算真正生效。并发控制同样要有明确上限，用信号量把同时在途的请求数压住，比单纯调低间隔更能避免瞬时打满对方连接。

四、请求头与会话

请求头的基本原则是“合理且一致”，而不是“越像浏览器越好”。User-Agent 应当说明自己是谁，并留下联系方式，例如 DocCrawler/1.0 (+https://example.com/bot; contact@example.com)。这样站点在日志里能认出你，需要限流或沟通时也能找到人。如果站点只对浏览器 UA 返回正常内容，先确认条款是否允许自动访问；允许的话，可以在自报身份的同时补充一个常见的浏览器标识，但不要编造一个不存在的版本号，比如声称自己是某个从未发布的 Chrome 大版本，这种矛盾本身就是异常信号。

Accept 与 Accept-Language 按实际需要设置即可。抓 HTML 时声明接受 HTML，抓 JSON 接口时声明接受 JSON，比一律照抄浏览器头更诚实，也更利于服务端返回正确的内容协商结果。Referer 只在有真实来源时携带：从列表页解析出的详情链接，把列表页作为来源是合理的；凭空构造一个来源则没有必要。

会话复用是 requests 里最实用的功能之一。requests.Session 会保持 Cookie、复用底层连接，既减少了 TLS 握手开销，也让站点看到一个连续的会话，而不是成百上千个孤立的连接。

需要提醒的是，会话复用不等于可以无限提速。一个 Session 加一个令牌桶，通常比十个 Session 各自狂奔更稳。至于请求头的排列顺序，requests 基于 urllib3 的拼接顺序与浏览器不同，想在这一层做到完全一致需要替换底层实现，收益很低，不建议投入。

五、代理的正当使用

代理本身是中性工具，问题在于用它做什么。正当的用法有三类：公司有固定出口，所有对外请求统一走这个出口，便于审计与白名单报备；需要验证自家服务在不同地域的返回，用对应地区的出口做检查；购买了合规代理服务，合同里明确了使用范围与频率限制。这三种场景的共同点是“有明确目的、有据可查”，而不是“为了不被发现”。

代理不是隐身。站点仍然能看到请求头、Cookie、行为节奏与 TLS 特征，换一个出口只改变了来源 IP 这一个维度。更常见的情况是：换了代理之后请求量成倍增加，反而更快触发风控。因此使用代理时仍要按出口分别限速，记录每个出口的请求量与错误率，出现大面积拒绝时先停下来看日志，而不是继续换出口。

还有一条实践原则：不要用代理轮换去突破站点明确设定的配额。配额是站点的规则，靠轮换出口绕开配额，本质上和未经授权进入他人账号没有区别。如果业务确实需要更大的量，正确路径是申请 API、购买数据授权或与站点协商，而不是把技术手段堆上去。

六、403、429 与 503 的处理

这三个状态码的含义不同，处理方式也应当不同。403 表示服务器理解请求但拒绝执行，原因可能是权限、地域限制、规则命中，也可能是站点整体封禁了这类客户端。429 表示请求过多，通常附带 Retry-After 告诉你要等多久。503 表示服务暂时不可用，可能是过载或维护，也可能带 Retry-After。把三者混为一谈、一律“重试三次”，是最常见的错误。

对 429 与 503，应当优先尊重 Retry-After。它的值可能是秒数，也可能是 HTTP 日期，两种都要解析。没有这个头时，使用带抖动的指数退避：第 n 次失败等待 base * 2^n，再乘以 0.5 到 1 之间的随机系数，并设置上限，避免等待时间无限增长。对 403，不要重试，应该停止当前域名的任务并人工检查：是 UA 被拉黑、是路径超出许可，还是整个站点不再欢迎自动访问。对 5xx，可以重试，但要有次数上限，超过上限转入死信队列并告警。

除了单请求级别的重试，还需要任务级别的熔断。连续若干次 403，或某个域名在十分钟内的失败率超过阈值，就暂停该域名的所有任务并告警。这时加代理、换 UA、提高并发都是错误方向，正确动作是看日志、确认规则、必要时联系站点。熔断之后不要立刻恢复，先做一次极低频的探测请求，确认返回正常再逐步放量；如果探测仍然失败，就保持暂停，把资源和时间用在其他数据源上。很多项目真正的问题不是“抓不到”，而是“抓不到还不肯停”，结果把对方和自己都拖垮。

七、动态页面：先找接口，再考虑渲染

遇到“源码里没有数据”的页面，第一反应不应该是上浏览器。大多数动态页面是前端调用了一个返回 JSON 的接口，接口地址、参数与分页规律在浏览器开发者工具的 Network 面板里一目了然。直接请求接口，成本是渲染方案的几十分之一，速度也快得多。只有在接口被签名、加密或根本不存在（比如内容由服务端模板加客户端脚本共同生成）时，才考虑浏览器渲染。

Selenium 3 是当时的常用选择：它能驱动真实的 Chrome 或 Firefox，执行页面脚本，等待元素出现。代价同样明显：每个实例占用几百 MB 内存，启动需要数秒，选择器随页面改版而失效，无头模式与有头模式在少数场景下行为不同。在决定使用它之前，先用 Network 面板确认接口是否真的不可直接调用，这一步通常能省掉整个渲染层。它适合低频、必须执行脚本、且已获得授权的场景，比如抓取自家后台的报表，或者对公开页面做少量抽样核对，不适合作为高频采集的主力。

使用时的关键点是等待策略。不要用 time.sleep 猜加载时间，而要用显式等待，等某个具体元素出现或某个条件成立；同时设置页面加载超时与脚本超时，避免一个页面卡死整个任务；实例一定要在 finally 里退出，否则残留的浏览器进程会迅速吃光内存。

无头模式在 Chrome 59 之后可用，加 --headless 即可，但要注意无头环境的字体、时区、窗口尺寸与有头不同，截图与布局相关的结果可能有差异。另一个常被忽略的成本是驱动版本：chromedriver 必须与浏览器大版本匹配，服务器上升级浏览器时忘了升级驱动，任务会整体失败。

八、登录态：只在本人授权后使用

有些数据只有登录后才能看到，比如自己账号下的订单、报表、学习记录。这类场景的合规做法是：由数据归属人本人在浏览器里登录，然后从开发者工具的 Application 面板导出 Cookie，交给脚本在本人授权范围内使用。脚本不模拟登录表单，不保存账号密码，不代替他人登录。

导出的 Cookie 有时效，也可能与 UA、IP 绑定。使用时要保持与导出时一致的 UA，会话过期后由本人重新导出，而不是让脚本自动续期。Cookie 属于凭据，应当加密存放、限制文件权限、不写入日志、不入库明文，任务结束后及时删除。多账号轮换以规避配额，或者用他人 Cookie 读取其数据，都不属于本文讨论的范围。

九、分布式抓取：队列、去重与调度

单机脚本跑到几千个页面就会遇到瓶颈：内存里存不下待抓队列，进程重启后状态全丢，多个 worker 之间互相重复抓取。这时需要把“抓什么”和“怎么抓”分开：用一个共享队列保存待抓 URL，用一组 worker 消费，用一个共享结构做去重，用统一的限速器控制每个域名的速率。

队列可以直接用 Redis 的列表，也可以用 RabbitMQ 这类消息队列。前者简单，后者有确认、重投与死信机制，适合任务量大、需要可靠性的场景。去重有两个层次：精确去重用一个 Set 保存已经见过的 URL，内存占用随规模线性增长；规模再大时用布隆过滤器，用少量误判换取固定的内存占用。布隆过滤器的误判只会把“没抓过的”误判为“抓过”，造成漏抓，不会重复抓，这个方向的误差是可以接受的。

调度上，按域名分队列是最实用的做法：每个域名一个队列、一个限速器，worker 从多个队列轮询取任务，某个域名被限流时不影响其他域名。失败任务进入重试队列，带上重试次数与下次执行时间，超过上限转入死信队列。所有 worker 共享同一套限速状态，否则单机限速在分布式下会失效。

共享限速在实现上通常是把令牌桶搬到一个中心位置：用 Redis 保存每个域名的令牌数与上次补充时间，worker 取任务前先执行一段脚本扣减令牌，扣不到就把任务放回队列并延后。这里要小心并发下的原子性，读取、计算、写回必须在一个原子操作里完成，否则多个 worker 同时读到“还有令牌”，实际发出的请求会成倍超出限额。另一个容易被忽略的点是重定向：一次任务可能产生多次请求，限速应当按最终发出的请求计，而不是按任务计。分布式系统里“看起来是 1 QPS、实际是 5 QPS”的偏差，多半来自这两处。

Scrapy 已经把调度、去重、重试、并发控制做好了，适合中等规模的整站抓取。需要调整的主要是并发与延迟相关的配置，以及针对特定站点的中间件。

AUTOTHROTTLE 会根据响应延迟自动调整延迟，遇到变慢就主动降速，比固定延迟更适应真实网络。RETRY_HTTP_CODES 里保留 429 是合理的，但中间件默认的固定退避不够，遇到带 Retry-After 的响应最好在自定义中间件里单独处理。管道适合做校验、去重与入库，下面的例子用 SQLite 做持久化去重，保证进程重启后不会重复写入。

十、数据质量：编码、边界与幂等

抓取系统的价值最终体现在数据质量上，而数据问题往往比被封更隐蔽。编码是第一关：优先使用响应头里的 charset，其次看页面 meta 声明，最后才用猜测。全站统一用 UTF-8 时问题不大，遇到 GBK 与 UTF-8 混用的站点，猜测错误会导致乱码，而乱码会让基于文本的去重与比对全部失效。

分页边界是第二关。常见的终止条件有四类：返回空列表、返回与上一页完全相同的内容、超过声明的总页数、下一页链接消失。只看“有没有下一页按钮”并不可靠，有的站点在最后一页仍然渲染按钮。更稳的做法是记录本页新增条数，连续两页新增为零就停止，同时设置最大页数作为兜底。

增量抓取要依赖可比较的信号。最可靠的是条件请求：保存 ETag 与 Last-Modified，下次带上 If-None-Match 与 If-Modified-Since，304 就跳过。没有这两个头时，用发布时间或列表页的顺序做水位线，只抓水位线之后的内容。URL 规范化同样重要：去掉无意义的查询参数、统一协议与大小写、跟随重定向到最终地址，否则同一个页面会被当成多个页面重复抓取。

断点续爬的关键是“状态与数据一起提交”。每处理完一个页面，就在同一个事务里更新进度表并写入数据；重启时从进度表恢复，而不是从头再来。写入使用业务主键做 upsert，保证同一条记录重复处理不会产生副本。幂等做得好，重试与补抓就不再是风险，而只是多花一点时间。

十一、监控与合规审计

长期运行的抓取任务需要一套最小监控：每分钟的请求数、状态码分布、403 与 429 的比例、解析失败率、新增条目数、平均耗时。这些指标不需要复杂的系统，写入日志后用一个脚本聚合，或者直接打到现有的监控平台即可。关键是指标要能回答“现在是否应该停”。

停手规则应当提前写死，而不是临场判断。比如：十分钟内 403 比例超过 5%，或连续 20 次请求返回 403，或 429 次数超过请求数的 10%，就自动暂停并告警。大面积 403 几乎总是意味着规则变化、路径越界或对方明确拒绝，此时增加代理、轮换 UA、提高并发都只会让情况更糟。正确的顺序是：停、看日志、确认 robots 与条款、联系站点、调整策略，确认无误会再恢复。

日志同时是合规审计的依据。每条记录至少包含时间、URL、状态码、耗时、出口 IP、重试次数与任务 ID，保留期限按公司制度与法律要求设定。审计要能回答：抓了哪些路径、抓了多少、为什么抓、数据存在哪里、谁有权访问。收到删除请求或站点通知时，能够快速定位并清理，而不是在一堆无结构的日志里翻找。

十二、一个小项目：每秒 1 次抓取公开文档

把前面的要点落到一个具体项目上：抓取 example.com 下 /docs/ 前缀的公开文档，限速每秒 1 次，带本地缓存，支持增量更新与断点续爬。项目不大，但包含了 robots 检查、限速、条件请求、解析、去重与状态持久化。

小结

反爬处理的核心不是伪装得更像浏览器，而是让抓取行为变得合规、可预测、可联系。动手前先确认 robots、服务条款、版权与个人信息边界，越界时申请 API 比升级工具更划算。工程上把限速、会话复用、条件缓存、指数退避与熔断做成默认配置，把 403 当作停止信号而不是重试信号。动态页面优先找接口，确需渲染时用显式等待并控制实例数量；登录态只在本人授权范围内使用。规模变大后，用队列、去重与共享限速把单机脚本改造成可恢复的分布式任务，同时用指标与日志守住“该停就停”的底线。
