requests 与 aiohttp 网络请求

本文属于《Python 学习路线》第 17/29 篇
上一篇系列目录下一篇

本文讨论 Python 里最常用的两种 HTTP 客户端：同步的 requests 与异步的 aiohttp。重点不在 API 清单，而在把请求发得稳、发得快所需要的几件事：连接复用、超时与重试、并发上限、流式读写。读完之后，你应该能为一个具体任务挑出合适的客户端，并知道哪些写法在线上一定会出问题。文中示例基于 Python 3.7、requests 2.19 与 aiohttp 3.3。

先想清楚：同步还是异步

在动手写代码之前，先要回答一个问题：这次任务的瓶颈在哪里。requests 是同步阻塞的，调用一次之后，线程就停在那里等 DNS 解析、等 TCP 握手、等 TLS 协商、等服务器返回第一个字节；代码读起来像顺序执行的脚本，异常栈清晰，断点调试也方便。aiohttp 走的是另一条路：请求发出后协程被挂起，事件循环转去处理别的连接，数据到了再唤醒。单线程就能同时挂住几千个「在等响应」的请求，代价是整条调用链都必须是 async 函数，任何一处同步阻塞都会把整个循环拖住。

判断标准不是「异步更先进」，而是等待时间占比。如果一个脚本一次只发几个请求，或者真正耗时的是解析 HTML、写数据库、算指标，那么换成异步几乎没有收益，反而让代码复杂度翻倍。反过来，如果一次要抓几百上千个 URL、每个响应体只有几十 KB、时间几乎全花在网络往返上，异步能把总耗时压到接近「最慢的那一个请求」。还有一个现实约束是生态：很多库只有同步接口，在协程里调用它们等于给事件循环踩刹车，这时用 loop.run_in_executor 丢进线程池，或者干脆整条链路保持同步，都比硬套 async 更划算。

requests：最小可用集

requests 的 API 设计目标是「给人用」。最常见的四件事是带查询参数、提交表单、提交 JSON、加请求头，每一种都有对应的关键字参数，不需要自己拼 URL 或手动序列化。

POST 的三种请求体要分清：data 传字典时是 application/x-www-form-urlencoded；json 传字典时会序列化并自动设置 Content-Type: application/json；传文件则用 files，走 multipart/form-data。

超时是最容易被忽略的参数。不传 timeout 时，requests 会一直等下去，一个卡住的连接就能把整个脚本挂死。传一个数字时它同时作用于连接和读取，传元组则可以分开设置。要注意语义：这里的读取超时指「两次收到数据之间的最大间隔」，而不是整个请求的总时长。所以一个持续慢慢吐字节的响应，总耗时可能远超设定值也不会超时，需要总时长兜底就得自己在外面计时，或者用信号量配合线程来中断。

编码问题也常在这一层出现。resp.text 的编码优先取响应头 Content-Type 里的 charset，缺失时按老规范退化成 ISO-8859-1，中文页面于是变成乱码。可靠的做法是先看字节：resp.content 是原始字节，需要文本时显式写 resp.encoding = 'utf-8'，或者用 resp.apparent_encoding 让 chardet 猜一个编码再赋值。猜编码并不总是准，能确定就不要猜。

Session：复用连接与状态

每次调用 requests.get，内部都会临时建一个 Session，用完销毁，连接不会复用。下一次请求还要重新解析 DNS、重新三次握手、重新协商 TLS。单次请求无所谓，放在循环里就是成倍的握手开销。Session 把这件事变成显式的：它持有一个 urllib3 连接池，按 host 缓存连接，同时保存 Cookie、默认请求头和认证信息。

连接池有两个容易踩的默认值：pool_connections 与 pool_maxsize 默认都是 10。单线程循环够用，一旦上了多线程，同时并发的请求数超过 10，urllib3 就会打印 Connection pool is full, discarding connection，多出来的连接用完即弃，复用等于失效。多线程场景应当把 pool_maxsize 调到并发数以上，通过 HTTPAdapter 挂到 Session 上。

Cookie 同样是 Session 级别的：服务器下发的 Set-Cookie 会被 http.cookiejar 收下，后续请求自动带上。这既是便利也是坑。同一 Session 混用多个账号，Cookie 会互相覆盖；长期运行的服务如果 Session 生命周期过长，Cookie 过期后也不会自动刷新，需要重新登录再把新的 Cookie 灌回去。

超时、异常与重试

requests 的异常都继承自 RequestException，实际需要区分的是三类：连接阶段的 ConnectTimeout、读取阶段的 ReadTimeout，以及既非超时也非状态码的 ConnectionError，DNS 失败、连接被重置、TLS 握手失败都归在最后一类。状态码异常不会自动抛出，必须显式调用 raise_for_status()，否则 404 和 500 会被当成正常响应继续往下走，错误在几十行之后才暴露，排查成本高得多。

重试要分两层看。第一层是「该不该重试」：只有幂等请求才适合自动重试，GET、HEAD、PUT、DELETE 重复执行结果一致，POST 重试则可能产生两笔订单、两条记录。第二层是「怎么重试」：requests 本身没有重试机制，要靠 urllib3 的 Retry 挂在 HTTPAdapter 上。

total 是所有类别重试次数的上限，backoff_factor 控制指数退避，status_forcelist 不写就只对连接类错误重试。还有一点常被忽视：重试会放大流量。3 次重试意味着最坏情况下请求量是 4 倍，如果对端此时已经过载，重试只会让它更糟。所以次数要少、退避要有，并且要配合整体失败率监控，不能把重试当成万能药。

代理与证书

公司网络里出网通常要走代理，requests 用 proxies 字典指定，按协议区分。注意 HTTPS 请求的代理地址 scheme 一般仍写 http://：客户端先向代理发 CONNECT 建立隧道，再在隧道里跑 TLS，代理自身并不需要是 HTTPS 服务。

证书这块，verify 可以传 CA 包路径，也可以传目录。企业内网普遍用自建 CA 给内部服务签证书，正确做法是把公司根证书装进系统信任库，或者显式传给 verify；也可以通过环境变量 REQUESTS_CA_BUNDLE 统一指定，避免每个调用点都写一遍。

verify=False 要明确说一句：不推荐，生产环境应当禁止。它关掉的不只是「证书是不是权威机构签的」，而是整个身份校验。中间人只要处在网络路径上，就能用任意自签证书冒充目标站点，你发出去的 Token、Cookie、表单内容在它面前等于明文。开发期图省事关掉，这个开关往往会跟着代码一起上线。真遇到自签证书，装 CA 才是唯一正确的解法。

aiohttp：把请求交给事件循环

aiohttp 的核心对象是 ClientSession，它同时承担连接池、Cookie 存储和默认配置三个角色，所以一个应用通常只建一个，在多个协程之间共享。请求用 async with 管理，响应体必须在退出上下文之前读完，否则连接无法归还。

ClientTimeout 的 total 是整个请求的上限，和 requests 的读取超时语义不同，迁移代码时最容易在这里搞混：原来写 timeout=10 是「每次读最多等 10 秒」，现在写 total=10 是「从发出到读完最多 10 秒」。asyncio.gather 一次性把所有协程排进事件循环，return_exceptions=True 让单个失败不影响其他任务，代价是失败被包在结果列表里，需要自己筛出来统计。Python 3.7 起可以直接用 asyncio.run 作为入口，不必再手写 run_until_complete 再关闭循环。

文本解码是另一个需要留心的地方。resp.text() 按响应头里的 charset 解码，缺省时按 UTF-8 处理，遇到只发 GBK 又不写 charset 的老站点会直接抛 UnicodeDecodeError。这类情况先 await resp.read() 拿到字节，再用确定的编码自行解码，比反复换库更省事。状态码检查同理，aiohttp 的 raise_for_status() 抛的是 ClientResponseError，异常对象上带着状态码与请求信息，写日志时一并记下来，比只记一句「请求失败」有用得多。

并发控制：信号量与连接池

gather 不加限制地扔一万个请求，会试着同时打开上万个连接：本地文件描述符先耗尽，出口带宽被占满，目标站点的连接数被打爆，结果是一大片超时和 5xx。限流有两个层次，通常要一起用。

第一层是业务层的信号量，控制「同时在飞的请求数」。asyncio.Semaphore 在协程里 async with 一下即可，超出配额的任务原地等待，不会占用连接。

第二层是连接池。TCPConnector 的 limit 限制总连接数，limit_per_host 限制单个 host 的连接数，ttl_dns_cache 可以缓存 DNS 结果、减少解析次数。两者作用不同：信号量管的是「允许多少个任务同时干活」，连接池管的是「底层允许多少条 TCP 连接」，后者对 keep-alive 复用更敏感。

限到多少合适，没有通用答案，但有几个约束可以参考：本地 ulimit -n 决定文件描述符上限，出口带宽除以平均响应体大小给出理论上限，目标站点的承载能力才是真正的天花板。对第三方站点，单 host 并发控制在个位数到十几，配合固定间隔，比「跑满」更可持续。

流式与大文件

下载大文件时，requests 默认会把响应体全部读进内存再返回，几百 MB 的文件足以把进程撑爆。加上 stream=True 后，响应体不会立即下载，而是通过 iter_content 按块读取，边读边写盘。

chunk_size 太小会让系统调用次数暴涨，太大则失去流式的意义，64 KB 到 1 MB 之间比较常见。如果服务端支持 Range，还可以用 headers={'Range': 'bytes=%d-' % offset} 做断点续传，起始位置由本地已下载的字节数决定。

aiohttp 的写法对应 iter_chunked，区别是读取本身也是协程。但写文件仍是同步阻塞操作，小文件无所谓，大文件在事件循环里写会阻塞其他协程，稳妥的做法是交给 run_in_executor。

性能对比要怎么做

「aiohttp 比 requests 快十倍」这类结论，多数来自不公平的对比：一边串行发 100 个请求，一边并发发 100 个，比的其实是并发度而不是库。要得到有意义的数据，至少控制住四个变量。

同一目标：两边访问同一个地址、同一份响应体，最好是自己搭的测试服务，避免对方限流干扰。同一并发：requests 侧用线程池开到 N，aiohttp 侧用信号量也限到 N，这样比的才是「相同并发下谁的开销更小」。预热与采样：第一次请求包含 DNS 与 TLS 开销，至少跑一轮预热，正式测量重复三次取中位数。指标成对看：平均吞吐（成功请求数除以墙钟时间）、错误率、延迟分位数一起报，只报吞吐不看错误率等于自欺欺人。

最后要接受一个事实：异步的收益与单请求延迟强相关。目标是同城内网、往返只有几毫秒时，事件循环的调度开销占比上升，两者差距会明显收窄；跨公网、往返几十上百毫秒时，异步才能把等待时间叠起来。所以选型要看真实链路，不要看别处的数字。

几个反复出现的坑

第一个，在 async def 里调用 requests。看上去只是「慢一点」，实际是把整个事件循环卡住：那几秒里所有其他协程都停摆，超时计时也跟着漂移。要么用 aiohttp 重写，要么 await loop.run_in_executor(None, requests.get, url) 丢进线程池。

第二个，ClientSession 跨事件循环复用。Session 和连接池都绑定在创建它的事件循环上，asyncio.run 每次都会新建循环，把上一个循环里的 Session 带过去，轻则报 attached to a different loop，重则连接状态错乱。规则很简单：Session 在协程内部创建，随循环一起销毁。

第三个，忘记关闭。requests 的 Session 不关会漏连接，aiohttp 不关会在退出时打印 Unclosed client session 与 Unclosed connector。这不只是警告，背后是没归还的连接和没释放的 socket，长时间运行的服务迟早会耗光描述符。

第四个，重试放大流量。重试次数、并发数、任务量三者相乘才是真实请求量。把 total 设成 5、并发 200，对端一封 IP，整批任务全挂。

第五个，gather 不带 return_exceptions。任何一个协程抛异常，gather 立即向上抛，其余任务虽然还在跑，结果却拿不到了。批量任务应当显式收集异常，最后统一统计失败原因。

小结

requests 与 aiohttp 不是替代关系，而是分工：一次只发少量请求、或者逻辑主体不在等网络上时，同步写法更简单也更可靠；面对成百上千个 URL 的 I/O 密集任务，异步能把等待叠起来。无论选哪个，四件事都要做对：用 Session 复用连接、连接与读取超时分开设置、只对幂等请求做有限重试、用信号量与连接池给并发封顶。遇到证书问题装 CA，而不是关掉校验。做完这些再去谈性能，测出来的数字才有意义。
