Go 编码规范总结

本文属于《Go 语言与工程》第 16/78 篇
上一篇系列目录下一篇

团队里关于 Go 代码风格的争论，最后往往落成两种结局：要么谁写谁有理，要么照搬一份别人家的规范文档，然后没有人执行。本文试着把“编码规范”这件事拆开，分清哪些可以交给工具自动完成，哪些必须写进团队约定，再逐项讲命名、包结构、错误处理、接口、并发、注释、测试与工具链的具体做法。适合已经能写 Go 服务、准备在团队内推行统一风格的读者。读完之后，你应该能判断一条规则该不该写、该写在哪一层，并拿到一份可以直接贴到评审模板里的检查清单。

规范的三个层次

Go 的规范之所以比很多语言好推行，是因为最底下那一层根本不给人选择的机会。gofmt 没有配置项，缩进、括号位置、对齐方式全部由它决定，任何人跑一遍结果都一样。这意味着“用 tab 还是空格”“左括号放哪”这类问题不该进入讨论，更不该写进文档，它属于工具层。

中间一层是官方文档。《Effective Go》讲的是语言层面的习惯：命名怎么取、错误怎么返回、接口怎么设计；Go Code Review Comments 则是一份更短的条目清单，很多团队的规范其实就是它的翻译版。这一层的特点是“有官方依据但无法完全自动化”，适合作为团队规范的底稿。

最上面一层才是团队自己的约定：目录怎么分、日志字段叫什么、注释用中文还是英文、pkg/ 要不要建。这一层没有对错，只有一致。判断一条规则该放哪一层，有个很实用的标准：能不能被工具稳定判定。能判定的写成脚本塞进 CI，不能判定的才写进文档、靠评审把关。把格式写进规范是浪费人力，把错误包装交给 linter 又做不到。

命名：短、准、不重复

包名要短，全小写，不用下划线，不用复数，也不要重复调用方已经知道的信息。一个 user 包里的类型叫 user.Service，读起来是 user.Service，而不是 user.UserService，后者等于把包名说了两遍。反例通常长这样：

缩写词的处理是最容易吵架的一处。约定很简单：URL、ID、HTTP、API 这类缩写要么全大写、要么全小写，不要写成 Url、Id、Http。所以是 userID 而不是 userId，是 HTTPServer 而不是 HttpServer；但包名一律小写，于是有 url.Parse、http.Get。首字母大小写同时决定可见性：大写导出，小写包内可见。导出意味着对外承诺，改了就是破坏兼容，所以新写的标识符先小写，等真有外部调用方再考虑导出。

名字长度与作用域成正比：三层循环里 i、v 够了；包级变量、字段与导出函数必须写清楚，读者看不到它的定义处。测试文件的命名是硬规则：xxx_test.go 与 xxx.go 同目录，测试函数 TestXxx，基准 BenchmarkXxx，示例 ExampleXxx。测试放在同一个包里可以访问未导出成员，放在 xxx_test 包里则强制只走公开 API，两者按需选择，不要混着用。

包与目录的分层

最常见的错误是按类型分层：models/ 放结构体，handlers/ 放 HTTP 处理，services/ 放业务逻辑，utils/ 什么都放。这种分法在项目小的时候很整齐，一旦业务变复杂就会撞墙：models 想调用 services 里的校验，services 又要引用 models，Go 的导入图不允许成环，编译器会直接拒绝。于是只能在中间再塞一个包，依赖关系越绕越乱。

正确的切法按职责：user、order、billing，每个包内部自带自己的模型、存储与业务规则，包与包之间通过少量导出类型交互。判断一个包是否切得合理，看它的名字能不能用一句话说清职责；如果只能叫 common、util、base，说明它没有职责。

internal/ 是编译器强制的边界，不是命名习惯。放在 internal/ 下的包，只能被以该目录的父目录为根的子树导入，外部模块即使拿到路径也编译不过。把“不打算给别人用”的实现放进去，比写一百行注释声明“这是内部包”有效得多。

cmd/ 放 main 包，一个二进制一个子目录，例如 cmd/api/main.go、cmd/worker/main.go，main 函数只做装配和启动，不写业务。pkg/ 则一直有争议：官方仓库里并没有这个目录，支持者认为它是“可以对外复用”的信号，反对者认为它只是把一层目录当成了形容词。两种做法都有人用，关键是团队内统一，别一半项目有、一半没有。

错误处理：值、包装与只处理一次

Go 的错误是值，不是异常。errors.New 造的是可比较的哨兵错误，fmt.Errorf 造的是带上下文的信息串：前者供调用方判断分支，后者给人看。这个版本还没有 %w，fmt.Errorf 无法保留原始错误，想在补充上下文的同时保留原因链，只能用 github.com/pkg/errors 的 Wrap，再用 Cause 取回最底层的原因。

由此引出第一条规则：错误只处理一次。要么记录日志并吞掉，要么包装后向上返回，不要既 log 又 return err。同一个错误在每一层都打一遍，日志里就会出现三份堆栈，排查时反而分不清哪一层是根因。

第二条：不要用 _ 吞掉错误。defer f.Close() 是最常见的漏网之鱼，写文件尤其危险，写入失败往往在 Close 时才暴露。至少写成 defer func() { if err := f.Close(); err != nil { log.Printf(...) } }()。

第三条：不要靠字符串比较判断错误，换一个数据库驱动后必然失效，要用哨兵值或自定义类型加断言。第四条：错误信息小写开头、结尾不加标点，因为错误通常会被拼接进更长的句子里，errors.Wrap(err, "load user") 读出来是 load user: connection refused。至于错误码如何分段、如何与 HTTP 状态码映射，那是接口契约层面的事，本文只谈编码风格里的惯例。

接口：小、在使用方定义

标准库把答案写在 io 包里：Reader 与 Writer 各只有一个方法，实现了 Read 就自动是 Reader，io.Copy 才能同时接受文件、连接、缓冲区与压缩流。接口越小，能被满足的场景越多，组合起来的威力也越大。

第三个原则是避免过早抽象。一个接口如果只有一个实现、而且只被调用一次，它没有带来任何收益，只是多了一次动态派发和一层跳转。先把具体类型写出来，等第二个实现真的出现，或者等测试确实需要替换时，再把接口抽出来，位置放在调用方。

并发：谁启动谁负责

goroutine 很便宜，便宜到容易被随手启动，然后忘掉。规范里最该强调的一句是：谁启动，谁负责它的退出。下面这段代码在很多项目里都能找到，它没有退出路径，进程结束前一直在跑，测试里更是会跨用例泄漏：

context.Context 用来传递取消信号、超时和请求范围内的少量元数据，约定放在函数的第一个参数，命名为 ctx。不要把它存进结构体，那会让生命周期变得含糊；也不要用它传业务参数，那些应该走显式参数。下游调用要一层层把 ctx 传下去，http.Request 也要带上，这个版本用 req.WithContext(ctx)。

不要用 time.Sleep 做同步。go f(); time.Sleep(time.Second); g() 在开发机上也许能跑，一到负载高的环境就会随机失败，因为调度器不保证一秒内 f 一定执行完。要等就用 sync.WaitGroup 或 channel，要限时就用 context.WithTimeout。

锁的粒度按数据的不变量定，不按代码块定：锁保护哪些字段必须一起变，临界区就覆盖这些字段的读写。临界区里不要做网络 IO、不要调用外部服务、不要往 channel 发送数据，否则一个慢调用会把所有等锁的 goroutine 一起拖住。读写分明时用 sync.RWMutex，但不要为了省一把锁而引入两把互相嵌套的锁，那是在给自己造死锁。

注释与文档

注释的第一用途是给读代码的人补上代码表达不了的信息，第二用途是生成文档。包注释写在 package 语句上方，以 Package 包名 开头，说明这个包负责什么、不负责什么。导出标识符的注释以标识符本身开头，这样 godoc 生成的列表才读得通：

TODO 要写成可追踪的形式，带上责任人和触发条件，例如 // TODO(lisi): 等订单服务迁移完成后删除这段兼容代码。只写 // TODO 的注释，半年后没人知道该不该删。

最重要的一条是解释“为什么”，而不是复述“是什么”。// i 加 1 这种注释没有任何价值，// 这里重试三次是因为对端限流窗口是 1 秒 才有价值，因为它记录了当时的约束，而约束会变，后来的人需要知道为什么当初这么写。

测试：表驱动与可读性

Go 的测试风格高度统一，核心是表驱动加子测试。把输入、期望、是否报错放进一个切片，用 t.Run 为每个用例起名字，失败时能直接定位是哪一行数据：

辅助函数要调用 t.Helper()，否则失败行号会指向辅助函数内部，排查时白跑一趟。

测试可读性比覆盖率更重要。一个测试只验证一件事，名字说清场景，造数据的部分抽成辅助函数。测试本身就是最准确的文档，新人读测试理解行为，比读实现更快。

异步逻辑的测试不要用 time.Sleep 等待。要么用 channel 让被测代码在完成时通知，要么用带超时的轮询，超时设得比预期长一个数量级，失败时打印当前状态。睡眠一秒的测试本地跑一百次都过，CI 上偶发失败，最后被 -count=1 掩盖。

工具链与 CI

规范落地靠的不是文档而是流水线。常用工具不多，分工却清晰：

gofmt -l . 列出所有未格式化的文件，CI 里只要输出非空就判定失败；本地开发用 gofmt -w . 直接改写，或者用 goimports 顺便整理 import 分组。go vet ./... 检查那些能编译但几乎肯定是 bug 的写法，比如 Printf 格式串与参数不匹配、锁被值拷贝、结构体标签写错。golint ./... 给风格建议，会有误报，适合提示而不适合阻塞合并。staticcheck ./... 做更深层的静态分析，能找到无效分支、永不返回的错误检查，误报率更低，很多团队设为必过项。今年新出现的 golangci-lint 把多个 linter 收进一个二进制，可以替代过去 gometalinter 的拼装方案。

flowchart TD
    A[本地提交] --> B[gofmt 检查]
    B -->|有差异| C[格式化后重新提交]
    C --> B
    B -->|通过| D[go vet]
    D --> E[golint 与 staticcheck]
    E --> F[人工评审]
    F -->|需要修改| A
    F -->|通过| G[合并到主干]

把这些命令写进 Makefile，比让每个人记五条命令可靠得多：

顺序也有讲究：格式最先拦，最容易修、争论最少；vet 其次，命中的多半是真问题；lint 放在最后，只看增量。CI 跑完整套，本地提交前跑 make check。

代码评审清单

规范落到评审环节，条目不能太多。下面十条覆盖前面各节最容易出问题的地方，可以直接当模板用：

  • 新增或修改的文件通过 gofmt，go vet 无告警。
  • 包名短小、无下划线，没有 util、common 这类无职责命名。
  • 导出的标识符都有注释，且注释以标识符名开头。
  • 缩写词大小写统一，ID、URL、HTTP 没有写成 Id、Url、Http。
  • 每个 error 都被检查，没有 _ 吞掉 Close 或 Scan 的返回值。
  • 错误只处理一次，没有既记录日志又原样返回。
  • 接口定义在调用方，且没有只有一个实现、只调用一次的接口。
  • 每个 goroutine 都有明确的退出路径，ctx 从入口一层层传到了下游。
  • 测试使用表驱动与 t.Run，没有用 time.Sleep 等待异步结果。
  • 新增依赖有明确理由，导入图没有出现环。

清单的价值在于把争论变成勾选，发现哪条不满足就直接指到具体行，比说“风格不太对”有效。清单也该演进：某条规则几个月没人违反，说明已成本能，可以删掉，把注意力让给新问题。

小结

Go 的编码规范可以分成三层：格式交给 gofmt，语言习惯参考官方文档，剩下的团队约定才需要写下来。命名追求短而准，包按职责切分并用 internal/ 守住边界，错误只处理一次且不吞掉，接口小而在使用方定义，goroutine 谁启动谁负责退出。注释解释为什么，测试用表驱动并保持可读。最后把 gofmt、go vet、golint、staticcheck 串进 Makefile 与 CI，让机器守住能自动判定的事情，人才有精力讨论真正需要判断的设计问题。
