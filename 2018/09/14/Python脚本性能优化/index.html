Python 脚本性能优化

本文属于《Python 学习路线》第 13/29 篇
上一篇系列目录下一篇

脚本能跑通和跑得快是两件事。一次日志处理要等十几分钟、一个批处理把内存吃满时，凭直觉改代码往往事倍功半：改了半天的位置未必是瓶颈。本文按“先测量、再定位、后优化”的顺序，串起 CPython 3.7 下常用的计时、剖析、内存分析与并发手段，最后用一个日志分析脚本走完整条链路。读者具备基本语法与标准库经验即可，读完后能独立做一次有依据的性能改造。

一、先测量再改：把“慢”变成可比较的数字

优化的第一步不是改代码，而是定义问题。同样是“慢”，可能指单次任务的延迟、单位时间的吞吐量，或者运行期间的峰值内存。三者的手段常冲突：缓存换延迟会推高内存，多进程提吞吐会让峰值内存翻几倍。动手前先写清楚改哪一个，以及改到多少算合格。

接下来是基准。没有基准的优化等于没有刻度的尺子，改完只能凭感觉说“好像快了点”。可用的基准至少满足：输入固定且有代表性，环境固定（同一台机器、同一个 Python 版本），运行时没有别的重负载抢资源，重复多次取最小值或中位数。样本要覆盖真实分布的长尾，比如超长行、编码异常的行、空字段，否则优化会偏向理想输入。基准脚本也应当入库，命令、样本与版本号放在一起，改动前后各跑一遍才有可比性。

flowchart TD
    A[明确目标 延迟 吞吐 还是内存] --> B[准备代表性样本 建立基准]
    B --> C[剖析 定位热点]
    C --> D[提出假设 单点修改]
    D --> E[复测 与基准对比]
    E --> F{达到目标}
    F -- 否 --> C
    F -- 是 --> G[校验输出一致 固化基准]

还有一条纪律：一次只改一个变量。同时换掉数据结构和 I/O 方式，即使变快了也不知道是哪一处起了作用。把假设写在提交信息里，收益为正就保留，为负就回退。

二、时间测量：perf_counter 与 timeit

最朴素的计时是 time.time()，但它返回系统时钟，可能被 NTP 校正甚至回拨，测毫秒级间隔并不可靠。标准库为此提供了单调时钟：time.perf_counter() 只会前进，分辨率最高；time.process_time() 只累计进程消耗的 CPU 时间，和墙上时间对比，可以判断代码是在真算还是在等 I/O。

取最小值有道理：干扰只会让测量变慢，不会让它变快，最小值最接近无干扰时的真实成本；中位数反映典型情况；平均值容易被偶发卡顿拉高。

对很小的代码片段，手写循环的计时误差会盖过被测代码本身，这时用 timeit。它在正式计时前自动决定循环次数，并支持独立的初始化语句：

-n 是每轮次数，-r 是轮数，-s 只执行一次且不计时。timeit 计时期间默认关闭垃圾回收，对分配密集的代码偏乐观；如果主要成本就是对象创建，应当打开 GC 再测。

预热同样重要。首次调用往往包含导入模块、编译正则、建立连接等一次性开销，文件系统缓存与 CPU 频率也要时间稳定，基准里先空跑一遍并丢弃结果是成本极低的好习惯。带缓存的函数第二次调用则不能代表首次。

三、函数级剖析：cProfile、pstats 与 py-spy

知道“慢”之后，下一步是找出时间花在哪些函数上。cProfile 是标准库自带的确定性剖析器，按函数记录调用次数与耗时。最直接的用法是 python -m cProfile -s tottime analyze.py，但结果混进业务输出后不便分析，落盘更好：

读报告的关键是分清两列。tottime 是函数自身耗时，不含子调用，它回答“到底谁在烧 CPU”；cumtime 是包含子调用的累计耗时，回答“这条链路的总账有多大”。合理的顺序是先按 cumtime 从顶层往下走，找到耗时集中的分支，再在分支内部按 tottime 找具体函数。常见的误读是把 cumtime 最高的函数当成要改的对象，而它往往只是调度者。另外要留意 ncalls：形如 20/1 表示递归，调用次数极大的小函数即使单次便宜，累计起来也可能占可观比例，通常适合缓存或移到循环外。

这份报告里 main 的 cumtime 最大却不值得改，真正要动的是 parse_line：它自身的 tottime 高，说明函数体（切分、循环、构造对象）开销大；它调用的 match 与 _strptime 各占一块，提示正则与时间解析是候选；read 则说明 I/O 也占了一部分。

cProfile 的局限：只到函数粒度，函数内部哪一行慢看不见；C 扩展内部的耗时不可见，会归并到调用它的函数上；默认只统计主线程；靠在每个调用点埋钩子工作，对调用极密集的代码有可观放大。它适合缩小范围，不适合精确到行。

需要看线上进程又不想改代码重启时，用 py-spy。它是采样式剖析器，直接读取目标进程内存来还原调用栈，开销低，可以 attach 到已经在跑的服务：

top 实时显示各函数的采样占比；record 生成火焰图，横向宽度就是时间占比；dump 打印所有线程的调用栈，排查“卡住了”很有用。采样剖析看不到调用次数，也可能漏掉极短的函数，但开销小，适合初步判断瓶颈类型。Linux 上读取其他进程需要 ptrace 权限，macOS 上需要 sudo。

四、逐行剖析：line_profiler

当范围已经缩小到某个函数，而函数有几十行时，需要行级数据。line_profiler 就是做这件事的：

给目标函数加 @profile 装饰器即可，kernprof 在运行时注入它，所以直接 python analyze.py 会因为找不到名字而报错；需要两种方式都能跑，可以在文件顶部做空实现兜底。

输出是一张表，每行给出执行次数、总耗时、单次耗时、占比与该行源码。读法是先按占比排序，再看次数：单次耗时高说明操作本身贵（一次正则、一次系统调用、一次大对象构造），值得换实现；执行次数高说明被反复执行，值得缓存或移出循环。两者叠加的行，通常一改就有收益。

在 IPython 里可以不改脚本，用 %load_ext line_profiler 加 %lprun -f parse_line analyze.main('access.log') 即可。代价是逐行埋点，开销比 cProfile 更大，只适合在缩小后的输入上跑。

五、内存：tracemalloc、memory_profiler 与对象开销

内存问题分两类：峰值过高被系统杀掉，以及持续增长最终耗尽。CPython 用引用计数加三代分代回收，实际遇到的“泄漏”多半不是真泄漏，而是容器只增不减、缓存没有上限、全局列表不断累积、生成器被意外物化。

tracemalloc 从 3.4 起进入标准库，能按分配点统计内存：

statistics('lineno') 按分配发生的行聚合，'traceback' 给出完整调用栈，适合定位“这个巨大的 list 是谁造的”。更有用的是两次快照做差：handle_one_batch() 前后各取一次，用 compare_to(before, 'lineno') 打印前十条。代价是每次分配都要记栈，速度明显下降，只在定位阶段打开。

memory_profiler 提供两个视角。逐行视角用装饰器打印每行的内存增量，能看出哪一行让占用跳了一截；时间视角用 mprof run 采样常驻内存，再用 mprof plot 画曲线。曲线比数字更有信息量：台阶式上升往往对应“把整个文件读进了列表”，缓慢爬升可能是缓存累积，锯齿则是 GC 在回收。

sys.getsizeof 常被误用，它只返回对象自身大小，不含引用的对象：

所以逐元素求 getsizeof 再相加会严重低估真实占用；需要递归统计可以用 pympler 的 asizeof。单个对象的基础开销也值得记住：64 位 CPython 上一个 int 约 28 字节、float 约 24 字节，空 list 约 56 字节、空 dict 约 240 字节，百万级元素时这些固定成本非常可观。

由此引出容器选择：大批同构数值改用 array.array 或 NumPy 数组，省掉每个元素的 Python 对象头；结构固定的小记录用 namedtuple，或者用 __slots__ 去掉 __dict__；3.7 的 dataclasses 更清晰，但默认仍带 __dict__。重复出现的字符串可以用 sys.intern 共享，状态码、方法名这类枚举值收益明显。

六、算法与数据结构

复杂度先于常数。O(n²) 的循环在 n 等于一千时是一百万次比较，在 n 等于十万时是一百亿次，任何写法上的微调都救不回来。先问复杂度，再问常数。

这里的“平均”有前提：哈希分布均匀、对象实现了稳定的 __hash__ 与 __eq__、装载因子没有失控。自定义类没定义哈希时默认按 id 计算，通常不是想要的；定义了 __eq__ 却忘了 __hash__ 则直接不可哈希。

几个替代值得记住：计数用 Counter，most_common 内部用堆而非全排序；分组用 defaultdict(list)，省掉 if key not in；去重且保序用 dict.fromkeys(seq)，3.7 的 dict 保证插入顺序；取前 k 大用 heapq.nlargest；有序查找用 bisect；两端进出用 deque，因为 list.pop(0) 是 O(n)。

嵌套循环里的查表是最常见的陷阱。把内层要查的集合提前建成 dict 或 set，复杂度就从 O(n·m) 降到 O(n+m)。按 key 聚合、建反向索引、预先分组，本质上都是这个思路：发现内层在“找某个东西”，就该换一个能直接查到它的结构。

内存方面，生成器最省力：sum(len(line) for line in f) 不会物化中间列表，写成列表推导再求和则会先把所有长度放进内存。生成器把“读入、处理、写出”变成流水线，峰值内存与输入规模解耦；代价是只能遍历一次，需要多次遍历或要 len() 时还是得物化。itertools 的 islice、chain、groupby 可以配合它把两步操作压成一趟流式处理。

七、字符串与 I/O

字符串不可变，+= 每次都构造新对象。CPython 对“引用计数为 1 的 str 就地扩展”做过优化，但这属于实现细节，遇到多引用、不同版本或别的解释器就会退化，不能作为写法的依据。

join 先算总长度再一次性分配，是线性时间；它只接受 str，混合类型要先转换。格式化语法的差异通常不是瓶颈，真正的浪费是在循环里反复计算不变的常量。

正则要显式编译并提到模块级。re 内部有编译缓存，但容量有限，模式一多就被挤掉；显式编译也让“这个模式是常量”在代码里可见。能用 str.split、startswith、in 解决的不要上正则，常数成本高得多。

编码方面，文本模式打开文件时显式写 encoding='utf-8'，不要依赖平台默认值。如果整行只需少数字段，可以二进制读入、只对需要的片段解码，省掉整行的解码与再编码；异常字节用 errors='replace' 处理，别让一行脏数据中断任务。

缓冲层次要清楚：for line in f 已经是带缓冲的迭代，比手写 readline 循环快；按块处理超大文件时用 f.read(1 << 20) 之类的块大小，但块边界可能切断行，要保留残余拼到下一块。写入时攒够一批再 writelines，或调大 open 的 buffering；循环里 print 到终端极慢。解析 CSV 用 csv 模块，底层是 C 实现，处理了引号与转义，速度通常也不输手写 split。

判断是否继续改代码，先看瓶颈是不是 I/O。磁盘利用率已经打满、或者网络往返占了大头时，再快的解析函数也没用。

八、向量化：NumPy 与 pandas 的边界

NumPy 把循环下沉到 C，配合连续内存与 SIMD，对同构数值数组通常有数量级的优势，是数值脚本性价比最高的一步。

收益之外有几个坑。构造数组本身要遍历一次，np.asarray 对 ndarray 不拷贝，对 list 则完整转换；数据只算一遍时，这次转换可能吃掉大部分收益。布尔索引 arr[mask] 会产生临时数组，大数组下峰值内存接近翻倍，必要时改成分块处理。不要在循环里 np.append，它每次重新分配并拷贝，应当预分配 np.empty(n) 再按索引赋值。dtype 也要选对：float32 省一半内存但累加精度会掉，整数溢出则是静默的。切片是视图、布尔索引是拷贝，改动前要分清。

pandas 的价值在带标签的表格运算与分组聚合，不在“把循环换个写法”。apply(axis=1) 本质仍是逐行 Python 调用，只是把 for 藏进了库函数，通常比向量化慢一到两个数量级；iterrows 更慢，还会在每行做类型整理。优先用内置的列运算、groupby 聚合、str 访问器与 merge，只有逻辑确实无法表达成列运算时才退回 apply，并接受它的成本。表格 API 的细节不在本文展开。

也有明确不值得的时候：数据量小，构造数组的开销占主导；逻辑含复杂分支，硬套向量化会写成难懂的掩码组合；处理对象以字符串与正则为主；一次性脚本引入 NumPy 还增加部署体积。向量化往往牺牲可读性，团队里没人看得懂的“快代码”是负债。

九、并发模型的选择

并发不是“加个线程就快”。选型前先判断瓶颈：在等网络与磁盘，还是在烧 CPU。用墙上时间除以 CPU 时间，比值远大于一说明大量时间在等待。

绕不开的是 GIL。CPython 用一个全局锁保护解释器状态，同一时刻只有一个线程执行字节码。由此可推出：纯 Python 的 CPU 密集循环，多线程不会加速，反而因切换略慢；阻塞式 I/O 在系统调用期间释放 GIL，多个线程可以重叠等待；部分 C 扩展在长计算中主动释放 GIL，比如 NumPy 的多数 ufunc、hashlib、zlib，这类计算用线程也能并行。切换也不是随时发生的，解释器默认每 5 毫秒检查一次（sys.getswitchinterval()），一个长时间不返回的 C 调用会卡住同进程的其他线程。

flowchart TD
    A[先看瓶颈类型] --> B{CPU 时间占比高}
    B -- 是 --> C{能否换算法或向量化}
    C -- 能 --> D[先改算法 成本最低]
    C -- 不能 --> E[多进程 或 C 扩展]
    B -- 否 --> F{并发连接或任务数量}
    F -- 少量 --> G[线程池]
    F -- 大量且库支持异步 --> H[协程]
    F -- 中等且库阻塞 --> G
    E --> I[注意序列化与内存开销]
模型 适合的瓶颈 能否利用多核 主要开销 典型用法 常见坑
线程 I/O 等待、会释放 GIL 的 C 扩展 部分 线程栈、切换、锁竞争 ThreadPoolExecutor、queue 共享可变状态、死锁
协程 海量并发连接、异步库 否 事件循环调度、协程对象 asyncio、aiohttp 一处阻塞调用拖垮全部
多进程 纯 Python 的 CPU 密集 是 进程内存、启动、序列化 multiprocessing、进程池 数据拷贝、Windows 启动方式

选择顺序：先看能否换算法或向量化，成本最低、收益最大；再看能否把零散的阻塞操作合并成批量；最后才加并发。协程适合 I/O 密集且库支持异步的场景，其事件循环、任务取消与超时另有专文讨论，这里只当作选项。concurrent.futures 提供统一接口，线程池与进程池可低成本互换，先用线程版验证逻辑、再换进程版验证收益。

十、多进程实践

多进程绕开 GIL，是纯 Python 计算密集型任务最直接的手段。基本形态是进程池加分片：

几个参数决定它是加速还是白忙。chunksize 控制每次派发的任务批量，任务太碎时通信与调度开销会盖过计算本身，按“每块几百毫秒”估算比较合适。imap_unordered 按完成顺序返回，省掉等待最慢分片的时间，代价是结果无序。

序列化是最大的隐性成本。参数和返回值都要经过 pickle，一个巨大的字典传回父进程，等于把内存拷贝与反序列化又做了一遍。让子进程完成聚合、只返回小结果，或者让它自己写文件、父进程只收路径。不可 pickle 的对象不能作参数：lambda、局部函数、打开的文件、数据库连接、锁，都要在子进程里重建，用 initializer 做一次性初始化最合适。

共享只读大数据需要想清楚。Linux 的 fork 让子进程按写时复制共享内存，但 Python 对象的引用计数会在访问时改动标记页，实际效果打折；Windows 只有 spawn，父子不共享地址空间。稳妥做法是每个子进程各自加载，或者用 numpy.memmap、mmap 映射同一份只读文件。

共享可变状态有两种选择。Value 与 Array 基于 ctypes 共享内存，访问快，但要自己加锁；Manager 返回代理对象，用起来像普通容器，但每次读写都是一次进程间调用，放进循环会慢得离谱。多数分析任务并不需要共享状态，分片计算、父进程合并更简单。进程数上，CPU 密集取核数或核数减一；内存密集先估算单进程峰值再乘上去，用上 swap 会慢一个数量级。

最后是 Windows 上的经典问题。spawn 会让子进程重新导入主模块，如果创建进程的代码写在模块顶层，就会无限递归地创建进程直到报错，所以入口代码必须放在 if __name__ == '__main__' 之下。子进程的异常会在取结果时重新抛出，但 traceback 往往不完整，任务函数内部应当自己捕获并记录日志。收尾用 with 或显式 close() 加 join()，直接 terminate() 可能留下写了一半的输出文件。

十一、缓存

缓存是把“重复计算”换成“重复查表”，前提是同样的输入会真的再来一次。函数级缓存用 functools.lru_cache：

使用时有几条硬约束。参数必须可哈希，传 list 或 dict 会直接报错，需要先转成 tuple；maxsize=None 表示不淘汰，在长期服务里等于缓慢的内存泄漏，应给定上限并用 cache_info() 观察命中率与条目数；返回可变对象会被所有调用方共享，改一处就污染全部，应当返回副本或只缓存不可变结构；typed=True 会区分 1 与 1.0，默认不区分。3.7 的实现内部有锁，但“查不到再计算”这一整段不是原子的，同一个 key 可能被并发计算多次，对幂等的纯函数可以接受，对有副作用的函数不行。

缓存最难的部分不是存，而是失效。数据会变时不能只用参数做 key，把版本号、文件修改时间、配置哈希拼进 key 最简单可靠。其次是 TTL：记录写入时间，过期重算，或定期整体 cache_clear()。主动失效最精确也最复杂，要维护“哪个数据变了清哪些 key”的索引，复杂度上来后不如换成进程外的缓存服务。

磁盘缓存适合“输入大、计算贵、结果可复用”的场景，比如报表的中间结果。key 要用输入内容的哈希而不是文件名，再拼上代码版本号与关键参数，避免改了算法还读到旧结果。写入用临时文件加 os.replace 保证原子性；读之前校验存在性与版本号，不符就当未命中。joblib.Memory 提供了现成的 @memory.cache；简单的键值存储可以用 shelve 或 sqlite3，后者在并发与查询上更稳。命不中时的成本也要算，对大文件做内容哈希可能比计算还贵，可以先用修改时间与大小粗判。

十二、走到 C：Cython、cffi 与 C 扩展

当热点是一个稳定的数值内核、算法已经最优、并发也榨不出更多时，才考虑把这一小块下沉到 C。判断标准是“这个热点会长期存在”，一次性的脚本不值得引入编译工具链。

Cython 是最平滑的路径，它接受接近 Python 的语法，加上类型声明后编译成 C 扩展：

提速主要来自 cdef：局部变量变成 C 类型后，循环里不再创建和销毁 Python 对象，也不再走字节码分发。数组要用类型化 memoryview（比如 double[:]）而不是 list，避免逐元素装箱；多核可以 prange 配合 nogil，但要处理 OpenMP 参数与循环内的线程安全。用纯 Python 模式编译 .py 提升有限，它省掉的是解释开销，省不掉算法本身。

cffi 适合调用已有的 C 库。ABI 模式用 ffi.cdef 声明原型、ffi.dlopen 加载动态库，构建时不需要头文件；API 模式需要编译器，但类型检查更多、调用路径更短。手写 CPython C 扩展最灵活也最贵：引用计数、错误返回、GIL 状态都要自己管，漏掉一个 Py_DECREF 就是内存泄漏。

维护成本必须提前算清。构建上，用户机器要有编译器，对外发布要为每个平台与 Python 版本准备 wheel；调试上，C 层崩溃不会给 traceback，需要 gdb 或 faulthandler；迭代上，改一行就要重新编译；团队上，维护的人要同时看得懂 Python 与 C。替代方案里，numba 用 @jit 在运行时编译数值函数，几乎零改造，但依赖 LLVM、首次调用有编译延迟、对 Python 对象支持有限。权衡收益、维护年限与团队能力，多数业务脚本的正确答案是停在向量化与多进程这一层。

十三、端到端案例：一个日志分析脚本

把前面的工具串起来看一个完整过程。场景是一个 Nginx access log 分析脚本：输入若干 GB 日志，输出按小时的 PV、UV 与流量汇总。初版单文件、逐行处理、纯 Python，跑完要等很久。

第一步建立基准。挑一份有代表性的一天数据作为样本，把命令、Python 版本与耗时记到固定文件里。样本要包含长 URL、异常行、不同状态码与不同时区，否则优化会偏向理想输入。

第二步做函数级剖析。用 python -m cProfile -o base.prof analyze.py sample.log 落盘，再用 pstats 按 tottime 排序。典型报告：解析函数自身耗时最高且调用次数等于行数；正则与时间解析各占一块；某处字典操作次数异常多；文件读取也有一块固定成本。

第三步做行级定位。给解析函数加 @profile，用 kernprof -l -v 在缩小后的样本上跑。常见问题行：每行都调用一次 re.match 而未预编译；同一行多次 split；用 strptime 解析时间；先把字段拼成 tuple 再解包。

示例省略了时区换算与后续处理，实际代码要按业务口径补齐。

第五步复测并换方向。解析改完后重新剖析，热点往往转移到聚合或 I/O 上。这时再动数据结构：用 dict.get 累加、用 Counter 计数、把 UV 集合按小时分片；若瓶颈变成读文件与解码，就改二进制读、只解需要的片段并调整块大小。

第六步并行。单进程 CPU 仍然打满时，把文件列表分片，用 Pool.imap_unordered 分发，chunksize 调到每块几十万行，子进程返回按小时的局部聚合，父进程合并。关键仍是“聚合在子进程完成、只传小结果”，回传每行记录会让序列化吃掉全部收益。

第七步验证。优化前后对同一份样本各跑一次，diff 两份输出；再测边界输入：空文件、全是非法行、跨年时间戳、含非法 UTF-8 字节的行。性能改造最常见的翻车不是变慢，而是结果悄悄变了。

第八步固化。把样本、基准脚本与剖析命令放进仓库，约定“改动解析逻辑必须重跑基准并对比输出”。优化前后的耗时请在自己的机器上测量，文件大小、磁盘类型与 CPU 核数都会显著影响结果。

十四、优化清单与反模式

把经验收成一份可执行的清单，按顺序做：

  1. 写清目标：是延迟、吞吐还是内存，合格线在哪里。
  2. 固定样本与环境，建立可重复的基准并记录版本。
  3. 用 perf_counter 或 timeit 确认真的慢，排除环境与测量误差。
  4. 用 cProfile 找函数，用 line_profiler 找行，线上问题用 py-spy。
  5. 按“算法与数据结构、I/O 方式、向量化、并发、C 扩展”的顺序尝试，成本从低到高。
  6. 每次只改一处，改完复测，收益为正才保留。
  7. 用 tracemalloc 或 memory_profiler 确认峰值内存没有恶化。
  8. 校验输出一致，把用例补进回归。

反模式同样值得列出来：

  • 凭感觉优化。改了十分之一代码，收益为零，还引入两个 bug。
  • 微优化上瘾。纠结 x + 1 与 x.__add__(1)，对总耗时毫无影响。
  • 忽略 I/O。CPU 占用只有三成却一直在优化计算，真正的瓶颈是磁盘或网络。
  • 循环里重复计算。len(items)、re.compile、属性查找、配置读取都该提到循环外；append = result.append 这类局部绑定只在确认是热点后再用。
  • 过早并行。单进程还没优化就上多进程，时间花在序列化与调试上。
  • 无界缓存。把 lru_cache(maxsize=None) 加在参数空间巨大的函数上。
  • 没有基线就上 C 扩展。用长期维护成本换几个百分点的提升。

小结

性能优化的核心不是记住多少奇技淫巧，而是建立“测量、假设、验证”的闭环：用可重复的基准把“慢”变成数字，用剖析工具定位到函数与行，再按成本从低到高尝试算法、I/O、向量化、并发与扩展。CPython 3.7 下最容易被低估的是数据结构与 I/O 方式，最容易被高估的是多线程；GIL 决定了线程只对等待有效，纯计算要靠多进程或 C 扩展。每改一处就复测，并始终校验输出一致，因为悄悄改变结果的“优化”比慢更糟。
