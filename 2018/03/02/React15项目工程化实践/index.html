React 15 项目工程化实践

React 16 已经在 2017 年 9 月发布，但不少线上项目仍停在 React 15.6 这条线上，短期内也不会整体升级。本文不谈新特性，只讨论这类项目真正需要的东西：依赖怎么锁定、目录怎么分层、入口如何装配、样式与构建如何配合、测试做到什么程度。读完之后，你应该能把一个 React 15 的仓库整理成结构清晰、可交接、可持续维护的工程。

2018 年维护 React 15 项目的现实

先说清楚版本口径。React 15.6 是 15.x 系列的最后一条维护线，它之前的 15.5 做了两件影响所有存量项目的事：React.createClass 被标记弃用并移入独立的 create-react-class 包，React.PropTypes 被移出核心并交给 prop-types 包。这意味着一个 2016 年写的项目，如果只是把 react 升到 15.6 而不补装这两个包，控制台会立刻出现成片的 warning，甚至直接报错。因此我们接手老项目时，第一步不是看业务代码，而是先看 package.json 里 react、react-dom、react-router、redux 这四者的版本组合是否自洽。

第二步是判断要不要升级到 2017 年 9 月发布的 React 16。收益是渲染层重构与更小体积，成本集中在三处：第三方组件库是否已经适配、业务代码里是否有依赖 findDOMNode 与字符串 ref 的写法、以及大量基于旧生命周期的组件在严格模式下是否会出问题。对于仍在快速迭代的业务项目，笔者更倾向整套升级，而不是让两个版本在同一棵组件树里共存。同一个页面里出现两份 react 实例，context 与事件系统都会错乱，排查成本远高于一次性升级。如果确实要试水，比较稳妥的做法是新建一个独立仓库验证，而不是在主工程里混装。新立项的项目则可以直接评估 React 16，本篇讨论的工程组织方式对两者同样适用。

第三步是把依赖锁死。package-lock.json 或 yarn.lock 必须入库，CI 上用 npm ci 或 yarn install --frozen-lockfile 安装，保证本地、测试、生产三处拿到完全相同的依赖树。对于 react、react-dom、react-router 这类会互相约束的包，我们直接写精确版本号，不用 ^；工具类依赖才允许小范围浮动。锁文件带来的麻烦是升级要显式执行，但换来的是”昨天还能跑，今天就白屏”这类问题的大幅减少。

目录结构：让分层比命名更重要

React 本身不规定目录结构，但一个超过三十个页面的后台项目，如果没有约定，半年后就会出现 components/ 里塞着整个页面、containers/ 里全是静态展示组件的局面。我们采用的划分方式是按职责切分，而不是按文件类型切分：

components 与 containers 的边界是这套结构最重要的纪律。判断标准很简单：一个组件如果直接 import 了 action 创建函数、或者从 state 里取数据，它就应该放进 containers；反之，只接收 props、不关心数据从哪来的组件放 components。这样做的好处是纯展示组件可以被任意复用，也可以被单独测试，不需要构造一整套 store。项目初期这条线容易被破坏，代码评审时要盯住。

styles 目录只放三类文件：reset.css、主题变量、以及极少数确实需要全局生效的样式。业务组件的样式一律与组件同目录，命名为 Button.css，由 CSS Modules 处理作用域。这样删除一个组件时，它的样式会跟着一起删掉，不会在全局样式表里留下无人认领的规则。

为了避免 ../../../ 这种深层相对路径，我们在构建配置里加了别名，让 import Foo from 'components/Foo' 可用。别名只在构建层生效，编辑器与 ESLint 也需要同步配置，否则 import/no-unresolved 会报错。

第二，routes 作为配置对象传给 Router，而不是写成 JSX 子节点。react-router 3 支持两种写法，集中式配置便于做权限拦截、按模块拆分路由文件，也便于在路由层统一挂 onEnter 钩子。history 则决定 URL 形态：browserHistory 需要服务端把所有路径回退到 index.html，hashHistory 不需要服务端配合但地址栏带 #。后台系统常用前者，嵌入式页面常用后者，这个选择要在项目初期定下来，中途更换会牵连所有外链。

window.__INITIAL_STATE__ 是为将来可能的同构预留的注入点，即便当前是纯前端渲染，也保留这个参数让 configureStore 的签名稳定。渲染本身没有魔法：ReactDOM.render 在 React 15 中是同步的，返回时 DOM 已挂载完毕，紧接着读取节点尺寸是安全的。这一行为在 React 16 之后发生了变化，但在 15 的代码里可以放心依赖。

组件写法：class、函数组件与 createClass 的退场

React 15 项目里同时存在三种组件写法，交接文档里最好把它们的适用范围说清楚。

第一种是 React.Component 子类，用于有内部状态或需要使用生命周期的组件。构造函数里初始化 state、绑定事件处理函数的 this，是这段时间最常见的模板：

第二种是无状态函数组件。它只接收 props 返回 JSX，没有 this、没有 state、没有生命周期，写起来最短，也最容易被测试：

函数组件不能挂 ref，也没有实例方法，需要复用逻辑时用高阶组件包一层更合适。

第三种是 React.createClass。它是 React 早期唯一的组件定义方式，内置了 getInitialState、getDefaultProps 和自动绑定 this，还支持 mixins 数组。这套 API 在 15.5 被标记弃用，并从核心包移到了 create-react-class。存量项目里如果还有大量 createClass，不建议为了”消灭 warning”而机械替换：mixins 没有直接的 class 等价物，多个 mixin 共享 this 上的隐式状态，迁移时应该顺手改成高阶组件或把逻辑抽成普通函数。没有被复用的 createClass 才适合逐条翻译成 class。这件事可以按模块分批做，不必一次动完。

PropTypes：迁到独立包，并认清它的边界

15.5 之后，PropTypes 不再挂在 React 上。升级到 15.6 却没有安装 prop-types 的项目，会在控制台看到”React.PropTypes is deprecated”或者干脆报 Cannot read property 'string' of undefined。修复方式只有两步：安装依赖，改引用。

写法上有几个约定值得固定下来。对象类型用 shape 描述关心的字段，不要用 object 敷衍；可能为空的属性不加 isRequired，但要在 defaultProps 里给默认值；children 用 PropTypes.node 而不是 element，因为文本和数组都算合法的子节点。

更重要的是理解它不做什么。PropTypes 只在开发构建里执行校验，命中问题也只是在控制台打印警告，不会抛异常、不会阻断渲染。生产构建中 React 会跳过这些检查，打包工具也可以把 propTypes 声明整个删掉。因此它不能替代后端校验，也不能替代组件内部对空值的防御。我们的约定是：propTypes 用于暴露组件契约、方便联调时发现问题；真正可能导致白屏的字段，仍要在 render 里做兜底判断。另外，propTypes 不应该在运行时被业务代码读取或修改，那属于滥用。

样式工程：CSS Modules 与 PostCSS

React 15 时代没有官方样式方案，团队通常在三者中选一个：全局 CSS 加 BEM 命名、CSS Modules、CSS-in-JS。我们选择 CSS Modules：改动最小，样式仍是 .css 文件，设计师也能直接看懂，作用域交给构建工具解决。

开启方式是在 2017 年发布的 webpack 3 的 css-loader 上传入 modules 选项，并用 localIdentName 控制生成类名的形态。开发环境希望类名可读，便于在 DevTools 里定位；生产环境希望类名短，节省字节：

PostCSS 负责三件事：autoprefixer 按 browserslist 补前缀、postcss-cssnext 让嵌套与自定义属性在开发时就能写、生产环境用 cssnano 压缩。配置放在独立的 postcss.config.js 里，而不是塞进 webpack 配置，这样编辑器插件和其它构建入口可以共用。需要提醒的是，CSS 自定义属性在 IE 11 上不生效，而当时的兼容清单里通常还有 IE 11，所以主题色这类变量必须由 PostCSS 在编译期展开，不能指望浏览器运行时支持。

主题与全局样式单独处理。src/styles/theme.css 里定义一批颜色、间距、字号变量，业务组件的 CSS 通过 composes 或直接引用变量来保持统一；reset.css 只在入口 import 一次。第三方组件库的样式必须覆盖时，用 :global 显式跳出作用域：

react-router 3 的核心是集中式路由表。所有路径在一个文件里声明，嵌套关系一目了然，权限判断可以放在 onEnter 里，避免每个页面组件各写一遍：

getComponent 是路由级代码分割的入口，配合 import() 让每个页面独立成 chunk。路由表按业务域分文件，再由 index.js 汇总，不要为了整齐把几百行路由写进一个数组。onEnter 里做鉴权要注意它是同步钩子，跳转用 replace 而不是 push，否则用户点浏览器后退会陷入循环。

Redux 3 的组织重点是 store 的构造与组件连接方式。store/configureStore.js 集中创建 store，开发环境挂 thunk 与日志中间件，并通过 compose 接入浏览器里的 DevTools 扩展；生产环境只保留 thunk：

reducer 按业务模块分目录，每个模块自带 action types、action creators 与 reducer，reducers/index.js 只做 combineReducers。组件侧一律用 connect 取数，mapStateToProps 只挑选该组件需要的字段，不要返回整个 state，否则任何一次无关更新都会让它重渲染。需要触发多个 action 时用 bindActionCreators 包一层，保持 props 上的回调签名稳定。至于 action 如何被 reducer 处理、中间件如何串联，属于 Redux 本身的话题，这里不再展开。

开发与构建：两处配置撑起日常

开发期与构建期的差异集中在两个文件：2017 年发布的 webpack 3 的 webpack.config.js 与 .babelrc。职责分清后，改构建不必靠口口相传。

热更新与接口代理

react-hot-loader 3 的接入分三步：.babelrc 里加 react-hot-loader/babel 插件、入口最前面引入 react-hot-loader/patch、再从 react-hot-loader 导入 AppContainer 包住根组件。它与 class 组件配合最稳；函数组件没有实例，热替换后自然不会保留内部状态，遇到不生效先用 class 版对照。接口调试交给 webpack-dev-server 的 proxy，前端仍请求同源的 /api，由开发服务器转发到后端，免去跨域与手改 baseURL：

Babel 6 的预设组合

.babelrc 保持最小集合：babel-preset-env 负责按目标浏览器降级语法，babel-preset-react 负责 JSX，另外两个插件几乎必装：transform-class-properties 支持箭头函数形式的类属性，transform-object-rest-spread 支持对象展开。babel-plugin-transform-runtime 把 _extends、_objectSpread 这类 helper 与 regenerator 从每个文件内联改为引用 babel-runtime，能明显减少重复代码；但它不注入实例方法，Array.prototype.includes 之类的缺口仍需在入口引入一次 babel-polyfill。两者分工不要搞混：runtime 管语法 helper，polyfill 管内置对象。

测试与几个反复出现的问题

组件测试用 Jest 22 加 Enzyme 3，适配器在测试启动文件里初始化一次。日常只做浅渲染，验证 props 到输出的映射与回调是否被调用，快照则只给稳定的小组件用：整页快照会随着样式类名和数据结构变动而频繁失效，维护成本高于收益。

常见问题有四个。一是只升级了 react 没装 prop-types，warning 刷屏；二是 createClass 组件用了热更新却不生效，因为它不在 class 组件那条更新路径上；三是 CSS Modules 里想覆盖第三方类名却忘了 :global，编译后选择器根本匹配不到；四是生产环境开了 source map 又把 .map 文件一起部署，等于公开源码，正确做法是上传到错误监控平台而不随静态资源发布。

小结

React 15 项目的工程化，本质是把”能跑”变成”可交接”：锁文件固定依赖组合，目录与命名固定职责边界，入口固定数据流方向。样式、构建、测试三块配置尽量收敛到少数几个文件，减少口口相传的隐性知识。升级到 2017 年 9 月发布的 React 16 可以规划，但不要在同一棵组件树里混装两个版本。把这些约定写进仓库的说明文档，比留在聊天记录里可靠得多。
