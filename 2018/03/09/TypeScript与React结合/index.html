TypeScript 与 React 结合

React 把界面拆成组件，组件之间靠 props 传递数据，但 JavaScript 并不会替我们检查这份数据长什么样。本文给一个中等规模的 React 项目接入 TypeScript 2.6，从依赖与 tsconfig 讲起，依次说明组件类型、props 与 state 的写法、事件和 ref 的标注，以及构建链路上的几个高频坑。读者读完应当能把一个现有的 JSX 组件文件改成类型完整的 tsx 文件，并知道哪些地方不必过度标注。

从“能跑”到“改得动”：为什么给组件加类型

React 的组件本质上是一个接收 props 的函数，或者一个带 state 的类。props 是参数，state 是内部变量。既然是参数，就存在“调用方传什么”与“被调用方要什么”的契约。JavaScript 把这份契约完全交给约定：字段叫什么、是什么类型、哪些必填，全靠人记和注释。

jsx 是 React 专属选项。取 "react" 时，tsc 把 JSX 编译成 React.createElement(...) 调用，这意味着每个 tsx 文件里都必须有 React 这个标识符在作用域内，这也是后文统一写 import * as React from "react" 的原因。取 "preserve" 时，tsc 只做类型检查、保留 JSX 原样，转译交给 Babel 的 babel-preset-react，适合已有 Babel 链路、只想加检查的项目。

其余几项的作用是：target: "es5" 保证产物能进 IE 11；module: "es2015" 把模块语法留给打包器处理，便于做 tree shaking；moduleResolution: "node" 让编译器按 Node 的解析规则去找 node_modules/@types 下的声明；strict 一次打开全部严格检查，新项目没有理由不开；noEmit 表示 tsc 只负责检查，真正的转译由 loader 完成，避免产物重复。

组件类型的三种写法

声明文件里，React 的组件被归纳为两种可被 JSX 使用的类型：类组件的 React.ComponentClass<P> 与函数组件的 React.StatelessComponent<P>（别名 React.SFC<P>）。日常写代码时，我们直接用它们的子类或标注，不必手写这两个类型。

第二种是函数组件。当时官方把这套类型叫作 SFC，即 Stateless Functional Component：

React.SFC<P> 的签名是 (props: P & { children?: ReactNode }) => ReactElement | null，因此函数体里可以放心地 return null，同时 children 已经自动包含在类型里，不必在每个组件上都写一遍。

它的好处是没有任何额外约束，需要给函数挂静态属性、或者团队不喜欢箭头函数时更顺手。代价是 children 要自己声明，defaultProps 也不会被自动识别为组件元信息。

怎么选？需要 state 或生命周期就用类组件；纯展示用 SFC；剩下两种情况用普通函数。注意组件名必须大写开头，TypeScript 与 JSX 都靠这一点区分“自定义组件”和 div 这类内置标签，小写开头的函数会被当成 HTML 元素去检查属性。

State 与 setState 的类型约束

state 的声明比 props 简单，但有两个细节值得说清。

第一，@types/react 把类上的 state 声明为 Readonly<S>。也就是说 this.state.count++ 会直接报错，只能走 setState。这正是我们想要的效果：绕过 React 的更新机制去改状态，本来就不会触发重渲染，类型系统把这条错误路径提前堵住了。

prevState 的类型自动是 Readonly<CounterState>，返回值必须能匹配 state 的形状。连续多次更新依赖旧值时，一定要用函数式写法，因为对象形式里的 this.state 可能是批处理前的旧值。

需要提醒的是 Readonly 只作用于第一层。this.state.items.push(x) 不会被拦住，若希望数组也不可变，把字段声明成 ReadonlyArray<Item>，让类型系统连同使用方式一起约束。

另外，类组件并不一定要写构造函数。直接把 state 写成类属性 state = { count: 0 }，类型依然受接口约束，还省掉了一遍 props 的重复标注，下一节的事件示例就采用这种写法。

列表页大多需要“加载中”占位，把这段逻辑抽成高阶组件很自然。难点在于包装之后的 props 还能不能保持原样。

这里有三个类型决策。第一，参数类型用 React.ComponentType<P> 而不是 React.Component<P>。前者是 ComponentClass<P> | StatelessComponent<P> 的联合，类组件和 SFC 都能传进来；后者只是个基类，SFC 根本匹配不上。第二，用泛型 P 承接被包裹组件的 props，调用 withLoading(OrderTable) 时 P 被推断为 OrderTableProps，返回的组件同样要求 orders，漏传照样报错。如果图省事写成 React.ComponentType<any>，包装一层之后所有检查都会消失，这正是很多团队觉得“加了 TS 也没用”的根源。第三，返回组件的 props 写成 P & WithLoadingProps，业务属性与包装器新增的属性合并，调用方既能传 orders 也能传 loading。

多出来的 loading 会随着展开运算符传给内层组件。多数情况下无害，介意的话可以用对象 rest 解构把它剔除，再传给 Wrapped。

还有两个非类型层面的注意点。包装后的组件 displayName 会丢失，React DevTools 里只显示 WithLoading，调试时建议手动补一个名字。原组件上的静态属性（例如 defaultProps、路由用的静态方法）也不会自动带过来，需要额外的提升处理。

接入的最后一步是让构建链路认识 tsx。安装 loader 之后，在 webpack 3（2017 年 6 月发布的版本）的配置里加一条规则即可：

ts-loader 与 awesome-typescript-loader 是当时的两条主流路线。前者直接调用 tsc，行为与命令行完全一致，报错信息也相同，配置最少；后者自己实现了一层编译，速度更快，还内置了交给 Babel 转译的能力，但在 TypeScript 版本升级时偶尔出现兼容问题。选一个即可，不必同时装。两者共同的毛病是类型检查与转译在同一进程里跑，项目一大，改一个文件要等全量检查完才刷新；折中办法就是上面这样开 transpileOnly，把检查挪到独立进程，错误仍会打印在终端里。

最后汇总几个反复出现的问题。一是 @types/react 与 react 主版本不一致，症状是报错指向声明文件内部；二是事件参数图快写成 any，等于把这一片的检查全部关掉；三是容器组件的 children 忘了声明，父组件一塞内容就报属性不存在；四是 setState 的对象里多写了 state 中没有的字段，被多余属性检查拦下，这其实是类型在帮忙。每一条都不难改，难的是知道它为什么发生。

小结

给 React 项目接入 TypeScript，核心是把 props 与 state 这两份隐式契约显式写出来：props 决定调用方怎么用，state 决定组件内部怎么变。组件类型只需记住 React.Component<Props, State> 与 React.SFC<Props> 两种主力写法，事件与 ref 的标注则是日常使用中最容易偷懒的地方。配置层面盯住 jsx: "react"、moduleResolution: "node" 和 @types 的版本对齐，构建层面按项目规模决定是否把类型检查拆到独立进程。不必追求给每一行都加类型，优先把组件边界、事件回调和对外暴露的 props 写准，收益就已经足够。真正的回报出现在半年后重构时：编辑器替你记住了所有调用点。
