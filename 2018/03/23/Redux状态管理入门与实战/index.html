Redux 状态管理入门与实战

组件之间共享数据，是每个 React 项目绕不过去的一道坎。当页面从几个组件长到几十个组件，props 一层层往下传的写法很快就会失控：改一个购物车数量，要沿着三层组件链把回调函数传下去；两个互不相邻的模块要同步一份筛选条件，只能靠父组件当中转站。本文从这些问题出发，讲清楚 Redux 的三个原则、action 与 reducer 的分工、store 的用法，以及如何用 react-redux 把 store 接到组件树上，最后给出异步请求、中间件和常见坑的处理办法。读完之后，你应该能在一个中等规模的 React 项目里独立搭起一套可维护的状态层。

为什么需要状态管理

先看一个具体的麻烦。一个后台列表页，顶部搜索框、中间表格、右侧详情抽屉。关键字要同时影响表格的请求参数和抽屉里的高亮，选中行又要反馈回表格。只用组件自身的 state，这份关键字要么被复制成三份，要么从最外层一路 props 传下去：前者一旦不同步，界面就自相矛盾；后者让中间那些不关心关键字的组件也被迫接收一个无关属性。

根源在于，我们把“数据放在哪里”和“数据属于谁”混在了一起。组件树是树形，业务数据之间却是网状：一份数据被多个分支读取，又被多个分支修改。硬把网状数据塞进树形组件，就必然产生提升状态、回调下钻、兄弟组件互相通知这些补丁写法。

更麻烦的是变更过程不可追踪。界面上某个数字不对时，我们只能顺着 setState 的调用点逐个排查，而这些调用散落在事件回调、定时器和请求回调里，没有任何一处代码能回答“这个值是怎么变成现在这样的”。

Redux 的答案是把状态从组件树里抽出来，放进一个独立对象，所有修改都走同一条通道。组件不再拥有数据，只负责读取和发起修改请求，数据放在哪里、由谁修改，都有了唯一答案。

Redux 的三个原则

Redux 的 API 很少，但背后有三条约束，理解了它们，后面的写法就都是自然推导。

第一条，单一数据源。整个应用的状态存放在一棵对象树里，由唯一的 store 持有。任何时刻把 store.getState() 打印出来，就是应用此刻的完整快照，调试时不必去几个组件里拼凑现场。

第二条，state 只读。不能写 state.list.push(item)，也不能写 state.user.name = 'x'，唯一能改 state 的方式是发起 action，它是一个描述“发生了什么”的普通对象。修改因此变成可记录、可回放的数据，时间旅行调试、操作日志、撤销重做都建立在这一点上。

第三条，用纯函数执行修改。接收旧 state 和 action、返回新 state 的函数叫 reducer，它必须纯：不改参数、不调接口、不读随机数、不依赖当前时间，同样输入永远得到同样输出。这条约束实际在保护第二条：reducer 纯了，state 的演进就完全由 action 序列决定，异常可以通过重放定位。

三条原则合起来，构成了一个很朴素的模型：一份数据、只能描述意图、修改由纯函数完成。Redux 本身没有魔法，它只是把这个模型用几十行代码实现了出来。

单向数据流

Redux 把一次状态变更拆成四步，方向始终一致，不会出现“状态改了界面没跟上”或“界面改了状态不知道”的纠缠。

flowchart TD
    UI[视图组件] -->|dispatch| A[action 对象]
    A --> R[reducer 纯函数]
    R -->|返回新 state| S[store]
    S -->|subscribe 通知| UI
    S -->|getState 读取| UI

第一步，视图里发生了一件事，比如用户点了“加入购物车”，我们不去改数据，而是 dispatch 一个 action。第二步，store 把 action 和当前 state 交给 reducer。第三步，reducer 返回新 state，store 用它替换旧的。第四步，store 通知订阅者，组件重新读取并渲染。

关键在于方向固定：组件只能读，想写只能发 action，写的结果只能由 reducer 决定。中间每一环都可以插入日志或断言，整条链路因此可观测。

初学者常问：为什么不直接在组件里写个方法改 store？那样修改逻辑又散回组件，reducer 不再唯一。单向数据流的价值不在省代码，而在把“谁能改”限制成一个点。

action 与 action creator

action 就是一个带有 type 字段的普通对象，type 用字符串描述发生了什么。约定上 type 写成大写下划线风格，并集中定义成常量，避免手写字符串拼错却只在运行时表现为“没反应”。

除了 type，其余字段由我们约定。社区常见做法是固定用 payload 承载数据，元信息放 meta，错误信息放 error。这套约定来自 Flux 标准 action 的讨论，中间件和日志工具可以用统一方式读取，不必为每个 action 写特判。早期代码常把数据摊平在顶层，例如 { type: ADD_TODO, text: 'x' }，能用，但 action 一多字段名就开始冲突。

需要强调的是，action creator 不是必须的，但它把“构造 action”这件事收拢到一处。组件里写 dispatch(addTodo(text)) 更短，也更容易在重构时统一修改；如果团队约定严格，还能在 action creator 内部做参数校验，把非法数据挡在 reducer 之前。

reducer 与 store

reducer 的签名是 (state, action) => newState，接收旧状态，根据 action 算出新状态。写 reducer 有三个硬性要求。

第一，不能改旧 state，只能返回新对象。React 靠引用比较决定是否重渲染；原地改数组再返回同一引用，connect 会认为状态没变，界面就不更新。正确做法是复制容器，替换掉要变的那一项。

这里用了对象展开语法，需要 Babel 的 babel-plugin-transform-object-rest-spread 转译，工具链较老时用 Object.assign 代替。数组的 map、filter、concat、slice 返回新数组，可以放心用；push、splice、sort 会改动原数组，要避免。

第二，switch 要有 default 分支并返回原 state。Redux 初始化时会用一个随机内部 action 调一次 reducer 拿初始值，此时匹配不到任何分支，返回 undefined 就会让 store 在启动时报错，第一次遇到往往不明所以。

第三，不能有副作用。发请求、写 localStorage、取随机数都不该出现在 reducer 里。它会被调用多次：开发模式会额外跑一遍比对结果，时间旅行调试会重放历史 action，热更新也会重跑，有副作用就会出事。

异步与中间件

真实项目里大部分 action 来自接口，而 dispatch 只接受普通对象。于是我们在中间插入一层：允许 dispatch 一个函数，由它在合适的时机再 dispatch 普通 action。redux-thunk 做的就是这件事，实现只有十几行。

thunk 让组件里只写 dispatch(fetchTodos()) 一行，请求逻辑和错误处理都挪到 action 层。代价是 action 层开始承担流程编排，复杂了会变成回调嵌套；控制好单个 thunk 的职责，不要把请求串成长链。

thunk 以中间件的形式接入。中间件的模型很朴素：拿到 store 返回一个函数，这个函数拿到 next 再返回一个函数，最内层拿到 action，决定放行、改写还是吞掉。

用 applyMiddleware 注册，顺序即执行顺序，中间件像洋葱一样嵌套：最外层先拿到 action，最内层最后执行 reducer。日志放在 thunk 之前，能同时看到函数调用和函数内部 dispatch 的 action；放在 thunk 之后，就只看得到 action 对象，看不到那次函数调用。

理解这一层后，很多东西就顺了：thunk 之所以能接受函数，是因为它在 next 之前判断参数类型，是函数就调用并注入 dispatch、getState，否则原样放行。自己写一个记录耗时或上报错误的中间件，也只需照抄这三层函数。

工程组织、性能与常见坑

小项目的目录很随意，actions/、reducers/、components/ 三个文件夹就能跑。文件一多，按技术角色分层就开始难受：改一个“待办”功能，要在三个目录之间来回跳。

另一种是按领域组织，社区称为 ducks 模式：一个功能一个文件夹，常量、action creator、reducer 放在一起，由 index.js 统一导出。

两种方式没有对错。按角色分层起步快，所有人都知道去哪找；按领域组织适合边界清晰的中大型项目，删改一个功能只动一个目录。笔者更倾向后者，前提是先划清领域，否则只是把混乱装进文件夹。

目录只是第一层，下面两件事更影响后期维护。

connect 默认做浅比较：mapStateToProps 返回的对象与上次逐字段比较，全部相等就不重渲染。因此只返回组件需要的字段，并尽量保持引用稳定。前面的示例为直观起见在 mapStateToProps 里做了过滤，列表变大后要把它移出去：每次 filter 都产生新数组，浅比较就失效了。数据量大时可以把派生计算交给 reselect 的 createSelector，它按输入缓存结果，输入不变就返回上次的输出。这是优化手段，先保证正确性再考虑。

几个高频错误值得单列。一是直接修改 state，state.list.push(item) 之后返回 state，引用没变，界面不更新。二是在 reducer 里发请求，开发模式下 reducer 会跑两遍，请求就发两次。三是 action type 手写字符串，两处拼写不一致，reducer 静默走 default，表现为“点了没反应”，所以常量要集中定义。四是往 store 里塞 DOM 节点、Promise、类实例这类不可序列化的东西，它们会让时间旅行和状态持久化失效。

小结

Redux 的核心只有三句话：状态集中放在一个只读对象里，修改只能通过描述事件的 action，计算新 state 只能由纯 reducer 完成。createStore、connect、applyMiddleware 都是配套工具，不是新概念。入门时先把三者的职责分清、把请求三态写规范，再考虑目录组织和 reselect 这类优化。真正要警惕的不是 API 记不住，而是把组件状态、服务端数据、界面开关一股脑塞进全局 store，让“单一数据源”退化成“单一垃圾场”。判断标准很简单：这份数据是否需要跨组件共享、是否需要被回放或调试，两个答案都是否，就留在组件里。
