Content Security Policy 入门

跨站脚本、第三方脚本失控、页面被嵌入钓鱼框架，这些问题有一个共同的缓解手段：告诉浏览器页面只允许加载哪些来源的资源。本文从一条最小的 CSP 策略讲起，逐条拆解常用指令、源列表语法、内联脚本的 nonce 与哈希方案，以及只报告不拦截的调试方式。读完你应该能为一个普通站点写出第一版可用策略，并知道哪些写法会让策略悄悄失效。

CSP 解决什么问题

浏览器对页面里出现的资源几乎是无条件信任的。模板拼接、富文本渲染、第三方统计脚本，任何一处把关不严，攻击者注入的代码就会以当前页面的身份运行，读取 Cookie 与本地存储，再把数据发到自己的服务器。这类问题属于跨站脚本（XSS）的范畴，本文不展开攻击分类，只关心一个防御问题：能不能让浏览器在执行之前就拒绝掉那些不该出现的资源。

Content Security Policy（内容安全策略，下称 CSP）给出的答案是一份白名单。服务器在响应里附带一条策略，声明脚本、样式、图片、字体、框架页面分别允许从哪些来源加载；浏览器在发出请求和执行代码之前逐条比对，不在名单里的直接拦下，并在控制台留下拒绝记录。它把默认全信改成了默认全不信、逐个放行。

这里要先把预期放正。CSP 管的是来源，不是内容：一段同源脚本究竟是业务代码还是被篡改的代码，它分辨不出来；服务端把敏感数据直接写进 HTML，它也拦不住。所以 CSP 是纵深防御中的一层，不能替代输出转义与输入校验，这一点在最后一节还会回到。

版本上，2018 年初 CSP Level 1 与 Level 2 已被 Chrome、Firefox、Safari、Edge 的当期版本支持，Level 3 仍是草案。本文只讲前两级里能放心使用的部分。

从一条最小策略开始

任何 CSP 都从 default-src 开始。它不针对某类资源，而是所有 -src 类指令的兜底：策略里只写 default-src 时，脚本、样式、图片、字体、请求全都按它的值来判断。

'self' 指当前页面的源，也就是协议、域名、端口三者的组合，与同源策略的判断方式一致。所以 https://example.com 页面上的 'self' 不包括 http://example.com，不包括 https://static.example.com，也不包括 https://example.com:8443。

这条策略生效后，页面会出现下面这些变化：

  • 同源的脚本、样式、图片与接口请求照常工作。
  • 外域 CDN 上的脚本、样式、字体被拒绝。
  • 内联 <script> 与 onclick 这类事件属性被拒绝。
  • <style> 块和 style 属性也被拒绝，因为 style-src 继承了 default-src。
  • eval 与 new Function 被拒绝，因为源列表里没有 'unsafe-eval'。

最后一条常被忽略。一些老模板引擎和图表库内部用 new Function 编译字符串，策略一上线就抛 EvalError。遇到这种报错，先查依赖里谁在动态编译，再决定是换实现还是局部放开，不要条件反射地加 'unsafe-eval'。

object-src 'none' 是几乎零成本的加固项，用来禁用 Flash、Java 插件这类可执行对象。default-src 'self' 只保证同源，同源的插件照样能加载，所以单独写一句更稳妥。

还有一个容易误判的地方：并非所有指令都会回退到 default-src。frame-ancestors、form-action、base-uri、report-uri 没有回退关系，不写就是不生效。很多人以为 default-src 'self' 顺便挡住了别人的页面嵌入自己，实际上完全没有。

常用指令与源列表语法

default-src 之后，日常打交道的指令就那么几条，按资源类型分工即可：

  • script-src：JavaScript 的来源，安全上最关键的一条，因为脚本能做的事情最多。
  • style-src：样式表与内联样式。style 属性也受它管，不只是 <link rel="stylesheet">。
  • img-src：图片，含 srcset、CSS 背景图和 favicon。
  • font-src：@font-face 加载的字体文件。
  • connect-src：XMLHttpRequest、WebSocket、EventSource、sendBeacon 的目标地址。前后端分离的项目最常在这里翻车。
  • frame-src：页面里嵌入的 iframe 地址。Level 2 又引入 child-src 统一管 frame 与 worker，两者都写兼容性更好。
  • base-uri：限制 <base href> 能指向哪里，防止有人插入 base 标签把相对路径整体劫持到外域。
  • form-action：表单提交的目标地址，防止注入的表单把用户输入送去攻击者的服务器。
  • frame-ancestors：谁可以嵌入本页，相当于 X-Frame-Options 的现代写法，并且只能写在响应头里。

源列表怎么写

源列表由空格分隔的来源表达式组成，常用的只有几类：

  • 'self'：同源，比较时算端口。
  • 具体域名：https://cdn.example.com，匹配该协议与该主机。
  • 通配符：https://*.example.com 匹配所有子域，但不匹配 example.com 本身；单独一个 * 匹配任意协议任意主机，等于放弃白名单，只适合临时测试。
  • 协议：https: 表示任意 HTTPS 来源，data: 允许 data URI（图片常用），blob: 常见于前端生成文件下载。
  • 端口：https://example.com:8443。不写端口时只匹配该协议的默认端口。

路径匹配要单独说一句。Level 2 起源列表可以带路径，但只能按目录做前缀比较，不支持通配符，也不能指向某个具体文件；历史上还有浏览器忽略路径直接按域名放行的实现。所以别把路径当成路由级白名单，重要资源宁可拆到独立域名。

'none' 是特殊值，表示这一类资源一律不允许，典型用法是 frame-ancestors 'none'。它不能和其他来源并列写：一旦并列，浏览器会忽略 'none'，其余来源照常生效，等于白写。

内联脚本的三种处理

来源列表管不到内联代码：<script>...</script> 之间的内容和 onclick="..." 属性都没有 URL 可供比对，所以默认一律拒绝。这是策略上线后最常见的报错来源。

'unsafe-inline' 是最省事的解法，但在 script-src 里加上它，等于把 XSS 防护的主要收益扔掉：攻击者只要能注入一段 <script> 或一个事件属性，就照样能执行。它有时确实躲不掉，比如老页面遍地内联事件、第三方脚本自己往页面里写内联代码，但至少要把它限制在 style-src 一侧，脚本一侧尽量别用。

更合理的做法是给每段被允许的内联脚本一个身份证明，常见的有两种。

strict-dynamic：让信任沿着脚本传播

nonce 和哈希解决了内联脚本，却解决不了另一类问题：被信任的脚本自己会往页面里插入新的 script 标签，例如异步加载器、广告位、框架的按需加载。这些动态插入的脚本通常拿不到 nonce，会被策略挡下。

strict-dynamic 就是为这个场景准备的。它的语义是：只要一个脚本由已被信任的脚本创建并插入，它就继承这份信任，不再检查来源；与此同时，源列表里的域名与 'self' 对脚本失效，'unsafe-inline' 也被忽略。信任的起点从”哪些域名”变成了”哪段代码”。

这种把新关键字与被废弃的旧白名单写在一起的做法，常被称为新旧双写。兼容性上要留意：当期 Chrome 与 Firefox 已支持 strict-dynamic，Safari 11 与 Edge 16/17 尚未支持，它们会忽略这个关键字，转而按后面的源列表判断。所以如果还要兼容 Safari，动态插入的脚本最好仍带上 nonce。另外，strict-dynamic 放大了被信任脚本的权限：某个带 nonce 的脚本一旦本身有漏洞，它插入的任何脚本都会被放行，信任链条越短越安全。

先收集再拦截：report-uri

直接把强制策略推上生产是有风险的，一条写错的 connect-src 就可能让所有接口请求失败。CSP 提供了只报告不拦截的模式：把响应头换成 Content-Security-Policy-Report-Only，浏览器照常加载资源，只把本该拦截的行为发到 report-uri 指定的地址。

两种下发方式与第三方资源

响应头是首选。<meta http-equiv="Content-Security-Policy" content="..."> 只适合没有后端控制权的场景，比如静态托管页面。两者的差异集中在四处：frame-ancestors、report-uri、sandbox 在 meta 中无效，只能靠响应头；meta 必须位于 <head> 内，且对出现在它之前的资源无效；多份策略同时存在时取交集，只会越收越紧；meta 方式无法覆盖非 HTML 响应。

第三方资源是最常见的冲突源。统计与客服脚本除了加载自身，往往还要回传数据，script-src 放行之后还要检查 connect-src；Web Font 需要同时放行样式表所在域与字体文件所在域；地图、支付 SDK 常会再拉起 iframe，frame-src 也得跟上；data URI 图标与前端预览要用 img-src data: blob:。排查时先看控制台，拒绝信息里会写明是哪条指令、哪个地址被拒；再对照 Report-Only 的报告聚合，通常半小时就能定位到具体依赖。切忌为了消一条报错就加 * 或 https:，那等于让整条策略失去意义。

常见坑与一条收敛路径

先列几个反复出现的坑，它们共同的特点是：策略看起来生效了，实际防护范围比预期小。

  • 'unsafe-inline' 与 nonce 并存。Level 2 规定 'unsafe-inline' 出现时 nonce 与哈希被忽略，于是内联脚本”能跑”，但任何注入的内联脚本也能跑。改完 nonce 一定要把 'unsafe-inline' 删掉再测。
  • 指令拼错。scriptsrc、default 这类未知指令会被静默忽略，控制台未必报警，结果是这类资源完全不受限。上线前用 curl -I 或 Network 面板核对响应头原文。
  • 用逗号分隔指令。CSP 用分号分隔，混入逗号会让浏览器解析失败并丢弃整条策略，页面看起来一切正常，防护为零。
  • 接口全挂。connect-src 未显式声明时会继承 default-src，跨域 API 被拦。正确做法是补一条 connect-src 'self' https://api.example.com，而不是加 *。
  • 多层代理重复添加响应头。nginx 在前面加一次、应用再加一次，浏览器拿到两条策略并按交集执行，会比预期更紧；排查时以最终响应的完整头为准。
  • 报告地址带上了完整 URL。落地页的查询参数、搜索关键词都会进日志，接收端要脱敏。

收敛顺序可以按风险从低到高排：先用 Report-Only 跑一到两周收集真实依赖；接着上几乎没有争议的 object-src 'none'、base-uri 'self'、frame-ancestors 'none'；然后补 default-src 'self' 与 connect-src、img-src 等显式指令；最后才动 script-src，用 nonce 配合 strict-dynamic 替掉内联白名单。每一步都保留 report-uri 观察一段时间，出问题能立刻定位到是哪条指令。

小结

CSP 的本质是一份由服务器下发、由浏览器执行的白名单，它把默认信任改成了默认拒绝，削掉 XSS 中最容易利用的那部分执行路径。入门阶段记住三件事就够了：default-src 是兜底但管不到 frame-ancestors、form-action、base-uri；内联脚本优先用 nonce 或哈希，而不是 'unsafe-inline'；上线先用 Report-Only 收集，再逐步收紧。它是纵深防御的一层，输出转义和输入校验仍然要做。真正难的部分不在指令本身，而在存量代码、第三方脚本与多级代理之间的协调，那属于工程落地的话题，本文不展开。
