前端安全之点击劫持与防护

点击劫持（clickjacking）是一种不需要注入脚本、也不需要拿到密码的攻击：攻击者只用一个透明 iframe，就能让用户在毫不知情的情况下按下某个按钮。本文从攻击原理讲起，先用两个本地 HTML 文件复现一次完整的点击劫持，再逐一介绍 X-Frame-Options 与 CSP 的 frame-ancestors 两种防护手段，包括它们的优先级、兼容性与配置写法，最后给出测试方法和几个常见的坑。读完之后，你应该能为站点选出合适的防嵌套策略，并清楚它何时会失效。

点击劫持：一次看不见的点击

点击劫持的核心只有一句话：让受害页面出现在攻击者的页面里，再让用户以为自己点的是攻击者的按钮。

具体做法并不复杂。攻击者准备一个看起来无害的诱饵页，上面放一个大大的“点击领取优惠券”按钮；然后用 iframe 把目标站点的一个页面嵌进来，把 iframe 设为透明、去掉边框、绝对定位，精确盖在诱饵按钮上方。用户看到的仍然是诱饵，但鼠标落点其实在 iframe 内部，事件被派发给了目标页面上的那个按钮。

浏览器在这里没有任何“被欺骗”的感觉。它不知道用户看到的像素来自哪一层，只知道点击坐标命中了 iframe 里的元素，于是照常执行。如果用户在那个站点上已经登录，请求会自动带上 Cookie，服务端看到的就是一次正常的、已认证的操作。

这也解释了它为什么危险：它不改动目标站点的一行代码，不依赖任何注入点，代码审计和常规的输入过滤都发现不了。攻击者要的也不是数据，而是用户的那一次点击，所以被盯上的按钮通常都带副作用：转账、下单、发帖、点赞、关注、修改密码、给第三方应用授权。

从防御角度看，问题的本质是：我的页面能不能被别人的页面框住。2008 年前后，安全社区开始系统讨论这类攻击，浏览器厂商随后陆续提供了拒绝被嵌套的响应头，这就是后文两条防线的由来。

变体：换一层伪装

上面是最朴素的形态。真实世界里，攻击者会根据目标页面的按钮布局换不同的伪装，思路上都是“让可见的与可点的错位”。

点赞劫持（likejacking） 是较早流行的一种。诱饵被包装成“点击查看大图”“点击领取”“点击投票”，iframe 里放的却是社交平台的点赞、关注或分享按钮。用户处于登录状态，一次点击就能产生一条公开动态，再沿好友关系扩散。2010 年前后，这类攻击在几个大型社交网络上出现过规模不小的传播，之后平台陆续补上了防嵌套头。

光标劫持（cursorjacking） 更进一步，攻击者用 CSS 自定义鼠标指针并配合位移，让假光标画在离真实热点几十像素的位置，用户以为点在“关闭”上，实际点在了“允许”上。它不改变透明层的做法，只是把“视觉与落点错位”做得更隐蔽。

双重嵌套（double framing） 针对的是前端检测逻辑。攻击者让页面 A 嵌入页面 B，B 再嵌入受害页 C，此时 C 的直接父窗口是 B 而不是 A。只检查“我是不是被嵌在别人的页面里”的粗粒度实现，遇到这种结构就容易判断失误。

拖拽劫持 则把“点击”换成“拖放”。HTML5 的拖放事件同样能被诱饵引导，攻击者诱导用户把内容拖进看不见的区域，或把敏感信息从页面里拖出来。防护上依然只能靠“不允许被嵌套”这一条根。

还有一些细节：隐藏滚动条、用 fixed 定位固定住 iframe 的可视区域，或者让诱饵页足够长，把 iframe 藏在折叠线以下再配合滚动。变的都是布景，不变的是“第三方页面被嵌进我的文档”这个前提。

第一道防线：X-Frame-Options

最古老也最省事的办法，是让服务端在 HTML 响应里带一个 X-Frame-Options 头。它只有两个取值值得使用：

DENY 最严格，任何页面都不能把它放进框架，包括自己站内的页面。SAMEORIGIN 稍微宽松一些，只允许同源的页面嵌套。这里的“同源”沿用浏览器一贯的定义：协议、主机、端口三者完全一致，http://www.example.com 与 https://www.example.com 不算同源，子域之间也不算。

还有一个 ALLOW-FROM https://partner.example，本意是给白名单用，但各家支持得很零散、行为也不一致，不要依赖它做业务白名单，需要白名单时请直接看下一节的 frame-ancestors。

多值与无效值是这块最容易踩的坑。有人把两个值用逗号拼在一起，或写错指令，期望浏览器“至少认一个”。实际上各浏览器处理并不统一：有的取第一个值，有的把整条头判为无效后直接忽略。一旦头被忽略，页面就回到可被嵌套的状态。正确做法是一条响应只出现一个合法取值。

IE8 起就支持 DENY 与 SAMEORIGIN，但它对“同源”的判定相对宽松，同站不同端口、不同协议的场景建议实测确认。这也引出了下一节的问题：既然有了 X-Frame-Options，为什么还需要一条 CSP 指令。

第二道防线：CSP frame-ancestors

CSP Level 2 把“拒绝被嵌套”收进了内容安全策略，指令名叫 frame-ancestors。它和 X-Frame-Options 表达的是同一件事，但语法更接近一条来源列表：

'none' 对应 DENY，不允许任何祖先页面。'self' 对应 SAMEORIGIN，允许同源页面嵌套。注意别和 frame-src 搞混：前者管“我的页面能嵌谁”，后者管“谁能嵌我”，方向刚好相反，写反了等于没有防护。

语义上有一点比 X-Frame-Options 更严格：浏览器会检查整条祖先链，只要有一层不在允许范围内，页面就拒绝渲染，而不只是看直接父窗口。攻击者惯用的中转页也被纳入了判断。

两者同时下发时，frame-ancestors 优先级更高。支持 CSP Level 2 的浏览器看到这条指令后就不再参考 X-Frame-Options，所以在响应里同时写两条并不冲突：新浏览器按 CSP 走，老浏览器退回 X-Frame-Options。这也是当下推荐的组合，而不是二选一。

兼容性方面，Chrome、Firefox、Safari 与 Edge 的现代版本都已支持 frame-ancestors，IE11 则完全不认这条指令，既不报错也不生效。考虑到仍有不少企业内网停留在 IE，只发 CSP 等于把老用户暴露在风险里。所以结论很直接：两个头都发，让每一代浏览器都拿到一条看得懂的规则。

还有一个细节：响应里出现多条 Content-Security-Policy 头时，浏览器会把它们同时执行，效果相当于取交集。因此可以在已有策略之外单独追加一条 frame-ancestors。

白名单也很难静态写死：同一个页面，作为独立站点访问时应禁止嵌套，作为组件嵌出时应允许特定祖先。可行的做法是让服务端按请求特征选择响应头，或者提供两个入口，内嵌版走单独域名。前端在运行时无法改变这个决策，方案评审时要说清楚。

但它只是补充，不能当作防护。第一，它依赖脚本执行，攻击者给 iframe 加上 sandbox 属性并去掉 allow-scripts，页面脚本就不运行了，而链接、表单这些不依赖脚本的元素照样能被点中。第二，window.top.location 的跳转会被同源策略和 sandbox 拦住。第三，脚本要等 HTML 解析到它才执行，在此之前页面已经渲染，手快的用户可能已经点下去了。

所以合理的定位是：服务端头负责“不让嵌”，前端脚本负责“被嵌了就装作不存在”，两者叠加能提高攻击成本，但单独使用任意一个都不够。

测试方法与常见坑

验证防护是否生效，最直接的办法就是拿自己写的攻击页去打自己的站点：

  1. 用前面那两个本地页面，先在不加任何响应头的服务上跑一遍，确认确实能点中隐藏按钮，建立基线。
  2. 给受害页面的服务加上头，再刷新攻击页，观察 iframe 是否变成空白。
  3. 打开浏览器控制台，应该能看到类似“拒绝在框架中显示，因为设置了 X-Frame-Options”的报错；这条报错本身就是生效的证据。

小结

点击劫持不注入代码、不窃取凭据，只借用用户的鼠标和已经登录的会话，因此常规的输入过滤发现不了它。防御的根只有一个：拒绝被不可信的页面嵌套。现阶段最稳妥的做法是同时下发 X-Frame-Options: SAMEORIGIN 与 Content-Security-Policy: frame-ancestors 'self'，让新老浏览器各取所需；确实需要被嵌入时，用 frame-ancestors 列出可信来源，并清楚它只能由响应头承载。window.top !== window.self 之类的脚本检测可以保留，但要明白它随时可能被绕过，只能当作补充。上线前用自己搭的攻击页和 curl 各验证一遍，重点检查那些容易被遗漏的中间页与错误页。
