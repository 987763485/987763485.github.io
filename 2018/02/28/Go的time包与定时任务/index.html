Go 的 time 包与定时任务

本文属于《Go 语言与工程》第 26/78 篇
上一篇系列目录下一篇

几乎每个后端服务里都藏着几段“过一会儿再做”的逻辑：五分钟后重试一次支付回调，每三十秒刷新一次缓存，每天凌晨清理过期数据。这些逻辑落到代码上，都绕不开 Go 标准库的 time 包。本文从 time.Time 的内部结构讲起，依次梳理时间单位、格式化与解析、时区处理，再进入 Timer、Ticker 两种原语，最后给出一个可直接改造的进程内定时任务骨架。读者读完应当能判断：什么时候该用 AfterFunc，什么时候必须 Stop 掉 ticker，以及为什么定时任务总是“看起来跑了，其实少跑了一次”。

time.Time 的两套时钟

很多人以为 time.Time 就是一个时间戳，实际上它在 Go 1.9 之后同时保存了两份读数：一份是 wall clock（墙上时钟），也就是我们日常理解的那个年月日时分秒；另一份是 monotonic clock（单调时钟），一个只在本进程内有效、只增不减的计数器。前者会被人为修改、被 NTP 校正，后者不会。

还有一个容易忽略的点：Duration 是 int64，比较可以直接用 <、>；但两个时间点必须用 Before、After、Equal。

时区对象有三个来源：time.UTC、time.Local（进程启动时从系统环境推断）和 time.LoadLocation。LoadLocation 会去读系统的时区数据库，在 Linux 上通常是 /usr/share/zoneinfo 目录。麻烦在于，用 scratch 或精简版 alpine 构建的镜像里往往没有这个目录，LoadLocation("Asia/Shanghai") 会直接返回错误。此时要么在镜像里装上 tzdata 包，要么干脆全链路使用 UTC，只在展示层做转换。笔者倾向于后者：服务端只认 UTC，时区是展示问题，不该渗进业务逻辑。

另外，LoadLocation 涉及文件读取，不要在每次格式化时调用，把它放在启动阶段加载一次、存进包级变量即可。

如果需要提前取消，Stop 返回 false 意味着定时器已经触发但值还没被取走，此时应当做一次非阻塞的排空，再 Reset。在 1.10 上，这是唯一稳妥的写法。AfterFunc 则适合“到点做一件事、不需要中途取消”的场景，它的回调在独立 goroutine 中执行，因此回调内部不能再假设自己处于原来的执行上下文。

Ticker 按固定间隔向通道发送时间值，是进程内周期任务最直接的实现：

这段代码能跑，但有两个前提必须清楚。第一，Stop 不能省。Ticker 不被停止时，运行时会一直持有它，关联的 goroutine 也可能永远阻塞在接收上，进程的 goroutine 数只增不减。第二，Ticker 的通道容量是 1，如果某次处理超过了间隔，后续的 tick 不会排队，而是被直接丢弃。也就是说，tick 的个数不等于任务的执行次数；如果你靠计数来实现“每三次做一次全量刷新”，在负载高的时候这个计数会失真。

由此引出最实用的一条纪律：不要在 ticker 的接收分支里做长任务。

真正的执行放到固定的 worker 里，调度循环只负责“按点敲门”。这样即使某一轮耗时超预期，也不会拖慢调度节奏，更不会让 tick 堆积成雪崩。这与系统级 cron 的思路相同，区别是进程内没有操作系统帮忙去重。

重叠策略其实只有三种，选哪种取决于任务性质：跳过（skip）适合对时效敏感、缺失一轮无关紧要的刷新类任务；排队（queue）适合每次都必须执行、但可以延后的任务，代价是队列可能越来越长；并发（parallel）只适合任务本身无状态且下游扛得住的情况。绝大多数业务任务应该选第一种，因为它把问题暴露在日志里，而不是拖垮系统。

幂等、补偿与夏令时

定时任务一旦上线，最怕的不是“跑得慢”，而是“多跑了一次”或“少跑了一次”。

幂等的做法是给每次执行一个业务上唯一的键。按天执行的任务可以用日期作为键，在执行前先尝试写入一条任务记录，写成功才继续，写冲突说明别的实例或上一轮已经做过。即使不用唯一索引，把结果写成幂等语句也能兜底，例如 UPDATE orders SET settled = 1 WHERE settled = 0 AND id = ?，重复执行不会产生副作用。有外部副作用的操作（发短信、调支付）更要先查后做，或依赖下游的幂等接口。

补偿针对的是失败与错过。失败重试应当有次数上限和退避间隔，time.AfterFunc(backoff, retry) 比在任务里直接 time.Sleep 更好，因为前者不占用当前 goroutine 的调用栈等待。错过执行（misfire）则发生在进程重启、机器故障期间：重启后读一次“上次成功执行时间”，如果发现已经跨过了一个执行点，就补跑一次，但只补最近的一次。盲目补齐历史上所有时间点，往往在下游恢复的瞬间制造一次流量高峰。

夏令时是另一个容易被忽视的来源。在实行夏令时的地区，春季切换当天凌晨两点可能直接跳到三点，于是“每天 02:30 执行”的任务在那一天根本不会触发；秋季回拨时，同一个本地时刻会出现两次，按本地时间调度的任务就会执行两遍。中国目前不实行夏令时，但服务面向海外用户时这个问题真实存在。稳妥的规则是：调度基准统一用 UTC，只在报表展示时换算成本地时间；如果业务确实要求“当地凌晨执行”，就接受它在切换日偏移一小时，而不是试图精确对齐不存在的时刻。

测试时间与常见坑

测试定时逻辑时，最省事的写法往往是 time.Sleep(5 * time.Second) 然后断言，代价是测试变慢且不稳定：机器一忙，五秒可能不够，断言就随机失败。更好的做法有两条。

第一条是把间隔变成可注入的参数，而不是写死在代码里。上面的 Scheduler 已经是这个结构，测试时传入 10 * time.Millisecond，一秒内就能跑完好几个周期。断言不要依赖“睡了多久”，而是用超时保护轮询某个计数器：

第二条是抽出 clock 接口。凡是需要读取“当前时间”的地方，都通过 Now() time.Time 获取，生产实现直接返回 time.Now()，测试实现返回一个可以手动拨动的固定值。这样“跨天”“跨月”这类逻辑不必真的等到第二天，改一行假时间就能验证。

最后把本篇涉及的坑集中列一遍，它们大多不是语法错误，而是逻辑上“看起来对”：

  • 在 for 循环里用 time.After，导致 Timer 不断堆积，应当复用 Timer 并 Reset。
  • 创建 Ticker 后忘记 Stop，goroutine 与运行时资源随重启次数累积。
  • 启动 go sched.Run(ctx) 后不做等待，主进程先退出，任务被拦腰截断。
  • 把 time.Duration 当成秒数传给只接受整数的接口，误差九个数量级。
  • 用 time.Parse 解析不带时区的时间串，结果被当成 UTC。
  • 用 == 比较两个 time.Time，忽略了 loc 指针与单调读数。

小结

time.Time 内部同时保存墙上时钟与单调时钟，前者用于展示与存储，后者用于测量耗时，两者不可混用。Duration 必须带单位；解析不带时区的字符串一定要用 ParseInLocation。Timer 适合一次性延迟，循环中要复用并 Reset；Ticker 是周期任务的底座，必须 Stop，且 tick 会因处理过慢而被丢弃。可靠的定时任务还要补齐三件事：用信号量或分布式锁防重叠、用唯一键保证幂等、用上次执行时间做一次补偿。把这些细节处理掉，进程内调度才配得上“按时执行”这四个字。
