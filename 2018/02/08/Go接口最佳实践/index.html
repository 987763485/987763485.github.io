Go 接口最佳实践

本文属于《Go 语言与工程》第 34/78 篇
上一篇系列目录下一篇

在一次代码评审里，笔者数了一个中等规模服务的接口数量：二十三个接口，对应二十三个实现，其中十九个接口在整个仓库里只有一个实现。这些接口没有带来替换能力，却让调用链多了一层跳转，也让测试多了一堆 mock。本文不重复接口的语法，而是从设计角度回答几个问题：接口应该由谁定义，应该定义多大，什么时候根本不需要接口，以及需求变化时如何扩展而不破坏实现方。读完之后，你应该能在评审里对“这里要不要加一个接口”给出有依据的判断。

接口多，不等于设计好

很多团队对接口有一种仪式感：新建一个结构体，顺手在它旁边放一个同名接口；写一个仓储，先定义 UserRepository 接口，再写 mysqlUserRepository 实现。问起原因，答案通常是“面向接口编程”“方便以后换实现”“方便写单元测试”。这三句话本身没有错，但它们描述的是结果，不是判据。接口是否值得存在，取决于此刻是否真的存在替换需求，而不是取决于未来某天可能存在。

从语言机制上看，Go 的接口是一组方法签名的集合。它描述的是“能做什么”，而不是“是什么”。一个类型只要方法集覆盖了接口的全部方法，就实现了该接口，不需要写 implements，也不需要导入接口所在的包。这种隐式实现带来的是依赖方向上的自由：实现方不必知道谁会使用它，使用方也不必知道实现藏在哪个包。

Render 不关心 w 是文件、内存缓冲区还是网络连接，也不导入它们的包；只要对方有 Write 方法，就能传进来。这正是接口最有价值的地方：把“我需要什么能力”和“这个能力由谁提供”分开，让依赖指向契约，而不是指向某个具体实现。

但隐式实现也意味着编译器不会在类型定义处提醒你“它应该实现某个接口”，检查只发生在赋值、传参、返回值这些使用点上。所以在库代码里，我们常写一行编译期断言：

理解接口值的结构，有助于解释后文的两个话题。一个接口值在运行时由两部分组成：动态类型和该类型对应的值。方法调用要先通过动态类型找到具体实现，nil 判断也要同时看这两部分。这决定了 nil 接口的陷阱，也决定了接口调用相对于直接调用多出来的那一点开销。

接口归使用方所有

既然实现是隐式的，接口就没有任何技术上的理由必须和实现放在同一个包。Go 的惯例是：接口声明在使用它的包里，而不是实现它的包里。这条规则比“面向接口编程”具体得多，也更容易在评审时执行。

这条规则也不能机械地理解成“接口只能出现在业务代码里”。框架与插件的场景中，接口由调用方法的一方定义并导出，实现方是第三方。http.Handler 由 net/http 的服务器调用，所以定义在 net/http；database/sql/driver 里的 Driver 由 database/sql 调用，所以定义在 database/sql。判断标准始终是“谁调用这些方法”，而不是“谁实现这些方法”。把这一点想清楚，就不会在“接口到底该放哪”上反复纠结。

Accept interfaces, return structs 的边界

“参数收接口，返回结构体”是 Go 社区流传很广的一条经验。它的价值在于把抽象放在最需要的地方：函数的参数是接口，调用方可以传自己的类型、适配器或测试替身；函数的返回值是具体类型，调用方拿到完整的方法集和字段，可以取地址、可以嵌入，也能在你新增方法后立刻使用。

这两行签名几乎概括了标准库的偏好。http.Handler 是参数位置的接口，服务器只要求“能处理请求”这一种能力；os.Open 返回具体类型，因为文件句柄除了读写还有大量调用方可能用到的能力。反过来，如果 Open 返回一个只有 Read 的接口，调用方想取文件大小就得类型断言，而断言失败时的行为只能靠文档保证。

返回接口并非绝对禁止。以下情况是合理的：实现要在运行时才能确定，且具体类型属于内部细节，例如工厂根据配置返回短信或邮件通知器；实现可能来自多个包，调用方不应该绑定到其中任何一个，例如 net.Dial 返回 net.Conn，底层可能是 TCP，也可能是 Unix socket；或者返回值本身就是一种长期稳定的抽象句柄。判断的关键是：调用方是否真的只需要这些方法，以及具体类型是否真的应该被隐藏。

两个常见的反例值得警惕。一个包只有一个内存缓存实现，却返回 Cache 接口，调用方想用 Len() 时发现接口里没有，只能改接口或者断言；一个函数接受十二个方法的接口，实际只调用其中一个，测试却要为十二个方法写空实现。前者是过早抽象，后者是接口过大，本质上都是让抽象的程度超过了真实需求。

还有一个边界：包内不导出的辅助函数，参数用具体类型往往更简单，编译器也更容易内联、更容易做逃逸分析。接口应该主要出现在包的边界、依赖注入点和确实需要多态的位置，而不是每一层都铺一遍。至于 interface{}，它不表达任何契约，只适合真正的泛化边界，例如 JSON 解码和格式化输出；拿它当普通参数，等于把类型检查推迟到运行时。

小接口与接口隔离

Go 社区有一句流传很广的话：接口越大，抽象越弱。标准库最常用的接口都小得惊人：io.Reader 和 io.Writer 各只有一个方法，fmt.Stringer 一个，error 一个，sort.Interface 三个且高度内聚。小不是目的，小带来的组合能力才是。

一个方法的接口几乎可以被任何类型接入。io.Copy(dst io.Writer, src io.Reader) 只要求“能读”和“能写”，于是文件、网络连接、内存缓冲、压缩流都能接在一起；json.NewEncoder(w io.Writer) 和 bufio.NewScanner(r io.Reader) 也是同样的思路。接口越小，能匹配的实现越多，调用方能做的组合也越多。

拆分也有一个度。按使用方拆，而不是按方法数量平均切：Get 和 List 都属于“读”，经常一起出现，放在 UserReader 里合理；如果把每个方法都拆成单独接口，调用方就要组合三四个参数，反而更难用。判断依据是“哪些方法总是被同一类调用方一起使用”，而不是“接口看起来够不够小”。

接口污染：为想象中的扩展买单

没有真实替换需求、没有第二个实现、也没有测试边界的接口，就是污染。它不一定写错，但一定在收利息。常见的来源有几类。

第一类是预判式抽象。“以后可能换 Redis”“以后可能换 MySQL”，于是先造一个接口。真到要换的时候，需求形状往往已经变了，旧接口里的方法不是多了就是少了，最后还是要改。第二类是语言习惯迁移。从 Java 或 C# 过来的工程师习惯一个类配一个接口，但那些语言需要显式声明实现，Go 不需要，照搬只有成本没有收益。

第三类是 mock 驱动。为了让 mock 框架能生成代码，先造一个大接口，再让生产代码去实现它。正确的顺序恰好相反：先把使用方需要的接口切小，替身自然就小。第四类是包门面。导出接口、隐藏结构体，看起来 API 很稳定，实际后果是调用方用不到新增方法，作者也不敢给接口加方法，因为那会破坏所有实现方。

第五类是把第三方 SDK 整个包一层。有人把客户端的所有方法抄成一个接口，美其名曰“隔离外部依赖”，测试里再 mock 全套。真正被用到的往往只有三五个方法，包住这几个就够了。

这些接口的代价是复利的：阅读时多跳一层，重构时牵一发动全身，nil 接口和方法集的问题出现得更频繁，运行时还多一次间接调用。最深的一条是，错误的抽象会冻结设计。接口一旦公开，删方法、改签名都是破坏性变更，你会被自己三年前写下的契约困住。

比较务实的做法是：先写具体类型，等第二个实现真实出现，或者测试确实需要一个替身时，再在使用方提取接口。提取时从调用点出发，只包含被调用的方法。重复几行代码不是最大的问题，错误的抽象才是。

方法集、指针接收者与 nil 接口

方法集决定了“谁实现了接口”，而接收者的选择决定了方法集。规则本身很短：值类型 T 的方法集只包含值接收者方法，指针类型 *T 的方法集包含值接收者和指针接收者方法。也就是说，只要接口里的方法用指针接收者实现，就只有 *T 满足接口，T 不满足。

编译器的报错会明确指出 Inc method has pointer receiver。这不是挑剔，而是语义：Inc 要修改接收者，而接口里装的是值的一份副本，修改副本没有意义。同样的原因，[]incrementer{counter{}} 不成立，必须写成 []incrementer{&counter{}}；map 的元素不可取地址，m["a"].Inc() 也不合法，需要先取出来调用，或者在 map 里直接存指针。

由此可以得到几条稳定的习惯。第一，同一个类型不要混用值接收者和指针接收者，混用会让方法集的边界变得难以预测，也会在不经意间复制整个结构体。第二，包含 sync.Mutex、sync.WaitGroup 这类同步字段的类型，一律使用指针接收者，go vet 的 copylocks 检查也会盯着这一点。第三，构造函数统一返回指针，容器统一存指针，接口的满足关系就始终一致，不会出现“这里能编译、那里不能”的割裂。

还有一处与 nil 相关的边界：接口值的比较。两个接口值相等，要求动态类型相同且值相等；如果动态类型本身不可比较，例如切片、map、函数，比较会在运行时 panic。把接口值当作 map 的键之前，先确认它的动态类型是可比较的。

接口嵌入与组合

接口嵌入是把多份契约相加。io.ReadWriter 就是 Reader 和 Writer 的嵌入，任何同时具备读写能力的类型都满足它。嵌入的好处是命名：调用方可以要求“既能读又能写”，而不必在参数列表里写两个接口。

接口嵌入适合能力相加，不适合模拟继承层级。设计组合接口时，要确保被嵌入的方法不重名：同名但签名不同的方法，任何类型都无法同时实现；同名同签名在当前版本里也会在接口定义处被拒绝，不会留到实现阶段才暴露。因此组合出来的接口，方法集应当是清晰、互不重叠的。

结构体也可以嵌入接口，用来复用默认实现或只覆盖部分行为。但它有一个容易忽略的风险：零值看起来可用，实际一调用就 panic。

logger{} 因为嵌入了 io.Writer，方法集里就有 Write，编译器认为它满足 io.Writer，可调用时必然 panic。解决办法是在构造函数里保证依赖非 nil，或者在方法内部判空后回退到 ioutil.Discard。任何时候都不要让一个“半初始化”的对象进入接口。

结构体嵌入结构体则是另一回事：字段和方法会被提升，同深度同名会产生歧义，必须在外部显式定义方法来解决。更重要的是，Go 的嵌入不是继承，没有虚函数分派。外层类型调用被提升的方法时，执行的就是内层类型的那个方法，不会动态地跑到外层的“重写版本”上。把嵌入当成“代码复用”而不是“父类关系”，能避免很多设计上的误会。

最后一条经验：不要为了方便，把 *sql.DB 这类大类型直接匿名嵌入自己的结构体。那会让你的类型凭空拥有几十个方法，既污染 API，也可能意外满足某些大接口。更稳妥的写法是持有一个未导出字段，显式转发真正需要暴露的方法。

用最小接口做测试替身

测试替身大致分三类：stub 返回预设值，fake 提供一个简化但可用的实现，mock 则断言交互过程。Go 社区更常用 fake，原因很实际：接口小，手写一个 fake 只要十几行，不需要引入 mock 框架，也不需要生成代码。

这个 fake 只做两件事：记录发送过的消息，按需注入错误。它的形状完全由 Mailer 决定，而 Mailer 又只包含 Register 真正调用的那一个方法。如果明天 Register 需要发送两封邮件，改动也只是在断言里把 len(m.sent) 改成 2。

反过来，如果一个接口有十个方法，测试替身就要写十个空实现，这时应该先怀疑接口，而不是先去学 mock 框架的语法。测试替身的复杂度是接口复杂度的镜像；替身难写，通常说明契约没有按使用方切开。

标准库已经提供了不少现成的替身，优先使用它们比自己造更可靠。bytes.Buffer 同时实现了 io.Reader 和 io.Writer，适合捕获输出；httptest.NewRecorder() 返回的 *ResponseRecorder 实现了 http.ResponseWriter，适合测试处理器；ioutil.Discard 可以丢弃不需要的输出；net.Pipe 提供一对内存中的连接。这些类型经过大量使用，边界行为比自己写的 fake 更接近真实。

还有两条边界值得记住。不要直接 mock 第三方 SDK 的具体类型，而是在自己的包里定义需要的小接口，再写一个适配器接第三方；测试针对自己的接口写替身，第三方升级时只需要改适配器。也不要为了可测试性把内部字段导出，或者在生产接口里加只有测试才调用的方法；那等于让测试需求污染公开 API，长期成本远高于换一种测试组织方式。

标准库的接口划分：三个案例

标准库是学习接口设计最好的材料，因为它必须在兼容性、性能与可扩展性之间做取舍。下面三个案例分别代表三种典型场景。

第一个是 http.Handler：

它只有一个方法，由服务器调用，所以定义在 net/http，任何类型都可以实现。http.HandlerFunc 让普通函数也能成为处理器，中间件的签名是 func(http.Handler) http.Handler，可以层层包裹。这里的接口同时出现在参数和返回值上，都是合理的：中间件必须能包裹任意处理器，返回接口是它的职责，而不是偷懒。

值得注意的是 http.ResponseWriter 的划分。它本身只有三个方法，分别用于设置响应头、写响应头和写响应体；Flush、Hijack 这些并非所有实现都支持的能力，被拆成了独立的 http.Flusher、http.Hijacker 小接口，需要的人用类型断言探测。这样做有两个好处：包装器和测试替身不必实现自己不需要的能力；将来增加新能力时，也不必修改 ResponseWriter 这个被所有人依赖的接口。

第二个是 sort.Interface：

三个方法共同描述“可排序序列”的最小能力，缺一不可，所以它们内聚在同一个接口里；而排序算法由 sort 包提供，数据结构和算法因此解耦。更有意思的是排序策略的位置：同一个 []Person 可以按年龄排，也可以按姓名排，做法是定义 byAge、byName 这样的切片类型并实现三个方法，而不是给 Person 加一个排序方法。排序方式属于调用点，不属于数据本身。sort.Reverse 则包装任意 sort.Interface 并反转 Less，展示了接口组合的另一种用法。

第三个是 database/sql/driver。这里的接口由调用方 database/sql 定义，由第三方驱动实现，属于典型的插件契约。它没有定义成一个包含几十个方法的大接口，而是按生命周期拆成 Driver、Conn、Stmt、Rows、Tx：Driver 负责创建连接，Conn 管理会话，Stmt 表示预编译语句，Rows 迭代结果，Tx 管理事务。每个角色的方法都不多，驱动作者可以按阶段实现，阅读者也能一眼看出职责边界。

更值得学的是它的演进方式。给 Driver 增加一个方法，会让所有第三方驱动瞬间编译失败，所以标准库选择新增可选接口，例如 driver.Execer、driver.Queryer，由 database/sql 在运行时通过类型断言探测驱动是否支持。支持就走快路径，不支持就回退到通用路径。io.Copy 对 io.WriterTo 和 io.ReaderFrom 的探测也是同一模式。这套“基础接口保持稳定，能力用可选接口叠加”的做法，是公开接口能够长期演进的现实答案。

性能、演进与检查清单

先说性能。接口方法调用与直接调用最大的差别在于目标不确定：编译器要通过接口值里的动态类型找到函数入口，通常也无法把调用内联。在每秒处理大量请求的热点路径上，这种开销值得测量；在普通的业务编排层，它通常会被 I/O 和数据库访问淹没。优化的顺序永远是先测量：用 go test -bench . -benchmem 看每次操作的耗时与分配次数，用 go build -gcflags '-m' 查看变量是否逃逸到堆上。不要凭直觉给所有函数套接口，也不要凭直觉把接口全部拆掉。

另一项成本是装箱。把一个非指针的值赋给接口，会把值复制进接口；如果编译器无法证明这份数据不会逃逸，还会在堆上分配。fmt.Println(v) 这类调用就是典型，参数被装箱成 interface{}。在循环里反复装箱一个大结构体，分配次数会明显上升。设计上的对策不是到处用指针，而是把接口放在包的边界和依赖注入点，热路径内部尽量使用具体类型，避免用 []interface{} 承载数值或高频小对象。

再说演进。给一个已经公开的接口增加方法，是彻底的破坏性变更：所有外部实现、所有测试替身都会编译失败；修改方法签名、删除方法同样如此。即便今天仓库里的实现都在自己手里，明天也可能有插件、有下游服务、有同事的分支。接口越小，未来增加能力的空间越大。

需要扩展时，有三条路可选。定义一个新接口，嵌入旧接口并加上新方法，例如 io.ReadWriter 之于 io.Reader；定义可选的能力接口，让调用方通过类型断言探测，例如 http.Flusher 和 driver.Execer；或者新增函数与构造函数，把新能力放在新入口上。三条路的共同点是：不改老契约，只加新契约。标准库能长期保持兼容，靠的就是这种克制。

最后给一份可以直接带进评审的清单：

  • 只有一个实现，也没有测试替身需求：删掉接口。
  • 接口定义在实现包，使用方被迫导入实现：把接口移到使用方。
  • 接口超过五个方法，调用方只用一两个：按使用方拆分。
  • 参数是 interface{}，进函数立刻断言成具体类型：改成具体类型或小接口。
  • 返回接口但只有一种实现：改成返回结构体。
  • 测试里为十方法的接口写 mock：先拆接口，再写替身。
  • 结构体嵌入了可能为 nil 的接口：构造函数保证非 nil。
  • 把具体错误指针返回成 error：显式 return nil。
  • 为“以后可能换实现”提前造接口：等第二个实现出现。

小结

接口是 Go 里最强的解耦工具，也是最容易被滥用的抽象。判断一个接口该不该存在，先问它是否服务于真实的使用方，而不是想象中的未来。让接口归使用方所有，保持一到三个方法的小尺寸，按调用方的关注点做隔离，用具体类型返回值、用接口接收依赖。测试替身要跟着接口一起小，标准库的划分方式值得反复参照。最后记住两条硬约束：方法集决定谁实现接口，公开接口一旦发布就很难再改。
