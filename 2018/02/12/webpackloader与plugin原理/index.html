webpack loader 与 plugin 原理

配一个 2018 年初的 webpack 3 工程，大多数时候是在抄配置：rules 里塞几个 loader，plugins 里塞几个插件，跑通就行。可一旦遇到“为什么我的 loader 顺序反了”“为什么插件里拿不到产物”，抄来的配置就不管用了。本文从 webpack 3 的构建模型讲起，把 loader 的链式调用、this 上下文、同步与异步写法，以及 plugin 的钩子机制拆开讲一遍，最后各手写一个能跑的 loader 与 plugin。读完你应当能看懂一份陌生的 webpack 配置，也能按需自己造轮子。

一次构建到底发生了什么

要理解 loader 与 plugin，先得知道它们各自站在构建流程的哪个位置。一次完整的构建，可以粗略概括成四步。

第一步是找入口。配置里 entry 声明的文件被当作起点，构建器从它开始读源码，遇到 require 或 import 就顺着依赖继续往下找。第二步是建图。每读到一个文件，构建器就把它登记成一个 module，模块之间的引用关系连起来，就是所谓的 module graph（模块图）。这张图是整次构建的核心数据结构，后面所有的拆包、优化、生成产物，都是在这张图上做文章。

第三步是分块。打包器按入口与异步加载点把模块图切成若干 chunk，一个 chunk 就是“会被打进同一个文件里的一批模块”。第四步是出产物。每个 chunk 经过模板渲染，变成最终写到磁盘上的 asset，也就是 dist 目录里那些 .js、.css、.html。

flowchart TD
    A[entry 入口文件] --> B[递归解析依赖]
    B --> C[module graph 模块图]
    C --> D[按入口与异步边界切分 chunk]
    D --> E[渲染模板生成 asset]
    E --> F[写入 output 目录]

这四步里，loader 只参与第二步的前半段：它负责把“一个文件”变成“一个 JS 模块”，别的不管。plugin 则不同，它可以在整条流程的任意节点上挂钩子，读取甚至改写 module graph、chunk 和 asset。一句话概括两者的分工：loader 管单个模块的翻译，plugin 管整场构建的调度。后面几节会把这个判断讲透。

loader 究竟是什么

打包器的世界里只有一种东西能被引用：JS 模块。可项目里还躺着 CSS、图片、字体、模板文件，它们既不是 JS，也不认识 module.exports。loader 就是填这个缝的：它是一个普通函数，输入是某个资源的文本或二进制内容，输出是一段合法的 JS 源码。

链的执行顺序：从右到左、从下到上

上面那条 use: ['style-loader', 'css-loader'] 最容易让人写反。请记住一个结论：loader 的执行顺序是从右到左（数组从后往前），从下到上（配置从后往前）。css-loader 在右边，所以它先跑；style-loader 在左边，所以它后跑。

这个顺序有它的道理。资源总是先被“翻译”成 JS，再被“接入”页面。css-loader 负责把 CSS 文本翻成 JS 字符串，style-loader 负责把这段字符串塞进一个 <style> 标签。反过来先塞标签，就没有东西可塞了。

flowchart LR
    A[style.css 源文件] --> B[css-loader 把 CSS 转成 JS 模块]
    B --> C[style-loader 生成插入 style 标签的代码]
    C --> D[最终 JS 模块]

值得强调的是，每个 loader 拿到的输入都是上一个 loader 的输出，而不是原始文件。所以写自定义 loader 时不能假设 source 就是磁盘上的内容，它可能已经是别人处理过的中间结果。这一点在排查“我的正则为什么匹配不到”时非常关键。

输入、输出与回调

loader 函数的完整签名有三个参数：source、map、meta。source 是待处理的资源内容，默认是字符串，配上 raw: true 后会是 Buffer；map 是上一个 loader 传下来的 Source Map；meta 是给同一条链上其他 loader 传私货用的附加信息，日常用得不多。返回值最简形式是一段字符串，它会被当作这个模块的最终代码。

字符串之外的输出，就得靠 this.callback 了。它挂在 loader 的 this 上，签名是 callback(err, code, map, meta)，比 return 多了错误位和 map 位。两种写法在语义上并不完全等价：return 只能带回代码，一旦你希望顺带输出 Source Map 或者抛出一个可控的错误对象，就必须用 this.callback。

真正的分水岭在异步。前面的例子都是同步函数，读文件、调接口、跑编译这类耗时操作写在里面会阻塞整个构建。解法是 this.async()：调用它会得到一个与 this.callback 同签名的回调，同时向构建器声明“这个 loader 是异步的，请等我的回调”。

有一处极易出错：调用 this.async() 之后，loader 的返回值会被忽略，你必须显式调用回调。如果异步任务因为异常路径提前返回而忘了调 callback，构建就会一直挂着，不报错、也不结束，只能 Ctrl + C。这是自定义 loader 最常见的一类“卡死”故障。

this 上有哪些能用的东西

loader 里的 this 是构建器注入的 loader context，除了 callback 和 async，还有几个高频成员值得记住。

this.resourcePath 是当前处理文件的绝对路径，this.context 是它所在目录，this.resourceQuery 是路径里问号后面的部分，例如 ?raw。做“按目录决定行为”的 loader 时，用 resourcePath 判断比在配置里堆正则稳得多。

this.query 是 loader 收到的参数。老写法是一段以 ? 开头的查询串，例如 use: 'markdown-loader?pedantic=true'，此时 this.query 就是 '?pedantic=true'，需要自己解析；新写法用 options 对象，this.query 直接就是那个对象。两者都支持，但混着写很容易出错，建议统一用 options。

this.emitFile(name, content) 可以直接往输出目录写一个文件，不经过模块系统。this.addDependency(file) 则告诉构建器“这个 loader 还依赖某个文件”，这样该文件改动时，当前模块会被重新构建——相当于补上构建器看不见的那条依赖边。

这几个 API 都不复杂，真正的门槛是意识到：loader 运行在一个被构建器托管的上下文里，不要用 process.cwd() 猜路径，也不要用 fs.writeFile 往 dist 里写东西。

plugin：在生命周期上挂钩子

loader 只能碰单个文件，想动“整场构建”就得用 plugin。打包器把编译过程切成了一系列命名事件，plugin 的本质就是往这些事件上挂一个函数，事件触发时被调用。

支撑这套机制的是 webpack 3 内部的钩子库 Tapable。它提供几种钩子类型：SyncHook 只能挂同步函数，按顺序依次执行；AsyncSeriesHook 挂的是异步函数，必须等上一个跑完才轮到下一个；还有并行的版本，多个处理函数可以同时开跑。compiler 对象上就挂着这样一组钩子，名字对应构建阶段。

plugin 的写法因此高度统一：一个类，一个 apply 方法。配置里 new 出实例之后，构建器会用 compiler 调用它的 apply。

用 ES2015 的 class 写更清楚，apply(compiler) 里做的事完全一样。webpack 3 的注册方法是 compiler.plugin(名字, 函数)，这一点和网上不少新文章里的 tap 写法不同：Tapable 的新版本把注册方法统一成 tap、tapAsync、tapPromise，同步钩子用 tap，异步钩子用 tapAsync（函数末尾多一个 done）或 tapPromise（返回 Promise）。webpack 4 尚未发布，本文的示例仍按 3 的口径写；如果你在别的项目里看到 compiler.hooks.emit.tapAsync(...)，那是同一套思想的另一种拼写。

同步与异步的区别不只在写法上。挂到同步钩子上的函数如果偷偷做了异步操作，构建器不会等它，构建会带着未完成的状态继续往下跑；反过来，把纯同步逻辑挂到异步钩子上却忘了调 callback，构建同样会停在那里。判断依据很简单：钩子的类型决定你能不能异步，参数的个数决定它等不等你。

边界在哪，坑在哪

用 loader 还是 plugin

判断标准可以压成一句话：只跟一个文件的字节打交道，用 loader；需要跨文件、跨 chunk 或读写产物，用 plugin。比如把 SCSS 编译成 CSS、把图片转成 base64、给 JS 加上 use strict，都是 loader；把所有 CSS 抽成一个文件、给产物打 banner、构建完把文件传到 CDN，都是 plugin。有些需求两边都能做，比如“给每个文件加版权注释”，此时优先选 loader，因为它更简单、只影响命中的文件，不会牵连整场构建。

还有一条建议：先找现成的。loader 与 plugin 生态已相当完整，自写之前先确认官方或社区版本是否覆盖需求，自造轮子的维护成本往往比想象中高。

四个高频坑

第一个是顺序写反。除了 style-loader 与 css-loader 这种典型组合，postcss-loader 必须排在 css-loader 右边（先执行），否则它拿不到 CSS 而是拿到已经变成 JS 的字符串，插件化报错会非常隐晦。记住“右边先跑”，并在改配置时先问一句“后一个 loader 需要什么形态的输入”。

第二个是返回值类型不对。同步 loader 返回 undefined、返回一个对象，或者异步 loader 用 Buffer 拼字符串，都会在后续环节炸掉。最保险的做法是：同步 loader 一定 return 字符串或 Buffer，异步 loader 一定只走 callback，两条路别混用。如果 loader 需要接收二进制（图片、字体），记得在函数上挂 module.exports.raw = true。

第三个是异步没回调。this.async() 之后，任何一条提前返回的分支都必须调 callback，包括 if (!source) return; 这类“什么都没做”的分支——正确写法是 return callback(null, source)。同类错误还有重复调用 callback，它会抛出“callback called twice”之类的提示，看到它就去检查是不是在 try/catch 和正常路径里各调了一次。

第四个是插件里拿不到想要的东西。emit 阶段 compilation.assets 已经齐全，但 stats 还没成型，此时读 compilation.getStats() 得到的是一份不完整的数据；需要完整统计就挂 done，它拿到的才是最终 stats。反过来，在 done 里改产物没有任何效果，因为文件已经落盘。选钩子前先确认“我要的数据在这个阶段生成了没有”，比反复试错快得多。

调试的小手段

自定义 loader 出错时，先在函数第一行打印 this.resourcePath，确认它在处理哪个文件、拿到的是不是预期形态的内容；plugin 则在钩子里打印 Object.keys(compilation.assets)，看清当前阶段有哪些产物。这两个动作几乎没有成本，却能省掉大量猜测。

小结

loader 是把单个资源翻译成 JS 模块的函数，靠 use 数组组织成链，执行顺序从右到左，前一个的输出就是后一个的输入。写 loader 时，同步用 return，异步用 this.async() 并确保回调一定被调用；this 上的 resourcePath、query、emitFile、addDependency 是最常用的四个能力。plugin 则是往 compiler 与 compilation 的 Tapable 钩子上挂函数，apply(compiler) 是唯一入口，emit 改产物、done 读统计、optimize-chunk-assets 加工单文件产物。选型时记住：单文件转换找 loader，全局调度找 plugin；拿不准就看数据边界在哪。最后，任何自定义 loader 与 plugin 都建议配一个最小 demo 单独验证，再往正式项目里接。
