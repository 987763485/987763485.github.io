Go 并发模型：goroutine 与 channel

本文属于《Go 语言与工程》第 33/78 篇
上一篇系列目录下一篇

Go 从诞生起就把并发做进了语言本身：一个 go 关键字就能启动新任务，一个 channel 就能在任务之间传递数据。但语法简单不等于模型简单，笔者见过太多把 goroutine 当线程用、把 channel 当队列用、最后死在死锁或数据竞争上的代码。本文从 goroutine 的调度与开销讲起，依次拆解 channel 的语义、select 的多路等待、context 的取消传播，再落到 worker pool、fan-out/fan-in、pipeline 三种常见模式，以及 -race 的验证方法。读完之后，你应该能判断一段并发代码为什么这样写、哪里会出问题，以及什么时候反而不该用 channel。

并发不是并行

先把两个常被混用的词分开。并发是程序的结构，指把工作拆成若干可以独立推进的任务；并行是执行的状态，指这些任务在同一时刻真的在多个核上跑。单核机器上也可以写出完全正确的并发程序，只是任务在时间片上交替前进；反过来，一个没有并发的程序永远谈不上并行。

Go 的运行时在用户态完成 goroutine 的调度，再把它们多路复用到少量操作系统线程上。同一时刻能执行 Go 代码的线程数由 GOMAXPROCS 决定，Go 1.5 之后它的默认值等于机器可见的 CPU 核数，也可以用环境变量 GOMAXPROCS 或 runtime.GOMAXPROCS(n) 修改。把 GOMAXPROCS 设为 1，程序仍然是并发的：多个 goroutine 会交替运行，遇到 channel 阻塞、系统调用或抢占点时切换，只是不会有两个 goroutine 同时执行。

这个区别解释了很多现象。一个 CPU 密集型的循环把 GOMAXPROCS 调到 1 会明显变慢；而一个等待数据库响应的服务，即使只有单核，也能靠并发撑起成百上千个连接，因为大部分 goroutine 都在等 I/O。运行时会在这些阻塞点把执行权交给别的 goroutine，这也是“用同步的写法得到异步的吞吐”的由来。

容器环境里还有一个当年的坑：Go 1.9 的运行时只认宿主机的 CPU 核数，看不到 cgroup 的 CPU 配额。一个限制 2 核的容器跑在 32 核的宿主机上，GOMAXPROCS 仍然是 32，线程数与调度开销都会偏高。当时常见的做法是在启动脚本里按配额显式设置 GOMAXPROCS，或者引入一个在启动时读取 cgroup 限额的小库。问题的根源不在 Go，而在于“核数”与“可用 CPU 时间”并不是一回事。

最后要提醒的是，并发不是免费的。每多一个 goroutine，就多一份调度与栈的开销；每多一处共享状态，就多一处需要同步的地方。Go 让启动并发任务变得便宜，却没有让并发推理变得便宜。后文的大部分内容，都是在讨论如何把这份推理成本降下来。

goroutine：一个 go 关键字背后

goroutine 是 Go 运行时管理的用户态任务。它不由操作系统调度器直接调度，而是由 Go 自己的调度器安排到操作系统线程上执行。教科书里常把模型简化为 G-M-P：G 代表 goroutine，M 代表操作系统线程，P 代表执行 Go 代码所需的上下文。M 必须先绑定一个 P 才能运行 G，P 的数量就是 GOMAXPROCS。这是一个简化模型，真实的调度器还有全局队列、工作窃取、网络轮询器等机制，但用它理解“为什么 goroutine 便宜”已经足够。

便宜的第一层原因是切换成本。goroutine 的切换发生在用户态，保存和恢复的寄存器与栈信息远少于线程切换，不需要陷入内核。第二层原因是栈。线程栈通常在创建时就预留固定大小，1 MB 到 8 MB 不等；goroutine 的栈从几 KB 开始，随着调用深度按需增长，用完还能收缩。于是同样一台机器，线程只能开几千个，goroutine 可以轻松开到几十万个。

但“能开”不等于“该开”。每个 goroutine 仍然占用栈内存和调度时间，如果它只是阻塞在一个永远不会有人发送的 channel 上，那就是泄漏，后文会专门讲。

go f(x) 的语义有三点值得记牢。第一，f 和参数 x 在当前的 goroutine 中求值，新 goroutine 只负责执行调用；第二，语句立即返回，调用者不会等待 f 结束；第三，f 的返回值会被丢弃，错误必须通过别的渠道传出来。最后一点经常被忽略：go doSomething() 编译能过，但如果 doSomething 返回 error，这个错误就永远消失了。

还有一个特性常让人不适应：goroutine 没有对外暴露的 ID，标准库也没有提供从外部杀死某个 goroutine 的接口。这并非遗漏，而是设计选择——强行终止一个正在修改共享状态的 goroutine，会让程序停留在无法推理的中间态。正确的做法是让它自己检查退出信号并返回，这个信号可以是关闭的 channel，也可以是 context。

channel：同步点，还是队列

Go 的并发哲学常被概括为一句话：不要通过共享内存来通信，而要通过通信来共享内存。channel 就是这句话的载体，它是有类型的管道，一端发送，另一端接收，类型系统保证送进去和取出来的是同一种东西。

用 make(chan T) 创建的是无缓冲 channel。它的语义不是“队列长度为 0”，而是“发送与接收必须配对”：发送方阻塞，直到有接收方准备好；接收方阻塞，直到有发送方送来值。两者在 channel 上会合，值直接从发送方交到接收方手里，中间没有存储。因此一次成功的无缓冲发送本身就是一次同步事件，发送返回时，接收方已经拿到了值。

用 make(chan T, n) 创建的是有缓冲 channel。发送方在缓冲区未满时立即返回，接收方在缓冲区非空时立即返回；只有满了才阻塞发送，空了才阻塞接收。缓冲区是一个异步边界，容量 n 表示“允许发送方领先接收方多少个值”。

这个区别决定了选型。无缓冲 channel 适合表达“交接”：任务必须被某个 worker 接走，生产者才能继续，节奏天然对齐。有缓冲 channel 适合表达“解耦”：生产者可以先把结果放进队列，消费者按自己的速度处理。容量不是越大越好，它实际上是在声明系统允许积压多少工作。容量设得过大，只是把背压问题推迟到内存耗尽的那一刻。

从实现角度看，channel 内部维护一个环形缓冲区、一个发送等待队列和一个接收等待队列，发送与接收的配对、goroutine 的唤醒都在运行时的锁保护下完成。由此可以得出一个容易被忽略的结论：channel 不是零成本的，每次操作都有加锁与调度开销，在高频、小数据量的场景里，它通常比一次普通的互斥锁操作更重。使用它换来的是清晰的同步语义，而不是更快的执行速度。

两个边界行为需要记住。未初始化的 channel 是 nil，对 nil channel 的发送和接收都会永久阻塞，关闭它会 panic；这个看似别扭的特性在 select 里很有用，因为 nil channel 的分支永远不会就绪。另外，channel 是引用类型，赋值和传参复制的是同一个底层结构，不会复制缓冲区里的数据。

关闭、range 与所有权

关闭 channel 的语义经常被误解。close(ch) 表达的是“不会再有新的值从这个 channel 发出”，而不是“销毁 channel”或“清空缓冲”。已经进入缓冲区的值仍然可以被接收，接收完这些值之后，接收方才看到关闭状态。

关闭之后有三条硬规则。接收一个已关闭的 channel 不会阻塞，立即返回元素类型的零值，用 v, ok := <-ch 接收时 ok 为 false；向已关闭的 channel 发送会 panic，重复关闭同一个 channel 也会 panic，关闭 nil channel 同样 panic；for v := range ch 会持续接收，直到 channel 被关闭且缓冲区取空，然后循环自然结束。

第三条规则让 range 成为消费端最常用的写法：发送方在结束时关闭，接收方只管循环，不需要自己判断“还有没有”。反过来，如果接收方用 for { v := <-ch } 而不检查 ok，关闭之后会陷入零值死循环，这是很典型的 bug。

由此引出 channel 的所有权原则：谁发送，谁关闭。发送方最清楚自己什么时候发完，也只有它能安全地关闭；接收方不应该关闭 channel，因为它无法知道是否还有其他发送方。当有多个发送方时，需要引入一个协调者：用 sync.WaitGroup 等所有发送方结束，再由一个单独的 goroutine 关闭 channel。

关闭还有一个不发送任何值的用法：把 channel 当作广播信号。close(done) 之后，所有阻塞在 <-done 上的接收者会同时返回；而向 channel 发送 N 个值只能唤醒 N 个接收者，还可能因为没人接收而阻塞。context 的 Done() 用的正是这个模式。

produce 的参数写成 chan<- int，这是方向类型的一种。Go 允许在类型里标注方向：chan<- T 只能发送，<-chan T 只能接收，chan T 双向。方向类型的价值在于编译期约束：函数体内无法对 chan<- T 做接收，也无法对 <-chan T 做发送，误用在编译时就会暴露。赋值是单向兼容的，双向 channel 可以传给需要单向 channel 的函数，反过来不行；因此把 <-chan T 作为返回值，等于给调用方一个只读视图。

方向类型并不限制关闭操作，向只发 channel 执行 close 是合法的，真正的约束仍然是前面的所有权约定。另外，chan<- <-chan int 这类写法要从左往右读：最外层是只发 channel，元素类型是只读 channel。

select：同时等待多个 channel

select 的语法像 switch，但每个 case 必须是一次 channel 操作。它把“我在等什么”从单个 channel 扩展成一组 channel：哪个先就绪就走哪个分支。

规则有三条。多个 case 同时就绪时，运行时随机选一个，这个随机性是为了避免某个 channel 长期被饿死，因此不能依赖书写顺序表达优先级；没有任何 case 就绪且没有 default 时，select 阻塞，直到至少一个就绪；有 default 时，select 永不阻塞，没有就绪分支就立刻执行 default，这就是非阻塞收发的写法。

还有一处语义容易被忽略：当结果与超时同时就绪时，select 会随机挑一个。如果 channel 带缓冲，超时分支被选中时结果可能已经躺在缓冲区里；如果这个结果持有连接或临时文件，超时分支要负责把它取出来清理。很多 goroutine 泄漏就是这么来的：调用方等到超时就返回了，发送方却还阻塞在无缓冲 channel 上，永远等不到接收者。

select 还有一个不直观但很有用的技巧：把某个 case 的 channel 设为 nil。nil channel 永远不就绪，于是这个分支被“关闭”。比如同时等待结果与取消信号，在取消已经发生后，如果只想等结果，就可以把取消 channel 置 nil。select {} 则是空 select，永久阻塞，通常只用于在 main 里阻止程序退出。

另一类问题不是死锁，而是泄漏：goroutine 阻塞在一个永远不会满足的条件上，既不退出也不报错。

如果函数从别的分支提前返回，那个 goroutine 会永远阻塞在发送上，它占用的栈和它引用的对象都无法释放。泄漏的可怕之处在于累积：每个请求漏一个，几天后就是几十万个 goroutine。

排查手段有几样。开发阶段最直接的是 runtime.NumGoroutine()，在压测前后打印，数量持续上涨就说明有泄漏。程序卡住时向进程发送 SIGQUIT（终端里按 Ctrl 加反斜杠），运行时会打印所有 goroutine 的调用栈；如果接入了 net/http/pprof，访问 /debug/pprof/goroutine?debug=2 也能拿到同样的信息。读栈的技巧是找数量最多的那一种栈，它们通常停在同一个 channel 操作上，顺着栈往上看是谁应该发送或关闭。

预防的原则只有一条：每一个可能阻塞的 channel 操作，都要能回答“谁会来接收、谁会来关闭、如果对方不来了我怎么办”。答不上来，就该引入超时或 context。

用 channel 做信号量与限流

channel 的阻塞特性可以直接当作计数信号量使用。带缓冲的 channel 里放进去一个值，就占用一个名额；取出来，就释放一个名额。因为缓冲区满时发送会阻塞，它天然把并发数限制在容量以内。

这里用 struct{} 而不是 bool，因为空结构体不占内存，语义上也只表示“一个令牌”。把 sem <- struct{}{} 放在 go 之前，主循环会在第 4 个任务处停下，goroutine 总数被压在 3 个左右；如果放在 goroutine 内部，虽然并发执行数仍是 3，但会一次性创建所有 goroutine，任务量大时内存并不划算。

同样的结构可以演变成限流器：按固定间隔向 channel 放令牌，处理请求前先取一个。标准库的 time.Tick 返回一个按间隔发送的 channel，写起来很短，但它创建的 ticker 不会被回收，长时间运行的服务应该用 time.NewTicker 并在退出时 Stop。

sync.WaitGroup 与 channel 的分工需要说清楚。WaitGroup 只回答一个问题：这一组任务是不是都结束了。它不传递返回值，也不收集错误。channel 负责传递数据、结果和取消信号。两者经常一起出现：channel 送结果，WaitGroup 等其他工作完成，最后一个完成的 goroutine 负责关闭结果 channel。Add 的调用时机、计数器复用等细节属于 sync 包的话题，这里不展开，只强调一条：Add 必须在可能调用 Wait 的 goroutine 之前完成，常见写法是在启动每个 goroutine 的循环里 Add(1)。

context：把取消信号传下去

前面几节里的退出信号都是一个 chan struct{}：需要停止时关闭它，所有等待者同时被唤醒。这个模式本身没有问题，问题在于它无法跨层传递。一个 HTTP 请求进来，handler 调用 service，service 调用数据库客户端，任何一层决定放弃时，都需要通知下面所有层。每层自己造一个 done channel，接口会变得难以组合。context 包就是为此设计的，它在 Go 1.7 进入标准库，到 Go 1.9 已经是服务端代码的通用约定。

context 是一棵树。context.Background() 是根，WithCancel、WithTimeout、WithDeadline 从已有 context 派生出子节点。取消父节点会级联取消所有子孙，取消子节点不影响父节点和兄弟节点。每个派生函数都返回一个 CancelFunc，调用它就撤销对应的子节点。

Done() 返回一个只读 channel，取消时被关闭；Err() 说明原因，是 context.Canceled 还是 context.DeadlineExceeded。Done() 返回的 channel 只用于等待，不要向它发送，也不要去关闭它，关闭由 context 自己完成。多个 goroutine 同时等待同一个 Done() 时，关闭会让所有人一起醒来，这就是“关闭 channel 作为广播”的标准用法。

规则不多，但都重要。context 作为函数的第一个参数，命名为 ctx；不要把它存进结构体，也不要让它在函数间“顺便”携带业务参数。WithValue 只适合放请求级别的元数据，比如 trace ID，把它当参数容器会让依赖关系变得隐蔽。不要传 nil，没有上下文时用 context.TODO() 占位。所有 WithTimeout 都必须 defer cancel()，否则即使任务提前结束，定时器也要等到超时才释放，在 QPS 高的服务里会积累成泄漏。

WithTimeout 与 WithDeadline 的区别值得单独说一句。前者用相对时长，后者用绝对时间点。跨服务调用时，上游剩下的时间才是真正有效的预算，把 deadline 一路传下去，比每一层各自设一个超时更合理，否则总耗时会被层层放大。

三种并发模式与错误收集

数据竞争、-race 与自查清单

channel 解决的是通信，不是所有共享状态。只要两个 goroutine 并发访问同一块内存，其中至少一个是写，且两者之间没有建立同步顺序，就构成数据竞争。Go 的内存模型用 happens-before 描述这种顺序：channel 的发送在对应接收完成之前发生，go 语句之前的写在新的 goroutine 开始前发生，锁的解锁在后续加锁之前发生。没有这些边，读到的值就没有保证。

最典型的例子是裸计数器：

counter++ 在机器层面是读、加、写三步，两个 goroutine 可能读到同一个旧值，各自加一后写回，其中一次就丢了。修法有三种：用 sync.Mutex 包住自增，用 sync/atomic 的原子操作，或者让一个 goroutine 独占这个计数器、其他 goroutine 通过 channel 发送增量。第三种是“用通信共享内存”的字面应用，但在这个场景里比锁更啰嗦。

判断该用哪种，笔者的经验是看数据的归属。状态有明确的主人、需要被多处读写时，用锁保护，临界区尽量短；数据在 goroutine 之间传递所有权时，用 channel；只是等待一组任务结束时，用 WaitGroup。把 channel 硬套到计数器上，代码更长，性能通常也更差，因为每次自增都要经过一次调度协调。

竞争不会每次都复现，所以需要工具。-race 是 Go 自带的竞争检测器，编译时插入检查代码，运行时记录内存访问并报告冲突：

报告以 WARNING: DATA RACE 开头，给出两处冲突访问的 goroutine 创建栈与访问栈，按栈就能定位到具体代码。代价是 CPU 和内存都有数倍开销，程序也会变慢，所以只用于测试和预发环境，不要带进生产。它能发现的是“这次运行中实际发生的竞争”，没跑到的那条路径仍然可能有问题，因此单测要尽量覆盖并发分支。

go vet 也值得放进 CI。它的 loopclosure 检查能发现 goroutine 里捕获循环变量的问题，copylocks 能发现复制了包含锁的结构体。这两类错误在 code review 里很容易被忽略，交给工具更可靠。

一份可以照着做的检查清单

写完一段并发代码，笔者通常会过一遍下面几条：

  • 每个 go 语句后面，谁负责等它结束？如果没人等，它是不是泄漏？
  • 每个 channel 由谁关闭？是否存在第二个发送方？
  • 每个可能永久阻塞的操作，有没有超时或取消路径？
  • 共享变量是否都在锁、原子操作或单一 goroutine 的保护之下？
  • 失败路径是否也能走到 close、cancel 和 wg.Done()？
  • 有没有在循环里创建定时器，或者启动没有上限的 goroutine？

这六条覆盖不了所有问题，但能挡住绝大多数线上事故。并发代码的难点从来不是写出能跑的版本，而是让它在超时、取消、部分失败这些边界上仍然可推理。

小结

goroutine 是运行时调度的轻量任务，启动便宜，却没有等待与终止的原语，必须靠 channel、WaitGroup 或 context 组织生命周期。channel 的容量是语义选择：无缓冲表达交接与同步，有缓冲表达解耦与允许的积压量。关闭 channel 表示“不会再有值”，只由发送方或协调者执行，关闭后的接收返回零值，向已关闭的 channel 发送会 panic。select 让一个 goroutine 同时等待多个事件，配合 default 做非阻塞尝试、配合 time.After 做超时，但要注意循环里的定时器开销。context 把取消信号沿调用链传播，所有可能阻塞的操作都应该响应它。最后，channel 不能替代对共享状态的设计，-race 与 go vet 应当成为并发代码的常规检查。
