HTTPS 迁移实践

把一个已经跑了几年 HTTP 的站点整体切到 HTTPS，难点不在装证书，而在切换过程中的顺序、兼容与善后。本文按“选证—签发—配置—续期—跳转—排错”的顺序走一遍，每一步都给出可以直接落地的 Nginx 配置和排查命令。读者最好对 Nginx 的 server 块和 DNS 有基本了解，读完后应当能独立完成一次中小型站点的迁移。

迁移的收益与成本

HTTPS 解决的是三件事：机密性、完整性和身份认证。明文 HTTP 下，链路上任何一跳都能读到 Cookie、表单内容和接口返回，也能在响应里插入脚本；TLS 把这三条同时补上，代价是握手与证书管理。

收益里最容易被感知的是浏览器态度。Chrome 从 56 起就把带密码或信用卡表单的 HTTP 页面在地址栏标成“不安全”，按官方路线图，Chrome 68（2018 年 7 月）会把所有 HTTP 页面都标记出来。Firefox 也在跟进同样的策略。

其次是能力与排名。Google 从 2014 年起把 HTTPS 作为一个轻量排名信号；更实际的是，浏览器只在加密连接上协商 HTTP/2，明文站点不能拿到多路复用和头部压缩带来的收益。

成本也要提前算清：证书申请与续期要有人负责；页面里历史遗留的 http:// 资源要逐个清理；老客户端可能因为不支持 SNI 或只支持 TLS 1.0 而连不上；首字节会多出一到两个 RTT，需要靠会话复用摊薄。这些都是一次性投入，但清理混合内容往往比想象中费时。

证书选型：DV、OV、EV 与 Let’s Encrypt 的位置

按验证强度，证书分三档。

DV（Domain Validation）只验证申请者对域名的控制权，通常通过 DNS 记录或 .well-known 下的文件完成，签发在分钟级。浏览器地址栏只显示锁，不显示组织信息，适合博客、API 和内部服务。

OV（Organization Validation）额外核验组织身份，需要营业执照、电话回访等材料，签发要一到三个工作日。证书主题里带组织字段，但主流浏览器的地址栏对 DV 和 OV 一视同仁，要展开证书详情才看得到差别。

EV（Extended Validation）的验证最严格，卖点是地址栏里的绿色公司名，但各家浏览器的展示策略并不一致，普通访客也很少注意。对内容站和接口服务而言，多付的钱买不到对应的安全增量。

Let’s Encrypt 自 2016 年正式开放后成为主流免费方案，它只签发 DV，有效期 90 天，靠 ACME 协议自动化续期。90 天听起来短，但它本就是为自动续期设计的：续期做对之后，有效期越短，密钥泄露的窗口越小。它不提供 OV/EV，也不适合需要向客户展示组织身份的场景。

2018 年 2 月这个时间点还有个细节：ACME v1 仍是默认协议，v2 计划在 3 月上线，泛域名证书要等 v2 才支持。眼下如果确实需要一张覆盖大量子域的证书，只能购买付费 DV，或者用多张 -d 列出的多域名证书拼起来。

用 Certbot 签下第一张证书

Certbot 有两种常用的验证方式，选哪种取决于 Nginx 的配置由谁维护。

--nginx 插件会读取现有配置，自己加上 443 的 server 块并 reload。它省事，前提是 Nginx 跑在本机、配置路径是标准的，且我们接受工具改动配置文件。如果用的是自行编译的 OpenResty，或者配置由配置管理统一生成，插件经常找不到站点而失败，这时要显式指定 --nginx-server-root 与 --nginx-ctl。

--webroot 不碰 Nginx，只把验证文件写进站点根目录的 .well-known/acme-challenge/ 下，再由 Let’s Encrypt 从 80 端口回源抓取。它适合容器环境和配置受管控的集群，前提是这台机器上有一个真实目录能被 80 端口的 server 块映射，且该路径不会被登录鉴权、404 规则或错误的跳转拦掉。

-d 必须把站点的所有入口域名都列全，漏掉 www 是后面“证书域名不匹配”的常见来源。签发完成后，证书落在 /etc/letsencrypt/live/example.com/ 下，其中 cert.pem 是叶子证书，chain.pem 是中间证书，fullchain.pem 是两者拼接。Nginx 里一律用 fullchain.pem，不要用 cert.pem，原因在证书链那一节会说。

Let’s Encrypt 对同一注册域名在一段时间内的签发数量有上限，调试阶段用 --staging 反复试，确认流程通了再换生产环境，这个习惯能省掉很多等待。

几个参数值得解释。listen 443 ssl http2 是 Nginx 1.9.5 之后的写法，同一个端口上同时提供 HTTP/2，不需要单独再开一个端口。ssl_ciphers 只保留 ECDHE 加 AEAD 的组合，前向保密和性能都更好；如果还要照顾只支持 DHE 的客户端，需要另外用 openssl dhparam -out /etc/nginx/dhparam.pem 2048 生成参数文件并配上 ssl_dhparam。

TLSv1 和 TLSv1.1 之所以还留着，是为了 IE 8、Android 4.x 这类存量客户端。不要凭感觉决定何时关掉它们，打开访问日志里的 $ssl_protocol 字段统计一两周，看到 TLS 1.0 的占比接近零再删。ssl_session_tickets off 是当时的常见选择，因为会话票据的密钥轮换在部分实现里不受控，用共享缓存加会话 ID 更可控。

迁移顺序：双协议并行、301 与 HSTS

迁移最容易出事的地方是顺序，推荐的节奏是：先让 80 和 443 同时对外服务，观察一到两周；确认没有混合内容报错、没有调用方失败之后，再把 80 全量 301 到 443；最后才开 HSTS。

双协议并行期间，用 curl -I 和浏览器开发者工具各看一遍，重点确认静态资源域名、接口域名、第三方回调地址是否都能走 HTTPS。灰度期最值得留意的是那些不在浏览器里跑的调用方：移动端旧版本 App、合作方的服务端回调、监控探针，它们往往把 http:// 写死在代码里，浏览器跳转对它们无效。

301 的写法有几个细节。用 return 301 https://$host$request_uri; 而不是写死域名，这样多域名、预发环境可以共用一份配置；不要用 302，它不传递权重，浏览器也不缓存。健康检查路径要单独放行，否则负载均衡器探活会一直收到 301。

HSTS 通过响应头告诉浏览器“以后只用 HTTPS 访问我”，一旦生效，用户在地址栏输入的 http:// 会在本地被改写成 https://，不再发出明文请求。开启顺序必须渐进：

这里有个 Nginx 的坑：add_header 的继承规则是“子级只要出现同名的 add_header，父级全部不继承”，而不是合并。如果某个 location 里也写了 add_header（比如缓存控制），server 块里的 HSTS 就会在那条路径上消失。稳妥的做法是把安全头写进一个片段文件，在每个需要的层级 include。

至于 preload，它是最后一步，而且原则上是单向的：域名一旦进入浏览器内置列表，要退出得等新版本发布并覆盖存量用户。提交前需要满足 max-age 至少一年、带 includeSubDomains 和 preload 指令，并逐一确认所有子域（包括暂时不用的）都能走 HTTPS，否则等于把自己的子域锁死。

混合内容与证书链：上线后才暴露的两类故障

页面主体已经走 HTTPS，但模板、CSS 或数据库里的富文本还引用着 http:// 的资源，浏览器就会报混合内容。主动内容（脚本、样式、iframe、XHR）会被直接拦截，页面往往表现为样式错乱、接口 404；被动内容（图片、音视频）在当时的浏览器里多数仍会显示，但控制台会警告，地址栏的锁标识也可能消失。用户看到的现象是“网站怪怪的”，而不是一条明确的错误。

命中的大多是可以改成相对路径或 https:// 的链接，http://www.w3.org/2000/svg 这类命名空间声明则不能动。改完之后再在浏览器控制台里过一遍每个页面，特别注意富文本内容和第三方组件动态注入的资源。协议相对写法 //cdn.example.com/a.js 看起来省事，但在非 HTTP 环境（如本地文件、部分客户端内嵌页）会解析成 file://，不建议使用。

CSP 的 upgrade-insecure-requests 可以让浏览器把页面里的 HTTP 子资源自动升级为 HTTPS，配合 report-uri 收集被升级的地址，能作为兜底把遗漏项捞出来；但它只是兜底，真正的修复仍然是改掉资源地址，因为并非所有浏览器都支持这条指令，升级后的地址也未必真的可用。

另一类故障更隐蔽：证书链不完整。桌面浏览器在某个时间点访问过使用同一中间证书的站点，会把它缓存下来，所以本机测试一切正常；但 Android 老版本、Java 客户端、curl 和部分监控探针没有这份缓存，握手时就会报 unable to get local issuer certificate。原因通常是配置里写了 cert.pem 而不是 fullchain.pem，或者把中间证书和叶子证书的顺序拼反了。

-showcerts 会列出服务端下发的整条链：正常应有两张，即叶子证书加中间证书，只有一张就说明中间证书没配。更直接的判断是看输出末尾的 Verify return code：0 表示链完整，20 是找不到本地签发者（缺中间证书），21 是链上某张证书校验失败。也可以把域名交给 SSL Labs 做交叉验证，它会指出链是否完整、是否支持前向保密。

几个反复出现的坑

只配 443，不配 80。 HTTP-01 验证永远失败，续期在三个月后突然中断；同时所有旧书签和邮件里的链接会直接打不开。80 端口要保留，只做验证放行和跳转。

80 上的跳转把验证路径也带走了。 如果 /.well-known/acme-challenge/ 被 301 到了另一个 vhost 的根，验证就会 404。用 location ^~ 放在跳转规则之前，并确认 webroot 目录与 -w 参数一致。

系统时间不同步。 证书校验依赖本地时间，偏差过大时会报 certificate is not yet valid 或已过期。用 chronyc tracking 或 ntpq -p 确认 NTP 正常，容器里尤其容易忽略。

防火墙只放行 80。 现象不是证书报错，而是 curl 一直卡住直到超时，容易误判成网络问题。先在服务器上用 ss -lntp | grep 443 确认监听，再从外部用 openssl s_client 试连。

私钥与证书不匹配。 多半是手工替换了其中一个文件，nginx -t 会报 SSL_CTX_use_PrivateKey 相关的 key values mismatch，改回同一批文件即可。

老客户端不支持 SNI。 Windows XP 上的 IE 和 Android 2.x 在单 IP 多证书的服务器上会拿到默认证书，从而报域名不匹配。这类客户端占比极低时可以直接放弃，但要在访问日志里确认过再决定。

小结

HTTPS 迁移是一次性的工程投入，真正的难点是顺序和善后，而不是签发本身。证书用 Let’s Encrypt 加 Certbot 即可，--webroot 适合配置受管控的环境，--nginx 适合单机小站；无论哪种，都要用 fullchain.pem 并在上线当天跑通 renew --dry-run。切换时先双协议并行，再 301，最后渐进开启 HSTS，preload 留到所有子域都确认之后。上线后盯住混合内容和证书链这两类只在真实客户端上暴露的问题，再给到期时间配一个独立告警。
