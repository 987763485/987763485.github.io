TypeScript 与 Vue 2 结合

Vue 2 的模板与选项对象之间没有编译期约束，字段改名、层级变化、拼写错误往往要等到运行时才暴露。本文讲清楚怎样把 TypeScript 接进一个 Vue 2 项目：两种组件写法如何取舍、vue-class-component 与 vue-property-decorator 怎么用、.vue 文件如何被 TypeScript 识别、构建与 tsconfig 要改哪些地方。读完可以在一份存量项目里落地一条可回滚的迁移路线。

为什么 Vue 2 项目需要 TypeScript

Vue 2 的核心是模板加选项对象。模板里写 {{ user.name }}，脚本里写 data() { return { user: {} } }，两者之间没有任何编译期约束：字段改名、层级变化、拼写错误，都要等到运行时才在控制台看到 Cannot read property 'name' of undefined。项目小的时候这不算问题，组件超过几十个、data 字段几十项之后，模板与脚本之间的“隐式契约”就成了维护成本的主要来源。

TypeScript 补的正是这段契约。把 user 声明成 User 接口，脚本里访问不存在的字段会立刻出现红色波浪线；重构时把 userName 改成 nickname，编辑器能列出所有引用点；调用子组件时，@Prop 声明的类型既是文档，也是补全来源。

还有两个常被忽略的收益。其一是接口即文档：后端返回的字段、Vuex 里的状态形状，写成 interface 之后，新同事不必翻三个文件猜数据结构。其二是渐进性：单文件组件可以逐个加 lang="ts"，没改完的 .js 组件照常工作，这让“引入 TS”从一次大重构变成一条可以排期的迁移路线。

需要先把边界说清楚：Vue 2 的模板在 2018 年初还没有官方的模板类型检查，类型安全主要覆盖脚本部分。指望“模板里写错变量也编译报错”并不现实，这一点要和团队讲明白，否则期待落空。

举个最常见的例子：列表页把 list 改成 items，模板里漏改一处，开发环境可能因为数据恰好为空而不报错，上线后用户一操作就白屏。类型检查覆盖不到模板，但至少能让脚本里的每一处引用在重命名时被编辑器标出来，把问题拦在提交之前。

两种写法：选项式加标注，还是类组件

第一条路是保留原来的选项对象，用 Vue.extend 声明组件，让 TypeScript 去推断 this：

Vue 2.5 的类型定义借助 ThisType 把 data、computed、methods 合并进 this，所以 this.count、this.doubled 都有类型。代价是 data 必须显式标注返回类型，否则空数组会被推断成 never[]。

第二条路是类组件：用 vue-class-component 把组件写成一个继承 Vue 的类，data 是类的属性，methods 是类的方法，computed 是 getter。这种写法更像“普通 TypeScript”，Props、事件等选项也能用装饰器表达，因此在 TS 场景下更常被推荐。

两者的取舍并不复杂：新项目、团队接受装饰器语法，选类组件；存量项目、只想先拿到类型而不动结构，选 Vue.extend。同一个项目里两种写法可以共存，但不建议在同一个组件里混用两套 data 声明。

类组件不是没有成本。它依赖装饰器语法，没接触过类似写法的同事需要适应；类的继承会带来 this 指向、父类钩子与子类钩子执行顺序的问题；Vue.extend 的推断虽然弱一些，但和现有代码、社区示例完全一致，排查问题时搜到的答案可以直接套用。选择之前先看团队的平均熟悉度，不要只因为“看起来更像 TypeScript”就上类组件。

规则很简单：@Component 装饰的类，实例属性成为 data，原型方法成为 methods，getter/setter 成为 computed，created、mounted 等钩子按同名方法识别。@Component({...}) 的参数就是原来的选项对象，components、filters、name 都可以照旧放进去。

有两个细节值得强调。第一，data 属性必须有初始值：todos: Todo[] = [] 既给了类型，也保证属性真的出现在实例上；只写 todos: Todo[] 不赋值，运行时很可能拿不到这个字段。第二，不要在类里再写 data()：类组件不接受 data 选项，两种声明只能选一种。

在 @Component 里注册子组件时，直接写 components: { TodoItem } 即可，导入的类本身就是组件选项。生命周期钩子按方法名注册在实例上，子类没有重写时会沿用父类的实现；一旦重写同名钩子，父类那一份不会自动执行，需要两段逻辑都跑时，在子类方法里显式调用 super.created()。mixin 与钩子的合并仍按 Vue 2 的选项合并策略走，和选项式组件一致。

它的含义是：任何以 .vue 结尾的导入，默认导出的类型都当作 Vue 实例。这能消除报错，也带来一个必须知道的局限：父组件拿到的类型是宽泛的 Vue，子组件的 Props 不会被检查。Vue 2 时代没有官方的单文件组件类型导出，想守住父子契约，只能在子组件内部用 @Prop 保证，或在父组件里手动断言。这是当时工具链的真实边界，不必假装它不存在。

配套的 tsconfig.json 要包含 .vue 里的脚本，include 写 src/**/*.ts 与 src/**/*.vue；allowSyntheticDefaultImports 必须打开，否则 import Vue from 'vue' 会报“模块没有默认导出”。

单文件组件里要写成 <script lang="ts">，vue-loader 才会把脚本块交给 TypeScript 规则；漏了 lang，文件仍按 JavaScript 处理，类型标注会直接变成语法错误。模板部分不受影响，照常写。

逐项说：experimentalDecorators 必须为 true，否则类组件根本编译不过；target 用 es5，把降级交给 ts-loader 或 Babel，保证 IE 11 能跑；module 用 es2015，把模块交给打包器处理，才能做 tree shaking；strict 建议新项目直接开，存量项目先开 noImplicitAny，strictNullChecks 留到迁移后期。lib 里要带 dom，$refs、事件对象都依赖 DOM 类型；es2015 提供 Promise、Map 等类型。sourceMap 让浏览器里的断点能落回 .ts 源文件。

transpileOnly: true 关掉 loader 内的类型检查，构建会明显变快，代价是错误只剩编辑器里能看到。补救办法是把检查挪到独立进程，2018 年初常见的组合是 fork-ts-checker-webpack-plugin：它复用同一份 tsconfig，在旁路线程里跑 tsc，把错误回显到终端。插件的具体版本按当时的生态选即可，思路是“转译与检查分离”。

另外两个小项：resolve.extensions 要加 .ts，否则 import './utils' 找不到文件；规则顺序不能反，.vue 必须先由 vue-loader 接手，脚本块才会流到 ts-loader。热替换方面，改文件后如果整页刷新，先确认 devServer.hot 与 HotModuleReplacementPlugin 都开了，再检查 .vue 有没有被别的规则抢走。

CI 里再补一条 tsc --noEmit，用同一份 tsconfig 做全量检查，防止有人绕过编辑器直接提交。它和旁路检查不冲突：开发时求快，合入前求全。

渐进迁移的顺序与常见坑

迁移顺序建议从“依赖少、影响面小”的一端开始：先工具函数与常量（纯 TS，最好改），再 Vuex 的 store 与 module（类型收益最大），然后叶子组件（Props 简单），最后容器组件与路由层。每一步都能独立提交、独立回滚，团队不必停下手上的需求。

共存规则有两条：.js 组件可以照常被 .ts 组件导入，.vue 的 lang 属性决定这个文件走哪条编译链；但同一个组件内不要既写 data() 又用类属性，两套 data 声明会互相覆盖。

工具链上还有一件小事：编辑器要装 Vetur 这类插件，才能高亮并检查 .vue 里的 TypeScript。团队统一插件与 tsconfig 之后，才能保证“我这儿有红线、你那儿也有”。迁移初期建议把 noImplicitAny 作为 CI 门禁，strict 全量打开放到最后，避免一次冒出几百个错误，把迁移节奏打乱。

还有一个边界值得写进团队规范：类组件适合有内部状态与交互的组件，纯展示组件不必强行改成类；functional: true 的组件在类型上更接近一个带 Props 的函数，用 Vue.extend 或 render 函数写反而更直接。

几个反复出现的坑：

  • 忘了 experimentalDecorators。报错是 “Experimental support for decorators is a feature that is subject to change”，很多人第一反应去查装饰器语法，其实是编译选项。
  • 在类组件里用箭头函数定义“方法”。箭头函数是实例属性，会被当成 data 收集，虽然能调用，但语义混乱，每次实例化都新建一份函数，也影响继承。方法就用普通方法，需要固定 this 时在钩子里处理。
  • 选项式写法里 data() { return { list: [] } } 推断出 never[]，要写成 list: [] as Item[]，或者给 data 标注返回类型。
  • 父组件传错 Props 不报错，误以为“TS 没生效”。其实是 .vue 的模块声明把组件类型放宽了，属于已知边界。
  • 热替换下类组件偶尔状态错乱，先排查有没有模块级的可变变量被复用，热替换不会重置模块作用域。
  • @Prop({ type: Array, default: [] }) 让多个实例共享同一个数组，数组与对象的默认值必须写成工厂函数，这一点和选项式写法相同。

小结

Vue 2 接 TypeScript 的核心不是把代码写得多“类型化”，而是让模板与脚本之间那份隐式契约显式化。存量项目可以从 Vue.extend 起步，新组件再逐步换成 vue-class-component 加 vue-property-decorator。shims-vue.d.ts 负责让编译器认识 .vue，但它不检查父子组件的 Props，这个边界要提前和团队对齐。构建上把 ts-loader 的转译与类型检查分开，用 transpileOnly 换速度、用独立进程换正确性。最后，迁移按“工具函数、store、叶子组件、容器组件”的顺序推进，每一步都可回滚，比一次性重写可靠得多。
