yarn 与 npm 包管理对比

从 2017 年下半年开始，前端项目里的 yarn.lock 越来越多，很多人第一次接触 yarn 是因为同事说”它装得快”。但装得快只是表象，真正影响协作的是锁文件、依赖解析结果和 CI 上的一致性。本文从包管理器的工作流程讲起，逐项对比 npm 5.x 与 yarn 1.x 的行为差异，最后给出团队选型与避坑建议。

包管理器到底在做什么

不少人对 npm 与 yarn 的印象停留在”哪个装得快”，但两者解决的是同一个问题：把一份声明式的依赖清单，还原成一棵可复现的 node_modules 树。拆开这条流水线，锁文件、缓存与离线模式才有落脚点。

一次完整的安装大体分四步。

第一步是解析依赖树。package.json 只写直接依赖和版本范围，例如 "react": "^16.2.0"，而 react 还依赖 loose-envify、prop-types，后者又有自己的依赖。包管理器要递归读取每份 package.json，并对同一个包的多条版本范围做出裁决：能复用就复用，不能复用就并存。这一步决定最终装哪个版本，也是两个工具结果可能不一致的根源。

第二步是下载 tarball。registry 提供元数据 JSON 与每个版本的 .tgz，元数据记录了依赖列表、bin 入口、文件摘要等；包管理器据此决定取哪些包，并放进本地缓存避免重复下载。

第三步是写 node_modules。解压之后还要在 node_modules/.bin 下建立可执行文件的软链接，npm run 里的脚本才能直接调用本地 CLI，同时校验 peerDependencies 并打印警告。目录结构上，npm 3 之后改为”尽量扁平”：能提升到顶层的依赖就提升，冲突时才在包内部再套一层。这也解释了”我明明装了新版本，运行时却还是旧的”——被加载的可能是内部嵌套的那一份。

第四步是生成锁文件。把本次真实解析出的版本号、下载地址和完整性校验值固化下来，下次安装照单执行，不再重新计算版本范围。

把这四步类比成编译，package.json 是源码，锁文件是中间产物，node_modules 是产物目录。两者的差异几乎都能放回这条流水线解释：谁先并行、缓存放哪、锁文件长什么样、解析是否稳定。

npm 5 带来了哪些变化

npm 5 随 Node 8 一起分发，这也是 2018 年大多数新项目默认就在用 npm 5.x 的原因。它对前四步中的三步都做了改动，值得单独梳理。

最受关注的是 package-lock.json 默认生成。npm 4 及以前，锁文件要靠 npm shrinkwrap 手动产出，名字还叫 npm-shrinkwrap.json。npm 5 之后，每次 npm install 都会写出 package-lock.json，”本地能跑、CI 上装出别的版本”的问题第一次有了通用解法。

第二个变化是 --save 成了默认行为。npm 4 里 npm install lodash 只把包放进 node_modules，不写进 package.json，忘了加 --save，别人安装时就缺这个包。npm 5 反过来做：安装即写入 dependencies，开发工具则配 --save-dev。这个细节消灭了一类”我本机有、别人装不上”的故障，也是照旧教程操作时最容易困惑的地方。

第三个变化在缓存与下载。npm 5 重写了缓存层，npm cache verify 可以校验缓存完整性，npm cache clean --force 用于强制清理；安装过程也做了并行化，体感比 npm 4 快。速度受网络与包数量影响极大，这里不做定量比较，只提醒一句：如果团队还停在 npm 5.0 或 5.1，建议先升到 5.4 以上，早期版本的锁文件生成规则经过几轮修补才趋于稳定。

yarn 1.x 的卖点

yarn 在 2016 年由 Facebook 开源，2017 年 9 月发布 1.0。它的动机是解决当时 npm 的几个痛点：安装慢、结果不确定、输出啰嗦，因此每个特性几乎都对准了一条具体抱怨。

yarn.lock 是它的核心。yarn 从第一天就把锁文件当必需品：yarn install 一定生成 yarn.lock，内容经过排序，同一份依赖在不同机器上产出的文本几乎逐行一致。锁文件冲突是团队最常见的合并冲突之一，格式稳定能显著减少无意义的差异。

并行下载是第二个卖点。npm 早期版本对依赖树的下载偏串行，包一多，网络往返就积少成多；yarn 把请求并发发出去，并用本地缓存短路下载过的包，热安装场景提升明显。这里同样不做秒数比较，结果高度依赖 registry 的响应速度与网络质量。

离线缓存是第三个卖点。yarn 把包缓存到全局目录，yarn install --offline 完全跳过网络，只用缓存完成安装。对 CI 而言可以把缓存目录挂载复用，对内网环境而言装依赖不再必须连外网。npm 5 也有缓存，但当时没有等价的严格离线开关，只能靠 --prefer-offline 间接减少请求。

第四个卖点是输出。yarn 用简洁的树形结构列出每个包的状态，失败时直接给出错包名与建议命令；npm 5 以滚动进度行与警告堆叠为主，日志一长就很难定位。这类差异不影响正确性，但天天用的人会在意。

两种锁文件的格式差异

锁文件的目标相同：把”这次装了什么”写成确定性记录；但两者结构不同，理解它才知道冲突该怎么处理。

package-lock.json 是 JSON，顶层有 name、version、lockfileVersion，数据在 dependencies 里。每个包一条记录，含版本、下载地址、完整性校验值和 requires；嵌套依赖放在该包的 dependencies 子对象中，与磁盘上的嵌套结构对应。

yarn.lock 则是一种自定义的类 YAML 文本格式，以”包名@版本范围”为键，下面缩进列出 version、resolved、integrity 和 dependencies。同一个包被多个范围引用时，会写成一行逗号分隔的复合键，因此文件更紧凑，也更适合逐行审查。

两种格式字段相近，差别在可读性与冲突粒度。JSON 结构固定，冲突常落在相邻的大段文本上，要小心括号配对；yarn.lock 的块状结构让冲突局限在某个包的一小段里，更好合并。

关键问题是能否混用，答案是不能。npm 不读 yarn.lock，yarn 也不以 package-lock.json 为依据；两者各按自己的算法解析，同一份 package.json 很可能装出不同的间接依赖，而 node_modules 只有一个目录，结果是谁最后装谁说了算。团队只能保留一个锁文件：用 npm 就提交 package-lock.json 并在 .gitignore 里排除 yarn.lock，反之亦然。用哪个取决于团队实际执行安装的那条命令，而不是谁的 README 写得更漂亮。

迁移的正确顺序是：删掉 node_modules 与旧锁文件，重装生成新锁文件，本地跑一遍构建与测试确认版本变化可接受，再一次性提交。最怕留着两把锁、两套工具交替使用，锁文件互相覆盖。

依赖类型与版本范围

锁文件解决”装哪个版本”，package.json 的字段则决定”这个包在什么场景下需要”。四个字段的语义经常被混用，尤其是 dependencies 与 devDependencies。

dependencies 是运行时依赖，构建产物或线上服务真正会加载的包，例如 UI 框架、工具函数库、后端 Web 框架。devDependencies 只在开发与构建时需要，例如打包工具、测试框架、代码检查工具。区分它们有两条实际意义：一是 npm install --production 只装 dependencies，部署镜像能小一大截；二是作为库发布时，使用者只会连带安装你的 dependencies，把测试框架写进去会让下游平白多装几十个包。

peerDependencies 表达”我与某个宿主包配合工作，但版本由使用方提供”。典型场景是插件：react-router 要求 react，eslint-config-airbnb 要求 eslint。npm 3 之后不再自动安装 peer 依赖，只在不满足时打印警告，yarn 1.x 同样只警告。因此看到 UNMET PEER DEPENDENCY 不能当噪声忽略，它往往意味着两份 React 同时存在于依赖树中，运行时会出现组件读不到 context 之类的异常。

optionalDependencies 是”装不上也不该失败”的依赖，比如某些带原生编译的包。安装失败时包管理器会跳过而不是中断整次安装，代码里需要自己做能力检测。

版本范围决定第一步解析的自由度。^1.2.3 允许升到 1.x 的最新版，不跨大版本；~1.2.3 只允许补丁位变动，即 1.2.x；写成 1.2.3 则锁死。* 与 latest 应尽量避免，它们让安装结果随发布时间漂移。实践中的共识是：应用项目对直接依赖用 ^，享受补丁与次版本修复；库项目可以放宽，但要意识到使用者会解析出比你测试时更新的版本。无论范围怎么写，锁文件都会把实际结果固定成精确版本——范围是”允许什么”，锁文件是”这次用了什么”。

常用命令、缓存与离线

两者的命令几乎一一对应，差异主要在参数名与默认行为。下表是笔者最常查的一组。

操作 npm 5.x yarn 1.x
安装全部依赖 npm install yarn install
新增运行时依赖 npm install lodash yarn add lodash
新增开发依赖 npm install jest --save-dev yarn add jest --dev
移除依赖 npm uninstall lodash yarn remove lodash
升级到范围内最新 npm update yarn upgrade
安装指定版本 npm install lodash@4.17.5 yarn add lodash@4.17.5
全局安装 npm install -g vue-cli yarn global add vue-cli
执行脚本 npm run build yarn run build 或 yarn build
执行本地 CLI npx <tool> yarn run <tool>
列出过期依赖 npm outdated yarn outdated

两点值得说明。其一，npm install 与 yarn add 并不对齐：npm 的 install 既能装全部也能装一个，yarn 把这两件事拆成 yarn install 和 yarn add。把 yarn install lodash 当成”装 lodash”是常见错误，yarn 会把它当作多余参数忽略或直接报错，装包必须用 yarn add。其二，yarn build 是 yarn run build 的简写，而 npm build 属于内部命令，脚本里写全 run 更稳妥。

命令熟悉之后要看缓存，它是速度的来源，也是离线能力的边界。npm 5 的缓存放在用户目录的 _cacache 里，按内容寻址存放 tarball 与元数据；npm cache verify 校验并清理无效条目，npm cache clean --force 整个清空。--prefer-offline 表示能用缓存就不发请求，但元数据过期时仍会联网，因此它只是”尽量省流量”，不保证离线可用。

yarn 的缓存更显式：yarn cache dir 打印目录，yarn cache list 列出缓存内容，yarn cache clean 清空。离线安装靠 yarn install --offline，它不发起任何网络请求，缺包时直接失败并指出缺的是哪个。

这带来一个常被误解的点：--offline 不等于”永远能离线”。以下情况一定失败：锁文件里是 git 地址或直接 tarball URL；缓存被 yarn cache clean 清过；换了 Node 版本或操作系统，带原生插件的包需要重新编译；项目新增了从未下载过的依赖。因此用在 CI 上要配缓存目录持久化，用在发布机上要保证缓存预热过，否则只是把网络问题变成更难排查的安装失败。稳妥的做法是本地用默认模式，网络不稳定时再退到 --offline 诊断，而不是把它写进默认脚本。

workspaces 与多包仓库

一个仓库里放多个包（组件库、工具函数、示例站点）时，逐个目录 npm install 会重复下载，本地包互相引用还得靠 npm link 手工连接，改一行源码就要重新 link。yarn 1.x 的 workspaces 就是为这个场景设计的。

与 lerna 的关系可以概括为：lerna 负责版本号、变更日志与发布，workspaces 负责依赖安装与本地链接，两者常配合使用，lerna 也可以把安装交给 workspaces 完成。是否需要 lerna 取决于是否要批量发版，其用法不在此展开。

团队选型与常见坑

选型不必纠结”谁更快”。真正影响日常的是三件事：结果一致性、CI 成本、以及出问题时的排查手段。

一致性靠锁文件，与选哪个工具无关：锁文件入库、安装以锁文件为准、升级走显式命令，结果就可复现。CI 上建议固定缓存目录（npm 的 _cacache、yarn 的 yarn cache dir），并打印实际使用的版本，npm -v 与 yarn -v 不同，解析结果就可能不同。私有 registry 在根目录的 .npmrc 里配置，yarn 同样读这个文件。至于 pnpm 这类内容寻址方案，本系列另有专文。

常见坑按出现频率排序：一是混用，两个锁文件并存、两套命令交替执行，谁最后跑谁生效；二是只删 node_modules 不删锁文件，重装仍按旧锁还原，误以为已经清理干净；三是全局包与本地包混淆，npm install -g 装的 CLI 与 node_modules/.bin 里的不是同一个；四是照着 npm 4 时代的教程到处加 --save，在 npm 5 里已是冗余；五是锁文件冲突时只挑一边保留，正确做法是先解开 package.json 的差异，再重装让工具重写锁文件并提交。

小结

锁文件是 npm 与 yarn 共同的核心，也是团队协作的真正抓手。npm 5 补上了默认锁文件与缓存改进，让”不用 yarn 也能复现安装结果”成为现实；yarn 的优势则集中在命令输出的可读性、离线安装和 workspaces。至于选哪个，选一个并让全团队、CI 配置和文档保持一致，比选哪个本身更重要。
