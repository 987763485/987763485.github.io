TypeScript 类型断言与类型守卫

本文属于《TypeScript 学习路线》第 7/74 篇
上一篇系列目录下一篇

类型断言与类型守卫是 TypeScript 里最容易被混用的两个概念：前者让编译器闭嘴，后者让编译器相信。本文从语法和运行时行为出发，说明 as T、<T>expr、非空断言各自做了什么、代价在哪里，再逐一讲清 typeof、instanceof、相等比较与自定义守卫的收窄规则。读完之后，你应当能在”这一行该写断言还是该写守卫”这个问题上给出有依据的判断。

类型断言的两种写法

TypeScript 提供两种断言语法，as T 与尖括号 <T>expr。两者在类型层面完全等价，区别只在书写位置：尖括号写在表达式前面，as 写在后面。由于 .tsx 文件里的尖括号会被当成 JSX 标签解析，社区普遍推荐统一使用 as，本文后续示例也只用这一种。

断言做的事情只有一件：告诉编译器”这个值的类型我比你清楚”，编译期把类型替换成你写的那个，运行时不生成任何代码。它不会调用构造函数，不会做拆箱装箱，不会遍历原型链，也不会校验字段。这一点必须记牢，否则很容易把断言当成类型转换来用。

编译器对断言并非完全不设防。它要求断言的源类型与目标类型之间存在重叠，也就是其中一方可以赋值给另一方，否则会报 “Neither type … is assignable to the other”。这条规则拦得住 "hello" as number 这类明显错误，却拦不住结构相近的类型，也拦不住经由 any 的中转。

还有一处常被忽略：断言只影响使用处的静态类型，不改变值本身。写 (x as any).foo() 能通过编译，但运行时是否真的有 foo，取决于那个对象的真实形状。如果它是 undefined，报错照样发生，只是编译器不再提前提醒你。

any 在断言里扮演”万能通行证”的角色：任何类型都能断言成 any，any 也能断言成任何类型。于是 as any 成了最常见的消音手段，也成了后面要讨论的风险源头。

JSON.parse 的返回类型是 any，断言把它”承诺”成 User。如果后端返回 {"id": "1", "name": "ann"}，id 运行时是字符串，下游调用 user.id.toFixed(2) 就会抛 TypeError: user.id.toFixed is not a function。这个错误发生的位置离出错的位置很远，排查成本很高。

断言与守卫在这里的差别是本质性的：断言的成本为零，风险留给运行时；守卫的成本是几行检查代码，换来的是类型与实际数据一致。工程上的折中做法是在边界处校验一次：HTTP 响应、localStorage 读出的字符串、postMessage 传来的对象，都用守卫检查后再进入内部逻辑，内部再放心使用断言。

! 非空断言与 strictNullChecks

非空断言写作表达式后面的 !，作用是告诉编译器”这个值不是 null 也不是 undefined“，从而从类型里剔除这两个成员：

它的意义完全依附于 strictNullChecks。这个选项关闭时，null 和 undefined 本来就可以赋值给任何类型，! 写了也等于没写；只有打开严格空检查，string | null 才是一个真实存在的联合类型，! 才有东西可剔除。所以在没有开严格空检查的项目里看到满屏的 !，多半是从别处抄来的代码。

! 适合的场景很有限，但确实存在：构造函数里按固定顺序赋值的字段、页面初始化后必然存在的 DOM 节点、紧跟判空之后的重复访问。判断标准是”这里的不为空由代码结构保证，而不是由数据保证”。

它不合适的地方同样明显。! 是纯编译期标记，运行时如果真是 null，会立刻抛 Cannot read property ... of null，而且抛出的位置就是那一行，看起来像个低级错误。一长串 a!.b!.c! 更是坏味道，说明类型建模没有反映真实约束，应该改成提前判空、拆中间变量，或者调整数据结构让”必然存在”这件事在类型里成立。

收窄的基础：typeof、instanceof 与相等比较

与断言相反，类型守卫是”能让编译器在分支内自动收窄类型”的表达式。它不改变运行时行为，只是把”条件为真”这个事实写进控制流分析：进入 if 分支后，变量的类型按条件缩小；else 分支则拿到补集。收窄对 if、else if、三元表达式、&&、|| 和提前返回都生效。

typeof 负责原始类型与函数。typeof x === "string" 之后，x 在分支内是 string；写成 "function" 时还能拿到函数签名。它有一个历史遗留必须记住：typeof null === "object"，所以判空不能靠 typeof。另外 typeof 对数组、日期、普通对象一律返回 "object"，它只能区分原始类型与函数，区分不了具体是哪种对象。

instanceof 按原型链判断，适合类实例。err instanceof TypeError 会让 err 收窄为 TypeError，date instanceof Date 同理。它的局限在跨执行环境时暴露：页面里内嵌的 iframe 有自己的全局对象，从里面传出来的数组不满足 instanceof Array，日期也同理。这类数据要靠结构判断，而不是原型判断。

提前返回的价值在于，每个分支结束后，剩下的类型已经被剥掉一层，后续代码不用再重复判断。这比层层嵌套的 else 更容易维护，也让编译器收窄的结果更贴近阅读时的直觉。

守卫函数的可复用性来自它的签名：它只依赖入参，不依赖上下文，所以可以放进公共模块被多处调用。需要注意的是，复用意味着改动的波及面也大，一个宽松的守卫被十个地方使用，等于十处都失去了保护。对核心数据结构，守卫应当写得严格一些，宁可多检查几个字段。

选型与常见坑

综合前面的分析，选择顺序可以定为：控制流收窄优先于自定义守卫，自定义守卫优先于非空断言，非空断言优先于类型断言，双重断言放在最后并且必须配注释。理由很朴素：越靠前的写法在运行时真的做了检查，越靠后的写法越接近一句注释，可信度完全取决于写它的人。

落到具体判断上：值来自外部或类型不确定，写守卫；类型确定但编译器推断不出来，先用断言救急，同时记下以后补类型；只处理 null 与 undefined，先判空再取值，实在绕不过去才用 !。断言不是不能用，而是每用一次都要能说清”我凭什么比编译器更确定”。

几个反复出现的坑值得列出来。守卫返回 boolean 而不是 v is T，调用处不收窄，这是最高频的一个。守卫的实现比类型声明宽松，只查了两个字段就宣称是完整结构，类型后来加了字段也没人补检查。判空之后又顺手写 as any，把刚收窄好的类型重新打回原点。在 .tsx 里用尖括号断言，被 JSX 解析器拦下。以及把 as any 当团队默认风格，类型系统还在，只是不再起作用。

小结

断言与守卫解决的是同一个问题的两面：前者声明类型，后者验证类型，编译器只对后者负责。as T 与 <T>expr 不产生任何运行时代码，写错时错误会推迟到运行时，as any 中转和双重断言要格外克制。! 只在严格空检查下有意义，适用于”由代码结构保证非空”的少数位置。typeof、instanceof、相等比较与 Array.isArray 覆盖了大部分内建收窄，业务结构则交给 v is T 的守卫，并且要保证实现与类型同步。判别联合加 never 穷尽检查，是当前成本最低的防错手段；in 收窄与断言函数都要等后续版本，眼下用自定义守卫和返回型 ensure 函数替代即可。
