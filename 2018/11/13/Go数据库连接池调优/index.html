Go 数据库连接池调优

本文属于《Go 语言与工程》第 56/78 篇
上一篇系列目录下一篇

Go 服务连 MySQL，多数人只写一行 sql.Open 就开始查数据，直到线上出现请求大面积超时、too many connections 或者莫名其妙的 invalid connection，才回头翻 database/sql 的文档。本文从连接池要解决的问题讲起，拆开 database/sql 的池模型，再落到参数估算、生命周期、故障排查、监控与压测。读者读完应当能为一个具体的服务算出合理的池大小，并在出问题时按步骤定位，而不是凭感觉调数字。

连接池到底解决什么问题

要理解池，先理解“不用池”的代价。一条 MySQL 连接从零建立，要经历 TCP 三次握手、MySQL 协议层的握手与认证（校验账号、密码与权限），开了 TLS 还要多一轮加密协商。每一段都有网络往返，跨机房时建一条连接动辄几十毫秒。如果每个请求都新开连接，响应时间里会有相当一部分花在握手和密钥计算上，数据库还没开始干活，CPU 先忙了起来。

连接本身还是有状态的资源。MySQL 5.7 默认是一连接一线程，每条连接在服务端都占着一个线程栈、一块会话内存，还带着自己的会话变量、临时表、事务状态。连接数涨上去，服务端的上下文切换和内存占用跟着涨，而这些开销并不直接产出查询结果。所以连接不能随用随建、用完就扔，也不能无限制地建。

连接池做的就是两件事。第一是复用：把建好的连接放进一个池子，用完不关闭，还给池子，下一个请求直接拿走，省掉握手与认证。第二是限流：池子设了上限，取不到连接的请求只能排队等待，等于给数据库加了一道背压，防止应用在数据库变慢时把它彻底压垮。第二点常被忽略，很多人把池当成纯粹的性能优化，其实它更重要的作用是保护下游。

这里要先破除一个直觉：池越大越好吗？不是。池的上限意味着“同时有多少条 SQL 在数据库上跑”。超过数据库能承受的并发，多出来的连接只是在服务端排队，同时还要占用线程与内存，反而让每条 SQL 都变慢。池太小会让应用侧排队，池太大则把排队从应用搬到了数据库，而数据库的排队更不可控。合理的大小取决于并发量、单条 SQL 的耗时和数据库的处理能力，这三者都要测量，不能拍脑袋。

database/sql 的池模型

Go 标准库的 *sql.DB 不是一条连接，而是连接池的句柄。它在第一次真正需要连接时才建连（sql.Open 只记录驱动与 DSN，不发网络请求），内部维护空闲队列，按需创建连接，并用几个参数约束总量与寿命。

三个核心参数是 SetMaxOpenConns、SetMaxIdleConns 和 SetConnMaxLifetime。maxOpen 是池中同时存在的连接总数上限，包含正在使用的和空闲的，取值为 0 表示不限制；maxIdle 是归还后保留下来备用的空闲连接数，超出的连接会被真正关闭，默认值是 2；connMaxLifetime 是一条连接从创建到被强制丢弃的最长时间，0 表示永不过期。还有一个容易被忽视的约束：如果 maxIdle 设得比 maxOpen 大，运行时会被自动压到 maxOpen，因为空闲数不可能超过总数。

获取与归还的流程可以概括为下面这张图。请求进来时，database/sql 先看空闲队列里有没有可用连接，有就直接取走并标记为使用中；没有且当前总数未达上限，就新建一条；两者都不满足，就只能阻塞等待别人归还，或者等到上下文取消。归还时，如果连接已经出错、超过寿命，或者空闲队列已满，就关闭它，否则放回队列。

flowchart TD
    A[业务调用 Query/Exec] --> B{空闲队列有连接?}
    B -- 有 --> C[取出并标记 inUse]
    B -- 没有 --> D{当前总数小于 maxOpen?}
    D -- 是 --> E[新建连接并认证]
    E --> C
    D -- 否 --> F[阻塞等待归还或 ctx 取消]
    F --> G{等到连接?}
    G -- 是 --> C
    G -- 否 --> H[返回错误]
    C --> I[执行 SQL]
    I --> J{连接可用且未超寿命?}
    J -- 否 --> K[关闭连接]
    J -- 是 --> L{空闲队列未满?}
    L -- 是 --> M[放回空闲队列]
    L -- 否 --> K

这个模型有两个值得注意的细节。其一，等待是没有默认超时的，如果业务用的是不带 Context 的 Query，池耗尽时 goroutine 会一直挂着，直到有连接归还，表现为接口全部超时但数据库却“看起来没事”。其二，maxIdle 的默认值只有 2，意味着即使你把 maxOpen 调到 50，高峰期过后也只有 2 条连接被保留，其余全部关闭；下一次流量高峰又要重新建连，形成周期性的延迟毛刺。

参数怎么定：从并发量反推

定参数之前，先把三个已知量摆出来：服务在这个数据库上的峰值 QPS，一条 SQL 从拿到连接到归还的平均持有时间 T，以及数据库实例允许这个服务占用的连接数上限。持有时间不等于 SQL 在服务端的执行时间，它还包括驱动编码、网络往返、结果集读取，通常要按 P95 而不是平均值来估算，因为池要扛住的是高峰而非平均。

用利特尔法则做一个粗算：系统内同时被占用的连接数，等于到达速率乘以每条连接的持有时间。若峰值为每秒 300 次查询，平均每次持有 8 毫秒，那么平均并发占用约为 2.4 条。这个数字往往小得让人意外，它说明大多数业务系统的池并不需要几十上百条连接。但平均值不能直接当上限，因为流量有突发、SQL 有慢的、网络有抖动，实际取值要在平均值上留出数倍余量，具体倍数应当由压测确定。反过来也能校验：若一条 SQL 要跑 200 毫秒、QPS 是 50，并发占用就是 10 条，池小于这个数，请求就会在应用侧排队，延迟被放大成“等待时间加执行时间”。

确定 maxOpen 时要同时受两个上限约束。应用侧的上限由并发与延迟目标决定，数据库侧的上限由实例的 max_connections 减去其他服务与运维预留后，按部署实例数均分。最终取两者中较小的那个，并留出一点余量。例如数据库允许这个业务共用 200 条连接，服务部署了 8 个实例，那么单实例的池上限不应超过 25 条，否则任何一个实例的扩容或流量倾斜都可能把数据库打满。

maxIdle 的建议是把它设成与 maxOpen 相同或接近。池的意义是复用，如果空闲连接只留两三条，每次流量上升都要重新握手认证，延迟曲线会出现明显的台阶。代价只是空闲时多占几条服务端连接，换来的是稳定的取用延迟。真正需要压缩空闲连接的是连接数极其紧张的场景，那时应当整体调小池，而不是只调小空闲数。

connMaxLifetime 不解决容量问题，它解决“连接是否还活着”，下一节单独说。三个参数没有通用数值，下面的方法只给量级，最终要靠压测与监控校准。

生命周期：别用到一条已经死掉的连接

MySQL 有两个空闲超时参数：wait_timeout 和 interactive_timeout。应用通过驱动建立的连接属于非交互式，受 wait_timeout 约束，空闲超过这个秒数就会被服务端主动断开。这个值在 5.7 的默认配置里很大，但生产环境常被调小，再叠加负载均衡、数据库代理各自的空闲回收策略，真实的寿命上限往往比想象中短。

问题的关键在于：服务端断开连接时，客户端并不会收到通知。TCP 连接可能只是收到一个 FIN，而连接池并不知道这条连接已经不可用。下一次业务取到它，写入请求后才发现对端已关闭，于是报出 invalid connection、unexpected EOF 或者 driver: bad connection。这类错误的特点是偶发、集中在低峰期后的第一波流量，排查时容易误判为网络抖动。

SetConnMaxLifetime 就是用来规避这个时间差的：让客户端在服务端动手之前，主动把老连接淘汰掉。取值必须小于链路上所有空闲超时的最小值，并且留出足够的余量，通常取那个最小值的几分之一。如果 wait_timeout 是 600 秒，寿命取 5 分钟比较稳妥；如果中间还有一层代理把空闲连接在 3 分钟时掐断，寿命就得按 3 分钟来算。这个参数不需要精确，宁小勿大，代价只是多一点建连。

寿命到期后，连接的关闭是惰性的：归还时发现已超期就关闭，空闲队列里的超期连接也会被后台清理协程收走，不会出现“到点全部断开”的惊群，因此这个值可以设得比较激进。

顺手说清楚时区。parseTime=true 让驱动把日期时间解析成 time.Time，而 loc 决定解析时用哪个时区，默认是 UTC。如果数据库里存的是本地时间，而 loc 没配，读出来的 time.Time 会整体偏移几个小时，且这种错误在格式化输出之前很难发现。稳妥的做法是服务端、连接会话、应用三处统一用同一时区，并在 DSN 里显式写上 loc，不要依赖默认值。MySQL 5.7 的 TIMESTAMP 还会做会话时区转换，DATETIME 不会，这一差异也要在建模时想清楚。

四类常见故障与排查顺序

池相关的问题，现象高度相似：接口变慢、超时、报错，但根因可能完全相反。先把最常见的四类分开看。

第一类是连接泄漏，也是最隐蔽的一类。db.Query 返回的 *sql.Rows 持有连接，只有遍历完并调用 Close 之后连接才会归还。常见错误是在循环里对每个结果集都写 defer rows.Close()，函数不返回，连接就一直不释放；或者在错误分支直接 return，而函数开头忘了写 defer。事务同理：Begin 之后连接被独占，某条错误分支直接 return 而没有 Rollback，这条连接就永远回不到池里。预处理语句也与连接绑定，长期不 Close 同样会累积。

第二类是池耗尽。表现为请求大量堆积在获取连接这一步，数据库的 CPU 却不高。判断依据是 DBStats 里的 InUse 长期顶在 maxOpen，WaitCount 持续增长，而 Open 已经等于上限。此时要看的是“谁占着连接不还”，而不是继续调大上限。

第三类是等待超时。池耗尽之后，带 Context 的请求会在截止时间到达时返回 context deadline exceeded，不带 Context 的请求则无限等待。监控上会看到超时集中在一批共享同一数据库或同一段慢 SQL 的接口。

第四类是数据库侧的 too many connections。这是服务端拒绝新建连接，错误来自 MySQL 而不是池。它说明所有客户端的连接上限之和已经超过了 max_connections。这个错误发生在“建连”阶段，池里的老连接仍然可用，所以现象常常是部分请求成功、部分请求直接失败。

排查可以按下面的顺序走，先分清是“拿不到连接”还是“拿到了但连不上”：

flowchart TD
    A[接口变慢或报错] --> B{错误信息是什么?}
    B -- too many connections --> C[服务端连接数打满]
    C --> C1[查 Threads_connected 与 processlist]
    C1 --> C2[核对各实例池上限之和]
    B -- context deadline / 长时间无响应 --> D{DBStats.InUse 是否等于 maxOpen?}
    D -- 是 --> E[池耗尽: 找占用者]
    E --> E1[抓 goroutine dump 看阻塞点]
    E1 --> E2[查未关闭的 Rows 与未回滚的 Tx]
    D -- 否 --> F[瓶颈不在池: 查慢查询与锁等待]
    B -- invalid connection / EOF --> G[连接被对端关闭]
    G --> G1[核对 wait_timeout 与代理空闲超时]
    G1 --> G2[把 ConnMaxLifetime 调小]
    B -- 连接被拒绝 --> H[查网络、白名单、max_connections]

goroutine dump 是定位泄漏最有效的手段。向进程发一个 SIGQUIT，或者在服务里挂上 net/http/pprof 后抓 goroutine?debug=2，搜索 database/sql.(*DB).conn，如果看到成百上千个 goroutine 停在这个函数上，就说明它们在排队等连接；再顺着调用栈往下看业务代码，通常能直接指到那个忘记 Close 的函数。

上下文、超时与连接的去留

从 Go 1.8 起，database/sql 提供了 QueryContext、ExecContext、QueryRowContext 和 BeginTx。带 Context 的版本不仅能让调用方在超时后立刻返回，还会把取消信号传给驱动：驱动向 MySQL 发送 KILL QUERY 或者直接断开底层连接。标准库文档写得很明确，上下文被取消时，sql 包会关闭这条连接。也就是说，被取消的那条连接不会被放回池里复用，而是直接销毁。

这个行为有两面。好处是不会有“查询还在服务端跑、客户端已经放弃”的僵尸 SQL 继续占用资源；代价是频繁取消会带来连接抖动，每次都要重新握手认证。所以超时时间不能拍得太短，必须大于正常查询的 P99，并且略大于数据库侧的执行上限，让数据库先自己终止，客户端再兜底。

事务对池的占用

事务是池的最主要占用者，因为一个事务从头到尾独占一条连接，中间不管有没有在跑 SQL，这条连接都不能给别人。BeginTx 的典型写法是“立刻 defer 回滚，成功则提交”：

事务对池的影响不只是“占一条”，而是“按事务时长占一条”。如果池上限是 20，平均事务耗时 50 毫秒，那么这套代码的理论事务吞吐上限就是每秒 400 个，超过就排队。想把吞吐提上去，缩短事务比扩大池更有效。常见的长事务来源包括：在事务里调用外部 HTTP 接口、发消息、写文件、等待锁，以及把一批本可以分开的写操作塞进同一个事务。这些都会让连接在无事可做时被白白占着，还会拉长锁持有时间、推迟主从复制。另外，Commit 发出后若网络中断，客户端无法判断服务端是否已提交，database/sql 通常会把这条连接判为不可用并关闭，业务侧要靠幂等键或唯一约束兜底，不能简单重试。

监控：先看见，再调参

调参的前提是能看见池的状态。*sql.DB 提供了 Stats()，返回一组从进程启动起累计的计数：

字段 含义
Open 当前已建立的连接总数，含使用中与空闲
InUse 正在被业务持有的连接数
Idle 空闲队列中的连接数
WaitCount 累计等待连接的次数
WaitDuration 累计等待的总时长
MaxIdleClosed 因空闲队列满而被关闭的连接数
MaxLifetimeClosed 因超过寿命而被关闭的连接数

其中 WaitCount 与 WaitDuration 最能说明问题：它们不为零，就说明池曾经不够用。用 WaitDuration 除以 WaitCount 可以得到平均等待时间，把它和接口的 P99 放在一起看，就能判断延迟里有多少是排队造成的。MaxIdleClosed 持续增长则说明 maxIdle 偏小，连接在被反复关闭又重建。

只看应用侧还不够，服务端的视角能验证你的判断。SHOW STATUS LIKE 'Threads_connected' 是当前连接数，Threads_running 是正在执行的语句数，Max_used_connections 是历史峰值。如果 Threads_connected 远大于各实例 InUse 之和，说明有连接没被应用正确关闭，或者有别的东西在连这个库；如果 Threads_running 长期很高而 InUse 不高，瓶颈在 SQL 本身，不在池。

告警的阈值要结合容量来定，比较通用的几条是：InUse 占 maxOpen 的比例持续超过八成、WaitCount 在几分钟内快速增长、Open 贴住上限不再下降、服务端 Threads_connected 逼近 max_connections 的八成。这几条同时出现两条以上，基本可以确定池需要调整或者存在泄漏。

怎么压测出合适的池大小

池的大小没有理论最优解，只有在某个流量模型下的较优解，所以必须压测。压测的目标不是刷出一个漂亮的最高 QPS，而是找到两个拐点：应用侧开始大量排队的那一点，和数据库吞吐不再随连接数增长的那一点。理想区间就在这两点之间。

方法上建议用固定 QPS 逐级加压，而不是一上来就固定并发数打满。固定并发时，QPS 会随数据库变慢而自动下降，你很难判断是流量不够还是系统不行；固定 QPS 则能清楚地看到“同样的流量下，延迟如何变化”。可以从预估峰值的五成起步，每档跑几分钟，每档增加两成，直到错误率或 P99 明显恶化。每一档都要记录四组数据：接口的 P50、P95、P99，错误率，WaitCount 与 WaitDuration 的增量，以及 MySQL 的 Threads_running。

对比不同池大小时，一次只改一个参数。常见的结果形态有三种：池调大后 QPS 上升、P99 下降，说明之前确实被池卡住；池调大后 QPS 不变、P99 反而上升，说明数据库已经饱和，多出来的连接只是在争抢 CPU 和锁；池调小后 QPS 略降但 P99 稳定，说明原来的池偏大，可以回收一部分连接。结论不能只看 QPS 一个数字。

压测还有几个容易失真的地方。数据量要接近生产，否则执行计划可能完全不同；要预热，避免把冷缓存下的第一波慢查询当成常态；压测客户端不能和被压服务挤在同一台机器上，否则先耗尽的是客户端的文件描述符；不要拿生产库做写入压测。工具方面，hey、vegeta、wrk 都能做固定速率压测，自己用 Go 写一个带限速的客户端也不难，好处是能把超时、连接复用、错误分类都按真实客户端的行为来配。

与 MySQL 侧的参数配合

应用侧的池不是孤立的，它必须和数据库的连接上限对齐。最基本的等式是：所有连接到这个实例的客户端，其连接数上限之和，不能超过 max_connections。这个和里既有本服务的多个实例，也有其他服务、数据同步工具、运维终端和监控采集器。只按自己的池大小去算，是 too many connections 最常见的原因。

max_connections 在 MySQL 5.7 里是可以在线调整的全局变量，但调大之前要先确认操作系统的文件描述符上限与内存是否够用，每条连接都要消耗一个文件描述符和一块线程栈。应用侧同时要限制单用户的连接数，可以给每个服务建独立账号并设置 max_user_connections，这样某个服务失控时不会把整个实例拖垮。

超时参数要分清楚。wait_timeout 作用于非交互式连接，也就是应用驱动建立的连接；interactive_timeout 作用于交互式客户端，比如命令行登录。两者都只影响空闲连接，不影响正在执行 SQL 的连接。应用的 ConnMaxLifetime 要小于 wait_timeout，这一点前面已经说过；如果 DBA 调整了 wait_timeout，应用侧要跟着复核，否则就会出现“改了一个参数，另一个服务开始报 invalid connection”的连锁反应。

慢查询是池问题的另一个源头。把 long_query_time 设得合理，打开慢查询日志并用 pt-query-digest 汇总，先解决扫描行数巨大、执行时间以秒计的语句。一条慢 SQL 占住连接的时间可能相当于几十条正常 SQL，池再大也填不满这个洞；5.7 的 sys 库也能直接查出最耗时的语句。

最后是权限与应急。应用账号不要用 root，也不要给 SUPER，但要保留一个独立的运维账号，在连接打满、普通账号连不进去时还能登录进去 KILL 空闲连接或者临时调大上限。

多实例、读写分离与故障切换

连接池是进程内对象，不跨进程共享。这一点决定了容量规划的基本算法：数据库上看到的总连接数，等于每个实例的池上限乘以实例数，再叠加其他客户端。服务从 4 个实例扩到 12 个，即使一行配置都没改，数据库的连接数也会变成三倍。滚动发布时更要注意，新旧版本会短暂并存，连接数可能出现接近翻倍的峰值，max_connections 必须按这个瞬时值留余量，而不是按稳态值。

读写分离的常见做法是准备两个 *sql.DB，一个指向主库，一个指向只读副本。两者的池参数应当分别设置：主库承担写入与事务，连接数通常不需要很多，但事务时长要控制；从库承担大量读请求，池可以更大，但要以从库的实际承载能力为限。写后立即读的请求必须走主库，否则会读到旧数据。

故障切换是池最难受的时刻。主库切换后，池里那些指向旧主库的连接全部失效，但池并不知道，还会继续把它们借给业务，直到某次使用时报错并被标记为坏连接。ConnMaxLifetime 能保证这些连接在有限时间内被自然淘汰，缩短切换后的阵痛期，但不能做到立即生效。对切换时间敏感的系统，可以在配置中心推送新地址后重建池：用 atomic.Value 保存当前的 *sql.DB，切换时先换上新句柄，再延迟关闭旧句柄，让仍在执行的查询跑完。

这段代码的关键是顺序：先让新流量拿到新池，再给旧池留一段排空时间。如果先关旧池，正在执行的查询会立刻失败；如果永远不关，旧池的连接会一直挂在旧库上。切换期间还应临时把读流量收回主库，等从库追上新的位点再放回去。

一份调优清单与几个误区

把前面的内容压缩成一份可以照着做的清单：

  • 全进程只保留一个 *sql.DB，在初始化时设置三个参数，并做一次 Ping。
  • 用峰值 QPS 乘持有时间估算并发占用，再按实例数折算单实例上限，与数据库可用连接数取小。
  • maxIdle 与 maxOpen 对齐，避免空闲连接被反复关闭重建。
  • ConnMaxLifetime 小于 wait_timeout、代理空闲超时、负载均衡空闲超时中的最小值。
  • 所有查询走 Context 版本，超时略大于数据库侧执行上限，入口处传递 r.Context()。
  • 每个 Rows 都 defer Close，每个 Tx 都 defer Rollback，遍历后检查 rows.Err()。
  • 事务里只做数据库操作，把 RPC、消息、文件写入移到事务外。
  • 采集 DBStats 与服务端连接数，对 InUse 比例、WaitCount 增速设告警。
  • 上线前做阶梯压测，上线后按流量变化复核，不用一套参数打天下。

误区一，池越大越好。池的上限是并发 SQL 的上限，不是吞吐的上限；超过数据库处理能力的连接只会增加争抢。误区二，只调池不看 SQL。一条慢查询能让任何大小的池失效，先看慢查询日志和执行计划，再谈参数。误区三，忽略网络中间件。负载均衡、数据库代理、NAT 网关都有自己的空闲超时，哪个先断，连接就在哪里失效，ConnMaxLifetime 必须按最短的那个算。误区四，把 ConnMaxLifetime 设成 0，认为“连接一直活着最省事”，结果把所有风险都留给了服务端超时。还要记住池不是熔断器：池满只会让请求排队，真正的熔断要在业务入口做。

小结

连接池首先是一道限流阀，其次才是性能优化。database/sql 的模型很简单：空闲队列、上限、寿命，三者共同决定连接怎么被借出与归还。参数应当从并发量和 SQL 耗时反推，再用阶梯压测校准，而不是照搬别人的数字。绝大多数线上故障不是池太小，而是连接没归还、事务太长、SQL 太慢，或者寿命比服务端的空闲超时还长。把 DBStats 和服务端的连接数一起监控，把 Rows.Close 与 tx.Rollback 变成肌肉记忆，池的问题就解决了一大半。
