主机安全加固实践

很多团队在等级保护整改时，拿到的是一张几十页的检查表，面对的却是十几台甚至上百台已经在线运行的 Linux 主机。本文从单机视角出发，把主机安全加固拆成账户、文件、服务、内核参数、审计、补丁六个层面，逐个说明每一项配置防的是什么、怎么做、怎么验证。适合需要独立完成服务器交付与安全整改的后端开发者和运维人员阅读，读完后你应当能为一批 CentOS 7 或 Ubuntu 16.04 LTS 主机制定一份可执行、可回滚的基线。

从一台机器开始：加固的边界与目标

2018 年下半年，等保 2.0 还在报批与试点阶段，很多单位已经按 1.0 的检查要求做主机整改。安全负责人关心检查项有没有对应配置，运维关心改完业务还能不能跑。主机加固之所以难，不在于命令复杂，而在于要在更安全与还能用之间找到一条可验证、可回滚的路径；一条说不清挡住什么风险的基线，迟早会被值班人员在半夜注释掉。

本文只讨论单机基线：一台标准的 Linux 服务器从装好到对外提供服务，中间应完成哪些配置。堡垒机、4A 与集中会话审计属于《运维审计与堡垒机》讨论的集中管控；入侵后的排查、取证与处置属于应急响应。边界划清楚，每一类配置才能讲透。

四条原则

最小权限。任何主体只应拥有完成职责所必需的最小能力。root 不应用于日常操作，业务进程以专用低权限账户运行，sudo 授权到具体命令而不是 ALL。判断权限是否必要只需问一句：这个账户被盗后，攻击者最多能做什么？

最小服务。系统上安装的每一个软件包、监听的每一个端口，都是潜在的入口。发行版预装的打印服务、蓝牙工具、邮件传输代理，以及排查问题时临时启动的测试服务，都应当在交付前逐一确认。没有在用的服务，最好的状态是既没有运行，也没有设置开机自启。

可审计。加固动作和系统关键行为都要留痕：谁改了 sshd_config，谁在凌晨用 sudo 执行了什么，账户是哪天创建的，出问题时要能回答。变更记录、命令历史与登录日志应在加固的同时就规划好。

可回滚。每一条变更都要能在十分钟内撤回。改配置前备份原文件并记录路径，防火墙规则先在当前会话里验证再写入持久化配置，重大变更前给虚拟机打快照。回滚方案不是写在文档里给自己看的，而是要在变更之前就实际演练过一次的。

加固前的资产与风险盘点

动手之前先做盘点，而不是先背检查表。盘点的目的是把”通用基线”裁剪成”这台机器的基线”。同样是 Web 服务器，面向公网提供服务的和只在内网被负载均衡调用的，SSH 来源限制、防火墙默认策略、日志外送要求都不一样。

一份可用的盘点清单至少应覆盖下面几项。

盘点项 要确认的内容 产出
业务角色 跑什么服务、依赖哪些端口、哪些账户 端口与账户白名单
登录入口 谁需要登录、从哪些网段、密钥还是密码 登录矩阵
数据敏感度 是否含个人信息、日志是否含敏感字段 分级与留存要求
现状基线 当前监听端口、SUID 文件、sudo 授权、定时任务 加固前快照
变更窗口 业务低峰时段、回滚方式、责任人 变更单

盘点结果要落成文件，与核查脚本放在一起：允许监听的端口写成 allowed_ports.txt，允许登录的账户写成 allowed_users.txt。没有基准的核查只能发现”看起来奇怪”，有基准才能发现”和上周不一样”。

最容易被忽略的是最后一步。很多团队把加固当成一次性项目，验收后再没人看过，半年后新装的软件带进来一个监听端口，或同事为排查问题把 SELinux 设成 permissive，基线就这样慢慢失效。

账户与认证：先把入口收窄

账户是主机上最直接的攻击面。弱口令、多余账户、允许 root 直接登录，这三件事凑在一起几乎等于把门虚掩着。这一节从清理账户开始，做到 SSH 只允许密钥登录，再用 sudo 把 root 能力切开。

排查的重点是三类账户。第一类是 UID 为 0 的非 root 账户，它们等价于 root，但常常不在管理员的视线里，发现后应当确认用途，无用的直接锁定。第二类是空口令账户，尤其是在一些老系统上，安装时创建的账户可能从未设置密码。第三类是随软件包安装的服务账户，例如 bin、daemon、adm、lp、games、ftp，它们本不该登录，但 shell 字段可能还是 /bin/bash。

处理方式要克制。不要看到用不上的账户就 userdel -r，因为文件属主会变成孤立的 UID，日志里也再查不到这个名字。更稳妥的做法是先锁定、再观察。

usermod -L 只影响后续认证，已建立的 SSH 会话不会断开，锁定后要配合 pkill -u 清理在线会话。服务账户改为 nologin 前，要确认没有 cron 任务依赖交互式 shell；nologin 拒绝登录，但 su -s /bin/sh 仍可切换，这属于预期行为。

SSH 密钥登录与禁止直登

SSH 是 Linux 主机最主要的入口，也是加固收益最高的一处。目标很明确：只允许密钥认证，不允许密码认证，不允许 root 直接登录，并且限制来源。

先在有权限的普通账户下生成密钥。客户端的私钥不要设置空口令，否则私钥文件一旦泄露就等于口令泄露。

服务端要保证目录与文件权限正确，否则 sshd 的 StrictModes 会拒绝使用该密钥。正确权限是家目录 700 或 750、.ssh 目录 700、authorized_keys 600，且属主必须是该用户本人。在启用 SELinux 的系统上，还要恢复文件上下文，这一点后文会展开。

然后是 sshd_config。下面是一组经过实践检验的关键项，写在文件末尾的全局段落即可。

几个容易误解的项：UsePAM yes 要保留，否则 pam_faillock 不生效，Ubuntu 上还会影响会话初始化；ChallengeResponseAuthentication 与 PasswordAuthentication 要同时关闭，只关后者时部分客户端仍会走密码路径；PermitRootLogin no 之后必须确保有普通账户可以 sudo；MaxAuthTries 与 LoginGraceTime 压缩暴力破解窗口，但不能替代密钥认证。

sudo：把 root 能力切开

禁止 root 直登之后，日常运维要通过普通账户加 sudo 完成。默认的 %wheel ALL=(ALL) ALL 给了全量权限，等保检查里通常会被认为授权过粗。更合适的做法是按角色拆分，写进 /etc/sudoers.d/ 下的独立文件。

Cmnd_Alias 里的命令要写绝对路径和完整参数，sudo 的匹配是命令加参数的前缀匹配，只写 /bin/systemctl 等于放开所有子命令。敏感操作建议封装成固定脚本，只授权脚本路径并控制脚本权限。log_input 与 log_output 记录会话输入输出，需预先创建 /var/log/sudo-io；改完用 visudo -cf 校验。

到这里，入口已经收窄：能登录的账户是白名单，认证靠密钥，root 不能直登，提权要走 sudo 并且留痕。下一节处理登录之后能看到什么、能改什么。

文件与权限：让敏感数据不外溢

Linux 权限模型只有属主、属组、其他人三档，问题往往出在默认值与继承上。文件加固的目标有两个：敏感文件不能被普通用户读到，可执行文件不能被随意替换。

敏感文件与 SSH 目录

/etc/shadow 存的是口令哈希，一旦可读就等于把离线爆破的材料送给了攻击者。CentOS 7 默认权限是 000，Ubuntu 16.04 是 640 且属组为 shadow，两种都可以接受，关键是不要出现其他人可读。同样需要检查的还有 /etc/gshadow、/etc/sudoers、/etc/ssh/ssh_host_*_key 以及各用户的 authorized_keys。

对 SSH 目录的权限要更严格，因为 sshd 默认开启 StrictModes，只要权限过宽就会拒绝密钥登录，而这种失败在日志里只表现为一句”bad permissions”，很容易被误判成密钥本身有问题。正确状态是家目录不超过 750、.ssh 为 700、authorized_keys 为 600。

在启用了 SELinux 的 CentOS 上，还有一个纯权限之外的坑：用 scp 或 cp 把公钥拷进 .ssh 时，文件可能带上 user_home_t 而不是 ssh_home_t，权限完全正确但 sshd 仍然读不到。解决办法是用 restorecon 恢复上下文。

umask 与默认权限

新建文件的默认权限由 umask 决定。多数发行版给普通用户的是 002 或 022，前者会让同组用户可写，对于多人共用的服务器并不合适。建议统一收紧到 027，即新文件默认 640、新目录默认 750。

只改 /etc/profile 不够，它只对登录 shell 生效，systemd 服务、cron 任务、su -c 都不会读它。服务的 umask 要在 unit 里声明，cron 任务在脚本开头自己设置。判断是否生效，直接创建文件看结果：

SUID、SGID 与粘滞位

SUID 程序以文件属主的身份运行，是提权链路上最常被利用的一环。系统自带的 passwd、su、sudo、mount 等需要 SUID，但一台 Web 服务器上出现一个属主为 root 的 SUID shell 脚本，就非常可疑了。加固的做法不是一律去掉，而是建立基线、定期比对。

首次输出保存为 suid-baseline.txt，之后每周 diff。RPM 系统可用 rpm -Vf /usr/bin/passwd 校验文件是否被改动，输出为空表示一致。发现异常先确认所属软件包（rpm -qf 或 dpkg -S），再决定移除 SUID 位还是卸载。

粘滞位主要用在共享目录上。/tmp 应当是 1777，这样任何用户都能创建文件，但只有属主能删除自己的文件，避免了在公共目录里互相覆盖或删除。更彻底的做法是给 /tmp、/var/tmp、/dev/shm 单独分区，并挂载为 nosuid,nodev,noexec。需要注意 noexec 会影响某些安装程序和脚本，上线前要确认业务没有在临时目录里执行东西。

服务与端口：只留下必须的那几个

刚装好的 Linux 服务器，默认启动的服务比多数人以为的多。CUPS、Avahi、蓝牙工具、Postfix 在服务器上几乎用不到，却各自监听端口、各有历史漏洞。落地顺序是：先看谁在监听，再看谁开机自启，最后用防火墙兜底。

用 ss 核查监听端口

netstat 属于 net-tools，在新系统上逐渐被 iproute2 的 ss 取代。ss -tulnp 一次列出 TCP 与 UDP 的监听端口及对应进程，是交付前必看的一张表。

读这张表时，重点不是记住端口号，而是建立”应该有”的清单。一台只跑 Nginx 与 SSH 的机器，期望只有 22 和 443；出现 25、111、631 就要问一句是谁开的。普通用户看不到别人的进程信息，查看进程需要 root 权限。

确认了多余服务之后，用 systemd 停用。这里要区分 disable 与 mask：前者只是去掉开机自启的软链接，服务仍可能被其他 unit 依赖而拉起；后者把 unit 链接到 /dev/null，是更强的禁止。

--now 表示同时停止，避免只改了开机项而进程还在跑。确定不用的软件包直接卸载更干净，unit 文件与依赖会一并去掉。

防火墙最小放行

服务收敛之后，用防火墙做第二道闸。CentOS 7 默认是 firewalld，Ubuntu 16.04 默认是 ufw，两者底层都可以落到 iptables。无论用哪个，原则都是默认拒绝入站、按需放行、限制来源。

命令顺序很重要：先加富规则放行内网 SSH，再移除通用的 ssh 放行，否则移除的瞬间内外网 SSH 会同时被切断。远程操作时，--reload 前要确认富规则已生效；稳妥的做法是开两个终端，一个变更，一个保持登录用于回滚。

习惯 iptables 的团队可以直接写规则，但要记得持久化，否则重启即失效。CentOS 7 需要 iptables-services，Ubuntu 用 iptables-persistent。

另一个常见的坑是 Docker：容器启动时会往 nat 与 filter 表插规则，可能绕过你写的 INPUT 链，导致”只放了 443，容器的 8080 却能从外面访问”。解决办法是在 DOCKER-USER 链补规则，或把容器端口只绑定在 127.0.0.1，由反向代理统一对外。

内核与网络参数：堵住协议层的边角

sysctl 的安全参数很多，网传的”一键优化脚本”常写上上百行，大半与安全无关，还有几条会影响性能。合理的做法是只处理确有攻击面的几类，并清楚每一条在防什么。改之前先用 sysctl 参数名 读当前值。

反欺骗与重定向

源地址欺骗是反射放大攻击的基础。攻击者伪造源 IP 发出请求，让响应打到受害者身上。rp_filter 做的是反向路径校验：收到一个包时，检查它的源地址是否真的能通过本机路由表回到那个方向，不能则丢弃。

default 只影响之后新建的网卡，all 影响所有已存在的网卡，两者都写才覆盖全面。多网卡且路由不对称的机器（比如双线出口）上，严格模式可能误杀正常流量，需要改为宽松模式 2 或按网卡单独设置。改完必须观察业务流量。

ICMP 重定向的本意是告诉主机”有更短的路径”，但在攻击者手里可以用来篡改主机的路由缓存，把流量引向自己。服务器通常不需要接受重定向，也不应该发送。

secure_redirects 只接受默认网关的重定向，对服务器同样没有必要。send_redirects 要求本机不充当路由器误导别人。源路由允许发送方指定路径，是探测拓扑的经典手段，应当直接禁用：

SYN 防护与广播

SYN Flood 利用的是三次握手的不对称：攻击者发大量 SYN 却不回 ACK，服务端为每个半连接分配资源，直到队列耗尽。SYN Cookie 的思路是不立即分配资源，而是把连接信息编码进序列号，等客户端回 ACK 时再重建。

这一条在主流发行版上默认开启，核查确认即可。tcp_max_syn_backlog 与 somaxconn 属于容量参数，不解决攻击问题，不应算作加固项，盲目调大还会增加内存占用。

广播 Ping 可以被用来做 Smurf 放大：攻击者伪造受害者地址向广播地址发 Ping，整个网段的主机一起回应，流量全部砸向受害者。服务器不应当响应广播地址的 Echo 请求。

后两条分别忽略格式非法的 ICMP 错误响应、记录源地址异常的包。log_martians 在遭受扫描时日志量会明显上升，要配合日志轮转，否则可能写满磁盘。

信息泄露与内存保护

还有几个参数与协议无关，但同属内核基础防护。地址空间布局随机化让攻击者难以预测函数与栈地址，应保持为 2。核心转储可能包含内存中的口令与密钥，不应允许 SUID 程序产生可读的 core。

dmesg_restrict 让非特权用户无法读取内核环形缓冲区，kptr_restrict 隐藏内核指针地址，两者都减少信息收集的线索。代价是排查问题时普通账户看不到内核日志，需要 sudo。

写入 /etc/sysctl.d/99-hardening.conf 之后，用 sysctl --system 让全部配置生效，再用 sysctl -a 或逐项读取确认。不要用 sysctl -w 改完就以为结束了，重启后会全部丢失。

没有使用 IPv6 的机器可以关闭协议栈，减少一类攻击面；依赖 IPv6 的则应保留并做同等强度的限制。

审计与日志：让发生过的事情查得到

前面几节做的是”不让坏事发生”，这一节做的是”坏事之后能还原”。审计要回答三个问题：谁登录了、谁提权了、关键配置何时被改。三者都依赖时间准确、日志留得住。

auditd 规则

auditd 是内核审计子系统的用户态守护进程，能记录系统调用级别的行为，比应用日志更难被绕过。规则文件放在 /etc/audit/rules.d/，用 augenrules 合并成 /etc/audit/audit.rules。

-p wa 监听写入与属性变更，-k 是事件标签。auid 是登录时的原始审计 UID，auid>=1000 排除系统服务，auid!=4294967295 排除非登录进程，过滤出来的才是”某个真实用户 sudo 后执行的命令”。64 位系统还应补一条 arch=b32 的对应规则，否则 32 位程序会漏掉。

规则生效后，改动 /etc/shadow 会立刻产生一条带 identity 标签的事件。ausearch -k identity -i 可以把数字字段翻译成可读文本；日常巡检看 aureport 的汇总，出问题时再按标签和时间范围下钻。

有一条规则要特别谨慎：-e 2 会把审计配置锁定为不可修改，任何后续的 auditctl 操作都会被拒绝，只有重启才能解除。它适合在基线完全定型之后启用，不适合在调试阶段写进去，否则你会发现自己在改规则时毫无反应。

journald 持久化与外送

systemd 的日志默认可能只存在内存里，重启就没了。要保证可追溯，必须改成持久化存储，并限制总占用，避免日志把根分区写满。

Storage=persistent 会在 /var/log/journal 下建立持久化目录，与内存日志并存。改完重启 systemd-journald。清理旧日志用 journalctl --vacuum-size=1G，不要手工 rm 目录里的文件。

日志留在本机有一个根本缺陷：攻击者拿到 root 之后可以删日志。所以关键主机应当把日志外送。最简单的做法是用 rsyslog 转发到日志服务器，@@ 表示 TCP，@ 表示 UDP。

生产环境应当在传输层加 TLS，并对日志服务器做写入隔离，让被攻陷的主机只能写、不能读、不能删。日志留存期限按等保的要求执行，2018 年常用的口径是不少于六个月，具体以所依据的标准条款为准。

时间同步

日志能不能用，取决于时间准不准。三台机器的时间各差几分钟，出问题时根本拼不出事件顺序；审计系统里的时间戳如果和真实时间偏离，取证价值也会大打折扣。CentOS 7 默认用 chrony，Ubuntu 16.04 默认用 systemd-timesyncd 或 ntpd。

chronyc tracking 里的 System time 一行能看出本机与参考源的偏差。内网环境应当指向单位自己的 NTP 服务器，而不是直接指向公网，同时用防火墙限制 NTP 只对内网开放，避免被利用做放大攻击。容器与虚拟机要注意宿主机时间漂移的问题，必要时在容器内也跑一个轻量的时间同步客户端。

补丁与基线核查：把一次性动作变成周期动作

补丁与 CVE 跟踪

补丁是成本最低的加固。2018 年的常态是”装完就不动”，机器跑两年不更新，内核与 OpenSSL 的已知问题全留着。合理做法是区分安全更新与功能更新：前者尽快跟，后者跟发布窗口。

CentOS 7 需要先装 yum-plugin-security，才能按安全公告筛选。升级前用 check-update 看清单，升级后用 history 留痕，出问题时可以回滚到某个事务。

Ubuntu 16.04 用 unattended-upgrades 自动安装安全更新，配置在 /etc/apt/apt.conf.d/50unattended-upgrades。自动更新要配合维护窗口与重启策略，内核更新后不重启等于没更新；不建议无差别自动重启，可攒到变更窗口统一做。

CVE 跟踪不要靠记忆。发行版安全公告会列出受影响与修复版本，订阅公告比自己扫新闻可靠。容器镜像同样要跟，基础镜像里的 OpenSSL 不会随宿主机升级。

基线做完之后，需要一条能反复执行的核查命令。下面的脚本只读，不修改任何配置，适合放进 cron 每周跑一次，把输出 diff 之后发邮件。

端口白名单来自加固前的盘点，这一点很关键：核查的价值在于和预期比，而不是和通用清单比。脚本退出码可以直接接入监控，非零即告警；每周输出存成带日期的文件，出问题时能回溯是哪一天开始漂移的。

回归验证

加固完成后按下面的顺序做一遍回归，顺序本身也是回滚的保障。

  1. 保持一个已登录的 SSH 会话不关，另开新会话验证密钥登录。
  2. 用普通账户执行一次被授权的 sudo 命令，再执行一次未授权的命令，确认前者成功、后者被拒。
  3. 从外部探测业务端口，确认放行符合预期，而不是只在本机 curl。
  4. 查看应用日志与 journalctl -p err，确认没有因权限收紧出现大量报错。
  5. 在 SELinux 机器上执行 ausearch -m avc -ts recent，确认没有新的拒绝记录。
  6. 记录变更文件清单与备份路径，写入变更单。

常见坑

改 SSH 把自己锁在门外。这是最高频的事故。AllowUsers 拼错、密钥权限过宽、SELinux 上下文不对、防火墙先于 sshd 生效，任何一种都能让人进不去。规避方式很朴素：保留一个活动会话，改完先 sshd -t，再 reload 而不是 restart，在第二个终端验证后才关闭旧会话。云主机要提前确认控制台或 VNC 可用。

SELinux 一关了之。遇到权限问题就把 SELinux 设为 disabled，等于拆掉一层强制访问控制，而且切回 enforcing 需要重新打标签，代价很大。正确做法是先看 ausearch -m avc 找到被拒绝的操作，用 semanage fcontext 加 restorecon 修正上下文，或用布尔值放行。调试期间可临时 setenforce 0，但不要改配置文件。

加固导致业务端口不通。常见原因有三个：防火墙默认区域被改、富规则顺序写反、Docker 自行插规则。排查时不要只看配置文件，先在本机 ss -tulnp 确认服务确实在监听，再从对端用 nc -vz 确认链路，最后看 firewall-cmd --list-all 的实际生效规则。

基线一次性做完没有持续核查。新装的软件、临时开的端口、为排查问题改回的配置，都会让基线慢慢失效。办法是把核查脚本纳入周期任务，把基线配置纳入配置管理，任何变更都走同一条流水线。加固不是一次验收，而是一个有反馈的循环。

小结

主机加固的起点不是命令，而是盘点：这台机器跑什么、谁要登录、暴露哪些端口。在此基础上，用最小权限收窄账户与 sudo，用最小服务收窄端口与进程，用文件权限与内核参数减少可被利用的边角，用审计与时间同步保证事后可追溯。每一条变更都要有备份、有验证、有回滚路径，并且能在下一个周期被自动核查出来。做到这些，一台机器的基线才算真正落地，而不是停留在检查表上。
