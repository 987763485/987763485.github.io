Go 实现统一响应与错误码

本文属于《Go 语言与工程》第 55/78 篇
上一篇系列目录下一篇

接口响应各写各的，前端就要为每个接口准备一套解析逻辑，排障时也说不清是网络错误、参数错误还是业务拒绝。本文从封套的字段设计讲起，在 Gin 1.3 上给出可运行的错误类型、响应函数与中间件，并处理参数校验、日志与文案分离。适合准备把一组接口收口成规范的 Go 开发者。

统一响应主要解决三件事。

第一是解析成本。移动端、Web 端、第三方调用方通常共用一个 HTTP 客户端封装，若每个接口形状都不同，封装层只能退化成“返回原始字节”，错误处理被推给每个业务页面。统一封套后，解析、重试、弹提示都能在封装层一次做完。

第二是错误定位。线上反馈“下单失败”，若响应只有一句“系统繁忙”，研发只能翻日志；若有稳定的业务码和请求标识，就能直接定位到分支和那条日志。业务码给机器和研发看，文案给用户看，两者不该混在一起。

第三是监控口径。网关、APM、告警规则通常按状态码和响应字段聚合。若失败也返回 200，错误率永远是零；若成功与失败结构不同，采集端还得写分支解析。统一封套让“成功率多少、哪类错误最多”变成一条聚合查询。

内部服务之间直接返回 struct 并没有错，RPC 有 IDL 约束，字段是强类型的；但面向浏览器的 HTTP 接口没有这层约束，调用方可能是任何语言，封套就是最低成本的契约。

响应封套的字段设计

最常见的两种形状是 code/message/data 与 success/data/error，前者用整数表达结果，后者用布尔值加错误对象。两者都能工作，区别在于让客户端做多少判断。

我倾向于 code/message/data。布尔值只能表达成败，无法区分“未登录”“无权限”“库存不足”；错误对象再嵌一层，解析路径变长；整数业务码则可直接进日志、进监控标签、进 switch 分支。

这里约定 code 为 0 表示成功。也有人用 200，好处是与 HTTP 状态码一致，坏处是容易被误认为 HTTP 状态；0 是 Go 的零值，未赋值的结构体天然就是成功。

message 只放可公开的文案，真正原因留给日志。data 用 interface{} 承载业务结构，失败时省略。omitempty 有代价：客户端不能假设 data 一定存在。若前端较多，宁可去掉它，让失败时返回 "data": null，形状始终一致。

HTTP 状态码与业务码的分工

“统一响应”常被误解成“所有接口都返回 200”，这是另一个极端。状态码由协议定义，表达请求在传输与语义层面是否成立；业务码表达应用内部的判断结果。分工清楚，网关、浏览器、监控才能各取所需。

有些场合必须用状态码。路径不存在返回 404，否则网关的重试与熔断、浏览器缓存都会失准；未登录返回 401，客户端拦截器可据此跳登录页；无权限返回 403，便于排查越权；请求体格式错误返回 400。它们都属于“请求本身有问题”，用 200 包装会让标准工具失效。

反过来，业务规则上的拒绝更适合 200 加业务码。“余额不足”“优惠券过期”“订单已取消”，请求格式没问题，服务也正常处理了，只是结果不满足业务前提。用 200 还是 409 都说得通，关键是全站一致，客户端知道要先看 code。

可以把常见场景固定成一张表：

场景 HTTP 状态 业务码段 说明
成功 200 0 data 携带结果
参数缺失或格式错误 400 1xxxx 字段名可放 data
未登录、令牌过期 401 1xxxx 由鉴权中间件统一返回
无权限 403 1xxxx 不要与 401 混用
资源不存在 404 2xxxx 等 业务资源不存在归入对应段
业务规则拒绝 200 或 409 3xxxx 等 同一项目内保持一致
服务内部错误 500 5xxxx 响应不含内部细节
下游依赖超时 503 5xxxx 可带 Retry-After

这张表不必写进每个 Handler，而是固化在错误构造函数里：调用方只描述“发生了什么”，状态码和码段由构造函数决定。客户端则两段式判断，先看 HTTP 状态是否为 2xx 以判断链路，再看 code 是否为 0 判断业务。

业务码怎么分段

业务码多起来后，最容易出现的局面是随手递增：今天 1001，明天 1002，半年后没人说得清 1043 属于哪个模块。分段是成本最低的治理手段，按业务域划出万位区间很常见。

一份可以直接起步的分段如下，五位数字，首位表示大类：

码段 归属 示例含义
0 成功 无
10000-19999 通用与鉴权 参数错误、未登录、无权限、限流
20000-29999 用户与账号 用户不存在、手机号已注册、密码错误
30000-39999 订单与商品 库存不足、订单状态不允许、商品下架
40000-49999 支付与资金 余额不足、重复支付、退款失败
50000-59999 系统与依赖 数据库错误、下游超时、内部错误

段内还可以按百位分组，例如 20100 至 20199 留给注册登录，20200 至 20299 留给资料修改。好处是看到码就能猜到位置；代价是段位表必须写进项目 README，代码里用常量而不是魔法数字。

两条纪律值得提前定下：已发布的码不复用，下线功能把码标记为废弃即可；码段只增不改，新增模块申请新段。更完整的码段治理、文档与客户端契约，属于错误码规范层面的工作。

中间件统一收口

错误在 Handler 里产生，但响应不该由每个 Handler 各自拼装，否则封套迟早走样。Gin 提供 c.Error(err)，它把错误追加到 c.Errors 而不立即写响应，适合“Handler 只报告，中间件统一输出”的分工。

参数校验错误的转换

参数错误是入口处最高频的错误，也最容易泄露框架细节。Gin 1.3 的绑定依赖 validator.v8，错误是英文的校验描述，直接返回给用户既不好看，也不稳定。

字段名来自结构体定义，不含用户输入，拼进文案是安全的；validator 的原始错误只作为 cause 进日志。校验只在入口做一次，Service 层默认拿到的是已校验的值，否则同一套规则会在多层重复维护。

校验规则怎么写、自定义 tag 如何注册，属于参数校验的话题。本文只关心“校验失败之后怎么变成统一响应”。

日志与响应分离

统一封套之后，最需要守住的边界是：响应只给可公开的信息，内部细节只进日志。这条线一旦模糊，轻则暴露实现，重则泄露数据。

具体做法有三条：message 永远来自常量或消息表，不拼接 err.Error()；cause 只在日志里出现，且用 %+v 打出堆栈；日志记下路由、方法、业务码、用户标识和请求标识。文案给用户看，日志给研发看，两者不该共用一段文本。

不要记录完整请求体。注册、支付接口的请求体里有手机号、身份证、银行卡，日志往往由多个团队共用，写入即扩散。确需排查时只记录脱敏字段或字段名。响应体里也不要带堆栈。

小结

统一响应的核心不是把 JSON 包一层，而是把成功与失败的表达变成全站唯一的约定。封套用 code/message/data，code 为 0 表示成功，分页固定成结构，空列表返回空数组。请求本身有问题用 4xx，业务规则拒绝用 200 加业务码，服务内部错误用 500 且不暴露细节。

错误用 AppError 承载码、文案、状态码与内部原因，跨层包装交给 pkg/errors，判断时先 errors.Cause 再断言，不要比较字符串。Handler 只调用 Fail，由中间件统一映射并写响应，panic 也走同一套封套。

对外只给可公开文案，堆栈、SQL、下游地址留在日志，用请求标识把两端串起来；文案集中到消息表，日志里记码不记译文。用表驱动测试和 httptest 锁住这些约定，新增模块就只剩申请码段、注册错误变量。码段治理、文档生成与客户端契约，是另一层问题。
