命令执行与反序列化漏洞

命令执行与反序列化是两类看起来相隔很远、结果却很相似的漏洞：攻击者都不需要登录服务器，只要把一段精心构造的数据送进应用，就有机会让服务器替自己执行代码。本文从防御视角梳理这两类问题的成因、常见入口与识别方法，重点放在如何写出不把输入拼进命令的代码，以及如何避免把不可信数据还原成对象。文中的示例均为无害演示，适合已经能独立开发 Web 服务、准备做安全整改的后端读者。

命令执行漏洞：输入如何变成系统命令

命令执行漏洞的本质，是应用把用户可控的数据当成了程序或命令的一部分。系统调用、shell、外部工具本身没有错，错在边界：数据原本只是“值”，却在拼接、传参或寻址时变成了“结构”。结构一旦被输入改写，攻击者就能追加命令、改变选项，或让程序访问本不该访问的路径。

shell 能识别的结构远不止分号。管道符可以让前一条命令的输出成为后一条命令的输入，& 可以把命令放到后台，反引号和 $() 会做命令替换，换行与重定向同样能改变执行流程。很多开发者以为“在输入两边加一对引号就安全了”，但只要引号可以被闭合，后面的内容依然会被当成命令。

命令拼接、参数注入与路径注入

虽然表现相似，成因却可以分成三类，修复手段也各不相同。

第一类是命令拼接，也就是上面看到的写法。用户输入进入 shell 命令行文本，shell 元字符改变了命令的数量和结构。它的根源是“把数据拼进了代码”，只要还经过 shell，黑名单就很难堵全。

第二类是参数注入。程序已经改用参数数组，不经过 shell，但输入仍然作为一个独立参数传给了外部工具。如果这个参数以 - 开头，就可能被工具当成选项。例如某个转换命令把用户提供的文件名放在末尾，攻击者传入一个形如 --output=/some/path 的值，工具就可能把结果写到攻击者指定的位置，或者去加载一个外部配置文件。参数数组保证了“一个元素就是一个参数”，却不能保证“这个参数的语义是安全的”。

第三类是路径注入。输入被当作文件路径使用，程序既没有做规范化，也没有限制根目录，攻击者用 ../ 就能跳出预期目录，读取或覆盖任意文件。如果这个路径随后又被交给外部程序处理，路径问题就会升级成命令执行。文件名以 - 开头、包含空格或换行，也属于同一类边界问题。

三者的共同点，是程序信任了输入的“语义”，而不只是信任了它的“类型”。因此防护也要分层：结构层面避免 shell，参数层面做白名单与语义校验，路径层面做规范化与根目录约束。任何一层单独使用都不够稳妥。

常见入口：命令执行藏在哪里

命令执行并不只出现在明显的“执行命令”按钮后面。只要某个功能需要调用操作系统，而输入又能影响调用的方式，就可能成为入口。下面几类场景在 2018 年的企业系统里仍然很常见。

CGI、表单与请求头

早期的 CGI 程序为每个请求启动一个进程，脚本里直接读取 QUERY_STRING 或表单字段，再拼进系统命令。这类系统今天看来老旧，但在网络设备管理页、监控平台、打印服务和中后台系统里仍有大量存量。一个典型的例子是日志处理脚本，把 User-Agent 原样拼进 echo 命令写入访问日志；攻击者只要伪造一个带分号的请求头，就能在服务器上执行命令，甚至不需要访问特定页面。

表单字段、URL 参数、Cookie、上传文件名，都在同一条信任边界上。尤其是文件名：很多程序认为“文件上传成功，名字总归安全”，但文件名同样由客户端决定，可以包含空格、引号、分号和路径分隔符。

图片处理、PDF 转换与文档预览

图片缩略图、格式转换、PDF 预览是命令执行的高发区。应用通常会把上传文件交给 ImageMagick、GraphicsMagick、ffmpeg、Ghostscript 或 LibreOffice 处理，调用时难免拼接文件名、尺寸、格式等参数。2016 年 ImageMagick 曾曝出与图像处理相关的命令执行问题，说明“只是处理一张图片”同样会碰到系统命令。

危险还在于运行身份：转换服务常以较高权限运行，甚至直接使用 root，一旦被利用，影响面远超普通 Web 进程。PDF 转换、视频转码、Office 文档预览也是同样的道理：输入是文件，输出是文件，中间却经过了一长串外部程序与参数。

备份脚本与运维接口

备份脚本喜欢用 shell 写，因为管道和重定向最方便。数据库名、备份目录、时间戳如果来自 Web 配置页，就可能被拼进 mysqldump、tar、gzip 组成的命令链。一个看似无害的“按库名备份”功能，只要库名没有校验，就可能变成任意命令执行。

运维接口的问题更直接：ping 检测、端口探测、路由追踪、日志检索、服务重启，这些功能天生就要和系统打交道。开发者常把它们放在内网，认为“外网访问不到就没事”。但攻击者可能已经进入办公网，或者通过 SSRF 一类的问题从外网触达内网服务。内网不是信任边界，权限才是。

防护：把命令当数据，而不是字符串

防护的核心思路只有一句：不要让输入参与命令结构的构造。具体落地时，可以按“调用方式、输入校验、运行环境、可观测性”四层来做。

白名单与语义校验

对输入做校验时，白名单永远优于黑名单。黑名单需要枚举所有危险字符，漏掉一个就可能失效；白名单只放行业务明确需要的形态，边界清晰。以网络诊断为例，如果功能只需要探测固定网段，就应当先解析成 IP，再判断是否落在允许范围内：

最小权限、隔离与日志

运行外部程序的进程应当使用专用低权限账号，禁止登录 shell，只授予完成工作所需的目录权限。图片转换、文档预览这类高风险任务，最好拆成独立服务，放进容器或沙箱，使用只读根文件系统，去掉多余的能力，并限制出网。这样即使被利用，攻击者也拿不到宿主机的完整控制权。

危险函数应当能禁则禁。PHP 可以在配置中关闭 exec、shell_exec、system、passthru、proc_open、popen；Python 代码规范里应禁止 os.system、os.popen 和 shell=True；Java 应避免 Runtime.exec(String) 这种整串调用。禁用不是万能的，但能提高攻击门槛，也能在代码评审时留下明显信号。

日志要记录调用的程序、完整参数、发起用户、退出码与耗时，而不仅记录“成功”或“失败”。主机层可以借助 auditd 记录 execve，并对“Web 服务进程启动 shell”“转换进程启动 curl 或 wget”这类行为设置告警。正常业务很少出现这种进程链，一旦出现就值得立即排查。

反序列化：当数据被还原成对象

序列化把对象变成字节流，反序列化再把字节流还原成对象。麻烦在于，许多格式不只记录数据，还记录“这是什么类”，并在还原时调用类里的特定方法。攻击者一旦能控制字节流，就能决定让哪个类被实例化、让哪个方法被触发。

Java、PHP 与 Python 的差异

Java 原生序列化会把类名、字段和 serialVersionUID 写进流中，ObjectInputStream.readObject 按名字加载类，并调用 readObject、readResolve 等钩子。单个类通常无害，但依赖库里可能存在一串从入口走到执行的可用类，也就是常说的 gadget 链。它的利用需要 classpath 中恰好有合适的类，条件更苛刻，但一旦成立，后果往往很直接。

PHP 的 unserialize 会把 O:4:"User":... 这样的字符串还原成对象，并在对象销毁、唤醒或字符串化时触发 __destruct、__wakeup、__toString。攻击者同样是在应用代码里寻找属性可控、方法可串联的链。PHP 7 起可以给 unserialize 传入 allowed_classes，把可还原的类限制在白名单内，这是成本很低的加固手段。

Python 的 pickle 更直接：流里可以描述“调用哪个函数、传什么参数”，__reduce__ 的返回值就是可调用对象与参数元组，loads 时会被执行。官方文档因此明确说明，pickle 不适合处理不可信数据。

三者的风险差异可以概括为：Java 需要“有类可用”，PHP 需要“有链可走”，Python 则把“调用什么”直接写进了数据。结论一致：数据来自外部时，不要交给原生反序列化。

识别：请求里的序列化痕迹

Java 序列化流以 AC ED 00 05 开头，base64 编码后通常以 rO0AB 开头，Content-Type 可能是 application/x-java-serialized-object。PHP 序列化数据常出现 O:、a:、s: 等标记，多藏在参数或 Cookie 里。Python pickle 的协议 3 和协议 4 以 \x80\x03、\x80\x04 开头，base64 后常见 gAN、gAS 前缀。

这些特征只适合作为检测线索。攻击者可以多次 base64 编码，也可以把数据放进 gzip 再传输，Java 流经 gzip 后常见的 H4sI 开头就是一例。判断时要先解码、再匹配魔数，同时结合接口用途与 Content-Type，不能只靠一条规则。

反序列化防护

最稳妥的做法是不反序列化不可信数据，接口一律使用 JSON 这类纯数据格式。确实需要跨进程传递对象时，也要让数据只携带值，不携带类型。若短期无法改造，至少加上签名校验，用 HMAC 确认数据来自可信方，并做好密钥管理；接收端再配合类型白名单，Java 使用反序列化过滤器，PHP 使用 allowed_classes，Python 拒绝来自网络的 pickle。

依赖治理同样重要。用不到的 gadget 库应当移除，版本要及时更新，构建时引入依赖扫描，别让旧版集合工具、表达式库长期留在 classpath 里。运行反序列化逻辑的进程要低权限，限制出网，避免被利用后直接连接外部地址。

检测与响应

WAF 与 IDS 可以围绕“解码后的魔数、异常的 Content-Type、参数中的序列化标记”建立规则，主机侧则关注 Java、PHP、Python 进程是否启动了 shell 或发起异常外连。日志至少留存六个月，发现可疑请求后先隔离主机、保留内存与磁盘镜像、封存访问日志，再轮换密钥并重装系统。完整的处置流程属于应急响应范畴，本文不展开。

小结

命令执行与反序列化的共同点，是数据越过了信任边界。前者靠参数数组、白名单与最小权限，后者靠拒绝原生反序列化、类型白名单与依赖治理。SQL 注入针对的是数据库查询语义，属于另一条边界，本文不展开。把上述写法变成默认习惯，比事后堆规则更有效。
