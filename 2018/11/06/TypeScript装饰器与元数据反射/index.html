TypeScript 装饰器与元数据反射

本文属于《TypeScript 学习路线》第 70/74 篇
上一篇系列目录下一篇

在 NestJS、TypeORM、Angular 这些项目里，控制器和实体类上总是挂着一串 @Controller、@Get、@Column 之类的写法。它们看起来像注解，实际上只是 TypeScript 在编译期替我们调用的一次普通函数。本文从编译产物出发，把五种装饰器的签名、求值与调用顺序讲清楚，再用 reflect-metadata 实现一个能跑起来的依赖注入容器，最后说明它与 TC39 标准提案的差别，以及几个容易踩的坑。读完你应该能自己写出路由、校验这类装饰器，并看懂框架源码里那层 design:paramtypes 的含义。

装饰器到底是什么

如果只看语法，装饰器像是给类加标注：在类、方法、属性、访问器或者参数前面写一个以 @ 开头的表达式。但 TypeScript 并没有为它发明新的运行时对象，也没有在类型系统里留下什么“注解”信息。装饰器是一段在类定义时被自动调用的函数，编译器负责把这次调用插进生成的 JavaScript。换句话说，它是语法糖，底下是普通的函数调用。

既然本质是函数调用，要回答的就是求值、调用顺序和参数这三件事。

五种装饰器与它们的签名

TypeScript 允许装饰器出现在五个位置，每个位置对应一个类型别名，签名都可以从 lib.es5.d.ts 里查到。下面的表格是写装饰器时最该记住的一张表。

位置 类型 运行时参数
类 ClassDecorator target: Function
方法 MethodDecorator target, key, descriptor
属性 PropertyDecorator target, key
访问器 MethodDecorator target, key, descriptor
参数 ParameterDecorator target, key 或 undefined, index

几处容易混淆。第一，访问器复用了 MethodDecorator，因为第三个参数同样是描述符，只是 value 换成了 get 和 set。第二，参数装饰器的 key 在构造参数上是 undefined，此时 target 是构造器。第三，静态成员的 target 是构造器而不是原型。这个区别处理元数据时很关键，同一个键名会挂在两个不同的对象上。

记住一句话就够了：工厂自上而下，装饰器自下而上。后面的顺序问题，基本都是这两句话的推论。

类装饰器：改构造器，或者换一个类

类装饰器只有一个参数，就是构造器。它的返回值决定了后续行为：返回 void 就地修改，返回一个函数则替换原类。三种常见用法分别是打标记、登记注册表、派生子类。

方法装饰器：拿到描述符就能改行为

方法装饰器是这套机制里最有用的一个。它拿到 target、key、descriptor，其中 descriptor.value 就是原方法。把它替换成新函数并在内部调用原函数，就能实现日志、耗时、缓存、重试、权限判断，这也是各种“切面”在 TypeScript 里的落地方式。

属性装饰器：只能看到原型和键名

属性装饰器的签名最短，只有 (target, key) 两个参数，返回值会被忽略。这不是疏忽：属性装饰器运行时实例尚未构造，根本没有“值”可供改写。它拿到的 target 是原型（实例属性）或构造器（静态属性），key 是属性名。

想在赋值时插入逻辑，只有一条路：在原型上安装访问器。因为构造函数里的 this.count = 0 会沿着原型链查找 setter，所以拦截是有效的：

跑起来会先看到 count: undefined -> 0，再看到 count: 0 -> 1。第一次输出来自字段初始化：count = 0 被编译成构造函数里的赋值，赋值触发原型上的 setter，此时 _count 还不存在，旧值是 undefined。这说明访问器确实能拦住初始化，也提醒我们初始化顺序会影响日志和校验。

访问器装在原型上，被所有实例共享；真正的数据存在每个实例自己的 _count 上，实例之间不会串。两个约束：原型上不能有同名属性遮蔽，configurable 要留成 true 以便子类再次装饰；内部存储的键要避免和用户字段重名，实践中用 Symbol 或加前缀。

更多时候，属性装饰器的作用不是拦截赋值，而是“记一笔”：把“必填”“最大长度 32”这类规则写进元数据，交给校验器在运行时读取。它只负责保存声明期的意图，这是理解元数据方案的钥匙。

还要澄清一个误解：属性装饰器不能改变类型。给 name: string 加上 @optional 不会让它变成可空，编译器依然要求赋值；类型层面的变化只能靠类型声明完成，装饰器只影响运行时。

参数装饰器：下标是唯一的位置信息

参数装饰器的签名是 (target, key, parameterIndex)。构造参数上 key 为 undefined，target 是构造器；方法参数上 target 是原型，key 是方法名。它的返回值同样被忽略，也就是说参数装饰器无法改变传进来的实参，也无法阻止调用。

参数装饰器还有一个限制：它不能装饰构造函数之外的普通函数参数，箭头函数、函数声明、方法类型签名都不行。能加 @ 的只有类声明、类成员及其参数，这一点在写工具函数时经常被忘记。

元数据反射：把类型信息留到运行时

JavaScript 的类型在编译后就消失了，design:paramtypes 之所以存在，是因为编译器主动把类型写成了值，承载它们的是 reflect-metadata。它给全局 Reflect 补上 defineMetadata、getMetadata、getOwnMetadata、hasMetadata、deleteMetadata 等方法，外加一个能当装饰器用的 Reflect.metadata。内部是一张 WeakMap，键是目标对象，值是按属性键索引的 Map，目标被回收时元数据随之释放。这套 API 至今是社区约定而非 ECMAScript 标准，版本停在 0.1.x。

三个由编译器写入的键

打开 emitDecoratorMetadata 后，只要某个声明上至少有一个装饰器，编译器就会为它追加 design:type、design:paramtypes、design:returntype 中的若干项。规则如下：

键 挂在哪个目标上 值的含义
design:type 属性、方法 属性类型；方法本身固定为 Function
design:paramtypes 类、方法 参数类型数组，顺序与声明一致
design:returntype 方法 返回类型，构造函数没有这一项

类型到值的映射有一套固定规则：string 变成 String 构造器，number 变成 Number，boolean 变成 Boolean，数组变成 Array，类类型变成类本身，void 变成 undefined，而接口、联合类型、字面量类型、泛型参数一律退化成 Object。any 同样是 Object，所以从元数据上无法区分“声明成 any”和“声明成接口”。这也决定了注入的边界：能用类作令牌的依赖可以自动解析，用接口抽象的必须显式标注令牌。

    B --> D["生成 __param(0, Inject(UserRepository))"]

装饰器工厂：用闭包保存配置

不带参数的装饰器直接写函数就行，@sealed 后面跟的就是函数本身。一旦需要配置，就必须再包一层：外层函数接收参数，返回内层函数，内层函数才是真正的装饰器。@Controller("/user") 里的 Controller("/user") 是一次普通调用，它的返回值才是挂在类上的装饰器。

两个函数都返回 ClassDecorator 或 MethodDecorator，类型标注写在返回位置比写在参数上更清楚。prefix 之所以能保留，是因为内层函数形成了闭包；外层执行完，作用域被内层引用着，不会消失。于是 @Controller("/user") 和 @Controller("/order") 各自持有一份互不干扰的配置。

闭包也带来限制：配置在类定义时就固定了。想根据环境变量改变前缀，只能在工厂执行的那一刻读取，之后再改环境变量不会影响已经创建的闭包。如果需要动态配置，就得让闭包捕获一个可变对象，而不是字符串。

工厂最容易犯的错是漏掉括号。写成 @Controller 时，编译器会试着把类本身当作 prefix 传进去，多数情况下直接报参数类型不匹配；如果工厂参数是 any 或者可选，它就静默返回一个装饰器，把类注册到错误的前缀上，等到请求 404 才发现。

执行顺序：一条容易记错的规则

把顺序问题拆成三个维度，就不会乱。

第一个维度是同一个目标上的多个装饰器。表达式自上而下求值，函数自下而上调用。两个 @tag 叠在一个方法上，先求值上面那个的工厂，再求值下面那个的工厂，然后先调用下面那个。

第二个维度是不同种类的目标。同一个类里，参数装饰器最先应用，然后是属性、方法、访问器装饰器，最后才是类装饰器。成员之间按声明顺序，静态成员和实例成员混在同一个序列里，只是挂载的对象不同。

第三个维度是继承。父类先定义，父类的装饰器先执行；子类定义时再执行子类的。类装饰器不会“继承”，父类被替换成子类构造器这件事不会自动作用到子类身上。但元数据会沿原型链被 getMetadata 找到，这是容易被忽视的差异。

事务

事务装饰器的套路和方法包装完全一样，只是把 try/catch 换成了提交与回滚：

它有三个隐含假设。方法必须返回 Promise，否则 await 立刻通过，事务在业务完成前就提交了；方法内部必须使用同一个 conn，若内部又调用 pool.query，那条语句根本不在事务里；嵌套调用不会自动合并事务，内层方法再被装饰一次就会另开连接。真实项目通常用请求级上下文保存连接，装饰器只负责从上下文取。

这三类需求说明了一件事：装饰器擅长“把横切逻辑挂到声明上”，不擅长表达复杂控制流。路由、校验、事务、缓存、鉴权都是典型的横切关注点，所以最适合用装饰器实现。NestJS 正是把这一点做到极致，@Controller、@Injectable、@UseInterceptors 全部建立在 experimentalDecorators 与 emitDecoratorMetadata 之上；模块划分与控制器用法属于另一个话题，本文不展开。需要强调的是，框架的便利来自约定而非魔法：一旦编译配置里少了 emitDecoratorMetadata，整套依赖注入会静默失效。

与 TC39 标准提案的距离

读到这里必须插一句警告：上面所有代码都是“tsc 方言”，不是 JavaScript 标准。2018 年 11 月，TC39 的 decorators 提案仍停留在 stage 2，而且前后改过几版，语义与 TypeScript 的实现相差很远。

差异至少有四处。第一，标准提案只覆盖类本身和类元素（方法、访问器、字段），不包含参数装饰器，@Inject 这种写法没有对应位置。第二，装饰器拿到的是元素描述符而非属性描述符，里面用 kind、name、descriptor 或 initializer 描述被装饰的东西；字段只能通过返回 initializer 改变初始值，不能随手改 descriptor.value。第三，标准提案不鼓励“返回新类”替换原类，类的形状在装饰器运行前就已确定。第四，元数据完全不在提案范围内，design:type 是 TypeScript 自己的约定，Reflect.metadata 也只是社区 polyfill；求值与调用顺序同样被重新定义过，不能拿现在的规则去套。

这意味着两件事。其一，本文的代码在 tsc 下能跑，换成只支持标准提案的编译器就不一定；Babel 7 需要开启 legacy 模式才能对齐现有语义，而且不生成 design:* 元数据。其二，不要假设装饰器代码可以跨工具链移植。把装饰器限制在框架层、业务代码少写元编程，是比较稳妥的策略；如果公共库依赖 design:paramtypes，必须在文档里写清楚“需要开启哪两个编译选项”，否则使用者会在运行时收到一堆 undefined。

标准提案什么时候定稿，2018 年的答案是“不知道”。它已经改了两年，每次改动都牵涉引擎实现和现有框架的兼容。在那之前，experimentalDecorators 就是事实标准，而这个“实验性”标签已经挂了三年多。

几个必须知道的坑

第一个坑是 reflect-metadata 的引入时机。它必须在任何带装饰器的模块求值之前加载，最稳妥的写法是入口文件第一行 import "reflect-metadata";。ES 模块按依赖图深度优先求值，入口的第一条 import 最先执行，这个位置可靠。反过来，如果被装饰的类先完成定义，__metadata 会因 Reflect.metadata 不存在而返回 undefined，元数据静默丢失，报错点却在一百行之外。

第二个坑是 emitDecoratorMetadata 的代价。每个带装饰器的声明都会多出若干 __metadata 调用，产物变大；更麻烦的是它把类型位置的引用变成值引用，原本只用于类型标注的 import 编译后被保留，既可能凭空造出循环依赖，也让“类型导入不产生运行时依赖”的常识失效。

第三个坑是循环依赖下的 undefined。模块 A 导入 B、B 又导入 A，先求值的一边是半成品，__metadata("design:paramtypes", [B]) 把这个半成品记下来，容器拿到的就是 undefined。规避手段有三种：改用字符串令牌打断类型引用，把解析延迟到调用时，或者像 NestJS 那样用 forwardRef 显式声明环形引用。

第四个坑是装饰器内部抛错。它在类定义阶段执行，一旦抛出，整个类声明失败、模块加载中断，堆栈却指向类声明那一行。稳妥的做法是做防御性检查，并让错误信息带上类名和成员名，例如 invalid route path on UserController.detail。

第五个坑是工具链差异。同样的源码，tsc 编译后能注入，Babel 编译后可能拿到空数组：legacy 插件只复刻调用顺序，不生成 design:* 元数据，补这块要额外的社区插件，而且对参数装饰器的支持并不完整。团队里有人用 ts-node、有人用 Babel、有人用 ts-loader 时，最好统一编译配置，并在 CI 里加一条冒烟测试：解析一个带依赖的类，断言依赖不为 undefined。

最后两个小问题。getMetadata 沿原型链查找，getOwnMetadata 只看自己，读路由前缀和参数表几乎都该用后者，否则子类会莫名继承父类的配置。属性与参数装饰器的返回值会被忽略，方法装饰器返回 undefined 时沿用原描述符但就地修改已生效，两种风格混用会让结果依赖叠加顺序，建议统一成“总是返回 descriptor”。另外，装饰器不能用在 declare 声明上，declare class Foo 加 @Injectable() 会直接编译报错。

小结

装饰器的本质是编译期插入的函数调用，理解它只需要抓住三件事：表达式自上而下求值，装饰器自下而上调用，不同目标之间按“参数、成员、类”的层次依次应用。五种装饰器里，类和方法的返回值有意义，属性和参数的返回值被忽略；属性装饰器拿不到实例，只能靠原型的访问器或者元数据来间接影响行为。

emitDecoratorMetadata 把类型写成了运行时的构造器引用，reflect-metadata 提供了存放它们的容器，两者合起来才让依赖注入成为可能。三个 design:* 键里，design:paramtypes 最常用，也最容易因为接口擦除和循环依赖而失效，所以生产代码里通常还要配一个显式的令牌机制。

实践上有三条建议：把装饰器限制在框架层和基础设施层，业务代码少写元编程；统一编译配置，并在 CI 里验证一次依赖解析；牢记这套语义属于 tsc 的实验性实现，与 TC39 提案不是一回事，不要假设它可以跨编译器移植。
