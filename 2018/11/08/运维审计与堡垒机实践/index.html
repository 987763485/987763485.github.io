运维审计与堡垒机实践

生产环境的 SSH 端口对办公网开放，出了问题却查不到谁在几点改了什么，这是很多团队在等保测评前才被迫面对的现实。本文从 4A 模型出发，讲清堡垒机的定位、部署方式、账号与授权设计、会话审计的落地细节，以及 2018 年常见的开源与商业选择。读完你应该能为几十到几百台服务器的环境画出可落地的运维审计方案。

为什么需要堡垒机

很多团队的运维入口是这样：生产服务器绑定公网地址，安全组对办公网段放行 22 端口，大家用自己电脑上的终端直接连；Windows 服务器开着 3389，凭据存在本地。日常操作很顺手，问题只在出事之后暴露。

一是追溯不了。日志能告诉你某个地址在凌晨用 root 登录过，但那是办公室出口的地址转换，背后可能是十个人；共用账号时，日志里连“谁”都没有。二是权限收不住，多数人手里是 root 或 Administrator。三是入口太多，人员流动时口令回收不干净。

堡垒机的思路是把“直接访问”改成“经过受控中间层访问”：流量先到堡垒机，由它完成身份校验、权限判断、目标选择、会话录制，再代理到目标主机，目标主机只允许堡垒机网段连入。每次登录因此都有明确的人、时间、目标与完整记录。

4A 模型：账号、认证、授权、审计

4A 是身份与访问管理里常用的四要素模型，国内在运维审计产品的选型与测评文档里被反复引用：

  • 账号（Account）：有哪些主体，以及主体在目标资源上对应什么身份。
  • 认证（Authentication）：怎么证明自己就是这个主体。
  • 授权（Authorization）：这个主体能对哪些资源做什么。
  • 审计（Audit）：谁在什么时候做了什么，事后能不能查清。

四者不是并列，而是有依赖的链条：账号是基础，决定“主体”与“目标身份”两端能否对上；认证是入口；授权是边界；审计是兜底，前三层配置得对不对只能靠记录验证。缺一环，其余三环都会失效。

落地时四者对应不同配置对象：账号对应“堡垒机用户 + 主机账号”，认证对应“认证源 + 二次认证”，授权对应“角色 + 资产授权 + 命令规则”，审计对应“录像 + 操作日志”。把这张映射记住，就不会把“开一台机器”和“给一个管理员角色”混为一谈。

部署架构：代理网关与高可用

部署要回答两个问题：运维流量怎么绕进来，又怎么出去。最常见的是网关（代理）模式：堡垒机是唯一入口，运维人员连它的 SSH 或 RDP 端口，在界面上选目标资产，堡垒机再用托管的主机账号去连目标。目标主机防火墙只放行堡垒机地址，办公网段不再直连。

这种模式不用改目标主机，也不用动网络设备，代价是所有流量都过堡垒机，带宽、并发连接数与录像写入的磁盘吞吐要提前算够。另一种是旁路模式：交换机镜像一份流量给审计设备，只解析与录像、不阻断，适合已有跳板机或不想改链路的老环境，但只能审计不能管控。

高可用要一起看四个部件：接入层两台设备加虚拟地址；配置与会话索引放共享数据库；录像放共享存储或对象存储；会话做粘性，RDP 中途切节点会断。数据库常是隐藏单点，备份与恢复演练不能省。容量粗算也简单：SSH 录像从几十 KB 到几 MB 都有，RDP 图形录像一小时几百 MB 并不奇怪，按并发、时长与留存期相乘再留一倍余量即可。

账号管理：一人一号与账号托管

堡垒机最容易做歪的是账号。第一个原则是一人一账号，禁止部门共用、禁止把管理员账号发给多人，共用账号等于放弃追溯。

第二个原则是人的账号与主机账号分离。运维只知道自己在堡垒机上的账号，不知道目标主机 root 的口令；堡垒机按授权决定谁能用哪个主机账号登录哪台资产。口令托管之后，改密变成批量动作：定期改密、改密后立即验证、失败告警。两个坑要避开，一是自动化脚本会被改密打断，需要单列并排除在计划外，或者改用密钥；二是改密窗口要避开业务高峰。

第三个原则是账号来源收敛。常规账号从 LDAP 或 AD 同步，离职调岗由人事流程驱动，至少每周比对一次，把“人走了账号还活着”挡在测评之前。

认证与授权：把门禁做在授权上

认证侧先接认证源，再叠二次认证。LDAP 或 AD 是最常见的认证源，口令与锁定策略由目录统一管理；二次认证用动态口令或短信验证码，管理员账号必须强制开启，因为堡垒机管理员权限最高，一旦被撞库，前面的审计设计都白做。

授权侧建议用角色而不是按人逐台点选：一个角色等于一组资产、一组主机账号、一组命令规则和一条时间策略，人只挂角色。命令规则做两层，黑名单拦住格式化磁盘、批量删除、改防火墙，白名单用于核心库，只放行少数命令；高危命令可配二次确认。

时间策略常被忽略：生产库登录限定在变更窗口内，窗口外拒绝或转审批，能挡掉不少“顺手看一眼”。但命令过滤的边界要认清，它匹配的是终端里敲进去的文本，脚本、编码内容、编辑器里调外部命令都能绕过；它的价值是减少误操作，真正的边界是资产授权与账号隔离。

会话审计：记录、回放与留存

会话审计由三类记录组成，不能互相替代。登录日志记元数据：谁、什么时间、从哪个地址、登录哪台资产、用了哪个主机账号、持续多久，体量小、查询快，是排查的第一入口。命令记录是解析终端输入流得到的文本，可按命令检索，但有遗漏和误判。终端录像保存完整输入输出，RDP 是图形录像，体积大、按需调取。

文件传输审计要单独配置：SFTP 上下行的文件名、大小、路径都要记，敏感目录可禁止上传或下载。剪贴板是图形协议特有的通道，策略一般是允许、禁止或单向。

留存与完整性决定审计能否站住脚。日志留存不少于 6 个月是等保的常见要求，1.0 与 2.0 报批稿的表述位置不同，方案里要写清依据。录像生成时计算摘要并集中存储，存储账号与运维账号分离，防止“改完机器再删录像”；堡垒机管理员自己的授权变更、改密、删录像同样要审计。日志增长快，建议分级：命令记录长期保留，图形录像按资产等级保留，过期归档而不是删除。

运维流程：申请、审批、访问、回收

技术手段要配流程才闭环：申请人提交资产、账号、用途和起止时间，负责人审批，堡垒机按结果生成带有效期的授权，到期自动回收。

工单与堡垒机的对接程度决定流程会不会被绕过。手工双录最容易脱节，审批单批了却没人改授权；有条件就用接口打通，审批通过回调创建授权，到期回调删除。临时授权一定带期限，半天、一天、一周分档。

紧急通道要提前设计：保留一到两个应急账号，口令封存、使用即告警、事后补单。没有紧急通道的团队，最后一定有人私留后门账号。发布走独立入口，用服务账号和密钥，权限按环境收窄、定期轮换。

常见落地问题

上线时踩到的坑，大多不是产品能力问题，而是环境适配问题。老系统不支持：Windows Server 2003 一类老系统的 RDP 版本低，图形代理可能连不上；只支持 telnet 的设备没有加密，需要协议代理并托管口令；某些数据库客户端要求直连端口，只能转发或单独纳管。

网络隔离。办公网与生产网常是单向或完全隔离，堡垒机放在哪一侧决定链路：放生产侧，运维要先能到堡垒机；放办公侧，堡垒机到生产要通。跨网段还要收窄端口开放范围，别让堡垒机自己变成新的暴露面。

性能与体验。图形会话卡顿通常来自链路时延、录像写入、加密开销，把设备放在离运维与目标都近的位置最有效，录像先写本地盘再异步转储更稳；体验差会直接导致大家想办法绕过。告警误报则多是黑名单正则写得太宽，把查看日志的命令也拦了，被误拦几次运维就要求关规则，做法是收窄黑名单、其余交给白名单与二次确认。日志太大靠分级留存与归档控制。

与等级保护条款的对应

等保 1.0（GB/T 22239-2008）里直接相关的是三组控制点：身份鉴别要求唯一标识、口令复杂度与登录失败处理；访问控制要求最小权限与职责分离；安全审计要求覆盖每个用户、记录重要事件、保护审计记录不被删改。堡垒机的用户体系、角色授权、会话录像正好逐条对上。

2.0 在 2018 年 11 月仍是报批稿，正式标准尚未发布，做方案只能按报批稿的身份鉴别、访问控制、安全审计控制点做差距分析，并在文档里注明报批状态。报批稿强调集中审计与审计记录保护，对堡垒机是利好，但不要对外写成“已按 2.0 合规”。日志留存不少于 6 个月是常见要求，引用时写清依据来自哪个标准版本。

选型与自建

开源路线以 JumpServer 1.x（2018 年的版本）为代表：Python 与 Django 体系，Luna 提供 Web 终端，Coco 承担 SSH 代理与命令拦截，Guacamole 负责 RDP 等图形协议，支持 LDAP 认证、资产授权与会话录像。它适合有研发能力、资产规模中等的团队，自建成本不止机器，还有存储、升级、漏洞响应和值班。

商业产品优势在协议覆盖全、录像与报表成熟、有原厂支持，代价是采购与绑定成本；云厂商方案开箱即用，但跨云与混合云受限，审计数据出网要单独评估。评估维度建议固定：协议与资产覆盖、并发与录像性能、认证源集成、授权粒度、审计完整性、高可用、接口能力、漏洞响应、总拥有成本。

上线前检查清单

上线前建议逐项确认：

  1. 资产清单完整，协议与版本已核对，不能纳管的资产有替代方案。
  2. 目标主机防火墙只放行堡垒机地址，办公网直连已关闭。
  3. 一人一账号，共享账号清理完毕，管理员强制二次认证。
  4. 主机账号全部托管，改密计划与自动化账号白名单已确认。
  5. 角色按最小权限配置，没有默认全量授权。
  6. 命令规则做过误拦测试，高危命令二次确认可用。
  7. 录像、命令日志、登录日志都能检索，留存期达标。
  8. 堡垒机管理员的操作本身有审计，录像不可被运维删除。
  9. 高可用与备份做过切换演练，数据库单点有预案。
  10. 审批与到期回收跑通一次完整闭环。

小结

堡垒机的价值不在于多一个登录入口，而在于把“人、账号、权限、行为”绑在一起。落地顺序建议先收敛入口和账号，再谈命令过滤与精细授权；先保证录像与日志可用，再谈报表。工具只是载体，决定效果的是授权模型是否收敛、流程是否闭环、审计记录是否可信。
