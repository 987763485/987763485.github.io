pandas 数据处理入门

本文属于《Python 学习路线》第 27/29 篇
上一篇系列目录下一篇

表格数据几乎每个后端项目都会遇到：运营要的销售报表、财务要的对账文件、排查问题时导出的订单明细。用纯 Python 的列表和字典处理，代码很快会淹没在循环与边界判断里。本文以一份虚构的销售订单数据为例，按读取、清洗、变换、聚合、输出的顺序，走一遍 pandas 0.23 的常用操作，并标出容易踩的坑。读完之后，你应该能把一份杂乱的 CSV 整理成结构清楚、可以直接交付的结果。

先看全景

一份表格从原始文件到最终报表，通常要经过几个固定阶段：先把文件读成 DataFrame，再清洗缺失值与错误类型，接着做列选择、派生列、排序等变换，然后按业务维度分组聚合，最后写出 CSV 或 Excel。本文的章节顺序与这条链路一致，示例统一使用同一份虚构的销售订单数据。

flowchart TD
    A[读取 CSV] --> B[清洗 缺失值与类型]
    B --> C[变换 选择 新增 排序]
    C --> D[聚合 按区域与品类]
    D --> E[输出 CSV 或 Excel]

本文只讨论表格层面的处理：带标签的行列、对齐、缺失值与分组聚合。ndarray 的内存布局与广播规则属于 NumPy，这里不展开。

为什么需要 pandas

后端开发里有一类需求反复出现：把业务库导出的 CSV 做成报表，按区域汇总销售额，核对两份表格的差异。这类工作有三个共同点：数据是二维的，每一列有自己的含义，列与列之间靠行号或主键对齐。

用纯 Python 处理，通常是一个列表装若干个字典，然后写循环。取一列要遍历，算合计要再遍历，缺失值要自己判断 None，两份表按主键拼在一起还得手写字典索引。难点不在逻辑，而在重复；一旦需求从“按区域汇总”变成“按区域和品类两个维度汇总”，循环就要重写。

Excel 适合看，不适合批量做。数据量一大操作就迟滞，处理逻辑也很难版本化、难测试。pandas 补的正是这个位置：它把二维表抽象成带标签的对象，列有名字，行有索引，缺失值、对齐、分组聚合都有现成的、经过优化的实现。同样的逻辑写成十几行 pandas 代码，可以放进脚本、定时任务，也可以被单元测试覆盖。

不过 pandas 不是数据库。它适合单机、内存放得下的数据集，量级通常在几十万到几百万行；再大的数据应该交给数据库或分布式计算。把它当作 Python 里的表格处理层即可。

Series 与 DataFrame

pandas 只有两个常用结构。Series 是一维的带标签数组，可以理解为“一列数据加一个索引”；DataFrame 是二维表，由多个共享同一索引的 Series 组成，既有行索引 index，也有列标签 columns。

索引不是行号。默认的 RangeIndex 是 0、1、2 这样的位置，但你可以把它设成订单号、日期等有业务含义的键；列标签则是表头字符串。二者合起来，让“取某一行某一列”可以用名字表达，而不是数位置。

每一列还有自己的 dtype。常见的有 int64、float64、object（字符串或混合类型）、datetime64[ns]、bool，以及用于省内存的 category。dtype 决定了这一列能做什么运算：object 列的加法是字符串拼接，只有数值列才是算术。读数据时类型不对，后面的筛选和聚合都会出错，所以第一步往往是看 df.info() 或 df.dtypes。

创建方式有三种典型入口：字典构造、列表构造、文件读取。字典的键成为列名，值成为列；列表的每个元素是一行；实际项目里绝大多数 DataFrame 来自 read_csv、read_excel 或数据库查询。

读取：read_csv 的常用参数

read_csv 是入口，也是坑最多的地方。它的默认假设是逗号分隔、第一行是表头、UTF-8 编码，只要现实数据偏离一点，就可能读出奇怪的列名，或者得到一张空表。

几个参数值得先记住。sep 指定分隔符，制表符用 sep=’\t’，分号用 sep=’;’；header=None 表示文件没有表头，这时配合 names 传入列名列表；dtype 显式声明类型，最典型的是把订单号、邮编这类“看起来像数字的编号”声明为 str，否则前导零会被吃掉；parse_dates 把日期列直接解析成 datetime；na_values 补充哪些字符串应当视作缺失值，比如 ‘NULL’、’-‘；usecols 只读需要的列，nrows 先读前几百行看结构。

中文环境有两个高频问题。第一是编码：Windows 上 Excel 另存的 CSV 常常是 GBK，用默认 UTF-8 读取会抛 UnicodeDecodeError，需要 encoding=’gbk’；反过来，UTF-8 文件可能带 BOM，读进来第一列的列名会变成 ‘\ufefforder_id’ 这种样子，打印 df.columns 才发现，解决办法是 encoding=’utf-8-sig’。第二是分隔符：有些系统导出的“CSV”其实用分号或制表符，直接读只会得到一列，先看一眼原始文件再决定 sep。

稳妥的习惯是读完之后立刻执行 df.head()、df.shape、df.dtypes，确认行列数、列名和类型符合预期，再往下写逻辑。

选择与过滤

选择数据有四套写法，分工要清楚。df[‘region’] 取一列，返回 Series；df[[‘region’, ‘amount’]] 取多列，返回 DataFrame；df[0:5] 这种切片按位置取行，但只对行有效，不要用它取列。

loc 按标签选，iloc 按位置选。df.loc[3, ‘amount’] 取索引为 3 的那一行的 amount；df.iloc[3, 1] 取第 4 行第 2 列。loc 的切片是闭区间，iloc 的切片是左闭右开，后者和 Python 列表一致，前者不一致，容易记混。需要同时限定行列时，df.loc[mask, [‘region’, ‘amount’]] 是最清晰的写法。

布尔索引是日常用得最多的。df[df[‘amount’] > 1000] 选出金额大于 1000 的行。多个条件要用 &、|、~，并且每个条件加括号，因为比较运算符的优先级高于位运算符。写成 df[df.a > 1 & df.b < 2] 会出错，或者得到和预期相反的结果。

链式赋值是新手最容易踩的坑。df[df[‘amount’] > 1000][‘discount’] = 0.1 会触发 SettingWithCopyWarning，而且可能根本没改到原表：第一步的布尔索引可能返回副本，第二步改的是副本。正确写法是把两步合成一次 loc：df.loc[df[‘amount’] > 1000, ‘discount’] = 0.1。如果确实想基于一份数据独立修改，先显式调用 .copy()，让意图清楚。

调试阶段可以把 pd.options.mode.chained_assignment 设为 ‘raise’，让链式赋值直接抛异常，而不是悄悄留下隐患。这个开关适合在开发环境长期打开。

清洗：缺失、重复与类型

真实的表几乎没有干净的。清洗一般按固定顺序走：先看缺失，再处理重复，然后统一类型，最后规范文本和日期。

缺失值用 isna() 或 isnull() 判断，返回同形状的布尔表；df.isna().sum() 能一眼看出每列缺多少。dropna() 删除含缺失的行，how=’all’ 只在整行都空时删，subset 限定只看某几列；fillna() 填值，可以填常数、前向填充 ffill，或者用列的均值。要注意 fillna 默认返回新对象，不写 df = df.fillna(…) 原表不会变；也可以传 inplace=True 原地修改，但更推荐显式赋值。

重复值用 duplicated() 标记、drop_duplicates() 删除。判断“重复”的依据是 subset 指定的列，业务上通常按订单号去重，而不是整行完全一致。去重前先想清楚保留哪一条；需要按时间取最新时，先排序再 drop_duplicates(keep=’first’)。

类型转换用 astype()：把字符串列转成 float 再求和，把编码列转成 category。转换失败会抛 ValueError，说明列里混了脏字符；先用 pd.to_numeric(errors=’coerce’) 把无法解析的值变成 NaN，再决定丢弃还是修正。

字符串处理走 .str 访问器，它把常用的字符串方法向量化：df[‘region’].str.strip()、.str.upper()、.str.contains(‘华东’)、.str.replace(‘市’, ‘’)。比逐行写 apply 更易读，也不容易漏掉异常值。日期用 pd.to_datetime() 转换，无法解析的值传 errors=’coerce’ 会变成 NaT，再用 isna() 找出来。转成 datetime 之后，.dt 访问器能取出年月日、星期，按月汇总很方便。

增删改与排序

新增列直接赋值，pandas 会按索引对齐：df[‘amount’] = df[‘quantity’] * df[‘unit_price’] * (1 - df[‘discount’])。注意是对齐而不是按位置，如果右边来自另一张表，索引不一致处会得到 NaN，这既是保护也是坑。

需要按行做复杂计算时用 apply。df.apply(func, axis=1) 把每一行作为 Series 传给函数，灵活但慢；能拆成列级运算的，优先写成向量化表达式。Series 上的 map 用于值映射，比如把渠道代码映射成中文名，没匹配到的会变成 NaN，通常再接一个 fillna。

改列名用 rename(columns={…})，只改指定的列；drop 删列用 drop(columns=[…])，删行用 drop(index=[…])，默认都返回新对象。排序用 sort_values，多列排序时 by 传列表，ascending 也传列表可以分别指定升降序；按索引排序则是 sort_index()。排序不会改变数据本身，但会影响取前 N 行的结果，做 TopN 时要先排对再取。

分组聚合

分组聚合是 pandas 最有价值的部分，心智模型是 split-apply-combine：按某列的值把行切成若干组，对每组算一个结果，再把结果拼回一张表。

df.groupby(‘region’)[‘amount’].sum() 返回以 region 为索引的 Series。想要多列多指标，用 agg 传列表或字典：df.groupby(‘region’)[‘amount’].agg([‘sum’, ‘mean’, ‘count’])，或者 df.groupby(‘region’).agg({‘amount’: ‘sum’, ‘quantity’: ‘max’})。多列分组传列表：groupby([‘region’, ‘category’])，结果带 MultiIndex，通常接 reset_index() 变回普通列，方便后续输出。

transform 和 apply 的区别要分清。transform 要求每组返回与组内行数相同的值，结果长度与原表一致，适合把组级统计量广播回每一行，比如算每个区域内部的占比：先用 groupby(‘region’)[‘amount’].transform(‘sum’) 得到组内合计，再相除。apply 允许每组返回任意形状，更灵活，开销也更大，能不用就不用。

还有一个常见困惑是 count 与 size：count 只数非缺失值，size 数行数，含缺失时两者结果不同。分组结果并回原表时注意索引对齐，必要时先 reset_index()。

合并：merge 与 concat

实际分析很少只靠一张表。订单表里是区域代码，区域表里是代码对应的负责人和销售目标，需要按代码拼起来。

merge 是数据库式的连接。pd.merge(orders, regions, on=’region’, how=’left’) 左表每行都保留，右表匹配不到的地方填 NaN。how 的取值 inner、left、right、outer 分别对应交集、左保留、右保留、并集。on 指定连接键；两边列名不同时用 left_on 和 right_on；同名列会带 _x、_y 后缀，用 suffixes 改成可读的名字。

理解连接结果的关键是基数。一对一（订单号对订单详情）不会增加行；一对多（一个区域对多个负责人）会让左表的行数膨胀，聚合前要特别小心，否则销售额会被重复计算。merge 之后先看 shape 是否符合预期，是很好的自检；发现行数变多，就回去检查右表的连接键是否唯一。

concat 负责拼接而不是连接。axis=0 纵向堆叠，列名对齐，缺失的列补 NaN，ignore_index=True 重排索引；axis=1 横向拼接，按索引对齐，索引对不上的行会各自留下 NaN。把多个月的 CSV 读成列表再 pd.concat(frames, ignore_index=True)，比在循环里反复追加更清晰。

输出：CSV 与 Excel

分析结果最终要交给别人，输出同样是流程的一部分。

df.to_csv(‘report.csv’, index=False, encoding=’utf-8-sig’) 是最常用的形式。index=False 去掉行索引，否则会多出一列没有名字的编号；encoding 用 utf-8-sig，让 Excel 打开中文不乱码。日期列默认写成完整时间戳，用 date_format=’%Y-%m-%d’ 控制格式；浮点数用 float_format=’%.2f’ 保留两位小数。不写路径时 to_csv 返回字符串，适合直接塞进接口响应或日志。

写 Excel 需要额外的引擎，xlsx 格式用 openpyxl：df.to_excel(‘report.xlsx’, index=False, engine=’openpyxl’)，没装会提示 ImportError，pip install openpyxl 即可。Excel 适合交付，不适合做数据交换的中间格式：它有行数上限，类型也会被 Excel 重新解释，跨系统传输仍然优先用 CSV。

输出前检查列名、索引列、缺失值和数值精度，这些细节决定了别人拿到文件后能不能直接用。

性能与常见坑

pandas 的性能来自底层 NumPy 的向量化运算，一旦退回 Python 层的逐行循环，优势就没了。最常见的反模式是 iterrows：它每行构造一个 Series，还要做类型推断，数据量大时明显变慢；同一列里混有整数和浮点时，取出的值可能整体变成 object。需要遍历时优先 itertuples，或者干脆把逻辑写成列运算。

向量化也是正确性问题：整列运算不会出现循环里改副本、忘记回写的情况。

内存方面，字符串列默认是 object，每个值都是一个 Python 字符串对象，开销不小。取值种类少的列（区域、渠道、状态）转成 category，能明显压缩内存，groupby 时也更省事。数值列可以用 pd.to_numeric(downcast=’integer’) 降低位宽。读文件时用 usecols 只取需要的列，是性价比最高的一步。df.info(memory_usage=’deep’) 可以看到真实占用；普通 info 对 object 列只统计指针大小，容易低估。

最后是链式索引。它可能触发警告，也可能在无意间操作副本；养成“赋值只用一次 loc”的习惯，能避免大部分问题。pandas 的 API 很多，不必一次记全，把读取、清洗、选择、分组、合并、输出这六类操作练熟，日常的表格处理就够用了。

小结

pandas 的价值不在于 API 多，而在于把表格处理中反复出现的操作抽象成了带标签的对象：读取时声明类型与编码，清洗时按缺失、重复、类型、文本的顺序推进，选择时区分 loc 与 iloc，聚合时理解 split-apply-combine，合并时先看基数，输出时别忘 index=False。把这几步固定成模板，再复杂的报表也只是多几列、多几个维度。遇到性能问题时，先检查有没有逐行循环和链式索引，再考虑 category 与列裁剪。
