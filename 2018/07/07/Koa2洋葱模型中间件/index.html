Koa 2 洋葱模型中间件

本文属于《TypeScript 学习路线》第 61/74 篇
上一篇系列目录下一篇

Koa 2 把一个个中间件串成可双向执行的调用链，也就是常说的洋葱模型。本文从 Koa 与 Express 的差异讲起，逐步拆解 await next() 的执行顺序、ctx 的组成、错误处理与路由组织，再给出日志、鉴权、限流、CORS 等可直接复用的中间件。适合已经会用 Express、准备把服务迁移到 Koa 2 的 Node.js 开发者阅读，示例统一使用 JavaScript，TypeScript 工程的配置不在本文范围内。

与 Express 的差异：中间件换了形状

Express 4 的中间件是 (req, res, next) 三个参数，处理完请求直接调用 res.send 之类的响应方法；Koa 2 的中间件则是 async (ctx, next)，没有 res，所有读写都落到 ctx 上。Koa 在 Node 原生 req、res 之外又包了一层 request、response 对象，再用访问器把它们常用的属性和方法委托到 ctx，因此写起来比 Express 少一层解包。

另一个明显差异是路由。Express 4 自带 express.Router，Koa 核心则只负责中间件调度，路由、请求体解析、静态文件都要另装模块，模板渲染可以用 koa-views 接到 ctx.render 上。这种“核心很小、能力靠拼装”的设计让依赖边界更清楚，代价是项目初始化时要自己决定装哪些包。

Koa 1 的中间件是 generator 函数，靠 co 驱动；Koa 2 改用 async 函数，Node 7.6 起原生支持，Node 8 LTS 上可以放心使用。异步函数带来的直接好处是错误可以像同步代码一样抛出：下游某个 await 拒绝，会沿着 Promise 链回到上游的 try/catch，不必层层手写 next(err)。

还要注意，Koa 不会因为某个中间件结束就立即发包，而是一直等到整条链执行完，再由内部统一写出响应。如果所有中间件都没设置 ctx.body，Koa 会返回默认的 404，而不是像 Express 那样把请求挂起。

洋葱模型：await next() 的前后两段

每个中间件都可以写成“前半段、await next()、后半段”的形状。请求先依次执行各层的前半段，到达最内层后，再从最内层往外依次执行后半段。下面用一个三层例子把顺序打印出来，同时在最外层记录耗时并写入响应头。

运行后终端依次输出 A 进入、B 进入、C 处理业务、B 返回、A 返回。await next() 的语义是“把控制权交给下一层，等它整个完成再回来”，所以它后面的代码一定晚于下游全部逻辑。也正因为如此，A 在 await next() 之后设置 X-Response-Time 仍然有效：Koa 要等中间件链全部 resolve 后才真正发送响应，此时响应头还没有冻结。

反过来说，如果下游抛出异常而当前层没有 try/catch，await next() 会以 rejected Promise 结束，后半段不会执行，异常继续往上游走。这也是错误处理必须放在最外层的原因。

后半段常用于收尾：统一加响应头、记录耗时、包装返回结构、做缓存。但它也能改写下游已经设置的 ctx.body 和 ctx.status，这是一把双刃剑，写通用中间件时要克制。

为什么叫洋葱：进入与返回顺序相反

把中间件按注册顺序竖着叠起来，整条链就像一颗洋葱：请求从最外层往里穿，响应从最里层往外冒，进入顺序与返回顺序正好相反。错误处理、日志、跨域、鉴权、路由这五层中间件加上业务处理，走向可以用下图表示。

flowchart TD
    A[请求] --> B[错误处理 进入]
    B --> C[日志 进入]
    C --> D[CORS 进入]
    D --> E[鉴权 进入]
    E --> F[路由匹配 进入]
    F --> G[业务处理]
    G --> H[路由匹配 返回]
    H --> I[鉴权 返回]
    I --> J[CORS 返回]
    J --> K[日志 返回]
    K --> L[错误处理 返回]
    L --> M[响应]

理解这张图，就能理解两个常见现象。第一，越靠外的中间件包住了后面所有逻辑，适合做兜底和全局统计；第二，越靠内层的中间件离业务越近，适合做参数校验和具体响应。

next() 只能调用一次。Koa 内部用 koa-compose 把中间件数组组合成一个 dispatch 函数，并用一个下标记录当前执行到第几层，重复调用会命中检查并抛出错误。简化后的核心逻辑如下：

一旦第二次调用 next()，下游会被重新执行一遍，日志重复、数据重复写入，甚至在响应头已经发出后再次改状态。Koa 选择直接报错 next() called multiple times，比悄悄产生脏数据更容易排查。

最内层的业务中间件通常不调用 next()，它负责生成响应；即使调用了，Koa 也只是让调用落到链尾的空回调，不会报错，但后面已经没有业务逻辑可执行。

另外，next() 必须被 await 或 return。写成 return next() 时后半段没有代码，问题不大；如果既不 await 也不 return，下游会与当前中间件并发执行，异常也不会回到当前层。这是从 Express 迁移过来最容易犯的错。

ctx 里有什么

ctx 是 context 的缩写，每个请求一个实例，贯穿整条中间件链。它上面挂着 request、response、state、cookies、throw 等成员，同时通过委托暴露了大量快捷属性，常用的有 ctx.method、ctx.url、ctx.path、ctx.query、ctx.ip、ctx.body、ctx.status、ctx.type。读写 ctx.body 实际落在 ctx.response 上，读写 ctx.query 实际落在 ctx.request 上。

ctx.state 是官方推荐的请求级传参位置，比如鉴权中间件写入 ctx.state.user，后面的路由直接读取。不要把自定义字段直接挂在 ctx 上，Koa 的委托属性很多，随手挂很容易撞名。ctx.cookies 提供 get 和 set，签名 Cookie 需要先配置 app.keys；ctx.throw 与 ctx.assert 用来主动抛错，前者直接构造 HTTP 错误，后者在条件不成立时抛错。

给 ctx.body 赋字符串时，Koa 默认把 Content-Type 设为 text/plain；赋对象或数组则序列化为 JSON，并在没有显式设置状态码时把默认的 404 改成 200。如果先写 ctx.status = 201，状态码会保留。

需要提醒的是，ctx.request.body 默认并不存在，只有装了 bodyparser 并解析成功后才有值；ctx.request.rawBody 则要在 bodyparser 开启 includeUnparsed 时才保留。

错误处理：把 try/catch 放在最外层

async 函数里的异常会变成 rejected Promise，Koa 的 dispatch 会把它继续往上游抛，所以最外层第一个中间件写一个 try/catch，就能兜住整条链。关键是它必须注册在最前面，否则在它之前执行的中间件出错时没人接。

ctx.throw(400, 'name 不能为空') 抛出的是 http-errors 实例，带有 status、expose 等属性。默认 4xx 的 expose 为 true，message 会原样返回；5xx 为 false，对外应换成固定文案，避免把数据库地址、堆栈之类的信息泄露出去。若某条业务错误需要自定义错误码，可以传第三个参数：ctx.throw(401, '令牌过期', { code: 'TOKEN_EXPIRED' })，上面的统一处理就能读到 err.code。

app.on('error') 是应用级错误事件，Koa 自身在无人处理的异常、响应流错误时也会触发它，这里适合接 winston、log4js 之类的日志库。不要在事件回调里再改响应，此时请求可能已经结束。还有一个边界：如果响应已经发出，修改 ctx.status 不会生效，只能记录错误并停止后续写入。

路由：koa-router 的 prefix、参数与嵌套

Koa 核心不带路由，最常用的是 koa-router 7.x。它的 API 与 Express Router 很像：new Router() 创建实例，get、post、put、delete 注册处理器，routes() 返回中间件，allowedMethods() 负责 405 与 OPTIONS。prefix 选项给整组路由加统一前缀，嵌套时用 router.use 把子路由挂进来。

请求体与文件上传

koa-bodyparser@4.2.1 负责 application/json 与 application/x-www-form-urlencoded，解析结果放在 ctx.request.body。用 enableTypes 明确只开这两类，解析失败时它会抛出 400，所以错误处理中间件必须在它外面。默认的 jsonLimit 是 1mb、formLimit 是 56kb，接口要收长文本时记得显式调大。

四个常用中间件

真实项目里最先补齐的通常是日志、鉴权、限流和 CORS。它们都很短，却能覆盖大部分横切需求；把它们挂在正确的层，业务代码会干净很多。

日志

日志中间件放在错误处理之后、业务之前，在 await next() 后统一打印方法、路径、状态码和耗时。

生产环境应把 console.log 换成结构化日志，并带上请求 ID，方便串联一次请求的多条记录。

限流

限流按客户端 IP 计数，用 Map 保存时间窗口和次数，超过阈值返回 429，并带上 Retry-After。

这个实现有两个明显局限：过期键不会自动清理，进程重启后计数清零；多进程部署时每个进程各算各的。生产环境应换成 Redis，用 INCR 加 EXPIRE 做固定窗口，多实例共享同一份计数。

CORS

跨域中间件要尽早执行，这样后面的 401、429 响应也会带上 CORS 头，前端才能读到错误信息。

回显 Origin 时不能写成通配符 * 再配 Allow-Credentials，浏览器会拒绝；必须维护白名单。只需要简单跨域时，也可以直接使用 koa2-cors，但白名单和凭据规则仍然要自己把关。

顺序错了，洋葱也会扎手

中间件顺序不是风格问题，而是执行语义。下面几条是踩过坑之后总结出的硬规则。

第一，错误处理必须最外层。它要包住后面所有中间件，才能接住路由、bodyparser、鉴权抛出的异常。把 try/catch 写在某个业务中间件里，只能兜住它自己的下游。

第二，bodyparser 必须在路由之前。路由处理函数读 ctx.request.body 时，解析已经完成；如果顺序反了，读到的是 undefined，接口表现为莫名其妙的 400。

第三，鉴权要在业务之前，但建议放在 CORS 之后。这样 401 响应也带跨域头，浏览器里的前端能拿到状态码；如果放在 bodyparser 之前，未登录请求可以少解析一次请求体，代价是登录接口要单独放行，按流量特点取舍。

第四，静态资源与 API 的顺序要明确。把 API 路由放在静态中间件之前，避免 public 下同名文件遮住接口；如果静态文件很多，也可以给静态资源单独挂前缀或交给 Nginx，Koa 只处理 API。

第五，allowedMethods() 跟在本组 routes() 后面，404 兜底放最后。所有 app.use 都要在 listen 之前完成，Koa 在启动监听时就把中间件数组组合成调用链，运行中再追加不会生效。

部署与调试

放在 Nginx 后面时，要把 app.proxy 设为 true，Koa 才会信任 X-Forwarded-For，ctx.ip 与 ctx.protocol 才能拿到真实客户端 IP 和协议。这个开关不能无条件打开：如果服务能被公网直接访问，客户端可以伪造请求头，限流和审计都会失真。只信任自己控制的代理，并让应用只监听内网地址。

优雅关闭要处理 SIGTERM 与 SIGINT。收到信号后停止接收新连接，等在途请求处理完再退出；再配一个超时兜底，避免长连接把进程拖住。pm2 的 reload 默认发送 SIGINT，两个信号都监听才能覆盖手工停止和滚动重启两种场景。

进程管理可以用 pm2。pm2 start app.js -i max --name api 以 cluster 模式按 CPU 核数起多个进程，pm2 reload api 滚动重启，pm2 logs api 看日志。但要记住每个进程独立：前面用 Map 做的限流、内存里的会话、本地缓存都不再全局一致，必须外置到 Redis。若团队已有 systemd 与日志采集，直接用 systemd 管单进程、Nginx 做负载均衡也可以，少一层工具依赖。

调试时用 node --inspect-brk app.js 启动，再打开 Chrome 的 chrome://inspect 就能下断点；临时排查还可以在中间件里打印 ctx.request.header，确认代理有没有把需要的头带过来。

小结

Koa 2 的中间件是一条可以双向执行的 async 调用链，await next() 之前的代码负责请求预处理，之后的代码负责响应收尾。ctx 把请求与响应封装成一组常用属性，配合最外层的 try/catch 就能统一错误格式。路由、请求体、静态资源都靠独立中间件拼装，顺序决定了谁能兜底、谁先执行。写业务中间件时记住三点：next() 只调一次并记得 await，错误处理放最外层，有状态的能力不要留在单进程内存里。
