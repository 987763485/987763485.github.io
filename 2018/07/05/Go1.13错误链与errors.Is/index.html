Go 1.13 错误链与 errors.Is

本文属于《Go 语言与工程》第 24/78 篇
上一篇系列目录下一篇

在分层架构里，一个来自数据库的错误往往要穿过 repository、service、handler 好几层才能到达调用方，等它被打印出来时，原始的错误类型和关键上下文常常已经丢失。本文讨论 Go 中的“错误链”思路：为什么需要它、在 Go 1.10 的当下如何用 github.com/pkg/errors 手工搭出它，以及 Go 2 错误处理草案里的 errors.Is、%w 与 Unwrap 可能把它带向哪里。读完后你应当能为自己的项目定下一套可执行的错误封装与判断规范。

为什么需要错误链

在分层应用里，错误很少在产生它的那一层被处理。数据库驱动返回一个错误，repository 把它交给 service，service 再交给 HTTP handler，handler 最后写日志、返回响应。如果每一层只是把错误原样往上扔，调用方看到的是一句孤立的 “connection refused”，既不知道是哪个用户、哪条 SQL，也不知道是连接池耗尽还是网络超时。

更常见的做法是每层用 fmt.Errorf 拼一句新消息，把上下文写进字符串。这样做看似信息更多，代价却很大：原始错误对象被丢弃，错误类型随之消失，调用方再也无法用相等比较或类型断言区分“记录不存在”和“数据库故障”，只能靠匹配字符串。字符串是给人看的，一旦文案调整，所有依赖它的判断都会悄悄失效。

这就是错误链要解决的问题：在保留原始错误身份的前提下，逐层附加上下文。链上的每个节点既是一个完整的错误，可以单独打印，又能通过约定回到它的原因。调用方沿链向下查找，就能在不依赖字符串的情况下判断错误类别。Go 1.10 的标准库还没有内建这条链，我们需要借助第三方库或自己写少量代码来模拟。

Go 的错误模型回顾

Go 的 error 是一个极简接口，只有一个 Error() string 方法，任何实现了它的类型都是错误。标准库 errors.New 返回一个只带消息的私有类型，通常被赋给包级变量，形成所谓的哨兵错误，例如 io.EOF、sql.ErrNoRows。调用方用 == 与哨兵比较，判断是否遇到某种已知情况。

两种手段各有局限。哨兵错误没有上下文，无法说明“在哪一步”出错；errors.New 生成的值除了相等比较做不了别的事。fmt.Errorf 能拼接上下文，但返回的仍然是一个只含消息的新错误，原始错误被彻底切断。自定义类型可以携带字段，可一旦被上层用 fmt.Errorf 重新包装，类型断言也会失败。换句话说，Go 1.10 的错误机制擅长表达“一个错误”，却不擅长表达“一串错误”。

当前的封装手段：pkg/errors

社区里最成熟的方案是 github.com/pkg/errors。它的基本用法此前文章已经介绍过，这里不再从头讲起，只围绕错误链的保留与判断展开。它提供五个常用函数：Wrap 与 Wrapf 在保留原错误的同时附加消息，WithStack 只记录调用栈，WithMessage 只加消息；Cause 则沿链取出最底层的错误。安装方式与当时其他依赖一样，用 go get 拉到 GOPATH 下：

选择哪个函数取决于想保留什么。Wrap 会同时加消息和堆栈，适合在错误第一次离开产生它的模块时使用；WithMessage 只加消息、复用原堆栈，适合已经记录过堆栈、只想补一句语义的情况；WithStack 不改变消息，适合把第三方库返回的裸错误接入链。三者都能被 Cause 解开，选择标准是堆栈由谁负责记录，而不是消息长短。

判断错误类别：从比较到解包

有了链，判断方式要跟着升级。最直接的是相等比较，err == ErrNotFound 只在错误没有被包装时成立，一旦经过 Wrap，外层已经是新的错误值，比较必然失败。第二是类型断言，例如 err.(*os.PathError)，它同样只检查最外层，包装之后也会失效。

错误链的边界：什么该封装，什么该原样返回

错误链不是越长越好。每加一层包装，就多一次分配、多一段要在日志里阅读的文字，也多一个可能泄露内部实现的机会。

该封装的地方通常是层与层的边界。repository 把驱动错误翻译成领域错误，service 在调用多个依赖时标注是哪一步失败，handler 在处理请求时补充请求标识。这些位置的共同点是语义发生了变化，包装让上层看到更有意义的错误。

不该封装的情况同样明确。若本层只是透传，没有新增任何信息，就原样返回，避免无意义的 “call failed: call failed”。若调用方依赖相等比较判断哨兵，包装前要想清楚是否同时提供了解包手段，否则判断会失效。日志只打一次是另一条铁律：在能拿到完整链的最外层打印一次 %+v，中间层只管返回，不要每层都 log 一遍，否则同一个错误会在日志里出现四五次，真正的原因反而被淹没。

还有安全边界。数据库连接串、文件绝对路径、内部服务名都可能藏在错误消息里。面向外部用户的响应应当只给稳定错误码和一句概括，完整链留给内部日志。

一个简单的自检方法是问三个问题：这层包装是否让错误更接近调用方的决策？上层是否真的需要这段上下文？如果删掉它，排障会损失什么？三个问题里有两个否定，就说明这层包装可以省掉。链的深度控制在三到五层，通常足以覆盖 repository、service 与 handler，再长就说明错误在层间被重复翻译。

Go 2 错误处理草案在讨论什么

标准库自身也在讨论这个问题。截至本文写作时，Go 1.10 是最新的稳定版本，Go 1.11 尚未发布、Go 1.13 更在路线图上；errors.Is/As、%w、Unwrap 来自 Go 2 错误处理草案，标准库版本尚不可用。草案仍在讨论中，最终形态可能调整，下面只谈它提出的几个核心概念。

第一是包装动词。草案建议让 fmt.Errorf 认识一个新的动词 %w，用它包装错误时，返回的错误会保留原错误，而不再只是拼字符串。这样最常见的包装方式不需要引入第三方库。

第二是 Unwrap 约定。草案设想错误通过 Unwrap() error 暴露下一层，链就是一连串 Unwrap，没有下一层时返回 nil。相比 Cause 直接跳到链尾，Unwrap 只走一步，把“遍历”交给标准库函数，灵活性更高。

第三是草案里的 errors.Is 与 errors.As。Is 沿链逐层比较，判断链上是否存在目标值；As 沿链逐层做类型匹配，把第一个匹配的错误赋给目标指针。两者都把前面手写的循环变成了标准库能力。

如果标准库落地：迁移路径与双栈期

如果标准库最终提供这些能力，现有项目不会一夜之间切换。可以预期一个双栈期：老代码继续用 pkg/errors，新代码尝试标准库，两者产生的错误在同一条链上共存。

迁移的第一步是收敛判断入口。项目里不要散落 err == ErrX 和手写循环，而是统一调用内部 errors 包的 Is 与 As。今天它们的实现基于 Cause，将来只需把实现换成标准库调用，业务代码不动。

API 设计建议

无论用哪种库，错误也是 API 的一部分，值得像函数签名一样设计。

优先导出哨兵错误。把 var ErrNotFound = errors.New("record not found") 放在包级，配一段注释说明什么场景会返回它，调用方就能稳定判断。哨兵适合类别有限且调用方需要分支的情况，不要为每个失败点都造一个哨兵。

需要携带数据时用自定义类型。例如 ValidationError 带上 Field 与 Reason 两个字段，调用方断言后可以直接拼装表单提示。类型应实现 Error() 给出简洁消息，字段保持只读语义，不要把内部可变状态暴露出去。

不要把内部错误直接透传给调用方。repository 返回的驱动错误包含表名、SQL 片段甚至连接地址，直接冒到 HTTP 层既是泄露也是耦合。正确做法是在边界翻译成领域错误，原始错误只作为链的一环保留给日志。

消息风格保持小写、无标点、不加感叹号，这是 Go 社区的惯例。消息描述“发生了什么”，而不是“失败了”；包装消息则补充“在哪一步”，例如 “find user”，而不是重复底层文案。

如果服务对外暴露 API，建议把哨兵错误映射成稳定的错误码，在 handler 一处完成转换。内部可以继续增加包装层，外部看到的码值不变，这样调用方既不依赖文案，也不需要理解内部错误链的形状。

小结

错误链的价值在于同时保留两样东西：给人看的上下文，和给程序判断的原始身份。在 Go 1.10 的今天，pkg/errors 的 Wrap、Wrapf 与 Cause 足以搭出这条链，再配一个二十行左右的 Is 就能稳定判断类别。封装要发生在语义变化的层边界，日志只在最外层打一次。Go 2 错误处理草案提出的 %w、Is、As 与 Unwrap 试图把这套做法收进标准库，但截至本文写作时仍是草案，标准库版本尚不可用。务实的策略是把判断集中到内部小包，今天用 Cause 实现，将来替换实现即可平滑迁移。
