Go 时间与日期处理

本文属于《Go 语言与工程》第 25/78 篇
上一篇系列目录下一篇

时间字段几乎出现在每个服务里：订单创建时间、令牌过期时间、日志时间戳。很多人第一次写 Go 时，会以为 time.Time 就是一个普通的时间戳，直到某次比较失败、某次解析悄悄得到零值，才发现它比想象中复杂。本文面向已经能写 Go、但在时间处理上踩过坑的读者，从 time.Time 的内部结构讲到布局、解析、时区、运算与序列化，最后给出速查表。读完之后，你应该能自觉采用“UTC 存储、本地展示”的做法，并知道在 Go 1.10 上哪些写法是安全的。

time.Time 里其实有两个时钟

time.Time 是一个结构体，逻辑上由两部分组成：wall clock（挂钟时间）和 monotonic clock（单调时钟）。前者是我们熟悉的年月日时分秒，会随着 NTP 校时、人工改时间而跳变；后者来自运行时的单调计数，只保证一直向前，不受系统时间调整的影响。

Go 1.9 起，time.Now() 返回的值同时携带这两部分。这样设计是为了让“测量经过的时间”变得可靠：

如果拿挂钟时间相减，遇到 NTP 往回跳一秒，就会出现负的耗时。time.Since、time.Until、Sub 在存在单调读数时优先使用它。

问题出在比较上。time.Time 可以直接用 ==，但 == 比较的是结构体的全部字段：wall 的编码、ext 以及 loc 指针。两个表示同一瞬间的时间，只要时区对象不同，== 就是 false。

所以判断“是不是同一时刻”永远用 Equal，== 只适合判断“是不是同一个值”，例如判断有没有被赋过值。零值 time.Time{} 对应 0001-01-01 00:00:00 UTC，常被当作“未设置”的哨兵；但它和数据库里的 NULL 不是一回事，后文会讲。另外，单调读数不会进入 JSON 与数据库，往返一次之后只剩挂钟部分，这也是比较逻辑不能依赖 == 的原因之一。

布局字符串：为什么是 2006-01-02

Go 的格式化不使用 %Y-%m-%d 这类占位符，而是拿一个固定的参考时间当模板：

它的 Unix 时间是 1136239445，也就是 01/02 03:04:05PM ‘06 -0700。Go 给这段参考时间的每个数字都赋予了含义：2006 是年，01 是月，02 是日，15 是 24 小时制的时，04 是分，05 是秒，Mon 是星期缩写，Jan 是月份缩写，MST 是时区名，-0700 是偏移。记忆口诀是“1 月 2 日 3 点 4 分 5 秒 6 年”。

常见布局如下：

写法 输出示例 说明
2006-01-02 15:04:05 2018-07-24 22:37:17 最常用的本地时间
2006-01-02T15:04:05Z07:00 2018-07-24T22:37:17+08:00 即 time.RFC3339
2006-01-02 2018-07-24 只到日期
15:04:05 22:37:17 只到时间
2006年01月02日 2018年07月24日 中文习惯

最容易犯的错，是把其他语言的占位符直接搬过来：

Format 只认参考时间里的那些数字组合，Y、D 都不是合法记号，于是原样输出。同理，mm 不会被当成分钟（分钟是 04），hh 也不会被当成小时。写了半天发现输出没变，多半就是这个原因。检查办法很简单：把布局打印一遍，看它是否真的包含 2006、01、02 这些数字。

解析：Parse 与 ParseInLocation

time.Parse 按布局把字符串转成 time.Time，返回时间和错误两个值。这是 Go 的惯例，但时间处理里忽略错误特别危险，因为失败时返回的是零值。

注意输出里的 +0000 UTC。布局中没有时区信息时，Parse 一律按 UTC 解释，而不是本地时区。很多人的第一反应是“解析出来再减 8 小时”，这种代码换一台机器、换一个时区就错了。

如果布局里自带偏移，例如 2006-01-02T15:04:05-07:00，那么字符串里的 +08:00 会生效，与传入的 location 无关。如果布局里是时区缩写 MST，而缩写无法识别，Go 会构造一个名字相同、偏移为零的时区，这种结果通常不是你想要的，生产代码里尽量用数字偏移或 IANA 名称。

还有一点：Parse 对格式相当严格，多余的空格、缺位的补零都会失败。2018-7-24 用 2006-01-02 解析会报错，所以从外部系统接收时间时，要么约定死格式，要么准备多个布局依次尝试。

时区：不要相信服务器的本地时间

Go 的时区信息来自 IANA 时区数据库，查找顺序大致是：环境变量 ZONEINFO 指定的目录、系统目录（如 /usr/share/zoneinfo）、$GOROOT/lib/time/zoneinfo.zip。time.LoadLocation("Asia/Shanghai") 返回的 *time.Location 就来自这个数据库。

这带来一个部署期的问题。基于 scratch 或精简镜像构建的容器里往往没有 tzdata，LoadLocation 会直接报错：

2018 年的标准库还没有内嵌时区数据，解决办法只有两个：在镜像里安装 tzdata（Alpine 用 apk add --no-cache tzdata，Debian 系用 apt-get install tzdata），或者把宿主机的 /usr/share/zoneinfo 拷贝进镜像并通过 ZONEINFO 指定。启动时加载一次并缓存，比每个请求都 LoadLocation 更稳妥。

更根本的做法是把时区当成展示层的问题：

flowchart TD
    A[外部字符串] --> B[按约定布局解析]
    B --> C[转换为 UTC]
    C --> D[存入数据库]
    D --> E[读取后按用户时区转换]
    E --> F[格式化输出]

写入时统一转 UTC，读取时再 In(loc) 转成用户所在时区。这样数据库里只有一种时间基准，跨时区排查问题时不会互相扯皮。数据库连接也建议固定时区，例如 MySQL 的 DSN 加上 loc=UTC&parseTime=true，避免驱动用服务器本地时区解释时间。

代码里可以用 t.UTC()、t.Local()、t.In(loc) 三个方法切换表示，它们返回的是同一瞬间的不同视图，不改变时间本身。time.Local 取的是进程启动时确定的本地时区，由 TZ 环境变量决定，容器里通常就是 UTC。测试里如果不想依赖系统时区，可以用 time.FixedZone("CST", 8*3600) 构造固定偏移的时区。

日期运算：Add、AddDate 与 Truncate

Add 接受一个 time.Duration，做绝对时长加法；AddDate 接受年、月、日三个整数，做日历加法。两者在月末的表现完全不同。

1 月 31 日加一个月，得到的是“2 月 31 日”，Go 会把它规范化成 3 月 3 日（2018 年 2 月只有 28 天，多出的 3 天顺延）。这不是缺陷，而是文档写明的溢出规则。如果业务语义是“下个月的最后一天”，必须自己判断：

这种规范化也发生在 time.Date 上：time.Date(2018, 2, 30, 0, 0, 0, 0, time.UTC) 会得到 3 月 2 日，月份传 13 会进位到下一年。这个特性可以用来算“某月第一天”“下个季度”之类的日期，但读取用户输入时不能依赖它，非法日期应当在校验阶段就拒绝。

Sub 返回两个时间之间的 Duration，配合 Hours()、Minutes() 使用。要注意 Duration 是纳秒级的 int64，大约 292 年就会溢出；计算“相差多少天”时，用 Sub 再除以 24 小时，遇到夏令时会差一小时，更稳妥的是按日历日逐项比较。

常见坑清单

第一个坑是隐式依赖本地时区。代码里写 time.Now() 本身没问题，但如果随后用 Format("2006-01-02") 落库，结果就取决于进程的 TZ 环境变量。开发机是东八区、容器是 UTC，同一条记录会差一天。显式传 location，或者在入口处统一转换。

第二个坑是夏令时。美国东部时间在 3 月第二个周日凌晨 2 点跳到 3 点，这一天的 2:30 根本不存在；11 月第一个周日 1:30 会出现两次。用本地时间做“每天 2:30 执行”的运算，遇到切换日就会出错。中国在 1991 年后不再实行夏令时，但用户与服务器可能在任何时区，涉及跨国的业务必须按 UTC 或明确的 IANA 时区计算。

第三个坑是忽略解析错误。time.Parse 失败返回零值，而零值是合法的 time.Time，直接入库就变成 0001-01-01，查询和统计都会被污染。所有解析调用都要检查 err，必要时在边界处直接拒绝请求。

第四个坑是 Format 的参考时间写错，前面已经说过。还有一个变体：布局写对了，却把 15 写成 03，12 小时制与 24 小时制混用，下午的时间会少 12 小时。

第五个坑在数据库层。连接参数没开 parseTime，扫描出来的是 []byte；开了 parseTime 但 loc 与写入时不一致，读出来的瞬间就偏了；MySQL 服务器、连接会话、应用三处时区各不相同，排查时极为痛苦。约定“连接固定 UTC、列用 DATETIME、展示层转换”能省掉大部分问题。

第六个坑是秒与毫秒混用。前端 JavaScript 的 Date.now() 给的是毫秒，Go 的 Unix() 给的是秒，接口里不写清楚单位，就会出现 1970 年或五万年后之类的结果。

第七个坑是用字符串比较时间。格式统一、补零完整时，字符串比较确实等价于时间比较；但 2018-7-24 与 2018-07-24 混在一起，排序结果就乱了。跨时区的字符串更不可比，+08:00 与 Z 结尾的值按字典序毫无意义。要比较就转成 time.Time，要展示再格式化。

小结

Go 的时间处理把“瞬间”和“表示”分得很清楚：time.Time 记录一个瞬间，布局与时区决定它怎么显示。比较用 Equal，运算分清 Add 与 AddDate，格式化牢记 2006-01-02 15:04:05 这个参考时间。工程上坚持 UTC 存储、边界转换、展示层格式化，能避免绝大多数跨时区问题。解析错误一定要处理，零值不等于空值，容器里记得装 tzdata。把这些习惯固定下来，时间字段就不再是事故来源。
