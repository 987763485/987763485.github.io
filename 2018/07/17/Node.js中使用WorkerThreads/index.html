Node.js 中使用 Worker Threads

本文属于《TypeScript 学习路线》第 54/74 篇
上一篇系列目录下一篇

Node.js 的单线程事件循环擅长处理 I/O，却在遇到 CPU 密集任务时显得笨拙：一段耗时的同步计算就能让整个进程的响应停滞。本文从这一痛点出发，介绍 Node.js 10.5.0 引入的实验模块 worker_threads，说明它的版本门槛、消息通信方式与生命周期管理，并给出线程池与生产灰度的注意事项。读完本文，你应当能判断一个任务是否适合交给 Worker 线程，并写出一个可运行、可回收的最小实现。

为什么需要 Worker Threads

Node.js 的主线程只有一个。JavaScript 代码在事件循环里依次执行，I/O 交给 libuv 的线程池或操作系统，完成后回调再排回主线程。这个模型对 I/O 密集的服务很合适：等待网络和磁盘的时间不占 CPU，少量线程就能支撑大量并发连接。

但事件循环的容量是按同步执行时间计算的。一段耗时的同步计算会占满主线程，在此期间定时器、网络回调、Promise 回调都无法推进。一个请求触发了大数组排序、图片解码、加密签名或复杂规则计算，同进程内的其他请求就只能排队。表现出来是接口延迟抖动、健康检查超时，严重时节点被负载均衡摘除。

以往的解法是把计算挪进 child_process 子进程，或者用 cluster 起多个进程分摊请求。两者都能利用多核，代价是进程较重：创建销毁有成本，进程间通信要序列化，内存也各自独立。worker_threads 提供的是第三种选择，同一进程内的多个 JavaScript 线程，创建更轻，通信走消息，适合把一段可控的计算从主线程剥离。

三种并发手段的定位

手段 隔离单位 通信方式 创建成本 适合的场景
child_process 独立进程 管道与 IPC，需要序列化 较高 调用外部程序、强隔离
cluster 独立进程 主进程分发连接 较高 HTTP 服务提升吞吐
worker_threads 同进程内的线程 postMessage 消息传递 较低 CPU 密集计算、任务并行

这张表的关键不在性能，而在边界。Worker 线程不替代另外两者：瓶颈在 I/O 就不要加线程；需要隔离不可信代码或调用外部程序，用子进程；要提升 HTTP 服务的吞吐，用 cluster 复制进程；只有当某个任务是明确的 CPU 消耗、结果又能异步返回时，才轮到 Worker。

worker_threads 在 Node.js 10.5.0（2018 年 6 月）加入，状态是实验特性。使用时必须显式打开开关：

消息是双向的：主线程用 worker.postMessage 发给 worker，worker 用 parentPort.postMessage 回到主线程；worker 侧监听主线程消息则用 parentPort.on(‘message’)。同一对端口之间的消息保持发送顺序，但不要假设不同 worker 之间存在任何顺序。

通信模型：克隆、转移与方向

结构化克隆

postMessage 的参数会经过结构化克隆算法复制，接收方拿到的是副本而不是引用。对象、数组、Map、Set、Date、TypedArray、ArrayBuffer 都能传；函数、Symbol 以及带方法的类实例不能按原样传递。类实例会被拆成普通对象，原型上的方法丢失，调用时报 not a function。实际做法是只传纯数据，接收方再自行组装。

可转移对象

消息方向与语义

消息是异步的，发送方不会等待接收方处理完；也没有内置的请求响应关联，需要自己在消息体里带一个 id，或者约定一问一答。频繁的小消息会带来序列化与调度开销，批量合并通常更划算。

workerData 与生命周期

启动参数通过第二个参数的 workerData 传入，worker 侧同步读取，适合传配置而不是传大块数据：

workerData 同样经过结构化克隆，主线程与 worker 各持一份副本，启动后修改互不影响。大块数据不要塞进 workerData，应当在连接建立后用消息加转移列表传递。

生命周期要盯住三个事件。message 是正常结果；error 是 worker 内未捕获的异常，触发后 worker 终止；exit 在退出时触发，参数是退出码，非 0 通常意味着异常或被终止。error 必须监听：EventEmitter 对没有监听者的 error 事件会直接抛出，效果就是主进程崩溃。

terminate() 用于主动停止，返回 Promise。它会中断正在执行的 JavaScript，不保证 finally 块执行，所以不要把它当资源释放手段；清理逻辑应当放在任务本身的正常返回路径里。反过来，worker 默认会让进程保持存活，一次性任务完成后应当 terminate，或者让 worker 自己退出，否则主进程迟迟不结束。

与 cluster 的取舍

cluster 的隔离单位是进程，每个 worker 进程有独立的内存空间与事件循环，主进程负责分发连接。它解决的是用满一台机器多核来提升 HTTP 吞吐的问题，进程崩溃不会带走其他进程，但内存开销按进程计，共享状态要靠外部存储或进程间通信。

维度 cluster worker_threads
隔离单位 进程 同进程内的线程
内存 各自独立，按进程计 同进程，开销较小
通信 主进程分发连接，进程间通信 postMessage 消息传递
故障边界 进程崩溃不波及其他进程 处理不当会波及主进程
典型用途 HTTP 服务横向扩展 CPU 密集计算

worker_threads 创建更快、内存更省，消息传递也更直接，代价是隔离性弱：一个 worker 的未捕获异常若处理不当会影响主进程，线程之间没有进程级别的故障边界。调试方面，2018 年的工具链对多线程支持有限，worker 内的断点体验不如单线程；cluster 的每个进程则可以单独 attach 调试器。

选择可以归结为一句话：要吞吐和故障隔离，用 cluster；要在一台机器上并行几段计算且不想付出进程成本，用 Worker。两者也能组合，每个 cluster 进程内部再按需开少量 worker，但层次一多，排障成本明显上升，实验阶段不建议叠加使用。

常见坑

路径按当前工作目录解析

new Worker(‘./worker.js’) 的相对路径以进程的当前工作目录为基准，不是以调用它的文件为基准。用 pm2、systemd 或在不同目录启动时，路径会指向别处。统一用 path.join(__dirname, ‘worker.js’)。

模块体系混用

worker 文件按 CommonJS 加载，require 与 module.exports 是可靠写法。Node.js 10 的原生 ES module 仍在实验阶段，worker 文件里直接写 import 会遇到解析错误；如果项目用 Babel 转译，要确认 worker 文件也被转译，且产物路径正确。

进程退不掉

worker 默认保持事件循环活跃。一次性任务忘了 terminate，进程会挂在那里；主线程结束时若还有 worker，也不会自动清理。一次性任务在收到结果后调用 terminate，常驻 worker 在服务关闭时统一终止，并在退出码非 0 时记录日志。

异常没有监听

worker 的 error 事件没有监听者时，主进程会因未处理的 error 崩溃。所有 Worker 实例都应绑定 error 与 exit，并在非正常退出时决定是重建还是让任务失败。try/catch 只能捕获 worker 内部的同步异常，异步回调里的错误仍要走 error 事件。

调试支持有限

worker 内的 console 输出会汇到主进程的标准输出，但断点与性能分析对多线程的支持有限，inspector 默认只调试主线程。排查阶段可以把计算函数抽成独立模块，先在单线程下单测，再放进 worker。

实验期的生产建议

先把结论说清楚：worker_threads 在 2018 年仍是实验特性，API 可能变化，不建议直接上生产。若确有 CPU 瓶颈需要验证，可以按下面的方式控制风险。

第一，做能力开关。把用 worker 执行封装在一个函数后面，由环境变量或配置决定走哪条路径，默认关闭；验证有效后按任务类型逐步放开，而不是按流量比例随机放开，因为只有部分任务适合并行。

第二，设置超时与降级。每个任务带超时，超时后 terminate 并重建 worker，同时回退到同步执行或返回降级结果。降级路径必须被测试覆盖，否则它只是纸面上的保险。

第三，限制资源。worker 数量设上限，队列设上限，队列满时快速失败。每个 worker 都有独立的 V8 堆，数量失控会先把内存吃满，而不是把 CPU 吃满。

第四，补上监控。记录任务耗时、排队长度、worker 数量、异常与退出码，并与主线程的事件循环延迟一起看。只有 worker 耗时长而主线程延迟正常，才说明拆分是有效的。

最后，锁定 Node 版本。实验模块的行为会随小版本调整，升级前在预发环境跑一遍计算类回归。

小结

Node.js 的单线程模型让 CPU 密集任务成为事件循环的阻塞源，worker_threads 在 10.5.0 中给出了同进程多线程的选项，但需要 –experimental-worker，且属于实验特性。它用 postMessage 传递结构化克隆的数据，用 workerData 传初始化参数，用 error、exit 与 terminate 管理生命周期。实践中最重要的是复用线程而不是按请求新建，并用线程池、超时与降级把风险控制住。在 Node.js 8 仍是生产主流的 2018 年，这项能力更适合验证与预研，而不是直接承担关键路径。至于如何在 Web 框架的中间件层接入，属于另一篇文章的话题，本文不展开。
