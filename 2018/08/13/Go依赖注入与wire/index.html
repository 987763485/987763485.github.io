Go 依赖注入与 wire

本文属于《Go 语言与工程》第 78/78 篇
上一篇系列目录下一篇

在 Go 项目里，依赖通常由构造函数一层层传进去，代码直白，但依赖一多，main 函数就会变成一个又长又杂的装配车间。本文从手写构造注入讲起，介绍 Google 的 wire 如何用代码生成把这部分工作自动化，包括 provider、injector、清理函数、接口绑定、多实例与测试替换，最后比较它与 dig/fx 的取舍，并列出常见坑。适合已经写过一段时间 Go、正在为项目依赖组织方式发愁的读者。

什么是依赖注入

依赖注入（Dependency Injection，DI）常被误解为某个框架或容器的名字。回到本质，它只描述一件事：一个对象不再自己创建依赖，而是由外部的装配层把依赖创建好、再传进来。构造依赖的责任从使用者转移到了装配层，这就是依赖注入的全部含义。

Go 社区里还有一种常见做法是全局单例或 init 函数：包级变量在 init 里初始化，任何函数直接引用。它写起来省事，代价是依赖关系变成隐式的：看一个函数的签名看不出它依赖什么，测试时必须小心翼翼地处理全局状态，init 的执行顺序也容易埋雷。依赖注入把这些问题摆到明面上，构造关系集中在少数几个地方，读代码的人顺着构造函数就能把整张依赖图拼出来。

需要强调，依赖注入不等于重量级容器。Java 生态里的 IoC 容器用注解和反射自动完成装配，这套思路在 Go 里并不流行；Go 的依赖注入通常就是构造函数参数，最多再加一个代码生成工具。理解这一点，后面的内容才不会跑偏。

换一个角度理解：一个对象获取依赖无非三种方式——自己 new、从全局变量取、由外部传入。前两种把“用什么”和“怎么用”绑死在一起，第三种把选择权留给装配层。依赖注入并没有消除依赖，它只是把依赖从实现细节提升为接口契约，让替换和测试成为可能。

Go 为什么常手写构造注入

在 wire 出现之前，绝大多数 Go 项目的手写注入都长一个样：repository 依赖 *sql.DB，service 依赖 Repository 接口，handler 依赖 *UserService，最后在 main 里按顺序 new 出来。没有注解，没有反射，也没有配置文件，装配过程就是几行普通函数调用。假设这些构造函数都已定义，main 里的装配就是三行：

这种写法有几个直接的好处。第一是显式：谁依赖谁，看构造函数签名一清二楚，不需要运行起来再猜。第二是编译期检查：类型对不上，go build 立刻失败，不会等到启动时才报缺少依赖。第三是可读：main 函数就是一张装配图，新人接手时从 main 往下读，很快能建立整体印象。第四是可测试：把参数换成 fake，就能在不碰数据库的情况下测 service 的逻辑。

与 setter 注入相比，Go 更偏爱构造函数注入。字段可以不导出，对象一旦构造完成就处于可用状态，不会出现“忘了调用 SetRepo”的半成品；依赖在编译期就固定下来，读代码时不必追踪某处是否在运行中改过字段。这种一次性构造的思路，也让清理函数的配对变得自然。

Go 的标准库也在鼓励这种风格。database/sql 的 *sql.DB 本身就是并发安全的句柄，适合在装配层创建一次、层层传递；net/http 的 Handler 是接口，组合方式同样是把依赖放进结构体。语言层面没有提供容器，社区也就顺势把构造函数注入当成了默认答案。

这也解释了为什么 Go 项目里的 main 函数往往比别的语言长一些。它不是单纯的入口，而是整个应用的 composition root：配置从哪里读、数据库连哪个实例、用哪个实现，全部在这里决定。只要依赖不多，这种直白是优点而不是缺点。

手写注入的痛点

依赖少的时候，手写注入几乎没有成本。但项目一旦长到十几个组件，问题会逐渐显现。

第一，main 变成装配工厂。每个组件都要按正确顺序创建，顺序错了编译能过、运行才炸；参数多了以后，main 里全是临时变量，真正的业务入口被挤到最底下。第二，签名改动会向上传导：Repository 的构造函数多了一个参数，所有手工装配的地方都要跟着改，包括 main、命令行工具、测试和临时脚本。第三，多入口重复：同一个服务往往有 HTTP 入口、定时任务入口和测试入口，每个入口都要复制一份装配代码，稍有遗漏就出现两套行为不一致的依赖图。第四，清理逻辑容易漏：数据库、连接池、后台 goroutine 都需要关闭，手写时经常只记得 defer 一个，忘了另一个。下面这段示意代码省略了 import 和部分类型定义，只保留装配与清理的主干：

wire 的两个角色：provider 与 injector

wire 是 Google 开源的一个编译期依赖注入工具，属于 Go Cloud 项目的一部分，目前仍是 0.x 版本。它不提供运行时容器，只做一件事：读取你写的装配声明，生成等价的普通 Go 代码。理解 wire 只需要抓住两个角色。

provider 就是普通的构造函数。它的第一个返回值是它提供的类型，后面可以跟 error 和清理函数。wire 不要求实现接口、不要求注册，也不要求改函数签名，任何符合形式的函数都能当 provider：

这个函数本身不会被执行，wire 扫描到它之后，会根据参数类型自动把 provider 串起来，生成真正干活的实现。为了避免占位实现被编进二进制，injector 通常放在带 // +build wireinject 构建标记的文件里；生成的文件则带相反的标记，两者互斥。

provider 多了以后，可以用 wire.NewSet 把它们打成一个集合，跨包复用。集合本身也是 provider 的一种，可以嵌套。跨包时，通常由提供实现的包导出一个 provider 集合变量，injector 只导入集合，不关心内部有哪些构造函数；测试时把集合里的某个 provider 换掉，就能得到一套行为不同的装配。集合让“生产用哪套、测试用哪套”变成显式的选择，而不是散落在各处的条件判断。wire 的解析完全基于类型：它从 injector 的返回值倒推，需要 UserService 就找返回 UserService 的 provider，再递归解决这个 provider 的参数，直到所有依赖都有着落。

因为生成的是普通代码，运行时没有反射、没有容器、没有额外的初始化开销，出问题时可以直接读 wire_gen.go，和手写装配没有区别。这是 wire 与 dig/fx 最根本的分野，后文会展开对比。

provider 的清理函数

wire 识别四种 provider 形式：只返回对象；返回对象和 error；返回对象和清理函数；返回对象、清理函数和 error。最后一种最适合数据库、连接池、后台服务这类需要释放的资源。

清理函数的约定很简单：provider 创建资源成功后，把如何释放它封装成一个无参无返回的函数一起返回。wire 在生成 injector 时，会把这些清理函数收集起来，按构造的逆序串成一个新的清理函数，交给 injector 的调用方。逆序的原因和栈一样：后创建的资源可能依赖先创建的资源，释放时必须反过来，先关依赖方再关被依赖方。

如果某个 provider 带清理函数，而 injector 的返回值里没有 func()，wire 会直接报错，提醒你漏掉了资源释放。反过来，injector 返回了清理函数但没有任何 provider 需要清理，也会显得多余。调用方拿到清理函数后应当立即 defer，并保证只调用一次。

举个具体的顺序：NewDB 先创建连接池，NewCache 再基于它创建缓存，生成代码会先调用 cacheCleanup，再调用 dbCleanup。如果反过来先关数据库，缓存的最后一次刷写就可能失败。清理函数不返回错误，所以释放失败通常只能记日志；对确实需要感知关闭错误的资源，应该在 provider 里自行处理，而不是把错误吞掉。

还要注意失败路径。provider 自己申请了资源、又在后续步骤失败时，应当自己释放已经拿到的部分，例如 NewDB 在 Ping 失败后先 db.Close() 再返回错误。不要指望生成代码替你兜底所有半成品状态：注入器只负责把成功的构造和对应的清理函数串起来，provider 内部的失败清理仍是 provider 自己的责任。

最后，清理函数里不要做耗时操作。关闭连接池、停止 goroutine、等待日志刷盘要尽量快；如果确实需要优雅退出，给清理函数加一个内部超时，避免进程退出被卡住。

wire 的解析按类型进行，wire.Build 里各元素的先后顺序不影响结果：它从 injector 的返回值出发倒推，先找 UserService 的 provider，再解决 Repository，再通过绑定找到 MySQLRepo，最后解决 *sql.DB。真正要注意的是歧义：同一个接口在同一张图里只能有一个有效绑定，同一个具体类型也不能被两个 provider 同时提供，否则 wire 会报 multiple bindings 之类的错误。

常见报错有两种：一种是“no provider found for Repository”，说明绑定写了但具体实现没进集合；另一种是绑定参数不是指针，wire 无法从中读出类型。遇到这类错误，先看 injector 的返回值，再顺着生成日志里的类型链往上找，通常比读生成代码更快。

顺便说一句，接口应当定义在使用它的包，而不是实现它的包；这样使用方只依赖自己需要的方法，实现方也不必为了绑定而导入使用方。wire 的绑定写在装配层，正好把这条原则落到了代码里。

测试时绑定特别好用。生产装配把 Repository 绑到 MySQLRepo，测试装配绑到 fakeRepo，业务代码一行不改。绑定只对当前 injector 生效，不会污染全局，这也是编译期注入相比全局注册表的优势之一。

多实例与命名：wire.Value、wire.Struct、wire.FieldsOf

当同一个类型需要多个值时，wire 的按类型解析会遇到麻烦。例如两个 string：数据库 DSN 和 Redis 地址，两个 provider 都返回 string，wire 无法判断该把哪个传给谁。wire 0.x 没有给同一类型起名字的机制，解决思路是让类型本身携带语义，或者把值收进结构体。

wire.Value 用来把一个现成的值注册为 provider，适合常量、配置和小对象：

它会在生成代码里直接写入这个值，所以只适合不可变、可安全复制的数据；不要把运行时才确定的配置或可变全局变量交给它。同一个 injector 里出现两个同类型的 wire.Value，同样会冲突。

wire.Struct 用结构体构造代替手写构造函数。wire.Struct(new(Config), "*") 表示 Config 的所有导出字段都由其他 provider 提供；也可以只列字段名，表示只注入这几个，其余留零值。它适合纯数据载体，省掉一个只做赋值的构造函数。例如 wire.Struct(new(Handler), "Service") 只注入 Service 字段，Handler 里的其他字段保持零值；写成 "*" 则要求每个导出字段都能被解析，任何一个字段缺少 provider 都会导致生成失败。用通配符前要确认结构体里没有故意留空的字段。

测试中的装配

依赖注入最直接的回报是测试。多数情况下，测试根本不需要 wire：service 依赖的是接口，直接传一个手写 fake 即可。

这段测试没有数据库、没有 wire、没有生成代码，运行在毫秒级。手写 fake 的另一个好处是意图明确：测试需要什么行为，fake 就实现什么行为，不会因为生产装配变化而被动失效。

表驱动测试同样适用：把 fake 的返回值做成用例字段，循环里构造 service 即可。需要连真实数据库的集成测试则相反，应当走生产装配或专门的测试装配，确保连接参数、迁移和清理逻辑与线上一致，不要用 fake 掩盖 SQL 错误。

当被测对象依赖链很深，手工拼装变得繁琐时，可以再考虑用 wire 生成测试装配。常见做法是单独建一个包（例如 internal/testapp），在里面放 fake provider 和带 wireinject 标记的 injector，运行 wire 生成一套指向 fake 的装配，测试导入这个包即可。这样 fake 不会进入生产二进制，生成文件也各自独立，不会和主装配互相干扰。

无论用哪种方式，都要把 wire_gen.go 当作构建产物看待：不要手改，不要在两套生成文件之间复制代码。团队如果选择提交生成文件，建议在 CI 里跑一遍 wire，再用 git diff –exit-code 检查生成结果是否与源码同步；如果选择不提交，就在构建脚本里固定执行 wire，确保每次编译前都重新生成。两种策略都行，混着来最容易出现“本地能跑、CI 编译失败”的怪问题。

与 dig/fx 的对比

Go 生态里另一派是运行时依赖注入，代表是 Uber 的 dig 和基于 dig 的 fx。dig 提供 Provide 和 Invoke：把构造函数注册进容器，运行时通过反射解析依赖图；fx 在 dig 之上加了生命周期钩子、模块化和应用骨架，适合搭服务框架。两者都不是标准库，思路与 wire 相反。fx 还提供 OnStart/OnStop 钩子，把资源的启动和关闭纳入应用生命周期；dig 本身只负责解析依赖，不管理生命周期。wire 把清理函数直接放进 injector 的返回值，思路上更接近手工代码，也更透明。

维度 wire dig/fx
解析时机 编译期生成代码 运行时反射解析
错误发现 运行 wire 或编译时 启动时 Invoke
运行开销 与手写代码相同 反射与图解析开销
可读性 生成代码可直接阅读 装配藏在容器里
灵活性 静态图，换实现要重新生成 可动态注册与替换
依赖 多一个代码生成步骤 多一个运行时依赖

wire 的优势是错误发现得早。少写一个 provider、接口没有绑定、出现循环依赖，都会在生成阶段暴露，而不是等到部署后启动失败。生成代码可读，排查问题时不需要理解容器内部；运行时也没有反射开销。代价是装配图是静态的，想在运行时根据配置切换实现，要么改 injector 重新生成，要么在 provider 内部做分支。

dig/fx 的优势是灵活，适合插件式架构或依赖图需要动态拼装的场景，团队熟悉容器 API 时上手也快。但依赖关系隐式、错误推迟到启动、调试时要翻容器日志，这些都是常见的抱怨。对大多数业务服务来说，依赖图在编译期就是确定的，wire 的静态方式更贴合 Go 的工程习惯。

选择时不必站队：小服务手写装配就够；依赖图稳定、入口多、测试多的项目上 wire；确实需要运行时动态能力时再考虑 dig/fx。把三者当成不同阶段的工具，而不是信仰之争。

常见坑与排查

第一坑是忘记运行 wire。改了 provider 参数或返回值，生成文件还是旧的，编译可能直接报参数不匹配，也可能阴差阳错继续工作，运行时才暴露问题。把 wire 挂到 go generate 上，并在提交前或 CI 里固定执行，是最省心的办法。

第二坑是手改生成文件。wire_gen.go 开头明确写着 DO NOT EDIT，下次生成会覆盖所有手工修改。需要调整装配时改 provider 或 injector，不要改生成结果。

第三坑是构建标记写错。injector 文件少了 // +build wireinject，占位函数会被正常编译，调用时返回 nil，表现为空指针 panic；标记和 package 之间少了空行，标记不生效，症状相同。生成文件则必须带 // +build !wireinject，两边标记互为补集，缺一个就会出现重复定义。

第四坑是循环依赖。A 的 provider 需要 B，B 的 provider 又需要 A，wire 在生成阶段会报 cycle。解决办法通常不是硬拆参数，而是重新审视职责：把共用部分抽成第三个组件，或者让其中一方依赖接口，由装配层决定实现。手写装配遇到循环依赖往往表现为构造顺序怎么排都不对，wire 至少会明确指出环在哪里。

第五坑是清理顺序与重复调用。清理函数按构造逆序执行，如果某个资源被两个组件共享，不要在两个 provider 里各注册一次关闭逻辑；清理函数尽量幂等，调用方只 defer 一次。多个 injector 各自创建同名资源时，也要确认它们是否真的应该共享同一个连接池。

第六坑是同类型冲突。两个 provider 都返回 *sql.DB，或者都返回 string，wire 会报 multiple bindings。回到上一节的办法：用有语义的类型、用结构体收拢配置，或者拆 injector。错误信息里通常会列出冲突的类型和候选 provider，顺着读就能定位。

第七坑是 provider 的可见性。injector 与 provider 不在同一个包时，provider 函数和 provider 集合变量都必须导出，否则 wire 看不到；反过来，把 injector 放在 main 包、provider 放在内部包，是很常见的分层方式。还要留意 import 关系，provider 包不要反向导入 main，否则会形成包级循环。

何时不该上 wire

wire 解决的是装配代码重复和手工维护的问题，它本身也带来成本：多一个工具依赖、多一步生成、多一类生成文件需要管理。以下几种情况，手写注入更合适。

项目很小，依赖不到十个，main 里十几行就能装配完。这时引入 wire 的收益接近于零，反而让新同事多学一套东西。只有一个入口、依赖图长期稳定、测试直接传 fake 就能覆盖，也没有必要上代码生成。

团队对代码生成不熟悉，或者代码评审流程无法接受生成文件。wire_gen.go 行数不少，review 时容易走形式；如果团队没有形成“生成文件不手改、CI 校验同步”的共识，生成文件迟早会和源码脱节。

依赖需要在运行时动态决定。例如根据租户配置选择不同的存储实现，或者插件在启动时注册自己，这类场景 wire 的静态图不擅长，手写工厂函数或运行时容器更自然。

还有一种情况是依赖图本身很浅，但构造参数很多。这往往说明某个组件职责过重，应该先重构，而不是用工具把问题藏起来。wire 能让装配代码变短，但不会让糟糕的抽象变好。

实践建议是渐进式：先用构造函数注入把依赖显式化，main 保持整洁；当装配代码开始重复、入口变多、测试需要反复拼装时，再把 wire 引进来。引入时先从一个 injector 开始，跑通生成、清理和测试三条链路，再逐步扩大范围。如果团队有多条构建流水线，还要把 wire 的版本固定下来，避免不同机器生成的文件格式不一致，给 diff 带来噪音。

小结

依赖注入在 Go 里不是容器，而是把构造责任集中到装配层的编码习惯；构造函数注入显式、可编译期检查，是默认选择。依赖变多后，手写装配会在 main、多个入口和测试中重复，wire 用 provider 描述“怎么造”，用 injector 描述“要什么”，在编译期生成普通 Go 代码。使用 wire 时重点掌握清理函数的逆序串联、wire.Bind 的接口绑定，以及用语义类型或结构体解决同类型冲突；测试优先手写 fake，需要时再生成测试装配。最后，wire 适合依赖图稳定、入口较多的项目，小项目继续手写即可，工具是为了减少重复，不是为了追求形式。
