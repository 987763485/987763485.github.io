FastAPI 入门：快速构建 API

本文属于《Python 学习路线》第 19/29 篇
上一篇系列目录下一篇

截至本文写作时，FastAPI 仍处于早期预览阶段，尚未正式发布，API 与文档可能变化；本文按作者公开的早期设计介绍，生产使用请等待稳定版本。

如果你写过一段时间的 Flask，大概都经历过这样的循环：从 request.args 里取值，手动转成 int，判断是否为空，捕获转换异常，再拼一个错误响应。接口一多，这类代码就在每个视图函数里重复一遍，而接口文档又要在另一个地方单独维护，改代码时很容易忘记同步。本文介绍的 FastAPI 试图把这三件事收拢到一处：用 Python 的类型注解描述参数，让框架完成校验，再顺带生成接口文档。本文适合已经会用 Flask 写接口、想了解这种新思路的读者。读完后你应当能看懂早期 FastAPI 的最小用法，也能判断它当下是否值得投入。

FastAPI 的出发点是：函数的签名本身就已经包含了类型信息，为什么不直接用它？把参数写成 item_id: int，框架读取注解，自动完成转换与校验，失败时返回结构化的错误；同时把这些信息汇总成 OpenAPI 描述，交给 Swagger UI 渲染。一份声明，三处复用。这个思路并不复杂，但在 Python 生态里此前少有人把它做得足够彻底。

需要强调的是，这只是设计目标。截至本文写作时，项目尚在早期预览，下面所有示例都是早期接口示意，实际 API 可能随作者调整。

技术底座：Starlette 与 Pydantic

FastAPI 本身并不从零实现 HTTP 协议，它站在两个库之上。

第一个是 Starlette，一个轻量的 ASGI 框架。ASGI 是相对 WSGI 的新一代异步网关接口规范，WSGI 的调用模型是同步的，一个请求占用一个线程直到返回；ASGI 则允许应用以协程的方式处理请求，在等待数据库或下游服务时可以交出控制权。Starlette 提供了路由、中间件、请求与响应对象、WebSocket 等基础能力。

第二个是 Pydantic，一个基于类型注解的数据校验库。你定义一个继承自 BaseModel 的类，声明字段与类型，Pydantic 负责在实例化时校验并转换，比如把字符串 "42" 转成整数 42，把缺失的必填字段报成错误。

两者分工清晰：Starlette 管连接与路由，Pydantic 管数据形状，FastAPI 在中间做黏合，把函数签名翻译成校验规则与文档描述。运行时要求 Python 3.7，因为这一版才正式把 async/await 稳定下来，并引入了 dataclasses 等便于描述数据的工具。若项目还停留在 Python 3.5 或 3.6，这套东西基本无法使用。

另一个约定是错误的分层。参数类型不对、必填字段缺失这类问题，由框架在进入处理函数之前拦下，返回表示请求无法处理的状态码；处理函数内部主动抛出的业务错误则是另一类。这种分工让业务代码不必再写一堆防御性判断，但也要求客户端把两类失败分开处理，联调前最好先对齐约定。

框架根据参数的类型决定数据来源：BaseModel 子类读请求体，标量读查询参数。tax 给了默认值，客户端不传也能通过；name 没有默认值，缺失即为错误。校验失败时，返回的错误体大致是一个包含 detail 列表的结构，每一项带出错位置、错误类型与说明，例如指出 body 中 price 字段不是合法数字。这种结构对前端比较友好，可以直接把字段级错误映射到表单上。

模型还可以嵌套。比如订单里包含一组商品明细，可以把明细定义成另一个模型，再在订单模型里声明为列表，校验会逐层递归下去，错误位置也会带上层级路径。查询参数同样支持声明为列表，用于接收重复出现的同名参数。这类能力在早期版本中已经具备雏形，但具体写法仍在调整，本文不再展开。

与手写校验相比，省掉的不只是 try/except，还有“校验规则与文档不同步”的问题。规则只有一份，写在签名与模型里，改了就同时影响校验与文档。代价是团队需要接受类型注解作为接口契约的一部分，这对习惯了动态类型的 Python 开发者是一个观念上的转变。

自动文档：描述是如何生成的

在早期设计中，FastAPI 会把路由、参数类型、Pydantic 模型的字段与默认值汇总成一份 OpenAPI 描述，再挂载 Swagger UI 供人浏览和调试。整个请求处理与文档生成的关系大致如下：

flowchart TD
    A[客户端请求] --> B[Starlette 路由匹配]
    B --> C[按签名解析路径与查询参数]
    C --> D[Pydantic 校验请求体]
    D -->|失败| E[返回结构化错误]
    D -->|通过| F[调用 handler]
    F --> G[序列化响应]
    B --> H[汇总路由与模型]
    H --> I[生成 OpenAPI 描述]
    I --> J[Swagger UI 展示与调试]

值得说明的是，这份描述是运行时根据已注册的路由推导出来的，不需要额外维护 YAML 文件。对内部服务而言，这意味着接口一上线就能在页面上看到参数说明并直接发请求，联调成本会低不少。不过在预览阶段，文档页面本身仍在完善，部分边界情况的描述未必准确，作者也在调整模型字段的展示方式。把它当作辅助工具即可，暂时不宜当作对外交付的正式契约。若接口要提供给外部团队，建议仍用版本化的文档或描述文件把契约固化下来，页面只作为调试入口，避免因框架升级导致描述漂移。

区别在于并发模型。async def 的函数运行在事件循环里，遇到 await 时挂起当前任务，去处理别的请求，适合数据库查询、调用外部接口这类 IO 密集场景。普通函数如果直接放在事件循环里执行，一次耗时操作就会堵住所有请求，因此设计上会把同步处理函数交给线程池。这个机制的具体行为在早期版本中还在打磨，读者应按“预览特性”看待。

运行需要 ASGI 服务器，uvicorn 是当时最常见的选择，支持热重载，开发时比较方便。要注意的是，异步并不意味着自动变快：如果处理函数里调用的是同步的数据库驱动，事件循环照样会被阻塞，收益有限。真要用好这条路线，整条调用链上的库都得支持异步，这在 2018 年的 Python 生态里并不是件轻松的事。

把三者放在一起，定位差别比较清楚：

Flask 的优势是简单直接，生态庞大，遇到问题几乎都能搜到答案。DRF 的优势是完整，认证、权限、分页、过滤都有现成方案，适合以 Django 为主的项目。FastAPI 在参数校验与文档上的体验确实更顺，但生态几乎是从零开始，中间件、认证、ORM 集成都要自己补。选择框架从来不是只看写起来爽不爽，还要看出了问题有没有人踩过同样的坑。

现阶段的限制

把话说透，早期预览阶段的问题至少有这几条。

其一，版本不稳定。接口随时可能调整，今天写的代码下周未必能跑，这对教学与生产都是负担。其二，生态小。第三方扩展少，常见需求如权限、限流、后台管理，都得自己实现或拼装。其三，生产案例少。没有足够多的线上系统验证过它在高并发、长连接、异常边界上的表现，性能方面的说法也缺少公开的、可复现的基准，本文不做任何数字上的比较。其四，文档仍在完善，示例与实际行为偶有出入。其五，团队协作成本。类型注解怎么写、模型放在哪一层、错误如何统一，都还没有形成社区共识，人一多就容易风格分裂，代码评审时缺少可对照的惯例。

那么什么时候适合试用？如果你的团队正在做内部工具、原型验证，或者本来就在用 Starlette 与 Pydantic，想少写一点胶水代码，可以拿它试试，但要有“随时重写”的心理准备。如果是对外服务、有明确交付日期、需要长期维护，现阶段不建议作为主力框架。

如果要现在上生产

需要马上交付一个 API 服务，比较稳妥的组合仍是两条老路。一条是 Flask 加 Marshmallow：Flask 负责路由，Marshmallow 负责序列化与校验，字段声明集中在一处，配合 apispec 之类的工具也能生成 OpenAPI 描述，虽然要多写一些配置，但每一块都成熟可控。另一条是 Django REST Framework：项目本身就在 Django 上时几乎不用犹豫，Serializer、ViewSet、权限与分页都是现成的，代价是要接受 Django 的整套约定。

这两条路的共同点是：出了问题能查到资料，招人时也容易找到熟悉的人。等 FastAPI 发布稳定版本、生态补齐、有可信的生产案例之后，再评估是否迁移也不迟。框架选型的机会成本，往往比少写几行校验代码高得多。

小结

FastAPI 的核心主张是把类型注解变成接口契约：签名描述参数，Pydantic 完成校验，框架据此生成文档，一份声明多处复用。它建立在 Starlette 的 ASGI 能力与 Pydantic 的校验能力之上，运行于 Python 3.7，异步是它的另一条主线。就本文写作时的状态而言，它还只是早期预览，接口会变、生态单薄、生产案例有限。学习它的设计思路是有价值的，把它直接放进生产则要谨慎；当下需要交付，Flask 加 Marshmallow 或 DRF 仍是更稳的选择。
