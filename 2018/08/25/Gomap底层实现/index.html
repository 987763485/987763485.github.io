Go map 底层实现

本文属于《Go 语言与工程》第 37/78 篇
上一篇系列目录下一篇

map 是 Go 里使用频率最高的容器之一，用起来简单，背后却藏着不少运行时细节。本文从 hmap 与 bmap 两个结构出发，解释 map 为什么无序、扩容时发生了什么，以及并发读写为什么会直接让程序崩溃。读完之后，你应当能读懂简化版的运行时结构图，并在写业务代码时避开常见的性能与并发陷阱。使用层面的增删改查与扩容现象，前文已经讨论过，本文只聚焦运行时实现。

从两个日常疑问说起

map 的用法几乎不用复习：make 创建、下标读写、delete 删除、range 遍历，几分钟就能上手。真正让人困惑的往往是两个现象：第一，同样的键值对，两次 range 出来的顺序可能不同；第二，两个 goroutine 同时读写同一个 map，程序有时会直接以 fatal error 结束，而不是返回一个可以 recover 的 panic。这两个现象都不是偶然，而是运行时结构直接决定的结果。

本文从 Go 运行时里的 hmap 和 bmap 入手，先看 map 在内存里长什么样，再沿着一次查找、一次写入的路径，解释哈希定位、扩容迁移、遍历取随机起点以及并发检测。文中代码是简化示意，字段命名接近真实源码，但省略了无关细节。最新版本 Go 1.11 刚在 2018 年 8 月发布，它的 map 实现与 1.10 一致，本文的讨论对这两个版本都适用。

hmap：map 的顶层结构

map 变量本身只是一个指针，指向运行时分配的 hmap。hmap 不直接存放键值对，它保存的是元信息和一个指向桶数组的指针，可以理解为一本书的目录页，真正的条目在后面的桶里。

count 让 len 成为 O(1) 操作；B 决定桶数组长度为 2 的 B 次方，扩容时桶数翻倍；hash0 是每个 map 独有的随机种子，参与哈希计算，使同样的键在不同 map 里落到不同位置，也能在一定程度上抵御构造哈希冲突的攻击；buckets 指向当前桶数组；oldbuckets 只在迁移期间非空；overflow 缓存已分配的溢出桶，真实布局里它放在 mapextra 中。结构里还有 flags 与 noverflow，后文会用到。

flowchart TD
    H["hmap"] --> B["buckets：长度 2 的 B 次方"]
    H --> OB["oldbuckets：仅扩容期间存在"]
    B --> B0["bmap 桶 0"]
    B --> B1["bmap 桶 1"]
    B1 --> OV["overflow 桶"]
    OV --> OV2["overflow 桶 ..."]

从图中可以看到三层关系：hmap 持有桶数组，每个元素是一个 bmap，bmap 装满后通过 overflow 指针串出更多桶。查找时先定位到某个桶，再在桶及其溢出链里逐个槽位比较。

bmap：一个桶里放了什么

bmap 是真正存放键值对的地方。一个桶固定有 8 个槽位，编号 0 到 7。每个槽位对应一个 tophash 字节、一个 key 和一个 value。运行时并不会为每个槽位单独分配结构体，而是把 8 个 tophash 放在最前面，紧接着连续放 8 个 key，再连续放 8 个 value，最后是一个 overflow 指针。“先 key 后 value”的布局是为了减少内存对齐浪费：key 与 value 大小不同时，同类数据集中存放可以避免大量填充字节。

tophash 是这个设计的点睛之笔。查找时先比较一个字节，只有 tophash 相同才需要比较完整的 key；大部分不匹配的槽位在第一轮就被排除，省掉了昂贵的字符串或结构体比较。tophash 还承担状态标记：0 表示该槽位及其后面都为空，1 表示该槽位为空但后面可能还有元素，2 到 4 是扩容迁移标记。普通哈希的高 8 位若落入这些特殊值，运行时会加偏移量，保证正常槽位的 tophash 不小于 5。一个桶的 8 个槽位用完后，新元素会放进溢出桶，溢出桶与原桶通过 overflow 指针连成链表。

哈希与定位：一次查找的路径

以 64 位平台为例，运行时用类型对应的哈希函数计算 key 的 64 位哈希值，hash0 会混入其中。这个哈希值被分成两部分使用：低位用来选桶，高位用来做 tophash。若当前 B 为 5，桶数组有 32 个桶，取哈希值的低 5 位就能得到 0 到 31 的桶编号；哈希值的高 8 位则写入槽位的 tophash，供桶内快速筛选。低位负责分布是否均匀，高位负责桶内筛选是否高效。

定位到桶之后，运行时按槽位顺序扫描：先读 tophash，与目标哈希的高 8 位比较；相同则取出该槽位的 key，用运行时的相等函数比较。整数直接比较位模式，字符串先比长度再比内容，结构体逐字段比较。tophash 不同就跳过，连 key 都不用碰。如果当前桶没找到，就沿着 overflow 指针进入下一个溢出桶，直到链表结束。整个过程不需要遍历所有键，只需要扫描一个桶链，因此平均查找代价与 map 的大小基本无关。

字符串 key 的哈希必须在每次操作时重新计算，运行时不会把哈希值缓存进字符串里。所以 key 越长，单次查找的哈希开销越大；这也是后面建议里提到 key 类型选择的原因之一。

扩容：装载因子 6.5 与增量迁移

map 不能无限往桶里塞。运行时用装载因子衡量拥挤程度：所有键值对数量除以桶数量，平均值超过 6.5 就触发扩容。这个阈值是空间与时间的折中：平均装到 6.5 个后再插入，冲突链开始变长，查找效率下降；阈值再低又会浪费空槽。除了装载因子，溢出桶过多也会触发扩容，此时往往是因为大量键被删除后又插入，桶里到处是空洞，需要整理。

扩容分两种。第一种是翻倍扩容：桶数组长度从 2 的 B 次方变成 2 的 B+1 次方，旧桶里的元素按哈希值的下一位分成两半，分别进入新桶数组的两个位置。第二种是等量扩容：桶数量不变，只是把旧桶和溢出桶里的元素重新紧凑地搬到新桶，解决溢出桶过多的问题。判断依据不同，但迁移流程一致。

迁移不是一次性完成的。一次搬完会让单个写操作停顿很久，所以运行时采用增量迁移：先把 oldbuckets 指向旧数组，buckets 指向新数组，然后每次写或删除操作顺带迁移一到两个旧桶。每个旧桶被访问时，里面的 8 个槽位和溢出链会被整体搬到新位置，并在旧槽位上留下迁移标记。迁移全部完成后，oldbuckets 被置空，旧数组才真正可被回收。这也是扩容期间内存占用会短暂上升的原因。

遍历为什么是无序的

理解了桶结构，无序就很好解释。range 一个 map 时，运行时并不会从 0 号桶、0 号槽位开始。它会取一个随机数，用低位决定起始桶，用另一位决定桶内的起始槽位，然后从那里开始绕一圈，把每个桶的 8 个槽位扫完，再沿溢出链继续。由于起点随机，两次遍历看到的第一元素通常不同，整体顺序自然也不固定。起点来自运行时随机数，不存在固定种子，运行时也不承诺顺序稳定。

扩容期间遍历更复杂。迭代器创建时如果迁移还没完成，它可能从旧桶区域开始，也可能从新桶区域开始；扫描过程中，有的键还在旧桶，有的已经被搬到新桶。运行时会同时检查两边，并用迁移标记避免同一个键被访问两次。所以扩容中的遍历看到的是新旧结构混合的结果，顺序更加不可预测。

规范层面，Go 只承诺遍历会覆盖当时的键集合，从不保证顺序。业务代码如果依赖顺序，正确做法是把 key 收集到切片里再排序，而不是假设某种“看似稳定”的顺序。遍历期间插入或删除键，新键可能被看到也可能被跳过，这一点同样没有定义。

删除一个键之后发生了什么

delete(m, k) 的流程与查找类似：算哈希、定位桶、比较 tophash 和 key，找到后把对应槽位的 tophash 改成空标记。如果 key 或 value 中含有指针，运行时还会把对应存储清零，避免垃圾回收器误以为对象仍被引用。删除完成后 count 减一，len 立刻反映变化。对 nil map 执行 delete 是安全的空操作，这一点与读取 nil map 一致，但向 nil map 写入会 panic。

但 map 不会因为删除而缩容。桶数组还是那么大，B 不变，已分配的溢出桶也不会立刻归还。删除只是留下可以复用的空槽，后续插入会优先填补这些空位。用 runtime.ReadMemStats 对比删除前后的 HeapAlloc，通常看不到明显回落。如果曾往一个 map 里塞过一百万条数据，再删到只剩几条，它占用的内存也不会自动降下来；只有 map 本身不再被引用、被垃圾回收，或者你重新创建一个 map 并替换它，这部分内存才会释放。这个行为在长生命周期的缓存结构里尤其要注意。

并发读写为什么直接崩溃

map 的设计目标之一是单 goroutine 下的高性能，因此它没有任何锁。为了保证写入过程中不被其他写操作破坏，运行时在 hmap 的 flags 字段里设置了一个 hashWriting 标志位。写操作开始时检查该位，如果已经被别的写操作置位，就抛出 concurrent map writes；检查通过后自己置位，写完再清除。读操作也会检查这个位，一旦发现有人正在写，就抛出 concurrent map read and map write。

关键在于，这些错误不是普通的 panic，而是运行时主动终止程序的 fatal error，用 recover 拦不住。原因是此时 map 的内部结构可能已经被破坏，继续运行只会得到更难排查的后果。即使没触发检测，并发读写仍是数据竞争，-race 可以帮你找出来，但生产环境不能依赖运气。

实际项目里的做法很直接：需要并发访问时，用 sync.RWMutex 包一层，读多写少且键集合相对稳定的场景可以评估 sync.Map，它的取舍与 API 细节留到专门的文章讨论，这里不展开。另一个常见错误是把 map 放进结构体传值，副本共享同一个底层 hmap，锁也必须跟着共享。

写业务代码时的几点建议

第一，能预估规模就预设容量。make(map[string]int, 1024) 会让运行时按 1024 个元素选择初始 B，保证 6.5 乘以桶数不小于这个值，从而避免插入过程中反复扩容和迁移。对于批量导入、解析大 JSON 这类场景，这个习惯能省下可观的分配与拷贝。

第二，key 类型尽量选择哈希开销小的。整数、指针的哈希代价基本固定；字符串要对全部字节做哈希，长字符串作为 key 且查找频繁时，开销会明显上升；结构体 key 会逐字段参与哈希与比较，字段越多越重。必须用长字符串时，可以在业务层先映射成短 ID，但要自行维护映射关系。

第三，value 很大时存指针。map[string]BigStruct 在插入和取值时都会复制整个结构体，而 map[string]*BigStruct 只复制一个指针，通常更划算；当然这也意味着对象分配在堆上，需要结合实际情况权衡。

第四，不要用 map 做无界缓存。它不会缩容，删除也不归还内存，长期运行的服务应当设置淘汰策略或定期重建。

用 benchmark 自己量一量

性能结论最好来自自己机器上的测量。Go 的 testing 包自带 benchmark，把下面两个函数放在同一个包里，就能对比预设容量与否的差异。第一个每次新建一个不带容量提示的 map，第二个带上元素总数作为提示，其余逻辑完全一致。

运行方式是 go test -bench=. -benchmem，输出里重点看三列：ns/op 表示单次操作耗时，B/op 表示每次操作分配的字节数，allocs/op 表示分配次数。带容量提示的版本通常分配次数更少，但具体差距取决于元素数量、机器和 Go 版本，本文不给出固定数字，你应当以自己跑出来的结果为准。还可以把 key 换成不同长度的字符串，观察哈希开销的变化；也可以写查找基准，先构造好 map，再在循环里反复读取，用 b.ResetTimer 排除构造阶段的影响。

小结

map 的表面是一组键值对，底层是 hmap、桶数组和 bmap 溢出链。哈希值低位选桶、高位做 tophash 筛选，装载因子超过 6.5 或溢出桶过多时触发扩容，迁移以增量方式分摊到后续操作。遍历起点随机，顺序不可依赖；删除只打空标记、不缩容，内存要等 map 整体回收。并发读写靠 hashWriting 检测，触发的是无法 recover 的致命错误，正确做法是加锁或按场景选用 sync.Map。预设容量、选好 key 类型、避免无界增长，再用 benchmark 验证，基本就能把 map 用得更稳。
