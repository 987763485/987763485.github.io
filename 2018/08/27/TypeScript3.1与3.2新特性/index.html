TypeScript 3.1 与 3.2 新特性

本文属于《TypeScript 学习路线》第 42/74 篇
上一篇系列目录下一篇

TypeScript 3.1 在 2018 年 8 月 27 日正式发布，而 3.2 还处在 RC 阶段。本文先把 3.1 里可以立刻用上的三项能力讲透：映射类型作用于元组与数组、函数声明上的属性、以及与 --resolveJsonModule 和 import 类型相关的配合。随后以“前瞻”的口吻梳理 3.2 RC 中已经公开的方向，包括 strictBindCallApply、泛型对象 rest/spread 和 bigint。读完之后，你应该能判断哪些改动现在就能落地，哪些要等正式版再动。

版本节奏：为什么新特性文章必须标注发布状态

TypeScript 的发布节奏在 3.0 之后变得相当规律：大约每两个月一个次版本。3.0 在 2018 年 7 月 30 日发布，带来了 unknown、项目引用与元组 rest 参数；3.1 在 8 月 27 日发布，也就是本文写作的当天；3.2 按计划要到 9 月下旬才会正式发布。换句话说，本文动笔时，3.1 是 npm 上 latest 标签指向的稳定版本，3.2 只是候选版本（Release Candidate）。

这个时间差直接决定了文章能写什么。把 RC 里的行为当成“现有能力”写进教程，读者照着敲却报错，是最常见的误导。因此本文对两个版本采用两种写法：3.1 的示例都可以在当前稳定版直接运行，3.2 的内容一律标注“RC 阶段”并给出“以正式版为准”的限定。下面这张图是本文涉及的时间关系。

flowchart LR
    A[3.0 发布于 2018-07-30] --> B[3.1 发布于 2018-08-27]
    B --> C[3.2 RC 本文写作时尚未正式发布]
    C --> D[3.2 正式版 以官方发布为准]

需要说明的是，RC 的含义是“功能面基本冻结、以修 bug 为主”，但它仍然可能调整细节。所以本文在 3.2 部分给出的示例，都建议等正式版落地后再合并进主干。

3.1 之一：映射类型可以作用于元组与数组

这是 3.1 里最有实际价值的一项改动，也是最容易在升级时“悄悄改变行为”的一项。

在 3.1 之前，Partial、Readonly、Required 这类内置映射类型只能安全地用在普通对象上。如果你把元组传进去，编译器会把元组当成一个带数字索引的对象来处理，得到的是一个奇怪的结构，长度信息与元素顺序都丢失了。3.1 之后，映射类型对元组和数组做了特殊处理，会保留它们的结构。

数组的表现也一致。Partial<string[]> 在 3.1 里是 (string | undefined)[]，Readonly<string[]> 则是 readonly string[]，也就是 ReadonlyArray<string>。映射类型会逐个元素地改写，而不是把整个数组换成一个普通对象。

理解这一点之后，很多“手写工具类型”就可以删掉了。以前为了表达“可选元素的元组”，我们不得不写 [string?, number?] 这样的手写类型，现在用一个 Partial 就够了；以前为了表达只读数组，要写 ReadonlyArray<T>，现在 Readonly<T[]> 也行，两者等价。

3.1 之二：在函数声明上直接声明属性

JavaScript 允许给函数挂属性，这是很常见的手法：函数本身是可调用的，同时又可以携带配置、缓存或几个辅助方法。TypeScript 在过去只对“赋值给 const 的函数表达式”支持得比较好，对函数声明（function f() {}）则比较保守。3.1 补上了这块。

在 3.1 之前，log.level = "info" 这一行会报 Property 'level' does not exist on type '(message: string) => void'。常见的绕法是把函数改成对象再挂属性，或者直接 as any，两种写法都会丢掉类型信息。3.1 之后，编译器会把同一作用域内的属性赋值视作对函数类型的扩展，之后读取 log.level 也能拿到正确类型。

这条规则有几个边界，值得提前知道：

  • 属性赋值必须和函数声明在同一个作用域内，跨模块或跨函数地“事后挂属性”不会被追踪。
  • 赋值要先于使用。先读 log.level、后赋值，读取处仍然是报错的。
  • 只对函数声明与赋给 const 的函数表达式生效，普通对象或类实例不适用。

两种写法怎么选？命名空间会额外生成一层立即执行函数，编译产物多一个包装对象；而“函数挂属性”的产物就是普通函数，对 CommonJS 调用方更友好，require 回来直接调用即可。若你的代码要与老的 module.exports = fn 风格互操作，后者更自然；若是组织一组彼此独立的工具函数，命名空间的导出更清晰。3.1 只是让第一种写法在类型上不再需要妥协。

3.1 的其他改进：JSON 模块与 import 类型

3.1 本身没有大改这两块，但它们和上面的特性常常一起出现，实际项目里绕不开，这里用一小节说明边界。

--resolveJsonModule 允许直接 import 一个 JSON 文件，并按文件内容推断类型。配合 3.1 的映射类型使用时，可以做的事很自然：把配置读进来，再用 Partial 派生一个“部分覆盖”的类型，用于合并默认配置与用户配置。

这里有两个细节。第一，JSON 推断出来的是放宽后的类型，"port": 3000 得到的是 number 而不是字面量 3000，所以不要指望从这里拿到字面量联合类型。第二，import 默认导入需要 --esModuleInterop（或至少 --allowSyntheticDefaultImports）配合，否则会提示该模块没有默认导出。

再说 import 类型。在类型位置写 import("./types").User 是合法的，它只参与类型检查，编译后会被完全擦除，不会在产物里留下 require。因此可以用它引用只存在于类型层的模块，而不用担心把运行时代码带进来。边界也很明确：它只能出现在类型位置，不能当值用，也不能用来调用构造函数；如果你需要运行时也拿到这个模块，仍然要写普通的 import 语句。

3.2 前瞻之一：strictBindCallApply

从 3.2 RC 的说明看，这一版最值得期待的是 strictBindCallApply。它要解决的是一个老问题：bind、call、apply 是 JavaScript 里类型最弱的三兄弟，过去 TypeScript 对它们几乎不做检查。

先看问题。Function.prototype.bind 在 3.1 及以前的类型声明里直接返回 any，call 与 apply 的参数也都退化成 any，参数校验形同虚设。结果是下面这种错误可以被静默放过：

打开 strictBindCallApply 之后，编译器会按原函数的签名去推导：bind 返回的函数只保留未被绑定的参数，call 与 apply 也必须给出完整的参数列表。

代价是：一些“故意动态”的写法会开始报错。比如给重载函数做 bind、把 this 换成另一个对象、或者用 apply 传一个 any[]，都可能被拦下。RC 阶段这些边界还在打磨，升级前建议先搜一遍代码里的 bind(、call(、apply(，心里有个数。这个选项属于 --strict 家族，一旦项目开了 strict: true，3.2 正式版之后它会自动生效，这是升级时最容易被忽略的一处行为变化。

3.2 前瞻之二：泛型对象 rest/spread 与 bigint

第二组是泛型场景下的对象展开，以及 bigint 类型。两者同样处在 RC 阶段。

先说 rest/spread。3.1 里对泛型做对象解构或展开，编译器往往退化成 {} 或直接报错，因为它无法证明 T 上一定存在某个属性。3.2 RC 让这类写法有了可用的类型：

对写工具库的人来说，这意味着 omit、pick、merge 这类函数可以少写很多类型断言，用户也不必再传一堆泛型参数。注意它仍然要求 T 受 object 约束，unknown 或裸泛型不行。

再说 bigint。3.2 RC 引入了 bigint 原始类型与 123n 这样的字面量，用于表示超出 Number.MAX_SAFE_INTEGER 的整数。它的限制比一般新特性更硬：

  • 目标需要是 ESNext。bigint 字面量不能被降级编译到 ES2018 或更低版本，设成低目标是直接报错，而不是退化成普通数字。
  • lib 要能提供 BigInt 的声明，显式写上 ESNext.Bigint 最稳妥，否则 BigInt 函数与大整数方法都可能找不到声明。
  • 运行时要支持 BigInt。Node.js 从 10.4 开始支持，浏览器端则要看具体版本。
  • bigint 与 number 不能混算，1n + 1 会抛 TypeError；JSON.stringify 遇到 bigint 也会抛错，序列化前要先转成字符串。

一句话总结这一组：工具库作者可以期待更精确的泛型推导，业务代码则要等目标环境真正支持 BigInt 之后再启用，别为了一个新类型把编译目标整体抬到 ESNext。

这种“按特性拆 lib”的做法从 2.x 就开始了，好处是不用为了一个 API 把整套新库都引进来，代价是 lib 写错时报错信息往往很隐晦——找不到 BigInt，第一反应通常是“类型定义没装”，实际上是 lib 少了条目。

RC 里还多了一个对排查配置很有用的开关 --showConfig。它不编译，只把当前目录下 tsconfig.json 解析、继承、合并之后的最终结果打印出来。extends 用得多的项目，经常出现“我明明在根配置里关了某个选项，为什么还在报错”的情况，多数是子配置覆盖或者 include 不匹配，用这个命令一看便知。

至于内置对象声明本身的收紧，RC 说明里提到过部分 API 的检查会更严格，但具体条目在候选阶段仍有调整。本文不逐条展开，等正式版发布说明确认后再补。升级时如果遇到“以前能过、现在报错”的内置方法调用，先看错误是否来自更新后的 lib 声明，再看是否与新增的严格检查有关。

升级建议：tsconfig、@types 与升级顺序

如果你现在用的是 2.9 或 3.0，3.1 的升级成本很低：它没有破坏性变更，主要是在既有语义上做补全。建议先把版本钉死，再逐项打开严格选项。

第一步，锁定版本。不要用 ^3.1.0，次版本之间的行为差异足以让 CI 在不同机器上给出不同结果：

第二步，整理 tsconfig.json。strict 是一个总开关，它把 noImplicitAny、strictNullChecks、strictFunctionTypes 等一起打开。老项目一次性全开，报错数量通常会让人放弃。更现实的做法是分三批：先开 noImplicitAny，处理隐式 any；再开 strictNullChecks，处理可能为空的返回值；最后开 strictFunctionTypes，处理回调参数的逆变问题。3.2 正式版之后，strictBindCallApply 也会被 strict 带进来，那时再单独做一轮。

第三步，检查第三方类型。@types/* 包由不同的人维护，有的还在用很老的编译器语法。升级后如果报错集中在 node_modules/@types 下，先升级对应的包；确实没有新版本时，可以临时开 skipLibCheck 把声明文件的检查跳过，但这只是止血，不要长期保留。同时注意 @types/node 的版本要和运行时对齐，Node 10 的项目不要装面向更新版本的类型包。

第四步，按依赖顺序推进。先升叶子模块（工具函数库、纯类型包），再升中间层，最后升应用入口。每升一层跑一次全量类型检查，把问题定位在当前层，而不是等到最后一次性面对几百条报错。3.2 正式版发布后，建议单独开一个分支只做 strictBindCallApply 的适配，别和新功能混在一起。

迁移中的三个常见坑

第一个坑来自映射类型。升级到 3.1 后，Partial、Readonly 作用在数组或元组上的结果变了，原先为了绕过限制而手写的工具类型可能和新行为打架。典型症状是某个数组属性的类型突然从“带数字索引的对象”变成“元素可空的数组”，下游的 Object.keys、for...in 写法开始报错。这类改动不会在运行时出问题，但类型层需要清理一遍旧的自定义映射类型。

第二个坑是 bind。3.2 正式版启用 strictBindCallApply 后，重载函数、this 类型复杂的类方法、以及把函数当高阶值到处传的代码，最容易报参数不匹配。处理原则是先看是不是真的传错了，确实是动态调用再局部断言，不要图省事把整个文件改成 any。

第三个坑是 lib。用 bigint 却没在 lib 里加 ESNext.Bigint，或者目标设成了 ES2018，报错都指向“找不到名称”，很容易被误判成类型包缺失。遇到这类提示，先看 tsc --showConfig 的实际输出。

小结

3.1 是可以立刻升级的版本：映射类型作用于元组与数组、函数声明上挂属性这两项改动直接减少了类型断言的用量，升级风险也低。3.2 的方向同样清晰，strictBindCallApply 补上了 bind/call/apply 的类型检查，泛型 rest/spread 与 bigint 则分别照顾了工具库作者和对大整数有需求的场景。但在本文写作时 3.2 仍是 RC，相关示例与选项细节都可能调整，生产项目建议先锁在 3.1，等 9 月下旬正式版发布后再按“先 lib、再 strict、最后 strictBindCallApply”的顺序逐步开启。
