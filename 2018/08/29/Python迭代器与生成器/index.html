Python 迭代器与生成器

本文属于《Python 学习路线》第 3/29 篇
上一篇系列目录下一篇

迭代是 Python 里出现频率最高的动作之一：for 循环、列表推导、sum、逐行读文件，底层走的都是同一套迭代协议。很多开发者能写出带 yield 的函数，却说不清 __iter__ 与 __next__ 的分工，也不知道生成器为什么只能遍历一次。本文从迭代协议讲起，依次拆开生成器的执行模型、send/throw/close、itertools 组合与分块读取的实战写法，最后落到性能边界与常见坑。读完你应当能判断一段代码该用列表还是生成器，并在遇到“数据莫名少了一半”时知道从哪里下手。

可迭代对象与迭代器：两个容易混淆的协议

初学者常把“可迭代对象”和“迭代器”当成同义词，其实它们是两个层次的概念，在语言规范里对应两个不同的魔术方法。

可迭代对象只承诺一件事：能产出一个迭代器。它实现 __iter__，返回一个迭代器。列表、元组、字典、集合、字符串、文件对象都属于这一类。迭代器则承诺两件事：能给出下一个元素，并且在取完之后明确告诉调用方“没有了”。它实现 __next__，元素耗尽时抛出 StopIteration，同时按约定让 __iter__ 返回自身。

这就解释了为什么 for 能作用于列表，却不能直接对列表调用 next()：列表没有“当前位置”，每次遍历都该从头开始，所以每次 __iter__ 都发出一个全新的迭代器；迭代器自己携带游标，才配拥有 __next__。

还有一条兼容路径：对象若没有 __iter__ 但实现了 __getitem__，iter() 会退化成从索引 0 逐个取，直到 IndexError。这是旧式序列协议的遗留，读老库源码时会遇到。

生成器函数：让函数学会暂停

只要函数体里出现 yield，这个函数就不再是普通函数，而是一个生成器函数。调用它不会执行任何一行函数体，只会立刻返回一个生成器对象；真正的执行发生在第一次 next() 时，遇到 yield 就暂停，把后面的值交出去，等下一次 next() 再从暂停处继续。

“暂停”暂停了什么？CPython 会保留生成器的栈帧：局部变量 i、当前字节码位置、异常处理状态都打包在这个帧里，但它已从调用栈上摘下。所以暂停期间调用栈是平的，主程序照常运行；恢复时把帧挂回去，从上次的位置接着跑。这也解释了为什么调试器在调用栈里看不到它。

用一张图概括整个驱动过程：

flowchart TD
    A[for 循环取下一个元素] --> B[调用 iter 得到生成器]
    B --> C[调用 next 驱动生成器]
    C --> D{执行到 yield 吗}
    D -- 是 --> E[挂起帧 把值交回循环]
    E --> A
    D -- 否 --> F[函数返回 抛出 StopIteration]
    F --> G[循环结束]

惰性求值是生成器最本质的收益：值在被需要的那一刻才算。查一次数据库、读一行网络响应，都可以推迟到循环走到那里。代价是副作用的时间点不直观，日志与异常的出现位置常与书写顺序不一致。

send、throw、close 与 yield from

yield 不只是一个出口，它还是一个表达式，有返回值。这个值来自调用方的 send()，于是生成器从“单向产出”变成了“双向通道”：调用方送进去一个值，生成器处理完再吐出一个值。

第一次必须用 next() 或 send(None) 启动，因为生成器还没跑到 yield，此时没有表达式可以接收值，直接 send 非 None 会抛 TypeError。这个“先预热”的步骤是生成器当协程使用时最典型的样板代码，3.6 的异步生成器把这套协议搬进了 async def，本文只提一句，不展开。

throw() 在暂停点注入一个异常，让它像普通异常一样在生成器内部抛出，可以被内部的 try/except 捕获。close() 则是注入 GeneratorExit，要求生成器立即收尾。两者都是为了让外部有能力打断一个正挂起的执行流，并把清理逻辑跑完：

在 finally 里再次 yield 是错误的：close() 的语义是“不要再产出值了”，解释器会抛 RuntimeError。清理代码只做关闭、回滚、记日志，不要试图继续往外送数据。

yield from 在 3.3 加入，用于把一个生成器的产出委托给另一个可迭代对象。它不只是语法糖：send、throw、close 都会自动透传，子生成器的 return 值会成为 yield from 表达式的值，子生成器抛出的 StopIteration 也被自动接住。

手写等价的循环要自己处理异常与返回值，代码会长不少；它也不减小递归深度，这一点后面还会提到。

itertools：把迭代器当零件拼装

标准库的 itertools 提供了一批返回迭代器的工具函数，特点是全部惰性、不复制数据。常用的几类可以这样记：

  • 取子集：islice(it, start, stop, step) 对任意迭代器切片，不支持负数索引，因为它没法知道总长度。
  • 造序列：count(start, step) 无限计数，cycle(it) 无限循环，repeat(x, n) 重复。它们都必须配合 islice 或 zip 之类有终止条件的消费者，否则就是死循环。
  • 拼接：chain(a, b) 顺序串接多个可迭代对象，chain.from_iterable(nested) 展开一层。
  • 分组：groupby(it, key) 把相邻且键相同的元素归到一组。
  • 复制：tee(it, n) 把一个迭代器裂成 n 份，内部用缓冲实现。

生成器的边界：一次性与不可见

生成器不是“更省内存的列表”，它有明确的限制，越界使用会得到静默的错误结果。

最要紧的一条是只能遍历一次。生成器耗尽后再 for 一遍，什么也不会发生，也不会报错，list(g) 得到空列表。同理它没有 len()、不支持索引和切片、不能回退。需要多轮访问时，要么在入口处 list() 物化，要么每次重新调用生成器函数。

第二条是调试不便。生成器暂停时，它的帧不在调用栈上，traceback 里看到的调用链会断在 next() 那一层，异常却发生在生成器内部。排查时容易误以为是循环写错了，其实是生成器里的某次取值失败。

第三条是异常传播路径。生成器内部抛出的异常会在驱动它的 next() 处重新抛出，位置看起来在循环里；反过来，循环体的异常不会自动送进生成器。判断 try/except 该写在哪一侧，靠的就是这条规则。

第四条是并发不安全。同一个生成器被两个线程同时 next()，后到的那个会收到 ValueError，提示生成器已在执行中。需要并发消费时，每个线程各自持有一个生成器，或者改用队列分发。

性能与内存：什么时候别用生成器

生成器不是免费的。创建对象、每次取值的帧切换与结束判断都是固定开销，纯遍历通常比直接迭代列表慢。数据量不大、需要多轮遍历或索引时，列表更简单也更快。

yield 与回调的取舍同理。回调层层嵌套后难读；生成器把“推”改成“拉”，代码是顺序的。但生成器只能被消费者拉动，外部无法主动推进（send 算半个例外），需要事件驱动或超时控制时，回调与队列更直接。

常见坑

第一，在遍历过程中修改被遍历的列表。对列表做 for 时增删元素，会让迭代器按索引前进，结果跳过元素或重复处理。正确做法是先收集要改的项，循环结束后统一处理。

第二，生成器被提前回收。引用计数归零时 CPython 立即关闭生成器，finally 照常执行，未消费的部分永久丢失。存进全局缓存或后台线程时要显式管理它的生命周期。

第三，return 的值拿不到。生成器用 return x 结束时，x 藏在 StopIteration.value 里，普通 for 看不见，只有手动 next() 并捕获异常才能取到。若确实需要返回值，通常说明该用普通函数了。

第四，递归生成器仍有深度限制。yield from 只是委托，不改变调用栈的深度，遍历很深的目录树时应当改用显式栈，而不是递归生成器。

小结

迭代协议把“能不能遍历”和“遍历到哪了”拆成 __iter__ 与 __next__ 两件事，for 只是这套协议的语法外壳。生成器用 yield 把函数变成可暂停的状态机，帧被保留、栈被让出，于是有了惰性求值与恒定内存。send/throw/close 让它成为双向通道，yield from 负责把委托的细节补齐，itertools 则提供了现成的零件。

实践上的判断很简单：一次性、顺序、数据量大，用生成器；需要多次访问、随机索引或长度，用列表。写生成器时守住两条底线，不在遍历中改动数据源，不假设它会被消费完。
