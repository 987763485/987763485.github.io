Python 正则表达式实战

本文属于《Python 学习路线》第 8/29 篇
上一篇系列目录下一篇

日志清洗、表单校验、配置解析，这些日常任务里几乎都能看到正则表达式的影子。本文以 Python 3.7 的标准库 re 为对象，从基础元字符讲到分组、前后查找、替换与编译复用，再落到日志解析、URL 提取和格式校验等实战场景，最后集中梳理常见陷阱。文章假设读者已经会写 Python，但正则仍停留在复制粘贴和试错的阶段；读完后应当能独立写出可读、可维护、性能可控的模式。

正则的边界：能做什么，不该做什么

正则表达式描述的是一类文本的形状：哪些字符、以什么顺序、重复多少次。它擅长在一段文本中定位、提取、替换符合形状的片段，例如从日志里捞出 IP、把日期从一种格式换成另一种、判断输入是否符合手机号的形式。它的长处是表达紧凑、执行直接，不需要为一次匹配写完整的词法分析器。

但它不是万能的。正则的经典模型无法记录任意深度的嵌套，因此解析 HTML、JSON、XML 这类层层嵌套的结构时，模式会迅速变得不可读且不可靠。一个常见的反例是用 <div>.*?</div> 去匹配页面，遇到嵌套的 div 时要么截断、要么错配，正确的做法是使用专门的解析器。同理，表达式求值、SQL、编程语言语法这类需要维护符号表与优先级规则的场景，应当交给 parser 或现成的语法库，而不是一条越来越长的正则。

判断标准可以概括为：如果匹配只依赖局部字符的形状，正则合适；如果匹配依赖已经读到了什么、嵌套到了第几层这类上下文状态，就该换工具。把这条边界记在心里，后面所有的技巧才有意义。

基础元字符：从字符形状开始

先认识最常用的一批元字符。. 匹配除换行符之外的任意单个字符；* 表示前面的元素重复零次或多次；+ 表示一次或多次；? 表示零次或一次；{m,n} 表示重复 m 到 n 次，{m,} 与 {,n} 分别表示至少 m 次与至多 n 次。量词默认作用于紧邻的前一个元素，想让多个字符整体重复，必须先用括号把它们括起来。

方括号 [] 定义字符集合，[abc] 匹配其中任意一个字符，[^abc] 匹配不在集合中的字符，[a-z0-9] 使用范围。集合内部的大部分元字符会退化为普通字符，只有 ]、\、^（在开头）和 -（在两个字符之间）需要留意，把 - 放在开头或结尾即可表示字面量。此外，\d、\w、\s 是预定义集合的简写，分别代表数字、单词字符与空白字符，大写形式 \D、\W、\S 表示取反。

锚点 ^ 与 $ 匹配字符串的开头和结尾（默认如此，多行模式另说），\b 匹配单词边界，也就是单词字符与非单词字符之间、以及字符串首尾的位置。下面的例子用它们处理邮箱与日期片段：

分组与捕获：让模式有结构

圆括号 () 有两层含义：分组与捕获。分组让量词可以作用于一段子模式，捕获则把括号内匹配到的文本保存下来，供后续引用。捕获组按左括号出现的顺序从 1 开始编号，group(0) 或 group() 返回整个匹配，group(n) 返回第 n 组，groups() 返回所有组的元组。

只想要分组、不想要捕获时，用非捕获组 (?:...)。它不占用编号，也不会出现在 groups() 里，既能避免打乱编号，又能减少不必要的开销。需要按名字取用时，命名组 (?P<name>...) 更直观，配合 groupdict() 可以直接得到字典。

命名组在模式较长时尤其有价值：日志格式、URL 结构这类字段多的场景，按名字取值比数括号可靠得多。命名组的名字必须是合法的 Python 标识符，同一个模式里不能重名。非捕获组常用于只想重复一段文本的地方，例如 (?:\d{1,3}\.){3}\d{1,3} 里的点分段，我们只关心整体，不关心中间每一段。

贪婪与非贪婪：匹配多少才算够

量词默认是贪婪的：.* 会先吞掉尽可能多的字符，再在后续模式匹配失败时逐个吐回来，这个过程叫回溯。与之相对，.*? 是非贪婪的，先尝试最短的匹配，只有在整体匹配失败时才继续扩张。两者匹配到的文本可能相同，也可能不同，取决于模式后面还跟着什么。

第一个模式把两个 <b> 之间的全部内容当成一个整体，第二个模式则在每个 </b> 处收手。写提取时通常希望后者，写整段替换时可能希望前者，关键是想清楚结束标志是什么。

回溯是理解性能问题的钥匙。引擎每吐回一个字符就要重新尝试剩余模式，如果模式里出现嵌套量词，例如 (a+)+$，失败时回溯次数会随长度指数增长，一段几十个字符的输入就能让程序卡住。Python 的 re 模块是回溯引擎，3.7 没有提供匹配超时参数，因此防线要建在模式设计上：能用字符类就不用 .，能写 [^<]* 就不写 .*?，避免嵌套量词，必要时先截断输入长度。

常用函数：返回值到底差在哪

re 模块的函数看起来相似，语义差别却不小。search 在整段文本中寻找第一个匹配，找到就返回 Match 对象，找不到返回 None；match 只从字符串开头尝试，但并不到结尾；fullmatch 要求整个字符串都匹配，是表单校验的正确选择。三者返回的都是 Match 对象，可以统一用 if m: 判断，再通过 group 取值。Match 还提供 start、end、span 和 string，需要定位命中位置时不必手动计算下标。

findall 返回列表：没有分组时是匹配文本的列表，有一个分组时是分组文本的列表，有多个分组时是元组的列表，这个变化是初学者最容易踩的坑之一。finditer 返回迭代器，产出的每个元素都是 Match 对象，需要位置和分组信息时应当用它。sub 返回替换后的新字符串，split 按模式切分并返回列表，两者都不会修改原字符串。compile 把模式编译成对象，之后重复使用；模块级函数其实也会缓存编译结果，但在循环里显式编译更清晰，也更稳定。

flowchart LR
    A[模式字符串] --> B[re.compile 编译]
    B --> C[search / match / fullmatch]
    C --> D[Match 对象]
    D --> E[group / groups / groupdict]
    D --> F[sub 替换 或 finditer 遍历]

在需要多次使用同一模式的代码里，先 compile 再调用对象方法，既避免了重复编译，也让模式集中在一处便于维护。re 模块内部有编译缓存，但缓存有容量上限，模式一多就可能被挤掉，不能把它当成万能的性能方案。

前后查找：只定位，不消费

前后查找用来声明某个位置的左边或右边必须是什么，但本身不消耗字符，匹配结果里不会出现这部分文本。(?=...) 是正向前瞻，要求右侧匹配；(?!...) 是负向前瞻，要求右侧不匹配；(?<=...) 是正向后顾，要求左侧匹配；(?<!...) 是负向后顾，要求左侧不匹配。

前瞻常用于密码规则这类多重约束：一条模式里并列多个前瞻，每个前瞻只检查一个条件，最后再用 .{8,} 消费整段。后顾适合提取某个前缀之后的内容，比如只要金额数字、不要货币符号。这里有一个重要限制：Python 3.7 的后顾要求定长模式，(?<=¥) 可以，(?<=\w+) 不行，会直接抛出错误。如果确实需要可变长度的后顾，可以借助第三方库 regex，它在这一点上做了扩展；标准库范围内则要改写模式，把不定的部分放进捕获组再取出来。

负向断言同样实用：\d+(?!\s*元) 可以找出后面不跟“元”的数字。需要注意的是，前后查找只做断言，不移动匹配位置，也不消费字符，组合使用时要想清楚每个字符最终由谁匹配。

替换进阶：回调、引用与转义

re.sub(pattern, repl, string, count=0) 把匹配到的部分替换成 repl，repl 可以是字符串或函数。字符串里用 \1、\2 引用捕获组，用 \g<name> 引用命名组；引用后面紧跟数字时 \1 会有歧义，\g<1> 更安全。函数回调接收 Match 对象并返回字符串，适合根据匹配内容计算替换值的场景，比如给数字统一加一。

替换字符串里的反斜杠有特殊含义，字面反斜杠要写成 \\；不合法的转义（例如 \d）在 Python 3.7 会直接报错，而不是原样输出。构造模式与替换文本时优先用 raw string，需要按字面匹配用户输入时用 re.escape。

编译与修饰符：把模式当成对象

re.compile 返回模式对象，方法有 search、match、fullmatch、findall、finditer、sub、split，参数与模块级函数一致。显式编译让模式只解析一次，还能附加修饰符、起名并在函数间传递。

修饰符用 flags 传入，多个用按位或组合。re.IGNORECASE 忽略大小写；re.MULTILINE 让 ^ 和 $ 匹配每一行的首尾；re.DOTALL 让 . 匹配换行符；re.VERBOSE 允许换行、缩进和注释，适合排版复杂模式。VERBOSE 下空白会被忽略，匹配字面空格要写 \ 或 [ ]，字符类内部的空白仍然保留。

修饰符也可以写在模式里，例如 (?i) 放在开头会作用于整个模式，(?i:...) 只作用于一个分组；后者在 3.7 可用。把修饰符和模式放在一起，读代码时不必来回查找。

实战：日志、URL 与输入校验

日志解析是命名组的典型场景。Nginx 的 combined 格式字段多、分隔符固定，把模式写成 VERBOSE 形式，每个字段一行并加注释，比一条挤在一起的长模式好维护。

URL 提取的关键是定义 URL 到哪里结束。用 https?:// 开头，再用排除空白、引号和中文标点的字符类吞掉剩余部分，通常比完整校验 URL 语法的模式更实用；完整语法非常复杂，提取只需要像 URL 的一段连续字符。

输入校验要区分简单与严格：\d{11} 只保证 11 个数字，1[3-9]\d{9} 还约束了号段，但两者都管不了号码是否真实存在。日期同理，\d{4}-\d{2}-\d{2} 只校验形状，2018-02-30 也能通过，真正的合法性要交给 datetime.strptime。正则负责形式，业务语义负责内容。

日期校验同样分两步：正则只检查形状，日历合法性交给标准库。

校验函数统一用 fullmatch 并返回布尔值，调用方不必了解正则细节。日期函数同样先用正则检查形状，再交给标准库判断闰年与月份天数，手写月份规则既繁琐又容易出错。号段规则会随时间调整，抽成常量或配置比散落各处更稳妥。

常见坑：从能跑到可靠

反斜杠与 raw string。'\b' 在普通字符串里是退格符，'\d' 会触发未知转义警告，模式应一律写成 r'...'，可以避免多数看起来对却匹配不上的问题。

match 与 fullmatch 混淆。re.match(r'\d+', '123abc') 会成功，因为只要求开头匹配；校验必须用 fullmatch，或者给模式加上 \Z。

findall 有分组时返回元组。模式里只要出现捕获组，返回结构就变了，提取完整匹配时改用非捕获组或 finditer。

灾难性回溯。嵌套量词、可选分支和超长输入相遇时，匹配时间会爆炸；简化模式、限定输入长度、用字符类替代 .，必要时把可疑匹配放进独立进程。

Unicode 与 \w。Python 3 的 str 模式下，\w 默认包含中文等 Unicode 字母，\d 也能匹配全角数字，做 ASCII 范围校验时要写 [0-9] 或加 re.ASCII。

$ 与结尾换行。$ 默认匹配字符串末尾或末尾换行之前，严格匹配结尾用 \Z。

小结

正则的核心不是背语法，而是想清楚三件事：匹配边界在哪里、哪些部分需要捕获、失败时引擎如何回溯。先用字符类和锚点收紧范围，再用分组与命名组表达结构，最后才考虑前后查找这类技巧。把模式写成 raw string 并显式编译，把校验与提取分开，能避开大多数坑。真正复杂的结构交给解析器，正则只做它擅长的那层文本匹配。建议为每个模式准备一组正例与反例，覆盖空串、超长输入和边界字符，可靠性靠例子而不是直觉。
