Go 1.11 模块管理 Modules

本文属于《Go 语言与工程》第 27/78 篇
上一篇系列目录下一篇

Go 1.11 于 2018 年 8 月发布，把 modules 带进了官方工具链，但直到年底它仍是需要手动打开的新能力。本文从 GOPATH 的老问题讲起，说明模块、go.mod 与 go.sum 各自解决什么，再走一遍初始化、补依赖、整理的完整流程，最后讨论版本选择、vendor、私有仓库与迁移中的常见坑。读者应当已经能用 Go 写简单服务，但还没在团队项目里系统使用过 modules。

GOPATH 模式留下的三个问题

GOPATH 是 Go 早期的工作区约定：所有源码都放在 $GOPATH/src 下，导入路径与目录结构一一对应，example.com/hello 这个导入路径必须对应 src/example.com/hello 这个目录。编译器据此找到包，go get 也据此把远程仓库克隆到固定位置。这个设计简单直接，却把“代码放在哪里”和“依赖是什么版本”绑死在了同一套目录规则上。

第一个问题是位置。项目不能随便放在磁盘的任何地方，必须在 GOPATH 的 src 之下，否则导入就找不到；一台机器通常只有一个 GOPATH，多个项目共享同一份依赖副本，谁改了依赖目录，所有人都受影响。

第二个问题是版本。go get 默认取仓库默认分支的最新提交，代码里没有任何地方声明“我需要 v1.2.0”。今天构建成功，明天同事重新拉一遍依赖，拿到的可能是另一份代码；线上出问题时，也很难回答“当时用的到底是哪个版本”。

第三个问题是冲突。项目 A 依赖某库的 v1，项目 B 需要同库的 v2，而 src 下同一个导入路径只能存在一份代码。开发者只能手工切换、改导入路径，或者给项目各自准备一个 GOPATH，用环境变量隔离。项目一多，这种手工操作很快就不可靠。

vendor：把依赖复制进仓库

Go 1.5 引入 vendor 目录（当时还需要实验开关），Go 1.6 起默认启用：构建时优先使用项目内 vendor/ 下的包，而不是 GOPATH 里的副本。这样每个项目自带一份确定版本的依赖，构建可复现，离线也能编译。

代价也很明显。vendor 目录是完整的源码副本，仓库体积迅速膨胀，代码评审里混进大量第三方代码；升级依赖要靠工具去改目录，缺少一份人能读的依赖清单；多个库各自 vendor，出现嵌套时优先级规则容易让人困惑。vendor 解决了“用哪份代码”，却没有解决“如何声明和求解版本”。

dep 与 glide：过渡方案

社区先有 glide，用 glide.yaml 声明依赖、glide.lock 锁定版本；后来有 dep，用 Gopkg.toml 与 Gopkg.lock，dep ensure 负责拉取并写入 vendor。它们把版本约束和锁定文件带了进来，比裸 GOPATH 前进了一大步，但都不是官方工具链的一部分，命令、锁文件格式与解析规则各成一套，而且仍然和 vendor 目录绑定。2018 年中的多数项目正处在这个状态：能用，但大家都在等一个标准答案。

模块到底是什么

一组包，一个版本号

模块是一组一起发布、一起打版本号的包的集合，根目录放一个 go.mod。模块路径既是这个集合的身份标识，也是它内部包的导入前缀：模块 example.com/hello 下的 util 子目录，导入路径就是 example.com/hello/util。一个仓库通常对应一个模块，也可以在一个仓库里放多个模块、各自带 go.mod，但多数团队不会这么做。

包与模块的关系需要分清：包是编译单元，模块是版本与依赖的边界。go.mod 里的 require 只记录模块，不关心你具体导入了它下面的哪个包；同一个模块里的所有包共享同一个版本。

go.mod：声明意图

go.mod 是纯文本，常见内容如下：

module 一行声明模块路径，必须与别人导入你时写的路径一致，否则下游会报路径不匹配。require 列出依赖模块及其最低版本要求，带 // indirect 的表示当前模块没有直接导入它，只是被别的依赖带进来。语言版本等信息后来也会记录在 go.mod 中；replace 与 exclude 则是可选指令，后面单独讨论。

go.sum：完整性校验

go.sum 记录每个依赖模块在特定版本上的内容哈希，通常以 h1: 开头。下载模块时，工具链会重新计算哈希并与 go.sum 比对，不一致就拒绝构建。它防的不是“版本选错”，而是“同一版本的内容被悄悄替换”：仓库被改写、代理返回了别的内容、本地缓存损坏，都会在这里暴露。

因此 go.sum 应当提交进版本库，并且不要手工编辑。它也不是锁文件：真正决定用哪个版本的是 go.mod 里的要求与最小版本选择算法，go.sum 只负责证明“拿到的这份内容是对的”。

一次完整的模块化流程

下面用一个最小项目走一遍，观察每一步的文件变化。

初始化

执行后目录里多出 go.mod，内容只有一行 module 声明，既没有依赖，也没有 go.sum。模块路径建议使用你能控制的域名或仓库地址；随手写成 hello 之类的短名字，以后一旦发布，导入路径就很难改了。

构建时自动补依赖

第一次构建会发现当前模块缺少 example.com/greeter，于是解析导入路径、找到对应仓库、挑一个版本、下载到本地模块缓存（默认在 $GOPATH/pkg/mod），再把 require 写进 go.mod，把校验和写进 go.sum。这条路径在 1.11 里已经可用，但选中的往往是默认分支上的最新版，生产项目不应完全依赖它。

go test 的行为相同：测试文件里新导入的包也会被自动加入 go.mod。区别只在于它同时编译测试代码，因此有时会把只用于测试的依赖也带进来。

整理、查看与预下载

go mod tidy 是日常最常用的命令，它负责增删与整理：删掉代码里已经不再导入的 require，补上漏掉的依赖，给间接依赖补 // indirect 标记并整理格式。它不会把已有依赖升级到新版本。

go list -m all 输出的是“构建列表”，也就是按版本选择算法算出来的最终结果，不是 go.mod 里写了什么。排查“为什么用了个老版本”时，先看这份列表，再顺着依赖链找是谁提出了这个要求。

GO111MODULE：三个取值

Go 1.11 的 modules 并不是无条件生效的，而是由环境变量 GO111MODULE 控制，它有三个取值：

  • off：完全退回 GOPATH 模式，即使目录里有 go.mod 也忽略，构建仍然去 GOPATH 与 vendor 目录里找包。
  • on：任何目录都启用模块模式，项目放在 GOPATH 里面也一样，go.mod 成为依赖的唯一来源。
  • auto：默认值。当前目录在 GOPATH/src 之外、且能找到 go.mod 时启用；如果项目位于 GOPATH/src 之内，即使有 go.mod，仍然按 GOPATH 模式工作。

最容易出问题的是 auto 在 GOPATH 内的判断。同一个项目，放在 $GOPATH/src/example.com/hello 下运行 go build，走的是老路径，go.mod 形同虚设；把它挪到别处，或者在同一条命令前加上 GO111MODULE=on，行为立刻改变。这也是很多人第一次试用 modules 时觉得“命令没反应”的原因。

2018 年底，modules 在 1.11 里仍被官方定位为可以试用的新能力，工具链细节在后续版本还会调整。因此团队必须统一口径：CI 里显式设置 GO111MODULE=on，本地用 Makefile 或脚本固化，文档中写清楚；不要一半人用 on、一半人靠 auto，否则同一条构建命令在不同机器上可能走完全不同的依赖解析路径。可以用 go env GO111MODULE 查看当前生效的值，用 shell 的 export 设置它；这些设置只影响当前环境，不会写进 go.mod。

版本是怎么选出来的

语义化版本与导入路径

模块版本采用语义化版本，形如 v1.2.3，分别表示主版本、次版本与修订号。次版本与修订号的变化应当保持兼容，主版本变化则意味着不兼容。为了允许不兼容的两个大版本共存，Go 要求主版本大于等于 2 时在模块路径上带后缀，例如 example.com/lib/v2。这样 v1 与 v2 的导入路径不同，可以同时出现在一个构建里，而不是像 GOPATH 时代那样互相覆盖。

在模块模式下，可以显式指定版本：go get example.com/lib@v1.2.0 会把要求写进 go.mod 并立即下载。省略版本时，工具链通常选择默认分支上的最新版本，这也是早期自动补依赖不太可控的原因。

最小版本选择

modules 选版本用的算法叫最小版本选择（Minimal Version Selection，MVS）。它的规则可以这样理解：每个 go.mod 只声明“我至少需要哪个版本”，构建时把所有模块提出的最低要求收集起来，对每个模块取这些要求中最高的那一个。

举个例子：主模块要求 example.com/lib v1.2.0，而 lib 自己要求 example.com/helper v1.1.0；主模块的另一个依赖要求 helper v1.3.0。最终构建列表里 helper 是 v1.3.0，因为它是所有最低要求里最高的，而 lib 在 v1.1.0 之上本来就能工作。

这个算法的好处是结果确定、可复现，而且不会因为你没改代码就悄悄升级。代价是升级必须显式进行：go get example.com/helper@v1.4.0 会改写 go.mod 中的要求；go get -u 会连带升级一批依赖，用之前要看清 diff。反过来，想降级也不能只把 require 里的版本改小，因为其他模块的最低要求还在，最终仍会选较高的那个，只能靠 replace 或等上游放宽要求。

require、replace 与 exclude

require 是最常用的指令，go mod tidy 会自动维护它。带 // indirect 的行表示该模块没有被当前代码直接导入，只是依赖的依赖；保留这些行是为了让构建列表完整、可审计，不要手工删掉。

replace 用来替换某个模块的来源，右侧可以是本地目录，也可以是另一个模块版本：

本地调试时把依赖指向相邻的源码目录，改完立刻生效，不必反复提交打标签。修复第三方库的 bug 时，可以 fork 一份、保留原来的模块路径，然后 replace example.com/greeter => example.com/fork/greeter v1.2.1。这里有一个重要限制：replace 只在主模块生效，你发布的库即使写了 replace，下游构建时也会忽略。所以不要指望用它帮使用者修依赖，正确做法是推动上游合并。

exclude 用来排除某个具体版本，MVS 会因此改选其他版本。它很少使用，通常只用于某个版本已被确认有严重问题、又暂时无法升级的场景。排除之后选中的版本可能出乎意料，而且同样只在主模块生效，排查依赖问题时容易造成困惑，能不用就不用。

vendor 与私有依赖

go mod vendor 会把构建列表中的依赖复制到项目内的 vendor/，并生成 vendor/modules.txt 记录模块与包的对应关系。默认构建仍然读模块缓存，要显式加 -mod=vendor 才会使用它，可以在 CI 里用 GOFLAGS=-mod=vendor 固化。适合提交 vendor 的场景是内网或离线构建、依赖审计；库项目则不适合，vendor 不会被下游使用，只会让仓库变胖。

Go 1.11 的 GOPROXY 默认是 direct，也就是直接通过 git 等版本控制工具拉取。可以把它指向自建的模块代理，代理需要实现 /@v/list、.info、.mod、.zip 几个接口，适合在内网做缓存与统一出口。私有仓库的认证不在 Go 工具链里，而是交给 git：配好 SSH key、使用 credential helper，或者把 https 地址重写为 SSH：

CI 上建议使用只读的部署密钥，不要把个人凭据放进流水线。

从 GOPATH 或 dep 迁移

迁移按下面的顺序做，风险最小：

  1. 在分支上确认旧构建可用，避免迁移和业务改动混在一起。
  2. 在项目根执行 go mod init，参数用原来的导入前缀。
  3. 跑 go mod tidy，把新增的 require 与 Gopkg.lock 逐项比对，关键依赖用 go get 固定回原版本。
  4. go build ./... 与 go test ./... 通过后，再跑一次 tidy 确认结果稳定。
  5. CI 改设 GO111MODULE=on，增加 go mod download，缓存 $GOPATH/pkg/mod，并在构建后检查 go.mod 与 go.sum 没有未提交改动。
  6. 删除 Gopkg 文件；vendor 要么删掉，要么保留并统一加 -mod=vendor。

常见报错有三类。module declares its path as ... but was required as ... 说明模块路径与导入路径不一致；checksum mismatch 说明 go.sum 与下载内容不符，清掉 pkg/mod 下对应目录重新下载即可，不要删 go.sum；cannot find module 或 unrecognized import path 多半是网络、代理、私有库凭据或路径大小写的问题。

几个容易踩的坑

go.mod 里的模块路径与代码中的导入路径不一致，本地能编过，发布后下游全部失败。删掉 go.sum 虽然能重新生成，但等于放弃完整性校验，CI 里 go.sum 的变动应当当作依赖变更来审。以为 tidy 会升级依赖是另一个误解，它只增删、不改已有版本。在 GOPATH 内依赖 auto，会误以为 modules 已经生效。路径大小写不一致的问题，也常常等到 Linux 构建机上才暴露。

小结

Go 1.11 的 modules 把版本约束、依赖清单与内容校验带进了官方工具链：go.mod 声明意图，go.sum 保证内容，MVS 负责算出确定的构建列表。它替代的是 GOPATH 的固定目录与 vendor 的源码副本，而不只是换了一个下载器。迁移时先在 CI 试点，统一 GO111MODULE 口径，锁定关键版本，再逐步删掉旧工具。对 2018 年底的团队来说，modules 已经可用，但仍值得留一条回退路径。
