Go 实现定时任务调度

本文属于《Go 语言与工程》第 57/78 篇
上一篇系列目录下一篇

定时任务看起来只是“每隔一段时间跑一个函数”，落地时却要回答选型、并发、重复执行、补偿与优雅退出。本文不重讲 time.Timer 与 time.Ticker 的语法，而是讲调度层怎么组织：先用标准库写一个最小调度器，再用 cron 表达式表达日历语义，最后处理多副本与可观测性。

一、先选型：三种调度粒度

第一类是固定间隔，例如每 30 秒刷新热点缓存、每 5 分钟上报心跳。它只关心“两次执行隔多久”，time.Ticker 就够。语义按启动时刻起算，进程 10:03:17 启动，下一次就是 10:03:47，不对齐整分。

第二类是日历时间点，例如每天凌晨 3 点对账、每周一 9 点发周报。用 Ticker 硬凑要自己处理跨天、跨月与闰年，代码很快难以阅读，应交给 cron 表达式。

第三类是集群内唯一执行。三个副本都注册了“每天 3 点对账”，没有额外机制就会对账三次，轻则重复写日志，重则重复扣款，问题于是变成“怎么选出唯一执行者”。

需求 推荐方案 主要风险
固定间隔、单实例 time.Ticker 长任务拖慢节奏
日历时间点、单实例 cron 表达式 时区与字段写错
多副本、只能跑一次 调度 + 分布式锁 锁过期、重复执行

判断标准很简单：这个任务重复执行一次会不会产生业务副作用？如果会，无论当前几个副本，都应按“将来会多副本”设计。

二、用标准库手写一个最小调度器

只要职责拆得清楚，一两百行就能写出一个够用的版本：任务描述、注册表、驱动循环、执行与收尾。

2.1 任务结构与注册表

任务至少需要名字、间隔、执行函数。名字不是装饰，它是日志、指标和锁的 key。再补上超时，避免某个任务卡死拖住整个循环。

两个设计是刻意的。注册表用 sync.RWMutex，因为注册集中在启动阶段、读取贯穿运行期；重名直接报错，是让“两个模块起了同名任务”在启动时暴露。任务函数带 context.Context，是后面做超时与取消的入口，事后再加会牵动所有调用方。

2.2 用 Ticker 驱动，一个任务一条循环

驱动可以共用一个 Ticker，也可以每任务一个。共用看似省资源，实则把所有任务绑到同一节拍，间隔只能取公倍数，一个任务慢下来还会牵连其他任务。一个任务一条 goroutine、一个 Ticker 更简单，任务之间天然并发。

time.Ticker 的通道容量是 1，接收方忙时新 tick 会被合并丢弃。这个细节决定了同一任务不会重叠：一次执行花了 90 秒而间隔 60 秒，下一次 tick 只会让循环立刻再跑一遍，而不是积压出两条并发执行。代价是实际周期变成“执行时间 + 间隔”。若要求到点就起、不管上一轮是否跑完，才需把 runOnce 放进 goroutine，并用缓冲为 1 的信号量限流。

2.3 panic 隔离与执行超时

定时任务最怕的不是报错，而是 panic。一次 nil map 写入或数组越界就会让进程退出；三个副本同时触发同一个 bug，服务会在同一秒全部倒下。因此每个任务都要有自己的 recover。

recover 只对同一个 goroutine 内的 panic 有效，任务里再 go 出去的协程崩了，进程照样退出。

超时的边界要说清楚：context 只传递“该停了”的信号，任务必须自己检查 ctx.Done()，或把 ctx 传给下游的 HTTP、数据库调用，超时才会生效；纯 CPU 死循环不会因为 WithTimeout 被杀掉。想让调用方无论如何拿回控制权，只能把 Fn 放进 goroutine 再 select，但那会留下无法回收的协程。更实际的做法是约定：任务的下游调用一律接受 ctx。

2.4 停止：等待在跑的任务收尾

关闭 stop 让所有循环退出，再等待 wg。sync.Once 包住 close，避免重复停止时对已关闭通道再 close。

因为 runOnce 在 loop 里同步调用，wg 天然覆盖正在执行的那一次，返回 true 就说明没有任务在跑。若改成异步执行，必须把每次执行也计入 WaitGroup。

三、引入 robfig/cron：把“每天几点”交给表达式

上一节的调度器只认间隔，遇到“每天凌晨 3 点”就无能为力。当时 Go 生态里最常用的是 robfig/cron，它把表达式解析、下次触发时间计算和任务表都封装好了。

用法只有三步：创建、注册、启动。

AddFunc 返回 error，是因为表达式可能在运行时才拼出来，语法错误必须当场上报，这比“启动后静默不执行”好排查。Start 是非阻塞的，内部为每个 entry 维护下一次触发时间。生产里我们更愿意把它只当作触发器，真正的执行仍走自己那层带超时、带 recover、带上报的 runOnce。

版本上，当时常见的是 v1 与 v2，构造都是 cron.New()，注册是 AddFunc(spec string, cmd func()) error，启动与停止是 Start()、Stop()，日常使用差别不大。之后的 v3 对构造与注册的签名做了不兼容调整，升级前需按当时的 changelog 核对，本文不展开细节。另外默认解析器认五个字段，写六字段的秒级表达式会直接报错，需要显式指定带秒的解析器。

3.1 五个字段与预设

标准表达式从左到右是“分、时、日、月、周”，用空格分隔：

位置 字段 取值范围 常用写法
1 分钟 0-59 */5 每 5 分钟
2 小时 0-23 3 凌晨 3 点
3 日 1-31 1 每月 1 号
4 月 1-12 * 每月
5 星期 0-6 1-5 周一到周五

30 2 * * 1 是每周一 2 点 30 分，0 */2 * * * 是每两小时整点，0 4 1 * * 是每月 1 号 4 点。

不想记字段位置就用预设：@yearly、@monthly、@weekly、@daily、@hourly 分别对应每年、每月、每周、每天、每小时的固定时刻，@every 1h30m 接受 Go 的 duration 写法，表示从启动时刻起算的间隔。预设可读性好，但掩盖了具体时刻，做容量规划时最好在注释里写明。

还有一个容易忽略的细节：它默认使用进程所在机器的本地时区。容器镜像通常把时区设成 UTC，于是“每天 3 点”在运维眼里成了北京时间 11 点。要么在镜像里装好时区数据并设置 TZ，要么显式使用带时区的调度器。

四、多副本：让同一个任务只跑一次

单机调度器在扩容那一刻就失效了。三个副本各跑一份 Ticker，各自在 3 点触发对账，数据库里就多出两倍流水。这不是调度器写得不好，而是“谁有资格执行”从未被回答。

4.1 重复执行从哪来

调度状态在内存里，每个进程都认为自己是唯一的。滚动发布时旧副本未退出、新副本已启动，两代进程会共存几分钟；重启还会让 last_run 消失。分布式调度的第一步不是加锁，而是承认三件事：副本数会变、进程会重启、任务可能执行到一半。

常见思路有三条。数据库唯一约束：建 job_lock 表，用主键冲突或 SELECT ... FOR UPDATE 抢占，依赖少、语义清晰，但长事务会拖住连接。Redis 租约：SET key value NX PX ttl，轻量，适合秒级到分钟级任务。选主：用 etcd、ZooKeeper 或 Consul 选出 leader，只有 leader 跑调度，适合任务多、需要统一视图的场景。

对中小规模服务，笔者更倾向 Redis 租约：实现短，过期机制能兜住进程崩溃。

4.2 Redis 租约：加锁、续期、防误删

NX 保证只有一个客户端写成功，PX 是毫秒级过期，Redis 2.6.12 之后就有，4.x 与 5.x 语义一致。value 不能随便填，它是本次持有者的唯一标识，通常用主机名、进程号加随机串拼成。

锁过期绕不开：任务跑 40 秒而 ttl 只有 30 秒，第二个副本在第 31 秒就能抢到锁，于是两个进程同时执行。办法是续期，起一个后台协程按 ttl 的三分之一去延长，并且续期与释放都要先校验 token，否则会把别人的锁续上或删掉。

释放时把 pexpire 换成 del，其余不变。用 Lua 是因为“读、比较、写”必须原子完成，两条独立命令中间可能被插入。脚本返回 0 说明锁已不属于自己，不能假装成功，应当记一条“锁已丢失”的告警。

即便续期，也无法完全避免“锁过期但任务没跑完”，GC 停顿与网络分区都可能让续期晚到。真正的边界不在锁，而在任务是否幂等：按日期分区、唯一索引、消息带幂等键。锁只降低重复概率。

五、错过执行与补偿

进程重启、机器故障、发布时间超预期，都会让某个时间点被跳过。要不要补取决于语义：清理临时文件错过了就等下一轮；账务对账必须补，否则当天数据缺口一直留着。

判断是否错过需要持久化的 last_run：一张 job_state 表记任务名、最后开始与结束时间、最后状态，启动时与当前时间比较，间隔超过一个周期就说明有缺席。

处理方式有三种。skip 最省事，把 last_run 推到当前时间，只记日志说明跳过几轮。catch up 按缺失的时间点逐个补跑，必须设上限，例如最多 24 次，否则停机三天后重启会瞬间打出上千次执行。第三种是只补最近一次，适合日报这类以最新状态为准的任务。

补偿必须幂等，因为“补跑”与“正常跑”可能同时发生。用业务日期做主键、状态位做乐观锁，比在调度层反复判断可靠。

六、优雅退出：先停入口，再等收尾

定时任务的退出比 HTTP 服务更容易被忽略，因为它没有“请求在处理”这种显式信号。容器收到 SIGTERM 后只给十几秒，若此时正在遍历十万行数据，强杀的结果就是写了一半。

顺序是三步：停止接收新触发、通知在跑的任务、设置最大等待时间。用 signal.Notify 接信号，用 context.WithCancel 传递“该收了”。

几个取舍值得说明。Stop 只关闭 tick 通道，不中断已在跑的任务，因为强行中断往往比跑完更危险；截止时间由 wait 控制，容器宽限期通常 30 秒，应用留 15 秒合理。任务函数要把 ctx 一路传下去，收到取消后主动返回，否则 Stop 只能干等。需要“做到哪记到哪”的任务，还应在退出前把进度刷进 job_state。

七、可观测性：别只打一行 log

调度出问题时，最没有信息量的一句话是“任务执行失败”。排查需要任务名、计划时间、实际开始时间、耗时、结果，以及这次是不是补跑。Result 就是为此设计的。

三个指标最值得关注：执行次数与失败次数，用来算失败率；执行耗时，用来发现越来越慢的任务；最后成功时间，用来发现根本没跑的任务。第三项尤其重要，进程活着、日志有输出、任务却没触发，只能靠“最后一次成功距今多久”发现。

告警要分级：单次失败只记日志，连续三次失败或超过两个周期没有成功才值得叫人，否则告警一定被忽略。

八、几个真实会踩的坑

第一，任务里随手 go 协程。外层有 recover，内层没有，panic 照样让进程退出；更常见的是内层比任务活得久，调度器记了“成功”，实际工作还在后台。任务函数应同步返回，要并发就在内部用 WaitGroup 收敛。

第二，cron 表达式的时区。开发机是东八区，容器是 UTC，同一行表达式相差八小时。上线前用固定时区测一次“下次触发时间”，比事后对日志便宜。

第三，长任务重叠。Ticker 天然不重叠，cron 会：上一轮没跑完，下一轮到点照样触发。在任务入口放一把进程内互斥锁，抢不到就记一条“跳过本轮”，比堆包装器稳妥。

第四，锁过期但任务没完成。续期只能降低概率，兜底仍然是幂等写与唯一约束。

第五，容器重启导致内存态调度丢失。Ticker 的相位、last_run、互斥标记全在内存，重启即清零。要补跑的任务，状态必须落库。

小结

定时任务的难点不在“定时”，而在调度层要承担的责任：选对粒度、隔离失败、控制并发、避免重复、补偿缺席、优雅收尾。单机场景用一任务一 Ticker，加 context 超时和每任务 recover 就够用；日历语义交给 robfig/cron，执行逻辑留在自己手里才能统一超时与上报；多副本先想清楚重复执行有没有副作用，再用租约或选主收口，并把幂等当作最后防线。
