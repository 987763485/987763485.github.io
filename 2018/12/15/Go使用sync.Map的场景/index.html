Go 使用 sync.Map 的场景

本文属于《Go 语言与工程》第 45/78 篇
上一篇系列目录下一篇

map 是 Go 里最常用的容器之一，但它在并发写入时会直接让进程崩溃，而不是返回一个错误。标准库从 Go 1.9 起提供了 sync.Map，社区里于是出现两种极端：有人把它当成万能并发 map，有人则完全不碰。本文从普通 map 的并发限制讲起，逐个说明 sync.Map 的方法语义，再结合读写比例给出选型建议和几个常见误用。读完之后，你应该能判断自己的场景该用 sync.Map，还是老老实实写一个 RWMutex 加 map。

为什么普通 map 不能并发写

Go 的 map 在语言层面没有对并发写做任何保护。多个 goroutine 同时对同一个 map 赋值，运行时一旦检测到，就会抛出 fatal error 并终止整个进程：

有人会问：既然是“检测到才报”，是不是概率很低、可以赌？不能。检查发生在写入路径上，两个写者一旦交错，进程就会退出；而在退出之前，其他 goroutine 可能已经读到了不一致的中间状态。这类问题往往在压测或线上高并发时才出现，本地单线程测试完全看不出来。开发阶段可以用 go run -race 或 go test -race 提前暴露数据竞争，但 -race 只能报告“发生过”的竞争，不能替代正确的同步。

并发读也一样：一个 goroutine 在读、另一个在写，会触发 concurrent map read and map write。解决思路只有两条：一把锁保护所有访问，或者换一个为并发设计的数据结构。前者是 RWMutex 加 map，后者就是 sync.Map。需要强调的是，sync.Map 不是“更快的 map”，它是针对特定访问模式做的专用结构，用错场景可能比加锁还慢。

sync.Map 的 API 与返回值

sync.Map 自 Go 1.9 进入标准库，零值即可使用，不需要 make，也不能在第一次使用之后再复制。它的键和值都是 interface{}，Go 1.11 没有泛型，所以取出来必须自己做类型断言。

它一共只有五个方法，下面逐个说明。

Store 与 Load

Store(key, value interface{}) 没有返回值：键存在就覆盖，不存在就插入。Load(key) 返回 (value interface{}, ok bool)，ok 为 false 表示键不存在；如果存进去的值本身就是 nil，Load 会返回 nil, true，所以判断存在性一定要看 ok，不能看值是否为 nil。

LoadOrStore

LoadOrStore(key, value interface{}) 返回 (actual interface{}, loaded bool)。键已存在时不覆盖，返回现有的值和 true；键不存在时存入传入的值，返回该值和 false。它是“要么读、要么写”的一次原子操作，后面的去重和一次性初始化都靠它。

注意第二个参数在调用时就已经求值了。如果构造这个值很贵，而绝大多数情况键都存在，那么每次调用都会白构造一次，这一点后面还会提到。

Delete 与取出后删除

Delete(key interface{}) 没有返回值，键不存在时什么也不做，不报错。Go 1.11 的 sync.Map 没有 LoadAndDelete。这个方法要解决的问题是“取出旧值并删除”，语义上相当于一次 Load 加一次 Delete，返回旧值和是否存在；1.11 里只能分两步做，中间其他 goroutine 可以插进来，既不是原子的，也可能让两个消费者拿到同一个值。如果业务要求每个任务只被处理一次，不要指望这个组合，要么在值里加状态并用锁保护，要么直接用 RWMutex 加 map。

Range

Range(f func(key, value interface{}) bool) 遍历当前能看到的键值对，f 返回 false 时提前结束。遍历顺序不保证，和普通 map 一样，每次都可能不同。

把五个方法放在一起看，会发现它刻意没有提供 Len、没有提供原子自增、也没有提供“比较后再写”。这不是遗漏，而是它的设计目标决定的：它只服务于“读多写少、键集合相对稳定”的访问模式，其他能力一概不承诺。

什么场景适合 sync.Map

官方文档的描述很克制：当多个 goroutine 的读写分布在互不相交的键上时，sync.Map 有优势。拆开看是三个条件。

第一，读多写少。缓存、配置、节点列表、路由表，都是写一次或偶尔更新，之后被大量读取。第二，键集合相对稳定，新增不多，删除更少。第三，不同 goroutine 各自负责不同的键，比如每个连接维护自己的状态、按用户 ID 分片处理，连写操作都很少撞在一起。

一个贴近业务的例子是网关里的路由表：配置中心推送新版本时整体写入几十个键，之后每个请求都要按路径查一次；键的数量和名字都稳定，读远多于写，正好是 sync.Map 的主场。判断标准可以简化成一句：写操作是否频繁，并且集中在同一批键上；是，就不适合。

为什么它快？大致思路是空间换时间：内部维护两份视图，一份是只读的 read，读取时用原子操作取，基本不需要互斥；另一份 dirty 是普通 map 加一把锁，承接新键的写入。读命中 read 时几乎没有竞争；读不命中会去 dirty 找并累计 miss，累计到阈值就把 dirty 提升为新的 read，旧 read 丢弃。代价是同一批键可能短时间存在两份，删除的键也要等提升时才真正清理，内存占用高于普通 map。这里不展开源码，记住结论即可：读路径便宜，写路径和键的增删都要付代价。

哪些场景不要用 sync.Map

反面清单比正面清单更有用。遇到下面几种需求，直接选 RWMutex 加 map，通常更简单也更稳妥。

写多的场景。写入新键要拿锁、更新 dirty，键的增删还会触发视图重建；写操作占到一半时，sync.Map 的优势基本消失。并发写同一个 key 时，多个写者又会在同一个 entry 上反复竞争，未必比一把锁便宜。

需要原子复合操作的场景。计数、先检查再更新、从池里取一个元素并标记为占用，都需要读和写作为一个整体完成。Go 1.11 的 sync.Map 没有比较并交换，Load 之后 Store 中间一定存在窗口。这类需求要么用 sync/atomic，要么用 Mutex 把整个复合操作包起来。计数器尤其不要放进 map：一个 int64 加 atomic.AddInt64 就够了。

需要长度或一致快照的场景。sync.Map 没有 Len，用 Range 数一遍是 O(n)，数出来的还只是遍历过程中的近似值。要上报“当前在线连接数”，应该单独维护一个原子计数，而不是遍历 map。

需要边遍历边修改的场景。Range 期间增删键的行为没有强保证，依赖它做清理或迁移很容易漏数据。

键频繁增删的场景。带过期时间的会话表、短链接缓存，每分钟大量键生灭，被删除的条目会拖到视图提升时才清理，内存容易涨。sync.Map 不负责淘汰，也不负责过期，这两件事都得自己在外层做。

建议至少做三组变量：键规模取 1000 与 10 万各跑一次，值分别用小整数和结构体指针，再对比有无删除；每组都在 -cpu 1 和 -cpu 8 下看趋势。如果 1:1 的负载下 RWMutex 已经胜出，就不必再考虑 sync.Map。单次运行会受 GC 和调度影响，可以加 -benchtime=3s 并重复三次取中位数。另外，不要带 -race 跑 benchmark，插桩后的数字不能用来比较。

Range 的边界

Range 最容易误解的一点是：它不提供一致快照。遍历过程中其他 goroutine 的写入，可能被看到，也可能看不到；遍历时新增的键，不保证会被访问；遍历时删除的键，也不保证不会被访问。文档的措辞是，并发写入或删除时，Range 可能反映该键在遍历期间的任意一个映射。这些行为都合法，所以不能拿它做精确统计。

因此，f 里不要做耗时操作，也不要假设自己看到的是某一时刻的完整数据。想做“清理过期键”这类近似工作，可以在 Range 里判断并 Delete，漏掉几个下一轮再处理即可；想得到准确的总数或一致的配置快照，应该用原子计数或在锁内复制一份。确实需要遍历期间看到稳定数据，就先在锁内把普通 map 复制成切片，再处理这份副本。f 返回 false 会停止遍历，适合“找到第一个满足条件的键就退出”的场景。

第二，用 Load 加 Store 做“检查再更新”。两个 goroutine 同时 Load 到旧值，各自加一后写回，结果只加了一次：

这和普通 map 上的 count++ 没有本质区别，都是数据竞争。能表达成“没有就写入”的，用 LoadOrStore；需要基于旧值计算新值，只能在外面加锁或用 atomic。反过来说，LoadOrStore 也不是计数器：它只保证某个键被写入一次，不会把新旧值相加。

第三，存了指针就以为字段也安全了。sync.Map 保护的只是“键到指针”这一层映射，指针指向的结构体字段仍然是共享内存。一个 goroutine 改字段、另一个读，照样是数据竞争，go test -race 一样会报。不可变对象可以放心共享；可变对象要么在锁内修改，要么整体替换指针，先构造新对象再 Store。

第四，复制包含 sync.Map 的结构体。sync.Map 内部有状态，第一次使用后不能再复制，复制出来的副本与原值各自独立，行为难以预料。go vet 的 copylocks 检查会提示：

结构体一律用指针传递，不要为了省一次分配按值返回。

第五，把它当无界缓存用，忽视内存。没有 TTL、没有容量上限、删除的键还可能滞留，长时间运行的服务很容易被它拖垮。键的生命周期由谁管理，应该在选型时就写清楚。

小结

普通 map 的并发写不是“结果可能不对”，而是 fatal error，recover 接不住，所以同步是必须的。sync.Map 用 read 与 dirty 两份视图换来了便宜的读路径，适合读多写少、键集合稳定、各 goroutine 负责不相交键的场景；写多、需要原子复合操作、需要长度或一致快照时，RWMutex 加 map 更合适。LoadOrStore 适合一次性初始化和去重，Range 则不保证一致快照。选型不要背结论，用贴近自己业务的 benchmark 测一遍；锁竞争的原理与优化手段，留到《Go 锁竞争与性能优化》里展开。
