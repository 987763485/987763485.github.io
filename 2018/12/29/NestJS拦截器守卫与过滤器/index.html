NestJS 拦截器、守卫与过滤器

本文属于《TypeScript 学习路线》第 66/74 篇
上一篇系列目录下一篇

上一篇我们搭起了 NestJS 5 的骨架：模块划分边界，控制器翻译请求，服务承载业务，管道守住参数入口。但真正让一个服务“像个服务”的，是请求进入方法之前的那道判断、方法执行前后那层包裹，以及出错之后那份统一的响应。本文沿着一次请求的生命周期，讲清楚守卫、拦截器与异常过滤器各自解决什么问题、按什么顺序执行、边界在哪里，最后用一个 JWT 加角色的组合示例把它们串起来。读者应当已经会写控制器与服务，读完后能为自己的接口补上鉴权、统一响应与错误处理。

请求在框架里走了一条什么路

先看全景。一次 HTTP 请求进入 NestJS 之后，并不是直接落到控制器方法上，而是依次穿过中间件、守卫、拦截器、管道，才抵达方法体；方法返回后，又要反向穿过拦截器的后段，最终被序列化成响应。任何一层抛出异常，控制权立刻转交给异常过滤器。

flowchart TD
  A[HTTP 请求] --> B[中间件 Middleware]
  B --> C[守卫 Guard]
  C --> D[拦截器 Interceptor 前段]
  D --> E[管道 Pipe]
  E --> F[控制器方法]
  F --> G[服务 Service]
  G --> H[拦截器 Interceptor 后段]
  H --> I[响应序列化]
  C -. 拒绝 .-> X[异常过滤器]
  D -. 抛错 .-> X
  E -. 校验失败 .-> X
  F -. 抛错 .-> X
  X --> J[统一错误响应]

这七层的职责边界可以用一句话概括：中间件处理与路由无关的横切事务，比如日志、CORS、请求体解析；守卫只回答“这个请求允不允许进来”；拦截器在方法调用前后包裹一段逻辑，能改写返回值；管道只负责把参数转成期望的类型并校验；控制器负责翻译 HTTP 语义；服务负责业务；异常过滤器只处理失败路径，把各种异常翻译成响应。

它们能拿到的东西也不一样。中间件拿到的是原生的 req 与 res，它不知道最终会命中哪个控制器，也不知道方法上挂了什么装饰器，所以做不了细粒度鉴权。守卫拿到 ExecutionContext，能知道目标类与目标方法，却拿不到方法的返回值，因为它执行时方法还没被调用。拦截器同样拿到 ExecutionContext，还额外拿到一个代表“后续调用”的句柄，因此是唯一能同时看到入参与返回值的一层。过滤器拿到的是异常对象与 ArgumentsHost，它只关心怎么把错误说清楚。

顺序上有两个容易忽略的细节。第一，同一类型的组件如果注册了多次，执行顺序是全局、控制器、方法；拦截器的前段按这个顺序进入，后段则完全反过来，像洋葱一样层层退出，所以全局拦截器包装的是最外层的响应。第二，异常过滤器不在正常链路上，它只在出错时介入；也正因为它站在最外层，守卫、拦截器、管道、控制器抛出的异常最终都会落到它手里。至于管道，它紧挨着方法体，是参数进入业务代码前的最后一道加工，具体写法上一篇已经讲过，这里只关心它的位置：守卫在它之前，拦截器在它两侧。

还有一层在 Nest 的异常体系之外，就是中间件。Express 适配器里的中间件抛错时，请求还没进入 Nest 的调用上下文，异常过滤器接不住，需要靠 Express 的错误处理中间件兜底。这也是为什么鉴权不要写在中间件里：写在那里，你既拿不到方法上的元数据，也享受不到统一的错误格式。

守卫：在方法执行前给出是或否

守卫是一个实现了 CanActivate 接口的类，只有一个方法 canActivate，返回值可以是布尔值，也可以是 Promise 或 Observable。返回 true 放行，返回 false 时框架直接抛出 ForbiddenException，客户端收到 403；如果判断依据是“没登录”而不是“没权限”，更合适的做法是主动抛 UnauthorizedException，让状态码变成 401。

canActivate 的参数是 ExecutionContext，它是 ArgumentsHost 的扩展，除了能切换到底层的 HTTP 请求与响应，还能通过 getHandler 拿到即将执行的方法引用，通过 getClass 拿到所属控制器的类。这两个引用正是元数据的入口：装饰器把信息写在方法或类上，守卫在运行时按引用读出来。

守卫里注入 Reflector，先读方法上的角色，没有再读控制器类上的，这样类级别的默认角色可以被方法级别覆盖。读取失败说明这个接口没有声明角色要求，直接放行；声明了而当前用户不在列表里，就拒绝。

使用时把装饰器挂在方法或控制器上，再用 @UseGuards 把守卫挂上去。挂在控制器上对整组路由生效，挂在方法上只对该方法生效，两处都挂时两边都会执行，不会互相覆盖。

基于角色的判断只看身份标签，遇到“只能改自己的订单”这类需求就不够了，这时要用基于资源的守卫。它在 canActivate 里先把目标资源查出来，比较归属，再把资源挂到 request 上供后续使用。这样做的好处是控制器里不必再查一次，坏处是守卫开始依赖数据访问，查询失败或资源不存在都要在这里给出明确结果，不能默默放行。

注册方式有三种。方法级与控制器级用 @UseGuards，适合局部接口；全局守卫用 app.useGlobalGuards 在入口注册，适合所有接口都要过的登录校验；如果守卫本身需要注入服务，比如上面查订单的写法，就不要用 useGlobalGuards，而是把它作为 APP_GUARD 注册到某个模块的 providers 里，让依赖注入容器来创建实例，否则构造函数里的依赖会是 undefined。

拦截器：把方法调用包起来

拦截器实现 NestInterceptor 接口，只有一个方法 intercept，参数是 ExecutionContext 与 CallHandler，返回值必须是 Observable。next 这个句柄代表“剩下的链路”，调用 next.handle() 才会真正执行管道、控制器与服务；不调用，方法体就永远不会跑。正因为拿到的是一个数据流，我们才能在它上面挂 RxJS 操作符：map 改写返回值，tap 做不计入结果的副作用，catchError 处理异常，timeout 限制总时长。

有一个约束必须刻在脑子里：next.handle() 只调用一次。它不是普通函数调用，而是创建一条冷数据流的动作，每次订阅都会重新执行一遍处理器。调用两次不会得到“前后各一份”，只会让控制器方法执行两遍，写接口会重复落库；如果确实需要多处订阅，应该用 share 之类的操作符复用同一条流，而不是重复调用。

最常见的用途是统一响应。客户端通常希望拿到 { code, data, message } 这样的信封，而不是直接把业务对象摊在顶层，于是拦截器在 map 里包一层。这里有一个边界要提前想清楚：不是所有返回值都适合包装，文件流、已经由 @Res 手动写出的响应都要跳过，前者会把二进制塞进 JSON，后者会出现 headers already sent。实际项目里一般给这类接口加一个跳过标记，在拦截器里读元数据决定是否包装。

耗时统计用 tap，位置在 next.handle() 之后。注意 Observable 是惰性的，写在前面的代码在请求进入时执行，写在 tap 里的代码在响应回来时执行，所以计时的起点要取在调用 handle 之前，因为 handle 只是把数据流搭好，真正的执行发生在订阅之后。

缓存也常放在这一层：进入时先查内存或 Redis，命中就直接返回 of(缓存值)，用一条现成的流短路后续链路。短路意味着管道与控制器都不会执行，所以缓存的键必须把路径参数与查询串都算进去，否则会给不同用户返回同一份数据。未命中时正常调用 next.handle()，并在 tap 里写入缓存，注意只缓存成功的结果。

超时用 timeout 操作符，超时会抛出 TimeoutError，再用 catchError 转成合适的 HTTP 异常。要清楚它只是让这条流以错误结束，并不会真的取消下游正在跑的数据库查询，所以数据库与外部 HTTP 客户端各自仍要设超时，两者是配合关系而不是替代关系。

拦截器可以挂在方法、控制器上，也可以全局注册。全局注册同样有两条路：入口里 app.useGlobalInterceptors(new TransformInterceptor())，或者作为 APP_INTERCEPTOR 写进模块的 providers。后者能参与依赖注入，拦截器里想用 Logger、配置服务时选它。

异常过滤器：定义错误的形状

框架自带的异常层会把 HttpException 转成 { statusCode, message, error }，把其他错误一律当成 500 并打日志。这个默认行为够用，但业务上通常还需要一个稳定的业务码、一个用于排查的请求标识，以及一套不透出内部细节的措辞，这就需要自定义过滤器。

过滤器是一个带 @Catch 装饰器的类，实现 ExceptionFilter 接口的 catch 方法。@Catch 不带参数表示捕获一切；也可以写成 @Catch(HttpException)，只处理某一类。第二个参数 ArgumentsHost 是宿主抽象，HTTP 场景下用 switchToHttp 取出 request 与 response，然后自己决定状态码与响应体。

真正的价值在于把领域异常翻译成 HTTP 语义。服务层不应该知道 409 还是 422，它只抛“余额不足”“订单状态不允许取消”这类领域错误，过滤器用 instanceof 逐一映射。这样换协议、加业务码、做国际化时只改一处，领域代码保持干净。映射表要显式写出默认分支：不认识的异常一律 500 且隐藏细节，绝不能把数据库报错原文返回给客户端，那是信息泄露。

注册方式同样两种。app.useGlobalFilters(new AllExceptionsFilter()) 最直接，但实例是在依赖注入容器之外 new 出来的，构造器里注入的 Logger、配置服务都拿不到；要注入就得把过滤器写进某个模块的 providers，并用 APP_FILTER 作为令牌。全局注册后所有控制器都受它保护，包括守卫与管道抛出的异常。

写过滤器时有几条硬约束。第一，catch 里不能再抛异常，否则会落到框架的默认处理，响应格式反而不可控。第二，响应只能写一次，如果控制器用了 @Res 已经发过响应，过滤器再写就会报 headers already sent。第三，过滤器接不住中间件里的错误，那部分要靠 Express 的错误处理中间件。第四，错误响应不经过拦截器的 map，所以成功与失败的格式要由拦截器与过滤器各自保证一致，最好共用同一套字段定义。

执行顺序与常见误区

第一，守卫里拿不到拦截器加工后的数据。守卫在拦截器之前执行，此时参数还没经过管道，方法的返回值更不存在，把判断建立在被包装过的响应上必然失败。第二，拦截器的 catchError 如果不重新抛出，而是返回一个兜底值，异常就被吞掉了，过滤器永远不会触发，客户端反而收到 200。第三，异步守卫忘记 return 或 await。canActivate 返回 Promise 对象时，对象本身是真值，框架会直接放行，必须把 Promise 交出去。

第四，全局注册有顺序。多个全局守卫按注册先后执行，APP_GUARD 的次序则取决于 providers 的书写顺序；鉴权守卫要排在角色守卫前面，否则角色守卫读到的是空用户。第五，@UseGuards 与全局守卫是叠加关系，不是覆盖关系。方法上声明了守卫，全局守卫照样执行；想让个别接口跳过全局守卫，只能在守卫里读元数据做判断，不能指望局部声明顶掉全局。第六，拦截器在管道之前，看到的请求体是未经校验与转换的原始值，不要在这里假设 DTO 已经成型。

组合示例：一个订单模块

把四件套装进一个订单模块。JwtAuthGuard 解析并校验令牌，把用户挂到 request 上；RolesGuard 依赖这个用户，所以顺序不能反。响应包装与异常处理用 APP_INTERCEPTOR 与 APP_FILTER 全局注册，控制器里只剩下角色声明与业务调用。

小结

守卫管准入，拦截器管包裹，过滤器管失败，三者各占生命周期的一段，谁也替代不了谁。判断该用哪一层，先问自己要的是拒绝请求、改写结果，还是描述错误。顺序要记牢：守卫早于拦截器，拦截器早于管道，过滤器只在异常路径上收尾。全局注册省事，但需要注入依赖时记得换成 APP_GUARD、APP_INTERCEPTOR 与 APP_FILTER。组合之前先保证每一层职责单一，再谈复用。
