Node.js 12 诊断报告与堆快照

本文属于《TypeScript 学习路线》第 59/74 篇
上一篇系列目录下一篇

线上服务跑着跑着内存涨了，或者 CPU 突然打满，重启一下又恢复正常，这是 Node.js 后端最常见的一类故障。本文围绕“怎么查”展开：先把问题分类，再讲现场保护，然后用内存采样、堆快照、GC 日志与 CPU profile 一层层缩小范围，最后用一个完整案例走完从告警到验证的全流程。文中涉及的 Node 12 诊断能力目前仍在路线图中，当下可用的手段以 Node 10 LTS 与 Node 11 为准。

先把问题分类：六种“慢”和“涨”

排查最怕一上来就抓快照。堆快照代价高、解读慢，如果问题其实出在句柄或者 CPU 上，抓完也只是白等一场。所以在打开任何工具之前，先根据现象把问题归到一个大类里，后面的动作才有方向。下面六类覆盖了绝大多数线上表现，每一类都先给出可观察的现象，再说明它和相邻类别的区别。

内存泄漏。典型现象是常驻内存与堆使用量长期单调上升，每次回收之后回落的谷值一次比一次高，最终触发容器内存上限被杀死，重启后曲线从头开始。关键词是“回落不到原来的位置”；每次 GC 后都能回到同一基线的，只是正常锯齿。

内存膨胀。内存曲线是平的，但基线本身很高，堆使用量长期贴着上限，GC 之后仍占用大半。它和泄漏的区别是没有持续增长的趋势，问题是“本来就不该占这么多”：可能缓存装得太多、单个对象太大、并发请求数太高，或者堆上限与容器配额不匹配。

GC 频繁。表现是 CPU 有相当比例消耗在垃圾回收上，日志里新生代回收密集出现，老生代标记压缩的间隔越来越短，接口延迟出现规律性抖动，而内存曲线看起来还算正常。这类问题往往由前两类引起，但它本身也会独立出现，比如新生代空间被调得过小。

CPU 打满。单核占用长期接近百分之百，负载值升高，请求开始排队，而内存曲线平稳。此时要看的是热点函数，不是堆。要注意一种假象：容器里限制了一个核，进程占用百分之百其实只是一个核满，宿主机看起来并不高。

事件循环阻塞。现象很特别：CPU 未必满，内存也正常，但定时任务开始漂移，健康检查偶发超时，接口 P99 出现尖刺而平均值还好。原因通常是某段同步代码把事件循环占住了，比如大 JSON 的解析与序列化、复杂正则、同步文件读写、大数组排序。这一类用 CPU profile 和延迟测量最有效。

句柄泄漏。文件描述符、套接字、数据库连接的数量持续上涨，最终出现“打开文件过多”的错误，或者连接池被占满导致请求全部超时。内存可能完全正常，这也是它最容易被误判的地方。看系统层面的句柄计数与连接池指标就能快速确认。

六类的观测入口并不相同：内存看堆与常驻集，CPU 看热点，延迟看事件循环，资源看句柄数。先把入口定下来，再去选工具，能省掉大量无效操作。

现场保护：抓快照之前先算代价

生产环境的每一次诊断动作都有成本，先做低成本观测、再决定是否动用高成本手段，是必须养成的顺序。

第一步是确认影响面：单实例还是全部实例，某个接口还是所有接口，最近有没有发布、改配置、调流量。很多“内存泄漏”是某次发布引入的，回滚就能止血；很多“CPU 打满”是流量结构变了，限流比抓快照更紧急。止血与定位要分开，止血优先。

第二步是看已有的监控与日志。进程的常驻内存、堆使用量、GC 次数与耗时、事件循环延迟、CPU、文件描述符数量、连接池占用，这些指标如果平时就采了，故障时看曲线比任何工具都快。日志侧重点找几类关键词：内存不足被杀的记录、打开文件过多、连接超时、上游响应变慢。监控能告诉你“什么时候开始”和“哪些实例”，这决定了后面抓哪台、抓几张。

第三步才是决定要不要抓快照，关键在理解代价。V8 的堆快照会把整个堆序列化成一个文件，抓取前通常要先做一次完整回收，抓取过程中进程基本处于停止状态。堆越大，停顿越久，接近上限的堆可能停几秒到几十秒，文件大小与堆的规模在同一量级。对一个正在对外服务的进程来说，这就是一次计划外的停机。原则很清楚：能在预发或副本上复现，就不要在线上抓；必须线上抓，就先从负载均衡摘掉，抓完重启再挂回去。

还有两个容易被忽略的细节。一是磁盘，快照文件动辄数百兆到数吉，容器根分区往往很小，抓之前确认可写目录的剩余空间，抓完尽快转走。二是权限与路径，容器里的工作目录不一定可写，写到自己挂载的卷上更稳妥。文件名带上实例与时间，方便后面做差。

图里有一条隐含的分叉：如果监控显示内存在涨，就走快照路线；如果内存平稳而延迟或 CPU 异常，就走 profile 路线。两条路线最后汇合到同一件事上——找到那段具体的代码，而不是停留在“内存高了”这种描述。

用 process.memoryUsage 做低成本观测

在动用快照之前，进程自己就能提供一份相当有用的数据。process.memoryUsage() 是同步调用，开销极小，可以放心地按分钟级采样。它返回四个字段，每个字段回答的问题都不一样，混着看很容易得出错误结论。

rss 是常驻集大小，指操作系统分配给这个进程、当前确实占用物理内存的部分。它包含 V8 的堆、堆外内存、代码段、线程栈，也包含已释放但操作系统还没回收的页。所以 rss 只涨不跌本身有欺骗性，判断泄漏时只能作为辅助。

heapTotal 是 V8 已向操作系统申请的堆空间总量，heapUsed 是其中真正被对象占用的部分。两者的差是当前的空闲余量。堆是按代管理的，已申请的空间不会立刻归还，所以 heapTotal 呈现阶梯式上升是正常的，关键是看 heapUsed 在回收之后能落到哪里。

external 指绑定在 JavaScript 对象上、但由 C++ 层持有的内存，最典型的就是 Buffer。它不计入 V8 的堆，却实实在在占用进程内存。如果 rss 涨而 heapUsed 平稳，external 也在涨，那问题多半在 Buffer 或原生模块，堆快照里反而看不到多少东西。

读这份数据要比较同一相位。垃圾回收是有周期的，随手取两个点，一个在回收前、一个在回收后，会得出相反结论。正确的做法是看每天的谷值：如果连续几天，GC 之后的 heapUsed 最低点都在抬高，斜率稳定，基本可以判定为泄漏；如果谷值不变、只是峰值变高，更可能是流量或批量任务带来的临时膨胀。

在诊断环境里可以加上 --expose-gc 手动触发回收，让“回收后”这个点变确定。它只适合排查，不要带进生产启动参数，业务代码也不该依赖。

堆快照：从增长最多的构造函数追到引用链

内存确认在涨，下一步是找出谁在持有对象。堆快照把某一时刻堆上的对象、引用关系与对象大小都记录下来，供离线分析。

建立连接

当前主流的做法是用 inspector 协议加 Chrome DevTools。启动时加上 --inspect，进程会监听一个调试端口；在容器外连接时需要显式指定绑定地址并映射端口。注意这个端口等同于进程的控制权，绝不能暴露在公网，只允许通过跳板机或内网访问。

然后在本地打开 Chrome，进入 chrome://inspect，配置目标主机的地址与端口，就能看到待调试的进程；走 SSH 隧道时把远端端口转到本地即可。这里不建议用 --inspect-brk，它会让进程在第一行就停住，用在线上等于直接让服务不响应。

连接成功后进入 Memory 面板，选 Heap snapshot 拍摄。面板里还有分配时间线与分配采样，前者适合看短时间内的分配行为，后者开销小但精度有限；定位长期泄漏仍以堆快照为主。

拍摄与对比

单张快照几乎无法判断泄漏，因为分不清“一直存在”和“刚刚新增”。有效的做法是拍两张做差：先点面板上的回收按钮触发完整 GC，拍下基线；让进程处理一段有代表性的流量，或者等待一个业务周期；再次 GC，拍第二张。选中第二张，在视图下拉里切到 Comparison 与基线对比。

对比视图会为每个构造函数列出新增与释放的对象数与大小变化。排查时按大小增量排序，前几名通常就藏着答案。需要注意几个内置条目：字符串、数组、编译后的代码与各类系统对象，它们的增长有时是结果而不是原因；真正的线索往往是业务构造函数，或者框架内部的缓存结构。

三个数字：Distance、Shallow Size、Retained Size

每个对象都有三个关键指标。Distance 是它到 GC 根的最短引用边数，数字越小越靠近根；一个对象的 Distance 突然变小，往往意味着它被挂到了某个长期存活的结构上。

Shallow Size 是对象自身占用的内存，不含它引用的其他对象。Retained Size 是删除这个对象后能连带释放的总内存，也就是它独占的那整片引用树。判断“谁最占地方”要看 Retained Size，判断“对象本身多大”才看 Shallow Size。一个只有几十字节的 Map 节点，Retained Size 可能是几百兆，因为它拽着一整棵子树。

一个常见误判是：互相引用或被同一父对象引用的对象，Retained Size 会互相包含，直接相加会重复计算。

顺着 Retainers 往上走

找到可疑的构造函数只是中点，还得回答“它为什么没被回收”。点开一个对象，下方的 Retainers 面板会列出所有引用它的地方，从最近的一层开始，逐层向上，直到抵达 GC 根。这条链就是它存活的理由。

读链时先看形状再看细节。如果链的末端是模块作用域、全局对象或者长生命周期的单例，说明是设计层面的持有；如果末端是定时器、事件监听器或者未完成的 Promise，说明是生命周期管理出了问题。链上经常出现闭包上下文，这时要看闭包捕获了哪些变量，很多“莫名其妙”的持有都是闭包顺手带进来的大对象。排查时可以在类过滤框里只留自己写的类型，先把框架与运行时排除。

用 heapdump 在进程内写快照

不是所有环境都允许开调试端口。托管容器、受管运行环境、策略严格的内网，都可能让 inspector 连不上。这时可以换一条路：让进程自己把快照写到磁盘，再把文件取走分析。

社区里的 heapdump 模块做的就是这件事。引入之后，它向进程注册一个信号处理，收到约定的信号时抓取堆快照并写入指定目录。相比 inspector，它只需一次信号，不需要长连接，也不必暴露端口；缺点是写入在进程内完成，同样会暂停服务，文件也落在进程所在机器的磁盘上。

这段代码有几处值得展开。路径必须落在挂载卷上，容器根分区的可写层空间有限，写到那里既可能撑爆磁盘，也拿不出来；文件名必须带实例标识与时间戳，多副本同时触发时才不会互相覆盖；写完之后尽快把文件搬走，快照通常和堆一样大，留几份就足以把磁盘占满。权限方面，运行用户对目标目录要有写权限，很多镜像默认以非 root 用户运行，这一点经常在真正需要抓的时候才被发现。

还有两个风险。第一，安装这个模块需要编译原生代码，生产镜像里通常没有编译工具链，应当在构建阶段装好并固化进镜像，而不是在故障时现场安装。第二，它是常驻依赖，会占用少量内存，也让进程多一个信号处理。合理的做法是只在诊断构建里引入，或者准备一个带诊断能力的镜像变体，用环境变量控制是否加载。

最后强调一次顺序：先摘流量，再发信号，抓完重启。在正在处理请求的实例上随手触发，那不是取样，是一次没有通知用户的停机。

GC 压力：trace-gc 与堆统计

有些问题不需要看对象，只需要看回收行为就能定性。垃圾回收的日志能告诉你两件事：回收有多频繁，停顿有多长。当前可用的手段是启动时加上 --trace-gc，让 V8 把每次回收的类型、耗时和前后堆大小打到标准输出。

日志里会反复出现几种回收：新生代的 Scavenge 频繁是常态，因为大部分对象朝生夕死；老生代的标记压缩出现得越密，说明存活对象越多、堆越紧张。判断压力看两个比值：单位时间内老生代回收的次数，以及单次停顿相对于请求延迟预算的比例。一次停顿就超过接口 P99 预算的，不管内存有没有涨都得处理。

进程内也可以拿到统计。v8.getHeapStatistics() 返回一组数字，其中 heap_size_limit 是堆的上限，used_heap_size 是当前使用量，total_available_size 是还能申请多少，还有 malloced_memory 与 peak_malloced_memory 反映堆外分配。特别值得盯的是 number_of_detached_contexts，它统计已经与全局对象断开、却还没被回收的上下文数量，这个数字持续增长通常意味着有东西在按住旧的执行上下文。

调大堆上限是很多团队的第一反应，--max-old-space-size 也确实能把崩溃推迟。但要清楚它只是把天花板抬高，让同样的泄漏需要更长时间才撞到上限。对一个稳定泄漏的进程，调大参数等于把故障从三天一次改成五天一次，同时让每次 GC 的停顿更长、快照文件更大、崩溃时的影响面更广。它适用于“确实需要更大堆”的场景，比如构建工具或者内存密集的批处理，不适用于掩盖泄漏。

CPU 侧：prof 与事件循环延迟

内存讲完，换一条线。CPU 打满或者延迟异常时，目标是找出那段吃掉时间的代码。当前有两条可用的采样路径，一条是老牌的 --prof，一条是 Node 11 起提供的 --cpu-prof。

--prof 在进程目录下生成一个日志文件，记录采样点。进程跑够一段时间后，用 --prof-process 把日志翻译成可读报告：

报告里先看 Summary 段的 ticks 分布，再看 JavaScript 段按耗时排序的函数列表。除了业务函数，还会出现内置函数、垃圾回收与 C++ 层条目。如果排在前面的全是垃圾回收，说明瓶颈在内存压力而非业务计算，应该回到上一条路线；如果大量时间落在原生模块，就要考虑是不是加密、压缩或数据库驱动在同步执行。

--cpu-prof 走的是另一套格式，产出的文件可以直接拖进 Chrome DevTools 的 Performance 面板，以火焰图的形式查看调用栈，读起来比文本报告直观得多。

两条路径都是采样，采样就有偏差：跑十秒只能得到几千个样本，短促热点会被稀释，冷启动开销又被放大。让进程在代表性负载下跑够半分钟，并且只开一个诊断参数。

CPU 没满但延迟有尖刺时，要看的是事件循环有没有被堵住。最便宜的测法是定时器漂移：设一个固定间隔的定时器，记录每次实际触发时间与期望时间的差，差值就是这一轮循环被占用的粗略证据。

这个数字不精确，但足够触发告警。要定位具体是哪段代码堵的，就在漂移发生时抓一份 CPU profile，或者用采样时间线看那一秒主线程在做什么。同步的大文件读写、超大 JSON 的序列化、回溯量大的正则、大数组排序与深拷贝，是最常见的元凶，它们都把本可挪走的工作整段压在了主线程上。

本篇只讨论怎么测出阻塞，不展开事件循环各阶段的调度原理，那部分属于另一个专题。

六种常见的持有方式

工具会给出对象和引用链，但链的形状往往有规律。下面六种模式覆盖了笔者见过的大部分泄漏，看到快照里的引用链，可以先往这几个方向套。

没有上限的全局缓存。用 Map 或普通对象做缓存，只写不删，键又是请求维度的，跑得越久存得越多。修复是给容量上限与过期时间，或换成带淘汰策略的实现；只读的派生数据可以交给弱引用，让 GC 在内存紧张时回收。

事件监听器没有移除。每次请求都往一个长生命周期的对象上挂监听，请求结束却不摘，监听器函数又通过闭包带着请求上下文。症状是监听器数量单调上涨，还会打印监听器过多的警告。修复是成对地添加与移除，一次性监听用 once，或者在生命周期结束时统一清理。

闭包持有大对象。回调里顺手引用了整个请求体、整个查询结果或者整个配置对象，而回调被存进了队列、缓存或者定时器。快照上看到的是一串闭包上下文，Retained Size 远大于闭包本身的体积。修复是只捕获需要的字段，不要让闭包成为大对象的最后一根引用。

Promise 与定时器没有收尾。轮询用的定时器在业务结束后没有清除，或者一条永不 settle 的 Promise 链一直挂着回调，回调又引用着请求作用域。修复是所有定时器都有对应的清除路径，异步流程加上超时与取消。

Buffer 与外部内存。小 Buffer 由内存池分配，切片会共享底层内存，一个几十字节的切片可能按住一整块池；把大 Buffer 放进缓存则会直接抬高 external。修复是必要时拷贝出独立内存，缓存 Buffer 要算真实体积而不是条目数。

连接与句柄没有释放。数据库连接、套接字、文件流用完之后没有关闭，错误分支上尤其容易漏。表现是句柄数上涨、连接池耗尽，内存却很正常。修复是用完即关，错误路径也要关，并且给池加上等待超时与泄漏检测。

这六种的共同点是“长生命周期对象持有了短生命周期数据”。排查时与其盯着对象大小，不如问一句：这个对象凭什么活这么久，谁该负责让它死。

一次完整的排查：导出服务的内存曲线

把前面的方法串起来看一个虚构的场景。某内容站点有一个导出服务，把文章批量导出成文件，四个副本跑在 Node 10 LTS 上，容器内存配额 1.5 GB，老生代上限设为 1 GB。上线两周后开始告警：常驻内存从 400 MB 涨到 1.2 GB，两天内被杀死三次，重启即恢复，流量没有变化。

第一步看监控，不做任何干预。堆使用量呈锯齿状上升，关键是每天的谷值从 300 MB 抬到 700 MB；external 平稳，句柄数与数据库连接数也平稳。由此排除 Buffer 与连接泄漏，范围收窄到堆上的对象。同时确认最近没有发布，排除了回滚止血这条捷径。

第二步加采样与 GC 日志。--trace-gc 显示老生代回收间隔从四十分钟缩短到六分钟，单次停顿从两百毫秒涨到接近一秒。存活对象在变多，且增长速度与导出请求量正相关，于是把怀疑范围锁定在导出链路上。

第三步抓快照。从负载均衡摘掉一个副本，用 --inspect 连上，手动 GC 后拍下基线，再用线上采样得到的参数回放三百次导出，再次 GC 后拍第二张。对比视图按大小增量排序，排在最前的业务类型是导出任务的包装对象，数量与回放次数几乎一比一。

第四步看引用链。点开其中一个对象，Retainers 显示它被一个 Map 持有，Map 又挂在模块作用域的单例上，Distance 很小。回到代码，问题一目了然：导出完成后把结果按任务号存进模块级 Map，本意是让前端轮询取结果，但只写不删，取走之后也没有清理。每次导出都留下一条记录，记录里还带着文件内容。

第五步修复。结果改写到对象存储，内存里只保留最近一百条元数据并设置过期时间，取走时立即删除；同时给缓存加条目数指标，超过阈值告警。改动不大，但把“无限增长”变成了“有界”。

第六步验证。用同一套回放再跑一遍，观察二十四小时：堆的谷值稳定在 300 MB 附近，不再抬升；老生代回收间隔恢复到四十分钟以上；导出接口的 P99 回到修改前水平。验证时特意用了相同的回放脚本与并发，否则流量差异会掩盖效果。最后把采样口径固化进值班手册：先看谷值，再看 GC 间隔，两者同时恶化才进入抓快照流程。

Node 12 与诊断报告的路线图

文章标题里的 Node 12，截至写作时还没有发布。按一年两个大版本的节奏，它会在 2019 年上半年进入当前版本线，而生产环境此刻应以 Node 10 LTS 为主、Node 11 作为特性验证。上面所有操作都是当下就能用的手段，不依赖未发布的特性。

社区正在推进的方向，是让诊断信息不再散落在各种开关和第三方模块里。讨论中的目标是：进程收到约定信号时，能一键产出一份结构化报告，把运行环境、堆统计、GC 情况、活跃句柄与事件循环状态打包在一起，落到磁盘或送到采集端。对值班的人，这意味着不必先连调试端口、也不必预装模块，就能拿到可归档、可对比的现场记录。

需要明确的是，这套能力目前仍处于实验与设计阶段，触发方式、字段命名、输出格式都可能调整，本文不给出具体开关。在正式文档发布之前，不要把它写进生产脚本或者告警流程，现有的采样加快照组合仍然可靠。可以提前做的是把采集口径定下来：指标叫什么、多久采一次、快照怎么命名、存到哪里。

小结

线上内存与 CPU 问题的排查，顺序比工具更重要：先分类，再保护现场，用低成本采样定性，最后才动用快照与 profile。读内存看 GC 后的谷值，读快照看 Retained Size 与 Retainers。调大堆上限只能推迟崩溃，真正的修复是找到那条不该存在的引用链，并用相同的回放验证它不再增长。
