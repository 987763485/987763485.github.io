Burp Suite 渗透测试实战

渗透测试的交付物不是一叠扫描报告，而是一组能被人复现、能被开发修掉的证据。本文以 2018 年仍在大量团队中使用的 Burp Suite 1.7.x 为主线，把一次获得书面授权的 Web 渗透测试拆成授权确认、代理与解密、站点地图、Repeater 验证、Intruder 批量请求、Scanner 复核、报告与复测几个阶段。文中所有示例都使用 example.com 或本地靶场，只讨论授权范围内的测试方法；未授权的扫描与探测不在本文讨论之列，也不应被尝试。

授权先于工具

在打开代理之前，先把“我能对什么做什么”写清楚，这是渗透测试与攻击行为之间唯一可靠的分界线。《网络安全法》在 2017 年 6 月施行之后，甲方在采购安全服务时普遍要求合同、授权书、保密协议三件套齐全；对测试方而言，授权书不是形式，而是出事时唯一能证明主观无恶意的材料。刑法中关于非法侵入计算机信息系统、非法获取数据与破坏系统的条款，并不以“是否造成损失”为唯一前提，越界本身就可能构成问题。

授权书要写到什么颗粒度

一份可执行的授权书至少包含九个要素。第一是主体：委托方与测试方的全称、签字人职务、盖章，个人接单时要有身份证件与联系方式。第二是资产清单，要细到域名、IP、端口、协议，明确子域是否包含在内，明确 CDN 与云防护背后的源站是否在范围内。第三是时间窗口，写清起止日期与每天允许操作的时段，避开对账、结算、大促和发布日。第四是允许的测试方式，主动扫描、口令测试、文件上传、社会工程、压力测试要逐项勾选，默认全部禁止。第五是禁止项，例如不得触碰第三方托管系统、不得发起真实支付、不得删除或修改业务数据、不得横向移动到清单外主机。第六是数据处理，约定可以取哪些字段、可以存多久、存放在哪里、如何加密与销毁。第七是沟通机制，日报时间、高危发现多久内电话通知、双方紧急联系人。第八是暂停与回滚，出现业务异常时谁有权叫停，测试上传的文件如何清除，被锁定的账号如何解锁。第九是责任边界，超出范围的动作必须先拿到书面追加授权。

这九条看着繁琐，实际执行时能省掉大量争执。最常见的纠纷是“测试账号是我们自己的，为什么不能跑字典”——授权书里没写口令测试，答案就是不能。

范围、环境与数据的三条边界

范围的第一条边界是资产。清单内的域名与 IP 才可访问，扫到清单外的主机要立即停止并记录，交给客户判断。第二条边界是身份，测试账号由客户创建，只赋予待测角色所需的权限，并且单独命名以便审计，例如以 tst_ 开头加日期后缀；不要借用真实员工账号，尤其是管理员账号。第三条边界是数据，只碰自己创建的测试数据，需要展示越权时读取一条由自己构造的记录即可，不浏览、不导出真实用户数据。

环境上优先选择预生产或影子环境。生产环境不是不能测，但要把写操作降到最低：能只读验证的不提交表单，能用自己的订单验证的不动别人的订单，能单请求验证的不批量跑。测试前和运维确认数据库有可用备份、发布窗口没有冲突、监控告警已知会，避免测试流量触发值班电话。数据脱敏贯穿全程：截图里的手机号、身份证号、银行卡号要打码，报告里的 URL 参数值要替换，证据文件加密存放，项目文件不带出客户网络。这些做法不增加多少工作量，却决定了报告能不能直接交给甲方存档。

1.7.x 的能力边界

Burp Suite 的定位是“本地拦截代理加一套围绕请求的工具箱”。浏览器把流量指向它，它解析 HTTP 报文、按规则拦截或放行，再把请求转发给目标。所有工具共享同一份请求与响应，因此从 History 里右键就能把一条流量送到 Repeater、Intruder 或 Scanner。2018 年 Burp Suite 2.0 已经出现，界面与工程结构变化不小，但企业内网、培训材料和大量甲方的验收标准仍以 1.7.x 为准，本文的菜单名称与操作路径也一律按 1.7.x 描述。

版本选择直接影响能做什么。Professional 版包含主动与被动 Scanner、不限速的 Intruder、项目保存与恢复、全局搜索、Extender 与 BApp Store，以及 Collaborator 客户端；Community 版保留了 Proxy、Repeater、Decoder、Comparer、Sequencer 和站点地图，Intruder 可用但被限速，没有 Scanner，也不能保存项目状态或安装扩展。如果测试范围里明确要求“手工验证为主、扫描为辅”，Community 版配合外部脚本也能完成大部分工作；但只要涉及批量请求、认证扫描和报告导出，Professional 版几乎是必需的。工具本身需要合法许可，不要在客户环境里使用来源不明的副本，这既违反许可协议，也会让证据链变得可疑。

运行环境同样值得提前准备。Burp 基于 Java，长时间抓包与大项目会让堆内存吃紧，启动参数里把最大堆调到 1 GB 以上是常见做法；代理默认监听 127.0.0.1 的 8080 端口，除非要让手机或另一台虚拟机接入，否则不要绑定到 0.0.0.0。测试用的浏览器最好是独立配置文件或独立虚拟机，日常浏览的 Cookie 与收藏夹不应该出现在测试机的 History 里，否则既污染分析，也容易把无关系统的凭据带进项目文件。

代理、证书与解密

整条测试链路的形状很简单：浏览器把请求交给 Burp，Burp 记录并可选地暂停，然后以客户端身份向目标发起连接，响应再原路返回。HTTPS 之所以能被看见，是因为 Burp 对浏览器扮演服务器、对服务器扮演客户端，用自己签发的证书完成两次握手；浏览器只要信任了 Burp 的根证书，就不会报警。

监听、证书与常见故障

监听器在 Proxy 的 Options 页配置，绑定回环地址与 8080 端口即可，同时勾选 “Support invisible proxying” 以兼容不按标准代理协议说话的客户端。浏览器端把 HTTP 与 HTTPS 代理都指向 127.0.0.1:8080，并在例外列表里排除内网地址与更新服务，避免系统更新把 History 刷满屏。证书的获取方式是在已配置代理的浏览器里访问 http://burp，下载 CA 证书后导入。Firefox 有独立证书库，在首选项的证书管理里导入到“证书颁发机构”；Chrome 与 Safari 走系统钥匙串，macOS 上导入后还要在证书详情里把信任设为“始终信任”；Windows 则导入到“受信任的根证书颁发机构”。

导入后仍看不到明文，通常有三个原因。一是证书没装进当前浏览器使用的证书库，尤其是 Firefox 与系统库分离的情况；二是访问的域名不在证书覆盖范围内，Burp 会现场签发，浏览器若开启了严格的证书校验就会拒绝；三是目标使用了双向认证，服务端要求客户端证书，这时需要在 TLS 设置里加载客户提供的 PKCS#12 文件。移动端更麻烦一些，Android 从 7.0 起默认不信任用户安装的证书，App 只认系统证书，遇到这种情况应当向开发确认是否有可安装测试证书的测试包，或者直接改用 Web 端与接口文档验证，不要用挂钩、改包之类的技术手段去绕过硬性校验，那既超出授权，也破坏证据的可信度。

Intercept、History 与 Scope

拦截开关建议默认关闭。开着 Intercept 逐条点 Forward 会让人把注意力耗在机械操作上，真正需要改包的场景其实很少；更高效的做法是让流量自然流过，在 History 里回看并挑出可疑请求，再右键送到 Repeater。需要拦截时用拦截规则收窄范围，例如只拦目标域、只拦 POST、只拦包含某个路径的请求，规则写在 Proxy 的 Intercept 选项卡里，支持按文件扩展名与正则过滤。

History 是测试过程中最容易被低估的资产。列表可以按状态码、MIME 类型、请求方法与关键字过滤，右键能给请求加注释与高亮颜色。笔者习惯用颜色区分身份：未登录流量一种颜色，普通用户一种，管理员一种，后续做越权对比时一眼就能找到同一接口在不同角色下的三条记录。History 里还保存了完整的请求头与 Cookie，报告里的复现步骤可以直接从这些记录里取，不必再靠记忆复述。

Scope 决定了“哪些流量算这个项目的”。在 Target 的 Scope 页填入域名，使用高级范围控制可以写主机正则与文件路径正则，把静态资源、第三方统计、支付回调排除在外。设好之后，回到 Proxy 的 Options 勾选只显示范围内的条目，History 与站点地图会立刻安静下来。手工输入容易漏掉子域，更稳妥的做法是复制 History 里那条请求的主机名，粘贴到 Scope 的添加框里。范围设置不只是为了界面清爽，它还是防止误伤的第一道闸门：任何不在 Scope 内的主机，都不应该收到本文所说的任何请求。

从站点地图到攻击面

信息收集的完整方法在《信息收集》一篇里已经展开，子域枚举、端口扫描、指纹识别的工具链不属于本文范围。这里只讲一件事：拿到客户确认的资产清单之后，怎样在 Burp 里把它们变成一张可操作的地图。

爬虫、被动记录与手工浏览

Burp 的爬虫从种子 URL 出发，解析页面里的链接与表单，把发现的路径填进站点地图。启动前要限制范围，把并发降到个位数，并且排除“退出登录”这类会把会话踢掉的链接，否则爬到一半会话失效，后面的页面全是登录页。需要登录后才能访问的区域，可以先用测试账号手工登录，再让爬虫带着当前 Cookie 继续；表单提交要谨慎，涉及删除、支付、审批的按钮一律不爬。

Professional 版的被动扫描会在流量经过时顺带记录问题，不发额外请求，适合在手工浏览阶段一直开着。主动扫描留到范围与认证都确认之后再开，这一点在下一节展开。手工浏览仍然是发现业务入口最有效的方式：把菜单点一遍，把列表翻几页，把导出与打印按钮各点一次，观察 History 里冒出来的接口。前端 JavaScript 文件也值得读一遍，接口路径、参数名、被注释掉的管理入口经常直接写在里面，这些线索比字典扫描精确得多。

给地图做标注

站点地图的价值在于结构，而结构需要人来标注。对每个关键请求加注释，写清它属于哪个角色、对应哪个业务动作、是否需要前置条件；把同一功能的多个入口合并成一个树节点，避免地图膨胀成几百条重复路径。发现清单之外的主机时不要访问，只在笔记里记下域名与发现时间，随日报交给客户确认。测试结束时，这张带标注的地图可以直接作为报告的附件，说明“测了什么、没测什么”，比一句“已全面测试”可信得多。

Repeater：把一条请求改到最小

Repeater 是整套工具里最像“手术刀”的部分：它不发批量请求，只把一条报文摆在面前，让人改一个字节、发一次、看一次响应。绝大多数漏洞的确认都发生在这里，扫描器给的结论只是线索，能不能站得住要看 Repeater 里那一问一答。

界面与基本操作

从 History、站点地图或 Scanner 的结果上右键发送到 Repeater，左侧是请求，右侧是响应，顶部有 Raw、Params、Headers、Hex 几种视图。Raw 视图最接近真实报文，适合改 Header 和观察编码；Params 视图把 URL 查询串与表单字段拆成键值对，改完会自动重新编码，适合避免手工编码出错。发送快捷键在 Windows 上是 Ctrl+R，macOS 上是 Cmd+R，每发一次会在上方留下一个编号快照，用尖括号翻页就能对比改动前后的响应。

响应默认不跟随重定向，这对测试是好事：302 的 Location 本身就是重要信息。需要以登录态在真实浏览器里看效果时，右键选择在浏览器中打开响应，Burp 会把当前响应渲染出来，但地址栏仍是本地地址，页面里的相对路径资源可能加载失败，这一点要心里有数。响应被压缩时 Raw 视图是乱码，切到 Render 或让 Burp 自动解压即可；请求里的 Content-Length 在 1.7 中默认自动修正，手工粘贴报文时若发现服务端返回 400，先检查长度与首行。

最小化验证与证据留存

一条可信的验证至少包含三步：先发原始请求建立基线，记录状态码、响应长度与关键字段；再只改一个变量重发，其他条件保持不变；最后解释差异为什么由这个变量引起。一次改三四个参数，即使结果异常也说不清是哪一个生效，报告写到复现步骤时就会露馅。做越权对比时，基线应当是“A 账号请求自己的资源”，实验组是“A 账号请求 B 的资源”，两组请求除身份与资源 ID 外完全一致。

上面这条请求是基线，把路径里的 1001 换成账号 B 的订单号重发，如果响应仍然是 200 且返回了 B 的订单字段，水平越权即成立；若返回 403 或跳转登录，说明服务端做了归属校验。改动越小，结论越硬。

证据留存不是截图了事。Repeater 里右键保存请求与响应，文件名带上编号与时间；记录测试账号、请求时间、完整 URL、被改动的字段、响应中的关键片段。涉及金额、订单号、手机号时，保存前先替换成等长的假数据，原始文件加密存放。两份响应需要逐字节比较时，用 Comparer 把内容粘进去做差异高亮，比肉眼可靠。若响应里出现了本不该出现的数据，取一条记录、一个字段即可，不要继续翻页，更不要导出。

Intruder：批量请求前的算术

Intruder 把一条请求里的指定位置变成变量，用 payload 逐个填充并批量发送。它的威力与风险来自同一个地方：请求数量会在几秒内放大几个数量级。因此在点下开始之前，先算清楚要发多少请求、目标能不能承受、授权书允不允许。

四种攻击类型

类型 变量与 payload 的关系 典型场景 请求数
Sniper 一组 payload，逐个位置轮换 单参数遍历 ID、跑一个字典 位置数 × payload 数
Battering ram 一组 payload，所有位置填同一个值 同一输入出现在多处，如 body 与 Cookie payload 数
Pitchfork 多组 payload 并行，按下标一一对应 已知账号与口令成对验证 取最短一组长度
Cluster bomb 多组 payload 做笛卡尔积 账号与口令的组合穷举 各组数量相乘

Sniper 最常用，也最容易被误用：如果请求里有三个参数被标了变量，它会依次只替换其中一个，另外两个保持原值，总请求数是三倍。Battering ram 适合验证“同一个值在多个位置是否一致校验”，比如用户名同时出现在表单和自定义头里。Pitchfork 用于成对数据，长度不齐时以最短的为准，多出来的 payload 会被静默丢弃。Cluster bomb 的请求数是乘积，两个一百条的字典就是一万次请求，在生产环境几乎必然触发告警，使用前必须得到明确许可并设定上限。

payload、线程与结果分析

payload 类型覆盖了常见需求：简单列表、从文件读取、字符块、数字序列、日期、暴力组合、空 payload 与用户名生成器。数字序列适合遍历自增 ID，但要设步长与上下限；空 payload 常用来重复发送同一条请求，观察频率限制或竞态。处理结果时，用 Grep Match 标记响应里是否出现“成功”“无权限”等关键字，用 Grep Extract 把用户 ID、余额等字段抽出来做成列，再按状态码与响应长度排序，异常项通常一眼可见。

线程数与延迟是控制压力的两个旋钮。默认线程数偏高，面向生产环境时建议降到个位数并加几十到几百毫秒的间隔；自动重试要关掉，否则一次超时会变成三次请求。开始前把总请求数报给客户，约定每秒请求数上限与中止条件，测试过程中盯住 5xx 比例与响应时间，一旦异常立即停止。口令测试的边界尤其要守住：只在授权书明确允许、且使用客户提供的测试账号时进行，不对真实用户账号跑字典，不尝试绕过锁定与验证码，命中弱口令后立即停止并当日报告。

Scanner：把机器当助手

Professional 版的 Scanner 分被动与主动两种工作方式。被动扫描只看已经流过的流量，不发新请求，适合全程开启，用来兜住明显的配置问题；主动扫描会向每个插入点注入变体，请求量取决于插入点数量与策略强度，必须挑时间、挑范围、挑端点。扫描前确认 Scope 只包含目标域，把登出、删除、支付、审批这类端点排除，扫描策略先在预生产环境跑一遍，观察请求规模再决定是否放到生产。

认证扫描是效果分水岭。未登录状态下的扫描只能看到登录页，结论几乎没有价值；正确做法是用测试账号录制一个登录宏，配合会话处理规则在会话失效时自动重放，或者退一步，先手工登录让 Burp 持有 Cookie 再开扫。宏重放会反复提交登录请求，若目标有错误次数锁定，必须提前和客户确认阈值，必要时改用长有效期的测试会话，而不是让工具反复尝试。扫描结束后逐条复核：在 Repeater 里重放原始请求，确认响应差异确实由该参数引起，排除输入原样回显造成的误报、统一错误页造成的假阳性、以及防护设备拦截页被当成漏洞证据的情况。Scanner 不懂业务，越权、支付逻辑、流程绕过它基本发现不了，自动扫描永远不能替代手工验证。

几个常见场景的验证思路

越权分为垂直与水平两类。垂直越权是低权限角色访问高权限功能，验证时用普通账号的会话直接请求管理接口，观察是否返回数据而非跳转登录；水平越权是同级用户互访，准备两个同角色账号，用 A 的会话请求 B 的资源标识。IDOR 是水平越权的常见形态，自增 ID 最容易命中，UUID 则需要从页面、接口响应或分享链接里找线索。无论哪种，只在自己创建的两条测试数据之间互访，取一个字段证明即可，不遍历、不批量导出。

参数篡改关注服务端是否重新校验。价格、数量、折扣、角色、状态这类字段常在前端被约束，把请求截下来改成边界值，观察订单金额与权限是否随之变化；隐藏字段与只读字段同样值得试一次。文件上传的验证只看四件事：扩展名是否按白名单校验、内容类型是否只信客户端、文件内容是否被识别、上传后的路径是否可预测且可访问。测试文件用纯文本并在内容里写明测试用途与日期，验证完立即删除并记录删除时间，不上传任何可执行内容。SSRF 的回连验证应当在自有靶场或自建监听服务上完成，只确认服务端是否发起了请求，不读取云元数据、不探测内网网段；若使用 Collaborator 一类带外服务，要先确认客户允许测试流量出网，并把域名写进授权书。所有场景的共同要求是：最小化、可复现、留证据、及时清理，发现高危先通知再继续。

扩展：按需加载，用完即关

BApp Store 在 Extender 里，分类大致集中在四个方面：编码与加解密类，用来处理业务自定义的签名、混淆参数；鉴权与会话类，帮助解析令牌、观察会话生命周期；日志与笔记类，把请求导出成便于比对的格式；扫描增强类，为被动扫描补充规则。插件本质上是能读到全部流量的代码，安装前应当确认来源与权限，只在受控机器上启用，并记录名称与版本以便复现。插件越多代理越慢，测试结束应当禁用。1.7 的扩展接口支持 Java 与 Python，编写自定义扩展属于开发工作，本文不展开。

报告：让开发能照着修

漏洞分级建议同时给出技术评分与业务影响。技术评分用 CVSS 3.0 的计算结果，业务影响则由数据敏感度、可利用前提、影响范围决定；两者不一致时以业务影响为主并在报告里说明理由，避免出现“评分中等但可以直接读到全部订单”的荒唐结论。等级分为严重、高、中、低与提示五档，每档给出判定标准，便于横向比较。

一份可交付的报告至少包含以下部分：项目概述与授权范围，写清资产清单、时间窗口与未覆盖项；测试方法与工具版本；风险统计与趋势；漏洞详情，每条包含编号、名称、等级、评分、受影响资产、前提条件、复现步骤、请求与响应证据、影响分析、修复建议；业务逻辑与合规观察；修复建议汇总与优先级；复测记录与结论；附录，放测试账号清单、数据处置声明与免责说明。复现步骤要能让一个没参与测试的开发照着做一遍，请求示例中的域名统一写成 example.com，参数值脱敏但保持结构，截图带时间戳并打码。复测只重放原始验证请求并回归相邻功能，结论分已修复、部分修复、未修复三种，附复测时间与复测人。

收尾：把痕迹收干净

测试结束当天完成四件事：停用或删除测试账号并重置相关口令；删除上传的测试文件与创建的测试数据，逐条核对清单；清理本机的 Burp 项目文件、导出的报文与截图，项目文件里含有完整 Cookie 与个人信息，不能留在共享目录；把 Burp 的 CA 证书从测试浏览器中移除。做完出具一份数据销毁确认单，写明销毁对象、时间、执行人与见证人，随报告一起归档。报告与证据按合同约定的期限保存并加密，分发范围限定在项目相关人，未经书面同意不得用于演示、培训或任何公开渠道。

小结

Burp Suite 把代理、重放、批量请求与扫描放在同一份流量之上，效率来自这种共享，风险也来自这种共享：一条没控制好的 Intruder 任务就足以让生产环境报警。授权书、Scope 与限速是三条必须始终在场的约束，Repeater 是确认漏洞的主战场，Scanner 只是提供线索的助手。把每条结论都做成可复现的最小证据，把测试数据与账号清理干净，报告才真正具备交付价值。
