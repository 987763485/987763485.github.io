TypeScript 3.5 与 3.6 新特性

本文属于《TypeScript 学习路线》第 44/74 篇
上一篇系列目录下一篇

TypeScript 的版本号跑得比不少团队的升级节奏还快。本文写于 2018 年 10 月，此时 3.2 刚发布不久，标题里的 3.5 与 3.6 在官方仓库中还只是远期编号：截至本文写作时，TypeScript 3.5 与 3.6 尚未发布，本文讨论的是社区提案、路线图与可能的方向，不是可用特性。如果你正在用 3.x 写服务端代码，想知道下一个版本值不值得等，这篇前瞻可以帮你把预期放到合理位置。

先把题目说清楚

2018 年的 TypeScript 保持着大约每两三个月一个 minor 的节奏：3.0 在 7 月底，3.1 在 8 月底，3.2 在 9 月底。按这个节奏往后推，尚未发布的 3.5 与 3.6 只能排到 2019 年，具体月份没人能提前给出。标题里的两个版本号更像一个坐标，标记“再往后两三个 minor 的时间点”，而不是两份已经写好的功能清单。

开源项目的 roadmap 是意图，不是合同：写在 milestone 里的条目会被推迟甚至取消，讨论热度高的提案也可能因标准未定而搁置。判断一个特性会不会进某个版本，可靠的办法是看三样东西：有没有设计文档与实现 PR，发布说明有没有列进 Breaking Changes，设计会议纪要有没有形成结论。只看社区讨论，很容易把“大家希望有”误读成“下个版本就有”。

下面先回顾 3.0 到 3.2 这条基线，再讨论两个远期版本上可能发生的变化。凡涉及 3.5 与 3.6 前瞻的部分，都只描述方向，不给日期，也不列“官方承诺”的 API。

基线：3.0 到 3.2 给了我们什么

3.0 带来两件影响工程结构的事：项目引用与 unknown。项目引用让一个仓库里的多个包各自持有 tsconfig.json，根配置只编排依赖，tsc -b 按依赖顺序增量构建，声明文件被下游复用。对单体仓库来说，这是把“全量检查”变成“只检查改动过的包”的关键一步。

unknown 则是对 any 的纠偏。any 是双向逃生舱，既能赋给别的类型，也能从别处赋进来；unknown 只保留“任意值都能赋给它”，要使用必须先证明类型，逼迫调用方在边界处做检查。

3.1 最实用的一项改进，是映射类型可以作用在元组和数组上。以前对元组做映射会丢掉长度信息与下标类型，3.1 之后映射结果仍是元组，元素位置一一对应。

3.2 补上了两块短板。一是 strictBindCallApply，让 bind、call、apply 也接受严格的参数检查，在此之前这三个方法几乎是类型系统里的黑洞。二是 bigint 类型支持，配合 target: esnext 可以直接标注大整数，不必用 any 兜底。

这三条基线决定了未来版本的改进空间：增量构建的上限、边界代码的风格，以及类型表达能力的边界。

3.5 前瞻之一：类型系统性能与增量构建

讨论 3.5 时，最确定的方向不是新语法，而是性能。类型检查本质是整程序分析：收集声明、解析依赖、对每个表达式做推断。项目越大成本越明显，而且同时压在 CI 的 tsc 和编辑器的每次按键上。

性能痛点集中在三处。一是声明文件规模，中等规模项目的 node_modules 里 .d.ts 往往比业务代码多一个数量级，检查时间大量花在别人写的类型上。二是类型实例化开销，深层嵌套的条件类型与映射类型会触发大量中间类型。三是增量粒度，tsc -b 能跳过未变化的包，但包内部改一个文件仍要重查整包。

这些都是长期议题，官方做法是收集可复现仓库、逐个优化热点，而不是发一个版本宣布“性能问题已解决”。所以对 3.5 前瞻的合理预期是：包含一批针对性修复与语言服务优化，但不会有“快多少倍”的公开承诺。

开发者能做的是把性能变成可度量的数字。tsc --extendedDiagnostics 会打印解析、绑定、检查各阶段耗时与内存占用，把它记进升级清单，每次升 minor 前后各跑一次，就能看出趋势。

如果某个包的检查时间异常，优先怀疑类型写法：给递归类型加深度上限、避免在热路径上做大规模条件类型分发、把过大的联合类型拆开，这些手段在 3.2 上就已经有效。

3.5 前瞻之二：装饰器标准化的讨论

装饰器是另一个会被反复提起的话题，因为它牵扯两套语义。TypeScript 现有的装饰器是多年前基于当时提案实现的实验性语法，要显式打开开关；TC39 的提案这些年改过好几轮，从能否带参数到私有成员怎么处理，结论都与早期版本有出入。

这两个开关是当时服务端框架的日常：控制器、依赖注入、ORM 实体几乎都靠装饰器加元数据描述。也正因为生态依赖太深，TypeScript 团队的态度一直克制：跟随标准，但不抢先破坏存量代码。标准未定稿前，实验性装饰器按原语义工作；即便将来引入标准语义，更可能新旧并存，用编译选项区分，而不是某天突然改掉求值顺序。

由此可以得出一个实用结论：把 3.5 前瞻当成“装饰器要大改”的信号去提前重写代码，没有依据。值得做的准备是把装饰器逻辑收敛到少数文件，让业务代码不依赖元数据细节，迁移成本就被关在小范围内。

标准装饰器提案在本文写作时仍处于讨论与调整阶段，不是 TypeScript 的现有语义。看到“下一个版本支持标准装饰器”这类说法，先去找提案文档与实现 PR，找不到就当作猜测。

3.6 前瞻之一：更严格的检查与配置演进

TypeScript 的严格检查不是一次性给的，而是一年年往里加。strictNullChecks 在 2.0，strictFunctionTypes 在 2.6，strictPropertyInitialization 在 2.7，strictBindCallApply 在 3.2。每次新增都遵循同一套流程：先作为独立开关发布，收集一两个版本的反馈，再讨论要不要并入 strict 这个总闸。

沿着这条线看 3.6 前瞻，合理的预期是“继续有小步的、可关闭的严格检查”，而不是某个具体开关的名字。名字和触发条件在正式发布前都可能变，本文不去猜。对工程团队来说，真正有用的动作是把配置写清楚，而不是依赖一个笼统的 strict: true。

把子项显式列出来有两个好处。一是升级时能一眼看出哪个开关改变了行为，排查“为什么突然报错”有据可依；二是团队可以按模块逐步收紧，新代码全开、老代码先关 strictPropertyInitialization，而不是一刀切。

严格检查的收益主要体现在边界上：DTO 字段、配置解析结果、外部接口返回值，这些地方开严格检查能立刻抓到问题；纯计算逻辑内部收益往往不如预期。按这个优先级排升级计划，比追求全仓库零 any 更现实。

3.6 前瞻之二：编辑器与语言服务

编译器之外，还有一半体验来自语言服务。编辑器里的补全、跳转、重命名、错误提示，背后是一个长期运行的进程，它维护着项目状态的增量视图。版本升级对开发者的感知，很多时候不是“多了一个语法”，而是“补全更准了”“错误提示的位置对了”。

改进方向可以描述：更快的增量诊断，让大仓库改一行不必等整包重查；更精确的错误定位，把报错缩小到具体一段；更安全的自动导入，避免跨包引用引入循环依赖。具体到 3.6 前瞻有哪几项，本文不做预测，这类改动常以零散 PR 合入。

对团队来说，可操作的是把编辑器的 TypeScript 版本固定下来。VS Code 默认使用自带版本，可能与项目依赖不一致，于是出现“本地不报错、CI 报错”的经典问题。把工作区指向项目内的编译器即可消除这类差异。

配置放在 .vscode/settings.json，重启编辑器后生效；它不能替代 CI，但能让本地诊断与流水线一致。

社区呼声：可选链、空值合并与联合类型收窄

前面几节讨论的是官方节奏，这一节讨论社区愿望。被提及最多的三项是可选链、空值合并，以及更聪明的联合类型收窄。

可选链与空值合并在本文写作时都还是 TC39 的提案，尚未进入语言规范。TypeScript 对这类语法的态度一贯谨慎：不自造语法，等标准定稿再实现。一旦编译器和标准走岔，迁移成本会落到所有使用者头上。所以正确表述是“社区长期讨论的提案”，而不是“下个版本就能写”。

这里的 == null 是有意为之，它同时匹配 null 与 undefined，比 === undefined 更贴合“缺省”的语义。把它封装成小函数，比在每个调用点展开判断更好维护。

联合类型收窄要分两面看。基于判别属性的收窄在 3.2 上已经很成熟，给联合类型加一个字面量字段，switch 之后每个分支都会自动收窄。真正不足的是高阶函数：传给 filter 的回调即使做了判断，编译器也不会收窄结果数组的元素类型，必须写成显式的类型守卫。

社区还希望编译器能根据返回值自动推断守卫、对更多模式做控制流分析，这些都在讨论中，没有时间表。现阶段把守卫写成具名函数复用，收窄逻辑就集中在一处。

版本策略：锁定、跟踪、不冒险

面对不确定的路线图，第一原则是锁定。typescript 写精确版本放进 devDependencies，锁文件提交进仓库，CI 与本地用同一个版本。minor 之间会有行为变化，语义化版本号只保证没有大改，不保证类型检查结果不变。

第二原则是跟踪发布说明。升级前读一遍 release notes，重点看 Breaking Changes 与更严格检查两节，把相关条目摘出来评估影响面。多数升级失败不是语法不兼容，而是检查变严后暴露了历史遗留问题。

第三原则是不拿 nightly 上生产。typescript@next 适合做兼容性预演：独立分支装 nightly，跑一遍 --noEmit，看未来的严格检查会不会打到自己。但放进生产依赖，等于把构建稳定性交给每天变化的包。

类型定义包也要一起看。社区维护的 @types 包通过 typesVersions 字段声明支持的编译器版本范围，3.1 起这个机制已经可用。升级之前先确认关键依赖的类型包有没有声明支持新版本，否则会出现“编译器升了、类型包还停在旧语法”的尴尬。

升级策略：小步走、双版本 CI

升级本身应该小步。一次一个 minor，每次只处理一类问题，比攒到年底跳两个版本好排查。顺序上也有讲究：先升级编译器、跑 --noEmit 看类型错误，再改代码，最后才打开新的严格检查。把“编译器行为变化”和“代码写法变化”混在一次提交里，出问题时很难定位。

CI 里同时跑两个版本，是成本最低的预警手段。一个版本是当前生产使用的，另一个是准备升级的目标版本，两边都只做类型检查，不产出构建物。

差异集中在少数文件就直接改；铺开到几十个文件，说明代码大量依赖隐式推断，应先补类型标注再升级。回滚方案也要提前想好：升级放独立分支，锁文件跟着走，出问题切回旧分支即可。

至于 3.5 与 3.6 前瞻，现阶段不需要为它们做任何代码准备。锁定版本、搭好 CI 矩阵、把装饰器与类型守卫收敛到少数文件，这些动作对任何未来版本都有效，也不依赖未发布的特性。

小结

TypeScript 3.5 与 3.6 在本文写作时尚未发布，任何功能清单都只能算推测。可讨论的方向有三类：类型系统与增量构建的性能优化、装饰器标准化的推进、严格检查与语言服务的打磨，都属于长期议题，不会在某个版本一次性完成。可选链、空值合并与更智能的收窄仍是提案，落地时间未知。对团队而言，正确姿势是锁定版本、读懂发布说明、用双版本 CI 做预警，把 nightly 留在预演分支。路线图不是承诺，等正式版发布后再评估，比提前下注更划算。
