Go 锁竞争与性能优化

本文属于《Go 语言与工程》第 51/78 篇
上一篇系列目录下一篇

一个用 goroutine 写出来的服务，功能测试全过，压测时 QPS 却卡在某条水平线上不动，P99 还在抖。profile 一拉，时间既不在 SQL 上，也不在 JSON 序列化上，而是排在一行 mu.Lock() 上。这是并发程序最常见的一类问题：不是逻辑错，而是大家在排队。

本文面向会写 goroutine 和 sync.Mutex、但对“为什么慢、慢在哪、怎么改”还没有方法论的读者，按“先测量、再定位、后改锁、最后回归”的顺序展开。

锁竞争是什么

临界区是那段“同一时刻只允许一个 goroutine 进入”的代码，sync.Mutex 的 Lock 与 Unlock 把它围起来。没有第二个 goroutine 同时到达时，加锁只是一次 CAS 加一次写，开销在几十纳秒的量级，轮不到它当瓶颈；一旦有人同时到达，后来的就必须等，这才产生竞争。

等待不是忙等。Go 的 Mutex 拿不到锁时会把当前 goroutine 挂到内部信号量上，由 runtime 把它 park 起来，让出 P 去跑别人；解锁时再 unpark 一个等待者，放回运行队列。这一来一回涉及调度器，可能还涉及线程的休眠与唤醒，成本远高于临界区里的几条指令。更隐蔽的成本在缓存：锁和它保护的数据在多个核之间来回传递，每次换手都要把 cacheline 重新拉一遍，核越多、争得越凶，这部分开销越大。

但“有竞争”不等于“该优化”。判断标准只有一个：这段等待是否真的吃掉了吞吐，或者拉高了尾延迟。常见信号有三个：CPU 利用率不高而延迟高，加压后 QPS 不涨；平均延迟尚可，P99 却随流量峰值同步跳高；火焰图里大量时间落在 sync.(*Mutex).Lock 与 runtime 的 semacquire 上。出现信号再往下查，否则改锁只是凭感觉。

先测量：mutex profile、block profile 与 trace

运行时有两条阻塞采样线。mutex profile 只统计 sync.Mutex 与 sync.RWMutex 的争用，记录争用次数（contentions）和等待时间（delay）。block profile 覆盖更宽，channel 收发、select、sync.WaitGroup 以及锁引起的阻塞都会记进去。两者默认关闭，因为采样本身有开销。

采样有两条必须知道的语义。第一，它是抽样而不是全量计数，delay 会按比例放大，所以只看相对排名；第二，mutex profile 记录的是等待方，栈顶通常就是那行 Lock()，它说明“谁在等”，不说明“谁持有太久”。

后者要靠 trace 补。go test -trace trace.out 配合 go tool trace trace.out，每个 goroutine 都有一段 Synchronization blocking 区间，把它和同时刻在跑的 goroutine 对起来，就能区分是等的人多，还是持锁的人干了太久。这两种情况在 mutex profile 上长得一样，处理方式却相反：前者减少争用，后者缩短临界区。

Mutex 的两种模式：正常与饥饿

Go 1.9 起，sync.Mutex 内部有正常模式和饥饿模式两种状态，这能解释很多“临界区明明很短，P99 还是有尖刺”的现象。

正常模式下，解锁会唤醒等待队列里的一个 goroutine，但被唤醒的人不保证拿到锁：它要和正在自旋的新来者竞争。新来者已经在 CPU 上跑着，通常更快，这种行为叫插队（barging）。插队减少了上下文切换、提高了吞吐，代价是等待者可能反复被抢。为了不让等待无限拖长，正常模式还会自旋若干次，赌临界区马上就要结束，省掉一次 park/unpark；自旋只在多核且没有其他等待者时才有意义。

饥饿模式是补丁：等待超过 1 毫秒，锁就切到饥饿模式，解锁时直接把锁交给队首等待者，新来的 goroutine 不自旋也不插队；等队列空了，或者队首等待时间已小于 1 毫秒，再切回正常模式。所以饥饿模式严格 FIFO，延迟可预期，吞吐下降。

这段实现给写代码的人三点指导。其一，临界区里一旦有 I/O、RPC、日志落盘这类慢操作，mutex 基本会长期停在饥饿模式，一个慢请求会拖住后面一串，比“锁有点多”严重得多。其二，临界区短而并发高时，正常模式配合自旋表现不错，不要一看到竞争就换方案。其三，不要自己用 atomic 拼自旋锁，自旋占着 P 不放，只会把 CPU 烧掉。

减小临界区

优化锁的第一手段不是换原语，而是让锁保护的东西变少。原则有四条：只锁真正共享的可变数据；锁内不做 I/O；能拆的锁拆开；读多写少再考虑读写分离。

注意这里把 defer c.mu.Unlock() 换成了显式 Unlock。Go 1.11 的 defer 还没做开放编码优化，热点路径上这点开销测得出；但只在确实测出热点、且函数没有多条返回路径时才这么写，漏掉一个 return 就会死锁。

另外两种缩小方式：一是把只读数据复制出来再处理，锁内只拷 slice 头或指针，锁外遍历，前提是元素不会被就地修改；二是按职责把一把大锁拆成几把。拆锁要小心加锁顺序，所有代码路径上的获取顺序必须一致，否则就是死锁的温床。

RWMutex：读多写少才划算

sync.RWMutex 允许多个读者并行、写者独占，看起来像 Mutex 的升级版，实际有明确的适用条件。

第一，只有读占绝对多数时才划算。RLock 并不免费：它要原子地修改同一个 readerCount，所有读者都在写同一块内存，多核下这条 cacheline 依然来回弹。临界区极短、读写比又不高时，RWMutex 往往比 Mutex 更慢。经验上读写比在十几比一以上、读临界区有一定长度，才值得换，而且要靠基准测试确认。

第二，写者会被读者挤压。一旦有写者在等，后续 RLock 会被挡住，这缓解了写饥饿，代价是读者延迟突然变长：高频短读的代码会把写推得很后，表现为偶尔一次写要等很久。

第三，也是最容易出事的：读锁不能嵌套。下面这段单看没问题，两个 RLock 都能成功；但此刻只要有一个 Lock 在排队，第二次 RLock 就会被阻塞，而第一次读锁还没释放，写者等读者、读者等写者，整个服务卡死。

这类死锁在低并发下复现不出来，一上量就炸。规则很简单：持有读锁期间，不要调用任何可能再次获取同一把锁的函数，包括回调、接口实现和懒加载。另外，RWMutex 不支持把读锁升级成写锁；需要“读到没有就写入”的逻辑，只能先放读锁再拿写锁，并且拿到写锁后重新检查状态，因为中间可能已被别人改过。

分片锁：把一把锁拆成多把

当竞争来自“很多 goroutine 操作同一张大表的不同 key”时，缩小临界区救不了你，因为每个操作本来就很短。这时要减少共享：按 key 把数据分成 N 份，每份一把锁，冲突概率在分布均匀时降到约 N 分之一。

分片数怎么定？先看并发写热点有多少，再看 GOMAXPROCS。太少没效果，太多则全量遍历要锁 N 次、快照变贵。实践中从 16 或 32 起步，用 -cpu=1,4,8 的基准对比，够用就停。退化有两个来源：哈希不均（比如 key 是递增 ID、哈希函数又太弱），以及必须跨分片原子完成的操作。后者一旦出现，要么退回全局锁，要么改成“分片累加、读取时汇总”的最终一致口径。

读多写少、key 集合稳定时，sync.Map 能省掉自己分片，但它的边界另文《Go sync.Map 的场景》有专门讨论。

原子操作：能不加锁就不加锁

共享状态如果只是一个字长，就没必要用锁。sync/atomic 提供了 AddInt64、LoadInt64、StoreInt64、CompareAndSwapInt64、SwapInt64，以及用来发布不可变值的 atomic.Value。

Go 的原子操作是顺序一致的：编译器不会重排，硬件层面也不需要手写屏障，这比 C++ 那套 relaxed/acquire/release 简单。它的价值在于消灭“等待”，而不是让指令变少。

两个坑要记住。其一，32 位平台上 64 位原子操作要求地址 8 字节对齐，否则直接 panic；把 int64 放在结构体第一个字段是安全写法，只在 amd64 上测过就上线，换到 32 位环境会崩。其二，不要用原子操作拼复杂逻辑：“先 Load 判断、再 Store 修改”不是原子的，中间会被插进来；要保证复合语义只能写 CAS 循环，而 CAS 循环在冲突激烈时一直空转重试，性能未必比 Mutex 好，正确性还更难论证。原子操作适合计数、标志位和一次性指针发布，不适合实现队列、栈与引用计数这类要处理 ABA 和内存回收的结构。

sync.Pool：减少分配，而不是减少竞争

sync.Pool 常被当成“对象池”甚至“连接池”，它真正的目标只有一个：复用临时对象，降低分配次数和 GC 压力。它没有容量上限、没有超时、不保证 Put 进去还能 Get 出来，也无法用来限流。

关键行为是：池中的对象在每次 GC 时都可能被清空。这意味着不能把需要长期存活的状态放进去；也不能假设预热之后命中率就是百分之百，池子的价值只在于同一轮 GC 之间的反复复用。所以它缩短延迟的作用有限，降低分配速率和 GC 频率的作用明显，用 -benchmem 看 allocs/op 比看 ns/op 更能说明问题。

还有一个隐蔽的坑：Put 回去的对象若还被外部引用，下次 Get 出来就产生别名，两个请求写同一块内存。规则是 Put 之后不再持有该指针，也不交给会异步使用的地方。

无锁化：让别人不共享

比“锁得更细”更彻底的是取消共享，常见三条路径。

第一条是通过通信共享内存：把状态收归一个 goroutine 独占，其他 goroutine 用 channel 发请求、收结果。状态修改天然串行，不需要锁，逻辑也好推理。代价是每次操作两次 channel 传递，吞吐上限等于那个 goroutine 的处理能力，缓冲与背压要提前设计。这条路适合状态机、会话注册表这类场景。

第二条是每个 goroutine 独占一份数据，最后合并。批量统计、分桶聚合都是这一类：worker 在局部变量上累加，结束后统一汇总，全程没有共享写入，连原子操作都省了。

第三条是写时复制：读路径完全不加锁，写路径构造新副本，算完原子地替换指针。适合配置、路由表、黑白名单这种读极多、写极少、数据量不大的场景：

前提是 *Config 发布后不再被修改，否则读方会看到撕裂的状态。写时复制每次都要复制整份数据，量大时不划算，应回到分片或 RWMutex。

一个案例：从全局 Mutex 到分片计数

场景很普通：接口里给每次请求打点，最初是全局一把锁加一个 map。

压测现象是：并发从 8 加到 64，QPS 基本不动，mutex profile 里 record 的 contentions 很大而 delay 不大。这个组合说明等待次数极多、单次等待极短，是典型的高频短临界区，也就是纯争用，而不是有人持有太久。trace 里能看到大量 goroutine 反复进出阻塞区间，没有谁长期占锁。

改法有两级。只需要一个单调递增的总数，直接换 atomic.AddInt64，代码最短。要按 path 分组，map 本身不能并发写，只能分片：按 path 哈希到 32 个分片，每片一把锁一张 map，读时汇总，即前文的 Counter。

选择顺序可以固化成一句话：先问能不能不共享，再问能不能不加锁，然后问能不能少锁一点，最后才问能不能多几把锁。反过来从分片开始改，往往只是引入不必要的复杂度。

小结

锁竞争的成本不在加锁指令，而在等待、调度与 cacheline 来回传递，所以必须先测量再优化：mutex profile 看争用次数与等待时间的比例，block profile 看所有同步原语的阻塞，trace 用来区分“等的人多”还是“持有太久”。

contentions 大而 delay 小，方向是减少共享，比如原子操作、分片、独占；delay 大而 contentions 小，方向是把 I/O、日志、序列化搬出临界区。

sync.Mutex 的饥饿模式解释了长临界区为什么把 P99 拉成一条长尾；RWMutex 只在读远多于写时才成立，而且读锁嵌套遇到排队的写者会直接死锁。

sync.Pool 解决的是分配压力而不是竞争；原子操作只适合单个字长的状态。任何改动都要用同一份基准、-cpu 梯度、-race 和复测的 profile 验证，只看一次 ns/op 不算验证。
