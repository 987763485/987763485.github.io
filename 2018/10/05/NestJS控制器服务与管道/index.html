NestJS 控制器、服务与管道

本文属于《TypeScript 学习路线》第 65/74 篇
上一篇系列目录下一篇

NestJS 在 2018 年已经走到 5.x，它把 Angular 那套模块、装饰器与依赖注入搬到了 Node 服务端，默认跑在 Express 适配器之上。本文从一次普通的 HTTP 请求出发，依次讲清楚模块、控制器、服务与管道各自负责什么、边界在哪里，以及它们如何协作完成参数校验与业务处理。读者需要会写 Express 路由、了解 TypeScript 的基本类型；读完后应当能用 NestJS 5 搭出一个结构清晰、带 DTO 校验的 CRUD 服务，并避开几个最常见的注入与校验陷阱。

从 Express 的空白画布说起

Express 给了我们路由和中间件，然后就没有然后了。项目一大，路由文件里混着参数解析、SQL、权限判断和错误拼装，每个人都按自己的习惯分层，最后没人说得清一次请求经过了哪些步骤。Koa 的洋葱模型更优雅一些，但同样不提供结构上的约定，分层靠团队自觉。

NestJS 的思路是先把结构定下来：控制器只负责把 HTTP 请求翻译成方法调用，服务承载业务逻辑，管道负责进入方法之前的转换与校验，模块把一组相关的控制器和服务圈在一起，并声明对外暴露什么。框架默认使用 Express 作为 HTTP 适配器，中间件生态照旧可用；也可以换成 Fastify，业务代码基本不动。这一切建立在 TypeScript 的装饰器与元数据反射之上，工程里需要打开 experimentalDecorators 与 emitDecoratorMetadata，并在入口引入 reflect-metadata。

对比一下：Express 里写 app.get(‘/users/:id’, handler)，取值、校验、查库、拼响应全在一个函数里；NestJS 里写 @Controller(‘users’) 加 @Get(‘:id’)，方法签名直接声明需要的参数，框架负责从请求里取值、跑管道、调用服务、序列化返回值。自由度换成了约束，代价是要先理解它的几个概念，收益是团队里所有人写出来的代码长得差不多。

版本上，本文对应 NestJS 5.x、Node 10 与 TypeScript 3.0/3.1。5.x 的小版本之间也有细节差异，网上示例版本混杂，照抄容易踩空，遇到对不上的地方先看安装的 @nestjs/common 版本号。

模块：先划边界，再写代码

@Module 装饰器的元数据就四项：imports、controllers、providers、exports。controllers 里声明的控制器会注册路由；providers 里声明的东西进入该模块的注入容器；exports 决定哪些 provider 可以被其他模块使用，没有出现在 exports 里的 provider，别的模块即使 import 了这个模块也拿不到；imports 则用来引入其他模块导出的能力。

每个应用至少有一个根模块，通常叫 AppModule，它把各个特性模块串起来。特性模块对应一个业务领域，比如用户、订单。判断边界的方法很朴素：如果两组代码共享同一批 provider 且总是一起变化，就放在一个模块；如果 A 模块需要的东西只是 B 模块内部实现的细节，就不要导出，让 A 通过 B 暴露的服务方法去访问。exports 是一份契约，导出得越多，日后重构越难。

循环依赖在模块层面也会出现，比如 UsersModule 要用 OrdersModule 里的服务，OrdersModule 又反过来要读用户信息。NestJS 提供 forwardRef 打破加载顺序上的死结，模块与服务两侧都要写：imports 里用 forwardRef(() => OrdersModule)，构造函数里用 @Inject(forwardRef(() => OrdersService))。但这只是让代码能跑起来，真正的解法通常是把双方共同依赖的部分抽成第三个模块，或者把依赖改成单向 —— 循环依赖往往说明边界划错了。

如果某个 provider 几乎每个模块都要用，比如配置、日志，可以用 @Global() 把模块声明为全局，只需在根模块 import 一次；但它会模糊依赖关系，用多了等于没有模块边界，能显式 import 就显式 import。

控制器：把 HTTP 请求翻译成方法调用

@Controller(‘users’) 给这一组路由加上前缀，方法上的 @Get、@Post、@Put、@Delete 决定 HTTP 方法与剩余路径。参数装饰器是控制器里最省事的部分：@Param(‘id’) 取路径参数，@Query() 取整个查询对象，@Body() 取请求体，@Headers(‘authorization’) 取单个请求头。它们都可以带参数名，不带时拿到整个对象。

返回值不需要手动 res.json，NestJS 会把普通对象序列化成 JSON；POST 默认返回 201，其余默认 200，需要别的状态码用 @HttpCode(204)。响应头可以用 @Header(‘Cache-Control’, ‘no-store’) 静态声明。

@Res 是一条分水岭。一旦在方法签名里注入 @Res()，NestJS 就认为你要自己接管响应，自动序列化与状态码都不再发生，必须自己调用 res.json() 或 res.send()，否则请求会一直挂着。这条路径适合下载文件、需要精细控制响应头、或者要复用已有 Express 处理器的情况，代价是失去统一性：拦截器与异常过滤器对响应的加工会绕开，测试也更啰嗦。原则是能返回对象就返回对象，表达力不够时才下沉到 @Res。

还有一条容易忽略的规则：路由按声明顺序注册，静态路径要写在带参数的路径前面，否则 @Get(‘:id’) 会把 /users/page 里的 page 当成 id，后续的类型转换直接失败。

服务与依赖注入

服务就是一个加了 @Injectable() 的普通类。装饰器本身没有魔法，是 emitDecoratorMetadata 把构造函数的参数类型写进了元数据，NestJS 启动时读取这些元数据，知道某个类需要哪些依赖，再从容器里取出实例塞进去。所以构造函数注入必须写类型：constructor(private readonly usersService: UsersService)，类型省了框架就不知道注入什么。

默认作用域是单例：整个应用只有一个 UsersService 实例，所有请求共享。这是好事，连接池、缓存、配置都该挂在单例上；反过来说，“当前用户”“本次请求 ID”这类状态不能放在服务的实例属性里，否则会在并发请求之间串味。确实需要请求级实例时可以声明 request 作用域，但实例会沿着依赖链向上传播，写法和性能都有代价，优先用参数把上下文传进去。

provider 不一定是类，NestJS 支持三种自定义写法：useClass 换实现，比如测试时用内存版仓储；useValue 直接给现成对象，适合配置、常量、第三方客户端；useFactory 按需构造，并用 inject 声明工厂依赖。token 默认是类本身，非类 provider 要自己起一个字符串或 Symbol，注入时用 @Inject(‘TOKEN’) 取。

管道：进入业务前的最后一道加工

管道是一个实现了 PipeTransform 的类，transform(value, metadata) 拿到参数值和一个描述对象，返回转换后的值，或者抛异常。它只做两件事：把字符串转成需要的类型，以及检查值是否合法。不合法就抛 BadRequestException，请求根本进不了服务层。

内置的 ParseIntPipe 正好替掉控制器里的 parseInt：参数写成 @Param(‘id’, new ParseIntPipe()) id: number，非法输入直接 400，控制器里不再需要防御式解析。NestJS 5 内置的管道数量有限，真正的主角是 ValidationPipe，但它需要 class-validator 与 class-transformer 配合。

DTO 是一个带校验装饰器的类，注意必须是类而不是 interface：interface 在编译后被抹掉，运行时没有任何元数据，校验器无从下手。字段上写 @IsString()、@IsEmail()、@Length(2, 20)、@IsInt()、@Min(0)、@IsOptional()，嵌套对象用 @ValidateNested() 配合 @Type() 转换。

ValidationPipe 的几个选项决定了它的性格：transform 为 true 时把普通对象转成 DTO 实例并做类型转换，比如把 “18” 变成 18；whitelist 为 true 时剥掉 DTO 里没声明的字段；forbidNonWhitelisted 为 true 时不剥而是直接报错。生产上我一般全局开启 transform 与 whitelist，安全要求高的接口再加 forbidNonWhitelisted。

管道的生效顺序是：全局 → 控制器 → 方法 → 参数，同一层级声明多个时按书写顺序执行。全局挂一个 ValidationPipe 就够了，别在参数上再重复挂一个，值会被转换两次，行为还未必一致。更常见的问题是全局管道与 @UsePipes 上的选项不同，导致部分接口的白名单行为跟预期不符。

异常：让错误有一致的形状

在服务里抛 new Error(‘…’) 是最容易犯的错：NestJS 会把它当成未预期错误返回 500，客户端拿不到任何有用信息。正确的做法是抛 HttpException 或其子类：NotFoundException、BadRequestException、UnauthorizedException、ForbiddenException、ConflictException，构造函数接受消息字符串或 { message, error } 对象，也可以显式指定状态码，如 new HttpException(‘参数不合法’, 422)。

异常抛出后由异常过滤器接管，默认实现把 HttpException 转成 { statusCode, message, error } 的 JSON，非 HttpException 一律 500 并记录堆栈。所以“统一错误结构”有一半是免费的，剩下的一半，比如业务错误码、国际化、日志埋点，需要自定义过滤器，那属于请求生命周期的后半段，本文不展开。

一条实践建议：服务层只抛语义化异常，不拼表现层细节；控制器保持薄，错误措辞集中管理，客户端才能稳定依赖这套结构。

配置与环境：dotenv 加一个薄封装

2018 年这个时候，官方还没有独立的配置模块，常见做法是 dotenv 加一个自己写的 ConfigService。dotenv 读取 .env 文件写入 process.env，之后任何地方都能读到；把它包成 provider 的好处是类型明确、可注入、可测试，也避免业务代码里到处散落 process.env.XXX。

要点有三：.env 不进版本库，仓库里放一份 .env.example 说明需要哪些键；配置在启动时一次性读取并校验，缺关键项就直接失败，不要等第一个请求才发现数据库地址是空的；测试里用 useValue 覆盖 ConfigService，而不是临时改环境变量。

把它注册成可注入的 provider，实践中的做法是建一个 SharedModule，providers 与 exports 都写上 ConfigService，需要的地方 import 它；直接在根模块里声明也能用，但其他模块要靠全局模块才拿得到，依赖关系就不那么直观了。

目录组织：按模块切，不按角色切

一个模块一个目录，目录里放这个模块的全部东西：users.module.ts、users.controller.ts、users.service.ts，加上 dto/ 与 entities/。跨模块共享的管道、过滤器、工具函数放 common/。

不要按技术角色建全局的 controllers/、services/ 目录。文件少的时候看着整齐，模块一多就要在三个目录之间来回跳，改一个功能开五个文件夹，而且依赖关系全藏在 import 里，看不出谁属于谁。

分层也别过度。控制器 → 服务 → 仓储是够用的三段；再往下拆 usecase、domain、infrastructure，除非团队真的需要，否则只是给 CRUD 加仪式感。判断标准是这一层有没有隔离变化：换数据库时只动仓储，加缓存时只动服务，就算分层有效；如果每次改需求都要把所有层改一遍，这些层就没有提供价值。

测试：复用模块定义，替换边界

@nestjs/testing 的 Test.createTestingModule 复用生产代码的模块定义，并允许替换 provider。单元测试里最常用的手法是给服务一个 mock：providers 数组里写 { provide: UsersService, useValue: mock }，再 module.get(UsersController) 拿到控制器直接调方法，测的是协作契约，不碰数据库。

e2e 测试用 imports: [AppModule] 起完整上下文，配合 supertest 发真实请求。它跑得慢，但能覆盖管道、序列化、异常处理这些单元测试看不到的环节，参数校验这种框架行为恰恰最适合用它验证。注意全局管道要在测试应用上也注册一次，或者改用 APP_PIPE provider 注册，让 e2e 自动继承，后者更不容易漏。

常见坑

第一是 provider 没导出。在 A 模块 import 了 B 模块，注入 B 的服务仍然报 Nest can’t resolve dependencies，先回头看 B 的 exports，而不是怀疑装饰器写错了。

第二是 DTO 写成 interface，或者字段忘了加装饰器。ValidationPipe 不会报错，只是什么都不校验；开了 whitelist 更隐蔽，字段会被全部剥掉，控制器收到一个空对象。

第三是管道重复或选项不一致。全局挂一个，参数上又挂一个，值被转换两次；全局没开 transform 时，@Query(‘age’) 拿到的是字符串，服务里做加法就变成了拼接。

第四是循环依赖。forwardRef 能让应用启动，但请求链路绕圈，后面加缓存或事务时会非常难受，宁可多抽一个模块。

第五是 @Res 之后忘了写响应，或者既 return 又调了 res.json，前者让请求挂起，后者在日志里留下 headers already sent。第六是 tsconfig 漏了装饰器选项或入口漏了 reflect-metadata，启动时报一堆 undefined 元数据错误，这类问题看一眼编译配置就能排除。

小结

NestJS 5 用约束换来了结构：模块声明谁能看见谁，控制器只做 HTTP 翻译，服务承载业务，管道守住入口。provider 默认单例，连接池与配置因此天然共享，但请求级状态必须靠参数传递，不能塞进实例属性。DTO 必须是带装饰器的类，transform 与 whitelist 决定了 ValidationPipe 是类型转换器还是安全边界。@Res 是逃生口而非常规写法，能返回对象就别接管响应。把这些用顺之后，guard、interceptor、filter 才有地方安放，那是请求生命周期的另一半，下一篇再谈。
