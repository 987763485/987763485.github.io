Python 连接 MySQL 与 ORM

本文属于《Python 学习路线》第 23/29 篇
上一篇系列目录下一篇

把一个 Python 服务接到 MySQL 上，看起来只是装个驱动、写几条 SQL，真正上线后出问题的却往往是字符集、事务边界和连接被服务端悄悄掐断这些细节。本文按“驱动 → SQLAlchemy Core → ORM”的顺序把三条路走一遍，示例都基于 Python 3.7、MySQL 5.7、PyMySQL 0.9 与 SQLAlchemy 1.2，可以直接跑。读完之后，你应该能判断手头的项目该停在哪一层，以及哪些坑必须提前躲开。

三种访问方式

Python 访问 MySQL 的路径大致可以分成三层。最底层是驱动，也就是实现 DB-API 2.0（PEP 249）的库。MySQLdb 基于 C 扩展，在 Python 3 上编译安装经常卡在找不到 mysql_config 这一步；PyMySQL 是纯 Python 实现，接口与 MySQLdb 基本一致，Django 里调用一次 pymysql.install_as_MySQLdb() 就能让它冒充 MySQLdb。驱动只认 SQL 字符串和参数元组，返回游标，其余的都不管。

中间层是 SQLAlchemy Core。它仍然以表为中心，但把 SQL 变成了可以组合的 Python 表达式，并且自带连接池、方言（dialect）和结果集封装。你完全可以只把它当作一个更聪明的驱动，不碰 ORM。

最上层是 ORM。SQLAlchemy ORM 和 Django ORM 都把表映射成类、把行映射成对象，用 Session 或 QuerySet 管理对象身份、关系和事务。代价是抽象会泄漏：写得不好就会出现 N+1 查询、隐式提交，以及意料之外的 SQL。

三者的分工其实很清楚。一次性脚本、数据修复、需要精确控制 SQL 的批处理，直接用驱动；报表、多表聚合、要用窗口函数或复杂 JOIN 的查询，用 Core 写更透明；有领域模型、关系多、需要单元测试的业务代码，用 ORM 收益最大。下图是三者共用的运行时结构，区别只在于最上面那一层由谁来拼 SQL。

连接与 DSN

PyMySQL 的 connect() 参数不多，但每一个都值得想一下。charset 必须显式写成 utf8mb4：MySQL 5.7 的默认字符集仍是 latin1，而 utf8 只有三个字节，存不下 emoji 和部分生僻字。connect_timeout、read_timeout、write_timeout 分别约束建连、读、写的等待时间，不设的话一次网络抖动就可能把工作进程挂住。

时区是另一个容易忽略的参数。MySQL 的 TIMESTAMP 在存取时会按会话的 time_zone 换算，DATETIME 则原样存取。如果服务器是 UTC、业务按东八区展示，最稳妥的做法是建连后立刻执行 SET time_zone = '+08:00'，让会话内的换算规则固定下来，而不是依赖服务器默认值。

事务与隔离级别

PyMySQL 在 autocommit=False 时，每条 DML 都处在一个隐式开启的事务里，只有显式 commit() 才落盘，连接关闭或进程退出则回滚。这解释了一个常见现象：脚本里 INSERT 明明没报错，去数据库里却查不到。

连接对象本身也是上下文管理器，with conn: 在正常退出时提交、异常时回滚，但它不会关闭连接，这点和文件对象不同。需要更细的控制时可以显式 conn.begin()，再决定提交还是回滚。

隔离级别决定了并发事务之间能看见什么。MySQL 5.7 的默认级别是 REPEATABLE READ，可以用 SELECT @@tx_isolation 确认。它的特点是在事务第一次读时建立一致性快照，之后同一事务里的普通 SELECT 都读这个快照，所以别人已经提交的修改你也看不见。重复执行同一条统计 SQL 得到不变的数字，往往不是缓存，而是快照。RR 还用间隙锁来防幻读，范围条件更新时锁住的区间比想象中大，两个事务以不同顺序更新相邻区间就容易死锁。

对大多数 Web 业务，把会话隔离级别调成 READ COMMITTED 更符合直觉：每次读都取最新已提交数据，间隙锁也少。做法是建连后执行 SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED。代价是同一事务内两次读可能不一致，所以“先查余额再扣减”这类逻辑必须用 SELECT ... FOR UPDATE 走当前读，而不是靠隔离级别兜底。

SQLAlchemy Core：SQL 与连接池

Core 的入口是 Engine 和 Connection。日常 SQL 用 text() 包一层，命名参数用 :name 的形式传入，这样同一段 SQL 可以在不同方言下复用，也不用数占位符的顺序。

ResultProxy 是对游标的封装，支持按列名取值、fetchone()、fetchall() 和 rowcount。它和游标一样只能顺序消费，遍历完再取就没有数据了；需要多次使用就先转成 list。DDL 和批量写入也走 execute()，多条语句记得包在 engine.begin() 里，它会在退出时提交、异常时回滚。

连接池是 Engine 自带的，默认 QueuePool、pool_size=5、max_overflow=10，也就是单进程最多同时持有 15 条连接。这个数字要乘以 worker 数去和 MySQL 的 max_connections 对账：4 个 worker 各开 15 条，就是 60 条，再加上运维和备份的连接，很容易顶到上限。pool_recycle 要小于服务端的 wait_timeout，pool_pre_ping 则作为兜底，代价是每次取连接多一次往返。

SQLAlchemy ORM：Session 与关系

ORM 的第一件事是把表声明成类。1.2 里的标准写法是 declarative_base() 加 Column，关系用 relationship() 在两端各声明一次，并用 back_populates 互相指向。

query() 返回的是 Query 对象，filter() 只是往表达式树里加条件，直到 .all() 才真正发 SQL，所以链式调用的顺序可以自由调整。Session 还是工作单元（unit of work）：对象改动先留在内存，flush() 时发出 INSERT/UPDATE，commit() 时提交并让对象过期，之后再访问属性会重新查库。这也是为什么提交后打印对象字段会多出一条 SELECT。

Django ORM 对照

如果项目本身就跑在 Django 上，没必要再引一套 SQLAlchemy。Django 2.1 的 Model 已经带上了迁移、admin 和表单校验，日常查询由 QuerySet 承担。声明方式和 SQLAlchemy 大同小异，区别是外键必须写 on_delete，否则 2.x 会直接报错：

QuerySet 同样是惰性的：Post.objects.filter(author_id=7)[:20] 在切片、迭代或 len() 之前不会发 SQL，这既方便拼条件，也容易在循环里反复求值。filter() 是 AND 关系，exclude() 取反，Q 对象表达 OR，F 对象让比较发生在数据库侧，例如 Post.objects.filter(id__gt=F("author_id"))。

解决 N+1 的两个方法是 select_related 和 prefetch_related。前者对应外键和一对一，在 SQL 里用 JOIN，只能用于单值关系；后者对应多对多和反向外键，先查主表再按 IN 查关联表，在 Python 里做拼装。经验是：post.author 这种正向单值关系用 select_related("author")，author.posts.all() 这种反向多值关系用 prefetch_related("posts")。两者可以叠加，但要留意 select_related 的 JOIN 会让主表行数随关联表放大。

另外两个常用手段是 only()/defer() 控制取哪些列，以及 values() 直接拿字典，跳过模型实例化的开销。update() 和 delete() 走的是批量 SQL，不触发 save() 和信号，凡是在信号里做缓存失效的逻辑都要单独处理。

表结构一定要用迁移管理，不要手工在库上改完再回来补代码。SQLAlchemy 侧的工具是 Alembic 1.0，初始化一次之后，每次改模型都生成一个版本脚本：

自动生成只是把 env.py 里的 target_metadata 和数据库现状做对比，它能识别新增表和列，对列类型变更、列重命名、索引改名却经常判断不准，生成的脚本必须逐行看过。Alembic 的每个版本都有 upgrade() 和 downgrade()，后者不写就只能前进不能后退，生产回滚时会很被动。

Django 的命令更简单：makemigrations 生成文件，migrate 应用，showmigrations 看状态，sqlmigrate app 0002 打印将要执行的 SQL。它的迁移文件同样成对提供正向和反向操作，但 RunPython 这类数据迁移的反向函数要自己写。

生产环境的变更顺序比工具更重要。加字段时先加可空列或带默认值的列，让新旧代码都能写；再发布读写该列的代码；最后回填历史数据、加非空约束。删字段反过来：先让代码不再引用，确认没有流量，再删列。大表的 ALTER TABLE 在 5.7 上仍可能锁表或长时间拷贝，安排在低峰期，并提前用 pt-online-schema-change 这类工具评估。回滚预案要和发布一起准备：代码回滚到上一版时，数据库结构必须仍被上一版兼容，所以“先加后删、分两次发布”是基本纪律。

常见坑

字符集。库、表、列、连接四处都可能是 latin1 或三字节的 utf8，只要有一处不对，中文就能存进去而 emoji 报 Incorrect string value。建库时写 DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci，连接串带 charset=utf8mb4，历史表用 ALTER TABLE ... CONVERT TO CHARACTER SET utf8mb4 逐张改并观察索引长度是否超限。

NULL 与空字符串。两者在 MySQL 里不是一回事，NULL = NULL 的结果也是 NULL，必须用 IS NULL；COUNT(col) 不数 NULL，COUNT(*) 才数行。唯一索引允许多个 NULL，却只允许一个空字符串，用空串当“未填”会让第二条插入失败。Python 侧 None 对应 NULL，从库里读出的 NULL 也是 None，判断时用 is None 而不是 == ""。

时间类型。DATETIME 不带时区、范围到 9999 年；TIMESTAMP 按会话时区换算、范围只到 2038 年，还带自动更新特性。订单创建时间用 DATETIME 更稳，跨时区展示在应用层换算。SQLAlchemy 取出的 DATETIME 是 naive 的 datetime，和 datetime.now(timezone.utc) 相减会直接抛 TypeError，两边的时区约定要统一。

连接闲置被断开。MySQL 的 wait_timeout 默认 28800 秒，但云数据库常调到 600 秒甚至更短。池里躺着超过这个时间的连接会被服务端单方面关闭，应用下一次借用就拿到 (2006, 'MySQL server has gone away') 或 (2013, 'Lost connection during query')。对策是把 pool_recycle 设得比 wait_timeout 小，再开 pool_pre_ping；Django 里对应的参数是 CONN_MAX_AGE，设成 0 表示每个请求结束就关连接，虽然多一次握手但最不容易出问题。

事务未提交。驱动层的 autocommit=False、ORM 里忘了 commit()、异常被 except 吞掉，都会让写入静默丢失。排查时先看 SHOW PROCESSLIST 里有没有长时间 Sleep 且持有事务的连接，再看 information_schema.innodb_trx 的 trx_started。

N+1。表现为接口平时很快，数据量一上来就慢十倍。开发阶段打开 SQL 日志（echo=True 或 Django 的 connection.queries），数一数一次请求发了几条 SQL，比上线后再猜有效得多。

选型建议

小项目、内部工具、定时脚本，直接用 PyMySQL 最省事：没有元类、没有 Session 生命周期，出了问题看 SQL 就能定位。业务表超过十来张、关系开始交织、需要单元测试里造对象时，上 ORM 才划算。报表和离线统计建议留在 Core 或原生 SQL，聚合查询用 ORM 表达往往既难读又生成低效 SQL，硬写不如老老实实写 SQL。

无论选哪层，有几条边界要守住。一个请求只用一个 Session，用完关闭；Session 不是线程安全的，也不要跨进程传递，更不能塞进 Celery 任务参数里。Django 与 SQLAlchemy 不要在同一套模型上混用，两个 Session 各自持有对象副本，提交顺序不可控，很容易互相覆盖。事务边界放在服务层，别让每个 Repository 方法自己 commit。连接池参数按 worker 数算总量，别让每个进程都以为自己是唯一的客户端。

小结

Python 连 MySQL 有三层可用：驱动最直接，Core 兼顾 SQL 可控与连接池，ORM 负责对象与关系。连接阶段把 charset=utf8mb4、超时和时区定死，能省掉后面一大半的怪问题。所有值都走参数绑定，批量写入用 executemany() 并按批切分。事务要有明确的开始与结束，REPEATABLE READ 的快照语义和间隙锁值得提前理解。ORM 的性能问题多半来自懒加载，用 joinedload 或 select_related 把 N+1 消掉。表结构交给 Alembic 或 Django migrations，生产变更遵守“先加后删、代码先行、可回滚”。
