Python 日志模块 logging 实践

本文属于《Python 学习路线》第 12/29 篇
上一篇系列目录下一篇

print 在单文件脚本里足够直接，一旦服务跑在后台、被多个进程共享、需要事后追查，短板立刻暴露：没有级别、没有时间、没有来源，也无法按文件切分。本文从 logging 的四个核心对象讲起，依次介绍级别设计、Handler 选择、格式化、dictConfig 配置、多进程写入与异常记录，最后列出常见的坑。示例基于 Python 3.7。读完后，你应能为一个中小型服务搭出一套可直接上线的日志配置。

一、为什么不能继续用 print

print 的问题不在于输出难看，而在于输出的内容无法被系统消费。日志的第一读者是人，第二读者是采集、检索与告警系统，print 对两者都不友好。

  • 没有级别。想临时打开细节、平时只看错误，print 做不到，线上只能改代码重启。
  • 没有时间与来源。一行 订单创建成功 看不出发生在哪一秒、由哪个模块的哪一行打出。
  • 不能分流。控制台给人看，文件要留档，错误要单独告警，print 只能写标准输出。
  • 性能不可控。每次调用都直接写标准输出，量大时同步 I/O 拖慢主流程，也没有便宜的关闭手段。

logging 把这些拆成可配置的部件：级别决定要不要记录，Handler 决定记录到哪里，Formatter 决定长什么样，Filter 决定哪些记录能通过。配置与代码分离后，同一份代码在开发机和线上可以表现完全不同。

二、核心模型：四个对象与一条调用链

  • Logger：业务代码直接调用的入口，负责判断级别、构造 LogRecord、把记录交给自己的 Handler 以及父级 Logger。
  • Handler：负责输出，把 LogRecord 写到流、文件、socket 或队列。一个 Logger 可以挂多个 Handler。
  • Formatter：负责把 LogRecord 渲染成一行文本，决定时间格式、字段顺序与分隔符。
  • Filter：负责过滤，可挂在 Logger 或 Handler 上，按名字、按上下文丢弃记录。

级别则是一组整数常量：DEBUG 为 10、INFO 为 20、WARNING 为 30、ERROR 为 40、CRITICAL 为 50。判断规则只有一条：记录级别大于等于 Logger 的有效级别才会被处理。

flowchart LR
    A[业务代码 logger.info] --> B[Logger 判断级别]
    B -->|低于有效级别| X[丢弃]
    B -->|通过| C[Filter 过滤]
    C --> D[Handler 流输出]
    C --> E[Handler 文件轮转]
    D --> F[Formatter 渲染]
    E --> F
    F --> G[控制台 文件 采集端]

Logger 用点号分层级。getLogger("app.db") 是 getLogger("app") 的子 Logger，app 又是 root 的后代。子 Logger 处理完自己的 Handler 后会把记录向上传递，这就是 propagate，默认开启。所以子 Logger 加一个 Handler、root 又保留一个，一条日志就会打印两遍。

级别也会继承。子 Logger 没设 level 时沿层级向上找，都没有就用 root 的级别，root 默认 WARNING。于是 logger.info 常常什么都不输出，因为 INFO 被 root 挡住了。

配置的目标因此很清楚：入口配一次，Logger 只负责发记录。

三、快速配置：basicConfig 与 getLogger(name)

最小的可用配置是 logging.basicConfig()。它作用于 root Logger，一次性创建 StreamHandler 并设置格式与级别，适合脚本与调试。

有两个细节值得注意。

第一，basicConfig 只做一次。它会检查 root 是否已有 Handler，有就什么都不做。如果某个被 import 的库在模块顶层调用过它，你的配置就被静默忽略，表现为格式与级别都没变。排查时打印 logging.getLogger().handlers 即可确认。

第二，模块里用 logging.getLogger(__name__)，不要直接调 logging.info。后者走 root，记录里没有模块名，也无法单独调级。用模块名作 Logger 名，日志自带 app.api.orders 这样的来源，按包名降噪、按包名开 DEBUG 都方便。

惯例是在模块顶部取一次赋给 logger，Logger 按名字缓存，重复调用不会产生新对象。

局限也很明显：只能配一个 Handler，不支持轮转与环境切换，也不能给不同模块不同级别。它适合脚本，不适合服务。

四、级别设计：什么该记，什么不该记

级别是运维契约，团队理解不一致，日志就会要么淹没重点，要么在关键时刻缺失。

DEBUG 用于开发期定位：入参与出参、分支走向、缓存命中、SQL 与耗时，读者是写代码的人，生产默认关闭。INFO 记录业务与生命周期的关键节点：服务启动与退出、配置加载、订单状态变更、外部依赖切换，读者是值班人员，生产默认开启。WARNING 表示“不正常但还能跑”：重试成功、降级到兜底数据、连接池接近上限。ERROR 表示“这个请求失败了”，需要人排查，但服务整体仍可用。CRITICAL 留给“服务已经不可用”：主库连不上、关键配置损坏、磁盘写满。

实践中有几条经验。

  • 判断 WARNING 与 ERROR 的分界线是“是否需要有人来看”：重试一次就成功的抖动记 WARNING，重试三次仍失败并返回 500 记 ERROR。
  • 不要用 ERROR 记录参数校验失败。这是客户端的正常行为，量大会把真正的故障埋掉。
  • 生产默认 INFO，DEBUG 通过环境变量开启，不要为排查问题改代码再发版。
  • 高频路径要采样。每个请求都打一条访问日志时，可以每 100 条抽 1 条，或者只记录慢请求与失败请求。日志量超过采集端处理能力，丢的是全部日志。
  • 单条日志不要拼大对象，把整个响应体塞进日志既拖慢主流程，也让检索变难。

级别继承也适用于子模块：给 app 设 DEBUG 后，app.db 也会输出 DEBUG；只想让某个子模块安静，必须显式设更高级别。

五、Handler：把日志送到正确的地方

Handler 决定日志的终点，常用的几个都在标准库里。

  • StreamHandler：写到流对象，默认是 sys.stderr。开发时用它，容器环境下也常用，由容器运行时统一收集。
  • FileHandler：追加写入指定文件。适合单机、低并发的场景，不做轮转，文件会一直变大。
  • RotatingFileHandler：按大小轮转，maxBytes 控制单文件上限，backupCount 控制保留几个历史文件，写满就改名为 .1、.2。
  • TimedRotatingFileHandler：按时间轮转，when="midnight" 每天切一次，backupCount=30 保留 30 天，适合按天归档、便于清理。
  • WatchedFileHandler：不自己轮转，但会检测文件是否被外部工具替换，配合 logrotate 使用。

Handler 自己也有级别。Logger 的级别决定“要不要生成记录”，Handler 的级别决定“这条记录要不要由我输出”，两者都通过才写。常见做法是 Logger 设 DEBUG 收集全部，控制台 Handler 设 INFO，文件 Handler 设 DEBUG。

重复输出的原因通常是链路里有两个 Handler：root 被 basicConfig 配了一个，业务代码又给 myapp 加了一个，而 propagate 仍是 True，记录先由 myapp 写一次，再冒泡到 root 写第二次。解决办法要么只在 root 上挂 Handler，要么给子 Logger 设 propagate = False，不要两种混着用。

六、格式化：让一行日志自带上下文

Formatter 用 % 风格的字段占位符。常用的字段不多，但每个都有明确用途。

  • %(asctime)s：时间，配合 datefmt 指定格式；默认带毫秒，排查并发问题时毫秒很关键。
  • %(levelname)s：级别名，固定宽度可以用 %(levelname)-8s 对齐。
  • %(name)s：Logger 名，通常就是模块路径，用来定位来源。
  • %(module)s 与 %(lineno)d：文件名与行号。行号在代码改动后会漂移，但排查时仍然最直接。
  • %(process)d 与 %(processName)s：进程标识，多进程部署时必备。
  • %(threadName)s：线程名，排查线程池问题时有用。
  • %(message)s：最终消息，必须放在格式串里。

字段越多，单行越长，检索成本越高。服务端日志保留时间、级别、来源、进程、消息五项即可，请求细节放进消息体的结构化字段。

采集端需要结构化数据时，手写一个 JSON Formatter 即可，不必引入第三方库。

ensure_ascii=False 让中文按原样输出，否则日志里全是转义序列。异常堆栈单独放一个字段，是为了避免一条日志跨多行：很多采集端按行切分，多行堆栈会被拆成碎片。

getMessage() 会做惰性格式化，所以应写 logger.info("order %s created", order_id) 而不是先拼字符串，级别不通过时前者完全不格式化。

按环境切换最直接的做法是每个环境一份 YAML，启动时由环境变量决定路径；也可以共用基础配置，在代码里浅合并，只覆盖级别与文件路径。级别最好还允许被 LOG_LEVEL 覆盖，便于临时排查。

YAML 的优点是层次直观、可写注释、运维也能改；缺点是引入 PyYAML 依赖、对缩进敏感、没有结构校验，字段写错往往不报错只是不生效。写在 settings.py 里同样可行，还能被单元测试覆盖。

八、并发与多进程：别让日志互相踩

多线程下 logging 是线程安全的：每个 Handler 在 handle 时对自身加锁，保证一条记录完整写出，字符不会交错。但锁的粒度是 Handler，写文件是同步 I/O，磁盘慢时所有线程都排在锁后面。

标准库从 3.2 起提供了 QueueHandler 与 QueueListener，把写操作挪到独立线程。

这里有个必须知道的细节：QueueHandler.prepare() 会用自己的 Formatter 把 record.msg 改成字符串并清空 record.args，下游 Handler 拿到的已是成品文本，它的 Formatter 只对 %(message)s 有意义。格式要配在 QueueHandler 上。

队列要有界。无界队列在消费者跟不上时吃光内存；有界队列满时阻塞生产者，相当于把压力传回业务线程，这是可预期的背压。退出时调用 listener.stop()，否则队列里的日志会丢。

多进程是另一回事。多个进程的 FileHandler 指向同一文件，问题不在记录交错，而在轮转：一个进程切分时，其他进程仍持有旧的文件描述符，继续往已改名的文件里追加。常见做法有三种。

  • 按进程分文件。文件名带上 pid，例如 app-%d.log，每个进程独立轮转，采集端按文件名合并。简单可靠，缺点是文件数量随进程数增长。
  • 交给外部设施。应用只写标准输出或 syslog，由容器运行时、syslog-ng、Filebeat 之类的采集端负责落盘与轮转。这也是容器部署下更常见的做法。
  • 单独起一个日志进程。所有 worker 把记录送进 multiprocessing.Queue，由一个专门的进程消费并写文件。实现成本最高，但写入是串行的，轮转也只有一个执行者。

不建议自己给文件加跨进程锁：不同文件系统上的行为不一致，网络盘上尤其不可靠，出了问题难以复现。

九、异常与敏感信息

记录异常要用 logger.exception，它只能在 except 块里调用，效果等价于 logger.error(..., exc_info=True)，会把完整的调用栈一并写入。

反面写法是 logger.error(str(e))，栈没了，排查只能靠猜；在 except 之外调用 exception 会打出 NoneType: None。想在没有异常时留栈，用 stack_info=True。

日志是泄露敏感信息的高发区。密码、token、cookie、身份证号都不应进入日志，整体打印请求头更是常见事故，Authorization 往往就在里面。做法是在入口裁剪：只记必要字段，query 先去掉敏感键，序列化请求体前走一遍脱敏函数。

把请求上下文带进日志，最省事的工具是 3.7 的 contextvars，配合 Filter 注入字段。

Filter 要挂在 Handler 上，不要挂在 Logger 上。Logger 上的 Filter 只对直接调用它的记录生效，子 Logger 冒泡上来的记录不经过它，这是字段时有时无的常见原因。格式串加上 %(request_id)s，同一请求的日志就能串起来。

十、常见坑与排查顺序

  • root 被第三方库污染。某些库在 import 时就调用 basicConfig 或直接 logging.info，格式与级别被抢先设定。对策是入口处最早执行配置，并把第三方 Logger 降到 WARNING。
  • basicConfig 不生效。root 已有 Handler 时它直接返回，静默失败。先看 logging.getLogger().handlers 是否为空。
  • Handler 重复添加。工厂函数被多次调用、模块被重新加载，都会让同一个 Logger 挂上多个 Handler。对策是加之前检查，或打一个已配置标记。
  • 日志阻塞主线程。同步写文件、网络 Handler、磁盘将满都会拖慢请求。对策是队列 Handler，并避免在日志参数里做耗时计算。
  • 日志文件权限。以 root 启动再降权运行，或容器挂载目录属主不对，都会抛 PermissionError。目录应提前创建并授予运行用户写权限，不要图省事给 777。

排查顺序可以固定：先确认 Logger 的有效级别，再确认 Handler 数量与各自级别，最后确认记录是否被 Filter 拦掉。

小结

logging 的价值在于把“记什么”和“记到哪”分开：业务代码只调 Logger，级别、去向与格式交给配置。脚本用 basicConfig 足够，服务上线用 dictConfig，按环境切换。级别要克制，生产默认 INFO，高频路径采样。多线程用队列 Handler，多进程不要共写一个文件。异常用 exception 记录堆栈，敏感字段在统一出口脱敏，请求上下文用 Filter 注入。
