React 服务端渲染初探

单页应用把渲染全部交给浏览器：HTML 里只有一个空的挂载点，首屏要等脚本下载、解析、执行完毕才看得到内容。服务端渲染把首屏 HTML 提前在 Node 进程里生成，让浏览器一拿到响应就能绘制。本文沿着一次真实请求的链路，讲清 React 服务端渲染的最小实现，以及数据、路由、样式、鉴权这几处最容易出问题的地方。读完之后，你应该能判断项目是否需要 SSR，并独立搭出一个可运行的同构骨架。

服务端渲染解决的是什么问题

单页应用的首屏路径是：浏览器拿到一个几乎空的 HTML，下载并执行打包后的脚本，发起数据请求，最后才把内容渲染出来。这条链路上任何一环变慢，用户看到的就是白屏。服务端渲染（Server-Side Rendering，SSR）把“生成 HTML”这一步提前到 Node 进程里完成，浏览器收到的响应已经包含首屏结构，解析完即可上屏，脚本稍后到达才接管交互。

它带来的收益主要有三处。第一是首屏内容：对电商、内容站这类以转化为目标的页面，白屏时间直接对应跳出率。第二是 SEO：Google 的爬虫能执行 JavaScript，但抓取预算有限，其他爬虫基本不执行，直出 HTML 更稳妥。第三是弱网与低端设备：即使脚本执行失败，页面上的文字和链接依然可读。

代价同样明确。服务器要为每个请求执行一次组件树，CPU 开销远高于返回静态文件；同一份代码要在两端跑通，window、document 这类浏览器对象随时可能让服务端崩掉；缓存策略也更复杂，HTML 里混着用户相关的数据，不能简单地整页缓存；部署上还多了一层 Node 服务，健康检查与错误监控都要补齐。

所以判断标准不是“SSR 更高级”，而是“首屏确定性值不值得这些成本”。内容型页面、对 SEO 有硬需求的站点值得做；后台管理系统、登录后才使用的工具，通常没有必要。

一次请求的完整链路

理解 SSR 的最好方式，是把它看成两条渲染路径：服务端渲染出首屏，客户端接管后续。两条路径执行的是同一棵组件树，只是运行环境不同。下图是一次请求从发起到可交互的完整时序。

sequenceDiagram
    participant B as 浏览器
    participant N as Node 服务
    participant D as 数据接口
    participant C as 客户端脚本
    B->>N: GET /posts/1
    N->>D: 带 Cookie 请求数据
    D-->>N: 返回 JSON
    N->>N: renderToString 生成 HTML
    N-->>B: 返回完整 HTML（含初始 state）
    B->>B: 解析并绘制首屏
    B->>C: 下载并执行 bundle
    C->>C: hydrate 绑定事件
    C-->>B: 页面可交互

图里有几个细节值得单独说明。服务端取数发生在 renderToString 之前，因为 renderToString 是同步函数，它不会等待 Promise，组件里写数据请求只会拿到空结果。服务端返回的 HTML 会带上 data-reactroot 属性，hydrate 时据此判断哪些 DOM 可以复用。客户端脚本必须出现在 HTML 之后，否则执行时找不到挂载点。

还有一个容易忽略的地方：服务端渲染只解决“首帧可见”，不解决“首帧可交互”。按钮在脚本执行完之前点了没有反应，这是 SSR 的固有特性。如果页面强依赖交互，可以先用骨架屏占位，把可点击的入口延后呈现。

数据预取与初始 state

真实页面一定要取数。顺序必须是先取数、再渲染：数据作为 props 传进组件，组件在渲染阶段只根据 props 输出结构，不发请求。

取数完成后还有一步同样重要：把同一份数据序列化进 HTML，让客户端首帧拿到完全相同的输入，通常约定挂在 window.INITIAL_STATE 上。

关于转义，这里值得多写几句。JSON.stringify 不会处理小于号，如果数据里出现 </script>，浏览器会认为脚本提前结束，后面的 JSON 变成页面文本，轻则报错，重则被构造成 XSS。经典写法是把 < 替换成 \u003c；此外 U+2028 与 U+2029 在旧引擎里是行终止符，直接出现在字符串字面量中会导致语法错误，也要一并转义。

不要把整个 store 都塞进去，只序列化首屏需要的字段，体积可控，也避免把敏感信息写进 HTML。密码、会话 token 永远不应该出现在初始 state 里。

客户端注水与首屏一致性

客户端拿到 HTML 后有两种挂载方式，差别很大。render 假设容器是空的，会清空内容重新创建 DOM；hydrate 复用服务端生成的标记，只绑定事件。SSR 必须用 hydrate，否则首屏 DOM 被丢弃重建，用户可能看到闪烁，已输入的内容也会丢失。

hydrate 会校验两端输出。文本不一致时，控制台会出现 Text content did not match 的警告；结构不一致时，会出现 Expected server HTML to contain a matching 的提示。轻微的不一致 React 会尝试修补，严重的不一致会让事件绑定错位，表现为点了没反应，或者点到了别的元素。

排查时先列一份“两端可能不同”的清单，再逐个排除：

不一致来源 典型表现 处理方式
当前时间、相对时间 服务端与客户端秒数不同 时间戳随 state 下发，格式化放到挂载后
Math.random()、自增 ID 每次输出都不同 服务端生成后写入 state
window 宽度、滚动位置 服务端直接报错或取到默认值 移到 componentDidMount，先给默认值
浏览器语言、时区 文案或日期格式不同 服务端读请求头，两端共用一份配置

还有一个隐蔽来源：组件初始 state 依赖 props 之外的全局变量，比如 localStorage 里的主题。服务端读不到，客户端读得到，首屏自然不同。做法是服务端给默认值，客户端挂载后再切换。

16.3 引入的新 Context 可以缓解层层传 props 的问题。用法上要注意：Provider 的 value 必须每次请求新建，不能放在模块作用域，否则上一个请求的数据会泄漏到下一个请求。

路由同构

单页应用的路由靠 history 监听地址变化，服务端没有 history，需要另一种方式把 req.url 告诉路由。react-router 4 为此提供了 StaticRouter：它接收 location 与 context，前者是当前地址，后者是普通对象，用来带回渲染过程中产生的跳转与状态码。

context 一旦提到模块顶层，并发请求之间会互相覆盖，表现为随机出现 302 或者 404，而且很难复现。

样式直出与首屏闪烁

首屏样式的目标只有一个：HTML 到达时样式已经在。常见做法有三种，各有取舍。

第一种，构建时把 CSS 从脚本里抽出来，输出独立文件，在 head 里用 link 引入。这是最稳的方案，浏览器解析到 link 就开始下载，与脚本无关。CSS Modules 的类名哈希在构建时确定，两端引用同一份产物就能保持一致。

第二种，把首屏关键样式内联进 head。适合样式量小的页面，省掉一次请求；样式一多会让 HTML 膨胀，反而拖慢首屏，内联体积一般控制在几十 KB 以内。

第三种，CSS-in-JS。组件里写样式，服务端渲染时要把收集到的样式抽出来插入 head，客户端再接管，否则会出现先无样式、后有样式的闪烁。

无论选哪种，都要避免把样式放在客户端脚本里，等 JS 执行时再插入 style 标签。那样首屏优势会被一次闪烁抵消，用户先看到裸 HTML，再看到排版跳变，体验比纯单页应用更差。

另一个细节是资源地址。link 与 script 要用绝对路径或 CDN 前缀，否则在 /posts/1 这类子路由下会请求错位置。

请求与鉴权

服务端发出的请求和浏览器发出的请求不是一回事。浏览器会自动带上目标域名的 Cookie，Node 进程不会；浏览器有同源策略，Node 没有。服务端请求业务接口时要显式透传用户的 Cookie，否则接口返回未登录数据，首屏渲染出“请登录”，客户端接管后又变回登录态，用户会看到一次闪变。

同一份请求代码在两端的差异主要是三处：地址、凭据、缓存。服务端必须用绝对地址，客户端可以用相对地址；服务端从 req.headers 取 Cookie 手动带上，客户端的跨域请求要设置 withCredentials。服务端请求通常不希望走缓存，客户端则相反。

更麻烦的是重复请求。服务端已经取过的数据，客户端挂载后又请求一遍，等于把首屏收益浪费一半，还会造成内容闪变。办法是让客户端首屏直接读 window.INITIAL_STATE，只在用户操作或数据过期时重新请求。

鉴权还有一个坑：token 存在 localStorage 时，服务端根本读不到，首屏只能按未登录渲染。这类项目要么改用 HttpOnly Cookie，要么接受首屏的未登录态，在客户端补一次用户信息请求。

性能与缓存

renderToString 是同步的。它会在当前事件循环里走完整棵组件树，期间不能处理其他请求；组件少时单次只要几毫秒，页面一大、嵌套一深，耗时会迅速上升，Node 进程会先于数据库成为瓶颈。

16.0 起提供的 renderToNodeStream 把结果变成可读流，配合 res.write 边渲染边发送，首字节更早到达。限制也要记住：开始写响应后，状态码和响应头已经定下，不能再改 302 或 404，中途出错也只能断开连接。涉及重定向和 404 判断的请求，仍然要先渲染完再决定。

缓存是性价比最高的优化。整页缓存以路径加用户角色为键，匿名页可以缓存较久；登录用户的页面要么按用户维度缓存，要么只缓存公共片段。多实例部署时缓存要放 Redis 这类共享存储，否则命中率会被实例数摊薄。HTML 里还嵌着初始 state，带用户信息的结果绝不能缓存后发给别人。

常见坑

window is not defined。模块顶层、渲染阶段或第三方库内部访问了 window、document、localStorage。把浏览器逻辑收进 componentDidMount，或在访问前判断 typeof window；只在客户端使用的库，改到挂载后再 require。

首屏不一致。除了前面列过的来源，还有构建产物版本不一致：HTML 引用的脚本带哈希，服务端却写死文件名，或者灰度期间新旧实例混跑，两端就会各渲染一套组件。服务端应当读取资源清单来拼地址。

内存泄漏。把 store 或 req 挂到模块级变量上“复用”，Node 常驻进程会把每个请求的数据留在内存里，跑几天就 OOM。请求级数据一律在请求内创建，定时器与订阅在卸载时清理。

静态资源 404。应用挂在子路径下时，资源和接口地址都要带前缀，最好由配置统一注入。

渲染异常。组件抛错时不要让整个请求变成 500 白屏，可以捕获后返回空壳 HTML，让客户端照常渲染，相当于自动降级成单页应用。前提是客户端入口不依赖服务端一定成功。

小结

服务端渲染的本质是用服务器算力换首屏确定性：服务端跑一遍组件树产出 HTML，客户端用 hydrate 复用这份 DOM 并接管交互。落地时守住三条线：取数在渲染之前完成，两端首帧输入必须一致，请求级状态绝不跨请求复用。数据、路由、样式、鉴权各有同构写法，先跑通最小链路再逐块接入，比一上来套框架更容易定位问题。是否值得做仍要回到业务：首屏与 SEO 的收益，能否覆盖多一层服务与双端约束的成本。
