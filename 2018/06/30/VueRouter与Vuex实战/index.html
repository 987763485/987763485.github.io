Vue Router 与 Vuex 实战

单页应用里，页面切换与共享状态最容易纠缠：路由参数散落在组件里，登录信息又在多个页面各存一份。本文以 Vue 2.5、vue-router 3.x 与 Vuex 3.x 为背景，从职责划分讲到路由配置、守卫、懒加载和模块化，最后集中处理刷新丢状态、重复请求这些实战问题，不重讲全家桶的目录搭建，也不讨论源码实现与选型方法论。适合已经能写 Vue 单文件组件、准备把项目从演示页推进到可维护工程的读者。

先分清职责：URL 与 store 的边界

路由和状态管理不是二选一，而是各自记录不同性质的信息。判断标准很简单：这个信息是否需要被收藏、分享、刷新后还原，或者直接决定用户看到哪一屏。如果是，放进 URL；如果它只在会话内跨页面共享，放进 store；如果只影响当前组件，留在组件的 data 里。

以常见的后台项目为例。用户列表的页码、筛选条件、详情页的 id，都应该出现在 URL 中，这样刷新、回退、把链接发给同事都能还原现场。当前登录用户、权限码、购物车、全局提示，适合放进 Vuex，因为它们跨页面共享却不适合出现在地址栏。弹窗开关、输入框的临时内容，则属于组件自己的状态。

最常见的错误是制造两个真相来源：把 $route.params.id 复制进 store，组件又同时读两边；或者 URL 已经是 /users?page=2，还在 store 里维护一个 currentPage。两处一旦不同步，就会出现“地址对了、列表不对”的怪问题。笔者的习惯是，能用 URL 表达的就以 URL 为准，store 只保存 URL 装不下的会话状态。

路由配置：动态参数、嵌套与命名

在 vue-cli 2 生成的项目里，路由集中在 src/router/index.js，用 new Router 创建实例后挂到根组件。下面是一份包含嵌套路由、动态参数与命名路由的配置。

几点值得说明。子路由的 path 不带前导斜杠，最终地址由父路径拼出来；props: true 把路由参数映射成组件属性，组件不必到处写 this.$route，测试时也更容易传参。命名路由的价值在于跳转时不用拼字符串，路径调整只改配置一处。

编程式导航用 this.$router.push，需要替换历史记录时用 replace，回退用 go(-1)。$router 是路由器实例，负责发起跳转；$route 是当前路由对象，只读地描述现在在哪。把这两个搞混，是新手最常见的报错来源。

嵌套路由对应的是页面布局：父级提供侧边栏和头部，子级通过 <router-view> 渲染列表或详情。如果子页面需要整页切换而不是嵌在布局里，就不要硬套嵌套，扁平路由更清楚。

hash 还是 history：刷新 404 的根源

hash 模式的地址形如 example.com/#/users/1，井号后的内容不会发给服务器，所以任何路径刷新都能回到 index.html，部署时几乎不用配置。代价是地址不够干净，部分统计工具对井号后的变化不敏感。history 模式借助 History API 去掉井号，地址更像传统多页站点，但服务器必须配合：用户直接访问 /users/1 时，Nginx 会去找这个真实路径，找不到就返回 404。

try_files 的含义是依次尝试：先找同名文件，再找目录，最后回退到 index.html，把路由交给前端。静态资源目录最好单独加一条 try_files $uri =404，否则缺失的 JS 也会被替换成 HTML，浏览器报的是语法错误，很容易误判。

刷新 404 的排查顺序：先看 Nginx 是否真的把请求转给了前端，再看 assetsPublicPath 与 router 的 base 是否一致，最后确认后端有没有拦截 /api 之外的前缀。开发环境正常、线上刷新就挂，八成是这条回退规则没配。若部署环境完全不受控，退回 hash 模式是成本最低的方案。

导航守卫：把一次跳转拆成几个阶段

一次路由切换并不是瞬间完成的。vue-router 3 把它拆成若干阶段，允许我们在不同位置插入逻辑。全局守卫管所有路由，路由独享守卫只挂在某条配置上，组件内守卫则跟随组件生命周期。

flowchart TD
  A[URL 发生变化] --> B[全局 beforeEach]
  B --> C[路由独享 beforeEnter]
  C --> D[组件内 beforeRouteEnter]
  D --> E[请求页面数据]
  E --> F[渲染组件]

最常用的是全局 beforeEach，适合做登录校验、修改标题和顶部进度条。它接收 to、from、next 三个参数，必须显式调用 next：不调用，导航会一直挂着；调用 next(false) 中断；传入路径或对象则重定向。

登录拦截最容易写出死循环：未登录访问 /orders 被重定向到 /login，而 /login 本身也要求登录，于是无限跳转。解决办法是在守卫里放行白名单，或者先判断目标就是登录页。另一个坑是异步校验：在请求返回后再调用 next 没有问题，但要保证任何分支都只调用一次，否则控制台会警告，页面行为也不可预期。

路由独享的 beforeEnter 写在路由配置里，适合只对某条路由生效的检查。组件内的 beforeRouteEnter 在组件实例创建前触发，拿不到 this，需要写成 next(vm => { ... })；beforeRouteUpdate 在参数变化但组件复用时触发；beforeRouteLeave 常用来拦截未保存的表单。

元信息与权限：菜单、页面与按钮

路由的 meta 字段是挂业务标记的地方。给需要登录的页面加上 meta: { requiresAuth: true }，守卫里统一判断，比在每个组件里写一遍可靠。角色也可以放进 meta.roles，跳转前与 store 里的角色求交集。

菜单通常由路由表生成：遍历配置，过滤掉 hidden: true 和当前用户无权访问的项，再渲染成侧边栏。这样菜单与路由同源，不会出现“菜单里有、点进去 404”的尴尬。若权限是登录后从接口拿到的，可以在拿到权限后筛选出可访问路由，用 router.addRoutes 动态追加；注意兜底的 404 路由要最后加，否则它会先匹配掉后面追加的页面。

路由级权限和按钮级权限解决的不是一个问题。前者决定用户能不能进入某个页面，后者决定页面里的某个操作要不要显示。只做菜单隐藏不叫权限控制，用户手动输地址照样能进；只做前端判断也不安全，接口必须再校验一次。按钮级常见做法是自定义指令 v-permission，在 inserted 钩子里根据权限码移除节点，或者用 v-if 配合计算属性。

路由懒加载：先打开首屏，再取其他页

默认情况下，所有路由组件都会被打进同一个 app.js，首屏必须等整包下载完。把路由改成动态 import()，构建工具会为每个入口生成独立 chunk，只有访问该路由时才加载对应文件。这在 2018 年的 webpack 3 里已经是成熟用法。

相同的 webpackChunkName 会把多个组件合并进同一个 chunk，适合按业务模块分组：用户相关放一个，订单相关放一个，避免碎成几十个小文件。魔法注释需要 Babel 能解析动态 import，vue-cli 2 的模板若没有启用对应语法，要在 .babelrc 里补上 syntax-dynamic-import 插件，否则构建会报语法错误。

加载态可以用全局守卫配合一个顶部进度条：beforeEach 开始、afterEach 结束，失败时在 router.onError 里收尾。更细的拆包策略、预加载与体积分析属于打包优化的范围，这里只讨论路由级分割这一层。

Vuex 的单向流：为什么 mutation 必须同步

Vuex 把共享状态收进一个 store，并规定了一条单向数据流：组件 dispatch 一个 action，action 执行异步任务后 commit 一个 mutation，mutation 是唯一能改 state 的地方，state 变化再驱动视图更新。这样任何一次状态变化都有名字、有载荷、有记录，调试时能回放。

mutation 必须同步，不是风格问题，而是工具链的前提。devtools 依赖“提交即完成”来做快照和时间旅行；如果 mutation 里塞了异步回调，快照拍到的只是中间态，多个异步任务交错时也无法判断状态是哪一步变成这样的。需要请求、定时器、Promise 的逻辑，全部放在 action 里，action 可以返回 Promise，让调用方知道何时完成。

getters 相当于 store 的计算属性，适合放派生数据，比如总件数、总价、按关键字过滤后的列表。它会被缓存，依赖不变就不会重复计算；不要在 getter 里做副作用。

组件绑定：辅助函数与 v-model

在组件里逐次写 this.$store.state.cart.items 很啰嗦，Vuex 提供了四组辅助函数。mapState 与 mapGetters 展开到 computed，mapMutations 与 mapActions 展开到 methods。展开运算符与对象写法可以混用，方便在映射之外再写本地计算。

表单与 store 的绑定要小心。直接给 state 绑 v-model 会绕过 mutation，严格模式下直接报错；正确做法是用带 get/set 的计算属性：读的时候返回 state，写的时候提交 mutation。这样输入框看起来还是双向绑定，数据流仍然是单向的。

如果多个组件都要读写同一个字段，把这段逻辑收进 mixin，或者封装成带 model 选项的组件，比在每个页面复制一遍更稳。

模块化：namespaced、跨模块与动态注册

项目一大，单个 store 文件会迅速膨胀。Vuex 的 modules 允许按业务拆分，每个模块有自己的 state、getters、mutations、actions。开启 namespaced: true 后，所有提交都要带模块前缀，避免不同模块出现同名 mutation。

跨模块调用有两种写法：在 action 里用 dispatch('user/loadProfile', null, { root: true })，或者从处理函数的参数中解构 rootState、rootGetters 直接读根状态。前者保持模块间松耦合，后者适合只读场景，不要在模块里直接改别的模块的 state。

动态注册适合按需加载的页面：store.registerModule('report', reportModule)，离开时再 unregisterModule。路由懒加载配合动态模块，可以让报表这类重状态只在进入时初始化。目录上，笔者通常保留一个 store/index.js 负责组装，store/modules 一模块一文件，getters.js 放跨模块的派生数据，mutation-types.js 只在团队需要统一常量时引入，不必为了形式而形式。

实战坑：刷新、严格模式与重复提交

刷新丢状态是第一个坑。Vuex 的状态只存在内存里，刷新必然清空。需要跨刷新保留的，通常只有登录凭证、用户信息和少量草稿，把它们写进 localStorage，并在创建 store 时读回；购物车这类数据是否持久化，要看业务能否接受本地与服务端不一致。不要图省事整棵 state 序列化，版本升级后旧结构会变成脏数据。可以在插件里用 store.subscribe，只挑白名单字段落盘。

严格模式在开发期很有用，它通过深度 watcher 检查所有非法修改，但 state 越大开销越明显。生产构建要关掉，通常写成 strict: process.env.NODE_ENV !== 'production'。同理，把大表单直接绑到 store，每敲一个字都产生一次 mutation，既卡又污染调试记录；用本地副本，保存时再提交，或者至少做防抖。

重复提交要靠状态和接口双保险：action 返回 Promise，组件维护 submitting，请求期间禁用按钮；服务端用幂等键兜底，防止用户刷新或重试造成两笔订单。

路由参数变化但组件复用，是另一个高频问题。从 /users/1 跳到 /users/2，vue-router 会复用同一个组件实例，created 和 mounted 不会再次执行，页面还停在上一个用户。解决方式是监听 $route，或者使用 beforeRouteUpdate。

还要注意 query 与 params 的区别：query 变化同样会复用组件，props: true 只映射 params，不映射 query。若列表页靠 query 驱动，监听时要连 $route.query 一起处理，或者把筛选条件收进一个对象再比较。

调试：devtools、日志与断点

调试 Vuex 先看 Vue devtools。Vuex 面板会列出每次 mutation 的名称、载荷和提交前后的状态，点一下就能回到那一刻，比在代码里到处 console.log 高效；面板里的记录开关可以暂停收集，避免高频输入刷屏。较新的 devtools 还提供 Timeline，把组件事件、路由变化与 mutation 排在同一条时间线上，适合判断“先点了什么、后改了什么”。

需要在控制台留痕时，可以在开发环境用 store.subscribe 打印 mutation 与提交后的 state，生产环境记得去掉。路由问题则适合在 beforeEach 里临时打一行 console.log(to.fullPath, from.fullPath)，或者在浏览器 Sources 面板给守卫打断点，观察 next 到底有没有被调用、被调了几次。很多“页面白屏”不是组件报错，而是某个守卫忘了放行。

小结

路由负责“我在哪”，Vuex 负责“我们共享什么”，先把这条边界划清，后面的配置才不会互相打架。路由部分记住三件事：动态参数与嵌套要配合命名路由使用，history 模式必须有服务端回退，守卫的每个分支都要有且只有一次 next。状态部分守住单向流：action 处理异步，mutation 同步落库，组件通过辅助函数与计算属性读写。懒加载、模块化和持久化都是在单向流上做分层，遇到刷新丢状态、参数变化不请求、重复提交这类问题，先回到数据流和生命周期里找原因。
