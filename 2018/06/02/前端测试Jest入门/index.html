前端测试：Jest 入门

单元测试长期是前端项目里最容易被跳过的一环：配置繁琐，断言库与运行器要分别选型，组件和 DOM 又难以在 Node 进程里运行。Jest 把这些环节收进一条工具链，安装之后几乎不用配置就能写下第一条断言。本文面向已经会写 JavaScript、但还没有系统使用过测试框架的前端开发者，从最小配置讲到 mock、快照、组件测试与覆盖率，并给出可以直接落地的工程集成方式。读完之后，你应该能在一个 React 或 Vue 项目里独立搭起测试目录，并让 CI 稳定地跑起来。

为什么用 Jest

前端测试存在一个悖论：业务越复杂越需要测试，而搭建测试环境的成本又高到让人放弃。Jest 的思路是把运行器、断言库、DOM 环境、mock 工具和覆盖率统计打包成一个依赖，安装完成后写一个测试文件就能跑。对大多数中小型前端团队来说，这种“先跑起来再补细节”的路径，比从零组装一套工具链更现实。

具体来说，Jest 有几个直接可用的能力。第一是零配置起步，默认查找 __tests__ 目录和 *.test.js 文件，不需要额外声明入口。第二是内置断言，expect 加匹配器覆盖了相等、真假、异常、调用次数等常见场景，不必再引入 Chai。第三是默认的 jsdom 环境，window、document、HTMLElement 这些浏览器对象在 Node 进程里可用，组件测试因此不需要打开真实浏览器。第四是并行执行，Jest 用工作进程池同时跑多个测试文件，总耗时接近最慢的那一批，而不是所有文件之和。第五是内建覆盖率，加上 --coverage 就会生成报告，无需单独配置 Istanbul。

代价是约定更多、定制能力有限：Mocha 只负责运行测试，断言、mock、覆盖率分别要接 Chai、Sinon 与 Istanbul，Jest 则把这些能力内置到同一个命令行里。

第一个测试从纯函数开始，先不碰组件和异步。假设有一个购物车模块，按单价与数量累加金额，并对非法价格抛出异常：

几个匹配器需要分清。toBe 用 Object.is 比较，适合数字、字符串、布尔值；toEqual 做递归的深比较，适合对象与数组，expect({ a: 1 }).toEqual({ a: 1 }) 能通过，换成 toBe 就会失败，因为两个字面量不是同一个引用。toBeTruthy 只要求值在布尔上下文里为真，空数组、字符串 '0' 都会通过，能写具体值时就别用。toThrow 接收字符串、正则或错误类，用来断言异常类型与消息。

当多条用例需要相同的初始数据时，用 beforeEach 而不是在每条 it 里重复声明。beforeEach 在每个 it 之前执行，适合重置数组、计数器、mock 调用记录；beforeAll 只执行一次，适合启动成本高且不会被修改的资源。测试结束后要清理的副作用放在 afterEach，例如恢复被替换的全局对象、卸载已经挂载的组件。Jest 不会自动帮你重置模块内部状态，这一点后文还会提到。

快照测试的边界

快照测试把第一次运行的结果序列化后存进 __snapshots__ 目录，之后每次运行都与存档比较，不一致就失败。它适合输出稳定、人工逐项断言成本高的场景，例如错误对象、配置生成结果，以及结构简单的展示型组件：

边界同样明显。快照记录的是“当前长什么样”，不是“应该长什么样”。一个布局频繁调整的组件，每次改样式都会产生 diff，开发者逐渐习惯无脑按 u 更新，快照就退化成噪音。比较稳妥的做法是只对变更可控的展示型组件使用快照，交互复杂的组件仍用显式断言检查关键节点与文案。组件快照通常还要配合序列化器，把框架的包装对象转成可读的树，否则存下来的是一堆内部字段。

更新快照用 jest -u，watch 模式下按 u 也可以。更新前必须看 diff：快照文件里出现的意外变化，往往就是这次改动引入的回归。快照文件应该进版本库，提交时和源码一起评审；如果把它加进 .gitignore，CI 上每次都会生成新快照，测试就失去了比较基准。CI 中加上 --ci 参数后，Jest 遇到缺失的快照不再自动写入，而是直接失败，这样可以防止本地忘记提交 .snap 文件。

另外，不要把快照当成唯一断言。快照通过只说明结构没变，不能说明行为正确；关键属性、回调是否触发、条件渲染的分支，仍然要写显式的 expect。

覆盖率：数字与有效性

--coverage 调用内置的 Istanbul 统计语句、分支、函数、行四项指标，默认在终端打印表格，并在 coverage/ 目录生成报告。落地时通常再加两个配置：collectCoverageFrom 限定统计范围，coverageThreshold 设置最低线：

入口文件只做挂载与启动，配置文件、mock 数据、常量表也不该计入分母。排除之后，数字才反映业务代码的真实情况。阈值不要一上来定 90，存量项目会长期卡在红线上；可以先设一个略高于当前值的门槛，要求新代码不拉低整体，再逐步上调。

覆盖率高不等于测试有效。一行代码被执行过，只说明测试碰过它，不说明断言检查了行为。branch 指标比行覆盖率更值得关注，它至少要求条件分支的两侧都被走到。

工程集成：watch、CI 与 ESLint

日常开发用 watch 模式。jest --watch 监听文件变化，只重跑与改动模块有依赖关系的测试；按 a 切到全量，按 p 过滤文件名，按 t 过滤用例名。

CI 里推荐两个参数：--ci 让缺失的快照直接失败，而不是自动写入；--runInBand 让测试在同一个进程里串行执行，牺牲速度换取更低的内存占用与更稳定的结果，容器内存受限时尤其有用。命令可以写成 jest --ci --runInBand --coverage。

flowchart TD
    A[编写或修改测试] --> B[本地 watch 模式]
    B --> C[提交代码]
    C --> D[CI 运行测试]
    D --> E[生成覆盖率报告]
    E --> F{达到阈值}
    F -->|是| G[合并]
    F -->|否| A

ESLint 与 Jest 的分工要清楚：ESLint 管静态问题，比如未使用变量、导入顺序、可疑写法；Jest 管运行时行为。可以加 eslint-plugin-jest 并开启 no-focused-tests，防止把 it.only 提交上去，导致 CI 只跑一条用例。

测试文件的命名与位置建议全组统一：与源码同目录命名 Button.test.js，或者集中放进 __tests__ 目录。无论选哪种，都要让 testMatch 与实际命名一致，避免新增文件悄悄不参与测试。辅助文件放在 test/ 下，命名不要带 .test。

常见坑与排查顺序

最后集中列出几类高频问题，它们大多不是 API 用错，而是测试之间互相污染。

定时器未清理。用了 jest.useFakeTimers 却没有恢复，后续依赖真实 setTimeout 的用例会挂起；组件卸载时没有清理定时器，也会留下悬空的回调。统一在 afterEach 里调用 jest.useRealTimers，组件里则把句柄存下来，在卸载钩子里清除。

共享状态。模块顶层的数组、对象、单例 store 在同一个测试文件里共享，前一条用例写进去的数据会影响后一条。在 beforeEach 里重建，或者把状态封装进工厂函数，每次返回新实例。jsdom 的 document 同样在文件内共享，挂载过的节点要显式卸载。

异步未 await。断言写在 then 或 setTimeout 里却没有返回 Promise，Jest 提前判定通过，失败永远不会暴露。除了统一用 async/await，还可以加 expect.assertions 兜底。

jsdom 缺少 API。jsdom 不负责布局，offsetHeight 与 getBoundingClientRect 一律返回 0；matchMedia、IntersectionObserver 在当期版本里也没有实现。依赖这些能力的组件，要在 setup 文件里补一个最小实现，或者把布局计算抽成独立函数单独测试。

Babel 配置不生效。测试文件里出现 import 就报 Unexpected token import，通常是 babel-jest 没装、.babelrc 不在项目根目录，或者配置里覆盖了 transform 却没有包含 babel-jest。先确认依赖，再检查配置合并顺序。

小结

Jest 的价值不在于功能比别人多，而在于把运行器、断言、DOM 环境、mock 与覆盖率收进一个依赖，让写测试的启动成本足够低。入门阶段先掌握 describe/it/expect、异步的三种写法与 jest.fn，再补上模块 mock、快照和组件测试，就足以覆盖大多数业务代码。配置守住三条：环境按代码类型选择，moduleNameMapper 处理别名与样式，覆盖率只统计业务源码。工程上把 watch 留给本地，把 --ci --runInBand 留给流水线。覆盖率只是提示，断言才是测试的内容。
