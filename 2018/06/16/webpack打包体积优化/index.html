webpack 打包体积优化

页面加载慢，很多时候不是接口慢，而是打包产物太大：首屏要下载、解析、执行几百 KB 的 JavaScript，中低端手机上这段时间足以让用户以为页面卡死。本文按“先测量、再优化”的顺序，讲清 webpack 3 与 webpack 4 下如何定位体积来源、做代码分割、抽取公共依赖、开启 tree shaking 与作用域提升，并说明每一步的代价与边界。读者需要能读懂并修改一份 webpack 配置，读完之后可以为现有项目建立体积基线，并按优先级逐项瘦身。

先把体积量出来

优化体积的第一步不是改配置，而是拿到一份可信的数据。很多团队的做法是听说了某个插件就加上试试，构建能过、页面能开，就认为优化完成；但首屏到底下载了多少字节、哪些模块占了大头，谁也说不清。没有基线，后面每一次改动都无法判断是收益还是倒退，也无法在回归时发现问题。

基线至少包含三个数字：首屏实际加载的 JS 与 CSS 在 gzip 之后的体积、首屏的请求数量、以及首次可交互的时间。三者要一起看。把一个大 bundle 拆成十个请求，字节数可能没有变化，但在 HTTP/1.1 的连接数限制下，请求排队反而会让首屏更慢；反过来，把所有代码塞进一个文件，缓存粒度又会变得很粗，改一行业务代码就让整个 vendor 缓存失效。

2018 年的 webpack 4 与仍在维护的 webpack 3 都能把构建统计导出为 JSON，这是后续所有分析工具的输入。

webpack 4 把命令行拆成了独立的 webpack-cli 包，未安装时命令会直接报错，上面的 npx 调用在两种版本下都能工作。webpack-bundle-analyzer 给出的是整体结构：哪些 chunk 偏大、每个 chunk 里第三方库占多少，它默认展示解析后的原始体积，也可以切换成 gzip 体积视图。source-map-explorer 更细，它读取 source map，把打包后的字节映射回源文件，能直接回答“这 80 KB 是哪个文件贡献的”。两者配合使用：先用 analyzer 找大 chunk，再用 explorer 定位到具体模块。

按体积排序时请使用 gzip 后的数字，而不是原始体积。JavaScript 与 CSS 是文本，gzip 能大幅缩小；图片和字体本身已经压缩过，gzip 几乎不再起作用。如果按原始体积排序，一张 200 KB 的图片会排在 150 KB 的 vendor 前面，但前者对首屏传输时间的影响通常小于后者。很多“优化图片”的收益其实来自减少请求，而不是压缩算法本身。

体积究竟从哪里来

拿到 stats 之后，把模块按来源归类，通常就能解释大部分体积。笔者习惯分成六类：业务代码、第三方依赖、重复依赖、未被使用的导出、source map，以及样式与字体。每一类的处理手段不同，混在一起谈“优化”很容易用错药。

业务代码是最容易误判的一类。它看起来都是自己写的，但路由页面、只在设置页用到的富文本编辑器、组件库自带的示例代码，都会被打进同一个入口。判断标准不是代码属于谁，而是首屏渲染是否需要它。

第三方依赖往往是真正的大头。UI 组件库、图表库、日期库、工具库，单独看每个都不算大，叠起来就非常可观。分析时不要只看安装体积，要看它实际被打进 bundle 的部分；一个包可能安装了几 MB，但只用到了其中几十 KB，也可能反过来，安装体积不大却因为整包引入而全部进入产物。

重复依赖更隐蔽。npm 3 之后依赖树被尽量扁平化，但当两个包对同一个库要求的版本区间没有交集时，node_modules 里会同时存在两份。它们在 bundle 里就是两份完整代码，运行时还可能出现 instanceof 判断失败、单例状态不共享之类的问题。用下面的命令可以快速确认。

未被使用的导出本来是 tree shaking 要解决的问题，但它也常常以“引入方式不对”的形式出现。import { debounce } from 'lodash' 在理想情况下只该带入一个函数，实际却可能把整个 lodash 拉进来，具体取决于这个包的模块格式与构建配置。看到某个工具库的体积与用法明显不匹配时，先怀疑引入方式。

source map 本身不会在正常浏览时被下载，但它会进入发布目录，也会影响构建与上传的时间。更重要的是，用 eval 形式的 devtool 会把 source map 内联进 bundle，让产物体积成倍增长，这类配置绝对不能出现在生产构建里。生产环境应使用独立的 .map 文件，并在不需要线上调试时选择不发布。

样式与字体常被忽略。引入一整套 UI 框架 CSS、几套图标字体、四五个字重的自定义字体，加起来的体积可能超过业务 JS。字体文件尤其要注意：一个中文字体动辄几 MB，全量引入几乎必然拖垮首屏。

把六类来源分别量化之后，再决定先动哪一类。

代码分割：改变的是下载时机

代码分割改变的是加载时机，而不是总体积。首屏只下载渲染首屏必需的代码，其余部分等用户真正需要时再取。对于一个有十几个路由的后台系统，首屏体积明显下降是很常见的，但把产物加起来看，总字节数可能一点没少。

最粗粒度的做法是入口拆分。多页应用本来就有多个 entry，每个页面天然是一个 chunk；单页应用也可以按“登录前”和“登录后”拆成两个入口，让登录页不必加载整个管理后台。入口拆分的代价是公共依赖需要在多个入口之间共享，否则每个入口都会重复打包一份 React，这正是下一节要解决的问题。

更常用的是动态导入。import() 返回一个 Promise，webpack 遇到它就把目标模块及其依赖单独打成一个 chunk，运行时按需加载。路由是天然的分界线：用户停留在列表页时，详情页、编辑页的代码完全没有必要下载。

公共依赖抽取与长期缓存

代码分割之后，紧接着的问题是：多个 chunk 共用的依赖放在哪里。如果每个异步 chunk 都自己打包一份 React，总体积会迅速膨胀；如果全部塞进主 chunk，首屏又会变重。公共依赖抽取要解决的就是这个平衡。

webpack 3 用 CommonsChunkPlugin 完成这件事。它按 name 逐个抽取，未被匹配的模块仍留在入口 chunk 里；常见做法是分两步：先把 node_modules 里的模块收进 vendor，再把运行时代码收进 manifest。

manifest 的作用是把 webpack 的运行时单独抽出来，这一步在 webpack 3 与 webpack 4 的配置里都不能省。运行时里保存着模块 id 与文件名的映射表，它会随着模块增删而变化；如果它和 vendor 打包在一起，每次业务代码改动都会让 vendor 的 hash 变化，长期缓存就失效了。

webpack 4 把这套机制换成了 splitChunks，配置从“抽哪个文件”变成了“按什么规则分组”，迁移时不能照搬。

chunks: 'all' 是关键：它表示同步与异步 chunk 都参与抽取，这是与 webpack 4 默认值 async 最大的区别；未显式设置时，只有异步 chunk 会被处理。minSize 避免把太小的模块抽成独立文件，反而增加请求数。cacheGroups 决定分组规则，priority 高的组先匹配。runtimeChunk: 'single' 等价于 webpack 3 里的 manifest。

长期缓存的前提是文件名与内容严格对应。但只改 hash 类型还不够，还要处理模块 id：两个版本默认都用数字作为模块 id，在中间插入一个模块可能让后面所有模块的 id 顺移，vendor 内容未变、hash 却变了。HashedModuleIdsPlugin 用模块路径的哈希作为 id，可以解决这个问题；webpack 4 也保留了它，如果观察到无关改动导致 vendor 的 hash 变化，可以显式启用。

分组也不宜过细。把每个第三方包都拆成独立 chunk，请求数会迅速上升，在 HTTP/1.1 下尤其吃亏。更实际的做法是按变更频率分两到三组：框架与运行时一组、变化较少的工具库一组、业务代码各自成组。这样既保住了公共部分的长期缓存，又不至于把请求数推得太高。

Tree shaking：让没用的导出不进产物

Tree shaking 的目标很直接：模块里定义了十个导出，业务只用了其中一个，产物里就只保留一个。它的前提是打包器能在不执行代码的情况下判断哪些导出被用到，因此整套机制建立在 ES module 的静态语法之上。

四个条件缺一不可。第一，源码必须是 ES module，import 与 export 是静态声明，打包器可以据此建立依赖图。第二，转译环节不能把它变成 CommonJS，否则导出变成运行时的属性赋值，静态分析就失效了。第三，压缩器要能删除死代码，把没有被引用的声明真正去掉。第四，包的声明要可信，webpack 4 引入的 sideEffects 字段就是用来告诉打包器哪些模块可以整个跳过。

最常见的破坏发生在 Babel 这一步。babel-preset-env 默认会把 ES module 转换成 CommonJS，因为它的默认假设是产物直接交给 Node 或旧浏览器运行，而不是再经过打包器。

modules: false 是整套配置里最关键的一行，含义是“不要处理模块语法”，把 import 与 export 原样留给 webpack。很多项目抱怨 tree shaking 没效果，追查下去都是这一行未配置。

webpack 4 还要求包自己声明 sideEffects，否则打包器不敢贸然删除“看起来没有被引用”的模块，因为导入一个模块本身可能就是在执行副作用，比如注册全局变量、注入样式。应用自己的 package.json 可以这样写：

Scope Hoisting：减少模块包装的开销

默认情况下，每个模块都会被包成一个函数，通过 __webpack_require__ 调用。模块数量上来之后，这层包装本身就有成本：闭包、参数传递，以及压缩器难以跨模块做常量折叠。作用域提升（Scope Hoisting）把满足条件的模块合并进同一个函数作用域，减少这层开销。

webpack 3 需要显式加插件，webpack 4 在 production 模式下才会默认开启。

限制同样明确：只有 ES module 才能参与合并；被多个入口共享的模块、CommonJS 模块、包含 eval 的模块都无法合并。因此它不是一个“开了就变小”的开关，收益取决于项目里 ESM 的占比。它对运行时开销的改善比体积更明显，压缩率会略好一些，但不会带来数量级的变化。放在优化顺序里，它应该排在依赖替换与 tree shaking 之后。版本迁移与新特性的完整叙述不在本文范围内，这里只把它当作体积与运行时的一个可选项。

依赖替换与按需引入

当分析工具指出某个依赖占了很大比例时，有三条路可走：按需引入、裁剪不需要的部分、换成更小的实现。三条路的成本依次上升，应该按顺序尝试，前一条能解决就不要急着走后一条。

按需引入最典型的例子是 lodash。它的入口文件把几百个方法挂在一个对象上，整包引入意味着这些方法全部进入产物。

更省心的做法是用 babel-plugin-lodash，它会在编译期把 import { map } from 'lodash' 改写成上面的路径形式，业务代码不必关心具体文件。lodash 还提供了 lodash-es，这是 ESM 版本，可以配合 tree shaking 使用，但前提是前面的 Babel 配置没有把模块语法转掉。

裁剪的典型例子是 moment。它的体积大头不是核心逻辑，而是几十种语言包。moment 内部用 require('./locale/' + name) 加载语言，webpack 看到这种动态表达式，会把整个 locale 目录都打进产物，尽管项目未必用到其他语言。

ContextReplacementPlugin 的作用是替换动态 require 的上下文，限定正则之后只有匹配的文件会被包含。如果项目根本不需要切换语言，也可以用 IgnorePlugin 忽略整个 locale 目录，再手动 import 'moment/locale/zh-cn'。两种方式都能减小体积，区别是前者保留了按需加载其他语言的可能。

组件库的按需引入是另一类常见需求。Ant Design、Element UI 这类库都提供了子路径导入，也可以配合 babel-plugin-import 在编译期改写导入语句。这里有一个容易被忽略的细节：很多“按需”只对 JS 生效，样式仍然是全量引入，结果 JS 小了、CSS 没变，接入时要分别确认。

替换依赖是收益最大也最危险的一步，评估时至少看四点：现有用法是否被覆盖、API 差异有多大、维护是否活跃、迁移需要多少测试成本。比如日期库，如果项目只做格式化和少量计算，换成体积更小、支持 tree shaking 的实现是合理的；但如果大量使用相对时间、时区换算、日历等能力，替换引入的 bug 成本可能远超节省的几十 KB。替换要按模块灰度，一次只换一处，并且用现有的测试用例兜底。

压缩与去除：最后才动的一层

压缩是最后一层，也是最容易被过度期待的一层。它能去掉空格、注释、长变量名，也能做一些等价变换，但它删不掉“本来就不该进来”的代码。一个偏大的 bundle 压缩之后可能小很多，但继续在压缩器上调参，空间已经非常有限，真正的大收益都在压缩之前。

webpack 3 使用 uglifyjs-webpack-plugin，通常直接调用内置的 UglifyJsPlugin，未额外安装依赖也能用。

webpack 4 的 production 模式自带压缩，默认使用的仍是 uglifyjs-webpack-plugin，4.x 早期版本尚未换成 Terser。它只能处理 ES5 语法，如果构建目标是现代浏览器、希望保留箭头函数与 class 以获得更小的产物，就需要换成 terser-webpack-plugin。Terser 是 UglifyJS 的分支，支持 ES6 及以上语法。

这一步要结合目标浏览器决定。如果还要兼容 IE 11，保留 ES5 输出更稳妥；如果只需要支持当年的现代浏览器，用 Terser 保留 ES6 语法能省下一部分体积，因为 class 与箭头函数不需要被降级成函数与 bind。

drop_console 需要谨慎。把 console 全部删掉确实能省一点体积，但线上排错时日志往往是第一手线索。更稳妥的做法是按级别保留，或者引入一个统一的日志模块，由 DefinePlugin 在构建时把实现替换成空函数，这样既能去掉调用，又保留了按环境切换的能力。

与压缩配套的是常量折叠。React 内部大量使用 if (process.env.NODE_ENV !== 'production') 包裹开发期校验，只有把这个常量替换成字符串，这些分支才会变成死代码，再被压缩器删除。webpack 4 的 production 模式会自动注入，webpack 3 必须手动配置，忘记配置时产物会明显偏大。

最后是传输压缩。服务端开启 gzip 是标配；brotli 可以选择性做预压缩，但它需要服务端支持，当时的主流 Web 服务器并不默认提供，是否启用要看部署环境，不能当作默认前提。

CSS 与静态资源

JS 之外的体积同样值得处理，只是优先级通常低一些。CSS 的问题主要集中在“全量引入”和“没有拆分”两件事上。

开发环境里，样式通过 style-loader 注入到 head，改一行代码就能热更新；生产环境则应该把 CSS 抽成独立文件：未抽取的样式会被内联进 JS，既不能并行下载，也无法单独缓存。webpack 3 用 ExtractTextPlugin，webpack 4 换成了 mini-css-extract-plugin。

webpack 3 的等价写法是 ExtractTextPlugin.extract({ fallback: 'style-loader', use: 'css-loader' })，并在 plugins 里用 [contenthash] 命名输出文件；webpack 4 里它已被标记为废弃，尚未移除。抽取的代价是多一个请求，并且开发环境会损失热更新体验，所以通常只在生产构建里开启，用环境变量区分两份配置。

如果引入了完整的 UI 框架或工具类 CSS，产物里可能有大量从未使用的选择器。PurgeCSS 一类工具的思路是扫描模板与 JS 文件，提取出现过的类名，删掉没有匹配到的规则。它在“类名都是字面量”的项目里效果明显，但风险也在这里：动态拼接的类名、服务端渲染的模板、第三方组件内部生成的类名，都可能被误删。稳妥的做法是先只生成报告、人工比对，再决定是否启用，并给关键前缀留白名单。

图片处理的关键是阈值。url-loader 的 limit 决定多大的文件会被转成 base64 内联进 CSS 或 JS。内联省掉一个请求，但会让宿主文件变大、失去独立缓存，而且 base64 编码本身会让体积增加约三分之一。常见的做法是把阈值设在几 KB，只内联图标这类小文件；大图交给压缩工具处理，并且在构建之外完成，避免每次构建都重复压缩。

字体是另一个大头。中文字体文件通常有几 MB，全量引入会让首屏等待很久。可行的做法是子集化：只保留页面实际用到的字符集，用 fontmin 之类的工具生成子集；或者退一步，使用系统字体栈，把自定义字体限制在标题等少量文本上。font-display: swap 可以让文本先用后备字体渲染，避免长时间空白，但它不减少字节数。

预加载与懒加载的配合

动态导入默认是懒加载：用户点到才去下载。这解决了首屏，却带来一个新的体验问题——点击之后要等。预取就是在这个间隙里做文章。

webpack 4.6 起才支持两个魔法注释：webpackPrefetch 与 webpackPreload。前者告诉浏览器“这个资源以后可能要用，空闲时下载”，会在页面里插入 <link rel="prefetch">；后者表示“当前导航马上要用”，与父 chunk 并行加载，优先级更高。

两者的区别在于优先级与时机。preload 会与关键资源争抢带宽，用错了反而拖慢首屏；prefetch 在浏览器空闲时进行，代价较小，但在低端设备或弱网下仍会占用连接。webpack 3 没有这两个注释，只能手工在 HTML 里插入 <link rel="prefetch">，或者借助 preload-webpack-plugin 在构建时按 chunk 生成。

策略上，只预取“下一步大概率会去”的路由，比如列表页预取详情页；不要给所有路由都加上 prefetch，那等于把懒加载又变回全量加载，只是把下载时间推后了。首屏关键资源则相反，应该尽量少而精：主 chunk 只包含框架、路由与首屏组件，其余全部切开。

还有一个容易忽略的点：预取的效果依赖缓存。如果静态资源没有设置合理的 Cache-Control，用户第二次进入时仍要重新下载，预取就白做了。这与前面讲的 contenthash 是同一件事的两面。

externals 与 CDN 的取舍

把 React、Vue 这类框架放到 CDN 上，通过 externals 告诉 webpack 不要打包，是 2018 年前后很常见的做法。

HTML 里对应的 script 标签必须放在业务代码之前，并且建议带上 integrity 与 crossorigin 属性，防止 CDN 被篡改时引入恶意脚本。externals 的映射关系是“模块名到全局变量名”，写错一个字母，运行时就会得到 undefined。

收益有两块：业务 bundle 变小，首屏少下载几百 KB；公共库被大量站点使用，CDN 上的缓存命中率高，用户可能早就有一份。风险同样有两块：一是可用性，CDN 一旦故障页面就白屏，必须有备用源或本地兜底；二是版本一致性，externals 声明的全局变量与 CDN 上的版本必须严格对应，升级框架时漏改一处，排查成本很高。

到了 2018 年，HTTP/2 已经大范围部署，这件事的性价比需要重新评估。多路复用降低了“减少请求数”的收益，公共库的跨站缓存收益也不如早期明显，而额外的域名意味着额外的 DNS 解析与 TLS 握手。这是当时的判断，各家浏览器与 CDN 的策略都还在变化。笔者的建议是：如果团队没有成熟的多 CDN 容灾，优先把框架打进 vendor 并做好长期缓存，稳定性比省下的那点字节更重要。

度量与回归：让体积不再反弹

体积优化最怕“优化一次，三个月后回到原点”。要让它可持续，必须把体积纳入构建流程，而不是依赖某个人记得去看。

第一步是把数据固化。CI 里跑一次生产构建，读取 stats.json，按入口汇总 gzip 后体积，与仓库里的基线文件比较。超过阈值就让构建失败，或者至少在 PR 里留一条评论。阈值不必设得太死，可以按“主入口增长不超过 5%，单个异步 chunk 不超过 50 KB”这样的规则，关键是让增长可见、可追溯。

webpack 4 的 performance 配置可以在资源超过阈值时给出警告，作为第一道防线；它只负责提示，不能替代 CI 里的硬性比对。

第二步是人工复核，这一步不能省。体积增长不一定有问题，新增一个功能页面本来就会变大；但如果一次改动让 vendor 涨了 200 KB，就值得问一句为什么。可以在 CI 里把 webpack-bundle-analyzer 的 HTML 报告作为构建产物存档，回溯时直接打开对比。

第三步是排优先级。笔者习惯的顺序是：先删依赖，包括用不到的包、重复的版本、整包引入的写法；再拆分与按需，包括路由懒加载、公共依赖抽取、预取；最后才抠压缩参数与 tree shaking 细节。原因很实际：前两步收益大且可解释，后两步的收益依赖代码结构，调参空间往往不如预期。反过来的顺序，先折腾压缩器，通常只能得到几个百分点的改善，却消耗大量时间。

最后别忘了验证真实体验。体积下降不等于首屏变快，如果关键请求变多、链路变长，用户感知可能没有改善；每次上线后对比首次可交互时间，才能确认方向是对的。

小结

打包体积优化不是一堆开关的叠加，而是一个“测量、归因、处理、回归”的循环。先建立 gzip 体积基线，用 analyzer 与 source-map-explorer 定位到具体模块；处理时按收益排序，先删掉不该进来的依赖，再做代码分割与公共依赖抽取，最后才考虑压缩与作用域提升。webpack 3 与 webpack 4 的手段大体对应，差异集中在 CommonsChunkPlugin 与 splitChunks、chunkhash 与 contenthash、以及 sideEffects 这几处，对照着改即可。把体积阈值写进 CI，优化成果才不会随时间流失。
