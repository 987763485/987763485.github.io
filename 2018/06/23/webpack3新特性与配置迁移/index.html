webpack 3 新特性与配置迁移

webpack 3 于 2017 年 6 月 20 日发布，是在 webpack 2 基础上做的一次小版本升级：配置结构大体兼容，变化集中在 Scope Hoisting、动态导入的魔法注释与构建性能。本文面向仍在使用 webpack 1 或 2、准备升级到 3 的团队，先讲清新特性，再按版本给出迁移步骤与常见报错。webpack 4 已于 2018 年 2 月 25 日发布，但大量存量项目仍停留在 3，本文只讨论 3 的配置与迁移，体积优化的完整方法不在此展开。

webpack 3 的定位（2017 年）

从版本号看，webpack 3 只是 2.x 的延续：2017 年 6 月 20 日发布 3.0，官方将其定位为一次小版本升级，没有推翻配置结构，多数 webpack 2 项目改几行配置就能跑起来。对业务项目来说，升级到 3 的风险远小于直接升 4，收益却已经覆盖了日常构建的主要痛点。真正值得关注的是三件事：Scope Hoisting 通过 ModuleConcatenationPlugin 把多个模块合并进同一个函数作用域，减小产物体积；围绕动态导入的魔法注释让 chunk 命名与预取更可控；构建性能持续优化。3.x 后期加入的 webpackPrefetch，也让按需加载的体验更好。

为什么还要专门写 3？因为 webpack 4 已于 2018 年 2 月 25 日发布，引入了新的模式配置，但生态里的 loader 与 plugin 需要时间跟进，不少团队的存量项目仍在 3 上维护。把 3 的配置吃透，既是当下维护的需要，也是将来升级 4 的铺垫。本文只讲 3 的特性与从 1 或 2 迁移到 3 的步骤，不展开完整的体积优化方法论，loader 与 plugin 的内部原理也另有专文。

Scope Hoisting：合并模块作用域

在 2017 年上半年的 webpack 2 项目里，每个模块都会被包进一个函数，产物是一个模块数组加一个 __webpack_require__，模块之间靠它互相引用。这种写法通用，但每个模块都有一层函数包装的固定开销，跨模块调用要经过运行时函数，压缩工具也难以跨模块分析。

Scope Hoisting 把满足条件的模块按依赖顺序拼接进同一个闭包，模块间的引用直接变成同一作用域里的变量引用，包装函数和运行时调用都少了，产物体积随之下降。合并之后，压缩工具能看到跨模块的常量与调用关系，未使用的导出也更容易被判定为死代码。启用方式是在插件数组里加入 ModuleConcatenationPlugin：

它有三个限制。第一，只对 ES module 生效，源码必须使用 import 与 export；被 Babel 转成 CommonJS 的代码、AMD 模块不会参与合并，因此要把 babel-preset-env 的 modules 设为 false。第二，动态 import() 会产生新 chunk，合并在 chunk 边界停下。第三，它和 tree shaking 分工不同：tree shaking 删除没有被使用的导出，Scope Hoisting 合并模块作用域，前者做减法，后者做合并，可以叠加使用。

Scope Hoisting 会让构建稍慢，调试时的调用栈也和源码结构不完全一致，所以通常只在生产配置里开启，开发环境保持默认即可。

代码分割的入口是 import()。在 2017 年发布的 webpack 3 中，不写注释时，构建结果会用数字给异步 chunk 编号，产物形如 0.bundle.js，既不直观，也不利于缓存。魔法注释写在 import() 的括号里，用来指定 chunk 名称与预取行为：

预取用 webpackPrefetch: true：父 chunk 加载完成后，浏览器空闲时插入 <link rel="prefetch"> 下载资源，适合下一步大概率会打开的页面。webpackPrefetch 从 2017 年发布的 webpack 3.6 开始支持。它对浏览器的要求是支持 <link rel="prefetch">，老浏览器会直接忽略，属于渐进增强。预加载用 webpackPreload: true，会在父 chunk 加载时插入 <link rel="preload">，优先级更高；但 webpackPreload 直到 webpack 4.6 才加入，webpack 3 中不可用。

还有一点容易忽略：注释必须保留到 webpack 解析阶段。Babel 与 TypeScript 一般不会删注释，自定义的转译链路要确认没有把它清掉，否则命名会退回数字。

webpack 3 没有 splitChunks，公共代码抽取全靠 CommonsChunkPlugin。它的作用是在多个入口或异步 chunk 之间找出重复模块，提取成单独的 chunk，让浏览器只下载一次，并借助文件名哈希长期缓存。

配置顺序会影响结果，manifest 必须放在最后；抽取粒度过细会产生大量小文件，通常 vendor 加 manifest 两层就够了。webpack 4 之后这套插件被新的分包配置接管，但那是升级到 4 才需要考虑的事。

从 1 迁移到 3：配置结构整体翻新

从 1 直接升到 3，跨度最大的是配置结构。2.x 已经做过一轮不兼容调整，3 沿用下来，按下面的清单逐项替换即可。

module.loaders 改为 module.rules；preLoaders、postLoaders 改为在 rules 里加 enforce: 'pre' 或 'post'。loader 链从 loaders: ['style-loader', 'css-loader?modules'] 改为 use 数组，参数放进 options，查询字符串写法不再推荐；-loader 后缀可以省略，style 等价于 style-loader。

resolve.extensions 的默认值在 webpack 1 时代（2016 年及以前）是 ['', '.webpack.js', '.web.js', '.js']，升级后变成 ['.js', '.json']，空字符串不再允许，路径必须带扩展名，用到 .vue、.ts 时要显式补上。resolve.root、resolve.modulesDirectories 合并为 resolve.modules；output.path 必须是绝对路径。原来用 resolve.root 指定源码根目录的项目，要把它挪到 resolve.modules 数组的第一位，否则绝对路径导入会失效。

OccurrenceOrderPlugin 已内置，重复声明没有意义；DedupePlugin 被移除；NoErrorsPlugin 改名为 NoEmitOnErrorsPlugin；json-loader 不再需要，webpack 2 起原生支持 JSON，可以连同依赖一起删掉。

迁移时建议先只改结构、不升依赖，确认能构建后再逐个升级 loader，出错时更容易定位是哪一类改动引起的。

从 2 迁移到 3：清理过渡配置

webpack 2 到 3 没有破坏性变更，重点不是改结构，而是清理当年为了兼容 1 代留下的过渡配置，并把插件升到支持 3 的版本。

LoaderOptionsPlugin 是 webpack 2 为老 loader 准备的桥接插件，用来把 minimize、debug、context 等选项传给仍在读旧接口的 loader。到 3，主流 loader 都已适配新 schema，这个插件通常可以删掉；只有个别多年未更新的 loader 仍依赖它，遇到报错再加回来，并尽量换成维护中的替代品。

UglifyJsPlugin 仍是内置的压缩插件。生产环境如果通过 devtool 生成了 source map，要传 sourceMap: true，否则压缩后的代码与 map 对不上，报错行号会指向压缩后的位置；不需要 source map 时保持默认的 false，避免无谓开销。压缩告警可以用 compress.warnings: false 关闭。

ExtractTextPlugin 要选 3.x，它与 3 的插件 API 匹配。用 2.x 搭配 3 时，常见现象是构建刷出 Chunk.entrypoints 弃用警告，严重时样式抽取异常；升级插件并确认 loader 写在 use 里，一般就能解决。

开发环境通常还会加 NamedModulesPlugin，让 HMR 日志与报错显示模块路径而不是数字 id，排查热更新问题时方便很多。它只应出现在开发配置中；生产环境若在意模块 id 稳定，用 HashedModuleIdsPlugin。HMR 由 HotModuleReplacementPlugin 与 devServer.hot 配合，升级后手动改一个组件，确认是局部更新而不是整页刷新。如果升级后 HMR 变成整页刷新，先检查 devServer.hot 是否开启、入口是否执行了 module.hot.accept，再确认开发环境没有误用样式抽取插件。

构建性能：先测量，再选手段

构建速度的优化要建立在测量之上：先看时间花在 loader、压缩还是解析上，再决定加什么。下面几项是 3 时代最常用的手段，各有适用边界。

cache: true 打开模块缓存，watch 模式下重复构建会复用上次结果；它是进程内缓存，重启即失效，适合开发阶段。缓存会额外占用内存，CI 环境通常不值得开启，本地开发收益更明显。include/exclude 用来缩小 loader 的处理范围，例如 Babel 只处理 src 目录、排除 node_modules，避免把大量第三方代码送进转译。

解析侧可以配置 resolve.modules，把源码目录放在 node_modules 之前，减少逐级向上查找；resolve.alias 给常用路径建短别名；resolve.extensions 保持精简并按命中频率排序。这一步对目录层级深的项目效果明显，但不要把 node_modules 从列表里去掉。

DLL 把变动很少的第三方库预先打包，业务构建通过 DllReferencePlugin 引用，跳过重复编译。它适合依赖多、库版本稳定、构建明显偏长的大型项目；小项目引入只会增加维护成本。DLL 生成的 manifest 要纳入版本管理或构建流程，否则业务构建找不到映射，配置会直接报错。随着 vendor 抽取与缓存策略成熟，DLL 的必要性在下降，是否保留以测量为准。

多线程 loader 同理：happypack 把 loader 放进子进程，thread-loader 把后续 loader 交给 worker 池，能缓解 CPU 密集的转译压力，但进程通信和内存占用也有成本，只在 Babel 处理量大、单线程确实成为瓶颈时引入。不要照搬别人的加速配置，也不要把未经测量的数字写进团队规范。

常见报错与排查

Cannot find module 'xxx-loader'：先确认依赖是否装进 devDependencies，再检查名字；2.x 起可以省略 -loader 后缀，新旧写法混用容易出错。全局安装的构建工具与本地 loader 不是同一套，统一用 npm scripts 调用本地版本；报找不到构建工具本身时，多半是全局 CLI 找不到本地包，删掉全局版本、改用脚本调用即可。

loader 版本不匹配：典型表现是构建直接抛错或出现奇怪的 AST 报错，例如 2.x 的 ExtractTextPlugin 配 2017 年发布的 webpack 3.x、sass-loader 与 node-sass 不配套。用 npm ls 检查依赖树里是否装出多份构建工具，升级时成组升级构建工具、dev-server、loader 与 plugin。

Module not found: Can't resolve './xxx' 多数是扩展名或大小写问题：resolve.extensions 没有包含 .vue、.ts，或者 Linux 上文件名大小写与导入路径不一致。

Chunk.entrypoints 警告：完整信息是 Use Chunks.groupsIterable and filter by instanceof Entrypoint instead，来自仍在使用旧 API 的插件，最常见的是 2.x 的 ExtractTextPlugin。它通常不影响构建，但说明插件该升级了。

CSS 顺序问题：抽取后的样式顺序取决于模块引用顺序与 chunk 生成顺序，多入口、异步 chunk 混用时容易错乱。先确认样式在入口处按期望顺序引入，再检查 allChunks 配置；不要依赖“先构建的 chunk 样式在前”这类假设，关键样式最好在入口统一引入。如果样式跨越多个入口，最好把基础样式单独抽成一份，避免同一选择器在不同页面出现不同优先级。

process.env.NODE_ENV 未替换：浏览器里没有 process 对象，源码中的变量必须由 DefinePlugin 在构建时替换，否则轻则开发告警不消失，重则直接报 process is not defined。值是 JSON.stringify('production')，webpack -p 会顺带注入，但显式配置更利于排查。

迁移检查清单

把上面的内容收拢成一条可执行的路径：

flowchart TD
    A[升级 Node 到 8 LTS] --> B[锁定 webpack 与插件版本]
    B --> C[逐项替换配置]
    C --> D[开发构建与 HMR 回归]
    D --> E[生产构建与产物对比]
    E --> F[页面功能回归与灰度发布]

检查项如下：Node 至少升到 8 LTS，老版本 Node 无法运行新版依赖；把 package-lock.json 或 yarn.lock 提交入库，保证团队与 CI 装到同一套版本；版本号统一写进 package.json，不要依赖全局命令；配置按小节逐条替换，每改一类构建一次；产物对比关注总体积、chunk 数量与文件名哈希是否符合预期；最后回归 HMR、生产构建、路由懒加载与样式。先在测试环境用生产配置完整跑一次，再切换线上流量；迁移期间保留一个可回滚的分支，比事后补救更省事。

小结

webpack 3 是 2017 年发布的一次小版本升级，以 Scope Hoisting 和性能为主，配置结构与 2 基本一致，真正的工作量集中在从 1 迁移时的结构翻新，以及从 2 迁移时的过渡配置清理。Scope Hoisting 只对 ES module 生效，和 tree shaking 分工不同；魔法注释让异步 chunk 的命名与预取可控，但 preload 在 3 中尚未可用；CommonsChunkPlugin 仍是这个版本抽取公共代码的唯一选择，vendor 加 manifest 是最稳妥的组合。迁移时先升 Node、锁版本，再逐项替换配置，最后用产物对比和 HMR 回归收尾，比一次性大改更容易控制风险。
