分布式缓存一致性方案

本文属于《Go 微服务架构》第 29/35 篇
上一篇系列目录下一篇

缓存几乎是把读性能从数据库里“偷”出来的最便宜手段，可一旦同一份数据存了两处，读写顺序和失效时机就成了必须交代的问题。本文从商品详情的读接口出发，讲清不一致是怎么产生的，几种主流方案各把窗口压到多长，以及真实系统里最常踩的坑。

本文面向已经会在业务里加一层 Redis、但还没系统整理过失效策略的开发者。读完之后，你应当能为一个具体接口选出合适的方案，并且知道它在什么情况下会退化成“看起来很快、偶尔返回旧数据”。

不一致是怎样产生的

先从商品详情接口说起。读请求先查 Redis，未命中再查 MySQL，然后回填并设置过期时间；写请求更新 MySQL 的价格，同时让对应缓存失效。这就是 cache-aside（旁路缓存），绝大多数业务系统用的都是它。

问题在于，MySQL 和 Redis 是两个独立系统，没有一个本地事务能同时覆盖两者。写操作必然被拆成“改库”和“动缓存”两步，两步之间只要有可能失败、有可能被其他请求插入，就会出现一段两种存储读数不同的时间。本文把这个时间段称为不一致窗口，一致性问题本质上就是如何把它压到业务可以接受的长度。

那为什么不直接更新缓存，而要删除？原因有四条。

第一，更新缓存会被并发写覆盖。两个写请求先后改同一行，库里最终是后者的值；若更新缓存的顺序反过来，缓存里留下的却是前者的值，要等过期才纠正。

第二，更新缓存可能白算。缓存值常是多表拼装的结果，写多读少时每改一次就重算一次，算完可能没人读。

第三，删除只表达“这份数据不可信了”，不关心缓存原来是什么；更新则要求写入者完整掌握缓存值的构造方式，多一条写入路径就容易写出残缺的值。

第四，缓存里可能有本不该存在的值，比如被风控过滤掉的字段、空结果占位。它们只能靠重走读路径产生，删除后由读请求重建更可靠。

代价也很明确：删除之后的第一次读必然未命中，回源压力集中在那一下。这与缓存击穿属于同一类问题，本文不展开，只提醒一句：删除策略必须和回源保护一起设计。

cache-aside：先更新数据库再删缓存

顺序上有四种组合，结论可以直接列成一张表。

顺序 结果 评价
先删缓存，再更新库 删除后、更新前的读请求会把旧值回填，之后长期是旧值 不可用
先更新库，再删缓存 窗口只在两步之间，窗口内读到旧值 推荐
先更新库，再更新缓存 并发写时缓存可能停在较早的值 不推荐
先更新缓存，再更新库 库写失败则缓存成为脏数据 不可用

“先删缓存再更新库”之所以危险，是因为删除动作清空了唯一的正确副本，而数据库还没变。此时任何一个读请求都会把旧值重新装回缓存，等写完库也不再有人去删它，不一致会一直持续到过期。

“先更新库再删缓存”的不一致窗口只有两步之间那一点时间，而且最坏情况是读到旧值，不会长期留脏。实现时要注意两点：删除必须发生在事务提交之后；删除失败不能把已经成功的写操作报成失败。

读路径同样要克制：只回填完整对象；未命中回源要加保护，避免一次删除把数据库打穿；TTL 要有上限，它是所有兜底手段里最后生效的一层。

删除失败之后：重试与补偿

删除不是本地内存操作，而是一次跨网络的调用。Redis 抖动、连接池耗尽、key 恰好落在正在迁移的槽上，都会让 DEL 失败。此时数据库已经提交，缓存还是旧值，这一段就是纯亏损的不一致窗口。

原则有三条：不回滚数据库，因为回滚会把一次成功的写入变成失败，而删除失败通常发生在提交之后；不把错误抛给调用方，因为写操作确实成功了，返回失败会诱导上游重试，产生重复写入；必须让删除有第二次机会。

待删除的 key 要落到一张表（或磁盘队列加副本），不能只放在进程内存里，否则重启后那批 key 就永远脏着。删除是幂等的，重复执行只是多一次 DEL，所以重试天然安全。

重试要设上限与退避。超过若干次仍失败就告警，让人确认 Redis 是否整体不可用，而不是无休止空转。重试任务也要限速，否则 Redis 恢复瞬间，积压的删除会变成一次小流量冲击。

如果读请求走的是从库，还有一个更隐蔽的问题：主库更新成功、缓存删除成功，但紧接着的读请求落到尚未同步的从库，读到旧值并回填。此时代码里没有任何一步失败，缓存却脏了。常见对策是写后一段时间内强制读主，或把第二次删除推迟到主从延迟之外。

延迟双删及其局限

延迟双删是对上面这个回填竞态的补丁：更新库之前删一次，提交之后再删一次，第二次删除延迟一小段时间执行。第一次删除让旧缓存提前消失，第二次删除负责清掉在更新期间被读请求塞回去的旧值。

sequenceDiagram
    participant W as 写请求
    participant R as 读请求
    participant DB as MySQL
    participant C as Redis
    W->>DB: 更新并提交
    R->>C: 读缓存，未命中
    R->>DB: 回源，读到旧值
    W->>C: 删除缓存
    R->>C: 回填旧值
    Note over C: 缓存留下旧值
    W->>C: 延迟后再删一次
    Note over C: 旧值被清掉，窗口结束

第二次删除不是万能的，效果完全取决于延迟时长：太短，读请求还没回填完，删了等于没删；太长，窗口被自己拉长。主从延迟本身在波动，一个固定值很难两头都占。

现实中还有几处约束。第二次删除同样可能失败，仍需重试兜底；同步 sleep 会白占请求处理时间，应改成延迟任务；第一次删除收益有限时可以省掉，只留提交后删除加异步补偿。

因此在方案选型里，延迟双删的定位是“用很小的改造成本把窗口压短一个量级”，而不是“解决一致性”。它不消除竞态，只让竞态发生在一个更短、更容易被 TTL 兜住的时间段里。

订阅 binlog：把失效从业务代码里移出去

前面几种做法的共同点是“由写业务负责删缓存”，只要有一条写入路径忘了删，或者顺序写错，就留下脏数据。更彻底的做法是让失效不再依赖业务代码，而由数据库的变更日志驱动。

MySQL 的 binlog 记录每一行变更。Canal 把自己伪装成一个从库，向主库注册并拉取 binlog，解析成结构化事件再投递出去。业务侧只负责写库，失效交给下游消费者。

flowchart LR
    A[业务写入 MySQL] --> B[binlog]
    B --> C[Canal 解析]
    C --> D[Kafka 投递]
    D --> E[失效消费者]
    E --> F[Redis DEL]

这条链路有几个必须交代的细节。

binlog 格式要设成 ROW。MySQL 5.7 和 8.0 都支持多种格式，只有 ROW 能拿到变更前后的完整行值；statement 记的是 SQL 语句，解析时无法还原“这一行变成了什么”，也就判断不出哪些缓存 key 受影响。

分区要按主键做。同一行的多次变更必须进入同一个分区，消费者才能按顺序处理；一旦乱序，先发出的“更新”可能晚于后发出的“再更新”生效，缓存就停在一个中间值上。

消费必须幂等。Kafka 2.6 的默认投递语义是至少一次，重复消息很常见。好在失效动作是删除，重复删除没有副作用，这正是选择“删除”而不是“写入新值”的又一个好处。

多副本要各自失效。每个实例、每个机房都有本地缓存时，就用消费者组广播（每个实例独立 group）让所有副本收到同一条消息；本地缓存没有共享存储，广播往往是唯一可靠的办法。

代价是链路变长。Canal 要高可用、维护位点、处理 DDL 变更；Kafka 要保证不丢消息；从写入到失效的耗时也从毫秒级变成秒级，具体取决于部署，必须实测。它适合写入路径多、缓存维度多的团队，不适合两三个写接口的小服务。

还有一处容易漏：Canal 只知道“哪张表的哪一行变了”。若缓存值是三张表拼出来的，就得维护一张映射，说明哪些表影响哪个 key。这张表往往是方案里最先腐化的部分，要跟着代码一起评审。

版本号与逻辑过期

不管是同步删除还是订阅 binlog，最终都要回答：回填时手里的值是不是最新的？版本号把这个判断显式化。

给每行数据维护一个递增版本（自增的 version 字段，或用更新时间戳代替），读取时把版本一起带出来，回填前先比较缓存里记录的版本：手里的版本更旧，就放弃这次回填。

比较与写入要用 Lua 或事务包起来，否则中间仍会被插进一次更新。版本号把“谁先谁后”从时间问题变成大小问题，不再依赖时钟；代价是每次写都要维护版本，读路径多一次判断。

逻辑过期走的是另一条路：缓存不设 TTL 或设得很长，值内部带一个 expireAt 字段。读到已经逻辑过期的数据时，先把旧值返回给调用方，同时异步刷新。它把失效瞬间的回源压力摊平了，但也明确承认会返回旧值。

刷新必须只由一个执行者做，常用一把短期分布式锁选主，持有时间短于业务超时，拿不到就放弃，等下次读再触发。锁在这里只是去重工具，不是一致性保证。

这个取舍很直白：用“可能返回过期数据”换“不会因为失效而抖动”。商品描述、榜单这类能容忍几十秒旧值的读场景可以用；订单状态、库存余额这类字段不适合。

把窗口量化，再谈方案

方案之间的差别，说到底是窗口长度和实现成本的差别。以“更新库后删缓存加失败重试”为例，从提交到缓存不再返回旧值，大致经过四段。

组成 含义 缩短手段
删除耗时 一次 DEL 的网络往返 同机房部署、复用连接
重试等待 失败到补偿成功的间隔 提高重试频率、加告警
主从延迟 从库追上主库的时间 关键读走主库、半同步复制
回填竞态 旧值回填后再次被清掉 版本号校验、延迟删除

这张表要配上真实数据才有意义。可行的做法是在读路径埋点，统计“缓存版本落后于数据库”的请求比例与持续时长，看分布而不是平均值：平均值会被大量正常请求稀释，真正伤人的是尾部那几秒。

剩下几个坑，几乎每个项目都会踩到其中一个。

事务边界最常见。提交前删缓存，等于提前告诉别人“可以来回填了”，而新值还不可见，读请求填回去的必然是旧值。删除要挂在提交成功的回调上。

批量失效要限速。更新上万条后逐条 DEL，或用 KEYS 按前缀扫描，都会占满 Redis 的单线程。应改为 SCAN 分批、控制并发，或合并成一次任务。

热点 key 与批量失效叠加时最危险：一个被大量读的 key 刚被删，回源会同时涌向数据库。回源保护属于缓存击穿的话题，这里只强调一句：删除策略必须和它配套上线。

最后是心态。跨两个存储的写不可能强一致，除非永远读主库。接受最终一致，并明确写出“允许多久的不一致”，比在代码里堆技巧有效。

小结

缓存一致性没有银弹，只有窗口长度和实现成本的权衡。多数系统从“先更新库、提交后删缓存、删除失败进重试队列”起步就够了。需要更短的窗口，再考虑延迟双删、binlog 订阅或版本号校验。无论选哪种，都要把窗口量化出来，并用带 TTL 的兜底守住下限。真正的护城河不是某个技巧，而是“所有写入路径都走同一个失效出口”这条纪律。
