Rust 错误处理在业务代码中的组织

本文属于《Rust 学习路线》第 21/68 篇
上一篇系列目录下一篇

Rust 把“可能失败”写进了类型系统：一个操作要么返回成功值，要么返回一个错误值，编译器会逼着调用方做出选择。可一旦进入业务代码，问题就从“要不要处理错误”变成了“错误类型怎么设计、在哪一层转换、日志在哪打、对用户暴露什么”。本文从 Option 与 Result 的分工讲起，依次讨论 ? 与 From、thiserror 与 anyhow 两条路线、错误上下文与入口兜底，最后落到错误分类、测试断言和几个高频的坑。读者最好已经写过一些 Rust，能看懂泛型与 trait，但还没有系统整理过错误处理的工程结构。

本文的示例基于 Rust 1.50 与 2018 edition，提到的第三方库只涉及 2021 年初已经稳定的 thiserror 1.x 与 anyhow 1.x，不讨论异步运行时的选型细节。

一、Option 与 Result：两种“不顺利”的语义分工

Rust 标准库用两个类型覆盖了绝大多数“不顺利”的情况：Option<T> 表示“可能有值，也可能没有”，Result<T, E> 表示“操作可能成功，也可能失败，失败时带一个原因”。两者都是枚举，都可以用 match、if let 和组合子处理，看起来很像，语义却完全不同。把二者混用，是业务代码里最常见的第一类问题。

Option 回答的是存在性问题：这个键在映射表里吗？这一行查到了吗？用户是否配置了昵称？“没有”是一个完全正常的答案，不需要解释。Result 回答的是动作的结果：读文件、发请求、扣库存、解析配置，这些动作失败时，调用方通常需要知道“为什么失败”，才能决定重试、提示用户还是上报。用 Option 表达失败，等于把原因扔掉了；用 Result<(), ()> 表达失败，则是把原因换成了一个没有信息量的占位符。

两者可以互相转换，但方向要选对。Option::ok_or 与 ok_or_else 把“没有”升级为“错误”，适合上层确实需要错误语义的场景，比如接口要求返回 404 而不是一个空对象。反过来，Result::ok() 会把错误吞掉，只保留成功值，除非调用方真的不关心失败原因，否则不要用。还有一个细节：ok_or 会立即构造错误值，即使 Option 是 Some；错误构造有成本时用 ok_or_else，把构造推迟到真正需要的时候。

在业务层，笔者建议把这条规则写进代码评审清单：函数签名里的 Option 只用于“存在与否”，凡是“做一件事但可能失败”，一律用 Result。这条规则看似教条，却能省掉大量“为什么这里返回 None”的追问。

还有一种常见的过度设计，是把可选值和失败叠成 Option<Result<T, E>>。这个类型有三层含义：没有值、有值但失败、有值且成功，调用方要嵌套 match 两次才能拿到结果，语义非常模糊。真遇到三态，不如定义一个枚举，把“未开始”“成功”“失败”写成三个有名字的变体；如果只是“可能没有”，就用 Option，不要提前为不可能的组合建模。

From 的价值在于解耦：业务函数不必知道仓储层用的是 MySQL 还是内存表，只要错误能转换过来。但自动转换也是一把双刃剑。? 只做类型转换，不附加任何上下文，等错误一路冒到入口，往往只剩一句“database error”，至于是哪条 SQL、哪个订单，已经无从查起。所以 ? 负责“传”，上下文要靠下一节讲的 context 或自定义错误变体来补。

手写 From 在错误变体多时会很啰嗦，thiserror 的 #[from] 可以自动生成；而 anyhow 为所有满足 std::error::Error + Send + Sync + 'static 的类型提供了到 anyhow::Error 的转换，所以在返回 anyhow::Result 的函数里，? 几乎可以直接用于任何标准错误。这也解释了一个常见现象：同一个项目里，底层函数返回具体错误类型，上层函数返回 anyhow::Result，? 把两者缝在一起。

需要提醒的是，? 也能用于返回 Option 的函数，此时 None 会提前返回。但 Option 与 Result 不能直接混用：在返回 Result 的函数里对 Option 用 ?，编译器会报类型不匹配，必须先 ok_or 或 ok_or_else 转成 Result。这个报错在新手里出现频率很高，记住“先升级语义，再传播”即可。

孤儿规则也值得知道：你只能为自己 crate 的类型或自己 crate 的 trait 实现 From。给外部错误类型实现 From<外部类型> 通常不可行，这时要么在自己的错误类型上写 From（目标是自己的类型，合法），要么用 map_err 在调用点做一次性转换。后者代码更长，但转换逻辑就在眼前，反而更清楚。

? 不是强制品。需要在出错时补充信息、回滚事务或转换分类时，显式 match 更合适；? 适合“这一层没什么可做，交给上层”的场景。判断标准不是代码长短，而是这一层是否真的能对错误做出有意义的处理。

三、两条路线：库用 thiserror，应用用 anyhow

标准库的错误抽象是 std::error::Error trait：它要求实现 Display 与 Debug，并提供默认返回 None 的 source() 方法，用来指向“导致当前错误的上一层原因”。手写这套实现并不难，但每个错误类型都要重复一遍 fmt 与 source，变体一多就非常枯燥。thiserror 把这个模板变成了派生宏，适合定义“调用方需要匹配”的具体错误类型。

这个枚举同时给出了三样东西：稳定的变体供调用方 match，面向人的 Display 文案，以及可追溯的 source 链。#[from] 让 ? 可以直接把 GatewayError 转成 PaymentError，#[source] 则用于“有来源但不需要自动转换”的字段。库作者应优先选择这条路线，因为库的调用方需要根据错误种类做不同处理，类型擦除会让这件事变得困难。

应用侧的情况不同。一个服务通常只在少数几个边界上处理错误：写日志、转 HTTP 响应、决定是否重试。此时为每个函数定义一个新枚举，收益很低，anyhow 更合适。它提供一个类型擦除的 anyhow::Error，可以包裹任意标准错误，附带一串上下文，还提供 anyhow::Result<T> 作为默认错误类型的别名。

如何选，可以用一句话概括：错误类型是给别人看的契约，就用具体枚举；错误只在自己进程里流动，就用 anyhow。由此还能推出一条硬规则：不要让 anyhow::Error 出现在库的公开 API 里。它不能 Clone，匹配变体要先 downcast，调用方也无法从签名看出可能失败的种类。反过来，应用内部也完全可以保留领域错误枚举，在最外层再统一包成 anyhow::Error，两者并不互斥。

还有一层常被忽略的契约：source() 链。库的错误类型一旦发布，变体名称、字段含义与 Display 文案都会进入依赖者的测试和日志，增删变体属于破坏性变更，这也是 #[non_exhaustive] 的价值所在。应用侧则可以放心依赖 anyhow 的链式结构，用 err.chain() 逐层取出原因，做结构化日志或上报；但不要把链上的文案当接口，它只是诊断信息。一个实用的折中是：库对外暴露具体枚举，同时提供返回 anyhow::Result 的便利入口，并明确后者只是便利层，不承担匹配职责。

四、错误上下文：context 与 with_context

anyhow::Context 为 Result 和 Option 都提供了扩展方法。context 接收一个实现了 Display 的值，with_context 接收一个返回该值的闭包。区别在于求值时机：前者无论成功失败都会构造消息，后者只在错误发生时才调用闭包。上下文里往往要拼接订单号、路径、用户输入，格式化有分配成本，所以带动态内容时优先用 with_context。

上下文应该回答“在做什么、对象是谁”，而不是重复底层错误已经说过的内容。每一层加一条就够了：仓储层说“查询订单 42 失败”，业务层说“取消订单失败”，入口层说“处理取消订单请求失败”。三条信息串起来，排障时能还原出完整路径；如果每层都写“数据库错误”，链条再长也没有增量信息。

打印方式决定了这些信息能不能被看见。Display（{}）只输出最外层的消息，Debug（{:?}）会输出完整的原因链，{:#} 则把链条用冒号连接成一行。日志里应该用 {:?} 或 {:#}，否则辛苦附加上下文就白费了。自定义错误类型时也要注意：Display 只写自己的那句话，把底层错误留给 source()，不要在文案里再拼一遍，否则同一句话会在链条里出现两次。

Context 也能用在 Option 上，把 None 转成带说明的错误，这在“配置项必须存在”的场景很好用。但上下文不是越多越好：同一层里对同一个错误连续加三条 context，读起来像流水账。一条能定位“做什么、对象是谁”的上下文，胜过三条重复的“失败了”。

日志有一条简单原则：同一个错误只在一个地方记录。每层都 log::error! 一遍，结果是同一件事在日志里出现五次，还互相掩盖了真正的边界。系统错误在入口以 error 级别记录完整链条，并附上请求标识；用户输入错误用 info 或 warn 记录简短信息即可，不必打回溯。密钥、令牌、完整身份证号这类内容不能进日志，上下文里只放标识符。至于 panic，它适合“不变量被破坏”的程序缺陷，不适合可预期的失败；异步任务里的 panic 通常由运行时捕获并终止该任务，但连接与中间状态未必干净，所以更要把预期失败放进 Result。

还有一类错误值得单独对待：启动阶段的错误。配置缺失、端口被占用、数据库连不上，这些失败继续运行也没有意义，应该在启动时快速失败，打印清晰的排查线索后退出，而不是等到第一个请求进来才暴露。运行期的错误则相反，单个请求失败不应该拖垮进程，能降级就降级，不能降级就返回 5xx 并让监控接管。把这两类错误分开，进程的生命周期会清楚很多。

六、错误分类：能否重试、谁来负责

错误一旦要跨越进程边界，就必须回答两个问题：这是用户的问题还是系统的问题？重试有没有意义？把这两个维度交叉，可以得到四类：用户错误且不可重试（参数非法、无权限）、用户错误但可重试（并发冲突，重新读取后可能成功）、系统错误且可重试（下游超时、连接被拒）、系统错误且不可重试（配置缺失、数据结构损坏）。分类不是学术练习，它直接决定 HTTP 状态码、日志级别、告警和重试策略。

让领域错误实现 Classify，适配层只依赖这个 trait 做映射，新增错误变体时只需要补一个 match 分支。HTTP 映射放在适配层，典型对应关系是：参数错误 400、未找到 404、冲突 409、暂时不可用 503、其余 500。503 可以附带 Retry-After，告诉客户端多久之后再来；500 不应该暴露内部细节，响应里给一个追踪号，细节留在日志里。

重试策略同样由分类驱动：只对标记为可重试的错误重试，只对幂等操作重试，并且只在一层重试。仓储层重试、服务层再重试、网关还重试，一次故障会被放大成几十次调用，这就是重试风暴。重试要加上退避与抖动，设置次数上限，并记录重试指标，否则失败会被掩盖成“慢”。

指标与日志的标签也应围绕分类设计。计数器用 kind、operation 这类低基数标签，能画出“哪类错误在上涨”；不要把用户 id、订单号、错误原文放进标签，基数爆炸会拖垮时序数据库。用户可见文案与内部诊断信息要分开：前者稳定、友好、不泄露实现；后者详细、只在日志里出现，两者靠错误码或追踪号关联。

分类应该由错误本身决定，而不是由 HTTP 层反推。kind() 放在领域层，映射表放在适配层，领域错误不必知道 404 与 503 的区别。这样换一个 gRPC 或命令行入口时，只需要写一张新的映射表，分类逻辑不用重写。反过来，如果错误枚举里直接出现 BadRequest、NotFound 这样的命名，领域层就被协议绑住了，调用方也会开始依赖状态码而不是错误语义。

错误码的设计也服务于分类：对外用稳定的数字或字符串标识，内部用它关联日志与文档。错误码一旦发布就不要复用，新增错误时分配新码，废弃的码保留说明。这样客户端可以按码分支，服务端也能在不改码的前提下调整文案。

七、模块边界：隐藏内部错误类型

模块对外暴露的错误类型，和它的函数签名一样，是契约的一部分。如果仓储层直接把 sqlx::Error 或 reqwest::Error 放进公开返回值，上层就被绑在了具体实现上：换驱动、升级大版本、甚至只是换一个连接池，都可能让调用方的 match 失效。更糟的是，基础设施错误的文案往往包含 SQL、主机名、内部路径，这些不应该出现在面向用户的响应里。

正确的做法是每个模块定义自己的错误枚举，在边界处把内部错误映射过去。公开枚举加上 #[non_exhaustive]（Rust 1.40 起稳定），允许以后新增变体而不算破坏性变更，调用方的 match 必须带兜底分支。

这段映射有两个要点。第一，语义相同的错误要合并，DbError 的十几种变体对上层没有意义，上层只关心“不存在”“重复”“不可用”。第二，无法归类的错误不要丢弃，装进 Unavailable 并保留 source，排障时还能看到根因。这样做的代价是样板代码和一层转换，收益是稳定的契约和可控的信息暴露。anyhow::Error 同样不应该出现在库的公开 API 中，它适合留在应用内部。

From 用起来顺手，但它是隐式的：读代码时看到一个 ?，未必知道错误被映射成了哪个变体。对于会丢失信息的转换，宁可写一个具名函数 map_db_error，在函数名和注释里说清楚规则；对于一一对应的转换，再用 From。模块边界上的映射应该有测试，至少覆盖“不存在”“重复”“其他”三条路径，否则新增一个内部变体时，很容易悄悄落进 Unavailable。

八、测试中的错误断言

测试错误时，最容易写坏的是“断言文案”。assert_eq!(err.to_string(), "订单不存在") 看似直接，实际上把用户文案变成了测试契约，改一个标点就要修一堆测试。更稳的做法是断言变体或分类，文案只在与用户明确约定的地方才断言。

unwrap_err 要求成功值的类型实现了 Debug，这是它偶尔不好用的原因；如果成功值很大或没有实现 Debug，可以用 match 手动取出错误。使用 anyhow 的应用测试，则先用 downcast_ref 拿回具体类型，再断言变体：

如果上下文本身就是契约，比如必须包含出错的文件路径，可以断言 format!("{:?}", err) 包含某个片段，但要克制：这种断言对文案调整很敏感。#[should_panic] 只用于测试 panic，不要用它测 Result，否则错误链和退出路径都验证不到。分类映射也值得单独测试：给定一个错误变体，kind() 与 HTTP 状态码应该符合预期，这比在每个接口测试里重复断言更经济。

用 anyhow 时还可以断言 err.chain() 里包含某条上下文，这比匹配整段 Debug 输出稳定。若一个错误同时有变体和上下文，先 downcast_ref 断言变体，再检查链上是否有关键信息，两层各司其职。

九、错误类型在项目结构中的落位

错误类型放在哪个文件，看似是目录习惯，实际会影响依赖方向。项目很小时，一个 src/error.rs 加一个 AppError 枚举就够了；随着模块增多，这个枚举会变成“上帝类型”：用户、订单、支付、存储的变体挤在一起，任何模块改动都要碰同一个文件，任意两个本来无关的模块也通过它产生了依赖。更麻烦的是，调用方为了匹配一个变体，不得不引入整个应用的错误类型。

比较可行的做法是按模块拆分：每个模块有自己的 error.rs，定义该模块对外承诺的错误；模块内部的实现细节用 pub(crate) 的枚举，不对外暴露。领域层只依赖自己定义的错误与端口，基础设施层在实现端口时，把驱动错误转换成领域错误。依赖方向始终指向内层，领域层不需要知道 sqlx 或 reqwest 的存在。

应用层再定义一个薄的 AppError，把各模块错误和基础设施错误组合起来，只负责分类、日志和响应映射。它不是新的“上帝枚举”，因为变体数量很少，通常就是“用户错误”“未找到”“冲突”“不可用”“内部错误”这几类，具体细节留在 source 里。这样，模块可以独立演进，入口处的映射规则也只有一份。

一个常见的反例是把 HTTP 状态码写进领域错误：UserError::BadRequest、OrderError::NotFound。领域层一旦知道 404，换一个 gRPC 或命令行入口时，这些名字就变得别扭，分类逻辑也被分散到各处。状态码属于适配层，领域层只回答“哪一类失败”。同理，日志句柄、追踪 id 也不应该塞进错误类型，它们是请求上下文，不是错误本身。

十、常见的坑

unwrap 与 expect 的滥用

unwrap 不是错误处理，它只是把错误换成了 panic。测试、一次性脚本、原型里用一用无可厚非；生产代码的请求路径上，对用户输入 unwrap 等于把一个本可以返回 400 的情况变成了崩溃或 500。确实“不可能失败”的地方可以用 expect，但要在消息里写清楚为什么不可能，让后来的人能判断这个假设是否还成立。有默认值时用 unwrap_or、unwrap_or_else 或 unwrap_or_default，不要先 unwrap 再兜底。

错误信息在转换中丢失

最常见的丢失发生在 map_err：map_err(|_| MyError::Io) 把原始错误整个丢掉，只留下一个变体名。其次是 Result::ok()，它把 Err 变成 None；再次是日志里用 {} 而不是 {:?}，原因链根本没打出来。定义错误变体时，要么用 #[from] 或 #[source] 保留原错误，要么把关键信息提取到字段里，不能既不带来源也不带细节。

Box<dyn Error> 的适用与代价

Box<dyn Error> 是最省事的统一错误类型：标准库提供了从具体错误到它的转换，? 可以直接用，适合原型、测试和小工具。代价是堆分配、动态派发和类型擦除：想拿回具体类型要 downcast，它也不能 Clone。跨线程传递时需要写成 Box<dyn Error + Send + Sync>，否则编译器不会放行。库的公开 API 不要用它，因为调用方无法从签名看出错误种类，只能靠字符串猜。

panic 与 Result 的边界

划分标准其实很简单：预期之内、调用方可能处理的失败用 Result；违反程序不变量、继续运行只会更糟的缺陷才用 panic。数组越界、unreachable!、锁中毒后状态不明，属于后者。catch_unwind 只能在边界处兜底，比如线程池的 worker，而且需要 UnwindSafe，它不是通用的错误处理机制。跨 FFI 边界更不能让 panic 展开，通常要转成错误码；如果编译时选了 panic = "abort"，连兜底的机会都没有。把这些边界想清楚，Result 与 panic 就不会互相侵占对方的地盘。

把错误当控制流

有些“错误”其实是正常分支：查询没有命中、幂等键已存在、状态机已经处于目标状态。把它们定义成错误，再在调用点立刻 match 回来，会让签名和日志都变得嘈杂，监控里也会出现大量“错误”计数。判断标准是：这个结果是否意味着本次操作没有完成预期目标？如果调用方本来就要处理它，而且它不表示任何异常，用 Option 或一个普通枚举更诚实。反过来，一旦决定它是错误，就不要在同一个函数里既返回错误又当布尔值用。

用 String 当错误类型

Result<T, String> 在原型里很常见，写起来快，但它把所有结构都压成了文本：调用方无法匹配，无法区分可重试与不可重试，也没法保留 source。等到需要分类或测试时，只能做字符串包含判断，改一个字就全盘失效。哪怕只定义一个带两三个变体的小枚举，也比 String 强；确实需要携带自由文本时，把它放进枚举的字段里，而不是让整个错误退化成字符串。

小结

Rust 的错误处理不是“把错误往上抛”这么简单，而是一套关于类型、边界与信息的设计。Option 只表达存在性，Result 才表达失败；? 负责传播与 From 转换，上下文要靠 context 补齐。库用 thiserror 定义可匹配的枚举，应用用 anyhow 串联上下文，两者在模块边界处汇合。错误要在入口统一分类、记录与映射，日志只打一次，用户文案与内部细节分开。最后，少用 unwrap，保住错误链，量一量错误类型的大小，并让测试断言变体而不是文案。
