微服务日志聚合方案

本文属于《Go 微服务架构》第 32/35 篇
上一篇系列目录下一篇

微服务把单体应用拆成几十上百个进程，日志也随之散落在每个节点的容器文件系统里，出问题时再 SSH 上机器 grep 已经不现实。本文从一条日志的生命周期出发，讨论采集、传输、存储、检索与成本控制，给出可直接落地的 schema、架构与运维要点。读者应当了解容器与基本日志库的用法，读完后能为自己的服务设计一套可演进、可负担的日志聚合方案。

为什么需要日志聚合

单体时代排查问题很直接：登录服务器，tail -f 盯日志，grep 找堆栈。容器化之后这套流程迅速失效。

一个中等规模的系统有几十个服务，每个服务多个副本。容器随时重建，日志随容器删除；副本会被调度到新机器，IP 与主机名都变；滚动发布时新旧版本并存。kubectl logs 一次只能看一个 Pod 的当前容器，跨服务、跨副本、跨时间段的检索几乎无法完成，而故障往往发生在服务交界处，只盯一个服务拼不出完整故事。

日志聚合就是把这些日志按统一格式采集，经缓冲写入集中存储，再提供带权限的检索入口；它解决的不是“把文件搬到一起”，而是让日志可检索、可关联、可治理。

集中式日志承担四类职责：故障排查，用关键字、trace id、时间窗定位；审计合规，回答谁在何时做了什么；业务分析，统计失败原因；补充指标，解释错误率升高的原因。但日志不能替代指标，把日志当指标源会让每次告警都扫描海量文本；分工应是指标发现异常，日志解释异常，链路定位环节。

需求 含义 常见做法
集中检索 所有服务与副本在一个入口可查 统一采集、存储与查询界面
关联 按一次请求串起跨服务日志 统一 trace id 与 request id
保留 热数据可查、冷数据可回溯 分层存储与生命周期策略
访问控制 团队只看有权看的数据 租户隔离、角色授权、查询审计
成本 采集、存储、查询可负担 采样、压缩、裁剪、分层

这些需求互相拉扯：查得快就要建索引，留得久就要接受冷查询变慢，字段齐全就要承担更大写入量，方案设计是在约束下取舍。组织分工同样重要：业务团队负责“写什么”，包括字段、级别与脱敏；平台团队负责“怎么流”，包括采集、缓冲、存储与权限，契约就是 schema。

日志 schema：字段先于工具

存储可以换 Elasticsearch，也可以换 Loki，但 schema 一旦被几十个服务采用，再改就要协调所有团队、重跑历史数据、调整看板，所以先讲 schema。

日志格式大致有三代。纯文本一行一句，对机器不友好：采集端靠正则提取，格式一变解析就失效。键值对形如 level=error service=order-api，比纯文本容易解析，但嵌套结构表达困难，转义规则各家不一。JSON Lines 一行一个对象，采集端不需要理解业务语义，字段增删不影响解析，代价是体积偏大、人读稍啰嗦。生产建议用 JSON，本地开发用可读文本，通过配置切换。

下面的字段表可作为团队契约，字段名一旦确定就不再改，新增能力通过新增字段表达。

字段 示例 说明
ts 2021-02-09T10:15:30.123Z 事件时间，UTC，毫秒
level error 固定枚举，统一小写
service order-api 逻辑服务名，不含版本与副本
instance order-api-7d9c-x2k 副本标识，采集端补齐
env prod 环境标识，防止测试混入
trace_id 4bf92f3577b34da6a3ce929d0e0e4736 32 位十六进制，链路共享
span_id 00f067aa0ba902b7 16 位十六进制，当前操作
request_id req-8f2c1a 入口生成，便于对外沟通
msg payment callback failed 稳定短句，不含变量
error.type timeout 错误分类，便于聚合
error.message context deadline exceeded 错误描述
error.stack 多行堆栈 整体一个字段，不拆行
http.status 504 HTTP 状态码
duration_ms 3000 耗时，便于找慢请求
schema_version 1 契约版本，便于兼容

时间戳必须由应用在事件发生时生成，使用 UTC、以 Z 结尾、精确到毫秒。不要用采集时间代替事件时间：缓冲会让它晚几秒甚至几分钟，排序与窗口统计都会失真。存储层可另记接收时间用于计算延迟，查询以事件时间为准，时区只在展示层转换。

level 收敛为 debug、info、warn、error、fatal 并统一小写，WARNING、Warning、warn 并存会让聚合把它们当成三个值。error 表示需人介入，warn 可自愈，info 记录关键状态；级别通胀会让 error 失去信号价值。

service 用稳定逻辑名，instance 才区分副本，最好由采集端从容器元数据补齐。把 IP 放进 service 会因 Pod 重建而无法对应历史日志。msg 要稳定、简短，变量放进独立字段：msg="user 123 login failed" 无法聚合，msg="login failed" 加 user_id=123 才能按原因分组。堆栈整体放进 error.stack，不要让采集端按行拼接，并发请求交错时会拼出错误堆栈。

敏感字段必须在应用侧处理。手机号、邮箱、身份证号、银行卡号、Cookie、Authorization 头、token 与密码默认都不进日志。做法是字段级白名单，只有显式声明的字段才落盘；采集端正则脱敏只能兜底。

一致性比工具更重要。常见三类不一致：同名字段含义不同，例如两个服务都用 uid，一个指用户 ID，一个指设备 ID；同义字段名不同，如 user_id、userId、uid 并存；格式不同，如时间有的带时区、级别有的大写。解决办法是内部日志 SDK 固化字段与格式，CI 检查必填字段与拼写，新服务接入按清单确认 trace 透传与脱敏。字段演进只增不改，改名双写过渡。

采集、传输与存储

采集层：agent、sidecar 与应用直写

日志写出来只是第一步，还要有人从节点上搬走。采集层只有三种基本形态。

形态 工作方式 优点 代价 适用场景
节点 agent 每节点一个 DaemonSet 读容器日志 资源省、与应用解耦、升级统一 需节点权限、租户隔离靠配置 大多数 Kubernetes 集群
sidecar 每 Pod 附带采集容器 隔离彻底、可按 Pod 定制 开销随 Pod 数线性增长 强隔离、遗留文件日志
应用直写 SDK 直接发往网关或存储 无需读文件、字段最全 侵入应用、需自行缓冲 托管环境、无法装 agent

多数团队应默认用节点 agent，把采集变成平台能力；sidecar 适合强隔离、遗留文件日志或独立解析规则；应用直写适合无法控制宿主的托管环境，但把可靠性责任推回应用。

无论哪种形态，都建议应用只写标准输出与标准错误，由运行时落盘。这是十二要素应用的约定：应用不负责路径、轮转与清理。自己写文件再配 logrotate，常因权限、时区、挂载卷失效，留下写满磁盘的隐患。

跨行日志是另一个难点。堆栈按行读取会被拆成几十条记录，检索时只剩首行有上下文。Filebeat 的 multiline 用“以空格或 at 开头”判断续行，单请求有效；并发请求的堆栈交错时，规则会把 A 的堆栈拼到 B 上。推荐让日志库把整个堆栈作为 JSON 字段输出，边界由产生日志的进程确定。Fluent Bit 1.6 对跨行日志支持有限，堆栈合并仍应放在应用侧。

采集 agent 最容易被压垮。存储变慢、网络抖动、Kafka 不可用都会让发送队列堆积；没有缓冲策略，agent 要么内存暴涨被 OOM Kill，要么直接丢日志。Fluent Bit 用 Mem_Buf_Limit 限制内存缓冲，超过后暂停读取；storage.type filesystem 把缓冲落到磁盘；DB 文件记录读取位置，轮转后不重复也不漏采。

内存只做短期队列，磁盘承担更长缓冲。但磁盘不是无限的，缓冲目录要有配额与告警，否则日志管道会把节点磁盘写满，从可观测性故障升级为业务故障。入口限速是另一种背压：日志量因 debug 或重试循环翻倍时能保护存储，但会丢日志。较稳妥的是只对低价值日志限速、错误日志不参与，并监控“因限速丢弃的条数”。

传输：直写还是 Kafka

采集之后有两条路：直写存储，或先进消息队列再由消费者写入。这不是越复杂越高级，而是对故障隔离与回放能力的判断。

直写路径最短：agent 发到 Elasticsearch 或 Loki，失败靠本地缓冲重试。组件少、延迟低、排障简单，但存储不可用时压力全落在 agent 磁盘，限流会传导到采集端；同一份日志要同时进入搜索与归档，需配多个输出，任一路变慢都拖累另一路。

Kafka 在中间解耦。采集端写进 topic 即可释放缓冲，下游按能力消费，存储变慢时积压停在 Kafka；它还带来削峰、回放、多订阅与消费者独立扩缩容。

代价是 Kafka 需要运维：分区、副本、磁盘与控制器选举都要人管，topic 与保留策略要治理，链路延迟从秒级变成秒到分钟级。分区模型有两个事实：只保证单分区有序；顺序重要时 producer 要用 service + instance 这类稳定 key，代价是热点实例只能被一个消费者处理；消费者数不能超过分区数。

日志量不大、只有一个下游、团队没有精力维护额外组件时，不必上 Kafka；它的价值在“多下游、可回放、强削峰”，三点都占不到时，只是把故障点从两个变成四个。

存储：三种后端

存储的能力边界由索引结构决定。Elasticsearch 用倒排索引，擅长全文检索与聚合，输入关键字能立刻命中；代价是索引占空间、写入要分词、副本再放大一倍，单位成本最高，字段映射失控还会拖垮集群。Loki 只索引标签，正文压缩后存对象存储，成本低，与 Grafana 结合紧密，适合“先圈范围再 grep”的排障；短板是全文检索弱，无标签约束要扫大量数据。ClickHouse 一类列式存储按列压缩，压缩率高、聚合快、可用 SQL 统计，但要自己定义表结构、处理写入批次与保留，适合日志结构稳定、分析需求重的团队。

维度 Elasticsearch Loki ClickHouse
索引 倒排索引 仅标签 列存
全文检索 强 弱，依赖扫描 中等
聚合分析 强 有限 很强
单位成本 高 低 低
运维复杂度 中高 低 中高
典型查询 关键字与聚合看板 服务加关键字定位 大范围统计

日志不该以同样价格保留同样时长。常见分层是热层 7 天，温层 30 天降低副本或换便宜介质，冷层或归档保留 180 天到 1 年，只留压缩原文，天数取决于合规与业务价值。Elasticsearch 用 ILM 迁移，Loki 依靠对象存储生命周期，归档链路把原始日志压缩写入对象存储。分层让“保留多久”成为显式决策，而不是磁盘写满后的被动删除。

选型时先列出最常用的三个查询：最近一小时的报错适合 Loki，跨服务聚合适合 Elasticsearch 或 ClickHouse，自由全文探索则非 Elasticsearch 莫属。预算与查询模式决定选型，而不是社区热度。

索引、标签与查询设计

存储选好后，决定查询体验与成本的是数据组织。Elasticsearch 的索引与 Loki 的标签，本质都是让查询先缩小范围，再扫描细节。

Elasticsearch 日志索引常按天切分，例如 logs-2021.02.09，删除与迁移以整索引为单位，ILM 可按年龄迁移与删除；缺点是索引数随时间增长，分片过多拖累集群。另一种做法是 rollover 加别名：写入别名指向当前索引，查询别名覆盖一段时间，业务代码只认别名。按服务切分让团队独立设置副本与权限，但索引数乘以服务数，小服务会产生大量碎片。稳妥做法是以按天切分为默认，确有大团队需要独立治理时再拆，每个索引设置合理分片数。

字段映射要显式声明。service、level、trace_id、http.status 用 keyword；msg 全文检索时用 text，保留 keyword 子字段用于聚合；结构不确定的附加字段放进 flattened，避免每个新键都生成映射。dynamic: false 比 strict 实用：未知字段存入 _source 但不建索引，不会因拼写错误拒绝日志。设置 ignore_above，防止超长字符串撑爆 keyword 索引。

filter 不参与评分且可缓存，适合时间、服务、级别；全文匹配放 must，能明显降低查询开销。

Loki 把日志按“流”组织，流的身份由一组标签唯一确定，例如 {cluster="prod", namespace="order", app="order-api"}。标签相同的日志打包成块压缩，标签进入索引。查询先由标签定位流，再在流内过滤。硬约束是标签基数决定流数量：把 request_id、trace_id、user_id、pod_name 放进标签，每个值都产生新流，几百万条流会让 ingester 内存暴涨。高基数字段应留在正文，用过滤器匹配。

合理标签通常只有 cluster、namespace、app、level、env。level 会把流数量乘以级别数，但能加快“只看 error”的查询，日志量大的团队可以保留；副本名、容器 ID、节点名一律不进标签。

先用标签圈定 order-api，再包含匹配，| json 把正文解析成字段，最后按 status 过滤；Loki 2.0 支持这类标签过滤与区间聚合，例如按服务统计错误速率：

| json 在查询时解析，灵活但每次都要付解析成本；高频字段应以 JSON 直接输出，并尽量用前置标签减少扫描。

两种存储的优化思路一致：先用低基数、高选择性的条件缩小范围，再全文匹配或解析字段。设计 schema 时想清楚哪些字段用于过滤，把它们放进索引或标签，只用于展示的留在正文。若某字段每天出现在过滤条件里却只能全表扫描，就是 schema 该调整的信号。

关联：trace id、request id 与时钟

聚合解决“都在哪”，关联解决“哪些属于同一次请求”。没有关联字段的集中日志只是更大的 grep 窗口；有了贯穿链路的标识，才能把一次失败从网关追到数据库。

四段依次是版本、32 位十六进制的 trace id、16 位十六进制的 span id、两位标志位，最低位表示是否采样。服务收到请求时复用它，生成自己的 span id，调用下游时写入新的头，于是整条链路共享 trace id，每个服务只负责自己的 span。OpenTelemetry 的 SDK 与 Collector 在 2020 年陆续进入 beta，但日志信号尚未定型，落地仍以 traceparent 手工透传为主。

日志库从 context 取出 Trace 写入 trace_id 与 span_id；调用下游时把 traceparent 放进请求头，gRPC 放进 metadata。异步链路同样要透传：消息头带上 trace id，消费者恢复上下文，否则一入队链路就断了。

request_id 与 trace_id 不冲突。前者在入口生成，通常返回给客户端，用户报障时报的是它；后者用于内部链路，可能由网关或上游生成。两者都记：一个对外沟通，一个对内定位；存在重试时，同一个 request_id 可能对应多条 trace。

分工是：指标回答“有没有问题”，链路回答“问题在哪个环节”，日志回答“具体发生了什么”。联动有两个方向：用异常 span 的 trace id 查日志，或点击 error 日志里的 trace id 看完整调用。前提是字段名统一、时钟大致同步、采样策略一致；若链路采样而日志没采，就会出现“有 trace 没日志”的断点。较好的做法是让采样决策随 traceparent 标志位传播，日志侧尊重同一决定。

时钟偏差最隐蔽。容器共享节点时钟，节点由 NTP 或 chrony 同步，正常偏差在毫秒级；虚拟机暂停、宿主机过载或 NTP 不可达时，偏差可能到秒级。表现是排序时下游日志排在上游之前，或窗口聚合边缘数据忽多忽少。应对方式：保证 NTP 可用并监控偏差；同时保留事件时间与接收时间，对比即可判断是应用时间错了还是采集延迟；统一 UTC 与毫秒精度，展示层再转本地时区。精度不必追到纳秒，过高只会增加存储与解析负担。时间格式统一用 RFC 3339，不要用不带时区的字符串，避免不同解析器给出不同时刻。

成本、采样与安全边界

日志账单往往在运行半年后才引起注意：写入量随服务数线性增长，索引与副本把存储放大数倍，查询 CPU 又叠加在同一集群。成本治理要从设计开始。

估算只需知道数量级。每日原始量等于实例数、每实例每秒条数、单条平均字节数与 86400 秒的乘积，再乘索引膨胀与副本系数、乘保留天数，就是主存储需求。纯假设的例子：40 个实例，每实例每秒 50 条，每条 400 字节，每日约 69 GB；索引开销按 30% 计，保留 1 份副本，30 天约需 5.4 TB。这些数字只演示算法，读者应代入自己的数据。估算的价值是暴露杠杆：实例数、每请求条数、单条长度、副本数、保留天数，任一减半都会明显降本。

降量有七个手段：级别治理，很多生产 info 是开发期残留；动态日志级别，排障时临时开 debug 并到期恢复；采样，高频低价值日志按比例保留、错误全量；丢弃健康检查与探针日志；字段裁剪；压缩；分层保留。

采样要按 trace id 做确定性哈希，而不是随机丢单条。对 trace id 取模，窗口内的请求整体保留；随机丢单条会得到“有入参没出参”的残缺记录。比例按类型区分，错误与慢请求全量，普通访问日志可以低至百分之几。调整要有记录，否则某天发现日志变少却没人知道原因。

日志平台汇集全公司运行细节，本身是高敏感系统。最常见的泄露不是外部攻击，而是日志里主动写入了完整请求体、Authorization 头、连接串、身份证号、支付签名。这些内容进入索引后很难删除单条，往往只能等索引过期。防线在应用侧：SDK 提供字段白名单，框架拦截请求头与响应体，代码评审把日志当代码审。采集端可用正则脱敏兜底，例如掩码手机号与邮箱，但不能替代源头。

访问控制要回答三个问题：谁能查、能查哪些、查过什么。认证接入统一登录，授权按团队与租户划分，查询保留访问日志。Elasticsearch 用角色控制索引权限，Loki 用租户头隔离，Grafana 按文件夹授权。隔离级别与敏感度匹配：同集群用命名空间加索引前缀，强隔离时再拆集群。传输与静态存储都要加密：采集到存储走 TLS，对象存储与备份都加密。日志里出现过的密钥即使脱敏，也应视为已泄露，及时轮换。平台账号要最小权限，只读账号不应能删除索引。

Kubernetes 采集的特殊性

Kubernetes 把采集细节变成平台问题：应用只写标准输出，路径、轮转、元数据、权限都由集群决定。理解这些，才能解释“为什么日志少了一段”。

kubelet 把标准输出写到 /var/log/pods/<namespace>_<pod>_<uid>/<container>/0.log，并在 /var/log/containers/ 下维护含 Pod 名与容器 ID 的软链接。文件格式取决于运行时：Docker 的 json-file 每行是含 log、stream、time 的 JSON；containerd 与 CRI-O 用 CRI 格式，每行以时间戳、流标识、标签开头。Fluent Bit 的 Parser cri 与 Parser docker 分别对应两者，混用运行时按节点或后缀区分。CRI 的 F 是完整行，P 是运行时对超长日志的切分，不是应用的多行日志，当成堆栈续行会粘错。

kubelet 按 containerLogMaxSize 与 containerLogMaxFiles 轮转，默认 10 MiB 与 5 个，每个容器最多保留约 50 MiB。采集器必须在文件被删除前读完，Rotate_Wait 就是宽限时间。日志突发时 10 MiB 可能几秒写满，采集器没读完就被轮转，表现为“中间缺了一段”；要靠调大上限、提高吞吐或降低日志量解决。

短生命周期 Pod 是另一个盲区。Job 执行完立即退出，Pod 随后清理，日志文件随之消失；采集器没读到末尾，最后输出就丢失。解决办法：让 Job 退出前等待日志刷出；给这类 Pod 配 sidecar，由 sidecar 转发并在退出前 flush；或把 Job 日志写到持久化位置。“Job 日志丢了”通常不是采集器 bug，而是生命周期设计没考虑采集。

DaemonSet 部署有两个细节。第一是容忍度，控制面节点通常带污点，采集器若只容忍部分污点，这些节点上的系统组件日志就无人采集。第二是资源与优先级，采集器要有 requests 与 limits，避免被业务 Pod 挤占，并用较高优先级防止被先驱逐。hostPath 用只读挂载，容器内不以 root 运行。

容器日志本身只有时间、流与正文，namespace、pod、labels 要靠采集器 watch Kubernetes API 补齐。Fluent Bit 的 kubernetes 过滤器会合并这些元数据，它需要 list 与 watch Pods 的 RBAC 权限；权限过大是风险，过小则字段缺失。补齐后不要把全部标签塞进索引或 Loki 标签，Pod label 里可能有版本号、提交哈希，基数不低。只把稳定、低基数的字段（namespace、app、env）提升为索引或标签，其余留在记录里按需查询。

多租户通常以 namespace 为边界：每个团队拥有若干 namespace，采集时打 team 标签，存储侧按 team 做索引前缀或 Loki 租户。平台团队负责采集器、缓冲与存储，业务团队负责日志内容与看板。

参考架构与运维

把前面的选择拼起来，一条可落地的链路如下：

flowchart LR
  A[应用标准输出] --> B[Fluent Bit DaemonSet]
  B --> C[Kafka 缓冲]
  C --> D[Logstash 或消费者]
  D --> E[Elasticsearch 热层]
  D --> F[Loki 与对象存储]
  E --> G[Kibana]
  F --> H[Grafana]
  E --> I[归档存储]
  F --> I
  G --> J[告警与值班]
  H --> J

应用只写标准输出，节点 agent 统一采集并补齐元数据，Kafka 承担削峰与回放，消费者做解析、脱敏与路由，热数据进 Elasticsearch 或 Loki，冷数据压缩归档。Kibana 与 Grafana 只读，告警从查询结果或独立规则触发。每一跳都可以独立扩容与降级：存储故障时 Kafka 积压，采集端继续工作；Kafka 故障时 agent 落盘缓冲。没有 Kafka 的小规模部署可去掉这一跳，让 agent 直写存储，但要把缓冲与重试配好。

运维要把管道当生产系统看。需要持续观测：DaemonSet 的期望副本数与就绪数、agent 输入速率、输出重试与丢弃计数、缓冲目录使用率、Kafka 消费延迟、存储写入拒绝率、查询 P95 延迟、各租户每日写入量。告警应围绕症状而不是原因：agent 掉线超过 5 分钟、丢弃率大于零、消费延迟超过 10 分钟、存储磁盘水位超过 85%、应用有流量但日志写入为零，这些都比“CPU 高”更值得叫醒人。

容量规划按峰值而非均值做。发布、促销、故障重试都会放大写入；按过去 90 天的峰值再留 30% 余量，比按日均值可靠。每季度回看增长曲线，把“哪个团队贡献了最多日志”做成看板，成本治理才有抓手。

升级与迁移要可回退。采集器版本先在少量节点灰度，确认解析与字段无变化再全量；更换存储时双写一段时间，用同一批查询对比两边结果，确认字段、时间与条数一致后再切读。topic 与索引的命名带上版本，schema 变更走兼容流程，避免升级当天的日志成为孤岛。

常见坑可以列成一张检查表：日志是非结构化文本，采集端正则频繁失效；缺少 trace id，跨服务排障靠猜；把 request_id、user_id 放进 Loki 标签，流数量爆炸；日志里打印密钥与个人信息；保留策略缺失，磁盘写满才删；agent 资源限制过低，频繁 OOM；只配内存缓冲，重启丢一段；把日志当指标，告警查询扫全表；没有负责人，管道坏了没人发现。

小结

日志聚合的本质是把分散事件组织成可检索、可关联的数据资产。先定 schema 再选型，字段一致性比存储产品更难替换；采集层优先用节点 agent，把标准输出、多行堆栈与磁盘缓冲处理清楚；是否引入 Kafka 取决于多下游、回放与削峰需求。存储按查询模式与预算选择，索引与标签设计直接决定成本上限。最后用 trace id 与统一时钟把日志、链路、指标连起来，用采样、脱敏、权限与分层保留让它可持续运行。
