秒杀系统：流量削峰与库存扣减

秒杀是检验系统高并发能力的典型场景：短时间内涌入的请求远超库存，任何一处非原子操作都会被放大成超卖或重复下单。本文从需求与约束出发，依次讨论分层过滤、Redis 预扣、Lua 原子脚本、异步下单、失败补偿与对账，并给出一套可落地的参考架构。读者应具备 Redis、消息队列与 MySQL 的基本使用经验，读完后能够独立设计一条端到端的秒杀链路，并知道每个环节可能在哪里出错。

需求与约束：先定义什么叫成功

秒杀的业务描述只有一句话：在某个时刻开放一批数量有限的商品，先到先得。真正困难的是把它放到线上之后，一组彼此冲突的约束会同时出现。本文先逐条拆开这些约束，因为后面的每个设计决策几乎都能回溯到这里。

第一组约束来自流量形态。读请求与写请求在同一秒内到达，读可以缓存、可以静态化，写却必须落到唯一的事实源上。峰值往往只持续几十秒到几分钟，按峰值长期扩容并不经济，系统必须在平时容量下靠削峰和降级撑过尖峰。这意味着“扩容”不是唯一答案，“拒绝”与“延后”同样是设计的一部分。

第二组约束是正确性。无超卖是硬约束，卖出的数量不能超过库存；少卖则相对可修复，可以通过回补库存、对账补偿把资格释放出来。这个不对称很重要：所有设计都应优先保证“宁可少卖，不可超卖”，因为超卖之后要么取消订单引发客诉，要么发货造成资损，都比少卖难处理。

第三组是公平与防刷。活动承诺先到先得、一人一单，接口就不能只靠前端按钮置灰来约束；脚本、代理池、批量账号都会绕过页面直接请求接口。公平性最终要落到服务端的一个唯一键上，而不是落在页面的交互上。

第四组是幂等。用户重复点击、网关重试、消息队列重投、消费者 rebalance，都会让同一条业务请求被执行多次；如果下单逻辑不是幂等的，重复请求就会变成重复订单和重复扣减。

第五组是下游保护。数据库连接数、支付服务、优惠券服务都不是为秒杀峰值设计的；秒杀流量如果直接穿透到这些系统，后果不是秒杀失败，而是整个站点不可用。

把这五组约束翻译成指标，团队才能在评审时判断方案是否合格；具体阈值应结合业务与压测结果确定。

指标 定义 目标
有效请求成功率 排除售罄后的请求中，成功拿到资格的比例 接近 100%
p99 延迟 下单接口端到端 99 分位耗时 由压测基线确定
数据库写压力 订单与库存写入的 QPS、活跃连接数 与库存量同阶，而非点击量
超卖数量 成功订单数减去库存 0
重复订单 同一活动同一用户的多笔订单 0
对账差异 Redis、数据库、订单三方库存之差 0

要特别区分“售罄”和“失败”。售罄是业务结果，应返回明确的业务码让用户停止重试；5xx 或超时才是系统失败，会诱发重试并放大流量。很多事故的起点，就是把售罄写成了异常。

本文的主线是：秒杀系统的第一目标不是把请求处理得更快，而是把绝大多数注定失败的请求尽可能便宜地拒绝掉。由此有两个原则：流量在到达核心资源之前逐层衰减；一致性判断收拢到尽可能少的原子操作里。接下来的章节就是这两条原则的展开。

分层过滤与流量整形：让洪峰逐层衰减

把请求想象成一条河，库存是下游的窄桥。与其在桥头加宽桥面，不如在上游修几道溢流坝。分层过滤就是这组溢流坝，每层都要回答两个问题：挡掉多少请求，给用户什么反馈。前者决定容量，后者决定用户会不会反复重试。

客户端：减少无效点击，但不承担正确性

最直接的一层在浏览器里。点击后立即置灰按钮、进入等待态，避免同一用户连点；倒计时用服务端返回的 serverTime 与 startTime 计算偏移，而不是相信本地时钟，否则时钟偏快的用户会提前发起请求，偏慢的用户会错过开始。活动结束后把按钮切换为“已结束”，停止轮询。

必须强调：客户端限制只是体验优化。请求可以绕过页面直接打到接口，按钮置灰不能作为幂等或防刷的依据，真正的约束必须在服务端。

CDN 与静态化：把读流量移出机房

活动页的 HTML、CSS、JavaScript 和图片全部放到 CDN，页面不含用户相关数据；昵称、资格状态等动态信息通过独立的轻量接口获取。CDN 缓存整页后，源站只处理少量动态请求。缓存 key 带活动版本号，配置变更时主动刷新，而不是等待 TTL 过期。

售罄后把活动页整体切成静态的“已结束”页面，原本打到源站的刷新流量就变成了 CDN 的边缘命中，源站连一次请求都看不到。

网关：进入服务前的第一道准入

网关负责鉴权、活动状态校验、按用户、IP 与设备维度限流，以及识别异常客户端。限流算法不展开，但拒绝必须快速且语义明确：返回 429 或业务码，并在响应头给出重试建议，否则客户端会在同一秒内重试，把限流变成压测。

网关本身要无状态、可水平扩展，限流状态放在 Redis 或集群计数器里；网关一旦成为单点，前面的分层就失去意义。

服务预检：用内存挡住大部分请求

进入秒杀服务后，先做一组无锁的本地检查：是否在时间窗口内、活动是否允许下单、本地售罄标记是否置位、该用户是否已在本地“已参与”集合里。配置启动时加载并订阅刷新；售罄标记由 Redis 的扣减结果广播，允许短暂过期。

这些检查都是只读的、可能过期的，因此只能用来减少流量，不能用来做最终判断。把它们放在 Redis 之前，是为了让绝大多数请求连一次网络往返都不需要。

流量整形：把 T0 的尖峰摊平

即使经过上述过滤，T0 时刻到达核心链路的请求仍然是一个尖峰。整形的手段可以组合使用。

预热：活动前把配置、库存 key、数据库连接池、HTTP 连接、消息队列的 topic 与分区准备好，避免第一个请求触发建连、建表或缓存加载；JIT 编译、TLS 握手、DNS 解析也算预热。

分批放行：按固定速率发放“入场券”，拿到券才允许扣减；队列有界，满了返回“排队人数过多”。尖峰被改造成可控的斜坡，代价是部分用户等待。

只读窗口与库存快照：开始后的前若干秒只展示“抢购中”，库存用“充足、紧张、售罄”三态快照，几秒刷新一次；精确库存既泄露商业信息，也诱发疯狂刷新。

售罄快速路径：Lua 扣到 0 时同时写入售罄标记，后续请求在本地或网关直接短路；标记必须有 TTL，并在重新放量时清除。

避免惊群：所有客户端在同一毫秒发起请求，会让建连、TLS 握手、缓存失效同时发生；服务端下发随机抖动，把请求摊开到几百毫秒。抖动上限要小于可感知的等待时间，否则会被误认为卡顿。

经过这几层，真正到达 Redis 的请求应当只剩库存量的小倍数，而不是点击量；每层都不需要完美，但每层都要挡掉一个数量级。

库存预扣：Redis 与 Lua 划出的原子边界

过滤之后，剩下的请求要回答两个问题：还有没有库存，这个用户是不是已经买过。这两个判断必须在同一个原子操作里完成，否则并发一上来就会出错。本节先解释为什么把库存放在 Redis，再给出预扣与回补脚本。

为什么是 Redis，而不是数据库

数据库的正确性来自行锁与事务，代价是同一库存行的更新被串行化：所有请求排队等这一行，连接池很快被占满，锁等待反过来拖慢整个实例。Redis 把库存放在内存里，命令单线程执行，Lua 脚本执行期间不会被打断；一次扣减只有一次网络往返，没有锁等待和事务回滚的开销。

角色要分清：Redis 是资格判定器，在高并发下快速回答“还有没有”；数据库是账本，最终记录“卖给了谁”。Redis 的写入可能因主从异步复制、故障切换或 AOF 落盘间隔而丢失，不能单独承担正确性。这一点在对账一节还会展开。

key 设计与初始化

一个活动至少需要三类 key：库存 seckill:{actId}:stock、用户占位 seckill:{actId}:user:{uid}、售罄标记 seckill:{actId}:soldout。花括号里的 actId 是 Redis Cluster 的 hash tag，保证这三个 key 落在同一个槽位；否则 Lua 在集群模式下会因跨槽报错。

用户占位不要放进大的 Set 或 Hash：大 key 在删除、迁移和过期时都会阻塞主线程，清理成本也高。用独立的 string key 加 TTL 更稳妥，TTL 至少覆盖活动时长、支付超时和对账窗口。

初始化在活动开始前完成，用 SET key stock NX 写入，值与数据库一致。NX 让初始化幂等：发布脚本重跑时不会把已扣减的库存重置。完成后校验一次数据库与 Redis 的数量，并把活动版本号写进配置，便于追溯。

为什么单独 DECR 不够

很多入门实现是“先 GET 判断大于 0，再 DECR”。并发下两个请求同时读到 1，都判断可以购买，各扣一次，库存变成 -1。即使换成一条 DECR，也只能避免读改写丢失，仍有三个问题：库存会被扣成负数；同一用户可以反复扣减；无法区分“未初始化”和“已售罄”。回补时直接 INCR，重试或多重补偿还会把库存加回初始值以上。

WATCH 加 MULTI/EXEC 也能解决原子性，但它是乐观锁：冲突时整个事务重试，热点下冲突率极高，重试会把流量放大数倍。Lua 在 Redis 内部一次执行完，没有中途插入，也没有客户端重试放大。

一段可用的预扣脚本

脚本把“校验库存、写入用户占位、扣减库存、写售罄标记”合并为一个原子操作，返回值对应不同的业务结果。

返回值的含义要在接口层固定：1 拿到资格，进入异步下单；0 售罄，返回业务码而不是异常；2 重复请求，返回上一次结果；-1 配置错误，必须告警，因为活动根本不该开始。

脚本用 EVAL 调试、EVALSHA 上线：首次执行前 SCRIPT LOAD 缓存脚本，之后只传 SHA1，省带宽也避免每次传输。节点重启或 SCRIPT FLUSH 后返回 NOSCRIPT，客户端要捕获并回退到 EVAL，不要当成业务失败。

脚本要保持 O(1)：不遍历列表、不用随机数、不依赖当前时间。随机与时间会让结果难以复现，也给主从切换后的核对增加变数。

幂等与防重：同一次购买意图只产生一个结果

即使预扣脚本挡住了同一用户的第二次扣减，请求仍可能在更后的环节重复：客户端超时重发、网关重试、消息重投。幂等要覆盖整条链路，而不只是入口。

三个层次

请求级幂等依靠全局唯一的 requestId：服务端记录 requestId 与结果，相同 requestId 再次到达时直接返回上次结果，不再扣减与建单。

业务级幂等依靠数据库唯一索引。对 (activity_id, user_id) 建唯一键，这是最终防线：无论请求从哪个入口进来，同一用户在同一活动只能有一行订单。

消息级幂等依靠消费者的业务判重。消息队列只保证至少一次投递，重复消息不可避免；消费者以订单号或 (activity_id, user_id) 为幂等键，重复执行的结果必须与第一次相同。

Redis 的 SET NX 只能作为快速路径。它可能因为过期、主从切换丢数据而失效，所以不能替代数据库唯一索引；它的价值在于把绝大多数重复请求挡在数据库之前。

表结构与插入方式

订单表至少要有两个唯一键：业务唯一键和请求唯一键。

uk_act_user 保证一人一单，uk_request 让接口层的重试也能被识别。插入时不要“先查再插”，那仍然是检查与写入分离的竞态；直接插入，捕获重复键错误，再按业务键把已有订单读出来返回。

MySQL 在单条语句因重复键失败时不会中止整个事务，同一事务里还能继续查询；这让“插入失败后读旧订单”可行，也避免把正常的重复请求包装成异常。

状态流转也要幂等

订单状态只能沿固定方向变化，所有变更都用条件更新表达，例如 UPDATE ... SET status = 1 WHERE id = ? AND status = 0。受影响行数为 1 才表示本次变更生效，为 0 说明状态已经被别的操作改过，当前操作应当放弃而不是覆盖。支付回调、超时关闭、人工补偿都遵守这条规则，才能避免“已支付订单被关闭”这类事故。

异步下单：状态机、落账与补偿

Redis 预扣成功后，如果同步创建订单，请求要等待数据库事务、优惠券核销甚至支付网关；等待队列很长，连接和线程会被迅速耗尽。异步化的思路是：Redis 只回答“有没有资格”，订单创建交给消息队列后的消费者，接口尽快返回“订单生成中”。

一条订单的状态机

flowchart LR
  A[INIT 初始] -->|Lua 预扣成功| B[RESERVED 已占位]
  B -->|消息投递成功| C[QUEUED 已入队]
  C -->|消费者建单| D[CREATED 待支付]
  D -->|支付成功| E[PAID 已支付]
  D -->|超时未支付| F[CLOSED 已关闭]
  B -->|投递确定失败| G[FAILED 已回补]

每个状态只允许特定的迁移，每次迁移都用条件更新或带校验的脚本完成。排查时只要看订单停在哪个状态，就能定位是哪一段链路出了问题。

消息设计与生产端

消息体至少包含活动 id、用户 id、sku、requestId、占位 id 与创建时间。分区键用用户 id，让同一用户的消息落到同一分区；秒杀不要求全局顺序，唯一键已经保证结果唯一，按活动分区反而会造成单分区热点。

生产端开启 acks=all 与重试，Kafka 2.6 的幂等生产者还能消除重试导致的重复。但 Redis 与 Kafka 之间没有事务，预扣成功而消息没发出去仍是缺口。明确失败时立即回补；发送超时属于结果未知，不能马上回补，否则消息可能已落盘，消费者随后建单时库存已被还回去。未知结果记录待确认状态，由对账任务在宽限期后按 requestId 查询订单是否存在，再决定回补还是重发。

消费端与超时关闭

消费者在一个事务里插入订单并扣减数据库库存：插入命中唯一键说明消息重复，直接结束事务并确认；扣减影响行数为 0 则回滚、告警并交给对账回补。提交后再确认消息，确认失败导致的重投同样被唯一键吸收。消费失败不能无限重试，超过阈值转入死信队列并告警，避免一条坏消息阻塞整个分区。

未支付订单需要关闭并释放库存。可以用延迟消息，也可以用定时任务扫表；MySQL 8.0 的 SKIP LOCKED 能让多个扫描实例互不阻塞。关闭执行 UPDATE ... SET status = 2 WHERE id = ? AND status = 0，受影响行数为 1 才回补 Redis 与数据库库存。支付回调同样用条件更新，两个操作只有一个能成功：支付赢了，关闭放弃；关闭赢了，支付回调发现订单已关闭，转入退款。这个竞态不处理，就会出现“订单已关闭但钱已扣”的客诉。

数据库设计：把数据库放回账本的位置

数据库在秒杀链路里只做两件事：记录订单，记录库存的最终扣减。它不应承担第一道拦截，因为每次写入都涉及事务、行锁与日志落盘，成本远高于 Redis。

stock >= 1 是真正的守卫，version 用于审计和后台调整时的 CAS，不是防止丢失更新的必需品，因为单条 UPDATE 已经在行锁下原子完成了读改写。用 SELECT ... FOR UPDATE 也能做对，但它多一次往返、锁持有时间更长，热点下所有请求仍然排在同一行上，吞吐不会更好。

分桶与分片

单行库存是天然热点。把一份库存拆成 N 个桶，按用户 id 哈希选桶，UPDATE ... WHERE bucket_no = ? AND stock >= 1，行锁冲突被分散到 N 行；总库存是所有桶之和，展示与对账时再聚合。桶数不是越多越好：桶太多会让售罄判断需要扫描全部桶，回补也更复杂。先按单库单表能承受的写入量估算，再用压测校准。

活动之间可以分表甚至分库，按 activity_id 路由，活动结束后归档。这样一场活动的写入不会影响另一场，也便于按活动限流。数据库最终看到的写入量应当与库存量同阶，而不是与点击量同阶；如果订单表 QPS 跟着点击量走，说明前面的过滤和异步都没有生效。

超卖防护的深水区：失败矩阵与对账

Redis 的脚本是原子的，MySQL 的事务是原子的，Kafka 的投递是至少一次的；三者拼在一起，并不存在跨系统的原子操作。不超卖不是某个组件单独保证的，而是本地原子性、幂等、补偿与对账共同收敛的结果。

故障点 现象 处理方式
预扣后消息发送失败 Redis 已减，订单不存在 明确失败立即回补；超时先挂起
消息在队列中丢失 预扣成功但无订单 对账按占位补发或回补
消费者建单前宕机 消息重投 唯一键吸收重复
建单成功但确认失败 消息重投 重复插入被唯一键拒绝
数据库主从切换 事务回滚或超时 消息重试，超限进死信
支付与关闭并发 状态互相覆盖 条件更新，只有一方成功
Redis 故障丢数据 预扣记录消失 以数据库为准重建

表里绝大多数故障的兜底都不是“再试一次”，而是“让重复执行无害”。幂等键与条件更新是贯穿所有行的共同前提。

对账任务负责发现没有被兜住的差异。它按活动读取三组数据：Redis 剩余库存、数据库各桶库存之和、订单表中占用库存的订单数（待支付与已支付）。理论上应满足：初始库存等于 Redis 剩余、已创建订单与已关闭待回补之和，差额就是尚未建单的在途占位。任一环节漏掉，等式就不成立。

对账先只读计算差异并告警，确认原因后再修复：Redis 丢数据时用数据库库存减去在途占位重建；孤儿占位按占位 id 回补；重复扣减生成补偿单，而不是直接改库存。所有修复都带幂等键（业务类型加业务 id）和审计记录，默认 dry-run，避免对账脚本本身成为新的故障源。

热点、容量、降级与压测

热点 key 与资源隔离

单个库存 key 在 Cluster 下只落一个槽、一个节点，再高的 QPS 也只能由这个节点承担。解决办法与数据库分桶同构：拆成 N 个 key，按用户哈希选桶，Lua 只操作一个桶；售罄判断改为聚合或单独计数器。代价是展示与对账更复杂，只有压测证明确实是瓶颈时才值得做。

本地缓存只用于只读数据：活动配置、商品信息、规则开关。库存绝不能缓存在本地用于判断，否则不同实例看到不同的库存，超卖几乎必然发生。本地售罄标记可以有，但必须短 TTL 并能被广播刷新。

连接池与线程池按隔离而不是共享来设计。下单、查询、对账使用不同的线程池，队列有界，满了快速拒绝；数据库连接池总量按实例数乘以池大小估算，必须小于最大连接数并留出余量。池大小是并发上限，不是吞吐来源，盲目调大只会把压力转成数据库的上下文切换。

容量估算

容量靠测量。先用代表性请求压出单实例能力，再按“实例数等于峰值 QPS 除以单实例能力与安全系数之积”估算，安全系数取 0.5 到 0.7。消息队列分区数不小于消费者实例数，否则扩消费者没有意义；数据库写入按库存量估算；Redis 的 ops 按每请求一次脚本计算。QPS 必须来自自己的压测，而不是行业传闻。

降级与熔断

降级开关要在活动前准备好并演练：关闭推荐、评论、积分等非核心功能；下单切为排队模式；售罄后返回静态页；数据库连接池接近上限时拒绝新的写请求，保护已有事务。熔断器挂在下游依赖上，失败率超过阈值就快速失败，避免线程被慢调用拖死。

监控至少覆盖各返回码比例、p99 延迟、Redis 错误与延迟、Kafka 积压、订单创建延迟、数据库 QPS 与连接数、对账差异。所有开关都要有操作审计，活动期间只允许预先演练过的变更。

压测：验证正确性，而不只是吞吐

压测的流量模型要接近真实：包含浏览、点击、重复点击与失败重试，用户集合足够大且不重复，请求分布有 T0 尖峰而不是恒定速率。只压下单接口会高估系统能力，只压静态页又会低估写路径的压力。

正确性断言比吞吐数字更重要。压测后检查：成功订单数等于库存、同一用户没有两笔订单、Redis 与数据库库存一致、没有负库存、消息积压归零。再做故障注入：停掉 Redis、暂停消费者、让数据库变慢、杀掉消费者实例，观察回补、重投与对账是否收敛。wrk 适合压 HTTP 接口并用 Lua 生成唯一用户，JMeter 适合编排登录、浏览、下单的完整场景；工具只负责产生流量，断言要自己写。

参考架构与常见坑

flowchart TD
  C[客户端] --> CDN[CDN 静态活动页]
  C --> GW[网关 鉴权与限流]
  GW --> S[秒杀服务]
  S -->|Lua 预扣| R[(Redis 库存与占位)]
  S -->|预扣成功后投递| MQ[(Kafka)]
  MQ --> O[订单服务]
  O --> DB[(MySQL 订单与库存)]
  O --> P[支付服务]
  J[对账任务] --> R
  J --> DB
  J --> MQ

主链路每一段都允许失败，失败后要么回补，要么重试，要么留给对账收敛；对账任务不在请求路径上，只负责发现和修复偏差。

常见坑

  • 先查库存再扣减，检查与写入分离。
  • 用数据库行锁扛热点，连接池被拖垮。
  • 没有业务唯一键，重试变成重复订单。
  • 把消息队列当 exactly-once，消费端不判重。
  • 支付成功后仍执行超时关闭与回补。
  • 回补不校验归属，库存被加回多次。
  • 不做对账，Redis 与数据库漂移无人发现。
  • 只压 happy path，不注入故障。

小结

秒杀系统的核心不是某个高性能组件，而是一组约束下的取舍：分层过滤把流量挡在核心之外，Redis 加 Lua 把资格判定收成一次原子操作，唯一键与条件更新让重复执行无害，异步下单与补偿收敛跨系统的不一致。数据库只做账本，Redis 只做闸门，消息队列只做缓冲。最后用对账与故障注入证明系统在异常下仍然正确。
