Istio 服务网格入门

本文属于《Docker 与 Kubernetes》第 33/51 篇
上一篇系列目录下一篇

微服务拆开之后，服务之间的调用关系迅速变成一张网。超时、重试、熔断、限流、灰度发布、加密传输、调用链追踪，这些能力如果每个服务各自实现一遍，就会在业务代码里堆满与业务无关的逻辑，而且不同语言、不同团队的做法很难统一。服务网格要解决的正是这件事：把这些通信治理能力从应用进程中剥离出来，下沉到基础设施层，让业务代码只关心业务。

Istio 是目前最主流的服务网格实现之一。本文以 Istio 1.10 与 1.11 为准，这两个版本的控制面已经合并为单一的 istiod。本文面向刚接触服务网格的读者，讲清楚它由哪些部分组成、请求如何被拦截和转发、几个核心资源各自负责什么，以及落地时会遇到哪些坑。流量治理的具体策略留给后续文章展开，这里只建立整体图景。

服务网格要解决什么问题

在没有服务网格的年代，微服务的通信治理通常有三种做法。第一种是在业务代码里引入 SDK，比如用某个公司的 RPC 框架，框架自带服务发现、负载均衡、熔断。这种做法的代价是语言绑定，跨语言接入困难，升级框架等于升级所有服务。第二种是把治理逻辑放到 API 网关，但网关只能处理南北向流量，集群内部服务之间的东西向调用管不到。第三种是每个团队自己写一套，重复建设且行为不一致。

服务网格的思路是把治理能力做成一个独立的进程，与业务容器并排运行，所有进出业务容器的流量都经过这个进程。业务代码不需要知道它的存在，也不需要引入任何 SDK。治理策略由控制面统一下发，运维人员可以用声明式配置描述“这个服务的超时是 3 秒”“这两个版本按 9:1 分流”，而不必改代码、重新打包、重新发布。

好处很直接：治理能力与语言无关，Java、Go、Python 写的服务享受同一套策略；策略变更不必改代码发版，配置下发即可生效；可观测性数据在代理层统一采集，口径一致。代价也很明显：多一层代理、多一份资源开销、多一套需要学习和运维的组件。

数据平面与控制平面

Istio 的架构可以切成两半。数据平面由一组 Envoy 代理组成，它们以 sidecar 的形式与业务容器部署在同一个 Pod 里，接管 Pod 的进出流量，负责真正的转发、负载均衡、TLS 加解密和指标上报。控制平面则是 istiod，它不碰任何一个字节的业务数据，只负责把用户写的配置翻译成代理能理解的格式并下发。

这种分工带来一个重要特性：控制平面短暂不可用时，数据平面仍然按最后一份配置继续工作。已经建立的连接不会断，路由规则也还在代理的内存里。所以重启或者升级 istiod，通常不会造成业务中断。这一点与传统网关把控制与转发耦合在一个进程里的做法不太一样。

flowchart TD
    U[运维提交 YAML] --> P[istiod 控制平面]
    P -->|xDS 配置| A[服务 A 的 Envoy]
    P -->|证书| A
    P -->|xDS 配置| B[服务 B 的 Envoy]
    A -->|mTLS 连接| B
    A --> C[业务容器 A]
    B --> D[业务容器 B]

图中箭头的方向值得注意：业务代码照常发出请求，请求被同一 Pod 内的代理截走，再由代理决定发给谁、如何加密。

Sidecar 注入与流量拦截

启用某个命名空间后，新建的 Pod 里会多出一个容器。用 kubectl 查看时，READY 列会从 1/1 变成 2/2，多出来的那个叫 istio-proxy，也就是 Envoy。两者共享网络命名空间，也就是共用 IP 与端口，这是拦截能够成立的前提。

自动注入依赖 Kubernetes 的准入控制。命名空间被打上 istio-injection=enabled 标签后，Istio 注册的 mutating webhook 会在 Pod 创建时改写 Pod 的 spec，插入一个初始化容器和一个代理容器。初始化容器负责写 iptables 规则，代理容器负责运行 Envoy。若使用基于修订版本的控制面，标签会换成 istio.io/rev，效果相同。

至于流量为什么会被截走，答案在 iptables。初始化容器在 Pod 的网络命名空间里写入 nat 表规则，把业务容器的出站流量重定向到 15001 端口，入站流量重定向到 15006 端口，这两个端口由 Envoy 监听。应用并不知道这件事，它连接的目标地址没变，只是数据包在半路被换了去处。代理自身的流量通过 UID 排除，避免自己转发自己形成回环。这里只需理解“透明重定向”的概念，规则细节与 Envoy 的监听器模型不在本文展开。

istiod 的职责

早期 Istio 的控制面拆成 pilot、citadel、galley、mixer 等多个组件，排查问题时先要弄清楚该看哪一个。这些职责后来逐步合并，到 1.10 与 1.11，控制面就是一个 istiod。它的工作可以归纳为三件。

第一是配置分发。istiod 监听集群里的 Service、Endpoint 以及 Istio 自定义资源，把声明式的配置翻译成 Envoy 能执行的 xDS 配置，推送给对应的代理。推送是按需的，某个代理只关心自己涉及的服务，不会收到全量配置。

第二是证书签发。istiod 内置 CA，为每个工作负载签发证书。证书里的身份不是随便起的名字，而是由命名空间与服务账号拼成的 SPIFFE 形式标识，比如 cluster.local/ns/default/sa/hello。代理通过 SDS 接口取证书并自动轮换，业务代码不需要读取任何证书文件。

第三是服务发现。它从 Kubernetes 读取 Service 与 Endpoint 的变化，再把 ServiceEntry 声明的外部服务合并进来，形成一份统一的服务注册表。代理拿到的是“有哪些服务、每个服务背后有哪些实例、实例的健康状态如何”，负载均衡的决策则在代理侧完成。

三件事有一个共同点：istiod 只产出配置与身份，不参与转发。所以 istiod 重启时，老 Pod 之间的调用照常，只是新 Pod 可能暂时起不来。

四类核心资源

Istio 用一组自定义资源描述治理意图，入门阶段最常接触的是四个。

Gateway 描述网格的边缘，回答“哪些端口、哪些协议、哪些域名可以从外面进来”，以及用哪张证书做 TLS 终止。它只负责监听和接收，本身不带路由规则，需要与 VirtualService 绑定才有意义。

VirtualService 描述路由，回答“什么样的请求应该去哪里”。匹配条件可以是域名、路径、请求头，目标可以是某个服务的不同子集，也可以是外部服务。它既能绑在 Gateway 上处理南北向流量，也能直接用于网格内部的东西向调用。

DestinationRule 描述目标侧的策略，回答“请求到了之后怎么对待”。它按标签把服务划分为若干 subset，并定义负载均衡算法、连接池大小、熔断阈值、以及与目标通信时使用哪种 TLS 模式。可以粗略记成：VirtualService 决定去向，DestinationRule 决定到达方式。

ServiceEntry 用来把网格之外的东西登记进来。数据库、第三方 API、另一个集群里的服务，默认不在服务注册表中，代理对它们一无所知，也就谈不上超时、重试与遥测。写一条 ServiceEntry 声明它的域名和端口，这些能力就补齐了。

一次请求经过的路径

一次从集群外部进入的请求，大致经过这些环节。流量先到达入口处的 Istio Gateway，它按端口和域名选中一条 VirtualService；VirtualService 按路径或请求头匹配，决定转发到哪个服务的哪个 subset；这条路由对应的 DestinationRule 提供 subset 的实例列表和负载均衡策略；请求于是被送到目标 Pod 的代理，再由代理转给同一 Pod 里的业务容器。

网格内部的服务互调少了 Gateway 这一段，其余相同。调用方容器发起连接，iptables 把包重定向到本 Pod 的 Envoy，Envoy 按路由规则选出目标实例，与目标 Pod 的 Envoy 建立连接，对方再交付给本地容器。所以一次调用会经过两个代理，出站一个、入站一个。排查时两侧的日志与指标都要看，只盯一端容易误判。

mTLS 与可观测性

mTLS 指双向 TLS，通信双方都要出示证书并验证对方身份，而普通 TLS 只验证服务端。在 Istio 里，每个工作负载都持有 istiod 签发的证书，代理之间自动完成握手，业务代码不参与。证书身份与 Kubernetes 的服务账号绑定，因此“谁在调用谁”有了可验证的依据，而不只是依赖 IP。

默认情况下，Istio 采用宽容模式：既接受 mTLS 流量，也接受明文流量，这是为了兼容尚未注入代理的服务，便于逐步迁移。确认全网格都已注入之后，可以通过 PeerAuthentication 把某个命名空间或整个网格切换为严格模式，此时明文请求会被拒绝。是否切换、何时切换，取决于存量服务的改造进度，不宜一步到位。

可观测性数据几乎都来自代理，而不是业务代码。指标方面，Envoy 统计请求数、响应码、延迟分位数，以 Prometheus 格式暴露，Istio 自带的仪表盘直接消费这些数据。日志方面，代理可以输出每次请求的访问日志，包含来源、目标、状态码和耗时。追踪方面，代理在请求经过时生成 span 并传播追踪上下文，但跨服务串联的前提是应用把相关请求头一路传下去，否则链路会在业务进程处断开。这也说明网格的观测粒度是服务之间，看不到方法内部。

安装、渐进采用与边界

安装可以用 istioctl，也可以用 Helm。前者适合快速体验，一条命令把控制面和默认配置装进集群；后者适合把版本与参数纳入 Git 管理。装完之后，给命名空间打上注入标签，重建工作负载，就能看到 2/2 的 Pod。建议先在测试命名空间完成这一步，确认代理正常启动、延迟无明显变化后再推广。

采用节奏上，稳妥的做法分三步。第一步只注入，不加任何路由规则，让所有请求按原样通行，观察资源占用和延迟；第二步引入 VirtualService 与 DestinationRule，先做最简单的按版本分流，验证配置生效路径；第三步再开启严格 mTLS 和授权策略。每一步都保留回滚手段，注入可以按命名空间关闭，路由可以删除资源恢复默认。

代价必须提前算清楚。每个 Pod 多一个容器，内存占用按代理数量线性增长，节点上 Pod 密度高时这笔开销不小；控制面需要额外节点或资源预留；配置从代码里搬到了 YAML 里，出错时排查链路更长，运维团队要熟悉 xDS、证书和 iptables 这几层概念。

它也不是所有场景都合适。服务数量很少、技术栈单一、团队规模小的系统，引入网格的收益可能抵不过复杂度；对延迟极度敏感的场景要评估多一跳代理的影响；Serverless 或托管平台不允许自定义 Pod 时，sidecar 模式也落不下去。

常见坑

注入不生效，多半是命名空间标签拼错，或者 Pod 在打标签之前就已存在，需要重建而不是重启容器。端口命名不规范，Istio 无法识别协议，会把流量当 TCP 处理，路由与指标都会失常，端口名应写成 http、http-web 这类前缀形式。健康检查被拦截，是因为探针走的是 kubelet 到 Pod 的路径，某些配置下需要放行，或改用 exec 探针。配置看似不生效，先确认资源所在命名空间与目标服务是否匹配，再用 istioctl analyze 与 proxy-status 核对下发状态。升级兼容问题则来自 CRD 与 API 版本变化，跨小版本升级前应阅读变更说明，先在非生产集群验证。

小结

服务网格把通信治理从业务代码搬到代理层：istiod 负责配置与身份，sidecar 负责转发与遥测。入门抓住注入、四类资源、请求路径三条线，先小范围跑通，再逐步收紧路由与安全。
