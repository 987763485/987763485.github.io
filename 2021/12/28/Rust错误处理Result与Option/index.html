Rust 错误处理：Result 与 Option

本文属于《Rust 学习路线》第 20/68 篇
上一篇系列目录下一篇

Rust 没有异常，也没有 null。它把“可能没有值”和“可能失败”这两种不确定性，分别交给 Option<T> 与 Result<T, E> 两个枚举来表达。编译器会逼着你在取出值之前先处理这两种情况，于是很多空指针与漏判错误在编译期就消失了。

本文从这两个类型的语义讲起，依次介绍构造与匹配、常用组合子、? 运算符的自动转换、unwrap 的使用边界，以及 main 返回 Result、迭代器中的处理与测试断言。示例以 Rust 1.56 为准，不涉及工程化的错误分层。

为什么需要两个类型

Option<T> 的定义只有两个变体：Some(T) 与 None。它回答的问题是“有没有”，典型场景是查找、解析和可选配置。Result<T, E> 的变体是 Ok(T) 与 Err(E)，回答的是“成没成”，失败时还要携带原因。

两者都是普通枚举，没有语言层面的特殊待遇。None 不携带类型参数，编译器要靠上下文推断 T；Result 的错误类型同样需要明确，否则单独写一个 Err(...) 无法确定 E。这也是函数签名必须写清返回类型的原因之一。

与异常相比，错误是返回值的一部分，调用者看签名就知道需要处理；与 null 相比，None 不能被当作值直接使用，必须先解构。配合 match 的穷尽性检查，漏掉分支就编译不过，这是语言提供的第一道保障。

选择哪一种，有一条朴素的标准：缺少一个值属于正常状态，用 Option；操作失败需要让调用方知道原因，用 Result。用 Option 表达失败会丢掉原因，用 Result 表达可选值又逼着调用方写无意义的错误分支，两者都不划算。

还有一个常被忽略的细节：Option<&T> 与裸指针占用同样的大小，因为编译器会把空指针这个非法值借来编码 None，Option<Box<T>> 也是如此。Result 一般没有这种优化，判别标签仍要占用空间。类型选择首先看语义，但在大量小对象里，Option 的零成本并非空话。

匹配是最基础的消费方式：

match 要求穷尽，这两个枚举的变体少，写全并不费力。只关心一个分支时，if let Some(v) = opt 更简洁；需要反复从可变容器取值时，while let Some(top) = stack.pop() 也很常见。不过 if let 不检查另一个分支，别把需要兜底的逻辑塞进去。

Option 提供了一组查询方法：is_some()、is_none()、as_ref()、take()。as_ref() 把 Option<T> 借成 Option<&T>，避免为了看一眼而移动所有权；take() 把值取走并留下 None，适合在 &mut self 方法里交出字段。Result 对应的是 is_ok()、is_err() 与 err()，后者把错误借用出来，返回 Option<&E>。这些方法本身不处理错误，只是让你在不解构的前提下观察状态。

模式还能写得更细。Some(0) 只匹配值为 0 的情况，Some(n) if n > 0 带守卫，Some(&x) 用于在借用上匹配。Rust 1.56 中 matches! 宏已经可用，matches!(opt, Some(x) if x > 0) 直接得到布尔值，比写一个只有两个分支的 match 轻便，适合放在条件判断里。

两个类型之间还有便捷的转换：Result::ok() 丢掉错误，只保留 Option<T>；Option::ok_or() 反向补上错误。Option::filter 则在值为 Some 时再执行一次判断，不满足就变成 None，适合把“存在但不符合条件”归入缺失。

组合子：把分支写成链

手写 match 清晰，但多层嵌套很快会变成金字塔。组合子把这些分支收进方法调用，保持一条纵向的链。

map 只作用于成功值：Some(3).map(|x| x + 1) 得到 Some(4)，None 原样传递；Result 的 map 同理，Err 不动。map_err 则专门变换错误，用于统一错误类型或补充上下文。

and_then 用于闭包本身也返回 Option 或 Result 的场合，否则会得到嵌套的 Some(Some(v))。or_else 在前者失败时提供后备，闭包拿到错误或空值，可以决定换一种方式重试。

unwrap_or、unwrap_or_else、unwrap_or_default 在失败时给出默认值，不 panic，是“缺省即可”场景的常用收尾。ok_or 与 ok_or_else 把 Option 转成 Result，None 变成指定的错误，这一步常在函数边界上做。

transpose 解决类型顺序问题：Option<Result<T, E>> 可以转成 Result<Option<T>, E>，反之亦然。读取可选配置并解析时很实用，先 map 解析得到 Option<Result<...>>，再 transpose，就能用 ? 统一处理。

map_or 把 map 与 unwrap_or 合并：opt.map_or(0, |x| x * 2) 在 None 时给出默认值。它适合一行内完成变换与兜底，但默认值表达式总会被求值，开销大时仍应拆成 map 加 unwrap_or_else。

还有两个容易混淆的方法：or 在前者为 None 或 Err 时返回后者本身，and 则在前者成功时返回后者，二者都不接受闭包。它们表达的是“备选值”与“顺序依赖”，与 or_else、and_then 的惰性计算区分开。选择时先问一句：后备值需要现算吗，需要就用带闭包的版本。

? 运算符与自动 From

? 是错误传播的语法糖。作用在 Result 上时，Ok(v) 取出 v 继续执行，Err(e) 立即从当前函数返回 Err(e)；作用在 Option 上时，Some(v) 取值，None 直接返回 None。它只能出现在返回类型兼容的函数里，main 也不例外。

真正省事的是错误类型的自动转换。? 在返回前会对错误调用 From::from，把源错误转成函数声明的错误类型。只要目标类型实现了对应的 From，io::Error、ParseIntError 就能混在同一个函数里：

还有一条容易忽略的规则：? 的提前返回就是普通的 return，沿途局部变量正常析构，没有异常那样的栈展开开销，也不会跨越栈帧寻找捕获点。因此它只影响当前函数，调用者可以继续决定重试、降级还是上报。

在返回 Option 的函数里，? 同样好用，但它只传播“没有”，不携带原因。比如依次从缓存里查两个键，任一缺失就返回 None，两个 ? 就能表达，不必嵌套 if let。这也是选型时要想清楚的地方：一旦用 Option 做传播，失败原因就留不下来。

unwrap、expect 与 panic 的边界

unwrap() 在 None 或 Err 时直接 panic，expect() 多带一条消息，panic 时打印出来。二者不是“错误处理”，而是“拒绝处理”：把可恢复的情况升级为程序崩溃。

它们有合理的位置。测试里最典型，失败就该立刻停下并指出哪一行；示例代码和一次性脚本里，也能省去噪音。还有一种情况是逻辑上不可能失败，比如对字面量正则做编译、从刚判断过非空的栈顶取值、解析自己刚刚写出的常量。此时 expect 比 unwrap 好，因为消息能说明“为什么这里不该失败”。消息要写事实，不要写 “failed” 这类没有信息量的词。

风险在于边界会随代码演化而移动。今天“不可能为空”的配置字段，明天可能来自用户输入；今天内部调用的函数，明天可能被公开。库代码尤其要谨慎，一个 panic 会把恢复的选择权从调用者手里拿走，而调用者往往更清楚当前请求能否降级。

unwrap_or 系列则完全不同：它们在失败时返回默认值，不会 panic。默认值廉价时用 unwrap_or，需要计算或分配时用 unwrap_or_else，类型实现了 Default 时用 unwrap_or_default。

panic 与可恢复错误

两类失败的界线不在“严重程度”的感觉上，而在“调用方能否合理地继续”。文件不存在、网络超时、输入格式不对、权限不足，这些都是预期内的失败，调用方可以重试、换路径、提示用户，应当用 Result 表达。

panic 适合程序自身出了 bug 或状态已经不可信：数组越界、整数除零、断言失败、违反了内部不变量。这类问题继续执行只会把错误扩散到更远的地方。默认的 panic 会展开栈并运行析构函数，随后线程结束；设置 panic = "abort" 时则直接终止进程。catch_unwind 可以拦住展开，但它不是通用的异常机制，只适合 FFI 边界或测试框架这类特殊场合。panic!、unreachable!、assert! 都是这条路径上的工具，用它们等于声明：此处失败不是调用者需要处理的情况。

一个常见的误用是把用户输入导致的错误写成 unwrap。命令行工具读到非法参数就崩溃，用户体验很差；正确做法是返回 Result，在 main 或最外层统一打印并以非零码退出。

返回 Err 时，运行时会用 Debug 打印错误并以非零状态码退出；返回 Ok(()) 则正常结束。这比自己写 match、打印、调用 process::exit 要简洁，也避免了在每一层都重复同样的收尾代码。

Box<dyn Error> 是所有实现了 std::error::Error 的类型的 trait object。? 借助标准库提供的 From 实现把具体错误装箱，于是 io::Error、ParseIntError、自定义错误都能从同一个 main 返回。Error trait 的核心要求是同时实现 Display 与 Debug，并提供 source() 描述错误链；1.56 中 source() 已有默认实现，返回 None。

这条路的代价是类型被擦除。拿到 Box<dyn Error> 之后，只能通过 downcast_ref 尝试还原具体类型，按错误种类分支处理变得笨拙。因此它适合二进制入口和一次性脚本，不适合库的公开 API。库应当返回具体的错误枚举，把如何组合、如何展示的决定留给上层。同理，Box<dyn Error> 也不是“万能错误类型”，它只是把多种错误装进同一个盒子，丢失的正是调用者做精细判断所需的信息。

如果错误需要跨线程传递，例如在线程池里执行任务，Box<dyn Error> 还要加上 Send + Sync。标准库已经为它实现了来自具体错误的转换，写起来只是签名变长一些，本质仍是同一个 trait object。

闭包里的 ? 需要留意：闭包有独立的返回类型，不能借用外层函数的 ?。要么让闭包显式返回 Option 或 Result，要么在闭包内用 map_or 之类的组合子收尾。至于 and_then 链，长度超过四五步就该考虑拆成具名函数，链式写法可读，但过长的链同样难以调试。

测试是断言的主场。assert!(result.is_err()) 检查失败路径，assert_eq!(result.unwrap(), 8080) 检查成功值，#[should_panic] 则用来确认某处确实会 panic。断言消息里带上实际得到的值，排查会快很多。对 Option 也可以直接比较：assert_eq!(find_user(1), None)，前提是内部类型实现了 PartialEq 与 Debug。

两个断言分别覆盖失败与成功路径。assert_eq! 在失败时会同时打印左右两边的值，比 assert!(a == b) 的信息量大得多；需要补充上下文时，可以再传一段格式化消息。测试里用 unwrap 是合理的，因为此时失败本身就是测试失败，堆栈会直接指向出错的行。

小结

Option 表达“有没有”，Result 表达“成没成”，两者都是普通枚举，靠 match 与组合子消费。? 负责传播并按 From 转换错误，是函数内部最常用的写法；unwrap 与 expect 只应出现在测试、示例和可论证不会失败的位置。

判断用哪一个，看失败是否属于正常流程、调用方是否需要原因。可恢复的失败返回 Result，破坏不变量的 bug 才 panic。main 返回 Result 配合 Box<dyn Error> 足以支撑小工具，库则应保留具体错误类型。业务代码中的错误分层与 anyhow、thiserror 的取舍，已在第 640 篇讨论过，本文不再展开。

写法上，优先用组合子与 ? 把主干流程拉平，把 match 留给需要区别处理多个分支的地方；链条超过四五步就拆成具名函数，报错信息和调试都会清楚得多。
