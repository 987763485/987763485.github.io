Rust FFI 与 C 互操作

本文属于《Rust 学习路线》第 45/68 篇
上一篇系列目录下一篇

Rust 与 C 的互操作是工程落地的常见需求：要么复用成熟的 C 库，要么把 Rust 模块嵌入既有系统，要么用 Rust 替换性能热点。FFI（Foreign Function Interface）就是两种语言之间的桥，桥面不宽，规则却不少。

本文以 Rust 1.56 为准，从 extern "C" 与 ABI 讲起，依次梳理类型映射、所有权、panic、回调、绑定生成、构建配置与测试排错，示例尽量保持最小可编译。

FFI 的典型场景

FFI 不是为炫技而存在的，它解决的是工程约束下的现实问题。最常见的一类需求是复用成熟的 C 库：数据库驱动、压缩、加密、图像解码等领域积累了大量经过多年验证的实现，重写一遍既不经济，也难以在短期内达到同等质量。此时 Rust 通过声明外部函数来调用它们，把 unsafe 收敛在薄薄的一层封装里。

第二类需求方向相反：已有系统用 C 写成，想把新增模块交给 Rust，以换取更好的内存安全与并发表达力。做法是把 Rust 编译成动态库或静态库，暴露一组 C 函数，再由原有构建系统链接进去。第三类需求来自性能热点：某段逻辑用脚本或高层语言写得太慢，可以用 Rust 重写，再通过 FFI 接回原系统。C++ 的名字修饰、异常与模板让直接互操作复杂得多，通常先包一层 C 接口，本文不展开。

需要提醒的是，跨语言调用不是零成本：每次调用都有传参、栈切换和可能的拷贝，字符串与容器的转换还常伴随内存分配。因此边界应划在粗粒度的位置，一次处理一批数据，而不是在紧循环里逐元素调用。FFI 的真正成本往往不在那几条指令，而在所有权与错误处理约定是否清晰。

extern “C” 与 ABI

ABI（Application Binary Interface）规定了两件事：函数怎么被调用，以及数据在内存里怎么摆放。它包括调用约定、参数与返回值的传递方式、名称修饰规则、结构体布局和栈清理责任。Rust 默认的 ABI 没有稳定性承诺，编译器可以对函数做重命名、重排参数甚至改变传参方式；一旦跨进程或跨语言，这些细节都必须钉死。extern "C" 的作用就是让函数采用目标平台的 C ABI。

导出函数写成 pub extern "C" fn，导入函数则放在 extern "C" { ... } 块中；导入时还可以用 #[link(name = "z")] 把库名写在声明旁，省去构建脚本里的链接参数。两者常被混为一谈，实际上前者决定“我怎么被调用”，后者声明“我要按什么规则调用别人”。只写 extern "C" 还不够：Rust 编译器仍会对符号做名称修饰，C 链接器找不到预期名字，所以导出时通常还要加 #[no_mangle]。#[no_mangle] 只改符号名，不改变 ABI，两个属性缺一不可。

在 Linux 上可以用 nm -D target/release/libdemo.so | grep add 确认符号是否真的导出；如果看到的是 _ZN 开头经过修饰的名字，说明漏了 #[no_mangle]。Windows 上调用 Win32 API 时常用 extern "system"，它在 32 位环境对应 stdcall，在其他环境与 C 接近；普通跨语言库仍以 extern "C" 为准。还有一个容易忽略的点：extern "C" 约束的是函数边界，不约束函数体内部，内部仍可自由使用 Rust 的安全抽象。

类型映射：从整数到结构体

跨边界的第一原则是按 C 的类型选 Rust 的类型。定宽整数可以直接对应，i32 对 int32_t，u64 对 uint64_t；但 C 的 int、long、char 宽度依赖平台，应使用 std::os::raw 中的 c_int、c_ulong、c_char。size_t 对应 usize，ssize_t 对应 isize，指针大小也随之匹配。协议若明确规定了位宽，就改用定宽类型并在文档里写清楚。

指针映射为 *const T 或 *mut T，无类型指针用 *mut c_void。Rust 引用带有非空、对齐、有效等强假设，C 传来的指针未必满足，入口处应先判空再转换。函数指针可用 Option<extern "C" fn(...)> 表达可空回调。bool 要特别小心：C99 的 _Bool 与 Rust bool 通常都是 1 字节，但旧接口常用 int 表示布尔值，按 bool 声明就会读错字节。

字符串是坑最多的部分。C 字符串以 NUL 结尾且不携带长度，Rust 的 String 保证 UTF-8 但不要求结尾 NUL。收到 *const c_char 后用 CStr::from_ptr 取得借用视图，调用前必须确认指针有效且确实以 NUL 结尾，否则仍是未定义行为；之后再调用 to_str() 检查 UTF-8，失败时可用 to_string_lossy() 有损转换。反向传递用 CString::new 构造带结尾 NUL 的缓冲区，内容含内部 NUL 时它会返回错误。

数组没有自动长度，惯例是传指针加长度。用 slice::from_raw_parts 重建切片前，必须确认指针有效、对齐且长度范围内的元素可读。结构体跨边界必须加 #[repr(C)]，字段顺序和填充才与 C 一致，嵌套结构体也要逐层标注；结构体里只能放 C 能理解的字段，String、Vec 需要改成指针或使用不透明句柄。布局是否真的一致不能只靠肉眼，在测试里断言 size_of 与关键字段偏移，能在切换平台或编译器时及时报警。

所有权、生命周期与内存安全

跨语言没有统一的借用检查器，所有权规则只能靠约定和文档。最基本的一条是“谁分配，谁释放”，并且释放必须发生在分配它的那一侧、使用同一个分配器。C 的 malloc 配 free，Rust 的 Box 配 Box::from_raw，不能交叉；在 Windows 上不同 CRT 之间混用分配器尤其危险。若接口需要把 Rust 分配的内存交给 C，必须同时导出一个释放函数，并在头文件里注明配对关系。

常见的所有权模式有四种。第一，调用方提供缓冲区，Rust 只借用并在返回时报告所需长度，适合定长或可重试的场景；两段式调用要把第一次返回的长度当成不可信输入，第二次调用前重新校验。第二，Rust 分配并返回指针，同时提供 *_free 函数，调用方用完后必须调用。第三，指针只在本次调用期间有效，C 不得保存。第四，通过 Box::into_raw、CString::into_raw 把所有权真正转移出去，之后由接收方用对应的 from_raw 收回。四种模式可以组合，但每条路径都要写清楚。

不透明句柄是控制所有权的实用手段：头文件里只声明 typedef struct Buffer Buffer;，C 看不到内部字段，也就无法误拷贝或误释放。生命周期在 FFI 签名里会被擦除，编译器无法阻止 C 在 Rust 对象销毁后继续持有指针，这类悬垂只能靠接口契约避免。入口函数还要逐一检查空指针、长度溢出、对齐和越界；双重释放通常来自两侧都以为自己是所有者，把释放集中到一个函数能减少这类问题。跨线程调用则要确认对象真的满足 Send 与 Sync，FFI 不会替你做这项检查。

panic、回调与错误传递

panic 不能跨过 extern "C" 边界。Rust 的栈展开依赖自己的元数据，C 栈帧不理解这套规则，一旦 panic 穿过边界就是未定义行为；即使某些编译器版本会插入中止逻辑，也不能把它当作可依赖的行为。正确做法是在导出函数的最外层用 catch_unwind 捕获，把 panic 转成错误码。注意它只能捕获展开型 panic，若设置 panic = "abort"，进程会直接终止；panic hook 仍会打印日志，这是排查线索。

AssertUnwindSafe 表示调用者愿意为跨边界的状态一致性负责，不是让 panic 变得安全。若函数修改了全局状态，捕获后还要继续使用这些状态，就需要回滚或重新初始化。

回调的方向相反：C 把函数指针交给 Rust，Rust 在合适时机调用。无捕获的函数可以直接写成 extern "C" fn；若要把闭包传过去，需要蹦床技巧：把闭包再装箱成 Box<Box<dyn Fn>>，用 Box::into_raw 得到薄指针并转成 *mut c_void 作为 user_data，回调里再逐层转回引用；注销回调时要把 user_data 收回并释放。这种写法通常要求闭包拥有其捕获的数据，否则生命周期无法覆盖 C 侧的保存时间。回调同样可能 panic，入口处也要捕获。若 C 会在别的线程调用回调，闭包还必须满足 Send。

错误传递建议用显式返回码加输出参数：成功返回 0，失败返回负数或枚举值，结果写入调用方提供的指针；需要文本信息时，定义固定大小的错误结构体，不要把 Rust 字符串的指针直接交出去。结构体里的消息缓冲区要保证 NUL 结尾，并写明超长时如何截断。errno 风格也常见：提供 last_error() 返回线程局部缓冲区里的消息，并约定下一次调用后失效。线程局部存储避免了全局变量的竞争，但调用方若要长期保存，必须自行拷贝。

bindgen、cbindgen 与构建配置

手写声明容易与头文件漂移。bindgen 从 C 头文件生成 Rust 的 extern "C" 声明和 #[repr(C)] 结构体，适合 C 是事实来源的场景。它依赖 libclang，通常在构建脚本里调用，或先用命令行生成再提交到仓库。生成结果是一层 unsafe 接口，不要直接在业务代码里到处调用，应在上面再包一层安全封装，把判空、长度和错误码检查收口。头文件很大时，用 allowlist 只生成需要的类型和函数，既缩短编译时间，也减少要审计的 unsafe 面。

cbindgen 的方向相反：从 Rust 源码生成 C 头文件，适合 Rust 是事实来源。它读取 #[no_mangle] pub extern "C" 函数和 #[repr(C)] 类型，按配置输出 .h。生成的头文件应纳入版本管理，并在 CI 中重新生成后比对，防止代码改了而头文件没更新。

cdylib 产出动态库供 C 链接，staticlib 产出静态库；若同时要给其他 Rust crate 使用，再加上 rlib。构建脚本通过 cargo:rustc-link-lib 和 cargo:rustc-link-search 声明依赖库与搜索路径，用 cargo:rerun-if-changed 声明何时重新运行。需要编译一小段 C 胶水代码时，cc crate 比手写编译命令更省事。静态链接部署简单但体积大，动态链接则要处理运行时的库搜索路径；发布前还应确认 panic 策略与目标平台一致。

测试、排错与常见坑

FFI 代码的测试要覆盖两侧。Rust 侧可以写单元测试，验证 CString 往返、空指针、零长度、含内部 NUL 的输入以及超长字符串；集成测试则用 cc 编译一个小型 C 程序，真实地链接并调用导出函数，检查头文件与库是否匹配。内存问题可以借助 Valgrind 或 AddressSanitizer：Rust 侧需要通过 nightly 工具链的 -Z sanitizer=address 开启，C 侧按编译器选项开启。错误路径同样要测：故意让回调返回失败、让 C 传入空指针，确认 Rust 不崩溃且错误码可读。模糊测试适合喂随机长度和随机字节，重点观察崩溃与泄漏，而不是只验证正常路径。

排错时先确认符号是否导出、ABI 是否一致，再看数据布局。nm、objdump 能看出符号名和调用约定；在 C 侧打印 sizeof 与字段偏移，和 Rust 的 std::mem::size_of 对照，能快速发现遗漏的 #[repr(C)] 或填充差异。若程序在边界附近随机崩溃，优先怀疑悬垂指针、长度计算和线程竞争，而不是业务逻辑。

常见坑还有几类。字符串编码不是 UTF-8 时 to_str() 会失败，不能想当然地 unwrap()；C 的 long 在 Windows 上是 32 位，在 64 位 Linux 上是 64 位，跨平台接口应改用定宽类型。可变参数函数在 Rust 中调用受限、定义尚未稳定，能不用就不用；C 侧若把 va_list 传进来，更要避免依赖布局。全局状态在动态库被多个模块加载时可能各自一份，初始化和销毁顺序都不可控。#[no_mangle] 的符号名冲突会让链接器悄悄选错实现，给导出符号加统一前缀能降低风险。

线程安全方面，C 可能从任意线程调用导出函数，Rust 的 RefCell、Rc 并不线程安全；共享状态应使用 Mutex、原子类型，或干脆要求单线程调用并写进契约。回调重入也要考虑：C 在回调里再次调用同一个 Rust 函数时，锁不能已经持有。对齐问题常出现在把 char 缓冲区强转成结构体指针时，正确做法是用 read_unaligned 或先拷贝到对齐的局部变量。把这些约定写进头文件注释和测试用例，比事后排查省力得多。

小结

FFI 的核心不是语法，而是契约：ABI 决定怎么调用，类型映射决定怎么解释内存，所有权约定决定谁来释放，错误码决定失败如何表达。把 unsafe 收在薄封装层，入口处判空、验长度、捕获 panic，出口处明确所有权，能避开绝大多数事故。绑定可以自动生成，但布局与生命周期仍需人工确认；测试要同时覆盖 Rust 与 C 两侧，并借助 sanitizer 与 Valgrind 查找内存问题。边界越窄、约定越清楚，互操作就越可靠。
