高并发红包系统设计与实现

红包是中文互联网里少数同时具备高并发、强资金属性与强社交传播的业务形态：一个春节活动可能在几分钟内涌入平时数十倍的流量，而每一分钱都必须对得上账。本文从业务模型出发，讲清拆分算法、Redis 预分配与 Lua 原子扣减、异步落库、幂等与对账这一整条链路，重点说明每个环节为什么这样设计、边界在哪里。本文面向已经熟悉 Redis 与消息队列基本用法、准备接手或重构营销资金类系统的后端工程师，读完后应当能独立画出红包系统的核心状态机，并判断自己的实现会在哪些地方超发或少发。

为避免与既有文章重复，秒杀系统的整体分层、幂等性的一般方法论本文不再展开，只讨论红包业务特有的约束：金额必须可拆分、领取必须一人一次、剩余量必须与资金严格对应。文中出现的并发量与耗时均为示意值，用于说明量级关系，不代表任何真实系统的实测结果。

红包业务模型与边界

动手写代码之前，先把名词定清楚。红包系统里有四个容易混淆的概念：红包单、份额、群红包、裂变红包。红包单是一次发放动作创建的实体，记录总金额、总份数、类型与状态；份额是红包单内可被领取的最小单位；群红包把领取人限定为群成员，它的并发特征是同一时刻大量成员争抢同一个红包单；裂变红包在领取成功后引导用户分享，分享出去的是新的红包单，用 parent_id 指向来源单。

边界需要说明：本文只讨论钱怎么发出去、怎么保证不重不漏，不讨论营销玩法、风控策略与前端动画。裂变红包在数据模型上只是多了一层父子关系，资金仍按单结算，因此后文的算法与链路对它同样适用。群红包多出的一次群成员校验，放在领取链路的最前面，属于业务准入，不影响资金逻辑。

三个不变量贯穿全文。第一，所有已发放份额之和等于红包单的已发金额；第二，已发金额不超过总额；第三，同一用户对同一红包单最多成功领取一次。前两条是资金约束，第三条是业务约束。任何设计如果无法在超时、重试、进程崩溃这些异常下继续满足这三条，就还没有写完。

存储上，金额一律以分为单位，用 BIGINT 保存，禁止用浮点数参与任何运算。下面是最小化的两张表，省略了索引与审计字段，只保留与资金相关的列。

uk_packet_user 是最后一道防线，它把“一人一次”从应用层约定变成了数据库层面的硬约束。即使缓存被清空、消息被重复投递，重复插入也会失败，而不是产生两条成功记录。uk_request 则服务于客户端重试：同一个请求号重复提交时，服务端可以直接返回首次的结果。

红包单的状态只允许单向迁移：初始化、可领取、领完或过期，关闭是运营侧的终止操作。每次迁移都写成带条件的更新，例如把“领完”写成 UPDATE red_packet SET status = 2 WHERE id = ? AND status = 1 AND sent_count = total_count，用影响行数判断是否迁移成功。这样即使两个请求同时判定“最后一份已被领走”，也只有一个能把状态推到领完，另一个会看到影响行数为零并重新读取。

拆分算法：二倍均值法与金额精度

拼手气红包的核心是一个随机拆分函数。最朴素的做法是每次在剩余金额里随机取一个数，但这样很容易出现前几个人拿走大部分、后面的人只能分到几分钱的情况。二倍均值法对此做了约束：每次取随机金额的上限设为“剩余人均金额的两倍”，既保证期望公平，又避免单份过大。

设剩余金额为 R、剩余份数为 N，人均为 R / N，则本次金额在 [1, min(2R / N, R - (N - 1))] 内均匀取值。第二个上限不能省：如果只剩 3 份、共 5 分钱，人均约 1.67 分，两倍均值向上取整也只有 4 分，一旦取到 4 分，后面两人就不够各分 1 分。R - (N - 1) 保证给后面每个人至少留下 1 分，这是金额精度带来的硬边界。

这个算法的期望是人均值 R / N，但方差并不小。以均匀分布近似，单次取值的方差约为人均值的平方除以三，也就是说人均 1 元时，单份金额的波动幅度在几毛钱量级，尾部会拖得比较长。实际业务中这个分布是可以接受的，它带来的“意外感”正是拼手气红包的产品目标。如果产品要求更集中，可以把上限从两倍降到一点五倍，代价是大额份额出现的概率下降。

用 Go 实现时，需要注意三点：金额用 int64；上限要 clamp；最后一份直接取剩余，不再随机。下面这个版本只在创建红包时执行一次，结果写入缓存，属于离线计算。

这个函数是纯函数，给定种子就能复现，便于单测与对账重算。它有一个已知偏差：最后一份不受两倍均值约束，可能明显大于前面的份额。金额小、份数少时偏差肉眼可见，有的实现会在最后三份改用“随机切两刀”收敛尾部分布。

拆分可以在两个时机发生，这直接决定了系统结构。预分配是在创建红包时就把 N 份金额算好，写入 Redis 的列表；领取时只做弹出，不再计算。实时分配是每次领取时在 Lua 脚本里按当前余额和剩余份数现算。两者的取舍如下。

维度 预分配 实时分配
领取耗时 一次弹出，稳定 需要计算，略高但仍在微秒级
内存占用 与份数成正比 只存余额与份数
可审计性 创建后即可全量核对 只能事后重算
故障恢复 列表丢失需重建，重建结果可能与已发不一致 状态少，恢复简单
适用场景 中小规模、需要提前风控 超大份数、内存敏感

笔者的建议是默认预分配。红包的份数通常有业务上限，而“创建时就能把每一份算出来”带来的可测试性与可审计性，远比省下的那点内存有价值。只有在份数达到百万级、且创建时间被严格限制的场景，才值得改用实时分配。无论选哪种，金额精度都必须统一到分：数据库存整数，接口传整数，前端只做展示层除法，任何一处用浮点都可能在对账时差出几分钱。

领取链路：Redis 预分配与原子扣减

领取是整条链路中并发最高的操作。一个热门群红包可能在几秒内被上千人同时点击，如果每次都去数据库做“查余额、改余额、插记录”，行锁会把请求排成一条长队，响应时间随并发线性上升。因此主流做法是把扣减放在 Redis 完成，数据库只承担最终的持久化。

先看整体时序。网关负责登录态校验与限流，领取服务只做参数校验和脚本调用，脚本返回成功后再发一条事件到 Kafka，由消费者异步写入 MySQL。用户看到的响应不等待落库，落库失败由补偿任务兜底。

  participant G as 网关

  participant R as Redis
  participant K as Kafka
  participant D as 落库消费者

  G->>S: 校验登录态与限流
  S->>R: EVALSHA 执行领取脚本
  R-->>S: 返回金额或重复标记
  S->>K: 发送领取成功事件
  S-->>U: 返回金额
  K->>D: 投递事件
  D->>D: 幂等写入 MySQL

Redis 中一个红包对应三类键：rp:list:{id} 是预分配的份额列表，rp:amount:{id} 是剩余金额，rp:claim:{id} 是已领取用户集合。份额列表决定“还能不能领”，剩余金额用于交叉校验“钱对不对”，已领集合负责“这个人是不是已经领过”。库存与金额之所以分开存，是因为它们回答的是不同的问题：份数回答业务问题，金额回答资金问题。两者在同一个脚本里更新，任何时刻都应当满足“列表元素之和等于剩余金额”，这条恒等式是后文对账的基础。

脚本必须把“查重、取份额、扣金额、记用户”四步放进一次 EVAL。Redis 执行脚本期间不会插入其他客户端的命令，四步因此成为一个不可分割的整体。下面是最小可用的版本，返回值的第一位是状态码，第二位是金额。

这段脚本刻意保持短小，只做四件事。原因在于 Redis 的脚本没有事务回滚：脚本执行到一半报错，前面已经执行的写命令不会撤销。所以参数校验、类型转换这类可能抛错的动作要尽量放在写操作之前，写操作本身只用确定不会失败的命令。把复杂的业务判断塞进 Lua，一旦某个分支抛错，就会留下“份额被弹出但用户没被记录”的中间状态，事后很难分辨。

调用侧要做两件事：用 EVALSHA 减少脚本传输，并在收到 NOSCRIPT 时回退到 EVAL 重新加载。同时给脚本设置合理的超时与重试策略，注意重试必须携带同一个请求号，否则会把“超时但其实成功”的请求变成二次领取。

异步落库的关键在消费者一侧。事件里至少要带 packet_id、user_id、amount、request_id 和事件 ID。消费者写库时依赖 uk_packet_user 与 uk_request 两个唯一索引，重复消息会命中唯一键冲突，捕获该错误后视为成功并提交位点，而不是无限重试。位点提交放在写库成功之后，宁可重复消费也不能丢消息，重复由唯一索引吸收。

扣减已在 Redis 成功，为什么还要落库？因为 Redis 是易失的。即使开了 AOF，主从切换仍可能丢掉最后一段写入，而资金记录不能只存在于内存数据库里。Redis 负责“扛住并发”，MySQL 负责“留下证据”，两者的职责不能互换。

幂等与防重：三层防线

红包的幂等有三个层次，分别对应三种重复来源。请求级幂等针对客户端或网关的重试，键是 request_id；用户级幂等针对用户重复点击、多端同时点击，键是 packet_id + user_id；消息级幂等针对 Kafka 的至少一次投递，键是事件 ID。三者不能互相替代，任何一层缺失都会在特定故障下暴露。

第一层在 Redis 脚本里，SISMEMBER 挡住绝大多数重复请求。它快，但不可靠：集合可能因为过期或被清空而丢失。第二层在 MySQL 的唯一索引，uk_packet_user 是最终裁决者。第三层是状态机，领取记录从“处理中”迁到“成功”，每次迁移都带上前置状态作为条件，避免“已退回”的记录被重新改成“成功”。

重复请求不应该返回错误，而应该返回首次的结果。用户点两次，看到两次相同的金额，体验才是对的；如果第二次返回“请勿重复领取”，用户会怀疑第一次到底成没成功。因此脚本在命中已领集合时，还要能拿到当时的金额。可以在 rp:claim:{id} 里存用户到金额的映射而不是集合，或者额外写一个带 TTL 的结果键 rp:result:{id}:{user}。前者省一次查询，后者便于设置过期时间，实践中按红包规模选择。

还有一种更隐蔽的重复：请求到达两个不同的服务实例，两边同时通过 SISMEMBER 检查。因为检查与写入在同一个脚本内，Redis 的单线程执行保证了只会有一个成功，这一点是脚本相对于“先查再写”两条命令的核心价值。如果拆成两条命令，两个实例都可能读到“未领取”，然后各自弹出份额，超发就此发生。

状态机的设计要覆盖失败路径。领取记录至少有“处理中、成功、失败、已退回”四个状态，红包单有“初始化、可领、领完、过期、关闭”五个状态。所有状态更新都写成条件更新，用影响行数判断胜负，而不是先查后改。条件更新在 InnoDB 下依赖行锁，同一行的并发更新会串行化，这正好是我们要的语义。关于锁的具体行为，可以参考 MySQL 官方手册中 InnoDB 锁的章节，后文参考资料给出了入口。

超发与少发：事务边界与消息补偿

超发的成因通常不是算法写错，而是原子性被破坏。第一位的原因是“先查后扣”拆成了两条 Redis 命令，两个请求都读到还有 1 份，然后各扣一次，余额变成负数。第二位的原因是重建缓存：运维发现缓存丢了，从数据库读出 sent_count 回填 Redis，但此时还有一批已领取、未落库的记录在 Kafka 里，回填的数值偏小，等于把已经发出去的钱又发了一遍。第三位的原因是脚本内部报错后继续执行，弹出了份额却没扣金额。

这三个原因指向同一条原则：状态的重建必须以“已持久化的成功记录”为唯一依据，并且重建期间必须停止写入。正确的重建流程是先把红包单置为不可领的维护状态，拒绝新的领取请求，等待消息积压清空，再用数据库中的成功记录重算剩余份额与金额，写回 Redis，最后恢复可领状态。这个过程会长达数分钟，但比事后追账便宜得多。

少发则是另一个方向：Redis 扣减成功，但事件没有到达 Kafka，数据库里没有这条记录。用户看到了金额，账上却没有。解决思路是在脚本里同时写一份待投递记录，把“扣减”和“待发消息”放进同一个原子操作。最简单的形式是在脚本末尾追加一次 RPUSH rp:pending {id} {payload}，后台线程负责把列表搬运到 Kafka，发送成功后再从列表移除。这样即使生产者瞬间不可用，事件也不会凭空消失。

搬运线程要处理“重复搬运”：从列表取出后发送成功、但移除失败，下次会再发一遍。这没有关系，消费端的唯一索引会吸收重复。真正要避免的是“移除了但没发出去”，所以顺序必须是先发后删。这个模式与本地消息表同构，只是把表换成了 Redis 列表，代价是 Redis 故障时仍可能丢一小段，因此还需要日终对账兜底。

Kafka 侧的关键配置是确认与幂等。生产者把 acks 设为 all，确保消息写入所有同步副本；开启 enable.idempotence，避免网络重试导致同一分区内出现重复；重试次数给足，并限制在途请求数，防止重试乱序。

需要强调的是，Kafka 的幂等生产者只保证“单分区、单会话内不重复”，它管不了业务层面的重复，也管不了跨会话的重发。业务唯一键仍然是必需品，消息中间件的幂等只是减少无效重复，不是替代方案。

补偿任务的职责是收敛中间状态。扫描“处理中”超过阈值（例如 30 秒）的领取记录，逐条判断：Redis 中该用户是否在已领集合里，若在则补写成功并重发事件，若不在则把记录置为失败。扫描要分页、限速，避免补偿本身成为新的压力源。补偿逻辑必须可重入，同一条记录被扫到两次不能产生两笔账。

热点、限流与大红包

Redis Cluster 按 key 的哈希槽分片，同一个红包的所有键落在同一个分片上。Redis 处理命令是单线程的，这意味着一个红包的领取速度上限，就是那个分片单核的处理能力。普通红包每秒几百次领取毫无压力，但一个面向全网的裂变红包，或者一个几万人的明星群，很容易把单个分片打满，表现为脚本耗时上升、同分片其他 key 的访问一起变慢。

应对单 key 热点的第一招是分桶。把预分配的份额列表按份数切成 M 个子列表，键名带上桶号，脚本根据用户 ID 的哈希选择桶。每个桶有自己的剩余金额，领取时只扣本桶。这样热点被摊到 M 个 key 上，只要它们落在不同分片，吞吐就能成倍提升。代价是“剩余总额”不再是一个原子读数，需要异步汇总，且某个桶先空时会出现“总额还有、这个桶没了”的情况，脚本要能跳到下一个桶重试。M 的取值要结合分片数，太小起不到分散作用，太大则汇总与运维成本上升。

第二招是限流，分层设置。网关层限制总入口 QPS 与单机连接数，防止流量把整个集群打垮；红包维度用令牌桶限制单个红包的领取速率，桶的容量按红包份数与预期时长估算；用户维度限制“每人每秒一次”，这一层其实已被幂等集合部分覆盖，但显式限流能更早地拒绝恶意刷接口。限流被触发时返回明确的“活动太火爆，请稍后再试”，而不是超时，让客户端有机会退避。

第三招是降级。当某个红包的分片负载超过阈值，可以临时把它切到“排队模式”：请求先写入一个队列，前端轮询结果。这会把同步等待变成异步，牺牲体验换取系统不崩。另一种降级是直接返回“已领完”，但这只适用于确实接近领完的红包，否则会引发客诉。降级开关必须能按红包粒度打开，且要有自动恢复条件，不能只靠人工记得关掉。

对于真正的超大红包，还有一种结构性做法：把“一个大红包”拆成“多个子红包”，每个子红包独立分片、独立计数，用户在哪个子红包领到就算成功。这在产品上表现为“分批放量”，本质是用业务规则换取技术上的可扩展性。是否采用取决于活动能否接受“同一时刻不同用户看到不同余量”，这需要产品与技术的共同决策。

对账、资金安全与过期退回

红包系统里最容易出事的不是峰值，而是峰值过后的账。资金安全依赖一条恒等式：红包单的已发金额加上剩余金额，必须等于总金额；已发金额必须等于所有成功领取记录的金额之和；已发份数必须等于成功记录的条数。三个等式分别落在数据库与 Redis 两侧，对账就是定期验证它们。

实时核对关注最近的时间窗。每隔一分钟，取最近五分钟内状态为成功的记录，按红包单聚合，与红包单上的累计值比对。这个粒度能在一分钟内发现异常，代价是要扫增量数据，因此需要 (status, updated_at) 上的索引。日终核对做全量，覆盖当天所有结束的红包单，同时与账务系统的资金流水比对：红包系统记的是业务单据，账户系统记的是资金变动，两边笔数与金额必须一一对应。

查出来的差异要分类处理，而不是一律改数。第一类是单边账：Redis 有、数据库没有，多半是消息丢失，按待投递列表或用户申诉补记；第二类是金额差：通常来自精度或重复扣减，需要定位到具体记录；第三类是状态不一致：红包单显示领完但记录数不足，说明有份额被弹出却没有对应记录。每一类都先进入差异池挂账，由自动冲正处理已知模式，超出阈值或模式未知的转人工。自动冲正必须设上限并留审计日志，绝不能写成“发现不平就改余额”。

过期退回是资金安全的另一半。红包创建时约定有效期，到期仍未领完的部分要退回发送方。退回由定时任务触发，但真正的难点在并发：任务把红包置为过期的同一瞬间，可能还有用户在领取。正确的顺序是先在数据库做条件更新，把状态从“可领”改成“过期”，影响行数为 1 才继续；影响行数为 0 说明红包已被领完或被关闭，直接跳过。状态变更成功后，再按数据库中的剩余金额发起退款，写入一条类型为退回的流水，并用红包单号加流水类型做唯一键，保证重复执行不会退两次。

退款金额必须以数据库为准，不能读 Redis 的剩余金额。原因很简单：Redis 可能落后于数据库，也可能因为重建而短暂不准，而退款是往外掏钱的动作，只能相信已经持久化的数据。退款前先把 Redis 中的状态位置为过期，领取入口读到过期即拒绝；退款完成后再清理键。顺序反了就会在清理与退款之间留下窗口，让用户看到“还有余额”却领不到。

压测、容量与可观测性

容量估算应当从业务假设出发，而不是拍一个 QPS。先估算峰值领取请求数：峰值在线用户数乘以点击率，再除以活动时间窗，得到平均 QPS，乘以三到五倍的峰值系数得到设计目标。然后用单分片实测的脚本处理能力去除，得到需要的分片数，再留出三成余量。所有输入都是假设值，结论也只是一个量级，真正的数字必须来自压测。

压测场景要覆盖四类操作：创建红包、领取、查询结果、过期退回。领取场景必须区分“分散在多个红包”和“集中在一个红包”，后者才能压出单 key 热点的瓶颈。施压时观察的不是单一 QPS，而是脚本耗时的 P99、错误码分布、Redis 各分片的 CPU、Kafka 的消费积压、落库延迟。如果 P99 上升但 CPU 不高，多半是脚本里有慢命令或大 key；如果 CPU 打满而 QPS 上不去，就是分片能力到顶，该分桶了。

可观测性要围绕“一笔领取能否被完整追踪”来建。网关生成 trace ID，透传到领取服务、消息头、消费者，日志里统一带上红包单号、用户 ID、请求号，用户 ID 做脱敏。指标至少包括：领取成功数、重复数、领完数、限流数、脚本耗时分布、消息生产失败数、消费积压、落库失败数。告警的重点不是 QPS，而是对账差异大于零、消费积压持续增长、落库延迟超过阈值，这三类才直接对应资金风险。

还有一个常被忽略的观测点：Redis 中份额列表的长度与剩余金额是否满足恒等式。可以每隔一段时间抽样几个活跃红包，用 LLEN 与 GET 交叉验证，再与数据库比对。这个检查成本很低，却能在用户投诉之前发现脚本逻辑的错误。

常见坑清单

  • 在 Lua 里做复杂业务：分支多、异常路径长，报错后已执行的写命令不会回滚；脚本只做校验与原子写。
  • 只靠先查后写防重：两条命令之间有空隙，并发下必然重复；查与写必须在同一脚本内。
  • 用浮点算金额：元与分混用，累加后差几分钱；全链路统一整数分。
  • 重建缓存覆盖实时值：未落库的领取被抹掉，等于二次发放；重建前停写，以成功记录为准。
  • 消息先删后发：发送失败就永久丢失；先发后删，重复交给唯一索引吸收。
  • 忽略退回与领取的并发：退款前先用条件更新改状态，金额以数据库为准。

小结

红包系统的难点不在单个算法，而在多条链路共同维持一组恒等式。拆分保证总额守恒，Lua 脚本保证查重与扣减原子，唯一索引保证最终不重，对账保证异常可被发现，过期退回保证未发出的钱能回到原处。落地时先把这些不变量写成可执行的校验与告警，再谈性能优化；顺序反了，压测数字再漂亮也守不住账。
