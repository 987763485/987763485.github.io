TypeScript 泛型约束与默认值

本文属于《TypeScript 学习路线》第 33/74 篇
上一篇系列目录下一篇

泛型写起来不难，难的是把约束写到恰到好处。约束太松，函数体里除了把值原样传出去几乎什么也做不了；约束太紧，调用方又会被挡在门外。本文从几个具体的小函数出发，讲清 extends 约束的语义、几种常见约束的写法、默认类型参数的推断优先级，以及参数之间如何互相引用，最后整理一组容易踩的坑和 API 设计上的取舍。

读完之后，你应该能为一个泛型选出既够用又不啰嗦的约束。文中的示例以 TypeScript 4.4 为准，都可以直接放进项目里验证；工具类型的内部实现、条件类型里的类型体操，以及编译器做类型推断的细节，分别属于另外几个话题，本文只在必要处点到为止。

无约束的泛型几乎什么都做不了

extends 检查的是可赋值性

T extends { length: number } 读作“T 必须是 { length: number } 的子类型”。这里的子类型与面向对象里的继承没有必然关系，它指的是可赋值性：只要某个值能够赋给 { length: number }，它的类型就满足这条约束。字符串可以，数组可以，函数也可以，因为函数对象自身带有表示形参个数的 length 属性；数字和布尔值则不行。

TypeScript 采用结构类型系统，判断依据是成员的形状，而不是类型的声明来历。一个类即使没有写 implements，只要公开成员对得上，同样满足约束：

约束只参与检查，不会把 T 变成约束类型。longer("hello", "hi") 的返回值类型仍然是 T 本身，而不是 { length: number }。这一点在约束很宽时尤其重要：调用方拿到的类型精度取决于推断出的 T，而不是那条宽泛的约束。

还要区分一种形似而神不同的写法。条件类型里的 T extends string ? A : B 也用了 extends，但那里的 extends 只表示一次类型关系判断，并不限制 T 的取值；本文讨论的是类型参数声明位置上的约束，两者含义不同。

几种常见的约束形态

一个泛型参数在函数体里能做什么，取决于约束提供了多少信息。与其每次临时拼一个形状，不如记住几种常见的约束形态，它们足以覆盖日常场景。

用 keyof T 约束键名

keyof T 得到 T 所有公开属性名组成的联合类型。把 K 约束为 keyof T，再用 T[K] 作为返回类型，按名取值就完全类型安全了：

这里的 K 由实参推断，调用方不需要手写 get<typeof user, "name">。传错键名时，报错会直接列出可用的键，这比运行时拿到 undefined 再排查要省事得多。若 T 带有字符串索引签名，keyof T 会退化为 string | number，此时约束几乎不再筛选键名，使用字典类型时要接受这一点。

当键名与 T 无关，只是想要“任意合法的属性键”时，可以写 K extends keyof any。keyof any 的结果是 string | number | symbol，标准库里的 PropertyKey 就是它的别名。直接写 PropertyKey 可读性更好。

object 约束则排除所有原始类型，接受对象、数组与函数。它适合表达“我要一个引用类型的值”，但它不提供任何成员信息，函数体里仍然访问不了具体属性。因此 object 往往只是过渡，真正需要读写字段时，还得换成更具体的形状。

默认类型参数与推断优先级

约束回答“T 必须能做什么”，默认值回答“调用方不说的时候，T 应该是什么”。二者经常一起出现：约束划定下限，默认值提供最常用的选择，让简单的调用不必写类型实参。

三者的优先级是：显式类型实参最高，其次是从实参推断，最后才是默认值。默认值只负责兜底，不会改变约束，也不参与从实参推断的过程：

p1 说明推断优先于默认值；p2 说明一旦开始显式给类型实参，后面的参数就只能靠默认值补齐，不能“指定 A、推断 B”。这也说明默认值最实用的场景：为后续参数准备合理起点，避免调用方写全。

顺序上有一条硬规则：带默认值的参数必须排在无默认值的参数之后，type Bad<T = string, U> = [T, U] 会直接报错。默认值还可以引用前面的参数，这为“由 T 推导 K”提供了方便。

约束过宽与过窄的取舍

约束是一份双向承诺：对调用方承诺“我只需要这些”，对函数体承诺“这些一定存在”。写宽了，函数体里处处要再收窄；写窄了，调用方被迫提供用不上的成员。两种偏差都会让泛型从帮手变成负担。

T extends object 是典型的过宽：它保证了传入的是引用类型，却不提供任何可访问的成员，函数体里连 obj.id 都写不了。Record<string, unknown> 稍好一些，可以按任意字符串取值，但取出来都是 unknown，键的精度也丢了。反过来，T extends { id: string; createdAt: Date; updatedAt: Date } 如果函数体只用到 id，就是在强迫调用方补齐两个时间戳，复用性会明显下降。

约束写成联合类型时，T 可以取其中任意一个成员，也可以取整个联合。T extends string | number 的函数体里只能使用两者共有的操作；想按具体类型分支，需要条件类型，那属于类型体操的范畴，本文不展开。一条实用的经验是：先写刚好够用的最窄约束，等真实调用方提出需求再放宽；反过来做，签名里往往会留下永远用不上的成员。

泛型在接口、类、函数与别名中的差异

同一套泛型语法，放在不同载体上，行为有细微差别，写公共库时尤其容易碰到。

接口与类型别名都支持默认值。接口可以声明合并，但合并的各处必须使用完全相同的类型参数列表，连默认值也要一致，否则编译器会拒绝后续声明。类型别名不支持合并，不存在这个问题，也不能与同名接口互换。

类上的类型参数属于实例一侧，静态成员不能引用它。static create(): Store<T> 这样的写法会被拒绝，因为静态成员在所有实例之间共享，无法对应某一个具体的 T；需要时把类型参数声明在静态方法自己身上。接口与类上的参数在创建实例或使用时确定，之后一直沿用，默认值也在那一刻生效。

函数上的类型参数属于调用签名，每次调用独立推断一次，默认值同样按调用判断。也正因为如此，函数不支持“只推断一部分”：要么全部交给推断，要么从头开始显式给出。这个限制在参数之间存在派生关系时最明显，解决办法通常是把函数拆成两层，先固定外层类型，再推断剩下的部分。

常见坑与 API 设计

最常见的报错是 Type 'X' does not satisfy the constraint 'Y'。它指向实参，而不是泛型声明，先看传入的类型缺了哪个成员，通常比盯着定义更快。若 X 是很长的联合或交叉类型，报错会很难读，把中间类型抽成有名字的别名即可。

keyof any 与 keyof T 混用也很常见：参数写成 K extends keyof any，函数体里却直接 obj[key]，编译器仍会报错，因为 obj 没有索引签名。要么同时约束 T extends Record<K, unknown>，要么老老实实用 keyof T。

另一种退让是把默认值写成 any，例如 function parse<T = any>()。这等于给泛型留了逃生口：调用方漏写类型时静默退化为 any，约束名存实亡。默认值应当是“最合理的常见类型”，而不是“最省事的类型”。同理，T extends any 与 T extends unknown 不构成有效约束，只会让签名显得煞有介事。

重载与泛型都能表达“输入不同、输出不同”。重载逐条列举，适合参数关系不规则、或返回类型依赖字面量取值的场景；泛型用一条规则概括，适合类型之间只是同一关系的不同实例。两者混用时，每个重载签名都要能被实现签名兼容，泛型参数还需要在实现签名里重新声明。

最后是数量。一个签名出现三个以上类型参数，调用方很难一眼看清对应关系；这时可以把相关参数收进配置对象，或拆成两步调用。命名上，T、K、V 适合短小的工具函数，业务代码用 TEntity、TResult 更利于阅读。泛型存在的意义是让类型关系显式可查，一旦读者需要反复展开定义才能看懂，它就已经写过头了。

小结

约束用 extends 表达“至少能做什么”，检查的是可赋值性，依据是结构而非继承；默认值则在推断无果时兜底，优先级低于显式实参。常见约束不外乎 keyof T、Record<string, unknown>、object、函数签名与构造签名几种，选择时以函数体真正用到的成员为准。写 API 时控制类型参数的数量，宁可拆成两层，也不要让调用方去猜。把这些规则用熟，泛型才会从语法装饰变成真正的设计工具。
