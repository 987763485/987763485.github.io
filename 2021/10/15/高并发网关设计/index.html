高并发网关设计

网关是流量进入系统的第一道关口，也是故障最先暴露的地方。当单机连接数从几千涨到几十万、配置从一天一次变成一分钟一次时，网关的设计难点就不再是“支持哪些功能”，而是连接模型、内存占用、配置切换与故障隔离之间如何取舍。

本文面向已经写过反向代理或简单网关、准备把服务推到更高并发量的后端工程师。我们会沿着一条请求的路径，依次讨论连接模型、协议代理、路由匹配、连接池与超时、限流位置、动态配置、优雅重启和可观测性，并给出 Go、Envoy 与 Nginx 在 2021 年前后可以落地的做法。API 网关的功能清单与限流算法本身不在本文展开，本文只关心高并发场景下的架构选择与常见陷阱。

网关在系统中的位置与职责边界

先明确网关在调用链上的位置。一个典型的服务端系统，用户请求先经过负载均衡与边缘网关，再进入内部网关，最后才到达具体的业务服务。可以用一张简化的链路图表示：

flowchart TD
    A[客户端] --> B[四层负载均衡]
    B --> C[边缘网关]
    C --> D[内部网关]
    D --> E[业务服务 A]
    D --> F[业务服务 B]
    E --> G[缓存]
    E --> H[数据库]

边缘网关面向公网，处理 TLS 卸载、域名与路径路由、身份校验、粗粒度限流和访问日志；内部网关面向集群内部，处理服务间流量的路由、超时、重试与灰度。两者的技术栈可以相同，但容量模型与安全假设完全不同：边缘网关要假设每一个连接都可能是恶意的，内部网关则更关注低延迟与配置的一致性。

职责边界是设计时最容易含糊的部分。网关适合承担与协议和流量相关、且与业务无关的横切能力，例如 TLS 终止、HTTP/2 到 HTTP/1.1 的协议转换、认证令牌的验签、请求头规范化、灰度分流和指标采集。它不适合承担业务规则编排、数据聚合、复杂的参数校验，也不应该成为服务发现的唯一事实来源。一旦网关里出现“查一次用户表再决定路由”这样的逻辑，它就会随业务迭代频繁发版，而发版正是网关最脆弱的时刻。

另一个边界是重试与熔断的分工。网关知道下游实例的健康状态和连接池水位，适合做连接级与实例级的保护；但它不知道一次请求是否幂等，也不了解业务降级后的兜底数据。因此合理的分工是：网关负责快速失败、隔离坏实例、限制并发，业务侧负责幂等与降级语义。把两者混在一起，往往会出现网关重试三次、业务又重试三次，最终把下游放大九倍的事故。

数据平面与控制平面分离

网关的内部结构可以按“谁转发数据、谁决定怎么转发”拆成两层。数据平面位于请求路径上，负责监听、解析、匹配、转发、记录；控制平面负责接收配置、校验、编译成内部模型，再下发给数据平面。Envoy 是这一架构最清晰的样本：监听器由 LDS 管理，路由由 RDS 管理，集群由 CDS 管理，端点由 EDS 管理，证书由 SDS 管理，统称 xDS。Nginx 则更传统，配置来自文件，通过 reload 生效；OpenResty 生态常用共享内存与定时拉取来模拟动态能力。

分离带来的第一个好处是故障隔离。控制平面短暂不可用时，数据平面应当继续用最后一份有效配置转发流量，而不是拒绝所有请求。这意味着数据平面必须把配置完整保存在本地，启动时优先加载本地快照，再向控制平面订阅增量。第二个好处是变更可控：配置在控制平面完成语法、语义和引用完整性校验，数据平面只接受已经编译好的结构，避免“半份配置”进入请求路径。

数据平面内部推荐使用不可变快照加原子指针切换。每次配置变更都构造一份新的路由表与集群表，构造完成后一次性替换指针，正在处理的请求继续持有旧快照，直到处理结束自然释放。这样读路径没有锁，也不需要担心配置更新把某个请求的路由表改到一半。用 Go 表达就是 atomic.Value 保存一个只读结构：

控制平面还需要处理版本与确认。Envoy 的 xDS 协议为每次响应带上 version 与 nonce，数据平面应用成功后回 ACK，失败则回 NACK 并保留旧版本。这套机制的价值在于把“配置是否真的生效”变成可观测的事实。自研网关至少应实现三件事：版本号单调递增、应用失败时回滚到上一版本、控制平面能查询每个实例当前生效的版本。缺少第三点，灰度发布时你无法判断某个实例到底吃没吃到新配置。

连接模型：从 C10K 到 C100K

网关的性能上限首先由连接模型决定。历史上 C10K 问题的核心是：阻塞式 IO 下每个连接占用一个线程，一万个连接就是一万个线程，线程栈与上下文切换把机器压垮。解决方案是事件驱动：用 epoll 或 kqueue 监听大量 fd，只在就绪时处理，单线程即可管理上万连接。Nginx 与 Envoy 都建立在这个模型上，采用固定数量的 worker 进程或线程，每个 worker 运行一个事件循环。

第二种模型是 goroutine 加网络轮询器。Go 的运行时把阻塞式的 net.Conn 调用挂在 netpoller 上，开发者写起来像同步代码，底层仍是事件驱动。一个 goroutine 的初始栈只有几 KB，按需增长，因此十万连接在内存上是可以承受的，但要扣除每个连接的应用层缓冲区。示意而言，若每连接读写缓冲各 4 KB，十万连接仅缓冲区就是约 800 MB，这还没算 TLS 的会话状态。所以“goroutine 很轻”不等于“连接不要钱”，估算时必须把缓冲区算进去。

第三种是每连接每线程，也就是传统的阻塞 IO 加线程池。它的优点是编程模型最简单，调试直观；缺点是线程数量随连接数线性增长，长连接场景下内存与调度开销都不可接受。它适合连接数有限、请求处理时间较长的内部服务，不适合面向公网的长连接网关。

C10K 到 C100K 的跨越，难点往往不在应用层，而在内核与部署环境。需要检查的参数包括：进程可打开的文件描述符上限、系统级文件句柄上限、监听队列长度 somaxconn、半连接队列 tcp_max_syn_backlog、可用本地端口范围，以及 NAT 环境下的连接跟踪表容量。还有一个容易被忽略的约束是端口耗尽：网关作为客户端访问上游时，每个新建连接占用一个本地临时端口，若上游不支持长连接，高 QPS 下会很快把端口用完，表现为连接超时而不是应用报错。

上面的参数只是起点，实际值要结合压测确定。尤其是 worker_connections，它统计的是单 worker 同时打开的连接总数，包含客户端连接与上游连接，配置成 65535 并不意味着能承载六万个客户端。

协议支持与代理语义

HTTP/1.1 是网关必须首先处理好的协议。它的 keep-alive 让一个 TCP 连接承载多个请求，但请求是串行的：同一个连接上前一个响应没有结束，后一个请求只能等待。网关因此要正确设置 Connection 头，在需要断开时返回 Connection: close，并在解析响应时依据 Content-Length 或 Transfer-Encoding: chunked 判断消息边界。边界判断出错，轻则响应错位，重则把两个请求的响应拼在一起返回给客户端。

HTTP/2 引入了流与多路复用，一个 TCP 连接上可以并发多个请求，头部使用 HPACK 压缩。对网关来说，这意味着连接数大幅下降，但并发度的计量单位从“连接”变成了“流”。Envoy 通过 max_concurrent_streams 限制单连接上的并发流数量，防止某个客户端用一条连接占满上游资源。同时要注意，HTTP/2 只解决了应用层的队头阻塞，TCP 层的丢包仍会让整条连接上的所有流一起等待，所以移动网络下并不能简单地把所有流量压到一条连接上。

WebSocket 与普通 HTTP 的区别在于连接升级之后就是全双工字节流。网关必须显式支持 Upgrade 与 Connection 头，并在升级成功后停止按 HTTP 语义切分消息，改为双向透传。这里最常见的两个问题是超时与缓冲：若沿用了普通请求的读超时，空闲的 WebSocket 会被误杀；若开启了响应缓冲，低延迟的消息推送会被攒批。正确的做法是单独设置较长的空闲超时，并对这类路由关闭缓冲。

gRPC 建立在 HTTP/2 之上，使用长度前缀的消息帧，状态码放在 trailers 的 grpc-status 中，而不是 HTTP 状态行。这带来两个要求：网关必须完整支持 trailers，且不能把响应当作普通 body 缓冲后重新编码；超时则通过 grpc-timeout 头传递，网关要能够解析并转换成上游的连接与请求超时。若用 HTTP/1.1 客户端访问 gRPC 服务，需要额外的转换层，这属于另一类网关的职责，本文不展开。

代理语义上有三个容易忽略的细节。第一是 X-Forwarded-For 的追加与信任边界，网关只能信任自己直接连接的那一跳，盲目取最左侧地址会被伪造。第二是请求头大小限制，HTTP/2 的头部压缩会让超大 Cookie 的影响被低估，仍需设置总大小上限并返回 431。第三是 Expect: 100-continue，网关要么正确转发中间响应，要么在本地应答，不能沉默地等客户端把大 body 发完。

路由匹配的数据结构与复杂度

路由匹配是把请求映射到上游集群的过程，输入包括域名、路径、方法、请求头，输出是集群、超时、重试策略等路由配置。最直观的实现是把所有规则放进一个列表顺序遍历，复杂度是 O(n)，n 为规则数。规则少时没问题，但当路由随业务增长到几百上千条，且每条都带正则时，单次匹配的 CPU 成本就会进入延迟分布的长尾。

更常见的做法是按域名分桶，再在桶内用前缀树匹配路径。域名可以用后缀树或哈希表处理，支持 api.example.com 与 *.example.com 两种形式；路径用压缩前缀树，匹配复杂度与路径长度相关，而不是与规则数量相关。精确匹配、前缀匹配、正则匹配应当分层：先查精确表，再走前缀树，最后才执行正则。正则规则要限制数量并预编译，避免在请求路径上做字符串编译。

Envoy 的路由配置体现了这种分层：虚拟主机按域名匹配，路由条目支持 prefix、path、safe_regex 等匹配方式，并遵循“最具体者优先”的规则；Nginx 的 location 则有明确的优先级顺序，精确匹配 = 最高，其次是以 ^~ 开头的普通字符串前缀，再次是正则，最后才是普通前缀。理解这些顺序比背配置更重要，因为很多“路由不生效”的问题其实是优先级写错，而不是匹配表达式写错。

路由表的规模还会影响配置分发。若实现是整表重建，每次增删路由都要把完整路由推给所有实例，实例也要重建前缀树；路由上千且变更频繁时，重建本身会成为 CPU 热点。优化方向是分片与增量：按域名或租户拆分路由，只推送受影响的部分，数据平面也只替换对应的子树。

上游连接池、keep-alive 与超时分层

网关访问上游的代价主要不在转发本身，而在建立连接。一次 TCP 握手加 TLS 握手，在跨机房场景下可能消耗几十毫秒，比业务处理还长。因此连接池是高并发网关的必需品：请求到达时从池中取一条已经建立的连接，用完归还。池的核心参数有四个：最大连接数、最大空闲连接数、空闲回收时间、获取连接的最大等待时间。

连接池不是越大越好。每条连接在上游都占用一个文件描述符和一份内存，上游服务的并发处理能力也有限。池的上限应当与上游实例的承载能力匹配，并通过并发限制与排队机制保护上游。Envoy 的熔断配置提供了这层保护：max_connections 限制到上游的连接数，max_pending_requests 限制排队数，max_requests 限制并发请求数，任一指标超限就快速失败而不是继续堆积。

keep-alive 有一个经典的竞态：网关认为连接可用，把它放回池中；上游恰好在这个时刻关闭了空闲连接；网关取出这条连接发请求，收到 RST，客户端看到 502。解决办法是让网关的空闲回收时间明显小于上游的 keep-alive 超时，并在收到 RST 时对幂等请求做一次安全重试。Nginx 的 keepalive_timeout 与 upstream 的 keepalive 指令需要成对配置，Envoy 则要关注 upstream_http_protocol_options 中的空闲超时。

超时应当分层，而不是一个值管到底。至少需要区分：客户端头部读取超时、客户端 body 读取超时、路由级总超时、上游连接超时、上游响应头超时、空闲超时、重试的单次超时。分层的意义在于定位问题：若连接超时先触发，说明网络或上游监听有问题；若响应头超时先触发，说明上游处理慢；若总超时先触发，可能是重试次数过多吃掉了预算。

超时预算还应当沿调用链传递。假设入口给某个请求的总预算是 800 ms，网关转发时就不能给上游 800 ms，而要扣掉自身处理与网络开销，留出余量。gRPC 用 grpc-timeout 传递剩余时间，HTTP 生态没有统一标准，常见做法是自定义 X-Request-Deadline 或在网关侧统一压短。否则入口早已超时，下游还在消耗资源。

重试必须与超时、幂等一起设计。网关层只应对连接失败、明确的 503、以及可判定安全的幂等请求做重试，并且要设置重试预算，例如重试请求不超过总请求的 10%。否则上游刚出现抖动，网关的重试会把流量放大，形成雪崩。Envoy 的 retry_budget 与 retry_on 就是为此存在的，配置时要显式列出可重试的条件，而不是笼统地重试所有 5xx。

限流熔断在网关层的位置

限流算法的细节已有专文讨论，这里只谈位置。网关位于流量入口，能把无效请求挡在业务之前，因此适合做三类限流：按来源 IP 或连接的粗粒度限流，用于抵御扫描与滥用；按租户或 API Key 的配额限流，用于商业上的用量控制；按路由的并发限制，用于保护单个上游集群。这三类都属于“入口保护”，特点是判断成本低、拒绝得早。

不适合放在网关的是细粒度的业务限流。例如“每个用户每秒最多下单五次”，这需要业务上下文，且往往要与库存、风控联动。把它塞进网关会导致网关依赖业务存储，破坏前面说的职责边界。更合理的做法是网关做一层粗筛，业务侧做精确控制，两层使用不同的 key 与阈值，避免互相干扰。

熔断在网关层更适合以“实例级摘除”的形式出现。当某个上游实例连续返回连接失败或 5xx，网关暂时把它移出负载均衡列表，过一段时间再放回试探。Envoy 的异常点检测提供了这种能力，按连续错误数或错误率触发，配合 max_ejection_percent 防止一次性摘掉过多实例。它与应用内的熔断器不是替代关系：网关摘除的是“实例不健康”，应用熔断的是“依赖整体不可用”。

放置限流时还要决定失败策略。限流组件自身故障时，是放行还是拒绝？对面向公网的边缘网关，通常选择放行并告警，因为误拒正常用户的代价更高；对保护核心数据库的内部网关，则应选择拒绝，避免故障扩散。这个选择要写进设计文档，并在演练中验证。

最后是反馈方式。被限流的请求应返回 429，并尽量带上 Retry-After，让客户端知道多久后可以重试。若网关直接断开连接或返回 503，客户端往往会立即重试，反而加剧拥塞。指标上要区分“限流拒绝数”与“上游错误数”，两者的告警阈值和处理路径完全不同。

动态配置、灰度与优雅重启

网关的配置变更频率往往被低估。新增一条路由、调整一个超时、摘除一个实例，在业务团队看来都是日常操作，但对网关来说都是线上变更。若每次都要重启进程，长连接会被成批切断，发布窗口只能安排在凌晨。因此动态配置不是锦上添花，而是高并发网关的基本能力。

配置下发有三种常见形态。第一种是文件监听，用 inotify 感知配置文件变化，解析成功后替换内存快照。第二种是轮询拉取，实例每隔几秒向配置中心请求版本号，有变化才拉全量。第三种是长连接推送，控制平面与每个实例保持一条流，变更实时下发，Envoy 的 xDS 就属于这一类。前两种实现简单但有延迟，第三种实时性好，却要处理断线重连与消息乱序。

无论哪种形态，都要遵循“校验、编译、切换、确认”四步。校验阶段检查引用是否存在，例如路由指向的集群是否已定义、证书是否过期；编译阶段把文本配置转换成不可变对象，预计算匹配结构；切换阶段替换原子指针；确认阶段向控制平面回报版本。任何一步失败都应保留旧快照，并输出明确的错误原因，而不是让实例停留在半新半旧的状态。

灰度发布是降低配置风险的关键。常见做法有三种：按实例比例下发，先推 1% 的实例观察指标；按请求特征分流，用请求头或用户 ID 哈希决定走新路由还是旧路由；按流量比例分流，在同一实例内让部分请求命中新集群。第一种最容易实现，适合配置结构变化；后两种更精细，但要求数据平面同时持有新旧两份配置，内存与匹配成本都会上升。

配置推送风暴是动态化的副作用。控制平面一次发布，若几千个实例同时重连、同时拉全量、同时回 ACK，控制平面与网络都会被打满。缓解手段包括：推送前合并去抖，多次变更只发最终版本；为实例的重连与拉取加入随机抖动；优先使用增量协议；对 ACK 限速。评估方案时，应把“一次全量发布需要多久”作为硬指标，而不是只看单次下发是否成功。

优雅重启与连接 draining

即使有了动态配置，代码升级仍然需要重启进程。优雅重启的目标是：新连接由新进程处理，老连接上的请求处理完再退出，客户端不出现连接重置。实现上分为停机与交接两种思路。

停机式优雅退出适用于实例可以短暂下线的场景。步骤是：先把实例从负载均衡中摘除，或让健康检查返回失败；等待一个摘除传播期，通常几秒到十几秒，确保调用方不再新建连接；然后停止接受新连接，通知现有连接进入 draining；等待在途请求完成或到达超时上限；最后退出。Go 的标准库提供了直接支持：

Shutdown 会关闭监听器并等待活跃请求结束，但它不会主动结束 keep-alive 空闲连接上的等待，也不会处理 WebSocket 这类长连接。因此还需要在 draining 期间给响应加上 Connection: close，并对长连接路由设置单独的排空策略，例如先发送关闭帧再等待客户端断开。

HTTP/2 的排空要靠 GOAWAY 帧。网关向客户端发送 GOAWAY，告知最后一个可处理的流编号，客户端之后不会再在该连接上新建流，已经在途的流继续完成。只发一次 GOAWAY 不够，因为通知到达前客户端可能已经发出新请求，成熟实现会间隔发送两次，第二次把流编号降到实际处理进度。Envoy 的 draining 序列大致如此，自研网关至少要做到“先 GOAWAY、再等待、最后关闭”。

交接式重启用于不能中断的场景。新进程启动后从老进程继承监听 socket，老进程停止 accept 但继续服务已有连接，等连接排空后再退出。Nginx 的二进制升级通过 USR2 信号与 pid 文件完成，Envoy 也支持热重启。这种方式对客户端透明，代价是运维复杂度更高；多数团队用停机式重启配合摘流已经足够。

无论哪种方式，都要给 draining 设置上限。若某个连接因为客户端不读响应而永久占用，排空就永远不会结束。上限到达后应强制关闭并记录日志，否则一次发布可能卡住整个集群的升级。

可观测性、容量与多级部署

访问日志至少要回答三个问题：走了哪条路由、打到哪个上游实例、时间花在哪里。因此除状态码与总耗时外，还要记录上游连接、首字节与响应完成的分段耗时。日志必须采样，否则高 QPS 下写盘本身会成为瓶颈。指标侧按路由、状态码与协议拆分 QPS 和延迟分位数，同时暴露连接池的活跃数、排队数与溢出数，这些数字比 CPU 更早预警。

链路追踪最好在网关完成注入：请求已带 traceparent 或 B3 头就透传，没有就生成，并在入口做一次采样决策后向下传递。网关不参与业务 span，但必须记录自己这一段的路由与上游耗时，否则跨服务排障时链路会在入口断掉。

容量评估先用利特尔法则估算并发：并发约等于 QPS 乘以平均延迟，再按峰值留出三到五成余量。压测要区分短连接与长连接、带 TLS 与不带 TLS，它们消耗的资源完全不同。多级部署时，边缘网关与内部网关应各自只做一次日志与限流，避免同一请求被重复计数；边缘侧重安全与配额，内部侧重实例保护与灰度。

常见坑

高并发下的问题往往不是功能错误，而是资源与边界没有被约束。大 body 不限制会打爆内存，应按路由设置上限或流式转发；慢客户端长期占用连接，需要头部与 body 超时；头部膨胀会撑大缓冲并触发 431；DNS 缓存过久会把流量压到已下线实例，需按 TTL 刷新并保留兜底地址；连接池打满表现为排队延迟飙升，要盯住 pending 数；配置推送风暴则靠合并、抖动与增量下发化解。

小结

网关的高并发能力来自一系列取舍：连接模型决定上限，不可变快照让配置切换无锁，分层超时与连接池保护上游，优雅重启保证变更不中断。设计时先算清连接数、请求速率与内存预算，再把限流、灰度与观测放在正确的位置，最后用压测验证每一个假设。
