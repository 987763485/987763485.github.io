OpenTelemetry 标准实践

本文属于《Docker 与 Kubernetes》第 38/51 篇
上一篇系列目录下一篇

到 2021 年，可观测性领域的工具已经足够多，麻烦反而变成了选择太多：链路追踪用一套 SDK，指标用另一套 SDK，日志再单独接一遍，每换一个后端就要改一次代码。本文讨论 OpenTelemetry（下文简称 OTel）试图解决什么问题，它在 2021 年的能力边界在哪里，以及怎样在 Go 服务里把它接进来而不至于踩坑。

需要先说明的是，OTel 在 2021 年并不是一个已经全部完工的标准。链路追踪相对成熟，指标还在推进，日志刚刚起步。把这三件事的成熟度混为一谈，是很多接入方案一开始就跑偏的原因。

为什么需要 OpenTelemetry

在 OTel 出现之前，可观测性代码的写法基本由后端厂商决定。用 Jaeger 就引入 Jaeger 的客户端，用 Zipkin 就用 Zipkin 的埋点库，两套 API 的 span 模型、标签命名、上下文传递方式都不一样。业务代码里散落着这些库的调用，一旦要换后端，往往要重写埋点，甚至重新梳理整条调用链。更麻烦的是同一个进程里可能同时接了两三个系统，重复上报、概念冲突，维护成本随时间上升。

社区曾经有两条并行的努力：OpenTracing 只定义追踪 API，不定义 SDK 与实现；OpenCensus 由 Google 主导，API、SDK、数据导出都自带，还包含指标。两者目标重叠却互不兼容，用户被迫二选一。OTel 的做法是把两条路线合并：吸收 OpenTracing 的 API 抽象思路，也吸收 OpenCensus 的完整实现与指标能力，形成一套厂商中立的标准。对使用者来说，最直接的好处是埋点代码只依赖 OTel 的接口，后端换成谁由配置决定。

厂商中立之外，OTel 还统一了数据模型。span 有明确的 name、kind、status、attributes、events、links，指标有明确的 instrument 类型与聚合方式，导出协议统一为 OTLP。统一模型的价值不在协议本身，而在于不同语言的 SDK、不同后端、Collector 之间的翻译有了共同语言，跨团队讨论问题时不必先解释各自用的是什么。

分层与三种信号

理解 OTel 的关键是先分清它的层次，很多人把这几层混在一起，于是产生了“装了 SDK 为什么还要 Collector”之类的疑问。

flowchart TD
    A[业务代码] --> B[API 层]
    B --> C[SDK 层]
    C --> D[导出器]
    D --> E[Collector]
    E --> F[后端: Jaeger / Prometheus 等]

API 层只描述“要记录什么”，比如开始一个 span、给计数器加一，它不关心数据最终去哪，也不做采样和批量上报。SDK 层是具体实现，负责采样决策、上下文管理、批量导出、资源合并。导出器把 SDK 产出的数据编码成某种协议发出去，OTLP 是原生选择，也可以通过桥接适配旧协议。Collector 是独立的进程，负责接收、处理和转发，让应用侧不必关心后端地址与格式。

同一套分层之下有三种信号，它们在 2021 年的完成度差异很大，这一点必须写清楚，否则很容易做出错误的选型。trace 是最成熟的：API 与 SDK 在多语言中已经稳定，语义约定、上下文传播、Collector 链路都已可用，生产环境可以直接依赖。metrics 当时仍在推进中，API 已经定型并提供了计数器、直方图等 instrument，SDK 也在快速迭代，但部分语言的实现完整度不一，指标导出与聚合的细节还在调整，适合试点而不宜假定一切都已稳定。logs 则处于早期，主要工作是定义日志的数据模型以及和 trace 的关联方式，配套的日志 SDK 与桥接方案尚不完善；这一时期的普遍做法仍然是继续用现有的日志库输出，再通过采集端补上 trace id 等字段，而不是等待 OTel 的日志 SDK。

因此，2021 年做落地规划时比较稳妥的顺序是：先把 trace 打透，让上下文和语义约定统一；再用 metrics 做试点，从少数核心服务开始；日志先解决关联问题，不急于替换现有日志栈。反过来，如果一上来就宣称“全套 OTel 可观测性”，实施时多半会在指标和日志的细节上返工。

Provider、Resource 与 Span

在 OTel 的模型里，Provider 是资源的入口。TracerProvider 负责创建 Tracer，MeterProvider 负责创建 Meter，它们相当于 SDK 的门面，一个进程通常各建一个，在启动阶段初始化，随后通过全局注册交给业务代码使用。Provider 持有采样策略、导出器、资源等配置，因此不要在请求路径上反复创建 Provider，那样既浪费连接又会丢失状态。

Resource 描述的是“谁产生的数据”，比如服务名、实例标识、部署环境、主机名。它随每条 span 和每个指标一起上报，是后端做筛选和聚合的基础。Resource 应当在 Provider 初始化时确定，而不是每次打点时手工塞进属性里。很多团队在后端看不到服务维度的视图，根源就是 service.name 没设置或各服务写得五花八门。

Span 表示一次操作，核心字段包括名称、开始与结束时间、状态、属性以及事件。属性是键值对，用来记录业务与协议信息，例如 HTTP 方法、状态码、数据库语句类型；事件用于记录操作过程中的离散时刻，比如重试、缓存未命中。属性的键应尽量遵循语义约定，名称要稳定且可枚举，不要拼接用户 ID、请求参数这类高基数值。

上下文传播与采样

跨进程追踪能成立，靠的是上下文传播。服务在处理请求时把当前 span 的标识写进请求头，下游读出后作为父上下文继续创建 span，整条链路才连得起来。OTel 默认采用 W3C Trace Context 规范，请求头是 traceparent，其中包含 trace id、parent span id 和采样标记；tracestate 用来携带厂商相关的附加状态。相比早期各家用自定义头部的做法，统一到 W3C 标准之后，跨语言、跨网关的链路拼接才真正可行。

除了追踪上下文，OTel 还支持 baggage。baggage 是一组随请求传播的键值对，不参与采样决策，也不会自动变成 span 属性，适合传递租户标识、灰度标记这类需要在整条链路上可见的轻量信息。baggage 会被序列化进请求头，因此必须控制体积，不要放敏感信息，也不要把它当成配置中心使用。

采样决定哪些 trace 被记录下来。头部采样在 trace 开始的瞬间做决定，实现简单、开销极低，常见策略是按比例采样或基于父级采样结果继承。它的缺陷是“先决定后观察”：无法根据链路中是否发生错误、耗时是否超标来补采。尾部采样则把决策推迟到整条 trace 结束后，由 Collector 根据完整数据判断是否保留，能保证错误链路不丢，但需要缓冲数据、集中部署，成本和复杂度都更高。2021 年尾部采样在 Collector 中已有对应处理器，本文只把它当作一种思路：先想清楚要保留什么样的 trace，再决定采样放在哪一层。

还要注意采样与指标的关系。span 被采样丢弃不等于指标失真，因为指标来自独立的聚合路径；但如果用“span 数量”去推算请求量，采样率一变结论就错了。这类混淆在排查问题时很常见。

Collector 的组成与部署形态

Collector 是 OTel 里最像基础设施的部分。它由三类组件构成：receiver 负责接收数据，processor 负责在链路中修改、过滤、批量处理数据，exporter 负责把数据发给后端。三者通过 pipeline 串联，每种信号各有一条 pipeline。常见的 processor 包括批处理、内存限流、属性增删、尾部采样；常见的 exporter 包括 OTLP、Jaeger、Prometheus 等。

配置里最值得强调的是 memory_limiter 要放在 batch 之前。批处理会在内存中堆积数据，如果没有前置的限流保护，后端变慢时 Collector 很容易被内存打爆，进而影响同机的其他进程。

部署形态通常有两种。agent 形态把 Collector 部署在每台主机或每个 Pod 上，应用只往本地发数据，由 agent 统一做批处理和打标签，网络路径短、故障域小，适合主机数量多、语言杂的环境。gateway 形态则集中部署一组 Collector，应用直接或经由 agent 发到网关，便于统一做采样、脱敏和路由，但多了一跳网络，容量规划与高可用必须提前考虑。实践中常见的是两层组合：agent 负责就近收敛，gateway 负责统一策略。

语义约定与后端对接

语义约定是 OTel 最容易被低估的部分。它规定了常见操作应该用哪些属性名，例如 HTTP 请求使用 http.method、http.status_code、http.route，数据库调用使用 db.system、db.statement、db.operation，RPC 使用 rpc.system、rpc.service、rpc.method。遵循约定的好处是后端和 Collector 能识别这些字段，自动生成接口维度的统计与拓扑，而不需要为每个团队定制解析规则。

需要提醒的是，2021 年的语义约定仍在演进，属性名在不同版本之间发生过调整，跨团队统一时应固定一个版本并在文档中写明，升级时当成一次小的不兼容变更来处理。自造属性并非禁止，但应加前缀区分，且避免与约定字段语义冲突。

与既有后端的对接并不复杂。追踪数据经 OTLP 送入 Collector 后，可由 Jaeger exporter 转发给 Jaeger，也可导出为 Zipkin 格式，让原有查询界面继续可用。指标方面，Prometheus 生态当时主要采用拉取模型，常见做法是让 Collector 暴露一个 Prometheus 格式的端点，由 Prometheus 定期抓取，从而把推模型与拉模型衔接起来。这样既保留了 OTel 的统一采集，也不必立刻替换现有的监控与告警体系。

开销、迁移与常见坑

先谈开销，避免夸大也避免低估。单个 span 的创建与属性写入是内存操作，成本很低；真正的开销在序列化与网络发送，因此批处理导出是默认选择，绝不能每条 span 同步发一次。开启全量采集时，高 QPS 服务的追踪数据量可能远超预期，带宽和存储往往先于 CPU 成为瓶颈，这也是采样必须存在的原因。Collector 侧的主要消耗是内存与 CPU，批处理、属性处理、尾部采样都会放大占用，容量规划时应当按峰值流量留出余量。

迁移策略上，比较务实的做法是先在入口服务接入 OTel，用桥接方式把已有的追踪库数据转成 OTel 格式，保证新旧链路能拼在一起；再逐服务替换埋点，最后统一切换到 Collector 转发。指标和日志不要同步大改，先解决追踪链路的完整性，收益最直观，风险也最可控。

落地过程中反复出现的坑大致有五类。第一是上下文丢失，典型场景是异步任务、线程池、消息消费和自建 HTTP 客户端没有把 context 带过去，表现为链路断成两截；解决方式是检查所有跨边界的调用，确保 context 一路透传。第二是 span 过多，在循环里为每条记录开 span，或在已经自动埋点的框架上再手工包一层，都会让链路臃肿、存储暴涨；原则是 span 对应有意义的操作，而不是对应每一次函数调用。第三是属性基数爆炸，把用户 ID、URL 全路径、订单号写进属性，会让后端索引膨胀、查询变慢；这类信息应放进日志或事件，属性只保留可枚举的低基数字段。第四是 Collector 变成单点，所有服务都指向一个没有副本的 Collector，它一重启整条观测链路就中断；agent 与 gateway 都应有多副本与本地缓冲。第五是采样后指标失真，用被采样的 trace 数量去推算请求量或错误率，结论会随采样率漂移；流量类结论应来自指标，追踪只用于定位个例。

小结

OTel 在 2021 年的价值，主要是把埋点从“绑定某个后端”变成“依赖一套中立接口”，并用统一的数据模型和 Collector 把采集与存储解耦。落地时要认清三种信号的成熟度差异：trace 可以放心用在生产，metrics 适合试点，logs 还处在定义模型的阶段。工程上抓住几件事就够：Provider 与 Resource 在启动时初始化，context 全程透传，属性遵循语义约定且保持低基数，批处理导出加 Collector 多副本，采样策略与指标口径分开考虑。把这几条做扎实，后面无论换哪个后端，都不必再重写一遍埋点。
