微服务可观测性建设

本文属于《Go 微服务架构》第 33/35 篇
上一篇系列目录下一篇

服务拆成几十个之后，一次请求会穿过网关、若干业务服务、缓存与数据库，任何一环抖动，用户看到的都只是一个失败页面。此时只看单机 CPU 和一张总览大屏，往往既说不清故障范围，也找不到根因。

本文从微服务排障的实际困难出发，讨论日志、指标、追踪三者的分工，统一标识与上下文传播，采集方式与数据关联，以及 SLI/SLO 和告警思路的转变。读完本文，你可以为团队勾画一条可落地的可观测性建设路径，而不是先买一套大屏。

排障难在哪里

单体应用时代，问题大多落在一台机器、一个进程里，登录服务器看日志、看线程栈，常常就能定位。微服务把一次调用拆成多段，排障的困难集中在四个方面。

第一，调用链变长。一个下单请求要经过网关、订单、库存、支付、消息队列等多个环节，用户看到的只是“下单失败”。失败可能是网关超时、库存服务变慢、数据库锁等待，也可能是某次重试放大了流量。没有链路数据，工程师只能按经验逐段排查。

第二，实例多且生命周期短。同一服务可能有多份副本，容器编排系统会随时扩缩容、迁移或替换实例。等我们登录机器准备查看现场，容器可能已经被销毁，日志也随实例一起消失。排障所依赖的“现场”必须被提前、持续地记录下来。

第三，日志分散且格式不一。每个服务写自己的文件或标准输出，字段命名、时间格式、级别定义各不相同，机器时钟还可能有偏差。想还原一次请求，靠“时间相近”去拼日志并不可靠，必须有一个贯穿全链路的标识。

第四，发布频繁。持续交付让一天内多次上线成为常态，故障与变更之间往往存在相关性，但变更记录、实例版本和请求数据分散在不同系统里。若不能把版本、实例和请求放到同一时间轴上，就很难判断问题是否由某次发布引入。

这些困难不是靠更努力地看日志能解决的。信息其实一直在产生，问题在于没有按“一次请求”和“一个时间段”组织起来。

可观测性与监控的区别

监控解决的是“已知问题是否发生”。我们预先定义指标和阈值，系统偏离预期就告警。它擅长回答“机器是否宕机”“磁盘是否将满”“错误率是否升高”，前提是事先知道要观察什么。

可观测性来自控制论，指系统的内部状态能否由外部输出推断。放到软件系统里，它强调从日志、指标、追踪等遥测数据出发，回答事先没有预料到的问题：为什么只有某个租户的请求变慢？为什么发布后某一类商品下单失败？这些问题在建设之初往往列不出来，只能依靠数据本身的维度和上下文去追问。

两者不是替代关系。监控是可观测性的一部分，是已经沉淀下来、可以自动执行的检查；可观测性则要求数据保留足够的细节和关联能力，允许工程师临时提出新问题。只做监控，团队容易陷入“告警没响就是没问题”的错觉；只谈可观测性却不建立基本监控，又会连系统是否活着都说不清楚。

一个实用的判断标准是：排障时能否不改代码、不上机器，仅沿着已有数据把范围从“整体异常”缩小到“某个服务、某个接口、某类请求”。如果做不到，说明可观测性建设还有明显缺口。

三种数据的分工

可观测性不等于把日志全部收上来。日志、指标、追踪回答的问题不同，成本结构也不同，混在一起谈，容易做成昂贵的日志仓库。

指标是按时间聚合的数值，如请求数、错误数、延迟分布和队列长度。它写入成本低、查询快，适合看趋势、设阈值和做容量规划；聚合之后丢失个体信息，只能指出“哪里不对”，难以说明“哪一次请求不对”。

日志是离散事件的详细记录，带时间戳和结构化字段，适合看参数、错误码和依赖返回。它信息最全，但量大、基数高，缺少统一格式时，检索成本会迅速上升。

追踪记录一次请求经过的服务与跨度，把调用关系、耗时和状态串起来，适合回答“慢在哪一跳”“谁调用了谁”。受采样影响，它通常只保留部分请求，更适合定位模式，而不是审计每一笔业务。

维度 指标 日志 追踪
回答的问题 是否异常、趋势如何 具体发生了什么 请求走了哪条路径
数据形态 聚合数值 离散事件 调用树与跨度
典型用途 告警、容量 定位细节、审计 链路分析、依赖梳理

三者的关系可以概括为：指标发现异常，追踪缩小范围，日志给出证据。只建其中一种，排障时总会缺一块。

统一标识与上下文传播

要让三类数据互相对上，前提是有一个贯穿请求的标识。最常见的是 trace id：入口服务生成或接受上游传入，之后每个服务、每次下游调用都携带同一个值。request id 常指单次 HTTP 请求的标识，如果每一跳都重新生成，它只能定位一跳，无法串起全链路。建设时应明确两者语义。

还应在上下文里保留租户 id、用户 id、业务单号等标识，它们能直接回答“影响哪些客户”“哪笔订单出问题”。但这些字段基数很高，不适合作为指标标签，否则会造成时间序列膨胀，放在日志和追踪属性里更合适。

传播是工程上的难点。HTTP 调用要写入请求头，gRPC 调用要放入 metadata，消息队列要把标识写进消息头，异步任务和线程池还要保证上下文不丢失。任何一环漏传，链路就会在这里断开。W3C Trace Context 这类规范已经约定了请求头格式，采用统一规范比自造字段更容易与网关、服务网格和第三方组件对接。

采集方式与资源开销

采集方式大致有三类。SDK 集成在应用里，语义最丰富，能拿到方法、参数和错误堆栈，也最容易保证上下文传播，代价是与语言和框架绑定，升级要改代码、重新发布。宿主机 agent 收集日志文件、系统指标和应用暴露的指标端点，侵入小、运维统一，但看不到应用内部语义。sidecar 与应用同生命周期部署，常见于服务网格，能代理流量、自动记录耗时与状态码，缺点是多一跳网络开销和资源占用，对业务逻辑仍然无知。

三类方式可以组合：基础指标和日志交给 agent，关键服务接入 SDK，网格内由 sidecar 提供网络层数据。选择时算三笔账：CPU 与内存、网络与存储、故障时的排查成本。采集端本身也可能成为故障源，必须限制资源，并保证采集失败不影响主流程。

数据关联决定成败。日志必须带 trace id，指标可以通过 exemplar 关联到具体追踪，细节不在本文展开。三套系统各自为政，工程师仍要在几个界面之间手工拼凑，投入越多越显得笨重。

SLI、SLO 与告警思路

可观测性最终要落到“系统是否满足用户预期”。SLI 是对用户体验的量化，常见的有可用性、错误率、延迟和业务成功率。定义时要写清分子分母，例如“成功返回的请求数除以有效请求总数”，并明确哪些请求算有效、哪些状态码算成功。

SLO 是给 SLI 设定的目标，例如“一个月内可用性不低于某个比例”。目标不应追求满分，越接近满分，投入的成本越不成比例。SLO 与错误预算配套：目标允许的失败额度就是预算，预算消耗过快说明稳定性恶化，应优先修复；预算充足时，团队可以更积极地发布。稳定性由此从口号变成可权衡的资源。

告警思路也要改变。传统告警围绕资源阈值：CPU、内存、磁盘剩余空间。资源指标适合诊断和容量规划，不适合作为主要的用户侧告警，因为资源高不等于用户受影响，资源正常也可能已经大量业务失败。更合理的做法是以用户症状为主：错误率、延迟、成功率等 SLI 异常时才呼叫值班，资源指标作为辅助信息附在告警里。这样能减少无效告警，也让值班人员第一眼看到影响范围。

工具选型与建设路径

选型容易变成厂商对比，先明确约束更有用。可以看四个维度：部署形态（自建或托管）、成本（存储、计算、跨机房流量）、查询能力（高基数检索、日志与追踪关联）、可迁移性（是否依赖专有 agent 或查询语言）。自建自由度高、长期成本可控，但需要专人维护；托管省心，数据出域和费用增长则要提前评估。无论选哪种，都应采用开放协议和标准字段，避免埋点被某一家产品绑死。

路径建议分三步：先统一日志，约定结构化格式，强制包含时间、级别、服务名、实例和 trace id；再补追踪，在入口和关键依赖上埋点，保证上下文跨 HTTP、gRPC 和消息队列传播；最后完善指标与告警，从用户视角定义少量核心 SLI，建立 SLO 闭环。日志与追踪见效快，指标和告警则依赖前面统一的命名与标识。反过来，先买大屏、先堆仪表盘，往往只能看不能查。

组织上要明确服务归属：每个服务有负责团队，告警发给能改动它的人，而不是统一丢给运维；值班要轮换、有升级路径和操作手册；故障后复盘，把缺失的埋点、失效的告警转成待办。责任边界不清，再好的平台也会退化成展示屏。

常见坑

第一，埋点不一致。各团队自定义字段名和错误码，服务名一会儿用下划线一会儿用短横线，数据无法聚合。应在基础库提供统一封装，用模板约束新服务。

第二，采样后无法排障。为省钱把追踪采样压得很低，出错时恰好没有样本。应优先保留错误请求和慢请求，并按业务重要性分层采样；策略要写进文档。

第三，日志基数爆炸。把用户 id、订单号、完整 URL 参数直接写进日志，甚至当作指标标签，存储和查询成本会失控。高基数字段留在日志正文或追踪属性中，指标标签只保留有限枚举。

第四，只建大屏不闭环。面板漂亮，却没有告警、负责人和处置流程，故障时没人看。建设应以缩短发现和定位时间为验收标准，而不是以接入多少数据源为标准。

小结

微服务排障难，本质是请求被拆散、实例被替换、数据被分隔。可观测性建设要让工程师用数据还原一次请求的全貌：指标看趋势与告警，日志看细节，追踪看链路，三者靠统一的 trace id 和上下文传播关联。采集方式要在侵入性、语义丰富度和资源开销之间取舍，SLI/SLO 则把稳定性变成可权衡的目标。落地时先统一日志与追踪，再补指标与告警，并明确服务归属与值班责任；避开埋点不一致、采样过度、日志基数失控和只建大屏这几个坑，建设才算闭环。
