分布式定时任务方案

本文属于《Go 微服务架构》第 20/35 篇
上一篇系列目录下一篇

分布式定时任务看起来只是把一段代码交给 cron 触发，但在多实例部署的环境里，同一份任务会被每个实例各执行一次。本文从单机定时任务的三个老问题讲起，梳理分布式调度真正要解决的几件事，再对比 Quartz 集群、xxl-job、ElasticJob 与 K8s CronJob 的取舍。

后面会顺带聊到时间轮和延迟队列的适用边界、分片广播、执行日志与告警，以及迁移和灰度时容易踩的坑。

单机定时任务的老问题

最早的写法很直接：在应用进程里起一个线程，睡到下一个整点再干活。Java 里是 @Scheduled(cron = "0 0 2 * * ?")，Go 里是 time.NewTicker 配一个循环，运维层面则常常直接在机器上写一行 crontab。单实例、单机部署时，这套东西简单可靠，出了问题看一眼日志就能定位。麻烦出现在服务开始多副本部署之后。

重复执行

同一个镜像起三份，三份都会在凌晨两点醒来，于是同一条对账任务被跑了三次。有人用 Redis 的 SET NX 加一把锁来挡，看似解决了，实际上又引入一串新问题：锁的过期时间设多长？任务执行时间超过周期怎么办？持锁的实例在任务中途挂掉，锁到期后另一个实例接手，前半段已经写入的数据怎么算？分布式锁只是把“谁执行”这件事从随机变成了竞争，并没有回答“执行到一半失败了怎么办”。

单点与扩缩容

任务代码和应用代码放在一起，生命周期就绑死了。发布时进程重启，正在跑的任务被直接杀掉；缩容时被摘掉的恰好是持有任务的实例，任务就凭空消失一段时间；扩容时又多出几个实例来抢同一件事。更隐蔽的是资源互相干扰：一个遍历百万行数据的导出任务，会把 Web 进程的 CPU 和连接池一起拖垮。

分布式调度要解决的几件事

把定时任务从应用里拆出来，本质上是在解决一组相互关联的问题。下图是一个常见的分层结构：调度层负责决定“什么时候、由谁执行”，执行层只负责“把这件事做完”。

flowchart TD
    A[调度中心] --> B[任务元数据存储]
    A --> C[选主与分片]
    C --> D[执行器节点 1]
    C --> E[执行器节点 2]
    D --> F[执行日志]
    E --> F
    F --> G[告警]

选主与分片

选主解决的是“同一时刻只有一个调度者”的问题，避免多个调度中心各自算出一份触发时间。分片解决的是“一件事能不能拆开并行做”的问题：一个扫描全表的任务，可以按用户 ID 取模切成 8 片，交给 8 个执行器同时跑。选主通常借助数据库行锁、ZooKeeper 临时节点或 etcd 租约来实现，核心要求是租约要能续期，持有者失联后能尽快被替换。

任务持久化

任务定义不能只存在于代码注解里。把它存进数据库之后，才能做到运行时改 Cron、临时禁用、手动触发、查看上次执行结果。表结构不需要复杂，关键字段是任务名、Cron 表达式、执行参数、路由策略、超时时间、失败重试次数和状态。

触发与执行分离

调度中心只做两件事：算出该触发的时刻，把触发请求发给执行器；执行器收到请求后异步执行，并把结果回写。分离之后，调度中心可以很轻，一台机器就能扛住大量任务的触发；执行器可以按任务类型单独扩容，重任务不再影响在线业务。代价是多了一次网络调用，必须考虑超时、重试和重复投递。

失败重试与错过触发

重试要区分两类失败。网络抖动、下游临时不可用属于可重试的，按固定间隔退避重试两三次即可；参数错误、数据不存在属于不可重试的，重试只会放大问题。重试次数和退避策略应该跟着任务走，而不是全局一个值。

错过触发是更容易被忽略的一项。调度中心重启、执行器全部下线、或者机器时间被校准，都会导致某个触发点没有发生。此时要明确策略：是补跑一次，还是直接跳过等下一个周期。对账类任务通常要补跑，且要记录补跑原因；统计类任务往往跳过更好，避免和历史数据重复叠加。

幂等是最后一道防线

无论选主多严谨、重试多克制，重复执行都无法彻底消除。执行器超时但任务实际成功、调度中心重发、人工手动触发，都会造成重复。因此每个任务在实现时都要自带幂等语义：按业务主键去重、用状态机卡住非法流转、或者让写操作本身可重入。通用的幂等方案不再展开。

主流方案对比

能落地的方案不多，思路却分成几派。下面按协调机制来区分，而不是按功能列表堆砌。

Quartz 集群：靠数据库行锁

Quartz 把触发器、任务和锁状态都存进数据库，集群中的每个节点通过 SELECT ... FOR UPDATE 抢占待触发的触发器，抢到就执行，执行完更新下次触发时间。优点是只依赖一个数据库，接入成本低，Java 生态里认知度高。缺点是触发信息的读写全部压在数据库上，任务量一大，锁竞争就很明显；节点故障后的恢复依赖库中状态，容易出现“触发器被锁住却无人处理”的情况。

xxl-job：调度中心加执行器

xxl-job 把职责切得很清楚：调度中心负责 Cron 解析、触发和日志展示，执行器以独立的进程或服务形式注册上来，通过 HTTP 接收触发请求。路由策略可以选择轮询、故障转移、一致性哈希、分片广播等。它自带管理界面，改 Cron、看日志、手动触发都比较顺手，对中小团队很友好。需要注意的是调度中心本身要做高可用，否则它就成了新的单点；另外执行器与调度中心之间的网络要稳定，超时设置要合理。

ElasticJob：ZooKeeper 协调与分片

ElasticJob 把协调工作交给 ZooKeeper，作业实例通过临时节点注册，由 ZK 完成选主和分片分配。它的分片模型比较自然：一个作业声明分成 N 片，每个实例领取若干片，实例增减时自动再平衡。适合“数据可以按维度切开”的批量处理场景。代价是多了一套 ZK 依赖，运维复杂度上升，作业的配置与运维界面也不如带控制台的方案直观。

K8s CronJob：只解决触发

CronJob 只是让 Kubernetes 按 Cron 创建 Job，再由 Job 拉起 Pod 执行。它天然解决了“只触发一次”和“执行环境隔离”，但不管分片，不管任务元数据管理，也不提供执行历史和告警。它适合那种一次性、无状态、跑完即走的批处理，比如每天导出一次报表；把它当作通用调度平台来用，往往要自己补很多外围能力。

时间轮与延迟队列

Cron 表达的是“日历上的某个时刻”，而业务里还有大量“相对于现在过多久”的需求：订单创建 30 分钟未支付就关闭、优惠券到期前 24 小时提醒。用 Cron 表达这些需求很别扭，只能靠每分钟扫一次表。

时间轮把定时器按槽位挂在环形数组上，指针每走一格就处理该槽内的任务，插入和删除都是常数时间，适合单机内海量短延时定时器。Netty 的 HashedWheelTimer 就是这种结构，Kafka 内部也用它处理请求超时。它的问题是不持久化，进程重启后定时器全部丢失，所以只适合可以重建的临时性超时。

延迟队列把“到点再做”落到中间件上。常见做法是用 Redis 的有序集合，成员是任务标识，分值是到期时间戳，另起一个消费者轮询取出分值小于当前时间的成员；也有团队用消息队列的延迟级别或死信队列来实现。它的优点是跨实例、可持久化；缺点是精度受轮询间隔限制，取任务与删任务不是原子操作，多消费者并发时要用 ZREM 的返回值判定归属。

选择上有个简单判断：任务是“每天几点做”就用调度框架，是“多少秒后做一次”就用延迟队列；两者都需要在消费侧做幂等，因为延迟消息同样可能重复投递。

分片广播与数据分片

分片广播是分布式调度里最有价值的能力之一。调度中心把同一次触发发给所有执行器，带上分片总数与序号，执行器只处理属于自己的数据。

这里有个容易踩的坑：分片总数不要跟着实例数走。如果分片数等于当前实例数，明天扩容到 6 个实例，分片语义就从“按 4 取模”变成“按 6 取模”，同一批数据可能被两个不同实例各处理一次。稳妥的做法是把分片数固定成一个较大的值（比如 16），实例数变化只影响每个实例领到几片，不影响取模规则。

分片还会带来数据倾斜：按用户 ID 取模通常均匀，按地区、按商户取模就未必。执行耗时要按分片打点，某个分片总是最后跑完，就要考虑换分片键或再切一层。

任务依赖与工作流

当任务从几个变成几十个，就会出现先后关系：明细同步完成后才能汇总，汇总完成后才能推送报表。最原始的做法是把下游任务的触发时间往后挪半小时，靠“猜”来保证顺序，一旦上游延迟就全线错乱。

更可靠的方式是把依赖显式表达成有向无环图：上游执行成功后发出完成事件，下游收到事件再启动。实现上可以简单到一张任务状态表加轮询，也可以用现成的工作流引擎。要额外处理三件事：检测环依赖，避免图上出现死循环；定义上游失败时下游是阻塞还是跳过；限制同一层的并发度，防止几十个任务同时打向下游数据库。

执行日志与告警

日志至少记录触发时间、实际起止时间、分片序号、耗时和异常摘要，按任务维度保留最近若干次。告警落在“连续失败”和“超时未完成”两个维度上，而不是每次失败都喊人，否则一个参数错误就能刷满整个群；可以连续三次失败才升级，并给任务设定最晚完成时间。

Cron 表达式与时钟的坑

第一，星期起点在不同实现里不一致，有的把周日当 0，有的当 1，写 1-7 未必是周一到周日，落地前要在目标框架里验证。第二，表达式方向写反：*/5 * * * * 是每 5 分钟，0 */5 * * * ? 是每 5 小时，多一个字段含义完全不同。第三，时区。容器默认跑在 UTC，业务按北京时间算账，配置里的“凌晨两点”实际是上午十点；跨夏令时的地区还会出现某天少一小时、任务被整体跳过。在调度层显式指定时区，比在每个任务里各自取本地时间可靠得多。

迁移、灰度与选型

迁移不要一次切完。先让旧任务在新平台上“只算不跑”，比对两边触发时刻是否一致；再按重要性分批切换，每批观察一到两个周期。切换期间新旧两套都可能触发，要靠幂等兜住，同时给旧任务留一个开关，出问题能秒级回退。

选型可按团队现状判断：任务量不大、已有稳定数据库，Quartz 集群够用；想要开箱即用的界面和分片，选带调度中心的方案；数据天然可切且已有 ZooKeeper，ElasticJob 更顺手；只跑一次性批处理，K8s CronJob 最轻。分界线不是功能多少，而是你愿意为调度这一层维护多少基础设施。

小结

分布式定时任务的核心不是“怎么定时”，而是“怎么保证一件事在正确的时间、被正确的节点、只做一次”。选主与分片决定谁来做，持久化与触发执行分离决定能不能管，重试、错过触发与幂等决定出错后能不能收场。落地时先想清楚任务能否分片、能否幂等，再挑框架；日志与告警覆盖失败和超时两个维度；迁移务必灰度，给回退留一条路。
