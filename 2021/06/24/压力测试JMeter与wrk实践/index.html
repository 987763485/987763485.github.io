压力测试：JMeter 与 wrk 实践

上线前的性能验证，常常败在方法而不是工具：脚本随手录一段，并发数拍脑袋定一个，看到聚合报告里的平均值就下结论。本文从压测要回答的问题出发，先厘清吞吐、延迟分位、错误率与资源水位这四个指标，再分别用 JMeter 5.x 与 wrk 4.x 搭出可复用的脚本，讨论闭环与开环两种模型的差别。

读完之后，你应当能为一个 HTTP 接口写出带参数化与断言的压测脚本，理解并发数与 RPS 之间并非线性关系，知道分布式发压的代价与发压机自身的瓶颈，并能从结果里区分应用、GC、数据库与网络四类问题。全链路压测平台的建设不在本文范围内，本文只谈单机与少量机器上的工具实践。

压测要回答的三个问题

压力测试不是把系统打挂，而是在受控条件下回答三个问题：这套配置能承载多少请求；压力升高时哪个环节先到极限；长时间运行后性能是否退化。若目标只是“看看能扛多少并发”，得到的数字通常无法复现，因为它缺少延迟约束与错误率约束。

描述结果至少需要四个指标。吞吐用 RPS 或 TPS 表示，统计口径要写清楚：是全部请求还是成功请求，是否包含被限流的请求。延迟不能只看平均值，平均值会被大量快请求拉低，掩盖长尾，应给出 P50、P90、P95、P99，长尾往往才是用户体验与超时配置的依据。错误率要区分连接失败、超时、5xx 与业务错误码，它们指向完全不同的瓶颈。资源水位包括发压侧与被测侧的 CPU、内存、GC 频率与停顿、连接数、数据库连接池、磁盘 IO 与网络带宽。

四个指标要一起看：只报一个很高的 RPS，却不提 P99 已超过一秒、错误率已到百分之几，这样的结论没有意义。把并发从低到高逐级加压，画出 RPS 与 P99 的曲线，RPS 增长放缓而 P99 陡升的位置就是容量拐点。

闭环与开环：并发数不等于 RPS

压测工具按施压方式分为闭环与开环两类，混淆两者是结果失真的常见原因。

闭环模型下，工具维持固定数量的虚拟用户，每个用户发完一个请求、收到响应后再发下一个。JMeter 的线程组默认就是这种模式。设并发数为 N、平均响应时间为 R 秒，忽略思考时间，稳定状态下吞吐 X 近似满足 X = N / R，这是利特尔法则（Little’s Law）的直观形式。若加入固定思考时间 T，则 X = N / (R + T)。举例来说，平均延迟 20 ms、并发 100 时，理论吞吐约 5000 RPS（示意值，仅用于说明关系）。

这个式子带来一个重要推论：闭环压测里的并发数是“在途请求数”，不是“用户数”；当服务变慢，R 增大，工具自动降低发压速率，系统反而被保护起来。所以闭环很难压出真正的过载，也解释不了“并发加到 500 为什么 RPS 上不去”——先看延迟是否已经变长。

开环模型按固定速率发起请求，不管上一个请求是否返回，更接近真实入口流量。开环需要足够的连接数和线程数支撑，否则工具自己会成为瓶颈。wrk 的限速参数、JMeter 的恒定吞吐量定时器都可以做近似开环，但后者在高压下精度有限，因为定时器仍受线程调度与响应阻塞影响。

JMeter：脚本、分布式与结果分析

典型的发压拓扑并不复杂，关键是把发压端、被测端与观测端分开：

flowchart TD
  A[发压机 JMeter 或 wrk] --> B[负载均衡]
  B --> C[应用实例一]
  B --> D[应用实例二]
  C --> E[数据库与缓存]
  D --> E
  F[监控与日志] -.采集.-> C
  F -.采集.-> D

JMeter 的测试计划以线程组为执行单位。线程数是在途请求上限，Ramp-up 是启动全部线程所需的秒数，循环次数与调度器决定压多久。Ramp-up 不要太小，否则瞬间建立的连接会让结果被握手与排队污染。

HTTP 请求的默认超时是无限的，必须在 Sampler 里显式设置连接超时与响应超时，否则一个卡住的请求会占住线程直到测试结束。断言只校验必要内容：状态码、业务码、关键字段是否存在。断言会在每个请求上执行，用正则去匹配几十 KB 的响应体，开销可能超过被测接口本身。

参数化用 CSV Data Set Config。把用户 ID、token、查询条件放进文件，设置“遇到文件结束不循环”，让每个线程取不同行；共享模式选择“所有线程”，避免多个线程读到同一账号而互相干扰。需要保持会话时，用 JSON 提取器或正则提取器做关联，把登录返回的 token 写入变量供后续请求引用。

多个请求构成一个业务动作时，用事务控制器把它们包起来，聚合报告里的 TPS 才是业务吞吐。定时器用于模拟用户思考时间，恒定吞吐量定时器可以限定速率，但它是尽力而为，压力接近上限时实际速率会偏离设定值，此时应改用开环工具或增加发压机。

单台发压机的能力有上限：JMeter 每个线程都有内存开销，几千线程就可能吃掉数 GB 堆内存。压测前先看发压机自身的 CPU、网络与文件句柄，若发压机已饱和，测出来的是它的极限，不是被测服务的极限。

分布式压测用一台控制机调度多台执行机。执行机启动 jmeter-server，控制机在命令行用 -R 指定节点列表，测试计划与 CSV 文件需要提前分发到各执行机，路径保持一致。控制机汇总结果，数据回传占用带宽，节点越多，汇总与时钟同步越麻烦。

JMeter 的常见误用几乎都与资源开销有关：在 GUI 模式下拉满线程压测，界面刷新本身就在抢 CPU；挂着“查看结果树”跑几万请求，内存很快耗尽；每个请求都加多条断言和正则；把日志级别调到 DEBUG，磁盘 IO 成为瓶颈。这些做法会让报告里的延迟包含工具自身的开销。

wrk：轻量发压与 Lua 脚本

wrk 4.x 用少量线程配合事件驱动处理大量连接，资源开销远低于 JMeter，适合快速摸清一个 HTTP 接口的吞吐上限。

线程数不应超过发压机的 CPU 核数，超过只会增加上下文切换；连接数决定同时在途的请求上限，也决定能压出多大的吞吐。二者要匹配，否则不是事件循环处理不过来，就是线程无事可做。建议固定线程数，逐步提高连接数，观察 RPS 与延迟的变化。

连接数受本地端口限制。一条 TCP 连接由一个四元组标识，发压机到同一目标地址时，可用源端口大约两万多个，再扣除 TIME_WAIT 占用，实际可用更少。连接数上千后出现“Cannot assign requested address”，通常不是被测服务拒绝，而是发压机端口耗尽。可以扩大本地端口范围、缩短 TIME_WAIT 回收时间，或改用多台发压机、多个目标 IP。

wrk 默认使用长连接，HTTP/1.1 复用同一条连接发多个请求。若被测服务在响应头里关闭连接，每次请求都要重新握手，结果会差一个数量级。做对比测试时必须固定连接策略，并在报告里注明。

工具选型与发压机隔离

维度 JMeter 5.x wrk 4.x
协议与场景 HTTP、JDBC、JMS 等，可用控制器编排业务 以 HTTP 为主，靠 Lua 扩展
脚本能力 图形化配置，CSV、断言、关联齐全 Lua 脚本，轻量灵活
资源开销 较高，线程与监听器都吃内存 很低，单机可打很高吞吐
结果呈现 聚合报告、HTML 报告完善 终端输出，需自行汇总
分布式 内置控制机与执行机模式 无内置，靠多机加汇总
适用场景 业务链路、需要断言与参数化 单接口压极限、快速回归

选型不必对立。常见做法是先用 wrk 压单接口，确认服务端上限与发压机能力，再用 JMeter 复现登录、下单、查询组成的业务链路，看混合场景下的相互影响。

发压机必须与被测服务隔离：不同物理机或至少不同宿主机，避免争抢 CPU 与带宽；不要共用入口带宽和负载均衡；关闭不必要的采集与日志；单独准备压测账号与数据，避免污染真实用户。发压机本身也要监控，CPU 打满、网络跑满、端口耗尽时，先解决发压侧问题再解读结果。

别把压测做成攻击

压测与攻击在流量特征上并无本质区别，区别只在授权与边界。开始前要有书面授权，写明目标地址、接口范围、压力上限与时间窗口；提前通知值班、DBA 与上下游依赖方；避开业务高峰与结算等敏感时段。压测流量最好带上专用 Header 或来源标识，便于在日志与监控里区分。

执行过程中要有随时中止的手段：控制台一键停止、脚本支持中断、发压机可被远程杀掉。设置自动熔断条件，例如错误率连续超过阈值、P99 超过设定值、被测服务健康检查失败，就立即降压或停止，而不是继续加并发“看看还能撑多久”。

结果解读与瓶颈定位

拿到报告先看错误率，再看吞吐与延迟。错误率超过预期时，吞吐数字没有意义。按错误类型分流：连接被拒绝，多半是 backlog 或端口耗尽；大量超时，通常是下游依赖或数据库变慢；5xx 集中出现，查应用日志与线程池；业务错误码升高，查限流与库存等业务规则。

定位瓶颈按层排查。应用层看线程池是否打满、锁竞争、连接池等待、GC 日志里的停顿；GC 频繁且停顿长，说明堆或对象分配有问题，此时加机器可能只是延缓。数据库看慢查询、活跃连接数、锁等待与 CPU，很多“接口慢”最终落在一条缺失索引的 SQL 上。网络看带宽是否跑满、重传率、RTT 与丢包，跨机房调用尤其明显。

几个反复出现的坑值得单独提醒。压测数据不真实：几千条数据测出的结果在千万级表上不成立，索引选择与缓存行为都会变。缓存命中失真：反复压同一批热 key，看起来吞吐很高，真实流量的冷数据会把压力全部打到数据库。只测单接口：链路上的鉴权与下游调用被忽略，混合场景的相互影响也看不到。忽略错误率：RPS 漂亮，但一半请求已失败。忽略发压机瓶颈：把发压机的上限当成了服务的上限。

小结

压测的价值在于可复现的结论，而不是一个孤立的峰值数字。先把目标、指标与约束写清楚，四个指标一起看，用拐点描述容量。理解闭环与开环的差别，别把在途请求数当成用户数，也别用闭环证明系统能扛过载。JMeter 适合业务链路的编排与校验，务必用命令行模式并控制断言、监听器与日志的开销；wrk 适合快速摸接口上限，但要关注线程、连接数、端口与长连接策略。发压机与被测服务隔离，压测在授权与熔断的前提下进行。把数据真实性、缓存命中、链路完整性与错误率写进报告，结论才站得住。
