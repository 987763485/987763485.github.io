Kubernetes 多集群管理

本文属于《Docker 与 Kubernetes》第 28/51 篇
上一篇系列目录下一篇

一个 Kubernetes 集群能撑到多大，是很多人都会问的问题。社区给出的规模上限看起来够用，可业务堆上去之后，先撑不住的往往不是 apiserver，而是协作方式与故障的波及范围。多集群于是从可选架构变成了迟早要面对的现实。

本文讨论多集群管理的整体图景：为什么要拆、常见形态、管理面与网络要解决什么、制品与身份如何统一，以及选型时的坑。Kubernetes 基础不再重复，多租户留给后续文章，GitOps 的工作流另有专文，这里只谈它在多集群中的角色。

为什么要多集群

把多个集群并排放着，运维成本一定上升。所以第一步不是选工具，而是想清楚单集群卡在哪里。常见动机有五类。

隔离。命名空间能隔开对象，却隔不开控制面。一次误删 CRD、一次 apiserver 被打满、一次 etcd 抖动，所有租户一起受影响。拆开集群，等于给每个团队一条独立的故障域，代价是维护成本上升。

地域。用户分布在多个区域时，把流量调度到最近的集群，既能降低延迟，也能满足数据不出境的要求。跨地域的单集群在 etcd 层面就很难成立：节点与 apiserver 的往返延迟超过几十毫秒，心跳与选主都会不稳定。

容灾。单集群的高可用只能做到控制面多副本、节点跨可用区。整个区域出问题时，仍需另一个集群接管。

爆炸半径。变更引发的故障规模，取决于变更作用在多大的范围上。把集群拆小，一次错误的滚动升级最多影响一个集群。

合规。等保与金融行业的分级要求，往往直接规定生产与测试隔离、不同密级数据不得同处一个环境。集群边界是最容易向审计人员解释的边界。

这几条动机里只有一部分必须靠多集群解决。纯粹为了隔离团队或灰度，多集群是较重的方案。先确认动机再拆分，比先搭联邦控制面再找理由省事得多。

多集群的几种常见形态

拆集群的方式，基本可以从“为什么拆”推出来，常见的有四类。

多环境集群。开发、测试、预发、生产各自独立，最普遍。好处是变更互不污染，坏处是四份配置容易出现“测试通过、生产不一样”的漂移，管理重点是配置一致与环境快速重建。

多云集群。业务分散在两家以上云厂商，动机可能是议价、避免锁定，也可能是并购遗留。难点不在 Kubernetes，而在各家的负载均衡、存储、网络实现不同，同一份清单要适配不同的 StorageClass 与 Ingress。

边缘集群。门店、工厂侧各放一个小集群，中心只做管控。节点少、网络差、经常离线，管理面必须有断网续传能力，且对资源占用敏感。

租户集群。为每个大客户单独开一套集群，隔离彻底，但运维成本乘以租户数，必须配合自动化的创建与销毁。

    A --> C[测试集群]

    A --> E[生产集群-区域二]

上图是默认模型：一个管理面，下挂若干成员集群。每个成员集群仍保留完整控制面，能独立工作。管理面应当是“增强”而非“必需”，否则它会成为新的单点。

管理面：注册、分发与统一 API

多集群首先要回答：管理面怎么认识这些集群。直接给每个集群准备 kubeconfig 最简单，但凭据散落、轮换困难。更常见的做法是在成员集群部署 agent，由 agent 主动向管理面建立长连接。连接方向反过来后，管理面不必直连每个集群，NAT 后面的边缘集群也能接入。

集群注册后会形成一个集群对象，记录名称、地域、标签、版本与健康状态。标签是调度的基础，比如按 region=cn-east 选择目标集群。集群对象还需要状态机，注册、就绪、不可达、下线四种状态不清楚，分发就会向失联集群反复重试。

配置分发的本质是“一份声明，落到多个集群”，能力大致分三档：模板渲染，用 Helm 或 Kustomize 渲染后分别 apply，简单但状态不可追踪；集中式分发，管理面保存模板与差异覆盖，推送并持续纠偏，Karmada 属于这一档；GitOps，集群内 agent 主动从仓库拉取并收敛，ArgoCD 与 Flux 是代表。差异化的粒度也要控制，按集群覆盖的字段越少，模板越容易维护。

GitOps 在多集群里的价值，是把期望状态变成仓库里的目录结构：一份基础配置加按集群覆盖的 patch，改动有提交历史，回滚就是 revert。代价是仓库成了生产环境的一部分，必须做好备份与权限控制；拉取模式还要求每个集群都能访问仓库。

再往上是统一 API 类项目。Karmada 用传播策略把工作负载与策略分发到成员集群，并在故障时迁移；Cluster API 把“集群本身”当成资源，用控制器负责创建、升级与扩缩，解决的是集群生命周期。两者常配合使用：一个造集群，一个往里放东西。

选型时先分清“管理应用”还是“管理集群”。前者看分发与漂移检测，后者看基础设施支持与升级路径。混在一个工具里，往往两边都不够好。

网络互通：Pod、Service 与 DNS

多集群最容易被低估的是网络。应用拆开之后仍然要互相调用，问题变成：集群 A 的 Pod 能否直接访问集群 B 的 Pod 地址？

默认不能，也不应该。每个集群有自己的 Pod CIDR 与 Service CIDR，网段大概率重叠，直接路由会撞车。可行的手段有三种。

一是网关暴露。把需要跨集群访问的服务通过 Ingress 或网关暴露，对端按域名访问。不要求网段互通，配置简单，是多数团队的第一选择，代价是多一跳，且要维护服务目录。

二是东西向网关。在集群之间建隧道，只把特定 Service 网段互相通告，Pod 通过隧道访问对端 Service VIP，Cilium 的 cluster mesh、Submariner 都属于这类。它对应用透明，难点在地址规划：必须提前给每个集群分配不重叠的网段，后期再改几乎不可能。

三是服务网格的多集群模式。控制面统一，数据面在各集群本地，跨集群调用由网关转发并携带身份与策略。它同时解决认证与治理，但组件多，对团队要求最高。

DNS 是同一件事的另一面。内置 DNS 只解析本集群的 Service，跨集群要么用外部域名，要么在 CoreDNS 里配置转发与存根域。转发规则写错的表现是解析超时而非报错，排查时先看 CoreDNS 日志。

延迟也要提前评估。同城跨集群往返在毫秒级，跨地域则是几十毫秒，串行调用五六个跨地域服务，累积延迟足以让页面变慢。这类链路应优先本地缓存、异步化或数据就近部署。不要把高频同步调用设计成跨集群。服务发现上，对端地址尽量用域名而不是写死 IP，后续迁移集群时才不用改配置。

制品、身份与可观测性

除了网络，还有三件事必须统一，否则多集群会退化成多个互不相干的手工作坊。

镜像与制品分发。跨云时把镜像同步到各云自己的仓库，让节点就近拉取，比跨公网稳定得多。同步可以由流水线在构建后触发，也可以用仓库的复制功能。注意清理策略，每个集群保留全量镜像会让存储成本翻倍。Helm chart 与清单同理，应放在各集群可达的制品库。

身份与 RBAC。理想状态是登录一次、权限在所有集群一致。通常是接统一身份提供方，用 OIDC 认证，再用同一套角色在各集群绑定相同的组。管理面若支持权限透传，要检查它是否把高权限带到成员集群。服务账号的 token 要有明确的有效期与最小权限，不要把 admin kubeconfig 复制到另一个集群当万能钥匙。

可观测性聚合。指标、日志、追踪都建议本地采集、中心存储。跨集群查询原始数据会放大网络开销，聚合后数据量小得多：指标在本地做 recording rule 只远端写聚合结果，日志在本地缓冲以免断网丢失，追踪要保证 trace id 跨集群透传。告警规则不要写死集群名，用标签聚合，新增集群才不用改规则。

灾备与流量切换

多集群的容灾能力，取决于切换有多快、切换后数据是否一致，这比集群本身的高可用难得多。

按恢复目标可分三档。冷备只保留基础组件，故障时再部署应用，恢复以小时计，成本最低；温备跑最小副本并持续同步数据，切换时扩容，恢复以分钟计；热备两个集群同时承载流量，切换只改权重，恢复以秒计，但成本与一致性要求最高。

有状态服务的难点在数据。数据库同步通常不交给 Kubernetes，而是用数据库自身的复制，主库在一个集群、备库在另一个。切换时做主备倒换，应用要能接受连接串变化。无状态服务简单些，镜像与配置齐备即可扩容接管。

流量切换先少量验证再全量，需要入口支持按权重或地域调度，也需要快速回滚。入口切换通常靠 DNS 或全局负载均衡完成，TTL 要提前调小，否则客户端缓存会让切走的流量迟迟不散。切换脚本必须演练，演练时要真的停掉主集群。没有演练过的灾备方案，基本等于没有。

选型建议与常见坑

如果团队还在单集群阶段，建议很明确：先把单集群的多命名空间用扎实，把资源配额、网络策略、RBAC 做清楚，把发布流程自动化。真正该拆分的信号通常有三个：变更事故已经影响到无关业务；业务有明确的地域或合规要求；规模触及上限且无法通过拆分工作负载缓解。

决定要拆之后，优先选“管理面可退化”的方案。成员集群应能在管理面失联时继续运行，只是暂时收不到新配置。这条原则能过滤掉不少强中心耦合的设计。

实践中反复出现的问题有几类：

  • 配置漂移。某个集群被手工改过参数，下次分发被覆盖，或因模板没覆盖而一直保留错误值。对策是禁止手工修改，并定期比对实际与期望状态。
  • 证书与凭据。apiserver 证书过期、agent token 未轮换、跨集群证书绑定了旧 IP，都会在某个夜里集中爆发。把到期时间纳入监控是最低要求。
  • 版本碎片化。集群逐个建起来版本各异，半年后升级时路径全不一样。应限定支持的版本窗口，新集群用当前稳定版本，老集群按计划收敛。
  • 跨集群 Service 延迟。把本可本地调用的服务拆到两个集群，平白多一跳。拆分前先画清调用关系，高频调用留在同一集群。
  • 控制面资源被低估。管理面与各类 agent 对成员集群也是开销，边缘场景尤其明显。

小结

多集群不是目标，而是隔离、地域、容灾、爆炸半径与合规共同作用的结果。拆分前先确认动机，能用一个集群加命名空间解决的，不要急着上联邦。

技术上，注册与分发是骨架，GitOps 让期望状态可追溯，Karmada 与 Cluster API 分别解决应用分发和集群生命周期；网络优先用网关暴露，确需 Pod 直连时提前规划不重叠网段；镜像、身份、可观测性要统一，灾备要真实演练。配置漂移、凭据过期、版本碎片化几乎每个多集群环境都会遇到，纳入日常巡检比事后救火划算。
