开源许可证合规

一个项目的依赖树里躺着几百个开源包，每个包都带一份 LICENSE 文件，这些文件的法律含义彼此不同。合规的目标不是把所有许可证都换成 MIT，而是在清楚义务边界的前提下，让使用、修改和分发行为都能被追溯和解释。

本文从许可证分类讲起，逐条拆解常见许可证的核心义务，再落到分发与 SaaS 的差别、链接方式与衍生作品的模糊地带、依赖传递中的冲突识别，最后给出一套可运行的工程流程：SBOM、扫描工具、准入清单、CI 门禁与合规报告。文中涉及法律判断的部分只描述通行理解与工程实践，具体结论需要由法务结合具体事实确认，本文不构成法律意见。

许可证的三层光谱

理解许可证的第一步是放弃“开源就是免费”的直觉，改用义务强度来排序。所有被 OSI 认可的许可证都允许商业使用，也都要求保留版权与许可声明，差别在于它们对“衍生作品”的定义范围，以及对源码披露的要求强度。按这个维度，业界通常把许可证分成三层。

第一层是宽松许可证（permissive），代表是 MIT、BSD 系列、Apache-2.0。它们允许你把代码嵌入闭源产品，只要求保留版权声明和许可文本，不要求你公开自己的修改。第二层是弱 copyleft，代表是 LGPL-2.1、LGPL-3.0 和 MPL-2.0。它们把 copyleft 的传染范围限制在库本身，通常允许闭源程序以动态链接方式使用，但你对库本身的修改仍要按同一许可证开放。第三层是强 copyleft，代表是 GPL-2.0、GPL-3.0 与 AGPL-3.0。它们要求整个衍生作品以同一许可证分发，并提供完整对应源码。

这个三层模型是有用的工程近似，但它不是法律定义。真实的判定依赖具体许可证条文、链接方式、进程边界和司法辖区，同一段代码在不同架构下可能落在不同层级。工程上正确的做法是：把分层当作风险初筛，把边界情形交给法务，而不是让工程师在代码评审里拍板。

宽松阵营的义务边界

MIT 是最短的一份许可证，全文只有一段。它要求在所有副本或实质性部分中保留版权声明和许可声明，除此之外几乎没有约束。它的两个空白值得记住：没有明示专利许可，也没有商标许可。前者意味着贡献者没有在条文层面承诺不向你主张专利，后者意味着你不能把项目名当作自己的品牌背书。

BSD 系列有两种常见变体。二条款版与 MIT 实质等价；三条款版多了一条禁止背书条款，禁止用作者或贡献者的名字为衍生产品做推广。这条经常被市场部门踩到：宣传物料里写“由某某团队出品”或“某某官方推荐”，如果没有单独授权，就已经越过了许可证给的范围。

Apache-2.0 是宽松阵营里条文最完整的。它要求保留版权、专利、商标和归属声明；如果上游分发了 NOTICE 文件，你必须随分发保留其中的内容，可以追加自己的声明，但不能删除原有条目；你对文件做了修改，要在修改过的文件里放置显著的变更说明；你要附上一份 Apache-2.0 的副本。它给出了明示的专利许可，同时附带了专利报复条款：如果你对采用该许可证的项目发起专利诉讼，指控其侵犯专利，你因该许可证获得的专利许可随即终止。这不是对使用者的额外负担，而是让专利持有人和采用者站在对等位置上的机制。

弱 copyleft 的传染半径

LGPL 的设计目标就是收窄 copyleft 的范围。它允许闭源程序以特定方式使用库，前提是用户仍然能够替换这个库：动态链接时保留可替换的共享库，静态链接时提供足够的目标文件让用户重新链接。同时，你对库本身的修改仍然要按 LGPL 开放，并且要提供库的完整源码。LGPL-3.0 构建在 GPL-3.0 之上，额外增加了安装信息要求，针对的是消费类设备把库固化在硬件里、用户无法替换的情形。

MPL-2.0 走的是另一条路：以文件为单位划分边界。被 MPL 覆盖的文件如果被修改，必须以 MPL 分发并提供源码；未修改的文件可以与闭源代码放在同一个二进制里。这条规则对“开放核心”型产品很友好，也让合规检查可以落到文件粒度，而不是整个仓库粒度。

强 copyleft 的整体性要求

GPL-2.0 的核心义务可以概括成三条：分发时提供对应源码，整个衍生作品按 GPL 分发，不得对下游附加额外限制。第三条最容易被忽视，它意味着你不能在 GPL 代码外再套一层禁止商用的条款。

GPL-3.0 在此基础上补了三块内容。一是反规避条款，要求提供安装信息，防止设备厂商用签名锁死用户替换软件的能力；二是明示专利授权，与 Apache-2.0 兼容；三是终止后的恢复机制，首次违规在收到通知后一定期限内完成纠正，许可可以恢复，而不是永久失效。

AGPL-3.0 只比 GPL-3.0 多一条，但这一条改变了很多产品的合规结论：如果用户通过网络与修改后的程序交互，你必须向这些用户提供获取对应源码的机会。它把义务触发点从“分发二进制”扩展到了“提供网络服务”。

分发、SaaS 与 AGPL 的网络条款

GPL 系列的义务几乎都挂在“分发”这个动作上。不分发，就不触发源码提供义务。这个区分在传统软件时代很清晰：卖光盘、卖安装包就是分发，自己在公司内部跑就不是。到了云服务时代，边界变得模糊，判断难度大幅上升。

先明确什么算分发。对外发布的安装包、容器镜像、移动端 App、随硬件出货的固件、交付给客户私有化部署的整套系统，都属于典型分发。容易被忽略的是间接分发：把镜像推到公开仓库、把 SDK 嵌进合作方的产品、把带二进制的构建产物上传到制品库并允许外部拉取，这些行为在实务中同样可能被认定为分发。反过来，在公司内部服务器上运行、不向外部提供二进制，通常不构成分发，但“内部”的边界需要谨慎界定：关联公司、外包团队、客户驻场环境是否算内部，取决于控制关系和合同安排，属于法律判断。

SaaS 的常见结构是：后端进程加载了某个 GPL 库，通过 HTTP 对外提供服务，用户拿不到二进制。按照 GPL-2.0 和 GPL-3.0 的通行理解，这种情形一般不触发源码提供义务。这正是 AGPL 被创造出来的原因。AGPL-3.0 第 13 条要求：如果程序通过网络供用户远程交互，你必须向这些用户提供获取对应源码的机会，通常的做法是在产品界面放一个源码下载入口，或在服务条款中给出获取方式。

这里有两个工程上必须澄清的点。第一，AGPL 的触发条件是“用户通过网络与该程序交互”，不是“分发”。只要修改过的 AGPL 组件参与了对外服务，就需要评估。第二，提供源码的对象是“与之交互的用户”，不是全世界，但实践中往往等同于公开发布，因此不能指望用登录墙规避。

落地时最有价值的动作是画一张部署图，逐个组件标注三件事：是否对外提供网络服务、是否随客户端分发、是否被修改过。把这张图和许可证清单叠在一起，义务就变得可计算了。

链接方式与衍生作品的边界

“衍生作品”是 copyleft 许可证里最关键也最模糊的概念。许可证文本给出的是原则，落到具体工程形态上，需要结合链接方式、进程边界、数据交换的耦合程度来判断。这一节描述的是业界常见的分析框架，不是结论；真正的定性属于法律判断，工程团队应当把边界情形提交法务确认，并把确认结果记录在案。

动态链接是最常见也争议最多的形态。自由软件基金会的立场是：动态链接形成的可执行文件构成单一结合作品，应当整体按 GPL 分发。这个立场有广泛影响，但它是一方的解释，不是普适的法律结论。不少商业产品采取的做法是把 GPL 组件放到独立进程里，通过本地 socket 或 HTTP 与主程序通信，主张两者是独立作品。这种隔离是否成立，取决于交互的紧密程度：如果主程序必须依赖该进程完成核心功能，且两者共享复杂数据结构，隔离主张的说服力就会下降。

静态链接的风险高于动态链接。静态链接把库的代码直接编进可执行文件，产物中包含了 GPL 代码的副本，主张“独立作品”的空间很小。弱 copyleft 场景下，静态链接 LGPL 库也有代价：你需要提供目标文件，让用户能够重新链接出替换了库的新版本。这条义务经常被忽略，直到有人真的要求行使它。

还有几种容易低估的形态。头文件包含：把 GPL 库头文件里的内联函数、宏、模板复制进自己的源码，实质上是在自己的文件里复制了受许可证约束的代码。代码生成：用 GPL 工具生成的代码，其许可证归属取决于工具的输出条款，有些工具明确声明输出不受许可证约束，有些没有，需要逐个核对。插件加载：通过 dlopen 之类的方式在运行时加载模块，是否构成结合作品，业界分歧很大，不能一概而论。

修改与使用也要分开看。使用一个 GPL 程序不产生开源义务；修改它并把修改后的版本对外分发，才产生。但“修改”的定义比想象中宽：打补丁、改配置默认值、删除功能、替换资源文件，都可能被认定为修改。工程上稳妥的做法是维护一份补丁清单，记录每个被修改的上游组件、补丁内容与分发范围。

综合起来，判断顺序可以归纳为四步：先看有没有分发，再看许可证层级，再看链接与进程边界，最后看是否修改。四步中任何一步落在灰区，都应该触发法务评审，而不是由工程师在代码评审里自行裁决。

依赖传递与许可证冲突

现代项目的依赖是传递的。你引入一个直接依赖，它又引入十几个间接依赖，间接依赖再往下展开，一个中等规模的 Node 服务很容易出现数百个包，Java 项目同样如此。许可证义务沿着依赖树传递：只要某个深层依赖是 GPL，它带来的义务不会因为“不是我们直接引的”而消失。

依赖树还有几个隐蔽入口，扫描工具未必默认覆盖。锁文件与包管理器缓存可能锁着一个已被上游撤下的版本；源码仓库里可能存在 vendored 目录，把第三方代码直接复制进自己的仓库；构建镜像的基础层可能自带系统包；前端打包产物里可能内联了某个库的压缩版本。合规扫描如果只读清单文件，会漏掉后三类。

冲突的本质是许可证条款互相矛盾，导致无法同时满足。几种典型组合值得记住。

Apache-2.0 与 GPL-2.0 不兼容。原因在 Apache-2.0 的专利报复条款：它对下游施加了 GPL-2.0 第 6 条所禁止的额外限制。因此把 Apache-2.0 代码并入 GPL-2.0 项目，会遇到无法同时履行两边义务的困境。GPL-3.0 则与 Apache-2.0 兼容，GPL-3.0 第 11 条的专利条款与 Apache-2.0 的设计相容，两者可以组合。

GPL-2.0 与 GPL-3.0 之间也不兼容。只声明 GPL-2.0 的项目不能吸收 GPL-3.0 的代码；声明 GPL-2.0-or-later 的项目可以选择升级到 GPL-3.0。这个后缀看似细节，实际决定了整个项目的升级路径，工程上应当把它当作重要元数据保存，而不是在扫描报告里被截断成 GPL-2.0。

AGPL 与 GPL-3.0 的组合需要额外注意。AGPL-3.0 的第 13 条比 GPL-3.0 更严格，两者混合后的整合作品通常要按 AGPL 分发，这意味着网络服务路径也会被覆盖。如果只想在内部工具里用 AGPL 组件，就必须确保它不进入对外服务的依赖闭包。

强 copyleft 与闭源组件的组合没有折中空间，只能选一条路：整体开源、替换组件、或者做进程级隔离并取得法务确认。宽松许可证之间通常可以共存，但仍要注意声明汇总：MIT 要求保留版权行，Apache-2.0 要求保留 NOTICE，BSD-3-Clause 要求保留禁止背书条款，这些义务不会因为彼此兼容而互相抵消。

许可证表达式是描述这些组合的通用语法。SPDX 定义了三种运算符：OR 表示任选其一，AND 表示需要同时满足，WITH 表示附加例外。一个组件声明为 GPL-2.0-only WITH Classpath-exception-2.0，含义是采用 GPL-2.0 但附带类路径例外，允许以特定方式链接而不触发 copyleft。这类例外条款经常被扫描工具简化掉，导致误报或不报，需要人工复核。

还有一种情况是上游换证。某个包从 MIT 改为源码可见但限制商用的许可证，或者从 Apache-2.0 改为更严格的条款，这类变更往往只在小版本里悄悄发生。工程上的对策是锁版本加升级评审：升级 diff 里必须包含许可证字段的比对，而不只是看变更日志和测试结果。

SBOM 与依赖扫描工具

要管理上述风险，前提是知道自己用了什么。SBOM（Software Bill of Materials，软件物料清单）就是这份清单的标准化表达。2021 年前后，SBOM 从合规圈的小众话题变成了供应链安全的基础设施，美国的相关行政令和多个行业的采购要求都在推动它落地。

目前有两种主流格式。SPDX 由 Linux 基金会维护，规格成熟，表达能力强，适合做法律与合规视角的清单，字段覆盖组件、许可证、版权、供应关系。CycloneDX 由 OWASP 社区推动，早期偏重组件的安全漏洞场景，结构更轻，对 VEX（漏洞可利用性声明）这类安全信息支持得更好。两者都有 JSON 表示，也都能表达依赖关系图，选哪个更多取决于客户和监管方要求，而不是技术优劣。

生成方式有三种。构建时生成最可靠，在流水线里由构建工具或专用插件输出，能保证清单与实际产物一致。源码扫描适合存量代码，可以覆盖 vendored 目录和历史仓库，但识别结果依赖扫描规则。镜像扫描适合交付前把关，能看到基础镜像里的系统包。三种方式互补，实践中常用构建时生成作为主清单，用镜像扫描做交叉校验。

工具层面，几类工具定位差别很大，混用会得到互相矛盾的报告。

FOSSA 是商业化的 SaaS 平台，接入仓库后自动解析依赖树，给出许可证与安全问题的合并视图，带政策引擎和审计留痕。它的优势是把“发现、判定、豁免、复检”串成流程，适合需要向客户或审计方出具报告的组织；代价是依赖网络上传代码信息，对保密要求高的项目需要评估。

ScanCode Toolkit 是开源的本地扫描器，直接读文件内容，识别许可证文本、版权行和作者信息。它不依赖包管理器，因此能覆盖 vendored 代码、历史遗留目录和来源不明的文件。缺点是速度慢，且对许可证文本的识别需要人工确认边界，适合做深度审计而不是每次提交都跑。

license-checker 是 npm 生态里的轻量工具，读取 node_modules 的元数据，输出依赖的许可证清单，可以按许可证类型直接让命令失败。它上手成本极低，适合放在 CI 里做第一道卡口，但只看 npm 生态，且依赖包自身声明的准确性。

SBOM 的落地要点不在格式，而在一致性。清单必须能和具体构建产物对应起来，因此要记录构建时间、提交号、镜像摘要，以及生成工具与规则库的版本。缺了这些，一份 SBOM 在出现争议时几乎无法自证。

企业流程：准入、豁免与门禁

工具解决发现问题，流程解决处置问题。一套能长期运转的开源合规体系，通常由四个环节组成：准入清单、扫描与门禁、豁免审批、归档与复检。

准入清单是第一道闸。把许可证分成三档并写进研发规范：白名单可以直接使用，灰名单需要架构评审并说明链接方式与分发形态，黑名单原则上禁止，确实需要时走豁免。分档标准应当结合业务形态制定，一家只做私有化交付的公司和一家纯 SaaS 公司，对 GPL 的容忍度完全不同。清单要随业务变化定期复核，而不是定一次用三年。

扫描与门禁解决“每次都查”的问题。门禁放在合并请求和发布两个节点：合并请求阶段跑快速扫描，只拦新增的高风险依赖，避免历史包袱让所有人无法提交；发布阶段跑全量扫描并生成 SBOM，作为交付物的一部分。门禁的判定结果要可解释，失败信息里应直接给出组件名、版本、命中的许可证和处置建议，否则开发者只会想办法绕过。

豁免审批是让例外可控的机制。每一条豁免都应当是一个有期限、有责任人、有缓解措施的记录：谁申请的、哪个组件、哪个版本、用在哪条产品线、分发形态是什么、采取了什么缓解手段、什么时候到期。豁免不是永久通行证，到期要重新评估。缺少到期时间，豁免表三年后就会变成一张谁也不敢动的历史遗迹。

归档与复检是应对审计的底牌。每次发布保存三样东西：SBOM、扫描报告、当期的豁免清单。保存期限按合同与行业要求确定，通常与产品生命周期挂钩。复检的触发条件包括上游换证、组件大版本升级、产品分发形态变化，以及监管要求更新。

常见误区、合规报告与整改

第一个误区是“开源等于随便用”。开源许可证是版权持有人给出的许可，不是放弃权利。许可附带了条件，不履行条件的使用就失去了许可依据。这个区别决定了合规工作的性质：它不是道德倡议，而是权利边界管理。

第二个误区是“内部使用不分发就没事”。这句话在纯内网、无外部交付的场景下大体成立，但“内部”的边界经常被业务悄悄突破：给客户做私有化部署、把镜像交付给合作方、让外包团队接入同一套制品库、把内部系统开放给合作伙伴登录。任何一个动作都可能把内部使用变成分发。更麻烦的是 AGPL，它根本不以分发为触发条件，只要对外提供网络交互就要提供源码。因此正确的说法是“内部使用通常不触发源码义务，但需要确认分发边界，并对 AGPL 单独判断”。

第三个误区是“删掉版权头就合规”。这恰好相反。几乎所有许可证都要求保留版权与许可声明，删除声明本身就是违约行为，在某些法域还可能涉及权利管理信息的问题。合规的做法是完整保留原始声明，把各组件的信息汇总到统一的第三方声明文件中，随产品一起交付。

还有几个高频误判值得一提。只看直接依赖，忽略传递依赖和 vendored 代码；把 Creative Commons 系列协议当作软件许可证使用，其中带非商业或禁止演绎条款的版本根本不符合开源定义；把“源码可见”当成开源，源码可见但限制商用的许可证不属于 OSI 认可的开源许可证；把公司内部自研组件默认当成自有资产，而它可能引用了外部代码。

合规报告是流程的输出物，结构应当稳定，便于逐年对比。一份可用的报告包含五部分：范围，说明覆盖的仓库、镜像与版本；方法，说明使用的工具、规则库版本与扫描时间；结果，给出组件总数、许可证分布、按风险分级的明细；处置，逐项说明替换、隔离、开源或豁免的决定与责任人；结论，说明残余风险以及下一轮复检时间。

整改需要排序，否则团队会被一屏红色告警压垮。建议按四档推进：阻塞级是强 copyleft 组件进入闭源分发路径，必须在发布前解决；高危级是无许可证或自定义许可证的组件，权利状态不明，风险不可估；中危级是声明缺失或 NOTICE 未汇总，通常补齐即可；低危级是文档与流程问题。每档给出明确的完成标准和责任人，比笼统的“尽快整改”有效得多。

小结

许可证合规的本质是把法律文本翻译成工程动作：先按义务强度给组件分层，再判断是否分发、如何链接、是否修改，最后把结论固化到 SBOM、门禁和豁免记录里。宽松许可证管好声明，弱 copyleft 管好库的边界与替换能力，强 copyleft 管好整体开源与源码提供，AGPL 还要多看一步网络交互。链接方式与衍生作品的定性属于法律判断，工程团队的职责是提供准确事实并把灰区交给法务，而不是自行下结论。流程上，准入清单决定能不能用，CI 门禁保证每次都用对，豁免与归档让例外可追溯。把这四件事做成常态，合规才不至于变成每次发布前的一次突击。
