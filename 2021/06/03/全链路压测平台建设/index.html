全链路压测平台建设

每年大促之前，团队都会面对同一个问题：整套系统到底能扛住多少流量。单接口压测只能回答某个服务在理想条件下的极限，却无法回答一次真实下单请求穿过网关、订单、库存、支付、消息队列之后，究竟在哪一环先撑不住。全链路压测要做的，就是把这条完整链路放到接近真实的流量下跑一遍。

本文从平台建设的角度，讨论全链路压测需要解决的三个问题、流量染色与数据隔离的实现思路、压测开关与流量模型的设计、监控与瓶颈定位方法，以及风险控制和组织协作。读者应具备基本的后端与中间件知识，读完后能够规划一套可落地、可控的压测平台，而不是停留在写几个压测脚本的层面。

从单接口压测到全链路压测

单接口压测的典型做法是：选一个服务，构造固定请求，在隔离环境里不断加大并发，直到响应时间或错误率越过阈值。它回答的是“这个接口在这个环境里的极限”。但它有三个天然缺口。

第一，调用链被切断。真实请求会经过网关鉴权、服务编排、缓存、数据库和消息队列，每一跳都有序列化、网络和排队开销，单接口压测看不到这些放大效应。第二，资源竞争被忽略。线上多个接口共享线程池、连接池、缓存和数据库，单独压一个接口时资源近似“独占”，测出的数字偏乐观。第三，数据分布失真。真实流量的热点商品、热点用户、冷热比例与压测构造的数据往往差别很大，缓存命中率和锁冲突随之改变。

全链路压测的目标可以归纳为三件事。其一是容量验证：在接近真实的流量模型下，确认端到端能支撑多少请求，以及每一层的水位。其二是瓶颈定位：当流量继续上升时，找出最先饱和的环节，是某个服务的线程池、数据库的连接数，还是缓存的带宽。其三是预案验证：限流、降级、扩容、切流这些手段在真实压力下是否真的生效，切换需要多长时间。

三者的关系可以用一条链路概括：

flowchart TD
    A[发压机] --> B[接入网关]
    B --> C[业务服务]
    C --> D[缓存]
    C --> E[数据库]
    C --> F[消息队列]
    F --> G[异步消费服务]

需要强调的是，全链路压测不是“把单接口压测的并发调大”，而是要在生产或准生产环境中，用带标记的流量走完整条链路，并且保证这些流量产生的数据不会污染真实业务。这就引出了后面两个基础能力：流量染色和数据隔离。

流量染色与全链路透传

流量染色是指给压测请求打上一个可识别的标记，让链路上的每个组件都能判断“这是压测流量”。没有染色，压测流量和真实流量无法区分，数据隔离、监控过滤、风险控制都无从谈起。

染色的载体需要统一约定。最常见的是 HTTP 头，例如约定一个内部头字段 X-Pressure-Flag，值为压测场景标识；RPC 调用放在框架的上下文附件里；消息队列放在消息属性中。也有团队用参数染色，在 URL 或请求体里加一个特殊字段，但这种方式容易进入业务日志、被透传到第三方，也容易被误当成业务参数，本文更推荐用元数据而不是业务参数来承载标记。

除了“是不是压测”，染色通常还需要携带场景标识和影子标识。场景标识用于区分不同压测任务，便于停止和清理；影子标识用于数据路由，例如把压测用户 ID 映射到一个保留号段，写库时据此选择影子库或影子表。三者可以合并在一个结构里，随上下文传递。

透传的难点不在入口，而在链路的每一跳。一个可用的方案是：入口过滤器解析标记，写入请求上下文；HTTP 客户端拦截器、RPC 框架过滤器负责在调用下游时继续携带；消息生产者写入消息属性，消费者在消费时恢复上下文；线程池任务提交时包装 Runnable，把上下文复制到执行线程。任何一处遗漏，标记就会在那一跳丢失，后续的写操作可能落到真实库。

数据隔离：影子库、影子表、影子缓存与消息

压测最大的风险是写脏生产数据。数据隔离要保证：压测流量读写的都是影子资源，真实用户看不到压测数据，压测结束后可以安全清理。

影子库是最彻底的方式：为压测单独准备一套数据库实例，结构与生产一致，通过染色标记在数据访问层路由。它的优点是隔离干净、清理简单；代价是资源成本高，表结构变更需要同步。实践中常用“同实例不同库”降低成本，但实例级的 CPU、IO 和连接数仍然共享，压测结果会受生产负载影响。

影子表是在同一个库内给表加统一后缀，例如订单表对应 order_shadow，由 DAO 层根据标记改写表名。它节省实例，适合中小规模；缺点是任何绕过 DAO 的 SQL、报表任务和人工查询都可能漏掉，DDL 变更也必须同时改两张表。

影子缓存同样需要路由。可以给 key 加固定前缀，或者使用独立的 Redis 实例与 DB 编号。需要特别注意本地缓存：如果压测和真实流量落在同一实例，本地缓存可能互相覆盖，最好让压测流量只进入专门的实例组。

消息隔离常被忽视。压测产生的消息必须进入独立 topic 或带独立 tag，消费组也要独立，否则真实消费者会处理压测订单，触发真实发货或通知。重试队列、死信队列、延迟消息同样要隔离。

压测开关与流量模型

压测能力必须默认关闭，按需开启。开关至少分三层：全局总开关、应用级开关、场景级开关。开关放在配置中心，客户端监听变更，所有变更留审计记录。白名单用于限定可以发起压测的来源，例如固定的发压机网段、压测账号和内部调用方；没有白名单的请求即使带了标记，也不应被当成压测流量。

流量模型决定压测能回答什么问题。固定并发（闭环）是维持一定数量的并发用户，响应变慢时实际 RPS 会下降，适合观察系统在持续压力下的稳定性和极限。固定 RPS（开环）按设定速率发请求，不因响应变慢而减速，更接近真实用户持续到达的场景，也更容易把系统压过拐点。梯度加压则按阶梯逐步提高速率，每一阶稳定运行一段时间，观察指标随压力的变化。

发压机本身也要被监控：多台机器需时钟同步，并关注 CPU、带宽、连接数和端口耗尽，否则压不上去的原因可能不在被测系统。流量比例应参照生产流量的接口分布和热点分布，而不是平均分配。

监控与瓶颈定位

压测期间要看的指标必须分层。应用层看 QPS、响应时间分位值、错误率、线程池活跃数与队列长度、数据库连接池占用、GC 停顿；数据库看 QPS、慢查询、锁等待、连接数、主从延迟；缓存看命中率、慢命令、大 key 和连接数；消息队列看堆积量和消费延迟；宿主机看 CPU、内存、磁盘 IO 与网络带宽。任何一层缺指标，瓶颈判断都会变成猜测。

所有指标都应按压测标记过滤，避免与真实流量混在一起；链路追踪同样要保留标记，才能从慢请求下钻到具体服务。定位时先看拐点出现的顺序：通常是响应时间先上升，随后线程池或连接池打满，最后错误率抬升。再看单机与集群的差异，如果只有部分实例异常，问题更可能在流量分配或个别节点。

实践中可以设置自动暂停条件，例如错误率超过 0.5%（示意值）或 P99 超过基线两倍（示意值）时暂停加压，先判断是系统瓶颈还是压测配置问题。

风险控制与演练组织

全链路压测在生产环境进行，风险控制不是附加项，而是平台的一部分。首先要保护真实流量：压测流量使用独立配额，设置全局并发上限和单场景速率上限，下游服务配置熔断与限流；一旦真实流量的延迟或错误率受到影响，应优先暂停压测。其次要有一键停止能力，停止动作包括停发压、关开关、暂停影子消息消费，并确认在途请求已结束，避免留下脏数据。

值班安排要提前确定。通常需要一名压测指挥负责节奏和决策，业务研发观察自身服务，DBA 与中间件团队负责存储和消息，运维负责发压机与网络。沟通渠道、升级路径、变更冻结窗口都要写进方案。压测当天不应同时发布业务代码或修改中间件配置。

一次完整的演练可以按下面的流程推进：

flowchart TD
    A[方案评审] --> B[准备影子资源与数据]
    B --> C[小流量预演]
    C --> D[梯度加压]
    D --> E[观测与记录]
    E --> F[停止并清理]
    F --> G[报告与复盘]

方案评审要明确压测范围、目标、流量模型、退出条件和回滚方式。预演用小流量验证染色、路由、监控和停止链路是否正常，再进入正式加压。报告至少包含目标与实际对比、瓶颈清单、容量结论、遗留风险和改进行动；复盘则要把本次发现的染色遗漏、配置错误转化为平台能力，而不是留在个人经验里。

组织协作上，平台团队负责 SDK、影子环境、发压编排和报告模板，业务团队负责接入改造与数据构造，SRE 负责稳定性保障。每场压测都应有唯一负责人，避免多头指挥。

常见坑与落地建议

染色丢失是最常见的问题，异步线程池、消息消费、定时任务和第三方回调都容易丢标记。解决方式是统一上下文包装，并在写入口做默认拒绝。异步链路则可能出现接口返回成功、后台任务却写了真实库的情况，异步任务必须从消息属性或任务参数恢复标记。

第三方依赖不能直接压，支付、短信、物流等外部服务需要挡板或只压到调用边界，同时注意对方的限流与计费规则。缓存穿透也要防：影子缓存未命中时如果直接查真实库，就等于绕过了隔离，数据访问层必须统一路由，而不能只改缓存 key。最后是清理不彻底，影子表、缓存和消息积压残留会让下一场压测互相干扰，清理要按场景标识执行并逐项核对。

小结

全链路压测平台的核心不是发压工具，而是让压测流量安全走完真实链路的一整套约束：统一染色并保证逐跳透传，用影子库、影子表、影子缓存和独立消息做数据隔离，以默认关闭的开关和白名单控制边界，再选择合适的流量模型加压。监控要分层并统一打标，风险控制要有一键停止和明确的值班安排，演练结束必须清理与复盘。把这些基础能力做扎实，容量结论才可信，压测才不会变成一次高风险的生产事故。
