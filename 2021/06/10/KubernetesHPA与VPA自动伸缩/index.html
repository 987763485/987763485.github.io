Kubernetes HPA 与 VPA 自动伸缩

本文属于《Docker 与 Kubernetes》第 26/51 篇
上一篇系列目录下一篇

集群里的 Pod 数量该给多少，是每个运维和开发都要面对的问题。给多了浪费钱，给少了半夜报警。Kubernetes 提供了两类自动伸缩手段：横向的 HPA 调整副本数，纵向的 VPA 调整单个 Pod 的 CPU 与内存请求。本文从指标链路讲起，拆开 HPA 的算法与行为控制，再看 VPA 的三个组件与重启代价，最后讨论两者冲突、与 Cluster Autoscaler 的分层配合，以及那些真正会踩的坑。

本文以 Kubernetes 1.21 与 1.22 为准。这个阶段 autoscaling/v2beta2 功能最全、用得最广，autoscaling/v2 还在推进，所以示例统一用 v2beta2，在 1.22 上可以直接跑通。

指标从哪来：metrics-server 与资源指标链路

自动伸缩的前提是“看得见”。Kubernetes 把度量拆成三条链路，理解它们的来源和延迟，比记住任何参数都重要。

第一条是资源指标（Resource Metrics），即 CPU 和内存的实际用量，由 kubelet 内置的 cAdvisor 采集，通过 Summary API 暴露。metrics-server 定期向每个 kubelet 抓取，聚合成 metrics.k8s.io 这个 API 组供 HPA 查询。它只保留最近的数据点，不做长期存储，因此不能拿来画历史曲线。

第二条是自定义指标（Custom Metrics），描述某个 Kubernetes 对象上的业务度量，比如某个 Deployment 的每秒请求数。第三条是外部指标（External Metrics），描述与集群对象无关的量，比如消息队列的积压条数、负载均衡的 QPS。后两者不在 metrics-server 的能力范围内，需要适配器把它们翻译成 custom.metrics.k8s.io 与 external.metrics.k8s.io 两个 API。

kubectl top 能出数，说明这条路是通的；若它报错而 Pod 明明在跑，多半是 metrics-server 的证书或网络问题，先把链路修好再谈伸缩。

这里有个常被忽略的延迟：cAdvisor 采样有间隔，metrics-server 抓取有周期，HPA 控制器默认每十几秒同步一次，叠加之后你看到的“当前值”可能是几十秒前的现实。关于震荡的讨论，根源都在这里。

HPA 的算法与扩缩节奏

HPA 的核心公式简单到可以用一行写出来：

期望副本数 = ceil(当前副本数 × 当前指标值 / 目标指标值)

举例来说，当前 4 个副本，每个副本的平均 CPU 利用率是 80%，目标是 50%，那么 4 × 80 / 50 = 6.4，向上取整得到 7 个副本。反过来，如果平均利用率只有 25%，4 × 25 / 50 = 2，缩到 2 个。

理解公式要注意三点。第一，参与计算的是平均值，取所有就绪 Pod 的指标均值，而不是某个最忙的 Pod。第二，向上取整意味着只要算出来超过当前值一点，就会多加一个副本，天然带扩张倾向，缩容一侧更保守。第三，公式里没有“趋势”，只看当下这一瞬间的比值，所以对突发流量反应快，对噪声也敏感。

HPA 还有内置的容差机制：算出的期望副本数与当前副本数非常接近时不动，否则指标在目标值附近轻微抖动就会让副本数来回跳。它不需要配置，但你得知道它存在，才不会奇怪利用率略高于目标为何没扩容。

averageUtilization 的分母是 Pod 的 CPU requests，不是节点的容量，也不是 limit。这一句是整篇文章最值得划重点的地方：requests 缺失或填得离谱，HPA 算出来的利用率就没有意义。利用率型指标依赖 requests，平均值型指标（averageValue）则直接比较绝对值，不受 requests 影响，选择哪种目标类型要先想清楚。

公式算出了“想扩到多少”，behavior 决定“多快到位”。1.18 之后 behavior 进入 v2beta2，用它可以把扩缩容的节奏拿捏得比较细。

policies 限制一段时间内允许变化多少，多条策略并存时由 selectPolicy 决定取哪条：Max 取变化最大者，Min 取最小者，Disabled 关掉这个方向。

stabilizationWindowSeconds 是稳定窗口，含义是“回顾过去这段时间内算出的所有期望副本数，取对当前方向最不利的那个”。扩容取最小值，缩容取最大值。上面的配置里扩容窗口是 0，算出多少就立刻扩多少，宁可多花钱也不让请求排队；缩容窗口是 300 秒，要连续五分钟都算出更低的副本数才真正缩。

这个非对称设计很实用：扩容慢的代价是用户超时，缩容慢的代价只是账单多几个数字，两者严重程度不对等。扩容窗口调小、缩容窗口调大，是绝大多数在线服务的合理默认。

但窗口也不是越大越好。设成半小时，一次真实的流量下滑要半小时后才释放资源，按量计费环境下这笔钱实打实要付。窗口应匹配业务周期：有明显潮汐规律的服务，窗口要短于波谷的持续时间，否则永远缩不下去。

多指标、自定义指标与外部指标

一个 HPA 可以同时挂多个指标，比如 CPU 利用率、每秒请求数、队列积压。规则是：每个指标各自算出自己的期望副本数，最终取其中的最大值。

取最大值而非加权平均，逻辑很直白：任一维度告急，服务就已不健康，多给副本总比少给安全。代价是只要有一个指标配得不合理（比如几乎不变化的指标配上过低阈值），它就会长期压着副本数下不来，其余指标形同虚设。上线多指标前，先把每个指标单独跑一段时间看曲线。

自定义指标与外部指标都依赖适配器。以 Prometheus 为例，集群里通常部署 Prometheus Adapter，它把 PromQL 查询的结果包装成 custom.metrics.k8s.io 或 external.metrics.k8s.io 的 API 资源，HPA 再按名字去查。适配器的定位是“翻译层”，不做采集也不做计算，只负责把已有指标体系接进聚合 API。

这条链路比资源指标长得多：应用暴露指标、Prometheus 抓取、Adapter 查询并转换、HPA 读取。每一跳都有延迟，端到端可能达到分钟级。用自定义指标做伸缩，behavior 的窗口要相应放宽，否则是拿一份过期的报表做实时决策。

VPA：把 Pod 调大调小

HPA 改的是副本数，VPA 改的是单个 Pod 的资源请求。它由三个组件构成，各管一段。

Recommender 是大脑。它读取 metrics-server 的历史用量，结合当前 Pod 的 requests，算出“按过去这段时间的用量，requests 该设成多少”，并给出目标值和上下界。

Updater 是执行者。它盯着 VPA 对象和实际 Pod，发现某个 Pod 的 requests 与建议值偏差过大，就按 updateMode 决定是否动手。这里有个 Kubernetes 的硬约束：运行中 Pod 的 resources 字段不可变（原地调整资源的能力在当时还在演进，不能当作可用特性），所以改变 requests 的唯一办法是重建 Pod。

Admission Controller 是守门人。新建 Pod 时，它按当前建议值把 requests 改写成合适的数字，保证“新来的 Pod 一开始就是对的”，这是 VPA 最温和的生效方式。

updateMode 有三个取值。Off 只给建议不改动，适合先观察，用 kubectl describe vpa 看它推荐多少。Initial 只在新 Pod 创建时应用建议，存量 Pod 不动。Auto 会驱逐偏差过大的 Pod 让它们按新配置重建，效果最直接，代价也最大。

Auto 的重启代价必须认真对待。它会在任意时刻驱逐 Pod，如果你的服务没有做好优雅退出、没有足够副本承接流量、或者启动需要预热几分钟，这次“优化”带来的抖动可能比资源浪费更难受。对有状态服务、对长连接敏感的服务，Auto 通常不是好选择。

HPA 与 VPA 的冲突

两者同时指向同一个工作负载，会打架。

设想 HPA 和 VPA 都盯着 CPU。流量上升，HPA 决定加副本；同时 VPA 观察到单 Pod 利用率升高，建议提高 requests。requests 一变，HPA 计算利用率的分母就变了，同样的实际用量算出的百分比立刻不同，HPA 于是又调副本数，两个控制器基于彼此刚改过的状态继续决策，很容易振荡。

社区的共识很明确：同一个工作负载，CPU 和内存只交给其中一个控制器。常见组合是 HPA 管副本数并用 CPU 或自定义指标，VPA 用 Off 只输出建议，由人决定是否调整 requests；或者 VPA 跑在 Initial 模式，只保证新 Pod 的起点合理。这样两者各司其职，不会互相污染输入。

与 Cluster Autoscaler 的分层配合

HPA 和 VPA 都工作在 Pod 层面，它们假设节点资源是够的。当 HPA 把副本数扩到 20，而集群没有空闲容量，多出来的 Pod 会卡在 Pending。这时候需要 Cluster Autoscaler 出场。

三者的分工是分层的：HPA 决定要几个 Pod，VPA 决定每个 Pod 要多少资源，Cluster Autoscaler 决定要几个节点。Cluster Autoscaler 观察 Pending 的 Pod，判断它们的请求能否被某个节点模板满足，然后扩节点组；缩容方向相反，它找长期利用率低、且 Pod 能被安全迁移的节点，先驱逐再回收。

分层配合的关键在于“请求”这个共同语言。HPA 扩容产生的新 Pod 带着 requests 进入调度队列，Cluster Autoscaler 读的正是这些 requests。填得虚高，节点会被过早扩出来却装不下几个 Pod；填得过低，节点看着有余量，实际一跑就 OOM，Pod 被驱逐后重新调度，形成循环。requests 是三层之间的契约，它不准，整条链路都在为错误的数字做优化。

扩容链路本身也有延迟：HPA 发现压力、创建 Pod、Pod Pending、Cluster Autoscaler 扩节点、节点注册、调度、拉镜像、应用启动，走完可能是几分钟。面对突发流量，自动伸缩救不了第一波冲击，它接的是持续压力，第一波要靠预留容量、限流和队列。

flowchart TD
    A[指标采集] --> B[HPA 计算期望副本]
    B --> C{与当前副本差异超容差?}
    C -- 否 --> D[保持不动]
    C -- 是 --> E[受 behavior 窗口约束]
    E --> F[创建或删除 Pod]
    F --> G{Pod 能否调度?}
    G -- 能 --> H[正常运行]
    G -- 否 --> I[Pending]
    I --> J[Cluster Autoscaler 扩节点]
    J --> H

震荡、冷启动与成本

把前面的线索收拢，震荡几乎都来自同一个源头：延迟加上正反馈。

指标有延迟，扩容有延迟，节点扩容还有延迟。当 HPA 终于看到副本不够，压力可能已经过去；扩出来的副本在压力消失后仍占着资源，缩容窗口又让它们多留一会儿。如果业务本身是短周期尖峰（比如每分钟一波的定时任务），伸缩系统永远在追赶过时的状态，表现就是副本数锯齿状波动，利用率却始终不高。

冷启动会放大这个问题。Java 服务启动要几十秒，镜像大的要拉几分钟，这期间新 Pod 不 Ready，既不参与均值计算也不接流量。HPA 看到 Ready 的 Pod 依然很忙，于是继续扩，等新 Pod 终于 Ready，压力早没了，结果是一堆空闲实例。应对办法：把 minReplicas 设到覆盖基线流量的水平、用就绪探针的 initialDelaySeconds 让新 Pod 晚一点进入统计、把扩容策略设得激进些以缩短追赶时间。

成本视角同样重要。自动伸缩不是“省钱开关”，它的价值是让容量跟随需求。minReplicas 太低，波谷省钱，但下次爬升要重新经历冷启动；太高，等于常年为峰值付费。合理做法是先测出基线负载需要的副本数作为下限，让伸缩只处理增量。

常见坑

requests 缺失。 没有 requests 的 Pod，HPA 的利用率型指标无法计算，控制器会报错并停止伸缩。给所有容器显式设置 requests，是使用 HPA 的前置条件，而不是可选项。

limit 与 requests 差距过大。 requests 很低、limit 很高，利用率看起来总是很低，HPA 迟迟不扩容，直到节点内存被压满、Pod 被 OOMKilled，输入严重失真。

无视指标延迟。 用自定义指标却配了很短的稳定窗口，等于拿旧数据做新决策。链路越长，窗口越要宽。

缩容过快。 缩容窗口设为零或极短，流量稍有回落就砍副本，下一波来时又要冷启动。缩容应当比扩容保守得多。

把状态服务交给 HPA。 数据库、有主从关系的中间件、需要本地持久卷的服务，副本数不是可以随便加减的量。扩出来的副本要加入集群、同步数据、重新分片，这些都不是 HPA 能理解的。这类服务适合手工扩容，或使用 Operator 层面的专用方案。

忽略 PDB 与优雅退出。 缩容时 Pod 被删除，若没有 PodDisruptionBudget 保护、没有 preStop 钩子和足够的终止宽限期，正在处理的请求会被切断。伸缩系统的正确性，一半取决于应用是否配合。

小结

HPA 的算法只有一个除法加一次向上取整，真正复杂的是周围的工程约束：指标从哪来、有多旧、requests 是否可信、扩缩节奏是否匹配业务周期。VPA 用重建 Pod 换取资源规格的准确，代价是重启，更适合以建议模式参与，而不是与 HPA 争夺同一个信号。Cluster Autoscaler 在最外层补上节点容量，三者通过 requests 这份契约衔接。

把这套东西跑稳的关键，不在于把参数调到多精细，而在于承认延迟的存在：指标是旧的，决策是滞后的，冷启动是要时间的。在这个前提下设计下限、窗口和降级手段，自动伸缩才是帮手，而不是新的故障源。
