Rust 基础数据类型

本文属于《Rust 学习路线》第 2/68 篇
上一篇系列目录下一篇

Rust 的类型系统不只描述数据长什么样，还决定了值能否被复制、何时被移动、在内存中占多少空间。许多初学阶段的编译错误，追根溯源都是对基础类型的行为不够熟悉。

本文从标量与复合类型讲起，依次说明字符串、常用集合、Copy 与移动、整数溢出与类型转换，目标是让读者能够准确选择类型，并理解编译器为什么拒绝某些写法。示例基于 Rust 1.51，均可直接在 cargo 项目中运行。

标量类型：整数、浮点、布尔与字符

Rust 是静态类型语言，每个值在编译期就有确定的类型。类型分为标量与复合两类：标量表示单个值，复合把多个值组织在一起。标量有四种，分别是整数、浮点数、布尔值和字符。

整数按有无符号分为 i 与 u 两个系列，按位宽分为 8、16、32、64、128 位。有符号整数采用补码，n 位可表示 -2 的 n-1 次方到 2 的 n-1 次方减 1；无符号整数表示 0 到 2 的 n 次方减 1。位宽一方面决定取值范围，另一方面决定溢出何时发生。

位宽 有符号 无符号 有符号范围
8 i8 u8 -128 ~ 127
16 i16 u16 -32768 ~ 32767
32 i32 u32 -2147483648 ~ 2147483647
64 i64 u64 约 -9.2e18 ~ 9.2e18
128 i128 u128 约 -1.7e38 ~ 1.7e38

此外还有 isize 与 usize，位宽跟随目标平台的指针宽度，64 位平台上就是 64 位。它们主要用于下标与长度，切片的 len() 返回 usize。跨平台代码不要假设 isize 一定是 64 位，也不要把它与 i64 混用。没有特别理由时整数默认用 i32：主流平台上运算快，取值范围也够日常使用；只有表示字节、位掩码或对接 C 接口时，才值得指定 u8、u32 这样的宽度。

字面量支持十进制、0x 十六进制、0o 八进制与 0b 二进制，可以用下划线分组，也可以直接加类型后缀。

浮点数有 f32 与 f64，对应 IEEE-754 的单精度与双精度，默认是 f64。它们只实现 PartialEq 与 PartialOrd，没有实现 Eq 与 Ord，因为 NaN 与任何值（包括自身）比较都不相等。这带来两个后果：浮点数不能直接作为 HashMap 的键，也不能用于要求全序的排序接口。

bool 只有两个值，占一个字节。char 占四个字节，表示一个 Unicode 标量值，范围是 U+0000 到 U+D7FF 以及 U+E000 到 U+10FFFF，代理项区间被排除。char 用单引号书写，字符串用双引号，两者不可混用。这里埋下一个易混点：'中' 是一个 char，占四字节，而它在 UTF-8 字符串里只占三字节。字符个数与字节数不是一回事。

复合类型：元组、数组与切片

元组长度固定、元素类型可以不同，适合临时组合几个相关的值。字段用 .0、.1 访问，也可以用 let 解构一次取出。元素为零的元组叫单元类型 ()，表示“没有有意义的返回值”，也是未写返回类型的函数的默认返回类型。

数组写作 [T; N]，要求元素同类型、长度在编译期确定。数据直接内联在所在位置，局部变量就在栈上，没有额外的堆分配，也没有指针间接寻址，因此访问很快。[0u8; 4] 是重复初始化语法，生成四个零。[u8; 4] 与 [u8; 5] 是两个不同的类型，不能互相赋值。越界访问在运行时 panic；下标是常量且越界时，编译器会直接拒绝。需要可变长度时用后文的 Vec，数组更适合固定大小的缓冲区、协议头、查找表。

切片 &[T] 借用一段连续元素，长度在编译期未知。它在运行时是一个胖指针：指向首元素的指针加上元素个数，共两个机器字。用范围语法从数组或 Vec 上取切片，范围越界同样 panic。

把参数写成 &[T] 而不是 &[T; N] 或 &Vec<T>，函数就能同时接受数组、Vec 与其他切片的引用，这是写库代码时的常见做法。字符串切片 &str 是同一机制在字节上的应用。

从布局看，数组元素彼此相邻、没有间隙，切片保证所借区间同样连续；元组字段的顺序在默认的 repr(Rust) 下并不保证，需要与 C 交换数据时才加 repr(C) 固定布局。日常业务代码不必关心这些，但“数组连续、切片是视图”这条直觉会一直有用。

字符串：String 与 &str

Rust 的字符串保证内容是合法 UTF-8，这一点由类型系统维护，不需要运行时反复校验。理解字符串的关键，是分清“谁拥有字节”和“谁在看字节”。

&str 是借用的字符串切片，本质是对一段 UTF-8 字节的只读视图，两个机器字：指针与字节长度。字符串字面量的类型是 &'static str，字节直接编入二进制的只读段，运行期间一直有效，所以不需要分配。

String 拥有数据，可以增长和修改，内部相当于一个 Vec<u8>，外加“内容始终是合法 UTF-8”的约束，三个机器字：指针、容量、长度，64 位平台上占 24 字节。修改方法都维护这条约束，例如 push_str 只接受 &str，不会让人塞入任意字节。

注意 + 运算符：它调用的是 add(self, &str)，左操作数按值传入，因此 a 被移动，之后不能再用；右操作数只借用。拼接多个字符串时 format! 更方便，它只借用参数并返回新的 String。

字符串不能用下标取字符，s[0] 无法通过编译。原因有两点：UTF-8 是变长编码，第 0 个字节未必是一个完整字符；即便取到字节，返回 u8 也不符合“取字符”的直觉。切片语法 &s[0..3] 是允许的，但两端必须落在字符边界上，写成 &s[0..2] 就会在运行时 panic。

长度也要分清：len() 返回字节数，"中文".len() 是 6，而 chars().count() 是 2。UTF-8 中 ASCII 占一字节，带附加符号的拉丁字母占两字节，常用汉字占三字节，少数符号占四字节。遍历字符用 for c in s.chars()，遍历原始字节用 s.bytes()。更复杂的字素簇标准库不处理，需要额外的 crate。

函数参数的经验法则是用 &str：它既能接收 &String（通过 Deref 强制转换），也能接收字面量，调用方不必交出所有权。需要返回或长期保存时才用 String。二者互转很直接：&s 或 s.as_str() 得到 &str，to_string() 或 String::from 得到 String。

常用集合：Vec 与 HashMap

Vec<T> 是堆上连续、可增长的数组，同样由指针、容量、长度三个字描述。元素个数超过容量时，它向分配器申请更大的空间并搬移元素，常见实现按倍数扩容。这意味着 push 可能让先前取得的元素引用失效，借用检查器会直接阻止“持有 &v[0] 的同时调用 push”这种写法。

访问元素有两条路径：v[i] 在越界时 panic，v.get(i) 返回 Option<&T>，把“可能不存在”写进类型。已知下标合理时用前者更简洁，处理外部输入时用后者更稳妥。预估规模时可以用 Vec::with_capacity 一次性分配，避免多次搬移。

HashMap<K, V> 位于 std::collections，要求键实现 Eq 与 Hash。insert 返回 Option<V>，给出被覆盖的旧值；get 返回 Option<&V>；entry 接口适合“不存在就插入”的统计场景。

默认哈希器是带随机种子的 SipHash（RandomState），能够抵抗针对哈希碰撞的拒绝服务攻击，代价是比某些非加密哈希慢，这是标准库在安全与性能之间的取舍。HashMap 的迭代顺序不保证稳定，每次运行甚至可能不同；需要有序遍历时用 BTreeMap，需要双端进出时用 VecDeque。集合元素拥有所有权，若要在集合里存放引用，必须处理生命周期，这部分留待所有权一文展开。

Copy、Clone 与移动语义

赋值和传参默认是移动：值的所有权转移给新绑定，原变量随即失效。对 String、Vec 这类拥有堆数据的类型，移动只复制栈上的几个字，堆上的字节一个也不动，代价恒定；原变量不能再使用，从而避免同一块内存被释放两次。

整数、浮点数、bool、char 以及由它们组成的元组和数组是另一套行为：赋值之后原变量仍然可用。原因是这些类型实现了 Copy，按位复制就能得到语义完整的副本，没有堆资源需要释放。Copy 是编译器的隐式行为，要求类型的所有字段都是 Copy。

Clone 则是显式的 .clone()，语义由实现者决定，通常是深拷贝。String 实现了 Clone，克隆会新分配堆内存并复制字节，代价与长度成正比。Copy 是 Clone 的子集：实现 Copy 必须先实现 Clone，惯用写法是 #[derive(Clone, Copy)]。

引用 &T 是 Copy，复制的是指针；&mut T 不是 Copy，因为同时存在两个可变引用会破坏独占规则，编译器会在需要时自动重借用。这里有一个常见困惑：对 &String 调用 clone()，得到的是 &String，因为方法解析先在 &String 上找到了 Clone 的实现；想要独立的 String，应写 s.to_string() 或 (*s).clone()。

所有权、借用与生命周期的完整规则另文讨论，本文只需建立一条直觉：栈上的纯值类型按位复制，堆上的拥有型类型默认移动，需要副本时显式克隆。

整数溢出与显式算术

运算结果超出类型的取值范围时，就发生了溢出。Rust 的处理方式取决于构建配置，这一点与很多语言不同，值得单独说明。

cargo build 与 cargo run 默认使用 debug 配置，开启溢出检查：一旦溢出立即 panic，报错信息类似 attempt to add with overflow。cargo build --release 默认关闭检查，溢出按补码回绕，例如 255u8 + 1 得到 0。也可以在 release 下用 -C overflow-checks=yes 重新打开检查。

这种设计让开发期尽早暴露错误，发布期不为每次算术付检查成本。副作用是同一段代码在两种构建下行为不同，因此不能把回绕当成可移植语义来依赖，尤其是在解析外部数据、计算金额、处理长度的时候。

除了溢出，整数除以 0 在任何构建下都会 panic，不受溢出检查开关影响。

类型转换、字面量与常量

字面量可以带类型后缀，如 42u8、3.14f32、1_000i64。没有后缀时，编译器根据上下文推断，推断不出来就用默认值：整数是 i32，浮点是 f64。推断常常来自使用处，例如把字面量放进 Vec<u64>，元素类型随之确定；collect() 这类泛型方法经常推断不出目标类型，需要显式标注。

as 是强制转换运算符，用于数值之间、指针与整数之间以及枚举到整数之间。它的特点是“总能成功”，也就意味着可能悄悄丢信息：300i32 as u8 等于 44，只保留低 8 位；-1i32 as u8 等于 255，符号位被重新解释。浮点转整数在 Rust 1.45 之后是饱和的，超出范围取边界值，NaN 转为 0；整数转浮点在数值超过 2 的 53 次方时可能丢精度。

因为 as 不报错，涉及外部数据时应优先使用 From / Into 与 TryFrom / TryInto。前者用于不会失败的转换，例如 u16 到 u32、&str 到 String；后者用于可能失败的窄化转换，返回 Result，例如 u8::try_from(300u16) 会得到错误。为自己的类型实现 From 之后，Into 会自动获得，这是编写 API 时的推荐做法。

常量与静态变量也常与类型一起出现。const 在编译期求值，可以定义在任何作用域，使用时内联展开，因此没有固定地址，也不能长期借用；它必须标注类型，命名习惯为全大写。static 有固定内存地址，整个程序运行期间都存在，取到的引用具有 'static 生命周期；可变静态变量需要 unsafe 才能访问，通常应当避免。数组长度这类编译期常量只能用 const。

最后可以用 std::mem::size_of 核对前文的描述：64 位平台上，&str 是 16 字节，String 是 24 字节，char 是 4 字节，[u8; 8] 是 8 字节。这些数字也解释了为什么大数组不宜按值传参，而应传切片。

小结

本文从标量讲到集合，重点不在罗列语法，而在建立几条稳定的判断。整数选型先看范围与符号，默认 i32 通常够用，涉及长度与下标时用 usize；char 是 Unicode 标量值，与 UTF-8 字节数无关；&str 是借用视图，String 拥有堆数据，函数参数优先用 &str。

Copy 决定赋值是否隐式复制，Clone 决定显式深拷贝；基础类型复制，堆类型移动。整数溢出在 debug 下 panic、release 下回绕，生产代码应显式选择 checked_*、wrapping_* 或 saturating_*。as 会静默截断，跨类型转换优先用 From / Into 与 TryFrom。把这些行为记牢，后续学习所有权、错误处理与模式匹配时会顺畅很多。
