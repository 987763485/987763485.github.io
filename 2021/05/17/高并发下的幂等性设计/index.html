高并发下的幂等性设计

重复请求在高并发系统里不是异常，而是常态：用户连点两次提交按钮、网关超时后自动重试、消息队列至少一次投递、运维手工补单，任何一条路径都可能让同一笔业务被执行两遍。幂等性要解决的问题，就是让这些重复落到系统里时只产生一次业务效果，而不是靠“运气好没撞上”。

本文从幂等的定义与业务边界讲起，依次讨论幂等键的设计、几种常见实现手段、分布式环境下的时序陷阱，以及重试、补偿与可观测性。读者需要具备基本的 MySQL 8.0 与 Redis 6.2 使用经验，读完后应能为下单、支付回调、消息消费等场景选出一套可以落地的方案。

幂等的定义与业务边界

数学上，幂等指 f(f(x)) = f(x)：连续应用同一个函数与只应用一次，结果相同。放到工程里可以表述为：同一个请求执行一次与执行多次，对系统状态造成的影响相同。这里强调的是“对状态的影响”，而不是“返回值相同”。第一次下单返回新建的订单号，第二次返回“已存在”并带回同一个订单号，这仍然是幂等；反过来，两次都返回“成功”却扣了两次款，就不再幂等。

判断一个操作是否需要幂等，要看它是否改变状态，以及重复执行会造成什么后果。查询类接口天然幂等，重复调用只是多消耗一点资源；真正的风险集中在写操作上：

  • 支付与退款：重复扣款、重复退款是直接的资损，必须强幂等，并且能对账。
  • 下单：同一份提交只应生成一笔订单，否则会重复占用库存、重复发货。
  • 回调通知：第三方支付、物流平台的回调普遍带重试，接收方必须容忍同一通知到达多次。
  • 消息消费：多数消息中间件提供的是至少一次投递，重复消费是设计前提而不是故障。

这里有一个常被忽略的边界：幂等不等于“去重”。同一个用户连续下两笔一模一样的订单，是两个合法请求，系统不应该把它们合并；而同一笔订单的提交被重复发送，才需要拦截。区分二者的依据是业务唯一键，而不是接口参数是否相同。因此讨论幂等之前，先要回答“什么算同一个请求”，这个问题定不下来，后面的技术选型都是空谈。

还要区分幂等与防重复提交。前端置灰按钮、提交后跳转，只能降低概率，无法给出保证：用户刷新页面、网络重试、直接调接口，都会绕过这一层。前端做体验，后端做保证，不能互相替代。

HTTP 语义与重试

HTTP 方法本身带有幂等约定：GET、PUT、DELETE 应当幂等，POST 不保证。GET 只读，重试没有副作用；PUT 用完整资源覆盖，重复提交结果一致；DELETE 重复删除通常也视为成功；POST 每次都会创建新资源，重试必须由业务层兜住。因此下单、支付这类接口即使采用 POST，也要让客户端带上幂等键，不能假设传输层会去重。

幂等键的设计

幂等实现几乎都围绕一个键：把“同一个请求”映射成同一个字符串，由存储层做唯一性判断。键设计得好，方案就简单；含糊的话，后面要用各种补丁去填。

常见的键来源有三类。

第一类是客户端生成。页面加载时向服务端申请一个 token 或 requestId，提交时原样带回。优势是在最外层拦住连点，缺点也明显：客户端可能复用旧值，可能根本不传，服务端仍要兜底。适合作为第一道防线，而不是唯一防线。

第二类是业务唯一键。订单号、支付流水号、退款单号、外部回调的通知 ID，都属于这一类。它们本身有业务含义，跨系统也能对齐，是最可靠的选择。设计时要求全局唯一、生成规则稳定，并且能反查到业务主体。

第三类是请求 ID。网关或 RPC 框架通常会生成 request id，可以拿来做兜底去重。但要注意，重试链路必须复用同一个 ID；如果每次重试都重新生成，这个 ID 就退化成日志标识，失去了去重意义。

除了来源，键的格式也要有约束：加业务前缀避免不同业务撞键，长度固定便于索引与分片，字符集限制在可打印范围，禁止把时间戳和随机数拼在一起当作“唯一键”，因为它在重试时无法复现。下面是一个简单的构造函数：

常用实现手段

实现手段可以按“谁来当裁判”分为三类：数据库唯一约束、带条件的更新语句，以及 Redis 这类外部存储。下面逐一说明。

唯一索引

这是最硬的兜底。业务表上对订单号建唯一索引，重复插入时 MySQL 返回 1062，捕获后按“已处理”返回即可。它不依赖应用逻辑，代码写错也能挡住重复数据。

去重表

一次请求要写多张表、业务表不方便加唯一键时，可以建独立的去重表，以幂等键为唯一索引，记录状态与结果摘要，并与业务写入放在同一个本地事务里，让“记录已处理”和“业务生效”一起成功或回滚。

状态机

有明确生命周期的业务，可以把“判断 + 修改”合并成带前置状态的条件更新，影响行数就是裁判结果：为 1 表示真正完成流转，为 0 表示已处理或状态不允许。

Token 预发

进入下单页时先申请 token 写入 Redis，提交时原子删除，删除成功才执行业务。关键在于用 DEL 的返回值判断，而不是先 GET 再 DEL，后者在并发下会让两个请求都读到 token。

乐观锁版本号

适合更新已有记录：读取时带出版本号，写入时作为条件，版本被改过就更新不到，由上层决定重试还是拒绝。它同时解决了幂等和并发覆盖。

Redis SETNX 与过期时间

跨服务、跨库时，用 SETNX 抢占幂等键最轻量：抢到的一方执行，没抢到的一方返回重复。TTL 必须大于最长处理时间，否则业务没结束键就过期，第二个请求会再次进入。

要注意失败时的处理：简单地把键删掉，等于把闸门重新打开，重试会再次执行业务。更稳妥的做法是把键的值改成“失败”并保留一段时间，让重试拿到明确结论。

INSERT … ON DUPLICATE KEY UPDATE

一条语句完成“插入或忽略”，避开先查后写。但 affected rows 语义容易误判：插入返回 1，更新有变化返回 2，无变化返回 0，不能只看返回值判断是否首次，通常还要读回状态。

分布式环境下的时序问题

最常见的错误是“先查再写”：查询去重表，没有记录就插入并处理。并发下两个请求同时查询，都得到“不存在”，于是都去插入、都去扣库存。数据库的唯一索引能挡住第二条插入，但如果业务逻辑在插入之前就已经执行，重复副作用已经发生。

正确的顺序是把“占位”放在业务执行之前，且占位必须原子。唯一索引插入、SETNX、条件更新都可以，关键是不要用“查询结果”作为继续执行的依据。

flowchart TD
    A[请求到达] --> B{幂等键是否已存在}
    B -- 是 --> C[返回首次结果]
    B -- 否 --> D[原子抢占幂等键]
    D -- 失败 --> C
    D -- 成功 --> E[执行业务并落库]
    E --> F{执行是否成功}
    F -- 是 --> G[标记成功并保存结果]
    F -- 否 --> H[标记失败或等待过期]

跨库、跨服务的场景还要再退一步：本地事务只能保证单库内的“去重记录 + 业务数据”原子，跨库时只能做到最终一致，需要靠对账与补偿兜底。分布式锁看似能解决一切，但有租约到期、网络分区、锁服务故障等问题，不能替代唯一约束，只能减少冲突。

消息重复消费与消费位点

消息队列的投递语义通常是至少一次，重复消费因此是常态。重复的来源有两个：生产端重试导致同一条消息被写入多次，消费端在处理成功后、提交位点前失败，重启后从旧位点重新拉取。前者靠生产端去重，后者靠消费端幂等，两者不能互相替代。

一个常见误区是拿消费位点当幂等键。位点描述“消费到哪”，同一条消息在不同重试轮次里可能变化，甚至在不同消费者之间漂移，用它去重并不可靠。正确做法仍是业务唯一键：消息体带上订单号或流水号，消费时以它去重。

位点提交的时机也影响重复概率。先提交位点再处理业务，进程崩溃会丢消息；先处理业务再提交位点，崩溃会重放。工程上普遍选择后者，再用幂等消化重放。如果位点能存进业务库，两者可以放进同一个本地事务，重复窗口会进一步缩小。

幂等与并发控制、顺序性的关系

这三个概念常被混在一起，实际解决的是不同问题。幂等保证“同一请求重复执行，效果与执行一次相同”；并发控制保证“多个不同请求同时执行，结果仍然正确”；顺序性保证“请求按业务期望的先后生效”。幂等并不等于并发安全：两个不同的下单请求携带不同的幂等键，都能通过去重，但库存只有一件时，仍然需要靠条件更新或乐观锁来防止超卖。

幂等也不能替代顺序控制。支付回调可能晚于关单请求到达，如果只用幂等键判断“是否处理过”，这笔迟到的支付仍会把已关闭的订单改成已支付。此时需要状态机做前置状态校验：只有待支付状态才允许转为已支付，其他状态一律拒绝并进入人工处理。版本号也能防止旧请求覆盖新状态。设计时把三者分开评估，比笼统地说“加个幂等”要可靠得多。

失败重试、补偿与可观测性

重试必须复用同一个幂等键，否则每次重试都是新请求，幂等形同虚设。重试要有上限和退避，对参数错误、余额不足这类不可恢复的失败直接返回，不要浪费次数。补偿针对“卡在处理中”的记录：定时任务扫描超时记录，反查下游真实状态，再决定置为成功还是失败。

可观测性决定问题能否被及时发现。至少要有三类信号：按业务类型统计的重复请求计数，用于判断上游是否在异常重试；幂等冲突日志，记录键、首次请求 ID 与当前请求 ID，方便定位“谁先到”；处理中记录的堆积量与最老年龄，用于发现卡死。指标可以统一成 idem_duplicate_total、idem_processing_age_seconds 这类形式，接入现有监控即可。

常见坑

  • 幂等键复用或重新生成：不同业务共用命名空间会互相误判；页面刷新后重新申请键，重复提交反而拦不住。
  • 过期时间拍脑袋：短于重试窗口会重复，过长会撑大存储，建议覆盖最大重试周期再加一个对账周期。
  • 跨库唯一性失效：分库分表之后唯一索引只在单表内生效，需要全局 ID 或独立的去重表。
  • 异步落库二次重复：同步链路去重通过，异步消费者又处理一次，异步链路必须透传同一个幂等键。
  • 把“处理中”当“已完成”：首次请求还在执行，第二次直接返回成功，用户看到成功但业务并没有生效。

小结

幂等本质上是一个业务约束，先定义“什么算同一个请求”，再谈技术手段。实现上优先依赖唯一索引与条件更新这类数据库裁判，Redis 抢占适合做前置拦截，但不能替代最终约束。并发、顺序与幂等是三个正交的问题，需要分别设计。最后，重试复用同一个键、补偿覆盖处理中状态、监控能看见重复与堆积，这套组合才算完整。
