分布式限流设计与实现

本文属于《Go 微服务架构》第 23/35 篇
上一篇系列目录下一篇

单机限流只能约束一个进程，而线上服务通常以多副本运行，还会随负载弹性伸缩，同一份配额被复制成 N 份之后，集群的实际放行量往往是配置值的数倍。更麻烦的是流量在实例之间并不均匀，长连接、缓存命中率差异、滚动发布都会让某一台机器先被打满。本文讨论把限流从单进程搬到集群层面时遇到的真实问题：几种主流架构各自的代价、Redis 与 Lua 组合的工程要点、配额预分配的误差从哪里来，以及热点分片、分层限流、降级与多活配额该怎么处理。读者应已了解令牌桶与漏桶的基本原理，本文不重复算法推导，只讲分布式环境下如何把它们拼成一套能上生产的系统。

为什么单机限流不够

单机限流的语义很清晰：进程内一个计数器或令牌桶，超过阈值就拒绝。它的隐含前提是“阈值等于这台机器能承受的量”，而这个前提在集群里几乎不成立。

副本数把阈值悄悄放大

假设某个接口单机配置每秒 100 次（示意值），部署 8 个副本，集群总放行量就是每秒 800 次，可配置者的本意往往是“全局每秒 100 次”。副本数一变，语义就变了：扩缩容把副本从 8 个拉到 20 个，上限跟着涨了一倍多，而下游数据库不会因为上游多开了几个 Pod 就多出连接数。单机阈值的乘积是随部署形态漂移的量，不是业务常量，它会在扩容当天失效，也会在缩容后变得保守。

流量不均让平均值失去意义

即使总量被控制住，分布也未必均匀。负载均衡器按连接数或轮询分发，长连接场景下新实例常常分不到流量；本地缓存命中率不同，同样的请求在不同实例上的耗时能差出几倍；某台机器恰好碰上宿主机上的干扰，处理能力下降，却仍被分到同样多的请求。结果是整体利用率还不到一半，个别实例已经开始拒绝，监控上表现为“总量没超，但用户看到了 503”。

阈值究竟在保护谁

更根本的问题是：限流是为了保护自己，还是保护下游？如果是前者，单机限流够用；但多数场景是后者，比如数据库、第三方支付接口、共享的缓存集群，这些依赖看到的是所有副本之和。一旦被保护的对象在进程之外，配额就必须是全局的，否则每个副本都认为自己在安全线以内，合起来却把下游压垮。

由此得出分布式限流的三条基本要求：配额是集群级的一个数；消耗要足够快，不能给每个请求叠加一次跨网络往返；配额系统本身不能成为新的单点。后面的架构选择，都是在这三条之间做权衡。

四种架构形态与取舍

把配额搬到集群上，常见做法有四类。它们不是互斥的，很多系统会同时用两三种，分别负责不同的层级。

flowchart TD
    A[请求到达] --> B{网关全局限流}
    B -->|超限| R1[直接拒绝]
    B -->|通过| C{边车本地限流}
    C -->|超限| R2[本地快速拒绝]
    C -->|通过| D[业务实例]
    D --> E{本地令牌桶}
    E -->|有配额| F[放行]
    E -->|无配额| G[向配额中心批量领取]
    G --> H[(Redis / Etcd)]
    H --> E
    F --> I[调用下游]

集中式：每次判断都问一次中心

最直接的做法是把计数器放在 Redis 或 Etcd 里，每个请求执行一次原子操作。语义准确，配额不会超发；代价是每个请求多一次网络往返，Redis 的延迟直接叠到接口延迟上，Redis 一抖整条链路跟着抖。

Etcd 用 Raft 保证强一致，写入要多数派确认，延迟比 Redis 高一个量级，通常只用于配置下发或低频配额结算，不适合放在请求主路径上。集中式更适合每日调用次数这类低频但要求精确的接口；在预分配方案里，它则退居为“配额池”。

配额预分配：本地桶加周期领取

思路是把全局配额切成小块，每个实例周期性地从中心领一批令牌放进本地桶，请求只在本地扣减，用完再领。这样绝大多数请求不产生网络调用，延迟与单机限流一致；代价是精度下降，集群里可能同时存在若干实例手里的“余粮”，放行量会略微超过全局配额。这是生产上最常见的选择：允许几个百分点的超发，远好过让 Redis 进入关键路径；后文会讨论怎么控制这个误差。

网关统一限流

如果所有入口流量都经过网关，把限流放在这里是自然的选择：它能看到完整的请求上下文，可以在路由匹配之后按接口、按租户、按来源 IP 分别计数，拒绝也发生得足够早。代价是网关自己要扛住全部流量，限流逻辑必须足够轻；而且它只管得住南北向流量，东西向调用需要另一层。网关侧通常分两级：进程内的本地桶做粗筛，中心侧只处理跨实例的总额与需要精确控制的场景。

边车限流

服务网格化之后，另一种位置出现了：在每个业务 Pod 旁边放一个边车代理，由它承担本地限流和配额领取。业务代码不必引入限流库，策略通过控制面下发；边车与业务同机部署，网络开销接近于零。Envoy 的本地限流过滤器加外部 rate limit 服务就是典型组合。

代价是运维复杂度：策略下发有延迟，边车开销要计入每个 Pod，排查链路更长。它适合已全面网格化、并希望把策略与代码解耦的团队；只有几个接口要限流时，引入边车并不划算。

四种形态的对比可以粗略归纳如下（数值为示意值，实际以压测为准）：

形态 判断延迟 精度 主要风险
集中式 增加一次 RPC 严格 中心抖动即全局抖动
配额预分配 基本无额外延迟 有超发 误差与配额泄漏
网关统一 一次本地判断 视实现 网关成为瓶颈
边车 一次本地判断 视实现 策略下发延迟

选择的原则并不复杂：把精确性要求高的放到中心，把吞吐要求高的放到本地，让中心只承担“发钱”而不是“记账”的职责，系统就稳了。

Redis + Lua：把判断放进服务端

集中式方案的关键不是 Redis 本身，而是“读取、判断、写入”必须原子完成。客户端先 GET 再 SET，两个请求会读到同一个旧值，各自认为还有余量，配额就这样被超发。Redis 单线程执行命令，天然适合把这三步打包；Lua 脚本经 EVAL 执行时，内部命令视为一个整体，中间不会被其他客户端插入。

滑动窗口的 key 设计

用 ZSET 实现滑动窗口是最常见的手法：score 存毫秒时间戳，member 存请求唯一标识，每次请求先清掉窗口外的成员，再数一遍集合大小，未超限才写入。三个操作放进一个脚本，就是原子的。

这段脚本有几个细节值得展开。

时间来源方面，now 由客户端传入，而不是在脚本里调用 redis.call(‘TIME’)：脚本里读服务器时间会削弱确定性，主从复制与集群模式下行为更复杂，而业务记录与日志对齐用的往往是应用时间。代价是客户端时钟不准会直接污染窗口，后文“常见坑”还会提到。

member 的唯一性直接决定计数是否正确。用固定字符串做 member，ZADD 会反复覆盖同一个成员，计数永远涨不上去，看起来配了阈值实际完全不生效；必须用请求 id、UUID 或者“时间戳加自增序号”。代价是集合元素数量等于窗口内请求数，高 QPS 加长窗口时内存占用可观。

key 的过期必须显式设置。ZSET 成员不会单独过期，清理要等整个 key 被删除；只在创建时设置一次，后续请求不断刷新，key 会一直存在。反过来，过期太短，窗口没走完 key 就消失，计数清零，限流形同虚设；经验是窗口长度再加一点冗余。

令牌桶与惰性补充

令牌桶在分布式下要解决的新问题是“谁来计算这段时间该补多少令牌”。常见做法是把上次补充的时间戳和当前令牌数一起存进 hash，每次请求先按时间差补令牌，再判断能否扣减。

注意拒绝分支里也要写回时间戳。只在放行时更新，被拒绝的请求不推进时间，下个请求算出的 delta 偏大，补出一批本不该有的令牌，阈值被变相放宽。这类“只在成功路径更新状态”的写法非常常见，也是压测结果对不上的典型原因。

过期时间的算法同理：桶从满到空需要 burst / rate 秒，key 的存活时间至少要覆盖这个长度，否则一段时间没有请求后 key 被删，下次从满桶开始，等于免费放行一批。

脚本缓存与集群限制

EVAL 每次都要把脚本文本发给 Redis 重新解析，脚本长了既费带宽也费 CPU。生产上应该先 SCRIPT LOAD 拿到 sha1，之后用 EVALSHA 调用；返回 NOSCRIPT（实例重启或脚本被清掉）时再退回 EVAL 并更新缓存。

在 Go 里通常封装成 client，启动时加载一次并把 sha1 存在内存，调用失败时区分 NOSCRIPT 与其他错误。两点提醒：EVALSHA 传入的 key 必须与脚本声明的 KEYS 一致；集群模式下脚本访问的多个 key 必须同 slot，否则报 CROSSSLOT。热点分片一节会回到这个问题。

此外，脚本必须保证确定性，同一份脚本在不同副本上的执行结果要一致，否则主从数据会分歧；至于脚本阻塞，后文“常见坑”会单独说。

配额预分配：批量、租约与误差

预分配把“记账”留在本地，把“发钱”交给中心。它能不能用，取决于三个参数怎么定：一次领多少、多久领一次、实例上下线时怎么回收。

批量大小与误差上界

设全局配额为 Q，活跃实例数为 N，领取周期为 T 秒，每个实例每次领取的额度约为 Q × T / N。每个实例最多压着一个批次的余量，所以集群最多超发 N × batch，相对误差约为 T（以秒计）。示意值：全局 10000 QPS、20 个实例、每 100 毫秒领一次、每批 50 个，最坏瞬时放行量约 11000，超发一成。

公式的结论很直观：误差与周期成正比、与批量成反比，两者其实是同一参数的两面。周期调短，误差降下来，中心压力变成 N / T，20 个实例每 100 毫秒一次就是每秒 200 次调用，对 Redis 毫无压力；周期调长，中心轻松，但实例在突发下要等更久才能补上额度，表现为“配了 500 QPS 却只跑到 300”。

取值上建议把误差控制在 5% 到 10%，同时保证 batch 大于一个请求批次，否则一次批量请求就能把本地桶打空，退化成每个请求跨网络。有明显突发的接口，本地桶上限可取 batch 的两三倍；要求平滑的接口，上限就等于 batch。

实例上下线与配额泄漏

中心必须知道当前有多少实例，否则 Q/N 算不出来。信息源有两种：实例用带 TTL 的 key 注册存活，中心扫描统计；或者直接读注册中心、K8s Endpoints，配额中心 watch 变更。前者简单，但实例被 kill -9 后 key 要等 TTL 才消失；后者准确，却引入了对控制面的依赖。

真正麻烦的是“配额泄漏”：实例崩溃前领走一批令牌，还没花掉就消失了。这部分额度既没在本地被消费，也没回到池子，只能等下个周期重新计算时被动稀释。频繁发布或实例被驱逐时泄漏会累积，表现为“阈值没到，放行量却偏低”。

缓解手段有三个。一是按期望副本数而不是存活数切分，宁可保守，也不让基数随实例数抖动。二是中心维护可回收的额度池，心跳带上剩余量并据此调整分发，代价是实现变复杂。三是接受泄漏，用监控兜底：把“中心剩余”和“本地已发放未消费”都打成指标，偏差超阈值就告警。

滚动发布是容易忽略的场景。新旧 Pod 并存的几分钟里实例数接近翻倍：按存活数分配，每个实例的 batch 减半，补额变慢，容易误限流；按固定副本数分配，总量就会超发。多数团队选后者，在发布窗口内接受短暂超发，因为误杀正常流量的代价更大。

时钟漂移与单调时钟

本地桶按时间差补令牌，若用墙上时钟，NTP 校时回拨会让 delta 变负，令牌被扣掉；时间向前跳则可能一次补满整个桶，瞬间放行一批。Go 的 time.Time 携带单调时钟读数，用 Sub 或 time.Since 计算间隔不受校时影响，这是本地桶必须用单调时钟的原因。

回到时钟漂移本身。跨机器的漂移没有这么容易消除：两个实例的时钟差几百毫秒，意味着在同一秒内一个已经补充了令牌、另一个还没有，短窗口（比如每秒重置的固定窗口）会因此出现放行量的波动。实践中的做法是：本地判断一律基于单调时钟的相对间隔，不依赖“整秒对齐”；只有统计和报表使用墙上时钟。固定窗口的分布式实现则要接受这一点，或者干脆改用滑动窗口加相对时间。

热点分片与分层限流

单 key 的限流器在两种情况下会失效：key 太热，或者粒度太粗。前者是性能问题，后者是语义问题。

按 key 哈希到多个桶

一个接口每秒几十万次请求，全打在同一 Redis key 上，即使集群有多个分片，这个 key 也只落在某一个节点，单节点 CPU 先到瓶颈。解决办法是把逻辑桶拆成 M 个物理桶，请求按 key（用户 id、设备号、请求 id 都行）哈希到其中一个，每个桶的阈值是总阈值的 1/M。

flowchart TD
    R[请求] --> H{uid 哈希取模 4}
    H --> B0[桶 0 阈值 2500]
    H --> B1[桶 1 阈值 2500]
    H --> B2[桶 2 阈值 2500]
    H --> B3[桶 3 阈值 2500]

这里有两个代价要认真对待。一是精度损失：哈希均匀时每个桶承担约 1/M 的流量，统计意义上可以接受，但流量倾斜时（比如某个大客户占了一半请求）会有一个桶先满而其余桶有余量，表现为“总量没到却开始拒绝”。二是 key 的基数：按用户维度分片，桶的数量等于用户数乘以分片数，内存与管理成本都上去了。

一个折中的做法是两级：全局层用粗粒度的分片桶控制总量，用户层用小的本地 LRU 桶控制个体，只有触发全局阈值时才去查中心。这样常态下几乎没有中心调用，异常时才有额外开销。

还要注意集群模式下的 slot 约束。脚本若同时访问“当前桶”和“全局余量”两个 key，它们必须在同一个 slot，否则报 CROSSSLOT。常见做法是用 hash tag，把 key 写成 rate:{order}:0 与 rate:{order}:total，花括号内的部分决定 slot。

全局、租户、接口、用户四层

真实的系统很少只有一层限流，常见的分层是这样：

层级 作用 典型实现
全局 保护整个集群或整个下游 预分配加中心池
租户 防止单个客户挤占资源 按 tenant 分片的滑动窗口
接口 保护单个下游依赖 本地令牌桶加周期领取
用户 防刷、防爬 本地 LRU 计数，必要时上中心

四层不是串行叠加，而是短路关系：任意一层拒绝就立即返回，顺序按成本从低到高排。全局层如果每次都要查中心，就不该放在最前面；通常是本地层先拦，放行之后再校验中心侧的租户额度。

层与层之间的配额关系要显式设计：全局配额应大于等于各租户配额之和，否则租户层永远打不满；租户配额之和又应小于下游真实容量，留出缓冲。这些数字靠人工维护迟早会不一致，稳妥的做法是写进同一份配置统一下发，并在发布时校验，租户配额之和超过全局配额就拒绝发布。

拒绝、排队与降级

超限之后的动作，比限流本身更容易出问题。

最直接的是拒绝，返回 429 或业务自定义错误码，并带上 Retry-After 提示多久后重试。这里有个细节：不要返回 500，也不要用看起来像系统故障的错误码，否则客户端的重试策略会把限流放大成雪崩。429 语义明确，配合 Retry-After 能让守规矩的客户端自动退避。

排队适合对延迟不敏感、对成功率敏感的场景，比如异步任务提交、报表生成：一个有界队列加超时，队列满就拒绝，等待超时也拒绝。最大的风险是把上游超时拖长，请求在队列里等了两秒才被处理，客户端早就断了，服务端还在为一个没人要的结果消耗资源。所以排队必须配合截止时间，入队记 deadline，出队先检查是否过期。

降级返回是另一条路：不拒绝，返回简化的结果。比如推荐接口返回热门榜单而不是个性化结果，商品详情页隐藏实时库存只显示“有货”。前提是调用方能接受这种结果，并且有办法区分正常与降级数据，通常在响应里加标记字段。

三种策略往往组合使用，按业务重要性分级：核心链路超限时排队或短暂等待，非核心链路直接降级返回缓存，纯附加功能直接拒绝。分级依据不是技术指标，而是“丢掉这个请求会造成多大业务损失”，这一点必须在设计阶段和业务方对齐。

跨机房与多活下的全局配额

单机房内做全局配额已经不容易，多活之后问题会放大一个量级。

如果每个机房独立计算配额，两个机房各按 100% 配置，合起来就是 200%，下游压力翻倍。如果所有机房共享一个中心配额，跨机房调用要走专线，延迟和可用性都成问题。常见的折中是按比例静态切分：全局 10000，两个机房各 5000，比例写进配置。优点是简单、不依赖跨机房调用；缺点是容量无法动态调度，一个机房流量涨了只能眼看着拒绝，另一个还有一半额度闲着。进阶做法是动态借调：每个机房周期性上报实际使用量，中心按“保底份额加弹性借用”重新分配，周期通常是分钟级，避免频繁变更引起震荡。

无论哪种方式，都要面对一个现实：机房之间不可能强一致。CAP 的选择在这里很明确，限流是从属功能，宁可短暂不一致也不能让配额中心拖垮业务。所以多活下的配额通常是“最终一致加本地保底”：本地永远保留一个最小可用额度，即使与中心失联也能继续服务，只是额度收缩到保守值。这个保底额度是整套系统最后的安全垫。

可观测性与压测验证

限流系统最怕的不是不生效，而是“看起来生效了，实际没有”。判断它是否真的在工作，至少需要几个指标。

一是放行量与拒绝量，按层级、接口、租户分别打点。只有总量不够，全局层放行、租户层拒绝和本地层拒绝代表完全不同的问题。二是本地桶水位，即 tokens / burst：长期贴地说明配额不够，长期接近满分说明给多了。三是中心侧剩余额度与调用延迟，前者反映池子是否领空，后者反映中心是否健康。四是配额偏差，即“中心已发放”与“本地已消费”的差值，它直接对应前文的泄漏。

日志要克制：限流是高频事件，每条拒绝都打日志，系统被打崩时会把日志一起打崩；按 key 每分钟汇总一次，只在首次触发和恢复时各打一条明细即可。

压测是验证限流效果的唯一可靠手段。一是流量要能命中限流器，很多脚本直接打后端接口，绕过了网关和边车，结论没有意义。二是要测边界而不是峰值，把目标 QPS 设为阈值的 90%、100%、120%，看放行量是否贴着阈值走。三是要测异常路径：杀掉一个 Redis 节点、制造一次网络分区、让某个实例的时钟偏几百毫秒，看系统是退化成保守限流还是直接放行。很多方案在正常路径上表现完美，一遇依赖故障就变成“全部放行”，这比不做限流更危险。

常见坑清单

Redis 单点与延迟。所有实例共用一个 Redis 主节点，节点抖动时所有判断一起超时。如果超时处理是“失败则放行”，抖动期间等于完全不限流；如果是“失败则拒绝”，则等于全站故障。比较稳妥的策略是失败时退回本地桶的保守额度，既不放大流量也不至于全拒。

Lua 脚本阻塞。脚本里做 ZRANGE 取全量成员、循环遍历几千个 key、对大集合排序，都会让 Redis 单线程卡住，影响的不仅是一个接口。脚本只应做常数级操作，集合大小要有上限。

时间回拨。前面讲过单调时钟，这里补充更隐蔽的一种：即使本地用单调时钟，传给 Redis 的 now 仍是墙上时钟。某台机器的时钟被回拨后，它写入的 score 会小于窗口下界，被 ZREMRANGEBYSCORE 立刻清掉，计数偏低。缓解办法是客户端对 now 做单调性修正，保证同一进程发出的时间戳不减。

配额泄漏。实例异常退出、发布时旧 Pod 被强杀、领取成功但写本地桶之前 panic，都会造成额度丢失。监控上表现为“中心发放量远大于实际放行量”，需要定期对账。

限流键基数爆炸。按用户 id、设备 id、请求参数做 key，基数可能上千万，Redis 内存被打满，还会触发淘汰把正在使用的计数 key 挤掉。必须给这类 key 设短 TTL，并优先用本地 LRU 承载，中心只处理聚合维度。

阈值拍脑袋。限流值来自容量评估与压测基线，一个没有数据支撑的阈值，只是给团队一种“我们做了保护”的心理安慰。上线前至少要回答：这个阈值对应下游多少连接、多长的排队时间。

小结

单机限流的问题不在算法，而在阈值会随副本数漂移、随流量分布失真。分布式限流要做的，是把“每台机器的能力”变成“整个集群的权利”，并在精度、延迟、可用性之间选一个合适的点。

集中式精度最高，但把中心放进了关键路径；配额预分配把网络开销挪出请求路径，代价是可估算的超发；网关与边车是部署位置的选择，不改变算法本身。Redis 加 Lua 的要点集中在原子性、时间来源、key 设计与过期策略，脚本缓存和 slot 约束属于工程细节。

预分配的三个参数决定了误差与补额速度，单调时钟和租约回收决定了异常情况下的行为；热点分片解决单 key 瓶颈，分层限流解决粒度问题，多活配额则要接受最终一致并保留本地保底。

实践建议只有一句：先把可观测性做起来，再谈阈值调优。没有放行量、拒绝量、桶水位和配额偏差这四组指标，任何限流参数都只是猜测。
