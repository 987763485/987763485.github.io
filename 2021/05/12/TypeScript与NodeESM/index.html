TypeScript 与 Node ESM

本文属于《TypeScript 学习路线》第 20/74 篇
上一篇系列目录下一篇

把一份 TypeScript 工程从 CommonJS 迁到 ESM，往往不是改几行 import 就能收工的事：编译器还在按旧规则找文件，Node 已经在按新规则解析路径，两套规则各说各话的时候，报错信息通常只有一句干巴巴的 ERR_MODULE_NOT_FOUND。本文从两种模块系统的加载语义讲起，梳理 2021 年前后 Node 与 TypeScript 对 ESM 的支持边界，再把 exports 字段、扩展名规则、互操作开关和双包问题逐个拆开，最后给出一条可以分步执行的迁移路线。

需要说明的是，本文讨论的是”模块如何被找到、如何被加载”这一层，而不是语法层面的 import 与 export 写法。理解了加载器的工作方式，很多看起来莫名其妙的报错就会变成可预期的结果；反过来，只记住几条配置模板，换个目录结构就会重新踩坑。

从加载方式看两套模块系统

CommonJS 的加载是同步的。require() 被调用时，Node 沿着文件系统逐级查找目标文件，读入源码，包进一个函数里立即执行，执行完成后把 module.exports 返回给调用方。整个过程阻塞在当前调用栈上，没有任何异步缝隙。这个设计在服务端很自然：文件就在本地磁盘上，读一个文件的时间可以接受，而且同步加载让”拿到的东西一定是执行完的”这件事变得确定。

ESM 的加载是异步的，而且要分三个阶段。第一阶段是构造，解析器读完整个模块图，把每个模块的导入导出关系记录下来，此时模块代码一行都没有执行；第二阶段是实例化，为每个模块建立内存中的绑定关系，导入方拿到的是指向导出方的活绑定，而不是值的拷贝；第三阶段才是求值，按依赖图的拓扑顺序执行模块体。三个阶段分开，意味着模块图必须在执行之前就完整可知，这也是 ESM 要求静态结构的原因。

静态分析带来的直接后果是：import 声明只能出现在顶层，模块说明符必须是字符串字面量，不能拼接变量，也不能放在 if 分支里。打包器因此可以在不执行代码的情况下构建完整的依赖图，做 tree-shaking、做预加载、做循环依赖的静态检测。CommonJS 做不到这些，因为 require('./' + name) 这种写法在运行时才知道目标是谁，工具只能保守地把整个目录都算进依赖。

循环依赖的表现差异最能说明问题。CommonJS 遇到循环时，会先返回一个”半成品”的 module.exports，等对方执行完再补上后面的属性。于是代码里经常出现这样的现象：模块 A 在顶层读 require('./b').foo，拿到的是 undefined，因为 B 还没执行到赋值那一行；但如果把读取推迟到函数体内，等真正调用时 B 早就执行完了，值又是对的。这种”取决于执行时机”的行为很难靠阅读代码判断。

ESM 的处理方式不同。因为实例化阶段已经建立了所有绑定，循环依赖不会产生 undefined，导入方看到的是活绑定，只要在求值时对方已经完成初始化，访问就是合法的。真正的风险变成了暂时性死区：如果 A 在模块顶层就使用从 B 导入的 const，而 B 此时还没求值，就会抛出 ReferenceError。两者的错误形态不一样，但根源相同——循环依赖本身就意味着初始化顺序存在歧义，能消除就应该消除。

flowchart TD
  A[入口模块] --> B[构造: 解析整个模块图]
  B --> C[实例化: 建立活绑定]
  C --> D[求值: 按拓扑序执行]
  D --> E[导出可用]

这张图值得记住，因为它解释了后面很多现象。比如为什么 ESM 里不能条件性地 import，为什么顶层 await 是可行的（求值阶段本身就在异步上下文里），以及为什么动态 import() 会成为绕开静态限制的唯一出口。

Node 的 ESM 支持现状

Node 对 ESM 的支持不是一次性完成的，而是从实验开关一路走到默认可用。Node 12.17 之后不再需要 --experimental-modules 开关，但官方文档仍然标注为实验性；到 Node 14 与 16，这套机制已经能支撑生产项目，细节还在补齐。2021 年 4 月 Node 16 发布，把此前散落在各个小版本里的修正收了进来，也让”要不要迁移”从技术尝鲜变成了工程排期问题。

决定一个 .js 文件按哪种方式解析的，不是代码内容，而是它所在包的 package.json。Node 从被加载文件所在目录向上查找，遇到第一个 package.json 就停下，读取其中的 type 字段：值为 "module" 时，该包内所有 .js 都当 ESM 处理；值为 "commonjs" 或者字段缺失时，都当 CommonJS 处理。这个作用域叫包作用域，粒度是整个包，而不是单个目录。

两个扩展名的优先级高于 type 字段。.mjs 永远是 ESM，.cjs 永远是 CommonJS，与所在包的声明无关。这条规则在迁移期非常有用：一个已经声明 "type": "module" 的包里，仍然可以把个别老文件改名为 .cjs 继续用 require 加载，不必为了几个文件回退整个包。

type 字段一旦改动，影响的是整个包内所有 .js 文件，包括测试文件、构建脚本和配置文件。很多项目第一次尝试迁移时只改了源码，结果 npm test 直接报 Cannot use import statement outside a module——因为测试文件还在按 CommonJS 解析，而它 import 了 ESM 模块。这类问题的根源不在代码，而在于包作用域的边界没有想清楚。

在加载行为上还有几处差异值得提前知道。ESM 模块顶层的 this 是 undefined，而 CommonJS 里是 module.exports；__dirname、__filename、require、module、exports 这几个名字在 ESM 里都不存在，不是被遮蔽，而是根本没有提供。这些缺失会在迁移时集中爆发，后文会给出替代写法。

顶层 await 是 ESM 独有的能力。CommonJS 的模块体是同步执行的，不可能等待；ESM 的求值阶段本身就在异步上下文里，所以在模块顶层直接 await 一个 Promise 是合法的。这个能力在 Node 14 后期出现，到 Node 16 才不需要额外开关，使用时要注意运行时版本下限。

最后是一条硬限制：在 2021 年的 Node 里，require() 不能加载 ESM 模块，会抛出 ERR_REQUIRE_ESM。反过来，ESM 可以通过 import() 动态加载 CommonJS 模块，因为 import() 返回 Promise，内部走的是 ESM 加载器，而 CommonJS 被当作只有一个默认导出的特殊模块处理。这个不对称决定了迁移只能从”被依赖的叶子模块”开始，而不是从入口开始。

exports 字段：条件导出与子路径封装

exports 字段是 Node 为 ESM 设计的包入口声明，也是近几年包生态里变化最大的一块。它取代了 main 的单一入口模型，允许一个包针对不同的加载方式和运行环境暴露不同的文件，同时把内部结构封起来。

最简单的形式是给一个字符串，效果类似 main，但语义更严格：它同时约束 import 和 require 两条路径。

真正的能力在对象形式。exports 的值可以按条件分组，Node 按书写顺序从上到下匹配，取第一个命中的分支。这个”顺序敏感”是很多诡异问题的来源：如果把 default 写在前面，后面所有条件都永远不会生效。

import 与 require 是最常用的两个条件，分别对应 ESM 加载器和 CommonJS 加载器。node 条件表示”当前在 Node 环境”，可以用来和浏览器构建区分；default 是兜底，必须放在最后。条件名不是固定枚举，Node 还支持通过 --conditions 传入自定义条件，一些库借此区分开发与生产构建。

exports 还有一个容易被忽视的作用：封装。一旦包声明了 exports，所有没有列出的子路径都不再可访问，require('date-utils/dist/internal/helper') 会直接报 ERR_PACKAGE_PATH_NOT_EXPORTED。这对库作者是好事，可以放心重构内部目录；对使用者则是破坏性变更，因为它切断了所有深路径导入。发布带 exports 的新版本时，最好把常用的深路径显式映射出来，给下游留出过渡期。

ESM 的路径规则：为什么扩展名不能省

CommonJS 的解析器相当宽容。require('./utils') 会依次尝试 ./utils.js、./utils.json、./utils.node，再尝试把 ./utils 当目录，读其中的 package.json 的 main，最后尝试 ./utils/index.js。这套”多试几次总能找到”的策略在本地开发时很省事，代价是每次加载都要做多次文件系统探测，而且同一个说明符在不同目录下可能指向不同文件。

ESM 把这条路堵死了。相对说明符必须以 ./ 或 ../ 开头，并且必须写全扩展名，解析器不做任何猜测。import './utils' 不会去找 utils.js，它会认为你要加载的就是一个名为 utils 的文件，找不到就报 ERR_MODULE_NOT_FOUND。目录导入同样不支持，import './helpers' 即使 helpers 目录下有 index.js 也会失败，报 ERR_UNSUPPORTED_DIR_IMPORT。

这个设计是刻意的。ESM 的说明符被当作 URL 处理，URL 没有”猜扩展名”的概念；补全规则一旦存在，服务端和浏览器、Node 和打包器之间就必然出现分歧。宁可让写代码的人多打四个字符，也不让解析行为依赖运行环境。

去掉猜测之后，裸说明符的查找反而简单了。import 'lodash' 仍然会沿目录向上逐级查找 node_modules，但找到包之后，入口完全由 package.json 的 exports 或 main 决定，不再尝试 lodash.js 之类的变体。NODE_PATH 环境变量在 ESM 里也不生效，因为它本质上是在扩展”去哪儿找”的搜索路径，与 ESM 的确定性目标冲突。

说明符是 URL，还带来几个细节。import.meta.url 给出当前模块的 file:// 地址，拼接相对路径时要用 new URL('./data.json', import.meta.url)，直接做字符串拼接会得到错误的路径。文件名里包含 # 或 ? 时会被当成 URL 的片段与查询部分，需要通过百分号编码转义。在大小写敏感的文件系统上，大小写不一致也会直接失败，而 CommonJS 在某些平台上曾经”碰巧能跑”。

对迁移者来说，这些规则意味着一项机械但无法回避的工作：把所有省略扩展名的相对导入补全。一个有几百个文件的项目，手工改一遍既枯燥又容易漏，比较务实的做法是先用脚本批量处理，再靠编译与测试兜底。

TypeScript 的 module 与 moduleResolution

TypeScript 里有两个容易混淆的选项。module 决定输出什么格式的模块代码，moduleResolution 决定输入的说明符如何解析成文件。前者影响产物，后者影响类型检查时能不能找到声明，两者必须与运行时的期望对齐，否则就会出现”编译通过、运行报错”。

在 2021 年 5 月的 TypeScript 4.2 与即将发布的 4.3 里，moduleResolution 的可选值主要是 classic 与 node。classic 是早期为浏览器场景设计的，与 Node 的行为差得远，实际项目基本不用。node 则完整复刻了 CommonJS 的查找逻辑：允许省略扩展名、允许目录导入、允许读 index.ts。

问题就出在这里。把 module 设为 esnext、moduleResolution 保持 node，TypeScript 会用宽松规则找到文件，然后把 import './utils' 原样输出到产物里。产物交给 Node 的 ESM 加载器，宽松规则不复存在，运行时立刻报错。类型系统和运行时在这一刻脱节了，而编译器不会给出任何警告。

需要说明的是，TypeScript 对 exports 字段与条件导出的完整支持当时还在演进，node 这套解析规则本质上仍然是 CommonJS 时代的模型。这意味着当依赖包只通过 exports 暴露类型、没有在根目录放 index.d.ts 时，类型检查可能找不到入口，而运行时却能正常加载。这种”运行时能跑、编辑器报红”的不一致，是那个阶段最典型的困扰之一。官方的 node12、node16 解析模式尚未落地，社区只能靠约定规避。

target 的选择相对自由。Node 16 对 ES2020 的语法支持已经比较完整，把 target 设为 es2019 或 es2020 都能跑；设为更高的目标则要确认运行时版本，避免产物里出现当前 Node 不认识的语法。declaration 打开是发布类型声明的前提，这一项在双包场景下会变得更复杂。

互操作：默认导入、esModuleInterop 与 import type

ESM 导入 CommonJS 时，Node 会把 module.exports 整体当作默认导出。所以 import fs from 'fs' 拿到的是完整的模块对象，这一点很直观。麻烦的是具名导出：CommonJS 没有静态的导出列表，Node 只能靠静态分析源码来推断，exports.readFile = ... 这类赋值能被识别出来，module.exports = function () {} 就只能得到默认导出。

TypeScript 这边的情况更绕。默认配置下，import fs from "fs" 会报错，提示模块没有默认导出，因为类型系统严格按 CommonJS 的声明来看。打开 esModuleInterop 之后，编译器不仅允许这种写法，还会在产物里插入一层包装，把 CommonJS 模块转成带 default 属性的对象，运行时行为与类型声明就一致了。

allowSyntheticDefaultImports 只影响类型检查，不改变任何输出。它适合把转译工作交给 Babel 或打包器的项目：那些工具默认就做了互操作包装，类型层面放宽即可。两者同时开启时，esModuleInterop 已经隐含了后者，不必重复配置。但要注意，一旦打开 esModuleInterop，import * as fs from 'fs' 得到的命名空间对象在类型上不再可调用，习惯这种写法的老代码需要调整。

另一个容易忽略的点是类型导入的擦除。TypeScript 在编译时会删掉只用于类型的导入，但判断”只用于类型”依赖类型信息，跨文件的类型再导出有时会让编译器保守处理，留下一条实际运行时会去加载模块的导入语句。如果那个模块在运行时并不存在，或者加载它有副作用，问题就出现了。

双包及其危害

所谓双包，是指一个 npm 包同时提供 CommonJS 与 ESM 两份产物，通过条件导出按加载方式分发。听起来是两全其美：老项目继续 require，新项目享受静态分析。但在 2021 年，双包是一个被反复警告的模式，原因不在于打包体积，而在于同一个包可能被加载两次。

Node 的模块缓存是按”解析后的文件路径 + 加载器”分别维护的。CJS 加载器有一份缓存，ESM 加载器有另一份。当应用里一部分代码 require('pkg') 加载了 dist/index.cjs，另一部分 import 'pkg' 加载了 dist/index.js，两份文件各自执行一遍，各自持有一份模块级状态。从应用的角度看，pkg 只被安装了一次，却存在两个互不相识的实例。

后果在涉及身份判断的地方最明显。库内部定义了一个错误类，用户代码 require 拿到的是 CJS 版本的类，而某个 ESM 依赖抛出的错误来自 ESM 版本，err instanceof MyError 就会返回 false，错误处理分支静默失效。单例同样会分裂：连接池、事件总线、注册表、依赖注入容器，只要状态挂在模块作用域上，双份实例就意味着双份连接、双份监听、双份内存。

还有一种更隐蔽的触发方式。条件导出的顺序如果写成 default 在前，或者用了 browser、module 这类打包器自定义条件，就可能出现”Node 拿到 CJS、打包器拿到 ESM”的错配。开发时用打包器跑得好好的，上线后 Node 直接加载，行为和本地不一致，排查成本很高。

当时的缓解办法有三条。第一条是只发布一份实现，另一份做薄包装：以 CommonJS 为主体，ESM 入口写成一个只做再导出的文件，内部 import 那个 CJS 文件再 export 出去。这样两种加载方式最终指向同一份代码，状态只有一份，代价是需要手写并维护具名导出的映射。

第二条是让模块本身无状态。把可变状态从模块作用域移到显式的实例对象里，instanceof 判断改为基于稳定的标识字段。这对新代码可行，对已有库则是重构。

第三条是只发一种格式。只发 CommonJS 最保守，ESM 用户仍能通过默认导入使用，代价是丢掉静态分析与 tree-shaking；只发 ESM 最激进，但当时 require() 还加载不了 ESM，会直接打断大量下游。这也是为什么那两年库作者普遍选择双包，同时把”不要依赖模块级单例”写进文档。

这个文件放在 dist/cjs 下，就把该目录重新划成一个 CommonJS 包作用域，与根目录的 "type": "module" 互不干扰。构建脚本在编译后把它拷过去即可。这个技巧在当时的双包库里非常常见，因为它是唯一不需要重命名产物的方案。

类型声明只发一份通常就够了，放在 dist/types 下，由 exports 的 types 条件指向。types 条件要写在最前面，因为条件按顺序匹配，如果 import 排在前面，类型检查就永远走不到 types 分支。

发布前还要检查 files 字段，确保 dist/esm、dist/cjs、dist/types 三个目录都进了包里，否则本地测试全绿、装到别的项目里却缺文件。这类疏漏在双包里格外常见，因为本地开发往往直接引用源码，根本没走过打包后的路径。

测试策略也需要调整。在 ESM 下直接跑源码的测试框架，当时大多支持得不够完整：有的需要额外的转译配置，有的对 import 的支持还标着实验。比较稳妥的做法是”先构建，再对产物跑测试”，把测试当成真实消费者。这样测的是 Node 实际会加载的文件，扩展名、exports 映射、条件导出都能被覆盖到；代价是每次改动都要等一次编译，反馈变慢。

开发期的热更新则绕不开 ts-node。它在 ESM 模式下需要借助 Node 的实验性 loader 机制启动，配置上要求 module 为 esnext，并且对路径别名的处理与 CommonJS 模式不同。由于 loader 接口本身还在变动，这套组合在 2021 年属于”能用但要盯着版本”的状态。工具链的具体取舍不在本文展开，这里只需建立一个判断：源码直跑与产物运行是两条不同的解析链路，任何一条通过都不代表另一条也能通过。

迁移路线与常见坑

迁移的关键不是把 require 换成 import，而是控制变量。一次只改一个维度，出了问题才能定位。比较稳妥的顺序是先锁运行环境，再动代码：在 package.json 里写明 engines 的 Node 版本范围，用 .nvmrc 固定开发与 CI 的版本，确认新版 Node 下现有 CommonJS 代码全部通过测试。这一步没有收益，但它把”迁移引入的问题”和”升级引入的问题”分开了。

第二步是盘点依赖。把直接依赖逐个确认是否提供 ESM 入口，是否声明了 exports。没有 ESM 入口的包不必强求替换，ESM 可以正常导入 CommonJS，只是具名导出受静态分析限制，默认导入最保险。

第三步是从叶子模块开始改。被依赖最少的工具函数、常量、类型定义先迁，入口文件最后迁。每迁完一层就跑一次测试，让问题在最小的范围内暴露。如果一个仓库里有多个包，可以逐包修改 "type"，用嵌套的 package.json 划出边界，而不是一次性全仓切换。如果项目里用了路径别名，最好在动 type 之前先把别名改成相对路径，因为 Node 的 ESM 并不认识 tsconfig 里的 paths，别名只在编译器和打包器内部有效。

第四步才是改包级声明。把 "type": "module" 加上去，把仍在用 require 的少量文件改名为 .cjs，把 main 升级为 exports。这一步做完，包对外的主入口就变了，需要按破坏性变更对待，发大版本。

动态导入要注意路径语义。import('./plugins/' + name) 里的相对路径是相对于当前模块的，不是相对于 process.cwd()，拼接时最好统一用 new URL() 生成绝对地址。另外 import() 返回 Promise，忘记 await 会让后续逻辑在模块加载完成前执行。

JSON 导入在当时需要 import assertions，并且依赖实验开关，不适合写进生产代码。读取配置文件的务实做法是用 fs.readFileSync 加 JSON.parse，或者用 createRequire 直接 require 那个 JSON 文件。

条件导出的顺序错误最隐蔽。把 default 写在 import 前面，表面上看一切正常，实际所有 ESM 用户都拿到了 CommonJS 产物，静态分析、tree-shaking 全部落空，双包危害也随之出现。写完 exports 后应当分别用 import 和 require 各写一个最小用例，确认命中的是预期文件。

打包器与 Node 的解析差异是另一类问题。打包器长期迁就 CommonJS 的宽松规则，允许省略扩展名、允许目录导入、支持 browser 字段替换模块；Node 的 ESM 一条都不认。在打包器里跑通的代码，直接部署到 Node 就可能找不到文件。判断标准很简单：以 Node 的解析结果为准，打包器只当优化手段。

还有两处细节容易被忽略。一是 import * as ns 得到的命名空间对象是只读的，不能给属性赋值，过去那种”导入后打个补丁”的写法在 ESM 下会直接抛错；二是循环依赖从”拿到 undefined”变成了”可能触发暂时性死区”，迁移后如果出现 Cannot access before initialization，先回头看模块之间是不是形成了环。

最后是具名导出的静态分析。CommonJS 包如果通过动态方式挂载导出，例如遍历对象批量赋值，Node 的分析器识别不出来，import { foo } 就会在运行时报错，而默认导入始终可用。遇到这种包，改回默认导入是最快的解法，不必去改依赖本身。

小结

CommonJS 与 ESM 的差异不止语法，更在于加载时机与解析规则：前者同步、宽松、运行时决定，后者异步、严格、执行前就要把整个模块图定下来。Node 用 type 字段与 .mjs、.cjs 扩展名划分作用域，用 exports 声明入口并顺带封装内部结构；TypeScript 则用 module 管输出、moduleResolution 管输入，两者必须与运行时对齐，否则就会出现编译通过而运行失败。

迁移时值得记住三点。第一，源码里显式写 .js 扩展名，让类型检查与运行时看到同一套路径。第二，类型导入一律用 import type，避免擦除不彻底带来的运行时加载。第三，认真对待双包的状态分裂与条件导出顺序，exports 写完要用两种加载方式各验证一次。

工具链在 2021 年仍在快速演进，解析模式的官方支持、loader 的稳定性都还没定型，因此迁移方案要留出回退空间：锁定 Node 版本，保持测试对产物运行，把 "type": "module" 的切换放在最后一步，并当作破坏性变更来发布。
