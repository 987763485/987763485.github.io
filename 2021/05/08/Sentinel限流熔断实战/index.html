Sentinel 限流熔断实战

本文属于《Go 微服务架构》第 22/35 篇
上一篇系列目录下一篇

微服务拆细之后，任何一个下游抖动都会被上游放大成雪崩。限流与熔断是两道最基础的防线，而 Sentinel 把这两件事做成了可动态配置的通用组件。本文从资源模型讲到规则落地，带你把 Sentinel 接进真实项目。

文章面向已经写过 Spring Cloud 服务、准备给接口加上流量保护的读者。读完后你应当能说清 Resource、Entry、Context 的关系，能为不同场景选择流控与降级策略，并知道规则怎么持久化、怎么避免常见的配置误区。示例中的阈值都是示意值，实际取值必须压测后再定。

先看清它解决什么问题

Sentinel 是阿里开源的流量治理组件，定位很明确：以“资源”为单位，在运行时对调用做统计与拦截。它不负责服务发现，也不替代网关，而是嵌在应用进程里，守住每个资源入口。它提供的能力可以归为五类：流量控制、熔断降级、热点参数限流、系统自适应保护、来源授权。

与网关限流相比，Sentinel 的优势是看得见业务语义：网关只知道路由与 IP，应用内却知道哪个方法、哪个参数被压垮了。两者互补，网关挡入口异常流量，应用内按资源精细保护。

Sentinel 有 Java 与 Go 两个主要客户端。Java 版生态最完整，和 Spring Cloud Alibaba 结合紧密；Go 版（sentinel-golang）覆盖了流控、熔断、热点、系统规则等核心模型，适合非 Java 技术栈。两边的概念是一致的，差异主要在接入方式和扩展点上。

资源、入口与上下文

Resource 是保护的基本单位。它可以是一个 HTTP 接口、一个 RPC 方法、一段数据库访问代码。定义资源的过程叫埋点，也就是在代码里显式告诉 Sentinel：“从这里开始，这段逻辑要被统计和保护”。

Entry 是一次资源访问的凭证。调用 SphU.entry("queryUser") 会返回一个 Entry，它代表本次进入；业务结束后必须在 finally 中调用 entry.exit()。Entry 成对出现，Sentinel 才能正确维护当前线程的调用栈和在途计数。

Context 是调用链上下文，用来描述“这次请求从哪里来”。命名入口通过 ContextUtil.enter("web", "app-a") 完成，第一个参数是入口名称，第二个参数是来源。同一个线程内，多次 entry 共享同一个 Context，调用树因此可以串起来。链路限流和来源授权都依赖它。

三者的关系可以用一条链路概括：

flowchart TD
    A[请求进入] --> B[Context 命名入口]
    B --> C[Entry 进入资源]
    C --> D[Slot Chain 责任链]
    D --> E[业务逻辑]
    E --> F[Entry.exit 释放]

真正干活的是 Slot Chain。它是一条有序的责任链，每个 Slot 只做一件事：NodeSelectorSlot 构建调用树，ClusterBuilderSlot 汇总来源统计，StatisticSlot 记录 QPS、响应时间与并发线程数；随后 AuthoritySlot、SystemSlot、ParamFlowSlot、FlowSlot、DegradeSlot 依次做检查。前半段“记录事实”，后半段“做出判断”，理解这个分工，后面的规则行为就不难推断了。

流控规则：先想清楚限制什么

流控规则的第一组选择是统计维度。按 QPS 限制的是每秒通过的请求数，适合接口型资源；按并发线程数限制的是同一时刻正在处理的请求数，适合调用外部依赖、处理时间波动大的场景。两者不能混为一谈：一个 QPS 为 20、平均耗时 50 毫秒的接口，并发通常只有 1 到 2，若把线程数阈值也设成 20，这条规则几乎永远不会触发。

第二组选择是流控模式：

  • 直接：只统计当前资源自身的流量，最常用。
  • 关联：当关联资源达到阈值时，限制当前资源。典型用法是写库繁忙时限制读接口，把有限的连接留给写操作。
  • 链路：只统计从指定入口进来的流量，同一资源的其他调用路径不受影响。它依赖 Context 的入口命名，未命名时会归入默认入口。

第三组选择是流控效果，也就是流量超限后的处置方式：

  • 快速失败：直接抛出 BlockException，由调用方兜底，行为最确定。
  • Warm Up：阈值在预热期内从低位逐步爬到设定值，避免冷启动时缓存未热、连接未建好就被打满。
  • 排队等待：请求按固定间隔匀速通过，超出等待时间的请求才被拒绝，本质是漏桶思路，只对 QPS 模式有效。

熔断降级与其他规则

熔断解决的是“下游已经坏了，别再打了”的问题。Sentinel 的熔断规则有三种统计策略：慢调用比例、异常比例、异常数。慢调用比例先定义什么叫慢，超过最大响应时间的请求计入慢调用，当请求量达到最小样本数、且慢调用占比超过阈值时触发熔断；异常比例看异常请求的占比；异常数则直接看窗口内的异常次数，适合低流量接口。

熔断器有三个状态：关闭时正常放行并统计；打开时直接拒绝，持续一个时间窗口；窗口结束后进入半开，放少量请求探路，成功则关闭，失败则重新打开。这个状态机与具体业务无关，本文不展开降级体系的设计，只强调一点：熔断的时间窗口要大于下游的恢复时间，否则会在下游还没缓过来时反复试探。

热点参数限流针对“同一个资源、不同参数值”的场景。比如商品详情接口，某个爆款商品带来的流量远高于其他商品，按整体 QPS 限制会误伤长尾商品。热点规则可以给指定参数索引单独设阈值，还能为特定参数值配置例外，属于精细化的补充手段。

系统自适应规则从应用整体视角出发，依据入口 QPS、平均响应时间、并发线程数、系统负载和 CPU 使用率做保护，触发后拒绝所有入口流量。它适合兜底，不适合替代单资源规则。授权规则则按来源做白名单或黑名单，来源取自 Context 的 origin，常用于限制只有网关或特定服务可以调用。

这几类规则可以叠加使用，但每叠加一层，排障成本就上升一层。实践中建议先上直接流控，观察一段时间后再补熔断与热点规则。

控制台、动态推送与规则持久化

Sentinel 控制台是一个独立的 Java 应用，启动后提供簇点链路、实时监控、规则配置等页面。应用端需要配置控制台地址并引入 transport 模块，启动时向控制台注册。控制台是懒加载的：应用启动后不会立刻出现，要等该应用的资源第一次被访问，客户端才会发起注册。

规则推送有推和拉两种模式。默认的简单模式由控制台直接调用客户端接口写入内存，配置最省事，但有两个明显问题：应用重启，规则没了；控制台重启，规则也没了。因此生产环境必须做持久化，常见方案有三种。

Nacos 是最常用的选择。做法是在 Nacos 中维护规则的 JSON 配置，应用端引入对应的 datasource 扩展，监听配置变更并自动刷新本地规则；同时改造控制台，让页面上的修改写回 Nacos，而不是只改内存。ZooKeeper 的思路一致，只是把配置节点换成 ZNode。本地文件方案适合单机或规则极少变更的场景，通过文件数据源定时读取，重启后仍能恢复。

三种方案的共同点是：规则权威副本存在应用进程之外，客户端只做缓存与监听。只做客户端监听、不改推送链路，是最常见的半成品配置，表现为“页面改完看似生效，重启又回到旧规则”。

接入方式：Java、Go 与两种回调

Spring Cloud 项目接入相对省事，引入 starter 并配置控制台地址即可，Web 接口、Feign 调用、RestTemplate 调用会被自动埋点，业务代码几乎不用改。需要自定义资源时，在方法上加 @SentinelResource，指定资源名和兜底方法。版本适配以项目实际依赖为准。

注解里有两个容易混淆的属性：blockHandler 和 fallback。前者只在抛出 BlockException 时生效，也就是被限流、熔断、授权拒绝时调用；后者处理业务方法自身抛出的异常。二者的方法签名要求不同，blockHandler 对应方法要多一个 BlockException 参数，fallback 对应方法可以接收 Throwable。默认情况下 fallback 不接 BlockException，如果希望一个方法兜住所有情况，需要显式配置，或使用 defaultFallback 做全局兜底。

生效顺序与常见配置误区

规则不是同时判断的，Slot Chain 的顺序决定了一切：授权、系统、热点、流控、熔断依次检查。任何一个 Slot 抛出 BlockException，后面的检查就不再执行。这带来两个直接后果：同一资源的流控与熔断同时触发时，看到的是流控异常；系统规则一旦触发，单资源规则根本没有机会执行。

理解顺序之后，再看几个高频误区：

  • 忘记 exit 或重复 exit。在途线程数是增减计数，漏掉一次 exit，计数就永久偏高，线程数限流会提前触发且无法自愈。
  • 把线程数阈值当 QPS 阈值设。两者量纲不同，线程数阈值应参考实际并发与耗时，通常远小于 QPS。
  • 链路规则不生效。没调用 ContextUtil.enter 命名入口时，所有流量归入默认入口，链路规则自然匹配不上。
  • 熔断样本数设得过小。低流量接口在样本不足时比例没有意义，容易因一两次抖动进入打开状态。
  • 规则双写互相覆盖。代码里 loadRules 一次，配置中心又推一次，重启顺序不同结果就不同。
  • 只调阈值不看超时。排队等待和慢调用判定都依赖调用方超时，超时设置不一致会让统计口径失真。

监控、调优与 Hystrix 的差异

控制台的实时监控按分钟聚合，能看到通过数、拒绝数、响应时间与并发，但保留时间有限，不适合作为长期观测依据。生产上通常把客户端的 metrics 日志采集到自有监控系统，围绕拒绝率、熔断次数、慢调用比例建看板，再配合告警。

调优的顺序应当是先压测、再定阈值。单机阈值取决于接口耗时、下游容量和机器规格，不能照搬别人的数字。规则上线后观察拒绝率：持续偏高说明阈值过低或容量不足，长期为零则说明规则形同虚设。规则调整也应灰度，先在单实例生效，确认无异常再全量。

最后说与 Hystrix 的定位差异。Hystrix 的核心是隔离，用线程池或信号量把依赖调用隔开，一个依赖变慢不会拖垮整个容器；Sentinel 默认不做线程池隔离，而是以并发线程数、响应时间等指标驱动规则，把“隔离”换成了“可配置的拒绝”。Hystrix 的命令与参数大多写在代码里，动态调整需要额外的配置体系；Sentinel 从设计上就把规则外置，支持控制台与多种配置中心。加上多语言客户端，Sentinel 更像流量治理基础设施，Hystrix 更像一个库。后者已进入维护状态，新项目选型时应纳入考虑。

小结

Sentinel 的核心是资源模型：Context 描述调用来源，Entry 标记一次进入，Slot Chain 按固定顺序完成统计与判断。流控规则要先明确统计维度、匹配模式和超限处置，再谈阈值；熔断规则要关注慢调用定义、最小样本数与时间窗口。规则必须外置持久化，只监听不推送、或只推送不持久化，都会在重启后露馅。埋点时保证 Entry 成对释放，注释里区分 blockHandler 与 fallback 的职责，能省下大量排障时间。最后，阈值来自压测而非猜测，规则调整要灰度，监控要能回答“为什么被拒绝”。
