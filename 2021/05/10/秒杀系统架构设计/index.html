秒杀系统架构设计

秒杀是电商系统里最极端的一类场景：一件商品在几秒钟内被几十万人同时争抢，库存却只有几百件。它考验的不是某个接口写得多快，而是整条链路在流量洪峰下能否守住库存与订单的底线。

本文从架构全景出发，讨论业务约束、分层过滤、库存模型、异步下单与降级兜底，说明各层如何分工与取舍，不展开具体技术实现。

秒杀业务的四个硬约束

秒杀的活动规则通常很简单：某个时刻开抢，库存只有几百件，价格远低于日常。规则越简单，流量越集中。设计架构之前，先看清四条硬约束。

第一是瞬时高并发。流量在开抢后几秒内集中涌入，峰值可能是平时的几十倍甚至上百倍。系统面对的是脉冲，按峰值长期扩容既不经济，也没必要。

第二是库存少。几百件商品对应几十万参与者，绝大多数请求注定失败。系统应该尽早、便宜地拒绝它们，而不是让每个请求都走完下单链路。

第三是强一致。库存不能超卖，订单与库存必须对得上；少卖可以接受，但要有对账和回补。这条约束决定了库存只能有一个可信的扣减点。

第四是防刷。脚本和群控会在毫秒级发起请求，普通用户无法竞争。资格校验和频率限制必须在库存扣减之前完成，否则无效请求会白白占用库存。

四条合在一起，判断就出来了：秒杀架构的目标不是让每个请求都成功，而是用最低成本识别无效流量，再把有限的有效流量有序送进后端。这与普通电商追求转化率的思路相反，秒杀追求的是确定性。

分层过滤：把流量挡在核心链路之外

分层过滤是秒杀架构的主干。每一层只做自己最擅长、成本最低的判断，尽量在便宜的地方把请求拦掉。下面是一条典型的过滤链路。

flowchart TD
    A[用户请求] --> B[CDN 与静态活动页]
    B --> C[前端按钮防重]
    C --> D[网关限流与黑名单]
    D --> E[服务层资格校验]
    E --> F[库存层原子扣减]
    F --> G[消息队列]
    G --> H[订单落库]
    F --> I[售罄页]

最前面是页面静态化与 CDN。活动页在开始前生成静态 HTML 推到边缘节点；倒计时由浏览器根据服务器时间计算，库存只展示“有货”或“售罄”。开抢瞬间的刷新压力落在 CDN 上，而不是应用服务器。

第二层是前端按钮防重。点击后置灰、限制间隔、携带一次性令牌，能挡掉大量误触和连点。但前端代码在用户手里，只能改善体验，不能当作安全边界，真正的防重必须放在服务端。

第三层是网关限流。按用户、IP、接口三个维度设阈值，超出的请求直接返回提示。限流算法不是本文重点，这里只强调位置：网关离用户最近，拒绝成本最低，适合承担第一波冲击。阈值要结合压测设置，拍脑袋的数字要么误伤，要么形同虚设。

第四层是服务层校验。检查活动是否开始、用户是否有资格、是否超过限购、验证码是否正确。这些判断依赖业务数据，放在网关做不了，但可以借助缓存把开销压得很低。

最后一层是库存扣减。它是整条链路唯一可信的闸门，前面所有层都可能被绕过。扣减必须原子、单点、可回补，并通过消息队列把下单异步化。

分层的价值在于成本递减：CDN 拦一次请求的成本远低于数据库回滚一次事务。所以能上移的判断尽量上移。

预约、资格校验与库存模型

秒杀不是从点击“立即抢购”才开始的。预约和资格校验提前算清“谁可以参与”，库存模型则在毫秒间决定“谁能拿到货”。

活动预约与资格校验

预约有两层作用：对用户是提醒，对系统是把不确定的到场流量变成可预估的数字，用于容量评估和分桶设计。但预约不等于购买资格，真正的资格还要看会员等级、实名状态、收货地址、历史购买记录和风控评分。

资格名单最好离线算好，活动前写入缓存或布隆过滤器。布隆过滤器的特点是“说不存在就一定不存在，说存在则可能误判”，命中后还要回源确认。这样能把绝大多数无资格请求挡在数据库之外。限购计数按用户和活动维度维护，扣减成功后再累加，避免用户被自己锁死。

防刷要贯穿资格校验。设备指纹、验证码、行为轨迹、IP 聚集度都可作为依据，但单一维度都不可靠。常见做法是分层：低风险放行，中风险要求验证码，高风险拒绝。目标是让刷单成本高于收益。

库存的预扣与分桶

库存模型要回答三个问题：在哪里扣、扣多少、扣错了怎么还。数据库可以用一条带条件的更新保证不超卖，但瞬时并发下同一行的锁竞争会让请求排队，响应时间迅速恶化。于是常见做法是预扣：活动前把库存搬到 Redis，以缓存为准做原子扣减，数据库只负责最终持久化。

预扣解决了性能问题，却带来缓存与数据库的时间差。这个时间差只能靠流水、对账和回补收敛，不能靠“双写”消除。Redis 原子扣减的具体写法，第 637 篇已经展开，本文不再重复。

单件商品热度极高时，一个 Redis key 也会成为瓶颈。分桶把 1000 件拆成 10 个桶，每桶 100 件，请求按用户 ID 哈希到固定桶，竞争被分散。代价是可能出现“总量还有、某个桶已空”的少卖。可以在桶空时向汇总池借货，或降级到其他桶重试，但借还要设上限和顺序，避免死锁和超借。

扣减与回补

一次完整的库存流转包括扣减、占用、确认和回补。扣减在请求通过校验后发生；占用表示库存已归属某个请求，但订单还没落库；确认在订单创建成功后；回补出现在下单失败、支付超时、用户取消等场景。

回补必须有业务单据号。没有单据号，重试和重复消费会多加库存，把“少卖”变成“超卖”。库存流水同样关键：每次扣减和回补都记一条，包含活动、用户、数量、时间和关联订单，出问题可按流水逐笔对账。

还要区分“预占”与“实扣”。预占只是锁定名额，超时未支付要自动释放；实扣才是真正的销售。两者口径不同，报表要分开统计，否则会出现运营看到“卖完了”、财务却没收入的尴尬。

异步下单与消息队列

同步链路越长，响应时间越不可控。秒杀把“抢”和“买”拆开：同步阶段只做资格校验、库存预扣和令牌生成，随后写一条消息返回“排队中”；订单落库、优惠计算、通知发送交给消费者异步完成。

这样做有三个好处：削峰，消息队列把脉冲拉平，消费者按数据库能承受的速率消费；解耦，订单、库存、通知各自订阅；可重试，消费失败可以重投，用户不必重新抢。

消息可靠性要单独设计。生产端可能发送失败，消费端可能重复消费，中间件也可能丢消息。常见做法是本地消息表：在扣减库存的同一事务里写一条待发送记录，由定时任务补发；或使用支持事务消息的中间件。核心要求只有一条：库存扣了，消息一定发出去。

消费端要保证顺序。同一用户的消息乱序，可能出现先建订单后扣库存的假象，按用户 ID 分区可以让同一用户落到同一队列。失败进入重试队列，多次失败进入死信队列，由人工或补偿任务处理。

前端拿到“排队中”后，用请求 ID 查询结果。轮询要控制频率并加退避，结果可以缓存在 Redis 里。成功、失败、处理中三种状态要明确展示，不能让用户对着转圈猜。

超卖、少卖与幂等防重

超卖是秒杀最不能接受的错误。根因通常不是“扣减不够快”，而是“判断和扣减不是一个原子动作”。两个请求同时读到库存为 1，各自判断“还有”，然后各自扣减，库存就变成了 -1。多副本各自计数、缓存与数据库不一致、回补重复执行，都会产生同样结果。

防线分三层。第一层是单点原子扣减，把判断和修改合并成一次操作，具体实现第 637 篇已经讲过。第二层是数据库约束，订单表对“用户 + 活动”建唯一索引，扣库存语句带上库存大于零的条件，即使缓存出错，数据库也不会写出超卖订单。第三层是对账，定时比对扣减流水、订单表和数据库库存，发现差异立即告警并冻结活动。

少卖是另一种失衡。预扣成功但下单失败、消息丢失、分桶不均、回补遗漏，都会让库存没卖完。少卖不产生资损，但影响口碑。处理办法是尽快发现、尽量自动回补：活动结束后按流水盘点，释放未确认的预占；分桶允许借还；差异抛给运营。

取舍很明确：宁可少卖，不可超卖。超卖意味着用户付了钱拿不到货，涉及赔付和品牌损失；少卖只是少做几单。所以边界情况都往“拒绝”一侧倒，例如库存服务超时就直接返回售罄。

幂等和防重是同一件事的两面。用户重复点击、网关重试、消息重复投递，都会让同一请求到达多次。方案有三类：请求令牌，一次有效；去重表，以业务唯一键插入，冲突即重复；状态机，订单只能从“待创建”走到“已创建”。唯一索引是最后保险，不能替代业务判断。要避免“先查后写”，查询和写入之间有空窗，并发下两个请求都会查到“不存在”。

降级兜底、容量评估与可观测性

再好的主链路也要兜底。售罄后立刻切到静态售罄页，由 CDN 缓存，后续请求不再进入应用；请求过多时展示排队页，用进度和预计时间安抚用户；被限流时给出明确提示和重试时间，而不是白屏。降级开关要提前准备：关闭推荐、评论等非核心功能，资格查询走缓存，库存服务不可用时直接按售罄处理。

容量评估要分层做。按“参与人数 × 到场率 × 点击次数”估算峰值，再分别核算网关、应用、Redis 和数据库的承载能力，最后乘冗余系数。这里只是示意，真实值必须来自压测。压测要覆盖完整链路，轮询查询和售罄页同样要验证，第 637 篇讲过具体做法，本文只强调每层都要有独立结论。

可观测性方面，至少盯住 QPS、响应时间、错误率、库存余额、消息堆积和订单创建成功率，按活动维度打点，用 traceId 串起完整路径。指标异常时要能立刻判断是流量、依赖还是数据问题。

常见误区

把限流当万能是第一个误区。限流只保护系统不被压垮，解决不了超卖、少卖和数据不一致，阈值不当还会误伤真实用户。

第二个误区是库存与订单各记各的。缓存扣了、数据库没扣，或订单创建了、库存没回补，活动结束对账才发现缺口。库存、流水、订单三者必须能互相对上。

第三个误区是迷信缓存与数据库双写。两种写顺序都有失败窗口，加重试只会让顺序更乱。秒杀应以一个扣减点为准，异步落库，再用对账收敛。

小结

秒杀架构的本质是分层过滤与确定性取舍：用静态化、前端防重、网关限流、资格校验层层削减流量，把唯一可信的扣减点留给库存层，再用消息队列把下单异步化。库存宁可少卖不可超卖，扣减与回补都要有单据和流水，幂等由唯一约束兜底。容量靠分层评估和压测，稳定性靠降级预案与可观测性，活动结束后还要对账复盘。
