热点账户与行锁竞争优化

平台型业务里，总有那么几个账户被全站流量反复更新：大商户的待结算账户、优惠券的总池、积分总账。并发一上来，这些行的更新就开始排队，接口响应时间抖动、死锁日志增多，严重时连接池被拖干、服务全面超时，而数据库的 CPU 却不见得高。

本文从 InnoDB 行锁的持锁时间讲起，先解释热点账户为什么会把数据库拖慢，再给出从压缩事务到账户拆分、异步记账、乐观锁的几层手段，最后说明拆分之后怎样做汇总与对账，以及选型时该看哪些指标。

热点账户从哪里来

账户表往往是最不起眼却最容易压垮系统的一张表。它的结构简单到只有几列：账户号、余额、冻结金额、版本号、更新时间。单条记录的读写都很快，慢的从来不是 SQL 本身，而是同一行上的并发。

典型的热点账户有三类。

第一类是平台大商户。电商平台先把买家的货款记在平台账户，再按结算周期打给商家。某个头部商家一天的订单量可能占全站相当大的比例，它的待结算账户就成了全站写入最密集的一行。下单要冻结、支付成功要扣减、退款要回补，动作全部落在同一个账户号上。

第二类是优惠券总池。券的余量常常记在“活动与券模板”这一行上，领券接口在高峰期被高频调用，每次都要判断余量再减一。哪怕业务上已经把券拆成了很多张实体券，只要库存计数还放在一行里，这一行就是瓶颈。

第三类是积分账户。签到、下单返积分、积分抵现、过期清理，多个入口都会改同一个用户的积分余额。如果产品还设计了“平台积分总账”用于财务核对，那么总账那一行会被所有用户的积分变动同时更新，热度与全站活跃用户数成正比。

这些场景的现象有一个共同的演进顺序。最初只是监控上某条 UPDATE 语句的平均耗时变长，P99 从几毫秒涨到几十毫秒；接着应用日志里出现锁等待超时，业务侧表现为部分请求失败后重试；再往后，InnoDB 的死锁检测频繁触发，SHOW ENGINE INNODB STATUS 的输出里能看到成片的 LOCK WAIT；最后，每个请求都要等锁，连接被逐一占满，服务对外表现为全面超时。

这个顺序值得注意：热点账户的故障常常不是“数据库算不过来”，而是“数据库在排队”，表现为 CPU 不高、连接数却接近上限。这也决定了优化方向——减少同一行上的并发持锁，而不是一味加索引、加机器。

行锁排队：持锁时间是分母

InnoDB 的行锁加在索引记录上，而不是加在“行”这个抽象概念上。一条 UPDATE account SET balance = balance - 100 WHERE id = 1 会在主键索引的这条记录上加排他锁（X 锁），并且一直持有到事务提交或回滚，而不是语句结束就释放。

这一点是理解热点账户的关键：一行记录的更新吞吐上限，近似等于 1 除以单次持锁时间。持锁 5 毫秒，这一行每秒理论上只能承受约 200 次更新；持锁 50 毫秒，上限就掉到 20 次。业务方看到的是吞吐上不去，实际原因却是所有请求都挤在同一行上排队。

SELECT ... FOR UPDATE 是当前读，会对读到的记录加排他锁；后到的事务如果命中同一行，就进入锁等待。InnoDB 的等待队列并非严格的先来先服务，但同一行上的排他请求事实上是串行的，前面的事务不提交，后面的事务只能等。

sequenceDiagram
    participant A as 事务 A
    participant B as 事务 B
    participant R as 账户行 id=1
    A->>R: SELECT ... FOR UPDATE，加 X 锁
    B->>R: SELECT ... FOR UPDATE，进入等待
    A->>R: UPDATE balance，继续持锁
    A->>R: COMMIT，释放锁
    R-->>B: 获得锁，继续执行

排队一旦形成，尾延迟会迅速恶化。假设每个事务持锁 10 毫秒，第 20 个排队的请求至少要等 200 毫秒；而上游往往还有 HTTP 超时和重试，重试又会带来新的请求，把队列撑得更长。这就是为什么热点账户的表现常常是“平时好好的，一到活动就整片超时”。

除了等待，还有两个连带问题。其一是死锁：一个事务要更新 A、B 两个账户，另一个事务按相反顺序更新 B、A，两边互等，InnoDB 会检测到并回滚其中代价较小的事务，应用层必须能够重试。其二是长事务：事务开得越久，undo 日志越难回收，MVCC 的版本链越长，其他查询的读代价也随之上升。

所以优化热点账户，本质上只做两件事：缩短每次持锁的时间，以及把一行上的并发分散到多行。下面几节按这个顺序展开。

第一层：把事务压到最短

在动结构之前，先看事务里到底放了什么。很多热点账户的持锁时间不是被 SQL 占掉的，而是被夹在中间的远程调用、消息发送、日志落库占掉的。把这些动作挪出事务，往往能立刻看到效果。

除了挪动逻辑，还有几个细节值得检查。

  • 判断与扣减合成一条语句。UPDATE account SET balance = balance - ?, version = version + 1 WHERE id = ? AND balance >= ? 把“查余额、判断够不够、扣减”压缩成一次加锁和一次往返，比先 SELECT 再 UPDATE 少一次持锁窗口。
  • 索引要能定位到唯一一行。更新条件走不到索引时，InnoDB 会扫描并锁住更多记录，队列自然更长。用主键或唯一键定位是最理想的情况。
  • 不要把大查询放进事务。统计、导出、分页这类慢 SQL 即使只读，也会拉长事务、占用连接。
  • 隔离级别不必迷信默认值。MySQL 8.0 默认是 REPEATABLE READ，范围条件在缺少合适索引时可能带来额外的间隙锁；如果业务能接受，改为 READ COMMITTED 可以减少这类锁冲突，但要以业务语义允许为前提。

这些改动成本低、风险小，应当先做。做完之后如果单行并发仍然打满，再考虑拆分。

第二层：拆账户、异步记账与批量合并

拆分是最直接的办法：把原来的一行变成 N 行，请求按某种规则落到不同行上，总余额等于各行之和。

以优惠券库存为例，可以把总池切成若干个桶，每个桶一行记录，领券时轮询或随机选桶，扣减时带上余量条件：

账户也是同理。可以按用户号取模分成子账户，也可以按业务维度拆成“可用、冻结、待结算”几个子账户，再各自分片。拆分的关键是让同一时刻的请求尽量落在不同的行上，而不是简单地多建几张表。

异步记账则换了一个思路：请求路径上不再直接改余额，而是先写一条流水，由后台按账户串行消费，再更新余额。

消费端把同一账户的流水归并后批量执行，N 条变动合并成一次 UPDATE，锁只加一次、只释放一次。为了不破坏余额的语义，消费端要保证同一账户的消息串行处理，常见做法是按账户号哈希到同一个分区或同一个消费线程。代价是余额变为最终一致，中间存在短暂延迟，页面上的余额可能比实际晚几百毫秒。

乐观锁与版本号适合另一类场景：先读出余额、在内存里算好、再写回。此时用 WHERE id = ? AND version = ? 做 CAS，失败就重读重试。但在真正的热点行上，冲突率极高，重试会形成风暴，反而放大压力；对于纯增减，直接用 balance = balance - ? 的原地更新更合适，它本身就是原子的，不需要版本号。

选择哪一层，取决于业务能容忍多少延迟。实时扣减要求强一致，就先压缩事务再分片；展示型余额、积分累计、账单汇总这类场景，异步加批量往往更划算。

拆分之后：汇总、对账与一致性

拆开容易，收口难。账户一旦分成多行，第一个问题就是“总余额怎么算”。

实时 SUM 只适合分片数很少的情况。分片一多，每次查询都扫一遍分片表，既慢又容易把读流量压到刚被写热的那些行上。更常见的做法是两层：展示侧维护一份汇总值，按固定周期从分片汇总并写入快照；需要精确值时再按账户实时求和。快照要记录切点时间，之后的增量用流水补上，避免“快照加增量”重复计算。

财务对账则依赖另一条链路：期初余额加上本期流水，应当等于期末余额。这条等式比任何缓存都可靠，也是发现拆分错误、重复记账、漏记的最终手段。流水表至少要包含业务单号、账户号、变动金额、变动前后余额、状态和时间，业务单号上建唯一索引，重复投递的消息在插入时就会失败，幂等自然成立。

一致性上要把“可用余额”和“账面余额”分开。异步记账期间，可用余额可以先按流水预估，账面余额以落库结果为准；两者出现偏差时有告警和对账任务兜底，而不是要求任何时刻都严格相等。跨分片转账是另一个难点：A、B 落在不同分片时，一个本地事务无法覆盖两行，只能用事务消息加补偿，或者把同一用户的账户固定到同一分片，把跨分片收敛成少数跨用户场景。无论哪种方案，都必须允许中间态存在，并且中间态可查询、可修复。

如何选型，以及几个常见的坑

方案没有绝对优劣，先问三个问题。

一是一致性要求。资金扣减、券核销这类操作不能出现超发或透支，必须强一致，优先压缩事务加行内条件更新；积分累计、账单统计可以最终一致，异步加批量更合适。二是并发量。用峰值并发乘以单次持锁时间，估算需要的并行度，再决定分几片；单行上限大致是持锁时间的倒数。三是审计要求。每一笔变动是否都要独立可查，决定了能不能合并记账；合并之后仍要保留明细流水，只是余额更新的次数变少。

几个容易踩的坑：

  • 拆分粒度拍脑袋。分得太细，汇总、对账、运维的成本都会上升；分得太粗，压不住峰值。建议按“峰值并发除以单行可承受并发”再留一倍余量来定。
  • 跨分片转账当成本地事务写。两次 UPDATE 中间失败就是脏数据，必须有事务消息或补偿任务，并且补偿要幂等。
  • 死锁只记日志不重试。热点账户上的死锁是常态，应用层要识别死锁与锁等待超时，做有限次重试并加随机退避，重试次数用尽再降级。
  • 幂等靠“先查后插”。并发下两个请求可能同时查到“不存在”，唯一索引才是可靠的闸门。
  • 锁等待时间设得过长。innodb_lock_wait_timeout 默认 50 秒，热点场景应调小，让请求快速失败而不是把连接挂死在那里。MySQL 8.0 提供的 NOWAIT 与 SKIP LOCKED 适合取任务队列这类场景，但账户扣减不能用 SKIP LOCKED 跳过被锁的行，那等于放弃一致性。
  • 分桶之后总打同一个桶。轮询要记录游标，桶空时及时跳过，否则拆分只是把热点从一行挪到了另一行。

小结

热点账户的本质不是数据量大，而是同一行上的持锁请求太多。先量一量事务的持锁时间，把远程调用、消息发送、慢查询挪出事务，用一条带条件的更新完成判断与扣减；这一步通常成本最低、收益最直接。仍然不够时再拆：按业务或用户分片、分桶，把并发摊到多行；能接受延迟的场景改为写流水加异步批量记账，用消息串行化保证同一账户的顺序。

拆分之后必须补齐汇总与对账：快照加增量算余额，期初加流水验结果，业务单号唯一索引保幂等。选型时看一致性、并发量和审计要求三件事，别为了拆分而拆分。最后提醒一句，死锁重试和幂等设计要在第一版就写进去，等到活动当天再补，往往来不及。
