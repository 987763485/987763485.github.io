TypeScript 5.0 装饰器与 const 泛型

本文属于《TypeScript 学习路线》第 51/74 篇
上一篇系列目录下一篇

“TypeScript 5.0”是这两年社区里被反复提起的名字，许多传言把装饰器重写、const 泛型甚至一批性能改进都打包进了这个版本。本文先把时间线摆正：截至 2021 年 4 月，TypeScript 的最新稳定版是 2021 年 2 月 23 日发布的 4.2，4.3 正在开发、按既有节奏会在 5 月与大家见面，而 5.0 既没有官方发布日期，也没有官方特性清单。在这个前提下，本文分别拆解装饰器标准化与 const 泛型这两个方向上的真实进展，并给出在 4.2 上就能落地的写法，帮读者分清“提案里的方向”与“今天能写进项目的代码”。

本文面向已经写过一段时间 TypeScript、被 experimentalDecorators 的怪异行为或者泛型推断的“类型变宽”困扰过的读者。读完之后，你应当能判断一条关于 5.0 的消息是事实还是猜测，也能知道在 4.2 与即将到来的 4.3 上，这两件事各自该用什么姿势应对。

先把版本坐标钉住

讨论“5.0 有什么”之前，必须先说清楚 TypeScript 的版本号意味着什么。它的 minor 版本号并不承载“重大重构”的承诺，而更像是一个按时间推进的发布批次：大约每三个月发布一个 minor，期间穿插若干 beta 与 rc。因此 4.2、4.3、4.4 这样的编号首先是时间刻度，其次才是功能刻度。

按这个节奏回看：4.2 于 2021 年 2 月 23 日发布，带来了更严格的 in 运算符检查、对元组长度与 abstract 构造签名的改进等；4.3 处于开发中，社区预期在 5 月发布。至于 5.0，它只是人们给“再往后若干个 minor 之后”起的一个方便称呼。官方从未给出 5.0 的日期，也没有发布过特性清单。任何声称“5.0 将于某月发布并包含某某特性”的说法，在 2021 年 4 月都只能算推测。

这里有一个容易被忽略的细节：版本号跨越整数并不意味着语言被重写。TypeScript 的演进一直是增量式的，破坏性变更需要经过弃用周期。即便真的走到 5.0，绝大多数项目也不会因为改一个版本号就编译不过。把 5.0 想象成“一次大清算”，是对其版本策略的误读。

三个不同的时间尺度

理解这两个话题，需要区分三种时间尺度。第一种是语言特性的落地时间，由 TypeScript 团队决定何时把某个语法纳入编译器；第二种是标准化的时间，由 TC39 的提案流程决定，从 stage 0 到 stage 4 可能跨越数年；第三种是生态适配的时间，涉及 Babel、各类构建工具、编辑器与大量存量代码。

装饰器恰好同时踩在这三条线上：TypeScript 早在 2015 年就实现了实验性装饰器，但对应的 JavaScript 标准提案至今没有走完流程。const 泛型则只涉及第一条线，是一个纯粹的编译器能力问题。把两者混在一起谈“5.0 会解决”，就会得出错误的预期。

装饰器：两套语法并存的现状

今天在 TypeScript 里写装饰器，用的是一套“实验性”语法。它由 experimentalDecorators 编译选项开启，从 2015 年随 1.5 版本引入，形态上接近注解：可以修饰类、方法、访问器、属性与参数，运行时表现为一个接收目标对象并可能返回替换值的函数。Angular 等框架的大量代码建立在这套语义之上。

这套语法的问题在于，它是 TypeScript 在标准尚未定型时的先行实现，与 TC39 后来推进的提案在语义上并不一致。最直观的差异是参数装饰器：实验性语法支持修饰构造函数或方法的参数，而 TC39 提案的方向里没有参数装饰器这一项。其次是对属性（字段）的处理，实验性语法把属性装饰器当作“在原型上打标记”，而提案希望字段装饰器能真正参与字段初始化，返回一个初始化函数。

提案不是“新版本号”，而是另一套语义

TC39 的装饰器提案在 2021 年 4 月处于 stage 3，也就是说设计方向基本确定，但仍在处理边缘情况与实现反馈。它与实验性语法的关系不是“升级”，而是“替换”：两者在同一个文件里不能混用，编译器要么按旧语义降级，要么按新提案降级。

提案的语义方向大致可以这样理解。类装饰器接收类本身与其上下文对象，可以返回一个新类来替换它；方法装饰器接收方法函数与上下文，返回的函数会替换原方法；字段装饰器接收一个“初始值为 undefined 的占位”和上下文，返回一个初始化函数，在实例构造时被调用。上下文对象里带有 kind、name、static、private 等元信息，取代了旧语法里散落在参数位置上的 target、key、descriptor。

需要强调：上面这段只是对提案形状的示意，context 的类型、返回值约束、字段装饰器的初始化时机，在 2021 年都还在讨论中。本文不给出“最终语法”，因为当时并不存在最终语法。

标准化为什么走了这么久

装饰器的标准化周期长，原因并不神秘，主要是三条。

第一，它同时被两类用户拉扯。一类是框架作者，希望装饰器足够强大，能改写类的形状、注入元数据、参与依赖注入；另一类是语言设计者，希望装饰器的行为可预测、可静态分析、不破坏引擎的优化。前者要能力，后者要约束，折中点需要反复试验。

第二，它与类字段的语义纠缠在一起。字段装饰器要参与初始化，就必须先确定字段初始化的顺序、this 的可见性、以及公有字段与私有字段在初始化阶段的差异。这些规则在 2021 年仍在调整，装饰器自然无法单独定稿。

第三，存量生态的迁移成本。Babel 与 TypeScript 都已经有大量基于旧语义的代码，一旦标准定稿，工具链需要提供过渡期，让旧代码继续编译、新代码用新语义。这个过程不可能靠一个版本号完成。

const 泛型：一个字面量被拓宽的老问题

第二个话题与标准无关，纯粹是类型推断的策略问题。TypeScript 在推断泛型参数时，倾向于把字面量类型“拓宽”为更宽的类型：传入 "get"，推断结果往往是 string 而不是 "get"。这个策略在多数场景下是合理的，它让函数签名不至于过度特化，但在需要保留字面量的场景里就成了麻烦。

问题在于 as const 是“调用方”的责任。库作者写了一个泛型函数，希望调用方传进来的字面量自动保留，却没法强制对方加断言；调用方忘了加，类型就退化成 string，错误要到很远的地方才暴露。这是一个责任错配：需要精确类型的是函数内部，付出代价的却是函数外部。

举个更贴近业务的例子。假设我们写一个事件总线，事件名用字符串字面量联合类型来描述，订阅与派发都要求事件名精确匹配。如果派发函数是普通泛型，传入 "order:created" 会被拓宽成 string，联合类型的检查就形同虚设；只有调用方逐处加 as const，才能拿回那层保护。这类场景在状态机、路由表、权限码里非常普遍，也正是提案被频繁提起的原因。

提案想做的事

社区里讨论的“const 类型参数”，思路是在类型参数声明处加一个修饰符，让该参数在推断时按 const 断言的方式处理，从而保留字面量、把对象成员变为只读。这样责任就回到了函数定义方：库作者声明“我这个参数需要字面量”，调用方无需额外书写。

必须说清楚：截至 2021 年 4 月，这个语法在 4.2 上无法通过编译，4.3 的开发内容里也没有它。修饰符的具体拼写、它与只读修饰符的交互、对数组与元组的处理，都还在讨论。任何“5.0 一定这样写”的说法都是猜测。

在 4.2 上该怎么写

既然提案没落地，工程上只能靠现有工具把坑填上。三种做法各有取舍。

第一种是调用方加 as const，也就是上一节展示的写法。优点是零成本、语义明确；缺点是约束不了别人，API 文档里得反复提醒。

第二种是让泛型参数继承一个更窄的约束，用条件类型把字面量“捞”回来。代价是签名变得复杂，报错信息也不够友好。

第三种是用重载或者显式的类型参数，把推断的责任交给调用方。它最笨，但在关键 API 上最可控。

三种做法的共同点是：要么牺牲调用体验，要么牺牲类型精度。这正是 const 泛型提案存在的理由，也是它值得关注的原因。但关注不等于可用，把它写进生产代码之前，先确认编译器版本支持。

升级策略上的建议

对多数项目来说，跟进 TypeScript 版本的合理策略是“跟 minor 但不追传言”。具体做法是：把 typescript 固定在某个 minor 的最新补丁上，读该版本的 release notes 确认破坏性变更；升级前跑一遍类型检查与测试；对于装饰器，明确项目用的是旧语义还是准备迁移，不要在同一个代码库里两种语义混着写。

还需要提醒一点：experimentalDecorators 与 emitDecoratorMetadata 会影响产物形状，升级编译器时这两项的行为变化往往比语法本身更容易出问题。如果项目依赖元数据做依赖注入，升级前务必在测试环境验证反射结果。

发布节奏与如何辨别传言

TypeScript 的发布节奏相对稳定：大约每三个月一个 minor，beta 用于收集反馈，rc 用于稳定收尾。这个节奏意味着，任何“下个版本会有什么”的可靠信息，都应该能在 beta 的 release notes 里找到对应条目。没有进入 beta 的特性，谈“即将发布”都为时过早。

辨别传言的方法可以归纳为三条。第一，看来源：官方博客的 release notes、GitHub 上的 milestone 与合并记录，是唯一可信的清单；二手文章里的“据悉”“预计”都要打折。第二，看阶段：一个特性在提案阶段、在编译器里以实验选项存在、默认开启，是三件完全不同的事，混为一谈就会产生“已经支持”的错觉。第三，看语法：如果一篇文章给出的示例代码无法在你手上的 4.2 里通过编译，那它谈的就是方向而不是现状。

小结

本文讨论的是方向，不是可用特性。截至 2021 年 4 月，TypeScript 的最新稳定版是 4.2，4.3 按节奏在 5 月发布，5.0 没有官方日期与特性清单，任何具体承诺都不可信。

装饰器方面，experimentalDecorators 是 2015 年留下的先行实现，TC39 提案处于 stage 3，两者语义不同、不能混用；提案在类、方法、字段三类装饰器上给出了更清晰的上下文与返回值约定，但最终细节尚未定稿。const 泛型方面，它要解决的是泛型推断把字面量拓宽的问题，把 as const 的责任从调用方移到定义方；在 4.2 上只能用断言、约束或显式类型参数来变通。

实践建议只有一句：以官方 release notes 为唯一依据，把版本号固定在可验证的 minor 上，等特性真正进入稳定版再改代码。
