缓存预热与热点 key 处理

缓存把读请求挡在数据库之前，可缓存本身并不是一开始就热的。发布、扩容、故障恢复之后，缓存里空空如也，原本被挡住的流量会一次性压到数据库上。本文讨论两件相邻的事：怎样在流量到来前把数据装进缓存，以及当某个 key 的访问量远超其他 key 时，怎样识别并拆解这份压力。

本文面向已经用上 Redis、正在为容量和稳定性做准备的开发者。读完后你应当能排出一次预热的时机与步骤，并为热点 key 选出一套可落地的组合手段。

冷启动的代价

缓存的全部价值建立在“命中”二字上，命中率越高，数据库承受的读压力越小。但命中率不是常量，而是一条从零向上爬的曲线：缓存刚建立、刚清空、刚换机器时它处在最低点，而业务流量不会因为缓存没准备好就推迟到来。

冷启动的来源无非三类：全新环境、扩容后本地缓存为空的新节点、故障恢复后的一片空窗口。

举个示意性的例子：某详情接口稳态读 QPS 为 2 万（示意值），命中率 95%（示意值），回源只有 1000 QPS（示意值）；冷启动时命中率为零，2 万 QPS（示意值）全部压向数据库，是平时的 20 倍。连接池先被打满，接着排队、超时，上游重试又放大一轮。

所以预热要同时解决两个问题：覆盖率，即流量到来时目标 key 有多少已在缓存里；速率，即装载过程给数据库和缓存带来多大压力。只追求覆盖率而不控制速率，预热自身就会变成一次故障。

预热的四个时机

预热不是上线时做一次就够的动作，它和系统的生命周期绑定，以下四个时机都应提前安排。

发布前。 新版本常引入新的 key：字段结构变了、序列化格式换了、key 里多了维度。这些 key 在旧缓存里不存在，发布后必然全部回源。做法是灰度期间双读双写，发布前把新 key 灌满，发布后先看新 key 的命中率，达标再切读，并保留旧 key 以便回滚。

扩容后。 新实例的本地缓存和远端分片都是空的。Kubernetes 里可以用 startupProbe 拖住新 Pod，让它在就绪探针通过前先跑完预热；接入层按权重逐步放量，而不是一次性把新副本的权重拉到和其他副本一样。

大促前。 大促的热点可以预测：主推商品、会场配置、活动规则。提前一段时间（比如一到两小时，示意值）把清单灌进去，同时给过期时间加随机抖动，避免这批 key 在同一时刻集中失效；对确定会爆的几个 key，可以提前建好副本。

故障恢复后。 Redis 重启后能恢复多少数据取决于持久化配置：RDB 是快照时间点，AOF 的完整度取决于 appendfsync，主从切换还可能丢掉未同步的写入。恢复后缓存可能只剩一部分甚至全空，此时要先收紧限流再启动预热。预热脚本应当做成常备工具，几分钟内能拉起。

预热的数据从哪来

确定要预热哪些 key，有三种常见来源，适用范围差别很大。

全量 从库或数仓导出全表，逐条构造 key 数据量可控的维表、配置 载入大量无人访问的数据，耗时长
抽样 按业务规则圈定，如近七天有销量的商品 口径明确的业务 规则之外的长尾仍会回源
访问日志 取网关日志或代理统计中访问靠前的 key 流量已跑过一段时间 依赖日志的完整性与时效

预热与限流的配合

预热和限流的顺序不能颠倒：先限流、后预热。限流是兜底，保证任何情况下回源量不超过数据库的承载；预热是优化，让尽可能多的请求不必回源。反过来做，一旦预热失败或只完成一半，系统就在没有保护的情况下迎接流量。

预热任务自身也要限速。它消耗数据库的读能力、应用内存和网络带宽，这些资源与线上请求共享。常见做法有三种：给预热任务单独的数据库连接池；用令牌桶把速率压在一个固定值；把任务安排在低峰期或以低优先级运行。

还有一个容易被省略的环节：就绪判定。预热跑完不等于可以放流量，判据可以是目标 key 的覆盖率达到某个比例（比如 90%，示意值），或回源 QPS 回落到阈值以下。这个判据应接入发布流程与健康检查，而不是靠人盯监控。

    B --> C{覆盖率达标}
    C -- 否 --> B

热点 key 的识别

热点 key 指单位时间内访问次数远高于同批 key 平均水平的 key。它可能是一个明星商品的详情、首页那份被所有人读取的配置，或某个活动页的库存计数。它的危险在于无法被分片摊平：无论集群有多少节点，这个 key 始终落在同一个分片上，而 Redis 处理命令是单线程的，一个 key 就能把一个分片的 CPU 吃满。

识别手段有四类，通常组合使用。

Redis 自身的统计最直接。把淘汰策略设为 LFU 系（如 allkeys-lfu）后，可以用 OBJECT FREQ 查看单个 key 的频次，也可以用 redis-cli 的 hotkeys 选项拉一份近似榜单。它基于概率采样，排名大体可靠，绝对值不必当真。MONITOR 开销极大，只适合短时间排查；SLOWLOG 只记录耗时长的命令，高频小命令不在其中。

客户端统计最贴近业务。在缓存 SDK 或数据访问层做一层滑动窗口计数，定期把超过阈值的 key 上报。好处是能拿到调用方、接口名与 key 的对应关系，直接定位业务；坏处是每个实例只看到一部分流量，需要汇总后再判断。

代理层统计最完整。请求经过代理时统一计数，天然覆盖所有客户端，也不占用业务进程的资源。托管缓存服务的热 key 分析原理大致相同。

监控与日志是补充。网关日志按 URL 与参数聚合，能看出哪个接口在被打，再反推具体 key；它有延迟，适合复盘而非秒级响应。

判定标准要写清楚，否则告警会变成噪音。建议同时满足三条：超过同批 key 平均值的一定倍数、持续时间跨过若干统计窗口、绝对次数超过下限。单次毛刺不处理，持续热点才处理。

热点 key 的处理手段

识别只是开始，处理要按读热点与写热点分开考虑：多数热点是读热点，写热点少见但更难处理。

本地缓存与多级缓存

最有效的一招是把热点搬到离请求最近的地方：进程内缓存作为 L1，Redis 作为 L2。热点 key 的读请求在本地内存就能满足，不再落到 Redis，延迟从毫秒级降到微秒级，分片压力也随之消失。

代价是新鲜度。L1 的值可能比 L2 旧，旧多久取决于本地 TTL。常见做法是给 L1 设很短的过期时间（比如几秒，示意值），再配合变更时的广播失效；广播可能丢失，短 TTL 是最后一道保险。本地缓存还必须有容量上限与淘汰策略，无界的 map 会一直涨，最后触发频繁 GC 甚至 OOM。

写入时要写满 N 份，读请求才可能命中任意一份。这带来写放大：一次写变成 N 次，N 越大写成本越高，副本间的不一致窗口也越长。所以 N 要按读写比来定，读远多于写时才值得。失效也必须覆盖全部副本，漏掉一份就会长期返回旧值。

读写分离

Redis 支持主从复制，可以让热点的读走从库，主库专心承接写。对读多写少的热点，加几个从库确实能分担压力。但它有两个限制：复制是异步的，从库可能读到稍旧的数据；从库数量受主库复制压力和运维成本约束，不可能无限加。写热点靠它解决不了。

请求合并

要注意两点：回源函数的 panic 会传播给所有等待者，需要在内部 recover；等待者共享同一个超时，回源很慢时所有请求会一起变慢，因此合并层要配合超时与降级。

限流与降级

前面所有手段都失效时，限流是最后一道闸门。按 key 维度而不是接口维度限流，可以让失控的热点只影响它自己。超过阈值的请求直接返回兜底值：默认价格、静态页面或上一次的旧值。降级的目标不是正确，而是让系统活着。

代价与边界

这些手段没有一个是免费的：本地缓存付出新鲜度与内存，多副本付出写放大与不一致窗口，请求合并付出尾延迟，限流付出部分请求的体验。选择本质上是在一致性、成本与复杂度之间取舍。

一致性代价值得单独说一句。凡把同一份数据复制到多处，都会产生一个“某个副本还没更新”的窗口，长度由失效机制决定：广播失效是毫秒级但可能丢消息，短 TTL 确定但上限更长。对价格、库存这类不能出错的字段，要么不用本地副本，要么读取时做一次版本校验。

容器化环境把本地缓存的问题放大了。Pod 是临时的，重建、滚动更新、节点驱逐都会让本地缓存归零；水平扩容时新副本缓存为空，若流量按连接数平均分配，新副本会用同样比例承担回源，反而成为最慢的一环。应对办法是：预热完成前不接流量，扩容按权重逐步放量，并始终把本地缓存当作纯加速层。容量要有明确上限（比如占堆内存 10%，示意值），超过就淘汰，同时监控命中率、淘汰次数与 GC 时间。

最后区分两个容易混淆的概念。大 key 说的是体积，一个 value 几 MB 甚至几十 MB；热 key 说的是频次，key 本身可能很小，但每秒被访问很多次。故障表现不同：大 key 拖慢网络传输、阻塞删除与迁移，热 key 打满单个分片的 CPU；两者也可能重叠，又大又热是最糟的组合。处理手段也不同：大 key 要拆分、压缩、用 UNLINK 异步删除；热 key 要副本、本地缓存与限流。统计时把两个维度分开，不要用一套阈值覆盖。

小结

缓存预热是在流量到来之前，用可控的速率把可预期的数据装进缓存；热点 key 处理是在压力已经集中到某一点时，把这份集中拆开。前者解决从零到一，后者解决从一到多。

落地时有几条经验：预热要先限流后装载，并有可重入约束与就绪判据；热点识别要组合 Redis 统计、客户端计数与代理层统计，判定标准带持续时间和相对倍数；处理按读热与写热分开选择，本地缓存优先，副本与拆分次之，限流兜底；容器化下把本地缓存当作纯加速层，假设它随时会空。
