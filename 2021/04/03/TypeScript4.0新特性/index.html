TypeScript 4.0 新特性

本文属于《TypeScript 学习路线》第 45/74 篇
上一篇系列目录下一篇

TypeScript 4.0 发布于 2020 年 8 月 20 日，到本文写作时已经是上一个年度的大版本。它没有引入颠覆性的语法，却在类型系统与工程能力上补齐了几处长期被吐槽的短板：元组可以展开拼接，元组元素可以起名字，类属性可以由编译器自行推断，错误处理也在静态类型上收紧了口子。

本文按“是什么、为什么、怎么做、坑在哪”的顺序，把这批新特性逐个讲清楚，并给出可以直接落地的配置与写法。阅读之前，假设你已经熟悉 TypeScript 的基础类型与 tsconfig.json 的常用选项。

可变元组类型

可变元组类型（Variadic Tuple Types）是 4.0 最核心的一项能力。它允许在元组类型里使用展开语法，把另一个元组或数组类型“铺开”到当前位置，从而描述长度不固定、但内部结构有规律的类型。

标签元组元素

标签元组元素（Labeled Tuple Elements）解决的是可读性问题。元组类型本身只有位置，没有名字，[string, string, boolean] 摆在接口里，调用方很难判断每个位置该传什么。

类属性推断

在 noImplicitAny 开启的项目里，4.0 之前的类属性必须显式标注类型，否则编译器会报“属性隐式具有 any 类型”。4.0 改变了这一点：编译器会根据构造函数里的赋值，以及类体中其他位置的赋值，推断属性的类型。

推断发生在所有赋值语句之后，取的是各次赋值的联合类型。如果构造函数里先赋 0，再在某个分支赋 null，属性类型就是 number | null，后续使用必须处理空值。

这项改动对老项目的影响是双向的。原本靠显式 any 压住的属性，现在会被推断成具体类型，一些以前能通过的运算会开始报错；反过来，原本因为忘记标注而编译失败的新代码，现在可以直接通过。升级后若出现“属性不存在于类型上”的错误，优先检查推断结果是否比预期更窄。

需要强调的是，推断只覆盖“在类内部能被看到的赋值”。通过 Object.assign(this, init) 这类动态写入，编译器无法追踪，属性仍会被推断为 undefined 或直接报错，此时应当显式标注。

短路赋值运算符

??=、||=、&&= 三个运算符是逻辑赋值表达式，把“先判断、再赋值”合并成一步。它们与 += 属于同一类语法糖，只是右侧的条件从算术变成了逻辑短路。

三者的差别完全由左侧的判断规则决定。??= 只认 null 与 undefined，这是它与 ||= 最关键的区别：当属性的合法值可能是 0 或空字符串时，用 ||= 会把有效值当成缺失值覆盖掉，而 ??= 不会。

这三个运算符还带来一个容易被忽略的好处：左侧表达式只求值一次。手写 obj.a.b ?? (obj.a.b = value) 时，obj.a.b 在条件与赋值中各出现一次，属性是 getter 时就会执行两遍；??= 只求值一次，语义更准确。

在 4.0 之前，这类写法需要 Babel 插件或运行时辅助函数来降级。4.0 之后编译器可以直接输出目标版本对应的代码。

catch 变量默认 unknown

这是 4.0 里最容易让老项目编译失败的一项改动。在此之前，catch 子句捕获到的变量类型是 any，可以随意访问属性、随意调用方法，编译器一概不管。4.0 把默认类型改成了 unknown。

原因很直接：JavaScript 允许抛出任何值，字符串、数字、普通对象都可以，throw 'boom' 完全合法。把它标成 any 等于向编译器撒谎，说这个值一定拥有某些成员。改成 unknown 之后，使用前必须收窄，这正是类型系统应有的态度。

构造器签名与 new

4.0 对构造器签名的推断做了一处并不显眼、却影响不少库类型定义的修正。在类型位置，new (...args) => T 表示“可以用这些参数构造出 T 的类”，它与普通函数签名 (...args) => T 是两回事：前者描述的是 new 调用的形状，后者描述的是直接调用的形状。

把 new 换成普通箭头函数，new ctor() 这一行就无法通过检查，因为编译器无法保证该值可以被构造。区分这两种签名，是写工厂函数、依赖注入容器和混入（mixin）时的基本功。

4.0 的修正在于：当一个泛型参数被推断为类时，编译器现在能更准确地保留它的构造签名，而不是退化成 any 或丢掉参数类型。实际表现是，create(UserService, 123) 这类参数不匹配的调用会更早报错，而不是悄悄放过。对类型定义作者来说，这是好事；对使用者来说，升级后可能出现一批此前被掩盖的错误。

需要留意的是，抽象类不能直接赋给 new (...args) => T。抽象类本身不可实例化，只能作为基类被继承。在 4.0 里表达“抽象构造器”仍然需要绕路，通常写成接口加 prototype 约束，或者干脆放宽为 Function。这一限制在后续版本中才有专门的语法支持，本文不展开。

增量构建与编辑器体验

tsc 的构建模式（--build）在 4.0 里得到了一次比较实在的改进，重点落在“只做类型检查、不产出文件”的场景。

–noEmit 下的增量构建

在 4.0 之前，--build 与 --noEmit 基本不能一起用：构建模式依赖产出的声明文件与输出文件来判断下游项目是否需要重新编译，一旦禁止产出，增量信息就断了，只能整体重编。4.0 之后，构建模式在 --noEmit 下也能保留增量能力，适用于“用 tsc 只做类型检查、产物交给 Babel 或打包器”的工程。

本文不给出具体提速比例，结果与项目规模、依赖图深度强相关。可以确定的是，改动越集中、项目引用划分越清晰，增量复用的比例越高。

还有一点容易踩坑：修改编译选项或升级 TypeScript 版本后，旧的 .tsbuildinfo 可能与新配置不匹配。遇到“改了代码却没重新检查”的怪现象，先删掉它再试。

编辑器侧的变化

4.0 起，编辑器在大项目里可以按需加载语义信息，而不必等整个工程解析完毕，代码补全与跳转的等待感有所缓解；部分场景下还会启用更轻量的语义模式。这些属于体验层面的优化，具体行为随编辑器插件版本而异，本文不做展开。

升级注意事项

把项目从 3.x 升到 4.0，绝大多数报错来自下面三类。建议按顺序处理，一次只动一类，避免错误互相掩盖。

第一类是 catch 变量变成 unknown 引发的访问错误。表现是大量 Object is of type 'unknown' 或 Property 'message' does not exist on type 'unknown'。处理方式不是批量加 as any，而是先看看错误是否来自少数几个公共的错误处理函数：把收窄逻辑集中在那里，业务层的 catch 往往只需要透传。若报错文件太多，可以先用 useUnknownInCatchVariables: false 让编译通过，再按模块逐步打开，把开关当作进度条而不是终点。

第二类是类属性推断改变带来的行为差异。典型症状是某个属性以前是 any，现在变成了联合类型，于是赋值或比较开始报错；另一种相反的情况是，属性被推断成了过窄的字面量类型，后续赋新值失败。前者说明原本的类型标注缺失，补上标注即可；后者通常需要在声明处写明更宽的类型，或者在赋值时加 as const 之外的显式类型。注意推断看的是构造函数的全部赋值路径，只要有一条分支赋了 undefined，整个属性就会带上 undefined。

第三类是 delete 操作数的限制。在 strict 模式下，delete 只能作用于可选属性，删除一个必需属性会被拒绝：

这条规则的意义在于：删除必需属性会让对象不再满足接口约定，后续代码却仍按接口使用它，运行时的 undefined 就是这样埋进去的。若确实需要删除，应把属性声明为可选，或者改用重建对象的方式，而不是绕开检查。

除这三类之外，++ 与 -- 在只读属性或可选链上的使用也更严格，obj?.count++ 这类写法可能不再被接受；部分内置类型定义的签名有微调，升级后偶尔会出现推断结果变化，重新声明局部变量类型通常即可解决。

升级顺序上，本文推荐先在独立分支上升级编译器、跑一次完整的类型检查，记录错误数量，再分模块清理。不要在同一次提交里既升级版本又重构代码，否则很难判断错误来自哪一边。CI 里应保留一次 tsc --noEmit 的独立检查，把类型错误拦在合并之前。

小结

TypeScript 4.0 的价值不在语法糖，而在把几个长期靠约定维持的地方交给了类型系统。可变元组类型让参数列表可以整体搬运，标签元组把位置的含义写进了类型，类属性推断减少了无谓的注解，短路赋值把“判断再赋值”压缩成一次求值。catch 变量改成 unknown 是最需要提前准备的改动，它会让老代码暴露出一批被 any 掩盖的问题，但收窄之后的错误处理才是可信的。升级时按“catch、属性推断、delete”三类错误分批处理，配合 --noEmit 的增量检查与合理缓存 .tsbuildinfo，可以把迁移成本控制在可预期的范围内。
