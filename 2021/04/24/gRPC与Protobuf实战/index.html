gRPC 与 Protobuf 实战

本文属于《Go 微服务架构》第 8/35 篇
上一篇系列目录下一篇

当服务拆分到一定数量，进程内的方法调用就变成了网络请求，接口契约、序列化开销和连接管理会同时成为问题。很多团队仍用 JSON over HTTP 传递数据，接口文档靠人工维护，字段含义只能从代码里猜。本文从 proto3 语法讲起，逐步搭建一个 grpc-go 服务，并讨论四种调用模式、超时传播、拦截器与常见陷阱。

读完之后，读者应能独立定义 proto、生成代码并跑通一次调用，也能判断哪些场景适合 gRPC、哪些场景继续用 REST 更划算；文中示例基于 Go 1.16，协议部分与语言无关。

为什么用 gRPC

REST 加 JSON 的组合足够简单，浏览器、curl 和网关都能直接处理，这也是它长期占主流的原因。但当调用发生在服务之间，几个弱点会被放大：JSON 是文本，字段名在每个请求里重复传输，序列化与解析都要付出额外开销；接口没有机器可校验的契约，字段类型和必填性只能靠文档与口头约定；HTTP/1.1 下同一连接上的请求基本串行，需要靠连接池堆并发；流式场景只能退化成轮询或自建长连接协议。

gRPC 针对的正是这几点。它用 .proto 文件描述服务和消息，这份文件既是接口定义，也是生成代码的输入，客户端与服务端的类型由工具保证一致，文档不再另写一份。消息用 Protobuf 编码，字段以编号和类型标识，省去重复的字段名，整数用变长编码，体积通常明显小于等价的 JSON，解析也不需要先做字符串匹配。

传输层是 gRPC 的另一半。它建立在 HTTP/2 之上，一条 TCP 连接可以并发承载多个流，头部经过压缩，请求之间不再互相阻塞；同时 HTTP/2 的流语义天然支持服务端推送和双向传输，四种调用模式才能落在同一套协议里。加上官方提供的多语言代码生成，Java、Go、Python 服务可以共用一份 proto，跨团队协作的摩擦小很多。

代价也需要提前知道：浏览器不能直接发起标准 gRPC 调用，前端接入通常要靠网关转换；二进制报文不能像 JSON 那样直接肉眼看，排障需要专门工具；契约一旦发布就要遵守兼容规则，随意改字段的代价比改 JSON 接口更高。

proto3 语法要点

一个 proto 文件由语法声明、包名、选项和若干 message、enum、service 组成。下面是一段订单服务的定义，覆盖了日常最常用的语法元素。

字段编号是编码后的身份标识，而不是给人看的顺序。1 到 15 的编号在编码时只占一个字节，适合放高频字段；16 以上的编号占两个字节。编号一经使用就不应更改，也不要在同一个 message 内重复。repeated 表示列表，proto3 默认对数值类型使用打包编码；map 表达键值对，键只能是整数或字符串；oneof 保证一组字段中最多只有一个被设置，适合表达互斥的支付方式；枚举的第一个值必须为 0，通常命名为 XXX_UNSPECIFIED，用来表示未设置。

reserved 是兼容性的护栏。删除字段时，应同时保留它的编号和名称，防止后来的人复用编号，把旧数据解释成新含义。proto3 移除了 required，所有字段在语法上都是可选的，业务上的必填需要应用层校验。

向后兼容的规则可以归纳为几条：只新增字段、不复用编号、不改变已有字段的类型和语义、枚举只在末尾追加值。旧版本客户端收到新字段会把它当作未知字段保存并透传，不会报错；把 int32 改成 string 这类操作则会直接导致解析失败。

四种调用模式

gRPC 的流式能力写在方法签名里：stream 出现在返回值位置表示服务端流，出现在参数位置表示客户端流，两边都有则是双向流。

一元调用是最常见的形式，客户端发一个请求、服务端回一个响应，行为和普通函数调用接近，适合查询、创建、更新这类有明确起止的操作。服务端流适合“一次请求、多次推送”的场景，例如订单状态订阅、日志跟随、大结果集分批下发；客户端拿到流之后循环读取，直到收到结束信号。客户端流方向相反，适合指标上报、文件分片上传这类“多次发送、最后汇总”的流程。双向流两端都可以独立收发，适合实时协作、聊天和长连接的交互式任务。

选择模式时不要为了“先进”而用流。一元调用最容易做重试、鉴权和监控，能用一元解决就不要引入流；只有当数据确实持续产生，或者单条消息大到需要分片时，流才划算。流一旦建立，连接生命周期变长，超时、取消和背压都要额外设计。

生成代码与项目布局

Go 侧需要两个插件：protoc-gen-go 负责消息类型的序列化代码，protoc-gen-go-grpc 负责服务端接口和客户端存根。安装方式如下，团队内应约定同一版本，避免各人生成的代码不一致。

生成时把 proto 目录和输出目录分开，保持 import 路径稳定：

每个 proto 会产出 order.pb.go 和 order_grpc.pb.go，前者是消息结构体，后者包含 OrderServiceServer 接口、注册函数和 OrderServiceClient。这两类文件都由工具生成，不要手改；重新生成前也不要把业务代码写进去。推荐把生成命令固化到脚本或 Makefile，proto 变更后统一执行，生成结果一并提交，这样构建机不需要安装 protoc。

目录上可以按“契约、生成物、实现、入口”四层摆放：api/order/v1 放 proto，gen/order/v1 放生成代码，internal/service 放业务实现，cmd/server 与 cmd/client 放入口。proto 的包名带版本号，后续不兼容的变更可以新开 v2，两版并存一段时间，比在一个文件里硬改安全得多。

Go 服务端与客户端

服务端实现生成的接口即可。嵌入 UnimplementedOrderServiceServer 是一个好习惯，后续 proto 新增方法时，旧实现不会因为缺少方法而编译失败，而是返回明确的“未实现”错误。

客户端先建立连接，再创建存根。连接应当复用，不要每次请求都 Dial，gRPC 的长连接和多路复用正是建立在复用之上的。

超时不是客户端单方面的事。gRPC 会把剩余时间写入 grpc-timeout 头，服务端拿到的 ctx 自带同一个 deadline，处理函数里再调用下游时，只要继续传递这个 ctx，剩余预算就会逐跳缩短，整条调用链不会出现“上游已经超时、下游还在慢慢算”的情况。因此处理函数中不要用 context.Background() 替换传入的 ctx，也不要在超时后继续写数据库。服务端还可以设置默认超时兜底，防止客户端不传 deadline 的请求长期占用资源。

拦截器：日志、认证与重试

拦截器是 gRPC 的中间件，一元调用和流式调用各有一套接口。一元服务端拦截器的签名固定，拿到方法名、请求和 handler，就能在前后插入逻辑。

日志之外，最常见的用途是认证：从 metadata.FromIncomingContext 取出 authorization，校验后把用户信息放进新的 context 传给业务。认证失败返回 codes.Unauthenticated，不要在业务代码里各写一套。多个拦截器用 ChainUnaryInterceptor 串联，顺序就是执行顺序，通常把恢复 panic 和日志放在外层，认证放在内层。

客户端重试也可以做成拦截器，但要守住三条：只重试幂等方法，例如查询；限制次数并加退避，避免故障时放大流量；每次重试都检查 ctx 的剩余时间，预算不足就直接返回。流式调用一旦开始传输就不适合整体重试，重试逻辑应放在建立流之前。

状态码、错误详情与网关转换

gRPC 有一套跨语言统一的错误模型：每个响应都带状态码和消息，Go 里用 status.Error 构造，用 status.FromError 解析。业务错误不要用自定义 error 字符串表达，也不要用字符串比较判断错误类型，否则跨语言调用时客户端根本无法识别。

常用状态码的含义需要约定清楚：参数不合法用 InvalidArgument，资源不存在用 NotFound，状态冲突用 FailedPrecondition 或 Aborted，未登录用 Unauthenticated，无权限用 PermissionDenied，限流用 ResourceExhausted，下游不可用用 Unavailable，超时用 DeadlineExceeded，兜底用 Internal。Unavailable、Aborted 和 DeadlineExceeded 通常可以重试，其余多数不该盲目重试。gRPC 还允许在状态里附带结构化的错误详情，例如逐字段说明校验失败的原因，客户端可以据此定位到具体输入。

对外提供 HTTP 接口时，不必为每个方法手写一层 controller。grpc-gateway 读取 proto 里的 HTTP 注解，生成一个反向代理，把 REST 请求转换成 gRPC 调用，再把响应序列化成 JSON。

这样同一份 proto 同时产出 gRPC 存根和 HTTP 路由，状态码会按映射表转换，例如 NotFound 变成 404、InvalidArgument 变成 400、Unavailable 变成 503。需要注意 JSON 映射规则与手写接口不完全一样：字段名默认转成小驼峰，枚举输出名称字符串，64 位整数输出为字符串以免精度丢失，前端对接时要按这个约定解析。

边界应当划清楚：面向公网、需要浏览器直接访问、依赖 CDN 缓存或文件上传的接口，继续用 REST 更省事；服务内部对延迟敏感、调用量大、需要流式传输或跨语言复用的接口，用 gRPC 收益更明显。常见做法是边缘用 REST，内部用 gRPC，由网关完成一次转换，而不是全站二选一。

常见坑与调试工具

第一类坑来自字段编号。删除字段后没有 reserved，后来的人复用了同一个编号，旧数据会被按新类型解析，轻则乱码，重则写坏业务数据。更隐蔽的是类型不兼容但 wire type 相同的情况，程序不报错，值却完全不对。修改 proto 时把“编号是永久资产”当作硬规则。

第二类坑是默认值。proto3 不区分“字段未设置”和“字段被设置为零值”，string 的空串、int32 的 0、bool 的 false 在反序列化后看起来一样。如果业务需要区分，可以使用 google.protobuf.StringValue 这类包装类型，或者使用较新版本 protoc 支持的 optional 字段，生成代码会带指针或 HasXxx 方法。用 GetXxx() 读值方便，但它永远无法告诉你字段到底有没有传。

第三类坑是消息过大。grpc-go 默认单条消息有 4 MB 的接收上限，超限会直接报 ResourceExhausted。把上限调大只是把问题推迟，正确做法是分页、分片或用流式传输，并在协议设计阶段就限制列表长度。大消息还会长时间占用内存和连接，给故障排查带来困难。

第四类坑是流控与背压。HTTP/2 有流量窗口，接收方处理慢时窗口缩小，发送方会被阻塞。服务端流如果无脑循环 Send，遇到慢客户端就会堆积，所以要在每次发送后检查错误，并在 ctx.Done() 时及时退出。客户端流则要控制生产速度，避免把内存里的数据一次性灌进缓冲区。

第五类坑是负载均衡。gRPC 连接长、并发高，一个连接会一直落在同一个后端实例上，四层负载均衡按连接转发，结果就是流量倾斜。需要客户端负载均衡配合服务发现，或者使用支持 HTTP/2 的七层代理、服务网格来按请求分发。

调试方面，grpcurl 可以在服务端开启反射后直接列出服务、查看消息结构并发起调用，不必先写客户端；生产环境不要长期开放反射，至少在网关层限制来源。日志里记录方法名、状态码和耗时已经足够定位多数问题，不建议打印完整请求体，既有隐私风险，也会让日志体积失控。

小结

gRPC 的价值不在“新”，而在于把接口契约、代码生成和传输效率放进同一套工具链。写好 proto 是第一步：字段编号一旦发布就当作永久资产，只新增字段，删除字段要保留编号。调用模式按数据形态选择，能用一元解决就不要引入流；超时要从入口一路传下去，拦截器统一处理日志、认证和有限重试。错误用标准状态码表达，对外接口交给网关转换，内部服务保持二进制通信。字段默认值、消息大小、背压和负载均衡这几个坑，最好在协议设计阶段就预留方案，而不是等线上出问题再补。
