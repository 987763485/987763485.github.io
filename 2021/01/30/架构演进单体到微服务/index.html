架构演进：单体到微服务

单体应用并不是技术债的同义词，微服务也不是架构成熟的标志。本文从“该不该拆”讲起，依次讨论边界划定、数据所有权、服务通信、平台前置条件与迁移路径，最后落到组织与度量。读者对象是正在维护单体系统、准备做服务化改造的后端工程师与团队负责人。

先判断该不该拆

很多团队把微服务当成架构升级的默认选项，却很少先问一句：当前的问题真的是单体造成的吗？单体系统最常见的痛点其实是模块边界混乱、构建与发布耦合、缺少自动化测试，这些问题在拆成服务之后一样存在，甚至会被网络调用放大。

如果出现下面几种情况，建议先不拆。第一，团队规模还小，沟通成本远低于维护几十个服务的成本。第二，领域边界尚不清晰，业务仍在快速试错，今天划出的“订单服务”可能下个季度就要和“履约服务”合并。第三，规模压力可以用更便宜的手段解决，例如加缓存、读写分离、垂直扩容，这些手段的复杂度远低于分布式改造。

此时更合适的目标是模块化单体（modular monolith）：仍然只有一个部署单元，但内部按业务模块分包，模块之间只通过显式接口通信，禁止跨模块直接读写对方的表；数据库可以按模块划分 schema，但保留在同一个实例里，事务仍然是本地的。模块化单体不是“落后的过渡态”，对相当多的业务来说它就是合理的终点：既保留了重构边界的自由，又不需要为分布式付出代价。

微服务真正交换来的是组织可扩展性，让多个团队能够独立发布、独立扩容、独立承担故障。如果组织本身没有这个需求，这笔交易就不划算。拆分过早的典型后果，是把进程内的方法调用变成网络调用，把编译期能发现的错误推迟到运行时，把一次断点调试变成跨服务的日志检索。

决定要拆之后，先要把收益和代价都写清楚。下表是笔者常用的对照清单。

维度 拆分带来的收益 必须承担的代价
发布 服务独立部署，变更影响面小 多套流水线、版本矩阵与联调成本
组织 团队按业务端到端负责 接口协商与跨团队沟通变多
伸缩 只给热点组件扩容 容量规划更碎，资源利用率下降
隔离 故障域变小，可局部降级 网络失败、分布式数据、排障链路变长
技术 允许局部替换技术栈 多语言带来的招聘与维护成本

五个常见驱动力是独立部署、团队自治、按组件伸缩、故障隔离与技术异构；代价则是网络失败、跨服务没有本地事务、可观测性缺口，以及 CI/CD、值班与基础设施投入成倍增加。

判断是否值得拆，可以做“收益归属”分析：收益无法落到具体团队或容量瓶颈上，它大概率只是技术兴趣。回退成本会随服务数量上升，决策时宁可保守。

边界：按限界上下文切分

服务边界是对业务模型的切分，而不是对代码目录的切分。领域驱动设计（DDD）中的限界上下文（bounded context）提供了一个可靠依据：同一个词在不同上下文中含义不同，那里就存在一条边界。例如“订单”在销售上下文里是报价与成交记录，在履约上下文里是待发货任务，在财务上下文里是应收凭证，三者的字段、生命周期与变更节奏都不同，硬塞进一个模型只会互相牵制。

按业务能力分解是另一种说法：先列出产品提供的能力，例如下单、计价、库存占用、支付、履约、结算，再让每个服务对应一项或一组紧密相关的能力。命名会暴露边界是否合理：user-service、order-service、inventory-service 以业务对象命名，通常能对上团队职责；controller-service、dao-service、utils-service 则是按技术层拆分的典型反模式，改一个功能要同时动三个服务、发三次版，得到的只是“分布式单体”。

方法上，事件风暴（event storming）是一种低成本的协作工作坊：把领域事件、命令、聚合与上下文用便利贴铺开，让业务与技术一起找语言边界。它不需要建模工具，重点不是画出完美模型，而是暴露分歧：两个团队理解不一致的地方，往往就是未来的故障点。

边界不是一次画定的。可以用三条经验校验：变更频率是否明显不同，数据所有权是否清晰，是否有一个团队能独立负责。三条都满足才值得独立成服务，否则先留在单体里作为模块。

数据所有权：一个服务一块数据

拆分服务时最容易犯的错误，是只拆代码不拆数据。多个服务共享一个库、直接 JOIN 彼此的表，看起来省事，实际上把数据库 schema 变成了最难回滚的公共接口：任何一张表的字段变更都要协调所有使用方，服务的独立发布也就名存实亡。原则只有一句：每个服务独占自己的数据，其他服务只能通过 API 或事件访问。

报表是常见的例外场景，但解法不是开放库权限。可以让报表侧订阅领域事件，或通过 CDC（变更数据捕获）把数据同步到读模型、数据集市或数仓，在离线侧做宽表与聚合。在线库只承担事务写入与点查，跨服务的 JOIN 留在分析系统里。

跨服务事务需要换一种思路。强一致的分布式事务（两阶段提交）在可用性与运维上代价很高，微服务架构更常用 Saga：把长事务拆成一系列本地事务，每一步都有对应的补偿动作，失败时按相反顺序补偿，整体达到最终一致。Saga 要解决的是幂等、补偿失败与中间状态可见性，这些应写进接口契约。

另一个关键细节是事务性发件箱（transactional outbox）。业务数据和“待发送事件”写在同一个本地事务里，再由独立的投递进程读取并发送到消息队列，发送成功后再标记。这样避免了“数据库写成功、消息发送失败”的不一致，代价是消费端必须接受重复消息并做幂等处理。

数据所有权也决定了故障边界：共享数据库会把所有服务的可用性绑在一起，而独占数据让服务可以独自降级。

通信：同步调用与异步事件

服务间通信分为同步与异步两类。同步适合必须立刻拿到结果的场景，例如查询商品、校验库存；异步适合状态传播，例如订单创建后通知履约、积分与风控。判断标准不是哪个更先进，而是调用方是否真的需要立刻拿到结果。

同步调用链要克制。一次请求的延迟是各段之和，可用性却是各段之积：每段 99.9% 可用，四段串起来就只剩约 99.6%。因此要限制调用深度，显式设置超时，只对幂等操作重试，并配合退避与抖动；熔断器在下游持续失败时快速返回，避免调用方线程被拖死。

异步事件把调用变成通知，代价是时序不再直观：消费可能延迟、重复、乱序。事件要带唯一 ID 与发生时间，消费端按业务键幂等，必要时用版本号拒绝过期事件。

接口演进要向后兼容：加字段可以，删字段和改语义不行；消费端忽略未知字段，生产端不假设消费端已升级。消费者驱动的契约测试可以把这条约束固化到 CI 中。

gRPC 基于 HTTP/2 与 protobuf，适合内部高频调用；REST 加 JSON 更通用，调试也方便。两者可以共存。

平台能力是前置条件

微服务对基础设施的要求比单体高一个数量级。容器化与镜像仓库保证环境一致、可回滚；CI/CD 支撑多服务的构建、测试与发布；服务注册与发现让实例变化对调用方透明；配置外置与密钥管理避免敏感信息散落在代码和镜像里；集中式日志、指标与请求追踪把一次跨服务调用串起来；入口网关统一承接外部流量。这些能力在单体时代可以凑合，服务化之后缺一不可。

能力不到位就强行拆分，得到的是“分布式单体”：服务数量很多，但必须一起发布，共享同一个数据库，出故障只能登录机器看日志。它的运维成本比单体高，交付效率却更低。

服务网格在 2021 年已经可用，能通过 sidecar 统一处理加密、重试与流量切分，但它不是必选项。控制面与 sidecar 会带来新的复杂度，团队规模不大时，先把 SDK 与网关层的治理做扎实更划算。

迁移路线：绞杀者模式

从单体到微服务不应该是一次重写。重写意味着长期维护两套系统，风险极高。更稳妥的是绞杀者模式（strangler fig）：在单体前面加一层路由，新功能直接做成服务，老功能按接缝逐步迁移，最终让单体萎缩到可以下线。

识别接缝是第一步。优先选择变更频繁、边界清晰、依赖少、读多写少的能力，例如消息通知、站内搜索、报表导出；核心交易与账务放在最后。每迁一个能力，先补自动化测试与监控，再动流量。

数据迁移最难。常见做法是过渡期双写：单体与新服务同时写，读流量先切到新服务，用双读比对发现差异；或者用 CDC 订阅 binlog，把变更实时同步到新库。无论哪种方式，都要有对账任务与回滚开关。

在单体与新服务之间加一层防腐层：由它转换旧模型与新模型，避免历史字段和特殊逻辑渗进新服务的领域模型。

flowchart TD
    A[模块化单体] --> B[抽取低风险服务]
    B --> C[建设平台能力]
    C --> D[逐步迁移业务能力]
    D --> E[读流量切换与双读比对]
    E --> F[写流量切换并保留回滚]
    F --> G[下线单体旧模块]

阶段划分可以更具体：第一阶段在单体内部做模块化，把跨模块访问收敛为接口；第二阶段抽一个低风险服务跑通全链路，验证流水线、监控与值班；第三阶段补齐平台能力；第四阶段按边界批量迁移；第五阶段清理残留模块与数据，正式下线单体。

组织与度量

康威定律指出，系统结构会复制组织的沟通结构。微服务能生效的前提是团队边界与服务边界对齐：一个服务有明确的负责团队，接口变更由该团队拍板，故障由该团队值班；两个团队共用一个服务，任何改动都要开会协调。

平台团队是有效的组织设计：业务团队负责领域逻辑与 on-call，平台团队提供流水线、可观测性、中间件与密钥管理。配套的是 SRE 实践：定义 SLI 与 SLO，用错误预算决定发布节奏，事故后做不追责的复盘。

度量要选反映交付与稳定性的指标，并在改造前后用同一口径对比：部署频率、变更前置时间、变更失败率、平均恢复时间，即 DORA 指标；再补充 P99 延迟与单位请求成本。不要用服务数量衡量进度。

评审时可以用一张清单排雷：是否在团队与边界不清时强行拆分，是否仍共享数据库，是否存在过长的同步调用链，是否只有服务数量而没有独立发布能力，是否缺少日志、指标与追踪，是否按表拆服务，是否忽略最终一致，是否低估值班与基础设施成本。

小结

微服务是用运维复杂度换组织可扩展性的选择，不是技术成熟的标志。拆分前先确认痛点真的来自部署与边界，否则模块化单体是更划算的终点。边界按限界上下文与业务能力划定，数据由服务独占，一致性交给 Saga 与 outbox。同步调用控深度、设超时、配熔断，平台能力先行，迁移用绞杀者模式小步推进。
