TypeScript 4.6 与 4.7 新特性

本文属于《TypeScript 学习路线》第 49/74 篇
上一篇系列目录下一篇

TypeScript 4.6 与 4.7 这两个版本号，在 2021 年 1 月还属于很远的未来。截至本文写作时，最新的稳定版本是 4.1，4.2 仍处于测试与开发阶段，尚未发布稳定版。因此本文不会给出这两个版本的“新特性清单”，那在当下只能是猜测，我们转而讨论 TypeScript 的发布节奏与团队的升级策略。如果你正被“4.6 会加入某某语法”之类的说法困扰，本文也会给出辨别信息源的方法。

先把“4.6 与 4.7”放回时间线上

TypeScript 的版本号是顺序递增的，没有跳号，也没有“提前预定”的通道。每个小版本在上一版稳定之后进入开发，走完迭代计划、测试与候选发布，再转为稳定版。按过去两年的实际节奏，小版本之间大致相隔一个季度：4.0 在 2020 年 8 月发布，4.1 在同年 11 月发布，这个间隔可以作为参考。由此推算，从 4.2 走到 4.6 至少要跨过四个发布窗口，接近一年；4.7 还要更晚。换句话说，站在 2021 年 1 月谈 4.6 与 4.7，谈的是一年左右乃至更久的版本。

这带来一个直接结论：此刻任何号称“4.6 将加入某语法”“4.7 会重写某模块”的清单，都不可能是官方承诺。官方路线图只描述方向，例如类型系统的表达力、编译性能、与 JavaScript 生态的互操作，而不会提前一年逐条列出特性。本文保留这个标题，是因为很多读者会带着这两个版本号来搜索；但正文的重心是发布节奏与升级方法，而不是一份无法核实的特性表。

还有一个常被忽略的事实：TypeScript 不提供长期支持分支，社区与工具链的适配总是围绕最新的几个小版本展开。因此“跳过中间版本、等 4.6 一次升到位”并不是省事，而是把多次小风险累积成一次大风险。

版本地图：4.0、4.1 与尚未稳定的 4.2

在讨论未来之前，先把已经落地的能力盘清楚。很多团队其实还没有把 4.0 与 4.1 的红利用上，却已经在焦虑 4.6。

4.0 带来的变化偏向“元组与赋值”：可变元组类型让泛型可以表达“任意长度的参数列表”，带标签的元组元素让签名更可读，类属性可以从构造函数参数推断，短路赋值运算符 ??=、||=、&&= 补齐了赋值场景，catch 变量在 strict 下默认变为 unknown。

4.1 则把类型系统往字符串方向推了一步：模板字面量类型允许用字符串拼接的方式构造类型，映射类型支持通过 as 重映射键名，条件类型可以在满足条件时递归展开。这三项能力组合起来，可以在类型层面描述“由事件名生成处理器名”这类命名约定。

4.2 仍在开发中，尚未发布稳定版。它的内容应以官方发布说明为准，本文不作预测，也不建议把排期建立在未稳定的版本上。对大多数团队来说，务实的做法是先确认 4.1 的能力已经用足：strict 是否全量开启，import type 是否用于纯类型导入，// @ts-expect-error 是否替代了沉默的 any。

判断是否用足，可以看两个信号：新代码里是否还大量出现显式的 any，以及公共 API 的类型能否让调用方获得补全。前者说明类型检查被绕过，后者说明类型信息在模块边界丢失。

发布节奏：beta、rc 与稳定版之间的固定节拍

TypeScript 的每个小版本都遵循相似的流程。开发阶段会有一个迭代计划，列出该版本正在处理的主题和已合并的改动；随后发布 beta，供生态提前适配；接近完成时发布 rc，原则上只修缺陷；最后转为稳定版，并配一份发布说明。这个节拍的价值在于可预期：工具链作者可以按 beta 提前发现不兼容，应用团队可以按 rc 做预演。

获取信息的渠道应当尽量靠近源头。官方博客会发布每个版本的说明，GitHub 仓库的 releases 页面可以按标签查看变更，npm 上的 beta、rc、next 标签则对应不同成熟度的构建。用 npm dist-tag ls typescript 可以看到当前各标签指向的版本号，这比二手文章的标题可靠得多。需要提醒的是，next 是每晚构建，适合验证问题，不适合生产环境。

废弃策略也遵循渐进而非突袭：先在某版发布说明中标记 deprecated，保留可用的过渡期，再选择合适时机移除。这意味着升级时看到的警告值得当场处理；拖到移除那一步，改动量往往已经翻倍。

与之相对，社区里流传的“版本预测”往往混合了三种东西：已经合并但未发布的改动、提案阶段的语法、以及作者个人的期望。三者被写成同一种语气，读者很难分辨。一个简单的判断方法是看它有没有给出对应的发布说明链接和合并记录；如果没有，就把它当作观点，而不是事实。

升级策略：一次只跨一个小版本

升级 TypeScript 最常见的错误，是把编辑器、typescript、@types/*、构建工具和 ESLint 解析器一次性全部升到最新。一旦编译报错成百上千条，就分不清是哪一处改动引起的。更稳妥的做法是把升级拆成可回滚的小步。

第一步是锁定版本。在 package.json 中写精确版本号，并提交锁文件，确保 CI 与本地拿到的是同一个编译器。第二步是一次只跨一个小版本，例如从 4.0 到 4.1，而不是从 4.0 直接到 4.6。每跨一步，先读该版本的发布说明，再动手改配置。

第三步是验证。先跑 tsc --noEmit，把类型错误与运行时测试分开看；再跑单元测试与构建，确认产物没有变化；最后检查 @types 包的兼容性，特别是 @types/node 与框架类型包，它们对大版本往往有最低 TypeScript 版本要求。

第四步是度量与留退路。记录升级前后的编译耗时和内存占用，留一条带标签的分支，确认线上稳定后再删除。单体仓库还要注意依赖提升：如果不同包解析到不同版本的 typescript，类型身份会不一致，表现为“明明同一个类型却赋值失败”。统一在根目录声明编译器版本，并让各包通过项目引用共享配置，可以避免这类问题。

仓库内的升级顺序也有讲究：先升不依赖内部包的基础库，再升业务包，最后升应用；每升一层就跑一次全量类型检查，把问题定位在最小的范围内。

破坏性变更清单与发布说明的读法

TypeScript 的破坏性变更大多不是语法层面的，而是类型检查变严或默认值调整。升级前可以按下面几类逐项排查。

  • target 与 lib 的默认值：默认值会随版本调整，不要依赖默认值，在 tsconfig.json 里显式写明。
  • 更严格的检查：strict 家族新增的检查项可能让旧代码报错，尤其是 catch 变量、可选属性与索引签名。
  • DOM 类型更新：lib.dom.d.ts 跟随浏览器标准更新，同名 API 的签名变化会波及前端代码。
  • 废弃项：被标记为 deprecated 的编译选项通常还能用，但会给出提示，应在下一个大版本前清理。
  • 模块解析：解析策略的细微调整会影响路径映射与包入口，升级后要重点回归多包项目。

读发布说明时，先看 Breaking Changes 与 Deprecations 两节，再看 Features；前者决定你要改什么，后者决定你能用什么。遇到不理解的条目，顺着链接看合并记录里的测试用例，通常比读摘要更快。不要只看二手总结，它们经常省略“仅在某种配置下生效”这类关键前提。

排查前可以先让编译器把最终配置打印出来：tsc --showConfig 会展开继承关系，显示 target、lib、strict 等选项的真实取值。很多“升级后才出现”的问题，其实是某个被继承的配置在旧版本里被忽略、在新版本里开始生效。

与版本号无关的长期准备

有些主题不会因为某个版本号而改变，它们值得在任何一次升级中顺带处理。

其一是模块互操作。Node 的 ESM 支持仍在演进，TypeScript 的模块解析尚未完整建模 package.json 的 exports 字段。混合使用 CommonJS 与 ESM 的项目，应尽早统一 esModuleInterop、allowSyntheticDefaultImports 等开关，并把入口文件的模块格式写清楚，而不是等到运行时才排查 default 取值问题。

其二是装饰器。TypeScript 现有的 experimentalDecorators 实现的是旧提案，新的装饰器提案仍在 TC39 的标准化进程中，两者并不兼容。使用 Angular、NestJS 这类依赖装饰器的框架时，应把装饰器配置视为框架约束，不要自行切换编译选项。

其三是错误处理的类型化。catch 变量变为 unknown 之后，正确的做法是在 catch 内做类型收窄，而不是用 any 绕过。这项改动会逼迫团队补齐错误边界，短期有成本，长期能减少“错误对象形状不一致”的故障。

其四是编译性能与声明文件。项目变大之后，incremental、项目引用、skipLibCheck 的取舍会直接影响开发体验；对外发布库的团队，还应把 .d.ts 当作公共 API 管理，纳入回归测试。这些工作与 4.6、4.7 是否会到来无关，却决定了升级时是否从容。

声明文件的质量尤其容易被忽视。开启 declaration 与 declarationMap 后，使用者跳转时能回到源码；但若导出的类型里混入了未导出的私有类型，生成的 .d.ts 就会报错或泄漏实现细节，升级编译器时这类问题会集中暴露。

度量、工具与团队流程

升级不该是某个人的顺手之举，而应是一次有度量的小项目。

flowchart TD
    A[记录当前版本与基线指标] --> B[阅读目标版本发布说明]
    B --> C[单独升级 typescript]
    C --> D[类型检查与测试]
    D -->|通过| E[对比耗时并灰度]
    D -->|失败| F[修复或回滚]
    E --> G[推广并更新团队文档]

工具层面，tsc --diagnostics 给出文件数、类型数、检查耗时等摘要，--extendedDiagnostics 更细，能看到绑定、检查、生成各阶段的时间。需要定位具体耗时来源时，可以用 --generateTrace 输出结构化追踪，再配合分析工具查看。项目引用与 --incremental 能显著缩短增量编译，但它们要求把包边界划清楚，否则收益有限。升级前先记录一组基线数据，升级后对比，才有“变慢了多少”的客观依据。

流程层面，可以指定一名升级负责人，维护一条 CI 矩阵，至少覆盖当前 Node LTS 与相邻两个 TypeScript 小版本。为核心类型写少量类型测试（例如用 tsd 之类的工具断言类型结果），把“类型行为”也纳入回归。内部有多个项目时，可以先在一个非关键包上灰度，观察一到两周再推广。回滚标准要提前写清楚，例如编译耗时上涨超过两成、或无法在一天内修完的类型错误，就退回上一个版本。最后把变更写进团队文档，注明升级原因、影响范围与已知问题，避免下一个人重复踩坑。

几个高频的坑值得单独列出：一次性升级所有依赖；用 skipLibCheck: true 掩盖库之间的类型冲突；依赖尚未公布的语法写业务代码；在生产依赖里使用 next 标签；只测运行时、不测声明文件。它们的共同点是把不确定性留到了最后。

小结

TypeScript 4.6 与 4.7 在 2021 年 1 月仍是远期版本号，当前稳定版是 4.1，4.2 尚未稳定，任何具体的特性清单都不可信。真正可控的是节奏与方法：理解小版本的发布流程，锁定版本、一次只跨一个小版本，用 tsc --noEmit 与测试验证，度量编译耗时并保留回滚路径。把 @types 兼容、模块互操作、装饰器配置和声明文件质量当作长期议题，而不是某个版本的临时任务。这样无论下一个版本号写着 4.2 还是 4.7，团队都能按自己的节奏跟进。
