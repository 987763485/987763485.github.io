API 网关设计与实现

本文属于《Go 微服务架构》第 17/35 篇
上一篇系列目录下一篇

服务拆成微服务之后，客户端要记住的地址越来越多，认证、限流、日志这些横切逻辑也在每个服务里重复一遍。API 网关把这些事收到一个入口上，让业务服务只关心业务。本文讨论网关的职责边界、路由与治理设计、配置热更新和可观测性，并用 Go 标准库写一个可以跑起来的最小实现。

为什么需要 API 网关

在没有网关的架构里，Web、iOS、Android 和小程序各自直连一组服务。每新增一个客户端，就要重复处理地址发现、鉴权、重试和兼容逻辑；每调整一次服务拆分，客户端也要跟着发版。API 网关的做法是在客户端与服务之间放一个统一入口：客户端只认识网关域名，网关按规则把请求转发到后端，并在转发前后完成认证、限流、日志等横切动作。

flowchart LR
  C1[Web 客户端] --> G[API 网关]
  C2[移动客户端] --> G
  G --> S1[用户服务]
  G --> S2[订单服务]
  G --> S3[库存服务]

这带来四个直接收益。第一，入口收敛，客户端不再感知服务拓扑。第二，横切关注点只实现一次，各语言、各团队的服务不必各写一套鉴权中间件。第三，协议与报文可以转换，例如对外提供 REST/JSON，对内调用 gRPC 或旧版 SOAP 服务。第四，多客户端适配有了落点，可以按客户端裁剪字段、聚合接口，或按版本路由到不同后端。

但网关不是微服务的必需品。只有几个服务、客户端也单一时，引入网关只会多一跳和一个要维护的组件；东西向流量为主、服务间调用已经由服务网格的边车处理时，网关也应只负责南北向入口，而不是重复做一套治理。判断标准很简单：横切逻辑是否已经在多个服务里重复，客户端是否真的需要一个稳定入口。

核心职责与架构分层

一个生产可用的网关通常承担这些职责：按 host、path、header、method 匹配路由；认证与鉴权；按路由、租户或调用方限流；熔断、超时与有限重试；请求头与报文改写；响应缓存；访问日志、指标与链路追踪；灰度与权重路由。职责看似很多，但可以归为两类：流量治理和连接管理。前者决定请求能不能过、怎么过，后者决定请求发给谁、发得多快。响应缓存的 key 至少包含租户与身份维度，避免串数据。

实现上要把数据面与控制面分开。数据面是每个请求都要走的转发逻辑：匹配路由、校验令牌、转发、记录日志。控制面负责配置的生成、校验与下发，通常是一个独立的管理服务或配置中心。网关实例本身保持无状态，统一挂在四层负载均衡之后；会话状态、限流计数、nonce 记录等放到外部存储。这样扩容只是多加实例，故障实例被摘除也不影响整体。

flowchart TD
  LB[四层负载均衡] --> G1[网关实例 1]
  LB --> G2[网关实例 2]
  CP[控制面与配置中心] -. 下发配置 .-> G1
  CP -. 下发配置 .-> G2
  G1 --> U1[上游组 A]
  G2 --> U1

配置下发有推、拉、监听三种模式。推模式实时性好，但要处理实例离线期间错过更新；拉模式简单，代价是收敛慢；监听模式（如 etcd watch）介于两者之间，需要处理断线重连后的全量同步。无论哪种，都要给配置带上版本号，实例上报生效版本，控制面才能判断是否全网一致。

实例还要处理健康检查与优雅退出。健康检查分存活与就绪：进程活着但配置未加载完时，只应通过存活检查，不应接流量。退出时先摘掉负载均衡权重，再停止接收新连接，等待在途请求完成，最后关闭连接池。直接 kill 进程会让正在处理的请求变成客户端超时，也会让上游看到一批无谓的断连。

路由与负载均衡

路由表是网关最核心的数据结构。一条路由至少包含匹配条件、上游组和一组策略：匹配条件由 host、path 前缀、header 与方法组成；策略包括是否剥离前缀、超时、重试次数、限流配额和鉴权方式。下面是一段简化的配置：

匹配必须确定优先级。精确匹配优先于前缀匹配，前缀匹配按最长前缀胜出；长度相同时再比较 host 与 header 条件，最后用显式 priority 兜底。实现上常按 host 分组，组内建前缀树，查找成本与路径段数相关，而不是与路由条数线性相关。

转发前往往要改写路径。对外暴露 /api/order，后端只认 /order，就剥离 /api 前缀；反过来也可以加前缀。改写规则要显式配置，不要在代码里按字符串猜。上游组则是一组实例地址加负载均衡策略：轮询简单均匀，最少连接适合耗时差异大的场景，一致性哈希用于需要把同一用户固定到同一实例的缓存类服务。

网关到上游必须复用连接。每个上游组维护连接池，开启 keep-alive，限制空闲连接数与单主机连接数；否则每个请求都要三次握手，延迟和端口消耗都不可接受。连接池大小要与上游并发能力匹配，过大只是把压力往后传。

认证、鉴权与流量治理

认证解决“你是谁”，鉴权解决“你能做什么”。网关适合做粗粒度鉴权，例如某个路由只允许带 admin 角色的令牌访问；资源归属这类细粒度判断仍应放在服务内，因为它需要业务数据。

JWT 校验有四步：验签名、验 exp 与 nbf、验 iss、验 aud。签名算法要与白名单比对，拒绝 none，也要防止把公钥当 HMAC 密钥使用的算法混淆攻击。验签调用成熟库，不要自己拼 HMAC 或解析 ASN.1。密钥轮换时用 kid 找对应公钥，公钥从 JWKS 端点缓存并定期刷新；令牌中的 sub、scope 可以透传，但透传头必须由网关重写，不能信任客户端自带的值。

API key 适合服务端之间的简单调用，放在 header 而不是 URL，避免进入访问日志和浏览器历史。更严格的场景用 HMAC 签名：客户端对 method、path、body 摘要、时间戳和随机数按固定顺序拼接后签名，服务端校验时间窗并记录 nonce，防止重放。nonce 要有 TTL，多实例部署时放 Redis 之类的共享存储。签名与摘要都调用标准库或成熟库，不要自己实现密码学。

限流放在网关有三个粒度：路由级保护后端、调用方级保证配额公平、并发级防止慢请求占满连接。入口适合用令牌桶，允许一定突发；算法细节不在本文展开。单机限流简单但有误差，多实例可以按实例拆分配额，或使用集中计数，前者会浪费配额，后者多一次远程调用，按精度要求取舍。

熔断保护的是调用链。上游错误率或连续失败超过阈值时进入打开状态，直接返回失败或降级响应；冷却期后进入半开，放少量请求试探，成功则恢复，失败则继续打开。熔断必须和超时一起用，没有超时的熔断只会在连接堆积后被动触发。重试只对幂等请求开启，采用指数退避加抖动并限制总次数；非幂等写请求重试可能造成重复下单，除非下游支持幂等键。

可观测性：日志、指标与追踪

网关是所有请求的必经之路，也是观测的最佳位置。访问日志至少记录时间、request id、客户端 IP、路由 id、方法、路径、状态码、耗时、上游地址以及请求和响应字节数。request id 要在入口生成，客户端带了也要校验格式或直接重新生成，随后写入响应头并透传给下游；服务日志带同一个 id，排障时才能串起来。

敏感信息必须脱敏。Authorization、Cookie、Set-Cookie 不落原文，查询参数里的 token 与签名同样处理；请求体默认不记录，需要时按采样和字段白名单记录。日志量大时按路由或状态码采样，错误请求全量保留。

指标关注四类：流量（QPS、并发连接数）、延迟（p50、p95、p99，而不是平均值）、错误（4xx 与 5xx 分开，按路由和上游统计）、上游健康（可用实例数、熔断状态、连接池使用率）。标签不要放用户 id、原始路径这类高基数维度，否则时序库会被撑爆。

链路追踪用 W3C Trace Context 的 traceparent 头传播上下文。网关作为入口创建根 span，后续服务继续传播；请求已带 traceparent 时先校验格式，再决定是否沿用。采样决定应在入口做，避免下游各自采样导致链路残缺。

认证、限流、日志适合做成中间件，按顺序包在 Gateway 外面；示例的 accessLog 演示了组合方式，恢复 panic、鉴权、限流可按同一签名接入。中间件只处理请求元数据，不要读写业务报文；需要改 body 的能力（如字段裁剪）会破坏流式转发，应单独评估。

发布、性能与常见坑

配置就是网关的代码，必须像代码一样发布。加载时做 schema 校验：路由 id 唯一、前缀不冲突、上游地址合法、超时为正数；上线前用样例请求跑一遍 dry-run，确认匹配结果。路由变更先小流量生效，按权重 1%、10%、50% 逐步放量，观察错误率和 p99 再全量，出问题切回上一个版本。API 版本用 /v1、/v2 路径前缀区分，上游蓝绿发布只切换上游组，不动路由。

性能优化先从请求路径上找浪费。配置不要每个请求解析，正则预编译，JSON 序列化能省则省；连接必须复用，Transport 的空闲连接数要显式设置；请求体设大小上限（如 http.MaxBytesReader），避免大包打满内存；代理大响应用流式复制，不要先读到内存。每请求分配的对象越少，GC 压力越小。压测给方法而不是数字：固定并发与请求分布，分别测 keep-alive 开关、不同 body 大小、p50 与 p99，再用 pprof 看 CPU 与堆分配。

部署位置上，边缘网关负责 TLS 终止与公网入口，WAF 和 DDoS 清洗放在它前面；内部网关负责东西向认证与灰度，如果已有服务网格，可以只保留南北向。多地域部署时每个地域一套网关、配置独立下发，避免跨地域依赖控制面。TLS 证书轮换要支持热加载，不能靠重启。

最后是几个常见坑。网关膨胀成业务编排层，字段聚合都往里塞，最后没人敢改；重试没有上限，上游故障时流量被放大数倍；没有幂等设计却重试写请求；请求体不设上限；超时缺省为无限；网关验了 JWT，服务却信任客户端自带的身份头；整个系统只有一个网关实例。前几个靠规范与评审，后两个靠架构约束：身份头只能由网关写入，并用内网签名或 mTLS 保护；网关至少两个实例并跨故障域部署。

小结

API 网关的价值不在于转发，而在于把认证、限流、灰度、观测这些横切能力收敛到一个稳定入口。设计时先划清数据面与控制面，路由模型、身份透传和超时重试要一起考虑；实现时保持实例无状态、配置原子替换、连接复用，并给请求体、并发和重试都设上限。最后记住两条底线：网关不承载业务逻辑，身份头只信网关自己写的。
