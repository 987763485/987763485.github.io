Kubernetes 网络模型与 CNI

本文属于《Docker 与 Kubernetes》第 29/51 篇
上一篇系列目录下一篇

很多同学第一次排查 Kubernetes 网络问题时，会同时面对三层抽象：Pod 之间凭什么能直接通，跨节点又是怎么把包送到对端的，ClusterIP 为什么连 ping 都不响应。本文按“模型约定—Linux 原语—跨节点方案—CNI 规范—常见实现—Service 与 DNS—策略与排障”的顺序把这些层拆开来讲，适合已经能部署集群、但希望把“为什么能通”弄清楚的读者。读完后你应当能画出一次 Pod 到 Pod 的报文路径，也能在 cni 报错、MTU 黑洞和 DNS 超时面前有一套固定的排查顺序。

Kubernetes 网络模型的四条约定

Kubernetes 并没有发明一套网络协议，它只对“网络应该长什么样”提出四条约定，然后要求每个节点上的实现去满足它们。

第一条，每个 Pod 拥有独立的 IP 地址，并且这个 IP 在集群内可直接访问。第二条，同一个 Pod 内的所有容器共享同一个网络命名空间，因此它们看到的是同一张网卡、同一个 IP 和同一份端口空间，容器之间用 localhost 就能互访。这也解释了一个常见约束：同一个 Pod 里的两个容器不能同时监听 80 端口，因为它们争的是同一个网络栈。

第三条，Pod 之间通信不经过 NAT 地址转换，对端看到的源地址就是发送方的 Pod IP。第四条，节点与 Pod 之间通信同样不做源地址转换，节点上的进程访问 Pod IP 时，Pod 里抓包看到的源地址就是节点地址。

这四条约定合起来，就是所谓的“扁平网络”：无论两个 Pod 是否在同一节点、是否在同一机架，双方都像接在同一台交换机上一样，只用对方的 IP 就能互通。它带来的直接好处是应用不用关心拓扑，服务发现和访问控制都可以基于 IP 与端口来做；代价是集群必须自己解决地址分配和跨节点转发，而这正是 CNI 要处理的事。

需要强调的是，模型只规定“结果”，不规定“手段”。用什么网段、走不走 overlay 封装、是否需要加密、能不能做 NetworkPolicy，全部由具体实现决定。一个集群只要满足上述四条，就可以自称符合 Kubernetes 网络模型。反过来，模型也没有承诺 Pod 一定能访问外网，那取决于实现是否配置了 SNAT 与默认路由，属于附加能力而不是模型的一部分。

Linux 网络原语：同节点报文怎么走

要理解 CNI 插件在做什么，得先把它用到的几个 Linux 网络原语摆出来。第一个是网络命名空间（network namespace），它把网卡、路由表、ARP 表、iptables 规则和套接字状态打包成一份独立视图。容器的“独立网络”本质上就是进程被放进了一个新的 netns，Pod 则更进一步：先创建一个只负责持有网络栈的 pause 容器，再把业务容器加入同一个 netns，于是它们共享同一份网络视图。

第二个是 veth pair。它是一对虚拟网卡，从一端发出的帧会直接出现在另一端，像一根两端各插着一个网口的网线。容器内的 eth0 是 veth 的一端，另一端留在宿主机上，通常命名为 vethXXXX。

第三个是网桥。宿主机上的 cni0（Flannel 的默认网桥）或 docker0 把若干 veth 的宿主端接在一起，形成一个二层广播域，同节点 Pod 之间靠它转发。第四个是路由表：Pod 内的默认路由指向网桥地址，宿主机则通过路由决定某个 Pod 网段是从网桥走，还是从隧道或物理网卡走。第五个是 iptables 与 conntrack，它们负责 NAT、端口映射和连接跟踪；第六个是 ARP，同网段通信要先问“这个 IP 对应哪个 MAC”。

同节点两个 Pod 通信，报文路径可以概括为下面这样。

flowchart TD
  A["Pod A eth0 10.244.1.5"] --> B["veth 宿主端 vethA"]
  B --> C["网桥 cni0 10.244.1.1"]
  C --> D["veth 宿主端 vethB"]
  D --> E["Pod B eth0 10.244.1.6"]
  C -.-> F["宿主机 eth0 192.168.10.21（跨节点时）"]

具体到一次 curl，过程大致如下：Pod A 查路由表，发现 10.244.1.6 在同网段，于是发 ARP 请求；网桥把它泛洪到同一网桥上的所有端口，Pod B 回应自己的 MAC；随后 A 把 IP 包封装成以太帧发给这个 MAC，帧从 vethA 出来落到 cni0，网桥查 MAC 表后从 vethB 送出，进入 Pod B。整个过程没有 NAT，源 IP 始终是 10.244.1.5，与模型约定一致。

可以用几条命令在节点上亲手验证这套结构。

读懂这几条输出，后面再看 CNI 配置与跨节点方案就不会觉得抽象：插件无非是在做“建 veth、接网桥、配 IP、写路由、装规则”这几件事的自动化。

跨节点通信：Overlay、路由与 MTU

当两个 Pod 落在不同节点上，问题从二层变成三层：Pod A 的网段只有节点 A 自己知道怎么走，节点 B 上的 Pod B 网段也只有节点 B 知道。业界有两条主线来解决它。

第一条是 overlay，也就是隧道封装。节点把完整的原始 IP 包再套一层外层头部，通过物理网络送到对端节点，对端解封装后交给本机网桥。VXLAN 是最常见的做法：原始以太帧被塞进 UDP 报文，目标端口 8472（Flannel）或 4789（标准端口），外层再套节点 IP。IP-in-IP 更轻，只加一个外层 IP 头，但要求两端都能处理这种协议号，跨 NAT 和部分云网络时容易受限。overlay 的优点是底层网络只需节点间三层可达，不关心 Pod 网段；缺点是封装带来了额外开销和排障难度。

第二条是路由，也就是让底层网络直接知道 Pod 网段在哪里。Calico 的 BGP 模式让每个节点把本机 Pod 网段通过 BGP 通告给对端节点或上游路由器，报文原样转发，不做封装，抓包时看到的仍是原始地址。代价是要求底层网络允许节点间交换路由，或者在云上把路由表项同步给 VPC。介于两者之间的是云厂商的 ENI 方案：直接把弹性网卡分配给 Pod，Pod IP 就是 VPC 内真实地址，天然可路由，但受网卡数量与 IP 配额限制。

封装会吃掉 MTU，这是最容易踩的坑。物理网卡 MTU 1500 时，VXLAN 外层需要 14 字节以太头、20 字节 IP 头、8 字节 UDP 头和 8 字节 VXLAN 头，共 50 字节，于是 Pod 网卡通常设为 1450；IP-in-IP 只多 20 字节，对应 1480；如果再加 IPsec 加密，头部更长，常见配置会落到 1400 左右。这些数字不是拍脑袋的经验，而是“1500 减去各层头部”的算术结果。

MTU 设错的后果很隐蔽：小包正常，大包（比如 TLS 握手后传输大响应、kubectl exec 拷贝文件）卡住或超时，看起来像应用故障。原因是发送端不知道路径变窄，IP 层设置了“不分片”标志，中间的封装节点又没有把“需要分片”的消息回传，形成黑洞。排查时在 Pod 里执行 ping -M do -s 1422 <对端 Pod IP>，逐步调整包长，就能定位实际可用的 MTU；长期方案是统一 CNI 与节点网卡的 MTU 配置，必要时启用 TCP MSS 钳制。

CNI：规范、插件与调用链

CNI（Container Network Interface）是一份很短的规范，外加一批可执行文件。它规定的核心只有三件事：配置文件长什么样、运行时怎么调用插件、插件返回什么。

调用方式是最原始的“可执行文件加标准输入输出”：容器运行时把网络配置 JSON 从标准输入传给插件，把上下文放进环境变量，插件完成操作后往标准输出打印结果。规范的核心动作有三个：ADD 负责为容器创建网络并分配 IP，DEL 负责清理，CHECK 在 CNI 0.4 中加入，用于校验已有配置是否仍然符合预期。另外还有一个 VERSION 动作，运行时用它探测插件支持的规范版本。配置里的 cniVersion 字段必须与插件能力匹配，版本不匹配时最常见的表现就是插件直接报错退出。

一次 ADD 的输入大致如下，runtimeConfig 与 ipam 字段是关键：前者用于传递端口映射、带宽等运行时参数，后者把 IP 分配委托给独立的 IPAM 插件。

插件返回的结果包含 interfaces、ips、routes 和可选的 dns，运行时据此在容器内配置网卡和路由。注意 CNI 只管“把网络接好”，既不做服务发现，也不规定 IP 从哪里来：host-local 把已分配地址记在本地文件，calico-ipam 从节点预分配的地址块里取，dhcp 则去问外部 DHCP。

真正发起调用的是容器运行时，而不是 kubelet 直接调用。kubelet 通过 CRI 请运行时创建 Pod 沙箱，运行时（dockerd 或 containerd）再按自己的 CNI 配置执行插件。配置目录通常是 /etc/cni/net.d，二进制目录是 /opt/cni/bin；运行时按文件名字典序读取，只用第一个合法的配置文件，这也是为什么 Flannel 与 Calico 同时安装时经常出现“装了却没生效”的情况。Calico、Cilium 这类插件还会以 DaemonSet 形式运行自己的 agent，由 agent 把 CNI 配置和二进制放到节点上。

由此可以归纳出 cni 类报错的排查顺序：先看 /etc/cni/net.d 下是否只有一份预期配置、cniVersion 是否被支持；再看 /opt/cni/bin 里有没有对应的可执行文件；然后看节点上 agent Pod 是否正常；最后才怀疑网段与路由。kubectl describe pod 事件里的 “failed to set up sandbox” 往往只是结果，真正的错误原因要去 journalctl -u kubelet 或运行时日志里找。

Calico、Flannel 与 Cilium 的取舍

三种插件代表三种设计取向。Flannel 最省心：按节点切分 Pod 子网，默认 VXLAN 封装，子网信息由 agent 写进本地文件，再由 bridge 插件完成接线；host-gw 后端改为在节点上直接写对端子网路由，要求所有节点同二层。它不实现网络策略，适合先把集群跑通。

Calico 走三层路由：节点上的 Felix 把策略与路由落到本机，BIRD 用 BGP 通告本机 Pod 网段，IPAM 按地址块把 IP 分给节点。默认清单常用 IPIP，也可切 VXLAN 以穿过不支持 IP-in-IP 的网络，或纯 BGP 不封装。策略能力由它自己实现，既覆盖命名空间内的 NetworkPolicy，也提供集群级全局策略。

Cilium 把转发与策略下沉到 eBPF，端点按标签获得安全身份，策略基于身份而不只是 IP，Pod 重建换地址后规则依然成立。它在当年已能承担部分 kube-proxy 职责，但多数集群仍保留 kube-proxy；是否替换取决于内核版本与团队对 eBPF 的排障能力，不宜当作默认答案。

Service 与 DNS：虚拟地址与解析链

ClusterIP 不属于任何网卡，只存在于转发规则里。kube-proxy 监听 Service 与 EndpointSlice 的变化，iptables 模式下写入 DNAT 规则：访问 ClusterIP 的报文在协议栈内被改写成某个后端 Pod IP，回包靠 conntrack 反向还原。IPVS 模式把 Service 与后端交给内核的 IPVS 虚拟服务器和 ipset，转发时查表，而不是逐条遍历增长中的规则链。这也解释了 ClusterIP 为什么 ping 不通：ICMP 没有对应的 DNAT 规则，包到不了任何后端，能 ping 通反而说明配置有问题。

conntrack 是另一个要点。DNAT 只发生在首个包上，后续包依赖连接跟踪表命中；表满时新连接被丢弃，表现为间歇性超时，需要关注 nf_conntrack_max 与节点上的连接数。hairpin 指 Pod 访问的 Service 后端恰好包含自身，回包路径不对称，需要 masquerade 源地址，否则会被对端丢弃。

DNS 由 CoreDNS 提供。Pod 的 resolv.conf 默认带 ndots:5 和一组 search 域，短名会依次拼上 <ns>.svc.cluster.local、svc.cluster.local、cluster.local 再查询，失败时产生多次多余请求。Headless Service 不分配 ClusterIP，直接返回全部 Pod 的 A 记录，常用于 StatefulSet 的稳定域名。解析异常时先拿 FQDN 与短名对比，再查 CoreDNS 日志与 Pod 的 dnsPolicy。

NetworkPolicy 与排障阶梯

NetworkPolicy 是命名空间内的资源，用 podSelector 选中一组 Pod，用 ingress 与 egress 描述允许的来源或目的，namespaceSelector 按命名空间标签匹配，ipBlock 匹配网段。空的 podSelector 表示本命名空间全部 Pod，配上空的 ingress 列表就是默认拒绝；策略只有允许项，没有显式拒绝，未被任何策略选中的 Pod 默认全通。

前提是策略必须由 CNI 落地，API Server 只负责存储；Flannel 单独使用时策略会被接受却不生效，这是最容易误判的一类“策略失效”。同理，Pod 直接暴露给集群外、忽略 conntrack 上限、插件版本落后于 Kubernetes 版本，也都是上线后才会暴露的隐患，规划阶段就该确认网段不重叠、MTU 一致、策略插件确实在岗。

排障可以按固定阶梯走：Pod 没有 IP 或卡在 ContainerCreating，先看 kubectl describe pod 事件与 CNI 配置；同节点不通查网桥与 veth；跨节点不通查隧道、BGP 邻居与路由；小包通而大包不通查 MTU；Service 不通先看 EndpointSlice 是否为空，再看 kube-proxy 的规则；域名解析失败对比 FQDN 与 search 域；最后才怀疑策略。两端同时用 tcpdump -i any -nn 抓包，能最快判断包丢在哪一跳。

小结

本文从四条约定出发，把 Pod 网络拆成网络命名空间、veth、网桥、路由与 iptables 这些可验证的原语，再沿 overlay 与路由两条路线走到跨节点，最后落到 CNI 规范、插件差异以及 Service 与 DNS 的虚拟化机制。实践中最值得先确认的三件事是：Pod 网段与 Service 网段不与机房、VPC 冲突；封装链路上的 MTU 统一；所选 CNI 真正执行 NetworkPolicy。遇到故障时按“Pod 地址、CNI 配置、同节点、跨节点、Service、DNS、策略”的顺序逐层排除，比直接重启节点有效得多。
