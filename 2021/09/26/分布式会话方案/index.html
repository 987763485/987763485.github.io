分布式会话方案

系统从单机走向多实例之后，会话往往是最先暴露出来的问题：用户上一秒还正常浏览，刷新几次就被踢回登录页；运维重启一台节点，半个机房的人同时掉线。本文从会话需要承载的数据出发，逐一分析粘性会话、集中式存储、无状态令牌与混合方案的适用边界，再讨论续期、注销、跨域与安全属性这些最容易被忽略的细节。

文中的示例以 Go 1.17 与 Redis 6.2 为准，代码只保留关键逻辑，省略框架绑定与完整的错误处理。读完之后，你应该能为自己的系统选出一套可落地、可运维、可迁移的会话方案，并清楚它在故障时会怎样退化。

会话里究竟要存什么

会话（session）本质上是服务端记住某个已通过认证的客户端的一段状态。它至少要回答四个问题：你是谁（用户 ID、租户 ID）、你能做什么（角色、权限范围、登录方式）、这次登录何时失效（创建时间、最后活跃时间、绝对过期时间）、以及它来自哪台设备（User-Agent 摘要、IP 段、设备标识）。前两项决定授权结果，后两项决定安全策略：能否异地同时登录、能否被管理员踢下线、出现异常时能否审计。

很多团队只把用户 ID 塞进会话，权限每次请求都回源查询。这样会话层看似很轻，实际把压力全部转给了权限服务，一旦权限服务抖动，所有已登录用户一起不可用。比较稳妥的做法是把变化频率低、判定必需的权限快照放进会话，把变化频繁、要求强一致的判断留在服务端，并在权限变更时主动失效相关会话。

登录态的一次典型流转如下：

    participant B as 浏览器
    participant G as 应用服务
    participant S as 会话存储
    participant D as 用户库

    G->>D: 校验账号与口令

    G->>S: 写入会话，以随机 ID 为键

    G-->>B: Set-Cookie 下发会话 ID
    B->>G: GET /orders 携带会话 ID
    G->>S: 读取会话并续期
    S-->>G: 会话数据
    G-->>B: 200 按权限渲染

图中把“写会话”和“发 Cookie”分成两步，是要强调顺序：先落库成功再下发凭据。注销时同理，先删服务端记录再清 Cookie，清 Cookie 只是让浏览器忘记，不能让已泄露的 ID 失效。

单机会话为什么在多实例下失效

单机时代的会话几乎不需要设计：进程内一个 map，键是随机 ID，值是结构体，再加一个后台协程定期清理过期项。它在单实例下工作得很好，因为内存和请求处理的进程是同一份东西。

一旦部署成多实例，这个前提就不成立了。负载均衡把同一个用户的第二个请求打到另一台机器，那台机器的 map 里没有这个键，于是判定未登录。更隐蔽的是“部分命中”：如果负载均衡按长连接复用，用户可能连续几次都落到同一台机器，看起来一切正常，直到某次扩容或连接重建才突然掉线。这类问题在测试环境很难复现，因为测试环境往往只有一个实例。

除此之外还有三个衍生问题。第一是发布与重启：进程内会话随进程消失，滚动发布期间用户会被分批踢出。第二是水平扩容无效：新节点是“空”的，它不承担任何已有会话，扩容只增加了计算能力，没有增加会话容量。第三是无法统一管控：管理员要踢人、风控要冻结账号、审计要查某用户登录过哪些设备，都得挨个节点去问。这三个问题不是内存会话实现得不好，而是状态被放在了错误的位置。

由此可归纳出三个评价维度：状态存在哪里、请求如何找到状态、失效如何传播。后面的方案，本质上都是在这三个维度上做取舍。

粘性会话：最低成本的权宜之计

粘性会话（sticky session）不改代码，只在负载均衡层做文章：按源 IP 做哈希，或者在响应中插入一个 Cookie，把同一客户端的请求固定到同一台后端。它在遗留系统改造中很常见，因为接入成本几乎为零。

代价同样明确。第一，扩容对已有会话无效。新加入的节点只能接收新分配的客户端，存量负载不会迁移，这在突发流量下很尴尬：机器加了，热点却没散。第二，故障被放大。一台节点挂掉，它承载的所有会话随之丢失，用户被迫重新登录，故障影响面与节点承载量成正比。第三，发布变得麻烦。滚动发布意味着逐台清空会话，必须配合优雅下线、连接排空，否则每次上线都是一次小规模的登录风暴。

还有几个容易被低估的边界。办公网与运营商 NAT 之后的用户共享出口 IP，源 IP 哈希会严重倾斜；移动网络切换基站时 IP 会变，会话随之漂移；用 Cookie 插入的方式虽比 IP 哈希准确，但在多级代理与 CDN 回源链路上可能被改写或丢弃。

因此粘性会话适合两类场景：会话本身不敏感、丢了重登代价很小的内部系统；以及作为迁移期的过渡手段，先把集中式存储建起来，再逐步把流量切过去。把它当成长期方案，等于把可用性押在“节点不挂、流量不偏、发布不停”这三个假设上。

集中式会话存储：把状态挪出进程

集中式会话的思路很直接：会话数据放到所有实例都能访问的存储里，实例本身无状态。请求进来后用会话 ID 去存储里查，查不到就拒绝。节点可以随意增删，发布不再影响登录态。

Redis 是最常见的选择，因为它天然支持按 key 过期，读写延迟低，主从与集群方案成熟。数据库也能存会话，优点是持久、可审计，缺点是每次请求都要读库，高频续期还会产生大量写，通常只在小流量系统或合规要求必须留痕时使用。

读多写少的场景还可以在进程内加一层 1 到 2 秒的本地缓存。它能削峰，但会把“踢下线”的生效时间推迟同样的量级；是否接受取决于业务，支付、改密这类操作必须绕过缓存直读。

无状态令牌：把状态交给客户端

无状态令牌的代表是 JWT，规范见 RFC 7519。服务端签发一个自包含的令牌，里面用 JSON 声明身份、过期时间等信息，再用密钥签名。后续请求带上它，服务端只需验签、检查过期，就能确认身份，完全不必查询存储。这带来了两个直接好处：横向扩展没有状态瓶颈，跨服务、跨语言传递身份也很自然。

另一个常见误解是“JWT 是加密的”。默认的 JWS 只签名不加密，载荷是 Base64URL 编码的明文，任何人都能解开看。手机号、身份证号、内部权限细节都不应放进去。确实需要保密时才用 JWE，但它会带来密钥管理与体积的额外复杂度，多数场景并不划算。

混合方案与选型

真实系统很少只用一种方案，更多是在几种手段之间做组合。常见的组合有三种。

第一种是“短访问令牌 + 服务端刷新令牌”。访问令牌有效期十几分钟，无状态、可被多个服务独立验证；刷新令牌存在 Redis 里，有效期数天，只能用于换取新的访问令牌，且每次刷新都轮换。这样既保住了横向扩展能力，又保留了吊销入口：踢下线只需删除刷新令牌，并要求访问令牌在分钟级内自然过期。

第二种是“不透明令牌 + 网关侧会话缓存”。令牌本身只是一串随机数，不携带任何信息，网关拿着它去 Redis 查会话，并在本地缓存几十秒。它比 JWT 更容易吊销，代价是每次查会话都有一次网络往返或缓存一致性问题。前文提到的本地缓存延迟，在这里同样存在。

第三种是“会话 + 局部无状态”。核心后台保留集中式会话，权限变化必须即时生效；面向 C 端的只读接口使用短期令牌，允许几十秒的失效延迟。这种做法看起来不统一，但它承认了一个事实：不同接口对“即时失效”的要求本就不同。

把几种方案放在一起比较：

维度 粘性会话 集中式存储 无状态令牌
改造成本 低 中 中高
扩容能力 差 好 好
即时吊销 容易 容易 困难
单点风险 低但故障放大 高，依赖存储 低
跨服务传递 弱 需共享存储 强
数据体积 无 服务端 随声明增长

选型时先问三个问题：能不能接受“踢下线有几十秒延迟”？会话数据是否需要在多个服务之间共享？团队有没有能力运维一套高可用 Redis？三个答案基本能锁定方向。若都拿不准，集中式存储是默认答案，它的行为最直观，出问题也最好排查。

Cookie 属性、CSRF 与跨域

无论会话 ID 放在 Cookie 还是请求头里，浏览器端的属性配置都直接决定安全边界。服务端下发时至少要写全这几个属性：

HttpOnly 让脚本读不到 Cookie，XSS 发生时攻击者无法直接窃取会话；Secure 限定只在 HTTPS 下发送，避免在明文链路上泄露；SameSite=Lax 阻止绝大多数跨站请求携带 Cookie，是抵御 CSRF 的第一道闸门。SameSite=None 只在前端与接口确实跨站时才用，且必须同时加 Secure，否则浏览器会直接拒收。

Domain 与 Path 是作用域，也是最容易配错的地方。Domain=.example.com 表示所有子域共享，a.example.com 与 b.example.com 都能读到；不写 Domain 则是宿主域专用，子域读不到。共享带来便利，也带来风险：任何一个子域被攻破，都可以读写主域的会话 Cookie。多子域系统常见的做法是把会话 Cookie 收敛到一个认证域，其他子域通过跳转或后端代理完成登录，而不是把 Cookie 铺到整个父域。

跨域场景还要处理 CORS 的凭据问题。前端携带 Cookie 时，Access-Control-Allow-Origin 必须是具体域名，不能是通配符，同时要返回 Access-Control-Allow-Credentials: true。不少团队在这里踩坑：预检请求通过了，实际请求却因为响应头缺了 Vary: Origin 被缓存串味，表现为“某些浏览器偶尔登录失效”。

CSRF 的防御不能只依赖 SameSite。旧版浏览器不支持该属性，部分场景又必须用 None，所以服务端仍需校验来源。常用手段是双提交 Cookie：把随机 token 同时写入 Cookie 和页面，提交时放在自定义请求头里，服务端比对两者是否一致。攻击者能让浏览器自动带上 Cookie，却无法读取它并放进请求头，这就构成了防御。对于纯 JSON 接口，强制 Content-Type: application/json 并要求自定义头，也能挡住表单类的简单请求。

会话安全：固定攻击、注销与并发登录

会话固定攻击的要害在于“让受害者使用一个攻击者已知的会话 ID”。攻击者先访问站点拿到一个 ID，再设法让受害者的浏览器也使用它，受害者登录之后，这个 ID 就升级成了已认证会话，攻击者直接拿着它访问即可。防御的核心只有一条：认证状态发生变化时，必须换发新的会话 ID。用户登录、提权、切换租户、修改密码，都要销毁旧会话并重新生成，绝不能沿用登录前的那个 ID。

注销看似简单，其实有两个层面。浏览器侧清 Cookie 只是让本地忘记，服务端记录还在，被窃取的 ID 依然有效；真正的注销必须删除服务端会话、移除用户索引，并让该 ID 立即不可用。如果使用了 JWT，还要把对应的 jti 或令牌版本写入短期的失效集合，长度只需覆盖访问令牌的剩余有效期。

并发登录控制依赖前面的用户索引。策略通常有三种：允许多端同时在线，只做设备列表展示；限制同时在线设备数，超出时挤掉最早登录的一个；单端登录，新登录直接顶掉旧会话。实现时先读集合、比较数量、再删除多余 ID，这个“读—判—写”必须原子化，否则并发登录会突破上限。对这个操作使用一段 Lua 脚本，比在应用层加分布式锁更轻。

踢下线是同一套机制的延伸：按用户查出所有会话 ID，逐个删除，同时清理索引。要注意的是，删除之后各实例的本地缓存可能还留着副本，所以要么接受一个短暂的生效延迟，要么在删除时广播一条失效消息，让各实例主动清缓存。

续期、一致性与故障降级

会话的过期策略通常是“滑动 + 绝对”两层：空闲超过一定时间失效，同时无论多活跃，登录满一定天数也必须重新认证。只有滑动过期，用户可能永远不重新登录；只有绝对过期，午休回来就被踢，体验很差。两者叠加，既控制风险，也照顾体验。

刷新令牌是滑动过期的另一种实现。访问令牌短期有效，刷新令牌长期有效，每次刷新都换发新的刷新令牌并作废旧令牌，这称为轮换。轮换的关键在于重放检测：如果某个已作废的刷新令牌再次出现，说明它可能被窃取，此时应立刻吊销整条令牌链，也就是同一登录会话派生的所有令牌。实现上给每次登录分配一个 family 标识，链上每个令牌都记录 family，异常时按 family 批量作废。

一致性方面要认清会话数据的性质：它读多写少，对跨实例的强一致要求不高，真正不能错的是“删除”和“权限变更”。因此常见的做法是写入走主库、读取允许短暂陈旧，但注销和权限变更走同步删除加事件通知。若把会话放进数据库，还要注意长事务与行锁：登录高峰时大量 UPDATE ... WHERE sid = ? 会在同一批热点行上排队，反而不如 Redis 的直接覆盖。

缓存故障时的降级策略必须提前定好，而不是等故障来了再拍脑袋。这里有一个绕不开的取舍：存储不可用时，是拒绝所有请求（fail-closed），还是放行（fail-open）？对支付、改密、后台管理，应当拒绝，宁可不可用也不能被绕过；对浏览类只读接口，可以短暂放行已签名的令牌，或退化为只读模式。把接口按敏感度分级，比全局一刀切更现实。

最后是单点问题。Redis 主从加哨兵能应对节点故障，但主从切换是异步复制，切换瞬间可能丢掉最后几条写入，表现为少量用户突然需要重新登录。这个代价通常可以接受，前提是客户端能正确处理 401 并引导重新登录，而不是陷入无限重试。使用集群模式时，还要注意会话 key 与用户索引 key 可能落在不同分片，跨分片的事务与脚本都不可用，设计时就要避免依赖它们。

容量、可观测性与迁移策略

容量估算要先算 key 的数量与单 key 体积。假设日活一百万、峰值同时在线十万，每人平均一点二台设备，会话总数就在十二万左右；单条会话按 1 KB 计，内存占用约一百多兆，加上 Redis 自身开销与副本，量级并不夸张。真正吃内存的是索引结构：为每个用户维护一个集合，集合本身的对象开销可能超过会话值，用户量大时应改用紧凑编码或定期清理空集合。所有数字均为示意，实际按自己的字段长度压测。

会话数据只与活跃用户数相关，与历史用户总量无关，过期 key 会被自动回收，因此容量规划盯住峰值在线数即可。反过来，如果内存随时间单调上涨，多半是过期策略失效：要么续期把 TTL 续成了永久，要么索引集合没有随会话删除而清理。

可观测性至少需要四个指标：当前会话数、登录成功与失败数、会话过期与主动注销数、以及会话读取的延迟分位。当前会话数不宜用 KEYS 统计，那会阻塞主线程；可以用 SCAN 采样估算，或者维护一个带过期时间的计数器。更有价值的指标是“过期率”，即单位时间内自然过期数与活跃会话数之比，它异常升高往往意味着续期逻辑或前端保活出了问题。

迁移要分三步走，切忌一次性切换。第一步双写：登录成功后同时写旧存储与新存储，读取仍走旧路径，观察新存储的写入成功率与数据形态。第二步双读灰度：按用户 ID 或流量比例切一小部分读新存储，命中失败时回退旧路径，同时记录回退率。第三步切换并观察一个完整的会话周期，确认没有用户因为迁移被迫重新登录，再停掉旧链路。

迁移期有两个细节值得提前约定：新旧 Cookie 用不同的名字，避免同名互相覆盖；回滚方案要真的演练过，而不是写在文档里。最忌讳的是“先停旧再启新”，一旦新链路有问题，全体用户同时掉线，回滚还要再经历一次登录风暴。

常见坑与收尾提醒

把前面散落的教训集中起来，大致是这么几类。

会话写入竞态。并发请求各自读—改—写整个会话，后写覆盖先写，导致踢下线失效、权限回退、设备列表错乱。对策是拆分可变字段、使用字段级更新，或引入版本号做比较交换。

JWT 无法即时吊销。签发即生效，过期前一直可用。对策是缩短有效期、引入令牌版本号或 jti 黑名单，并接受分钟级的生效延迟；不要指望在纯无状态的前提下做到即时失效。

Cookie 作用域配错。父域与子域共享、Path 写死到某个接口、SameSite=None 却漏了 Secure，都会造成“登录成功但下一个请求又未认证”。上线前用浏览器开发者工具逐个确认属性的实际值，比读代码可靠。

时钟偏差。JWT 的 exp、nbf 依赖签发方与验证方的系统时间，机器时间漂移几分钟就可能造成令牌被判定为未生效或已过期。所有节点应统一走 NTP，验证时留出少量时钟偏移容差，而不是把过期时间设得很长来掩盖问题。

Redis 单点与切换丢写。没有哨兵或集群时，一次重启就是全员掉线；有切换能力时，也要接受异步复制带来的少量会话丢失。会话存储的可用性目标应当与登录入口对齐，因为它就在登录链路上。

小结

会话方案没有银弹，只有取舍。粘性会话成本最低，但把可用性押在节点稳定上；集中式存储行为直观、易于管控，代价是多了一个必须高可用的依赖；无状态令牌扩展性最好，却在即时吊销上天然吃亏。多数系统最终会走向混合：短期令牌承担高频验证，服务端存储守住注销与权限变更的底线。

落地时优先把三件事做对：会话 ID 用密码学随机数并在登录时换发，Cookie 属性写全 HttpOnly、Secure、SameSite，注销与踢下线同时清理服务端记录和用户索引。这三件事与选哪种存储无关，却是安全与体验的基本盘。

剩下的属于运维与演进：把在线数、过期率、读取延迟纳入监控，迁移用双写双读灰度，降级按接口敏感度分级。把这些边界想清楚，会话就不再是那个“说不清为什么掉线”的黑盒。
