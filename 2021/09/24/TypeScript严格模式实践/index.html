TypeScript 严格模式实践

本文属于《TypeScript 学习路线》第 36/74 篇
上一篇系列目录下一篇

strict 在 tsconfig 里只是一个布尔值，但它背后是一组各自独立的编译选项。很多团队把它当成一次性开关，打开后面对几百条报错，最后用 any 和 ! 把红色压下去，严格模式也就名存实亡。

本文按选项逐项拆解 strict 究竟打开了什么：每一项解决什么问题、打开后会出现哪些典型报错、应该怎么修。之后讨论 4.4 新增的两个相关开关，以及存量项目如何渐进落地，避免把严格模式做成一场运动式的改造。

strict 是一个开关集合

在 tsconfig.json 里写下 "strict": true，编译器并不会因此多出一个名为 strict 的检查，它只是把一组布尔选项批量置为 true。这些选项各自盯着不同的位置，也可以被单独覆盖。

拆成多个开关并非多此一举：不同检查的迁移成本差异很大，alwaysStrict 几乎零成本，strictNullChecks 却可能触及每一行取值代码。拆开之后，团队才能按成本排序推进，而不是被最贵的那一项卡住。也正因如此，strict 打开后仍要逐项审视，而不是把关闭某一项当成个人偏好。

截至 TypeScript 4.4，strict 覆盖的成员包括 noImplicitAny、noImplicitThis、strictNullChecks、strictFunctionTypes、strictBindCallApply、strictPropertyInitialization、alwaysStrict，以及 4.4 起新加入的 useUnknownInCatchVariables。它并不包含 noUncheckedIndexedAccess、exactOptionalPropertyTypes、noImplicitOverride 这些同样以 no 开头的检查，这一点常被误解。

问题在于，配置项一旦写进仓库，下一个人很难判断它是深思熟虑的妥协还是历史遗留。凡是关闭的选项，都应当在配置旁注明原因、责任人和计划清理的时间，否则所谓严格模式会一点点被关回去。

还需要明确一点：严格模式是编译期的约束，除了 alwaysStrict 会输出 "use strict" 之外，它不产生任何运行时行为。它不会让代码变慢，也不会替你做任何数据校验。想确认最终生效的配置，可以用 tsc --showConfig 打印合并后的结果，extends 与单项覆盖都会体现在里面。

strictFunctionTypes 与 strictBindCallApply

strictFunctionTypes 检查函数类型参数位置的型变。参数是输入，所以接受更宽参数的函数可以替代接受更窄参数的函数，反过来不行。

这段报错值得理解而不是绕开：若允许赋值，调用 general({ name: "cat" }) 时实际执行的是只接受 Dog 的函数，运行时就会访问不存在的 bark。事件回调的经典坑也在这里：给 click 写了只接受 MouseEvent 的处理函数，赋给期望 Event 的位置就会报错。修法是参数写宽，进函数后再用 instanceof 或字段判断收窄。

这项检查有一个历史例外：以方法语法声明的成员仍然双变，以属性语法声明的函数类型才严格检查。把接口里的 onClick(dog: Dog): void 改成 onClick: (dog: Dog) => void，报错行为会不同。这不是漏洞，而是为兼容内置类型做出的取舍。

strictPropertyInitialization 与 alwaysStrict

这一项要求类的实例属性在构造函数结束时已经确定赋值，并且依赖 strictNullChecks 一起工作。

修法按推荐程度排列：能直接给默认值的就给默认值；必须由外部注入的，放进构造函数参数属性；确实在条件分支里赋值，就把分支补全到编译器能证明所有路径都覆盖，而不是用 ! 糊过去。

依赖注入框架常用属性注入，构造函数里确实拿不到值，此时可以写 private http!: HttpClient。! 是明确赋值断言，意思是“我保证运行时已经赋值”，编译器从此不再检查这一项。它没有运行时效果，字段若真的没被赋值，错误只是被推迟到调用那一刻。更稳妥的做法是用工厂函数返回构造完成的对象，或者把可选依赖写成 http?: HttpClient，在使用处显式处理缺失。判断标准很简单：这个字段在对象被外部使用之前是否一定有值，若答案不确定，就不该用 !。

alwaysStrict 则让每个文件按严格模式解析，并在 CommonJS 输出中加上 "use strict"。ES Module 和 class 内部本来就是严格模式，因此它的实际影响集中在老式脚本上：禁止隐式全局变量、禁止 with、禁止重复参数名。这一项几乎不带来迁移成本，很少需要单独讨论。

同一个版本还引入了 exactOptionalPropertyTypes。它不属于 strict，但与空值检查关系密切，常被放在一起讨论。默认情况下，age?: number 既允许键不存在，也允许显式写 { age: undefined }，因为可选属性被当作 number | undefined。打开该选项后两者被区分：?: 只表示键可以缺席，显式传 undefined 会报错，要同时接受两种写法必须声明成 age?: number | undefined。

这个差异在对象展开时最明显：{ ...defaults, retries: maybeUndefined } 会把键显式写进去，开启后可能整片报错。对 React 组件 props 这类大量使用可选属性的对象，影响尤其明显。它适合对配置对象、序列化结果要求精确的代码库，不适合作为默认项贸然打开，先确认依赖的类型声明是否兼容。

渐进开启与 CI 门禁

存量项目一次性打开 strict，报错动辄上千条，这是多数失败迁移的起点。可行的路径是按范围推进：用 extends 抽出基础配置，新代码、工具包、纯函数模块先开，老模块逐个目录跟进。

基线冻结是另一条实用手段。先跑一次 tsc --noEmit 拿到当前错误集合存成基线，CI 中只允许错误数量下降、不允许上升，新增文件必须零错误。加 --pretty false 可以让输出便于脚本解析。把门禁挂在 PR 上，比事后集中整改有效得多。若仓库是 monorepo，更省事的做法是按包拆分 tsconfig，用项目引用把严格包与非严格包隔离，编译速度也能受益。

第三方类型不兼容时，处理顺序建议是：先升级对应的类型包或库本身；其次在本地 d.ts 中做模块增强，只补缺失的成员；最后才在调用点做最小范围的断言，并把断言收敛进一个适配函数。

模块增强只补缺失的部分，原有声明继续生效。改完要回归 tsc --noEmit，确认没有引入新的冲突。最糟的做法是写一个全局声明把整个模块标成 any，那等于把严格模式从这一整块代码里删掉。

边界、误区与收益

严格模式保证的是代码内部类型一致，不是外部数据可信。接口返回值、localStorage、URL 参数、postMessage 的内容都可能在运行时与声明不符。接口文档写着 id 是数字，实际返回字符串，编译器无从判断。类型只是编译期的假设，边界处仍然需要运行时校验：手写类型守卫，或引入校验库，把 unknown 解析成可信结构后再进入业务逻辑。把这两件事混为一谈，是严格模式下最危险的错觉。

几个高频误区值得点名。其一是一刀切全开，几千条报错面前失去耐心，最后用 any 和 ! 批量消音，配置看着很严格，检查实际被绕过。其二是把 ! 当万能药，非空断言每多一处，strictNullChecks 的收益就少一分，可以把断言数量纳入评审关注项。其三是以为把 any 换成 unknown 就安全了：unknown 不能直接使用，若每次都 as 回具体类型，只是把风险挪了个位置，真正的价值来自收窄分支本身。

推进节奏同样重要。先选一个中等规模、依赖较少的模块试点，把常见报错和对应修法整理成清单，让评审有据可依；再把“新增代码不得引入 any 与非空断言”写进团队约定。除了错误总数，还可以统计豁免条数的变化，它比错误数更能说明检查是否被绕过。

收益方面，最直接的是重构信心与编辑器体验：重命名、改签名、删字段时，编译器会把受影响的位置列出来。其次是减少由空值引发的线上错误，这类问题往往藏得深、复现难。这些收益不会立刻体现在业务指标上，却会在每一次改动时兑现。成本主要是一次性改造和第三方类型维护。务实的做法是先统计错误类型分布，看空值类、隐式 any 类、初始化类各占多少，从占比最高、修法最机械的一类开始，用两三个迭代完成主体迁移，再决定是否收紧到 exactOptionalPropertyTypes 这类更细的选项。

小结

strict 是八个检查开关的集合，理解每一项比记住那个布尔值更重要。strictNullChecks 划出空值边界，noImplicitAny 与 noImplicitThis 堵住隐式推断，函数与类的检查分别约束签名和初始化，4.4 又把 catch 变量收归 unknown。落地靠分目录配置、带保质期的豁免、基线冻结和 CI 门禁，而不是一次豪赌。类型不替代校验，少用 !、少留 any，严格模式才真正生效。
