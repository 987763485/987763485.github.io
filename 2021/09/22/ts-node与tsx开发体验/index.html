ts-node 与 tsx 开发体验

本文属于《TypeScript 学习路线》第 21/74 篇
上一篇系列目录下一篇

在 Node.js 里写 TypeScript，最朴素的做法是先 tsc 编译成 JavaScript，再 node 运行产物，改一行代码就要走一遍编译。开发期这种来回切换非常打断思路，于是出现了直接执行 .ts 文件的运行器：ts-node 与本文要对比的 tsx。本文面向已经会用 TypeScript、正在搭 Node 服务或脚本工具的同学，讲清两者的工作原理、加速手段、常见坑，以及什么时候该用它、什么时候该回到编译产物。

阅读本文不需要事先了解 Node 的 ESM 加载机制细节，但需要知道 package.json、tsconfig.json 各自的作用；文中出现的耗时与体积数字均为示意值，仅用于说明量级差异。

为什么开发期需要 TypeScript 运行器

TypeScript 不是 Node.js 能直接执行的语言。Node 16 的模块加载器只认 JavaScript，.ts 文件对它来说只是一段无法解析的文本。所以任何“用 TypeScript 写 Node 程序”的方案，本质上都要在某处完成一次“类型语法剥离”，区别只在于这次剥离发生在什么时候、由谁来做。

传统流程把剥离放在前面：tsc 读取 tsconfig.json，把整个 src 目录编译到 dist，再由 node dist/index.js 启动。这条链路的问题不在正确性，而在反馈速度。一次改动要经历“保存、编译、重启、观察”四步，编译本身还要处理未改动的文件；项目稍大一些，冷启动的等待就会从“可以忍受”变成“干脆去泡杯茶”。

更麻烦的是路径与调试信息的错位。堆栈里出现的是 dist/xxx.js:12:5，要回到源码得靠 source map，断点也要先弄清楚停在编译后文件还是原始文件上。开发期关心的是“这段逻辑对不对”，而不是“产物长什么样”，编译在此时是纯粹的开销。

运行器的思路是把剥离推迟到加载时：入口仍然是 .ts，进程启动时在内存里完成转译，再交给 Node 执行。源码路径、行号、模块解析都保持在开发者的心智模型里，改完保存即可重跑。代价是每次启动都要重新转译，且类型检查是否保留需要单独决策——这正是后文所有取舍的源头。

ts-node 的工作方式

ts-node 最早依附于 CommonJS。它向 Node 的 require 扩展机制里挂一个编译钩子，当 require 遇到 .ts、.tsx 这类扩展名时，先调用 TypeScript 编译器把源码转成 JavaScript，再把结果交给 Node 的模块系统求值。整个过程在同一个进程内完成，不需要写临时文件，也不需要额外的子进程。

这条命令看起来只是换了可执行文件，实际发生了三件事：读取 tsconfig.json、按需转译被加载的模块、执行转译结果。第一件事最容易被忽视。默认情况下 ts-node 不是“转译一个文件就跑”，它还会做类型检查，而类型检查需要构建完整的程序图——include 里声明的文件、被引用的 .d.ts、types 字段引入的全局声明，都要纳入。于是启动耗时与项目规模正相关，几十个文件的服务就可能让每次启动多等上一两秒（示意值）。这也是很多人第一次用 ts-node 就得出“比编译还慢”结论的原因：慢的不是执行，而是启动时的检查。

flowchart TD
  A[npx ts-node src/index.ts] --> B[读取 tsconfig.json]
  B --> C{是否开启 transpileOnly}
  C -- 否 --> D[构建程序并做类型检查]
  C -- 是 --> E[仅剥离类型语法]
  D --> F[调用转译器输出 JS]
  E --> F
  F --> G[Node 模块系统求值]
  G --> H[业务代码运行]

transpileOnly 与 swc 加速

--transpileOnly 是 ts-node 最重要的开关。它跳过类型检查，只做语法层面的类型剥离，单文件转译，不构建程序图。启动耗时随之从“与项目规模相关”变成“与入口依赖链相关”。代价也很明确：类型错误不会阻止进程启动，const n: number = "x" 这样的代码能一路跑到运行时才报错，甚至根本不报错。

合理的做法是把检查挪到别处，让两道工序各司其职：开发时用 --transpileOnly 追求反馈速度，提交前与 CI 里单独跑一次 tsc --noEmit。编辑器里的语言服务也在实时检查，但它只覆盖打开的文件，不能替代全量检查。

把这段配置写进 tsconfig.json 后，ts-node 会用 @swc/core 代替 TypeScript 自带的转译器。swc 用 Rust 实现，单文件转译的开销远小于 ts.transpileModule，在大型项目里差距明显。需要注意 swc 只负责转译，不负责类型检查，也不处理 const enum、装饰器元数据之类的边角语义，遇到这类代码要先确认行为是否一致。若项目大量使用装饰器，建议先在分支上跑一遍测试再切换。

tsconfig-paths 与路径别名

tsconfig.json 里的 baseUrl 与 paths 只影响类型检查与编辑器，Node 运行时完全不知道它们的存在。于是 import { db } from "@/lib/db" 在 ts-node 下会直接抛“找不到模块”。解决办法是引入 tsconfig-paths，在进程启动前把别名注册进模块解析：

–files 与 –esm 的限制

--files 让 ts-node 在启动时加载 tsconfig.json 中 include 的全部文件。它主要解决两类问题：全局类型声明（如给 process.env 补充类型）在只转译入口时不会被加载；transpileOnly 下某些只被类型引用的文件也不会进入依赖链。加上 --files 可以缓解，但它同时把“按需加载”变回“全量加载”，启动又会变慢，属于典型的用速度换确定性。

--esm 则是另一条路：不再挂 require 钩子，而是以 Node 的 loader 形式介入 ESM 的解析与加载。它要求项目是 ESM（package.json 的 type 为 module，或文件后缀为 .mts），module 至少为 esnext，并且加载方式必须是 node --loader ts-node/esm，而不能是 ts-node --esm。这些约束在当时相当严格，下一节单独说明。

ts-node 在 ESM 下的坑

ESM 的解析规则与 CommonJS 不同，这是所有麻烦的根源。CommonJS 允许省略扩展名、允许目录导入（自动找 index.js），ESM 则要求导入说明符精确指向文件。于是即便源码是 utils.ts，导入时也得写成 ./utils.js：

这条规则让不少人第一次写 ESM 版 ts-node 就卡住：编辑器可能不报错，运行时却抛 ERR_MODULE_NOT_FOUND。原因是 TypeScript 在 module: esnext 下默认不校验扩展名，而 Node 的 loader 严格按字面路径查找。

第二个坑是 moduleResolution。TypeScript 4.4 的解析模式只有 classic 与 node，还没有后来为 ESM 准备的 node16 一类选项，因此 paths 别名、package.json 的 exports 字段在类型层面都得不到完整支持。实践中的妥协是：类型检查仍按 node 解析，运行时靠 tsconfig-paths 或手写相对路径；别名越多，ESM 迁移成本越高。

第三个坑是 loader 的顺序。node --loader ts-node/esm 会把 ts-node 插入加载链，它只接管 .ts 一类扩展名，其余交回默认 loader。如果同时使用别的 loader（例如某些打补丁工具），多个 --loader 会串成一条链，谁在前谁先拿到解析机会，顺序错了就会出现“类型没被剥离就被求值”的报错。另外，ts-node 在 loader 模式下默认仍做类型检查，想关掉得设环境变量 TS_NODE_TRANSPILE_ONLY=true；靠命令行参数是传不进去的，因为它此时只是被 Node 加载的模块。同理，child_process 派生的子进程不会继承 --loader，主进程能跑的 .ts 在子进程里照样报“未知扩展名”。

tsx 的 esbuild 路线

tsx 的思路与 ts-node 不同：它不调用 TypeScript 编译器，而是用 esbuild 做转译，并在外面包一层自己的模块解析。esbuild 用 Go 实现，转译是纯语法操作，一个文件几乎是即时完成，所以 tsx 的启动开销主要花在进程初始化与依赖加载上，而不是编译。

tsx 默认不做类型检查，这与 --transpileOnly 等价，但省掉了“先构建程序图”的那一步，因此在同一台机器上通常比开类型检查的 ts-node 快出数倍（示意值，实际取决于项目规模）。它同时支持 CJS 与 ESM 入口：CJS 走 require 钩子，ESM 走 loader，使用者不必为了运行方式改 package.json。

watch 是 tsx 内置的，不依赖 nodemon。它监听入口的依赖图，文件变化后重启子进程；对只改了类型的文件，重启也在所难免，因为它不区分“影响运行的改动”和“只影响类型的改动”。

flowchart LR
  A[.ts 源码] --> B[esbuild 转译]
  B --> C[内存中的 JS]
  C --> D[Node 执行]
  E[文件变化] --> F[watch 重启子进程]
  F --> A

与 Node 版本的关系需要说清楚。tsx 的 ESM 支持依赖 Node 的 loader 机制，Node 16 上该机制仍带实验性标记，启动时可能看到警告；CJS 入口则不受影响。项目若锁定较老的 Node（例如 12），ESM 入口基本不用考虑，只能用 CJS。反过来说，如果团队已经统一在 Node 16 且以 CJS 为主，tsx 与 ts-node 的差异主要体现在启动速度，而不是能力边界。

生产环境为什么不建议直接用

开发期追求的是反馈速度，生产追求的是确定性与资源效率，两者的最优解不同。把运行器直接搬上生产，会同时丢掉三样东西。

第一是类型检查这道闸门。运行器默认不做检查（或只检查一次启动），一个类型错误可能变成线上某个分支的静默错误。CI 里跑 tsc --noEmit 能补上，但那已经说明“检查”与“运行”是两件事，运行器并不提供保障。

第二是启动开销与内存。每次扩容、每次重启都要在进程内完成转译，冷启动时间被拉长；ts-node 的类型检查还会额外占用内存。对需要快速扩缩容的服务，这段开销会直接体现在扩容延迟上。第三是依赖体积：typescript、ts-node、esbuild 这些本该留在 devDependencies 的包，一旦运行时要靠它们，就得装进生产镜像或生产依赖，镜像体积与攻击面一起变大。

正道仍是构建产物部署：CI 里 tsc -p tsconfig.build.json 输出到 dist，生产只跑 node dist/index.js，NODE_ENV=production，source map 单独归档供排查。若想进一步缩短冷启动，可以用 esbuild 或 swc 做打包，但那是“构建得更快”，而不是“运行时现编译”。运行器的定位始终是开发与脚本工具，不是生产运行时。

Monorepo、测试与选型

多包仓库里每个包有自己的 tsconfig.json，通常用 extends 继承根配置。paths 指向兄弟包的 src 能让类型跳转顺畅，但运行时依旧不认；两条出路是让包之间通过构建产物引用（tsc -b 加 project references），或在运行器侧统一注册 tsconfig-paths。tsx 会把 paths 交给内建解析，行为随版本变化，升级后要回归验证。

测试运行器

ts-jest 默认按 tsconfig 做类型检查，慢；开启 isolatedModules 后只转译，速度接近 babel-jest，代价同样是放弃类型检查。vitest 走 Vite 的转换链，天生只转译，当时生态还在补齐。它们与本地运行器互不共享缓存，配置要各写一份。

选型建议

以 CJS 为主、需要完整类型检查、项目较老：选 ts-node；只追求启动速度、愿意另跑 tsc --noEmit：选 tsx；要上 ESM 而 Node 尚在 16：先用 tsx 试水，ts-node 的 loader 组合需要更多调试。一次性脚本优先 tsx，长期服务两者皆可，团队已有配置往往是决定因素。

常见坑

  • tsconfig 不一致：运行器与 tsc 用的不是同一份配置，或工作目录不同，表现为编辑器不报错、启动却报错。
  • 装饰器：esbuild 不产出装饰器元数据，依赖反射的依赖注入会失效，NestJS 一类项目慎用 tsx。
  • paths 运行时未解析：类型检查通过，启动却找不到模块，需要 tsconfig-paths 或改回相对路径。
  • ESM 与 CJS 混用：同一包里两种格式并存时，default 导入的形状不同，容易拿到 undefined。

小结

运行器把编译从“前置步骤”变成“加载时动作”，换来反馈速度，也把类型检查挪出了运行路径。开发期用它，检查交给 tsc --noEmit 与 CI；生产用构建产物部署。选型先看模块格式与装饰器需求，再看启动速度，最后看团队已有配置。
