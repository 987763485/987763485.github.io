Rust 宏：声明宏与过程宏

本文属于《Rust 学习路线》第 27/68 篇
上一篇系列目录下一篇

宏是 Rust 中唯一能在编译期生成代码的机制，也是不少读者翻开标准库或框架源码时最先卡住的地方。本文从宏与函数的差别讲起，逐步说明 macro_rules! 的匹配规则、片段说明符、重复与卫生性，再进入过程宏的三种形态以及 syn、quote 的配合方式。读完之后，你应当能独立写出可维护的声明宏，并为自己的类型实现一个派生宏，同时判断哪些场景其实不该用宏。

文中示例以 Rust 1.55 为准，只使用稳定版能力；宏 2.0 与编译器内部实现不在讨论范围内。

宏与函数的分界

日常写业务代码，函数足以覆盖绝大多数需求：参数个数固定、类型写在签名里、调用发生在运行时。宏的定位完全不同，它在编译期把一段代码替换成另一段代码，编译器看到的已经是展开后的结果。这个差别决定了三件事。

第一是参数形式。println! 可以接收任意多个参数，vec![1, 2, 3] 的元素个数也随调用变化，函数做不到这一点，只能用切片或元组凑合。第二是接收的内容。宏拿到的是 token 序列，不是求值后的值，所以它能接受类型、模式，甚至一整段语句，matches!、assert_eq! 这类“看起来像语法”的工具才得以成立。第三是出现的位置。宏调用可以写在表达式、语句、模式、类型乃至模块项的位置上，lazy_static! 就是在 item 位置展开的。

代价同样明确。宏在编译期展开，调试器看到的是展开后的代码，断点与变量名可能和源码对不上；IDE 的跳转、补全与重命名对宏内部的支持弱于普通函数；错误信息通常指向调用处，而不是宏定义内部。理解这些代价，才能判断什么时候值得写宏。

Rust 的宏分两类：用 macro_rules! 定义的声明宏，以及运行在编译器进程里的过程宏。前者按 token 模式匹配，写法接近语言内建的语法规则；后者是一段真正的 Rust 程序，可以任意计算，但必须放在独立的 crate 中。

冒号后面的部分是片段说明符，它决定这一段 token 按什么语法类别解析。常用的有十种：

说明符 匹配内容
expr 表达式
tt 单个 token 树
ident 标识符或关键字
ty 类型
pat 模式，顶层不能直接写竖线
path 路径，如 std::vec::Vec
stmt 语句
block 花括号块
item 项，如函数、结构体
literal 字面量

片段说明符有一个容易踩的限制：某个片段之后只能跟有限的分隔符。expr 与 stmt 后面只允许出现 =>、,、;，写成 $e:expr + 1 会得到 “no rules expected token” 之类的报错。原因在于解析器需要在匹配阶段就确定表达式的边界，允许任意后续 token 会带来歧义。遇到这种需求时，改用 tt 逐个接收，或者把整个表达式交给 expr 一次吃完再在展开侧处理。

重复语法解决变长参数。$( ... )* 表示零次或多次，+ 表示一次或多次，? 表示零次或一次，分隔符写在重复体之后：

递归是声明宏处理嵌套结构的常用手法：每次吃掉一个 tt，把剩下的 token 递归交给自己，直到匹配空输入的基本规则。

这种写法简单直接，但展开深度与 token 数量成正比，长列表会触碰编译器的递归上限，后文会专门讨论。

声明宏最实用的场景是消除样板：为一组相似类型生成实现、把字面量列表加工成常量表、在测试里批量构造用例。它的长处是写法轻、不需要额外 crate；短处是只能做 token 层面的重组，碰到需要读取类型信息的需求就得让位给过程宏。判断标准很简单：如果展开规则能用几句话描述清楚，声明宏就够用；如果规则依赖于被标注项的结构，直接上过程宏。

卫生性与导出

卫生性（hygiene）指宏展开产生的标识符与调用位置的同名标识符处于不同的语法上下文，从而不会意外冲突。声明宏的卫生性是部分的：局部变量受保护，项、类型与路径不受保护。

宏内部的 x 与 main 里的 x 互不干扰，这是局部变量卫生性在起作用。反过来，宏也无法直接读取调用处的局部变量：

value 在宏定义处并不存在，展开后同样找不到调用处的 value，因为标识符携带的是定义位置的上下文。正确做法是把值作为参数传入。这既是卫生性的要求，也提醒我们：宏的输入应当显式，不要依赖调用环境的隐式约定。

不卫生的部分同样要注意。若宏展开出一个固定名字的函数或类型，在同一模块调用两次就会得到重复定义错误。生成内部项时，应加足够独特的前缀，或者改为生成匿名结构、闭包，避免污染调用者的命名空间。

跨 crate 使用时，在宏定义前加 #[macro_export]，宏会被放到 crate 根，用 crate_name::macro_name! 调用；2018 edition 下也可以先 use crate_name::macro_name;。带此属性的宏不受模块私有性约束，等于公开 API，需要认真写文档并考虑向后兼容。

卫生性还会影响宏内部的临时变量。若展开时创建的 let 绑定与调用处同名，编译器不会报冲突，但阅读展开结果的人容易混淆。给临时变量加上宏名前缀（如 __sum_total）是常见约定，既减少视觉干扰，也降低名字意外相同的概率。

过程宏的三种形态

函数式宏适合输入不是合法 Rust 语法的场景，例如在宏内部读取一份 DSL 或配置片段。它的输入同样可以先交给 syn 解析，也可以直接遍历 TokenStream，灵活性最高，可读性风险也最大。

调试、错误与测试

宏最麻烦的地方是“看不见”。cargo expand 这个独立工具能把展开后的代码打印出来，是排查问题的第一手段：先确认展开结果是否符合预期，再检查逻辑，比盯着宏定义猜要快得多。过程宏还可以在编译期用 eprintln! 输出中间结果，内容会打到编译器的 stderr 上。

测试方面，声明宏就是普通代码，用 #[test] 调用并断言结果即可；同时把带语言标注的示例写进文档注释，cargo test 会把它当作文档测试执行，等于免费获得一组用例。过程宏的失败路径需要专门工具，trybuild 可以编译一组预设的 .rs 文件并比对报错输出，适合锁定错误信息不回归。无论哪种宏，都应为合法输入与非法输入各准备几条用例。

常见坑与取舍

第一是展开顺序。宏参数是 token 树，传入时不会先求值，也不会先展开；外层宏先展开，内层后展开。若外层把参数重新拼接，内层宏可能拿到意料之外的 token。组合宏时，最好让每层只负责一件事。

第二是递归深度。默认的 recursion_limit 是 128，前面那个 count! 在 token 较多时就会报错。可以在 crate 根加 #![recursion_limit = "256"] 提高上限，但更根本的办法是分块递归：一次吃掉两个或四个 token，把深度降到对数级。tt 递归尤其容易踩坑，因为它对每个 token 都展开一次。

第三是类型推断。展开代码里常出现 let 绑定、闭包与默认整型，类型错误在调用处爆出来，指向的却是宏内部的行。遇到 “type annotations needed” 时，先 cargo expand，再在展开结果上补标注，定位速度远快于修改宏定义。

第四是错误信息的可读性。宏越通用，报错越抽象，tt 与 expr 混用时编译器可能只提示 “expected expression”。设计时应尽量收紧片段说明符，宁可多写几条规则，也不要为了灵活全用 tt。

第五是过度使用。宏会拉长编译时间、削弱 IDE 支持、让调用栈难以追踪。能用泛型与 trait 表达的抽象，优先用泛型；能用函数或结构体封装的重复，优先用函数；只有在语法层面必须扩展，或者需要接受不定数量 token 时，才轮到宏。

至于何时不该用宏：跨类型复用行为，用 trait；编译期常量计算，用 const fn；按类型分派，用 trait 与关联类型。宏是最后手段，不是第一选择。

小结

宏的本质是编译期代码生成：声明宏靠 token 模式匹配，适合语法层面的小扩展；过程宏靠 Rust 程序计算，适合派生实现与属性处理。写声明宏时牢记匹配顺序、片段说明符的后续限制以及重复变量的对应关系；写过程宏时把解析、生成、报错三件事分开，用 syn 解析、quote 生成、syn::Error 报错。卫生性要求输入显式，$crate 保证跨 crate 路径可靠，cargo expand 与 trybuild 则分别解决“看不见”和“改坏了”的问题。最后一条经验是克制：宏的收益在语法层，成本在可读性与工具链，多数重复逻辑用泛型和函数就能解决。
