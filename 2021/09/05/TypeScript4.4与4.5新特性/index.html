TypeScript 4.4 与 4.5 新特性

本文属于《TypeScript 学习路线》第 48/74 篇
上一篇系列目录下一篇

TypeScript 4.4 已于 2021 年 8 月 26 日正式发布，距本文写作不过十天，社区讨论还集中在升级后冒出的类型报错上。本文先把 4.4 里真正会影响日常代码的几项改动讲清楚，再顺着官方迭代路线，梳理当时尚在预览阶段的 4.5 方向。

需要提前说明的是，4.5 在本文写作时并未发布，其特性只停留在提案与 nightly 版本中，语法和命名都可能调整。因此下文对 4.5 只谈方向与动机，具体行为请以最终的 release notes 为准。

从 catch 变量默认 unknown 说起

TypeScript 4.4 最容易被感知的变化，是 useUnknownInCatchVariables 在 strict 模式下默认开启。在此之前，try...catch 捕获到的变量类型是 any，你可以随手读取它的任意属性，编译器不会阻拦；代价是运行时一旦抛出的是字符串或普通对象，那些属性访问就会直接崩掉。

开启之后，catch 变量的类型变成 unknown，任何未经检查的成员访问都会报错。这个改动的思路和 unknown 本身一致：先承认“我不知道抛出来的是什么”，再要求调用方显式判断。它把一类潜在的运行时错误提前到了编译期，代价是升级瞬间会出现一批新报错。

收窄的写法并不复杂，最常见的是 instanceof 判断，其次是针对 Error 形状的结构化检查。对于确实无法预知抛出物的老代码，也可以退回到显式标注 any，但那等于主动放弃这层保护。

如果项目暂时不想处理这批报错，可以在 tsconfig.json 中把 useUnknownInCatchVariables 单独设为 false，而不必整体关掉 strict。这是 4.4 提供的一条温和迁移路径：新代码享受保护，存量代码留出改造时间。

精确可选属性：exactOptionalPropertyTypes

第二个值得单独拿出来讲的开关是 exactOptionalPropertyTypes。它默认关闭，也不属于 strict 家族，需要手动开启。要理解它，先要区分两个在运行时并不相同、在旧类型系统里却被混为一谈的状态：属性“不存在”，以及属性“存在但值为 undefined”。

在 4.4 之前，x?: string 的可写类型实际上包含了 undefined，因此下面三种写法都能通过检查。开启该选项后，显式赋 undefined 会被拒绝，只允许省略属性。

这项检查的价值在于让类型贴近运行时语义。属性缺失时，"timeout" in opts 为 false，Object.keys 不会列出它，JSON.stringify 也不会输出它；而显式写 undefined 时，键是存在的。许多库正是靠“键是否存在”来决定是否覆盖默认值，旧类型系统却无法表达这种差异。

如果业务上确实需要“可以显式传 undefined”，把类型写成 timeout?: number | undefined 即可。注意读取侧不受影响，opts.timeout 依旧是 number | undefined，因为属性可能根本不存在。这个开关更像一把精细的刻刀，适合在类型边界清晰的项目里使用，而不是无脑打开。

对库作者而言，这一选项还意味着声明文件要更诚实：如果某个属性在实现中确实可能被赋值为 undefined，就应显式写成 T | undefined，而不是让调用方去猜。否则使用方一旦开启精确检查，传值处就会报错，而问题其实出在类型声明上。

索引签名的新形态：symbol 与模板字符串

索引签名过去只接受 string 与 number 两种键类型。4.4 把口子扩到了 symbol 和模板字符串模式，这让一批原本只能靠 any 或交叉类型绕过的场景有了正经写法。

先看 symbol。当对象需要挂载一些不希望与字符串键冲突的元数据时，用唯一的 symbol 作键是常见做法，但旧版类型系统无法描述“任意 symbol 键都映射到某类型”。

再看模板字符串模式。它允许用字面量模板描述键的命名规律，例如 CSS 自定义属性必须以 -- 开头。下面的写法既约束了值的类型，也拒绝了不符合模式的键。

需要提醒的是，模式索引签名仍然是索引签名，它不会替你检查某个具体键是否一定存在，也不会产生联合类型的穷尽性。它的作用是约束“键的形状”和“值的类型”，而不是做键的枚举。此外，对象字面量的多余属性检查与模式匹配的交互细节较多，遇到意外报错时，先把对象显式标注为目标类型，再逐步定位。

类 static 块：把静态初始化写进类体

4.4 支持了类静态初始化块，也就是常说的 static 块。在此之前，要在类定义完成后执行一段静态初始化逻辑，只能写在类外面，或者借助立即执行函数，代码组织上总有些割裂。

static 块的优势在于作用域。块内可以访问类的私有静态成员，临时变量也不会泄漏到外层；this 指向类本身，而不是实例。多个静态字段与静态块之间，按书写顺序依次执行，这一点与普通字段初始化一致。

继承关系下的顺序尤其要留意：基类的静态初始化一定先于派生类完成，因此派生类的静态块可以安全读取基类的静态成员，反之则不行。块内不允许 return，也不能使用 await；如果初始化确实需要异步，应在块内启动一个 Promise 并自行处理后续流程。编译目标方面，设为 es2022 或 esnext 时会原样保留，低目标下则由编译器降级展开。

静态块的另一类常见用途是注册：把当前类登记到一张映射表中，供工厂函数按名字创建实例。这样注册逻辑与类定义放在一起，新增实现时不容易漏写；代价是导入该类就会触发副作用，测试中需要留意模块的加载时机。

别名条件与判别式的控制流分析

控制流分析是 TypeScript 类型收窄的核心机制，但此前的实现只认“当场写出”的条件。如果把判断结果先存进一个变量，再用这个变量做分支，收窄就会失效。4.4 补上了这块短板，官方称之为别名条件与判别式的分析。

判别式联合类型同样受益。当下面的 kind 判断被存进常量后，分支内依旧能正确收窄到对应的成员类型。

这项能力有明确边界：别名必须用 const 声明，且声明后不能被重新赋值；如果变量是 let，或者在闭包中可能被修改，编译器就不会据此收窄。理解这一点很重要，否则容易误以为是编译器“时灵时不灵”。实践中，把判断结果命名为 isString、hasValue 这类断言式变量，既能提升可读性，也能顺带获得收窄。

还要注意，别名分析只采信类型层面的证据。普通布尔函数的返回值不会被当作收窄依据，除非该函数本身声明了类型谓词（形如 value is T）；此时把调用结果存进常量，分支内同样能收窄。反过来，纯粹的数据比较只要是用 const 保存的，就可以放心依赖。

工具链与编辑器体验

除了类型系统本身，4.4 在排查配置问题时也给了一件顺手的工具：--explainFiles。它会列出当前编译程序包含的每一个文件，并说明该文件为何被纳入，例如被某个入口导入、命中 include 规则、来自默认库，或者由某个 @types 包带入。

当项目里莫名出现全局类型冲突，或者打包结果比预期大时，这份清单往往比逐层翻 tsconfig.json 更快定位问题。尤其是某些依赖间接引入的 @types 包，会悄悄把全局声明塞进编译上下文，靠肉眼很难发现。

拼写建议也在这一版本周期里更实用：属性名写错时，编译器会给出 Did you mean ... 的提示，并列出候选成员。对于名字冗长的配置对象，这条提示能省下不少查文档的时间。编辑器侧则提供了内联提示，在函数调用处直接显示参数名，阅读他人代码时不必反复跳转签名，属于体验层面的改进，不影响编译结果。

4.5 的预览方向：尚未发布

必须先把状态说清楚：截至本文写作时，TypeScript 4.5 尚未发布，仍处于 nightly 与预览阶段，官方也没有给出最终的特性清单。按照大约三个月一个版本的迭代节奏，正式版预计要到当年晚些时候，但具体日期与语法请以最终的 release notes 为准。下面几项是当时讨论较多、方向相对明确的内容，仅作预览，不宜在生产代码中依赖。

第一项是 Awaited 类型。异步代码里经常出现层层包裹的 Promise，await 一次未必能拿到最终值，Awaited<T> 想做的是递归展开 thenable，描述“真正等待完成之后”的类型。它既可能作为内置工具类型提供，也会影响 async 函数返回值的推断。方向是明确的，但具体的递归深度限制与边界行为，当时仍在调整。

第二项是 import type 的名称内联修饰符。此前要把类型导入和值导入分开写两行，提案允许在一条语句里混合，用 type 前缀标记其中某个名称。

这样做的好处不只是少写一行。在 isolatedModules 下，编译器需要判断某个导入是否只用于类型；内联标记把意图直接写在了名称上，转译工具不必猜测，也就不容易误删运行时要用的导入。

第三项是私有字段的 in 存在性检查。类可以用 #field in obj 判断某个对象是否由本类构造，从而实现所谓的品牌检查，而不必依赖强制类型转换或额外的哨兵属性。第四项是让模板字符串类型参与判别式收窄：当联合类型的判别属性是模板字符串字面量时，针对具体字符串的比较也能触发收窄，这与 4.4 的别名判别式分析是一脉相承的思路。

最后是两项与模块输出相关的讨论。--preserveValueImports 试图阻止编译器删除那些“看起来没被使用、但运行时确实需要”的值导入；--module es2022 则希望在不设 esnext 的前提下使用顶层 await 等较新的模块特性。两者都涉及转译与运行时的边界，最终形态在本文写作时尚未确定。

如果想提前感受这些能力，可以在独立分支安装 nightly 版本编译一遍，观察报错与推断结果，但不要把 nightly 写进主分支的依赖版本；预览版的类型定义随时会变，锁死版本反而会拖住后续升级。

升级注意事项

从 4.3 升到 4.4 通常不需要改代码，但几处默认行为的变化值得提前评估。第一处是 catch 变量的 unknown 化。建议写一个可复用的守卫函数，而不是在每个 catch 里重复判断，也不要用 as any 一压了事。

第二处是 exactOptionalPropertyTypes 与第三方类型的兼容。不少 @types 包仍按旧语义书写可选属性，开启该选项后，把 undefined 显式传给这些属性就会报错，而调用方往往只是转发一个可能为空的配置。务实的做法是新项目直接开启，老项目先在一两个包上试水；确实需要透传 undefined 时，把类型改成 T | undefined 并注释原因，而不是用断言掩盖。

第三处是 static 块的执行顺序。静态字段与静态块按书写顺序执行，基类先于派生类完成初始化。把有顺序依赖的初始化集中写在同一处，避免派生类的静态块去读基类尚未赋值的成员；如果顺序确实复杂，宁可退回类外的显式初始化函数，让依赖关系一眼可见。

小结

TypeScript 4.4 已经发布，最值得关注的是 catch 变量默认变为 unknown、可选的 exactOptionalPropertyTypes、symbol 与模板字符串模式的索引签名，以及 static 块和控制流分析的增强。升级时优先处理 catch 收窄，再评估精确可选属性对第三方类型的冲击。

4.5 在本文写作时尚未发布，Awaited、import type 内联修饰符、私有字段 in 检查等只是预览方向，语法与行为都可能变化，请以最终 release notes 为准。对生产项目而言，稳妥的策略是先升到 4.4 并打开新检查，等 4.5 正式发布后再逐项试用。
