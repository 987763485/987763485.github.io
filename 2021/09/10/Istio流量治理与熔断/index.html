Istio 流量治理与熔断

本文属于《Docker 与 Kubernetes》第 34/51 篇
上一篇系列目录下一篇

把服务搬上 Kubernetes 只是第一步，真正让人睡不着觉的是服务之间的调用关系：某个下游慢了一百毫秒，上游线程池就被拖满；发版时想让新版本只接百分之五的流量，却只能靠副本数硬凑；一次机房抖动引发雪崩，事后复盘发现没有任何一处限流和熔断。Istio 想解决的正是这类问题，它把流量规则从业务代码里抽出来，变成可以声明、可以回滚、可以审计的配置。

本文以 Istio 1.10 与 1.11 为准，围绕流量治理这条主线，讲清 VirtualService 与 DestinationRule 的分工，路由匹配与灰度发布怎么写，超时重试和熔断如何配合，故障注入与流量镜像怎么用于演练，最后落到规则生效顺序、可观测性和一组真实踩过的坑。入门概念留给 702，Envoy 内部实现留给 707，零信任落地留给 719，本文只谈治理本身。

两类资源的分工

写 Istio 流量规则时，最常见的困惑不是 YAML 语法，而是不知道该把一段配置放进哪个对象。Istio 把治理拆成两层：一层决定请求去往哪里，一层决定到达之后如何对待这个目标。前者是 VirtualService，后者是 DestinationRule。把这两层分清，后面所有的路由、灰度、超时、熔断才有地方安放。

VirtualService 描述的是“请求路径”。它的核心字段是 hosts 和 http，每一条 http 规则包含三部分：match 决定哪些请求命中，route 决定命中后发往哪个 destination，其余字段则是对这条路由的修饰，例如 timeout、retries、fault、mirror、rewrite。一句话概括，VirtualService 是面向请求的、有顺序的规则表，它回答“这个请求该走哪条路”。

DestinationRule 描述的是“目标侧策略”。它同样有一个 host，但内容不再是匹配条件，而是 trafficPolicy：负载均衡算法、连接池上限、异常检测（熔断）、上游 TLS 模式，以及 subsets 子集定义。DestinationRule 回答的是“对这个服务的所有连接，我允许多少并发、如何挑选实例、发现坏实例后怎么处理”。

两者通过 subset 连接。subset 是 DestinationRule 里用标签选出来的一组 Pod，例如 version: v2；VirtualService 的 route.destination 只写服务名和 subset 名，不直接写标签选择器。这种设计让“哪些实例属于 v2”只在一处定义，路由规则可以反复引用。

    VS --> D2[destination: reviews v2]

从图里可以看出一个容易被忽略的事实：熔断和连接池并不作用在 VirtualService 上，而是作用在“到某个 subset 的连接”上。因此如果两个 subset 指向同一批 Pod，却只给其中一个配了异常检测，实际效果会取决于流量走了哪条路，而不是集群整体状态。

还有一层优先级需要记住。DestinationRule 的 trafficPolicy 可以写在顶层，也可以写在 subsets[].trafficPolicy，还可以写在 portLevelSettings 里。生效顺序是从具体到一般：端口级覆盖 subset 级，subset 级覆盖顶层。排查“为什么我配的策略没生效”时，先看有没有更高优先级的覆盖。

路由匹配与灰度发布

路由匹配是流量治理的入口。Istio 的 HTTP 匹配支持 URI、headers、method、queryParams、sourceLabels、gateways、port 等维度，URI 又分 exact、prefix、regex 三种。匹配遵循“按书写顺序，首条命中即停止”的规则，这一点与防火墙规则类似，因此书写顺序本身就是语义的一部分。

实践中的书写原则是“越具体越靠前”。把带 header 的灰度规则放在全量规则之前，否则全量规则会先吃掉所有请求，灰度规则永远不会被求值。这类错误不会报错，配置校验也会通过，只会在灰度时表现为“新版本一个请求都没有”，非常隐蔽。

上面这段同时演示了两种灰度思路。第一条规则是“命中特定 header 就走 v2”，适合内部测试账号、特定租户或前端灰度开关；第二条是按权重分流，90 与 10 是示意值，实际比例按发布节奏定。两条规则并存时，带 header 的请求一定走 v2，其余请求按 9:1 随机分配。

需要注意的是，权重表达的是“请求级”的比例，不是“用户级”的比例。同一个用户在两次请求之间可能一会儿落 v1、一会儿落 v2。如果业务要求同一会话固定在一个版本，可以在 DestinationRule 里配置基于 cookie 或 header 的一致性哈希负载均衡，但这与按权重拆分会相互影响：哈希把同一会话钉在某个实例上，权重只决定实例集合的构成。两者叠加的真实效果必须实测，不能只看配置推断。

金丝雀与蓝绿的区别，落在配置上其实就是“权重渐变”与“整体切换”。金丝雀按 1%、5%、20%、50%、100% 逐步放大，每一档都观察错误率与延迟；蓝绿则准备两套完整环境，用 header 或整比例把流量一次性切过去，出问题再切回。前者对容量要求低、暴露面小，后者回滚最快、验证最彻底。

超时与重试

分布式系统里，最贵的不是失败，而是“不知道失败”。超时把不确定的等待变成确定的错误，让调用方有机会释放线程、返回兜底；重试则在错误确实短暂的情况下，用额外请求换取成功率。Istio 把这两件事都做成了路由级配置，不需要改一行业务代码，但也正因为配置在外部，写错了很难被代码评审发现。

timeout 写在某条 http 规则上，作用于命中这条规则的所有请求。它统计的是整条请求的生命周期，包含重试在内，而不是每一次尝试。这一点非常关键：如果 timeout 设成 3 秒，retries 允许 3 次尝试、每次 perTryTimeout 为 2 秒，那么实际并不会跑到 6 秒，第一次尝试超时后剩余预算只剩 1 秒，后续尝试会被整体超时切断。配置看起来层层设防，实际只有第一层生效。

attempts 是总尝试次数，包含第一次，因此 attempts: 3 意味着最多重试两次。perTryTimeout 限制单次尝试的时长，retryOn 用逗号分隔的条件决定哪些响应或错误值得重试，常见取值包括 5xx、reset、connect-failure、retriable-status-codes。最后这个条件需要配合 retriableStatusCodes 使用，只有列在其中的状态码才会被当作可重试。

上面的 3 秒、3 次、2 秒都是示意值，真实取值要先测出下游的延迟分布，再按 P99 留出余量。一个稳妥的约束是 attempts × perTryTimeout 不超过 timeout，否则后面的尝试只是纸面上的配置；反过来，如果 timeout 远大于乘积，超时保护就形同虚设，慢调用会长时间占住上游线程。

重试最危险的地方不是重试本身，而是它在调用链上被逐层放大。假设三个服务依次调用，每一层都配置 3 次尝试，最下游一次故障会被放大成 27 次请求。下游本来已经过载，重试像放大器一样把压力再乘一遍，最终把“局部慢”变成“整体雪崩”。这个问题在 2021 年依然是服务网格落地时最常见的生产事故来源之一。

控制放大的办法有三条。第一，只在最靠近用户的一层做重试，内层服务把重试关掉，让失败快速向上传递。第二，给重试设预算，例如用总尝试次数或时间窗口限制，而不是无脑放开。第三，坚持幂等前提：只有 GET、HEAD 这类安全方法，或者业务上明确可重复执行的接口，才允许自动重试；下单、扣款这类非幂等写操作，重试等于重复提交，必须靠业务侧的去重键兜底。

还有一类错误常被误判为“重试没生效”。如果下游返回的是 4xx，例如 400 或 404，默认不会被重试，这是合理的；但如果业务把内部错误包装成 200 加错误码，Envoy 只看到 200，自然不会重试。治理层只能根据协议层信号做判断，业务语义必须由应用自己处理。

熔断：连接池与异常检测

很多人把 Istio 的熔断理解成一个开关：错误多了就跳闸。实际机制要细一些，它由两个互补的部分组成：连接池限制是“闸门”，异常检测是“剔除”。前者控制并发与排队，后者把不健康的实例从负载均衡池里拿出去。只配其中一个，都会得到半套保护。

连接池配置在 DestinationRule 的 trafficPolicy.connectionPool 下，分 TCP 与 HTTP 两组。tcp.maxConnections 限制到目标服务的最大连接数，connectTimeout 控制建连超时；HTTP 侧的 http1MaxPendingRequests 限制等待就绪连接的请求数，http2MaxRequests 限制到目标的最大并发请求数，maxRequestsPerConnection 控制连接复用程度，maxRetries 限制并发重试数。当这些上限被击穿时，Envoy 会直接拒绝新请求，并在访问日志里留下 UO 标志。

这里的 100、50、200、5、30 秒同样是示意值。连接池上限的正确算法是从下游容量倒推：单实例能稳定处理多少并发，乘以实例数，再留出冗余，而不是照抄别人的 YAML。上限设得太松，保护等于没有；设得太紧，正常流量也会被误杀，表现为莫名其妙的 503。

outlierDetection 是真正意义上的熔断。它关注两类信号：consecutive5xxErrors 统计连续收到的 5xx 响应，consecutiveGatewayErrors 统计 502、503、504 这类网关错误，后者对 TCP 场景也适用。计数在 interval 窗口内进行，达到阈值就把该实例驱逐 baseEjectionTime，在此期间不再向它分配新请求。

驱逐不是永久的。时间到期后实例会被放回池子，然后重新开始计数；如果很快又连续失败，驱逐时长会按次数累加，这就是所谓的退避。maxEjectionPercent 限制最多驱逐多少比例的实例，防止一次网络抖动把所有实例都踢光；minHealthPercent 则定义了恐慌阈值，当健康实例比例低于它时，Envoy 会忽略驱逐状态，把请求发给所有实例——宁可打到可能坏的实例，也好过全部拒绝。

这套机制有一个容易被忽略的前提：异常检测基于“每个 Envoy 自己的观察”。调用方 A 的 sidecar 认为某个实例坏了，只影响 A 发往该实例的流量，其他调用方不受影响。因此它更适合处理“某个实例对某些调用方持续报错”的场景，而不是全局性的下游故障。全局故障应该靠连接池上限和上游的限流来兜底。

阈值怎么定，是熔断落地中最容易拍脑袋的一环。连续错误次数太小，比如 1 次，任何偶发失败都会触发驱逐，池子剧烈抖动；太大，比如 50 次，等触发时上游早已被拖垮。可行的做法是先观察基线：在正常流量下统计单位时间的错误分布，把阈值设在“明显偏离基线但不至于被单次抖动触发”的位置，再用故障注入验证驱逐与恢复是否符合预期。这个过程无法省略，因为每个服务的流量特征不同，没有通用数字。

故障注入与流量镜像

故障注入解决的是“演练没有故障”的难题。线上环境一年可能只遇到几次超时和几次 5xx，靠真实事故验证熔断与降级，代价太高；靠单元测试模拟，又验证不了代理层的真实行为。Istio 允许在路由上直接注入延迟与中止，让故障变成可按比例、可随时撤销的配置。

延迟注入用 fault.delay，指定固定延迟与生效比例。它模拟的是“下游变慢”，用来验证上游的超时设置是否合理、线程池会不会被慢请求占满、前端有没有加载态。中止注入用 fault.abort，指定 HTTP 状态码与比例，模拟的是“下游直接报错”，用来验证重试是否按预期触发、熔断是否在阈值后打开、降级文案是否正确。

这段配置的含义是：一成的请求被延迟 5 秒，半成的请求直接返回 503，其余正常转发。比例与时长都是示意值，演练时应从 1% 起步，确认监控无异常后再放大。故障注入发生在路由选定之后、请求转发之前，被注入的请求不会真的打到下游，因此不会污染下游数据，但它会真实占用上游的连接与等待时间，这一点与真实故障一致。

演练前要先想清楚三件事：观察什么指标、什么条件下终止、如何一键撤销。观察指标至少包括错误率、P99 延迟、连接池拒绝数与熔断驱逐数；终止条件可以是错误率超过预设阈值，也可以是业务侧告警；撤销手段最简单的是把注入比例改成 0，或者直接删除这条 VirtualService 规则。没有终止条件的演练不是演练，是事故预演。

流量镜像（mirror）解决的是另一个问题：新版本还没有资格接真实流量，但又想用真实请求验证它。镜像把同一份请求复制一份发给影子服务，主请求照常返回，影子服务的响应被直接丢弃，不影响调用方。

镜像请求会带上 -shadow 后缀的 Host 头，方便影子服务区分来源。它有一个必须提前想清楚的副作用：镜像不是只读的。如果被镜像的接口会写数据库、发消息、调用第三方，影子服务会真的执行这些操作，造成重复写入。因此镜像只适合只读接口，或者影子服务连接独立的影子库、影子队列。把写接口直接镜像到生产同库的新版本，是这类方案最典型的事故。

镜像与灰度的关系也值得说明。镜像不改变主链路的流量分布，新版本收到的请求量等于被镜像的比例，但它的响应不参与判定；灰度则让新版本真正承载一部分用户。合理的顺序是先用镜像验证功能与性能，再用小比例灰度验证真实用户体验，最后全量。两步都省，等于把风险全部压在上线那一刻。

边界：Gateway、ServiceEntry 与 sidecar 拦截

治理规则要生效，请求必须先经过 Envoy。这句话听起来像废话，但它解释了三个边界对象的存在意义。

入口流量从 Gateway 进入。Gateway 描述的是“在网格边缘开哪些端口、监听哪些域名、用什么证书”，它只负责接入与 TLS 终止，真正的路由仍然由 VirtualService 完成。VirtualService 的 gateways 字段把两者绑定：写了 mesh 表示作用于网格内部，写了某个 Gateway 名称表示作用于入口，两个都写则同时生效。只配 Gateway 不配 VirtualService，流量进来后没有路由，表现为 404；只配 VirtualService 不绑 Gateway，外部流量根本进不来，表现为连接被拒。

网格外的服务通过 ServiceEntry 纳入治理。它用 hosts 声明外部域名，用 location 区分网格内外的服务，用 resolution 指定解析方式，再把端口与端点补全。加上 ServiceEntry 之后，针对这个外部依赖的 VirtualService 与 DestinationRule 才能生效，超时、重试、熔断才有落点。没有它，应用访问外部 API 的流量只是一个透传的 TCP 连接，治理层看不见也管不着。

sidecar 注入决定了 Pod 里有没有 Envoy。开启命名空间标签后，新建的 Pod 会多出一个容器与一个初始化容器；初始化容器在 Pod 网络命名空间里写入 iptables 规则，把出站流量重定向到 15001 端口，把入站流量重定向到 15006 端口，同时排除代理自身使用的端口与 UID，避免流量回环。应用对此完全无感，它仍然连接原来的服务地址，只是数据包在中途被截走。

这也解释了几个常见现象。第一，只有被注入的 Pod 才受治理，没注入的 Pod 直连服务，规则对它无效。第二，通过 localhost 或 127.0.0.1 发起的调用不经过出站重定向，绕过治理，这类调用在边车容器与主容器共享网络时尤其容易写错。第三，注入发生在 Pod 创建时，给运行中的 Deployment 打标签不会让已有 Pod 自动获得 sidecar，必须滚动重启。第四，如果集群启用了 CNI 模式，iptables 规则由节点上的代理统一写入，排查时要看的位置与初始化容器模式不同。

生效顺序与冲突排查

治理规则写得越多，越需要一张清晰的“谁先谁后”的地图。一次请求进入 Envoy 后，判定顺序大致如下：先按监听端口与 Gateway 决定用哪组路由配置，再在 VirtualService 中按 host 找到候选规则，然后按 http 数组的书写顺序逐条匹配，首条命中即停止；命中后按 route 的目标确定 subset，最后由 DestinationRule 提供这个 subset 的连接池、异常检测与 TLS 策略。

这条链路里有两个容易出错的地方。其一是 host 的写法。VirtualService 与 DestinationRule 的 host 必须指向同一个服务，短名会按资源所在命名空间补全成完整域名，因此跨命名空间引用时必须写全称，否则两个资源各指各的，看起来都创建成功，实际毫无关联。其二是同一 host 上存在多个 VirtualService 时的合并行为，规则会被合并后统一求值，顺序不应当作为设计依赖；可靠的做法是一个 host 只维护一个 VirtualService，把多条规则写在同一个 http 数组里。

排查配置不生效，有一套固定的顺序，比盲改 YAML 有效得多。先确认控制面是否接受：istioctl analyze 能发现引用不存在的 subset、host 拼写错误、Gateway 未绑定等静态问题。再确认数据面是否同步：istioctl proxy-status 会显示每个代理的配置版本与同步状态，出现 STALE 说明推送没到。最后确认代理里到底有什么：istioctl proxy-config route 与 proxy-config cluster 可以直接导出某个 Pod 的路由表和集群表，配置在不在、权重是多少，一目了然。

还有一类“规则写了但流量不按它走”的原因与端口命名有关。Istio 依据 Service 的端口名判断协议，名字必须以 http、http2、grpc、tcp 等前缀开头，例如 http-web。如果端口名写成 web 或 tcp-web，代理会把流量当成不透明 TCP 处理，所有 HTTP 层的匹配、超时、重试、故障注入统统失效。这类问题不会报错，只会表现为“配置正确但没效果”，是排查时最值得优先检查的一项。

可观测性

流量治理如果缺少观测，就只是把配置写得更复杂。Istio 的 sidecar 天然处在请求路径上，因此能免费产出三类信号：指标、访问日志、追踪，前提是它们要被正确开启和解读。

指标方面，最常用的是 istio_requests_total，它按来源工作负载、目标工作负载、响应码、上报方等维度计数，可以直接算错误率；istio_request_duration_milliseconds 提供延迟分布，用来观察治理规则是否把长尾削平；TCP 场景则有连接打开与关闭的计数。这些指标由代理上报，与业务埋点相互独立，因此即使应用没有埋点，也能看到服务间的真实调用情况。

访问日志默认关闭，需要在网格配置里指定输出路径才会打开。打开后每条请求都会留下来源、目标、耗时、响应码与一个关键字段 response_flags。这个字段是排障的核心：UF 表示上游连接失败，通常指向实例不可达或端口不对；UO 表示连接池溢出，说明并发上限被打满；NR 表示没有匹配到路由，说明 VirtualService 的 host 或匹配条件有问题；UT 表示上游超时。看到 503 时先看这个标志，比逐层加日志快得多。

追踪需要在网格配置里设置采样率与上报地址，并确保应用把请求头里的追踪上下文继续传下去。代理只能保证自己这一段被记录，如果应用在发起下游调用时丢掉了这些头，链路就会断在中间，表现为“只有一段 span”。采样率是成本与覆盖率的权衡，全量采样在高峰期会带来可观的存储开销，通常从较低比例起步，排障时再临时调高。

这三类信号要配合使用。指标告诉你“有问题”，日志告诉你“哪一类问题”，追踪告诉你“问题发生在哪一跳”。只建指标不看日志，会在 503 面前束手无策；只开追踪不做采样控制，会在账单面前束手无策。

常见坑

把前面各节的边角料集中起来，就是治理落地时反复出现的一组问题。它们的共同点是：配置合法、校验通过、上线后才暴露。

重试放大排在第一位。它往往不是某一次改配置造成的，而是每个团队各自“加一点保护”，叠起来变成乘法。治理层的重试应当集中在一处，内层显式关闭，并在变更时检查整条链路的 attempts 乘积，而不是只看自己这一层。

超时层级不一致排在第二位。调用方的治理超时、应用自己的客户端超时、下游服务的处理超时、数据库连接超时，四者如果没有单调递增的关系，就会出现“上游已经放弃、下游还在计算”的浪费，或者“下游刚超时、上游已经重试”的重复执行。合理的顺序是外层略大于内层，并给每一层留出可观测的余量。

熔断阈值拍脑袋排在第三位。连接池上限照抄博客、连续错误次数随手写 5、驱逐时长随手写 30 秒，这类配置在流量平稳时看不出问题，一旦下游抖动，要么完全不触发，要么把池子清空。阈值必须从容量测试与线上基线来，且要随着实例数变化重新校准。

mTLS 与治理混用是第四类。开启严格模式的 PeerAuthentication 后，如果 DestinationRule 的上游 TLS 模式仍被显式设为禁用，或者应用自己又建立了一条明文连接，就会看到大量 503。治理规则与安全策略作用于同一条连接，任何一方假设错误，另一方都会以“连接失败”的形式表现，排查时不要只盯着路由。

最后一类是配置未生效，原因已经被前面几节覆盖：命名空间不对、host 写成短名、subset 未定义、端口未按协议命名、Pod 没有注入 sidecar、代理处于过期状态。它们的共同排查入口是 istioctl analyze 加 proxy-status，先证明配置到了代理，再讨论配置对不对。

小结

Istio 的流量治理可以浓缩成一句话：VirtualService 决定请求去哪，DestinationRule 决定到了之后怎么对待目标。路由匹配按书写顺序首条命中，灰度用权重、蓝绿用整体切换，两者都不要依赖副本数比例。

超时与重试要当成一个整体设计，timeout 覆盖整条请求，attempts 与 perTryTimeout 的乘积不能超过它；重试只放在最外层，且以幂等为前提。熔断由连接池闸门与异常检测剔除共同构成，阈值从容量与基线推导，不能照抄。

治理规则只有在流量经过 Envoy 时才生效，因此 Gateway、ServiceEntry 与 sidecar 注入是三个必须理解的边界；规则写完后用 istioctl analyze、proxy-status、proxy-config 三步确认落地，再用指标、访问日志与追踪验证效果。把故障注入与流量镜像纳入日常演练，比事故后复盘更有价值。
