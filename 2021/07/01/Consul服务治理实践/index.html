Consul 服务治理实践

本文属于《Go 微服务架构》第 15/35 篇
上一篇系列目录下一篇

服务数量一旦过了十几个，把对端地址写进配置文件就开始变成一种负担：上线要改配置，扩容要改配置，某台机器挂了还要有人半夜去删掉那一行。服务发现要解决的就是这件事，让调用方在运行时问一句“谁还活着”，而不是在编译期就知道“应该是谁”。

本文从 Consul 的定位与能力边界讲起，依次梳理 server 与 client 的架构、服务注册的几种方式与健康检查类型、DNS 与 HTTP 两套发现接口、KV 与 watch、ACL 与令牌、多数据中心的复制模型，以及与 Kubernetes 的集成方式，最后落到生产环境的规模、端口、TLS、备份、升级和几个高频踩坑点。配置中心的方案对比不在这里展开，本文只关心 Consul 本身怎么用、用到什么程度就该停手。

定位与能力边界

Consul 是 HashiCorp 用 Go 编写的基础设施治理工具，单个二进制文件同时承担了注册中心、健康检查、键值存储与访问控制的职责。它最初要解决的问题很具体：在没有中心化编排系统的年代，让散落在物理机和虚拟机上的进程能够互相找到对方，并且在对方不健康时尽快停止调用。

从功能上看，Consul 提供五件事：服务注册与发现、健康检查、KV 存储、ACL 权限控制、多数据中心。前四件在一个数据中心内部闭环，第五件决定了它与多数同类产品不在一个层级上——Eureka 需要额外的同步机制才能跨区，而 Consul 把多数据中心做进了协议本身。

但 Consul 并不是万能的。它不负责流量治理，权重路由、熔断、重试这些要么由调用方自己实现，要么交给网关或代理层，本文后面提到的 Connect 也只是提供了服务间加密与身份，不负责这些策略。它也不是配置中心的最佳载体，KV 写入要经过 Raft 复制，不适合承载高频变更的配置，配置模型与推送机制是另一套问题。

与同类产品相比，三者的差别可以概括为一句话：Eureka 只做服务发现，模型是 AP 的，实现简单但一致性弱、功能窄；Nacos 把注册中心与配置中心合在一起，控制台与命名空间的设计更贴近国内使用习惯；Consul 强在一致性与多数据中心，代价是运维复杂度高、需要理解 Raft 与 gossip。选型没有绝对优劣，关键在于你是否真的需要跨机房与强一致的 KV。

架构：server、client 与两层 gossip

集群里的每个节点都运行一个 agent 进程，agent 有两种角色。server 参与 Raft 共识，负责保存集群状态、处理写请求、维护服务目录；client 不持久化状态，只把请求转发给 server，并负责本机服务的注册与健康检查。除 server 外，业务机器上通常只跑 client。

每个数据中心内部有一层 LAN gossip，基于 Serf 实现，负责成员管理与故障检测；各数据中心的 server 之间还有一层 WAN gossip，用来交换跨机房的节点与端口信息。Raft 只在同一数据中心的 server 之间运行，因此一个数据中心的仲裁失败不会直接拖垮另一个，这正是多数据中心模型的基础。

server 的数量应当是奇数：3 台可以容忍 1 台故障，5 台可以容忍 2 台。超过 5 台不会让写性能更好，反而拉长 Raft 的提交延迟，因为每次写都要等多数派确认并落盘。

各端口的分工如下：

端口 用途
8300 server 之间的 RPC，只有 server 需要互通
8301 LAN gossip，TCP 与 UDP 都要放通
8302 WAN gossip，TCP 与 UDP，只有 server 之间
8500 HTTP API 与 Web UI
8600 DNS 接口，TCP 与 UDP
8400 本地 CLI RPC，只监听回环地址

服务注册与健康检查

注册的粒度是“节点上的服务”：一台机器是一个 node，node 上可以挂多个 service，每个 service 用 ID 唯一标识。ID 不填时默认等于服务名，这意味着同一台机器上注册两个同名服务会互相覆盖，做多实例部署时要显式给出 ID。

注册有三条路径。第一条是配置文件，把 service 段写在配置目录里，agent 启动或收到重载信号时读取。这是最稳妥的方式，状态跟着配置文件走，agent 重启不会丢。第二条是 HTTP API，向 /v1/agent/service/register 提交一段 JSON；这种方式注册的信息只存在于 agent 内存中，agent 重启就消失，适合临时调试或由外部编排系统在启动容器后调用。第三条是程序内集成，服务在启动时通过 Consul 的客户端库自己注册、退出时自己注销，把注册与进程生命周期绑在一起，代价是每个服务都要引入依赖。

健康检查由 agent 在本地执行，常见的类型有四种。script 检查执行一段命令，退出码为 0 视为健康、1 视为 warning、其他视为 critical；HTTP 检查对给定地址发 GET，状态码 200 视为健康；TCP 检查只做端口连通性探测；TTL 检查反过来，由服务自己定期调用 /v1/agent/check/pass/<check-id> 续约，超时未续约就转为 critical。四种方式各有盲区：HTTP 检查看不出业务依赖是否可用，TCP 检查只能证明端口在监听，TTL 检查一旦服务进程卡死但没退出，反而会因为心跳线程还在跑而误报健康。

检查结果有三种状态，passing、warning、critical，服务发现默认只返回 passing 的实例。deregister_critical_service_after 值得单独强调：它让一个持续 critical 的服务在超过阈值后被自动从目录中摘除，避免死实例长期占用列表。

服务发现：DNS 与 HTTP

Consul 对外提供两套发现接口，一套是 DNS，一套是 HTTP。DNS 的好处是零侵入，任何语言的老系统都能用，只要把 resolver 指到 agent 的 8600 端口。

DNS 接口默认只返回 passing 实例，结果顺序是打乱的，不保证轮询，也不做加权，真正的选择逻辑留给客户端。这里有个常被忽略的细节：查询名最好带上结尾的点，写成 order-api.service.consul.，否则 resolver 会按 ndots 配置依次拼接搜索域，多发出几次无用的查询，延迟会明显升高。

HTTP 接口更适合需要结构化信息的场景，比如要同时拿到实例的元数据、所在机房和检查详情：

与 DNS 不同，HTTP 的 /v1/health/service 默认会把不健康的实例一起返回，必须显式加 passing=1，这是接入时最容易写错的一处。返回体里每个实例都包含 node、service 与 checks 三段，checks 中保留了最近一次探测的输出，排查“为什么这台机器被判为不健康”时非常有用。

KV 与 watch

KV 是一棵扁平的键树，路径本身承担层级语义，写入时不会自动创建父节点，但按前缀读取时可以一次取回整棵子树：

除了 CAS，KV 还提供 acquire 与 release，配合 session 可以实现带自动过期的分布式锁：session 绑定 TTL 并可以挂健康检查，持有者失联后锁会自动释放。这套原语足够做选主和轻量互斥，但它的每一次写都要走 Raft，把高频计数或队列塞进 KV 是很常见的误用。

关于 watch，需要先纠正一个印象：Consul 没有服务端主动推送。所谓 watch，本质是阻塞查询——请求带上上一次结果的 index 和 wait 时间，服务端在数据变化或超时后才返回，客户端拿到新结果再发起下一轮。

这套机制在 HTTP 接口上工作得很好，但 DNS 接口没有等价能力，只能靠 TTL 缓存被动刷新，这也是后面要讲的 DNS 缓存问题的根源。

ACL 负责把这些接口保护起来。开启 ACL 后必须提供一个 management 级别的引导令牌，再由它创建策略并签发令牌。策略按资源与权限描述，服务注册、KV 前缀、节点读、会话操作各自独立：

令牌分两类：agent 使用的令牌决定它能注册什么、能读哪些节点；服务或应用使用的令牌决定它调用 API 时的权限。ACL 一旦开启，未携带令牌的请求默认被拒绝，包括 DNS 查询，所以灰度开启时务必先用 default_policy = "allow" 观察一段时间，再收紧到 deny。

多数据中心与 Kubernetes 集成

多数据中心的模型很直接：每个机房是一套独立的 Consul 集群，拥有自己的 server 与 Raft 日志，服务目录不做跨机房复制。各机房的 server 通过 WAN gossip 组成一个松散的整体，跨机房查询时，本地 server 把请求转发给目标机房的 server，取回结果后返回给调用方。

由此带来两个推论。其一，写入只发生在本地机房，跨机房没有分布式事务，也就不存在写冲突；其二，跨机房查询是一次额外的网络往返，机房间的延迟会直接叠加在服务发现上，因此能本地解析就不要跨机房解析，跨机房调用应当由专门的网关或就近路由承接。

故障域的划分同样清晰：某个机房的多数派丢失时，该机房无法写入，注册与注销都会失败，但读请求仍可以用 stale 模式从本地状态返回；其他机房不受影响，只是查不到这个机房的新实例。这也是 Consul 比单集群方案更适合多机房的原因——故障被限制在一处。

在 Kubernetes 上，Consul 有两种常见的落地方式。第一种是目录同步，用官方的同步组件把 Service 与 Endpoints 写进 Consul 目录，让集群外的虚拟机服务也能按同样的方式发现 Pod；同步可以是单向的，也可以双向，双向时必须处理命名冲突与删除时序。第二种是 Connect，通过注入 sidecar 为服务间调用提供双向 TLS 与身份校验。Connect 的细节属于服务网格话题，本文只把它当作“Consul 自带的服务间加密方案”来理解，不作为落地的必选项。

生产实践与常见坑

规模上，server 用 3 台或 5 台独立机器，不要与业务混部；client 与业务同机部署，注册与检查都在本地完成。服务数到几千、检查数上万时，先撑不住的往往不是 server，而是 client 的检查并发，需要放宽检查间隔、减少脚本检查。机房边界应当对应数据中心边界，而不是把多个机房塞进一个集群靠标签区分。

安全与运维上有四件事必须做。其一，只放通必要端口，跨机房只开 8300 与 8302，8500 与 8600 限制在内网。其二，开启 TLS，服务端与客户端都校验对端证书，同时校验 server 主机名，证书主题需要匹配 server.<dc>.<domain> 的命名约定；DNS 接口本身没有加密能力，只能靠网络边界保护。其三，定期用 snapshot 做快照并异地留存，快照包含目录与 KV，恢复时要求集群处于健康的多数派状态。其四，升级逐台滚动，先升 server 并保证多数派始终在线，观察 Raft 日志稳定后再继续，client 最后升。

实际的故障大多来自下面几类：

  • 健康检查误判：检查地址写成 127.0.0.1 而服务只监听内网地址，探测永远失败；检查超时短于接口的 P99，业务高峰期实例被批量判死；脚本检查依赖的命令在精简镜像里不存在，所有实例同时转 critical。
  • 服务注销：通过 API 注册的服务在 agent 重启后消失，流量被摘走一半却没人发现；进程被强杀时来不及注销，留下幽灵实例，需要靠 deregister_critical_service_after 兜底。
  • DNS 缓存：Consul 返回的 TTL 很短，但客户端的 stub resolver 或运行时自带的缓存未必遵守，负缓存还会把一次解析失败记住几十秒；实例数频繁变化时，DNS 的抖动比 HTTP 接口明显得多。
  • 跨数据中心延迟：每次跨机房解析都要多一次 server 之间的往返，故障时超时还会放大，跨机房调用应当走就近入口而不是直接解析远端地址。
  • KV 滥用：把大对象、高频计数甚至消息塞进 KV，写入全部经过 Raft，既拖慢注册写入，也让快照体积失控。KV 适合放少量、低频、需要一致读的数据，并且从一开始就约定前缀规范。

小结

Consul 的价值在于用一个二进制把服务发现、健康检查、KV 与多数据中心串了起来，代价是需要理解 Raft 的多数派、gossip 的两层结构与一致性的取舍。落地时优先用配置文件注册，把健康检查设计成能反映真实可用性的探测。多数据中心是它最强的部分，也是最容易被误用的部分，跨机房查询的延迟要提前算进容量。KV 只放低频一致数据，ACL 从第一天就规划好令牌，快照、TLS 与滚动升级一个都不能省。
