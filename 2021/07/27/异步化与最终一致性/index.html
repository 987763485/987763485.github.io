异步化与最终一致性

把一次下单拆成「写订单库」和「发消息通知库存、积分、风控」之后，接口的响应时间确实降下来了，但问题也从性能转移到了状态：用户看到的「处理中」要停留多久，消息发送失败由谁补，重复消费会不会多扣一次积分。本文讨论的正是这条从同步调用走向异步协作的路径，包括异步边界的判断、outbox 模式、幂等消费、重试与死信、对账，以及最终一致性对业务承诺的影响。

本文面向已经写过业务代码、正准备把核心链路改造成消息驱动，或者正在为「数据偶尔不一致」写工单的后端工程师。读完之后，你应该能判断一条链路能不能异步、该怎么保证业务落库与消息发出不脱节，以及如何用对账和可观测性把最终一致性变成一个可运维的工程问题，而不是一句口头承诺。

哪些链路适合异步化

同步调用的耗时等于所有下游耗时的累加，任何一个下游抖动都会沿调用链放大，重试还会把放大倍数再乘一遍。异步化把「请求内必须完成的工作」缩到最小，其余交给消息通道，代价是把确定性换成时效性，把调用栈换成状态机。因此在动手之前，先判断链路是否具备三个前提。

前提一：不在用户等待的关键路径上

第一类适合异步的是非核心链路。下单主流程必须确认订单已创建、金额已锁定，否则用户不知道自己的操作是否成功；而发短信、加积分、写行为日志、推送站内信，这些动作失败并不影响交易成立。判断方法很简单：问一句「这一步失败，用户是否必须立刻知道并且重来」。答案为否，才有异步的资格。

需要注意「非核心」不等于「不重要」。积分少发一样会投诉，只是发生在几分钟之后。异步化降低的是同步失败对主流程的影响，并没有消除这项工作的正确性要求，把非核心链路当成可以随便丢的链路，是改造中最常见的第一个误解。

前提二：结果可补偿、可重放

第二类适合异步的是结果可补偿的业务。库存扣减可以通过反向操作归还，优惠券可以退回，积分可以冲正，这些动作都具备「再执行一次」或「反向执行一次」的能力。反之，发短信、发推送这类外部副作用几乎没有补偿手段：短信已经到达用户手机，你无法把它收回。对于不可补偿的动作，异步化必须配合「只发一次」的去重语义，或者干脆保持在同步链路里，用失败即报错的方式处理。

判断补偿成本要看远一点。有些操作表面可补偿，实际会留下痕迹：发票已提交税务系统，冲红要走另一套流程；面单已打印，作废需人工介入。这类动作更适合留在同步链路做前置校验。

前提三：业务能容忍延迟

第三类适合异步的是对时效不敏感的场景。消息通知延迟几秒无人在意，搜索索引延迟一分钟可以接受，报表数据延迟一小时更是常态。反过来，风控决策、库存预占、余额校验这类需要「当前这一刻的准确值」的判断，不能在异步链路上做，因为消息到达时世界已经变了。

延迟容忍度应当写成一个明确的数字。库存同步允许滞后 3 秒还是 30 秒，决定了消费端的并发度、重试策略与告警阈值。说不出这个数字，说明业务还没想清楚一致性要求，此时贸然异步化，后面一定会以「数据不对」的形式返工。

一个补充场景：流量削峰

除了上面三类，还有一类场景常被忽略：流量削峰。秒杀瞬间请求量远超平峰，同步直连数据库必然打满连接池。把请求先写入队列，消费端按数据库能承受的速率拉取，用排队时间换取系统不崩。但它把「排队中」暴露给了用户，必须配合状态展示与超时兜底，否则用户会重复提交，制造更大的流量。

同步改异步后的语义变化

很多改造出问题，不是因为技术选错了，而是改造者默认「接口行为不变，只是变快了」。同步调用与异步协作有三处语义差异：返回值不再代表结果、超时不再代表失败、重试不再是调用方的自由。这三处没有体现在接口契约和状态模型里，前端、测试与运维就会按旧语义理解系统。

返回值从结果变成受理凭证

同步接口返回 200，意味着订单已经落库，用户刷新页面就能看到。改成异步之后，接口返回 200 只意味着「受理成功」，真正的工作可能还在队列里排队。这是一种契约降级，必须显式表达，通常有两种做法。

第一种是返回 202 Accepted，并在响应体中给出业务流水号和查询地址。202 的语义是「已接受处理，结果另行通知」，但也要求调用方改变习惯：不能拿到 202 就查订单，而要按流水号轮询或等待回调。第二种是同步完成主记录落库，只在响应体里标注子流程状态，例如「已创建、权益发放中」。它对前端更友好，代价是主记录多出一个中间态要维护。

两种做法都要求一件事：中间态必须有明确的出口。订单不能永远停在「权益发放中」，要么在消费成功后流转到「已完成」，要么在超时后流转到「已完成（权益待补）」并进入补偿队列。缺少出口，中间态就会变成僵尸状态。

超时不再等于失败

在同步链路里，调用超时基本可以认定为失败，调用方重试是合理的。在异步链路里，超时只说明「这一段时间内没等到结果」，消息可能还在队列里，也可能已经消费成功只是回执丢了。如果调用方按旧习惯重试，就会制造出重复请求。因此异步接口必须回答一个问题：同一个业务请求重复提交时，系统如何识别。

标准答案是由调用方生成幂等键，服务端在受理层去重。幂等键应来自业务语义，例如「用户 ID + 业务类型 + 客户端请求号」，而不是时间戳或随机数。收到重复请求时，返回第一次受理的流水号与当前状态，而不是新建记录。没有这一步，后面的消息去重、对账修复都缺少稳定的业务主键。

推送与轮询也属于这一层：轮询简单但间隔难调，推送实时但要维护回调并处理丢失，常见折中是短轮询加低频兜底。

重试的责任发生转移

同步调用里，重试是调用方的选择，重试几次、间隔多久由调用方决定。异步协作里，重试的责任转移到消息通道和消费端，调用方只提交一次。这带来两个直接后果：一是消费端必须能承受重复投递，二是重试节奏必须由服务端控制，否则所有调用方在同一时刻重试，会把下游打成雪崩。

事件驱动与消息队列

异步化的载体是消息，但把「调用」直接改成「发消息」，往往会把原本清晰的接口契约变成一堆含义模糊的字符串。原因在于，调用是点对点的命令，消息是广播式的事实。设计消息时首先要分清这两者，再决定用哪一类中间件、配置哪一档投递语义。

事件是事实，命令是请求

命令消息（command）表达「请做某件事」，通常只有一个消费者，语义上接近一次远程调用，例如「扣减库存」。事件消息（event）表达「某件事已经发生」，可以有零个或多个消费者，发布者不关心谁来消费，例如「订单已支付」。两者的可靠性要求不同：命令丢了，业务就断了，必须有明确的失败反馈；事件丢了，通常只是某个下游的视图没更新，可以由对账修复。

混用会带来麻烦。把「扣减库存」做成事件广播给三个消费者，三个服务都会去扣库存；把「订单已支付」做成命令只发给积分服务，以后新增的风控与数据团队就无处订阅。本文的建议是：跨服务、多下游的广播用事件，点对点、有明确责任人的动作用命令，并在消息头里显式区分类型。

一条合格的事件消息至少应包含：全局唯一的事件 ID（消费端去重用）、事件类型与版本号（兼容升级）、聚合根 ID（分区与顺序）、发生时间、业务流水号与链路追踪 ID。缺少事件 ID，消费端只能靠业务字段拼凑去重键；缺少版本号，事件结构一改，老消费者就会解析失败。

中间件选型与投递语义

选型的第一步是问清楚需要的投递语义。Kafka 在 0.11 之后提供了幂等生产者与事务能力，但消费端默认仍是至少一次（at-least-once）：位点提交在消费之后，进程在两者之间崩溃就会重复消费。所谓「精确一次」依赖事务与读已提交隔离，代价是吞吐下降，实际业务里更常见的做法是接受至少一次投递，用消费端幂等把重复吃掉。

Kafka 2.8 的幂等生产者通过 enable.idempotence=true 打开，配合 acks=all、retries 大于零、max.in.flight.requests.per.connection 不超过 5 才能生效，解决的是生产者重试造成的重复写入与乱序。副本层面还需要 min.insync.replicas 至少为 2，否则 acks=all 退化为只写主副本，主副本一挂消息就丢。2.8 同时把 KRaft 模式作为预览提供，去 ZooKeeper 的正式版本仍在路线图上。

RabbitMQ 的优势在路由：交换机类型丰富，死信交换机与 TTL 队列可以组合出延迟重试，适合命令型场景。Redis 6.2 的 Stream 提供消费组与待确认列表，适合已有 Redis、消息量不大、希望少引入组件的团队，但持久化与堆积能力不能与专门的队列相比。关键是别用轻量方案承载核心交易。

本地消息表与事务消息

回到那个绕不开的问题：业务数据写入数据库和消息发送，如何保证「要么都成功，要么都失败」。数据库事务管不到消息中间件，消息中间件也管不到数据库，两套系统之间没有分布式事务的默认能力。工程上有两条成熟路线：在本地事务里顺便记录一条待发消息，或者使用消息中间件自带的事务消息。

本地消息表：把消息写进同一个事务

本地消息表（outbox）的思路非常朴素：在业务库里建一张消息表，业务数据与消息记录在同一个本地事务中提交。事务成功，消息一定被记录；事务回滚，消息记录也一起消失。之后由一个独立的投递进程扫描未发送的记录，发到消息队列，成功后再把记录标记为已发送。

建表时有几个细节值得强调。event_id 上的唯一索引既供消费端去重，也防止业务代码重复插入；aggregate_id 单独成列，是因为投递时要用它做分区键，若等到发送时才从 JSON 解析，既慢又容易因格式变化出错；(status, next_retry_at) 的联合索引决定扫描效率，扫描语句必须能走索引，否则消息表一大就会拖慢整个库。

投递进程有两种实现。轮询方式用 SELECT ... WHERE status = 0 AND next_retry_at <= NOW() ORDER BY id LIMIT 200 FOR UPDATE SKIP LOCKED 取一批，发完批量更新状态；MySQL 8.0 支持 SKIP LOCKED，多实例并行扫描不会互相阻塞。CDC 方式用 Debezium 订阅 binlog，把 outbox 的插入事件直接转成消息，业务代码不用写投递逻辑，代价是多一套 CDC 组件的运维成本。

代码注释里那行「会导致重复发送」是 outbox 的核心认知：它保证「不丢」，不保证「不重」。投递成功后、标记状态前崩溃，下一轮扫描会再发一次，这个窗口无法用本地事务消除，只能交给消费端幂等。任何声称不丢不重且不要求消费端配合的方案，都值得怀疑。

事务消息：把确认交给中间件

RocketMQ 的事务消息是另一条路线。生产者先发一条对消费者不可见的「半消息」，中间件持久化成功后返回确认，生产者再执行本地事务，根据结果向中间件提交或回滚。如果生产者在执行本地事务后崩溃，中间件会定时回查生产者的本地事务状态，由生产者根据业务表判断该提交还是回滚。

事务消息把「消息可见性」交给了中间件，减少了自己写投递进程的工作量，但回查逻辑必须幂等且只读，业务也被绑定在同一个中间件生态里。本地消息表则完全在业务库内闭环，代价是自行维护投递与清理。两者都不解决消费端重复，这一点在下一节展开。

消费端幂等与去重

在至少一次投递的前提下，重复是常态而非异常：生产者重试会重、投递进程崩溃会重、消费者处理完但位点未提交也会重。因此消费逻辑的第一条设计原则是「重复执行不改变结果」，而不是「想办法不重复」。

去重键的选择

去重的最外层是消息 ID。用事件 ID 建一张消费记录表，与业务写入放在同一个本地事务里，主键冲突即说明处理过，直接提交位点跳过。这张表需要定期清理，通常只保留最近若干天的记录，因为重复窗口远小于业务生命周期，保留过久只会让表无限膨胀。

但消息 ID 只能挡住「同一条消息重复投递」，挡不住「同一业务事实被两条不同消息表达」。例如订单服务因重试生成了两条事件 ID 不同、内容相同的支付成功事件，消费端按事件 ID 去重就会加两次积分。此时必须引入业务去重键，例如「订单号 + 权益类型」，并在业务表上建唯一索引。唯一索引是最后一道防线，它把并发下的重复写入交给数据库裁决。

位点提交与重复窗口

消费端还有一个容易忽视的选择：先处理业务再提交位点，还是先提交位点再处理业务。前者在崩溃时最多重复处理，后者在崩溃时会丢消息。在至少一次语义下，正确顺序永远是先处理、后提交，然后用幂等消化重复。任何为了「避免重复」而提前提交位点的做法，本质上都把语义降级成了至多一次。

重试、死信与人工补偿

异步链路一定会遇到「这条消息怎么都处理不成功」的情况：下游接口持续报错、数据本身非法、依赖的服务已经下线。此时无休止重试只会拖垮消费组，直接丢弃又会让数据永久缺失。工程上的答案是分层处理：可恢复的错误退避重试，不可恢复的错误进死信，死信再由人工或脚本处置。

退避重试与重试上限

重试必须带退避，且要有上限。固定间隔重试会让故障下游在恢复瞬间遭遇同等强度的洪峰，指数退避加随机抖动可以把压力摊平。Kafka 没有延迟队列，常见做法是把失败消息投递到分级重试主题，每个主题对应不同延迟，由独立消费者延时拉取；RabbitMQ 可以用 TTL 队列加死信交换机达到同样效果。

重试次数要与业务时效挂钩。一条库存扣减消息重试两小时才成功，订单可能早已超时关闭，此时「成功」反而制造新的不一致。因此重试策略要包含截止时间，超过时效的消息转入死信并触发人工处理。

死信不是垃圾桶

死信队列的价值不在于存放失败消息，而在于让失败可见、可查、可重放。一条消息进入死信时，至少要保留原始消息体、失败原因、重试次数、首次与最后失败时间。缺少这些信息，值班同学面对一堆消息体只能靠猜。

人工补偿的入口应当做成工具而不是脚本。值班同学按业务流水号查询死信，看到失败原因后选择重放、修正后重放或标记忽略，每次操作都留审计记录。忽略也是合法处置：业务已取消的消息强行重放只会制造脏数据。关键是「忽略」必须被记录，否则对账时无法解释差异来源。

重试还要防住重试风暴：失败后无间隔重试、多个消费者争抢同一个重试主题、下游恢复后积压消息全量重放，这三点都会把小故障放大成雪崩，分别靠退避、独立重试主题与重放限速解决。

对账：把不一致找出来

前面所有机制都在「尽量不发生不一致」，对账解决的是「已经发生了怎么办」。它是最终一致性的最后一道闸门，也是唯一能给出确定性结论的手段：不依赖消息是否送达，只依赖两份持久化数据是否吻合。

对账分两层。总量对账按日或按小时比较两侧的笔数与金额合计，只要差额不为零就值得追查；它成本低、覆盖全，但说不出差异在哪。明细对账按业务流水号逐条比对，找出缺失、重复与金额不符的记录，成本高，通常只对差异区间或高风险业务开启。

差异修复必须走补偿接口，而不是直接改库。直接改库绕过业务校验与流水记录，下一次对账仍然对不上，也没人能解释数据是谁改的。补偿接口要幂等，修复后重跑对账确认收敛。差异原因也要归档：是消息丢失、消费失败未重试，还是上游根本没落库，归因清楚才知道该修哪一层。

消息顺序与分区键

Kafka 只保证分区内有序，跨分区不保证。因此「同一订单的事件必须有序」这件事，只能靠分区键来落实：以订单号或用户 ID 作为 key，同一聚合根的事件就会落到同一分区，被同一个消费者按序处理。用随机 key 或轮询发送，等于主动放弃顺序。

调整分区数会打破这个前提：同一个 key 的哈希落点改变，改分区前后的积压消息可能被不同消费者并发处理。因此分区数应在建主题时按峰值吞吐规划好，确需扩容时先停止生产、消费完积压再切换。

即使分区有序，消费端的并发也会打乱顺序：一个分区被多个线程并行处理，后到的消息可能先完成。解决办法是分区内串行、分区间并行，或者在业务层用版本号防御，让状态机拒绝「旧状态覆盖新状态」。后者更稳妥，它同时防住了重试与跨系统乱序。

一致性窗口与读己之写

最终一致性必须给出时间承诺，否则只是一句「迟早会好」。这个承诺应写成可验证的窗口：多少秒内完成，超时后进入什么状态，用户看到什么提示。假设业务承诺 5 秒内权益到账，消费端处理能力、重试间隔与告警阈值都要围绕这个数字设计，超过窗口仍未完成的事件应单独统计。

窗口一旦确定，就要接受它带来的体验问题，最典型的是读己之写：用户刚提交订单就跳转详情页，而详情页读的是从库或搜索索引，数据还没同步，于是显示「订单不存在」。这不是 bug，而是读写路径不一致的必然结果。

常见的三种解法各有权衡：读写都走主库最简单，但把读压力全压回主库；会话粘滞让同一用户的读落到同一副本，成本低但延迟仍在；携带令牌最严谨，写操作返回版本或位点，读请求带上它，服务端发现视图未追上就等待或回源。产品层面还有一招：写入成功后先用本地数据渲染，待服务端确认后再覆盖，用户感知到的是「立刻可见」。

可观测性与常见坑

异步链路出问题时，日志往往帮不上忙，因为故障表现是「少了一条数据」而不是「报了一个错」。可观测性要围绕消息生命周期建设：生产与消费速率、积压量（lag）、端到端延迟分位数、重试次数分布、死信数量、人工补偿成功率，以及 outbox 表待发送条数。积压告警要用「持续增长」而非瞬时值，否则每次发布重启都会误报。

常见坑可以列成一张自查表。先发消息后落库，事务回滚后消息已经发出，下游凭空多出一笔；消费者没有幂等，重试一次就多扣一次；重试没有退避与上限，故障期间把下游打死；生产者用异步发送却不检查回调，消息在缓冲区里丢失而业务毫不知情；分区键选错或中途扩容，顺序错乱导致状态回退；outbox 表只写不清理，几个月后拖慢整个库；消费端捕获异常后仍然提交位点，失败被静默吞掉。

这些坑的共同点是「本地测试全部通过」，它们只在并发、崩溃、网络抖动这些非正常路径上出现。因此异步链路的测试重点不在正常流程，而在故障注入：杀掉投递进程、让下游返回 500、重复投递同一条消息、把消费位点回拨，观察系统是否仍能收敛到一致状态。

小结

异步化不是把调用换成消息，而是把一次确定性的事务拆成多个可观测、可重试、可补偿的步骤。判断一条链路能否异步，看它是否不在用户等待路径上、是否可补偿、是否有明确的延迟上限；三者缺一，就留在同步链路里。

落地时有三个不可省略的部件：用本地消息表或事务消息保证落库与发消息不脱节；用业务去重键与唯一索引让重复投递不产生副作用；用对账与补偿给不一致兜底。三者合起来，才构成可对外承诺时间窗口的最终一致系统。

最后，把一致性当成可运维指标而不是口号：积压、延迟、死信、补偿成功率都要有面板和告警，故障注入要进入日常测试。
