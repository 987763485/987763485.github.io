TypeScript 大型项目类型治理

本文属于《TypeScript 学习路线》第 35/74 篇
上一篇系列目录下一篇

一个几十万行的 TypeScript 仓库，最容易被误判为“类型写得好”。真正决定体验的并不是类型写得多精巧，而是类型系统在长期协作中是否仍然可控：新同学能否在十分钟内找到某个领域对象的定义，改动一个接口后编译器能否准确指出受影响的模块，以及一次全量构建究竟要等多久。

本文讨论的是治理而非技巧。它关注工程结构、类型边界、严格模式的落地节奏、断言与 any 的收敛、第三方声明的维护，以及如何用编译器的诊断输出定位性能瓶颈。工具类型的写法留给专门的文章，本文只谈如何让一个已经庞大的项目重新变得可预测。

类型失控的四种表现

类型问题很少以“报错”的形式出现，更多时候它表现为团队对编译器的集体不信任。当开发者习惯性地说“这里类型不对，加个 any 就好了”，类型系统就已经从资产变成了负债。

第一种是编译变慢。全量 tsc 的耗时逐月上涨，开发者于是绕开类型检查，改用 ts-node、esbuild 或干脆跳过 tsc 直接跑测试。检查一旦不在关键路径上，类型错误就会积压，积压又反过来让下一次全量检查更慢，形成闭环。

第二种是循环依赖。类型层面的循环引用不会让运行时崩溃，但会让类型推断退化为 any，也会让模块拆分的边界失效。import 一个类型却意外引入了整个模块的副作用，是大型项目里最常见的隐性耦合。

第三种是 any 扩散。一个函数参数被标成 any，它的返回值、调用方的回调参数、下游的解构变量都会跟着失去类型。any 具有传染性，而且传染过程没有任何告警。

第四种是类型与运行时不一致。接口声明字段必填，后端实际可能返回 null；类型写着枚举只有三个值，服务端已经悄悄加了第四个。这类问题编译器无法发现，只能靠边界处的运行时校验补上。

flowchart TD
  A[编译变慢] --> B[绕过类型检查]
  B --> C[any 扩散]
  C --> D[类型与运行时偏离]
  D --> E[重构成本上升]
  E --> A

这张图说明治理不能只挑一个点下手。只清理 any 而不解决编译速度，清理成果很快会被重新填满；只做增量编译而不划定类型边界，编译再快也挡不住跨层引用带来的连锁修改。

编译单元：Project References 与增量编译

大型项目的第一刀应该切在编译单元上。TypeScript 3.0 引入的 Project References 允许把一个仓库拆成若干子项目，每个子项目有自己的 tsconfig.json 和输出目录，根配置只负责引用它们，不包含任何源文件。

composite 会强制开启声明文件输出，并记录每个文件的签名摘要到 .tsbuildinfo。之后用 tsc -b 代替 tsc，构建工具会按引用关系拓扑排序，只重新编译签名发生变化的项目及其下游。编辑器打开 apps/web 时，也不会把整个仓库塞进同一个 program。

这里有一个必须提前说明的坑。路径别名会把 @acme/core 直接解析到源码文件，而不是引用项目产出的声明文件，于是同一个文件可能同时属于两个 program，报出“文件不在项目文件列表中”的错误。解决办法是让别名指向构建产物，或在引用方开启 disableSourceOfProjectReferenceRedirect。

路径别名的收益与代价

路径别名解决的是可读性问题。../../../domain/user 这样的相对路径在重构时极易断裂，改成 @/domain/user 之后，移动文件只需要改一处映射。TypeScript 4.1 之后 paths 可以脱离 baseUrl 单独使用，这让配置的副作用小了一些。

代价有三个。其一，tsc 只做类型检查，不会改写输出中的模块路径，运行时必须由打包器或 tsconfig-paths 之类的加载器补齐，测试与构建的解析方式一旦不一致，就会出现“编译通过、运行报错”。其二，baseUrl 指向仓库根时，任何裸模块名都可能被解析到 src 下，漏装依赖也能编译通过，问题被推迟到线上。其三，别名让跨包引用变得毫无阻力，边界因此更容易被突破。

笔者的建议是：应用层保留一到两个别名前缀，库包内部坚持相对路径或包名自引用；baseUrl 不要指向仓库根，能省略就省略；别名规则与打包器配置由同一份配置生成，避免两处漂移。

类型边界：领域类型、DTO 与公共类型包

工程结构解决的是“编得动”，类型边界解决的是“改得动”。判断边界是否清晰有一个简单标准：删除任意一个模块，受影响的文件是否集中在它的下游，而不是散落在半个仓库。

推荐的层次是界面、应用、领域、基础设施。领域层只描述业务概念，不依赖框架与传输格式；DTO 描述接口报文，只出现在应用层与基础设施层的交界处；两者之间用显式的映射函数转换，而不是让领域对象直接承担序列化职责。

flowchart TD
  UI[界面层] --> APP[应用层]
  APP --> DOMAIN[领域层]
  APP --> DTO[DTO 与校验]
  DTO --> INFRA[基础设施层]
  DOMAIN -. 不依赖 .-> INFRA

映射代码看起来啰嗦，却是类型与运行时一致性的落点。后端把某个字段改成可空，编译器只会在映射函数里报错，而不会让空值一路漂到界面。金额、时间、标识符这类值对象也在边界处校验，后续代码便可信任类型声明。

跨包共享的类型放进独立的公共类型包，例如 @acme/types。这个包只包含类型与常量枚举，编译产物只有声明文件，不引入运行时依赖，消费方统一用 import type 引入，确保它不会进入打包结果。公共类型包必须独立发版，任何字段变更都按语义化版本处理，禁止用本地路径直接引用源码。

strict 的渐进开启与例外管理

strict 是一组开关，不是不可分割的整体。老项目直接打开它，往往会得到成千上万条错误，团队的第一反应是关掉，此后再也打不开。可行的路径是按编译选项逐个开启，每开一个，修完，稳定两周，再开下一个。

顺序上先易后难：noImplicitAny 通常早已开启；strictFunctionTypes 与 strictBindCallApply 的报错集中在回调与工具函数，改动量可控；strictPropertyInitialization 会逼出类字段的初始化问题；strictNullChecks 改动面最大，应放在最后，并且按目录推进。

按目录推进依赖多个 tsconfig：根配置继承一份基础配置，新目录直接 strict: true，老目录先维持宽松，修完一个就把该目录的 include 移进严格配置。这样严格范围只增不减，也不会出现“改了一半又退回去”的反复。

例外必须有账可查。允许在迁移期使用 // @ts-expect-error，但必须写清原因与跟踪单号；禁止无说明的 @ts-ignore，因为它会在错误消失后继续沉默。例外数量应当作为技术债指标进入周报，只允许下降。

any、unknown、never 与断言的治理

三者不是难度递进关系，而是职责不同。any 表示放弃检查，并把这个放弃传递给所有接触它的表达式；unknown 表示“值存在但未知”，使用前必须收窄；never 表示不可能发生的分支，用来让编译器验证穷尽性。

规范可以写得很短。外部输入一律先落到 unknown，经过类型守卫或 schema 校验后再进入业务代码；业务代码中禁止新增 any，确实需要过渡的，写成 any 并附注释与清理期限；catch 的参数默认是 any，应显式标注为 unknown 后再收窄，否则一个拼写错误就能骗过编译器。

assertNever 的价值在于：以后给 Status 加成员，编译期就会在这一行报错，而不是等到线上出现空白标签。

类型断言则应被视为“向编译器作证”。as const 是无害的收窄，可以放心使用；as SomeType 只在确实掌握编译器不知道的信息时使用，例如刚完成校验的响应体；as unknown as T 的双重断言基本等同于 any，评审时应当直接拦下。@ts-expect-error 会在错误消失后自行报错，提醒开发者删掉这行豁免。

声明文件、类型测试与 lint 分工

第三方类型有三条来源，优先级依次是：包自带的声明、DefinitelyTyped 上的 @types 包、团队维护的本地声明。前两者用 npm install -D @types/foo 安装，版本要与运行库的主版本对齐，@types/node 还应匹配实际运行的 Node 版本。

确实没有类型时，在仓库的 types/ 目录写一个最小声明，并通过 typeRoots 或 paths 纳入编译，而不是在业务文件里随手 declare module "foo"。模块扩充要落在独立的 .d.ts 中，用接口合并补充字段：

最需要警惕的是 declare module "*" 这类通配声明，它等于给所有未知模块发放 any 通行证，短期省事，长期让整个依赖树失去检查。

类型测试的定位要分清。tsd 适合库与公共类型包，用 expectType 与 expectError 把“类型应当是什么”写成断言，随单测一起跑；DefinitelyTyped 的传统工具是 dtslint，规则更严，适合贡献上游。业务应用用 tsc --noEmit 加少量断言即可。lint 则负责守住风格与高危写法：no-explicit-any 拦截新增的逃逸，consistent-type-imports 保证类型导入不被误打成运行时依赖，no-floating-promises 找出忘记处理的 Promise。后者需要开启 type-aware 模式，也就是在 parserOptions.project 中指向 tsconfig，代价是 lint 变慢，建议只在 CI 与改动文件上运行。

编译性能分析与版本升级

类型层面的性能问题几乎都能从诊断输出里读出来。先跑一次不带增量缓存的检查，观察各个阶段的耗时：

--extendedDiagnostics 有几项指标值得长期跟踪：Check time 反映类型检查耗时，Instantiations 反映泛型与条件类型的展开次数，Types 与 Symbols 反映类型图规模，I/O Read time 与 Memory used 则能暴露声明文件过多的问题。Instantiations 异常增长通常意味着某个泛型在深层嵌套结构上被反复推导，顺着 --generateTrace 的产物能找到具体文件。

常见成因有四类：入口文件通过 export * 把整棵依赖树拉进同一个 program；全局 .d.ts 声明过多，每个文件都要重新加载；条件类型在大型联合类型上递归展开；skipLibCheck 被关闭导致所有依赖声明都参与检查。对应手段是缩小 program、收敛全局声明、给递归类型加上限，日常构建打开 skipLibCheck，升级时再临时关闭以定位冲突。

版本升级应当被当作一次小型迁移。把 typescript 固定在 package.json 中，不写范围符；一次只升一个小版本，先读发布说明里的破坏性变更；升级分支上先跑全量 tsc --noEmit，再跑 lint 与单测。要注意 lint 生态的滞后：typescript-eslint 对新版编译器的支持通常晚于官方发布，编译器升得太快，lint 可能直接无法解析。升级前后各存一份诊断输出做对比，既能发现性能回归，也能确认类型图没有膨胀。

团队协作与评审清单

治理最终要落到流程上，以下几条适合直接写进合并请求模板。

第一，新增依赖必须说明类型来源：自带声明、@types 包，还是需要自建声明。没有类型来源的依赖不接受合入。

第二，禁止新增无说明的 any、@ts-ignore 与双重断言。确有需要时，在评审中说明原因、影响范围与移除计划。

第三，公共类型包的字段变更必须伴随版本号变更，并在变更说明里列出受影响的消费方。

第四，拒绝跨层引用：被引用模块的路径里不应出现不属于当前层的目录名。

第五，涉及外部数据的代码必须展示运行时校验，类型声明不能替代校验。

把这些条目与 CI 中的 tsc --noEmit、lint、类型测试串起来，治理才具备可持续性。工具负责守住底线，评审负责解释例外，两者缺一不可。

小结

类型治理的目标不是让类型更复杂，而是让改动的影响范围可以被预测。本文从四种失控表现出发，给出几条可独立落地的线索：用 Project References 切小编译单元，用别名提升可读性但控制其副作用，用领域类型、DTO 与公共类型包划清边界，按编译选项渐进开启 strict 并登记例外。

在写法层面，unknown 优先于 any，never 用于穷尽检查，断言与 @ts-expect-error 必须带理由；第三方类型优先走官方声明与 DefinitelyTyped，本地声明保持最小。最后用 --extendedDiagnostics 定期体检，把版本升级当作迁移来做，并用评审清单把规范固定下来。治理没有终点，但每一次收敛都会让下一次重构便宜一点。
