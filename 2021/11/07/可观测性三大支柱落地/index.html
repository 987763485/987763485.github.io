可观测性三大支柱落地

本文属于《Docker 与 Kubernetes》第 39/51 篇
上一篇系列目录下一篇

很多团队并不缺监控数据，缺的是把数据串起来的能力：指标告诉你“出了问题”，日志告诉你“错在哪一行”，追踪告诉你“慢在哪个调用”，可三套系统各自为政，排障仍然靠人肉拼接时间戳和请求 ID。本文从数据模型出发，讨论 Metrics、Logs、Traces 三者的结构差异、关联手段、采样与存储成本，以及一整套从告警到定位的落地流程，重点放在那些真正会决定平台能否长期用下去的工程约束上。

文中涉及 OpenTelemetry 的具体接入代码请回看第 690 篇，告警规则的治理与降噪留给第 712 篇，微服务建设总览在第 693 篇。本文假设你已经有一套能跑起来的采集链路，讨论的是如何让这三类数据在成本可控的前提下互相印证，而不是再搭一套演示环境。

从三条平行数据到一条证据链

三类信号回答的是不同问题。Metrics 适合回答“是否异常、影响多大”，它便宜、连续、易于告警；Logs 适合回答“具体发生了什么”，信息密度高但体积大；Traces 适合回答“慢在哪一段、错在哪个依赖”，它把一次请求拆成有父子关系的 span。只靠其中任何一种，排障时都会留下盲区：只有指标，你知道错误率涨了却不知道哪类请求；只有日志，你能看到异常堆栈却拼不出完整调用链；只有追踪，你能看到慢在数据库，却不知道数据库当时在报什么错。

从数据模型看，三者的差异直接决定了成本结构。Metrics 是预先聚合的数值，存储量取决于活跃时间序列的数量，与请求量只有间接关系；Logs 是离散的文本记录，成本主要来自写入字节数和被索引的字段；Traces 是结构化的事件树，成本约等于请求量乘以采样率再乘以单条 trace 的 span 数。这个差别意味着，不能用一套“全量采集”的思路对待三种信号，否则不是指标被高基数拖垮，就是日志账单失控。

落地中最常见的失败也不是工具选错，而是三套系统彼此孤立：服务名写法不一致、时间戳时区不同、日志里没有 trace id、指标标签和追踪资源属性对不上。平时看不出问题，故障时才发现无法从告警跳到具体请求。本文按数据模型、信号关联、采样与成本的顺序展开。

Metrics：时间序列、标签与基数

一条时间序列由什么唯一确定

指标系统里最小的存储单位是样本，即一个时间戳加一个数值。样本按时间排列成时间序列，而一条时间序列由指标名和一组标签唯一确定。例如 http_requests_total{service="order", method="POST", status="500"} 与 status="200" 是两条完全不同的序列。理解这一点很重要：标签不是“附加信息”，它参与定义序列的身份，也就直接决定了存储与查询的成本。

四类指标类型需要区分使用。Counter 只增不减，适合请求数、错误数、字节数；Gauge 可增可减，适合队列长度、连接数、内存占用；Histogram 在客户端按桶累计，适合延迟与响应大小；Summary 在客户端直接计算分位数。Counter 的“只增”是逻辑约定，进程重启会归零，因此查询时要用 rate 或 increase，它们会自动处理归零，而不是直接对原始值做减法。

基数：指标系统真正的成本变量

标签的取值组合数就是基数。每出现一个新的组合，系统就要为它建立一条序列，占用内存中的倒排索引和磁盘上的块。基数增长不是线性的：把用户 ID 放进标签，几百万用户就是几百万条序列；把完整 URL 放进标签，路径参数会让序列数随业务数据无限膨胀；把错误消息放进标签，几乎每条日志都能生成新序列。这类标签在演示环境里看不出问题，上线后往往在一天内把监控实例打爆。

治理的原则是：标签只放可枚举、可预期、数量有上界的维度，比如服务名、环境、地区、状态码、接口模板。具体 ID、原始 URL、错误详情应该放进日志或 span 属性，那里按条存储，不会生成序列。路径要先模板化，/orders/:id 而不是 /orders/123456。可以用下面的查询定期检查谁在制造序列，数字仅为示意：

Logs：结构化、字段规范与索引成本

从文本到事件

日志的本质是离散事件。传统做法把变量拼进字符串，人读起来方便，机器只能靠正则去猜；结构化日志要求把可变部分放进固定字段，消息本身保持稳定。这样同一条“订单创建失败”在千万行日志里拥有相同的模板，可以按字段过滤、聚合，也可以在采集端做脱敏和路由。

一条可用的结构化日志至少应包含事件时间、级别、服务名、环境、消息模板、trace id、span id，以及少量与事件相关的业务字段。下面的 JSON 只是示意，字段名一旦确定就应写进规范，而不是每个服务自由发挥：

字段规范的要害是稳定和可枚举：级别只用 debug、info、warn、error 四档；时间统一为带时区的 RFC 3339 或统一 UTC；服务名与指标、追踪中的服务名完全一致；业务字段采用统一下划线命名并限定类型。不要把整个对象序列化进一个字段，也不要把异常堆栈塞进 message，堆栈应单独成字段，既便于折叠展示，也避免污染消息模板。

采集、索引与边界

容器环境下最省事的路径是应用只写标准输出，由节点上的采集代理读取容器日志文件，附加 Pod、命名空间、节点等元数据后转发。这里有两个细节容易被忽略：多行日志尤其是 Java 堆栈，需要按行首模式合并，否则一行堆栈会被拆成几十条事件；时间戳必须使用应用写入的事件时间，而不是采集时间，否则容器重启或代理积压时，整条时间线都会错位。

成本主要来自索引而不是原始存储。对全部文本做全文索引，写入放大和空间开销都很高，而排障时真正高频的过滤条件往往只是服务、级别、trace id、错误码和时间范围。合理的做法是结构化字段建倒排索引，消息正文只做轻量索引或干脆不索引，压缩后按需扫描；对 debug 级日志按比例采样，error 级全量保留；对高噪声组件单独限流，避免一个死循环把整个日志管道打满。

日志不是数据库。用日志做业务查询、统计订单量、对账，短期方便，长期会带来成本、权限与一致性问题，这类需求应回到业务库或指标。日志里也不要记录密码、令牌、完整身份证号和银行卡号，脱敏必须在采集端完成，而不是指望查询时再遮住。保留期按用途分层：排障用 7 到 30 天，审计与合规日志转冷存储并单独授权，这些数字同样是示意值。

Traces：span 模型、父子关系与采样位置

Span 与调用树

一次 trace 由全局唯一的 trace id 标识，内部包含若干 span。每个 span 记录 span id、parent span id、名称、起止时间、状态、属性与事件。没有父 span 的是根 span，通常对应网关或入口服务；父子关系表达“谁调用了谁”，把每个 span 的耗时按时间轴排开，就能看出时间花在了哪一段。

  A[gateway] --> B[order-service]
  B --> C[mysql]
  B --> D[payment-service]
  D --> E[redis]

跨进程传递靠上下文传播。HTTP 调用通常把 trace id、span id 和采样标记放进请求头，服务端取出后以当前 span 作为父节点创建子 span；消息队列没有天然的请求头，需要把上下文写进消息属性，消费端再恢复。异步边界是链路断裂的高发区，很多“追踪只到网关”的系统，问题就出在发消息时没有带上上下文。

Span 的粒度需要克制。每个函数都包一层 span，会带来大量无意义的节点和写入成本，真正有价值的是 I/O 边界、外部依赖、数据库语句、缓存访问和关键业务阶段。自动埋点覆盖框架与中间件，业务阶段手工补充，命名用“动词加对象”，例如“校验库存”。属性只放低基数、短文本的上下文，请求体、响应体和大对象不应该进 span。

错误要在 span 上显式标记：状态置为 error，记录异常类型与消息，必要时附加事件。只有耗时没有错误标记，追踪就退化成一张时序图，排障时还得回去翻日志。采样决策则应在链路入口做一次，并把结果随上下文传播，保证同一条 trace 的 span 要么都被采集、要么都不被采集；下游服务如果各自重新随机采样，会得到残缺的调用树，看起来像“某些服务没有调用”，实际只是样本丢了。

把三种信号接起来

trace id 是贯穿链路的钥匙

Exemplar：让指标指向具体请求

指标是聚合后的数字，天然看不到单条请求。Exemplar 弥补了这一点：直方图的每个桶在记录计数时，可以附带一个样本值和一个 trace id，查询面板上就能看到“这一分钟的 P99 对应哪几条慢请求”，点击后跳转到追踪。它依赖客户端暴露 exemplar、服务端开启 exemplar 存储，以及面板支持跳转，三者缺一不可。

实践中常见的坑是只配了客户端，存储没开，或者指标名与追踪服务名对不上，导致跳转过去查不到数据。exemplar 的数量也应受控，通常每个桶只保留少量最新样本，它不是全量索引，不能指望靠它做完整分析。另一个办法是从指标面板携带时间范围和服务标签跳到追踪查询页，由查询条件筛出候选 trace，这种方式不依赖 exemplar，但精度低一些。

统一的资源属性是关联的前提

无论走哪条路径，三类数据都必须共享一套身份：服务名、环境、版本、集群、Pod。指标里叫 service，日志里叫 service_name，追踪资源里叫 service.name，三者对不上，任何自动跳转都会失败。更隐蔽的是版本漂移：发布后新 Pod 的版本标签变了，但日志采集配置没更新，排障时就会把新旧版本的数据混在一起看。

因此，资源属性要在采集层统一补齐，而不是依赖应用自觉上报。服务名从部署清单注入，环境和版本从发布系统注入，Pod 与节点信息由采集代理附加。平台应提供一张“服务目录”，把服务名与负责人、仓库、仪表盘、告警规则关联起来，这张目录本身就是最便宜的关联设施。

采样策略与高基数治理

头部采样：简单，但看不见长尾

头部采样在请求入口按固定比例决定是否记录，比如 1%，然后把决定写进上下文传给下游。它实现简单、开销低，不需要缓冲，也不会产生“半条链路”。问题在于决策发生在请求结束之前，系统还不知道这次请求会不会报错、会不会超时，因此低频的严重错误很可能正好落在未采样的 99% 里。

固定比例还会随流量变化而失真：低峰期一分钟只有几十个请求，1% 可能一条都不采；高峰期同样的比例又会写入过多数据。比较稳妥的做法是按目标吞吐动态调整比例，并把实际采样率记录在 span 或资源属性中，查询时乘以权重还原估算总量。采样率不是“越小越省钱”，它决定了你能否看见长尾问题。

按错误与慢请求采样：需要尾部决策

“错误全采、慢请求多采、正常请求少采”听起来理想，但它要求系统在看到完整结果之后再决定，这就是尾部采样。尾部采样器需要按 trace id 聚合所有 span，缓存一段时间，等根 span 结束或超时后再判断：命中错误、耗时超过阈值、或带有特定属性的 trace 全量保留，其余按较低比例保留。

代价是真实的。假设入口流量每秒一万个请求，平均 trace 持续 10 秒，缓存里同时存在十万条 trace；若每条 trace 的 span 数据为 5 KB，单实例就需要约 500 MB 只用于等待，这还没算索引与网络抖动带来的放大，数字仅为示意。多实例部署时还必须按 trace id 做一致性路由，否则同一条 trace 的 span 散落在不同实例，谁也拼不出完整链路。

采样率要算，不要拍

确定采样率至少要回答三个问题：每天能承受多少存储、需要多高的统计置信度、哪些错误绝对不能漏。前两个决定基础比例，第三个决定例外规则。一个可操作的起点是先用全量数据跑一周，统计各服务的 trace 量与错误分布，再按预算反推比例；上线后持续对比采样估算值与真实计数，偏差过大就说明采样逻辑有问题。

高基数治理与采样是同一笔账的两面。指标侧要建立标签白名单，禁止用户 ID、请求 ID、完整 URL、错误消息进入标签；采集侧用 relabel 规则丢弃或重命名危险标签；确实需要按用户排查的场景，把 ID 放进日志与 span 属性，那里不会生成时间序列：

同时要给基数设预算，比如单个服务活跃序列不超过五万条，超过就触发评审。没有预算，治理就只能靠事故推动。

存储与成本：保留期、降采样与冷热分层

三种信号的存储成本结构不同，优化手段也不能互换。指标的占用大致等于活跃序列数乘以采样点数，可预测、可压缩；日志的占用由写入字节数决定，索引往往比原文更贵；追踪的占用等于请求量、采样率与平均 span 数的乘积，还带有明显的写入放大。做预算时应分别估算，再相加，而不是用一个总数拍脑袋。

保留期应该按“还会不会用到”来定，而不是统一三十天。指标原始精度保留一到两周足够定位近期问题，长期趋势用降采样后的聚合数据；追踪通常只保留一到两周，错误 trace 可以单独延长；日志的排障窗口多为七天到一个月，审计日志则转冷存储并按合规要求单独设定。所有保留策略都要有自动过期，不能依赖人工清理。

降采样必须提前设计，因为它是不可逆的。原始样本删掉之后，无法再从平均值恢复分位数，也无法重新按新维度聚合。指标的 rollup 要在保留关键标签的前提下进行，日志可以按级别采样或合并相似事件，追踪则可以对成功且快速的 trace 进一步抽稀。任何降采样都要记录规则与生效时间，否则历史曲线会出现无法解释的断层。

冷热分层是控制成本的最后一道闸门。热层用本地或高性能块存储，保留最近几天数据，支撑交互式查询与告警；温层用对象存储加列式压缩，保留数周到数月，查询延迟升高但可以接受；冷层只做归档，需要时异步导出。分层的关键是查询入口统一，用户不必知道数据在哪一层，平台根据时间范围自动路由，并在跨层查询时给出延迟提示。

可以粗估来校准预期：每天一亿条 span，平均每条 1 KB，原始数据约 100 GB 一天；保留七天是 700 GB，若存两份副本就是 1.4 TB，还没算索引与压缩差异。这些数字只是示意，但足以说明采样率从 100% 降到 10% 对账单的影响。成本还应分摊到团队与服务，谁产生的数据谁负责预算，平台提供用量看板，而不是到月底才由基础设施团队统一买单。

从告警到复盘：排障流程与 SLO

一条可复用的排障路径

成熟的排障不是打开哪个系统算哪个，而是一条收敛的路径：告警指出症状，指标确认影响面，追踪定位瓶颈，日志给出原因。下面的流程刻意从粗到细，目的是尽快缩小范围，避免一上来就在海量日志里搜索：

flowchart TD
  A[告警触发] --> B[看指标确认影响面]
  B --> C[定位服务与接口]
  C --> D[找慢或错误 trace]
  D --> E[查 trace id 日志]
  E --> F[确认根因并止损]

第一步看指标，是为了回答“影响多少用户、哪些接口、从什么时候开始”。这一步也会暴露数据问题：错误率曲线与日志错误量对不上时，可能是采集断点或标签漂移。第二步用 exemplar 或时间范围筛出候选 trace，优先看错误 span 与耗时最长的下游调用。第三步拿 trace id 查日志，重点看异常堆栈、重试记录和依赖返回码。每一步都应有时间盒，十分钟没有进展就换假设，而不是无限下钻。

SLI、SLO 与错误预算

没有统一口径，“系统是否健康”就会变成争论。SLI 是实际测量值，例如“成功请求占比”或“在 300 毫秒内完成的请求占比”；SLO 是目标，例如“过去 28 天可用性不低于 99.9%”。分子分母必须定义清楚：哪些请求算好事件、健康检查是否计入、客户端取消算不算失败。口径不清的 SLO 比没有 SLO 更危险，因为它会制造虚假的安全感。

错误预算是 SLO 的另一种表达：99.9% 的月目标意味着约 43 分钟的不可用额度，这个数字随窗口长度变化，仅为示意。预算的价值在于把可靠性变成可管理的资源：预算充足时可以加快发布，预算消耗过快时冻结高风险变更、补测试与演练，而不是等故障发生后再互相追责。基于燃烧率的告警比静态阈值更贴近用户体验，具体规则与降噪策略留给第 712 篇展开。

告警本身要携带可执行信息：受影响的 SLI、查询链接、仪表盘、值班负责人、最近一次发布记录。值班同学收到告警后不应先问“这是什么”，而应能直接进入排查。复盘则聚焦系统改进：为什么监控没有更早发现、为什么恢复花了这么久、哪些手工步骤可以自动化。把每次故障都变成一条规则、一个看板或一段自动化，可观测性平台才会随时间变强，而不是越用越吵。

数据质量、平台化与常见坑

三种最常见的数据质量问题

第一是缺失。采集代理崩溃、证书过期、目标被误删、Pod 换了标签，都会让曲线突然归零或消失。归零和“没有数据”是两回事，查询时要用 absent 或“无数据”状态区分，关键 SLI 还应配置采集存活告警。第二是时间同步。同一笔请求在网关、应用、数据库上的时间戳如果来自不同步的时钟，追踪里的因果关系会颠倒，跨度出现负值；节点必须统一走时间同步服务，平台也要监控时钟偏移。第三是标签漂移。服务改名、环境标识从 prod 变成 production、版本标签格式调整，都会把一条曲线劈成两段，历史对比随之失效。标签变更应走登记与双写过渡，而不是直接改。

平台化与组织协作

平台化的目标不是再做一个大屏，而是把采集、元数据、存储、查询和权限收拢成统一入口。业务团队只负责按规范埋点，平台负责管道可靠性、默认保留期、基数上限、敏感字段脱敏和成本看板。自助能力体现在模板化：新建服务时自动生成仪表盘、告警规则和排障手册的骨架，让团队不必每次从零配置。

组织上要分清两类责任。平台团队对采集链路、存储成本和查询体验负责；业务团队对埋点质量、SLI 定义和告警有效性负责。埋点字段应在代码评审中检查，高基数标签和敏感信息在合并前就拦下来。成本按服务分摊并定期回顾，值班复盘产出的改进项要有负责人和截止时间，否则平台会逐渐退化成“出事才打开”的摆设。

五个反复出现的坑

  • 埋点泛滥：每个函数都加 span、每条分支都打日志，成本上升而信噪比下降。埋点应覆盖边界与关键阶段，而不是覆盖代码行。
  • 标签用用户 ID：把用户、订单、请求 ID 放进指标标签，序列数随业务数据增长，最终拖垮监控后端。这类维度属于日志与追踪。
  • 日志当数据库：用日志做统计、对账和业务查询，既贵又不可靠。业务问题回到业务库，趋势问题交给指标。
  • 采样率拍脑袋：固定 1% 既不随流量调整，也不保证错误可见。采样率要按预算计算，记录在数据里，并定期校验估算偏差。
  • 只看单信号：指标涨了不看追踪，追踪慢了不查日志，最后仍然靠猜。三类信号的价值在关联，不在数量。

小结

三大支柱各有自己的数据模型与成本曲线：指标贵在基数，日志贵在索引，追踪贵在采样后的写入量。落地时先把身份体系统一，用 trace id、exemplar 和资源属性把三类数据串起来，再谈分析与告警。采样率与保留期按预算计算，高基数标签从源头治理。排障流程应固化为从告警到指标、追踪、日志的收敛路径，SLI 与错误预算则把可靠性变成可以协商的资源。数据质量与平台自助能力决定这套体系能否长期运转，埋点规范与成本分摊要一开始就立起来。
