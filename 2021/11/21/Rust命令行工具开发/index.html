Rust 命令行工具开发

本文属于《Rust 学习路线》第 63/68 篇
上一篇系列目录下一篇

命令行工具是 Rust 的强项：产物是单个可执行文件，启动快，交叉编译与静态链接也有成熟方案。本文以假想的批量文本处理工具 batchfmt 为例，走一遍从项目结构、参数解析、配置到日志与进度、管道与退出码、测试与打包发布的流程；读者应能读懂 Rust 基础语法，但不要求命令行开发经验。

本文代码基于 Rust 1.56 与 2021 edition，参数解析使用 clap 3.x 的派生宏；2021 edition 于 2021 年 10 月随 1.56 发布，只是一组编译器批次开关，不改变 crate 间的兼容关系。batchfmt 读取文本文件，统一缩进与行尾后写回或输出，另带统计子命令。

项目结构与 main 的返回类型

用 cargo new batchfmt 创建二进制 crate，入口是 src/main.rs。工具超过几百行就值得拆文件：cli.rs 放参数结构体，config.rs 负责配置，run.rs 放业务逻辑，main.rs 保持薄。这样参数解析能单独测试，业务也不依赖终端；集成测试放 tests/cli.rs，把可执行文件当黑盒运行。

Rust 允许 main 返回 Result<(), E>，只要 E: Debug。成功时退出码为 0；失败时运行时向标准错误打印 Error: 加 Debug 表示，退出码为 1。小工具够用，但 anyhow 的 Debug 是多行且带错误链缩进，不像面向用户的提示。更稳妥的是在 main 里接住错误，用一行文本打印上下文链，再自行决定退出码，后文展开。

clap 3 的派生宏把结构体定义变成命令行的唯一事实来源：字段名映射为参数名，文档注释变成帮助文本，#[clap(version)] 自动读取 CARGO_PKG_VERSION。先加上依赖，注意 env 特性要显式打开，后面读取环境变量时会用到：

--help 按字段顺序与文档注释组织，子命令单独列出，注释里的空行会保留为段落。帮助信息是用户最先看到的产品界面，值得像写文档一样打磨，至少写清单位、默认值与取值范围。

配置的优先级

参数一多就需要配置文件，优先级必须提前定好，否则同一选项两处取值不同会很难排查。本文的顺序是：命令行高于环境变量，环境变量高于配置文件，配置文件高于内置默认值。越靠近本次调用的设置越优先，越持久的设置越靠后，符合多数人的直觉。

环境变量交给 clap：字段上写 #[clap(long, env = "BATCHFMT_JOBS")]，命令行没给时它去查环境变量，变量名统一加 BATCHFMT_ 前缀避免撞车。配置文件用 serde 反序列化，字段全部声明为 Option，缺失项留到合并阶段：

配置文件查找也要约定。显式传入 --config 却找不到文件必须报错；未传入时按平台惯例找默认位置：Linux 用 $XDG_CONFIG_HOME/batchfmt/config.toml 或 ~/.config，macOS 用 ~/Library/Application Support，Windows 用 %APPDATA%。默认文件不存在应静默跳过，别让新用户先建空文件。配置里可能有令牌，日志只打印路径。

日志、进度条与终端颜色

输出分两类：程序结果走标准输出，运行过程走标准错误。日志属于后者，借助 log 门面与 env_logger 实现，模块里只写 info!、debug!，由入口决定级别，库代码就不绑死日志后端。-v 重复次数映射级别是 Unix 的常见约定：

默认只显示警告，-v 打开信息级，-vv 打开调试级，更多进入追踪级。平时输出干净，排障时按需加参数。env_logger 默认写标准错误，务必保持，否则日志混进标准输出会破坏管道。

批处理几千个文件，长时间没反馈会让人以为卡死。进度条可用 indicatif 一类的库，但先判断终端：标准错误不是 TTY（重定向、CI）时不应绘制，只留最终汇总。可用 atty 的 is(Stream::Stderr) 判断。绘制目标显式设为标准错误，用 set_position 更新，用 finish_and_clear 清理；在进度条上方打日志时用库提供的打印方法，避免两套输出互相覆盖。

颜色同理，要同时满足：输出是 TTY、NO_COLOR 未设置、TERM 不是 dumb。再提供 --color auto|always|never 覆盖判断，always 在重定向时也着色，never 完全关闭。红色标错误、黄色标警告即可，别把颜色当唯一信息载体。

管道、退出码与错误输出

Unix 工具的契约很朴素：标准输出只放数据，标准错误只放提示，退出码表达结果。遵守它，batchfmt convert a.txt | sort | uniq 才能正常工作。“开始处理”之类的话写进标准错误；支持 --format json 时，标准输出不能混入一个字节的额外内容，否则 jq 会直接失败。

应用层用 anyhow 能省样板：返回 anyhow::Result<T>，用 Context 补上“在哪个文件、哪一步失败”，用 bail! 提前返回，用 ensure! 表达断言。它的价值在错误链组装，不在类型系统。库 crate 不应把 anyhow 暴露到公开 API，应返回具体错误类型，由应用层汇总展示。错误类型的语言机制不在本文展开。

退出码约定不必复杂，但要在文档写清：0 全部成功；1 运行失败，例如文件读不了、格式不合法；2 留给参数用法错误，这也是 clap 的默认行为，不要挪用。多文件部分失败仍可用 1，并在标准错误列出清单；更多退出码只会让脚本作者多查文档。

管道还有经典问题：batchfmt big.txt | head -n 5 时下游读够五行就关闭管道，上游继续写会收到 EPIPE。Rust 默认忽略 SIGPIPE，错误以 BrokenPipe 从写操作返回，而 println! 写失败会 panic。应改用 writeln! 写加锁的标准输出，遇到 BrokenPipe 安静地以 0 退出，其余错误照常上报：

读取方向也要照顾管道。约定单个 - 表示标准输入，用 io::stdin().lock() 配合 BufRead 逐行处理，不要一次性 read_to_string，否则大文件会吃光内存。逐行写标准输出有锁开销，包一层 BufWriter 并在正常路径 flush，能减少系统调用。

跨平台、打包与启动性能

跨平台第一原则是不要在字符串层面拼路径。全程用 PathBuf 与 Path，用 join 追加层级，展示时用 display()，系统调用时保持 OsStr。Windows 的分隔符、盘符与长路径规则都不同，字符串拼接迟早出错。换行同理：读取时按 \n 切分并容忍 \r，写回默认 \n，确有需要再给 --crlf，不要按编译目标偷偷改变输出。

信号处理常被忽略。用户按 Ctrl-C 时进程默认立刻终止，写了一半的文件和临时文件都会留下。稳妥做法是先写同目录临时文件，成功后 rename 原子替换；用 ctrlc 一类的库注册处理函数，收到中断先清理再退出，退出码用 130。Unix 还要考虑 SIGTERM，容器停止时发的就是它。处理函数里只做标记，真正清理放在主循环检查标记之后。

关键概念是 C 运行库。默认 GNU 目标动态链接 glibc，产物小，但依赖运行环境的 glibc 版本，旧发行版可能报符号缺失；musl 目标把 libc 静态编入可执行文件，复制到任何同架构 Linux 都能跑，代价是体积略大、部分场景稍慢。静态链接不是万能药：依赖 OpenSSL 等原生库时，需要静态版本并正确配置链接器。Windows 还要区分 MSVC 与 GNU 工具链。

启动时间是隐形指标。Rust 本身启动很快，容易被拖慢的是：main 开头的大量初始化、无条件编译巨大正则、启动就建线程池、读取用不到的配置。把这些推迟到真正需要时，或至少让常见路径只做最少的事。可先用 time batchfmt --version 粗看，再用 hyperfine 多次测量。

分发方式取决于用户群。内部工具把 release 产物打成 tar 包、附校验和放进制品库；开源项目常用 cargo install 从源码构建，或提供预编译包与包管理器配方。README 要写清支持平台、最低系统要求与升级方法。版本号遵循语义化版本，--version 至少包含程序名与版本号，方便报障时粘贴。

几个容易踩的坑

短参数冲突。 clap 默认把 -V 留给版本、-h 留给帮助，所以 -v 可安全用于 verbose；若给别的字段指定 short = 'V'，调试构建会在启动时 panic 提示重复。字段名也讲究，叫 version 或 help 容易与自动生成的参数冲突，换成语义明确的 show_version 更稳。把参数结构体放进单元测试，很快能暴露这类问题。

-- 透传。 工具需要把剩余参数原样交给另一个程序时，普通位置参数会把 -x 当成自己的选项而报错。clap 3 可用 #[clap(last = true)] 标记 Vec<String> 字段，在 -- 之后收集全部内容；也可用 allow_hyphen_values 放宽单个参数。-- 之后不再解析是 POSIX 惯例，帮助文本要写明。

非 UTF-8 路径。 Linux 文件名是任意字节序列，不一定能转成 String。std::env::args() 遇到非 UTF-8 参数会 panic，应改用 args_os()；clap 内部使用操作系统字符串，配合 parse(from_os_str) 接收 PathBuf 是安全的。确实需要文本时再 to_str()，把 None 当可处理错误而非 unwrap；打印用 display()，无法解码的部分会被替换。

终端宽度与字符宽度。 帮助和进度条不要写死 80 列，窗口可能更窄或更宽；能读终端尺寸就按它来，读不到退回保守值。中文等全角字符在终端通常占两列，按字符数补空格会让表格错位，对齐时应使用能计算显示宽度的库。文件名过长要截断，否则一行反复折行，画面抖得没法看。

日志污染标准输出。 这是开发机最难发现、却最易破坏脚本的问题：调试用的 println! 忘了删，配合 --format json 就把输出变成非法 JSON。约定诊断信息走 eprintln! 或日志宏，评审时把标准输出的每次写入当 API 审查。另外 process::exit 不运行析构函数，深埋业务代码的退出会让缓冲来不及 flush、临时文件来不及删，退出只应发生在最外层。

小结

Rust 命令行工具的骨架不复杂：用 clap 3 派生宏把参数定义成结构体，用 Option 字段给配置分层留空间，日志与进度送标准错误，结果留给标准输出。main 返回 Result 适合原型，正式发布要自己接住错误，才能控制提示与退出码。测试覆盖参数解析和真实进程两条路径；跨平台问题集中在路径、换行与信号。发布时开启 release 优化、按需静态链接，并把启动路径上的多余工作推迟。
