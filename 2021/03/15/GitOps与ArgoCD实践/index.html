GitOps 与 ArgoCD 实践

本文属于《Docker 与 Kubernetes》第 45/51 篇
上一篇系列目录下一篇

把 Kubernetes 清单放进 Git，再由集群内的控制器把清单持续拉下来应用，这套做法在 2020 年前后有了统一的名字：GitOps。本文从 GitOps 的四条原则讲起，比较 push 与 pull 两种部署模型的差异，再以 2021 年初的 ArgoCD 1.8 为例，完整走一遍安装、连接仓库、创建 Application 与配置同步策略的过程。读完之后，你应该能为团队搭起一条以 Git 为唯一事实源的交付链路，并且知道哪些坑最容易踩。

本文面向已经会用 kubectl 管理应用、熟悉 Deployment 与 Namespace 基本概念的读者。Kubernetes 对象本身的细节不再重复，Ansible 相关的配置管理话题也不在本文范围内。

从 kubectl apply 到 GitOps

在没有 GitOps 之前，最常见的交付方式是：CI 流水线构建镜像、推送 registry，最后执行 kubectl apply 或 helm upgrade。问题会随着集群数量增长而放大：流水线里存放着集群的 kubeconfig，权限往往是 cluster-admin；某次发布失败后没人知道集群里到底是什么版本；有人半夜改了副本数排查问题，第二天忘了改回来，集群与代码库就此分叉。

GitOps 的核心主张很朴素：把 Git 仓库当作系统期望状态的唯一事实源，集群里的实际状态只能由控制器从仓库推导出来。任何变更都先落到 Git，走代码评审，再由控制器同步到集群。这样一来，发布历史就是提交历史，回滚就是 revert，集群漂移会被自动发现甚至自动纠正。

这套理念通常被归纳为四条原则。第一是声明式：用 YAML 描述期望状态，而不是写一堆“先创建 A 再修改 B”的命令脚本。第二是版本化且不可变：所有清单进入 Git，每次变更都有提交号可追溯。第三是自动拉取：集群侧主动拉取清单，而不是等外部系统推过来。第四是持续协调：控制器不断对比期望状态与真实状态，差异出现就处理。

flowchart TD
    A[开发者提交清单到 Git] --> B[ArgoCD 发现新提交]
    B --> C[Repo Server 渲染清单]
    C --> D[Controller 对比期望状态与实际状态]
    D -->|存在差异| E[执行同步]
    D -->|一致| F[保持 Synced]
    E --> D

这条闭环就是“持续协调”的含义。它带来一个推论：集群里的一切都该能在仓库里找到出处，凡是无法用清单表达的东西，都会成为闭环之外的例外。

push 与 pull：两种部署模型的差异

理解 GitOps，关键要看清部署动作由谁发起。push 模型里，CI 在流水线最后一步把清单推到集群，凭据保存在流水线中；pull 模型里，集群内的 agent 主动去仓库取清单，流水线对集群一无所知。

维度 push 模型 pull 模型
发起方 CI 流水线 集群内控制器
集群凭据位置 流水线变量或凭据库 只在集群内部
网络方向 CI 到 API Server 控制器到 Git 仓库
漂移检测 需要额外巡检 协调循环天然具备
审计来源 流水线日志 Git 提交历史
失效影响 流水线挂了就发不出去 控制器挂了，集群仍保持现状

安全边界的差别最值得强调。push 模型下，任何一个能改流水线的人，实际上都握有集群的写权限，一旦 CI 被攻破，攻击面直接延伸到集群内部。pull 模型把这个方向倒过来：集群只信任仓库内容，对外只需要一条出站连接去拉代码，仓库凭据也留在集群里。攻击者即便拿到仓库的写权限，也要经过评审与同步策略才能让变更落地，链路更可控。

代价同样存在：集群要能访问 Git，内网隔离严格时需要代理或镜像仓库；控制器成为关键组件，它挂了新变更就发不出去；渲染层出错时，排查路径也更长。

ArgoCD 的架构与对象模型

ArgoCD 是 pull 模型的典型实现，以一组 Pod 跑在集群里，同时管理本集群和其他集群。组件分工清晰，理解它对排查问题很有帮助。

API Server 即 argocd-server，对外提供 gRPC 与 REST 接口，也是 Web UI 的后端。它本身不保存状态，所有数据来自 Kubernetes 里的 Application 对象和 Secret，因此可以多副本部署。Repo Server 即 argocd-repo-server，负责克隆仓库、缓存代码，并调用 Kustomize、Helm、Jsonnet 等工具把清单渲染成纯 YAML。Application Controller 是一个 StatefulSet，持续监听 Application，做状态对比，并在需要时发起同步。Redis 只承担缓存，丢了可以重建，但会带来一段时间的重复渲染开销。开启 SSO 时还会多一个 Dex 组件。

对象模型只有两个核心类型。Application 描述“把哪个仓库的哪个路径，部署到哪个集群的哪个命名空间”，是同步的最小单位。AppProject 则是边界，规定一组 Application 允许使用哪些仓库、可以部署到哪些目标、能创建哪些集群级资源。前者回答做什么，后者回答允许做什么。

把两者分开，是为了让“谁能改什么”有落点。多租户场景下，平台团队维护 Project，业务团队只在自己的范围内创建 Application，越权操作会在准入阶段被拒绝。

安装、连接仓库与第一个 Application

ArgoCD 的安装就是应用一份官方清单。单集群试用装标准版即可，生产环境建议使用同目录下的高可用清单，把 API Server 与 Repo Server 各起两个副本。

首次登录的用户名是 admin，初始密码是 argocd-server Pod 的名称。拿到密码后建议立刻用 CLI 修改，并开启 SSO。

连接 Git 仓库有两种方式。命令式适合试验：argocd repo add <repo-url> --username <user> --password <token>；声明式更适合长期维护，在 argocd 命名空间创建一个带 argocd.argoproj.io/secret-type: repository 标签的 Secret，写入地址、用户名与令牌。后者能随平台仓库一起版本化，换令牌也只需改一个文件。

应用之后，执行 argocd app get guestbook-dev 能看到 Sync Status 与 Health Status 两个维度：前者表示集群状态是否等于仓库渲染结果，后者表示资源本身是否健康。刚创建时通常是 OutOfSync / Missing，点一次 Sync 才会真正创建资源。同步成功不代表应用可用，反之亦然。

同步策略与多环境布局

手动同步适合首次上线和敏感环境，日常开发更常见的是自动同步。syncPolicy.automated 下有三个开关，作用各不相同。

配置项 作用 建议
automated 仓库有新提交就自动同步 开发环境开启
selfHeal 集群被手工改动后自动改回 配合自动同步使用
prune 删除仓库中已移除的资源 生产环境谨慎开启
allowEmpty 允许渲染结果为空时同步 默认关闭，防止误删全量

prune 是最需要敬畏的一项。开启后，只要资源从仓库里消失，控制器就会把它从集群删掉。正常流程里这正是我们想要的，但一旦路径配错、渲染失败返回空结果，或者有人误删了整个目录，后果就是成片资源被清理。因此生产环境通常自动同步加 selfHeal 打开，prune 单独评估，并用 allowEmpty: false 兜底。

多环境布局有两种主流做法。按目录分层是最常见的一种，base 存放公共清单，overlays/dev、overlays/staging、overlays/prod 通过 Kustomize 打补丁，各自只描述差异部分。

ArgoCD 会自动识别目录里的 kustomization.yaml 并调用 Kustomize 渲染，无需额外配置；如果目录里有 Chart.yaml，则按 Helm Chart 处理，可以在 source.helm 下指定 valueFiles、parameters 和 releaseName。两种方式都能用，选择标准是团队更熟悉哪一种模板语言，而不是哪个更“云原生”。

另一种做法是按分支区分环境，main 对应生产，develop 对应开发。它看起来省事，却把环境差异藏进分支合并里，回滚和审计都会变复杂，环境超过两个就不建议使用。

Application 多起来之后，手工创建很难维护。常见做法是 app-of-apps：用一个 Application 指向存放其他 Application 清单的目录，同步它就会创建出整组应用。它本质上是“Application 管理 Application”，没有引入新概念。

健康检查、同步波次与回滚

ArgoCD 对常见工作负载内置了健康判断规则：Deployment 看副本是否全部就绪，StatefulSet 看有序滚动是否完成，Job 看是否成功，PVC 看是否绑定。这层判断是“资源健康”而不是“业务健康”，它不关心接口是否返回 500。

真正麻烦的是资源顺序。Namespace 要先于其下的对象，CRD 要先于自定义资源，数据库迁移要先于新版本 Deployment。ArgoCD 用同步波次解决：给资源打上 argocd.argoproj.io/sync-wave 注解，数字小的先应用，默认波次为 0，负数表示更早。

波次与钩子是两套机制。波次只控制顺序，资源最终仍属于应用；钩子则声明这个资源是同步过程的一部分，可设为 PreSync、Sync、PostSync，结束后按 hook-delete-policy 决定是否清理。数据库迁移、缓存预热适合用钩子，普通依赖顺序用波次即可。

回滚有两条路径。第一条是 ArgoCD 的历史回滚：argocd app history guestbook-dev 列出历次同步的修订号，argocd app rollback guestbook-dev 2 直接回到某次状态。它快，但只改变集群，不改变 Git，下一次自动同步会把状态又拉回仓库的最新提交，等于回滚失效。第二条是 Git revert，提交一次反向变更，让仓库与集群一起回退。后者才是 GitOps 语义下的正解，前者只适合应急止血。

Application 默认只保留最近 10 条历史，revisionHistoryLimit 调小会让可选的回滚点变少，习惯用历史回滚的团队至少保留 20 条。

密钥、RBAC 与多租户

Git 是唯一事实源，这句话遇上线上的密码就会卡住。数据库口令、镜像凭据、TLS 私钥不能明文提交，但排除在仓库之外，又会在集群里制造手工维护的黑洞。2021 年初常见的三种做法各有定位。

Sealed Secrets 的思路是“加密后放心提交”。集群里跑一个控制器持有私钥，开发者用 kubeseal 把 Secret 加密成 SealedSecret 提交，只有目标集群能解密，简单且无外部依赖，但密钥轮换与跨集群共享比较别扭。External Secrets 相反，仓库里只放“去哪里取哪个键”的引用，由 Operator 从 Vault 或云厂商密钥服务同步成 Secret，适合已有集中密钥管理的组织。

RBAC 的入口是 argocd-rbac-cm 里的 policy.csv，语法接近 Casbin：主体、资源、动作、对象、效果。

这段配置表示 team-a 组继承 team-a-dev 角色，只能查看和同步 team-a 项目的应用，不能删除，也不能碰其他项目。配合 AppProject 的仓库与目标限制，就构成双层防线：RBAC 管能不能操作 Application，Project 管它能碰哪些集群资源。

多租户还要考虑组件级隔离。共享一套 ArgoCD 时，各租户的 Application 都在 argocd 命名空间，仓库凭据也共享给 Repo Server，隔离强度有限；合规要求高的团队不如按租户独立部署实例。接入统一身份时启用 Dex，把用户组映射到 RBAC 角色，可免去另维护一份账号。

常见坑与应对

Application 清单太大，apply 报注解超长。 Application 的 CRD 带着完整的 OpenAPI 校验，客户端 apply 会把整份对象塞进 last-applied-configuration 注解，一旦超过 256 KB 就会失败，典型报错是 metadata.annotations: Too long。解决办法是改用服务端 apply：kubectl apply --server-side -f application.yaml。内嵌大段 Helm values 时尤其常见。

手工改动被默默改回。 开了 selfHeal 之后，有人 kubectl edit 调大副本数排查问题，几分钟后就被改回原值，现场消失，排查反而更难。正确的姿势是排障前先关掉自动同步，argocd app set guestbook-dev --sync-policy none，定位完再把变更写回 Git。

prune 删掉了不该删的东西。 控制器只认仓库，凡是集群里存在、仓库里没有、又归属于该 Application 的资源，都会被清理。HPA 创建的副本、Operator 生成的辅助对象、手动加的临时 ConfigMap 都在此列。确实需要保留的资源可加 argocd.argoproj.io/sync-options: Prune=false 豁免，但更稳妥的是先在小环境验证影响面。

仓库连不上，或者新提交不生效。 私有仓库要确认 Repo Server 的出站网络、DNS 和证书；用 SSH 地址时还要提供 known_hosts，否则会卡在主机校验。另一种情况是仓库有新提交、界面却停在旧版本，多半是 Repo Server 缓存，执行 argocd app get guestbook-dev --refresh 强制刷新即可。

Helm 的 hook 资源导致永远 OutOfSync。 Helm 渲染出的 hook 资源在 ArgoCD 眼里就是普通对象，同步后它们的注解与期望状态不一致，应用会一直显示 OutOfSync。要么改用 ArgoCD 自己的波次与钩子，要么用 ignoreDifferences 忽略相关字段。本地 Kustomize 版本与内置版本不一致时也会出现类似问题，需在 argocd-cm 里固定构建参数。

小结

GitOps 的价值不在工具，而在把“集群里应该有什么”收敛成一份可评审、可回滚的 Git 记录，ArgoCD 只是把这条闭环工程化。四条原则里，持续协调是最容易被低估的一条，它同时带来漂移自愈和误删风险，因此 prune 与 selfHeal 要按环境分级开启。落地时先把仓库结构、Project 边界和密钥方案定下来，再谈自动同步，能省掉大量返工。回滚优先走 Git revert，历史回滚只当止血手段。最后记住：凡是绕过 Git 的变更，迟早会在下一次协调中被抹掉。
