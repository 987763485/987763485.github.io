Serverless 架构与 Knative

本文属于《Docker 与 Kubernetes》第 50/51 篇
上一篇系列目录下一篇

Serverless 在 2021 年已经不算新词，但它常常被简化成“不用管服务器”的一句口号，而不是一套可以被推敲的架构约束。本文先把这个问题拆成 FaaS 与 BaaS 两种形态，再看清楚按需伸缩、缩到零和计费模型各自意味着什么，最后落到 Knative 这个在 Kubernetes 上实现 Serverless 的项目上。

截至 2021 年初，Knative 仍处在 0.x 阶段（0.20、0.21 附近），API 还在变化，社区也仍在讨论哪些对象应该进入核心。因此本文的定位是一份入门加避坑的笔记：讲清楚概念、对象与取舍，配置只做示意，真正升级前请对照当时的官方文档。

两种形态：FaaS 与 BaaS

Serverless 在 2021 年不是一个单一技术，而是一组“把运维责任转移出去”的约定。截至 2021 年，业界通常把它分成两半：FaaS 与 BaaS。

FaaS（Function as a Service）以函数为部署单位。开发者只提交一段处理逻辑和它的依赖，平台负责运行时、扩缩容、安全补丁与可用性。调用由事件触发，一次 HTTP 请求、一条队列消息、一个对象上传完成，都可以成为入口。函数被约定为无状态、短生命周期，两次调用之间不保证复用同一个进程，因此本地内存和临时文件都不能当作可靠存储。AWS Lambda、阿里云函数计算这类产品是这一形态的代表，本文只把它们当作类别举例，不比较具体产品的差异。

BaaS（Backend as a Service）把数据库、对象存储、消息队列、身份认证这些后端能力做成开箱即用的服务。开发者不再申请虚拟机，也不再调连接池参数，只在代码里调用 SDK。这种形态的 Serverless 味道，在 2021 年主要体现于计费与运维界面：按用量付费，容量由服务方兜底。

真实应用几乎都是两者的混合体：函数承担无状态的业务入口，状态放进 BaaS 的存储与队列。这一点决定了后面所有约束——函数随时可能被替换或销毁，任何需要跨调用保留的东西都必须外置。

按需伸缩、缩到零与计费模型

把 Serverless 等同于“自动伸缩”，是 2021 年最常见的误解。普通的自动伸缩依据 CPU、内存等资源指标调整副本数，副本数有下限，空闲时仍然占着机器；而 2021 年的 Serverless 实现依据请求伸缩，并允许下限为零。

“缩到零”不是营销词，而是一个明确的架构承诺：一段时间没有请求，实例可以被完全回收，此时不产生计算费用。代价是下一个请求到来时必须先创建实例，这段等待就是冷启动。换句话说，2021 年的 Serverless 平台把闲置成本换成了首请求延迟，这笔交易是否划算，取决于流量形态。

计费模型也随之改变。虚拟机按小时或按月租用，只要开机就付费；2021 年的 Serverless 按请求次数加上执行时长计费，粒度细到秒甚至更小，没有请求就不计费。2021 年的主流平台大多还提供每月免费额度，演示环境和低频内部工具的成本因此接近于零。

计费细则里有几个容易被忽略的陷阱：执行时长通常按取整计算，短请求的实际单价会被放大；并发数往往有配额，突发流量可能被限流而不是被扩容；出网流量、日志存储以及预热用的最小实例都要单独计费。做预算时如果只看“每百万次调用多少钱”，很容易低估真实开销。这些数字会随平台与区域变化，本文不给具体报价。

Knative：Kubernetes 上的 Serverless 层

如果集群已经是 Kubernetes 1.20，又想要 Serverless 的伸缩语义，2021 年一个自然的选择是 Knative。它的定位不是替代 Kubernetes，而是在其上补一层“请求驱动的抽象”。

Knative 早期由 Build、Serving、Eventing 三部分组成，Build 后来被移除，构建工作交给 Tekton 一类工具，所以现在谈 Knative 主要指两块：Serving 负责把容器镜像跑成可按请求伸缩、可切分流的服务；Eventing 负责事件的接入、路由与投递。两者都以 CRD 形式安装，用 YAML 描述，和集群里其他资源一样被 kubectl 管理。

它和直接写 Deployment 的差别在抽象层级。Deployment 描述“我要几个副本”，Knative 描述“我要一个能处理请求的版本”，副本数由它自己算，甚至可以为零；路由与流量分配也由它接管，灰度发布于是变成改一个百分比字段。Kubernetes 的对象模型本文不再重复，Pod、Deployment 的细节请参考同系列的基础篇目。

代价是组件更多。Serving 需要一个网络层承载入口流量，2021 年常见的选择是 Istio，也有 Kourier、Contour 这类更轻的选项；还需要 autoscaler、activator、controller 等角色协同。排障时要多看几个地方，集群资源开销也不再只是“业务 Pod 那一点”。

截至 2021 年初，Knative 仍是 0.x 版本（0.20、0.21 附近），API 在版本之间发生过不兼容调整，升级前必须读 release notes，不能假设对象结构稳定。

Serving 的四个核心对象

Serving 的概念不多，但四个对象之间的关系要一次讲清，否则看 YAML 会迷路。

Configuration 描述“当前期望的容器模板”，包含镜像、环境变量、资源限制、并发参数等，像一个声明式的版本工厂。每次模板发生变化，就产生一个新的 Revision。Revision 是不可变快照，创建后不再修改，名字由服务名加序号生成；不可变是关键设计，它让回滚与流量切分有了稳定的锚点。Route 描述“请求分给哪些 Revision、各占多少比例”，持有域名与流量规则，是流量的唯一入口。Service 则是便利对象，创建它会同时生成 Configuration 与 Route，日常基本只写它。

  S --> RT[Route]
  C --> V1[Revision v1]

流量切分与灰度发布

Route 的价值在于把“发布”和“扩容”解耦。同一份配置里可以同时指向多个 Revision，按百分比分配流量，每个 Revision 又各自按需伸缩。

典型做法是先把新 Revision 以 10% 接入，观察错误率与延迟，再逐步提到 50%、100%。tag 字段会为这个 Revision 生成独立域名，方便测试同学直接访问新版本，而不影响主入口。另一个便利之处是回滚：只要旧 Revision 还在，把百分比改回去即可，镜像与配置都不必重新准备。

需要提醒的是，百分比切分是请求级的，不是会话级的。同一个用户可能这次打到旧版本、下次打到新版本，对依赖本地缓存或会话状态的服务并不友好；这类服务需要自己做粘性，或者干脆采用蓝绿切换，把 100% 一次性切过去再观察。

KPA：并发指标与 activator

Knative 的自动伸缩器叫 KPA（Knative Pod Autoscaler）。它不看 CPU，而是看每个实例正在处理的请求量，默认指标是并发数，也可以切换为每秒请求数。目标值通过 target 注解给出，例如 50 表示希望每个实例平均同时处理 50 个请求（示意值）。

为什么不看 CPU？因为这类负载常常是 I/O 密集的，CPU 利用率上不去但请求已经排队，以并发为准更接近“这个实例忙不忙”的真实体感。代价是它对业务特征敏感：一个慢请求会长时间占住并发额度，导致扩容过度。

缩到零由稳定窗口决定。KPA 观察一段时间的指标，确认没有请求后把副本降到零，这个窗口在 2021 年的版本里默认是 60 秒左右，可以调整。窗口太短会导致反复抖动，太长则闲置成本上升。

真正有意思的是 activator。副本为零时没有进程可以接请求，activator 先把请求接住并缓冲，同时通知 autoscaler 拉起实例，等实例就绪后再转发；缩容期间它还会统计在途请求，避免请求打到正在退出的实例上。所以冷启动的那段时间里，用户感受到的是“等了一下”，而不是连接被拒绝。

flowchart TD
  U[请求] --> A[activator 缓冲]
  A --> K[KPA 拉起实例]
  K --> R[转发请求]
  R --> P[queue-proxy 上报指标]
  P --> K

每个业务 Pod 里都会注入一个 queue-proxy 容器，由它转发流量、统计并发并把指标报给 autoscaler。排查伸缩异常时，先看 queue-proxy 的指标，再看 autoscaler 的决策日志，比盯着副本数猜要有效得多。

Eventing：Broker、Trigger 与 Source

Serving 解决的是“请求进来怎么办”，Eventing 解决的是“事件发生之后谁来处理”。Eventing 在 2021 年的模型由三个对象撑起来。

Broker 是一个事件入口，可以理解为集群内的消息总线，生产者把事件发给某个 Broker，不关心谁来消费。Trigger 是订阅规则，挂在 Broker 上，按属性过滤事件并指定订阅者。Source 是事件的生产者适配器，把外部系统的事件转成统一格式送进 Broker，定时触发、Kubernetes 事件、消息队列都有对应的实现。

事件统一用 CloudEvents 信封描述，包含 type、source、id 等属性，过滤与路由都依据这些属性，而不是消息体的内部结构。这个设计的意图是解耦：生产者不必知道有几个消费者，消费者也不必知道事件从哪来。代价是多了一跳 Broker，延迟与运维复杂度都要计入成本；对延迟极敏感的场景，点对点调用反而更简单。

冷启动、可观测性与适用场景

冷启动从哪里来

冷启动不是一个原因，而是一串串行的等待：调度 Pod、拉取镜像、启动运行时、加载应用、通过就绪检查。任何一段慢，用户都会感知到。

缓解手段也就对应这几段。设置 minScale 保留最小副本，直接绕开缩容到零，代价是常态成本；对低频但重要的服务做定时预热，用一次轻量请求把实例叫醒；把基础镜像做小、把依赖分层，减少拉取时间；把重初始化移出请求路径，例如提前构建缓存；配置启动探针，让 Knative 在应用真正可服务之前不要接流量。

这些手段都有边界。预热会破坏按需的初衷，最小副本本质上是为延迟付费；镜像优化只能减少固定开销，无法消除运行时初始化。所以更根本的判断是：这个服务的首请求延迟能否被业务接受。能接受就不必优化；不能接受，说明它可能不适合缩到零。

观测看哪几个层面

第一层是请求侧，看入口的错误率与延迟分位，尤其是冷启动请求的尾延迟。第二层是伸缩侧，看每个 Revision 的并发、副本数与缩容事件，判断 KPA 的目标值是否合理。第三层是组件侧，activator、autoscaler、controller 与网络层的日志，能解释“为什么没有扩容”这类问题。

指标主要来自 queue-proxy 与各控制器，2021 年的常见做法是接进 Prometheus 再用 Grafana 出图，日志按 Revision 打标签聚合。链路追踪需要应用配合，在 2021 年的 Serverless 场景下更容易断链，因为每次调用可能落在新实例上。

什么时候不该用

适合的场景有共同特征：流量有明显波峰波谷、请求可以拆成短小的无状态单元、能容忍首请求的额外等待。内部工具、Webhook 接收端、定时任务、事件处理管道都属于这一类。

不合适的场景同样清晰：长连接与长任务，缩容会直接掐断；强状态服务，本地缓存与本地磁盘没有保障；稳定的高 QPS，按需伸缩省不下钱，反而多一层组件；启动极慢的应用，冷启动不可接受；团队没有 Kubernetes 运维能力，多一层抽象就多一层故障面。

前面提到的年代限制在这里要重申：截至 2021 年初，Knative 的 0.x API 仍在演进，把生产流量压上去之前，先在小集群里跑一轮升级演练，比读十篇介绍文章更有用。

小结

Serverless 在 2021 年的核心不是“没有服务器”，而是把伸缩单位从副本改成请求，并允许缩到零，代价是冷启动与状态外置。Knative 把这套语义搬到了 Kubernetes 上：Serving 用 Configuration、Revision、Route、Service 描述版本与流量，KPA 以并发指标驱动伸缩，activator 负责零副本时接住请求，Eventing 用 Broker、Trigger、Source 组织事件。灰度发布在 Knative 里只是改 Route 的百分比，回滚也只是改回去。落地前先确认三件事：启动是否够快、状态是否已外置、团队是否能维护这层组件。最后记住它当时还是 0.x，API 会变。
