TypeScript 泛型工具类型实现

本文属于《TypeScript 学习路线》第 31/74 篇
上一篇系列目录下一篇

TypeScript 自带的 Partial、Pick、ReturnType 这些工具类型，用起来像黑盒：写上去就生效，出错时却只能盯着红色波浪线猜。本文把它们逐个拆开，用最少的语法从零实现一遍，再讨论递归、分布式条件类型和模板字面量类型这些进阶手段。读完你应该能做到两件事：看见一个陌生的工具类型，能立刻说出它由哪几块拼成；自己写工具类型时，知道编译器会在哪里卡住。

先把工具箱倒出来

打开 lib.es5.d.ts，能看到 TypeScript 官方对这批工具类型的定义。它们没有魔法，全部建立在四种能力之上：keyof 取出键的联合、索引访问 T[K] 取出值的类型、映射类型批量改写属性、条件类型加 infer 做模式匹配。这四种能力组合起来，就足以表达绝大多数“对类型做变换”的需求，而工具类型不过是把常见变换固化成可复用的别名。

理解这一点很关键。很多同学背下了 Omit 的签名 Omit<T, K extends keyof any>，却说不清第二个参数为什么是 keyof any 而不是 keyof T；也说不清 Omit 在带索引签名的接口上为什么会“丢东西”。本文的顺序是：先实现最简单的几个，把映射类型的机制讲透；再处理联合类型，引入分布式条件类型；然后走进递归与模板字面量类型；最后集中处理那些只有在真实项目里才会踩到的坑。

从映射类型开始：Partial、Required、Readonly

keyof 是这一切的起点。对任意对象类型 T，keyof T 得到一个由字面量类型组成的联合。它可以被索引访问 T['id'] 取回属性类型，也可以被约束 K extends keyof T 限定取值范围。这几个语法拼在一起，就是映射类型的全部机关：

映射类型的写法形似索引签名，语义却完全不同。索引签名描述“任意键都是这个类型”，映射类型则是把 T 的键逐个取出、加工、再组装成新对象。最典型的应用就是 Partial：

三个记号需要记住：? 增加可选，-? 移除可选，readonly 加只读，-readonly 去掉只读。它们只能出现在映射类型里，不能当作普通接口定义中的“变量开关”。写 -? 的时候不要漏掉减号，{ [K in keyof T]?: T[K] } 与 { [K in keyof T]-?: T[K] } 在报错信息里的差别很隐蔽，前者只会让某个字段“突然可选”，调用处不会报错。

这类写法有一个不显眼但极其重要的性质，官方文档称之为同态映射（homomorphic mapped type）。只要映射的键来源直接写成 keyof T，编译器就会把它识别为“对 T 的逐属性变换”，于是 T 上的修饰符会被自动保留。Partial<User> 之所以让 email 既可选、又保持 string | undefined 的读值类型，正是这个机制在起作用。反过来，一旦把键换成别的表达式，同态性质就丢了，修饰符不会被带过来。

同态性还解释了另一件事：Readonly 作用在数组或元组上，得到的是只读数组，而不是“把 length、push 变成只读属性”的怪东西。编译器对数组、元组、Map 这类内置结构有专门处理，这也是为什么手写一个“遍历 keyof T”的映射类型去处理数组，结果往往和 Readonly 不一致。

在 4.1 之前，映射类型只能保留原有键名。想按规则改名，只能手写接口或退回到字符串索引。这条限制在 2020 年 11 月被 as 子句打破，后面讲模板字面量类型时再展开。

挑与删：Pick、Omit、Record

Pick<T, K> 的意思是“从 T 里挑出 K 列出的键”。实现只需要两步：约束 K 必须是 T 的键，再用映射类型遍历 K 而不是 keyof T。

这里 K 是“键的联合”，映射类型遍历它；T[P] 是索引访问，取回原类型。K extends keyof T 既是约束也是校验：传 'age' 会直接报错，而不是静默产出一个空对象。这一点很重要，因为工具类型最常见的失效方式不是报错，而是“悄悄地算出一个过于宽泛的类型”。

Record<K, T> 是另一个方向的构造：

Record 是少数不依赖 keyof T 的工具类型，它把键的联合直接铺成属性。日常最常用的场景是“穷举映射”：用它配 keyof 可以强制每个键都有值，漏掉一个就报错。

Pick 不保留同态性，因为它的键来源是 K 而不是 keyof T。所以 Pick<User, 'email'> 得到的 email 依然是可选的，但这只是因为 T['email'] 本身就带 undefined，不是修饰符被继承。区分这两种情况，在排查“为什么某个字段突然可选”时很关键。

有人会用 as 子句重写 Omit：{ [P in keyof T as P extends K ? never : P]: T[P] }。它在 4.1 之后才可用，好处是保留同态性，代价是每次实例化都要对键做一次条件判断。官方库至今仍用 Pick 加 Exclude 的组合，性能是原因之一。

条件类型与 infer：从 Exclude 到 InstanceType

条件类型的形状是 T extends U ? X : Y。先别把它读成“类型层面的 if”，它更准确的语义是“T 是否可赋值给 U”。可赋值是子类型关系，判断比“相等”宽松：'a' extends string 为真，而 string extends 'a' 为假。理解这一点，才能预料到后面各种“为什么这里匹配上了”的意外。

分布式条件类型：联合类型被拆开的那一面

同一段 T extends U ? X : Y，当 T 是联合时，结果不是“整体判断一次”，而是“每个成员各判断一次，再把结果并起来”。这就是分布式条件类型（distributive conditional types）。

如果按“整体判断”理解，会以为得到 (string | number)[]。实际得到的是 string[] | number[]，两者并不等价：前者允许混装，后者不允许。这个差异在写“把联合映射成对象”的工具类型时会直接决定类型是否安全。

分布式的触发条件很窄，三条必须同时满足：T 是裸露的类型参数、条件类型直接作用在 T 上、实例化时 T 是联合。一旦给 T 套上任何包装，分布式立即关闭：

方括号把联合“包”成一个整体再判断，分发就没有了。这是控制分布式行为的开关，社区里常写成 [T] extends [U]。同样的道理，左侧写成 T & {} 或 T[] 也会关掉分发。判断某段代码会不会分发，就看 extends 左边是不是光秃秃一个 T。

分布式有一个容易被忽略的边界：never 是空联合，对空联合做分发，结果是 never，而不是“每个成员的结果”。所以 Exclude<never, string> 是 never，ToArray<never> 也是 never。写工具类型时若发现某个分支“整段消失”，先检查传进去的是不是 never，其次检查是不是条件类型把联合拆散了。

分布式还有一个实用推论：它能天然处理“输入可能是单个值也可能是数组”的场景。T extends any[] ? T[number] : T 在 T 为联合时会对每个成员分别判断，数组成员被摊平成元素类型，非数组成员原样保留。很多库的 Normalize 类型就是这么写的，读源码时看到 extends any ? 这种“看起来什么都没判断”的条件，基本都是在利用分布式。

递归类型：DeepPartial 与 DeepReadonly

内置工具类型都只作用一层。Partial<User> 让 address 可选，但 address 内部的字段依然必填。深层配置对象、嵌套 DTO 都需要“递归地”应用同一个变换。

看起来够用，实际有两个问题。第一，函数也是 object，DeepPartial<() => void> 会把函数拆成属性映射，丢掉调用签名。第二，数组也是对象，会被拆成带数字索引的结构，length、push 这些成员的处理方式与预期不符。更稳的版本要先排除函数和数组：

DeepReadonly 同理，只是把 ? 换成 readonly。这里有个细节：readonly 只能加在属性上，所以必须走映射类型，不能像 Partial 那样用交叉类型拼出来。网上有些写法用 Readonly<T> & ... 逐层嵌套，遇到数组和元组就会出错。

递归不会无限展开。TypeScript 对递归类型实例化有深度限制，社区实测大约在 50 层上下（不同版本、不同结构会有出入，不要把它当成稳定常量）。超过之后编译器会报 Type instantiation is excessively deep and possibly infinite，而且这条错误一旦出现，往往会把整个文件里后续的类型检查一起带崩。这条提示说的是“类型系统算不下去了”，不是“业务代码有逻辑错误”，两者的处理方向完全不同。

Prev[D] 靠元组的索引访问做“减一”，D extends 0 是终止条件。到 0 之后不再访问 Prev[0]，递归停止，剩下的层级保持原样。这比“祈祷数据不要超深”可控得多，代价是签名变长，阅读者需要理解这套计数器。把 D 暴露成第二个类型参数还有额外好处：调用方可以按数据形状指定深度，而不是被迫接受一个全局常量。

第二种是“只递归到业务需要的深度”。树形结构通常只在编辑场景需要深层可选，列表展示用一层 Partial 就够，没必要为了统一而让所有地方都付出递归开销。第三种是干脆不递归：把深层类型写成显式接口。类型体操的收益是“少写重复”，如果递归带来的编译时间和报错可读性损失更大，显式写法反而更划算。

递归类型的报错通常指向最外层调用，而不是真正爆掉的那一层。定位时可以把深度参数临时调小，看错误在哪一层消失，再回推数据结构里最深的那个分支；也可以先把递归替换成一层映射，确认基础变换本身是对的。先排除“类型写错”，再怀疑“类型太深”，顺序反了会浪费很多时间。

最后一个陷阱：递归与分布式叠加会放大计算量。DeepPartial<A | B> 会对每个联合成员各跑一遍递归，成员一多，开销接近乘法关系。给递归类型加约束、缩小输入范围，比事后加 --skipLibCheck 有用得多，后者只是跳过了声明文件的检查，管不到你自己写的类型。

模板字面量类型：用 4.1 的语法改写键名

组合还会带来性能问题。类型检查不是免费的，每展开一层条件类型、每做一次联合分发，编译器都要付出计算。递归类型、大联合、模板字面量的笛卡尔积三者叠加，编辑器会明显卡顿，tsc 的耗时也会上涨。判断一段类型是否太重，可以看两个信号：编辑器里悬停要等一两秒才出提示；tsc --extendedDiagnostics 显示 Check time 异常增长。后者在 2021 年的 4.x 上已经足够好用，定位到具体文件后再逐个注释掉可疑类型即可。

控制手段是有优先级的。第一，能用简单映射就不用条件类型，Pick 比手写键过滤快，因为后者要遍历联合。第二，给泛型参数加约束，缩小候选范围，避免对 any 或超宽联合做展开。第三，把高阶类型的结果固化成具体类型别名，让编译器缓存住，而不是在几十个调用点反复推导。第四，必要时给递归设上限，前面已经示范过。

还有一个常被忽略的边界：type 与 interface 在展开行为上不同。接口是惰性求值的，类型别名往往在使用处展开。深层嵌套的别名在报错时会把整条展开链打出来，错误信息长达几十行；换成接口或加一层中间别名，报错会干净很多。TypeScript 4.2 对类型别名的保留做了改进，减少了不必要的展开，但这只是改善，不是可以依赖的保证。

最后一条经验关于命名。工具类型本身的名字由官方固定，自己写的变换应该用能读出语义的名字：NullableFields、WithId、DeepPartial 都比 T1、Util 好。类型报错是给人看的，名字是第一层文档。

工具类型还需要测试。类型层面的回归不会在运行时暴露，改一个 ? 就可能让几十个调用点悄悄变宽，而 tsc 一声不吭。3.9 引入的 // @ts-expect-error 让这件事可做：把期望报错的用法写进测试文件，编译通过即验证成功；一旦某天这段代码不再报错，注解本身会报“未使用的 expect-error”，回归立刻暴露。

IsEqual 用两个函数类型的可赋值性来判断“完全相等”，比直接写 extends 严格，能区分 any 与 unknown，也能区分可选属性与“值里带 undefined 的必填属性”。这种技巧在 4.x 时期被各类类型库反复使用，代价是它本身也要消耗编译时间，测试文件里不要堆上千条断言。

最后是一个取舍问题：不是所有重复都值得用工具类型消掉。两三个字段的接口，手写一遍比引入一个五层嵌套的类型更快读懂；只有当同一套变换在五个以上地方重复，或者它能强制保证一致性（比如从常量数组推导联合类型）时，抽象才划算。类型代码和运行时代码一样，抽象是有成本的，只不过账单开在编译期和同事的耐心上。

六个容易踩的坑

第一个坑：interface 与索引签名。对一个带索引签名的接口用 keyof，得到的是 string | number 而不是具名属性，Pick 之后所有具体字段都会消失：

Omit<Dict, 'count'> 的结果里既没有 count，也没有其他具名属性，只剩一个索引签名。原因是 Omit 走 Exclude<keyof T, K>，而 keyof Dict 是 string | number，'count' 本来就不在这个联合里，Exclude 什么也没删掉，Pick 又把整个 string | number 键铺了回去。这个结果不算错，只是不精确：类型系统无法表达“从字符串索引里挖掉一个键”。

第二个坑：可选属性与 undefined 不是一回事。开启 --strictNullChecks 后，{ a?: number } 的 a 读出来是 number | undefined，但那是“可以不写”；而 { a: number | undefined } 的 a 是必填的，只是允许显式写 undefined。Required<T> 只去掉 ?，不会把 undefined 从值类型里剔除：

如果业务上要“必填且非空”，得再叠一层 NonNullable，或者针对具体字段单独声明。这里没有银弹，取决于你想表达哪一种约束，写之前先想清楚调用方需要的是“必须提供”还是“必须有效”。

第三个坑：Omit 丢掉索引签名，也就是第一个坑的另一面。实践建议是：对带索引签名的类型，不要用 Omit 做字段裁剪，改用 as 子句的键过滤，或者直接写一个新接口。同理，keyof 遇到 any 会得到 string | number | symbol，遇到 { [k: string]: any } 会得到 string | number，不要指望它给出具体键名，类型系统在这里只能退化成宽泛的索引。

第四个坑：分布式条件类型在 never 上的行为。Exclude<never, string> 是 never，T extends any ? ... : ... 在 T 为 never 时整段消失。写“如果 T 是联合就分别处理”的工具类型时，记得用 [T] extends [never] 显式判空，否则输入为空联合时，你会得到一个凭空出现的 never，而报错位置离真正的原因很远。

第五个坑：把工具类型当运行时校验。Partial<User> 不会让 JSON 里的多余字段消失，Required<User> 不会在运行时检查字段是否存在，Readonly<T> 也拦不住 Object.assign。类型只在编译期存在，跨进程边界的数据必须做运行时校验。接口层直接用 as User 把未校验的数据塞进类型系统，是这类问题的典型来源。

第六个坑：Record 的键约束。Record<string, T> 与 { [k: string]: T } 等价，但 Record<'a' | 'b', T> 要求两个键都出现，少一个就报错。用 Record 做配置表时，如果键集合来自后端返回的字符串，Record<string, T> 会让任意键都合法，拼错的键也不会报错。想让拼写错误暴露，键类型必须是字面量联合，而这通常意味着要在代码里维护一份常量数组，再用 typeof arr[number] 取出联合。

这六个坑有一个共同点：类型系统给出的是“它能证明的东西”，不是“你以为它保证的东西”。工具类型只做结构变换，不理解业务语义，边界处的校验和断言仍然要人来写。

小结

本文从头实现了十来个内置工具类型，它们最终只归结为三种手段：用映射类型逐属性变换，用条件类型加 infer 做模式匹配，用 4.1 的键重映射改写键名。keyof 与索引访问是这两套手段共同的入口，理解 T[keyof T] 能取到值的联合，就能读懂大半的键过滤写法。三条暗线贯穿全篇：同态映射决定修饰符是否保留，裸类型参数决定条件类型是否分发，递归深度决定编译器还能不能算下去。写自定义工具类型时，建议先写一层并悬停确认展开结果，确认无误后再叠加递归或 as 子句；遇到 Type instantiation is excessively deep，先调小深度参数定位分支，而不是直接怀疑业务代码。类型是给人读的，可读性和正确性同等重要，超过三层嵌套就该拆名字了。
