TypeScript 类型体操：条件类型实战

本文属于《TypeScript 学习路线》第 32/74 篇
上一篇系列目录下一篇

条件类型是 TypeScript 类型系统里最像“编程”的一块：它让类型可以 if/else，可以按联合成员逐个分发，还可以配合 infer 从既有类型里“抠”出局部。很多开发者能看懂别人写的 T extends U ? X : Y，一旦要自己写却常常卡在分配律、infer 位置和递归边界上。本文从语法本质讲起，把条件类型拆成几个可复用的模式，再用几个在真实项目里反复出现的工具类型把写法串起来。

阅读本文只需要对泛型、联合类型、交叉类型有基本认识，熟悉 interface 与 type 的区别即可，不必提前掌握映射类型的高级用法；文中代码以 TypeScript 4.1 与 4.2 为基准，涉及模板字面量类型的地方会明确标注版本前提。

从一次类型建模的困境说起

假设我们有一组读取配置的函数，返回值可能是普通对象、数组，也可能被包在 Promise 里。为了让调用方拿到的类型和实际返回一致，最直觉的做法是给每个分支写一个重载，或者干脆返回 any。前者在组合一多就迅速膨胀，后者等于把类型安全直接扔掉。条件类型要解决的正是这类“结果类型随输入形状变化”的问题。

语法本身很短：T extends U ? X : Y。读法是“如果 T 可以赋值给 U，那么结果是 X，否则是 Y”。这里的 extends 既不是继承，也不是相等判断，而是可赋值性判断，这一点决定了后面几乎所有的行为：子类型会通过，never 可以赋值给任何类型，而两个结构相同但来源不同的类型也能互相赋值。

可以把条件类型的能力分成三层。第一层是判断，比如判断一个类型是不是数组、是不是函数；第二层是提取，借助 infer 从既有结构里拿出局部；第三层是变换，配合映射类型、模板字面量类型与递归，把整个类型重写成另一个形状。所谓类型体操，落到实处就是这三层能力的反复组合。

分配律：条件类型默认会拆开联合

裸类型参数才会分配

先看一个容易被忽略的例子。定义一个给字符串字面量加前缀的类型，传入 'a' | 'b' | 1，结果不是对联合整体的判断，而是 "str-a" | "str-b" | 1：每个成员都被单独判断了一次。原因在于：当被检查的类型是一个“裸”的类型参数时，条件类型会对联合的每个成员分别求值，再把各成员的结果合并成联合。这就是分布式条件类型（distributive conditional types）。

这个行为的动机是实用：Exclude、Extract 这类工具类型都依赖逐成员过滤。Exclude<T, U> = T extends U ? never : T 之所以能从联合里删掉指定的成员，正是因为 T 被拆开逐个比较，命中的成员变成 never，而 never 在联合里会被吸收掉。

分配律还有一个推论：如果传入的是 never，由于它是空联合，分布之后没有任何成员参与求值，结果直接就是 never。这解释了很多“为什么我的类型变成了 never”的疑问，它不是编译器的 bug，而是定义的必然结果。

什么时候应该阻止分配

有三类场景需要主动包裹。其一是整体判断，例如“这个联合是否全部满足某个约束”“这个类型是否是 never”。其二是需要把联合原样交给映射类型或 keyof，因为分配之后每个分支只能看到单个成员。其三是避免某个分支产生 never 之后被联合吞掉，导致结果看起来“什么都没剩下”。

反过来，当你想对联合逐个成员做变换时，就应该保持裸类型参数，不要习惯性地加元组。判断标准很简单：问自己一句“我是想处理每个成员，还是想处理这个联合本身”，答案决定了要不要加那对方括号。

infer：把类型当成可以解构的样本

infer 的本质是模式匹配

infer 只能出现在条件类型 extends 右侧的类型模式里，用来声明一个待推断的类型变量。它像正则表达式里的捕获组：左边给出一个带洞的结构，匹配成功就把洞里的实际类型绑定给变量，然后可以在 true 分支里使用。这个能力在 TypeScript 2.8 随条件类型一起引入，也是大量工具类型的起点。

理解 infer 的关键是把它当成“结构匹配”而不是“类型转换”。编译器拿实际类型去套模式，能套上就推断，套不上就走 false 分支。因此模式写得越具体，匹配范围越窄；写得越宽松，拿到的类型越模糊。

infer 出现在逆变位置会得到交叉

同一个类型变量如果在多个逆变位置被推断，编译器会把候选类型求交，而不是求并。这个反直觉的规则是 UnionToIntersection 的基础，后文实战部分会展开。先记住结论：协变位置（返回值、属性）推断出联合，逆变位置（函数参数）推断出交叉。

infer 与联合的交互

如果被匹配的类型是联合，而条件类型又是分配式的，那么 infer 会在每个成员上分别推断，最终结果是各分支结果的联合。例如从 (() => string) | (() => number) 中提取返回值，得到的是 string | number。如果希望只匹配其中某一种，需要先用元组或额外的筛选条件把范围收窄，否则很容易得到一个比预期宽得多的联合。

递归条件类型与终止条件

递归条件类型的写法并不神秘：在条件类型的某个分支里再次引用自己。真正需要设计的是终止条件。一个能收敛的递归类型通常具备三个特征：存在一个不再递归的基础分支、每次递归的输入严格变小、递归深度在编译器可接受的范围内。

Flatten 的终止分支是“不再是数组”，DeepReadonly 的终止分支是“不是对象”。两者都保证了输入在每一层被消耗掉一部分。反过来，如果递归调用的实参与入口类型相同，或者只是在外层包了一层新结构，编译器就会一直展开下去。

TypeScript 4.1 对递归条件类型做了两项改进：一是放宽了此前对递归类型别名的限制，允许类型别名在条件类型中直接引用自身；二是对处于尾递归位置的递归做了优化，使得像 UnwrapPromise 这种“每次只剥一层、递归调用就是整个分支结果”的写法可以处理更深的嵌套。需要强调的是，这个优化只覆盖尾位置，而且不改变“类型检查有成本”的事实。如果在递归结果外面再套一层模板字面量或元组，优化就失效了，深度稍大仍会报 Type instantiation is excessively deep and possibly infinite。

模板字面量类型：把字符串当结构来解析

4.1 带来的字符串能力

TypeScript 4.1 引入了模板字面量类型。它允许在类型位置使用反引号拼接字符串，并在 ${} 中放入类型；当放入的是 infer 时，就变成了对字符串的模式匹配。同一版本还提供了 Uppercase、Lowercase、Capitalize、Uncapitalize 四个内在工具类型，用于处理大小写。

这套能力让编译器第一次能理解“字符串是有协议的”。路由路径、事件名、CSS 属性名、i18n key 本质上都是带结构的字符串，过去只能靠运行时校验或手写联合类型，现在可以在类型层解析并生成。

联合转交叉：合并插件注入的上下文

推导过程分两步。第一步利用分配律，把联合的每个成员包装成一个只接收该成员参数的函数类型，得到一个函数联合。第二步用 (arg: infer I) => void 去匹配这个函数联合，由于参数位置是逆变的，I 必须同时满足所有候选，推断结果就是它们的交叉。中间件、插件系统里常把多个模块声明的上下文合并成一个对象，用的就是这一招。

string & K 不是多余的：keyof T 的结果可能是 string | number | symbol，而模板字面量只接受前两者，交叉一下既满足约束，也把 symbol 键过滤掉了。键重映射还能用来做排除，把 as 写成条件表达式，返回 never 的键会在结果里消失，这比先 Omit 再映射少一层嵌套。

可读性：类型也是要维护的代码

类型体操最容易滑向的境地，是写出一个能通过编译、但除了作者没人敢改的类型。可读性和正确性一样重要，下面几条经验在团队协作里尤其有效。

第一，给每一层起名字。把嵌套三层的条件类型拆成三个有语义的别名，错误信息会指向具体的别名，而不是一长串无法阅读的表达式。别名本身就是文档，UnwrapPromise 比 T extends Promise<infer V> ? ... 更能说明意图。

第二，用 extends infer 固定中间结果。当同一个表达式要在多个分支里重复使用时，先把它绑定到一个变量，既避免重复求值，也让逻辑更接近普通的命令式代码：

第三，控制嵌套深度。超过三层的三元表达式，人眼已经很难跟踪括号的归属。此时应该拆成多个类型别名，或者把判断顺序重新排列，让最常见的分支先返回。类型系统没有 if/else if 的语法糖，但命名良好的别名可以起到同样的作用。

第四，给工具类型写注释和示例。类型别名旁边的 // { a: string } 这样的结果注释，价值不亚于函数上的文档注释。半年后回来修改的人，靠的就是这几行示例判断行为有没有变。

最后一条是克制。不是所有约束都值得放进类型系统。把一条业务规则编码成类型，意味着以后每次规则调整都要同步修改类型，并且可能引入难以定位的编译错误。判断标准是：这条规则是否稳定、是否在编译期就能确定、出错时是否会造成严重后果。三个答案都是肯定，才值得动用类型体操。

命名上也可以形成约定：处理“一层”的工具用原名，递归处理所有层级的加 Deep 前缀，负责解包的用 Unwrap 前缀，只做筛选的用 Extract 或 Filter。这套约定不能强制，但当团队里所有人都按同一套词根命名时，阅读陌生类型的成本会明显下降。

调试与性能：让编译器把话说清楚

类型错误的信息往往很长，但真正有用的部分只有几处。先看错误码：Type instantiation is excessively deep and possibly infinite 基本可以断定递归没有收敛或者深度超限；Type 'X' is not assignable to type 'never' 通常意味着某个分配分支被算成了空联合；Property 'x' does not exist on type 'never' 则说明前面的判断把一个本该有值的类型收窄成了 never。

定位问题时，最有效的办法是把大类型拆小，逐个断言。给中间结果起一个别名，把鼠标悬停在别名上，就能看到编译器实际算出的类型，而不是最终报错处那个被层层包装的结果。如果悬停只显示别名而不展开，可以用一个“强制展开”的小工具：

另一个常被忽略的工具是编辑器本身。TypeScript 语言服务在悬停、跳转定义、查找引用时都会展示类型的展开结果，把复杂的类型拆成多个别名之后，这些功能才真正可用。命令行下可以用 tsc --noEmit 确认整体类型检查是否通过，用 tsc --diagnostics 观察检查耗时，判断最近的类型改动是否让整个项目变慢。

性能方面，需要建立一个基本认知：类型检查不是免费的，而且它在编辑器里是持续运行的。一个递归映射作用在两百个属性的接口上，每次按键都可能触发重新求值。可以采取的优化包括：限制递归深度、避免在大联合上做笛卡尔积、把稳定的计算结果固化成手写的联合类型而不是每次推导、以及在 tsconfig.json 里开启 skipLibCheck 跳过第三方声明文件的检查。

关于尾递归优化，4.1 之后确实让一些深层递归变得可行，但它只对尾位置的递归生效，并且不同编译器版本的优化范围可能有差异。把“能跑通”当成“可以放心用”是危险的，尤其是当类型来自用户输入或第三方数据、深度不可控的时候。比较稳妥的做法仍然是显式设置深度上限，在超限时退回到宽松类型，让类型系统在“精确”和“可用”之间保持平衡。

常见坑

never 是空联合，不是“什么都没有的类型”

never 表示不可能出现的值，在联合运算里它会被吸收，在条件类型里它是空联合。这带来两个后果：Exclude<'a', 'a'> 的结果是 never，而映射一个 never 会得到空对象 {}，不是报错。很多“类型莫名其妙消失了”的问题，源头都是某个分支算出了 never。判断时应写 [T] extends [never]，不要写 T extends never，后者对裸类型参数会分布成 never，永远进不了 true 分支。

any 同时扮演两个角色

any 在条件类型里表现得像“两边都成立”。any extends string ? 1 : 2 的结果是 1 | 2，因为 any 与任何类型都兼容，编译器无法排除任何一个分支。另一方面，T extends any 恒为真，用它是判断不出“是不是 any”的。常见的检测手段是利用交叉的吸收性质：

这类技巧说明了 any 的危险：它会静默穿透整个条件类型链，让精心设计的约束失效。对外部输入建模时，入口处就应该把 any 收窄成 unknown 或具体类型，不要让它在类型体操里流转。

unknown 不是 any 的简单替代

两者都能接收任意值，但行为完全不同。T extends unknown 恒为真，因为所有类型都可以赋值给 unknown；unknown extends T 只在 T 为 unknown 或 any 时为真，常用于“是否是顶层未知类型”的判断。用 unknown 接收数据之后，必须先做类型收窄才能访问属性，这正是它比 any 安全的地方。把库的泛型默认值从 any 改成 unknown，往往能立刻暴露出一批未经校验的访问。

可选属性会悄悄改变判断

{ a?: string } 与 { a: string } 在结构上不相等。前者不能赋值给后者，所以 T extends { a: string } 对带可选属性的类型会走 false 分支。同时，T['a'] 在开启严格空值检查时是 string | undefined，条件类型里如果没考虑 undefined，就会出现“明明有值却匹配不上”的情况。处理可选属性时，映射类型里的 -? 可以去掉可选修饰，Required<T> 只处理第一层，嵌套结构仍需自己递归。

分布式条件类型与 keyof 的组合

这是一个非常隐蔽的坑：keyof (A | B) 得到的是两个类型的公共键，而分配式的条件类型会让 keyof 分别作用于每个成员：

想要“联合中任一成员出现过的键”，需要用分配式写法；想要“所有成员共有的键”，就直接 keyof。两者语义相反，写反了不会报错，只会在使用处出现难以理解的赋值失败。

宽泛类型会让递归静默失败

递归条件类型遇到 string、number 这类宽泛类型时，往往不会报错，而是提前命中某个分支并返回一个错误的结果。例如把 BuildTuple 用在 number 上，T['length'] extends number 立刻成立，函数直接返回空元组，加法结果变成另一个加数本身。模板字面量的递归也一样，CamelCase<string> 会原样返回 string，看起来“没坏”，实际上什么也没解析。给这类工具加类型参数约束只是第一步，更重要的是在实现里显式处理宽泛类型，让失败变得可见，而不是悄悄返回一个看似合理的值。

还有一个只读修饰的坑：readonly string[] 不能赋值给 string[]，因此 T extends (infer E)[] 对只读数组会走 false 分支。写通用工具类型时，数组通常要匹配两次，先用 ReadonlyArray<infer E> 接住只读数组，再处理可变数组；否则从 as const 或只读接口传进来的数据会莫名其妙地落到 never。

小结

条件类型的核心只有一条规则：T extends U ? X : Y 判断的是可赋值性，裸类型参数会自动对联合分发，需要整体判断时用元组包裹。infer 把类型当作可解构的样本，函数参数、返回值、数组元素、Promise 内层、元组首尾都能按位置提取；递归则要先把终止条件和深度上限设计好。4.1 的模板字面量类型让字符串协议进入类型系统，配合键重映射可以生成路由参数、事件名和样式对象的类型。真正决定这些技巧能否落地的，不是写得有多复杂，而是可读性、性能和边界处理：给中间结果起名、给递归设上限、对 never、any、可选属性和宽泛类型保持警惕。建议从项目里一两个稳定的约定开始试用，确认维护成本可接受之后，再逐步扩大范围。
