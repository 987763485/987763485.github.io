TypeScript 类型安全的后端接口

本文属于《TypeScript 学习路线》第 40/74 篇
上一篇系列目录下一篇

后端接口的类型安全，最容易在三个地方漏水：请求体从网络进来时是 unknown，处理器里被随手断言成 DTO，响应又在序列化时悄悄变了形状。本文沿着「类型从哪里来、在哪里断掉、怎么补上」这条线，比较手写 DTO、运行时校验推导、从契约生成这三类做法，再讨论 zod 与 io-ts 的建模差异和 tRPC 这类端到端方案。读完你应该能为一个中等规模的 Node 服务选出一套可落地的类型方案，也知道它的边界在哪里。

接口类型的三处来源

一个 HTTP 接口的形状，由三块拼成：路径参数、查询字符串、请求体，再加上返回的响应体。这几块类型从哪里来，直接决定了它们能信几分。工程上常见的做法只有三类，各自的代价并不相同。

手写 DTO。最直觉的方式是定义 interface CreateUserBody { name: string; age: number }，然后把它标在处理器参数上。类型写得快，读起来也清楚，但它和运行时没有任何契约关系：编译之后类型被擦除，req.body 依旧是 any，谁都可以传一个 age: "十八" 进来。手写 DTO 的价值在于描述「我们期望什么」，不在于保证「我们收到什么」。它适合内部调用、已经被上游保证过的数据，或者作为生成结果的补充。

运行时校验推导。先写一个能在运行时执行的 schema，再从 schema 反推静态类型。zod、io-ts、class-validator 都属于这一类。它的好处是单一事实源：校验规则和类型声明是同一份代码，改一处两边同时生效，不会出现「类型说必填、校验说可选」的分裂。代价是要多写一层声明，而且 schema 本身也有类型，写错了照样能过编译。

从契约生成。当接口文档（OpenAPI、JSON Schema）或数据库表结构已经存在时，可以反过来生成类型。前端从 OpenAPI 生成客户端类型，后端从数据库 schema 生成实体类型，这类工具在 2021 年前后已经相当成熟。它适合已有契约、多方对接、或者以数据库为中心的系统。缺点是生成物与实现之间没有强制同步，文档一漂移，类型就成了过期的地图。

把三者放在一起比较，差别其实只有两列：类型什么时候确定，以及运行时有没有人把关。

来源 类型何时确定 运行时是否校验 主要成本
手写 DTO 编译期 否 与实现漂移，靠人守
运行时校验推导 从 schema 推导 是 多写一层声明
契约生成 生成时 需额外接中间件 文档与实现漂移

三类做法并不互斥。一个常见的组合是：请求体用运行时校验推导，响应体用生成的实体类型裁剪，路径与查询参数手写少量常量。真正的分界线不在于选哪种，而在于你是否清楚「这份类型在哪一层被验证过」。类型系统只在编译期工作，网络边界上的数据永远是不可信的，这句话是后面所有讨论的前提。

端到端类型能走多远

所谓端到端类型，是指同一份类型定义同时约束服务端的处理器和客户端的调用点。改了服务端的字段名，客户端在编译时就会报错，而不是等到线上返回 undefined 才发现。这个目标很诱人，但先要看清它到底保证了什么。

从服务端到客户端，类型有两条传递路径。一条是代码生成：把类型写进 .d.ts 或生成一个客户端 SDK，通过 npm 包或相对路径引用。另一条是直接引用：客户端用 import type 拿到服务端的路由类型，由 TypeScript 自己算出每个调用的入参与返回值。前者跨语言、跨仓库都能用，代价是每次改动都要重新生成；后者零生成、改完即生效，但要求前后端在同一个 TS 工程或 monorepo 里。

sequenceDiagram
  participant C as 客户端
  participant R as 路由层
  participant V as 校验器
  participant H as 处理器
  C->>R: 请求（类型已知）
  R->>V: 解析 path/query/body
  V-->>R: 失败则返回错误联合
  V->>H: 收窄后的入参
  H-->>C: 响应（类型已知）

图里那条「类型已知」的箭头，只覆盖了编译期。运行时真正发生的事是：字节流被 JSON.parse 成一个 any，然后被某个函数断言成期望的形状。端到端类型能保证的是「形状一致」，不能保证「内容正确」。字段叫 age、类型是 number，但值可以是 -1；枚举值在白名单里，但业务上这个状态不该出现；响应符合类型，但权限判断写错了。这些都属于语义，类型系统管不到。

还有几处边界容易忽略。跨语言时类型传递会断掉，Go 服务给 TS 客户端只能用生成的方式，生成器对 oneOf、nullable、递归结构的处理各有偏差。版本偏移时类型会撒谎：客户端还是旧版本、服务端已经加了必填字段，编译期一切正常，运行时 400。JSON 本身也有信息损失，Date 变成字符串，undefined 在序列化时被丢弃，Map 和 BigInt 根本无法表达。端到端类型是一条很有效的防线，但它防的是「写错名字」，不是「传错值」。

既然类型保证不了内容，校验应该放在哪里就有了讲究。全部压在路由层，领域层就默认所有入参都干净，一旦有别的入口（定时任务、消息队列、内部 RPC）复用了同一段逻辑，假设立刻失效。全部下沉到领域层，又会让 HTTP 层的错误信息丢失上下文，用户看到的只是一句「参数错误」。比较稳妥的分工是：HTTP 边界做形状校验，把 unknown 变成有类型的对象；领域层入口做业务校验，比如余额是否足够、状态是否允许迁移。前者用 schema，后者用普通的判断加领域错误，两者职责不同，不要混在一处。

与之配套的是契约测试。拿一组真实的请求与响应去跑 schema，确认「文档、校验器、实现」三者说的是同一件事。这类测试写起来不复杂，却能拦住大部分漂移，尤其是在接口被多人维护的项目里。

用 zod 把校验与类型合成一件事

zod 的思路很直接：schema 既是运行时的校验器，也是类型层面的值。写一次声明，parse 时用它检查数据，z.infer 时用它取出静态类型。

z.infer 做的是把 schema 的类型参数取出来，得到的结果就是 parse 成功之后的类型。这里有一个容易被忽略的细节：带 transform 的 schema，输入类型和输出类型并不相同。比如 z.string().transform(s => new Date(s))，进来的是字符串，出去的是 Date，而 z.infer 取的是输出。请求侧尤其要留意，因为查询参数永远是字符串。

parse 失败会抛出 ZodError，safeParse 则返回 { success: true, data } 或 { success: false, error } 的联合。在 HTTP 边界上建议统一用 safeParse，把失败转成结构化的校验错误响应，而不是让异常穿过层层中间件。zod 的错误对象带 path，能直接定位到 body.items[2].price 这种深层位置，拼进错误体几乎不用额外处理。

还有一个开关值得知道：z.object 默认会剥掉未声明的键，要拒绝多余字段得显式调用 .strict()。写接口时我更倾向严格模式，因为客户端多传一个字段，往往意味着它按另一版契约在调用，早报错比默默忽略好。跨字段的约束用 .refine() 表达，比如结束时间必须晚于开始时间。

校验失败的反馈方式也需要设计。zod 默认会收集对象下所有字段的问题，而不是遇到第一个就停，这对表单类接口很友好：一次请求就能告诉调用方哪几个字段不合格。但 message 是写给开发者看的英文短语，直接透给终端用户并不合适。可行的做法是保留 path 与错误类型，由客户端或一层映射表翻译成面向用户的文案，服务端只保证结构稳定。把这个约定写进错误体，前端的展示逻辑就不用为每个接口单独适配。

最后一条原则：不要反向操作。先有 interface 再补一份 schema，等于维护两份声明，早晚会分叉。如果 DTO 已经存在且不能改，可以用 z.ZodType<CreateUserBody> 去约束 schema 的推导结果，让编译器替你检查两者是否同步，这比人工比对可靠得多。

io-ts 的编解码模型

同样是「用运行时的值推导类型」，io-ts 走的是另一条路。它把 schema 称作 codec，编码与解码是一对互逆的函数，校验失败不抛异常，而是返回一个 Either。

两者最直观的差别在错误模型。io-ts 的 decode 返回 Either<Errors, A>，调用方必须显式处理左右两支，配合 fp-ts 的 fold 或 isRight 使用；zod 则给了「抛异常」和「返回结果对象」两种风格，习惯 try/catch 的团队上手更快。io-ts 的 Errors 是结构化的数组，PathReporter 只是其中一种呈现方式，想输出自定义错误体需要自己遍历；zod 的 issue 天生带 path 与 message，直接映射成 API 错误更省事。

第二个差别是编解码的方向性。io-ts 的 codec 概念上是双向的，decode 把外部数据变成领域对象，encode 再变回去，配合 io-ts-types 里的 DateFromISOString 这类组合子，可以很自然地把 ISO 字符串和 Date 对应起来。zod 用 transform 也能做同样的事，但它的管道感更强，通常是单向的：入站校验加转换，出站再写一个函数。对多数后端来说只用到 decode 一个方向，这个差别不影响选型；当出站数据也需要严格变换时，双向模型会更整齐。

第三个差别是生态与心智负担。io-ts 与 fp-ts 绑定较深，类型签名里经常出现 TypeC、Mixed、Kind 这些词，没接触过函数式编程的同事读起来会卡。zod 的 API 更平，链式调用接近直觉。2021 年初的新项目选 zod 的明显更多，存量项目里 io-ts 仍有大量使用，尤其是已经引入 fp-ts 的代码库。选型的实际标准不是谁更先进，而是团队里能不能有人看懂报错。

请求、响应与错误的统一建模

先约定响应信封。我的建议是成功时直接返回数据，失败时返回统一错误体，而不是所有响应都包一层 { code: 0, data }。HTTP 状态码已经表达了成败，再包一层业务码，两套语义迟早会打架：状态码 200 而业务码 500 的响应，监控和网关都无从判断。

错误种类要克制。有的团队把「用户不存在」「密码错误」「账号被锁」拆成三种错误，看似精确，实际给客户端增加了大量分支，也让攻击者能据此枚举账号。对外只暴露少数几类，把细节写进日志和 traceId，是可维护性与安全性之间的平衡点。另外，同一个 kind 在不同接口里应保持同样的语义与状态码，不要让客户端去记「这个接口的 conflict 是 409，那个是 422」。

响应侧也值得做一次出站校验。开发环境里对返回值再 parse 一遍，能抓住「类型写着 Date、实际返回字符串」这类漂移；生产环境可以关掉或采样。成本很低，收益是把问题暴露在服务端日志里，而不是等客户端报错再来排查。

分页、排序、过滤这三个参数族，各有各的陷阱。

分页有两种形态：page/pageSize 适合后台列表，cursor/limit 适合信息流，后者在数据频繁插入时不会重复或漏项。无论哪种，pageSize 都必须有上限，否则一个 pageSize=100000 就是一次全表扫描加一次巨大的序列化。查询参数到手时是字符串，必须显式转换并校验，不能指望框架帮忙。

排序的字段名绝不能让客户端自由拼接。用 z.enum(['createdAt', 'name', 'score']) 限定白名单，方向用 z.enum(['asc', 'desc'])，拼 SQL 时再查一张映射表，绝不能把字符串直接塞进 ORDER BY。这一条既是类型问题，也是注入问题。

还有一个细节值得强调：校验之后的 params、query、body 只应该存在于这次调用的闭包里。如果把它们写回 req.body 供下游使用，就等于又制造了一个「声明与事实可能不符」的位置。传参比改 req 安全。

校验顺序也影响体验。路径参数最便宜，且决定了资源是否存在；查询参数次之；请求体最大，解析成本最高。先校验便宜的、再解析贵的，能在明显非法的请求上省掉一次无用的 JSON 解析。至于「资源不存在」返回 404 还是 403，取决于是否愿意暴露资源的存在性：对公开资源用 404 更安全，对协作型后台用 403 更利于排查。这类决定不是类型问题，但会体现在错误联合的设计里，值得在写第一版时就定下来。

服务端也可以反向利用契约。用 express-openapi-validator 之类的中间件按文档校验请求，等于把文档变成了运行时防线；或者反过来，从 zod schema 生成文档片段，让代码成为事实源。两条路选一条，不要两边都手写，否则又回到两份声明迟早分叉的老问题。

生成物有几处偏差需要提前知道。OpenAPI 3.0 用 nullable: true 表达可空，而不是 type: ['string', 'null']（后者是 3.1 的写法），不同生成器对它的处理并不完全一致；additionalProperties 缺省时并不等于「不允许额外字段」；oneOf 与 anyOf 生成后常常退化成联合或交叉，语义有损失；枚举值一旦增删，生成的联合类型会让所有未处理的 switch 报错，这既是保护，也是迁移成本。

最大的风险仍然是漂移。文档说 age 是整数，实现返回了字符串，生成器无从得知。契约需要测试兜底：拿真实响应去校验文档，或者至少在 CI 里对文档变更做提醒。没有测试的契约，只是另一份会过期的注释。

数据库侧的生成是同一思路的另一个入口。Prisma 2 会从 schema 生成精确到列的类型，TypeORM 的实体也能反推出属性类型，省掉了手写实体接口的功夫。但生成的实体类型是「存储形状」，不是「接口形状」，两者经常差得很远：实体里有 passwordHash、deletedAt、内部自增主键，这些都不该出现在响应里；实体里的关联关系是嵌套对象，接口往往只需要一个 authorId。

tRPC：不要生成，直接引用

2021 年初，tRPC 提供了第三条路线：不生成任何东西，客户端直接 import type 服务端的路由类型。它的做法是把每个过程的输入、输出、错误都编码进一个巨大的泛型对象，客户端调用时由 TypeScript 递归解析。下面是与当时版本接近的示意（早期 API 的签名随版本略有差异，思路一致）：

这条路线省掉了代码生成、DTO 同步和 SDK 发版。改一个字段名，客户端立刻飘红；给某个过程加上 input 校验，调用点的参数类型同步变化。对长期被「接口文档和实现两张皮」折磨的团队，吸引力很大。

代价是前提很硬。前后端必须同语言、同仓库，或者至少能引用到同一个类型包；构建工具要能处理跨包的 import type，否则类型解析会明显变慢。类型是编译期的，因此客户端与服务端必须一起构建、一起发布，这在单体应用里是常态，在前后端独立发版的团队里就成了障碍。

限制也要说清楚。它只适合自有前端调自有后端，公共 API、移动端、第三方对接都不适用，因为这些场景里类型根本无法传递。部署不同步时类型会撒谎：客户端编译时认为字段存在，服务端还是旧版本，编译期一路绿灯，运行时照样失败。错误形状也得团队自己约定，框架只保证你声明的输入输出，业务错误码仍要设计一套可辨识联合。路由嵌套很深时，编辑器的类型检查会明显变慢，2021 年初的工具链对此还没有太好的优化手段。

笔者的判断是：小团队、单体仓库、迭代频繁的内部后台，收益最大；对外暴露的接口，还是老老实实写契约。tRPC 不是「更好的 REST」，它是一套把类型共享做到极致、同时把适用范围收窄的取舍。选它之前先问一句：三个月后，前端还会和后端在同一个仓库里吗。

常见坑与版本演进

any 泄漏。req.body、JSON.parse 的返回值、res.json() 的参数，在多数类型定义里都是 any，一旦赋给变量就顺着调用链扩散，后面所有的字段访问都不再有检查。TS 4.0 起 catch 子句的变量可以显式标注为 unknown，这是个好习惯；更通用的原则是让所有外部值先落到 unknown，再由 schema 收窄。noImplicitAny 只能拦住没写的 any，显式写出来的 any 要靠 lint 规则和代码评审。

类型断言绕过校验。req.body as CreateUserBody 是最常见的写法，也是把整套体系打回原形的写法。as unknown as T、非空断言 !、@ts-ignore 同理。断言本身不是错，错在把它放在边界上：边界处应该出现的是 parse，不是 as。评审代码时看到 as，就问一句「这里的运行时保证来自哪里」，答不上来就是隐患。

可选字段与 null。? 表示键可以不存在，null 表示键存在但值为空。数据库的可空列对应 null，对应不到 undefined；JSON 序列化会把 undefined 整个丢掉，null 则会保留。接口里最好只用一种方式表达「没有值」：本文的建议是响应里用 null，请求里用「不传」，schema 上分别写 .nullable() 与 .optional()。两者叠加写成 .optional().nullable() 看似周全，实际让调用方多了一种需要判断的状态。

日期序列化。类型写 createdAt: Date，JSON 里实际是 "2021-03-22T00:48:34.000Z"。客户端拿到字符串却以为是 Date，调 .getTime() 就在运行时炸。两种解法：DTO 里统一用 ISO 字符串，需要时再转；或者在 schema 里用 transform，入站转成 Date，出站再转回字符串。选一种并在全项目贯彻，不要一半接口给字符串、一半给时间戳。

枚举演进。字符串枚举比数字枚举更适合接口，因为数字枚举有反向映射，值也可能因为插入成员而漂移。但新增枚举值依然是破坏性变更：老客户端不认识新值，switch 走不到对应分支。客户端要有兜底分支，服务端不要在同一个字段上复用含义不同的值。数据库里存字符串还是整数，也要和接口层的表达分开考虑，别让存储格式牵着契约走。

错误被吞。空 catch {}、忘记 await 导致的 unhandled rejection、已经 res.json() 之后又调用 next(err)、错误体里带上堆栈和 SQL 语句，这些都是线上排障的噩梦。统一错误中间件要保证三件事：每个错误都有可检索的 traceId，日志里记录完整上下文，响应里只给必要信息。

版本演进。TypeScript 4.1 引入了模板字面量类型和 noUncheckedIndexedAccess，4.2 引入了 noPropertyAccessFromIndexSignature，这类编译开关会改变既有代码的类型判定。升级时最好一次只开一个，单独提交、单独修，别和业务改动混在一起。接口本身的兼容性原则很朴素：加可选字段安全，加必填字段破坏，删字段、改字段类型、改枚举含义都是破坏性变更。客户端要能容忍未知字段，服务端要保留旧字段至少一个大版本，中间用灰度验证。

小结

接口类型的三处来源各有取舍：手写 DTO 快，但管不住运行时；运行时校验推导能做到单一事实源；契约生成适合已有文档或数据库的系统。真正决定成败的不是选哪个库，而是把校验放在边界上、让类型从校验结果流出来，而不是用断言把类型按在数据上。zod 与 io-ts 的差别在错误模型和函数式程度，选团队读得懂的那个即可。端到端类型能防写错名字，防不了传错值，跨语言、跨仓库、部署不同步这三处边界要提前设计。最后，分页排序过滤、错误联合、日期与枚举这些细节，才是接口类型在长期维护中最容易腐烂的地方。
