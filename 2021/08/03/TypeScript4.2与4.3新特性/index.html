TypeScript 4.2 与 4.3 新特性

本文属于《TypeScript 学习路线》第 47/74 篇
上一篇系列目录下一篇

TypeScript 4.2 于 2021 年 2 月 23 日发布，4.3 于同年 5 月 26 日发布，到本文写作时两者都已进入稳定版本，可以放心用于生产项目。本文不打算逐条复述发布公告，而是把两个版本中真正影响日常编码的部分挑出来，说明它们各自解决了什么问题、升级时会触发哪些编译错误，以及怎样把这些能力分阶段引入既有仓库。

阅读本文需要熟悉 TypeScript 的基础类型系统和 tsconfig.json 的常用选项。文中示例均以 strict 为前提，命令行的写法以 npm 安装的本地 tsc 为准。如果你正在维护一个从 4.1 甚至更早版本升级过来的项目，可以直接跳到最后一节看升级顺序，再回头查阅具体特性。

版本坐标与升级的起点

先把升级成本和节奏摆清楚。两个稳定版相隔三个月，中间没有破坏性的语言变更，因此从 4.1 升到 4.3 可以一次完成，也可以分两步走。TypeScript 4.4 预计本月晚些时候发布，不在本文范围。

两个版本的侧重点并不相同。4.2 更像一次表达力与可观测性的更新：类型别名在更多场景下保持原样，元组允许剩余元素出现在开头和中间，抽象类可以写成构造签名，另外补上了两个诊断开关，帮助我们在大型仓库里定位问题。4.3 则偏向类与继承的契约：override 让覆写变成显式声明，#private 把私有成员推进到运行时，static 索引签名补齐了静态侧的类型描述，构造参数类型也能作用于抽象类。

升级前建议做三件事。把 typescript 固定到具体版本，而不是留在 ^ 范围里；确认 @types/node 等类型包与编译器版本匹配；在 CI 中保留一份 tsc --noEmit 的基线输出，方便对比新增错误。下面按版本展开，每节都给出可复现的示例与对应的编译错误。

更智能的类型别名保留

在 4.2 之前，编译器对类型别名的处理偏保守。当别名指向一个由多个对象类型组成的联合时，错误信息、编辑器悬停和声明文件里经常出现完全展开后的结构，原本一行能读懂的别名变成了好几屏的字面量。4.2 调整了这条规则：在把别名赋给联合或交叉类型的场景里，编译器会尽量保留别名本身。

这个改动只影响类型的显示与声明文件输出，不改变任何类型检查结果。它的价值在于可读性：团队约定好的 UserId、JsonValue 这类别名不会在报错时被拆散，代码评审时 .d.ts 的差异也更小。需要注意，保留是有条件的，编译器仍会在某些需要结构比较的位置展开别名，因此不要把它当作稳定的对外契约。如果库的声明文件对类型展示有严格要求，升级后应重新检查 tsc --declaration 的产物，而不是假设输出与旧版逐字一致。

4.2 的元组、构造签名与诊断开关

元组类型在 4.0 引入可变元组后已经能表达“任意长度的参数列表”，但剩余元素被限制在最后一位。4.2 放宽了这条限制：一个元组里仍然只能有一个剩余元素，但它可以出现在开头或中间，只要剩余元素后面不再跟可选元素或第二个剩余元素。

在 4.1 及更早版本中，上面两个别名都会报“剩余元素必须是元组的最后一个元素”。这条限制解除后，包装函数、参数拼接和类型层面的“取尾部”都更容易表达。例如给一组参数统一补上结尾的请求标识，可以直接写成 [...Args, string]，而不必为每种长度单独声明。使用时仍要守住两条边界：剩余元素最多一个，且它后面不能出现可选元素，否则编译器无法确定元组长度。

同一版本还补上了抽象类的构造签名。在此之前，类型系统无法描述“某个类，可能是抽象的”，库作者只能用 Function 或具体构造器来近似，调用方往往要加断言。

abstract new 只出现在类型位置，它描述的是“可被继承、不可被直接实例化”的构造器。把它用作参数类型后，依赖注入容器、插件注册表这类只负责保存构造器、稍后才决定如何实例化的代码，就能准确表达意图。若在函数体内直接 new Ctor()，编译器会提示不能实例化抽象类，这正是我们想要的保护。

除了类型表达力，4.2 还补了两个诊断开关。第一个是 --noPropertyAccessFromIndexSignature。索引签名会让任意属性名都通过检查，点号访问于是成了拼写错误的温床：写错一个键，类型系统只会返回索引签名的值类型，错误要等到运行时才暴露。打开该选项后，点号访问只对显式声明的属性生效，来自索引签名的键必须用方括号读取。

这个选项刻意没有并入 strict。它约束的是书写风格，而不是类型安全本身，所以官方把它留作团队自行决定。对于大量读取 process.env 或配置字典的项目，开启后能立刻发现若干拼写问题，但也会让一批原本合法的点号访问变成错误，建议在专门的一次提交里集中处理。

第二个开关是 --explainFiles，它不改变检查结果，只是让编译器交代每个文件为什么进入编译单元。

输出会标明某个文件是被 include 匹配进来的、被谁 import 的、由 reference 引入的，还是来自默认库与 @types。当构建越来越慢、或者出现两份同名类型互相冲突时，这个开关比盲目翻 tsconfig.json 高效得多。

override 与显式覆写契约

4.3 引入 override 修饰符，并在 --noImplicitOverride 打开时强制使用。它的出发点是一个很常见的故障：基类的方法被重命名或删除，子类里那个同名方法不会报错，而是安静地变成一个全新的方法，调用方仍然以为覆写生效了。

开启 --noImplicitOverride 后，任何覆写基类成员的方法、属性或访问器都必须带 override，否则编译器会报错，提示该成员必须带 override 修饰符。反过来，如果基类根本没有这个成员，写了 override 同样会报错，提示该成员并未在基类中声明。两个方向合起来，覆写就从“碰巧同名”变成了显式契约。

override 本身不依赖编译选项，即使不开 noImplicitOverride 也可以写，此时它只做“基类必须存在该成员”的校验。因此迁移可以分两步：先在子类上补修饰符，再打开开关，避免一次性出现成百上千条错误。还要注意，override 只适用于类成员，接口实现、对象字面量赋值都不需要也不能使用它。

4.3 的类型推断与类成员

模板字面量类型在 4.3 中的推断更可靠了。当参数类型写成由类型参数与固定片段拼接的模板字面量时，编译器会尝试把实际传入的字符串拆成模板片段，反推出类型参数，而不是直接退回 string。

这类推断让路由表、事件名、CSS 变量名等以字符串约定为核心的 API 更容易获得精确类型。推断失败时编译器仍会退化为较宽的类型，所以不要指望它处理任意复杂的嵌套模板，遇到推断不出预期结果的情况，显式标注类型参数通常比继续加约束更省事。

useDefineForClassFields 的语义与陷阱

这个选项并非 4.2 新增，但两个版本期间它是升级事故的高发区，值得单独说明。类字段在标准中的语义是用 Object.defineProperty 定义自有属性，而 TypeScript 早期为了实现装饰器等需求，采用赋值方式初始化。useDefineForClassFields 打开后，编译器改为标准语义；把 target 设为 ESNext 时它默认开启，因此“只改 target”就可能悄悄改变运行结果。

最典型的破坏是访问器被遮蔽。赋值语义会触发原型上的 setter，定义语义则直接创建自有属性，setter 完全不会被调用。

第二种情况更隐蔽：只写类型、不给初始值的字段声明，在定义语义下也会生成一个值为 undefined 的自有属性，从而盖住基类的同名访问器。若这个字段只是用来描述类型，应改成 declare value: number;，让编译器跳过代码生成。

第三种情况是初始化顺序。字段按声明顺序在 super() 返回后依次初始化，构造函数体内的赋值则晚于全部字段初始化。原本依赖“构造器先赋值、字段再读取”的写法，在切换语义后可能读到 undefined。迁移时建议先在一个分支上打开选项跑完整测试，再逐个类核对字段声明；如果项目同时使用装饰器，还要确认装饰器与字段定义的执行顺序符合预期。短期内无法调整时，可以暂时保留旧语义，但要把它当成技术债记录在案，而不是长期默认。

升级路线与构建链配合

综合上面的内容，可以给出一条风险可控的路径。第一步只升级编译器版本，不改任何选项，用 tsc --noEmit 与基线对比，确认新增错误集中在类型别名展示和元组声明上。第二步处理 4.3 的 override：先给所有覆写成员补上修饰符，再打开 noImplicitOverride，这样错误数量可控，也不会把真正的漏覆写混在噪音里。第三步单独评估 useDefineForClassFields，它与运行时行为相关，应当独立提交、独立回归。最后再开启 noPropertyAccessFromIndexSignature 这类风格型选项。

构建链要保证“只有一处负责降级”。使用 ts-loader 时，转译由 tsc 完成，只要 tsconfig.json 一致，语义就一致；开启 transpileOnly 只是跳过类型检查，输出仍遵循同一套选项。使用 babel-loader 时则有两个转换器，Babel 的类字段插件存在规范模式与宽松模式，后者接近赋值语义，与打开选项后的 tsc 不一致。此时要么让 Babel 负责规范语义、tsc 只做检查，要么显式关闭该选项并在两处配置中写清注释，避免类型检查通过而运行时行为不同。

严格选项的开启原则是一次一个。每开一项，先统计新增错误、评估修复成本，再决定是当次修完还是拆成后续任务。大面积使用 @ts-ignore 会把问题永久掩埋，确实需要保留的例外应改用 @ts-expect-error 并写明原因，这样一旦上游修复、错误消失，编译器会反过来提醒我们删掉这行抑制。多人协作的仓库还可以把选项收敛到共享的基础配置里，由各子包继承，避免同一个仓库出现多套互不兼容的语义。

小结

4.2 的价值在于表达力与可观测性：类型别名在更多位置保持原样，元组剩余元素可以出现在开头和中间，抽象类有了 abstract new 构造签名，--explainFiles 与 --noPropertyAccessFromIndexSignature 则补上了排查与约束手段。4.3 把重点放在类的契约上，override 让覆写显式化，#private 提供运行时私有，static 索引签名与抽象类的 ConstructorParameters 补齐了边角。升级时先升版本、再看错误，把 override 与 useDefineForClassFields 分开处理，严格选项逐项开启，是这两个版本最稳妥的落地方式。
