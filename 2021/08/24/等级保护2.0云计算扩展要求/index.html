等级保护 2.0 云计算扩展要求

云上的等保和机房里的等保，用的是同一套标准，落地时却常常卡在同一个问题上：这一条到底该由云服务商做，还是由租户自己做。本文从 GB/T 22239-2019 的云计算安全扩展要求出发，梳理 IaaS、PaaS、SaaS 三种服务模式下的责任边界，逐层说明物理环境、通信网络、区域边界、计算环境与管理中心的落地要点，再给出云租户侧的配置清单、常见不符合项与整改优先级。

读完本文，读者应当能为一个跑在公有云上的业务系统画出责任矩阵，判断哪些测评证据必须自己准备，哪些可以引用云服务商的测评结论，并在整改排期时知道先动哪一刀。

云计算扩展要求的定位

等级保护 1.0 时代的国家标准按对象分册，信息系统、主机、网络、应用各有一本，云计算的形态在当时还没有成为主流。到了等保 2.0，GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》把分散的要求合并成一个标准，结构上分成安全通用要求与安全扩展要求两部分。通用要求回答“一个等级保护对象应当具备什么能力”，扩展要求则针对云计算、移动互联、物联网、工业控制等新型形态，补充或调整那些在通用条款里找不到明确载体的内容。

理解“扩展”二字是关键。它不是另起一套标准，也不是可以把通用要求绕过去的替代品，而是在通用要求之上叠加的一层约束。一个云上的三级系统，既要满足三级的安全通用要求，也要满足与云计算相关的扩展要求；两者冲突时，以更具体、更严格的一方为准。举个常见的例子：通用要求里讲机房选址、门禁、防雷防火，这些条款对云租户来说根本无法执行，扩展要求就把这部分责任明确归到云服务商一侧，同时要求租户通过合同、测评报告等方式确认云商确实做到了。

扩展要求约束的是两类主体。一类是云服务商，负责云平台自身的物理设施、虚拟化层、管理平台和租户隔离能力；另一类是云租户，负责自己在云上创建和配置的那一部分，包括账号、网络、主机、应用、数据。标准在条文表述上用“云服务商”和“云租户”区分责任，实施时应当逐条判定适用主体，而不是把整份要求原样丢给集成商。

还有一个容易被忽略的前提：定级对象是分开的。云平台本身作为一个等级保护对象定级备案，云上的业务系统作为另一个对象定级备案，两者的级别可以不同。一个三级业务系统跑在二级云平台上，在合规上是不成立的，这也是不少项目在测评前才发现的问题。扩展要求里的很多条款，只有在明确了“我评的是平台还是业务系统”之后，才知道该由谁举证。

三种服务模式与责任边界

云计算的三种服务模式，决定了责任边界切在哪里。IaaS 把虚拟机和网络交给租户，租户从操作系统开始往上自己管；PaaS 把运行时、中间件、数据库做成了服务，租户只管应用和数据；SaaS 连应用都交出去了，租户只剩下账号、配置和业务数据。责任边界随着抽象层次上移而不断向云商一侧移动，但永远不会完全消失，租户总有一部分事情要做。

flowchart TD
    A[业务数据与账号配置] --> B[应用与业务逻辑]
    B --> C[中间件与运行时]
    C --> D[操作系统与补丁]
    D --> E[虚拟化与物理设施]

图中越靠下，云商承担的比例越高；越靠上，租户的责任越重。IaaS 下租户要负责操作系统及以上的全部内容，PaaS 下操作系统与中间件多由云商负责，SaaS 下只剩账号与数据。等保测评时，这条分界线就是判断“这条不符合项该开给谁”的依据。

把这条线落到条款上，可以整理成一张责任矩阵。下表是本文建议的通用切分方式，具体项目还要结合云商提供的责任共担说明做微调。

层面 IaaS PaaS SaaS
物理环境 云商 云商 云商
虚拟化与资源隔离 云商 云商 云商
网络虚拟化与边界设备 云商提供能力，租户配置 云商提供，租户少量配置 云商
操作系统与补丁 租户 云商 云商
中间件与数据库 租户 云商（托管） 云商
应用与身份权限 租户 租户 租户（配置为主）
数据与备份 租户 租户 租户（部分可委托）

这张表最值得记住的一点是：即便在 SaaS 模式下，租户仍然对账号、权限和数据负责。很多数据泄露事件并非云商被攻破，而是租户把对象存储的读权限开成了匿名可读，或者把一个高权限账号的密钥写进了前端代码。责任共担模型里，云商负责“云的安全”，租户负责“云中的安全”，这句话说起来顺口，真正落到测评证据上，能说清楚的人并不多。

安全物理环境与安全通信网络

安全物理环境是扩展要求里责任归属最清楚的一层。机房的选址、建筑抗震、门禁与视频监控、防雷防火防水、供电与 UPS、温湿度控制、电磁防护，这些在通用要求里由运维单位负责的条目，在云上整体转移给云服务商。租户不需要再去证明机房有没有双路市电，但需要证明自己选择了一个具备相应能力的机房。

租户在这一层仍有几件事要做。一是选择资源所在的地域和可用区，确认数据没有落到境外，这对有数据本地化要求的行业是硬约束。二是自带设备与专线接入，本地机房通过专线接到云上时，路由器、光端机、加密机仍属租户资产，物理防护与冗余由租户负责。三是托管区与专有云，机柜由云商提供，柜内设备由租户上架维护，物理访问走云商审批并留记录。四是灾备，跨可用区不等于跨地域，两地三中心的距离要求不会因为上了云就自动满足。

租户在这一层能拿到的证据，主要是云服务商的等级测评报告、备案证明、服务协议中的安全条款，以及部分云商公开的第三方审计报告。测评时通常把云商报告作为物理环境的支撑材料，再补充租户侧的合同与区域选择记录。这里有个细节：云商报告按区域、按平台出具，租户要确认业务所在区域和可用区是否落在覆盖范围内，拿一份不覆盖本地域的报告去交差，复核时很容易被退回。

安全通信网络的变化更微妙。通用要求关注通信设备的冗余、传输的完整性与保密性，云上则变成对虚拟网络的设计与配置。云商提供 VPC、子网、路由表、安全组、网络 ACL、VPN 网关、专线网关这些能力，租户用它们拼出自己的网络拓扑。跨租户的隔离由云商在虚拟化层和网络虚拟化层保证，不同租户的流量在物理网络上通过隧道标识区分，这部分租户看不见也管不了，只能在责任矩阵里写明由云商承担。

租户要管的是自己 VPC 内部的通信。生产、测试、办公三条网络要分段，数据库子网只允许应用子网访问，管理网段与业务网段分离，跨可用区的流量走内网而不是绕公网。使用专线或 VPN 连接本地与云上时，隧道两端的加密算法和密钥要符合要求，密钥不能长期不换。跨地域复制、跨账号数据交换这类场景，如果走的是公网端点，必须加传输层加密，并且限制源地址范围，不要图省事把端点暴露给整个互联网。

安全区域边界：虚拟防火墙与流量隔离

上了云之后，“边界”这个词的含义变了。物理世界里的边界是一台防火墙、一根网线，看得见摸得着；云上的边界是一组策略，分布在安全组、网络 ACL、虚拟防火墙、路由表和云商提供的隔离机制里。边界没有消失，只是从设备变成了配置，从一次性建设变成了持续维护。

云上的边界至少有三层。最外层是互联网出入口，租户的弹性公网地址、负载均衡、NAT 网关都在这一层，云商通常在这里提供 DDoS 清洗和 Web 应用防火墙能力，租户需要主动开启并按业务特征调策略。中间层是 VPC 之间与子网之间的边界，跨 VPC 互联、对等连接、专线打通之后，两个原本隔离的网络就连成一片，如果不补策略，等于把内网横向移动的通道直接铺好。最内层是实例之间的边界，靠安全组实现，默认应当拒绝，按需放通端口和源地址。

安全组配置是最容易出问题的地方。最常见的三种错误是：为了排查问题临时把某端口对全网开放，事后忘了收回；把数据库端口对整个 VPC 网段开放，而不是只对应用子网开放；管理端口与业务端口混在同一个安全组里，导致运维通道随业务一起暴露。正确的做法是把安全组当成代码来管理，命名规范、用途单一、变更留痕，重要的策略变更走审批。下面这段是容器环境里用网络策略限制东西向流量的写法，思路与安全组一致，只是作用在 Pod 这一层。

入侵防范在云上要靠多层叠加。网络层有云防火墙和流量清洗，主机层有入侵检测 agent，应用层有 WAF，这三层缺一层都会留下盲区。很多租户只买了 WAF 就认为边界安全了，结果攻击者通过一个未纳入 WAF 的直连地址绕过防护，或者从内网横向打到数据库。测评访谈会问“边界防护是否覆盖所有互联网入口”，存在未覆盖入口，这一条就很难说清。

安全审计的对象也变了。传统边界设备出的是会话日志，云上要采集的是流日志、防火墙命中日志、负载均衡访问日志和 NAT 转换日志。这些日志默认往往不开，或者只保留很短时间，租户需要显式开启并投递到集中存储。日志本身也是边界的一部分：谁改了安全组、谁开了公网地址，这些操作记录要在云审计里查得到，否则事后无法还原一次暴露是如何发生的。

安全计算环境：虚拟机、镜像与资源隔离

计算环境是租户责任最重、也最容易做偏的一层。身份鉴别、访问控制、安全审计、入侵防范、恶意代码防范、可信验证，在云上都要落到具体配置项上，而不是一台台物理服务器的手工加固。租户面对的是几十上百台虚拟机、一批镜像和若干容器集群，靠人工逐台登录改配置，既不现实也证明不了“持续有效”。

身份鉴别要先从云账号本身做起。控制台的主账号只用于极少数管理操作，日常运维使用子账号并绑定多因素认证；不同职责的账号按最小权限授权，能只读的不给写，能限定资源范围的不给全局；程序访问使用独立的访问密钥，密钥定期轮换，禁止写进代码仓库和前端页面。主机层面则要禁用密码登录、改用密钥对，限制登录源地址，保留登录审计。这几件事听起来基础，但测评中因为“主账号多人共用”或“密钥硬编码在前端”被记为不符合的项目并不少见。

访问控制要分两个层面。云平台侧解决“谁能操作哪些资源”，主机侧解决“谁能读写哪些文件、执行哪些命令”。前者依赖云商的权限体系，租户要把角色分清：网络、系统、安全管理员三权分立，审计员只读日志不能改配置。后者依赖操作系统的用户与权限，应用不要用 root 运行，敏感目录收紧权限，sudo 使用要留痕。

恶意代码防范在云上有两种做法。一种是在每台主机上装 agent，实时检测和查杀，缺点是 agent 要维护升级、可能影响性能；另一种是在镜像构建阶段做基线扫描，在运行阶段用主机安全服务做行为检测。两者结合比较稳妥：镜像保证出厂干净，agent 保证运行时不跑偏。需要注意的是，容器场景下 agent 装在宿主机上，容器内文件系统往往扫不到，得靠镜像扫描加运行时监控来补。

镜像管理是云计算特有的控制点，也是很多项目最薄弱的地方。镜像来源要收敛，只用云商的公共镜像和企业内部维护的私有镜像，禁止从不明来源导入。私有镜像要有基线：关闭无用服务、删除默认账号、打好补丁、装好监控 agent。镜像要扫描漏洞和恶意文件，不通过的不允许上生产。仓库权限最小化，推送只给构建流水线，拉取按项目划分，禁止匿名拉取。镜像至少要做到版本可追溯，知道线上机器是用哪个镜像 ID 创建的。

快照保存的是磁盘在某一时刻的完整内容，可能有数据库文件、配置文件和密钥材料，一旦被共享给其他账号或设为公开，等同于数据泄露。快照要加密，共享要审批，跨账号复制留记录，删除设保护期。迁移方面，热迁移时内存数据在宿主机之间传输，租户应确认通道加密、迁移发生在同一地域内，跨地域迁移要单独评估合规问题。资源隔离则看邻居效应：CPU、内存、磁盘 IO 是否有限额，关键业务是否使用独占实例或专属宿主机。

安全管理中心与租户侧的配置责任

安全管理中心在云上是“两套中心”的格局。云商侧有一套，管的是平台自身的账号、权限、审计、漏洞和事件，租户看不见细节，只能通过云商的测评报告和服务说明确认其存在；租户侧也有一套，管的是自己云上资源的账号、日志、配置和密钥。扩展要求里关于集中管控的条款，落到租户身上就是一句话：你有没有一个地方，能同时看到自己所有账号、所有区域、所有资源的安全状态。

租户侧的安全管理中心由几块能力拼成。统一身份负责账号与权限，把人、角色、资源绑定起来；云审计负责操作记录，谁在何时改了安全组、删了数据库、开了公网地址都要能查到；日志服务把主机、应用、网络设备的日志集中起来，做检索和告警；配置审计持续比对资源配置与基线，发现漂移；密钥管理负责主密钥的生成、轮换与授权；堡垒机收口运维通道。这些能力多以托管服务提供，租户要做的是开通、配置、接入和日常看板。

日志的留存与保护是测评必查项。法律要求网络日志留存不少于六个月，测评会核对实际留存天数和可查询范围。经验有几条：日志投递到独立的日志账号，与业务账号隔离，避免业务账号失守后日志一起被删；存储桶开启写一次读多次的锁定策略，防篡改和误删；日志服务本身也要有访问控制；时间同步统一到同一时区与时间源，否则跨服务关联分析会对不上。

账号、密钥、日志、备份这四件事是云租户最核心的配置责任，云商无法代劳。账号方面，建立账号清单，标注用途、负责人、权限范围和最后登录时间，长期不用的及时停用；密钥方面，禁止在代码、镜像、环境变量明文里存放长期密钥，改用托管密钥服务或临时凭证，能轮换的一律轮换；日志方面，明确哪些日志必须开、存多久、谁能看；备份方面，定义恢复点目标和恢复时间目标，定期做恢复演练，并把备份账号与生产账号隔离，防止勒索软件连备份一起加密。这四件事做得扎实，云上等保的大部分管理类条款就有了落脚点。

容器与 Serverless 带来的新边界

2021 年，容器已经是大中型互联网公司的默认交付方式，Serverless 也从概念走向生产。麻烦在于：等保的对象是“系统”，而容器和函数把边界切得更碎，传统“一台主机一个 agent”的防护模型开始失效。

容器的风险集中在三处。第一是镜像供应链，基础镜像过期、依赖库带漏洞、构建过程中被注入恶意文件，这些问题会随着镜像分发到所有环境。第二是运行时隔离，容器共享宿主机内核，配置不当的权限、挂载的敏感目录、开启的特权模式，都可能成为逃逸的起点。第三是编排层的配置，集群的管理接口暴露、基于角色的权限过宽、密钥以明文形式存在配置对象里，这些问题在传统主机上并不存在。对应的做法是：镜像统一构建并扫描，集群开启准入控制拦截高风险配置，网络策略限制 Pod 之间的访问，运行时检测关注异常进程与异常外联，管理接口不暴露公网。

Serverless 把边界推得更远。函数运行时由云商管理，租户拿不到主机，装不了 agent，也看不到文件系统，测评时“主机加固”“恶意代码防范”这类条款需要换一种举证方式：用函数的身份与权限配置、代码依赖扫描、网关侧的访问控制、调用日志和链路追踪来替代。函数的最大风险是权限过大和事件注入，一个能读全库的函数被任意事件触发，后果不比一台失守的主机轻。

需要说明的是，截至本文写作时，等级保护标准并没有为容器和 Serverless 单列一套扩展要求，实践中是把它们映射到安全计算环境、安全管理中心的通用条款上，靠测评机构与建设方共同确认举证方式。这是一种过渡状态，随着云原生形态的普及，相关的标准解读和测评实践还会继续演进。对建设方来说，稳妥的策略是把集群和函数计算当作独立的等级保护对象来梳理边界，别让它们成为责任矩阵之外的灰色地带。

测评证据与常见不符合项

云上测评的取证方式与机房时代差别很大。GB/T 28448-2019《信息安全技术 网络安全等级保护测评要求》给出的方法仍然是访谈、核查和测试，但“核查”的对象从设备面板变成了控制台页面、配置导出文件和接口返回结果。测评员要看的不是你口头说开了日志，而是日志服务里确实有连续多天的记录、能按资源检索、能导出到指定存储。

证据的效力有高低之分。控制台截图直观，但容易被质疑时效性；配置导出、合规检查报告、接口查询结果更可靠，因为它们带有资源标识和时间戳；云审计的操作记录则能证明配置变更过程。稳妥的做法是三类配合：合规检查报告说明整体状态，配置导出说明具体参数，审计日志说明变更经过。涉及云商责任的部分，用测评报告、备案证明和服务协议条款支撑，并注明覆盖的区域与范围。

测评中最常见的不符合项，集中在四类。第一类是租户没有接管自己的责任，把云商通过测评等同于自己的系统通过测评，安全组、账号、日志一概未配置。第二类是日志不可得，云审计没开、日志服务没接、留存天数不足，或者日志存在业务账号下，业务账号一失守日志就被清空。第三类是快照与镜像权限过大，快照被共享给外部账号甚至设为公开，镜像仓库允许匿名拉取。第四类是镜像与主机未做漏洞扫描，补丁长期不更新，基线配置与安全要求脱节。

不符合项 典型表现 整改方向
责任未接管 只有云商报告，无租户侧配置记录 建责任矩阵，逐条落实租户项
日志不可得 未开云审计，留存不足六个月 集中投递到独立日志账号并锁定
快照权限过大 快照公开共享、跨账号复制无审批 加密、收回共享、加审批与审计
镜像未扫描 直接使用来源不明镜像 收敛来源，构建即扫描，禁匿名拉取

这四类问题有个共同点：都不是技术难题，而是责任没有落到人。测评前集中补配置能过一时，但配置漂移会在几个月内把状态打回原形，所以真正有效的整改是把这些检查项接进日常的合规巡检和发布流程。

与通用要求的衔接及整改优先级

两者衔接落地可概括为三步：适用性分析、差距评估、整改排期。适用性分析就是前面那张责任矩阵，把每条要求标注为云商、租户或共担，标错就全盘偏差。差距评估要把云商的测评结论当作输入而非答案，租户侧的配置项必须自己核一遍。整改按风险与举证成本排序：先收公网暴露面和高权限账号，这两项风险最大、测评必查；再补日志与审计，它既是控制措施也是其他条款的证据来源；然后是镜像扫描、补丁与资源隔离；最后才是备份演练和制度文档。

还有一点值得提醒：等保测评是基线，不是上限。通过测评只说明达到了一个共同的及格线，云上的真实风险还取决于业务自身的威胁模型。把责任矩阵、配置基线和巡检脚本沉淀下来，比反复为测评临时抱佛脚更有价值。

小结

云计算扩展要求并没有发明新的安全目标，它做的是把通用要求里那些在云上失去载体的条款重新安放到具体的主体身上。理解它的钥匙是责任边界：物理设施和虚拟化层归云商，账号、网络配置、主机、镜像、数据和日志归租户，服务模式只决定这条线画在哪里。落地时先画责任矩阵，再按层核对配置，最后用可追溯的证据证明状态；整改则从暴露面和身份开始，往日志、镜像、备份依次推进。容器与 Serverless 目前还没有独立的扩展要求，把它们显式纳入等级保护对象的边界，比留一块灰色地带更安全。
