接口性能优化案例合集

接口变慢时，最常见的错误是先猜原因再改代码。本文选取笔者在 2021 年上半年处理过的若干线上案例，覆盖 N+1 查询、深分页、字段与序列化、连接池与超时、缓存误用、索引失效、锁粒度、串行远程调用、同步改异步以及传输压缩等方向。

每个案例都按“现象、定位、改动、验证、副作用”五步记录，重点不是给出标准答案，而是展示如何用测量把猜测变成证据。本文面向有线上接口维护经验的后端读者，示例以 MySQL 8.0、Redis 6.2 与 Go 1.16/1.17 为准；文中出现的数量均为示意值，实际项目请以自己的监控数据为准。

先把“慢”拆开

优化之前，先确认慢在哪个环节。一个 HTTP 接口的耗时大致由网关排队、应用内计算、数据库等待、远程调用、序列化与网络传输几部分组成。只盯着应用日志往往看不出区别，需要把链路上的时间分段打点：入口与出口记录总耗时，数据库访问记录语句与耗时，远程调用记录目标服务与超时，序列化前后记录字节数。有条件时结合链路追踪与 pprof 一起看，前者给出调用关系，后者给出 CPU 与内存的去向。

定位阶段还要区分“慢”和“偶发慢”。平均值正常而 P99 很高，通常是锁等待、连接池耗尽、慢查询或下游抖动造成的；平均值本身就高，多半是调用次数或数据量的问题。二者的改法完全不同，先把分布看清楚，能省掉大量无效改动。

还有一点容易被忽略：优化结论必须带上测试条件。同一接口在低峰与高峰、冷缓存与热缓存、小数据集与大数据集下的表现可能完全不同，记录基线时要把并发量、数据规模、实例规格与缓存状态一并写下来。否则改动上线后指标没有变化，很难判断是方案无效，还是前后条件根本不可比。

每个案例的记录建议固定成五栏，写清楚现象、定位、改动、验证与副作用。验证必须使用同一份数据与同一套入口，前后各测一次；副作用则要回答三个问题：资源是否转移到了别处，一致性是否被削弱，故障时是否有兜底。

案例一：N+1 查询与逐条远程调用

现象：一个订单列表接口，页大小 20 时数据库调用次数明显上升，页越大越慢；换成远程调用后同样的问题再次出现——每条记录都要查一次用户服务。

定位：慢查询日志里出现大量结构相同、只有参数不同的语句；链路追踪上能看到一排并列的短 span，数量与页大小一致。这类问题不需要复杂分析，统计一次请求内的 SQL 条数即可确认。

改动：把循环内的单条查询改为一次批量查询，再用 map 组装。下面的示例用 sqlx 的 In 展开占位符，实际项目也可以手写占位符。

远程调用同理，优先推动下游提供 batch 接口，或者在本服务内按批聚合后再发。验证时对比一次请求内的数据库语句数与总耗时，通常能看到调用次数从 N+1 降到常数级。

副作用有三点：IN 的参数不能无限增长，需要按固定大小分批；批量接口要处理部分 ID 不存在的情况，避免整页报错；下游 batch 接口本身也需要限流，否则只是把压力集中到了同一时刻。

案例二：深分页改为游标或延迟关联

现象：后台列表翻到后面几页时明显变慢，前几页正常；同样的查询条件，页号越大耗时越长。

定位：EXPLAIN 显示扫描行数远大于返回行数，LIMIT 的偏移量被计入扫描成本。MySQL 需要先读出前面所有行再丢弃，偏移越大浪费越多。

改动分两种。业务允许“下一页”式浏览时，用游标最直接：记住上一页最后一条的主键，下一页从它之后取。

必须保留跳页能力时，可以用延迟关联：先在索引上取主键，再回表取整行，减少回表次数。

验证看两件事：执行计划里的扫描行数，以及相同页号下的响应时间。延迟关联的收益取决于子查询能否走覆盖索引，若 status 与排序列没有合适的联合索引，改善会很有限。

副作用：游标分页不支持随机跳页，排序键必须稳定且唯一，否则会漏行或重复；延迟关联仍然要扫描偏移量，只是少了回表，深到一定程度依旧会慢，最终还是要靠业务约束或归档来收敛数据范围。

案例三：多余字段、序列化与传输开销

现象：接口返回的 JSON 体积偏大，移动端弱网下加载慢；应用侧 CPU 占用上升，pprof 显示序列化占比不低。

定位：先看响应体大小与字段清单，常见问题是直接 SELECT * 后把整行结构体序列化出去，其中包含详情、扩展 JSON 等大字段；再看序列化耗时与网卡出流量，确认瓶颈在编码还是传输。

改动：查询只取需要的列，定义专用的响应结构体，避免把数据库模型直接暴露给调用方；对确实较大的文本响应启用 gzip，由服务端根据 Accept-Encoding 决定是否压缩。

验证：对比改动前后的响应字节数、序列化耗时与客户端首屏时间。压缩只对文本有效，图片、视频与已压缩内容再压一次通常没有收益，反而多耗 CPU。

副作用：响应结构体与数据库模型分离后，字段变更需要同步维护两处；gzip 会增加服务端 CPU，压缩级别越高越明显；若中间还有缓存，缓存 key 必须带上编码方式，否则可能把压缩后的内容发给不支持的客户端。

案例四：连接池、超时与串行调用

现象：流量上来后接口大量超时，但数据库与下游的负载并不高；日志里出现获取连接等待，或者请求在某个远程调用上成片卡住。

定位：先看连接池指标：当前打开数、空闲数、等待次数与等待时长。等待时长上升而数据库 CPU 平稳，说明池子太小或连接被长时间占用。再看超时配置：如果单次远程调用允许等待很久，请求会一直占着 goroutine 与连接，故障时迅速堆积。最后看调用链，三个本可并行的远程调用若首尾相接，耗时就等于三者之和。

改动：按并发量与单次耗时估算池大小，设置获取连接的超时，避免无限等待；超时按层设置，下游单次超时之和要小于本接口的总超时，给上层留出决策时间；相互独立的远程调用改为并行，并传入同一个 context，任一路失败或超时即取消其余调用。

验证：观察连接等待时长、接口 P99 与下游错误率。并行改造后总耗时接近最慢的一路，而不是各路之和。

副作用：池子调大可能把压力转移给数据库，必须结合数据库连接上限；超时调短会把慢请求变成错误，需要评估业务容忍度；重试要有次数上限并配合退避，否则超时会在下游放大成数倍流量；并行会让下游在同一时刻收到成倍请求，必要时配合批量接口或信号量限流。连接池参数如何取值属于另一篇的主题，这里只强调“有上限、有超时、可观测”。

案例五：缓存命中率低与大对象

现象：接入 Redis 后数据库压力没有下降，接口耗时也没有改善；或者命中率看着很高，但网络出流量与反序列化开销反而上升。

定位：先看命中率与 key 分布。命中率低常见于 key 设计过细或带了随机后缀，每次请求都落到不同的 key；也可能写入后很快过期，热点数据反复回源。命中率高但慢，则要检查 value 大小，把整页 HTML 或整张大对象塞进一个 key，读取时的一次网络传输就足够拖慢接口。Redis 6.2 的慢日志与 MEMORY USAGE 可以帮助确认。

改动：key 按“业务:对象:ID”组织，保证同一实体的读写落到同一个 key；只缓存热点且计算昂贵的数据，大对象拆成小块或改存字段；对确认不存在的查询缓存短 TTL 的空值，减少穿透式回源；更新时删除而不是覆盖，避免并发写导致旧值长期存在。

验证：命中率、回源次数、Redis 出流量与接口耗时要一起看。命中率提升但回源次数没降，说明统计口径或被其他路径抵消，不能只看一个指标。

副作用：缓存一致性变弱，更新与删除之间仍有窗口；大 key 拆分后读取次数变多，需要批量获取；空值缓存会占用内存，TTL 过长会掩盖真实的数据写入。穿透、击穿与雪崩的完整方案不在本文展开，这里只强调缓存不是默认答案，命中率与 value 成本都要量。

案例六：索引失效、锁粒度过大与异步边界

现象一：某条按时间范围加状态的查询随着数据增长逐渐变慢，EXPLAIN 的 type 为 ALL，扫描行数接近全表。定位后发现联合索引的顺序是“状态、创建时间”，而查询只带了时间范围，最左前缀用不上；列上套函数、参数类型与列类型不一致导致的隐式转换，也会让索引失效。改动是把区分度更高、查询必带的列放在前面，或按实际查询重建联合索引；验证看执行计划是否走到 range 或 ref，以及扫描行数是否下降。副作用是索引增多会拖慢写入、占用空间，删除旧索引前要确认没有其他查询依赖。

现象二：下单接口在高峰期出现行锁等待，但单条更新并不慢。定位发现事务里先更新库存，随后调用远程风控接口，网络往返期间一直持有行锁。改动是把远程调用移到事务之外，或先做校验再开事务，把事务缩短到只包含必要的读写；验证看锁等待时间与事务持有时长。副作用是拆分后需要重新检查一致性：校验与写入之间数据可能变化，必要时用版本号或条件更新兜底。账户类热点行的竞争属于另一个话题，本文不展开。

现象三：主链路里有积分、通知、日志等非关键动作，串行执行拉长了响应。改动是改为异步：写入消息队列或投递到后台任务，主链路只保证核心数据落库。验证看主链路耗时与异步任务的积压量。副作用最需要提前想清楚：消息可能丢失或重复，消费必须幂等；异步失败对用户不可见，要有重试、死信与告警；业务能否接受短暂的不一致，要由产品与业务方确认，而不是由技术单方面决定。同步改异步的边界，本质上是一致性与时延的取舍。

小结

接口优化应先测量后动手：把耗时拆到应用、数据库、远程调用与序列化各段，分清均值高还是长尾高，再决定改哪里。本文的案例可以归为三类：减少次数（N+1、串行调用）、减少数据量（字段、分页、压缩、大对象缓存）、减少等待（连接池、超时、锁粒度、异步化）。优化的顺序也应从成本最低、容易回滚的改动开始，例如先补索引、再改批量，最后才考虑引入缓存或异步。每一类改动都会把成本转移到别处，验证时要同时看目标指标与资源曲线，副作用则要回答一致性、故障兜底与可观测三个问题。最后提醒一句：压测数据要与生产数据分布接近，否则优化出来的结论只对测试环境成立。
