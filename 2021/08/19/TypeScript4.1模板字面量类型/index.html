TypeScript 4.1 模板字面量类型

本文属于《TypeScript 学习路线》第 46/74 篇
上一篇系列目录下一篇

字符串是 JavaScript 里最常见的值，也是最难约束的一种。想表达“这个参数只能是 user:created 这类名字”时，过去的做法要么是在联合类型里把每个字符串手写一遍，要么干脆退回 string，把检查推迟到运行时。TypeScript 4.1 引入的模板字面量类型改变了这一点：它让类型系统可以像模板字符串那样拼接与拆解字符串字面量，把一批原本只写在文档和单元测试里的命名规则，变成编译器能够检查的类型。

本文写作于 2021 年 8 月，距离 TypeScript 4.1 发布已有大半年，社区对它的讨论也从“语法糖”转向了真实的工程用法。本文不打算罗列所有技巧，而是按语法、联合展开、内置工具、键重映射、组合用法、落地场景、边界与坑的顺序，把模板字面量类型讲成一条可以照着走的路径。读者需要熟悉泛型、联合类型和映射类型的基本写法，读完应当能为自己的项目设计出类型安全的字符串键。

从模板字符串到类型

模板字面量类型（Template Literal Types）的写法与 JavaScript 的模板字符串几乎一模一样，区别只在于它出现在类型的位置上，占位符里放的是类型而不是值。

把占位符换成类型参数，就得到更一般的形式。此时 T 可以是 string、number、bigint、boolean 四类原始类型，也可以是它们的字面量类型，甚至是另一个模板字面量类型。编译器会把占位符替换成对应类型的取值集合，拼出一个新的字符串字面量类型。

最后一行值得留意：boolean 在类型层面等价于 true | false，所以它展开成两个字面量，而不是一个笼统的字符串。这也提示了模板字面量类型的基本机制——它处理的始终是有限的字面量集合，string 只是其中最宽的那个成员。

子类型关系与类型擦除

模板字面量类型并不是一种新的运行时值，编译之后它会被完全擦除，产物里只剩下普通的字符串。它带来的收益全部发生在类型检查阶段。

在类型关系上，任何模板字面量类型都是 string 的子类型，赋值方向因此是单向的：具体的窄类型可以赋给 string，反过来不行。这一点和普通字面量类型完全一致，理解它有助于判断什么时候该把参数声明成模板类型、什么时候该退回 string。

实践中常见的误区，是把模板类型当成“字符串校验函数”。它只在编译期检查已知字面量，值一旦来自 JSON 或表单输入，就只能靠断言，真正的防线仍在运行时。

联合类型在占位符中的展开

当一个模板类型里含有多个占位符，且每个占位符都是联合类型时，结果是把所有组合逐一列出，也就是做笛卡尔积。

这个规则可以省掉大量重复书写。类名、事件名、CSS 变量名往往由几个维度的枚举拼成，以前需要在常量表里手工维护，现在只要把维度写成联合类型，组合结果由编译器算出来。

一个实用的判断标准是：如果这个联合类型你没法在注释里写清楚它有多少个成员，那它对读者和编译器来说都已经太重了。

内置的四个字符串操作类型

TypeScript 4.1 随模板字面量类型一起内置了四个工具类型：Uppercase、Lowercase、Capitalize、Uncapitalize。它们由编译器内部直接实现，不从标准库里的其他别名推导而来，因此对任意字符串字面量都能给出精确结果。

另一个容易忽略的细节是宽类型上的退化：Uppercase<string> 的结果就是 string。编译器无法枚举无限集合，遇到宽类型时只能放弃精确性。所以在泛型里写 T extends string 之后，若调用方传入的正是 string 本身，后续拼接都只会得到 string，这是取舍，不是缺陷。

用 as 做键重映射

模板字面量类型单独使用时能力有限，它真正的威力来自和映射类型结合。TypeScript 4.1 给映射类型加了 as 子句，允许在遍历键的同时改写键名，语法形如 [K in keyof T as 新键]。

string & K 这一段容易被忽略。K 来自 keyof T，类型可能是 string | number | symbol，而模板类型的占位符只接受能转成字符串的原始类型，直接写 K 会报错。先与 string 求交叉，把范围收窄到字符串键，既满足约束，也顺带过滤掉了 symbol 键。

as 子句还有一个好用的副作用：当它返回 never 时，这个键会被直接丢弃。于是可以用条件类型筛选键，而不必先生成再剔除。

两条规则组合起来，就足以覆盖大部分“名字有规律、结构有对应”的场景：根据字段名生成 getter，根据状态字段生成 action 名，根据路由名生成跳转函数名。生成本身不难，难的是保证生成结果和真实使用处始终对得上，这也是下一节要处理的问题。

API 路径

把版本号和资源名做成联合，路径就能在编译期确定，拼错一个字符都会立刻报错。带资源 ID 的路径可以用 ${number} 占位。

这类约束在封装请求层时尤其有用：把路径参数收窄成模板类型，调用方就没法拼出服务端不存在的地址，重构接口版本时也能靠编译器找出所有调用点。

事件总线

事件名往往采用“领域:动作”的格式，载荷类型则因事件而异。用映射类型把事件表转成“名字到载荷”的对应关系，订阅函数就能根据名字推断出回调参数。

如果事件名还要按领域分组，可以再叠加一层模板类型，把 created、deleted 这两个动作与固定的 user: 前缀拼起来，得到该领域的两个事件名。它与 keyof Events 的交集，就是全部可以订阅的名字。

表单字段

表单的派生状态（错误信息、是否触碰、是否禁用）往往以字段名为前缀或后缀。用 as 重映射一次生成整套类型，既省掉手写，也保证字段增删时派生结构同步变化。

对比手写版本，模板类型的价值不在于写得少，而在于“不会漏”：新增字段时派生类型自动多出一项，编译器会提醒你补全初始值和处理逻辑。

限制、坑与不该用的地方

联合过大会拖慢编译

这是最实际的限制。模板类型展开时按笛卡尔积生成成员，维度一多，字面量数量会迅速过万。编译器需要为它们建立类型关系、做可赋值检查，还要写进声明文件。表现是保存文件后类型检查变慢、跳转定义卡顿，严重时编辑器会长时间无响应。

规避办法不是优化写法，而是减少维度：能在运行时拼的字符串就不要在类型层拼，能用一条联合概括的规则就不要拆成多层模板。类型是用来防错的，不是用来做字符串处理的。

字符串不能做算术

模板类型只做拼接和匹配，不包含任何运算。想要“版本号加一”“序号递增”这类效果，类型层面无法表达，只能退回到联合类型手动枚举。

同样的道理，${number} 匹配的是能被解析成数字字面量的字符串，比直觉里的“纯整数”宽松，小数这类写法也会落进来。若业务上只允许某段范围内的正整数，仍然要写运行时校验。

类型不等于运行时校验

模板类型全部在编译期生效，编译后不留痕迹。来自接口、URL 参数、JSON.parse 的字符串，标注只是“你认为它是什么”，不是“它确实是什么”。as 断言能绕开检查，所以边界处必须补上真实的判断函数，模板类型最多用来约束函数签名。

错误信息难读

复杂的模板类型报错时，编译器往往把展开后的整个联合打印出来，几十上百个字面量堆在提示里，很难定位到底哪个成员不匹配；用了 infer 之后，提示还可能指向条件类型的内部分支。缓解办法是给中间类型起有意义的名字、把大类型拆成几个小别名，并在公共 API 上只暴露收敛后的结果。

该退回去的时候

如果取值范围本来就是有限且固定的几个字符串，直接写联合类型更清晰：type Status = "idle" | "loading" | "done" 一眼就能读完，而用模板类型生成的等价物需要读者在脑子里展开。规则必须依赖运行时数据才能确定，或者命名规律本身还在频繁变动时，也不值得固化成类型。类型写法的收益，要和维护成本一起算。

小结

模板字面量类型把字符串的拼接与匹配搬进了类型系统：占位符接受原始类型与字面量，联合在其中按笛卡尔积展开，四个内置工具类型负责大小写转换，映射类型的 as 子句则让键名可以按规则重写。

它最适合处理“名字有规律、结构有映射”的字符串，例如 i18n 键、API 路径、事件名和表单派生字段。使用时应当控制联合规模，把运行时校验留在边界，并对复杂类型做好命名与拆分。

它也不是万能工具。取值有限时，朴素的字符串联合往往更易读；规则依赖运行时数据时，校验函数才是正解。把类型用在能长期稳定的命名约定上，收益最大。
