Go 单元测试与 mock 实践

本文属于《Go 语言与工程》第 29/78 篇
上一篇系列目录下一篇

单元测试写起来不难，难的是写得让团队愿意长期维护：不因一次重构就大面积失败，也不因依赖数据库和网络而时好时坏。本文围绕 Go 1.13 的标准库与当时主流的 testify、gomock、go-sqlmock，讨论测试分层、表驱动、接口设计与各类依赖的隔离手法，并总结一套在 CI 中稳定运行的实践。读者应已能编写基本的 TestXxx 函数。

测试分层：先想清楚这一层要证明什么

测试常被分成单元、集成与端到端三层。单元测试只验证一段内存中的逻辑，运行时间应在毫秒级；集成测试把数据库、缓存、消息队列等真实依赖接进来，验证协议、SQL 与配置；端到端测试从 HTTP 入口走到存储，数量最少。三层不是按目录划分，而是按“这次失败能定位到哪里”划分。

值得写单元测试的，是分支多、边界多、又容易用纯内存构造输入的代码：价格计算、权限判定、状态机、参数校验、错误映射。反之，一个只做“拼 SQL 再调用驱动”的仓储方法，用 mock 写单测只能证明自己调用了自己，真正的风险在字段映射与事务边界，应该交给集成测试。判断标准很简单：逻辑在进程内用单元测试，语义依赖外部系统用集成测试。

表驱动与子测试：把用例当数据

表驱动把“输入、期望、说明”放进切片循环执行。好处不只是少写几行，而是新增用例时只加一行数据，评审时能一眼看出覆盖了哪些边界。用例结构体至少包含名称、入参与期望；错误用例用 wantErr 标记，避免用错误字符串做精确比较。Go 1.13 已有 errors.Is，可以判断哨兵错误或包装后的原因。

子测试的名字会拼进完整路径，配合 -run ‘TestParseLimit/超过’ 可以只跑一条。并行子测试要在子测试内部调用 t.Parallel，父测试会等所有并行子测试注册完毕后再统一放行；因此不要在父测试循环里做会被并发改写的共享状态，也不要在子 goroutine 里调用 t.Fatalf。并行适合彼此独立、以 CPU 计算为主的用例；涉及同一个临时文件或同一个数据库连接的用例，并行只会制造随机失败。

接口与可测试性：依赖在使用方定义

Go 的接口是隐式实现的，这给测试留了很大空间。要让一个服务可测，最有效的办法不是引入 mock 框架，而是把外部依赖变成构造参数：服务只依赖一个小接口，真实实现和测试替身都满足它。

接口应定义在使用方所在的包，而不是实现方。仓储包不需要知道自己被谁抽象成什么样；使用方按自己需要的最小方法集声明接口，通常一到三个方法即可。接口越大，替身越难写，测试也越容易被迫关心无关方法。这也是“接受接口、返回结构体”的实际价值：构造函数接收接口便于替换，返回值用具体类型便于调用方使用完整能力。

但抽象要有理由。若某段逻辑只依赖标准库的缓冲区或只有一个实现且没有副作用，直接用真实对象更清楚。为了 mock 而给每个类型都配一个接口，会让调用链上多出一层没有信息量的间接，读代码的人需要在两个文件之间来回跳。

手写 fake：用状态说话

测试替身常见有三类。stub 只返回预设结果，不关心被调用几次；fake 则带一个简化的真实实现，例如用 map 充当仓储；mock 预先记录期望，测试结束时验证“某方法以某参数被调用了多少次”。前两者通常做状态验证：调用业务方法后检查 fake 里的数据或返回值；mock 做行为验证：检查协作对象是否被按要求调用。

testify/mock：用期望描述协作

testify 1.x 的 mock 包把期望写成链式声明：On 指定方法名与参数匹配器，Return 给出返回值，Once、Times 限制次数，最后用 AssertExpectations 统一检查。它适合协作关系明确、需要验证调用参数的场景。

几个细节值得注意。第一，Called 的参数必须与签名一致，返回值用 Get 加类型断言取出，断言失败会 panic，最好在辅助函数里统一处理。第二，mock.Anything 会放过任何值，用多了等于没验证；关键参数用具体值，上下文这类无法比较的对象才用它，或用 mock.MatchedBy 写一个小谓词。第三，AssertExpectations 只检查声明过的期望，未声明的方法被调用会直接让测试失败，这既是行为验证的价值，也是它脆弱的原因：实现里多调一次缓存，测试就可能红。第四，方法名是字符串，重命名时编译器不会提醒。

gomock：生成式 mock 与取舍

gomock 需要先用 mockgen 生成代码。source 模式从源文件解析接口：mockgen -source=repo.go -destination=mock/repo_mock.go -package=mock；reflect 模式则编译并反射目标包：mockgen -package=mock example.com/app/user UserRepo。前者不要求包可构建，适合接口独立的项目；后者能一次生成多个接口。生成物应提交到仓库，CI 不要依赖开发者本机是否装了 mockgen。

取舍可以简单化：接口多、协作方多、团队已经在用代码生成，选 gomock；只想快速替换一两个依赖，testify 的心智负担更小；依赖只有两三个方法，手写 fake 最直观。

HTTP 测试：从 handler 到中间件

处理函数本质上是“请求进、响应出”的纯函数，用 httptest.NewRecorder 就能在进程内调用，不必监听端口。

断言至少覆盖状态码、Content-Type 与关键字段；错误分支要单独建用例，检查返回的错误码与消息结构，而不是只测 200。中间件链的测试方法相同：把 handler 用中间件包起来再交给 recorder，重点验证鉴权失败是否短路、请求 ID 是否写回响应头、panic 是否被恢复成 500。需要验证真实客户端行为，例如超时、连接复用、重定向时，用 httptest.NewServer 启动一个临时服务器，把它的 URL 注入客户端，测试结束调用 Close。

数据库测试：sqlmock 的边界

go-sqlmock 1.x 实现了 database/sql/driver，可以拦截驱动调用，适合验证仓储层的参数传递与扫描逻辑。

ExpectQuery 与 ExpectExec 默认按正则匹配 SQL，空格、换行、列顺序稍有变化就会失配，所以要用 regexp.QuoteMeta 包住字面量，或者换成 QueryMatcherEqual。这种匹配本质上是在比较字符串，它既不解析 SQL，也不知道表结构；复杂查询改了索引或连接条件，sqlmock 依然会通过。因此不要在 sqlmock 里测多表 join、聚合、窗口函数，那些应该放集成测试。

更可靠的做法是准备一个真实测试库：TestMain 里建表并灌入基础数据，每个用例在事务中执行，结束时回滚，保证互不污染。仓储需要能接受 *sql.Tx，常见做法是让方法接收一个 Querier 接口，*sql.DB 与 *sql.Tx 都满足它。连接串由环境变量控制，未配置时 t.Skip。sqlmock 留给“参数是否正确传入”“扫描是否处理 NULL”这类小问题即可。

时间、随机与外部服务

时间是最常见的隐形依赖。直接调用 time.Now 的函数无法稳定测试月末、闰年与超时边界。把时间来源抽成只有一个 Now 方法的 Clock 接口，生产实现返回 time.Now，测试实现返回固定时刻或可推进的假时钟。这样“优惠券是否过期”“重试间隔是否退避”都能瞬间验证，不必 sleep 等待。

随机同理。math/rand 的全局函数若不显式设置种子，默认序列是固定的，测试之间还会互相影响。更好的做法是让被测代码接收 *rand.Rand，测试用 rand.New(rand.NewSource(42)) 构造独立实例；验证分布时跑固定次数并断言范围，不要断言具体序列。

外部 HTTP 服务用 httptest.NewServer 假扮：在 handler 里检查路径、请求头与请求体，返回预设 JSON 或指定状态码，再把服务器 URL 注入客户端配置。这样连重试也能测：让前两次返回 500，第三次返回 200，统计 handler 调用次数，就能确认重试策略。所有测试都应设超时，HTTP 客户端配置 Timeout，context 带 deadline；用 sleep 等 goroutine 完成是最脆弱的写法，应改为 channel 通知或 WaitGroup 等待。

测试组织：文件、辅助函数与 TestMain

测试文件与被测代码同目录，文件名以 _test.go 结尾。同包测试可以访问未导出标识符，适合白盒；package user_test 只走公开 API，适合充当“第一个外部用户”。两者可以共存，笔者通常把边界与错误分支放同包，把核心用例放外部包。

重复的构造代码抽成辅助函数，第一行调用 t.Helper()，失败时行号会指向调用处而不是辅助函数内部。测试数据放到 testdata 目录，go 工具链会忽略它；golden file 也放这里，用 ioutil.ReadFile 读取，比较前统一换行符。需要更新时加一个 -update 标志重写文件，评审时看 diff 即可。

CI 与稳定性：让失败可复现

CI 上推荐的基础命令是 go test -race -count=1 -timeout=120s ./...。-race 打开竞态检测，能抓到普通运行看不见的并发读写，代价是内存与时间成倍增加；-count=1 禁用结果缓存，避免“本地通过、CI 用旧缓存通过”；-timeout 防止死锁的用例把流水线挂住。包级并行由 -p 控制，用例级并行由 -parallel 控制。

当时 go test 还没有内置的随机顺序开关，想暴露顺序依赖，可以在 CI 里轮换 -run 的分组；更根本的办法是每个用例自己建依赖、自己清理，不共享包级变量。偶发失败一旦出现，先用 -count=100 -run TestX 复现，再检查四类原因：固定端口或临时文件名冲突、对时间与调度顺序的假设、未关闭的 goroutine 或连接、测试之间共享的可变状态。修复后让它连续跑一夜，确认不是概率变小而是根因消失。覆盖率门槛与统计口径属于另一篇文章的主题，这里不展开。

常见反模式

第一，测试实现细节。断言私有函数被调用、断言 SQL 字符串逐字相等、断言日志内容，都会让重构变成改测试。测试应该面向可观察行为：返回值、持久化结果、HTTP 响应。

第二，mock 过多。一个用例 mock 五个协作方，说明被测对象边界不清；每加一个依赖都要改一遍测试，团队很快会绕过测试。只在进程边界（数据库、HTTP、消息、时钟）做替身，内部协作尽量用真实对象。

第三，断言没有上下文。只写 if got != want { t.Fail() }，失败时看不出输入与期望。统一格式为“函数（输入） = 结果，want 期望”。

第四，共享可变状态。包级 map、单例连接、全局配置被多个用例修改，测试顺序一变就失败。测试应自建依赖；确实需要全局资源时，在 TestMain 里初始化并保证只读。

第五，忽略 goroutine 泄漏。启动了后台 goroutine 却没有退出路径，短时间看不出问题，-race 与长时间运行才会暴露。让每个 goroutine 都有 context 或 done channel，测试结束时等待它退出。

小结

单元测试的核心不是工具，而是边界：把不稳定的时间、网络与存储挡在接口之外，让核心逻辑可以用普通函数调用验证。表驱动与子测试负责组织用例，fake 负责状态，mock 负责协作契约，httptest 与 sqlmock 负责协议层。工具选型上，手写 fake 优先，testify 求快，gomock 求类型安全与调用约束。最后用 -race、-count=1 与超时把测试放进 CI，持续清理 flake，测试才会成为重构的底气。
