TypeORM 迁移与查询优化

本文属于《TypeScript 学习路线》第 72/74 篇
上一篇系列目录下一篇

把 TypeORM 用在真实项目里，难点往往不在实体怎么写，而在表结构如何安全演进、查询如何在数据量上来后仍然稳定。本文基于 TypeORM 0.2.x、Node 10/12 与 MySQL 5.7，从关闭 synchronize 讲到迁移的创建、执行与回滚，再进入 QueryBuilder、N+1、分页、索引和事务，目标是一套能评审、能回滚、也能被 EXPLAIN 验证的工作流。

从 synchronize 到迁移

为什么生产必须关掉同步

synchronize: true 会在连接建立后对比实体与库表结构，直接执行建表、加列、改类型、删列。开发初期它很省事，但依赖三个假设：库是空的、数据可以丢、没有并发访问，生产一条都不成立。

更麻烦的是没有评审记录。字段改名在同步逻辑看来就是“删旧列、加新列”，启动日志一闪而过，数据已经没了；大表上的 ALTER 还可能卡在元数据锁上，甚至拖到启动超时，多实例同时启动还会竞争。用 NODE_ENV 控制也不稳，配错一次保护就失效。稳妥的做法是硬编码为 false，开发和测试同样走迁移；生产改表只有一条路径：提交迁移文件、评审、在发布流程中单独执行。

四个命令与 up/down 的职责

TypeORM 0.2 的迁移由 CLI 驱动。先装 typeorm、mysql2、reflect-metadata 与 ts-node，在 package.json 里加入口：

migration:create 生成带时间戳的空类，适合手写 DDL 或数据修复；migration:generate 把实体元数据与当前库对比，自动写出差异，适合开发期起稿。migration:run 按文件名中的时间戳顺序执行尚未记录的迁移，migration:revert 只回退最后一条，退多条就多执行几次。

up 负责向前变更，down 负责撤销。可逆性要在写 up 时就设计：加列对应删列、建索引对应删索引，这类结构操作容易对称；删列、改类型、清洗数据则很难真正还原，down 至多把结构补回来，数据已经不在。这类迁移不要写看似能跑、实际丢数据的 down 充数，应在注释和发布说明里标明不可逆，执行前备份。另外，迁移一旦在任一环境执行过，就不要再改它的内容，修正应追加新迁移，否则记录相同、结构却不同。

连接配置与环境隔离

TypeORM 0.2 默认读取项目根目录的 ormconfig.json，需要读环境变量时改用 ormconfig.js。配置里最容易出错的是三个 glob：entities、migrations、subscribers。开发期写 src/**/*.ts，编译后必须指向 dist/**/*.js，否则 CLI 会报告“没有待执行迁移”，应用也可能在运行时才发现实体缺失。

cli 段只影响 CLI 生成文件的位置，必须与 migrations 的 glob 对得上。密码不要写进仓库，ormconfig.js 可以直接读 process.env，由启动脚本注入；多环境让同一份配置按 NODE_ENV 切换库名和 glob，连接名用 -c 区分。应用侧用 createConnection() 读取同一份配置，NestJS 6 则由 TypeOrmModule.forRoot() 代劳；CLI 走独立 Node 进程，两边要指向同一对象，否则会出现“应用能连、迁移找不到”的错位。

迁移编写规范

一个迁移只做一件事

把建索引、加列、回填数据、删旧列塞进同一个文件，失败时很难判断执行到哪一步，回滚也只能整段退回；拆开之后，每个文件都能单独评审、单独重试，发布节奏也可以拉开。命名用动词开头，例如 AddStatusToUser、BackfillUserStatus，不看代码就知道意图。生成的迁移先删无关 diff 再提交。

大表变更分阶段

大表变更不要指望一条 ALTER TABLE 解决。稳妥的是分阶段：先加一个允许 NULL 的新列，这一步只改结构；再按主键分批回填，每批一千行左右，批间留出间隔，避免长事务、undo 膨胀和主从延迟；然后让应用双写新旧列，读路径逐步切到新列并观察一段时间；最后才在后续版本删掉旧列。每步都能独立发布和回滚，影响面小。

flowchart LR
    A[加可空列] --> B[分批回填]
    B --> C[双写并切读]
    C --> D[后续版本删旧列]

给已有数据的表加非空且无默认值的列会失败；先加可空列、回填后再改约束，或保留可空由应用层保证。

在线 DDL 的边界

MySQL 5.7 的 Online DDL 能覆盖一部分操作：加二级索引、加列通常可以 ALGORITHM=INPLACE, LOCK=NONE，但加列仍可能重建表，改列类型、改字符集往往会退化成 COPY 并阻塞写入。即使是 online 操作，开始和结束也要短暂获取元数据锁，前面有长事务没提交，DDL 就会排队，后面的查询也跟着排队。用 lock_wait_timeout 让 DDL 快速失败，比无限等待安全。

PostgreSQL 11 的 CREATE INDEX CONCURRENTLY 可以不阻塞写入，但它不能放在事务块里，TypeORM 需要用 -t none 单独执行这条迁移；失败会留下无效索引，必须检查后删除重建。无论哪种库，都要在接近生产的数据量下演练，空表耗时没有参考价值。

DDL、事务与失败处理

MySQL 的 DDL 会隐式提交。迁移里先 ALTER TABLE 再写 DML，事务边界已经被切断，后面任何一步失败，前面改掉的结构都回不去；CREATE INDEX、DROP INDEX 同样如此。MySQL 8.0 的原子 DDL 只保证单条语句的崩溃安全，并不会把 DDL 纳入你的事务。TypeORM 默认会尝试用事务包住迁移，但这在 MySQL 上只能保护纯 DML，不能把 DDL 变成原子操作。PostgreSQL 的 DDL 是事务性的，失败可以整体回滚，代价是 DDL 期间持锁、系统表膨胀，所以同样要短。

迁移失败后不要急着“再跑一次”。migrations 表只记录成功执行完的迁移，失败的那条不在里面，但它的部分语句可能已经生效；盲目重跑，很可能卡在“列已存在”或“索引已存在”。正确做法是人工检查当前结构，能补则补，不能补就从备份恢复，再把修复写成新的迁移。DDL 迁移可以用 queryRunner.hasTable、hasColumn 做幂等判断，至少让重跑不会因为对象已存在而中断。

生产也不要把 migrationsRun: true 当默认选项。多个实例同时启动时，TypeORM 0.2 没有跨进程的迁移锁，两个进程可能同时读到“待执行”并一起执行。把迁移拆成独立发布步骤，只由一个任务执行，应用只负责连接。

QueryBuilder 与参数绑定

QueryBuilder 把 SQL 的结构留在 TypeScript 里，同时保留可控性。从 Repository 或 Connection 创建即可：

参数一律用命名占位符绑定，不要把变量拼进字符串。拼接不仅带来注入风险，也让执行计划难以复用；动态列名或排序字段要用白名单映射，不要直接接受前端传值。

innerJoin 只用于过滤或聚合，不会把关联对象放进结果；innerJoinAndSelect、leftJoinAndSelect 才会查出关联列并映射到实体。select 可以限制列，但用 getMany 时记得带上主键，否则实体去重和后续关联都会出问题。

getMany 返回实体数组并按主键去重，适合业务查询；getRawMany 返回扁平的原始行，列名就是 select 里的别名，适合聚合报表。需要总数时用 getManyAndCount，它会额外发一条 count 查询，别在循环里反复调用。

N+1 与关联加载

最典型的性能问题是在循环里查关联：先查出 100 个用户，再对每个用户执行一次 find 取文章，1 条查询就变成了 101 条。单条都快，总往返却放大百倍，日志里全是只差一个参数的同构 SQL。

改成一次 leftJoinAndSelect('user.posts', 'post')，或者在 find 的 relations 里声明 posts，都能把查询收敛成一条。leftJoinAndSelect 更直观，也方便继续加条件；relations 适合简单的加载场景。要注意一对多会让结果集按行膨胀：100 个用户每人 20 篇文章就是 2000 行，getMany 会去重，但网络和内存仍按 2000 行算。关联多、数据大时，拆成两次查询再在应用层拼装，往往比一条大 join 更稳。

eager: true 看似省事，代价是每次加载该实体都会带上关联，不管当前用例需不需要；层级一深，还会级联出意料之外的查询。它只适合几乎总要用到的配置类关联，列表页不要用，必要时用 loadEagerRelations: false 关掉。排查 N+1 不用猜，开发环境把 logging 设为 ['query']，或者给 maxQueryExecutionTime 设一个阈值，看一次请求发了几条 SQL、哪些重复。

分页：skip/take 与游标

skip/take 和 limit/offset 在 TypeORM 里不是同义词。skip/take 面向实体分页：查询带一对多 join 时，它会先用子查询取出当前页的主键，再按主键取完整数据，因此一页仍然是 20 个实体。limit/offset 直接落到 SQL 的 LIMIT/OFFSET，作用于 join 之后的行；一个用户有 5 篇文章，取 20 行可能只得到 4 个用户，翻页还会跳过或重复。规则很简单：实体分页用 skip/take，扁平的原始查询才用 limit/offset，两者不要混用。

OFFSET 100000 并不是跳过十万行不读，而是扫描后丢弃，越翻越慢。信息流这类场景更适合游标：用上一页最后一条的排序键做条件，而不是页号。

这里用 (created_at, id) 做联合游标，是因为 created_at 可能重复，只拿它做条件会漏行或重复，补上唯一的 id 才能稳定排序；索引也要按 (created_at, id) 建，否则条件写对了，执行计划仍可能走全表。游标分页不能跳到第 N 页，这是取舍；后台管理需要页码时，可以保留 offset，但限制最大深度，或者用延迟关联先取主键再回表。

索引与执行计划

索引要跟着查询走，而不是跟着表走。先列出高频查询的过滤、排序和返回列，再决定复合索引的列顺序：等值条件放前面，范围条件放后面，排序字段尽量与索引顺序一致，这样范围扫描之后不需要额外排序。最左前缀意味着 (status, created_at) 能服务 status = ? AND created_at >= ?，却服务不了只按 created_at 的查询；如果后者也高频，就要单独建索引。

覆盖索引能避免回表：查询需要的列都在索引里，读完索引就能返回。列表页只取 id、status、created_at 时，(status, created_at) 已经覆盖（InnoDB 二级索引自带主键），不必回到聚簇索引。但索引会变宽，写放大和空间占用都会增加，不要为了覆盖把所有列都塞进去。

验证靠 EXPLAIN，不靠感觉。重点看 type 是否从 ALL 变成 range 或 ref，key 是否命中预期索引，rows 的估算量是否可接受，Extra 里有没有 Using filesort、Using temporary。EXPLAIN 是优化器的估算，不是实际执行；数据分布倾斜时估算会偏，必要时用真实数据跑一遍。也不要在性别、状态这类低基数列上单独建索引，选择性太差，必须和其他条件组合才有意义。

事务边界与隔离级别

connection.transaction 把回调放进一个事务，正常返回就提交，抛错就回滚，适合大多数业务场景。隔离级别可作为第一个参数传入；MySQL 默认 REPEATABLE READ，PostgreSQL 11 默认 READ COMMITTED，两者对不可重复读和幻读的表现不同，跨库迁移时不能假设行为一致。需要更细的控制时用 QueryRunner：

release() 必须放在 finally，否则连接不回池，流量一上来就会耗尽。事务边界应落在业务用例上：一次下单的扣库存、写订单、记流水放在一起；调用外部支付、发消息、写文件不要放进去，这些操作无法随数据库回滚，还会把事务拖长。长事务持有行锁和旧版本数据，既阻塞 DDL，也拖慢 purge。锁的顺序要统一，死锁无法完全避免，但可以捕获后做有限次重试。

排查流程与常见坑

排查链路

排查性能可以固定成一条链路：先在开发或预发打开 SQL 日志，确认 ORM 发了什么；再到慢查询日志里按耗时排序，用 pt-query-digest 聚合；对目标 SQL 跑 EXPLAIN，看索引和扫描行数；然后改索引或改 SQL；最后用接近生产的数据量压测回归。生产不要长期开全量 query 日志，开销和磁盘都吃不消，用 maxQueryExecutionTime 只记录超过阈值的语句更现实。

常见坑

findOne 在 0.2 里既支持 findOne(id)，也支持 findOne({ where: { id } })；写成 findOne({ id }) 不会按 id 过滤，而是被当成空条件返回第一条，TypeScript 类型检查能挡住一部分，JS 项目里则很容易漏。save 会触发级联、实体监听器和订阅者，还可能先查一次再决定插入还是更新；update 直接 UPDATE，不触发这些钩子，也不处理级联，批量改数据时要想清楚用哪个。

迁移文件被 .gitignore 里的宽泛规则忽略，或者构建产物没带上 dist/migration，部署时就会“没有迁移可跑”；migration:generate 放到生产执行，则会拿实体和线上库做 diff，生成删列、删索引这类不可控变更。

小结

迁移与查询优化，本质是把隐式行为变成显式决定：关掉 synchronize，让每次改表都有文件、有评审、有回滚预案；用参数绑定和明确的关联加载写出可预测的 SQL；用 EXPLAIN 和真实数据验证索引，而不是凭直觉堆索引；把事务收在业务用例内，保持短小。做到这些，ORM 才只是工具，不会成为故障源。
