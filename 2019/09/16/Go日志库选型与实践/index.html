Go 日志库选型与实践

本文属于《Go 语言与工程》第 22/78 篇
上一篇系列目录下一篇

日志是最古老的可观测手段，也是最容易被写坏的一环。笔者所在的团队在今年上半年把三个 Go 服务从 logrus 迁到 zap，过程中踩的坑比预想的多：字段名不统一导致检索失灵、开发环境的 Debug 级别被带上生产、容器里按天切文件把磁盘写满。本文从日志的职责讲起，依次拆解标准库 log、logrus、zap、zerolog 的设计与取舍，再落到级别、采样、上下文、错误、轮转、性能与迁移这些工程细节上。读完之后，你应该能为自己的服务选一个合适的库，并且知道哪些坑可以提前绕开。

日志到底该记什么

日志有三个用途：排障、审计、指标补充。三者对日志的要求并不一样，混在一条流里，往往谁都做不好。

排障日志面向人。它需要足够的上下文（请求参数、下游返回、耗时、重试次数），允许冗余，保留期短，几天到两周即可。审计日志面向合规与追责，要求完整性、不可篡改、长期留存，字段固定，写入路径最好独立（单独文件或单独的消息队列），不能因为业务日志降级而被一起丢掉。指标补充则介于两者之间：日志能回答“这一条请求发生了什么”，指标回答“整体错误率是多少”。

把日志当指标用是常见的误区。每次查询都要扫全量文本，成本高、延迟大，量一上来索引先扛不住。要计数就用 counter，要分位就用 histogram，日志只负责保留个例样本。

与 tracing 的边界也值得说清。trace 回答“一次调用经过哪些服务、各段耗时多少”，log 回答“某一段里发生了什么”。两者靠 trace_id 关联，但不要把每个 span 都打成一条日志，也不要用日志拼凑调用链。最后一条：日志不是错误处理。if err != nil { log.Println(err) } 然后继续往下跑，是把错误吞掉，而不是处理错误。

日志是要花钱的

按每条几百字节、每天千万条估算，一天的原始日志就有几个 GB，加上副本与索引膨胀，实际占用往往是两三倍。保留一个月，就是几百 GB 的存储和相应的检索成本。所以保留策略要提前定：排障日志七到十四天，审计日志按合规要求单独保存，指标类信息根本不进日志。

字段设计也会影响成本。重复度高的字段（service、level、endpoint）在每条记录里位置固定、取值有限，压缩率就高；如果字段顺序每次都变，压缩算法找不到重复模式，存储会明显变大。这一点在 logrus 上尤其明显，因为 map 的遍历顺序是随机的。真实项目里不会有人为了压缩率去改日志库，但在选型时知道这个差异，能解释为什么同样的日志量，两个服务的磁盘占用差了一截。

标准库 log 的边界

标准库 log 只有三个可调项：输出目标、前缀、标志位。log.SetOutput 换 writer，log.SetFlags 控制时间、文件名、行号，log.SetPrefix 加前缀。包级函数背后是一个默认 Logger，用 log.New 可以造出互不干扰的实例。

它的局限也很清楚：没有级别，没有字段，没有采样，输出是自由文本；Printf 的格式化在调用点完成，无论这条日志最终是否输出，字符串都已经拼好了；包级函数共享全局状态，测试之间会互相污染。

标准库还剩一个有用的能力：log.New 接受任意 io.Writer，所以可以配合 io.MultiWriter 同时写文件和控制台。这在本地开发时很方便，但要注意 io.MultiWriter 是顺序写、任一目标报错就整体报错，不要在生产用它拼接网络 writer，一个慢目标会拖住所有日志调用。

那么什么时候标准库就够了？命令行工具、一次性脚本、服务启动早期的初始化日志（此时配置尚未加载，日志组件还没建好），以及规模很小、不打算长期演进的服务。判断标准可以很朴素：如果你从来没有按字段检索过日志，标准库完全够用。引入一个日志库的成本不只是依赖，还有团队要共同遵守的字段约定。

结构化日志：字段而不是句子

拼接字符串的日志，人和机器都难受。写下 log.Printf("user %d login failed from %s", uid, ip) 之后，想统计“某个 IP 的登录失败次数”，只能写正则去捞。结构化日志把一条记录拆成时间、级别、消息和若干键值对，序列化成 JSON，采集端直接解析成字段建索引。

字段命名要在团队层面统一，否则同一个含义会演化出 user_id、uid、userId 三种写法，检索时互相漏。笔者建议的约定是：time、level、msg 三个字段必备且由库生成；业务字段一律 snake_case；请求链路字段固定为 request_id 与 trace_id；单位写进字段名，用 cost_ms 而不是含义模糊的 cost；布尔值加 is_ 或 has_ 前缀。

还有一个容易忽略的点：高基数标签。把 user_id、order_id、完整 URL、原始 SQL 当作字段记录下来没问题，但不要拿它们做索引或聚合维度。聚合维度应当是 service、level、status_code、endpoint 这类取值有限的集合。这条经验和 Prometheus 的 label 规范是同一个道理，只是在日志系统里更容易被忽视，因为“多打一个字段又不花钱”的错觉很强。

字段的类型也要讲究。数字就存成 JSON number，不要先 strconv.Itoa 再当字符串写入，否则采集端要先做一次类型转换才能算分位数；布尔值同理，不要写成字符串 "true"，两种表示混在一起，聚合时会出现三个取值。耗时字段统一存毫秒或秒的数值，并在名字里标明单位，避免有人传 time.Duration 的纳秒值、有人传毫秒值，报表上差出六个数量级。

开发看文本，生产存 JSON

本地开发时 JSON 很难读，zap 的 Development 预设、zerolog 的 ConsoleWriter、logrus 的 TextFormatter 都能输出彩色文本。但要守住一条：开发与生产使用同一套字段名，只是渲染方式不同。笔者见过开发环境走 log.Printf 风格、生产才切 JSON 的项目，结果所有字段解析逻辑只在生产生效，联调时一切正常，上线后索引全是空的。字段一致性比可读性重要，可读性靠 Formatter 解决，不能靠换写法。

logrus：友好的 API 与它的代价

logrus 是当时最流行的选择，API 手感好：包级函数直接可用，WithField 与 WithFields 返回一个 *Entry，Hook 和 Formatter 都可以插拔。

Entry 是不可变的：每次 WithFields 都会复制一份字段 map。这既是优点（父子 logger 互不影响、并发安全），也是开销的来源。

性能瓶颈主要来自三处。其一，logrus.Fields 是 map[string]interface{}，写日志时要遍历 map，序列化时靠反射和类型断言逐个取值；其二，Logger 内部有一把互斥锁，所有并发写入被串行化，QPS 高时锁竞争很可观；其三，每次调用都会分配 Entry、map 和若干字符串，字段越多分配越多，最终都变成 GC 压力。

那它适合什么场景？QPS 不高、日志量以每天几 GB 计、团队更看重开发效率和 Hook 生态（直接推 Elasticsearch、发告警消息）的服务。以及作为迁移的起点：先用 logrus 把结构化字段的规范建立起来，再替换实现，比一步到位容易得多。

zap：类型化字段与 core 结构

zap 的设计目标很明确：在保持结构化输出的前提下，把每次写日志的分配压到最低。为此它放弃了两样东西：可变参数里的 interface{}，以及“随便传什么都行”的宽松接口。

最直观的体现是字段构造函数。zap.String、zap.Int64、zap.Duration、zap.Time 都是强类型的，编码器知道每个字段的确切类型，不需要反射。错误用 zap.Error(err)，它会根据错误类型选择字段名，比 zap.String("error", err.Error()) 多保留一层信息。实现了 fmt.Stringer 的对象用 zap.Stringer("peer", addr)，注意它是在日志真正输出时才调用 String()，因此 String() 里不要做重活。

Logger 与 SugaredLogger 的取舍是新手最常问的问题。logger.Sugar() 得到 SugaredLogger，可以用 Infow、Errorf 这类带格式化的写法，代价是参数走 interface{}，多一次装箱和类型判断。笔者的经验是：固定字段的调用一律用 Logger，只有确实需要格式化字符串、或者字段数量动态变化时才用 SugaredLogger，并且不要在同一个包里两种风格混用，否则读代码的人要反复确认这里到底会不会分配。

底层结构值得了解，因为所有定制都发生在这里。zapcore.Core 由三部分组成：Encoder 把字段编码成 JSON 或 console 文本，WriteSyncer 负责落地（文件、stdout、多路复用），LevelEnabler 负责过滤。zap.NewCore(encoder, sink, level) 可以拼出任意组合，zap.WrapCore 则能在不改调用点的情况下替换 core，采样、补字段、脱敏都靠它实现。

zap.NewProduction() 与 zap.NewDevelopment() 是两套预设：生产配置输出 JSON、级别 Info、开启采样、Error 以上附堆栈；开发配置输出 console 文本、级别 Debug、堆栈从 Warn 开始，并默认带上 caller。实际项目里更常见的是基于 zap.Config 修改：把 Encoding 换成 console、把 OutputPaths 指向 stdout，再用 cfg.Build() 生成。切记不要在生产使用 Development 配置，那等于把 Debug 日志全量打开。

zerolog：零分配的链式 API

zerolog 走的是另一条路：日志事件直接以 JSON 字节流的形式追加到缓冲区，尽量不做中间对象分配。官方文档里反复强调“zero allocation”，实现手段是把字段直接编码进 []byte，数字用 strconv.AppendInt 这类函数写入，避免 interface{} 装箱。

API 是链式的，log.Info() 返回一个 *Event，Str、Int、Err、Dur 依次追加字段，最后必须调用 Msg 或 Msgf 才会真正写出。漏掉 Msg 是一条常见 bug：代码能编译通过，日志却一条都没有。

zerolog.New(w) 接受任意 io.Writer，开发时套一层 zerolog.ConsoleWriter 就得到可读输出，生产直接写 JSON。级别可以用全局的 zerolog.SetGlobalLevel，也可以在子 logger 上 Level(zerolog.InfoLevel) 单独设置，后者在“某个模块临时开 Debug”时很有用。

zerolog 的取舍在于可读性。链式调用把“构造事件”和“写出事件”分离，字段多的时候一眼看不出这条日志最终长什么样；Msg 必须显式调用，也让静态检查难以兜底。它更适合日志量大、对分配敏感、并且团队已经习惯 JSON 检索的服务；如果团队里有人经常写错链式调用，收益会被调试成本吃掉。

三者对比：怎么选

把三者放在一起，差异主要在四个维度上，下表是笔者的总结，不含任何性能数字，因为数字依赖字段数量、编码器、输出目标，抄别人的结论没有意义。

维度 logrus zap zerolog
API 风格 方法调用 + Fields map 强类型字段函数 链式调用，末尾 Msg
扩展点 Hook、Formatter Core、Encoder、WriteSyncer Hook、LevelWriter
字段类型 interface{}，反射编码 编译期确定 编译期确定
并发模型 单锁串行 无锁（core 内自行加锁） 无锁，按 writer 同步
生态成熟度 Hook 最多 官方配置、采样、与 gRPC 集成完善 轻量，周边较少
适合场景 中小流量、快速开发 高流量、长期维护 极致轻量、日志密集

API 风格没有优劣，只有匹配。logrus 的 WithFields(map) 对动态字段友好，字段从 map 里来的时候不用逐个展开；zap 的强类型 API 在编译期就能发现拼写和类型错误，但字段多时代码行数明显变长；zerolog 最紧凑，代价是“必须记得写 Msg”。

性能结构上的差别，本质是“字段如何进入缓冲区”：反射加装箱、类型化编码、直接追加字节。前者灵活，后两者快。生态上，logrus 的 Hook 数量最多，很多老中间件只提供 logrus 适配；zap 的 zapcore 抽象最完整，做多路输出、按级别分流最顺手；zerolog 的周边相对少，但核心 API 稳定，依赖也最少。

维护活跃度方面，2019 年这三个库都在持续发版，zap 与 zerolog 的提交更密集，logrus 进入维护模式的说法在社区里已经出现，但它的接口稳定，老项目继续用并没有问题。选型时不必追新，先看团队现有代码和采集链路支持什么格式。

级别与采样：让日志量可控

四个级别的边界要划清楚。Debug 只在开发与排障时打开，记录变量值、分支走向这类细节，生产必须默认关闭。Info 记录业务状态变化，一条请求一到三条为宜（进入、关键状态、完成），不要拿它打印循环里的每一项。Warn 表示可恢复的异常：降级、重试后成功、配置缺失但用了默认值，需要有人偶尔扫一眼，但不至于半夜叫人。Error 表示需要人介入的失败：请求失败、依赖不可用、数据不一致。

生产默认级别设为 Info，这是最稳妥的起点。Fatal 要慎用，它内部调用 os.Exit，defer 不会执行，写在库里等于替调用方做生死决定；Panic 同理，只应出现在 main 里。

比级别更棘手的是日志风暴。一个下游超时，可能在几秒内产生几十万条几乎相同的错误，采集端被打挂，真正有用的日志反而被淹没。zap 内置了采样器，可以按级别和消息归并限流：

zerolog 提供了 logger.WithContext(ctx) 与 zerolog.Ctx(ctx)，可以直接把 logger 挂在 context 上；zap 没有内置这套机制，需要自己写一对 WithLogger、FromContext，key 用私有类型避免冲突。

这里有条原则：context 只放请求范围内的元数据——request_id、trace_id、必要的身份标识，以及（可选的）已经绑定好字段的 logger。不要把业务参数塞进 context 往三层函数里传，那是隐式依赖，读代码时看不出来，写测试时也根本构造不出正确的 context。

链路要真正串起来，下游调用必须把 id 传下去：HTTP 走 header，gRPC 走 metadata。日志里同时打 request_id 和 trace_id，前者由网关或本服务生成，后者由 tracing 组件生成，两者不要混用同一个值，否则排查时会得出错误结论。

如果某个函数要打很多条日志，把子 logger 作为参数显式传入，比每次都从 context 里取更清楚；从 context 取 logger 更适合中间件、框架这类横切逻辑。

错误日志：只在边界打一次

Go 1.13 带来了 %w、errors.Is 与 errors.Unwrap，错误可以逐层包装并保留原始类型。包装链好用，但日志策略要跟上，否则同一条错误会在每一层被打一遍，最后检索出五条内容相同、堆栈不同的记录。

规则可以概括成三句话：中间层返回错误时不打日志，最多留一条 Debug；在 HTTP、gRPC、消息消费这类边界上记录一次；堆栈只在边界采集。zap 的 zap.Error(err) 会识别实现了 fmt.Formatter 的错误并展开链条，zerolog 的 Err(err) 默认只取 Error() 字符串，需要额外调用 Stack() 或自己格式化，这一点在迁移时经常被忽略。

业务错误与系统错误要分开。ErrNotFound、参数校验失败属于预期分支，用 Warn 记录甚至不记录，不打堆栈；数据库超时、序列化失败、上游返回异常才是 Error。如果把“用户输错密码”打成 Error，告警阈值很快就失去意义，值班同学会学会忽略所有 Error。

还有一个容易混淆的边界：返回给调用方的错误和写给工程师看的日志不是一回事。前者要简短、稳定、不暴露内部结构，后者则可以带上 SQL、参数和完整错误链，两者不要互相代替。

几个参数的含义要弄清。MaxSize 是触发切分的阈值，不是硬上限，单条超大日志会让文件略微超出。MaxBackups 和 MaxAge 谁先满足谁生效，两者都设成 0 表示不清理，磁盘迟早写满。Compress 省空间但增加 CPU，日志量大的机器上要观察一下切分瞬间的抖动。

按天轮转的好处是文件名即日期，人肉排查方便；坏处是流量突增时单个文件可能好几个 GB，采集端读起来吃力，而且“当天”的边界依赖时区。按大小轮转更均衡，缺点是文件名与时间不对应，只能靠内容里的时间戳定位。笔者的建议是只保留一套机制：按大小切分，用 MaxAge 兜底，不要同时上 cron 和 lumberjack，否则两套逻辑会互相搬文件。

容器环境则相反：应用直接写 stdout，轮转交给容器 runtime 和采集 agent（fluentd、filebeat 之类）。应用自己切文件的前提是挂了 volume，否则容器一重建日志全丢。采集边界也要划清：业务进程只负责写，不负责传输和聚合，不要在请求路径上同步推 Elasticsearch，一次网络抖动就会拖慢整条链路。

性能实践：从调用点到压测

日志的损耗分布在四个地方，按影响从大到小是：输出（磁盘或网络 IO）、编码（反射还是类型化）、调用点的参数构造（字符串拼接、Sprintf）、锁竞争。选库只能解决第二项，其余三项要靠使用方式。

先说热路径上最常见的浪费：日志关了，参数还在算。

zap 的字段构造函数是普通函数参数，在进入 Debug 之前就已经求值；Check 返回 nil 时整段跳过。logger.Core().Enabled(zap.DebugLevel) 也能达到类似效果，但 Check 少一次调用。zerolog 在级别关闭时事件为空，后续 Str 是空操作，可同样救不了调用点已经算好的参数。

字段也要预分配。一条请求里要打五条日志、每条都带 request_id 和 user_id，正确做法是在入口 With 一次，把子 logger 传下去；每处重复传两个字段，不仅代码啰嗦，还多两次编码。

异步输出是另一条路，但要认清代价：

每个 Write 仍要复制一次字节，队列满时丢日志，进程退出前必须把 channel 排空，否则最后几条——往往正是崩溃前的关键日志——会丢。除非写入确实压垮了请求延迟，不建议上异步；真要用，务必把丢弃计数暴露成指标。

至于要不要优化，得自己量。不要抄博客上的纳秒数，机器、Go 版本、字段数量、输出目标都不同。写一个 testing.B，先排除 IO 干扰，再单独测真实落盘：

跑 go test -bench . -benchmem，重点看 allocs/op，它比 ns/op 更稳定，也更能解释 GC 压力。横向对比时保持字段数量、字段类型、输出目标完全一致；想看并发表现就加 b.RunParallel；想模拟真实场景，把 sink 分别换成 ioutil.Discard 和真实文件各跑一遍，两组差值就是 IO 成本。

迁移策略：抽象层要小

从 logrus 迁到 zap，最容易犯的错是直接把调用点全改成 zap，改到一半发现某处依赖 logrus 的 Hook。比较稳的顺序是先加一层薄抽象，再替换实现。

要点有三个。第一，不要照抄某个库的全量 API，Fatal、WithError 这类能力按需再加，接口越大适配成本越高。第二，字段类型用自己的 Field，不要直接返回 zap.Field，否则抽象层只是 zap 的别名，换库时调用点照样全改。第三，接口里不要出现 *logrus.Entry 或 *zap.Logger，具体类型一旦泄漏，抽象层就失去意义。

flowchart TD
    A[现状：直接调用 logrus] --> B[引入最小 Logger 接口]
    B --> C[适配器包装 logrus]
    C --> D[统一字段名/级别/时间格式]
    D --> E[实现 zap 适配器]
    E --> F[灰度一个非核心服务]
    F --> G[双写对比输出]
    G --> H[删除 logrus 依赖]

第四步的双写很关键，它能暴露“某个字段其实是在 logrus 的 Hook 里补上的”这类隐藏依赖。最后一句忠告：不要过早自研日志库。除非有多租户路由、特殊脱敏、与内部配置中心深度集成这类真实需求，否则自研的成本会集中在采样、轮转、并发安全、兼容性这些看不见的地方。用现成的库加一层薄封装，通常已经够了。

常见坑清单

全局 logger 被测试污染。 logrus.SetOutput(&buf) 之后忘记恢复，后面的测试全部写进上一个 buffer，断言随机失败。用 t.Cleanup 恢复现场，或者干脆在构造时注入实例，不碰包级函数。

字段顺序不稳定。 logrus 的 Fields 是 map，遍历顺序随机，两次输出的字段顺序可能不同，对整行文本做断言的测试会偶发失败。这不是 bug，但说明测试姿势不对：应该解析成 map 再比较。顺带一提，这也是坚持 JSON 输出的理由之一——按 key 取值，顺序无关。

把大对象整个打进日志。 用 %+v 打印整个请求体或整个结构体，单条日志几十 KB，采集端截断，磁盘飞快增长，还容易顺手把密码带出去。只打 id、数量和关键状态，大对象打长度或哈希。

敏感信息没有脱敏。 手机号、身份证、token、密码、Cookie 都可能出现在日志里。靠在每个调用点判断不可靠，正确位置是 core 或 encoder 层：字段名命中 password、token、secret 就替换成固定占位符。至少要做到这一层，别等审计时才想起来。

时区不统一。 应用按本地时间打日志、容器是 UTC、采集端又转一次，排查时差八小时，怎么也对不上。约定是：写入一律 UTC，用 Unix 时间戳或带 Z 的 RFC3339，展示层再转本地时区。lumberjack 的文件名可以用 LocalTime 方便人看，但内容里的时间必须是 UTC。

忘记 Sync。 用了缓冲 writer 却没在退出时 Sync，容器收到 SIGTERM 后最后几条日志丢失。把 defer logger.Sync() 放在 main 里，并配合信号处理做优雅退出。

在 init 里初始化日志。 配置还没加载，日志已经按默认值建好了，测试也无法替换。日志组件的构造应该显式发生在 main 或依赖注入的装配阶段。

让规范可执行

字段词表写在文档里，通常没有人看。可行的做法是把检查塞进流水线：用正则扫描源码里出现的字段名，白名单之外的 zap.String、WithField 直接让构建失败；把“业务代码不得出现 Fatal”做成 lint 规则；在 code review 清单里加一条“新增字段是否已登记”。这些手段都不高级，但比开会有效。

另一个经验是给高频字段提供构造函数，例如 log.OrderID(id)、log.RequestID(rid)，让正确写法比错误写法更省事。规范的落地从来不靠自觉，靠的是让违规变得麻烦。

小结

日志选型没有银弹，只有匹配。标准库适合小工具和启动阶段；logrus 的 API 与 Hook 生态最友好，适合中小流量与快速迭代；zap 的类型化字段与 core 抽象适合长期维护的高流量服务；zerolog 胜在轻量与分配，适合日志密集、团队也习惯链式风格的项目。

比选库更重要的是规范：统一字段名与时间格式、明确级别边界、在边界只打一次错误、用 request_id 串起链路、给日志量设上限。这些做不好，换哪个库都会在凌晨三点被叫起来。至于性能，先用 testing.B 在自己的场景里量一遍，再决定要不要优化——大多数服务的瓶颈不在日志编码，而在日志本身写得太多。
