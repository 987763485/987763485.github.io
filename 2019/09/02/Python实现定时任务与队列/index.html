Python 实现定时任务与队列

本文属于《Python 学习路线》第 18/29 篇
上一篇系列目录下一篇

定时任务与异步队列是后端服务里最容易“先跑起来、再补功课”的两块基础设施。本文从 Python 的视角出发，先比较进程内调度、系统 cron 与队列三种形态，再依次讲清 APScheduler 3.x 的用法与坑、Celery 4.x 的架构与任务设计，最后落到监控、部署和选型。读者最好写过 Flask 或 Django 项目，对 Redis 或 RabbitMQ 有基本印象。

定时任务的三种形态

定时任务看起来只是“到点执行一段代码”，但放进生产环境，首先要回答三个问题：由谁触发、触发失败谁来补、同一时刻允许跑几份。按触发者的位置，常见形态有三种。

进程内调度：在应用进程里启动一个调度器，最典型的是 APScheduler。优点是部署简单，任务可以直接复用应用里的配置、数据库连接与日志；缺点是调度器与业务进程同生共死，进程重启期间的触发点会错过，多副本部署时每个副本都会各自触发一次。

系统 cron：由操作系统按 crontab 触发脚本。优点是独立于应用、语言无关；缺点是感知不到业务状态，失败没有重试，输出只能重定向到日志文件，任务执行时间超过间隔时还会重叠。容器环境里还要额外处理时区、环境变量和 PID 1 的问题，很多基础镜像默认并不带 cron。

分布式队列的延迟任务：应用只负责把“要做什么”投递到 broker，由独立的 worker 在指定时间附近取出执行。它把触发与执行拆开，天然支持重试、削峰与横向扩容，代价是多了一套 broker 和 worker 需要运维。

选择时可以问四个问题：任务丢了能不能接受，能否容忍重复执行，单次执行有多久，未来要不要加机器。答案越偏向“不能丢、可能很久、要扩容”，就越应该走向队列。

APScheduler 基础

APScheduler 3.x 的模型由四部分组成：scheduler 负责协调，trigger 决定何时触发，jobstore 保存 job，executor 负责真正调用函数。把这四者的关系理清，配置就不会写成一团。

scheduler 常用两个：BlockingScheduler 会阻塞当前线程，适合独立脚本；BackgroundScheduler 在后台线程里运行，适合嵌进 Flask、Django 这类已有主循环的应用。两者 API 一致，只是启动方式不同。Web 项目通常在应用初始化时创建调度器，并保证只创建一次。

trigger 有三类：interval 按固定间隔，cron 按日历表达式，date 在某个时刻执行一次。日常用得最多的是 cron，它支持 day_of_week、hour、minute 等字段，语义与系统 cron 接近，但完全由 Python 计算，不依赖宿主机的 cron 实现。

jobstore 默认是 MemoryJobStore，进程结束 job 就没了；需要跨重启保留时换成 SQLAlchemyJobStore，把 job 写进数据库。executor 默认是线程池，CPU 密集型任务可以换进程池，但函数与参数必须可序列化。

id 是 job 的身份，replace_existing=True 让重复调用 add_job 时更新而不是报错，这在多进程启动或多处注册的场景里很重要。coalesce 与 misfire_grace_time 一起决定“错过的触发怎么办”，下一节会展开。

APScheduler 的常见坑

把 APScheduler 用在生产上，出问题的地方往往不在 API，而在进程模型与失败处理。

多进程重复执行。用 gunicorn 启动四个 worker，如果每个 worker 都在启动时创建一个 scheduler，同一个任务就会执行四次。APScheduler 3.x 的内存 jobstore 没有跨进程协调，数据库 jobstore 也不会自动加锁。可行的做法有三种：把调度器拆成单独进程，只由它触发；用 Redis 或数据库的分布式锁保证同一时间只有一个实例真正执行；让调度器只负责投递消息，执行交给队列 worker。最后一种最省心。

时区。scheduler 的 timezone、trigger 的 timezone、数据库里存的时间、宿主机的时间，任意两处不一致都会导致跑错点。建议统一在配置里写死 Asia/Shanghai，数据库存 UTC，只在展示层转换。使用 cron 触发器时还要考虑夏令时，国内不涉及，但服务面向海外用户时会遇到。

misfire_grace_time。调度器停机、线程池被占满、机器休眠，都会让任务迟到。迟到时间小于 grace 时会补跑，超过则记为 missed 并丢弃。这个值不是越大越好，补跑一个几小时前的任务，可能比不跑更危险。

任务重叠。max_instances 限制同一 job 的并发实例数，超过时新的触发会被跳过并记录一条 warning。如果任务耗时不可控，还应该加 coalesce=True，避免恢复后连续补跑多次。

异常被吞掉。APScheduler 会把 job 里的异常记录下来，但默认只写日志，不会让主流程感知。务必注册监听器，把失败接到统一的告警通道。

进程重启后内存 job 丢失。默认的 MemoryJobStore 只活在进程内，重启后必须靠代码重新注册。如果 job 是运营在后台动态添加的，就必须用持久化 jobstore；同时要保证 job 函数在代码升级后仍然可导入，否则恢复时会报错。

从定时任务到队列

即使调度器写得再稳，只要任务变重、变多，迟早会遇到三个瓶颈：触发与执行耦合在同一个进程，扩容时调度也跟着扩容；失败只能靠重跑整个流程；高峰期任务堆积，低谷期机器空闲。队列解决的正是这三件事：把“什么时候做”与“做什么”解耦，用 broker 缓冲峰值，用确认机制支持重试，用 worker 数量控制吞吐。

Celery 4.x 的架构由四个角色组成：producer 是业务代码，调用 delay 或 apply_async 把消息发出去；broker 保存消息，常用 Redis 或 RabbitMQ；worker 从 broker 取消息并执行；result backend 保存返回值与状态，属于可选项。消息里只放任务名和参数，真正的代码在 worker 一侧。

任务设计：幂等、参数与粒度

队列只保证至少一次投递。worker 崩溃、确认消息丢失、主动重试，都会让同一个任务执行多次，所以任务必须幂等。常见做法有三种：用业务唯一键建数据库唯一索引，重复插入直接忽略；用状态机做条件更新，例如 UPDATE orders SET status='paid' WHERE id=? AND status='pending'，根据受影响行数决定是否继续；或者用 Redis 的 SET key value NX EX 3600 做短期去重。锁的过期时间要覆盖任务的最长执行时间，否则前一个还没跑完，后一个已经拿到锁。

参数尽量小。消息里只传 ID、少量标量和版本号，任务内部再查数据库。不要传 ORM 对象、文件句柄或大字典，它们要么无法用 JSON 序列化，要么让消息体积膨胀，拖慢 broker 并占用内存。序列化器坚持用 JSON，不要为了省事开 pickle，后者在反序列化时可以执行任意代码。

任务粒度以“一个可独立重试的业务单元”为准。把下载、解析、入库、发通知塞进一个任务，任何一步失败都要从头再来；拆成四个任务用 chain 串起来，失败时可以只重试其中一环。但也不能拆得过碎，否则 broker 往返与状态管理的成本会超过任务本身。

超时。Celery 的 soft_time_limit 会在任务内部抛 SoftTimeLimitExceeded，给代码一个清理的机会；time_limit 由父进程强制杀掉子进程，无法捕获。长任务一定要设超时，否则一个卡死的任务会一直占着 worker 的并发槽位。

重试与失败处理

失败要分类。网络抖动、下游 5xx、锁冲突这类瞬时错误值得重试；参数错误、数据不存在、权限不足这类确定性错误重试多少次都一样，只会放大故障。Celery 4.2 之后可以用 autoretry_for 声明可重试的异常类型，配合 retry_backoff 做指数退避：

retry_backoff=True 让间隔按指数增长，retry_backoff_max 封顶，retry_jitter=True 加随机抖动，避免大量任务在同一时刻重试形成二次峰值。max_retries 必须设，无限重试会把一个坏任务变成永久循环。

需要在重试时改变参数或记录上下文，可以用 bind=True 拿到 self，调用 self.retry(exc=exc, countdown=...)，重试次数从 self.request.retries 读取。注意 self.retry 通过抛异常终止当前执行，它后面的代码不会运行，清理逻辑要放在 finally 里。

超过最大重试次数后，Celery 默认把任务标记为 FAILURE，消息被丢弃。如果业务不能接受丢消息，需要自己实现死信队列：在任务外层捕获最终失败，把任务名、参数、异常和失败次数写入失败表或另一个队列，再由人工或补偿任务处理。RabbitMQ 本身支持死信交换机，但配置与运维成本更高，很多团队选择在应用层做。

运营需要动态增删任务时，改配置文件再重启并不现实。当时的常见做法是数据库驱动的 scheduler，Django 项目用 django-celery-beat，把周期任务与 crontab 存表，beat 指定 DatabaseScheduler 后读取并投递，后台改完无需重启。非 Django 项目也有基于 SQLAlchemy 的同类实现，思路一致。

监控与部署

Flower 是当时最常用的面板，能看 worker、活跃任务、队列长度与历史结果，启动命令为 celery -A tasks flower --port=5555；命令行用 inspect active、inspect ping、status 做快速排查。队列积压要单独告警：Redis 看 list 长度，RabbitMQ 看 ready 与 unacked。积压持续增长，通常意味着 worker 不足、任务变慢或下游被拖住；worker 心跳丢失，则说明进程挂了或与 broker 断连。

日志要带任务 ID，业务日志通过 self.request.id 关联，失败任务才能和上下游串起来。耗时可以用 task_prerun、task_postrun 信号统一采集。告警阈值先观察真实分布再定，不要凭感觉。

部署时 worker 与 Web 进程分离，单独扩容、单独发布。并发模型默认 prefork，适合普通阻塞与 CPU 任务；I/O 密集且任务量很大时可换 gevent，但要求代码是协作式的。长期运行的 worker 容易内存泄漏，设置 worker_max_tasks_per_child 让子进程执行若干任务后主动替换。SIGTERM 触发 warm shutdown，会等待正在执行的任务，编排系统的停止宽限期要大于最长任务时间；配合 task_acks_late=True 和较小的 worker_prefetch_multiplier，被强杀的任务还能重新投递，但这更要求任务幂等。

选型与常见坑

方案 适用场景 主要限制
APScheduler 单实例、任务少、希望共享应用代码 无分布式协调，重启易丢 job
Celery Beat 已有 Celery 集群，统一定时与异步 beat 单点，动态调度要额外组件
系统 cron 与语言无关的运维脚本 无重试与观测，容器内不可靠
云定时任务 不想维护调度组件 触发粒度与网络访问受产品限制

单机少量任务用 APScheduler；已有 Celery 集群就用 beat；运维脚本用系统 cron；不想维护调度组件、又能接受厂商绑定，可以考虑云定时任务。本文示例按 Python 3.7 编写，3.8 将于 2019 年 10 月 14 日发布，海象运算符等新语法届时可用，但依赖生态跟进需要时间，生产环境不必急着改写法。

几个高频错误：把 Celery 当 RPC，在请求里 delay(...).get() 同步等结果，会占住 Web 进程，任务一慢就超时，甚至和同一 worker 池互相等待；result backend 无限增长，不需要结果时加 ignore_result=True 并设置 result_expires；在任务里复用 Web 进程的全局 ORM session，fork 后连接可能已损坏，应在任务内创建 session 并在 finally 关闭；时区不一致，beat、worker、数据库、cron 各说各话，部署后用测试任务核对实际触发时间。

小结

定时任务的核心是触发者、失败补偿与并发控制。小规模单实例可以用 APScheduler，但要接受它没有分布式协调；需要可靠执行、重试与扩容时交给 Celery，让 cron 或 beat 只做投递。任务要幂等、参数小、有超时，重试要分类并设上限。监控、时区与优雅停机这些非功能细节，往往才是线上事故的真正来源。
