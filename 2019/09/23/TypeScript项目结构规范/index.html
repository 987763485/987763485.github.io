TypeScript 项目结构规范

本文属于《TypeScript 学习路线》第 73/74 篇
上一篇系列目录下一篇

项目变大以后，真正拖慢团队的往往不是类型写不出来，而是文件放错位置、依赖方向混乱、构建脚本各写一套。本文面向已经能写 TypeScript、准备把一个小服务做成长期维护项目的读者，从目录、tsconfig、路径别名、项目引用一直讲到 lint、测试与 CI。读完后你应当能为一个 Node 服务落下第一版结构，并知道每个配置项在解决什么问题。本文不讨论类型语法，那部分留给语言本身的文章。

一、先定边界，再画目录

结构没有唯一答案，但有两个问题必须先回答：代码按什么切分，以及一个仓库里放几个可发布单元。

按职责分层适合业务规则相对稳定、团队人数不多的服务。domain 放实体与领域服务，application 放用例编排，infrastructure 放数据库、HTTP 客户端和消息队列适配器。它的好处是依赖方向单一，测试领域逻辑时不需要起数据库。

按功能垂直切分适合业务模块多、每个模块有自己的规则与数据的系统。每个 modules/order、modules/user 内部再分 controller、service、repository，修改一个需求通常只动一个目录。两者并不矛盾：大模块内部仍可分层，小项目不必为了分层而分层。

单体与多包的边界看发布节奏。只有一个部署单元、依赖版本总是一起升级时，单包加清晰目录就够；当 CLI、服务端和共享类型需要独立版本、独立发布时，再拆成多包。过早拆包会把一次重构变成跨仓库升级，成本远高于收益。

二、src 下的目录组织

推荐把可编译源码全部放进 src，让根目录只保留配置、脚本和文档。src 下按前面的选择放置 domain、application、infrastructure，或者只放 modules，不要两套体系并存。config 放环境配置的默认值与校验，scripts 放构建、迁移、数据修复等一次性命令，test 放跨模块的集成测试与测试工具。单元测试跟源码同目录，后文会解释原因。

层级不要超过四层。每多一层，导入路径就多一段 ../../，重构时移动文件的成本也随之上升。判断标准很简单：如果一个新的开发者要在脑海里数三层才能找到某个文件，这个目录就该压平。另一个常见错误是把编译产物和源码混在一起，dist、coverage 必须被排除在编辑器搜索和类型检查之外。

三、tsconfig 的关键项

tsconfig 不是越全越好，每一项都应对应一个明确后果。下面是一份面向 Node 服务的起点：

target 决定降级程度。Node 10 与 12 都支持 ES2018 的大部分语法，设为 es2018 可以保留 async/await 与对象展开，减少 helper 代码。module 与 moduleResolution 要匹配运行时：CommonJS 加 node 解析是 2019 年 Node 项目最稳妥的组合；若使用 ESM，需要额外的扩展名与互操作处理，不适合作为默认选项。

strict 是一组开关的总和，包含 strictNullChecks、noImplicitAny 等。新项目应一次打开；老项目逐步开启的策略放在最后一节。esModuleInterop 让 import express from 'express' 在 CommonJS 包上可用，代价是类型层面引入 synthetic default，团队需要统一写法。

skipLibCheck 跳过 node_modules 中声明文件的交叉检查，能显著缩短编译时间，但不会放过你自己代码里的类型错误。rootDir 与 outDir 决定产物目录结构；如果 rootDir 设错，dist 里会多出一层 src。declaration 为库或需要被其他包引用的模块打开，应用服务可以关闭以减少产物；sourceMap 建议始终打开，线上排错依赖它。

实际项目通常把配置拆成三份：tsconfig.json 供编辑器使用，tsconfig.build.json 负责产物，tsconfig.test.json 负责测试。基础文件只放共性，构建文件用 exclude 去掉测试，测试文件设置 noEmit 并补上测试框架类型。这样同一个仓库里，编辑器、CI 构建与测试各自读到正确的配置，不会互相污染。

四、路径别名与运行时解析

目录一深，../../../domain/user 这样的导入既难读又难改。baseUrl 与 paths 可以在编译期解决这个问题：

要紧的一点是：paths 只影响 TypeScript 的类型解析，不会改写编译后的 require。tsc 产出的 JavaScript 仍然写着 require("@domain/user")，Node 运行时找不到这个包。开发期用 ts-node 时，需要 ts-node -r tsconfig-paths/register；直接跑编译产物时，要么在入口最早处 require tsconfig-paths/register，要么让打包器在构建时把别名改写成相对路径。选择哪种方式取决于你是否打包，不能只在 tsconfig 里配完就认为结束。

发布 npm 包时还有第二个坑：declaration 生成的 d.ts 会保留别名。使用方没有同样的 paths 配置，编辑器就会报找不到模块。通用做法是公开入口只使用相对路径，或者在打包阶段用工具重写声明文件；把内部别名当成私有约定，不要让它出现在对外类型里。

五、项目引用与多包边界

当仓库里出现 shared、server、cli 三个包时，最直接的做法是各自 tsc，再按顺序复制产物。项目引用把这件事交给编译器：每个子包打开 composite，根 tsconfig 用 references 列出它们。

子包需要开启 composite，它会强制生成声明文件并写入 .tsbuildinfo。根目录执行 tsc --build 时，编译器先构建被依赖的包，再构建上层；第二次只重编变化的部分。配合 --watch 可以常驻，适合本地多包开发。

项目引用只解决构建顺序与增量，不解决包管理。依赖方向仍要写进规范：shared 不依赖 server，domain 不依赖 infrastructure。monorepo 的工具选择不在本文展开，但包边界应以“能否独立编译和测试”为检验标准。

引用路径指向子包目录而不是单个文件，TypeScript 会读取该目录的 tsconfig。若两个包互相引用，tsc --build 会直接报错，这比运行时才暴露循环依赖更早。composite 还要求源码位于 rootDir 内，把测试混进构建配置会破坏这个前提，因此构建与测试的配置要尽早分开。

六、用接口约束依赖方向

分层最容易破的地方是 domain 里直接 import 数据库客户端。一旦领域对象知道 SQL，单元测试就必须准备连接，换存储也会牵动业务代码。做法是把领域需要的操作定义成接口，由 infrastructure 实现，在应用启动时注入。

application 只依赖这个接口，infrastructure 提供具体实现。依赖方向从“高层依赖低层”反转为“低层实现高层定义的契约”，这就是依赖反转在工程结构里的落点。

@typescript-eslint 负责解析类型，规则本身仍是 ESLint 的。边界插件能表达更细的“只允许某层引用某层”，思路相同：把架构约束变成 CI 会失败的检查。新规则先设为 warn，清理完历史违反再改 error。

七、构建、运行与错误堆栈

开发期追求反馈速度，生产期追求可预测。常见组合是 ts-node 直接运行入口，nodemon 监听文件变化并重启；两者只用于本地。ts-node 默认做类型检查，项目变大后可加 --transpile-only 换取启动速度，把类型检查交给编辑器和 CI。

生产环境运行编译产物：先执行 tsc，再执行 node dist/main.js。构建配置可以继承基础配置，排除测试文件，并打开 noEmitOnError，避免把半成品发布出去。若使用路径别名，记得在入口加载解析器，或者干脆在构建时消除别名。

source map 要随部署包一起发布，并在进程入口加载 source-map-support，让错误堆栈指向 .ts 源码。不要把 map 放进公网静态目录，那等于公开源码结构。日志里记录构建版本与 commit，排错时才能把堆栈和代码对应起来。

八、规范、测试与 CI

代码规范与提交前检查

ESLint 管“可能出错”，Prettier 管“长什么样”，两者不要互相兼职。ESLint 6 配合 @typescript-eslint 2.x 读取类型信息，Prettier 1.x 负责缩进、引号与换行；用 eslint-config-prettier 关掉冲突规则，不要把格式化规则再写一遍。

规则数量要克制。一次引入上百条规则，团队会在文件头堆 disable 注释，最后没人再看。建议先启用 recommended，再加上与项目实际 bug 相关的几条：未处理的 Promise、误用 any、未使用变量。新规则先 warn，观察一周再决定是否升级。

提交前用 husky 加 lint-staged，只检查暂存文件：

这比全量 lint 快得多，也不会因为别人的旧文件挡住你的提交。规则配置放在独立的 .eslintrc.js，用 overrides 区分 src 与 test；编辑器读取同一份配置，保存时自动修复，CI 只做检查不做修复。若两边行为不一致，开发者会觉得规则时灵时不灵，进而习惯性地加 disable。

测试布局与测试配置

单元测试与源码同目录，命名 order.service.spec.ts，优点是移动文件时测试跟着走，导入路径短，审查代码时能直接看到覆盖情况。集成测试放 test/，因为它们往往需要数据库、消息队列或启动整个应用，生命周期与纯函数测试不同。

测试需要单独的 tsconfig，把 Jest 或 Mocha 的类型加进去，并排除在构建之外：

coverage 目录要同时加进 .gitignore、ESLint ignore 和 tsconfig exclude，否则编辑器会把生成的 HTML 当成源码。测试里的路径别名不生效，通常是因为 Jest 不读 tsconfig 的 paths，需要在 moduleNameMapper 里再写一遍，或者改用相对路径。

测试文件是否进入主配置的 include 也要统一。若主配置包含测试，构建时必须 exclude，否则 dist 里会出现 spec 文件；若主配置不包含，编辑器又可能缺少测试类型。折中方案是主配置只含 src，测试配置显式 extends 并加入 test，两份配置各司其职。

CI 流水线

CI 的顺序固定为 install、lint、typecheck、test、build。把便宜的检查放前面，失败得快；build 放最后，确保产物真的能生成。缓存 npm 缓存能缩短一半时间，但缓存键要带 package-lock.json 的哈希，否则依赖变更后仍在用旧缓存。

Node 10 与 12 的矩阵用于跑测试，lint 与 build 选一个主版本，避免重复消耗。还要加一条干净安装检查：在全新目录执行 npm ci 后构建，能发现漏提交的锁文件与只在本地存在的全局依赖。发布产物只从 CI 打出，不要从开发者机器直接上传。

多个 Node 版本不必重复跑全部步骤，可以拆成两个 job：主版本跑 lint、typecheck 与 build，所有版本只跑 test。job 之间通过缓存或构建产物传递，避免每个版本都重新安装依赖。流水线时间降下来，开发者才愿意在合并前等它跑完。

九、配置、文档与常见问题

配置按环境分层：config/default.ts 放默认值，config/production.ts 覆盖差异，启动时读取环境变量并校验。校验放在进程入口，缺端口、缺数据库地址就立即退出，不要等到第一个请求才报错。

密钥只从环境变量或密钥管理服务读取，不写进 default.ts，也不要把服务端配置打进前端包。前后端共享的只有公开配置，例如 API 基地址。

文档方面，README 至少写清启动命令、目录职责、环境变量和测试方式；每个目录放一个简短 README，说明这里放什么、不许放什么。架构决策记录不必上重流程：在 docs/adr 下按序号建 Markdown，写背景、决策、后果三段，一次决策一页，随代码一起评审。

常见问题集中在三处。循环依赖通常来自桶文件：a/index.ts 导出 service，service 又导入 b，而 b 从 a/index.ts 取类型，加载顺序一变就出现 undefined，减少桶文件、直接导入具体模块即可。桶文件还会让 Node 加载整个目录的副作用，启动变慢，测试也更容易互相污染。路径别名在测试中不生效，按上一节处理。strict 逐步开启时，先开 noImplicitAny 与 strictNullChecks，再处理 strictFunctionTypes 等；每开一项单独提交并修完，不要一次性打开后长期挂着几百个错误。

小结

项目结构的目标不是好看，而是让依赖方向可见、让改动范围可预测。先确定单包还是多包，再选分层或垂直切分；目录控制在四层以内，配置、脚本、测试各有固定位置。tsconfig 的每一项都要能说出影响，路径别名要同时考虑编译期与运行时。用项目引用管理多包构建，用 lint 规则把分层约束变成 CI 检查。最后把 lint、类型检查、测试、构建串成固定顺序，让规范靠工具执行，而不是靠记忆。
