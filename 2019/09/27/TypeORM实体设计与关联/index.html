TypeORM 实体设计与关联

本文属于《TypeScript 学习路线》第 71/74 篇
上一篇系列目录下一篇

实体层是 TypeORM 项目的地基。装饰器写起来很短，却同时决定数据库结构、查询行为和序列化结果。本文示例以 MySQL 5.7 和 TypeORM 0.2.x 为基线，PostgreSQL 的差异会单独说明。文章从表映射与列类型讲起，依次讨论主键、关系、级联、加载、索引、继承、钩子、软删除和测试，最后集中列出常见坑。读完之后，你应该能为中等规模的业务设计出边界清晰、行为可预期的实体层。

实体是表的投影

实体的本质是带元数据的类：类对应表，属性对应列，实例对应行。@Entity('users') 把 User 注册到 users 表；不写参数时 TypeORM 用类名当表名。在 Linux 上 MySQL 的表名大小写敏感，开发机与服务器配置不一致时，很容易遇到“表不存在”。因此本文建议显式写出表名，统一使用小写加下划线。TypeORM 0.2.x 通过 createConnection 建立连接，实体列表在连接配置里声明，漏注册的实体不会自动出现在元数据中。

列名同样值得显式声明。属性用 camelCase，数据库用 snake_case 是常见约定；可以逐列写 name，也可以引入命名策略统一转换。默认策略基本保持原名，社区的 snake case 策略会同时改写表名、列名、外键名和连接表名。两种做法都行，但不能混用：迁移生成后再换策略，等于所有表改名。项目起步时就要定下来，让实体、迁移和手写 SQL 共用一套命名。synchronize: true 只适合本地开发，正式建表与变更交给迁移，本文不展开迁移流程。

列类型与时间字段

@Column 的类型可以靠反射推断，但推断依赖 emitDecoratorMetadata 和编译配置，跨数据库时也不稳定。稳妥的做法是显式写 type，并把长度、精度、可空性一起写清楚。varchar 要给 length，它会影响 MySQL 5.7 在 utf8mb4 下的索引长度；金额用 decimal 并指定 precision 与 scale，不要用 float；bigint 与 decimal 在 mysql 驱动里以字符串返回，类型标注应如实写成 string，否则迟早遇到精度问题。

列默认是 NOT NULL，允许空必须写 nullable: true；default 只影响建表，不会在 JS 侧补值；select: false 让普通 find 跳过该列，适合密码哈希，但要用 QueryBuilder 的 addSelect 才能取回。文本字段还要在 varchar 与 text 之间做选择：前者适合有长度上限、需要索引的短文本，后者适合正文，但不能整列建索引。枚举在 MySQL 落成原生 enum，在 PostgreSQL 会创建独立类型，新增取值要改类型定义，业务状态通常更愿意用 varchar 加应用层校验。

MySQL 与 PostgreSQL 的类型并不一一对应：json 在 PostgreSQL 应写 jsonb；MySQL 没有原生 uuid，@PrimaryGeneratedColumn('uuid') 实际存成 varchar(36)，PostgreSQL 的 uuid 则需要先启用 uuid-ossp 扩展；布尔值在 MySQL 落成 tinyint(1)，在 PostgreSQL 是真正的 boolean。

时间字段最容易出事。MySQL 的 datetime 按字面值存储，不随时区转换；timestamp 按会话时区换算，还有 2038 年上限。PostgreSQL 的 timestamptz 存 UTC、按会话时区显示。跨时区业务应统一存 UTC：连接配置设 timezone: 'Z'，应用层只处理 UTC，展示时再转本地。需要毫秒时给 datetime 加 precision: 3，否则只到秒。@CreateDateColumn 与 @UpdateDateColumn 能省掉手写默认值，但类型和精度仍要显式指定，不能指望数据库替你把时区问题解决掉。

主键与外键

主键策略要早定。自增整数紧凑、有序，InnoDB 的聚簇索引按主键组织数据，插入局部性好；缺点是暴露规模，也不方便多库合并。UUID 可由应用生成，适合需要提前知道 ID 或跨服务合并的场景，但随机 UUID 会让聚簇索引的插入点分散，MySQL 里还要按 36 个字符的字符串存储。折中的做法是自增主键加一个对外唯一的业务 ID；有序 UUID 已经超出 0.2 的默认能力。

外键写在关系的拥有方。@JoinColumn({ name: 'author_id' }) 决定列名，TypeORM 默认会建外键约束。约束能保证引用完整性，但批量导入、分库分表或历史数据不干净时也会碍事。0.2.x 的关系装饰器没有关闭外键的开关，确实要关时只能在迁移里删掉生成的约束；代价是完整性由应用保证，并且要给外键列建普通索引，否则按作者查文章会全表扫描。onDelete 决定父行被物理删除时子行怎么办：RESTRICT 是默认值，CASCADE 连删，SET NULL 要求列可空。

关系与拥有方

关系分拥有方与反向方。拥有方持有外键列或连接表，只有它的改动会写库；反向方只是导航属性，方便写 post.author 这样的查询。@JoinColumn 与 @JoinTable 只能出现在拥有方；双向关系要两边都写装饰器，并用箭头函数回指，避免模块加载时的循环依赖。

Post.author 是 @ManyToOne，User.posts 是 @OneToMany，后者不是数据库列，只是把关系反过来看。@OneToOne 同样由带 @JoinColumn 的一侧拥有外键，TypeORM 会为这一列补一个唯一约束；如果手动改过表结构，要确认约束还在，否则同一个用户仍可能被两条 profile 指向。@ManyToMany 必须有一侧写 @JoinTable，中间表名和两个列名都建议显式指定：默认名由表名和属性名拼出来，改成 post_tags 后，DBA 和手写 SQL 都更容易读懂。若在反向方执行 tag.posts.push(post) 再保存，连接表不会变化，这是“关系没保存”最常见的原因。

级联与软删除

级联常被误解。cascade: true 是 ORM 层的传播：save(post) 会一并插入或更新 post.tags 中的实体，remove(post) 会删除这些关联实体。它不等于数据库的 ON DELETE CASCADE，后者只在 SQL 的 DELETE 真正落到父行时生效。两者可以同时用，但一个发生在 Repository 调用里，一个发生在数据库内部。

级联不是越多越好。cascade: true 包含 remove，删除一篇帖子可能连带删掉被多个帖子共享的标签；保存从请求体拼出来的大对象，也可能把没打算改的关联一起写掉。较稳的默认是只开 cascade: ['insert', 'update']，删除走显式调用；只有父子生命周期完全一致、子实体不会被别处引用时，才考虑 remove。

在官方版本落地前，最好把过滤条件收进仓储方法，避免每个查询都手写一遍。软删除不会触发数据库的 ON DELETE CASCADE，子表数据仍在，查询也不会自动过滤，需要在业务层一并处理。它还会和唯一约束打架：已软删除的行仍占着唯一键，再创建相同邮箱会失败。PostgreSQL 可以用带 WHERE deleted_at IS NULL 的部分唯一索引；MySQL 5.7 没有这个能力，只能把删除标记做成非空列并纳入唯一键，或在业务层校验。软删除适合“误删恢复”，不适合当归档；数据量长期增长时，仍要设计清理策略。

加载策略

加载策略有三种。eager: true 让每次 find 都自动带上关系，写法省事，但它是隐式的：列表页只想取标题，也会 JOIN 出全部作者和标签；多层 eager 叠加会让结果集膨胀，分页数量失真。lazy: true 把属性类型改成 Promise<T>，访问时再查库，读起来像普通属性，实际每次 await 都可能是一条 SQL；它依赖 Promise，序列化成 JSON 只会得到空对象，不适合直接返回前端。

本文的建议是默认不用 eager 和 lazy，在查询处显式写 relations: ['posts']，复杂查询用 QueryBuilder 的 leftJoinAndSelect。这样“这次请求到底查了什么”写在代码里，审查和优化都有据可依。循环里逐条 await 关系就是 N+1，识别与改法留给查询优化那篇。

索引与唯一约束

@Index 可以加在列上，也可以加在类上声明复合索引；@Unique 声明唯一约束，列上的 unique: true 是它的简写。复合索引的列顺序不能随便排：等值条件放前面，范围和排序放后面，查询才能用上最左前缀。订单列表常按租户、状态过滤再按时间倒序，索引应是 (tenant_id, status, created_at)，只建 (created_at) 基本没用。

索引和约束都建议显式命名，统一用 idx_表名_列名、uk_表名_列名。名字会进入迁移文件，默认名在不同版本里可能变化，排查慢查询时也不直观。索引并非越多越好，每个索引都会增加写入成本和磁盘占用，低选择性的布尔列单独建索引往往没有意义。MySQL 标识符最长 64 个字符，utf8mb4 下长字符串索引还受字节数限制，超长字段应改用前缀索引并在迁移里写 SQL。

继承与嵌入式

继承有三种常见用法，边界要分清。第一种是抽象基类：把 id、created_at 等公共列放在不带 @Entity 的基类里，子类各自建表，查询也各自独立。第二种是单表继承：父类加 @TableInheritance，子类用 @ChildEntity，所有字段挤在一张表，靠类型列区分；子类特有列必须 nullable，表会越来越宽，只适合子类型字段少、经常一起查询的场景。第三种是嵌入式：用 @Column(type => Money) 把值对象摊进同一张表，适合金额、地址这类没有独立身份的小对象。

不要为了复用几个字段就上继承。组合、显式重复两列，往往比一层抽象更容易读；单表继承尤其容易在半年后变成一堆 nullable 列。判断标准很简单：子类型是否真的需要多态查询，字段差异是否稳定；答案含糊时，就用独立实体加公共基类。

钩子、实体边界与序列化

钩子适合做纯内存的规范化：@BeforeInsert 里把邮箱转小写、生成 slug，@BeforeUpdate 里补齐派生字段，@AfterLoad 里计算只读的展示属性。这些都不引入额外 IO，也容易测试。把发邮件、写审计日志、调用远程接口放进钩子则是坏主意：钩子与 save 绑定，批量保存时会被放大，失败还会让整个事务回滚，而且它拿不到请求上下文。

更要记住触发范围：save 会触发监听器，repository.update()、insert()、delete() 以及 QueryBuilder 的批量更新不会。同一张表可能有两套写入口，一套经过钩子、一套不经过。若某条规则必须绝对成立，应放到数据库约束或统一的仓储方法里，而不是只靠 @BeforeUpdate。@AfterLoad 在每次加载实体时执行，包括关联加载，里面做重计算会拖慢所有查询。

实体也不等于接口模型。把 @Body() 直接声明成实体，等于把 id、role、balance 交给客户端；正确做法是单独的 DTO，用 class-validator 校验，再在服务层显式映射到实体。返回时同理：密码哈希即使加了 select: false，也可能在某个 addSelect 之后被带出来，最好再配合 class-transformer 的 @Exclude() 与 NestJS 的 ClassSerializerInterceptor，或者干脆返回 DTO。贫血实体在 CRUD 场景里并不可耻，只有当不变量复杂到需要行为封装时，才值得把领域逻辑放进实体。

测试、种子数据与常见坑

测试库要与开发库、生产库彻底分开。测试连接可以用 synchronize: true 建表，但只能指向一次性的库；dropSchema: true 会在每次连接时清空，适合本地与 CI，不适合共享环境。种子数据用固定内容的 fixture 或 factory 生成，每个用例只造自己需要的数据；不要从生产导一份 dump 再脱敏，既慢又容易泄漏。用例之间不要依赖自增 ID 的固定值，种子函数应返回实际插入的实体；需要清表时用 TRUNCATE 或事务回滚，而不是删除整个库。

事务回滚是常用的隔离手段：用 createQueryRunner 开启事务，把 queryRunner.manager 传给被测代码，用例结束后回滚。前提是仓储确实用了这个 manager；如果服务内部直接 getRepository，那条 SQL 跑在另一个连接上，回滚覆盖不到。MySQL 的 DDL 会隐式提交，建表要放在事务之外。

常见坑集中在几处。双向关系直接 JSON.stringify，会因 post.author.posts 的循环引用抛异常，返回 DTO 最省事。save 一个带空数组关系的对象会清空连接表，更新标量字段前应先查出实体。多对多中间表不显式命名，迁移和排查都难受。时区、select: false 忘记 addSelect、循环里查关系导致的 N+1，也都是上线后才暴露的典型问题；N+1 的优化在查询优化那篇展开。

小结

实体设计没有一套放之四海皆准的模板，但有几条稳定的原则：表名、列名和索引名显式写清楚；列类型与可空性不要依赖推断；关系只在拥有方写连接列，级联能少开就少开；加载策略显式声明，不用 eager 偷懒；钩子只做内存内的规范化；实体不直接充当请求和响应模型。把这些边界守住，实体层就能在需求变化时保持可读、可迁移、可排查。
