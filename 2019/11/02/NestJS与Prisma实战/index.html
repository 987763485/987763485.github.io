NestJS 与 Prisma 实战

本文属于《TypeScript 学习路线》第 69/74 篇
上一篇系列目录下一篇

把 Prisma 接进 NestJS，最容易被忽略的不是 API 怎么写，而是版本：2019 年下半年能用于生产的是 Prisma 1.x，Prisma 2 仍处于预览。两者的配置方式、client 构造和事务能力都不一样，网上不少示例已经把 2.x 的写法当成默认答案。本文以 Prisma 1.x 为准，环境取 NestJS 6.x、TypeScript 3.6、Node 12 和 PostgreSQL 11，从一个用户与文章的小服务出发，走完建模、部署、生成 client、接入 Nest、CRUD、关联查询、分页、事务和上线的整条链路，并明确标出 1.x 的能力边界。

为什么在 Nest 里选 Prisma

先厘清一个容易混淆的点：Prisma 1 不是把 ORM 塞进 Node 进程，而是把数据访问拆成“生成出来的 client”和“独立运行的 Prisma server”。client 只负责把调用翻译成 GraphQL 请求，server 再翻译成 SQL。这个结构多了一个运维组件，但也带来两个直接收益。

第一是类型安全。client 由 datamodel 生成，createUser、users、user 这些方法和它们的入参、返回值都有 TypeScript 类型；字段名写错、必填参数漏传，在编译期就会报错，而不是等请求进来才变成 500。第二是单一事实来源。表结构、关系、枚举都写在 datamodel.prisma 里，数据库迁移和 client 类型从同一份定义派生，不需要在实体装饰器和迁移脚本之间来回对照。

与 TypeORM 的差别可以用一句话概括：TypeORM 是进程内的传统 ORM，实体即代码；Prisma 1 把查询执行放到独立 server 后面，client 更像一个类型安全的远程数据访问层。两者都能完成 CRUD，选型的关键是团队是否愿意多运维一个组件，以及能否接受 schema 变更由 prisma deploy 主导。实体设计和迁移优化的细节不再展开，交给 TypeORM 的专文。

Prisma 1 的组成与 prisma.yml

Prisma 1 由四部分组成。Prisma server 是独立进程，持有数据库连接；管理 API 供 CLI 部署 datamodel、创建服务；query engine 在 server 内负责把 GraphQL 查询计划落成 SQL；生成的 client 则是应用代码唯一直接接触的对象。请求路径大致如下。

flowchart LR
    A[Nest Controller] --> B[Service]
    B --> C[Prisma Client]
    C -->|HTTP 与 GraphQL| D[Prisma Server]
    D --> E[(PostgreSQL)]

prisma.yml 是服务的根配置。endpoint 同时编码了 server 地址、服务名和 stage；datamodel 指向模型文件；secret 是服务 API 的密钥，省略它等于把接口暴露给任何能访问 endpoint 的人；generate 决定生成哪种语言的 client 以及输出目录；hooks.post-deploy 可以在部署后自动执行生成，避免忘记第二步。

endpoint 里的 /blog/dev 不是随便写的路径，blog 是服务名，dev 是 stage。生产换一个 stage 或独立 server，配置用环境变量注入，不要把真实地址和 secret 提交进仓库。

管理 API 与服务 API 是两条通道，也使用两套密钥：CLI 部署走管理 API，应用查询走服务 API，混用会得到 401。自托管时 server 通常用 Docker 运行，PRISMA_CONFIG 里配置数据库连接和端口；server 与 CLI 的大版本要保持一致，否则部署协议可能不兼容。

type 对应一张表，字段后的 ! 表示必填，[] 表示列表。@id 让 Prisma 生成 cuid 字符串主键，因此接口参数和 DTO 里的 id 都应该是 string，不要习惯性地用 ParseIntPipe。@unique 除了加唯一约束，还让该字段可以作为 user({ email }) 的查询条件。@default 处理默认值，枚举值直接写名字。@createdAt 与 @updatedAt 由 Prisma 维护，应用侧只读。枚举值只允许字母、数字和下划线，并且必须以大写字母开头；@unique 字段允许为 null，多个 null 不算冲突，这一点与 SQL 唯一索引一致。

关系要两边都写，@relation 的 name 用于消歧，onDelete 决定父记录删除时子记录怎么办。上面的 posts 标了 CASCADE，删用户会连带删文章；默认行为是 SET_NULL，如果关系字段又是必填，删除就会失败。注意 1.x 不允许双向关系两端都设 CASCADE。

还有一个限制值得提前知道：Prisma 1 的 datamodel 只直接表达唯一约束，@unique 会在库里建唯一索引；普通索引和复合索引没有对应的指令，只能在数据库上手工创建，并写进部署清单。这一点在性能部分还会提到。

部署、生成与生产变更

本地先用 Docker 起一个 Prisma server，再装 CLI。数据库选 PostgreSQL 11，connector 配好之后，server 会自己维护迁移状态。初始化与部署的命令很直接。

prisma deploy 做两件事：把 datamodel 与 server 上的版本做 diff，执行数据库变更；把服务 API 更新到新模型。prisma generate 则根据部署后的 schema 生成 client。顺序不能反：先生成再部署，client 可能认识旧字段，却不认识新表。把 prisma generate 放进 post-deploy 钩子，是成本最低的防错手段。

日常改模型可以固定为五步：改 datamodel.prisma；在测试环境 prisma deploy；确认数据影响并备份；prisma generate；重启应用。prisma deploy 遇到可能丢数据的变更会要求确认，--force 会跳过确认，这个参数只应该出现在明确知道后果的脚本里。

Prisma 1 的迁移由 deploy 管理，项目里没有一串可审阅的 SQL 迁移文件。好处是改完模型就能部署；坏处是变更内容不透明，重命名字段往往被识别成“删旧列、加新列”，数据不会自动搬过去。安全做法是 expand-migrate-contract：先加新字段并双写，再迁移数据，确认没有读旧字段后再删旧字段，分三次部署完成。生产发布还要把独立 stage、部署前 pg_dump、CI 人工审批和回滚方案写进流程。prisma export 导出的是规范化 JSON，适合搬数据，不能替代数据库备份；手工建的索引和手工 SQL 数据迁移也要单独记录，因为 deploy 不会替我们生成它们。

接入 Nest：模块、服务与注入

Prisma client 是一个普通类，最自然的接法是继承它并注册为 Nest provider。

这里必须点破一个版本差异：Prisma 1 的 client 基于 HTTP，没有 Prisma 2 预览版里的 $connect() 和 $disconnect()。onModuleInit 里做一次探测，是为了让 endpoint 写错或 server 没起来时尽早失败；onModuleDestroy 对 1.x 没有连接可断，留空即可。如果项目另外用 pg 直连数据库做事务，那个池才需要在 onModuleDestroy 里 end()。照抄 2.x 模板会在启动时报 this.$connect is not a function。别忘记在入口调用 app.enableShutdownHooks()，否则容器发 SIGTERM 时钩子不会执行。

模块是否加 @Global() 要看项目规模。全局模块省掉每个特性模块的 imports，适合 Prisma 这种基础设施；代价是依赖关系被隐藏，新同事看不出某个 service 的数据能力从哪里来。模块多、边界要求高时，宁可让每个特性模块显式 import PrismaModule。如果不想继承 client，也可以改用组合，把实例放在私有字段里；继承胜在能直接使用生成的全部方法，代价是类型面很大。

注入之后，CRUD 几乎就是一对一的映射。

生成 client 的方法命名有规律：单条查询是单数 user，列表是复数 users，写入是 createUser、updateUser、deleteUser。createUser 的入参直接是字段对象，没有 Prisma 2 预览线的 data 包装；updateUser 才用 { where, data }。user({ id }) 查不到时返回 null，不是抛异常，service 里要显式判断并抛 NotFoundException，否则 controller 会把 null 当成 200 返回。

读取关联数据时，Prisma 1 没有 Prisma 2 预览线的 include/select。单条记录用 fluent API 链式取关系，列表则用 $fragment 一次把需要的字段和关系取回来。

$fragment 里的字符串是 GraphQL 片段，字段名写错不会在编译期报错，这是它不如主 API 类型安全的地方。列表上的关系不能直接链式取，users().posts() 这种写法在 1.x 里不成立；要么用 $fragment，要么先取列表再按 id 批量查，后者很容易滑向 N+1。

更新关系也有对应的嵌套操作：update 改关联记录，delete 删关联记录，upsert 存在则改、不存在则建。删除父记录前先想清楚级联范围，CASCADE 很省事，但误删的代价也更大。单条记录的 fluent 查询是两次往返，详情页可以接受，列表页就应改成一次 $fragment。

分页、过滤与排序

分页参数是 first、skip、after、before、last。first 配 after 是游标分页，first 配 skip 是偏移分页。过滤用 where，字符串字段有 _contains、_in、_gt 等后缀，多个条件用 AND/OR 组合；排序用单个 orderBy 字符串，例如 createdAt_DESC。

where 的后缀由字段类型决定：字符串有 _contains、_starts_with、_ends_with，数值和日期有 _gt、_gte、_lt、_lte，枚举和布尔直接等值。关系过滤用 posts_some、posts_every、posts_none，例如 posts_some: { published: true } 表示至少有一篇已发布文章；这类条件生成 SQL 时可能带子查询，数据量大时要用执行计划确认。

游标分页在数据频繁插入时更稳，不会像 offset 那样出现重复或漏项；代价是不能直接跳页，前端要按“下一页”设计。offset 适合后台管理这类需要页码的场景，但 skip 很大时数据库仍要扫描前面的行。总数用 connection 的 aggregate().count() 单独查，不要为了拿总数把整页数据再取一遍。游标分页还要求排序值稳定：按 createdAt 排序时，如果多条记录时间相同，边界上仍可能重复或漏记录；对时间精度没有把握时，后台列表用 offset 更省心。

事务边界

Prisma 1 的事务能力要分两种情况。单次嵌套写入在 PostgreSQL 和 MySQL 上是原子的：创建用户和它的文章要么都成功，要么都回滚，这是 server 在一条 mutation 里完成的。跨多个聚合的操作则没有 $transaction 可用；1.x 没有把多个 client 调用包进一个事务的公开 API，Prisma 2 预览里的相关能力当时也不能当作生产依赖。

还要注意，嵌套写入的原子性只在关系图内成立；一次业务如果要改用户、订单和审计三棵独立的树，即使同库，也不要把希望寄托在单次 mutation 上。

需要强一致时有三条路。第一，把操作设计成一次嵌套写入，让它们落在同一个关系图里。第二，绕开 Prisma server，用 pg 或 mysql2 开数据库事务，直接执行 SQL；代价是这部分逻辑失去 client 的类型保护，也要单独管理连接池。第三，接受最终一致，用补偿或状态机处理失败。转账、扣库存这类场景不要指望“多调几次 client，失败再重试”能保证原子性。

错误处理、测试与性能

错误处理的目标是：业务能识别，用户能理解，日志能定位，响应不泄露底层结构。唯一约束冲突在 Prisma 1.3x 里的错误码是 3010，message 会带模型和字段名，不要在 controller 里直接返回给前端。建议在全局异常过滤器里集中映射：3010 转 409，记录不存在转 404，连接失败或 server 不可达转 503，其余未识别错误记日志后返回 500 和通用文案。错误码可能随版本变化，过滤器里留一条基于错误类型的兜底判断，比把数字散落在业务代码里稳。

记录不存在通常不是数据库错误，而是 user({ id }) 返回 null；在 service 里判断并抛 404，比让后续代码访问 null.email 更可控。连接失败的原始错误可能带 endpoint、主机名和端口，日志里保留，响应里只给“数据服务暂时不可用”。

测试上，service 层可以把 PrismaService 替换成对象 mock，验证参数拼装和分支逻辑；但 mock 不会验证 where 语法、关系字段和事务行为，这些要靠连真实 Prisma server 的集成测试。测试库用独立数据库和独立 endpoint，套件之间用 TRUNCATE "User", "Post" CASCADE 清表，比每个用例都 prisma reset --force 快得多。e2e 用 Test.createTestingModule 启动应用，再配 supertest 打接口；涉及并发的用例不要共享同一批数据。

性能上，Prisma 1 每次调用都是一次到 Prisma server 的 HTTP 请求，列表里逐条取关联很容易变成 N+1；用 $fragment 一次取回，或者接受分页后按页批量取。只取需要的字段，别把大文本和 BLOB 带进列表。索引方面，@unique 自动建唯一索引，createdAt 这类排序列要在库里手工建索引，并用 EXPLAIN ANALYZE 验证。连接池在 Prisma server 一侧，应用实例增多不会成倍放大数据库连接，这是它的好处；反过来说，server 本身要监控和扩容，不能只盯着 Nest 进程。

常见坑还有几个：把 endpoint 和 secret 写进代码或提交 .env，secret 泄露等于数据 API 裸奔；改了 datamodel 忘记 prisma generate，编辑器还认旧类型，运行时却已经换了 schema；部署和生成顺序颠倒，client 会落后一个版本；生产误连开发 endpoint，轻则写进测试库，重则把开发数据当生产数据展示；把 Prisma 2 预览线的 schema.prisma、新的 client 类、$connect，以及后来才有的 $transaction 抄进 1.x 项目，代码看起来更现代，实际一个都跑不起来。

小结

Prisma 1 在 2019 年的定位很明确：它用独立的 Prisma server 换取类型安全的 client 和声明式的数据模型，适合愿意多运维一个组件、并且能接受 schema 变更由 CLI 主导的团队。它的风险也同样明确：迁移过程不透明、跨聚合事务能力弱、普通索引要手工维护。Prisma 2 的预览线值得关注，尤其是单文件 schema 和更轻的运行时，但在本文的时间点它还不是生产方案。选型时先把版本钉死，再把部署、备份和回滚流程跑通，比追新更重要。如果团队暂时没有精力维护 Prisma server，继续用 TypeORM 并等待 Prisma 2 走出预览，也是一种合理选择；技术选型要服务于交付节奏，而不是版本号。
