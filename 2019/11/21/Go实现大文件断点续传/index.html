Go 实现大文件断点续传

本文属于《Go 语言与工程》第 69/78 篇
上一篇系列目录下一篇

把 2 GB 文件一次性 POST 上去，失败一次就要从头再来；弱网、网关超时、进程崩溃，都会让已传完的几百兆白费。断点续传要解决的是“传了一半之后怎么办”。本文讲协议分工、分片会话、断点查询、校验合并与并发边界，不展开 multipart 报文。

从问题到设计：协议层与业务层各管什么

大文件上传会撞上几堵墙：单请求时间长，中间设备可能先超时；弱网带宽抖动，失败概率随文件增大；重试若从零开始，流量和磁盘写入都白费；重复点击还可能把同一文件传很多遍。断点续传把长传输拆成可重试的短请求，把整体失败降为局部失败。

职责要分开。协议层只管分片、会话、断点和完整性；业务层管权限、配额、归属、存储和扫描。混在一起，协议会被业务字段撑大，客户端也得理解存储细节。HTTP 没有通用的断点续传上传标准：Range 是下载时的部分读取，multipart 只解决单请求内的字段封装，都不跨请求记忆状态。因此要定义一层小协议，说清创建会话、查询、上传、合并、取消五件事。

会话要记录上传 ID、分片大小、总片数、总大小、整文件哈希和已完成位图，并配一条状态机：init → uploading → merging → done，失败退回 uploading 或 failed，超时变 expired，主动取消为 canceled。每次转换都要带条件，单机用会话锁，多机用数据库条件更新；受影响行数为 0 说明别人先转了。done 不再收分片，重复合并返回首次结果；merging 期间到达的分片要拒绝；failed 保留分片供重试。

flowchart TD
    A[init 创建会话] --> B[uploading 接收分片]
    B -->|客户端请求合并| C[merging 合并与校验]
    C -->|成功| D[done 完成]
    C -->|失败| B
    B -->|取消| E[canceled]
    B -->|超过有效期| F[expired]

分片策略：大小、数量与偏移

分片大小决定偏移算法。固定大小最省心：第 i 片偏移为 i * chunkSize，长度等于 chunkSize，最后一片取 fileSize - i * chunkSize。动态分片能适应网络，但每片都要记偏移和长度，还要处理同一区间被不同大小切过的历史数据，复杂度不划算。本文只采用会话内固定大小，创建后不允许修改。

大小是权衡。分片太小，请求数、元数据、校验和连接开销都会放大，10 GB 按 256 KB 切就是四万片；分片太大，单次失败重传的字节多，占用连接时间长，也容易撞上代理的请求体上限。常见落点是 1 MB 到 10 MB，内网可偏大、公网弱网可偏小；具体值由服务端给出允许范围，客户端在范围内选择，不要写死。

数量要有上限。限制单文件 20 GB、单片最小 1 MB，最多两万片，再大就拒绝，既保护位图与日志，也避免海量小请求拖垮服务。最后一片可小于标准大小但不能为 0，空文件建议走普通上传。偏移必须由服务端按会话参数计算，客户端只报索引；这样客户端记错分片大小时，入口的长度校验能立刻发现，而不会把数据写到错误位置。

服务端接口设计

接口保持资源化，五个动作对应五个端点。创建会话提交文件名、总大小、期望分片大小和整文件哈希，服务端校验范围、生成不可猜测的上传 ID，返回实际分片大小、总片数和过期时间。分片接口直接收原始字节，Content-Type 为 application/octet-stream，不再套 multipart，少一层解析和临时文件。

方法与路径 作用 成功状态
POST /v1/uploads 创建会话，返回 uploadId 与分片参数 201
GET /v1/uploads/{id} 查询状态与已落盘分片 200
PUT /v1/uploads/{id}/chunks/{index} 上传一个分片 204
POST /v1/uploads/{id}/complete 校验并合并 200
DELETE /v1/uploads/{id} 取消并清理 204

分片用 PUT，因为 PUT 幂等：同一 uploadId + index 重复提交结果应一样。客户端超时后不知道服务端是否收到，最安全的做法是原样重试；服务端发现该索引已有分片且哈希一致，返回 204，不一致返回 409，不能默默覆盖。创建会话可接受 Idempotency-Key，避免连点生成两个会话；合并以会话为幂等键，完成后再调返回同一结果。

状态码要说明责任：参数或长度不符 400，未登录 401，不存在或非本人统一 404（不用 403 泄露 ID 是否存在），状态冲突 409，过期 410，哈希不符 422，限流 429，磁盘失败 500。uploadId 是标识符不是凭证，必须绑定用户；四个操作都校验登录用户，分享时另发一次性令牌。

分片写入与断点查询

写分片的顺序：鉴权、加载会话、检查状态与索引、核对 Content-Length、限制请求体、边写临时文件边算哈希、校验长度与哈希、会话锁内发布、更新元数据。长度检查放在读请求体之前；要求准确长度，chunked 不可知，应拒绝。MaxBytesReader 防止声明长度后多塞字节。

关键是顺序与原子性。临时文件和目标文件同目录，os.Rename 才是同文件系统内的原子替换；跨文件系统会返回 EXDEV，只能复制加删除。TempFile 以 0600 创建，目录 0700。发布放在会话锁内，保证“检查旧哈希、重命名、更新元数据”不被同索引请求插队。

断点查询不能只听客户端说传完了。服务端扫描分片目录，确认文件存在且长度等于 chunkLen(i)，再返回已完成索引；位图更紧凑，两万片只需 2500 字节，Base64 放进 JSON 即可。位图是缓存，目录是事实来源；元数据丢失可从目录重建，只信内存表则重启后会把已传分片当成没传。客户端拿位图取交集，只补缺失索引，不把本地记录当成服务端状态。

校验与合并

分片校验有两层。CRC32 快，适合发现偶然位翻转；SHA-256 慢，但能抵抗有意的碰撞构造。只防网络错误，CRC32 足够；分片来自不可信客户端或要留审计证据，就用 SHA-256。本文统一 SHA-256，省两套字段；性能敏感时也可每片 CRC32 快速筛错、合并时再算整文件 SHA-256。

哈希要边读边算。hash.Hash 实现了 io.Writer，与文件一起放进 io.MultiWriter，一次 io.Copy 同时完成落盘和摘要；校验读文件同理。整文件哈希在合并时顺带计算，不再把成品完整读一遍。合并的三个约束是按索引顺序、恒定内存、失败可回滚：先确认分片齐全且长度正确，再写 .merging 临时文件，从 0 到 totalChunks-1 依次 io.Copy，同时喂给整文件哈希，最后核对总长度与哈希，Sync、Close、原子重命名。

合并也要幂等。两个 complete 同时到达，只允许一个把 uploading 改成 merging；另一个看到 merging 返回 202 或 409，看到 done 返回首次结果。成功后删分片释放空间，但保留结果记录一段时间，否则客户端重试 complete 会得到 404，无法确认是否成功。失败不删分片、不留 .merging，下次重拼；整文件哈希反复不匹配则标记 failed，让客户端重算后重传。

并发上传与磁盘 IO

客户端并发不是越大越好。每片都是一次完整请求，服务端要写文件、算哈希、fsync、更新元数据；并发太高会让磁盘来回寻道、fsync 排队，带宽也被切碎。公网通常 3 到 5 个并发，内网 8 个左右；服务端按用户和全局各设信号量，超出排队或返回 429。每片 fsync 能保证掉电后已确认分片不丢，若允许崩溃后重传少量分片，可只在合并时刷；文档要写清 204 代表页缓存还是已落盘。

乱序到达正常：分片按索引命名，合并按索引遍历，到达顺序不影响结果。重复分片用哈希判断，内容一致就当成功，不一致拒绝。两个请求同时写同一索引时各写临时文件，发布阶段用会话锁串行化，最后只有一个重命名生效。

合并与写入之间要有屏障。合并开始时索引可能看似齐全，但某请求还在写临时文件，遍历会读到半截文件。把“发布分片”和“开始合并”放在同一把会话锁里：合并先把状态改成 merging，后续分片请求看到状态不对就拒绝，只有锁内完成重命名的分片才算数。位图更新与文件落盘必须作为整体。

Range 的边界与客户端实现

Range 常被误当成断点续传的通用答案。它只定义已存在资源的部分读取：客户端发 Range: bytes=1048576-，服务端返回 206 和 Content-Range；不支持就忽略并返回 200；起点越界返回 416。它适合下载续传，不适合上传分片：HTTP 没有规定 PUT 加 Content-Range 的标准行为，不同代理差异很大。

下载续传还需一致性保护。记录偏移时同时记录 ETag 或最后修改时间，再次请求带上 If-Range；资源变了就返回 200，避免把新文件后半段拼到旧文件前半段。上传完成后若要提供下载，把 Range 作为独立下载能力，与上传会话解耦：上传负责收齐并校验，下载负责按偏移读完整文件。

客户端用 http.NewRequestWithContext 创建请求，把取消、超时、重试挂在同一个 context 上。请求体用 io.NewSectionReader 包住本地文件，只读当前区间；NewRequest 无法从 SectionReader 推断长度，必须显式设置 ContentLength，否则走 chunked，服务端长度校验就失去意义。

超时不要用一个很大的 Client.Timeout 一刀切：连接、TLS 握手、等待响应头分别设短，单片截止时间按分片大小和最低带宽估算。重试只针对幂等请求，网络错误、408、429、5xx 可指数退避加抖动，其余 4xx 不重试。进度回调按片触发。断点信息存本地文件或数据库，记录上传 ID、文件大小、修改时间、分片大小和位图，用临时文件加原子重命名写入；恢复前核对文件并与服务端位图取交集，令牌不要写进断点文件。

生命周期、安全与测试

临时数据要有生命周期。会话写 expires_at，每次成功上传顺延；后台任务定期扫描过期会话并删目录；合并成功删分片，只留结果记录一段时间；进程启动清理 .merging 和孤儿目录。失败重试的残留也交给 GC，不能指望客户端取消。磁盘配额要监控单用户总量、单机可用空间和临时目录占比，接近上限时拒绝新会话并告警。

安全覆盖入口和落点：所有接口先鉴权，uploadId 绑定用户；限制文件大小、分片数、并发和频率；索引必须是整数且落在 [0, totalChunks)，越界拒绝；路径由服务端生成的 ID 和索引拼接，客户端文件名只用于展示，不能进 filepath.Join；临时目录 0700、文件 0600，不放 Web 根或可执行目录。病毒扫描放在合并后、对外可见前，通过才可用；校验和解决完整性，不解决文件是否恶意。

测试用 httptest.NewServer 起真实服务端，临时目录用 ioutil.TempDir 创建并在 defer 删除（Go 1.13 还没有 t.TempDir）。表驱动覆盖 1 字节、恰好整除、最后一片有余数、空文件被拒、重复片、乱序、断网恢复、哈希不匹配、并发写同一片、重复 complete、取消与过期。除状态码外，还要把合并结果与源文件逐字节比较，并检查结束后临时目录清空；并发用例加 -race。

常见坑

  • 分片大小中途改变，偏移全部错位；服务端按会话参数计算偏移与长度，客户端不能自报 offset。
  • 合并按到达顺序而不是索引顺序，文件内容错位；遍历必须从 0 到总片数减一。
  • 临时文件和失败分片不清理，磁盘慢慢被填满；GC、取消、合并失败三条路径都要覆盖。
  • 多个请求直接写同一个最终文件，内容交错；临时文件加原子重命名，再用会话锁串行发布。
  • 把上传 ID 当鉴权凭证，链接一泄露就能劫持会话；它只是标识，必须绑定用户并校验令牌。
  • 信任客户端传来的“已完成”列表或总大小；合并前服务端要自己查目录、长度和哈希。
  • 合并时用 ioutil.ReadAll 把整个文件读进内存；用 io.Copy 流式追加。
  • 把 HTTP Range 当成上传协议；Range 适合下载续传，分片上传需要自己的会话协议。

小结

断点续传的本质是把长传输拆成可重试的小请求，用服务端会话记住进度。协议层负责分片、索引、断点和校验，业务层负责鉴权、配额、归属与扫描；固定分片、服务端算偏移、原始字节上传、临时文件加原子重命名，是链路做稳的支点。合并要按序流式进行，失败可回滚，完成要幂等；客户端用 context 控制超时与取消，只重试幂等请求并保存断点。清理、限流和测试同样重要，复杂度往往在失败与并发的边界上。
