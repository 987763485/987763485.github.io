Node.js 12 新特性实践

本文属于《TypeScript 学习路线》第 60/74 篇
上一篇系列目录下一篇

Node.js 12 在 2019 年 4 月发布，10 月转入 LTS，正好卡在 Node.js 10 生命周期的后半段。本文不逐条翻译发布说明，而是从升级决策出发，梳理 TLS 1.3、V8 7.4、worker_threads、ESM 和诊断报告在真实项目中的用法与边界。读者应已熟悉 CommonJS 与基本的服务端调试，读完后能判断自己的服务该不该升、先升什么、哪里可能踩坑。

一、时间线：从 Current 到 LTS

Node.js 12.0.0 于 2019 年 4 月 23 日发布，接替 11 成为 Current 线；2019 年 10 月，12 线转入长期支持（LTS），代号 Gallium。本文写作时，12 已经可以用于生产，但它的生态位与 10 并不相同。Node.js 10 在 2018 年 10 月进入 LTS，按官方计划于 2020 年初转入维护期，2021 年 4 月结束支持；Node.js 12 的支持窗口则延伸到 2022 年 4 月。因此，2019 年底到 2020 年一季度是自然的升级窗口：先把新项目和边缘服务迁到 12，再处理核心服务。官方节奏是每年 4 月发布一个大版本，10 月把偶数版本转为 LTS；奇数版本只维护到下一个大版本出现，11 很快退出舞台，12 才是需要认真对待的目标。Node.js 10 转入维护期后只接收关键修复，把新功能留在 10 上，等于让技术债继续累积。需要强调的是，TLS 1.3、新版 V8 与 worker_threads 都默认开启，升级不是换一个二进制那么简单，TLS 行为、模块加载和原生模块都要重新验证。

二、V8 7.4 与语言能力

Node.js 12.0 把 V8 升到 7.4。对业务代码最直接的变化是语法：私有类字段（#name）、Object.fromEntries()、String.prototype.matchAll() 等在此版本进入默认可用的范围，写工具函数和解析逻辑时少绕一些弯。性能方面，官方发布说明明确提到参数个数不匹配的调用路径优化，V8 7.x 在解析与 await 上的改进也随这次升级进入 12。这类收益与代码形态强相关，官方给出的是相对值，本文不引用具体百分比。Intl 的数据与格式化行为同步更新，只能作定性判断：日期、货币、排序的边界输出可能与 10 不同，升级后应对这些结果做快照测试，而不是假设完全一致。

三、TLS 1.3：默认开启之后

Node.js 12 使用 OpenSSL 1.1.1，TLS 1.3 默认可用：tls.DEFAULT_MAX_VERSION 为 TLSv1.3，tls.DEFAULT_MIN_VERSION 为 TLSv1.2，TLS 1.0 与 1.1 默认关闭。TLS 1.3 把完整握手从两次往返降到一次，恢复握手可以做到 0-RTT；它移除了 RSA 密钥交换和一批旧套件，默认只保留 AEAD 套件，前向保密成为常态。握手轮次减少对高延迟链路最明显，移动网络下，一次往返就可能决定首屏时间。

0-RTT 的代价是请求可被重放：攻击者截获 early data 后可以再次发送。对下单、支付、改密码等非幂等接口，应禁用 0-RTT；只有静态资源或明确幂等的查询才值得考虑。Node 的 tls 模块没有提供 early data 接口，默认不会接受 0-RTT 数据，风险主要出现在 Node 前面由 Nginx 或 HAProxy 终止 TLS 的部署里。

兼容性排查从三处入手：只支持 TLS 1.0 或 1.1 的老客户端（很老的 Android、Java 6、部分嵌入式设备）在 12 的默认配置下会握手失败；中间设备可能对 TLS 1.3 的握手扩展处理不完整；证书链必须带齐中间证书。反向代理、负载均衡和 APM 探针也要确认支持 1.3，否则会出现应用直连正常、经过代理失败的现象。

如果 TLS 在 Nginx 或 HAProxy 处终止，要确认代理的 OpenSSL 版本与协议配置；只开 1.3 而忘了 1.2，会把一部分客户端直接挡在门外。验证时除了看协商版本，还要看证书链：openssl s_client -showcerts 能列出服务端发送的整条链，链不全时浏览器可能靠缓存补全，命令行客户端却会失败。此外，TLS 1.3 的会话恢复与 1.2 不同，多实例部署要关注会话恢复配置的一致性。

四、worker_threads：CPU 密集任务的新去处

Node.js 12 的 worker_threads 已是稳定模块，不再需要 --experimental-worker。它提供 Worker、parentPort、MessageChannel、SharedArrayBuffer 等能力：每个 worker 有独立的 V8 isolate 和事件循环，主线程与 worker 通过消息通信，结构化克隆负责复制数据；需要共享内存时，用 SharedArrayBuffer 配合 Atomics。

与 cluster 的分工可以概括为：cluster 解决多进程分摊连接，worker 解决单进程内的 CPU 密集任务。cluster 的每个 worker 是独立进程，内存不共享，适合把 HTTP 服务摊到多核；worker 更轻，启动成本低，能通过共享内存交换大块数据，适合图像处理、加解密、复杂计算和大 JSON 解析。把 HTTP 服务从 cluster 改成 worker 并不会自动提升吞吐，反而要自己处理连接分发；cluster 的共享端口、轮询调度与 IPC 细节不在本文展开。

迁移时注意三点：worker 不适合执行会阻塞事件循环的同步 I/O；消息传递有序列化成本，大对象优先用 transferList 转移 ArrayBuffer 所有权；worker 内的未捕获异常要通过 error 事件接住，否则可能只看到线程退出。

五、ESM 的实验状态与边界

Node.js 12.13 的 ESM 仍标注为 Stability 1（实验）。运行时必须加 --experimental-modules，否则 .mjs 会按 CommonJS 处理并报错；加载时还会打印实验警告。package.json 的 type 字段在 12 已生效："type": "module" 会让作用域内的 .js 和省略扩展名的文件按 ESM 加载，"type": "commonjs" 或省略该字段则维持 CommonJS。

互操作限制要提前知道：ESM 里没有 require、__dirname、__filename，需要 createRequire 和 import.meta.url 自行构造；import 必须写扩展名，目录索引不会自动解析；从 ESM 导入 CommonJS 时，12 只支持默认导出，import { method } from 'cjs-package' 会报错；CommonJS 也不能 require() 一个 ESM 文件。

另一个常被忽略的点是 "type": "module" 的作用域：它按最近的 package.json 生效，monorepo 里不同子包可以有不同的模块类型，但构建产物、测试配置和编辑器插件未必都按同一规则解析。迁移前先画出包边界，比逐个文件改后缀更重要。

生产是否可用？我的判断是：2019 年底，把 ESM 直接作为服务端运行入口的条件还不成熟。TypeScript 编译、测试框架、覆盖率工具和部分依赖仍以 CommonJS 为假设；"type": "module" 一改，作用域内所有 .js 都会换语义，容易连带影响脚本和工具配置。较稳妥的做法是继续用构建工具输出 CommonJS 给 Node 运行，只在小范围内部脚本里试用 ESM，等加载器稳定、工具链跟上后再迁移。

六、诊断报告：能救命，但还不是稳定契约

诊断报告在 Node 11.8 引入，Node 12 仍标注为 Stability 1（实验）。它必须显式开启：--experimental-report 是总开关，--report-* 只是触发器与输出控制；没有总开关时，单独写 --report-on-fatalerror 会直接报错。这个边界要写进运维手册，避免值班同学以为加一个参数就能拿到报告。

可用开关包括：--report-on-fatalerror 在 OOM、内部断言失败等致命错误时生成；--report-on-signal 在收到信号时生成（默认 SIGUSR2，Windows 不支持）；--report-directory 与 --report-filename 控制落盘位置。报告是 JSON，包含进程与系统环境、命令行、JavaScript 与原生栈、堆统计、libuv 活动句柄、资源用量、环境变量和已加载的动态库。

报告最有价值的是故障现场：JavaScript 栈定位业务代码，原生栈看是否卡在 OpenSSL 或 libuv，句柄列表判断事件循环是否被拖住，堆统计区分 old space 增长与外部内存泄漏。容器里核心转储常被禁用，这些字段尤其有用。

实验性意味着字段、格式和开关都可能在小版本变化，不能把报告当稳定 schema 解析；报告会写入完整环境变量，可能带密钥，目录权限要收紧；单份报告不大，但故障循环触发时会迅速堆积，必须配轮转和清理。生产上建议只在预发或问题复现时开启，或用 process.report.writeReport() 按需写一份；更稳的组合仍是 --inspect 加 Chrome DevTools 的堆快照、process.memoryUsage() 做趋势监控；GC 的内部机制不在本文展开。

七、启动参数与性能工具

Node.js 12 对启动路径做了初始化拆分，官方发布说明把它列为改进项，但幅度依赖应用，本文不引用单一数字。真正影响线上内存的是堆上限：--max-old-space-size 控制老生代上限，容器里必须按内存配额显式设置，例如 --max-old-space-size=1536；默认值随平台变化，可用 node --v8-options | grep max-old-space-size 查看。设置过小会频繁 GC，过大则可能触发 OOM kill。

--max-old-space-size 可以写进 NODE_OPTIONS，但它只影响老生代，Buffer 与外部内存不受这个上限约束，容器内存限制仍要留出堆外空间。观察内存趋势时，process.memoryUsage() 的 heapUsed、external、rss 要一起看，只看 heapUsed 容易误判。

启动快照（snapshot）在 Node 12 仍处于实验和内部构建阶段：标准 CLI 文档里没有可用的用户快照开关，V8 快照主要服务于运行时自身的构建。把冷启动优化寄托在快照上为时过早，先做依赖裁剪、延迟加载和减少顶层同步工作更实际。

八、其他值得关注的变更

HTTP 解析器默认切换到 llhttp，这是 12 相对 10 的一个实质变化；--max-http-header-size 可以调整请求头上限，遇到 431 时先看这里。fs.promises 与 readdir 的 withFileTypes 让目录操作少一层回调；assert.strict 把 equal、deepEqual 收紧为严格比较，适合在测试里统一入口。

这些改动单看都不大，但都属于升级后容易观察到的行为差异：请求头过大被拒绝、目录项类型判断、断言因类型不同而失败。把它们纳入回归用例，比在故障后翻 changelog 更省时间。

assert.strict 适合在测试入口统一引入：const assert = require('assert').strict;，之后 assert.equal 就是严格相等，避免 '1' == 1 这类误判。HTTP 侧还要显式设置 headersTimeout，不要让慢连接长期占用资源。

九、升级实践与风险控制

升级顺序建议：先在 CI 增加 12 的矩阵，与 10 并行跑单元测试和集成测试；再用预发环境验证 TLS、ESM、原生模块；最后按服务分批切换。用 nvm 的团队可以固定 .nvmrc：

容器镜像建议固定小版本，例如 node:12.13.0-stretch-slim，不要用 node:12 浮动标签；Debian slim 对原生模块的兼容性比 Alpine 的 musl 更省心。依赖检查至少做三件事：npm ci 重装锁定树、npm ls 看 peer 冲突、对有原生扩展的包执行 npm rebuild，确认 node-gyp 与 N-API 版本匹配。原生模块是升级中最常见的硬故障：node-gyp 需要匹配的 Python 与编译工具链，预编译二进制则要确认 ABI 版本；N-API 模块通常跨版本可用，但仍要在目标镜像里跑一次加载测试。

回滚方案要和发布方案一起设计：保留 10 的镜像与启动参数，数据库和缓存协议保持双向兼容，先切流量再观察错误率与 TLS 握手失败率。风险主要在四处：TLS 1.3 与老旧客户端、ESM 与工具链、诊断报告的磁盘与环境变量泄露、实验 API 在小版本间的破坏性变更。任何一项没有验证，都不要把核心服务一次性全量切到 12。

小结

Node.js 12 在 2019 年底的定位很清楚：它是未来两年的 LTS 主干，TLS 1.3、V8 7.4 和稳定的 worker_threads 是实打实的升级理由；ESM 与诊断报告则仍带实验标签，只能有条件使用。新项目、面向公网且客户端较新的服务、以及有 CPU 密集计算的团队，可以尽快升级；依赖大量原生模块、客户端环境老旧、工具链深度绑定 CommonJS 的团队，可以先用 10 再等一两个小版本。升级的关键不是换版本号，而是把 TLS、模块加载和诊断能力逐项验证，并准备好回滚。
