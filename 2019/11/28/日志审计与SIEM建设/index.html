日志审计与 SIEM 建设

等保 2.0 即将于 12 月 1 日起实施，日志审计正从“有没有设备”转向“能不能回答问题”。不少团队把日志全量灌进 SIEM，真正出事时却说不清谁在几点、从哪台机器做了什么。本文从日志源盘点、归一化、关联规则讲到告警运营，适合做等保整改或搭建日志平台的工程师，读完后可按步骤搭起一套可用体系。

一、日志审计的目标：可追溯、可发现、可取证

日志审计的第一目标不是“把日志都存起来”，而是让日志回答三个问题：发生了什么，是否可发现；是谁在什么时间从哪台设备做的，是否可追溯；记录能否被采信，是否可取证。若字段缺失、时间错乱、检索不了，存得再多也只是占用磁盘。

SIEM 是把这三件事工程化的一套能力：采集、解析归一、关联分析、告警、留存与检索。它不是装完就生效的产品，而是需要持续维护的内容生产线；衡量成效不是接入了多少设备，而是常见问题能否快速查清、告警能否被准确解释。

二、日志源盘点：七类来源与采集方式

盘点时按“谁会产生与安全相关的事件”列清单，覆盖七类来源。

网络设备包括防火墙、路由器与交换机，记录连接放行或拒绝、NAT 转换、配置变更，关键字段是五元组、命中规则与动作，通过 syslog 外发。

安全设备包括 IDS/IPS、WAF 与终端防护，提供特征命中与阻断结果，关键字段是特征名、源目的地址与严重级别，常用 syslog 或 API。

主机包括 Linux 与 Windows，记录登录、提权、进程与账号变更；Linux 可读 auditd 与系统日志，Windows 读取安全事件日志，由 agent 采集。

数据库记录登录失败、DDL/DCL、批量导出与慢查询，依靠数据库审计日志或采集插件。

中间件记录访问与错误日志，应用记录登录、权限变更、数据导出等业务事件；前者读文件，后者最好由应用直接输出 JSON。

云平台的控制台操作、API 调用与流日志，通过云厂商 API 定时拉取。

每一类都要落到具体字段：时间、主体（账号或进程）、客体（主机、库表、接口）、动作、结果与来源 IP。盘点表没有的字段，后面的规则一定写不出来。

三、日志分级与留存：六个月只是底线

日志按用途分为四类。安全日志用于检测与响应，包括认证、防火墙、入侵检测与终端事件；审计日志记录权限变更、配置修改与数据访问等可问责行为，要求完整、只读、可追溯；业务日志用于排障与分析；调试日志只在短期有用，不应长期占用在线存储。

留存周期按价值与合规要求分层。等保相关要求提出日志留存不少于六个月，这是底线：安全与审计日志至少保留六个月，重要操作可以更长；业务日志按需保留；调试日志几天即可。为控制成本，常用冷热分层：热数据保留最近七到三十天，放在高性能索引中供检索；温数据保留一到三个月，压缩后仍可查；冷数据归档到对象存储，需要时再恢复。归档不是一丢了之，应保留索引与校验值，确保取回后仍可核对。

六个月要求的工程落地，关键是按天建索引并配置生命周期策略，让过期数据自动转入低成本存储或删除，而不是等磁盘写满再人工清理。

四、时间同步与归一化：关联分析的两块地基

时间同步：先对齐时钟，再谈关联

关联分析的第一步不是写规则，而是对齐时钟。防火墙、主机、数据库各自计时，若相差几十秒，同一会话在两边就对不上。日志源与采集器应指向同一组 NTP 服务器，内网时间源再向外同步。操作系统可用 chrony 或 ntpd 持续校准，并监控偏移量，超过阈值就告警。

存储时统一用 UTC，展示时再转本地时区，避免跨时区设备混在一起。时间戳至少保留到秒，关键设备最好带毫秒。每条记录同时保留事件发生时间与采集到达时间：前者用于关联，后者用于发现时钟异常与补采延迟。

归一化：字段模型不是改名字

归一化是把不同厂商的日志映射到同一套字段模型，常用字段包括 event_time、event_type、src_ip、dst_ip、src_port、dst_port、user、action、result、device、severity 与 raw。解析规则要覆盖 syslog（RFC 3164/5424）、JSON、CEF 等常见格式，可用 grok 或正则解析；解析失败保留原文并打标记，不能静默丢弃。

归一化不是改字段名那么简单。源地址要统一格式并区分内外网，账号要映射到统一身份，动作要收敛到有限枚举，结果要统一为成功或失败，缺失值要有明确语义。字段类型也要统一，端口是整数而不是字符串，否则范围查询会失效。

五、采集传输与存储检索：别让管道成为瓶颈

采集与传输

Linux 主机用 rsyslog 集中转发，网络设备通过 syslog 外发，应用与中间件日志用 filebeat 类采集器读取文件。syslog 默认走 UDP，丢包不可知，跨网段应改为 TCP 并启用 TLS；采集器与接收端双向认证，避免日志被伪造或窃听。

传输链路要有缓冲与断点续传：采集端先把日志写到本地磁盘队列，接收端不可用时继续缓存，恢复后按位点续传。Kafka 一类消息队列常放在采集与解析之间，起到削峰和解耦作用。采集链路也要避免单点：至少两台接收端做负载均衡，采集器多实例部署并由中心统一管理；采集进程要限制资源占用，防止拖垮业务主机。

存储与检索

索引按天滚动、按日志类型拆分，避免一个索引承载所有来源；分片不宜过多，小分片会放大集群开销，分片数应结合数据量与节点数规划。保留策略绑定索引模板，过期自动关闭或删除。

查询性能取决于三件事：时间范围是否收敛、过滤字段是否有索引、排序是否必要。排障时先限定时间与主体，再逐步放宽条件，避免全量模糊匹配。容量估算用可测量的方法：先抽样统计日均 EPS 与单条平均字节数，乘以留存天数与副本数，再留出约两成余量；上线后按月复核实际增长，而不是拍脑袋。

六、关联规则与用例：把日志变成可处置的事件

关联规则：从单事件到时序

规则分为四类：单事件规则匹配一条日志的字段，例如敏感文件被删除；阈值规则统计单位时间内的次数；时序规则要求事件按顺序出现；多源规则把网络、主机与应用日志按同一实体拼接起来。规则越复杂，维护成本越高，应优先用简单规则覆盖高价值场景。

以“多次登录失败后成功”为例，检测逻辑是：同一账号在五分钟内失败达到五次，随后十分钟内出现一次成功登录，按账号与源地址分组告警，并附带首次失败时间、成功时间与失败次数。只关心认证结果序列，不涉及攻击操作。阈值、窗口与分组字段都应来自基线，不能照抄；对堡垒机健康检查、已登记的扫描器要单独排除。

用例建设：从威胁场景出发

用例从威胁场景出发，而不是从设备能力出发。下表把五个高频场景的数据源、检测逻辑、误报来源与处置动作放在一起，便于逐项落地。

用例 数据源 检测逻辑 误报来源 处置动作
暴力破解 主机、应用登录日志 失败次数超过基线后出现成功 密码过期、共享账号 冻结会话、强制改密
异常登录 认证日志、资产台账 地点、时段或设备异常 出差、VPN 出口变化 二次认证、联系本人
权限变更 主机、数据库审计 加入管理员组、授权语句 正常变更运维 核对工单、回滚
数据导出 数据库审计、应用日志 短时批量查询或下载 报表、备份任务 限流、确认用途
Web 攻击痕迹 WAF、应用访问日志 拦截与异常参数聚集 爬虫、误拦截 封禁、排查主机

四件事缺一不可：数据源、检测逻辑、误报来源与处置动作。误报来源要具体，例如运维批量操作、监控探活、共享账号；处置动作要可执行，例如冻结会话、二次认证、联系责任人。写不清的用例不要上线。

七、告警调优：别让团队对告警失去信任

告警调优的目标是让每条告警都值得看。先做基线：统计正常时段的登录分布、常用源地址、账号行为与日志量，阈值围绕基线设置，并按部门与资产级别调整。白名单必须有期限、有负责人、有原因，到期自动失效，不能变成永久黑洞。

聚合与去重按“规则 + 实体 + 时间窗”合并同类告警，同一账号的连续失败只生成一条事件。告警分级按影响与置信度划分：高置信度且涉及核心资产的立即处置，低置信度的先观察或进入日报。每周统计准确率与处置时长，把长期无人处理的规则下线或重写。出现“狼来了”时，先查规则为何不准，再决定是否调阈值；简单关掉告警只会让风险隐身。

八、运营流程与合规映射：上线只是起点

运营流程

SIEM 上线只是开始。值班表要明确谁看告警、多久响应；告警按级别设定响应时限，工单记录处置过程；涉及取证时，第一时间保全原始日志、镜像与校验值，记录交接链，避免证据被覆盖。事件结束后复盘规则是否漏报、数据源是否缺失、流程卡在哪一步。衡量运营的指标包括平均发现时间、响应时间、误报率与用例覆盖率，用来发现最薄弱的环节。

合规映射

等保 2.0 已于 2019 年 5 月 10 日发布，即将于 12 月 1 日起实施。它对日志审计的要求是方向性的：重要用户与重要操作要有审计记录，审计记录要留存不少于六个月并防止删除、修改，设备时间要统一，日志与审计数据宜集中管控。具体控制项以标准正文为准，不逐条引用。

把方向落到工程上：留存对应生命周期策略，审计记录对应日志源与字段完整性，集中管控对应 SIEM 的采集与权限，防篡改对应只读存储、校验值与异地备份。合规检查时能拿出连续、可检索的记录，比堆制度文件更有说服力。

九、常见问题：六个容易踩的坑

最常见的问题是只采不析：日志接入了却没人看、没有规则，平台沦为归档库。其次是字段缺失与解析失败无人发现，规则写完才发现关键字段为空，应把解析成功率做成监控指标。

规则照搬也很常见，别人的阈值放到自己业务里不是误报就是漏报，必须结合基线重调。告警无人处置比没有告警更糟，会消耗团队信任；存储爆盘往往因为没设生命周期策略，或调试日志被长期保留。最后是敏感信息未脱敏：日志里出现口令、令牌、身份证号，应在采集端掩码，并限制查询权限、加密存储。

小结

日志审计与 SIEM 建设是一条从“采得到”到“用得好”的链路：先盘清日志源与关键字段，再解决时间同步与归一化，用分级留存控制成本，用关联规则和用例把威胁变成可处置的告警，最后靠运营流程与调优把体系跑起来。等保 2.0 实施在即，合规是起点而不是终点。能回答“谁在何时做了什么”，才是日志审计真正的价值。
