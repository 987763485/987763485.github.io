WAF 部署与规则调优

WAF 是等保整改中最早接触、也最容易被业务投诉“误杀”的安全设备。本文从防御侧运维角度，说明 WAF 与相邻设施的分工、部署方式取舍，并以 ModSecurity 与 OWASP CRS 为例，走一遍规则分级、误报治理、性能评估、日志联动与灰度上线的流程。读者具备 Nginx 与 Linux 基础即可，读完后应能完成一次可观测、可回滚的 WAF 上线与调优。

WAF 在防护体系中的位置

WAF 工作在应用层，检查方法、URI、头部、Cookie、参数与请求体，补上了网络层设备看不见的部分，例如一个格式合规的 POST 请求里是否夹带了注入语句。

与相邻设施的分工可以这样理解：防火墙决定“能不能连”，IDS/IPS 判断流量“像不像攻击”，WAF 判断“这个 HTTP 请求业务是否应该接受”，RASP 则在应用进程内判断“执行到危险函数时要不要拦”。四者不是替代关系：防火墙对内容无感，IDS 旁路取证，IPS 粒度较粗，RASP 覆盖最细但侵入进程。

WAF 也不能替代代码修复。规则匹配的是已知模式，参数化查询、输出编码、权限校验才是消除漏洞的根本。等保 2.0 标准已于 2019 年 5 月发布，将于 12 月 1 日实施，WAF 是满足边界防护与审计要求的常见措施，但测评看整体措施是否有效。

部署模式的选择

常见做法有四种。

反向代理最容易落地：Nginx 作为入口终止 TLS，由 ModSecurity 检查后转发源站。证书、规则、日志集中，扩容和灰度方便；代价是多一跳，源站必须只接受 WAF 回源地址，否则攻击者直连源站就能绕开防护。

串接透明代理把设备桥接在链路上，不改变 IP 规划，适合不能改拓扑的老系统。HTTPS 要么在设备上持有证书解密，要么只能看到 SNI，前者涉及私钥保管，后者放弃内容检测。设备还需支持断电直通，避免单点故障。

云 WAF 通过 DNS 调度把流量引到云端，源站隐藏成本低，规则由服务方维护。关键风险是源站暴露：历史 DNS 记录、证书透明日志或邮件头都可能泄露真实 IP。源站防火墙只放行回源网段并定期核查，同时评估数据经第三方的合规问题。

模块嵌入把 ModSecurity 作为服务器模块加载，延迟最低，但规则与服务器版本强耦合，升级和隔离更麻烦。

模式 延迟 证书管理 源站暴露 运维成本
反向代理 增加一跳 WAF 持有 需限制回源 中
串接透明 增加一跳 WAF 持有或无法解密 不暴露 中高
云 WAF 取决于回源链路 上传至云端 需回源白名单 低
模块嵌入 最小 Web 服务器持有 不适用 低但耦合

ModSecurity 基础配置

ModSecurity 的核心是引擎开关、请求体访问和审计日志。Nginx 侧常见组合是 2.9 系列配合连接模块，3.x 的连接器仍在演进，选型时要确认兼容性。

SecRuleEngine 有三个取值：On 检测并阻断，Off 关闭，DetectionOnly 只记录。上线第一步应设为 DetectionOnly，让规则在真实流量里跑一段时间再决定阻断策略。它仍会做完整匹配和日志写入，性能开销不比 On 小多少，不能当成免费的观察模式长期挂着。

SecRequestBodyAccess 决定是否解析请求体。设为 Off 时，POST 参数、JSON、multipart 规则全部失效，只剩 URI 和头部检查，防护出现盲区。开启后要配套设置请求体上限，否则大文件会拖垮内存和临时目录。

审计日志用 SecAuditEngine RelevantOnly，只记录规则命中或状态码异常的事务，避免日志占满磁盘。SecAuditLogParts 保留审计头、请求头、请求体、命中详情与结束标记即可。日志单独挂盘并轮转，写入阻塞时不应影响业务。

OWASP CRS 的规则组织

CRS 3.x 是当时的主流版本，规则按文件名前缀排序加载：crs-setup.conf 负责默认动作、异常分数阈值和响应体检查，REQUEST-9xx 处理请求侧，RESPONSE-9xx 处理响应侧，排除规则则分列 CRS 前后，前者关闭规则，后者调整分数。

CRS 3.x 默认采用异常评分：单条规则命中只累加分数，由评估规则按总分决定是否拦截。低置信度规则不会直接误杀，但需要在同一事务里综合判断。

paranoia level 从 PL1 到 PL4，级别越高启用的规则越多、越激进，误报也越多。新上线应从 PL1 开始，跑稳后再根据漏报逐步提高；直接上 PL4 往往第一天就收到大量投诉。入站规则关注参数注入、协议异常与路径穿越，出站规则关注敏感信息泄露，开启出站检查会带来额外开销。

规则编号有区间含义，但不同版本会调整，调优应以审计日志里实际出现的 ID、消息和标签为准，不要凭记忆判断编号对应哪类攻击。

从观察到阻断：规则分级与调优流程

调优不是“看到报警就加白名单”，而是可重复的闭环。

flowchart TD
    A[DetectionOnly 观察] --> B[按规则 ID 与 URI 聚合]
    B --> C{分类}
    C -->|真攻击| D[保留规则并告警]
    C -->|误报| E[写精确排除]
    C -->|爬虫| F[限速与白名单]
    C -->|业务特征| E
    E --> G[回放回归]
    G --> H[小流量阻断]
    H --> A

第一步观察，至少覆盖一个完整业务周期，包括高峰与月末结算等特殊时段。第二步统计，从审计日志按规则 ID、URI、参数名聚合，找出命中量最大和增长最快的组合。第三步分类：真实攻击、规则不理解业务导致的误报、爬虫扫描器、业务固有特征（如富文本提交的 HTML）。第四步写排除，必须精确到“哪条 URI 的哪个参数、关闭哪条规则”。第五步回归，回放历史请求样本，确认没有放过真实攻击，也没有影响其他站点。

规则分级可按“置信度乘危害”做：高危害高置信的先阻断，例如明确的命令注入；高危害易误报的先告警，例如搜索参数里的 SQL 关键字；低危害只记日志，定期复盘。阻断策略应允许按虚拟主机、按 URI 前缀配置，而不是全站一刀切。

误报治理的边界

误报来源很集中。富文本与 Markdown 编辑器会把大段 HTML 当参数提交，触发 XSS 规则；JSON 字段可能同时含引号、尖括号和 SQL 关键字；文件上传的 multipart 体是二进制，按文本扫描既慢又易误判；图片或附件做 Base64 后放进 JSON，编码串会被当成混淆载荷；商品标题里出现 select、union 也会命中注入规则。

治理手段有两种，差别很大。SecRuleRemoveById 整条移除规则，该规则的所有目标都不再生效，作用范围取决于配置所在的虚拟主机或目录，属于“大锤”。ctl:ruleRemoveTargetById 只在当前事务、当前匹配范围内移除指定目标，例如只放过某个 URI 的 content 参数，其他参数和 URI 仍检查，属于“手术刀”。多数误报应该用后者。

作用域要收敛：不同虚拟主机使用独立的规则文件，排除规则写在对应的 REQUEST-900-EXCLUSION-RULES-BEFORE-CRS.conf 中并注释，注明工单号、申请人和失效日期。排除规则也要评审，避免为快速恢复业务写下全站 ctl:ruleEngine=Off。

文件上传与 JSON 请求体的处理

上传接口最容易出问题。ModSecurity 要把 multipart 体解析成参数和文件，超过内存阈值的部分落到临时目录。SecRequestBodyLimit 小于业务允许的文件大小时，请求会在 WAF 层被拒绝；Nginx 的 client_max_body_size 更小时，请求到不了 WAF，用户看到 413，日志里却什么都没有。两个限制要一起调整，并留出编码膨胀余量。

上传接口只检查文件名、Content-Type、表单字段等元数据，不对文件内容做文本匹配；临时目录放在独立磁盘并定期清理，响应体检查默认关闭。确需检查内容时，应交给病毒扫描或专门解析服务，而不是让 WAF 把二进制当文本跑正则。

JSON 接口要显式启用解析器，否则规则只能看到原始字符串，参数级排除无从谈起。启用后限制请求体大小与嵌套深度，并对 Base64 附件字段设检查上限；大段编码数据送进正则引擎，既拖慢延迟也放大 CPU 消耗。

性能与容量评估

WAF 的成本来自规则数量、正则复杂度、请求体上限和并发连接数。规则越多、paranoia level 越高，单请求匹配次数越多；正则越复杂，回溯越久；请求体上限越大，内存与临时文件压力越高。PCRE 匹配次数与递归深度限制只能兜底，根本办法是精简规则、缩小范围。

压测在预发环境做，先关 WAF 测基线，再开启 WAF 回放同一份流量，比较 p95 与 p99 延迟、单核 QPS、CPU、错误率和日志写入。只压静态页没有意义，要覆盖 JSON 体、文件上传、大 Cookie 的真实接口。观察指标包括 WAF 进程资源、上游连接时间、日志磁盘等待和命中率，容量规划要留出规则更新与突发流量余量。

某接口成为瓶颈时，优先按 URI 关闭不必要的检查，而不是调大超时或连接数；超时调大只会让慢请求堆积，最终耗尽 worker 连接。

日志、联动与合规留存

审计日志是调优的原料，也是事后追查的证据。一条记录通常包含事务 ID、客户端地址、请求行、规则 ID、严重级别、命中参数和请求体片段。送到 SIEM 前要按事务边界做多行合并，再解析出上述字段。ELK 7.x 是当年常见的组合，Filebeat 采集、Logstash 解析、Elasticsearch 存储、Kibana 展示。

重点看三类视图：规则 ID 命中趋势、源 IP 命中排行、URI 误报分布。与 IPS 或防火墙联动封禁要谨慎。单次命中不足以证明恶意，扫描器、CDN 回源、NAT 出口都可能产生相似请求。只对高置信规则、短时多次命中的源 IP 自动封禁，时长从小时级开始，并维护白名单；网段封禁必须人工确认。错误封掉 CDN 回源 IP，可能瞬间让整站不可用。

等保 2.0 对安全审计提出日志留存与保护要求，落地还要结合《网络安全法》关于日志留存不少于六个月的规定。日志服务器单独授权、时钟同步、防篡改，审计与业务日志分开保存，留存期限、备份和访问审批写进制度。

上线、灰度与回滚

上线分四步：先在测试虚拟主机开启 DetectionOnly，确认配置与日志正常；再选一个流量较小的生产域名观察一到两周，积累误报清单；然后只对高危规则开启阻断，低危规则继续告警，监控 403 比例和业务成功率；最后逐步扩大阻断范围，每次变更保留上一版配置。

回滚必须比上线更快。规则文件纳入版本管理，变更前备份，重载前执行 nginx -t。应急开关至少两级：一级切到 DetectionOnly，保留观测能力；二级切到 Off，用于规则导致大面积不可用的极端情况。切换后平滑重载，避免连接中断。

灰度期间要与业务方约定通知机制：出现误杀时，业务提供请求样本和时间点，安全侧在日志里定位具体规则。每次规则更新后做小流量回放，确认没有新增高频命中再全量发布。

几个常见坑

只开规则不看日志，是最常见的浪费。规则装完没人管，误报会积累到业务方要求关设备。

排除规则过宽，等于自己拆掉防线。一条全站生效的 SecRuleRemoveById，可能让高危规则永久失效，后来的人甚至不知道它存在过。

把 WAF 当唯一防线，会掩盖代码层的问题。规则更新永远滞后于接口变化，真正的修复仍在应用侧。

忽略 HTTPS 卸载后的真实 IP，会让日志和封禁失真。WAF 前还有负载均衡时，要用可信代理列表配合 real_ip 模块还原地址，并确认 X-Forwarded-For 由边界设备重写，否则攻击者可以伪造来源。

规则更新导致业务中断，往往发生在自动更新之后。CRS 升级会引入新规则、调整评分，必须在预发环境回归，不能在生产直接拉取最新规则。另一个坑是审计日志磁盘写满，写入失败可能影响请求处理，监控必须覆盖磁盘使用率。

小结

WAF 是应用层边界防护的一环，不是防火墙、IPS 或 RASP 的替代品，更不能替代代码修复。部署模式要在延迟、证书、源站暴露和运维成本间取舍，自有业务从反向代理加 ModSecurity 起步最稳。调优关键是先用 DetectionOnly 观察，按规则 ID、URI 和参数聚合分类，用精确到参数的 ctl:ruleRemoveTargetById 治理误报，再小流量阻断并保留回滚通道。审计日志接入统一平台，谨慎自动封禁，按等保与法律要求留存，WAF 才能持续运转。
