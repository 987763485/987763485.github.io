应用安全测试：SAST 与 DAST

应用安全测试最常见的误区，是把某一款扫描器当成安全工作的全部：装好、跑一遍、导出报告，然后指望漏洞自己消失。本文从 SAST 与 DAST 的原理讲起，逐步落到 CI 集成、误报治理、覆盖率、门禁策略与修复闭环，帮助正在建设 DevSecOps 流程的团队，把“能扫”推进到“扫得准、修得动、管得住”。

一、为什么需要两类测试

应用安全测试要回答三个问题：代码里有没有危险写法，运行中的系统表现出什么行为，这些行为是否可能被滥用。SAST（Static Application Security Testing，静态应用安全测试）回答第一个，DAST（Dynamic Application Security Testing，动态应用安全测试）回答后两个。两者观察对象不同，能发现的缺陷类型也不同，因此“选 SAST 还是 DAST”是个伪命题。

白盒的优势在于看得见结构。扫描器直接读取源码或编译产物，能在合入前指出外部参数未经校验就流入数据库查询，也能指出异常处理把堆栈返回给调用方。它不必运行系统，适合放在提交阶段，反馈快、定位到行。代价是不理解运行时装配，依赖注入、反射、动态拼接都会让分析丢失上下文。

黑盒的优势在于看得见事实。DAST 从外部发请求看响应，能确认反射型跨站脚本是否真的出现在页面里，能发现目录列表、缺失的安全响应头、暴露的调试接口。这类问题出在运行态或配置，源码可能完全正常。代价是覆盖率受爬虫限制，业务逻辑漏洞要多步骤、多角色才能触发。

盲区恰好互补。SAST 擅长数据流污染，DAST 擅长运行态证据；SAST 能覆盖没有入口的分支，DAST 只能覆盖被请求触达的路径；SAST 对框架魔法无能为力，DAST 对源码一无所知。成熟的做法是让两类结果进入同一套缺陷管理流程，用同一条闭环修复和验证。

本文讨论的扫描与测试均以书面授权为前提，在明确范围、时间窗口和测试账号内进行，生产环境扫描须单独审批。

二、SAST 的工作机制

从源码到可分析的中间表示

静态分析的第一步不是“找漏洞”，而是把代码变成机器可推理的结构。词法分析切 token，语法分析构造抽象语法树（AST），语义分析建立符号表、解析类型、绑定调用。到了这一步，扫描器才能区分“名为 query 的字符串变量”和“真正执行 SQL 的对象方法”。

在此之上，工具通常构建调用图和控制流图（CFG）：前者回答“谁会调用谁”，后者回答“在什么条件下走到这里”。Java 可分析字节码，Python、JavaScript 更依赖源码解析和类型推断。语言的动态特性越多，分析要做的假设越多，误报越难压下去。SAST 的结论只是保守假设下可能成立，而不是运行时事实。

数据流与污点传播

SAST 最核心的方法是污点分析。它把外部可控输入标记为 source，把危险操作标记为 sink，沿赋值、拼接、调用、返回值追踪污染是否到达；中途的校验、转义、类型转换或参数化绑定视为 sanitizer，污染在此切断。

规则如何描述漏洞模式

SAST 的规则分两类。模式匹配描述可疑语法结构，例如调用危险函数、密钥写成字面量、关闭证书校验；数据流规则描述数据从哪里流到哪里，注入类多属此类。规则带编号、级别、语言、修复建议和弱点分类，便于统计与流转。

可维护性比规则数量重要。企业有自研框架、统一数据访问层和自定义校验注解，通用规则不认识，就会把安全写法误判。需要声明净化函数、补充框架模型和自定义规则，把团队最佳实践教给扫描器；写完还要用历史漏洞和公开基准回归，确认误报没有失控。

三、DAST 的工作机制

爬虫、代理与两类扫描

DAST 的输入是运行中的应用。扫描器先充当爬虫，从入口页面跟踪链接、表单和前端路由，枚举可达页面与接口；也可以作为代理，记录测试人员或自动化用例产生的真实流量。前者覆盖广但容易迷路，后者贴近业务但依赖人工，实际通常两者结合。

被动扫描只观察流量，不改变请求。它检查响应头是否缺少安全策略、Cookie 是否缺少必要属性、错误页面是否泄露堆栈、页面是否引用过期组件。被动扫描风险低，适合测试环境长期开启，也适合生产环境低频巡检。主动扫描则对参数做类型、长度和编码上的变异，观察状态码、响应长度、报错特征和耗时差异。探针应当是无害的测试字符串，扫描器据此推断注入点，而不是破坏数据。

主动扫描的难点在于判定。同样的响应差异，可能是漏洞，也可能是时间戳、随机 token 或负载均衡造成的波动。成熟的工具会做多次基线请求、对比相似度、识别反射位置，并给出置信度。扫描深度也要控制：参数组合爆炸时，全量变异会带来巨大流量，合理做法是先按参数类型和风险排序，再限制每个参数的探针数量。

认证态与 API 扫描

未登录扫描只能看到登录页。认证态扫描要解决三个问题：如何登录、如何保持会话、如何覆盖不同角色。常见做法是录制登录过程形成登录宏，让扫描器定期重放；或注入有效的会话 Cookie 与请求头。会话过期、验证码、短信二次验证都会打断扫描，因此测试环境最好提供稳定的测试账号，并在受控范围内关闭验证码。

角色问题更关键。越权漏洞的本质是低权限用户访问了高权限资源，只用一个账号永远发现不了。需要为每个角色配置独立会话，分别爬取，再对比同一资源的访问结果。工具只能辅助，真正的权限矩阵仍要由熟悉业务的人梳理。

API 扫描是另一个难点。没有页面可爬时，可以从接口描述文件导入端点，也可以从代理流量提取请求。扫描器需要理解路径参数、查询参数、JSON 请求体、认证头和内容类型，才能构造有效变体。有状态接口还要保证调用顺序，否则大量请求会因前置条件不满足而失败。涉及删除、支付、发消息等副作用的接口，应明确排除或使用沙箱数据。

四、IAST 与 RASP 的位置

IAST（Interactive Application Security Testing，交互式应用安全测试）可以理解为“在运行时做静态分析”。它通过字节码插桩或语言代理，把探针装进应用进程，在测试用例或爬虫驱动业务运行时，观察真实的数据流。因为看到的是实际执行路径和实际参数，IAST 的误报通常低于纯静态分析，定位也能落到具体调用栈；但它依赖测试用例真正走到问题代码，未被覆盖的分支依然看不见。

RASP（Runtime Application Self-Protection，运行时应用自我保护）则把探针放在生产环境，在请求执行过程中检测并阻断危险行为。它的价值在于给无法立即修复的老系统争取时间，相当于在应用内部做一层“虚拟补丁”。代价是性能开销、稳定性风险和生产环境误拦截，任何一次误杀都可能直接影响业务，因此规则必须经过充分灰度。

两者都不能替代 SAST 与 DAST。IAST 需要测试流量，RASP 需要生产部署，它们解决的是“测试更准”和“运行时兜底”，而不是“提交前发现问题”。务实的组合是：SAST 守住提交与合并，DAST 守住测试环境，IAST 作为重点项目增强，RASP 只在稳定性有把握的核心系统试点。

五、工具类别与选型维度

市面上的应用安全测试工具可以粗分为开源与商业两类，但真正的差异不在“免费还是收费”，而在能力边界与维护成本。开源工具通常可审计、可改造、部署灵活，适合有安全工程能力的团队；缺点是语言与框架支持参差不齐，规则更新依赖社区，遇到误报往往要自己读源码定位。商业工具在规则覆盖、报告体系、工单集成和技术支持上更完整，代价是采购流程长、黑盒程度高，深度定制不一定方便。

选型时建议固定一张评估表逐项打分，而不是被演示环境里的“漏洞数量”打动。第一项是语言与框架支持，必须覆盖团队的主力技术栈，并能识别常见的 Web 框架、ORM、模板引擎和内部公共库。第二项是构建方式，工具能否直接处理 Maven、Gradle、npm、pip、Go modules 的产物，能否处理多模块项目，决定了接入成本。第三项是规则可维护性，是否提供稳定的自定义规则机制、清晰的文档、能否纳入版本管理，这些决定了半年之后团队还能不能继续用下去。

第四项是扫描速度与增量能力。全量扫描再快，也扛不住每次提交都跑一遍大型仓库；能否只分析变更文件及其调用链，能否复用编译缓存，直接决定开发者愿不愿意等。第五项是误报率，不能只看厂商宣传，应该拿两三个真实项目做试点，用历史漏洞样本回放，统计“报了但不成立”和“该报没报”的比例。第六项是 CI 友好度，包括命令行是否稳定、退出码能否区分“发现问题”和“执行失败”、报告是否机器可读、能否以容器方式离线运行。此外还要评估代码隐私与部署形态，以及扫描结果能否进入现有的缺陷跟踪、沟通工具和日志平台。

六、在 CI 中的集成

CI 集成的第一条原则是快慢分离。提交和合并请求阶段只跑增量扫描，目标是在几分钟内给出与本次改动相关的结论；全量扫描放到夜间或发布前，允许跑几十分钟。第二条原则是结果可追溯，每次扫描都要与代码版本、构建号、扫描器版本和规则版本绑定，否则复扫和审计时无法说明“当时到底扫了什么”。

增量扫描的关键不只是“只扫变更文件”。一个文件被修改，风险可能出现在调用它的上游入口，也可能出现在它调用的下游 sink，因此工具需要支持按变更集扩展调用链，至少覆盖直接调用方和被调用方。合并请求阶段通常先以评论或警告的形式呈现结果，等规则稳定、基线建立之后，再对新增的高危问题执行阻断；阻断条件由严重级别、是否新增、是否已确认共同决定。

夜间全量扫描承担三件事：覆盖增量扫描漏掉的跨模块路径，运行完整规则集，以及对测试环境执行 DAST。DAST 需要可重复部署的环境、种子数据和稳定登录方式；环境由流水线临时拉起最理想，如果只能用共享测试环境，则要约定扫描窗口、限速，并避开联调时间。

上面的流水线使用通用命令占位，目的是说明结构而不是绑定某个产品：增量任务只在合并请求时触发，夜间任务由定时调度触发，报告无论成功失败都保留。落地时还要补充缓存、超时和重试，并把扫描器的退出码映射为流水线状态。扫描器崩溃、依赖下载失败、许可证过期都会返回非零退出码；不加区分，团队就会把工具故障当成发现漏洞，久而久之不再信任门禁。稳妥的做法是让包装脚本输出结构化结果，判断是“有阻断级发现”还是“执行异常”，后者默认不阻断但必须告警。

扫描产物建议统一归档，至少保留到对应版本下线。报告格式优先选择 JSON 加一种通用测试报告格式，前者供平台二次分析，后者供 CI 展示。归档时同时保存基线和抑制规则文件，复扫时才能判断问题是新出现的还是历史遗留。

七、误报治理：把噪声变成可运营的资产

误报治理的第一步是分类，而不是急着点“忽略”。至少把结果分成四类：确认的漏洞、误报（路径不可达、框架已防护、规则不认识内部封装）、业务接受的风险（已知且有人负责）、重复报告。四类处理方式完全不同，混在一起统计，既看不清工具质量，也看不清真实风险。

基线（baseline）是控制噪声的核心手段。首次全量扫描后，研发和安全一起评审，把确认的存量问题冻结为基线，记录规则编号、文件指纹、责任人和计划修复时间。此后合并请求只对“基线之外的新增发现”执行阻断，存量按计划消化。基线需要版本管理，也需要到期机制：定期重新评估，避免历史问题被永久掩盖。

抑制规则要精确到“规则加代码位置指纹”，而不是按文件或目录整体关闭。每条抑制都写清原因、责任人、到期时间和关联工单，到期后自动失效。允许按规则抑制某类误报，但要有规则 owner 审核；不允许因为目录误报多就整个排除，那等于主动制造盲区。测试代码、生成代码和第三方依赖可以排除，但排除清单本身也要评审。

误报率需要持续度量。可以定期抽样，人工判断告警是否成立；也可以统计抑制率、误报关闭率和同一规则的重复告警次数。数据出来之后，优先改造误报最多的几条规则：补充框架模型、声明净化函数、缩小匹配范围，必要时下线规则。治理的目标是让开发者相信“被报出来的大概率是真问题”，这份信任一旦失去，门禁就会形同虚设。

八、覆盖率：知道自己没看到什么

安全测试的覆盖率不是一个百分比就能说清的概念。对 SAST 而言，至少要区分三层：代码是否成功构建并被解析，哪些目录被排除，增量扫描是否覆盖变更代码的调用链。大型项目往往包含多个语言、多个构建单元，扫描器可能只成功分析了其中一部分，报告却看起来“全部通过”。因此要定期导出未解析文件清单，交给对应模块负责人确认原因。

对 DAST 而言，覆盖率体现在接口、角色、参数和状态四个维度。接口维度看“文档里有多少端点，爬虫实际触达多少”；角色维度看“每个角色是否都用自己的会话扫过”；参数维度看“每个接口的关键参数是否都被变异过”；状态维度看“需要前置条件的多步流程是否走通”。只用一个未登录会话扫一遍首页，覆盖率可能低得惊人，但报告上只会写“未发现高危漏洞”，这种结论具有误导性。

扫描深度同样要明确。爬虫的最大深度、每个参数的探针数量、单次扫描的时间预算、是否渲染 JavaScript，都会影响结果。SPA 应用在 2019 年已经很常见，传统爬虫对前端路由和异步接口的识别能力有限，需要额外提供接口清单或代理流量。覆盖不到并不可怕，可怕的是不知道哪里没覆盖；把“未覆盖模块与端点清单”作为报告附件，比给出模糊的覆盖率数字更有管理价值。

九、门禁策略：阻断什么、放行什么

门禁的目标是阻止风险进入主干，而不是阻止程序员下班。合理的门禁只阻断三类发现：已人工确认的、本次改动新引入的、严重级别达到阈值的。存量走基线，按计划修复；未确认的告警进入待定区；低危记录在案，不占用合并窗口。把新增和存量分开，是门禁能否长期执行的关键。

新代码可以严格，老代码需要缓冲。新增行引入的高危问题应直接阻断，历史遗留问题给出整改期限。阈值不是越低越好：连中危、低危都阻断，开发者就会拆分提交、关闭规则，或把真问题标成误报，门禁看似严格，信号已经失真。稳妥的节奏是先运行观察模式，统计每天阻断多少次、其中多少是误报，再逐步收紧。

紧急放行必须是正式通道，而不是私下关掉检查。申请中写明原因、影响范围、审批人、补偿措施和有效期。补偿可以是临时 WAF 规则、网络访问限制、加强监控或缩短发布窗口；到期后自动恢复门禁，并由安全团队复扫确认。所有放行留档、定期复盘。没有这条通道，团队会用更隐蔽的方式绕过；有了它，例外才可度量、可收敛。

门禁的位置也要讲究。合并请求阶段适合跑增量 SAST 和单元测试，反馈快、上下文完整；DAST 依赖部署环境，放在发布前或夜间更合适。门禁规则应提前公布，附上修复示例和负责人，让开发者知道为什么被拦、怎么改。当拦截量突然下降、抑制规则突然增多、扫描覆盖率异常缩水时，要把它当成绕过信号排查，而不是当成质量提升。

十、修复闭环：从告警到规范

一条可修复的告警，至少包含代码位置或请求详情、复现条件、风险说明、修复建议和规则编号。只给一句“存在 SQL 注入”，研发无法判断是哪个参数、哪条路径，只能来回沟通。工具输出越接近工单语言，修复效率越高，这也是选型时要验证报告可读性的原因。

工单流转要解决归属和去重。扫描结果自动进入项目问题列表，按代码归属指派责任人；同一指纹的重复告警合并，避免一个人收到几十条通知。修复时限按严重级别约定，例如严重立即处理、高危一周、中危一月、低危排期；具体天数由团队按业务节奏确定，但一旦确定就要可统计、可追责。修复后必须复扫同一规则、同一位置，确认告警消失，并补一条回归用例。

比修完这一个更重要的是根因分析。漏洞频繁出现，可能说明编码规范缺失，可能说明公共组件没有安全默认值，也可能说明团队不知道这种写法有风险。分类统计原因，才能决定投入方向：缺规范补规范，缺能力封装组件，缺意识做培训。最后把修复方式写进编码规范、脚手架模板和代码检查规则，让下一个人在不了解漏洞细节时也能默认写出安全代码。

十一、度量与汇报：别让漏洞数成为唯一的 KPI

安全度量至少覆盖四组指标：发现了多少、修得多快、修得多彻底、漏了多少。发现数按严重级别和项目统计；修复率与平均修复时长反映闭环效率；重开率反映修复质量；逃逸率反映上线后才被发现的比例；误报率和覆盖率反映工具与流程是否健康。单看任何一项都容易失真，组合起来才有解释力。

把漏洞数量当作唯一 KPI，会制造反向激励。团队可以少扫描、拆分项目、把问题标成误报、只报低危，让数字变好看，风险却没有下降。更合理的是看趋势和风险暴露时长：高危从发现到关闭平均用了多久，存量高危是否按计划减少，同类问题是否还在重复出现。汇报时分层表达，给研发看可行动清单，给管理层看风险趋势和资源缺口。

十二、落地路线：先接通，再收紧

落地从一张资产清单开始：有哪些应用、用什么语言、由谁负责、部署在哪里、有没有测试环境和测试账号。没有清单，扫描范围就是模糊的，覆盖率也无从谈起。同时明确授权边界和数据处理要求，测试账号最小权限，测试数据脱敏，生产扫描单独审批。

第一阶段选技术栈匹配、配合度高的项目试点，跑通 SAST 与手工 DAST，校准规则，建立基线，记录误报类型。第二阶段接进 CI，做到增量告警和夜间全量，结果自动开工单，不急着阻断。第三阶段才对新增高危开启门禁，配套例外流程和度量。第四阶段平台化：统一规则管理、多语言、API 扫描、IAST 试点和跨项目报表。每一步都以上一环节稳定为前提。

组织配套同样重要。每个研发团队培养一两名安全联络人，负责初筛和规则反馈；安全团队负责规则、基线、例外审批和复盘；管理层明确优先级和资源。工具只是放大器，流程和责任不清，再好的扫描器也只会生产无人处理的报告。

小结

SAST 与 DAST 不是竞争关系，而是从代码结构和运行行为两个方向逼近同一目标。理解污点传播、爬虫与响应判定，才能判断扫描结果为什么可信、哪里不可信。落地顺序应是先接通 CI、再建立基线、最后收紧门禁，同时用误报治理维护信任，用覆盖率清单暴露盲区，用修复闭环把单次告警转化为团队规范。安全测试的价值不在于报告多厚，而在于风险是否被持续、可验证地降低。
