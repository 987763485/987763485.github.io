Go 结构体设计规范

本文属于《Go 语言与工程》第 28/78 篇
上一篇系列目录下一篇

结构体是 Go 里最普通也最易被忽视的构件。线上问题常常不在算法，而在字段该不该导出、锁有没有被复制、零值能不能直接用。本文从包的边界、内存布局、嵌入、tag 和拷贝语义讲到构造函数与分层，适合能写 Go、希望把结构体设计得更稳的读者。

一、导出性：先想清楚包的边界

Go 用首字母大小写表达可见性，大写导出，小写包内可见。每个导出名都是对使用者的承诺：名字、签名一旦被依赖，再改就是破坏性变更。因此，导出与否应看其他包是否真的需要，而不是“以后可能用得上”；辅助类型和细节默认保持小写。

字段是否导出同样重要。一旦导出，调用方就能直接读写，你也就失去了以后加校验、改内部表示的自由。若类型带有不变式，例如金额不能为负，应把字段设为小写，通过方法暴露受控操作。反过来，配置、请求参数、对外 DTO 这类纯数据载体，导出字段更直接，便于序列化。

函数该返回接口还是结构体，也有取舍。经验是“返回具体类型，接受接口”。构造函数返回 *Decoder，调用方既能使用全部方法，也能按需抽象；一开始返回接口，使用者会被迫依赖一个可能过窄的契约。只有需要刻意隐藏实现，或确实存在多种实现时，返回接口才合理。

二、零值可用：让 var x T 就能工作

Go 没有构造函数也能创建变量，零值是否可用决定类型好不好用。标准库就是示范：var mu sync.Mutex 可以直接加锁，var buf bytes.Buffer 可以直接写入，var wg sync.WaitGroup 可以直接计数。这些类型把内部状态设计成“零值即合法初始状态”。

切片和映射的零值语义要分清。nil 切片可以 len、range、append，追加时自动分配，返回 nil 切片通常没问题；nil 映射可以读，但写入会 panic，声明后必须用 make 或字面量初始化。把两者混为一谈，是最常见的运行时错误。

设计自己的类型时，应优先让零值可用。例如计数器把锁和计数都放进结构体，零值就能工作。只有在需要默认值、申请资源、校验参数，或零值本身有歧义时，才提供 NewXxx。构造函数应返回完整可用的对象，而不是让调用方再补一步 Init；后者容易漏调，也会让并发问题更隐蔽。延迟初始化用 sync.Once 收敛，别每次裸判 nil。

三、字段顺序与内存布局：把大字段放在前面

字段顺序既影响可读性，也影响内存占用。编译器按对齐要求插入填充字节，保证每个字段的地址满足对齐。把小字段夹在大字段之间，填充会变多；把对齐要求高的字段排在前面，往往能减少浪费。看两个语义相同、顺序不同的结构：

差别来自填充：Bad 在 A 之后要空出字节，才能让 B 按 8 字节对齐，末尾还要补齐；Good 把 int64 放前面，两个 bool 紧挨着。字段越多、类型越杂，差距越明显。单个对象差几字节不算什么，但结构体要放进百万级切片或缓存敏感的热路径，节省的内存就值得考虑。

不必对每个结构体都重排。先保证语义分组和可读性，再检查高频、大批量的结构体，用 unsafe.Sizeof 对比。完整计算涉及平台字长和 ABI，本文只点到“顺序会影响大小”。把同类型小字段放在一起，也能减少填充。

四、嵌入与组合：提升不等于继承

匿名嵌入会把被嵌入类型的字段和方法“提升”到外层，让外层看似拥有这些能力。这不是继承：两者没有子类型关系，接收者仍是被嵌入的值。命名嵌入只是普通字段，调用时写 d.Animal.Speak()，语义更明确，也不污染外层方法集。

嵌入值还是指针，会改变方法集，进而影响接口满足。若方法定义在指针接收者上，嵌入 Animal 时，Dog 值的方法集不含 Speak，只有 *Dog 满足接口；嵌入 *Animal 时两者都满足，但调用可能落到 nil 指针上。

不要为了复用几个方法就嵌入。嵌入会把被嵌入类型的导出方法一并暴露，等于扩大 API，也把两个类型的演化绑在一起；被嵌入类型新增方法时，外层可能意外满足接口，或与自己的方法冲突。含互斥锁的类型尤其不要匿名嵌入，否则 Lock、Unlock 会成为外层 API 的一部分。只有确实是“是一个”关系，且愿意公开其能力，才用匿名嵌入；只是“有一个”，就用命名字段。

五、结构体 tag：写给反射看的元数据

tag 是字段后的字符串，编译期不参与类型检查，运行时由反射读取。常见的有 json、db、validate：分别控制序列化键名、数据库列名和校验规则。格式为 key:"value"，多个键用空格分隔，值内用逗号分隔选项，例如 json:"name,omitempty"。

omitempty 是最容易踩坑的选项。它把“零值”当成“没有提供”，空字符串、数字 0、布尔 false、nil 指针和空容器都会被省略。若要区分“用户没传”和“传了 0”，就不能依赖 omitempty，而应使用指针字段或标志位。若只是想减小响应体，省略零值通常没问题，但要确认前端没把“字段缺失”当成错误。

tag 拼写错误不会编译报错。把 json 写成 josn，程序照常运行，只是结果不符；键名写错、逗号位置不对，要等到运行时才暴露。go vet 能检查部分格式非法的 tag，但管不了键名是否正确，关键结构体最好配序列化测试。未导出字段不会被 encoding/json 处理，写 tag 也无意义。

六、可变性与拷贝：值接收者不是随便选的

接收者用值还是指针，先看语义：需要修改接收者，或结构体较大、拷贝成本高，用指针；不可变的小值用值。更实用的规则是一致性：只要有一个方法用了指针接收者，其余也统一用指针，避免调用方困惑。

更要紧的是，含同步原语的结构体不能拷贝。sync.Mutex、sync.WaitGroup 的状态与实例绑定，拷贝后两份状态互不相干，看似加了锁，实际保护的却是两份数据。go vet 的 copylocks 检查会报告“passes lock by value”，把 go vet ./... 放进 CI 能拦住它。

切片和映射字段是浅拷贝。赋值包含切片的结构体只复制切片头，底层数组仍共享，改同一元素会互相影响；映射复制的是指针，任何一方写入对方都看得见。若承诺值语义，就在赋值或返回时显式克隆；若本来就是共享，应在注释里写清所有权。

七、构造函数与校验：把非法状态挡在门外

类型需要默认值、外部资源，或字段之间存在约束时，裸字面量很容易造出非法状态。此时提供 NewXxx，返回 (*T, error)，在函数里完成校验和初始化，比让每个调用方各自检查更可靠。错误信息要指出哪个参数不合法，而不是笼统地说“失败”。

可选参数一多，签名就会膨胀。选项模式在 2019 年已成熟：每个可选项写成一个 Option 函数，构造函数接收变长参数，调用处可读性好，新增选项也不破坏签名。它适合库或框架的公开 API；如果只是服务内部使用，配置结构体更简单，字段一目了然，也方便从配置文件反序列化。

两者并非互斥：对外用选项、对内用配置结构体也是常见组合。关键是分清必填与可选。必填项作为构造参数，让编译器检查；可选项交给选项或配置。不要把十几个布尔开关堆进构造函数，那种签名难读，也易传错位置。

八、DTO 与领域模型分离：一个结构体打不了天下

请求体、响应体、数据库模型和领域对象，字段看似差不多，职责却不同。请求结构体处理缺省和恶意赋值；响应结构体涉及字段兼容性；数据库模型跟表结构绑定，tag 和列名属于持久化细节；领域对象承载业务规则，不应被 JSON 或 SQL 标记污染。合并成“万能结构体”短期省事，长期会把 API、表结构和业务逻辑缠在一起。

典型风险是过度提交：把请求结构体直接绑定到数据库模型，攻击者多传一个 is_admin，就可能被写进库里。转换函数只挑选允许的字段，风险自然收敛。转换代码放在边界层，例如 HTTP handler 或 repository 适配层；逻辑复杂时可单独建 converter 包，但不要塞进领域对象。

字段少时，多写一个结构体和几行转换似乎啰嗦；等接口加字段、表改列时，边界清晰的价值就会显现。判断是否该拆分，可以问：这个结构体有几个变化原因？如果 API 兼容性和数据库迁移都会让它变，就该拆。

九、接口设计：小接口，使用方定义

Go 的接口隐式满足，让我们不修改实现就能抽象。但“能抽象”不等于“该抽象”。接口应由使用方定义：服务层需要存储能力，就声明只含所需方法的接口，由 repository 实现；而不是在 repository 包里预定义大而全的接口。前者按需裁剪，后者往往随实现膨胀。

接口要小。标准库的 io.Reader 和 io.Writer 各只有一个方法，却能组合出文件、网络、缓冲、压缩等大量能力。方法越多，实现负担越重，mock 越难写，调用方还会被迫依赖用不到的方法。一到三个方法是舒适区，超过五个就该反思是否揉进了多个职责。

不要为“以后可能换实现”提前抽象。没有第二个实现、也没有测试替换需求时，直接依赖具体类型更简单；需求出现再提取接口，成本并不高。还要记住接口 nil 的陷阱：值为 nil 的具体指针赋给接口后，接口本身并不为 nil。“无对象”尽量用 nil 接口表示。

十、命名与注释：让 godoc 自己会说话

字段命名要短而明确，同一包内保持一致。Go 的惯例是缩写全大写：ID、URL、HTTP、API、JSON，不要写成 Id、Url；作为复合词的一部分时按整体处理，如 UserID。布尔字段用肯定语义，enabled 比 disabled 少一层负担；带单位的字段把单位写进名字或注释，Timeout 要说明是秒还是毫秒。

导出标识符必须有注释，并以标识符本身开头，这样 godoc 才能正确排版。注释不要复述名字，而要补充其表达不了的信息：单位、取值范围、是否可为 nil、是否并发安全、由谁负责关闭。结构体字段的注释也会出现在 godoc 里，对公开类型尤其重要。一个字段是“调用方必须设置”还是“零值表示默认”，写清楚能省大量沟通。

十一、常见坏味道清单

第一是巨型结构体：几十个字段什么都能塞，最后没人说得清哪些字段有效。按职责拆分，或用组合把相关字段收拢成子结构体。第二是布尔参数：NewServer(addr, true, false) 读代码的人必须跳到定义才知道含义，能用具名选项就用选项，能用枚举就别用布尔。

第三是过多可选字段：一个结构体里一半字段可空，调用方永远在猜哪些组合合法。必填项收进构造函数，可选项收进选项或配置，剩下的用默认值兜底。第四是 nil 与零值混用：有时 nil 表示“未设置”，有时表示“空”，有时又表示“删除”，同一字段三种语义，必然出 bug。第五是把 map 当结构体：map[string]interface{} 看似灵活，却丢掉了字段名、类型和文档，深层嵌套后连键名都记不住。

小结

结构体设计没有银弹，但有几条原则：可见性从包的边界出发，导出即承诺；优先让零值可用，必要时用构造函数守住不变式；字段顺序在批量场景下值得优化，但别牺牲可读性；嵌入要克制，命名组合更安全；tag 是运行时契约，必须用测试兜底；含锁的类型不可拷贝，切片和映射要明确共享语义。再往上，用 DTO、领域对象和小接口划界，结构体就不会随业务增长变成一团乱麻。
