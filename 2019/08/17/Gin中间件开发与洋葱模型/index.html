Gin 中间件开发与洋葱模型

本文属于《Go 语言与工程》第 67/78 篇
上一篇系列目录下一篇

路由决定请求交给谁处理，中间件决定它在到达业务函数前后经过哪些关卡。Gin 的中间件就是签名相同的处理函数，按注册顺序拼进切片，再由游标依次调用。本文以 Gin 1.4 与 Go 1.12 为例，先讲清执行顺序与三种注册位置，再落到鉴权、超时、跨域、错误处理和测试。读者应已能用 Gin 写路由；读完后应能设计一组顺序正确、职责清晰的中间件，并知道哪些写法会在线上出事。

中间件与洋葱模型

Gin 没有为中间件定义专门的类型。gin.HandlerFunc 就是 func(*gin.Context) 的别名，中间件只是注册在业务函数之前的同签名函数，区别在职责和位置，而不在类型系统。也正因如此，它能做的事和普通 handler 一样多：读请求、写响应、改上下文、提前结束请求。

每条路由在注册时都会把分组中间件与自己的处理函数拼成 HandlersChain。请求匹配后，引擎把切片放进从对象池取出的 Context，游标置为 -1，调用一次 c.Next()。Next 只是游标自增加循环调用；中间件在函数体里再次调用它，就会在内部再跑一轮，把后面的函数执行完再返回。递归的调用栈形成层层嵌套，这就是洋葱模型的来源。

由此可以推出两点。第一，注册顺序决定嵌套顺序：最先注册的在最外层，c.Next() 之前的代码最早执行，之后的最晚。第二，后半段运行时业务 handler 通常已写出响应，所以那里只适合日志、耗时统计、资源清理，不能再改状态码或响应体。

提前结束请求要用 c.Abort()。它把游标设成极大的终止值，循环立刻不成立，后面的处理函数不会再被调用。AbortWithStatus 在终止的同时写状态码，AbortWithStatusJSON 再补一个 JSON 体。要注意 Abort 只影响后续的链，不会中断当前函数，写在它后面的语句仍会执行，所以中止时几乎总要紧跟 return。

洋葱的执行顺序

假设注册了 A、B 两个中间件，最后是业务函数 H，执行顺序是 A 前半段、B 前半段、H、B 后半段、A 后半段。可以把它想成往洋葱中心走再原路返回，也可以对照 Express 的 next() 与 Koa 的 async 洋葱：思想一致，只是 Gin 用切片加游标实现，没有 await 语法糖，后半段必须写在 c.Next() 之后。

flowchart TD
    A[请求进入] --> B[Logger 前半段]
    B --> C[Auth 前半段]
    C --> D[业务 Handler]
    D --> E[Auth 后半段]
    E --> F[Logger 后半段]
    F --> G[响应返回]

这个顺序解释了 Logger 为什么能统计完整耗时：它在最外层记开始时间，等内层全部返回后才算差值。也解释了在 c.Next() 之后调用 c.JSON 为什么只得到 Headers were already written 的警告：状态码和响应头在第一次写出时已发给客户端，后面再改没有意义。

注册位置与作用域

Gin 提供三种注册方式，作用范围依次收窄。r.Use() 挂在根分组上，对所有随后注册的路由生效；r.Group("/api", Auth()) 创建带公共前缀和公共中间件的分组，还可以嵌套；r.GET("/report", Auth(), Report) 只给这一条路由加中间件，参数从左到右构成链，业务函数放最后。

这里有个容易忽略的细节：链是在注册路由那一刻拼接的，不是请求到达时动态计算的。Use 只是往分组的 Handlers 切片追加函数，之后注册的路由才会把这份切片复制进自己的链。先注册路由再调用 Use，那条路由不会获得新中间件；分组创建后再 group.Use()，也只影响其后注册的路由。线上“中间件明明加了却不生效”，多数是这个原因。

顺序错误带来的问题往往比漏加更隐蔽。把鉴权放在 CORS 之前，浏览器的预检请求不带令牌，会被 401 挡下，前端看到的却是一条跨域错误；把 Recovery 注册在业务分组内部，注册在它之前的中间件发生 panic 就没人接住；给整个引擎加鉴权而把健康检查和静态资源也圈进去，监控探针会一直收到 401。比较稳妥的全局顺序是：Logger、Recovery、CORS、错误处理、鉴权，再往后才是业务分组。

分组的价值在于把共同前缀和共同前置条件绑在一起，例如 /admin 统一挂鉴权与审计，/public 只挂限流。单路由中间件适合一次性需求，例如某个导出接口单独加 30 秒超时。三种方式混用时，要能用一句话说清每个请求实际经过的链。

内置中间件：Logger 与 Recovery

gin.Default() 等价于先 gin.New()，再 Use(Logger(), Recovery())。这两个中间件覆盖了最基础的可观测性与兜底，但默认行为未必适合生产。

Logger 在 c.Next() 之前记录时间与请求行，在之后读取状态码、耗时、响应体大小和错误信息，拼成一行日志。默认格式包含时间戳、状态码、客户端 IP、方法与路径，排查慢请求够用；接入统一日志系统时，用 LoggerWithConfig 提供 Formatter，改成 JSON 或固定分隔符，并用 SkipPaths 去掉健康检查这类噪音。BodySize 是已写出的字节数，ErrorMessage 来自 c.Errors 中的私有错误，正好和错误处理中间件衔接。

Recovery 是一个 defer 加 recover：捕获 panic 后打印 panic 值与调用栈，再 AbortWithStatus(500)。默认输出到标准错误，生产环境应换成 RecoveryWithWriter，写进日志文件或日志库。调用栈包含源码路径，只能进日志，绝不能返回客户端；对外只给不带细节的 500。还要记住 recover 只能捕获同一个 goroutine 的 panic，另起的 goroutine 一旦 panic，整个进程都会退出。

静态文件也走同一套链。r.Static("/static", "./web/static") 注册的是带通配符的 GET 与 HEAD 路由，全局中间件同样作用在它们身上。若全局挂了鉴权，静态资源就会 401；应把静态目录放进独立分组，或让鉴权中间件按前缀跳过。CORS 相反，应尽量靠前，让预检和错误响应都带上跨域头。

鉴权中间件与上下文传值

鉴权中间件的职责很单一：取出凭证、验证、把身份写进上下文、放行；失败就中止并返回 401。凭证通常放在 Authorization 头里，格式是 Bearer 加空格加令牌。解析前先检查前缀，避免把空值或别的认证方案当成令牌。

以 JWT 为例，解析时要显式校验签名算法。jwt-go 的 Parse 会按令牌头里的 alg 选择算法，如果不检查，攻击者可以把 alg 改成 none 或换成非对称算法来绕过验签。校验通过后还要检查过期时间与必要字段，再把用户 ID 写进 c.Set。键名用包级常量，避免裸字符串拼错后只能得到一个取不到值的空接口。

后续 handler 用 c.Get 读取，第二个返回值表示键是否存在，取值后必须做类型断言；c.MustGet 在键不存在时会 panic，只适合确定由前置中间件写入的场景。上下文只放身份标识和少量请求级数据，不要塞数据库连接或敏感字段。c.Set 底层就是写 map，没有加锁。

失败分支值得单独强调：调用 AbortWithStatusJSON 之后一定紧跟 return。它内部先 Abort 再写 JSON，链确实被截断，但当前函数还会继续跑，后面的查库、写日志甚至再次写响应都会产生难以理解的行为。

超时、context 与 goroutine 安全

Go 的请求自带上下文。c.Request.Context() 在客户端断开或服务端关闭连接时被取消，下游的数据库查询、RPC、HTTP 调用都应带上它，否则上游走了，下游还在消耗连接和 CPU。Go 1.12 还没有 NewRequestWithContext，外发请求先构造再 req.WithContext(ctx)；数据库侧用 QueryContext 一类方法。

Gin 没有内置超时中间件。思路是换上带截止时间的 context，调用 c.Next() 跑完后续处理，返回后若已超时且响应未写出，补一个 504。它只能通知不能终止 handler：Go 无法从外部杀死正在执行的函数，handler 必须在耗时操作里监听 ctx.Done()。若只加中间件而不传 context，请求仍会跑满全程，504 也可能在业务写出响应后才出现。

另一个高频问题是 goroutine。*gin.Context 在请求结束后会被放回对象池，下一次请求可能复用同一个对象；直接起 goroutine 持有原始指针，等它醒来时上下文可能已被重置，读到别的请求的数据，甚至发生数据竞争。Gin 提供 c.Copy() 生成只读副本：复制 Keys 与 Request，把 ResponseWriter 置空、handlers 清空、游标设为终止值。副本可以读，但不能写响应，向它调用 JSON 会 panic。

异步任务还需要独立的生命周期。请求的 context 在响应结束时就被取消，goroutine 里若继续用它查库，往往刚拿到连接就被取消。正确做法是用 context.Background() 派生一个带自己超时的 context，并把需要的数据在启动 goroutine 之前取出来传进去。最后是并发写响应：http.ResponseWriter 不支持并发写，两个 goroutine 同时写会让响应体交错、状态码互相覆盖，Gin 也会检测到重复写头并打印警告。需要并行取数时，用 channel 或 sync.WaitGroup 收敛结果，最后只在 handler 里写一次。

手写一个 CORS 中间件

浏览器的同源策略只允许页面读取同源响应。带自定义头或 JSON 体的跨域请求会先发 OPTIONS 预检，服务端回答允许的方法与头，真实请求才发出。最小实现三步：判断来源、写回 CORS 头、对预检返回 204 并中止。来源要回显具体 Origin 并加 Vary: Origin，不能写 *；携带 Cookie 时 Access-Control-Allow-Credentials 为 true，此时 Origin 与 Allow-Headers 都不能用通配符，只能逐个列出。

注册位置同样重要。CORS 应全局注册：Gin 的 404 链不含分组中间件，只定义 GET 的路径收到 OPTIONS 会落到 NoRoute，分组中间件不执行。全局注册还能让鉴权失败、参数错误、panic 兜底的响应带上跨域头，前端才读得到真实状态码。

错误处理中间件

handler 遇到错误可以自己写响应，也可以交给上层。后者的入口是 c.Error(err)：把错误追加到 c.Errors，可标记类型、附加元数据，但不中止链也不写响应，所以调用后仍要 return。统一处理放在中间件里：先 c.Next()，返回后检查 c.Errors 非空且响应未写出，才接管。响应已写出时只能记日志。

错误映射用自定义类型承载 HTTP 状态码、业务码与用户可读消息；错误经 github.com/pkg/errors 包装时，先用 Cause 取出根因再断言。Go 1.12 的标准库还没有把错误链做进语言，工程里普遍依赖这个库。

它与 Recovery 的分工要讲清楚：c.Error 处理预期内的业务错误，响应 4xx 加封套；Recovery 处理 panic，响应 500 且不暴露细节。panic 会展开调用栈，错误中间件 c.Next() 之后的代码不会执行，所以 Recovery 必须在更外层。业务错误也不该靠 panic 传递。业务码如何分段、哪些错误对用户可见，留给专门的文章；本文只关心中间件把错误变成响应。

用 httptest 测试中间件

中间件测试不必启动服务器：httptest.NewRequest 造请求，httptest.NewRecorder 收响应，交给引擎的 ServeHTTP 后就能断言状态码、响应头与响应体。测试前设置 gin.SetMode(gin.TestMode) 关掉调试输出。鉴权这类分支明确的中间件适合表驱动，每个用例新建引擎，避免中间件越挂越多；除状态码外，还要在业务 handler 里置标志位，断言失败分支没有执行，才能证明 Abort 真的截断。

跨域中间件要断言回显的 Origin、Vary 与预检状态码；错误处理要断言封套里的业务码，并覆盖响应已写出的分支；超时中间件可以配短暂超时和故意阻塞的 handler，断言 504。测试顺序时，让几个处理函数往同一切片追加标记，最后比较完整序列，比单独断言某个函数被调用更能发现错误。加上 -race 跑一遍，还能发现上下文被并发读写的问题。

常见坑清单

  • Abort 之后忘记 return，后续语句继续执行，可能重复写响应。
  • 以为不调用 Next 就能短路。引擎外层循环仍会调用后面的 handler；写了 401 却没 Abort，业务函数照样执行。
  • 在 Next 之后写响应。头已发送，Gin 只打印 Headers were already written，客户端看到的仍是旧响应。
  • 顺序错误：CORS 晚于鉴权、Recovery 太靠内、全局鉴权挡住探针与静态资源。
  • 在 goroutine 里持有原始 *gin.Context，或向 c.Copy() 写响应。
  • 先注册路由再 Use，或分组创建后补 Use，中间件不生效。
  • 超时中间件不向下游传 context，误以为它能终止 handler。
  • c.Set 存入可变对象，随后在别处并发修改。

小结

中间件是一条由注册顺序决定的函数链，Next 进入内层，Abort 截断，二者构成洋葱模型。全局、分组、单路由对应不同作用域，链在注册时拼接，顺序与时机不能想当然。鉴权、超时、跨域、错误处理的核心都是及时中止、只写一次响应、把 context 传下去。*gin.Context 不是并发安全的，跨 goroutine 只能用只读副本与独立生命周期。
