Go 单例模式与 sync.Once

本文属于《Go 语言与工程》第 46/78 篇
上一篇系列目录下一篇

单例大概是设计模式里被讨论得最多、也用得最滥的一个。Go 没有专门的语法支持它，落地形态通常是一个包级变量加一次初始化，而并发恰好让“只初始化一次”变得比看上去难。本文从朴素的惰性初始化讲起，说明双重检查锁定为什么在 Go 里靠不住，再讲 sync.Once 的用法、Do 的 panic 语义、带错误的单例写法与测试中的重置，最后讨论什么时候干脆不要单例。适合已经写过 Go 服务、想弄懂并发初始化的读者。

单例在 Go 里意味着什么

单例模式的定义很朴素：某个类型在进程内只存在一个实例，并提供一个全局访问点。在 Go 里它由两部分组成：唯一性由包级变量保证，因为包只会被初始化一次；访问点是一个导出函数。

Go 社区对全局状态的态度偏保守，理由都是工程上的实际情况。其一，依赖变成隐式的，看签名看不出它读了全局配置，测试必须先摆好环境。其二，包级变量跨用例存活，测试之间互相污染。其三，初始化时机不可控，第一次调用往往发生在请求路径上，失败得晚。其四，并发可见性问题，后面会展开。

双重检查锁定及其历史

为了兼顾“无锁快路径”和“只创建一次”，上世纪九十年代起，Java 与 C++ 社区流行起双重检查锁定。2001 年前后，Java 社区指出它在没有 volatile 的内存模型下是错的：构造函数写字段与把引用写入共享变量之间可能被重排，另一个线程可能看到一个非 nil、字段却还是零值的对象。Java 5 修订内存模型之后，这个模式才算修好。

它至少保证了创建只发生一次。但快路径那次读既没加锁也不是原子操作，与锁内的写构成数据竞争。Go 的内存模型只对 channel、mutex、atomic 这些同步原语给出 happens-before 保证，普通变量读写没有：编译器可以重排指令，CPU 也可以让写以不同顺序对其他核心可见。结果就是别的 goroutine 可能先看到指针、后看到字段，拿到构造到一半的对象。

“我在 x86 上跑了一年都没事”是常见辩护。x86 的内存序确实强，它“往往”能跑对，但这是运气不是承诺：换到 ARM 服务器、换一个 Go 版本，假设就破了。Go 又没有 volatile 可以打补丁，想修正只能把快路径换成 atomic.LoadPointer 配 atomic.StorePointer，还要引入 unsafe，复杂度立刻上一个台阶。

真正缺的是内存屏障语义

双重检查锁定缺的不是“再补一把锁”，而是快路径与慢路径之间的同步配对。初始化对字段的写必须以“发布”的方式让其他 goroutine 看到，读取方必须以“获取”的方式确认看到的是完成品，这就是 release 与 acquire 语义，也就是常说的内存屏障。mutex 的 Unlock 与 Lock、channel 的收发、atomic 操作都能提供配对，普通变量读写不能。手写正确的版本并非不可能，而是不值得，标准库已经把这件事做完了。

性能方面，快路径就是一次 atomic.LoadUint32，开销在纳秒量级，与一次配置解析或网络拨号不在一个数量级，没有理由为此手写双重检查锁定；真正要注意的是别在循环里反复调用 Do。

初始化失败：panic 语义与错误返回

文档写明的 panic 语义

Go 1.12 的 sync.Once 文档里有一句容易被忽略的话：If f panics, Do considers it to have returned; future calls of Do return without calling f。也就是说，f 一旦 panic，Once 把它当作已经返回，后续调用直接返回，不会再执行 f，没有“回滚”这回事。

对照实现就很好理解：置位写在 defer 里，panic 展开时 defer 照样执行，done 被置为 1、锁被释放，panic 继续向上抛。

麻烦在于：如果 panic 被上层 recover 了（比如 HTTP 框架的恢复中间件），进程没有退出，单例却永远停在未初始化状态，之后每个请求拿到的都是 nil，报错位置离根因可能隔了几十层。所以初始化函数的第一条纪律是不要 panic，除非那是不可恢复的编程错误。

失败之后如何不陷入死局

既然 Once 不会重试，就要在“允许失败”上做选择，通常有两条路。

第一条是快速失败。初始化放到启动阶段同步执行，失败就记日志并退出，或把错误返回给 main。问题在发布或重启时立刻暴露，而不是等第一个请求。对配置、数据库连接这类“没有它服务就没法工作”的依赖，最省心。

第二条是把失败变成返回值。初始化函数把 error 带出来，Once 只负责“尝试过一次”，是否重试由业务决定，适合可以降级、稍后重试的依赖。若确实需要重试，就不能直接用 Once，而要用 mutex 加状态位自己实现，或用 golang.org/x/sync/singleflight 合并并发重试，避免失败瞬间打满下游。

无论选哪条路，都不要让“nil 单例”在进程里流通。发现初始化失败后继续提供服务，等于把一个确定的错误拖成随机的空指针。

用依赖注入替代全局单例

结构体方案再往前走一步，就是彻底不提供全局访问点：在 main 里创建一次，然后作为参数传下去。

所谓单例的“唯一”，此时由装配层保证，而非包级变量。构造函数校验依赖非 nil，字段不导出，对象构造完就可用。收益很直接：依赖在签名里可见，测试天然隔离，生命周期清楚——谁创建谁关闭，main 里一个 defer 就能收尾；需要多套实例时也不必改全局。依赖多起来后，手写装配会变长，可以交给 wire 生成，但生成的仍是显式传递的代码。wire 的用法在《Go 依赖注入与 wire》里讲过，不再展开。

单例适合什么，不适合什么

适合做成进程内唯一的东西，通常有几个共同点：本身并发安全、创建成本高、生命周期与进程一致。数据库连接池是典型，*sql.DB 内部已维护连接池和锁，全进程一份最合理；只读配置、日志器、指标注册表、模板缓存也属于这一类。要留神 logger：它可以共享，但当前用户、trace id 这类请求级字段不该塞进全局 logger，而应在每个请求里派生。

不适合的同样明显。带请求状态的对象首当其冲，比如保存当前用户、请求体缓冲区的结构体，做成单例后并发请求互相覆盖，症状是偶发的数据串号。生命周期独立于进程的资源也不适合，例如每个租户一个连接、每个任务一个临时目录。需要多个实例的东西更不该硬套。

还有一点必须说清：单例只保证“只有一个实例”，不保证“并发安全”。内部若有可变字段，仍要加锁或用 atomic 保护。判断标准很简单——先问方法是否读写共享可变状态，再谈要不要唯一。

几个容易踩的坑

第一，在 Do 内部再次触发同一个 Once。文档明确写了，若 f 导致 Do 被再次调用会发生死锁，因为 Mutex 不可重入。初始化函数里调用一个会回过头来调用本函数的方法，是常见诱因。

第二，在 f 里起 goroutine 然后立刻返回。此时 done 已置位，其他调用者以为初始化完成，实际拿到半成品，那个 goroutine 的写入也没有同步保证。确实需要异步预热，就在 f 里用 WaitGroup 等它结束。

第三，把内部可变状态暴露出去。Get 直接返回内部 map 或 slice，调用方随手增删，单例就成了人人可改的全局变量。应返回值拷贝，或只暴露方法。

第四，依赖包级变量的初始化顺序。同一包内 Go 按依赖关系排序，跨文件、跨包则依赖编译器给出的文件顺序，不要押注；两个单例互相引用还会触发 initialization cycle。把顺序写进 main 更可靠。

小结

单例在 Go 里不是语法特性，而是“包级变量 + 一次初始化”的约定；难点不是怎么写，而是并发下只写一次、写完如何被看见。sync.Once 以一次原子读为快路径、互斥锁加双重检查为慢路径，同时提供所需的内存语义，正确性和性能都足够，没有理由再手写双重检查锁定。使用时记住两点：f 不要 panic，失败通过包级错误变量带出并在 Do 之外返回；Once 不会重试，需要重试就换工具。测试与解耦的正解是结构体加构造函数，进一步则在 main 中创建一次、显式传递。确实需要全局唯一时再用 Once，其余场合让依赖显式流动。
