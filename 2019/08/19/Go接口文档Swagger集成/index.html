Go 接口文档 Swagger 集成

本文属于《Go 语言与工程》第 68/78 篇
上一篇系列目录下一篇

前后端联调时，最怕的不是接口有 bug，而是双方理解不一致：字段名拼错、必填项漏传、错误码对不上。本文以 Gin 1.4 项目为例，讲清楚如何用 swaggo 注解从代码生成 Swagger 文档，并让文档直接发起调试请求。读完后你能搭起一套“改代码顺手改文档”的流程，也知道它在哪些地方会失效。

为什么需要接口文档

接口文档是前后端之间的契约，要回答的问题很具体：路径、方法、请求字段、必填与否、类型、成功与失败的返回结构。契约清楚，前端可以先造 mock 数据并行开发，后端也不用在联调时反复解释。

问题通常不在“有没有文档”，而在“文档是否跟得上代码”。手写文档放在 Wiki 里，接口改了三轮，文档还停在第一版；新人照着旧文档调用，得到一堆 400，排查半天才发现字段早已改名。过期文档比没有文档更糟，它会制造错误预期。

做法分两类：设计先行，先写 OpenAPI 描述再实现；代码生成，在 handler 上写注解，由工具扫描源码产出文档。前者契约更严谨，后者胜在离代码近，改接口时注解就在眼前。本文走后一条路，工具是 swaggo/swag 加 gin-swagger，输出 Swagger 2.0；OpenAPI 3.0 虽已发布，但当时围绕 Gin 的注解工具链仍以 2.0 为主，够用且稳定。

工具链：swag 与 gin-swagger

两个角色要分清。swag 是命令行工具，解析 Go 源码的注释与结构体，生成 docs 包，内含 docs.go、swagger.json、swagger.yaml。gin-swagger 负责运行时提供 Swagger UI 与静态资源，页面加载后读取 /swagger/doc.json 渲染接口列表。

swag 做的是静态分析，不运行代码。它按包扫描文件，用 go/ast 解析注释，再结合结构体字段与 json tag 推导 schema。因此运行时拼出来的路由、反射注册的 handler、动态决定的字段，都不会出现在文档里。

运行时，UI 会向 /swagger/doc.json 请求描述文件，再按 BasePath 拼接真实接口地址。因此 docs 包必须被编译进二进制，否则页面能打开，接口列表却是空的。

逐行看。@title 是文档标题，显示在页面顶部；@version 是接口版本，与代码 tag 无关，纯属文档信息；@description 支持简单换行与 Markdown，但别写太复杂的格式，不同版本 UI 的渲染效果并不一致。

@securityDefinitions.apikey 定义一种鉴权方式，后面的 ApiKeyAuth 是自定义标识，供接口上的 @Security 引用；@in header 与 @name Authorization 说明 token 放在哪里。这几行必须连在一起，中间不要插入其他注解。

接口注解逐项说明

接口级注解写在 handler 上方，与函数之间不能有空行，否则 swag 不认为它们属于这个函数。一个创建接口如下：

@Summary 是一行短标题，出现在列表里；@Description 是详情，可写业务规则与错误语义；@Tags 决定分组，同一标签的接口归在一起，建议按资源名而非 Controller 名分组。

@Accept 与 @Produce 声明请求和响应的 MIME 类型，常用 json；表单与文件上传分别用 x-www-form-urlencoded 和 mpfd。它们影响 UI 上请求体编辑器的形态，写错会导致示例请求发不出去。

@Param 信息量最大，格式是“名字 位置 类型 是否必填 描述”，五段用空格分隔。位置只能是 path、query、header、formData、body；类型可以是 string、integer、boolean、number、file 等基础类型，也可以是结构体名；描述含空格时用双引号包起来。

@Success 与 @Failure 的格式是“状态码 花括号里的类型 模型”，花括号里写 object 或 array。Swagger 2.0 没有 oneOf 这类组合能力，不同业务错误通常共用一个响应封套，靠 code 字段区分。@Router 写“路径 方法”，方法小写并放在方括号里；路径占位用花括号，如 /users/{id}，而 Gin 路由是 /users/:id，两套写法别混。

注解之间的顺序没有严格要求，但每条注解必须独占一行，描述也不要手动折行。

请求体用结构体承载，json tag 决定文档里的字段名，binding tag 供 Gin 校验，两者要一起维护：

body 参数的写法是 @Param user body CreateUserRequest true “用户信息”。body 只能有一个，类型必须是结构体名，不能写 object 或 map，swag 需要字段定义才能展开 schema。

字段上的 example 会出现在 UI 的示例值里。时间字段用 time.Time，swag 会推导成 string 加 date-time 格式；如果项目里用自定义时间类型，要说明序列化后的格式，避免前端按错误格式解析。

参数位置的区别，说到底是数据来自请求的哪一部分。path 参数来自 URL 路径，必须声明为必填，名字与 @Router 里的占位符一致：

query 来自问号后的键值对，常用于筛选与分页，可以带默认值和范围约束：

header 用于自定义请求头，例如链路追踪 ID；formData 用于表单与文件上传，文件类型写 file，同时 @Accept 要声明 mpfd。body 与 formData 不能同时出现，前者是整体 JSON，后者是逐字段提交。

上传接口把参数位置写成 formData，类型写 file；header 参数同样是五段式，只是位置换成 header，名字要按请求头的真实拼写写，大小写不要随意改。

需要强调：default、minimum、Enums 这些修饰只作用于文档与 UI 预填，不会在服务端自动生效。默认值该在代码里补的还要补，枚举该校验的还要校验。文档描述契约，不代替实现。

要区分两件事：文档里的鉴权声明只影响 UI 的调试行为和阅读者的理解，不参与任何服务端校验。真正的鉴权仍由中间件完成，JWT 的签发、刷新与吊销也不在本文范围内。另外，公开部署的 UI 等于把接口清单交给所有人，生产环境要么关闭，要么放到内网或网关鉴权之后。

版本管理与 CI 校验

生成物入库之后，最容易出现的问题是“代码改了，docs 没重新生成”。靠自觉不靠谱，把它放进流水线。每次提交前本地跑一次 swag init，CI 里再跑一次，然后检查工作区是否有差异：

只要有 diff，就说明注解与生成物不同步，让流水线直接失败。这个检查成本很低，却能挡住绝大多数文档过期的问题。代码评审时也应把 docs 的 diff 当作正文看：新增了哪个接口、哪个字段从必填变成可选，一眼就能看出来。

多版本文档要提前规划路径。推荐把大版本放进 BasePath，例如 /api/v1 与 /api/v2，各自维护独立的 handler 与注解；如果两个版本长期共存，更稳妥的做法是拆成两个服务，或拆成两份独立部署的文档，而不是在同一个进程里注册两套 spec。后者依赖全局注册状态，后注册的容易覆盖先注册的，调试时非常迷惑。

还要注意，@version 与 API 的大版本是两回事：前者只是文档展示信息，真正决定请求路径的是 BasePath 和路由注册。

常见坑与规避

第一类是注解拼写错误。swag 对无法识别的注解是静默忽略的，把 @Summary 写成 @Summry，生成不会报错，只是 UI 上少了一行标题；字段级的修饰写错同理。生成后逐页翻一遍，比事后排查便宜。还有一种隐蔽情况：@Param 的必填标记误写成 false，参数永远不会标成 required，联调时双方都容易忽略。

第二类是 @Router 与实际路由不一致。注解里写 /users/{id}，Gin 里注册成 /user/:id，文档看起来正常，点“试一下”却返回 404。路由字符串无法在注解里引用常量，只能靠评审和联调发现；把路由表集中管理，注解与注册代码放在同一个文件里，能减少漂移。

第三类是结构体缺 json tag。没有 tag 时，schema 直接用 Go 字段名，UI 上出现 Name、Email 这样的大写字段，和实际 JSON 对不上；匿名的内联结构体还会生成难以辨认的 schema 名，前端看不懂。DTO 一律补齐 json tag，是成本最低的规范。

第四类是泛型思维。Go 1.12 时代没有泛型，不要尝试写 Response[T]，也不要为了复用把响应定义成 map[string]interface{}，那样生成的 schema 是空的。老老实实为每种返回写具体结构体，或者用 data=Type 覆盖。

第五类是文档路径与 BasePath 打架，前面已经说过，swagger 路由必须挂在根引擎。第六类是跨域：文档页面和 API 不同源时，浏览器的预检请求会先到，CORS 中间件必须允许 Authorization 头，否则 Authorize 里填了 token 也发不出去。这类问题在本地用 file:// 打开 swagger.json 时不会出现，一部署就暴露。

与其他方案对比

手写 OpenAPI YAML 是最直接的替代方案。它的优势是设计先行、语言无关，前端可以拿描述文件直接生成 mock 和客户端；代价是要单独维护一份文件，接口一变就得同步改，漂移风险和 Wiki 文档一样。

goa 这类框架走的是另一条路：用 DSL 描述设计，生成服务端代码、客户端代码和文档。契约约束最强，但需要按它的方式组织项目，学习与迁移成本都不低，适合从零设计的新项目。

gRPC-gateway 则以 proto 为唯一来源，同时生成 gRPC 服务和 REST 网关，并附带 Swagger 描述。内部服务之间以 RPC 为主、又需要对外暴露 HTTP 接口时很合适，代价是引入 protoc 工具链和额外的一层转换。

对已经用 Gin 写了不少接口的项目来说，注解生成的侵入性最小：不改路由结构，不引入新框架，只在 handler 上方加注释。它的短板也很明确——注解是注释，编译器不校验，必须靠 CI 和评审兜底。

小结

接口文档的价值在于它是契约，而不在于它长什么样。注解生成解决的是“文档离代码太远”的问题，让更新成本降到顺手为之；它不能解决“注解写错”的问题，那需要生成后的检查与流水线校验。落地时记住三件事：全局注解与 BasePath 要和路由前缀一致，生成物要入库并在 CI 中比对，生产环境的文档入口要有访问控制。工具会换代，这三条与工具无关。
