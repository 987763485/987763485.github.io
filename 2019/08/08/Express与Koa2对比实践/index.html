Express 与 Koa 2 对比实践

本文属于《TypeScript 学习路线》第 62/74 篇
上一篇系列目录下一篇

Express 和 Koa 2 是 2019 年 Node.js 服务端绕不开的两个名字。本文不比较谁“更好”，而是把两者的中间件模型、错误处理、响应组织、路由与生态放在一起，用可以运行的最小示例说明差异从何而来，最后给出新项目选型与老项目迁移的判断依据。读者需要对 Node.js 的 HTTP 模块和 Promise 有基本了解。

一、两条来路：从 connect 到 async/await

Express 诞生于 2010 年，作者 TJ Holowaychuk 借鉴了 Ruby 的 Sinatra，把“路由加中间件”的做法带进了 Node.js。它早期的中间件机制直接来自 connect：一个请求依次经过若干函数，每个函数的签名是 (req, res, next)，调用 next() 表示交给下一个。Express 3 把 connect 作为依赖内置，Express 4 则做了拆分：内置中间件被移到独立包，路由被提炼成 express.Router，核心只留下应用与路由两层。这一版接口稳定了很多年，2019 年线上绝大多数 Express 服务仍是 4.x。

Koa 同样出自 Express 的作者团队，2013 年发布，设计目标是“更小、更富有表达力”。Koa 1 依赖 generator 与 co 库来模拟同步写法，Koa 2 改用 async 函数；async/await 在 Node.js 7.6 之后成为默认能力，Koa 2 也因此真正具备了落地条件。两者的定位差异从名字就能看出来：Express 是一个完整的 Web 框架，路由、静态文件、视图渲染都有约定；Koa 只提供 HTTP 内核，一个 ctx 对象和一套中间件调度，其余能力全部交给中间件。

这个差异不是审美问题。async/await 让“等待下游处理完再继续”成为语言级能力，中间件因此可以写成前后两段，Koa 的洋葱模型正是建立在这上面；而 Express 的 next() 只是一个放行信号，它没有返回值可以等待。后面几节的差异，几乎都能追溯到这一点。

二、中间件模型：线性回调与洋葱

先看 Express。中间件按注册顺序进入一个数组，请求到来时从头到尾走一遍，每个中间件决定是否调用 next()。它是一个线性的责任链：谁调用 next()，谁就把控制权交出去；谁写了 res.end() 或 res.send()，谁就结束这次请求。

这段代码的输出顺序是 logger before、handler、logger after。看起来也有“回程”，但要小心：logger after 之所以能执行，是因为下游的 handler 是同步返回的；一旦下游有异步操作，next() 会立刻返回，logger after 可能在响应之前就打印了。Express 没有“等所有下游完成”的语义，这是它和洋葱模型最本质的区别。

sequenceDiagram
    participant C as 客户端
    participant L as 日志中间件
    participant A as 鉴权中间件
    participant B as 业务处理

    L-->>C: 响应

请求从外层穿到内层，再原路穿出来，每一层都有明确的进入点和退出点，这就是“洋葱”。Express 的执行顺序则是单向的：logger before、鉴权、业务处理、响应发出，至于 logger after 落在哪里，取决于下游是否同步。想在 Express 里稳定地做后置处理，得借助 on-headers、监听 res 的 finish 事件之类的旁路手段，模型本身不提供。

三、错误处理：谁能接住下游的异常

Express 的错误处理靠一个约定：四参数中间件 (err, req, res, next) 就是错误处理器，必须注册在所有路由之后。同步代码里 throw 出的异常，Express 会在调用处理函数时用 try/catch 捕获并转成 next(err)；但异步回调里抛出的异常不在这个 try/catch 范围内，必须自己调用 next(err)。

2019 年最常踩的坑是 async 路由。Express 4 不认识 async 函数返回的 Promise，await 抛出的异常不会自动进入错误中间件，请求会一直挂起，进程则可能报 unhandledRejection。常见做法是包一层：

ctx.throw 来自 http-errors，会根据状态码生成带有 status 与 expose 属性的错误，生产环境可以据此决定是否把细节暴露给客户端。

对比下来，Express 的错误要“逐层上报”，谁异步谁负责调用 next(err)，漏一处就断链；Koa 的错误“自然冒泡”，一个 try/catch 能覆盖它下面所有中间件，最外层的错误中间件因此可以写得非常薄。反过来说，Koa 也要求团队养成写 await next() 的习惯，漏掉 await 的中间件既不会等待下游，也捕获不到下游的错误。

四、响应与上下文：res 直写与 ctx.body

Express 把 Node.js 原生的 req 与 res 直接交给处理函数，只是加了几个便捷方法。res.status(404).json({ message: ‘not found’ }) 链式设置状态码与响应体，res.send 根据参数类型决定 Content-Type，res.sendStatus 用状态码对应的文本作为响应体。响应头一旦发出，res.headersSent 变为 true，再改状态码或头就没有意义了，这一点在写统一响应包装时要特别注意。

请求侧，req.query 由 query parser 解析，req.params 来自路由占位符，req.body 则依赖解析中间件。Express 4.16 起内置了 express.json() 与 express.urlencoded()，不再必须单独安装 body-parser，但老项目里仍常见 app.use(bodyParser.json()) 的写法。Koa 侧通常使用 koa-bodyparser，解析结果通过 ctx.request.body 读取。

Koa 的 ctx 把请求与响应聚合成一个对象：ctx.request 与 ctx.response 是封装后的对象，ctx.req 与 ctx.res 才是原生对象。最常用的 ctx.body 是一个访问器，赋值时 Koa 会根据类型推导响应：对象序列化为 JSON，字符串按 HTML 或纯文本处理，Buffer 作为二进制，Stream 直接管道输出，赋 null 则返回 204；显式设置 ctx.status 可以覆盖默认值。ctx.state 是一个约定好的命名空间，用来在中间件之间传递当前请求的数据，比如登录用户。

六、生态、成熟度与性能

Express 的优势首先在存量。近十年的积累让 npm 上几乎每一种需求都有现成中间件：session、passport 认证、multer 上传、cors、helmet、各类模板引擎的视图适配。代价是质量参差，一些包多年不更新，深层依赖里可能带着早已废弃的模块。Express 4 本身的维护节奏偏保守，2019 年的更新主要是小版本与安全修复，好处是接口稳定，从 4.0 升到 4.17 几乎不需要改代码。

Koa 的中间件数量少一个量级，但常用能力都有对应实现，且因为基于 async 函数，中间件源码普遍更短、更容易读。它的门槛在于概念：要理解 Promise、洋葱顺序与 await 的必要性，团队里只要有人漏写 await，问题往往表现为接口偶发无响应，排查成本不低。Koa 的核心维护者不多，更新节奏同样克制。

调试体验也值得纳入选型。Express 的调用栈贴近原生，出错位置比较直观；Koa 的 await 链在旧版本 Node.js 上堆栈容易被截断，Node 12 默认开启异步堆栈后有所改善，但仍要求开发者从中间件顺序入手定位。人力方面，Express 几乎不需要额外培训，Koa 至少需要一次团队内的分享与约定。

性能方面只做定性判断：Koa 的核心更轻，请求路径上的抽象更少，中间件链通常也更短，理论上单请求开销更小；Express 因为历史包袱，中间件栈往往更长。但在真实服务里，时间主要花在数据库查询、下游 RPC、模板渲染和序列化上，框架调度所占的比例很小。拿 hello world 级别的压测结果做选型依据并不靠谱，真要看数据，应该用自己的路由和中间件栈去压。对绝大多数业务来说，性能不是决定因素，错误处理是否清晰、团队是否熟悉，权重更高。

七、迁移策略：渐进替换而不是整体重写

从 Express 迁到 Koa，最稳妥的方式是按边界逐步替换，而不是推倒重来。

第一步是统一错误处理与日志。把 Express 的四参数错误中间件翻译成 Koa 最外层的 try/catch，确保状态码、响应体格式、日志字段与原来一致。这一步决定了迁移期间两套服务的可观测性是否对齐，也方便按接口对比行为。

第二步是按路由边界切分。新接口直接用 Koa 写，旧接口保持不动，两者共享同一套 service 与数据访问层。部署时用 Nginx 或网关按路径分流，比如 /api/v2 走 Koa，其余走 Express。这样迁移的粒度是“一个接口”，而不是“一个系统”，出问题可以按路径回切。

第三步是替换路由与中间件。express.Router 的挂载前缀对应 koa-router 的 prefix，req.params 对应 ctx.params；body-parser 换成 koa-bodyparser；cors、helmet 这类偏底层的库在 Koa 侧有对应封装，也可以直接包一层使用。替换时逐一确认中间件的执行顺序，Express 里靠注册顺序隐式表达的东西，在 Koa 里变成了显式的 await。

第四步是测试回归。接口级测试用 supertest 对两种应用都适用，重点回归错误码、Content-Type、空响应是否为 204、重定向行为，以及那些直接读写 res 的第三方中间件。这些细节最容易在迁移后悄悄变化。

反向迁移同样要想清楚。如果团队不熟悉 async 调试，或者某个关键中间件只有 Express 版本，回到 Express 的成本并不比迁出去低。迁移的收益主要来自两处：结构化的错误冒泡，以及响应后置处理；如果现有代码已经用 asyncHandler 之类的封装抹平了前者，收益会明显变小。

还有两个细节值得提前约定：Koa 中不要直接操作 ctx.res 写响应，那会绕过 Koa 的响应处理；Express 中 res.send 之后不要再写业务代码，重复写入与异常都可能被吞掉。

八、2019 年的现实建议

站在 2019 年看，Node.js 10 是当时的 LTS，Node 12 在 4 月发布、要到 10 月才转入 LTS，新项目在两者之间选都可以，Koa 2 依赖的 async/await 早已不是问题。Express 4 与 Koa 2 都是成熟稳定的选择，不存在谁将被淘汰的问题。

新项目的判断可以简化成三个问题：团队是否普遍熟悉 Promise 与 async/await；接口是否以 JSON 为主、是否需要统一的响应包装与耗时统计；是否依赖大量现成的 Express 中间件。前两个答案是“是”、第三个是“否”，选 Koa 2 会更顺手；反过来，Express 4 能让项目更快跑起来，可查的资料也更多。

老项目的建议更直接：没有明确痛点就不要迁。框架替换本身不产生业务价值，除非现有的错误处理已经严重拖累排障，或者响应组织方式反复出错。真要迁，按上一节的路径做灰度，先迁一个边缘接口，验证工具链与部署流程。

维度 Express 4 Koa 2
中间件签名 回调函数 (req, res, next) async 函数 (ctx, next)
执行模型 线性责任链，next 仅放行 洋葱模型，await 等待回程
错误捕获 同步自动，异步需 next(err) try/catch 捕获全部下游
响应方式 直接操作 res ctx.body 访问器
路由 内置 express.Router 需 koa-router
请求解析 4.16 起内置 express.json 需 koa-bodyparser
生态 数量最多，质量参差 数量较少，常用齐全
学习曲线 平缓 需理解 Promise 与洋葱
适合场景 快速交付、依赖成熟中间件 精细控制、统一响应治理

小结

Express 与 Koa 2 的差异，根源在于 next 是不是一个可以等待的 Promise。Express 用回调维持了最简单的线性模型，代价是异步错误要手动上报、响应后置处理缺少结构；Koa 2 借助 async/await 把中间件变成可进可出的洋葱，错误自然冒泡，响应可以在回程统一加工，代价是核心极简、能力要靠中间件拼装。选型时先看团队与存量，再看是否需要统一治理，性能放在最后。老项目渐进替换优于整体重写，新项目能把错误处理写清楚就是好方案。
