TypeScript 3.3 与 3.4 新特性

本文属于《TypeScript 学习路线》第 43/74 篇
上一篇系列目录下一篇

TypeScript 的版本节奏在 2019 年明显加快：3.3 于年初发布，3.4 在 3 月底跟进，3.5 已于 5 月底正式发布，3.6 尚未发布。对仍停留在 3.0/3.1 的 Node 项目来说，3.3 与 3.4 是一次成本不高、收益明确的升级。本文不逐条复述发布说明，而是围绕业务代码最常用到的几项能力展开：联合类型调用、as const、readonly 元组、globalThis、高阶类型推断与增量构建。文中的示例分别在 3.3.3 和 3.4.5 下用 tsc --noEmit --strict 验证过，读完你可以判断哪些写法可以立刻采用，哪些配置需要再等一等。

先厘清版本坐标

TypeScript 并不严格遵循语义化版本，minor 版本也可能改变类型检查行为。3.3 的主要目标是修补联合类型调用这个长期痛点，同时改善 composite 项目的监听构建；3.4 则一次性带来了 as const、readonly 元组、globalThis、高阶类型推断和 --incremental，是这两个版本中内容更密集的一个。3.5 虽然已经发布，新增内容主要是 Omit 辅助类型、更严格的联合类型多余属性检查等，本文只在必要时提及。

升级前要先固定版本。package.json 中写 "typescript": "3.4.5" 而不是 ^3.4.0，避免某次安装悄悄拉到行为不同的新版本。下面所有结论都以 3.3 与 3.4 的最终补丁版为准。

TS 3.3：联合类型可以调用了

在 3.3 之前，由多个函数类型组成的联合类型几乎不能直接调用。编译器要求所有成员的参数列表完全一致，否则就报 TS2349。这个限制在真实代码里很常见，例如一个字段既可能是“吃水果并打分”的函数，也可能是“描述颜色”的函数：

3.3 改变了规则：编译器把各成员的参数类型求交集，构造出一个对所有成员都安全的调用签名。Fruit 与 Color 的交集是 "orange"，因此只有 "orange" 可以通过检查，返回值则是 number | string：

理解“交集”是关键。联合类型表示“二者之一”，调用时必须同时满足每个成员对参数的要求，所以参数取交集；返回值取并集，调用方拿到 number | string 后仍需自行收窄。这个特性没有放松类型安全，只是把原本无法表达的合法调用放行了。

它也有明确边界：联合中最多只能有一个成员带多个重载，最多只能有一个成员带泛型签名。因此 number[] | string[] 上的 map 依然不可调用，因为 map 是泛型方法。forEach 这类非泛型方法可以调用，但在 noImplicitAny 下回调参数可能被推断为 any 并报错，显式写成 (animal: Dog | Cat) 即可。

TS 3.3 的构建侧改进与一个常见误配

3.3 还修了 composite 项目在 --build --watch 下的构建方式。在此之前，--build 模式虽然只重编受影响的子项目，但进入某个子项目后仍会整项目重建；3.3 让 --build 的监听模式复用单项目增量构建的文件监听设施，只重新检查真正受影响的文件。官方给出的实测数据是构建时间下降 50% 到 75%，对拆了多个 tsconfig.json 的后端 monorepo 很划算。

这里要区分两个容易混淆的机制：3.3 改善的是 --build --watch 下跨子项目的监听构建；3.4 的 --incremental 则是把上一次编译的项目图写入磁盘，让下一次独立的 tsc 进程也能复用。前者面向开发时的常驻监听，后者面向多次执行的命令行构建。

另一个常见误配是 --declaration 与 --allowJs 同时开启。有些新教程会建议用这对组合从 JavaScript 生成声明文件，但在 3.3 中执行会直接得到 TS5053：allowJs 不能与 declaration 同时指定。这个组合在本文写作时仍不可用，所以不要照搬；如果项目里已有 JS 文件需要类型，稳妥做法是手写 .d.ts，或者先把模块迁移到 .ts。

TS 3.4 的 as const：保留最窄的字面量类型

默认情况下，TypeScript 会对字面量做类型拓宽：对象属性 port: 3000 被推断为 number，数组 ["GET", "POST"] 被推断为 string[]。这符合“变量之后可能被重新赋值”的假设，但在配置对象和常量表里，我们恰恰希望保留字面量。3.4 引入的 as const 断言解决的正是这个问题：

限制同样要记住：as const 只能直接作用于字符串、数字、布尔、数组和对象字面量。(Math.random() < 0.5 ? 0 : 1) as const 或 (60 * 60 * 1000) as const 都会报错，必须把断言挪到每个分支的字面量上，或者先算出常量再断言。在 .tsx 文件中也不能使用尖括号形式 <const>。

readonly 元组与 readonly 数组

3.4 给数组类型加了 readonly 修饰符，readonly string[] 等价于 ReadonlyArray<string>；元组也可以加，写成 readonly [string, number]。readonly 元组只允许读取固定位置，不能写入、push 或 pop：

它与 ReadonlyArray<string | number> 的区别在于“长度和位置是否已知”。后者只保证元素可读且类型是 string | number，长度任意；前者明确只有两个元素，第一个是 string，第二个是 number，因此可以和普通元组一样解构、按下标访问，只是不能修改。赋值方向是单向的：可变元组可以传给接受 readonly 元组的参数，反过来不行。

as const 是生成 readonly 元组最常用的方式。展开一个 readonly 元组会得到新的可变数组，但元素类型退化为联合类型，长度信息也丢失：

globalThis：一份代码里的全局对象

在 globalThis 之前，跨环境访问全局对象要写一长串判断：浏览器用 window，Node 用 global，Web Worker 用 self，再配合 typeof 守卫和声明合并。3.4 开始，TypeScript 能对 ES 规范里的 globalThis 做类型检查，它指向当前环境的全局对象，代码不再需要为环境分支。

它适合同构库、环境开关和测试注入这类确实需要“全局唯一入口”的场景。业务状态仍应通过模块或依赖注入传递，不要因为有了统一的写法就把全局变量当成架构。

在 3.3 及更早版本中，makeBoxedArray 会被推断成 (arg: {}) => Box<{}[]>。原因是推断 A、B、C 时，makeArray 和 makeBox 内部的类型参数还没有着落，编译器只能先用空对象类型占位；随后调用 makeBoxedArray("hello!").value[0].toUpperCase() 就会报“{} 上不存在 toUpperCase”。

3.4 会把这些自由类型变量保留下来，并把它们提升到结果函数的类型参数列表上，于是 makeBoxedArray 的类型变成 <T>(arg: T) => Box<T[]>，调用时再推断 T，链式调用也就通过了类型检查。对 pipe、compose、map 这类工具函数来说，这意味着包装一层不再必然丢失泛型信息。

它的适用条件很具体：调用泛型函数、参数里又有泛型函数、推断结果为自由类型变量时才会触发。它不是万能的推断增强，随手写的错误注解仍然会挡住推断，跨模块的公共 API 也建议保留显式类型签名，避免把推断细节当成契约。

--incremental 与 .tsbuildinfo

3.4 新增的 --incremental 会把上一次编译的项目图保存到磁盘，下一次 tsc 只重新检查受影响的部分。默认情况下，缓存文件生成在 outDir 下，名为 tsconfig.tsbuildinfo；可以用 tsBuildInfoFile 指定位置和名字：

这个文件只服务于编译加速，删除它不会影响运行时代码，只是下次会全量构建。使用 composite 的项目总会生成 .tsbuildinfo，因为项目引用之间的增量构建依赖它；tsc --build 会读取这些文件来决定哪些子项目需要重编，因此项目引用与 --incremental 是互补关系，而不是二选一。

放到 CI 上要谨慎。缓存应当把 .tsbuildinfo 和它对应的编译产物放在一起，并以 TypeScript 版本、锁文件、tsconfig.json 作为缓存键；不要把不同分支或不同编译器版本的缓存混用，否则容易出现“本地正常、CI 增量构建漏编”的问题。缓存损坏时最省事的恢复方式永远是删掉 .tsbuildinfo 重新全量构建。

构建流程保持简单：tsc -p tsconfig.json 产出 dist，再用 node dist/server.js 启动。开发阶段常用 ts-node，它遵循同一份 tsconfig.json 做类型检查，但不会读取 .tsbuildinfo；追求启动速度时可以用 ts-node --transpile-only，把完整类型检查留给 tsc --noEmit 和 CI。

升级步骤建议固定为四步：先把版本钉死到 3.4.5（或已发布的 3.5.x）；运行 tsc --noEmit 收集所有新错误；跑单元测试与集成测试，重点关注 Readonly<T> 与高阶推断相关的类型变化；最后在预发环境观察一轮再全量。TypeScript 的 minor 升级很少改动运行时，真正需要回归的是类型契约和构建脚本。

第二，readonly 元组不能直接传给可变元组参数。把 readonly ["api", 8080] 传给 (pair: [string, number]) 会报 TS2345，提示缺少 push、pop 等方法。正确的修法是让参数接受 readonly [string, number]，或者在边界处复制并重建一个可变元组，而不是用 as any 把只读性抹掉。

第三，联合类型调用的改进不等于类型安全放松。返回值仍是各成员返回值的并集，使用前要收窄；map 这类泛型方法依旧不能在 number[] | string[] 上调用；带重载或泛型签名的联合也有成员数量限制。把它理解为“允许更聪明的调用”，而不是“任意调用都能过”。

第四，as const 不能作用于计算表达式，也不能先声明再断言一个已经拓宽的变量。类型断言必须紧贴字面量，否则你断言的只是 number 或 string，拿不到字面量类型。

小结

3.3 的价值集中在两点：联合类型调用按参数交集放行，以及 --build --watch 复用文件监听带来的构建提速。3.4 则是内容更丰富的一次更新：as const 让配置对象和常量表保留字面量，readonly 元组把“固定长度且不可写”表达得更精确，globalThis 统一了跨环境全局对象，高阶类型推断让 compose、pipe 不再丢泛型，--incremental 则把构建缓存落到了磁盘。

对日常业务代码，最值得马上用的是 as const 与 readonly 元组：它们不需要改运行时，却能让常量、action、配置的类型明显更准。升级时优先钉死版本、先跑 --noEmit，再把 --incremental 纳入 CI 缓存策略。

至于版本路线，3.5 已于 5 月底发布，提供 Omit 等辅助类型；3.6 截至本文写作时尚未发布，按官方路线图会在生成器类型检查、数组展开推断等方向继续收紧。可选链 ?. 与空值合并 ?? 目前仍是后续版本的提案，不能当作 3.4/3.5 的现有语法使用。装饰器同样属于实验特性，采用前请确认框架与编译配置。
