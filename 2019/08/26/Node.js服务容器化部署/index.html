Node.js 服务容器化部署

本文属于《TypeScript 学习路线》第 74/74 篇
上一篇系列目录下一篇

把 Node.js 服务装进容器，看起来只是写一个 Dockerfile 的事。真正做起来，问题往往出在细节上：镜像里带了开发依赖，构建一次要十几分钟；容器停了十秒才被强杀，连接池里的请求全断；本地跑得好好的，上了镜像却因为 bcrypt 编译失败起不来。

这一篇按一条可落地的路径走：从为什么容器化开始，选基础镜像，写多阶段 Dockerfile，处理依赖、用户、配置、健康检查、信号与日志，最后把构建接进 CI，并列出几个反复出现的坑。示例默认使用 Node 10 LTS，Node 12 的写法在需要时单独说明。

为什么要容器化

同一份代码在开发机、测试机和线上跑出三种结果，多数时候不是代码的问题，而是运行时环境不同：Node 小版本、系统库、全局安装的工具，甚至时区。容器把应用和它的依赖打包成一个不可变镜像，交付物从“一份代码加一份部署文档”变成“一个带标签的镜像”，扩缩容时也只是多起几个相同容器。出问题时换回旧标签即可，不必在服务器上改配置、重装依赖。调度与滚动发布属于编排层，另行处理，本文只关心单个镜像怎么做好。

Node 服务有三个特殊点。其一，依赖里有原生模块时，二进制与 libc、CPU 架构、Node ABI 绑定，换个基础镜像就可能失效。其二，node_modules 动辄几百 MB，安装策略直接决定镜像大小和构建时间。其三，Node 进程常被当作 PID 1 直接启动，信号语义与普通进程不同，退出行为要专门处理。

基础镜像怎么选

官方 node 镜像提供多个变体：完整版基于 Debian，带编译工具；slim 去掉文档和部分工具，体积小很多；alpine 基于 musl libc，压缩后只有几十 MB。2019 年这个时间点，生产上稳妥的选择是 node:10-slim：Node 10 处于 LTS 维护期，Debian 的 glibc 与绝大多数预编译原生模块兼容。Node 12 在 2019 年 4 月发布，按官方计划要到 10 月才转入 LTS，此刻可以用它做验证，不建议直接把核心服务切过去。

slim 镜像基于 Debian，连 curl 和 git 都没有。这不是缺陷，而是在提醒我们：Dockerfile 里不能假设系统装了什么，需要什么就在构建阶段显式安装，探活则尽量用 Node 自带的 http 模块。

alpine 的吸引力是体积，代价是 musl。bcrypt、sharp 这类带预编译二进制的包，发布方通常只提供 glibc 版本，在 alpine 上要么回退到源码编译，要么直接报错；编译又需要 python、make、g++，装完体积优势所剩不多。若确实要用 alpine，构建阶段和运行阶段必须使用同一个 alpine 基础镜像，避免 ABI 不一致。

镜像标签不要只写 node:10。至少固定到 node:10-slim 这类明确变体，重要服务可以固定小版本，升级基础镜像当作一次需要回归的变更。

多阶段 Dockerfile

多阶段构建从 Docker 17.05 起可用，在 18.09/19.03 上已是常规做法。思路是把“编译需要的东西”和“运行需要的东西”分开：builder 阶段装全部依赖、编译 TypeScript；runtime 阶段只拿 dist 和裁剪后的生产依赖，编译器、源码、测试文件都不进最终镜像。

最终镜像只包含运行所需：Debian 基础层、生产依赖、dist。以一个中等规模的服务为例，builder 阶段接近 1 GB，最终镜像通常能压到 200 MB 上下，具体取决于原生模块和依赖数量。builder 阶段不会被推送到镜像仓库，它只在本机构建时存在。

几个细节值得说明。builder 里安装 python、make、g++ 只为编译原生模块，apt 索引在同一层删掉，不会留在镜像里。npm prune –production 在构建阶段完成裁剪，运行阶段不再执行安装，启动更快，也不会因为网络问题失败。COPY –chown 在复制时设定属主，比复制完再 chown 少一层，也不会让 node_modules 多出一份副本。CMD 用 exec 形式，node 直接成为主进程，信号不会被 shell 吞掉。

依赖安装与缓存分层

npm ci 与 npm install 的区别在于：前者严格按 package-lock.json 安装，lockfile 与 package.json 不一致时直接失败；后者可能顺手改写 lockfile。npm ci 还会先删掉现有的 node_modules，所以它适合干净环境，不适合拿来增量更新本地开发目录。CI 和镜像构建里应当只用 npm ci，保证每次构建的依赖树一致。lockfile 本身要提交到仓库，并在代码评审里当作正式文件对待，升级依赖产生的 diff 才可追溯。

分层缓存的关键是顺序：先 COPY 两个清单文件，再 RUN npm ci，最后才 COPY 源码。只要清单没变，Docker 会复用依赖层，改一行业务代码不会触发重新安装。反过来，如果一开始就 COPY 全部文件，任何改动都会让缓存失效。

运行阶段只需要生产依赖，可以在 builder 里用 npm ci –only=production 单独装一份，也可以像上面的例子那样先装全量再裁剪。构建机上可以挂载 npm 缓存目录减少重复下载，但缓存不要 COPY 进镜像。私有源通过 .npmrc 配置 registry，凭据用构建参数或挂载的 secret 传入，不要写进 Dockerfile，也不要把 .npmrc 提交到仓库——镜像层里删掉文件，并不会删掉历史层中的内容。

非 root 用户

官方 node 镜像自带 uid 1000 的 node 用户，直接用即可；如果基础镜像没有，就用 groupadd 和 useradd 建一个系统用户。创建用户和拷贝文件的先后顺序要注意，配合 –chown 使用，否则先 COPY 再 chown 会多出一层几百 MB 的 node_modules 副本。

USER node 之后，进程在容器内没有 root 权限。docker run 时可以用 –user 临时覆盖，但镜像里的 USER 才是默认保障。这不是形式主义：容器默认的 capability 集合虽然比宿主机少，但 root 仍能改文件、绑低端口、读挂载进来的敏感目录；应用一旦被攻破，攻击者拿到的起点就是容器 root。非 root 运行把可利用面缩小到普通用户，配合只读根文件系统效果更好。

需要写文件的目录（上传、临时文件）提前 chown 给 node，或者挂载可写卷；其余代码目录保持只读。批量 chown 会把整个目录重写一遍，在大项目上耗时明显，所以更推荐在 COPY 时就带上属主。日志不要写文件，后面会讲。

.dockerignore

镜像构建时，Docker 会把上下文目录整个发给 daemon。没有 .dockerignore 时，node_modules、.git、测试报告、本地 .env 都会进入上下文，构建变慢，缓存也更容易失效。在 CI 上这一点更明显，因为上下文还要经过网络上传。更危险的是 .env、.npmrc、证书私钥这类文件，一旦被 COPY 全部文件带进镜像，就等于把凭据发布了。

配置、健康检查与启动校验

12-Factor 的第三条是把配置存在环境里。镜像应当在任何环境都能启动，差异通过环境变量注入：数据库地址、密钥、外部服务端点都不进镜像。构建时烘焙配置的后果是，同一个镜像无法在预发和生产复用，改一个地址就要重新构建，也容易把生产密钥留在测试镜像里。把配置外置之后，改配置只需要重启容器，不必重新构建镜像。

启动时先校验必填变量，缺一个就退出并打印缺了哪些键，这比运行到第一个请求才报错要好定位。.env 只用于本地开发，由 dotenv 读取；容器里不要放 .env，环境变量由部署系统注入。

健康检查要分两层看。进程活着不等于服务可用：事件循环被堵死、连接池耗尽时，进程还在，请求已经超时。HEALTHCHECK 让 Docker 定期执行命令，连续失败后容器状态变为 unhealthy。start-period 给应用留出启动时间，避免刚启动就被判失败。slim 镜像里没有 curl，用 node 自己发请求最省事。健康端点只做轻量检查，返回体保持很小，不要把连接串或内部拓扑写进去；依赖故障更适合交给就绪探针。就绪决定是否接流量，存活决定是否重启，这两件事在编排层配置，本文不展开。

信号与优雅退出

docker stop 先给 PID 1 发 SIGTERM，等待 10 秒（默认）再 SIGKILL。问题在于，Linux 对 PID 1 有特殊照顾：没有安装处理函数的信号，默认动作会被忽略。Node 默认不处理 SIGTERM，于是容器里的 node 作为 PID 1 时会“无视”停止信号，10 秒后被强杀，正在处理的请求直接断掉。

两个办法可以一起用。一是在代码里显式监听 SIGTERM 和 SIGINT，调用 server.close 停止接收新连接，等在途请求结束后再退出；同时设一个短于 10 秒的兜底定时器，超时就退出。二是启动容器时加 –init，让 tini 作为 PID 1 转发信号并回收僵尸进程；也可以把 tini 装进镜像作为 entrypoint。

server.close 只停止监听，不会主动断开 keep-alive 的空闲连接，这些连接会让回调迟迟不触发，所以兜底定时器不能省。若前面有反向代理，先把实例从上游摘掉，再发停止信号，顺序反了仍会有请求打到正在关闭的进程。如果进程用 cluster 起了多个 worker，主进程要把信号转发下去，否则 worker 收不到停止通知；容器里通常一个容器一个进程，是否用 cluster 要结合 CPU 限制评估。错误处理本身在《Node 异步错误处理》里讨论过，这里只关心进程如何体面地结束。

日志

容器里的日志应当写到 stdout 和 stderr，由运行时收集，而不是写进容器内的文件。写文件的问题很实际：容器删除后文件就没了，多副本时要去每台机器上捞，磁盘写满还会连带服务挂掉。

结构化日志便于检索：一行一个 JSON，至少包含时间、级别、消息、请求标识。请求标识要能从入口透传到下游，排查时才能把一次调用的日志串起来。pino 这类以 JSON 为默认输出的库，比自己拼字符串更省事。时间统一用 ISO 8601 的 UTC，容器默认时区就是 UTC；如果业务必须用本地时区，在镜像里装 tzdata 并设置 TZ，但日志时间仍建议保留 UTC，展示层再转换。曾见过容器时区是 UTC、数据库是东八区，排查时对时间对到怀疑人生。info 级别不要打印请求体和密钥，访问日志里的 Authorization 头要脱敏。

镜像体积、安全与 CI

体积控制的常用手段：选 slim 基础镜像、多阶段构建、装完删 apt 索引和 npm 缓存、运行阶段不放编译工具。层数本身不是越少越快，真正占空间的是每层新增的文件；把 apt update 和 install 写在同一个 RUN 里，后面的删除才有效。

安全上，基础镜像要定期更新，Node 10 的小版本会修安全问题；镜像扫描按类别做：操作系统包漏洞、语言依赖漏洞、镜像里的密钥与敏感文件。扫描放进 CI，发现高危就阻断发布。扫描结果要能对应到具体层，修复时才知道是换基础镜像还是升依赖。还要记住，镜像层是叠加的，docker history 能看到每一层的内容，后面一层删掉密钥文件，前一层里依然躺着明文。

CI 里最小验证是：构建成功，起容器，请求健康端点返回 200，再停掉容器确认退出正常。本地验证不需要完整流水线，用 docker build 构建、docker run 起容器，确认健康端点可用即可。标签建议用语义化版本加 git 短哈希，例如 registry.example.com/order-api:1.4.0-a1b2c3d，生产只用不可变标签，latest 只留给本地。

常见坑

  • COPY 全部文件放在 npm ci 之前，改任何文件都重装依赖，构建从一分钟变成十分钟。
  • 用 npm install 代替 npm ci，lockfile 被悄悄改写，不同次构建装出不同版本。
  • 在 alpine 上装 bcrypt，没有预编译包又没有编译工具，node-gyp 直接失败；要么换 slim，要么在 builder 装工具并保证运行阶段同一 libc。
  • 容器时区是 UTC，业务代码按本地时间格式化，日志和数据库差 8 小时。
  • SIGTERM 没有处理函数，docker stop 等满 10 秒后 SIGKILL，滚动发布时每次都丢一批请求。
  • 把 EXPOSE 当成端口发布，实际上它只是声明，映射仍要靠 docker run -p。

小结

容器化的价值不在 Dockerfile 本身，而在于把运行环境变成可版本化、可复现的交付物。镜像不是构建一次就一劳永逸，它和代码一样需要维护。实践顺序可以是：先用 node:10-slim 加多阶段构建把镜像跑起来，再补 .dockerignore、非 root 用户和健康检查，最后处理信号、日志与 CI。每一步都不复杂，但漏掉任何一步，问题都会在流量上来或发布时暴露。等 Node 12 转入 LTS，可以安排一次基础镜像升级，把回归用例跑一遍再切换。
