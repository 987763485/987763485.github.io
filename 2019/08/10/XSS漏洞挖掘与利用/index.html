XSS 漏洞挖掘与利用

本文从一次搜索框回显的排查过程出发，梳理 XSS 的成因、三类触发路径与不同 HTML 上下文下的编码差异，再给出授权测试中的检测流程、CSP 等纵深防御手段和修复闭环。文中的验证仅用于证明问题存在，不涉及数据窃取或持久化控制。本文适合已经能写页面与接口、希望把安全问题定位到具体代码行的开发者阅读。

一、XSS 的本质：数据被放进了代码的位置

浏览器加载页面时，先把 HTML 解析成 DOM，再按顺序执行脚本。HTML 本身没有“数据区”和“代码区”的严格分界：一段文本只要落在标签开始、属性值或脚本块的位置，就会被解析器当成结构或代码。XSS 的根本原因，是应用把不可信数据拼进了这些位置，却没有按位置做编码。

同源策略要求协议、域名和端口一致，限制的是不同源之间的读取：a.example.com 的脚本不能随意读取 b.example.com 的响应。但它不限制本页脚本做什么。一旦攻击者的脚本在目标页面的源下执行，它就能读取当前 DOM、以当前用户身份发起同源请求、调用页面暴露的接口。同源策略保护的是“别的源”，XSS 却发生在本源内部。

因此判断回显是否危险，不能只看有没有弹窗，而要看数据最终进入了哪种解析上下文：同一段字符串放在 <div> 之间是文本，放进 <script> 就可能成为代码。

二、三类 XSS 的触发路径

按数据路径可分为反射型、存储型和 DOM 型，差别不在 payload，而在“谁把数据放进了输出”。

反射型 XSS 的数据来自当前请求，经服务端模板回显后立即返回。常见入口是搜索结果页的 q 参数、错误提示、跳转参数。它不落库，需要诱导受害者点击构造链接，多了一次交互。检测时关注参数是否原样出现在响应中。

存储型 XSS 的数据先写入数据库或缓存，之后每次读取都触发。评论区、昵称、简介、工单、后台日志都是高发点。影响面通常最大，一条留言可能影响所有访问者，包括管理员。检测需要“提交、再次访问、换账号访问”三步确认。

DOM 型 XSS 可能完全没有服务端参与。前端脚本从 location.hash、location.search、document.referrer 或 postMessage 中取出数据，再写入 innerHTML、document.write 或 eval 一类接收点。payload 不经过服务端，“查看网页源代码”往往看不到，必须在开发者工具的 Elements 面板观察运行时 DOM。

可以用一张表对比三者的检测重点：

类型 数据路径 常见入口 检测重点
反射型 请求到服务端回显 搜索、错误页、跳转参数 响应中的编码情况
存储型 提交、落库、再次输出 评论、昵称、工单、日志 二次访问与跨角色
DOM 型 浏览器 API 到前端拼接 hash、search、referrer 运行时 DOM 与接收点

三、上下文决定编码方式

同样输入 <，在不同位置后果不同，因为解析器在不同状态下的规则不同。编码前先要认清输出点属于哪种上下文。以下示例只说明闭合关系，脚本均为 alert(1) 级别的无害验证。

标签之间是最常见的位置，例如 <div>这里是输入</div>。此时 < 会开启新标签，输入 <img src=x onerror=alert(1)> 会被解析成一个带事件属性的图片。正确做法是把 &、<、>、"、' 转成 HTML 实体。

属性值内部需要区分是否加引号。<input value="输入"> 中，双引号必须被编码，否则输入 " onmouseover="alert(1) 可以闭合属性并新增事件。若属性未加引号，空格、>、= 都可能截断属性值，风险更高。属性编码要覆盖引号与空白。

URL 属性有自己的协议层。<a href="输入"> 中，即使引号被正确编码，javascript:alert(1) 仍然是可执行链接。这里需要的是协议白名单：只允许 http、https、相对路径，拒绝 javascript:、data: 等协议前缀。

脚本块内是 HTML 实体失效的地方。<script>var q = "输入";</script> 中，浏览器不会把 &lt; 还原成 <，需要的是 JavaScript 字符串转义，例如把引号、反斜杠、换行和 < 处理成 \x22、\x5c、\x0a、\x3c。还要防止 </script> 提前闭合，因此 < 必须转义。

CSS 上下文同样存在拼接风险，style="输入" 或 <style> 块内的值需要 CSS 转义，并对 url()、expression 一类危险结构做限制。现代浏览器已不支持 expression，旧页面仍需考虑。

这说明不存在一种通用过滤函数能适配所有位置，正确顺序是先确定输出位置，再选择编码器。

四、检测方法：从输入点到输出点

授权测试的核心是建立“输入点—输出点”的映射，而不是盲目提交 payload。

第一步是梳理输入点。除表单和查询参数外，还要看路径段、JSON 字段、请求头（Referer、User-Agent 常被写入日志并在后台展示）、文件元数据、postMessage。记录参数名、类型与是否需要登录。

第二步是定位输出点。提交唯一标记串，例如 xss7f3a，在响应 HTML、DOM 树和页面脚本中搜索。它出现在 HTML、属性还是脚本变量里，决定后续测试方向。Elements 面板显示解析后的 DOM，Network 面板显示原始响应，两者要对照。

第三步是探测编码行为。先提交 <、>、"、'、&、/ 这几个字符，观察它们在响应中是否变成实体、被删除或转成别的形式。若被实体化，说明该位置有编码；若原样保留，再判断它落在什么上下文里。不要一上来就提交完整 payload。

第四步是验证。确认上下文后，才用最小化无害 payload 验证：标签间用 <img src=x onerror=alert(1)>，属性内用带引号闭合，脚本内用 ";alert(1);//。目标是证明数据被当作代码执行，不是造成影响。弹窗出现后立即停止，不进一步读取数据。

对于存储型，还需要盲测思路：提交后到列表页、详情页、管理后台、导出文件和邮件通知中查看。若环境不具备这些入口，应在报告中说明未覆盖。

过程要保留请求响应、时间、账号、浏览器版本和截图，作为复现依据与证据链。

五、编码与转义的分层

编码不是“把危险字符删掉”，而是“让数据在目标上下文里保持数据身份”。

HTML 实体编码用于标签间和属性值，把 &、<、>、"、' 转为 &amp;、&lt;、&gt;、&quot;、&#x27;。要先处理 &，否则会二次转义已有实体。

属性编码还要关注未加引号的属性。更稳妥的做法是统一加引号，再对引号编码。

JavaScript 编码用于脚本块和事件属性。除字符串转义外，还要避免把 JSON 直接拼进脚本。可把数据放在 <script type="application/json"> 中，读取后 JSON.parse，并对 < 转义，防止提前闭合。

URL 编码用于查询参数和路径段，浏览器端用 encodeURIComponent，服务端用对应函数。它不编码 '、(、)，若结果还要进入 HTML 属性，仍需再编码一次。

服务端模板引擎通常提供默认转义，但默认值因引擎而异。Django 的 {{ value }} 默认转义，|safe 会关闭；Jinja2 开启 autoescape 时类似；Go 的 html/template 按上下文选择；Thymeleaf 的 th:text 转义而 th:utext 不转义；EJS 的 <%= %> 转义而 <%- %> 不转义。使用前应查清所用引擎的默认行为。

要强调“按输出编码”而非“在输入处统一过滤”。同一条昵称可能同时出现在 HTML、JSON、邮件和日志里，每个位置需要不同编码。输入处能做长度、字符集和格式校验，但不能替代输出编码。

六、CSP：收窄爆炸半径

内容安全策略（Content-Security-Policy，CSP）通过响应头告诉浏览器：本页允许加载哪些来源的脚本、样式和图片。它不修复 XSS，只在编码疏漏时限制脚本能力。

最基本的配置是限制脚本来源：

script-src 'self' 禁止内联与未知来源脚本，能挡掉部分注入。代价是原有的内联脚本和 onclick 会失效，需迁移到外部文件或事件监听。

必须保留内联脚本时，可以使用 nonce：服务端每次响应生成随机值，同时写入响应头和 script 标签的 nonce 属性。nonce 不能写死在静态页面里，否则失去意义。

strict-dynamic 是 CSP 3 的机制，它让带 nonce 或 hash 的受信脚本动态插入的脚本也被信任，从而减少对域名白名单的依赖。2019 年浏览器支持并不一致：Chrome 与 Firefox 较新版本可用，Safari 滞后，旧浏览器会忽略。因此它适合渐进增强，应保留 'self' 等回退来源。

报告模式只记录不拦截，可收集被阻止的资源，避免一刀切故障，观察后再切换为强制模式。

CSP 不能修复服务端拼接 HTML 的问题，只能降低执行成功率；过宽的 CDN 域名或 JSONP 端点仍可能被利用。它是纵深防御，不是替代品。

七、HttpOnly 与 Cookie 的边界

不少早期资料把 HttpOnly 当成“防 XSS 手段”，这不准确。HttpOnly 让 document.cookie 读不到该 Cookie，降低会话标识被脚本直接读走的风险。它阻止不了 XSS，因为脚本仍在页面执行，仍可读取 DOM、以用户身份发起请求、执行页面操作。

会话 Cookie 应同时设置 HttpOnly、Secure 和 SameSite：

SameSite=Lax 限制跨站请求携带 Cookie，能降低 CSRF 和部分跨站场景下的影响；Strict 更严格，但会影响从外部链接进入时的登录态。2019 年并非所有浏览器都默认 Lax，服务端应显式声明，不能依赖默认值。高敏感操作还应叠加 CSRF Token、二次确认与操作审计，它们与输出编码并列，不能互相替代。

八、框架与 DOM 的默认安全

前端框架默认转义文本插值：React 把子节点当文本，Vue 的 {{ }} 也做转义，风险集中在逃生舱上。React 的 dangerouslySetInnerHTML 会直接把字符串写入 DOM，使用前必须先做白名单净化。

Vue 的 v-html 同理，也不应作用于用户输入。原生接口中，innerHTML、outerHTML、insertAdjacentHTML、document.write 都不转义，应优先使用 textContent 或框架的文本插值。

富文本是例外，需保留部分标签时应采用白名单，只允许固定标签和属性，禁止 on* 事件属性和 javascript: 协议，并在服务端再净化一次，因为客户端净化可以被绕过。框架的转义只覆盖文本节点，把输入拼进 href、src 时协议检查仍需单独做。

九、修复闭环：从一行代码到一条规则

修复的第一步是分清职责：输入校验管“值是否符合业务格式”，输出编码管“值在当前上下文是否安全”。前者不能替代后者，后者也不承担业务规则。

建议提供统一编码组件，把 HTML、属性、JavaScript、URL 四种编码封装成函数，模板层只调用组件，不允许业务代码手写拼接。代码审查设置可执行规则：搜索 innerHTML、dangerouslySetInnerHTML、v-html、document.write、eval，搜索模板中的 |safe、th:utext、<%-，检查所有 href 是否经过协议白名单。

回归测试要断言输出结果，而不只是页面能打开：

除了单元测试，还应有端到端用例：提交一条含标记的评论，断言页面上以文本形式显示，且 DOM 中不存在对应的图片元素。修复提交应同时带上回归用例，防止后续重构把编码去掉。

十、报告与复测

报告应包含类型与等级、受影响的 URL 与参数、复现步骤、无害 payload、实际与预期结果、影响面、修复建议和截图。等级要结合是否需要登录与诱导交互、影响用户数量、能否触达管理后台，以及 HttpOnly、CSP 等缓解措施判断。

复现步骤要让另一位工程师能独立完成：账号、入口、参数与观察面板。payload 保持 alert(1) 级别，不写入真实数据。修复建议要落到具体文件与行号，并给出验证方法。复测按清单确认：原始与编码变体是否失效、同一参数在其他页面是否修复、回归用例是否通过、CSP 报告是否仍有异常。

十一、合规提醒

以上方法仅适用于获得书面授权的资产。在等级保护或日常安全测试中，测试前应明确域名、时间窗、测试账号与禁止动作，不触碰第三方组件和共享设施。发现漏洞后应通过约定渠道提交给责任方，说明影响与修复建议，不公开披露、不传播细节、不下载真实数据。修复后复测并关闭，把问题补充进审查规则与回归用例。

小结

XSS 的本质是数据进入了代码的位置，同源策略不能提供页面内部的保护。三类 XSS 的差别在数据路径，检测分别关注响应、落库回显和运行时 DOM。编码要跟随上下文，CSP、HttpOnly、SameSite 都是纵深防御，不能替代输出编码。修复要落到统一组件、审查规则和回归测试，验证始终限定在授权范围内。
