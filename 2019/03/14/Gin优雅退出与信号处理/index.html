Gin 优雅退出与信号处理

本文属于《Go 语言与工程》第 63/78 篇
上一篇系列目录下一篇

服务进程如何结束，和它如何启动一样重要。本文从进程信号讲起，说明 Gin 应用怎样借助 http.Server.Shutdown，在收到 SIGTERM 后停止接收新请求、等待在途请求处理完毕，再按正确顺序释放后台任务、消息消费者与数据库连接。文中还会讨论长连接、健康检查与 Kubernetes 终止流程这些容易被忽略的细节，适合已经把 Gin 服务跑起来、准备上线，或者正在排查“发布时偶发 502”的读者。

为什么需要优雅退出

在本地开发时，结束一个服务的方式通常是 Ctrl+C，或者干脆关掉终端窗口。进程消失，端口释放，下一次 go run 照常启动，看不出任何问题。但生产环境里，进程的消失从来不是它一个人的事：它可能正持有几十个数据库事务、几百条 TCP 连接、一个还没 flush 的日志缓冲区，以及若干条已经从消息队列取出、尚未确认的消息。

Go 程序如果没有注册信号处理函数，SIGTERM 会走操作系统的默认动作，进程立刻终止，正在执行的 goroutine 被丢在半路，连 defer 都不会执行。这种“硬停”带来的后果往往不会在监控大盘上立刻显形，而是以零散的错误日志和用户投诉的形式出现：

  • 客户端正在等待的请求被 RST 掉，表现为 connection reset by peer，经过网关后变成 502 或 504；
  • 一个涉及多张表的业务操作只写了一半，比如库存扣了、订单没落库，事后需要人工对账；
  • 使用带缓冲的日志库时，最后几十毫秒的日志留在内存里，偏偏这段时间的日志对排查问题最有价值；
  • 消息已经消费但还没 ack，进程退出后 broker 重新投递，业务侧出现重复处理；
  • 连接池里的连接没有机会发送 quit，MySQL 侧留下一批 sleep 状态的连接，直到 wait_timeout 才被清掉。

触发这些场景的操作，比很多人想象的频繁：滚动发布要逐个替换实例，弹性缩容要下线机器，集群缩容与节点驱逐会把 Pod 赶走，systemctl restart 和 docker stop 也都会发信号。可以说，只要服务会被部署，就一定会被终止，区别只在于终止时体不体面。

所以优雅退出的定义可以概括为三个动作：停止接入新的工作，把已经在做的工作做完或者推进到一个安全的边界，然后有秩序地释放资源并以正常退出码结束。下面几节分别解决这三个动作在 Gin 服务里怎么落地。

信号基础：SIGTERM、SIGINT 与 SIGHUP

信号是 Unix 提供的异步通知机制。内核把一个整数发给进程，进程可以选择忽略它、捕获它，或者接受默认动作。终止类信号的默认动作基本都是让进程退出，但退出方式并不相同，理解这一点是写好退出逻辑的前提。

SIGTERM 的编号是 15，语义是“请终止”。它可被捕获，是体面退出的标准信号：kill 命令默认发它，docker stop 先发它，Kubernetes 终止 Pod 时发的也是它，systemd 停止服务同样如此。收到 SIGTERM 之后做什么，完全由程序自己决定，这正是优雅退出的入口。

SIGINT 的编号是 2，来自终端的 Ctrl+C，语义是“中断”。它在交互场景里表示用户想停下当前程序，在容器里也常被用作停止信号。Go 标准库把它导出为 os.Interrupt，写代码时用这个名字比记数字更清楚。

SIGHUP 的编号是 1，历史上表示终端挂断。很多守护进程借用它做“重新加载配置”，但这只是程序之间的约定，并不是内核赋予的含义。如果一个程序没有捕获 SIGHUP，默认动作仍然是终止进程。所以看到运维用 kill -HUP 让某个服务重载配置时，不要想当然地认为自己的服务也会这样，除非你显式注册了处理逻辑。

还有两个信号需要单独说明：SIGKILL（9）和 SIGSTOP 既不能被捕获，也不能被忽略。它们是内核层面的最后手段，kill -9 发出去，进程没有任何反应的机会。这意味着优雅退出的前提是对方向你发了 SIGTERM；如果发布脚本图省事直接 kill -9，代码写得再周全也没用。

容量为 1 够不够？同一时刻连发两个信号，channel 里只会留下一个。对退出流程来说这通常无所谓：第一个信号启动退出，第二个信号的含义是“别等了，马上退”。不少服务会利用这一点做两段式退出，第一次走优雅流程，第二次直接 os.Exit。

signal.Stop 与第二次信号

signal.Stop 用于取消注册，调用之后该信号恢复系统默认动作。它有两个实际用途。

第一个用途正是上面提到的两段式退出。程序进入优雅退出后，如果排空过程卡住，运维会再发一次 SIGTERM。此时若仍然只做“记录日志”，进程就会一直挂着。比较稳妥的写法是：第一次收到信号后调用 signal.Stop(sigCh)，这样第二个 SIGTERM 会走默认动作直接杀死进程，不需要在业务代码里再判断计数。

第二个用途是避免污染。信号注册是进程级的状态，一旦注册就全局生效。如果某段代码只是临时想观察信号，比如测试用例或者被多次调用的初始化函数，用完必须 signal.Stop 并在必要时 close channel，否则注册会一直累积，行为变得难以预测。写公共库时尤其要注意：库不应该长期霸占进程的信号，那是应用层的职责。

Shutdown 到底做了什么

http.Server.Shutdown 从 Go 1.8 起进入标准库，它的行为可以拆成四步：关闭所有监听器，使 ListenAndServe 与 Serve 立刻返回 http.ErrServerClosed；关闭处于空闲状态的 keep-alive 连接；等待活跃连接处理完毕转为空闲；如果传入的 context 到期，则返回 ctx.Err()。

这里要抠一个措辞：超时之后，Shutdown 只是“返回”，并不会强制关闭仍在处理中的连接。如果希望立刻断开，需要在它返回错误后再调用一次 Close()。不少“明明设了超时，进程还是卡住”的困惑，都来自误以为超时会顺手把连接杀掉。

Shutdown 与 Close 的区别也在这里。Close 立即关闭监听器和所有连接，在途请求当场中断，效果接近直接 kill；Shutdown 则是先礼后兵，一边拒绝新连接，一边给在途请求留出完成的时间。两者都只作用于 HTTP 层，不会替你关闭数据库、Redis 或消息消费者，这部分要自己编排。

在途请求与长连接

Shutdown 等待的是“活跃连接变为空闲”，这个设计默认普通 HTTP 请求总会有结束的时候。但有三类连接不会自然结束：WebSocket、SSE（服务端推送），以及耗时很长的大文件下载。它们会让 Shutdown 一直等到 context 超时，把优雅退出拖成一次超时退出。

比这更麻烦的是被劫持的连接。WebSocket 完成协议升级后，底层连接被应用接管，net/http 不再跟踪它。标准库文档明确写着：Shutdown 既不关闭也不等待被劫持的连接。于是进程可能在某条 WebSocket 正在写数据时退出，客户端看到的就是连接被重置。

这部分只能由业务层配合，思路有三条。第一，维护一份长连接注册表，收到信号后先遍历通知，WebSocket 发关闭帧、SSE 推送一个结束事件，让客户端知道这是正常下线而不是网络故障。第二，给长连接设置独立的、更短的宽限期，超过就主动关闭，不要指望它们自己结束。第三，对下载类接口，在 handler 的循环里周期性检查退出标志，能提前返回就提前返回。

顺序上建议先处理长连接，再调用 Shutdown，否则 Shutdown 会被这些永不空闲的连接拖住。框架无法代劳这件事，因为“何时可以安全中断”只有业务自己知道。

资源关闭的顺序

HTTP 停止只是第一环。一个完整的退出顺序通常是：HTTP 停止接收新请求，后台 worker 停止，消息消费者停止，数据库与 Redis 关闭，最后 flush 日志。总原则是“先停止产生新工作，再停止处理工作，最后释放处理工作所需的依赖”。

顺序反了会很难查。先关数据库，worker 还在跑，日志里会刷出一片 sql: database is closed；先关日志，后面所有关闭失败的错误都看不见；先停消费者再停 worker，worker 可能还在往队列里投递，投出去的消息没人消费。

sync.WaitGroup 足以编排大部分场景：后台任务收到停止信号后自行返回，主流程 Wait 到它们真正退出，再去关依赖。

golang.org/x/sync/errgroup 也可以，g.Wait() 会返回第一个错误，适合并行关闭几个互不依赖的资源。但它不替你决定顺序，有依赖的步骤仍要串行。另外每个关闭动作都该有超时，否则某个依赖不响应，进程就卡在最后一步。

健康检查与 Kubernetes

只做 Shutdown 还不够。信号到达的瞬间，负载均衡可能仍在往这个实例转发请求，这些请求会直接被拒。正确的顺序是：收到 SIGTERM 后先把 readiness 置为失败，等负载均衡把实例摘掉，再调用 Shutdown。

到了 Kubernetes 这边，terminationGracePeriodSeconds 默认 30 秒，它从 preStop 开始执行时计时，覆盖 preStop 和主进程退出的全部时间。如果 preStop 睡了 10 秒，Shutdown 超时又设了 20 秒，再加上关资源的时间，就已经超了，kubelet 会补一发 SIGKILL，前面的努力全部作废。所以三个数字要一起算：preStop 等待加 Shutdown 超时加资源关闭时间，必须小于宽限期。

常见坑

  • Shutdown 传入 context.Background()：没有截止时间，等于无限等待，一个卡住的请求就能让进程一直不退，最后挨 SIGKILL。
  • 忘记处理 http.ErrServerClosed：日志误报监听失败，甚至提前 log.Fatal。
  • 信号 channel 没有缓冲：运行时非阻塞发送，信号可能被直接丢掉。
  • 在 goroutine 里调用 os.Exit：跳过全部 defer，连接没关、日志没 flush，等于没做优雅退出。
  • 超时时间比负载均衡摘除时间还短：Shutdown 开始时新流量仍在进入，排空无从谈起。
  • 只停了 HTTP，忘了定时任务和消息消费者：进程退出时位点没提交，消息被重复投递。

小结

优雅退出的本质是给进程一个“收尾”的阶段，而不是让它瞬间消失。实现上分三层：用 signal.Notify 加缓冲 channel 接住 SIGTERM 与 SIGINT；用带超时的 context 调用 http.Server.Shutdown，并正确处理 http.ErrServerClosed；在 HTTP 停止之后按依赖顺序关闭 worker、消费者、数据库与日志。长连接、readiness 摘除和 Kubernetes 宽限期这三处最容易出问题，需要业务代码与部署配置一起配合。最后提醒一句：所有超时值都应从“最长请求耗时”和“探针与摘除的实际时间”推算，照抄别人的数字往往就是事故的开始。
