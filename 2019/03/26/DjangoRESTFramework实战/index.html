Django REST Framework 实战

本文属于《Python 学习路线》第 22/29 篇
上一篇系列目录下一篇

用 Django 做后端，很快会遇到一个岔路口：继续用模板渲染页面，还是把数据以 JSON 的形式交给前端与移动端。前者是 Django 的传统强项，后者则需要一套约定来处理序列化、校验、分页与权限。Django REST Framework（下称 DRF）正是在这个位置上成长起来的框架。本文不罗列全部 API，而是沿着一个商品接口从无到有的过程，把 DRF 3.9 的主要构件串起来，适合已经会写 Django 视图、准备交付第一个 REST 接口的读者。

从一个商品 API 说起

DRF 的定位与组成

假设我们要做一个商品目录服务，需求很朴素：分类下列出商品，支持分页、按分类筛选、按价格排序；读接口允许匿名访问，写接口要求登录，删除只允许管理员。这些功能用 Django 原生视图都能实现，但每一项都要手写：解析 JSON、限制可写字段、统一错误格式、读取分页参数、逐条判断权限。重复三五个接口之后，代码里会堆满相似的胶水。

DRF 的价值不是让 Django 支持 REST，Django 本身就能返回 JSON，它的价值在于把这些横切关注点抽成可组合的类。核心构件可以按一次请求经过的顺序来记：Serializer 负责模型与 JSON 之间的转换和校验；View 与 ViewSet 负责组织业务流程；Router 把 ViewSet 映射成一组 URL；认证回答“你是谁”，权限回答“你能不能做”；分页、过滤、排序则在查询集交给序列化器之前裁剪数据。把这六件事分开看，DRF 的继承体系就不再显得庞杂。

DRF 不是 ORM 的替代品，序列化器也不是另一个 Model。它默认建立在 Django 的 QuerySet 之上，写得不好同样会产生大量 SQL。后文讨论 N+1 时会看到，序列化器也会放大数据库问题。

一次请求的处理链路

先看整体链路。下面这张图省略了内容协商与渲染的细节，只保留主干：

flowchart TD
    A[HTTP 请求] --> B[URL 路由与 Router]
    B --> C[ViewSet 初始化]
    C --> D[认证 Authentication]
    D --> E[权限 Permission]
    E --> F[限流 Throttle]
    F --> G[解析请求体 Parser]
    G --> H[查询集与过滤分页]
    H --> I[Serializer 校验]
    I --> J[业务逻辑与 ORM]
    J --> K[Serializer 序列化]
    K --> L[渲染 JSON 响应]

顺序值得记住：认证先于权限，权限先于业务；过滤与分页发生在 get_queryset 之后、序列化之前。理解了这个顺序，就能判断一段逻辑该放在哪里。“只能看到自己的商品”是查询集层面的约束，写在 get_queryset 里最稳妥；“已下架商品不能修改”是对象级权限；“价格必须大于 0”则属于序列化器校验。放到错误的位置，代码也许能跑，但会在列表接口或批量操作时露出破绽。

Serializer：模型与 JSON 之间的翻译层

序列化器同时承担两个方向的转换：入口把请求数据校验并落成模型实例，出口把模型实例展开成可渲染的字典。声明字段就是在定义对外契约，显式列出 fields 比用 __all__ 安全，新增的数据库字段不会被无意暴露。

读写属性要分清。read_only=True 的字段只出现在响应里，write_only=True 的字段只接受输入；required=False 允许省略，但它与默认值、partial=True 是两回事。source 用于把对外字段名映射到模型属性，示例中的 category_id 让客户端提交主键，序列化器内部仍操作 category 对象。嵌套序列化器默认只读，想连同关联对象一起写入，需要自己实现 create 与 update，或者用 PrimaryKeyRelatedField 接收主键。

SerializerMethodField 适合拼装展示字段，值来自 get_<field_name> 方法。它只读，也不能参与反序列化；如果方法里查库，列表接口会立刻退化成 N+1。

校验分两层。validate_<field> 处理单字段规则，返回清洗后的值；validate 处理跨字段规则，返回 attrs。错误用 ValidationError 抛出，DRF 会收集成“字段到错误列表”的映射。数据库约束不要只靠序列化器，唯一性校验在并发下仍可能穿透，最终要有唯一索引兜底。

视图：从 APIView 到 ModelViewSet

DRF 的视图有三层台阶，选哪一层取决于接口之间的差异有多大。

APIView 最接近 Django 的 View：方法名即 HTTP 方法，认证、权限、请求解析和响应渲染由 DRF 接管，业务完全手写。它适合一次性的动作接口，或者流程特殊、复用价值低的端点。下面的例子先省略分页，把注意力放在流程上。

GenericAPIView 加上 mixins，把列表、创建、详情、更新、删除拆成可拼装的流程，同时提供 queryset、serializer_class、get_queryset、get_serializer 等基础设施。下面的视图与上面的功能等价，但分页和过滤只要挂上属性就能生效：

ModelViewSet 再进一步，一次给出 list、create、retrieve、update、partial_update、destroy 六个动作，配合 Router 只需一个类就能覆盖一组资源接口。此时定制点从“写方法”变成“覆盖钩子”：get_queryset 管数据范围，get_serializer_class 按 self.action 切换输入输出，perform_create 补默认字段，perform_destroy 可以做软删除。

列表接口用轻量序列化器，只返回卡片需要的字段；详情和写入才用完整序列化器，这是很常见的一刀。要注意 get_queryset 的分支必须覆盖匿名用户，直接拿 AnonymousUser 去过滤外键会抛异常。层级也不是越高越好：各动作差异很大时，硬塞进一个 ViewSet 会让钩子越写越绕，退回 APIView 或 GenericAPIView 反而清楚。

Router、自定义动作与版本化

Router 把 ViewSet 的动作翻译成 URL。SimpleRouter 只生成资源路由，DefaultRouter 额外提供 API 根视图和可选的格式后缀，调试时更方便，本文用它。

注册的前缀不要带结尾斜杠，Router 会自己补；basename 用于生成 URL 名称，省略时 DRF 会尝试从 queryset 推导，显式写出更稳妥。生成的路由覆盖集合与详情两层：GET 与 POST 落在 /products/，GET、PUT、PATCH、DELETE 落在 /products/{pk}/。所有路由都以斜杠结尾，客户端漏写时，APPEND_SLASH 会把 GET 重定向，但 POST 可能丢失请求体，接口文档里要写清楚。

资源之外的动作用 @action 声明。detail=True 生成 /products/{pk}/toggle-active/，detail=False 则挂在集合上。默认 URL 名是 basename 加动作名，下划线会转成连字符，可以用 reverse('product-toggle-active', args=[pk]) 取地址。自定义动作同样经过认证、权限与过滤，不要在方法里绕开 get_object() 直接查库，否则对象级权限不会执行。

版本化不必一开始就上复杂机制。把 /api/v1/ 写进项目路由最直观，缓存、日志和网关规则都能按前缀处理；DRF 自带的 URLPathVersioning、NamespaceVersioning 只是把这层解析规范化。关键是同一时间只保留少量版本，给旧版本设定下线窗口，并通过访问日志确认调用方已经迁移。序列化器按版本拆文件，别在一个类里堆条件分支。

认证与权限

认证解决“你是谁”，权限解决“你能做什么”，两者串联但职责不同。DRF 内置的 AllowAny、IsAuthenticated、IsAdminUser 覆盖大多数场景，IsAuthenticatedOrReadOnly 则是内容型接口的常用默认值。

权限类可以实现 has_permission 做视图级判断，也可以实现 has_object_permission 做对象级判断。后者只有在调用 get_object() 时才会触发，列表接口不会逐条检查；因此“只能看自己的商品”必须落实为查询集过滤，光写对象权限是不够的。下面这个权限类只覆写对象级方法，读请求放行，写请求要求本人或管理员：

认证方式的选择取决于客户端。SessionAuthentication 复用 Django 的会话 Cookie，适合与后端同源的网页；它对非安全方法强制 CSRF 校验，跨域前端要额外处理。TokenAuthentication 从 Authorization 头读取 Token，不依赖 Cookie，适合移动端和第三方调用；Token 长期有效，注销就是删除记录，必须走 HTTPS，也不能放进 URL 或日志。OAuth 适合需要授权的第三方生态，本文不展开。

分页、过滤与搜索

分页不是可选项。没有分页的列表接口在数据量上来后会把整张表读进内存，再序列化成巨大的 JSON，数据库和客户端一起遭殃。

PageNumberPagination 用 page 和 page_size 参数，响应里有 count、next、previous、results，前端能画出页码，最直观；代价是深页的 OFFSET 很大，翻页期间有新数据插入还会重复或漏条。LimitOffsetPagination 语义相近，适合无限滚动和分批导出，同样要设 max_limit。CursorPagination 把排序位置编码进 cursor，要求排序稳定，不返回总数、不能跳页，但在大数据量、频繁写入的时间线场景下最稳。

页大小必须有上限。page_size_query_param 允许客户端指定大小，max_page_size 兜住边界，否则一个 page_size=100000 就能把接口打穿。全局 PAGE_SIZE 只是默认值，字典表之类的固定小接口可以设 pagination_class = None 关闭分页。

过滤入口是 filter_backends。字段少、条件简单时，filterset_fields 让 DjangoFilterBackend 按模型字段生成精确匹配，旧教程里的 filter_fields 在 2.0 里仍可用，只是会提示改名；需要价格区间、跨表 slug 时，写 FilterSet 更清楚。

SearchFilter 读取 search 参数，默认对 search_fields 做不区分大小写的包含匹配，字段越多 SQL 越重；OrderingFilter 读取 ordering 参数，ordering_fields 是白名单，只放开需要且已建索引的列。FilterSet 条件复杂时，可以在 get_queryset 里用 ProductFilter(request.query_params, queryset=qs).qs 手动执行，避免与 filterset_fields 重复过滤。

错误处理与状态码

序列化失败返回 400，响应体是字段到错误列表的映射；validate 抛出的非字段错误放在 non_field_errors，抛字典则按字段归位。前端应按字段渲染提示，而不是把整个对象拼成一句话。

全局异常响应可以用 EXCEPTION_HANDLER 统一包一层业务码，但不要吞掉未处理的异常。返回 None 时 DRF 会把异常交还 Django，日志和监控才不会失明。

性能与常见坑

列表慢，先怀疑 N+1。序列化器访问 product.category.name 时，如果查询集没带关联，每一行都会补一条 SQL；列表里展开 category.products 也一样。前向一对多用 select_related，反向与多对多用 prefetch_related，再配合 only() 只取必要字段，SQL 的条数和列数都能降下来。分页本身就是性能手段，CursorPagination 还能省掉 count 查询；过滤与排序字段要有索引，否则数据量一大就全表扫描。

is_valid() 默认返回布尔值，忘了检查就访问 serializer.data 会抛断言，统一用 is_valid(raise_exception=True) 让错误直接变成 400。PATCH 走 partial=True，required 字段可以缺席，validate 里不能假设 attrs 一定有值，要回退到 self.instance。写操作涉及多张表时用 transaction.atomic 包住，库存扣减用 select_for_update 锁行；事务里不要调用外部 HTTP 服务，否则连接会被长时间占用。

权限只写认证是另一个高频错误：IsAuthenticated 只保证登录，不保证资源归属；对象权限要靠 get_object() 触发，列表必须靠 get_queryset 收口。Router 前缀不要带结尾斜杠，命名空间与 reverse 名称要统一，否则版本切换时前端拿到的地址会集体失效。

小结

DRF 的难点不在 API 数量，而在职责划分：Serializer 管契约与校验，View 管流程，Router 管地址，权限管边界，分页与过滤管数据量。先把这条链路走通，再逐步替换默认实现，比一上来堆配置更稳。写接口时多问一句“这段逻辑放在哪一层”，很多坑在设计阶段就能避开。
