NestJS 微服务实践

本文属于《TypeScript 学习路线》第 67/74 篇
上一篇系列目录下一篇

单体应用写到一定规模，模块之间的调用会织成一张看不见的网：改一次下单流程，要同时理解库存、优惠与支付三段代码；发一次版，要把整块应用一起重启。微服务不是银弹，但当团队边界、部署节奏与技术栈开始互相牵制时，它提供了一种把复杂度切开的手段。本文以 NestJS 5.x 为基准，从“该不该拆”的判断讲起，依次说明 @nestjs/microservices 的抽象、传输层选择、消息与事件模式、混合应用与网关，最后用一个电商拆分案例把契约、补偿与灰度上线串起来。读完之后，你应当能判断自己的项目是否到了拆分的时候，并写出第一个可运行、可观测、可回滚的 NestJS 微服务。

先判断：什么时候真的需要微服务

三个站得住的动因

第一个动因是团队边界。康威定律说，系统结构会复制组织的沟通结构。当同一个仓库里同时有订单、库存、结算三个小组，每次合并都要互相等待代码评审，每次发布都要协调窗口，团队的摩擦成本就会超过拆分的成本。此时把边界画清楚，让每个小组拥有自己的服务与发布流水线，收益是真实的。

第二个动因是独立部署与独立扩缩容。单体里一个导出报表的功能可能吃掉大量内存，一次图片处理的高峰可能拖慢整个应用。拆开之后，CPU 密集型服务可以单独扩容，变更频率低的服务可以很久不发版，故障也被限制在更小的爆炸半径内。

第三个动因是异构技术栈。推荐团队用 Python 训练模型，主站是 Node.js，支付网关需要用 Go 承接高并发。微服务允许每个边界选择最合适的语言与存储，但代价是运维复杂度上升：多套运行时、多套依赖、多套监控。

除以上三条，其余理由大多站不住。“别人都在拆”不是理由，“想用新技术”也不是理由。微服务解决的是组织与部署的耦合，不是代码质量问题；它会把耦合从进程内搬到网络上，让问题更贵，而不是更便宜。

什么时候不该拆

下面这份清单，如果多数答案是否定的，就应当先做单体。第一，团队是否已经大到无法在同一个发布单元里协作？第二，领域边界是否已经清楚，能否说清每个服务拥有哪部分数据？第三，是否具备持续集成、集中日志、指标监控与告警？第四，是否有自动化部署与快速回滚能力？第五，核心链路的调用延迟是否允许增加一次网络往返？第六，是否有人力维护多套部署、证书、配置与值班？

六个问题里若有三项以上回答“没有”，拆分带来的收益大概率会被运维成本吃掉。更稳妥的路径是“模块化单体”：仍然一个进程、一个数据库，但在代码层面把订单、库存、支付划成互不越界的 NestJS 模块，模块之间只通过公开的服务接口通信，禁止直接注入对方的 Repository。这样既保留了单体的部署简单，又提前把未来的接缝留好。等到某个模块真的需要独立扩容或独立发布，再沿着已有接缝切开，成本会低得多。

NestJS 的微服务抽象

从 HTTP 应用到消息驱动

普通的 NestJS 应用通过 NestFactory.create 创建，底层绑定 Express 或 Fastify 适配器。请求进来后，框架根据控制器上的路径与方法元数据找到处理函数，依次经过中间件、守卫、拦截器与管道，最后把返回值写成 HTTP 响应。整条链路的关键词是“请求—路由—响应”。

微服务应用换了一套入口。NestFactory.createMicroservice 不启动 HTTP 服务器，而是根据配置创建一种传输层策略，由它去连接 TCP 端口、Redis、NATS、MQTT 或 gRPC。消息到达后，框架不再看 URL，而是拿消息里的 pattern 去匹配处理函数。处理函数返回的值会被序列化，沿原通道送回调用方；抛出的异常则被包装成错误消息。这里没有路由的概念，也没有状态码，取而代之的是 pattern 与消息体。

维度 HTTP 应用 微服务应用
启动方式 NestFactory.create NestFactory.createMicroservice
入口 HTTP 请求 传输层消息
匹配依据 方法与路径 pattern
返回结果 响应体与状态码 序列化后的返回值或错误
中间件 可用 不适用，改用守卫、管道与拦截器
监听方式 app.listen(port) app.listen(callback)

这张表里最值得记住的是最后两行。微服务没有 HTTP 的中间件栈，习惯用中间件做鉴权、日志、限流的团队，需要把这些逻辑改写为守卫、拦截器，或者在网关层统一处理。也正因为入口变了，原来依赖 Request 对象的代码不能直接复用，业务服务与控制器要尽量与传输方式解耦。

传输层怎么选

TCP：默认选项，先跑起来

不写 transport 时，NestJS 使用 TCP。它在一个长连接上传输 JSON 消息，服务端监听端口，客户端按地址连接。优点是零额外依赖：不需要部署消息中间件，不需要运维新组件，延迟也低，适合服务数量不多、部署在同一内网或同一台机器上的场景。

TCP 传输层的边界也很清楚。它没有内建的认证与加密，任何能连上端口的人都能发消息，所以不能直接暴露到公网；跨机房调用要么走专线，要么自行加 TLS 隧道。它也不适合作为事件总线：一个 pattern 通常对应一个处理者，广播给多个服务并不是它的强项。连接断开时客户端会尝试重连，但重连期间的请求会失败，调用方必须把超时与重试写好。

Redis：已有缓存的顺手之选

很多团队本来就在用 Redis 做缓存与会话，于是顺手把它当成消息通道。NestJS 的 Redis 传输层基于发布订阅：pattern 就是频道名，请求与响应各占用一个频道。配置只需要一个连接地址。

它适合轻量通知、缓存失效广播、开发环境联调，部署成本几乎为零。但发布订阅不持久化：订阅者离线时发布的消息直接丢弃，Redis 重启也不会补发。把订单创建、库存扣减这类不能丢的事件放在上面，等于把资金安全寄托在一次网络连接上。Redis 5.0 虽然引入了 Stream 这种可持久化的结构，但当时 NestJS 的 Redis 传输层仍然走发布订阅，两者不要混为一谈。

NATS：轻量的事件总线

NATS 用一个极小的服务端进程提供基于主题的消息路由，支持队列组：多个订阅者订阅同一主题时，消息只投递给组内一个实例，天然适合多副本消费。核心 NATS 的语义是“最多一次”，服务端不落盘，消费者离线就错过消息；需要持久化时要额外部署 NATS Streaming。对内部事件总线而言，它运维负担小、启动快，在 2019 年的中小团队里很受欢迎。

MQTT：为设备与弱网准备

MQTT 通过 Broker 转发，主题可以分层，支持通配符订阅，QoS 分为 0、1、2 三档。它的设计目标是低带宽、不稳定网络与海量连接，因此常用于物联网设备接入、移动端推送。放到内部服务调用上，它也能工作，但主题命名、权限控制、Broker 运维都要额外设计。QoS 1 意味着“至少一次”，重复投递是常态，消费者必须做幂等。

gRPC：跨语言与强契约

当服务用不同语言编写，或者接口需要严格的 schema 时，gRPC 更合适。它用 Protocol Buffers 定义消息与方法，编译期生成各语言客户端，字段类型与编号都是契约的一部分。NestJS 侧需要指定 proto 文件路径与 package 名，消息处理函数用 @GrpcMethod 声明对应的服务方法。

代价是构建链更重：proto 要版本化、要 review、要处理向后兼容，调试也不如直接看 JSON 直观。若团队全是 TypeScript、服务数量不多，TCP 加共享类型定义往往更划算。

传输层 适用场景 主要代价
TCP 同内网、少量服务、低延迟调用 无鉴权加密，广播能力弱
Redis 已有 Redis、轻量通知与广播 不持久，离线即丢
NATS 内部事件总线、多副本消费 核心模式不持久，需另配持久化
MQTT 设备接入、弱网、主题订阅 Broker 运维，可能重复投递
gRPC 跨语言、强类型契约 proto 管理与构建复杂度

消息模式与事件模式

MessagePattern：请求与响应

@MessagePattern 声明的是一个“命令”：调用方发出消息，等待一个结果。服务端的处理函数正常返回，返回值被序列化后送回；抛出异常，异常被包装成错误消息送回。语义上它接近一次远程函数调用，适合查询与需要确认结果的写操作，例如 order.find、inventory.reserve、payment.refund。

命令的命名应当是“做什么”，而不是“发生了什么”。一个 pattern 只应由一个服务负责，否则请求会被随机分给其中一个处理者，行为不可预测。

EventPattern：已经发生的事实

@EventPattern 声明的是一个“事件”：某件事已经发生，发布者不关心谁在听，也不等待结果。处理函数的返回值会被忽略，异常也不会传回发布者。它适合副作用与广播，例如订单创建后发积分、发短信、更新报表。

事件命名应当是“发生了什么”，用过去式，例如 order.created、inventory.reserved、payment.succeeded。同一事件可以有多个消费者，也可以暂时没有消费者；发布者不应假设任何下游存在。

两者的差别不只是返回值，而是失败责任。命令失败，调用方立刻知道，可以重试或回滚；事件失败，发布者毫无感知，必须有日志、告警、重试与死信兜底。很多团队把该用命令的地方写成事件，结果下单成功、库存没扣，直到盘点才发现。

客户端：注入、连接与超时

用 ClientsModule 注册

调用方不需要自己 new 一个客户端，而是通过 ClientsModule.register 把连接配置注册成 provider，再用名字注入。这样做的好处是连接配置集中在模块里，测试时可以整体替换成内存实现。

name 是注入令牌，可以注册多个下游，例如 INVENTORY_SERVICE 与 PAYMENT_SERVICE。主机与端口应当来自环境变量，而不是写死在代码里；同一个镜像要在测试、预发、生产三套环境里运行，配置必须外置。

连接是懒建的

ClientProxy 不会在应用启动时立刻建立连接，而是在第一次 send 或 emit 时才连接。这样启动更快，但如果下游地址配错，问题会推迟到第一笔业务请求才暴露。对关键依赖，可以在模块初始化钩子里主动连接，让故障在启动阶段就显现。

主动连接适合“没有它就不能对外服务”的下游；如果下游只是可选的报表服务，启动时连不上就崩溃反而降低了可用性。连接失败后的重连由传输层负责，应用层仍要准备超时与降级。

超时与错误传播

每个跨进程调用都必须有超时。没有超时，下游卡住时调用方的连接、内存与请求上下文会一直堆积，最终把上游也拖垮。超时值要小于上游给自己的预算：网关给订单接口 2 秒，订单调用库存就只能是几百毫秒，不能反过来。

错误传播有三类来源。服务端主动抛出的 RpcException，会带着错误信息回到客户端；RxJS 的 TimeoutError 表示在限定时间内没有收到响应；连接层的错误则可能是端口不通、证书过期或对端重启。客户端应当把它们翻译成自己的领域错误，再决定重试、降级还是直接失败，不要把底层异常原样透给前端。

混合应用：一个进程，两种入口

真实项目很少一次性把所有流量切到微服务。更常见的情况是：应用仍然对外提供 HTTP，同时把内部接口以 TCP 或 Redis 暴露出来，让新服务可以先调用它。NestJS 的混合应用正好覆盖这个过渡期。

两种入口共享同一个依赖注入容器。HTTP 控制器与消息控制器可以注入同一个 OrdersService，事务、缓存、数据库连接都是同一份，不需要重复搭建。对过渡期来说，这意味着旧调用方继续走 HTTP，新调用方走 TCP，业务逻辑只有一份。

但混合应用不是终点。两个入口跑在同一个事件循环里，HTTP 的突发流量会挤占消息处理，消息处理里的长任务也会拖慢 HTTP 响应；进程崩溃时两种入口一起不可用，故障隔离无从谈起；测试矩阵也从一套变成两套。它适合作为“拆分的中间态”，上线时就应该约定退出条件，例如三个月内把旧 HTTP 调用全部迁移完，然后摘掉其中一个入口。把混合应用当成长期架构，等于同时承担单体与微服务的成本，却只拿到一半收益。

网关与 BFF

服务拆开之后，浏览器不能也不应该知道每个服务的地址。对外仍然需要一个统一入口，这就是 API 网关；如果网关还针对不同客户端做裁剪，它同时扮演 BFF（Backend for Frontend）的角色。下图是一个典型的调用关系。

  G -->|send stock.query| S[库存服务]
  O -->|emit order.created| S
  S -->|emit inventory.reserved| O

网关应该做什么

网关的第一职责是收敛入口：统一 TLS、统一域名、统一鉴权。令牌校验、租户识别、限流与黑白名单放在这里，比在每个服务里复制一遍更可靠。第二职责是协议转换：外部是 HTTP/JSON，内部可能是 TCP 消息或 gRPC，网关负责把请求翻译成命令，把结果翻译回响应。第三职责是聚合：一个商品详情页需要商品、价格、库存三份数据，网关可以并发调用三个服务，拼成一个响应，减少客户端的往返次数。

BFF 则进一步按客户端拆分。移动端只需要精简字段，后台管理端需要完整信息，两边的聚合逻辑与发布节奏都不同。用一个 BFF 服务同时伺候所有客户端，最终会变成一堆条件判断；按端拆成两个薄层，反而更容易维护。

不要把业务逻辑堆在网关

网关最容易失控的地方，是“顺手在这里改一下”。今天加一个优惠计算，明天加一个库存判断，半年后网关连上了数据库，所有业务变更都要改同一个仓库，所有团队共用一个发布窗口，分布式单体就这样诞生了。网关一旦成为瓶颈，拆分服务省下来的独立性会被全部抵消。

一条可执行的规则是：网关只做“翻译与编排”，不拥有数据，也不做状态变更的最终裁决。聚合时可以调用服务、可以裁剪字段、可以并行请求，但价格怎么算、库存能不能扣、订单状态怎么流转，必须由对应服务决定。如果一段逻辑需要读写业务表，它就不属于网关，而属于某个服务。

可靠性与可观测性

幂等：消息系统的第一道防线

只要经过网络，就必须假设消息会重复。客户端超时重试、Broker 重投、消费者在处理完成后崩溃，都会让同一条消息被处理两次。幂等的做法不是“小心一点”，而是让重复处理不产生额外效果。

常见做法是给每条消息一个全局唯一的消息 id，消费者在本地事务里先写一张去重表，消息 id 上有唯一索引；插入冲突就说明处理过，直接返回。更简单的做法是利用业务状态机：扣库存时执行带条件的更新，只有状态仍为“待预占”时才扣减，重复请求自然更新不到行。两种做法都要求“去重记录”和“业务变更”在同一个本地事务里，否则仍会出现写了去重却没改业务、或改了业务却没写去重的缝隙。

重试、死信与补偿

重试要有边界。只对可恢复的错误重试，例如连接失败、超时、下游暂时不可用；参数校验失败、库存不足这类确定性错误重试多少次都一样。重试间隔应当递增并加入随机抖动，避免所有实例在同一时刻再次打垮刚恢复的下游。次数用尽后，把消息写入死信表或死信主题，记录原始消息、失败原因与堆栈，再配一个可以按条件重放的工具。没有死信的重试，只是把故障藏进了日志。

若传输层支持确认，事件消费者还要想清楚确认时机。处理成功后再确认，崩溃会导致重投，因此必须幂等；先确认再处理，崩溃就会永久丢消息。多数业务应选择前者，用幂等换可靠性。

超时与熔断

超时是调用链的刹车。每一跳都要设置比上游更短的超时，给上游留出降级与返回错误的时间；如果下游超时是 3 秒，上游也设 3 秒，上游只会先被拖死。超时值要基于压测与真实延迟分布，而不是拍脑袋。

熔断是超时的补充。下游连续失败达到阈值后，断路器打开，后续请求直接失败，不再占用连接与等待时间；经过一段冷却期进入半开状态，放少量请求试探，成功则闭合，失败则继续打开。NestJS 5.x 没有内置熔断器，可以在 ClientProxy 外再包一层，用计数器与定时器实现，也可以引入社区库。关键不是用哪个库，而是承认“下游会长时间不可用”，并让失败快速、可控。

日志与 correlation id

一次下单可能经过网关、订单、库存、支付四个进程，出问题时最怕日志各说各话。解决办法是在入口生成一个 correlation id，随消息信封一路传递，每个服务在日志里带上它。查问题时用一个 id 串起所有服务的日志，比按时间猜要快得多。

日志至少记录：服务名、pattern、correlation id、耗时、结果状态与错误码。消息体默认不要全量打印，里面可能有手机号、地址与支付信息；需要排查时按采样开关临时打开，并设置保留期限。

健康检查

每个服务都应能被检查健康状态：带 HTTP 入口的服务暴露 GET /health，纯微服务用消息 pattern 或另开管理端口。健康检查不应放在需要鉴权的业务路由里，也不应做重活：检查进程能否响应、数据库连接是否可用、关键下游是否能 ping 通，每项给一个很短的超时，全部通过返回 200，否则返回 503。

健康检查要区分“活着”和“能服务”。进程活着但数据库断开，不应继续接流量；而如果把每个下游都设为硬依赖，任何一个抖动都会让整个集群同时摘除实例。只把真正影响核心功能的下游放进就绪检查，其余的降级为告警。

数据边界与一致性

每个服务拥有自己的数据库，其他服务不得直连或共享表。共享表会把 schema 变成跨团队接口，一方改字段，另一方半夜告警。跨服务取数只有两条路：同步调用查询命令，简单但增加耦合与延迟；或订阅事件维护本地读模型，查询快但有延迟。

分布式事务是拆分最真实的代价。两阶段提交跨异构存储难落地。更现实的是最终一致：Saga 把大事务拆成多个本地事务，每步准备补偿；本地消息表保证业务写入与事件发布同生共死，再由投递任务重试。编排式流程清晰但协调者易成中心，协同式耦合低但链路难追踪。两种都要接受中间状态，并如实展示“处理中”。

案例：从单体拆出订单与库存

设定一个 NestJS 电商单体，订单、库存、支付同库同进程，下单时用本地事务同时写订单、扣库存。大促时库存行锁把接口拖到超时，库存团队又要独立发布，于是只拆库存，订单与网关不动。

契约与补偿

命令走 MessagePattern，事件走 EventPattern，所有消息带同一个信封：id 用于幂等，version 用于演进，correlationId 用于追踪。

正常路径是订单落库为待处理，发出 order.created；库存服务消费后执行预占，成功发 inventory.reserved，订单确认；库存不足发 inventory.rejected，订单取消。inventory.reserve 命令保留给补偿与重试使用。异常路径由定时任务兜底：扫描停留过久的订单，查询预占是否存在，不存在就取消，存在就释放后取消。补偿命令也要幂等，重复释放不能报错。

灰度上线顺序

  1. 部署库存服务，双读对比，只记录差异不切流量。
  2. 消费者先上线，只写影子表，不真正扣减。
  3. 双写：本地扣减照旧，新服务在影子库存上预占，逐笔比对。
  4. 切写：按租户或比例打开开关，旧路径保留可回滚。
  5. 切读、停双写、备份后下线旧表，观察一个完整业务周期。

原则是消费者先于生产者、读先于写、每一步都能用开关退回。

常见坑

  • 按技术层拆服务，controller、service、dao 各成一个服务，得到分布式单体。
  • 共享数据库，schema 变更变成跨团队破坏性变更。
  • 消息没有版本，新增字段让老消费者解析失败。
  • 消费者重启丢消息，发布订阅不持久，关键事件没有位点。
  • 同步调用链过长，延迟叠加、故障放大。
  • 没有超时与重试边界，连接堆积，故障扩散。

小结

微服务是组织与部署的工具，不是代码质量的捷径。先用三条动因与六项清单判断该不该拆，再守住数据边界，用命令与事件分清失败责任。NestJS 5.x 把传输层做成适配器，真正难的是 send 与 emit 的冷 Observable、超时、幂等、死信与可回滚的灰度。
