信息收集与资产梳理

很多团队的安全工作是从“扫一遍主域名”开始的，却说不清自己到底有多少资产暴露在互联网上。本文换一个视角：把信息收集当成日常资产管理的一部分，先划清授权边界，再用被动与主动两类手段把家底摸清，最后沉淀成一份能持续维护的资产台账。内容面向刚接手安全工作的开发者和运维人员，读完可以独立组织一次合规的资产盘点，并把发现的问题变成可跟踪的整改项。

为什么要做资产梳理

安全圈有一句老话：你不知道的资产，就是你防不住的资产。漏洞可以补，策略可以调，但一台没人记得的测试服务器放在公网上，任何防护措施都覆盖不到它。资产梳理要解决的第一个问题，不是“哪里有漏洞”，而是“我们到底有什么”。

在笔者接触过的环境里，未知资产通常来自几个固定的方向。

其一是影子资产。业务为了赶进度，开发同学自己申请一台主机、绑一个域名就上线了，没有走审批，也没有登记。这类资产往往不打补丁、不开日志，账号还是默认口令，等到出事才被发现。

其二是过期域名与闲置解析。项目下线了，域名没有及时注销，或者 DNS 里还留着一条指向旧主机的解析记录。域名一旦被他人抢注，邮件、单点登录回调甚至白名单都可能被顺带接管。

其三是测试与预发布环境。测试环境为了联调方便，经常关掉认证、打开调试接口、把数据库端口直接暴露出来，而它的代码往往比生产环境落后好几个版本。攻击者不需要攻破生产，从这个“后门”进来一样能拿到数据。

其四是第三方托管。官网放在外包手里，活动页挂在内容平台上，对象存储开了公共读，小程序后端由供应商维护。这些资产在法律和业务上属于自己，在技术上却不在自己的机房和监控范围内。

所以信息收集不该是渗透测试项目里的一次性动作。渗透测试有明确的起止时间，测试报告交付之后，资产又会在几个月里悄悄变化。把收集动作常态化，按季度或按月重跑一遍，才能让台账跟得上现实。这也是等级保护里“资产清单”这类基础工作的意义：连资产都列不全，后面的定级、测评、整改都无从谈起。

授权与合规：先划范围，再动手

信息收集分两类，边界完全不同。

被动收集指的是使用公开渠道获取信息：域名注册记录、DNS 解析结果、证书透明度日志、搜索引擎索引、公开代码仓库。这些数据本来就是公开的，查询行为不会给目标系统带来额外流量，风险最低。但“公开”不等于可以随意使用：搜索引擎的服务条款、注册局的查询频率限制、代码仓库里的他人隐私，都要一并考虑，不要把“公开”当成“免费且无限”。

主动收集则是直接向目标主机发包：解析子域名、扫描端口、请求页面、探测目录。只要报文发到了对方的服务器，就属于主动探测。这里只有一条底线：只对自有资产或已获得书面授权的资产做主动探测。授权文件里要写清楚域名与网段范围、时间窗口、允许的手法、禁止的动作（例如不做口令爆破、不做拒绝服务测试）、应急联系人。范围之外的一律不碰，哪怕只是“顺手看一眼”。

扫描速率是另一个容易被忽略的合规点。扫描器默认的并发往往按公网带宽设计，直接对着生产环境跑，轻则把日志刷满、告警风暴，重则把老旧的业务系统拖垮。实践中应当先降并发、拉长间隔，在业务低峰期执行，并对关键系统做白名单排除。发现异常时立刻停止，先确认业务影响，再决定是否继续。扫描是为了看清资产，不是证明自己能打。

还有一点需要提前说清楚：主动收集拿到的结果，属于企业内部敏感数据。资产清单里往往包含内网地址、中间件版本、后台路径，这些信息一旦泄露，等于把攻击面地图送给对方。台账本身也要按敏感数据管理，控制访问权限，不要随手放在公共网盘或聊天群里。

被动收集：先画出资产轮廓

被动收集的目标是拿到一张“可能属于我们”的候选清单，它不追求准确，只追求覆盖。后续再用主动手段逐条确认。

域名注册信息是第一层。通过 whois 可以拿到注册人、注册商、创建与到期时间、DNS 服务器。对自有资产来说，最有价值的字段是到期时间与注册邮箱：到期时间用于续费提醒，注册邮箱用于反查同一主体注册的其他域名。需要注意，域名开启隐私保护后，注册人会被代理信息替换，剩下的价值主要是到期时间与 DNS 服务器。

DNS 记录是第二层，也是信息量最大的一层。常见记录类型各有含义：

  • A 与 AAAA 记录给出域名对应的 IPv4/IPv6 地址，是资产与 IP 的对应关系；
  • CNAME 记录指向另一个域名，常用于 CDN、对象存储、第三方服务，顺着它可以发现托管关系；
  • MX 记录指向邮件服务器，邮件系统往往是独立的一批资产；
  • TXT 记录常用于域名所有权验证、SPF 反垃圾邮件策略，验证记录里经常泄露第三方平台的名称。

第三层是证书透明度日志。CA 在签发证书时必须把证书提交到公开日志，这些日志可以被任何人查询。查询某个域名在日志里出现过的所有证书，能发现大量“曾经存在、现在不解析”的子域名，比如临时活动页、测试接口、已经下线的旧系统。这类历史子域名最容易被漏掉。

第四层是搜索引擎与公开代码仓库。搜索引擎的高级语法可以按站点、标题、URL 特征、文件类型筛选，用来找后台入口、暴露的文档、报错页面。公开代码仓库则常出现配置文件里写死的测试地址、内网 IP、第三方接口密钥。这两类信息都属于公开数据，但使用时要注意：只做自查，不批量爬取；发现密钥先走内部流程轮换，不要在公开渠道复述。

最后是企业组织关系。集团与子公司、并购来的业务、海外站点，往往各自维护一套域名和证书，母公司的资产台账里根本没有它们。梳理时要按法人主体和业务线各过一遍，把“谁负责、谁付费、谁运维”问清楚。这一层靠技术手段查不出来，只能靠人和流程。

主动收集：在授权范围内确认细节

被动收集给出候选，主动收集负责确认：这个域名还活着吗，它解析到哪台主机，主机上开了什么服务，服务是什么版本。

子域名枚举是最先做的一步。常见做法是字典拼接加 DNS 查询：把常见的前缀（www、mail、test、dev、api、admin 等）与主域名组合，逐个查询是否存在解析记录。字典要按企业实际情况裁剪，不要直接套用网上那种几十万行的通用字典，既慢又容易触发对方 DNS 的限流。除了字典，还可以从已有证书、页面里的外链、JS 文件中的接口地址反推子域名。查询时控制并发，遇到大量超时就停下来看看是不是被限流了。

端口与服务识别用 Nmap 7.x。最常用的组合是先快速看常见端口，再对存活主机做版本识别：

-sV 会主动发送探测报文，识别服务名称与版本号，这对判断“版本是否过旧”很关键。-T3 是较为温和的时序模板，生产环境不要用 -T4 以上的激进模式。-oX 输出 XML，方便后续用脚本转成表格，比手工抄写可靠得多。

Web 指纹用于判断站点跑的是什么。三个地方最有效：响应头里的 Server、X-Powered-By 等字段；页面引用的静态资源路径与文件名规律，比如某种框架固定的 JS 目录结构；以及默认的 favicon、登录页样式、报错页特征。指纹本身不是目的，重点是判断系统由谁维护、版本是否过旧，从而确定优先级。

目录与接口发现要格外克制。只对授权范围内的站点做，使用小规模字典，限制请求速率，遇到 403 与 429 立即降速或停止。很多团队的扫描把 WAF 打出了封禁，业务方第二天来投诉，这类事故完全可以通过限速避免。发现的后台路径、接口地址要记进台账，但不要在报告里贴出可直接访问的完整链接。

资产台账：把发现变成记录

收集结果如果只停留在扫描报告里，过两周就没人看得懂了。台账要回答四个问题：这是什么、在哪里、谁负责、有多重要。字段不必多，但每一列都要有明确的用途，否则填两次就荒废了。

域名 IP 端口 服务与版本 环境 负责人 重要性 到期时间
www.example.com 192.0.2.10 443 Nginx 1.14 生产 zhangwei 高 2021-06
api.example.com 192.0.2.11 443 Tomcat 8.5 生产 lina 高 2021-06
test.example.com 192.0.2.20 8080 Tomcat 7.0 测试 lina 中 2019-08
mail.example.com 192.0.2.30 25/443 Postfix 生产 chenlei 高 2022-01

除了表格里的字段，还建议补三列。一是协议，区分 HTTP、HTTPS、数据库协议，便于判断是否明文传输。二是暴露面，标注“公网可访问”“仅内网”“经代理”等状态，它直接决定优先级。三是归属确认状态，把“扫描发现但还没人认领”的资产单独标出来，这类记录才是真正需要追的。

台账要有生命周期。新资产上线时登记，变更时更新，下线后不要立刻删除，改为标记“已下线”并保留半年，因为域名和 IP 可能在缓冲期里被重新启用。责任人一栏必须落到具体的人，写部门等于没写。台账的存放也要控制权限，避免多个表格文件互相覆盖。

排序与持续化

台账建好之后要排序，否则几百条记录等于没有重点。排序看两个维度：暴露面与业务重要性，二者的组合决定先后。公网可直接访问、承载敏感数据、版本明显过旧、又没有明确负责人的资产排在最前，这四类条件同时命中的，通常就是下一季度整改清单的头部。

flowchart TD
    A[被动收集候选] --> B[主动确认]
    B --> C[登记台账]
    C --> D[按暴露面与重要性排序]
    D --> E[生成整改工单]
    E --> F[定期重扫与变更比对]
    F --> C

持续化的关键在“比对”而不是“重扫”。每次扫描结果与上一版台账做差集，新出现的子域名、新开的端口、新签发的证书，都是需要确认的变更。这些变更可以来自例行扫描，也可以来自证书透明度日志与 DNS 解析的监控。发现之后要走确认流程：先问归属，确认是自家资产就补登记，确认是外包或第三方就补协议与联系方式，无人认领的按风险处置。最后一步是和 CMDB、工单系统打通，把资产记录与变更单、整改单关联起来，让“发现”真正变成“有人负责修”。

常见误区

实践中重复出现的错误有这么几个。只看主域名，不管子域和历史域名，结果漏掉最危险的测试系统。只扫 80 和 443，忽略 8080、8443、数据库端口，很多管理后台就开在非标准端口上。把 CDN 或 WAF 的地址当成源站，后续所有判断都建立在错误的前提上。扫描不限速，被对方封禁或拖垮业务，反而制造了新问题。台账建完就锁进抽屉，半年后与现网完全对不上。发现未知资产不确认归属，直接写进报告，等于把问题留给下一个人。

小结

信息收集的价值不在“收集”这个动作，而在它产出的资产视图。先明确授权与限速，再用被动手段扩大候选面、用主动手段确认细节，最后把结果整理成有责任人、有生命周期、能持续比对的台账。把这件事做成季度例行工作，比每年做一次渗透测试更能降低真实风险。漏洞验证与利用不在本文范围。
