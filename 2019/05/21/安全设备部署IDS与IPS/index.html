安全设备部署：IDS 与 IPS

不少团队在等保整改时买了 IDS 或 IPS，上架、插线、灯全绿，却说不清它挂在哪一段、误报由谁处理。本文从部署与运营视角，讲清角色差别、旁路与串接的取舍、规则调优与日志联动。读完应能画出带设备位置的网络简图，也能写出可执行的上线观察计划。

先把三种设备摆到正确的位置

很多同学把 IDS 与 IPS 当成同一类设备的两个型号。它们最关键的差别不在检测能力，而在失败时的后果，这决定了后面的部署与运营纪律。

IDS 只观察，IPS 会动手

IDS（Intrusion Detection System，入侵检测系统）工作在旁路：交换机复制一份流量给它，原件继续流向目的地。设备宕机、规则写错、升级重启都不影响业务，代价是只能看见、不能拦住，告警到处置之间始终有空窗。

IPS（Intrusion Prevention System，入侵防御系统）串接在链路中，流量必须穿过它，判定为恶意的会话可直接丢弃或阻断。响应被压到毫秒级，它自己也成了链路的一部分：故障、策略写错、性能不足，都会直接变成业务中断。一句话，IDS 的风险是漏报，IPS 的风险是误杀加断网，所以后者的部署纪律要严得多。

NIDS 与 HIDS 看的是不同层面

按数据来源再分一层。NIDS 抓网线上的包，能看到扫描、漏洞利用、木马回连、DNS 隧道，却看不到主机内部，尤其是加密后的内容。HIDS 以 agent 跑在服务器上，监控文件完整性、进程、账户、关键日志和本地连接，能发现文件被改、多出计划任务这类网络层无从判断的事件。

两者不是替代关系。NIDS 覆盖广、对业务无侵入，适合做第一道筛子；HIDS 看得深，适合放在核心业务服务器和数据库上。常见用法是 NIDS 报警指向某台主机，再由 HIDS 确认改了什么。

WAF 与 IPS 的边界

WAF 和 IPS 都会拦攻击，解析深度不同。WAF 理解 HTTP：URL、参数、Cookie、会话、上传文件，能判断参数里是正常文本还是注入片段；IPS 是通用网络设备，对 Web 语义理解有限，只能靠载荷特征猜，误报率更高。

边界这样划：注入、XSS、文件包含、命令执行交给 WAF；端口扫描、漏洞利用框架流量、蠕虫、木马心跳、口令爆破交给 IPS。两者都开时要接受同一攻击报两次，在平台去重。

对业务影响 无 故障即断网 同左，另加解析开销

部署在哪里：四个位置与两种接入

位置由你要回答的问题决定：看外部打进来，还是看内部横向移动。下图是中等规模网络的常见摆法。

flowchart TD
    Internet[互联网] --> Router[边界路由器]
    Router --> FW[边界防火墙]
    FW --> IPS[IPS 串接]
    IPS --> Core[核心交换机]
    Core --> DMZ[DMZ 区]
    Core --> LAN[办公与业务内网]
    Core -. 镜像流量 .-> IDS1[边界旁路 IDS]
    DMZ -. 镜像流量 .-> IDS2[DMZ 旁路 IDS]

互联网边界最经典，能看清扫描、爆破、利用和回连，也是测评常查的一段。DMZ 放在对外服务前面，盯 Web 攻击与 webshell 通信，与 WAF 互补。核心交换机旁挂覆盖南北向总流量，一台管多个区域，性价比高但流量大。内网东西向最难：通常只对关键服务器段做镜像，或用 HIDS 补位，全内网串接的成本与风险不可接受。

旁路：镜像、分光与 TAP

端口镜像最省事，交换机上把端口或 VLAN 复制到观察口即可，缺点是忙时可能丢包、占用背板带宽。分光器按比例分光，不占交换机资源，也不怕流量突增，但施工要断纤，需要窗口期。TAP 串在链路中一分二，可靠性最好，成本最高。

三种方式共同的坑是只镜像了单向流量。会话是双向的，只收请求收不到响应，TCP 重组和协议解析都会出问题，表现为大量半连接告警和莫名漏报。配完镜像口一定要抓包双向验证。

串接：把设备变成链路的一部分

串接的收益是阻断，代价是可用性，工程上要准备三样东西。一是 bypass，断电或进程崩溃时物理直通，业务不中断，但 bypass 期间毫无防护。二是双机热备，做会话同步，切换时已建连接不断。三是链路聚合，多链路捆绑分流，但同一会话的五元组哈希必须落在同一台设备，否则会出现一半报文被阻断、一半放行的怪现象。

还有一点常被忽略：串接设备的升级、重启、规则更新都要断流，必须走变更窗口，不能像旁路那样随手点。

检测原理决定了能力边界

从特征到行为

最基础的是特征匹配：把五元组与载荷模式逐条比对，命中就告警。它快、准、好解释，但只认已知，改一个字节、换一种编码，特征就失效。特征型设备于是总在追漏洞。

为对抗规避，设备要做协议解析：重组 TCP 流，按 HTTP、DNS、SMB 解码，处理分片、压缩与编码，再在还原后的语义上匹配。解析器写得粗，误报就多；解析器与目标系统对重叠分片理解不一致，漏报就来了。同一份流量两台设备结论不同，属常态。

第三类是异常行为：先跑基线，统计单位时间的连接数、失败率、上下行比例、外联分布，偏离就报。它擅长发现扫描、爆破和周期心跳，但基线要时间积累，业务一变就得重学，否则会把促销流量当攻击。

规则集与版本

规则分社区与商业两类，每条有规则号、修订号和依赖的引擎版本。更新不是越勤越好：新规则可能带来新误报，也可能依赖新引擎。稳妥做法是先在测试环境用回放流量跑一遍，确认告警增量可接受再推生产，并保留上一版规则包以便回滚。把 Windows 规则全开在纯 Linux 网段，除了噪声没有收益。

加密流量留下的盲区

如今大部分业务走 TLS，IPS 在 443 上只能看到证书、SNI、包长和时序，针对 Web 的注入、上传、命令执行基本无能为力。理论上可在出口做 TLS 卸载再送检，但涉及证书管理、隐私合规和成倍性能开销，多数单位并不采用。结论是：别指望 IPS 覆盖加密流量，这块要靠有证书的 WAF、主机 agent 和终端日志补位。

上线调优：先观察，再阻断

观察期不是走过场

新设备先跑两到四周观察模式，只告警不阻断。这期间记录每天告警总量，按源、目的、规则号排行，找出噪声最大的前二十条规则。没有这份基线，调优都是拍脑袋。

白名单要小，也要有人负责

扫描器、监控拨测、备份、CDN 回源、健康检查几乎必然触发告警。处理方式不是关规则，而是加白：用业务名、源、目的、规则号四要素限定范围，附申请人和到期时间。白名单要定期复核，否则半年后就是一张谁也说不清来历的放行清单。

误报的闭环与规则分级

一条告警进来，先看原始报文和会话上下文，确认是误报、环境噪声还是真事件；再决定加白、调阈值、禁用单条规则，或提交厂商修正，全程留记录。最忌讳一出误报就关设备：关一条规则只损失一个检测点，关设备等于整段网络裸奔。

规则按危害分三档：高危直接阻断，例如已知木马回连、蠕虫利用、明确的远程命令执行；中危只告警，例如扫描探测、口令爆破、可疑客户端；低危仅记录，例如信息泄露和协议异常。上线初期阻断面一定要窄。

性能与容量：标称值不等于可用值

厂商标称的吞吐往往是特定包长、关闭部分检测能力下的理想值，混合流量、开启深度检测后要打折。除吞吐外还要看三项：并发会话数决定长连接业务能否扛住，新建连接速率决定突发访问会不会丢会话，时延决定串接是否可接受。平均值最没有参考价值，要看忙时峰值，至少取十五分钟粒度和 P95。

串接设备成为瓶颈时，表现是丢包、重传、时延上升，业务侧往往只反馈变慢。上线前应当用测试仪打流验证，或先在低峰期短时串接观察。扩容手段有限：链路聚合、双机分担、把非关键链路改回旁路。数据库同步、存储复制、语音这类时延敏感流量，不要串在 IPS 后面。

日志、留存与联动

每条告警至少要能回答：什么时候、哪台设备、源和目的是谁、什么协议、命中哪条规则、严重级别、执行了什么动作。时间必须统一，设备、服务器、日志平台各用自己的时钟，关联分析就会得出攻击在响应之后这种荒唐结论，所以 NTP 要指向同一时源。

日志通常送 SIEM 或态势平台做关联，再与防火墙联动下发封禁。联动要谨慎，自动封禁可能封掉 NAT 出口、CDN 回源地址或云清洗节点，一次误封就是一片用户不可访问。稳妥做法是先封十五分钟并自动解封，同时推给值班人确认。

留存时间按等保要求不少于六个月。1.0 的《信息系统安全等级保护基本要求》对审计记录留存有明确表述；2.0 的 GB/T 22239-2019 已于 2019 年 5 月 10 日发布、12 月 1 日实施，本文写作时尚未生效，条文中延续了六个月的口径。实际执行以现行标准与主管单位要求为准，容量按日告警量乘以单条大小再乘一百八十天估算。

运营指标与告警疲劳

日常至少盯五个数：日告警量、误报率、平均响应时间、规则覆盖率、设备可用性。误报率等于确认误报数除以告警总数，长期超过一半说明调优没做完；响应时间从告警产生算到处置完成；可用性要区分设备在线和检测生效，bypass 状态下设备在线，防护却等于零。

告警疲劳的根源是数量而不是能力。缓解办法：按源地址和规则聚合，同一事件只推一条；只把高危推到值班群，中低危进日报；每周看趋势而不是逐条看；设定升级路径，明确什么情况必须半夜叫人。

一次部署的完整过程

笔者参与过一次中型电商的整改：边界一台防火墙，DMZ 三台 Web 服务器，内网约五百台终端，测评提出入侵防范要求。

方案是边界串接 IPS 双机，DMZ 与核心交换机各旁路一台 IDS。实施分三步。第一步，旁路跑两周记录基线，发现每天数千条告警，绝大多数来自漏洞扫描器、监控拨测和 CDN 回源。第二步，按四要素加白，告警降到百余条，规则分成三档，只留十余条高危规则处于阻断状态。第三步，选凌晨窗口串接，提前配好 bypass，保留原直连光纤，并约定回滚判据：时延明显上升、业务错误率抬头或设备负载过高，十分钟内拔线恢复直连。

串接当晚就触发了一次回滚：一条规则把报表系统的长连接误判为异常，部分查询超时。恢复直连后取样分析，加白并降级该规则，一周后重新上线，未再复发。

几个反复出现的坑

镜像口只配单向，协议解析残缺，告警忽多忽少；串接单机没有 bypass，设备一挂整层断网；规则全开不做性能评估，忙时直接丢包；只买设备不配人，告警堆在邮箱里；全站 HTTPS 却指望 IPS 看见内容；设备与服务器时间不同步，日志根本对不上。还有一个隐性的：把旁路 IDS 当 IPS 汇报，测评时说不清阻断能力。

小结

IDS 与 IPS 的差别在失败后果，不在检测能力。位置由要回答的问题决定，接入方式由可用性要求决定。规则调优是长期工作，先观察后阻断，白名单要小且有主。性能按峰值和真实包长评估，日志要能关联、要留够时间，指标盯住误报率与响应时间。设备只是起点，没有运营的 IDS 和 IPS，最终都只是一盏绿灯。
