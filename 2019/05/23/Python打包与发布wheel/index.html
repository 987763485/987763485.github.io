Python 打包与发布 wheel

本文属于《Python 学习路线》第 11/29 篇
上一篇系列目录下一篇

代码在本地跑通只是第一步，让它能被同事用一条 pip install 装上，是另一套工程。本文从一个空目录开始，走完打包、构建、上传、验证的全流程：先看清 sdist 与 wheel 的差别，再写出可用的 setup.py，处理版本号与依赖，最后把包发到 TestPyPI 与正式索引。文中包名统一用 example-pkg，仅作示例；虚拟环境与 requirements 的组织不在本文范围。

两种分发包：sdist 与 wheel

发布到索引上的成品有两种形态。源码分发包叫 sdist，扩展名是 .tar.gz；二进制分发包叫 wheel，扩展名是 .whl。“分发包”（distribution）与代码里的“包”（package）不是一回事：一个分发包可含多个包。

sdist 里装的是源码，外加 setup.py、MANIFEST.in 与被收集进来的文档和测试。好处是与平台无关；代价是安装时必须现场构建：pip 先解包，在临时目录执行构建脚本，再按结果把文件搬进 site-packages。这一步要求目标机器上有 setuptools、编译器和 C 库头文件。

wheel 则是预先构建好的 zip，目录布局已经是安装后的最终形态，只差解压到 site-packages 并处理脚本入口。pip 拿到 wheel 几乎不做计算，因此安装快、结果稳定，也不需要编译器。

优先发 wheel 的理由有四条。一是速度：含 C 扩展的包编译一次可能要几分钟，每次部署都重编，时间就不可控。二是环境：生产镜像往往只装运行时，没有 gcc 与 python3-dev。三是确定：同一份源码在不同机器上编出的二进制可能不同，wheel 把这份不确定性在构建机上解决一次。四是可审计：安装 wheel 不执行任意构建代码。

但 sdist 不能省。源码是事实来源，wheel 只是派生产物；少见架构与老旧系统没有对应 wheel，pip 会退回源码安装；下游要打补丁、审计代码，也得有 sdist。规范做法是两个都传，让 pip 按平台挑选。

wheel 的文件名怎么读

wheel 的文件名是一段结构化的信息，格式为“分发名-版本-Python 标签-ABI 标签-平台标签”，各段之间用连字符分隔：

第一行是纯 Python 包最常见的样子：py3 表示适用于 Python 3，none 表示不依赖特定 ABI，any 表示与平台无关。第二行的 py2.py3 表示同一份 wheel 同时兼容 Python 2 和 3，当时仍有不少库这么发。第三行则完全不同：cp37 指明 CPython 3.7，cp37m 是 ABI 标签，manylinux1_x86_64 是平台标签，说明其中的 .so 只能在符合 manylinux1 约定的 64 位 x86 Linux 上使用。

两个细节容易忽略。文件名里的分发名会把连字符换成下划线，example-pkg 写成 example_pkg，这是规范化规则，不是笔误；版本号则按 PEP 440 规范化，预发布版本 1.0.0rc1 原样保留。读懂文件名，就能判断手里的 wheel 能否装到目标机器上。

根目录名 example-pkg 是仓库名，可以随便起；包目录 example_pkg 才是 import 时写的名字。两者只差连字符与下划线，技术上允许完全不同，但对读者最友好。

包目录下必须有 __init__.py。Python 3.3 起有命名空间包，没有它也能导入，但发布场景仍建议用普通包：find_packages 靠它识别包。里面放版本号与少量导出名即可，不要写耗时逻辑，否则每次导入都要付代价。

tests/ 与包目录平级，不放进去。测试不该进 wheel，但可以进 sdist，方便别人复现问题。README.md 会被渲染成 PyPI 项目主页，值得认真写：一句话说明用途，一段安装命令，一段最小示例。LICENSE 不是可选项，没有许可证的包在不少公司里禁止引入。

setup.cfg 是元数据的另一个落脚点，适合放静态配置，例如 bdist_wheel 的 universal 标志。它与 setup.py 的分工要提前定好：同名元数据后读到的覆盖先读到的，容易只改一处。MANIFEST.in 只影响 sdist 的内容，写法很直白，一个模式一行：

还有一类文件不该入库：build/、dist/、*.egg-info/、__pycache__/。它们是构建产物，可由源码重新生成；.egg-info 里的 SOURCES.txt 还会缓存上一轮的文件列表，导致“明明加了文件却没打进去”。写进 .gitignore 即可，需要时用 python setup.py clean --all 清一遍。

setup.py 的关键字段

setup.py 本质是一个被构建工具执行的 Python 脚本，调用 setuptools.setup()，把元数据和打包规则当作参数传进去。下面这份可以直接用：

name 是分发名，也是 pip install 里敲的名字，发布后不要再改，否则等于换了另一个包。version 下文单独讨论。description 是一句话简介，会出现在搜索结果里，控制在六十个字符以内。

long_description 是项目主页的正文。读文件时用 open(..., encoding="utf-8")，不要依赖系统默认编码：Windows 上默认编码并非 UTF-8，中文 README 会直接让构建报 UnicodeDecodeError。long_description_content_type 指明格式为 Markdown，不写则按纯文本渲染，表格和代码块会变成一团。

packages 决定哪些目录进 wheel。手写列表容易漏，标准做法是 find_packages()：递归查找带 __init__.py 的目录，填入点分路径。exclude 用来挡测试目录，tests 与 tests.* 都要写，后者挡其下的子包。

install_requires 声明运行时依赖，安装本包时会一并解析。约束给下限再加上限比较稳妥，例如 requests>=2.21,<3，既避开有问题的老版本，也为大版本变化留出确认机会。代码里 import 的第三方包都要列进来，哪怕开发机上早就装好了。

python_requires 声明支持的 Python 版本，较新的 pip 会据此拒绝在不满足条件的解释器上安装，比装完再遇到语法错误友好得多。classifiers 是固定取值的标签，供检索与页面展示，不影响安装，但认真项目会填全：开发状态、目标用户、许可证、Python 版本、操作系统。

entry_points 里的 console_scripts 生成命令行入口。等号左边是命令名，右边是“模块路径:函数名”，函数不能带参数，返回值被忽略。安装后 pip 会在环境的 bin/（Windows 是 Scripts/）下生成包装脚本，敲 example-cli 就会调到 example_pkg/cli.py 的 main，比让用户记 python -m example_pkg.cli 自然得多。

package_data 与 include_package_data 负责包内的非 Python 文件。前者按“包名: glob 列表”指定，后者表示遵循 MANIFEST.in 的收集结果。两者都写是常见做法，但要记住 MANIFEST.in 只管 sdist，wheel 里的数据文件最终由这两项决定，这也是“文件没打进去”的根源。

attr: 和 file: 两个指令省掉了在 setup.py 里读文件、正则匹配的样板代码。2019 年这两种风格并存，没有哪一种是唯一正确的；团队里选一种，别在同一个项目里两处都改。

版本号：语义化、单点与不可重传

版本号遵循语义化版本的约定：不兼容改动升主版本号，新增向后兼容功能升次版本号，修 bug 升修订号。0.x 阶段可以认为接口随时会变，这也是把初始版本写成 0.1.0 的原因。

Python 侧还要满足 PEP 440 的写法。除了 1.4.2 这种标准形式，常见的有预发布 1.0.0rc1、1.0.0b2、1.0.0a1，开发版 1.0.0.dev3，以及 1.0.0.post1 表示修复打包问题但代码未变。排序规则是：1.0.0a1 < 1.0.0b1 < 1.0.0rc1 < 1.0.0 < 1.0.0.post1。预发布版本默认不会被 pip 选中，用户必须加 --pre 才会装上。

版本号只能有一个来源。常见做法是在 example_pkg/__init__.py 里写 __version__，让 setup.py 去读，或用 setup.cfg 的 attr: 指向它。两处各写一个，早晚出现 wheel 元数据是 0.1.0、包内还是 0.0.9 的错位。另外别在 __init__.py 里 import 重型依赖来算版本，构建环境未必装了它们。

最需要提前知道的一条规则是：同名版本不能覆盖。索引一旦接受了 example-pkg 0.1.0，这个文件名就永久占用，再传一次会被直接拒绝。写错元数据、漏了文件、README 渲染失败，都不能靠“删掉重传”解决，因为下游可能已经把 0.1.0 写进了锁定文件。正确做法只有一条：修好，递增版本号，发 0.1.1。也正因为如此，正式上传之前一定要在 TestPyPI 上演练一遍。

构建与检查

构建前把 setuptools、wheel、twine 升到当年主流版本。wheel 提供 bdist_wheel 命令，缺了它只能打出 sdist；setuptools 太旧则元数据不被索引接受，而这类问题要到上传时才暴露。

整个流程可以用一张图概括，后面的小节按这条链路依次展开：

    A --> C[wheel .whl]
    B --> D[twine check]
    C --> D
    D --> E[TestPyPI 演练]
    E --> F[正式索引]
    F --> G[用户 pip install]

命令跑完，dist/ 下应有两个文件；出现 .zip 或 .egg 说明工具链过旧。上传前用 twine check dist/* 过一遍，它会解析元数据并尝试渲染 README，缺字段或格式不合法直接报错，几乎零成本。

PyPA 不久前发布了 build 前端，命令是 python -m build，在隔离环境里分别构建两种分发包，避免本机已装的包影响结果。它要求在 pyproject.toml 里声明构建依赖（PEP 518）：

这里声明的只是“用什么工具来构建”，包名、版本、依赖仍写在 setup.py 或 setup.cfg 里。build 当时还算新工具，多数项目与 CI 脚本依旧以 setup.py 为主，两者产物应当一致。

发布：先 TestPyPI，再正式索引

TestPyPI 是独立索引，账号需单独注册，数据与正式库不互通。它的价值就在演练：同样的文件名与元数据先在这里走一遍，总比在正式库上撞墙好。

认证方面，PyPI 当时已开始提供 API token，形如 pypi- 开头的一长串，可按项目限定权限，用户名加密码也仍然可用。twine 用 --username __token__ --password <token> 传入，也可走 TWINE_USERNAME、TWINE_PASSWORD 环境变量。习惯配置文件的话，~/.pypirc 分 [testpypi] 与 [pypi] 两段填写 repository 与凭据。该文件必须 chmod 600，不能进版本库，也不能出现在 CI 日志里；CI 用密钥变量注入，token 只授予目标项目的写权限。

演练满意后，去掉 --repository-url 再传一次，就是正式发布。

含 C 扩展：manylinux 与 auditwheel

纯 Python 包打成 py3-none-any 就到处能装，含 C 扩展的包没这么轻松。wheel 里是编译好的 .so，依赖构建机的 glibc 版本与 CPU 架构。直接在普通 Linux 上构建，平台标签会是 linux_x86_64，这样的 wheel 传不上 PyPI，索引只接受承诺了兼容范围的标签。

manylinux 标准（PEP 513 定义的 manylinux1）解决的正是这件事：在足够老的系统上构建，只链接白名单内的系统库，保证 glibc 不低于某个版本、架构相同的机器都能用。实践上是在官方 manylinux Docker 镜像里构建，编译器与库版本都是固定的。

auditwheel 是配套工具。auditwheel show 列出 wheel 依赖的外部共享库，指出哪些不在白名单内；auditwheel repair 把越界的库（例如某个版本的 libssl）复制进 wheel 并改写标签，让它自给自足。代价是体积变大，同一个库在多个包里各带一份。

为什么值得折腾？对比源码安装就清楚了。用户机器上要有 gcc、Python 头文件与各库的开发包，安装时现场构建，几十秒到几分钟不等；任何一步失败，部署就卡住，报错还埋在几百行编译日志里。所以科学计算、数据库驱动这类包几乎都把 manylinux wheel 当成一等公民，并在 CI 里按 Python 版本与架构组合构建。

私有源与内网分发

内部包不进公共索引，走私有源。pip 的两个参数要分清：--index-url 替换默认索引，此后所有包都从私有源取；--extra-index-url 只是追加来源，公共包仍可来自 PyPI。前者更可控，团队通常让私有源代理 PyPI，配置里只写一条：

trusted-host 只在用 HTTP 或自签证书时需要，长期开着等于放弃证书校验。上传私有仓库仍是 twine，把 repository 指向内网地址即可；写权限按项目授予发布账号，读权限可放开给 CI 与开发机。

几个高频的坑

find_packages 漏包，多半是子目录缺 __init__.py；包内数据文件没进去，是只写了 MANIFEST.in 而 wheel 走 package_data；install_requires 漏依赖，在开发机上永远发现不了，只有干净环境才暴露；README 编码不对，构建时抛解码错误；在 macOS 上构建却指望 Linux 能用，平台标签不匹配；版本号重复上传，只能递增后重发。

小结

打包发布是一条不可逆的流水线：源码进 sdist，构建出 wheel，检查后先上 TestPyPI，验证通过再发正式索引。setup.py 的字段决定“装进去什么”，版本号决定“下游能否稳定复现”，twine 与干净环境验证决定“发出去的东西真能用”。把这几步固化成脚本，比记住命令更可靠。
