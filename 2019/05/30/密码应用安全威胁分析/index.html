密码应用安全威胁分析

密码应用的安全问题，很少以“算法被攻破”的形式出现，更多是参数选择、密钥保管、协议配置和运维习惯出了问题。本文从防御视角梳理五个层面的常见威胁，适合正在做定级备案、密评准备或安全整改的开发者阅读，读完后应能对照系统列出一份风险清单。

先建立威胁模型

密码应用要解决四类问题：机密性，数据被截获也读不懂；完整性，数据未被篡改；身份鉴别，确认对方或数据来源真实；不可否认性，发送方事后无法抵赖。四类目标对应不同的算法组合与失效方式。

威胁分五个层面：算法层看算法与参数是否站得住；实现层看代码调用是否正确、是否通过旁路泄露信息；密钥层看密钥全生命周期是否受控；协议层看握手、证书与版本协商是否会被绕过或降级；运维层看人、环境和流程是否抵消了前四层的努力。

五层相互放大：硬编码密钥会让算法加固失去意义，证书校验缺失会让精选套件形同虚设。先找最薄的一环，比堆砌措施更有效。

还要记住：算法本身没问题、用法错，比算法被攻破常见得多。MD5 碰撞需要相当算力，而“用 MD5 存口令”的错误，任何拿到数据库的人都能立刻利用。

算法层：过时算法与错误用法

过时算法为什么还在用

MD5 和 SHA-1 的碰撞攻击已被证明：攻击者可构造内容不同、摘要相同的消息。落到证书、软件包签名或电子合同上，破坏的是完整性。新系统不应再把它们用于口令、摘要或签名。DES 有效密钥只有 56 位；3DES 分组仍是 64 位，在大量数据下有分组碰撞风险；RC4 的密钥流存在统计偏差，在 TLS 中已被主流浏览器列为不安全。判断标准不是“还能不能用”，而是“有没有成本可接受的分析方法”。

密钥长度同样如此。RSA 1024 位已不适合新系统，至少应跟随当时的行业基线使用 2048 位；椭圆曲线选 256 位左右。低于基线就是明确的短板。

口令是特殊场景。MD5 加盐仍常见，但口令熵低，可离线枚举。应使用 bcrypt、scrypt 或 PBKDF2 等口令哈希算法，并为每个口令生成独立的盐。

分组模式与 IV 的坑

ECB 对每个分组独立加密，相同明文分组产生相同密文分组，攻击者不解密也能看出结构，不应被用于任何需要语义安全的场景。

CBC 要求 IV 随机、不可预测且每次更换；IV 固定会让相同明文产生相同密文，IV 可预测则可能被操纵第一个分组。CTR、GCM 对 IV 更严格：同一密钥下重复 IV 不仅泄露明文关系，还可能泄露认证密钥。工程上应把生成 IV 与加密绑定在同一个函数里。

CBC 还只提供机密性。攻击者可翻转密文分组，可控地改变明文。新系统应优先用 AEAD；必须用 CBC 时，采用先加密再 MAC，并让 MAC 覆盖 IV 和密文。

随机数：最容易被忽视的输入

密码学要求随机数“不可预测”，而不是“看起来乱”。以时间或固定种子初始化的普通随机函数不能生成密钥、IV、盐或会话标识。Python 的 random 适合模拟抽样，不适合安全场景。

Java 用 SecureRandom，Go 用 crypto/rand，Node.js 用 crypto.randomBytes。判断标准是文档是否明确声明“密码学安全”；只强调速度或分布均匀的，不适合承担安全职责。

算法层的结论是：不要自己发明密码学，也不要用“能跑通”当正确性标准。

实现层：侧信道与错误处理

实现层不改变算法的数学结构，而是利用运算过程泄露的信息。时序侧信道最典型：比较字符串时若发现第一个不同字节就返回，耗时便与“前缀匹配了多少字节”相关，攻击者可逐字节猜出 MAC 或令牌。缓存侧信道通过观察查表对缓存的依赖推断密钥。防护是让执行路径和数据访问与秘密无关：用常数时间比较，优先使用硬件指令或审查过的库，不在秘密数据上做分支。

填充预言（padding oracle）是另一类经典问题。CBC 解密后要检查填充，如果应用对“填充错误”和“MAC 错误”返回不同的错误码、页面或响应时间，攻击者就能把解密变成可反复询问的预言机，在没有密钥时逐块还原明文。防护是改用 AEAD，或先加密再 MAC、验证 MAC 前不泄露解密细节，并统一所有失败响应。

错误信息泄露常与填充预言相伴。异常堆栈、SQL 报错、密钥文件名返回给客户端，等于把内部结构告诉攻击者。生产环境应关闭详细错误，日志脱敏，对外只返回统一错误码。本节只讲原理与防护，不提供利用步骤。

密钥管理：从生成到销毁

密码应用有一个残酷的规律：算法再强，密钥泄露就等于没有加密。问题往往不出在技术，而出在习惯。

硬编码密钥最常见：密钥写进源码、配置文件、镜像或前端脚本，随后进入代码仓库，被复制到无数台机器。即使从代码里删除，历史提交和构建产物里仍然留着。密钥与数据同存也很普遍：加密密钥和数据库备份放在同一目录、同一块磁盘，拿到备份就同时拿到了锁和钥匙。没有轮换，则一把密钥用到底，一旦泄露，历史数据都无法补救。

权限分离和备份也容易失守。开发、运维、审计共用同一个密钥管理账号，等于取消相互制约；密钥备份未加密，或备份介质访问控制比生产还松，都会让前面的努力归零。销毁不彻底常被忽略：删除文件不等于擦除磁盘，快照、归档、日志、测试数据里可能仍有副本。

密钥全生命周期应有检查表：生成使用密码学安全随机源，长度符合基线；分发走受控渠道，必要时信封加密；存储放入专用密钥管理设施，按最小权限授权；使用禁止打印、禁止写入普通日志、禁止跨环境复用；轮换设定周期，并保证旧数据可解密；备份加密并与生产密钥分离；销毁覆盖所有副本，必要时密码销毁。每项都要有责任人和可核查记录。

协议与配置：TLS 只是起点

TLS 是密码应用最集中、也最容易配错的地方。2019 年生产环境仍以 TLS 1.2 为主，TLS 1.3 标准已发布并在推广，兼容性允许时可在新系统启用。套件应禁用 RC4、3DES、出口级和匿名套件，优先选择带前向保密的 ECDHE 与 AEAD 组合；版本与套件在服务端显式限定，不依赖客户端“通常会选安全的”。

证书校验是高频失守点。客户端必须验证证书链、有效期和主机名，证书的签名算法也应避开 SHA-1，但有些内部 SDK 为“先跑通”关闭校验，或接受自签名证书，为中间人攻击留了门。降级攻击干扰握手，迫使双方使用更弱版本或套件；服务端禁用老旧版本、客户端不提供降级开关是基本防护。HSTS 强制浏览器使用 HTTPS，能缓解 SSL 剥离，但依赖首次访问的可信性。双向认证适合服务间调用，代价是客户端证书的签发、轮换和吊销都要管理。

国密算法：边界比选型更重要

SM2 是基于椭圆曲线的公钥算法，SM3 是摘要算法，SM4 是分组密码。SM2 可用于签名、密钥交换和公钥加密，SM3 用于完整性校验，SM4 用于对称加密。常见的误解是把它们当成“换了名字的 RSA、SHA-256 和 AES”，直接套用旧代码的调用习惯。

SM2 的签名与加密必须区分。签名用私钥生成、对方用公钥验证，解决身份鉴别与不可否认；加密用对方公钥、对方用私钥解密，解决机密性。两件事在工程上应使用不同的密钥对，不能把签名密钥直接拿来加密。SM2 签名需要高质量随机数，随机数重复或可预测会危及私钥，这与 ECDSA 类似。SM4 使用 CBC 等模式时同样需要随机 IV，不能因为是国密就跳过模式与随机数要求。国密 TLS 的兼容性是落地难点：不同浏览器和操作系统支持程度不一，通常需在网关层适配，并覆盖客户端版本测试。

运维与检测：把威胁找出来

运维层面的问题最不起眼，却最容易把技术防护清零。开发或测试环境直接使用生产密钥，测试人员、外包人员和 CI 日志都可能接触；日志打印完整手机号、身份证号、银行卡号、口令和令牌；数据库备份未加密，或加密密钥与备份放在一起；第三方组件自带弱算法、示例密钥或关闭校验的默认配置。这些问题不会在单元测试里报错，只会在出事后的溯源里出现。

检测要把人工审查和工具结合。代码扫描重点关注硬编码密钥、可预测随机数、危险 API，例如 ECB、MD5、DES、RC4，以及关闭证书校验的开关；配置核查关注 TLS 版本、套件、证书链和 HSTS；密钥清单记录每把密钥的用途、归属、存放位置、轮换周期和备份情况；渗透测试（在授权范围内）中的密码相关检查项包括证书有效性、协议与套件、错误信息、令牌随机性和密钥可获取性。整改记录要落到具体文件和配置项。

案例分析：三重错误叠加

某内部系统要加密存储手机号，开发人员选择了 AES，但主流程用 CBC 且 IV 固定全零，批量导出模块为了省事改用 ECB，密钥则放在配置文件中随代码提交进了仓库。代码审查时，AES/ECB 与硬编码的 IV 首先引起注意；导出密文后发现相同手机号产生相同密文，不同记录之间还能看出重复的分组结构。由于手机号取值范围有限，攻击者拿到密文后可离线枚举比对，恢复明文；仓库历史中的密钥，又能解密其他使用同一把密钥的数据。

影响不止手机号。固定 IV 让 CBC 下的相同明文得到相同密文，ECB 则直接把分组结构暴露出来；硬编码密钥让“拿到代码”约等于“拿到解密能力”。整改分三步：换成带认证的 AES-GCM，每次生成随机 IV 并与密文一起保存；把密钥迁出代码和配置文件，交给专用密钥管理设施，按应用授权并定期轮换；清理仓库历史中的密钥，重新加密存量数据，补充代码扫描规则。这个案例没有高深算法问题，三个错误都是工程习惯问题。

长期关注：量子计算

量子计算对 RSA 和椭圆曲线公钥算法的潜在影响，是一个需要长期关注的议题。就 2019 年的工程现实而言，它仍处于研究和早期探索阶段，不构成可落地的现实威胁，也不应该成为当下盲目替换算法的理由。更务实的准备是保持算法敏捷性：让算法标识、密钥长度和协议版本可配置、可升级，关注标准化进展，在迁移条件成熟时能平滑切换。

小结

密码应用的威胁分布在算法、实现、密钥、协议和运维五个层面，任何一层的短板都可能让其他层的加固失效。算法层要避免过时算法、错误模式和弱随机数；实现层要用常数时间比较、统一的错误处理和 AEAD 模式；密钥管理要覆盖生成、存储、使用、轮换、备份和销毁的全生命周期；协议层要限定版本与套件、严格校验证书；运维层要把密钥、日志、备份和第三方组件纳入日常检查。与其追求“用了什么算法”，不如先回答“密钥在哪里、谁能拿到、出了事能不能发现”。
