GORM 关联查询与预加载

本文属于《Go 语言与工程》第 64/78 篇
上一篇系列目录下一篇

一个列表接口只返回 20 条订单，日志里却留下 21 条 SQL；等数据量涨到一百条，慢查询监控开始报警，而索引其实一直都在。这类问题多数不是数据库写错了，而是 ORM 取关联数据的方式错了。本文从 N+1 讲起，把 GORM 1.x 的四种关联定义、Preload 与 Joins 两条预加载路径、关联写入与事务边界、软删除和 Hook 在关联场景下的连带影响依次拆开。读完你应该能算清一次请求该发几条 SQL，并知道每条 SQL 上该带什么条件。本文只讨论关联与查询，连接池参数与单表 CRUD 的基础留给同系列的其他篇目。

它的代价不只是”多几条 SQL”。每一次查询都要单独做一次网络往返、一次语句解析和一次执行计划生成；在 MySQL 侧，这些短小的查询通常命中索引，单条并不慢，但它们在连接池里被串行占用，一条慢一点就拖着整页变慢。更麻烦的是，开发机上只有三条测试数据，永远看不出问题，直到线上第一页有一百条记录。

GORM 1.x 的四种关联

约定优于配置：外键到底放在哪张表

GORM 1.x 把关联分成四类，判断依据只有一条：外键字段在哪张表上。这条规则决定了你写 Company Company 还是 CompanyID uint，也决定了预加载时它生成的 WHERE 条件长什么样。

flowchart LR
    Company -->|1:N| User
    User -->|1:1| Profile
    User -->|1:N| Order
    Order -->|1:N| OrderItem
    User ---|N:M 经 user_roles| Role
  • belongs to：外键在声明关联字段的这一方。User 里写 Company Company，外键就是 User.CompanyID，值来自 companies.id。
  • has one：外键在对方表。User 里写 Profile Profile，外键是 profiles.user_id。
  • has many：同样是外键在对方表，只是字段是切片。User.Orders []Order 对应 orders.user_id。
  • many2many：两张表都不放外键，靠一张中间表连起来。User.Roles []Role 配合 gorm:"many2many:user_roles;"，中间表默认有 user_id 和 role_id 两列。

默认命名规则很简单：外键列名等于”关联类型名 + 主键名”，即 CompanyID、UserID；被引用的列默认是对方的主键。只要遵守这套约定，结构体里一个标签都不用写。

有一处容易被误解：结构体里有 CompanyID 字段，并不等于数据库里有外键约束。1.x 的迁移主要负责建表、补列和补索引，外键约束建议显式声明，否则”关联”只是 ORM 层面的约定，删除公司时数据库不会替你拦下任何东西：

用标签改写约定

真实项目里，表结构很少完全按约定长。老系统的订单表可能用 buyer_no 而不是 user_id 关联用户，用户表用 member_number 而不是主键做业务键。这时候要改两处：子表用哪一列做外键，父表用哪一列被引用。

has one 与 has many 的写法一致，只是字段类型不同。belongs to 用的是同一对标签，但两侧角色互换：foreignKey 指本方结构体里的字段，association_foreignkey 指对方表里被引用的列。

标签键名在 1.x 里不区分大小写，foreignkey 与 foreignKey 是同一个意思，社区文章里两种写法都能见到，不必纠结。真正需要小心的是”多个关联指向同一张表”：一张订单既有下单人又有操作员，两个字段都指向 users，如果都按默认约定取名，两组关联会争抢同一个 user_id 列，最后只有一个能取到数据。正确做法是各自配一个独立外键列，并用标签显式指出来。

多对多：中间表也是一张表

many2many 的默认中间表名是 user_roles，两列分别是 user_id 和 role_id。它没有自己的模型，也不出现在你的结构体里，但它在数据库里是实打实的一张表，需要主键或唯一索引来防止重复：

顺带对比一下 Related：它面向单条记录，需要你先有主键，用法是 db.Model(&order).Related(&order.Items)；Preload 面向集合。两个 API 都能取关联，但在列表场景里用 Related 基本等于手写 N+1。

还有一个隐式预加载的开关，db.Set("gorm:auto_preload", true) 会把当前模型的所有一级关联全部预加载。它看起来省事，实际上很危险：模型上加一个新关联，所有用这个模型的地方都会悄悄多一条 SQL，而且无法按场景裁剪。笔者只在一次性脚本里用过它，业务代码里一律显式列出关联名。

条件里的列名建议带上表名，比如 orders.status。一旦关联查询里出现了 JOIN（例如你又叠加了 Joins），不带表名的列会直接报 ambiguous column，这类错误在测试数据少的时候同样看不出来。

限制也同样明确。第一，一对多不能用。Joins("Orders") 在 1.x 里不支持，原因不复杂：一百个用户每人三张订单，JOIN 出来是三百行，主表字段被重复三百次，GORM 没有可靠的办法把这些行再折叠回切片，还容易把分页和计数算错。第二，字段扫描依赖别名。如果你自己写了 Select，又只写了 users.*，被关联字段就永远是零值，而且不报错；反过来，两张表都有 id、name、created_at 时，不带别名的 Select * 会让同名列互相覆盖。第三，LIMIT 作用在连接后的结果上，一旦不小心 JOIN 了会膨胀的表，一页 20 条可能只返回 5 个不同的用户。

和 Preload 的取舍可以归纳成一句话：要展示数据，用 Preload；要拿关联表的列参与筛选和排序，用 Joins。展示的场景占绝大多数，所以 Preload 应该是默认选择，Joins 是带着明确目的才用的优化手段。两者混用是最常见的浪费：Preload("Company").Joins("Company") 会发出两条 SQL，第二条 JOIN 的结果被第一条预加载覆盖，除了增加数据库压力没有任何收益。

关联写入与 Association

创建时自动保存关联

Create 不只插入主表。1.x 默认会把结构体里已有的关联一起保存：belongs to 的关联对象会被先插入，has many 的切片逐条插入并回填外键。

这个默认行为省了很多手写代码，也制造了不少事故。比如从请求体直接绑定结构体时，客户端多传一个 Company 字段，就会在 companies 表里凭空多出一条记录；又比如只想更新用户昵称，顺手 Save 了整个对象，关联订单被一并更新。控制手段有两个：在字段上关掉自动保存，或者在这一次写入上关掉。

事务：边界画在哪里

一次写操作往往同时改主表和关联表，两步之间出错就会留下半条数据。事务的边界应该覆盖”这两个写要么都成，要么都不成”的最小集合，而不是整个请求处理函数。

软删除：看不见的行仍在表里

DeletedAt 的语义

gorm.Model 里的 DeletedAt *time.Time 是指针，NULL 表示未删除，有值表示删除时间。只要模型带了这一列，GORM 就会给所有查询自动补上 deleted_at IS NULL，Preload 生成的子查询同样会补。

唯一索引与软删除的冲突

这是软删除最经典的坑。用户表 email 上有唯一索引，用户注销后记录只是被打了时间戳，索引项还在，同一个人想用原邮箱重新注册就会撞唯一键。直觉上的补救是建复合唯一索引 (email, deleted_at)，但在 MySQL 里这不管用：唯一索引对 NULL 的处理是”多个 NULL 视为互不相同”，而未删除的行 deleted_at 全是 NULL，于是活跃用户之间反而可以重复。

可行的方案有三类。第一，删除时把唯一列改写，比如 email = concat(email, '#deleted#', id)，把冲突转移到已删除的行上，代价是列语义被污染。第二，不用时间戳表达删除，改用 is_deleted tinyint 配合复合唯一索引 (email, is_deleted)，删除时把标志位置成主键值或其他唯一值，活跃行固定为 0。第三，热数据表只放活跃记录，删除即物理删除并归档到历史表，唯一索引自然干净。三种方案各有代价，选哪一种取决于这张表要不要支持”恢复”。

关联查询里的软删除

软删除在关联场景下有两个反直觉的结果，都和查询路径有关。用 Preload 时条件会带到子查询上，已删除的子记录不会出现，这是符合预期的。用 Joins 时，被 JOIN 进来的表不会自动补 deleted_at IS NULL，主表条件加了、关联表没加，于是一个已删除的公司仍然会以”正常公司”的身份出现在用户信息里。排查时如果发现”这条数据明明删了还能查到”，先看它是走 Preload 还是走 Joins。

另一个结果是级联。父记录软删除后，子记录并没有被标记，单独查子表仍然能查到它们；只有从父表出发的查询才会因为父表条件而”看不到”。这在统计报表里会表现为总数对不上：按订单表统计的销售额包含了已注销用户的订单。要不要级联软删除子记录，是一个业务决策，需要显式写在删除逻辑里，不能指望 ORM。

这段代码在单条查询时只是多一条 SQL，看起来无害；一旦列表页 Preload("Items") 取回一百条明细，AfterFind 就跟着触发一百次，辛苦消灭的 N+1 又原样回来了，而且藏在模型层，光看 handler 根本发现不了。判断方法依旧是数日志：预加载本应只增加固定条数，如果 SQL 条数随记录数增长，先查模型上有没有 AfterFind。

第二个，Hook 里用包级 db 而不是当前事务。Hook 拿不到调用方的 tx，写操作就走另一条连接，于是主流程回滚了、Hook 里的写入留下了。1.x 的 Hook 可以通过 scope *gorm.Scope 参数拿到当前连接，复杂项目里应该走这条路；最省事的规避方式是不要在 Hook 里写库。

第三个，用绕过 Hook 的 API 更新字段，导致 Hook 维护的不变量失效。UpdateColumn 与 UpdateColumns 会跳过 Hook 与自动时间戳，用它改 status 时，BeforeSave 里的规范化就不会执行。这类不一致往往在几周后才以”某些行的数据格式不对”的形式暴露。

性能：少查、少取、分批

关联查询的性能优化有一条清晰的主线：先保证 SQL 条数是常数，再削减每条 SQL 搬运的列数和行数，最后处理大结果集。

只取需要的字段。 Select 能显著减少网络传输与扫描，但在关联场景里有一个硬约束：主表必须选出主键和预加载所需的外键列，否则 Preload 拼不出 IN 条件，关联会静默为空。

分页要克制。 一页 20 条与一页 2000 条，预加载的 IN 列表长度差一百倍，内存里挂的对象也差一百倍。深翻页用 OFFSET 越翻越慢，改成基于主键的游标更稳：

大结果集分批处理。 1.x 没有开箱的批量迭代器，需要自己写游标循环，关键是每批都带上预加载，且不要在一次循环里累积结果：

内存要按”行数乘层数”估算。 预加载不是流式的：一批 1000 条订单，每条 20 条明细，就是两万个结构体同时驻留，再加上反射分配的开销。嵌套两层时这个数字还要乘。与其调大页大小，不如把接口拆成”列表只给摘要、详情单独请求”，让每次请求的数据量可控。

用 Debug() 看真实 SQL，不靠猜。 优化的依据是日志里的语句、EXPLAIN 的执行计划，以及真实压测的响应分布；凭”感觉这条 SQL 应该很慢”去加索引，通常只是把问题挪了个位置。本文不给具体耗时数字，因为同一段代码在不同机器、不同数据分布下的表现差异极大，只有你自己环境里的日志和 EXPLAIN 算数。

常见坑与排查顺序

前文散落的问题，这里按”症状、原因、处置”收拢成一份清单。

  • 关联名拼错，接口返回空数组。Preload("Orderz") 这类错误编译期发现不了，运行时也不一定报错，更常见的结果是关联字段保持零值。处置：在测试里断言关联已填充，而不是只断言主表条数。
  • 既写了 Preload 又写了 Joins，SQL 条数比预期多一条。原因是被 JOIN 的表在预加载里又查了一遍。处置：同一次查询里二选一。
  • 用 Joins 预加载，已软删除的关联记录仍然出现。原因是软删除条件只加在主表上。处置：在 Where 里显式补关联表的 deleted_at IS NULL，或改用 Preload。
  • Association 的调用看起来成功，但数据没变。多半是主键为空（记录还没 Create），或者关联值取自另一个未保存的对象。处置：先落库拿到 ID，再操作关联，并检查 Association(...).Error。
  • 事务里混用了 db 与 tx，出现锁等待超时或读到旧值。处置：把 db 从闭包里拿出来，回调内一律用 tx。
  • Preload 里加了 Limit，结果不符合”每组取前 N 条”的预期。原因是预加载是一条批量查询。处置：改成按父记录分批查，或写原生 SQL。
  • 主表 Select 漏了外键列，预加载静默为空。处置：Select 至少包含主键与全部关联外键。

排查顺序建议固定下来：先开 Debug() 数 SELECT 条数，确认是常数还是与记录数同增；再看每条 SQL 是否带上了预期条件（软删除、状态、分页）；最后才用 EXPLAIN 看索引。顺序反过来，容易在索引上花一天，却发现根因是循环里少写了一个 Preload。

小结

关联查询的复杂度不在语法，而在”一次请求究竟发几条 SQL、每条语句取多少行”。Preload 是默认答案，它把 N+1 压成与记录数无关的常数条 SQL，嵌套用点号路径，条件写在关联查询上；Joins 是带目的的手段，只适用于 belongs to 与 has one，且要接受字段别名、分页与软删除上的额外约束。写入侧要记住 Create 会连带保存关联、Association 需要主键、GORM 没有隐式级联；事务里一律用 tx。软删除则改变了三件事的语义：数据库级联不再触发、唯一索引仍被占用、Joins 不会替你过滤已删行。把这些边界写进代码评审清单，比事后追查一条慢 SQL 划算得多。
