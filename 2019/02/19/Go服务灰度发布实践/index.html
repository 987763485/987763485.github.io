Go 服务灰度发布实践

本文属于《Go 语言与工程》第 62/78 篇
上一篇系列目录下一篇

灰度发布要解决的不是“怎样把新版本部署上去”，而是“怎样用最小的代价确认新版本可以承担全部流量”。本文从分流维度、Go 服务内的实现、数据兼容、观测判定与回滚几个方面，拆解一套可以落地的灰度流程，并用一个虚构的订单服务走完从 5% 到 100% 的全过程。适合已经能把 Go 服务跑起来、准备第一次独立负责线上发布的读者。

一、灰度发布解决什么问题

很多团队把发布当成一个部署动作：镜像构建成功、容器起来、健康检查通过，就算完成。真正的事故往往发生在健康检查之后——新版本能启动，却在真实流量下暴露出空指针、慢查询、序列化不兼容或者下游超时。灰度发布的价值，是把“全部用户一起承担变更风险”改成“先让一小部分用户承担，确认之后再扩大”。

具体来说，灰度要实现三个目标。

第一是降低发布风险。任何一次代码变更都可能引入缺陷，区别只在于缺陷被多少用户遇到。灰度把新版本先暴露给小比例流量，即使失败，受影响的请求数也被限制在一个可以计算的范围内。这个范围就是常说的爆炸半径（blast radius）。5% 的流量出错和 100% 的流量出错，对客服、对收入、对品牌的影响完全不是一个量级。

第二是验证新版本。测试环境可以验证功能，却很难复现生产的数据分布、下游延迟、缓存命中率和用户行为。灰度让新版本在真实依赖和真实数据上运行，观察错误率、延迟长尾、资源饱和度和业务指标是否与旧版本一致。它验证的不只是“代码对不对”，还包括“容量够不够”“依赖扛不扛得住”。

第三是建立可回退的决策点。灰度把一次大发布拆成若干次小决策：5% 时要不要继续，25% 时要不要继续，50% 时要不要继续。每个决策点都应当有明确的指标、观察窗口和负责人。没有决策点的灰度只是“慢慢部署”，出了问题仍然靠人临时拍脑袋。

灰度、蓝绿、金丝雀与 A/B 测试的边界

这几个词经常被混用，实际关注点并不相同。

策略 流量形态 主要关注点 回退方式
蓝绿部署 两套完整环境，一次性切换全部流量 环境一致性、切换速度 把入口切回旧环境
金丝雀发布 少量真实流量进入新版本，逐步扩大 新版本指标是否正常 摘除新版本实例或回切流量
灰度发布 按权重、用户、租户、地域等维度逐步放量 整个过程的风险控制与数据兼容 回切流量、回滚配置
A/B 测试 两组用户同时使用不同业务策略 业务指标差异是否显著 结束实验，保留胜出策略

可以这样理解它们的关系：灰度发布是一个工程过程，金丝雀是灰度中最常见的一种放量方式，蓝绿是部署形态上的一种全量切换方式，而 A/B 测试关注的是产品假设，不是代码正确性。A/B 测试中两个版本都可能是“正常”的，只是业务效果不同；灰度发布中旧版本是基线，新版本必须先证明自己不比基线差。

还有一个常见误解：既然有预发环境，为什么还要灰度？预发环境缺少真实流量，也缺少真实的数据倾斜。某些 bug 只在特定租户的大订单、特定省份的地址库或者缓存冷启动时出现，预发很难覆盖。灰度不是测试的替代品，而是最后一道生产验证。

二、分流维度与一致性

灰度首先要回答一个问题：一个请求应该进入新版本还是旧版本？这个判断依据就是分流维度。维度选得好，灰度可控且可解释；维度选得不好，用户会在两个版本之间来回跳，指标也会被污染。

按权重分流

按权重是最直观的方式：新版本承接 5% 的请求，旧版本承接 95%。实现上可以是在网关层随机选择，也可以是在服务内生成一个随机数再比较阈值。

它的优点是实现简单、放量平滑，适合无状态、可重试、单次请求即可完成的服务，例如图片处理、内容渲染或者内部计算接口。缺点也很明显：同一个用户的连续请求可能一会儿落到旧版本、一会儿落到新版本。若两个版本的返回结构或交互流程有差异，用户会看到页面闪烁、购物车数量跳变，甚至重复提交。

因此，按权重适合“版本差异对用户不可感知”的场景，或者只作为服务间调用的粗粒度分流。面向终端用户的核心链路，通常要把权重和稳定身份结合起来。

按请求头分流

请求头分流常见于测试账号、内部员工和合作方联调。网关识别 X-Release: canary，把请求转发到灰度实例；普通用户不带这个头，继续走稳定版本。

这种维度非常精确，适合小范围 dogfooding。但要注意两点。第一，客户端可以伪造请求头，边缘网关必须显式删除外部传入的同名头，再由可信入口重新写入，否则任何用户都能把自己切到灰度版本。第二，请求头只在单次请求内有效，如果它由前端根据某个开关动态添加，仍然可能出现同一用户在不同页面命中不同版本的情况。

请求头更适合“人”的灰度，而不是“流量比例”的灰度。它通常与白名单配合，作为放量前的第一步。

按 cookie 或用户 ID 哈希

这是面向 C 端业务最常用的方式。取用户 ID、登录态中的稳定标识或者匿名设备号，计算哈希，再映射到 0 到 99 的桶号。桶号小于放量比例的进入新版本，其余留在旧版本。

当放量比例从 5% 提高到 25% 时，原来落在 0 到 4 号桶的用户仍然在新版本，新增的是 5 到 24 号桶。这个性质很重要：已经验证过的那批用户不会被重新洗牌，新增用户则是从未灰度过的群体，风险仍然可控。相比之下，如果每次都用 hash(uid) % 当前实例数 来选实例，实例数一变，几乎所有映射都会改变。

哈希的输入必须是稳定标识。用户 ID 最好，登录态里的 openid 次之；匿名场景可以用设备 ID 或长期 cookie。不要用 IP：移动网络出口会变，办公室 NAT 会让一群人共享同一个地址，家庭宽带重新拨号也会换 IP。用 IP 做键，用户今天在灰度组、明天在对照组，体验和统计都会失真。

还有一个细节是盐值。灰度期间哈希盐必须固定，不能每天换，也不能把版本号拼进键里。盐一变，分桶结果整体重排，等于把灰度用户重新随机了一次。

按地域或租户分流

面向企业的服务通常有天然的分组：租户 ID。把某个租户整体切到新版本，既能控制影响面，又便于和客户沟通。租户分流通常由网关或服务内的鉴权中间件完成，因为租户 ID 来自登录态。地域维度则适合验证与机房、时延、地址库相关的改动，例如先在某个省份放量，观察当地的下单成功率和配送时效。

地域分流的实现通常在网关：根据用户 IP 解析省份，再查一张地域到版本的映射表。这张表要能热更新，否则每次调整都要改配置、发版。地域维度的风险是边界不稳定，IP 库更新、用户漫游、CDN 回源都可能让判断漂移，所以它更适合“按区域逐步开放功能”，而不是严格的实验分组。

租户维度则要注意权限和数据隔离。把租户 A 切到新版本后，如果新版本写入了只有新代码能读的字段，租户 A 的数据在回滚后可能无法被旧版本正确处理。这就是下一节要展开的数据兼容问题。

一致性哈希的简单实现

按用户哈希取模适合“按比例放量”，但当我们需要把用户稳定地映射到某一组实例时，普通取模就不够了：增加或摘除一个实例，大量用户会被重新分配，缓存命中率骤降。一致性哈希把节点和键都放到同一个环上，键顺时针找到的第一个节点就是归属节点；增删节点只影响环上相邻的一段。

每个物理节点放 100 到 200 个虚拟节点，可以让数据分布更均匀。Add 之后需要重新排序，生产环境通常在初始化时一次性建环，变更时重建并原子替换，而不是在请求路径上加锁排序。

要区分两种用途：按比例灰度用的是“阈值分桶”，它保证放量单调增加；一致性哈希解决的是“键到实例”的稳定映射，常用于分片缓存、会话粘滞或者按用户归属选择后端。两者可以叠加，但不能指望一致性哈希自动解决版本兼容。

分流逻辑放在哪里

分流可以放在三个位置，各有取舍。

网关层最省事。Nginx 或统一 API 网关能看到路径、域名、请求头和 cookie，按权重或 cookie 做路由不需要改动业务代码，回切也只是改一条规则。缺点是网关不一定理解业务身份，匿名用户和登录用户的关联、租户与账号的关系，往往只有服务自己知道。

服务内中间件最灵活。Go 服务可以在中间件里读取用户 ID、租户 ID、实验配置，做更细的判定，还能把版本号写进日志和追踪。缺点是每个服务都要实现一遍，语言栈不统一时容易各自为政。

服务网格把分流下沉到 Sidecar，理论上与语言无关，规则统一由控制面下发。它适合服务数量多、语言杂的团队，但会引入额外的网络跳数、Sidecar 资源开销和一套新的运维对象；没有相应的平台能力时，排查一次路由问题可能比改 Nginx 配置更费时间。本文只把它作为对照，具体落地仍以网关加服务内中间件为主。

三、从网关到服务内的落地

Nginx：实例权重与版本分流

Nginx 里有两个层面的“权重”，很容易混淆。upstream 中的 weight 是同一组后端实例之间的负载比例，不是版本比例；要让 5% 的请求进入另一组实例，需要 split_clients 按 key 做哈希分桶。下面的配置把用户 cookie 中的 uid 作为键，5% 进入灰度 upstream，其余进入稳定 upstream：

split_clients 对键做哈希后按百分比划分区间，同一个 uid 会稳定落在同一组；把 5% 调到 25% 时，原来的 5% 仍在灰度组，新增的是后续区间。若 cookie 缺失，所有匿名请求会共享空键，全部落进同一个桶，因此网关要尽早种下第一方匿名标识，或者在键里拼上设备号。

proxy_next_upstream 默认只对幂等请求做重试；不要为了“提高成功率”加上 non_idempotent，订单创建一旦超时重试，可能重复下单。

调整比例不必改代码，但 Nginx 的 upstream 是启动时加载的。常见做法是配置中心保存比例，机器上的 agent 渲染模板、执行 nginx -t 校验，再 nginx -s reload。reload 会启动新 worker、旧 worker 处理完在途请求后退出，配合 worker_shutdown_timeout 可以避免长连接被硬断。

Go 中间件：按 header 与 cookie 选版本

当两个版本在同一个进程内以 feature flag 的形式共存时，可以在中间件里完成选择；当两个版本是独立部署时，中间件更多是读取网关写入的版本标记，保证日志和下游调用带上一致的标签。

这段代码有三个安全边界。X-User-Id 必须由网关覆盖写入，不能直接信任客户端；Percent 必须在配置加载时校验在 0 到 100 之间，非法配置应回退到 0 而不是全量；Salt 在一次发布周期内不能变。配置更新通过 atomic.Value.Store 原子替换，读路径没有锁。

中间件也可以直接调用 r.Cookie("uid") 读取 cookie；经过网关时优先使用注入的 header，避免重复解析。

如果灰度版本是单独部署的，通常在入口按 cookie 路由，服务内只做两件事：把 X-Release-Version 继续传给下游，以及把它写进日志和追踪。不要在每一层重复做百分比判断，否则 5% 经过三层调用，实际触达灰度的请求比例会接近 15%，而且各层判断可能不一致。

配置中心：把比例变成可审计的配置

灰度比例不适合硬编码在镜像里。一次发布要经历 5%、25%、50%、100% 多个阶段，每次都重新构建镜像既慢又容易出错。更常见的做法是把比例、盐值、白名单放进配置中心，服务启动时拉取并落本地缓存，运行时订阅变更。

配置下发的要点是失败安全：配置格式错误、字段缺失或者连不上配置中心时，服务应当停留在上一次确认过的配置，首次启动则默认 0%。每次变更都要记录操作人、时间、旧值和新值，事后复盘时才能解释“为什么 25% 停留了四十分钟”。

服务网格的对照

服务网格把路由规则从应用进程里拿出来，交给 Sidecar 执行，理论上可以做到语言无关、规则统一。按 header、cookie 或用户 ID 做一致性哈希路由，确实是它的强项。但代价是每个 Pod 多一个容器、每次调用多一跳，路由规则、证书轮换、控制面升级都需要专人维护。2019 年这套方案更适合服务数量多、语言栈复杂的平台型团队；只有几个 Go 服务时，Nginx 加中间件已经够用。

四、数据兼容：比流量更难的部分

流量可以在几秒内切回去，数据不行。灰度期间新旧版本同时读写同一套 MySQL、Redis 和消息队列，只要 schema、字段语义或者缓存格式不兼容，回滚就会从“切流量”变成“修数据”。所以数据库变更要采用 expand-contract 模式，把一次破坏性变更拆成四个可回滚的阶段。

expand-contract 的四个阶段

第一阶段是扩展，只加不删：新增可空字段、新表或者新索引，旧代码完全不受影响。第二阶段是双写与回填：新代码同时写新旧字段，后台任务分批把历史数据补齐。第三阶段是切换读：新代码优先读新字段，读不到时回退旧字段，旧代码仍然能正常运行。第四阶段是收缩：确认没有旧版本实例、没有旧数据依赖之后，再停止写旧字段并删除它。切流量必须放在双写生效之后、收缩之前；切读可以与切流量同步，但切流量前要确认旧版本仍能读新数据。

第一步就把列设成 NOT NULL 且没有默认值，是最常见的错误：旧版本执行插入时不知道该填什么，会立刻报错。回填也不要指望一条 UPDATE 改完整张表，大表上它会长时间占用锁和 IO，应该按主键分批，记录进度，可中断可重试。

Go 侧要特别注意 NULL。旧数据在新字段上是 NULL，直接 Scan 到 string 会报错，这个错误往往只在读取历史订单时出现，测试环境的数据太干净，根本复现不了。

判断“新旧版本能同时读写”的标准很具体：新代码能读旧行，旧代码能读新行；没有改列名，没有改枚举含义，没有依赖 SELECT * 的列顺序；旧版本写入时不会违反新约束。收缩必须等到全量发布并度过回滚窗口之后，否则旧镜像一旦回切，就会读到已经被删掉的列。

消息格式与缓存

消息队列的兼容原则与数据库类似，但多了一个时间维度：灰度期间产生的消息，可能在几分钟后才被消费，那时消费者可能已经切回旧版本。因此新增字段要可选，消费者要忽略不认识的字段，生产者在过渡期保留旧字段；不要删除字段、改变字段类型或者复用旧字段名表达新含义。消息里带一个 schema_version，可以让消费者在兼容逻辑变复杂时做出判断。

缓存要按版本隔离 key，例如从 order:detail:%d 改成 order:detail:v2:%d。新旧版本各写各的 key，至少不会互相覆盖成对方无法解析的格式。代价是新版本刚上线时缓存全冷，数据库压力会上升，放量前要做一次预热，或者让新版本在未命中时回源并异步回填。不要在不改 key 的情况下改变序列化格式，否则回滚后旧版本读到新格式，整个缓存层都会报错。

五、观测与判定

灰度能不能继续，不能靠“看起来还行”，要靠指标。至少要看四类：错误率、延迟、饱和度和业务指标。错误率要同时统计技术错误与业务错误，HTTP 500 只是其中一部分，下单失败、支付回调验签失败同样要算进去。延迟要看 P95 和 P99，平均值会掩盖长尾。饱和度看 CPU、内存、goroutine 数、连接池使用率和队列积压。业务指标则是最贴近用户的那一层，例如下单成功率、支付转化率、客单价。

比较方法比指标本身更容易出错。灰度组和对照组必须在同一时间窗口内比较，因为流量有明显的早晚高峰；不能拿灰度组今天的数据对比稳定组昨天的数据。分流键要稳定，否则两组用户画像不同，比较结果没有意义。样本量可以用两个比例的近似公式估算：每组所需样本约为 16 × p × (1 - p) / δ²，其中 p 是基线错误率，δ 是希望检测到的最小差异。若基线错误率为 1%，希望发现 0.5 个百分点的上升，每组大约需要六千多个请求；灰度只承接 5% 的流量时，这意味着要观察足够长的时间，不能看了五分钟就下结论。

所有观测数据都要带版本标签。响应头写 X-Release，日志里加 release 字段，追踪的 span 上打同一个标签，指标按版本聚合。否则事故发生时，你只能看到整体错误率上升，却不知道是哪一批实例贡献的。

判定阈值要事先写进发布单，而不是事后解释。例如错误率超过基线的两倍并持续十分钟、P99 超过基线 50%、连接池使用率超过 80%，任一条件满足就暂停放量。阈值不必追求普适，但必须让值班同学在夜里也能照着执行。

六、回滚：把决定提前

回滚的第一步是止损，不是查原因：把灰度比例归零、关闭白名单、把入口权重切回稳定组。流量回切通常只需要几秒到几分钟，这段时间里新版本仍在运行，正好保留现场。不要急着删掉灰度实例，日志、goroutine 栈、CPU profile 和出问题的请求样本都在里面。

第二步是判断问题属于代码还是数据。代码问题可以回退镜像或关闭开关；数据问题不能假装没发生。如果新版本已经写入了旧版本无法理解的字段、消息或者缓存格式，直接回退可能让旧版本在读取时大面积报错。这时应当前向修复：先让旧版本具备兼容读能力，再补数据、修代码，然后重新发一个版本。expand-contract 的价值就在这里，扩展阶段的设计让回滚始终有一条安全路径。

回滚有三根杠杆：流量、配置、镜像。三者要能独立操作，不能全都依赖同一个发布系统。旧镜像至少保留一个回滚窗口，标签使用 git sha 或镜像 digest，不要只留 latest，否则需要回滚时才发现镜像已经被清理。

回滚能力需要演练。每季度抽一个服务，在预发把 5% 流量切到新版本再切回，记录从发现问题到流量归零的耗时。目标不是“理论上能回”，而是“十分钟内能回”。责任也要提前写清楚：发布负责人做继续或回滚的决定，值班同学在约定阈值被触发时有权直接回切；超过约定时限仍未定位，先回滚再排查。

七、一条可执行的发布流水线

flowchart TD
    A[构建不可变镜像] --> B[部署灰度实例]
    B --> C[内部流量验证]
    C --> D[5% 放量]
    D --> E[25% 放量]
    E --> F[50% 放量]
    F --> G[100% 全量]
    G --> H[观察期后清理旧版本]
    C -->|异常| R[流量回切]
    D -->|异常| R
    E -->|异常| R
    F -->|异常| R

每一步都要有准入和退出条件。构建阶段的准入是代码评审通过、单元测试和集成测试通过，退出条件是产出带 git sha 的不可变镜像。部署灰度实例时不接真实流量，准入是镜像扫描通过，退出条件是健康检查、启动日志和配置版本核对无误。内部流量阶段只对白名单开放，退出条件是没有 panic、没有启动期错误。

5% 阶段建议至少观察三十分钟，退出条件是错误率、P99 和饱和度均在阈值内。25% 和 50% 阶段每档至少一小时，尽量覆盖一个流量小高峰，退出条件是各项指标继续达标且业务指标没有显著恶化。100% 之后仍要观察二十四小时，确认没有延迟暴露的问题，再下线旧版本、清理旧配置，过渡字段按计划收缩。任何一步不满足退出条件，都回到上一档或者直接回切，不允许“再看看”。

八、一次完整的放量：订单优惠服务

虚构一个订单优惠服务：v2 改变优惠分摊算法，并新增 discount_source 字段。上线前按 expand-contract 加了可空列，但回填任务还没跑完，测试库里的订单恰好都有值，灰度就这样开始了。

镜像用 git sha 标记，先部署两个灰度实例，不接流量；白名单账号验证下单、取消、退款三条链路。随后按 uid 哈希放 5%，观察三十分钟，错误率 0.18%，与稳定组的 0.20% 接近，P99 持平。放到 25% 后二十分钟，灰度组错误率升到 0.9%，P99 是稳定组的 1.6 倍，日志里 release=canary 的请求集中出现 converting NULL to string is unsupported。

值班同学先看版本标签，确认错误只来自灰度组；再按租户维度拆分，发现集中在有历史订单的租户。根因很快清楚：新代码把 discount_source 直接 Scan 进 string，而回填未完成，旧订单该字段为 NULL。发布负责人决定回切，网关比例归零，灰度实例保留；从确认到流量归零用了三分钟。

修复不是回滚数据库，而是前向修复：字段改成 sql.NullString，读取时回退旧逻辑，补跑回填，并在测试数据里加入 NULL 样本。第二天重新按 5%、25%、50%、100% 放量，每档观察一小时以上，全量后观察二十四小时再清理旧列。复盘结论有三条：数据兼容检查必须在灰度前完成；灰度环境要使用与生产同源的数据样本；告警要能按版本维度聚合，否则定位会慢很多。

九、常见坑

  • 灰度实例连同一个数据库，新代码假设新字段一定存在，旧数据一读就报错。
  • 按 IP 分流，用户换网络就漂移，指标和体验都不可信。
  • 只看平均延迟，长尾已经在恶化，平均值仍然漂亮。
  • 灰度环境的配置、副本数、下游地址与生产不一致，验证结论无法外推。
  • 旧镜像被 CI 清理，需要回滚时无镜可用。
  • 日志和追踪没有版本标签，只能靠实例名猜。
  • 灰度实例按全量容量的一小部分配置，放到 50% 时先被压垮，误判为新版本性能差。

小结

灰度发布的核心不是某个工具，而是把风险切成可观察、可回退的小步：稳定分流、数据先行、指标判定、限时回滚。先把这四件事做成流程，再考虑服务网格等更自动化的方案。发布频率越高，越需要把判断标准和回滚动作提前写好，让一次发布成为一次可重复的工程操作，而不是一场临场发挥。
