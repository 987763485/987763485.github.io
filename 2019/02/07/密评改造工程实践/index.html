密评改造工程实践

密评是商用密码应用安全性评估的简称，要回答的是信息系统里的密码有没有用对、有没有真正起作用。本文从工程实施角度，说明密评评什么、哪些系统会被要求做、四个层面各有哪些典型密码应用点，以及一次改造从差距分析到测评复测要走完的步骤。文中也会点出几个常见坑，适合正在配合等保与密码整改的开发、运维和项目负责人阅读。

密评是什么，和等保是什么关系

合规、正确、有效

商用密码应用安全性评估，评的是信息系统中商用密码应用的合规性、正确性和有效性。合规性看算法、产品和服务是否符合国家要求，自研算法或早该淘汰的国际算法过不了关。正确性看实现细节：分组模式、初始向量、密钥长度、随机数来源是否用对；同一套 SM4，ECB 模式与带随机 IV 的 CBC 模式，强度完全不同。有效性看密码是否真正覆盖需要保护的资产和链路，而不是设备买了、流量却绕过去。

等保管“安全”，密评管“密码”

等保测评关注整体保护能力，有没有身份鉴别、访问控制、入侵防范、数据备份；密评把密码这条线单独拎出来，追问鉴别背后用了什么密码技术、密钥在哪里、传输与存储的机密性和完整性是否真由密码保证。两者有重叠，但不能互相替代：等保报告里写一句“采用加密传输”，不代表密评会认可；密评也不会重复核查机房防火和边界访问控制列表。可以粗略记成，等保是全面体检，密评是专项检查。

写作时点要交代清楚

截至本文写作时，密评仍在试点推进，具体要求以主管部门和试点文件为准。《密码法》在 2019 年初仍是草案/征求意见阶段，2020-01-01 才施行，因此现在还不存在“不做就违法”的普遍义务，项目压力多来自主管部门要求、行业规范或等保整改的延伸。试点期各地在评估范围、材料清单、报告格式上并不统一，这一点后面还会展开。

哪些系统会被要求做

适用对象

等保三级及以上的系统是主要对象，尤其是政务、金融、能源、交通、医疗、电信等关键行业的重要信息系统。这些系统数据敏感、影响面大，密码又是最容易被“表面合规”糊弄的保护手段。部分行业和地区也会把等保二级纳入，具体看属地口径。

触发场景

常见有四类：新建系统上线前，可研与设计阶段就要把密码应用方案做进去；已建系统接受定期评估，通常与等保测评周期合并考虑；等保测评或安全检查发现密码应用缺失，被要求限期整改；主管部门专项检查，或行业下发密码应用要求。

先确认属地口径

试点期的现实是各地要求不完全一致。有的地方先从政务云、门户网站切入，有的从金融、医保系统开始；同一个省，不同地市对材料深度、测评机构选择、整改期限的要求也可能不同。项目启动前先确认三件事：是否必须做、按什么口径做；报告交给谁；测评机构的资质与排期。不要拿外省经验直接套，也不要把厂商的销售话术当成政策依据。

范围也要控制。不是所有系统都要“全套国密”，内部办公 OA 和对外支付系统的评估深度显然不同，按重要程度排序、先做核心系统，比平均用力有效。

四个层面：从机房走到数据

评估通常按物理和环境、网络和通信、设备和计算、应用和数据四个层面展开。可以把它想成一条数据路径：进机房、走网络、上机器、落到数据，每层都有对应的密码应用点。

物理和环境

门禁与视频监控是主要对象。密码应用点包括门禁卡的身份鉴别、重要区域进出记录的完整性、视频存储的完整性。要注意老式逻辑加密卡不算合规的密码应用，记录只存本地硬盘，也很难证明没被改过。

网络和通信

链路加密、通信双方身份鉴别、访问控制信息完整性、集中管理通道保护。常见做法是分支机构之间用支持 SM 算法的 IPsec VPN，对外网站部署国密 SSL，运维通道单独加密。

设备和计算

服务器与网络设备的身份鉴别、日志完整性、重要程序完整性、密码模块自身安全。典型做法是 SSH 改为证书登录、关键配置做 SM3 摘要基线比对、审计日志签名后外送。

应用和数据

用户身份鉴别、访问控制信息完整性、传输与存储机密性、重要操作不可否认。数据库敏感字段加密、电子票据签名、接口防重放都落在这层，和业务代码贴得最近，改造量也最大。

按这条路径走一遍，比对着条款编号逐条找证据更不容易漏。

算法与产品：先划清边界

三种算法各管什么

SM2 是非对称算法，256 位密钥，用于数字签名、密钥交换和公钥加密；SM3 是哈希算法，输出 256 位摘要，用于完整性校验、HMAC 和密钥派生；SM4 是对称分组算法，128 位分组与密钥，用于数据加密。三者不是替代关系，一次签名往往先对报文做 SM3 摘要，再用 SM2 私钥签名。

算法只是入场券

真正决定安全的是密钥管理。同样一句 SM4/CBC/PKCS7，密钥在密码机里、由主密钥派生，和密钥硬编码在代码里，风险完全不同。测评时专家问得最多的不是“用了什么算法”，而是“密钥怎么生成、存在哪、谁能用、怎么换、怎么销毁”。

密码机、密码卡与软件模块

服务器密码机的密钥不出设备，接口标准，可做双机热备，适合核心业务，缺点是成本和机房规划要求高。密码卡插在服务器 PCIe 上，性能好、单价低，但密钥与主机绑定，主机失陷时风险更高，迁移也麻烦。软件密码模块部署最灵活，适合测试和小流量场景，密钥在主机内存或磁盘里，防护能力弱，是否满足合规要求要提前确认。

选型顺序是先明确性能、可用性和合规要求，再算成本，不要先买设备再找场景。

差距分析要落到具体系统、接口和数据表，只写“某条款不满足”没法指导施工。方案设计和密钥体系设计可以并行，但密钥体系必须在实施前定稿，否则代码写完再改密钥层级，返工量会翻倍。内部验证别只测通路径，证书过期、主备切换、时钟偏移这些异常场景，才是测评现场容易出问题的地方。

落地时的四个硬骨头

国密 HTTPS 的兼容性

2019 年初，主流浏览器与客户端对国密 SSL 的支持有限，不少手机 App、老版本 Java 客户端和嵌入式设备不认 SM2 证书链。一刀切切换，结果往往是上线当天一片握手失败。稳妥做法是双证书、双栈：同一域名部署两套证书，服务端按客户端能力协商；或者新老客户端分流，给老客户端留过渡期。还要检查证书链是否完整、负载均衡是否透传 SNI，并按真实客户端占比决定退场时间。

数据库字段加密与查询

字段加密后，等值查询、范围查询、LIKE、排序和唯一索引都会受影响，密文长度也会变。工程上的折中是：只加密真正敏感的字段；需要等值查询的字段另存一列盲索引，对规范化明文做 HMAC-SM3 后建索引；范围和模糊查询改到业务层过滤，或同步到独立检索库；加密列换成更长的类型，给密文和 IV 留空间；主键和外键不加密。这些要在方案阶段定，代码写完再改成本会翻几倍。

签名验签的性能与轮换

验签是 CPU 密集操作，集中在网关做很容易成为瓶颈。上线前要按峰值 QPS 压测，确认单机验签能力、连接复用和超时降级策略，量大的场景考虑密码卡或签名服务集群。密钥轮换要带版本号，新密钥签新数据，验签方保留旧公钥一段时间，等旧数据过期再下线。没有版本号，换密钥那天就是全站故障。

时间戳与随机数

签名报文要带时间戳和一次性随机数 nonce，服务端在窗口期内去重，防止重放。前提是各节点时间同步，NTP 必须做，否则正常请求会被时间戳校验拒掉。随机数要用密码模块的随机源，不要用语言自带的伪随机函数，更不要拿时间当种子；CBC 的 IV 每次加密都要重新生成，绝不能复用。这些细节在代码评审时最易被放过，却直接决定正确性能不能过。

密钥管理：比算法更难

生命周期六步：生成、分发、存储、使用、轮换、销毁。生成在密码模块内完成，不能用软件伪随机；分发走受保护信道，用密钥加密密钥（KEK）分层；存储与数据分离，不进配置文件、代码仓库和镜像；使用时应用只拿到使用权限，运维能重启设备却导不出密钥；轮换定期做，人员离职或疑似泄露时立即做，旧密钥保留用于解密历史数据；销毁按规程覆写，留下审批记录。

主密钥保护数据密钥，数据密钥加密字段，做到一字段一密钥，单点泄露不波及全库。密钥操作全部审计并异地保存，最忌讳密钥和密文同表同机。

项目管理：范围、窗口与回滚

一期只做核心系统和对外门户，把必须做与可以后做分开，逐系统列改造点和工作量，范围失控是超期主因。改造窗口放在后半夜或周末，提前确认停机时长与通知口径；数据库加密要预留回填和校验时间。每次变更都要能回滚：证书双栈按开关切回，加密列过渡期保留明文副本但严控权限。与等保整改合并能省一次停机，顺序是先边界加固和主机基线，再密码改造，最后统一验证。

几个常见的坑

只买密码机不改业务，抓一次流量就暴露。算法套用但密钥管理缺失，密钥躺在 application.yml 里，等于把锁和钥匙挂在一起。忽略客户端兼容，上线当天老客户端全部握手失败。测评前临时补文档，经不起访谈追问。把密评当一次性验收，系统会变更、密钥要轮换，通过只是持续运营的起点。

小结

密评评的是密码应用的合规性、正确性和有效性，不是买了几台设备。先确认范围和属地口径，再按差距分析、方案、密钥体系、实施、自测、测评、复测推进。算法只是基础，密钥全生命周期管理才是主体。截至本文写作时密评仍在试点，具体要求以主管部门和试点文件为准。
