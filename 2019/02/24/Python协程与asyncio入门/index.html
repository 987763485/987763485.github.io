Python 协程与 asyncio 入门

本文属于《Python 学习路线》第 15/29 篇
上一篇系列目录下一篇

一个抓取两百个页面的脚本，用 requests 串行跑要几分钟，改成协程并发之后可能只要十几秒；但把 async 当成语法糖到处乱用，也常写出既慢又难查的代码。本文从并发模型讲起，依次拆开协程、事件循环、Task、取消与超时，最后用 aiohttp 写一个可运行的并发抓取程序。读完你应该能判断一段代码该不该异步，以及如何避开 asyncio 最常见的几个坑。

从并发模型说起：线程、进程与协程

一个网络服务的大部分时间不在计算，而在等待：等数据库返回、等下游接口响应、等磁盘写完。并发模型的选择，本质上是在回答“等待的时候，CPU 去做什么”。Python 里常见的三种答案是进程、线程和协程，它们的边界比很多教程描述的更清楚。

三种并发单元的分工

维度 多进程 多线程 协程
调度者 操作系统 操作系统 事件循环（用户态）
切换成本 高，涉及地址空间 中，涉及内核态 低，只是函数调用
并行能力 真并行，可用多核 受 GIL 限制 单线程，无并行
共享状态 需要进程间通信 共享内存，必须加锁 同线程共享，仍需小心
适用场景 CPU 密集、强隔离 阻塞式 I/O、存量库 高并发 I/O、大量连接

进程之间内存隔离，一个崩了不拖垮另一个，能真正吃到多核，代价是创建和切换都重，进程间通信也麻烦。线程共享同一份内存，创建比进程便宜，但任何一个线程的崩溃都可能带走整个进程，共享数据还要加锁。协程更轻：它的调度完全不需要操作系统参与，只是同一个线程里一段可以暂停和恢复的执行流程。

这里必须提前说清 GIL。CPython 的解释器锁让同一时刻只有一个线程执行字节码，所以多线程在纯计算任务上几乎拿不到多核收益；但线程在等待 I/O 时会释放 GIL，这也是“多线程适合 I/O”这句话的由来。协程干脆放弃了线程，在单线程里用事件循环把等待时间重叠起来，把“切换”变成一次普通的函数返回。

协作式调度意味着什么

线程是抢占式的：操作系统在时间片用完时把执行权拿走，你无法预测切换点，所以共享状态必须加锁。协程是协作式的：只有执行到 await，协程才主动让出控制权，其余时刻它一直占着线程。

这个差异带来两个直接后果。好的一面是切换点明确，许多在多线程里需要锁的地方，在协程里可以只靠“两次 await 之间不插入其他操作”来保证；调试时调用栈是连续的，断点也听话。坏的一面是没有任何机制能打断一个不肯让出的协程：一段死循环、一次 time.sleep、一个同步网络请求，都会把整个事件循环钉住，其他协程全部停摆。后文有一节专门处理这个问题。

为什么 I/O 密集适合，CPU 密集不适合

判断标准是任务把时间花在哪里。I/O 密集的任务，大部分时间在等，协程在这些等待点切换，单线程就能维持大量并发连接，内存开销也远小于同等数量的线程。CPU 密集的任务需要的是并行算力，而一个事件循环在同一时刻只跑一个协程，切换还要付出调度成本，异步化不会让它更快，反而更慢。

所以正确的组合通常是：I/O 并发放给协程，重计算交给多进程或 C 扩展。把两者混在同一个事件循环里，是后面很多性能问题的根源。至于 profiling、向量化和缓存该怎么做，属于另一篇文章的话题，这里不展开。

协程的基础：async def、await 与执行时机

调用协程函数并不会执行它

这是初学者最容易误解的一点，也是排查“异步代码没生效”时的第一现场。用 async def 定义的函数，调用它并不会运行函数体，而是返回一个 coroutine 对象，函数体一行都没有执行。

如果既不 await 也不运行，解释器会在垃圾回收时给出警告：RuntimeWarning: coroutine 'fetch' was never awaited。这条警告几乎总是意味着某处少写了一个 await，不要忽略它。

await 到底做了什么

await 后面接一个 awaitable，可以是协程、Task 或 Future。它的语义是：把当前协程挂起，把控制权交回事件循环，等目标完成之后再从这一行恢复。挂起期间，当前协程的局部变量、执行位置都保留在它自己的栈帧里，恢复时接着往下走，不需要重新计算。

真正运行：asyncio.run

Python 3.7 增加了 asyncio.run，它是启动异步程序的推荐入口。它负责创建新的事件循环、运行传入的协程直到完成、取消残留任务、关闭异步生成器，最后关闭循环并清理执行器。一句话：它把启动和收尾都包好了。

把入口写在 if name == “main“ 里是个好习惯，避免模块被导入时意外启动整个抓取流程。asyncio.run 每调用一次都会新建一个循环，因此它只适合作为程序的最外层入口。在一个已经在运行的协程里再调 asyncio.run，会直接抛出 RuntimeError，这一点在事件循环一节还会再提。

事件循环：asyncio 的调度中心

循环到底在做什么

去掉所有封装，事件循环就是一个 while 循环，每一轮大致做三件事。第一，检查定时器堆里有没有到期的回调，把到期的放进就绪队列。第二，通过 selector 询问操作系统哪些文件描述符可读或可写；Linux 上通常是 epoll，macOS 上是 kqueue。第三，按顺序执行就绪队列里的回调，每个回调一般只把某个协程往前推一步，推到下一个 await 就停下。

协程本身并不神奇，真正驱动它的是 Task。协程在 await 处挂起时，会把所等待的 Future 交给 Task；Task 给这个 Future 挂上完成回调，Future 完成时回调唤醒 Task，协程就从挂起的位置恢复。整个过程没有线程栈的切换，只有 Python 对象之间的调用与回调。这正是“单线程内切换”的实现方式，也是它比线程切换便宜的原因。

顺带解释一个常见写法：await asyncio.sleep(0) 并不等待任何真实时间，它只是把当前协程重新排到就绪队列尾部，让其他协程有机会先运行。需要在长循环里主动让出控制权时，这是成本最低的方式；但它不会等待 I/O，真正的等待仍然要交给异步接口。

asyncio.run 内部做的正是这件事，额外加上取消残留任务、关闭异步生成器、关闭默认执行器等收尾工作。二者不是两套互不相干的 API，run 是更高层的封装。新代码优先用 run，老代码里的 run_until_complete 也不必急着改，但要知道它不会帮你做清理。

同一个循环在同一时刻只能跑一个 run_until_complete。嵌套调用，或者在已经运行的循环里再调 asyncio.run，都会立刻抛出 RuntimeError，提示循环已经在运行。典型场景是在 Jupyter Notebook 里直接调 asyncio.run，或者在 async 函数体里又调了一次 asyncio.run。后者应当改成 await。

一个循环绑定一个线程

事件循环对象和创建、运行它的线程绑定。在 A 线程创建的循环，不能直接拿到 B 线程里运行；硬要这么做，通常得到 RuntimeError 或者难以解释的超时。如果确实需要从别的线程提交协程，应该用 loop.call_soon_threadsafe 投递普通回调，或者用 asyncio.run_coroutine_threadsafe 提交协程，并等待它返回的 concurrent.futures.Future。

还有一个容易踩的细节：asyncio.get_event_loop 在没有运行循环的线程里可能悄悄创建一个新循环，你拿到的并不是你以为的那个。在协程内部，用 3.7 新增的 asyncio.get_running_loop 获取当前正在运行的循环，语义明确，失败时会直接报错，比 get_event_loop 可靠得多。

Task 与并发编排

create_task：把协程变成可调度的任务

await 是串行等待，要让多个协程同时跑，需要把它们包装成 Task。Task 是 Future 的子类，负责驱动协程，并把结果或异常保存下来，供后续取用。

两个 fetch 几乎同时开始，总耗时约 1 秒，而不是 2 秒。create_task 会立即把协程排进循环的就绪队列，即使当前协程不让出，任务也会在下一个调度点开始执行。

3.7 之前常见的写法是 loop.create_task 或 asyncio.ensure_future；3.7 起 asyncio.create_task 是推荐写法，它会自动取当前运行的循环，省掉把 loop 传来传去的麻烦。ensure_future 仍然可用，但它既接受协程也接受 Future，语义更宽，读代码时不容易一眼看出意图。

任务引用：一个真实存在的坑

事件循环对 Task 只持有弱引用。创建任务后如果不保存返回值，任务可能在执行途中被垃圾回收，日志里出现 Task was destroyed but it is pending!，而且往往伴随“请求发出去了但回调没执行”的诡异现象。

官方文档专门提醒过这一点。成本最低的保险是：每个 create_task 的返回值都有一个归宿，要么马上 await，要么放进列表或集合统一等待。

gather：一次性等所有结果

gather 接受一组 awaitable，返回结果列表，顺序与传入顺序一致，而不是完成顺序。

异常语义需要记牢。默认 return_exceptions=False 时，任何一个任务抛异常，gather 会立刻把这个异常抛给调用者，但其他任务不会被取消，仍然在后台继续跑。也就是说，“一个失败、全部退出”并不是 gather 的默认行为，需要自己取消其余任务。设成 return_exceptions=True 时，异常会作为结果列表中的元素返回，调用者必须逐个检查，否则会把异常对象当成正常结果使用。

还有一个方向相反的细节：如果等待 gather 的协程本身被取消，gather 会取消它内部的所有子任务。取消是向下传播的，这一点在设计任务树时要利用好。

wait 与 as_completed：不同的等待策略

asyncio.wait 接受 Task 或 Future 的集合，通过 return_when 控制何时返回，可选 FIRST_COMPLETED、FIRST_EXCEPTION、ALL_COMPLETED。它返回两个集合：已完成的和未完成的，结果要自己从任务对象里取。适合“先到先处理”，或者“等到第一个成功就继续”的场景。它的参数应当是 Task 或 Future；直接传协程对象容易让人误判任务边界，先 create_task 再传更稳妥。

函数 返回 顺序 单个任务失败时 适用场景
gather 结果列表 与传入一致 默认立刻抛出，其余继续 结果都要、顺序固定

选择哪一个，取决于你要的是“全部结果的集合”，还是“最早的可用结果”。前者用 gather，后者用 as_completed；需要精细控制何时返回，再考虑 wait。

取消与超时：协作式停止

cancel 不是 kill

Task.cancel 不会杀死协程。它做的事情是：如果任务正挂在某个 await 上，就往协程内部抛一个 CancelledError；如果任务还没开始执行，取消会在它第一次被调度时生效，函数体不会真正运行。协程收到 CancelledError 后可以清理资源，但必须让它继续向上传播，否则取消会被吞掉，调用方以为停下来了，实际任务还在跑。

在 3.7 里，CancelledError 仍然是 Exception 的子类，这一点很要命：一个宽泛的 except Exception 会把它一并捕获，取消就此失效。写兜底异常处理时，要么先单独捕获并重新抛出 CancelledError，要么确保 except 分支最后 raise。

finally 里做清理是安全的，但不要在清理中执行可能长时间挂起的操作。如果外层在清理期间再次调用 cancel，清理中的 await 会收到第二次取消信号。如果清理动作必须完成，可以用 shield 包住，或者改成同步方式执行。

超时之后要清理什么

超时从来不等于“什么都没发生”。连接可能已经建立，临时文件可能已经写入一半，数据库事务可能已经开启，信号量可能还没释放。正确的做法是把资源的获取与释放放进同一个 try/finally 或 async with，让正常路径、异常路径、取消路径走同一段清理代码。凡是“成功后才释放”的写法，在取消面前都会漏。

协作的工具箱：同步原语与异步迭代

Lock、Semaphore 与 Queue

asyncio 提供了与 threading 对应的一组原语：Lock、Event、Condition、Semaphore 和 Queue。它们不是线程安全的替代品，而是给同一个事件循环里的协程使用的。协程只在 await 处切换，竞态窗口比线程小，但“先检查、再修改”如果跨越了 await，依然会出问题。

async with lock 在进入时 await 获取锁，退出时释放。没有竞争时几乎不花时间；有竞争时，后来的协程挂起等待，不占用 CPU。

async for 与异步生成器

普通 for 从可迭代对象同步取值；async for 从异步可迭代对象取值，每一次取值都可能 await。最常见的来源是异步生成器：函数体里既有 yield 又有 await，用 async def 定义。它在 3.6 就已可用，3.7 的 asyncio.run 会在退出时负责关闭它们。

这种结构的价值在于，分页细节被封装在生成器里，调用方拿到的是一条条数据，而不是一整页。数据不必全部装进内存，消费端处理慢时，生成器就在 yield 处暂停，天然形成速率匹配。流式解析网络响应、逐行处理日志，都可以套用同一个模式。

async with 与异步上下文管理器

async with 对应实现了 aenter 和 aexit 的对象，这两个方法都可以 await。aiohttp 的响应、数据库连接池借出的连接、需要异步加锁的临界区，都属于这一类。

3.7 还提供了 contextlib.asynccontextmanager，可以用一个异步生成器写出异步上下文管理器，省掉两个魔术方法的样板代码。把释放逻辑放在 finally 里，正常退出、抛异常、被取消三种情况都会经过它，这是异步代码里最可靠的资源清理位置。

别阻塞事件循环

一次阻塞，全部停摆

事件循环是单线程的。任何同步阻塞调用，包括 time.sleep、requests.get、同步文件读写、大段纯计算，都会让整个循环停下来。它不是“这个协程慢一点”，而是所有协程、所有定时器、所有心跳一起停。

判断标准很简单：这个函数在等待期间会不会让出 CPU？如果不会，就不能直接在协程里调用。把它放进线程或进程，让循环本身保持轻量。

第一个参数传 None 表示使用默认的线程池执行器，也可以传入自己创建的 Executor 控制线程数。注意它并没有把 requests 变成异步，只是把阻塞动作挪到另一个线程，事件循环继续跑。线程数要有上限，并发一高就开几百个线程，内存和上下文切换的成本会把省下的时间吃回去。

进程池适合少量、计算量大的任务；每个任务都要序列化参数和结果，切得太碎反而更慢。这里的边界可以记成一句话：协程负责等待，执行器负责计算。更系统的性能手段，例如 profiling 与向量化，留待专门的文章讨论。

aiohttp 实战：并发抓取

安装与会话复用

aiohttp 3.x 的核心是 ClientSession。它持有连接池、Cookie、默认超时等状态，应该在整个程序里复用一个实例，而不是每个请求建一个。每个请求都新建 Session 会反复建立连接、反复握手，既慢又容易把文件描述符耗尽。

Session 要在协程里创建、在同一个循环里使用，并用 async with 或显式 close 关闭。把在一个循环里创建的 Session 拿到另一个循环里用，通常得到 Event loop is closed 之类的错误。

超时与连接池

aiohttp 3.x 用 ClientTimeout 表达超时，可以分别限制总时长、建连时长和读取间隔：

连接池默认有上限，limit 控制总连接数，limit_per_host 控制单个主机的连接数。抓取同一站点时把 limit_per_host 调小，既是礼貌也是自保：对端开始限流时，连接开得越多，失败得越快。

状态码要自己检查。aiohttp 不会因为 4xx 或 5xx 抛异常，需要调用 resp.raise_for_status 才会把错误状态转成异常。响应体也要及时读完，async with 退出时虽然会释放连接，但没读干净的连接可能无法复用，池子被占满后程序看起来像卡在等待连接上。

调试与常见坑

打开调试模式

设置环境变量 PYTHONASYNCIODEBUG=1，或者在代码里调用 loop.set_debug(True)，会打开 asyncio 的一组检查：未 await 的协程、执行时间过长的回调、从未被取回的异常。其中最有价值的是慢回调日志，回调执行超过默认的 0.1 秒就会打印一行 Executing 加任务信息加耗时，阻塞调用几乎无处遁形。

调试模式本身有额外开销，生产环境不建议长期开启，排障时用环境变量临时打开即可。

三个常见警告怎么读

RuntimeWarning: coroutine 'xxx' was never awaited，说明调用了 async 函数，却既没有 await，也没有包成任务。协程对象被丢弃，函数体从未执行，业务逻辑自然没有发生。

Task was destroyed but it is pending! 说明循环关闭时还有任务没结束。常见原因是任务只创建没保存引用，被垃圾回收了；或者主协程提前退出，没等后台任务收尾。asyncio.run 在退出前会取消剩余任务，所以这条警告更多出现在手工管理循环的代码里。

Task exception was never retrieved 说明任务抛了异常，但没有任何人 await 它，异常被留在任务对象里，直到对象销毁才被打印。它的危险在于业务已经失败，日志却出现在很久之后，时间线完全对不上。

处理顺序是固定的：先找到创建任务的代码，再确认每个任务的返回值是否有归宿——被 await、被 gather 收集、放进集合，三者至少占一个。

asyncio.all_tasks 是 3.7 新增的接口，只返回尚未完成的任务，正好用来做这类快照。配合调试模式的慢回调日志，多数卡死问题能在几分钟内定位。

关闭之后再用循环

RuntimeError: Event loop is closed 几乎总是两种原因：一是在 asyncio.run 返回之后继续使用旧的 loop 对象；二是把循环 A 里创建的 Session、连接、Future 拿到循环 B 里使用。解法是让资源生命周期与循环一致——循环里创建，循环里关闭，不要把跨循环的对象塞进全局变量。

七个高频坑

  1. 在协程里调用 time.sleep、requests、同步数据库驱动，阻塞整个循环。
  2. 忘记 await，或者把 await 写进普通函数，后者在编译阶段就是语法错误。
  3. 在 gather 里塞入不会结束的任务，例如 while True 的消费者，导致 gather 永远不返回。正确做法是发结束信号或显式取消。
  4. 捕获 CancelledError 后不重新抛出，取消失效，任务假死。
  5. 取消之后继续使用已经关闭的连接、文件或会话。
  6. 在子线程里创建循环，却指望主线程的协程能 await 它；跨线程要用 run_coroutine_threadsafe。
  7. 用 asyncio.run 包住本来就在循环里的代码，触发循环已在运行的 RuntimeError。

这七条覆盖了日常遇到的大部分问题，它们的共同点是：把异步当成了“自动变快”的开关，而忽略了它是一套需要遵守约定的调度模型。

小结

asyncio 的世界观可以用三句话概括：协程是可暂停的函数，事件循环负责在等待点之间调度，Task 是把协程接入循环的凭证。判断要不要用它，只看任务是 I/O 密集还是 CPU 密集；用上之后，守住三条底线——不在协程里阻塞、不丢失任务引用、取消时正确清理并重新抛出 CancelledError。做到这些，gather 的异常语义、wait_for 的清理、Session 的复用就都是自然推论，而不是需要背诵的规则。
