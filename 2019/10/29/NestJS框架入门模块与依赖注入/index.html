NestJS 框架入门：模块与依赖注入

本文属于《TypeScript 学习路线》第 64/74 篇
上一篇系列目录下一篇

NestJS 在 2019 年已经发布到 6.x，很多团队把它当作从 Express 走向结构化服务端开发的第一步。初学者常把它的门槛归因于装饰器太多，真正难的是模块边界与依赖注入：同一个 service，注册在不同的模块里、用不同的 provider 写法，运行时的实例数量、可见范围和生命周期都不一样。本文以 NestJS 6.x 和 TypeScript 3.6 为基准，从启动过程一路讲到动态模块、作用域、生命周期钩子与测试，读完后你应该能为一个中等规模的服务划出清晰的模块边界，并在遇到注入报错时知道该查哪里。

设计取向与最小可运行应用

Angular 的影子，服务端的内核

NestJS 的设计语言明显借自 Angular：用模块组织应用，用装饰器声明元数据，用构造函数注入表达依赖。对应关系很直接，Angular 的 @NgModule 变成 @Module，@Component 变成 @Controller，@Injectable 则几乎同名保留。但两者面向的问题不同：Angular 的核心是组件树与变更检测，Nest 的核心是请求管线与对象图。Nest 没有模板、没有变更检测，也不要求你把所有东西都塞进一个根组件。

第二层关系是它与 Express、Koa 的关系。Nest 本身不实现 HTTP 服务器，而是通过平台适配器委托给底层框架。默认安装的是 @nestjs/platform-express，请求最终由 Express 处理；换上 @nestjs/platform-fastify，路由和请求对象就换成 Fastify 的实现。这解释了为什么 Nest 里仍然可以使用 Express 的中间件生态，也解释了为什么业务代码不应直接摆弄 req 与 res：一旦绑死具体适配器，替换底层或做单元测试都会变难。

可以用一句话概括三者的分工：Express 是库，路由和中间件给你，目录结构自己定；Koa 也是库，用洋葱模型把中间件串起来；Nest 是框架，在适配器之上规定了模块、注入和一条固定的请求处理链。框架带来的约束不是免费的，但换来了可替换的基础设施与可测试的依赖图。

从 main.ts 到第一个请求

最小应用只有两个文件。main.ts 负责引导，app.module.ts 负责声明根模块。

NestFactory.create 做的事情比看上去多：读取 AppModule 的元数据，递归加载 imports，为每个模块建立独立的注入容器，按依赖顺序实例化 provider，最后返回一个尚未监听端口的应用对象。因此 create 之后的代码适合做全局配置，listen 才真正把端口打开。把全局前缀、全局管道、全局过滤器放在这一段，读者一眼就能看到应用的横切配置。

目录结构不必复杂，但要围绕模块而不是技术类型来分。入口 main.ts 与根模块 app.module.ts 放在 src 下，基础设施放在 src/common 与 src/config，每个业务切片一个目录，模块、控制器、服务、DTO 放在一起。按层建 controllers/、services/ 的大目录在项目变大后会让一次改动跨越很多文件夹，而按 feature 组织能把变更收敛在一个目录内。

装饰器能工作，靠的是编译配置而不是运行时魔法。TypeScript 3.6 使用实验性的装饰器实现，tsconfig.json 必须打开 experimentalDecorators 与 emitDecoratorMetadata。前者让 @Module、@Injectable 这类装饰器通过类型检查，后者让编译器把构造函数参数的类型写进元数据，注入容器才知道某个位置需要什么。需要强调的是，这套装饰器是 TypeScript 的实验性实现，与 TC39 当时仍在讨论的新装饰器提案并不相同：它没有 context 参数，也不能用 addInitializer 注册初始化逻辑，两者的写法并不兼容。元数据依赖 reflect-metadata，Nest 的依赖里已经带了它，自己搭入口时要在最早的位置引入一次。

模块：应用的分层单元

@Module 的四个字段各有明确职责。imports 声明本模块需要哪些其他模块导出的 provider；controllers 声明本模块的路由入口，Nest 会为它们注册路由；providers 是本模块注入容器的注册表；exports 决定哪些 provider 或模块能被外部看见。四者里最容易忽略的是 exports，因为它在开发阶段不报错，直到另一个模块试图注入时才炸。

模块的可见性是单向的。一个 provider 写进 providers 只代表本模块内可注入，默认对别处不可见；只有同时出现在 exports 里，导入本模块的其他模块才能拿到它。导出一个模块则是另一层含义：它会把那个模块的 exports 再导出一次，形成传递可见。下面这个用户模块把服务暴露出去，把仓储藏在内部：

模块实例默认是单例。无论在多少地方 imports: [UsersModule]，容器都只会创建一份 UsersModule 及其 provider，这是 Nest 能够安全管理连接池与缓存的基础。但要注意，单例的前提是“同一个模块节点”。如果两个模块各自在 providers 里写了同一个类，容器会为它们分别实例化，得到两个互不相干的对象，状态与连接都不共享。这类问题不会在启动时报错，只会表现为缓存命中率异常或数据库连接数翻倍。

feature module 与 shared module 是两种常见角色。feature module 对应一个业务切片，拥有自己的控制器、服务与数据访问；shared module 提供日志、配置、数据库连接这类横切能力，通常只有 providers 与 exports，没有控制器。AppModule 是组合根，只负责把 feature module 与 shared module 拼起来，不写业务逻辑。有些团队喜欢用 @Global() 把 shared module 设为全局，省掉每个模块的 imports，代价是依赖关系从代码里消失，读一个模块时无法判断它用了哪些基础设施。我的建议是只对真正的全局设施使用 @Global()，例如配置与日志，其余老老实实导入。

Provider 与注入令牌

四种注册写法

providers: [UsersService] 是简写，等价于 { provide: UsersService, useClass: UsersService }。完整的 provider 对象有两个关键字段：provide 是令牌，useClass、useValue、useFactory、useExisting 四选一决定实例从哪来。

在讲四种写法之前，先把 @Injectable() 的职责说清楚。它标记一个类由容器管理，但标记本身不等于注册，注册仍然发生在模块的 providers 里。它真正做的是让编译器为构造函数参数生成元数据，容器才知道每个位置该注入什么。一个没有依赖的类即使不写 @Injectable() 也能被实例化，但只要构造函数里有注入参数，就应当加上它，否则元数据缺失，解析会失败。

useClass 交给容器去 new，构造函数参数照样注入，适合有依赖的实现类。useValue 直接给一个现成对象，适合配置常量、第三方客户端实例，以及测试里的替身；容器不会对它做任何处理，给什么用什么。useFactory 在需要异步、需要按条件选择实现、或者需要先读配置再建连接时使用，函数可以返回 Promise，Nest 会等它 resolve 后再继续启动。useExisting 是别名，让第二个令牌指向已经存在的实例，而不是再造一个。

选择哪种写法有一条简单准则：能直接 new 且依赖简单的用 useClass；值是静态的用 useValue；创建过程有异步、条件或副作用用 useFactory；只是给已有实例起别名用 useExisting。

令牌、接口与依赖倒置

类作为令牌最自然，容器用类本身作键，类型系统也能帮你检查。字符串令牌灵活但容易拼错，两个模块都写 'CONFIG' 却指向不同东西时，容器无法察觉；Symbol 令牌没有这个问题，因为每个 Symbol() 都是唯一值，定义一次、处处引用，不会与别处的同名令牌撞车。Nest 没有 Angular 那样的 InjectionToken 类，字符串与 Symbol 就是它提供的令牌形式，这一点常让从 Angular 转过来的读者困惑。

接口不能直接当令牌，原因在编译期而不是框架。TypeScript 的接口只存在于类型空间，编译后完全消失；emitDecoratorMetadata 遇到接口类型只能写入 Object。容器拿到 Object 这个令牌，既不知道你要哪个实现，也无法区分两个不同的接口。于是标准做法是“接口描述契约，令牌负责查找，模块负责绑定”：

作用域与生命周期

单例、请求与瞬态

默认情况下 provider 是单例：应用启动时创建一次，所有请求共享。这也是最该优先选择的作用域，因为无状态服务配上单例，内存占用和性能都最好。

Scope.REQUEST 让容器为每个请求创建新实例。代价不在实例本身，而在传播：如果一个单例服务注入了请求作用域的 provider，它自己也会被迫变成请求作用域，这种变化会沿着注入链一路上溯到控制器。链上每一个对象都要按请求重建，原本可以缓存的解析结果全部失效。Nest 6 的请求作用域实现依赖每个请求的上下文，控制器、守卫、拦截器只要碰到请求作用域的依赖，都进入按请求实例化的路径。

Scope.TRANSIENT 介于两者之间：每个注入它的消费者各拿一份新实例，消费者之间不共享。它适合有状态但状态只属于某个消费者的辅助对象，比如一次导出任务专用的格式化器。瞬态不会向上传播作用域，但同样绕过了单例缓存，不要在热点路径上滥用。

真正需要请求作用域的场合并不多：多租户请求要携带租户连接、需要拿到当前登录用户、需要贯穿整条链路的追踪 ID。即便在这些场景，也可以把范围压到最小：只在控制器或一个薄的上下文服务上使用请求作用域，把上下文作为显式参数传给下层，而不是让整个服务层都跟着变成请求作用域。依赖注入解决的是对象装配，不该成为传递运行时数据的唯一手段。

初始化与关闭的顺序

生命周期钩子让模块有机会在正确的时间点做事。OnModuleInit 在模块的 provider 全部实例化之后调用，依赖模块先于被依赖模块，所以可以放心使用注入进来的对象。OnApplicationBootstrap 在所有模块初始化完成后、开始监听端口之前调用，适合做需要“全量就绪”的准备工作。OnModuleDestroy 与 OnApplicationShutdown 在关闭时触发，顺序与初始化相反，先关依赖者再关被依赖者。

  Factory->>Mod: 实例化 provider
  Factory->>Mod: onModuleInit
  Factory->>Mod: onApplicationBootstrap
  Main->>Factory: listen(3000)
  Main->>Factory: close()
  Factory->>Mod: onModuleDestroy
  Factory->>Mod: onApplicationShutdown

实现钩子时建议显式 implements 对应接口，拼错方法名时编译器会提醒。构造函数只做赋值，重 IO 放到 OnModuleInit：构造函数里发起的连接一旦失败，错误会淹没在模块加载栈里，而且测试中构造一个 provider 就会产生副作用。关闭阶段则要确保连接池、消息消费者、定时器都被释放，否则进程可能挂住不退。Nest 提供 app.enableShutdownHooks() 监听进程信号并转成 app.close()，生产环境仍建议在自己的信号处理里显式调用 close 并设置超时，避免某个钩子卡死导致无法退出。

动态模块：把配置留到运行时

@Module 的元数据在编译期就固定了，但基础设施模块的参数往往只有运行时才知道：数据库地址、邮件服务器、第三方密钥。动态模块解决的正是这件事。模块类提供一个静态方法，接收参数后返回 DynamicModule 描述对象，容器照着这份描述去装配。它不是新机制，只是把原本写在装饰器里的 imports、providers、exports 改成运行时计算。

命名上有一套社区惯例：forRoot 表示全局只配置一次的根模块，forRootAsync 用于配置本身依赖其他 provider 的场合，register 或 forFeature 表示按 feature 重复注册、每次参数不同。forRoot 返回的对象里，module 字段必须指向模块类自身，否则容器不知道这份描述属于谁；providers 与 exports 的写法和普通模块完全一致，只是内容来自参数。

动态模块还可以再导出其他模块。把数据库、缓存、邮件几个基础设施模块收进一个 InfrastructureModule，在它的 exports 里列出这些模块，业务模块只导入 InfrastructureModule 就能拿到全部能力。这是“再导出”的正当用法，但要注意它不会把 provider 变成全局，只是沿着导入链继续传递可见性。另一个注意点是重复调用：同一个模块类用不同参数多次 forRoot，容器会按不同的动态元数据建立不同节点，连接池和定时器就可能各来一份。forRoot 只应出现在根模块，重复注册的参数化需求交给 register。

循环依赖：forwardRef 能修好，但通常不该修

循环依赖分两个层级，症状相似，处理方式不同。

模块级循环是 AModule 的 imports 里有 BModule，而 BModule 又导入了 AModule。JavaScript 的模块求值顺序会让其中一方在装饰器执行时还是 undefined，容器于是读到不完整的元数据。Nest 提供 forwardRef，把模块引用包进一个箭头函数，等两边都完成定义后再解析：

forwardRef 的作用是把解析推迟到实例创建阶段，让容器有机会先构造其中一方再补上引用。它能消除报错，但不会消除环本身。代价体现在三处：构造顺序变成隐式知识，读代码看不出谁先就绪；先构造的一方可能持有尚未完成初始化的对象，在 OnModuleInit 里调用对方方法时要格外小心；测试时必须原样复制这套延迟引用，否则测试通过而线上失败。请求作用域介入后，延迟解析与按请求重建叠在一起，问题会更难复现。

更值得做的是判断这个环说明了什么。两个服务互相调用，往往意味着它们共享了同一块领域知识，应该把这块知识下沉成第三个 provider，例如一个独立的统计仓储；也可能是模块切得太细，两个模块本来就该合并。模块级的环则常来自“桶文件”式的再导出，把公共依赖移到更下层就能解开。只有在边界确实合理、只是初始化顺序需要调整时，才保留 forwardRef，并在代码里写清楚为什么成环。

与 Express 中间件的分工

从 Express 转到 Nest 的人，第一反应往往是把鉴权、日志、参数处理全部写成中间件。Nest 确实支持中间件，类中间件实现 NestMiddleware 的 use 方法，在模块的 configure 里按路径绑定，还能通过构造函数注入依赖，比 Express 的中间件更灵活。但 Nest 在中间件之后还有一层固定的请求管线，把不同职责拆给了不同构件，硬把逻辑塞进中间件会绕开这些机制。

构件 执行位置 能看到什么 适合做什么
中间件 路由处理前 原始请求与响应对象 请求日志、请求头规范化、原始体处理
守卫 进入处理器前 ExecutionContext 与路由元数据 认证、角色与权限判断
拦截器 处理器前后 调用上下文与返回值流 计时、结果包装、缓存、审计
管道 参数进入处理器前 单个参数的值与类型元数据 类型转换、DTO 校验
异常过滤器 抛出异常后 异常对象与宿主信息 统一错误响应格式

这张表最重要的信息是顺序：中间件最先执行，守卫次之，拦截器再包住管道与处理器。守卫能读到路由上通过 SetMetadata 附加的信息，因此适合做声明式鉴权；中间件拿不到这些元数据，只能看 URL 和请求头，写在里面的权限判断会随着路由增多而变成一堆字符串匹配。管道负责“这个参数是否合法”，守卫负责“这个请求是否允许”，拦截器负责“调用前后要做什么”，三者的边界清楚，测试也能各测各的。中间件与请求管线的完整细节不在这里展开，本文只强调一点：能用守卫和管道表达的逻辑，不要退回中间件。

测试：替换依赖，而不是启动整个应用

Nest 的可测试性来自注入容器。单元测试用 Test.createTestingModule 建一个独立的容器，只放被测 provider 和它的直接依赖，不需要 HTTP 服务器，也不需要真实数据库。容器里的任何令牌都可以用 useValue 换掉，仓储、邮件客户端、时钟都变成可控的假对象。

compile() 只负责构建容器，不会监听端口；要拿到可以发请求的应用，还得在 createNestApplication() 之后显式调用 init()，端到端测试里这一步经常被漏掉。测试真实模块时，可以用 overrideProvider 在完整依赖图上做局部替换：

overrideProvider 接受类、字符串或 Symbol 令牌，返回的构建器还支持链式替换多个 provider。它适合“模块装配是真实的，只有外部依赖是假的”这类测试；如果连服务本身也替换掉，测试就失去意义了。

端到端测试则换一个思路：导入 AppModule，创建真实应用，用 supertest 发请求，验证路由、守卫、管道、过滤器串起来的整体行为。

测试模块与真实应用有三处差异需要心里有数。第一，main.ts 里的全局配置不会被复制，setGlobalPrefix、useGlobalPipes 都要在测试应用上重新设置，否则路由对不上或校验不生效。第二，只在根模块注册的全局模块与全局增强器，在只导入某个 feature module 的测试里并不存在，注入会失败。第三，环境变量与配置文件可能指向测试环境，断言里不要依赖具体的端口或外部服务。比较稳妥的组合是：大量用替身的单元测试，加上少量导入 AppModule 的端到端测试，后者负责证明“接线正确”，前者负责证明“逻辑正确”。

配置与环境：让缺失的密钥启动即失败

Nest 6 时代读取环境变量的标准做法是 @nestjs/config，它封装了 dotenv，并把配置变成一个可注入的 ConfigService。在根模块里调用 forRoot，把 isGlobal 打开，其他模块就不必反复导入。真正值得花时间的是校验：环境变量天生是字符串，端口要转成数字，枚举要限制取值，密钥缺失应该在启动时暴露，而不是在第一次签名时抛错。

validationSchema 在启动阶段执行，校验后的值会进入 ConfigService，get('PORT') 拿到的已经是数字。缺失 JWT_SECRET 或长度不足时进程直接退出，这是好事：配置错误越早发现，修复成本越低。envFilePath 也可以指向多个文件，适合把公共默认值与环境差异分开管理。生产环境通常不把配置文件带进镜像，配置由进程环境或密钥管理服务注入，代码里只保留读取逻辑。

密钥纪律只有一条：不要写进代码，也不要提交进仓库。.env 放进 .gitignore，示例文件只保留键名和占位符；日志里不要打印整个配置对象；ConfigService 也不要直接塞给控制器，让每个模块注入自己需要的那几个键，或者包一层带类型的配置服务，把字符串键收敛到一处。这样换配置来源时，改动不会散落在业务代码里。

常见坑与排查顺序

第一个坑是忘记 exports。报错通常长这样：“Nest can’t resolve dependencies of the UsersService (?). Please make sure that the argument UserRepository at index [0] is available in the OrdersModule context.” 关键词是最后的模块名，它告诉你容器在哪个上下文里找不到依赖，而不是依赖本身不存在。修复方式有两种：把 provider 加进提供者模块的 exports，或者让使用方直接导入提供者模块。前者更符合边界设计。

第二个坑是 provider 重复注册。同一个类出现在两个模块的 providers 里，容器会各建一份实例。症状很隐蔽：内存缓存看起来失效、定时任务执行两次、数据库连接数比预期多一倍。排查时可以在启动后打印关键 provider 的构造次数，或者在测试里用 TestingModule.get 取两次比较引用。修复方式是只在一个模块注册并导出，其他地方导入模块；需要别名时用 useExisting，不要用 useClass 再造一份。

第三个坑是滥用请求作用域。一个 service 加了 Scope.REQUEST，整条注入链都按请求重建，压测时 QPS 下降、垃圾回收频繁，却很难联想到作用域。判断标准很简单：这个依赖是否真的每个请求都不同？如果只是要拿当前用户，优先在控制器取出来，作为参数传给服务；确实需要贯穿多层时，再把请求作用域限制在边缘的一个上下文服务上。

第四个坑是用 forwardRef 掩盖设计问题。两个模块互相导入、两个服务互相注入，加完 forwardRef 报错消失，团队就默认问题解决了。实际上依赖图仍然成环，初始化顺序、测试替身、请求作用域都会在后期出问题。每次写 forwardRef 都应该附带一句注释，说明为什么不能拆；如果说不出来，就该拆。

第五个坑是在构造函数里做重 IO。连接数据库、拉取远程配置、扫描目录，这些操作放在构造函数里会让“创建一个对象”变成“启动一个系统”。单元测试构造 provider 时会被迫连接真实资源，失败信息也会被模块加载栈淹没。正确做法是构造函数只赋值，把 IO 放到 OnModuleInit，并让失败直接抛错、阻止应用进入监听状态。

排查注入问题的顺序可以固定下来：先读报错里的模块上下文，确认令牌是否匹配；再查提供者模块有没有 exports；然后确认这个 provider 是否被注册了多次；最后才怀疑循环依赖与作用域。按这个顺序走，大多数问题不需要读框架源码。

小结

NestJS 的模块与依赖注入不是装饰器语法题，而是边界设计题。模块决定谁可见，exports 是显式的公开契约；provider 的四种写法决定实例从哪来，令牌决定按什么键查找；单例是默认答案，请求作用域只在边缘使用。动态模块把运行时配置纳入装配过程，生命周期钩子把初始化与释放放在可控的时间点。遇到注入失败时，先看报错里的模块上下文，再检查 exports、重复注册与循环依赖，通常能很快定位。把这几件事做对，Nest 的其余部分都只是在这张对象图上增加构件。
