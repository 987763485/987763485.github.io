Python 异常处理实践

本文属于《Python 学习路线》第 6/29 篇
上一篇系列目录下一篇

异常处理的语法只有几个关键字，工程上的取舍却不少。本文面向已经会写 try/except 的读者，讨论 Python 3.7 下如何划分异常层次、如何捕获与重新抛出、日志和重试的边界在哪里，以及 Web 与并发场景中的异常该在哪一层收口。语法基础不再重复，重点放在可维护性与排障成本上。

一、EAFP 与 LBYL：先请求原谅，还是先获得许可

Python 社区推崇 EAFP：先按正常路径操作，失败再用异常补救。与之相对的是 LBYL：先用条件判断排除失败可能，再执行。选择标准不是风格偏好，而是失败是否罕见。

字典取值是典型例子：缺键属于异常路径，直接下标访问配一个 except KeyError 意图清楚；若缺键是常态，用 get 更合适。LBYL 的真正问题在于检查与使用之间存在时间窗口：os.path.exists 返回真之后，文件仍可能在打开前被删除，先查后做在并发下天然有竞态，直接做、失败再处理反而更稳。

EAFP 也有成本，异常的抛出与堆栈展开远贵于一次分支判断。若某条路径每秒触发上万次异常，它就不该被当作异常：解析用户输入时把 ValueError 当常规分支，既慢又污染日志，应改用显式判断。一句话，罕见失败用 EAFP，常见分支用条件判断。

读取配置也是常见的取舍点：直接打开并解析，捕获异常时把文件路径写进消息，调用方一眼就知道该改哪里。这比先判断存在性再解析少一层分支，也不存在检查与使用之间的竞态。

二、异常层次与捕获粒度

所有异常都继承自 BaseException，其下四个直接子类是 SystemExit、KeyboardInterrupt、GeneratorExit 与 Exception。业务异常几乎都应是 Exception 的后代，这决定了捕获的底线：except Exception 不会接住 Ctrl+C 与进程退出，裸 except: 会。裸捕获等价于 except BaseException，会让该停的进程停不下来，也会掩盖测试失败；即便要兜底，也应写 except Exception。

内置异常按语义分族。LookupError 之下是 KeyError 与 IndexError；OSError 覆盖文件、网络与权限问题，FileNotFoundError、ConnectionError、TimeoutError 都是它的子类；ValueError 表示值不合法，TypeError 表示类型不匹配。捕获 OSError 能统一处理 I/O 故障，但只关心“文件不存在”时就该写具体类型，否则磁盘满、权限不足也会被当成同一件事。

多个 except 自上而下匹配，命中即跳出，所以具体类型必须写在前面，把 except OSError 放在 FileNotFoundError 之前会让后者永远失效。共享处理逻辑时可以用元组。原则是只捕获自己知道如何处理的异常，库函数多数时候应原样上抛，兜底留给服务边界。

as e 的绑定在 except 块结束时会被删除，目的是打断异常对象与堆栈帧之间的引用环。需要跨块使用就提前赋给另一个名字，否则会得到 NameError。这也说明异常对象不适合长期持有，记录类型与消息通常就够了。

还有一条 3.7 的细节值得记住：生成器内部意外抛出 StopIteration 会被转换成 RuntimeError（PEP 479）。在生成器里不要用 StopIteration 当普通信号往外传，需要结束就写 return。

三、try/except/else/finally 的执行时机

四个块的顺序固定：try 正常执行，无异常时进入 else，有异常且类型匹配时进入 except，无论如何 finally 都会执行。except 块内部再抛出的异常，也不会被同一组 except 接住，而是直接向外传播。else 常被忽略，它的价值是缩小 try 的范围：把可能失败的调用放进 try，把只有成功后才做的事放进 else，else 中的异常就不会被同一组 except 误捕。省略 else 时，也不要为了省事把成功后的逻辑塞回 try。

finally 的职责是清理，不是返回。在 finally 里 return 会丢弃 try 中待返回的值，也会吞掉正在传播的异常。

更隐蔽的是清理代码自己抛异常，它会替换原始异常，根因退到 __context__ 里。清理逻辑要么保证不抛，要么单独捕获并记录：关闭失败不该盖住主流程的错误，但也不能完全无声。finally 中的 break 同样会改变控制流，也应避免。

四、自定义异常：为业务建立词汇表

内置异常描述的是语言层面的错误，业务含义需要自己表达。常见做法是建立应用异常基类，再按“调用方可能采取的动作”划分子类，而不是按错误消息划分。

收益有三点：边界层用一个 except AppError 就能统一映射状态码与响应体；订单号、资源 ID 等结构化字段随异常传递，日志和响应直接可用，不必解析字符串；测试也有稳定的断言目标。

在基类上再加一个 retryable 标志，边界层就能据此决定是否重试，而不必把类型判断散落到各处。字段里不要放密码、令牌与完整请求体，异常对象经常被原样序列化进日志。

反面做法是每发现一个错误就新建类，最后得到几十个只差一句话的异常，捕获方无从下手。判断标准是调用方是否需要区别处理：需要区分重试、提示用户或告警就分开，否则合并，差异放进消息与字段。也不建议让业务异常多重继承内置异常，那会让“捕获 ValueError”的含义变模糊。

五、异常链与重新抛出

异常在传播途中被替换，是排障困难的常见来源。在 except 块里抛出另一个异常，解释器会自动把原异常挂到新异常的 __context__ 上；写 raise NewError(...) from e 则显式设置 __cause__。两者都保留根因，区别在语义：from e 表示“我确认由它引起”，适合跨层包装；隐式链只说明处理旧异常时又出了新问题，多见于清理失败。

from None 关闭隐式链的展示，适用于底层异常只是实现细节的场合，例如把 KeyError 转成对外的“配置缺失”。它只影响展示，__context__ 仍然存在，调试时依旧取得到。

日志里看到 “The above exception was the direct cause” 说明用了 from e，看到 “During handling of the above exception” 则是隐式链。两者都意味着根因在更靠下的堆栈里，排查应往下看，而不是只盯着最后一行。

重新抛出时，裸 raise 与 raise e 不同。裸 raise 在原位置继续传播，traceback 保留最初的抛出点；raise e 在当前行重新抛出同一个对象，会追加当前帧，看起来错误像是发生在这里。日志里的出错行也会指向重新抛出的位置，掩盖真正的失败点。需要原样上抛时，永远用裸 raise。

若调用方需要根据原始异常做决策，比如区分超时与拒绝连接，就不要包装；只有跨越抽象层次时才包装并保留 cause，让日志里两层信息都在。

六、日志与重试：记录一次，重试有限

异常日志最常见的错误是重复。每一层都记录再抛出，一次故障打出五段相同堆栈，真正有用的那条被淹没。约定应该是：谁处理，谁记录。中间层只补充上下文后继续抛，最外层统一记录一次。

logger.exception(msg) 等价于 logger.error(msg, exc_info=True)，只能在 except 块内使用，否则记录到的是 NoneType: None。两者选哪个不影响结果，团队统一即可。业务标识放进 extra 而不是拼进消息，便于日志系统按字段检索。

这里的 raise 说明记录不等于处理，上层可能还要回滚事务或返回错误响应。

日志级别也要区分：可预期的业务异常用 warning 并带上 code，未预期异常才用 error 或 exception，否则告警会被大量 400 淹没。记录前确认消息里没有密码、令牌与完整身份证号，异常文本经常原样带出用户输入。

重试只对暂时性故障有意义：连接超时、连接被重置、服务端 502/503、数据库死锁。参数错误、鉴权失败、资源不存在，重试多少次结果都一样，只会放大故障。重试还需三个条件：操作幂等或带幂等键、有最大次数与总时限、退避带抖动，避免所有客户端同时涌向刚恢复的服务。

重试要包住单个可重试的动作，而不是整段业务流程，否则可能重复扣款、重复发消息。退避的上限也要设，指数增长几轮后会变成分钟级等待，而请求早已超时。重试次数与最终耗时都应上报指标，否则退避是否生效、故障是否在扩散都无从判断。第三方库的异常未必等于内置类型，例如 requests 的连接错误与超时都有自己的类，应先映射再进入重试逻辑。

七、上下文管理器：把清理写成协议

with 把“进入时准备、退出时清理”固化成协议：__enter__ 的返回值绑定给 as 后的名字，__exit__ 接收异常类型、异常值与 traceback，返回真值表示异常已被处理，不再向外传播。

__exit__ 返回 False 或 None 是最常见的正确写法：清理做完，异常继续飞。返回 True 等于吞掉整段代码的异常，除非清楚后果，否则不要用。

用 contextlib.contextmanager 写资源类往往更短：yield 之前是进入逻辑，之后是清理逻辑，try/finally 保证清理一定执行。contextlib.suppress 是“只忽略指定异常”的语法糖，比空 except 更能表达意图，例如删除临时文件时忽略 FileNotFoundError。

清理本身也可能失败，__exit__ 抛出的异常会替换正在传播的异常。关闭连接、删除临时文件这类操作，应在 __exit__ 内部自行捕获并记录。需要同时管理多个资源时，可以用 contextlib.ExitStack 依次注册，退出时逆序清理，避免多层嵌套的 with。

八、并发、异步与 Web 边界

并发代码里的异常不再沿调用栈直线上浮，而是被 Future 或 Task 收起来。concurrent.futures 中，future.exception() 返回异常对象而不抛出，future.result() 才重新抛出并带上工作线程的堆栈。用 as_completed 遍历时必须逐个调用 result()，否则失败会被静默忽略。线程池的异常不会让主线程崩溃，只会在取结果时暴露；提交任务后从不取结果，失败就永久丢失。

asyncio.gather 默认在第一个异常处向外抛，但其余协程不会被自动取消，仍在后台运行；return_exceptions=True 则把异常当作结果返回，调用方必须逐个判断。两种行为都不算错，错的是不知道它们存在。Task 的异常若始终没人 await，回收时只会打印一条 Task exception was never retrieved，极易被忽略。协程的细节留给后续文章，这里只需记住：并发中的异常必须显式收口。

Web 层是最后一道关口。Flask 用 @app.errorhandler 按异常类注册处理器，Django 用中间件的 process_exception，或在视图层把领域异常转成响应。共同原则是：领域异常映射为稳定的状态码与统一响应结构，日志记录完整堆栈与请求标识，响应体只给用户可读的信息。客户端错误用 warning 级别，服务端错误用 error 并触发告警，两类问题不应混在同一条告警规则里。

生产环境绝不能把 traceback 返回给客户端：堆栈里有文件路径、SQL 与内部主机名，是信息泄露的常见入口。错误码与提示文案也应分离，客户端按 code 分支处理，文案随后可以独立调整。

九、常见反模式清单

把前面的讨论压缩成清单，评审代码时可以直接对照：

  • 裸 except: 或 except BaseException，吞掉中断与退出信号。
  • except Exception: pass，故障静默，问题延后爆发且更难定位。
  • 用异常做常规流程控制，解析、判空、循环终止都靠抛异常，性能与可读性双输。
  • 在 finally 里 return 或抛异常，覆盖返回值，吞掉或替换原始异常。
  • 捕获过宽后按消息判断，if "timeout" in str(e) 依赖文案，升级依赖即失效。
  • 记录后又抛出，层层重复，一次故障多段堆栈。
  • 包装时忘记 from e，根因丢失，只剩一句“操作失败”。
  • 用 raise e 代替 raise，堆栈多出一帧，误导排查方向。
  • 对业务校验错误重试，无意义地放大负载。
  • 把异常对象当返回值传给上层，调用方容易忘记检查。

小结

异常处理的目标不是“不报错”，而是让错误在正确的位置被处理，并留下足够的排障信息。只在能处理的地方捕获，按具体类型捕获；用自定义异常表达业务语义，用 raise ... from 保留根因；在边界统一记录一次日志并映射对外响应；只对暂时性故障做有上限、有退避的重试；清理逻辑交给上下文管理器，不在 finally 里改变控制流。把这些落成团队约定，异常代码才不会退化成一片 pass。
