安全域划分与边界防护

安全域划分解决的不是买什么设备，而是先回答“谁可以和谁说话、说到什么程度”。很多团队把网络画成一张大平面，靠一台防火墙隔开内外，一旦攻击者进入内网，横向移动几乎没有阻力。本文从划分方法讲到访问控制矩阵、设备分工、防火墙策略、DMZ 与微隔离，最后落到变更运营和等保 2.0 映射，适合正在做整改或梳理内网边界的工程师。

安全域的本质是信任边界

安全域（Security Zone）是一组具有相同业务属性、数据敏感度和信任级别的资产集合。域内可按较宽松的规则通信，跨域则必须经过边界设备，按最小权限逐条放行。划分不是为了把网络切碎，而是把大量点对点关系收敛成少量域间关系，让策略可写、可审、可维护。

域内信任，不等于域内不设防

“域内信任”不是同一网段可以随便访问。它指域内主机身份和用途相对可控，边界不必为每台主机单独设规则，防护重心放在主机加固、账户、补丁和审计上。即便如此，数据库区内部也不应允许任意主机互访，管理区同样要区分管理员的操作范围。

反过来，如果域内主机已经被攻陷，域边界就是阻止扩散的最后一道闸门。因此域内信任的前提是资产清楚、基线达标、日志完整，否则只是心理安慰。

三条划分轴：业务、数据、信任级别

实际划分通常同时考虑三条轴。业务轴按职责分，例如交易、订单、内容、办公；数据轴按敏感度分，例如公开数据、个人信息、支付数据、密钥；信任级别轴按暴露面和失陷后果分，例如互联网可达、合作方可达、仅内部可达、仅运维可达。

三条轴冲突时，优先级由风险决定：数据敏感、暴露面大的系统，即使同属一个团队，也应单独成域。常见错误是照组织架构图划域，部门各一个域，结果同一个域里既有公网门户，又有存着身份证号的数据库。

划分方法：从业务清单到边界

划分不是对着拓扑图拍脑袋，而是有输入、有输出、可复核的过程。稳妥顺序是业务梳理、数据流、资产分级、边界识别，最后才是地址规划与设备选型。

业务梳理先列出所有对外和对内服务，写清负责人、用户群体、峰值流量和依赖关系。数据流梳理沿一次完整请求，标出每一跳：浏览器、CDN、负载均衡、应用、缓存、数据库、消息队列、第三方接口。资产分级把主机、数据库、中间件、存储按重要程度和敏感度打标签，至少区分核心、重要、一般三级。边界识别则寻找信任级别变化的位置，这些位置就是防火墙、代理或网关应当部署的地方。

边界识别比地址规划更重要

很多项目先分 IP 段，再倒推区域，最后发现同一段里混着测试机和数据库。正确做法是先确定边界，再为每个域分配连续地址段；地址段只服务于路由和策略聚合，不承担安全语义。边界不一定是防火墙：跨云专线、容器入口、VPN 网关、API 网关都可能是信任级别的分界点。

边界确定后形成三份文档：区域清单写职责、负责人、地址段与资产范围；互联清单写域间全部访问关系；设备清单写每个边界由什么设备控制。

典型区域与暴露面

区域名称各家不同，但职责相通；写清每个区域“谁能进来、能去哪里”，比争论名字更有价值。

互联网接入区是外部流量的第一站，通常部署边界路由器、清洗设备、外网防火墙和反向代理。它暴露面最大，只允许已登记的业务端口进入，管理面绝不暴露公网，入站连接必须经过 NAT 和策略双重收口。

DMZ 放置必须被互联网访问、又不该接触核心数据的服务，例如门户静态资源、API 前置、邮件网关、文件交换。DMZ 主机即使被攻陷也不能横向进入应用区和数据区，到内网的连接应极少且明确到端口。

应用区承载业务逻辑，只接受 DMZ 和办公区的已授权请求，不直接面向互联网。数据区存放数据库、缓存、对象存储和备份，只接受应用区和运维管理区的连接，禁止办公终端直连，禁止公网地址映射到数据库端口。

管理区是运维人员进入各区的唯一入口，堡垒机、跳板机、监控、日志、补丁服务器放在这里。访问方向应是管理区到被管对象，而非反过来；管理区不承载业务，也不与办公区混在一个 VLAN。

办公区面向员工终端，暴露面来自钓鱼、恶意软件和违规外联。控制重点是出网代理、终端准入、办公到应用的按需授权，而不是把办公网当成可信内网。开发测试区单独隔离，使用脱敏数据，禁止配置生产数据库连接，代码发布走独立制品通道。

访问控制矩阵

区域图回答“分成几块”，矩阵回答“块与块之间通什么”。每一行是一条访问关系，至少包含源域、目的域、协议、端口、用途和审批人，落地时再加有效期、工单号、执行设备和复核记录。

矩阵的核心纪律是默认拒绝。没有登记的组合一律不通，而不是“先放着，出事再说”。每条放行都要能回答：为什么需要、为什么是这些端口、为什么范围不能再小。回答不了的规则，要么补材料，要么删掉。

最小权限在矩阵里体现为四个“具体”：源具体到地址组而非整个私网，目的具体到服务而非整个网段，端口具体到监听端口而非端口范围，时间具体到项目周期而非永久。临时联调、第三方支持必须设到期时间，到期自动失效，避免临时规则变成永久后门。

矩阵还是业务与安全之间的契约。应用负责人签字确认访问关系，安全团队把它翻译成设备策略，运维负责执行和留档。矩阵更新必须先于策略变更，不能出现设备已放通、文档还写着禁止的情况。每季度用实际流量与矩阵比对，既能发现漏登记的连接，也能发现没人使用的僵尸规则。

边界设备的分工

边界防护常被简化成“买一台防火墙”，但不同设备回答不同层面的问题，可以重叠部署，却不能互相替代；职责一混，某类攻击就会成为盲区。

防火墙工作在网络层和传输层，核心是五元组过滤与状态检测：源地址、目的地址、源端口、目的端口、协议，加上连接状态。它能精确控制“谁能连谁”，却看不懂 HTTP 参数里有没有注入，也分不清正常登录和暴力破解。

WAF 工作在应用层，解析 HTTP 请求头、URL、参数、Cookie 和上传内容，能识别注入、跨站脚本、恶意文件上传等攻击。它通常以反向代理或串接方式部署在 Web 入口，适合保护 80 和 443 端口，但对数据库协议、SMB 共享、内网远程桌面无能为力。

IDS 与 IPS 的差别在动作：IDS 旁路镜像，只告警不阻断；IPS 串接在链路中，可以丢弃会话。它们擅长发现扫描、漏洞利用、木马回连和口令爆破，但受加密流量和性能约束，不能替代防火墙做精细的访问控制。

堡垒机是运维流量的统一入口，负责账号托管、权限分配、命令审计和会话回放。它解决“谁在什么时间对哪台机器做了什么”，而不是网络隔离。把堡垒机当防火墙用，或让运维绕过堡垒机直连服务器，都会让审计链条断裂。

代理分为正向和反向。正向代理服务内部用户出网，可按域名、端口、用户做白名单，并留下访问日志；反向代理位于服务入口，承担 TLS 卸载、路由和部分防护。出网如果不收口，数据外传和恶意软件回连就很难发现。

防火墙策略设计

策略设计不是把能通的都写上，而是用最少规则表达最清楚意图。好规则只看名字就知道为什么存在。

白名单、状态检测与方向

默认策略必须拒绝，入站和出站都是。先允许业务必需流量，再显式拒绝并记录其余。状态检测让返回流量自动通过，不必为每个连接写反向规则；但 UDP、ICMP 和路由不对称场景要单独验证，否则请求出去了、响应回不来。

方向要写进规则名和注释。同一端口，应用区访问数据区与反向访问是两条规则，风险和审批人不同；写反轻则业务不通，重则留下反向通道。

顺序、分组与命名

防火墙按顺序匹配，命中第一条即停止，因此具体规则在前、宽泛规则在后。宽泛规则排前面会让后面的精细规则永不生效，这就是策略遮蔽。上线前要逐条检查遮蔽关系，尤其是宽泛规则与精细规则并存时。

地址组和服务组用于聚合，不是隐藏。地址组按角色命名，如“订单应用集群”，而不是“组 1”“临时”。成员变更留记录，避免测试机塞进生产组；嵌套不超过三层，否则排障困难。

冗余清理与 NAT

策略只增不减是通病。清理不能只看配置，要看命中计数：连续九十天零命中的允许规则，要么业务下线，要么流量改道，都应进入待确认清单。重复、被覆盖、地址组为空的规则可合并删除；删除前先在拒绝日志观察一周。

NAT 与策略的关系常被忽略。源转换改变源地址，目的转换改变目的地址，策略匹配的是转换前还是转换后，不同设备顺序不同。设计时要明确“先转换后过滤”还是“先过滤后转换”，并写全双向规则。数据库只做目的 NAT 而不做策略限制，等于把内网端口暴露给公网。

日志也是策略的一部分。拒绝日志必须开，关键允许日志按重要性选择；全开会被噪声淹没，全关则无法追溯。至少保留管理、数据库和跨区访问的日志。

DMZ 设计：把“可被攻陷”当作前提

DMZ 的设计前提不是“这里不会出事”，而是“一旦出事，不能伤到核心”。对外服务应尽量前置：静态资源、反向代理、API 网关放在 DMZ；必须由应用处理的逻辑，只暴露明确的回源地址和端口。数据库、缓存、消息队列不进入 DMZ，也不允许 DMZ 直接访问数据区。

反向代理在这里承担三件事：终止 TLS，隐藏后端真实地址；按域名和路径路由，只暴露必要的接口；统一记录访问日志，为 WAF 和审计提供输入。后端应用服务器不绑定公网地址，安全组或防火墙只接受代理地址的回源请求。这样即使某台 DMZ 主机被攻陷，攻击者拿到的也只是一个没有数据、没有内网权限的跳板。

运维通道要单独设计。不要为了“方便排查”把 SSH 或远程桌面映射到公网，也不要在 DMZ 主机上保存内网凭据。正确做法是从管理区经堡垒机接入，堡垒机到 DMZ 的规则单独审批，会话全程录屏；临时排障用完即关，不保留长期账号。DMZ 与内网之间尽量由不同的防火墙接口或不同的设备承载，避免一条策略写错就绕过了整段边界。

微隔离：把策略推到工作负载旁

传统防火墙管南北向，东西向流量在核心交换机内部转发的部分往往看不见。微隔离（Micro-segmentation）的思路是把访问控制点下沉到主机或容器，以工作负载的身份、标签和角色而不是固定 IP 来定义策略，让“应用 A 只能访问数据库 B 的 3306”这种关系在每一台主机上生效。

2019 年这项技术仍在落地早期。主机代理方案相对成熟，能覆盖物理机和主流虚拟化平台，但要解决 agent 兼容性、性能开销和跨平台管理；容器侧更多依赖编排系统自带的网络策略，跨集群、跨云仍然割裂。它适合保护核心数据，不适合一上来就全公司铺开。

实施顺序建议是：先做流量可视化，至少观察两到四周，拿到真实的东西向连接清单；再设计标签体系，按应用、环境、角色打标签，避免用 IP 当身份；然后在只告警不阻断的模式下下发策略，逐条确认误报；最后按应用灰度开启阻断，保留一键回退。微隔离不能替代区域边界防火墙，它补的是域内细粒度控制；如果区域本身没划清，直接上微隔离只会把混乱复制到每一台主机。

横向移动防护：假设边界已经被穿过

边界防护做得再好，也要假设某台主机已经失陷。横向移动防护要让攻击者即使拿到落脚点，也难找下一个凭据、难用熟悉的协议跳板、难在日志里消失。

第一道是凭据隔离。管理员账号与办公账号分开，服务器本地管理员不用统一弱口令，Domain Admin 一类高权限账号不登录办公终端和邮件服务器。运维人员用实名账号经堡垒机提权，操作可追溯；服务账号只授予运行所需权限，禁止交互式登录。凭据一旦不能复用，横向移动的成本就会显著上升。

第二道是管理面与业务面分离。管理端口只对管理区开放，业务端口只对应用区开放，两者不共用同一个监听地址和同一套账号。SMB、RDP、WinRM 这类高风险协议要在边界和主机两层限制：能不用就不用，必须用时限定源地址、账户和时段。远程管理优先走堡垒机，不允许多台服务器之间随意互连。

第三道是日志与检测点。登录成功与失败、特权组变更、服务安装、计划任务创建、防火墙拒绝记录、DNS 异常查询，都是横向移动的影子。日志要统一时间、集中采集，并设置基线告警，例如某台 Web 服务器突然向数据库端口发起大量连接，或办公终端在深夜登录多台服务器。检测不追求一次抓准，追求把异常从噪声里挑出来。

远程接入与第三方

远程办公和第三方运维是边界上最容易被开口子的地方。VPN 仍是 2019 年的主流方案，但必须配合多因素认证、实名账号、终端合规和最小路由：只下发需要的网段，不做全内网通吃；分离隧道要谨慎，避免终端一边连内网一边把流量交给不可信网络。账号离职即停，长期不用自动禁用。

零信任在当年更多是一种方向而不是成熟产品：不再默认“内网即可信”，而是每次访问都验证身份、设备状态和上下文，按应用授权而不是按网段授权。落地可以从暴露面最大的一两个系统开始，先做统一身份、强认证和细粒度代理，不必推倒现有网络。它和区域划分并不矛盾，区域解决粗粒度隔离，零信任解决“同一个区域内也不默认放行”。

第三方接入要单独成域。专线或 VPN 只允许到达合同约定的系统，源地址、目的地址、端口、时段四者同时限定；对方账号由本方创建，不使用共享账号；接入过程有本方接口人陪访，操作留日志。项目结束要同时回收网络策略、账号、证书和专线，不能只停账号忘了关端口。

变更与运维：让策略可追溯

策略变更必须走工单，工单里写清业务原因、源和目的、端口、持续时间、影响范围和回滚方法。执行前由第二个人复核，重点看方向是否写反、地址组是否选错、是否会被更宽的规则遮蔽；涉及核心区或管理区的变更，安排在业务低峰窗口，并提前通知值班人员。

变更后要验证，而不是“保存即完成”。从源端发起连接，确认放行符合预期；再从非授权源发起连接，确认拒绝生效；查看命中计数和日志，确认流量走新规则而非旧规则。回滚方案提前准备，至少能恢复到变更前的配置版本，不能靠记忆手工反向修改。

策略审计建议每季度一次，按“矩阵、配置、流量、日志”四样对照：矩阵里有但配置里没有的，是漏配；配置里有但矩阵里没有的，是违规；有配置但长期零命中的，是候选清理对象；日志里出现但矩阵里没有的，是未知连接。审计结果要有负责人签字和整改期限，否则下一次审计会发现同样的问题。

与等保 2.0 的方向性映射

等保 2.0 的 GB/T 22239-2019 已于 2019 年 5 月 10 日发布，将于 12 月 1 日实施。本文写作时仍处于新旧标准衔接期，具体控制项和测评口径应以正式标准和测评机构要求为准，这里只谈方向，不引用条款号。

2.0 常被概括为“一个中心、三重防护”：安全管理中心，以及安全通信网络、安全区域边界、安全计算环境。区域划分正好是“安全区域边界”的落地基础：先有域，才谈得上域间访问控制、入侵防范和恶意代码防范；管理区与堡垒机对应“安全管理中心”的集中管控思路；主机加固、账户权限、审计日志对应“安全计算环境”；网络架构、通信加密和带宽保障对应“安全通信网络”。

映射的价值是把合规语言翻译成工程动作，而不是为条款堆设备。区域清单、互联矩阵、边界策略、日志留存既是检查会看的东西，也是日常运营的底稿；底稿做实，测评时只需导出和抽样。

常见问题

域划得过多，管理成本失控。 有的团队按每个应用一个域，最后几十个区域、上百条互联关系，策略没人维护得过来。划分粒度应由信任级别差异决定，同一信任级别、同一数据敏感度、同一运维主体的系统可以合并；一般企业从五到八个区域起步足够，规模变大后再细分。

默认放通，靠黑名单挡攻击。 “先全通，出事再封”在早期很方便，却把安全建立在已知威胁上。正确顺序是默认拒绝、按矩阵放行、记录拒绝流量；新业务上线前先提交访问关系，而不是不通了再临时开全网。

策略只增不减。 项目结束、系统下线、临时联调到期，规则却留在设备上。每季度清理零命中规则，给临时规则设到期时间，变更时同步更新矩阵，策略规模才不会失控。

管理区与业务区混用。 堡垒机、监控、补丁服务器和业务应用挤在同一网段，一旦业务主机被攻陷，攻击者可直接摸到运维工具和凭据。管理区应独立成域，只允许运维终端经堡垒机进入，到业务区单向受控。

日志缺失，出事无法追溯。 只开拒绝日志还不够，NAT 转换前后的地址、用户身份、会话时长都要能关联。日志时间统一到同一时源，留存不少于六个月，并定期演练“给定一个 IP，能否还原它访问过什么”。做不到，区域划分就只剩一张好看的拓扑图。

小结

安全域划分是把复杂网络收敛成可管理信任关系的方法：先按业务、数据和信任级别定边界，再用访问控制矩阵把关系写清楚，最后用防火墙、WAF、IDS/IPS、堡垒机和代理各司其职地执行。域内信任必须建立在资产清楚、基线达标和日志完整之上，域间则坚持默认拒绝与最小权限。微隔离和零信任是方向，不是一蹴而就的替代品；比技术选型更重要的是变更纪律和季度复核。把矩阵、配置、流量、日志四样对齐，边界才真正守得住。
