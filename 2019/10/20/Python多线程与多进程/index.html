Python 多线程与多进程

本文属于《Python 学习路线》第 14/29 篇
上一篇系列目录下一篇

可 Python 程序并不会自动用满多核。很多人第一次写并发，是把一段循环丢进 Thread，跑完发现并没有变快，于是得出“Python 多线程是假的”这个半对半错的结论。本文从 GIL 讲起，梳理 threading、queue、concurrent.futures、multiprocessing 的用法与边界，最后给出与协程的取舍和排障手段。读者应已能写普通的 Python 3 脚本，读完可以判断手上的任务该用线程、进程还是协程。

一、先判断任务类型，再选并发手段

并发的手段只有三类，区别在于隔离的粒度。线程共享同一份内存，切换由操作系统调度，通信几乎零成本，但要自己处理竞态；进程各有独立地址空间，绕开了 GIL，代价是启动慢、通信必须序列化；协程在单线程内协作式切换，只适合主动让出的等待场景，遇到阻塞调用会拖住整个事件循环。

选择的关键不是“哪个更高级”，而是时间花在哪里。I/O 密集的任务，比如请求接口、读写文件、查询数据库，CPU 大部分时间在等，线程和协程都能把等待重叠起来；CPU 密集的任务，比如图像处理、文本解析、加解密，线程受 GIL 限制无法并行，只能换进程。判断方法很朴素：给代表性代码计时，再用 cProfile 看耗时集中在计算函数还是 recv、read 这类调用上；等待占比越高，并发收益越大。

    B -->|是| C{并发连接是否上千？}
    C -->|是| D[协程]
    C -->|否| E[线程池]
    B -->|否| F[进程池]

二、GIL：它是什么，以及它不保证什么

CPython 用引用计数管理对象生命周期，赋值、传参、离开作用域都在改动计数器。若多线程同时增减计数，就需要逐对象加锁，而对象数以百万计，空间与竞争成本都不可接受。于是 CPython 用一把全局锁保护解释器状态与对象计数，这就是 GIL。GIL 首先是为了让解释器实现简单、单线程性能足够好，而不是限制开发者，它也是 CPython 的实现细节，不是 Python 语言规范的一部分。

GIL 的直接后果是：同一时刻只有一个线程执行 Python 字节码。多线程跑 CPU 密集任务时，线程轮流持有 GIL，总耗时不会比单线程少，切换还带来额外开销。解释器不会一直霸占 GIL，它按固定间隔尝试切换，间隔由 sys.getswitchinterval() 决定，3.8 的默认值是 5 毫秒。

GIL 会在两类时机释放。一是阻塞操作：socket 收发、文件读写、time.sleep、等待锁与子进程，执行前先放开 GIL 再进入系统调用。二是部分 C 扩展在进入长计算前主动释放，例如 NumPy 的部分数组运算、zlib 压缩、hashlib 摘要计算。这也解释了常见现象：同样用线程，爬虫能提速几十倍，纯 Python 循环却几乎不动。

最后要划清界线：GIL 不等于线程安全。counter += 1 在字节码层面是“读取、相加、写回”三条指令，线程可能在读写之间被切换，两次自增只生效一次。GIL 只保证单条字节码不被打断，而绝大多数业务操作都由多条字节码组成；把 GIL 当同步原语，是并发 bug 的常见来源。

三、threading：从竞态到同步原语

Thread 的用法很简单：传入可调用对象与参数，start 启动，join 等待结束。下面的例子刻意制造竞态，四个线程各做十万次自增，正确结果应是四十万。

修复方式是把“读改写”整体放进临界区。Lock 不可重入，同一线程重复获取会把自己锁死；RLock 允许同一线程多次获取，适合持锁函数再调用同样加锁的函数。用 with 获取锁，异常路径也能保证释放，比手工 acquire/release 安全。

其余原语各有用处。Condition 用于“等某个条件成立”，等待方必须在 while 循环里调用 wait，因为唤醒可能是虚假的，也可能被别的线程抢先消费；Event 适合一次性开关，比如通知工作线程开始或停止；Semaphore 限制同时进行的数量，比如对外部服务的并发连接。三者都建立在锁与条件变量之上，拿它们替代 sleep 轮询，既省 CPU 也少延迟。

守护线程值得单独提醒。daemon=True 必须在 start 之前设置；主线程退出时解释器不会等待它们，而是直接终止，finally 与缓冲区刷新都可能来不及执行。守护线程只适合可随时丢弃的后台任务，需要落盘的工作必须显式 join。

四、线程安全的数据结构：queue 与 deque 的边界

标准库提供了现成的线程安全容器，首选 queue.Queue。它内部用锁与条件变量保护，put/get 可阻塞也可带超时；传入 maxsize 得到有界队列，生产快于消费时 put 阻塞，形成背压而不是吃光内存。配合 task_done 与 join，还能等队列中的任务处理完。

collections.deque 的两端进出是原子操作，append、appendleft、pop、popleft 在 CPython 中不会被打断，拿它做简单的生产者消费者队列可行，也比 Queue 轻。但原子性只覆盖单个方法：if d: d.popleft() 在判断与取出之间可能被别的线程清空，随后抛 IndexError。

内置容器同理。list.append、dict.setdefault 在 CPython 中由一次 C 调用完成，实践中常被当作原子操作，但这是实现细节而非语言承诺；if key not in d: d[key] = value 这类“检查再写入”一定是复合操作，必须加锁。单步操作可以依赖，复合逻辑一律用锁或 Queue。

五、concurrent.futures：把线程池用成接口

手工管理线程列表很快会重复：限流、收结果、传异常、等超时，每件都要自己写。concurrent.futures 把这些收进 ThreadPoolExecutor，submit 返回 Future，结果与异常都装在里面。

map 按输入顺序返回结果，写法最短，但只能传一个参数，也不方便做差异化处理。as_completed 按完成先后产出，适合“谁先回来先处理谁”的抓取。异常不会在提交时抛出，而是存进 Future，直到调用 result() 才重新抛出；从不取结果，异常就静默消失，这是线程池最隐蔽的坑，务必用 add_done_callback 记录，或在退出前遍历所有 Future。

超时有两层含义：future.result(timeout=3) 只是最多等三秒，超时抛 TimeoutError，任务仍在后台跑；as_completed(timeout=10) 是整体上限，到点后未完成的任务同样不会被取消。3.8 的 shutdown 只有 wait 参数，不能批量取消排队任务；只能自己记录 Future 逐个 cancel()，已在执行的任务无法打断。

六、multiprocessing：进程、池与启动方式

进程绕开 GIL，代价是数据必须跨地址空间传递。最基础的是 Process，接口与 Thread 对齐：传目标函数与参数，start 启动，join 等待。

Pool 的四个方法要分清：map 一次切分并阻塞到全部完成，适合批量短任务；starmap 允许元素是参数元组；imap 返回迭代器，边算边取且保持顺序；imap_unordered 同样流式，但不保证顺序。chunksize 控制每次分派的任务数，任务小调大能减少通信，耗时不均调小能让负载更均衡。

启动方式决定子进程如何诞生。Linux 默认 fork，直接复制父进程内存，启动极快，但父进程若已有多线程、持有的锁或连接，子进程会继承这些不一致状态，使用它们可能直接死锁。Windows 只支持 spawn，重新启动解释器、导入主模块、用 pickle 传参，慢但干净；macOS 从 3.8 起默认也改为 spawn。可用 get_start_method() 查看当前方式，必要时以 set_start_method("spawn") 显式指定，且必须在创建进程之前调用。

七、进程间通信与共享状态

进程之间最稳妥的方式是消息传递，共享可变状态越少越好。Queue 基于管道加锁实现，可传任意可 pickle 对象；Pipe 更轻，只有两端，适合一对一通道。共享内存用 Value 与 Array，数据在共享的 mmap 区域，读写最快，但只支持固定类型且要自己加锁。

Manager 提供另一种便利：Manager().dict() 返回代理对象，用法与本地容器几乎一样，背后却是独立的管理进程，每次读写都要过 IPC 与 pickle，单次开销比本地操作高出一到两个数量级，循环里频繁访问会把并发收益吃光。它适合少量、低频的协调状态，而不是共享缓存。

跨进程传递绕不开 pickle，限制随之而来：lambda、函数内定义的嵌套函数、打开的文件、生成器、线程锁都无法序列化；自定义类必须定义在模块顶层，否则子进程按名字找不到它。遇到 PicklingError，先看对象是不是“可导入的名字”，而不是调 pickle 参数。

跨进程的锁同样存在。mp.Lock() 可在进程间互斥，但粒度越粗，串行化越严重。死锁的四个必要条件——互斥、占有且等待、不可抢占、循环等待——在线程与进程里完全一样；对策是固定加锁顺序、避免持锁做 I/O、给 acquire 加超时。

八、进程池的坑与开销

进程池的第一道坎是序列化。pool.map(lambda x: x * 2, data) 一定失败，因为 lambda 没有可导入的名字；换成模块级函数或用 functools.partial 绑定参数即可。第二道坎是全局状态：子进程是独立副本，里面改的全局变量、日志配置、数据库连接，父进程与其他子进程都看不到。初始化状态要用 Pool(initializer=...)，让每个子进程各自建立上下文。

第三道坎是异常的呈现方式。map 与 apply 会把子进程的异常重新抛到父进程，apply_async 却只把异常存进 AsyncResult，不调用 get() 就永远看不到；子进程若被信号杀死，比如内存超限被 OOM killer 干掉，父进程可能只看到进程提前结束，连堆栈都没有。给任务加超时、记录子进程退出码，是排查这类问题的最低要求。

最容易被忽略的是入口保护。spawn 下子进程会重新导入主模块，创建进程池的代码若写在模块顶层，导入时就会再次创建进程，Windows 上直接抛 RuntimeError，Linux 上也容易演变成进程风暴。把入口逻辑放进 if __name__ == "__main__": 之下，是跨平台脚本的基本纪律。

开销方面，线程创建与切换在微秒量级，每个线程默认预留数 MB 栈空间，几百个线程就开始给调度器和内存带来压力；进程启动要复制页表、重新导入模块，通常在几十毫秒量级，还多占一份解释器内存。池大小没有万能公式：CPU 密集任务取 os.cpu_count() 即可，再多只是排队；I/O 密集可按“核数 ×（1 + 等待时间 / 计算时间）”估算，再用压测校准。不要凭感觉开一千个线程。

九、与 asyncio 的取舍

协程的细节另有专文，这里只谈边界。连接数成千上万、单次操作很短时，协程的成本远低于线程；CPU 密集任务交给进程池；手上只有阻塞库，比如 requests、旧版数据库驱动，就用线程池关住它们，而不是强行改写。

混用时只有一条铁律：不要在协程里直接调用阻塞函数。事件循环是单线程的，一次几十毫秒的阻塞就会让所有协程停摆。正确做法是用 loop.run_in_executor 把阻塞调用丢进线程池或进程池，用 await 等 Future；从其他线程投递回调要用 call_soon_threadsafe。另外，3.8 的 ThreadPoolExecutor 默认线程数改为 min(32, CPU 核数 + 4)，比早先的“核数乘五”保守，显式指定 max_workers 仍更可控。

十、调试、可观测性与常见反模式

并发问题难复现，先把现场留下来。创建线程时给 name，日志格式带上进程与线程标识，事后才能把散落的行拼回一次请求。

卡死时，faulthandler 最省事：faulthandler.enable() 让段错误打印 Python 栈，dump_traceback_later(30, repeat=True) 每隔三十秒把所有线程的栈打到 stderr，能看出大家卡在哪个锁上。进程还在跑却不出结果，可用 py-spy dump --pid 附加到运行中的进程，无需改代码或重启；py-spy top 能看到各线程占用，判断时间耗在计算、I/O 还是等 GIL。

最后列出反复见到的反模式：用线程跑 CPU 密集任务，把串行变成带切换开销的串行；忘记 join，守护线程被拦腰截断，非守护线程又把进程吊住不退出；在子进程里改全局配置，父进程与其他子进程毫无感知；用无界队列缓冲，消费一慢内存就线性上涨；用 sleep 轮询代替 Event 或 Condition，既费 CPU 又引入延迟。它们的共同点是：把并发当成加个装饰器就能生效的东西，没想清楚共享了什么、谁在等谁。

小结

GIL 让 CPython 的线程无法并行执行字节码，所以线程适合重叠 I/O 等待，进程适合吃掉多核，协程适合海量轻量连接。线程之间靠锁、条件变量与 Queue 协调，进程之间靠消息传递与少量共享内存，跨进程数据都要过 pickle。线程池与进程池能省掉大半样板代码，但要记得取回 Future 的结果，否则异常静默丢失；进程池还要守住入口保护与可序列化两条底线。动手前先 profile，动手后先加日志与线程名，比事后猜测便宜得多。
