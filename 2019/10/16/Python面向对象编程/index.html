Python 面向对象编程

本文属于《Python 学习路线》第 5/29 篇
上一篇系列目录下一篇

面向对象是 Python 中最容易被低估的部分：语法一学就会，工程上用对却不容易。本文从实例与类属性讲起，依次讨论封装、继承与方法解析顺序、组合、魔术方法、抽象基类、dataclasses 与对象生命周期，最后落到设计原则、反模式和可测试性。示例基于 Python 3.8，重点不是罗列语法，而是说明每项机制解决什么问题、代价在哪里。

一、类与实例：从 init 说起

很多教材把 __init__ 称为构造函数，这个说法并不准确。对象在 __init__ 执行之前就已经由 __new__ 创建，__init__ 只负责挂初始状态，返回值必须是 None；后面的 __new__、不可变类型与单例都依赖这一点。

方法定义在类里，调用时却自动带上实例，靠的是描述符协议：函数是描述符，通过实例访问时返回绑定方法，把实例作为第一个参数传入。所以 cart.add("A") 与 Cart.add(cart, "A") 等价，self 只是约定俗成的参数名，并非关键字。

属性查找顺序是实例字典、类字典、基类链。实例属性写在 __init__ 里，每个对象一份；类属性写在类体中，所有实例共享。问题不在共享，而在共享可变对象。

limit 适合做类属性，因为它是不可变常量；items 必须放进 __init__。若把 items = [] 写在类体里，所有购物车会往同一个列表追加商品，症状是用户看到别人的订单，且重启进程才能复现。默认参数 def add(self, item, bucket=[]) 是同一个陷阱的另一种写法，默认值只在函数定义时求值一次。

二、封装：约定、名称改写与 property

Python 没有强制访问控制，只有约定。单下划线开头表示内部使用，解释器不做限制；双下划线开头（最多一个结尾下划线）会触发名称改写，__secret 被改成 _ClassName__secret。它避免子类意外覆盖，并不防止外部访问，知道规则的人仍可直接读写。

名称改写还有副作用：子类里写 self.__x 会变成 _Sub__x，与父类的 _Base__x 是两个属性，调试时容易误判为“父类字段没生效”。团队通常只用单下划线表达“别碰”，双下划线留给需要隔离的细节。

直接暴露字段的问题不在当下，而在演化：今天 p.age = -1 没人管，明天要加校验，所有调用点都得改。@property 让读取写法保持不变，把校验放进 setter。

getter 适合轻量校验，不适合放数据库查询或网络请求，属性语法会让调用方误以为它和普通字段一样便宜。3.8 新增的 functools.cached_property 可缓存首次计算结果，适合昂贵的只读派生值，但要求实例可写且没有 __slots__。deleter 用得少，多用于释放外部资源。

三、继承与 MRO：super() 到底调用了谁

继承表达 is-a 关系，复用的是接口与实现。单继承的语义清楚，多继承则要面对菱形问题：若 B 和 C 都继承 A，D 同时继承 B、C，D 调用的方法到底走哪条路？Python 用 C3 线性化给出唯一答案，并把结果保存在类的 __mro__ 里。

输出顺序是 D、B、C、A、object，调用结果为 ['D', 'B', 'C', 'A']。规则可以概括为：子类先于父类，声明顺序靠前的基类优先，所有基类都排在自己的父类之前。C3 会拒绝无法满足这些约束的继承声明，直接抛出 TypeError。

关键在于 super() 的含义：它不是“调用父类”，而是“调用 MRO 中的下一个类”。所以 B 里的 super().ping() 在 D 的实例上会走到 C，这也是协作式多继承能工作的原因。若 B 忘记调用 super()，C 的方法就被跳过，菱形结构立刻变成隐蔽的 bug。多继承时，每个参与类都应接受并传递额外关键字参数，并在链条末端停止。

四、组合优先：把变化装配进去

继承最贵的成本是耦合。子类不仅依赖父类的公开方法，还常常依赖受保护字段、初始化顺序和内部调用关系；父类改一行，所有子类都要重新验证，业界称之为脆弱基类问题。语义也更麻烦：Stack 继承 List 看似省事，但 List 允许按下标插入，后进先出约束根本守不住。

组合把“是什么”换成“有什么”：对象在构造时接收协作者，行为可运行时替换，测试时能塞入假实现。下面的报表类不关心格式化细节，只依赖一个 format 方法，这就是策略模式，也是最朴素的依赖注入。

该继承的时候也有明确信号：需要模板方法，由父类固定流程、子类填步骤；需要抽象基类约束接口；或者框架要求继承某个基类。判断标准不是“能不能复用代码”，而是子类是否真的可以替换父类而不破坏调用方。拿不准时先用组合，等共性稳定后再提取基类。

五、魔术方法：让对象融入语言习惯

魔术方法的语义由解释器规定，写错不会报错，只会产生奇怪的结果。

__repr__ 面向开发者，理想形式是能重建对象的表达式；__str__ 面向用户。只定义 __repr__ 时，str() 会回退到它，因此至少把 __repr__ 写好，日志和调试器都会受益。

__eq__ 与 __hash__ 必须一起考虑。类一旦定义 __eq__，__hash__ 会被隐式置为 None，实例立刻不可哈希；若对象要放进 set 或做字典键，就得显式实现 __hash__。约束是：相等的对象哈希必须相同，参与哈希的字段必须不可变。用可变字段算哈希，对象修改后就再也找不回来。

比较时返回 NotImplemented 而非 False，给解释器尝试反射方法的机会；直接返回 False 会让对称比较出现偏差。示例假定金额与币种创建后不再修改，否则哈希值会漂移。

容器协议同样常用：__len__ 支持 len，__iter__ 支持 for，__getitem__ 支持下标并兜底迭代，对象因此能传给 sum、sorted。上下文管理器靠 __enter__ 与 __exit__，后者返回 True 会吞掉异常，通常应返回 False 或 None。

运算符重载要克制：向量相加符合直觉，给“发送邮件”定义加号只会让人困惑。

六、类方法与静态方法

@classmethod 的第一个参数是类而不是实例，最常见的用途是替代构造器：从字典、环境变量或文件创建对象。写成类方法后，子类调用会得到子类实例，而写死类名的静态工厂做不到这一点。

@staticmethod 不接收 self 也不接收 cls，本质是挂在类命名空间里的普通函数。它的价值是归类与覆写：函数只服务这个类、子类可能想换实现时，放进来合理；若与类状态无关，模块级函数更直白，也更好测。不要把类当成命名空间垃圾桶。

类方法也常被用来实现单例，但单例把依赖藏进全局状态，测试之间互相污染；除非确实只有一个实例，否则用注入替代。

七、抽象基类与协议

抽象基类解决“接口写了但没人遵守”的问题。继承 abc.ABC 并用 @abstractmethod 标记的方法，在实例化时检查：少实现一个就抛 TypeError。检查发生在实例化而非定义类时，拼错方法名往往要等到运行时才暴露。

ABC 还支持 register 把第三方类注册为虚拟子类，isinstance 会认，但不会继承任何实现，适合适配已有类型。

3.8 引入的 typing.Protocol 提供了另一条路：结构化子类型。只要对象有相同签名的方法，就满足协议，不需要显式继承。它主要服务静态检查器，运行时不强制；加 @runtime_checkable 后可用于 isinstance，但也只检查方法是否存在，不检查签名。

鸭子类型的边界在于文档与测试。“需要哪些方法、各自什么语义”必须写清楚，并用假实现验证。协议宜小，三五个方法足够；塞进二十个方法，等于没有抽象。

八、dataclasses：值对象的捷径

dataclasses 在 3.7 进入标准库，用类型注解自动生成 __init__、__repr__ 和 __eq__，适合值对象与传输结构。它没有运行时校验，注解只是声明，别把它当成 ORM 或表单验证。

可变默认值必须用 field(default_factory=...)，直接写 items: list = [] 会抛 ValueError，这也比普通类安全。frozen=True 生成不可变对象并顺带提供哈希，但只阻止字段重新赋值，字段指向的列表仍可修改，深不可变要自己保证。order=True 按字段声明顺序生成比较方法，字段顺序因此变成公开契约，调整时需谨慎。__post_init__ 用来做校验或计算派生字段，同时使用 frozen 时赋值要绕过限制，说明这个组合不适合。

取舍上，纯数据、相等性由字段决定、行为很少时用 dataclass；有复杂不变式、需要大量行为或延迟加载时，普通类更清楚。继承时还要注意默认值顺序：带默认值的字段不能排在无默认值字段前面。

九、对象生命周期：别把清理交给析构

__new__ 负责创建并返回实例，__init__ 负责初始化。日常几乎不需要重写 __new__，例外是继承不可变内置类型，或需要控制实例创建，例如缓存与单例。

__del__ 是最不该依赖的钩子。何时调用取决于引用计数与垃圾回收，循环引用时更晚；解释器退出时不一定执行，异常也只会被忽略。用它关闭文件、提交事务或写日志，迟早会丢数据。

正确做法是把资源生命周期收进上下文管理器，用 with 保证每条退出路径；需要兜底时用 try/finally，进程级清理用 atexit。关键清理必须发生在确定的代码路径上，而不是寄托于析构。

十、设计原则：落到可执行的判断

设计原则落到 Python 里都是具体的判断。

单一职责：一个类只回应一类变化。报表类既拼 SQL 又排版又发邮件，改模板要回归数据库逻辑；拆成取数、格式化、发送三段，各自可测。

开闭原则：新增一种导出格式应加一个类，而不是在 if fmt == ... 里再加分支，策略注入天然满足。

里氏替换：子类必须能替换父类。矩形与正方形是反例：正方形限制宽高相等，调用方设宽后按面积公式计算，结果不符预期。子类若要收窄输入或抛出父类没有的异常，就不该继承。

接口隔离：小而专的协议优于大而全的基类，客户端只依赖用到的方法。

依赖倒置：高层策略与低层细节都依赖抽象。业务服务依赖 Mailer 协议而非具体 SMTP 类，换供应商只改组装处。

十一、常见反模式

反模式往往不是一次写坏的，而是需求堆积出来的。

万能基类：BaseManager 逐步长出连接池、权限、缓存、审计，最后没人敢改。按变化原因拆分，比按“都是管理类”归类可靠。

深继承树：超过三层的继承链，读代码要在多个文件间跳转，方法解析靠猜。用组合抽出变化点，继承只留一层。

在 __init__ 里做 IO：构造时连数据库、读文件、发请求，测试必须准备真实环境，错误也无处安放。构造只装配依赖，动作交给显式方法。

isinstance 满天飞：每加一个类型就改一遍分支，说明行为该放进类里，或用协议统一。并非禁止 isinstance，边界处分派合理，散落业务逻辑才是问题。

改了 __eq__ 没改 __hash__：对象进 set 后重复，或做字典键取不到值。两者要么一起定义，要么明确不可哈希。

把 dataclass 当万能 DTO：同一个类既做接口入参、数据库行，又做领域对象，字段一多就互相牵制。按边界拆分，转换代码更少。

十二、测试友好性

可测试性不是测试团队的事，而是类设计的副产品。构造函数注入协作者，类不自己创建依赖，测试就能用假对象替代；依赖全局变量或模块级单例，测试只能靠 monkeypatch，顺序一变就互相影响。

假对象只需实现被调用的方法并记录参数，比 mock 框架的链式断言更直白。时间、随机数、文件系统都应有明确入口，不要在方法内部直接调用。类难测通常不是测试写得差，而是职责太多或依赖被隐藏，应改设计而不是加 mock。

小结

面向对象的核心不是继承，而是边界：用封装守住不变式，用组合装配变化，用继承表达真正的替换关系。把 __init__ 限制在状态初始化，资源交给上下文管理器，相等与哈希一起设计，能避开大多数隐蔽 bug。抽象基类与协议表达契约，dataclass 承载数据，都不该越界。可测试性是最诚实的复杂度指标：难以注入依赖的类，通常也难以维护。
