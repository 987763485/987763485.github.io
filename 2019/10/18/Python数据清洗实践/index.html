Python 数据清洗实践

本文属于《Python 学习路线》第 28/29 篇
上一篇系列目录下一篇

拿到一份从业务库导出的 CSV，字段名带空格、日期混着三种写法、手机号里夹着全角字符，直接 groupby 往往得到似是而非的结果。数据清洗要做的，是把“能看”的数据变成“能算”的数据，并让每一步改动都有据可查。本文以 pandas 0.25.1、NumPy 1.17 与 Python 3.7 为例，按一条完整的链路讲清每个环节的判断依据和常见坑。读者应已熟悉 DataFrame 的基本读写与筛选。

一、清洗的目标：从原始表到可用表

清洗不是把数据改成想要的样子，而是在尽量少损失信息的前提下，让数据满足下游的计算假设。因此先明确下游要回答什么问题：算日活只需要用户与时间两列，做用户画像却要合并订单、行为和资料表。目标不同，能容忍的缺失率与异常值也不同。

一条可复用的流程是：获取、审视、清洗、验证、交付。获取时记录来源与导出时间；审视只看不改，产出问题清单；清洗按清单逐项处理，每步记录行列变化；验证用独立脚本核对关键指标；交付时连同数据字典与质量报告交给下游。顺序不能颠倒，先改后看等于边改边猜。

结构上应满足 tidy data 的三条原则：每列一个变量，每行一个观测，每种观测单元单独一张表。把“2019-01”“2019-02”做成列，月份就成了列名而不是变量，聚合会很别扭；把用户资料与订单混在一张表，一个用户有多笔订单时资料就会重复。宽表适合展示，长表适合计算。

二、载入与初探：先看清数据长什么样

读文件时就把类型信息带上，而不是全部按字符串读进来再改。dtype 指定关键列类型，encoding 处理编码差异，na_values 声明缺失标记，parse_dates 让日期列在载入时就是时间类型。这既省一次转换，也避免 pandas 把“0”或“-1”误当成有效数值。

订单号和用户 ID 一定要按字符串读。它们看起来是数字，却没有运算含义，按整数读会丢前导零，超过 2 的 53 次方还会损失精度。载入后先看 shape，再用 head 检查列名与首行，info 看非空数量和类型，describe 看数值分布；describe(include='all') 还会给出分类列的 unique、top、freq，能快速发现“同一个城市有十几种写法”。内存用 memory_usage(deep=True) 估算，浅层统计容易低估。

三、缺失值：删还是填，先问业务

先量化，再决策。df.isnull().sum() 给出每列缺失数量，除以行数就是缺失率，排序后通常能看出规律：某几列同时偏高，往往是同一条采集链路断了，而非随机丢失。把缺失率与业务时间轴对照，还能判断是系统故障、字段后来才上线，还是用户本来就不该填。

删除还是填充，取决于缺失机制与场景。缺失率极低且完全随机的字段可直接删行；关键字段缺失且无法回补的也应删行，但要记录删了多少。均值填充适合近似正态的数值列；中位数对偏态与异常值更稳健，收入、金额优先用它；众数用于分类列，却会放大某个类别；前向填充只适用于状态延续的场景，对无序的用户资料用前向填充等于把别人的值安在此人头上。

缺失本身可能是信息。“未填写”和“不适用”是两种缺失：用户没选性别，与商品没有性别属性，含义完全不同；把后者填成“未知”再当普通类别统计，结论就偏了。也不要盲目 fillna(0)：金额缺失填 0 会把“没发生”混进“发生了但为零”，均值被拉低，转化率算错。更稳妥的是保留缺失，另加一列标记，让下游决定。

四、重复值：重复往往有业务原因

duplicated() 返回布尔序列，drop_duplicates() 直接去重。整行一致的重复多半来自重复导出、重试写入或日志回放；只按主键重复而其他字段不同的记录，可能是用户改资料后留下的多个版本。先弄清哪种，否则会把有效的历史版本当成脏数据删掉。

subset 决定用哪些列判重，keep 可取 first、last 或 False。按订单号去重通常保留 last，即最新版本；保留 first 适合“首次提交为准”。keep=False 会删掉所有参与重复的行，只用于挑出可疑记录复核，直接丢掉可能连正确的那条也没了。去重后核对行数变化并抽查被删记录，确认删掉的是冗余而非本应并存的记录。

五、类型转换：让列说它该说的话

CSV 没有类型，读进来都可能是 object。类型不对，排序、聚合和时间运算都会出错：字符串金额按字典序排，“9”会排在“10”后面；日期是字符串，就没法按月重采样。转换的原则是显式、可核对，不要指望 pandas 自动猜。

astype 适合已知且干净的列，遇到无法转换的值会直接抛错，这其实是好事，能尽早暴露问题。to_numeric(errors='coerce') 把无法解析的值变成 NaN，流程不中断，但必须紧接着核对：把转换后为空、转换前非空的行挑出来，确认是“1,234”这种千分位、单位混在值里，还是真正的脏数据。to_datetime 同理，errors='coerce' 之后要统计产生了多少 NaT，而不是转完就当成功。

分类类型不只是省内存。它把取值限制在固定集合内，拼写错误会变成 NaN，排序也能按业务顺序。缺点是新增类别要先改 categories，且不能直接做数值运算，适合状态、等级、渠道这类低基数枚举列。

六、字符串清洗：不可见字符最费时间

字符串问题大多出在“看起来一样”。首尾空格、全角空格、不间断空格、零宽字符肉眼都看不出，却会让 == 和 groupby 把同一个值分成几组。清洗顺序建议先统一空白与不可见字符，再统一大小写和全半角，最后做替换与抽取。

str.normalize('NFKC') 能一次性处理全角字母、数字与兼容字符，对汉字没有影响，适合放在清洗链末端。str.split 按分隔符拆列，传 expand=True 可得到多列。str.contains 默认按正则匹配，查找“C++”这类含元字符的字面量时必须转义，或传 regex=False；str.extract 用捕获组取子串，正则中的 .* 是贪婪的，会一直吃到行尾，应改成非贪婪的 .*? 或更精确的字符类。抽取失败会得到 NaN，同样要统计失败率并抽查原文。

七、日期与时间：时区是隐藏的坑

日期列先确定格式。%Y-%m-%d 与 %d/%m/%Y 在“03/04/2019”上会给出完全不同的结果，能拿到导出规范就不要让 pandas 猜；确实混杂多种格式时，分批用 format 解析再合并，并记录每批数量。

tz_localize 给“没有时区信息”的时间贴上时区，tz_convert 则要求时间已经带时区，两者搞反会直接报错。跨时区数据先在源头统一成 UTC，展示时再转本地时区，可以避免夏令时切换那天出现重复或缺失的一小时。若原始列混着 +08:00 和 Z 两种后缀，直接 to_datetime(..., utc=True) 更稳。dt 访问器还能取 dt.date、dt.hour、dt.dayofweek，按周、按月聚合都靠它。

八、异常值：先判断，再处理

描述统计是发现异常值的第一道筛子。describe() 给出最小、最大和四分位数，最大值比 99 分位高出几个数量级，或最小值出现负数，都值得追查。箱线图常用的 IQR 规则是：低于第一四分位数减 1.5 倍四分位距、或高于第三四分位数加 1.5 倍四分位距的点视为离群。

IQR 不假设分布，对偏态数据比 Z-score 稳健；后者用均值和标准差衡量偏离，而这两个量本身会被极端值拉偏，样本小或分布右偏时，既可能漏掉异常，也可能误判长尾。业务阈值往往更可靠：订单金额为负、年龄超过 120、注册时间早于公司成立日，这类规则来自领域知识，应写进校验脚本。

关键认识是：异常值不等于错误值。大客户的单笔大额订单、促销期间的流量尖峰都是真实数据，删掉会低估业务规模。处理前回到源头确认：录入错误就修正，单位不一致就换算，真实极值就保留并单独说明。只有无法修复且影响结论时才剔除。

九、表结构：宽长转换与多表连接

先用 rename 统一列名，按需选择列并 drop 掉其余列，能让后续代码更稳。分析阶段偏爱长表，因为分组、绘图都按“维度列加数值列”工作。melt 把列名收成一列变量名，pivot_table 把变量展开成列，前者宽转长，后者做交叉汇总。转换后检查行列总数是否守恒，别把缺失组合悄悄丢掉。

多表连接先确认三件事：连接键、键是否唯一、连接后应有多少行。merge 的 how 默认 inner，会丢掉匹配不上的行；做用户宽表通常选 left。pandas 0.25 支持 validate='one_to_one' 或 'many_to_one'，键不唯一时直接报错，比事后发现行数膨胀可靠。连接前后各记一次行数，是成本最低的防线。

十、索引与排序：索引不是数据

索引影响对齐，却不属于业务字段。业务索引让 loc 查询更自然，也可能在 concat 时按索引对齐，意外产生大量 NaN。清洗阶段建议保持默认整数索引，过滤或连接后用 reset_index(drop=True) 复位，避免行号错位。

sort_values 支持多列与升降序组合，na_position 决定缺失值排前还是排后。多级索引便于表达层级，却不易扁平化与导出；下游是数据库或 Excel 时，交付前用 reset_index() 还原成列。

十一、可复现：把清洗写成管道

一次性脚本的通病是无法重跑：换机器或换批数据，结果就对不上。把清洗拆成若干纯函数，每个只做一件事并返回新的 DataFrame，再由一个入口按顺序调用。

每一步打印行数变化，跑完能看出哪一步删多了。关键中间结果落盘为 CSV 或 Parquet（需 pyarrow），既方便复查，也避免反复解析。对易错的转换，用几行手工样例做断言，以 pandas.testing.assert_frame_equal 比较预期与实际；样例要覆盖空值、全角字符、重复主键和跨时区时间。

十二、性能与内存：先省内存再谈速度

pandas 的向量化操作远快于逐行 apply，字符串清洗也优先用 str 访问器。读大文件用 chunksize 分块，每块只保留聚合结果，峰值内存就从整表降到一块。低基数文本列转成 category，内存通常明显下降，排序与 groupby 也更快，代价是类别集合需要维护。

inplace=True 常被当成省内存的银弹，其实它并不保证不产生临时对象，而且返回 None，容易写出 df = df.drop(...) 之类的错误。另一个误区是在循环里反复 append，正确做法是先收集到列表再 concat 一次。优化应以测量为准，更不要把未经测试的数字写进文档。

十三、常见坑：几个反复出现的错误

链式赋值是最高频的警告。df[df['amount'] > 0]['flag'] = 1 先在切片上取值再赋值，可能改不到原表，还会触发 SettingWithCopyWarning。应写成一行的 .loc：df.loc[df['amount'] > 0, 'flag'] = 1。

NaN 与 None 混用也常出问题。数值列缺失是 NaN，object 列里可能同时有 None、NaN 和空字符串；isna() 能识别前两者，空字符串却不算，必须先用 na_values 或 replace 统一。merge 后行数翻倍，多半是连接键不唯一，应回到粒度检查，而不是用 drop_duplicates 掩盖。浮点数比较需留容差、日期解析的日月歧义，都是“默认输入干净”的错觉；清洗恰恰是拒绝这个默认。

十四、交付：数据字典与质量报告

清洗的终点不是一张干净的表，而是一份可被下游信任的交付物。数据字典要写清字段含义、类型、单位、是否可空、取值范围和枚举值；质量报告要给出总行数、缺失率、重复率、异常值清单及处理方式。两者与数据文件放在一起，版本号与生成时间缺一不可。

与下游的契约还包括粒度、时区和刷新频率。“每行一个订单”与“每行一个订单商品”的指标口径完全不同；时间存 UTC 还是本地时间，必须提前约定。写进文档并在交付时核对，能省掉大量“数字对不上”的扯皮。

小结

数据清洗的核心不是记住多少 API，而是建立可核查的判断顺序：先看结构和分布，再决定缺失、重复、类型与异常怎么处理，每一步留下行数、比例和理由。tidy data 决定表的组织方式，显式类型与统一时区决定计算是否可信，函数化与样例测试决定结果能否重跑。真正难以替代的是业务判断，代码只是把判断固定下来。
