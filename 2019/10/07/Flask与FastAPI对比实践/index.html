Flask 与 FastAPI 对比实践

本文属于《Python 学习路线》第 20/29 篇
上一篇系列目录下一篇

Flask 与 FastAPI 是 2019 年 Python 后端最常被放在一起讨论的两个 Web 框架。前者已经稳定运行多年，后者在 2018 年底发布后迅速进入生产环境。本文不比较谁更好，而是从请求模型、校验、依赖组织、文档、生态、部署与迁移几个维度做结构性对照，帮助读者结合团队与业务做选型。读者应熟悉 Python 3.7 与基本的 HTTP 概念。

两种起点：微框架与类型优先的 API 框架

Flask 诞生于 2010 年，核心理念是「小」。它只负责路由、请求响应对象和模板渲染，底层依赖 Werkzeug 与 Jinja2，数据库、表单、认证都交给扩展。Flask 1.0 在 2018 年发布，1.1 在 2019 年 7 月跟进，API 已经相当稳定。它运行在 WSGI 之上，请求由同步的 worker 处理，这是理解后面所有差异的起点。

FastAPI 在 2018 年底公开发布，2019 年下半年处于 0.4x 阶段。它把 HTTP 层交给 Starlette（ASGI），把数据模型与校验交给 Pydantic，自己提供参数提取、依赖注入和 OpenAPI 生成。它的默认叙事是「异步优先」，但并非只能写异步：普通 def 视图会被放到线程池执行。本文示例基于 Python 3.7；3.8 即将发布，但生产依赖仍以 3.7 为主，示例不使用新语法。

定位差异决定了两者的默认工作方式：Flask 让你自己挑组件，自由但要求团队自定约定；FastAPI 把校验、文档与依赖注入做进框架，代价是接受类型驱动风格。想清这一点，后面的对比才不会沦为功能清单。

请求处理模型：WSGI 的同步 worker 与 ASGI 的事件循环

WSGI 规定的是同步调用：服务器把 environ 交给应用，应用返回一个可迭代的响应体。一个 gunicorn 同步 worker 在任意时刻只处理一个请求，遇到数据库查询、外部 HTTP 调用就阻塞，直到结果返回。要提高并发，常规做法是增加进程，或改用 gevent、gthread worker 把等待叠起来。

ASGI 把应用定义成可等待的调用，服务器与框架通过事件循环调度。一个 uvicorn 进程可以同时持有大量连接，某个请求在等待 I/O 时，事件循环转去处理别的请求。这种模型在「连接多、单次计算少、等待外部服务多」的负载下最有效，例如网关聚合、实时推送、批量调用第三方接口。

但异步不是万能加速器。若请求主要消耗 CPU，如加解密或复杂计算，事件循环会被单个任务占住，其他请求一起排队。这类工作仍应交给多进程、Celery 或独立的计算服务。判断标准很简单：时间花在等，还是花在算。等得多，异步有结构性收益；算得多，增加进程才是正解。

依赖注入：应用上下文与 Depends

Flask 没有显式的依赖注入容器。它提供应用上下文与请求上下文，current_app、g、request 在视图里随手可用；扩展通常在 create_app 里初始化。需要「当前用户」时，常见做法是在 before_request 里解析令牌并写入 g.user，视图直接读取。这种方式上手快，但依赖是隐式的：看函数签名不知道它用了什么，测试时要构造上下文。

FastAPI 的 Depends 把依赖写进签名，由框架解析、缓存与复用。数据库会话、当前用户、分页参数都可以是可调用对象，测试时用 dependency_overrides 替换。依赖显式、层次清楚，适合多人协作与需要替换实现的场景。

这里没有绝对优劣：小项目里 Flask 的上下文更轻；接口多、依赖链长时，显式依赖更容易审查。真正要避免的是把全局状态当依赖到处取用，那会让测试和维护变难。

文档：自动生成与契约维护

FastAPI 启动后自带 /docs 与 /redoc，分别是 Swagger UI 与 ReDoc，原始描述在 /openapi.json。路由、参数、模型、响应状态都会进入文档，字段说明取自 Field。对前后端分离的团队，这就是可执行的契约：模型改了，文档随之变化，联调少一轮口头确认。

Flask 默认没有这层能力。可以用 flask-restful 组织资源，再配 apispec 或 flask-smorest 生成 OpenAPI；也可以用 flasgger 从 docstring 或 YAML 读注解。方案都可行，但声明与实现是两套东西，需要纪律保持同步，否则文档很快过期。

文档的价值不在「好看」，而在减少沟通与回归风险；接口对外且变更频繁时，自动生成的收益最明显，只有几个页面的后端则手写 Markdown 也够用。

生态与成熟度：存量优势与演进风险

Flask 的扩展生态是最大资产：数据库有 Flask-SQLAlchemy，登录有 Flask-Login，迁移有 Flask-Migrate，权限、缓存、限流都有现成选择。大量 2014 到 2018 年的项目仍在运行，招聘市场上「会 Flask」几乎是 Python 后端默认要求，问题也容易搜到答案。

FastAPI 年轻得多，2019 年仍处于 0.x。核心功能可用，但小版本调整参数、重命名模块并不罕见，Pydantic 也还在 1.0 之前，升级偶尔要改代码。周边生态在快速补齐，尚未形成 Flask 那样的稳定惯例。选择它意味着接受较快的演进，同时锁死依赖版本、升级前读变更记录。

成熟度不等于质量：老生态轮子多、学习成本低，新框架历史包袱少、类型体验好。团队要评估的是「谁承担升级与踩坑的成本」，而不是只看 GitHub 星数。

性能：只做结构性分析

本文不引用任何 benchmark 数字。跑分受硬件、Python 版本、worker 数量、请求体与序列化方式影响，照搬网上的数字没有参考价值。能做的是看清开销来源。

第一是等待模型。I/O 密集且下游延迟高时，异步能用更少进程撑住更多连接，内存也更低；下游很快、以计算为主时，同步多进程并不吃亏。第二是序列化。FastAPI 用 Pydantic 校验并序列化响应，字段多、嵌套深时有额外开销；Flask 配 marshmallow 同样有开销，手写 dict 最省但易错。第三是启动与内存。ASGI 应用与 Pydantic 模型在导入期构建，冷启动略重；Flask 通常更轻，但常驻服务里差距很快被摊薄。

真正可信的做法是拿自己的接口与数据量压测：固定机器与 worker 数，测 P95 延迟、吞吐和内存，再决定是否值得换框架。框架通常不是瓶颈，数据库查询、外部调用和糟糕的索引才是。

数据库与 ORM：同步与异步的边界

两者都能配 SQLAlchemy，差别在调用方式。Flask 请求是同步的，SQLAlchemy 1.3 的 Session 可直接用，Flask-SQLAlchemy 还管理作用域与连接回收，事务就是熟悉的 commit 与 rollback。

FastAPI 里要区分路由类型：def 路由会进入线程池，可以安全调用同步 ORM；async def 路由跑在事件循环里，调用同步驱动会阻塞整个进程。2019 年可用的异步方案是 asyncpg、aiomysql 配合 databases 之类的封装；SQLAlchemy 本身还没有原生 async ORM，复杂查询与关系加载仍要回到同步世界。

常见的折中是：路由用 async def 处理外部 I/O，数据库仍走同步 Session，但把库操作放进线程池，或干脆把该路由写成 def。要小心「半异步」：在 async 函数里直接 session.query()，本地测试看不出问题，线上并发一高就全面变慢。

部署：进程模型与反向代理

Flask 的经典组合是 gunicorn 加同步 worker，前面挂 Nginx。worker 数按 CPU 核数估算，通常 2 到 4 倍，再按内存与阻塞情况调整；大量时间花在等待时，可换 gevent 或 gthread worker，但要确认驱动与扩展兼容。uWSGI 也能用，配置更复杂。

FastAPI 用 uvicorn 启动，常见两种方式：uvicorn –workers 多进程，或 gunicorn 配 uvicorn.workers.UvicornWorker。前者简单，后者在优雅重启、超时与日志上更成熟。worker 数不必照搬同步模型，单进程已能并发处理大量 I/O，通常从核数起步再压测调整。

两者都建议把 Nginx 放在最前面，处理 TLS、静态文件、请求体限制与超时。需要流式响应或 WebSocket 时，buffering 与超时要单独调，否则异步框架的能力会被代理层吃掉。部署的真正差别不在命令，而在容量规划：同步看进程数，异步看单进程的并发上限与下游承受能力。

迁移成本：从 Flask 到 FastAPI 要改什么

路由层最直观：Flask 的 int:user_id 要改成 {user_id} 并加类型注解，methods 参数变成 @app.get、@app.post 等装饰器。请求解析从 request.args、request.form、get_json() 转为函数参数与 Pydantic 模型，原来手写的默认值与类型转换可以删掉。

错误处理需要重写。Flask 用 @app.errorhandler 捕获异常并返回 jsonify，FastAPI 用 HTTPException 表达业务错误，再用 exception_handler 统一格式；校验失败由框架返回 422，若前端只认 400，要在异常处理器里转换。响应也从 jsonify 加状态码，变成返回 dict 或 response_model。

扩展要逐个找替代。Flask-Login 的会话与权限、Flask-SQLAlchemy 的查询风格、Flask-Migrate 的命令，在 FastAPI 侧通常要换成依赖项、原生 SQLAlchemy 与 Alembic。测试也要改：Flask 的 test_client 换成基于 requests 的 TestClient，fixture 里维护应用与数据库的方式随之调整。

迁移可采用绞杀者模式：新接口用 FastAPI 写，旧接口留在 Flask，Nginx 按路径分流，稳定后逐步搬。风险可控，但两套依赖、日志与鉴权会并存一段时间，运维成本要算进去。

选型建议：按场景而不是按喜好

新项目以 JSON API 为主、团队愿意用类型注解、需要自动文档，FastAPI 是很自然的选择；它的校验与依赖注入能减少样板代码，异步模型也便于对接外部服务。已有 Flask 项目运行稳定、扩展依赖深、团队熟悉其上下文与调试方式，继续维护通常比重写划算。

实时性要求高的场景，如 WebSocket、长轮询、大量并发上游调用，ASGI 的结构性优势更明显；以报表、后台管理、CPU 计算为主的系统，换框架收益有限。交付周期紧、团队没有异步经验时，贸然上 FastAPI 容易在阻塞调用和线程池上踩坑，先用 Flask 跑通业务更稳。可用下表初筛：

场景 倾向 主要理由
新建 JSON API，需要对外文档 FastAPI 校验、OpenAPI 与依赖注入一体
存量 Flask 项目，扩展依赖多 Flask 迁移面大，收益有限
大量等待外部 I/O、长连接 FastAPI 事件循环可叠加等待
CPU 密集或批处理 两者皆可 关键在进程池与任务队列
团队无异步经验、交付期紧 Flask 心智负担低，资料多
快速拼装后台与管理界面 Flask 扩展成熟，模板生态好

表格只是起点。团队能否维护、出问题能否定位、招聘是否容易，往往比框架特性更难量化，也更决定成败。

常见误区

第一是为「异步」而异步。收益来自等待的叠加，若下游是同步数据库或 SDK，改成 async def 只是把阻塞换了个位置，复杂度却上升。第二是在 async 路由里调用阻塞库：requests、time.sleep、同步 ORM、文件读写都会卡住事件循环，应改用异步客户端，或把路由写成 def 交给线程池。

第三是忽略 Pydantic 的版本变化。0.x 时期字段参数、校验器写法、配置项都调整过，照着半年前的博客写，可能导入就失败；锁定版本、读变更记录、给模型写测试，比事后排查便宜。第四是把 FastAPI 当成 Flask 的替代品一刀切：两者在错误格式、依赖组织、扩展生态上差异很大，已有项目全量重写往往得不偿失。

还有一种隐蔽的误区是只看开发体验，不看运维。异步服务的线程转储、阻塞检测、连接池监控与同步服务不同，团队要准备好工具与预案，否则上线后连「为什么慢」都说不清。

小结

Flask 与 FastAPI 的差异，本质是同步微框架与异步类型化框架的差异。Flask 胜在成熟、自由、存量生态庞大；FastAPI 胜在校验、文档与异步 I/O 的一体化。选型先看负载是等待型还是计算型，再看团队经验与维护成本，最后才看功能清单。无论选哪个，都别在异步路由里调用阻塞库，别把框架当成性能瓶颈的替罪羊，也别为了新潮牺牲可维护性。
