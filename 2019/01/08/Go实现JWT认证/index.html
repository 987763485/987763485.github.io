Go 实现 JWT 认证

本文属于《Go 语言与工程》第 59/78 篇
上一篇系列目录下一篇

JWT 在前后端分离的项目里已经很常见，但把它用对并不只是调用一个库签出字符串。本文从三段结构讲起，用 Go 的 jwt-go 3.x 完成签发、解析、中间件、刷新与注销，并列出几个高频的坑。适合已经能写 HTTP 服务、准备给接口加登录态的同学。认证体系的整体设计请参考《Token 认证机制设计》，本文只讲 Go 侧的落地。

为什么需要 JWT

传统的会话方案是服务端保存 session，浏览器只拿一个 session id。单机部署时这套东西很省心：登录成功写一条记录，退出时删掉，中间件按 id 查一次即可。问题出在扩容之后：请求可能落到任意一台机器，session 要么做粘性会话，要么集中存到 Redis 或数据库。粘性会话在发布、扩缩容时很脆弱，集中存储则让每个请求都多一次远程调用。

JWT 换了个思路：把“你是谁、什么时候过期”这些信息直接写进令牌，由服务端签名，客户端保存。服务端收到令牌后只做一次签名校验，不需要查询任何存储，水平扩容时天然一致。代价也很明显：令牌一旦签发，在过期之前服务端无法单方面让它失效，注销和改权限都变得麻烦；令牌体积比 session id 大，每个请求都要带上。理解这两面，后面的设计才有依据。

从职责上看，JWT 只解决“这块内容有没有被篡改、有没有过期”，不解决“这个人有没有权限访问这个接口”。前者是签名与声明校验，后者仍然要查业务数据或权限缓存，两者不能混为一谈。

三段结构：header、payload、signature

一个 JWT 是三个 base64url 片段用点号连接起来的字符串，形如 xxxxx.yyyyy.zzzzz。第一段是 header，描述令牌类型和签名算法；第二段是 payload，存放声明（claims）；第三段是 signature，对前两段的签名。

base64url 不是加密

很多人第一次看到 payload 能直接解出明文会感到意外。base64url 只是把二进制按 6 位一组映射到 URL 安全的字符集：把标准 base64 的 + 和 / 换成 - 和 _，并去掉末尾的 = 填充。它是编码，不是加密，任何人拿到令牌都能还原出 header 和 payload，不需要密钥。

这一点直接决定了使用边界：payload 里不要放密码、身份证号、手机号、内部接口地址这类敏感信息。需要客户端读取的展示性信息（用户 id、昵称、头像地址）可以放，但也要假设它已经公开。真正需要保密的内容应该留在服务端，令牌里只放一个能查到它的标识。

标准声明

JWT 规范定义了一组注册声明，字段名都很短，目的是控制令牌体积：

  • iss：签发者，通常是认证服务的标识。
  • aud：预期使用方，资源服务要核对。
  • sub：主体，一般放用户 id。
  • exp：过期时间，Unix 秒。
  • nbf：生效时间，早于这个时间令牌无效。
  • iat：签发时间。
  • jti：令牌唯一 id，注销和防重放时很有用。

自定义声明可以随意加，但要避开这些已注册的名字，也不要用过短又容易混淆的键。exp、nbf、iat 都是 NumericDate，也就是从 1970-01-01 UTC 起算的秒数，不是格式化字符串，也不是本地时间。

签名怎么算

以 HS256 为例，签名内容是 base64url(header) + "." + base64url(payload)，用密钥做 HMAC-SHA256，再把结果 base64url 编码，拼成第三段。验证时服务端用同样的方式重算并比较。所以改动 payload 的任何一个字符，签名都对不上；而攻击者没有密钥，就造不出新的签名。

这里有个容易被忽略的细节：签名针对的是 header 和 payload 的原始编码，不是解码后重新序列化的 JSON。验签必须使用收到的原始片段；如果实现先把 JSON 解析出来、再重新拼接去验签，字段顺序或空白一变，签名就对不上，也容易给伪造留下空间。成熟的库会处理好，自己手写时要注意。

算法选择：HS256 还是 RS256

header 里的 alg 决定用哪种算法验签。实际项目里多数场景在 HS256 和 RS256 之间二选一，二者的差别不只是性能。

对称与非对称

HS256 是 HMAC-SHA256，签发和验证共用一把密钥。它的优点是实现简单、计算快、令牌短，适合单体服务，或者服务数量少、部署边界清晰的内部系统。缺点也同样来自“共用”：每一个验证方都持有签名密钥，也就都具备签发能力；任何一处泄露，等于整条链路失守。

RS256 是 RSA-SHA256，私钥签发、公钥验证。认证服务独占私钥，网关和各个资源服务只分发公钥，公钥泄露不影响安全。代价是签名运算比 HMAC 慢一个数量级，令牌也更长，而且密钥的生成、分发、轮换需要有人负责。我的建议是：单体内用 HS256 就够了；一旦有多个团队的服务都要独立验令牌，或者要把验证能力开放给外部，就换成 RS256。

密钥管理

无论选哪种算法，密钥都不能出现在代码和仓库里。常见做法是从环境变量或配置中心读取，启动时检查长度和格式，缺失就直接拒绝启动，不要留一个默认值兜底。HMAC 密钥应当是足够随机的字节串，至少 32 字节，不要用项目名、secret 这类可猜的字符串；RSA 私钥文件权限设为 0600，不随镜像一起分发。

需要轮换时，header 里的 kid 用来标识密钥版本，验证方根据它选择对应的公钥。kid 只能作为查表的键，必须在服务端维护的白名单里取值，绝不能拿它拼文件路径或发起网络请求，否则就是一个典型的注入点。

必须校验 alg，拒绝 none

JWT 历史上有过一类著名的算法混淆攻击：服务端用 RS256 公钥验签，攻击者把 header 的 alg 改成 HS256，再用那把公开的公钥当作 HMAC 密钥重新签名。如果实现直接按 header 声明的算法选择验证方式，伪造的令牌就能通过。防御办法很直接：签发端固定算法，验证端也只接受预期的算法，其他一律拒绝。

none 是规范里为“不签名”预留的算法，任何生产环境都不应该接受。jwt-go 默认会拒绝 none，但我们仍要在 Keyfunc 里显式检查算法类型，把“只接受 HS256”写成代码，而不是依赖默认行为。

用 jwt-go 签发令牌

当时 Go 生态里最常用的是 github.com/dgrijalva/jwt-go 的 3.x 版本，它提供了 StandardClaims、NewWithClaims、ParseWithClaims 这一套 API，足够覆盖常规需求。安装时把版本固定在 3.x，避免某天拉到一个不兼容的主版本。

先定义自己的声明结构。把 jwt.StandardClaims 匿名嵌入，注册声明就有了；业务字段只放必要的标识，不要放角色列表和具体权限。TokenVersion 用于后文的注销方案，签发时从用户记录里读出当前版本号。

注意 ExpiresAt 用的是 now.Add(15 * time.Minute).Unix()，即绝对时间点换算成秒。它的类型是 int64，直接塞一个 time.Time 编译不过；如果用本地时区格式化再转成数字，值还会随时区偏移。统一用 Unix 秒，是这里最省事的纪律。

解析与校验

验证令牌用 jwt.ParseWithClaims，传入原始字符串、一个声明结构体的指针和 Keyfunc。库会调用 Keyfunc 取得密钥完成验签，并把 payload 反序列化到结构体，同时检查 exp 和 nbf。Keyfunc 在验签前执行，正好用来放算法白名单。

err 不为空时仍然要判断具体类型。jwt-go 把过期、签名错误、格式错误都包在 *jwt.ValidationError 里，用位掩码区分，只有过期这一位值得单独告诉客户端，其余统一按非法处理，避免把“签名错了还是格式错了”暴露给攻击者。即便 err 为 nil，也建议再确认一次 token.Valid，这是防御性写法。

中间件：把用户放进 context

中间件只做三件事：取出令牌、验证、把声明挂到 context.Context 上。不要在中间件里判断某个接口需要什么角色，那是授权层的事，混在一起会让复用变得困难。

这里有几个约定值得固定。第一，Authorization 头只认 Bearer 前缀，大小写按规范处理，取不到就立即返回，不要再去 cookie 或 query 里找，否则等于给自己开了多个入口。第二，401 与 403 要分清：没登录、令牌无效是 401，登录了但没权限是 403，前端对两者的处理完全不同。第三，过期和非法返回不同的业务码，前端才能在收到 token_expired 时静默刷新，而不是直接把用户踢回登录页。第四，令牌不要拼进 URL，也不要整段打进访问日志，日志里最多保留 jti 的前几位。

刷新机制：双令牌与轮换

访问令牌有效期短，用户体验就会变差；有效期长，泄露后的窗口就大。折中方案是双令牌：access token 只活 15 分钟，refresh token 活 7 天，前者过期后用后者换一对新的。

refresh token 不能只靠“自包含 + 长过期”就完事，那样同样无法撤销。它必须在服务端有记录：Redis 里以令牌摘要为键，值为用户 id、令牌版本、所属令牌族和过期时间。存摘要而不是原文，即使 Redis 被读走也不能直接使用。

sequenceDiagram
    participant C as 客户端
    participant A as 认证服务
    participant R as Redis
    C->>A: POST /auth/refresh
    A->>R: 查询 refresh 记录
    R-->>A: 记录或不存在
    alt 记录有效
        A->>R: 删除旧记录，写入新记录
        A-->>C: 新 access + 新 refresh
    else 记录不存在（疑似重放）
        A->>R: 撤销整个令牌族
        A-->>C: 401，要求重新登录
    end

刷新时必须轮换：旧 refresh 用过一次就删除，同时签发新的 refresh。这样每个 refresh 只能用一次，被盗用的令牌一旦被真正用户先用了，攻击者手里的那份就失效。更进一步的做法是记录令牌族（family）：当服务端收到一个“已使用过”的 refresh 时，不只拒绝这一次，而是把整个族全部撤销，因为此时无法判断谁才是合法持有人，最安全的动作是让双方都重新登录。

这里省略了存储实现和错误处理，重点在顺序：先确认旧记录存在且版本正确，再签发新令牌，最后用新记录替换旧记录。替换动作最好放在一个事务或 Lua 脚本里，避免并发刷新时两个请求都成功。另外，refresh token 也应该带 exp，Redis 的 TTL 只是兜底，双重过期更稳妥。

注销：无状态令牌的代价

注销是 JWT 最别扭的地方。服务端不保存会话，自然也没有“删除会话”这个动作。常见做法有三种，各有取舍。

第一种是缩短有效期，让令牌自然过期。实现成本为零，但注销后仍有一段窗口期可用，只适合安全要求不高的场景。第二种是黑名单：注销时把令牌的 jti 写入 Redis，TTL 设为剩余有效期，中间件验签后多查一次。它的代价是每个请求多一次 Redis 往返，等于把无状态又拉回有状态；好处是粒度细，可以精确到单个设备。第三种是令牌版本号：用户表或缓存里存一个 ver，签发时写进声明，中间件比对不一致就拒绝。改密码、强制下线时把 ver 加一，该用户所有旧令牌立即失效。它省去了逐令牌记录，但粒度粗，踢一个设备会踢掉全部，而且中间件仍要读一次版本缓存。

常见坑

  • exp 用本地时间或格式化字符串。正确做法是 Unix 秒，服务端之间还要校时，否则一台机器快几分钟就会把有效令牌判成过期。
  • 只验签名不验 iss 和 aud。签发给 A 系统的令牌可能被拿去访问 B 系统，只要密钥相同就能通过，这两个声明必须显式比对。
  • 把角色和权限列表全塞进 payload。令牌不过期权限就不更新，管理员被降权后仍能操作；payload 里只放 sub，权限在服务端查缓存。
  • 无条件相信 header 里的 kid，甚至拿它拼路径或请求地址。kid 只是选密钥的索引，必须来自服务端维护的白名单。
  • 多个服务各配一份密钥，轮换时漏掉一个，表现为“有的接口通、有的返回 401”。密钥要集中管理，发布前逐个核对。
  • 不区分 access 与 refresh 的用途，拿 refresh 直接访问业务接口。签发时加一个 typ 声明，验证时分别检查。

小结

JWT 的可靠性建立在三件事上：签名算法固定且拒绝 none，声明校验完整，密钥不落进代码。Go 侧用 jwt-go 3.x 的 NewWithClaims 与 ParseWithClaims 就能覆盖签发和验证，中间件负责把 Claims 放进 context，并把过期与非法分成两个业务码。刷新用短 access 加长 refresh，refresh 存服务端、一次一换、检测重放；注销则按安全要求选择黑名单或版本号。最后记住 payload 是明文，能少放就少放。
