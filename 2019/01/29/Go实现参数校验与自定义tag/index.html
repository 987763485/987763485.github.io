Go 实现参数校验与自定义 tag

本文属于《Go 语言与工程》第 60/78 篇
上一篇系列目录下一篇

接手一个 HTTP 接口时，最容易被低估的工作是参数校验：字段一多，if 就会堆成山，错误文案散落各处，前端还得逐个猜。本文以 Go 1.11 和 go-playground/validator v9 为例，从基础 tag 讲到自定义校验函数与跨字段规则，并给出中文错误翻译和几个常见坑。读完后，你应该能把校验从 handler 里抽成一层，让非法请求在进入业务逻辑之前就被挡住。

为什么校验要放在边界

HTTP 接口的第一条现实是：请求体里的任何字节都不可信。前端的必填提示、长度限制、下拉框选项都只是体验，用 curl、脚本或被改过的客户端可以轻易绕过。真正能约束数据的，只有服务端在入口处做的那一次检查。

尽早失败是第二个理由。请求完成 JSON 绑定后立刻校验，非法请求就不会进入 service，不会占用数据库连接，也不会产生半条业务数据。反过来，如果校验散落在业务逻辑深处，一个字段错误可能要经过几次查询才暴露，错误还会被层层包装，最后只剩一句“创建失败”。

第三个理由是错误信息。客户端需要知道哪个字段错了、触发了什么规则、期望的值是什么。把这些信息结构化地返回，前端才能把提示落到具体输入框，而不是弹一个笼统的 toast。

因此校验层通常放在 handler 与 service 之间：handler 负责解析和绑定，校验层判断结构是否合法，service 只处理业务规则。格式、长度、枚举、字段之间的简单关系属于校验层；余额是否足够、手机号是否已注册这类需要查库的判断，仍然留在 service。

flowchart LR
    A[HTTP 请求] --> B[绑定 JSON]
    B --> C[结构体 tag 校验]
    C -->|失败| D[400 与字段错误]
    C -->|通过| E[Service 业务规则]

常用 tag 的语义如下：

tag 作用 示例
required 值不能是零值 required
min / max 数值大小或长度范围 min=2,max=20
len 精确长度 len=11
email 邮箱格式 email
url URL 格式 url
oneof 值在枚举内 oneof=male female
gte / lte 大于等于、小于等于 gte=0,lte=150
dive 继续校验切片或 map 的元素 dive,min=1

min、max、len 的含义随字段类型变化：数字比较数值，字符串比较字符数（按 rune 计），切片、数组和 map 比较元素个数。同样是 min=2，写在 int 上是“不能小于 2”，写在 string 上是“至少两个字符”。len=11 用在手机号字符串上表示 11 个字符，不是数值等于 11。

required 判断的是 Go 零值，0、空字符串、false、nil 指针都算没传。这一点后面还会展开，因为“0 是合法值”的字段最容易在这里出错。email 和 url 只检查格式，不会去解析域名，也不保证地址可达。

oneof 用空格分隔允许值，按字符串比较，适合状态、性别、渠道这类字符串字段；数字枚举更稳妥的做法是写自定义函数。omitempty 表示字段为空时跳过后面的规则，常和 url、min 这类可选约束搭配，不要和 required 写在一起。gt、lt 与 gte、lte 的区别只在是否包含边界，下界为 0 时要确认清楚，否则合法的 0 会被挡掉。

字段规则彼此独立，同一层的普通字段前一个失败，不会让后面的字段跳过；如果某条规则依赖另一个字段有值，应使用 required_with 或结构体级判断，否则会返回一串连带错误。错误多并不总是好事，客户端需要的是能逐项修正的提示，而不是同一原因重复多遍。

读懂 ValidationErrors

validate.Struct 返回的是 error 接口，底层通常是 validator.ValidationErrors，它是 []validator.FieldError 的切片。直接打印是一串英文，先做类型断言再逐条处理：

Field() 是出错字段名，Tag() 是触发的规则，Param() 是规则参数，Value() 是当前值，Kind() 是反射类型。例如 Name 太短时，会得到 field=Name tag=min param=2 value=张 kind=string。还有 StructField()，它始终返回 Go 字段名，排查时比 JSON 名更好定位。切片里的结构体元素出错时，Field() 仍是元素里的字段名，Namespace() 才会带上 Items[0] 这样的路径，记录日志时用后者更容易还原现场。

validator 默认收集全部字段错误，顺序按字段声明顺序。建议一次返回全部，客户端可以一次改完；错误太多时截断，例如只取前 10 条。只返回第一条适合分步表单，但“第一条”由字段顺序决定，调整结构体字段可能改变用户看到的提示。还要注意 Value() 不要原样记录或回显，密码、令牌这类字段会因此泄露。

跨字段校验

同一层结构体内的简单关系，用内置的跨字段规则就够了：

eqfield 判断两个字段相等，gtfield 判断当前字段大于另一个字段。参数写的是 Go 字段名，不是 JSON 名，写成 password 会找不到字段。这类规则只能引用同一层结构体的字段：嵌套结构体看不到外层，dive 进去的元素里，Parent() 指向的是元素本身。字段声明顺序不影响取值，因为 JSON 解码早已完成；但它影响错误输出的顺序，采用“只返回第一条”策略时，顺序就决定了用户先看到哪条提示。

把校验收成一个包

校验器只需要初始化一次。把 validate、trans 和 InitValidator 放进独立的 validatorx 包，对外暴露 Validate(req interface{}) error 和翻译函数，handler 不直接 new，也不在请求处理中注册规则。这样所有接口共用同一份字段名策略和文案，测试时也只需初始化一次。

小项目用包级变量就够了；如果进程内有多套规则，比如开放平台和内部接口的提示口径不同，就返回一个包含 Validate 与 Translate 的结构体，由调用方持有。不要为了“灵活”把校验器塞进 context，它本身没有请求级状态，放进去只会让依赖关系变模糊。

几个容易踩的坑

指针与零值

纯值字段的 required 按零值判断，年龄 0、金额 0、开关 false 都会被当成没传。如果 0 是合法值，要么去掉 required 改用 gte=0，要么把字段改成指针：

指针字段的 required 只判断是否为 nil，指向 0 的指针算有值，这正是它区分“没传”和“传了 0”的原理。代价是取值前要判空，序列化时也要注意 nil 的输出。

omitempty 与 dive 的顺序

规则按从左到右执行，dive 是一个分界点。validate:"min=1,dive,min=2" 表示切片至少一个元素，且每个元素至少两个字符；写成 dive,min=1 则只约束元素，空切片反而能通过。omitempty 放在 dive 前面才会跳过 nil 切片，放到后面只作用于元素。map 上的 dive 校验的是值，键的规则要另写函数，不能指望元素规则顺带覆盖。

错误字段名与敏感值

没有注册 RegisterTagNameFunc 时，Field() 返回 Go 字段名，前端拿到的是 UserName 而不是 user_name，两边约定容易对不上。另一个细节是不要把 Value() 直接拼进响应或日志，密码、验证码、令牌都会因此落盘。

panic 与并发

tag 写错不会在编译期报错。未知规则名、min=abc 这类非法参数，会在调用 Struct 时 panic，而不是返回 error。稳妥的做法是给每个请求结构体写一个启动即运行的单测，用零值调用一次 Struct，把 tag 错误挡在上线前；中间件里再加 recover 兜底。RegisterValidation、RegisterStructValidation 不要在请求处理过程中调用，注册完成后 Validate 可以并发使用，但注册阶段本身没有并发保护。

小结

参数校验应该紧贴入口：绑定之后、业务之前，让非法请求尽早失败。validator 把规则变成结构体上的 tag，基础约束用内置规则，特殊格式用 RegisterValidation，跨字段关系用 eqfield、gtfield 或结构体级函数。错误处理要先做类型断言，再借 FieldError 取出字段、规则和参数；配合 RegisterTagNameFunc 与中文翻译，客户端才能拿到可展示的提示。最后别忽略零值、dive 顺序和 tag 拼写这三类问题，它们大多能靠启动自检提前发现。
