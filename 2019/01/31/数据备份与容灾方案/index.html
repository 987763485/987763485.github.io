数据备份与容灾方案

备份与容灾在多数团队里都处于一种尴尬位置：平时没人关心，出事时才发现方案只写在文档里。本文想把它拆成两件可以被量化、被验收的工程任务。我们先从 RPO 与 RTO 这两个指标出发，说明需求如何分级；再落到 MySQL 5.7 与 XtraBackup 2.4 的具体命令、3-2-1 原则、加密与权限、容灾分级与恢复演练。读完本文，你应该能为一个中小规模业务写出一份自己敢签字、也敢在事故现场执行的备份方案。

从 RPO 与 RTO 开始

很多团队把备份与容灾混为一谈，结果方案做得很热闹，真出事时却答不上两个最基本的问题：能接受丢多少数据，能接受停多久。把这两个问题变成数字，方案才有讨论的基础。

备份解决的是“数据还在不在”，产物是一份可以脱离原系统独立存在的副本，对抗误删、误更新、勒索软件、存储损坏这类逻辑与介质故障。容灾解决的是“服务能不能继续”，关注机房断电、网络中断、整片区域不可用，产物是一套能在别处接管请求的运行环境。备份可以很完整却让业务停上一整天，容灾可以秒级切换却挡不住一条 DELETE 把表清空。

两个指标分别是：

  • RPO（Recovery Point Objective，恢复点目标）：允许丢失多长时间窗口内的数据。RPO 为 5 分钟，意味着最多回退到 5 分钟前的状态。
  • RTO（Recovery Time Objective，恢复时间目标）：从故障确认到服务恢复可用，允许消耗多长时间。

这两个数字不是技术指标，是业务指标，应该由业务方签字，而不是由运维拍脑袋。数字越严苛，成本上升得越快，而且不是线性上升：RPO 从 24 小时收紧到 1 小时，可能只是把备份从每天改成每小时；从 1 小时收紧到接近 0，就得引入半同步复制、跨机房专线，成本是另一个量级。

按业务分级是一种务实的做法。下面这张表是笔者常用的起点，具体数字仍需与业务方逐条确认。

业务级别 典型系统 RPO RTO 主要手段
核心交易 订单、支付、账务 秒级到 0 分钟级 半同步复制、同城双活、binlog 实时归档
重要内部系统 OA、工单、报表库 15 分钟到 1 小时 2 到 4 小时 每小时增量、每日全量、温备环境
一般业务 内容站、活动页 4 到 24 小时 8 小时以上 每日全量、异地冷备
日志与归档 访问日志、审计流水 24 小时 天级 定时打包、对象存储、生命周期转冷

分级的意义在于把预算花在刀刃上。给日志归档做双活是浪费，给订单库只留一份本地全量则是赌博。最常见的错误不是级别定低了，而是所有系统共用一套方案：核心库 RPO 超标，日志库又为不必要的高频备份付了存储费。

还有一点要提前说清：RPO 与 RTO 是验收指标，不是设计口号。方案写完，必须用一次真实恢复测出实际耗时。没有测量过的 RTO，只是一个愿望。

备份类型与恢复链

确定指标之后，才轮到选备份方式。全量、增量、差异这三个词几乎所有文档都会提，但真正决定事故现场成败的，是它们构成的“恢复链”。

全量备份是把范围内全部数据完整复制一份，优点是恢复简单：一份备份加一段日志，路径最短，出错环节最少。缺点是每次都读全量，耗时与存储开销随数据量线性增长；几百 GB 的库每天做一次全量，窗口很快顶到业务高峰。

增量备份只备份“上次备份以来发生变化的部分”。这里的“上次”通常指上一次任意类型的备份，所以增量是链式的：周日全量，周一增量，周二增量。要恢复到周三的状态，必须先还原周日全量，再依次重放周一、周二的增量，最后用日志补齐到具体时刻。链条上任何一环损坏或丢失，后面的增量全部作废。

差异备份备份的是“上次全量以来变化的部分”，参照点固定在全量，所以恢复只需要“最近一次全量 + 最近一次差异”，链路只有两段。代价是差异备份会越来越大，越接近下一次全量，体积越接近全量本身。

三者的取舍可以归结为一句话：增量省空间、恢复慢且脆弱；差异折中；全量最稳、最贵。工程上常见的组合是“每周全量 + 每日差异 + 持续归档日志”，或者“每周全量 + 每小时增量 + 持续归档日志”。选哪一种，取决于你更怕存储账单，还是更怕恢复时手忙脚乱。

    A[周日全量备份] --> B[周一增量]
    B --> C[周二增量]
    C --> D[周三故障时刻]
    A --> E[恢复：还原全量]
    E --> F[重放周一增量]

除了按范围划分，备份还有另一个维度：物理与逻辑。

逻辑备份导出的是 SQL 语句或数据文本，mysqldump 是典型代表。它的优势是可读、可编辑、可跨版本导入，还能只恢复某一张表。劣势是慢：导出要读数据、拼 SQL，导入要逐条执行、重建索引，数据量大时恢复时间可能是物理备份的数倍。逻辑备份对字符集、时区、SQL 模式敏感，跨环境恢复时经常在这些细节上翻车。

物理备份直接复制数据文件与日志文件，XtraBackup 是代表。优势是快，恢复相当于把文件放回原位再做一次崩溃恢复；劣势是与版本、页大小强绑定，通常不能跨大版本恢复，也很难只恢复单表。两者并不互斥：物理备份兜底大库，逻辑备份负责单表抢救与跨环境迁移。

最后是热备、温备、冷备这组按“服务状态”划分的概念。热备在数据库正常读写时进行，依赖存储引擎的一致性快照能力，InnoDB 支持，MyISAM 不支持；温备会限制写入但允许读；冷备要求停库。生产环境尽量选热备，因为停库窗口本身就是一次小型故障，而且很多团队根本拿不到停机审批。冷备的价值在于简单可靠，适合变更窗口内的最后一次兜底。

3-2-1 原则：为什么“另一台机器”不算异地

3-2-1 是备份领域流传最广的经验法则，内容只有三句话：至少三份数据，两种不同介质，一份放在异地。它针对的不是“硬盘会不会坏”，而是“故障有多大的相关性”。

先说三份。原始数据算一份，另外两份是备份。为什么不是一份备份？因为备份本身也会坏，而更常见的情况是：备份正在写、备份介质正在老化、备份文件正在被某个清理脚本删除。多一份的意义不是提高单点可靠性，而是让“备份的备份”这条路径存在。

再说两种介质。这里的介质指存储类型与失效模式不同，例如本地磁盘阵列加磁带或对象存储，而不是同一台服务器上两块同型号硬盘。同批次、同固件的磁盘有相同的缺陷与相近的寿命曲线，一起上电，也会一起到达写入上限。介质分离同时也是控制器与文件系统层面的分离。

最关键的是“一份异地”。很多人对这一条的理解是“放到另一台机器上”，于是把备份目录挂载到同机房的另一台服务器，或者干脆挂到同一台机器的另一块盘。这在故障域上几乎没有收益：

  • 同一机房共享供电、空调、消防、核心交换机与出口带宽，一次市电切换或一次机柜级事故可以同时带走生产机与备份机。
  • 同一套运维体系共享账号、密钥、自动化脚本与挂载配置。一条写错的 rm -rf 或一段批量清理脚本，会顺着挂载点把备份一起删掉；勒索软件也会沿着已挂载的目录加密备份文件。
  • 同一套监控与告警意味着同一个盲区。备份机失联时，告警可能和生产机一起消失。

所以“异地”是一个故障域概念，不是地理距离概念。判断标准不是隔了几公里，而是：这里的故障会不会同时影响生产侧。同城另一栋楼如果走同一路市电、同一根光缆、同一个运维账号体系，它的独立性就要打折扣；反过来，同一园区内物理隔离、供电与网络独立的另一栋楼，可能比跨城但共用一套账号的机房更有价值。

落地时可以用三个问题自检。第一，备份路径是否与数据文件位于同一块设备或同一个存储池？第二，执行备份的账号是否对生产数据拥有写权限？能删生产数据的账号，也能删备份。第三，异地副本是否可读、可校验？只写入不读取的副本，本质上是一种心理安慰。

一个务实的组合是：生产机只留最近一次用于快速回滚的短周期副本，长期备份写入独立存储，再由它同步一份到异地；异地的写入凭据与生产环境隔离，并保留一段不可变窗口，即使攻击者拿到凭据，也无法在窗口期内删除已有副本。

MySQL 逻辑备份：一致性快照与位点

MySQL 的备份方案通常由三部分组成：周期性全量、持续归档的 binlog、以及为缩短恢复时间而增加的增量。先看最常用的全量工具 mysqldump。

mysqldump 输出一批 CREATE TABLE 与 INSERT 语句，简单通用，但默认参数并不适合在线库。不加参数直接跑，它会逐表加读锁，导一张、释放、再导下一张，各表处于不同时间点。对有订单主表与明细表的库，备份里可能出现“主表有这笔订单、明细表还没有”的错位状态；恢复后数据看起来完整，对账时才发现异常。

InnoDB 表的正确做法是使用一致性快照：

--single-transaction 在导出开始时开启一个可重复读事务，整个导出过程读取的都是这个事务的一致性快照。MVCC 让后续写入不影响已开启事务看到的版本，因此既不需要锁表，也能得到同一时间点的数据。这也是它只能用于 InnoDB 的原因：MyISAM 没有事务与 MVCC，加了参数仍会因并发写入产生错位，只能退回 --lock-tables，接受写入阻塞。

--master-data=2 会在输出文件开头写入一行注释，记录备份开始时的 binlog 文件名与位点，形如 -- CHANGE MASTER TO MASTER_LOG_FILE='mysql-bin.000123', MASTER_LOG_POS=456789;。取 2 表示写成注释，恢复时不会自动执行；取 1 则写成可执行语句，导入时会直接配置复制关系，一般不推荐。这一行是“全量 + binlog”能够衔接的关键：没有位点，就不知道从哪里开始重放。

--master-data 需要 RELOAD 权限，配合 --single-transaction 时会短暂获取一次全局读锁，以保证位点与快照严格对应。--flush-logs 在备份开始时切分新的 binlog，让日志边界清晰，便于归档与清理。--set-gtid-purged=OFF 用于 GTID 环境，避免导出文件写入 SET @@GLOBAL.GTID_PURGED 后在目标实例上报错。

XtraBackup 物理热备与 binlog 归档

逻辑备份的短板在恢复阶段暴露得最明显。几百 GB 的库，导入时要逐条执行 INSERT、逐棵重建索引，耗时往往是导出时的数倍。业务等不起的时候，就需要物理备份。

Percona XtraBackup 2.4 是 MySQL 5.7 时代最常用的物理热备工具。它直接复制 InnoDB 的数据文件，并在复制过程中持续跟踪 redo log，保证最终得到一个内部一致的副本，备份期间数据库可以正常读写。

增量备份的判定依据是 LSN（Log Sequence Number），不是文件的修改时间，因此不能手工挑选文件拼凑。备份目录里的 xtrabackup_checkpoints 记录了本次备份的起始与结束 LSN，增量能否接上，全看这个文件。

物理备份之外，还必须持续归档 binlog。binlog 是两个备份点之间的“时间轴”，也是唯一能把数据恢复到“故障发生前一秒”的手段。归档方式有两种：定时把 binlog 文件同步到备份存储，或者用 mysqlbinlog 以流的方式持续拉取。

方式一适合对 RPO 要求高的场景，缺点是连接断开后需人工确认续传位置；方式二简单，但只能归档已经切换掉的日志文件，正在写的那个拿不到，RPO 至少是一个日志文件的生命周期。无论哪种，都要定期清理已被全量覆盖的旧日志，否则备份存储会被 binlog 撑满，而撑满的后果是备份任务集体失败。

完整的恢复顺序是固定的：先 prepare 并回拷全量，启动实例确认可以正常打开；再确认全量对应的 binlog 位点；然后按文件顺序重放 binlog，直到指定时间点；最后校验数据并交由业务确认。顺序不能颠倒，也不能跳过“启动确认”直接重放，因为一个连启动都失败的实例，重放只会把问题放大。

文件与对象数据：别只盯着数据库

数据库之外的资产同样需要保护：用户上传的图片、合同附件、导出报表、配置文件、证书私钥、构建产物。这类数据的难点不在体积，而在数量与变更模式。

rsync 是最常用的工具，-a 保留权限与时间戳，--delete 让目标与源严格一致。问题恰恰出在 --delete：它删除“目标端存在而源端不存在”的文件，一旦源路径写错，或源目录被误挂载成空目录，一次同步就会把备份端清空。使用时路径要经过变量校验，并先以 --dry-run 跑一遍看清单。

--link-dest 用硬链接构造“看起来是完整快照、实际只存增量”的目录。代价是硬链接共享 inode，任何一个副本被就地修改，其他副本也会跟着变，所以快照目录必须只读。

比文件复制更可靠的是存储快照。LVM 或写时复制的文件系统可以秒级创建时间点视图，前提是快照瞬间文件系统必须静止：数据库还在写时直接打快照，得到的可能是写到一半的状态。正确做法是先 fsfreeze 冻结，或对 MySQL 执行 FLUSH TABLES WITH READ LOCK，打完立刻解冻；冻结要有超时保护，否则一次卡住的备份会变成一次真实的停服。

对象存储侧有三项通用能力值得用起来：版本化让覆盖与删除可回溯；生命周期规则把冷数据转到低成本层，并按合规要求设定最短保留期；跨区域复制提供一份地理上独立的副本。方案里应写清这三条要求，而不是绑定某个产品的按钮名称。

所有备份最终都要落到“可验证”上。文件级备份的校验至少包括三项：文件数量与总大小是否与源端在合理范围内一致；关键文件是否有校验和；抽样恢复是否可读。对图片目录，抽样打开若干文件即可；对数据库导出文件，抽样导入临时实例跑一条计数查询，比看文件大小有意义得多。

加密、权限与审计

备份文件是数据的完整副本，敏感程度与原库相同甚至更高：原库还有访问控制、审计日志与网络隔离，而一份明文 SQL 文件躺在备份目录里，拿到磁盘就能读走全部数据。等保检查里，“备份数据未加密存储”是很常见的一条不符合项。

落盘加密应该在备份生成时就完成，而不是事后再补：逻辑备份在管道里加密，物理备份整体加密，或在支持加密的存储层完成。算法不必追求新奇，AES-256 配合成熟工具链就足够。

密钥管理有一条硬规则：密钥不能和备份放在一起。把密码写进备份脚本、脚本与备份同机存放，等于没加密。密钥应由独立流程保管，脚本运行时从受限的配置中心或环境变量读取，恢复时由两方共同授权。

传输环节同样要加密。备份跨机传输走公网时必须 TLS，走内网也不应默认信任：在内网被镜像抓包，和放在公网没有本质区别。

数据库侧的备份账号要遵循最小权限。逻辑备份需要 SELECT、SHOW VIEW、TRIGGER、LOCK TABLES（--single-transaction 下对 MyISAM 表仍需要）、RELOAD（--master-data 与 --flush-logs）；物理备份需要 RELOAD、LOCK TABLES、REPLICATION CLIENT，某些场景还需要 PROCESS。不要图省事直接给 ALL PRIVILEGES 或 FILE：备份账号一旦有写权限，就有能力破坏生产数据，而它通常写在自动化脚本里，凭据扩散面很大。

审计要覆盖两个方向：谁在什么时间执行了备份、读了哪些库；谁在什么时间把什么数据恢复到了哪台机器。恢复往往比备份更危险，因为它会把旧数据写回生产。恢复权限应单独授予，每次恢复都有工单与记录，写明备份标识、恢复目标、时间点、执行人与业务确认人。

容灾分级：从冷备到双活

备份管数据，容灾管接管能力。按接管速度，容灾大致分四级：冷备只有设备与介质，恢复时要重新部署；温备的数据持续同步，但服务不常驻，接管需要启动与验证；热备的服务常驻待命，切换主要是流量切换；双活则是两套环境同时承载流量。级别越高，成本与复杂度上升越快，而且双活会把一致性问题从“故障时”提前到“每一天”。

同城双活对抗机房级故障，两地三中心再加一个异地中心对抗区域级灾难。三者定位不同：同城解决“楼塌了”，异地解决“城淹了”，备份解决“表删了”。很多方案把三者混着写，结果预算花在双活上，误删时却找不到一份可用的历史副本。

数据复制方式决定了切换时的一致性。异步复制主库提交即返回，备库允许落后，切换时可能丢掉最后一段事务；半同步要求至少一个备库确认收到日志才返回成功，能降低丢失概率，但并不等于零丢失——备库确认的是“收到”而不是“已应用”，且网络抖动时会退化为异步。切换前必须查清备库已应用到的位点，并明确丢失部分由谁签字，否则事后一定扯皮。

切换本身是流程而不是脚本：要有决策人、判定条件、回切方案，还要防脑裂——旧主库恢复后不能直接以主库身份加入，必须先确认落后多少。没演练过的切换脚本，第一次执行通常就是故障当天。

恢复演练：没恢复过的备份不算备份

“备份成功”只证明写操作完成了，不证明数据可用。能证明的只有一件事：从备份恢复出一个能启动、能查询、数据正确的实例。

演练频率按业务级别定，核心系统每季度一次，一般系统每半年一次。演练要有清单：选哪份备份、恢复到哪个时间点、在哪个隔离环境、由谁执行、验收标准是什么。环境必须与生产隔离，独立的网段与实例名，避免旧的恢复数据被应用误连。

每次演练都要记录实际耗时，并与 RTO 对比。第一次超时是正常的，重要的是找到时间花在哪一段：取备份、传输、prepare、回拷、重放日志，还是应用验证。演练后要复盘，把缺的步骤补回文档，把脚本里写死的路径改掉。

监控与治理

备份系统本身也需要被监控，至少盯四个指标：成功率、单次耗时、备份体积、告警是否送达。体积突然变小往往比失败更危险，可能意味着某张表被漏备、某个库连接失败被静默跳过。告警必须送到人，而不是发进没人看的群。

保留策略要写成规则：每日、每周、每月各保留若干份，并按合规要求设定最短留存期。清理任务与备份任务必须解耦，避免“清理跑在备份之前”把最后一份可用副本删掉。调度器本身也要避免单点，凭据过期、磁盘写满、证书到期，这三类问题造成的备份中断占了相当大的比例。

一次误删表的完整恢复

下面这次事故是虚构的，但每一步都来自真实项目的做法。某天下午，一位同事在清理测试数据时连到了生产库，执行了一条没有 WHERE 的 DELETE，订单明细表被清空，二十多分钟后才发现，期间仍有新订单写入。

第一步是止损而不是恢复：收回该账号权限，确认没有其他会话在写这张表，记录当前时间。第二步是评估：确认误删时间点、表结构、这期间是否有新数据写入。第三步才是恢复。

恢复的关键在于“停在哪”。--stop-datetime 与 --stop-position 都可用，但时间点依赖 binlog 时间戳，主从切换或时钟回拨时可能不准，更稳妥的是先用 mysqlbinlog 找到误删语句的 end_log_pos，再用 --stop-position 精确截断。重放范围要覆盖全量位点到误删点之间的所有日志文件，中间缺一个，数据就缺一段，往往要等到对账才发现。

第四步是校验。对比恢复实例与生产库的表行数、关键金额汇总、最近一小时的新增记录数；抽查若干订单的主子表关联是否完整。第五步是业务确认，由业务方在测试环境验证核心流程，确认后才把数据导回生产，且只针对受影响的表，避免整库覆盖。

整个过程中，恢复耗时与每一步的时间点都要记录，事后复盘回答三个问题：误删为什么能发生，备份为什么可用或不可用，恢复为什么快或慢。这次事故真正的运气不是有备份，而是 binlog 恰好完整、位点清晰。

几个反复出现的坑

  • mysqldump 不加 --single-transaction，多表时间点不一致，恢复后出现孤儿记录。
  • 备份与数据库放在同一块盘或同一个存储池，磁盘故障时一起消失。
  • 只备份不校验，文件截断、结尾缺 Dump completed 都没人发现。
  • 恢复时 binlog 位点算错，多放了一段含误操作的日志，等于把事故重演一遍。
  • 备份账号权限过大，能写能删，备份本身成为攻击面。
  • 演练从不做，RTO 只存在于文档里，第一次真实恢复就是事故现场。

小结

备份与容灾要分开设计：前者用 RPO 衡量数据能丢多少，后者用 RTO 衡量服务能停多久，两个数字都必须由业务确认并被实际测量。技术上，全量加 binlog 是最稳的底座，物理备份缩短恢复时间，逻辑备份保留单表与跨环境能力；3-2-1 原则的核心是故障域隔离，同机房的另一台机器不构成异地。加密、最小权限与审计决定备份会不会成为新的泄露源，恢复演练决定这套方案在事故当天是否真的存在。
