Node.js 事件循环深度解析

本文属于《TypeScript 学习路线》第 53/74 篇
上一篇系列目录下一篇

回调为什么有时像插队，有时又像被无限推迟？线上服务那些“偶发卡顿、健康检查超时”的毛病，追到根上往往就是事件循环被一段同步代码占住了。本文从调用栈与任务队列讲起，走一遍六个阶段，再看微任务与 libuv 线程池，最后给出测量阻塞、拆分重活的可行做法。适合已经能写 Node.js 服务、但对其调度机制只有模糊印象的读者。

从调用栈到事件循环

Node.js 常被描述为“单线程”，这个说法只说对了一半。我们写的 JavaScript 确实只在一条主线程上执行，同一时刻只有一段代码在跑；但网络读写、文件读写、DNS 解析这些等待并不由主线程承担，而是交给 libuv 和操作系统。主线程不必守着 socket 等数据到达，它只负责把已经能跑的代码跑完。也正因为如此，Node.js 擅长大量并发连接，却不擅长单个耗时计算。

理解事件循环，先要分清三个部件。

调用栈最容易理解：函数调用时压入栈帧，返回时弹出，后进先出。只要栈里还有帧，任何回调都没有机会执行，这就是“同步代码阻塞一切”的原因。

任务队列存放等待执行的回调。I/O 完成、定时器到期、Promise 决议，都会让某个回调具备执行资格，被放进相应的队列。

事件循环则是那个调度者：它反复检查调用栈是否为空，为空时按固定顺序从各个队列里取出回调，压栈执行。

flowchart TD
    A[同步代码在调用栈中执行] --> B{调用栈为空}
    B -- 否 --> A
    B -- 是 --> C[事件循环按阶段取回调]
    C --> D[回调入栈执行]
    D --> E[清空 nextTick 与 Promise 队列]
    E --> C
    F[I/O 完成或定时器到期] --> G[回调进入对应队列]
    G --> C

这里有一个容易被忽略的细节：队列不止一条。不少教程把事件循环画成“一个队列加一个循环”，据此得出“回调严格按注册顺序执行”的结论，这在 Node.js 里是错的。真正决定顺序的，是回调属于哪条队列、当前循环走到了哪个阶段。把阶段弄明白，才能解释为什么两个看似等价的写法会有不同的执行次序。

六个阶段

一次完整的循环由六个阶段组成，顺序固定，循环往复。每个阶段都维护自己的回调队列，事件循环进入某个阶段后，会尽量把该阶段队列里的回调执行完（存在数量上限，避免某个阶段饿死其他阶段），然后进入下一阶段。

timers：执行到期的 setTimeout 与 setInterval 回调。到期与否只在进入该阶段时判断，精度是毫秒级。如果进入该阶段前主线程被长任务占住，定时器只能等到下一轮，这是“定时器不准”的主要来源。

pending callbacks：执行上一轮被推迟的 I/O 回调，典型场景是某些 TCP 错误。业务代码很少直接感知这个阶段。

idle, prepare：libuv 内部使用，写业务代码时基本可以当作不存在。

poll：整个循环的核心。它做两件事：执行已就绪的 I/O 回调；队列为空时，决定在这里等多久。如果有 setImmediate 待执行，就结束等待转去 check；如果有定时器将要到期，就回到 timers；两者都没有，就在这里阻塞，直到新事件把它唤醒。也正因为 poll 会阻塞，一段耗时的 I/O 回调会把后面的定时器全部推后。

check：执行 setImmediate 回调。它紧跟在 poll 之后，位置固定，这是 setImmediate 名字里“immediate”的唯一依据。

close callbacks：执行 close 事件的回调，例如 socket.destroy() 之后触发的 close。

六个阶段走完算一轮，随后回到 timers 开始下一轮。需要强调的是，阶段本身并不耗时，占住主线程的永远是阶段里执行的回调。这里先记住一个结论：定时器回调、I/O 回调、setImmediate 回调分属不同阶段，它们之间没有“谁先注册谁先执行”的约定。

微任务：nextTick 与 Promise 的位置

六个阶段之外还有两条特殊的队列：process.nextTick 的回调队列，以及 Promise 决议后的微任务队列。后者由 V8 维护，Node.js 在每一轮里负责把它清空。它们不属于任何一个阶段，而是插在阶段之间、甚至每个回调之后执行。

时机规则可以概括为两条。第一，每个回调执行完毕，事件循环都会先清空 nextTick 队列，再清空 Promise 微任务队列，然后才继续往下走。第二，阶段与阶段切换时，同样会清空这两条队列。因此微任务不会等到某个阶段，当前这段同步代码一跑完，它们就插进来。

优先级上，nextTick 高于 Promise。这不是 Node.js 更“偏爱”它，而是实现顺序决定的：先处理 Node.js 自己的 nextTick 队列，再让 V8 处理微任务队列。在同一段代码里同时注册 nextTick、Promise、setImmediate 与定时器，前两者会在当前代码结束后立即执行，后两者要等循环走到对应阶段。

这个例子还说明一件事：在 I/O 回调内部，微任务的优先级高于 setImmediate。很多人以为“先注册先执行”，于是把 setImmediate 写在 nextTick 之前，结果仍然被微任务插队。

微任务的另一面是风险。因为清空动作发生在每个回调之后，如果在 nextTick 回调里继续注册 nextTick，队列会被不断补满，事件循环永远回不到阶段里去。这就是“递归 nextTick 饿死 I/O”：定时器不触发，网络请求收不到响应，健康检查超时，而进程看起来还活着。

这类代码通常不是故意写的，而是递归逻辑忘了加终止条件，或者把“下一轮再处理”写成了“立刻再处理”。排查时看到 CPU 占满、日志停止输出、接口全部超时，就要怀疑主线程被困在了微任务里。

libuv 线程池：四个线程在忙什么

网络 I/O 走的是 epoll、kqueue、IOCP 这类系统机制，不需要线程池。但文件操作、DNS 解析、部分加密与压缩没有对应的异步系统调用，libuv 只能把它们交给线程池，用“同步执行加完成通知”的方式模拟异步。线程池默认只有 4 个线程。

会用到线程池的常见 API 有几类：fs 的异步方法，如 readFile、writeFile、stat；dns.lookup，它内部调用系统的 getaddrinfo；crypto.pbkdf2、crypto.scrypt、crypto.randomBytes；以及 zlib 的异步压缩方法。注意 fs 的同步版本不进入线程池，它直接在主线程上跑。

线程数可以用环境变量 UV_THREADPOOL_SIZE 调整，但有两个注意点。它只在进程启动时读取一次，运行中修改无效，必须在启动脚本里设置；数值也不是越大越好，线程过多会增加上下文切换和内存占用，通常按 CPU 核数与负载类型权衡，而不是无脑调大。更重要的是，线程池解决的是“阻塞式系统调用”的并发问题，它不能让主线程上的 JavaScript 变快。一段死循环、一次大 JSON 解析，仍然会把整个事件循环按住，这点不会因为调大线程池而改变。

阻塞排查：先测量，再定位

事件循环有没有被阻塞，不能靠感觉。最直接的指标是“定时器漂移”：注册一个每秒执行一次的定时器，记录每次实际间隔，超出预期太多就说明主线程被别的代码占住了。这个思路在生产上很实用，几十行代码就能挂进监控。

阈值取多少要看业务：普通接口服务对几十毫秒的停顿并不敏感，长连接与实时推送则要求更严。把漂移值打成监控指标，比事后翻日志有效得多，至少能回答“卡顿发生在几点、持续多久”。

有了现象，再定位到具体函数，需要采样剖析。V8 自带 –prof 开关，运行后生成日志，再用 node –prof-process 解析成可读的调用栈统计。较新的 Node 版本还提供 –cpu-prof，直接输出 Chrome DevTools 可以打开的 .cpuprofile 文件，火焰图更直观；这个开关在不同小版本上的可用性有差异，用之前先执行 node –help 确认一下，别在文档和实际版本之间想当然。

如果已经怀疑某一段代码，用 process.hrtime 打点更直接。它返回秒与纳秒组成的数组，差值精度远高于 Date.now，适合测量毫秒级的解析、序列化与循环。

常见的阻塞源就那么几类，排查时可以按这个清单过一遍。同步文件 API，如 readFileSync、statSync，在大文件或网络挂载盘上尤其慢；大 JSON 的 parse 与 stringify 全是同步的，几十 MB 的响应体足以让循环停顿数百毫秒；带嵌套量词的正则遇到不匹配的长串会发生回溯爆炸，耗时随长度指数增长；pbkdf2Sync、scryptSync 把本该在线程池里做的计算搬回了主线程；死循环与超大循环，包括前面说的递归 nextTick。

需要说明的是，本文只讨论时间维度上的阻塞。内存泄漏、堆快照分析属于另一套工具和另一条思路，不在本文展开。

把重活挪出主线程

知道阻塞源之后，处理办法大致分三层，改造成本从低到高。

第一层是拆块。把一个长循环切成小段，每段结束用 setImmediate 让出事件循环，让 I/O 和定时器有机会插进来。批处理脚本、数据导入这类任务适合这么做。

每批处理一百条，总耗时不会明显缩短，甚至会略微变长，但单次停顿从“几秒”降到“几毫秒”，请求不再成片超时。这里选 setImmediate 而不是 setTimeout(fn, 0)，是因为前者在 check 阶段执行，不受 1 毫秒规整的影响，让出得更干脆。

第二层是 worker_threads。它在 Node 10.5.0 引入，写这篇文章时仍是实验特性，必须加 –experimental-worker 参数才能启用，Node 8 上根本没有这个模块。它能让一段计算真正跑在另一条线程上，主线程继续处理请求。

代价是数据要跨线程序列化传递，线程启动也有开销，所以它适合单次几十毫秒以上的计算，不适合把每个小函数都搬过去。实验特性还意味着 API 可能调整，升级 Node 时要专门回归。

第三层是独立服务。把视频转码、报表生成、图片处理这类重活拆成单独的进程或服务，用消息队列通信，Node.js 只负责接请求、投递任务、回传结果。这一层改造最重，但边界最清楚，也最方便单独扩容。

几个常见误解

setTimeout(fn, 0) 并非立即执行，0 会被规整为至少 1 毫秒，回调仍要排队。Promise 回调也不是“下一轮”，它在当前回调结束后立刻执行，比 setImmediate 更早。await 之后的代码同样是微任务，恢复时机与 then 一致。nextTick 则不属于 Promise，它是 Node.js 自己的队列，优先级更高。

小结

事件循环的本质是调用栈清空后按阶段取回调，六个阶段的顺序解释了定时器、I/O 与 setImmediate 的差异。微任务插在回调之间，nextTick 又先于 Promise；libuv 线程池只有四个位置，它解决的是阻塞式系统调用的并发，而不是 JavaScript 的计算速度。线上卡顿先用定时器漂移测量，再用剖析工具定位，最后按拆块、worker_threads、独立服务的顺序改造。
