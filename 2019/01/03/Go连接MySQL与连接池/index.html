Go 连接 MySQL 与连接池

本文属于《Go 语言与工程》第 58/78 篇
上一篇系列目录下一篇

用 Go 写服务，几乎绕不开 MySQL。本文从 database/sql 的定位讲起，把 DSN 参数、池参数、增删改查、预处理、NULL 与时间类型、事务边界串成一条线，最后给出一个分层的 repository 示例。适合刚把 Go 服务接上数据库、还在被 Scan 报错和连接超时困扰的读者。

database/sql 不是驱动

很多初学者把 database/sql 当成 MySQL 驱动，写了 import "database/sql" 之后调用 sql.Open("mysql", dsn)，运行时报 unknown driver "mysql"，才发现少了一行导入。database/sql 是标准库里的抽象层，它定义 Driver、Conn、Stmt、Rows 等接口，并在接口之上实现了一个并发安全的连接池；真正讲 MySQL 协议、负责握手与收发包的是第三方驱动。两者的关系更像插座与插头，标准库规定形状，驱动负责通电。

因此驱动要以匿名导入的方式注册自己：

下划线表示只执行包的 init 函数，不直接使用包内符号。驱动在 init 里调用 sql.Register("mysql", &MySQLDriver{})，把名字与实现登记到全局表；之后 sql.Open 才能按名字找到它。少了这一行，编译能过，运行必错。

第二个要建立的观念是：*sql.DB 不是一条连接，而是池的句柄。它内部维护空闲连接列表、打开连接计数与等待队列，可以被多个 goroutine 同时使用。正确做法是进程启动时创建一次，注入到各 repository，退出时 Close；而不是每个请求 sql.Open 一次再关掉。

DSN 的组成部分

DSN 是数据源名称，格式固定为 用户名:密码@协议(地址:端口)/库名?参数=值。一个常见的写法如下：

前半段是身份与位置：用户名、密码、tcp 协议、地址端口、默认库名。库名可以留空，之后用 blog.posts 这样的全限定名访问，但建议显式写上，避免驱动行为不直观。密码里若出现 @、/、: 等字符，容易把 DSN 解析弄乱，应避免使用，或改用配置项分别传入。

后半段才是踩坑密集区，逐个说。

parseTime=true 决定 DATE、DATETIME、TIMESTAMP 三类的扫描结果。不开这个参数，驱动把时间列当成 []byte 返回，你往 time.Time 里 Scan 会直接报类型不匹配；开了之后才转成 time.Time。这是新手最常见的一个“明明字段有值却扫不进去”。

loc 指定解析时间时使用的时区，默认是 UTC。数据库里存的 DATETIME 本身不带时区，驱动按 loc 给它贴上时区标签。如果服务器在东八区、程序却用默认 UTC，读出来的时间会差八小时。可以写 loc=Local，但它依赖进程运行环境的 TZ，容器里经常是 UTC，结果本地开发正常、上线就错。更稳妥的是显式写 loc=Asia%2FShanghai，斜杠要 URL 编码成 %2F。

charset=utf8mb4 关系到字符能否存进去。MySQL 里的 utf8 实际最多三字节，存不下 emoji 和部分生僻字，写入时可能报 Incorrect string value，也可能被静默截断。建库建表与连接都使用 utf8mb4，两头一致才不会出现“有的客户端能写、我的服务不能写”。

三个超时参数容易被忽略。timeout 是建立连接（TCP 握手加认证）的超时；readTimeout 与 writeTimeout 是单次读写的超时。不设置时，网络半开或对端不响应，调用可能挂很久，把上游的 goroutine 一起拖住。一般设成秒级，并与服务的整体超时预算对齐。这些是驱动层超时，与后文的 context 超时是两套机制：前者管一次网络 IO，后者管整条调用链。

最后一条纪律：DSN 里不要拼接任何用户输入。它包含账号密码，应该来自环境变量或配置文件，日志里打印时要脱敏。把它当普通字符串随手拼接，既可能破坏解析，也可能把凭据写进日志。

初始化与三个池参数

sql.Open 的名字有欺骗性，它并不建立连接。调用时驱动只检查 DSN 的格式，把参数解析好存起来，真正的 TCP 连接要等到第一次执行语句时才拨号。这意味着 sql.Open 返回 nil 错误，不代表数据库可达；地址写错、密码错误、库不存在，都要到第一次查询才暴露。生产服务如果在启动时才发现连不上，滚动发布就会陷入“进程活着但不可用”的状态。

所以初始化要加一次显式探活：

PingContext 会从池里取一条连接并发送 ping，既验证了网络与认证，也顺带完成一次建连。失败时先 Close 再返回，避免泄漏半初始化的池。

三个池参数只需要先理解语义。SetMaxOpenConns 限制同时打开的连接总数，包括正在使用和空闲的；默认值 0 表示不限制，流量一大就可能把 MySQL 的 max_connections 打满。SetMaxIdleConns 限制空闲池大小，默认只有 2，如果你的并发长期高于 2，多出来的连接归还后会被直接关闭，下次请求又要重新握手；一般设成与最大连接数同一量级。SetConnMaxLifetime 是连接的最长存活时间，到点后连接在用完后被丢弃。它的意义在于躲开 MySQL 的 wait_timeout：服务端先断开空闲连接，客户端却以为还能用，下一次查询就报 invalid connection。把它设得比 wait_timeout 短，就能让客户端主动换新连接。

这三个值的取舍、监控与压测属于另一个话题，本文只要求先把它们显式设上。

增删改查与 Scan

database/sql 为查询提供了两类入口。QueryContext 返回 *sql.Rows，用于多行结果；QueryRowContext 返回 *sql.Row，用于确定最多一行的场景，它把 Close 与 ErrNoRows 的处理藏在了 Scan 里。写操作走 ExecContext，返回 sql.Result。

预处理与参数化

参数化查询有两种写法：把参数直接交给 ExecContext，由驱动内部完成转义与执行；或先 PrepareContext 得到 *sql.Stmt，再反复传参。后者适合同一条语句在短时间内执行很多次的场景，比如批量导入：

Stmt 会记住语句在服务端的标识，后续执行省去重复的解析与计划生成。但它绑定在具体的连接上：来自 db.Prepare 时，若原连接忙，驱动会在另一条连接上重新准备；来自 tx 时则只在事务内有效。所以 defer stmt.Close() 不能漏，长期不关的 Stmt 会让连接无法回收。

参数化能防注入，原因不在驱动“过滤了危险字符”，而在 SQL 文本与数据从传输层就分开：语句先被解析成带占位符的模板，参数作为独立的值送达，永远不参与语法分析。哪怕参数里写着 ' OR 1=1 --，它也只是某个字符串列的值。反过来，只要把用户输入拼进 SQL，无论怎么手工转义都迟早出问题。

由此得出一条硬规则：值可以参数化，标识符不行。表名、列名、ORDER BY 的方向都无法用 ? 代替，只能做白名单映射。比如排序字段只能从固定集合里选，选不中就用默认值。

NULL、时间与 decimal

数据库列允许 NULL，Go 的 string、int64 不允许。直接把 NULL 扫进这些类型会得到 converting NULL to string is unsupported 之类的错误。标准库为此提供了 sql.NullString、sql.NullInt64、sql.NullTime 等包装类型，它们多了一个 Valid 字段：

用 *string 也可以，遇到 NULL 时被置为 nil，语义更贴近“可空”。两种方式都能工作，关键是团队内统一。

时间类型依赖前面提到的 parseTime。开启后，DATETIME 与 TIMESTAMP 可以直接扫进 time.Time；列可为空时用 sql.NullTime。要注意 TIMESTAMP 会随会话时区转换，DATETIME 不会，跨时区部署时优先用 DATETIME 并在应用层统一按 UTC 存储、按需展示，比依赖数据库会话时区更可控。

DECIMAL 是另一个容易失手的地方。驱动把它以字节形式返回，扫进 string 能完整保留精度，扫进 float64 则会引入二进制浮点的舍入误差。金额、单价这类字段应当用 string 接收，再交给定点数库或按分存储的整数处理；只有确定只做展示、不参与计算的场景，才可以图省事用 float64。

事务与上下文

事务从 BeginTx 开始。它接受上下文，意味着可以给整个事务设一个截止时间：

defer tx.Rollback() 是 Go 里的惯用法：无论从哪条路径返回，只要没提交就回滚。提交成功之后这个 defer 仍会执行，此时 Rollback 返回 sql.ErrTxDone，属于预期行为，直接忽略即可。它换来的是“忘记回滚”这类错误被彻底消除。

事务内的每一条语句都必须用 tx 的方法。如果中途顺手写了 db.ExecContext，那条语句会从池里另取一条连接、在事务之外自动提交，既不受回滚保护，还可能因为锁等待把事务卡死。这是很难在生产环境复现的一类 bug。

上下文超时对事务同样生效。ctx 到期后，驱动会取消正在执行的语句并回滚事务，Commit 返回错误。所以事务的截止时间要覆盖其中所有语句，不能只包住第一条。

还有一条经验：事务里不要做远程调用、发消息、等第三方接口。事务持有一条连接，也可能持有行锁，任何慢操作都会把锁的持有时间成倍放大。正确顺序是先完成外部调用，再把需要原子写入的部分放进事务。

常见错误清单

排查连接问题，先看这几处。

忘记 rows.Close() 是最常见的连接泄漏。Rows 持有连接，不关闭就不会归还，池里的连接被占满后，后续请求全部阻塞在等待队列里，表现为接口整体变慢而不是报错。

在循环里写 defer rows.Close() 同样危险。defer 要到函数返回才执行，循环一千次就压了一千个待关闭对象，连接直到函数结束才释放。defer 应写在循环外，紧跟查询之后。

Scan 参数数量或顺序不匹配，报错信息通常是 expected N destination arguments。列顺序改了而代码没改，也会出现类型对不上却很难一眼看出的情况，查询里显式列出字段比 SELECT * 安全得多。

连接被服务端 wait_timeout 断开，报错多为 invalid connection 或 unexpected EOF。除了把 SetConnMaxLifetime 设短，还应在 DSN 里设置 timeout 与读写超时，让失效连接尽快以错误形式暴露，而不是长时间悬挂。

时区不一致表现为“写入是 10 点、读出来是 2 点”。检查三处：DSN 的 loc、MySQL 的 time_zone、以及应用是否在展示层又转了一次时区。三者只允许一处做转换。

utf8 与 utf8mb4 混用则表现为 emoji 写不进去，或者某些接口能写、某些不能。把库、表、列、连接四处的字符集统一成 utf8mb4，再把排序规则对齐，问题基本消失。

小结

database/sql 提供接口与连接池，驱动负责协议，两者通过匿名导入连接；sql.DB 是长期持有的池句柄，不是一条连接。DSN 里的 parseTime、loc、charset=utf8mb4 与超时参数决定了时间、字符和故障行为。初始化用 PingContext 探活并显式设置三个池参数；查询记得关 Rows、查 Rows.Err()，写操作区分 ErrNoRows 与真实错误。参数化把语句与数据分开，是防注入的根本；NULL、时间、金额要选对承载类型。事务用 defer tx.Rollback() 兜底，语句全走 tx，且不要在事务里做远程调用。
