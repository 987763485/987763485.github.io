Node.js 异步错误处理最佳实践

本文属于《TypeScript 学习路线》第 57/74 篇
上一篇系列目录下一篇

线上最常见的一类故障，不是进程崩了，而是进程还活着、请求却永远没有响应。这类问题多半出在异步错误的传递链上：错误被抛出后没有人接，或者被接住后没有继续传。本文按回调、Promise、async/await 三代写法梳理错误的流向，再落到 Express 与 Koa 的错误中间件、超时重试、日志字段与优雅退出这些工程细节。读者应已能独立编写 Node 服务，读完可以对着一张调用链说清楚“这个错误最终会到哪里”。

回调时代的 error-first 约定

Node 的核心 API 几乎都遵循同一套约定：回调函数的第一个参数留给错误，成功时为 null，真正的结果放在第二个参数。

为什么把 error 放在第一位？因为回调没有返回值通道，调用者只能靠参数顺序形成固定的检查习惯。错误在前，读代码的人第一眼就会看到分支；结果在前，则很容易在解构之后才想起还有失败这回事。这个约定贯穿 fs、net、dns 等模块，也是后来 util.promisify 能够自动转换的基础。

同步抛错与异步回调抛错

try/catch 只能捕获当前调用栈上同步抛出的异常。回调是在未来的某个 tick 由事件循环调用的，那时 try 块早已执行完毕，调用栈也换了一层。

这个 throw 会一路冒到事件循环，变成未捕获异常，进程默认退出。setTimeout 的回调、EventEmitter 的监听器也是同样的道理，在它们内部抛错，外层的 try 一律无效。

process.nextTick 更容易让人误判。它的回调排在当前操作之后、事件循环进入下一阶段之前，时机非常靠前，但它仍然是异步的：

所以“把可能出错的代码包进 try/catch”只对同步段有效。异步段的错误必须在回调内部处理，或者交给进程级兜底。可以用一张图概括错误的去向：

  A[调用异步 API] --> B{错误发生在哪里}
  B -->|同步参数校验| C[try/catch 可以捕获]
  B -->|回调内部 throw| D[uncaughtException]
  B -->|Promise 被 reject| E[最近的 catch 或 unhandledRejection]

Promise：错误从抛出变成值

Promise 把异步结果收进一个对象，错误不再是“抛出去”，而是“reject 出来”，于是可以在链尾统一挂一个 .catch。这解决了回调时代错误无处安放的问题，但也带来了新的盲区。

reject 与 .catch 的位置

两条规则值得记住：then 的回调里抛出的异常会自动转成 rejection，沿链继续向后传；.catch 等价于 .then(undefined, onRejected)，只处理它之前的环节。如果把 .catch 放在链中间又不重新抛出，错误就被“吃掉”了，后面的 then 会拿到 undefined 继续执行，这比直接失败更难排查。

未处理的 rejection

一个被 reject 却没有任何处理器的 Promise，在 Node 10 里只会打印一行 UnhandledPromiseRejectionWarning，进程继续运行。这意味着业务已经失败，调用方却没有收到任何响应，监控上看进程健康、CPU 正常，只有客户端在超时。线上“请求挂死但服务没挂”的案例，很大一部分来自这里。默认行为在版本之间并不一致，不能把“只警告”当成规范，后文会专门讨论策略。

Promise.all 的部分失败

Promise.all 是快速失败：任意一个 reject，整体立刻 reject，其余结果不再等待。已经成功的值拿不到，尚未完成的任务也不会被取消，仍然在后台跑完，副作用照常发生。

async/await 的新边界

async/await 让异步代码重新长得像同步代码，await 会把 rejection 还原成 throw，于是 try/catch 又能用了。但边界只是被移动，并没有消失。

return await 的取舍

在 try 块里，return await task() 与 return task() 并不等价。后者把 Promise 直接交给调用方，当前函数随即返回，rejection 发生在本函数之外，这里的 catch 不再生效；前者会等结果出来再返回，错误仍在 try 的作用域内。

判断标准很简单：需要在当前函数里捕获、补充上下文或做清理，就必须 return await；只是透传结果，直接 return 更轻，少一次微任务调度。不要为了“看起来整齐”给所有返回都加上 await。

最后一道防线

uncaughtException 和 unhandledRejection 都不是“让服务继续跑”的钩子。前者触发时，事件循环已经处于未知状态：可能有一个写了一半的回调，可能有一个被破坏的请求上下文，继续服务只会制造更难排查的脏数据。官方文档对此的措辞是“不安全”。

正确的处理只有三步：把错误和现场完整写进日志，停止接收新请求，清理后以非零码退出，交给进程管理器拉起新实例。unhandledRejection 同理。Node 10 与 Node 12 的默认行为都是打印警告后继续运行，区别在于 Node 12 提供了 --unhandled-rejections=strict，可以让它按未捕获异常处理并以非零码退出。默认值一致不代表可以依赖它，生产环境应当显式选定行为并写进启动脚本。

这里先 server.close 再退出，是为了让在途请求有机会完成；十秒的定时器用 unref 去掉引用，不会自己拖住事件循环。

Express 的错误中间件

Express 靠参数个数识别错误处理器：必须是四个参数 (err, req, res, next)，少一个就会被当成普通中间件，永远不会被调用。它要注册在所有路由之后。

同步 handler 里 throw 是安全的，Express 在调用路由时包了 try/catch，会自动转成 next(err)。异步 handler 则没有这层保护：Express 4 不认识返回的 Promise，async 函数里的 rejection 不会自动进入错误中间件，请求会一直挂到客户端超时。

响应格式要统一，至少包含业务码、可展示的文案和 requestId。5xx 一律不回传 err.message 和堆栈，它们可能带出 SQL 片段、文件路径或内网地址；客户端只拿到通用文案和请求编号，排查时用编号去日志里对。4xx 的业务错误可以给出具体原因，例如“余额不足”，这类信息本来就是给用户看的。

真正的取消需要底层支持。AbortController 在浏览器端已经随 fetch 规范可用，但 Node 核心当时并未内置，只能借助 abort-controller 这类 npm 包，而且 http 模块对取消没有统一约定，整体仍处于实验阶段。工程上更现实的做法是设置 socket 超时，超时后主动 destroy 连接。

重试的边界

只重试“可能自己恢复”的错误：网络抖动、连接重置、下游 503、超时。参数错误、鉴权失败、404 重试多少次都一样。写操作默认不重试，除非接口支持幂等键，否则一次超时可能对应一次已经成功的扣款，重试就变成重复扣款。

退避采用指数加随机抖动，并同时限制次数与总时长。三次重试、每次上限十秒，最坏情况会让上游等三十秒，因此重试必须套在总超时之内，超出预算就直接失败。

错误分类与可观测性

业务错误是预期内的分支：参数不合法、余额不足、没有权限。它们应当映射到 4xx，带稳定的错误码，文案可以直接给用户看。系统错误是缺陷或容量问题：连接池耗尽、下游超时、读取了 undefined 的属性。它们映射到 5xx，需要告警和人工介入。两类混在一起，后果不是告警泛滥，就是把系统故障当成用户错误回一个 400，真正的问题被埋掉。

日志至少固定几个字段：requestId（入口生成，透传给下游）、userId、路由与方法、耗时、err.name、err.message、err.stack 和业务码。requestId 是把一次请求在多个服务里的日志串起来的唯一线索，比时间戳可靠。

最后是一个常见错误：不要把 error 对象直接 JSON.stringify。message 和 stack 都是不可枚举属性，序列化结果是 {}，日志里只剩一个空对象。应当显式挑选字段，或者使用 util.inspect、日志库提供的 serializer。挂在错误对象上的自定义上下文同样需要显式提取，遇到循环引用时 JSON.stringify 还会直接抛错，把错误处理逻辑本身弄挂。

优雅退出的正确姿势

发布、缩容、迁移都会给进程发 SIGTERM。这时不能立刻 process.exit()，那会截断正在写的日志和未完成的响应；也不能什么都不做，容器会在宽限期后发 SIGKILL。

标准流程是：停止接受新连接，等待在途请求结束，关闭数据库和消息队列的连接，最后让进程自然退出。server.close 只负责第一步，它不再接受新连接，但要等所有连接关闭才触发回调。麻烦在于 HTTP 的 keep-alive：浏览器或网关的空闲连接要等到 keep-alive 超时才释放，在途的长请求也可能拖很久，回调迟迟不来。所以需要自己记录 socket，在宽限期结束后强制销毁：

想让退出码可区分，可以在清理完成后设置 process.exitCode = 0 并停止持有事件循环，让进程自己走完，而不是用 exit 打断收尾工作。容器场景还有一个前提：Node 进程必须是 PID 1 或者能收到信号。直接以 Node 作为容器主进程时，记得加 --init，否则 SIGTERM 可能到不了应用，宽限期一过就被 SIGKILL，前面所有清理都白做。

常见反模式清单

  • 吞掉错误：catch 里只打一行日志，既不重新抛出也不返回失败，调用方以为成功。
  • 在回调里 throw：等价于主动制造一次未捕获异常，外层 try 完全无效。
  • 忘记 return：if (err) callback(err) 之后继续往下执行，回调被调用两次，Express 里表现为响应头重复设置。
  • 只 reject 一个字符串：丢失堆栈和错误类型，上层无法分类，只能靠匹配文案。
  • 包装错误时丢掉原始信息：当时还没有 cause 选项，至少把原 message 和 stack 拼进新错误，或挂在 err.original 上。
  • 用 catch 返回默认值掩盖故障：缓存读失败返回空数组，页面看起来正常，数据却已经错了。

小结

异步错误处理的核心不是记住某个 API，而是清楚每一段代码的错误最终流向哪里。回调靠 error-first 约定，Promise 靠链尾的 catch，async/await 靠 try/catch 的边界，三者都不能跨越事件循环。业务代码负责把错误分类并补充上下文，框架层负责把它转成合适的响应，进程层只做记录与退出，不假装还能继续服务。把这几层边界划清楚，线上“请求挂死、进程还活着”的问题会少一大半。
