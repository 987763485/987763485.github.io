Go 实现文件上传与分片

本文属于《Go 语言与工程》第 66/78 篇
上一篇系列目录下一篇

文件上传看起来只是把请求体写进磁盘，真正落到服务端却处处是边界：请求体能有多大、内存会不会被撑爆、临时文件谁来删、文件名能不能直接拼路径。本文从 multipart/form-data 的报文结构讲起，用 Go 1.12 的标准库实现单文件上传与分片上传，再把合并、校验与安全边界串成一条可用的链路。

从报文结构理解 multipart/form-data

表单里有文件时，浏览器不会用 application/x-www-form-urlencoded，因为二进制字节要先做百分号转义，体积膨胀，服务端还得逐字节还原。multipart/form-data 把每个字段当成一段独立的“信件”，用分隔线隔开，二进制内容原样放进去。

请求头里会带一个 boundary 参数，它是一串浏览器随机生成的字符：

请求体就由这条边界切分成若干 part。注意实际分隔行比 boundary 多两个前导连字符，结束行还要在末尾再加两个：

每个 part 由头部、一个空行、内容三部分组成，头部至少有 Content-Disposition，name 是表单字段名，filename 只出现在文件字段上。内容与分隔行之间用 CRLF 隔开，所以严格的分隔符是 \r\n--boundary，这也意味着 boundary 不能出现在文件内容里，否则解析会错位。

理解结构之后，服务端的任务就清楚了：找边界、切 part、读头部、交出内容。mime/multipart 已实现这套状态机，我们不必手写，但要知道它的代价——内容可能落在内存，也可能落在磁盘，取决于传入的参数。

为什么不能直接读整个请求体

最常见的错误写法是 ioutil.ReadAll(r.Body)，把整个请求体读进内存再解析。几十 KB 的图片没问题，一旦有人传 2 GB，进程内存就顶到上限。上传接口是外部可触达的入口，先全读进来等于把内存控制权交给调用方。

正确的姿势是让数据流动：读一点、写一点，任何时候只保留固定大小的块。io.Copy 配合 multipart.File 就能做到，后面会看到写法。

解析请求：内存阈值与请求体上限

标准库把解析入口收在两个方法上：r.ParseMultipartForm(maxMemory) 和更常用的 r.FormFile(name)。后者在内部会先调用前者，参数用的是默认值 32 MB。

这里有一个被广泛误解的参数。maxMemory 不是“允许上传的最大字节数”，而是解析时最多把多少 part 内容留在内存，超出部分写到 os.TempDir() 下的临时文件。它控制的是内存与磁盘的分界点，不是请求的准入门槛。

真正拦截超大请求的是 http.MaxBytesReader。它包一层 r.Body，读取超过指定字节数时返回错误，同时会通知服务器在响应后关闭连接，避免客户端继续把剩余数据推过来：

请求体上限决定最多能传多大，内存阈值决定其中多少留在内存。只设前者，60 MB 的文件仍会把 32 MB 读进内存；只设后者，请求体可以无限大，磁盘先被打满。MaxBytesReader 的值应略大于业务允许的文件大小，给边界和头部留余量。

MultipartForm 的 Value 是普通字段，File 是文件字段的映射，每个字段对应 []*multipart.FileHeader，因为同名文件字段可以出现多次。RemoveAll 清理解析产生的临时文件，不调用就会留到进程退出，在容器里尤其危险。

单文件上传：流式落盘与文件名处理

拿到 multipart.File 之后它只是一条可读流，可能是内存里的 *bytes.Reader，也可能是磁盘上的 *os.File。用 io.Copy 接到目标文件，内部以固定缓冲区循环搬运，进程内存与文件大小无关。

这段代码有三个决定。O_EXCL 让同名文件无法覆盖；0640 表示属主读写、同组只读，目录用 0750，即使被挂到 Web 根下也不能被遍历；out.Sync() 把页缓存刷盘，代价是一次系统调用，但能保证掉电后文件不是只剩元数据。

文件名是最容易出事的一环。filename 只是客户端声明，可以任意构造。直接拼路径会踩两个坑：../../etc/cron.d/x 这类穿越，以及某些平台上反斜杠不算分隔符，..\..\x 会变成合法的长文件名。先统一分隔符、再取 filepath.Base、最后白名单校验扩展名，三步都不能省；白名单只解决“叫什么”，不解决“是什么”。

h.Size 只是参考值，不能当作可信的大小依据，真正的约束还是 MaxBytesReader，落盘时也可以再用 io.LimitReader 包一层。

存储布局：目录分片与容量边界

文件一多，单目录就难维护：ext4 在单目录几十万文件时，readdir 与查找都会变慢，备份迁移也痛苦。常见做法是按时间与哈希两级分片：

第一级按日期，便于清理归档；第二级取哈希前两位十六进制，把同一天的文件散成 256 个桶。桶名与文件名都由服务端计算，用户输入不参与路径拼接。

目录权限 0750、文件 0640，属主是专用账号。上传目录不要放在静态资源目录下，更不要给可执行权限——很多入侵的起点就是上传目录里的脚本被 Web 服务器执行。正确做法是只做静态读取，或者由应用层鉴权后转发。

容量要有配额。单机可以用 syscall.Statfs 读挂载点可用块数，低于阈值就拒绝新上传并告警；也可以按租户在数据库记累计用量。只靠“磁盘满了再说”不行，磁盘写满会连带影响日志、数据库和临时文件。

对象存储是另一条路：客户端先申请带签名和有效期的上传地址，直接把字节传给存储服务，应用服务器只负责签发凭证和接收回调。好处是不承载流量，坏处是校验与清理要重新设计。本文以本地磁盘为准，理解了本地链路，迁移时才知道哪些环节不能丢。

分片上传：把大文件拆成可控的块

一个 2 GB 的文件走单请求，会撞上几堵墙：网关连接超时、网络抖动、失败后从头再来。分片把一次大传输拆成若干独立请求，哪片失败只重传哪片。

flowchart TD
    A[客户端计算文件哈希] --> B[申请 uploadId]
    B --> C[按固定大小切块]
    C --> D[逐片上传 带序号与校验和]
    D --> E[服务端校验并写入临时目录]
    E --> F{所有分片到齐}
    F -- 否 --> D
    F -- 是 --> G[按序拼接并校验整体哈希]
    G --> H[原子重命名到正式目录]
    H --> I[清理临时分片]

协议字段不多，但每个都有用途。uploadId 由服务端生成并返回，不能由客户端自报，否则谁都能往别人的任务里塞数据；chunkIndex 从 0 开始，totalChunks 固定总数，服务端据此判断越界与是否收齐；checksum 是该片摘要；fileHash 是整体哈希，为秒传和合并校验做准备。

服务端收到一片时，按顺序做四件事：确认 uploadId 存在且属于当前用户；确认 chunkIndex 落在 [0, totalChunks) 内；确认片大小不超过约定的块大小（最后一片可以更小）；重新计算摘要并与 checksum 比对。四项都过了，才写到 临时目录/uploadId/index.part。

writeIfMatch 先写带随机后缀的临时文件，边写边算哈希，通过后再 os.Rename 成 index.part，校验失败也不会留下“已完成”的错误分片。同序号重复上传直接覆盖，内容相同则结果不变；两个请求同时写同一片时各写各的临时文件，最后只有一次重命名生效，不会交错。这就是最朴素的幂等。

临时目录按 uploadId 隔离，除分片外放一份元数据，记录总片数、文件大小、创建时间，进程重启后靠它恢复任务。清理交给定时任务，超过保留期仍未合并的目录整个删掉。

合并：按序拼接与原子落盘

所有分片到齐后合并。输入是 0.part 到 n-1.part，输出一个完整文件。关键约束仍是内存：不能全读进内存再拼，而应打开目标文件，依次 io.Copy 每个分片，同时把字节喂给哈希计算器，最后与整体哈希比对。

os.Rename 的原子性有个前提：源和目标在同一文件系统。系统临时区常常是 tmpfs 或另一块盘，目标在业务盘上，重命名会返回 EXDEV。所以临时目录应和最终存储同挂载点，比如统一放在 /tmp/uploads 下，否则只能退化成“复制 + 删除”。

并发是必须处理的问题。两个请求同时合并会写同一个 .merging 文件，结果不可预测。做法是给每个 uploadId 一把锁，并用状态机约束转换：uploading 只能到 merging，merging 只能到 done，转换靠文件锁或数据库条件更新保证。重复请求看到 done 直接返回成功。合并成功后删临时目录，失败则保留分片供重试。

这里只走“分片到齐后合并”的主路径。完整的断点续传还要处理 Range、清单查询、过期清理与跨会话恢复，留给后面单独展开。

断点查询与秒传的基本思路

客户端中断后重新连接，不应该从零开始。服务端提供一个查询接口，传入 uploadId 或文件哈希，返回已经收到的分片序号列表，客户端跳过这些序号继续上传即可。实现上，分片文件是否落盘就是最直接的状态，扫描目录拿到序号，比维护一份容易失真的内存表更可靠。

秒传则更简单：上传前客户端先算整个文件的哈希，问服务端“这个哈希存在吗”。服务端在文件表里按哈希查一条记录，命中就直接返回已有文件的引用，一个字节都不用传。它依赖“同一份内容只存一份”的去重策略，也要防止有人拿哈希探测别人是否上传过某个文件，所以查询接口同样需要鉴权，返回的信息只到“存在或不存在”。

安全边界：比功能更重要

上传是典型的“把外部数据放进自己地盘”的操作，安全设计要覆盖整条链路。

大小限制是第一道闸。请求体上限、单文件上限、分片数上限、单用户日上传总量，四个维度都要有，缺一个就会被人用合法的请求慢慢耗尽资源。

类型校验不能只看扩展名，也不能只看请求头里的 Content-Type，这两者都由客户端控制。正确做法是读文件头部的若干字节做内容嗅探，http.DetectContentType 会按魔数判断常见格式，再与扩展名白名单交叉验证。对图片还可以进一步用解码器试读，解码失败就拒绝，这样能顺带挡掉一部分伪装成图片的恶意文件。

路径穿越前面已经处理过，原则是用户输入永远不参与路径拼接，落盘名一律由服务端生成。压缩包要当心压缩炸弹：一个几十 KB 的 zip 解压后可能膨胀到几十 GB，解压前必须限制解压后的总大小和文件数量，并且拒绝包含绝对路径或 .. 的条目。

病毒扫描通常以接口形式接入，文件落盘后先进入隔离区，调用扫描服务，返回干净才移动到正式目录并对外可见。扫描是异步的，所以文件状态要显式建模为“待扫描、可用、已拒绝”，不能让未扫描的文件直接被下载。

最后是鉴权与配额。上传接口必须登录后才能调用，uploadId 要绑定用户，下载要走鉴权而不是把目录暴露成静态资源。配额既包括容量，也包括请求频率，避免有人用大量小文件拖垮元数据存储。

几个容易踩的坑

ParseMultipartForm 的参数当成总大小上限，是最常见的误解，结果内存阈值设得很大，并发一上来堆就爆了。临时文件不清理同样普遍，RemoveAll 忘了调用，或者解析失败提前 return，/tmp 会以肉眼可见的速度增长。

分片乱序到达本身不是问题，按序号命名、合并时按序遍历即可；真正的问题是重复分片与越界序号没有校验，导致合并出的文件被悄悄污染。合并时把所有分片读进内存再拼接，则是把分片省下的内存又一次性还了回去。

文件名直接拼路径、上传目录带可执行权限、下载接口不做鉴权，这三件事经常一起出现，也经常一起变成事故。把它们当成上传功能的验收项，而不是“以后再补”的优化项。

小结

multipart/form-data 用边界切分字段，理解 part 结构之后，解析就只是状态机加流式拷贝。单文件上传的要点是 MaxBytesReader 限总量、ParseMultipartForm 定内存阈值、io.Copy 落盘、服务端生成文件名。分片上传把大文件拆成可重传的块，每片校验、按序合并、同盘原子重命名，再用状态机和锁保证并发下的幂等。安全上把大小、类型、路径、配额四件事做扎实，比任何单点技巧都有效。
