Node.js 性能调优：内存与 GC

本文属于《TypeScript 学习路线》第 58/74 篇
上一篇系列目录下一篇

服务跑两天就变慢，重启就好；容器里的进程莫名被杀，日志只有一行 OOM。这类现象成因各不相同。本文从 V8 的内存布局讲起，说明堆、栈与外部内存各管什么、process.memoryUsage() 怎么读；再讲 Scavenge 与标记清除、如何用 --trace-gc 观察停顿；最后落到泄漏定位与参数调优。适合遇到内存问题只会「加大内存再重启」的读者。

Node 的内存版图

Node 里「内存」对应好几个不同的东西：rss 涨了，可能是堆里对象没释放，也可能只是 Buffer 分配得多；堆用量正常、进程却被杀，可能是外部内存顶到了天花板。

堆：新生代与老生代

V8 把 JavaScript 对象放在堆上，再按存活时间分成两代：新生代（young generation）和老生代（old generation）。新生代很小，64 位平台上默认在十几 MB 量级，内部又分成两个半区（semi-space），新对象几乎都先落在其中一个；老生代大得多，存放几轮回收后仍存活的对象以及大对象。

分代的前提是「大多数对象朝生夕死」：请求里临时拼出的字符串、中间结果、解析出来的 JSON，生命周期往往只有几毫秒，放在一块小区域里扫一遍就能收走；缓存、连接、配置这类长期对象则被晋升到老生代。

两代大小决定了 GC 的行为：新生代满得快，Scavenge 频繁但很快；老生代满了才标记清除，次数少，一旦发生停顿明显更长。--max-old-space-size 与 --max-semi-space-size 调的正是这两块。

栈、外部内存与 Buffer

栈（stack）不属于堆，函数调用的局部变量、返回地址、参数都压在栈上，大小由 --stack-size 控制，超出就是熟悉的 RangeError: Maximum call stack size exceeded；它只和递归深度有关，与泄漏基本无关。

真正容易被忽略的是外部内存（external memory）。Buffer 是最典型的例子：内存在 V8 堆之外由 C++ 分配，堆里只留一个很小的对象指向它。所以一个上百 MB 的 Buffer，在 heapUsed 里几乎看不出来，external 却明显上涨。文件读写、网络收发、图片处理背后都是 Buffer。

读懂 process.memoryUsage()

Node 提供了 process.memoryUsage()，一次拿到四个字段，单位都是字节：

四个字段要连起来读：

  • rss 是操作系统看到的进程占用，包含堆、栈、代码段、Buffer 等。它只增不减很常见，因为 V8 释放的内存不一定立刻还给系统，拿它判断泄漏容易误判。
  • heapTotal 是 V8 已拿到的堆额度，heapUsed 是真正被对象占用的部分。两者差距大说明堆刚扩过容；heapUsed 持续贴近 heapTotal 且 heapTotal 一路上涨，才值得警惕。
  • external 单独统计外部内存，查 Buffer 问题时必须看它。

单点绝对值意义不大，曲线才有意义。

V8 的垃圾回收

还得知道 V8 何时、以什么方式把不用的对象收走，这决定了停顿长什么样。

Scavenge：新生代里的复制

新生代采用复制式回收，算法叫 Scavenge。两个半区一个用（from），一个空着（to）；回收时把 from 里存活的对象复制到 to，交换身份后整块清空 from。复制成本只与存活对象数量有关，与垃圾多少无关，正适合「大部分对象都死了」的场景。存活过两轮 Scavenge 的对象会被晋升（promote）到老生代；对象体积较大或 to 区空间不够时也会直接进老生代，所以突然分配大对象会让老生代提前填满。

Mark-Sweep 与 Mark-Compact

老生代存活率高、对象大，复制不划算，V8 改用标记清除（Mark-Sweep）：从根（全局对象、栈上引用等）出发遍历可达对象并打标记，没被标记的就是垃圾。缺点是留下碎片，于是还有标记整理（Mark-Compact），把存活对象往一端挪，腾出连续空间。整理要移动对象，代价更高，V8 按碎片情况决定是否整理。

增量标记与并发标记

早期的标记是全停顿的：标记期间 JavaScript 完全停下，堆越大停得越久，表现为请求抖动。V8 后来引入增量标记（incremental marking），把一次长标记拆成小步穿插在 JS 执行之间；再往后是并发标记（concurrent marking），让辅助线程在后台标记，主线程只做少量收尾，写屏障（write barrier）保证期间新增或修改的引用不被漏掉。

但 GC 并非完全无停顿：Scavenge 本身要停住主线程，老生代的收尾和整理也要停。目标不是消灭停顿，而是让停顿可控，别让堆无节制地长，也别让老生代塞满短命的大对象。

观察 GC：先让数据说话

–trace-gc 与 –trace-gc-verbose

启动时加参数即可：

输出一行一次 GC，包含时间戳、耗时、类型与回收前后的堆大小。类型里有 Scavenge、Mark-Compact、Mark-Sweep，看类型就知道落在新生代还是老生代，看前后堆大小就知道收回多少。--trace-gc-verbose 会多打印空间细节与停顿构成，量很大，只适合短时间打开。

v8.getHeapStatistics()

程序内可以直接读 V8 的堆统计：

heap_size_limit 是堆上限，total_heap_size 对应 heapTotal，used_heap_size 对应 heapUsed。v8.getHeapSpaceStatistics() 还能按空间（new_space、old_space、code_space 等）列出大小与用量，判断哪一代吃紧特别有用。Node 12 起堆上限默认值会参考系统可用内存，先打印确认比凭印象猜可靠。

三个信号：频率、暂停与增长

看 trace 不要只盯单次，三个信号最有价值。

一是频率。Scavenge 本来很密，老生代回收很久才来一次；若它从几分钟一次变成几秒一次，说明有对象持续晋升，或老生代已填满。

二是暂停时间。单次标记整理从个位数毫秒涨到几十毫秒，对外就是接口毛刺。把窗口内停顿累加除以窗口长度，就是 GC 占比，偏高时延迟一定不稳。

三是回收后的堆底。每次 GC 结束时的 heapUsed 才是真正活着的东西。底一轮比一轮高是泄漏的典型形状；底稳定而峰值高，多半是分配太猛。

内存泄漏的常见模式

所谓泄漏，绝大多数是「本该释放的引用被一直持着」。V8 不会漏，是代码把对象挂在了不该挂的地方。

全局缓存无上限

最朴素的一种：

请求越多，cache 越大，直到堆被填满。缓存没错，错在没有上限与过期；至少给条数或大小设上限，再加 TTL 与淘汰策略。

闭包持有大对象

闭包捕获的是整个作用域，哪怕函数体里只用一个字段，整个对象也可能被留住，常见于把大对象塞进回调、事件处理器或 then 里。拆解很简单：先取出需要的字段，让闭包只引用这一小份。

事件监听器未移除

EventEmitter 的监听器挂在实例上，实例不销毁，监听器就一直被引用，又反过来引用它捕获的上下文。长连接、单例的 emitter 最容易积累。setMaxListeners 只是把警告压下去，注册与移除要写在同一个生命周期里。

定时器与 Interval 未清理

每调用一次就多一个永不停止的定时器，回调还持有 id 及相关对象。定时器要保存句柄，在销毁或请求结束时 clearInterval，setTimeout 递归轮询同理。

Promise 链挂住

永远 pending 的 Promise 会把它引用的上下文留在堆里，典型场景是请求忘了设超时。给外部调用统一加超时封装，比事后查快照省事。

Buffer 与外部内存

把大 Buffer 存进数组或 Map 当临时缓冲，是外部内存泄漏的常见来源。它在堆外，快照里只有一个小壳对象，heapUsed 看着正常，直到 rss 或 external 顶到天花板，所以 external 必须一起进监控。

数据库连接未释放

连接池耗尽先是请求排队、超时，然后才是内存上涨。借了连接却没归还（异常分支没走 finally），连接对象与会话状态都会累积。借还必须包在 try/finally 里。

用堆快照定位泄漏

模式对不上、代码又大，就得上工具。

–inspect 与 DevTools 的三个视图

启动后用 Chrome 打开 chrome://inspect 连上进程，在 Memory 面板抓 Heap Snapshot。三个视图配合用：Summary 按构造函数聚合，先看哪类对象数量异常；Comparison 是排查主力，隔一段时间抓第二张，按新增数量排序，多出来的就是嫌疑人；Retainers 回答「谁在引用它」，沿引用链追到 GC Root，那条链就是持有者，多半能直接看到元凶：某个全局数组、某个 emitter 的 listeners、某个没清掉的定时器。

调优手段与边界

定位到问题就改代码；确认没有泄漏之后，才轮到参数。

堆上限不是万能药

（512 MB 只是示例，实际值按机器内存与实例数分配。）提高上限能推迟 OOM，但不会修复泄漏：只是从每天重启一次变成每三天一次，而且单次标记扫的堆更大、停顿更长。正确顺序是先确认对象生命周期合理，再按常驻集大小留余量。上限也不该等于机器内存，要给操作系统、栈、外部内存和其他进程留空间。容器里默认值按宿主机内存算，限额小时必须显式指定，否则会被 OOM Killer 干掉。

–max-semi-space-size 的取舍

这个参数调整新生代每个半区的大小（单位 MB）。调大后 Scavenge 次数变少，短命对象更多死在新生代、不必晋升，老生代压力减轻；代价是单次复制范围更大、停顿变长，基础内存更高。它适合分配速率高、存活率低的服务，比如大量 JSON 解析；分配少的服务收益有限。改之前先用 trace 确认 Scavenge 是热点。

对象池要谨慎，流式与分批更实在

「少分配」是降低 GC 压力的正路，但对象池经常帮倒忙：新生代分配本来就快，短命对象是常态，自己维护池子反而引入状态清理与复用竞争，池子还可能变成泄漏源。值得复用的是创建成本高的东西：数据库连接、HTTP 连接、正则、编译好的模板。

压测与验证

改完要有对照：固定压测场景，先跑基线，再跑优化后，比较同一窗口内的堆曲线与 GC 次数。

-c 是并发连接数，-d 是持续秒数，ab 也能用。压测期间同步开 --trace-gc，或采集 heapUsed 与 external。对比四件事：结束后堆能否回落到接近起点，老生代 GC 次数是否随请求量线性增长，高分位延迟是否被停顿抬高，external 是否单调上升。只看吞吐不够，有些「优化」只是把问题推迟到压测之后。

常见坑

  • 把 rss 当堆内存：它包含栈、代码段、Buffer 和未归还的空闲页，用它判断泄漏几乎必然误判。
  • 只加 --max-old-space-size 不修泄漏：等于给漏水的桶换个大桶。
  • 在生产高峰期抓快照：序列化的开销可能直接把进程推过内存红线。
  • 忽略外部内存：Buffer 泄漏在 heapUsed 上几乎看不见。
  • 缓存没有 TTL：内存只增不减，只能靠重启恢复。
  • 用单点数值下结论：要看趋势，尤其是每次 GC 之后的堆底。

小结

Node 的内存要分两块看：V8 堆里的对象，以及堆外的 Buffer 与外部内存；process.memoryUsage() 的四个字段各管一段，单看 rss 最容易误判。GC 方面，Scavenge 负责短命对象、频繁但短暂，标记清除与整理负责老生代、次数少但停顿长，增量与并发标记把长停顿切碎，却无法完全消除。排查顺序应是先观察、再定位、最后调参数：用 --trace-gc 与 v8.getHeapStatistics() 拿到频率、停顿与堆增长，用快照的对比与引用链找到持有者，确认生命周期合理之后，再谈两个堆参数。绝大多数内存问题本质是引用没释放，参数只能推迟爆发；heapUsed 与 external 的曲线要长期留在监控里。
