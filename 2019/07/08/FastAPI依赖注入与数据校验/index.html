FastAPI 依赖注入与数据校验

本文属于《Python 学习路线》第 21/29 篇
上一篇系列目录下一篇

FastAPI 在 2018 年底公开发布，到 2019 年年中已经有不少团队拿它写内部服务与对外接口。它最吸引人的地方并不是跑分，而是把类型注解同时当成校验规则、序列化规则和文档来源，写一遍声明，三件事一起成立。本文沿着「参数怎么校验、模型怎么定义、依赖怎么组织、错误怎么统一」这条线，把日常开发真正会用到的部分讲清楚。读者需要会写 Python 3.7、了解基本的 HTTP 语义，读完应当能独立搭起一个结构清晰、可测试的 FastAPI 服务。

FastAPI 的定位与本文边界

站在 Starlette 与 Pydantic 肩上

FastAPI 自己几乎不做底层工作。HTTP 解析、路由匹配、中间件、Request 与 Response 来自 Starlette；数据模型、类型转换、字段约束来自 Pydantic；FastAPI 负责的是把它们粘起来，并在这层粘合里加入依赖注入、参数提取和 OpenAPI 文档生成。把这三个名字的分工记住，很多行为就不用猜：路由与生命周期归 Starlette，模型与校验归 Pydantic，Depends、Query、Path、response_model 是 FastAPI 自己的语法糖。

这种分工带来一个直接后果：校验发生在进入视图函数之前。视图函数拿到的参数已经是声明过的类型，不需要再写 int(request.args.get(...)) 这类防御代码。错误则以统一的 422 响应返回，结构由框架生成，前端可以按同一套规则解析。

版本现状与示例环境

本文的示例基于 Python 3.7 与 0.3x、0.4x 时期的 FastAPI。这个项目迭代很快，小版本之间偶尔会调整参数签名，升级前最好看一眼变更记录，不要默认照抄半年前的博客。依赖只有两个：

需要说明的是，FastAPI 在 2019 年已经可以用于生产，但它还不是一个「冻结」的框架，周边生态（权限、ORM 集成、迁移工具）都还在成型。本文只讲用法与边界，不讨论该不该选它；框架之间的横向比较留给另一篇。

路径参数与查询参数

类型注解就是校验规则

最简单的接口就能体现它的设计取向：

item_id 声明为 int，访问 /items/abc 会得到 422，响应体里写明字段位置、传入值和期望类型，而不是抛一个 500。q 有默认值、又不在路径模板里，于是被识别为查询参数；如果把 q 写成 q: str 而不给默认值，它就变成必填的查询参数。这套规则只有三条：出现在路径模板里的名字是路径参数；其余标量类型是查询参数；Pydantic 模型或 Body 声明的是请求体。

函数用 def 还是 async def 也有实际差别。def 会被放进线程池执行，内部可以放心调用阻塞的数据库驱动；async def 直接在事件循环里跑，里面出现阻塞调用就会卡住整个进程。

用 Query 与 Path 加约束

仅有类型还不够，业务上常见的「页码从 1 开始」「名称长度 3 到 50」「编码只能是小写字母和短横线」需要额外声明：

Path 与 Query 的第一个位置参数是默认值，写 ... 表示必填；把路径参数写成 item_id: int = 5 这种带默认值的形式，框架会直接报错，因为路径参数不可能缺省。gt、lt 是开区间，需要闭区间时用 ge、le；字符串用 min_length、max_length 和 regex。这些约束在解析阶段生效，越界的请求根本进不到函数体，函数里拿到的 page 一定在 1 到 99 之间。

把 description 写进声明还有个副作用：它会出现在自动生成的文档里，前端联调时不必再问参数含义。

可选参数与隐式转换

Optional[str] = None 与 str = "" 都能让参数变成可选，区别在语义：前者区分「没传」与「传了空串」，后者把两者合并。做筛选条件时建议用前者，因为「不限」和「名称为空」往往是两件事。

隐式转换也要心里有数。查询串里的一切都是字符串，page=2 会被转成整数，page=abc 会被拒绝；浮点数、日期、UUID 同理，只要在注解里写对类型即可。布尔值最容易出意外，不同写法会被解析成不同结果，接口文档里最好明确约定用 1/0 或 true/false，不要指望客户端猜。复杂结构（列表、字典）不适合塞进查询串，真需要时用请求体，或约定 tags=a,b,c 自行切分。

响应模型与状态码

输入校验之外，输出也需要契约。response_model 决定响应的形状：过滤多余字段、按声明做类型转换，并把结构写进文档：

这里的关键是：函数返回什么并不重要，框架会按 response_model 重新校验并序列化输出。多出来的字段被丢弃而不是报错，这一点与输入校验相反；缺字段或类型不符则会在服务端抛出响应校验错误，属于代码问题。把 UserOut 单独定义，而不是直接返回 UserIn，就是为了让密码这类字段没有机会漏出去。

如果只想返回客户端真正设置过的字段，可以在装饰器上加 response_model_exclude_unset=True，未显式赋值的字段不会出现在 JSON 里，适合 PATCH 这类局部更新接口。这个参数在 0.3x 的较新版本中才出现，升级前先确认一下签名。

状态码有两个入口：装饰器上的 status_code 影响文档和成功响应的默认值；需要按分支返回不同状态码时，在函数签名里加 response: Response，直接改它的 status_code。创建资源用 201，删除成功且无内容用 204（此时不能有响应体），不要一律 200 了事。

从函数依赖到嵌套

几个容易踩的坑

依赖里做重活是最常见的性能问题。依赖在每个请求都会执行，把一次全表统计、一次远程调用塞进去，接口耗时就会翻倍；依赖应当只做「解析与准备」，真正的业务放到视图或服务层。

yield 依赖忘了 try/finally，连接池很快就会被耗光，这种泄漏在低并发下几乎看不出来。同步阻塞函数放进 async def 路由同样是隐雷：一次慢查询就会卡住事件循环，同一进程的所有请求一起变慢，要么改成 def 交给线程池，要么把阻塞调用换成异步驱动。

响应模型泄露敏感字段多半是图省事直接返回了输入模型或 ORM 对象，response_model 能过滤字段，但前提是你真的定义了输出模型。最后是版本混用：本文的 Config、@validator、constr 都是 0.3x 的写法，看到模型配置不写在内部类 Config 里、校验函数不用 @validator 的示例，先确认它对应的 Pydantic 版本，否则会得到一堆看不懂的报错。

小结

FastAPI 的核心是把类型注解当成唯一的契约：参数注解负责入参校验，Pydantic 模型负责请求体与输出结构，response_model 负责裁剪响应，Depends 负责把鉴权、分页、数据库会话这些横切逻辑抽出来复用。用好它的关键不在记住多少 API，而在守住几条边界：校验放在声明里，副作用放在依赖的清理段里，敏感字段靠输出模型挡住，阻塞调用不要混进 async def。版本上要保持克制，0.3x 时代接口仍在变，照抄示例前先对一遍签名，把测试写扎实，升级才不会变成一次冒险。
