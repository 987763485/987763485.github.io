Go 并发模式：worker pool

本文属于《Go 语言与工程》第 40/78 篇
上一篇系列目录下一篇

一个 HTTP 接口为每条记录开一个 goroutine，平时跑得好好的，流量翻三倍后进程内存陡增、下游数据库连接被打满，重启只能暂时缓解。这类问题很少是 goroutine 写错了，而是并发度没有上限。本文围绕 worker pool 这一模式，从固定 worker 的骨架讲起，依次讨论关闭顺序、context 取消、背压、panic 隔离、优雅退出、结果归位与指标，最后给出一个可运行的 HTTP 服务示例。读者应熟悉 goroutine、channel 与 sync 的基本用法；channel 的底层结构不在本文范围内。

为什么需要 worker pool

先复盘一个很常见的场景。某同步接口从队列里取出一批待处理记录，对每条记录启动一个 goroutine 去调用外部服务，然后等待全部完成。单机 QPS 只有几十时，这个写法简单直接，延迟也低。活动开始后流量涨了三倍，进程的 RSS 从 300 MB 涨到 2 GB，数据库连接池报出大量获取连接超时，外部服务也开始返回 429。把并发改成一个固定数字之后，同样的流量下内存回到 400 MB，错误率反而下降了。

原因并不复杂。goroutine 很轻，但不是免费。Go 1.12 中每个新建 goroutine 的初始栈是 2 KB，随着调用深度增加还会扩容，此外还有调度器维护的运行队列、GC 需要扫描的栈对象。十万个 goroutine 意味着至少两百 MB 的栈内存，加上每个 goroutine 持有的请求对象、缓冲区，实际占用往往翻几倍。更关键的是，这些 goroutine 并没有在干活，它们大多阻塞在等连接、等响应上，却依然占据内存，并让 GC 的标记阶段扫描更多对象。

第二个原因是下游的承受能力。服务自己的并发度可以随便调，数据库连接池通常只有几十个连接，第三方接口的配额往往按每秒请求数计算。上游放开 goroutine，等于把压力原样透传给下游，最后大家一起超时。worker pool 把并发度收拢成一个显式的常量，让服务主动适配下游，而不是等下游拒绝。

第三个原因是背压。无限制地创建 goroutine 时，任务进入系统没有任何阻力，队列在内存里无限增长，故障表现为内存耗尽这种最难看的形式。有了固定数量的 worker 和一条容量有限的队列，任务提交端会变慢或被拒绝，压力得以及时反馈给调用方，系统在过载时仍然可控。

所以 worker pool 解决的从来不是“如何并发”，而是“并发多少、排队多久、满了怎么办”。它把这三个问题从隐式的运行时行为变成代码里可以阅读、可以配置、可以观测的策略。

固定 worker 的基本骨架

worker pool 的结构可以用一句话概括：一条任务 channel，若干个长期存活的 worker 循环取任务，一条结果 channel，外加一个负责收尾的 WaitGroup。任务从左侧流入，worker 是固定数量的消费者，结果从右侧流出。

    J --> W1[worker 1]
    J --> W2[worker 2]
    J --> W3[worker N]
    W1 --> R[(results channel)]
    W2 --> R
    W3 --> R
    R --> C[收集者]

这段代码不长，却包含了三个必须讲清楚的所有权约定。

第一，jobs 由生产者关闭，worker 永远不关闭它。channel 的关闭语义是“不会再有新值”，只有掌握“还有没有新任务”这一信息的一方才有资格关闭。在这个例子里，任务是固定的切片，生产者发完就知道结束了，所以由它关闭。worker 只使用 range jobs，range 在 channel 关闭且缓冲取空后自然退出，不需要额外的退出标志。

第二，results 不能由任何一个 worker 关闭。多个 worker 并发写同一条 channel，谁都不知道别人是否还在发送，任何一方关闭都会让其他 worker 的发送 panic。正确的做法是另起一个 goroutine，用 wg.Wait() 等到所有 worker 退出，再关闭 results。这个“等待组加关闭者”的组合是 Go 并发代码里最常见的收尾结构，值得背下来。

第三，收集者必须在 worker 运行期间持续读取 results。上例中主 goroutine 在启动完生产者和关闭者之后立刻进入 for r := range results，读取是并发的。如果把这段读取挪到 wg.Wait() 之后，就会死锁：worker 发结果时无人接收而阻塞，worker 不退出，wg 永远不归零。

另外，wg.Add 必须在启动 worker 之前完成，不能放进 goroutine 内部。计数如果先启动后增加，主流程可能在计数尚未加一时就调用 Wait 并立即返回，收尾逻辑提前关闭 results，随后 worker 发送就会 panic。这个竞态在单元测试里未必出现，压测时才暴露。记住一条规则：Add 属于启动方，Done 属于退出方。

还有一个容易忽略的细节：关闭 jobs 之后，缓冲里剩下的任务仍然会被 worker 取完。关闭不等于丢弃，它只是拒绝新的发送。理解这一点，后面的优雅关闭才能建立在正确的预期上。

这个骨架适合“一批固定任务、跑完就结束”的场景。真实服务里的池通常长期存活，任务从 HTTP 请求或消息队列不断进来，还会遇到取消、超时和停机，这就需要把结构改造成一个带状态的对象。

用 context 控制生命周期

长期存活的池有两层生命周期，必须分开处理。第一层是池本身，从启动到停机，对应一个由 context.WithCancel 创建的池级 context；第二层是单个任务，由提交方创建，带着请求的截止时间，请求被取消或超时后，任务应该尽快放弃。把这两层混成一个 context，是很多实现出问题的起点：要么停池时把正在写回的结果一起丢掉，要么某个请求取消导致整个池退出。

最后是停池的顺序。直接 cancel 池级 context 会让所有 worker 立刻返回，队列里没开始的任务和正在执行的任务都被抛下。更稳的做法是先停止接收新任务，让 worker 把队列排空，等一个宽限期，仍未完成才取消。这个顺序与下一节的关闭流程是同一件事，只是取消是最后的兜底手段。

背压：队列该有多长

jobs channel 有没有缓冲，决定了系统在过载时的行为，而不只是性能差异。无缓冲时，提交者必须等到某个 worker 空闲才能把任务交出去，提交本身就成了限流器；有缓冲时，提交可以先进队列，短时间的突发被吸收，但队列也会掩盖“处理不过来”的事实，直到队列堆满、内存上涨。

形态 提交行为 过载表现 适用场景
无缓冲 必须等到空闲 worker 提交方立即变慢，背压最强 任务耗时长、队列无意义
有缓冲 队列未满时立即返回 先堆积，满后阻塞或拒绝 允许短突发的在线服务
有缓冲加拒绝 满时立刻返回错误 快速失败，保护自身与下游 对外接口、有 SLA 要求

缓冲长度的直觉来自排队论：队列只能吸收突发，不能提高吞吐。如果平均处理速度已经低于到达速度，队列再长也只是把崩溃时间推后。工程上常见的做法是把队列长度设成“几秒钟的流量”，例如 worker 数为 16、单任务平均 100 ms，每秒处理约 160 个，队列取 320 到 640，相当于给两到四秒的抖动留余量。这个数字最终要靠压测确认，而不是拍脑袋。

panic 隔离：别让一个任务打挂整个池

goroutine 里的 panic 不会被别的 goroutine 捕获。只要没有在当前 goroutine 的 defer 里 recover，整个进程就会退出。对一个池来说，这意味着某个任务解析了一段脏数据、做了越界切片，就可能让整台机器上的所有请求一起消失。更隐蔽的情况是 worker 数量为 8，其中一个 worker 因 panic 退出，池的吞吐悄悄降到七分之一，监控上只看到延迟上升，没有任何报错。所以池必须为每个任务建立隔离带。

有几点必须说清楚。第一，panic 值不一定是 error，可能是字符串、整数，甚至是 nil，所以 PanicError 用 interface{} 保存原值，不要假设类型。第二，recover 之后 worker 必须继续循环，而不是 return，否则隔离带只保护了进程，没有保护池的容量。第三，不要把 recover 写在 worker 循环的最外层。那样虽然进程不会崩，但当前 worker 会退出，而且队列里的任务没人接手；只有在“任务函数之外的代码也可能 panic”时，才需要在更外层再兜一层，并且要补一个 worker 或者让池进入降级状态。

还有一条工程原则：panic 应该被上报，而不是被静默吞掉。把 panic 计数接入指标，配置告警，定期归零排查。如果一段代码经常 panic，正确的修复是改代码，而不是靠 recover 维持运行。recover 的定位是隔离故障、保住进程，不是让 bug 消失。

优雅关闭：先停入口，再排空，最后兜底

优雅关闭要解决三个问题：不再接收新任务、把已经接收的任务做完、在限定时间内没做完就强制退出。听起来简单，落地时最容易踩的坑是“向已关闭的 channel 发送”。只要还有提交者在并发发送，关闭 jobs 就有 panic 风险，而这正是长期存活的池与固定任务批处理最大的区别。

解决办法是收拢发送权：不让业务代码直接写 jobs，而是写一条 submit channel，由一个常驻的调度 goroutine 统一转发，并由它独占 jobs 的关闭权。这样 jobs 只有一个发送者，关闭时机完全可控。为突出关闭逻辑，下面的结构省略了 context、指标等字段。

dispatch 退出时会关闭 jobs，worker 的 range 取完剩余任务后自然结束。关闭流程因此变成一条单向链路：关闭 quit，调度器停止转发并关闭 jobs，worker 排空队列后退出，WaitGroup 归零。没有任何一方需要在不确定的时机关闭 channel。

结果收集与顺序

多个 worker 并行执行，结果到达的顺序取决于任务耗时、调度和网络抖动，与提交顺序没有关系。如果业务需要按原顺序返回，只能在结果里带上任务 ID，收集完成后再归位，而不能指望“先提交的先回来”。这一点在批量查询、导出和聚合场景里尤其重要，很多偶发的错位问题都源于此。

收集结果有两种结构。第一种是共享的 results channel，所有 worker 往同一条 channel 写，由一个收集者统一读取。它适合批处理，也方便集中统计。第二种是每个任务自带一条 reply channel，调用方提交后直接在自己的 channel 上等结果。它把“谁关心这个结果”表达得更清楚，天然支持每个请求独立超时，缺点是没有统一的汇聚点，指标要另外埋。

可观测性：把池的内部状态暴露出来

池出了问题时，最常见的现象是“变慢了”，但慢在哪一段并不清楚。是任务在队列里排太久，还是执行本身变慢，还是下游超时导致 worker 被长期占用？如果只有总耗时，这三种情况看起来一模一样。因此一个可用的池至少要暴露四类指标：在途任务数、队列长度、任务耗时分布、失败计数。

标准库的 expvar 是最省事的起点，它把变量注册到 /debug/vars，返回 JSON，不需要引入任何依赖。

expvar.Func 在每次抓取时调用，所以队列长度是实时值；计数用 expvar.Int 的 Add，内部已经做了同步。在途数要在任务开始前加一、结束时减一，最好用 defer 保证 panic 路径也能减掉。耗时直方图用 expvar.Map 手工分桶，桶边界按业务 SLA 设定，别照抄示例。

如果要接入 Prometheus，client_golang 在 2019 年的稳定 API 已经够用：

kind 标签只取有限的几个值，例如 ok、error、panic、timeout。千万不要把任务 ID、URL 或用户 ID 作为标签，那会让时间序列数量爆炸，Prometheus 的内存会先于业务崩溃。

比耗时更有价值的是把等待时间和执行时间分开。从提交到 worker 开始执行之间的间隔，反映队列积压程度；执行时间反映任务本身和下游的健康度。只统计后者，会在队列已经排了几十秒时仍然显示“平均耗时 20 ms”，完全误导排查方向。实现上在 Job 里记录一个入队时间戳，worker 取出时先算等待时间，再单独打点。

最后是日志。每个失败任务至少记录任务 ID、重试次数、耗时和错误原因；panic 额外记录堆栈。日志字段和指标标签保持同一套命名，排查时才能在两个系统之间对上号。

常见的坑

前面各节已经零散提到一些问题，这里集中列出最容易复发的几类，每一条都对应真实的排查现场。

goroutine 泄漏。池本身的 worker 是常驻的，不算泄漏；泄漏通常发生在“临时 goroutine”上，例如在 handler 里另起一个 goroutine 提交任务，却在客户端断开后直接返回。这个 goroutine 可能永远卡在 jobs <- 或 reply 的接收上。池化之后，提交路径必须带 context，所有等待都要用 select 包住，确保调用方放弃时 goroutine 能退出。排查时访问 /debug/pprof/goroutine?debug=1，如果大量 goroutine 停在 chan send，基本就是这个原因。

重复关闭。关闭 jobs 的代码同时出现在生产者、Close 和某个 worker 里，单独测试都正常，一并发就 panic。channel 的关闭权必须唯一，配合 sync.Once 保证 Close 幂等。不要用“先判断是否关闭再关闭”的写法，判断和关闭之间仍有竞态。

忘记 cancel 或过早 cancel。context.WithTimeout 创建的定时器要靠 cancel 释放，循环里创建而不 cancel，几分钟就能积累上万个定时器。反过来，把 defer cancel() 写在异步提交的函数里，会让任务刚进队列就被取消。判断标准很简单：cancel 的作用域必须覆盖任务真正结束的时刻。

无缓冲 results 导致卡死。这是新手最常遇到的死锁，症状是程序没有任何输出、CPU 占用为零、pprof 显示所有 goroutine 都在 chan 操作上。共享 results 时，要么并发收集，要么给足缓冲，没有第三种办法。

闭包捕获循环变量。Go 1.12 的 for range 复用同一个迭代变量，启动 goroutine 时如果直接引用它，所有 goroutine 看到的都是最后一个值：

这个坑在 worker 内部同样存在。如果 worker 从 jobs 取出任务后又启动子 goroutine 处理，而子 goroutine 引用的是 range 变量，就会出现任务串号。传参或重新声明都能解决，关键是意识到变量是复用的。

recover 放错层级。只在 worker 循环外 recover，panic 后 worker 直接退出，池的并发度悄悄下降；只在任务函数里 recover 却不记录，故障被彻底吞掉。正确的组合是任务级 recover 加指标与日志，循环外再留一层兜底并触发告警。

结果 channel 由 worker 关闭。这是重复关闭的变体，多个 worker 都认为自己干完了，最后一个关闭时其他 worker 可能还在发送。关闭者只能有一个，而且必须是确认所有发送者都退出之后的那一方。

一个完整的 HTTP 服务示例

下面把前面的结构拼成一个可运行的服务：HTTP 接口接收目标 URL，把抓取任务交给池，池返回响应片段和耗时。为了控制篇幅，指标埋点从略，抓取逻辑做了简化。

这个例子有三个值得注意的设计。第一，Reply 的容量固定为 1，调用方超时离开后，worker 仍然能把结果写完并继续处理下一个任务；如果容量为 0，worker 就会永久卡在这条发送上，等于池少了一个 worker。第二，Submit 同时监听提交通道、池关闭和请求 context，任何一方先结束都能让调用方及时返回。第三，任务侧有 5 秒的 HTTP 超时，请求侧是 3 秒，外层比内层短，用户不会等到下游超时之后才收到错误。实际项目中一般反过来：内层下游超时略短于外层请求超时，让错误在内部先暴露，便于记录具体原因。

压测时不要只测吞吐。先用固定并发数跑闭合压测，观察队列长度和任务等待时间；再逐步提高并发，找到“吞吐不再上升、延迟开始陡增”的拐点，这个拐点对应的并发数才有参考价值。go test -bench 适合测池本身的开销，注意加上 -race 检查数据竞争；HTTP 层可以用 vegeta 之类的工具做开环压测，避免客户端自己成为瓶颈。worker 数量的初始值可以从 CPU 核数开始：CPU 密集型取核数或核数加一，IO 密集型取核数的几倍，最终都以压测结果为准。

小结

worker pool 的价值不在于“用 channel 写并发”，而在于给并发度一个明确的上限，并把过载时的行为写进代码。固定 worker 的骨架很简单，难的是所有权：jobs 由唯一的生产者关闭，results 由等待所有 worker 退出后的收尾者关闭；任务级 context 与池级 context 分开管理，取消是建议而非强杀；队列长度只能吸收突发，满时的拒绝策略才是系统的安全阀。再往上，panic 隔离保证单个任务不拖垮进程，两阶段关闭保证停机时不丢在途任务，指标把等待时间和执行时间分开暴露，这些细节决定了一个池能否在线上长期稳定运行。把这些约定固化到团队的基础库里，比在每个业务里重写一遍要可靠得多。
