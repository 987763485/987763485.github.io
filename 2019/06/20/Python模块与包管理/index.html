Python 模块与包管理

本文属于《Python 学习路线》第 9/29 篇
上一篇系列目录下一篇

写过几个脚本之后，迟早会遇到这样的问题：两个文件互相导入时报错，或者明明装好了包却提示找不到模块。它们大多不是语法错误，而是对导入机制缺少整体认识。本文从模块与包的定义出发，串起 import 的执行过程、搜索路径、包初始化、相对导入与循环导入，并给出可以直接套用的排查思路。

从模块到包：代码的组织单位

一个 .py 文件就是一个模块

在 Python 里，模块的粒度很小：任何一个 .py 文件都是一个模块，文件名去掉后缀就是模块名。例如项目里有一个 utils.py，同目录下的其他脚本就可以用 import utils 加载它。模块是命名空间的最小单位，函数、类和变量都挂在这个命名空间下，因此不同模块可以使用同名函数，只要导入时区分清楚。

模块名区分大小写，也必须是合法的标识符。my-module.py 无法用常规 import 语句导入，因为减号会被解析成运算符；实践中应使用小写字母加下划线。

包是带 init.py 的目录

当代码多到一个文件放不下时，就需要目录来分组。在 Python 3.3 之前，一个目录必须包含 init.py 才会被当作包；这个文件可以是空的，但它的存在本身就是声明。这样的目录称为常规包（regular package）。例如：

包被导入时，Python 会执行它的 init.py，然后把这个包对象放进 sys.modules；子包和子模块不会自动全部加载，除非 init.py 里显式导入，或者调用方逐个导入。

包内模块的导入路径

理解导入路径的关键，是分清模块的完整名字和文件位置。完整名字从顶层包开始，例如 myapp.services.billing；能否找到它，取决于 myapp 的父目录是否在 sys.path 上。如果直接进入 myapp 目录再启动脚本，顶层包的名字就不存在了，导入自然失败。

import 的几种写法与缓存机制

四种常用形式

最常见的写法是 import x。它加载模块 x，并在当前命名空间绑定一个同名变量，之后通过 x.func() 访问成员，来源一目了然。

第二种是 from x import y，只把 y 绑定到当前命名空间。它写起来短，但大量使用会让代码难以追溯来源，最好只对明确、少量的成员使用。

第三种是 import x as y，给模块起别名。别名常用于名字很长的模块，或为了兼容不同实现。别名一旦确定，就应在整个项目里保持一致。

第四种是 from . import sibling，用在包内部，表示从当前包导入同级模块。点号数量代表向上跳几层：一个点表示当前包，两个点表示上一级包。它只能出现在包内的模块里，单独运行这个文件时通常会报错。

模块只执行一次

无论 import 语句写了多少遍，同一个模块在一次解释器进程里只会被执行一次。第一次导入时，Python 先创建模块对象，把它放进 sys.modules 字典，然后执行模块顶层的代码；后续的 import 直接复用字典里的对象，不再重复执行。

这带来两个后果。第一，模块顶层不适合放有副作用的操作，比如读写文件、连接数据库；测试时经常要“重新加载”模块来复位状态，本身就说明这些事不该放在顶层。第二，模块级变量天然是单例，适合放配置和共享缓存，但它们会一直存在，修改时要考虑对其他调用方的影响。

模块搜索路径：sys.path 的组成与顺序

路径由四部分拼成

写 import requests 时，Python 并不知道它在哪，只会按 sys.path 的顺序逐个目录查找。这个列表在解释器启动时构造，通常由四部分组成：

  1. 脚本所在目录。直接运行 python script.py 时，script.py 所在的目录会被放在列表最前面；在交互式解释器里则是对应的当前目录或空字符串。
  2. PYTHONPATH 环境变量。它允许用户追加额外的目录，常用于本地开发时让多个项目互相引用。
  3. 标准库目录。Python 自带的模块，例如 json、os、collections，都在这里。
  4. site-packages。第三方包经 pip 安装后的落点，位于当前虚拟环境的目录下；不激活虚拟环境就运行脚本，用的就是系统解释器和系统包。

顺序带来的覆盖风险

由于脚本目录排在标准库和 site-packages 之前，只要项目里出现一个与标准库同名的文件，它就会优先被导入。例如在项目根目录放一个 json.py，代码里的 import json 拿到的就是这个本地文件，而不是标准库；如果它内部又恰好 import json，就会导入自己，形成自我循环。同理，random.py、logging.py、email.py 都是高风险名字。这类问题往往不报“找不到模块”，而是报某个属性不存在，排查起来很绕。

另一个风险是 PYTHONPATH 的滥用。它把本机目录带进所有项目的导入环境，同名包会由先出现者静默获胜。团队协作时应尽量少用它，把代码做成包并用 pip install -e . 装进虚拟环境，让依赖关系显式化。

python -m 与直接运行脚本的差异

python script.py 会把脚本目录放在 sys.path[0]；python -m package.module 则先把当前工作目录放进 sys.path，再按模块名查找，找到后以模块身份执行。区别在包的场景里最明显。

假设 myapp 下有 main.py，执行 python -m myapp 时，Python 把 myapp 当成包导入，相对导入可以正常工作。而执行 python myapp/main.py 时，sys.path[0] 变成 myapp 目录，顶层包 myapp 不再可见，文件里的 from . import config 会直接失败。

all 控制 from myapp.models import * 时导出哪些名字。没有定义时，星号导入会导出所有不以单下划线开头的名字；定义之后只导出列表里的名字。它只影响星号导入，不影响显式导入。生产代码应尽量避免星号导入，它让名字来源模糊，也容易覆盖已有变量。

不要在 init 里做重活

既然导入包就会执行 init.py，把耗时操作放在这里，代价会被所有导入方承担。比如读取配置、连接数据库、扫描插件目录，都会让 import myapp 变慢，甚至让测试直接失败。更隐蔽的问题是循环导入：init.py 导入子模块，子模块又回头导入包里的名字，很容易拿到尚未初始化完成的对象。

稳妥的做法是让 init.py 保持轻薄，只做导入和少量常量定义；连接、扫描等动作封装成 init() 或工厂函数，由调用方在合适的时机触发。这样导入廉价且可预测，测试也更容易隔离。

隐式命名空间包

PEP 420 在 Python 3.3 引入了隐式命名空间包：一个没有 init.py 的目录，也可以作为包的一部分被导入。典型用途是把同一命名空间拆到多个发行包中，例如 mycompany.tools 和 mycompany.plugins 由两个 wheel 提供，安装后在 site-packages 里合并。

命名空间包适合大型组织做插件式拆分，但也带来不确定性：目录里少写 init.py，导入可能“碰巧成功”，掩盖配置错误。普通项目仍建议使用常规包，显式写上空 init.py。

绝对导入与相对导入

绝对导入从顶层包写起，例如 from myapp.models import User；相对导入用点号表示当前位置，例如 from .user import User 或 from ..services import billing。一个点代表当前包，两个点代表父包。关键是：相对导入解析的是当前模块所属的包，而不是文件系统里碰巧相邻的目录。

相对导入只在模块有包上下文时才有意义。用 python myapp/models/user.py 直接运行，解释器把文件当作顶层脚本，package 为 None，点号没有参照物，于是抛出 ImportError: attempted relative import with no known parent package。正确做法是从项目根目录用 python -m myapp.models.user 启动，或把入口收敛到包外的启动脚本。

PEP 8 建议使用绝对导入：来源清晰，移动文件时只需改一处。相对导入更适合包内部紧密耦合、需要表达“同级”关系的模块。两者可以混用，但同一项目里最好有统一约定，不要让读者在点号里数层级。

循环导入：成因与三种解法

当 a.py 导入 b，而 b 又导入 a，就形成循环导入。Python 不提前检测依赖图，只是按顺序执行：导入 a 时先创建其模块对象放进 sys.modules，执行到 import b；b 又 import a，此时字典里已有 a，于是直接返回那个只执行了一半的对象。如果 b 在导入阶段就访问 a 中尚未定义的函数或类，就会得到 AttributeError 或 ImportError。

第一种是延迟导入：把 import 从模块顶层移到函数内部，调用时才执行。这能快速打破循环，代价是依赖关系被藏了起来。第二种是重构依赖：把双方共同需要的类型或工具抽到第三个模块，让 a 和 b 都依赖它。这是最干净的解法，但需要梳理边界。第三种是条件导入：只为类型标注服务的模块，放进 if TYPE_CHECKING: 分支，运行时并不导入；配合 from future import annotations，标注不会在导入时求值。

三种办法都只是把问题挪了个位置：延迟导入把错误推迟到请求处理时，重构依赖需要改动设计，局部导入让调用链更难读。真正要问的是：这两个模块是否承担了过多职责？多数循环导入背后都是一个本可拆开的巨型工具模块，把公共部分下沉，往往比打补丁更有效。

包的对外接口需要一点自律。all 明确星号导入的范围；单下划线开头的名字表示内部使用，解释器不会阻止访问，但这是给读者的契约。版本号通常放在 init.py 里，写作 version = “0.3.1”，方便运行时排查；它应与安装包元数据里的版本保持一致，否则会出现装的是新版本、代码却报告旧版本的情况。打包成 sdist 或 wheel、上传私有源属于分发环节，本文不展开。

常见坑与排查清单

遇到导入问题，可以按下面的顺序检查：

  1. 模块名是否撞车。项目里有没有 json.py、random.py、types.py 这类文件？它们会遮蔽标准库，表现为属性缺失而不是找不到模块。
  2. 目录是否缺 init.py。不用命名空间包的话，补一个空文件最省事。
  3. 启动方式是否正确。包内带相对导入的模块，应从项目根目录用 python -m 启动，而不是直接 python path/to/file.py。
  4. sys.path 是否被污染。打印列表，确认第一项是否预期目录，并检查 PYTHONPATH 和虚拟环境。
  5. 是否卡在循环导入。看报错里有没有“partially initialized module”，沿着导入链找出互相引用的两个模块。

同一份代码被导入两次、模块级状态出现两份，通常是因为一次以包内模块导入、一次以脚本直接运行，两个不同的键指向同一个文件。统一入口方式即可避免。

小结

模块是 .py 文件，常规包是带 init.py 的目录，导入的本质是按 sys.path 查找、在 sys.modules 里缓存并执行一次顶层代码。把 init.py 保持轻薄，优先使用绝对导入，用 python -m 启动包内入口，能避开大部分导入问题。遇到循环导入时，先想依赖边界，再考虑延迟导入这类技术手段。
