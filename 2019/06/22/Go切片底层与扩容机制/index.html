Go 切片底层与扩容机制

本文属于《Go 语言与工程》第 39/78 篇
上一篇系列目录下一篇

在 Go 的日常开发里，切片几乎是最常用的数据结构，但“看起来会用”和“知道它为什么这样表现”之间隔着一段距离。本文从运行时视角拆开切片的三个字段，解释 append 何时原地写入、何时搬移数据，以及共享底层数组带来的种种现象。读完之后，你应该能判断一段切片代码会不会产生意外的别名修改，也能写出更省内存、更少拷贝的写法。数组与切片的语法细节不再赘述，映射的底层结构也不在本文范围内。

数组是值，切片是描述符

先明确一个前提：数组和切片在类型系统里是两种完全不同的东西。数组的长度是类型的一部分，[3]int 与 [4]int 是两个不兼容的类型，赋值时逐元素复制，函数传参也是一次完整拷贝。数组变量本身就代表那块连续内存，长度在编译期就已确定，运行时没有任何“长度字段”可供修改。

切片则不是数据本身，而是一个三字段的描述符：一个指向底层数组某元素的指针、当前长度 len、可用容量 cap。切片变量只占这几个字段的空间，真正的元素存放在它指向的数组里。因此把切片赋给另一个变量、或者传进函数，复制的是描述符，不是元素；两个描述符可以指向同一块内存，这就是后面所有共享现象的根源。

用值语义和引用语义来概括并不精确，但足够帮助记忆：数组赋值是“复制整栋房子”，切片赋值是“复制一张写着地址的纸条”。纸条可以有很多张，房子只有一栋，谁拿着纸条都能改动房子里的东西。数组在元素可比较时可以用 == 整体比较，切片则只能与 nil 比较，这也从侧面说明二者在类型系统中的位置不同。

三种创建方式与 len、cap 的计算

最常见的创建方式是字面量。[]int{1, 2, 3} 会先分配一个长度恰好为 3 的数组，再让切片指向它，所以长度和容量都是 3。第二种是 make：make([]int, 3) 只给长度，容量默认等于长度；make([]int, 0, 8) 则明确区分了两者，长度为 0、容量为 8，表示“先占好能放 8 个元素的位置，但目前一个元素都没有”。第三种是从已有数组或切片上切出一段。

切片的规则是左闭右开：s[low:high] 包含下标 low 到 high-1。新切片的长度等于 high - low，容量等于原容量减去 low。这里最容易看错的是容量：它从 low 一直算到原底层数组的末尾，而不是算到 high。省略边界时，low 默认为 0，high 默认为原长度。

共享底层数组：省拷贝，也埋隐患

从数组或另一个切片切出的子切片，不会复制任何元素，新旧两个切片指向同一块内存。修改子切片的元素，原切片能看到；反过来也一样。

还有一种常见操作是反复丢弃头部：s = s[1:]。它不复制任何元素，只是把 Data 前移一个位置，并把 Len 和 Cap 各减一。解析缓冲区时这种写法很自然，但底层数组一直完整保留，只要还有切片指向它，被丢弃的头部就不会被回收；如果同时另存了原始切片，内存更是一点也省不下来。

append 何时原地写，何时搬家

append 的判断逻辑可以概括为一句话：先看容量够不够。够，就在长度对应的位置写入，返回一个长度增加、容量不变的新切片头，底层数组仍是原来那块；不够，就分配一块更大的数组，把旧元素复制过去，再写入新元素，返回的切片指向新数组。

扩容倍数在 Go 1.12 的运行时里大致是这样的：如果本次需要的容量超过旧容量的两倍，就直接采用需要的容量；否则，旧长度小于 1024 时按两倍扩展，达到 1024 之后每次增加约四分之一，循环累加直到够用。算出目标容量后，运行时还会按内存分配器的尺寸档向上取整，所以实际的 cap 常常比算出来的值略大。不必记住具体数字，记住“小切片翻倍、大切片按比例增长”即可。

元素类型的大小也会影响最终结果。运行时先算出所需字节数，向分配器的尺寸档取整，再除以单个元素的大小得到容量，所以元素越小，取整带来的富余越明显；结构体较大时，容量往往更接近计算值。这也是同样追加一批元素，[]byte 与 []int64 的扩容次数可能不同的原因。

    C --> D[返回 len 变大 cap 不变的切片头]

指针变化带来两个直接后果。第一，append 的返回值必须重新接收，写成 append(s, x) 而不赋值，编译可以通过，但结果被丢弃，什么也不会发生。第二，扩容之后，旧切片仍然指向旧数组，内容停在扩容前的状态；如果你把旧切片另存了一份，它不会跟着“升级”。这也是并发场景下共享切片格外危险的原因：一个 goroutine 在扩容，另一个还拿着旧数组。

copy：长度取小，绝不扩容

copy(dst, src) 返回实际复制的元素个数，这个数量等于 len(dst) 与 len(src) 中较小的那个。它只按长度计算，完全不看 dst 的容量，也不会替 dst 扩容；目标有多长，最多就写多少个元素。

切片作为函数参数

把切片传进函数时，复制的是切片头：Data、Len、Cap 三个字段各复制一份，底层数组不复制。因此函数内通过下标修改元素，调用方一定看得见；但函数内让切片“变长”，调用方不一定看得见。

addOne 执行时容量足够，1 确实被写进了底层数组的第二个位置，但函数只修改了副本的 Len，调用方的 Len 仍是 1，所以看不到它。如果调用方写 s[:2]，又能把那个 1 读出来：数据在，长度不在。这种“写进去了但看不见”的状态最迷惑人。要让长度变化传出函数，只能返回新切片并让调用方接收，这也是标准库里许多函数返回 []T 的原因。

其余几个坑更常见，几乎每个 Go 新手都会踩一遍：

  • 丢弃 append 的返回值。append 可能返回指向新数组的切片，不接收就等于什么都没做。
  • 在循环里复用变量并保存子切片。若每轮都对同一个切片重新切片再存入结果集，所有结果可能共享同一块内存，最终看到相同的值；需要独立数据时用 copy 或重新 make。
  • 混淆 len 与 cap。索引只允许小于 len，cap 再大，s[len] 依然越界 panic；想使用预留空间必须先重新切片。
  • 把 nil 切片与空切片混为一谈。var a []int 是 nil，b := []int{} 不是 nil，两者 len 和 cap 都是 0；JSON 序列化时前者是 null，后者是 []，判断有无数据应该看 len。nil 切片可以直接 append，运行时把它当作长度和容量都为 0 的切片，第一次追加才分配内存。
  • 切片表达式的上界超过 cap 会 panic，而不是自动扩容；append 才是唯一会扩容的操作。

小结

切片不是数组的别名，而是由 Data、Len、Cap 组成的描述符，赋值和传参复制的都只是这个描述符。len 决定可访问范围，cap 决定 append 能否原地写入，二者之差是最容易误判的地方。容量足够时 append 会改写共享数组，容量不足时才分配新数组并复制，所以返回值必须重新接收。三索引切片可以限制容量、阻断越界写入，但不能切断对原数组的引用；需要长期持有大缓冲的一小段时，用 copy 摘出来。把这些规则记成“谁拥有这块内存、长度是多少、还能写多远”，大多数切片 bug 都能在写代码时避免。
