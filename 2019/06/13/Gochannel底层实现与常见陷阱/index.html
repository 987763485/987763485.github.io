Go channel 底层实现与常见陷阱

本文属于《Go 语言与工程》第 38/78 篇
上一篇系列目录下一篇

几乎每个 Go 程序都会用到 channel，但真正理解它的人并不多。本文从 runtime 中的 hchan 结构出发，沿着发送、接收、select 与 close 四条主线，把 channel 的运行时行为拆开来看，再落到工程中最常见的泄漏、死锁与关闭时机问题。它适合已经会写 go func() 与 chan、却在排查卡死或泄漏时缺少抓手的中级开发者。读完之后，你应当能对着一段 channel 代码说出它会在哪里阻塞、为什么会泄漏，以及该怎样改。

channel 在运行时是什么

以下讨论以 Go 1.12 的运行时源码为准。在语言层面，chan 是一个引用类型，make(chan T, n) 返回的值可以复制、可以传参。但在 runtime 眼里，它就是一个指向 hchan 结构体的指针。make 被编译器翻译成对 runtime.makechan 的调用，返回值被塞进一个 chan T 类型的变量里。理解这一点很重要：你手里的 channel 变量只是句柄，真正的状态全部在堆上的那个 hchan 里，多个 goroutine 通过同一个指针共享它。

hchan 的字段不多，但每一个都对应一条语义：

字段 类型 含义
qcount uint 缓冲区中当前的元素个数
dataqsiz uint 环形缓冲区的容量，即 cap(ch)
buf unsafe.Pointer 指向环形缓冲区首地址，无缓冲时为 nil
sendx uint 下一个写入位置的下标
recvx uint 下一个读取位置的下标
recvq waitq 因接收而阻塞的 goroutine 队列
sendq waitq 因发送而阻塞的 goroutine 队列
lock mutex 保护以上所有字段的互斥锁

除了这些，还有 elemsize、elemtype 记录元素大小与类型，供运行时的内存拷贝使用；closed 是一个 uint32 标志，关闭之后置 1。源码里在 lock 字段上方有一段注释，大意是：持有这把锁时不要改变其他 goroutine 的状态，尤其不要唤醒别人，否则可能与栈收缩互相等待。

makechan 在分配时还有一个优化：元素类型不含指针时，hchan 与缓冲区在同一块内存里一次分配；含指针时则分开分配，让 GC 能单独扫描缓冲区。

qcount 和 dataqsiz 是一对容易混淆的字段。前者是“现在有几个”，会随收发变化；后者是“最多能放几个”，make 之后不再改变。判断缓冲区满不满，看的是 qcount == dataqsiz；判断空不空，看的是 qcount == 0。sendx 与 recvx 只是游标，它们相等并不代表空或满，必须配合 qcount 才能确定状态。

无缓冲与有缓冲的差别，在结构体里就是 dataqsiz 是否为零。make(chan int) 得到的 dataqsiz 为 0，buf 是空指针，此时的 channel 没有“存放”能力，发送与接收必须当场配对：发送方把值直接交给接收方，或者把自己挂起等接收方出现。make(chan int, 4) 则多了一块可以放 4 个元素的缓冲区，发送方可以先把值放进缓冲区就返回，不必等接收方。换句话说，无缓冲 channel 传递的是“交接时刻”，有缓冲 channel 传递的是“队列位置”。

环形缓冲区如何转动

有缓冲 channel 的 buf 是一段连续内存，按 elemsize 切成 dataqsiz 个槽位。运行时的 chanbuf 用一句指针运算定位槽位：首地址加上下标乘以元素大小。所谓“环形”，并不是内存真的首尾相连，而是下标走到末尾后回到 0，让有限的槽位被反复使用。

发送时，运行时做四件事：把值拷贝到 sendx 指向的槽位；sendx 加一，若等于 dataqsiz 则归零；qcount 加一；解锁返回。接收是对称的：从 recvx 指向的槽位把值拷贝到目标变量；把该槽位清零；recvx 加一并在越界时归零；qcount 减一。清零这一步容易被忽略，它不是为了“讲卫生”，而是为了让槽位里不再持有指向堆对象的指针，避免已经出队的数据还被 GC 视为存活。

用容量为 4 的缓冲区走一遍，注意两个游标的相对位置：

操作 sendx recvx qcount 缓冲区内容
初始 0 0 0 空
发送 a 1 0 1 a
发送 b、c 3 0 3 a b c
发送 d 0 0 4 a b c d，已满
接收 0 1 3 b c d
接收 0 2 2 c d
发送 e 1 2 3 c d e

可以看到 sendx 在写满一圈之后回到了 0，而 recvx 紧跟在后面。缓冲区满时 qcount 等于 dataqsiz，此时发送方不能覆盖最老的元素，只能阻塞，进入 sendq 等待；缓冲区空时 qcount 为 0，接收方同样只能阻塞。这两个“只能”是有缓冲 channel 与“自带丢弃”的队列最本质的区别：channel 从不静默丢数据，它用阻塞把压力传回上游。

环形设计的好处是常数时间。如果每次出队都把后面的元素往前搬，容量为 n 的缓冲区在频繁收发下就会退化成 O(n) 的拷贝。环形结构只移动两个下标，代价与容量无关。代价是缓冲区的内容不再是一段“从头到尾都有意义”的序列，任何遍历都必须从 recvx 开始、绕回 0、走到 sendx 之前。这也是为什么运行时只暴露 len 与 cap 两个快照，而快照在并发下随时会过期。

sudog：一次等待的代表

当发送或接收无法立刻完成时，goroutine 不会原地自旋，那样会白白占着 CPU 和 P。运行时的做法是：为这次等待操作申请一个 sudog，把它挂到 channel 的等待队列上，然后调用 gopark 让当前 goroutine 睡去，把 P 让给别人。可以把 sudog 理解成“一张排队号”，它代表的不是 goroutine 本身，而是“某个 goroutine 想在这个 channel 上做一次发送或接收”这件事。

sudog 的关键字段有这些：g 指向等待的 goroutine；elem 指向数据要拷入或拷出的地址，通常指向该 goroutine 栈上的变量；c 记录它挂在哪个 channel 上；next 与 prev 把同一队列里的等待者串成双向链表；isSelect 标记这次等待是否来自 select；releasetime 记录开始阻塞的时间，供 block profiling 统计。channel 里的 sendq 与 recvq 各是一个 waitq，内部只保存 first 与 last 两个指针，入队和出队都是 O(1)。

gopark 做的是状态切换：把当前 goroutine 标成 waiting，解除它与 M 的绑定，然后进入调度循环。这里有一个容易忽略的配合：挂起之前 channel 的锁还握在手里，如果就这样睡过去，别的 goroutine 连队列都碰不到。所以 gopark 接受一个 commit 函数，在真正切换出去之前调用它，把 channel 的锁释放掉。发送路径传的是 chanparkcommit，接收路径也一样。这个设计保证了“检查队列”和“挂入队列”是一个原子动作，中间不会漏掉唤醒。

唤醒由 goready 完成：把目标 goroutine 的状态改成 runnable，放进某个 P 的运行队列，等调度器安排它上 CPU。要注意，被唤醒不等于立刻运行，中间可能隔了一段时间；但由于数据在唤醒之前就已经交接完毕，接收方晚一点跑也不影响正确性。这也解释了为什么 channel 的语义是“同步交接”而不是“唤醒即执行”。

四条发送路径

把 chansend 从头读到尾，会发现发送的去向可以归为四条，接收是它的镜像。先看发送。

flowchart TD
    A[chansend 入口] --> B{channel 为 nil}
    B -- 是 --> C[永久阻塞]
    B -- 否 --> D[加锁]
    D --> E{已关闭}
    E -- 是 --> F[panic]
    E -- 否 --> G{recvq 有等待者}
    G -- 有 --> H[直接拷贝给接收者并唤醒]
    G -- 无 --> I{缓冲区有空位}
    I -- 有 --> J[写入环形缓冲区并返回]
    I -- 无 --> K{是否允许阻塞}
    K -- 否 --> L[解锁并返回 false]
    K -- 是 --> M[挂入 sendq 并 gopark]
    M --> N[被唤醒后检查结果]

第一条是“有人等着收”。加锁之后先看 recvq，只要队列非空，就把值直接拷贝到那个接收者的 sudog.elem 指向的栈变量里，然后唤醒它。这条路径完全绕过缓冲区，只发生一次拷贝。有人会问：缓冲区里可能还有数据，直接交接会不会插队？不会。因为接收者只有在缓冲区为空时才会挂起，recvq 非空意味着缓冲区必然是空的，直接交接正好符合先进先出。

第二条是“缓冲区有空位”。把值写进 sendx 指向的槽位，推进游标与计数，解锁返回。发送方不需要挂起等待接收者，这是有缓冲 channel 在生产者快于消费者时的主要收益。

第三条是“缓冲区满了，或者根本没有缓冲区，而且没人在等”。此时当前 goroutine 构造 sudog，elem 指向要发送的变量，把它挂到 sendq 尾部，然后 gopark。等某个接收者到来，会在取走数据的同时把它唤醒。醒来之后它还要检查 sudog.success：如果 channel 在等待期间被关闭，这次发送要以 panic 收场。

第四条是“不允许阻塞”，典型来源是带 default 的 select。编译后调用的是非阻塞版本的发送：先做一次无锁的粗略检查，条件明显不满足就直接返回 false，连锁都不抢；条件可能满足才加锁确认。这也是 select 加 default 比“先 len 再发送”更可靠的原因，后者在并发下必然有竞态。

接收侧的顺序完全对称：先看 sendq，有等待的发送者就直接从它那里取；否则看 qcount，非零就从 recvx 处取；再否则挂起自己。这里有一个精巧的处理：当缓冲区已满且有发送者在等时，接收者先从队头取出一个元素，再把发送者的值填到队尾。由于队列是满的，队头与队尾恰好是同一个槽位，一次搬移就同时完成了“出队”和“让发送者入队”，并且保持了顺序。

select 是怎么选中的

select 看起来像语法糖，实际上是一段相当复杂的运行时逻辑。编译器会为每个 case 生成一个 scase，记录 channel 指针、操作类型（发送、接收还是 default）以及数据地址，再额外生成两个下标数组：pollorder 决定扫描顺序，lockorder 决定加锁顺序。当 select 只有一个发送或接收 case、再加一个 default 时，编译器会直接改写成 selectnbsend 或 selectnbrecv，根本不进 selectgo，这是常见的快路径。

先讲随机。selectgo 进入后第一件事是用 fastrandn 把 pollorder 洗成随机排列。这样做的目的不是好玩，而是防止饥饿：如果总按源码顺序扫描，排在前面的 case 在长期运行中会占尽便宜，后面的 case 永远轮不到。随机化之后，每个就绪的 case 被选中的概率相同，这是一种概率意义上的公平。注意它只保证“就绪者之间等概率”，并不保证“每个 case 最终都会被执行”，如果某个 case 长期不就绪，它依然可能一直落空。

再讲加锁。一个 select 可能同时涉及多个 channel，如果两个 goroutine 各自以相反的顺序锁住同一组 channel，就会死锁。运行时的对策是按 channel 的地址排序，得到 lockorder，然后严格按这个顺序依次加锁，解锁时再逆序释放。地址排序是任意的，但所有 goroutine 看到的顺序一致，环就不会形成。这个技巧在工程代码里同样适用：同时持有多把锁时，先约定一个全局顺序。

加完锁进入第一轮扫描，按 pollorder 逐个检查：接收 case 看 sendq 有没有等待者、qcount 是否大于零、channel 是否已关闭；发送 case 先看 channel 是否已关闭，再看 recvq 有没有等待者、缓冲区是否有空位。只要命中一个，就执行它并返回。这里没有“先来后到”，只有随机顺序，所以同一个 goroutine 面对多个同时就绪的 case 时，选哪个是不确定的。

如果第一轮什么都没找到，就轮到 default。default 不是“优先执行”，而是“实在没得选才执行”。运行时在扫描过程中只是记下它的下标，扫描结束后仍无就绪 case，才走 default 并立刻返回。所以带 default 的 select 不会阻塞，只是没得选时走默认分支。

没有 default 且没有任何 case 就绪时，进入第二轮：为每个 case 申请一个 sudog，接收 case 挂到对应 channel 的 recvq，发送 case 挂到 sendq，然后 gopark。此时这个 goroutine 同时出现在多个等待队列里，任何一个 channel 先就绪，都能把它唤醒。醒来之后它要重新加锁，扫描所有 case 找出成功的那一个，再把其余 channel 上的自己摘掉。这一步“去注册”不能省，否则队列里会留下指向已结束等待的 sudog，后续的发送者可能对着一个空壳做交接。

关于惊群，需要区分两种情形。一次普通发送只会从 recvq 里摘下第一个等待者，不会把所有人都唤醒，所以多个接收者等同一个 channel 并不会因为一次发送而集体苏醒。而 close 会唤醒 recvq 上的全部等待者，因为关闭之后每个接收者都应该拿到零值，这是语义要求，不是浪费。真正需要警惕的是另一种模式：大量 goroutine 各自 select 同一个“完成信号”，信号一到全体醒来去抢同一把锁或同一个下游资源，这时应该改用只唤醒一个的队列，或者用 sync.Once 把后续动作收敛成一次。

close 的四条红线

close 是 channel 上唯一会改变“生命周期”的操作，语义可以概括为四条：关闭后继续发送会 panic；关闭后接收不再阻塞，缓冲读完后返回零值与 ok 为 false；重复关闭会 panic；关闭 nil channel 也会 panic。这些不是约定，而是运行时的硬性行为，只能靠 recover 兜底。

close 在运行时走 closechan。它先加锁，检查 closed 是否已经为 1，是则直接 panic；否则置 1，然后把 recvq 上的等待者逐个摘下，把它们指向的接收变量清零，让这些接收者醒来后拿到零值；再把 sendq 上的等待者逐个摘下，它们醒来后会发现自己等待的发送失败，从而 panic。注意顺序：先处理接收者，再处理发送者。摘下所有 goroutine 之后，closechan 先解锁，再统一调用 goready。原因就是前面提到的那条约束：持有 channel 锁时不能唤醒别人，否则可能与栈收缩互相等待。

还有一个常被误解的点：关闭不会清空缓冲区。接收方只有在 closed 为 1 且 qcount 为 0 时才返回零值与 false；只要缓冲区里还有数据，就照常返回数据且 ok 为 true。所以“关闭之后还能不能读到剩下的数据”的答案是能，而且必须读完才算消费干净。所谓“关了就丢消息”，问题往往出在消费方提前退出、没有读完缓冲区，而不是 close 本身。

range 会自动处理 ok，读到关闭且缓冲为空时退出，这是消费端最常用的写法。但前提是有人负责关闭，否则循环永远不会结束。

nil channel：最安静的 channel

声明但未 make 的 channel 是 nil。对 nil channel 发送或接收不会 panic，而是永久阻塞：运行时入口的第一件事就是判断 c == nil，然后调用 gopark 睡过去。由于根本没有 hchan，也就没有任何队列能挂住它，没有任何发送者或接收者能唤醒它。这个 goroutine 会一直停在 waiting 状态，直到进程结束。

close 是例外，关闭 nil channel 直接 panic。len 与 cap 返回 0。把这些行为放在一张表里对比更清楚：

操作 nil channel 已关闭 channel
发送 永久阻塞 panic
接收 永久阻塞 立即返回零值，ok 为 false
关闭 panic panic
len/cap 0 缓冲区剩余数/容量
select 中 该分支被忽略 接收分支永远就绪

“在 select 中被忽略”是 nil channel 最有价值的特性。运行时在第一轮扫描时会把 nil 的 case 直接跳过，于是我们可以用把变量置 nil 的方式动态关掉一个分支，而不必写两个几乎相同的 select。上一节关闭 channel 后把 ch = nil 的写法，利用的正是这一点。

它也是陷阱的来源。把 nil channel 当作“空的实现”传进函数，调用方一发送就会永久卡住；结构体里忘了初始化 channel 字段，方法里一读就挂起。这类 bug 不会报错，只会表现为 goroutine 数缓慢上涨或者请求永远不返回，排查时应当把“零值 channel”列为可疑项。

几个反复出现的陷阱

泄漏：没人收，也没人关

最典型的泄漏是“发送方在等一个永远不会来的接收者”。无缓冲 channel 的发送必须有人接手，一旦消费者因为错误分支提前返回、或者根本没启动，发送方就会永远挂在 sendq 上。它占用的栈、闭包捕获的变量、以及这些变量引用的对象都不会被回收。goroutine 泄漏比内存泄漏更隐蔽，因为它在监控上首先表现为 goroutine 数只涨不跌，内存要过很久才看得出来。

第二种是“接收方在等一个永远不会来的关闭”。for v := range ch 的退出条件只有一个：channel 被关闭且缓冲区读空。如果生产路径有多个分支，其中一个分支忘了 close，消费循环就会一直等下去。第三种是“生产者退出路径不完整”，例如向结果 channel 发送时没有配合 done，主流程超时返回后，工作 goroutine 仍卡在发送上。

判断一段代码会不会泄漏，可以用一个简单的提问法：这个 goroutine 里的每一次发送和接收，是否存在一条确定的路径能把它解开？如果答案依赖“对方总是会来”，那它迟早会泄漏。

死锁：同一 goroutine 自锁

这段代码会得到运行时的 fatal error: all goroutines are asleep - deadlock!，因为主 goroutine 一阻塞，整个程序就没有可运行的 goroutine 了。但把同样的逻辑放进一个还有别的 goroutine 在跑的程序里，运行时就不会报死锁，它只会安静地卡住，这比直接崩溃更难查。另一种是循环等待：两个 goroutine 各自向对方的无缓冲 channel 发送，双方都在等对方接收，谁也不肯先收，于是僵住。

sync.WaitGroup 也会制造类似问题：在同一个 goroutine 里先 wg.Add(1)、再向无缓冲 channel 发送、最后 wg.Wait()，而接收者要等 Wait 返回之后才启动，顺序上就永远错开了。遇到这类代码，先把“谁在等谁”画成有向图，环一出现就是死锁。

关闭：发送方与关闭者的错位

“谁接收谁关闭”这句话流传很广，它在单发送者场景下确实能用，但一旦有多个发送者就会出事。接收方关闭 channel 后，尚未完成的发送者会立刻 panic；发送前的 closed 检查与真正入队都在同一把锁内完成，所以关闭一旦发生，后续发送必然 panic，不存在侥幸。多个发送者时应当引入一个独立的关闭者：所有发送者通过 done 退出，WaitGroup 计数归零后，由协调者关闭结果 channel。

重复关闭同样常见于“防御式”代码：两个清理函数都觉得自己有责任 close。解决办法是把关闭责任收敛到一处，或者用 sync.Once 包一层。向已关闭 channel 发送则往往发生在“重启 worker”这类逻辑里，旧的生产者还没退出，新的消费者已经把 channel 关了。

缓冲区大小靠感觉

“怕阻塞就加个 1000 的缓冲”是很常见的直觉，但缓冲区不是免费的。它会把背压推迟：上游以为写成功了，实际上数据只是堆在内存里，积压到极限时阻塞会以更猛烈的方式出现。它还会让关闭变复杂：关闭时缓冲区里可能还剩一批数据，消费方是否要读完、读完之后做什么，都得有明确约定。缓冲为 0 表示“交接”，为 1 表示“允许一个在途”，这两个值有清晰语义；大于 1 的容量应当由压测数据或明确的批量模型推出来，而不是随手写。

另外两个小坑：用 len(ch) 判断“有没有数据”再决定收不发，在并发下毫无意义，快照随时会过期；在 for 循环里写 select 加 default 做“非阻塞轮询”，没有退避就会把 CPU 打满，这实际上是把 channel 当成了自旋锁。

泄漏怎么查

怀疑泄漏时，第一步是确认它真的存在。runtime.NumGoroutine() 返回当前 goroutine 总数，在健康检查或定时任务里打点，观察趋势即可。绝对值不必太在意，运行时自己也有若干常驻 goroutine，不同版本数量还会变；有意义的是“请求量平稳时它是否持续上涨”，以及“压测结束后它是否回落到基线”。

第二步是拿到现场。引入 net/http/pprof 之后，/debug/pprof/goroutine?debug=2 会输出所有 goroutine 的调用栈，直接 curl 下来就能看。要找的是大量停在同一个位置的栈，尤其是停在 chan send 或 chan receive 上的。用 go tool pprof 连上去，top 看聚合、traces 看完整调用链，比肉眼翻输出高效得多。没有 HTTP 服务时，可以用 runtime.Stack(buf, true) 主动把全部栈 dump 到日志或文件里，再由信号或管理端口触发。

GODEBUG 也能帮上忙，但它不是泄漏检测器。GODEBUG=schedtrace=1000 每秒打印一行调度器状态，里面有 goroutine 总数、各 P 的运行队列长度，数字持续上涨就说明有东西没退出；GODEBUG=gctrace=1 打印每次 GC 的摘要，如果堆持续上涨，可能是泄漏的 goroutine 抓着引用不放。这两个开关只告诉你“有事”，定位仍然要靠栈。

几种值得背下来的写法

worker pool。固定数量的 worker 从同一个任务 channel 取活，结果写到另一个 channel。任务 channel 由生产者关闭，worker 用 range 消费，关闭即退出；结果 channel 由一个专门的协调者关闭，条件是 WaitGroup 归零。这个“谁关闭结果”的结构值得记住，它避免了接收方关闭的老问题：

扇出与扇入是它的变体：扇出是把任务分给多个 worker，扇入是把多个来源合并到一个 channel。合并时同样需要“等所有来源结束再关闭输出”，否则下游会提前收到关闭信号而丢掉后到的数据。实现上仍然是 WaitGroup 加一个关闭协调者，模式不变。

超时控制。select 加 time.After 是最短写法，但在循环里要小心：time.After 每次都新建一个定时器，定时器在触发前不会被回收，循环次数多、超时时间又长时，堆里会堆积大量待触发的定时器。循环内的正确写法是复用一个 time.NewTimer，用完 Stop 并处理已被触发的情况。

取消与优雅关闭。context 的 Done() 本质上就是一个只读的关闭信号 channel，取消时被 close，所有监听者同时被唤醒，这正好利用了 close 的广播语义。done := make(chan struct{}) 是同一手法的手写版本，struct{} 不占空间，close 之后所有 <-done 立刻返回。优雅关闭的顺序是：先停止接收新任务（关闭任务 channel 或停止监听），再等在途任务结束（WaitGroup 配合超时），最后释放资源。不要在还有发送者的时候关闭任务 channel，也不要用一个没有超时的 Wait 把退出流程挂死。

最后要说清楚 channel 的边界。它不是并发的万能钥匙：单纯计数用 sync/atomic，保护一段临界区用 sync.Mutex，读多写少的缓存用 sync.RWMutex，一次性初始化用 sync.Once。channel 擅长的是“传递数据所有权”和“广播事件”，把这两类问题交给它，代码会清晰；把互斥、计数、状态查询也塞给它，得到的往往是更慢、更难读、更容易泄漏的实现。

小结

channel 的所有行为都可以从 hchan 推出来：qcount 决定空满，sendx 与 recvx 驱动环形缓冲区，sendq 与 recvq 保存被挂起的 sudog，lock 保护这一切。发送与接收都只有几条固定路径，先看对方队列，再看缓冲区，最后才挂起自己；select 用随机顺序扫描、按地址顺序加锁，close 则是一次带唤醒的广播。真正难的不是记住这些字段，而是在写代码时始终清楚“谁会关闭”“谁会退出”“阻塞的那一端有没有人来解”。把这三问答清楚，绝大多数死锁与泄漏都不会发生。
