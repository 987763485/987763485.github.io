NestJS 与 TypeORM 实战

本文属于《TypeScript 学习路线》第 68/74 篇
上一篇系列目录下一篇

把 TypeORM 接进 NestJS 并不难，难的是接得干净：连接什么时候建立、Repository 从哪里来、事务边界划在哪一层、测试时又该怎么替换数据库。本文从一个最小的用户模块出发，走完安装、配置、实体、注入、增删改查、事务与测试的整条链路，重点讲清各个部件如何拼在一起，以及上线前必须改掉的默认值。读完之后，你应该能独立搭起一个结构清晰、可以测试、也敢上线的数据访问层。

为什么要在 NestJS 里用 TypeORM

很多人的第一反应是：TypeORM 本来就能单独用，何必再多装一个适配包？答案不在功能，而在装配方式。如果在入口文件里直接建连接，连接就会变成一个随手可取的全局对象：谁都能导入它，谁都能在任何时刻发起查询，测试时无法替换，进程退出时还容易忘记关闭。项目小的时候这不算问题，模块一多，它就变成一种看不见的耦合。

@nestjs/typeorm 做的事情，是把 TypeORM 的几个核心对象翻译成 Nest 容器里的 provider。TypeOrmModule.forRoot() 是一个动态模块，它在内部创建连接，并把连接本身注册进容器；TypeOrmModule.forFeature([User]) 则针对某个实体生成 Repository 的 provider，注入令牌由框架统一生成，业务代码不需要知道连接是从哪里来的。实体列表集中声明，漏注册会立刻报错，而不是等某个请求进来才发现表映射不存在。

flowchart TD
    A[AppModule] --> B[forRoot 创建连接]
    B --> C[Connection 与连接池]
    D[UsersModule] --> E[forFeature 注册实体]
    E --> F[Repository of User]
    C --> F
    F --> G[UsersService 注入]
    G --> H[Controller 调用]

这样装配换来三个实际好处。第一是生命周期一致：连接在依赖注入完成之后、端口监听之前建立，收到关闭信号时 Nest 会先销毁连接再退出，不会出现请求还在执行、连接池已经关掉的竞态。第二是可替换：Service 依赖的是 Repository<User> 这个令牌，单元测试里换成内存实现即可，业务代码一行不用改。第三是可组合：多数据库、读写分离这类需求，只要多声明一个具名连接，业务模块的写法基本不变。这三点，恰好是自己手写单例连接最难处理的部分。

安装与连接配置

先装三个包：框架适配层、ORM 本体、数据库驱动。数据库用 MySQL 5.7，驱动选 mysql2；如果团队用 PostgreSQL，把驱动换成 pg 就行，配置项的键名大体对应。

连接参数不要写死在代码里。比较稳妥的做法是单独放一个配置文件，从环境变量读取，并在启动阶段校验必填项，让配置错误在启动时就暴露，而不是等到第一个请求超时。

这里有几个参数值得展开。synchronize: false 是生产环境的硬要求。它为 true 时，TypeORM 会在每次启动时比对实体与库表结构，并自动执行建表、加列、改类型。开发阶段图省事可以开，上线必须关掉：一次不小心的字段改名，可能让 TypeORM 生成删列语句，数据直接丢失，而且这个过程没有回滚，也没有评审记录。表结构变更应该走迁移脚本，这部分放在《TypeORM 迁移与查询优化》里展开。

autoLoadEntities: true 让 forFeature 注册过的实体自动进入连接配置，省掉手写通配路径。若项目里还有不经过模块加载的实体，或者要映射已有的旧表，就需要显式写 entities 数组，必要时用 EntitySchema 描述表结构。

logging 与 extra 是两组容易被忽略的配置。开发时打开 query，能把实际执行的 SQL 打出来，排查分页和关联加载问题非常省事；生产只留 error，避免日志被 SQL 淹没。extra.connectionLimit 控制连接池上限，默认值往往偏小，并发一上来就会看到请求排队，这个值要和数据库的 max_connections 一起算。

最后是环境变量的加载顺序。Node 的模块按导入顺序求值，databaseConfig() 在模块定义时就被调用，所以 dotenv 必须在根模块之前执行。把 import 'dotenv/config'; 放在入口文件最上面，或者干脆在配置文件顶部调用一次 dotenv.config()，都能保证读到值。忘记这一步的典型症状是：本地明明有 .env，启动却报缺少变量。

实体：跟着模块走

实体本身的写法并不复杂，这里只保留最小字段，列类型、关联、索引等设计问题留给《TypeORM 实体设计与关联》。

几点说明。@Entity('users') 显式写了表名，避免日后调整命名策略时悄悄换了表；@PrimaryGeneratedColumn() 对应自增主键，类型是 int，量级真的很大时再考虑换成 bigint。unique: true 会在建表时生成唯一索引，这也是后面处理重复注册的依据。select: false 让默认查询不带出密码哈希，需要校验时再显式 addSelect，比在每个序列化层做过滤可靠。@CreateDateColumn 由 ORM 填充时间，不要在业务代码里自己 new Date()，否则时区处理会分散在各处。

文件放在 src/users/user.entity.ts，与模块、Service 同目录。不建议建一个全局的 entities 目录，那样实体会逐渐脱离模块边界，最后没人说得清哪张表归谁管。文件名统一用 .entity.ts 后缀，需要通配时也方便。

Repository 注入

实体有了，还要让 Nest 知道它属于哪个模块。在模块里用 forFeature 登记，框架就会为它生成 Repository 的 provider。

forFeature 的作用域仅限当前模块：它把 Repository<User> 注册成 provider，别的模块想用，要么自己再登记一次，要么由本模块导出 Service。前者适合纯粹的数据访问，后者适合把业务规则收在一处。实践中后者更常见，因为让别的模块直接操作自己的表，等于把表结构变成了公共接口，以后想改字段都要先做兼容。

有了 Repository，常规操作就是几个方法的组合。下面这个 Service 覆盖了创建、按主键查询、更新、删除，并把失败情况翻译成 HTTP 语义明确的异常。

这里有两组容易混淆的方法。create 只是把普通对象转换成实体实例，不会碰数据库；save 才会执行插入或更新，并且会走实体监听器与级联保存。update 和 delete 直接拼 SQL，不加载实体、不触发监听器，返回的是一个结果对象。要判断“有没有改到东西”，就得看 affected，它是 0 时说明主键不存在，此时抛 404 比静默成功更诚实。

唯一键冲突不能用“先查后插”来解决。两个请求同时查到邮箱不存在，然后同时插入，第二个仍然会失败；数据库的唯一索引才是最终的裁判。MySQL 驱动会把这类错误包成 QueryFailedError，错误码是 ER_DUP_ENTRY，在这里映射成 409，调用方就能区分“参数错”和“资源已存在”。

事务：在 Service 里划边界

单条语句自带原子性，但一次业务动作往往要写多张表：发帖之后作者的发帖数要加一，扣库存之后要写流水。这类操作必须放进同一个事务，否则中途失败就会留下不一致的数据。

TypeORM 0.2 里最顺手的写法是从连接调用 transaction，回调参数是一个绑定在事务上的 EntityManager。用它取出的仓库、执行的保存和更新，都在同一个事务里：

回调正常返回则提交，抛出异常则回滚，异常继续向上传播，交给全局异常过滤器统一处理。注意事务里用的必须是 manager 上的方法，如果顺手写成 this.postRepository.save(...)，那条语句会从连接池另取一条连接执行，跑到事务外面去，看起来一切正常，回滚时却留下了脏数据。这是实际项目里最常见的事务误用。

需要更细的控制时，可以用 QueryRunner 手动开启和提交。它适合需要中途查询、按条件决定提交还是回滚的场景，代价是必须自己写 try/catch/finally，并且一定要在 finally 里 release()，否则连接会被一直占着。

事务边界应该落在 Service 的方法上，而不是 Controller，也不建议跨 Service 传递 EntityManager。边界越小越好：事务里只做数据库操作，不要调用外部 HTTP 接口、不要发消息、不要读写文件。外部调用慢且不可控，把它包进事务等于让数据库锁跟着一起等，连接池很快就会被拖干。确实需要“先落库再通知”的场景，应该先提交，再发消息，并接受最终一致。

测试：内存库与 mock

数据访问层的测试有两个层次，选哪个取决于你想验证什么。想验证 SQL 确实能跑通、实体映射没有写错，就用真实数据库的替代品；只想验证 Service 的分支逻辑，就把 Repository 换成 mock。

需要 sqlite3 驱动时，把它装成开发依赖即可，不要混进生产依赖。测试结束记得 await moduleRef.close()，让连接正常释放，否则多个测试文件并行时会互相占着文件句柄。

上线前要处理的几个坑

第一，synchronize 忘了关。开发库里一路开着很舒服，发布时忘了改，第一次启动就可能生成删列或改类型的语句。最稳妥的做法是在代码里写死 false，本地需要自动建表时走迁移命令，而不是让一个布尔值去赌运气。

第二，实体没注册。症状是启动或首次查询时报找不到实体元数据，或者注入时报找不到 Repository 的 provider。排查顺序很清楚：实体有没有被模块的 forFeature 引入、类上有没有 @Entity、文件有没有被编译进产物。

第三，模块循环依赖。用户模块要查帖子数、帖子模块要查用户信息，两边互相导入，容器初始化会直接失败。用 forwardRef 包住模块引用与构造函数注入可以解开，但这通常是边界没划清的信号，更彻底的办法是把共享查询下沉到独立模块。

第四，连接池耗尽。长事务、忘记 release 的 QueryRunner、在事务里调用外部接口，都会占着连接不放，表现是请求越来越慢，最后集体超时。先把 connectionLimit 与数据库的 max_connections 对齐，再排查慢查询和泄漏。

第五，N+1 查询。列表页里循环访问关联属性，一条列表查询会退化成几十条明细查询，开发环境数据少时完全看不出来。加载策略与批量查询的写法放在《TypeORM 迁移与查询优化》里，这里只提醒一句：看到循环里有 await，就要警惕。

第六，迁移没进发布流程。本地靠 synchronize 建表，测试库靠手工改，生产靠 DBA 执行脚本，三套结构迟早对不上。迁移文件应该与代码一起提交、一起评审、一起发布。

小结

把 TypeORM 接进 NestJS，核心就三件事：用 forRoot 让连接跟随应用生命周期，用 forFeature 把实体变成可注入的 Repository，用 Service 收拢查询与事务边界。配置上守住两条底线：生产环境的 synchronize 必须为 false，测试环境不要连真实数据库。事务里只做数据库操作，外部调用留到提交之后。实体设计、迁移流程与查询优化，是这条链路跑通之后才需要深入的部分。
