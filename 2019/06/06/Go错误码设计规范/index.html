Go 错误码设计规范

本文属于《Go 语言与工程》第 65/78 篇
上一篇系列目录下一篇

HTTP 状态码只能说明“哪一类请求失败了”，却说不清“具体为什么失败”。同一套接口同时服务 Web、移动端与第三方系统时，靠匹配错误文案来分支处理既不牢靠，也无法跨语言复用。本文从码段划分、错误类型、分层转换、文档契约与可观测性几个角度，整理一套可以直接落地的 Go 错误码规范，适合刚开始做多团队协作的后端开发者。读完后你应当能为自己的业务设计出一套稳定、可治理的错误码体系。

错误码要解决的三个问题

很多团队最初并不设错误码：接口失败时返回一段中文描述，客户端用 strings.Contains 判断关键字。这种做法在单团队、单语言、文案几乎不变的项目里能撑一阵，一旦接口要同时服务 App、小程序与开放平台，问题就暴露了：文案改一个字，客户端的分支就失效；同一个“库存不足”在不同接口里措辞不同；日志里只能按字符串聚合，告警规则越写越乱。

错误码的第一个价值，是让客户端可以编程处理。客户端拿到一个稳定的整数，就能决定是提示用户修改参数、引导重新登录、自动重试，还是跳转人工客服，而不必理解服务端的自然语言。

第二个价值，是形成跨语言、跨团队的契约。Go 服务、Java 老系统、iOS 与 Android 客户端，甚至外部对接方，都可以围绕同一张码表开发。码表和字段名、枚举值一样，是接口文档的一部分，不能只存在于某位开发者的记忆里。

第三个价值，是让日志与告警可以聚合。按错误码计数，能快速看出“今天下单失败里有多少是库存不足、多少是参数错误”；按错误码配置告警阈值，也比匹配日志文本可靠得多。

需要强调：错误码不是给用户看的文案。用户看到的是“商品暂时卖完了，换一件试试”，这句话可以随运营策略、语言和语气随时调整；错误码则是给程序与排障人员看的稳定标识，不应直接展示给终端用户，也不应把文案本身当成码。两者的生命周期完全不同，混在一起设计，后面一定互相拖累。

码段划分：让数字自己说话

错误码建议使用定长数字，并把每一个位段赋予含义。笔者常用的是 5 位十进制：前 2 位表示业务域，第 3 位表示错误类型，后 2 位表示域内序号。这样全站最多 100 个业务域，每个域 10 类错误、每类 100 个具体码，对中等规模的系统足够用。

先按业务域分段：

码段 业务域 维护团队
10xxx 用户与账号 用户平台组
20xxx 订单与交易 交易组
30xxx 商品与库存 商品组
40xxx 支付与结算 支付组
90xxx 通用与系统 基础架构组
99xxx 预留扩展 暂不分配

再在每个域内按错误类型细分子段，以订单域为例：

子段 错误类型 示例
201xx 参数与校验 20101 参数缺失或格式错误
202xx 状态与冲突 20202 库存不足
203xx 资源不存在 20301 订单不存在
204xx 权限与身份 20401 无权操作该订单
205xx 依赖与系统 20501 库存服务不可用
209xx 域内预留 暂不分配

这种“域 + 类型 + 序号”的结构有两个好处。其一，看到 20202 就能猜到它属于订单域的状态冲突类，排障时不必先查表；其二，新增错误时只在对应子段里追加序号，不会打乱既有码。各域还应保留一段不分配的区间，用于临时活动、内部试验或未来拆分业务域，避免新业务无处安放。

段位长度是取舍。4 位只能容纳 100 个域、每域 100 个码，业务一多就会被迫跨段借用；6 位空间充裕，但念起来、记起来、在表格里对齐都更费劲，排查时也容易抄错。5 位是多数团队能接受的折中。若坚持使用字符串码，例如 ORDER_STOCK_SHORTAGE，可读性更好，但更长、更易拼错，还可能被客户端按前缀解析，反而形成隐式耦合。无论选数字还是字符串，全站只能有一种风格，不能在同一个响应里混用。

还有一个细节：数字码若以 0 开头，部分客户端会按整数解析而丢掉前导零，因此码段最好从 1 开头；若确实要用 0xxxx，文档里必须声明字段是字符串。本文示例统一按 5 位整数处理。

业务码与 HTTP 状态码的分工

HTTP 状态码工作在传输与协议语义层，业务码工作在业务语义层。两者不是替代关系，而是分工：状态码告诉网关、负载均衡与监控系统“这次请求大体属于哪类结果”，业务码告诉调用方“具体是哪条业务规则没有通过”。

HTTP 状态 语义 典型业务错误
400 请求格式或参数不合法 参数缺失、类型错误、字段越界
401 未认证或凭证失效 未登录、令牌过期
403 已认证但无权限 越权访问、角色不足
404 资源不存在 订单不存在、商品已删除
409 与资源当前状态冲突 库存不足、重复提交、状态不允许
429 触发限流 请求过于频繁
5xx 服务端故障 依赖超时、数据库不可用、未知崩溃

映射是多对一的：一个 409 可以对应库存不足、优惠券已使用、订单已取消等多个业务码；反过来，一个业务码只应固定映射到一个 HTTP 状态。这个方向不能反，否则监控按状态码统计时，会把“用户输错参数”算成“服务端故障”。

不要把业务码塞进 HTTP 状态码。有人把“订单不存在”定义成 444，把“库存不足”定义成 445，看起来一一对应，实际上破坏了协议：网关不认识这些状态，浏览器与 CDN 按标准语义处理，监控面板也只认标准分类。更常见的反模式是无论成败都返回 200，把错误藏在响应体的业务码里。这样前端确实省事，但网关、日志采集和 SLA 统计都看不到失败，线上故障会被“200 率 100%”掩盖。

同样，也不要把业务失败放进 5xx。库存不足是正常的业务结果，不是服务故障；用 500 返回它，会污染错误率、触发无意义的告警，还可能让客户端或网关误以为可以重试。5xx 只留给“没有预料到、需要人介入”的情况。

分层：只在懂业务的地方分配码

错误从存储层往上走，职责要分清：repository 只返回领域错误，例如“记录不存在”“唯一键冲突”，它不认识 HTTP，也不引用业务码包；service 判定业务语义，把领域错误转换成 AppError，业务码只在这一层分配；handler 只做映射，把 HTTPStatus 与 Code 写进响应。

flowchart TD
    A[repository 返回领域错误] --> B[service 判定语义并分配业务码]
    B --> C[handler 映射 HTTP 状态与响应体]
    C --> D[客户端按 code 分支处理]
    B --> E[未识别错误折叠为内部错误]
    E --> F[堆栈只写入日志]

一个错误只能分配一次业务码。不要在 repository 给一个码，service 觉得不合适又换一个，handler 再兜底换第三个。层层换码会让同一个原因在不同接口下表现不一致，客户端也无法依据码表预期结果。下层已经标成 AppError 的，上层应原样透传，只在获得新信息时补充 Details。

消息、i18n 与文档契约

Message 建议使用面向开发者的英文，例如 insufficient stock，服务于日志检索与排障；用户看到的中文、英文、日文文案应单独维护。可以放在客户端以错误码为 key 查表，也可以由服务端按 Accept-Language 返回 user_message。无论放哪边，原则都是“码稳定、文案可改”：运营改一句提示不必改码，新增一种语言也不动业务逻辑。

参数化消息不要把变量拼进 Message。“库存只剩 3 件”里的 3 应放在 Details，由展示层套模板；否则 message 随数据变化，既无法聚合，也可能把敏感信息带进日志。文案表同样以 code 为 key，而不是以英文 message 为 key。

错误码表是契约的一部分，至少应包含：码、含义、HTTP 状态、触发条件、处理建议、是否可重试、引入版本、当前状态。文档与代码放在同一个仓库，改码时同步改表。版本化遵循“只增不改”，已有码的含义永不改变；废弃时先标为 deprecated，公告并保留若干版本，确认没有客户端依赖后再移除。移除已发布的码属于破坏性变更，应随接口主版本发生。客户端 SDK 最好由同一份码表生成，至少暴露码常量、可重试判断与文案查询，避免三处各写一遍。

可观测性：让错误码可聚合

日志用结构化字段记录 code、http_status、route、trace_id、耗时与用户标识，不要把这一切拼进 message。trace id 由网关生成并透传，经 context 带到各层，排障时可以从一条响应串起整条调用链。指标按 code 计数，告警分两层：5xx 与未知错误看总量，具体业务码看突增，例如 20202 突然翻十倍，往往意味着库存同步出了问题。Details 与 message 都可能进日志，手机号、身份证、令牌等敏感字段必须在写入前脱敏，或者干脆不记。

常见坑

  • 一个错误多个码：同一个原因在不同接口返回不同码，码表就失去意义。码应在语义源头分配一次。
  • 码随文案变：把文案哈希或自增序号当码，改一个字就换码。码与 message 必须解耦。
  • 把堆栈返回客户端：会暴露表名、文件路径与内部实现。堆栈只进日志，响应只给码与安全的细节。
  • 5xx 里混业务错误：污染错误率、触发误告警，还会诱导客户端做无意义的重试。
  • 既不复用也不废弃：复用旧码会让老客户端误判；永不废弃则码表膨胀。应标记 deprecated，观察调用量后再移除。

小结

错误码是一份长期契约：码段负责可读与可扩展，AppError 负责在层间无损传递，HTTP 映射负责与协议对齐，文档、监控与废弃流程负责让它可治理。先把码表和治理规则定下来，再写业务代码，比事后补一套码省力得多。示例中的码段是虚构的，治理方法却是通用的。
