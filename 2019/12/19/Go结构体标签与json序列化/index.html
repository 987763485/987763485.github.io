Go 结构体标签与 json 序列化

本文属于《Go 语言与工程》第 31/78 篇
上一篇系列目录下一篇

结构体标签只是字段后面的一小段字符串，却决定了 JSON 的键名、空值处理和类型转换。本文以 Go 1.13 为准，围绕 encoding/json 的字段匹配、tag 选项、时间与数字、流式解码与常见故障展开，帮助读者把结构体与外部契约稳定对接。结构体如何分层不在讨论范围内，示例也省略了 import 与部分周边代码。

一、字段如何对上号

序列化只处理导出字段，首字母小写的字段会被静默跳过，既不报错，也不出现在结果里。字段没有 tag 时，键名就是字段名本身；标准库不会把 TotalFee 自动转成 total_fee，也不会转成 totalFee。字段按声明顺序输出，嵌入字段的导出字段会被提升到外层。

反序列化时，标准库先找键名与字段名或 tag 完全相同的字段，找不到再做一次大小写不敏感的匹配。因此 {"Name":"x"} 能落进 json:"name"，{"NAME":"x"} 也可以，{"user_name":"x"} 不行，下划线不会被当成分隔符。很多人误以为会自动转下划线，其实只是忽略了大小写。

二、tag 的语法与静默失败

tag 的完整形式是 json:"名字,选项1,选项2"，名字在前，逗号分隔选项。名字留空表示沿用字段名，例如 json:",omitempty"。常用选项只有 omitempty、string 和 -，其中 - 必须单独作为名字使用；拼错的选项会被当成未知选项忽略。

最后一行不会省略空字符串，因为解析出的选项是 " omitempty"，不匹配任何已知选项。更隐蔽的是整段 tag 写坏：json: "name" 冒号后多空格，json:name 少引号，反射取不到值，字段退回默认名。编译器不检查 tag 内容；go vet 能发现格式畸形，却发现不了 omitemtpy 这类拼写错误。跨边界结构体应当用真实报文往返测试，逐键比对。

三、omitempty 与“零值”语义

omitempty 的依据是 Go 的零值：布尔 false、数值 0、空字符串、长度为 0 的数组、切片和 map、nil 指针与 nil 接口都会被省略。它不认识“业务上的空”，也不认识结构体：一个所有字段都为零的结构体，仍会被序列化成 {}。time.Time 的零值是 0001-01-01T00:00:00Z，加了 omitempty 也照常输出，这是时间字段最常见的误判。

指针提供了另一条路。*string 为 nil 时配合 omitempty 会消失，指向空字符串时则输出 ""，正好区分“没提供”和“提供了空值”。sql.NullString 是结构体，不会被 omitempty 省略，默认还会输出 {"String":"","Valid":false}，大多数前端契约并不接受。建议把它留在数据访问层，在 API 层换成指针。

解码同样有信息损失：字段是 int 时，JSON 里没有这个键和显式传 0，解出来都是 0。做 PATCH 时，用指针字段或带 Set 标记的自定义类型，才能知道客户端是否提供该字段；必填校验放在解码之后，不要指望 tag 承担。

四、命名、忽略与字符串化

命名是契约的一部分

Go 字段习惯用 ID、URL、HTTPStatus 这样的缩写，JSON 侧却要照顾调用方。camelCase 对 JavaScript 前端更自然，snake_case 在 Python、Ruby 和多数开放平台更常见；两种都能用，关键是同一服务内统一，所有跨边界字段显式写 tag，不依赖默认字段名。这样重命名字段也不会悄悄改变契约。缩写词按一个单词处理，写成 userId 或 user_id，不要混用。把典型响应放进测试逐键断言，是成本最低的规范手段。

- 与 -,

json:"-" 表示该字段在序列化和反序列化时都被完全忽略，适合密码哈希、内部备注这类永远不该出现在报文里的字段。json:"-," 常被误解为“序列化时忽略、反序列化时可读”，实际并非如此：它只是把键名定为 -，字段照常参与两个方向。标准库文档说明，这是给名字真的叫 - 的字段用的。

如果确实需要“只读不写”或“只写不读”，只能拆 DTO，或者实现自定义的 MarshalJSON/UnmarshalJSON，没有现成的 tag 选项。敏感字段除了加 -，更稳妥的是单独定义响应结构体，按白名单逐字段赋值，避免以后有人新增字段时把内部数据带出去。

,string 与大整数

string 选项让数字或布尔值以 JSON 字符串的形式出现：int64 的 1990 变成 "1990"，true 变成 "true"。它适用于字符串、布尔、整数和浮点数；给字符串字段再加 ,string 会编码两层引号，得到 "\"abc\""，通常不是想要的结果。反序列化时，它要求 JSON 值本身是字符串，传数字会报类型错误。

这个选项最实际的用途是保护大整数。JavaScript 的 Number 只有 53 位尾数，能安全表示的最大整数是 2^53-1，即 9007199254740991；19 位的订单号、雪花 ID 超过这个范围后，JSON.parse 会把末尾几位抹平。服务端用 int64 保存没问题，但发给浏览器时应转成字符串。金额也建议用字符串或“分”为单位的整数传输。

五、时间与自定义序列化

时间的默认格式

time.Time 实现了 MarshalJSON，默认输出 RFC3339 格式，并保留时间值携带的时区偏移：2019-12-19T09:29:08.123456+08:00，UTC 时间以 Z 结尾。小数秒按需要输出，不是固定六位。反序列化只接受 RFC3339 及其变体，2019-12-19 09:29:08 这种空格分隔的数据库格式会直接报错。

时区要在边界上统一。DATETIME 本身不带时区，驱动开启 parseTime 后按 loc 把它解释成 time.Time；若一半服务写本地时间、一半写 UTC，同一张表迁到别的机器就会整体偏移。建议入库和 API 都统一 UTC，由前端按用户时区展示；契约要求保留偏移就写进文档，不要依赖默认值。

空时间的零值是 0001-01-01T00:00:00Z。由于 time.Time 是结构体，omitempty 不会省略它；用 *time.Time 可以让 nil 消失，或者定义可空时间类型，把零值输出成 null。生日、账期这类只有日期含义的字段不要直接用 time.Time，否则会带上无意义的时间和时区，应该用自定义的 Date 类型固定格式。

自定义 MarshalJSON 与 UnmarshalJSON

默认格式不符合契约时，实现这两个方法即可。序列化方法定义在值接收者上，T 和 *T 都会实现 json.Marshaler；定义在指针接收者上则只有 *T 实现，把 T 值作为顶层值传给 json.Marshal 时不会调用。反序列化必须用指针接收者，否则方法改的是副本，字段看起来毫无变化。

六、nil、空值与未知字段

nil 切片与空切片

var s []string 是 nil 切片，json.Marshal 得到 null；s := []string{} 是非 nil 空切片，得到 []。反序列化时，null 解成 nil，[] 解成空切片。对前端来说这两个值并不等价：null.map(...) 直接抛异常，[].map(...) 正常返回空数组。列表字段没有特殊语义时，应在构造响应时初始化为 make([]T, 0)，并且不要加 omitempty，否则 nil 和空切片都会消失，前端连字段都拿不到。

数据库查询没有结果时，切片通常是 nil；直接透传给接口就会变成 null。可以在 DTO 层统一补空切片，也可以定义 type List []T 并为它实现 MarshalJSON，在 nil 时返回 []。后一种方式更省心，但要注意值接收者才能同时覆盖 nil 切片和普通切片。

未知字段与版本演进

默认情况下，JSON 中多出来的键会被忽略，这既是兼容性来源，也是拼写错误的温床。Go 1.10 起，Decoder 提供了 DisallowUnknownFields，可以在解码时对未知字段报错：

严格模式对嵌套结构体同样生效，但对 map 和 interface{} 无效。它只检查未知键，不检查必填字段和取值范围，后者仍要单独做。

这项能力不能轻率地开在公开 API 上。宽容读取让服务端可以先忽略客户端的新字段，等客户端升级完再启用；一旦严格拒绝未知字段，客户端新增字段、服务端删除旧字段都会变成破坏性变更。稳妥的划分是：内部配置、签名固定的 webhook、版本化内部接口可以严格；公开接口保持宽容，用 schema 校验和日志发现异常字段。

七、流式处理与转义

Decoder、Encoder 与 RawMessage

小报文用 json.Marshal/Unmarshal 即可；报文很大或以流方式处理多个值时，应该用 Decoder 和 Encoder。json.NewDecoder(r.Body).Decode(&v) 不需要先把整个请求体读成 []byte，但它不会限制大小，仍应在外面套一层 http.MaxBytesReader，防止恶意请求占满内存。json.NewEncoder(w).Encode(v) 会把值写到 ResponseWriter，并在末尾追加一个换行；单个响应无伤大雅，按行解析反而正合适。

如果响应是巨大的 JSON 数组，直接 Decode 到 []T 仍会把所有元素放进内存；可以用 dec.Token() 读掉开头的 [，再逐个 Decode 元素，最后读 ]。

json.RawMessage 把一段 JSON 原样保留，等真正需要时再解析，适合事件信封、转发和按类型二次解码。它避免了一次无谓的结构体映射，但字节仍然在内存里，不要把它当成大报文的“零拷贝”方案。Decoder.UseNumber 则让 interface{} 中的数字保持为 json.Number 而不是 float64，需要无损读取时有用。

HTML 转义

默认情况下，encoding/json 会把 <、>、& 转义成 \u003c、\u003e、\u0026，目的是让 JSON 可以安全地嵌进 HTML 的 <script> 标签，避免内容里的 </script> 提前闭合脚本。URL 查询串里的 & 因此会变成 \u0026，客户端解析后仍然是 &，只是日志里看起来别扭。

如果确认响应只作为 application/json 使用，可以用 Encoder.SetEscapeHTML(false) 关掉这层转义。它只存在于 Encoder 上，json.Marshal 没有对应开关；想在 Marshal 路径关闭，只能先写入 bytes.Buffer 再用 Encoder。关闭之后不要再把 JSON 拼进 HTML，因为 </script> 可以正常闭合标签，XSS 风险随之回来。边界是：JSON 接口只负责数据，HTML 转义交给模板。

八、数字精度与性能

数字精度

JSON 规范没有区分整数和浮点数，Go 把数字解码到 interface{} 时默认用 float64。float64 的尾数只有 53 位，并非所有大于 2^53-1 的整数都能精确表示：

如果结构体字段声明为 int64，解码会走整数解析，不会经过 float64，这层是安全的；丢失发生在 JavaScript 的 JSON.parse，或者把值塞进 interface{}、map[string]interface{} 的时候。json.Number 可以保住原始字面量：dec.UseNumber() 之后，interface{} 里的数字是字符串形式的 json.Number，调用 Int64() 或 Float64() 再转换。它适合通用处理，不适合直接参与算术。

金额不要用 float64。0.1 在二进制浮点里没有精确表示，0.1 + 0.2 的结果是 0.30000000000000004，用 == 比较也会失败。做法是以“分”为单位存 int64，或者用十进制定点库，在 API 边界再格式化成字符串。浮点数只用于允许误差的度量值。

性能与复用

encoding/json 依赖反射，标准库会缓存类型与字段的解析结果，但每次序列化仍要逐字段读取、拼接和分配。优化很直接：不要对同一个对象反复 Marshal，日志和响应共用一份字节；不要在热路径上先 Marshal 再 Unmarshal；直接把 json.Encoder 接到 http.ResponseWriter，省掉手写 Write。它不会消除反射，收益要用 go test -bench 在自己的数据结构上量，不能照搬倍数。

复用结构体解码时要小心。Unmarshal 不会先把目标清零，JSON 里没有出现的字段会保留上一次的值，map 还会逐键合并。复用前显式赋零值，或者每次新建对象，能避免很难复现的串数据问题。吞吐高的接口可以考虑代码生成，但生成步骤和维护成本要一起算；普通接口先把契约做对，比微优化更有价值。

九、常见坑清单

  • tag 拼写错误或选项多了空格，字段静默退回默认名；用真实报文做契约测试。
  • 字段名大小写不匹配，解码得到零值；user_name 不会自动匹配 UserName。
  • 嵌入结构体同层同名字段，只有一个带 tag 时它优先，否则整体忽略；合并后检查输出键。
  • omitempty 对结构体、time.Time、sql.NullString 不生效；需要省略就用指针或自定义类型。
  • 父子指针互相引用，Marshal 返回循环引用错误；对外 DTO 只保留 ID 或引用链接。
  • 把 error 直接放进响应结构体，得到的是 {} 或 null；应该输出错误码和消息字符串。

小结

结构体标签不是装饰，而是接口契约的一部分。跨边界字段显式命名并统一风格；用指针区分“零值”和“未提供”；时间统一时区，空时间用可空类型；大整数和金额用字符串或整数分传输；对 nil 切片、未知字段和 HTML 转义做出明确选择。把 Marshal 的错误当成正常错误处理，用契约测试锁住键名和格式。
