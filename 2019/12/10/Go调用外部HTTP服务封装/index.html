Go 调用外部 HTTP 服务封装

本文属于《Go 语言与工程》第 70/78 篇
上一篇系列目录下一篇

外部依赖是服务端最不可控的部分。把 http.Get 散落在业务代码里，超时、重试、错误判断就会各写一套，线上出问题只能靠日志猜。本文不重复讲 net/http 的请求构造与状态码，而是从一个统一客户端出发，逐层加上超时、重试、熔断、连接复用、鉴权与可观测性，最后给出可以拆开落地的封装。适合会发 HTTP 请求、准备把调用逻辑收口的读者。

为什么需要封装

Go 发一个请求只要几行，问题往往出在之后的可靠性上。最常见的写法是直接调用 http.Get，它使用 http.DefaultClient，而 http.Client 的零值没有超时。上游一旦卡住，goroutine 会一直等，连接也不释放；流量上来后，自己的服务先被拖垮，这是级联故障的典型起点。

散落各处的调用还有几类共性毛病。每个业务函数自己写循环重试，次数和间隔全凭手感，POST 被重放造成重复写入；错误只做 if err != nil 判断，调用方分不清网络断开、超时还是上游 500；日志里没有上游的 request ID，排查只能按时间戳对；每个调用点各配一个 Transport，连接池各建一套，keep-alive 形同虚设。

封装的目标不是少写几行，而是把可靠性策略收到一处：超时、重试、隔离、错误类型、鉴权与指标。集中之后才能测试、调参，复盘时答得出“当时重试了几次”。

先改 Client 与 Transport 的默认值

http.Client 是并发安全的，应该在整个进程里共享。通常只关心两个字段：Timeout 与 Transport。Timeout 覆盖从拨号到读完响应体的全过程，零值表示永不超时，适合兜底，不适合做阶段控制。

真正决定连接行为的是 Transport。http.DefaultTransport 已配好连接池，但 MaxIdleConnsPerHost 仍是默认值 2。对同一上游并发 50 个请求时，只有 2 条会被保留复用，其余用完即关；高并发下会看到大量 TIME_WAIT，握手和 TLS 开销也跟着上涨。

正确的做法是复制一份默认配置再按需调整，不要改全局的 http.DefaultTransport。它被标准库和其他依赖共享，改了影响范围不可控。

MaxIdleConns 至少要覆盖“上游数量乘以单上游并发”；IdleConnTimeout 要小于上游或负载均衡的空闲超时，否则会拿到一条已被对端关闭的连接；DialContext 的连接超时要单独设，默认 30 秒对内部调用太长。

用 context 把超时分层

一次外部调用至少有两段时间：建立连接、等待响应。连接超时放在 net.Dialer.Timeout，TLS 握手由 TLSHandshakeTimeout 控制，等待响应头由 ResponseHeaderTimeout 控制，整个调用则由 context 的 deadline 兜住。

不要用 Client.Timeout 一把梭。它能兜底，但粒度太粗：设 30 秒，慢接口会占住 goroutine 30 秒；设 1 秒，稍大的响应体可能在读取中途被掐断，错误只表现为 *url.Error，难以判断慢在哪一段。

推荐给每次调用一个总预算，单次尝试再设更小的预算。比如网关给本服务 2 秒，本服务调下游的总预算设 1.5 秒，单次尝试 800 毫秒，剩余时间留给重试和序列化。预算必须逐层递减，否则会出现“下游等我、我等下游”的互相拖死。

Go 1.13 提供了 http.NewRequestWithContext，可以直接把 ctx 绑到请求上；更早的代码只能先 http.NewRequest 再调用 req.WithContext(ctx)，两者效果一致。

判断超时要靠错误链。errors.Is(err, context.DeadlineExceeded) 识别 deadline 到期，errors.Is(err, context.Canceled) 识别主动取消；对 net.Error 则用 errors.As 取出后调用 Timeout()。取消通常不该重试，超时在还有预算时可以再试。

请求构造与可重放的 body

拼接 URL 最容易埋坑。用字符串相加拼 query，参数里的空格、& 和中文都不会转义，轻则 400，重则参数被截断。正确做法是用 url.Values 组装再交给 Encode()，它会按键排序并转义，顺带让缓存键和日志更稳定。

路径参数要用 url.PathEscape，不能直接塞进路径。如果 host 来自用户输入，还要做白名单校验，否则这个客户端会成为 SSRF 的跳板。

请求体先 json.Marshal 成 []byte，每次尝试用 bytes.NewReader 重新包。这样重试时 body 天然可重放，不必依赖 GetBody。http.NewRequest 对 *bytes.Buffer、*bytes.Reader、*strings.Reader 会自动设置 GetBody，遇到 307/308 重定向时标准库靠它重发 body；如果传的是管道或文件流，GetBody 为空，重定向就会失败。

Header 至少设置 Accept、Content-Type 和 User-Agent。默认的 Go-http-client/1.1 常被网关拦截或限流，带上服务名与版本，排查时也更容易定位调用方。

响应处理与错误分类

拿到响应后立刻 defer resp.Body.Close()，再把 body 读完。不关闭会泄漏连接；没读到 EOF 就关闭，连接不会回到池子，keep-alive 等于没开。

读 body 要限制大小。上游异常时可能返回几百 MB 的错误页，直接 ioutil.ReadAll 会把内存打满。用 io.LimitReader 多读一个字节，超过上限就按错误处理，并放弃这条连接。

状态码要分类：err == nil 只代表拿到了响应，不代表业务成功。2xx 解析业务数据；3xx 默认由 Client 自动跟随，最多 10 次；4xx 是调用方的问题，例如参数、鉴权、配额；5xx 是上游故障。非 2xx 的 body 同样要读，里面的错误码和 message 是排查依据，但对外返回时要截断并脱敏，不能把上游内部信息原样透给用户。

JSON 解码默认忽略未知字段，这是好事：上游加字段不会让旧客户端崩掉。但必填字段要自己校验，因为字段缺失与合法零值无法区分。金额、ID 这类大整数可以用 json.Number 接，避免 float64 的精度丢失。

错误类型建议自定义 APIError，携带状态码、上游 request ID、截断后的响应体和 Retry-After。Error() 只负责给人看，程序判断交给 errors.As；底层错误用 %w 包装，保留错误链，调用方再用 errors.Is 判断超时与取消。这样业务代码不必解析字符串，也不会因上游改文案而失效。

重试与熔断

哪些错误值得重试

重试的前提是错误可恢复、操作可重复。连接被拒绝、连接被重置、单次尝试超时、502/503/504 都可以再试；4xx（429 除外）说明请求本身有问题，重试只会得到同样的结果；构造、编解码失败属于本地 bug，重试没有意义；调用方主动取消则应立即返回。

幂等性是第二条边界。GET、HEAD、PUT、DELETE 天然幂等，POST 不是。对 POST 自动重试，必须让上游支持幂等键，或业务侧有去重表。拿不准时，宁可不重试，也不要把重复写入的锅甩给运维。

退避与预算

退避采用指数增长加抖动。固定间隔会让所有实例同时再次涌向上游，抖动把重试打散；次数控制在 2 到 3 次，总耗时不能突破 context 的预算。等待必须可取消，不要用 time.Sleep。

Retry-After 是上游给出的明确指示，值为秒数或 HTTP 日期。它应与退避时间取较大者，但仍受总预算约束；如果它要求等 60 秒而预算只剩 2 秒，正确做法是直接失败，而不是干等。

    I --> D

熔断三态

重试处理偶发失败，熔断处理持续故障。上游已经不可用时，重试只会继续堆请求，还占着自己的 goroutine、连接和超时预算。熔断器连续失败后直接拒绝，给上游恢复时间，也保护调用方自己。

状态机只有三个状态：关闭时放行并统计连续失败；失败达到阈值（例如 5 次）后打开，后续请求立即失败；冷却 30 秒后进入半开，只放一个探测请求，成功则关闭，失败则重新打开。

一个互斥锁加几个字段就够。关键是两点：半开只允许一个探测，否则恢复瞬间会被并发打满；判定成功时排除 4xx，因为 4xx 说明上游活着，把它算作失败会让熔断器误开。

与重试叠加时顺序要清楚：先问熔断器是否放行，再进入重试循环；熔断器只记录整次调用的最终结果。若每次尝试都记一次，几次尝试就能把阈值打满，熔断器反而成了重试的放大器。

连接复用与鉴权

连接复用

keep-alive 默认开启，但复用有条件：body 必须读到 EOF 并关闭。任何一次提前 return 或忘记 Close，都会让连接被丢弃。高并发下这不是小浪费，而是端口耗尽与延迟抖动的来源。

连接池挂在 Transport 上，要被共享。零值的 http.Client 使用全局 http.DefaultTransport，池子确实是共享的；一旦为改配置给每个 Client 配独立 Transport，池子就各建一套，空闲连接要等到超时才回收。共享 Client 是并发安全的，但不要在请求过程中修改它的字段，那是数据竞争。

IdleConnTimeout 要略小于上游的空闲断开时间，否则客户端以为连接可用，发出去才发现对端已关，表现为 EOF 或 connection reset。这类错误可以重试，但本不该发生。

鉴权

API Key 放在 Header，不要放在 query。query 会进入访问日志、浏览器历史和代理记录，泄露面大得多。Bearer Token 同理，统一由客户端注入，业务代码不要各自拼 Authorization。

签名请求要把 method、路径、body 哈希、时间戳和随机串一起纳入 HMAC；服务端校验时间窗口与 nonce，防止重放。密钥从环境变量或配置中心读取，不能硬编码，也不能打进日志；记录请求时对 Authorization、Cookie 和敏感 query 参数做脱敏。

Token 有有效期，需要缓存并在过期前刷新。刷新要用互斥锁串行化，避免并发请求同时去打鉴权服务；刷新失败时，如果旧 token 还没过期，可以继续用，不要立刻清空。

可观测性与测试

指标与日志

外部调用至少要有四个指标：请求总数、耗时直方图、重试次数和熔断器状态。请求总数按上游、方法、状态码分组；命名遵循 Prometheus 惯例，计数器以 _total 结尾，耗时以秒为单位并带 _seconds 后缀，例如 http_client_requests_total、http_client_request_duration_seconds、http_client_retries_total 和 http_client_circuit_open。标签基数要控制，不要把完整 URL、用户 ID、request ID 放进标签，否则时间序列会爆炸。

日志用结构化格式，一次逻辑调用至少一行，字段包括 request ID、上游、方法、路径模板、状态码、尝试次数、耗时和错误分类。request ID 从入口透传，没有就生成一个并写入请求头；上游返回的也记下来，对接工单时能对上。重试可以打 debug 日志，但不要在循环里打 info，否则一次故障就会刷满磁盘。

定位慢在哪一段时，可以用 httptrace 记录 DNS、建连、首字节的时间，区分网络问题与上游处理慢。

用 httptest 造故障

外部服务不能作为测试依赖：它慢、不稳定，还可能产生费用。httptest.NewServer 可以在本地起一个假上游，按需返回 503、延迟响应或超大 body，覆盖重试、超时和限额三条路径。

模拟连接失败时，注入自定义 RoundTripper 比造真实网络故障简单得多。用函数类型实现 RoundTrip，直接返回 net.OpError 或超时错误，再统计调用次数，就能验证重试上限与熔断阈值。测试里还应把退避基数调小，否则重试用例会慢好几秒。

超时用例可以让 Handler 睡 500 毫秒，再传入一个 50 毫秒 deadline 的 context，断言 errors.Is(err, context.DeadlineExceeded)，顺便验证重试没有突破总预算。测试全部在本地完成，不依赖真实外部服务。

完整封装与常见坑

把前面的片段收拢，一个可用的客户端由四部分组成：配置、选项函数、入口方法与单次请求。入口方法负责编排熔断和重试，单次请求只关心“发一次、读回来、分类”。出参用 interface{} 接收，Go 还没有泛型，这是最直接的写法。

鉴权头可以放在 doOnce 里从 tokenSource 取，也可以做成一个 RoundTripper，让 Do 只关心重试与熔断。

常见坑集中在所有权与状态上，下面几条几乎每次都有人踩：

  • 忘记关闭 body，或在读完之前 return，连接无法复用。
  • 重试时复用同一个 *http.Request，body 已到 EOF。
  • 请求之间修改共享 Client 或 Transport 的字段，产生数据竞争。
  • 超时过大甚至不设，上游一慢就拖垮自己，形成级联故障。
  • 把 5xx 吞掉并返回 nil，重试与熔断全部失效。
  • 对非幂等 POST 盲目重试，造成重复写入。
  • 只判断 err != nil，日志里全是无意义的 EOF。

小结

封装外部调用，本质上是在不可靠的网络上划定自己的失败边界。超时要分层并逐级递减，重试要限定错误类型和总预算，熔断要在连续失败后主动止损，连接复用要靠读完并关闭 body 来维持。把状态码翻译成带 request ID 的错误类型，把次数、耗时和熔断状态变成指标，问题才能被定位而不是被猜测。所有故障场景都应当能用 httptest 在本地复现，否则这套封装只是看起来可靠。
