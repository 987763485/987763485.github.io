Go 连接 Redis 与缓存设计

本文属于《Go 语言与工程》第 71/78 篇
上一篇系列目录下一篇

读多写少的接口最容易在流量上来时暴露问题：数据库连接被占满，慢查询排队，响应时间从几十毫秒涨到几秒。缓存是最直接的缓解手段，却也带来一致性、失效与故障扩散。本文以生产环境常见的 Redis 5.0 与 go-redis v6.15/v7 为例，讲连接管理、cache-aside、TTL、穿透与雪崩、分布式锁和 Pipeline，适合准备把缓存接进 Go 服务的读者。

缓存的位置与边界

缓存是数据库前面的一层内存副本。一次 Redis 读取通常在亚毫秒到几毫秒，而一次走索引的 MySQL 查询即使命中缓冲池，也要经历网络往返与 SQL 解析；把热点结果放进 Redis，既降低延迟，也把大部分读流量卸下来。商品详情、配置、榜单这类读多写少的数据收益最明显。

但缓存不是数据库，没有事务与约束，数据随时可能因淘汰、重启或误删而消失。判断能否缓存，除了读写比，还要看能否接受短暂旧值、能否从权威源重建、重建代价是否可控。余额、库存这类读不应把 Redis 当作唯一来源。

连接管理：一个进程一个 client

redis.NewClient 返回的 *redis.Client 自带连接池，可以被多个 goroutine 同时使用。它应在进程启动时创建一次，通过依赖注入或包级变量共享，退出时 Close。每次请求都新建 client 是最常见的错误：每个 client 都会建立 TCP 连接、启动后台 goroutine，请求一多就会耗尽文件描述符。

连接池参数按业务量估算。PoolSize 是每个节点的最大连接数，默认 10 * runtime.NumCPU()；MinIdleConns 是常驻空闲连接，默认 0，突发时会集中拨号。所需连接数大致等于 QPS 乘以平均命令耗时（秒），再留一倍余量，取 32 到 64 比较稳妥。Redis 5 的命令执行是单线程的，连接过多只会增加调度开销。

超时同样关键。DialTimeout 控制建连，ReadTimeout 与 WriteTimeout 控制单次命令，PoolTimeout 控制等连接。默认值 5 秒、3 秒、3 秒、4 秒，对在线接口偏长，Redis 抖动时请求会成批卡住；生产上通常收紧到几百毫秒。

启动时用 Ping 做健康检查，失败就快速失败；运行期可以每 30 秒探活，但不要塞进每个请求。go-redis v6.15 与 v7 都提供 WithContext，可以透传请求截止时间；更早的 v6 版本只能靠 Options 里的超时。

IdleTimeout 要小于中间设备的空闲断连时间，否则会拿到已被对端关闭的连接。优雅退出时记得 Close。

命令、序列化与 key 设计

最常用的是 Set、Get、Del。写缓存尽量把值与过期时间放在同一条 Set 里，避免 Set 成功、Expire 失败留下永久 key；需要单独续期时用 Expire，查看剩余时间用 TTL（返回负值表示 key 不存在或未设过期）。Get 在 key 不存在时返回 redis.Nil，这是“未命中”的约定信号，不是故障；与网络错误混在一起，会在缓存故障时误判为数据不存在。

批量读写用 MGet 与 MSet。MGet 返回 []interface{}，顺序与传入 key 一致，缺失位置是 nil；但 key 太多会长时间占用 Redis 单线程，通常控制在 100 个以内。对象字段多、每次只读几个时，可以用 Hash 的 HGet、HSet、HMSet；总是整取整存则序列化成一个字符串更省内存。

序列化没有唯一答案。JSON 可读、跨语言，redis-cli 直接能看到内容，代价是体积与编解码开销；protobuf 体积小、有 schema，适合内部高频调用，但要维护 .proto 与生成代码。gob 只适合纯 Go 内部，不建议用于跨版本缓存。

用 JSON 时注意数字精度：解码到 interface{} 会变成 float64，超过 2^53 的 ID 会丢精度，可用 int64 或字符串承接。缓存结构带 version 字段，便于将来兼容。

key 要当成接口设计。推荐 业务:实体:标识:属性，全小写、冒号分隔，如 shop:item:1024:detail；前缀带版本号，切换结构时可双写过渡。不要直接拼用户输入；Cluster 下可用 hash tag 把相关 key 固定到同一 slot。

cache-aside 的读写路径

cache-aside（旁路缓存）是最常见的模式：业务代码显式读写缓存，读时先查缓存、未命中查库并回填，写时先更新数据库、成功后删除缓存。

flowchart TD
    A[读请求] --> B{缓存命中}
    B -- 是 --> C[返回缓存数据]
    B -- 否 --> D[查询数据库]
    D --> E{查到数据}
    E -- 是 --> F[写回缓存并设 TTL]
    F --> G[返回数据]
    E -- 否 --> H[写入空值缓存]
    H --> I[返回不存在]

读路径要区分命中、未命中与缓存故障。未命中查库，查到就回填并设 TTL，查不到按穿透策略写短 TTL 空值；缓存故障时降级读库，但要加并发保护，否则 Redis 一挂，请求会全压到数据库。

写路径选择删除而不是更新缓存。并发写会乱序，后到的请求可能先完成，各自更新缓存会留下旧值；删除把重建交给下一次读，顺序问题自然消失。缓存值常是聚合结果或裁剪视图，更新要重复业务计算，成本高且容易漏字段。

删除失败要有补偿：请求内有限次重试，或投递消息队列异步重试，也可订阅 binlog 变更失效（如 canal）。无论哪种，都保留 TTL 作为最后保险。回填失败不应影响主流程，写缓存失败只记日志与指标，别把缓存写成强依赖。

一致性与并发回填

先写库再删缓存仍有短窗口：写库成功、删缓存之前，读请求拿到旧缓存。窗口只有一次更新加一次删除的耗时，下一次写还会再删，可以接受。反过来“先删缓存再写库”窗口更大：删完后、写库前，读请求未命中并把旧值回填，写库完成后缓存里仍是旧值，直到 TTL 才自愈。

延迟双删试图缩小窗口：更新前删一次，更新后休眠几百毫秒再删。休眠要覆盖一次“未命中、查库、回填”的耗时，只能靠压测取值；它还占用请求资源，主从延迟时第二次删除也可能落空。它降低概率，不保证正确。

并发回填可用 golang.org/x/sync/singleflight 合并同一 key 的并发调用，其余调用等待并共享结果，2019 年它已经足够稳定。但它只在进程内生效，20 个实例就有 20 次回源；跨实例要合并，得用分布式锁或逻辑过期。

另一种竞态更难处理：读请求 A 读到旧值，写请求 B 更新数据库并删除缓存，A 随后把旧值写回。缓解手段有回填前校验版本、带版本拒绝回退、延迟双删；只要读写没有共享的串行化机制，就无法彻底消除。把 TTL 设短更实际，强一致的读应直接读主库。

穿透、击穿与雪崩

穿透

查询不存在的数据时，缓存与数据库都不命中，请求每次都穿透到数据库；被随机 ID 刷接口时，库会被无效查询占满。参数校验挡住非法输入，空值缓存把“不存在”记下来（TTL 30 到 60 秒），布隆过滤器在查库前做拦截。

布隆过滤器用位数组和多个哈希：写入时把对应位置 1，查询时只要有一位是 0，元素一定不存在。它只有假阳性、没有假阴性，适合前置拦截。容量要按元素数量与误判率预估；标准布隆不支持删除，频繁增删要定期重建或改用计数布隆。Redis 5 原生没有 Bloom 命令，需要模块或客户端实现。

击穿

击穿是单个热点 key 过期瞬间，大量请求同时回源。互斥锁最直接：回源前执行 SET lock:item:1024 <token> NX PX 3000，拿到锁的查库回填，没拿到的短暂等待后重读缓存；锁的过期时间要大于一次回源的最坏耗时。

singleflight 是进程内互斥，代码简单，但多实例时每个实例仍回源一次，适合回源不贵的场景。逻辑过期把过期时间写进 value，Redis 不设 TTL，读到过期数据先返回旧值，再由后台异步重建；可用性高，代价是数据可能更旧，还要额外维护重建锁与后台任务。

雪崩

雪崩有两类：大量 key 同时过期，常见于批量导入或重启后的集中预热；以及 Redis 整体不可用，请求涌向数据库并把它压垮。前者靠 TTL 抖动与分散预热。

后者需要几层防线：本地缓存顶住最热的一部分读；用信号量或令牌桶限制回源并发；对数据库访问熔断，错误率超阈值就返回降级结果；接口层明确哪些数据可以返回默认值或旧值。Sentinel 与 Cluster 能缩短故障时间，但切换期间仍有抖动，客户端要短超时并接受少量失败。预案要在平时演练，确认降级开关有效。

TTL 设计与热点 key

每个缓存 key 都该有 TTL，除非有明确的失效链路与容量评估。永久 key 的风险是数据永远陈旧、内存只增不减、淘汰不可控；Set 的 expiration 传 0 就是永不过期。TTL 长度等于可接受陈旧时间加重建成本：热数据短一些保证新鲜，冷数据长一些减少回源。

TTL 必须加抖动，例如叠加 10% 到 20% 的随机量。批量导入或重启预热时，同一批 key 常在同一秒写入，TTL 相同就会在同一秒集体过期，正好触发雪崩。按热度分层是另一个思路：热 key 5 到 10 分钟、温 key 1 小时、冷 key 1 天；但热 key 的 TTL 越短，击穿风险越高，要配合互斥或逻辑过期。

热点 key 是单点问题：某个 key 的 QPS 远高于其他 key，而 Redis 单线程处理命令，一个 key 就能打满一个核。识别可以用 redis-cli --hotkeys（依赖 LFU 策略）、短时 MONITOR 采样（影响性能，只适合排查）、代理层或客户端按 key 统计 QPS。

第一层是本地缓存：进程内放一个带 TTL 的 LRU（如 hashicorp/golang-lru），TTL 取 1 到 5 秒，把大部分读挡在 Redis 之前；代价是实例间数据最多差一个本地 TTL。第二层是拆分 key，例如 hot:item:1024:0 到 hot:item:1024:9，读随机选一个，写更新全部；读被摊开，但写放大 10 倍，不同分片也可能短暂读到不同版本。不可拆的聚合结果，只能靠本地缓存。

分布式锁与批量命令

分布式锁常用来避免重复劳动，比如只让一个实例重建缓存或执行定时任务。正确的加锁是一条 SET key value NX PX ttl：NX 保证 key 不存在时才写入，PX 同时设毫秒过期，整条命令原子执行。不要用 SETNX 再 EXPIRE，中间崩溃或断网会留下永不过期的锁。

value 必须是调用方生成的唯一标识（UUID 或随机串）；释放时先比较再删除，且比较与删除要在 Lua 里完成，否则可能删掉别人的锁。

锁的过期时间要大于业务执行时间，但 GC 停顿、下游超时都可能让执行变长。看门狗每隔 TTL 的三分之一续期，续期同样用 Lua 校验 value。进程长时间挂起时看门狗也会失效；要求绝对互斥的场景应使用数据库行锁或 fencing token，Redis 锁更适合“尽量别重复做”。

Pipeline 解决 RTT 浪费：串行 100 条命令就是 100 次往返，每次 1 ms 就是 100 ms。Pipeline 把命令缓冲后一次发送，Redis 顺序执行后一次返回；go-redis 用 pipe := rdb.Pipeline() 逐条调用，最后 pipe.Exec() 提交。

注意两点：Exec 只返回第一个错误，逐条结果仍要检查，批量读里的 redis.Nil 属于正常情况；批量不是越大越好，过大的 pipeline 会占用客户端内存，也让 Redis 在处理期间无法服务其他请求，每批 100 到 500 条为宜。TxPipeline 用 MULTI/EXEC 防止插队，但没有回滚，不要拿它当关系型数据库的事务。

容量、可观测性与常见坑

缓存可以丢，但要先算清回源压力：全部失效时数据库能否承接？RDB 适合缓存，恢复快，但 fork 的写时复制会额外占内存，maxmemory 不要贴着物理内存，通常留 25% 到 30% 余量。AOF 的 everysec 最多丢一秒数据，代价是持续磁盘写入；纯缓存一般不必开启。

淘汰策略要与数据性质匹配：allkeys-lru 适合纯缓存；allkeys-lfu（Redis 4.0 起）按访问频率淘汰，对热点更友好；混了不能丢的 key 时用 volatile-lru，并确保它们都有 TTL；noeviction 写满就报错。maxmemory 必须设置，否则会一直吃到系统 OOM。

监控至少看四项：命中率、延迟、错误率、连接池等待。命中率由 INFO stats 的 hits 与 misses 算出，长期低于 90% 就要查 key 设计与 TTL；延迟看 redis-cli --latency 与慢查询，p99 超过 10 ms 先查大 key 与 KEYS；错误率包括超时与 WRONGTYPE；连接池看 PoolStats() 的 Timeouts 与等待次数。这些数字可以作为告警阈值的起点。

常见坑：同一 key 用了不同类型会得到 WRONGTYPE；忘记 TTL 会让内存缓慢上涨；大 key 在删除、迁移、传输时造成尖峰，用 redis-cli --bigkeys 排查并拆分；锁超时短于业务耗时会失去互斥；把 Redis 当消息队列也要谨慎，LPUSH 加 BRPOP 在消费者崩溃时丢消息，5.0 的 Stream 有消费组与 ACK，但堆积与持久化仍不如专业消息队列。

小结

缓存设计的关键不是记住命令，而是承认它只是副本：数据要能从权威源重建，失效要能兜底，故障要能降级。连接池按量估算，读写走 cache-aside 并优先删除缓存，TTL 加抖动，热点与批量用本地缓存和 Pipeline。穿透、击穿、雪崩各有手段，但没有一种能同时满足强一致与高可用；强一致读请回到数据库。
