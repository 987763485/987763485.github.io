安全加固：Linux 基线配置

等保 2.0 已于 2019 年 12 月 1 日正式实施，许多团队第一次被要求拿出主机基线的配置证据。本文面向需要在 CentOS 7 与 Ubuntu 18.04 上亲手落地的运维和后端工程师，给出一份可以照着做的清单：每一项说明改什么、为什么改、怎么验证，并附上可直接复制的配置片段。主机加固的方法论此前已有专文讨论，本文不再重复推导，只把操作层面的细节摊开。

基线的意义与落地流程

基线是一组经过评审、版本固定的最低安全配置。它的价值不在于某一条参数有多神奇，而在于所有机器在同一套标准下运行，出问题时可以对照、可以复现、可以审计。对等保 2.0 而言，身份鉴别、访问控制、安全审计、入侵防范这些层面的要求，最终都要落到具体的配置文件上；检查人员看的是 sshd_config 里的那几行和验证记录，而不是口号。

落地流程可以概括为五步，缺一步都会留下隐患：

flowchart TD
    A[资产盘点] --> B[选择基线]
    B --> C[配置实施]
    C --> D[验证与取证]
    D --> E[变更管理]
    E --> B

资产盘点要回答三个问题：有哪些主机、跑什么业务、谁负责。没有清单，基线就只能抽样，漏掉的那台往往就是入口。基线选择要结合发行版与业务角色，Web 服务器和数据库服务器关注的项并不相同，但账户、SSH、审计这些公共项必须一致。配置实施尽量交给配置管理工具或版本化脚本，而不是登录上去手敲。验证与取证是基线的另一半，每一项都要有对应的检查命令和输出留档。变更管理保证基线本身也会演进：内核升级、业务上线都会让旧条目失效，文档要有版本号和变更记录。

需要强调的是，基线不是一次性脚本。机器会漂移，新机器不断加进来，半年后回头看，总有人为了排查问题临时改过参数。务实的做法是把检查脚本接入日常巡检和上线流程，让偏离在当天被发现，而不是等测评前突击。

账户与口令

账户是第一道门。先盘点能登录的账户：

对离职人员、测试账号、共享账号，该删的删，该锁的锁。系统账户要区分对待：daemon、bin 这类只需要 nologin，而 nobody 不应拥有家目录。锁定可以用 usermod -L 配合 -s /usr/sbin/nologin，但要注意有些服务账户需要 shell 才能切换，改之前先确认依赖，不要一刀切。

文件权限是最便宜的一道防线：/etc/passwd 应为 644，/etc/shadow 与 /etc/gshadow 应为 000 或 640，属主属组为 root。很多人只记得改 shadow，却忘了备份文件 shadow- 与 passwd-，它们同样包含口令散列。

口令策略分两层：login.defs 管有效期与长度下限，PAM 管复杂度与失败锁定。

pwquality 在 CentOS 7 与 Ubuntu 18.04 上都可用，替代了老的 pam_cracklib。失败锁定用 pam_faillock：CentOS 7 可通过 authconfig --enablefaillock --faillockargs="deny=5 unlock_time=900" 打开，Ubuntu 18.04 默认仍是 pam_tally2，需要在 /etc/pam.d/common-auth 中配置。锁定策略要同时考虑运维自己：deny 设得太小，一次误操作就会把值班人员挡在门外，通常 5 次、锁定 15 分钟是折中的起点。

root 直接登录要限制。SSH 层用 PermitRootLogin no，控制台层用 /etc/securetty 只保留 tty1，日常操作通过普通账户加 sudo 完成。这样审计日志里才有具体的人，而不是一片 root。

SSH 加固

SSH 是暴露面最大的服务，也是最容易把自己锁在门外的服务。建议的顺序是：先配好密钥登录并验证，再关闭口令认证。生成密钥用 ssh-keygen -t rsa -b 4096，把公钥写入目标账户的 ~/.ssh/authorized_keys，文件权限 600，目录 700。私钥要设口令，不能放在共享目录；离职人员离职当天就要从 authorized_keys 中移除。

几个细节值得说明。AllowUsers 与 AllowGroups 二选一即可，用组更利于人员变动时批量维护；写 AllowUsers 时格式是“用户@来源地址”，写错会导致全员被拒。改端口只能减少扫描噪音，不能替代认证加固，防火墙规则要同步放行新端口。登录横幅用于满足告知义务，内容不要泄露系统版本。UseDNS no 可以避免反向解析拖慢登录。

改完不要急着重启：

reload 不会断开已有会话，这正是我们需要的窗口：保留当前连接，另开一个终端用新配置登录验证，确认无误再退出。若只改了文件没有 reload，配置根本不会生效，这是最常见的“改了但没用”的原因。

sudo 与文件权限

sudo 的目标是让每个人用自己的账户完成必要操作，而不是共享 root 口令。最小权限的落地方式是分组加命令白名单：

NOPASSWD 的风险常被低估：一旦该账户被入侵，攻击者无需口令即可执行白名单内的命令，而 systemctl 这类命令往往能间接读写任意文件。因此 NOPASSWD 只应给自动化账户，白名单要写全路径、避免通配符，改完用 sudo -l -U deploy 核对实际授权。sudoers 只能用 visudo 编辑，它在保存时做语法检查；直接改文件写错一个逗号，可能让所有人失去 sudo。

文件权限方面，除了前面的 passwd 与 shadow，还要关注 /etc/sudoers（440）、SSH 主机私钥（600）、authorized_keys（600）、/etc/crontab（600）。SUID/SGID 程序是提权常用的跳板，应定期盘点并与软件包清单比对：

发现不属于任何软件包的 SUID 文件，先隔离再分析。临时目录挂载时加上 noexec、nosuid、nodev，可以挡掉一类“上传后执行”的攻击；umask 统一设为 027，避免新建文件默认对其他用户可读。Web 目录的属主应为运行账户，权限从 750 起步，任何情况下都不该出现 777。

服务最小化与内核参数

服务最小化靠两张表互相印证：一张是开机自启清单，一张是监听端口清单。

两张表对不上，就说明有服务被 socket 激活或由其他进程带起来。端口清单要定期重跑，容器映射和临时调试最容易留下意外的监听。关闭前先确认业务依赖，telnet、rsh、ftp 这类明文协议应直接卸载而不是只停服务；不确定的先用 systemctl disable --now，观察一周再决定是否卸载。对于会被 socket 激活的单元，disable 不够，需要 mask。

内核参数解决的是网络栈层面的常见攻击面：

rp_filter 严格模式在非对称路由环境下会误丢包，多网卡或策略路由的机器要先测试。ip_forward 默认为 0，但装了 Docker 或做 NAT 的机器必须为 1，照抄配置会打断容器网络。kptr_restrict 在 CentOS 7 的 3.10 内核上取 1 即可。写入文件后执行 sysctl --system，再逐项读回验证；只改 /etc/sysctl.conf 而不放进 sysctl.d，容易和云镜像自带的配置互相覆盖。

审计、SELinux 与防火墙

审计规则要围绕“谁改了账户、谁提了权、谁动了关键文件”来写：

用 augenrules --load 加载，auditctl -l 查看。最后一行 -e 2 把规则设为不可变，重启前无法修改，适合生产环境，但调试阶段要先注释掉。全量 execve 审计能记录命令执行，代价是日志量成倍增长，磁盘和性能都吃不消，建议只对关键目录或特定用户做定向审计。日志轮转在 /etc/audit/auditd.conf 中配置，max_log_file 与 num_logs 要按留存要求算容量，space_left_action 至少设为 syslog，避免磁盘写满后系统不可用。

SELinux 的取舍很简单：能 enforcing 就不要停在 permissive。遇到拒绝先看审计日志，用 audit2why 判断原因，用 restorecon 修复上下文，用 semanage fcontext 增加自定义路径规则，确实需要放行再用 audit2allow 生成最小策略。setenforce 0 只应出现在排障的几分钟里，改完必须切回并记录。Ubuntu 18.04 默认用 AppArmor，思路相同：aa-status 看状态，aa-complain 临时放宽，规则改好后切回 enforce。

防火墙要默认拒绝、按需放行：

运行时规则和永久规则是两套：只加 --permanent 不 reload 不生效，只加运行时规则 reload 后会丢。业务上线新增端口时，防火墙变更要和发布单一起走，否则第二天凌晨就会出现“服务正常但连不上”。

补丁、时间同步与日志

补丁策略的核心是节奏而不是速度。每月固定一个安全更新窗口，先在测试环境验证，再分批推到生产。CentOS 7 用 yum update --security 配合 yum-plugin-security 只装安全更新，Ubuntu 18.04 用 unattended-upgrades 处理 security 源。内核更新需要重启才生效，kpatch、kgraft 这类热补丁只能覆盖部分漏洞，不能替代重启窗口，也不能当作长期方案。更新后用 uname -r 与 rpm -q kernel 核对实际运行版本，别只看安装列表。

时间同步常被忽略，但日志检索、证书校验、认证协议都依赖它。chrony 是 CentOS 7 与 Ubuntu 18.04 的默认选择：

内网环境应指向内部 NTP 源，并限制服务器只允许内网客户端访问，避免成为反射放大的一环。偏差超过秒级就要查链路和配置，而不是简单重启服务。

日志方面，CentOS 7 的登录日志在 /var/log/secure，Ubuntu 18.04 在 /var/log/auth.log。journald 默认可能只存在内存，重启即丢，应在 /etc/systemd/journald.conf 中设置 Storage=persistent 与 SystemMaxUse=2G。重要日志要外送，rsyslog 用 @@ 走 TCP 转发到日志服务器，本地留存只是第一份，日志服务器本身也要做访问控制，否则集中存放反而扩大了泄露面。《网络安全法》要求网络日志留存不少于六个月，容量规划要按这个下限倒推。

用只读脚本做基线验证

基线的验证脚本必须只读：不写文件、不改服务、不执行 setenforce 0 和 iptables -F 这类动作。检查项输出统一格式，退出码约定 0 为通过、1 为存在不符合项、2 为用法或环境错误，方便接入 CI 与监控。

脚本里所有判断都基于读取，跑一百遍也不会改变系统状态。建议把检查项按账户、SSH、权限、网络、审计分组，输出 JSON 或固定分隔符文本，接入现有巡检平台。阈值和期望值不要写死在脚本里，抽成配置文件，基线换版本时只改配置。

变更、回滚与常见坑

改 SSH 之前，先给自己留后路：保持当前会话不退出，另开一个会话验证新配置，确认能登录后再关旧的；同时确认带外管理可用，比如云控制台的 VNC 或机房的 KVM，这是被锁在门外时唯一的救生通道。配置文件先备份再改，备份名带日期，回滚就是覆盖回去再 reload。变更窗口尽量避开业务高峰，涉及登录方式的改动最好安排在有人值守的时段。

灰度同样适用于基线：先改一台边缘机器，观察一天，再按批次推进。用配置管理工具下发，比逐台登录可靠；至少也要保证脚本入库、有版本号、有执行记录。回滚步骤要提前写进变更单：恢复备份、sshd -t 校验、reload、从第二个会话验证、检查 /var/log/secure 有没有异常。回滚不是失败，拖着不回滚才是。

最后列几个反复出现的坑。改完 SSH 没有 reload，配置停留在文件里；sysctl 只写了临时命令，重启后全部丢失；SELinux 一出问题就 setenforce 0，久而久之 enforcing 形同虚设；审计规则开了全量命令执行，几天后磁盘告警；firewalld 只加了运行时规则，reload 后端口又关了；只改了一台机器，其余机器继续裸奔。这些问题的共同点不是技术难度，而是缺少验证和变更记录。

还有一个容易被忽略的坑是配置冲突：/etc/sysctl.conf、/etc/sysctl.d/*.conf 与云厂商初始化脚本可能同时写同一个键，后加载的覆盖前面的；而 sshd_config 恰好相反，同一指令重复出现时以第一次为准，把新行追加到文件末尾常常不生效。每次变更后用 sshd -T、sysctl -n 读回实际值，比盯着文件可靠。

小结

Linux 基线配置没有一招制敌的银弹，它是一组互相支撑的小事：账户收紧、SSH 只留密钥、sudo 按需授权、权限与 SUID 定期盘点、服务与端口对得上账、内核参数持久化、审计与防火墙形成闭环。等保 2.0 实施之后，这些配置不再只是“最佳实践”，而是需要留痕的证据。建议的推进顺序是先堵入口（账户与 SSH），再收敛权限（sudo 与文件），然后做服务与内核收敛，最后补齐审计、日志与验证脚本。如果只能先做三件事，那就是关掉口令登录、管住 sudo、把检查脚本跑起来。把检查脚本接入上线流程，基线才不会在半年后变成一纸空文。
