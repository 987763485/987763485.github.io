越权访问与逻辑漏洞

很多系统把登录做得很严密，却在登录之后失守：用户 A 能看到用户 B 的订单，普通员工能调用管理员接口，一分钱的商品能下单成功。问题很少来自密码学缺陷，多是服务端把该自己判断的事交给了客户端。本文讨论越权与逻辑漏洞的共同成因、检测思路与修复模式。文中请求与代码均来自自建实验环境，账号与数据均为虚构；测试以书面授权和明确范围为前提。

一、共同成因：认证不等于授权

认证回答“你是谁”，授权回答“你能做什么”。登录成功只证明身份真实，不证明有权访问某个订单、某个租户的数据，或执行某次状态迁移。越权与逻辑漏洞的根源，多是服务端在某个环节信任了客户端的输入或状态。

常见的信任错误有四类：信任对象标识，请求带了订单号就默认它属于当前用户；信任身份字段，直接采用前端传来的 role、user_id；信任业务数值，价格、数量、折扣由客户端提交；信任次数与顺序，默认操作只发生一次、回调一定来自支付平台。

前端校验与隐藏按钮只能提高门槛，不能构成授权。系统是否可靠，要看它在最坏输入下是否仍只做规则允许的事。

二、水平越权：归属校验缺失

水平越权是相同角色的用户访问彼此的资源，典型形式是 IDOR，即不安全的直接对象引用。订单、消息、发票、附件下载，只要请求里出现资源标识，就可能成为入口。问题常出在查询只按主键取数：

把 1001 改成 1002，若接口仍返回 200，越权即成立。自增 ID 便于枚举，UUID 只是难猜，并不改变缺少归属校验的事实。

授权实验中用两个自建账号做最小验证：A 创建测试订单并记录编号，B 登录后用自己的会话请求 A 的订单，只改标识，不遍历、不下载：

返回 200 且带有 A 的收货信息即可确认；返回 403 或 404 时，还要排除前端拦截或 WAF 误伤。批量接口同样要查，ids=1001,1002 可能一次带出多条他人记录。修复的关键不是把 ID 换得更难猜，而是让查询条件包含当前主体。

三、垂直越权：角色边界形同虚设

垂直越权是低权限用户执行高权限操作，例如普通用户调用管理接口、客服查看财务报表。它常与“前端隐藏”同时出现：菜单里没有“用户管理”，接口地址却仍可被直接请求。

菜单权限和接口权限是两套东西。菜单决定界面可见性，接口决定数据与动作。另一个缺口是“登录即放行”：控制器只校验会话有效，没校验角色；角色判断写在前端路由，后端默认信任。

若返回用户列表，说明接口缺少角色校验。还要检查导出、旧版本与内部调用接口，往往只有主入口加了注解。修复上，管理接口应有独立鉴权并默认拒绝，网络隔离只是纵深防御。

四、参数篡改：客户端数值不可信

参数篡改是把请求当作可编辑的表单，常见位置有 URL 查询串、请求体、请求头（如 X-User-Id、X-Role）、Cookie 与隐藏字段，被改的通常是价格、数量、角色与状态。

把 price 改为 1、quantity 改为 -1，是必须验证的边界。负数量可能让金额变成负数，进而触发退款；角色从 user 改为 admin 则可能直接提权。测试只在自建环境使用测试商品与账户。

客户端校验只改善体验，不能作为安全边界。服务端应白名单绑定字段，价格从商品表读取，优惠按规则计算，身份从会话解析；请求体中的 user_id、role、status 一律忽略。

五、业务流程漏洞：规则没有闭环

业务逻辑漏洞不依赖特殊字符，而是让系统按攻击者期望的顺序执行。常见形态有状态机跳步、支付回调伪造或重放、优惠券重复领取、退款金额篡改。

状态机跳步的典型表现是：系统设计了待支付、已支付、已发货、已完成、已取消，接口却只检查当前状态是否在允许集合里，没有检查从哪来、到哪去，于是取消后的订单仍可发货，未支付订单可直接完成。

支付回调的问题通常在三处：没有验签或密钥硬编码；回调金额与订单号没有和本地记录核对；同一回调可重复消费，导致重复入账。优惠券常见领取接口没有唯一约束，退款金额若取自请求体而非订单与支付记录，就可能被改大。

每一条虚线都应对应一条服务端拒绝规则。回调处理还应记录外部流水号，保证同一笔支付只迁移一次状态。

六、竞态条件：并发下的“只允许一次”

“只能领一次”“余额不能为负”“库存不能超卖”，这些规则在单请求下成立，在并发下却可能失效。典型模式是先查询再写入：两个请求同时读到余额 100，各自判断足够并扣款，最终余额为 -100。这是检查与使用之间的时间差。

授权环境中，可用测试工具对同一合法请求并发发送若干次，观察是否只成功一次。重点看领券、扣款与扣库存三类接口，并限制并发数与次数，避免影响共享环境。

七、权限模型：RBAC、ABAC 与最小权限

权限设计先回答两个问题：功能权限与数据权限分别由什么决定。RBAC 用用户、角色、权限点描述“能不能做某个操作”，适合菜单与接口；ABAC 用属性描述“能不能对某个资源做某个操作”，属性可来自部门、租户、资源密级与时间。真实系统往往混用：接口用 RBAC 控制入口，数据范围用归属与租户属性过滤。

资源归属是最基本的数据权限。订单有 owner_id，文档有 creator_id，数据表有 tenant_id，所有读写都应在查询层带上这些条件，多租户系统尤其要防止只按主键查询。

最小权限要求用户、服务账号与数据库账号都只拥有完成工作所需的权限。校验位置同样重要：控制器适合入口检查，真正的裁决应放在服务层或数据访问层，因为同一动作可能被 HTTP 接口、定时任务、消息消费者触发。默认拒绝、显式放行，是模型长期可维持的前提。

八、检测方法：矩阵、清单与手工验证

检测这类问题靠的不是扫描器，而是结构化的手工验证。先建立角色矩阵：未登录、普通用户 A、普通用户 B、客服、运营、管理员，逐行列出权限边界。再建立接口清单：从路由配置、前端脚本、抓包记录中收集接口，记录方法、路径、参数、所需角色与资源类型。

然后才是改包。用 Burp Suite 拦截，保持会话不变，每次只替换一个变量：对象 ID、角色字段、状态值、金额或数量。观察状态码、响应长度与关键字段，判断服务端是否重新做了判断。不要只看 200 或 403，有些系统会用 200 返回“无权限”的 JSON。

参数枚举要有边界。只测相邻、自己的、不存在的与格式非法的 ID，不按顺序遍历，不下载数据。批量遍历容易触发告警，也可能构成过度访问，超出授权范围。日志中同一账号短时间请求大量不同对象 ID，或大量 403 后突然出现 200，都值得复核。检测结束后，把过程、请求样本与结论写入记录。

九、修复模式：让校验贴着数据走

修复优先改服务端。

统一鉴权与默认拒绝。网关做粗粒度拦截，服务做细粒度判断，未声明权限点的接口默认不可访问；权限点按“资源 + 动作”命名，如 order:read、refund:approve。

资源归属查询。读取单条资源时把当前主体写进查询条件，查不到返回 404，避免用 403 暴露资源是否存在：

状态机校验。把允许的迁移写成表，执行前检查当前状态、目标状态与操作者，并用版本号做乐观锁。

幂等与金额服务端计算。支付、退款、发券接收客户端请求号，服务端落唯一索引并复用首次结果；金额以订单快照与支付记录为准，用整数分计算。

敏感操作二次确认。改密、换绑手机、大额退款、删除数据，要求重新认证或二次审批，并记录操作者、时间、对象与结果。这些模式的共同点，是校验贴着数据走，和写入处于同一事务边界。

十、测试用例设计：四类用例覆盖一个接口

对每个涉及资源的接口，至少设计四类用例：他人资源、越权角色、非法状态、重复提交。

用例类型 构造方式 期望结果
他人资源 用 B 的会话请求 A 的对象 ID 404 或 403
越权角色 普通账号请求管理接口 403，无副作用
非法状态 对已取消订单发起支付 409，状态不变
重复提交 同一请求号提交两次 只产生一条记录

以订单为例：用 B 的令牌访问 A 的订单，用普通令牌调用退款审批，对已取消订单发起支付，用同一 request_id 连续提交两次退款。每条用例都要记录请求、响应与数据变化。

修复后的回归要跑完整矩阵。同一漏洞常有变体：URL 参数换成请求体、单条换成批量、主接口换成导出。新增接口应纳入清单，回归脚本只重复验证已知用例。

十一、报告与复测：把风险说清楚

测试前先确认授权：书面委托、时间窗、域名与 IP 范围、可用账号与禁止事项。范围之外不碰，发现越界立即停止并告知；测试数据使用自建账号与虚构商品，结束后清理。

报告应包含标题、风险等级、影响面、前置条件、复现步骤、证据与修复建议。风险等级由可能性与影响共同判断，影响面写清涉及的角色、数据与资金。

复现步骤必须无害：只改一个参数，只读取一条测试数据。证据中的令牌、手机号、身份证号要脱敏；未修复细节不公开发布，通过约定渠道提交。

复测按清单执行：原用例、同参数换位置、正常流程、日志记录。只有原用例与主要变体都被拒绝、业务功能正常，才可关闭问题。

十二、常见误区

只靠前端隐藏。隐藏菜单、禁用按钮只是界面变化，接口仍然开放。

只校验登录，不校验归属。会话有效只说明“你是某个用户”，不说明“这个资源属于你”。

把 UUID 当权限。UUID 难以枚举，但一旦通过链接、日志或导出泄露，缺少归属校验的系统仍会被访问。

日志记录敏感参数。把令牌、密码、身份证号、完整请求体写进日志，等于把越权影响再放大一次；日志应记录主体、对象、动作与结果，敏感字段脱敏。

小结

越权与逻辑漏洞的共同点，是服务端把判断权交给了客户端。防御的核心不是把 ID 藏起来，而是让每次访问都在服务端重新回答：你是谁、资源属于谁、当前状态允许做什么。把归属条件写进查询，把状态迁移写成表，把金额与幂等交给服务端，再配合多角色矩阵与四类用例的回归，大多数问题都能在上线前发现。测试始终在授权范围内进行，修复后按清单复测。
