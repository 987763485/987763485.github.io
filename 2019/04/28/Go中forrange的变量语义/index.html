Go 中 for range 的变量语义

本文属于《Go 语言与工程》第 49/78 篇
上一篇系列目录下一篇

for k, v := range x 大概是 Go 里写得最多的一行代码，正因为太顺手，很多人从没想过 k 和 v 到底是什么。本文要回答的就是这个看似细小、实际会影响并发正确性的问题：循环变量是每轮新建，还是自始至终只有一组？想清楚这一点，才能解释为什么循环里启动的 goroutine 总是打印最后一个值、为什么把 &v 收集起来会得到一串相同地址。本文面向已经能写 Go 循环、但还没仔细读过 range 语义的读者，读完后你应该能判断什么时候必须显式复制变量，以及 range 后面的表达式在何时被求值。

先说结论：复用的是同一组变量

在本文所面对的 Go 1.12 里，for k, v := range x 中的 k 与 v 只在循环开始前声明一次，之后的每一轮都是往这两个变量里重新赋值。换句话说，循环体里看到的 k、v 是同一块内存，只是其中的内容被一轮一轮覆盖。这与 C 语言三段式循环的直觉不同，常被从其他语言转过来的开发者忽略。

range 后面的表达式只求值一次

除了变量复用，range 还有一条容易被忽略的规则：range 关键字后面的表达式在循环开始之前求值一次，求值结果会被保存下来供整个循环使用。循环体里再去修改这个表达式里的变量，并不会让循环换一个对象继续遍历。

map 与 channel 的处理方式又不一样。range 一个 map 时，表达式求值得到的是 map 的引用，运行时会创建一个迭代器，循环过程围绕这个迭代器推进；range 一个 channel 时，保存的是 channel 的引用，每轮从里面接收一个值。它们都不会复制容器里的数据。

不同被遍历类型的行为差异

range 能作用在数组、数组指针、切片、字符串、map 和 channel 上，每一种的取值规则都值得单独记一笔。

数组与切片都按索引从小到大推进，循环次数以开始时的长度为准。

字符串的 range 按 UTF-8 解码，第一个返回值是当前字符首字节的下标，第二个返回值是 rune 类型的码点。下标不是“第几个字符”，而是字节偏移：

输出中 G 与 o 各占一个字节，空格占一个字节，语 的下标是 3，言 的下标是 6，而 len(s) 是 9。如果想按字节遍历，应当写普通的 for i := 0; i < len(s); i++，此时 s[i] 是 byte。遇到非法 UTF-8 序列时，range 会产出 U+FFFD 替换字符，并只前进一个字节，这一点在处理来路不明的文本时要留意。

map 的遍历顺序是随机的：运行时在每次 range 开始时随机选择起始桶与桶内偏移，同一个 map 连续遍历两次顺序通常不同，程序不应依赖固定顺序。需要有序输出时先取 key 排序：

channel 的 range 形式只接收一个值，循环会一直阻塞等待，直到 channel 被关闭；关闭之后缓冲区里剩余的值仍会被取完，然后循环正常结束。如果 channel 从未关闭，循环就永远不会退出；如果 range 的是 nil channel，则会永久阻塞。写代码时通常由发送方负责关闭，接收方不要关。

最后是整数。在 Go 1.12 中，for i := range 10 这样的写法是编译错误，range 只接受数组、切片、字符串、map 与 channel。想循环固定次数，只能老老实实写 for i := 0; i < 10; i++。这一点常被其他语言的习惯带偏，遇到编译错误时不必怀疑语法，直接改成三段式即可。

遍历时修改容器会怎样

既然 range 表达式只求值一次，那么“边遍历边修改”的效果就完全取决于被修改的是副本还是共享的底层数据。

切片是最常被修改的。循环体里给 nums[i] 赋值会直接落到共享的底层数组上，后续轮次读到的 v 也会是修改后的值；而 append 出来的新元素不在循环开始时的长度范围内，本轮循环看不到。如果 append 没有触发扩容，新元素其实写进了同一块底层数组，只是循环的长度已经固定，仍然不会多跑。

数组则相反：range 拿到的是副本，改副本不会影响原数组，只有改 arr[i] 才落到原数组上；而 v 始终来自副本，把数组当固定长度缓冲区用时尤其要留意这一点。

map 允许在 range 过程中删除 key。删除一个尚未遍历到的 key，它不会再被产出；删除已经遍历过的 key 则没有影响。新增 key 的行为则没有保证：新 key 可能出现在后续迭代里，也可能完全被忽略。因此“一边 range 一边往 map 里塞数据”不是可靠的遍历方式，需要新增时应当先收集到临时切片，循环结束后再合并。

只要值、不要键：for range 与 _

range 的常见形式有三种。for i, v := range x 同时要下标和值；for i := range x 只要下标，此时第二个返回值被直接丢弃，不再逐元素复制到 v；for range x 两个都不要，只用来驱动循环次数或等待 channel 关闭。map 与 channel 同理，第一个返回值换成 key 或没有。

不过更地道的写法是直接省略第二个变量，写成 for i := range items。下划线在这里的作用是占位，它不创建可用变量，也不会因为“未使用”而报错；但 for _, _ := range items 这种两个都是下划线的写法会触发 no new variables on left side of :=，两个值都不要时应当写 for range items。

复制成本与编译器优化

v 是元素的副本，这一点决定了 range 的性能特征。每轮循环都要把元素复制进 v，成本大致等于元素类型的大小：int、float64 这类小值几乎无感；string 与 interface{} 复制的是头部，字符串底层字节不会被复制；而包含多个字段的大结构体，每轮都是一次实打实的按值复制。

逃逸分析会进一步放大这个问题。只要 v 的地址逃出本轮循环，比如存进切片、交给 goroutine 或被闭包捕获，编译器就无法再把它放在栈上，只能分配到堆。由于变量是复用的，整个循环只产生一个堆对象，所有保存下来的指针都指向它；这既造成别名问题，也让这个对象一直存活到最后一轮结束。改成 v := v 之后，每轮各有一个对象，逃逸的规模才与轮次对应。用 go build -gcflags=-m 可以看到 moved to heap 之类的提示，帮助定位是哪个变量逃逸了。

几个反复出现的坑

第一个是循环里的 defer。defer 只是把调用推迟到函数返回，并不会把参数以外的执行环境一起冻结：

如果希望每一轮的值都被正确记录，同样要用参数传入或 v := v。顺带区分一种情况：defer f.Close() 的接收者在 defer 语句执行时就已求值，每轮关闭的是各自的文件，值不会串；但关闭都堆到函数结束，循环里打开大量文件会耗尽描述符，这类资源应放进立即执行的函数里处理。

第二个是误以为改 v 能改容器。for _, v := range s 中的 v 是副本，给它的字段赋值不会影响 s 里的元素，调用以值接收者声明的方法也一样。要修改元素，必须写 s[i].Field = ...，或者让切片存放指针。

第三个是依赖 map 的遍历顺序。把 map 直接 range 后拼接成 JSON、拼 SQL、做测试断言，输出都可能抖动。需要稳定结果时先排序 key，测试里也不要假设顺序。

第四个与并发有关。循环里启动的 goroutine 若写共享变量，需要加锁或用 channel 传结果；变量复用带来的别名会让竞争更难排查，开发期用 -race 跑测试能省不少时间。

关于“每轮新建变量”的讨论

循环变量复用带来的困惑实在太多，社区里一直有提案希望把它改成每轮新建，让闭包捕获到各自的值。这里需要明确：这个变更并没有发生在 2019 年，本文面对的 Go 1.12 仍然是复用语义；按后来公开的版本计划，直到 Go 1.22 才真正改为每轮新建变量。在升级到那个版本之前，代码必须按本文描述的复用语义来写，v := v 之类的防御也不能省。

小结

range 的循环变量在 Go 1.12 中只声明一次，每轮覆盖同一个对象，这直接决定了闭包捕获与取地址的结果。range 后的表达式在循环开始前求值一次：数组被整体复制，切片只复制头，map 与 channel 只保存引用；循环中 append 或重新赋值都不会改变循环次数。字符串按 UTF-8 解码、map 顺序随机、channel 依赖关闭、整数不可 range。写并发代码时，用 v := v、参数传值或索引重取保证一轮一份；大结构体优先用索引取地址，避免不必要的复制与逃逸。把这些规则记牢，比记住几个坑的结论更管用。
