Python 虚拟环境与依赖管理

本文属于《Python 学习路线》第 10/29 篇
上一篇系列目录下一篇

Python 的依赖管理看起来简单，真正落到多人协作和线上部署时却处处是坑：版本冲突、解释器混用、环境无法复现。本文从这些具体问题出发，讲清 venv 与 virtualenv 的用法和差别，梳理 requirements.txt 的写法与分层组织，再讨论锁定、哈希、私有源以及 pipenv、poetry 这类项目级工具的取舍。读者读完应当能为一个 Python 3.7 项目搭出一套可复现的依赖流程。

从全局环境说起：三个具体问题

多数人第一次接触虚拟环境，都是被一个具体问题逼过来的。项目 A 依赖 requests 的早期版本，项目 B 的新代码用到了后来才加入的参数，两者装在同一个全局 site-packages 里，后装的覆盖先装的，于是总有一个项目在别人的机器上跑不起来。这类冲突不会在安装时报错，只在运行时以奇怪的方式暴露。

第二个问题是解释器混用。开发机上往往同时存在系统自带的 Python、包管理器安装的 Python、pyenv 管理的 Python。pip 属于哪一个 Python，取决于 PATH 的先后顺序；python 又可能是另一个。于是出现“明明装了包，导入却报找不到模块”的现象——包装进了 A 解释器，脚本却由 B 解释器执行。

第三个问题出现在交付环节。开发机上经过若干次随手安装之后，环境里究竟有什么、版本是多少，谁也说不清。把代码拷到测试机，缺什么装什么，装到能跑为止；上线时再重复一遍。这样的“能跑”既不可复现，也无法审计，回滚时更是不知从何下手。

三个问题的共同根源是：Python 默认把第三方包装在解释器自己的 site-packages 目录里，而这个目录对所有项目共享。虚拟环境做的事情很朴素——为每个项目准备一份独立的 site-packages 和一组独立的命令入口，项目之间互不干扰。

flowchart TD
    A[一台机器] --> B[全局解释器 site-packages]
    B --> C[项目 A 依赖 1.x]
    B --> D[项目 B 依赖 2.x]
    C --> E[后装者覆盖先装者]
    D --> E
    E --> F[运行时报错]
    A --> G[项目 A 的 .venv]
    A --> H[项目 B 的 .venv]
    G --> I[各自独立，互不影响]
    H --> I

解释器路径与命令的对应关系是最容易出错的地方。环境里的 python 是一个符号链接或小型启动器，它通过 pyvenv.cfg 找到基础解释器，再把包搜索路径指到环境内部。所以“激活”本质上只是修改 PATH，让 shell 优先找到 .venv/bin 下的命令。IDE、cron、supervisor 这些不经过交互式 shell 的地方不会自动激活，必须写绝对路径，例如 /path/to/.venv/bin/python。

.venv 不应入库，写进 .gitignore 即可。理由有三：目录里是平台相关的二进制和绝对路径，换台机器就失效；体积不小；内容完全可以由依赖声明重新生成。与之相对，依赖声明文件必须入库，另外建议在 README 里写明基础 Python 版本，或者用 pyenv 的版本文件固定。还有一点：venv 目录不要移动或改名，入口脚本与 pyvenv.cfg 里记着创建时的绝对路径，搬走之后表面能跑，实际指向旧位置。

venv 与 virtualenv 的差别

2019 年 virtualenv 仍然是常见选择，版本在 16.x。两者目标一致，差异在实现与覆盖面。virtualenv 是第三方包，需要先安装，但它创建环境更快，因为预置了打包好的种子文件，不必每次都走一遍安装流程；它还能用 -p 指定任意已安装的解释器，并照顾 Python 2.7 这类老版本。venv 来自标准库，开箱即用，但只能用当前这个解释器创建环境，早期版本在细节选项上也不如 virtualenv 灵活。

选择上不必纠结：新项目、纯 Python 3.7 环境，用 venv 就够了，少一个依赖；需要同时维护 Python 2 项目、需要在一台机器上批量创建多个版本的环境，或者团队已有统一脚本，继续用 virtualenv 完全合理。

requirements.txt：把依赖写下来

虚拟环境解决“装在哪里”，依赖文件解决“装什么版本”。requirements.txt 的格式极简：一行一个依赖，# 开头为注释，空行忽略，也可以在文件里用 -r 引用另一个文件。

三种版本约束要分清。== 精确匹配，是部署时最想要的写法；>= 只给下限，最终装到什么版本取决于安装当天的索引内容，等于把不确定性推迟到最后一步；~= 是兼容发布约束，~=1.3.0 等价于 >=1.3.0 且限定在 1.3.*，允许补丁级升级，不允许升到 1.4。宽松的约束适合开发期快速迭代，锁定则留给交付环节。

pip freeze 的用途是把当前环境里所有已安装包按 == 导出，相当于给验证过的环境拍照。局限也同样明显：它导出的是整棵依赖树，间接依赖被逐一钉死，日后升级某个直接依赖时冲突排查更麻烦；它会把以 -e 方式安装的本地路径或 Git 地址原样写进去，换台机器就失效；在 Windows 上冻结出来的文件常常带着平台专属的包，拿到 Linux 上装不上。

更稳妥的做法是把两件事分开：手写一份只列直接依赖的清单（有的团队命名为 requirements.in），在干净环境里安装并测试，再用 pip freeze 生成锁定文件供部署使用。当时已有 pip-tools 这类工具可以把这一步自动化。

分层依赖：把测试与文档挡在生产之外

一个项目的依赖其实分几层：运行时必需、开发与测试使用（pytest、flake8、black、ipython）、构建文档使用（Sphinx）、打包发布使用（wheel、twine）。混在一个文件里，最直接的后果是生产镜像里多出几十个用不到的包，镜像变大、构建变慢，攻击面也随之变大。

如果项目本身要发布成包，还有另一种表达方式：在 setup.py 的 extras_require 里声明 dev、docs 等可选组，使用者用 pip install -e ".[dev]" 一次装齐。两种方式可以并存，requirements 文件更适合应用型项目，extras 更适合库。

安装、缓存与镜像源

pip install -r requirements.txt 是日常使用频率最高的命令。它按文件顺序解析、下载、构建、安装；中途某一行失败时，前面的包已经装上，环境处于半成品状态。所以脚本里应当让出错即停，失败后从干净环境重来。

pip 默认把下载的包缓存在本地，Linux 在 ~/.cache/pip，macOS 在 ~/Library/Caches/pip，Windows 在用户目录下的 pip 缓存目录。缓存让重复安装快很多，但两种场景下应当关掉：一是 CI 或镜像构建，缓存会被打进镜像层，白白增大体积；二是怀疑缓存里的包损坏或被替换时。--no-cache-dir 同时禁用读取与写入，它不会让安装变快，只是让结果更干净。

可复现构建：锁定、哈希与私有源

“可复现”的最低要求是：同一份代码、同一份依赖声明，在任何一台机器上装出相同的版本组合。做到这一点，需要把所有依赖（含间接依赖）写成 == 并提交锁定文件，安装时不因索引变化而漂移。

更严格的做法是哈希校验。pip install --require-hashes -r requirements.txt 要求文件每一行都带 --hash=sha256:...，pip 会核对下载到的包摘要，不匹配就拒绝安装。它的价值在于：即使镜像站被替换、传输被篡改，或有人重新上传了同版本号的包，安装也会失败，而不是悄悄装上一个不同的东西。代价是维护成本——每升级一个包都要更新对应哈希，因此通常由工具生成而不是手写。

私有源在企业里很常见：内部组件放在私有索引，公开包仍走公共源。可以用 --extra-index-url 追加一个源，也可以把 index-url 指向私有源，由它代理上游。认证信息绝不能写进 requirements.txt 或 setup.py，那等于把密码提交进版本库。可行的做法是：CI 中通过环境变量或密钥管理注入，本地放一份权限为 600 的 ~/.netrc，或者使用系统钥匙串。任何出现在构建日志里的凭据，都应视为已经泄露。

    A[手写直接依赖] --> B[干净环境安装并测试]
    B --> C[生成锁定文件与哈希]
    C --> D[提交版本库]
    D --> E[构建镜像时安装]
    E --> F[测试与生产使用同一镜像]

pipenv 与 poetry：两种项目级方案

requirements.txt 只描述“包”，不描述“环境”和“操作流程”，于是有了项目级工具。

pipenv 用 Pipfile 记录直接依赖，分成 [packages] 与 [dev-packages] 两组，用 Pipfile.lock 记录解析后的完整版本与哈希；pipenv install 自动创建并管理虚拟环境，pipenv run 在环境里执行命令。它一度很受关注，但当时社区的争议不小：锁定过程慢，解析器在某些依赖组合下会卡住或给出难懂的错误，跨平台表现不一致，维护节奏也令人担心。用它不是错误，但要有心理准备。

poetry 走另一条路：用 pyproject.toml 的 [tool.poetry] 段声明依赖，用 poetry.lock 锁定，命令上提供 poetry add、poetry install、poetry build、poetry publish，把依赖管理、虚拟环境与打包发布串成一条线。它在 2019 年仍处于 0.x，接口和小版本间的行为还会变，用在长期项目上要评估升级成本。需要说明的是，pyproject.toml 本身来自 PEP 518，规范早已存在，但当时 setuptools 仍是事实标准，poetry 的用法属于工具约定，不是社区唯一答案。

选型时可以看几件具体的事：团队是否熟悉、CI 能否复现锁定结果、私有源是否支持、Windows 是否顺滑。工具是手段，锁定与可复现才是目的。

pip install -e . 是开发时最常用的形式：它在 site-packages 里放一个指向项目目录的链接，代码改动立即生效，不必反复安装。注意它同时会按 install_requires 安装运行依赖，并在项目根目录留下 .egg-info。pip install . 则是正常安装，会把包复制进环境。

真正用于交付的是 wheel。它是预构建的分发格式，安装时不需要再执行 setup.py，速度快、结果稳定；含 C 扩展的包还要针对平台与 Python 版本构建。构建命令可以是 python setup.py bdist_wheel，也可以是 pip wheel . -w dist。sdist 适合发布到公共索引让使用者自行构建，生产部署优先用 wheel。

依赖要分清两类：install_requires 是运行必需，会被使用者的环境继承；extras_require 里的开发、测试、文档依赖只有显式请求时才装。把测试工具塞进 install_requires 是很常见的错误，它会让每个使用者都被迫安装 pytest。

部署：让构建产物与运行环境一致

部署的原则只有一句：构建阶段把环境定死，运行阶段不再改动。基础镜像固定到明确的小版本，不要用 latest 标签，构建时只拷贝锁定文件并执行 pip install --no-cache-dir -r requirements.txt，依赖层放在代码层之前以利用层缓存。绝不在服务器上执行 pip install -U 或“装个最新版试试”，那会让生产与测试脱节，也无法回滚到确定的组合。镜像里再加一个 PYTHONUNBUFFERED=1，让容器日志及时输出。

环境与部署中的常见坑

  • 忘记激活环境，依赖被装进了全局。先看 which python 与 sys.executable，再决定是否清理。
  • 用 sudo pip install。它会覆盖系统包，严重时影响系统工具，系统级安装应交给发行版的包管理器。
  • pip 与 python 不是一对，PATH 顺序一变就错位，统一用 python -m pip 最稳。
  • pip freeze 把本地路径或 Git 地址写进锁定文件，提交前必须逐行检查。
  • 锁文件不提交，或者把 .venv 提交进仓库，两种做法都会让复现落空。
  • Python 版本与 wheel 不匹配。升级解释器后应重建环境，不要在旧环境里原地补装。

小结

虚拟环境负责隔离，依赖文件负责记录，锁定与哈希负责复现，三者合起来才算一套完整的依赖管理。日常最省心的组合仍然是 venv 加分层的 requirements：开发机装全量，生产只装运行时，锁定文件进版本库，部署时按锁定文件安装。换一台机器能一次装出同样的环境，就是这套流程合格的标志。
