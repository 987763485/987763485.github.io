Go 内存对齐与 unsafe 包

本文属于《Go 语言与工程》第 48/78 篇
上一篇系列目录下一篇

同一份数据，字段只换个顺序，结构体就可能从 32 字节缩到 16 字节；一段看起来只是加了个偏移的指针运算，也可能让程序在另一台机器上崩溃。本文从处理器访问内存的方式讲起，解释 Go 的对齐规则，演示 unsafe.Sizeof、Alignof、Offsetof 的用法，再讨论 unsafe.Pointer 的转换边界与常见陷阱。示例基于 Go 1.12 和 64 位平台，读完你应该能判断什么时候值得重排字段，什么时候应该离 unsafe 远一点。

为什么需要内存对齐

处理器访问内存，并不是真的可以从任意一个字节开始取任意长度。数据总线、缓存和内存控制器通常按字或者缓存行来搬运数据；一个 8 字节的整数如果起始地址不是 8 的倍数，就可能横跨两个总线周期，或者跨越两条缓存行，处理器不得不拆成两次访问再拼接结果。x86 对多数非对齐访问比较宽容，代价是额外开销；一些 ARM、MIPS、SPARC 平台则会直接触发异常，在 Go 程序里表现为 SIGBUS。原子操作的要求更严格，跨边界的读改写没有办法保证原子性，所以在 32 位 x86、ARM 等平台上对 64 位变量做原子操作时，sync/atomic 明确要求调用方保证 8 字节对齐。

为了避免这些麻烦，编译器和 ABI 约定：某种类型的变量，其地址必须是某个数 m 的倍数，这个 m 就是该类型的对齐系数。unsafe.Alignof 返回的就是它。基本类型的对齐通常等于它的大小：bool、byte 是 1，int16 是 2，int32 是 4，int64 是 8。但这并非普遍规律。32 位 x86 上 int64 仍然是 8 字节，对齐却只要 4；指针、int、uintptr 的大小则跟着字长走，64 位是 8 字节，32 位是 4 字节。所以对齐系数既不能简单等同于字段大小，也不能简单等同于机器字长，它是由目标架构的 ABI 和编译器共同决定的。

结构体把这些规则串了起来。编译器按声明顺序放置字段，每个字段的起始偏移必须是该字段对齐系数的倍数，不满足就在前一个字段后面插入若干填充字节；结构体本身的对齐系数取所有字段对齐系数的最大值；结构体的总大小再向上取整到这个对齐系数的倍数。最后一步很关键：只有总大小是结构体对齐的整数倍，元素连续排列的数组才能保证每个元素都对齐。字段之间的空洞、末尾的补齐，都是这套规则的自然结果。

三个函数：Sizeof、Alignof 与 Offsetof

unsafe 包提供了三个在编译期求值的函数，前两个的参数可以是任意类型的表达式。它们的返回值都是 uintptr，不是 int，当作 int 使用时需要显式转换。

  • unsafe.Sizeof(x) 返回类型为 x 的值在内存中占多少字节，包含结构体内部的填充和数组元素的连续排列，不包含它通过指针引用的对象。
  • unsafe.Alignof(x) 返回类型为 x 的变量所要求的最小对齐，结构体取字段的最大值，数组取元素类型的值。
  • unsafe.Offsetof(x.f) 返回字段 f 相对于结构体起始地址的偏移，参数必须是字段选择表达式，不能是普通值。

这三个函数的实参不会被求值，写 unsafe.Sizeof(f()) 不会调用 f；只要类型大小固定，结果就是常量，可以直接用来声明数组长度。比如 var buf [unsafe.Sizeof(User{})]byte 是合法的。下面用一个简单的结构体看看三者如何配合。

这里要提醒一句：这些数字是目标平台相关的。上面注释里的结果来自 64 位平台；换到 32 位平台，int64 的对齐可能变成 4，uintptr 变成 4 字节，同一个结构体的大小和偏移都可能不同。后文没有特别说明时，都按 64 位平台讨论。

结构体填充：字段顺序为什么会改变大小

理解了规则，再看一个更极端的例子。下面两个结构体的字段完全相同，只是顺序不同。

在 64 位平台上运行，得到的大小与偏移如下（单位：字节）。

字段 Bad 中的偏移 Good 中的偏移
Flag 0 12
ID 8 0
OK 16 13
Code 20 8
Tag 24 14
结构体总大小 32 16

Bad 的布局是：Flag 占 0 号字节；ID 要求 8 字节对齐，1 到 7 号成为空洞；OK 在 16；Code 要求 4 字节对齐，17 到 19 又是空洞；Tag 在 24；总大小 25 向上取整到 32。Good 先放 ID 和 Code，三个 bool 放在 12、13、14，最后补 1 个字节到 16。字段一个没少，占用少了一半。

这就是“把大字段放前面”的经验来源。更准确地说，通常是按对齐系数从大到小排列，让每个字段尽量落在已对齐的位置。常见的 8 字节对齐组有 int64、float64、指针、string、interface，4 字节组有 int32、float32，再往后是 int16 和 bool、byte。不过字段有语义分组，或结构体要映射外部格式时，顺序不能随便动。

重排只改变内存布局，不改变字段名和访问方式。Go 编译器不会为了省空间自动重排字段，声明顺序就是内存顺序，所以重排必须由开发者显式决定。在 32 位平台上，int64 的对齐可能只有 4，Bad 会变成 24 字节，Good 仍是 16，结论一样。

空结构体与零大小字段

struct{} 的大小是 0，对齐是 1。用 chan struct{} 做信号、map[string]struct{} 做集合，都是利用它不占数据空间。一百万个元素的 []struct{}，底层数组不占字节，切片头仍然要占 24 字节。

数组和切片里的零大小元素还有地址上的特殊性。[1000]struct{} 的大小是 0；make([]struct{}, 3) 的三个元素可能位于同一地址，&s[0] == &s[1] 在常见实现中为真。规范允许两个不同的零大小变量具有相同地址，但没有承诺一定相同，所以不要用地址区分它们，需要区分时用下标。

unsafe.Pointer 的四条转换规则

unsafe.Pointer 是 Go 里唯一的通用指针类型。官方给出四条转换规则：*T 可以转成 unsafe.Pointer；unsafe.Pointer 可以转成任意 *T；uintptr 可以转成 unsafe.Pointer；unsafe.Pointer 可以转成 uintptr。前两条让不同指针类型互通，后两条让指针和整数运算搭上关系，真正危险的是后两条。

uintptr 是足够大的无符号整数，能装下地址，但它不是指针。GC 只扫描指针类型的字，不会把 uintptr 里的数字当成对象引用；编译器也不会因为一个 uintptr 保存了地址就延长对象寿命。于是下面这种写法是危险的。

从 x 转成 u 之后，x 可能被判定为不再使用，对象随之被回收；栈增长和复制也会让旧地址失效。把 u 转回指针，得到的可能是一个悬空地址。即使这次没出错，也不能说明写法正确。

还有两个误解。第一，unsafe.Pointer 转成 *T 不检查大小和对齐，T 比原类型大或者地址不满足对齐要求，读写就会踩到别的内存，或者在 ARM 上触发异常。第二，uintptr 适合打印地址和一次性算术，不适合作为结构体字段、缓存键或跨函数传递的“指针”。go vet 能发现一部分问题，但只是静态检查。

常见合法用途

unsafe 并非洪水猛兽，标准库和基础库都在用，只是用得很有边界。

第一类是与 C 交互。cgo 为 C 结构体生成 Go 类型，布局由 C 编译器决定，生成的类型通常能对上。但 C 的 long 在 64 位 Linux 上是 8 字节、Windows 上是 4 字节，int 也随平台变化，跨语言边界应优先用 int32、int64 等固定宽度类型。带 #pragma pack 的紧凑结构体、位域、柔性数组没有布局保证，必须按字节解码。

第二类是字段偏移和未导出字段的访问。序列化、ORM、测试工具可能绕开导出规则直接按偏移读写，这类代码对 Go 版本和结构体定义非常敏感，字段一改就可能失效；自己业务里的结构体，直接写字段名永远更好。

第三类是零拷贝。把 []byte 当成只读字符串是流传很广的技巧：

它把切片头重新解释成字符串头，省掉一次拷贝。但返回的字符串与原切片共享内存：修改 b，字符串内容就跟着变，不可变性被破坏；如果这个字符串已经作为 map 的键，底层字节一变，查找结果就不可预测；切片被复用或放回对象池后，字符串看到的内容也会变。它依赖切片头前两个字段的布局，规范并不保证。普通业务直接写 string(b)。

切片头与字符串头：只可观察，不可依赖

切片变量是描述符：64 位平台上占 24 字节，包含数据指针、长度、容量；字符串占 16 字节，包含数据指针、长度。reflect.SliceHeader 和 StringHeader 暴露了这两个布局。

地址每次运行可能不同，Len 和 Cap 与切片状态一致；子切片的 Data 会按元素大小偏移，这能解释切片共享底层数组、扩容后旧切片仍指向旧数组。

但观察不等于依赖。SliceHeader 的文档明确说它只是运行时表示，不能安全或可移植地使用，不同 Go 版本和架构都可能调整布局。

Go 对象前面没有 Java 那样的 mark word，分配信息在 mspan 里；map 的底层哈希表是另一个话题，这里不展开。

常见危险与边界

第一，GC 不追踪 uintptr。把地址存进整数，等于把对象从 GC 视野里摘出去；对象被回收、栈被复制后，整数还在，指针已经失效。跨函数保存 uintptr 应视为 bug。

第二，越界访问，指针算术绕过边界检查，可能破坏堆。第三，对齐不匹配，*byte 强转 *int64，地址不是 8 的倍数时，amd64 上可能只是变慢，ARM 上可能异常，原子性也无保证。

第四，平台差异，int、指针、uintptr 随字长变，int64 的对齐和结构体大小也随平台变；用 unsafe 把结构体写进文件或网络包，换平台就可能读不出来，应改用 encoding/binary。第五，编译器和运行时优化：内联、逃逸分析、栈复制和 GC 时机都会影响行为，go vet 只能发现一部分问题。

原则是能不用就不用；必须用时缩到最小，写清前置条件，针对目标架构测试，优先使用标准库的安全抽象。

性能视角：什么时候值得重排字段

结构体数组的内存是元素大小乘个数，元素从 32 字节降到 16 字节，一百万个就从 32 MB 降到 16 MB；这是按 Sizeof 算出的占用，不是性能提升。顺序访问有预取掩盖，随机访问和缓存紧张时差距更明显；常见的 64 字节缓存行里，32 字节结构体放两个，16 字节放四个。

但重排会改变字段顺序，可能影响 JSON 输出和文本 diff；字段少、对象少、瓶颈在网络或数据库时，收益可以忽略。先测量再动手。

小结

内存对齐是 ABI 的要求，Go 用填充和末尾补齐满足它；Sizeof、Alignof、Offsetof 在编译期给出大小、对齐和偏移。字段顺序影响填充，是否重排应由测量决定。struct{} 为 0，结尾却可能引入填充；uintptr 不是指针，互转必须在一个表达式里完成。切片头和字符串头可以看，不要依赖。
