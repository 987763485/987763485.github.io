Python 函数、闭包与装饰器

本文属于《Python 学习路线》第 4/29 篇
上一篇系列目录下一篇

函数在 Python 里不是语法结构，而是实实在在的对象；理解这一点，才能理解闭包为什么能记住外层变量，装饰器为什么只是“把函数传进去、把函数换出来”的语法糖。本文从一等函数讲起，依次拆解作用域规则、闭包晚绑定陷阱、带参数装饰器、functools.wraps、类装饰器与标准库工具，最后给出一个日志、计时、重试、鉴权组合的实战方案。读者需要会写基本的 def 与类，读完后应能独立写出可维护的装饰器，并避开常见的几个坑。

函数是对象

很多语言把函数当作附属于类的成员，Python 不这样看。def 是一条可执行语句：解释器执行到它时，创建一个函数对象，然后把名字绑定到该对象上。既然是对象，函数就有类型、有属性、有身份，也可以像整数和字符串一样被赋值、装进容器、作为参数传递、作为返回值返回。这套能力在术语上叫“一等函数”（first-class function），它不只是语法层面的便利，更是后面所有闭包与装饰器技巧的地基。

函数对象上的几个常用属性

函数对象携带了不少元信息，调试和写框架时经常要用：

  • __name__：函数名，日志和错误信息里最常见。
  • __doc__：文档字符串，help() 与 pydoc 读取的就是它。
  • __defaults__：位置参数默认值组成的元组，没有默认值时为 None。
  • __kwdefaults__：仅关键字参数的默认值字典。
  • __code__：编译后的代码对象，包含参数个数、局部变量名、字节码等。
  • __dict__：函数自己的属性字典，可以往上面挂任意元数据。
  • __annotations__：参数与返回值的注解字典，3.7 下仍是普通字典。

__defaults__ 值得单独演示，因为它解释了一个常被误解的现象：默认值在函数定义时求值一次，之后保存在函数对象里，可以被替换。

def 与 lambda 的边界

lambda 创建的是同一个 function 类型的对象，区别只在语法：lambda 的函数体必须是单个表达式，不能包含语句，不能写注解，也不能带文档字符串。它适合“就地用完即弃”的小函数，例如排序键：

一旦逻辑超过一个表达式，或者需要复用、需要调试，就应该换回 def。原因很实际：lambda 的 __name__ 是 "<lambda>"，出现在日志和 traceback 里几乎不提供信息；它也无法写文档字符串，团队协作时阅读成本更高。PEP 8 明确建议不要把 lambda 赋值给变量名，需要名字就说明它值得一个 def。笔者的经验法则是：key=、sorted、max、简单的回调可以用 lambda；只要出现条件分支、函数调用嵌套两层以上，立刻改成 def。

作用域与闭包

理解了函数是对象，下一个问题是：函数体里的名字从哪里找？Python 采用词法作用域，名字解析顺序通常概括为 LEGB：Local（当前函数的局部作用域）、Enclosing（外层函数的作用域）、Global（模块全局作用域）、Builtins（内置名字空间）。这个顺序在函数定义时就已经由代码结构决定，而不是由调用位置决定，这一点是闭包能够成立的根本原因。

一个容易踩的细节是：只要函数体里对某个名字发生了赋值，这个名字在整个函数内就被判定为局部变量，哪怕赋值语句在引用之后。于是下面这段代码会抛出 UnboundLocalError：

闭包如何保存自由变量

闭包（closure）指内部函数引用了外部函数的局部变量，并且内部函数在外部函数返回之后仍然存活。被引用的变量叫自由变量（free variable），Python 不会把它拷贝进内部函数，而是把它放进一个“单元格”（cell），内部函数持有对这个 cell 的引用。可以用 __closure__ 观察：

__closure__ 是一个元组，里面的元素是 cell 对象；cell_contents 就是当前的 count。两次调用 make_counter() 产生两个互不影响的 cell，所以 c1 与 c2 的计数彼此独立。这正是闭包比全局变量优越的地方：状态被封装在函数对象内部，不需要额外的类，也不会污染模块命名空间。

nonlocal 是 Python 3 才有的关键字，它声明“我要改的是外层函数的绑定”。如果不写 nonlocal，count += step 会让 count 变成 counter 的局部变量，随后在赋值前读取，同样触发 UnboundLocalError。只读自由变量则不需要任何声明，解释器会自动从外层 cell 取值。

闭包保存的是变量本身，而不是变量在某一刻的值。这个区别看似细微，却是下一节所有陷阱的源头。

装饰器的本质

装饰器经常被讲得神秘，其实它只用到两个已经讲过的能力：函数是对象，函数可以作为参数和返回值。所谓装饰器，就是一个“接收函数、返回新函数”的可调用对象，而 @ 只是把这种调用写得更靠近函数定义而已。

别忘了 functools.wraps

上面的 timed 与 retry 都能工作，但它们有一个共同的副作用：被装饰之后，函数的名字、文档、签名都变成了 wrapper 的。打印 slow_add.__name__ 会得到 wrapper，help(slow_add) 显示的是包装函数的签名 (*args, **kwargs)，原本精心写的文档字符串也不见了。对一两个函数的小脚本无所谓，对框架和团队协作就是灾难。

标准库提供了 functools.wraps，它是一个用在包装函数上的装饰器，负责把原函数的元信息复制过来：

functools.wraps 内部调用 update_wrapper，默认复制 __module__、__name__、__qualname__、__annotations__、__doc__，更新 __dict__，并设置 __wrapped__ 指向原函数。inspect.signature() 遇到 __wrapped__ 会继续向内查找，所以签名也能恢复成 (text)，而不是 (*args, **kwargs)。需要提醒的是，__defaults__ 并不在复制清单里；如果代码真的依赖它，要自己赋值，或者干脆通过 inspect.signature 读取。

为什么这件事重要？因为大量工具靠这些元信息工作。日志系统用 __name__ 区分函数；Sphinx 用 __doc__ 生成 API 文档；Flask 用视图函数的 __name__ 推导 endpoint，若所有视图都叫 wrapper，注册第二条路由时就会冲突；Django 的 login_required、DRF 的权限类、pytest 的 fixture 名称、装饰器叠加时的调试信息，也都会受影响。更麻烦的是排错：异常栈里全是 wrapper，根本分不清是哪个接口出错。写装饰器的第一原则因此可以概括为：只要写了 wrapper，就加上 @functools.wraps(func)，成本一行，收益长期。

类装饰器：两个方向

“类装饰器”这个词有两个含义：用类去装饰函数，以及用装饰器去装饰类。两者用途不同，这里分开说。

用装饰器修饰类

装饰器的本质是“接收一个对象、返回一个对象”，这个对象不必是函数，也可以是类。接收类、返回类的可调用对象，就是类装饰器。最常见的用途是注册与批量改写：

用类实现装饰器

反过来，一个实现了 __call__ 的类实例也是可调用对象，因此可以拿来做装饰器。它的优势是状态放在实例属性上，比闭包的 cell 更直观，也更容易扩展：

CountCalls(ping) 返回的是实例，ping 这个名字从此指向实例；调用 ping() 实际执行 __call__。计数保存在 self.calls 上，外部可以直接读取，这对限流、统计、熔断一类需要暴露状态的装饰器很友好。带参数的类装饰器则要把参数放进 __init__，把函数放进 __call__，结构相当于把三层函数换成了“构造 + 调用”两步。

两种写法如何取舍？函数闭包轻量、直观，适合无状态或状态简单的场景，也是绝大多数项目的默认选择；类实现适合需要多个方法、继承、显式状态和单元测试的场景，例如一个可配置的限流器。类实现有一个必须知道的限制：实例不是描述符，如果直接用它装饰类里的实例方法，通过对象访问时不会自动绑定 self，调用会少一个参数。要在方法上使用，得额外实现 __get__，或者老老实实用函数闭包。笔者在项目里通常只用类装饰器装饰模块级函数，方法一律用函数式装饰器，避免这类隐蔽问题。

理解这条链的意义在于：顺序不是装饰器的细节，而是语义的一部分。把鉴权放在日志外层，未授权的请求就不会留下日志；把重试放在鉴权外层，权限错误可能被重试多次；把计时放在缓存内层，缓存命中时就不会被计时，放在外层则能测到包含缓存查找在内的端到端耗时。每加一层，都要问一句“我希望这一层看到什么、看不到什么”。

可测试性方面有三条经验。第一，业务函数本身不依赖装饰器就能测试，装饰器应当透明，这也正是 functools.wraps 的价值。第二，把时间、睡眠、认证查询这类副作用做成可替换的依赖：示例中的 USERS 可以换成注入的仓储对象，time.sleep 可以在测试里替换成空函数，这样重试测试不必真的等待。第三，给每个装饰器单独写测试，而不是只测组合后的结果；否则一旦顺序调整，失败原因很难定位。

可读性方面，一个函数叠三层通常是上限，超过就该停下来审视。若多个接口需要同一组横切逻辑，可以提供一个组合装饰器，把固定顺序封装在一个地方，并写清文档；若逻辑开始带业务分支，例如“管理员跳过重试、游客降级返回缓存”，那就不是装饰器该管的事，应当下沉到服务层用普通代码表达。所谓“装饰器地狱”，往往不是装饰器本身的问题，而是把流程控制硬塞进了包装链。

几个高频的坑

第一个坑是漏掉返回，而且往往漏两处：装饰器忘了 return wrapper，或者 wrapper 忘了 return func(...)。前者让被装饰的名字变成 None，定义完立刻调用就会报 'NoneType' object is not callable；后者让所有返回值静默变成 None，如果函数本来靠返回值工作，错误会延迟到很远的地方才暴露。写完装饰器，先检查这两个 return，能省掉大量调试时间。

第二个坑是参数转发不完整。有人图省事写成 def wrapper(a, b)，一开始能用，等调用方加上关键字参数或第三个参数就崩了。除非确实要限制签名，否则一律写 *args, **kwargs 并原样转发。需要保留精确签名时，可以借助 inspect.signature 做校验，但那是另一层话题，不能替代透传。

第三个坑是在装饰器里吞异常：

调用方以为操作成功，监控看不到错误，数据却已经不一致。装饰器可以记录异常、转换异常类型、决定是否重试，但默认应当让异常继续向上传播；需要记录时用 logger.exception 再裸 raise，它保留原始栈，写成 raise exc 反而会多出一层当前帧，不利于定位真正的出错点。

第四个坑是带参装饰器少一层或括号写错。@retry 会把函数本身当作 times 传进去，直到执行 range(1, times + 1) 才报类型错误；@retry() 则是合法的，表示使用全部默认参数。判断方法很简单：装饰器工厂的参数表里有必填项时，必须写括号；没有必填项时，带不带括号是两种不同的调用，不能混用。

第五个坑是异步函数遇上同步 wrapper。同步 wrapper 调用 async def 函数只会得到一个协程对象，并不会执行函数体：

这段代码不会立刻报错，调用方 await 之后协程照样执行，但计时完全失真，异常也不会经过 try；若调用方忘了 await，还会收到 coroutine was never awaited 的 RuntimeWarning。正确的做法是为协程单独写一个 async def wrapper，内部 return await func(...)；如果同一个装饰器要兼顾两者，用 asyncio.iscoroutinefunction(func) 判断后返回不同的 wrapper。

第六个坑是把本该每次调用的代码写到了装饰器外层。例如把 start = time.time() 写在 def wrapper 之前，测到的是导入时刻到现在的时长；把数据库连接建在装饰器函数体里，所有调用共享一个可能已经断开的连接。记住：装饰器外层只在定义时执行一次，wrapper 内部才属于每次调用。

最后一个坑与状态有关。用闭包或类实例累计计数时，count += 1 不是原子操作，多线程下可能丢失更新；lru_cache 的字典本身有锁保护，但“先查缓存、未命中再回源”的整体流程没有，多个线程可能同时回源。装饰器让状态变得隐蔽，一旦涉及并发，就要显式加锁或改用线程安全的数据结构。

小结

函数在 Python 里是一等对象，可以被赋值、传参、返回，也可以携带属性；这是闭包与装饰器的共同前提。作用域按 LEGB 解析，闭包通过 cell 保存自由变量，保存的是变量而非某一刻的值，循环中的晚绑定与可变默认参数都由此而来。装饰器只是 func = decorator(func) 的语法糖，不带参数时两层，带参数时三层，装饰发生在定义时，包装逻辑发生在调用时。functools.wraps 应当成为肌肉记忆，它保住了日志、文档与框架反射所依赖的元信息。落地时把装饰器限制在边界层，保持每层单一职责，控制叠加数量，并让业务函数脱离装饰器也能独立测试，这样得到的才是工具，而不是负担。

最后说明边界：本文讨论的是函数作为对象、闭包捕获变量、装饰器包装调用这三件事，刻意没有展开 yield、迭代协议与生成器表达式，那属于迭代器与生成器专题。实际写装饰器时也会遇到生成器函数，此时 wrapper 要决定是返回生成器对象还是消费它，这是包装策略问题，生成器本身的暂停与恢复机制不在这里重复。
