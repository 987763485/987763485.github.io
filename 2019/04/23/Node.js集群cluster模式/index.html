Node.js 集群 cluster 模式

本文属于《TypeScript 学习路线》第 56/74 篇
上一篇系列目录下一篇

Node 的 JavaScript 执行是单线程的：一个进程再忙，也只会吃满一个 CPU 核，其余核心看着它排队。cluster 模块给出的答案不是线程，而是进程——主进程负责监听端口和调度，多个 worker 进程共同处理请求。本文从最小的可运行示例讲起，解释端口为什么能被多个进程“共享”、worker 崩溃后如何拉起、怎样做到重启时不断连接，以及多进程带来的会话、定时任务和日志问题。读完之后，你应当能判断一个服务该不该上 cluster，以及上了之后要补哪些配套。

为什么需要 cluster

一个进程只用一个核

Node 把 JavaScript 放在一条线程上执行，事件循环、回调、你的业务代码都排在这条线程里。libuv 的线程池只承担文件读写、DNS 解析这类少数任务，业务逻辑并不在池子里跑。所以一个 Node 进程即使 CPU 打满，也只是把一个核吃满。

这里要区分并发和并行。事件循环擅长并发：一万个连接同时挂着，每个连接只占一点内存，切换成本极低。但它不擅长并行：同一时刻只有一段 JS 在执行，如果某个请求里有 30 毫秒的同步计算，这一万个连接的响应时间都要顺延这 30 毫秒。想让多核真正干活，只能开多个进程。

多进程，而不是多线程

多线程共享内存，一个线程越界写入可能带走整个进程，还要小心锁和竞态；多进程各有独立的堆和事件循环，一个 worker 挂掉，主进程还能把它拉起来，隔离性好得多。代价是内存不共享：worker 1 里的全局变量、缓存、计数器，worker 2 完全看不到。这个代价会一直延伸到后面的会话、限流和定时任务。

还有一个容易混淆的选项：worker_threads 在 Node 10 已经可用，但需要加 --experimental-worker 才打开，它适合把一段 CPU 密集的计算切出去，避免堵住事件循环。cluster 解决的是另一个问题：整个 HTTP 服务怎么吃满多核。两者不冲突，本文只讲后者。

端口共享：真正 listen 的只有一个进程

回到 EADDRINUSE 的疑问。cluster 并没有让每个 worker 去 bind 同一个端口，它拦截了 listen：worker 调用 listen(3000) 时并不真的创建监听套接字，而是把地址告诉主进程；主进程替它监听，再通过 IPC 把句柄发下来。从操作系统看，监听套接字只有一个，归主进程所有。

flowchart TD
    C[客户端连接 3000 端口] --> M[主进程持有监听套接字]
    M -->|accept 后按轮询分发| W1[worker 1]
    M -->|accept 后按轮询分发| W2[worker 2]
    M -->|accept 后按轮询分发| W3[worker 3]
    W1 --> R[各自解析 HTTP 并响应]
    W2 --> R
    W3 --> R

连接建立时，主进程 accept 出 socket，按策略挑一个 worker，把这个连接句柄递过去；worker 收到后包成 net.Socket，交给 HTTP 解析器。主进程只做 accept 和转发，不做解析，单个连接的开销很小。但它仍是一个单点：主进程的事件循环一旦被业务代码堵住，所有新连接都进不来。

Windows 的差异与 round-robin

在 Linux 和 macOS 上，默认是主进程轮询分发（round-robin）：第一个连接给 worker 1，第二个给 worker 2，依次循环。分配很均匀，短连接场景下各 worker 的负载几乎一致。

Windows 上默认换了一种做法：libuv 支持把监听句柄复制给子进程，多个进程可以同时对同一个句柄调用 accept，由内核决定谁拿到连接，主进程不再参与分发。这种方式的分配不保证均匀，但省掉了一次进程间转发。

两种策略各有软肋。round-robin 只看连接数，不看 worker 忙不忙：如果 worker 3 接了十个长连接正在做重活，主进程仍会把新连接继续派给它，后面的请求只能排队。内核抢占则相反，空闲的进程更容易抢到新连接，短连接突发时更均衡，但长连接一旦建立就固定了。

这些差异对业务代码是透明的，但要记住：不要假设连接会落在哪个 worker 上，也不要假设同一个客户端的两次请求会进同一个进程——这正是后面会话问题的根源。

IPC：主进程与 worker 怎么说话

cluster.fork() 时会自动建立一条 IPC 通道，底层是一对管道（Unix domain socket 或 Windows 命名管道）。worker 里可以直接用 process.send 和 process.on(‘message’)，主进程侧则是 worker.send 和 worker.on(‘message’)。

消息是异步的，默认按 JSON 序列化。所以 Date 会变成字符串，值为 undefined 的字段会直接消失，循环引用会抛错；消息里带 Buffer 时，收到的其实是 { type: ‘Buffer’, data: […] } 这样的普通对象，需要自己还原。

传递句柄，但别传大对象

句柄在同一时刻只能归一个进程使用，发出去之后原进程就不该再碰它；句柄也只在本机有效，不能跨机器传递。日常业务几乎用不到这个能力，知道它存在、知道 cluster 的端口共享靠它实现即可。

更需要留意的是消息体积。IPC 通道带宽有限，序列化还发生在主进程的事件循环里。传一个几 MB 的数组，主进程要花时间把它转成字符串，这段时间无法 accept 新连接，所有 worker 都跟着等。配置、命令、小批量的任务适合走 IPC；大批量数据应该走 Redis、消息队列，或者让 worker 自己去查库。反过来也一样：不要让几十个 worker 在启动时同时向主进程要全量配置，启动风暴往往就是这么来的。

优雅重启

发布新版本时，如果直接杀掉所有 worker 再启动，客户端会看到一批 502 或连接重置。cluster 提供了更温和的路径，前提是弄清楚每个方法究竟做到哪一步。

disconnect 与 kill 的差别

worker.kill() 给进程发信号（默认 SIGTERM），进程立刻开始退出，正在处理的请求被切断，客户端看到连接被重置。它适合卡死、内存爆掉这种必须强杀的场合。

worker.disconnect() 温和得多：它关闭这个 worker 里所有的 server，不再接受新连接，然后等已有连接自然结束；连接都结束后关闭 IPC 通道，worker 自己退出。注意它不保证“立刻”——HTTP 的 keep-alive 连接空闲着不会主动关，server.close() 在 Node 10 里只停止接受新连接，并不去断开空闲的长连接，worker 就可能一直挂着。实践中的做法是：记录每条连接的建立时间，disconnect 之后把空闲太久的连接主动 destroy，再设一个总超时，到点还没走就 kill。

零停机的步骤

  1. 主进程 fork 一个新 worker，等它的 listening 事件。这个事件表示 worker 里的 server 已经就绪，可以接连接了。
  2. 新 worker 就绪后，从旧 worker 里挑一个，调用 disconnect()。此刻新连接只会进新 worker，旧 worker 只处理存量连接。
  3. 给旧 worker 一个宽限期，例如 30 秒，期间它继续把在途请求做完。
  4. 宽限期结束仍未退出，就 kill()，并在日志里记下这次强杀，说明有请求被中断。
  5. 依次替换完所有旧 worker，把这次发布的进程列表记进日志，方便事后核对。

一次性替换全部 worker，容量会在短时间内翻倍，内存紧张的机器要分批做。

零停机的关键不是重启得多快，而是旧进程在什么时候停止接客。只要新进程在旧进程退出前就已监听就绪，中间就没有空窗；先杀后起，哪怕只慢一秒，这一秒里的连接也都失败了。

状态与会话：多进程不共享内存

上 cluster 之后，第一类事故几乎都和“以为共享”有关。

session 必须外置

用户第一次请求落在 worker 1，登录态写进 worker 1 的 Map；第二次请求被分到 worker 2，Map 里没有这条 session，用户被踢回登录页。解决办法是把 session 放到进程之外：Redis 存会话，cookie 里只放 session id；本地内存最多做一层只读缓存，不能作为唯一来源。同理，内存里的限流计数器、验证码、一次性 token，要么外置，要么接受“每个 worker 各算各的”这种偏差。

定时任务只让一个进程跑

八个 worker 各跑一个 setInterval，对账任务就执行了八次，还可能互相覆盖同一批数据。两种处理：把定时任务拆到单独的入口，用一个只跑 cron、不参与 HTTP 服务的进程；或者用分布式锁，保证同一时刻只有一个 worker 真正执行。Redis 的 SET NX EX 是最省事的锁，拿到锁的干活，其余跳过本轮。锁一定要带过期时间，否则持锁的 worker 崩了，任务就再也不跑了。

WebSocket 的粘性会话

长连接在建立时就被分配到某个 worker，之后一直留在那里，这本身没有问题。问题出在广播：worker 1 想通知所有在线用户，可它只知道自己身上的连接。两种做法：负载均衡层做粘性会话（例如 nginx 的 ip_hash），让同一客户端总落到同一 worker；或者把广播交给 Redis 的发布订阅，每个 worker 订阅同一频道，收到消息后只推给自己持有的连接。后一种更彻底，也不依赖负载均衡的配置，值得优先考虑。

与 PM2、容器的分工

PM2 的 cluster 模式就是 cluster 模块的封装：pm2 start app.js -i max，它替你 fork、替你重启、替你 reload，还带日志聚合和监控面板。代码里再写 cluster.fork() 就重复了，进程数会变成乘积。PM2 的 fork 模式则是单进程，适合定时任务、队列消费者这类本来就不该多开的进程。

到了 Kubernetes，思路又翻了一层。一个 Pod 跑一个 Node 进程，扩缩容交给副本数，滚动更新交给 Deployment，崩溃重启交给 kubelet。这时在容器里再开 cluster，等于在小盒子里再切几份：CPU 限额是一核，开四个 worker 只会互相抢这一核，还会让资源计量和自动扩缩容的指标失真。

一个粗略的判断：服务跑在固定虚拟机上、没有编排系统，用 cluster 或 PM2 是合适的；已经有 Kubernetes 或同类平台，优先用多副本，把进程管理交给平台；只是想把 CPU 密集计算挪出请求路径，那应该看 worker_threads 或独立的任务进程。

监控与常见坑

盯住重启次数和内存

至少要监控四项：worker 的退出次数与退出码，在 exit 事件里按 worker.id 聚合；每个 worker 的内存，定时打印 process.memoryUsage().rss，只看主进程没有意义；每个 worker 的 CPU，某个 worker 明显偏高，说明请求里有长任务或分配不均；以及每条日志都带 pid。

内存泄漏的典型模式是：worker 内存阶梯式上涨，撞到 –max-old-space-size 的上限，V8 报 heap out of memory，进程退出，主进程拉起新的，几小时后再来一遍。表现是服务隔一阵抖一下，监控上重启次数和内存曲线同步爬升。排查时用 –inspect 接上 Chrome DevTools，抓两次堆快照对比，或者定时 heapdump 到磁盘事后分析；先看请求低谷时内存有没有回落，能快速区分泄漏和正常的缓存波动。

几个反复出现的坑

  • 在 worker 分支里漏写 else，每个 worker 又去 fork，进程树翻倍。
  • 主进程里写业务逻辑，它一阻塞，所有 worker 都接不到新连接。
  • 所有 worker 跑同一个定时任务。
  • 重启直接 kill，客户端看到 502。
  • 日志不带 pid，出问题无法定位是哪个进程。
  • 多个 worker 同时往一个文件追加写，自己实现的日志轮转尤其容易内容交错或截断。日志统一写 stdout，交给单进程或采集 agent。

小结

cluster 用多进程把 Node 服务铺到多个 CPU 核上：主进程持有监听端口、分发连接、拉起崩溃的 worker，worker 专心处理请求。它不是多线程，进程之间不共享内存，所以 session 要外置，定时任务要加锁或独立进程，WebSocket 广播要走粘性会话或发布订阅。上线前把优雅重启的流程跑通，让每条日志都带 pid，把重启次数和内存纳入监控。cluster 不是免费的，它把单进程的问题换成了分布式的问题，配套没跟上，省下的 CPU 会被这些新问题吃掉。
