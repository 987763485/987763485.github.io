TypeScript 2.1 新特性详解

本文属于《TypeScript 学习路线》第 23/74 篇
上一篇系列目录下一篇

TypeScript 2.1 发布于 2016 年 12 月，是这门语言第一次让类型去“操作键”，而不只是描述值。本文站在 2.6 的时间点回看这次发布：keyof、索引访问类型、映射类型与四个内置工具类型如何配合，对象 rest/spread 与 async 降级又给工程带来了什么，以及这些能力在今天应该怎样用。适合已经会写泛型、想把类型声明写得更省事的读者。

2.1 在版本线上的位置

截至本文写作时的 2.6，TypeScript 已经经历了几个以“检查更严”为主题的版本。回头看 2.1，它的意义不在检查，而在表达力：在此之前，泛型能表达“装着 T 的容器”，却无法用一个类型去描述“T 有哪些属性名”。2.1 补上了这块空白，类型第一次可以对键做运算。

可以这样理解两代写法的差别。假设要把一个接口的所有字段变成可选，在没有映射类型的日子里，只能为每个接口手写一份几乎相同的新接口，字段一多就难以维护；2.1 之后，一个映射类型就能覆盖所有对象类型。Partial、Readonly、Pick、Record 这四个内置类型，正是在这套机制上写出来的，它们至今仍是声明文件里出现频率最高的工具类型。

同一版本还带来了两件与类型表达无关、但影响产物的事：对象 rest/spread 的支持，以及 async 函数向 ES5/ES3 的降级。再加上 --target es2016 与 --target es2017 两个新目标，2.1 实际上同时改变了“类型怎么写”和“代码怎么发”两头。下面按这个顺序展开。

keyof 与索引访问类型

keyof T 的结果是 T 的所有属性名构成的联合类型，每个成员都是字符串字面量类型。它只在编译期存在，不会生成任何运行时代码。

这个类型最常见的用途是约束参数：与其让调用方传任意字符串再到运行时才发现写错，不如要求键必须落在 keyof T 里。需要注意，如果 T 带有字符串索引签名，keyof T 会退化成 string | number，因为 JavaScript 里数字索引最终也会被转成字符串，索引签名无法把两者区分开。另外，keyof 作用在联合类型与交叉类型上的结果方向相反：keyof (A | B) 只保留两个类型共有的键，keyof (A & B) 则是两边键的并集。这一点在给泛型写约束时经常被忽略，容易让约束过宽或过窄。

索引访问类型 T[K] 则用键去取属性类型。写法与取值表达式一样，只是发生在类型层。

T[K] 里的 K 可以是字面量、字面量联合，也可以是另一个类型参数。把它和 keyof 组合起来，才能写出“键与值一一对应”的函数。

关键在于返回值写的是 T[K] 而不是 T[keyof T]。后者会把所有值类型混成一个联合，前者保留了“传哪个键就得到哪个类型”的对应关系；而 K extends keyof T 保证调用方传错键时在编译期就报错。此后大量库函数——取值器、表单字段的读写、状态更新函数——都以这个模式声明类型。

映射类型：对键做一次遍历

如果 keyof 是“取出键”，映射类型就是“拿着键重新造一个对象类型”。

读法是：[K in keyof T] 相当于对键联合做一次 for-in，K 依次取每个键；冒号右边是新属性的类型，可以引用 T[K]，也就是原对象在该键上的类型。右边写 T[K]，得到结构相同的新类型；右边写固定类型，得到“同构但换了值类型”的映射。

映射的键集合不一定来自 keyof T，也可以直接写一组字符串字面量。{ [K in "small" | "large"]: number } 会生成两个属性，相当于手工列出所有允许的键。换句话说，映射类型遍历的是任意字面量联合，keyof 只是最常用的一种来源；理解这一点，才能看懂库里那些只针对几个固定键生成的类型。

在 2.1 里，映射类型能给属性加两种修饰：? 让属性可选，readonly 让属性只读。

当映射的源头恰好是 keyof T、且 T 是类型参数时，编译器会把它当作同构映射，保留原类型上已有的可选与只读修饰。这条规则是 Partial 与 Readonly 能正确作用在任意接口上的前提。也要注意，2.1 的映射类型只会“加上”修饰，还不能把已有的 ? 或 readonly 去掉，这一点要等到后续版本才补上。

四个内置工具类型

2.1 的 lib.es5.d.ts 直接给出了四个工具类型的定义，读一遍就明白映射类型在解决什么问题。

前两个是同构映射的最短写法：一个把所有属性变成可选，一个把所有属性变成只读。Pick 把映射的源头从 keyof T 换成调用方给出的键集合 K，因此结果是原类型的子集，K extends keyof T 保证只能挑真实存在的键。Record 反过来，用一组键生成取值类型相同的属性，常用来表达字典或配置表。

这四份定义都很短，但边界必须说清楚。它们都是浅层的：Partial 只处理第一层属性，嵌套对象仍然保持原样；Readonly 同样只约束第一层，而且只在编译期生效，运行时对象照样可以改。另外，2.1 里 Record 的键被约束为 string 的子类型，所以 Record<1 | 2, string> 这样的数字字面量键还不能直接写，需要数字键时得改用带索引签名的接口。

对象 rest/spread 的类型行为

对象 rest/spread 属于 ES2018 的内容，2.1 先一步在类型检查与降级上支持了它。解构剩余属性时，编译器会从原类型里减去已经取出的键。

rest 的类型是精确的剩余结构，而不是整个 Todo，也不是 any，所以把它继续传给需要那两个字段的函数是安全的。展开构造新对象时，同名属性以靠后的为准，这正好支撑不可变更新：先铺开旧状态，再覆盖要改的字段，旧对象本身不动。

两个坑值得提前说明。第一，展开是浅拷贝，嵌套对象仍然是同一个引用，改动 next 里嵌套的数组会同时影响 todo；需要深拷贝时只能自己递归或借助工具函数。第二，展开只复制自有可枚举属性，原型上的方法和访问器不会以访问器的形式保留，getter 会被求值后当成普通值复制。

降级产物方面，目标低于 ES2015 时，对象展开会编译成 __assign 辅助函数，剩余解构会编译成 __rest，并且每个使用到的文件都会各带一份。项目里这类文件一多，体积就会明显增加，配合 --importHelpers 与 tslib 可以只保留一份实现。

async/await 降级到 ES5

2.1 之前，async 函数只能在目标为 ES2015 及以上时编译；如果项目还要照顾 IE11，就只能用 Promise 链手写。2.1 把这条限制去掉了，async/await 可以降级到 ES5 甚至 ES3。

降级后的形态不是简单的回调嵌套，而是把函数体改写成状态机：__awaiter 负责创建并驱动 Promise，__generator 把每个 await 前后的代码切成片段，按顺序推进。这样语义与原生 async 保持一致：try/catch 能捕获 await 的拒绝，循环和条件分支也能在正确的位置暂停与恢复。与 Babel 6 的方案不同，TypeScript 自带这两个辅助函数，不需要额外引入 regeneratorRuntime。

代价首先落在运行时依赖上。TypeScript 只为 Promise 提供类型，不提供实现；面向 IE11 或老版本 Node 时，必须自己引入 polyfill，例如 es6-promise 或 core-js 的 promise 模块。编译配置也要配套：lib 里要包含 es2015.promise（或者直接写 es2015），否则会看到 “Promise only refers to a type” 这类错误，因为编译器只认识名字，不认为它是一个值。

其次是产物与调试体验。每个 async 函数都会展开一套状态机，辅助函数默认在每个文件重复，--importHelpers 加 tslib 能缓解体积问题。生成代码的堆栈更长，断点常常落在状态机内部，排查异步问题时不如原生 async 直观。最后是写法上的坑：连续的 await 会让本可并行的请求变成串行，需要并行时应该先用 Promise.all 合并，再统一等待。

还有一点容易被忽略：async 函数无论内部有没有 await，返回值都会被包成 Promise；函数里同步 throw 的错误也会变成 rejected Promise，而不是直接抛给调用方。因此调用处要么用 await 配合 try/catch，要么补上 .catch()，否则错误会被静默吞掉，这类问题在降级后的代码里同样存在。

两个编译选项的变化

–target es2016 与 es2017

2.1 之前 target 只到 es2015，2.1 补上了 es2016 与 es2017。target 决定两件事：语法降级的程度，以及默认加载哪个标准库声明。

选 es2016，** 与 **= 会原样保留，标准库里出现 Array.prototype.includes 的声明；选 es2017，async 函数不再需要 __awaiter，函数参数列表的尾逗号也原样保留，标准库里多了 Object.values、Object.entries 与 padStart/padEnd。

但要记住，target 只影响编译产物和类型声明，不会给运行时补任何东西。把 target 设成 es2017 再发布到只支持 ES5 的浏览器，产物会直接语法报错；如果运行环境已经是 Node 8，把 target 定为 es2017 则可以少一层降级，产物更接近源码。多数面向浏览器的项目仍应保持 es5，再用 lib 单独声明需要的标准库，例如 ["es2015", "dom"]，这样既能用上 Promise 的类型，又不必把整个目标抬到 ES2017。

target 与 module 是两件独立的事：target 决定语法降级，module 决定模块语句编译成 commonjs、amd 还是 es2015。把 target 设为 es2017、module 保持 commonjs，在 Node 项目里是很常见的组合；反过来，target 为 es5 时同样可以把 module 设为 commonjs，两者互不牵制。

–noImplicitAny 的改进

2.1 调整了隐式 any 的检查方式：报错位置更贴近声明，而不是等到使用处才暴露；对先声明、后赋值的变量，编译器会根据赋值演化出类型，不再一律当成 any。

这个改动让 --noImplicitAny 更容易落地：不必为了消除报错给每个临时变量补 any，正常的“先建空数组再填充”也不会被误伤。代价是类型检查更依赖代码顺序，如果变量在第一次确定赋值之前就被使用，仍然会得到隐式 any 的报错，这时应该补上显式类型而不是绕开检查。

配置对象与表单模型

配置合并是最常见的场景。用 Partial 描述“调用方只需要传想改的字段”，函数内部再补齐默认值，入参的意图就写进了类型。

表单模型更适合 Pick 与 Record。Pick 给表单或列表定义字段子集，避免把整张表的结构透传给组件；Record 描述键不固定的字典，例如表头映射、错误码文案。再配合 Readonly 标注只读视图，接口的入参与出参可以各用一份类型描述，不必靠注释约定。

不过工具类型不能替代运行时校验。它们描述的是编译期的形状，接口返回的 JSON、本地存储里读出的内容，在运行时都可能是任意结构；类型断言或类型标注只是让编译器相信我们，边界处仍然要自己检查字段是否存在、类型是否正确。

后来者站在什么基础上

2.1 之后，四个工具类型逐渐成了声明文件里的通用词汇，后续版本继续沿两个方向推进：检查更严，2.3 用 --strict 把一批开关打包；推断更准，2.4 让函数的返回值也参与泛型推断。但类型系统能做的仍然只是查表与映射，还不能在类型层表达条件分支，遇到需要按类型分流的场景，当时只能用重载或联合类型手工展开。把 keyof、索引访问、映射类型这三件工具理解透，比记住某个内置类型的名字更有价值，因为新的工具类型基本都是这三者的组合。

小结

TypeScript 2.1 的核心，是把类型从“描述值”推进到“描述键”：keyof 取出键联合，T[K] 按键取值，映射类型拿着键重新造类型，而 Partial、Readonly、Pick、Record 只是这套机制的四份标准答案。对象 rest/spread 让不可变更新有了简洁写法，async 降级让同一份源码可以同时服务新老环境。使用时记住三个边界：工具类型都是浅层的，对象展开是浅拷贝，async 降级依赖 Promise 与辅助函数。把这些边界写进团队约定，2.1 带来的表达力才算真正落到工程里。
