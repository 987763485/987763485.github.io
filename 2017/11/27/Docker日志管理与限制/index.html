Docker 日志管理与限制

本文属于《Docker 与 Kubernetes》第 12/51 篇
上一篇系列目录下一篇

容器上线一段时间之后，很多团队遇到的第一个磁盘告警都来自 /var/lib/docker，而罪魁祸首往往是一个几十 GB 的容器日志文件。本文从容器日志的产生方式讲起，说明默认 json-file 驱动的落盘位置与读取机制，再给出全局与单容器的日志限制配置，并整理应用侧写法与排错命令。读完本文，你应该能为自己的环境配出一套“日志可查、磁盘可控”的方案。

一、容器日志从哪里来

在物理机或虚拟机上，应用通常把日志写进 /var/log 下的文件，运维再用 logrotate 切割。容器改变了这件事的默认路径：Docker 并不关心容器里写了哪些文件，它只接管容器主进程的标准输出与标准错误。

具体来说，docker run 启动容器时，Docker 会把 PID 1 进程的 stdout 与 stderr 接到一条管道，再交由宿主机上的日志驱动（logging driver）处理。应用打印到控制台的每一行，都会经由这个驱动被处理：默认情况下写入宿主机的 JSON 文件，配置之后也可以转发给 syslog、journald、fluentd 等外部系统。

这意味着两件事。第一，容器内 /var/log/app.log 这类文件对 Docker 来说是“不可见”的，它既不会被 docker logs 读到，也不会随容器删除而留下任何痕迹——文件就在容器的可写层里，容器一删就没了。第二，日志的归宿由启动容器时的驱动配置决定，而不是由应用写了什么文件决定。

docker logs 做的事情很朴素：找到这个文件，逐行解析 JSON，把 log 字段还原成文本输出。它不做级别过滤、不做字段提取，也不跨容器聚合。所以“日志里为什么有一堆 JSON”和“为什么 docker logs 不支持按级别查询”这两个问题的答案是同一个——默认驱动的职责只是原样持久化字节流，解析与检索交给下游系统。

由此可以推出几个使用边界：

  • docker logs 能用的前提是驱动把日志存在本地且可读。json-file 与 journald 满足这一点，而 syslog、fluentd、gelf、awslogs、splunk 把日志发走之后本地不留副本，此时执行 docker logs 会提示该驱动不支持读取。
  • 日志文件的属主是 root，权限为 0600。普通用户需要加入 docker 组或使用 sudo 才能直接查看，这也避免了同一台机器上不同业务之间互相窥探日志。
  • 容器删除时，其日志目录一并删除。需要长期留存的日志，要么挂载出来，要么走集中式驱动，不能指望 docker logs 充当归档。

三、日志无限增长的代价

json-file 驱动默认不做任何轮转。容器的日志文件会一直增长，直到磁盘写满或容器被删除。这不是理论风险：一个每次请求打印两行访问日志的服务，按每秒 100 次请求、每行 200 字节估算，一天就能写出约 3 GB；如果某个异常路径在循环里打日志，几分钟就能吃掉几十 GB。

磁盘写满的后果远不止“应用写不了文件”。Docker daemon 自身也在这块盘上工作：镜像层、容器可写层、元数据数据库都在 /var/lib/docker。一旦分区满，会出现下面这些连锁反应：

  1. 应用写日志失败，可能直接抛异常退出，而退出原因又因为写不进日志而无法排查。
  2. 镜像无法拉取、容器无法创建，报错信息往往是 no space left on device，与真正的故障点相隔很远。
  3. daemon 在写元数据失败后可能进入异常状态，docker ps 卡住不返回，重启 daemon 也需要先腾出空间。
  4. 如果使用大量小文件（例如应用自己在容器内切割日志），还可能先耗尽 inode，此时 df -h 显示还有空间，但就是创建不了新文件，需要用 df -i 才能看出来。

注意 max-file 只有在同时设置 max-size 时才有意义。只给 max-file 而不给 max-size，文件永远不会触发轮转，个数上限也就无从谈起。轮转时当前文件被重命名为 <id>-json.log.1，编号依次后移，超出 max-file 的最旧文件被删除；docker logs 会一并读取轮转文件，只是总量被封了顶。

六、换驱动：journald、syslog、fluentd

除了 json-file，Docker CE 17.09 还支持 journald、syslog、fluentd、gelf、awslogs、splunk 等驱动。它们的差别不在于“能不能记日志”，而在于日志最终存在哪里、由谁检索。

journald 把日志交给宿主机的 systemd-journald，用 journalctl 就能按服务、时间、优先级查询，还能借助 journal 自带的限额控制总量。它的好处是与宿主机操作系统日志统一管理，docker logs 依然可用；代价是日志受 journal 的存储策略约束，容器与宿主机日志混在一起，多租户环境里需要额外区分。

syslog 把每行日志转发到本机或远端的 rsyslog、syslog-ng，适合已经有 syslog 集中收集体系的老机房。配置时用 --log-opt syslog-address=tcp://10.0.0.5:514 指定地址，也可以用 syslog-format 调整报文格式。日志一旦发走，本地不留副本，docker logs 随之失效。

fluentd 面向日志管道：容器把结构化记录发给 fluentd，再由 fluentd 做缓冲、打标签、分发到下游存储或检索系统。它适合“应用只负责产出、平台统一处理”的分工，fluentd-address 指向收集端即可。需要注意的是，收集端不可达时驱动的行为会影响应用启动与写入，配置前要确认好缓冲与失败策略，不要在网络抖动时把业务拖下水。

选择驱动的判断标准可以归纳成三条：团队已有的日志基础设施是什么，就优先接什么；是否需要 docker logs 这种“就地看一眼”的能力；日志量级是否已经超出单机文件的承载范围。三者冲突时，通常让生产环境走集中式驱动，同时在测试环境保留 json-file 便于排查。

七、应用侧：格式、多行与脱敏

驱动和参数只是兜底，真正决定日志质量的是应用怎么写。以下几条值得写进团队规范。

第一，日志只写标准输出与标准错误，不要往容器内文件写，更不要在容器里装 logrotate 自己切割。容器可写层里的文件会随着写入不断膨胀，切割出来的旧文件同样占用空间，而且容器重建后全部丢失，运维却在宿主机上找不到任何东西。

第二，优先输出单行 JSON。结构化的字段让下游可以按 level、request_id、path 过滤和聚合，而不是用正则去啃自由文本：

要注意，json-file 驱动会在外面再包一层自己的 JSON，于是文件里出现“外层 log 字段里套着一段 JSON 字符串”的双层结构。这不影响采集，但检索时要多解析一次，团队应提前约定好外层字段名。

第三，日志级别要能调，生产默认 info，debug 只在排障时短时打开。很多磁盘事故的根因就是某次排障把 debug 打开后忘了关。

多行日志：让堆栈成为一条记录

Java 的异常堆栈、Python 的 traceback 天然是多行的。日志驱动按行切分，于是一次异常在 json-file 里会变成十几条独立的记录，每条只带一个堆栈帧，检索时既难聚合也容易漏看上下文。这是容器日志最典型的“格式事故”。

解决方向有两个。应用侧的办法最彻底：把整个异常序列化成一行再输出，例如放进 JSON 的 error 字段，把内部换行转义成 \n，这样驱动看到的就是一条记录，堆栈内容完整保留，下游解析后仍可还原。代价是本地用 less 直接看文件时可读性差一些。

采集侧的办法是让具备多行合并能力的收集端处理，例如 fluentd 一侧按行首特征合并——以空格或 at 开头的行视为上一条的续行，直到出现新的时间戳或日志级别为止。要点在于合并发生在日志离开容器之后，因此它要求日志先转发给收集端；docker logs 读到的仍然是拆散的行，这一点无法靠驱动配置改变。团队应在“应用吐单行”与“采集端合并”之间选一条并写进规范，混用会让同一套检索规则时灵时不灵。

敏感信息：脱敏必须前置

安全方面有三条底线。其一，任何密码、访问令牌、会话 Cookie、完整的证件号与银行卡号都不得进入日志，日志系统通常比数据库更容易被更多人访问。其二，脱敏必须在应用侧完成，日志驱动只负责搬运字节，不会替我们识别敏感字段；采集端做过滤属于“第二道防线”，不能当作唯一防线。其三，不要把环境变量整体打印出来做“启动自检”，这类日志经常顺带泄露数据库口令和云平台密钥。使用 syslog 走 UDP 时还要意识到日志是明文传输的，跨网段收集应改为 TCP 并配合 TLS 或专线。

接下来是笔者见过最多的几个坑。改完 /etc/docker/daemon.json 没有重启 docker，配置等于没写；重启了但只对新容器生效，老容器依旧无限增长，需要重建。max-size 不带单位会被当成字节；max-file 只是保留个数，不是大小。给 syslog 驱动传 max-size，容器直接起不来。用 rm 删掉正在写的日志文件，空间不会立刻释放，因为 daemon 还持有文件描述符，正确做法是重建容器或先把文件截断。最后一种更隐蔽：容器里跑了应用自带的日志切割，宿主机上 du 看到的目录很小，可写层却在悄悄膨胀，问题被推迟到某次镜像提交或磁盘告警时才暴露。

日志驱动不支持读取时，docker logs 报错是设计使然，排查应转向 journald、syslog 服务端或 fluentd 的下游，而不是反复重启容器。

小结

容器日志来自标准输出，默认由 json-file 驱动逐行落盘且不做轮转，必须用 max-size 与 max-file 封顶。daemon.json 提供全局默认，单容器与 Compose 按服务覆盖，改动需要重启 daemon 且只对新容器生效。应用侧应输出单行结构化日志、做好脱敏、不要自行切割文件。选驱动时对齐已有的日志基础设施，当驱动不支持读取时，排查要转向集中日志系统。
