Docker 健康检查与重启策略

本文属于《Docker 与 Kubernetes》第 13/51 篇
上一篇系列目录下一篇

容器跑起来了，端口也映射了，可请求还是 502，这类问题在把服务搬进 Docker 的头几个月里几乎每周都会遇到。本文从“进程活着”和“服务可用”的差别讲起，介绍 Dockerfile 中的 HEALTHCHECK、Docker CE 17.09 新增的 start-period 参数，以及四种重启策略的语义。读完之后，你应该能为一个 HTTP 服务配出可用的健康检查，并且清楚它到底能做什么、不能做什么。

从“容器在运行”到“服务可用”

docker ps 的 STATUS 一栏写着 Up 3 minutes，不少人就此认为服务没问题。这个状态只说明容器里的 1 号进程还在，既不表示端口已经能接受连接，也不表示业务逻辑能正常返回。一个 Go 或 Java 服务从进程启动到真正可服务，中间还有几步：监听端口、注册路由、初始化连接池、预热缓存、加载配置。在这几秒到几十秒的窗口里，进程活着，请求却会失败。

更麻烦的是一种“半死”状态。进程没有退出，但已经死锁、连接池耗尽，或者被长时间的 GC 停顿拖住，对外表现为持续超时。这类故障不会产生“退出”事件，只看进程在不在，等于放弃了对它的可见性。

所以判断服务状态其实包含两个不同的问题：进程是否还值得保留，以及实例现在能不能接收流量。前者关心“还活着吗”，后者关心“能干活吗”。Docker 的健康检查只给了一个笼统的状态，没有把两者拆开，实际项目里往往要靠两个端点自己区分，后文实战一节会展开。

从 Docker 1.12 起，镜像可以声明一条健康检查命令。引擎按固定节奏在容器内执行它，把结果记成三种状态：starting 表示刚进入探测，healthy 表示最近一次成功，unhealthy 表示连续失败达到阈值。docker ps 的 STATUS 会带上括号说明，docker inspect 里则有完整的连续失败次数和每次探测的输出。

这里要先记住一个前提：健康状态是给人看、给外部系统读的元数据，Docker 引擎本身不会因为容器变成 unhealthy 就做任何处置。它不停容器、不重启容器，也不会把端口映射摘掉。这个误解是后面许多坑的源头，我们会在重启策略一节专门澄清。

在 Dockerfile 中声明 HEALTHCHECK

最常见的声明位置是 Dockerfile，由它派生的所有容器默认继承这条检查。一条 HEALTHCHECK 由选项和命令两部分组成，选项控制探测节奏，命令决定判断逻辑。

命令的退出码是唯一的判断依据：0 表示健康，1 表示不健康，2 保留给将来使用，其余非零值一律按不健康处理。命令打印什么都不影响结论，输出只是被截断后存进日志，供人排查。

命令有 exec 和 shell 两种形式。exec 形式写成 JSON 数组，不经过 shell；shell 形式等价于在容器里执行 /bin/sh -c，带 || exit 1 的写法只能用这一种。代价是多一层 sh 进程，超时被杀掉的是 sh，它派生的子进程未必能一起清理干净；命令里含引号或 $ 时，转义也要多留一份心。

选项不给就用默认值：interval 30 秒、timeout 30 秒、retries 3 次、start-period 0 秒。这套默认值对本机调试够用，对生产来说探测太稀疏，通常都要调。一个 Dockerfile 里写多条 HEALTHCHECK 只有最后一条生效，派生镜像不想要时用 HEALTHCHECK NONE 关掉，运行时也可以用 docker run --no-healthcheck 临时禁用。

运行参数、健康状态与健康日志

探测节奏可以在启动时覆盖，不必为了改一个 timeout 重新构建镜像。docker run 提供 --health-cmd、--health-interval、--health-timeout、--health-retries，以及 Docker CE 17.09 才加入的 --health-start-period。

start-period 专门解决启动慢的问题：宽限期内的失败不计入 retries，一旦成功就提前进入正常判定，宽限期结束后的失败才开始累计。冷启动要三四十秒的服务，把 retries 调大不如把宽限期设对，因为后者只放宽启动阶段，不影响运行期的灵敏度。

看状态最直接的是 docker ps，Up 2 minutes 后面会多出一个 (healthy)、(unhealthy) 或 (health: starting)。要精确判断，用 docker inspect 读 State.Health：

Status 是三态字符串，FailingStreak 是当前连续失败次数，Log 保留最近若干次探测的开始时间、耗时、退出码和输出。排查“为什么被判成不健康”时，看最后一条日志往往比猜快得多。批量筛选用 docker ps -q --filter health=unhealthy。

还有一点常被忽略：探测进程本身也跑在容器里，会占用 CPU 和进程号。手动 docker exec 跑一遍同样的命令，是区分“检查写错了”和“服务真坏了”的最快办法。

健康检查该查什么，不该查什么

健康检查的质量取决于那条命令到底查了什么。按代价从低到高，常见的选择有四类。

TCP 端口。用 nc -z 127.0.0.1 8080 之类的命令确认端口在监听，它只能证明 socket 打开了，不能证明应用能处理请求——刚 bind 完还没注册路由的进程同样能通过。适合当兜底，不适合当唯一手段。

HTTP 接口。请求一个专用的 /healthz 并判断状态码，这是最常用也最平衡的方式。要点是必须让非 2xx 变成非零退出码：curl 不加 -f 时，服务返回 500 也会以 0 退出，健康检查于是永远显示正常；加上 -f 才会把 4xx/5xx 映射成失败。wget 则要配 -q -O /dev/null，它默认把响应体写到标准输出。

数据库连接。如果健康检查必须覆盖依赖，就让端点里做一次极轻的探测，比如带 500 毫秒超时的 Ping，复用已有连接池，不要每次新建连接，更不要在检查里执行统计、全表扫描或任何写入。

依赖服务。把上游纳入检查要非常谨慎：A 查 B、B 查 C，一次 C 的抖动会让整条链路上的容器同时变成 unhealthy；如果外面还挂了自动重启脚本，就会演变成重启风暴。依赖关系更适合放在就绪判断里，由负载均衡决定是否摘流量，而不是让容器自己判死刑。

反过来，有几件事不该放进健康检查：跑业务查询、调用计费或短信接口、写临时文件、清理缓存。判断标准很朴素——这条命令会被每个实例按秒级频率重复执行，它必须只读、幂等、快速，耗时最好控制在 timeout 的三分之一以内。

健康检查的代价与节奏

健康检查不是免费的，代价体现在三处：探测开销、判定延迟、误判带来的连锁反应。

interval 太短是第一类问题。每次探测都要 fork 一个进程、建立一次连接，1 秒一次意味着单容器每天八万多次探测；十几二十个容器跑在同一台宿主机上，这些开销会实打实体现在负载曲线上，日志也会被检查输出刷满。10 到 30 秒是多数服务的合理区间。

timeout 太长会让探测排队。单次探测迟迟不返回，下一次只能等它结束，实际间隔被拉长，发现故障的时间也随之漂移。经验上 timeout 取 interval 的三分之一到二分之一，比如 interval 10 秒配 timeout 3 秒。

retries 决定灵敏度与稳定性的平衡。设为 1，一次网络抖动或 GC 停顿就足以把状态打成 unhealthy；设得太大，故障要等很久才暴露。3 次是默认值，也是多数场景的起点。按 interval 10 秒、retries 3 计算，从第一次失败到标记 unhealthy 大约要二三十秒，这段时间应该能和上游的熔断、重试预算对上。

start-period 太短是最隐蔽的一类。宽限期只有 10 秒，应用冷启动要 40 秒，那么从第 10 秒起失败就开始计数，还没等到真正就绪，失败已经攒够。表现是“每次发布都有一段时间不健康”，很容易被误判成网络问题。把宽限期设成实测启动时间的一点五倍左右，比反复调 retries 更靠谱。

还有一项成本是日志。检查命令输出较多时，Log 里堆积的内容既占内存也干扰排查，所以命令要尽量安静，成功时不输出任何东西。

重启策略的四种语义

重启策略回答的是另一个问题：容器退出之后怎么办。它和健康检查是两套独立机制，经常被混为一谈。

策略 触发条件 手动 stop 之后 守护进程重启之后
no 从不重启，默认值 保持停止 保持停止
on-failure[:N] 仅非零退出码，最多 N 次 保持停止 不覆盖此场景
always 任何退出码 停止，dockerd 重启后恢复 重新拉起
unless-stopped 任何退出码 保持停止 保持停止

策略只能在 docker run 时指定，Dockerfile 里没有对应指令；已经运行的容器可以用 docker update --restart=unless-stopped api 修改，不必重建。

几个细节值得记住。on-failure 的触发条件是退出码非零：进程异常退出会重启，而 docker stop 属于人为停止，不该被当成故障；被 SIGKILL 时退出码是 137，按失败计。always 不区分正常退出和崩溃，适合“本来就该一直存在”的 Web 服务，但用它掩盖启动即崩溃的配置错误，只会收获一条不断刷新的 Restarting (1) 3 seconds ago。Docker 的重启带递增退避延迟，不会瞬间打满 CPU，日志量却依然可观。

和 systemd 对照一下会更清楚：systemd 的 Restart=on-failure 由 PID 1 托管进程，能拿到退出码和信号；Docker 的重启由 dockerd 托管容器，触发源是容器退出事件。语义相近，职责不同，在容器里再套一个 systemd 并不是推荐做法，两者选其一即可。

最后一个误区是给容器配了 always 就以为万事大吉。如果进程没有退出，只是不再响应，always 什么都不会做，这正是下一节要处理的情况。

健康检查不会重启容器

这是本文最需要强调的一句：健康检查不触发重启。容器变成 unhealthy 时，引擎只更新 State.Health，容器继续运行，端口继续映射，RestartCount 保持为 0。

可以自己验证：把 health-cmd 写成 exit 1，跑一个带 --restart=always 的容器，等几分钟，docker ps 会显示 Up 3 minutes (unhealthy)，而 docker inspect --format '{{.RestartCount}}' 仍然是 0。重启策略只响应“退出”事件，健康检查根本不产生退出事件。

处置 unhealthy 有三条路。一是让应用自己退出：遇到配置缺失、端口被占、迁移失败这类不可恢复错误时直接以非零码退出，把判断权交给 on-failure。这是最省事也最可靠的做法，它复用了一条本来就存在的路径。

还有几个收尾的坑。其一，alpine、distroless 和 scratch 里通常没有 curl，检查命令会以 127 退出，容器从第一秒起就是 unhealthy，写命令前先确认工具存在。其二，localhost 可能先解析到 ::1，而服务只监听了 127.0.0.1，探测会被拒绝，所以检查里显式写 127.0.0.1。其三，shell 形式的检查命令超时后被杀的是外层 sh，子进程可能残留，能用 exec 形式就别偷懒。其四，配完健康检查不等于有人看：unhealthy 既不告警也不重启，监控必须把 State.Health.Status 采走。

小结

容器在运行只是进程层面的信号，服务可用需要一条真正检查业务路径的命令。健康检查负责暴露状态，重启策略负责在容器退出后把它拉回来，两者之间没有自动连接，unhealthy 必须靠应用自退、外部巡检或编排层处置。参数上先按实测启动时间把 start-period 设对，再让 interval、timeout、retries 与上游的重试预算对齐。最后把健康状态接入监控，否则它只是一行没人看的括号。
