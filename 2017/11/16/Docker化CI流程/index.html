Docker 化 CI 流程

本文属于《Docker 与 Kubernetes》第 18/51 篇
上一篇系列目录下一篇

持续集成最难的部分往往不是脚本本身，而是“脚本在谁的机器上跑”。本文从把 CI 流程整体搬进容器的动机讲起，对比 DinD 与挂载宿主机 docker.sock 两种执行模型，再按拉代码、构建镜像、跑测试、推送、部署触发这几个阶段给出可落地的写法，最后用 GitLab CI 与 Jenkins 各给一份示例，并总结缓存、标签、清理上的常见坑。适合已经在用 Jenkins 或 GitLab CI、但构建环境仍然靠手工维护的团队参考。

为什么 CI 要容器化

2017 年上半年，我们的 CI 还跑在一台 Ubuntu 16.04 的构建机上：Node、Go、MySQL 客户端、Android SDK 全部装在同一台机器里，用几段 shell 脚本串起来。项目少的时候这样很省事，项目一多，问题就集中爆发：A 项目要求 Node 6，B 项目刚升到 Node 8，两个项目共用一份全局安装的 node_modules；某个同事为了调试临时升级了全局的 gulp，第二天三个项目的构建同时变红。排查半天，结论是“构建机上某样东西被改了”。

容器化解决的正是这一类问题，具体可以拆成三个诉求。

环境一致。把编译工具链、运行时、系统库都写进 Dockerfile，开发本地、CI、预发用的是同一份镜像。构建失败时，任何人 docker run 同一个镜像就能复现，而不是先问“你机器上装的是什么版本”。

依赖隔离。每个项目、每个阶段用各自的镜像。A 项目锁 Node 6.11，B 项目锁 Node 8.6，互不影响；集成测试需要 MySQL 5.6 和 5.7 两个版本时，也只是起两个不同 tag 的容器而已。

构建产物可复现。镜像有 tag，也有内容摘要，构建时用 node:8.6.0 而不是 node:latest，半年后回滚旧版本，拿到的仍然是同一套工具链。这一点在排查“历史版本为什么构建不出来”时尤其重要。

与虚拟机做构建机相比，容器启动是秒级，单机可以并发跑多个任务。Docker CE 在 2017 年已迭代到 17.09，多阶段构建（17.05 起）也已稳定，把 CI 交给容器不再是技术赌注。

两种执行模型：DinD 与挂载 docker.sock

docker 命令本身几乎不干活，它只是把请求通过 HTTP 发给 dockerd。所以在 CI 里用 Docker，第一个要回答的问题是：daemon 在哪里。当期有两种主流做法，选错了后面全是坑。

DinD：在容器里再跑一个 dockerd

DinD（Docker-in-Docker）的做法是让 job 容器自己启动一个 dockerd，docker 客户端通过 TCP 连过去。GitLab CI 里用 services 声明一个 dind 容器即可，alias 让客户端能用主机名 docker 找到它：

它的优点是干净：job 结束容器销毁，构建产生的镜像、容器、缓存一起消失，不会污染宿主机，也不会和别的 job 抢同一个 daemon。代价是三点。第一，dind 容器需要 --privileged，这等于把内核能力交给了 job；第二，每个 job 都是新的 daemon，镜像层缓存默认不跨 job 保留，除非额外配置；第三，2375 端口是明文，只应在 runner 内部网络里使用，跨主机时必须换成 TLS 的 2376。

挂载 docker.sock：借用宿主机的 daemon

另一种做法是不启动新的 daemon，只把宿主机的 /var/run/docker.sock 挂进 job 容器：

容器里只有客户端，构建实际发生在宿主机上，所以镜像直接落在宿主机，层缓存天然被所有 job 共享，第二次构建往往快很多。但这里有一个必须说清的风险：能访问 docker.sock 的进程，等价于宿主机上的 root。它可以起一个挂载 / 的容器把宿主机文件读走，也可以直接关掉别的服务。任何来自 Pull Request 的代码都不应该在这样的 runner 上执行。

还有一个容易踩的细节：-v 的源路径是由 daemon 在宿主机上解析的，不是由客户端容器解析。如果客户端容器内的工作目录和宿主机不一致，就要保证两边路径相同，或者改用命名卷传递构建上下文。

对比项 DinD 挂载 docker.sock
隔离性 较好，job 结束即销毁 差，与宿主机同级
权限要求 需要 privileged 需要可写 sock
层缓存 默认不跨 job 天然共享
并发构建 互不干扰 共用 daemon，需注意资源
适用场景 公有云、多租户 runner 内网自建、可信分支

笔者的取舍是：内部可信分支用 sock 挂载，图缓存和速度；外部贡献者的构建走 DinD，或放到独立构建机上。

流水线的五个阶段

模型定了，接下来是流程本身。一个容器化的 CI 流水线通常可以拆成五步，每一步都围绕同一份镜像展开：

flowchart TD
    A[拉取代码] --> B[构建镜像]
    B --> C[在容器里跑测试]
    C --> D[推送镜像到仓库]
    D --> E[触发部署]

拉代码：由 CI 系统负责，通常还会带上 submodule 和 tag。版本号要在这一步取好，后续镜像里不一定有 .git。

构建镜像：用项目根目录的 Dockerfile 构建出 app:<commit>，这是整条流水线的主产物。

跑测试：直接 docker run 这个镜像执行测试命令，而不是在 runner 宿主机上跑。这样测的就是待发布的那个镜像。

推送镜像：测试通过后再 docker push，标签同时打 latest 和 commit 短号。先推后测是反模式，仓库里会堆满没通过测试的镜像。

触发部署：CI 只负责发出信号，比如调用部署系统的接口，或者打一个带版本号的 git tag。本期不展开部署侧的实现。

阶段之间传递的不是工作目录，而是镜像标签。把 app:<commit> 写进一个文本文件作为 artifact 传给下一阶段，比让每个阶段各自重新构建要可靠得多。

几个细节值得强调。基础镜像写 node:8.6.0 而不是 node:8 或 node:latest，是因为后者会随时间漂移，今天的 latest 和半年前的不是同一套东西。npm install 依赖 package-lock.json，所以它必须提交进仓库，且要在 COPY . . 之前单独拷贝。apt-get update 和 install 写在同一条 RUN 里，否则拆开后 update 那层会被缓存，install 却可能拉到过期的索引。

缓存目录也要在镜像里规划好。npm 的缓存默认在 /root/.npm，Go 在 /go/pkg，Maven 在 /root/.m2。如果 runner 上把这些目录挂成卷，或者用 CI 的 cache 保留下来，依赖安装的耗时可以从几分钟降到十几秒。

缓存：层复用、runner 缓存与 –cache-from

Docker 的构建缓存是按层命中的：某条指令的输入没有变化，就直接复用上一次的结果。这带来两个实践要求。第一，变化频率低的指令放前面，安装依赖在拷贝源码之前。第二，任何会让输入变化的操作都要小心，比如 COPY . . 之后紧跟 npm install，改一个 README 就会让依赖重装。

在单机上这已经够用，但 CI runner 往往是临时的，job 一结束容器和镜像层都没了。这时有三种补缓存的办法。

最直接的是把缓存目录挂出来。GitLab CI 的 cache 可以按 lock 文件的校验和设置 key，node_modules 变了才重建；Jenkins 则更常见的是在构建机上挂一个持久卷给 ~/.npm。这类缓存和 Docker 层缓存是两套东西，前者缓存的是下载结果，后者缓存的是整条指令的执行结果。

第二种是 --cache-from，Docker 17.05 起支持。思路是把上一次构建的镜像拉回本地，让构建器把它当作缓存来源：

它的前提是缓存镜像里的层在本地真实存在，所以必须先 pull，光写参数没有用。实践中通常让每个分支维护一个 cache 标签，主分支构建成功后覆盖它。要注意 --cache-from 只对本地已存在的层生效，跨 registry 的按层复用并不像后来的构建工具那样智能，命中率取决于上一次构建的指令是否完全一致。

第三种是让 runner 长期存活，镜像层留在宿主机上。这也是挂载 docker.sock 的隐性收益：所有 job 共享同一份层缓存。代价是并发时可能互相干扰，磁盘也会越用越多。

镜像标签与私有仓库推送

镜像标签决定了半年后还能不能找回某次构建。我们的约定是每个镜像至少打两个标签：一个是不可变的提交短号，一个是跟随分支的 latest 或分支名。

只用 latest 是典型的坏习惯：出问题时无法回答“线上跑的是哪次提交”，回滚也没有明确目标。只用工号也不行，工号在不同 CI 系统之间不可比。提交短号加构建号，既方便人读，也方便机器追溯。标签到镜像摘要是多对一的关系，需要精确固定时，记下 docker inspect 里的摘要即可。

清理、资源控制与几个反复出现的坑

容器化 CI 跑上一个月，构建机最常见的故障是磁盘满，而不是脚本写错。每个 job 都会留下悬空镜像、停止的容器和构建缓存，长期存活的 runner 尤其明显。可以在 job 结束时收尾：

同时限制并发。DinD 每个 job 都带一个 daemon，内存和磁盘占用是叠加的；sock 挂载虽然轻，但多个 docker build 同时抢 CPU，构建时间反而更长。用 docker stats 观察峰值，把 runner 的并发数定在一个既跑得满又不至于把机器拖垮的值，比事后加磁盘更有效。

最后是几个反复出现的坑。镜像里没有 git：构建脚本里执行 git rev-parse 会直接失败，版本号要在 CI 阶段取好，用 --build-arg 传进去。容器内的时区是 UTC：依赖本地时间的测试在 runner 上会莫名其妙失败，要么在镜像里设 TZ，要么让测试不依赖本地时区。docker.sock 权限过大：前面提过，但仍最容易被忽略，能提交代码的人即可借此拿到宿主机权限，公有仓库要把这类 runner 隔离出去。上下文和缓存的浪费：.dockerignore 没写、COPY 顺序不对，构建时间会从一分钟变成十分钟。

小结

容器化 CI 的核心不是“用上 Docker”，而是把构建环境、依赖和产物都变成可版本化的对象：Dockerfile 固定工具链，镜像标签固定产物，两者合起来才能回答“这次构建到底用了什么”。执行模型上，DinD 隔离好但慢且需要特权，挂载 docker.sock 快但等于把宿主机交给 job，按仓库的可信程度二选一。流水线本身保持简单：构建、测试、推送都用同一份镜像，测试通过再推，标签同时留 commit 短号与 latest。缓存和清理要一开始就设计，否则半年后一定会在磁盘和构建耗时上付出代价。
