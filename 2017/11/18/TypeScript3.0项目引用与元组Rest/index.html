TypeScript 3.0 项目引用与元组 Rest

本文属于《TypeScript 学习路线》第 30/74 篇
上一篇系列目录下一篇

TypeScript 3.0 在本文写作时并不存在：2017 年 11 月的稳定版本是 2.6，3.0 只是 issue 列表和邮件组里被反复提起的名字。项目引用（project references）与元组 rest（tuple rest）都属于这个尚未发布的版本上的讨论，社区把它们写成提案、画出草图，但没有一行实现可以从 npm 上装到。本文先把 2017 年多包项目真实的做法讲清楚，再看这两个方向各自想解决什么问题，最后给出今天就能用的替代方案与迁移建议。

先厘清时间线：3.0 还不存在

打开 npm 安装 TypeScript，2017 年 11 月拿到的是 2.6。这个版本在 10 月底发布，补上了更严格的函数参数检查、// @ts-ignore 与本地化提示，也顺手修掉了一批声明文件合并的老问题。紧随其后的版本还在开发分支上，而 3.0 连里程碑都没有排定，只是设计讨论里一个用来指代”下一轮大改”的称呼。

所以本文里出现的 composite、references、tsc --build，以及 [string, ...number[]] 这种类型写法，全部是讨论稿里的样子，不是可以粘进项目的语法。笔者把它们写出来，不是为了教读者马上使用，而是让读者在评审会上听到这些词时不至于发懵，也能判断某个方案值不值得等。

还有一个容易被忽略的前提：提案读起来通顺，落到编译器上却要解决类型推断、错误信息、增量构建等工程问题。因此下面的展望只讨论”想解决什么问题”，不讨论”什么时候能用”。

2017 年的多包项目是什么样子

一个稍具规模的前端团队，当年常见的仓库结构是这样的：根目录放一个 package.json 和一个 lerna.json，下面 packages/ 里并排放着三到十个子包。典型切法是基础库、组件库、业务应用各占一个包：@scope/core 放工具函数与数据模型，@scope/ui 依赖 core 做组件，@scope/app 再依赖前两者组装页面。用 lerna 的理由很实在——改跨包接口时不必在三个仓库间来回提合并请求，也不用先发测试版本再升级依赖。

每个子包有自己的 package.json，用 main 指向编译产物、用 types 指向声明文件；每个子包也有自己的 tsconfig.json，因为它们的输出目录不同，依赖的全局类型也不同——core 要照顾 Node 环境，app 则需要 dom 库。如果每个子包都把 strict、target、moduleResolution 抄一遍，改一次规范就要改十次，extends 正是为这个场景准备的。

跨包引用的三条现有路径

多个 tsconfig.json 只解决”怎么编译”，不解决”编译时怎么找到隔壁包”。2017 年可用的办法基本只有三条，每条都有明确的适用场景。

它的好处立竿见影：在 app 里写 import { parseDate } from '@scope/core'，跳转直接落在 core 的 .ts 上，改完立刻生效，不必先构建。代价是边界被抹掉——app 的编译把 core 源码一起拉进程序，rootDir 稍有不慎就报”文件不在 rootDir 下”，产物层级也会乱。更麻烦的是运行时：编译器认识 @scope/core，Node 不认识，产物里的 require 仍要靠 node_modules 里的真实包；路径别名还得在构建工具的 alias 里同步一份，两处不一致就会”编译通过、运行报错”。

第二条是软链接。lerna bootstrap 会把仓库内的包互相链进 node_modules，等价于手工 npm link。这条路最贴近真实发布形态：代码里写的包名就是发布后的包名，运行时和编译时看到的是同一个东西。前提是隔壁包已经产出声明文件，并且 package.json 的 types 字段指对了位置：

现有做法为什么让人难受

把上面三条路拼起来能跑，但维护成本会在包数量超过五个之后迅速上升，痛点集中在四处。

第一是构建顺序靠人脑记。core 改了接口，ui 必须先重编，app 才能拿到新类型；若 app 先跑，读到的还是上一次的 lib/index.d.ts，编译器不报错，只按旧类型安静检查，等运行时才炸。团队只能把顺序写进根目录脚本，或每次全量构建，用时间换确定性。

第二是没有增量。tsc -p 每次都是整包重编，一个两百行的改动要等十几秒；开了 declaration 之后还要额外写盘。想只编改动过的部分，只能自己写脚本比对文件时间戳，脆弱且难维护。

第三是声明文件重复且会漂移。路径映射与声明文件消费是两套解析逻辑，跳转时而落在 src，时而落在 node_modules/@scope/core/lib；后者是上次构建的快照，可能与源码差了两个提交，对着过时定义排查半天，才发现是没重新编译。

第四是编辑器体验不一致。软链接在部分工具链下被解析成真实路径，同一个文件出现两份实例，类型被判定为不兼容；2.5 的 --preserveSymlinks 只控制链接解析方式，管不了构建顺序与声明文件时效。这四条叠加，就是多包 TypeScript 项目”能跑但不敢动”的根源。

展望：项目引用想把包边界变成编译边界

社区关于项目引用的讨论，起点正是上面那个顺序问题。思路并不复杂：依赖关系已经写在 package.json 里，为什么不让编译器也读一份？如果每个包在自己的 tsconfig.json 里声明”我依赖谁”，编译器就能排出拓扑顺序，先编依赖再编上层，而不是靠脚本里的人肉次序。

这个方向想要达到的效果，可以拆成三句话。其一，依赖关系显式化，引用写在配置里而不是藏在文档或 shell 脚本中，新同事克隆仓库后不必问人就知道先编谁。其二，跨包解析改走声明文件而不是源码，类型边界清晰，也不会把对方的源码卷进自己的 rootDir。其三，为增量构建留出入口，编译器知道了图结构，就有条件跳过没有变化的工程。

展望：元组 rest 想解决什么

另一条讨论线在类型层面。2017 年的元组是定长的：[string, number] 恰好两个元素，多一个少一个都不行。这个规则在描述固定结构时很好用，但一碰到”前面几个参数固定、后面数量不定”的函数就失灵了。

现实的例子随处可见：日志函数的第一个参数是级别，后面是任意多个数值指标；路径拼接函数的第一个参数是根路径，后面是任意多段子路径。用元组写不出来，用 any[] 又丢掉首元素信息，调用方传错顺序也没人提醒。当时的妥协是写重载，为”一个指标””两个指标””三个指标”各写一条，第四条就没人愿意写了。

社区讨论中的元组 rest，目标就是把这层信息补回来：允许在元组类型里用 ... 表示”剩余部分”，并且剩余部分本身带类型。设想中的写法是这样，同样未发布，2.6 无法解析：

它与定长元组不是替代关系，而是补上”长度可变”这块拼图；定长元组本身的推断规则另有专文，此处不展开。

在 2.6 里模拟可变长参数

既然元组 rest 还没发布，现阶段的可行做法是把”前缀固定”和”数量不定”拆成两层：类型层用少量重载覆盖常见长度，实现层用数组接收，运行时再用类型守卫校验。

迁移建议：现在该做什么

面对还没发布的特性，最差的选择是提前按设想重构：配置里写 references 只会报未知选项，脚本换成 tsc --build 会让 CI 立刻红。理性做法是承认方向，只做那些无论方向是否落地都成立的事。

第一，把包边界画清楚。每个包只暴露一个入口 src/index.ts，禁止 import '@scope/core/lib/internal/xxx' 这类深层路径。好处与具体特性无关：将来有了项目引用，加两行配置就能接上；即便一直没有，代码也更可维护。

第二，让每个包拥有独立且自洽的 tsconfig.json，公共部分通过 extends 继承，rootDir、outDir、include 都写全。这是项目引用所要求的前提，也是今天就能减少误编译的手段。

第三，固定”先声明、后消费”的链路：跨包类型一律通过已构建的 .d.ts 消费，本地用 lerna 软链接串联，CI 按 core → ui → app 串行构建，并把顺序写进脚本，而不是依赖默认并发。yarn 工作区可承担链接这一步，二者选一。

第四，控制路径映射的使用范围。paths 适合编辑器内的快速跳转，但生产构建应以包名为准；如果两套解析并存，务必让构建工具的别名与 tsconfig 保持一致。

第五，给新包准备脚手架。多包仓库的隐性成本是”每个人建的包都不一样”，一份含 package.json、tsconfig.json、入口与测试目录的模板，比任何语法特性都更能降低摩擦。

做到这五条，等项目引用真正可用时，迁移只是加开关、改命令；做不到，即使特性发布，也会因包间互相引用源码而无从下手。

小结

本文讨论的两个方向在 2017 年 11 月都还不存在：稳定版是 2.6，项目引用与元组 rest 只停留在社区讨论和路线图里，文中出现的 composite、references、--build 与 [string, ...number[]] 都不能直接使用。项目引用要解决的是多包项目的编译顺序、增量与跨包解析问题，本质是把包边界变成编译边界；元组 rest 要解决的是”前缀类型固定、长度可变”的表达问题，让重载不再随参数个数膨胀。在它们落地之前，多份 tsconfig.json 加 extends、paths 映射、软链接与声明文件已经能支撑绝大多数场景，只是需要人工维护顺序。真正值得现在就投入的，是清晰的包边界、独立的工程配置和显式的构建链路——这些工作与版本号无关，却决定了未来能否平滑接上新能力。
