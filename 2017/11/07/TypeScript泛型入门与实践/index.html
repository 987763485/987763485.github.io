TypeScript 泛型入门与实践

本文属于《TypeScript 学习路线》第 4/74 篇
上一篇系列目录下一篇

泛型是 TypeScript 类型系统里最容易被跳过、也最容易用错的一块。很多人第一次写下 <T>，只是为了消掉一个 any，结果把泛型写成了带语法糖的 any。本文从几个具体的小函数出发，讲清泛型函数、泛型接口、泛型类、约束与默认类型参数的用法，再给出三个可以直接搬进项目的实战封装，最后总结几条命名与取舍上的建议。读完之后，你应该能判断一段代码到底需不需要泛型，以及约束应该写多紧。

绝大多数情况下调用方不需要写类型参数。编译器会根据实参自动推断出 T，这个过程叫类型推断。推断是“从值到类型”的单向推导，所以上例中三个调用各自得到了精确的结果，而不是 any。多个类型参数时也是同样的规则：

约束：给类型参数划一条边界

不加约束的 T 对编译器来说是完全未知的，函数体里除了把它原样传递，什么也做不了。想访问某个属性，就得先告诉编译器“传进来的东西至少长这样”：

extends 在这里不是类继承的意思，而是“必须满足这个形状”。由于 TypeScript 采用结构类型，只要对象拥有一个 number 类型的 length 属性，就算是字符串、数组还是自定义对象都可以通过。约束的价值在于换来函数体内部的安全访问：编译器知道 a.length 一定存在，也知道它是 number，于是比较运算合法。

同时要注意，返回值仍然是 T 而不是 { length: number }。约束只规定下限，不抹掉具体类型，所以 longest("abc", "de") 得到的还是 string，调用方可以继续用字符串的方法。

两个常见误区

误区一：把泛型当成带尖括号的 any

学了泛型之后，很容易走向另一个极端：所有函数都加一个 T，需要访问属性时断言一下，返回时再断言一下。这样写出来的代码编译能过，类型信息却一点没留下：

这个 T 除了让签名看起来高级，没有提供任何约束。问题出在约束过宽：<T> 等价于 <T extends {}>，它只排除了 null 与 undefined，对属性一无所知，于是函数体只能靠 as any 强行开洞。更糟的是返回值也是 any，整条调用链的类型都被污染了。

判断标准其实很简单：如果函数体里出现了 as any 或大量的类型断言，说明约束没写对。把参数收窄到真正需要的形状，断言往往就消失了：

另一个相关的问题是“约束只写了一半”。例如需要一个带 id 的实体，却写成 T extends object，函数体里照样访问不到 id，还得再断言一次。约束应该精确到“我真正用到的成员”，多一分浪费，少一分不够。

误区二：在函数体里对 T 做假设

泛型的类型参数在运行时是不存在的，因此任何依赖“T 是什么”的操作都不成立。最典型的错误是试图实例化它：

编译器在检查函数体时，对 T 的了解仅限于它的约束（没有约束时就一无所知），它无法保证 T 可以被 new 出来。正确做法是把构造函数作为参数传进来，用一个构造签名描述它：

{ new (): T } 读作“一个不带参数、返回 T 的构造器”。这样约束落在了参数上，函数体里的 new ctor() 就有了依据，调用方传错类也会被立刻发现。

同理，访问未知属性、调用未知方法、用 instanceof T 做运行时判断，都是行不通的。类型参数只在编译期参与检查，编译产物里没有任何痕迹，运行时的分支判断仍然要靠 typeof、instanceof 或者自定义的类型守卫。理解了这一点，就不会再指望泛型替你完成运行时校验。顺带一提，T 上能做的事，严格来说只有把它赋值给同样约束的变量、放进容器、或者原样返回，剩下的都得靠约束来授权。

类型参数的命名与可读性

单参数用 T，键用 K，值用 V，元素用 E，这些是社区约定，看一眼就知道角色。参数多了不要硬凑字母，改成 TKey、TValue 这类有含义的名字；超过三个，通常说明函数职责太重，该拆了。

还有一条检验规则：类型参数至少要在签名里出现两次，才能把两处类型关联起来。function log<T>(value: T): void 里的 T 只出现一次，没有任何约束力，直接写具体类型即可。如果函数体里必须为某个类型写特殊分支，也说明它并不真正泛型。

小结

泛型的本质是把类型当作参数，让输入与输出共享同一个类型变量，从而在不丢类型信息的前提下复用代码。函数、接口、类型别名和类都可以带类型参数，extends 划定下限，默认值降低调用成本。落地时盯住两件事：约束精确到真正用到的成员，函数体里不对 T 做运行时假设。最后用“类型参数是否出现两次”筛一遍，大部分滥用都能被筛出来。
