Docker 资源限制与监控

本文属于《Docker 与 Kubernetes》第 11/51 篇
上一篇系列目录下一篇

2016 年底的一个下午，我们的一台 16 GB 内存的宿主机突然连不上 SSH。等运维从控制台登进去，dmesg 里已经是刷屏的 oom-killer 记录，sshd、crond、监控 agent 都被内核杀过一轮，业务容器死了又活、活了又死。事后查下来，肇事的是当天上线的一个定时任务容器：它的 JVM 堆按宿主机内存算出了 4 GB 上限，再叠加堆外内存和 page cache，一路把整机吃干。

同一周的另一台机器是另一种症状。那台机器上跑着六个容器，其中一个做图片转码，上线后邻居的接口响应时间从 30 ms 涨到 400 ms，docker stats 里那个容器的 CPU 常年 700% 以上。没有任何进程被杀，也没有任何报错，只是所有人都变慢了。

两次事故的共同点是：容器都是 docker run 直接起，谁也没有写 -m，谁也没有限制 CPU。容器给人的直觉是”隔离”，但隔离的是视图，不是资源。默认情况下，一个容器可以拿走宿主机上几乎所有 CPU 和内存，直到把别人挤死。

默认没有上限

Docker 的默认行为是”不限制”。不加 -m，容器能用完整台机器的内存；不加 CPU 参数，所有容器挂在同一条运行队列上，权重相同。这在单容器、专用机器的场景下没有问题，但只要一台机器上跑多个容器，资源就成了公共池。

争抢的后果比”慢一点”严重得多。内存被吃光时，Linux 的 OOM killer 会挑一个”分最高”的进程杀掉，它并不知道哪个是业务主进程，也不知道哪个是刚启动还没预热完的容器。CPU 被打满时虽然不杀进程，但同一批容器要排队，延迟抖动会传导到所有服务上。

限制的意义有三层。第一是公平：给每个容器划一个上限，避免一个失控的服务拖垮整机。第二是故障隔离：限制之后，出事的是那一个容器，它退出、重启、报警，而不是宿主机一起躺下。第三是容量规划：只有当每个容器的上限是明确的数字，才能算出”一台 16 GB 的机器该放几个 4 GB 的服务”，而不是靠拍脑袋。

至于 cgroup 怎么把进程分组、怎么记账，属于内核机制，在《Docker 原理：namespace 与 cgroup》里已经拆过；本文只讲命令行参数、验证方法和监控告警，机制部分一句话带过。

内存：三个值的关系

内存是最容易出事的一项，也是参数最容易记混的一项。Docker 1.12/1.13 上有三个相关参数：

-m（写作 --memory）是硬上限，写到 cgroup 的 memory.limit_in_bytes。容器里的进程申请内存时，只要 cgroup 总用量没超过它，内核就不干预；一旦超过，内核先尝试回收 page cache，回收不动就把这个 cgroup 里分数最高的进程杀掉，这就是 OOM。

--memory-reservation 是软上限。它不阻止容器超用，只在系统内存紧张时作为回收的优先级参考：内核会更积极地回收超过 reservation 的部分。

--memory-swap 最容易理解错。它设的是”内存 + swap”的总额，不是 swap 单独的大小。所以 -m 512m --memory-swap 1g 意味着内存 512 MB、swap 512 MB；如果 --memory-swap 和 -m 相等，等于禁用 swap；如果不写 --memory-swap 但写了 -m，默认容器可以用的 swap 是 -m 的两倍（也就是 swap 大小等于内存大小），这个默认值经常被人忽略。设为 -1 表示不限制 swap。

OOM 之后怎么查

容器被 OOM 杀掉之后，第一现场往往只剩一个退出码。docker ps -a 里能看到状态是 Exited (137)。137 是 128 加 9，9 是 SIGKILL，说明进程被强杀；但要确认是 OOM 而不是别的原因（比如手动 docker kill、或者宿主机重启），还要看两处。

OOMKilled 为 true，基本可以定性。注意这个字段反映的是”这个容器是否因 OOM 被杀”，如果容器里有多个进程、死的是其中一个，容器的退出码和这个字段未必同步，需要结合日志看。

第二处是内核日志：

这一行会给出被杀进程的 PID、进程名、anon-rss（实际驻留内存），拿 PID 去 docker top 或 cgroup 目录里对一下，就能确认是哪个容器。如果是整机级别的 OOM（没有 cgroup 前缀的那类记录），说明被吃的不是某个容器的额度，而是宿主机本身，问题更大。

排查时还要区分”限得不够”和”泄漏”。如果 anon-rss 是缓慢爬升到上限的，多半是内存泄漏或者缓存没有上限；如果是一瞬间冲上去的，要看看是不是某个请求把整张表读进了内存、或者 JVM 堆参数写错了。前者该改代码，后者该调参数，把 -m 调大只是把爆炸时间往后推。

CPU：权重与配额是两件事

CPU 参数常被混用，其实分两类，作用完全不同。

--cpu-shares 是相对权重，默认 1024，可设 2 到 262144。它只在 CPU 紧张时才有意义：两个容器权重分别是 1024 和 512，抢同一批 CPU 时大致按 2:1 分。如果只有一个容器在跑，它照样能吃满所有核。所以权重解决的是”抢的时候怎么分”，不是”最多用多少”。

绝对配额靠 --cpu-period 和 --cpu-quota 配合。period 是一个调度周期的长度，默认 100000 微秒，也就是 100 ms；quota 是一个周期内允许消耗的 CPU 时间。--cpu-quota 50000 表示每 100 ms 最多用 50 ms，等于半个核。两个参数都用微秒表达，写起来不直观，但在 2017 年初这是唯一稳定的”限死上限”的方式。

这里要提醒一句：1.13 的 docker run --help 里已经能看到 --cpus，但当时它还不算稳定接口，不同版本上的行为有出入，生产环境不要依赖，老老实实写 period 和 quota。

--cpuset-cpus 是另一种思路：不限制用量，而是把容器钉在指定的核上。它对 NUMA 敏感、对缓存局部性敏感的服务有用，也能把吵的容器和延迟敏感的服务在物理上分开。代价是这些核被占住了，别的容器用不到，规划时要按峰值留余量。

块设备 I/O 限速

I/O 限制用得比内存和 CPU 少，但在有备份、转码这类重 I/O 任务的机器上很有必要。

--blkio-weight 是权重，和 --cpu-shares 一样只在竞争时生效，而且只在本机容器之间比较，宿主机上的普通进程不参与这套权重。--device-read-bps 与 --device-write-bps 是硬限速，按设备指定，支持 kb/mb/gb 单位，另有对应的 iops 版本。

这一组参数的适用范围比看上去窄。它作用于块设备层的请求，对文件系统层的写入、page cache 的脏页回写、以及 NFS 这类网络存储，限速效果都不理想。所以实践中的用法是：用它挡住”备份任务把磁盘打满”这类粗粒度问题，真正的 I/O 隔离还是靠拆机器、拆盘。

进程数：顺手挡住 fork bomb

--pids-limit 从 1.10 起可用，限制的是容器内 PID 的数量，也就是进程加线程的总数。

它的价值在于兜底。一个写错的脚本在容器里递归 fork，或者依赖被人注入了死循环，几秒钟就能把宿主机的 PID 表耗尽，之后整机谁也起不了新进程。有了这个上限，爆炸被关在容器里，容器自己起不来新进程，日志和退出码都还能看。

阈值不能拍太小。JVM、Go 的运行时都会起不少线程，一个普通 Java 服务几百个线程很常见，先 docker top 或者看 /proc/<pid>/status 里的 Threads，按峰值的 1.5 到 2 倍给。

验证限制是否真的生效

参数写对不代表限制生效：单位写错、compose 文件里被别的字段覆盖、镜像自带的启动方式不同，都会让限制落空。最可靠的验证是进容器看 cgroup 文件：

CPU 配额可以直接压测验证。容器里跑一个死循环，宿主机上 top 看这个进程的 CPU 占用，配额半个核就应该稳定在 50% 左右；如果飙到 100%，说明配额没生效，回头查 HostConfig 里的字段：

读懂 docker stats

docker stats 是日常最常用的读数工具，不带参数时每两秒刷新一次：

几个数字的含义要分清。

MEM USAGE 是容器实际占用的内存，扣掉了可以被回收的 page cache，所以它通常比 memory.usage_in_bytes 小。LIMIT 就是 -m 设的值；没设 -m 时这里显示的是宿主机总内存，很多人误以为”容器拿到了这么多”，其实是”没有上限”的意思。

CPU % 是一个比值：一个采样间隔内，容器消耗的 CPU 时间除以宿主机总时间，再乘以核数。所以它可以超过 100%，800% 表示吃满了八个核。

NET I/O 和 BLOCK I/O 都是累计值，单位是字节换算后的结果，看趋势比看绝对值有用。BLOCK I/O 统计的是块设备层的读写，走 page cache 的写不一定立刻计入，这也是它和 iostat 对不上的原因之一。

第一次读数是 0，是因为这些速率需要两个采样点做差，刚启动时没有基线。用 --no-stream 取单次快照时，拿到的正是这种”间隔为 0”的结果，CPU % 和网络速率可能为 0，但 MEM USAGE 这类瞬时值仍然准确。写脚本采集时要连采两次，或者干脆用下面说的采集器。

从快照到趋势

docker stats --no-stream 适合临时看一眼，也适合塞进 crontab 每分钟写一行日志，但样本一多，SSH 上去一个个敲就不现实了。

2017 年初比较常用的做法是 cAdvisor：一个容器跑起来，它会把宿主机上所有容器的 CPU、内存、网络、文件系统用量按容器维度暴露成 metrics，自带一个简单的 Web 界面，也能被 Prometheus 抓取。当时的 Prometheus 还在 0.x/1.x 的早期，采集链路基本是 cAdvisor 加 node_exporter，Grafana 出图。本文不展开配置，只强调一个方向：监控要落到”每个容器的 limit 是多少、当前用了多少”这两个数上，只留宿主机整体水位，出了事仍然要靠猜。

告警阈值怎么定

阈值不是越敏感越好，告警必须可行动，否则一周之后所有人都会把它静音。下面几条是当时实践下来比较稳的。

内存看两个点：持续五分钟超过 limit 的 85%，说明这个服务的内存曲线在往上走，该看是不是泄漏；一分钟内超过 95%，说明马上要 OOM，立刻处理。最硬的一条是 OOM 事件本身，docker events --filter event=oom 能实时收到，比任何百分比都准，收到就该有人看一眼。

CPU 要区分”故障”和”容量”。短时间 100% 往往是正常的批处理或者突发流量，不该告警；持续十五到三十分钟维持在 80% 以上，是扩容或者优化信号，按周报处理更合适。真正该实时告警的是配额被打满导致请求排队，这要靠应用的延迟指标，而不是 CPU 百分比。

容器重启用 docker inspect 的 RestartCount，十分钟内超过三次就值得看一眼：可能是 OOM 循环，也可能是健康检查写错了。磁盘则要看 inode，df -i 超过 85% 时，磁盘明明还有空间但写不进去，日志容器最容易踩这个坑。

几个反复踩到的坑

第一个是 Java 的堆。2017 年的 JDK 8 默认按宿主机内存推算堆上限，容器里 free 一看是 16 GB，JVM 就敢把 -Xmx 定到 4 GB，而容器的 limit 只有 512 MB，启动没多久就被 OOM 杀掉。当时的 JVM 不会读 cgroup 的限制，唯一可靠的做法是显式写 -Xmx，并留出三分之一给堆外内存和线程栈。

第二个是 free 本身。/proc/meminfo 没有按容器隔离，容器里执行 free -m 看到的永远是宿主机的数字。判断容器内存要读 cgroup 文件或者看 docker stats，不要相信 free 和 top 的头部汇总。

第三个是 swap。--memory-swap 与 -m 相等等于禁用 swap，很多机器本身也关了 swap，此时内存一旦到顶就是直接 OOM，没有任何缓冲。这其实是好事，行为可预测；但如果有人按”有 swap 兜底”的思路把 limit 设得很紧，就会频繁看到 137。

第四个是限制过紧导致启动失败。JVM 启动时要预留堆空间，镜像构建、数据库初始化这类操作也会短时吃掉大量内存，-m 256m 对一个 Spring 应用基本起不来。新服务上线前先用宽松值跑一轮压测，拿到峰值再收紧，比拍一个整数靠谱。

一张对照表

资源 参数 查看方式 典型阈值
内存 -m、--memory-swap docker stats、memory.limit_in_bytes 使用率长期低于 85%
CPU 配额 --cpu-quota、--cpu-period cpu.cfs_quota_us、CPU % 长期低于 80%
CPU 绑核 --cpuset-cpus cpuset.cpus 按峰值多留一核
块设备 --blkio-weight、--device-*-bps BLOCK I/O、iostat 看写延迟而非总量
进程数 --pids-limit PIDS、/proc/<pid>/status 峰值线程数的 1.5 到 2 倍
稳定性 无 RestartCount、docker events 十分钟内不超过 3 次
磁盘 无 df -i inode 使用率低于 85%

小结

资源限制的落点只有三条：给每个容器写上明确的上限，进容器确认限制真的生效，用容器维度的指标而不是宿主机指标做告警。参数会随版本变化，这三条不会变。
