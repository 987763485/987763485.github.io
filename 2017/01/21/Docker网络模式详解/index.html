Docker 网络模式详解

本文属于《Docker 与 Kubernetes》第 8/51 篇
上一篇系列目录下一篇

容器跑起来了，日志也打印出监听成功，浏览器却怎么也连不上——这是很多人第一次用 Docker 部署服务时踩的坑。本文从这个问题出发，把 Docker 1.13 提供的几种网络模式逐一讲清：各自怎么工作、适合什么场景、坑在哪里，最后给出一套可以照着执行的排查顺序。读者需要对 docker run 有基本使用经验。

从一个连不上的服务说起

先还原现场。一个 Node 服务被打进镜像，启动命令大致如下：

容器状态是 Up，日志显示 server listening on 127.0.0.1:3000，进容器里 curl 127.0.0.1:3000 也能拿到响应，但在宿主机上 curl 127.0.0.1:3000 直接被拒绝。于是开始怀疑端口映射写错了，改 -p、换端口、重启 Docker，全都没用。

问题出在监听地址上。127.0.0.1 是一个回环地址，只在本机的 loopback 网卡上有效。容器有自己独立的网络栈，它的 127.0.0.1 指的是容器内部的 loopback，而不是宿主机的。宿主机的请求经过端口映射后，目的地址是容器的 172.17.0.x，报文从 eth0 进来；此时没有任何进程监听在这个地址上，内核只能回一个 RST，表现出来就是连接被拒绝。

把监听地址改成 0.0.0.0 就好了：

0.0.0.0 表示“本机所有网卡地址”，容器 eth0 上的 172.17.0.x 也被包含在内。这个坑与 Docker 无关，任何跑在独立网络栈里的进程都一样，只是容器里特别容易撞上。

默认的 bridge 网络

不指定 --network 时，容器就接入默认的 bridge 网络。Docker 守护进程启动时会在宿主机上创建一块叫 docker0 的虚拟网桥，默认地址是 172.17.0.1/16，可以把它理解为一台软件交换机：插在上面的设备处于同一个二层网络，彼此可以直接通信。

每启动一个容器，Docker 就创建一对 veth 设备，一端插在 docker0 上，另一端放进容器的网络命名空间并命名为 eth0，再从 172.17.0.0/16 里分配一个地址。底层是 network namespace 与 veth pair，具体机制在《Docker 原理：namespace 与 cgroup》里已经讲过，这里不再重复。

默认 bridge 下的通信关系可以概括为三点。宿主机与容器互通：宿主机直接访问 172.17.0.x 即可，容器访问宿主机则走 docker0 的网关地址 172.17.0.1。容器之间互通：同一网桥上的容器处于同一网段，直接用 IP 访问。容器访问外网：源地址在 docker0 上被做一次 SNAT，换成宿主机的地址发出去。

用 IP 互访听着简单，实际很别扭。容器的 IP 是按启动顺序分配的，删掉重建之后大概率会变，写死在配置文件里的地址过两天就失效。默认 bridge 又不提供名字解析，ping db 这种写法完全不工作。这两点正是后面自定义网络要解决的问题。

端口映射：把流量引进来

外部要访问容器里的服务，就得做端口映射。-p 8080:80 把宿主机 8080 转到容器 80；-p 127.0.0.1:8080:80 只监听宿主机回环地址，外网访问不到，适合只给本机 Nginx 反代的后台服务；-P 则把镜像里 EXPOSE 声明的端口随机映射到宿主机高位端口。

docker port 用来反查映射关系，输出形如 80/tcp -> 0.0.0.0:8080；映射疑似失效时可以先跑它。

端口映射的本质只有一句话：Docker 在宿主机的 nat 表里写入 DNAT 规则，把发往宿主机某端口的报文目的地址改写成容器 IP 加容器端口，回程再由 conntrack 还原。所以它并不是“转发”，而是在内核网络层改地址，性能损耗很小。也正因为依赖 iptables，宿主机上如果装了 firewalld 或其他会改写规则的工具，映射失效时先去看 nat 表。

还有一个容易忽略的限制：-p 的宿主机端口不能重复，两个容器都想映射 8080，第二个会直接启动失败。

host 模式：共用宿主机网络栈

--network host 让容器不再创建独立的网络命名空间，而是直接使用宿主机的网络栈。容器里看到的网卡、路由、/etc/resolv.conf 与宿主机完全一致，也就没有独立的容器 IP。

这种模式下 -p 是无效的，因为根本不存在 NAT 转换这一步，服务监听在哪个端口，宿主机上就是哪个端口。好处是性能最好，少了两层地址转换，网络吞吐接近裸机；坏处是隔离性几乎为零，端口冲突变成硬冲突：宿主机上已经有 Nginx 占了 80，容器里的 Nginx 就起不来。

host 模式适合两类场景：对网络性能敏感、或者需要真实客户端源 IP 的服务，比如高流量反向代理、监控采集器；以及临时排障，用 host 模式跑 curl 或 tcpdump，能立刻判断故障在网络层还是应用层。常规 Web 服务不建议用它，端口管理会失控。

none 模式：只有一个 lo

--network none 是最彻底的一种，容器有自己的网络命名空间，但里面只有一块 lo，没有 eth0，没有默认路由，也没有 DNS。

这种容器完全无法与外界通信，听起来没用，实际有两个用途。一是跑纯计算任务，比如批处理、密钥生成、离线数据转换，从设计上就杜绝它偷偷联网，安全性最好。二是作为自定义网络的起点：先以 none 模式启动，再用 docker network connect 把需要的网络接进来，容器就只拥有被显式授予的那几张网卡。

在多网络场景里这个组合很常见：一个内部服务同时接入 backend 和 monitor，业务与指标采集的流量互不影响，接入哪些网络完全由运维决定。

container 模式：共享别人的网络栈

--network container:<name|id> 表示新容器不复用宿主机，而是复用另一个已存在容器的网络命名空间。两个容器看到的是同一组网卡、同一个 IP、同一张路由表，localhost 互相指向对方。

因为共享网络栈，新容器不能再指定 -p，端口只能由第一个容器声明。这个模式最典型的用法是 sidecar：主容器跑业务，旁路容器负责日志采集、抓包或者代理，两者通过 127.0.0.1 直接通信，不需要经过任何网络转发，也不占用额外地址。

用 container: 模式时要注意生命周期绑定。被共享的容器一旦停止或删除，共享方的网络也会跟着失效，所以启动顺序和依赖关系必须明确。另外两个容器的进程共享同一个端口空间，sidecar 想监听 8080 而主容器已经占了，就只能换端口。

这个模式可以看作后来 Pod 概念的雏形：一组容器共享网络命名空间，靠回环地址高效通信，对外表现为一个整体。2017 年初 Docker 还没有编排层面的“组”抽象，多容器顺序要靠脚本或 Compose 维持。

自定义 bridge 网络

Docker 1.9 引入了 docker network 子命令，允许用户自己创建 bridge 网络。到 1.13，这已经是容器互联的推荐做法。

与默认 bridge 最大的区别是内置 DNS。同一自定义网络里的容器可以用容器名互访，api 里直接连 db:3306，不用关心它这次拿到哪个 IP。容器重建后名字不变，地址变了也不影响调用方。

除了容器名，还可以给容器挂别名：

同一个网络里多个容器可以共享一个别名，解析时会返回多个地址，等于一个简易的客户端负载均衡。用别名而不是名字的好处是，业务代码里写的 mysql 与具体容器名解耦，换实例不用改配置。

自定义网络还带来网络级隔离：不同网络默认不通，需要显式 docker network connect 打通。实践中按业务域划网段，frontend、backend、monitor 各用一个 /16，既避开公司内网，也让“谁能访问谁”一目了然。

容器间通信与 –link 的退场

在自定义网络之前，官方方案是 --link：

它的做法是在目标容器的 /etc/hosts 里写一条记录，同时在接收方注入一组环境变量，比如 DB_PORT_3306_TCP_ADDR。这套机制在 2017 年已经被标记为过时，文档里明确建议改用自定义网络，原因是它只能单向连接、必须按顺序启动、容器重启后 hosts 记录可能失效，而且无法跨主机。

但 --link 在实际项目里还能见到，多半是历史遗留：老镜像的启动脚本读的是 DB_PORT_3306_TCP_ADDR，迁移到自定义网络后变量不再注入，服务起不来。迁移时先保留 --link，同时把代码改成直连服务名，验证通过后再删掉参数。

隔离与网段规划要一起考虑。默认 bridge 上所有容器天然互通，一个容器被入侵就能扫到同网段的其他服务；自定义网络把广播域切开后，攻击面小很多。建议把反向代理与数据库分到两个网络，代理再单独接入 backend，形成两层结构。

DNS 与解析顺序

容器里的 /etc/resolv.conf 由 Docker 在启动时生成。默认 bridge 模式下，它写的是宿主机的 DNS 配置，通常是 nameserver 192.168.x.1 之类；自定义网络则是另一套机制。

在自定义网络里，resolv.conf 的 nameserver 指向 127.0.0.11，这是 Docker 内嵌的 DNS 服务器。它监听在容器命名空间的回环地址上，请求先到这里，Docker 再按网络范围决定怎么答：同一网络里的容器名和别名直接返回容器 IP，其他域名转发给上游解析器。这也是为什么 127.0.0.11 只出现在自定义网络中，默认 bridge 没有这项能力。

--dns 用来覆盖上游服务器，可写多个，按顺序尝试。它不会影响容器名解析；容器名解析不了时，先确认两个容器是否在同一自定义网络，而不是去调 DNS 地址。在容器内跑 nslookup db 就能分辨。

跨主机网络：overlay 与 macvlan

单机上的几种模式解决不了多主机互联。2017 年初的现实是：overlay 网络要么跑在 Swarm mode 里（1.12 起内置），要么依赖 Consul、etcd 这类外部键值存储来同步网络状态，后者的部署与维护成本不低。

overlay 的做法是在宿主机网络之上再封一层，容器之间通过 VXLAN 隧道通信，看起来像在同一个二层网络里。它需要集群里所有节点对网络状态达成一致，因此键值存储或 Swarm 不可省略。macvlan 则给容器分配一个与宿主机同网段的真实地址，直接暴露在物理网络上，适合需要被外部设备直连、需要固定 IP 的旧系统；但它要求网卡支持混杂模式，很多云主机并不放行。

建议很直接：十来个容器、两三台机器的小团队不要自建 overlay，维护键值存储、处理节点上下线、排查隧道丢包，投入远超收益。这个阶段用“每台机器跑独立服务，前面挂 Nginx 分流”更稳，真需要动态扩缩容再交给编排工具。

一个可照做的排查顺序

网络不通时不要乱改配置，按层次从下往上查，通常三五分钟能定位。

  1. docker network inspect <net> 看容器是否真的在目标网络里，子网和网关是否正确。
  2. 在宿主机 ip addr 看 docker0 或自定义网桥是否存在、有没有地址；ip route 确认到容器网段的路由在。
  3. iptables -t nat -L -n 查 DNAT 规则有没有生成，端口映射失效十有八九是这里被别的防火墙工具刷掉了。
  4. 进容器网络命名空间看：nsenter -t $(docker inspect -f '{{.State.Pid}}' web) -n ip addr，确认 eth0 起了、地址对、默认路由指向网关。
  5. 还不行就抓包：在宿主机 tcpdump -i docker0 port 8080，或在容器命名空间里抓 eth0。请求有没有到达、回包有没有发出，一看便知。

顺序的关键是“先确认链路，再怀疑应用”。不少网络问题最后发现是服务只监听了 127.0.0.1，或者端口与 -p 写的不是同一个。

模式对照与小结

模式 独立 IP 端口映射 典型用途 主要坑
bridge（默认） 有，172.17.x.x 支持 单机普通服务 只能用 IP 互访，重启后地址变
自定义 bridge 有，自选网段 支持 多容器协作、按名解析 跨网络默认不通，需手动 connect
host 无，共享宿主机 无效 高性能代理、临时排障 端口硬冲突，隔离性差
none 只有 lo 不支持 离线计算、多网络起点 无外网，需手动接入网络
container 与目标容器相同 不能指定 sidecar、日志采集 生命周期绑定，端口共享
overlay 有，跨主机统一 支持 Swarm 集群 依赖键值存储，排障复杂
macvlan 有，同物理网段 一般不用 需要固定 IP 的设备 需混杂模式，云上常不可用

选型可以记一条简单路径：单机优先自定义 bridge，需要极致性能或真实源 IP 才用 host，纯计算用 none，sidecar 用 container，跨主机先想清楚是否真需要。绝大多数“Docker 网络问题”不在模式选择，而在监听地址、端口映射和防火墙规则这三处。
