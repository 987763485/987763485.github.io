Go 指针与内存布局理解

本文属于《Go 语言与工程》第 6/78 篇
上一篇系列目录下一篇

切片在函数里改了却没生效，换一种写法又生效；结构体只是调整了字段顺序，占用就从 24 字节降到 16 字节。这类疑惑很少来自语法本身，多半来自对值传递与内存布局的直觉不准。本文以 Go 1.7 为基准，在 64 位环境下从指针语义讲到逃逸分析、结构体对齐、切片与 map 的头部结构，再落到基准测试与 pprof 的实测方法，目标是让读者看到一段代码时，能大致判断它在内存里长什么样、会不会分配。

从一个”没生效”的切片说起

先看一段在业务代码里很常见的写法。我们有一个用户列表，想把每个人的年龄加一，于是写了两个函数：一个按下标遍历，一个用 range 的第二个返回值遍历。调用之后，前者生效，后者看起来什么都没发生。

两个函数都没有返回值，参数类型也完全一样，差别只在于循环体里操作的是谁。range 在遍历切片时，会把当前元素拷贝到循环变量 u 里，u.Age++ 改的是这份拷贝，循环结束就丢弃。按下标访问则不同，users[i] 是底层数组里那个真实的位置，自增直接写回去。

指针能做什么，不能做什么

Go 的指针比 C 克制得多。取地址用 &，解引用用 *，指针的零值是 nil，没有别的初始化仪式：

对结构体指针，选择器会自动解引用，写 p.Age 和写 (*p).Age 等价，语言里没有 C 的 -> 运算符。new(T) 分配一个零值 T 并返回 *T，它和 &T{} 在语义上接近，后者在复合字面量里还能顺便赋值。

真正需要记住的限制有三条。第一，没有指针运算。p++、p + 1 都不合法，想访问数组里的下一个元素，只能用 &s[i] 或切片下标，编译器会在这些地方插入边界检查。第二，不能随意转换指针类型。*int 和 *int64 之间没有隐式或显式转换，即使两者宽度相同也不行，唯一的口子是 unsafe.Pointer，而这已经离开了类型安全的范围。第三，指针不能指向不可寻址的值，比如 map 的元素、常量、函数返回值，&m[k] 会直接编译失败，原因会在 map 一节展开。

unsafe.Pointer 可以和任意指针类型、uintptr 互转。但 uintptr 只是整数，垃圾回收器不会把它当成指针，不能把地址存进 uintptr 长期持有，否则可能留下悬空地址。规范允许的用法是在同一个表达式里完成转换，典型场景是系统调用参数和字段偏移计算：

指针的零值是 nil，解引用会 panic，错误确定且可追踪。两个指针可以用 == 比较地址；指向同一个变量的指针相等，指向两个相等但不同变量的指针不相等。只要还有一个指针指向对象的某个字段，整个对象就会保持存活，垃圾回收器不会提前回收它。

值传递：拷贝的到底是什么

Go 规范里只有一种参数传递方式：值传递。赋值语句拷贝值，函数调用把实参拷贝给形参，return 也拷贝返回值。所谓”切片是引用类型”只是口头说法，准确的说法是切片的头部里含有一个指向底层数组的指针，拷贝这个头部之后，两个头部指向同一块数组。

判断一个函数能不能改到调用方的数据，只需要问一句：拷贝出来的这个值里，有没有一条通往原对象的路径。int、bool、结构体本身没有，所以函数里怎么改都只影响副本；指针有，所以可以通过解引用改到目标；切片头部有 Data 指针，map 和 channel 的变量本身就是指向运行时结构的指针，所以它们看起来像引用。

addKey 能生效，是因为 map 变量里存的就是指向 hmap 的指针，拷贝后两个变量指向同一个哈希表；dropMap 不生效，是因为把局部变量置为 nil 只是让这个副本不再指向哈希表，调用方手里的那个指针毫发无损。renameByPtr 里 range 拷贝的是 *User，拷贝前后都指向同一个用户，所以修改字段能落回原对象。把参数换成 []User，同样的写法就会失效，原因和开头的例子完全一样。

数组和切片经常被混淆：[3]User 作为参数会整体拷贝，函数里改哪个都不影响调用方；[]User 只拷贝头部，底层数组被共享。字符串头部也是指针加长度，但不可变，任何”修改”都会产生新字符串。

方法接收者也一样：值接收者拿到副本，指针接收者拿到地址的副本。编译器会对可寻址的变量自动取地址，但那只是语法糖，不是引用传递。

逃逸分析：变量究竟住在哪

知道参数被拷贝还不够，下一步要问：这个副本分配在栈上还是堆上。栈上的变量随函数返回自动消失，分配只是一次栈指针移动；堆上的变量要经过内存分配器，还要被垃圾回收器扫描。Go 编译器用逃逸分析决定这件事：如果一个变量的地址可能在该变量所属的函数返回之后仍被访问，它就必须搬到堆上。

newPoint 是最典型的逃逸：函数返回了局部变量的地址，栈帧马上要销毁，编译器只能把它放到堆上。useLocal 里的 p 没有被取地址，也没有传给可能保存它的地方，编译器可以让它留在栈上。makeCounter 返回的闭包持有 n，闭包本身可能活过 makeCounter 的栈帧，所以 n 必须搬走。keep 把指针写进全局变量，编译器无法证明它何时被释放，也只能让它逃逸。

除了返回局部变量地址、闭包捕获、存入全局变量，还有几类常见来源：把值装进 interface{} 时，若不能直接放进一个指针字，运行时就要分配内存存放副本，即装箱；把指针送进 channel、存进 map、传给未知的外部函数，编译器通常保守判定逃逸；切片扩容的新数组、大小在编译期未知的 make，往往也落在堆上。

逃逸分析是保守的。跨包调用、接口方法调用、反射，都可能让编译器放弃精确判断，宁可多分配一次。内联会改变结论，所以同一个函数在不同版本、不同调用点下的表现可能不同；可以用 -gcflags '-l' 关闭内联做对照。

需要强调的是，逃逸到堆不等于性能灾难。小对象分配很快，真正的代价是分配速率高了之后回收更频繁。把每一次 escapes to heap 都当成 bug 去消灭，往往收益很小；合理的做法是先测量，再决定是否调整。

栈与堆：两种完全不同的分配

Go 的每个 goroutine 都有自己的栈，初始很小，64 位下是 2KB 量级。这个数字是有意压低的：一个服务里同时存在成千上万个 goroutine 时，如果每个都预留几 MB 栈，内存很快会见底。函数调用需要更多空间时，运行时会分配一块更大的栈，把旧栈的内容整体拷过去，再让所有指向旧栈的指针改指新地址，这就是从 Go 1.4 开始采用的连续栈。栈按需增长，通常翻倍，64 位下的默认上限在 1GB 量级，空闲时也可能收缩。

栈增长不是免费的。拷贝的成本与当前栈大小成正比，指针修正依赖编译器为每个栈帧生成的指针图，递归很深或者局部变量很大时，一次扩容可能拷贝相当多的内容。因此”栈分配一定快”只在摊还意义上成立：绝大多数调用不会触发扩容，触发了也由多次调用分摊。真正要避免的是在热路径的递归函数里放置巨大的局部数组，那会让每次深入都拖着越来越大的栈走。

抛开扩容，栈分配本身确实便宜。函数入口把栈指针往下挪一段，局部变量就有了位置，不需要向中心分配器申请，不需要加锁，也不需要为每个变量记录释放信息；函数返回时栈指针复位，整块空间一次性收回。垃圾回收器会把栈当作根来扫描，但栈上的对象不会单独经历”分配、标记、清扫”的完整生命周期。

堆则是另一套路径：对象按大小归类，从线程本地缓存取，不够再向中心结构和操作系统要。堆对象要被回收器追踪，分配速率高会推高回收频率。逃逸分析把确定不会活过栈帧的对象留在栈上，减少堆压力。但这不是二选一：栈对象可能因扩容被搬动，堆对象只要数量可控，代价也可以接受。

还有一个常被忽略的细节：栈上的大对象会放大栈扩容的成本，而堆上的大对象会放大回收的扫描成本。前者适合拆小或复用，后者适合减少指针密度。

用 unsafe 量一量结构体

unsafe 包里最常用的三个函数是 Sizeof、Alignof、Offsetof。它们都在编译期求值，参数不会被真正执行，所以 unsafe.Sizeof(f()) 不会调用 f。Sizeof 返回类型或值占用的字节数，Alignof 返回对齐要求，Offsetof 返回某个字段相对结构体起点的偏移，参数必须是字段选择表达式。

Before 的顺序是 bool、int64、bool。A 放在偏移 0，占 1 字节；下一个字段 B 要求 8 字节对齐，所以偏移 1 到 7 这七个字节被填充浪费掉，B 落在 8 到 15；C 落在 16，占 1 字节；结构体整体的对齐要求是 8，大小必须是 8 的倍数，于是末尾再补 7 字节，总共 24。After 把 int64 提到最前面：B 占 0 到 7，A 放在 8，C 放在 9，末尾补 6 字节到 16。字段一个没少，语义完全一样，只因为顺序不同，每个值省下 8 字节。

对齐不是为了刁难开发者，而是硬件访问内存的自然要求。CPU 读取一个 8 字节整数时，如果地址按 8 对齐，一次总线周期就能完成；跨缓存行或非对齐访问则可能拆成多次，某些架构上甚至直接陷入异常。Go 规定每个类型的对齐值，结构体的对齐值等于字段里最大的那个，大小再向上取整到对齐值的倍数，于是填充必然出现。bool 只占 1 字节，却可能因为邻居是 int64 而”连累”出七个空洞。

调整字段顺序是最简单的优化手段，但要分清场合。参与序列化的结构体、通过 cgo 暴露给 C 的结构体、依赖反射按字段顺序输出的代码，都不应为了省几字节随意重排；字段顺序也是可读性的一部分。真正值得动手的是会被大量复制的值类型，比如切片元素、map 的值、频繁传参的配置结构体。

unsafe 给了我们观察布局的眼睛，也仅此而已。不要用 unsafe.Pointer 加偏移去访问字段来”提升性能”，那样的代码绕过了类型系统，会在编译器调整布局或者换平台时悄悄失效。量布局是诊断手段，不是日常写法。

切片头：三个字段引发的共享

切片变量不是数组，而是三字段头部：指向底层数组的指针、长度、容量。64 位下正好 24 字节，unsafe.Sizeof([]int{}) 就是 24。reflect.SliceHeader 描述同样的布局，但官方不建议手写，因为 uintptr 不参与指针追踪。

长度决定哪些下标合法，容量决定 append 在不再分配之前还能塞进多少元素。函数收到切片时，这三个字段被整体拷贝，所以函数内 s = s[:1] 或 s = append(s, x) 都只改副本的长度和容量，调用方看不到。能共享的是指针指向的数组，前提是写入没有越过原长度、也没有触发重新分配。

append 在容量不足时会分配新数组，把旧元素拷过去，再追加新元素，返回一个指向新数组的新头部。Go 1.7 的大致策略是：需要的容量超过旧容量两倍时直接用需要的容量；否则旧容量小于 1024 时翻倍；再大就按 1.25 倍左右增长，最后向上取整到分配器的大小级别。这个策略是实现细节，元素类型、大小级别、版本都会影响结果，写代码时只应该依赖”容量足够时复用、容量不足时重新分配”，不要依赖具体的增长倍数。

字符串与 []byte：不可变带来的拷贝

字符串的头部只有两个字段：指向字节序列的指针和长度，64 位下是 16 字节。它没有容量，因为字符串不可变，任何拼接、截取、替换都要么共享原数据，要么产生新数据。字面量存放在只读段，运行时不复制；用 s[i:j] 截出来的子串仍然指向原来的字节序列，只是指针偏移、长度变短。

长度是按字节算的，不是按字符算的。Go 源码和运行时都按 UTF-8 处理字符串，一个汉字通常占 3 字节，一个 emoji 可能占 4 字节。想数”字”要用 utf8.RuneCountInString，想按字符遍历要用 for range，它每次解出一个 rune；用下标 s[i] 拿到的是单个字节，对多字节字符没有意义。

字符串和 []byte 的转换通常要拷贝：[]byte(s) 分配新内存并抄字节，string(b) 同样抄一份，这样不可变性和可改性才不会互相破坏。编译器在少数场景能省掉拷贝，比如用 []byte 做 map 查找的临时键，但这些优化依赖版本和上下文，不能当成语言保证。

拼接尤其要小心。循环里的 s += piece 每次都可能分配新字符串并复制已有内容，复杂度是平方级的；strings.Join 能先算总长度再一次性写入，适合已知分片的场景；边拼边写更适合 bytes.Buffer，它内部维护一个可增长的字节切片，WriteString 摊还下来是线性的。本文写作时标准库还没有 strings.Builder，它在较新的版本里才加入，2017 年初的项目里用 bytes.Buffer 是常规做法。

buf.String() 同样是一次拷贝；buf.Bytes() 返回内部切片，但之后不能再写缓冲区。子串也有持有问题：从大字符串里截一小段长期保存，整个大字符串都无法回收，因为指针仍指向原数组。需要长期持有时，复制一份小的再存。

map 与 interface：两套描述符

map：桶、搬迁与取不到的地址

map 变量本身是一个指针，指向运行时的 hmap。hmap 记录桶数组、B（桶数量的对数）、哈希种子、扩容进度等元信息；每个桶默认容纳 8 个键值对，桶内先是 8 个 tophash 字节，用来快速排除不匹配的键，然后是键数组和值数组，装不下时通过溢出桶串成链表。当元素数量与桶数量之比超过约 6.5 的装载因子，或者溢出桶太多，运行时就分配两倍数量的新桶，把旧桶逐步搬迁过去。搬迁是渐进的，插入和删除会顺带搬几个桶，避免一次扩容造成长停顿。

这就是 &m[k] 编译不过的原因：map 元素不是稳定位置，扩容时键值对会搬到别的桶，取到的地址随时失效。编译器只允许整体赋值 m[k] = v。需要稳定地址就把值改成指针，map[string]*User 里的指针可以拷贝，指向的对象不随桶搬迁；代价是多一次跳转，回收要追踪的指针也更多。

遍历顺序随机是刻意设计。运行时在每次 range 开始时随机选一个起始桶和桶内偏移，一部分原因就是防止业务代码依赖某种偶然的顺序。即便同一个 map 连续遍历两次，结果通常也不同；需要有序输出时，先把键取出来排序，再按序访问。遍历时删除当前键是安全的，新增的键是否会被这次遍历看到则没有保证。

nil map 可以读、可以 range、可以 delete，但写入会 panic。var m map[string]int 之后必须先 make 才能赋值，这一点和 nil 切片可以直接 append 不同。

interface：类型指针加数据指针

接口值在内存里是两个字。空接口 interface{} 由类型指针和数据指针组成；非空接口（比如 io.Reader）由 itab 指针和数据指针组成。itab 里记录了接口类型、动态类型以及该类型实现接口方法的函数表，方法调用通过这张表间接跳转。无论装进去的是 int 还是 *User，接口值本身的宽度都是两个机器字，64 位下是 16 字节。

把具体值装进接口叫装箱。如果值能直接放进一个指针字（指针、map、channel、func 等），数据字直接保存它；否则运行时需要分配一块内存存放副本，再把地址填进数据字。把一个 int 放进 interface{} 再取出来，可能经历一次分配和一次类型断言；在热循环里反复装箱，allocs/op 会明显上升。小整数有运行时的静态表可以复用，但这不是可以依赖的通用优化。

接口还有一个经典陷阱：接口值为 nil，要求类型字和数据字同时为 nil。

p 是 nil 指针，但装进接口后类型信息是 *bytes.Buffer，接口值整体不为 nil。调用 r.Read 会进入方法，然后在解引用 nil 接收者时 panic。函数返回接口时，如果实现类型是指针，失败分支要显式 return nil，不能返回一个值为 nil 的指针变量。

接口比较有边界：动态类型可比较时按类型和数据比较，动态类型是切片、map 或函数时比较会 panic。类型断言用 ok 兜底，类型 switch 适合分支处理，它们都只检查动态类型。

垃圾回收与写屏障的演进

Go 1.5 把需要较长停顿的回收换成并发标记清扫，标记与业务代码同时运行，只在开始和结束保留短暂 STW。1.6 和 1.7 继续并行化标记、拆细栈扫描，停顿方向是变短。具体毫秒数取决于堆大小和机器，本文不给数字。

并发标记的难点在于：标记线程认为某个对象是白色的（未访问），业务代码却在这时把指向它的指针写进了已经扫描过的黑色对象。如果不干预，这个对象会被漏标并错误回收。写屏障就是插在指针写入处的检查，把这种变化记录下来，让标记阶段之后补扫。Go 1.5 用的是插入式屏障，标记结束前需要重新扫描各 goroutine 的栈；开发中的 Go 1.8 计划把插入式与删除式屏障合成混合写屏障，正是为了省掉这次重扫。Go 1.8 按计划在 2017 年 2 月发布，本文写作时还没有正式发布，这里说的是开发分支上的方向，不是已经可用的结论。

写屏障只在标记期间开启，平时指针赋值没有额外成本。触发频率由 GOGC 控制，默认值 100 表示堆增长到上一轮存活对象的两倍左右时启动下一轮；调大可以减少回收次数但占用更多内存，调小则相反。回收的扫描成本与指针密度有关：一个装满指针的结构体要逐个追踪，而 []byte 这样的大块无指针数据只需要跳过。这也是优化布局时除了字节数之外要看的第二个维度。

实测：基准、allocs/op 与 pprof

判断一段代码是否真的分配，不能靠猜。testing.B 的基准函数会被反复执行，b.N 由框架自动调整到统计稳定的次数，配合 -benchmem 能直接看到每次操作分配了多少字节、分配了几次。

输出里的 ns/op 是每次操作的耗时，B/op 是每次操作的字节数，allocs/op 是每次操作的分配次数。预分配版本通常 allocs/op 为 1，不预分配的版本会随扩容次数上升，两者的耗时差距在元素多时更明显。-count=5 跑多轮可以看波动，单次结果很容易被机器噪声带偏。

进入交互后，top 按累计分配量排序，list 函数名 能看到具体行，web 生成调用图（需要本机有 graphviz）。-alloc_space 看的是累计分配，适合找”谁分配得最多”；-inuse_space 看的是当前仍存活的对象，适合找内存泄漏式增长。线上程序可以用 GODEBUG=gctrace=1 观察每轮回收的堆大小和停顿，也可以定时读 runtime.ReadMemStats，但不要把某次采样当成长期基线。

小结

指针、切片头、map、接口和字符串头，本质上都是”一小段描述符加一块共享数据”。值传递拷贝的永远是描述符，能不能改到原对象，取决于描述符里有没有指针。结构体大小由字段顺序和对齐决定，逃逸分析决定它落在栈上还是堆上。
