TypeScript 2.3 新特性详解

本文属于《TypeScript 学习路线》第 25/74 篇
上一篇系列目录下一篇

TypeScript 2.0 在 2016 年 9 月发布，2.1 在年底跟上，2.2 还在路上，而 2.3 只挂在官方 roadmap 上。本文把两条线分开写：已经能在项目里落地的部分给出可以运行的写法，路线图上的部分只谈方向与风险，不把没发布的东西当成现成能力。适合已经在用 tsc 做类型检查、但还没系统梳理过空值检查与类型推导的读者。读完你应该能判断哪些开关值得现在打开，哪些要等版本。

先对齐版本：2.0、2.1 可用，2.2 在途，2.3 只有路线图

先把时间线摆清楚。TypeScript 2.0 于 2016 年 9 月发布，--strictNullChecks、基于 @types 的声明包、控制流分析都是这一版的正式能力。2.1 于 2016 年 12 月发布，带来了 keyof、查找类型、映射类型，以及把 async 函数降级到 ES5/ES3 的输出。2.2 的代码已经在测试版里，能确认的是它围绕 object 类型和空值检查做补强，细节在正式版之前还可能微调。2.3 则只存在于官方 roadmap。

所以必须说清楚：截至本文写作时，2.3 还在官方 roadmap 上，没有发布；下面能落地的示例全部基于 2.0/2.1/2.2，2.3 的部分只谈路线图与预期。团队内部按版本规划把这篇稿子叫作“2.3 新特性”，这是排期上的叫法，不代表能力已经可用。把没发布的东西写进技术选型，最后背锅的是维护代码的人。

因此全文分两半：前半部分逐项拆 2.0 到 2.2 的能力，代码都可以直接跑；后半部分谈 2.3 的方向和工程接入，凡是尚未发布的都会单独标注。

–strictNullChecks：把 null 和 undefined 从所有类型里剥出去

在 2.0 之前，null 和 undefined 是所有类型的合法值，一个声明为 string 的变量可以被赋成 null，编译器不会有意见，错误要等到运行时才炸。--strictNullChecks 打开之后，类型系统把这两个值当成独立类型，只有显式写成联合类型的位置才允许它们出现。

迁移旧代码时最常见的冲突是“我确定这里不为空”。2.0 为此提供了非空断言 !，写法是 el!.textContent。它只是告诉编译器“相信我”，运行时没有任何检查，编译产物里也不会多出一行判断。另一个更稳妥的做法是类型守卫：写一个返回 v is T 的函数，把判断逻辑封装起来，调用处由编译器自动收窄。两者都能过编译，区别在于断言把风险留给了运行时，守卫把风险压回了类型层。

我们的经验是，断言只用在两类地方：刚由框架保证过的 DOM 查询结果，以及测试里刻意构造的边界值。业务分支里一律先收窄再使用，否则等于把空值检查退化回 2.0 之前的写法。另外这个开关要整个项目一起开，包括引用的 .d.ts；声明文件里没标 | null 的函数会被当成非空，这也是那段时间 DefinitelyTyped 上声明包被密集修订的原因。

控制流分析：收窄跟着赋值走，never 用来收尾

2.0 的另一个变化是控制流分析真正参与类型推导。变量在赋值之后类型会变窄，if、switch、return 之后的分支也会被分别计算。同样的代码在 1.8 里要靠手写断言，2.0 里编译器自己就能推出来。

never 是这套分析里的收尾类型：一个函数如果永远不返回，比如内部只有 throw 或者死循环，返回类型就是 never。它的实际用途是穷尽性检查，switch 覆盖完联合类型的所有成员之后，剩余分支里的变量被推成 never，此时给它赋值会报错；将来联合类型加了新成员，编译器会主动提醒你漏了一个分支，而不是等到线上拿到 undefined。

这块和 --noImplicitAny 经常一起谈，但两者管的不是一件事。--noImplicitAny 管的是“参数没标注就别偷偷当 any”，控制流分析管的是“标注之后类型怎么随代码变化”。只开前者，类型是标上了，收窄仍然靠人。当时还没有一个开关能把严格选项一次打开，tsconfig.json 里只能逐项写 noImplicitAny、strictNullChecks、noImplicitThis。统一总开关是 2.3 路线图上讨论的方向，尚未发布，所以项目模板里我们仍然把开关一条条列出来，顺便当文档用。

模块解析与 @types：类型声明改由 npm 分发

2.0 之前，第三方库的类型声明靠 typings 工具和 typings.json 管理，装一个库要跑两条命令，声明来源和包来源还对不上。2.0 起，TypeScript 默认会去 node_modules/@types 下找声明，模块解析顺序也改成先看包自带的 types 字段，再看 @types 目录。于是安装方式变成了两步。

@types 下的包由 DefinitelyTyped 统一发布，版本跟着上游库走，声明包自身用 @types/lodash@4.x 这样的版本号对齐。好处是依赖树只有 npm 一份，npm shrinkwrap 能一并锁住；坏处是声明包和库的版本可能不同步，升级库之后要顺手看一眼声明有没有跟上，否则会出现“运行没问题、编译报错”或者反过来的情况。

typings 并没有立刻消失。2.0 刚发布时，不少库作者还没把声明合并进 @types，团队的过渡办法是：新库一律用 @types，老项目里已有的 typings.json 先留着，等 2.2 前后把 typings 目录整体删掉、换成 @types 依赖，再清理 tsconfig.json 里指向 typings/main.d.ts 的 files 配置。这个过渡期大约持续了半年，属于纯粹的机械劳动，但拖得越久成本越高，尤其是声明文件和库的实际 API 已经漂移的时候。

readonly 与索引签名：编译期的只读，不是运行时冻结

readonly 在 2.0 里被加到属性上：初始化之后不能再赋值，唯一的例外是构造函数里。它和 const 的区别在作用位置，const 约束变量绑定，readonly 约束对象成员，所以一个对象可以被 const 声明，同时成员全部只读。

索引签名上加 readonly 是 2.0 补的一处细节。在这之前可以声明“任意 key 都是 string”，但没法表达“这些 key 都不许改”。它对付的是配置表、常量映射、字典这类对象：读取随便，写入必须集中在初始化处。

需要提醒的是，这些检查全部发生在编译期，产物里既没有 Object.freeze，也没有 defineProperty。如果对象会流到不受类型系统约束的地方，比如第三方脚本回传、JSON.parse 之后重新赋值，只读就只是君子协定。我们的做法是在导出的常量对象上额外调一次 Object.freeze，类型检查和运行时各守一道，谁漏了都还有另一道兜着。

keyof 与查找类型：写一个类型安全的 get

2.1 引入两个互相关联的能力：keyof T 得到一个由 T 的公有属性名组成的联合类型，T[K] 是查找类型，表示“T 在键 K 上的类型”。两者组合，就能把“传一个对象和一个字符串、返回对应属性”的写法约束住，而不是让 any 从中间漏过去。

关键是 K extends keyof T 这个约束，它同时锁住了入参 key 的合法范围和返回值的类型。返回值写成 T[K] 而不是 T[keyof T]：前者是精确的单个属性类型，后者是所有属性类型的联合，调用处还得再收窄一次才能用。有了这套写法，按字段名取配置、表单取值、给 lodash 的 get 做包装，都能少写一层断言。代价是签名变长，读代码的人要先理解 keyof，所以我们一般只在公共工具函数上用，业务代码里不滥用。

映射类型：Partial、Readonly、Pick、Record 的来历

2.1 的映射类型解决的是一类重复：拿到一个接口，想要它的“全可选版本”“全只读版本”“只取几个字段的版本”。以前只能手抄一遍，接口一改两份就漂移。映射类型的语法是 [P in K]，K 必须是 keyof 出来的联合类型或者字符串字面量联合。

这四个并不是编译器里的黑魔法。翻开 lib.es5.d.ts，看到的定义和上面几乎一致，所谓内置只是随编译器一起分发。理解这一点很关键：项目里可以照同样的套路写自己的 Nullable<T>、DeepPartial<T>，不必等语言加新特性。

实际用起来，Partial 适合“更新补丁”的入参，Pick 适合从实体里裁出列表页要的几个字段，Record 适合把状态码映射成文案表。要注意映射类型只作用在类型层，不改运行时对象：Partial<T> 不会替字段填默认值，补默认值的活还得自己写，否则 undefined 会照常漏到业务里。

async/await 降级到 ES5：__awaiter 与 __generator

ES2017 的 async 函数当时还没走完定稿流程，Node 7 上要加 --harmony-async-await 才能跑，浏览器基本没有原生支持。不过 TypeScript 2.1 已经能把 async 函数编译到 ES5/ES3，产物是一台状态机，靠两个辅助函数驱动。

用 --target es5 编译后，函数体会被包进 __awaiter(this, void 0, void 0, function () { return __generator(this, function (_a) { ... }) })，每个 await 的位置变成 case 标号加 _a.sent()。__awaiter 负责把 Promise 串起来，__generator 负责保存局部变量、记住恢复执行的断点。两个函数默认内联在每个文件里，文件一多就重复，所以 2.1 提供 --noEmitHelpers 搭配 --importHelpers，改成从 tslib 统一引入。

最容易踩的坑是运行环境没有 Promise。降级只改语法，不提供实现，IE11 和旧版 Android WebView 上必须自己引 polyfill，同时要在 lib 里加 es2015.promise，否则连 Promise 这个类型都找不到。我们的做法是入口统一引 core-js 的 Promise 实现，业务模块不单独引，避免打包出多份。

object 类型与 2.2 的空值推导

object 是 2.2 引入的类型，表示“除原始类型之外的一切”。string、number、boolean、symbol、null、undefined 都不能赋给它，数组、函数、类实例可以。它比 {} 和 any 都准确：{} 接受所有非空值，连数字都能进；any 则什么检查都不做。适合放在只关心“是个对象”、不关心具体形状的位置，比如 WeakMap 的键、Object.assign 的目标、日志序列化的入参。

2.2 同时在 --strictNullChecks 下把表达式的空值推导推进了一步：a || b、a && b 和三元表达式的结果类型会剔掉不可能出现的 null 与 undefined，而不是机械地取两侧的联合。这对老代码友好，很多“明明判断过了还报错”的地方不用再加断言。需要说明的是，2.2 当时还在测试阶段，这些行为以测试版为准，正式版之前不排除调整。

2.3 的 roadmap：方向可以看，生产不能用

2.3 还没发布，官方 roadmap 上能确认的只有方向：一是更完善的生成器与迭代器降级，让 --target es5 下的 for...of、展开与解构在迭代器上的行为更彻底；二是更严格的检查方向，包括把若干严格开关打包成统一入口的讨论。这些条目没有正式文档，也没有稳定行为，本文不给出示例，更不建议据此调整项目结构。

判断标准很简单：npm 上装不到正式版、release notes 没发，就不能写进生产依赖。roadmap 的用途是排期和评估迁移成本，不是技术选型的依据。等 2.3 真正发布，再拿实际产物回来验证上面这两条，那时的结论才有意义。

工程接入：tsconfig 与 Babel 6 的分工

落地到项目，配置里最要紧的是三个字段：target 决定语法降级的程度，lib 决定能看见哪些标准库类型，严格检查决定这套类型系统到底有多少约束力。

target 写 es5 是为了覆盖 IE11，代价是生成器与 async 都要降级，产物明显变长。lib 要写全：只写 es5 就没有 Promise 类型，补上 es2015.promise 才认。严格项当时没有总开关，strict 这个一键入口还在 2.3 的 roadmap 上，尚未发布，所以只能逐项打开；等项目升到对应版本，再考虑把它收敛成一行。

Babel 6 与 tsc 的分工要提前说死，否则两边都做语法降级、都引辅助函数，产物会肿一圈。我们的约定是：.ts 文件由 tsc 负责类型检查与降级，Babel 只处理 tsc 的产物和项目里的纯 .js，用 babel-preset-es2015 继续处理语法、用 polyfill 补运行时。类型检查只有 tsc 一家，Babel 不做校验，它也不认识 .ts 语法。这条边界写进 README 之后，新同学配错预设的情况少了很多。

小结

2.0 解决的是“类型系统能不能表达空值与只读”，2.1 解决的是“类型能不能从已有类型推导出来”，2.2 继续补 object 与空值推导的边角。这些都值得现在打开，但迁移要按项目节奏来，别一次性把 strictNullChecks 砸到几十万行老代码上。2.3 只适合放进排期表，不适合放进依赖表。

版本 能力 状态
2.0 strictNullChecks、控制流分析、readonly、@types 已发布
2.1 keyof 与查找类型、映射类型、async 降级 已发布
2.2 object 类型、空值推导增强 在途
2.3 生成器与迭代器降级、更严格检查 roadmap，尚未发布

如果只来得及做一件事，我会先开 strictNullChecks，同时把非空断言压到最低。它带来的收益比后面几个特性加起来都直接，也最能暴露老代码里靠运气运行的部分。
