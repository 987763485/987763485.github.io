TypeScript 类与访问修饰符

本文属于《TypeScript 学习路线》第 2/74 篇
上一篇系列目录下一篇

多人协作的项目里，类的成员一旦被外部调用，就不再是内部实现细节。本文从一次 SDK 升级的犹豫写起，梳理 TypeScript 2.x 中 public、private、protected、readonly、static、abstract 的实际边界，重点说明它们编译到 ES5 之后还剩下什么、哪些约束只在编译期成立，以及日常最容易踩到的报错与改法。适合已经会写 class、准备把代码交给别人使用的开发者。

三个修饰符，与它们编译后的样子

去年下半年，我们维护着一套给几条业务线共用的 SDK。HttpClient 里有个 buildQuery 方法，本意只是把参数对象拼成查询串，供类内部的请求方法使用。当时没在意修饰符，它就成了公开 API：业务方直接调用它，有人甚至依赖了它对数组的序列化格式。等到我们想把签名改成支持嵌套对象，才发现这不是重构，而是一次破坏性变更，只能新加一个方法、把旧的标成废弃。这件事之后，我们给 SDK 里所有类过了一遍可见性：哪些成员是承诺，哪些只是实现细节。

JavaScript 的类在这一点上没有任何表达力，所有成员一律公开，语言层面不存在访问控制。TypeScript 在类型层面补上了这一层，提供 public、private、protected 三种成员可见性。不写修饰符时默认是 public，所以绝大多数代码其实一直在用 public，只是没写出来。private 限定在本类内部，子类也不行；protected 放宽到子类，类的外部仍然不可见。构造函数也可以加 private，那样这个类就只能在自己内部 new。

由此带来几个必须接受的事实。第一，any 是一把万能钥匙，写成 (counter as any).step = 100 编译通过，运行时也照常生效。第二，同一个类内部可以访问另一个实例的 private 成员，这一点和 Java 不同，编译器判断的是这段代码在不在类体里。第三，字段会出现在 Object.keys、for...in 与 JSON.stringify 的结果里，把 token 之类的字段设成 private 并不会让它不被序列化。第四，纯 JavaScript 的调用方压根不参与检查。

还有一个副作用：private 会让结构类型局部地名义化。两个类成员完全一样，只要其中一个带 private 成员，就不能互相赋值，因为编译器无法确认私有成员来自同一处声明。

参数属性与 readonly

写惯了 Java 或 C# 的人初到 TypeScript，很容易写出一堆重复的样板代码：先声明字段，再在构造函数里逐个赋值。TypeScript 提供了参数属性（parameter property）来省掉这一步，在构造函数参数前加访问修饰符即可，编译器会自动声明同名字段并完成赋值。

规则不多，但有几条是硬约束：参数属性只能出现在构造函数里；修饰符只能是 public、private、protected，可以与 readonly 组合，顺序是可见性在前；一个参数属性会在类上生成同名成员，因此不能再在类体里声明一遍同名字段，否则报重复标识符。

参数属性最适合依赖注入，Angular 2 的组件与服务几乎全靠它把依赖写短。代价是构造函数的签名同时承担了 API 声明，参数一多，读者要来回对照才知道类上有哪些字段。我们的约定是参数属性只用于注入的依赖。

readonly 解决的是另一个方向的误用：字段声明之后不该再被赋值。它只能出现在属性声明和参数属性上，赋值点只有两处，声明时的初始化和所属类的构造函数。构造函数之外任何赋值都是编译错误，报 TS2540。

readonly 用在数组上要绕一下。TypeScript 里对应的类型是 ReadonlyArray<T>，只读数组要写成这种泛型形式。它去掉了所有会修改数组的方法，只留下 length、索引读取，以及 map、filter、reduce 这类不改变原数组的方法；把 ReadonlyArray<number> 传回需要 number[] 的地方必须显式转换，编译器不会替你放行。

但要说清楚，readonly 同样只在编译期生效。产物里它什么也不生成，字段照旧是构造函数里的赋值；ReadonlyArray 运行时就是数组，Array.isArray 返回 true，另一个持有同一数组的变量照样能 push。readonly 也不递归，readonly config: { timeout: number } 只禁止替换 config 这个引用，不禁止修改 config.timeout。真要在运行时冻结，得用 Object.freeze，那是另一套机制，与类型检查互不替代。

static 成员与静态工厂

static 成员挂在构造函数对象上，不在 prototype 上，所以实例里访问不到 defaultTimeout，必须写 Connection.defaultTimeout。它和可见性修饰符可以叠加，private static 是最常见的组合。

构造函数私有加静态工厂是常用搭配。私有构造函数不是为了防住 new，而是把创建逻辑收到一处：以后要加连接池、要返回缓存实例、要悄悄换成子类，都不用改调用点。代价是这类不能被继承：基类构造函数一旦标成 private，子类声明 extends 时直接报错。

读的时候，子类能拿到基类的静态值：ES5 产物里由继承助手把静态成员复制到子类构造函数，新一些的编译器版本改用 Object.setPrototypeOf 接起静态侧。写的时候，User.count += 1 在子类上创建了自有属性，基类的数字从此不再增长。共享可变状态放在静态成员上，一旦有继承就变成多份，这是静态属性最隐蔽的坑。我们的约定是静态成员只放不可变常量，比如默认超时和表名，计数器这类状态放进模块级对象或实例字段。

另外，静态方法里的 this 指向调用它的构造函数，写 this.defaultTimeout 在子类调用时取到的是子类遮蔽后的值，写死类名则永远取基类的值。

abstract 与 implements

抽象类表达的是“这一类东西有共同骨架，但骨架本身不完整”。它不能被实例化，new Storage() 直接报 TS2511；它可以有构造函数、字段和已经实现的方法，这正是它与接口最大的区别。

抽象方法只有签名没有方法体，子类要实现全部抽象方法，漏一个就报 TS2515，除非子类自己也标成 abstract。上面的 normalize 是 protected，子类能调用但不能对外暴露，正好把共享实现和受控入口放在一起。

接口是纯形状，没有实现也没有状态。需要共享代码与状态、存在明确基类与派生类关系时用抽象类；只是描述长什么样、希望一个类满足多份约定时用接口。类只能单继承，接口可以一次实现多个，常见做法是抽象类给骨架，接口给能力。

implements 只做检查，不生成任何代码，编译后的类与不写它时一模一样。一个类可以同时实现多个接口，用逗号分隔。

需要留意的是，接口约束的是实例侧，不是构造器。类有两套类型：实例类型和静态侧（构造函数）的类型，implements 检查的永远是前者。所以带构造签名的接口不能拿来 implements。

实例上没有 new 这个成员，implements ClockConstructor 必然失败。这类接口的正确用法是标注工厂函数的参数，或者标注一个接收类本身的变量。把实例侧和静态侧分清，能省掉很多“为什么 implements 不检查构造函数”的困惑。

访问器 get 与 set

访问器看起来像字段，实际是方法。TypeScript 里有两条规则最常踩：访问器不能与同名属性共存；只有 get 没有 set 时，这个属性在类型上就是只读的，赋值报 TS2540。

这里的 private value 必须换个名字。如果写成 private celsius 再加 get celsius()，编译会报 TS2300 重复标识符，因为两者在类型上占用了同一个名字。2.x 还要求 get 与 set 的可见性一致，get x() 配 private set x() 编译不过，想把写操作藏起来只能改成方法。

编译到 ES5 后，访问器不出现在构造函数里，而是定义在 prototype 上，产物是 Object.defineProperty(Temperature.prototype, "celsius", { get: ..., set: ..., enumerable: true, configurable: true })。因此它不占实例的自有属性，Object.keys 看不到它，JSON.stringify 也不会输出它。字段与访问器在序列化上的差异经常让人意外。另外，访问器要求 ES5 以上目标，项目还在 --target es3 时会直接报错。

继承中的可见性与 super

子类重写基类成员时，可见性必须保持一致。把 protected 放宽成 public 报 TS2415，收窄成 private 同样报 TS2415。TypeScript 在这里比 Java 保守，它不允许子类扩大可见性：按基类类型使用的地方已经习惯了“子类之外不可见”的约定，一旦放宽，同一份代码在不同声明下会得到不同的检查结果。

基类的 private 成员在子类里根本不可见。子类声明同名成员时，编译器不会当成重写，而是认为有两份独立声明，同样报 TS2415。遇到这种报错，先确认基类里是不是有同名字段，改名通常比改可见性省事。

super 的时机是另一条硬规则。派生类构造函数里，super 必须先于任何 this 访问，否则报 TS17009；整个构造函数没有调用 super，报 TS2377。若子类带初始化字段或参数属性，super 还必须是构造函数的第一条语句（TS2376），放进 if 分支基本过不了编译。方法里的 super.move() 没有这些限制，它只是沿原型链找基类方法，与构造函数里的 super() 是两回事。

真正的私有字段还只是提案

上面所有的 private 都建立在“所有人用 TypeScript 且守规矩”的前提上。要真正隐藏数据，只能靠 JavaScript 自己的机制。2017 年 1 月，类的私有字段（用 # 前缀声明的那种）还停留在 TC39 提案阶段，尚未可用：语法没有进入规范，浏览器和 Node 6 都不认识，Babel 6 也转不了，不能写进生产代码。

退一步有闭包与 WeakMap 两种做法。

闭包最彻底，但每个实例都会复制一份方法，也没法与 prototype 上的方法共享逻辑；WeakMap 不污染实例、键随实例回收，代价是每次读写多一次查找，序列化和克隆时还要额外处理 this。TypeScript 里常见的折中是：类上保留 private 字段做编译期约束，真正敏感的数据放进模块内的 WeakMap，对外只暴露方法。

声明文件里的类

发布 npm 包的类型，或者给没有类型的库补声明，写的是 .d.ts。这类文件只有类型信息，类的声明要加 declare。

declare 表示“这个类在别处存在，编译器只需要知道它的形状”，因此方法只写签名。手写声明文件最常见的错误是漏掉 declare，编译器会把类当成实现，然后抱怨方法缺少实现体。用 tsc --declaration 从源码生成时，产物会自动带上 export declare class。还要注意两点：.d.ts 里的 private 依然参与类型兼容判断；declare class 不产生任何 JS，运行时必须有对应实现，UMD 包或全局变量都行，否则就是 undefined is not a constructor。

常见编译错误与排查

修饰符相关的报错集中在几个错误码上，下面是一段真实的编译输出。

  • TS2341：类外访问 private 成员。改成公开 API，或加公开方法转发，别用 as any 盖住。
  • TS2445：protected 成员在子类之外被访问，多见于工具函数。
  • TS2415：子类与基类冲突，通常是重复声明基类的 private 成员，或改了可见性。
  • TS2515：普通类漏实现继承来的抽象成员；补实现，或把类也标成 abstract。
  • TS2420：implements 没满足接口，一般是少成员或签名不匹配。
  • TS2377 与 TS17009：派生类构造函数缺 super，或在 super 之前用了 this。
  • TS2300 与 TS2540：访问器与同名字段重名；给 readonly 赋值。

小结

修饰符是给编译器和读代码的人看的契约，不是运行时保险箱。判断标准可以简单一点：对外承诺的成员才写 public，其余先收紧，等真有调用方再放开。

修饰符 可见范围 编译后产物 常见误用
public 任意位置，默认 无痕迹 漏写，内部方法变成公开 API
private 仅本类内部 无痕迹，普通赋值 当作运行时隐藏
protected 本类与子类 无痕迹 子类改可见性，报 TS2415
readonly 声明处与构造函数 无痕迹 以为能冻结对象
static 构造函数对象 静态属性赋值 存可变计数，继承后分家
abstract 仅作基类 普通构造函数 该共享实现却只写接口
