Linux 文件系统与 inode

本文从一次“磁盘明明还有空间，却写不进文件”的故障讲起，把 Linux 文件系统的分层、inode 的职责、硬链接与软链接的差别、inode 耗尽与已删除文件不释放空间这几件事串起来。适合已经会用 df、du、ls，但遇到文件系统问题只能重启了事的开发者。读完你应该能独立判断一个“写不进去”的报错究竟卡在空间、inode 还是进程占用上。

可用 inode 是零。这块盘上放着几十万个小文件，每个只有几百字节，加起来不到两个 GB，却把 inode 用光了。文件系统能创建多少文件，不只取决于还剩多少字节，还取决于还剩多少个 inode。要理解这一点，得先看清文件系统是怎么分层的。

文件系统的分层：VFS、ext4 与块设备

Linux 对“文件”的抽象是分层的。最上面是 VFS（Virtual File System），它定义了一组统一的接口：打开、读取、写入、查找目录项。用户态程序调用 open、read、write 时，只跟 VFS 打交道，不关心底下是 ext4、XFS 还是 NFS。中间一层是具体文件系统，CentOS 7 默认用 XFS，也可以格成 ext4；Ubuntu 16.04 装机默认是 ext4。最下面是块设备层，负责把文件系统的逻辑块映射到磁盘扇区，中间的页缓存、I/O 调度都在这一层完成。

flowchart TD
    A[应用程序 open/read/write] --> B[VFS 统一接口]
    B --> C[ext4]
    B --> D[XFS]
    C --> E[块设备层]
    D --> E
    E --> F[磁盘]

在这个分层里，一个“文件”其实由三样东西组成。文件名是给人看的字符串，存放在目录里；inode 是文件的元数据，记录权限、属主、大小和数据的存放位置；数据块才是文件内容本身。目录负责把名字映射到 inode 号，inode 负责找到数据块。三者拆开之后，同一份数据可以拥有多个名字，也可以没有名字却仍被进程打开着——后面几节要讲的怪异现象，根源都在这里。

VFS 这一层也解释了为什么 df 和 du 的结果常常对不上：前者统计块设备上已分配的块，后者沿目录树累加文件占用的块，统计口径不同，再加上被进程占用的已删除文件、被遮住的挂载点，数字自然有出入。

inode 里存了什么

inode 常被译作“索引节点”。每个 inode 有一个编号，在同一个文件系统内唯一，ls -i 就能看到。它保存的内容比较固定：文件类型（普通文件、目录、字符设备、套接字等）、权限位、属主与属组、文件大小、三个时间戳、链接计数，以及指向数据块的指针。ext4 的 inode 还记录扩展属性，块映射默认走 extent 树，早期或关闭 extent 的文件系统则用十几个直接和间接指针。

最容易被忽略的一点是：inode 里没有文件名。名字不属于文件的元数据，它属于目录的内容。所以 mv a.txt b.txt 之后，inode 号不变、数据块不动，只是目录里那条记录换了名字。同一个道理，cp 会新建 inode 和数据块，而 mv 跨文件系统时本质上是复制加删除。

三个时间戳也值得分清楚。mtime 是内容最后被修改的时间，ctime 是 inode 状态最后变化的时间，改权限、改属主、加硬链接都会刷新它，atime 则是最后访问时间。ls -l 默认只显示 mtime，要看全部三个得用 stat。不少同步和备份脚本只看 mtime，一旦用 chmod 动过权限，mtime 没变而 ctime 变了，这些脚本就会认为文件没更新过。

目录也是文件

目录在 Linux 里同样是一种文件，只不过它的内容是目录项列表，每一条目录项记录一个名字和对应的 inode 号。用 debugfs 可以只读地窥探 ext4 的内部结构，输出最左边的数字就是 inode 号：

这条命令直接读块设备，绕过了挂载点，所以看到的是磁盘上真实存在的目录项。名字和 inode 的映射就存在这里，这也是“同一个 inode 可以有多个名字”的全部秘密：目录里写两条指向同一 inode 的记录，两个名字就指向同一份数据，谁也不是谁的副本。文件系统并不强制一个 inode 只能被一个目录项引用，它只用一个链接计数来记有多少条目录项指向自己。

理解了目录项，也就明白了为什么目录里文件数极多时 ls 会变慢：查找名字要把目录项列表扫一遍，XFS 和 ext4 后来加了哈希索引来缓解，但名字到 inode 的映射关系没有变。

硬链接与软链接

ln 创建的是硬链接，它只做一件事：在目录里新增一条目录项，指向已有的 inode，并把该 inode 的链接计数加一。ln -s 创建的是软链接，也叫符号链接，它是一个独立的文件，有自己的 inode，文件内容只是一串路径字符串。

%h 就是链接计数，两个硬链接都显示 2。这组输出把三者的差别交代得很清楚：硬链接的 inode 号与源文件相同，类型仍是普通文件；软链接有自己的 inode，类型是符号链接。由此可以推出几条实践规则。

删除时，硬链接只是让计数减一，计数归零才真正释放数据块；软链接被删除只是少了那个路径文件，目标毫发无损，而目标先被删除时，软链接就悬空了，访问时报 No such file or directory。跨文件系统时，硬链接不可用，因为 inode 号只在单个文件系统内唯一，换个分区就可能撞号；软链接存的是路径，跨分区没有问题。指向目录时，硬链接被文件系统直接禁止，普通用户做不了，这是为了防止目录树出现环；软链接指向目录则是常见做法。

目录的链接计数不等于一：每个目录内有 . 和 .. 两条目录项，新目录的计数是 2，每多一个子目录加一。用 stat 看目录的 links 值，可以快速数出直接子目录的数量。

inode 数量与耗尽

回到开头那次故障。inode 的总数在格式化时按比例定下，之后不能单独增减；扩大文件系统只会按同一比例增加，比例本身改不了。df -i 显示的就是这个池子的使用率：

mkfs.ext4 默认按每 16 KB 分配一个 inode，也就是 -i 16384。对存放视频、镜像这类大文件的盘，这个比例很浪费，一块 1 TB 的盘会白白预留出几千万个 inode；而对小文件密集的场景又远远不够。预估方法很朴素：用文件总数乘以平均文件大小，看是否超过“容量除以每 inode 字节数”。一块 100 GB 的盘按默认比例只有约 650 万个 inode，如果上面放的是平均 2 KB 的会话文件、邮件队列或大量小图片，五千万个文件根本装不下，写到一半就会报空间不足，而 df -h 仍然显示有大半空闲。

所以格式化时就该按用途选参数。mkfs.ext4 -i 4096 表示每 4 KB 一个 inode，适合小文件；-T small 是同一意图的预设，-T largefile 则反过来，每 1 MB 才一个 inode。-N 可以直接指定 inode 总数，用来精确控制。XFS 的处理方式不同，inode 是动态分配的，用 xfs_info 能看到 imaxpct 这个上限百分比，默认 25，空间够就一般不会耗尽，但也不是无限。已经上线的盘如果 inode 打满，最现实的办法是把小文件迁到单独的分区，而不是原地扩容。

打开、删除与空间不释放

另一种“删了文件空间却没回来”更让人困惑：rm 掉一个正在被写入的大日志，df -h 的已用率纹丝不动。原因仍然在 inode 的链接计数上。rm 只是删掉目录项，计数减一；只要还有进程持有这个文件的打开描述符，内核就认为数据仍在使用，inode 和数据块都不会回收。此时文件已经没有名字，但通过 /proc/<pid>/fd 依旧能读写它。

输出末尾的 (deleted) 就是标记，2w 说明是 2 号描述符以写方式打开。处理办法只有两条：重启持有该文件的进程，让它关闭描述符；或者直接截断它，> /proc/1234/fd/2 会把文件长度清零，空间立刻释放，但文件依然没有名字。所谓“重启服务才回收空间”，本质就是关掉了所有打开的描述符。

块、稀疏文件与 du、ls 的差异

ls -l 显示的是 inode 里记录的逻辑大小，du 统计的是实际分配的块数。对普通文件两者大致相等，对稀疏文件则可能差出几个数量级。稀疏文件是文件系统的优化：truncate 或 dd seek 跳过的区域不分配数据块，读出来全是零，却不占磁盘。

du 的输出是 0，不代表文件是空的，只代表没有数据块被分配。要判断一个目录吃掉多少真实磁盘，应当看 du；要判断文件“看起来多大”，才看 ls -l。du --apparent-size 可以强制按逻辑大小统计，用来和 ls 对齐。迁移时要注意，cp 默认会把稀疏文件展开成实心文件，备份大镜像时会凭空多占几 GB，应该用 cp --sparse=always 或 tar -S 保留稀疏结构。

挂载与 /proc/mounts

文件系统要被访问，必须挂到某个目录上，这个目录叫挂载点。挂载之后，挂载点原有的内容被遮住，直到卸载才重新可见。所以当 df -h 显示某个分区满了、而 du 怎么也找不到大文件时，先怀疑有东西挂在了原本用来占位的空目录上。

/proc/mounts 是内核给出的事实来源，每行六个字段：设备、挂载点、类型、挂载选项、dump 与 fsck 顺序。mount 的输出更易读，findmnt 则能按树形展示并过滤：

bind mount 是把一个已有目录再挂到别处，两边共享同一批 inode，常用来把宿主机的目录交给另一套环境使用，mount --bind /srv/app /var/lib/app 之后，两个路径看到的是同一份文件。容器里看到的文件系统之所以和宿主机不同，就是启动时做了一串挂载与隔离，那部分另有专文，这里只需知道容器内的 /proc/mounts 是挂载传播的结果，不能当作宿主机的全貌。

日志与临时文件治理

日志和临时文件是 inode 消耗的两大来源。一个服务每天切几十份日志、每份再按小时细分，几个月下来就是几十万个小文件。治理分两层。先是控制数量，用 logrotate 的 rotate、daily、maxage 压住保留份数，并在切割后用 postrotate 让服务重新打开文件：

不重新打开文件，就会出现上一节说的局面：旧文件被改名后仍被进程占着，新文件写不进原来的描述符，空间也不释放。再是按 inode 清理。find /tmp -type f -mtime +7 -delete 按时间清，目录里文件极多时逐层删子目录比一次扫平更稳。如果误删了文件、进程还开着，先用 lsof 拿到 inode 号，再在别的目录里执行 find / -inum 131095 2>/dev/null，看它是否还有另一个硬链接；没有的话，只能从 /proc/<pid>/fd 把内容拷出来。养成给重要目录做硬链接或定期备份的习惯，比事后恢复可靠得多。

一张排查表

把前面的机制串起来，遇到文件系统相关的报错时可以按现象反查。笔者自己的顺序是先看 inode 与空间两个维度，再看进程占用，最后才怀疑挂载方式和链接关系。

现象 先跑的命令 常见原因
写文件报空间不足，df -h 却有空闲 df -i inode 耗尽，小文件过多
删掉大文件后空间不释放 lsof | grep deleted 进程仍持有已删除文件的描述符
du 统计远小于 df 已用 findmnt、mount 有文件系统遮住了挂载点
du 远大于 ls -l 的大小 stat、du --apparent-size 稀疏文件，或目录项本身占块
给文件建硬链接报错 df -T 源和目标不在同一文件系统
目录的链接计数大于 1 stat 含子目录，或 .、.. 的引用
软链接访问报文件不存在 ls -l、readlink 目标已被删除，链接悬空

小结

Linux 文件系统的要点是把“名字、元数据、数据”三件事拆开：目录项负责名字到 inode 的映射，inode 负责权限、大小与块指针，数据块才存真正的内容。理解了这层拆分，硬链接、软链接、inode 耗尽、已删除文件占着空间不放，都只是同一套机制的推论。日常排查请把 df -h 和 df -i 一起看，删除大文件前先确认没有进程占用，格式化数据盘前按文件大小分布选好 inode 比例。多数“磁盘满了”的故障，答案就在这几条命令里。
