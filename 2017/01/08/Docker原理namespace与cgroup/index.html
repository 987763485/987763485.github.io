Docker 原理：namespace 与 cgroup

本文属于《Docker 与 Kubernetes》第 3/51 篇
上一篇系列目录下一篇

2016 年年底，我们有一台 CentOS 7 的机器上跑着几个 Node 服务，全部用 Docker 1.12 起。某天值班时收到两条告警：一条说某个批处理容器的内存使用超过了 2 GB，另一条说这个容器的进程数掉了。登上去看，三件事让我停了很久。

第一件，在容器里执行 top，看到的是宿主机上全部进程：sshd、dockerd、containerd-shim，还有隔壁容器的 node 进程，一个不少。第二件，这个容器最终被杀掉了，docker inspect 里 OOMKilled 是 true，退出码 137，但在宿主机上 free 一看还剩十几 GB 空闲。第三件，容器里 ps aux | wc -l 的结果和宿主机上几乎一样，我们那个按进程数判断服务是否健康的脚本因此一直在误报。

三件事查下来，原因都不复杂。这个容器启动时带了 --pid=host，因为里面跑着一个采集宿主机指标的 agent，需要看见全部进程；/proc 又是从宿主机直接挂进去的，所以 ps、top 拿到的是宿主机那份进程表。至于 OOM，跟宿主机的空闲内存没有关系：启动参数里写了 -m 2g，内核对这个 cgroup 记账到 2 GB 就开始回收，回收不动就挑一个进程杀掉。宿主机内存再多，也不影响这个上限。

这次排查之后，我把”容器”这个词在脑子里重新定义了一遍：它不是一台小虚拟机，而是一个被内核动了手脚的普通进程——看到的世界被裁过，能用的资源被记过账，能做的动作被列过白名单。本文就把这三件事拆开讲：namespace 负责”看得见什么”，cgroup 负责”能用多少”，capabilities 与 seccomp 负责”能做什么”。搞清这三条线，前面那些看起来诡异的现象就都能解释了。

容器不是轻量虚拟机

先把定义摆出来。一个 Docker 容器，本质上是这样一个进程：它由 runc 通过 clone 创建，创建时带上一组 CLONE_NEW* 标志，于是拥有独立的 PID、mount、network、UTS、IPC 视图；创建后被放进一组 cgroup，CPU、内存、块设备 IO、进程数都按目录里的数值受控；它的根文件系统是若干只读镜像层加一个可写层联合挂载出来的；它的 capabilities 被裁到十几个，系统调用被 seccomp 过滤。这几件事凑齐，才叫”容器”；少任何一件，它都只是一个普通进程。

虚拟机是另一条路。Hypervisor 虚拟出 CPU、内存、磁盘、网卡，guest 里跑一个完整的内核，内核再管理 guest 里的进程。容器没有这一步：容器里的进程直接跑在宿主机内核上，系统调用直接进宿主机内核，只是在进入之前，内核先按 namespace 换了一份视图。

维度 虚拟机 容器
内核 每个 guest 一个完整内核 共享宿主机内核
启动 引导内核与 init，数十秒 fork/exec 加挂载，毫秒到秒级
隔离 硬件虚拟化，边界在内核之外 内核提供的视图，边界在内核之内
密度 单机个位数到几十 单机上百很常见
镜像 几 GB 的磁盘镜像 几十到几百 MB 的分层镜像

隔离强度上的差别要说得直白些。虚拟机逃逸需要打穿 Hypervisor，容器逃逸只需要一个内核漏洞加一个 CAP_SYS_ADMIN；共享内核意味着内核版本、sysctl、/proc 的一部分、时钟、设备都是共用的。所以”容器更轻”和”容器更不安全”是同一件事的两面，不是两件事。

启动速度也一样。容器启动没有内核引导，所谓”启动”是 runc 准备 rootfs 的挂载、写好 cgroup 文件、clone 出进程、exec 用户命令。镜像已经在本地时，这段时间通常是几十到几百毫秒；慢的时候多半卡在镜像层没缓存或者存储驱动上。顺带一句，编排层的事情本文不涉及。

调用链：从 docker run 到 clone

docker CLI 本身几乎不做事，它把参数打包成 JSON，通过 /var/run/docker.sock 发给 dockerd。dockerd 处理镜像、网络、卷这一层的事情，然后把”起一个容器”翻译成 containerd 的接口调用。containerd 管理容器的生命周期与镜像分发，真正创建进程时它会拉起一个 containerd-shim，由 shim 调用 runc。runc 是 OCI 运行时规范的参考实现，负责最脏的一段：准备 rootfs、建 cgroup、带命名空间标志调 clone、pivot_root、exec。当时 OCI 的运行时规范还没发布 1.0，仍停留在 rc 阶段。

这段拆分是 2016 年定下来的。Docker 1.11 把 containerd 引进来，1.12 又把 swarm mode 塞进 dockerd；到 2017 年初，containerd 已经从”dockerd 的内部库”变成一个可以被别的系统调用的守护进程。好处是职责清楚了：dockerd 重启不影响已经在跑的容器，因为容器的父进程是 shim 而不是 dockerd，这也是升级 Docker 时容器能不重启的原因。

flowchart LR
  cli["docker CLI"] -->|REST over unix socket| daemon["dockerd"]
  daemon -->|gRPC| ct["containerd"]
  ct --> shim["containerd-shim"]
  shim --> runc["runc"]
  runc -->|clone + CLONE_NEW*| proc["容器进程"]
  runc -->|写 cgroup 文件| cg["/sys/fs/cgroup"]
  runc -->|pivot_root| fs["overlay2 挂载的 rootfs"]

namespace 总览与 PID namespace

namespace 是一层给进程换视角的机制。同一份全局资源，在不同 namespace 里的进程看到的是一份不同的副本：进程号、挂载表、网卡、主机名、IPC 对象、uid 映射，都是这样被改写的。2017 年初的内核里，Docker 会用到的有六种，加上 4.6 才进来的 cgroup namespace 一共七种。

namespace 隔离的东西 /proc/<pid>/ns 下的名字 clone 标志
PID 进程号空间，能否看见别的进程 pid CLONE_NEWPID
Mount 挂载表与根目录 mnt CLONE_NEWNS
Network 网卡、路由表、iptables、端口空间 net CLONE_NEWNET
UTS hostname 与 domainname uts CLONE_NEWUTS
IPC System V 共享内存、信号量、消息队列 ipc CLONE_NEWIPC
User uid/gid 映射与 capabilities 的边界 user CLONE_NEWUSER
Cgroup 进程看到的 cgroup 根路径 cgroup CLONE_NEWCGROUP

读懂这张表要抓住两点。第一，namespace 是视图机制，不是配额机制，它不限制任何资源用量；一个容器里 fork 出多少进程、吃多少内存，和它有几种 namespace 毫无关系。第二，一个进程可以只加入其中几种：--network=host 就是不要 network namespace，--pid=host 就是不要 PID namespace，这正是开篇那台机器 top 能看到全部进程的直接原因。

PID namespace：进程号从 1 重新开始

内核里每个 task 都有一个全局唯一的 pid 编号，PID namespace 在这层编号外面套了一张翻译表。同一个进程，宿主机上看到的是 12345，容器里看到的是 1；/proc 里的目录名、ps 的输出、信号的目标，全都走这张表。所以在容器里 kill 1 和在宿主机上 kill 1 是两件不同的事。

PID 1 在 namespace 里有一串特殊待遇，值得单独记住：

  1. 内核不会给 namespace 的 1 号进程投递”没有注册处理函数”的信号。也就是说，SIGTERM 发过去没有反应，是内核跳过了默认动作，而不是进程主动忽略。docker stop 对一个不处理 SIGTERM 的 PID 1 只能等 10 秒再 SIGKILL，这就是 2016 年大家往镜像里塞 tini、dumb-init 的原因。
  2. 孤儿回收的责任落在 1 号进程身上。namespace 内父进程先退出的孤儿会被挂到 1 号名下，1 号要负责 wait；如果 1 号本身就是业务进程，它通常不会 wait，僵尸进程就慢慢堆起来了。
  3. 1 号退出，整个 namespace 里的进程会被内核一并杀掉，namespace 随之销毁。所以容器的主进程一挂，其他进程也活不下来。

Mount namespace：rootfs、pivot_root 与 overlay2

每个 mount namespace 有一份独立的挂载表，clone(CLONE_NEWNS) 时从父进程复制一份。所以容器里的 mount、umount 不会动到宿主机，前提是挂载传播属性设对了。Docker 的 rootfs 就是在这份私有挂载表上拼出来的：若干个只读的镜像层，叠一个属于这个容器的可写层。

写入发生在第一次真正写某个文件的时候。内核发现这个文件只存在于下层，会先把整个文件复制到 upperdir，再由写入方修改，这叫 copy-up。删除则相反：upperdir 里放一个 0/0 的 whiteout 字符设备，把下层同名文件遮住，文件本身没有被动过。docker diff 输出的 A、C、D 三个字母，对应的就是新增、修改、删除这三类记录。

copy-up 是按文件粒度的，代价经常被低估。如果镜像层里有个 500 MB 的数据文件，容器的第一次写就要拷 500 MB，还会多占 500 MB 磁盘。所以数据库目录、日志目录、上传目录必须挂 volume：volume 本质是 bind mount，直接落在宿主机文件系统上，不经过联合挂载，也不受 copy-up 影响。

根目录的切换用的是 pivot_root 而不是 chroot。chroot 只是把进程的 root 指针指向另一个目录，老的根仍然挂在挂载树上，只要进程手里还留着指向老根的 fd，或者有 CAP_SYS_CHROOT 又能 mount，就有路溜回去。pivot_root 做的是把整个挂载树的根换掉，然后让 runc 把老根 umount 掉，从挂载表里彻底摘走；这才叫断根。chroot 在 runc 里只作为某些辅助场景的兜底存在。

挂载传播属性也值得一提。runc 会把容器内的挂载点设为 private 或 slave，容器里执行 mount 不会把事件传播回宿主机的挂载表；反过来说，宿主机后来插入的 U 盘、挂载的 NFS，也不会自动出现在已经启动的容器里，因为那份挂载表在 clone 时就已经复制完了。这也是”为什么容器里看不到宿主机新挂的盘”的标准答案。

最后是几个必须重新准备的特殊文件系统。/proc 要跟 PID namespace 配套重新挂；/sys 通常以只读方式挂入；/dev 由 runc 用 tmpfs 搭一个最小集合，只有 null、zero、full、random、tty 这几个节点，其余设备节点要 --device 才会出现。

还有一个当年的现实问题：CentOS 7 上 Docker 默认的存储驱动一度是 devicemapper 的 loop 模式，thin pool 只有 10 GB，写满后容器报 no space left on device，而 df -h 看着还有空间。overlay2 在 1.12 之后逐渐成为首选，Ubuntu 16.04 的 4.4 内核原生支持，CentOS 7.2 之后的内核也回填了支持；迁移前先看一眼 docker info 里的 Storage Driver。

Network namespace：veth、docker0 与端口映射

每个容器一份 network namespace，意味着独立的网卡列表、路由表、iptables 规则、socket 端口空间和 lo 回环。两个容器可以同时监听 80 端口而不冲突，因为”端口”这个编号只在各自的 netns 里有意义；宿主机上的 80 已经被占用也不影响容器里的 80。

网卡是这样塞进去的：veth pair 是一对虚拟网卡，从一头发出去的包会从另一头收到。创建容器时，runc 建一对 veth，一头放进容器的 netns 改名为 eth0，另一头留在宿主机上叫 vethxxxxx，再插到 docker0 这个网桥上。

docker0 默认是 172.17.0.1/16，既是网桥也是容器的默认网关。容器之间通信走二层转发，不经过 NAT，所以互相访问速度快，也不消耗宿主机端口。

出网才需要 NAT。容器的默认路由指向 docker0，源地址是 172.17.0.x，这个地址在外面不可路由；宿主机打开 net.ipv4.ip_forward，再在 nat 表的 POSTROUTING 上做 MASQUERADE，把源地址改成出口网卡的地址。外面看到的流量来自宿主机 IP，回来的包靠 conntrack 还原。所以容器访问外网失败时，先查 ip_forward，再查 MASQUERADE 规则，比怀疑应用快得多。

端口映射的本质是 DNAT，不是”监听转发”。dockerd 会在 nat 表里建一条 DOCKER 链：

包到达宿主机 8080，在 PREROUTING 阶段被改写成 172.17.0.2:80，再转发进 docker0。另外 dockerd 还会起一个 docker-proxy 进程在宿主机上监听 8080 做用户态转发，主要兜底 DNAT 处理不了的路径，比如从宿主机自己访问映射端口、以及早期内核的 hairpin 问题；--userland-proxy=false 可以关掉它，代价是某些访问方式要自己补 iptables 规则。

-p 8080:80 和 -p 127.0.0.1:8080:80 的差别也在这条规则上：后者的 DNAT 只匹配目的地址是 127.0.0.1 的包，外网打不进来，只给本机 Nginx 反代用时这是正确姿势，比在应用层做 IP 白名单可靠。

两个常见的坑。第一，容器里执行 ip addr 只看到 lo 和 eth0，看不到 docker0，因为 docker0 在宿主机的 netns 里，这不是网络坏了。第二，docker0 默认占 172.17.0.0/16，一旦和公司内网网段撞上，路由会非常难受，上线前用 --bip 或 daemon.json 里的 bip 换掉，别等到出问题再改。至于 --network=host，等于容器直接用宿主机的 netns，端口就是宿主机的端口，也不再需要 DNAT，代价是这层隔离彻底消失。

UTS、IPC 与 User namespace

UTS namespace 管的是 hostname 和 domainname，是最简单的一种。docker run -h web-1 设主机名，不设就用容器 ID 的前 12 位。它的意义在于老程序喜欢拿 hostname 当节点标识：没有隔离时，容器里执行 hostname foo 会把整台机器的名字改掉；有了 UTS namespace，每个容器可以各叫各的，宿主机不受影响。

IPC namespace 隔离 System V 的共享内存、信号量和消息队列，也包括 POSIX 消息队列。默认每个容器一份私有的，PHP-FPM、PostgreSQL 这类重度依赖共享内存缓冲的服务不会互相踩键值。需要共享时有两个开关：--ipc=host 让容器用宿主机的 IPC，性能好、兼容老程序，但等于主动放弃这层隔离；--ipc=container:<id> 让两个容器共用一份，典型的 sidecar 用法。

User namespace 是七种里最晚成熟、也最容易被忽略的。它隔离的是 uid/gid 的映射关系，以及 capabilities 的适用边界。容器里可以是 root（uid 0），但这个 0 在宿主机上可以映射成 100000 这种没人用的普通 uid：

Docker 侧的开关是 --userns-remap=default，配合 /etc/subuid、/etc/subgid 预先分配 id 段。开了之后，容器里的 root 在宿主机上毫无特权，就算逃出去也只是个普通用户，这是所有隔离手段里最实的一层。

但 2016 年真正在生产上开它的团队不多，原因有三个：overlay2 与 user namespace 的组合当时还有限制，镜像里所有文件的属主都要重新 chown 一遍（镜像越大越痛），CentOS 7 上的相关默认配置也不友好。更常见的折中是镜像里用 USER 指定非 root 用户跑业务，虽然治不了”容器内 root 等于宿主机 root”的根，但成本低得多，配合 cap-drop 已经能挡掉大部分顺手攻击。

顺带提一句 cgroup namespace，4.6 才进内核，作用是让容器内看到的 cgroup 根路径变成自己那棵子树。Docker 在 2016 年底还没有默认启用它，所以本文后面讲 cgroup 时，路径一律按宿主机的视角写。

cgroup v1：从 memory 开始记账

namespace 解决”看得见”，cgroup 解决”用多少”。cgroup 的思路很朴素：在 /sys/fs/cgroup 下按子系统建树，把进程的 pid 写进某个目录的 tasks 文件，它就归这个节点管；节点目录里的一组文件就是限额与统计。CentOS 7 与 Ubuntu 16.04 用的都是 cgroup v1，各子系统各自一棵树，互不相干：

常用的是 cpu、cpuacct、memory、blkio、pids、devices、freezer 这几只。systemd 会把每个服务放进自己的 cgroup，Docker 起的容器默认落在 /sys/fs/cgroup/<子系统>/docker/<完整容器 id>/；如果 daemon 用 systemd 做 cgroup 驱动，路径则是 system.slice/docker-<id>.scope。cat /proc/<pid>/cgroup 能一次看到进程在每个子系统里的位置，这是后面做验证实验的入口。顺便说一句，cgroup v2 当时还处在内核实验阶段、尚未普及，本文不涉及。

还有一点要记住：限制沿层级继承。容器目录里的数值是它自己的节点，父节点（比如 /sys/fs/cgroup/memory/docker）上的设置会成为所有容器的共同上限，所以排查时不要只看容器那一层。把进程放进节点有两个入口，往 tasks 写 pid 只影响那一个线程，往 cgroup.procs 写则是整个进程的所有线程一起进，排查时后者更常用。

memory：限额、统计与 OOM

这个目录里真正要看的只有几个文件。memory.limit_in_bytes 是硬上限，-m 或 --memory 就写在这里；memory.usage_in_bytes 是当前记账用量；memory.max_usage_in_bytes 是历史峰值；memory.stat 给出 rss、cache、swap 的分项；memory.oom_control 里能读到 under_oom 状态，也能写 oom_kill_disable。

第一个容易误解的点是 usage 包含 page cache。容器里读一个大文件，cache 涨上去，usage 逼近 limit，内核会先回收这些可回收的页，而不是立刻杀人。所以”usage 贴着 limit”不等于”马上要挂”，真正危险的是 memory.stat 里的 total_rss 贴着 limit，那部分回收不掉。

第二个点是 OOM 的作用域。真的收不回来时，内核在这个 cgroup 内部触发 OOM killer，挑一个进程杀掉，通常挑 rss 最大的那个；dmesg 里会出现类似 Memory cgroup out of memory: Kill process 12345 (node) score 123 的记录，容器退出码 137（128 加 9），docker inspect 里 State.OOMKilled 为 true。注意被杀的范围是这个 cgroup，不是整台机器，这正是开篇那个困惑的答案：宿主机空着十几 GB，容器照样死。

还有一个常被忽略的参数是 swap。设了 -m 却没设 --memory-swap 时，容器可以用到两倍内存额度的 swap；在开了 swap 的机器上，”内存明明超了却没 OOM”多半就是这个原因。真要严格限制，两个参数一起给。

cpu：quota/period 与 shares 是两回事

cpu 子系统里有两套完全不同的旋钮，混着讲会得出错误结论。

第一套是带宽限制，靠 CFS 的周期与配额。cpu.cfs_period_us 默认 100000，即 100 ms 一个周期；cpu.cfs_quota_us 默认 -1 表示不限，写 50000 就是每个周期最多跑 50 ms，也就是半个核。命令行上这两个值直接对应 --cpu-period 与 --cpu-quota：想要一个半核，就写 --cpu-quota=150000；想要半个核，写 --cpu-quota=50000。按核数直接写的 --cpus 当时还在合入，稳定版里用不上，笔者反而习惯自己算 quota，账更清楚。

顺带说一句 -c。它是 --cpu-shares 的简写，不是配额。想限半核却写成 -c 0.5，Docker 会直接报错；就算写成 -c 512，也只是把权重减半，机器空闲时这个容器照样能跑满所有核。

它的语义是上限而非独占。容器在一个周期里跑满配额就会被 throttle 到下一个周期，哪怕机器上还有空闲核。cpu.stat 里的 nr_throttled 与 throttled_time 直接记录这件事。一个单线程的 Node 服务被设成半个核之后，一次 200 ms 的同步计算会被切成几个周期执行，P99 延迟突然变差，根因就在这里。

第二套是权重。cpu.shares 默认 1024，对应 --cpu-shares，没有单位也没有绝对含义，只在自己的 cgroup 和别的 cgroup 争抢同一个核时才生效：两个容器 shares 分别是 1024 和 512，抢起来大致是 2 比 1。机器空闲时，shares 为 2 的容器照样能跑满所有核。所以 shares 保证不了下限，只决定”抢的时候分多少”。

如果确实要绑核，用 --cpuset-cpus=0,1，那是 cpuset 子系统，语义又不同：它改变的是进程能在哪些 CPU 上被调度，而不是能用多少时间。

pids 子系统只有一个关键文件 pids.max，默认 max。Docker 1.12 里可以直接 --pids-limit 200。它的价值不在正常业务，而在防 fork bomb：一个死循环 fork 的脚本能在几秒内耗尽宿主机的 pid，整机跟着不可用；有了上限，超出的 fork 直接返回 EAGAIN，影响被关在一个容器里。默认不设限是个隐患，不少团队是被坑过一次才补上的。

安全边界：capabilities、seccomp 与只读根

namespace 和 cgroup 之外，还有一层决定”能做什么”的开关。

capabilities 把 root 的特权拆成几十项。Docker 默认只给容器十几项，包括 CHOWN、DAC_OVERRIDE、SETUID、SETGID、NET_BIND_SERVICE、NET_RAW、KILL、MKNOD、SYS_CHROOT 这些日常要用的；SYS_ADMIN、SYS_PTRACE、SYS_MODULE、SYS_TIME 都不给。容器里 cat /proc/self/status | grep CapEff 能看到当前的有效位图，用 capsh --decode= 解出来是哪些位：

这条命令把权限收到只剩”绑定 1024 以下端口”一项，是 2016 年比较推荐的做法。反过来，--privileged 会把所有 capabilities 全给、关掉 seccomp 与 AppArmor、把宿主机的设备都挂进来，等于这层防护整体失效；线上除极少数需要操作硬件的场景，不应该出现它。

seccomp 是第二道闸。Docker 从 1.10 起给容器挂一份默认 profile，直接拒绝四十多个系统调用，主要是加载内核模块、kexec、部分已废弃的调用，另外对 socket、clone 这类调用还有参数级白名单。要放行只能用 --security-opt seccomp=unconfined，但那就等于把它关了，不建议这么干。想确认某个调用是不是被拦，dmesg 里会留下 seccomp 的审计记录。

第三道是文件系统。--read-only 把整个根挂成只读，只有显式声明的卷和 --tmpfs /tmp 可写。这一条对防”应用被打了之后往镜像里写 webshell”特别有效，代价是要提前把应用会写的目录都准备好，改造量比想象中大一些。

最后是 root 用户的风险。没有开 user namespace 时，容器里的 uid 0 在宿主机上也是 uid 0，再叠加 SYS_ADMIN 或者一个没打补丁的内核漏洞，逃逸就不是难事。所以镜像里尽量用 USER 切到非 root，只给必要的 capabilities，根文件系统只读，三件事一起做才有意义。

三个流传很广的误解

第一个，容器里 free 看到的是宿主机的内存。/proc/meminfo 没有 namespace，它反映的是整个内核的内存状况，到 2017 年也没有隔离。于是在一个限制 256 MB 的容器里，free 会理直气壮地显示 16 GB。想让应用看到”正确”数字，当时常见的办法是挂 lxcfs，把 /proc/meminfo、/proc/cpuinfo 换成按 cgroup 数值伪造的版本。

第二个，nproc 不准。它读 /proc/cpuinfo，同样是全量视图：容器里 nproc 出来是 32，而 --cpu-quota=200000 只给了相当于两个核的时间片。Node 的 os.cpus().length、Java 的 availableProcessors()、Go 的 runtime.NumCPU() 都有同样的问题，按 CPU 数决定线程池大小的库会在容器里开出一堆抢不到时间的线程。这也是 --cpuset-cpus 在当年流行的原因之一：它能顺带让 nproc 看起来正常。

第三个，ulimit 与 cgroup 不是一回事。ulimit -n 是 per-process 的 rlimit，限的是单个进程能开多少 fd；pids.max 是 cgroup 级的进程数；memory.limit_in_bytes 是 cgroup 级的内存，三者互不覆盖。容器里的 rlimit 默认继承 dockerd 的设置（再由 systemd 的 LimitNOFILE 决定），要改得用 --ulimit nofile=65535:65535，改 cgroup 文件没有用。同理，ulimit -v 限的是虚拟地址空间，和 memory cgroup 的记账完全是两套逻辑。

小结

回到开头那句话：容器是一个被内核约束的普通进程。namespace 决定它看到什么，cgroup 决定它用多少，capabilities 与 seccomp 决定它能做什么，overlay 拼出来的 rootfs 决定它有什么文件。这四件事全部由宿主机内核执行，没有一层自己的内核，所以它快、轻、密度高，也所以它的隔离强度天生比虚拟机低一个量级。

排查容器问题可以按固定顺序走：先看 /proc/<pid>/ns/* 确认隔离有没有被主动放弃（--pid=host、--network=host、宿主机 /proc 挂进来），再看 /proc/<pid>/cgroup 找到它在每棵 cgroup 树上的位置，然后读对应目录里的数值，最后才怀疑应用。开篇那三个现象，按这个顺序很快就能定性。
