从一次首屏排查说起

去年冬天我们接手了一个后台管理系统，用的是 React 15 加 TypeScript 2.1，构建还是 2016 年主流的 webpack 1.x。项目按业务分了七八个页面：订单列表、订单详情、报表中心、权限设置、日志审计。路由表写在一个 routes.ts 里，每个页面的组件都在文件顶部用 import 引进来，再挂到路由配置上。

上线三个月后，首屏的 app.js 长到了 1.7 MB（未压缩），4G 网络下白屏三秒以上。运营同学早上打开系统只看一眼待办，却要等整个报表模块和图表库下载完。按路由拆包是最自然的想法：用户进哪个页面就下载哪个页面的代码。可是我们改了一版，把页面组件换成运行时才去取，app.js 只从 1.7 MB 降到 1.5 MB，剩下的部分纹丝不动。

排查下来，问题出在两个地方。第一，所有 import 都写在文件顶层，打包器在构建时就把路由表能看到的模块全部收进同一个 chunk，运行时再想”按需”已经没有东西可按。第二，那些体积最大的模块并不在路由表里，而是被页面里的枚举和常量文件间接带进来的：一个 enums.ts 里定义了十来个数字枚举，每个都被几个页面引用，谁也摘不出去。

第二个问题在同一周的线上排障里又露了一次头。订单状态在日志里是 status=2，支付渠道是 channel=1，退款原因是 reason=3。值班的同学对着代码翻 enum 的定义才对上号，翻错一个文件就得到相反的结论。数字枚举在编辑器里很好用，可一旦离开 IDE、进入日志、数据库和 HTTP 报文，它就退化成一串没有含义的整数。

这两件事看起来无关，其实指向同一个缺口：类型声明在编译期能表达的东西，和运行时真正需要的东西，中间隔着一层。动态 import 想让”什么时候加载”变成运行时决定，字符串枚举想让”值是什么”在运行时也保持可读。本文先讲 2017 年初的模块形态与静态 import 的边界，再讲当时可用的动态加载手段及其类型问题，最后落到枚举：数字枚举的坑、字符串枚举在 roadmap 上的讨论，以及 2.4 到来之前的替代写法。

版本现状与本文的边界

先摆时间线：它决定了本文哪些代码能跑、哪些只能当草图看。

TypeScript 2.0 在 2016 年 9 月发布，带来了 --strictNullChecks、用 @types 管理声明文件、--lib 指定内置库这几项基础设施。2.1 在 2016 年 12 月发布，keyof、映射类型，以及把 async/await 降级到 ES5/ES3 是它的主要卖点——这意味着同一份 2.1 的代码可以既用 async，又输出到 ES5，不必再等 Babel 的 stage 预设。2.2 正在收尾，object 类型是它最显眼的新东西。

至于 2.3 和 2.4：截至写作时，两者都还只在 roadmap 上。roadmap 页面列了方向——2.3 计划把若干严格检查聚合成一个 --strict 开关，2.4 讨论弱类型检测、动态 import 与字符串枚举——但版本号、发布时间、最终语义都没有承诺，nightly 里也还看不到可用的实现。所以本文的示例一律基于 2.1，凡涉及 import() 与字符串枚举的写法，都是”提案里长这样、我们预期它会怎么落地”，不是能直接粘进 .ts 就编译通过的东西。

strictNullChecks 的空值收窄、keyof 与映射类型的用法，属于另一篇文章的范围，这里只在必要处带一句，不重复展开。

当时的模块形态：--module 决定产物

TypeScript 自己不负责加载模块。它做的是把 ES module 语法翻译成目标模块系统的调用，--module 决定翻译成哪一种，--moduleResolution 决定它按什么规则找文件。这两件事经常被混为一谈：前者管”输出长什么样”，后者管”输入从哪来”。

静态 import 为什么挡住了按需加载

第一层限制来自语法。ES module 规范里，import 声明只能出现在模块顶层，不能塞进 if、函数体或循环。下面这种写法在 TypeScript 2.1 里直接报错，没有任何开关可以放开：

限制的根源是静态链接。模块的所有绑定在求值之前就已建立，import 得到的是 live binding——值会跟着导出方变，但绑定关系本身不可替换。正因为依赖图是静态的，循环依赖才有确定的求值顺序，变量提升和暂时性死区才有意义。语言层面一旦允许条件化导入，这些保证全部作废。

第二层限制来自打包器。构建时从 entry 出发遍历依赖图，每一条静态 import 都是一条边，边上的模块自然被收进同一个 chunk。把它们拆出去反而多一次网络请求，打包器没有理由这么做。2016 年常用的 webpack 1.x 里，字面量 require("./pages/report") 同样会被打进当前 chunk；写成 require("./pages/" + name) 这种表达式，webpack 会退化成 context，把目录下所有匹配的文件都收进来，体积不减反增。

第三层限制来自类型。TypeScript 把 import 翻译成 require 之后，求值时机一点没变：模块加载时一次性执行完，副作用也是那时发生的。很多人第一反应是把 import 挪进函数体，语法不允许；退而求其次写 require，又立刻掉进 any，前面辛苦建立的类型在入口处断掉。

所以按路由拆包这件事，卡点不在”打包器不支持拆”，而在”源码里没有给打包器一个可以拆的位置”。我们需要一种语法，它既在模块系统里合法，又能让工具看出这里是一个切分点。

import() 提案：形态与工具链的识别

TC39 的动态 import 提案给出的语法只有一句：import(specifier) 是一个表达式，返回 Promise，兑现值是模块的命名空间对象。截至本文写作时，它在提案流程里还没有走完，没有被写进任何正式标准，浏览器也没有实现；但打包器已经先动了——2017 年 1 月刚发布的 webpack 2 就把它当成了切分点。

它与静态 import 的差别，正好对应前面三层限制。语法上，它是表达式，可以出现在函数体、条件分支，甚至 Promise.all 的参数里；模块路径可以是任意表达式，不再要求字面量。语义上，它不做静态提升，调用时才去解析和求值；同一个模块的命名空间对象是缓存的，重复调用拿到的是同一份，但每次都会返回一个新的 Promise。工具层面，打包器看到 import("./pages/report") 就知道这里要单独出一个 chunk，字面量参数决定 chunk 里装什么；如果参数是拼接出来的表达式，又会退化成把整个目录打包的 context。

真要在 2017 年 1 月的 .ts 文件里写这一行，编译器会直接拒绝。TypeScript 2.1 的解析器根本不认识表达式位置的 import，报的是语法错误，类型断言救不回来，当时也没有”忽略下一行”的注释指令可用。所以只有两条路：把动态导入写进 .js 文件，交给打包器处理，TypeScript 侧再用声明文件描述它的导出；或者继续用 require.ensure，等编译器跟上。按 roadmap 的讨论，2.4 会接受这个语法，并把 --module commonjs 下的产物降级成类似 Promise.resolve().then(() => require("./report")) 的形状——这属于预期，不是现在能验证的事实。

类型怎么补回来

动态加载最难受的地方不是加载，而是加载完之后类型就断了。补类型有三条现成的路。

第一条路利用 import elision。我们照常写一句静态导入，但只在类型位置使用它，编译后这条 require 会被擦掉，运行时不会把模块打进首屏：

typeof ReportPage 就是整个模块命名空间的类型，page.renderReport 有完整签名，改错名字会报错。前提是 ReportPage 一次都不能出现在值位置：写一句 console.log(ReportPage)，擦除就失效，模块又回到首屏。落地时我养成了习惯，编译完在产物里搜一遍 pages/report，确认首屏 chunk 里没有它。

第二条路是手写声明。把动态模块的 .js 留在原地，旁边放一个同名 .d.ts，TypeScript 解析 ./pages/report 时会用声明文件当类型，不会去看实现：

这样做的好处是动态模块可以被单独维护，坏处是声明和实现会漂移，需要有人盯着。全局的 require 声明也归在这条路里，写成 declare var require: ... 或合并 NodeRequire 接口。

第三条路是等语言支持类型位置的 import。typeof import("./pages/report") 这种写法读起来最顺，把模块路径直接当类型用，不用额外的导入语句；但截至 2.1，类型位置出现 import(...) 同样是语法错误，这条路当时走不通，只能先用 import * as 加 typeof 顶着。

最后说一个容易被忽略的配置项：--moduleResolution。只有 node 模式才会按 Node 的规则去 node_modules/@types 里找全局声明、读 package.json 的 types 字段、解析目录下的 index.ts；classic 模式只做相对路径查找，是给老代码用的。团队里出现过”全局 require 声明明明写了却报找不到”的情况，最后发现是 --types 白名单把那个声明包排除了。配置最好一次定死。

拆包之后的工程问题

语法通了、类型补了，事情只完成一半。动态导入把”一次构建”变成了”构建期切分加运行期拼装”，工程上会冒出四类新问题。

第一类是 chunk 命名与缓存。output.chunkFilename 通常写成 [name].[chunkhash:8].js，chunk 名来自 require.ensure 的第三个参数（2017 年 1 月发布的 webpack 2 把它挪到了第四个），名字要稳定、可读，别用自增 id。风险在于发布：用户停留在旧页面，点击菜单时请求的是上一版的 chunk 文件名，而服务器上只剩新版本，直接 404。表现是”点了没反应”，控制台里一条脚本加载失败。我们的处理是在加载失败时给出明确提示并引导刷新，同时把 chunk 名带进错误上报。

第二类是公共依赖被重复打包。报表页和订单详情都引了 moment 和 lodash，各自切一个 chunk 的结果是两份库各带一遍，总下载量反而变大。2016 年的 webpack 1.x 只能把公共库固定放进 entry 的 vendor chunk，异步 chunk 通过全局变量或 externals 引用；webpack 2 的 CommonsChunkPlugin 多了处理异步 chunk 的选项，可以把多个异步 chunk 的公共部分抽成一个共享 chunk，但 1 月刚发布时文档还很薄。

第三类是加载失败与重试。弱网下 chunk 请求超时是常态，重试要克制：同一个 chunk 连续失败两次就让用户手动点，别写死循环。重试时不要用时间戳拼查询串来绕缓存——打包器会把它识别成表达式，退化成把整个目录打进 context，chunk 体积失控。真要绕缓存，重新插入 script 标签或整页刷新更可控。

第四类是服务端渲染。require.ensure 是打包器注入的运行时函数，Node 里根本不存在，同构代码执行到这一行会直接抛错。稳妥的写法是在入口处判断环境：

枚举的三种形态与产物

TypeScript 2.1 的枚举有三种写法，编译结果的差别比语法差别大得多，后面的取舍全靠这点认识。

Direction["Up"] = 0 这个赋值表达式的值是 0，于是紧接着拿 0 当键写 Direction[0] = "Up"，反向映射就是这么来的。结果是同一个对象上挂了两套键：Direction.Up === 0，同时 Direction[0] === "Up"。方向并不对称：名字到值靠声明，值到名字靠运行时写回，而写回只在值是数字时成立。这也是字符串枚举不做反向映射的原因：值本身是字符串时，两套键会撞在一起。

第三种是折中，编译时加 --preserveConstEnums：使用处仍然内联，但枚举对象也照常输出一份。适合”既要体积、又要运行时对象”的场景，比如既要在业务判断里内联，又要遍历成表单选项。

数字枚举的四个坑

数字枚举用起来顺手，问题都在它离开编辑器之后暴露。第一个坑是可读性。日志里 status=2、channel=1、reason=3，值班的人必须打开源码对照成员顺序。跨服务时更麻烦：订单服务、支付服务、前端各有一份”状态”枚举，谁也不知道对方的 2 指什么，只能在文档里维护对照表，而文档永远落后于代码。埋点的数字到了 BI 还要再建字典表翻译，链路上任何一环改了顺序，历史数据就失真。

第二个坑是值漂移。数字枚举默认从 0 自增，在中间插入一个成员，后面所有成员的值集体加一。已经落库的整型字段、消息队列里的事件码、客户端本地缓存的草稿，全部错位。缓解办法是显式赋值并留出空隙，比如 Created = 10, Paid = 20，但两个人同时往空隙里加成员照样会撞，编译器不会替你去重。

第三个坑是契约。后端 Java 那边如果直接序列化 ordinal()，脆弱程度一模一样：枚举顺序一调整，接口含义就变了。后来我们跟后端约定”每个状态必须有稳定的 code”，这条约定和数字枚举的默认自增正好相反：语言给的默认值，恰恰最不适合做契约。

公平地说，数字枚举并非一无是处。JSON 报文里一个数字只占一两个字节，字符串要占八到十个字节；在每天上千万条的上报流里，这个差异是实打实的成本。所以结论不是”数字枚举不能用”，而是”要按用途分开”——这一点留到讲取舍时再展开。

2.1 对这段代码的反应是报错：Type '"created"' is not assignable to type 'number'。语法解析没问题，是语义检查拒绝——当时的枚举成员只允许数字常量表达式。roadmap 上”字符串枚举”这条讨论了几个点：值是否必须唯一（数字枚举允许重复，字符串要不要照办）、是否保留反向映射（倾向不做，理由前面说过）、const 字符串枚举能否像数字那样内联、成员能否数字与字符串混用（倾向允许但明确不推荐）。这些都还是讨论，没有定稿语义，不能照着写生产代码。

在那之前，字符串字面量联合类型能干同样的活。它没有运行时开销，类型检查还比枚举严格——枚举的洞在于任意 number 都能赋值，联合类型不接受集合外的值。

几个细节值得说明。as OrderState 不能省：对象字面量里的字符串属性会被推宽成 string，不写断言的话 OrderState.Created 只是 string，传给参数处又得再断一次。类型和值同名是故意的，导入之后既能当类型也能当值，读起来和枚举几乎一样。ORDER_STATES 数组是为了运行时校验和遍历，它和类型定义是两处维护，新增成员时容易只改一处，这种不一致只能靠单元测试兜住。

守卫的签名 value is OrderState 是 1.6 起就有的用户定义守卫。这里用 indexOf 而不是 includes，是因为 --target es5 下默认 lib 里没有 ES2016 的数组方法，除非显式加 --lib es2016——--lib 是 2.0 才有的开关。

枚举与联合类型的取舍

先看产物：字符串联合在打包产物里是零字节，类型擦除之后什么都不剩；普通枚举每个都要生成对象，反向映射让成员数量翻倍；const enum 产物为零，但内联依赖编译器看到全部声明。

const enum 的这项依赖，在逐文件转译的链路里会直接断掉。ts-loader 的 transpileOnly 模式，以及任何逐文件处理的工具，都拿不到别的文件里的枚举声明：普通枚举还能退化成运行时对象，const enum 则要么报错，要么悄悄变成普通枚举（体积优势消失）。--isolatedModules 就是把这类跨文件假设显式禁掉，打开之后引用环境里的 const enum 会直接报错。2017 年初 Babel 一侧还没有官方的 TypeScript 预设，所以这条限制当时主要体现在 ts-loader 上。

再看库的边界。导出一个枚举，等于要求使用方在运行时也认得这个对象，类型声明和运行时实现绑在一起；导出一个字符串联合，使用方只需要那份 .d.ts，常量对象可选，甚至可以完全不导出，由使用方自己写字符串。对跨团队契约来说，后者更轻。

数字枚举仍有它的位置：权限位掩码这类密集数值（1 << 0、1 << 1，一个整数存十几项权限）、只在内部流转且不落库的状态机、高频上报里对字节敏感的事件码。这些场景的共同点是”数值本身就是语义”，不需要人读，也不需要跨版本稳定。

维度 数字枚举 字符串枚举（roadmap） 字符串字面量联合
运行时产物 对象，含反向映射 对象，无反向映射 无
日志可读性 差 好 好
值稳定性 依赖显式赋值 依赖显式赋值 值即契约
编译期约束 任意 number 可赋值 收紧 最严
可遍历 可以 可以 需额外数组

升级与迁移：从数字枚举到字符串联合

迁移的难点不在改类型，而在历史数据：数字已经进了数据库、缓存、消息队列，代码可以一天改完，数据不能。我们按四步走。

第四步，处理持久化。数据库加一列字符串，双写一段时间；读的时候优先新列，为空则回退旧列并顺手回填；等回填脚本跑完、确认没有旧客户端还在读数字，再删旧列。缓存和消息队列同理，消费端要能同时认两种形态，入口处用 assertOrderState 把住。

整个过程最怕 any 逃逸。JSON.parse 的结果是 any，直接断言成 OrderState 等于什么都没校验；正确做法是立刻过 assertOrderState。同理，as OrderState 只允许出现在守卫内部和常量对象定义里，业务代码里出现一次就该在评审里打回。把 --noImplicitAny 打开，至少能让这类断言显形。

一张能力状态表

判断标准很简单：能在 2.1 上编译通过的才算”已发布”，其余都只能算方向。

能力 状态 当时的替代方案
动态 import 表达式 roadmap（2.4 讨论中，未定稿） require.ensure 加类型别名；或写在 .js 里
字符串枚举 roadmap（社区提案与讨论） 字符串字面量联合加常量对象加守卫
类型位置的 typeof import 当时不支持 import * as 后取 typeof；手写 .d.ts
–strict 聚合开关 roadmap（2.3 计划） 逐项打开 strictNullChecks 等开关
弱类型检测 roadmap（2.4 讨论） 构造函数内手动校验、必填参数前置
@types 与 –lib 已发布（2.0） 直接使用
–module es2015 已发布（2.1） 交给打包器做 tree shaking
const enum 已发布 注意 isolatedModules 与单文件转译
按路由拆包 已发布（require.ensure，2016 年起） 配合 chunk 命名与失败重试

小结

动态 import 与字符串枚举在 2017 年初都是方向，不是现成的工具。能落地的做法是：用 require.ensure 或 System.import 拿到切分点，用 import * as 加 typeof 把类型接回来，用字符串字面量联合替代还写在 roadmap 上的字符串枚举。真到 2.4 落地那天，这些替代写法也不会白费——它们逼着我们把对外契约写成字符串、把加载失败想清楚，而这两件事和语法无关。先按今天能编译的方式把结构摆对，等语法到位时只需要删掉适配层。
