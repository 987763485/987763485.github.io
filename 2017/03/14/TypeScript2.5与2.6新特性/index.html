TypeScript 2.5 与 2.6 新特性

本文属于《TypeScript 学习路线》第 27/74 篇
上一篇系列目录下一篇

上周的例会上，同事把笔记本转到投影上，指着 GitHub 的 milestone 列表问了一句：TypeScript 的版本号都已经排到 2.5、2.6 了，我们的项目还停在 2.1，是不是落后了两个大版本？

这个问题很典型。过去半年里，TypeScript 的发布节奏明显加快：2.0 带来 strictNullChecks 与 @types 的组织方式，2.1 补上 keyof 与映射类型，2.2 刚刚落地。版本号一路小跑，团队的认知却往往滞后一两拍。于是“要不要升级”就变成一个既涉及技术、也涉及排期的问题。

先把结论放在前面：截至本文写作时，真正可以安装、可以在生产里跑的稳定版本只到 2.2；2.3 还在开发中；2.4 及以后只存在于路线图和 issue 讨论里。本文的示例全部基于 2.1 与 2.2，谈到 2.5、2.6 时，说的是“社区在讨论什么”，而不是“已经能用什么”。

截至 2017 年 3 月的版本时间线

把时间线摊开，版本号带来的紧迫感会消解大半。下面这张表按“能否在 npm 上装到稳定版”来划分状态，而不是按 milestone 的编号。

版本 状态 大致时间 团队该怎么对待
2.0 已发布 2016 年秋 生产可用，@types 体系从这一版开始
2.1 已发布 2016 年末 生产可用，keyof、映射类型、async 降级
2.2 刚发布 2017 年初 可以升，先在小项目验证
2.3 开发中 未发布 只在分支上试，不进主干
2.4 路线图 未排期 读 issue，不做计划
2.5 路线图 未排期 同上
2.6 路线图 未排期 同上

表格里最容易被误读的是“2.2 刚发布”这一行。刚发布意味着生态还没跟上：@types 下的包、编辑器插件、CI 镜像里的全局 tsc，都需要几周时间才追平。急着在同一天升到 2.2，遇到的问题多半不是语言特性，而是工具链的版本错位。

还有一个细节值得说明：milestone 是维护者用来归档 issue 的工具，创建 milestone 的成本很低。一个 2.6 的 milestone 存在，只代表“这个问题我们打算在 2.6 处理”，不代表 2.6 的日期、范围已经确定。把 milestone 当成发布公告，是版本焦虑的主要来源。

2.2 已经落地的能力

在讨论未来之前，先把手上能用的东西说清楚。2.2 是一个偏保守的版本，没有引入颠覆性的语法，但对日常写业务代码的帮助很直接。

最值得关注的是 object 类型。它表示“任何非原始类型的值”，用来替代过去那种宽泛的 {} 或 any：

这个类型的好处是把“我要一个键值容器”的意图写进了签名。过去用 {} 表达同样的意思，但 {} 在 TypeScript 里几乎接受一切非空值，约束力很弱。需要注意的是，object 与内置的 Object 不是一回事，后者包含所有带包装对象的值，实际项目里应当优先用 object。它也只保证“是对象”，不保证有某个字段，需要读属性时仍要靠泛型约束或类型收窄。

另一项变化发生在 --strictNullChecks 之下。2.2 修补了可选属性、联合类型在判空之后的可达性分析，减少了一些“明明已经判断过，编译器仍然报可能为空”的误报。这类改进不会改变写法，却直接影响团队愿不愿意把严格空值检查打开。完整的规则与迁移成本已经由《TypeScript 2.3 新特性详解》展开，这里不再重复。

从升级成本看，2.2 对绝大多数项目是加法：新类型可以用也可以不用，旧代码不改也能编译。真正需要留意的是 @types 包的版本，而不是语言本身。

路线图上的 2.3：方向而非承诺

2.3 是当前开发分支对应的版本，也是最容易让人产生“马上就能用”错觉的一个。社区讨论里能看到的线索主要有两条。

第一条是生成器与迭代器的降级质量。当编译目标设为 ES5 时，for...of、展开运算符、yield 都要靠辅助函数模拟，过去在边缘场景下会出现语义偏差或体积膨胀。路线图上的工作是把这套降级做得更完整，让同一份源码在 ES5 与 ES2015 目标下行为一致。

第二条是检查项的组织方式。TypeScript 的严格检查是逐个开关打开的，noImplicitAny、strictNullChecks、noImplicitThis 各有各的名字。社区一直在讨论提供一个总开关，把推荐的一组严格检查一次性打开，降低新项目的配置成本。这个讨论在 issue 里持续了很久，但截至本文写作时还没有随稳定版发布。

需要强调：以上都是“在做什么”，不是“已经能用什么”。2.3 的最终范围随时可能调整，本文不给日期，也不建议把它写进排期。至于 async/await 在 ES5 下的降级细节，2.1 起就已经可用，展开讲解在《TypeScript 2.3 新特性详解》里，此处只作划界。

2.4 的讨论：动态 import 与字符串枚举

2.4 的 milestone 里能看到两类讨论，恰好都来自真实项目的痛点。

第一类是动态 import() 的解析。webpack 2 在 2017 年 1 月正式发布后，import() 成为按需加载的常规写法，但 TypeScript 当时还不能完整识别这种表达式，模块类型要么丢失，要么得用 require 加断言绕过去。社区希望编译器能解析 import() 并推断出 Promise 与模块形状，而不是把它当成未知调用。截至本文写作时，这只是 issue 里的方案讨论，没有随稳定版发布。动态导入的用法与边界由《TypeScript 2.4 动态 import 与字符串枚举》专门讨论。

第二类是字符串枚举。数字枚举早就可以用，但业务里更常见的是与后端约定的字符串状态，比如订单状态、错误码。社区提出的方案是允许枚举成员初始化为字符串字面量，这样既能享受枚举的类型约束，又不必在前后端之间做一次映射。争议点在于：字符串枚举是否允许反向映射、与联合类型如何共存、编译后产出多大。这些问题没有定论，2.4 也就没有定论。

对这两个话题，正确的态度是“读 issue、不改代码”。如果项目确实需要按需加载，继续用现有的 require 写法并补类型断言；如果确实需要字符串常量，用 const 对象加联合类型就能达到接近的效果，不必等新版本。

2.5 方向：越往后越模糊

到了 2.5，milestone 里的条目明显变少，而且更像维护者的工作清单，而不是一份功能预告。从 issue 的标签和讨论看，方向大致集中在三处：编译性能与增量检查、编辑器里的响应速度、以及错误信息的可读性。这些都是“用起来更顺”的改进，不是“多一个语法”。

这也解释了一个现象：版本号越往后，能写的内容越少。不是因为维护者不努力，而是因为远处的计划本来就粗。一个条目在 2.5 的 milestone 里，可能只是“有人提了，先放这儿”，到了排期时被拆成三个 issue，或者整体挪到 2.6。把这种条目写成“2.5 将支持某某”，等于替维护者做了承诺。

因此本文对 2.5 只给出一句判断：它是一个以打磨为主的版本，短期内不会改变你写业务代码的方式。如果你的项目现在跑在 2.1 或 2.2 上，没有任何理由为了 2.5 推迟当前的重构或发布。

2.6 与 roadmap 的读法

2.6 的 milestone 比 2.5 更空，多数条目是从更早的版本挪过来的，涉及模块解析的边角、类型推断的个别场景。它们的共同点是：只有维护者能判断优先级，外部用户无法据此安排工作。任何“2.6 会解决某问题”的说法，都应该被当成猜测。

这也是本文想强调的方法：roadmap 不是 release notes。release notes 描述已经发生的事，可以逐条核对；roadmap 描述可能发生的事，条目会改标题、被拆分、被合并，甚至在发布前整段砍掉。博客把 roadmap 写成 release notes，代价是读者据此做选型，半年后才发现落空，而文章还留在搜索结果里。

合理的写法只有一种：注明“截至某日未发布”，说明信息来自 milestone 还是 issue，并明确不确定性。本文对 2.5 与 2.6 的处理，就是这种写法。

第四步是容易漏掉的基线对比：先在旧版本上跑一遍，记下错误总数与错误码分布，再在新版本上跑一遍。两个数字的差值才是升级引入的问题，绝对值没有意义——很多项目本来就带着几十个历史错误。

统计之前还要确认 tsconfig.json 的 include 覆盖了全部源码。只检查 src 而漏掉 test、scripts，会让错误数看起来很漂亮，问题留到升级之后才暴露。

如果项目用 Babel 6 转译，还要单独跑一次 tsc --noEmit。Babel 只剥掉类型标注，不做类型检查，构建通过不代表类型通过，这条边界在后文的风险清单里还会提到。

升级风险清单

第一，lib.d.ts 会变。每个 TypeScript 版本都自带一份标准库声明，升级后 DOM、ES2015 等库的类型定义可能增删。项目若依赖默认库，升级当天的报错往往来自这里。缓解办法是在 tsconfig.json 里用 lib 显式列出需要的库，把变化面收窄。

第二，@types 包会漂移。@types/node 的主版本跟 Node 版本走，@types/react 之类的包又不跟库的版本同步，一次 npm install 就可能拉到与编译器不匹配的声明。锁定 @types 的版本，和锁定 typescript 同样重要。

第三，Babel 6 与 tsc 的职责边界容易混。Babel 负责转译、不负责类型检查；tsc 负责检查、可以只检查不产出。两条流水线并行时，常见故障是 Babel 构建成功、tsc 报错没人看，或者反过来。把 tsc --noEmit 设成 CI 的独立步骤，别让它藏在构建脚本里。

第四，CI 缓存会让“版本没升”悄悄发生。node_modules 被缓存、全局 tsc 来自镜像、npx 命中旧包，都会让本地与 CI 行为不一致。升级后第一件事是在 CI 日志里打印 tsc --version，确认它真的是新版本。

迁移策略：小步走，留退路

顺序比速度重要。先把 typescript 与关键 @types 锁到精确版本，提交 yarn.lock 或 npm-shrinkwrap.json，保证任何人装出来的依赖树一致。然后按小版本递进，2.1 到 2.2 单独做一次，不要从 2.0 直接跳到 2.2 再顺手改代码。

每次只修一类错误。先处理 lib.d.ts 带来的库差异，再处理 @types 的签名变化，最后才动业务代码。三类混在一起，出问题时无法判断是哪一步引入的。每修完一类就提交一次，让 diff 可读、可回滚。

保留可回滚点：分支、tag、CI 产物三样至少留两样。设一个时间盒，比如两天，超过就回滚而不是继续硬扛。升级不是一次性任务，能停下来也是一种能力。

什么时候不该升级

三种情况建议维持现状。老项目，尤其是全局脚本、jQuery 插件、没有模块化的代码，类型检查的收益本来就低，升级只会带来一堆无从下手的报错。依赖锁死的项目，框架与 @types 互相绑定，单独升 TypeScript 会撕开版本矩阵。团队没有类型检查习惯的项目，升上去也只是多几行红色波浪线，最后把严格开关一个个关掉，等于白升。

还有一种临时情况：发布窗口临近。升级应该安排在两次发布之间，而不是提测前一天。

小结

截至 2017 年 3 月，能用的稳定版本到 2.2，2.3 在途，2.4 及以后只有路线图。升级评估的关键不是追版本号，而是确认基线、锁死依赖、小步验证、留好退路。至于 2.5 与 2.6，读 issue 可以，做排期不行。

2.1 已发布 keyof、映射类型、async 降级 多数项目的合理起点
2.2 刚发布 object 类型、空值检查修补 可升，先跑基线
