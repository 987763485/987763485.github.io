TypeScript 命名空间与模块

本文属于《TypeScript 学习路线》第 11/74 篇
上一篇系列目录下一篇

仓库里同时存在两套模块写法，是这两年在老项目里最常见的光景：一边是 namespace App.Utils 加 --outFile，编译出一个挂满全局变量的文件；一边是新目录里的 import/export，交给打包器处理。本文从这段具体的混乱出发，讲清 TypeScript 里 namespace、module 关键字与外部模块三者的来历、语法和编译产物，再谈两种写法如何互操作、老代码怎么一步步迁走。适合已经会写 TypeScript、但面对一仓库混杂写法不知道从哪下手的读者。

从一段越写越大的 namespace 说起

去年接手的一个后台项目，前端代码是从 2013 年一路加功能加到今天的。打开 src/app 目录，第一眼就是 namespace App.Utils：日期格式化、Cookie 读写、半个表单校验器，四年下来涨到两千多行。构建配置里写着 outFile: "dist/app.js"，产物是一坨 IIFE，浏览器里 window.App 下面挂着一串对象。与此同时，新同事在隔壁目录写 import { request } from './http'，那个目录是新项目，用 webpack 2 打包（2017 年初发布的版本）。

两套写法在同一个仓库里共存，谁也不服谁。老代码改一行要重跑一遍全量编译；新代码想复用老的工具函数，只能在文件顶上补一行 /// <reference path="../app/utils/date.ts" />，再写 App.Utils.formatDate(...)，否则编译器根本不认识 App。更麻烦的是评审时的分歧：有人说 namespace 挺好，简单直接；有人说它是上一代的产物，新代码一律不许用。

先把词澄清。TypeScript 1.5 之前，文档把现在叫命名空间的东西称作”内部模块”（internal module），把 CommonJS、AMD 那套称作”外部模块”（external module）。1.5 起统一改名：内部模块叫 namespace，外部模块就叫 module。改名的原因是 ES2015 定稿之后”模块”有了确定含义，再拿它指一个挂在全局对象上的分层命名空间，会让人误以为两者是一回事。所以看到老文章里的”internal module”，直接按 namespace 理解即可；看到”external module”，指的是有 import/export、需要加载器或打包器的文件。

两个文件各自生成一个 IIFE，都带 App.Utils || (App.Utils = {}) 的守卫，合并之后 App.Utils 上同时有 formatDate 和 trim。这就是所谓的跨文件合并，编译器负责检查类型，运行时负责把成员挂到同一个对象上。第三，合并只对命名空间成立，两个文件里出现同名的普通变量或同名函数，编译器会直接报重复声明。

合并也带来一个隐性代价：文件之间没有显式依赖。string.ts 用不用得到 date.ts 里的东西，编译器不关心，只要两边都声明了 App.Utils 就算一家人。真正决定运行时行为的是拼接顺序，下一节的三斜线指令就是为这件事服务的。

三斜线指令与 –outFile

三斜线指令是写在文件最顶部的单行注释，只有出现在文件第一个语句之前才生效。

它的作用是告诉编译器”这个文件之外还有这些文件，类型检查时一起看”。在 --outFile 模式下，它同时还承担排序职责：编译器按引用关系做一次拓扑排序，被引用的文件排在前面，没有引用关系的文件按 tsconfig.json 里 files 数组的顺序拼接。典型的配置长这样：

三斜线指令还有一个变体 /// <reference types="node" />。TypeScript 2.0 引入 @types 之后，用它引入 node_modules/@types 下的声明包，比写相对路径稳定得多。今天再看到满屏的 reference path，基本可以判定这是一个没有模块化的老工程，文件依赖全靠人肉维护。

迁移：从 namespace 到 ES module

迁移的原则只有一条：一个文件一个文件地改，每一步都让 tsc --noEmit 保持干净。整体重写听着痛快，改到一半才发现某个工具函数被二十个页面引用，回滚都回不干净。

flowchart TD
    A[挑一个叶子工具文件] --> B[去掉 namespace 外壳]
    B --> C[成员改为 export]
    C --> D[调用方改成 import]
    D --> E[tsc --noEmit 找残留的 App.xxx]
    E --> F[处理循环依赖与副作用初始化]
    F --> G[删掉三斜线指令与 outFile]

从叶子节点开始，因为它们只被引用、不引用别人。把 namespace App.Utils { export function trim() {} } 改成顶层 export function trim() {}，调用方从 App.Utils.trim(s) 改成 import { trim } from './utils/string'。

真正花时间的是两类问题。一是循环依赖：namespace 时代两个文件互相引用毫无压力，所有东西都挂在同一个全局对象上；拆成模块后，循环引用拿到的是”写了一半的导出对象”，运行时可能是 undefined，而类型检查不会报错。解法通常是把共用的类型和常量抽到第三个文件，或者把读取对方状态改成参数传入。二是副作用：老代码靠拼接顺序完成的初始化，比如给 String.prototype 打补丁、往路由表注册页面，必须变成显式的副作用导入：

打包器的视角可以顺带说清。--outFile 的产物是一个 IIFE 大文件，里面没有 export 语句，2017 年的 webpack 2 或 Rollup 看不到任何模块边界，只能当整体处理：没用到的函数照样打包，tree-shaking 无从谈起。全局污染是同一问题的另一面，var App 落在 window 上，两个 bundle 各带一份同名命名空间时互相覆盖。所以项目上了打包器，--outFile 就该退场；反过来，产物是给内嵌页面用的单文件，或者给不用打包器的用户分发 .js 加 .d.ts，它仍是最省事的选择。

小结

把四种写法放在一起看，选择并不复杂：

写法 产物 适用场景 迁移成本
namespace 加 --outFile 单个 IIFE，挂在全局对象上 无打包器的老页面、单文件分发的库 高，调用点全要改
import / export 每文件一个模块，交给打包器 新项目、Node 端代码 低，本身就是目标形态
import = require / export = require 调用，整体引入 引 CommonJS 包、导出单个函数 中，改成整体引入
export as namespace 声明 只有类型，没有运行时代码 给 UMD 库补声明 低，可长期保留

命名空间不是错误，它是模块标准落地之前 TypeScript 给出的一个够用的答案，代价是全局作用域、隐式依赖和无法静态分析的产物。2017 年再开新项目，没有理由选它；老项目也不必推倒重来，按目录、按叶子节点慢慢迁，让编译器在每个中间状态都保持干净，比任何一次性重构方案都可靠。
