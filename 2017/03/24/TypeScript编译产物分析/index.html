TypeScript 编译产物分析

本文属于《TypeScript 学习路线》第 14/74 篇
上一篇系列目录下一篇

我们把 TypeScript 交给 tsc 之后，真正跑在浏览器里的是另一套代码。线上出问题时，堆栈落在 __extends、__awaiter 这类名字上，读源码的经验就失效了。本文按语法逐块对照 tsc 2.1 与 2.2 的编译产物，说明每个开关改变了什么、辅助函数从哪里来、体积与调试成本落在哪里。适合已经会写 TypeScript、但还没认真读过输出结果的开发者。

从一段看不懂的堆栈说起

去年底的一个项目，页面在低版本浏览器上报错，堆栈只有三行，最上面一行指向 app.js 第 1240 行，函数名是 __awaiter。源码里没有这个名字，在整个仓库里搜索也没有结果，因为它压根不存在于源码，是编译器在输出阶段自己加进去的。

这样的经历大概每个 TypeScript 项目都会遇到一次。tsc 并不只是把类型标注擦掉，它还要把类、装饰器、async 函数这些较新的语法翻译成目标环境能执行的旧语法，翻译过程依赖一批运行时辅助函数。看懂这些函数的形状，等于拿到了一张阅读编译产物的地图。下面从命令行开关开始，逐个语法看输出。

tsc 的输出控制

tsc 的行为几乎由命令行参数或 tsconfig.json 决定。日常最常调整的是五个：target 决定降级到哪个语法版本，module 决定模块的包装形式，outDir 决定输出目录，sourceMap 决定是否生成映射文件，declaration 决定是否额外产出类型声明。

target 的默认值是 es3，这是 2017 年仍然容易踩的坑：不显式写 target，编译器的很多假设都停留在很旧的年代。要兼容 IE 11，es5 就够；只跑 Node 6 以上，可以直接用 es2015，此时多数语法原样保留，产物与源码接近同构。

module 与 target 相互独立，两者组合决定最终文件的长相：

target module 产物特征 常见场景
es5 commonjs 类降级为函数，require 与 exports Node 端、打包前
es5 amd define 包裹，依赖数组前置 RequireJS 项目
es5 es2015 语法降级，import 与 export 保留 交给打包器处理
es2015 es2015 几乎与源码同构 Node 6 以上、现代浏览器

第一段是 __extends，它先把父类的静态成员逐个复制给子类，再处理原型链。中间那个空函数 __ 不是多余的：直接写 Object.create 在不支持它的 ES3 环境会报错，用一个临时构造函数 new __() 既能拿到父类原型，又能保住 constructor 指向。这是辅助函数里最典型的”兼容老环境”写法。

第二段是类本身。class Animal 变成一个同名 var 加一个立即执行函数，类体里只剩构造函数，speak 被挂到 Animal.prototype 上。注意字段 name 是在构造函数里赋值的，所以每个实例各有一份；方法在原型上共享。这就是”类只是语法糖”最直白的证据，也解释了为什么给原型加方法不会增加实例内存。

第三段是继承。子类构造函数先调用 __extends，然后把自己的逻辑写成 _super.apply(this, arguments)，用 || this 兜住父类构造函数返回对象的情况。super.speak() 则变成 _super.prototype.speak.call(this)，静态方法上的 super 会被编译成 _super.xxx.call(this) 的形式。还有一个容易忽略的差异：这样挂上去的方法是可枚举的，for...in 会遍历到 speak，而 ES2015 原生类的方法不可枚举。

__decorate 收到四个参数：装饰器数组、目标对象、属性名、属性描述符。目标不是类时它先取 getOwnPropertyDescriptor，然后从数组末尾往前依次调用，最后用 Object.defineProperty 把描述符写回去；如果环境里有 Reflect.decorate，会优先交给它。这就是为什么多个装饰器写在同一个方法上时，执行顺序是自下而上。

从产物能读出四条顺序规则。方法装饰器在类体定义完之后、return 之前执行，所以它早于类装饰器；属性装饰器拿到的描述符是 void 0，因为它只能改原型上的占位；参数装饰器被 __param 包了一层，第四个参数是参数下标，并且排在数组末尾，倒序执行时先于方法装饰器；类装饰器的返回值会替换整个构造函数，所以它最后生效。至于装饰器内部做什么，产物里看不到，那属于框架的事。

__awaiter 的职责是把生成器包装成 Promise：它接收 this、arguments、一个 Promise 构造器和生成器函数，内部用 new P(...) 建 Promise，step 里判断 done，没结束就把 yielded 值交给 Promise.resolve(...).then(fulfilled, rejected) 继续驱动。第三个参数传 void 0 表示用全局 Promise。

__generator 则把函数体变成 switch (_a.label) 的分支表。[4, expr] 是”暂停，等待这个值”，_a.sent() 取回结果；[2, value] 是 return。每个 await 占一个 case，try/catch 包在状态机外层，异常经 generator.throw 走到 rejected 分支。

这里有一条硬依赖：产物假设运行时有 Promise。IE 11 没有，必须先引入 es6-promise 或 core-js 的 polyfill，否则一进 __awaiter 就是 Promise is not defined。tsc 只改写语法，不补内置对象，这条边界要记住。也正因为如此，2017 年初的浏览器端与 Node 6 跑的仍是这段产物，原生 async 要等 Node 7.6。

它优先用原生 Object.assign，没有就退回 for...in 加 hasOwnProperty 的循环。IE 11 正好没有 Object.assign，走的是回退分支，这也是当年 Object.assign polyfill 常被单独提起的原因。两个分支都是浅拷贝，只复制可枚举的自有属性，嵌套对象仍是共享引用。

装饰器元数据：design:type

再打开 emitDecoratorMetadata，__decorate 的数组里会多出 __metadata 调用：

三个键各管一类信息：design:type 是属性或方法的类型，design:paramtypes 是参数类型数组，design:returntype 是返回值类型。它们从类型标注抄来，标注本身已被擦掉，所以 interface 和联合类型只能落成 Object。__metadata 最终调用 Reflect.metadata，运行时必须先加载 reflect-metadata，否则这一步直接报错。依赖注入类的框架就是靠读 design:paramtypes 决定给构造函数传什么，这也是它要求两个装饰器开关同时打开的原因。

辅助函数的体积与 --importHelpers

每个辅助函数开头都带 this && this.__extends 这类判断，为的是脚本被重复加载时不重复定义。但默认行为是每个文件各注入一份：两百个文件的项目，只要有几十个用了类、async 或装饰器，__extends、__awaiter、__generator、__decorate 就会被复制几十遍。压缩工具能缩短函数名，却没法跨文件合并这些定义，它们各自处在独立作用域里。

--importHelpers 从 2.1 起可用，打开后产物改成引用：

tslib 就是把辅助函数单独打包的小库，2017 年初已经可以 npm install tslib@1 直接安装，体积只有几 KB。代价是它从编译期的事变成运行时依赖：dependencies 里要有它，AMD 项目要在路径配置里指过去，版本还要和 tsc 大致匹配，否则新引入的辅助函数会找不到。库作者通常划算，单入口应用则要看重复量。

sourcemap：映射文件里有什么

--sourceMap 为每个 .js 生成同名 .map，内容是纯 JSON：

mappings 用 Base64 VLQ 编码，每一段说明产物第几列对应源文件第几行第几列，浏览器与错误监控平台都按它还原位置。sources 是相对路径，默认不带源码正文；要让映射自带源码，得加 --inlineSources，内容写进 sourcesContent。--inlineSourceMap 更进一步，把整个 map 以 base64 塞到 .js 末尾，Node 端单文件部署方便，浏览器端会明显增大体积。

生产环境是否上传 .map 取决于错误监控怎么接：传到监控平台但不公开访问，堆栈可读又不泄露源码；直接放进静态目录，等于把源码公开。稳妥做法是构建时生成、上传后从发布产物里删掉，或在服务端限制 .map 的访问。本地调试则在 DevTools 的 Sources 面板直接看到 .ts，断点打在 TypeScript 上，映射由浏览器完成。

与 Babel 6 的分工

2017 年一个 TypeScript 项目通常有两条流水线。一条是 tsc 全包，类型检查与降级一次完成，产物直接交给打包器；另一条是 tsc 只做类型检查（--noEmit）或只输出 ES2015 模块，语法降级交给 Babel 6 的 babel-preset-env，polyfill 交给 core-js。

两条线的产物有实质差异。类：Babel 生成 _classCallCheck 与 _createClass，方法用 Object.defineProperty 定义，不可枚举，贴近原生语义；tsc 直接挂 prototype，方法可枚举。继承：Babel 的 _inherits 校验父类必须是函数或 null，_possibleConstructorReturn 检查 super() 的返回值；__extends 只做复制。async：Babel 依赖 regenerator runtime，通常经 babel-plugin-transform-runtime 从 babel-runtime 引入；tsc 用内联的 __generator。复用：Babel 的 transform-runtime 天然把辅助代码外置，tsc 要显式开 --importHelpers。

反过来，Babel 做不了需要类型信息的事：const enum 内联、命名空间合并、export =，它只能报错或原样保留。所以当年的常见组合不是二选一，而是 tsc 管类型与模块形态，Babel 管剩余语法的降级。

语法与产物对照

语法 target 产物特征 注意点
类与继承 es5 构造函数 + 原型方法 + __extends 方法可枚举，字段按实例分配
装饰器 es5 __decorate + __param 倒序执行，类装饰器最后生效
装饰器元数据 es5 __metadata 三个 design 键 依赖 reflect-metadata
async/await es5 __awaiter + 状态机 运行时必须有 Promise
解构与展开 es5 _a 临时变量 + __assign 浅拷贝，IE 需 polyfill
数字枚举 任意 双向映射对象 体积随成员数翻倍
const enum 任意 字面量内联 值在编译期冻结
迭代 2.2 仅数组按下标展开 2.3 的降级尚未发布
辅助函数 es5 每文件一份或引用 tslib --importHelpers 后成为依赖
调试 任意 .map 加 VLQ 映射 生产环境谨慎公开

小结

编译产物不是黑箱，它由几条固定规则生成：类落到构造函数与原型，继承靠 __extends，装饰器靠 __decorate 倒序执行，async 展开成 __awaiter 包着 __generator 状态机，解构与展开靠 _a 这类临时变量和 __assign。这些辅助函数默认每个文件一份，--importHelpers 可以把它们挪进 tslib。

排查线上问题时，先确认 target 与 module，再看堆栈里的辅助函数名，基本能定位到源码的哪一类语法。还有一条边界比产物形状更容易被忽略：tsc 只改语法，不补 API，Promise、Object.assign、Symbol.iterator 都要靠 polyfill 兜住。
