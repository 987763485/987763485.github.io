Docker 私有仓库 Harbor 搭建

本文属于《Docker 与 Kubernetes》第 15/51 篇
上一篇系列目录下一篇

团队把服务拆成容器之后，第一个卡住的不是 Dockerfile 怎么写，而是镜像放在哪里。公网 registry 不能放公司镜像，靠 docker save 和 docker load 在机器之间倒腾又太笨。本文记录一次 Harbor 私有仓库的落地过程：从选型、安装、证书、权限到复制与故障处理，适合正准备在内网自建镜像仓库的运维与后端同学，读完可以照着命令走一遍。

需求：镜像不该出内网

事情的起因很朴素。公司内网有一批业务镜像，里面有数据库连接串和内部接口地址，这些东西不可能推到公网。最初的替代方案是 docker save 打成 tar 包，scp 到目标机器再 docker load。三四台机器、十几个镜像还能忍，等到测试、预发、生产三套环境加上每周两次发版，tar 包就在机器之间互相传，谁都说不清哪个是最新的。

更麻烦的是版本追溯。docker images 列出来一堆 <none>，谁也记不住上周五上线的那版镜像对应哪个提交。我们需要一个地方，能按项目存放镜像、能打标签、能控制谁能推谁能拉、最好还能看到操作记录。

这件事在 2017 年并不新鲜，Docker 官方早就提供了 registry 镜像，Harbor 也已经是 CNCF 下的项目。要选的只是：跑一个裸 registry，还是上一个带管理界面的仓库系统。本文的结论是后者。

选型：官方 Registry 与 Harbor

最轻的方案是直接跑官方镜像 registry:2。它实现 Docker Registry HTTP API V2，把镜像层以 blob 写进本地目录，配一个 config 就能用。缺点是只做存储和分发，像一个没有门卫的仓库：没有界面，没有用户概念，没有项目隔离，想限制某个团队只能推自己的镜像，只能在前面套一层 nginx 做 basic auth，而且所有镜像共用一个命名空间。

Harbor 是 VMware 开源、后来捐给 CNCF 的镜像仓库，2017 年初主流的 1.1/1.2 一代已有比较完整的企业功能。它没有重写 registry，而是在前面加了一层：存镜像的还是 registry，Harbor 负责认证、授权、界面和周边任务。镜像数据仍是标准格式，客户端的 docker push 行为不变。

Harbor 比裸 registry 多出来的四件事，正好对应我们当时的四个痛点。

  • 项目管理：镜像按项目分组，项目名成为镜像路径的第一段，团队之间天然隔开。
  • RBAC：成员分角色，访客只能拉，开发者能推能拉，管理员能管成员，不用在 nginx 里维护账号。
  • 复制：把某个项目或某批标签同步到另一个 Harbor 实例，跨机房分发不用人肉搬运。
  • 审计：谁在什么时候推了哪个镜像、删了什么，都有日志可查。

反过来说，如果只是单机自用、只有一个人推镜像，官方 registry 加一个 volume 就够了，没必要引入六七个容器。选型看的是团队规模，不是功能多少。我们当时十几个人、三套环境，Harbor 的复杂度付得起。

Harbor 的内部组成

第一次 docker-compose ps 看到七个容器，容易以为这是个庞然大物。按职责拆开，每个都很薄。下面的图是 1.x 一代的部署形态，容器由同一个 compose 文件拉起。

flowchart TD
    C[客户端 docker push/pull] --> N[proxy: nginx]
    N --> U[ui: core]
    N --> R[registry: 存储镜像层]
    U --> D[(mysql: 元数据)]
    U --> V[(redis: 会话缓存)]
    U --> J[jobservice: 复制与清理任务]
    L[log: 日志收集] --> U
  • nginx（proxy）：唯一对外暴露的入口，监听 80/443，把 /v2/ 转给 registry，其余转给 core，同时负责体积限制和证书。
  • registry：官方 registry 镜像，真正写镜像层的地方，数据落在 /var/lib/registry。它不判断权限，信任前面传来的认证信息。
  • core（ui）：Harbor 自己的 Go 服务，提供界面和 API，处理登录、项目、成员、权限与镜像元数据，auth_mode 这类配置归它。
  • mysql：存用户、项目、角色、镜像 tag 与审计记录，是真正的元数据库，不是缓存。
  • jobservice：后台任务进程，复制、远程同步、过期镜像清理这类耗时活儿都由它跑，状态写进数据库。
  • redis：存会话和一些短期状态，丢了不影响镜像数据，但会打断已登录用户的会话。
  • log：收集各容器的日志做集中输出，排障时比 docker logs 一个个翻方便。

镜像数据和元数据是两套东西：registry 目录里是二进制层，mysql 里记着”这个 tag 指向哪一层”。备份只备一边，恢复出来就是有界面没镜像、或者有镜像但列表空白的半瘫状态。

前置条件

Harbor 对宿主机的要求不算高，但有几项必须提前确认，否则安装脚本跑到一半才报错。

  • Docker：1.12 或 1.13 都可以，安装脚本会检查版本。我们用的是 1.13，compose 文件是 v2 格式。
  • docker-compose：1.8 以上，能解析 v2 的 services 写法。它是独立二进制，和 Docker 版本不绑定。
  • 域名与证书：需要一个内网能解析的域名，比如 harbor.corp.local。客户端拿它比对证书，用 IP 访问会直接报证书错误。
  • 磁盘：镜像层很占地方，一个中等项目一个月几十 GB 很正常。给 /var/lib/registry 单独挂盘，别和系统盘混。
  • 端口：80/443 给 nginx，不要被别的服务占用，安装脚本会检查端口冲突。

离线环境要额外准备。release 包里有脚本和 compose 文件，但七个容器的镜像要单独拉。在一台联网机器上把镜像导出成 tar，再拷进内网。

导入后核对一遍 tag，和 compose 文件里写的一致再开始安装，否则 docker-compose up 会去公网拉镜像然后失败。

安装：从 release 包到登录页

Harbor 有在线版和离线版两种安装包，后者把镜像 tar 一起打进去，内网直接用离线版。解压后目录里主要是 harbor.cfg、docker-compose.yml 和 install.sh。要改的只有 harbor.cfg，其余文件不要手改，安装脚本会用它们生成最终配置。

需要动的配置项不多，下面这几个必须处理。

改完执行安装脚本。它会校验版本、检查端口、按 harbor.cfg 渲染配置并拉起容器，最后打印登录地址。整个过程两三分钟。

装完还有一个容易漏的动作：确认客户端能解析 hostname，必要时写进 /etc/hosts。访问 https://harbor.corp.local 看到登录页，用 admin 进去就算成功。页面打不开但容器都在跑，先看 nginx 日志，多半是证书或端口。

HTTPS：自签证书与信任链

Harbor 按 ui_url_protocol 决定 nginx 是否监听 443，但证书不会自动生成，要自己放进 certs/ 目录，文件名固定为 harbor.crt 和 harbor.key。内网没有公网 CA，通常自签根证书再签发服务器证书。

客户端不认识这个 CA，docker login 会报 x509: certificate signed by unknown authority。把 ca.crt 分发到各机器的信任目录，重启 Docker 重新加载。

--insecure-registry 是另一条路：声明这个仓库可以走 HTTP 或跳过证书校验。代价很直接——镜像层和登录凭据都以明文或未验证的通道传输，中间人可以替换镜像内容而 Docker 不报警。它只适合两种场景：完全隔离的内网做临时验证，以及证书还没签好时的过渡。上生产就该去掉，否则等于拆掉仓库唯一的传输保护。

项目与权限模型

Harbor 里所有镜像都必须属于某个项目，项目是权限的最小单位，也是镜像路径的第一段。这跟裸 registry 里随便命名不同：library/nginx 和 payment/api 是两条完全独立的路径。

项目分公开和私有。公开项目的镜像任何人登录后都能拉，适合基础镜像和公共中间件；私有项目只有成员能访问。默认的 library 是公开项目，别把带配置的业务镜像丢进去。

成员角色有四档，按项目授予，同一个人在不同项目里可以是不同角色。

  • 项目管理员：管成员、管仓库、能删镜像，一般给项目负责人。
  • 开发人员：能推能拉，不能改成员，日常研发用这个。
  • 访客：只读，能拉不能推，适合测试和外部协作方。
  • 受限访客：只读且看不到日志，给审计要求更严的场景。

镜像的完整路径是 host/project/image:tag，三段都不能省。直接 docker tag nginx:1.11 harbor.corp.local/nginx:1.11 会失败，因为第二段被当成了镜像名而不是项目名，必须先建项目再按三段推。

客户端使用

客户端不用装额外工具，Docker 自己就能推拉。先登录，凭据存在 ~/.docker/config.json，之后 push 自动带上。

如果仓库暂时还是 HTTP，或证书链没铺到这台机器，要在客户端声明不安全的仓库。1.13 的写法是改 /etc/docker/daemon.json，改完重启服务。

标签习惯要早点养成：不要只用 latest，它无法追溯，回滚只能靠记忆。用语义化版本或提交短哈希，比如 1.4.0 和 1.4.0-a3f9c21 各推一份，出问题能精确回到某个构建。

Docker 的基础概念、网络模式和资源限制不在本文范围，这里只关心镜像怎么进出仓库。接编排系统时凭据注入是编排层另配的事。

跨机房复制

复制解决的是”镜像推过一次，不想再推第二次”的问题。典型场景是研发机房的 Harbor 作为唯一入口，生产只允许从内部同步；或者两地各一个实例做灾备。入口在界面的”仓库管理”：先加远程实例，填目标地址和凭据，再在策略里选源项目、目标项目与触发方式。

规则里可以指定仓库名和标签过滤，比如只同步 release-*，避免把每次构建的临时标签都搬过去。任务由 jobservice 执行，界面上能看到进度和失败原因。带宽要实际考虑：500 MB 的镜像跨机房可能跑十几分钟，策略最好放夜间并给足超时。失败重试是自动的，但目标端磁盘满了，重试再多次也没用。

用户与 LDAP

Harbor 默认用本地数据库认证，即 auth_mode = db_auth，管理员在界面上建账号。人数少时最省事，缺点是账号要手工维护，人一走就留下僵尸账号。

人数多了就接 LDAP 或 AD，把 auth_mode 改成 ldap_auth 再填连接信息。不同版本给的字段名不完全一样，按当前版本 harbor.cfg 里实际给出的字段填，不要照抄别处。大致包括：服务地址与端口、Base DN、Search DN 与密码、用户过滤条件、LDAPS 证书校验。本地账号仍然保留，admin 作为兜底入口不要删。改完同样要重跑 install.sh，只重启容器有时不生效。

备份与升级

备份要分两半做。元数据在 mysql 里，用 mysqldump 导出；镜像在 registry 的存储目录里，用 tar 打包或走文件系统快照。两者要在同一时间窗口做，否则会出现数据库记着某个 tag、存储里却没有对应层的情况。

升级的顺序更容易出错。新版本会带来新的 compose 文件和库结构，正确做法是先 docker-compose down，备份数据目录与数据库，再解压新版本、沿用旧的 harbor.cfg 与证书、执行 ./install.sh，脚本会处理 schema 迁移。不要在容器还跑着时覆盖 compose 文件。

常见故障

几个踩过的坑，按出现频率排。

x509: certificate signed by unknown authority：客户端不认 CA。把 ca.crt 放进信任目录并重启 Docker；检查证书的 SAN 是否包含实际访问的域名，用 IP 访问一定会失败。

413 Request Entity Too Large：镜像层超过 nginx 的上限。改 Harbor 的 nginx 配置，把 client_max_body_size 调到 0 或足够大的值，然后重载 nginx。这个值在 Harbor 的模板里，改完要重新渲染配置。

登录返回 401：先确认用户名密码，再确认 auth_mode 与实际账号来源一致——用 LDAP 模式去登一个本地账号，或者反过来，都会 401。凭据缓存脏了可以 docker logout 后重登。

磁盘写满：registry 目录涨得快，多半是旧 tag 没清。Harbor 能按策略清理，但删除是异步的，空间不会立刻回收，还要一次 registry 的垃圾回收。给这个分区单独设监控阈值，写满之后 push 会全部失败，连删除都可能失败。

小结

Harbor 的价值不在于它自己实现了 registry，而在于它在官方 registry 外面补齐了企业要的那层管理：项目隔离、按角色的权限、跨实例复制和审计。安装本身不复杂，真正花时间的是证书信任链、客户端的三段式镜像路径，以及备份时别把元数据和镜像层分开。

如果重来一次，我会把三件事放最前面：先规划域名和证书，别用 IP 顶着；先定项目命名规范，别让 library 变成垃圾桶；先写好备份脚本并演练一次恢复。仓库是基础设施，它的可靠性不取决于装得多顺，而取决于出事时能不能把镜像和数据找回来。
