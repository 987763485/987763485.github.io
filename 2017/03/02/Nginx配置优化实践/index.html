Nginx 配置优化实践

Nginx 的配置文件很短，默认值却几乎处处保守：连接数按单机千级估、超时按分钟计、到上游的连接默认不复用、后端故障只在被动重试时才暴露。本文从一次活动页 502 与 504 交替的故障出发，沿着进程模型、事件模型、配置分层、upstream、超时、缓冲、连接复用、静态资源、日志、限流、HTTPS 与容器化部署逐层展开，说明每个指令到底在解决什么问题、默认值为什么常常不够、改动它会付出什么代价。适合已经能维护一份站点配置、但还没有系统整理过默认值取舍的读者。读完之后，应当能独立完成一次反向代理层的容量估算与超时梳理。

故障现场：502 与 504 交替出现

三月的一个周五晚上八点，活动页准时挂到首页入口。流量在十分钟内从每分钟两百次请求涨到接近三千，随后监控开始抖动：一部分用户看到 502，另一部分人等到三十秒后收到 504，两种错误交替出现，比例大概三七开。值班的同事先看 CPU，四台后端机器的负载都在三成上下，内存平稳，磁盘没有明显写入；再看 Nginx 的 error.log，满屏是两类记录，一类是 upstream timed out (110: Connection timed out) while connecting to upstream，另一类是 upstream timed out (110: Connection timed out) while reading response header from upstream。

这两行日志看着相似，含义差得很远。connecting 阶段的超时是 TCP 握手就没建起来，多半意味着后端 accept 队列满了、进程卡死、或者机器已经不可达；reading response header 阶段的超时是连接建好了、请求也发出去了，但迟迟等不到第一个字节，通常是后端业务慢，或者它自己的下游慢。Nginx 对前者的反应是立刻换一台（如果配置允许），对后者的反应只有等，等到 proxy_read_timeout 耗尽再放弃，然后给客户端一个 504。

CPU 不高恰恰是最重要的线索：瓶颈不在计算，而在等待。反向代理进程的绝大部分时间都花在等 socket 可读可写上，真正吃 CPU 的只有协议解析和内存拷贝。一台四核机器扛着几千并发而 CPU 只有三成，说明它并不是算不动，而是被连接数、文件描述符或者单条连接的存活时间卡住了。

事后复盘，问题由三件事叠加而成。worker_connections 还是默认的 1024，前端 keepalive_timeout 又是默认的 75 秒，大量空闲连接长期占着额度；upstream 里有一台后端因为一条没走索引的查询而变慢，四分之一请求打过去就卡住；proxy_read_timeout 保持默认的 60 秒，客户端等不及先断开再重试，把入口流量又放大了一轮。三者单独看都不致命，叠在一起就成了 502 与 504 交替的场面。

本文不打算给一份抄了就能用的万能配置。更有用的是理解每个指令背后的机制，知道默认值从哪里来、改动它会牵动什么。下面的顺序基本就是那次排查的顺序：先看容量，再看等待，最后抠细节。

进程模型与事件模型

一个 master，多个 worker

Nginx 启动之后通常是一个 master 进程加若干个 worker 进程。master 不处理请求，它负责读配置、绑定端口、fork 出 worker，并在收到信号时完成平滑升级和日志重开；worker 才是真正 accept 连接、读写数据、与上游通信的进程。这个划分带来两个直接好处：worker 之间不共享连接状态，不需要为每条连接加锁；master 可以用很小的代价完成换一批 worker 这种操作，这正是 nginx -s reload 能平滑生效的基础。

worker_processes 早期要手工填成 CPU 核数，1.3.8 之后支持 auto，按可用核心数自动设置。2017 年一线在用的 1.10 与 1.12 都支持这个写法，没有理由再写死数字。要注意 auto 读的是进程可见的 CPU 数：容器里如果只限制了 cpu quota 而没有限制 cpuset，auto 可能按宿主机核数起进程，几十个 worker 抢几个核的时间片，上下文切换反而把延迟抬上去。这种情况下显式写数字更稳妥。

worker_connections 与真正的并发上限

worker_connections 默认 1024，含义是单个 worker 能同时打开的最大连接数。注意它统计的是连接，不是请求。HTTP/1.1 的 keepalive 让一条连接可以承载多个请求，所以连接上限和 QPS 不是一回事：连接数看的是并发驻留，QPS 看的是周转速度。两者之间差着一个复用系数，而复用系数又取决于 keepalive_timeout。

关键在反向代理场景下，一条客户端连接往往对应一条到上游的连接。浏览器连 Nginx 占一个描述符，Nginx 连后端再占一个，两个都记在同一个 worker 的额度上。于是理论最大并发客户端数约等于 worker_processes 乘以 worker_connections 再除以二。四核、默认 1024 的情况下是 4 × 1024 ÷ 2 = 2048，再扣掉监听套接字、日志文件、临时文件，以及 upstream keepalive 池里闲置的那些连接，实际可用还要更低。

这解释了那次故障为什么在三千并发附近塌掉。额度用尽时，error.log 里会出现 worker_connections are not enough 这类 emerg 级别记录，新连接直接被拒，客户端看到的就是连接被重置或者 502。调大这个值必须配合系统层：worker_rlimit_nofile 要放开，systemd 单元里的 LimitNOFILE 也要放开，否则 Nginx 自己调大了额度，内核那边的文件描述符上限还是会先撞墙。

比较稳妥的一组值是 worker_connections 4096 到 10240、worker_rlimit_nofile 与 LimitNOFILE 都设 65535，然后在压测里观察 established 连接数与 worker 的占用是否接近上限。不要一上来就填 65535，那只是把连接堆积的错误推迟到内存耗尽的那一刻。

epoll 与反向代理的契合

每个 worker 是单线程的，内部跑一个事件循环。它把所有关心的 socket 注册给内核，内核在某个 socket 就绪时通知它这个可以读了，worker 再去读，读完继续等。Linux 上的这套机制就是 epoll。select 与 poll 每次调用都要把整个描述符集合从用户态拷进内核、再线性扫一遍，连接数上千之后这部分开销就无法忽略；epoll 只在注册和就绪时做工作，代价跟活跃连接数相关，而不是跟总连接数相关。

use epoll 在老配置里很常见。Nginx 会按平台自动选择事件模型，Linux 2.6 以后默认就是 epoll，写与不写效果一样；保留它的意义主要是让读配置的人知道这台机器依赖什么。真正需要留意的是另一面：单线程事件循环意味着任何一个阻塞调用都会卡住整个 worker 上的所有连接。

反向代理恰好是 IO 密集型工作，worker 的时间几乎都花在等客户端发数据、等上游返响应上，几乎不做计算。事件驱动模型把等待从占用线程变成注册回调，一台四核机器挂住上万条连接而 CPU 仍然很低，是这个模型的常态而不是异常。这与开篇的现象互为印证：CPU 低不能当成健康指标，判断它是否健康要看连接数、等待时间和错误率。

也正因为如此，在 Nginx 里做重计算是很危险的：一个耗时 100 毫秒的阻塞操作，乘以这条 worker 上并发的上千条连接，就是把整体延迟抬高一个数量级。同步访问数据库、调用阻塞模块、写复杂正则都属于这一类；把这些逻辑放到上游，让 Nginx 专心转发更省心。

配置分层与平滑重载

Nginx 的配置是树形的：http 管全局，server 管一个虚拟主机，location 管一类 URI。大多数指令沿着这棵树向下继承，子层不写就用父层的值。真正容易踩的是另一类指令——数组型的，比如 proxy_set_header、add_header、proxy_next_upstream。它们的规则不是逐条合并，而是”子层只要出现一条同名指令，父层的整个数组就被丢弃”。所以在 server 里统一设了三个 proxy_set_header，某个 location 里为了加一个 X-Real-IP 又写了一条，父层那三个就全没了，上游收到的 Host 会变成默认值。遇到这种诡异现象，先数一数同名指令出现在几层。

组织站点配置靠 include。主配置里留一行 include /etc/nginx/conf.d/*.conf;，每个站点一个文件，upstream 定义单独放一个文件，改哪个站点只动哪个文件。关键是不要在 nginx.conf 里直接写业务。

改完先跑 nginx -t。它检查语法、指令合法性、证书与 include 文件是否可读，不检查上游是否活着，也不检查端口是否被占用。检查通过再 nginx -s reload。reload 的实质是给 master 发 HUP：master 用新配置起一批新 worker，新 worker 开始 accept，老 worker 停止 accept 并把手上的连接处理完再退出。整个过程不丢连接，但也不是瞬间完成：正在下载大文件、正挂着长轮询的老 worker 会一直活到请求结束，进程列表里会同时出现两代 worker。发布后看一眼老进程是否退干净，是判断”这次 reload 是否真的平滑”的简单办法。

还有一个容易被忽略的副作用：upstream 的 keepalive 连接池属于 worker，换代时整池丢弃，新 worker 要用全新的 TCP 连接去连后端。如果平时靠长连接省掉了握手，reload 那一刻会出现一次握手与 TLS 开销的尖峰，后端连接数也会跳一下。所以在高流量时段做 reload，最好一台一台摘流量再做，而不是四台一起。

upstream：调度、重试与健康检查的边界

upstream 块里默认的调度是轮询，请求按顺序分给每台后端，不考虑谁快谁慢。least_conn 改成”连接数最少者优先”，对响应时间差异大的服务更友好，因为它把新请求给当前最闲的那台，而不是机械地轮流。ip_hash 按客户端地址做哈希，同一来源固定落到同一台，用来在没有集中式 session 存储时维持会话；代价是扩缩容时哈希环整体位移，大量会话失效，而且 NAT 后面的用户会被压到同一台上。这两条都是 2017 年最常用的选择，一致性哈希要商业版，不在讨论范围。

失败判定是这套机制里最需要说清楚的部分。max_fails 默认 1，fail_timeout 默认 10 秒，意思是 fail_timeout 窗口内失败达到 max_fails 次，这台就被标记为不可用，接下来 fail_timeout 时间里不再分给它，时间到了再放一个请求过去试探（有的版本是半开式的单请求试探）。max_fails=0 表示关闭这套被动判定，任何失败都不摘除。把 max_fails 设成 3、fail_timeout 设成 15 秒，比默认值更适合真实后端：默认值太敏感，一次网络抖动就能把一台健康机器摘掉十秒。

proxy_next_upstream 决定哪些失败值得换一台重试，默认是 error 和 timeout。error 包括建连失败、后端直接断连，timeout 包括连接、读、写三个阶段的超时。很多人会加上 http_502 与 http_504，让后端自己返回的错误也触发重试；这在读多写少的接口上能提高成功率，但在写接口上很危险。Nginx 默认不重试非幂等请求，除非你显式写了 non_idempotent；一旦写了，一个已经落库的 POST 可能被执行两次。配合 proxy_next_upstream_tries 限制重试次数也很重要，否则四台机器全慢的时候，一个请求要耗掉四倍超时时间才返回。

这里必须写明一个边界：开源版 Nginx 没有主动健康检查。它不会定期去请求后端的某个探针地址，只能靠真实请求的失败来计数，再用 fail_timeout 到期后的试探来恢复。所谓”半死”的机器——端口还在、能建连、但业务线程池已经打满、响应要几十秒——只能等 proxy_read_timeout 耗尽才被算作一次失败。这就是开篇那次故障里 504 特别多的原因：坏掉的那台不是拒绝连接，而是慢慢不回，Nginx 每打到它一次就要等满 60 秒，客户端往往先于 Nginx 放弃。

把超时压到业务能接受的长度，比加更多重试更有效。一个 5 秒就放弃的请求，用户最多等 5 秒；一个 60 秒才放弃的请求，用户早就刷新了三次，而每次刷新都在后端多留一份负载。

超时、缓冲与请求体

五个时间各管一段

Nginx 的超时指令不少，默认值大多在 60 秒上下，看起来”很宽容”，实际是把故障的暴露时间拖长。它们各自管的是不同阶段，混着调往往越调越乱。

proxy_connect_timeout 管的是与上游建立 TCP 连接的时间，默认 60 秒。这个值几乎没有理由设大：内网建连正常在毫秒级，超过 3 秒基本可以判定对方有问题，继续等只是让客户端多挂 57 秒。它不包括 DNS 解析——upstream 里的地址在启动或 reload 时就解析好了，这一点在容器场景里会变成大问题，后面单独说。

proxy_read_timeout 管的是两次成功读之间的最大间隔，默认 60 秒，不是整个请求的总时长。这是最常被误解的一条：后端每吐一点数据，计时器就重置一次，所以一个持续输出二十分钟的流式接口不会因为它而断，而一个卡住不动的接口会在 60 秒时被切断。理解了”间隔”二字，就知道调成 300 秒并不能让慢接口变快，只是陪着一起等。

proxy_send_timeout 管的是向上游发送请求时两次写之间的间隔，默认 60 秒。请求体很大而客户端上传很慢时，这个值才有意义；普通的 JSON 请求几毫秒就发完了，它几乎不会触发。

client_body_timeout 与 client_header_timeout 管的是读客户端这一侧：前者是读请求体的间隔，后者是读完请求头的时限，默认都是 60 秒。它们是慢速攻击（slowloris）的防线之一，反过来也别为了”让用户慢慢传”把它调到几百秒。

keepalive_timeout 是另一类东西，默认 75 秒，控制客户端空闲连接还能保留多久。它不产生错误，只占用额度：一条空闲连接在 75 秒内仍然算在 worker_connections 里。前端是浏览器时，15 到 30 秒通常够用；前端是另一层代理或负载均衡时，两层的 keepalive 要错开，否则一方刚关、另一方正好发请求，就会出现偶发的连接重置。

这组数字背后是一条简单的账：单条请求占用连接的时长约等于建连、后端处理、传输三者之和，而 keepalive 让空闲连接也占额度。把 read_timeout 从 60 秒降到 15 秒，等于把最坏情况下的连接占用时间压到四分之一，同样的 worker_connections 能撑住四倍的并发。这不是靠调大参数换性能，而是靠尽早放弃换容量。

缓冲与临时文件

proxy_buffering 默认开启。开启后 Nginx 会尽快把上游的响应读进自己的缓冲区，读满或者读完就释放上游连接，再按客户端的消费速度慢慢发。好处是上游连接被快速归还，keepalive 池的复用率显著提高；坏处是响应被完整缓冲，客户端要等更久才看到第一个字节，而且大响应会落到磁盘。

需要关掉缓冲的场景很明确：服务端推送、长轮询、以及后端自己就在做流式输出的接口。这类响应如果被缓冲，客户端会一直收不到数据，直到缓冲区满或者请求结束。关掉有两种方式：location 里写 proxy_buffering off;，或让后端在响应头里带 X-Accel-Buffering: no，后者更灵活，哪些接口流式由业务决定。

缓冲区本身有三个参数。proxy_buffer_size 存响应头，默认 4k 或 8k，它不参与 proxy_buffers 的数量分配，是单独的一块。响应头特别大时——塞了很多 Cookie、带了很长的 JWT、或者上游回了一堆自定义头——会报 upstream sent too big header while reading response header from upstream，客户端看到的是 502，很容易被误判成后端崩溃。遇到过这种情况，先把这个值调到 16k 再排查别的。proxy_buffers 是响应体的缓冲，默认 8 个 4k 或 8k；proxy_busy_buffers_size 限制”正在往客户端发”的那部分缓冲上限，一般是单个 buffer 的两倍。

响应超过缓冲区总容量后，多出来的部分会写进临时文件。proxy_max_temp_file_size 默认 1024m，一个 800m 的下载会先在磁盘上落一份；磁盘慢时这个环节就是新瓶颈，临时目录和系统盘同分区时写满会影响整台机器。把 proxy_temp_path 指到独立分区，或对大文件下载把 proxy_max_temp_file_size 设为 0 并关闭缓冲让它直通，更常见。

请求体大小

请求体这一侧最典型的坑是 client_max_body_size，默认 1m。超过就直接返回 413，请求根本不会到达上游，所以后端日志里什么都没有，只有 Nginx 的 access.log 里一个 413。上传功能上线前必须显式调大，同时留意 client_body_buffer_size：请求体小于它时留在内存，大于它时写 client_body_temp_path。把这两个临时目录放到容量充足的分区，比事后清理 /var 更省事。

连接复用与静态资源

到上游的连接默认是不复用的，这一点很多人不知道。原因是 Nginx 对上游默认使用 HTTP/1.0（proxy_http_version 默认 1.0），每次请求结束就关连接；即使你把版本改成 1.1，Nginx 仍然会把客户端发来的 Connection 头原样转给上游，浏览器发的是 keep-alive，看着没问题，但中间某一层如果发了 close，上游就会照做。所以复用需要三个条件同时成立：upstream 块里写 keepalive 64，location 里写 proxy_http_version 1.1，再用 proxy_set_header Connection “”; 把这个头清空。三条缺一条，连接池就是空的。

复用带来的收益在内网高 QPS 下非常直观：TIME_WAIT 数量下降一个量级，后端不用为每个请求做一次 accept，TCP 慢启动也被省掉。代价是连接寿命变长，后端重启时这些连接变成死连接，第一个打上去的请求会失败一次，再被 proxy_next_upstream 重试掉。

静态资源是另一套参数。sendfile on 让内核直接把文件内容送进 socket，省掉用户态的两次拷贝；tcp_nopush on 配合 sendfile，把响应头和文件开头凑成一个完整的包再发，减少小包数量；tcp_nodelay on 则相反，它让最后一个不满的包立即发出，不再等。open_file_cache 缓存文件描述符和元信息，max=10000 inactive=30s 是常见起点，配上 open_file_cache_valid 60s 与 open_file_cache_min_uses 2；文件更新频繁的目录不要开太久，否则会拿到旧的 Content-Length。

压缩要看文件类型。文本类（HTML、CSS、JS、JSON）压缩比高，值得开；图片、视频、字体本身就是压缩格式，再 gzip 一遍几乎不减小体积，只多花 CPU。gzip_comp_level 5 是性价比拐点，再往上收益很小。如果构建时已经生成了 .gz 文件，用 gzip_static on 直接发，连压缩的 CPU 都省了。缓存头交给 expires 30d 处理，但 HTML 入口文件不要跟着长缓存，否则发版后用户还拿着旧页面去请求已经被删掉的哈希文件名。

日志、限流与 HTTPS

access_log 默认是每条请求写一次，高 QPS 下这几行 write 会实打实占掉一部分 CPU。加上 buffer=32k flush=5s，日志先攒在内存里再批量落盘，代价是进程被强杀时最多丢 5 秒的记录。log_format 里除了常规字段，一定要加 $request_time、$upstream_response_time、$upstream_addr 与 $upstream_status。这四个字段决定了你能不能把”慢”定位到 Nginx 还是后端，后面排查一节还会用到。

日志切割不要 restart。把文件 mv 走之后给 master 发 USR1，它会重新打开日志文件，worker 随之切换，正在处理的请求不受影响。logrotate 的 postrotate 里写 kill -USR1 $(cat /var/run/nginx.pid) 就够了，配 create 保持权限，别用 copytruncate——那会让 Nginx 继续往被截断的旧 inode 里写。

限流有两个维度。limit_req 按速率限，本质是漏桶：rate=10r/s 表示匀速放行，burst=20 是桶的容量，超出的请求要么排队要么直接 503。加 nodelay 后桶内请求立即处理、不排队，对延迟敏感接口更重要，因为排队本身就在占连接。limit_conn 按并发连接数限，适合防单个客户端开几百条连接拖垮下载服务，配 limit_conn_zone $binary_remote_addr zone=perip:10m 使用。key 用 $binary_remote_addr 而不是 $remote_addr，前者是 4 字节的二进制，同样 10m 共享内存能装的地址多得多。

限流最容易出的问题是误伤。公司出口、运营商 NAT、移动基站后面的用户共用一个公网地址，按 IP 限 10r/s，整个办公室一起用就会集体 503。可行的缓解是按 URI 分组限流、把 burst 放大到能容纳正常突发，以及给内部网段做白名单：用 geo 判断来源，命中白名单时把 key 映射成空串，key 为空的请求不计入限流。

HTTPS 部分，证书链是最常见的坑。ssl_certificate 要指向包含中间证书的完整链文件，只放叶子证书时，桌面浏览器往往能靠 AIA 自动补全，而旧版 Android 和 Java 客户端会直接握手失败，表现为”部分用户打不开”。协议版本按 2017 年的现实，关掉 SSLv3，保留 TLSv1 到 TLSv1.2 的过渡，同时把 ssl_session_cache shared:SSL:10m 打开，10m 大约能放四万个会话，握手开销能降一大截。HTTP/2 在较新的 Nginx 上已经支持（1.9.5 起提供，1.10 之后进入稳定分支），但 2017 年我们只在小流量域名上评估，主干链路仍跑 HTTP/1.1，因为上游、监控和压测工具都还没跟上。

容器里的 Nginx 与线上排查

动态解析：resolver 与变量化 proxy_pass

把 Nginx 放进容器、反向代理同网络里的其他容器，会撞上一个物理机上不存在的问题：地址是会变的。Docker 自带的 DNS 在 127.0.0.11，自定义网络里的容器名能解析成容器 IP，但 upstream 块里的 server api:8080 只在启动或 reload 时解析一次。后端容器重启换了地址，Nginx 仍往旧地址建连，客户端看到 502，不 reload 就永远好不了。

让解析发生在运行时的办法是把地址放进变量。proxy_pass http://$backend; 这样的写法会让 Nginx 在每个请求上重新查一次名字，配合 resolver 127.0.0.11 valid=10s ipv6=off; 就能在十秒内跟上地址变化。代价有两个，都必须提前知道：变量化之后如果地址后面还带 URI（比如 proxy_pass http://$backend/;），Nginx 无法再替你拼接 location 匹配后剩下的路径，必须自己写 $uri 或 $request_uri，否则请求会打到根路径，这是最常见的 404 来源；变量化之后也用不了 upstream 块的负载均衡与 keepalive，等于用动态解析换掉了连接复用。

所以更常见的折中是：稳定服务用 upstream 加服务名，接受”重启后 reload 一次”；只有地址频繁变动的边缘服务才用变量。启动顺序也要考虑，depends_on 只保证容器先启动，不保证能接受请求，Nginx 起来时上游还没 ready 的几百毫秒里，靠 max_fails 与重试撑过去。

三个数字的差值

stub_status 是最轻的观测手段，在本地 location 里打开并限制来源，就能看到 Active connections、accepts、handled、requests 以及 Reading、Writing、Waiting 三个状态。Waiting 高说明空闲的 keepalive 连接多，不是故障；Writing 高说明正在往慢客户端写数据。日志级别平时保持 warn 就够，排查时临时调到 info，不要长期开 debug，那既写满磁盘，也让 worker 把时间花在格式化日志上。

真正定位问题靠两个耗时字段的差值。$request_time 是从读到客户端第一个字节到把响应发完的总时长，$upstream_response_time 是从连上后端到收完后端响应的时间。前者大、后者小，说明时间花在客户端网络、排队或者缓冲落盘上；两者都大，说明后端本身慢；后者是短横线，说明这个请求根本没走 upstream，要么是静态文件，要么是 Nginx 自己生成的错误页。重试发生时，upstream 时间会是逗号分隔的多个值，几段相加才是真实等待。

小结

Nginx 的默认值是为”能跑起来”设计的，不是为”扛住流量”设计的。容量上先算清 worker_processes 乘 worker_connections 再除以二的账，并同步放开文件描述符；等待上把连接、读、写三个超时压到业务能接受的长度，让失败尽早暴露；链路上打开 upstream 的 keepalive，用三个开关换掉重复握手；观测上让日志带上两个耗时字段，用它们的差值区分是客户端慢、Nginx 慢还是后端慢。至于限流、HTTPS 与容器里的动态解析，都是在这些基础之上按场景加的补丁，加之前先想清楚它会误伤谁、会牺牲什么。
