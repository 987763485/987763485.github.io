Go 错误处理哲学与实践

那段代码是一条很普通的分层调用链：HTTP handler 调 service，service 调 repository，repository 再调第三方的支付客户端。每一层都写了 if err != nil { return err }，也每一层都顺手打了一行日志。结果是一次失败在日志里留下四行一模一样的 “something went wrong”，却没有一行说清楚是哪一层、哪个订单、哪个参数出的问题。最后只能靠时间戳把几条日志拼起来，再去翻代码猜。

后来我把项目里所有 something went wrong 都改掉了。改的过程发现，问题不在于日志写得少，而在于错误向上传递时被剥掉了全部上下文：谁调的、操作什么对象、底层原因是什么，这些在每一层 return err 时就已经丢了，日志只是把”丢信息”这件事重复了四遍。

Go 的错误处理经常被吐槽啰嗦，但它有一套朴素的设计：错误是值，由调用者显式检查，向上传递时由人决定加什么信息、在哪里记录、要不要转换。用得好不好，直接决定线上问题是五分钟定位还是五小时。本文按这条线索往下走：先看 error 是什么，再看几种表达手段，最后讨论记录、边界与测试上的取舍。读者能读懂基本 Go 代码即可。

error 是一个接口

Go 标准库里对错误的定义只有两行：

任何类型，只要实现了 Error() string，就满足 error。标准库里的 errors.New 返回的是一个内部结构体指针，fmt.Errorf 格式化之后返回的也是一个只带消息的错误值。也就是说，绝大多数时候我们手里的 error 就是一个字符串的包装，别无其他。

这个定义解释了很多事。第一，错误可以像普通值一样赋值、返回、塞进结构体字段、放进切片，不需要语言层面的特殊支持。第二，检查错误就是一次普通的 if，控制流是看得见的：读代码的人从上往下扫一遍，就知道哪一步可能失败、失败之后走哪条路。

Go 不用异常，原因也在这里。异常把控制流藏进了类型系统之外，一个函数调用可能直接跳到几百行之外的 catch，中间经历了哪些清理、哪些状态变化，得靠人去推。Go 的选择是把失败写进返回值，让调用者当场做决定：是重试、是降级、是包装后继续往上扔，还是干脆记一笔日志继续跑。代价是满屏的 if err != nil，收益是每一个失败点都有一个明确的责任人。

这跟 JavaScript 的 try/catch 是两种思路：JS 里抛出去的东西可以不是 Error，调用方也看不出函数会抛什么；Go 把失败摊开在返回值上。Go 的啰嗦是设计出来的，不是缺陷。

有一处细节值得记住：error 是接口，所以 err == nil 判断的是接口本身是否为空，而不是它里面装的值是否为空。这个坑在自定义错误类型那节会具体说。

哨兵错误：用包级变量表达”是不是这一种情况”

标准库里有几个错误值你一定见过：io.EOF、sql.ErrNoRows、context.Canceled。它们的用法是先定义成一个包级变量，再由调用方用 == 比较：

这类错误常被叫作哨兵错误（sentinel error），只回答”是不是这一种情况”。读文件读到结尾不是故障，而是一个需要被识别的正常状态；查询没命中一行也一样，调用方通常要把它转成自己的”不存在”语义。

要理解哨兵错误，先得区分 errors.New 和 fmt.Errorf。两者在 2017 年的标准库里能力差不多，都只产出一个带消息的错误值，区别在于消息是固定的还是拼出来的：

errors.New 每次调用也会返回新指针，所以能拿来比较的前提是”只调用一次，把结果存进包级变量”。fmt.Errorf 生成的消息里带了变量，天生不适合比较，它的定位是给人看的上下文。

这带来哨兵错误的两个局限。一是它不能携带数据，调用方只能知道”是哪一种”，拿不到订单号、重试次数这类细节。二是它跨层传递时很脆弱：中间任何一层用 fmt.Errorf 重新拼一次消息，== 就失效了，原始的哨兵值被埋在字符串里再也取不出来。所以用哨兵错误要守一条规矩：要么原样返回，要么用后面讲的包装方式保留原因，不要随手重新格式化。

自定义错误类型：让错误带上数据

当调用方不只需要知道”是哪一类”，还需要拿到 code、字段名、冲突的订单号时，就该定义结构体了。做法很直接：结构体实现 Error()，需要判断时用类型断言取详情。

Error() 里只拼人类可读的信息，结构化字段留在结构体上：日志打全量字段，HTTP 层按 Code 映射状态码，都不需要解析字符串。返回多种错误时，type switch 比连续断言清爽：

包装：让每一层的上下文留下来

2017 年的标准库还没有官方的错误包装机制，社区里的事实做法是第三方库 github.com/pkg/errors（用 glide、dep 这类工具拉进 vendor 目录）。它提供三件事：Wrap 加一层消息并记录调用栈，WithStack 只记栈不改消息，Cause 一路剥到最底层的原始错误。

包装后的消息是一条从外到内的路径：load order for pay: find order 20170326001: sql: no rows in result set，配合 %+v 还能打出调用栈，读起来等于顺着调用链走了一遍。要注意 Cause 只剥实现了 Cause() error 的包装，中间混进一个只拼字符串的错误，链条就断了。

不想引第三方也可以自己写十几行：定义一个只要求 Cause() error 的接口，包装类型同时实现 Error() 和 Cause()，取值时循环剥。原则只有一条：每一层只补”这一层才知道的信息”，比如操作名和业务主键，不要把下层说过的话重抄一遍。

错误信息、日志与只处理一次

错误消息有几条约定俗成的规则：小写开头，结尾不加标点，因为它经常被拼进更长的句子里；把关键参数写进去，让人不用打开代码就能复现；不要写 “failed to” 这种不增加信息的空话。

这条消息交代了动作、对象和原因，顺序是从具体到根本，读起来像一句正常的话。反过来，fmt.Errorf("failed: %v", err) 除了多一层壳什么都没加，不如直接返回原错误。

敏感信息绝对不能进消息：密码、token、完整手机号、SQL 里的明文参数。日志会被采集、转发、长期归档，一条带 token 的错误消息等于一次泄露。确实需要定位的，只留长度或哈希前缀。

日志这一侧，当年团队里普遍用 logrus 一类库打结构化字段。错误对象应该作为一个字段传进去，不要提前拼进消息：

request_id 在入口处生成，放进 context 一路传下去，这样一次请求跨多个服务、多条日志也能串起来。错误码与用户提示的映射放在边界层做：内部错误记全量细节，返回给用户的是一句稳定的话加一个可查询的错误码。把 sql: no rows in result set 直接吐到页面上，既看不懂，也等于把实现细节告诉了外面。

日志这一侧还有个更隐蔽的问题：开头那个例子里，同一个错误被”处理”了四遍。每层打日志再返回，看起来尽责，实际让日志失去定位能力——四条记录说同一件事，谁也不知道哪条是源头。

约定可以简化成一句话：错误要么被处理，要么被传递，二者只做一次。处理意味着有人做了决定，比如记录日志并降级、转换成另一种错误、给用户返回提示；传递意味着原样或包装后交给上层。中间层通常只做后者，因为它既不知道全貌，也没有权力决定怎么办。

panic、recover 与 goroutine 的边界

panic 不是异常机制的替代品，它表达的是”程序进入了不该进入的状态”。适合的场景很有限：启动时配置非法，与其带着错配置跑下去，不如在 main 里直接崩掉；switch 的 default 表示逻辑上不可能到达；依赖注入时必需的对象为 nil。它们都是编程错误，越早暴露越好。

业务失败不该用 panic。订单已关闭、余额不足、参数校验不通过，都是预期内的分支，调用方有能力处理，把它们变成 panic 只会逼着每一层都写 recover。

测试错误

表驱动测试里判定错误只有两种可靠方式：比值、比类型。哨兵错误用 ==，自定义错误断言后检查关键字段。不要比较完整的消息字符串，消息是给人的，改一个标点测试就红了；除非那句话本身就是契约，比如会直接展示给用户的提示。

这段能成立，前提是 errors.New 的结果只创建一次并存进包级变量，两边比的是同一个指针。被测代码如果用 fmt.Errorf 重新生成一句同样的话，== 立刻失败——这正是生产代码里该用哨兵值的地方。至于失败路径，靠接口注入一个永远返回指定错误的 stub 就够了，不必连数据库，也不必改全局变量。

反模式与场景对照

几个反复见到的写法值得单独点出来。忽略错误用 _ = f()，只有关闭文件、刷日志这类”失败了也无能为力”的调用才勉强可以，而且要写注释说明理由，其余一律处理。把 err.Error() 存进数据库或结构体字段，等于把错误降级成文本，之后既不能比较也不能取字段。在 defer 里直接给具名返回值赋值，会覆盖函数真正的错误：

正确写法是先判断：if e := tx.Rollback(); e != nil && err == nil { err = e }。除此之外，每层都打日志、用 panic 做业务分支、把内部错误原文返回给用户，也都是常见坑。

场景 做法 反模式
只需判断种类 包级哨兵值加 == 比较错误字符串
需要带 code 与字段 结构体实现 Error()，断言取字段 把信息拼进消息再解析
跨层传递 包装补上下文，边界处剥到根因 每层重新拼一遍消息
记录日志 只在 handler、main、goroutine 顶部记 每层 log 完再 return
可以降级 记一条 warn，走备用逻辑 直接返回 500
编程错误 panic，中间件与 goroutine 各自 recover 用 error 层层上传
写测试 比哨兵值、断言类型、注入 stub 比完整消息文本

小结

Go 的错误处理没有魔法，全部靠三个决定：错误用什么类型表达、向上传递时补什么上下文、在哪一层做处理。哨兵值负责回答”是不是这一种”，自定义类型负责携带数据，包装负责保留链路，三者可以叠在一起用。日志只该出现在知道业务全貌的边界上，中间层只管把信息补进错误里往上交。至于 panic，留给它该待的地方：程序真的不该继续跑的时候。
