Linux 网络诊断工具详解

线上服务”有时能连、有时超时”，是最折磨人的一类故障。同一份代码同一份配置，从办公网访问十次成功七次，换一台机器又全部正常。第一反应往往是”网络不好”，于是换端口、改防火墙、调超时时间，几轮下来现象没变，线索倒被覆盖掉了。本文讲一个笨办法：先确认问题发生在哪一层，再决定看什么。适合能跑命令、但面对一堆网络工具不知道先用哪个的读者。

为什么先分层，而不是先换配置

一次请求要经过一串相对独立的环节：解析域名、查路由、送到目标网卡、进程监听端口、TCP 握手，最后才是应用层收发数据。任何一环出问题，用户看到的都是同一句”连不上”。

难点就在这里：现象同构，原因却分散在五层。一开始就动配置，等于在未知变量里随机挑一个改，改对了是运气，改错了还会让”哪次改动起了作用”变得无从判断。分层排查把过程变成收敛：每层只回答一个是非题，先把范围压到一层，再在这一层深挖。下面的流程是笔者现在习惯的路径，逐层排除。

flowchart TD
    A[现象：连接超时或失败] --> B{DNS 能解析出地址吗}
    B -- 否 --> B1[查 resolv.conf 与 nsswitch]
    B -- 是 --> C{路由能到达目标网段吗}
    C -- 否 --> C1[查 ip route 与网关 ARP]
    C -- 是 --> D{端口有进程监听吗}
    D -- 否 --> D1[查 ss 监听与进程存活]
    D -- 是 --> E{TCP 握手能完成吗}
    E -- 否 --> E1[抓包看 SYN 与 RST]
    E -- 是 --> F[问题在应用层]

每一层都有对应的主力工具：DNS 用 dig，路由用 ip route 与 mtr，端口用 ss，握手用 tcpdump，应用层用 curl。记住这个顺序比记住几十个参数有用。

分层不是为了把流程变僵。真实故障常有两层同时出问题，笔者的做法是每层只做一次最小验证并记录结果，五层过完再回头看哪份证据最可疑。动手前先花两分钟问清现象，能省掉一半工作：所有请求都失败还是间歇失败，只有这台客户端失败还是全部失败，失败时立刻报错还是卡住再超时。立刻返回 connection refused，说明包到了目标但端口没开或被明确拒绝；卡住几十秒才超时，说明包很可能没到，或者回来的路上被丢了。仅这一条，就能把范围砍掉一半。

连通性：ping、traceroute 与端口探测

第一步通常是 ping。它发 ICMP Echo Request，收到 Reply 就说明目标地址在网络层可达。默认会一直发下去，故障时要指定次数与超时。

ping 通只说明地址在网络层活着，不代表服务可用；ping 不通更不能判定网络断了，很多环境在防火墙或内核参数里禁掉了 ICMP。判断”禁 ping”的间接办法是用 TCP 探测已知端口：端口能通而 ping 不通，基本可确认是 ICMP 被拦。

nc -vz 的输出很适合写进脚本，但要分清 refused 与 timed out：refused 是对方回了 RST，网络通、端口没开；timed out 是没有任何回应，通常是中间设备丢包或目标不可达。

路径问题看 traceroute，它靠逐跳增加 TTL、让路由器回 ICMP Time Exceeded 拼出路径。默认走 UDP，很多网络不友好，加 -I 换 ICMP 或 -T 换 TCP 成功率更高。一次性的 traceroute 看不出”偶发”，判断间歇丢包要用 mtr，它持续统计每一跳的丢包率与延迟。

读 mtr 有个陷阱：某一跳丢包率高、但它后面所有跳都正常，通常不是真丢包，而是那台路由器对探测包限速，转发数据时并不丢。只有丢包从某一跳一直延续到最后一跳，才说明问题在那一段，否则很容易把责任推给一台无辜的设备。

DNS：解析慢和解析错是两件事

DNS 的问题分两类：解析结果是错的，或者解析本身很慢。前者表现为连到了错误的地址，后者表现为每次新建连接都先卡一两秒，两者要用不同的证据区分。

日常用得最多的是 dig，它直接构造查询报文，输出能看到状态码、应答条数和耗时。host 是它的简写版；nslookup 更老、输出格式不统一，脚本里不好解析，笔者只在没有 dig 的机器上才用它。

+trace 绕过本机的递归服务器，自己从根开始逐级问下去，因此能回答普通查询回答不了的问题：是权威服务器给错了记录，还是本地递归缓存了旧记录。两者不一致，问题就在本地递归这一侧。

解析顺序由两个文件决定。/etc/resolv.conf 里是 nameserver 列表和 options，注意 timeout 与 attempts 的默认值：默认超时 5 秒、重试 2 次，第一个 nameserver 不通时，客户端要等完这一轮才去问第二个，表现出来就是”偶尔卡五秒”。/etc/nsswitch.conf 的 hosts: 一行决定先查本地文件还是先查 DNS，顺序写错会让 /etc/hosts 里的条目失效。

容器里的 DNS 与宿主机不一样，这是最容易忽略的差异。容器通常有自己的 /etc/resolv.conf，由运行时在启动时写入，指向内置的转发服务；容器内的 127.0.0.1 指容器自己，所以在容器里写 nameserver 127.0.0.1 往往解析不出任何东西。search 域和 ndots 还会影响短域名的解析次数：短域名先被拼上 search 域去试，试完才查原名，解析慢有时就是这么来的。

套接字与端口：先确认有没有人在听

DNS 给出地址之后，下一个问题是目标机器的端口上有没有进程在监听。这一层的主力工具是 ss，它直接从内核的套接字表取数据，连接数多时比 netstat 快得多；net-tools 在 CentOS 7 与 Ubuntu 16.04 上已不是默认必装，新机器常常没有这个命令。

ss -lntp 的输出里，Local Address:Port 一列要看清楚绑定地址。0.0.0.0:80 表示监听所有网卡，127.0.0.1:80 表示只监听本机回环，从外部访问必然失败；[::]:80 是 IPv6 的通配地址，在多数系统上同时接受 IPv4 映射连接，但防火墙规则未必一起放行。很多”服务起来了但外部连不上”的案例，最后都落在这一个字符的差别上。

netstat -lntp 与 ss -lntp 参数几乎一一对应，迁移成本很低；lsof -i 则从进程视角反查，适合已知进程名、想知道它占了哪些端口。

连接状态里，TIME_WAIT 和 CLOSE_WAIT 最容易被误读。前者出现在主动关闭连接的一方：它已发完 FIN 并收到对方的 FIN，但还要等 2MSL 才释放，目的是让迟到报文有地方可去、最后的 ACK 能重传。所以 TIME_WAIT 多说明这台机器短连接多、且它是主动关闭方，属正常现象，只是端口会被占一段时间。

CLOSE_WAIT 完全是另一回事：它表示本端收到了对方的 FIN，但应用还没有调用 close。这个状态不会自己消失，堆积起来只有一个原因——程序没有正确关闭套接字，常见于异常分支漏了关闭、连接池只借不还。看到大量 CLOSE_WAIT，不要去调内核参数，要去查代码。

抓包：让内核把证据交出来

前面几步只能给出”通或不通”，遇到”有时通有时不通”就要看报文。tcpdump 最直接，-i any 抓所有网卡，-nn 关掉名称解析，避免被 DNS 反向查询拖慢。抓包先把范围收窄，只抓关心的主机和端口，否则高流量机器上输出会瞬间刷满屏幕。

抓到的包适合存下来慢慢看：-w 写 pcap，用 Wireshark 打开可以顺着一条流看完整的请求响应；-r 用来读回已有的 pcap，便于把现场文件带回自己机器分析。

两个现实约束。一是权限：抓包需要 CAP_NET_RAW，只能用 root 或 sudo，这也意味着 pcap 里可能有明文凭据，不能随手丢在共享目录。二是开销：每个包多一次拷贝，-s 0 尤其明显，生产机要配合过滤器与更短的抓取时间；-i any 是伪设备，不支持混杂模式。

HTTP 层：curl 把一次请求拆成几段

链路和端口都通，问题就落在应用层。curl -v 能给出完整现场：解析到哪个地址、连的哪个 IP 和端口、TLS 握手是否完成、回了什么状态码，一眼能看出是打到了错误实例，还是被中间层改写了请求。

只看单次请求不够，慢要慢得有依据。curl -w 可以把一次请求拆成几个阶段分别计时：

time_namelookup 到 time_connect 之间是建连耗时，time_appconnect 是 TLS 握手完成的时间，time_starttransfer 是首字节到达的时间。如果 time_namelookup 占了大头，问题在 DNS；如果首字节很晚而建连很快，问题在服务端处理。

两个参数常被误用。--resolve 可以把某个域名强行指到指定 IP，用来绕过 DNS 验证”换了地址是否就正常”，它只影响本次请求，比改 hosts 干净。-k 只是跳过证书校验，并不加密任何东西，也不能证明对端可信；在排查自签证书时临时用一下可以，写进脚本或生产配置就是把中间人攻击的门留着。至于 wget，它更适合整站抓取、断点续传这类下载场景，诊断能力弱于 curl，笔者一般只在目标机器上只有 wget 时才用它做一次最简单的可达性验证。

路由与转发：包到底从哪张网卡出去

如果包连本机都出不去，要看路由表。ip route 已替代 route -n，default via ... dev eth0 那一行决定默认出口，缺了它的机器只能访问同网段。多网卡机器还要看策略路由，ip rule 决定先查哪张表，ip route get 能直接告诉你某个目标会走哪条路由、用哪个源地址发出，比人肉比对整张表快得多。

NAT 问题看 iptables -t nat -L -n -v，其中 -v 的包计数才是关键：DNAT 规则的计数一直是 0，说明流量根本没走到这条规则；SNAT 计数在涨但回包到不了，通常是出口地址选错。同网段通信失败还要看 ARP 缓存，ip neigh 里出现 FAILED 或 incomplete，表示二层没解析出来，常见原因是地址写错、VLAN 不通或对端并没有开机。

带宽与连接跟踪：慢和丢包是两回事

现象是”慢”而不是”不通”时，要看谁在占带宽。iftop -i eth0 -n 按连接显示实时速率，nethogs 按进程聚合，能直接指出是哪个程序在跑流量。两者都要 root，也只适合短时间观察。

另一类丢包来自连接跟踪表满。做过 NAT 的机器上每个连接都要在 conntrack 表里占一项，conntrack -S 能看到 insert_failed 与 drop 的增长，表满时新连接被直接丢掉，表现就是”老连接正常、新连接全部超时”。把 /proc/sys/net/netfilter/nf_conntrack_count 与同目录的 _max 一比就知道余量；短期可以调大上限，长期还是要查连接为什么没有及时释放。

容器场景：借宿主机的工具进命名空间

容器里的网络故障，从宿主机排查往往比进容器快。nsenter -t <pid> -n 借用目标进程的网络命名空间，之后运行的 ip、ss、tcpdump 都是宿主机的二进制，看到的却是容器内的网卡、路由和套接字。pid 用 docker inspect -f '{{.State.Pid}}' <容器名> 取。

镜像往往很精简，docker exec 进去可能连 ss、ping 都没有，apt-get 又未必能联网。此时要么用宿主机工具配合 nsenter 检查，要么拷一个静态编译的 busybox 进去应急。前者更快，也不会污染镜像。

一个完整的排查案例

现象：某内部接口在办公网访问，十次有两三次超时，重试即可成功，从跳板机访问几乎不复现。

九点十分先 ping，四次全通、延迟稳定，主机是活的；nc -vz 连试十次，三次卡满三秒返回 timed out，其余很快成功，”端口没开”不成立；mtr -r -c 50 显示路径稳定、没有持续丢包，链路也排除。抓包看到失败的那几次只有 SYN、没有 SYN-ACK，重传后才成功，像是建连被拖慢。

十点改用 curl -w，失败请求的 time_namelookup 高达三秒，真正的建连只用了十几毫秒，方向一下清楚了：慢在解析。dig 直查权威服务器毫秒级返回，查本机配置的递归服务器却三次里有两次要等满五秒。

十点半打开 /etc/resolv.conf，第一行是一个已经下线的旧 DNS，第二行才可用。客户端每次都要先等第一个服务器超时、重试，才转向第二个，于是表现为”偶尔卡几秒、重试就好”。删掉失效条目后现象消失。回头看，前面换端口、改防火墙，全是在没有证据时乱动。

症状、工具与要看的东西

症状 先用什么 看什么
域名解析慢 dig、curl -w time_namelookup、resolv.conf 里失效的服务器
完全连不上 ping、nc -vz 是 refused 还是 timed out
偶发超时 mtr、tcpdump 丢包是否延续到最后一跳，有没有 SYN-ACK
服务起了外部不通 ss -lntp 绑定地址是 0.0.0.0 还是 127.0.0.1
连接堆积 ss -ant、conntrack -S CLOSE_WAIT 数量、insert_failed
带宽被占满 iftop、nethogs 哪个连接、哪个进程
容器内异常 nsenter -t <pid> -n 容器自己的路由与 DNS

小结

先分层定位，再在那一层找证据，最后才动配置，改完还能说清是哪一处改动让现象消失。工具不难，难的是忍住”先改一下试试”的冲动。本文只覆盖连通性与抓包，CPU、内存、磁盘的观测不在范围内，另有专文。
