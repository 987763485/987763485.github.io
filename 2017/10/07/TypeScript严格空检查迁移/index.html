TypeScript 严格空检查迁移

本文属于《TypeScript 学习路线》第 9/74 篇
上一篇系列目录下一篇

2017 年，TypeScript 已经是不少前端团队写业务代码的默认选择，但大多数项目只开了 noImplicitAny，strictNullChecks 仍然关着。关闭状态下，null 和 undefined 可以赋给任何类型，编译器给出的类型标注其实在说谎，线上最常见的 Cannot read property 'x' of undefined 就这样漏了过去。本文从一段熟悉的代码出发，讲清楚 strictNullChecks 改了什么、为什么应该单独先开它、存量代码怎么分批迁移，以及在没有可选链的年代如何写出安全的嵌套访问。适合已经会用 TypeScript、正准备给老项目加严格检查的工程师。

问题的麻烦之处不在于难修，而在于难发现。它集中出现在数据边界上：接口返回、缓存读取、DOM 查询、数组查找、配置缺省。这些分支在单元测试里覆盖成本最高，在开发环境里又往往恰好有数据，于是错误被一路带到线上，由真实用户的空缓存触发。

更隐蔽的是数字与布尔值。undefined 参与算术不会抛错，而是安静地得到 NaN，然后 NaN 沿着调用链一路传播，最后在一个完全无关的页面上显示成空白或 0。相比直接崩溃，这种静默错误排查成本更高，也更难写回归测试。

语言层面有两个空值，来源并不相同。undefined 表示“没有值”，是变量声明未赋值、函数未传参、对象没有该属性时的默认结果；null 表示“有值，值就是空”，通常由开发者或后端显式给出。两者都是 falsy，很多存量代码用 if (x) 一把抓，看起来能用，实际把 0、空字符串、false 也一起吞掉了。严格空检查的价值之一，就是逼着我们把这类模糊判断重新写清楚。

TypeScript 从 2.0 起提供 strictNullChecks，但直到 2017 年，大量项目仍然让它保持默认关闭。原因很现实：打开开关，存量代码会瞬间冒出成百上千条错误。本文要讨论的，就是如何把这些错误变成一次可控的工程改造，而不是一次失控的重写。

strictNullChecks 到底改变了什么

首先要明确，strictNullChecks 不是运行时检查。打开它，编译产物不会有任何变化，不会插入判空代码，也不会在访问属性前抛错。它改变的只有一件事：编译器对“哪些值可以赋给哪些类型”的判断。

关闭时，null 和 undefined 是所有类型的合法取值，string 类型的变量可以是 null，number 类型的参数可以是 undefined，类型标注只描述了“正常情况”，对异常情况没有任何约束。开启后，两者各自成为独立类型，只与自身、any 以及显式包含它们的联合类型兼容。具体体现在三个方面。

第一是可赋值性。声明为 string 的变量不能再接收 null 与 undefined，必须写成 string | null 或 string | undefined。这条规则会沿着赋值、返回值、对象字面量一路传播，是绝大多数报错的源头。很多人在迁移第一天就觉得“报错怎么这么多”，原因就是它把过去隐藏在所有类型里的空值一次性翻了出来。

第二是成员访问。当一个值的类型是 User | null 时，直接读取 .name 会被拒绝，因为编译器无法证明它不为空。同理，可选属性 email 的读取类型是 string | undefined，不能直接传给要求 string 的函数。这条规则看起来琐碎，却正好覆盖了线上崩溃最常见的形态。

第三是函数签名。参数类型为 string 的函数不接受 string | undefined 的实参；声明返回 string 的函数也不能在某个分支返回 undefined。这两条让空值沿着调用链显式地传播，而不是在某一层被悄悄吞掉。调用方从此必须面对“可能为空”这个事实，而不是把它留给运行时。

还有一点容易被忽略：标准库的类型声明早就按严格模式写好了。document.getElementById 返回 HTMLElement | null，数组的 find 返回 T | undefined，这些标注一直存在，只是在开关关闭时被忽略。所以打开检查并不需要等第三方声明更新，浏览器 API 这一层立刻就能受益，收益来得比想象中快。

需要强调的是，收窄是路径敏感的。编译器只在当前控制流上相信“这个值不为空”，一旦把它传进回调、或者中间调用了一个可能修改它的函数，之前的结论就可能失效。迁移时最常见的困惑“我明明判断过了，为什么还报错”，多半来自这里。稳妥的做法是在判空之后立刻把值复制到一个新的局部常量，再在回调里使用它，这样编译器和你看到的是同一个值。

null 与 undefined 的语义分工

开启检查之后，团队很快会面对一个具体问题：某个字段“没有值”，到底该标成可选、标成 | null，还是两者都允许。三种写法在类型层面都能表达“可能没有”，但语义不同，混用会让调用方无从判断。

可选属性 email?: string 的含义是“这个属性可能不存在”。读取它得到 string | undefined，但对象本身仍然合法。映射到 JSON 上，就是字段整个缺失。显式联合 email: string | null 的含义是“属性一定存在，值可能是空”，对应 JSON 里的 "email": null。如果后端契约区分这两种情况，类型就应该如实写出来，而不是用可选属性一把概括。

可选参数与默认参数也有类似的区别。参数写成 port?: number 时，调用方可以完全不传；写成 port: number | undefined 时，必须显式传一个 undefined。默认参数只对 undefined 生效，对 null 不生效，这一点在从 JavaScript 迁移时经常踩到：把 null 传进去，函数不会使用默认值，而是拿着 null 继续执行，随后在某个算术或字符串操作里出错。

笔者的建议是定一条团队约定：内部代码统一用 undefined 表示缺失，只在对接后端、数据库或历史接口时保留 null，并在适配层完成转换。理由很实际：一种空值只需要一套判断，两种空值会让每个函数都写成 x !== null && x !== undefined，评审时也很难判断是否漏了一种。约定写进 README 或代码规范，比每个人凭感觉写要可靠得多。

还有一个必须纠正的习惯：用逻辑或提供默认值。value || fallback 在 value 为 0、空字符串、false 时同样会走 fallback，而这三者在业务里都是合法值。开启严格检查后，应该统一改成 value !== undefined ? value : fallback，意图更准确，也不会吞掉合法的假值。这个改动本身与类型无关，但它是空检查迁移里最值得顺手做掉的一批小修。

为什么不直接打开 strict

TypeScript 2.3 引入了 strict 这个聚合开关，它等价于同时打开 noImplicitAny、noImplicitThis、strictNullChecks 和 alwaysStrict。新项目直接写 "strict": true 是最省事的选择，本文并不反对。但对于已经运行两三年的存量项目，一次性全开通常不是好主意。

第一个原因是报错不可归因。一个几万行的项目全开之后，报错列表往往有几千条，其中既有“变量可能为空”，也有“参数缺少类型标注”，还夹杂着 this 的类型问题。它们混在同一个输出里，既无法排优先级，也无法分批交付。团队很快会陷入一种状态：每天修几十条，数字却不见明显下降，因为新写的代码又在制造新的同类错误。

第二个原因更危险：为了尽快让编译通过，开发者会用 any 和断言把错误压下去。这等于把刚打开的检查又关掉了，只是关得更隐蔽。严格空检查真正有价值的部分，是逼着人思考“这个值从哪里来、为空时业务怎么处理”，一旦用断言跳过，思考也就跳过了。三个月后回看，代码里多了一堆 !，线上该崩的地方照崩。

第三个原因与聚合开关本身的性质有关。strict 包含的规则集合会随着编译器版本演进，今天打开的是一组规则，升级之后可能变成更大的一组。存量项目如果一开始就依赖 strict: true，每次升级编译器都要面对一批来源不明的新错误。分项打开则不同，每一项什么时候开、由谁负责修，都是明确的决定。这也是迁移期间应该固定 TypeScript 版本、升级时单独安排一次验证的原因。

所以更稳妥的顺序是：先开 strictNullChecks，再开 noImplicitAny，然后是 noImplicitReturns，最后处理 noUnusedLocals 与 noUnusedParameters。这个顺序的依据是修复成本与影响面。空检查的修复通常是局部的：加一个判断、改一个类型、把返回值标成可空，行为不变，容易评审。noImplicitAny 则往往要求补齐整个函数的输入契约，甚至要给没有类型的第三方库写声明，影响面大得多，适合等声明文件补齐之后再开。未使用变量这类规则属于清理型，放在最后，否则迁移期间大量临时变量会天天报警，反而让人麻木。

使用 extends 时有两个细节值得记住。一是相对路径以配置文件自身所在目录为基准解析，不是以执行命令的目录为基准，把配置文件放进 config/ 之后，include 里的路径也要相应调整。二是数组类型的选项是整体覆盖而不是合并：base 里写了 "lib": ["es5", "dom"]，子配置再写 "lib": ["es2015"]，结果只剩 es2015，不会自动并入 dom。迁移时如果突然出现一批找不到 document 的错误，多半就是这个原因。

范围扩大的顺序建议从叶子模块开始：纯函数工具库、日期与格式化、与业务无关的适配层。这些模块依赖少、调用方多但接口稳定，改起来风险最低，也最容易写出单元测试。中间层（service、store）随后跟进，最后才是入口与容器组件。反过来先改共享类型是最糟的选择：给一个被几十处引用的接口加上 | null，等于一次性制造几十个报错，评审也无法按业务拆分，最后只能整包回滚。

另外要控制单次提交的规模。一个目录一个 PR，控制在二三十个文件以内，让评审者能逐条看懂每个判空背后的业务假设。迁移不是比谁快，而是比谁留下的判断是对的。新目录和新文件则应该从第一天起就纳入严格配置，哪怕它引用了老代码，也要在边界处把可空值处理掉，避免一边迁移一边制造新的债务。

两类高频报错怎么读

迁移过程中，绝大多数错误可以归入两类。学会快速分辨它们，能省下大量时间。

第一类是 Object is possibly 'null' 或 Object is possibly 'undefined'，错误码分别是 2531 与 2532。它的意思是“你在一个可能为空的值上取属性或调用方法”。出现这条错误，说明类型声明是对的，使用方式需要改：要么在使用前判空，要么用控制流证明这个值不可能为空。它几乎总是出现在迁移的第一天，也几乎总是集中在少数几种模式上，比如数组查找结果、缓存读取结果和 DOM 查询结果。

第二类是 Type 'undefined' is not assignable to type 'string'，属于 2322 可赋值性错误。它通常出现在三个位置：把可能为空的变量赋给非空变量、把可能为空的实参传给必填参数、函数声明返回 string 却在某个分支返回了 undefined。这条错误指向的是“声明与实现不一致”，修法有两种：如果确实可能为空，就改声明；如果不可能为空，就补上缺失的分支。前者是承认现实，后者是修复逻辑，都比加断言更有价值。

读错误时先问一句：是声明错了，还是使用错了？声明错了就改类型，这是最诚实的修法；使用错了就加判断。只有两者都不成立、而你又掌握编译器不知道的信息时，才轮到断言。按这个顺序处理，报错数量会稳定下降；反过来先加断言，报错会立刻消失，但问题只是被挪到了运行时。

笔者给团队定的规矩是：每一个 ! 都必须能说出一句“为什么这里一定不为空”，说不出来就改成判断。合法的场景其实不多：由同一份模板保证的 DOM 节点、测试夹具里的固定数据、以及刚刚校验过但编译器无法跟踪的不变量。不合法的场景更多：find 之后直接加 !、JSON.parse 之后用 as 断言成接口再加 !、以及为了少写两行判断而随手加的 !。这些用法在评审时应该当作红旗，因为它们把“可能为空”这个事实从代码里抹掉了，下一个改这块代码的人不会再想到还有这个分支。

第三方声明与团队落地

存量项目不可能只用自己的代码。第三方库的声明文件质量参差不齐，有的写于严格空检查之前，参数标成必填、返回值标成非空，实际却可能返回 null。这类问题会让迁移凭空多出一批无法修改的报错，必须先有处理预案，否则团队很容易卡在某个依赖上，最后把整个目录从严格配置里移出去。

第一个工具是 skipLibCheck。它从 2.0 起可用，作用是跳过对所有 .d.ts 文件的内部检查，只检查你自己的代码。对于依赖树里个别写坏的声明，这个开关能让迁移继续推进，是性价比最高的应急手段。但它只应该用来隔离第三方，不能用来掩盖自己写的声明文件，否则等于给自己留了一个不受检查的后门。用它的时候最好在配置里写一行注释，说明是为哪个包开的，等对方修复后删掉。

第二个是版本对齐。@types 下的包独立发版，同一份代码在不同时间安装，拿到的声明可能不一样，甚至出现昨天能编译、今天不能的情况。把 @types/node、@types/lodash 这类常用包在 package.json 里固定版本，并提交 lock 文件，能让本地与 CI 的行为一致。这不是洁癖，而是迁移期间减少变量的必要手段：当报错数量突然上涨时，你至少能确定不是依赖在背后换了声明。

第三个是补齐最小声明。对于完全没有类型的库，不要用一行 declare module "x"; 一关了之，那等于把整棵依赖树变成 any，严格检查在这里完全失效。正确做法是写一份最小声明，只声明你实际用到的部分，并如实标出可空：

写声明时会发现，很多“应该不会为空”的假设其实没有依据，这本身就是一次有价值的梳理。至于当前版本没有按行忽略错误的编译指令，绕过检查只能靠断言或单独配置，这反而逼着团队把问题真正修掉。

还有一个比声明更根本的做法：在边界做一次校验。所有外部输入，包括接口响应、本地存储、URL 参数、第三方回调，都在进入系统的第一层被检查并转换成内部类型。内部类型可以大胆地声明为非空，因为能构造出它的路径只有一条。严格空检查真正奖励的，是这种把不确定性挡在边界外的结构，而不是在每个函数里重复判空。校验函数本身要处理 any，但它的输出是可信的，这就是所谓的“一处脏、处处净”。

代码评审时重点看四件事：新增的 ! 有没有理由、新增的 as 有没有把可空断言成非空、公共函数的返回值是否明确标注了可空、以及 .d.ts 的改动是否同步到了调用方。前两条针对个人习惯，后两条针对接口契约。一个团队只要坚持三个月，! 的数量会自然下降，因为它每次出现都会被问一句“凭什么”。

最后是节奏。迁移不是一次运动，而是一段持续数月的日常。比较健康的安排是：每周固定一个下午处理迁移任务，每个迭代消化一到两个目录，遇到阻塞就记录到债务清单并跳过，不在单个文件上纠缠太久。清单上写清楚目录、负责人、阻塞原因和计划时间，比任何动员都有效。等严格目录的覆盖率超过八成，再讨论打开 noImplicitAny，团队不会觉得这是又一次折腾，而是水到渠成的下一步。

小结

strictNullChecks 不改变运行时，只改变编译器对可赋值性的判断，把 null 与 undefined 从“所有类型的合法取值”变成需要显式声明的成员。它值得单独先开，因为修复局部、行为不变、容易评审，而 strict 一次全开会让报错混杂，诱使团队用断言消音。迁移的骨架是分层配置加叶子模块优先：宽松配置继续负责构建，严格配置只做 noEmit 门禁，范围按目录扩大，单次提交控制在可评审的规模。工具层面记住三句话：判空优先于断言，断言必须说得出理由，外部输入在边界校验一次。等这些习惯稳定下来，再打开 noImplicitAny 和其余严格选项，会顺利得多。
