Linux 常用命令速查

在服务器和容器里干活，卡住人的往往不是难题，而是“这个目录为什么满了”、“配置里哪一行写了这个地址”这类具体问题。本文按场景而不是按字母整理常用命令，覆盖查找、查看、权限、磁盘、进程、网络、传输与管道组合，每个场景先给问题再给命令。适合刚接手 Linux 服务器、或者需要在容器里排查问题的开发者，读完能凭一张“场景地图”找到该敲哪条命令。

一、先按场景选命令

按字母排序的速查表适合确认拼写，不适合回忆。真正在机器前卡住的时候，脑子里冒出来的不是命令名，而是一句话：“这个目录怎么这么大”、“日志里什么时候出现过这个报错”。所以本文按场景组织，每一节先给问题，再给命令。

运维里被问得最多的问题大致是四类：东西在哪、内容是什么、为什么慢或者满、怎么搬走。它们分别对应查找类（find、grep）、查看类（less、tail）、状态类（df、du、ss、ps）和传输类（tar、scp、rsync）。先把这张地图记住，具体参数随时可以查。

还有一件事值得先确认：命令到底装没装。CentOS 7 最小化安装不带 net-tools，ifconfig 敲下去就是 command not found；Ubuntu 16.04 的精简镜像里常常缺 ps 和 ping，要装 procps 与 iputils-ping。容器里更常见，curl、dig、ss 经常不在。遇到“这条命令在别的机器上明明能用”，先用 command -v 看一眼路径，比怀疑人生有效。

本文示例以 CentOS 7 与 Ubuntu 16.04 的默认 bash 为准，默认以普通用户执行；需要 root 的操作会在注释或正文里注明，动手前先确认自己当前的身份。

二、找文件与搜内容

“找一份三天前改过的配置”和“查哪个文件里写了这个数据库地址”是两类问题：前者靠文件元数据，后者靠文件内容。主力命令分别是 find 与 grep，它们经常配合使用。

2.1 find：按元数据筛

find 的语法是 find 起始目录 条件 动作，多个条件写在一起是“与”的关系：

-mtime -7 里的负号是“小于”，+7 是“大于”，这条规则同样适用于 -size 和 -atime，第一次用时很容易记反。-type f 限定普通文件，能把目录和套接字排除掉，结果干净很多。

如果只是按名字找，还有 locate 这条捷径：它查的是 updatedb 维护的索引库，几乎瞬间返回，代价是结果可能滞后，刚创建的文件要等下一次索引更新才看得到。CentOS 7 最小化安装默认没有它，需要装 mlocate 并跑一次 updatedb；急着找刚生成的文件时，仍然用 find。

2.3 grep：常用参数与场景

grep 的参数不多，按场景记更牢：

-r 递归、-n 行号、-i 忽略大小写、-v 取反、-l 只输出文件名，--include 比事后用管道过滤省事。至于 grep -r 与 find | xargs grep 怎么取舍：只关心内容、目录里基本都是文本，直接用 grep -r；需要先按类型、时间、大小筛一轮，或者要跳过某些大目录，就先 find 再交给 grep。两者不是替代关系。

常见的误用是把 grep -r 直接跑在 / 或 /var 上，撞到 /proc、/sys 会刷出整屏的 Permission denied 和 Input/output error。加 --exclude-dir 或直接缩小范围，比事后翻屏找结果省时间。文本处理与替换属于另一篇文章的范围，这里只到“找得到”为止。

三、看文件与改文件

文件操作分两层：先能看清内容，再谈怎么复制、移动和删除，顺序反了就很容易误删。

3.1 先看清楚，再动手

cat 只适合小文件：几百行的配置、一张证书、一段脚本。对着几百 MB 的日志用 cat，终端会滚上几分钟，还可能把内存吃紧。大文件交给 less：

head 与 tail 负责截取，tail -f 是看日志的标配。日志被 logrotate 切割后，-f 盯着的还是旧的文件描述符，这时要改用 -F，它按文件名重新打开：

wc -l 数的是行而不是请求数，多行格式的日志（比如 Java 的堆栈）更不能拿行数当业务量。

3.2 复制、移动与删除的边界

cp -a 相当于 -dR --preserve=all，备份配置目录时用它，恢复后权限不会莫名变成 644。mv 在跨分区时实际是复制再删除，大目录会慢，中途失败还会留下半个目标。

rm -rf 没有回收站这一层，-f 又吞掉了确认提示，危险边界集中在通配符和变量上：rm -rf /data/app/* 在目录为空时什么也不删，但 rm -rf $DIR/* 在 DIR 为空时会展开成 rm -rf /*——bash 把未定义的变量替换成空串，命令就指向了根目录。这类事故在运维圈里反复出现，值得在脚本里加一道判断。

ln -s 建的是软链接，源文件删掉后链接成为死链；删除链接本身用 rm link，不要在末尾加斜杠，rm -rf link/ 会顺着链接删进源目录。

四、权限：chmod、chown 与 umask

ls -l 的第一列 -rw-r--r-- 分三段，依次是属主、属组、其他人，每段三位 rwx。三位一组换算成数字是 4、2、1 相加，所以 644 就是属主可读写、其他人只读。

符号写法适合“只改一位”，数字写法适合“一次设定完整状态”。最该警惕的是 chmod -R 777：它把写权限给了所有人，Web 目录一旦被上传脚本，攻击者立刻就能执行，这不是“先跑起来再说”的快捷键，而是实打实的隐患。

chown 换属主与属组，格式是 chown 用户:组 文件，递归加 -R：

umask 决定新建文件的默认权限。它输出一个掩码（通常是 0022），文件用 666 减去掩码得到 644，目录用 777 减去掩码得到 755。所以用编辑器新建、或者用 > 重定向出来的脚本天然没有执行位，“脚本没有执行权限”多数时候不是权限被改坏了，而是创建方式决定的结果，chmod +x 补上即可。

目录上的 x 与文件上的 x 含义不同：对目录而言，它表示“能进入并访问目录内的条目”。一个目录有 r 却没有 x 时，ls 能看到文件名，却拿不到大小、属主这些详情，访问里面的文件也会被拒绝。给 Web 目录设权限时 755 是常见值，正是因为它同时满足了“能列目录”和“能读文件”。

另一个容易误判的原因是换行符：脚本从 Windows 拷过来，首行变成 #!/bin/bash\r，执行时报 bad interpreter。用 file deploy.sh 看到 CRLF，或者 cat -A 看到行尾的 ^M，就能确认，dos2unix 转一下就好。权限模型的完整规则（包括粘滞位、ACL、sudo 配置）另有专文，这里只做速查。

五、磁盘与空间：df、du 与 inode

“磁盘满了”是第一大求助理由。先分清两个命令的分工：df 看文件系统整体，du 看目录占用。

du -sh * 在目录文件很多时会跑很久，因为要遍历所有 inode；先 --max-depth=1 定位到某个子目录，再往里钻，比一上来就全盘扫要快。

顺便提一句，df -h 的 Use% 到 100% 之前就可能写不进去了：ext4 默认给 root 保留 5% 的块，普通用户看到 95% 以上就该着手清理。不少监控把告警线定在 90%，道理相同，留给日志和临时文件一点缓冲。

找个别的大文件，用 find 更直接：

-xdev 让它不跨文件系统，避免扫进 /proc、/sys 和挂载的 NFS；2>/dev/null 吞掉权限报错，结果才看得清。

还有一种情况最有迷惑性：df -h 显示 100%，du -sh 把各目录加起来却差了几个 GB。常见原因有两个。一是文件已被删除但进程还开着句柄，空间不会释放：

找到对应进程后重启它，空间就回来了；直接 kill -9 也行，但要看清楚进程是哪个。二是 inode 用尽：每个文件都要占一个 inode，几十万个小文件（session、缓存、邮件队列）会把 inode 耗光，此时块还有空余，写入却报 No space left on device。df -i 看 IUse% 一栏就明白了，处理办法只能是删小文件，扩容量没有用。

六、进程与网络快查

进程这部分只讲“怎么快速定位”，状态、信号语义、优先级与 top 的交互留给进程管理专文。

pkill -f 的匹配范围比想象中大：它看的是完整命令行，凡是参数里恰好含这段字符串的进程都会被选中，比如正在 tail 同名日志的会话、打开相关文件的编辑器。执行前先用 pgrep -af 看一遍命中的列表，确认无误再动手。

kill -9 之所以是最后手段，是因为进程收不到清理机会：临时文件留在磁盘上，数据库可能留下未提交的事务，共享内存段也可能不释放。合理的顺序是先 kill（TERM），等几秒看进程是否退出，仍不退出再考虑 -9。

网络排查是另一组高频动作：

curl -I 发的是 HEAD 请求，个别服务对 HEAD 返回 405，这时换成 curl -s -o /dev/null -w "%{http_code}\n" 地址，只取状态码更稳。ss 已经全面替代 netstat，CentOS 7 与 Ubuntu 16.04 都自带，-l 监听、-n 不做名字解析、-t TCP、-p 显示进程，四个字母拼起来正好是排查端口占用的最小组合。至于 ifconfig，两个发行版的最小化安装都不保证有，看地址与路由用 ip addr、ip route 更省事。

七、打包、传输与管道组合

tar 的 -f 后面必须紧跟文件名，参数顺序是历史包袱，统一写成 -czf、-xzf、-tzf 最不容易错。解压前用 -t 列一下内容是个好习惯：既能确认包没坏，也能发现包里是不是带了一层多余的目录，避免解完在 /data 下多出十几个文件。

跨机器搬文件有两条路。scp 走 SSH，简单直接；rsync 做增量，第二次只传变化的部分：

发布几百 MB 的静态资源时，rsync -avz 和 scp 的差别非常明显，前者只传改动过的文件，后者每次全量。尾部斜杠是 rsync 的经典坑：dist/ 表示“目录里的内容”，dist 表示“目录本身”，写错会得到 /var/www/dist/dist/index.html。--delete 让目标端与源端完全一致，会删掉目标端多出来的文件，配 -n 先看清单再执行。

打包与同步都绕不开排除项，node_modules、.git、日志文件既大又没必要传，--exclude 可以写多次：

tar 的 --exclude 按归档内的成员名匹配，写 node_modules 会排除任意层级下的同名目录，要精确到某一层就把路径写全，比如 app/node_modules。rsync 的排除规则按相对路径算，两者并不完全通用，套用之前先用 -t 或 -n 验证一次。

管道与重定向是把这些命令串起来的手段：

2>&1 的顺序不能反。> out.log 2>&1 先把标准输出指向文件，再让标准错误复制标准输出的方向；写成 2>&1 > out.log 时，标准错误仍指向终端，只有正常输出进了文件。tee 解决“既想盯着看又想留证据”的问题，-a 是追加，不加就覆盖。

八、历史、别名与几个反复踩的坑

效率上最值得投入的是历史记录。Ctrl+R 做反向搜索，输入片段后连续按可以继续往前翻，回车执行，Ctrl+G 放弃；history 配合 ! 系列能省下大量重复输入：

alias 写在命令行里，重启 shell 就没了，要持久化得放进 ~/.bashrc，改完 source ~/.bashrc 生效。历史记录也有反面：命令里带密码（mysql -p密码、curl -u 用户:口令）会明文留在 ~/.bash_history 里，共享机器上等于把凭据贴在墙上。export HISTCONTROL=ignoreboth 能让重复命令和以空格开头的命令不进历史，敏感操作前先敲一个空格。

接下来是四个反复出现的坑，它们比记不住参数更费时间。

第一个是通配符前面多敲出的空格。rm -rf /data/app/ * 中间多一个空格，删除目标就从“app 目录下的内容”变成“当前目录下的所有内容”。敲删除命令前，用 echo 让 shell 把通配符展开给你看：echo rm -rf *.log，输出的才是真正会执行的命令。

第二个是文件名带空格。for f in $(ls) 遇到 my report.pdf 会拆成两个名字，循环体里的 $f 自然是错的。改用 find -print0 配 read：

第三个是命令串联用错符号。cd /backup; rm -rf * 在 cd 失败时照样执行删除，因为分号不看前一条的成败；换成 &&，前一条失败就停下来。脚本开头加 set -u，让未定义变量直接报错退出，是防住 rm -rf $DIR/* 最便宜的一道保险。

第四个是管道里到底有几个进程。./import.sh | grep ERROR 卡住时，只结束 import.sh 的 pid，下游的 grep 可能还挂在管道上；反过来只结束 grep，上游继续写管道时会收到 SIGPIPE 而退出。要清理整条流水线，按父进程找或者直接结束进程组更干净，别只盯着 ps 里看到的第一个 pid。

小结

速查表的价值不在篇幅，而在把命令和场景对上号：找东西用 find 与 grep，看内容用 less 与 tail -F，判断空间先 df 再 du，搬文件优先 rsync。危险系数最高的三个动作是 rm -rf、chmod -R 777 和 kill -9，动手前多敲一条 ls、pgrep 或 df -h，成本几乎为零。把这些组合写进脚本时，加上 set -u 和 &&，比事后恢复便宜得多。进程、权限、systemd、网络诊断各自还有专文展开，本文只保证下次对着黑屏时，你知道先敲哪条命令。
