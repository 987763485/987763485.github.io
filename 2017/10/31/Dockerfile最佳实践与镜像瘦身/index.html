Dockerfile 最佳实践与镜像瘦身

本文属于《Docker 与 Kubernetes》第 6/51 篇
上一篇系列目录下一篇

会写 Dockerfile 和写好 Dockerfile 之间，隔着一份清单：镜像是不是够小、构建是不是够快、结果是不是可复现、容器里的进程是不是该用 root 跑。本文面向已经能独立写出一个可运行 Dockerfile 的读者，把散落在文档、issue 和踩坑记录里的经验收拢成可以逐条对照的检查项，重点放在体积从哪里来、怎么一层层削掉。读完你应该能对着一份现成的 Dockerfile 指出哪几行在浪费空间，并知道每一处修改的代价在哪里。

镜像里的每一兆从哪里来

在动手瘦身之前，先要把体积的来源分清楚。把 docker images 里那一列数字拆开，绝大多数镜像的体积都能归到五类：基础镜像自带的根文件系统，语言运行时和系统库，只在构建期用得到的工具链，构建过程留下的中间文件，以及和程序运行毫无关系的杂物（文档、man 手册、测试用例、静态库）。这五类里只有前两类是运行必需，后三类都是可以商量甚至必须删掉的。

这里有一个容易被忽略的前提：镜像由一层层只读的层叠加而成，每一层只记录相对上一层的增量。删除文件并不会让下层变小，只会在当前层写入一条“已删除”的标记，下层那份数据依然躺在镜像里。也就是说，一个 500 MB 的文件在某层被创建、在下一层被 rm 掉，镜像总大小依然是 500 MB 加上一点点。理解这一点，后面关于“合并 RUN”的所有建议才有依据。

选一个更小的地基：基础镜像

同样一个程序，换掉 FROM 那一行往往是最省力的一刀。当年的官方镜像大致分三档：完整发行版（debian:stretch、ubuntu:16.04）、精简发行版（debian:stretch-slim）、以及 alpine:3.6 这类以 musl libc 和 BusyBox 为基础的小镜像。三者的体积差距是数量级的，但代价并不相同，选型时要把代价算进去。

-slim 变体基本只做减法：去掉文档、locale 和部分调试工具，glibc 与包管理器都还在，行为与完整版一致，属于风险最低的替换。如果项目依赖 apt 安装系统库、依赖 glibc 的某些行为，先换成 slim 通常不会出意外。

alpine 的代价在 libc。它用 musl 替代 glibc，纯计算代码大多没问题，但有几类要格外小心。一是预编译的二进制，尤其是动态链接 glibc 的第三方工具，直接拷进去会报找不到解释器；二是 Node 的原生扩展，node-gyp 需要 python、make、g++ 和 musl 的头文件，很多带预编译产物的包在 alpine 上装不上，只能现场编译；三是 DNS 解析与 locale 的细节，musl 的解析器对部分旧写法的 search 域支持不同，locale 数据也不完整，做中文时间格式化时要自己补。这些坑不是不能用 alpine，而是要在构建期就把它们踩完，别留到线上。

scratch 是另一档：一个完全空的镜像。它只适合静态链接的二进制，Go 是典型场景，CGO_ENABLED=0 编出来的程序不依赖 libc，把可执行文件和 CA 证书一起拷进去就能跑。代价是这个镜像里没有 shell，docker exec 进去无从下手，排障只能靠日志和外部工具。它适合对体积与攻击面都极敏感的探针、边车类程序，不适合还在频繁调试的业务服务。

层、顺序与缓存

Docker 的构建缓存按层匹配：某条指令的文本和它依赖的父层内容都没变，这一层就直接复用；一旦某一层失效，它后面的所有层都要重建。这条规则决定了一件事，把变化频率低的内容放在前面。源码几乎每次提交都变，依赖清单往往几周才动一次，所以正确顺序是先拷清单、装依赖，再拷源码。

如果反过来先写 COPY . .，任何一次改代码都会让 npm install 那一层失效，依赖得从头下载一遍。这个顺序上的差别，在本地可能只是几十秒，在 CI 里就是每次构建都重新走一遍网络。

合并 RUN 的目的并不是减少层数，而是让“产生垃圾的动作”和“清理垃圾的动作”落在同一层，下一节会看到具体写法。顺带说一句，COPY 的缓存还会比对文件内容的校验和，.dockerignore 没写好时 node_modules 一变、COPY . . 就失效，构建时间会立刻把问题暴露出来。

包管理器的清理必须写在同一层

回到开头那个反例。apt-get update 和 apt-get install 分成两条 RUN，索引文件就被固化在中间层，即使后面删掉也减不了体积。正确写法是把更新、安装、清理串成一条链，用 && 连接，任何一步失败都会中断构建，不会留下一个“装了一半”的镜像。

三个细节值得单独说。--no-install-recommends 会阻止 apt 顺带装上“推荐”包，在 slim 镜像上这一项常常能省下可观的体积，而这些推荐包大多只是让系统更“完整”，对服务本身没有用。rm -rf /var/lib/apt/lists/* 清掉的是包索引缓存，几十 MB 量级，只有在同一层里删除才真正消失。最后，不要在镜像里执行 apt-get upgrade：它会让同一个 tag 在不同时间构建出不同内容，直接破坏可复现性，系统补丁应该通过更换基础镜像的 tag 来解决。

把 update 单独放一层还有个副作用：那一层一旦被缓存，几天后再构建时用的就是过期索引，install 很可能报 Failed to fetch 之类的 404，只能加 --no-cache 重来。写在同一层之后，索引与安装始终是同一次构建的产物，这类问题自然消失。至于装哪个版本，能定就定，libpq5=9.6.* 这样的写法比裸包名更可控，至少不会因为上游发版而在某天突然构建失败。

需要编译的场景更麻烦。build-essential、python-dev 这类包体积大，却只在 make 时用得上。如果不使用多阶段构建，常见的做法是在同一层里安装、编译、再 apt-get purge --auto-remove 掉编译依赖，把所有动作挤进一条 RUN。写法冗长，但这是没有多阶段构建时的唯一选择。alpine 侧对应的是 apk add --no-cache，索引根本不写盘，省掉了清理这一步；CentOS 系则是 yum install -y && yum clean all。

上下文、COPY 与 ADD

docker build . 里的那个点并不是“Dockerfile 所在目录”，而是构建上下文：客户端会把这个目录整个打包发给守护进程。目录里如果躺着 node_modules、.git、几轮构建的产物，传输和后续的 COPY 都要为它们付出代价。.dockerignore 就是用来挡这一刀的。

写法与 .gitignore 类似，支持 ! 取反。有两点建议：一是把构建产物目录也写进去，避免“上一次构建的产物被拷进镜像、又被新产物覆盖”这种隐蔽问题，也让 COPY . . 的缓存判断更稳定；二是不要忽略 package-lock.json、Gopkg.lock 这类锁文件，它们恰恰是可复现构建的依据。

COPY 与 ADD 的区别只有两条，但都值得记住。ADD 遇到本地 tar 包会自动解压，这个隐式行为读 Dockerfile 时很容易被忽略，别人看到 ADD app.tar.gz /app 未必知道落地的是解压后的目录树；ADD 还支持远程 URL，但下载的文件不会解压、不校验任何签名，而且这一层无法利用缓存，源站一变内容就悄悄跟着变。所以取舍很简单：除非确实需要解压本地 tar，一律用 COPY。需要下载文件时，改用 RUN curl -fsSL ... && ...，至少能把校验和写进同一条命令。

还有一处细节：COPY 尽量拷具体文件而不是整个目录，把依赖清单单独放一行，既有利于缓存命中，也避免编辑器的临时文件被带进镜像。

构建与运行分离：把工具链留在构建阶段

上一节“装、编译、再 purge”的写法，在多阶段构建里可以整段省掉。多阶段构建自 17.05 起可用，思路是在同一个 Dockerfile 里写多个 FROM，每个阶段有独立的文件系统，最终镜像只从构建阶段取走需要的那几个文件。

第二个 FROM 之后产出的才是最终镜像，编译器和源码都不在其中。构建阶段的层不会进入最终结果，因此那一侧可以放心安装完整的工具链，不必再为清理写一堆 && rm -rf。本文只把它当作瘦身手段提一句，阶段的组织、构建参数的传递等内容属于专文范围，不再展开。需要提醒的是，多阶段并不会自动让镜像变小：最后阶段如果仍然 COPY . . 把源码带进去，或者 FROM 一个完整发行版，该省的一分也省不下。

运行身份、元数据与启动语义

瘦身之外，还有一组几乎零成本、却经常被漏掉的规则。首先是运行身份：默认情况下容器里的进程以 root 运行，容器被突破时攻击者拿到的就是 root，创建专用用户是成本最低的一道防线。

node:8-alpine 已经预置了 node 用户，直接用即可；换到 debian:stretch-slim 就要自己建：RUN groupadd -r app && useradd -r -g app app。这里有个顺序问题，USER 一旦生效，后面的 RUN 都以该用户执行，装包、建目录都会失败，所以 USER 必须放在需要 root 的指令之后，并且 COPY 时就把属主设好，否则应用读不到自己的文件。

元数据方面，LABEL 用来记录维护者、源码地址这类信息，docker inspect 可以直接读到。EXPOSE 只是声明端口，不会真的发布，但能让阅读者和 -P 知道服务监听在哪里。WORKDIR 比 RUN cd 可靠得多，后者只在当层生效，下一层又回到根目录，这是新手最常踩的坑之一。ENTRYPOINT 与 CMD 的组合值得记一句：前者定义“这个镜像是什么程序”，后者给默认参数，docker run image arg 中的 arg 会替换 CMD，固定入口又要允许传参时，ENTRYPOINT ["server"] 配 CMD ["--config", "/etc/app.conf"] 是最清晰的写法。至于 HEALTHCHECK，它属于可观测性，与体积无关，另有专文讨论。

可复现性与检查手段

“在我机器上是好的”在容器里同样成立，原因往往只有两个：基础镜像用了 latest，或者依赖没有锁版本。latest 是一个会移动的标签，今天拉到的还是 Debian 9，下次可能就是下一个大版本，同一个 Dockerfile 构建出两个不同的镜像，排查问题时连起点都对不上。应固定到具体 tag，条件允许再固定 digest，FROM debian@sha256:... 能保证内容一字不差。依赖同理，apt-get install 不写版本、npm install 不带 lock 文件，构建结果都会随时间漂移。

检查手段主要是两条命令。docker history 逐层列出指令和该层大小，哪一层突然变大一眼可见；docker images 看总量，再 docker run --rm -it image sh 进去用 du -sh /* 逐目录找大文件。习惯做法是构建完先看一遍 history，把最大的三层记下来，再决定是删文件、换基础镜像还是拆多阶段。

比较体积时还要注意口径。仓库里的层是压缩传输的，落到磁盘上则是解压后的大小，同一个镜像在两个地方读到两个数字并不奇怪；团队里统计“镜像多大”，最好约定看哪个指标，否则讨论了半天其实在说两件事。

几种常见误区可以对照自查：RUN cd /app 不改变后续指令的工作目录，必须用 WORKDIR；把密钥写进 Dockerfile 或用 COPY 拷进去，即使下一层删除，它也仍留在构建历史里，应改为运行时注入；为了层数少硬把所有命令塞进一条 RUN，可读性和缓存粒度都会变差，层数本身并不是指标；在 RUN 里用 curl | bash 装东西，版本不受控也无法审计。这些错误的共同点，是把“镜像能跑”当成了终点。

小结

镜像瘦身不是一次性的清理，而是一组可以固化的习惯：先确认体积来自哪一层，再从基础镜像、层顺序、包管理清理、上下文过滤、多阶段构建几个方向逐个收敛。每改一处都要问两个问题，运行期是否真的需要它，构建结果是否仍然可复现。把非 root 用户、固定 tag、WORKDIR 这类零成本规则写进团队模板，比事后翻 history 找大文件有效得多。下次评审 Dockerfile 时，拿这份清单逐条对照即可。
