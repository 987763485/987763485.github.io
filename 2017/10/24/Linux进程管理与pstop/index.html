Linux 进程管理与 ps、top

线上机器变慢时，很多人的第一反应是敲一个 top，却说不清屏幕上那几列数字的含义。本文从进程的身份讲起，把 ps 与 top 的字段、状态码、负载均值逐层拆开，再落到信号、作业控制与四类故障的排查路径。读者应当已经能在 Linux 上部署服务，但排障时仍常靠“重启试试”。

进程的身份证：PID、PPID 与进程组

内核把每一次程序执行都包装成一个进程，并分配一个进程号（PID）。PID 在小范围内顺序分配、循环复用，所以“昨天日志里的 12345”和“今天看到的 12345”大概率不是同一个东西，排查时最好连启动时间一起记下来。

比 PID 更能说明来历的是父进程号（PPID）。所有进程都挂在同一棵树上，树根是开机时由内核拉起的 1 号进程；在 CentOS 7 与 Ubuntu 16.04 上，这个位置由 systemd 占据。执行 ps -o pid,ppid,cmd -p $$ 可以立刻看出当前 shell 的父进程是谁，通常是 sshd 或者某个终端程序。父进程先退出时，孤儿进程会被 1 号进程收养，这一点在追问“是谁拉起了一堆 python 脚本”时非常有用。

再往外一层是进程组（PGID）和会话（SID）。进程组是信号投递的最小单位，一次 kill 带上负号就能打给整组；会话则大致对应一次登录，会话首进程通常持有控制终端（TTY）。只有前台进程组才有资格读终端，后台进程组去读会被内核用 SIGTTIN 暂停，这正是“后台任务莫名其妙停住”的经典原因。

-o pgid= 里的等号表示不要表头，输出干净得可以直接喂给别的命令。这种“只取字段”的写法后面还会反复出现。

状态码：R、S、D、T、Z 到底在说什么

随便敲一行 ps aux，STAT 那一列几乎全是 S，偶尔蹦出一个 R，出问题时才会看到 D 或 Z。这五个字母描述的是进程“此刻在等什么”，而不是它的健康程度。

  • R：正在 CPU 上跑，或者在运行队列里等着被调度。短暂出现很正常，若长期有一堆 R，说明 CPU 是瓶颈。
  • S：可中断睡眠，在等事件（网络包、锁、定时器）。绝大多数空闲进程都在这，睡得着也醒得来，收到信号会立刻响应。
  • D：不可中断睡眠，卡在内核里等一个“不能被打断”的操作，多见于磁盘 I/O、NFS、某些驱动。它不占 CPU，却会把负载均值推高。
  • T：被作业控制停住（Ctrl-Z 或 SIGSTOP），或者正被调试器跟踪。它不会自己醒来，要 SIGCONT。
  • Z：僵尸。进程本体已经退出，只剩一个 task_struct 占着 PID，等父进程调用 wait() 收尸。
flowchart TD
    NEW[进程创建] --> R[R 运行或可运行]
    R -->|等待事件| S[S 可中断睡眠]
    R -->|等待慢速 IO| D[D 不可中断睡眠]
    S -->|事件到达| R
    D -->|IO 返回| R
    R -->|Ctrl-Z 或 SIGSTOP| T[T 停止]
    T -->|SIGCONT| R
    R -->|进程退出| Z[Z 僵尸]
    S -->|进程退出| Z
    Z -->|父进程 wait 回收| G[彻底消失]

STAT 后面还可能跟修饰符：s 会话首进程，l 多线程，+ 前台进程组，< 高优先级，N 低优先级。Ss 多半是守护进程，Rl 则是在多线程烧 CPU。

D 和 Z 最容易被误解。D 状态下 kill -9 也杀不掉，因为信号要等系统调用返回、进程回到用户态才被处理；该看的是 wchan 与 cat /proc/<pid>/stack（需要 root）。Z 则根本杀不死，它已经死了，问题在父进程：找到 PPID 对应的程序重启，或者补上漏掉的 wait()。长期堆积的僵尸会耗尽 PID 空间，导致新进程 fork 失败。

ps：两套写法与字段差异

ps 的参数风格来自两个传统：BSD 风格不带横线（ps aux），System V 风格带横线（ps -ef）。两种写法在 2017 年的发行版上都能用，差别在于默认展示的列。

最实质的差别是 ps -ef 有 PPID 而没有 %CPU、%MEM，ps aux 反过来。查“谁拉起的”用前者，查“谁在吃 CPU 和内存”用后者，两者都不够时就用 -o 自己拼。

理解字段比记住顺序更重要。VSZ 是虚拟内存大小，包含已申请未用的堆和映射进来的共享库，普通 Java 进程显示几个 GB 不奇怪；RSS 才是驻留物理内存的部分，但共享库的页被重复计入，把所有进程的 RSS 相加会超过物理内存。%MEM 是 RSS 除以总内存，做容量评估比 VSZ 靠谱。TIME 是累计消耗的 CPU 时间而非运行时长，跑了三天 TIME 只有两秒说明它一直在睡；START 只给日期或时刻，判断启动时间用 etime 更准。

还有一个常被误读的地方：ps aux 里的 %CPU 是这个进程整个生命周期内的平均值，不是瞬时值。一个跑了十小时、刚刚开始发疯的进程，%CPU 可能只有 3%。要看瞬时占用，得靠 top，或者用 pidstat 连续采样。

真正在脚本和排障里好用的，是 --sort、-o 和几个过滤参数的组合。

--sort 的键名前面加负号表示降序，不要写成 --sort=%cpu-；head 要多留一行给表头，否则“前 5 名”实际只有 4 个。

top 的界面：五行表头加一张进程表

top 默认每 3 秒刷新一次，画面分两半：上半是五行摘要，下半是按 CPU 排序的进程列表。很多人只盯着下面那张表，其实前五行才是判断“机器整体是否健康”的入口。

第一行的 load average 是 1、5、15 分钟三个负载值，留到下一节专门讲。第二行的 Tasks 给出总数与各状态的计数，zombie 不为 0 就该去查父进程了。

第三行 %Cpu(s) 把 CPU 时间拆成若干份。us 是用户态，sy 是内核态，ni 是调过 nice 值的用户态时间，id 是空闲，wa 是等 I/O 的空闲——它算在空闲里，所以 id 高不代表没压力，wa 高才是磁盘或网络存储慢的强信号。hi、si 分别是硬中断和软中断，网卡打满时 si 会抬头。st 是虚拟化环境下被别的虚拟机“偷走”的时间，云主机上长期偏高说明该换规格了。

内存那两行的单位随 procps-ng 版本是 KiB 或 MiB。used 的口径是总量减去空闲再减去缓存，所以“内存用了 90%”先别慌，buff/cache 可回收，该看的是 avail Mem。Swap 有占用不必立刻告警，但 si、so 持续非零说明内存真的不够，进程在被反复换进换出。

下半部分的进程表，前几列与 ps 同源：PR 是优先级（默认 20），NI 是 nice 值（默认 0），VIRT 对应 VSZ，RES 对应 RSS，SHR 是共享内存部分，S 就是前面讲的 R/S/D/T/Z，TIME+ 是累计 CPU 时间，精确到百分之一秒。VIRT 动辄几十 GB 的进程不必惊慌，那只是地址空间。

top 的价值有一半在交互键上。procps-ng 3.3 这一代的操作逻辑是：大写字母决定排序，小写字母决定显示内容。

  • P 按 CPU 排序，M 按内存排序，T 按累计 CPU 时间排序。刚进界面默认就是按 CPU 排，跑久了想找内存大户就按 M。
  • 1 展开每个逻辑核的单独占用。判断“是单线程打满一个核，还是所有核一起忙”全靠这个键，单核 100% 而总体只有 12%，通常意味着代码里有个串行热点。
  • c 在命令名和完整命令行之间切换。同一个 java 进程可能有十几个，只有完整命令行能区分哪个是订单服务、哪个是网关。
  • k 杀进程。按下后先输 PID，再输信号，默认 15（SIGTERM），回车执行。在 top 里误杀的风险比命令行低，因为它要求你手输 PID。
  • r 调整 nice 值，输入 PID 和新的 nice（正数降优先级，负数需要 root）。
  • u 按用户过滤，H 切线程视图，f 选字段，d 改刷新间隔，W 存布局到 ~/.toprc，q 退出。

批处理场景下用 -b 关掉交互：top -b -n 1 | head -20 可以塞进定时任务留档；top -b -d 1 -n 60 > /tmp/top.log 能在故障复现时录一分钟现场。只想盯一个进程时用 top -p 3128，看线程用 top -H -p 3128，列出的 PID 是线程 ID，配合 jstack 正好能对上号。

负载均值：三个数字到底在数什么

负载均值不是 CPU 使用率，而是“可运行状态与不可中断睡眠状态的进程数”的指数衰减平均。前者在排队等 CPU，后者卡在 I/O 上，两类都算。这一点与传统 Unix 不同，也是“CPU 空闲但负载 8”的原因。

三个数字分别是 1、5、15 分钟的平滑值，可以直接读 /proc/loadavg：

最后两个字段是“当前可运行进程数/总进程数”和最近分配的 PID。判断标准只有一条：把负载与逻辑核数比。4 核机器上负载 4 意味着刚好排满，没有余量；持续高于核数，队列会越来越长，接口延迟随之上升。1 分钟值突然飙高而 15 分钟值平稳，说明故障刚刚发生；三个值一起高，说明问题已经持续了一段时间。

还有一个容易踩的坑：/proc/loadavg 不属于任何命名空间，容器里读到的仍是宿主机的负载。在容器里看到负载很高就断定是自己的服务有问题，往往会查错方向。

信号与作业控制：先礼后兵

信号是内核投递给进程的异步通知，kill 只是“发信号”，行为由信号编号决定，所以 kill -l 值得记一下，日常打交道的不过下面几个。

信号 编号 默认行为 典型用途
SIGHUP 1 终止 守护进程常把它重定义为“重载配置”
SIGINT 2 终止 Ctrl-C，发给前台进程组
SIGKILL 9 终止 不可捕获、不可忽略，最后手段
SIGTERM 15 终止 kill 的默认信号，请求优雅退出
SIGSTOP 19 暂停 不可捕获，作业控制用
SIGCONT 18 继续 唤醒被暂停的进程

SIGTERM 与 SIGKILL 的区别不在“温和”与“粗暴”，而在语义：前者是请求，进程可以捕获它，从而关闭连接、刷盘、写完日志再退出；后者由内核直接抹掉进程，缓冲区里的数据可能丢失，共享内存和临时文件留在原地。正确顺序永远是先 TERM，等几秒确认没退再 KILL。连着敲两次 kill -9 没有额外效果，只会让你失去线索。

SIGHUP 的语义完全取决于程序有没有接管它。nginx、sshd 这类守护进程会重载配置，普通前台程序收到 HUP 则按默认行为直接退出，这就是“退出终端后后台任务跟着死掉”的由来。容器里 1 号进程对信号的处理另有约定，很多镜像需要额外的 init 进程转发信号。

把视角放回终端，作业控制其实就是信号的另一套外壳：挂起、继续、终止，每一步背后都是信号。在交互式 shell 里，它把“进程”变成了可以挂起、切换、接管的对象。

nohup 做两件事：把 SIGHUP 设为忽略，以及在没有重定向时把输出追加到 nohup.out。disown 只是把作业从 shell 的表里摘掉，让 shell 退出时不再发 HUP，进程对信号的处理没变。两者都能实现“关掉终端任务继续跑”，但 nohup 更保险。要彻底脱离终端可以用 setsid 进入新会话，代价是再也没有控制终端，输出只能靠日志。

找到进程，并给它设个边界

按名字找进程用 pgrep -af nginx，-a 让它同时输出完整命令行，比 ps | grep 少一次误伤自己的机会；pgrep -u www-data -l 按用户过滤。只想要 PID 时 pidof sshd 更直接，但它按可执行文件名匹配，改过进程名的脚本它认不出来。

要知道一个进程占着哪些文件、端口和目录，用 lsof -p 3128；查谁占了 80 端口用 lsof -i :80。/proc/<pid>/ 则是内核给出的原始视图：status 有线程数与 VmRSS，cmdline 是命令行，cwd 指向工作目录，fd/ 下每个描述符一个链接。“删了文件空间不释放”“句柄泄漏”的答案都在这里。

限制分两条线。优先级用 nice 调，范围从 -20 到 19，值越大越谦让；资源上限用 ulimit 看，它只影响当前 shell 及其子进程，软限制不能超过硬限制。要长期生效得写 /etc/security/limits.conf，由 pam_limits 在登录时套用，改完必须重新登录，已运行的进程不受影响。

nofile 的默认值通常是 1024，反向代理、消息队列这类连接密集型服务撞上它时，报错往往只是含糊的“Too many open files”，先 ulimit -a 再查 /proc/<pid>/limits，能立刻分清是没改还是改错了地方。

四个排障现场

CPU 高。top 里按 P 排好序，按 1 看是不是只有一个核在满，按 c 看清完整命令。定位到 PID 后，Java 用 top -H -p 找线程再 jstack 对应，其他服务用 strace -c -p 采十秒看系统调用分布。%sy 高而 %us 低时，问题多半在系统调用、锁竞争或中断，不在业务代码。

内存持续上涨。ps -eo pid,rss,cmd --sort=-rss | head 找到大户，隔几分钟再看 RSS 是否单调上升。缓慢上升、avail Mem 同步下降、又没有对应流量增长，基本可判泄漏；这时先 jmap 留现场再重启。

僵尸进程。ps -eo stat,ppid,pid,cmd | awk '$1 ~ /^Z/' 一次列全，重点看 PPID 是谁。僵尸杀不掉也不用杀，它只是一条等待回收的记录，父进程重启或补上 wait() 之后自然消失，数量持续增长才值得处理。

D 状态卡住。ps -eo pid,stat,wchan:32,cmd | awk '$2 ~ /D/' 能一次列出所有卡在不可中断睡眠的进程，wchan 会告诉你卡在哪个内核函数。配合 top 的 wa 与 iostat -x 1（需 sysstat）判断是本地磁盘还是 NFS；此时 kill -9 无效，要先解决存储。

小结

进程排查的顺序应当固定下来：先用 ps 或 top 看清状态与资源，再用 pgrep、lsof、/proc 确认身份与足迹，最后才谈信号和优先级。状态码里最需要警惕的是 D 与 Z，前者说明存储有问题，后者说明父进程有问题，两者都不是“杀一下”能解决的。负载均值要跟逻辑核数比，还要记得它把 I/O 等待也算了进去。发送信号永远先 TERM 后 KILL，给进程留出收尾的机会，也给自己留出排查的线索。
