TypeScript 2.7 新特性：定长元组

本文属于《TypeScript 学习路线》第 28/74 篇
上一篇系列目录下一篇

当前 TypeScript 的稳定版是 2.5，2.7 还只是开发中的版本，本文提到的“定长元组”属于正在讨论和实现的方向，语法与行为都要以最终发布为准。元组在 2.5 里已经能把每个位置标上不同的类型，但这份“位置清单”在编译器眼里更像一句口头约定：长度不参与检查，越界下标照样能读，push 也不看还剩几个位置。本文从元组的基本用法讲起，梳理 2.5 下这些能力的边界，再介绍社区正在讨论的定长方向，并给出三套当下就能落地的替代写法。

元组是什么：给每个位置单独标类型

在 TypeScript 里，数组的类型写作 number[] 或 Array<number>，它表达的是“里面装的都是 number，有几个都行”。可现实中的数据经常是“位置固定、每个位置含义不同”：地图上的一点是经度加纬度，一条排行榜记录是名字加分数，一行统计是标签加计数。用 number[] 去描述这类数据，丢掉的恰恰是“第一个是经度、第二个是纬度”这层信息，读代码的人只能靠注释去猜。

元组（tuple）就是为这种场景准备的。它的写法是把每个位置的类型按顺序写在方括号里，位置和类型一一对应：

从类型关系上看，元组是数组的子类型：一个 [string, number] 可以赋给 (string | number)[]，反过来则不成立，因为 (string | number)[] 并不保证第一个位置是字符串、第二个位置是数字。这也意味着元组能调用数组的所有方法，map、forEach、slice 都可以直接用，只是返回值通常会退化成普通数组。

要注意的是，元组约束的是“每个位置是什么类型”，不是“一共有几个位置”。前半句 2.5 已经做得很好，后半句正是本文要讨论的缺口。

为什么“定长”值得单独做一次

有人会问：长度不对就自己在运行时判一下，何必让类型系统管？问题在于，元组被用到的场合，恰恰是长度错误后果最直接的场合。

坐标与向量是最典型的一类。[lng, lat] 一旦多一个或少一个，画出来的点就会飞到地图外面；矩阵运算里，行向量和列向量的长度对不上，算出来的结果没有任何意义，但代码不会抛异常，只会安静地给出错误数字。

键值对是第二类。把对象转成 Object.entries 风格的数据、把 Map 摊平成数组、把统计结果排成队列，这些结构都要求“两个位置，一个键一个值”。如果某条记录因为上游数据缺失变成了一个元素，后续的 forEach(([k, v]) => ...) 里 v 就是 undefined，而错误会一路传到最后渲染层。

CSV 行解析是第三类，也是笔者踩过坑的地方。每一行按逗号切开后，本应得到固定列数的元组。列数少了，后面的字段整体左移，类型对不上却很难在编译期发现：

第四类是函数参数列表。把一组参数打包成元组再传给 apply，或者从配置里读出一组参数依次传给构造函数，长度必须严格对应。少一个参数，被调函数拿到 undefined；多一个参数，多余的部分被静默忽略，调用方还以为自己传对了。

这四个场景的共同点是：长度错误不会立刻抛异常，而是变成 NaN、undefined 或错位的字段，漂到很远才暴露。把这类错误挡在编译期，比在运行时堆防御性判断便宜得多。

草案中的方向：让长度参与类型检查

TypeScript 的 issue 列表里，关于元组长度的讨论持续了很长时间，社区方案的核心思路可以概括成一句话：把长度也变成类型的一部分，而不是一条可以被忽略的元信息。目前讨论中的方向大致有三层。

第一层是让 length 拥有字面量类型。长度是 2 的元组，它的 length 属性类型就是 2，而不是笼统的 number。这一步看起来只是精度提升，实际是后面两层的前提：只有长度成为类型，编译器才能拿它和别的长度做比较。

第二层是让下标访问与长度挂钩。下标落在 0 到 length - 1 之内，拿到对应位置的类型；落在范围之外，直接报错，而不是退化成元素类型的联合。这一层直接堵住了前文那个 p[2] 的例子。

第三层是让赋值时的长度参与可赋值性判断。把一个长度不足或超出的值赋给定长元组，应当报错，而不是靠“元素类型能对上”就放行。经过变量、函数返回值中转之后也不应例外。

需要说明的是，这三层目前都还停留在讨论与实现阶段，具体细节（比如可选元素如何计入长度、只读位置怎么处理、数组方法要不要跟着收紧）都还没有定论。push 这类会改变长度的方法是否一并禁止，社区里的意见也不一致，我们不把它当成承诺。可以确定的是，方向是“让长度成为硬约束”，而不是继续停留在注释和文档里。

同期 2.7 的开发分支上还在讨论其他几个议题，本文只聚焦元组这一条线，不展开。

现在就能用的三种替代方案

等待版本不是唯一的选项。下面三种写法都在 2.5 下可用，分别适合不同的场景，可以按需组合。

方案一：用对象换字段名

如果元组的位置语义已经复杂到需要注释才能看懂，那它本来就该是一个对象。对象把“第几个位置是什么”换成“字段叫什么”，长度问题自然消失，多一个字段少一个字段都由类型检查兜住：

代价有两个。一是序列化后体积变大，[116.4, 39.9] 变成 {"lng":116.4,"lat":39.9}，在传输成千上万个点的场景里要权衡。二是解构写法不再对称，const { lng, lat } = a 可读，但不如 [x, y] 紧凑。笔者的经验是：跨模块传递的数据用对象，函数内部临时算的中间值用元组。

三种方案并不互斥：配置与接口数据用对象，解析边界用守卫，纯计算模块内部用 Pair、Vec2 这类别名，元组只在生命周期很短的地方出现。

迁移建议：什么时候等，什么时候现在就改

判断标准只有一条：长度错误会不会带来难以定位的后果。会，就无论 2.7 是否发布都该主动约束；不会，等版本只是省事。

可以按下面三种情况分开处理。公共 API 与跨模块的数据结构，现在就改成对象或“对象加数组”的组合，因为它们一旦上线就很难改，越早定形越好。外部数据入口，现在就补守卫，因为定长元组即便发布也不会替你做运行时校验，接口传来的东西在类型上永远只是“声称”。纯内部的计算代码，可以保留元组，等定长检查落地后再享受一次免费升级，这类代码改动面小，迁起来也快。

还要提醒一点：定长检查变严后，靠 push 和下标拼数据的旧代码可能报错。计划升级的团队最好提前清理越界访问与变长操作，把升级变成可控的改造，而不是发布当天的一堆红色波浪线。

小结

元组在 2.5 里解决的是“每个位置是什么类型”，还没有解决“一共有几个位置”。当前的三个漏口很具体：length 的类型是 number、越界下标不报错、push 不检查剩余容量，它们的共同后果是把编译期错误推迟成运行时的 NaN 与 undefined。社区讨论中的定长元组方向，是把长度变成字面量类型，让下标访问和赋值都受它约束，但具体细节尚未定稿，本文的例子只能当作方向示意。在它发布之前，对象、类型守卫、长度别名这三套写法已经能覆盖绝大多数场景，而且它们对未来升级是兼容的。笔者建议：先按“错误后果”给现有元组分类，把危险的那部分现在就改掉，剩下的等版本。
