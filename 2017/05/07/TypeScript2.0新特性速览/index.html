TypeScript 2.0 新特性速览

本文属于《TypeScript 学习路线》第 22/74 篇
上一篇系列目录下一篇

本文记录的是一次真实的版本升级：一个停留在 TypeScript 1.8 的老项目，怎样在两天里升到 2.0，又怎样面对 --strictNullChecks 打开后的一千多条报错。适合已经会写 TypeScript、正准备升级或刚被报错淹没的读者。读完后你会知道 2.0 各项特性在迁移现场分别意味着什么、先开哪个开关、哪些坑可以绕开。

从一千多条报错说起

这个项目从 2015 年开始写，一直用 TypeScript 1.8。tsconfig.json 里只有 target 和 module 两项，类型检查近乎放养。决定升级的契机很实际：接手的人越来越多，接口字段拼错要等运行时才暴露；依赖的类型声明要么靠库自带，要么用 typings 手动装，版本经常对不上。

升级那天的操作很简单：改 package.json，安装 2.0，打开 strictNullChecks，重新编译。终端刷出一千一百多条错误，大半是 Type 'null' is not assignable to type 'string'。数字吓人，但逐条看下去，多数是变量初始化顺序和可选参数没写类型，真正藏着的空值 bug 只有十几处。

把报错按来源分了一下：与空值相关的约七百条，集中在可选属性、函数返回值和变量初始化；接口与实现不匹配的约两百条，是之前改字段留下的；剩下的来自声明文件和模块解析。这个分布决定了后面的顺序：先修接口，再处理空值，最后收拾声明。

这就是 2.0 带来的东西：不是新语法，而是把以前默认放行的 null/undefined、隐式 any、可被随意改写的属性，统统摆到编译期来谈。下面按升级时踩到的顺序，把各项变化过一遍。

非空断言 ! 与类型守卫

! 是后缀语法，意思是”这里我保证不是空”：

它只从类型里删掉 null/undefined，不生成任何运行时检查。升级初期我们用它压掉了几十条报错，代码 review 时又一条条改回守卫。原因很直接：断言把责任从编译器转移到了人身上，而人不会每次都记得。能写出运行时判断的地方，就不该用 !。

readonly：只读写在类型上

readonly 修饰属性，赋值只允许发生在声明或构造函数里：

它和 const 不是一回事：const 约束变量绑定，readonly 约束属性；readonly 在编译后被抹掉，运行时照样能改，只是绕过去要写类型断言。升级时我们给配置对象、常量表和组件的 props 都加上它，哪些数据不该被改一眼可见。需要提醒的是它只做浅层保护，属性若是对象，对象内部仍可修改。

模块解析与 @types

1.8 时代装第三方类型声明，用的是 typings 或更早的 tsd：项目根目录多一个 typings.json，再执行 typings install lodash --save --global，声明文件落在 typings/ 下，还得靠注释引用。2.0 把这条路并进了 npm：类型包统一发布在 @types 作用域下，装依赖就是装类型。

tsconfig.json 里保持 moduleResolution 为 node，编译器会自动去 node_modules/@types 找声明。只有需要限制全局类型时才写 types，需要额外目录时才写 typeRoots：

注意 types 是白名单：一旦写了它，没列出的全局声明就不会被自动加载，页面里突然冒出 Cannot find name 'describe' 多半是这个原因。迁移时先删掉所有 typings 的引用注释，再按报错逐个补 @types 包；找不到对应声明的老旧库，就在 src/types 下自己写一个 declare module。

--noImplicitAny 抓的是”没写类型、编译器也不吭声”的位置，最典型的是函数参数：

回调参数通常不用手写，上下文能推断出来；推断不出的，宁可标 any 也不要放着不管，至少搜索时能看见。这个开关在我们项目里只报出两百多条，改起来比 strictNullChecks 轻松，适合作为第一步。

--strict 是 2.3 刚发布的总开关，一次性打开 noImplicitAny、strictNullChecks、noImplicitThis 和严格模式。它适合新项目，老项目直接开等于把两项最重的检查同时压上来，报错会混在一起、难以分批推进。因此当年团队仍以逐项开关为主，--strict 只在新仓库里评估使用。

增量编译、--watch 与编辑器体验

2.0 的 tsc 还没有真正的增量编译缓存，命令行每次都是全量检查；能依靠的是 --watch，进程常驻，文件变化后重新走一遍：

中型项目全量编译约四十秒，--watch 首次之后每次几秒，改一个文件等两三秒出结果，尚可接受；文件数上千以后，等待会明显变长。当时的办法是缩小 include 范围、把 node_modules 排除干净，再打开 --skipLibCheck 跳过声明文件内部的检查：

skipLibCheck 只跳过 .d.ts 内部的类型检查，不影响自己代码的检查，代价是第三方声明之间的冲突不会被发现。编辑器走语言服务，本身就维护着增量状态，所以 VS Code 里的报错通常比命令行快；遇到提示迟钝，先确认 typescript.tsdk 指向本地版本，再重启语言服务。

迁移顺序：先开哪一项

我们的顺序是 noImplicitAny 在前、strictNullChecks 在后。前者报错少、改动局部，还能让后续的空值检查更有依据；后者影响面大，适合单独占一个迭代。若项目规模不大、又急着定型，反过来先开空值检查也成立，但两项一起开会让报错互相掩盖。

strictNullChecks 的报错建议分三类处理：明显该有值的，补类型或初始化；确实可能为空的，加判断或默认值；暂时吃不准的，用 any 或类型断言压住，并留下 TODO。当年没有 ts-ignore 这类注释开关，临时压制只能靠 any 或类型断言，因此每压一条都要记下来，否则半年后没人知道哪些断言是欠账。

我们按目录推进，每清完一个目录就提交一次，并在提交信息里记下当天的开关状态。这样 CI 变红时能快速定位是哪一批改动引入的，也方便回滚单个目录而不是整个升级。

配置上可以按目录渐进：新代码放 src/，旧代码放 legacy/，两个 tsconfig 分别设置严格度，构建时先编译新目录、再编译旧目录。等旧目录的报错清到可接受范围，再合并配置。不要为了清零而全局关掉检查，那等于白升。

与 Babel 6 的分工

项目里已有 Babel 6 的构建链，升级后并没有让 tsc 接管输出，而是分成两步：tsc --noEmit 只做类型检查，转译仍交给 Babel。这样已有的 babel-preset-env、transform-runtime 和按浏览器补丁的策略都不用动。

Babel 一侧用 babel-preset-typescript 去掉类型标注。它在 2017 年初已经能用，但生态还在补：const enum、namespace 的部分写法、装饰器元数据等能力并不完整，遇到就得退回 ts-loader，或者把这部分代码单独交给 tsc。另一个限制是 Babel 不做类型检查，noEmit 那一步必须留在 CI 里，否则类型错误会一路溜到线上。

对大多数团队，2017 年更稳的组合仍是 ts-loader 直接接 tsc，Babel 负责它擅长的语法降级；两套方案并存时，务必只让一个工具产出 JS，避免重复转译。

一页速查：收益与代价

升级前后对比最能说明问题。全量编译从二十多秒涨到四十秒，--watch 的反馈仍在三秒内；产出的 JS 与 1.8 时代几乎一样，运行时行为没有变化，回滚成本很低。真正变化的是写码习惯：接口字段先想清楚可不可空，配置对象默认加 readonly，遇到 ! 会在 review 里被问一句”你能保证吗”。

按实际帮助排序，strictNullChecks 排第一，它抓到的空值问题最多；@types 排第二，它把类型声明的维护并回了 npm；控制流分析排第三，属于顺手就用的改善；readonly 与 never 穷尽检查更像锦上添花，没有它们也能升级。--strict 在 2.3 刚发布的时点还不适合老项目，逐项开关反而更容易控制节奏。

代价也要写清楚。两天里大约一天半在改类型，半天在处理 @types 与构建；strictNullChecks 的报错虽然一次清完，后续两周仍不断冒出漏网的 undefined。第三方库没有声明时只能自己补 declare module，这部分维护成本会长期存在。编辑器统一版本也花了半天，早期有人没切 tsdk，提交的代码在 CI 上才报错。

如果重来一次，我们会把 noImplicitAny 与 @types 迁移放在同一周，把 strictNullChecks 单独排一个迭代，并且在开开关之前先补齐接口定义。这样报错数量会少一半，改动也更容易 review。还有一点经验：升级前先在 CI 里加一条 tsc --noEmit，让类型检查成为合并门槛，比事后集中清报错有效得多。

也不是所有项目都该马上升级。代码量小、类型本来就少，收益有限；构建链还停在老工具上的，先升构建再升类型系统更稳。判断标准是团队有没有人愿意长期维护类型声明，否则 @types 装得越多，无人处理的红色波浪线也越多。

特性 开关 迁移收益 代价
空值检查 --strictNullChecks 空值问题在编译期暴露 报错量大，接口需要重写
非空断言与守卫 语法（! 与 is） 快速处理可疑值 滥用断言会把风险推到运行时
控制流分析 默认开启 少写断言，分支自动收窄 复杂闭包内推断仍不理想
只读属性 readonly 配置与组件 props 不可变 只在编译期生效，且是浅层保护
类型声明 @types 与 typeRoots 声明跟随 npm 依赖 老库没有声明，需要自己补
隐式 any 检查 --noImplicitAny 消除隐式 any 回调与旧工具函数要补类型
严格总开关 --strict（2.3 刚发布） 一次配齐严格检查 老项目难以一次落地
编译反馈 --watch 与 --skipLibCheck 缩短反馈，绕开声明冲突 并非真正增量，可能漏掉声明问题

小结

TypeScript 2.0 对老项目的价值，不在于多几个语法，而在于把空值、隐式 any 和可变属性这些长期靠约定维持的东西变成了编译错误。升级路径并不复杂：钉住本地版本、统一切好编辑器版本、先开 noImplicitAny 再开 strictNullChecks，用 @types 替换 typings。真正的成本在改代码和补声明，不在安装。

迁移时守住两条：能用守卫就不用 !，能写联合类型就不要留 any。--strict 在 2.3 刚发布的阶段可以评估，但老项目仍建议逐项开启。至于 keyof、映射类型这些类型编程能力，等基础检查稳定后再学也不迟。
