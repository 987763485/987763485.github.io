Docker 容器间通信方案

本文属于《Docker 与 Kubernetes》第 9/51 篇
上一篇系列目录下一篇

一个 web 容器要访问数据库，最容易出问题的地方往往不是 SQL，而是“它到底该连哪个地址”。本文从一次半夜改配置的经历出发，梳理 Docker 里两个业务容器可靠通信的几个环节：发现、就绪、调用与数据通道。读完你应该能为自己的项目选一套不依赖固定 IP 的连通方案。

从一个连不上的数据库说起

去年冬天接手的一个项目，部署方式很朴素：一台 4 核 8G 的云主机，用 docker run 起两个容器，web 跑 Node 服务，db 跑 MySQL 5.7。图省事，连接串里直接写了 10.0.0.17:3306，那是 db 容器启动后用 docker inspect 查到的地址，测试一切正常。

两个月后升级镜像，docker rm 掉旧容器再 run 一个新的，web 立刻报 ECONNREFUSED。原因不复杂：容器重建后拿到了 10.0.0.21，而配置文件还停在旧地址。那天晚上的处理方式很原始，改配置、重启、再改回来，来回三次，因为预发和线上各有一套 IP 写死在不同的环境变量里。

这次折腾说明，容器通信的第一课不是“怎么连”，而是“不要记住地址”：创建、销毁、重建都是常态，写死 IP 的配置迟早变成故障。

从机制上说，同一台宿主机上的两个容器各自持有独立的网络命名空间，通过 veth 设备接到同一张网桥上，二层是通的。这部分属于内核网络的基础设施，本站《Docker 网络模式详解》已经拆开讲过，本文不再重复。对写业务的人来说，真正要解决的是两件事。

第一是“发现”：web 怎么知道 db 现在在哪。靠人肉维护 IP 列表显然不可持续，需要一套随容器生命周期自动更新的名字到地址的映射。第二是“策略”：哪些容器允许互访、走哪个端口、对方还没准备好时怎么办。发现解决“找得到”，策略解决“找得对、连得稳”，后面几节基本都围绕这两个词展开。

默认 bridge 只能靠 IP，自定义网络才有名字

docker run 不带 --network 时，容器会落在默认的 bridge 网络上。这张网桥上挤着所有没有指定网络的容器，看起来省事，实际有两个硬伤：一是默认网络没有内嵌 DNS，容器之间只能靠 IP 互访，--name 起的名字在这里不参与解析；二是所有互不相干的应用共享同一张网桥，谈不上隔离。

Docker 早年给出的补丁是 --link，把 db 以别名链进 web，由 Docker 往 web 的 /etc/hosts 和一组环境变量里写地址。这个参数在 1.9 之后就被标记为不推荐，2017 年的官方文档已经明确提示它可能被移除，但老教程流传太广，现在仍能看到 --link db:db 的写法。它的毛病在于单向依赖、改动需要重启双方，也无法表达“这两个容器属于同一个应用”。

在用户自定义网络上，Docker 会提供一个内嵌的 DNS 服务，容器可以直接用容器名解析到对方。web 里连 db:3306 就够了，db 重建几次、地址怎么变，都不影响 web 的配置。

这里有个容易忽略的前提：必须处在同一张网络。把 web 放进 app_net、db 留在默认 bridge，db 这个名字对 web 来说根本不存在，报错是 Could not resolve host，而不是连接被拒。分不清这两类错误，排查时会白走很多弯路。

容器起来了，不代表服务好了

Compose 文件里写一行 depends_on: [db]，很多人以为顺序问题就解决了。它只保证 docker-compose up 先创建 db 再创建 web，不保证 MySQL 已经能接受连接。MySQL 容器启动后要先初始化数据目录，第一次启动十几秒很常见，这段时间 web 早已跑起来并尝试连接，于是首次部署必然报错，第二次因为数据目录已就绪反而正常——这种“重跑一次就好”的现象，最容易把问题掩盖过去。

更根本的办法是让应用自己具备重试能力。连接失败不退出，按指数退避重连，直到成功或超过上限再报错退出，交给编排层重启。这一条对任何编排工具都成立，也是后面讲跨主机时唯一不会失效的手段。

在此之上再加健康检查，让“就绪”这件事对 Docker 可见。Dockerfile 里可以写 HEALTHCHECK，Compose 的 2.1 格式则支持在依赖上声明条件：

容器之间不需要 -p

-p 8080:80 做的是宿主机端口到容器端口的映射。它的服务对象是容器之外的世界：浏览器、前面的 Nginx、另一台机器。web 调 db 时，数据包从 web 的网卡出发，经网桥直接到 db 的网卡，根本不会经过宿主机的 3306。

见过把 db 的 3306 映射到宿主机，再让 web 连“宿主机 IP:3306”的写法。绕这一圈的代价不小：多一次地址转换、多一个对外暴露面、宿主机 IP 一变又要改配置，而且数据库端口直接开在公网上，扫描器几分钟就能找到。除非确实需要在本机用客户端连进去看数据，否则不要映射数据库端口；要调试就用 docker exec -it db mysql -uroot -p，或者临时加 -p 127.0.0.1:3306:3306，只绑回环地址。

对外提供服务时同样要收窄绑定地址。-p 127.0.0.1:8080:80 只允许本机访问，前面挂 Nginx 做入口；写成 -p 8080:80 则等于监听所有网卡，防火墙一旦有疏漏就是敞开的。端口映射是给外部用的，内部通信应当留在容器网络里。

走 HTTP 还是 RPC

地址通了，接下来要决定用什么方式说话。同一台宿主机上的两个容器，网络延迟本来就在毫秒以下，协议开销的差距远小于团队熟悉度的差距。笔者的默认建议是 HTTP 加 JSON：调试方便，curl 一条命令就能验证，Nginx、日志、监控全都认识它。只有内部调用量大、接口结构固定、对序列化成本敏感时，才值得上 gRPC、Thrift 这类 RPC 框架。

无论选哪种，有三个参数必须显式设置，不能吃默认值：连接超时、读超时、重试次数。不少 HTTP 客户端默认不设超时，db 一旦卡住，web 的请求会一个个挂在那里把线程耗光，最后整条链路雪崩。给一个 3 秒的连接超时、10 秒的读超时，比事后做任何性能优化都值钱。

连接池同样不能忽略。每个请求新建一条 TCP 连接，在容器网络里虽然不算慢，但握手开销和 TIME_WAIT 堆积在并发上来后很可观。主流客户端库都自带连接池，把最大连接数、空闲超时按实际并发调一下，别放任默认值。

重试则要配合幂等来设计。GET 天然幂等，重试是安全的；POST 下单这类写操作，如果第一次其实已经写成功、只是响应在网络上丢了，盲目重试就会多出一笔订单。可行的做法是让客户端生成一个请求 ID 随请求带上，服务端按 ID 去重；或者干脆不对写请求自动重试，把失败交给上层处理。读多写少的内部调用，只对读开重试通常就够了。

同步调不通的时候，考虑消息队列

如果 web 只是“通知”另一个服务去做某件事，并不需要立刻拿到结果，同步调用就是自找麻烦：下游慢一点，上游跟着慢；下游挂了，上游的重试能持续到天亮。这时把调用换成消息更合适。RabbitMQ 3.6 和 Redis 的 list、pub/sub 都是当期常见选择，前者提供确认、持久化和灵活路由，后者胜在项目里本来就在用，不必新增组件。

用队列换来的是解耦和削峰，代价是最终一致：页面上不能立刻看到结果，得设计“处理中”的状态。判断标准很简单，问一句“用户需要马上看到这个结果吗”，需要就同步，不需要就异步。

消费端有两件事必须处理。一是确认机制：处理成功后再 ack，处理中途进程挂掉，消息会重新投递；反过来先 ack 再处理，一崩溃消息就永久丢了。二是重复消费：ack 丢失、网络抖动都会让同一条消息被投递两次，消费逻辑必须幂等，常见做法是按消息里的业务 ID 建唯一约束，重复写入自然被数据库挡掉。

还有一个常见错误是把队列当数据库使，消息堆积几百万条无人消费。队列深度和消费延迟要进监控，超过阈值就报警。

不建议把共享文件当消息通道，用目录里出现文件来表示“有新任务”。轮询有延迟，删除与读取不是原子操作，失败重试也没有记录，出了问题无从查起。这类需求应该用队列。

Compose 默认会为项目建一张网络，名字是项目名加 _default，文件里所有服务自动加入，服务名就是可解析的主机名。所以最简单的 compose 文件不需要写任何 networks，web 直接连 db 即可：

跨主机与安全边界

容器分散到多台机器后，同宿主机那套名字解析就失效了。Docker 的答案是 overlay 网络，靠 Swarm 模式或外部键值存储同步各节点的网络状态，让容器看起来像在同一张网里。它要开放额外端口、引入额外组件，出问题时排查链路也长得多。团队只有一两台机器时，笔者的建议很朴素：应用层直连对方主机映射出来的端口，配好 TLS 与重试，比勉强铺 overlay 更省心。

安全上有三条底线。按应用划分网络，web 与 db 一张、后台任务另一张，不要全挤在默认 bridge；只暴露必要端口，数据库和队列一概不做宿主机映射；容器之间的流量默认明文，跨主机传密码、令牌必须走 TLS，或者放进受信任的内网网段，不要假设“内网就安全”。

小结

场景 方案 注意点
同宿主机两个业务容器 自定义 bridge 网络 同一网络，用容器名
一个服务需要多个名字 --network-alias 仅同网络内有效
依赖的服务启动慢 健康检查加重试 3.x 的 depends_on 不支持条件
只需通知、不等结果 RabbitMQ 或 Redis ack 与幂等缺一不可
两个容器交换文件 命名 volume 挂只读，慎并发写
多服务编排 Compose 默认网络 服务名即主机名
跨主机 overlay 或直连 小团队选后者

回到开篇那个半夜：连接串写成 db:3306，两个容器放进同一张自定义网络，再加一个启动重试，那次故障根本不会发生。容器通信的难点不在网络机制，而在我们是否愿意放弃“地址不变”的假设：让名字负责发现，让重试负责波动，让队列负责解耦，剩下的交给编排工具。
