Go 1.8 环境搭建与 GOPATH

本文属于《Go 语言与工程》第 1/78 篇
上一篇系列目录下一篇

第一次在新机器上装 Go，卡住人的往往不是语法，而是“代码到底该放在哪”。本文从一次 go get 报错讲起，把 Go 1.8 的安装、三个环境变量、GOPATH 工作区、依赖拉取和日常工具链串起来，读完应当能独立搭起一套可编译、可测试、能切换项目的 Go 环境。

报错从这里开始

我最初把项目放在 ~/projects/hello，写完 main.go 直接编译，引用标准库一切正常，可只要 import 自己写的另一个包，终端就抛出一行 cannot find package "hello/util" in any of: ...。另一台机器上更奇怪：go get github.com/gin-gonic/gin 明明提示成功，代码里 import 它却依旧说找不到。

两个现象指向同一件事：Go 不在“当前目录”里找包，而是在一组固定的根目录里找。这组根目录由 GOPATH 指定，go get 把远程仓库下载到它的 src 下，编译器也只在 src 下按 import 路径逐级查找。项目放在 ~/projects，对 Go 来说等于不存在。

Go 1.8 之前，GOPATH 没设置时工具链会直接报错；1.8 起有了默认值 $HOME/go，问题便从“变量没设”变成“代码放错地方”，报错更隐蔽，原因却相同。所以本文先把工作区规则讲清楚，再回头看安装。

安装 Go 1.8

官方推荐的安装方式是下载二进制压缩包，解压到 /usr/local，得到 /usr/local/go 这个固定目录。如果机器上装过旧版本，先把旧目录删掉，避免残留的标准库和工具混在一起；解压本身不覆盖已有文件。

三个环境变量与工作区目录

这三个变量名字相近，职责却完全不同，混淆它们是新手报错的常见源头。

GOROOT 是 Go 自身的安装目录，里面装着标准库源码、编译器和 go 命令。它由安装位置决定，通常不需要手动设置；只有装在非常规路径或多版本并存时，才需要显式指定。

GOPATH 是工作区，也就是你写代码和存放第三方库的地方。Go 1.8 给它的默认值是 $HOME/go，在这之前的版本里不设置就直接报错。它可以配置多个路径，用冒号分隔，但只有第一个用于 go get 下载和 go install 输出，其余仅参与查找，所以多路径在实践中很少用。

GOBIN 决定 go install 把可执行文件放到哪。它的默认值是空字符串，为空时落到 $GOPATH/bin；一旦显式设置，所有项目编译出的二进制都挤在同一个目录，反而容易重名覆盖。除非要把工具集中到 ~/bin，一般保持默认。

src、pkg、bin 的分工

GOPATH 目录下约定俗成有三个子目录，各管一件事。src 放所有源代码，你自己的项目和 go get 拉下来的第三方库都在这里，按 import 路径层层展开。pkg 放编译后的包归档文件，路径里带平台后缀，例如 pkg/linux_amd64/，供后续编译复用。bin 放 go install 产生的可执行文件，只要它在 PATH 里，装完的工具就能直接调用。

关键在于 src 下的目录层级必须和 import 路径完全一致。import "github.com/you/hello/util" 之所以能被解析，是因为编译器把 GOPATH、src 和这段字符串直接拼成了磁盘路径。Go 1.8 没有模块声明文件，import 路径本身就是包的唯一标识，没有第二处可以声明“这个目录叫什么名字”。所以目录一旦建错，代码再正确也编译不过。

包名、目录名与 internal

目录名和包名是两个概念，但实践中应当保持一致。import 路径的最后一段是目录名，代码里 package 后面写的是包名，调用时用的是包名。把 src/github.com/you/util 里的包声明成 package helper，引用者必须写 import ".../util" 却用 helper.Foo() 调用，读代码的人每次都要回头确认。唯一的例外是 main 包，它的包名固定为 main，与目录名无关。

一个目录里只能有一个包，测试文件可以声明成 xxx_test 形成外部测试包，这是特意留的口子。同一目录下混入两个不同包名的源文件，编译会直接报 found packages a and b。

internal 是 Go 用来表达“仅内部可见”的目录名。放在 internal 下的包，只能被 internal 父目录这棵树里的代码导入，树外的包引用会被编译器拒绝。比如 github.com/you/hello/internal/db 只有 github.com/you/hello 下的代码能用，别人即便拿到源码也导不进来。这条规则由工具链强制执行，不需要文档约定。

另一种常见报错是 import cycle not allowed。Go 禁止包之间循环引用，A 导入 B、B 又导入 A，即使只是各用一个函数也不行。解决办法通常是把双方共用的类型或函数抽到第三个包里，或者由上层包做参数传递，而不是让底层包反向依赖。

go get 与 vendor

go get 做两件事：按 import 路径把远程仓库克隆到 $GOPATH/src 下对应位置，然后编译安装。它要求机器上有 git 或 mercurial，并且能访问托管站点。常用参数有三个：-u 先把已有仓库更新到最新再安装，-d 只下载不安装，-v 显示执行过程。

落到 src 下的就是一份普通的源码副本，可以直接读、直接改，这也是当年排查第三方库问题最常用的手段。副作用是 go get -u 拉的是默认分支的最新提交，没有版本约束：今天能编译，明天上游改个函数签名就可能挂掉。

vendor 目录用来解决这个不确定性。它在 Go 1.5 引入，1.6 起默认开启，做法是把依赖的源码复制到项目根目录下的 vendor/ 里，随项目一起提交。解析 import 时，编译器按“就近原则”查找：先看当前包所在目录下的 vendor，再逐级向上找父目录的 vendor，都没有才回到 $GOPATH/src，最后是 $GOROOT/src。因此 vendor 里的副本会盖住工作区里的同名包。

手工维护 vendor 不现实，2017 年常用 glide 与 dep。glide 用 glide.yaml 声明依赖、glide.lock 锁定提交，glide install 负责填充 vendor；dep 是官方正在推进的实验性工具，用 Gopkg.toml 和 Gopkg.lock，命令是 dep ensure，当时还没有定稿，团队里更多是试点。需要说明的是，Go 1.8 没有模块的概念，也没有任何在源码里声明依赖版本的语法，版本信息只能存在于这些工具的文件和锁文件里。

多项目共用一个 GOPATH

多个项目共用同一个 GOPATH 时，所有第三方库只有 src 下那一份。A 项目依赖某库的旧版本，B 项目要用新版本，go get -u 一执行，A 就可能编译失败；反过来把旧代码放回去，B 又坏了。更麻烦的是这种故障没有提示，往往在别人的机器上才暴露。

用 go test 写测试

测试文件以 _test.go 结尾，和被测试代码放在同一个目录，go test 会自动收集，普通构建则完全忽略它们。测试函数固定以 Test 开头、接收 *testing.T，不需要额外注册。包内测试直接声明 package calc，可以访问未导出成员；需要只测公开接口时，声明成 package calc_test 并导入自己。

表驱动是 Go 里最普遍的写法：把输入、期望值和用例名放进一个切片，循环执行，失败时打印用例名。新增场景只是往切片里加一行，比复制十几个函数清晰。Go 1.7 起有了 t.Run，可以让每个用例单独成子测试，-run 还能按名字筛。

./... 表示当前目录及其所有子包，是跑全项目测试的标准写法。覆盖率用 -cover 直接看百分比，要定位到具体行就输出 profile 再用 go tool cover 打开网页。基准测试必须以 Benchmark 开头，框架反复调整 b.N 直到结果稳定，-benchmem 顺带给出内存分配次数。

工具链与编辑器

gofmt 是官方格式化器，不接受任何风格争论。单个文件用 gofmt -l main.go 检查、gofmt -w main.go 改写，整个项目用 go fmt ./...，它会找出所有包再逐个格式化。团队里通常把它挂进编辑器保存动作或 pre-commit 钩子。

go vet 检查编译器不会报、但几乎一定是 bug 的写法，例如 Printf 占位符与参数类型不匹配、结构体标签拼写错误、无效果的赋值。它不替代测试，适合放进 CI 的第一步。go doc 在终端查标准库和本地包的文档，go doc fmt.Println 比开浏览器快。go list ./... 列出项目所有包，写脚本时很常用。

编辑器方面，VS Code 装 Go 插件后首次打开 .go 文件会提示安装一批工具，包括补全用的 gocode、跳转用的 godef、格式化并整理 import 的 goimports，让插件自动装即可。把 go.formatTool 设成 goimports，保存时既格式化又补上缺失的 import。vim 用户装 vim-go，执行 :GoInstallBinaries 安装同一批工具，常用的还有 :GoBuild、:GoTest、:GoDef。它们都装在 $GOPATH/bin，换工作区后要重装或复制。

环境搭好之后，剩下的问题基本集中在几类。第一类是 GOPATH 的幻觉：Go 1.8 默认 $HOME/go，代码被要求放在 ~/go/src 下，人却还在 ~/projects 里敲命令。第二类是把项目放在 GOPATH 之外，标准库能编译，一 import 自己的包就报 cannot find package，此时先看 go env GOPATH，再确认路径前缀是否吻合。

第三类是包名与目录名不一致，编译能过，调用方却对不上名字。第四类是 go get 卡住或超时，当年的常用做法是在 shell 里设置 http_proxy 与 https_proxy 让 git 和 go get 都走代理，或者用 gopm 这类带下载能力的工具，最稳妥的办法是在能访问的机器上 git clone，再把整个仓库连 vendor 一起拷进项目。另外不要用 sudo go get，否则 $GOPATH 里会留下一堆 root 所有的文件，之后普通用户 go install 就会报权限错误。

小结

Go 1.8 的环境可以概括成一句话：一套工具链，一个工作区，代码按 import 路径摆放。安装只是解压加 PATH，真正需要理解的是 src、pkg、bin 的分工，以及 import 路径与磁盘目录的一一对应；依赖版本在 2017 年靠 vendor 和 glide、dep 这类工具管理，还没有模块。多项目冲突优先用独立工作区或 vendor 隔离，gofmt 与 go vet 尽早接进流程。下表的路径对照可以留着排查时用。

路径 作用 常见错误
$GOROOT Go 安装目录，标准库与工具链所在 指向旧版本，与 PATH 里的 go 不是同一套
$GOPATH 工作区根目录，1.8 默认 $HOME/go 以为没设就不生效，项目其实在另一个根下
$GOPATH/src 源码，按 import 路径逐级存放 目录层级与 import 路径不一致，报找不到包
$GOPATH/pkg 编译后的包归档，按平台分目录 手工改动或随意清空，导致全量重编译
$GOPATH/bin go install 生成的可执行文件 没加进 PATH，装完的工具无法直接执行
$GOBIN 指定二进制输出目录 与多工作区混用，同名工具互相覆盖
vendor/ 项目内锁定的依赖副本 放错层级或未提交，换机器后编译失败
