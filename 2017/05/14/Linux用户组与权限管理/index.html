Linux 用户、组与权限管理

权限问题几乎从不出现在教程的第一课里，却总在部署那天集中爆发。本文从一次真实的入职故障说起，把用户与组、权限位、umask、特殊权限、ACL 和 sudo 串成一条线，最后给出一张排查表。内容基于 CentOS 7 与 Ubuntu 16.04，命令在两者上通用，差异之处会单独说明。

从一个下午的故障说起

去年组里来了一位新同事，领到一台 Ubuntu 16.04 的开发机。第一件事是装环境，sudo apt-get install 刚敲下去就报错：xxx is not in the sudoers file. This incident will be reported.。我们把他加进 sudo 组，问题解决，大家都没往心里去。

两周后同一个人的部署脚本出事了。脚本以专用账号 deploy 运行，负责把构建产物同步到 /var/log/myapp 并追加日志，结果每一步都返回 Permission denied。目录是运维手工建的，属主 root、属组 root、权限 755，而 deploy 既不是 root 也不在 root 组里，自然写不进去。更隐蔽的是第二层：即使把目录改成 deploy 可写，脚本自己新建的子目录仍然是 755，同组的另一个账号还是进不去。

这两件事看着不相干，根子却是同一个：我们只记得“给权限”，没弄清账号属于哪些组、目录的属组是谁、进程创建文件时默认带什么权限。后面几节就按这个顺序拆开讲。

三个文件与 uid、gid

Linux 的用户信息不在数据库里，而在三个纯文本文件中。

/etc/passwd 每行七个字段，用冒号分隔：

第二字段的 x 只是占位，真正的口令散列放在 /etc/shadow，这样普通用户读 passwd 也拿不到密文。第三、第四字段是 uid 与 gid，系统靠这两个数字判断身份与主组。第五字段是备注，第六是家目录，第七是登录 shell。把 shell 写成 /usr/sbin/nologin 是最简单的封禁手段：账号存在、能被服务使用，但人登不进来。

/etc/shadow 有九个字段，依次是用户名、加密口令、最后一次修改口令的天数（从 1970-01-01 起算）、两次修改的最小间隔、最大有效天数、过期前警告天数、宽限天数、账号失效日期、保留字段。口令位是 !! 或 * 时表示这个账号没有可用口令，通常也就无法登录。

/etc/group 每行四个字段：组名、组口令占位、gid、成员列表。注意成员列表只列“附加组”，主组不会重复出现，判断组关系不能只看这个文件。

uid 有几个约定值值得记住。0 永远是 root，而且任何 uid 为 0 的账号都等价于 root，多出来的 uid 0 账号基本可以当作后门处理。CentOS 7 与 Ubuntu 16.04 都把 1 到 999 留给系统用户，普通用户从 1000 开始分配（更早的 CentOS 6 是从 500 开始，看到 500 多的 uid 不必惊讶）。系统用户没有口令、没有可登录 shell，专供 nginx、mysql 这类服务降权运行，这是最小权限原则在账号层面的体现。

-m 建家目录，不加它有些发行版不会建；-s 指定 shell，给服务账号一律用 /usr/sbin/nologin；-G 是附加组，多个用逗号隔开。最容易出事的是 usermod -G：它执行的是“替换”而不是“追加”，漏掉 -a 会把此前的附加组全部冲掉，docker 组没了、www 组也没了。改完务必用 id 复核。

passwd 除了改自己的口令，还能由 root 改别人的、锁定账号、设置过期策略，passwd -e 可强制下次登录改口令。groups 打印某人的组列表，和 id -Gn 等价。

组与主组、附加组

组是权限的批量发放单位。与其给五个人分别授权，不如建一个组，把目录的属组设为它，再把人放进去。

主组是账号在 /etc/passwd 里那个 gid，新建文件时默认继承它；附加组只影响“能访问什么”，不影响新建文件的属组。一个人只有一个主组，附加组可以有任意多个；id -gn 看主组，id -Gn 看全部。

改完组关系，已经登录的会话不会立刻生效，因为进程启动时就把组列表读进了内核。此时要么退出重登，要么执行 newgrp www 开一个以该组为主组的新 shell。生产上更常见的做法是直接重新登录，或者用 sg www -c "command" 只对单条命令切换组。

权限位：rwx 的两种含义

ls -l 第一列那串 -rwxr-xr-- 要拆成四段看：第一位是文件类型，- 普通文件、d 目录、l 符号链接；后面每三位一组，分别是属主、属组、其他人的权限。r 读、w 写、x 执行，但同样的字母落在文件与目录上，含义差别很大。

对文件而言，r 是能读取内容，w 是能修改内容，x 是能作为程序执行。对目录而言，r 是能列出里面有哪些条目，w 是能在其中新建、删除、重命名条目，x 是能进入该目录、能访问其中已知名字的子项。这三者互相独立：只有 r 没有 x，ls 能看到文件名，但 cat 里面的文件会失败；只有 x 没有 r，进得去、能打开已知路径，却列不出目录内容。很多人把目录的 w 理解成“能修改目录里的文件”，其实改文件内容看文件自己的 w，目录的 w 只管“条目能不能增删”。

八进制是这三位的紧凑写法：r=4、w=2、x=1，每组相加，三组连写。755 即属主读写执行、同组读执行、其他人读执行；644 是属主读写、其余只读；600 只有属主能读写。chmod 两种写法都要会：

符号法的价值在于“增量修改”。用 chmod 755 改一个原本 750 的脚本，会把组的写权限一并抹掉；符号法只碰你指定的位。-R 递归时要格外小心，它会把执行位无差别地加到普通文件上，a+rX 里的大写 X 就是为这种场景准备的。

权限位决定“能做什么”，属主与属组决定“对谁生效”。chown 改属主，chgrp 改属组，一条命令也能同时改：

chown user:group 是最常用的形式，冒号两边都可以省略，省略属主写成 :www，省略属组写成 deploy:。

递归修改的风险在于“顺手”。chown -R deploy:www / 这类手滑足以让系统报废，因为 /etc/shadow、/usr/bin/sudo 都依赖 root 属主；即便范围小一些，把 ~/.ssh 的属主改错也会让公钥登录失效。执行前先用 ls -ld 看清目标，必要时加 -c 让 chown 打印每一处改动，改完再核一遍。还要记住 chown 默认跟随符号链接，改的是链接指向的目标文件，只有加 -h 才动链接自身，这一点在部署软链接目录时经常被忽略。

umask：新文件的默认权限

新建文件的权限不是凭空来的，它由“基准权限减去 umask”得到。基准值固定：目录 777，文件 666（默认不给执行位）。umask 里的位表示“要扣掉的部分”，计算方式是按位取反再与：

这就解释了新目录 755、新文件 644 的来源：多数系统默认 umask 是 022。开篇那个部署故障的第二层也在这里：服务账号的 umask 是 022，脚本建的子目录是 755，同组账号没有写权限，日志轮转或追加就失败。解决办法不是事后 chmod -R，而是把 umask 调成 002，配合目录的 setgid 位，让新建内容从一开始就属于正确的组。

特殊权限：s 与 t

九个权限位之外还有三个特殊位，占八进制的第一位。它们用 ls -l 看时寄生在 x 位上：s 表示“有执行位且置了特殊位”，S 表示“置了特殊位但没有执行位”。

setuid 作用在可执行文件上，进程运行时临时获得文件属主的身份。最典型的例子是 /usr/bin/passwd：普通用户本来读不了 /etc/shadow，却能改自己的口令，靠的就是这个二进制文件属主为 root 且带 setuid 位。程序内部会校验“你只能改自己的口令”，把提权限制在必要范围内。这也是 setuid 危险的原因：一旦某个 setuid root 程序有漏洞，任何本地用户都能借它拿到 root；排查时用 find / -perm -4000 可以列出全部 setuid 文件。

setgid 有两种用法。放在可执行文件上，进程以文件属组的身份运行；放在目录上，目录里新建的文件和子目录会自动继承该目录的属组，而不是创建者的主组。后者是团队共享目录的标准做法：

sticky bit 只对目录有意义，作用是“目录里的文件只有属主、目录属主或 root 能删”。/tmp 的 1777 就是它：所有人都能写，但删不掉别人的临时文件。没有它，任何用户都能清空别人正在用的 socket 或锁文件。

三个位也能用符号设置：chmod u+s、chmod g+s、chmod o+t。清理权限时别图省事写 chmod -R 777，它会把 setuid 与 sticky 一并抹掉。

ACL：给单个用户开口子

传统权限只有属主、属组、其他人三档，遇到“组只读、但让某一个人可写”就卡住了：改组权限会把所有人都放开。ACL 解决的正是这个粒度问题。CentOS 7 默认支持，Ubuntu 16.04 需要先装包：

默认 ACL 用于继承，只对目录有意义：在目录上设了默认条目，之后新建的子目录和文件会自动带上同样的 ACL。

-d 表示 default，只影响此后新建的内容，不回溯已有文件；想让存量也生效，要再用 -R -m 设一次普通 ACL。ACL 条目一多，ls -l 已经看不全，排障必须靠 getfacl，最后往往变成隐形的权限债。

sudo：把 root 关进笼子

多人共用的机器不该共用 root 口令，sudo 的价值是“以谁的身份执行哪条命令”可以逐条授权，并且留下日志。编辑规则一律用 visudo，它会在保存时做语法检查；直接改坏 /etc/sudoers 的后果是任何人都无法再提权，只能进单用户模式救场。

SSH 登录与密钥权限

~/.ssh/authorized_keys 的权限必须是 600，~/.ssh 必须是 700，家目录不能对同组或其他人可写。这不是建议，是 sshd 的硬性检查：只要权限过宽，它会直接忽略这个文件并在日志里写一行 Authentication refused: bad ownership or modes。原因很直白，公钥文件若可被别人改写，对方就能塞进自己的公钥，密钥认证形同虚设。

服务端还有两个开关值得改。PermitRootLogin no 禁止 root 直接登录，需要时先用普通账号登录再 sudo；AllowUsers deploy ops 只允许名单内的账号建立会话，比防火墙规则更贴近“谁能进来”这个问题。改完先 sshd -t 检查配置，再 reload，避免把自己关在门外。

容器里的用户

小结

权限问题几乎都能还原成三个问题：这个进程以哪个 uid 运行、它属于哪些组、目标对象对这几组身份放开了什么。先答清这三问，再谈 chmod 和 chown。默认值比一次性修补更重要：umask、目录的 setgid、Dockerfile 的 USER，都是让新内容一出生就带着正确权限的手段。至于 SELinux，它是在传统权限之上再加一层标签检查，本文不展开，遇到“权限明明对却仍被拒”时记得 getenforce 看一眼。
