Docker 镜像分层与缓存

本文属于《Docker 与 Kubernetes》第 4/51 篇
上一篇系列目录下一篇

本文从一次“只改一行代码，构建时间却翻了十倍”的事故讲起，把 Docker 镜像的层、overlay2 的读写路径、构建缓存的命中与失效讲透，再落到依赖安装、多阶段构建、体积与安全治理上。读者不需要预先了解联合文件系统，但应当写过 Dockerfile、跑过 docker build。读完可以判断自己的构建为什么慢、缓存为什么没命中，并把一套可复现的优化手段用到项目里。

一次改一行的构建事故

六月的某个下午，我改了一个订单接口里的空指针判断，只动了一行 Go 代码。提交之后，CI 上的镜像构建从一分多钟变成了十二分钟，部署窗口被硬生生拖后。日志里最刺眼的是依赖安装那一步：dep ensure 把二十几个依赖从头拉了一遍，网络慢的时候还要重试。

我先怀疑网络，把构建机的代理、DNS、镜像源都查了一遍，又换了台机器重试，结果一样。回到本地执行 docker build -t api:test .，每一步后面都没有 Using cache，从 COPY . . 开始全是 Running in ...。把 Dockerfile 摊开，问题就很清楚了：

COPY . . 排在依赖安装前面，任何源码改动都会让这一层的内容校验和变化，后面两步自然全量重来。这不是 Docker 的缺陷，而是分层模型在按规则工作；理解了规则，同一份 Dockerfile 完全可以做到改源码只重建最后一层。

镜像是什么：只读层、元数据与两个 ID

镜像可以拆成两部分：一组按顺序叠放的只读层，以及一份描述这些层怎么用的配置。层里装的是文件系统差异，配置里装的是环境变量、默认命令、工作目录、端口声明和构建历史。docker history 把两部分摊在同一张表里：

IMAGE 列是层的短 ID，CREATED BY 是当年执行的指令，SIZE 是这一层相对父层新增的字节数。加上 --no-trunc 可以看到完整命令与完整 ID；docker inspect 则能看到镜像配置里的 RootFS.Layers。

层 ID 和镜像 ID 不是一回事。层 ID 指向一份文件系统差异；镜像 ID 是配置对象的 sha256，配置里按顺序记录了每一层的 diff_id，也就是该层未压缩 tar 包的 sha256。由此可以解释两个常见现象。第一，同一个镜像在不同机器上的层 ID 可能不同，因为层 ID 是本地存储给层分配的句柄，跨机器真正一致的是 diff_id。第二，docker images 里的 SIZE 是把各层大小直接相加，共享的基础层在每个镜像里都被算了一遍，所以把所有镜像的 SIZE 加起来会远大于磁盘占用，真实占用要看 docker system df。

还有一个容易忽略的点：镜像本身不含可写层。可写层是容器运行时才有的，容器删除就消失；docker commit 做的事，就是把某个容器的可写层固化成新的一层，追加到镜像末尾。所以“镜像是一组只读层”这句话要补全：它是一组只读层加一份元数据，运行时再在顶部叠一个可写层，三者合起来才是容器看到的文件系统。

overlay2：层怎样拼成一个根文件系统

docker info 的 Storage Driver 一栏决定了层怎么落盘。2017 年主流发行版里，Ubuntu 16.04 的 4.4 内核默认使用 overlay2；CentOS 7 的 3.10 内核要较新的小版本才支持 overlay2，老机器上还常见 overlay 或 devicemapper。本文以 overlay2 为例，只看它和镜像分层有关的部分。

启动一个容器后，docker inspect 能看到这个容器对应的四个目录：

LowerDir 是一个用冒号分隔的目录列表，每一项对应镜像里的一层，顺序是从上到下。UpperDir 是这个容器自己的可写层。此外还有 WorkDir，它是 overlayfs 准备写时复制时用的临时区，属于实现细节，不要手动往里放东西；MergedDir 则是合并后的挂载点，容器里的进程看到的就是它。

读路径是合并。每个 diff 目录里只存相对父层新增或修改的文件，overlayfs 把多个 lower 目录叠在一起，同名路径由上层覆盖下层，目录则做合并。读一个文件时，内核从最上层往下找，命中第一个就返回，所以容器看到的是所有层的并集，但每个具体文件只来自某一层。

写路径是复制。修改一个位于 lower 层的文件时，内核先把该文件整份复制到 upperdir，再在副本上改；新建文件直接写进 upperdir；删除 lower 里的文件时，upperdir 里生成一条 whiteout 记录，表示“这一层看不到它”。这一套就是常说的写时复制（Copy-on-Write，CoW）。它的代价很直接：第一次写大文件要付出整份复制的开销，所以数据库数据目录、日志目录应该挂 volume，让写入绕过联合文件系统。

容器的可写层就是那个 UpperDir。容器删除时它一并删除，内容不会回到镜像；docker commit 做的事，是把 UpperDir 打包成新的一层追加到镜像末尾。反过来，十个容器共用一个镜像时，只读层在磁盘上只有一份，每个容器只多出一个 UpperDir。这是分层在存储上的收益，也是后面讲 registry 只传缺失层的基础。

层数也有现实成本。overlay2 启动容器时要把所有 lower 目录拼进挂载参数，层数太多会让参数变得很长，实践中几十层就该留意；这也是“别把每个命令都写成一条 RUN”的一个理由。

哪些指令会生成层

规则并不复杂：

  • RUN、COPY、ADD 会生成内容层。它们改变文件系统，指令结束时 daemon 把差异打包成一层。
  • FROM 不生成层，它引入基础镜像已有的层。
  • ENV、WORKDIR、CMD、ENTRYPOINT、LABEL、EXPOSE、USER 只修改镜像配置，不产生内容层，在 docker history 里显示为 0 B。
  • 同一条 RUN 里创建又删除的临时文件不会进入层，因为层记录的是指令结束时的差异；但删除来自更低层的文件，只会在当前层留下 whiteout，数据仍留在低层。

最后一条同时解释了两件事：合并 RUN 可以“藏住”中间产物，而把删除单独写成一条 RUN 则毫无作用。后文讲镜像瘦身和安全时还会回到这一点。

构建缓存：一次命中要看三样东西

docker build 从 FROM 开始逐条执行指令，每条指令先算缓存键，再决定复用还是执行。命中要同时满足三个条件：父层一致，也就是上一条指令产生的层与缓存中的相同；指令文本一致，包括参数、顺序和空格，变量展开后的结果也算文本的一部分；对 COPY 和 ADD，被复制文件的内容校验和一致，只看内容，不看修改时间。

任何一条不满足，daemon 就执行这条指令并生成新层。新层的 ID 与旧层不同，后续指令的父层条件随之失效，于是从这一条开始全部重建。所以缓存不是“按文件缓存”，而是“按层缓存”，且是一条链。终端里的 Using cache 与 Running in ... 就是命中与未命中的直接标记。

第三条只对 COPY 和 ADD 生效，而且只计算被复制的那部分文件：COPY package.json ./ 不会因为仓库里其他文件变化而失效，COPY . . 则会。RUN 没有文件校验和，它该不该重跑完全由前两条决定，这正是包管理命令容易踩坑的根源。

这带来一个容易被忽略的后果：命中缓存意味着指令根本没有执行。RUN curl -o /tmp/data.json http://example.com/data 只要指令文本不变，就会永远复用第一次下载的内容，远端数据更新了也不会重新拉；RUN apt-get upgrade 这类指令即使写进 Dockerfile，也会因为缓存而长期不生效。需要每次取新内容时，要么改变指令文本，要么显式用 --no-cache 构建，要么把这一步移到构建之外。

缓存失效链与指令顺序

把开头的事故画成链路就很直观：

flowchart LR
  A[FROM golang:1.8] --> B[COPY 依赖清单]
  B --> C[RUN 安装依赖]
  C --> D[COPY 源码]
  D --> E[RUN 编译]
  E --> F[镜像]

在这条链上，任何一环换了层 ID，右边全部重来。改一行源码命中的是 D，于是 E 必然重跑，这很正常；有问题的是原 Dockerfile 把 COPY . . 排在依赖安装之前，源码一改，B 和 C 也跟着作废，而它们本来与源码无关。

由此得到排指令顺序的唯一原则：变化频率低的放前面，变化频率高的放后面。基础镜像最少变，其次是系统包，再其次是语言依赖清单，然后是依赖安装，最后才是源码和编译。每一层只为它真正依赖的输入负责，不让无关变化穿透到后面。

另一个推论是“贵而稳定”的步骤值得单独成层。下载大包、编译系统库这类操作耗时最长，只要输入稳定，就应该让它尽量靠前，这样日常改代码时它可以一直命中。反过来，调试阶段可以放心用 --no-cache 强制全量，但不要把 --no-cache 写进 CI 的默认参数，那等于放弃了整个缓存体系。

还要注意，缓存是构建机本地的。换一台机器、换一个 CI runner，缓存就是空的，第一次构建必然全量。指令顺序优化的收益主要体现在有热缓存的重复构建上，这也是为什么 CI 要么固定构建机，要么用 --cache-from 预热。

17.05 起 docker build 支持 --cache-from，机制是让 daemon 把指定镜像的历史层当作可用缓存。CI 通常先拉取上一次成功构建的镜像，再执行 docker build --cache-from api:previous -t api:new .；daemon 逐条比对指令，能与旧镜像历史对上的层直接复用。这里有三个前提：旧镜像必须先在本地，所以 pull 不能省；两次构建必须使用同一份基础镜像，否则从 FROM 起就对不上；被复用的层在本地要存在，--cache-from 不会替你下载缺失的中间层。跨机器共享缓存时，这三点经常只做到一半，于是看起来加了参数却没什么效果。

构建上下文与 .dockerignore

docker build . 里的 . 不是“Dockerfile 所在目录”这么简单，它是构建上下文。CLI 会把整个上下文打包成 tar 流发给 daemon，daemon 在服务端解包，COPY 和 ADD 只能从这个上下文里取文件。2017 年的实现是每次构建都完整发送，哪怕所有层都命中缓存，这一步也省不掉。于是上下文大小直接变成每次构建的固定开销：本地 daemon 要走一遍打包，远程 daemon 还要加上网络传输。

一个前端项目里，node_modules 动辄几万个小文件、几百 MB，.git 带着完整历史也不小，再加上构建产物、日志、本地数据库文件，上下文很容易上 GB。结果就是缓存全命中也要等半分钟，构建机的临时目录被撑满。这些文件本来也不会被 COPY 用到，纯属陪跑。

.dockerignore 就是为此存在的，语法接近 .gitignore，放在上下文根目录：

它有两个作用。第一，减小上下文，缩短每次构建的传输与解包时间；第二，防止 COPY . . 把开发依赖、密钥、版本历史带进镜像。第二条更重要：COPY . . 的层校验和覆盖被复制的全部文件，node_modules 里任何一次安装都会让这层失效，而它本来与镜像内容无关，镜像里会重新安装依赖。把 node_modules 排除掉，这一层的校验和才真正只反映源码。

需要强调的是，.dockerignore 不改变 COPY . . 的缓存语义。只要被复制的集合里有一个字节变化，这层还是失效。所以它解决的是“上下文太大”和“不该进镜像的文件”，解决不了“源码在前面导致依赖重装”，后者只能靠调整指令顺序。另外，.dockerignore 要放在上下文根目录而不是 Dockerfile 旁边，用 -f 指定别处的 Dockerfile 时尤其容易搞错。

用多阶段构建把工具链留在构建阶段

Docker 17.05 在 2017 年 5 月引入了多阶段构建，本文写作时 17.06 刚发布，17.05 已经可用，但不少团队还停在 17.03，所以下面也给旧版本的替代方案。

第一条 FROM 起名为 builder，编译工具链、vendor、源码和中间产物都留在这一阶段；第二条 FROM 从 alpine 重新开始，只复制编译好的二进制。最终镜像里没有 Go 工具链，没有 vendor，也没有源码。COPY --from 也可以写阶段序号，例如 COPY --from=0，但起名更清楚，阶段多了也不容易数错。

体积对比可以看一个示例项目：构建阶段基于 golang:1.8，加上 vendor 和工具链约 700 MB；最终镜像基于 alpine:3.6，加上二进制和 CA 证书约 20 MB。这两个数字只是示例量级，真实项目因依赖而异，但差距的方向是一致的：编译环境通常比运行时大一个数量级以上。层数也从十几层降到四五层，docker history 一眼能看完。

停在 17.03 的团队没有 COPY --from，常见做法是两段 Dockerfile：第一段负责编译，把二进制输出到挂载的卷或宿主机目录；第二段从零开始，只复制二进制。这要求 CI 里多一步 docker run -v 或 docker cp，麻烦但效果接近。另一种偷懒写法是 FROM builder 之后再删文件，工具链仍然留在下层，体积减不下来，不建议。

17.05 同时给 docker build 加了 --target，可以只构建到指定阶段。CI 里先 docker build --target builder 验证编译是否通过，再完整构建一次最终镜像，能避免在同一个 Dockerfile 上反复试错；本地调试也常用它停在 builder 阶段，进容器检查编译环境。阶段命名因此不只是可读性问题，它还是构建入口的名字。

多阶段也有坑。alpine 用 musl libc，如果二进制依赖 cgo 或动态链接，复制过去会跑不起来，所以示例里显式写了 CGO_ENABLED=0。运行阶段还需要 CA 证书、时区数据这类东西，alpine 默认很精简，得自己补。调试时可以在 builder 阶段保留符号表，最终阶段用 -ldflags "-s -w" 减小体积，代价是 panic 栈的信息会少一些。

层复用、registry 与 digest

镜像分层不只省本地磁盘，也省网络。registry 里每个镜像由 manifest 描述，manifest 列出配置 blob 和各层 blob 的 digest；客户端 push 时先问 registry 哪些 blob 已经存在，只上传缺的那些，所以给已有基础镜像的新镜像打标签时，日志里会大量出现 Layer already exists。pull 同理，本地已有的层直接跳过。一个团队统一基础镜像的收益就在这里：十个服务共用同一个 node:6.10 或 alpine:3.6，所有构建机上这些层只有一份，推拉时也只传业务层。

这也解释了为什么“每个服务一个定制基础镜像”很浪费。一旦每个基础镜像都从不同起点各自构建，层就没法共享，registry 存储和发布带宽都会放大。更好的做法是把公共部分收敛成少量基础镜像，并且尽量从官方镜像直接派生，而不是各自从 ubuntu 开始装一遍。

tag 与 digest 的关系则经常被混淆。tag 是一个可变的指针，api:latest 今天指向 A，明天可以被指向 B；digest 是 manifest 内容的哈希，内容不变 digest 就不变。docker pull api@sha256:... 拉到的永远是那一份内容，而 docker pull api:latest 拉到什么取决于 registry 当时的状态。发布记录、compose 文件、部署脚本里如果只写 tag，回滚时很可能拿到的已经不是当初那个镜像。

2017 年很多团队用 latest 加 Git 提交短哈希的双标签，前者给人看，后者用于追溯，但两者都还是 tag。更稳妥的做法是构建完成后记录 docker inspect --format='{{index .RepoDigests 0}}' 的输出，把它写进发布单，或者在部署配置里直接用 digest 引用。tag 漂移的典型症状是“同一份配置在两台机器上跑出不同行为”，以及本地缓存与远端不一致时反复拉取同一个标签。

另外，删除 tag 并不会立刻删除 blob，registry 只在垃圾回收时才可能释放空间。这意味着误推的镜像即使删了标签，层数据可能还在，安全事件里要按“已经泄露”处理，而不是删个标签就结束。

体积、安全与清理

找到大层

docker images 看总量，注意共享层会被重复计数；docker system df 看真实占用和可回收空间；docker history 从下往上看每一层新增了多少。找大层时按 SIZE 排序，重点看两类：安装系统包或编译工具的层，以及把构建产物或数据文件复制进来的层。

常见的浪费有几种：apt 索引没清、编译头文件和静态库留在镜像里、COPY . . 把测试数据和日志带进来、在镜像里解压了安装包却没删压缩包。处理原则是“同一个 RUN 里产生、在同一个 RUN 里清理”，因为跨层删除只会留下 whiteout，空间并不会回来。

合并 RUN 的取舍

合并能减少层数、隐藏中间产物，但也会让缓存粒度变粗：一条 RUN 里任何一步的输入变化，整条都要重跑。笔者的经验是围绕“稳定边界”合并：系统包安装加清理合成一条，语言依赖安装合成一条，不要把依赖安装和源码编译合并——前者稳定、后者频繁，合在一起等于每次改代码都重装依赖。层数不是越少越好，可缓存性和可读性也要算进去。

Docker 1.13 起还提供了实验性的 --squash，需要 daemon 以实验模式启动，构建时把所有层压成一层。它能把中间产物和删除痕迹真正抹掉，适合对层数极度敏感的场景；代价是失去层共享，基础层无法与其他镜像复用，推送时每次都要传一个更大的 blob，缓存也只能整体命中或整体失效。2017 年它仍是实验特性，不适合作为常规发布流程的默认选项。

层里的秘密删不掉

安全上最反直觉的一点是：在后面的层里删除文件，文件仍然留在前面的层里。RUN rm /app/config/prod.key 只是在当前层写了一条 whiteout，docker save 把镜像导出成 tar，逐层解开就能在低层找到原文件。同理，ENV API_TOKEN=... 会写进镜像配置，docker history --no-trunc 直接能看到；RUN curl -H "Authorization: ..." 也会留在构建历史里。

补救只有一条可靠路径：重建镜像，确保敏感内容从未进入任何一层，然后立刻轮换泄露的凭据。镜像可能已经被推到 registry、被拉到别人的机器上，删除标签不等于收回。多阶段构建能帮上忙：把需要密钥的步骤放在 builder 阶段，最终镜像不复制相关文件；但 builder 阶段的层仍留在构建机缓存里，CI 机器必须视为不可信环境。运行时注入环境变量或挂载文件，比把密钥烘焙进镜像安全，2017 年可选的密钥管理方案还比较有限，至少要做到镜像里不放长期凭据。

清理的边界

本地清理的常规手段是 docker system prune，它会删除停止的容器、悬空镜像和未使用的网络；配合 docker rmi $(docker images -f "dangling=true" -q) 处理悬空层，用 docker system df 对比清理前后的变化。不要直接删 /var/lib/docker 下的目录，除非确定要重建整个 daemon 的存储。

CI 构建机的磁盘治理要单独说：构建缓存、旧镜像、日志会持续增长，一台跑几十个项目的构建机几周就能满。可行做法是每次构建前执行一次 docker system prune -f，把基础镜像固定保留，构建完只保留最近若干次产物；把构建机和发布机分开，避免清理动作影响正在运行的容器；对磁盘使用率做监控告警。缓存全清会让下一次构建变慢，所以要在磁盘安全和构建速度之间定一个阈值，例如使用率超过八成再清。

小结

把全文的因果压缩成一张表：

现象 原因 改法
改一行源码，依赖全部重装 复制源码排在依赖安装之前 先复制清单并安装，再复制源码
每一步都命中，构建仍然很慢 上下文带上了 node_modules、.git 用 .dockerignore 缩小上下文
apt-get install 报 404 update 层被缓存，索引过期 update、install、清理合并成一条 RUN
镜像接近 1 GB 工具链、vendor、源码进了最终镜像 多阶段构建，只复制产物
删掉的密钥仍能被找到 删除只写 whiteout，低层数据还在 重建镜像并轮换凭据
两台机器上同一 tag 行为不同 tag 漂移 发布记录固定 digest
构建机磁盘告警 缓存、悬空镜像、旧标签堆积 定期 prune，构建与运行分离

镜像的层不是抽象概念，它决定了缓存的粒度、传输的单位和泄露的边界。把 Dockerfile 当成一条从稳定到易变的流水线来排，把依赖清单当成稳定边界，把源码和编译放在末尾，大部分构建慢的问题都会消失。多阶段构建则把“构建需要什么”和“运行需要什么”分开，这既是体积问题，也是安全问题。最后记住两句话：缓存是链式的，任何一环变化都会让后面重来；删除不等于消失，层会记住你放进去过什么。
