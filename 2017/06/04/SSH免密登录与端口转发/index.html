SSH 免密登录与端口转发

每天早上坐到工位，第一件事是打开终端：先 ssh 到跳板机，再从跳板机 ssh 到测试机；改完接口想看数据，又得开一个窗口连数据库，密码再输一遍。一天下来，十几个窗口排在那里，输密码的次数比敲 git status 还多。更麻烦的是，那台 MySQL 只监听内网的 3306，从家里的笔记本、从本机的图形化客户端，根本连不上，只能登到服务器上用命令行查。这两件事其实是同一个问题的两面：一是凭证怎么证明，二是网络怎么抵达。本文先把密钥认证理顺，再讲清楚 SSH 自带的几种隧道，最后给出一张按需求查命令的对照表。适合已经会用 ssh 登录、但还停留在“每次输密码”阶段的读者。

从密码到密钥对

密码登录的问题不只是麻烦。密码要在网络上传输（虽然有加密信道保护），服务器上存的是可被撞库的哈希，团队里共用一套密码更是常态，谁走了都不知道该改哪一台。密钥认证换了一个思路：验证的不是“你知道什么”，而是“你手里有什么”。

一对密钥由两部分组成：私钥和公钥。私钥留在自己的机器上，永远不出门；公钥可以随便给，贴到任何一台你想登录的服务器上。登录时服务器发一段随机数据，客户端用私钥签名，服务器用事先存好的公钥验签。私钥本身不会在网络上传递，服务器拿到的也只是签名结果，所以即使某一台服务器被攻破，攻击者也拿不到能登录其他机器的东西。

目录与文件的权限是这里唯一的硬性约束：~/.ssh 必须是 700，私钥 600，authorized_keys 600。权限过宽时 sshd 会直接拒绝认证，而不是打个招呼继续，具体现象放到故障一节再说。权限本身的含义在《Linux 用户、组与权限管理》里已经讲过，这里只把它当成一个必须满足的前置条件。

用 config 文件管住一堆环境

机器一多，命令行就会变得没法看：端口是 2222 的、用户是 deploy 的、密钥是另一个文件的，每次都要把参数拼对。OpenSSH 允许把这些东西写进 ~/.ssh/config，之后一个短别名就能代表一整串参数。

配置好之后 ssh db-test 等价于原来那一长串。Host 后面可以写通配符，比如 Host 10.20.* 给整个网段套一组默认值；同一个参数在多处出现时，OpenSSH 取最先匹配到的那个值，所以具体的 Host 段要写在 Host * 前面。多环境常见的做法是按前缀分组，dev-、staging-、prod- 各一段，把用户和端口固定下来，再给生产环境单独指定一把密钥，避免顺手拿测试密钥去连生产。

这里唯一需要斟酌的是 StrictHostKeyChecking。它默认是 ask，第一次连接会打印服务器指纹让你确认，确认后写进 known_hosts，之后指纹变了就拒绝连接。有人为了省事把它设成 no，代价是彻底放弃了中间人攻击的防线：任何能劫持 DNS 的人都可以冒充你的服务器。笔者的建议是公网机器保持默认，只有在频繁重建的测试容器、一次性的 CI 环境里才关掉。至于重装机器后出现的指纹冲突，用 ssh-keygen -R 主机名 删掉旧记录再连即可，不要养成直接删整个 known_hosts 的习惯。

ssh-agent 与密钥口令

给私钥加上口令是值得的：笔记本丢了，捡到的人至少不能直接拿走你的所有服务器。但口令一加，每次登录又要输一遍，等于把密码换了个名字。ssh-agent 解决的就是这个矛盾：它在内存里保管解密后的私钥，其他程序通过一个 Unix socket 请它代为签名，私钥本身始终不落到磁盘上。

eval 是必需的，因为 ssh-agent 自己只打印环境变量赋值语句，要由当前 shell 执行才会生效。这也意味着 agent 的生命周期跟着登录会话走，关掉终端再开一个，通常要重新 ssh-add。

再进一步是 agent forwarding，也就是 ssh -A 或配置里的 ForwardAgent yes。它把本地的 agent socket 转发到远端，于是你在跳板机上可以直接 ssh 到后面的机器，用的还是本地那把钥匙，中间机器上没有私钥文件。听起来很美，风险也很实在：远端只要有 root 权限，就能通过那个 socket 让 agent 替你签名，等于借你的身份登录所有信任这把钥匙的机器。所以只在自己完全掌控的跳板机上开，别对着客户的机器、也别对着多人共用的堡垒机随手 -A。

本地端口转发：把远端服务搬到本地

密钥解决了“怎么进去”，隧道解决“怎么够得着”。本地转发是最常用的一种：把远端某台机器上的端口，映射到本地的一个端口上。

远程端口转发：把本地服务推到远端

本地转发是“拉”，远程转发是“推”。假设你在本机 3000 端口跑了一个刚写完的服务，想给外网的同事看一眼，但机器在 NAT 后面没有公网地址；手上恰好有一台公网 VPS，就可以反过来借它的端口。

此时在 VPS 上访问 http://127.0.0.1:9000，看到的其实是本机 3000 端口的页面。默认情况下 GatewayPorts 是 no，VPS 只在回环地址上监听，所以外网仍然访问不到；如果确实要对外开放，需要在 VPS 的 sshd_config 里设 GatewayPorts yes，同时想清楚这个端口暴露的是什么。这是内网穿透最小的方案：不用装额外软件，不用在防火墙上开口，只要有任意一台能 ssh 的公网机器。代价是它依赖这条 SSH 连接活着，连接一断端口就没了，稳定性要靠下一节的保活来补。VPN 当然也能解决同类问题，但那是一整套网络改造，为了临时看一个页面并不划算。

保活与断线重连

隧道最怕的不是建不起来，而是悄无声息地断掉。中间经过 NAT 或防火墙时，空闲几分钟的连接会被会话表清掉，本地却仍然以为隧道还在，直到某次查询卡住才发现。要区分两个层次的保活：TCP 层的 TCPKeepAlive 默认是开的，但它发出的探测包可能被中间设备直接丢弃，而且它判断的是链路，不是 SSH 会话；更可靠的是 SSH 协议层的 ServerAliveInterval，客户端每隔若干秒发一个加密的探测包，连续几次没有回应就主动断开，至少不会让你对着一个假活的连接发呆。

这三个值合起来的意思是：每 60 秒探一次，连续 3 次无响应就判定断开，最多容忍三分钟。放在 Host * 里对全部主机生效，对经常挂着的隧道尤其必要。

安全边界与常见故障

密钥认证把风险集中到了一处：私钥。所以第一条规矩是私钥永远不外发，一人一对，共享账号的 authorized_keys 里按人追加，离职时删掉对应那一行。给自动化任务用的密钥可以在行首加限制：

from= 限定来源网段，command= 把这把钥匙锁死为只跑一个脚本，转发能力也一并关掉。这样即使文件泄露，能做的事也有限。服务端再把 PasswordAuthentication 设为 no，爆破面直接消失；配一句 fail2ban 挡掉反复试错的 IP 即可。改配置前先确认密钥能登，改完另开窗口验证。

Permission denied (publickey) 是最常见的报错，排查顺序是：先 ssh -v 看客户端提供了哪把钥匙、服务端接受了哪些算法；再查用户名与家目录是否正确、authorized_keys 内容是否完整、目录 700 与文件 600 是否满足、StrictModes 是否拦下、SELinux 上下文是否对（restorecon -R ~/.ssh）、PubkeyAuthentication 是否被关、config 里的 IdentityFile 是否指错。服务端日志在 /var/log/secure 或 journalctl -u sshd 里。端口冲突看 ss -lntp；隧道报 administratively prohibited，多半是服务端设了 AllowTcpForwarding no。

小结

密钥解决身份，隧道解决可达性，配置文件和 agent 解决日常的顺手程度。把这四件事分开看，很多“ssh 又连不上了”的问题就能按层定位。下表按需求归档，命令中的地址与端口按自己的环境替换。
