Docker 与 Jenkins 持续集成

本文属于《Docker 与 Kubernetes》第 17/51 篇
上一篇系列目录下一篇

每次发版，我们都要在本地敲一遍构建命令，再把镜像传到服务器，最后登录机器重启容器。三步本身都不复杂，复杂的是它们之间没有任何记录：谁在什么时候构建了什么，失败在哪一步，出了问题该退回哪个版本，全靠人记。本文把这条手工链路改造成一条 Jenkins 流水线，重点讲清楚 Jenkins 与 Docker 结合的两种方式、镜像构建与推送、部署回滚以及常见故障。读者不需要事先了解 Jenkins Pipeline，但应当用过基本的 Docker 命令。

从三步手工发版说起

我们的服务不多，一个后端 API、一个前端静态站，外加两个定时任务。发版流程写在内部 wiki 上，一共三步：

  1. 在项目目录执行 docker build -t api:latest .；
  2. 把镜像 docker save 成 tar 包，用 scp 传到目标机，或者在有外网的机器上 docker push；
  3. ssh 登录目标机，docker pull 之后 docker run 重启容器。

这三步单独看都很简单，连起来却总有一处会被漏掉。有一次构建完忘了推送，目标机拉到的还是上周的镜像，重启后页面毫无变化，排查了半小时才发现问题不在代码；还有一次直接覆盖了 latest，第二天要回滚时，上一个可用的镜像已经被新的覆盖，只能临时从备份机里找。更麻烦的是，这些操作只留在终端历史里，换个人接手很难还原当时做了什么。

把流程固化成流水线，要解决的不是“少敲几条命令”，而是三件事。第一是可重复：同样的提交，任何人触发都得到同样的镜像，构建参数、基础镜像、环境变量都写在仓库里。第二是可追溯：每个镜像都能对应到具体的 commit，日志里能看到每一步的耗时与输出。第三是可中断：某一步失败就停下来，不要带着半成品继续往下走，更不要在生产机上“先试试看”。

流水线的边界也要提前想清楚。构建、测试、打 tag、推送仓库属于持续集成，登录目标机替换容器属于持续部署，两者可以放在一条流水线里，也可以拆开，用人工确认隔开。本文先把它们串成一条，再在最后讨论哪些环节应该加闸门。

Jenkins 2 与 Declarative Pipeline

2017 年上半年，Jenkins 2.x 的 LTS 版本在 2.46 附近，Pipeline 已经是内置推荐能力。它提供两种写法：Scripted Pipeline 本质上是一段 Groovy 脚本，灵活但容易写成一团；Declarative Pipeline 用固定的段落描述流水线，结构清晰，2017 年的 1.2 版本已经支持 environment、post、parallel 等常用能力，足够覆盖中小团队的场景。本文统一使用后者。

Pipeline 的第一个变化是把 Jenkinsfile 放进代码仓库。过去任务配置躺在 Jenkins 的网页表单里，改一个构建参数要登录服务器，评审时也看不到差异；现在流水线和业务代码一起提交、一起 review，分支切换时流水线也跟着切换。第二个变化是 Jenkinsfile 本身有了稳定结构：

pipeline 是整条流水线的外壳，agent 指定在哪里执行，stages 里按顺序排列阶段，每个 stage 的 steps 才是真正执行的命令。post 用来做收尾，无论成功失败都会走到这里，适合归档产物、清理临时文件、发送通知。options 里的 timestamps() 让每行日志带上时间，排查“卡在哪一步”时非常有用；buildDiscarder 限制历史构建数量，避免 Jenkins 自己的磁盘先被日志撑满。

需要提醒的是，Declarative Pipeline 1.2 的表达能力仍然有限。复杂的条件判断、循环生成 stage，往往要退回 script { } 块里写 Groovy。但要有节制：script 块一旦超过十几行，流水线又成了难以评审的脚本，不如把逻辑抽到仓库的 shell 脚本里，Jenkinsfile 只负责编排。

Jenkins 里的两种 Docker 用法

“用 Docker 跑 Jenkins”这句话很容易被混为一谈，实际上有两种完全不同的用法，目的和风险都不一样。

第一种是让 Jenkins 本身跑在容器里。docker run 启动一个 Jenkins 容器，把 jenkins_home 挂出来持久化配置与构建历史，再暴露 8080 端口。这样做的好处是安装简单、升级方便，坏处是 Jenkins 容器会长期驻留，里面的工具链需要自己维护，构建产生的缓存也会落在卷里。它解决的是“Jenkins 装在哪”，不解决“构建环境是否干净”。

第二种是让构建步骤跑在容器里。每一次构建启动一个临时容器，在容器内执行 npm test、mvn package 之类的命令，结束后容器销毁。它解决的是“构建环境是否一致”：项目 A 需要 Node 6，项目 B 需要 JDK 8，不必在同一台构建机上反复升降级，也不会出现“我这里能跑”的差异。代码仓库里通常会放一个构建镜像的 Dockerfile，Jenkins 只负责 docker run 它。

这两种用法可以并存：Jenkins 自己跑在容器里，构建步骤再用 docker run 启动另一个容器。但后者才是隔离的来源。把 Jenkins 放进容器，并不会让构建步骤获得隔离；如果直接在 Jenkins 容器里执行 npm test，用的仍是长期驻留的环境。

本文重点讲第二种。至于 Jenkins 容器本身的镜像与卷，属于部署 Jenkins 的范畴，这里不展开。

代价是权限。挂载 docker.sock 等于把宿主机的 Docker 守护进程交给容器，而 Docker 守护进程默认以 root 运行，能通过它启动一个挂载宿主机根目录的容器，再读写任意文件。换句话说，能改 Jenkinsfile 的人，基本等同于拿到了构建机的 root。如果仓库允许所有人合并请求，构建机就可能被当作跳板。

因此要把这条边界守好：Jenkins 只部署在专用构建机上，不和生产服务混跑；仓库的合并权限收紧到少数人；构建机上不存放生产环境的私钥；发现异常镜像或容器及时清理。常见的小坑是用户 ID 不一致，容器里的 jenkins 用户没有权限访问套接字，日志里会报 permission denied while trying to connect to the Docker daemon socket。把该用户加入宿主机的 docker 组可以解决，但这同样等于授予 root 权限，只应在专用构建机上做。CentOS 7 开了 SELinux 时，挂载卷还需要加 :z 标签，否则容器内读写会被拒绝。

方式二：Docker-in-Docker

当构建环境不允许挂载宿主机套接字时，另一种做法是 Docker-in-Docker，简称 dind：在容器里再启动一个完整的 Docker 守护进程，构建命令连接这个内层守护进程。2017 年常用的组合是启动一个 docker:17.05-dind 容器，再让 Jenkins 通过 DOCKER_HOST 连过去：

--privileged 是 dind 的硬性前提。内层守护进程要创建命名空间、挂载文件系统、操作网络设备，没有特权模式基本起不来。这带来的问题是：容器的隔离几乎被拆掉，它可以访问宿主机的设备，也可以看到宿主机的很多内核信息。为了让构建“更隔离”而选择 dind，结果却运行了一个特权容器，这个矛盾要先想明白。

第二个代价是缓存。dind 的镜像与层存放在它自己的 /var/lib/docker 里，容器一删就全没了；即使挂载了卷，卷也会随着构建次数膨胀，且多个构建共用时容易互相干扰。首次构建要重新拉基础镜像、装依赖，时间从几分钟变成十几分钟；网络受限时还会卡在拉取。

所以 dind 更适合托管型 CI 或无法触碰宿主机守护进程的场景。自有构建机上，挂载套接字通常更简单，缓存也更好管理。无论选哪种，都要把构建机当作一次性资源来设计：上面不放持久数据，坏了可以重建。

镜像的构建过程应当完全由仓库描述。Dockerfile 跟着代码走，基础镜像、依赖安装、启动命令都在里面，Jenkins 只传参数：

--build-arg 适合放构建期的非敏感参数，例如 npm 源地址、编译开关、构建序号。它不适合放密码：构建参数会留在镜像历史里，docker history 能看到。运行期配置应通过环境变量或挂载文件传入。

tag 的策略决定了回滚是否可行。我们的做法是每次构建打两个 tag：一个是 commit 的短 sha，形如 a1b2c3d，它是不可变的，部署和回滚都以它为准；另一个是分支名，方便人查找，但会被后续构建覆盖。latest 只在测试环境图省事时使用，绝不作为生产部署的依据。分支名里如果带斜杠，例如 feature/login，不能直接当 tag 用，需要替换成 feature-login 之类的形式。

推送之前要先登录私有仓库。Harbor 和官方 Registry 的登录命令一样，都是 docker login，区别主要在权限模型与界面，搭建过程不在本文范围内。凭据不要写进 Jenkinsfile，而是交给 Jenkins 的凭据管理：在系统设置里添加用户名密码类型的凭据，赋予合适的作用域，流水线通过 withCredentials 绑定到环境变量：

withCredentials 的作用域仅限于代码块内部，块外的步骤拿不到这两个变量。Jenkins 会在日志里把凭据值替换成掩码，但掩码只匹配原样字符串，一旦密码被 base64、拼接或写入文件，就可能原样打印出来。因此脚本里不要 echo 密码，不要 set -x，也不要把 docker login 的配置文件复制到工作区。凭据按团队或项目划分作用域，避免一个仓库的凭据被另一个仓库引用。

缓存、磁盘与并发

镜像层缓存能不能命中，取决于 Dockerfile 的指令顺序。把 COPY package.json 放在 COPY . . 之前，依赖没有变化时 npm install 那一层就能复用；反过来，任何一次源码改动都会让依赖重装。缓存也不是越多越好，构建机跑上几个月，悬空镜像和构建缓存能占满整个磁盘，随后构建会在 no space left on device 处失败。用 crontab 每周执行一次 docker system prune -f，并定期清理 Jenkins 的旧工作区，比磁盘告警后再救火可靠。

并发是另一个容易忽略的问题。两个分支同时构建，可能同时推送同名的分支 tag，后完成的覆盖先完成的；如果部署阶段也并发，两个 docker run 会抢同一个容器名和端口。对部署任务加锁，或者直接用 options { disableConcurrentBuilds() } 禁止同一任务并发，都能避免这类竞争。真正用于部署的 tag 必须是 commit sha，这样即使分支 tag 被覆盖，已发布的版本仍然可定位。

小结

流水线的价值在于把构建、凭据、部署和回滚变成仓库里可评审的文本。先选对 Docker 用法，再处理缓存与并发，最后用一张表固定每一步的失败动作：

阶段 动作 失败处理
测试 单元测试与静态检查 阻断后续阶段，通知提交者
构建 docker build，打 commit sha tag 保留日志，清理悬空镜像
推送 登录 Harbor 并 push 重试一次，仍失败则停止
部署 拉取、替换容器、健康检查 自动回滚到上一个 tag
确认 input 等待人工批准 超时取消，不部署
