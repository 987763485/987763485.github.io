Go 包管理与工程结构

本文属于《Go 语言与工程》第 13/78 篇
上一篇系列目录下一篇

2017 年初，笔者所在的小组接了一个内部工单系统。最初只有一个人写，图省事，所有代码都堆在 main 包里：main.go 里注册路由，handler.go 里写 HTTP 处理，model.go、db.go、utils.go 依次排开，编译出来就是一个二进制，跑得挺稳。半年后项目交给五个人维护，问题一个接一个冒出来。

先是编译。任何一个人改动 utils.go 里的一个函数，五个人本地都要重新编译整个包，编辑器补全也跟着卡。然后是冲突：五个人改同一个包，合并三天两头打架，代码评审时一个 diff 横跨几百行，谁也说不清改动影响了谁。更麻烦的是依赖：handler.go 调 utils.go 的格式化函数，utils.go 又要读 model.go 里的结构体，等你想把日志单独拆出去，发现它反过来依赖 handler 里的全局变量，包内互相引用成了死结。最后是测试：想给订单逻辑写个单元测试，得先把数据库连接、路由、全局配置全部初始化一遍，跑一次十几秒。

这些问题的共同点是：代码的物理边界和逻辑边界对不上。Go 用包（package）作为编译、测试、可见性的基本单位，包的划分直接决定了五个人能不能并行干活。本文讲的是 GOPATH 时代怎么给多人项目分目录、定边界、管第三方依赖。环境安装、GOROOT 与 GOPATH 的关系、第一个程序怎么跑，前一篇文章《Go 1.8 环境搭建与 GOPATH》已经讲过，这里只用一句话带过：所有代码都住在 $GOPATH/src 下面。下面从 import 路径说起。

GOPATH 与 import 路径：目录就是包

GOPATH 模式下没有“项目根目录”这个概念，只有 $GOPATH/src。一个包的 import 路径，就是它相对于 src 的目录路径。假设团队仓库叫 github.com/acme/order，目录大致如下：

那么 service 包的 import 路径就是 github.com/acme/order/service，internal/store 的路径就是 github.com/acme/order/internal/store。编译器不会去别的地方找：先看当前包附近的 vendor 目录，再把 import 字符串拼到 $GOPATH/src 后面。没有配置文件，没有搜索路径，目录在哪，包就在哪。

这带来两个直接后果。第一，仓库地址就是 import 路径的前缀，github.com 不是装饰品。仓库改名、换组织、迁移到自建 Git 服务，全仓库的 import 都要跟着改，否则 CI 上立刻 cannot find package。第二，fork 别人的库之后如果直接改代码，import 路径仍然是原仓库地址，本地会同时存在两份同名包，改的那份不生效，这是新手最常见的“改了没反应”。

引用名来自包声明，不来自目录名。导入 github.com/acme/order/service 之后，代码里写 service.New()，这个 service 是文件开头 package service 声明的名字。约定上两者保持一致，但目录名允许带连字符（比如 go-redis），包名不允许，所以这类目录里通常声明成 redis，调用时写 redis.NewClient()。第一次见到的人往往对着目录名找半天，不知道 redis 是从哪冒出来的。

还需要记住：一个目录就是一个包，同一目录下所有 .go 文件必须声明同一个包名（_test 后缀的外部测试包除外）；子目录是独立的包，不是“子包”，父包不会自动把子目录里的符号带进来。go get github.com/acme/order/... 里的三个点表示递归处理所有子目录，仅此而已。

标准工程结构：cmd、pkg、internal、api、web、scripts

Go 官方从来没有规定过目录结构，go build 只认包，不认 pkg、cmd 这些名字。它们流行，是社区反复踩坑后达成的共识，可以借用，但不必当成教条，取舍的标准是项目规模和协作方式。

逐个说清楚。cmd/<app>/main.go 是每个可执行程序的入口，一个仓库可以有多个：cmd/api 提供 HTTP 服务，cmd/worker 消费后台任务，cmd/migrate 跑数据库迁移。main 函数应当很薄，只做三件事：解析命令行参数、装配依赖、调用真正的业务入口然后处理退出码。业务逻辑写在 main 里，等于把整个程序锁死在不可 import 的包里。

pkg/ 放“确实要被别的仓库 import”的库代码，比如公司内部通用的金额计算、ID 生成。它的存在前提是有外部消费者，没有外部消费者就不要建这个目录，否则你只是给自己多套了一层路径。internal/ 放业务主体和所有不愿意对外承诺的实现，下面单独讲。

api/ 放协议，不放实现：protobuf 定义、Swagger 文档、错误码表之类。改动 api/ 意味着接口变了，需要评审。web/ 放服务端渲染用的模板和静态资源，如果项目是纯 API，就不需要它。scripts/ 放构建与运维脚本，注意这些脚本不该被任何 Go 代码 import，它们只是同仓库的附属物。

取舍在哪里？五个人的项目，cmd/ 加 internal/ 已经能解决开篇提到的全部问题，pkg/ 等到真的有外部引用再加，api/、web/ 按需。目录层级每多一层，import 路径就长一截，新人理解成本也高一截。

internal：编译器强制的边界

internal 是 Go 工具链里少见的强约束。规则一句话：import 路径中带 internal 的包，只能被该 internal 父目录之下的代码导入。以 github.com/acme/order/internal/store 为例，只有 import 路径以 github.com/acme/order/ 开头的包能导入它；外部项目写 import "github.com/acme/order/internal/store"，编译器直接报错，大意是 use of internal package not allowed。

为什么说它才是真正的边界？因为 pkg/ 也好，命名约定也好，都靠自觉和代码评审；internal 靠编译器，绕不过去。这带来两个实际好处。一是重构自由：internal/store 里的函数签名、结构体字段随便改，不用担心某个外部项目悄悄依赖了它。二是 API 面清晰：仓库里哪些东西是承诺，哪些是随时可变的实现，看目录就知道。

internal 可以嵌套，a/internal/b/internal/c 里的 c 连 a 的其他子目录都进不去，只有 b 能用。判断依据是 import 路径前缀，不是磁盘位置，在 GOPATH 下用符号链接把目录指来指去，也不会改变这个判断。仓库自己的 cmd/ 在父目录之下，所以可以正常导入 internal/；vendor 里第三方依赖的 internal 同样受保护，你没法绕过去调它的私有实现。

但别走极端。把所有东西塞进 internal，等于放弃了对外复用，也等于承认这个仓库永远只服务一个程序。判断标准很简单：这个包有没有可能被别的仓库导入？有可能，放 pkg 并认真设计导出面；没可能，放 internal，给自己留足改动的余地。

包的设计：一个包一个职责

拆包的第一原则是能用一句名词短语说清它是干什么的。store 管持久化，notify 管通知，money 管金额，边界一目了然；如果一句话说不清，或者要用“以及”“还有一些”来补充，那就是该继续拆了。

包名要短。小写、单个单词、不加下划线，调用时写成 order.New() 而不是 order.NewOrderService()。包名已经表达了上下文，类型名里再重复一遍就是口吃。

要特别警惕 utils、common、helper、base 这类名字。它们的问题不在于名字难听，而在于没有职责，于是所有人都往里扔东西：时间格式化、字符串截断、数据库连接、HTTP 封装，最后这个包依赖了项目里几乎所有的类型，而项目里几乎所有包又依赖它。它一旦变动，全仓库重编译；它想引用上层，立刻循环依赖。正确的做法是按领域归位：时间处理进 clock，分页参数进 page，和订单相关的格式化就留在 order 里，哪怕只有十行。

导出面越小越好。新写的函数、类型、字段先小写，等真的有第二个包要用，再改成大写并补上注释。导出就是承诺，承诺越多，以后改动的包袱越重。golint 会提醒你导出的标识符缺注释，这个提醒值得听：写不出注释，往往说明这个导出本来就不该存在。

循环依赖：编译器不让你绕过去

Go 在包级别禁止循环 import，编译时报 import cycle not allowed，没有开关可以关掉。原因不神秘：包是编译单元，也是 init 函数的执行单位，A 依赖 B、B 又依赖 A，初始化顺序就无解了。语言干脆把这条路封死，逼着开发者把依赖方向想清楚。

循环依赖通常不是一开始就有的，而是慢慢长出来的。典型场景是订单创建成功后要发通知：order 包 import notify 调它的函数，后来通知内容需要读取订单详情，notify 又反过来 import order，编译立刻失败。

拆开的办法是接口下沉，也就是依赖倒置。让使用方定义接口，实现方去满足它：

order 不再 import notify，只依赖自己定义的 Notifier；notify 包实现这个方法，也不需要认识 order。最后在 cmd/api/main.go 里把两者装配起来，这就是依赖注入。如果两个包确实要共享一组数据结构，可以把模型下沉到更底层的 domain 包，但要盯紧它，别让 domain 变成下一个垃圾桶。判断依赖方向有个朴素的标准：底层的包不应该知道上层的包存在，箭头要单向。

依赖管理：go get、vendor 与 dep

go get 是 GOPATH 时代的默认安装方式：把仓库克隆到 $GOPATH/src 下对应的路径，再编译安装。它拉的是默认分支的最新提交，没有版本号的概念。今天能编译，明天上游改个函数签名就可能编不过，五个人本地的依赖版本还各不相同，可重现构建无从谈起。

Go 1.5 引入 vendor 目录做实验，1.6 默认开启，到 1.8 已经稳定：编译时优先使用从当前包逐层向上找到的 vendor/，找不到才回 GOPATH。但 vendor 只负责“把代码放进来”，不解决“放哪个版本、怎么更新”，版本锁定要靠 glide 或 dep。需要说明的是，2017 年还没有 modules 这样的官方方案，dep 只是官方在推的实验项目。

以 dep 为例，dep init 扫描 import，生成 Gopkg.toml、Gopkg.lock 并把依赖写入 vendor/；dep ensure 按 lock 还原；dep ensure -add 增加依赖；dep ensure -update 升级。glide 的对应命令是 glide init、glide install、glide up：前两个生成声明并按 lock 还原，up 才会重新解析版本。CI 上只跑 ensure 或 install，跑 up 等于每次构建都赌上游。

vendor 的工作流与入仓取舍

vendor 要不要入仓，团队必须明确表态。入仓的好处是构建不依赖网络，CI 稳定；依赖升级在 diff 里看得见，评审拦得住意外变更。代价是仓库体积变大，升级时 diff 噪音多。不入仓则靠 lock 文件加 CI 缓存，但 2017 年没有官方代理，上游删库或网络抖动都会让构建挂掉。多数团队选择入仓，配套纪律只有一条：vendor 里的改动要么提交进仓库，要么推回上游，不能只留在某个人本地。否则本地能跑、CI 拉下来还是旧代码，排查起来非常费劲。

测试的组织

测试文件与被测包同目录，文件名以 _test.go 结尾，go test ./... 递归执行。同包测试（package order）能碰未导出符号；外部测试（package order_test）只走导出 API，更接近调用方视角，两者可以共存。

internal 包的测试没有特殊规则，测试文件放在该目录里即可；跨包集成测试可以新建 internal/integration 包，它在仓库内，导入 internal 合法。测试数据放同目录的 testdata/，工具链会忽略这个目录。

耗时用例用构建标签隔离：文件顶部写 // +build integration，空一行再写 package，日常 go test ./... 不编译它，需要时用 go test -tags=integration ./...。

构建与发布

构建入口收进 Makefile，把命令固定下来：build 执行 go build -o bin/api ./cmd/api，test 执行 go test ./...，lint 依次跑 gofmt -l、go vet、golint。版本在编译期注入：-ldflags "-X main.version=$(VERSION)"，main 里留一个变量接住，api -version 就能打出编译信息。

发布时交叉编译一句带过：GOOS=linux GOARCH=amd64 go build，产物直接拷到服务器。

常见错误

包名与目录不一致：目录叫 helpers，声明却是 package util，别人 import 后写 util.X，对着目录找不到；编译器不报错，golint 会提示。

main 包被 import：业务写进 cmd/api，别的包只能 import 它来复用，编译器报 is a program, not an importable package。逻辑放 internal，main 只做装配。

相对 import：import "./store" 在当年的工具链里已被排斥，多数情况直接报错；就算编过，别的包也引用不了。

vendor 里改了没提交：本地一切正常，CI 拉下来还是旧版本。改动要么提交，要么推回上游。

目录职责对照

最后把职责压成一张表，贴在 README 里比写在文档里管用。

目录 放什么 不该放什么
cmd/ 各程序的 main，只做装配 业务逻辑、可复用函数
pkg/ 确定被外部导入的库 只在本仓库用的代码
internal/ 业务实现与私有包 需要对外承诺的 API
api/ 协议定义、文档、错误码 具体实现
web/ 模板、静态资源 Go 业务代码
scripts/ 构建、发布、迁移脚本 被 Go 代码 import 的包
testdata/ 测试夹具 会被编译的 .go 文件
vendor/ 锁定版本的依赖 手改后不提交的补丁

小结

包划分解决的是协作边界，不是审美。按职责拆包，用 internal 藏住不承诺的部分，导出面能小则小；依赖保持单向，循环用接口下沉与依赖注入拆开；第三方依赖用 vendor 加 lock 文件锁死。目录可以慢慢长，边界最好从第一天就立住。
