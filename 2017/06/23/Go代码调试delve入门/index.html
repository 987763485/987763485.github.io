Go 代码调试：delve 入门

本文属于《Go 语言与工程》第 15/78 篇
上一篇系列目录下一篇

线上一个后台任务卡住不动，加日志、重新编译、重启，一轮下来问题却不再复现——这类故障靠打印很难查。本文介绍 Go 的源码级调试器 delve：安装、单步、断点、goroutine 与调用栈，再到测试、attach 和远程调试，最后给出它与日志、性能分析的分工。适合会写 Go、但还没系统用过调试器的读者。

卡住的 goroutine 与失效的日志

先看一个真实场景。一个订单对账服务在凌晨跑批，主流程从队列里取任务，交给一组 worker goroutine 处理，结果写进一个带互斥锁的 map。低峰期一直正常，压测到一定并发后，进程会突然不再消费，队列堆积，健康检查却还是通的——因为主 goroutine 卡在 wg.Wait()，HTTP 端口由另一个 goroutine 撑着。

第一反应是加日志。在取任务前后 fmt.Println，在 Lock 和 Unlock 前后各打一行，在写 map 前后打印 key。改完重新编译、发版、重启，盯着终端。结果无非两种：要么问题不复现，要么复现了，日志却只说明某个任务进了处理函数、没出来；至于它卡在锁上还是卡在别处、锁在谁手里、其他 goroutine 在干什么，一概看不到。

日志的局限在这类问题里很明确。它只能证明代码走到过哪里，不能证明此刻停在哪一行；要看新变量就得改代码、重新编译、重启，而重启恰好把现场毁掉；打印本身还会改变时序，让一个只在特定交错下出现的 bug 消失。这次要的不是更多输出，而是把进程按在原地，逐个 goroutine 看它停在哪一行、栈是什么、变量是什么。这是调试器的活。

Linux 上惯用的 gdb 在这里不太好使。Go 有自己的调度器：goroutine 是用户态的，成千上万个 goroutine 复用少量系统线程，栈还会按需增长和搬迁。gdb 只认线程和地址，bt 出来的是 runtime.mcall、runtime.schedule 这类运行时帧，goroutine 的编号、状态、各自的栈都要手工从 runtime 的内部结构里挖。它也不认识 Go 的 string、slice、map、interface，print 一个 map 只能得到两个机器字。想按 goroutine 下断点、想列出所有阻塞的 goroutine，gdb 做不到。

delve 补的正是这一层。它用 ptrace 控制进程，同时读取 Go 二进制里的 DWARF 与 runtime 符号，因此知道每个 goroutine 的 id、状态和栈；命令也按 Go 的概念设计：goroutines 列出全部，goroutine 12 切过去，whatis 看类型。2017 年前后它是社区里最活跃的 Go 调试器，也是 VS Code 的 Go 扩展与 JetBrains Gogland 背后的调试后端。它的边界也要说清楚：delve 看的是某一刻的进程内部状态，回答不了哪个函数最耗 CPU、哪里分配最多，那是 pprof 的领域。

安装与那几道权限门槛

2017 年还是 GOPATH 工作区，delve 用 go get 装：

源码会落在 $GOPATH/src/github.com/delve/delve，可执行文件落在 $GOPATH/bin/dlv。确认 $GOPATH/bin 在 PATH 里，否则下一步只会得到 command not found。当时的 delve 还停留在 0.x，小版本之间命令名和参数都有出入，遇到资料与本机对不上，先 dlv help 看这一版支持什么，别照抄博客。

装完不等于能用。调试器要借操作系统的 ptrace 接口控制另一个进程，而这条路被系统刻意收紧了。Linux 上 kernel.yama.ptrace_scope 默认为 1，只允许跟踪自己的子进程：dlv debug 自己 fork 出被调试程序，没问题；dlv attach 到一个已经在跑的进程，就会得到 operation not permitted。临时放开可以 sudo sysctl -w kernel.yama.ptrace_scope=0，或者直接 sudo 跑 dlv，后者会让调试会话产生的文件属主变成 root，用完记得清理。macOS 从 10.12 起要求调试器有代码签名，没有签名会直接报权限错误，处理办法放在后面的常见问题里。容器里还多一层 seccomp，同样留到 attach 那一节。

断点：文件行、函数与条件

断点有两种下法：按函数名 break main.handle，或者按位置 break main.go:20。位置里的文件名可以用相对包目录的短名，也可以用绝对路径；在 main 包以外的包里调试时，短名偶尔会歧义，写全路径最稳。断点下好之后，breakpoints 列出所有断点及其编号、命中次数和实际位置，clear 2 删掉 2 号，clearall 一次清空。

真正省时间的是条件断点。循环里每次迭代都停一下，人工 continue 几十次，很快就烦了；把条件写进断点，只有满足时才停：

条件的求值发生在命中点，用的是那一帧可见的变量，所以写 t.ID 可以，写一个还没进入作用域的变量会直接报错。它的开销也不能忽略：每次走到这一行都要停下来求值再决定是否中断，循环体很大时会让程序明显变慢，本地调试可以接受，别指望在压测环境里长期挂着。

还有两个细节。行号写在空行、注释或右花括号上时，delve 会把断点挪到最近的一条可执行语句，breakpoints 里显示的位置可能和你写的行号差一两行，这是正常的。想临时让某个断点失效，也就是别的调试器里 disable 的那个动作，当时的版本没有特别顺手的开关，比较稳妥的做法是 clear 掉、需要时再加回来，或者给它加一个更严格的条件。

goroutine：切换、阻塞栈与持锁者

断点命中时，delve 会把整个进程停住，不只是撞上断点的那个 goroutine。这看着像副作用，其实是排查并发问题的前提：停下来之后，所有 goroutine 的位置都还在。goroutines 列出全部，每行给出 id、状态、当前所在位置和创建位置：

状态那一栏是判断的关键。semacquire 表示在等信号量，多半是锁或 WaitGroup；chan receive 表示在等 channel；IO wait 表示在等网络或文件；running 才是真正占着 CPU 的。哪一个是主 goroutine、哪几个在等、已经等了多久，一眼就分出来了。

要看某个 goroutine 的栈，用 goroutine 6 把上下文切过去（早期文档里也写作 switch 6），再 stack；不想切换就用 goroutine 6 bt，直接打印它的栈。栈从下往上看：runtime.gopark → sync.runtime_SemacquireMutex → sync.(*Mutex).Lock → main.handle，底部几帧是运行时的等待机制，靠近顶部、属于自己代码的那一帧才是线索所在。

回到对账服务：主 goroutine 停在 sync.(*WaitGroup).Wait，三个 worker 有两个停在 sync.(*Mutex).Lock，一个停在 main.handle 里 mu.Lock() 与 mu.Unlock() 之间且状态是 running——后者就是持锁者。如果它迟迟不往下走，要么卡在临界区里的某个调用上，要么是死锁的另一半。此时把断点下到那一行，print 它的局部变量，比猜一百行日志都直接。

变量、指针与调用栈

print 接受的是表达式，不只是变量名：print tasks[0].Cost、print len(tasks)、print shared[1]、print cap(tasks) 都能用。切片默认显示类型、长度、容量和底层数组的前几个元素，元素多了就用下标或子切片 print tasks[0:2] 挑着看；map 小的时候会整张打印，几百个 key 的 map 就只取关心的那个键，不存在的键返回零值，不会报错。

指针要分两步看。print &t 得到 *main.Task 类型的地址，print *(&t) 才把结构体展开；print wg 是一个 *sync.WaitGroup 的地址，想看内部字段得 print *wg。嵌套指针一层层解引用即可，但别在已经失效的帧上解引用，拿到的是上一轮循环留下的内存，看着像数据错乱，实际是调试姿势错了。

不确定类型时用 whatis：whatis t 输出 main.Task，whatis shared 输出 map[int]int，whatis wg 输出 *sync.WaitGroup。接口变量尤其需要它——它告诉你接口背后此刻装的到底是什么类型，再去 print 具体字段，能省掉大量类型断言的猜测。当时版本的命令就叫 whatis，别按新版文档去找别的名字。

调用栈方面，stack（简写 bt）打印当前 goroutine 的栈，frame 2 切到第 2 帧，up 和 down 在帧之间上下移动。切过去之后，locals、args、print 都作用于新的帧，这是查“参数在哪儿被改坏”的标准手法：从出错的位置逐帧往上，看每一层拿到的入参。

帧缺失是另一类常见困惑。Go 1.8 的编译器会内联小函数，如果调试的是普通 go build 出来的二进制（dlv attach 的典型场景），被内联的函数不会单独占一帧，对应的局部变量会显示 unreadable 或 optimized out。dlv debug 默认加 -gcflags "-N -l" 就是为了避免这件事；自己构建供调试的二进制时，也记得带上这两个参数。

它要求权限，且会把目标进程的所有线程逐个停住——业务是真的暂停，不是变慢。生产环境要格外克制：只在已从负载均衡摘掉的实例或预发环境上用，提前打招呼，拿到想要的状态就 continue 或 detach。容器里还多两道门：默认 seccomp 配置会拦 ptrace，容器通常也没有 SYS_PTRACE，启动参数得加 --cap-add=SYS_PTRACE --security-opt seccomp=unconfined；docker exec 进去往往连 dlv 都没装，在宿主机上用 nsenter -t <pid> -p 换个 PID 视图可以解决看不到进程的问题，但解决不了能力与 seccomp 的限制。

断点、日志与 pprof 的分工

三种手段解决的不是同一类问题。断点适合确定性的逻辑错误：能本地或预发复现，需要同时看多个变量、调用栈和 goroutine 状态，一次停下来就能问出答案。日志适合并发时序和长周期问题：偶发、难复现、必须长期在线，结构化日志加请求 id，是生产环境唯一能保留现场的手段。pprof 适合统计性问题：哪个函数吃 CPU、哪里分配最多、锁竞争多严重，它回答“哪里多”，不回答“这一次为什么错”。

实际顺序通常是：监控和日志把范围缩到一个函数，本地用测试复现，断点进去看状态；确认是性能问题而不是逻辑问题，再交给 pprof。三者不是替代关系，用错工具的表现也很典型——拿日志猜并发交错，或者拿断点去查 CPU 热点。

常见报错与速查表

macOS 上 could not launch process: operation not permitted 多半是 dlv 没签名。用 codesign -s "dlv-cert" $(which dlv) 签一次，证书取钥匙串里自建的代码签名证书；临时用 sudo 也能绕过，但不推荐，而且每次 go get 重装后都要重签。

Linux 上的 could not attach to pid ...: operation not permitted，先看 kernel.yama.ptrace_scope，再确认容器是不是缺 SYS_PTRACE。

break foo.go:12 提示找不到位置、或者断点永不命中，通常是路径不匹配：delve 记的是编译时的绝对路径，换目录、符号链接、容器内外路径不一致都会对不上。用绝对路径下断点，或 dlv exec 时加 --wd。变量显示 optimized out 则是优化与内联导致，回到 -gcflags "-N -l"。

小结

delve 补上了 gdb 缺的那一层：它理解 goroutine，也理解 Go 的类型。日常最值得练的三件事，是用 dlv debug 单步一遍可疑函数、用 goroutines 找出谁在等锁、用条件断点把失败用例单独拎出来。它替代不了日志与 pprof：线上偶发问题靠日志保留现场，性能问题靠 pprof 统计。把断点留给能停下来的场合，这套工具用起来才舒服。
