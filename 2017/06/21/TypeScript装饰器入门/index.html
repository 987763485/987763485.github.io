TypeScript 装饰器入门

本文属于《TypeScript 学习路线》第 17/74 篇
上一篇系列目录下一篇

装饰器的价值不在于语法好看，而在于它把日志、校验、缓存这类横切逻辑从方法体里挪了出去。本文从 TypeScript 2.3 的写法讲起，逐个拆开四种装饰器的参数与返回值，再落到路由注册与参数校验两个能跑的例子。

从一个被样板代码淹没的类说起

假设我们在维护一个用户服务，类里有三个方法：查询、创建、修改。每个方法开头记一条日志，入口处校验参数，查询还要加一层内存缓存。等功能写完，方法体里真正处理业务的行数只剩下三四行，其余全是 console.time、try/finally、if (!params.id) throw、cache.get(key) 这样的重复段落。

更麻烦的是这些段落长得几乎一样，却只能一段段复制。想统一改日志格式，要翻遍整个文件；想知道哪些方法被缓存过，只能靠命名去猜。我们把这类重复代码叫横切关注点：它们和业务逻辑没有直接关系，却必须出现在每个方法里。

面向对象给出的答案是继承与组合。继承会把类层级绑死，组合又需要在每个方法里手动调一次包装函数，仍然要改方法体。装饰器想解决的就是最后一公里：让包装逻辑写在方法外面，用一行 @log() 挂在方法头上，方法体保持干净。

本文按”怎么写、怎么用”的顺序展开：先看四种装饰器各自拿得到什么，再看装饰器工厂与执行顺序，然后用 reflect-metadata 补上运行时类型信息，最后写一个路由注册和一个参数校验。读完之后，你应该能自己写出可用的方法包装器，也知道这套机制在 2017 年还处在什么状态。

打开实验开关，再看清它的本质

装饰器在 2017 年仍是 ECMAScript 的 stage-2 提案，离进入标准还有距离，语法和语义都改过几轮。TypeScript 从 1.5 起就以实验特性的形式支持它，所以要用就得在 tsconfig.json 里显式打开：

experimentalDecorators 打开语法与转译；emitDecoratorMetadata 让编译器在装饰过的声明上额外写入类型元数据，后面讲依赖注入时会用到。两个开关都带 experimental 前缀，官方的态度很明确：可以用，但别指望它与最终标准一字不差。写作时 TypeScript 2.3 已经稳定，2.4 刚发布，装饰器相关的行为没有变化。命令行下等价的写法是 tsc --experimentalDecorators --emitDecoratorMetadata。

打开开关只是拿到语法。要真正用好，得先接受一句话：装饰器是一个函数，它在类定义时被调用，而不是在实例化时。

@sealed 这一次调用发生在 UserService 这个绑定完成之后，效果相当于把返回值重新赋给类名。TypeScript 会把它编译成 __decorate 辅助函数的调用，产物形状与调用顺序在《TypeScript 编译产物分析》里已经拆过，这里只记住结论：装饰器是类定义阶段的一次性钩子，它拿到的是类、原型、属性名和描述符这些静态对象，拿不到实例。

这也是理解后面四种装饰器的钥匙。它们被调用的时机相同，区别只在于编译器传给它们的参数不同，以及返回值被用在哪里。顺带一提，Angular 2 的组件声明与依赖注入就建立在这套机制上；本文只讲机制本身，不展开框架用法。

类装饰器：拿到构造函数

类装饰器只有一个参数：构造函数。返回值可以是 void，也可以是一个新构造函数，后者会替换掉原来的类。

方法装饰器：包装原方法

方法装饰器收到三个参数，这是最常用的形态。target 在实例方法上是类的原型，静态方法上是构造函数；propertyKey 是方法名，可能是字符串或 symbol；descriptor 是属性描述符，value 就是原方法。返回值可以是新描述符，也可以什么都不返回，此时允许原地修改它。

两个容易踩的点：必须写 original.apply(this, args)，直接用 original(...args) 会丢掉实例上的 this；另外直接改 descriptor.value 最省事，重新拼一个描述符容易漏掉 enumerable 与 configurable，枚举和继承行为会跟着变。

前面的例子已经用过工厂：@withVersion("1.2.0")、@retry(3)。写法就是把装饰器再包一层，外层收配置，内层才是装饰器本身：

@log("user") 与 @log("user", true) 共用同一个工厂，配置留在调用处。工厂在类定义时执行一次，返回的装饰器函数紧接着被调用，两步都发生在 new 之前。

多个装饰器叠加时，顺序问题才会显现。规则是：表达式自上而下求值，装饰器函数自下而上调用。

输出依次是：求值 上、求值 下、求值 参数、求值 类，然后是 调用 参数、调用 下、调用 上、调用 类。参数装饰器先于它所属的方法装饰器被调用，类装饰器永远是最后一个。这个顺序是规范的一部分，写注册逻辑时要依赖它：方法装饰器先把路由信息挂到原型上，类装饰器最后统一读取。

限制与风险

装饰器是编译期语法，不是运行时能力。带 @log() 的源码必须经过 tsc 或 Babel 处理，直接丢给浏览器或 Node 就是语法错误。这也意味着行为取决于转译器，换一条工具链就可能遇到细微差异。上线前最好固定转译器与版本，不要让一半模块走 tsc、一半走 Babel。

Babel 6 的支持不完整。在 Babel 链路里写装饰器，需要 babel-plugin-transform-decorators-legacy，babel-preset-stage-2 里带的就是它。它按旧版语义转译，方法包装能跑通，但 emitDecoratorMetadata 提供的那套元数据拿不到，design:paramtypes 全是空的。项目若依赖 reflect-metadata 做注入，就老实走 tsc；两者混用会出现”测试里能注入、构建后不能”的怪现象。

装饰器只能挂在类上。类声明、方法、属性、访问器、参数都可以，普通函数声明、函数表达式、箭头函数都不行。想在函数上做同样的事，只能手写高阶函数，把包装显式写出来。这条限制来自语法本身，不是实现偷懒。另外，包装后的函数 name 与 length 通常会变，日志里出现 anonymous 不必惊讶。

继承还会让问题更隐蔽：父类原型上的元数据，子类同样读得到，注册逻辑若不区分自身与继承，同一个处理器会被注册两次。这也是前面反复用 getOwnMetadata 的原因。

提案仍在变化。stage-2 意味着语法与语义都还可能调整，装饰器与类字段的先后、描述符如何传递、元数据是否进入标准，都还在讨论之中。experimentalDecorators 里的 experimental 不是谦辞。生产项目用它没问题，但不要把抽象设计得太深，否则标准落地时迁移成本会堆在业务代码里。

还有一条来自实践：装饰器适合日志、鉴权、缓存、校验这类与业务无关的逻辑。涉及业务流程分支的代码不要塞进去，否则调用栈里多出几层包装，出错时的行号与堆栈都对不上，排查成本远高于省下的几行代码。

对照表与小结

把四种形态放在一起，参数个数就是能力边界：

类型 参数 能做什么 不能做什么
类 构造函数 改原型、返回新构造函数、注册元数据 拿实例、拦截方法调用
方法 target、key、descriptor 包装或替换方法、调整描述符 改方法体内部、影响未装饰的调用
属性 target、key 记录元数据、用 defineProperty 改写 读初始值、天然按实例存值
参数 target、key、index 记录参数位置与规则 读取或改变参数值

装饰器把”包装一个方法”从体力活变成了声明。四种形态的参数依次减少，能力也依次减弱：类装饰器能换掉构造函数，方法装饰器只能换掉一次调用，属性和参数装饰器连值都碰不到，只留下元数据。理解这条递减线，就不会拿着属性装饰器去改值，也不会指望参数装饰器完成校验，校验的执行者永远是方法装饰器。

实践上建议从方法装饰器入手。先写日志与重试，确认 this、描述符、异常路径都没被破坏，再考虑元数据与容器。每加一个装饰器都问一句”它必须在类定义时决定吗”，答案是否定的，就写成普通函数更清楚。

装饰器不是越多越好。一个方法上挂五个装饰器时，阅读者要在五个文件之间跳转才能拼出完整行为，成本已经超过它省下的样板代码。把它当成一种受控的语法糖，而不是架构本身。
