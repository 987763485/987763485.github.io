Nginx 安装与静态资源服务

把 npm run build 得到的 dist 目录打成压缩包，附上一句“放到服务器上就行”发给运维，大概是很多前端第一次接触部署的场景。第二天收回来的问题通常很零碎：首页能打开，刷新二级路由却 404；JS 有几百 KB，gzip 却没生效；index.html 被缓存了一个月，发版后用户还在看旧页面。这些问题都不难，但都得在 Nginx 这一层解决。本文从安装讲起，一步步搭出一个能托管静态站点、支持单页应用、缓存与压缩都正确的配置，面向刚接手部署工作的前端与后端同学；环境以 Nginx 1.10/1.11 一代、CentOS 7 与 Ubuntu 16.04 为例。

安装：三条路与各自的取舍

安装 Nginx 大致有三条路，选哪条取决于两件事：能不能接受发行版自带的版本，以及要不要自己控制编译模块。

第一条是发行版包管理器。CentOS 7 的官方源里没有 Nginx，得先启用 EPEL；Ubuntu 16.04 则直接自带。好处是一次到位：systemd 服务、logrotate 配置、SELinux 策略、默认站点目录都替你准备好，systemctl start nginx 就能跑。坏处是版本跟着发行版走，2017 年上半年，EPEL 与 Ubuntu 都还停在 1.10 一代，想要新特性只能等。

第二条是官方源。nginx.org 提供 yum 与 apt 仓库，稳定线与主线分开维护，升级仍走包管理器，能跟到 1.11、1.12 一代。代价是多一个第三方源和签名密钥要维护，而且不能和发行版自带的包混装，否则配置文件会被两套包来回覆盖。

第三条是源码编译。它适合需要特定模块、或者要把 Nginx 装到非标准路径的场景，编译前要准备 pcre、zlib、openssl 的开发包，装完没有 service 文件，升级也得手工重来。

装完之后，先别急着写业务配置，用 nginx -V 看清楚手里这个二进制到底带哪些模块。它会输出版本号和完整的 configure arguments，--with-http_ssl_module、--with-http_gzip_static_module 这些参数在不在，直接决定了后面的 HTTPS 与预压缩能不能用。配置文件改完则用 nginx -t 检查语法，这条命令在生产上应该成为肌肉记忆。源码安装的可执行文件在 /usr/local/nginx/sbin 下，配置与日志也在同一前缀里，和包管理器装出来的路径完全不同，排错前先确认自己操作的是哪一套。至于把 Nginx 放进容器，是另一条部署路径，本文不展开。

目录结构、最小配置与 MIME

Nginx 的配置是分层的：/etc/nginx/nginx.conf 是主文件，里面用 include 把其他文件拼进来。CentOS 系的包默认包含 conf.d/*.conf，Debian 系还多一层 sites-available 与 sites-enabled：站点配置写在 sites-available，再用软链接放进 sites-enabled，启用与停用就是加删链接。两种布局没有优劣，关键是团队内统一，别一半站点在 conf.d、一半在 sites-enabled。日志固定在 /var/log/nginx/ 下，access.log 与 error.log 各一份；默认站点目录，CentOS 是 /usr/share/nginx/html，Ubuntu 是 /var/www/html，里面那个欢迎页可以用来确认安装成功。

MIME 映射藏在主配置的 http 块里：include mime.types 按扩展名查表，default_type application/octet-stream 兜底，charset utf-8 给文本响应补上字符集。少了 mime.types，CSS 与 JS 会以二进制流下载而不是被浏览器解析；charset 缺省只作用于 text/html，需要时可以用 charset_types 把 CSS、JS 也纳入。

root 与 alias：路径怎么拼

这两个指令都用来定位文件，区别只在拼接方式。root 把完整 URI 接在目录后面，alias 用目录替换掉 location 匹配到的前缀。

尾斜杠是 alias 最常见的坑：location 以斜杠结尾而 alias 没写，剩下的 URI 会直接粘到目录名后面，/static/app.css 就变成了 /data/assetsapp.css，日志里只剩 404。反过来，location 没带斜杠、alias 带了，会拼出 /data/assets//app.css，多数系统能容忍双斜杠，但 location 的匹配范围也变成所有以 /static 开头的路径，/static-old 同样会命中。稳妥的写法是两边都带斜杠，并且只在 URI 与磁盘目录不同名时才用 alias；同名场景一律用 root，少一层心智负担。root 也可以写在 server 层由各 location 继承，继承的是目录，不是拼接规则，URI 依旧完整接到目录后面，不会因为 location 变长而缩短。正则 location 里用 alias 还要把捕获组拼进路径，否则替换结果不会如你所愿，日常静态站点很少需要走到这一步。

SPA 的 history 路由兜底

history 模式下，/orders/42 只存在于地址栏，磁盘上没有对应文件，用户一刷新，请求打到 Nginx 就 404。try_files 给这类请求一个统一出口：先看 $uri 有没有同名文件，再看 $uri/ 是不是目录（是的话继续找 index），都不成立就内部跳转到 /index.html，把路由交还给前端。整个过程对浏览器是一次 200，地址栏不变。

兜底要收口，否则某个 JS 改名后，请求会拿到一份 200 的 HTML，浏览器报语法错误，排查方向就被带偏了。接口同理：Nginx 的前缀匹配取最长的那条，把 /api/ 单独指给上游，它就不会被前端路由吞掉。

代理与负载均衡的完整写法见《Nginx 反向代理与负载均衡》，这里只强调边界。还要记得，$uri/ 依赖 index，root 下没有 index.html 时，兜底一样会失效。

缓存与 gzip：只压该压的，只缓存该缓存的

静态站点的缓存策略可以概括成一句话：带内容 hash 的文件名长缓存，入口 HTML 每次协商。构建工具给 JS、CSS 文件名加上 hash 后，内容一变名字就变，可以放心让浏览器存上一个月。expires 30d 会同时生成 Expires 与 Cache-Control: max-age，前者是绝对时间，受客户端时钟影响，后者是相对时间，现代浏览器以 max-age 为准。

这里有两个细节。add_header 在当前层级出现后，上层的 add_header 不再继承，如果 http 块里配过安全响应头，要在 location 里补回来；发布顺序也要配合，先传新的 JS、CSS，最后覆盖 index.html，中间态才不会出现旧页面引用已删除文件的情况。no-cache 不是不缓存，而是每次使用前回源确认，配合 ETag 通常只多一个 304 往返；真正禁止落盘的是 no-store，纯静态站点很少需要。如果站点前面还有 CDN，缓存会多一层决策：public 允许边缘节点保存，s-maxage 专门约束共享缓存；入口 HTML 不适合让 CDN 长期持有，宁可让它多回一次源。

压缩只对文本有意义。gzip on 之后 text/html 默认就会压，不必写进 gzip_types；CSS、JS、JSON、SVG 要显式列出；图片、字体、zip 本身就是压缩格式，再压一遍体积不降反升，还白耗 CPU。

gzip_comp_level 与 worker 数量的取舍属于调优范畴，见《Nginx 配置优化实践》。验证是否生效，用 curl 带上 Accept-Encoding 请求一个 JS，看响应头里有没有 Content-Encoding: gzip 即可。

HTTPS 的最小配置

HTTPS 的最小配置只有三样：证书、私钥、监听 443。证书向 CA 申请，拿到 fullchain 与 key；私钥权限设为 600、属主 root。证书链不完整会让部分安卓机直接报错，crt 文件里要带上中间证书，这一点在浏览器里看不出来，只会在移动端零星出现。

80 的 server 块只做一件事：用 301 把请求连同路径、查询串一起送到 HTTPS。$request_uri 保留原始 URI，比 $uri 更可靠，前者带查询串，后者只有路径。443 的块里关掉 SSLv3，保留 TLS 1.0 到 1.2，2017 年的客户端兼容性还需要这一档；ssl_session_cache 让复用的连接少做一次握手，对静态站点是顺手的收益。

HTTP/2 则要谨慎：较新版本内置了 http_v2 模块，可以在 listen 443 ssl 后面加 http2 参数，但 2017 年是否开启要结合访客浏览器与 CDN 评估，不是必选项。语法上 http2 与 ssl 写在同一行 listen 里，单独再写一行 listen 443 http2 会变成另一个监听。确认全站资源都能走 HTTPS 之后，可以再加一条 Strict-Transport-Security，max-age 先从几分钟试起，确认没有遗漏的 HTTP 资源再逐步加长，设错了回退很麻烦。证书到期前记得续期，换证后先 nginx -t 再 reload，别直接重启，静态站点的连接可以平滑过渡。

403、404、500 的排查顺序

403 先看权限。Nginx 的 worker 以 nginx（CentOS）或 www-data（Ubuntu）身份运行，站点文件要对它有读权限，路径上每一级目录都要有执行权限，文件 644、目录 755 是最省事的组合。CentOS 还要看 SELinux：getenforce 返回 Enforcing 时，放在 /data 下的文件默认没有 httpd_sys_content_t 上下文，chcon 可以临时改，semanage fcontext 加 restorecon 才是重启后仍然有效的做法。

目录里没有 index 又没开 autoindex，访问目录同样是 403，这类 403 在错误日志里往往只有一行 directory index of … is forbidden，很容易和权限问题混淆。权限问题不要用 chmod -R 777 糊过去，静态目录变成全局可写，后患比 403 大。

404 先查真实路径：root 或 alias 拼出来的位置对不对，尾斜杠是否一致，文件是不是传到了旧目录。SPA 项目所有路径都 404，多半是 try_files 没写，或者 index.html 不在 root 下；只影响深层路由的，则要检查兜底是否被更长的 location 截走。

500 先去 error_log 找第一条错误，而不是盯着浏览器。常见原因是 include 的文件被删、rewrite 成环、FastCGI 进程挂掉；上游没起来更多表现为 502，日志里是 connect() failed，按地址和端口逐个确认即可。500 还有一种来源是 try_files 的内部跳转成环，兜底目标又匹配回同一个 location，日志里会写 rewrite or internal redirection cycle。状态码只是结果，错误日志里的第一行才是原因。

上线前的验证与速查表

配置写完不等于上线完成，静态站点至少要过五道检查。第一，nginx -t 必须通过，reload 之后确认 worker 已经换上新配置；第二，用 curl 直接请求服务器 IP 并带上 Host 头，绕过 DNS 与 CDN，确认源站本身是对的；第三，刷新一个深层路由，确认返回 200 且内容是 index.html，再请求一个不存在的 JS，确认它仍然是 404；第四，看响应头里的 Content-Encoding 与 Cache-Control，确认压缩与缓存按预期生效；第五，翻一下 error_log，确认没有权限或路径相关的报错。

连不上和返回错误要分开处理。连不上多半是防火墙没放行，CentOS 7 用 firewall-cmd --add-service=http --permanent 与 --add-service=https，Ubuntu 用 ufw allow 80/tcp 和 ufw allow 443/tcp，放行后重载防火墙；能连上但看到默认欢迎页，则是 server_name 没匹配，请求落到了 default_server，本地用 curl -H "Host: static.example.com" http://127.0.0.1 就能排除 DNS 干扰。

把这几条检查固化成发版脚本里的 curl，比事后凭记忆排查可靠。下面这张表把常见需求、关键配置与易错点放在一起，作为日常速查。

需求 关键配置 常见错误
托管静态目录 root 加 index 目录无读权限、SELinux 上下文不对
站点显示欢迎页 server_name 域名不匹配，落到 default_server
SPA 刷新 404 try_files 兜底 没排除接口与静态资源

还有两条容易忽略的运维习惯：改配置永远先 nginx -t 再 reload，reload 是平滑的，restart 会瞬断；证书、域名、站点目录这类信息写进配置注释，半年后接手的人能少猜很多。发布时先传资源、后传 HTML 的顺序，也值得写进部署脚本，而不是靠人记住。

小结

静态资源服务看起来只是把文件放进目录，真正决定体验的是几个边界：路径拼接、路由兜底、缓存有效期、压缩范围。本文从三种安装方式讲到最小 server 配置，再到 root 与 alias、SPA 兜底、缓存与 gzip、日志、HTTPS 和错误排查，每一块都可以独立验证。初次搭建时建议先用最小配置跑通，再按需求逐条叠加，每加一条就 reload 一次并观察日志。生产环境的连接数、缓冲区、压缩级别属于调优范畴，代理与负载均衡属于另一条链路，分别见《Nginx 配置优化实践》与《Nginx 反向代理与负载均衡》。
