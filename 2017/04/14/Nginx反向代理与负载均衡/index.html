Nginx 反向代理与负载均衡

今年年初，我们把一个日活不高但请求很碎的小系统从单机拆成了两台后端。拆之前想得很简单：Nginx 在前面轮询，后端多一台，容量翻倍。上线当天问题就来了：用户隔几分钟就被踢回登录页，后端日志里所有请求的来源地址都是同一台内网机器，排查时完全分不清真实用户。本文从这次事故出发，讲清 Nginx 反向代理与负载均衡的语义，重点是路径拼接、请求头、失败判断和发布时的行为。阅读前只需了解基本的 HTTP 与 Nginx 配置写法。

从单机到两台后端

最初的架构很朴素：一台 4 核 8G 的机器，Nginx 提供静态文件，Node 进程监听 3000 端口，session 直接存在进程内存里。用户量上来之后，晚高峰的 CPU 经常打满，最简单的办法是再加一台后端。配置改得也很快，在 http 块里声明一个 upstream，把两台机器都放进去，再把原来的 proxy_pass 指向这个组，重载之后看起来一切正常。

问题在第二天集中爆发。用户登录后刷新几次页面，有时正常，有时又回到登录页；同一个用户在不同标签页里的状态甚至不一致。第一反应是会话没有保持，于是加了 ip_hash。办公室用户稳定了，手机用户仍随机掉线，因为移动网络出口地址经常变化。继续查才明白，ip_hash 只是把同一来源固定到同一台后端，没有解决两台后端不共享会话这个根本问题；把 session 挪到 Redis 后，掉线才消失。

第二个问题更隐蔽：后端日志里的 remote_addr 全是 Nginx 的内网地址，按 IP 做的审计和风控全部失效；退出登录后跳到打不开的地址，因为后端用绝对 URL 生成重定向，带着内网主机名和端口。还有一次请求超时后重试，订单表多出一条重复记录。

这四个现象分别对应路径拼接、客户端信息、响应地址和失败重试四条主线，也是后面几节要逐一拆开的部分。

正向代理与反向代理

代理的本质是替别人转发请求，区别在于站在哪一侧、替谁办事。正向代理部署在客户端一侧，客户端明确知道它的存在，并主动把请求交给它；它替客户端去访问目标服务器，目标服务器看到的来源是代理，而不是真正的客户端。公司里统一出网的代理、开发时用 curl -x 指定的代理，都属于这一类。

反向代理则部署在服务端一侧。客户端以为自己访问的就是源站，实际上连接终止在代理上，由代理决定把请求交给哪台后端。客户端不需要任何配置，也无从知道背后有几台机器。Nginx、HAProxy 以及当年的 CDN 回源层，做的都是反向代理的活。

flowchart LR
  U[用户浏览器] --> N[Nginx 反向代理]
  N --> A[后端 10.0.0.21:3000]
  N --> B[后端 10.0.0.22:3000]
  N --> S[静态资源目录]

放在架构里看，反向代理是流量的唯一入口：它先与客户端建立连接，完成 TLS 握手、请求解析和路由判断，再作为客户端向后端发起一条新的连接。对用户来说，Nginx 就是服务器；对后端来说，Nginx 就是唯一的客户。两层连接彼此独立，源地址、协议、超时都随之改变，这正是开篇那些问题的根源。理解反向代理，本质上就是理解这两条连接之间的差异，以及 Nginx 在中间做了哪些补充和改写。

proxy_pass 的路径拼接

proxy_pass 是反向代理最核心的指令，但它的路径规则常被简化成“加不加斜杠”，实际取决于指令里有没有写 URI。写 proxy_pass http://app_backend; 时只给了上游地址，没有 URI，Nginx 会把客户端原始 URI 原样转发；写 proxy_pass http://app_backend/; 时多了一个 /，这个 / 就是 URI，Nginx 会把 location 匹配到的那段前缀替换成它，再把剩余部分接上去。查询串不参与替换，默认原样保留。

以上两种是互斥写法，实际配置只保留一种。如果要把它转到 /v1/users，写成 proxy_pass http://app_backend/v1/; 即可。

真正容易踩的是 location 与 proxy_pass 两侧斜杠不对齐。比如 location 写成 /api/，proxy_pass 却不带斜杠，后端收到的仍然是 /api/users，而后端路由里只有 /users，于是稳定地返回 404；反过来，location 不带斜杠、proxy_pass 带斜杠时，前缀边界对不上，拼接结果可能多出一个斜杠，也可能吃掉一段路径。排查这类问题时，不要盯着配置文件猜，直接在后端把 req.url 打进日志，一眼就能看出 Nginx 到底送来了什么。

实践上建议：location 与 proxy_pass 的尾部斜杠要么都保留，要么都省略，前缀与后端真实路由保持一致；需要去掉 /api 时就明确写带 / 的 URI，并注释映射关系。

请求头、响应头与重定向

Nginx 转发请求时会大体保留客户端发来的头，但有两个关键项会被改写：Host 默认变成 proxy_pass 里的上游主机名，Connection 默认被设为 close。因此后端看到的 Host 往往是 10.0.0.21:3000 这样的内网地址，按域名分站、拼接绝对链接的逻辑都会走偏。客户端地址默认没有传递，后端只能看到 Nginx 的地址。

upstream 把若干后端定义成一个命名组，proxy_pass 指向组名即可，不必把地址散落在各个 location 里。一个带权重和失败判断的配置大致如下：

会话保持的取舍值得单独说。ip_hash 零改造、不依赖外部存储，但分布天然不均：一个出口地址后面可能藏着几百个用户，手机换网就会重新映射，后端下线时这部分会话照样丢失，只能算临时缓解。基于 Cookie 的粘性会话在开源版没有内置指令，需要第三方模块或商业版；共享 session 把状态放到 Redis，任何一台后端都能处理任何请求，扩缩容不受影响，代价是多了一个必须高可用的依赖。条件允许时应优先共享 session。

max_fails 与 fail_timeout 构成一套被动失败判断：在 fail_timeout 时间内失败达到 max_fails 次，这台后端就被标记为不可用，并在接下来的 fail_timeout 内不再接新请求，之后再放行试探。默认值分别是 1 次和 10 秒，内网服务通常可以放宽到 2 次、30 秒，避免偶发抖动就把节点摘掉。需要明确的是，截至 2017 年 4 月，开源版 Nginx 没有主动健康检查，只有这种依赖真实请求的被动摘除；节点恢复后也要等计时窗口结束才会重新尝试，低峰期故障可能很久都发现不了。要主动探测，只能自己写脚本、编译第三方模块，或使用商业版。

失败重试、超时与缓冲

proxy_next_upstream 决定什么情况下把请求交给下一台后端。默认值是 error timeout，也就是连接失败、读超时这类传输层问题才重试；后端明确返回 502、503、504 时，默认并不换机器，因为 Nginx 已经收到了完整响应。若希望这些状态码也触发重试，需要显式写出：

重试不是免费的。最危险的情况是后端已经处理完业务，写库成功，但在返回响应时超时，Nginx 认为这次失败并转发给下一台，下一台再执行一遍，订单或评论就重复了。POST、PATCH 这类非幂等请求默认不会在请求已发出后重试，这是保护机制，不要为了“提高成功率”随手加上 non_idempotent。真需要重试时，应该由业务提供幂等键，并限制重试次数与总耗时。

超时参数里，proxy_connect_timeout 只覆盖与后端建立连接的时间，内网服务设成两三秒足够，默认的 60 秒只会让故障暴露得更慢。proxy_read_timeout 是两次读操作之间的空闲时间，不是整个请求的总时长：一个持续输出数据的接口不会因为总耗时超时，而一个卡住不动的后端会在空闲时间达到阈值时被断开。

proxy_buffering 默认开启。Nginx 会尽快从后端读完响应，放进内存缓冲或临时文件，再按客户端的消费速度发送。这样后端可以尽早释放连接，慢客户端也不会拖住后端，对大文件下载是好事。但它会破坏需要实时到达的响应：SSE 事件被攒在缓冲区里，前端迟迟收不到，看起来像连接没建立。此时要关掉缓冲，并让应用返回 X-Accel-Buffering: no 作为双保险：

大文件下载则通常保留缓冲，同时确保临时目录所在磁盘有足够空间；关闭缓冲会让 Nginx 同步转发，慢客户端会长时间占用工作进程，是否值得要按实际流量权衡。这部分只讨论代理行为，worker 数量、连接复用等更底层的调优不在本文范围内。

多级代理与真实 IP

CDN 到 Nginx 再到后端时，每一层都应追加 X-Forwarded-For。若入口直接用 $proxy_add_x_forwarded_for，客户端自带的伪造值会留在最左边；后端取第一个，就会把攻击者指定的地址当成真实 IP。入口要覆盖而不是追加，内层再追加，后端从右往左跳过已知代理。

real_ip 模块让 $remote_addr 变成真实地址，之后的追加才正确。信任范围只能写 CDN 回源段，并用安全组禁止绕过 CDN 直连源站；信任范围过大等同于允许伪造。

灰度与平滑发布

灰度可以先改权重：新版本 1、旧版本 9，观察错误率后再调。权重是请求级比例，长连接会让单条连接一直落在同一台，实际比例有偏差。down 只影响新请求，存量连接继续。改完先 nginx -t 再 nginx -s reload；reload 启动新 worker，旧 worker 处理完存量连接后退出，普通请求不断，WebSocket 可能滞留很久，要单独处理。

小结

反向代理把一条客户端连接拆成两条独立连接，路径、Host、来源地址、协议和超时都要在中间补齐。负载均衡则在多台后端之间做选择，并把失败、重试和发布纳入同一套规则。先把这些语义写清楚，再谈参数调优，配置才不会在故障时反咬一口。最后把常见需求与对应指令整理成表，便于配置时逐项核对。
