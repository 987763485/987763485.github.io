TypeScript 声明合并与模块扩展

本文属于《TypeScript 学习路线》第 13/74 篇
上一篇系列目录下一篇

给第三方库补一个方法，最省事的做法是打开 node_modules 里那份 .d.ts 直接改一行；最贵的做法也是它——下一次全新安装，改动消失，构建在别人的机器上失败。TypeScript 早就提供了正规路径：声明合并（declaration merging）负责把同名声明拼成一个实体，模块扩展（module augmentation）负责把这份能力用到别人的模块上。本文从一次真实的翻车讲起，拆开五组合并规则、declare module 与 declare global 的生效条件、默认导出为什么扩不上，最后落到发布类型与排错手段。适合已经能在项目里写声明文件、但在”给别人的类型打补丁”时反复踩坑的读者。

这次事故里其实压着两个独立问题：类型从哪来，实现在哪来。手改 node_modules 把两者捆在一起，还顺手把类型焊死在某个版本上：库升级后目录结构一变，你改的那份文件要么被覆盖，要么和新版声明对不上，报错位置还落在 node_modules 里，团队里没人愿意进去看。运行时补的方法则没有类型承载，靠手改声明”骗”过编译器，换台机器就露馅。

正规做法是把扩展写成项目自己的声明文件：先 import 原模块，再在一个 declare module 块里写同名接口。这样安装依赖不会覆盖它，升级库时它还留在仓库里，类型与实现也能分开管理。

这里要先分清两个容易混为一谈的概念。声明合并是编译器对同名声明的一贯处理方式，接口、命名空间、类、函数、枚举都能参与；模块扩展是这套规则在模块上的特例，即在 declare module "x" 里写一个与模块内已有声明同名的接口。前者是机制，后者是用法；分不清这两层，扩展不生效时就容易盲目改写法。

声明合并的五组规则

声明合并不是一个开关，而是编译器处理同名声明的默认行为：同一作用域内出现多个同名声明时，只要种类允许，编译器就把它们当成同一个实体的多个片段，各自贡献一部分成员。理解这套规则，先要分清两个空间。

值空间放运行时真实存在的东西：变量、函数、类构造器、枚举对象、命名空间对象。类型空间放只在编译期存在的名字：接口、类型别名、类型参数。有的声明同时占两个空间：class 既提供构造器这个值，又提供实例类型；enum 既提供对象值，又提供成员类型；namespace 既提供对象值，又提供限定名。合并时两个空间各算各的，互不干扰。

五组常见组合的规则如下。

组合 合并结果 顺序要求
interface + interface 成员叠加，同名方法成为重载 无
namespace + namespace 导出成员叠加 无
class + namespace namespace 的导出成员成为类的静态成员 namespace 必须在后
function + namespace 同上，成员挂在函数对象上 namespace 必须在后
enum + namespace namespace 成员挂到枚举对象上 namespace 必须在后

后三组要求 namespace 写在类、函数、枚举之后，写反了编译器会直接报错，理由是合并后的静态成员需要依附在一个已经存在的值上。

flowchart TD
    A[同一作用域出现同名声明] --> B{占用哪个空间}
    B --> C[仅类型空间 interface 与 type]
    B --> D[仅值空间 const 与 function]
    B --> E[两个空间 class enum namespace]
    C --> F[类型成员叠加 冲突即报错]
    E --> G[值与类型各自合并]

有几类声明不参与合并，值得单独记住。类型别名重复声明会直接报 Duplicate identifier，因为别名是”重命名”而不是”可增长的形状”；同一作用域的 const、let 重复声明同样不允许；export default 导出的东西没有可供引用的名字，也无法用同名声明命中。还有一个前提常被忽略：合并只发生在同一作用域。两个模块文件各写一个 interface Foo，彼此毫无关系；想让它们合并，必须让两份声明落在同一个作用域里，这也正是模块扩展要做的事。

接口合并：成员叠加与重载顺序

接口合并是最常用的一组，规则可以概括成一句话：非函数成员按名字叠加，同名函数成员变成重载，类型对不上就报错。

叠加只解决”多出成员”，不解决”改成员”。同一个非函数成员在两份声明里出现且类型不同，编译器会报 Subsequent property declarations must have the same type。它不会替你挑一个，也不会做联合类型，因为合并的语义是”同一个属性”，而不是”两个候选”。可选性也算类型的一部分：开启 --strictNullChecks 之后，一边写 name: string、另一边写 name?: string 同样冲突。这条规则在模块扩展里尤其重要——你只能补库没有的字段，不能把库已有的 string 改成 string | null。

同名方法走另一条路径：每一份声明里的同名方法都成为重载签名。这里有一个反直觉的细节，后声明的那一组会排在前声明的前面，组内保持书写顺序。假设库里有这样一个接口：

调用签名与构造签名同样按重载合并，索引签名则要求类型相容，两个 [key: string]: number 与 [key: string]: string 放一起会直接报错。泛型接口还有一个约束：合并的各份声明必须拥有一致的类型参数列表，名字和约束都要一致，interface Box<T> 与 interface Box<U extends object> 不能合并。

namespace 合并：跨文件与两个空间

namespace 的基本语法在前文《TypeScript 命名空间与模块》里已经讲过，这里只讨论合并相关的部分。namespace 的合并规则是”导出成员叠加”：多个同名 namespace 的 export 成员合并到同一个对象上，没有 export 的成员只属于它所在的那一份声明，外面看不到，也不参与合并。

这段代码里，Store.Item 是类型，Store.version 与 Store.find 是值。类型空间与值空间在这里分开结算：Store.Item 不能当值用，let x: Store.version 也不成立。namespace 合并时两个空间各自累加，不会因为一边有同名成员就影响另一边。这一点在扩展第三方命名空间时很关键——你能补一个接口，不代表你能补一个同名的常量。

跨文件合并有一个前提：这些文件必须是全局脚本，也就是文件里没有任何顶层 import 或 export。只要加上一句 export {}，文件就成了模块，namespace 被包在模块作用域里，两个文件各有一份 Store，永远不会合并。真正需要跨文件共享类型时，正确做法是模块化导出，而不是继续依赖全局合并。

运行时的顺序问题也值得单独说。每个 namespace 块编译出来是一段立即执行函数，按文件加载顺序依次往同一个对象上挂成员。类型检查阶段编译器知道全部成员，运行时却只知道已经执行过的那部分。如果 a 文件在顶层直接调用 Store.find，而定义 find 的 b 文件排在后面，编译能过，运行时报 Store.find is not a function。类型层面的合并是”全量视图”，运行时的合并是”按序累积”，两者的差异只能靠调用位置来规避：把跨文件的初始化逻辑放进入口文件，等所有 namespace 块执行完再调用。

这段代码每一行都有约束。import "chart-lite"; 看着多余，其实是整段写法成立的前提：它让当前文件成为模块。如果去掉它，文件里没有任何顶层导入导出，就是一个全局脚本，此时 declare module "chart-lite" 的含义会从”扩展已有模块”变成”完整声明一个叫 chart-lite 的模块”。后者会遮住包里自带的类型，import Chart from "chart-lite" 拿到的类型全变成 any，编辑器不报错，检查却全部失效。这是模块扩展第一大坑，而且症状是”太安静”，比报错难查得多。

第二个作用是确定解析基准。declare module 后面的模块名要按模块解析规则找到真实文件：写包名时走 node_modules，写相对路径时相对于当前声明文件，而不是相对于使用方。所以在 src/types/ 下写 declare module "./foo"，找的是 src/types/foo 这个模块，而不是 src/foo.ts。跨目录扩展相对路径模块极易指错，能写包名就不要写相对路径；非要写，先把声明文件放到与目标模块同级的目录。

同样是 "../foo"：声明文件在 src/types/ 下时指向 src/foo.ts，把这个文件挪到 src/types/chart/ 后，同一个字符串就指向 src/types/foo.ts，必须改成 "../../foo"。扩展声明一挪位置就失效，通常就是这个原因。

第三个约束是只能”加”，不能”改”。在块里重新声明 render(): Promise<void> 而库里是 render(): void，得到的是两条互不相容的声明，编译器报后续属性类型不一致。想改已有成员的类型，唯一的办法是改库或换库，模块扩展没有这个能力。

第四个约束是块里的内容会成为模块的一部分，包括新导出的函数。但新增导出只在类型层面成立，运行时不存在的成员照样是 undefined。因此实践上应当把模块扩展严格限制在”补已有接口”和”补可选字段”上，新增可调用成员必须同时有运行时补丁，并且补丁的加载顺序要早于调用。

最后是生效范围：声明文件一旦被纳入编译，扩展对整个程序生效，不分目录、不分模块，代价是影响面变成全局。

全局扩展：declare global 的边界

有些东西不属于任何模块，比如注入到 window 上的配置、给原生原型补的方法。这类扩展要用 declare global：

export {} 依然是让文件成为模块的手段，而 declare global 只能在模块文件里使用。写成全局脚本再写 declare global，编译器会报”全局作用域的扩展只能直接嵌套在外部模块或环境模块声明中”。这条限制的用意是避免自我指涉。

declare global 的位置也有要求，必须直接写在模块顶层，不能塞进 namespace 或函数里。块内可以写接口、类型别名、var 声明，但不能写带初始化的实现，因为环境上下文不允许产生运行时代码。

给 Window 加成员是相对安全的一类扩展：窗口对象只有一个，注入的配置通常在入口脚本里赋值，类型和运行时容易对齐。要注意的是命名。__APP_CONFIG__ 这类带前缀的名字能避开与浏览器新 API 或其他库的冲突；如果写成 config、store 这种通用词，两年后浏览器真加了一个同名属性，你的声明就会和标准库打架。

给 Array、String 这类内置原型加成员，代价高一个量级。第一，运行时必须真的扩展原型，而且要用 Object.defineProperty 把方法设为不可枚举，否则任何 for...in 遍历数组的地方都会多出一个键，老代码里这种遍历并不少见。第二，合并 Array<T> 时类型参数列表必须与标准库一致，写成 interface Array { last(): any } 会直接报类型参数不匹配；写成 interface Array<T> 才合法。第三，所有数组都获得这个方法，包括第三方库内部创建的数组，一旦你的实现有边界问题，影响面是整个应用。第四，未来 TypeScript 的标准库若加入同名成员，升级编译器就会冲突，而错误出现在 lib.es5.d.ts 里，很难一眼看出是自己的声明造成的。

判断标准可以简化成一句：这个成员是否真的属于该类型。给 Window 加注入配置属于”环境补充”，可以接受；给 Array 加 last 属于”改造内置类型”，除非是在写工具库并且有充分测试，否则更应该做成普通函数 last(arr)。类型系统能表达”数组有 last”，不代表应该让它有。

这里只讨论类型侧：合并不会创建任何运行时属性，Vue.prototype.$http 仍要自己挂。风险在于 Vue 是全局共享的实例类型，一旦加上一个必选成员，所有组件都被要求相信它存在，包括那些根本没装插件的测试环境。写成可选成员 $http?: Http 更诚实，调用处用类型守卫收窄，代价是每次都要判空。

顺序、冲突与定位手段

声明合并对书写顺序比较宽容：类型声明可以先使用后声明。真正的顺序约束只有两类。一类是前面提过的 class、function、enum 与 namespace 合并，namespace 必须在后。另一类是运行顺序，类型合并给出的是全量视图，值仍然按文件加载顺序累积，在初始化完成前调用合并进来的静态成员会得到 undefined。

冲突的表现形式很固定。两个同名属性类型不一致，报”后续属性声明必须具有相同的类型”，错误指向后一份声明，根因却常常在第一份——比如 @types 包升级后把某个字段从 string 改成了 string | null，你的扩展还停留在旧类型。

skipLibCheck 会改变你看到的错误。这个 2.0 起提供的选项让编译器跳过所有 .d.ts 文件的类型检查，只检查 .ts。好处是升级依赖时不被第三方声明文件里的互相冲突卡住，坏处是它恰好掩盖了声明合并最典型的故障：两个包在全局声明了同名但不同类型的成员，或者你的扩展与新版库冲突。开启它之后，这些错误消失，使用处的类型却可能悄悄变成 any 或错误的那一支。排查合并问题时应当临时关掉它。

定位”扩展没生效”有一条固定路径。先用 tsc --listFiles --noEmit 确认声明文件是否在编译列表里，不在就检查 tsconfig.json 的 include、files 与 exclude。再用 tsc --traceResolution --noEmit 看模块名解析到了哪个文件，输出里会写明 Module name 'xxx' was successfully resolved to ...，如果解析到的是你自己的空声明而不是包里的 index.d.ts，就说明文件被当成了环境模块声明，缺一个顶层 import。最后打开目标的 .d.ts，确认你要合并的东西真的是 interface，而不是类型别名或匿名对象类型。

发布自己的类型与扩展

扩展如果只在本项目用，放在 src/types/ 并纳入 include 即可。如果要把扩展随插件一起发布，package.json 里的 types 字段必须指向一个真实存在的声明入口：

types 与 main 可以指向不同文件，前者给编译器，后者给 Node。声明入口里不要复制宿主库的类型，而是用副作用导入把扩展挂上去：

这句 import "chart-lite"; 同时解决两个问题：让文件成为模块，从而让 declare module 成为扩展；以及在消费者加载你的类型时，把宿主包的类型一并拉进程序。宿主包要放在 peerDependencies 或 dependencies，不能只放 devDependencies，否则消费者安装后解析不到模块，扩展直接失效。

@types 的边界值得说清。它是给”没有自带类型的包”补声明的公共仓库，不是给”已有类型”的包打补丁的地方。给别人的包做项目级扩展，正确位置是你自己的仓库；即使扩展具有通用价值，提交到 DefinitelyTyped 也通常会被建议改由原库吸收或做成独立插件包。把扩展写进 @types 还会污染所有安装者的全局类型。

常见错误清单

把通配写成万能兜底。 declare module "*" 或 declare module "some-*" 会让所有解析失败的导入静默变成 any，连拼错的模块名也不再报错。通配只该用于 *.vue、*.css 这类资源导入，并且尽量写明后缀。

在脚本文件里写 declare module "lodash"。 文件没有顶层导入导出时，这不是扩展而是完整声明，包里自带的类型被绕过，整个包退化成 any。加一行 import "lodash"; 或 export {}; 即可转换语义。

在 .d.ts 里写实现。 环境上下文不允许函数体和初始化表达式，写了会报”环境上下文中不能声明实现”。

扩展文件没被纳入编译。 放在 types/ 但 include 只写了 src，或者被 exclude 排除，文件等于不存在。

类型有了，运行时没有。 模块扩展不产生任何代码，声明了 setWatermark 不等于实例上有这个方法。发布扩展时要把运行时补丁一并交付。

速查：目标、写法、生效范围与风险

目标 写法 生效范围 风险
给第三方模块的接口补字段 模块内 import 后 declare module "包名" 整个程序 库升级后成员被删或改名
给全局对象补注入值 模块内 declare global 扩 Window 整个程序 命名冲突，需加前缀
改造内置原型 declare global 扩 Array<T> 整个程序与所有库 影响遍历与第三方代码
合并自有命名空间 同名 namespace 叠加导出成员 同一作用域 跨文件仅限全局脚本
无类型包的最小声明 declare module "x"; 该模块全部为 any 整包失去检查
扩展默认导出的库 合并其具名接口，或写包装函数 视目标而定 无目标时静默失效

小结

声明合并是 TypeScript 处理同名声明的基础规则，接口叠成员、方法变重载、namespace 叠导出，各有各的约束。模块扩展把这条规则引到别人的模块上，成立的前提是文件本身是模块、目标确实是可合并的具名声明、扩展文件被纳入编译。默认导出与匿名类型没有合并入口，这时包装函数比硬凑声明更可靠。最后记住一条底线：类型可以合并，运行时不会，任何扩展都要有对应的代码或明确的加载约定。
