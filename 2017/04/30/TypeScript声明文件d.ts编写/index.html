TypeScript 声明文件 d.ts 编写

本文属于《TypeScript 学习路线》第 12/74 篇
上一篇系列目录下一篇

接手一个 2015 年立项的后台项目时，我们遇到的第一件事是：页面里用 script 标签引入的三个库都没有类型声明。图表库 viz-core、日期工具 datefmt，还有一套公司内部的请求封装。TypeScript 把它们全部标成红色波浪线，补全失效，参数写错也没有任何提示。

有人不耐烦，在文件顶部加了一行 declare var viz: any，红线消失了，类型检查也一起消失了。任何属性都能访问，任何参数都能传，编译器不再说话。我们花力气引入 TypeScript，结果在最需要保护的地方留了一个洞。

本文从一个前端开发者第一次写 d.ts 的视角出发，讲清声明文件的几种写法、各自对应哪类库，以及怎么确认它真的被加载。读完应该能给一个没有类型的 npm 包补上一份够用的声明，并知道该把它放在哪里。

d.ts 是什么

.d.ts 是 TypeScript 的声明文件，里面只有类型信息，没有一行可执行代码。它描述“某个在运行时已经存在的值长什么样”，而不去创造这个值。

把 .d.ts 交给 tsc，产物里不会多出任何 js 文件。它只是编译器的输入，用来做类型检查。因此声明文件里不能写函数体、不能初始化变量、不能有分支和返回语句，写了会得到 “An implementation cannot be declared in ambient contexts.” 这样的报错。

declare 的含义是“我保证运行时这个名字存在，你只管按我说的类型检查”。编译器相信这句保证，不做任何验证。所以声明写错不会在编译期暴露，只会在运行时炸掉，这也是声明文件需要配测试的原因。

一个 .d.ts 默认是全局脚本，里面声明的名字直接进入全局作用域。只要文件里出现顶层的 import 或 export，它立刻变成模块，全局声明随之失效。这一点先记下，后面“常见错误”一节会再遇到。

全局声明：给 script 标签引入的库补类型

老项目里最常见的场景是库通过 <script> 挂在 window 上。此时没有模块系统参与，对应的声明文件应该是全局脚本，用 declare var、declare function、declare class、declare namespace 把这几个全局名字描述出来。

declare var 描述一个全局变量，declare function 描述一个全局函数，declare class 描述一个可以用 new 调用的构造器，declare namespace 描述一个挂在全局上的对象。四者可以写在同一份文件里，也可以拆成多份，编译器会把它们一起收进来。

这类文件通常放在项目根的 typings/ 目录，再在 tsconfig.json 的 include 或 files 里列出来。它不需要被任何文件 import，只要参与编译就会生效。写完全局声明后，renderChart(document.body, [1, 2, 3]) 能正常推断，传错参数也会立刻报错。

要注意全局声明是“污染式”的：声明的名字一旦进入全局，所有文件都能看到它，也可能与别处的同名声明冲突。只给确实挂在 window 上的库写全局声明，能走模块就走模块。

模块声明：declare module “pkg”

如果库是 npm 包，走的是模块系统，声明就要写成模块声明。最省事的写法是简写形式，只有一行 declare module "datefmt";。它只告诉编译器“这个模块存在”，从里面 import 出来的东西全是 any。它适合临时挡住报错，但等于没有类型，只能当过渡。

泛型与约束

库的 API 里到处是泛型，声明文件只需要把类型参数原样写出来，不需要给出任何实现：

extends 用来收窄类型参数的范围，K extends keyof T 是最常用的一种：它保证传入的 key 确实是对象的属性名，返回值才能安全地写成 T[K]。没有约束的泛型等于 any 的另一种写法，调用方得不到任何有用信息，尽量给参数加上能加的下界。

接口和类的泛型写法一致，类上的类型参数在实例成员里可以直接使用。TypeScript 2.3 刚加上泛型参数的默认值，写 <T = string> 可以让调用方省略类型实参，但社区里的库还没跟上来，声明老库时用不上。

声明文件里真正高频的只有泛型和约束，更复杂的类型运算不在本文范围内。

嵌套一层通常够用，两层以上会让使用处的类型名变得很长。命名空间本身的语法、以及与模块的取舍，已经在《TypeScript 命名空间与模块》里讲过，这里只谈它在声明文件里的组织作用：把类型别名和接口集中在库的名字下，让使用者写 Viz.Options 而不是在全局里猜。

发布：types 字段与 @types

自己维护的库要把声明一起发出去，否则使用者装完包就只剩 any。入口声明文件通常命名为 index.d.ts，或与 main 指向的文件同名，再在 package.json 里声明：

types 是官方字段，typings 是早期的同义写法，两者等价，编辑器都认。解析顺序是先看 types，再找 main 同名换后缀的 .d.ts，最后找包根的 index.d.ts。files 决定发布时带上哪些文件，声明文件必须列进去，否则本地开发一切正常、装到别人机器上类型就没了，这是发版后最难查的一类问题。

不想自己写的库，先看社区有没有现成声明：npm install @types/lodash --save-dev，包会落在 node_modules/@types/lodash/index.d.ts，编译器自动加载，不需要 import。tsconfig 里的 types 数组可以限定只加载哪几个，typeRoots 可以改搜索根目录。2017 年主流库的声明基本都在 DefinitelyTyped 仓库里，流程是 fork、在 types/ 下建目录、写 index.d.ts 和配套的 xxx-tests.ts、文件头标明版本与作者，然后提 PR，合并后由自动流程发布成 @types/xxx。

常见错误

第一类是在 .d.ts 里写实现。声明文件里的每个函数都不能有函数体，写了会直接报错；反过来，有人把带实现的代码改名成 .d.ts 想让编译器闭嘴，结果整个文件都不再产生代码，运行时自然找不到模块。

第二类是模块声明写错名字。declare module "viz-core" 只对字符串完全一致的 import 生效，大小写、/dist/chart 这类子路径都要单独声明。相对路径 import 也不能用环境模块声明兜底，declare module "./chart" 是无效的。

第三类是顶层 import 让全局声明失效。一个本该提供全局名字的 d.ts，只要加了一行 import 就变成模块，里面的 declare var 不再进入全局，使用处会报找不到名字，而编译器不会提示原因。解决办法是把这些声明包进 declare global，或者把需要 import 的部分拆到另一个文件。

第四类是用 skipLibCheck 掩盖冲突。打开它之后所有 d.ts 都不做类型检查，两个 @types 包声明了同名全局变量时，冲突被静默吞掉，运行时后加载的覆盖先加载的。它只适合在第三方声明本身有错、又等不到升级时临时开启，不该写进默认配置。

调试：确认声明真的被加载

“明明写了却没生效”是声明文件最常见的问题，九成原因是文件没进编译，或者模块名没对上。别靠猜，让编译器把过程打出来：

--traceResolution 的输出里能看到每个模块的解析过程，成功时会打印 “… was successfully resolved to …”，后面跟的路径是 d.ts 才算数。如果只解析到 js 而没出现 d.ts，就去检查 types 字段、index.d.ts 的位置和 files 配置。--listFiles 用来确认手写的全局声明是否参与编译，没出现就说明 include 漏了目录。--noEmit 保证这两条命令只做检查，不会往 dist 里写文件。

还有一个土办法：在声明里故意把类型写错，比如给一个字符串变量标成 number，看编辑器是否立刻报错。报错说明文件被加载了；如果一切安静，问题就在加载环节，不在声明内容。另外注意编辑器可能用的是自带的 TypeScript 版本，命令行通过不代表编辑器通过，把编辑器切到工作区版本再验证一次。

一张对照表

库的类型 声明写法 引入方式
只有 script 标签的全局库 顶层 declare var、declare function、declare class <script> 之后直接用全局名
带 ES Module 导出的 npm 包 declare module "pkg" 内写 export import { x } from "pkg"
CommonJS 单导出 模块声明内写 export = import x = require("pkg")
UMD 模块声明内加 export as namespace Foo 全局 Foo 或 import 均可
社区已有声明的包 安装 @types/pkg 自动加载，不需要 import

小结

d.ts 不产生任何代码，它只是把运行时的形状写下来给编译器看，所以写法必须和库的引入方式对齐：script 用全局声明，npm 用模块声明，UMD 在模块声明上加一行 export as namespace。写完之后不要只看红线有没有消失，用 --traceResolution 和 --listFiles 确认文件真的进了编译，再故意写错一个类型，验证检查确实在跑。最后记住 any 不是终点，一行 declare var lib: any 换来的安静，代价是整个库的调用都失去保护。本文对声明合并与模块扩展只到“知道去哪查”的程度，真要做扩展时，回到那两篇专文。
