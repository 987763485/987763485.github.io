Go 的 strings 与 strconv 包

本文属于《Go 语言与工程》第 9/78 篇
上一篇系列目录下一篇

日志分析大概是很多人写 Go 的第一个真实任务：读文件、按分隔符切开、把字段转成数字、累加。每一步都只有一行代码，可 strings 与 strconv 这两个包偏偏最容易被”顺手写”写坏——一个被忽略的 error，就足以让整张报表的数字失去意义。本文从一段出错的统计脚本出发，把这两个包按使用场景梳理一遍：字符串的字节本质、查找与切分、拼接的取舍、解析与格式化的错误处理，最后落到一个可以复用的清洗函数。适合已经能写 Go 基本语法、准备处理真实文本数据的读者。

这类 bug 的可怕之处在于它不 panic、不报错，只是安静地给出错误答案。所以本文不打算罗列 API，而是按”我要做什么”来组织：先弄清字符串到底是什么，再看 strings 能做什么，最后看 strconv 在解析失败时究竟返回什么。

字符串是字节序列，不是字符数组

Go 的 string 是不可变的字节序列，底层是一段连续字节加一个长度（字符串头与拷贝的细节在指针与内存布局那篇已经讲过，这里一句带过）。这决定了两件事：len(s) 返回字节数，s[i] 取到的是 byte 而不是字符。对纯 ASCII 文本，字节数恰好等于字符数，所以很多人写了很久都没察觉；一旦出现中文，直觉就失效了："Go语言" 的 len 是 8，因为两个汉字各占 3 个字节。

要按字符遍历就用 range，它会把 UTF-8 字节流解码成 rune，遇到非法字节返回 utf8.RuneError 并前进一个字节。注意 range 给出的下标仍然是字节偏移，不是第几个字符：

截断的坑就出在这里。s[:5] 是按字节切的，"Go语言"[:5] 把”语”的三个字节切掉一个，结果已经不是合法 UTF-8，打印出来末尾是一个替换字符。按字符截断要先转 []rune：string([]rune(s)[:3])。[]rune 会分配新内存，长文本里频繁转换是有代价的，能按字节处理的场合就别转。判断合法性用 utf8.ValidString，数字符个数用 utf8.RuneCountInString，清洗外部数据时这两个函数很省事。

strings 的常用函数，按用途分组

strings 的函数不少，但按”我要做什么”归类之后其实只有五组，记住分组比背函数名有用。

查找类有 Contains、Index、HasPrefix、HasSuffix。判断前缀不要写 Index(s, p) == 0，HasPrefix 既清楚又不会让人怀疑你想找的是首次出现位置。这几个函数都是逐字节比较，对 UTF-8 恰好也成立，因为 UTF-8 不会出现一个字符的字节序列是另一个字符前缀的情况。需要大小写不敏感地查找时，标准库没有现成函数，只能先归一化再查；模式复杂、量又大，那是 regexp 的事，本文不展开。

切分类有 Split、SplitN、Fields。Split 保留空字段，所以 strings.Split("a,,b", ",") 得到三个元素，中间那个是空串——这一点经常被忘记，随后用下标取字段就取错位。SplitN 限定切几段，适合”只切前两段、剩下的整体保留”的场景，比如按第一个冒号切开配置行。Fields 按任意连续空白切分并丢掉空字段，处理人写的文本、命令行输出时比 Split(s, " ") 稳得多，前者对我们的日志正好合适。

拼接类只有 Join，把 []string 用分隔符连起来，内部会先算好总长度再一次性分配，比循环里 + 好得多，后面还会提到。

替换类是 Replace(s, old, new, n)，n 为负数表示全部替换。2017 年的 Go 1.8 里还没有 ReplaceAll，全部替换就老老实实写 -1，代码里看到一个 -1 不要以为是笔误。裁剪类有 Trim、TrimSpace、TrimPrefix、TrimSuffix：Trim 的第二个参数是”字符集合”而不是”子串”，Trim(s, "ab") 会去掉两端所有的 a 和 b，想删整个前缀必须用 TrimPrefix。TrimPrefix 在前缀不存在时原样返回，不会报错，所以它适合清理可选的标记，不适合做校验。

大小写与比较：不要用 ToLower 做判断

ToLower、ToUpper 返回新字符串，原串不变。它们做的是 Unicode 映射而不是简单的 ASCII 加减 32，所以对中文没有影响，对某些特殊字符却可能改变字节长度——拿返回值去和原始下标对应是不安全的。

更常见的坏习惯是用 strings.ToLower(a) == strings.ToLower(b) 做比较。这样写结果通常没错，但每次比较都要分配两个新字符串，放在按请求执行的路径上就是白白多出来的 GC 压力。正确工具是 strings.EqualFold(a, b)，它逐字符做大小写折叠，不分配内存，还能处理一些 ToLower 处理不好的等价关系，比如 Kelvin 符号与普通 k。HTTP 头名、配置键、用户输入的命令关键字，都适合用它。

边界也要说清：EqualFold 只做大小写折叠，不做 Unicode 规范化，也不感知语言环境，预组合的 é 与”e 加组合音标”并不相等。多语言文本比对是另一个话题，标准库这两个函数解决不了。

拼接字符串的三种选择

string 不可变，每次 + 都要分配一块新内存并把两边都拷进去。偶尔拼三五次无所谓，但写进循环就是 O(n²)：拼到第 n 次时，前 n-1 次的内容要完整复制一遍。

三种手段各有适用面。+ 适合次数固定、数量很少的场合，比如拼一个短提示。strings.Join 适合已经拿到一个切片、元素个数已知的情况，它先累加长度、一次分配，是这类需求的最优解：

bytes.Buffer 适合”边算边写、事先不知道有多少段”的场合，比如逐行生成一份报告。它内部是可增长的字节切片，WriteString 摊还下来是常数时间；如果能估个大概，先 Grow 一下能少几次扩容。要注意 Go 1.8 里 buf.String() 会把内容拷贝成新字符串，所以别在大循环里反复调它。

至于 strings.Builder，它是 Go 1.10 才加入的，2017 年 4 月写代码时还没有这个东西，当时的标准答案就是上面三者。看到 Builder 的示例，说明那份资料比本文新，读的时候留意版本差异。

strconv 的解析函数与它们的错误

Atoi 和 Itoa 是最常用的两个捷径，但它们只是封装：Atoi(s) 等价于 ParseInt(s, 10, 0)，Itoa(i) 等价于 FormatInt(int64(i), 10)。需要控制进制或位宽时就换用后两个。

ParseInt(s, base, bitSize) 的 base 取 0 表示根据前缀自动判断（0x 十六进制、前导 0 八进制），取 2 到 36 表示指定进制。bitSize 决定结果的范围，可取 8、16、32、64，函数返回的始终是 int64，由调用方按位宽转换。这一参数不只是”提醒”，它参与溢出判断：ParseInt("300", 10, 8) 会返回错误，哪怕 300 放进 int64 绰绰有余。解析端口、状态码这类有明确范围的字段时，把 bitSize 写对，等于免费做了一次范围校验。ParseUint 同理，但它不接受负号，解析 ID、长度这类非负值更合适。

ParseFloat(s, bitSize) 接受普通小数、科学计数法，也接受 Inf、NaN，清洗用户输入时要留意后者。ParseBool 的白名单很窄，只认 1、t、T、TRUE、true、True 和对应的假值，"yes"、"on" 一律失败——面对配置文件里的开关，得自己先做一层映射。

错误值怎么判断？最简单的是 err != nil。需要区分”格式不对”和”数值越界”时，把错误断言成 *strconv.NumError，再看它的 Err 字段是不是 strconv.ErrSyntax 或 strconv.ErrRange。这个区分有实际意义：前者说明数据是脏的，后者说明数据可能是被截断或单位写错了，日志里该记的上下文并不一样。

格式化：Format 系列与 Sprintf 的取舍

strconv 一侧的格式化函数与解析函数一一对应：FormatInt、FormatUint、FormatFloat、FormatBool。FormatFloat(f, 'f', 2, 64) 表示定点两位小数，第二个参数换成 'e' 是科学计数法，'g' 交给函数自己选；精度传 -1 表示用能唯一表示该值的最少位数，做调试输出时很好用。

fmt.Sprintf("%d", n) 结果相同，代价不同：Sprintf 要把参数装箱成 interface{}，再靠反射解析格式串。单次调用差别看不出来，放进每秒几万次的循环里就是明显开销。规则很朴素：日志、错误信息这类低频路径怎么好读怎么写；缓存键、批量 ID 这类热点用 strconv。差多少不要凭感觉，写个 Benchmark 跑一下，go test -bench 比任何断言都可靠。

五个反复出现的坑

第一个是吞掉 Atoi 的错误，开篇已演示过后果。判断标准很简单：返回值要参与计算或写库，就必须处理 err，哪怕只是记一条带原始字段的日志再跳过。

第二个是误以为解析失败一定返回 0。Atoi 遇到非法字符确实返回 0，但数值越界时返回的是边界值：ParseInt 返回 math.MaxInt64 或 math.MinInt64，ParseFloat 溢出返回正负无穷。所以”结果为 0 就是失败”这种判断是错的，唯一的依据只有 err。这也是为什么溢出往往比格式错误更危险——脏值看起来完全合法。

第三个是空串与空白串不分。Atoi("") 和 Atoi(" ") 都失败，TrimSpace 之后都变成空串，而 "0" 是合法值。判断字段为空要写 strings.TrimSpace(s) == ""，否则一个空格就能绕过校验。

第四个是循环里用 + 拼字符串。数据量小时看不出问题，日志一多就变成几分钟跑不完，原因在上一节已经说过。

第五个是先 Split 再按下标取值，却不检查长度。日志格式一变，fields[8] 就 panic；而如果用 SplitN 并检查 len(fields)，同样的脏数据只会被跳过。解析外部文本时，任何下标访问前都该有一次长度判断。

[]byte、string 与 UTF-8 校验

[]byte(s) 和 string(b) 都会拷贝。这不是实现细节，而是语言层面的保证：字符串不可变，若转换后还能通过切片改到同一块内存，不可变性就破了。所以”转一下再处理”在热路径上有成本，能复用同一份 []byte 就别来回转。例外是 m[string(b)] 这种用字节切片做 map 键的写法，编译器会优化、不产生拷贝，读配置表时很常用。

从外部拿到的字节流不一定是合法 UTF-8，直接 range 会把每个非法字节变成 utf8.RuneError，数据被悄悄改写。入库或落盘前用 utf8.ValidString(s) 检查一次，代价是一次线性扫描，换来的是后面所有环节都不用再怀疑编码。需要长度限制时用 utf8.RuneCountInString 数字符，别用 len，否则中文用户会被莫名其妙地截短一半配额。
