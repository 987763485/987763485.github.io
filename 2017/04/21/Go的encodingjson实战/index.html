Go 的 encoding/json 实战

本文属于《Go 语言与工程》第 10/78 篇
上一篇系列目录下一篇

去年冬天接手一个订单同步的需求，要把系统里的订单推给第三方的物流平台。对方给了文档、给了测试环境，看起来只是拼几个字段的事，结果联调来回改了三版才跑通。第一版栽在字段名上，第二版栽在数字精度上，第三版栽在空数组上。本文把 encoding/json 里这几处容易想当然的地方梳理一遍，示例基于 Go 1.8，在 GOPATH 下建一个 main 包即可运行。

从一次联调事故说起

第一版的问题出在字段名。对方文档写的是 orderNo，实际返回的是 order_no，我们照着文档写成 OrderNo，三条路各走各的，解析出来全是零值，日志里一排空字符串，谁也说不清是没查到还是没解析到。

第二版改完 tag，字段能进来了，订单号却对不上。订单号是十九位的长整型，解到 float64 之后末尾几位被抹平，推过去查不到单，对方反馈“单号不存在”，我们这边显示推送成功。

第三版处理空数组。对方在没有明细时返回 []，我们结构体里的切片是 nil，转发时被序列化成 null，下游校验直接拒收。三次事故对应三类知识：字段匹配规则、数字的表示、空值的语义。下面按这个顺序展开，最后给一张对照表。

基础：Marshal、Unmarshal 与字段可见性

先立三条底线。其一，只有导出字段参与序列化，首字母小写的字段会被静默跳过，既不报错也不提示。其二，默认字段名就是 Go 字段名原文，标准库不会把 TotalFee 转成 total_fee，也不会转成小驼峰。其三，字段匹配发生在运行时，靠反射完成，写错了编译器一无所知。

反序列化这边，匹配规则比序列化宽松一档：先找名字完全相同的字段，找不到再做大小写不敏感的比较。所以 {"totalFee":1990} 和 {"TOTALFEE":1990} 都能落进 TotalFee，但 {"total_fee":1990} 不行，下划线不会被当成分隔符。这条规则解释了开篇的第一版事故，也解释了为什么不少人误以为标准库会自动转下划线——他们恰好只试了大小写。

指针与 nil 的行为要单独记。把 nil 指针传给 Marshal，得到的是 null，不会报错；把 nil 指针传给 Unmarshal，得到的是 json: Unmarshal(nil *Order) 这样的运行时错误，因为没有对象可写。结构体字段为指针时，JSON 里的 null 会把指针置为 nil；字段是值类型时，null 什么都不做，字段保持原值。

还有一点在复用结构体时最容易踩：Unmarshal 不会先把目标清零。JSON 里没出现的键，原值原封不动；切片会被整体替换；map 则是逐键合并，旧键会留下来。实践中要么每次新建目标对象，要么在复用前显式清零。

struct tag 与匿名字段

tag 是贴在字段后面的反引号字符串，格式为 json:"名字,选项"，名字与选项之间用逗号分隔，选项可以叠加。最常用的四个开关是改名、omitempty、- 和 ,string。

改名不必多说。omitempty 的含义是“值为空时不输出这个键”，空的判定包括 false、0、nil 指针与 nil 接口、长度为零的字符串、切片和 map。注意它不认结构体的零值，一个所有字段都为零的结构体，在标准库眼里并不空，照样输出 {}。这也是后面空值一节要单独处理的原因。

json:"-" 是彻底忽略，字段既不读也不写。写成 json:"-," 则是把键名定为减号本身，两者只差一个逗号，效果天差地别。,string 让数字或布尔值以字符串形式出现，接收方拿到的是 "1990" 而不是 1990；它只对字符串、整数、浮点、布尔有效，给 string 字段再加 ,string 会编码两层引号。

tag 最阴的地方是写错不报错。json: "name" 冒号后多一个空格、json:name 忘了引号，反射解析时都拿不到合法值，字段悄悄退回默认名；json:"nmae" 拼错了字母，编译照样通过，只是键名对不上。前一类畸形 tag 可以用 go vet 查出来，后一类只能拿真实报文核对。

匿名字段默认展开。内嵌的 Base 如果没写 tag，它的字段会被提升到外层，JSON 是平的，不出现 Base 这一层。一旦给匿名字段写了 tag，它就不再展开，而是以 tag 名作为键、整体作为一个对象出现。

同名字段的优先级按嵌套深度算：浅的覆盖深的。同一层出现多个同名字段时，如果其中只有一个带 tag，带 tag 的胜出；如果都带 tag，这几个字段全部被忽略。这条规则不常遇到，但把两个内嵌结构体合并到一起时就会撞上。

数字与动态结构

Unmarshal 到 interface{} 时，所有数字一律变成 float64，这是标准库的既定行为，不是精度选项。float64 只有 53 位有效位，超过 2 的 53 次方的整数无法精确表示，十九位的订单号正好落在这个区间之外，开篇的第二版事故就是这么来的。

解法有两条。第一条是把目标字段声明成 int64 或 json.Number，前者要求报文里是纯数字，后者保留原始字符串。json.Number 本质是 string，提供 Int64、Float64、String 三个方法，Int64 遇到小数会返回错误，正好可以当作校验。第二条是在解码器上开 UseNumber，它只影响落到 interface{} 里的数字，开启后类型是 json.Number 而不是 float64。

结构未知或只是转发时，map[string]interface{} 是最快的入口。取值务必用带 ok 的断言，v.(int) 这种写法在数字落在 float64 上时必然 panic，而 interface{} 里的整数断言成 int 失败，是新手最常见的崩溃来源之一。类型不确定时用 type switch，把 string、json.Number、[]interface{} 几类分别处理。

json.RawMessage 用来延迟解析。它本质是 []byte，Unmarshal 时原样保留那一段字节，不校验内部结构。常见用法是先解一层信封，看 type 字段决定把 payload 再解成哪个结构体；转发场景下直接把它塞回新结构体，也能避免解了再编、白白走一遍反射。

注意两点：RawMessage 里的字节必须是合法 JSON，Marshal 时不会替你检查；Unmarshal 得到的字节是拷贝，可以安全地留到解码器复用之后。

自定义编解码

标准库对时间只认 RFC 3339，对枚举只会输出数字，对“空值”没有业务语义。这三类需求都靠实现 MarshalJSON 和 UnmarshalJSON 解决。做法是给基础类型起一个具名类型，在它上面挂方法，方法内部不要再调用同类型的 json.Marshal，否则会无限递归；需要借用默认行为时，先定义 type alias T 去掉方法集再转过去。

序列化方法用值接收者，反序列化方法用指针接收者，这是惯例：前者让值类型和指针类型都能编码，后者必须能改写目标。枚举同理，把 int 包一层，输出时查表转成字符串，输入时反向查找，遇到未知值返回错误而不是静默归零。空值语义也在这里落地，比如把 "" 编码成 null，或在 UnmarshalJSON 里把 null 解释成“显式清空”。

流式处理

报文大到一个 []byte 放不下，或者一个连接上连续来了多个对象时，用 json.Decoder。它从 io.Reader 增量读取，Decode 一次消费一个完整值，内存占用与单个对象同阶。循环的写法固定，退出条件只认 io.EOF。

这里的 io.EOF 必须用等号比较，不能当成普通错误往外抛，否则正常结束会被记成失败。文件里是数组时，可以先 Decode 一个 []Order，也可以自己读掉左括号后用 dec.More() 控制循环，后者更适合超大数组。输出侧用 json.Encoder，Encode 会自动补一个换行，正好适合一行一条记录的日志格式；它的 SetEscapeHTML 和 SetIndent 也只在 Encoder 上才有。注意 Decoder 自带缓冲区，不要再从同一个 reader 上另起读取，两者会抢数据。

空值、缺省与 HTML 转义

null 与字段缺失不是一回事

JSON 里没有值有两种写法：键不存在，键存在但值是 null。两者解码到结构体后完全一样，都是零值，标准库不提供区分手段，指针字段也不行，两种情况都是 nil。

如果业务只关心“有没有值”，指针够用。如果“缺失”表示沿用旧值、“null”表示显式清空，就得自己留证据。最省事的办法是把字段声明成 json.RawMessage：键缺失时是 nil，值是 null 时是 null 四个字节，一眼可分。另一个办法是实现 UnmarshalJSON，先解到 map[string]json.RawMessage，用带 ok 的取值判断键是否存在，再逐字段赋值，顺带可以记一个 NameSet bool。

omitempty 在这里还有局限：它判断的是“空”，不是业务上的“零值”。整数 0 会被省略，可 0 可能是有效值；结构体永远不会被判定为空，哪怕所有字段都是零，也照样输出 {}。想让空结构体消失，要么改成指针，要么写自定义序列化。

HTML 转义的两面

默认情况下，Marshal 会把 <、>、& 转成 \u003c、\u003e、\u0026，U+2028 与 U+2029 也会被转义。第一次看到 \u0026 容易以为出了 bug，其实这是为了把 JSON 安全地嵌进 HTML。

Marshal 没有关闭转义的参数，只能换 json.NewEncoder，调用 SetEscapeHTML(false) 后再 Encode，末尾会多一个换行，需要自己裁掉。需要关闭的场景通常是对方要求原文可读，或者 JSON 要进模板再被读取。

关闭之后，</script>、<!-- 这些片段会原样出现，嵌入页面时必须自己处理，否则脚本标签被提前闭合。边界要分清：以 application/json 返回的响应，浏览器不会当 HTML 解析；真正危险的是把未转义的字符串拼进页面。转义是纵深防御，不是给拼接开绿灯。

性能：先少做，再快做

Marshal 依赖反射，字段越多、嵌套越深，单次开销越大。标准库会缓存类型信息，但每次编码仍要遍历字段、增长缓冲区，所以优化的顺序应该是：先减少调用次数，再减少数据量，最后才抠内存分配。

几个直接有效的做法：需要拼进固定缓冲区时，用 bytes.Buffer 的 Grow 预留容量，避免多次扩容拷贝；用 Encoder 直接写目标 writer，省掉先 Marshal 成 []byte 再拷贝一遍；循环里不要反复编解码同一份常量配置，解析一次缓存起来；批量接口一次编码整个切片，不要每条记录调一次。Marshal 本身可以并发调用，但 Encoder 和 Decoder 持有状态，不能跨 goroutine 共享。

基准测试要写对，否则数字没有意义：

go test -bench . -benchmem 会同时给出耗时和分配次数。只有确认编码真的在 profile 里占了大头，再考虑手写序列化或代码生成，过早优化往往只是把可读性换掉。

常见错误与对照表

把上面几节里最容易复发的错误集中列一下，这些都是编译期不会提示、只在联调时暴露的问题：

  • 字段首字母小写，编码后凭空少几个键，没有任何报错。
  • tag 多空格、少引号，整条 tag 失效；键名拼错则安静地写成另一个名字。
  • 以为 Unmarshal 会做下划线转驼峰，实际上只做大小写不敏感匹配。
  • 把 interface{} 里的数字断言成 int，运行时 panic，应先断言 float64 或 json.Number。
  • 对 nil 指针调用 Unmarshal，得到运行时错误而不是自动分配。
  • 复用同一个结构体连续解码，上一轮的字段残留，误判成新数据带着旧值。
  • omitempty 把有效的 0 和空字符串吞掉，或者对结构体完全不起作用。
  • 关闭 HTML 转义后把 JSON 直接拼进页面。
  • 在循环里对同一份数据反复编解码。

下面按“需求、做法、坑”收拢成一张表，可以直接当检查清单用。

小结

encoding/json 的默认行为足够应付八成的接口，剩下两成集中在三处：字段可见性与命名匹配、数字的表示精度、空值的语义。把 tag 当成接口契约的一部分，逐字段对照真实报文；把大整数和可能为空的字段单独设计类型；需要区分“缺失”和“null”时不要偷懒用指针。最后用基准测试代替直觉，确认优化真的落在瓶颈上，而不是把可读性换成了更慢的代码。
