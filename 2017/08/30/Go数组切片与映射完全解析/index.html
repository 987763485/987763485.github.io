Go 数组、切片与映射完全解析

本文属于《Go 语言与工程》第 7/78 篇
上一篇系列目录下一篇

切片和映射是 Go 程序里出现频率最高的两种数据结构，也是最容易“用错却不知道错在哪里”的地方：在函数里明明改了切片，调用方却看不到；只 append 了几个元素，另一个变量里的数据却跟着变了；从 map 里取出结构体改一个字段，原值纹丝不动。这些现象背后没有魔法，只有一个三字段的结构体、一块被共享的底层数组，以及一张会扩容的哈希表。本文从数组的值语义讲起，逐层拆开切片头、扩容规则、三索引切片与 range 的拷贝行为，再转到 map 的桶结构、遍历无序和并发读写，最后给出几条可以直接落到代码里的建议。适合已经能写 Go 程序、但被切片和 map 的“怪现象”绊过的读者。

数组：长度被写进类型里

Go 的数组和 C 的数组长得像，语义却完全不同。第一件要记住的事：数组的长度是类型的一部分。[3]int 和 [4]int 是两个不同的类型，互相赋值需要显式转换，而长度不同时连转换都不合法。这也意味着我们没法写一个“接受任意长度 int 数组”的函数，想要这种灵活性，就得换成切片。

第二件事：数组是值类型。赋值、传参、放进结构体字段，全都是整体拷贝，不存在“两个变量指向同一个数组”这回事。

arr[i] 用在数组指针上是合法的语法糖，等价于 (*arr)[i]，Go 会自动解引用。这样既避免了拷贝，又能真正修改调用方的数据。

数组还有一个常被忽略的性质：如果元素类型可比较，数组就可比较，可以用 == 判断相等，也可以做 map 的键。[16]byte 因此在工程里常被拿来当固定长度的 ID 或摘要值，既能比较又能当键，这两点在切片上都做不到（切片只能与 nil 比较）。不过数组的用处大体止步于此，日常代码里我们写的是 []int，读作“int 的切片”，它才是 Go 里真正的一等公民。

切片头：一个只有三个字段的结构体

切片不是“数组的别名”，它本身是一个很小的值，由三个机器字组成。标准库在 reflect 包里把这个结构公开了出来，运行时的内部定义与之同构：

classDiagram
    class SliceHeader {
        Data 指向底层数组
        Len 长度 可索引范围
        Cap 容量 可扩展上限
    }
    class BackingArray {
        元素0
        元素1
        元素2
        元素3
        元素4
    }
    SliceHeader --> BackingArray : Data 指向某处

把这三个字段想清楚，后面所有的“怪现象”都能自己推出来。Len 是我们能用 s[i] 访问的范围，越界会 panic；Cap 是从切片的第一个元素数起、到底层数组末尾还有多少个元素，它只对 append 和再次切片有意义。在 64 位平台上，一个切片头占 24 字节，所以传切片的开销是常数级的，与它“看起来装了多少数据”无关。

关键点在于：对数组或切片做切片操作，生成的是一个新头，指向同一块内存，一个元素都不会被复制。这个过程是 O(1) 的。

cap(s) 为什么是 4？因为 s 的起点是 arr[1]，从这里到数组末尾还剩 arr[1]、arr[2]、arr[3]、arr[4] 四个位置。容量永远从切片自己的起点算，而不是从底层数组的起点算。这条规则解释了一个常见困惑：s[:0] 之后长度归零，容量却一点没少，仍然可以继续 append 而不用分配。

表达式 结果长度 结果容量
arr[1:3] 3 − 1 = 2 5 − 1 = 4
arr[2:] 3 3
arr[:0] 0 5
arr[:] 5 5

需要强调的是，切片头里的 Data 只是一个地址，它不记录这块内存有多大、属于谁。运行时既不知道 arr 这个数组变量的存在，也不会在 arr 离开作用域时通知切片。谁在引用这块内存、能引用到哪一格，全靠 Len 与 Cap 这两个整数自觉约束。

append 做了什么：容量够就地写入，不够就搬家

append 是内建函数，签名看起来像 func append(s []T, vs ...T) []T。它接收一个切片头，返回一个新的切片头，所以必须把返回值接住：

它的行为可以分成两条分支。第一条：如果 len(s) + 新增元素个数 <= cap(s)，就在底层数组的 len(s) 位置开始写入，返回的新头 Data 不变、Len 变大、Cap 不变。这是纯粹的就地写入，不涉及内存分配。第二条：容量不够，运行时就分配一块更大的数组，把老元素复制过去，再追加新元素，返回的头指向新数组。老数组完全不受影响，仍然被别的切片引用着。

这段代码里的 b 之所以“没跟着变”，正是因为扩容发生了。如果把容量改成 4，append 就会就地写入 a[2]，此时 b 虽然长度还是 2，底层数组的第 3 格已经被改成 3——b 看不出变化，但任何基于 b 再切片、再 append 的操作都会读到这个 3。同一个 append 调用，行为取决于容量，这就是切片最容易让人误判的地方。

新容量到底给多少？这是运行时 growslice 的实现细节，不属于语言规范。可以描述的规律是：小切片阶段新容量大致翻倍，随着容量增大，增长比例会逐步降低，以免一次搬动太多内存；最终容量还会按元素大小和内存对齐向上取整。不同 Go 版本的具体策略可能调整，所以不要写依赖某个容量数值的代码，只依赖“均摊下来每次 append 是常数时间”这一条保证。

共享底层数组：最隐蔽的一类 bug

切片赋值、传参、切片再切片，都不复制元素。只要两个切片头的 Data 落在同一块数组上，且索引区间有重叠，它们就能互相看见对方写入的值。

三索引切片：给容量上一把锁

普通切片表达式 s[low:high] 只约束长度，容量是被动继承的——从 low 一路算到原切片容量的尽头。规范里还有一种写法 s[low:high:max]，叫完整切片表达式，它把容量也钉死：

三个下标必须满足 0 <= low <= high <= max <= cap(a)，否则运行时 panic（下标是常量时编译期就能报错）。max 的合法上限是原切片的容量，不是长度，这一点和 high 不同。

它解决的是一个很具体的问题：怎么把一段数据交出去，同时保证对方 append 时不会写脏我的数组。

safeView 的容量被限制成 2，任何 append 都只能走“分配新数组”这条路，即使对方拿着它做了一大堆写入，也只影响它自己那份副本。

如果写成 s.buf[start:end]，调用方一句 append(rec, x) 就可能把下一条记录的第一个字节覆盖掉——因为它还有剩余容量，append 会就地写入。加一个 end 作第三个下标，这类跨记录的污染从根源上消失。

代价要说清楚：三索引切片没有复制任何数据，safeView 和 a 仍然共享同一块数组，读到的内容依然会随 a 变化。它锁住的只是写入边界，不是数据本身。要真正隔离，还是得 copy。

另外有一个语义细节值得记住：s[low:high:max] 里的 max 是相对原切片起点的绝对下标，而不是“再往后多少个”。写 a[1:3:4] 得到的是长度 2、容量 3 的切片，因为 4 - 1 = 3。不少人在第一次使用时会把 max 当成容量直接填，结果算错一格。

切片作参数，以及 range 的拷贝语义

把切片传给函数时，复制的是那 24 字节的头，不是底层数组。由此可以推出三条经常同时出现在一段代码里的结论。

第一条：函数内修改元素，调用方看得见，因为大家指向同一块数组。

第二条：函数内 append 导致扩容时，调用方完全看不见，因为函数只改了它自己那份头的 Data 和 Len，调用方的头还是老样子。

第三条：函数内 append 没有扩容时，数据写进了共享数组，但调用方的 Len 没变，所以“看不见”；等调用方自己再 append，就会把这份数据覆盖掉——两份逻辑上都“不存在”的写入互相打架。

如果确实需要让函数扩展切片，只有两种选择：把新切片作为返回值交回去，或者传切片的指针。

第一种写法更符合 Go 的习惯，也更难用错；第二种只适合必须同时改多个返回值或者需要表达“就地更新”的场景，比如某些解码函数。

还有一点和切片形成对照：map 是引用类型。把 map 传给函数，函数里增删的键值对调用方立刻能看到，不需要返回值，也不需要传指针。

这是因为 map 值本身就是一个指向运行时结构的指针，复制它只是复制了指针。

map 的底层直觉：桶、哈希与装载因子

不需要背运行时源码，但有几条结构性事实值得建立直觉，它们直接决定了 map 的性能特征和那些“看起来很奇怪”的行为。

map 的底层是一组桶。键经过哈希函数得到一个整数，其中一部分位用来选中某个桶，另一部分位（通常取高位字节，实现里叫 tophash）存在桶里，用于快速预筛选。每个桶固定能放若干个键值对（当前实现是 8 个），装满之后再挂溢出桶，形成链表。查找时先定位桶，再在桶内比对 tophash，最后才逐个比较完整的键。

flowchart TD
    K[键 key] --> H[哈希函数]
    H --> B[取低位选桶]
    B --> BUCKET[桶 含 8 组键值]
    BUCKET --> T[比对 tophash]
    T -->|命中| CMP[比较完整键]
    T -->|未命中| OV[下一个溢出桶]
    OV --> BUCKET
    CMP -->|相等| VAL[返回对应值]

键多了会触发扩容。触发条件是元素数量与桶数量的比值超过某个阈值，这个阈值（装载因子）是运行时内部常量，具体数值不属于语言规范。扩容会申请大约两倍数量的桶，但不是一次性搬完：运行时把老桶标记出来，后续的写入和删除操作顺带搬几个，直到搬空。这叫渐进式扩容，目的是避免一次写入引发长时间停顿。

这套机制解释了几个常见现象。

第一，range map 的顺序是随机的，而且每次运行都可能不同。这不是 bug，是刻意的设计：运行时在遍历时随机选一个起始桶和一个桶内偏移，就是为了让所有人从一开始就无法依赖顺序。想要稳定输出，必须自己排序：

第二，delete 不会缩容。删掉一半键之后，桶的数量和内存占用基本不变，留下的空槽还会拖慢后续查找。如果一个大 map 需要周期性清空，重建一个新 map 往往比循环 delete 更划算，因为老 map 整块交给 GC 回收。

第三，单次写入的耗时不均匀。绝大多数写入是 O(1)，但撞上扩容搬迁的那一次会明显偏慢。对延迟敏感的服务，如果有一个几十万键的 map 在请求路径上被随机写入，尾延迟就可能出现毛刺；常见的缓解手段是预热（启动时把数据灌进去，让扩容提前发生）或者换用别的数据结构。

平均而言，查找、插入、删除都是常数时间，这是 map 的设计目标；但“常数”背后有哈希计算、桶定位、键比较三笔开销，键越长、哈希越慢，这个常数就越大。

并发读写 map 会发生什么

切片在并发读写下最多是数据竞争、读到半新半旧的值；map 则更激烈，运行时会直接把进程干掉。

这段程序通常会以 fatal error: concurrent map writes 结束。一个 goroutine 读、另一个写，则可能看到 fatal error: concurrent map read and map write。要注意两个细节。

其一，这是 fatal error，不是普通的 panic。运行时检测到之后直接终止程序，defer 里的 recover() 接不住，日志也来不及优雅收尾。原因很实在：map 的写入可能正好发生在扩容搬迁的中途，此时桶的状态是不完整的，继续执行只会读到错乱的数据，不如立刻停下。

其二，检测是概率性的。运行时有专门的标志位来发现“有人正在写”，但只有在时间窗口恰好重叠时才会命中。所以“我压测了一周没崩”不能证明代码安全，只能证明还没撞上。

解决办法是让访问串行化：加锁、按 key 分片成多个 map、或者换用并发安全的结构。Go 1.9 新加入的 sync.Map 把读路径做成了基本无锁，适合读多写少、键集合基本稳定的场景，比如只增不删的配置缓存；它的 API 与适用边界另文讨论，这里只需记住它不是 map 的通用替代品——写多的场景下它通常比“map 加锁”更慢。

前面讲的是机制，这一节把机制换成习惯。下面几条在 code review 里出现频率最高，改动都很小，收益却直接体现在内存和延迟上。

能预估规模就预分配。 切片的容量、map 的容量提示，都是“一次分配换掉多次分配”的买卖：

别让 range 复制大结构体。 for _, v := range items 每轮都拷贝一个元素。元素是几百字节的结构体时，这份拷贝在热路径上很显眼：

复用切片前，先把指针元素清干净。 常见的对象池写法是 buf = buf[:0]，它保留底层数组、长度归零，下一轮直接 append。但如果元素类型含指针（切片、map、字符串、接口、结构体里的指针字段），被截断的那部分元素仍然留在数组里，GC 会认为它们还活着：

别让一个小切片拖住一整块内存。 从 1 MB 的缓冲区里切出 100 字节返回，这 100 字节的切片头仍然指向那 1 MB，整块内存都无法回收：

这类“长命的小切片指向短命的大数组”是内存泄漏的经典形态，尤其容易出现在解析器、日志处理和网络协议实现里。

map 要清空就重建。 delete 只清槽位不缩桶，反复增删之后桶数组会维持在高水位。周期性清空的大 map，直接 m = make(map[K]V)，让老结构整体被回收更干净。

两个典型排错案例

机制讲完之后，看两个把上述知识点串起来的场景。它们的共同点是：代码单独看每一行都没问题，错在跨函数、跨请求的共享关系上。

第一个案例是“导出的文件内容会串”。为了省掉重复分配，代码里用了一个包级缓冲区：

Reset 只是把长度归零，底层数组和容量都还在，所以 Bytes() 返回的切片与缓冲区共享内存。调用方如果把这个返回值存起来稍后写文件，而另一个请求已经调用了 renderCSV，第二次写入就会覆盖第一次的内容；两个请求并发时，输出可能前半段是一个人的数据、后半段是另一个人的。排查时容易怀疑并发写文件，实际根因是返回了一个“还在被别人用”的切片。

修法有两条，选哪条取决于调用频率：每次 new(bytes.Buffer)，用分配换正确性；或者保留复用，但返回前 copy 一份出来。后者的写法是 out := make([]byte, buf.Len()); copy(out, buf.Bytes())。判断标准很简单：函数返回的切片，调用方会不会在本次调用结束后继续持有？会，就不能返回复用缓冲区里的视图。

第二个案例是“缓存越用越乱”。缓存把内部切片直接交给调用方：

某个调用方拿到之后觉得“顺手排个序更方便展示”，一句 sort.Slice(list, ...) 就把缓存里的顺序改了；另一个调用方 append(list, extra)，因为容量还有富余，直接把 extra 写进了缓存的下一个槽位。之后所有读这个键的地方都拿到被污染的数据，而缓存本身没有任何写入日志，看起来像是“数据自己变了”。

修法是让 Get 返回副本，或者在存进去的时候就限制容量：c.items[key] = list[:len(list):len(list)]，这样调用方 append 必然触发分配，至少不会污染缓存；但排序、改字段这类操作仍然会穿透，所以最稳妥的还是返回副本，并在文档里写明“返回值可自由修改”。这两条经验可以推广成一句原则：跨模块传递切片时，要么明确它是只读视图，要么给它一份副本，不要留给调用方去猜。

小结

数组是值，长度属于类型，赋值即拷贝；切片是“指针 + 长度 + 容量”的小结构体，赋值只复制这个头，元素仍然共享。append 在容量够时就地写入、不够时搬家，扩容比例属于实现细节，能依赖的只有均摊常数时间。切片的一切“意外”都源于共享底层数组：函数内 append 的可见性、range 变量被复用、返回子切片拖住大数组，都是同一个原因的不同表现。三索引切片把容量钉死，是库函数保护自己数据的低成本手段；真正要隔离数据，仍然只有 copy。map 是哈希桶加渐进式扩容，遍历顺序被刻意打乱，元素不可寻址，并发写会直接终止进程。把这些机制记在心里，代码里那些看似玄学的 bug 大多能在几秒钟内定位。
