Linux 文本处理三剑客

2017 年夏天，一台 CentOS 7 上的 Nginx 日志涨到了 2GB。产品同学要状态码分布，运维同学要慢请求排行，我还想看看流量在一天里怎么起伏。为一个只用一次的需求写 Python 脚本，编辑、调试、装依赖，成本比问题本身还高。本文从这份日志出发，讲清 grep、sed、awk 的分工与常用手法，最后给出一套可以直接套用的日志分析命令。读者只需要会基本的命令行操作，读完应当能独立完成大多数行级文本的筛选、改写与统计。

为什么是这三件工具

Linux 上做文本处理，绕不开 grep、sed、awk。它们都诞生于 Unix 早期，行为稳定，几乎所有服务器都预装。三者都以行为单位，都从标准输入读、向标准输出写，因此可以首尾相接。grep 负责哪些行留下，sed 负责留下的行变成什么样，awk 负责从行里算出什么。分工不是强制的，但拆开之后每条命令只做一件事，组合起来更清楚。

三件工具的分工

过滤、改写、计算

grep 的核心动作是匹配：给定一个模式，输出匹配的行，或者输出不匹配的行。它不改变行内容，也不理解字段，只关心「这一行里有没有我要的东西」。因此 grep 最适合做第一道筛子：从海量日志里挑出 5xx，从代码库里找出某个函数调用，从配置文件里找出未注释的配置项。

sed 的核心动作是替换与编辑：按行号或正则定位，然后删除、插入、替换。它面向的是「文本的形状」，比如把 Windows 换行改成 Unix 换行，把连续空行压成一行，把某段配置里的旧域名换成新域名。sed 的默认行为是逐行处理，读一行、执行脚本、输出一行，只有显式使用多行命令时才会把多行放进同一个模式空间。

awk 的核心动作是计算：它把每一行自动切成字段，允许你按字段写条件、做累加、建关联数组，最后在 END 里输出汇总。awk 是一门小语言，有变量、数组、条件、循环、函数，但本文只把它用在文本处理场景里，不展开成一门通用编程语言教程。记住它的定位：当你要「按某个字段分组计数」「按某列求和」「输出格式化的多列报表」时，awk 比 cut、sort、uniq 的组合更直接。

三者都是流式处理器：读一行、处理一行、输出一行，处理完就丢弃，常驻内存只有缓冲区那么大。真正吃内存的是 sort，它要对全部输入排序，数据量大时会用临时文件做外部排序。这解释了为什么「awk 统计 + sort 排序」在超大文件上仍然可行，而「先把所有行读进数组再排序」的写法迟早会出问题。

grep：先决定哪些行留下

基本正则与扩展正则

grep 的模式默认是基本正则表达式（BRE）。BRE 把 +、?、|、(、)、{、} 都当作普通字符，想要它们具备元字符含义，必须加反斜杠，写成 \+、\?、\|、\(、\)、\{n\}。这种设计来自早期的 ed 与 grep，今天看来相当别扭。扩展正则表达式（ERE）则把这些符号直接当元字符，grep 通过 -E 启用：

grep 的边界

第一，-P 并非到处都有。CentOS 7 自带的 GNU grep 支持 -P，Ubuntu 16.04 的 GNU grep 也支持；macOS 自带的是 BSD grep，不认 -P。脚本要在 macOS 上跑，就不能依赖 PCRE。替代方案是用 -E 表达同样的意思，复杂到 -E 写不出来时，再考虑 perl -ne 或 pcregrep，但要接受额外的依赖。

第二，二进制文件。grep 发现文件里有 NUL 字节时，默认不再逐行输出，只打印一句「Binary file … matches」。日志被截断、混进了压缩包或数据库文件时就会遇到这种情况。确认要看内容可以加 -a 强制按文本处理，想跳过二进制文件则用 -I。递归搜索时我一般加 -I，避免终端被一堆乱码刷屏。

第三，性能。grep 的正则引擎对普通模式做了优化，逐行扫描 2GB 日志通常在几秒到十几秒的量级。拖慢速度的常见原因不是文件大，而是模式写得差：两端都加 .* 会让引擎在每一行反复尝试，大量分支的或运算也会增加回溯。能确定是固定字符串时用 -F，比正则快一个档次；只关心是否存在时加 -q，命中即退出，不必读完整个文件。

打印、删除、插入与追加

默认情况下 sed 会把模式空间的内容自动打印到标准输出，-n 关闭这个自动打印，只有遇到 p 才输出。因此 sed -n '5,10p' 是「只看这一段」，而 sed '5,10p' 会把 5 到 10 行打印两遍。d 则相反，它删除模式空间并立即开始下一轮，后面的命令不再执行。把 -n、p、d 组合起来，就能从大文件里截取片段而不必读完整份文件。

多行模式：N 与 D

awk：按字段做计算

记录、字段与两个特殊块

awk 的基本单位是记录，默认一条记录就是一行，$0 表示整条记录，$1 到 $NF 表示各个字段，NF 是当前记录的字段数。NR 是已经读过的记录总数，跨文件累加；FNR 是当前文件内的记录号，每换一个文件就归零。处理多个日志文件时，用 FNR == 1 判断「新文件的第一行」，用 NR == 1 只能判断「所有文件的第一行」，这是两者最实际的区别。

默认分隔符是任意数量的空格或制表符，连续空白算一个分隔符，行首行尾的空白会被忽略。这个默认值对 Nginx 日志刚好合适，所以前面的命令没有写 -F。遇到 CSV、冒号分隔的 passwd、制表符分隔的报表，就要显式指定：

awk 不适合复杂 CSV

awk 的字段切分是「按分隔符切」，它不理解引号。-F, 遇到 "Zhang, San",28 这样的行，会把引号里的逗号也当成分隔符，字段立刻错位；字段里带换行的 CSV，更是从「一行一条记录」这个前提上就不成立。gawk 提供了 FPAT 可以按「字段的模样」匹配，但这不是 POSIX awk 的能力，CentOS 7 的 gawk、Ubuntu 16.04 的 mawk、macOS 的 BSD awk 行为并不一致。简单 CSV 且确定没有引号、没有换行时，awk 足够；一旦涉及转义引号、内嵌逗号、跨行字段，就应该换 Python 的 csv 模块或专门的解析器，不要在原位打补丁。判断标准很简单：如果一条记录可能跨多行，awk 的行模型就已经失效了。

组合起来的几种套路

先筛后算

grep 负责把数据量降下来，awk 负责在剩下的行里计算，这是最常用的两段式。比如只看 5xx，并按接口路径统计：

grep 的模式以请求行结尾的引号开头、以空格结尾，等于锚定状态码字段，不会误匹配字节数或 UA 里的数字。awk 用 sub 去掉查询字符串，把 /api/orders?id=1 和 /api/orders?id=2 归并到同一个接口。awk 自己也能写 $9 ~ /^5/，但先让 grep 缩小输入，脚本更简单，也更容易中途查看样例。

用 sed 取区间

配置文件里常要截取某个块。sed -n '/^server {/,/^}/p' app.conf 会打印从 server { 到下一个 } 的内容，适合结构简单、没有嵌套的同级块。如果块里还有 location 之类的嵌套，第一个 } 就会提前结束，这时应该用能理解括号层级的工具。

xargs 批量处理

需要把「找到的文件」交给下一个命令时，xargs 负责把标准输入变成命令行参数，并在参数过多时自动分批：

执行前先在副本上试跑。文件名可能含空格时，这个写法会拆错参数，应该让上游输出 NUL 分隔、下游用 xargs -0，例如 find /etc/nginx -name '*.conf' -print0 | xargs -0 ...。xargs 空输入时的行为各平台不同，GNU 版本可用 -r 禁止执行一次。

别用无用的 cat

cat access.log | grep error 里的 cat 纯属多余，grep 可以直接读文件，少一个进程、少一次数据复制。需要把多个文件接成一条流时，cat 才有意义：cat access.log access.log.1 | awk ...。判断标准很简单：cat 后面如果只有一个文件，而且下一个命令能直接接受文件名，就删掉 cat。管道本身只在这里作为连接手段出现，Shell 的变量、循环、条件不在本文范围内。

性能、安全与可移植性

大文件怎么跑得更快

第一招是 LC_ALL=C。grep、sed、awk 在 UTF-8 语言环境下要逐字符判断多字节边界，改成 C 语言环境后按字节处理，纯 ASCII 的日志能快出一截：

这个技巧只适用于「模式和数据都是 ASCII」的情况。用 LC_ALL=C 去匹配中文，字节序列会被拆开，结果不可靠。第二招是尽量流式：不要让 awk 把所有行存进数组，数组的大小取决于键的基数，不取决于文件行数；sort 才是真正需要内存或临时磁盘的阶段，可以用 TMPDIR 把临时文件指到大盘。第三招是尽早过滤，grep -q 命中即停，awk 里用 next 跳过不需要的行，都比读完再判断省事。

就地修改与正则风险

-i 之前先备份，这不是形式主义。sed -i.bak 在 GNU 与 BSD 上都能用，至少留下一个可回滚的副本。替换规则先在 sed -n p 里空跑，确认命中行数和内容，再执行写回。正则本身也可能成为风险：嵌套量词如 (a+)+$ 在回溯引擎上会呈指数级爆炸，grep -P 用的 PCRE 正是回溯引擎，遇到不可信的模式或超长行可能卡死。能确定是固定字符串时用 grep -F，必须用复杂正则时加 timeout 限制运行时间：

macOS 默认没有 GNU timeout，脚本里要么装 coreutils 用 gtimeout，要么在服务端执行这类操作。替换内容来自变量时，还要转义替换串里的 & 和反斜杠。

GNU 与 BSD 的差异

本文的命令在 CentOS 7 与 Ubuntu 16.04 上可以直接跑，因为两者都是 GNU 工具；换到 macOS 就会遇到三处典型差异。sed 的 -i 必须带后缀参数，sed -i '' 是 BSD 写法；grep 没有 -P，PCRE 相关的模式要用 -E 重写；awk 是 BSD awk，不支持 gawk 的 gensub、asort、FPAT 等扩展。Ubuntu 16.04 的默认 awk 其实是 mawk，也不支持这些 gawk 扩展，这一点比 macOS 更容易被忽略。

写可移植脚本的原则是只用 POSIX 子集：grep 用 -E 而不是 -P，sed 用 -E 而不是 -r，awk 不碰 gensub 和排序函数，需要这些能力时先检测再降级。确要使用 GNU 版本，可以在 macOS 上通过 Homebrew 安装 gnu-sed、grep、gawk，它们分别以 gsed、ggrep、gawk 的名字出现，脚本里显式调用带前缀的命令，比修改系统默认工具安全。团队脚本还应在开头检查命令是否存在，缺工具时明确报错。

遇到文本处理需求时，先判断它属于哪一类任务，再选工具，最后套用骨架补参数。下表把本文的高频用法压缩成一张速查表，命令中的路径、模式和字段号按实际情况替换。

小结

grep 决定哪些行进入视野，sed 决定这些行变成什么样，awk 决定从这些行里算出什么。三者都以行为单位、都以标准输入输出为接口，因此可以自由拼接，也都可以在 2GB 的日志上保持流式处理。选择工具时先看任务类型，再看数据的规整程度：字段稳定就用 awk，结构复杂或带引号就换真正的解析器。-i 之前备份、复杂正则加超时、跨平台只用 POSIX 子集，是三条能避免大多数事故的纪律。把常用组合固化成脚本时，保留每一步的中间输出，比写一条很长的一次性管道更可靠。
