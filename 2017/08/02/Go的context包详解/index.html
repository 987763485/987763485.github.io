Go 的 context 包详解

本文属于《Go 语言与工程》第 32/78 篇
上一篇系列目录下一篇

一个 HTTP 请求进来之后并发起三个 goroutine 查数据库，用户关掉页面，服务端却什么都不知道，连接池被慢慢吃满——这是很多 Go 服务上线后遇到的第一个真实问题。本文从一个这样的故障出发，讲清 context 的四个方法、取消与超时如何沿调用链传播、值该放什么不该放什么，以及在 HTTP、数据库和 RPC 中如何落地。读者需要会写基本的 goroutine 与 channel；本站已有并发专文，这里只聚焦取消传播与使用边界。

从一次被忽略的取消说起

去年冬天，订单查询接口在晚高峰出现了一批超时。排查下来数据库并不慢，慢的是连接池：池子被占满了，后来的请求全在排队。这个接口收到请求后会并发起三个 goroutine，分别查订单主表、物流状态和用户积分，任何一个返回就写回响应。

问题出在用户取消之后。前端等得不耐烦，点了取消，浏览器断开了连接，可服务端的三个 goroutine 完全不知情，仍然握着连接把 SQL 跑完，再把结果写进一个已经没人读的 channel。一个请求泄漏三条连接，几百个并发就把池子耗光了。更麻烦的是这类泄漏不会报错，只表现为”越跑越慢”，重启之后又恢复正常，很难定位。

根源不是并发写错了，而是这些 goroutine 缺少一个共同的信号：这个请求已经不需要结果了，可以停下来了。Go 给出的标准答案就是 context。它把一次请求的生命周期串成一条链，让上游的取消、超时、截止时间沿着调用链一路传到底层，底层只要在关键位置监听，就能及时退出。

context 是什么

context 从 Go 1.7 起进入标准库，此前它在 golang.org/x/net/context 里，接口与用法基本一致。它定义了一个只有四个方法的接口：

四个方法对应三件事：取消信号、截止时间、少量请求范围的元数据。它们被打包在同一个对象里，以函数参数的形式向下传递，于是天然形成一棵树，父节点一取消，整棵子树都能收到通知，而兄弟分支互不影响。

需要强调的是 Done() 返回的是一个只读 channel，取消时的动作是”关闭”而不是”发送一个值”。关闭 channel 会立刻唤醒所有正在接收的 goroutine，这正是广播语义；如果改用发送，就得为每个监听者准备一份，数量根本无法预知。理解这一点，后面所有的 select 写法都好解释了。

context 的定位是请求范围，不是一个万能容器。它不负责传配置、不负责传依赖，也不应该被当成全局变量的替代品。把边界守住，它就是一个很薄的、可靠的生命周期工具；守不住，它就会变成到处隐式取值的泥潭。

根 context：Background 与 TODO

每棵 context 树都有一个根。标准库提供了两个入口：context.Background() 返回一个永远不会被取消、没有截止时间、也不带任何值的空 context，通常用在 main 函数、初始化、测试和请求的起点；context.TODO() 返回的对象与它完全一样，区别只在语义——TODO 表示”这里还没想好该用哪个 context，先占个位”。

两者都保证非 nil，所以任何接受 context 的函数都不该收到 nil。传 nil 往往不会立刻出错，直到某处调用 ctx.Done() 才 panic，而那时调用栈已经很深，排查成本很高。暂时没有可传的 context 就传 context.TODO()，它是留给未来的标记；确定这是一棵树的起点，才用 context.Background()。

这个区分看似吹毛求疵，实际很有用：评审时看到 TODO，就知道这里还有一条传播链没有接上，而不是一个”合理”的根。

最常见的取消来自 context.WithCancel。它返回一个子 context 和一个取消函数：

子 context 的 Done() 在两种情况下关闭：有人调用了 cancel，或者父 context 被取消。取消函数必须被调用，并且要保证在所有返回路径上都被调用，所以惯例是拿到手就紧跟着 defer cancel()。

不调用会怎样？这个子节点会一直挂在父节点上，直到父节点自己被取消。如果父节点是 Background()，它就永远不会释放，节点上关联的定时器、子节点集合、等待中的 goroutine 都跟着泄漏。go vet 的 lostcancel 检查能拦住最明显的一类，提示信息是 “the cancel function is not used on all paths”，看到这句基本就是漏了 defer。

cancel() 是幂等的，重复调用没有副作用。所以既可以在 defer 里兜底，也可以在某个分支里提前取消，两者不冲突。这让提前退出的代码写起来很自然。

超时与截止时间

手动取消适合”用户已经走了”这种情况，更多时候我们关心的是”最多等多久”。context.WithDeadline 接受一个绝对时间点，context.WithTimeout 接受一段时长，后者内部就是把 time.Now().Add(d) 交给前者，两者产生的 context 行为一致，选哪个只取决于手上有什么。

关键规则是取最小值：子 context 的截止时间不会晚于父 context。父节点只剩 200 毫秒时，子节点传 2 秒也没有意义，实际生效的仍是 200 毫秒。这条规则保证了超时只能收紧、不能放宽，调用链越往下剩余时间越少，与真实的服务依赖关系吻合。

超时触发后 Err() 返回 context.DeadlineExceeded，主动取消则返回 context.Canceled。两者是不同的值，调用方据此区分”我不要了”和”等太久了”：前者通常静默丢弃，后者往往要记一条日志。

用 WithValue 传请求范围的值

context.WithValue 给子 context 挂一个键值对，只能被这棵子树读到。它的设计目标是请求范围的元数据：请求 id、认证后的用户身份、来源 IP 之类，数量少、生命周期与请求一致、下游到处都要用。

也不要用它传业务参数。函数的入参写在签名里，读代码的人一眼能看到依赖；塞进 context 之后依赖变成隐式的，调用方不知道要准备什么，被调方不知道值从哪来，单元测试还得手工拼一个 context。更实际的问题是类型断言，取不到值就是 nil，一次疏忽就是 panic。判断标准很简单：这个值是否所有下游都关心、且与本次请求绑定？是，才放 context；只是一个函数需要的参数，就老老实实写在参数列表里。

取消信号如何向下传播

取消是单向的：父节点取消，所有子孙节点都会收到；子节点取消，父节点和兄弟节点不受影响。这条不对称的规则让每个函数都能安全地给自己加超时或提前退出，而不会误伤调用方。整棵树的方向始终是从上往下，所以”从上游拿 ctx、原样往下传”是最重要的纪律。

数据库与 RPC 调用

database/sql 从 Go 1.8 起提供 QueryContext、ExecContext 和 PrepareContext，第一个参数都是 context。查询超时或调用方取消时，驱动会中断这次查询并返回错误，不必再依赖各驱动的私有超时设置。

要分清两件事：context 让查询停下来，rows.Close() 让连接回到池子，缺了后者照样泄漏，开头那个故障两个都要修。

RPC 方向以 gRPC 为例，生成的客户端方法第一个参数就是 context，超时随请求头带到服务端；服务端 handler 拿到的 ctx 与客户端同源，客户端取消后服务端也能感知。跨进程传递的少量元数据可以挂在 metadata 上，但不要指望用它搬业务数据，序列化与体积都不合适。

几条必须守住的约定

第一条是位置：context 永远作为第一个参数，名字统一叫 ctx。这是整个生态的默契，签名里一眼就能看出这次调用受谁控制。

第二条是归宿：不要把 context 存进结构体，更不要放进全局变量。结构体是长期对象，context 只属于一次调用，生命周期对不上；存进去之后，同一对象上的不同请求会共用一份取消信号，一个请求取消就波及全部。业务代码里几乎没有需要破例的场景。

第三条是责任：拿到 cancel 就 defer cancel()，不要赌这个分支不会提前返回。go vet 只能检查静态可见的路径，运行时才决定的分支只能靠习惯兜住。

第四条是克制：只有真正需要感知取消的函数才接收 context。给纯计算函数加一个 ctx 参数，除了让签名变长没有任何作用。同理，派生新 context 要有明确目的，加超时用 WithTimeout，加值用 WithValue，不要为了形式统一而随手新起一个根。

常见错误清单

  • 用 context.Background() 切断传播。函数内部需要 context 却另起一个根，上游取消就传不进来，开头那个故障正是这么写的。正确做法是从参数拿，参数没有就补上。
  • WithValue 的键冲突。两个包都用字符串键，后写的覆盖先写的，取出来的类型还可能对不上。键用自定义类型，读取一律 comma-ok。
  • 超时设得比上游还长。上游 500 毫秒就放弃，下游设 3 秒，等于白等；下游应该更短，或者直接复用上游的 ctx，不再新设。
  • 忘记 cancel 导致泄漏。WithCancel 与 WithTimeout 都会在父节点注册子节点，不 cancel 就一直挂着，定时器也不释放，压测时表现为内存缓慢上涨。
  • goroutine 里写回结果时没考虑取消。结果 channel 若是无缓冲的，对端已经走了，发送会永远阻塞。发送同样要放进 select，监听 ctx.Done()。

小结

context 的价值不在于 API 有多丰富，而在于把”这次调用还要不要继续”变成一条显式、可传递的信号。它只向下传播，所以每个函数最该做的，是把上游的 ctx 原样接住；WithValue 只放与请求同生命周期的少量元数据；cancel 一定要调用。守住这几条，goroutine 泄漏和连接池耗尽会少一大半。

场景 用哪个 注意点
需要手动取消 context.WithCancel 必须 defer cancel()
只关心最长耗时 context.WithTimeout 比上游更短
有明确时间点 context.WithDeadline 传绝对时间
传请求 id 与身份 context.WithValue 键用自定义类型
程序入口 context.Background() 不要传 nil
暂时没有可传的 context.TODO() 之后记得替换
