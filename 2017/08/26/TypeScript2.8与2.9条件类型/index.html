TypeScript 2.8 与 2.9 条件类型

本文属于《TypeScript 学习路线》第 29/74 篇
上一篇系列目录下一篇

类型系统能不能像代码一样写 if？当我们希望“传入数组就返回元素、传入单值就原样返回”时，2.4 的泛型、重载和映射类型都只能绕路实现。本文从一个请求封装的真实需求出发，先用手头已有的手段把问题解决一遍，再讨论社区与官方 issue 里正在酝酿的条件类型草案。

需要先交代背景：本文写作时 TypeScript 的当前稳定版本是 2.4，2.8 与 2.9 都还不存在，T extends U ? X : Y 与 infer 只是讨论中的语法，随时可能改名或调整语义，不能当作现有能力使用。文中标注为现有的写法都只用到 2.4 的语法，草案部分会单独注明。

any 让调用点后面的检查全部失效：users.map(...) 与 user.name 都不会报错，因为编译器不知道它们是什么。我们想要的规则很朴素——路径指向集合时返回数组，指向单个资源时返回对象。这是一条类型层面的条件判断，可 2.4 的工具里没有“判断”这个动作。

当时的工具箱包括联合类型、交叉类型、泛型与约束、keyof、索引访问 T[K]、映射类型、字面量类型和函数重载。它们的共同点是“统一变换”：给定一个类型，按同一条规则算出另一个类型。联合类型是求并，映射类型是逐键改写，索引访问是按键取值，没有一个能表达“如果 T 是某种形状，就走这条分支，否则走另一条”。

2.4 的类型推导已经能处理很多复杂情况，缺的是让开发者把这个判断写出来的语法。泛型参数在声明处被约束成一个范围，签名里没有分情况的位置，于是这类需求最后只落到两种写法上：穷举重载，或者退成 any。接下来的三节分别看这三种手段能做到什么程度。

现有手段之一：函数重载

最直接的办法是把每种输入输出组合都写成一条签名。重载的匹配规则是从上往下找第一条兼容的签名，实现签名对外不可见，只负责兜住所有情况：

在调用点，这套写法确实有效：字面量参数会被匹配到对应的签名，list 拿到 User[]，one 拿到 User。但它的代价在三个地方。

第一是数量。每个路径都要单独写一条，二十个路径就是二十条；再加一个布尔参数 withMeta，签名数量立刻翻倍。第二是精度边界。只要路径是拼接出来的变量，比如 '/api/users/' + id，类型是 string 而不是字面量，匹配就会落到最后的 any 兜底，前面的努力全部作废。第三是不可复用。重载只存在于函数声明上，别的泛型代码没法引用“这个函数的返回类型”，也没法把“根据输入决定输出”这件事抽成一个类型，供其他工具函数使用。

重载适合“接口数量有限、调用方式固定”的场合，比如给第三方库补声明；不适合“规则通用、只按形状分支”的场合，那正是条件类型想解决的问题。

现有手段之二：泛型约束与联合类型

第二条路是把“输出由输入决定”写进泛型。2.1 引入的 keyof 与索引访问类型 T[K] 让我们可以表达“取出某个键对应的值类型”，这是 2.4 里最接近条件判断的能力：

这里有两个关键点。K extends keyof T 保证键一定存在于 T 上；T[K] 是索引访问，编译器会把 K 的实际类型代进去，算出属性类型。因为 K 是联合类型，T[K] 自然成为各成员类型的联合，不需要额外的分发逻辑。

这套写法解决了一类问题：输出类型跟着“键”走，但方向固定，只能从对象到属性值，回答不了“T 是不是数组”“有没有 null”。而且约束是单向收紧的：一旦传入的键是动态算出来的 string，K extends keyof T 就不成立，只能退回不带约束的版本，精度随之丢失。

还有一点常被忽略：泛型推导只在调用时发生一次，T[K][] 是延迟计算，规则固定。需求若变成“数组取元素、非数组取自身”，索引访问就表达不了，因为这是两种运算，需要判断来选择。

现有手段之三：映射类型与 keyof 做类型变换

第三条路是映射类型。2.1 一并带来的 Partial、Readonly、Pick、Record 都是它的产物，我们也可以自己写：

{ [P in keyof T]: ... } 这种写法叫同态映射，它会遍历 T 的每一个键，并对每个键施加同一条规则。同态映射还有一个好性质：它会保留原属性的可选性和只读性，Readonly<T> 因此不需要额外处理修饰符。

问题也在这里——规则对每个键都一样。如果想写“值是数组的键保持不变，值是 null 的键去掉 null”，映射类型做不到，因为花括号里没有分支。要对不同键用不同规则，只能拆开键集合，分别映射再交叉：

三条路走下来：重载能表达分支，但只能逐个枚举；泛型和索引访问能“跟着键走”，但方向单一；映射类型能批量改写，但规则必须统一。缺的是一个可以嵌在类型里的三元表达式。

草案构想：把条件写进类型

在社区的讨论和官方仓库的 issue 里，这个缺口通常被描述成一句话：给类型系统加一个三元表达式。草案的写法与值层面的三元几乎一致。至于它最终落在哪个版本号上，当时并没有定论，讨论中 2.8 与 2.9 都被提到，也可能拆成几次发布：

阅读方式要抓住一件事：这里的 extends 表示“可赋值给”，不是类继承。整句读作“如果 T 可以赋值给 U，结果取 X，否则取 Y”。因为它是类型而不是值，所以写在类型别名、参数约束、返回值位置都可以。

条件可以串联成类似 switch 的链式判断，匹配从上往下，第一个成立的分支生效。区别在于它是类型，可以被别的类型引用、组合、再次判断，而重载只能挂在函数上。

第二件必须理解的事是分配律。当条件左侧是一个“裸”的类型参数，而实参是联合类型时，条件会对联合的每个成员分别求值，再把结果合并：

分配律既是威力也是坑。它让“对联合每个成员做同一件事”变得自然，相当于类型层面的 map，后面的 Exclude 全靠它。但它也会带来意外：Boxed<never> 得到 never 而不是 never[]，因为空联合没有成员可分；any 在条件里也有特殊行为，讨论中对它走哪个分支一直没有定论。

flowchart TD
    A[输入类型 T] --> B{T 可赋值给 U 吗}
    B -->|是| C[求值 X 分支]
    B -->|否| D[求值 Y 分支]
    C --> E[得到结果类型]
    D --> E

草案中的 infer：从形状里提取类型

光有分支还不够。很多场景需要的不是“选一个现成类型”，而是“从匹配到的类型里掏出某一部分”，比如从函数类型里掏出返回类型。草案为此引入了 infer：它写在 extends 右侧，占住一个位置，匹配成功后这个名字就能在真分支里使用。

三行用的是同一个套路：先用一个结构去匹配输入，匹配的位置用 infer 命名，再在真分支里把它当作类型使用。(...args: any[]) => infer R 匹配任意函数，R 是返回类型；(infer U)[] 匹配任意数组，U 是元素类型；Promise<infer U> 匹配 Promise，U 是包裹的值类型。匹配不上就落到假分支，ElementType<string> 得到 string 本身。

infer 有两个明确的限制。它只能出现在条件类型的 extends 右侧，不能单独声明；同一个条件里可以出现多个 infer，但绑定顺序、位置能否重复都属于未定稿的细节。函数重载、可选参数、rest 参数在这些位置上的推导规则也只有方向，没有结论。所以这一段只能当作“如果语法这样设计可以这样写”的推演，2.4 的编译器看到 infer 会直接报错。

手写方案的局限

第一个问题是组合爆炸。如果再加一个 unique 布尔参数，签名就要写四条；参数维度每增加一个，数量就乘一次。一个稍微复杂的工具库，声明文件里几百行重载是常态。

第二个问题是不可组合。重载是函数声明的一部分，不能被别的类型引用。“给我一个类型，它表示 toArray 的返回类型”这句话在 2.4 里写不出来，只能复制粘贴签名。反过来，条件类型写成的 ElementType<T> 可以出现在任何类型位置，也能被其他条件继续判断。

第三个问题是维护成本：新增一种输入形状就要改签名列表，还要保证实现签名兼容所有分支；漏掉一条不会报错，只会在调用点悄悄落到 any 兜底，很难在评审里发现。

现在该不该押注草案语法

笔者的建议是：可以关注，但不要在 2017 年的生产项目里按草案写代码。2.4 的解析器不认识 infer，写进 .ts 文件只会得到语法错误，写进注释又不会被执行，两头都没有收益。

现在真正值得做的，是把类型工具集中管理。新建一个只导出类型的文件，比如 src/types/utils.ts，把 ElementType、Nullable、Omit 放进去，业务代码只从这里导入。未来语法落地时，替换面只有这一个文件，语义也有统一的注释可查。

类型契约最好用赋值来测：写一行 const check: string[] = toArray('hello');，返回类型一变，编译立刻失败，比读注释可靠，也不需要额外的测试框架。至于何时跟进新语法，以官方 CHANGELOG 为准，不要依据 issue 里的讨论稿，语法和语义都可能变。

小结

条件类型要解决的是“类型签名里没有分支”这个缺口，T extends U ? X : Y 读作“可赋值则取前者”，配合分配律可以对联合逐成员处理。infer 让类型可以从函数、数组、Promise 等结构里被提取出来，标准库里的 ReturnType、Exclude 一类工具因此只需要两三行。

但在 2.4 上，这些还只是讨论中的草案。当下能用的仍是重载、泛型约束、索引访问和映射类型，它们足以应付大部分场景，代价是枚举与重复。比较稳妥的做法是把这些手写工具收进单独的类型文件，用赋值测试固定契约，等语法真正发布后再一次性替换。
