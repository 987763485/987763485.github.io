Docker 多阶段构建实践

本文属于《Docker 与 Kubernetes》第 7/51 篇
上一篇系列目录下一篇

本文从一个 900MB 的 Go 服务镜像出发，讲清楚 Docker 17.05 引入的多阶段构建如何把编译环境与运行环境拆开。读者应已能写基本的 Dockerfile，读完之后可以为 Go、Node、Java 服务各写出一份精简的运行镜像，并掌握体积验证、缓存顺序、调试与 CI 分阶段构建的做法。

从一个 900MB 的镜像说起

2017 年夏天，笔者接手了一个用 Go 写的内部服务。它功能不复杂：读几个配置、连一个 MySQL、对外提供十几个 HTTP 接口。CI 每次发布都会构建镜像并推送到私有 Registry，直到有一次网络抖动导致发布卡住，我才认真看了一眼 docker images 的输出：这个服务的镜像有 912MB。

把镜像拆开看，九百多兆里真正干活的部分很小。基础镜像是 golang:1.8，它自带 Go 编译器、标准库源码、git、gcc、make 和一整套构建工具；镜像里还躺着 GOPATH 下的项目源码、_test.go 文件、vendor 目录、构建过程产生的中间对象，以及为了排查问题装进去的 curl 和 vim。而容器启动后执行的只有一个十几 MB 的静态二进制，它监听 8080，读环境变量，写日志，仅此而已。

这种镜像的代价是多方面的。发布时要推送九百多兆，内网 Registry 尚可忍受，跨机房就要几分钟；测试环境每次扩容都要拉一遍；几十个服务各存几份，构建机的磁盘很快见底。更麻烦的是安全面：编译器、包管理器、shell、源码全在运行镜像里，一旦应用出现命令执行漏洞，攻击者拿到的不是一台只跑一个二进制的容器，而是一台带完整工具链的机器。构建时用过的私钥、内网地址、临时传入的构建参数，也可能留在镜像历史或源码里。

问题不在 Docker，而在用一张镜像同时承担构建和运行的思路。构建需要的东西很多，运行需要的东西很少，两者的生命周期也完全不同：构建工具只在构建的几分钟里有用，运行镜像却要在生产环境里躺几个月。多阶段构建解决的正是这个错配，它允许在同一个 Dockerfile 里写多个 FROM，前几个阶段负责编译，最后一个阶段只把产物复制进来。

多阶段构建是什么

多阶段构建在 Docker 17.05 中引入，对应 2017 年 5 月发布的 CE 版本。它的语法只有两条新增内容：FROM <image> AS <name> 给阶段起名，COPY --from=<name> 从先前的阶段复制文件。一个 Dockerfile 里可以出现任意多个 FROM，构建时按顺序执行，只有最后一个阶段的文件系统会成为最终镜像；前面的阶段在构建结束后就被丢弃，不会出现在 docker images 的标签列表里，也不会被推送到 Registry。

多阶段构建把选择基础镜像这件事拆成了两次：builder 阶段可以放心用重量级镜像，runtime 阶段则从一个干净的小镜像开始。产物通过 COPY --from 显式搬运，这份搬运清单就是运行镜像的全部内容，也成了可以在代码评审里逐行确认的契约。

阶段命名与引用

AS 后面的名字是该阶段在当前 Dockerfile 内的标识，只在构建期间有效，不会变成镜像标签。命名之后，后面的阶段就可以用 COPY --from=builder 取文件，也可以用 --target builder 只构建到这一阶段。名字建议按职责取，builder、test、assets、runtime 这类比 stage1、stage2 耐读，也不会在阶段增删时失去意义。

-ldflags "-s -w" 去掉符号表和调试信息，一个十几兆的二进制通常还能再小两三成，代价是符号表和 DWARF 被裁掉，事后再用调试器分析 core dump 会困难一些，线上排查要靠保留未裁剪的构建产物。

scratch 是一个空镜像，没有 shell、没有包管理器、没有 /etc/passwd，也没有时区和证书。这既是它体积小的原因，也是它的全部使用约束。Go 程序向外发起 HTTPS 请求时，crypto/x509 会读取 /etc/ssl/certs/ca-certificates.crt；文件不在，握手就会报 x509: certificate signed by unknown authority。同理，time.LoadLocation("Asia/Shanghai") 需要 /usr/share/zoneinfo 下的数据，只设 TZ 环境变量而不拷数据，得到的仍是 UTC。这两件事在开发机上永远不会暴露，因为开发机什么都有。

ENTRYPOINT 必须用 exec 形式，也就是方括号数组。shell 形式会被展开成 /bin/sh -c，而 scratch 里没有 /bin/sh，容器会以 no such file or directory 启动失败。这条规则对 CMD 同样成立。

Node 前端：构建与静态托管分离

前端项目是多阶段构建的另一个典型场景。2017 年主流的单页应用仍然由 webpack 2 或 3 打包，构建产物是一组静态文件，运行时只需要一个能发文件的 Web 服务器。构建阶段要 Node、npm、几百兆的 node_modules，运行阶段一样都用不上。

COPY package.json 单独一行是为了缓存：只要依赖清单没变，npm install 这一层就直接命中缓存，改业务代码不会触发重新下载。这条顺序在多阶段里同样重要，后面讲缓存时会展开。

运行阶段完全没有 node_modules，因为 2017 年的 webpack 构建已经把用到的模块打进 bundle，浏览器执行的是打包后的 JS，服务器只负责把文件发出去。这是前端场景最容易被忽略的收益：单阶段镜像里那几百兆 node_modules 对运行毫无贡献，却要跟着每次发布走。nginx 镜像只有几十兆，加上 dist 通常不到 60MB。

有一个必须做的清理是 .dockerignore。如果构建上下文里带着开发机的 node_modules，COPY . . 会把它整个复制进 builder，覆盖掉容器里刚装好的那一份。macOS 上编译的 native 模块在 Linux 容器里本来就不能用，覆盖之后 npm run build 会报模块加载错误，而且报错位置和真实原因相隔很远。.dockerignore 至少写上 node_modules、dist、.git，顺带也能把构建上下文从几百兆压到几兆。

有时候 node_modules 必须进运行镜像，例如服务端渲染，或者干脆是一个 Node 写的 API 服务。这时运行阶段仍然用 node:6-alpine，但依赖要重装成生产依赖：

Java 服务：Maven 构建与依赖分层

Java 的镜像通常比 Go 和 Node 更臃肿，因为 JDK、Maven 本地仓库、项目依赖加起来很容易超过 600MB。多阶段构建在这里的收益最大，做法也更讲究：运行阶段不仅要换掉 JDK，还要把依赖和业务代码分成不同的层。

builder 阶段先只复制 pom.xml，执行 dependency:go-offline，让 Maven 把依赖和插件下载到本地仓库；之后才复制 src 并打包。这样改一行 Java 代码只会让后面两层失效，依赖下载那一步仍然命中缓存。-B 关掉交互式输出，CI 日志更干净。

运行阶段用 JRE 而不是 JDK。JDK 里的 javac、tools.jar、调试工具在运行时用不到，去掉它们既减体积也减攻击面。target/lib 由 maven-dependency-plugin 的 copy-dependencies 目标生成，配合 manifest 里的 Class-Path，java -jar 就能从同目录的 lib 加载依赖。这个插件要在 pom.xml 的打包阶段绑定好，否则运行镜像里只有 jar，启动时会报 NoClassDefFoundError。

两条 COPY --from 的顺序有讲究：依赖目录先复制，应用 jar 后复制。依赖在两次发布之间通常不变，这一层可以长期命中缓存；jar 每次构建都变，只让最后一层失效。2017 年还没有 Spring Boot 的分层 jar 能力，这种靠 Dockerfile 手动分层的做法是最直接的替代。若依赖很多，可以按变更频率再拆一层，但没有必要为几百 KB 的差异把文件拆得太碎。

-DskipTests 只跳过测试执行，测试代码仍会被编译；如果连测试编译都不想等，可以用 -Dmaven.test.skip=true。笔者倾向于前者，因为测试编译能提前暴露接口不匹配的问题，而真正的测试执行放在 CI 的独立阶段，失败时信号更清晰。

多模块项目要注意：只复制根 pom.xml 时，子模块的依赖解析不全，go-offline 会漏掉一部分；稳妥的做法是把各模块的 pom.xml 按目录结构一起复制，再执行依赖下载。

缓存与顺序

多阶段构建不改变层缓存的判定规则，命中与失效仍然按指令和输入内容计算，原理在本站《Docker 镜像分层与缓存》里已经展开，这里只谈它在多阶段下的用法。多阶段带来的新东西是：每个阶段有独立的层链，builder 的缓存和 runtime 的缓存互不干扰；只要某一步的输入没变，重建时就会直接复用上一次的层。

最常见的顺序错误是把 COPY . . 放在依赖安装之前。源码里任何一个字符变化都会让这一层失效，后面的 npm install 或 mvn dependency:go-offline 跟着重跑，一次构建多花几分钟。正确顺序是先复制清单，装依赖，再复制源码：

这样升级依赖和改业务代码会触发不同的层，日常改代码不会重新拉一遍依赖。前提是 dep ensure 在只有清单的目录里也能工作，实际项目里要验证一次。

ARG 也会参与缓存。构建参数值变了，用到它的那一层就会失效；把版本号、提交号通过 ARG 传进 RUN 里的编译命令，每次发布都会让编译层重跑，这是预期行为。反过来，不要把易变的值传给 ENV 或放在依赖安装之前，否则缓存会被无谓地击穿。

阶段之间的依赖也要顺着缓存设计。runtime 阶段的 COPY --from 只关心源阶段产出的文件内容，builder 内部哪一层变了并不重要；所以 builder 里可以放心加调试工具、跑测试，只要最终产物不变，runtime 的层仍然命中。把测试阶段放在 builder 之后、runtime 之前，测试失败时不会产生新的运行镜像，缓存也不会被污染。

CI 上要额外注意：缓存属于构建机的 Docker daemon，换一台机器就是冷启动。2017 年常见的做法是保留一台固定的构建机，或者让 CI 的 job 尽量落在同一台 agent 上。docker build --cache-from 可以拉取上一次推送的镜像来复用层，但多阶段下它只能恢复最终镜像里存在的那几层，builder 阶段的缓存不在推送内容里，编译仍然要从头跑。这是 17.05 时期多阶段构建的一个现实限制，规划 CI 时间时要把这部分算进去。

调试多阶段构建

多阶段构建的调试比单阶段麻烦一点：构建在哪个阶段失败，最终镜像里都看不到现场，因为失败时根本没有最终镜像。办法是把中间阶段变成一个可以运行的目标。

--target 告诉构建器只构建到指定阶段，后面的阶段不执行，也不要求它们语法上能通过。这让运行阶段还没写好、先调 builder 成为可能。进去之后可以检查 /out 下有没有产物、go env 是否符合预期、ls /etc/ssl/certs 是否为空；确认之后再跑完整构建。

如果怀疑是缓存导致的问题，例如明明改了文件，构建却仍在用旧内容，可以加 --no-cache 重建一次做对照。日常不要习惯性加这个参数，它会把所有层重新跑一遍。缓存本身的行为可以用构建输出的 Using cache 行确认，哪一层开始不再显示缓存，问题就出在那一层。

COPY --from 报找不到文件时，错误信息只会说某个路径不存在，不会告诉你源阶段里到底有什么。这时同样先构建 builder，再 ls 对应目录。笔者遇到过一次：Go 的构建产物输出到了 /go/bin，而 Dockerfile 写的是 /out，本地开发时因为 GOBIN 被设置过，谁也没发现，直到 CI 上换了干净环境才暴露。

安全收益与边界

多阶段构建最直接的安全收益是缩小运行镜像的内容。编译器、包管理器、shell、源码、测试工具都不在最终镜像里，应用一旦被攻破，攻击者面对的是一个几乎没有工具的容器：没有 curl 下载载荷，没有 gcc 现场编译，没有 git 翻源码找配置，也看不到构建时留下的内网地址。这不是万能的隔离，但它确实提高了从一个接口漏洞走到控制整台机器的门槛。

注意 USER 只改变进程的 uid，不改变文件属主。COPY --from 保留了源文件的 uid/gid，如果文件是 0600 且属于 root，非 root 进程读不到。17.05 的 COPY 还没有 --chown 参数，稳妥的做法是在 builder 里 chmod 成运行用户可读，或者确保复制进来的文件权限是 0644。这个问题在 scratch 里尤其难查，因为既没有 shell 也没有 ls，只能靠应用报的权限错误反推。

第三个收益与秘密有关。构建时需要的令牌、私有仓库口令，可以只出现在 builder 阶段，不进入最终镜像。但要小心两种泄漏路径：一是把秘密写进 ARG，构建参数可能留在镜像历史里；二是用 COPY 把带令牌的配置文件复制进去，即使后面在同一个 RUN 里删掉，文件仍留在那一层。正确做法是让 CI 在构建前完成登录，Dockerfile 里不出现凭据；必须传入时只让它在 builder 的 RUN 内生效，并且不要推送 builder 镜像。

需要清醒的是，多阶段构建不等于安全镜像。运行镜像仍然共享宿主机内核，基础镜像里的 OpenSSL、musl、nginx 仍可能有漏洞；scratch 只是把包的数量降到零，应用自身的漏洞一个也不会少。基础镜像要固定到具体版本而不是 latest，并纳入定期重建和扫描的流程。体积小也让扫描结果更干净。

在 CI 里，多阶段构建的最大价值是把测试、构建、发布拆成三个可以独立失败的目标。以一个带测试阶段的 Dockerfile 为例：

常见坑

第一个坑是 scratch 里没有 shell。HEALTHCHECK CMD curl -f http://localhost:8080/health 会失败，因为 shell 形式和 curl 都不存在；写成 exec 形式也没有用，scratch 里同样没有可用的探针程序。入口点写成 ENTRYPOINT ./start.sh 也不行，脚本需要解释器。解决办法要么在应用里实现健康检查接口，由外部监控或编排层探测，要么换用 alpine 作为运行镜像，接受几十兆的体积。FROM scratch 之后也不能再写 RUN，任何安装动作都必须提前在 builder 里完成。

第二个坑是静态链接失败。最常见的原因是为了某个库打开了 cgo，例如 SQLite 驱动、图像处理库，或者代码依赖了系统解析器。编译能过，容器一启动就报找不到文件或共享库。判断方法是在构建产物上跑 file 或 ldd，ldd 显示 dynamic 就说明还有动态依赖。要么关掉 cgo 换纯 Go 实现，要么把运行镜像换成与 builder 同 libc 的 alpine，而不是 scratch。

第三个坑是证书与时区。前者表现为所有对外 HTTPS 请求报 x509: certificate signed by unknown authority，后者表现为日志时间差八小时、定时任务在错误的时间触发。两者都不会在构建阶段报错，只在运行阶段出现。修复方式就是前面 Go 案例里的两行 COPY --from，并且在 builder 里先装好 ca-certificates 与 tzdata。如果运行镜像基于 alpine 而不是 scratch，也要确认这两个包确实存在。

第四个坑是环境不继承。每个 FROM 都从零开始，builder 里的 WORKDIR、ENV、USER、安装的包都不会带到 runtime。ARG 更绕：写在第一个 FROM 之前的 ARG 只能用在 FROM 行里，想在某个阶段内使用，必须在那个阶段里再声明一次。笔者见过 ARG VERSION 写在文件开头、却在 runtime 阶段读不到的情况。类似的还有复制路径写错：COPY --from=builder /build/target/*.jar /app/ 只会报一句找不到文件，不会告诉你源阶段里实际有什么。路径尽量写死到具体文件名，复制完用 docker run --rm image ls -l 验证。

与单阶段构建的取舍

多阶段不是默认答案。判断标准有两条：构建环境与运行环境的差异有多大，镜像被拉取的频率有多高。

解释型服务如果构建只是复制几个文件，运行镜像和构建镜像又是同一个基础，多阶段的收益接近于零，反而多一层间接。真正值得用的是两类：编译型语言，工具链比产物大一个数量级；前端项目，node_modules 只服务于构建。只要出现这两种情况，收益立刻按几百兆计算。

代价是 Dockerfile 变长、多一个要维护的基础镜像，复制清单也成了隐式契约：应用新增模板或迁移脚本时忘了加 COPY，本地构建成功，容器启动才报错。缓解办法是给运行镜像加一条冒烟测试，启动后请求一个真实接口。可读性上，两三个阶段通常比单阶段更清楚，因为职责写在 FROM 上；超过四五个阶段就开始难跟。Docker 17.05 之前的环境用不了这套语法，只能沿用两个 Dockerfile 加 docker cp 的旧办法。

应用类型对照

应用类型 builder 镜像 runtime 镜像 注意点
Go 静态服务 golang:1.8-alpine scratch 关闭 cgo，拷证书与时区，exec 形式
Go 含 cgo golang:1.8 alpine:3.6 保持 libc 一致，不能 scratch
Node 静态站点 node:6-alpine nginx:1.12-alpine 只拷 dist，忽略宿主 node_modules
Node SSR 或 API node:6-alpine node:6-alpine 生产依赖重装，native 模块同 libc
Java 服务 maven:3.5-jdk-8-alpine openjdk:8-jre-alpine 依赖分层拷贝，测试单独阶段

小结

多阶段构建的核心是把构建产物当成唯一契约：builder 阶段可以臃肿，runtime 只接受显式复制进来的文件。改造时优先处理编译型服务与前端项目，两到三个阶段足够；先复制依赖清单再复制源码，调试用 --target 进入中间阶段，CI 用独立目标跑测试。使用 scratch 时，静态链接、CA 证书、时区数据三件事缺一不可。
