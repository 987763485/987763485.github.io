Systemd 服务管理入门

很多团队把服务从 CentOS 6 迁到 CentOS 7 之后，第一件不习惯的事就是 /etc/init.d 下的脚本不再被直接调用，取而代之的是 systemctl 和一堆 .service 文件。本文从这段迁移经历出发，讲清 systemd 的 unit 是什么、一个 service 文件怎么写、启停与日志怎么配合，以及笔者踩过的几个坑。读者只要写过启动脚本、用过 service 命令，就可以顺着读下去。读完后应该能独立为一个自研服务写出可用的 unit，并在它启动失败时定位原因。

从 SysV init 到 systemd

要理解 systemd 的设计，先回想 SysV init 的工作方式。系统启动时，init 读取 /etc/inittab 决定运行级别，然后按 /etc/rc.d/rc3.d/ 里 S01、S02 这样的编号顺序，依次执行指向 /etc/init.d/ 脚本的符号链接。这套机制的问题也很明显：所有服务串行启动，前一个脚本不返回，后一个就得等着。为了让网络先就绪，管理员只能靠编号和脚本里的 sleep 凑顺序，机器越多，开机越慢。

systemd 换了一套思路。每个服务被描述成一个 unit，unit 里声明自己需要什么、应该在谁之前或之后启动，剩下的调度交给 systemd。互不依赖的服务可以并行拉起，需要顺序的地方用依赖表达，而不是用编号猜。此外还有两点变化值得注意：一是按需启动，socket 或 D-Bus 请求到达时才拉起对应服务；二是日志统一，服务的标准输出和标准错误被 journald 接管，不再需要每个程序自己往 /var/log 写文件、自己做轮转。

对从 SysV 迁移的团队来说，systemd 还留了一条兼容路径：systemd-sysv-generator 会在开机时扫描 /etc/init.d/，为旧脚本生成临时 unit，所以老服务不会立刻失效。但这只是过渡手段，生成的 unit 无法表达精细的依赖和重启策略，该重写还是要重写。想看开机时间花在哪里，可以用 systemd-analyze blame 按耗时排序，再用 systemd-analyze critical-chain 看关键路径，这比在 SysV 下靠时间戳推算舒服得多。

迁移时最容易犯的错，是把启动脚本原样搬进 ExecStart。SysV 脚本通常自己处理后台化和 PID 文件，而 systemd 希望服务在前台运行、由自己托管生命周期。理解这一点，后面的字段就好理解了。

本文的环境是 CentOS 7（systemd 219）与 Ubuntu 16.04（systemd 229），两者的 unit 语法一致，个别字段的可用性会随版本略有差别，文中遇到时会说明。

unit：systemd 管理的基本单位

systemd 把所有可管理的对象统称为 unit，用文件后缀区分类型。日常打交道最多的是下面几种：

  • .service：一个后台服务或一次性任务，对应原来的 init 脚本。
  • .target：一组 unit 的集合，用来表达“系统到达某个状态”，可以粗略对应 SysV 的运行级别。multi-user.target 相当于带网络的命令行模式，graphical.target 相当于图形模式。
  • .timer：定时触发器，到点后去启动它关联的 service，是 crontab 的替代方案之一。
  • .socket：监听一个套接字，有连接进来才启动对应的 service，实现按需拉起。
  • .slice：把进程分组，配合 cgroup 限制一组服务的 CPU、内存，名字类似目录层级，如 system.slice、user.slice。

unit 有两种状态要区分。active/inactive 描述当前是否在运行，enabled/disabled 描述是否设置了开机自启。一个服务完全可以处于 enabled 但 inactive，这表示它开机会启动，此刻没跑。用 systemctl list-units --type=service 看当前加载了哪些服务，用 systemctl list-unit-files --type=service 看系统里所有 unit 文件及其自启状态，后者包含没在运行的。

启动过程可以用一张简图概括：

flowchart TD
    A[内核挂载根文件系统] --> B[启动 systemd PID 1]
    B --> C[读取 unit 与依赖关系]
    C --> D[并行启动 default.target 的依赖]
    D --> E[拉起 network、日志、各 service]
    E --> F[进入 multi-user.target 或 graphical.target]
    F --> G[systemctl 可随时启停单个 unit]

图中“并行”是关键。启动顺序只由 After/Before 决定，没声明关系的服务谁先谁后并不确定，需要顺序就明确写出来。

[Service] 描述进程怎么跑。Type=simple 表示 ExecStart 启动的进程就是主进程，且它不会自己转入后台。User/Group 指定运行身份，省略就用 root，这不是好习惯。WorkingDirectory 设定工作目录，程序里用相对路径读文件时全靠它。Environment 直接写环境变量，EnvironmentFile 从文件读取，前面的 - 表示文件不存在也不报错。ExecStart 必须是可执行文件的绝对路径，不能写 shell 管道或重定向。ExecReload 定义 systemctl reload 时执行什么，这里给主进程发 SIGHUP 让它重读配置。Restart 与 RestartSec 控制异常退出后的重启。

[Install] 只在执行 systemctl enable 时被读取。WantedBy=multi-user.target 的意思是：把本服务挂到 multi-user.target 的 wants 目录下，开机进入这个 target 时顺带启动。没有 [Install] 段的 unit 可以手动 start，但 enable 会报错，因为它不知道自己该挂到哪。

Type 与 PIDFile：谁才是主进程

Type 是 service 段里最容易选错的字段，因为它决定了 systemd 如何判断“启动完成”以及“该盯着哪个进程”。常见的取值有四种。

Type=simple 是默认值。systemd 执行 ExecStart 后立刻认为服务已启动，然后把该进程当作主进程。适合自己不转入后台、一直占着前台的程序，Go、Node.js 写的服务大多属于这一类。注意“立刻认为启动成功”并不等于进程真的没事，如果程序启动后马上因为配置错误退出，你会看到它短暂 active 然后变成 failed，或者因为 Restart 反复重启。

Type=forking 用于传统守护进程：ExecStart 启动的程序会 fork 出子进程，自己退出，由子进程继续服务。systemd 看到父进程退出，就认为启动完成，但它不知道子进程是谁，所以需要 PIDFile 指向 PID 文件，或者依赖程序自己写对。以 Nginx 为例：

如果 Type=forking 但没写 PIDFile，systemd 会尝试用 GuessMainPID 去猜，猜不准时就管不住真正的进程，systemctl stop 可能只杀掉了已经退出的父进程。反过来，如果程序明明在前台运行，却写成 forking，systemd 会一直等父进程退出，直到 TimeoutStartSec 超时，报一个“start operation timed out”的错误，而进程其实好端端跑着。这是迁移旧脚本时最常见的一类误配。

Type=oneshot 用于执行完就结束的任务，比如初始化数据目录、加载内核模块。它允许写多条 ExecStart 按顺序执行，也常配合 RemainAfterExit=yes 让服务在执行完后仍显示 active。Type=notify 则要求程序主动调用 sd_notify 告诉 systemd“我准备好了”，对启动耗时长的服务最精确，但需要改代码或引入库。

Exec 系列与重启策略

ExecStart 之外，service 段还有一组以 Exec 开头的指令，它们共同描述服务的生命周期。ExecStartPre 在启动前执行，可写多条，按顺序运行，适合建目录、改权限、检查配置；ExecStartPost 在启动后执行；ExecStop 定义停止动作；ExecReload 定义重载动作。所有 Exec 指令都要求绝对路径、不经过 shell，用 /bin/sh -c 包一层虽然能跑，却会把信号和退出码的处理搞复杂，能不用就不用。

不写 ExecStop 时，systemd 默认向服务的 cgroup 发送 SIGTERM，等待 TimeoutStopSec（默认 90 秒），仍未退出就补一个 SIGKILL。这套默认行为按 cgroup 杀，能把服务 fork 出来的子进程一起收走，比手写 kill 脚本可靠。只提醒一句：进程收到 SIGTERM 后要优雅退出，把缓冲刷盘，别走到 SIGKILL 那一步。

Restart 决定进程退出后要不要拉起来，常用取值如下：

  • no：不重启，默认值。
  • on-failure：只有非零退出码、被信号杀死、超时才算失败并重启。最常用。
  • always：无论怎么退出都重启，包括正常退出。
  • on-abnormal：只在被信号杀死或超时时重启，普通失败不重启。

配合 RestartSec=5s 可以避免疯狂重启。还要注意启动频率限制：systemd 219 在 [Service] 段用 StartLimitInterval 与 StartLimitBurst 控制启动次数，默认 10 秒内 5 次，超限后 unit 进入 failed 并不再自动重启。看到 start request repeated too quickly 时，先查程序本身，而不是怀疑 systemd。

重载要单独说。systemctl reload 只在 unit 定义了 ExecReload 时才有效，否则报 “Job type reload is not applicable”。重载适合重新读取配置而不中断监听套接字，但它依赖程序实现，不是 systemd 的魔法。若程序不支持，老老实实 restart，并接受短暂中断。

环境变量、工作目录与运行身份

服务在 systemd 下跑不起来，十有八九和环境有关：通过 systemctl 启动的进程不继承登录 shell 的环境，/etc/profile 里的 export、~/.bashrc 里的 PATH 都不生效。依赖环境变量的程序，必须在 unit 里显式声明。

EnvironmentFile= 从文件读取，适合把密钥、数据库密码这类不便入库的内容放在 /etc/sysconfig/ 下。文件格式是每行一个 KEY=VALUE，不支持 export 前缀，# 开头为注释。路径前的 - 表示文件缺失时忽略。注意它只做文本解析，不会执行 shell，所以 FOO=$(hostname) 这类写法不会被求值。

WorkingDirectory= 设定进程的工作目录，目录必须存在，否则启动直接失败。User= 与 Group= 指定运行身份，切换发生在 ExecStartPre 之后、ExecStart 之前，因此前置命令仍以 root 执行，建目录、改属主正好利用这一点。切到非 root 后，程序读配置、写日志都需要相应权限，这点在把 root 服务改成普通用户时最容易漏。

启停、开机自启与 unit 文件存放

日常操作就那么几条，记住语义比记参数重要：

enable 并不修改 unit 本身，而是在 /etc/systemd/system/multi-user.target.wants/ 下创建一个指向 unit 的符号链接，disable 就是删掉它。这也解释了为什么改了 [Install] 段要重新 enable 一次，旧链接不会自动搬家。

unit 文件有两个主要位置。/usr/lib/systemd/system/ 放软件包自带的 unit，由包管理器维护，升级时会被覆盖；/etc/systemd/system/ 放管理员自己写的 unit 和覆盖配置，优先级更高，两者同名时 /etc 下的生效。只想改一两个字段，可以用 drop-in：在 /etc/systemd/system/ordersync.service.d/ 下放一个 override.conf，只写要覆盖的段和字段。systemctl edit ordersync 会自动建好这个目录并打开编辑器，systemctl cat ordersync 则能看到合并后的最终内容，排查“为什么修改没生效”时很有用。

如果需求是“每天凌晨跑一次清理脚本”，timer 可以替代 crontab：OnCalendar=*-*-* 03:00:00 定义时间，Persistent=true 让关机错过的任务在开机后补跑，执行记录照样进 journal。取舍只点到为止：需要依赖关系、统一日志、错过补跑时选 timer，简单任务用 crontab 更省事。

日志与排查

服务把日志打到标准输出后，就由 journald 接管，用 journalctl 按 unit 过滤：

-p 的级别从 0 到 7，依次是 emerg、alert、crit、err、warning、notice、info、debug，写 -p err 表示 err 及更严重的都显示。--since 除了绝对时间，也接受 "2 hours ago"、yesterday 这类相对写法。

默认情况下日志只存在内存和 /run/log/journal，重启即丢。要持久化，创建 /var/log/journal 目录，确保 journald.conf 里 Storage=auto（目录存在即持久化），再重启 journald。多数发行版默认不建这个目录，所以同一套排障习惯在不同机器上表现可能不同。日志占满磁盘时，用 journalctl --disk-usage 查看，用 journalctl --vacuum-size=500M 或 --vacuum-time=7d 清理，比直接删文件安全。

日志之外，还有几个高频的坑。改完 unit 忘记 daemon-reload 是最常见的一个：systemctl restart 用的是已加载的旧配置，你会以为修改没生效，反复折腾半天。systemctl status 里如果提示 “unit file changed on disk”，就是它在提醒你。

Type 选错则是第二个。程序自己 fork 到后台却写 simple，systemd 盯着那个已退出的父进程，服务显示 inactive 或 failed，可进程还在跑；程序在前台却写 forking，则要等到启动超时。判断依据是程序到底占不占着前台，不确定就先用 Type=simple 试。

环境变量不生效还有两种隐蔽原因：EnvironmentFile 里的文件权限不对，或者写了 export 前缀导致整行被当成一个奇怪的键。用 systemctl show ordersync -p Environment 可以直接看到 systemd 实际拿到的变量。

第四个坑与权限和 SELinux 有关。把程序放到 /opt 下自建目录，SELinux 可能给它一个错误的上下文，进程一读配置就被拒，日志里只有一句含糊的失败，真正的 AVC 记录在 /var/log/audit/audit.log。用 ls -Z 看上下文，用 restorecon -Rv /opt/ordersync 修复，再用 ausearch -m avc -ts recent 确认。CentOS 7 默认开启 enforcing，这个问题比 Ubuntu 上常见得多。另外，服务往 /tmp 写临时文件时，注意 systemd 可能给它独立的私有 /tmp，别的进程看不到，这不是 bug。

最后提醒一句：本文讲的是宿主机上的服务管理。把 systemd 当容器里的 PID 1 是另一回事，镜像里通常不该带 init，这部分不在本文展开。

小结

systemd 用 unit 描述服务，用依赖代替启动顺序，用 journald 收拢日志，核心收益是可控与可观测。写一个 service 的关键只有三件事：选对 Type，让程序在前台运行；写清 ExecStart 与运行身份；需要自启就补上 [Install]。修改 unit 后记得 daemon-reload，排查时先看 systemctl status 再看 journalctl -u，多数问题在这两步就能定位。从 SysV 迁移时，别照搬后台化和 PID 文件逻辑，把生命周期交给 systemd。
