crontab 定时任务配置

从一份 0 字节的备份说起

去年夏天，一位同事把写好的备份脚本挂到一台 CentOS 7 的服务器上。脚本手动执行时一切正常，mysqldump 导出的 SQL 有几百兆，tar 打包后落在 /data/backup 下，文件名带着当天的日期。为了省事，他直接在 crontab -e 里加了一行：

第二天早上，目录里确实多了一个文件，大小却是 0 字节。第三天、第四天也一样。把同一行命令复制到终端里敲一遍，又能生成完整的包。于是问题从”脚本写错了”变成”cron 跑的环境和我的终端不一样”。

真正的原因有两处。一是 PATH：cron 执行任务时只带一个很短的 PATH，脚本里调用的 mysqldump 装在 /usr/local/mysql/bin 下，交互式登录时由 /etc/profile 补进 PATH，cron 根本看不到这个目录，命令以”command not found”失败。二是工作目录：cron 不会切到脚本所在目录，它停在用户的家目录里，脚本里那句 tar -czf backup-$(date +%F).tar.gz ./data 把相对路径解析到了 /root 下面，打包了一个不存在的目录。tar 先把目标文件创建出来，读取目录失败，留下的就是 0 字节。

这个事故几乎概括了 crontab 的全部坑：时间怎么写、任务以谁的身份跑、环境从哪来、输出去了哪里。下面按这几个问题依次展开。本文只谈 cron 的配置与运维，Shell 语法本身不重复，写法上的约定可以参考本站《Shell 脚本编程入门》。

cron 基础：命令、五个字段与特殊写法

crontab 命令只有三个常用参数。crontab -e 编辑当前用户的 crontab，保存后 cron 会在下一次检查时自动加载，不需要重启服务；crontab -l 打印内容；crontab -r 删除当前用户的全部任务，且没有二次确认。笔者习惯在改动前先执行 crontab -l > /root/crontab-20170819.bak，出事时还能捞回来。

每个任务占一行，前五个字段是时间，第六个字段是命令：

五个字段依次是分钟（0-59）、小时（0-23）、日（1-31）、月（1-12）、星期（0-7，0 和 7 都是周日）。取值除了单个数字，还有几种写法：

  • * 表示该字段的每一个取值都匹配，0 3 * * * 是每天 3 点整。
  • */5 表示按步长取，*/5 * * * * 是每 5 分钟一次；10-50/10 是 10 到 50 分之间每 10 分钟。
  • 1-5 表示闭区间，0 9 * * 1-5 是工作日 9 点。
  • 1,15 表示枚举，0 4 1,15 * * 是每月 1 号和 15 号的 4 点。

要留意”日”与”星期”的关系。两者都以 * 开头时，cron 只看被限定的另一个；两者都被限定时，多数实现（包括 CentOS 7 的 cronie）按”或”处理：0 3 1 * 1 是每月 1 号或者每周一，而不是”每月 1 号且为周一”。想表达”且”只能把判断放进脚本，这也是排错时最容易看错的一行。

另一个陷阱是命令里的百分号。crontab 把 % 当作换行符，第一个未转义的 % 之后的内容会被当成标准输入，所以文件名里的 $(date +%F) 必须写成 \%：

除五个字段外，cronie 和 Ubuntu 的 cron 还接受 @ 开头的快捷写法：@reboot 开机后执行一次，@hourly 等价于 0 * * * *，@daily 等价于 0 0 * * *，还有 @weekly、@monthly、@yearly。月名和星期名可用英文缩写，jan 到 dec、sun 到 sat，大小写不敏感，0 9 * * mon-fri 与 0 9 * * 1-5 等价。这些写法依赖实现，BusyBox 的 cron 就不支持，精简镜像里尤其常见，写之前先在目标机器上验证。

用户级与系统级：多出来的用户名字段

用 crontab -e 编辑的内容存在哪里？CentOS 7 放在 /var/spool/cron/<用户名>，Debian 与 Ubuntu 放在 /var/spool/cron/crontabs/<用户名>，权限是 600，属主是用户自己。不要直接用编辑器改这个文件，绕过 crontab 命令容易留下权限和时间戳问题。想给别的用户加任务，用 crontab -u alice -e，这需要 root 权限；谁能使用 cron 由 /etc/cron.allow 和 /etc/cron.deny 控制，两者同时存在时以 allow 为准。

系统级配置有三处，格式和用户级不完全一样。/etc/crontab 与 /etc/cron.d/ 下的文件，在五个时间字段和命令之间多一个用户名字段，以 /etc/cron.d/app-backup 为例：

也就是说，系统级任务可以指定以哪个用户运行，而用户级任务的身份由 crontab 的属主决定，第六个字段直接就是命令。/etc/crontab 适合放系统维护任务；应用自己的任务更推荐在 /etc/cron.d/ 下单独建文件，一个应用一个文件，变更时容易审阅和回滚。这里有三个细节：文件属主必须是 root、权限 644；文件名不能带点，cronie 会忽略 app.conf.rpmsave 这类文件；SHELL、PATH、MAILTO 这类变量要写在任务行之前。

/etc/cron.daily、/etc/cron.hourly 这些目录又是另一种形式，里面只放可执行脚本，不写时间字段，由 anacron 按周期调用。CentOS 7 默认装了 cronie-anacron，机器关机错过了执行时间，下次开机后会补跑一次，这一点比普通 crontab 任务省心。

cron 的环境与调试

cron 启动任务时不会加载 /etc/profile、~/.bash_profile 或 ~/.bashrc，它只给进程一个很简陋的环境：HOME 取自 /etc/passwd，LOGNAME 是任务所属用户，SHELL 默认 /bin/sh，PATH 通常只有 /usr/bin:/bin。这就是”终端里能跑、cron 里不行”的头号原因。/usr/local/bin、/opt/... 下的命令，以及 rbenv、nvm 装出来的可执行文件，都不在这个范围内。

还要注意 /bin/sh 和 bash 的差异。CentOS 7 的 /bin/sh 是 bash 的 POSIX 模式，Ubuntu 16.04 的 /bin/sh 是 dash，[[ ]]、数组、source、set -o pipefail 在 dash 下要么报错要么行为不同。crontab 里写成 sh /data/scripts/backup.sh 时 shebang 会被忽略，脚本里的 bash 语法照样失败；要么直接执行脚本让 shebang 生效，要么在 crontab 顶部把 SHELL 设成 /bin/bash。

输出与日志：先让任务开口说话

cron 默认把任务的 stdout 和 stderr 收集起来，通过本机邮件系统发给任务所属用户。CentOS 7 最小化安装通常带着 postfix 但没启动，邮件发不出去，输出等于扔了；有些机器则相反，/var/spool/mail/root 每天涨，一封封 “command not found” 没人看。所以第一件事是决定输出去哪：在 crontab 顶部写 MAILTO="" 关掉，或者重定向到文件。

重定向的写法有顺序讲究。>> /var/log/backup.log 2>&1 表示先把标准输出追加到文件，再让标准错误指向标准输出当前的目标，两者都进日志；写成 2>&1 >> /var/log/backup.log 则是先把标准错误接到终端，再把标准输出接到文件，错误信息照旧进邮件。&> 是 bash 的简写，crontab 默认用 /bin/sh 时不一定认，统一用前一种最稳。

排查时先看 cron 自己的日志。CentOS 7 的 /var/log/cron 由 rsyslog 写入，能看到任务被调度的记录，包括执行用户和完整命令行；Ubuntu 16.04 默认没有这个文件，等价内容是 /var/log/syslog 里的 CRON 行，用 grep CRON /var/log/syslog 或 journalctl -u cron 查。要记住这类日志只证明”cron 启动了任务”，不证明任务成功，成功与否得看脚本自己的日志和退出码。

脚本侧的几条约定

cron 只负责按时把进程拉起来，进程内的健壮性要脚本自己保证。几条开销很小、收益很大的约定：

第一行写 #!/bin/bash，紧接着 set -euo pipefail：命令失败就退出，引用未定义变量报错，管道中任意一段失败都能被感知。set -e 有盲区：命令在 if 条件或 || 之后不会触发，但对”一步失败就整体失败”的备份任务够用。再加一个 trap 'echo "failed at line $LINENO" >&2' ERR，日志里就能看到失败位置。

第二是加锁。备份跑得比预期久，下一次调度又来了，两个进程同时写同一个文件，结果通常是文件损坏。flock 在 CentOS 7 和 Ubuntu 16.04 上都可用：

-n 表示拿不到锁立即退出，不排队；timeout 3600 给整个任务设上限，超时后发送 TERM 并返回 124。锁文件放 /var/lock 或 /run/lock，别放 /tmp，那里可能被清理。如果脚本内部加锁，可以 exec 9>/var/lock/backup.lock 后用 flock -n 9 || exit 0，效果一样。

第三是退出码和日志要能对上。脚本每条关键步骤打一行带时间戳的日志，失败时用非零退出码结束，crontab 里可以用 || 接告警，监控也能靠退出码采集。别用 exit 0 掩盖失败，这比没有日志更难查。

时间与时区：容易被忽略的一层

cron 按系统本地时区解释那五个字段，读的是 /etc/localtime，timedatectl 可以查看当前时区。很多云主机的默认时区是 UTC，图省事没有改，结果 crontab 里写的”凌晨 2 点”实际是北京时间上午 10 点，备份和业务高峰撞在一起。要么把系统时区改成 Asia/Shanghai，要么在写任务时自己换算，最怕两种机器混用。

如果不想动系统时区，CentOS 7 的 cronie 支持在 crontab 顶部写一行 CRON_TZ=Asia/Shanghai，让这个文件里的任务按指定时区计算。这是实现相关的扩展，Ubuntu 16.04 自带的 cron 并不支持，用之前要在目标机器上验证，不能当成通用写法。

夏令时是另一个坑。切换那天凌晨 2 点到 3 点的时刻可能不存在，也可能出现两次，落在窗口里的任务就会跳过或重复执行一次。国内没有夏令时，但服务器若按海外时区配置就绕不开。稳妥的做法是把对时间敏感的任务放到凌晨 4 点以后，或者用 @daily 加脚本内的日期判断，让任务具备幂等性——重复跑一次不出错，比精确到某一分钟更重要。

容器里的 cron 与运维实践

把 crontab 搬进容器，第一道坎是 PID 1。镜像的启动命令一般是应用进程，cron 守护进程不会自己起来；就算装了 cronie，也要用 crond -n 让它前台运行（Debian 系镜像是 cron -f）。用 & 把 cron 丢到后台再启动应用，日志会丢、信号收不到，容器退出后还留下孤儿进程。比较稳妥的两种做法：应用容器里不装 cron，另跑一个 sidecar 容器专门执行定时任务，通过 HTTP 接口或 docker exec 触发；或者由宿主机上的 cron 调用容器。任务一多、有依赖和重试要求，还是要交给调度系统，cron 只保留系统维护类任务。

运维层面，crontab 最怕的是”没人知道它存在”。建议维护一份任务清单：任务名、所在机器、执行用户、频率、负责人、失败时找谁。每条任务都要有告警出口，最简单的就是 || mail，更规范的是把退出码和日志交给监控采集。/etc/cron.d 下的文件纳入配置管理，用 Ansible、SaltStack 这类工具下发，不要在生产机上直接 crontab -e，变更走评审。同一台机器上 systemd timer 也能替代 cron，日志直接进 journal、还能声明依赖，但在 CentOS 7 与 Ubuntu 16.04 上 crontab 依然是主流。

小结

cron 的坑集中在三件事：时间字段的边界、执行环境简陋、没有反馈。把命令换成绝对路径、在脚本里设置 PATH 并自己 cd、给输出明确去处、用 flock 和 timeout 兜底，大部分事故都能拦住。

现象 原因 排查
生成 0 字节文件 PATH 缺目录或工作目录不对 env -i 复现，日志里打 pwd、env
任务完全不执行 时间字段写错、% 未转义、/etc/cron.d 文件名带点 看 /var/log/cron 或 journalctl -u cron
手动能跑、cron 失败 /bin/sh 为 dash、未加载 profile 脚本首行 #!/bin/bash，显式设 PATH
天天收到邮件 输出未重定向 改为 >> file 2>&1 或 MAILTO=""
同一任务跑了两份 上次未结束又触发 加 flock -n，并设 timeout
某天少跑一次 夏令时或机器关机 核对 timedatectl，改用 anacron 补跑

说到底，crontab 只是一行配置，可靠性来自写配置的人有没有把环境、日志和失败路径想一遍。把这些习惯固定下来，它仍是最省事的定时任务工具。
