TypeScript 与第三方库集成

本文属于《TypeScript 学习路线》第 18/74 篇
上一篇系列目录下一篇

2017 年上半年，我们把一个维护了三年的后台管理页面从 jQuery 迁到 TypeScript。项目不大，几千行脚本，计划是先让编译通过，再慢慢补类型。第一天就卡住了：入口文件里写下 import * as $ from "jquery"，编辑器立刻在 jquery 下面画了红波浪线，提示 TS2307，找不到模块 “jquery” 的声明文件。换成 lodash，报错一模一样。

有人不耐烦，翻出 Node 的类型声明，直接写 const _ = require("lodash")。编译通过了，_ 的类型是 any，调用 _.get、_.debounce 都不报错，看上去问题已经解决。但接下来两周，这类代码成了项目里最危险的部分：方法名拼错不报错，参数顺序写反不报错，lodash 小版本升级后行为变了也不报错。类型安全从入口处就丢了，更麻烦的是 any 会顺着返回值一路扩散，最后连调用方写好的类型标注也形同虚设。

问题不在 TypeScript，而在于编译器根本看不到这个库长什么样。import 只告诉编译器”这里有个模块”，模块里有什么，得靠声明文件来描述。本文按实际接入的顺序，把第三方库的类型来源、安装配置、模块解析、导入写法和常见坑梳理一遍，适合刚开始在存量项目里推行 TypeScript 的读者。

三条路：类型从哪里来

遇到一个库，先别急着写声明。按顺序找一遍，多数情况在前两步就能解决。

先看库自己带没带。打开 node_modules 下该包的 package.json，找 types 或 typings 字段；没有的话，看包根目录有没有 index.d.ts。moment 就属于这一类，声明跟着代码一起发布，版本天然对齐。近两年用 TypeScript 写的新库，大多也会自带。

再查 DefinitelyTyped。这是社区维护的声明仓库，发布在 npm 的 @types 作用域下，包名是原包名前加 @types/。jquery、lodash、express 这些老库都在里面。用 npm view @types/xxx version 探一下，有版本号就说明有货。

最后才是自己写。只有三种情况值得动手：库是团队内部的、库已停止维护且社区没有声明、库刚升级而 @types 还没跟上。第三种最好只在本地补一份临时声明，等上游更新后删掉，不要顺手往 DefinitelyTyped 提 PR，除非你打算长期维护。

顺序不能反。先写声明再发现 @types 已经存在，两套声明会打架；装了 @types 却发现库自带类型，一样会报重复定义。判断依据始终是包里的文件，不是博客里的经验。

但 synthetic 这个词是重点：它只让类型检查闭嘴，不生成任何互操作代码。TS 编译到 commonjs 时会把默认导入改写成 require("lodash").default，而 CommonJS 模块没有 default 属性，运行时拿到的是 undefined。如果整条链路由 Babel 或打包工具做模块转换，它们会补上互操作，才碰巧能跑。所以纯 tsc 项目里，对 CommonJS 库老老实实用 import * as；只有确认构建链会处理默认导入，才打开这个开关。

同理，import { debounce } from "lodash" 这种命名导入在声明层面就不成立，声明写的是整体导出，得改成 _.debounce 或单独引入 “lodash/debounce”。

全局库：script 标签引入的 jQuery

存量页面往往还是用 script 标签引 jQuery，没有模块系统。这时 @types/jquery 末尾那句 export as namespace $ 起了作用：它把模块里的导出声明成一个 UMD 全局，脚本文件里不 import 也能直接用 $ 和 jQuery。

问题出在”脚本文件”四个字上。一个 .ts 文件只要出现顶层 import 或 export，它就是模块，模块里看不到 UMD 全局，必须显式导入。迁移时最典型的怪现象就是：同一个项目，老文件里 $ 正常，新文件里报找不到名称 $，原因就是新文件加了 import。

声明里的导出形态要和运行时对应。UMD 包常用 export =，ES 模块风格用 export default 加具名导出，写错形态，检查通过、运行时却拿到 undefined。全局脚本类库没有模块，就不能用 declare module，而是在全局 d.ts 里写 declare var Foo: ...，两者别混用。

渐进式补类型是个好习惯：先声明入口函数，返回值先用宽松的接口，实际用到哪个字段再补哪个。每次只补当前真正调用的部分，比一次照抄文档更不容易写错，也方便在 review 里核对。唯一不能做的，是把所有成员都标成 any——那等于绕一圈又回到 require。

类型与运行时不一致

声明是二手信息，运行时才是一手事实。不一致通常来自三处。

一是库升级了，@types 没跟上。新增的方法没有声明，调用就报错；删掉的方法声明还在，编译通过，运行时才炸。升级主库和升级 @types 应该当成同一个动作，放进同一次提交，这是最省事的预防。

二是声明本身写错。DefinitelyTyped 由社区维护，签名写反、可选参数标成必填并不罕见。遇到疑似问题，先写一个最小复现，对照库的文档和源码确认，再去提 issue 或在本地覆盖，别急着改自己的调用。

三是 skipLibCheck。打开它只是让编译器不再检查 d.ts 内部的类型一致性，可以绕过第三方声明之间的冲突，也能加快编译。但它不修正错误签名：你的调用仍然按错误签名检查，运行时该错还是错。把它当止痛药，别当治疗。

版本冲突与迁移策略

@types 之间的依赖也会打架。典型症状是”两个不同路径下的同名类型不兼容”，比如两个包各自依赖不同版本的 @types/react，React.Component 被当成两个不同的类型。先看依赖树：

输出里出现多个版本，先 npm dedupe 尽量提升，仍然不行就在 devDependencies 里锁成同一个精确版本。2017 年 npm 5 已经默认生成 package-lock.json，团队里用 yarn 的则靠 yarn.lock，本质都是把解析结果固定下来，避免今天能编译、明天装完就红。

迁移到 TypeScript 的存量项目，最忌讳”先全量 any 再慢慢改”。更现实的做法是先把第三方边界收口：所有对 lodash、jQuery、请求库的调用集中到 src/lib 下的几个适配文件，适配层对外只暴露自己定义的函数和类型，内部允许暂时用 any，但要显式标注并登记。业务代码只依赖适配层，等边界稳定，再逐个把内部的 any 换成真实类型，最后才打开 noImplicitAny 和 strictNullChecks。

这样做的原因是 any 的扩散路径被切断了：库升级、声明写错、版本冲突，影响都停在适配层，不会渗进业务代码。反过来，如果一开始就在页面里直接调 _.get，后面想收紧类型，等于把整个项目重读一遍。

小结

第三方库集成，说到底是给编译器补一份它能理解的契约。判断顺序始终是：库自带类型优先，其次 @types，最后才自己写；自己写也只写当前用到的那部分，别用一行简写把整个模块变成 any。

工程配置上有三件事值得一次做对：@types 装进开发依赖并与主库版本对齐；模块解析显式固定为 node，别让 module 的改动把它带偏；别名在编译器和打包器两边保持一致。导入形态则要看模块本质：CommonJS 库用 import * as，默认导入要想清楚运行时由谁做互操作；script 引入的全局库靠 export as namespace，模块文件里再补一句 declare var。

声明与运行时不一致时，先核对两边版本，skipLibCheck 只是让编译器少说话，不是修复。最后，用一层适配把第三方调用收口，让 any 有明确边界，再逐步替换。TypeScript 2.5 刚发布，这套流程不会因为小版本升级而改变，真正要花时间的始终是边界梳理，而不是找哪个开关。

库的类型来源 引入方式 注意点
库自带（moment） import * as moment from "moment" 升级库时一并验证声明
@types（lodash、express） import * as _ from "lodash" 版本对齐，避免与自带声明重复
全局库（jQuery，script 引入） export as namespace，模块内补声明 UMD 全局在模块文件里不可见
自写声明（内部库） declare module "foo" 写最小成员 别留一行简写，别全 any
完全无类型 适配层封装，显式 any 标注 定期清理，防止扩散
