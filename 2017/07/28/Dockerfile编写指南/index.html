Dockerfile 编写指南

本文属于《Docker 与 Kubernetes》第 5/51 篇
上一篇系列目录下一篇

上周同事把一个 Node 服务交给我部署，Dockerfile 只有六行：FROM node:6、RUN apt-get update、RUN apt-get install -y build-essential python、COPY . .、RUN npm install、CMD npm start。它确实能跑，构建十分钟，启动之后页面也能打开，于是这份文件在仓库里躺了半年。直到要上线，问题才一个个浮出来：镜像 1.2GB，改一行业务代码也要等十分钟，容器里的进程以 root 身份运行，docker stop 之后要等满十秒才退出，日志里还有被硬切断的连接。

这份 Dockerfile 没有语法错误，错的是写法。指令的语义、层的顺序、用户与信号，每一个细节都在给后面接手的人挖坑。本文按一份真实文件的改造顺序，把构建指令和启动指令过一遍，说明每条指令到底做了什么、什么时候会踩坑、应该怎么写。目标是让这份文件从“能跑”变成“可以交付”。层与缓存的原理、多阶段构建的完整用法另有专文，这里只在必要处点到为止。

基础指令：FROM、RUN、COPY 与 ADD

FROM：一切的起点

FROM 必须是文件里第一条有效指令（ARG 除外），它决定了后面所有指令的运行环境。最常见的误用是写 FROM node:latest：今天构建出来的是 Node 8，下一个大版本发布后又会变成别的样子，同一个文件在不同时间产出不同镜像，出了问题也无从复现。正确做法是锁定具体的小版本与变体，例如 FROM node:6.11-slim。生产镜像还应写全 registry 地址。

RUN：每条命令都是一层

RUN 在构建时执行命令，并把结果固化成镜像的一层。写 RUN 有三个习惯值得养成。第一，把相关的安装动作合并成一条，用 && 连接，并在同一条命令里清理缓存；分成多条 RUN 时，后一条删除的文件仍然留在前一条产生的层里，体积一点没少。第二，让失败尽早暴露，shell 形式下先写 set -e，避免前面的命令失败、后面的命令继续跑。第三，RUN 只做构建期的事，启动命令交给 CMD 和 ENTRYPOINT。层如何复用、缓存何时失效，《Docker 镜像分层与缓存》已经讲透，这里不再展开。

RUN 也有 exec 形式，写作 RUN ["apt-get", "install", "-y", "curl"]。它不经过 shell，变量、通配符和管道都不会展开，日常用不到。

COPY 与 ADD：默认选 COPY

COPY 把构建上下文里的文件复制进镜像，语义单一：源、目标，需要跨阶段时加 --from。ADD 在 COPY 之上多了两个能力：源是本地 tar 包时自动解压，源是 URL 时直接下载。这两个能力都是坑。URL 形式不会校验内容，也不会解压远程的 tar 包，下载下来的文件权限固定为 600，而且只要 URL 不变这一层就永远命中缓存，上游更新了也不会重新拉取。tar 自动解压还会把解压动作藏起来。经验规则是：需要复制就用 COPY；确实要解压本地 tar 包时才用 ADD，并在注释里写清楚。远程文件应当用 RUN curl -fSL ... && tar ... 显式处理，至少还有机会加校验和。

WORKDIR、ENV 与 ARG

WORKDIR 设置后续指令的工作目录，目录不存在会自动创建。它比 RUN cd /app 可靠，后者只影响当前那条命令，下一条又回到根目录。同一个文件里可以多次出现 WORKDIR，写相对路径时基于上一次的值。

ENV 设置的环境变量会写进镜像，容器运行时依然存在，docker inspect 里能查到，因此适合放应用的默认配置，例如 ENV NODE_ENV=production、ENV PORT=8080。ARG 只在构建期有效，构建结束后不进入容器的运行环境，适合放版本号、下载地址这类构建参数。边界要分清：运行时要读的用 ENV，只在构建时决定行为的用 ARG。ARG 还有一个隐患，它会出现在镜像历史里，这一点在讲秘密时还会提到。

启动指令：CMD 与 ENTRYPOINT

两种形式

CMD 和 ENTRYPOINT 都支持 shell 形式与 exec 形式。shell 形式写成 CMD npm start，Docker 会把它包装成 /bin/sh -c "npm start"；exec 形式写成 CMD ["node", "server.js"]，进程直接由 exec 启动。这个区别在构建阶段无关紧要，在启动阶段却决定了一切。

谁负责启动，谁负责参数

CMD 提供默认的启动命令，docker run myapp:1.0.0 /bin/sh 会把它整个覆盖掉。ENTRYPOINT 提供固定的可执行程序，后面的 CMD 则退化成它的默认参数。两者同时存在时，docker run myapp:1.0.0 --port 9000 里的参数会先替换 CMD，再拼到 ENTRYPOINT 之后。想临时换掉入口，可以用 docker run --entrypoint /bin/bash myapp:1.0.0。所以通用的组合是：ENTRYPOINT 用 exec 形式写固定程序，CMD 写默认参数；普通业务镜像只写一条 exec 形式的 CMD 也够用。

信号传递

容器里的 1 号进程很特殊：内核不会替它执行默认的信号处理，发给它的 SIGTERM 如果没有被显式捕获，就等于没发。shell 形式下 1 号进程是 /bin/sh，sh 默认不转发信号，应用根本收不到 SIGTERM。docker stop 于是只能等完默认的十秒宽限期，再发 SIGKILL 强制杀掉，正在处理的请求被直接切断。这就是开篇那十秒的来历。

exec 形式让应用自己成为 1 号进程，Node 里加一段 process.on('SIGTERM', ...) 就能优雅关闭。如果应用确实需要 shell 做少量初始化，可以安装 tini 一类的最小 init，或者在 docker run 时加 --init（1.13 起可用），由 Docker 注入负责转发信号与回收僵尸进程的 1 号进程。Nginx 可以用 STOPSIGNAL 指定停止信号。用 docker top 可以确认 1 号进程是不是应用本身。

基础镜像与层的顺序

alpine、slim 与 scratch

选基础镜像本质上是选一组系统库。alpine 只有几 MB，用 musl 作为 C 库，而主流发行版和绝大多数预编译二进制都基于 glibc。差异平时看不见，碰上 node-gyp 编译的 addon 或预编译二进制就会暴露，报找不到符号甚至“not found”。遇到这种情况可以装 libc6-compat 缓解，但更稳妥的做法是先确认依赖链里没有强依赖 glibc 的组件，再决定是否换用 alpine。

debian:stretch-slim 或官方的 node:6.11-slim 保留了 glibc 和 apt，体积比完整版小一大截，兼容性却和普通 Debian 一致。scratch 是空镜像，只能放静态编译的程序，Go 服务常用；它没有 shell、没有包管理器，docker exec 进去连 ls 都没有，出问题时只能靠日志和外部工具。

体积、兼容性、可维护性很难同时拿满：先保证能跑，再用 slim 压体积，最后才考虑 alpine。

多阶段构建一句话

如果镜像里还留着编译工具链，说明构建阶段和运行阶段没有分开。17.05 起支持的多阶段构建正是为解决“构建工具留在镜像里”而出现的，写法和取舍见《Docker 多阶段构建实践》，本文不展开。

把变化少的放在前面

层的顺序直接决定缓存命中率。COPY . . 放在 npm install 之前，任何一次代码改动都会让依赖安装重跑，构建时间从几十秒变成十分钟。正确顺序是先 COPY package.json、再 RUN npm install、最后复制其余源码；只要依赖清单没变，安装层就一直复用。这条规则的细节和缓存失效的判断方法同样在《Docker 镜像分层与缓存》里，这里只记住结论。

构建上下文与 .dockerignore

docker build . 结尾那个点不是“当前目录”，而是构建上下文：Docker 客户端会把整个目录打包发给守护进程，再由守护进程按 COPY 和 ADD 取文件。客户端和守护进程还可以不在同一台机器上，这份传输就更实在。项目根目录里有 node_modules、.git、日志和测试数据时，上下文动辄几百 MB，每次构建都要先传一遍。

.dockerignore 就是给这份打包排除文件用的，语法与 .gitignore 类似，一行一个模式，! 表示例外，支持通配符。至少要排除依赖目录、版本库元数据、日志、本地环境文件和构建产物：

以非 root 用户运行

开篇那份文件没有 USER，容器里的 Node 进程就是 root。很多人觉得“容器是隔离的，root 无所谓”，但容器共享宿主机内核，root 能做的事情比想象中多：挂载进来的数据卷，容器里写出的文件在宿主机上属主就是 root；一旦应用被拿下，攻击者拿到的就是一个 root shell，配合内核漏洞还可能逃逸到宿主机。应用很少非绑 1024 以下端口不可，默认用普通用户运行才稳妥。

另外两点。第一，非 root 用户不能绑定 1024 以下的端口，应用监听 8080 一类的端口，再用 -p 80:8080 映射出去。第二，USER 只影响进程身份，不会自动改变已存在文件的权限，日志目录、上传目录、缓存目录都要提前 chown，否则应用启动后的第一件事就是写文件失败。

端口、健康检查与元数据

EXPOSE 只是一条声明，告诉读文件的人和链接容器“这个镜像打算监听 8080”，它不会发布端口，写不写都不影响 -p。真正发布端口的是 docker run -p 8080:8080 或 compose 里的 ports；-P 则把所有 EXPOSE 的端口随机映射到宿主机高位端口。把 EXPOSE 当成访问控制是常见误解。

LABEL 用来记录元数据，LABEL maintainer="ops@example.com"、LABEL version="1.4.2"、LABEL git.commit="a1b2c3d" 都可以，docker inspect 能直接读到。它不占运行时资源，却能回答“镜像从哪来”。镜像 tag 同样如此：用带语义化版本和 git 短哈希的稳定标签，生产环境不要用 latest，也不要把同一个 tag 反复覆盖。

构建参数与秘密

ARG 的值会留在镜像历史里。用 docker build --build-arg NPM_TOKEN=xxx 传入令牌，再在 RUN 里写进 .npmrc，即使同一条命令末尾把文件删掉，docker history 里依然能看到这个值，镜像推到仓库就等于把令牌公开了。密码、私钥、token 都不应该走 ARG，也不应该出现在任何 RUN 的命令行里。

可行的做法有三类：一是把秘密留到运行时注入，用环境变量、挂载文件或编排工具管理；二是用多阶段构建，在有秘密的构建阶段完成安装或编译，只把产物复制到最终镜像；三是 1.13 之后 swarm 提供的 docker secret，把秘密以文件形式挂进服务。无论哪种做法，原则只有一条：镜像本身不包含秘密，历史里也不留痕迹。

高频错误与指令速查

还有四个错误几乎每个新手文件都会犯。把 apt-get update 和 apt-get install 分成两条 RUN，缓存过期后 install 会拿着旧索引装包；正确写法是用 && 串起来，并在同一条命令里清掉包列表。安装时忘了 --no-install-recommends，apt 会顺带装上推荐包和文档，镜像凭空大出几百 MB。COPY . . 放在依赖安装之后，用宿主机的 node_modules 覆盖镜像里刚装好的那一份。ENTRYPOINT 写成 shell 形式，信号收不到，停止时只能被强杀。

写新文件时对着下表检查一遍，能省掉大部分返工：

指令 作用 常见误用
FROM 指定基础镜像 用 latest，不锁版本
RUN 构建期执行命令 拆成多条，清理失效
COPY 复制上下文文件 放在依赖安装之前
ADD 复制并解压或下载 用 URL 下载且不校验
WORKDIR 设定工作目录 用 RUN cd 代替
ENV 写入运行期环境变量 用来存秘密
ARG 构建期参数 传密码，留在历史里
CMD 默认命令或参数 shell 形式，收不到信号
ENTRYPOINT 固定入口 shell 形式，参数无法追加
EXPOSE 声明端口 误以为会发布端口
HEALTHCHECK 健康探测 镜像里没有探测命令
USER 切换运行用户 一直留在 root
LABEL 记录元数据 不写版本与来源

小结

一份可交付的 Dockerfile，标准不是“构建成功”，而是镜像够小、构建够快、进程够规矩、秘密不留在历史里。锁定基础镜像版本，按变化频率排好 COPY 与 RUN，用 .dockerignore 控制上下文，用 USER 降权，用 exec 形式和 HEALTHCHECK 让进程可被管理。这些都不难，难的是每条都坚持。
