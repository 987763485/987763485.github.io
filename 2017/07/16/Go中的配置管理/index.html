Go 中的配置管理

本文属于《Go 语言与工程》第 12/78 篇
上一篇系列目录下一篇

一个把测试环境指到生产库的下午，让我开始认真对待“配置从哪来”这个问题。本文梳理命令行参数、环境变量与配置文件三种来源，给出一个按层覆盖的 Load() 实现，并讨论校验、脱敏与热更新这些容易在复盘里被反复提起的细节。适合已经能写 net/http 服务、准备把代码交给别人维护的读者。

从一次事故说起

2017 年春天的一个下午，测试同学在群里问：为什么集成测试把刚造的数据删了，界面上却冒出几万条陌生订单。答案不复杂——测试环境跑的那份二进制，连的是生产库。连接串写死在 storage/db.go 顶部的一个常量里，有人为了“临时验证”改成了生产地址，提交时忘了改回来，另一次合并又把它带了进去。真正让人难受的不是这次误操作，而是排查花了两个小时：没有人说得清这个进程到底读了哪份配置，因为配置散落在常量、init() 里的 os.Getenv 和一段只存在于某台机器上的 JSON 文件里。

事故之后我们做的第一件事，是把所有配置项列成一张表：从哪来、默认值是什么、改了要不要重启。下面就从这张表说起。

三种来源与优先级

12-Factor 应用有一条原则是“在环境中存储配置”：代码与配置分离，同一份构建产物在不同环境里跑。落到 Go 服务上，常见来源有三种，各自解决的问题并不相同。

命令行参数面向“这一次运行”。调试时加一个 -log.level=debug，或者临时打开某个开关，用完即弃，不必改任何文件。它的生命周期最短，也最适合运维人员手动干预。

环境变量面向“这一台机器、这个容器”。容器平台与 PaaS 几乎都只提供环境变量这一种注入方式，同一份镜像在 dev、staging、prod 之间靠它区分。凡是每个环境都不同的值，比如数据库地址、外部服务的密钥，都应该走这里。

配置文件面向“这个项目本身”。项数一多，环境变量会变成几十个难以检索的名字；有层级、需要注释、需要随代码一起评审的结构，写在文件里更清楚，比如日志切割规则、路由白名单。

四层优先级由此确定：命令行参数高于环境变量，环境变量高于配置文件，配置文件高于代码里的默认值。越靠近运行现场的来源越具体：命令行表达“这一次”的意图，环境变量表达“这一个环境”的意图，文件表达“这个项目”的默认。

flag：把参数绑定到结构体

flag 是标准库，够用且没有外部依赖。它有三种定义方式，最实用的是 flag.StringVar 这类把值直接写进变量的函数：第一个参数是变量地址，正好可以指向配置结构体的字段。

默认值就是第三个参数，它同时承担着文档的作用：-h 会把参数名、默认值和说明一起打印出来，所以说明文字要写清楚单位与合法范围。flag.Parse() 解析的是 os.Args[1:]，遇到 -h 或 --help 时会打印用法后退出；单横与双横在这里等价，-port 和 --port 都能识别，但同一份代码里最好统一。

有两个细节值得单独说。其一，flag.String 返回的是指针，值要等 Parse() 之后才可靠，在 Parse() 之前解引用读到的是默认值，这种“看起来能跑”的误用很难在 review 里被发现。其二，测试里不要用全局的 flag.CommandLine，它出错时会直接退出进程；用 flag.NewFlagSet("app", flag.ContinueOnError) 更可控，也方便在同一个测试进程里反复解析。

flag 适合少量、扁平、一次性的参数。项数一多，命令行会长到没人愿意敲，而且密码之类的值不该走命令行——ps 和 shell 历史都会把它留下来。

环境变量：Getenv 与 LookupEnv

os.Getenv 只返回一个字符串。键不存在时它返回空串，键存在但被设成空串时它也返回空串，这两种情况在业务上往往含义完全不同：前者是“没配，用默认值”，后者可能是“明确关掉某个功能”。os.LookupEnv 多返回一个布尔值，正好补上这个缺口。

命名上统一加应用前缀，再按模块分层：APP_DB_HOST、APP_DB_PORT、APP_LOG_LEVEL。前缀能避免与系统变量撞车，比如 PATH、HOME、HOSTNAME；分层则让 env | grep APP_ 一次列全。读取动作要集中在一处，不要让 os.Getenv 散落在各个包里——散开之后就没人能回答“这个值到底从哪来”，而这正是开篇那场事故的根因。

必填项空值即失败，可选项空值视为未提供。这条规则要写进注释，否则下一个人会把空串当成合法值传下去。

配置文件：JSON、YAML 与查找顺序

标准库自带 encoding/json，不需要任何依赖，缺点是它不支持注释、不允许尾逗号，人工手改时一个逗号就能让服务起不来。YAML 支持注释和层级，可读性更好，2017 年常用的是 gopkg.in/yaml.v2，按 GOPATH 的习惯要 vendor 进 vendor/gopkg.in/yaml.v2，构建时会优先使用 vendor 目录里的副本。TOML 结构扁平时更直观。选型经验：项少、由程序生成的用 JSON；项多、需要注释、由人维护的用 YAML。

路径查找按由具体到通用的顺序：-config 显式指定最优先；其次是环境变量 APP_CONFIG；再是当前目录的 config.yaml；最后是 /etc/app/config.yaml。找到第一个就停，不要合并多份文件，否则“到底生效了哪份”又会变成排查时的谜题。要注意相对路径依赖工作目录：go run 时是项目根目录，systemd 启动时可能是 /，两者读到的文件完全不同，生产环境一律传绝对路径。

分层合并：一个 Load 函数

合并的难点不是顺序，而是“这一层有没有提供这个值”。Go 的结构体零值无法区分“没写”和“写成了 0”，所以文件层用指针字段接收，只有非 nil 才覆盖：

Load() 把四层按顺序叠上去，命令行必须最后应用，因此 flag 先解析到独立的 flagValues，再统一合并，而不是让它直接写进最终配置：

    B --> C[环境变量]
    C --> D[命令行参数]
    D --> E[校验并启动]

注意端口用 0 表示“命令行没提供”，用户真想传 0 就表达不出来；更稳妥的是用 fs.Visit 遍历真正设置过的 flag。任何“0 是合法值”的配置项都不能用哨兵判断。

配置结构体与类型设计

结构体按模块嵌套，Server、DB、Log 三段与 YAML 的层级一一对应，读者打开文件就知道哪一项属于哪一块。字段必须导出，否则 yaml.Unmarshal 写不进去；tag 用小写下划线，和 YAML 风格保持一致。

端口与地址要拆成两个字段。把 ":8080" 或 "0.0.0.0:8080" 存成一个字符串，看起来省事，实际上既不好校验端口范围，也容易在拼接 IPv6 地址时出错：

启动校验与敏感信息

校验要在启动时做完

配置错误的代价，取决于它被发现的时间点。端口越界如果在监听时才发现，进程已经初始化了一堆东西；数据库地址写错如果等到第一次查询才暴露，要等到有流量才知道。所以 Load() 的最后一步是校验，失败就直接返回错误，让进程退出。

校验函数把能查的都查一遍，收集起来一次性报出，而不是遇到第一个错就返回——一次改完五个问题，比来回启动五次舒服得多：

错误信息里必须带配置项的名字。只写“端口非法”，运维还得回头翻文档；写成 server.port=70000 超出 1-65535，并且提示它可能来自 APP_SERVER_PORT，对方就能自己解决。数据库连接串可以用驱动自带的解析函数先过一遍，mysql.ParseDSN 之类的解析器能提前拦住格式错误，比在连接阶段收到一个含糊的握手失败要好。

敏感信息不进仓库

密码、密钥、证书私钥，一律不写进仓库，也不写进镜像。本地开发用 config.local.yaml，把它加进 .gitignore；生产环境的值通过环境变量注入。仓库里可以放一份 config.example.yaml，只保留键名和占位符，新同事照着填。

日志是另一个泄漏点。启动时打一行 log.Printf("%+v", cfg) 很常见，这一行会把密码原样写进日志文件，而日志往往会被收集到中心服务器，保留期以月计。安全的做法是给敏感类型实现 String()，输出时把值换成星号；或者提供一个 Sanitize() 返回副本，打印前统一走它。命令行参数同样不能放密码，ps 和 shell 历史都看得到。

热更新：SIGHUP 与并发

配置改完，是重启还是重载？重启简单，但会断开连接、清空本地缓存，发布频繁时体验很差；SIGHUP 重载不用停进程，适合调日志级别、限流阈值这类纯数值。代价是代码里多了一条并发路径。

并发读写的坑在于“半个配置”。如果重载时逐个字段赋值，读方可能看到新端口配旧超时的中间状态；如果读方还持有旧结构体的指针，字段被并发改写就是数据竞争。atomic.Value 的用法是整体替换指针，读方 Get() 一次拿到不可变快照，天然没有撕裂；用 sync.RWMutex 也可以，但每次读都要加锁，收益不大。要点只有一条：配置对象一旦发布就不再修改，重载等于换一个新的。

不是所有配置都能热更。监听地址和端口要重建 listener，数据库连接串要重建连接池，worker 数量往往和已启动的 goroutine 绑定，这些都只能重启。判断标准很朴素：这项配置是否需要重建某个资源。需要重建的，重启；纯数值、纯开关的，才值得做热更。另外，重载失败时要保留旧配置，不能先清空再加载，否则一次手滑的 YAML 就能让服务失去全部配置。

多环境与几个常犯的错误

文件组织上，config/base.yaml 放公共项，config/dev.yaml、config/staging.yaml、config/prod.yaml 只放差异，APP_ENV 决定叠加哪一份。这个变量必须校验：取值不在白名单里就报错退出，不要静默退化成 dev，那等于把开发配置带上了生产。生产文件里也不放密码，留给环境变量。

容器里没有“改配置文件再重启”的便利，同一份镜像要跑三个环境，配置只能在启动时注入：一是环境变量，docker run -e 或 compose 的 environment 段；二是挂载文件到 /etc/app/config.yaml。值少且敏感走环境变量，项多有层级走文件。无论哪种，镜像里都不该出现任何与环境相关的值。更远的分发方案是配置中心，比如 Consul、etcd，但那要配套的权限与审计，不在本文范围内。

几个反复出现的错误

os.Getenv 分不清“没配”和“配成空”，必填项会被静默放过，统一换 LookupEnv。YAML 用了 tab 会直接报错，同级键差一个空格则会被解析成子级，port 莫名其妙变成 server 的子项，报错只给行号，改完单独跑一次解析最快。相对路径依赖工作目录，systemd 的 WorkingDirectory 和 go run 不一样，读到的可能根本不是你以为的那份文件。配置被 %+v 打印进日志，密码随之进入日志平台，这是最容易被忽略的一处泄漏。环境变量名拼错则完全没有提示，程序安静地用了默认值；启动时把每个配置项的来源打一行，能省下大量猜测。

小结

配置管理的目标只有一个：让“这个进程读了什么”随时可以回答。默认值、文件、环境变量、命令行四层依次覆盖，命令行最后赢；结构体按模块拆分，时长与地址用合适的类型；启动时一次校验完；敏感值不进仓库、不进日志；能热更的只有不需要重建资源的项。

开篇那张表，新项目可以直接照着填：

配置项 来源 默认值 是否热更
server.host 文件 / flag 0.0.0.0 否
server.port 文件 / flag 8080 否
server.timeout 文件 / flag 5s 是
db.host 环境变量 无，必填 否
db.max_open 文件 / 环境变量 20 否
log.level 文件 / 环境变量 info 是
log.file 文件 空，输出到 stdout 否
