TypeScript 类型推断与收窄

本文属于《TypeScript 学习路线》第 8/74 篇
上一篇系列目录下一篇

一个函数按参数不同返回字符串或数字，调用方为了省事在每一处都写 as string，某天新增一个分支，编译依然通过，线上却抛出了 toUpperCase is not a function。这类问题的根源往往不是类型系统不够强，而是我们没有把“我知道”变成“编译器知道”。本文以 TypeScript 2.4 为基准，梳理类型推断的几条来路、控制流收窄的规则，以及 2.x 在闭包、属性访问和异步代码上的能力边界，适合已经能写接口、但仍在被 any 和断言包围的前端与 Node 开发者。

类型推断解决的是“不写类型时，编译器能知道多少”；控制流收窄解决的是“在同一段代码里，编译器能否根据条件把宽类型缩小”。两者合起来，才是 TypeScript 在 2.x 阶段真正好用的部分。理解它们，目标不是炫技，而是知道什么时候可以省略标注、什么时候必须补上，以及什么时候断言会骗过编译器。

推断从哪里来：初始化、返回值、上下文与公共类型

推断不是一条规则，而是几套机制在不同位置起作用。同样是 const，写在变量上、写在对象属性上、写在数组元素上，结果并不一样；同样是函数，返回值的位置和回调参数的位置，推断方向也相反。先把四个来源分开看，后面的收窄才有落脚点。

函数返回值推断

不写返回类型时，编译器会收集函数里所有 return 表达式的类型，再求一个最佳公共类型。分支返回字符串和数字，结果就是 string | number；分支返回同一个类的不同子类，结果可能是公共基类。

返回值推断让内部函数写起来很轻，但它有两个明显的边界。第一，递归函数无法只靠自身推断出返回类型。编译器在分析函数体时又遇到了对自身的调用，只能把返回类型当成 any，并在开启 noImplicitAny 时报错：

最佳公共类型

数组字面量和条件表达式会用到最佳公共类型。编译器在所有候选类型里找一个“大家都能赋值给它”的类型；找不到时，2.x 的退路往往很粗糙：

Circle 和 Square 没有公共基类，最佳公共类型找不到可用的共同成员，2.x 常见的结果是退到 {}，非公共属性自然无法访问。解决方式不是责怪推断，而是在声明处写清楚：const shapes: Array<Circle | Square> = [...]。最佳公共类型适合简单同构数据，遇到多形状对象、类层次或需要保留字面量的场景，显式标注比让编译器猜更可靠。

推断负责“尽量少写”，标注负责“在边界上说清楚”。两者不是对立的：好的 TypeScript 代码通常只在边界标注，让函数体内部享受推断，而不是每一行都写类型。

字面量类型与拓宽

字面量类型是推断系统里最容易被低估的一环。"loading" 不只是一个值，也可以是一个只包含该值的类型；true、false、1、-1 同样可以成为类型。它们本身没有多少操作，却是后面可辨识联合能够收窄的前提。问题在于，编译器并不会在所有位置都保留字面量，它会根据位置的可变性决定是否“拓宽”。

拓宽指的是把字面量类型提升为它所属的宽类型："a" 提升为 string，1 提升为 number，true 提升为 boolean。是否拓宽，取决于这个位置以后能不能被改写：

原则可以概括为：需要参与判断的值在声明处保留字面量，其余值接受拓宽，不要为“看起来精确”给每个变量都加标注。前者是可辨识联合的基础，后者是让代码保持可读性的前提。

泛型推断：从实参到类型参数

泛型函数在调用时可以完全不写类型参数，编译器会从实参反推。这个机制让 first([1, 2, 3]) 得到 number | undefined，而不需要写成 first<number>([1, 2, 3])：

推断的方向是从参数到类型参数，再从类型参数回到返回类型。返回类型本身通常不参与反推，除非调用结果处已经有一个明确的上下文类型。2.4 开始支持把返回类型作为推断目标，但它的作用是让上下文更早地约束类型参数，而不是让一个毫无线索的调用凭空猜出 T。

还有一类退化容易被忽略：any 参与的推断。any 在推断里像黑洞，任何与它结合的类型参数都会变成 any，后续访问全部失去检查：

泛型把推断的责任推到调用处：公开签名要保证不写类型参数也能得到有用的结果；一旦退化成 {} 或 any，应把它当成 API 设计问题，而不是在每个调用处补断言。

上下文类型：回调、事件与 Promise 链

上一节提到匿名回调的参数可以自动获得类型，这里把这个机制再往下拆一层。上下文类型并不是“编译器读了函数体再猜参数”，而是先有一个期望的函数类型，再用它去检查函数表达式。期望类型来自调用点的签名、变量的显式标注、对象字面量的目标接口，或者返回值位置的标注。检查是双向的：参数从目标类型获得类型，返回值则被目标类型约束。

控制流收窄：typeof、instanceof、in 与比较

收窄发生在控制流分析里。编译器沿着 if、else、switch、return、throw、&&、|| 和条件表达式走一遍，在每个位置维护“这个变量当前可能是哪些类型”。类型守卫表达式负责把当前类型集合切成两部分：满足条件的一部分进入真分支，剩下的进入假分支。

最常用的是 typeof。它能区分 JavaScript 的几种基本类型，也会把 null 单独暴露出来：

typeof 能识别的结果包括 "string"、"number"、"boolean"、"undefined"、"function"、"object" 和 "symbol"。需要注意的是 typeof null === "object"，所以用 typeof value === "object" 判断对象时，null 也会进入真分支。正确写法是先排除 null，或者用 value !== null && typeof value === "object"。这个坑来自 JavaScript 本身，收窄只能忠实反映它，不能替我们修正。

收窄还支持提前返回和逻辑组合。if (!value) return; 之后的代码里，value 已经是排除掉空值后的类型；if (user && user.profile) 的右侧能享受到左侧的收窄；switch 的每个 case 也会分别收窄。这些规则组合起来，能让大部分“先判断、再使用”的代码完全不依赖断言。真正的难点不在单个守卫，而在跨语句、跨函数、跨异步边界时，收窄还能保留多久。

守卫的核心风险在于：编译器完全信任这个签名，不会验证实现。上面的函数如果只检查了 id 就返回 true，raw.name 在类型上仍然是 string，运行时却可能是 undefined。所以守卫必须检查谓词类型声称的全部必要字段，并且不能有副作用；它是一份用代码写成的契约，写错比不写更危险。另一个限制是谓词类型必须能赋给参数类型，参数用 any 最灵活，但也意味着入口处少了一层检查，适合放在解析外部数据的边界上，而不是业务逻辑内部。

可辨识联合把守卫的思路变成结构：每个成员有一个字面量标签，switch 标签时，每个 case 自动收窄到对应成员。真正的技巧在 default 分支，用 never 做穷尽检查：

如果以后给 State 增加一个 kind: "empty" 的成员，却忘了加 case，state 在 default 里就不会是 never，赋值语句立刻报错。这个报错的位置非常准确：它指向漏掉的分支，而不是某个遥远的调用处。反过来，如果标签被写成 string 而不是字面量，switch 无法排除任何成员，default 里的 state 仍是整个联合，穷尽检查也就失效了。标签的字面量类型是可辨识联合能够工作的前提，这一点比记住语法更重要。

default 里返回 never 类型的值看起来奇怪，但它是合法的，因为 never 可以赋给任何类型。更常见的写法是调用一个 assertNever 函数并抛出异常，既满足类型检查，也在运行时兜底。无论哪种写法，目标都一样：让“新增成员但忘记处理”从运行时问题变成编译期错误。

断言与收窄的边界

as 是“我说了算”，! 是“我保证非空”。两者都只改类型，不生成运行时检查，也不转换值。as 只检查两个类型是否足够重叠，! 只是从类型里去掉 null 和 undefined：

这些写法编译期都合法，运行时没有任何保护。断言只适合已经做过运行时校验，或测试夹具等完全可控的场合；其余情况应该用守卫或显式判空。

收窄有三道边界。闭包里，let 变量可能被重新赋值，2.x 不会把外层的收窄带进回调；先赋给 const 可以保留。属性访问上，函数调用可能改掉属性，编译器却仍相信旧判断；数组下标和别名也不参与收窄。异步代码里，await 期间其他任务可能修改对象，绑定没变不代表内容没变：

真实数据、迁移与对照表

数组方法的推断比直觉保守。filter 不会因为回调排除了 null 就改变元素类型，结果仍是 (T | null)[]；find 和 Map.get 在 strictNullChecks 下都返回 T | undefined；Map 的泛型参数同时约束键和值，cache.get(1) 会直接报错；JSON.parse 返回 any，这个 any 会污染后续推断。这些地方要么用类型谓词，要么用守卫，要么先判空：

迁移的顺序比工具更重要。先处理边界：HTTP 响应、localStorage 和第三方库的返回值，定义接口并用守卫把 any 挡在入口。然后打开 noImplicitAny，让隐式 any 显形；一次性全开往往报错太多，可以按目录或按公共层分批。接着删除函数体内部的冗余标注，只保留参数、返回值和导出类型；再打开 strictNullChecks，逐个处理 find、Map.get 和可选属性。最后清理 as 和 !，每删一个就补一个运行时检查。先开 noImplicitAny 能拿到真实清单，先加类型更容易渐进；更稳的做法是在小范围先开标志、同时补边界类型，不要为了消错而写 any。

写法 推断结果 收窄是否生效 建议
let x = "a" string 否，已拓宽 需要字面量就标注
const x = "a" “a” 是 可用于判别
const o = { kind: "a" } kind: string 否 接口标注字面量
arr.filter(v => v !== null) (T | null)[] 否 改用类型谓词
map.get(k) V | undefined 判空后生效 先检查再使用
JSON.parse(s) any 否 边界处加守卫
"text" in node 不收窄 否，2.4 的限制 自定义守卫
x as T T 强制 仅在验证后使用
x! 去掉空值 强制 确认非空再用

小结

推断让代码保持轻量，收窄让编译器参与证明。边界处写清类型，运行时不确定的数据用守卫收口，断言只留给已经验证过的值。理解 2.x 在闭包、属性和异步上的边界，比记住多少种守卫语法更重要。
