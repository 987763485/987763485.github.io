shebang 与三种执行方式

脚本的第一行通常长这样：

这行叫 shebang，# 加 ! 告诉内核：请用后面的解释器来执行这个文件。它必须是文件的第一行、前两个字节，#! 与路径之间不能有空格。一个常见故障是在 Windows 上编辑过脚本，行尾变成 CRLF，内核拿着 /bin/bash\r 去找解释器，报 bad interpreter: No such file or directory，用 dos2unix 转一下就好。

#!/bin/bash 与 #!/bin/sh 的区别不在名字，而在两个发行版里 /bin/sh 指向谁。CentOS 7 的 /bin/sh 是 bash 的符号链接，以 sh 模式启动，行为接近 POSIX；Ubuntu 16.04 的 /bin/sh 是 dash，一个更小更快的 POSIX 实现。同一份 #!/bin/sh 脚本，在 CentOS 上能跑，在 Ubuntu 上可能因为用了 [[ ]]、数组或 function 关键字而失败。判断原则很简单：脚本里用了任何 bash 专有语法，就写 #!/bin/bash；追求可移植，就老老实实只写 POSIX 支持的东西。

写好之后要给执行权限：

./deploy.sh 让内核读取 shebang，用指定的解释器执行；当前目录不在 PATH 里，所以 ./ 不能省。bash deploy.sh 则是显式启动一个 bash 进程，把文件当参数读进去，shebang 那一行只会被当成注释，写了 #!/bin/sh 也照样按 bash 跑，这恰好掩盖了移植性问题。同理，sh deploy.sh 在 Ubuntu 上会用 dash 解释，不兼容的语法会立刻暴露。没有 shebang 也没有执行权限时，./deploy.sh 直接失败；有的 shell 会退而用自己的解释器执行，行为取决于调用者，不该依赖。

变量与引号

赋值、展开与只读

写成前者，bash 会把 name 当作要执行的命令，报 command not found。等号右边如果含空格，必须整体加引号，dir=/home/deploy/my project 会让 bash 去执行一个叫 project 的命令。赋值语句的右边不做分词和通配符展开，这一点与普通命令参数不同，所以 pattern=*.log 存进去的就是字面量 *.log。

引用变量写 $name 即可，但只要后面紧跟字母、数字或下划线，就必须用花括号划出边界：$name_suffix 会被解析成变量 name_suffix，写成 ${name}_suffix 才是我们想要的。花括号还承载了默认值、长度、截取等扩展，后文会陆续用到。

双引号、单引号与命令替换

三种引号的分工可以一句话概括：双引号里变量和命令替换仍然生效，但空格与通配符不再有特殊含义；单引号里一切都是字面量；反引号与 $() 都表示命令替换。

命令替换推荐 $()，它是 POSIX 标准，可以嵌套，括号配对一目了然。反引号在嵌套时要反斜杠转义，可读性差，只在必须兼容极老的环境时才用。$(...) 的结果如果直接参与分词，同样会被拆开，所以习惯上写成 "$(...)"。

不加引号时，Shell 会对展开结果做两件事：按 IFS 拆词、对 * 和 ? 做路径展开。这就是事故的根源。一条经验是：只要变量的值来自外部（参数、配置、命令输出），就给它加双引号；只有在明确希望分词或展开通配符时才裸写。判断文件是否存在这类场景尤其要小心，[ -f $file ] 在文件名为空时会变成 [ -f ]，表达式恒为真，写成 [ -f "$file" ] 才正确。

参数：位置变量与 “$@”

脚本的输入靠位置参数传递。$0 是脚本被调用时的名字，$1 到 $9 是前九个参数，第十个开始必须写 ${10}。$# 是参数个数，常用来做最少参数校验：

要注意 $0 只反映调用方式：./deploy.sh 得到 ./deploy.sh，用绝对路径调用就得到绝对路径。需要定位脚本所在目录时，${BASH_SOURCE[0]} 更可靠，它不受当前工作目录影响；这是 bash 的扩展，#!/bin/sh 里不可用。

参数缺省时可以用 ${1:-默认值}，它只在变量为空或未设置时替换，不会修改原变量；${1:=默认值} 则会顺手把值赋给变量。要求参数必须存在时用 ${1:?缺少源目录}，bash 会打印提示并以非零状态退出。这三种写法比手写一串 if [ -z "$1" ] 清爽得多。

$@ 与 $* 在不加引号时几乎一样：都按空格把参数重新拼成一串，带空格的参数会被再次拆开。区别在加引号之后："$@" 展开成若干个独立参数，每个参数保持原样；"$*" 把所有参数用 IFS 的第一个字符（默认是空格）连成一个字符串。转发参数时几乎总是要 "$@"：

如果写成 for arg in $@，调用方传进来的 "my project" 会变成两轮循环。同理，脚本里调用另一个脚本时写 backup.sh "$@"，才能把参数原样传下去。

shift 把参数列表整体左移一位：$1 被丢弃，原来的 $2 变成 $1，$# 减一；shift 2 一次移两位。它常和 while [ $# -gt 0 ] 搭配手写参数解析。不过带选项的场景里，getopts 更省事，后文会给出模板。

条件判断：[ 与 [[

[ 看起来像语法，其实是一个命令，[ -f "$file" ] 等价于调用 test，因此中括号内侧必须留空格，[$a=$b] 会被当成一个找不到的命令名。[[ 则是 bash 的关键字，由解释器直接处理，两者最实际的区别有三点。

第一，[[ 内部不做分词和通配符展开。变量为空时 [ $a = $b ] 会退化成 [ = x ]，报 unary operator expected，而 [[ $a = $b ]] 安然无恙。第二，[[ 支持 &&、|| 和正则匹配 =~，还可以用 == 做通配符匹配，例如 [[ $file == *.log ]]。第三，[[ 里的 < 和 > 可以直接比较字符串，不必像 [ 那样转义成 \<，因为后者会被 shell 当成重定向。

常用的文件测试符有 -f（普通文件）、-d（目录）、-e（存在）、-r（可读）、-x（可执行）。字符串测试用 -z 判断为空、-n 判断非空。数值必须用 -eq、-ne、-gt、-lt、-ge、-le，不能用 >，那在 [ 里是重定向，在 [[ 里是字符串比较。

&& 与 || 在命令层面表示“前一条成功才执行后一条”和“前一条失败才执行后一条”，可以串联成 cmd1 && cmd2 || cmd3。这套写法适合短判断，逻辑一复杂就该换成 if，否则失败原因的归属会变得难以阅读。另外，[ 里的 -a、-o 虽然还能用，但已被 POSIX 标记为过时，嵌套时歧义很大，不要再用了。

退出码、set -e 与调试

每条命令结束都有退出码，$? 取到上一条的值，0 为成功。判断失败用 if ! cmd; then 或 cmd || exit 1，不要拿 $? 和数字逐个比较。

在脚本开头写 set -e 能让命令失败时立即退出，但它比想象中宽松：出现在 if、while、&&、|| 里的命令失败不会触发；local x=$(false) 也检测不到，因为 local 本身返回 0，后者要拆成先赋值再声明。set -u 让引用未定义变量直接报错，正好治开篇那种空变量，代价是 ${1:-} 这类写法必须补齐。set -o pipefail 让管道中任一环节失败都算失败，否则只看最后一个命令。三句通常一起写：

小结

Shell 的语法不多，难的是它默认会把字符串拆开、又常常把失败默默放过。把引号、[[ ]]、while read 与 set -euo pipefail 练成肌肉记忆，开篇那类事故就能挡住大半。最后把常见需求、对应写法与坑整理成一张表，写脚本时可以直接对照。

需求 写法 坑
拼接路径 "$dir/$file" 空格拆词、变量为空
遍历文件 for f in *.log $(ls) 拆词、二次展开
逐行读文件 while IFS= read -r line; do ...; done < f 接管道导致变量丢失
判断文件 [[ -f "$file" ]] [ -f $file ] 在空值时恒真
返回结果 echo 配合 $(...) 日志混入、子 shell 隔离
失败即停 set -euo pipefail local x=$(cmd) 掩盖失败
参数解析 getopts 加 shift 只支持短选项
清理现场 trap 'rm -rf "$tmp"' EXIT 变量未加引号

脚本写到最后，拼的不是语法技巧，而是对边界条件的敬畏：空变量、空格、失败的命令、提前到来的信号。把这些都当成常态，脚本才配待在部署流程里。
