Docker 数据卷与容器持久化

本文属于《Docker 与 Kubernetes》第 10/51 篇
上一篇系列目录下一篇

容器里的数据到底存在哪，是很多人第一次用 Docker 跑数据库时才会认真想的问题。本文从一次误删事故讲起，梳理容器可写层与数据卷的区别，再逐一说明 volume、bind mount、tmpfs 三种挂载方式的用法、备份恢复流程和常见坑。适合已经会 docker run、准备把有状态服务放进容器的读者，读完后你应当能为一个数据库容器设计出可备份、可迁移的持久化方案。

从一次误删说起

事故本身很普通。测试环境磁盘告警，同事看到几个 mysql-test 容器占地方，顺手 docker rm -f 清掉，随后重新 docker run 了一个同名实例，结果半年的测试数据没了。原因不复杂：当初启动时只写了 docker run -d --name mysql-test mysql:5.7，没有挂任何目录，MySQL 只能把数据写进容器的可写层。

可写层的生命周期与容器完全绑定。容器运行时，读写都落在最上面那层；容器停止，层还在，docker start 能接着用；一旦 docker rm，这层随容器一起被删除，里面的数据库文件、上传附件、日志统统消失。它既不在镜像里，也不在宿主机某个直观的目录里。镜像分层与写时复制的细节，本站《Docker 镜像分层与缓存》已经讲过，这里只强调结论：可写层是临时草稿纸，不是存储。

有人会想到 docker commit：把当前容器提交成镜像，数据不就保住了吗？这只在极窄的场景下成立。commit 得到的是包含当前文件系统状态的镜像，之后容器再写入的数据不会自动进入这个镜像；要更新就得再 commit 一次，每次都是一层新镜像，体积只增不减。更麻烦的是，镜像里混进了运行时的日志、临时文件和数据库的脏页，既不方便校验，也无法按表恢复。docker commit 是制作镜像的手段，不是备份方案。

结论很直接：需要活过容器生命周期的数据，必须放到容器之外，再用挂载接进来。这也是本文剩余部分要展开的内容。

三种挂载方式

Docker 提供三种把外部存储接进容器的方式，理解它们的差别，比记住命令更重要。

volume（数据卷）由 Docker 管理，Linux 上默认落在 /var/lib/docker/volumes/<卷名>/_data。卷有名字，可以用 docker volume ls 看到，删除容器时不受影响，适合数据库数据、需要备份和迁移的目录，以及多个容器共享的读写目录。它是“给容器用的磁盘”，使用者不需要关心宿主机上的具体路径。

bind mount（绑定挂载）把宿主机上任意一个已存在的目录或文件映射进容器，路径由使用者指定，Docker 只负责挂载。它适合开发阶段挂源码做热更新、挂 Nginx 配置、把日志写到宿主机统一收集。代价是容器与宿主机耦合，换一台机器路径就可能不存在。

tmpfs 挂载只把内容放在内存里，不落磁盘，容器停止即消失。它适合临时缓存、会话文件、存放解密后的敏感内容。用法是 --tmpfs /tmp 或 --mount type=tmpfs，不需要指定宿主机路径。

三者的选择可以先用一句话判断：要长期保存且由 Docker 管，选 volume；要和宿主机上的文件实时同步，选 bind mount；只求快、丢了也无所谓，选 tmpfs。下文按这个顺序展开。

inspect 的输出里最关键的是 Mountpoint，它告诉你卷在宿主机上的真实位置，Linux 下通常是 /var/lib/docker/volumes/dbdata/_data。这个目录属于 root，直接进去改文件不是常规做法，但排查问题时很有用。删除卷用 docker volume rm dbdata，如果还有容器在使用，Docker 会拒绝删除，需要先停掉并移除相关容器。

卷分两种。命名卷有明确的名字，例如 dbdata，适合长期保存、备份和跨容器共享；匿名卷没有名字，Docker 会分配一串 64 位十六进制 ID。匿名卷通常来自两种写法：docker run -v /var/lib/mysql ... 只给了容器内路径，或者镜像的 Dockerfile 里声明了 VOLUME /var/lib/mysql。匿名卷同样能持久化，但名字不可读，容器删掉后很难确认哪个卷对应哪份数据，清理时也容易误删，生产环境应尽量使用命名卷。

还有一个容易忽略的事实：卷不随容器删除而删除。docker rm 只移除容器，命名卷仍然留在 docker volume ls 里，直到显式执行 docker volume rm。这既是保护，也是负担，闲置卷会一直占磁盘。

-v 与 –mount 的写法差异

挂载参数有两种写法。-v 是简写，把源、目标、选项用冒号串起来；--mount 是 key=value 形式，语义更明确。

-v 的源如果以 / 开头，按 bind mount 处理；如果不是路径，按命名卷处理；如果只写一个容器内路径，则创建匿名卷。--mount 要求显式写出 type，把 source 和 target 分开，读起来不容易歧义。--mount 在 docker run 中要较新的版本才支持，17.06 已经可用，而 17.03 的机器仍以 -v 为主，团队里最好统一一种写法。

两者最实际的行为差异在宿主机路径不存在时：-v /srv/site:/usr/share/nginx/html 会自动在宿主机创建 /srv/site 目录，权限是 root，容器里的进程如果没有权限写入就会报错；--mount 则会直接报错，拒绝启动。自动创建看起来方便，却容易把拼错的路径悄悄变成一个空目录，等发现时容器已经把空目录当成数据目录初始化了。需要长期维护的挂载，--mount 的严格性反而更安全。

bind mount 的权限直接沿用宿主机的 uid 和 gid。容器内进程不是 root 时，写宿主机目录就可能 permission denied；反过来，容器以 root 写入的文件在宿主机上也归 root 所有。开发机上问题不大，多人共用或生产环境要谨慎。

CentOS 7 默认开启 SELinux，bind mount 还多一道标签检查。容器访问宿主机目录被拒时，先看 journalctl 或 ausearch 里有没有 AVC 拒绝，再给 -v 加 :z 或 :Z。:z 表示该目录可被多个容器共享，:Z 表示私有、只给当前容器使用，二者都会修改宿主机目录的 SELinux 标签。同一个目录被两个容器以 :Z 挂载会互相冲突，这种情况应改用 :z。只读挂载用 :ro，多个选项用逗号隔开，例如 -v /srv/site:/usr/share/nginx/html:ro,Z。

数据库持久化与备份

数据库是持久化需求最典型的场景。MySQL 官方镜像的数据目录是 /var/lib/mysql，PostgreSQL 是 /var/lib/postgresql/data，只要把命名卷挂到这两个路径，删容器、换镜像都不会丢数据：

初始化只发生一次。MySQL 镜像在数据目录为空时，才会根据 MYSQL_DATABASE、MYSQL_USER 等环境变量建库建用户；PostgreSQL 则在空目录时读取 POSTGRES_PASSWORD 并执行 /docker-entrypoint-initdb.d 下的脚本。目录里一旦有数据，这些环境变量和初始化脚本都会被忽略。很多人改了密码重启容器发现不生效，原因就在这里，只能进库修改，或者清空卷重来。

备份有两条路。mysqldump 是逻辑备份，导出 SQL，跨版本、跨平台都能恢复，还能只恢复单张表，缺点是慢、占 CPU，且要加 --single-transaction 才能让 InnoDB 表在备份期间保持一致，数据量不大时每天定时 dump 最省事。卷备份是物理备份，直接打包数据目录，速度快、还原出来和原来一模一样，但依赖相同的数据库大版本和存储引擎，不能拿来单独恢复某张表。升级前做一次卷备份、日常用 dump，是比较稳妥的组合。

容器里的 uid 与文件属主

宿主机上 ls -ln 看到卷目录属主是 999 或 1000，是另一类高频问题。镜像里的服务往往以固定 uid 运行，例如 MySQL 镜像的 mysql 用户是 999，很多基础镜像的第一个普通用户是 1000。这个数字被原样写进文件属主，与宿主机上的用户名没有关系：宿主机上 uid 999 可能根本不存在，也可能恰好是某个普通账号。

排查分三步：docker exec db id 看容器内进程的 uid；docker exec db ls -ln /var/lib/mysql 看数据文件属主；再到宿主机 ls -ln /var/lib/docker/volumes/dbdata/_data 对照。三者不一致时，容器就会报 Permission denied 或无法初始化。

规避办法有三种。首选让容器内的 uid 与宿主机目标目录的属主一致，构建镜像时用 --build-arg 或 entrypoint 里的 usermod 调整；其次在宿主机上 chown -R 999:999 把目录交给容器用户，但要知道 999 在宿主机上是谁；最后是让容器以 root 运行，简单却扩大权限面，不建议在生产环境使用。多容器共享同一卷时，更要提前约定 uid，否则 A 容器写、B 容器读就会失败。

几个常见的坑

第一，拿空目录覆盖镜像内已有内容。-v /empty:/etc/nginx 会让容器里的配置目录变成空目录，Nginx 直接启动失败。bind mount 不会帮你复制镜像里的原文件；命名卷则不同，首次挂载到非空目录时，Docker 会把镜像里的内容复制进空卷，之后就以卷里的为准，镜像升级也不会更新卷里的旧配置。

第二，匿名卷越积越多。用 docker volume ls -f dangling=true 可以列出没有被容器引用的卷，确认无用后再删：docker volume rm $(docker volume ls -qf dangling=true)。不要在生产机上不检查就执行，卷名对不上时可能删掉仍在用的数据。

第三，docker rm 默认不删匿名卷，docker rm -v 才会。命名卷无论如何都不受 docker rm -v 影响，需要手动删。反过来，docker rmi 删除镜像不会动任何卷，所以清理磁盘时别只盯着镜像。

第四，卷里的数据不会随镜像更新。镜像里改了初始化脚本或默认配置，只要卷非空就不会生效，升级前要读 changelog，必要时手工迁移。

小结

容器适合跑无状态进程，有状态数据则要显式挂出来。判断标准不是“数据重不重要”，而是“容器删掉后还需不需要”。下表把常见数据与挂载方式对应起来，可作为选型时的速查。

数据类型 挂载方式 生命周期 注意点
数据库数据 命名卷 独立于容器 初始化仅一次，备份要一致
上传文件 命名卷或 bind mount 独立于容器 注意 uid 与容量
源码与配置 bind mount 跟随宿主机 SELinux 加 :z，可 :ro
日志 bind mount 跟随宿主机 轮转在宿主机做
临时缓存 tmpfs 容器停止即消失 占内存，不落盘

最后三条建议：生产环境用命名卷，别依赖匿名卷；备份要同时覆盖数据库逻辑导出和卷内文件；升级镜像前先验证卷里的旧数据能否被新版本正确读取。
