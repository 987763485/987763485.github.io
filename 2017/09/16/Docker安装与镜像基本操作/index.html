Docker 安装与镜像基本操作

本文属于《Docker 与 Kubernetes》第 2/51 篇
上一篇系列目录下一篇

概念文章读完之后，真正卡住人的往往是第二节：装哪个包、装完为什么连不上 daemon、镜像拉下来放在哪、容器删了数据怎么还在。本文以 Docker CE 17.06 为基准，走一遍 Ubuntu 16.04 与 CentOS 7 两条安装路径，再讲清镜像、容器、仓库三组常用命令和 run 的参数。读完你应该能在干净的服务器上从零装好 Docker，并且不再被“容器里的 localhost”和“挂载目录没权限”绊住。

镜像、容器与 Docker 的关系

先把三个词摆正位置，后面的命令才有归属感。

镜像（image）是一份只读的模板，打包了文件系统和一个默认的启动命令。它由若干层叠加而成，层间按内容寻址复用，原理在《Docker 镜像分层与缓存》里已经拆过，这里只记住一句：镜像自己不会运行，也不会被修改。

容器（container）是镜像的一次运行实例。Docker 在只读层之上再加一个可写层，容器里的新增和修改都落在这里。所以删掉容器，可写层随之消失，镜像毫发无损；想保留改动，就得 commit 成新镜像，或者把数据写到挂载卷里。

仓库（registry）是存放镜像的地方，Docker Hub 是默认的公共仓库。pull 是把镜像从仓库搬到本地，push 是反向操作，run 则在本地镜像之上创建容器。

两条安装路径：Ubuntu 16.04 与 CentOS 7

两个发行版的包名和源配置不同，顺序却一样：清旧包、装依赖、加官方源、装 docker-ce。先看 Ubuntu。

安装后的三项验证

装完先别急着跑业务镜像，按顺序做三步，能挡掉绝大多数安装问题。

第一步，docker version。输出分 Client 和 Server 两段。两段都有内容，说明客户端连上了 daemon；只有 Client 段并在末尾报 Cannot connect to the Docker daemon，问题就在服务端，和镜像、网络无关。两段版本号还应当一致，客户端 17.06 而服务端 1.12，多半是机器上还留着旧的 docker-engine。

第二步，docker info。这条命令的信息量大，安装阶段重点看四项：

  • Storage Driver：Ubuntu 16.04 上可能是 aufs 或 overlay2，CentOS 7 上常见 devicemapper 或 overlay2。
  • Cgroup Driver：一般是 cgroupfs，用 systemd 的系统上也可以改成 systemd。
  • Docker Root Dir：默认 /var/lib/docker，磁盘规划要按这个路径来做。
  • Registry Mirrors：配置了加速器才会出现。

镜像的六个基本动作

镜像命令不多，按使用频率是 pull、images、inspect、tag、rmi、history 六个。

docker pull 负责下载。不加标签默认取 latest，这是最容易被滥用的约定——它只是个普通标签，不代表最新，也不会自动更新本地镜像，除非显式再 pull 一次：

docker images 列出本地镜像。SIZE 列不是各层体积之和，而是解压后占用的磁盘空间；同一镜像的多个标签显示成两行，体积只算一份。docker images -f dangling=true 可以单独看悬空镜像——没有标签、也不被任何容器引用，是清理的主要对象。

docker inspect 输出镜像的完整 JSON，信息全但不好读，实践中都是配 -f 取字段：

docker history 从另一侧看镜像，列出每一层的创建命令和大小。排查“镜像为什么这么大”时，这条命令能直接指出是哪一步塞进了几百 MB：

docker tag 不改内容，只给同一个镜像 ID 再挂一个名字，典型用途是打上仓库地址，为推送做准备：

docker rmi 删除镜像。两个常见失败原因：镜像有多个标签时只删指定标签，全删完才释放空间；镜像被容器引用时（包括已停止的容器），必须先 docker rm 容器或加 -f。别用 rm -rf /var/lib/docker 清空间，daemon 的元数据会一起没掉。

容器的日常命令与 run 的七个参数

容器命令可以按生命周期记：run 创建并启动，ps 查看，stop 停止，start 唤醒，restart 重启，rm 删除。logs 和 exec 则是运行期最常用的两个观察与进入手段。

docker ps -a 的 STATUS 列会显示 Exited (0) 或 Exited (1) 这样的退出码，这是排查“容器起来就挂”的第一手线索。docker stop 只是发信号让主进程退出，容器和可写层都还在，docker start 能原样唤醒，只有 docker rm 才真正销毁。已停止的容器仍占磁盘，这就是 docker ps 看着干净、磁盘却越来越满的原因。

run 的参数多，先掌握七个就够日常使用：

参数 作用 常见写法
-d 后台运行，不占用终端 docker run -d nginx:1.12
-it 分配伪终端并保持标准输入，用于交互 docker run -it ubuntu:16.04 bash
--name 给容器起名字，替代随机名 --name web
-p 端口映射，宿主机端口在前 -p 8080:80
-v 挂载卷或目录，宿主机路径在前 -v /srv/www:/usr/share/nginx/html
-e 注入环境变量 -e TZ=Asia/Shanghai
--rm 容器退出后自动删除 --rm 配一次性任务

两个组合值得单独说。-it 后面必须跟一个前台进程，镜像默认命令若是启动守护进程，交互 shell 会立刻退出，所以要显式指定 bash。--rm 适合一次性任务，跑完自动清理，不会留下满地 Exited 容器。

两个反复出现的误解：端口与挂载

误解一：容器里的 localhost 就是宿主机。 不是。每个容器有独立的网络命名空间，127.0.0.1 指向容器自己的回环网卡。容器里连不上宿主机的 MySQL 并报 Connection refused，十有八九是地址写成了 localhost。

-p 127.0.0.1:3306:3306 这种写法更容易让人误会：它限制的是宿主机上这个端口只监听回环地址，对外不暴露，与容器内怎么访问宿主机毫无关系。容器要访问宿主机上的服务，得用宿主机的实际地址。默认 bridge 网络下宿主机的 docker0 网卡地址通常是 172.17.0.1：

更稳妥的做法是把数据库也放进容器，用自定义网络让容器名直接当主机名解析：

自定义网络自带 DNS，DB_HOST=db 就能解析到数据库容器。默认的 bridge 网络没有这个能力，只能靠已不推荐的 --link 或者写死 IP，而写死 IP 在容器重建后就失效。

误解二：挂载宿主机目录后，容器想怎么写就怎么写。 目录挂载不做任何用户映射，容器内进程的 uid 到了宿主机还是那个 uid。症状有两个方向：容器内进程以 root 运行，写出来的文件在宿主机上属主也成了 root；容器内进程以普通用户运行（如 nginx 镜像里的 nginx 用户），对属主是别人的目录就没有写权限，直接报 Permission denied。

排查时先看两边的 uid：

处理方式有三种：把宿主机目录 chown 成容器内那个 uid；用 -u $(id -u):$(id -g) 让容器以当前用户运行；或者改用命名卷 -v webdata:/data，权限交给 Docker 管理。数据库这类只做持久化、不需要人直接编辑的数据，命名卷更合适。在 CentOS 上还多一层：SELinux 会拦住容器访问宿主机目录，需要在挂载参数后加 :z 或 :Z 重打标签，否则同样报 Permission denied，原因却和 uid 无关。

清理磁盘与四类常见故障

Docker 占磁盘的速度超出预期：容器的可写层、没用上的镜像层、容器的 json 日志，都算在 /var/lib/docker 里。

先看清楚再动手，docker system df 给出四个分类的总量，加 -v 可看逐项占用：

清理的主力是 docker system prune，它一次删掉所有已停止的容器、未被使用的网络、悬空镜像和构建缓存：

它会要求确认，-f 可跳过。后来的版本加了 -a，连没有被容器引用的镜像也一起删，杀伤面大得多，跑着业务的机器上先别加。只想处理悬空镜像，用 docker rmi $(docker images -q -f dangling=true) 更可控。docker volume prune 删的是数据不是缓存，要格外小心。

四类故障按出现频率排列。

连不上 daemon

报 Cannot connect to the Docker daemon，先 systemctl status docker，再看 journalctl -u docker -n 50。CentOS 上常见原因是装完没 systemctl start，或者 /etc/docker/daemon.json 的 JSON 写错导致启动失败——一个多余的逗号就够。

存储驱动不合适

docker info 里看到 devicemapper 且 Data loop file 指向一个 loop 文件，说明是 loop-lvm 模式，默认 100 GB 上限且性能一般。CentOS 7 上应确认内核支持 overlay2，或按官方文档配 direct-lvm；旧教程里“必须用 devicemapper”的说法已经过时。

磁盘被写满

df -h /var/lib/docker 报警后，用 du -sh /var/lib/docker/* 定位。日志是大头，给 daemon 配上日志轮转比事后清理有效得多：

写进 /etc/docker/daemon.json 后 systemctl restart docker 生效。注意这个配置只对新创建的容器起作用，已有容器要重建才会应用。

拉取镜像慢或超时

跨境访问 Docker Hub 慢是常态，在 daemon.json 里加 registry-mirrors 数组，值填云厂商分配的加速地址，重启后用 docker info 确认 Registry Mirrors 生效。若只是个别镜像拉不动，先 docker pull 单独试：manifest unknown 是标签写错，i/o timeout 才是网络。

小结

安装阶段真正要记住的只有两件事：先清掉 docker.io、docker-engine 这些旧包，再从官方仓库装 docker-ce；装完用 docker version、docker info、hello-world 确认客户端、daemon、网络三条链路都通。日常操作围绕镜像与容器两组命令展开，run 的 -d、-p、-v、-e、--name、--restart 覆盖了绝大多数场景。两个最容易踩的坑是容器内的 localhost 和挂载目录的 uid 权限，前者靠自定义网络或 docker0 地址解决，后者靠对齐 uid 或改用命名卷。最后，docker 组等价于 root，别为了方便发给所有人；磁盘要定期用 docker system df 看一眼，日志轮转一开始就配上。
