Docker Compose 多容器编排

本文属于《Docker 与 Kubernetes》第 14/51 篇
上一篇系列目录下一篇

一个稍具规模的 Web 应用，很少只由一个容器构成：反向代理、应用进程、数据库往往各自成容器，还要共享网络与数据目录。如果每次部署都手工敲一串 docker run，再手动 docker network create，除了重复劳动，还很容易漏参数。本文用 Nginx + Go 应用 + MySQL 的例子，讲清 Docker Compose 的定位、核心字段、网络与数据卷，并整理出这段时间里最常踩的几个坑。

从一条命令说起：Compose 解决什么问题

2017 年把一个小的电商后端放上服务器，常见的组合是 Nginx 做反向代理与静态资源、Go 应用监听内部端口、MySQL 存数据。只用 docker run，一次启动大概是这样：

这三条命令能跑，但问题很快暴露：网络名、卷名、端口、环境变量都散落在命令历史里；换一台机器或交给同事，只能复制粘贴；改一个参数就可能漏掉一条。更麻烦的是启动顺序，数据库还没起来，应用连上去就退出，只能反复 docker start。

Compose 把这些“docker run 参数”收进一个 YAML 文件，用声明式的方式描述“我要哪些服务、它们怎么连、数据放哪”，然后一条 docker-compose up -d 完成创建网络、构建镜像、按顺序启动。文件还能入库，配置随代码一起走，代码评审时端口和环境变量的变化一目了然。

需要说明的是，Compose 不是集群调度器。它面向的是一台机器（或一台开发机）上的多容器应用，服务的副本调度、跨主机网络不在它的职责范围里，那属于集群调度工具的领域。

核心字段：一个服务由什么描述

services 是唯一的必填顶层键，下面每个键就是一个服务名。服务名不只是给人看的，它同时是容器加入网络后的 DNS 名，后文会反复用到。

image 指定镜像。同时写了 build 与 image 时，Compose 构建完成后把结果打成这个名字，up 时若本地已有同名镜像就直接复用，除非显式加 --build。

build 只说明“用哪个目录作为构建上下文”，Dockerfile 怎么写、怎么分层是另一个话题，这里不展开。实践中要注意上下文目录会整体发给守护进程，node_modules、.git 这类目录应当写进 .dockerignore。

ports 的格式是“宿主机端口:容器端口”。只写容器端口（如 "8080"）时，Docker 会随机分配宿主机端口，要用 docker-compose port app 8080 才能查到，不适合需要固定入口的服务。反过来，只在内网互访的服务根本不需要 ports，容器之间走服务名即可。

environment 既能写成列表，也能写成 KEY: VALUE 映射，后者对布尔值和数字更友好。需要注意值里的 $ 会被当成变量替换，密码里带 $ 时要写成 $$。

env_file 从文件读取变量，优先级低于 environment，同名时以 environment 为准。密钥文件不要提交到仓库，在 .gitignore 中排除，部署时由配置下发。

数据持久化：命名卷与绑定挂载

容器的可写层随容器删除而消失，数据库这类有状态服务必须把数据放到卷里。Compose 里两种写法对应 Docker 的两种挂载方式：

源不以 / 或 . 开头、而是直接写一个名字的写法，就是命名卷。卷由 Docker 创建在 /var/lib/docker/volumes 下，生命周期与容器解耦：删掉容器，数据还在；docker-compose down 默认也不删卷，只有 down -v 才会连卷一起清掉。这一点在测试环境里很好用，在生产环境里则要格外小心，误敲一次 -v 就是一次数据丢失。

绑定挂载把宿主机目录直接映射进容器，改配置文件不用重建镜像，是 Nginx 配置、证书这类文件的常用做法。代价是耦合了宿主机的目录结构，换机器就要保证路径一致；文件不存在时 Docker 会自动建目录，属主是 root，非 root 进程写入会报权限错误。

顶层 volumes 的声明不只是为了复用。没有声明的命名卷在 docker-compose down -v 时同样会被删，但声明之后可以加 external: true 引用外部已存在的卷，也可以指定 driver。MySQL 的数据目录建议用命名卷而不是绑定挂载，尤其在 macOS 上，绑定挂载要经过一层文件共享，写入慢且容易出现权限不一致。

网络：服务名就是 DNS 名

不写任何网络配置时，Compose 会为项目创建一个名为 <项目名>_default 的 bridge 网络，所有服务自动加入。项目名默认取 compose 文件所在目录名，可以用 -p 覆盖。同一网络内的容器可以用服务名互相访问，Docker 内置的 DNS 会把服务名解析到容器 IP，这也是 environment 里能直接写 DB_HOST=mysql 的原因。

默认网络够用，但把数据库和反向代理放在同一张网里并不合适。更稳妥的做法是按职责划分网络，只让需要的服务连通：

服务名解析在容器重启后会跟着更新，不需要手工维护 IP。排查连通性时，docker-compose exec app sh 进去执行 getent hosts mysql 或 ping mysql，比在宿主机上猜端口有效得多。需要提醒的是，localhost 在容器里永远指容器自己，这一点在后文的坑里还会提到。

depends_on 的语义：只管顺序，不管就绪

初学者最容易误解的字段是 depends_on。看下面的写法：

它的确切含义是：创建并启动 app 之前，先创建并启动 mysql 容器。仅此而已。Docker 只保证“容器进程已经拉起”，不保证进程内部已经完成初始化。MySQL 第一次启动要初始化数据目录，往往需要十几秒才监听 3306，而 app 的进程可能一秒后就绪，连不上数据库直接退出。

在 v2 的 2.1 格式里，depends_on 还支持 condition: service_healthy，可以等到健康检查通过再启动依赖方。到了 v3，这个写法被移除了，原因是 v3 的 schema 要兼容 Swarm 模式，而 Swarm 的服务调度模型里没有“等某个服务就绪”的概念。所以用 v3 时只有两种选择：应用自己做连接重试，或者在入口脚本里循环等待依赖端口可用。

更规范的做法是给依赖服务加 healthcheck，再用外部工具或应用逻辑判断，restart 策略则负责进程意外退出后的拉起。健康检查与重启策略的细节属于另一篇文章的范围，这里只强调一点：不要因为写了 depends_on 就认为启动顺序问题已经解决。

多环境：override 文件的合并规则

本地开发与线上部署的参数总归不同：开发要挂代码目录、开调试端口，线上要固定镜像标签、关掉调试。Compose 的约定是准备两个文件，docker-compose.yml 写公共部分，docker-compose.override.yml 写本地差异。默认情况下，后者的内容会被自动读取并与主文件合并，不需要任何参数：

几个反复出现的坑

端口冲突。 报错通常是 Bind for 0.0.0.0:80 failed: port is already allocated。宿主机上已经有一套 Nginx 在监听 80，或者上一次的容器没停干净。先用 ss -lntp | grep :80 确认占用者，再决定是改映射端口还是停掉宿主机的服务。切换项目目录时项目名会变，旧项目的容器不会被新项目接管，也容易造成端口被占的错觉。

容器里的 localhost 不是宿主机。 把 DB_HOST 写成 127.0.0.1，应用连的是自己容器里的 3306，必然失败。容器之间一律用服务名；确实要访问宿主机上的服务，Linux 下可以连 docker0 网桥的地址，macOS 与 Windows 的 Docker for Mac/Windows 需要额外配置，本文不展开。

数据卷权限。 绑定挂载的宿主机目录属主往往是当前登录用户，而镜像里的进程以 mysql、nginx 等低权限用户运行，写不进去就报 Permission denied。要么调整宿主机目录属主，要么改用命名卷，让 Docker 初始化卷时带上镜像里预设的权限。

镜像没有重新构建。 改了代码执行 up -d，容器还是旧行为，因为 up 只在镜像不存在时才构建。加 --build 强制重建；若连依赖层都没变却仍旧异常，再考虑 --no-cache。构建缓存本身是按 Dockerfile 指令逐层判断的，调整指令顺序带来的收益属于镜像构建的话题。

把启动顺序当成依赖就绪。 前面已经说过，depends_on 不等待服务可用。上线后遇到“偶发启动失败、重启一次就好”，先怀疑这里。

什么时候不必用 Compose

只有一个容器、没有额外网络与卷的项目，docker run 一条命令更直接，引入 compose 文件反而多一层维护。临时排查问题、跑一次性工具容器，也是 docker run --rm 更合适。判断标准可以简单一些：需要同时管理两个以上有协作关系的容器、或者这套组合要在多台机器上重复部署时，Compose 的收益才明显。它解决的是“单机多容器的声明式管理”，不是编排的全部。

小结

Compose 的价值在于把散落在命令历史里的容器参数固化成可评审、可复用的文件，一条 up -d 就能拉起整套开发环境。用好它只需要抓住三件事：服务名即 DNS 名，网络决定谁能访问谁；命名卷管数据、绑定挂载管配置；depends_on 只管启动顺序，服务就绪要靠应用重试或健康检查。写文件时坚持用 config 校验、用 override 区分环境，多数“玄学问题”都能在启动前被发现。
