Go 的 sync 包：Mutex 与 WaitGroup

本文属于《Go 语言与工程》第 35/78 篇
上一篇系列目录下一篇

go 关键字让并发变得廉价，也让共享状态的问题变得常见：一个计数器、一张缓存表，只要被多个 goroutine 同时读写，就可能给出难以复现的错误结果。本文从一次典型的数据竞争入手，讲清 sync.Mutex、sync.RWMutex、sync.WaitGroup 与 sync.Once 的用法、语义和常见误用，示例都可以直接用 go run -race 跑起来。读完之后，你应该能判断一段并发代码该不该加锁、锁该加在哪，以及为什么 WaitGroup 有时会提前放行。

Go 把并发的门槛降得很低：在函数调用前加一个 go，它就跑到另一条执行流里去了。门槛低带来的副作用是，很多人写完就默认它没有问题。下面这段代码就是一个典型：

更麻烦的是，数据竞争在 Go 里属于未定义行为。Go 的内存模型只承诺：通过锁或 channel 建立了 happens-before 关系的读写，才有确定的可见性；两个没有任何同步的 goroutine 之间，编译器和 CPU 都可以重排指令，也可以把变量长期放在寄存器里。所以在我机器上跑对了，完全不能作为证据。

标准库自带一个检测器。开发时用 go run -race 运行，测试时用 go test -race：

它的原理是记录每次内存访问之间的 happens-before 关系，只有两个没有同步的访问真的并发发生时才会报告。因此它不会误报，但可能漏报：没有执行到的分支它看不见。代价是程序会慢几倍、内存占用上升，所以只在开发和 CI 阶段打开，生产环境不带 -race 编译。

三种常见的 Mutex 误用

复制了带锁的结构体

sync.Mutex 一旦被使用就不能复制。复制出来的锁是另一把锁，保护的却还是原来那份数据，等于没有保护。

调用方拿到的是副本，加锁和解锁都发生在副本上，原来的 Counter 完全没有被保护，value 的自增也丢了。同样的错误会出现在这些地方：把结构体作为参数传值、函数返回结构体而不是指针、append 进 []Counter、放进 map[string]Counter、用 for range 遍历 []Counter 后直接调用方法。go vet 能抓到其中大部分：

忘记 Unlock 与重复 Lock

第一次传入空 key，这把锁就废了。后续所有 goroutine 都卡在 Lock 上，程序看起来没死，其他不经过这把锁的逻辑还在跑，但这条路径彻底不动了。改成 defer s.mu.Unlock() 即可，代价只是多一次函数调用。

重复 Lock 的表现是死锁：某条路径已经持有锁，又调用了一个内部会 Lock 的方法。这类问题 go vet 抓不到，只能靠约定：不导出需要持锁调用的内部方法，或者拆成两套命名，公开的 foo 负责加锁，内部的 fooLocked 假定调用方已持锁。

持锁调用外部代码

回调、接口方法、channel 发送都可能间接获取同一把锁，或者阻塞很久。稳妥的做法是先复制一份待处理的数据，解锁之后再逐个执行。凡是锁里调用了自己不完全了解的代码，都值得停下来想一秒。

sync.RWMutex：读多写少的取舍

RWMutex 把读和写分开：RLock 可以被任意多个 goroutine 同时持有，Lock 则是独占的。写者持有锁时，任何 RLock 都要等；写者在排队时，后来的 RLock 也会被挡住，好把锁优先交给写者，避免写饥饿。这是文档里明确写出的语义，理解它才能解释为什么读操作会突然变慢。

它适合读远多于写、且读的临界区不是一两条指令的场景，比如配置表、路由表、字典缓存。RWMutex 内部要维护读者计数和写者信号，开销比 Mutex 大；如果临界区只是取一个指针，用 RWMutex 反而更慢，老老实实用 Mutex 就好。

两个常被忽略的限制。其一，RLock 期间只能读，对 map 的写入和删除都不行，哪怕只改一个键。其二，不能升级锁：先 RLock 再 Lock 会死锁，因为 Lock 要等所有读者释放，包括自己。需要更新时，先 RUnlock 再 Lock，并在拿到写锁后重新检查条件。

关于 map 补一句：多个 goroutine 同时读写同一个 map，运行时会直接抛错退出，它不会给你只错一点的机会。这个现象的成因属于 map 内部结构的话题，本文不展开，但结论要记住：map 的并发安全必须由使用者自己保证。

sync.WaitGroup：等一组 goroutine 结束

WaitGroup 是一个计数器：Add(n) 加 n，Done 减一，Wait 阻塞到计数器归零。它解决的是主 goroutine 怎么知道后台任务都做完了，比 time.Sleep 可靠得多。

三条规则值得背下来。第一，Add 在 go 语句之前调用，先登记再启动，Wait 才可能看到正确的计数。第二，Done 用 defer 放在 goroutine 开头，保证 panic 或提前 return 也能减一。第三，传给闭包的是循环变量的副本：Go 1.9 里 for 的循环变量在整个循环中复用，如果闭包直接引用 url 而不通过参数传入，所有 goroutine 看到的都是最后一个值，抓取结果会变成同一个 URL 重复 N 次。

WaitGroup 和 Mutex 一样不能复制，作为参数传递时要传指针；放进结构体时，结构体本身也应该用指针使用。

WaitGroup 的三个坑

在 goroutine 内部 Add

主 goroutine 执行到 Wait 时计数还是 0，Wait 立即返回，函数结束，后台任务被半路丢弃。这类 bug 在低负载时不容易出现，一上量就开始丢任务，而且日志里往往什么都没有。修法只有一条：把 Add 挪到 go 之前。

计数器变成负数

Done 的次数多于 Add，运行时会 panic，报 sync: negative WaitGroup counter。常见来源是同一个 wg 被用在两批任务上，或者某条错误路径里多写了一次 Done。用 defer 时尤其要检查：函数里是不是既 defer 了 Done，又在某个分支手动 Done 了一次。

复用前没有等归零

WaitGroup 可以复用，但必须等上一批的 Wait 返回、计数归零之后再 Add。否则新一轮的 Add 会和上一轮的 Done 混在一起，Wait 可能提前返回，也可能永远不返回。实践中更好的做法是每批任务用一个局部变量，而不是共享一个包级 wg；局部变量的生命周期天然对应一批任务，复用问题根本不会出现。

最后补充一点：Wait 本身可以被多个 goroutine 同时调用，都会在归零时被唤醒。但 Wait 与 Add 并发调用是危险的，文档要求 Add 的调用发生在 Wait 之前或计数已经归零之后。

sync.Once：只做一次，并且做完才算数

初始化单例、加载配置、注册指标，这类只应该执行一次的逻辑，手写一个 if 加锁很容易出问题。sync.Once 的 Do 保证：无论多少 goroutine 同时调用，f 只会执行一次；并且在 f 返回之前，其他调用 Do 的 goroutine 都会阻塞。这个带同步语义的完成，比只执行一次更重要。

几个要点。Do 里的函数不要 panic：在 Go 1.9 的实现中，f panic 之后 Once 仍然认为它已经完成，后续调用直接返回，client 会一直是 nil，问题被推迟到更远的地方才爆出来。初始化可能失败时，应该把错误存下来，由调用方判断，而不是让 f panic。也不要在 Do 内部递归调用同一个 Once，那会死锁。Once 适合进程内一次性初始化，不适合按 key 缓存初始化结果，后者还是得自己用锁加 map 实现。

顺带提两个同包工具：sync.Pool 用来复用临时对象、减轻 GC 压力；sync.Cond 用来在条件满足时唤醒等待者。两者细节都比较多，本文不展开。

锁的粒度、加锁顺序与不该用锁的时候

用固定顺序避免死锁

转账是最经典的例子：A 转 B 和 B 转 A 同时发生，两个 goroutine 各自先锁住自己的账户，再去锁对方的账户，就互相等待了。

死锁的四个必要条件里，最容易打破的是循环等待：给所有锁定义一个全局顺序，按 ID、按地址或者按层级都行，任何路径都按这个顺序加锁。粒度上也有取舍：锁太粗，并发度上不去；锁太细，一次操作要拿好几把锁，死锁概率和开销都上升。一般的做法是先按数据边界分锁，一个结构体一把锁，只有在压测证明存在热点时再拆。

标准库的 Mutex 不支持超时

Go 1.9 的 sync.Mutex 只有 Lock 和 Unlock，没有尝试加锁，也没有带超时的 Lock。如果一段代码可能长时间持锁，调用方没有办法等一百毫秒拿不到就走。可行的替代是把共享状态交给一个专门的 goroutine，用 channel 加 select 做超时控制，这属于另一套并发模型，本文不展开。更实际的做法是从源头避免：不要让临界区里出现可能长时间阻塞的操作，这样锁的持有时间就是可控的。

什么时候不该用锁

  • 数据只读。初始化完成后不再修改的配置、字典，直接读就行，加锁只是浪费。
  • 单个计数器。sync/atomic 的 AddInt64、LoadInt64 更轻，但它只能保护单个值，多个字段之间的不变量仍然需要锁。
  • 所有权明确转移。一份数据只由一个 goroutine 拥有，通过 channel 把指针交给下一个 goroutine，就不需要锁。这就是常说的用通信共享内存，具体写法属于 channel 的话题，这里只提一句。

选择的依据不是哪个更高级，而是这段数据到底有没有被多方同时访问。没有共享就没有竞争，锁能不加就不加；一旦要加，就加在最小的临界区上，让锁和被保护的数据待在一起，并且给所有锁规定一个固定的获取顺序。

小结

并发问题的根源是共享可变状态，锁只是把访问串行化的手段，不是目的。Mutex 的零值可用但不可重入、不可复制，含锁的结构体一律用指针接收者，Unlock 尽量交给 defer。临界区只包住内存操作，回源、日志和回调都放到锁外；缓存场景用查锁、放锁、回源、再锁写入的写法换取并发度。RWMutex 适合读多写少且临界区不短的情况，要接受写者优先带来的读延迟。WaitGroup 的关键是 Add 必须在 goroutine 启动之前、每批任务用独立变量、复用前等计数归零。最后，能不加锁就不加锁，必须加时按固定顺序获取，并记住标准库的 Mutex 没有超时。
