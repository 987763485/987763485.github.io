Go 测试：testing 与表格驱动

本文属于《Go 语言与工程》第 17/78 篇
上一篇系列目录下一篇

写 Go 服务时，测试往往是最先被省略、最后才补上的部分。本文从 go test 的运行机制讲起，逐步介绍 testing 包中最常用的几个接口，以及如何用表格驱动和子测试把用例组织得清晰可维护。读完之后，你应该能为一个普通的 Go 包写出失败信息清楚、可以并行执行，并且能用覆盖率与竞态检测兜底的测试。

go test 如何找到并运行测试

Go 的测试没有独立的测试框架，测试代码就是普通的 Go 文件，只是文件名必须以 _test.go 结尾。go build 和 go install 会忽略这类文件，只有 go test 会把它们一起编译进去。执行 go test 时，工具链会把被测包和所有 _test.go 编译成一个临时的测试二进制，再运行其中名字形如 TestXxx 的函数，最后把结果汇总打印出来。

测试文件放在哪个包里，决定了它能看见什么。最常见的是与被测代码同包，例如 package price。这样测试可以直接调用未导出的函数、访问未导出的字段，适合做细粒度的白盒测试。另一种写法是 package price_test，即所谓的外部测试包。它只能使用被测包导出的 API，相当于把自己当成一个普通调用方。两种文件可以同时存在于一个目录中。笔者通常把针对内部实现的用例放在同包文件里，把面向公开 API 的用例放在 _test 包里，这样一旦公开接口被改坏，外部测试会第一时间报错。

运行范围也有讲究。在包目录下直接执行 go test 只跑当前包；在项目根目录执行 go test ./... 会递归跑所有子包，但会跳过 vendor 目录。测试的入口是包级函数，init 函数同样会先执行，所以不要在 init 里做联网、读文件这类副作用大的事情，否则连只想跑一个用例都会变得困难。

TestXxx 的签名与两种失败方式

一个测试函数的签名是固定的：接收一个 *testing.T，没有返回值，名字必须以 Test 开头且紧跟大写字母。参数名习惯写成 t，类型由 testing 包提供，测试通过时函数正常返回，失败时则通过 t 记录错误或终止。下面是最朴素的形式：

t.Errorf 的行为是“记录错误并继续执行”，等价于先调用 t.Fail() 再写日志。它适合校验多个互相独立的断言，让一次运行暴露尽可能多的问题。t.Fatalf 则是“记录错误并立刻结束当前测试函数”，内部调用 t.FailNow()，后者会通过 runtime.Goexit 终止当前 goroutine。它适合后续代码依赖前面结果的情况，例如初始化失败后再断言只会引发空指针。

两者有一个共同的限制：只能在测试函数所在的那个 goroutine 里调用。若在测试里另起 goroutine 并在其中调用 t.Fatalf，测试框架无法正确收尾，go test 也会提示这个误用。并发场景里更稳妥的做法是把错误通过 channel 传回主 goroutine，或者只用 t.Errorf 并由主 goroutine 等待结束。另外，t.Error 与 t.Fatal 只接受字符串，日常几乎总是用带格式的 Errorf、Fatalf，把上下文一起打出来。调试时还可以用 t.Logf 记录中间值，它只在测试失败或加了 -v 时输出，不会像 fmt.Println 那样把无关信息混进标准输出，也不会打乱并行测试的日志。

从重复代码到表格驱动

假设有一个解析分页参数的函数，它接受空字符串时返回默认值，遇到非数字报错，超过上限则截断。如果按最直接的方式写，会得到三个高度相似的测试函数，复制粘贴之间很容易漏改断言里的数字：

表格驱动（table-driven test）把“输入”和“期望输出”从控制流中抽出来，放进一个结构体切片，循环只写一遍。新增用例只是往表里加一行，不会碰断言逻辑，也就不会出现“复制后忘了改”的典型错误：

结构体里的字段就是一份小型规格说明：raw 是输入，want 与 wantErr 是期望，name 用来标识用例。表本身还可以被多个测试函数复用，例如同一批输入既测解析函数，也测它在上层 handler 中的表现。需要留意的是，循环里不要用 t.Fatalf，否则第一个失败会中断整张表，后面的用例再也跑不到；用 Errorf 加 continue 更合适。表里还应刻意补齐边界：空字符串、零值、上限、刚好越界、含多字节字符的输入，这些用例只多一行，却能覆盖手写测试最容易遗漏的分支。另外不要用 map 存用例，Go 的 map 遍历顺序是随机的，同一个失败每次出现的次序都不同，排查时很折磨。

子测试：命名、筛选与并行

上面的写法有一个问题：所有用例共用一个测试函数，失败时只能看到一条错误，不知道是哪一行、哪个场景。把循环体交给 t.Run 就能解决。t.Run(name, func(t *testing.T)) 会创建一个子测试，名字由第一个参数决定，完整名称是“父测试/子测试”，报告和筛选都按这个层级处理：

子测试的名字会进入输出，空格在展示与筛选时会被替换成下划线，所以 -run 'TestParseLimit/empty_uses_default' 可以只跑默认值这一条。-run 的每一段都是正则表达式，用 -run 'TestParseLimit/(empty|normal)' 就能挑出一组相关用例，调试时非常省时间。

t.Parallel() 表示这个子测试可以与其他标记为并行的测试同时运行。它的语义需要说清楚：调用后测试会先暂停，等同一层级的顺序测试全部跑完再恢复；父测试也会等到所有并行子测试结束后才算完成。因此并行只适合纯计算或只读操作，共用同一个临时文件、同一个全局变量的用例不要并行。示例中的 tt := tt 是必要的，循环变量在每次迭代中复用，不复制一份的话，闭包可能全部读到最后一个用例；这个细节在老版本 Go 里尤其容易踩坑。

让失败信息自己说话

测试失败时，最耗时的往往不是发现失败，而是判断为什么失败。只写 t.Errorf("failed") 等于把排查工作完整地留给下一个看日志的人。一条合格的失败信息至少包含三件事：用什么输入、期望什么、实际得到什么。命名参数时尽量带上类型感，字符串用 %q 可以暴露首尾空格与不可见字符，结构体用 %#v 能看清字段：

还有两个细节值得坚持。其一，错误断言不要只判断 err != nil，在期望报错的用例里顺手检查错误信息是否包含关键片段，否则函数因为别的原因失败也会被当成通过；例如期望参数错误时，除了标记 wantErr，再断言 err.Error() 含有 "limit" 之类关键字，能挡住“别处崩溃、恰好报错”的假通过。其二，失败信息里不要打印密码、令牌、完整身份证号这类敏感数据，测试日志同样会进 CI 归档，泄漏面并不小。

辅助函数与 t.Helper

当多个测试需要同一段准备逻辑时，把它抽成辅助函数。辅助函数接收 *testing.T 作为第一个参数，这样它也能报告失败：

t.Helper() 是 Go 1.9 新增的方法，用来把这个函数标记为“测试辅助函数”。没有它时，t.Fatalf 报告的行号会落在辅助函数内部，读者看到的是一行与用例无关的代码；加上之后，testing 会沿调用栈回溯，把失败位置指向真正调用 mustParseLimit 的那一行。行号看似小事，但在表驱动测试里，它往往就是定位是哪个用例出错的唯一线索。所有会调用 t.Error、t.Fatal 系列方法的辅助函数都应该在开头写上一句 t.Helper()，这是笔者审阅测试代码时的必查项。

如果整个包都需要一份准备，例如一个临时目录或测试数据库，可以用 TestMain。它是 Go 1.4 引入的约定：只要包里定义了 func TestMain(m *testing.M)，测试框架就不再直接跑用例，而是调用它，由它决定何时执行 m.Run()：

m.Run() 返回各测试汇总后的退出码，必须原样交给 os.Exit，否则失败会被吞掉。TestMain 适合启动一次、所有用例共享的资源，但它没有 *testing.T，不能做断言，也不参与 -run 筛选，准备逻辑一旦写重，单跑一个小用例也要付出完整代价。多数情况下，在用例内用 defer 清理局部资源、只在确实需要进程级共享时动用 TestMain，是更可持续的选择。

测试 HTTP handler：httptest

Web 服务的测试常被拖到最后，理由是“要起服务器、连数据库”。实际上 net/http/httptest 让 handler 可以完全在进程内测试：httptest.NewRequest 构造请求，httptest.NewRecorder 充当 http.ResponseWriter，再把两者交给 handler 的 ServeHTTP，整个过程不监听端口。

覆盖率、竞态与常用参数

go test -cover 会在结果后附加一行语句覆盖率，例如 coverage: 78.5% of statements。想看具体哪些行没跑到，就在包目录下生成 profile 再打开 HTML：

浏览器里会用不同颜色标出已覆盖与未覆盖的代码，红色往往集中在错误分支和参数校验上，正好提示该补哪些用例。覆盖率只统计被测包的语句，测试文件本身不计入，所以不必为了数字在测试里堆代码。但它只说明某行被执行过，不说明结果被检查过：一个只有 if err != nil { return } 而没有断言的测试，同样能把覆盖率刷满。笔者的用法是把它当作“找盲区”的工具，而不是考核指标，更不会为了数字去写没有断言的用例。

加上 -race 后，运行时会记录内存访问的先后关系，一旦发现没有同步保护的同址读写，就打印两条调用栈并让测试失败，输出中带有 DATA RACE 字样。竞态检测依赖 cgo，运行速度会慢数倍，通常放在本地提交前和 CI 上跑，而不是每次保存都跑。它只能报告实际执行到的冲突，所以并发用例要尽量让多条路径都被调度到。

最后是几个每天都用的参数。-v 输出每个测试的通过状态与 t.Log 内容，排查时先加它；-run 按正则筛选测试或子测试；-count=1 表示每个测试只执行一次，在支持测试结果缓存的工具链上，它也是跳过缓存、强制重跑的手段；-short 配合测试里的 testing.Short() 跳过依赖外部服务的慢用例：

性能测试与剖析是另一套话题，benchmark、-benchmem 与 pprof 的写法另有专文，这里不展开。

小结

Go 的测试能力几乎全部来自标准库：_test.go 决定测试代码的边界，TestXxx(t *testing.T) 是入口，Errorf 与 Fatalf 分别对应“继续收集问题”和“立即停止”。表格驱动把输入与期望集中成数据，t.Run 让每个用例拥有独立名字，t.Parallel 在安全的前提下缩短总耗时。失败信息要写清输入、期望与实际，辅助函数记得调用 t.Helper() 把行号还给调用方。最后用 -cover 找盲区、用 -race 查并发问题，并把 -v、-run、-short 变成日常习惯，测试才会从负担变成反馈回路。
