TypeScript 与 Node.js 结合开发

本文属于《TypeScript 学习路线》第 19/74 篇
上一篇系列目录下一篇

Node.js 项目里写 JavaScript，最常听到的抱怨是接口字段记不住、重构时不敢动、编辑器的补全靠猜。TypeScript 正好能补上这三块短板。本文以 2017 年底的 Node 8 LTS 与 TypeScript 2.6 为基准，从一个空目录开始，把 @types/node、tsconfig.json、开发时运行、生产构建与调试串成一条可落地的链路，最后给出三个笔者踩过的坑。读完后，你应该能独立给一个纯 Node 服务或 Express 应用加上类型，而不必推翻现有代码。

为什么在 Node 项目里引入 TypeScript

Node 生态以 JavaScript 为主，动态类型带来两方面的代价。一是调用边界靠记忆：某个工具函数要求传入 { retries, timeout }，少写一个字段、拼错一个键名，只有运行到那一行才会暴露。二是重构靠胆量：把一个函数从回调改成 Promise，或者调整参数顺序，改动点常常散落在十几个文件里，靠全局搜索一条条核对。

TypeScript 的价值集中在三点。第一，类型即契约，模块导出的函数签名就是调用说明书，编辑器能直接提示参数名与返回值结构。第二，编译期检查把一部分运行时错误前移，尤其是 undefined 取值与拼写错误。第三，重构安全，重命名字段或修改签名后，tsc 会把所有不兼容的调用点一次性列出来。

代价也要说清楚：多了一步编译，第三方包可能没有类型声明，团队里若放任 any 蔓延，类型会退化成注释。所以引入 TypeScript 的正确姿势是先把 strict 打开、把模块边界写准，而不是给所有变量补一个 any 交差。对服务端来说，最值得标注的三处是配置、对外接口的输入输出、以及第三方 SDK 的返回值，这三处最容易在半年后变成事故现场。

最小工程：package.json 与 tsconfig.json

先建目录、初始化项目，再装三样东西：编译器、Node 的类型声明、开发时的执行器。

接着写 tsconfig.json。Node 场景下真正需要拍板的只有几项：模块格式必须是 commonjs，因为 Node 8 的稳定模块系统仍是 CommonJS；target 选 es2017，Node 8 原生支持 async/await，不必降级成生成器加状态机；rootDir 与 outDir 让源码与产物分居 src 和 dist；sourceMap 为后面的调试铺路；types 显式限定只加载 Node 的全局声明。

strict 在 2.3 之后已是一组开关的集合，新项目没有理由不开。include 只收 src 下的 .ts，避免把 dist 里的旧产物再卷进编译；工程里若有不想参与的脚本，宁可显式列出目录，也不要用宽泛的 **/*。moduleResolution 写 node 则保证 import 'lodash/fp' 这类子路径按 Node 的解析规则去找文件。

package.json 里补上入口与脚本，三条命令各司其职：dev 直接跑源码，build 产出 dist，start 用产物启动，贴近线上形态。

入口文件先小到不能再小，确认整条链路能跑通再往里加业务。

注意 import * as http 这种写法：在 TypeScript 2.6 下，它针对 export = 风格的 CommonJS 模块是合法的，编译结果就是一句 require，这也是当期引用内置模块的标准姿势。

@types/node 与类型声明的查找顺序

写 Node 代码时用到的 fs、path、process、Buffer、__dirname，类型都不来自 TypeScript 本身，而是来自 @types/node。它是 DefinitelyTyped 维护的 Node 类型包，按 Node 的大版本发版：跑 Node 8 就装 @types/node@8，跑 Node 9 就换 9.x。版本对不上，是后文要专门讲的坑。

不装它会怎样？import * as fs from 'fs' 直接报找不到模块的声明，process 与 Buffer 也会变成未定义标识符，整个工程从第一行开始飘红。

编译器的查找顺序可以记成三条。第一，全局声明默认从 node_modules/@types 下的每个包加载，可以用 typeRoots 换目录，用 types 白名单只留需要的。第二，模块声明先看目标包的 package.json 里有没有 types 或 typings 字段，没有就找同目录的 index.d.ts。第三，再找不到才去 node_modules/@types/<包名> 里翻，例如 @types/express。

这样一来第三方库分成两类：有社区类型包的，装一个 @types 就够；完全没有类型的内部老包，在 src/types 下写一份环境声明兜底，include 会把 .d.ts 一起纳入编译。

这份声明只是让编译通过，它不会校验运行时行为，所以接口宁可写窄一点，也不要为了省事全部标成 any。类型文件放在 src 下还有个好处：.d.ts 不产生额外输出，dist 里保持干净。

@types/node 的小版本跟随 Node 的小版本推进，运行时新增的 API 很快会出现在类型包里。团队里几个人装到的 8.x 未必相同，package-lock.json 必须提交，否则同一份代码可能在这台机器通过、在那台机器报错。

开发时运行：ts-node 与热重载的取舍

有了 ts-node，npm run dev 就能直接执行 .ts 文件：它在内存里调用 TypeScript 编译，再把结果交给 Node 运行，不落盘、不产生 dist。优点是改代码时不必先想构建；缺点是每次启动都要全量类型检查，工程变大后启动从一秒拖到三四秒。它本质上只是一个 require 钩子，遇到依赖原生模块的包仍可能出问题。

热重载有三条路线，取舍各不相同。第一条是 ts-node-dev --respawn src/index.ts，监听源码变化并重启子进程，--respawn 让进程崩溃后自动拉起，开箱即用。第二条是 nodemon --watch src -e ts --exec ts-node src/index.ts，把监听与执行解耦，规则可以写进 nodemon.json，对已经在用 nodemon 的团队迁移成本最低。第三条是 tsc -w 持续产出、nodemon --watch dist dist/index.js 负责重启，跑的是真实构建产物，最接近线上，代价是每次改动要等编译落盘，慢半拍。

笔者的选择是：日常用前两条，涉及资源文件、构建配置、__dirname 的改动时切到第三条复验一遍。另外，开发期不必让类型检查拖慢重启，ts-node 提供了只转译、跳过类型检查的开关，把把关留给编辑器与 build 阶段即可。用 tsc -w 配合 nodemon 时，把 --delay 调大到几百毫秒，能避开文件写了一半就被加载的时序问题，省掉不少“改了没生效”的困惑。

调试：–inspect 与 source map

Node 6.3 起内置了 --inspect，启动后打开 Chrome 的 chrome://inspect 就能用开发者工具调试服务端进程。--inspect 让进程直接跑起来，--inspect-brk 则在第一行暂停，适合调试启动阶段的初始化逻辑。调试端口默认监听 9229，在容器或远程机器里要写成 --inspect=0.0.0.0:9229 并在 DevTools 里手动添加地址，否则连接会被拒绝。

跑产物最简单：node --inspect dist/index.js，在 DevTools 里给 .js 打断点。想让断点落在 .ts 上就要靠 source map：tsconfig.json 里的 sourceMap: true 会为每个 .js 生成同名的 .js.map，调试器读取文件末尾的映射地址后，自动把位置还原到源码。

生产构建与发布产物

npm run build 执行 tsc -p tsconfig.json，按 rootDir 的结构把 src 下的文件一一编译到 dist，只为 .ts 生成 .js 与 .js.map。发布与部署时有几个约定值得固定下来。

第一，main 必须指向产物而不是源码。写成 "main": "dist/index.js"，别人 require 你的包时才不会去加载一个 .ts 文件然后直接报语法错误。第二，files 决定 npm pack 与发布的内容，写上 "files": ["dist"]，src、测试与配置就不会进包；发布前用 npm pack --dry-run 看一眼清单，比事后在服务器上发现少文件强得多。第三，build 不能只有 tsc：模板、SQL、静态配置这些资源不是 TypeScript，编译器不会碰它们。

如果这个包还要被别的 TypeScript 项目引用，再打开 declaration: true，让 tsc 一并产出 .d.ts，并在 package.json 里写上 "types": "dist/index.d.ts"；只给服务自己用的工程不必开，声明文件只会拖慢构建。构建前记得清空 dist，否则上一次的残留文件会让发布内容多出几个早已删除的入口。

运行时边界：环境变量与异步的类型

编译期再严，也管不到进程启动时读进来的字符串。process.env 的每个值都是 string | undefined：Number(process.env.PORT) 在变量缺失时得到 NaN，process.env.DATABASE_URL 可能是 undefined，直到第一次连库才炸。

治理办法很土但有效：所有环境变量在一个模块里集中读取并校验，对外只导出一个类型明确的配置对象。

这样业务代码只依赖 AppConfig，测试时构造一个假对象即可，不必再摆弄 process.env；配置缺失在启动阶段就失败，比跑到一半才报错好查。NODE_ENV 那里用了类型断言，是本篇少数可以接受断言的位置，因为合法取值由启动脚本保证。required 的返回值被收窄成 string，靠的正是 strictNullChecks 对 if 分支的排除，这也是打开 strict 后最直接的收益之一。

本地开发常用 dotenv 把 .env 里的键值注入 process.env，在入口最早处调用一次 require('dotenv').config() 即可。要注意它只是塞字符串进去，类型依旧是 string | undefined，上面那层校验一步都不能省；.env 不要提交进仓库，CI 与线上交给部署平台注入。

三个常见坑

坑一：__dirname 与资源文件

__dirname 返回当前文件所在目录。源码在 src/services/mailer.ts 时，path.join(__dirname, '../../templates') 指向 src/templates；编译到 dist/services/mailer.js 后，同一行指向 dist/templates。因为 rootDir 保住了目录层级，路径写法本身不用改，真正的问题是资源文件没被复制过去。典型现象是本地用 ts-node 一切正常，上线读模板报 ENOENT。排查顺序很固定：先看 dist 下有没有那个目录，再怀疑路径拼接，处理办法就是上一节的 postbuild。

坑二：@types/node 与运行时版本错位

类型包是编译期的事实，运行时不认。笔者见过一个服务本地用 Node 6 跑、依赖里装了 @types/node@8，util.promisify 一路绿勾，上线后报 promisify is not a function。反向也成立：运行时是 Node 8，类型停在 Node 6，Buffer.from 这类新 API 会被标红，逼着人写 any 蒙混过去。

对策有三层：engines 写清最低版本；本地与 CI 用 nvm 固定同一个大版本；类型包跟着运行时走，并由 package-lock.json 锁住。启动时顺手打印 process.version，线上排错能少猜一轮。顺带一提，engines 只是声明，npm 默认只警告不拦截，除非给项目打开 engine-strict，它替代不了版本管理。

坑三：export = 与 export default 不是一回事

Node 世界只有 module.exports，而 TypeScript 的 export default 编译出来是 exports.default，还带一个 __esModule 标记，两者并不等价。写一个对外发布的 CommonJS 模块，正确姿势是用 export =：

使用方在 2.6 下写 import createApp = require('./create-app')，或者 import * as createApp from './create-app'。反过来，若模块内部用了 export default，CommonJS 侧 require 拿到的是 { default: fn }，直接调用必然报“不是函数”。

时间点也要记住：能抹平这层差异的 esModuleInterop 选项要到 2.7 才发布，本文写作时还没有。看到配置里写着它的教程，先确认自己装的版本；照抄的结果常常是类型检查全绿、运行时拿到 undefined。

三个坑的共同点是：类型系统只覆盖编译期。凡是运行时才成立的东西——文件位置、Node 版本、模块导出形态——都要单独验证一次，别把编辑器不报错当成没问题。

小结

在 Node 里用 TypeScript，核心是把四件事钉死：module 用 commonjs、target 用 es2017，让产物与运行时能力对齐；@types/node 跟着 Node 大版本走；开发用 ts-node 换速度，上线只跑 tsc 的产物；调试用 --inspect 加 source map，让断点与堆栈都回到 .ts。脚本保持 dev、build、start 三条，外加一条复制资源的钩子，就足够支撑一个中小型服务。剩下的都是细节：资源要复制、类型包要锁版本、export = 与 export default 不要混着用。
