TypeScript 类型系统入门：基础类型

本文属于《TypeScript 学习路线》第 1/74 篇
上一篇系列目录下一篇

JavaScript 项目变大之后，最难排查的往往不是语法错误，而是“这个字段到底存不存在”“这个函数会不会收到 null”这类约定问题。TypeScript 把这些约定写进代码，让编译器在运行之前替我们检查一遍。本文面向刚接触 TypeScript 的 JavaScript 开发者，从原始类型、对象与函数讲到联合类型、窄化和结构类型，目标是建立一套可复用的类型思维，而不是背一张语法表。示例基于当时的 TypeScript 2.6。

一、类型是编译期的约束

TypeScript 最容易被误解的一点，是把它当成“带类型检查的 JavaScript 运行时”。实际上，类型标注只存在于编译阶段。tsc 完成检查后，会把类型标注、接口、泛型参数统统抹掉，产出的仍然是普通 JavaScript。浏览器和 Node 并不知道 number 与 string 的区别，也不会在函数调用时校验参数。

假设这段代码被一个没有类型的旧模块调用，传入字符串 “12”，编译器不会知道；运行时 “12”.toFixed 是 undefined，调用它就会抛错。类型系统在这里帮不上忙，因为它看到的调用方也必须是 TypeScript，而且调用方得遵守声明。

这引出两个结论。第一，类型检查能挡住的是代码内部的契约不一致：把字符串传给只接受数字的函数、访问对象上不存在的字段、忘记处理可能为 null 的返回值。第二，它挡不住外部数据。接口返回的 JSON、localStorage 里读出的字符串、用户输入，在运行时都可能是任意形状；类型标注只是我们“声称”它是什么，编译器无法替我们验证。

关注点 编译期（tsc） 运行时（JS 引擎）
类型标注 检查后擦除 完全不存在
函数参数 按声明检查 不检查
外部 JSON 按声明信任 可能是任意形状
出错表现 编辑器提示或构建失败 TypeError 等异常

所以学习 TypeScript 的第一课不是记住多少关键字，而是分清哪些问题应该在编译期解决，哪些必须留给运行时。本文后续讨论的所有类型，都建立在这个前提上：类型是写给编译器和读代码的人看的，不是运行时的保险。

二、原始类型与空值语义

TypeScript 的原始类型与 JavaScript 的原始值对应：boolean、number、string、symbol、null、undefined。标注语法是在名字后面加冒号和类型：

多数时候不必写标注，编译器会从初始值推断。let count = 42 得到 number，const title = "TS" 得到字面量类型 “TS”，后文会解释这个差别。真正需要标注的是没有初始值的变量、参数，以及初始值不足以表达意图的地方。

null 与 undefined 在 JavaScript 里既是值又是类型。TypeScript 对它们的处理由一个开关决定：strictNullChecks。关闭时，null 和 undefined 可以赋给任何类型，string 实际上包含了“字符串或空值”；打开时，它们成为两个独立的类型，只能赋给显式包含它们的联合类型。

需要强调的是，strictNullChecks 只改变类型检查，不改变运行时。它不会给变量补默认值，也不会把 null 变成 undefined；所有判空逻辑仍然要自己写，只是现在编译器会盯着我们写。TypeScript 2.3 起提供的 --strict 会把包括它在内的若干严格选项一起打开。至于存量项目如何分阶段开启、第三方声明文件怎么处理，是另一个工程话题，本文只讨论语义。

三、数组、元组与空数组

数组类型有两种等价写法：number[] 和 Array<number>。前者更短，后者在元素类型是联合或对象时更易读，例如 Array<string | number>。只读数组用 ReadonlyArray<T> 表达，它禁止 push、splice 等修改操作，但读取不受影响。

避免麻烦的办法很朴素：在声明处标注。const list: string[] = [] 让意图立刻明确，也避免后续写入把类型带偏。空对象同理，const cache = {} 推断不出索引签名，需要写成 { [key: string]: number } 或对应的接口。

最后提一个读取上的细节：数组下标访问在默认配置下返回元素类型，而不是“元素或 undefined”。即使数组可能为空，nums[10] 的类型仍是 number，运行时却可能是 undefined。这个行为与 strictNullChecks 无关，是数组类型自身的取舍；需要处理越界时，只能自己判断长度。

五、函数类型：参数、返回值与 never

函数类型由参数列表和返回值组成。参数类型通常必须写，因为编译器无法从调用处反推声明；返回值可以推断，但对外暴露的函数建议显式写出，避免实现改动时悄悄改变契约。

可选参数用 ?，必须放在必选参数之后；带默认值的参数本身也是可选的，而且默认值会参与类型推断：

两者的区别在运行时：可选参数不传就是 undefined，默认参数不传会使用默认值。类型层面，times = 2 让 times 成为可选参数，调用 repeat("ab") 合法；但如果显式传入 undefined，默认值同样会生效。这一点在封装配置对象时经常被忽略。

返回值的两个特殊类型是 void 与 never。void 表示函数不返回有意义的值，运行时仍然返回 undefined；never 表示函数永远不会正常返回，要么抛异常，要么无限循环。

never 是所有类型的子类型，可以赋给任何类型，反过来不行。它最常见的用途是穷尽检查：当联合类型的所有成员都被处理完，剩下的值会被收窄为 never，此时再访问它的属性就会报错，从而提醒我们漏了分支。

回调类型里还有一条容易忽略的规则：如果函数类型声明返回 void，那么传入一个有返回值的函数是允许的，返回值会被忽略。这让 items.forEach(item => results.push(item)) 这样的写法不会因为 push 返回 number 而报错。规则的本意是“调用方不关心返回值”，而不是“函数必须返回空”。

七、窄化：让类型跟着分支走

窄化是类型系统里最像推理的部分：编译器根据运行时的判断，在不同分支里把联合类型收窄成更具体的成员。上一节留下的问题——联合类型只能访问共有属性——正是靠窄化解决的。

八、结构类型：形状相同就兼容

TypeScript 采用结构类型系统：判断两个类型是否兼容，看的是形状，而不是名字。只要目标类型要求的成员都存在且类型匹配，就认为兼容。

p3 从未声明自己实现了 Point，但它有 x 和 y，且都是 number，于是可以传给 draw；多出来的 z 不影响兼容性。这与 Java、C# 的名义类型不同：在那里，一个类必须显式声明 implements Point 才算数。

类与接口之间也遵循同样的规则，但参与比较的是实例的公开成员。私有成员会引入一个少见的“名义”成分：两个类即使公开形状相同，只要私有字段来自不同声明，就不能互相赋值。这是结构类型系统为了保证封装而留的例外。

结构类型带来的直接好处是测试友好。依赖一个只有方法的接口时，传一个手写对象即可，不需要继承或 mock 框架。

代价则是“意外兼容”。两个形状相同但语义不同的类型可以互相赋值：以元为单位的金额和以分为单位的金额都是 number，编译器无法分辨；用户 ID 和订单 ID 都是 string，传错也不会报错。需要区分语义时，常见做法是用交叉类型附加一个只存在于类型层面的标记字段，构造时显式断言一次，之后就能靠类型阻止混用。

还要注意 {} 与 object 的区别。在 strictNullChecks 打开时，{} 接受任何非 null、非 undefined 的值，包括数字和字符串；object（2.2 引入）只接受非原始类型。想表达“任意对象”时用 object，想表达“任意非空值”时才用 {}。

九、any 的代价与泛型的位置

any 的语义是放弃检查。一个值被标成 any 之后，可以访问任意属性、调用任意方法、赋给任意类型，而且这种不检查会沿着赋值和返回值传播。

更糟的是，any 会污染调用链：const user: User = parse(text) 不会报错，user 之后的字段访问又恢复了检查，但检查建立在错误的信任之上。开启 noImplicitAny 可以阻止隐式 any，显式写下的 any 仍然需要人来克制。

当时还没有 unknown 这个类型。TypeScript 团队已经在讨论引入一种“只能收窄、不能直接使用”的顶层类型，按路线图可能要等到 3.0 才会落地；在 2.6 上它并不存在。当前的替代方案是：边界处用 any 接收，紧接着用运行时校验或守卫函数把它转成具体类型，不要让 any 流过模块边界。

如果只需要表达非原始值，用 2.2 引入的 object 比 any 精确；如果只是暂时说不清结构，可以把 any 限制在一个解析函数内部，对外仍然返回具体类型。类型系统的价值来自可信，而不是看起来处处都有类型。

泛型常被当成进阶内容，但它首先解决的是一个朴素问题：容器里的元素类型要跟着使用场景变化，而检查不能丢。数组就是最熟悉的例子，number[] 与 Array<number> 是同一种类型，尖括号里的 T 只是元素类型的占位符。Promise、ReadonlyArray 也是同样的思路。

十、推断、断言与迁移心智

类型推断决定了我们少写多少标注。编译器主要在三个位置推断：变量初始化、函数返回值，以及上下文类型。

上下文类型是指根据使用位置反推表达式类型。把箭头函数直接传给 map 时，n 不需要标注；把同一个箭头函数先赋给一个没有类型的变量，n 就可能变成 any 或触发隐式 any 报错。写事件回调、配置对象时，这种差别尤其明显：同一个函数写在调用处能获得完整的参数类型，抽成独立变量后反而需要手动补标注。

经验规则可以归纳成四条：函数参数必须标注，除非有上下文类型；对外导出的函数写返回类型；空数组、空对象、可能为 null 的变量在声明处标注；联合类型难以收窄时，用类型别名把成员命名清楚。其余情况交给推断。标注越多不代表越安全，重复的标注反而容易和实现脱节，改动一处忘记同步另一处，编译器就会给出误导性的错误。

把上面的规则压缩成一张表，落地时更容易对照：

场景 建议 理由
函数参数 显式标注 编译器无法从调用处反推
导出函数返回值 显式标注 固定对外契约
局部变量 交给推断 减少重复标注
空数组、空对象 声明处标注 避免 any 扩散
联合类型 用别名命名 便于收窄与复用

类型断言告诉编译器“我知道得比你多”：

断言只影响编译期，不会在运行时做转换或检查。如果 id 为 app 的元素其实是 span，这段代码照样编译通过，运行时行为由 DOM 决定。断言的风险在于它绕过了编译器唯一的防线，所以应该尽量集中在边界处，并在旁边写清楚为什么可以这样断言。经验上，每写一个断言，都应该能回答“如果它不成立，运行时会在哪一行出错”。

断言有两种写法：value as T 与 <T>value。后者在 .tsx 文件里会和 JSX 标签的语法冲突，所以团队通常统一使用 as，本文的示例也采用这一种。

双重断言 value as any as User 几乎可以骗过所有检查，除非在迁移旧代码，否则不应出现。非空断言 value! 是另一种断言，语义是“这里的值一定不是 null 或 undefined”，同样不产生运行时检查。它适合用在编译器无法证明、但代码结构已经保证的地方，比如刚赋值完就读取的字段；不适合用来消除满屏报错。当 ! 越来越多时，通常说明数据边界没有描述清楚，应该回头补类型，而不是继续向编译器保证。

从 JavaScript 迁移到 TypeScript，最有效的心智模型不是“给每一行加类型”，而是分两步：先描述数据形状，再描述函数边界。

第一步，把接口返回、配置、组件 props 这些核心数据结构写成 interface 或 type，想清楚哪些字段可选、哪些只读、哪些是联合取值。第二步，给模块对外的函数标注参数和返回值，让模块之间的契约先固定下来。内部实现尽量依赖推断和收窄，等编译器报错的地方再逐个处理。

flowchart LR
  A[梳理数据形状] --> B[定义 interface 或 type]
  B --> C[标注模块边界函数]
  C --> D[依赖推断与收窄]
  D --> E[处理编译器报错]
  E --> F[逐步扩大迁移范围]

这样做的好处是改动集中、可回滚：数据形状和函数边界稳定之后，内部实现可以慢慢改，类型检查会像一张网提示遗漏的分支。反过来，如果一上来就给所有局部变量加标注，既写不出准确的类型，也会把时间耗在无意义的语法上。更现实的做法是先让新代码带上类型，旧代码通过边界函数逐步收口，而不是追求一次性全量迁移。

还有一点需要提前接受：类型不是越严格越好。一个刚迁移的模块，用 any 挡住暂时说不清的数据，比写一个错误的类型更诚实；但要在代码里留下 TODO，并把 any 限制在边界。同样，断言和 ! 也不是洪水猛兽，它们是类型系统留给人类的逃生通道，关键在于用得少、用得清楚、用得有理由。类型系统的价值来自可信，而不是看起来全都有类型。

小结

TypeScript 的类型是编译期契约，运行时仍然是 JavaScript，外部数据永远需要运行时校验。原始类型、对象、数组、元组和函数类型构成了描述数据的基础；字面量类型与联合、交叉让我们能表达有限取值和组合关系；窄化则让编译器沿着分支逐步收窄类型。结构类型系统用形状判断兼容，灵活但需要警惕意外兼容。any 会关闭检查并传播，应该限制在边界；泛型让容器与函数在保住类型的同时复用。迁移时先描述数据形状，再描述函数边界，让推断和收窄承担剩余工作；把这些基础打牢，再读声明文件和框架自带的类型定义会轻松很多。
