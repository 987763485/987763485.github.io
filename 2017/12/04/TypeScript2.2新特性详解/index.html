TypeScript 2.2 新特性详解

本文属于《TypeScript 学习路线》第 24/74 篇
上一篇系列目录下一篇

TypeScript 2.2 在 2017 年 2 月发布，夹在 2.1 的键运算与 2.3 的严格模式聚合之间，存在感不算强，却补上了三块基础拼图：object 类型、更严格的 never 检查，以及 mixin 类的类型支持。本文从这三个特性出发，结合示例说明它们分别解决什么问题、边界在哪里，以及从旧版本升级时容易踩的坑。适合希望把类型写得更准确的读者。

一、2.2 的位置：从描述键到描述值

2016 年底发布的 TypeScript 2.1 把重点放在“键”上：keyof 取出属性名，映射类型批量改写属性，Partial、Pick、Record 则把常见的对象变换固化成工具类型。键的语义补齐之后，另一个问题浮出水面：值本身该如何约束？一个函数只想接收“非原始值”，用 any 太松，用 Object 又会放行字符串；一个函数永远抛出异常，返回类型写 void 并不准确；两个类想共享一段实现，单继承又不够用。

TypeScript 2.2 正面回答了这三类问题：新增 object 类型，收紧了 never 的检查，并让类可以继承一个类型参数，从而支持 mixin 写法。它还对 null 与 undefined 的若干边界做了处理，使严格空检查下的行为更一致。本文写作时的稳定版本已是 2.6，回头看，这三个特性都不算耀眼，却都成了常用工具。

接下来我们按 object、never、mixin 的顺序逐一展开，再讨论严格空检查下的边界和升级时的注意事项。2.3 把 strictNullChecks 等开关聚合进 --strict，方向与 2.2 一脉相承：让类型系统的约束更贴近运行时的真实行为。

二、object 类型：不是“任意对象”

object 的字面意思容易让人误会。它并不表示“任意对象字面量”，也不表示“可以随意取属性的字典”，而是表示所有非原始值。在 TypeScript 的定义里，原始值包括 number、string、boolean、symbol、null 和 undefined，除此之外的值都属于 object：对象字面量、数组、函数、Date、正则、Map、类实例，统统满足。

函数也被算作对象，这与 JavaScript 的运行行为一致：函数本来就可以有属性、可以作为参数传递。字符串虽然能调用 toUpperCase，但语言层面仍是原始值，不能传给 object 参数。

与几个容易混淆的类型对比，差别会更清楚：

类型 接受原始值 接受 null/undefined（开启 strictNullChecks 时） 主要用途
any 是 是 完全放弃检查
Object 是 否 需要 Object 原型成员
{} 是 否 表示“非空值”
object 否 否 排除原始值

需要强调的是，object 只承诺“不是原始值”，不承诺任何结构。它没有声明任何属性，也没有索引签名，因此在函数体内既不能读 value.id，也不能写 value[key]。从 2.1 的视角看，keyof object 的结果是 never，正好说明它没有任何已知的键。把它当成“任意对象”来用，很快就会撞上编译错误。

若需要“任意字符串键的字典”，应该写索引签名或使用 2.1 引入的 Record<string, T>；若需要具体形状，应该定义接口。object 的职责只有一个：在参数或返回值的位置，把原始值挡在门外。

四、never：没有值的底部类型

never 是类型系统里的底部类型：它是所有类型的子类型，却没有任何值属于它。听起来抽象，用起来很具体——它描述“这个函数不会正常返回”。

never 与 void 常被混淆。void 表示函数正常结束时没有返回值，调用方拿到的是 undefined；never 表示函数根本走不到返回点，要么抛出异常，要么永远不结束。把永远抛错的函数标成 void，类型上不会报错，但调用方会误以为后续代码还能继续执行，表达力就丢了。

never 的另一个用途是穷尽检查。对一个可辨识联合做 switch，如果所有分支都处理完，默认分支里的值会被收窄为 never；此时把它传给一个只接受 never 的函数，就能让编译器替我们确认没有漏掉成员：

2.2 对 never 检查的补强

2.2 收紧了 never 的相关规则。其一，声明返回 never 的函数，函数体不能存在可达的终点：如果某个分支悄悄 return 了，或者循环条件可能为假，编译器会指出来。其二，never 在联合类型中会被吸收，string | never 就是 string，不会留下一个多余的分支；收窄到 never 的分支在类型层面已不可达，继续访问属性会直接报错。其三，never 作为所有类型的子类型，可以赋给任何位置，这让 assertNever 这类函数可以放在任何返回位置，而不用写类型断言。

这些规则单独看都很小，合在一起才让 never 从“文档里的概念”变成可以依赖的编译期约束。需要提醒的是，never 变量可以被赋给任何类型，却不能被赋入任何值；如果看到“类型 never 上不存在属性”的报错，通常不是类型写错了，而是那段代码已经被判定为不可达。

五、mixin 类：用函数组合类

JavaScript 的类只有单继承，共享实现通常靠“把一段行为混入另一个类”，写成高阶函数：接收一个基类，返回继承了它的匿名类。TypeScript 2.2 之前，这种写法很难获得完整的类型：类不能继承一个类型参数，extends Base 会报错，只能靠断言或 any 糊过去。2.2 允许类表达式继承类型参数，mixin 终于可以类型安全地表达。

运行时层面，mixin 返回的是真正的类，instanceof 对每一层都成立：admin instanceof User 与 admin instanceof TimestampedUser 都为真。这一点比用 Object.assign 拷贝属性更可靠，后者不会建立原型链，也无法通过 instanceof 判断。

六、mixin 的边界与代价

2.2 的 mixin 支持有明确的边界。

首先是构造函数。派生类如果自己写构造函数，必须用单个 rest 参数把参数转发给 super：

这意味着混入内部拿不到基类构造函数的具体参数类型，args 是 any[]；参数检查发生在 new 调用处，由推断出的构造签名负责。若基类构造函数有重载或特殊参数，这种“整体转发”会比较笨拙。TypeScript 对继承类型参数的类有额外限制，比如构造函数必须是单个 rest 参数，否则直接报错。

其次是 super 与基类成员。约束写成 Constructor<{}> 时，类型系统只知道基类实例是空对象，混入内部无法调用基类的方法，也无法安全地重写后 super.method()。想把约束收窄成带方法的接口，所有被混入的基类就都必须满足该接口，灵活性下降。mixin 更适合“叠加新能力”，不适合“精细改造基类行为”。

再次是私有状态。2017 年时 JavaScript 还没有私有字段语法，TypeScript 的 private 只是编译期修饰符。混入类访问不到基类的 private 与 protected 成员；带私有成员的类在结构类型系统里也带有“声明来源”的印记，跨声明替换容易失败。实际项目里，mixin 通常只依赖基类的公开成员，把共享状态放在混入自己这一层。

最后是复杂度。每叠一层就多一层匿名类，构造函数名不直观，错误堆栈也会变长。两三层尚可接受，再多不如回到组合：把能力做成独立对象注入，类型更清晰。

七、strictNullChecks 与升级注意事项

object 与空值的边界值得单独说一句。开启 strictNullChecks 时，null 和 undefined 不能赋给 object，上面的 inspect(null) 会立即报错；关闭时，它们可以赋给包括 object 在内的几乎所有类型，类型层面的保护就消失了。2017 年不少项目还没开启严格空检查，看到 object 参数就以为“一定非空”是危险的，运行时判空仍不能省。可选参数 value?: object 是 object | undefined，也要先收窄。

从旧代码升级到 2.2，object 与 never 是两类主要报错来源。

第一类是把 Object 或 {} 换成 object 之后，原来能传字符串、数字的调用点开始报错。这不是 2.2 变严格了，而是新类型本来就不接受原始值。处理方式要看意图：如果函数确实只处理非原始值，修改调用方或补上类型收窄；如果只是想要“任意值”，应该继续用 {} 或泛型；如果代码里调用了 toString、hasOwnProperty，object 上没有这些成员，要么换成 Object，要么先收窄到具体接口。另一个常见错误是 obj[key]：object 没有索引签名，需要改成 { [key: string]: T } 或 Record<string, T>，再用泛型约束键。

第二类是 never 引起的报错。函数标注了 never 却在某个分支正常返回，编译器会要求你删掉那个 return 或者把返回类型改掉；switch 的穷尽检查报“不能赋给 never”，通常意味着联合类型新增了成员而分支没跟上，这是好事，按提示补分支即可；如果某个变量被收窄成 never 后还在取属性，说明那段代码不可达，应当删除而不是加断言。还有一种隐蔽情况：函数本该抛错，但某个分支可能什么都不做就结束，推断结果不再是 never，补一个兜底 throw 最稳妥。

mixin 的升级问题相对少，主要是旧的高阶函数写法没有声明构造器约束，或者内部构造函数不是 rest 参数形式。按 2.2 的规则补上 Constructor<T> 约束与 super(...args) 即可；如果基类含有私有成员，先确认混入没有越界访问。总体原则是：先把 object 用在真正需要“非原始值”的边界，把 never 用在真正不会返回的函数与穷尽检查上，不要为了用新特性而全局替换类型。

小结

TypeScript 2.2 不是一个以大特性著称的版本，但它补齐了三块基础设施：object 让“非原始值”成为可表达的类型，never 让“不会返回”与穷尽检查变得可靠，mixin 支持则让类的能力组合有了类型安全的写法。使用 object 时要记住它只排除原始值，既不保证形状，也不提供索引签名；使用 never 时要区分它与 void，并利用联合类型的吸收与收窄做穷尽检查；使用 mixin 时要接受构造函数整体转发、基类成员不可见、私有状态难共享这些代价。升级时，object 相关的报错多半来自旧代码把 Object 当成了“任意对象”，never 相关的报错则往往在提醒你补全分支或删除不可达代码。把这三个特性放在 2.1 的键运算与 2.3 的严格模式之间看，2.2 的定位很清楚：让类型系统从“描述形状”走向“描述行为”。
