Go 标准库 net/http 实战

本文属于《Go 语言与工程》第 20/78 篇
上一篇系列目录下一篇

用 Go 写一个 HTTP 服务，往往只需要十几行标准库代码，但真正上线之后，超时、连接复用、优雅关闭这些细节才会逐个暴露出来。本文从最小的服务器写起，依次拆开 Handler 接口、ServeMux 的匹配规则、请求解析与响应写出，再补上中间件、超时配置、优雅关闭与客户端调用。读完你应当能只用 net/http 搭出一个结构清晰、可以安全上线的服务，并知道哪些坑必须提前避开。

从一个最小的服务器开始

Go 1.9 的标准库自带完整的 HTTP 服务端与客户端实现，写一个能响应请求的服务不需要任何第三方依赖。最小的版本只有两步：用 http.HandleFunc 向默认的 ServeMux 注册一条路径，再调用 http.ListenAndServe 监听端口。

这段代码可以直接 go run 运行。ListenAndServe 是阻塞调用，只要服务正常提供，它就不会返回；一旦返回，返回值一定非 nil。常见的两类原因，一是端口被占用或监听地址非法，二是我们主动调用 Shutdown 之后返回的 http.ErrServerClosed。所以不要 go http.ListenAndServe(...) 之后对返回值不闻不问，监听失败时进程会安静地“活着”。

地址参数 ":8080" 表示监听本机所有网卡的 8080 端口；如果只想让本机访问，写成 "127.0.0.1:8080"。第二个参数传 nil 表示使用全局默认的 http.DefaultServeMux。示例这样写最短，但正式项目更推荐自己创建一个 ServeMux 再交给 http.Server：全局变量无法隔离，两个包都往 DefaultServeMux 注册路径时很容易冲突，测试时也没法为每个用例准备独立的路由表。

一次请求进来后，处理链大致如下：

sequenceDiagram
    participant C as 客户端
    participant S as http.Server
    participant M as ServeMux
    participant H as Handler
    C->>S: 发起 HTTP 请求
    S->>M: 按路径查找 pattern
    M->>H: 调用 ServeHTTP(w, r)
    H-->>C: 写入状态码与响应体

后面关于中间件、超时和关闭的讨论，都是在链路上找合适的插入点。

HandlerFunc 是一个函数类型，它的方法把自身当作函数调用一次。于是 http.HandlerFunc(fn) 这个类型转换，就把 fn 变成了一个 Handler。http.HandleFunc 内部做的正是这件事：接收函数，转换成 HandlerFunc，再注册到 mux 上。初学者常把 http.HandleFunc（注册路由）和 http.HandlerFunc（类型适配）混为一谈，记住前者是动作，后者是类型即可。

ServeMux 的匹配规则与自行判断方法

ServeMux 是标准库自带的路由器，规则不多，但每一条都会影响线上行为。它的规则可以概括为：不带末尾斜杠的 pattern 要求路径完全相等，带末尾斜杠的 pattern 按子树前缀匹配；多个 pattern 同时命中时，取最长的那一个。

几个容易忽略的细节：

  • pattern 以 / 结尾表示一棵子树。/static/ 能匹配 /static/、/static/app.js、/static/a/b.css，但不匹配 /static。
  • 如果只注册了 /static/，访问 /static 时 mux 会自动返回 301，重定向到 /static/。这对 GET 无伤大雅，对 POST 却会让客户端困惑，必要时两个 pattern 都注册。
  • / 是最终兜底。任何没有更具体匹配的路径都会落到它上面，所以首页处理器必须自己判断 r.URL.Path，否则随便一个不存在的地址都会返回首页的 200。
  • mux 匹配的是净化后的路径。请求里出现 ..、. 或连续斜杠时，会先 301 到清理后的地址，这是安全设计，但也意味着客户端要能跟随重定向。
  • 注册顺序不影响结果，匹配只看 pattern 的长度和前缀，与注册先后无关。

最关键的一点：Go 1.9 的 ServeMux 只认路径前缀，既不解析 HTTP 方法，也不支持路径参数。像 GET /users/:id 这种写法在这个版本里既不会按方法匹配，也不会解析参数，只会变成一个几乎不可能命中的 pattern。想区分方法，只能在处理器里自己判断：

解析请求：查询参数、表单与 JSON

请求数据的来源主要有三处：URL 查询串、表单体和 JSON 体。它们的解析方式不同，出错时的行为也不同。

r.Body 由服务器在处理器返回后自动关闭，不需要我们调用 Close；但如果只读了一半就返回，剩余部分会被丢弃，连接通常也无法复用，不需要读完时应尽早返回。

写出响应：头、状态码与 JSON 编码

响应的顺序是有讲究的：先通过 w.Header() 设置响应头，再调用 w.WriteHeader(status) 写出状态码，最后写响应体。WriteHeader 只能生效一次，之后再修改头字段不会有任何效果，标准库只会在日志里留一句 superfluous WriteHeader。如果完全没调用 WriteHeader，第一次 w.Write 会隐式写出 200。

直接写 JSON 最省事的方式是 json.NewEncoder(w).Encode(v)：它把编码结果直接写到连接上，还附带一个换行。方便归方便，错误处理却很别扭——它写完响应体你才拿到错误，此时状态码已经发出，只能记日志；如果先写了 200 才发现数据无法序列化，客户端拿到的就是一个空的成功响应。对 API 响应，笔者更倾向先编码到内存、确认无误后再写：

json.Marshal 失败时还没有写任何字节，因此可以安全地回退到 500。响应头也统一，不会出现 text/plain 与 application/json 混用的情况。如果不显式设置 Content-Type，标准库会嗅探前 512 字节来猜类型，JSON 很容易被猜成纯文本，客户端的自动解析就会失效。

状态码要按语义使用：创建成功返回 201，删除成功且无内容返回 204，参数错误 400，未认证 401，无权限 403，资源不存在 404，冲突 409，服务端故障 500。需要特别注意，204 和 304 不允许有响应体，写完状态码再写内容会被服务器拒绝并记录错误。

错误响应同样要克制。http.Error 会设置 Content-Type: text/plain、写入消息并调用 WriteHeader，适合快速返回纯文本错误。但对外的消息应当是稳定的、不包含内部细节的文案，例如 "internal server error"；真正的错误值用日志记录下来。把 err.Error() 原样返回给客户端，等于把数据库地址、SQL 片段和文件路径交到攻击者手里。

中间件：用 Handler 包 Handler

中间件在标准库里的形态非常朴素：一个接收 http.Handler、返回 http.Handler 的函数。因为处理器本身就是接口，包装它不需要任何框架支持。

日志中间件只保留最小实现，字段规范与采样策略是另一个话题。恢复中间件用 defer 捕获 panic，防止一个越界访问把整个进程带走；但如果 panic 发生在响应写到一半之后，500 也发不出去，它只能保证进程继续服务，不能保证响应完整。

超时配置与优雅关闭

http.Server 的零值可以直接启动，但它的几个超时字段默认都是 0，含义是永不超时。一个只发了半截请求头的连接就能长期占住一个 goroutine 和文件描述符，慢速攻击正是靠这一点耗尽服务的。上线前至少显式设置下面几项：

ReadHeaderTimeout 只限制读完请求头的时间，专门防慢速头攻击；ReadTimeout 覆盖从连接建立起读完整请求的时间，包含请求体；WriteTimeout 从读完请求头开始计时，覆盖整个响应的写出，必须大于业务最长处理时间，否则耗时任务会在写响应时被切断；IdleTimeout 控制 keep-alive 连接两次请求之间的空闲时间，Go 1.8 起可用，不设置时退回 ReadTimeout。这些数值没有通用答案，要按接口实际耗时留余量；负载均衡器的空闲超时还应小于 IdleTimeout，否则会出现偶发的连接重置。

进程收到 SIGTERM 时不能直接退出，否则正在处理的请求会被拦腰截断。Go 1.8 提供的 Shutdown 正好解决这个问题：

这段代码把监听放到独立 goroutine，主 goroutine 等待信号。Shutdown 会停止接受新连接、关闭空闲连接，并等待正在处理的请求结束；如果等待超过传入 context 的期限，它返回 context 的错误，此时再调用 Close 强制断开。注意 Shutdown 只等 HTTP 处理器返回，不等待处理器内部另起的后台 goroutine。这类任务要用 sync.WaitGroup 登记，在 Shutdown 之后按同一个期限等待。后台 goroutine 也不要继续使用 r 或 r.Body：处理器返回后请求体已关闭、r.Context() 已取消，需要的数据应当在启动 goroutine 之前拷贝出来。

HTTP 客户端与高频的坑

客户端同样有默认值陷阱。http.Get 使用没有超时的 DefaultClient，对端不响应时调用会一直挂着。正确做法是自建一个复用的 Client，显式设置 Timeout，再用 http.NewRequest 构造请求：

Client 可以并发使用，内部维护连接池，整个进程共用一个即可；每次新建 Client 反而会让连接无法复用。Do 返回的 error 只覆盖传输层失败和重定向策略，404、500 都不会进 error，必须自己检查 StatusCode。resp.Body 一定要 Close，即使不读内容；想复用连接，还要把 body 读干净，否则连接会被丢弃。读取时套一层 io.LimitReader，避免对端返回超大响应把内存吃满。

最后还有两个高频的坑。一是在调用 http.Error 后忘记 return，继续写业务响应，此时头已经发出，日志里会出现 superfluous 警告；二是把内部错误原样返回给客户端，既泄漏细节，也让接口契约不可控。

小结

net/http 的 API 很小，难的是把默认值逐个改成适合生产的值。本文的路线可以概括为：用 Handler 接口组织业务，用 ServeMux 做前缀路由并自行判断方法，请求解析显式检查错误并限制大小，响应先编码再写状态码，中间件只依赖标准接口。上线前补齐读写超时与 IdleTimeout，用 Shutdown 配合信号和 WaitGroup 收尾，客户端复用同一个带超时的 Client 并记得关闭 body。把这些做对，标准库足以支撑大多数中小规模的服务。
