Go 基准测试与性能分析

本文属于《Go 语言与工程》第 18/78 篇
上一篇系列目录下一篇

接口变慢、内存上涨的时候，凭直觉改代码往往南辕北辙。本文从 testing.B 写起，讲清楚怎样写出可信的基准、怎样读懂 ns/op 与 allocs/op、怎样用 pprof 和逃逸分析把“慢”落到具体的函数与行，最后给出一条可以照着执行的优化流程。适合已经会写 TestXxx、希望让 Go 服务跑得更稳的读者。

基准测试与单元测试的分工

单元测试回答的是“对不对”，基准测试回答的是“多快、代价多大”。TestXxx 用断言把预期结果钉死，一旦行为偏离就失败；BenchmarkXxx 不做判断，它只把同一段逻辑重复执行足够多次，然后报告每次操作的平均耗时与内存分配。两者都写在 _test.go 文件里，由 go test 分别识别。

这个区别影响很大。单元测试的通过与否是二值的，基准测试的输出是一组连续的数值，因此它必须回答三个前置问题才有意义：测的是哪段代码、输入是什么规模、跑在哪台机器上。缺少任何一个，数字都无法比较。

笔者见过不少团队把“优化”做成这样：某位同事觉得某个函数慢，随手换一种写法，提交时说“这样更快”。没有基线也没有复测，Review 时谁也判断不了。基准测试的价值就是把这类争论变成可复现的实验：改前跑一遍，改后用同样的命令再跑一遍，数字自己会说话。

还有一点容易忽略：基准函数默认不运行。只有加上 -bench 参数，BenchmarkXxx 才会被调用。这是有意设计的：基准通常比单元测试慢，不适合放进每次提交的快速检查；改动性能敏感路径时再单独跑。

第一个基准函数：b.N 与计时器

基准函数的签名固定为 func BenchmarkXxx(b *testing.B)。函数体里最重要的是 b.N：它不是我们指定的次数，而是测试框架在运行时逐步调整出来的循环上限。框架先给一个较小的值试跑，如果总耗时不足 -benchtime（默认 1 秒），就把 b.N 调大重跑，直到总耗时达到目标或者次数达到上限。

由此得到一个必须记住的结论：基准函数体可能被执行多次，b.N 每次都不一样。函数体里只能放可重复的纯计算，不能有“只发生一次”的副作用。

如果准备数据本身有成本，比如从文件读入、构造十万条记录，就必须把这部分排除在计时之外。b.ResetTimer() 会清零已累计的时间和内存统计，并从调用处重新开始计时；与之配套的还有 b.StopTimer() 与 b.StartTimer()，用于循环中间需要暂停计时的场景。

注意 buildFixture 虽然写在 ResetTimer 之前，仍然位于会被重复执行的函数体里。如果它修改全局状态，第二次进入基准时数据就可能翻倍。稳妥的做法是让准备逻辑幂等。

运行参数与结果解读

常用参数不多，但每个都有明确用途：

  • -bench=.：运行当前包里所有基准，. 是正则，也可以写 -bench=Concat 只匹配名字。
  • -benchmem：额外输出 B/op 与 allocs/op 两列，这是内存视角的关键。
  • -benchtime=5s：把默认的 1 秒拉长，减小偶然误差；调代码时可以写更短的值加快反馈。
  • -count=5：把同一组基准重复跑 5 次，用来观察波动，而不是只看一个孤零零的数字。
  • -run=^$：不跑普通测试，只跑基准，避免单元测试的耗时混进来。
  • -cpu=1,4：分别以 GOMAXPROCS=1 和 4 运行，观察并发度对结果的影响。

名字末尾的 -4 是运行时的 GOMAXPROCS，用来确认这次测量的并发度。三个指标的含义分别是：ns/op 是每次操作的平均墙钟耗时；B/op 是每次操作平均分配的字节数；allocs/op 是每次操作发生的内存分配次数。后两者比耗时稳定得多，因为它们只取决于代码路径，基本不受机器负载影响。

读数时也要知道这些数字说明不了什么。第一，它不告诉你是哪一行慢，要知道得靠 profile。第二，它是多次迭代的平均值，掩盖了最慢的那几次，不能当作延迟分布使用。第三，它只反映固定 GOMAXPROCS 下的表现，锁竞争、channel 阻塞要另设计实验。第四，它不能跨机器比较，CPU 型号、频率、内存带宽都会改变结论，能比的只有同一台机器上的前后两次。

常见错误与噪声控制

错误一：把 setup 放进循环。 每次迭代都重新构造输入，测出来的时间大部分花在准备上。这类错误在结果里往往表现为 ns/op 大得离谱、B/op 偏高，却容易被误读成“业务逻辑就是慢”。反过来也有一种：setup 放在循环外却忘了 ResetTimer，把准备时间摊进了每次操作。

错误二：把 I/O 和外部依赖算进去。 基准里打日志、读文件、连数据库、发 HTTP 请求，测到的就是磁盘和网络，而不是代码本身。基准应该只跑纯内存逻辑，外部依赖用固定的内存数据替代；接口层的吞吐与延迟是压测工具的活。

错误三：结果被优化掉。 如果返回值没人使用，编译器与运行时就有理由不保留这次计算，ns/op 会小得不真实。最省事的防优化手段是把结果写入一个包级变量，让它“有人用”：

循环体里只保留一次赋值，读者一眼能看出被测的是什么；这点开销可以忽略。

错误四：只跑一次就下结论。 基准输出是一次运行的平均值，而一次运行会受很多因素影响：后台进程、CPU 降频、GC 时机、编译缓存是否命中。同一份代码连续跑三次得到四千、四千三、九千八 ns/op 并不罕见，最后那个异常值可能只是恰好赶上了一轮 GC 或者系统更新。

所以结论至少要建立在多次运行上。-count=5 会把每组基准重复执行 5 次，输出 5 行；要看的是分布，而不是挑最小的那个报喜。如果波动范围很大，说明测量本身不可靠，应先排查环境。

对比两组结果时，可以用 golang.org/x/perf 里的 benchstat，它读入多次运行的输出并给出统计意义上的差异判断。我们团队的做法更朴素：把 -count 的输出存成文件，人工看中位数和范围，超出噪声的差异才认。

几条降低噪声的经验：测量时不要同时编译、同步文件或跑容器；笔记本插上电源，避免省电策略降频；固定 GOMAXPROCS，用 -cpu 明确写出来；一次只改一个变量，改完用完全相同的命令重跑。这些要求听起来琐碎，但性能优化里最贵的成本往往不是改代码，而是相信了一个错误的数字。

CPU 与内存 profile

基准给出“慢”这个事实，profile 给出“慢在哪”。两者配合，才构成完整的证据链。

CPU profile 的用法是在跑基准时加 -cpuprofile：

go test 会在当前目录留下一个 concat.test 可执行文件，把二进制和 profile 一起交给 pprof，符号才能正确解析。进入交互界面后，常用的三个命令是：

  • top：按开销排序列出函数，flat 是函数自身的耗时，cum 是包含其调用的累计耗时。
  • list 函数名：把源码和每一行的采样数并排显示，直接定位到热点行。
  • web：生成调用关系图，需要本机安装 graphviz；没有图形环境时，用 top 与 list 已经足够。

一个容易误判的点是只看 flat 排行。某个小函数 flat 很高，可能只是被调用得极多，真正的成本在调用方；反过来，cum 很高但 flat 很低的函数自己并不慢，只是“路过”。两个列一起看，再用 list 落到行，结论才可靠。

逃逸分析与在线 profiling

有时候 profile 显示某个函数分配很多，代码里却明明没有 new 或 make。这时要看逃逸分析：编译器判断一个变量能否安全留在栈上，判断不了就放到堆上，而堆分配意味着更大的 GC 压力。

输出里出现 escapes to heap 或 moved to heap 的行，就是编译器给出的理由。常见的触发场景包括：把局部变量的地址返回出去、把值装进 interface{}、被闭包捕获、作为参数传给编译器无法分析的函数、对象体积过大。

需要强调，逃逸不等于错误。返回指针本身就是语义的一部分，调用方需要这个对象活得比函数更久。我们要消除的是热路径上无谓的逃逸，比如为了少写一个参数就把配置结构体装进 interface{}，或者在循环里反复创建本可以复用的缓冲。

基准与 profile 解决的是“离线”问题，线上服务还需要另一个入口。标准库的 net/http/pprof 只要匿名导入，就会把一组调试端点挂到默认 mux 上：

之后可以用 go tool pprof http://127.0.0.1:6060/debug/pprof/profile 抓 30 秒的 CPU 采样，用 /debug/pprof/heap 查看堆。安全上必须强调：这些端点没有身份认证，会暴露函数名、调用栈、命令行参数甚至源码路径。只监听回环地址或内网，使用独立端口，不要挂在对外服务的 mux 上，更不要通过公网反向代理暴露出去。

go tool trace 是另一个视角。go test -bench=. -trace=trace.out 之后执行 go tool trace trace.out，可以在浏览器里看到 goroutine 何时运行、何时阻塞、GC 什么时候发生。它适合回答“并发为什么上不去”“谁在等锁”这类问题，不适合替代 CPU profile 找热点。

优化流程：先测量，再动手

把上面的工具串起来，一条可执行的流程大致是：

flowchart TD
    A[建立基线：固定命令与参数] --> B[确认瓶颈在 CPU 还是内存]
    B --> C[用 profile 定位到函数与行]
    C --> D[一次只改一处]
    D --> E[同参数重跑并加 -count]
    E --> F{差异是否超过噪声}
    F -- 是 --> G[保留改动并记录数据]
    F -- 否 --> H[回退改动，重新定位]

几个原则值得反复强调。第一，优化前必须有基线，否则无法判断改动是否有效。第二，怀疑要有证据，profile 指向哪里就改哪里，不要凭“map 一定比 slice 慢”这类印象动代码。第三，一次只改一个变量。第四，改完不仅看基准，还要跑完整测试，确认语义没有变。

还有一种反模式是“为了基准而写代码”：把函数拆得七零八落只为减少一次分配，可读性下降，收益却落在噪声里。基准是工具，不是目标，保持代码简单通常更好。

小结

基准测试的核心不是“跑得更快”，而是把性能变成可比较、可复现的数字。写基准时把准备逻辑移出计时范围，用一个包级变量接住结果，别把 I/O 算进去。读结果时同时看 ns/op、B/op 与 allocs/op，并用 -count 多跑几次排除噪声。定位阶段靠 -cpuprofile、-memprofile 与 go build -gcflags="-m"，线上服务则用 net/http/pprof，但必须严格限制访问范围。最后按“建立基线、定位、单点修改、回归验证”的顺序推进，让每一次优化都有据可查，而不是一次凭感觉的赌博。
