TypeScript 接口 interface 与类型别名

本文属于《TypeScript 学习路线》第 3/74 篇
上一篇系列目录下一篇

Interface 与 type 是 TypeScript 里描述对象形状的两种写法，日常用起来几乎一样，却在声明合并、扩展方式和表达能力上分道扬镳。本文从初学者的困惑出发，对照两者的语法与能力边界，说明它们各自适合的场景，并给出一次可落地的重构过程。读完之后，你应该能解释“为什么这里用 interface、那里用 type”，而不是凭手感挑一个。

两种写法，同一个形状

接手一个写了一年多的 TypeScript 项目，多半会看到两种描述对象形状的写法并存：一部分文件用 interface 定义数据结构，另一部分文件用 type 起一个别名，等号右边再写对象字面量。两种写法都能通过编译，编辑器给出的提示也几乎一样，于是“到底该用哪个”成了代码评审里反复出现的问题。

这个困惑并非初学者独有。TypeScript 采用结构类型（structural typing）系统：只要两个类型的成员形状兼容，它们就可以互相赋值，类型的名字并不参与判断。下面两段声明描述的是同一个形状，把 User 换成 Employee 不会影响任何使用处：

正因为“形状”才是判断依据，两者在大多数业务代码里可以互换。需要做选择的地方集中在三处：能否被重复声明并合并、能否表达非对象的类型、以及扩展时的写法与报错表现。

从语法上看，interface 引入的是一个具名类型声明，type 引入的是一个类型别名，等号右边可以是任意类型，对象字面量只是其中一种：

可选属性、只读修饰符、索引签名与方法简写，两边都支持。区别在于 type 的右边不限于对象：它可以指向基础类型、联合、元组或函数类型。

接口用调用签名（call signature）表达，读起来像一个只有签名、没有实现的对象；类型别名则把函数类型直接写在等号右边。功能上等价，选哪种更多是团队习惯，函数类型与重载的细节不在本文展开。

另外，两者都只存在于编译期，编译产物里没有对应代码，所谓“interface 会增加运行时开销”的担心并不成立。

声明合并：interface 的开放扩展能力

同名接口在同一个作用域里出现多次时，TypeScript 会把它们合并成一个类型。这不是语法糖，而是语言层面刻意保留的扩展机制。

合并规则可以概括为三点。第一，成员取并集，后声明的接口补充前一个接口没有的成员。第二，同名成员的类型必须兼容，若前一个声明 method: string，后一个声明 method: number，编译器会直接报错。第三，函数成员会汇总成重载列表，调用时依次尝试匹配。

这个特性最实用的场景是给已有类型“打补丁”。浏览器的全局对象、第三方库暴露的接口，往往在我们拿到类型定义时并不完整。与其修改 node_modules 里的声明文件，不如在自己的代码里补一个同名声明：

同理，当一个公共接口预期会被不同团队扩展时，可以把它设计成 interface，让使用方各自补充字段，而不必回到源头修改。这种开放扩展的能力，是类型别名给不了的。

需要强调的是，合并只发生在同一作用域内：两个模块文件里的同名接口互不相干，跨模块扩展需要模块增强（module augmentation）语法，属于声明文件的范畴，本文不展开。

类型别名不能重复声明

报错原因不是形状冲突，而是名字冲突。类型别名、接口、类共享类型空间里的名字，因此 type Point 还会与同名的 interface 或 class 冲突。编译器不会尝试合并两个别名，也不会做任何隐式取舍。

重构时要留意：把 interface 改成 type，可能让别处依赖声明合并的扩展失效；若类型已被多方扩展，就不要轻易改。

第二个差异是可读性。交叉类型层层叠加后，编辑器的悬停提示里可能出现一长串展开的类型；接口继承倾向于只显示名字。排查类型问题时，短小的名字通常比展开的表达式更好读。

第三个差异是参与合并的能力。交叉类型产生的匿名结构无法成为声明合并的目标，而接口的名字可以。这正是库作者偏爱用接口暴露契约的原因之一。

各自的主场：type 的表达力与 interface 的契约性

接口的职责是描述对象形状，它能描述函数、数组、带索引签名的字典，却无法表达“二选一”或“固定长度的序列”。这些是类型别名的主场。

严格来说，类也可以 implements 一个对象类型的别名，所以“implements 只能配 interface”是误解。区别在于语义：interface 表达的是可被实现、可被扩展的契约，type 更像一次性的形状描述。库的入口类型用 interface，使用方看到的是一个稳定的名字，而不是一段需要展开的表达式。

性能与工具链：传闻与事实

社区里长期流传一种说法：interface 比 type 快。这个说法有来源，但需要限定条件。

编译器在检查赋值兼容性时，需要比较两个类型的成员。接口是一个有名字的类型，编译器可以为它缓存与其他类型的关系；类型别名，尤其是交叉类型和映射类型，往往要在比较前展开，层级越深，展开的工作量越大。因此在类型关系非常复杂的大型项目里，把热点处的交叉类型换成接口继承，确实可能让编辑器的响应变快一些。

但把它当成普遍规律就越界了。大多数项目的检查耗时主要来自源文件数量、第三方声明和泛型推断，两者的差异通常淹没其中；更常见的性能问题是几十层交叉与复杂映射类型，而不是关键字本身。

错误信息的可读性差异更值得关注。接口在提示中通常以名字出现；交叉类型则可能被展开成实际结构，嵌套较深时能占满大半个屏幕。排查类型错误时，可读性直接决定效率，这一点比毫秒级的检查差异更实际。

至于增量编译，当时可用的手段主要是 tsc --watch 与编辑器语言服务，它们与类型写法的关系缺少公开的量化数据。笔者不建议仅凭传闻选型，把性能当作“避免过度嵌套”的提醒即可。

常见误区与选择建议

先澄清三个流传很广的误解。

其一，interface 只能描述类。接口描述的是形状，任何对象都可以满足它，包括对象字面量、函数返回值、JSON.parse 的结果。类之所以常与接口一起出现，是因为 implements 提供了显式校验，而不是因为接口有类型限制。

其二，type 不能扩展。类型别名确实没有 extends 关键字，但交叉类型可以组合出新形状，接口也可以 extends 一个对象类型的别名。缺少关键字不等于缺少能力，只是写法不同。

其三，交叉类型等于继承。继承表达“是一个”的层级关系，交叉表达“同时满足多个形状”。冲突检测时机也不同：继承在声明处报错，交叉把冲突属性收敛为 never，到使用处才报错；交叉还不参与声明合并。把交叉当继承用，短期能编译，长期会让类型关系难以追踪。

基于以上差异，笔者建议按下面的顺序判断：

场景 建议
公开 API、组件 props、服务层契约 interface
需要被第三方或后续模块扩展 interface
需要 implements 表达契约 interface
联合、元组、字面量集合 type
映射类型、工具类型 type
纯内部的简单对象形状 跟随团队约定

把判断过程画成流程图，大致是这样：

flowchart TD
  A[待描述的类型] --> B{是联合、元组、字面量或映射吗}
  B -->|是| C[使用 type]
  B -->|否| D{需要被外部扩展或 implements 吗}
  D -->|是| E[使用 interface]
  D -->|否| F[跟随团队约定]

最后一条常被低估：团队一致性比单点最优更重要。同一目录里一半 interface、一半 type 并不算错，却会让 review 反复纠缠格式问题。可行的做法是在规范里写清边界，比如“对外暴露的类型一律 interface，内部工具类型一律 type”，再用 lint 规则兜底。约定不必完美，能被稳定执行才有价值。

小结

interface 与 type 都能描述对象形状，编译后都不存在运行时产物，日常可以互换。真正的分水岭有三条：接口能声明合并、能作为稳定契约被扩展和实现；类型别名能表达联合、元组、字面量与映射类型；扩展方式分别是 extends 与交叉类型，冲突报错的时机也不同。选型时先看类型本身要不要联合或映射，再看它要不要开放给外部扩展，两条都不满足就跟随团队约定。性能传闻可以作为避免深层交叉的提醒，但不足以成为选型依据。最重要的不是选中哪个关键字，而是让同一个项目里的选择可预测、可解释。
