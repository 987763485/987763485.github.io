TypeScript 配置 tsconfig 详解

本文属于《TypeScript 学习路线》第 10/74 篇
上一篇系列目录下一篇

几乎每个 TypeScript 项目的根目录都躺着一份 tsconfig.json，但不少人的做法是从上一个项目整份拷贝，只把 outDir 改个名字。配置能跑，却说不清每一行在做什么，遇到「找不到模块」「重复标识符」这类报错时只能靠搜索碰运气。本文按 2.6 版本的选项口径，把 compilerOptions 和文件范围字段逐项拆开，说明每个开关影响的是语法降级、类型检查还是产物形态，最后给出一份带注释的最小配置。适合已经能写 TypeScript、但还没有系统读过配置文档的读者。

tsconfig.json 的角色与查找规则

tsconfig.json 只做两件事：告诉编译器编译哪些文件，以及用什么规则编译。前者由 files、include、exclude 描述，后者全部放在 compilerOptions 里。它不参与运行时，也不会进入产物，本质是一份给 tsc 阅读的工程描述。

查找规则值得先说清楚，因为很多「配置不生效」的困惑都来自这里。在命令行直接执行 tsc 且不带输入文件时，编译器从当前工作目录开始逐级向上查找名为 tsconfig.json 的文件，使用第一个找到的；一直到根目录都没有，就报错退出。这个向上查找的行为意味着，在子目录里执行 tsc，很可能用的是上层目录的配置，而不是你以为的那一份。

四个顶层字段的分工

compilerOptions、files、include、exclude 这四者合起来只描述两件事：编译规则与文件范围。files 是一个字符串数组，逐条列出相对路径，不接受通配符，写几个就编译几个，适合入口明确的小项目或需要精确控制的场景。include 接受 glob，支持 *、? 与 **/ 三种通配，例如 src/**/*.ts 会匹配 src 下任意层级的 .ts 文件。exclude 不独立选文件，它只是在 include 的结果上做减法；如果没有写 include 也没有写 files，编译器默认把项目目录下的 **/* 全部纳入，此时 exclude 的作用尤其关键。

默认情况下，编译器已经把 node_modules、bower_components、jspm_packages 以及 outDir 指向的目录排除在外，所以简单的项目不写 exclude 也不会误伤。但 exclude 有一个边界必须记住：它只影响 include 扩出来的文件集合，不影响被 import 进来的文件。也就是说，即使某个文件被 exclude 掉，只要它被范围之内的模块引用，编译器仍然会加载并检查它。想真正把一份代码挡在编译之外，正确做法是让它不被任何纳入范围的文件引用，而不是在 exclude 里写一条规则。

target 与 lib：语法降级和类型声明是两件事

target 决定把新语法降级到哪个版本，取值有 es3、es5、es2015、es2016、es2017。它处理的是箭头函数、class、模板字符串、解构、async 函数这类写法，把它们改写成旧引擎能执行的等价代码。降级只改写法，不补能力：target 设成 es5 之后，Promise、Map、Array.prototype.includes 依然是运行环境提供的东西，编译器不会替你实现。target 的默认值是 es3，实际项目几乎都会手动改成 es5 或更高。

lib 管的是另一层：编译时认为哪些内置类型存在。它不产生代码，只提供声明。默认值跟随 target，例如 es5 对应 dom、es5、scripthost，es2015 对应 dom、es2015、scripthost。也就是说两者默认绑定，一旦手写 lib，这层绑定就断了。lib 的粒度还可以很细，例如只补一条 “es2015.promise”，而不引入整套 es2015，适合只需要 Promise 类型、不想放开全部 ES2015 API 的场景。

最常见的错搭是 target 为 es5、lib 只留 es5，代码里写了 Promise，编译器报「Promise 仅指类型，但在此处被当作值使用」。补上 es2015 就能过编译，但运行时是否真有 Promise 取决于 polyfill 与浏览器版本。反过来，target 设成 es2017 却要兼容 IE 11，则是语法降级不足，产出的 async 函数在旧浏览器里直接是语法错误。两个方向都要对齐目标环境。

module 与 moduleResolution：产物格式和查找算法

module 决定 import 与 export 在产物里变成什么。commonjs 产出 require 与 exports，给 Node 或按 CommonJS 处理的构建链使用；es2015（也可写 es6）保留 import 语句，适合产物再交给打包器做静态分析；amd 与 system 面向当年的模块加载器，新建项目很少以它们为首选。选哪个取决于产物交给谁，与代码里写的是不是 import 无关。

同一段源码在 module 为 es2015 时，import 与 export 会原样保留，交给下游处理，这也是库项目常选 es2015、应用常选 commonjs 的原因之一。

moduleResolution 是另一个维度。它不管产物长什么样，只管 import 后面那个字符串怎么找到文件，取值 node 和 classic。classic 是早期编译器的策略，只按相对路径逐层查找，不认 node_modules，新项目不该再用；node 模拟 Node 的查找过程：先看相对路径，再依次尝试 .ts、.tsx、.d.ts，遇到目录则读 package.json 的 types 或 typings 字段，没有就找 index。默认值按 module 推断，module 为 amd、system、es2015 时默认 classic，其余默认 node。既然会变，就显式写出来，别让它跟着 module 一起漂移。

还有一个常被误解的选项 allowSyntheticDefaultImports。它只是允许「对 CommonJS 模块使用默认导入」通过类型检查，不改变产物。产物里依然会去访问 require 结果的 .default，运行时有没有这个属性，取决于模块本身或打包器是否做了兼容处理。

strict 是聚合开关，不是一项检查

从 2.3 起，可以只写 “strict”: true，它等价于同时打开若干子项。按 2.6 的口径，展开后是五项：noImplicitAny、strictNullChecks、strictFunctionTypes、noImplicitThis、alwaysStrict。其中 strictFunctionTypes 是 2.6 新增的，只检查函数类型位置的参数逆变，方法声明的参数仍是双变，这是为兼容 Array 等内置接口刻意留下的缺口。alwaysStrict 让产物带上严格模式标记，noImplicitThis 要求显式交代 this 的类型，两者不改变代码意图，只是把原本隐含的假设摆到台面上。

聚合的好处是省事，麻烦在于一开全开会让存量项目一次面对成百上千条报错。所以常见做法是先 “strict”: true，再把暂时扛不住的子项单独关掉，例如 “strictNullChecks”: false。这种写法合法：strict 只是把默认值改成 true，显式写出的子项优先级更高。

如果从零开启，顺序建议是先 noImplicitAny、后 strictNullChecks。前者报错集中在参数和变量声明，补一个类型标注就能消掉，改动是局部的；后者把 null 与 undefined 纳入类型系统，几乎每一处取值和属性访问都可能需要收窄，改动面是全局的。先把隐式 any 显式化，再开空检查时至少类型信息是完整的，不会在双重报错里打转。迁移的具体手法另有专文，这里只关心选项本身。

rootDir、outDir 与意外编译

outDir 指定产物根目录，tsc 按输入文件的相对位置在它下面重建目录树。这棵树的形状由 rootDir 决定，默认取所有输入文件路径的最长公共父目录。默认值看似聪明，实际很容易翻车：只要 include 里混进一个项目根下的配置文件或 tests 目录，公共父目录就被抬到项目根，产物从 dist/index.js 变成 dist/src/index.js，引用路径全部错位。

显式写 “rootDir”: “src” 是一道护栏。编译器会检查每个输入文件是否都在这棵子树下，不在就报「文件不在 rootDir 下」。问题在编译期暴露，比部署时才发现路径错位划算得多。前提是 src 里确实只放源码，测试与脚本放在 src 之外，靠独立的配置去编译。

另一个常见现象是产物被自己再编译一遍。tsc 默认只认 .ts、.tsx、.d.ts，outDir 里的 .js 不会回头被当成源码；但一旦打开 declaration，产出的 .d.ts 就会被 include 的 **/* 重新捞进来，表现为莫名其妙的重复标识符。outDir 默认在 exclude 名单里，可如果改过 exclude 或用了多个输出目录，就得手动确认它被排除。把 outDir 放进 src 内部更是自找麻烦，源码树和产物树会互相污染。顺带一提，若不想在类型报错时仍然写出半成品，可以打开 noEmitOnError，让 tsc 在有错误时直接放弃写文件。

写法上注意两点。第一，键和值都相对 baseUrl，不要用 ../ 跳出基准目录，否则同一份配置在不同机器上可能解析出不同结果。第二，映射只影响编译期，编译器靠它找类型，但不会改写产物里的模块说明符，dist 里依然是 require(“@/utils/date”)。

这就引出最常见的「编译通过、运行报错」：Node 不认识 @ 开头的路径，打包器也不认识，除非在构建配置里再写一份 alias，或在运行时用模块别名方案做一次映射。两份配置必须同步维护，改一处忘一处就是线上事故。笔者的建议是别名能少用就少用，只在目录层级深、相对路径超过两三层时才引入。另外，把 baseUrl 设成 “.” 虽然让顶层目录都成为可解析模块，却也会干扰 rootDir 的推断，收益远小于代价。

声明、调试与全局类型

declaration 打开后，每个 .ts 都会额外产出一个同名 .d.ts，把类型信息随包发出去。做库必须开，应用一般用不上；发布时要把 .d.ts 与 .js 放在一起，并在 package.json 的 types 字段指向入口声明。它还会顺带改变 include 与产物目录的关系，上一节提到的 .d.ts 被重新纳入就是这么来的。

skipLibCheck 跳过声明文件之间的兼容性检查，只跳过 .d.ts，不跳过你写的 .ts。常见用途是绕开两个第三方包的类型冲突，或省下检查 node_modules 里大量声明的时间。代价是自己手写的全局声明也不再被检查，所以维护公共类型包的项目不要图快打开它。

sourceMap 生成 .js.map，调试时把降级后的代码映射回 .ts 的原始行。inlineSources 进一步把源码内容嵌进 map，产物不必再附带 src 目录。生产环境带不带取决于源码算不算资产：把 map 发到公开静态目录等于公开源码，可以只在错误监控平台私有上传；完全不生成则线上堆栈全是降级后的 js，排查成本很高。这是团队取舍，没有统一答案。

types 与 typeRoots 管的是哪些全局声明会被自动加载。typeRoots 默认指向 node_modules/@types 及其上层目录，types 未指定时，该目录下所有包都会进入全局作用域，依赖一多就会出现全局类型打架、编译变慢。显式写 “types”: [“node”, “jest”] 后只加载这两者，其余包仍然可以 import，只是不再自动进入全局。如果自家声明没有放在 @types 下，把 typeRoots 指向自己的声明目录即可，不必为此专门发一个包。

extends、最小配置与常见报错

extends 从 2.1 起可用，用于继承另一份配置。compilerOptions 会与基配置逐项合并，同名字段以子配置为准；include、exclude、files 则是整体覆盖，不做数组拼接。相对路径有个坑：baseUrl、outDir、include 在基配置里相对基配置所在目录解析，在子配置里相对子配置，所以公共配置应放在能覆盖所有子项目的层级。

日常遇到的配置问题，多半能归到三类。一是找不到模块：先确认 moduleResolution 是 node，再确认路径被 baseUrl 与 paths 覆盖，最后看目标包是否自带 .d.ts，没有就得自己补声明；对 CommonJS 包使用默认导入而报错，属于 allowSyntheticDefaultImports 的管辖范围。二是重复标识符：常见原因是同一文件被 files 与 include 同时纳入、@types 下装了两份同名声明的包，或 outDir 里的 .d.ts 被 include 捞了回来，用 tsc –listFiles 可以看出实际加载了哪些文件。三是产物目录混进源码：检查 outDir 是否落在 src 内、rootDir 是否显式指定、exclude 是否排掉了产物目录。

小结

tsconfig.json 的每个字段都在回答三个问题之一：编译哪些文件、按什么规则检查、产出什么形态。target 与 lib 要分开看，前者是语法降级，后者是类型声明；module 与 moduleResolution 同样要分开看，前者管产物格式，后者管模块查找。strict 是聚合开关，子项可以单独覆盖，开启顺序建议先 noImplicitAny 后 strictNullChecks。改动 paths、rootDir、outDir 时，记得同步检查打包配置与产物结构。配置本身写不出花来，但它决定了团队每天看到的报错长什么样。
