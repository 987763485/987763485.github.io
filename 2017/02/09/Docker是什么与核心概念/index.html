Docker 是什么与核心概念

本文属于《Docker 与 Kubernetes》第 1/51 篇
上一篇系列目录下一篇

同一个项目在自己机器上跑得好好的，换一台机器就报找不到依赖，这大概是每个开发者都遇到过的场面。本文面向刚接触 Docker 的读者，把镜像、容器、仓库、Dockerfile、数据与网络这几个核心概念一次讲清楚，并给出最常用的一批命令。读完你应该能独立跑起一个容器，看懂同事发来的那串 docker run，也知道哪些细节需要再去看专文。

从一个配了一天的下午说起

去年年底组里来了一位新同事，第一天让他把项目跑起来，结果配环境配了整整一天。装 Node，版本不对；装依赖，编译原生模块失败；数据库连不上，最后发现是本地端口被别的服务占了。到下班前他终于在自己的笔记本上看到了首页，第二天提交代码，持续集成又挂在一模一样的依赖问题上。

后来我们把项目打成了一个镜像。新同事只需要装好 Docker，拉下镜像，一条 docker run，十分钟后就开始写业务代码了。

「在我机器上是好的」这句话之所以成立，是因为「我的机器」里其实包含了操作系统版本、语言运行时、系统库、环境变量、目录结构这一整套东西，而这些从来没有被写进代码仓库。Docker 做的事情，就是把这套东西固化成一个可以分发、可以打标签、可以回滚的产物。它不是一门新语言，也不是一个新的虚拟化平台，而是一套把「运行环境」当成软件来交付的方法。

容器与虚拟机：共享内核的轻量隔离

容器常被拿来和虚拟机比较，因为两者要解决的问题相同：在一台物理机上隔离出多个互不干扰的运行环境。区别在于隔离发生在哪一层。

虚拟机在硬件之上跑一层 Hypervisor，每台虚拟机里都有自己完整的操作系统内核，应用跑在各自的内核上。容器不模拟硬件，它直接跑在宿主机内核上，靠内核本身的能力把进程看到的文件系统、网络、进程列表分开。由此带来四个结论。

第一，内核共享。虚拟机各自一份内核，容器共用宿主机那一份，所以 Linux 上不能直接跑 Windows 容器；Docker for Windows 当时的做法是在底下垫一层 Linux 虚拟机。

第二，启动快。虚拟机要引导内核和 init 进程，通常以几十秒计；容器本质上是启动一个被隔离的进程，一般在一秒以内。这个差别直接改变了使用习惯——虚拟机是「开一台机器」，容器是「跑一条命令」。

第三，隔离强度不同。虚拟机的边界由 Hypervisor 提供，比较硬；容器依赖内核，安全性弱一档。所以容器适合跑自己团队的服务，不适合放来路不明的多租户代码。

第四，资源开销小。虚拟机有固定的内存与磁盘配额，空转也要占着；容器按进程实际用量计，一台 8G 内存的机器上跑十几个容器是常态。

一句话概括：容器是进程级隔离，虚拟机是机器级隔离，前者轻、后者硬。具体机制本文不展开，namespace 与 cgroup 怎么配合，另有《Docker 原理：namespace 与 cgroup》一篇专门讲。

镜像：只读的分层模板

镜像是一个只读的模板，里面装着文件系统和一个默认的启动命令。可以把它想成一张安装光盘：自己不会运行，但每次「安装」都能得到一个一模一样的环境。

它并不是一个整块的压缩包，而是一层层叠出来的。Dockerfile 里每条会改动文件系统的指令产生一层，每层只记录相对上一层的差异。这样做有三个好处：拉取时只传本地缺的层，多个镜像可以共用底层，构建时能复用缓存。我们拉一个 Node 镜像时看到好几行 Downloading，其实就是一个个层在下。

层只读，所以同一个基础镜像被十个项目共用，磁盘上也只存一份。

每个镜像有两套标识。一套是仓库名加 tag，比如 node:6；另一套是内容寻址的 ID 与 digest。ID 由镜像内容算出，内容变一点，ID 就完全不同，所以千万别把它当版本号用。digest 是仓库侧的完整摘要，形如 sha256:...，比 tag 严格——tag 可以被重新推送指向别的镜像，digest 不会变。

docker images 用来列本地镜像，五列分别是名字、标签、镜像 ID、构建时间和大小。如果两个仓库名指向同一个 IMAGE ID，说明内容完全一样，只是贴了不同标签，磁盘上也只有一份。

容器：镜像的一个运行实例

容器是镜像跑起来之后的样子。同一个镜像可以起任意多个容器，各自的改动互不影响。

关键在于可写层。镜像的所有层都是只读的，容器启动时，Docker 在镜像最上面加一个很薄的可写层，所有写操作都落在这里。读文件时先看可写层，没有再往下找只读层。因此容器里改坏的东西不会污染镜像，删掉容器重开一个又是干净的。

生命周期四步对应四条命令。docker create 只创建容器、备好可写层，不启动；docker start 让它跑起来；docker stop 给主进程发信号并留十秒缓冲，超时才强杀；docker rm 删除容器和那层可写数据。日常用得最多的是 docker run，它等于 create 加 start。

docker ps 只显示正在运行的容器，加 -a 才能看到已经退出的。新手最常问的是「我明明起过，怎么没了」，多半是容器里的主进程执行完就退出了，容器自然停在 Exited 状态。排查第一步永远是 docker ps -a 看退出码，再用 docker logs 看它最后输出了什么。

仓库：镜像的集散地

仓库用来存放镜像。默认的公共仓库是 Docker Hub，官方的 node、redis、mysql 都在上面有维护得不错的镜像，拿来就能用。公司内部一般另搭一个私有仓库放业务镜像，不往公网推。

本地没有镜像时，docker run 会自动去拉；也可以显式 docker pull redis:3.2。推镜像要先 docker login，再给镜像打上带用户名或仓库域名前缀的标签，然后 push。

最需要小心的是 tag。tag 只是人贴上去的别名，本身没有任何语义约束。latest 不是「最新版本」，而是「没写 tag 时的默认值」，docker pull redis 与 docker pull redis:latest 完全等价。问题在于同一个 tag 可以被反复推送覆盖，上周拉的 node:6 与今天的可能已经不是同一份内容，线上出问题时根本对不上。所以生产环境应该用明确的版本号，必要时用 digest 固定。仓库不会拦你覆盖标签，这件事只能靠约定。

私有仓库可以买 Docker Hub 的付费服务，也可以用官方那个 registry 镜像自建。

Dockerfile：把环境写成代码

镜像是构建出来的，构建脚本就是 Dockerfile。它是一串指令，从上往下执行，每条会改动文件系统的指令生成一层。

逐条看。FROM 指定基础镜像，必须写在第一条。WORKDIR 设工作目录，后面的相对路径都以它为基准，目录不存在会自动创建。COPY 把构建上下文里的文件复制进去。RUN 在构建阶段执行命令，装依赖就靠它。EXPOSE 声明这个容器打算监听哪个端口，它只是声明，不会真的发布端口。CMD 是容器启动时的默认命令，会被 docker run 后面跟的命令整体覆盖。

ENTRYPOINT 与 CMD 容易混。ENTRYPOINT 定义「这个镜像就是干什么的」，docker run 后面的参数会追加到它后面；CMD 更像默认参数，容易被替换掉。两者可以同时出现，前者写可执行文件，后者写默认参数。

构建命令是 docker build -t myapp:1.0 .，最后那个点表示构建上下文是当前目录。上下文会整体打包传给 Docker，所以别忘了写 .dockerignore，把依赖目录和版本库目录排除掉，否则传输和解压都白花时间。

缓存在这里最值得说。每条指令执行前，Docker 会判断这一层能否复用：指令文本没变、上一层内容也没变，就直接用缓存。所以顺序很关键。先复制依赖清单再装依赖，最后才复制代码，这样改业务代码时依赖层仍然命中缓存，构建只要几秒；反过来先复制全部代码，改一行字就要重装依赖。

数据：容器删了，数据去哪了

容器那层可写层跟着容器一起生灭，docker rm 一执行就没了。把数据库文件、上传的图片放在容器层里，等于把数据放在临时目录。要持久化就得挂出来，有两种方式。

一种是 volume，由 Docker 管理，存在宿主机上专门的目录里，用名字引用：-v dbdata:/var/lib/mysql。名字第一次用时自动创建，容器删了卷还在，下次挂同一个名字数据就回来了。这是官方推荐的做法，跨平台一致。

另一种是 bind mount，直接把宿主机的一个路径挂进容器：-v /data/mysql:/var/lib/mysql。好处是文件就在你熟悉的位置，改配置、看日志都方便；坏处是依赖宿主机的目录结构和权限，换台机器路径可能根本不存在。

两种写法的区别只在冒号左边：写绝对路径是 bind mount，写名字是 volume。docker volume ls 可以看有哪些卷，注意卷的生命周期独立于容器。

网络：默认的 bridge 与端口映射

不指定网络时，容器都连在 Docker 默认创建的 bridge 网络上，各自分到一个内网地址，容器之间能互访，但宿主机之外的机器访问不到，因为端口没有暴露出来。

-p 8080:80 做的事就是转发：宿主机的 8080 转到容器的 80。冒号左边是宿主机，右边是容器，方向记反是最常见的笔误，真正让外部能访问的是 -p。

同一网络里的容器可以直接拿容器名当主机名互访，比记 IP 可靠。网络模式不止 bridge 一种，这里只讲最常用的用法，细节见《Docker 网络模式详解》。

组合：两个容器如何一起跑

一个 Web 加一个数据库，最少要三条命令：建网络、起数据库、起应用。

应用用容器名 db 连数据库，对外映射 8080。跑是跑起来了，麻烦在后面：启动顺序、重启策略、环境变量越写越长，换台机器还得把这些命令再抄一遍。命令不是文档，过一周自己都记不全。

docker-compose 做的就是把这一组 docker run 的参数写进一个 YAML 文件，用一条命令起停整组容器，配置还能提交进仓库。它的价值不在「更高级」，而在可复现。语法本文不展开。

四个常见误解

容器不是虚拟机。它不虚拟硬件、不引导内核，进去 ps 只看到一两个进程是正常的；也别在容器里用 systemd 管服务，一个容器一个主进程才是它的用法。

镜像不是备份。镜像固化的是环境与代码，不含数据，拿它当数据快照，恢复回来只会得到一个空库。

latest 不是版本号，只是默认标签，会漂移。要可追溯就用明确的版本号或 digest。

数据不要写在容器层。它会随容器删除而消失，也会让镜像之外的差异越滚越大，该挂卷就挂卷。

四条背后是同一件事：别把容器当成要长期维护的机器。它一次性、可重建，配置写进 Dockerfile，数据挂在卷上，随时可以扔掉重来。

学习路径与边界

顺序建议：先把 run 与 build 用熟，能把现有项目容器化；再理解数据与网络；最后才碰资源限制与编排。跳着学，排查时一定会卡。

本文刻意略过三块内容，各有专文：《Docker 原理：namespace 与 cgroup》讲隔离怎么实现，《Docker 网络模式详解》讲各种网络模式，《Docker 资源限制与监控》讲内存、CPU 与观测。机制层面的东西，等日常用熟了再看会顺很多。

小结：概念与命令对照

概念 一句话解释 常用命令
镜像 只读的分层模板 docker images
容器 镜像的运行实例，多一层可写层 docker run、docker ps -a
仓库 存放与分发镜像的地方 docker pull、docker push
Dockerfile 构建镜像的脚本 docker build
卷 独立于容器生命周期的数据目录 docker volume ls
网络 容器互访与对外暴露的通路 docker network create
compose 一组容器的启动清单 docker-compose up

这张表里的命令敲熟之后，容器就没那么神秘了：它只是一个被隔离起来的进程，外面包着一份可复现的文件系统。
