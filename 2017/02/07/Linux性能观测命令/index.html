Linux 性能观测命令

线上接口突然变慢，登录机器一看 CPU 不高、内存也够，于是把怀疑投向代码，改了两版却没好转。这类”资源看起来很闲、用户就是很慢”的故障，多半藏在磁盘 I/O、连接队列或者某一次阻塞调用里。本文按”先全局后局部”的顺序，把 CentOS 7（内核 3.10）与 Ubuntu 16.04（内核 4.4）上随手可用的观测命令串成一条排查路径：先判断是哪类资源出了问题，再定位到进程，最后落到系统调用与热点函数。读完之后，你应该能在几分钟内判断一台机器”慢在哪”，并且知道哪些数字不能照字面相信。

一次”CPU 不高、内存也够”的故障

事情发生在一个订单查询接口上：P99 从 80ms 涨到 1.2s，错误率没动，请求还在成功返回，只是变慢。我们先查应用日志，没有异常堆栈；再看连接池，活跃连接数正常；重启一台实例，好了十分钟又慢回去。就这样折腾了将近两个小时。

顺着这条线继续查：

%util 常年在 95% 以上，await 从正常的 2ms 涨到 120ms，w/s 并不高但单次写入极慢。也就是说磁盘并没有被大量小请求打满，而是每次写入都要等很久，典型的”设备已经饱和，但吞吐并不高”。再用 iotop -oPa 看具体进程，发现两个东西在抢盘：一个是凌晨没跑完、拖到白天的备份任务，另一个是应用自己把访问日志按请求同步刷盘。

请求线程在写日志时被阻塞，处理能力下降，新连接进不来，于是又叠加了第二个问题。ss -s 显示 TIME_WAIT 有两万多个，ss -lnt 里 8080 端口的 Recv-Q 持续非零，说明排队已经发生在内核的 accept 队列里，而不是应用内部。

最后把备份任务挪到凌晨并限速，日志改成异步落盘，调大 backlog，重启。三个动作里只有第一个是根因，后两个是缓解。这个案例值得记住的地方不在于结论，而在于三个最常看的数字全都正常：CPU 不高、内存 available 还有 6GB、磁盘空间也够。如果观测只停留在”CPU 和内存”，这类问题永远找不到。

观测方法论：USE 与先全局后局部

排查性能问题最容易犯的错，是打开 top 盯着第一行看，看到一个不高的数字就换一台机器。有效的做法是先有框架，再选命令。

USE：对每类资源问三个问题

USE 方法把系统拆成若干资源：CPU、内存、磁盘、网络接口、以及更下层的控制器与总线。对每一类资源，依次问三个问题：

  • 利用率：这段时间里资源有多忙？CPU 的 us + sy、磁盘的 %util、网络的带宽占用。
  • 饱和度：有多少工作在排队等它？CPU 的 runqueue 长度与 load、磁盘的 aqu-sz 与 await、内存的 swap 换入换出。
  • 错误：有没有出错？网卡的 errors/dropped、磁盘的 dmesg 报错与 smartctl、内存的机器检查异常。

这三个问题里，饱和度最容易被漏掉，也最能解释”资源不忙但很慢”。开头那个案例，磁盘利用率 98% 是”忙”，await 120ms 是”排队”，两者一起才构成完整的判断。只看利用率，会得出”磁盘很忙，加块盘”；加上饱和度，才知道”单次 I/O 太慢，先查是谁在同步写”。

把这张表在心里过一遍，排查时就不会东一榔头西一棒子：

资源 利用率 饱和度 错误
CPU us、sy、mpstat 单核 load、vmstat 的 r dmesg、mcelog
内存 free 的 used、available si/so、OOM 日志 dmesg、edac-util
磁盘 iostat -x 的 %util await、aqu-sz dmesg、smartctl -a
网络 sar -n DEV 的 txkB/s netstat -s 重传、ss -s ip -s link 的 errors

先全局，后局部

观测的顺序应当是从粗到细，每一步都用上一步的结论缩小范围：

  1. 全局：uptime、vmstat 1、top 看三十秒，判断是 CPU、内存、I/O 还是网络。
  2. 子系统：mpstat -P ALL、iostat -x、sar -n DEV、ss -s，定位到哪一类资源、哪个设备、哪个核。
  3. 进程：pidstat、iotop、top -H，定位到哪个进程、哪个线程。
  4. 代码：strace -c、perf top、/proc/<pid>/stack，定位到系统调用与热点函数。

反过来，一上来就 strace 某个进程，范围太窄：可能盯错了进程，也可能盯错了资源。越往下层的工具开销越大，先做便宜的观测是有实际意义的。

一次只改一个变量

这条纪律比任何命令都重要。见过太多次”重启 + 调大连接池 + 加一台机器”三件事一起做，然后问题消失了，谁也不知道是哪个起了作用，下次复发时又要从头猜。

正确的做法是：记录时间点，记下改动前的基线数字（load、await、P99），只改一项，等一个完整的观测周期（至少几分钟，覆盖一次流量波动），再对比同一组数字。如果无效，改回去，再试下一项。观测数据要和变更记录对齐，否则事后无法复盘。

还有一点：观测本身有成本。strace -c 能让被跟踪的进程慢几倍，perf record 在高频采样下也会吃掉可观 CPU，iostat 的每次采样都要读内核计数器。生产环境上，先看 /proc 里的现成计数，再考虑启用采样工具；必须用的时候，限定时间（比如 timeout 30）并挑一台不影响主流程的实例。

负载：三个数字和它们骗人的地方

uptime 输出末尾那三个数，是 1 分钟、5 分钟、15 分钟的平均负载。它们不是三次独立采样，而是内核每 5 秒读一次当前值，再用指数衰减平滑出来的：1 分钟那一项对瞬时变化最敏感，15 分钟那一项最迟钝。所以看趋势比看绝对值有用：三个数递增说明负载在爬升，递减说明在恢复；1 分钟跳高而 15 分钟还低，多半是一次备份或日志轮转。

负载和核数的关系

Linux 的 load average 统计的是”正在运行 + 等待运行”的 task 数量，粗略地说就是排队长度。它和 CPU 核数直接相关：4 核机器上 load 4 意味着每个核都恰好有一个任务，属于刚好饱和；load 8 意味着平均每个任务要等一轮才能被调度。

经验上的分档是：load / 核数 小于 0.7 算舒适，0.7 到 1.0 属于接近饱和，长期大于 1.0 就该看看是谁在排队，大于 2.0 基本可以认定有问题。但这只是起点，不是判决书——因为负载里还混进了另一类任务。

不可中断睡眠也会推高负载

Linux 的 load average 与其他 Unix 有一个重要差别：它把 TASK_UNINTERRUPTIBLE（也就是 ps 里的 D 状态）的 task 也算进去了。这类 task 不占 CPU，它在等 I/O 完成、等锁、等 NFS 响应，处于”叫不醒”的状态。

于是就会出现开头那种矛盾：CPU 空闲 60%，load 却是 9。这 9 里面可能有一大半是卡在磁盘上的进程。判断方法很直接：

如果 D 状态进程很多，且 wchan 指向文件系统或块设备相关函数，那负载的根子在 I/O，不在 CPU。此时去加 CPU 或者调大线程池都没有意义，只会让更多线程一起卡在同一个设备上。反过来，如果 D 状态很少而 r（running）很多，那才是真的算力不够。

另外，load 不区分任务权重，死循环线程和只跑几毫秒的定时任务都算 1，所以它只适合判断排队长度，不负责回答”谁在浪费 CPU”——后者要靠 pidstat。

CPU：先把”忙”拆开

top 顶部那一行 %Cpu(s)，把 CPU 时间分成了若干份。多数人只看 id（空闲），实际上其余几列才是线索：

  • us：用户态时间。高，说明应用在算，可能是热点函数、也可能是死循环。
  • sy：内核态时间。高，说明系统调用频繁、锁竞争激烈，或者在做大量内存分配与网络收发。
  • wa：等待 I/O 完成的时间。注意它是”CPU 空闲但因为有未完成的 I/O 而没有被调度去做别的事”的记账，高 wa 通常意味着磁盘或网络存储慢。
  • hi / si：硬中断与软中断。网卡流量大时 si 会明显升高。
  • st：被 hypervisor 偷走的时间。云主机上 st 高，说明宿主机上的邻居在抢 CPU，你自己的机器上找不到原因。

单核不均：mpstat -P ALL

top 默认显示的是所有核的平均值，平均值会掩盖单核打满。一个典型的 8 核机器，一个线程跑满一个核，总体 us 只有 12.5%，看起来非常闲，但那个线程所在的请求就是慢。

输出按核列出 %usr、%sys、%iowait、%soft、%idle。如果只有一个核 %usr 接近 100，其余都闲，那问题就是单线程热点，方向是查这个线程在算什么，而不是加机器。%soft 集中在某一个核，通常是网卡中断都落到了 CPU0，可以考虑 irqbalance 或调整 /proc/irq/*/smp_affinity。

按进程与线程归因

pidstat 给的是区间增量，而不是 top 那种开机以来的累计值，更适合回答”过去 5 秒谁在吃 CPU”。加 -t 展开到线程，再配合 top -H -p <pid> 拿线程 ID 对照栈，是定位单线程热点的常规路径。

vmstat：一屏看全系统

第一行是开机以来的平均值，从第二行起才是区间值，这一点后面还会说。这里关心的是 r、b、in、cs：r 是等待运行的进程数，等价于瞬时排队长度；b 是处于不可中断睡眠的进程数；in 是每秒中断次数；cs 是每秒上下文切换次数。

cs 的绝对值没有统一标准，几万很常见。要看的是它和 sy 的关系：cs 高、sy 也高，通常是锁竞争或者大量短系统调用；cs 高而 sy 不高，可能是线程数过多导致的调度抖动。用 pidstat -w 1 可以看每个进程的自愿切换（cswch/s，等 I/O 或锁）和非自愿切换（nvcswch/s，时间片用完被抢占）。非自愿切换高，说明可运行线程多于核数，减少线程数往往比加 CPU 更有效。

in 高的时候，先看 /proc/interrupts 里是哪一类中断在涨。网卡中断随流量涨是正常的；如果是某个设备的中断数异常增长，可能是硬件或驱动问题。软中断（si）高而流量并不大时，要怀疑是不是有小包攻击或者连接数异常。

把上面几列组合起来，可以得到一个粗略的判据：us 高查代码，sy 高查系统调用与锁，wa 高查磁盘，si 高查网络与中断，st 高就找云厂商。这五条不能覆盖所有情况，但能在大方向上少走弯路。

内存：别看 free，看 available

很多人看到 free 只剩 598MB 就开始紧张，这是最常见的误读之一。Linux 会把空闲内存尽量拿去做 page cache，缓存文件内容；这部分内存随时可以被回收给应用使用。所以判断”还有多少内存可用”，要看 available 这一列。

available 是内核给出的估算值：在不引起 swap 的前提下，还能分配多少内存给新进程。它大致等于 free 加上大部分可回收的 buff/cache，再减去一些不可回收的缓存与预留。

buff/cache 里其实混了两类东西：buff 是块设备的元数据缓存，通常很小；cache 是 page cache、tmpfs 与共享内存。读多的机器 cache 大是健康表现，说明热数据在内存里；真正要担心的是 available 持续走低且 swap 开始活动。

swap 与 OOM

看 si 与 so：前者是每秒从 swap 换入的页数，后者是换出。两者长期为 0，说明内存压力不大；持续为非零，说明系统已经在用磁盘当内存，此时任何应用的延迟都会抖，因为一次缺页就可能要读盘。偶发的个位数不必惊慌，内核的 kswapd 会做一些预防性回收。

swap 用满不等于立刻 OOM。OOM 触发条件是内核在直接回收之后仍然分配不到内存，此时 oom-killer 会按 oom_score 挑一个进程杀掉，通常挑占用 RSS 最大的。事后确认要看：

在 CentOS 7 上，/var/log/messages 由 rsyslog 写入，日志里会带上被杀进程的 RSS 与 oom_score_adj。被杀的是自己的服务时，先确认是流量增长、缓存无上限，还是真有泄漏，不要只想着加内存。

判断泄漏要看趋势而不是瞬时值：/proc/<pid>/status 里的 VmRSS 连续几小时单调上涨，基本可以确认；要看具体是哪段映射在涨，读 /proc/<pid>/smaps 按区间汇总 Rss。drop_caches 只在排查缓存影响时用一次，不要写成定时任务，清完之后系统要重新预热，短时间会更慢。

磁盘：%util 只是入场券

磁盘是”资源不忙但很慢”最常见的发源地，因为它的延迟单位是毫秒，而 CPU 是纳秒。iostat 属于 sysstat 包，CentOS 7 与 Ubuntu 16.04 都预装或一条命令可装。

几个字段的含义需要说清楚：

  • r/s、w/s：每秒的读、写请求数，也就是 IOPS。
  • await：每个请求的平均耗时，单位毫秒，包含排队时间。
  • aqu-sz：平均队列长度，队列越长说明排队越严重。
  • %util：设备处于忙碌状态的时间比例。

关键在于把 await 和 r/s、w/s 一起看。w/s 不高但 await 很高，说明每次写入本身很慢，可能是机械盘寻道、RAID 卡电池失效导致写缓存被关闭、或者底层存储限速。w/s 很高且 await 也高，说明队列堆积，属于吞吐打满。这两种情况的处理方式完全不同：前者要查设备与链路，后者要考虑拆分流或换介质。

%util 要谨慎对待。对单块机械盘，接近 100% 基本等于饱和；但对 SSD、RAID 阵列、SAN 卷，设备可以并行处理多个请求，%util 到 100% 并不代表没有余量。这时候 await 与 aqu-sz 比 %util 更可信。反过来，某些虚拟化环境下 %util 的计算方式并不可靠，只能当参考。

找到写盘的进程

-o 只显示有实际 I/O 的进程，-P 按进程聚合（默认按线程），-a 显示累计而非瞬时速率。iotop 需要 root，且在 3.10 内核上依赖内核的 task I/O 统计，能用但自身有一定开销，不要长期挂着。

如果 iotop 不可用，pidstat -d 1 也能给出每个进程的 kB_rd/s 与 kB_wr/s，更轻量。再往下，/proc/<pid>/io 里的 read_bytes 与 write_bytes 是累计值，两次采样相减就是区间内的真实磁盘 I/O，比 rchar、wchar（包含缓存命中）更准确。

空间层面，df -h 看容量，df -i 看 inode 使用率。inode 耗尽的原理与处理另有专文讨论，这里只需要记住：磁盘还有空间但写不进去，先看 df -i，报错通常是 “No space left on device”，但 df -h 显示还有很多空余。

最后是”到底哪个文件在写”。lsof -p <pid> 能列出进程打开的文件，按 REG 过滤即可；lsof +D 在大目录上非常慢，不适合生产，先用 iotop 定位进程更实际。

网络：连接状态比带宽更常出问题

多数”接口慢”的网络问题并不在带宽，而在连接数、队列和重传。ss 来自 iproute2，CentOS 7 与 Ubuntu 16.04 默认安装，比 netstat 快得多，因为后者要遍历 /proc/net/tcp 的全部内容。

这行汇总已经能说明很多问题。estab 是当前建立的连接，timewait 是处于 TIME_WAIT 的连接数。TIME_WAIT 由主动关闭的一方产生，持续 2 倍 MSL（Linux 上约 60 秒），用来保证最后一个 ACK 能重传、并让旧连接的延迟报文消散。它是正常状态，不是泄漏。但数量长期维持在几万，会占满本地端口，客户端尤其容易撞上”Cannot assign requested address”。

处理方式要分角色：如果是客户端（比如反向代理连后端），net.ipv4.tcp_tw_reuse=1 可以让新连接复用处于 TIME_WAIT 的端口，这是有效的；服务端被动关闭时，TIME_WAIT 堆在服务端并不影响新连接，不必处理。tcp_max_tw_buckets 限制总数只是掩盖问题。至于 tcp_tw_recycle，它在 NAT 环境下会误丢连接，不要在 2017 年的生产环境里打开它，后来的内核版本已经把它移除了。

比 TIME_WAIT 更值得警惕的是 CLOSE_WAIT。它表示对方已经关闭、本端还没调用 close()，数量持续增长基本等于应用有连接泄漏：

监听队列与 backlog

在 LISTEN 状态下，Recv-Q 是当前已经完成三次握手、等待应用 accept() 的连接数，Send-Q 是 backlog 上限。Recv-Q 持续接近 Send-Q，说明应用接受连接的速度跟不上，新连接会在内核里排队甚至被丢弃；此时 netstat -s 里的 “listen queue of a socket overflowed” 会增加。调大 somaxconn 与应用的 backlog 只能缓解，根子还是应用处理不过来。

非 LISTEN 状态下，Recv-Q 表示已收到但应用还没读走的字节数，这个值长期很大，说明读得慢。

带宽、丢包与重传

rxkB/s、txkB/s 与网卡标称带宽对比，能判断是否打满。千兆网卡实测跑到 110MB/s 左右就到顶了。但更多时候带宽只用了三成，延迟却很高，这时要看重传：

netstat -s 里的 segments retransmitted 与总数相除就是重传率，超过 1% 就值得查链路。ss -tin 可以看单条连接的 rtt、cwnd、retrans，适合确认”是不是某几条连接在拖后腿”。物理层丢包用 ip -s link 看 errors 与 dropped，网卡队列丢包用 ethtool -S eth0 看 discard 计数。

进程与文件：从系统落到具体对象

定位到某个进程之后，还需要回答三个问题：它打开了什么、它在等什么、它把时间花在哪些系统调用上。

端口与文件句柄

lsof 输出很长，按类型过滤更有用：REG 是普通文件，IPv4/IPv6 是套接字，DIR 是目录。当应用报 “Too many open files” 时，先确认是句柄泄漏还是上限太小：

前者看 Max open files 的软硬限制，后者看实际用量。数量接近上限且持续增长，是泄漏；没接近上限却报错，可能是 fs.file-max 或者 systemd 单元里的 LimitNOFILE 没生效——CentOS 7 用 systemd 管理服务，/etc/security/limits.conf 对这类进程不一定生效，这一点常被忽略。

/proc 里的现成信息

/proc/<pid>/status 是最便宜的信息源，不需要任何额外工具：

State 是进程状态，VmRSS 是实际占用的物理内存，VmSwap 是被换出的部分，Threads 是线程数，两个 ctxt_switches 是自愿与非自愿上下文切换的累计值。两次读取相减，就能算出这个进程的切换频率。Threads 异常增长往往意味着线程池没有上限，或者每次请求都新建线程。

strace 的适用边界

strace -c 按系统调用聚合次数与耗时，是回答”它在等什么”的快捷方式：

-c 输出统计表，-f 跟随所有线程，-p 附加到已有进程。典型的读法：futex 占比高说明锁竞争；大量 read 每次只读几百字节说明有小 I/O；epoll_wait 占比高而 CPU 不忙，说明在等事件，瓶颈在别处。

但它有明确的边界。strace 基于 ptrace，每次系统调用都要停下来通知跟踪进程，等于加了两趟上下文切换。在高并发服务上，附加 strace 可能让延迟翻几倍，甚至把服务拖垮。所以只在低流量实例或短时间窗口内使用，必须带 timeout，不要拿它做长期监控，也不要同时对多个进程 strace。需要长期、低开销的观测时，应该换 perf 或者应用自身的埋点。

追踪：perf 与火焰图

strace 只能看到系统调用的边界，看不到用户态内部在算什么。要回答”CPU 到底花在哪个函数上”，需要采样型 profiler。2017 年初在 Linux 上的标准答案是 perf，它利用内核的 perf_events 子系统，按固定频率采样调用栈，开销远低于 ptrace。

perf top 是实时视图，适合快速看一眼；perf record 把样本写进 perf.data，再用 perf report 交互式浏览。-F 99 表示每秒采样 99 次，取 99 而不是 100 是为了避开定时器与采样频率共振导致的偏差；-g 记录调用栈。

火焰图是把 perf report 的文本变成一张更容易读的图。当年的工具链是 Brendan Gregg 的 FlameGraph 脚本：

读法有三条：横轴是采样占比，不是时间顺序，条越宽表示该函数占用的 CPU 越多；纵轴是调用栈深度，下面是调用者，上面是被调用者；找自己代码里最宽的条，而不是最顶上的条。最顶上往往是 libc 的 memcpy 或者内核的 schedule，真正有意义的是它的父节点——是你的哪段代码调用了它。如果一条宽条下面挂着 syscall，说明时间花在内核；如果挂在 futex，说明在等锁。

perf 在生产上最常见的障碍是权限与符号。/proc/sys/kernel/perf_event_paranoid 默认是 2，普通用户只能观测自己的进程，且看不到内核态样本；要分析内核热点需要 root 或把它调到 0 以下。看内核符号还需要装 kernel-debuginfo（CentOS）或 linux-image-*-dbgsym（Ubuntu），否则一堆 [unknown]。Java 这类 JIT 语言还要额外生成符号映射，否则栈里只有地址。

需要说明的是，这些年在内核追踪上出现了新工具，但 2017 年初还未进入发行版，属于后来才有的方向；当下把 perf 用熟已经足够覆盖绝大多数 CPU 热点问题。

组合套路：三条常用路径

单个命令只能回答一个问题，真正省时间的是把命令按固定顺序串起来。下面三条路径覆盖了日常大部分场景。

一分钟快速体检

这套顺序的逻辑是：先看负载趋势与内核有没有报错，再用 vmstat 判断大类，然后分别用 mpstat、pidstat、iostat、sar 确认 CPU、进程、磁盘、网络，最后用 ss -s 看连接总量。全部跑完不超过一分钟，每条都只看区间值。它不能替代深入分析，但能第一时间排除大部分方向。

数据库慢查询时的观测顺序

遇到”数据库慢”，不要第一反应就去翻慢查询日志。正确的顺序是自下而上：先用 iostat -x 确认数据盘是否饱和、await 是否升高；用 vmstat 确认有没有 swap 活动；用 top 看 mysqld 的 us 与 sy 比例；用 ss -s 看连接数是否暴涨。主机层没问题，再进实例层看 SHOW PROCESSLIST 与慢查询日志，最后才是单条 SQL 的执行计划。

这个顺序能避免一类常见误判：SQL 本身没变慢，是磁盘被备份任务拖慢了，此时优化 SQL 毫无意义。反过来，如果主机层一切正常而 mysqld 的 us 很高、慢查询里出现了新的全表扫描，那才是 SQL 的问题。

容器宿主机上的观测差异

容器内跑 free、top、iostat，读到的往往是宿主机的数据：/proc/meminfo、/proc/stat、/proc/loadavg 都没有做命名空间隔离。于是容器里 free 显示整机 64GB 内存，nproc 显示宿主机的 32 核，但进程实际只能用 cgroup 限额里的那部分。看到”内存很充裕”却频繁 OOM，或者”CPU 很闲”却延迟很高，多半就是被限额卡住了。

此时要去看 cgroup 自己的计数器：CPU 被限流看 cpu.stat 里的 nr_throttled 与 throttled_time，内存看 memory.stat 与 memory.failcnt。具体的 cgroup 参数与 Docker 资源限制配置另有专文，这里只强调一点：在容器里做性能观测，先确认你看到的是谁的数。宿主机上的 iostat 也是同理，它看到的是整块盘，不区分是哪个容器写的。

采样与记录：别只看当下

前面所有命令都有一个共同缺陷：它们只描述”你盯着屏幕的这一分钟”。故障往往在你登录之前就发生过，或者在你离开之后才复发。

sysstat 包默认带一个 cron 任务，每 10 分钟把所有指标写进 /var/log/sa/saDD，保留一周左右：

事后回看某个时间段的 CPU、内存、磁盘、网络，比现场猜可靠得多；需要更细粒度就调 /etc/cron.d/sysstat。nmon 适合交互式看，也能按秒记录成文件再用 nmon -f 的分析脚本出图。再往上，就把 load、await、si/so、TIME_WAIT 数这些关键指标定期送进监控系统（当年常见的是 Zabbix 或 StatsD 加 Graphite），让趋势和告警替你值守。

常见误读

  • top 的 %CPU 可以超过 100。它是按单核计的，一个四线程进程跑满四个核会显示 400%，不代表异常。
  • free 里的 buff/cache 不是被吃掉的内存，它可回收，判断依据是 available。
  • iostat 第一次报告不可信，那是开机以来的平均值；加 -y 跳过，或从第二行开始读。
  • vmstat 第一行同样是平均值，区间值从第二行起。

小结

性能观测的难点不在命令，而在顺序与判断。先用 USE 把资源分成利用率、饱和度、错误三个维度，按”全局—子系统—进程—代码”逐层缩小范围，并且一次只改一个变量。看到 CPU 不高、内存也够却很慢时，优先怀疑 wa、await、D 状态与连接队列。所有命令的数字都有口径，%CPU、buff/cache、iostat 与 vmstat 的首行都需要换算或跳过。最后，把这些指标持续记录下来，故障结束后还能回看，才算真正把观测做完整。
