TypeScript 高级类型：交叉与联合

本文属于《TypeScript 学习路线》第 5/74 篇
上一篇系列目录下一篇

接口返回的数据有四种形状，为了省事，我们把它写成一个”所有字段都可选”的大接口，结果调用处到处判空。本文从这个常见场景出发，讲清联合类型与交叉类型各自的语义、类型收窄的几种写法、可辨识联合的穷尽检查，以及两者组合时的分配规则与常见误用。文章基于 2017 年初的 TypeScript 2.1 / 2.2，示例可以直接放进开启 --strictNullChecks 的项目里编译。

第一，类型没有表达互斥关系。text 与 value 不可能同时存在，类型系统却认为它们可以任意组合，非法数据也能顺利赋值。第二，调用处被判空淹没。想读文本得先写 if (item.text)，想把数字格式化得先确认 value 不是 undefined；这些判断在运行时从不失败，却污染了每个调用点。第三，写入方向失去检查，构造对象时漏字段不会有任何提示。

问题的根源是一个类型承担了四种含义。正确的做法是先把四种形状分别描述出来，再用类型运算把它们组合成”其中之一”。这正是联合与交叉要解决的问题：联合描述”或”，交叉描述”与”。

联合类型用竖线连接若干成员，写法是 A | B。它的语义是：这个位置的值属于其中至少一个成员，而不是同时属于全部。先把四种形状拆开：

如果多个成员有同名字段但类型不同，读到的类型是这些类型的联合：一个成员把 extra 声明成 string，另一个声明成 number，item.extra 就是 string | number，仍需收窄。

要让联合真正好用，必须能”从联合走到具体成员”，这就是类型收窄。下一节先看交叉类型，再回头讨论收窄的各种手段。

交叉类型：同时满足

交叉类型用 & 连接，A & B 表示这个值既要满足 A，也要满足 B。对于对象类型，结果就是把两边的成员合并成一个更”厚”的类型：

类型收窄：让编译器跟着分支走

联合类型的值是其中之一，编译器默认只知道公共部分。收窄（narrowing）指的是在某个分支里，编译器根据运行时检查把类型缩小到具体成员。TypeScript 支持几种固定的收窄方式，各有适用范围。

typeof 适合原始类型。它在 if 分支里把联合拆成若干段，string、number、boolean、function、undefined、object 都能识别。有一个老问题：typeof null 的结果是 'object'，因此 typeof x === 'object' 并不排除 null，仍要单独判一次。

instanceof 适合类实例，收窄依据是原型链。它在同一个运行环境里可靠，但如果对象来自另一个 iframe 或另一份类定义副本，instanceof 会返回 false，此时应改用结构化判断。

in 用来检查某个属性是否存在。需要说明的是，本文写作时的 2.2 版本还不会因为 in 检查自动收窄类型，只能把它包进自定义守卫；自动收窄是后来的版本才补上的能力（2.7，2018 年）。字面量相等判断则直接有效，item.kind === 'text' 之后，item 就被收窄为 TextItem，这也是下一节可辨识联合的基础。

可辨识联合：用一个字段区分

四个成员都带一个 kind 字段，取值分别是 'text'、'number'、'date'、'image'，这种每个成员都有一个取值互不重叠的字面量字段的联合，叫做可辨识联合（discriminated union）。这个字段就是判别式，编译器靠它在 switch 或 if 里把联合拆开。

有一个容易踩空的细节：default 里直接写 return item 不会报错，因为 never 可以赋给任何类型。必须借助一个形参类型为 never 的函数，才能把”这里不该有值”变成错误。判别式字段也必须真的是字面量类型；写成 kind: string 时 switch 无法收窄，整个机制失效。

联合与交叉的组合

两种类型运算可以嵌套，但有一处语法陷阱：& 的优先级高于 |，所以 A | B & C 会被解析成 A | (B & C)，而不是 (A | B) & C。写组合类型时括号必须显式加上，和表达式里的位运算一样容易记错。

语义上，(A | B) & C 满足分配律，等价于 (A & C) | (B & C)：先从 A 和 B 里选一个形状，再把 C 的字段叠上去。用它写表单字段很自然，名称、标签、是否必填抽成公共部分，差异部分各自定义。

好处是公共字段只声明一次，将来加 hint 或 disabled 只改 FieldMeta 一处。要提醒的是，这个版本对 (A | B) & C 做判别式收窄有时不如展开成 (A & C) | (B & C) 稳定；某个分支没收窄时，先按分配律改写一遍。

联合参数加收窄则简单得多：一个签名，函数体里用 typeof、in 或判别式分开处理，短板是返回类型只能写成联合。取舍很直接：返回类型要随入参精确变化就用重载，否则用联合参数加收窄。另外重载按声明顺序匹配第一个可接受的签名，顺序写反会被更宽的签名抢走调用。

判断空值时，item.title === undefined 本身就是一个收窄动作，if 块里的 item.title 会变成 string。要注意 ? 在 strictNullChecks 关闭时只是”可以省略”，读出来的类型仍是 string，判空完全靠自觉。--strictNullChecks 的完整影响另有专文，本文只关心它与联合的交界。

字面量类型：现在只能手写联合

可辨识联合依赖字面量类型，而 2017 年初还没有 as const（那是 2019 年的 TypeScript 3.4 才加入的，写这篇文章时并不存在）。当年能得到字面量类型的手段只有三种：在类型位置直接写字面量、给接口字段标注字面量、依赖 const 声明的字面量推断。

最后一条最容易出问题。const 变量得到字面量类型，但对象属性和数组元素会被放宽：const notice = { level: 'warn' } 里 level 是 string，const levels = ['info', 'warn'] 是 string[]，传给需要 Level 的位置就会报错。当年的解法是显式标注 const levels: Level[] = ['info', 'warn']，或对单个值断言 'warn' as Level；as const 要等到 2019 年的 3.4 才有，这里用不上。也要注意别把断言当校验，'debug' as Level 照样能通过编译，运行时却是一个不存在的取值。

几个容易写错的地方

把联合当成交叉。 最常见的误判是以为 A | B 之后两边字段都能用。联合只能读公共字段，交叉才能同时具备两边的字段。判断口诀是：| 是”或”，值属于其一；& 是”与”，值同时满足。

Object.assign 的返回类型。 它是交叉，不是联合。Object.assign({}, a, b) 的返回类型是 A & B，看起来正好是”字段合并”。但同名字段类型不同时交叉结果是 never，运行时却是后一个对象直接覆盖前一个，两者并不一致。合并配置对象时最好让同名字段类型保持一致。

数组的两种写法差别很大。 (A | B)[] 是混合数组，同一个数组里可以既有 A 又有 B；A[] | B[] 是整个数组只能是同一种。写列表渲染时前者才是想要的，后者会让 push 处处报错。反过来，如果一个函数返回 A[] | B[]，调用方拿到后连 map 都不好写，通常应该改成 (A | B)[]。

类型断言滥用。 item as TextItem 只让编译器闭嘴，不做运行时检查，也不做数据转换。联合被”压”成某个成员后，判别式收窄和穷尽检查都失效，漏掉的分支重新变成运行时错误。断言报”类型不完全重叠”时，说明两个类型确实对不上，应该回头检查数据流，而不是补 as any 绕过去；需要窄化就写守卫函数，把判断留在运行时。

与泛型约束配合

T extends A | B 把泛型参数约束为两个成员之一。这里的 extends 是”可赋值”的意思，不是类继承。泛型的好处是保留具体类型，函数原样返回 T，调用方拿到的仍是那个具体成员，而不是联合。

要注意泛型参数不会因为约束是联合就自动收窄，在 T extends Item 的函数体里读 item.text 依然报错，必须先用守卫收窄成 TextItem。实践中更有用的是结构式约束，比如上面只要求有 id，既能读公共字段，又不限制传入哪个成员。keyof T 得到的是键组成的联合，与本文的联合正好搭档，它另有专文，这里只提一句。

小结

联合描述”或”，交叉描述”与”，收窄是从联合回到具体成员的唯一安全通道，可辨识联合配合 never 能把遗漏的分支变成编译错误。写业务类型时，先用字面量字段做判别式，公共字段用交叉叠加，函数返回类型需要跟着入参精确变化时再考虑重载。类型断言只用于确有把握的场景，不要拿它替代守卫。

写法 语义 常见误用
A | B 值为其中之一 直接访问成员特有字段
A & B 同时满足，字段合并 同名字段冲突得到 never 却以为能合并
(A | B) & C 分配为 (A & C) | (B & C) 漏括号，被解析成 A | (B & C)
x is T 自定义收窄 守卫实现写错，编译器发现不了
判别式加 never 穷尽检查 判别式写成 string，收窄失效
a?: T 键可以省略 与 a: T | undefined 混用，丢失语义差别
(A | B)[] 混合数组 误写成 A[] | B[]
