Go 命令行工具开发

本文属于《Go 语言与工程》第 14/78 篇
上一篇系列目录下一篇

我们组的发布流程一直挂在一个 shell 脚本上：拉代码、跑测试、编译前端、把产物传到两台机器、重启进程。最初只有五个参数，半年后变成十七个，getopts 的 case 分支排了四十多行，中间还夹着三段用 sed 改配置文件的逻辑。谁要动它，都得先在本地试三遍，因为脚本没有类型也没有测试，参数拼错时它不会报错，只会安静地跑完，然后在服务器上炸掉。

真正让人下决心换掉它的是两件事。一是我们需要在 macOS 上交叉编译出 Linux 的二进制，脚本里判断平台的那一段已经没人敢改；二是同事想把这套流程接进内部调度系统，需要的是一个能返回明确退出码、能输出机器可读结果的命令，而不是一堆 echo。

选 Go 的理由很朴素：单文件二进制、标准库够用、交叉编译一条命令。2017 年 2 月，Go 1.8 刚发布（2 月 16 日），http.Server 的优雅关闭等新特性我们用不上，但这个版本的编译速度和工具链稳定性让人放心。命令行工具真正需要的参数解析、目录遍历、子进程调用、日志，标准库全都给了，一行第三方依赖都不用引。

本文以一个发布工具 rel 为例，把从参数解析到交叉编译、测试、发布的整条路走一遍，适合已经能读懂 Go 基本语法、准备把手上脚本换成二进制的读者。

参数解析：os.Args 与 flag

os.Args 是程序启动时拿到的原始参数切片，os.Args[0] 是程序自身的路径，其余按用户输入原样排列。它的好处是零成本，坏处同样明显：没有类型、没有默认值、不区分长短选项，-env prod 和 -env=prod 要自己兼容，写错顺序也没人拦。参数超过五个以后，手写解析的代码会比业务逻辑还长。

标准库的 flag 包解决了绝大部分问题。用法是先注册、后解析，注册时给出名称、默认值和一句说明：

字符串、布尔、整数分别对应 flag.String、flag.Bool、flag.Int，另外还有 flag.Duration，在写超时参数时比整数加单位注释更清楚。注册顺序不影响解析，取到的都是指针，所以在 Parse 之后再解引用才是用户真正传入的值。

-h 和 --help 不需要自己实现。flag 在遇到未定义的 -h 时会打印全部已注册参数及其说明，然后以退出码 2 结束，这份输出就是最省事的文档。想自定义格式可以覆盖 flag.Usage，但多数内部工具没必要。

位置参数用 flag.Args() 取。flag 的规则是遇到第一个不以短横线开头的参数就停止解析，后面的全部算位置参数，因此 rel -env prod deploy api 里 -env 生效，而 deploy、api 落在 Args() 中；反过来写成 rel deploy -env prod，-env 只会被当成普通字符串。这个细节要在帮助信息里写清楚，否则调用方一定会踩。

布尔参数有个小坑：-dry-run 表示真，关闭要写 -dry-run=false，不能写成 -dry-run false，因为后者会把 false 当成位置参数。

子命令：手写就够了

发布工具最后长成 rel deploy、rel rollback、rel status 三个子命令。实现它不需要任何框架：先看参数个数，取出 os.Args[1] 做 switch，每个分支建一个独立的 flag.FlagSet，再解析剩下的参数。

FlagSet 用 flag.NewFlagSet("deploy", flag.ExitOnError) 创建，注册方式与全局 flag 完全一样，好处是各子命令的参数互不干扰，-h 也只列自己那几条。解析失败时让它直接退出即可，内部工具没必要为错误的命令行做恢复。

退出码的约定值得单独说：0 表示成功，1 表示业务失败（测试没过、目标机器无响应），2 表示用法错误（参数缺失或取值非法）。这套约定与 flag 的默认行为一致，接进调度系统后，上游只看退出码就能区分”值得重试”和”先把参数改对”。

三条流各司其职

Unix 的老规矩是三块流分开：stdin 进、stdout 出结果、stderr 出诊断。Go 里对应 os.Stdin、os.Stdout、os.Stderr，而 fmt.Println 写的是 stdout。这个分工在库里看着像教条，做成命令之后立刻见效：同事要 rel status | grep api，CI 里有人把 stdout 重定向到文件归档，只要诊断信息走 stderr，管道和重定向都不会被污染。

工具要能读列表，就该支持 rel deploy --from - 从标准输入取机器清单，上游可以直接 cat 管道进来。逐行处理用 bufio.Scanner，它按行切分，内存占用与总行数无关：

形参写成 io.Reader 而不是 *os.File，测试时换成 strings.NewReader 就能跑，不必造临时文件。Scanner 的单行上限默认 64KB，超长行会返回 bufio.ErrTooLong，用它读日志这类输入时要留意，必要时用 sc.Buffer 放大。

文件与目录：先问存在性

发布工具要做的事很琐碎：把 dist 下的文件全部找出来上传、检查版本标记文件是否已存在、在临时目录里拼装待传的压缩包。

遍历目录用 filepath.Walk，回调里既能做剪枝，也能统一处理错误：

单点判断用 os.Stat。麻烦之处在于文件不存在时它同样返回 error，于是每处调用都要补一句 os.IsNotExist(err)，漏写就会把”首次发布”判成故障。笔者的做法是把它收进一个小函数，让返回值明确区分”不存在””存在但不是普通文件””真的出错了”三种情况，调用方不必再关心 errno 细节。顺带说一句，这个年代还没有统一的错误包裹判断，判断错误类型只能靠 os.IsNotExist、os.IsPermission 这类辅助函数，别指望用类型断言包打天下。

临时文件用 ioutil.TempFile("", "rel-")，它返回已打开的文件与完整路径，用完 defer os.Remove(name) 配合 Close。开发机上尤其需要它：十几次试跑留下的半成品文件，比 bug 更难清理。

调用外部命令：别拼 shell 字符串

有些步骤不值得用 Go 重写，比如 rsync、tar、ssh。os/exec 的 Command 接受命令名和参数切片，关键在于不要把整行拼成一个字符串交给 sh -c：

切片形式的参数会被直接交给 execve，没有引号解析、没有变量展开、没有分号与反引号，即使 host 被写坏，也只是一个奇怪的主机名，而不是一条命令。

只关心成败时用 Run()，要拿输出用 Output()。两者返回的错误都带着退出状态，需要具体码值时再看 cmd.ProcessState.ExitCode()。stderr 默认被丢弃，而排查失败最需要的恰恰是它，所以要么设 cmd.Stderr = os.Stderr 直接透传给用户，要么收进缓冲区随错误一起返回：

需要注意 Output() 在失败且未设置 Stderr 时，*exec.ExitError 里只保留了一部分输出，缓冲区的写法更稳妥。

配置的三个来源

rel 的配置来自三处：命令行参数、环境变量、配置文件。优先级固定为参数高于环境变量、环境变量高于文件，理由是表达方式越”临时”优先级越高：临时改一次用参数，某台机器长期固定的用环境变量，团队默认值写进文件。

判断某个参数是否被显式设置，用 fs.Visit 收集已赋值的名称，比拿当前值和默认值比较可靠，因为用户完全可能传入一个恰好等于默认值的参数，而这两种情况的语义并不相同。

配置文件就选最朴素的格式：一行一个 key=value，用 bufio.Scanner 读完塞进 map，几十行代码足够。这个场景不需要 TOML、YAML，也不需要 viper 那类库。它们解决的是多格式、远程配置、热加载之类的问题，在内部工具里一个都不存在，引进来只会多一层要跟着升级的依赖。等到子命令树复杂到需要统一注册、配置需要按目录层级合并时，再去考虑 cobra 与 viper 也不迟。

日志用标准库 log 就够，要做的是给它一个前缀和一个明确的输出目标：

log.Fatal 与 log.Fatalf 内部是 os.Exit(1)，不会执行任何 defer。用到临时文件清理、连接关闭的地方应改成返回错误，由 main 统一退出，否则临时目录会慢慢堆满。

长任务的进度输出有三个讲究。其一必须写 stderr，rel deploy | tee 时进度条混进产物会让人很难受。其二非交互环境不要用 \r 刷新的进度条，CI 日志里它会变成一长串相互覆盖的字符，加一个 --no-progress 开关最省事。其三要节流，几千个文件逐个打一行会明显拖慢速度，按百分比或每 N 个打一次更实际：

GOOS 与 GOARCH 两个环境变量决定目标平台，不用装虚拟机，也不需要额外的交叉工具链。给 Linux 服务器和 macOS 各出一个二进制，就是两行命令：

这个年代的目录结构还是老三样：bin、pkg、src，所有代码必须放在 $GOPATH/src 之下，导入路径就是它在 src 里的相对路径。副作用是项目不能随手放在桌面上编译，否则 import 路径会变成 _/Users/... 这种无法解析的形式。团队通常约定仓库名与导入路径一致，比如 github.com/example/rel，本地用软链接或者干脆把工作目录设成 $GOPATH/src/github.com/example。

纯 Go 的项目交叉编译几乎不会失败；一旦用到 cgo（例如链 SQLite），就要显式写 CGO_ENABLED=0，否则 Go 会去找目标平台的 C 编译器然后报错。依赖管理此时还是 dep、glide 这类工具，vendor 目录会把依赖一起放进仓库，倒让编译环境更容易复现。macOS 上产出的二进制不带签名，发给同事时对方可能要右键打开一次，这是系统的事，与构建无关。

测试与发布

命令行工具最容易写成一坨 main，一旦如此就没法测。笔者的做法是把 main 压到几十行，只负责解析参数、组装 Options 结构体、调用 run(opts)，所有判断逻辑放进普通函数，输入输出都通过参数传入。

表驱动在 Go 里是惯例，t.Run 让每个用例单独出现在 go test -v 的输出里，失败时不必猜是哪一行。这里的经验是：凡是要”造一个环境”才能测的逻辑，多半是函数边界划错了，先改结构再补测试。

小结

把脚本换成 Go，收益不在语言本身，而在于每一步都有了明确的边界：参数交给 flag 解析，退出码有约定，诊断信息走 stderr，外部命令以切片传参，核心判断是可以单独测试的纯函数。代价是要多写一些样板代码，但这些代码写一次就能一直用，而且下次做别的工具时可以直接照搬。

回头看，这个工具不到八百行，却替掉了那个谁都不敢动的脚本。如果重做一遍，笔者会把顺序调成：先划函数边界和错误约定，再写 main，最后补交叉编译、测试与 Makefile。工具类项目的复杂度几乎都堆在边界上，语法从来不是问题。真正要花时间的是想清楚”失败时调用方该看到什么”，这一条想明白了，剩下的都是查标准库文档的活。
