LoRA 低秩适配微调

手上有一份几百条的领域数据，想让开源大模型学会自己的说话方式，最直接的做法是全参数微调。但脚本一跑起来，往往第一步就卡在显存上：一张 24 GB 的卡连 7B 模型的训练状态都放不下，更不用说为每个任务各存一份完整权重。本文介绍 LoRA 这种低秩适配方法，说明它为什么能用极少的可训练参数逼近全量微调，并给出基于 transformers 与 PEFT 的流程、显存估算与评估思路。读完可以动手在单卡上完成一次小规模指令微调。

全参数微调的成本压力

要理解 LoRA 的价值，先要算清楚全参数微调到底贵在哪里。假设基座是一个 70 亿参数的模型，用混合精度训练。权重按 16 位存储约占 14 GB，但训练时还需要梯度（同尺寸，14 GB）、Adam 的一阶与二阶动量（通常按 32 位存，各 28 GB），再加上前向过程中保存的激活值。加起来轻松超过 80 GB，单张消费级显卡根本放不下，只能上多卡或 ZeRO 之类的切分方案。这还只是“跑得起来”的门槛，没有算调参时反复试错的成本。

第二笔开销在存储与部署。全参数微调产出的权重与基座同样大小。若手上有十个业务场景，就要存十份 14 GB 的模型，还要各自准备推理服务与版本记录。很多团队的模型仓库比代码仓库大两个数量级，回滚一次要重新拉几十 GB。

第三笔开销在灾难性遗忘。全量更新会一并改写基座学到的通用能力，领域数据只有几百条时，模型很容易“学会了格式、丢掉了常识”。要缓解就得混入通用数据、调低学习率、加正则，工程复杂度迅速上升。

于是问题变成：能不能只更新一小部分参数，让训练状态和产出文件都小下来，同时不明显损失效果？LoRA 的答案是把更新限制在一个低秩子空间里。此前的 Adapter 层在层间插入小模块，也能接近全量微调，代价是推理多了一串串行计算；LoRA 把增量直接加在原矩阵上，推理时可以合并回去，不引入额外层。

低秩假设：把增量写成两个小矩阵

LoRA 的核心假设是：模型针对某个下游任务所做的调整，不需要占满整个参数空间，它可以被一个低秩矩阵很好地近似。形式化地，对一个预训练权重矩阵 W（形状为 d×k），全参数微调学的是一个同尺寸的增量 ΔW；LoRA 则令 ΔW = B·A，其中 A 是 r×k，B 是 d×r，且秩 r 远小于 d 与 k。训练时 W 被冻结，只更新 A 与 B，前向计算变为：

h = W·x + (alpha / r)·B·A·x

可训练参数量从 d×k 降到 r×(d+k)。以 d = k = 4096、r = 8 为例，原矩阵约 1678 万参数，而 A 与 B 合计约 6.5 万，只有原来的 0.4% 左右。秩越低，压缩越狠，表达能力也越受限。

两个实现细节值得注意。其一是初始化：A 用随机高斯初始化，B 全零，这样训练开始时 ΔW 恰好为零，模型行为与基座一致，不会打乱预训练表示。其二是缩放因子 alpha / r：它让调整量的大小与秩解耦，换 r 时不必大幅重调学习率。很多实现里 alpha 取 r 的两倍，是常见的经验起点，并非硬性规定。

需要强调，“低秩”是假设而不是定理。它成立的前提是任务相关的调整确实集中在少数方向上。分类、格式改写、风格迁移通常如此；要让模型学会一门新语言或大量新知识，低秩子空间可能装不下，这时要么提高秩，要么承认 LoRA 不合适。

推理阶段有两种用法。分离加载保留基座，另存一份几 MB 的 adapter，推理时先加载基座再挂上；合并则把 (alpha / r)·B·A 直接加到 W 上，得到一个普通权重矩阵，部署时不增加任何延迟。前者便于一个基座服务多个任务，后者便于交付与压测。

参数怎么定：秩、缩放与目标模块

实际动手时，四个参数决定了这次微调的成败。

秩 r 控制容量。经验上 4 到 16 足以覆盖大多数指令跟随与风格迁移任务，数据少、任务简单时取 4 或 8，与基座差距大时再往上加。r 太小会欠拟合，表现为损失下降缓慢、输出仍是基座腔调；r 太大则参数变多、过拟合风险回升，收益很快饱和。

alpha 控制调整幅度。真正起作用的是 alpha / r 这个比值，相当于给低秩分支乘了一个系数。固定 r 而把 alpha 翻倍，等于放大更新步长，效果类似提高学习率；同时按比例放大 r 与 alpha，比值不变但容量增加。实践里常从 alpha 等于 r 或 2r 起步，再按损失曲线微调。

dropout 加在低秩分支的输入上，只在训练时生效。数据只有几百上千条时，0.05 到 0.1 的 dropout 能明显缓解过拟合；数据充足时保持 0 即可。注意它不会让基座权重随机失活，只影响这条旁路。

目标模块决定把 adapter 贴在哪里。最经典的选择是注意力里的 q_proj 与 v_proj，参数量省、效果稳定。任务更难时可以扩展到 k_proj、o_proj 以及前馈层的 gate_proj、up_proj、down_proj，容量上去了，可训练参数也随之增加。通常不建议改词嵌入与输出头，它们占比大，且容易破坏词表层面的通用性。

模块选择的影响往往比秩更大。只贴 q、v 时，模型更像在调整“关注什么”；把前馈层也纳入，才接近调整“如何处理”。效果上不去时先铺开模块，再考虑加秩，通常更划算。

从基座到 adapter：训练流程与实践

整个流程可以拆成五步：加载基座、注入 LoRA、冻结原权重、训练、保存与合并。用 mermaid 表示如下。

flowchart TD
    A[加载基座模型与分词器] --> B[注入 LoRA 配置]
    B --> C[冻结基座参数]
    C --> D[构造指令数据集]
    D --> E[训练若干轮]
    E --> F[保存 adapter]
    F --> G{部署方式}
    G -->|多任务共用基座| H[分离加载 adapter]
    G -->|单任务交付| I[合并进基座权重]

用 transformers 加 PEFT 写出来并不长。示例以 GPT-2 为基座，仅演示接口形状；换成 GPT-J、OPT 或 BLOOM 时，目标模块名字要按结构改，比如 BLOOM 用的是 query_key_value。不同版本的库函数签名有差异，运行前请对照所装版本文档。

保存下来的目录里只有 adapter 的权重与配置文件，体积通常在几 MB 量级，相当于基座的千分之一。加载时先建基座，再用 PEFT 的加载接口把 adapter 挂上去。

合并后的权重与“基座 + adapter”数值等价，但评测基线不能混用；线上若两种形态并存，必须各跑一遍。

数据：格式、截断与损失掩码

指令微调的数据通常是一条条三元组：指令、可选的输入、期望的回答。落到训练样本上，需要自己拼成字符串模板，例如“下面是一条指令，请给出回答。指令：…… 回答：……”。2022 年还没有统一的对话模板约定，模板由作者自己定，关键是训练与推理必须用同一个，否则模型学到的是错位的模式。

拼接之后要做分词与截断。最大长度设成 512 或 1024，超长样本截断或丢弃，不要让一个样本撑爆整批显存。批内长度不一致时要 padding，并把 pad 位置在损失里屏蔽，否则模型会努力学习“如何输出填充符”。因果语言模型的标签是输入右移一位，所以对 prompt 部分统一置为 -100，只对回答计算损失，这一点对效果影响很大。

小数据集最大的敌人是过拟合。几百条样本、3B 以上的模型，往往一两轮就记住训练集：训练损失一路下降，验证损失中途回升，生成时开始复读原句。对策是留出百分之十做验证、按验证损失选检查点、适度加 dropout、把学习率降到 1e-4 附近，并混入少量通用语料。验证集太小时指标噪声很大，人工看几十条生成结果比盯数字可靠。

显存账本与 8-bit 加载

LoRA 省下的是优化器状态与梯度，省不下基座权重和前向激活。以 7B 模型、16 位权重为例：基座约占 14 GB；可训练参数若只有两千万，梯度与 Adam 状态加起来不到 0.5 GB；真正的大头是激活值，它随批大小、序列长度和层数增长，长序列下几 GB 很常见。所以“LoRA 只要 8 GB 就能训 7B”这类说法，通常指极小批、梯度累积加检查点重算，不能当通例。

显存不足时第一个手段是梯度检查点，用计算换显存，代价是慢约三成。第二个手段是 8-bit 加载：用 bitsandbytes 把冻结的基座量化到 8 位存放，前向时反量化参与计算。基座不参与更新，量化误差不会被优化器放大，这一招在 LoRA 场景下格外合适，能把权重占用几乎减半。8-bit 加载只省显存，不改变 LoRA 的数学形式，也别指望它提升效果。

第三个手段是缩短序列与减小批。很多团队一上来就把最大长度设成 2048，实际上领域数据的中位长度可能只有两百个 token，按实际分布定长度，省下来的显存比任何技巧都直接。

评估：别只看任务指标

LoRA 的评估要回答两个问题：目标任务学会了吗，通用能力退化了没有。

任务侧用可自动判定的指标。分类任务看准确率与 F1；生成任务用精确匹配、ROUGE 之类的重叠度指标，或用规则校验输出格式。这些指标便宜、可回归，适合每次训练后自动跑。局限也明显：措辞不同但语义正确的回答会被判错，所以只适合粗筛。

通用能力侧要防退化。取一份与训练数据无关的小评测集，比较微调前后的表现，重点看常识问答、指令跟随与长文本续写。若模型开始对所有问题都用同一句式作答，说明模板学过头了。几十条覆盖不同任务类型的样本就足以暴露问题。

最后是人工抽检。从验证集和真实请求中各取二三十条，逐条看事实性、格式、语气与拒答行为。这一步无法自动化，却最能发现指标看不到的毛病，比如模型把训练数据里的具体人名、日期当成通用知识复述出来。

与全量微调对比时，要比的不只是分数，还有训练成本、产出体积、推理延迟与回滚难度。数据量有限时 LoRA 往往能与全量微调打平；数据升到数万条、任务与基座差异很大时，全量微调仍有优势。两条路线都跑一遍再决定，比先验地认为某一种更好要稳妥。

局限与版本管理

秩设得太低会学不动，表现是损失降到某个值后不再下降，生成始终带着基座套话。这时先加目标模块，再考虑加秩；盲目把 r 调到 64 通常只是让 adapter 变大。反过来，秩够高而数据只有几百条时，模型会把 adapter 当记忆库，泛化更差。

目标模块的选择强依赖模型结构。同样是“注意力投影”，GPT-2 叫 c_attn，BLOOM 叫 query_key_value，写错名字不会报错，只会静默地一个参数都没挂上。训练前务必打印可训练参数数量，确认它不是零，也不是全量。

合并带来版本管理问题。adapter 与基座是绑定关系，基座换一个提交、换一个精度，adapter 就可能失效或效果漂移。工程上应把“基座名称 + 版本 + adapter 文件 + 训练配置 + 数据快照”整体登记，合并后的权重是另一个独立产物，不能与 adapter 共用版本号。一个基座服务多个任务时，优先保留分离加载，合并只作交付前最后一步。

最后是能力边界。LoRA 擅长调整行为与格式，不擅长注入大量新知识。想让模型记住整套产品文档，检索增强通常比微调更合适；两者解决不同层面的问题，可以叠加，但不能互相替代。

小结

LoRA 用一个低秩增量 ΔW = B·A 替代全参数更新，把可训练参数压到千分之一量级，让单卡微调大模型变得可行。动手时先确认目标模块名称与可训练参数数量，再从 r 取 8、alpha 取 16、dropout 取 0.05 起步，用验证损失而不是训练损失选检查点。显存的大头仍然是激活值，梯度检查点与 8-bit 加载是两把常用的省显存工具。评估要同时看任务指标、通用能力与人工抽检，产出则按“基座 + adapter + 配置 + 数据”整体登记。把它当作行为对齐的工具，而不是知识注入的手段，预期就不会跑偏。
