库存扣减的三种方案

库存扣减看起来只是一条减法语句，真正难的是让它在并发、重试和故障下依然成立。本文只讨论“扣减”这一个动作，把常见实现归纳为三条路线：数据库扣减、Redis 预扣后异步落库、消息队列串行化，逐条拆开讲清原子性从哪里来、一致性边界在哪里、失败之后怎么补，最后给出按业务形态选型的判断依据。

一、先把问题定义清楚

先把几个容易被含糊带过的概念钉死。本文把范围限定在一次扣减动作上：给定订单号、商品 SKU 和数量，系统要给出成功或失败，并且这个结论在重复调用、进程崩溃、消息重投时依然成立。至于秒杀怎么排队、页面怎么静态化、热点账户怎么记账，属于另外的篇目；本文只聚焦扣减本身的三种实现。

先约定库存模型。最朴素的表只有一列可售数量，扣减就是把它减一。只要业务存在“下单锁定、支付确认、超时释放”的流程，单列模型就不够用，通常拆成可售、锁定、已售三个数字：扣减把数量从可售挪到锁定，支付成功再从锁定挪到已售，超时取消则挪回可售。三者满足一条恒等式，可售加锁定加已售等于总库存。它是后面所有对账逻辑的基准，任何方案破坏了它，早晚要在某处补回来。

再约定两个失败模式。超卖是卖出数量超过总库存，属于资损事故，是必须杜绝的硬约束；少卖是库存还在，订单却提示售罄，属于体验与营收损失，是可以有限容忍的软约束。两者的实现代价并不对称：做成“宁可失败不可多扣”，超卖风险下降，少卖概率上升；反过来则相反。选型时先想清楚业务更怕哪一种，而不是先比性能。

一次合格的扣减要同时满足四件事。第一是原子，判断“够不够”和“减掉”之间不能插入其他请求；第二是幂等，同一个订单重复到达只能生效一次；第三是可追溯，每一次增减都要留下流水；第四是可补偿，失败或取消时能把数量准确加回去。

还有一个前提容易被忽略：库存数据放在哪里，谁说了算。只要引入缓存或内存计数，就出现两个副本，扣减便从本地事务问题变成一致性问题。三种方案的共同本质，都是把并发收敛到一个单点：数据库行锁、Redis 单线程、消息队列的单个分区。差别在于收敛点放在哪一层、失败时留下什么痕迹。

二、方案一：数据库扣减

数据库是库存最常见的权威副本。这个方案不引入额外组件，正确性由 InnoDB 的行锁和事务保证，适合库存量不大、单 SKU 并发有限的场景。它有三种写法：条件更新、乐观锁、悲观锁，原子性的来源相同，代价各不相同。

这条语句还有几个细节。sku 上必须有唯一索引，否则扫描会扩大锁范围，可重复读级别下还会产生间隙锁，把相邻记录一起锁住。MySQL 8.0.16 起 CHECK 约束真正生效，可以加一条 CHECK (qty >= 0) 作为最后防线，但它是异常兜底，不应替代 WHERE 条件。

影响行数为 0 并不等于售罄。记录不存在、商品已下架、分库路由错误，结果都是 0。失败路径上按 SKU 做一次轻量查询区分原因，成功路径不增加开销。另外，MySQL 驱动的 CLIENT_FOUND_ROWS 选项会让返回值变成匹配行数而非变更行数，本文建议保持默认。

乐观锁：版本号与重试

当事务里需要先读出库存做计算，再写回时，条件更新就不够用了。典型场景是按库存比例分配、组合商品拆解、多仓选仓。这时用版本号做比较并交换：

版本号匹配成功才更新，失败说明期间有人改过，应用重新读取再试。版本号单调递增，不会出现 ABA：即使数量恰好回到原值，版本也已经变了。版本号还能保护同一行上的其他字段，避免只改数量却覆盖别人刚改的阈值。

乐观锁的成本在重试。冲突概率随并发上升，重试次数也上升，数据库压力被进一步放大。工程上要设上限，比如三次，并加短退避；超过上限直接失败，把压力还给入口的限流。另一个常见错误是把版本号当成唯一条件，忘了 qty >= 2，一旦版本恰好匹配而库存已经不足，就会扣成负数。

悲观锁：SELECT FOR UPDATE 的代价

悲观锁先锁行，再判断，再更新：

SELECT ... FOR UPDATE 在主键或唯一索引等值条件下加排他行锁，后续 UPDATE 复用同一把锁。锁从 SELECT 开始持有，直到 COMMIT 才释放。好处是临界区内可以执行任意复杂的判断，比如会员限购、活动资格、多仓库存；坏处是临界区从一条语句扩大为整个事务，包含两次网络往返、应用计算和流水插入。

锁持有时间就是吞吐上限。热点行上排队的请求越多，平均等待越长，连接被占用的时间也越长。连接池耗尽往往比锁本身更致命：一批慢事务占满连接，不相干的查询也拿不到连接，故障从单个 SKU 扩散到整个服务。事务超时、连接池上限、接口超时三者要一起设置，并保证超时后事务回滚、连接归还。

一个订单涉及多个 SKU 时，加锁顺序必须固定，比如按 SKU 主键升序依次锁定。顺序不一致会形成环路，InnoDB 检测到后回滚其中一个事务并返回 1213，应用必须重试整个事务，而不是只重试某条语句。等锁超过 innodb_lock_wait_timeout 会返回 1205，默认五十秒，对在线接口显然太长，应按业务调小。MySQL 8.0 支持 FOR UPDATE NOWAIT，拿不到锁立即报错，适合快速失败；SKIP LOCKED 会跳过被锁的行，适合任务领取，但用在库存上等于把订单让给别人，通常不合适。

事务边界与行锁竞争

单条 UPDATE 在自动提交模式下本身就是一个事务，原子性没有问题。真正的设计点是外层事务的边界：库存、订单、流水必须一起成功或一起失败，所以它们要放在同一个本地事务里。事务内只做数据库操作，不调用远程服务、不等待外部回调；发消息也应挪到事务之后，或者用本地消息表保证一致。

隔离级别方面，MySQL 8.0 默认是可重复读。等值命中唯一索引时，两种级别差别不大；范围扫描则可能带出间隙锁，扩大冲突面。把这类事务显式设为读已提交更可控，代价是 binlog 必须使用 row 格式。监控上可以看 information_schema.INNODB_TRX 里的事务年龄，以及 MySQL 8.0 的 performance_schema.data_locks 与 data_lock_waits，定位是哪一行、哪个事务在排队。

这个方案的单次扣减不会超卖，因为判断和减法原子完成；也不会因为并发而少卖，失败的请求没有消耗库存。它真正的少卖来自结果不确定：事务提交时连接断开，应用既没拿到成功也没拿到失败。解决办法是提交后按订单号回查流水，或者让重试依靠订单号唯一键识别出“已经扣过”。一旦事务提交，回滚就只能是写反向流水，而且反向操作同样要幂等。

三、方案二：Redis 预扣与异步落库

单行串行是数据库方案的共同瓶颈。Redis 把数据放在内存里，由单线程执行命令，可以把“判断够不够、先减掉”这一步前移到数据库之前。库存的权威副本仍在数据库，Redis 只承担预扣，真正记账由异步消费者完成。这个分工带来一个直接后果：预扣成功不等于订单成功，两个副本之间出现了时间窗口，方案的全部复杂度都在处理这个窗口里的失败。

脚本要短，只做内存操作，不循环大集合，不使用时间和随机数。Redis 5.0 之后脚本默认按效果复制，但短脚本仍是纪律，因为执行期间整个实例是阻塞的。集群模式下，脚本涉及的所有键必须落在同一个槽，库存键和预扣键要带相同的 hash tag，例如 stock:{SKU-1001} 与 resv:{SKU-1001}:202212050001，否则 EVAL 会直接报跨槽错误。

调用方式上，生产环境先用 SCRIPT LOAD 取得 SHA1，之后用 EVALSHA 执行，减少脚本传输；收到 NOSCRIPT 错误时回退到 EVAL 并重新加载。Redis 7.0 的 Function 可把脚本注册为库，但当时尚未成为主流。

预扣记录与幂等

预扣记录至少要有订单号、SKU、数量、状态、创建时间和过期时间。状态机只有三个值：已预扣、已落库、已回补。所有状态迁移都用带条件的 Lua 完成，例如只有处于已预扣状态才允许回补，重复回补直接返回成功但不加库存。

过期时间要覆盖业务的最长链路，包括支付超时、风控审核和人工处理。但绝不能只靠 TTL 释放库存：键到期等于隐式回补，而订单可能还活着，用户支付时才发现库存没了。正确做法是延迟消息或定时扫描主动释放，TTL 只作为清理残留的兜底。反过来说，TTL 也不能太短，否则重试会变成第二次扣减。

异步落库、失败回补与对账

预扣成功后，订单服务创建订单并投递扣减消息，消费者再写数据库：

sequenceDiagram
    participant C as 客户端
    participant O as 订单服务
    participant R as Redis
    participant M as 消息队列
    participant S as 库存消费者
    participant D as MySQL
    C->>O: 提交订单
    O->>R: EVALSHA 预扣
    R-->>O: 成功或失败码
    O->>O: 本地事务写订单与预扣记录
    O->>M: 投递扣减消息
    O-->>C: 返回受理结果
    M->>S: 投递消息
    S->>D: 事务内写流水并条件扣减
    D-->>S: 影响行数
    S->>R: 标记预扣已落库
    S->>M: 提交位点

链路上有三处可能断：预扣成功但消息没发出去、消息发出但消费失败、消费成功但位点没提交导致重投。前两处造成 Redis 已扣而数据库未扣，表现为少卖；第三处如果消费端不幂等，会造成数据库多扣，表现为超卖。

发送失败的处理有两种。一种是在本地事务里写预扣记录，再由定时任务扫描“已预扣、未投递”的记录补发；另一种是使用支持事务消息的队列，把本地事务与发送绑在一起。前者简单、依赖少，后者链路更短，但要求队列支持半消息与回查。

落库端的原则是流水先行、条件兜底。在同一个事务里先插入流水，用请求号与 SKU 的唯一键去重，再执行带 qty >= n 的条件更新。数据库扣不动说明 Redis 与数据库不一致，这不是普通业务失败，应当回滚事务、转入重试或死信并告警，而不是静默把订单置为失败。

预扣成功但订单创建失败，比如参数校验不通过、风控拒绝、用户取消，需要把数量加回去。回补脚本与预扣脚本对称：检查预扣记录状态，只有已预扣才执行 INCRBY，并把状态改为已回补。状态判断和回补在同一个脚本里完成，否则重复回补会把库存越加越多。已落库的订单取消则走反向流水，不再动 Redis 的可售数。

对账是这套方案的生命线。两个副本之间有一条恒等式：数据库可售数量等于 Redis 可售数量加上所有已预扣未落库的在途量。直接把 Redis 余额和数据库可售数相比通常对不上，因为忽略了在途量。按分钟窗口比对时要同时读取 Redis 当前值、预扣总量和数据库流水增量，日终再逐 SKU 校验恒等式。发现差异后，最危险的动作是直接用数据库的值覆盖 Redis，这会把在途预扣重新放出来，瞬间超卖。稳妥流程是先冻结该 SKU 的扣减入口，再以数据库为准减去已确认的在途量，重建 Redis 键，最后解冻并观察一个核对窗口。

Redis 的持久化与复制也会影响正确性。AOF 每秒刷盘最多丢一秒写入；主从复制是异步的，故障切换可能丢掉最后一段。丢掉的是预扣记录，重启后库存看起来更多，于是超卖。可以用 WAIT 等待指定数量的副本确认，或配置 min-replicas-to-write，代价是可用性下降。更稳妥的做法是定期以数据库为准重建 Redis，把缓存当成可丢弃的派生数据，而不是账本。

四、方案三：消息队列串行化

按 SKU 分区，把并发变成排队

Kafka 的 topic 分成多个 partition，生产者指定消息 key，相同 key 的消息落到同一分区；同一个消费组内，一个分区同一时刻只被一个消费者消费。把 SKU 作为 key，同一 SKU 的扣减请求就天然串行，不需要分布式锁。RocketMQ 的顺序消息用队列选择器按 SKU 取模，思路相同。

分区数决定并行度，但只对不同 SKU 有效。单个热点 SKU 始终落在一个分区，增加分区不会提高它的处理速度，这一点在容量规划时最容易被忽略。需要保证顺序的也只有同一 SKU，跨 SKU 没有顺序要求，不应该共享分区，否则一个慢 SKU 会拖住无关商品。

结果回调与吞吐、延迟的取舍

扣减是异步的，接口不能直接返回最终结果。常见做法是下单接口返回“已受理”和请求号，前端轮询或服务端推送；消费者处理完把结果写到回调 topic，订单服务订阅后推进状态机。回调同样要幂等，订单状态只允许从“处理中”进入“成功”或“失败”一次。

吞吐上限等于分区数乘以单分区处理速率。单分区是串行的，批处理、合并提交能提高吞吐，却会增加延迟和失败重放的代价。延迟由排队时间和处理时间组成，高峰期排队占大头。这个方案适合削峰，把瞬时洪峰摊到一段可控的时间里；不适合要求几十毫秒内拿到扣减结果的强交互场景。积压要作为一级指标监控；增加消费者受分区数限制，扩容前先确认分区够不够。

三种方案并不是互斥的。常见的组合是 Redis 预扣加数据库条件更新兜底：Redis 决定谁有资格下单，数据库在落库时再用 qty >= n 守最后一道门。即使 Redis 算错，数据库也不会被扣成负数，代价是不一致时部分订单在落库阶段失败，需要补偿把预扣回补掉。这个组合把超卖从资损降级为少卖加告警，是很多团队愿意接受的折中。MQ 串行化则常常作为落库端的形态，与预扣组合使用。

选型可以先问三个问题。第一，单 SKU 的峰值是否会让一行记录成为瓶颈？如果不会，数据库条件更新足够。第二，扣减前是否需要复杂校验？如果需要，悲观锁的表达力更好，但要接受更长的临界区。第三，能否承担两套存储不一致的运维成本？如果不能，不要选预扣，也不要选纯异步。

六、五个关键问题

超卖与少卖

超卖的本质是判断依据与扣减结果不在同一个原子边界内，或者同一笔请求被执行了两次。数据库条件更新把边界压到一条语句，Lua 把边界压到一个脚本，MQ 把边界压到一个分区内的顺序处理。边界守住之后，超卖只能来自幂等失效和副本回退。少卖则相反，多来自扣了但业务失败没有回补，或者预扣长期悬挂。监控上要同时看负库存告警和超时未落库的预扣。

重复扣减

幂等键要用业务请求号，不要用数据库自增 id，因为后者在重试时会变。唯一索引放在流水表上，通常由请求号加 SKU 组成，插入成功才继续扣减，冲突即视为已处理。正向扣减与反向回补要用不同的 action 值，共用唯一键会把一次正常回补误判为重复。

回补与库存回滚

回补不是简单执行 INCRBY，要有状态机约束：只有已预扣未落库才能回补，只有已扣减未冲正才能反向。支付前取消，释放的是锁定库存；支付后退款，则要决定数量回到可售还是进入残次品隔离区，两者的库存归属不同，不能混用一条 SQL。所有反向动作都要写流水，记录原因、操作人和前后值，否则对账时无法解释差异。

热点 SKU

单行或单键的串行无法靠加机器解决。可选的办法是分桶，把总库存拆成多行或多键，按用户标识哈希选桶，扣不动再按固定顺序顺延；代价是碎片化和汇总复杂，补货与初始化必须统一处理。也可以在入口放本地令牌或队列，把并发挡在扣减之前。桶数要与目标并发匹配，过多会让单个请求连续试很多桶，反而增加延迟。

分库分表后的库存归属

库存表按 SKU 分片，订单表通常按用户分片，两者不在同一库，本地事务失效。原则是库存数据只由库存服务写，订单服务通过接口或消息调用，不直接跨库更新。跨分片的一致性用本地消息表加重试来保证，不要为了扣减引入两阶段提交，它的阻塞代价与库存场景并不匹配。若业务允许，让库存与订单共用分片键最省事，但会限制查询维度。

七、对账、补偿与监控

流水表

流水是幂等、对账、审计的共同基础。最小结构如下：

request_id 与 sku 的组合保证幂等，sku 加时间支撑按窗口聚合，status 区分已生效与已冲正。流水只追加，不更新数量；状态变更用带条件的 UPDATE。

定时核对

核对分三层：实时层看消息是否卡住，分钟级按 SKU 比对 Redis 与数据库的增量，日终做全量恒等式校验。比对口径要先定义：数据库按流水聚合成功状态的增减，Redis 同时取当前余额与窗口内预扣量，把在途量纳入公式，否则差异全是噪声。预扣记录还要单独扫描超过预期时长仍未落库的条目，这是最直接的少卖信号。

差异修复

发现差异后先冻结该 SKU 的写入，避免修复过程中数据继续变化；再以流水为准确定应然值，重放缺失的扣减或回补；最后解冻并观察一个核对窗口。禁止直接用数据库余额覆盖 Redis，也禁止手工改数不留痕。修复脚本本身要幂等，失败可以重入，执行记录要能追溯到具体差异单。

监控指标

至少覆盖：扣减请求量与失败率，并按原因拆分；库存不足比例；事务年龄与行锁等待时间；预扣未落库时长的 P99；回补失败数；死信数量与最老消息年龄；消费积压；对账差异条数与方向；负库存计数。指标要能按 SKU 下钻，否则热点出问题时，总量看起来一切正常。

八、按业务形态选型

普通商品以数据库条件更新为主，读算写场景加乐观锁，复杂校验用悲观锁。强一致、可审计，运维成本最低。

秒杀适合 Redis 预扣加 MQ 异步落库，数据库保留条件更新兜底。入口限流、页面静态化、排队与结果轮询属于秒杀架构的完整话题，本文不展开；就扣减本身而言，预扣脚本、幂等键、回补与对账四件事必须齐全。

预售的预扣窗口长达数天甚至数月，不适合把记录长期放在 Redis。用数据库预占表记录定金、尾款时间和释放时间，定时任务释放超时未付的预占，尾款支付成功再把预占转为已售。一致性由数据库保证，代价是峰值吞吐回到单行串行，需要分桶或错峰开售来缓解。

团队能力也是选型变量。没有对账、补偿与积压告警的团队，选 Redis 或 MQ 只是把超卖推迟到下一次故障。可运维性往往比峰值数字更重要。

小结

库存扣减的三种方案，差别不在 SQL 或脚本写得好不好，而在把一致性边界放在哪一层。数据库扣减用事务和行锁守住强一致，是多数系统的默认选择；Redis 预扣把争抢前移，用最终一致换吞吐，必须配套幂等、回补与对账；MQ 串行化把并发变成排队，适合削峰，但要接受延迟与积压。无论选哪种，扣减语句里的数量条件、请求号唯一键、可追溯的流水，这三件事都不能省。
