Protobuf 编码原理与性能

本文属于《Go 微服务架构》第 9/35 篇
上一篇系列目录下一篇

Protobuf 是后端服务之间最常见的序列化格式之一，但多数人只停留在“写 .proto、跑 protoc、调 Marshal”这一层。一旦抓包看到 08 ac 02 10 03 这样的字节串，或者面对一个“加个字段会不会把线上打挂”的问题，底层的规则就变得重要了。

本文只讨论编码本身：一条消息如何变成字节、如何被读回来，这套规则又如何决定了体积、解析开销与向后兼容的边界。gRPC 的调用方式、拦截器与流式传输不在讨论范围内。读完之后，你应该能手工解析一条简单报文，能判断某次字段改动是否会破坏兼容性，也能对“Protobuf 一定比 JSON 快”这类说法给出更有条件的回答。本文以 protobuf 3.21（即 protoc 21.x）为准，语法用 proto3，示例代码用 Go。

从一条字节串说起

假设有一个采集服务，每隔几秒把传感器的读数发给聚合服务。线上偶发“数据对不上”的问题，运维从抓包工具里导出一段报文，内容是十几个字节的十六进制：08 ac 02 10 03 1a 02 61 62 ...。它既没有字段名，也没有分隔符，人眼完全读不出含义。

很多人第一反应是“这是加密过的吧”。并不是。Protobuf 不做加密，也不做压缩，它只是把“字段叫什么”这件事从报文里搬到了 .proto 文件里。通信双方在编译期就约定了字段编号与类型，运行时只需要传编号和值。信息并没有消失，只是被移到了带外，而带外的那份契约恰好是可以放进版本库、可以 review、可以生成代码的。

这个设计带来两个直接后果，也是理解全文的钥匙。

第一，报文里没有冗余的元信息。JSON 里每一条 "sensorId": 300 都要重复一遍字段名，Protobuf 只写一个字节的编号。字段名越长、消息条数越多，省下来的字节就越可观。

第二，解析依赖 schema。拿到一段字节，如果没有对应的 .proto，你只能知道“字段 1 是一个 varint，值是 300”，无法知道它叫 sensor_id，也无法知道 300 这个数字代表什么。这既是 Protobuf 紧凑的原因，也是它调试不便的原因。后面会看到，这种“强依赖契约”的特性同样塑造了它的兼容性规则。

要读懂那段字节，只需要掌握三个概念：tag、wire type 和 varint。这三者构成了 Protobuf 编码的全部骨架，剩下的都是组合。

TLV 与 wire type

Protobuf 的报文是一条条“字段记录”首尾相接，每条记录采用 TLV 结构：先写 tag，需要时写长度，最后写值。没有全局的消息头，没有字段总数，也没有结束标记，解析器一直读到字节流末尾为止。

tag 本身是一个 varint，它的低 3 位是 wire type，高位是字段编号。用公式表达就是 tag = (field_number << 3) | wire_type。之所以把两者打包在一起，是为了让解析器在读到一个 tag 的瞬间就能同时知道“这是第几号字段”和“这个值有多长、该怎么读”。

wire type 只有五种有效取值，它们决定了值的物理形态。

wire type 名称 含义 对应类型
0 VARINT 变长整数，读到最高位为 0 为止 int32、int64、uint32、uint64、sint32、sint64、bool、enum
1 I64 固定 8 字节，小端序 fixed64、sfixed64、double
2 LEN 先读长度（varint），再读该长度的内容 string、bytes、嵌套消息、packed repeated
5 I32 固定 4 字节，小端序 fixed32、sfixed32、float
3 / 4 SGROUP / EGROUP 分组开始与结束，已废弃 proto2 的 group

这张表解释了一件容易被忽略的事：字段类型在报文里被“降维”成了三种物理形态加两种定长。int32 与 bool 在字节层面没有区别，都是 varint；float 与 fixed32 也没有区别，都是 4 字节。真正区分它们的是 .proto 里声明的类型，而不是报文本身。

这种设计给解析器留了一条捷径：遇到不认识的字段号，可以根据 wire type 直接跳过。wire type 0 就一直读到高位为 0 的字节；1 跳过 8 字节；5 跳过 4 字节；2 先读一个 varint 长度再跳过对应字节数。整个过程中不需要理解值的内容，甚至不需要知道这个字段存在。这正是“给旧版本程序发新版本消息”能够工作的物理基础。

varint 与 zigzag

varint 是 Protobuf 里出现频率最高的编码。规则只有两条：每个字节用低 7 位承载数据，最高位表示“后面还有没有字节”；多个字节时低位组在前，也就是按小端序拼接。解码时把每字节的低 7 位取出来，依次左移 0 位、7 位、14 位累加即可。

一个字节的 7 位能表示 0 到 127，两个字节能表示 0 到 16383。所以 300 需要两个字节：300 的二进制是 1 0010 1100，切成 7 位一组从低位开始是 0101100 和 10。前者补上续位标记得到 1010 1100，即 0xAC；后者不需要续位，就是 0x02。于是 300 编码为 ac 02。反过来说，看到 ac 02 时先取 0x2C，再取 0x02 左移 7 位加进去，得到 300。

这种编码对“小整数多”的场景非常友好：取值在 0 到 127 之间的字段只占一个字节，比固定 4 字节省了四分之三。但它对负数极其不友好。int32 的负数在编码前会被符号扩展成 64 位，最高位全为 1，于是每一个负数都固定占 10 个字节。-2 会被写成 fe ff ff ff ff ff ff ff ff 01，整整 10 个字节，仅仅为了表示一个负号。

zigzag 就是为解决这个问题而生的。它把有符号整数做一个双射变换，让绝对值小的数映射到绝对值小的无符号数：正数变成原来的两倍，负数变成绝对值的两倍减一。用位运算写就是 (n << 1) ^ (n >> 31)（sint32）或 (n << 1) ^ (n >> 63)（sint64）。-2 经过变换得到 3，编码成单字节 03；1 得到 2，编码成 02；-1 得到 1，编码成 01。

原值 int32 编码 字节数 sint32 编码 字节数
0 00 1 00 1
1 01 1 02 1
-1 ff ff ff ff ff ff ff ff ff 01 10 01 1
300 ac 02 2 d8 04 2
-300 10 字节 10 d7 04 2

结论很直接：字段可能出现负数时，用 sint32 / sint64 而不是 int32 / int64，时间差、坐标偏移、库存增减量是最典型的受益者。语义上永远非负的计数与长度，用 int32 或 uint32 就够了，不必再套一层 zigzag。

还有一点需要留意：varint 的解析对畸形输入是敏感的。规范把 varint 限制在 10 个字节以内，超过就应当报错；而 int32 字段收到一个超出 32 位范围的值时，会被截断成低 32 位，不会报错。这类“静默截断”在跨语言互通时偶尔会造成难以定位的偏差，写入方应当保证取值范围与声明类型一致。

长度前缀与 packed repeated

wire type 2 是结构最丰富的一类。它的格式是“tag + 长度 + 内容”，长度本身也是一个 varint，表示后面内容的字节数。字符串、字节数组、嵌套消息都走这条路：解析器先拿到长度的精确值，就能一次性分配缓冲区、一次性拷贝，不需要像解析 JSON 字符串那样逐字符扫描找结束引号。

这里的长度是内容字节数，不是字符数。UTF-8 下一个汉字占 3 字节，一个 4 字的标签长度前缀写的是 12 而不是 4。proto3 还要求 string 必须是合法 UTF-8，遇到非法字节序列时主流实现直接报错，而 bytes 不做任何校验。把二进制数据塞进 string 字段是常见错误，它在 Go 里可能侥幸跑通，到了严格校验的语言就会失败。

repeated 字段的编码有两种形态。非 packed 形态下，每个元素都带一个完整的 tag，语义上等价于“同名字段重复出现多次”，解析器把它们依次追加进列表。packed 形态则把所有元素的值首尾相接，外面套一个 wire type 2 的长度前缀，整个数组只有一个 tag。

当 values = [1, 300, 5] 时，packed 编码是 0a 04 01 ac 02 05，一个 tag 加一个长度，后面 4 个字节是三个 varint 拼在一起。非 packed 编码则是 08 01 08 ac 02 08 05，多出了两个 tag 和一个长度。元素越多，差距越大，因为 packed 把“每个元素一个 tag”摊薄成了“整个数组一个 tag”。

proto3 规定标量数值类型的 repeated 字段默认 packed，而 proto2 默认不 packed，需要显式写 [packed = true]。但无论声明如何，解析器都必须同时接受两种形态，这是规范的硬性要求，原因很现实：老版本 proto2 代码可能还在发非 packed 的数据。这条规则也提醒我们，判断兼容性时不能只看自己这一端的声明。

packed 只适用于数值标量，字符串、bytes、嵌套消息本身就是长度前缀结构，规范不允许再套一层。所以看到 wire type 2 时不要急着判定它是 packed 数组，它同样可能是嵌套消息或一段文本，最终要靠 .proto 里的声明来区分。

现在逐段拆开。第一个字节 08 是 tag：低 3 位 000 说明 wire type 是 0（varint），高位 00001 说明字段号是 1，正是 sensor_id。紧接着的 ac 02 按 varint 解码得到 300。三个字节，没有字段名，没有冒号，没有任何分隔符。

第二个 tag 是 10，低 3 位为 0，字段号 2，即 delta。值 03 是 zigzag 编码，反变换 (3 >> 1) ^ -(3 & 1) 得到 -2。如果当初把 delta 声明成 int32，这里会变成 10 个字节，整条消息立刻胖了一圈。

第三个 tag 是 1a，二进制 0001 1010，低 3 位 010 即 wire type 2，字段号 3。后面 02 是长度，再后面 61 62 是 ASCII 的 a、b。三个部分构成了一个完整的长度前缀记录。

第四个 tag 是 22，低 3 位 010，wire type 2，字段号 4。长度 04 说明后面 4 个字节都是数组内容：01 解出 1，ac 02 解出 300，05 解出 5。注意这里只有一个 tag，如果换成非 packed，同样的三个数要多花 3 个字节。

最后 28 01：tag 28 的低 3 位为 0，字段号 5，值 01 表示 true。bool 在字节层面就是一个取值 0 或 1 的 varint，没有任何特殊性。

同样的内容写成 JSON 是 {"sensorId":300,"delta":-2,"label":"ab","samples":[1,300,5],"ok":true}，六十多个字节。这个对比只是为了说明结构差异，并不是 Benchmark：换成一段长文本，两者的差距会迅速收窄，这一点在性能一节还会展开。

调试时不必每次都手算。protoc --decode_raw 可以在没有 .proto 的情况下把字节流打印成字段号加推断值的形式；如果有 .proto，用 protoc --decode=Reading reading.proto 就能得到可读的文本格式。这两个命令在排查线上报文时非常实用。

字段号与兼容性演进

字段号是 Protobuf 兼容性体系的基石，而它的取值区间被设计得很有层次。字段号 1 到 15 编码后的 tag 只占一个字节，因为 (15 << 3) | 7 = 127，正好塞满 7 位。字段号 16 到 2047 的 tag 需要两个字节。再往上直到 2 的 29 次方减一（536870911）是三到五个字节。区间 19000 到 19999 被保留给 protobuf 实现自身，写进 .proto 会直接编译报错。

于是就有一条常识：把最常出现、体积最敏感的字段放在 1 到 15 之间，偶尔出现的往后放。这不是微优化，在每秒几十万条消息的链路上，每个字段省下的一字节会累积成带宽。

真正的风险来自字段号的“回收”。设想第一版有 string phone = 3;，后来业务下线了这个字段，有人把声明删掉，半年后新同事为了加一个 int32 level = 3; 而复用了这个编号。此时线上还残留着老版本写入的数据、消息队列里还有积压的旧消息、某些边缘节点还没升级。新代码读到这些字节时，看到 tag 是字段 3 且 wire type 是 2，会认为这是一段合法的长度前缀数据，于是把一个电话号码当成 level 解析，得到一个荒唐的数值，而且不会报错。这类问题极难定位，因为每一端都“正常工作”。

reserved 会让任何复用这些编号或名字的改动在编译期失败，把线上事故提前成一次编译错误。保留字段名同样重要，因为 proto3 的 JSON 映射依赖字段名，名字被复用到语义完全不同的字段上，会让日志、配置、外部对接方产生误读。实践中还有一条经验：字段号一旦分配出去，就当作永久占用，宁可让编号出现空洞。

类型变更则需要看 wire type 是否一致。同一 wire type 内的替换在字节层面是兼容的，但可能有精度损失：int32、int64、uint32、uint64、bool 之间可以互转，因为都是 varint，只是取值范围不同；sint32 与 sint64 之间可以互转，但它们与 int32、int64 之间不兼容，因为 zigzag 变换改变了数值本身。fixed32 与 sfixed32 可以互转，fixed64、sfixed64 与 double 可以互转，都是 4 字节或 8 字节的定长。string 与 bytes 在字节层面兼容，前提是 bytes 的内容确实是合法 UTF-8。嵌套消息与 bytes 也兼容，这正是 Any 能够工作的原因。

反向的兼容也需要说清楚。给消息新增字段是最安全的操作：旧代码读到不认识的 tag，按 wire type 跳过，其余部分照常解析。proto3 从 3.5 起会保留这些未知字段，重新序列化时原样带出去，这对代理、网关这类“只转发不消费”的服务很重要。副作用是消息被反复读写后体积不会缩小，调试时还会看到一堆自己代码里不存在的字段。

枚举的演进规则常被忽略。proto3 要求第一个枚举值必须是 0，且 0 值不参与序列化，所以枚举的默认值天然是“未指定”。当旧代码收到一个新枚举值时，proto3 会把它当作普通数字保留下来，不会丢弃；proto2 则会把它放进未知字段，读取时得到的是默认值。这两种行为都意味着业务代码必须对未知枚举值做兜底，不能假设 switch 覆盖了所有分支。

proto2 与 proto3 的默认值差异

这一节值得单独拿出来讲，因为它是线上“字段丢了”问题最常见的来源。

proto2 的每个 singular 字段都有显式的存在性标记。生成代码里会有 has_phone() 这样的方法，能区分“从没设置过”和“显式设置成了空字符串”。如果显式把一个字段设成默认值，序列化时它照样会被写进报文，因为存在性标记为真。

proto3 在 3.0 到 3.14 这段时间里走了另一条路：标量字段只有隐式存在性（implicit presence）。序列化时，等于默认值的字段直接不写；反序列化时，没出现的字段就填默认值。两条路径最终得到同一个对象，于是“未设置”和“设置为零值”在语义上彻底不可区分。字符串的空串、数字的 0、bool 的 false、枚举的 0 值，全都会在报文里消失。

这个设计在多数场景下没有问题，甚至是体积优势的来源之一：一个刚创建、大部分字段为空的对象，序列化出来可能只有几个字节。但它有三个后果。

第一，无法表达“把字段清空”。做一个 PATCH 接口，客户端想把昵称改成空字符串，序列化后这个字段根本不出现，服务端无法区分“不要改昵称”和“把昵称改成空”。第二，用零值表达业务含义会失效，比如 int32 status = 3 里 0 代表“正常”，一个正常状态的对象里根本读不到这个字段，日志里看就是缺失。第三，基于报文做审计或对账时，统计“多少条消息设置了某字段”会系统性偏低。

社区为此演化出几种补丁方案。最经典的是 wrapper 类型，google.protobuf.Int32Value、StringValue 包一层消息，存在性就变成“消息是否为空”，可以判断。另一种是 google.protobuf.FieldMask，让客户端显式列出要更新的字段路径，语义清晰但对接成本高。用额外 bool 字段做标记可读性最差，不推荐。

真正的解决方案在 2021 年落地：proto3 重新引入了 optional。protobuf 3.15 起，在 proto3 里写 optional int32 level = 3;，该字段就恢复了显式存在性，生成代码里有对应的 HasLevel() 与指针或可选类型。实现上它被编译成一个只含单个成员的合成 oneof（synthetic oneof），因此在 wire 层面与普通字段完全一致，老代码读它不会有任何问题，只是看不到存在性。

使用它有两个约束：需要 protoc 3.15 及以上且运行时代码库版本匹配，老工具链会直接报错；它只解决“有没有”，不解决“该不该更新”，PATCH 语义仍建议配合 FieldMask 或明确的更新掩码。

至于 required，proto3 直接取消了它，proto2 里也早就不推荐使用。原因很直接：required 把校验前移到了序列化环节，一个字段缺失会让整条消息无法解析，而字段一旦 required 就永远不能删除，等于把自己锁死在契约里。

体积与解析开销

把前面的规则汇总一下，Protobuf 的体积优势来自四处：字段名不进入报文，只留一到几个字节的 tag；小整数用 varint，一个字节就能表达 0 到 127；数值数组用 packed，整个列表共享一个 tag；没有冒号、引号、逗号、缩进，也没有浮点数的十进制文本。

但这些优势都不是无条件的。以长文本为主的消息里，一段 2 KB 的描写会让字段名省下的几十个字节显得微不足道，两者的主体都是那段原文。取值分布很宽的整数也不划算：varint 的长度取决于数值大小，随机生成的 64 位 ID 有一半概率落到 10 字节区间，反而比 fixed64 固定 8 字节更费，这类字段应当用 fixed64 或 string 承载。

字段稀疏的小消息同样差距有限，Protobuf 每个出现的字段至少贡献一个 tag 字节。而经过压缩的链路最容易被忽略：JSON 里重复出现的字段名恰好是通用压缩算法最擅长处理的内容，gzip 或 zstd 之后两者会明显靠拢。所以“Protobuf 比 JSON 小”在“传输前已压缩”的场景下要打个折扣。本文不给具体倍数，任何倍数都强烈依赖数据形态，可靠的做法是拿自己的样本序列化一遍，比较长度与耗时。

解析速度的逻辑则不太一样。Protobuf 的解析器不需要做词法分析，不需要在字节流里找引号与转义，数字直接从二进制读出来，不需要 strconv 那样的字符串到数值的转换。更关键的是，wire type 让解析器可以跳过不关心的内容：一个只读取 sensor_id 的消费者，可以对其余字段一概不看，直接按长度跳过。JSON 做不到这一点，它必须把整段文本完整地切分成 token 才能保证结构正确。

不过“Protobuf 解析快”同样有条件，条件不满足时它也会慢。

首先是必须有 schema，并且最好是代码生成的解析器。用反射遍历字段、按名字查表、动态构建结构的实现，会把省下来的时间又吐回去。Go 的 google.golang.org/protobuf 在 v1.20 之后重写了运行时，代码生成的消息类型走的是生成好的快速路径，反射只作为兜底。

其次是内存分配。反序列化要为每个 string、bytes 和嵌套消息分配新内存，这部分开销与格式无关，只与数据量有关。热路径上应当复用消息对象，用 proto.Reset 清空后重新填充，或借助 Merge 选项把新数据合并进已有实例；缓冲区则可以用 sync.Pool 缓存，避免每条消息都触发一轮 GC。

第三是字符串转换。Go 里 []byte 转 string 默认会拷贝，一条消息里字符串字段越多，拷贝成本越高。这是语言层面的成本，不是编码格式的问题，但在做容量规划时经常被算到 Protobuf 头上。

第四是未知字段的保留。前面提到 proto3 会保存不认识的字段，这份保存是有代价的：需要额外的结构和内存。如果一个服务只是转发，且确定上游不会再读这些字段，可以用 proto.UnmarshalOptions{DiscardUnknown: true} 关掉它，换来更小的内存占用。

把这些放在一起看，选型判断就清楚了。内部 RPC、移动端弱网、大流量消息主题，Protobuf 优势明显：字段多、小整数多、结构稳定、双方都能接受重新生成代码。对外开放的 API、需要人直接读写的配置、浏览器请求，JSON 更合适：无需 schema、调试直观、工具链现成。真正不该做的是把两者当成信仰之争，为一个每天几千次调用的内部接口引入代码生成。

使用注意：嵌套、map、oneof、Any

这几种结构在语法上很简单，但它们的编码行为各有各的坑。

嵌套消息就是 wire type 2 的一种：内层先独立序列化，再作为外层字段的内容写入，外层长度前缀等于内层字节数。这意味着编码必须从内向外进行，任何一层内容变化都会让外层长度失效，需要逐层回填。这也是 Protobuf 无法“边算边拼”的原因：不知道内层多长，就写不出外层长度。层数越深，回填与拷贝越多，实践中建议控制在两三层以内。

map 在编码上没有特殊类型，它被展开成 repeated 的 entry 消息，key 是字段 1、value 是字段 2，entry 自己再套一层长度前缀。由此有三个约束：遍历与序列化顺序都不保证，Go 的实现甚至刻意随机化，所以不能用序列化结果做签名或哈希；同一个 key 出现多次时后者覆盖前者；key 只能是整数或字符串。

oneof 表示“一组字段中最多只有一个生效”，设置新成员会清空旧成员，序列化时只写当前那个。它在 wire 层面与普通字段完全一样，成员各自保留字段号，所以把字段移进或移出 oneof 不会解析失败。但语义会变：老代码把成员当普通字段看，如果新代码先后设置了两个成员，老代码会看到两个字段都存在，行为取决于它自己的处理顺序。另外 oneof 成员不能是 repeated 或 map。

Any 承载“类型在运行时才确定”的消息，编码上是两个字段：type_url 存完整类型名，value 存序列化后的字节。代价是接收方必须持有对应类型并注册到解析器，否则只能拿到一段不透明的 bytes；type_url 里的类型名一旦变化，解析就会失败。它适合插件、事件总线这类确实需要开放类型的场景，不适合日常建模。

最后补一个容易被忽视的组合问题：如果消息里要先压缩再传输，顺序必须是先序列化、再压缩，接收方先解压、再反序列化。反过来把压缩后的字节塞进 bytes 字段，虽然也能工作，但会让长度前缀失去意义，也让抓包工具彻底无法解析。

编码之外：gRPC 只是传输

最后需要把两件事分开：Protobuf 是编码格式，gRPC 是传输协议。二者经常一起出现，边界却很清楚。

gRPC 在 HTTP/2 之上定义了一种消息帧：1 个字节的压缩标志，4 个字节的大端长度，然后是消息体。消息体默认是 Protobuf 序列化后的字节，但帧格式本身并不关心里面是什么。方法名、超时、鉴权令牌、链路标识都放在 HTTP/2 的 header 里，属于 metadata，与 Protobuf 编码无关。响应状态码与错误详情走 trailer，也不在消息体里。

这种解耦带来两个影响。其一，同一个 .proto 可以走 gRPC，也可以塞进 Kafka 消息体、写进对象存储、作为缓存值。序列化与传输是两套独立的决策，换了传输方式，编码规则一条都不用改。其二，gRPC 的 codec 可替换，理论上能用 JSON 承载同样的服务定义，只是生态里几乎没人这么做。

更重要的是性能归因。一条 RPC 变慢时，原因至少有四层：序列化本身、网络往返与队头阻塞、服务端业务处理、框架层的拦截器与元数据开销。Protobuf 只负责第一层，而且往往是最便宜的一层。真正拖慢链路的是多次序列化、深拷贝、字段膨胀，以及把大消息塞进同步调用。排查时先确认消息大小与序列化次数，再谈换格式。

至于 gRPC 的服务定义、四种调用方式、拦截器与流控，那是另一篇文章的主题，本文不再展开。

小结

Protobuf 的编码规则其实只有三条：tag 把字段号与 wire type 打包成 varint，varint 让常见的小整数只占一字节，长度前缀让解析器能够精确跳过不认识的内容。剩下的 zigzag、packed、未知字段保留，都是这三条规则的推论。

理解这套规则的收益有三个。排查问题时，你能从十六进制里读出字段号和值。设计接口时，你会把热字段放在 1 到 15、删字段时写 reserved、需要区分“未设置”时加 optional。做性能判断时，你会先问数据形态，而不是笼统地说“二进制比文本快”。

如果你只记住一句话，那就是：Protobuf 的紧凑与兼容，都是用“强依赖 schema”换来的。契约维护得好，它是一套非常划算的交换；契约被随意改动，它出的问题会比 JSON 隐蔽得多。
