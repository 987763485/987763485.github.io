Kubernetes 多租户实践

本文属于《Docker 与 Kubernetes》第 27/51 篇
上一篇系列目录下一篇

多租户不是一个开关，而是一组边界叠加出来的结果。很多团队划出几个命名空间、绑定几个 RoleBinding 就宣布完成，直到某个租户的爬虫写满磁盘，或者没有网络策略的 Service 被隔壁扫了个遍。本文以 Kubernetes 1.22/1.23 为准，梳理命名空间级、集群级、虚拟集群三类模型，以及 RBAC、配额、网络、存储、Pod 安全、准入、节点、镜像、DNS、审计等隔离手段。

本文的重点是“边界在哪里、边界有多硬”：命名空间是逻辑边界，不是安全边界；RBAC 控制 API 访问而非运行时行为；配额保护集群资源而非应用质量，只有说清每层的职责和局限，才能拼出与风险匹配的方案。

三种多租户模型与隔离强度

多租户的诉求可以拆成三句话：看不到彼此的资源，改不了彼此的配置，也拖不垮彼此的服务。前两句是安全，后一句是稳定性。Kubernetes 原生的隔离机制几乎都围绕命名空间展开，因此社区通常把多租户分成命名空间级、集群级和虚拟集群三类。三者不是互斥的，很多平台会组合使用，但必须先明确自己需要哪一档隔离强度。

命名空间级多租户

这是最常见的形态：所有租户共享一套 API Server、etcd、调度器和节点池，每个租户得到一个或多个命名空间，平台通过 RBAC、ResourceQuota、NetworkPolicy 和准入策略把租户约束在自己的命名空间内。它的成本最低、密度最高，适合相互信任的内部团队，例如同一公司的业务线、测试和预发环境。

但“共享”意味着爆炸半径也是共享的：一个误绑的 ClusterRoleBinding 可以让所有租户获得集群管理员权限；一个没有配额的命名空间可以耗尽节点内存，挤走隔壁租户的 Pod；一个没有网络策略的命名空间，其 Service 对整个集群可见。命名空间级多租户的隔离强度，取决于平台有没有把 RBAC、配额、网络、准入这几层都补齐，而不是取决于命名空间本身。

Kubernetes 1.22 移除了大量 beta API，租户清单必须统一到稳定版本；升级前用 kubectl apply --dry-run=server 在预发集群验证，否则平台升级会变成所有租户一起排障。

集群级多租户

每个租户独占一个集群，或者按“租户 + 环境”拆分集群。API Server、etcd、节点、CNI、CSI 全部独立，一个租户的故障和攻击面被限制在自己的集群内，隔离强度最高。代价是控制面成本、版本升级、监控接入和生命周期管理都要乘以租户数量，小团队容易被集群数量拖垮。

集群级隔离也不是自动安全的。托管集群的默认 RBAC、Dashboard、kubelet 只读端口、云厂商元数据服务都可能成为新的入口；如果多个集群共用 CI 凭据或镜像仓库管理员账号，边界又会被拉平。多集群的注册、配置分发和灾备属于另一个话题，本文不展开。

虚拟集群

虚拟集群的思路是给租户一个“看起来独立”的控制面：租户拥有自己的 API Server 视图、CRD、RBAC 和版本节奏，实际的工作负载被同步到宿主集群的某个命名空间中运行。它解决了 CRD 全局冲突、租户想自己装控制器、租户集群版本不一致等问题，适合开发测试环境和平台内部的“集群即服务”。

虚拟集群的弱点在运行时。租户的 Pod 仍然跑在共享节点上，共享内核、kubelet 和容器运行时，网络与存储也由宿主集群提供。因此它强化的是 API 层隔离，不是内核层隔离；面对互不信任的外部租户，仍需要独立节点或独立集群来兜底。

隔离强度由最短板决定

flowchart TD
    A[共享集群] --> B[命名空间级]
    A --> C[集群级]
    A --> D[虚拟集群]
    B --> B1[共享控制面与节点]
    B --> B2[依赖 RBAC 配额 网络策略]
    C --> C1[独立控制面与节点]
    C --> C2[边界最硬 成本最高]
    D --> D1[独立 API 与 CRD]
    D --> D2[共享节点 运行时隔离弱]

三类模型的差别可以压成一张表。表中“运行时隔离”指进程、内核、设备层面的隔离，不是 API 权限隔离。

模型 API 隔离 运行时隔离 成本 典型场景
命名空间级 中，靠 RBAC 约束 弱，共享节点内核 低 内部团队、环境隔离
集群级 强，独立控制面 强，独立节点 高 外部客户、合规场景
虚拟集群 强，独立 API 视图 弱，共享宿主节点 中 开发测试、CRD 隔离

选型不要追求“最强”，而要找“风险与成本匹配”的那一档。内部团队的误操作风险，用命名空间加配额加网络策略通常够用；对外售卖的 SaaS 或承载不同等级数据的平台，应把独立集群或至少独立节点池作为默认答案。

命名空间：最基本但不完整的边界

命名空间是多租户的地基。它把名字的作用域切开，让不同租户可以各自拥有名为 web 的 Deployment、名为 db 的 Service，而不会互相覆盖。它也是 RBAC、ResourceQuota、NetworkPolicy、LimitRange 的作用域单位，平台的所有租户策略几乎都挂在这个对象上。

命名空间提供了什么

第一是命名作用域。同一命名空间内资源名唯一，跨命名空间可以重名；Service 的 DNS 名称会带上命名空间，例如 web.team-alpha.svc.cluster.local。第二是权限作用域。RoleBinding 只在一个命名空间内生效，这是把租户管理员限制在自己地盘里的基础。第三是配额作用域。ResourceQuota 和 LimitRange 都是命名空间对象，配额按命名空间独立计算。

第四是策略选择器的作用域。NetworkPolicy 用 podSelector 和 namespaceSelector 选择目标，租户标签打得规范，策略才能写得准确。第五是默认身份：每个命名空间自动拥有 default ServiceAccount，Pod 未指定时使用它，这也是共享 ServiceAccount 风险的来源。

它不提供什么

命名空间不是内核命名空间。它不隔离进程、网络协议栈、文件系统、设备，也不隔离节点。同一节点上的两个 Pod，无论属于哪个租户，都共享内核；内核漏洞、容器运行时漏洞、错误的 hostPath 挂载，都可能让隔离失效。把命名空间当成安全沙箱，是多租户实践里最典型的误解。

命名空间也不覆盖集群级资源。Node、Namespace、PersistentVolume、StorageClass、ClusterRole、CustomResourceDefinition、Webhook 配置等对象不属于任何命名空间。租户如果能创建 CRD，就能定义全局类型，和其他租户的 CRD 发生版本冲突；如果能创建 ClusterRoleBinding，就能把权限扩散到所有命名空间。这些权限默认不应该给租户。

还有一个容易忽略的点：命名空间的删除是异步的。命名空间进入 Terminating 后，控制器要逐个清理资源，遇到卡住的 finalizer 可能停留很久。租户退租时，平台不能只看删除命令是否返回成功，还要确认命名空间真正消失、PV 按回收策略处理完毕、DNS 记录和证书是否清理。命名空间的生命周期管理，应该和租户的入职、退租流程绑定在一起。

把命名空间当作租户的交付单元

实践上，平台团队应该把“创建一个租户”封装成可重复的模板，而不是让租户自己 kubectl create namespace。创建命名空间是集群级操作，普通租户不应该拥有这个权限；即使拥有，新建的命名空间也不会自动带上配额、LimitRange、默认拒绝的 NetworkPolicy 和正确的 RBAC。

一个可用的租户命名空间至少包含以下内容：统一的标签，例如 tenant.example.com/name 和 tenant.example.com/tier；ResourceQuota 与 LimitRange；默认拒绝的 NetworkPolicy；租户专用的 ServiceAccount 与 RoleBinding；必要的镜像拉取 Secret；以及指向平台监控、日志系统的采集配置。把这些对象放进一个 Git 仓库目录，用 GitOps 工具同步，命名空间才真正成为可审计、可复制、可回收的交付单元。

RBAC 与最小权限

RBAC 回答的是“谁能在哪个范围内对哪类资源做哪些动作”。它由四个对象组成：Role 定义一组命名空间内的权限，ClusterRole 定义集群范围的权限，RoleBinding 把角色授予命名空间内的主体，ClusterRoleBinding 把角色授予整个集群。RoleBinding 也可以引用 ClusterRole，但授权范围仍被限制在 RoleBinding 所在的命名空间，这是平台最常用的组合方式。

用组而不是用个人

租户的权限应该授予身份提供商里的组，而不是某个离职同事的账号。下面的 Role 只允许读写工作负载和配置，刻意没有授予 secrets、pods/exec 和删除命名空间的权限。pods/exec 等价于在容器里执行命令，能读到挂载的令牌和环境变量，不应该作为开发者的日常权限。

内置的 view、edit、admin 可以作为起点：view 不允许读 Secret，edit 可以，admin 能管理命名空间内的 RoleBinding，却不能改配额和命名空间本身。cluster-admin 不应授予任何租户，排障走带审批和时效的提权流程。

system:authenticated 的风险

system:authenticated 是一个内置组，所有通过认证的主体都会自动属于它，包括普通用户、ServiceAccount 令牌和联邦身份账号。把某个 ClusterRole 绑定到 system:authenticated，等于向全集群所有已认证身份开放这组权限。如果绑定的角色包含 Secret 读取、Pod 创建或 pods/exec，攻击者只要拿到任意一个低权限令牌，就能横向到所有租户。

同样危险的是 system:unauthenticated，它对应匿名请求。默认的 system:public-info-viewer 和 system:discovery 只提供版本、API 发现之类的公开信息，问题不大；但如果有人为了“让监控能访问”而把自定义 ClusterRole 绑到匿名组，边界就彻底消失了。审计时应该先列出所有 ClusterRoleBinding，检查 subjects 里是否出现这两个组。

ServiceAccount 是容易被忽略的身份

每个命名空间都有 default ServiceAccount，Pod 默认会挂载它的令牌。如果多个租户共用同一个 ServiceAccount，或者把租户 A 的令牌以 Secret 形式复制到租户 B，RBAC 的命名空间边界就被绕过了。正确做法是每个工作负载使用独立的 ServiceAccount，只授予它需要的权限；不需要访问 API Server 的 Pod 显式设置 automountServiceAccountToken: false。

较新的 Kubernetes 默认使用带过期时间的投射令牌，但有效期内仍然可用。租户能创建 Pod，就能让 Pod 以指定 ServiceAccount 运行，因此平台要限制高权限 ServiceAccount，并对 RBAC 变更做审计和评审。

资源配额与 LimitRange

命名空间解决了“在哪里”，配额解决“用多少”。ResourceQuota 是命名空间级的硬上限，API Server 在准入阶段计算命名空间内已有资源加新对象是否超限，超限就拒绝创建。它既能限制 CPU、内存等资源，也能限制对象数量，防止租户用大量 ConfigMap、Service 或 PVC 把 etcd 和云资源拖垮。

配额要同时约束 requests 和 limits

调度器看的是 requests，节点上的实际占用受 limits 约束。只配 limits 不配 requests，Pod 会被当成零请求，调度器可能把大量 Pod 塞到同一节点，直到内存耗尽触发驱逐；只配 requests 不配 limits，单个 Pod 可能无限膨胀，把节点拖垮。配额里两者都要有，并且用 LimitRange 提供默认值。

配额不等于公平

配额保证单个租户不超上限，但不保证公平。一个租户在配额内跑满 200 个 Pod，仍可能占满节点，让另一个租户的 Pod 因资源不足而 Pending。缓解 noisy neighbor 可以按租户划分节点池、设置不同 PriorityClass、对超额使用告警。配额是“防爆炸”的底线，不是调度公平性的完整答案。

对象数量配额同样重要。services.nodeports 和 services.loadbalancers 设为 0，可以避免租户随意占用节点端口和云负载均衡器；count/deployments.apps 和 count/configmaps 可以防止控制器和配置对象无限增长。Kubernetes 原生没有配额层级，父命名空间不会自动汇总子命名空间的用量；需要层级配额时，只能借助 HNC 一类的外部项目，或者由平台在 CI 里做汇总校验。

网络隔离：默认允许，必须主动拒绝

Kubernetes 的网络模型是扁平的：每个 Pod 有独立 IP，默认情况下任意 Pod 可以访问任意 Pod，跨命名空间也不例外。命名空间只改变 DNS 名称和 API 作用域，不改变数据面连通性。真正决定 Pod 之间能不能通信的，是 NetworkPolicy 以及 CNI 是否实现了它。

NetworkPolicy 的语义

NetworkPolicy 是命名空间对象，通过 podSelector 选中一组 Pod，再声明这些 Pod 允许的入站和出站流量。它有两个容易误解的地方。第一，策略是“默认允许、选中后拒绝”：没有被任何策略选中的 Pod 仍然接受所有流量；一旦被选中，只有策略里明确允许的流量才能通过。第二，策略是叠加的，多条策略之间取并集，没有显式的 deny 规则。要拒绝某类流量，只能通过“不把它写进任何 allow 规则”来实现。

一条连接要成功，源端的出站策略和目标端的入站策略都必须允许。很多团队只在目标命名空间写了 ingress 规则，却忘了源端命名空间的 egress 默认拒绝，结果两边都觉得自己配了策略，流量还是不通。排查时应该同时看两端，并确认 CNI 确实在执行策略。

租户命名空间创建后，第一件事应该是放一条默认拒绝所有入站和出站的策略，再按需放行 DNS、同命名空间通信和入口控制器。下面的例子只展示结构，实际端口和选择器要按环境调整。

CNI 支持差异是最大的坑

NetworkPolicy 只是 API 对象，执行者是 CNI 插件。Calico、Cilium、Antrea、Weave Net 等实现了策略执行；单纯的 Flannel 只负责连通性，不执行 NetworkPolicy，策略对象可以创建成功，但流量不受影响，这比报错更危险。部分云厂商 CNI 只支持 ingress 或完全不支持，选型时要查能力矩阵。

验证方法很朴素：A 访问 B 被拒绝，B 访问 A 同样被拒绝，DNS 和允许的入口仍然可用；每次升级 CNI 或更换节点池都重跑一遍。策略“创建成功”不等于“生效”，这是最容易产生虚假安全感的地方。

另外两个边界要记住：使用 hostNetwork 的 Pod 在很多实现里不受 NetworkPolicy 约束，hostPort 也会绕过部分策略；云厂商的元数据服务地址 169.254.169.254 应该被出站策略显式拒绝，除非租户确实需要节点身份。NetworkPolicy 工作在 L3/L4，不能按 HTTP 路径或方法做限制；需要 L7 授权时，属于服务网格的范畴，本文不展开。

存储、镜像与 Pod 安全

存储隔离

StorageClass 是集群级资源，租户不应该有创建或修改它的权限。平台提供少量受控的 StorageClass，再通过准入策略限制租户只能使用白名单里的类。PVC 是命名空间对象，PV 是集群对象；动态供给时，租户创建 PVC，CSI 驱动创建 PV 并绑定，租户通常看不到 PV 本身，但平台必须确保 PV 的回收策略和退租流程匹配。

reclaimPolicy: Delete 适合临时数据，PVC 删除后底层卷随之释放；reclaimPolicy: Retain 适合需要保留的数据，但退租后 PV 会变成 Released，需要人工清理，否则一直占着存储和配额。共享文件存储还要注意访问模式：ReadWriteOnce 是节点级挂载，不是 Pod 级；ReadWriteMany 允许多节点同时挂载，若底层文件系统没有目录级隔离，一个租户的错误挂载可能看到另一个租户的数据。存储隔离最终要落到“每个租户独立 PVC、独立后端目录、独立加密密钥”上。

镜像与仓库隔离

镜像仓库经常被忽略。所有租户共用一个管理员账号，等于把供应链的根权限交了出去。更合理的做法是按租户划分仓库命名空间，给每个租户一个只能推送自己项目的机器人账号，把拉取凭据做成命名空间内的 imagePullSecret。准入策略可以要求镜像必须来自受信任的仓库前缀，禁止 latest 标签，要求使用 digest 或不可变标签，并在入库时做漏洞扫描。

漏洞是否阻断部署取决于业务风险。多租户平台至少要做到高危漏洞可见、镜像来源可追溯，并禁止租户绕过仓库直接拉取公网镜像，否则前面所有的 Pod 安全策略都会承受更大压力。

Pod 安全：PSP 退场前的过渡

PodSecurityPolicy（PSP）在 Kubernetes 1.21 被标记为弃用，计划后续移除；1.22 和 1.23 仍可用，但不适合作为新平台的长期方案。PSP 是集群级对象，通过 RBAC 绑定，控制 Pod 能否使用特权模式、hostPath、hostNetwork 等；配置绕、排障难，而且只影响创建和更新，不影响已运行的 Pod。

Pod Security Standards 定义 privileged、baseline、restricted 三个级别，Pod Security Admission 在 1.23 进入 beta，可通过命名空间标签启用。它把“Pod 该长什么样”从集群级 PSP 收敛到命名空间级标签，作用域终于和租户边界对齐。1.22 里它还是 alpha，需要显式开启特性门控，因此 2022 年初的存量集群大多仍在使用 PSP，或用策略引擎实现同等约束。

上面的写法是“强制 baseline、对 restricted 只告警和审计”。迁移时先全部设为 warn 和 audit，观察违规情况，再逐租户切到 enforce。无论用 PSP、Pod Security Admission 还是策略引擎，都应禁止特权容器、hostPath、hostNetwork、hostPID，要求非 root、只读根文件系统、丢弃不必要的能力，并启用默认 seccomp。对真正不可信的租户，还需要 gVisor、Kata Containers 这类运行时隔离，或者独立集群。

准入控制与策略引擎

准入控制是 API Server 持久化对象前的最后一道闸门：变更类准入补默认值，校验类准入拒绝不合规对象。Kubernetes 内置配额、LimitRange、Pod Security 等控制器，但“所有 Pod 必须有租户标签”“镜像必须来自指定仓库”“禁止 NodePort”这类平台规则，需要策略引擎落实。

OPA Gatekeeper 用 Rego 写规则，以 ConstraintTemplate 定义约束类型，再用 Constraint 声明生效范围，适合有 Rego 经验的团队。Kyverno 用 YAML 描述策略，支持 validate、mutate、generate，适合以清单为主的团队。两者都是平台策略的统一入口，不是 RBAC 的替代品：RBAC 管 API 权限，策略引擎管对象内容。

策略上线分三步：audit 记录违规，warn 提示租户，最后 enforce 拒绝。直接 enforce 会把存量工作负载挡在门外。策略 webhook 还要考虑可用性：失败的 webhook 可能阻塞整个集群的 Pod 创建，应设置合理超时，用 namespaceSelector 排除 kube-system，对非关键规则使用 failurePolicy: Ignore，并保证多副本运行。策略引擎的 ServiceAccount 权限很大，证书和配置也要重点保护。

节点、DNS、证书与审计

节点隔离

命名空间共享节点，就意味着共享内核和 kubelet。对隔离要求更高的租户，可以把节点池按租户划分：给节点打标签和污点，租户的 Pod 通过容忍和节点亲和性落到自己的节点池，其他租户的 Pod 因为污点无法调度进来。

污点只负责“赶走别人”，容忍只负责“允许进来”，还要用 nodeAffinity 把租户 Pod 吸引到对应节点，否则 Pod 可能调度到没有污点的公共节点。节点池隔离能减少资源争抢和跨租户的本地卷误挂载，但不能防御内核漏洞和容器逃逸；真正互不信任的租户，应该使用独立集群或独立虚拟机。托管集群的 kubelet 配置通常由云厂商控制，平台更多是限制节点上的 DaemonSet、hostPath 和特权 Pod。

DNS 与证书

DNS 是共享的。CoreDNS 为所有命名空间提供解析，租户 A 默认可以解析 db.team-beta.svc.cluster.local，即使 NetworkPolicy 随后阻断了连接，服务名和命名空间结构仍然暴露。默认拒绝出站后只放行 DNS 能减少任意查询；更严格的环境可以按租户拆分 DNS 视图，但不要把 DNS 当成授权机制。

证书方面，cert-manager 的 Issuer 是命名空间级的，ClusterIssuer 是集群级的。租户应使用自己的 Issuer，把 TLS Secret 留在自己的命名空间；共享 ClusterIssuer 时要限制可引用的命名空间，避免为任意域名签发证书。通配符证书爆炸半径大，尽量按租户子域签发，并做好轮换和私钥访问审计。

审计日志

审计日志记录“谁在什么时候对什么对象做了什么”。审计策略可以按用户、组、资源、命名空间设置 None、Metadata、Request、RequestResponse 等级。多租户场景至少记录 Metadata，把用户名、组和命名空间关联起来；RequestResponse 会记录请求和响应体，可能把 Secret 写进日志，除非合规要求，否则不要对 Secret 开启。

审计是事后发现手段，不是预防手段。平台应该把审计日志送到独立的日志系统，设置保留期，并对敏感动作告警：读取 Secret、pods/exec、创建 ClusterRoleBinding、修改 ResourceQuota、删除命名空间。租户自己的审计视图只能看到自己的命名空间，跨租户的审计数据由平台保管，避免租户之间互相窥探。

平台团队与租户的分工

平台负责集群生命周期、CNI 与 CSI、Ingress、策略、可观测性、备份升级、命名空间交付和配额治理；租户负责工作负载清单、requests 与 limits、网络策略、ServiceAccount、Secret、镜像卫生和值班。边界要写进文档和评审清单，避免“平台以为租户会配，租户以为平台默认配”。

自助不等于放任。平台提供命名空间模板和 GitOps 仓库，租户用 PR 声明配额和网络放行，策略引擎校验后自动创建；入职有清单，退租有回收流程，包括删除命名空间、处理 Retain 的 PV、清理 DNS 和证书。平台由此从工单执行者变成守门人。

成本分摊靠标签。tenant、cost-center、env 由准入强制，按命名空间的实际请求量和用量做 showback，再把控制面、Ingress、监控等共享成本按约定比例分摊。配额是上限不是账单，闲置预留和超卖会让“配额占比”与“实际成本”偏离，报告里要写清口径。

常见坑

只做命名空间不做网络策略，是最常见的虚假安全感。命名空间不阻断流量，没有默认拒绝策略时，租户的数据库端口对整个集群可见。配额不设默认请求同样普遍：要么因缺少 requests 被拒绝，要么 Pod 以零请求进入调度，直到节点内存耗尽才暴露。

共享 ServiceAccount 会把身份边界抹平。租户 A 的 Pod 使用租户 B 的 ServiceAccount，或者所有人共用 default，RBAC 再精细也没有意义。CRD 是集群级对象，租户自行安装 CRD 会和别的租户发生版本冲突，甚至覆盖平台控制器依赖的类型；应该由平台统一管理，或者用虚拟集群隔开。监控标签泄漏则更隐蔽：Prometheus 默认抓取所有命名空间，Grafana 又共用数据源，租户能看到别人的指标和标签，等于把业务拓扑暴露出去。

其余几个坑包括：CNI 根本不执行 NetworkPolicy；把 PSP 当成完整安全方案；给租户集群级只读权限，导致节点和 PV 信息外泄；退租时只删命名空间，Retain 的 PV、负载均衡器、DNS 和证书长期残留。每个坑都应固化成平台检查项，进入自动化测试和入职评审。

小结

隔离强度由最弱的一层决定：命名空间是组织单位，不是安全边界；RBAC 和配额解决“能做什么、用多少”，网络策略、Pod 安全和准入解决“能碰谁、能跑什么”，节点与集群隔离才是不可信租户的硬边界。

落地建议分阶段：先统一命名空间模板、RBAC 组和配额默认值，再补默认拒绝的网络策略与存储、镜像约束，最后引入策略引擎、节点池、审计告警和成本分摊。每加一层都要测试它真的生效，并把自助流程和退租回收一起设计。
