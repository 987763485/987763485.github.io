服务自保护与过载保护

一个服务在流量正常时表现得体，接口响应几十毫秒，错误率接近零；一旦流量翻了几倍，或者某个下游突然变慢，它的表现会迅速失控：延迟从几十毫秒涨到几秒，超时开始出现，客户端重试涌入，线程池被占满，连健康检查都开始失败，最后整个实例被摘除，压力转移给剩下的实例，雪崩由此发生。过载不是某个组件的故障，而是一种系统性状态，它以正反馈的方式自我放大，如果不加干预，服务很难靠自己走出泥潭。

本文讨论服务如何在这种状态下保护自己：先看清过载的表现与成因，再建立一套能反映真实压力的负载指标体系，然后用自适应限流、排队与拒绝、背压、隔离、重试预算等手段把压力挡在合适的位置，最后用压测和容量水位验证这些手段是否有效。限流算法的推导、Sentinel 的接入、降级与熔断的细节、容量规划的方法，分别在前面的文章中讲过，本文只在必要处引用，不再重复。

过载的表现与成因

过载指到达服务的请求量超过了它在当前资源和依赖状态下能够有效处理的上限。这个上限不是常量：依赖变慢、实例减少、缓存失效、垃圾回收变频繁，都会让它下移。因此同一个服务在上午能轻松承接的流量，到了下午可能就会把它压垮。判断是否过载，不能只看入口 QPS，而要看系统是否已经进入“越忙越慢、越慢越忙”的循环。

从延迟上升到雪崩

最直观的表现是延迟上升。请求进入系统后先排队，再被处理，处理期间还可能等待下游。排队论中的 Little 定律告诉我们，系统中的平均请求数等于到达率乘以平均停留时间；当处理能力接近饱和时，新到达的请求只能在队列里等待，延迟随利用率上升呈非线性增长。平时几十毫秒的接口，可能在几分钟内变成几秒，而入口 QPS 的涨幅看起来并不夸张。

第二层表现是队列堆积。队列可能出现在多个位置：内核的 accept 队列、Web 框架的请求队列、线程池的任务队列、连接池的等待队列、消息队列的积压。队列长度是过载最早的信号，因为它通常先于延迟和错误率变化。一个有界队列被填满，说明系统已经没有余量；一个无界队列持续增长，说明内存在被缓慢透支。

第三层是线程或执行单元耗尽。采用 thread-per-request 模型的服务，每个请求占用一个线程，线程在等待数据库、HTTP 调用或锁时不能复用。线程池被占满后，新请求连排队的机会都没有。Go 服务虽然用 goroutine 代替线程，单个 goroutine 的开销小得多，但 goroutine 终究要消耗栈内存、调度时间和下游连接，数量失控同样会拖慢整个进程，表现为调度延迟上升和 GC 压力增大。

第四层是连锁超时与雪崩。上游调用下游时设置超时，下游变慢后上游的请求一直占着连接和 goroutine 直到超时；上游的超时又让它的上游超时，错误沿着调用链向上扩散。与此同时，客户端和网关看到错误后重试，重试请求又加剧了拥塞；健康检查因为排队而失败，负载均衡器把实例摘除，剩余实例承担更多流量，最终整个集群一起不可用。这条链路可以画成一个正反馈回路。

flowchart TD
    A[流量增加或依赖变慢] --> B[队列堆积]
    B --> C[延迟上升]
    C --> D[客户端超时与重试]
    D --> A
    C --> E[健康检查失败]
    E --> F[实例被摘除]
    F --> G[剩余实例压力更大]
    G --> B

需要强调：过载保护的目标不是让所有请求都成功，而是在超出能力时保持系统可控——保住核心流量、尽快失败、不让状态继续恶化。只要承认“有一部分请求必须被拒绝”，后面的手段才有讨论的基础。

压力从哪里来

流量突增是最容易被想到的原因：促销活动、热点事件、爬虫、客户端集中刷新。但更多时候，过载的导火索不是流量本身，而是容量下降或依赖变慢。依赖变慢会让每个请求占用资源的时间变长，相当于把服务的有效容量按比例削掉；一次慢查询、一次缓存击穿、一次跨机房网络抖动，都可能触发同样的连锁反应。

重试放大则是最隐蔽的一种。假设调用链有三层，每层在失败后最多重试两次，那么最下游看到的流量最多可以放大到原来的二十多倍（3 的 3 次方）。如果重试没有预算、没有抖动、没有幂等约束，它就不再是容错手段，而是拥塞的放大器。容量下降同样常见：发布期间实例分批重启、节点被驱逐、CPU 被限流、磁盘写满、连接泄漏，都会让本已紧绷的系统失去最后一点余量。

负载指标：不要只看 CPU

要控制过载，先要有一套能反映“系统还有多少余量”的指标。CPU 使用率是最常用的一个，也是最容易误导人的一个。它适合判断计算密集型服务的繁忙程度，却不适合判断一个大量等待 I/O 的服务是否还能接客。一个服务可能 CPU 很低，但连接池已经耗尽、请求全部堵在等待队列里；另一个服务 CPU 接近满载，却只是因为流量结构变化，延迟仍在可接受范围。单看 CPU，两种情况的结论都会错。

CPU 指标本身也有陷阱。容器里的 CPU 使用率是宿主机视角还是 cgroup 视角，差别很大；设置了 CPU limit 的容器在超限时会被内核节流（throttling），表现为周期性停顿，平均使用率可能并不高，但尾延迟已经明显恶化。多核机器上还要看是否有个别核心被打满，单核热点和整体繁忙对延迟的影响完全不同。load average 同样需要谨慎：Linux 的 load average 统计的是可运行和不可中断睡眠的进程数，包含大量等待磁盘 I/O 的进程，而且容器内看到的往往是宿主机的数值，不能直接当作“每核负载”使用。

真正贴近过载状态的指标有四类。第一类是队列长度，包括服务端待处理请求数、线程池队列长度、连接池等待数和消息积压量，它反映“已经进来了但还没被处理”的工作量。第二类是并发数，也就是正在处理中的请求数（inflight），它与吞吐、延迟满足 Little 定律，可以直接和压测得到的容量上限比较。第三类是延迟分位，p95、p99、p999 比平均值敏感得多；还要注意超时的请求常常没有进入延迟统计，过载时“成功的请求看起来很快”是一种幸存者偏差。第四类是错误与拒绝，按 429、503、超时、连接拒绝、熔断打开等类型分开统计，才能区分“主动保护”与“被动故障”。

指标 反映的问题 主要盲区
CPU 使用率 计算资源是否紧张 等待型服务可能很低；容器节流不可见
load average 可运行与不可中断任务的数量 包含 I/O 等待；容器内常是宿主机值
队列长度 已到达但未处理的工作量 无界队列会掩盖饱和

此外还应关注依赖侧指标：下游调用的延迟与错误率、连接池活跃数与等待数、GC 停顿、磁盘与网络饱和度。过载往往先出现在某个依赖的等待队列上，而不是本服务的 CPU 上。“不要只看 CPU”的完整含义是：同时看资源、队列、并发和延迟，并且以延迟和队列为主，以资源为辅。

自适应限流：让阈值跟着系统走

固定 QPS 阈值的问题在于它假设容量不变。实际上，实例规格、数据规模、依赖响应时间、缓存命中率都在变，今天压测出来的安全值，下个月可能已经偏高或偏低。更麻烦的是 QPS 并不等价于负载：一个请求可能只查一次缓存，也可能触发十次数据库查询，同样的 QPS 对系统的压力可以相差一个数量级。阈值靠人工拍板，就只能靠事故来校准。

自适应限流的思路是把服务看成一个受控系统：目标是维持可接受的延迟或排队水平，而不是维持某个 QPS。控制器周期性观察负载信号，与目标值比较，再调整允许通过的并发数或速率。负载升高时收缩，负载回落后再缓慢试探着放开。它不预测流量，只对系统当前的反应做出反馈，因此对容量变化和流量结构变化都更宽容。

可用的反馈信号主要有三类。基于并发的做法直接限制 inflight，超过上限就拒绝，上限由算法动态调整；基于延迟的做法比较当前响应时间与低负载时测得的基线，延迟明显高于基线就说明请求在排队；基于队列的做法看排队长度或排队时间，队列持续非空就收缩。三者可以组合，但不要把多个信号简单取最小值，否则任何一个抖动都会让限流器过度保守。

BBR 拥塞控制常被拿来类比：它通过测量最小 RTT 和最大带宽来估计瓶颈处的排队，而不是等丢包才减速。自适应限流借用的是“用延迟膨胀判断排队”的思想，并不需要真的估计带宽。Sentinel 提供的系统自适应规则就是这类思路的工程实现，具体规则项与接入方式见第 655 篇，这里不展开。

令牌桶与并发限制的配合

令牌桶控制速率，并发限制控制在途数量，两者解决的不是同一个问题。令牌桶关心“单位时间放进来多少请求”，能削掉突发；但它不关心每个请求要处理多久。当依赖变慢、单请求处理时间从几十毫秒涨到几百毫秒时，同样的 QPS 会让 inflight 成倍增长，资源照样会被耗尽。令牌桶的令牌发放与突发语义见第 639 篇，这里只说配合方式。

两者的关系可以用 Little 定律描述：并发数约等于吞吐乘以平均延迟。假设目标吞吐是每秒一千次，正常延迟是五十毫秒，那么平均只需要五十个并发；延迟涨到五百毫秒，同样的吞吐就需要五百个并发（以上数值仅为示意）。并发上限应该按压测得到的真实处理能力来设，而不是按正常延迟算出来的理论值；令牌桶的速率则按下游配额或业务合同来设。前者保护自己，后者保护别人。

落地时把两道闸门放在不同位置：入口做速率限制，按租户、接口或来源分配配额；执行前做并发限制，拿不到执行槽位就快速拒绝。只做速率限制，依赖一慢就会堆满；只做并发限制，短时间的突发仍会把队列打满，而且无法约束长期的平均速率。两者都设好之后，再配合短队列和截止时间，才算完整的入口保护。

排队、拒绝与背压

队列必须有界

队列不是免费的缓冲。请求在队列里等待的时间同样消耗客户端的耐心，等到真正被处理时，客户端可能已经超时离开，服务却还在为一个没人要的结果忙碌。队列还会占用内存，无界队列把过载问题从“拒绝服务”变成了“延迟无限增长，最后 OOM”，后者更难恢复。任何排队结构都应该有明确上限，并且这个上限要和延迟预算对齐：队列能吸收的只是微突发，不是持续的超额流量。

请求进入队列时应该带上截止时间，出队时先检查是否已经过期，过期就直接丢弃并计入指标。很多系统在过载时做了大量无效功，原因就是请求早已超时，工作线程还在按部就班地查库、拼装响应。拒绝要发生在尽可能早的位置：网关、框架入口、执行槽位之前。拒绝的代价应该很小，不要为一条错误响应去查配置、渲染模板或写一条同步日志。

拒绝时返回什么状态码也有讲究。429 表示请求过多、触发了速率限制，通常带 Retry-After 告诉客户端何时再试；503 表示服务当前不可用或已过载，适合表示“不是你的配额问题，而是我暂时处理不了”。响应体尽量短，不要在过载时生成大段 JSON 或错误页。所有拒绝都要计数，按接口和原因分开，否则事后无法判断是保护生效还是故障扩散。

优先级与差异化

不是所有请求都同等重要。健康检查、控制面指令、已付费租户的核心交易，与后台导出、批量同步、爬虫抓取，对系统的重要程度完全不同。过载时如果一视同仁地随机拒绝，最先被牺牲的可能是最不能出问题的那部分流量。合理的做法是按优先级分队列或分资源池，给高优先级流量预留容量，低优先级流量先被拒绝。

优先级队列要防止饿死和反转。低优先级请求长期得不到执行，业务上可能同样不可接受，可以设置老化机制，让等待过久的请求逐步提升优先级；高优先级请求如果和低优先级请求共用同一个连接池，仍然会被堵住，所以隔离要一直做到资源层。另一种差异化思路是按成本拒绝：同样是一个请求，全表扫描和主键查询的代价差很多，可以在入口根据参数或接口类型提前拒绝高成本请求。

背压：让上游知道下游满了

背压是指下游把“我处理不过来”的信号传回上游，让上游降低发送速度，而不是继续把请求堆在中间。没有背压的系统，每一层都以为自己加一个队列就能消化波动，结果压力被层层缓冲、层层延迟，最后在最弱的一环集中爆发。背压的本质是拒绝缓冲的诱惑，让拥塞信息尽快回到产生流量的地方。

背压可以借助多种机制传递：HTTP 的 429 与 503、gRPC 的 RESOURCE_EXHAUSTED、TCP 的窗口与 HTTP/2 的流控、消息队列的消费者滞后、以及代码里带缓冲 channel 的阻塞发送。在 Go 中，向满的 channel 发送会阻塞，这就是最朴素的背压；但阻塞必须同时监听 context，否则上游取消后发送方会永久卡住。

在请求链路里，背压还意味着截止时间要端到端传递。上游只剩一小段预算，下游就不应该再按自己的固定超时去等；每一跳都用剩余预算，才能保证超时的请求尽快释放资源。队列应尽量靠近执行者，不要在调用链的每一层都放一个大队列；每多一层缓冲，背压信号就多衰减一次，过载的真相就更晚被看见。

隔离、重试与降级的边界

用隔离舱限制故障半径

隔离的思路来自船舱的隔水舱：把资源切成互不影响的几块，一块进水不会拖沉整条船。服务里最常见的做法是按依赖划分线程池或连接池，让慢的依赖只耗尽自己的配额，不占用其他依赖和核心接口的资源。Java 生态里线程池隔离很直观；Go 服务虽然不为每个请求绑定线程，仍然可以用信号量为每个依赖设置并发上限，效果类似。

隔离的粒度可以按依赖、按接口、按租户，也可以按部署单元。批处理、导出、全量同步这类重活，最好拆到独立的进程或独立的实例组，不要和在线交易共享同一个连接池。池子的大小要按下游能承受的并发来定，而不是越大越好；把池子开得很大，只会把排队从自己的进程转移到下游，同时让下游更难恢复。

这个池子不提供无限等待：拿不到配额就等到调用方取消为止。对在线请求来说，这比默默排进一个无界队列更诚实。

重试预算与抖动

重试只能在链路的一层做，通常在离用户最近、最了解业务是否幂等的那一层。每一层都重试，失败会被逐层放大；没有抖动的固定间隔重试，会让所有客户端在同一时刻再次冲向已经过载的服务。退避加随机抖动是基本要求，同时要尊重服务端返回的 Retry-After，不要把“稍后再试”当成“立刻再试”。

重试预算把重试量约束在总请求量的一个比例内。可以把成功请求的一部分换算成重试令牌，只有拿到令牌才允许重试，令牌耗尽时直接失败。这样即使故障面很大，重试流量也不会超过系统能承受的上限。下面的函数只负责计算带抖动的延迟，预算与次数上限要在调用方控制。

全局随机源要在进程启动时播种，否则各实例会得到相同的抖动序列，抖动就失去意义。还要明确哪些错误值得重试：连接建立失败、明确的超时、5xx 通常可以重试；参数错误、鉴权失败、业务规则拒绝不应重试；429 要按 Retry-After 等待。非幂等操作只有在有幂等键或去重机制时才能重试，否则重试会把“一次失败”变成“两次扣款”。

降级与熔断只做边界

降级与熔断的机制在第 672 篇已经展开，这里只强调它们在过载保护中的位置。降级必须是预先设计、提前演练的开关，而不是事故发生时的临场发挥：返回缓存、返回默认值、关闭非核心功能、缩小查询范围，这些路径都要在低峰期验证过。熔断器按依赖维度设置，打开后快速失败，半开时只放少量探测流量；它适合阻止对已知故障依赖的无效调用，但不能代替容量规划，也不能把过载误判成业务错误。

一个常见的误区是所有实例同时打开熔断、同时进入半开、同时放量探测，结果下游刚恢复就被再次打垮。探测流量应该加随机抖动，并设置较小的上限。另一个误区是熔断后没有兜底，调用方拿到异常直接向上抛，等于把故障原样传递；熔断和降级要成对设计，前者负责停止无效调用，后者负责给出可接受的替代结果。

平台层的边界与容量验证

在 Kubernetes 上，requests 决定调度，limits 决定上限。CPU limit 设置过紧会触发节流，请求的平均 CPU 可能不高，尾延迟却周期性变差；memory limit 触发的是 OOMKill，进程直接重启，比变慢更突然。HPA 默认按 CPU 扩缩容，对等待型服务并不合适，可以改用并发数、队列长度或自定义业务指标；但 HPA 有采集和调度延迟，扩容速度赶不上秒级突增，maxReplicas 还受下游容量约束。它适合削峰，不适合当作第一道过载保护。

压测要用开放模型：按固定到达率发请求，而不是固定数量的 worker 循环调用。后者在服务变慢时会自动降低发压速率，恰好掩盖了过载。用阶梯流量找到延迟开始非线性上升的膝点，再在膝点以下确定运行水位，并为单实例或单可用区故障留出余量；容量规划的系统方法见第 708 篇。除了正常流量，还要演练依赖延迟升高、实例被摘除、重试集中爆发等场景，验证保护手段真的会动作。

可观测性方面，入口看请求速率、错误率和延迟分位，资源看利用率和饱和度，保护层看当前限流值、inflight、拒绝数、熔断状态和连接池等待数。告警应绑在用户可感知的 SLO 上，而不是单独盯 CPU；过载排查时，链路追踪能指出时间耗在排队、下游还是锁上。日志在过载期间要限速和采样，这一点在后面的坑里还会提到。

常见坑与自查

第一个坑是限流阈值长期不变。业务量、实例规格、依赖性能都在变，阈值需要定期用压测复核；更好的做法是固定阈值与自适应限流并用，固定值兜底，自适应值跟随系统状态。

第二个坑是只看入口 QPS。一个入口请求可能扇出成多次下游调用，异步任务和重试也不计入入口指标；真正的压力要看下游 QPS、inflight 和队列，而不是网关上的那个数字。

第三个坑是重试风暴。多层重试、固定间隔、对超时也重试，会把一次抖动放大成持续拥塞；重试预算、抖动、单层重试和幂等约束缺一不可。

第四个坑是健康检查拖垮服务。把数据库连通性、下游可用性放进存活探针，过载时探测失败导致实例被重启或摘除，反而减少容量；存活探针只应判断进程是否还能工作，依赖状态交给就绪探针，并控制探测频率与超时。

第五个坑是过载时日志打满磁盘。每个失败请求都打一条带堆栈的错误日志、同步写盘，磁盘写满后进程连启动都失败；应对错误日志限速采样、异步写入，并给系统和日志目录留出保底空间。

小结

过载是一个正反馈过程，保护的关键是尽早发现排队、主动拒绝一部分请求、把压力尽快传回上游，而不是靠加队列硬扛。指标上要同时看队列、并发、延迟分位和错误类型，不能只盯 CPU；手段上要让自适应限流、令牌桶、并发上限、有界队列、背压、隔离、重试预算和降级互相配合。所有阈值都应来自压测和运行数据，并在容量变化后重新校准。最后，保护机制本身也要被观测和演练，否则它只是一段从未生效过的代码。
