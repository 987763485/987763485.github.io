Rust 与 Python 混合部署

本文属于《Rust 学习路线》第 46/68 篇
上一篇系列目录下一篇

Python 的生态让团队可以很快把想法变成服务，但在计算密集、内存敏感或需要长期稳定运行的环节，解释器与动态类型会带来额外成本。Rust 提供了接近 C 的性能与编译期安全保证，又不引入垃圾回收和重量级运行时，于是“用 Python 组织业务、用 Rust 承担热点”成为一条务实的路线。本文围绕这条路线，讲清楚混合部署的几种形态、PyO3 的核心用法、GIL 与数据边界、打包与部署细节，以及那些往往只在联调阶段才暴露的坑。

本文讨论应用层面的混合，不展开 C ABI、链接器与符号导出这些底层话题，也不涉及 C++ 互操作；版本背景为 Rust 1.58、Python 3.9/3.10、PyO3 0.15/0.16，文中性能数字除特别说明外均为示意值，只用于说明数量级。

动机：Python 的生态与 Rust 的边界

Python 的优势在于生态与组织能力。数据处理有 NumPy、pandas，Web 有成熟的框架，运维脚本、任务调度、胶水代码都能快速完成，团队招人和交接的成本也低。问题出在边界上：解释执行、对象装箱、动态分派让纯 Python 循环的单核效率有限；GIL 让同一进程内的多线程难以并行执行计算任务；长时间运行的服务里，内存占用和尾延迟也更难预测。

Rust 正好补上另一侧。所有权与借用检查把大量内存错误挡在编译期，没有垃圾回收意味着停顿可预测，零成本抽象让高层写法仍能编译出紧凑的机器码，Send/Sync 又让并行计算的安全边界清晰。把 JSON 解析、规则匹配、特征计算、压缩解压、图像预处理这类 CPU 密集且接口稳定的逻辑放到 Rust，往往能同时获得吞吐与稳定性。

但“混合”不是把整个服务重写一遍。跨语言边界本身有成本，团队要维护两套工具链、两套调试手段和一条跨平台的构建流水线。合理的做法是先找到真正热的那一小段，测量、隔离、定义清楚输入输出，再决定用扩展模块还是独立服务。本文后续的讨论都建立在这个前提上：Python 负责编排、IO 和业务变化，Rust 负责边界清晰的计算内核。

判断是否值得，可以用三个问题：这段逻辑是否占据足够的 CPU 时间，接口是否长期稳定，团队是否有人能维护 Rust 代码。如果答案是否定的，优化 Python 本身、换算法或加缓存通常更划算。反过来，如果一段代码每秒要被调用上万次、每次处理的数据却很小，跨语言调用的固定开销就会吃掉收益，这时应该先合并调用，而不是急着迁移。

三种混合形态

从进程边界看，Rust 与 Python 的结合只有三种基本形态，选择哪一种，决定了后面的打包、部署和排错方式。

第一种是 Rust 扩展模块。Rust 编译成动态库，Python 通过 import 加载，调用发生在同一进程、同一地址空间里。它的调用开销最小，通常只是一次函数调用和若干次对象转换；数据可以共享内存，适合低延迟、高频次的热点函数。代价是耦合最深：扩展必须为每个目标平台和 Python 版本构建，崩溃会直接把宿主进程带走，GIL 也仍然是绕不开的约束。

第二种是 Rust 独立服务。Rust 程序以 HTTP 或 gRPC 暴露接口，Python 作为客户端调用。两者可以有各自的发布节奏、资源配额和故障域，Rust 侧还能被其他语言复用；扩容时按服务扩，不必连 Python 一起扩。代价是序列化与网络往返，单次调用通常在毫秒级（示意值，取决于协议与网络），并且多了一层需要运维的进程和一套接口契约。

第三种是 Python 嵌入 Rust，即在 Rust 程序里启动解释器执行 Python 脚本，常用于把 Python 当作插件语言或配置语言；它与前两种方向相反，本文不展开。

如果函数每秒被调用成千上万次、参数只是几个数字或一段字节，扩展模块更合适；如果一次调用就要传几十 MB 数据，或者希望计算服务独立扩容、独立重启，独立服务更合适；离线批处理可以写成 Rust 命令行工具，由 Python 调度，本质上仍是第二种形态的变体。一个常见的误区是“既然要性能就用扩展”，但若调用频次很低，网络与序列化的代价反而更容易被观测、限流和治理。

PyO3 的核心构件

PyO3 是 Rust 侧的 CPython 绑定库，它把 C API 包装成安全的 Rust 接口，同时支持“Rust 扩展模块”和“Rust 嵌入 Python”两个方向。对大多数项目来说，只需要记住四类构件：#[pyfunction] 暴露函数，#[pymodule] 定义模块入口，#[pyclass] 与 #[pymethods] 暴露类型，以及围绕它们的类型转换和错误映射。

类型转换、异常与 GIL

跨语言调用的第一道成本是类型转换。PyO3 为常用类型提供了双向映射：Rust 的整数、浮点数、布尔值与 Python 的 int、float、bool 对应，String 与 &str 对应 str，Vec<T> 与 list 对应，HashMap 与 dict 对应，Option<T> 对应 None 与具体值。参数位置使用 FromPyObject，返回值位置使用 IntoPy<PyObject>；这也是自定义类型要实现的两个 trait。

错误处理遵循同一条思路：Rust 的 Result 在边界上被翻译成 Python 异常。PyResult<T> 就是 Result<T, PyErr>，? 会把 PyErr 直接抛给调用方；PyValueError、PyTypeError、PyKeyError 等类型对应内置异常，自定义异常可以用 create_exception! 声明。需要特别注意的是，std::io::Error 虽然会自动映射为 OSError，但携带的上下文有限；serde_json::Error 这类第三方错误则不会自动转换。通常应显式 map_err 成 PyRuntimeError 或业务自定义异常，并在消息中保留上下文，否则 Python 侧只能看到一句笼统的报错。

GIL 是另一个绕不开的边界。CPython 用一把全局锁保护解释器状态，扩展函数被调用时默认持有 GIL，这意味着函数执行期间其他 Python 线程无法执行字节码。若扩展内部只是做几微秒的加法，持锁无所谓；若它要在 Rust 里跑几十毫秒乃至数秒的纯计算，就必须主动释放，否则多线程服务会被这一把锁串行化。

PyO3 提供 Python::allow_threads：在闭包执行期间释放 GIL，闭包返回后重新获取。它有三个适用条件。第一，闭包内不能访问任何 Python 对象，包括 &PyAny、PyObject 和持有 Python 引用的结构体，因为这些对象的访问都要求持锁；需要的数据应先转换成 Rust 原生类型再移入闭包。第二，闭包及其返回值必须满足 Send，否则无法保证跨线程安全。第三，只有在计算时间明显长于释放与重新获取锁的开销时才值得使用，太短的临界区反而会增加切换成本。

反过来，如果 Rust 自己创建线程并在其中调用 Python（例如回调），必须用 Python::with_gil 重新附着到解释器，不能把 Python 令牌跨线程保存。理解这一点，后面讨论“为什么多线程没有加速”时就有了统一的解释。

数据交换的边界

跨语言调用最容易被低估的成本，是数据在边界上的搬运。Python 的 list 是一个 PyObject 指针数组，每个元素都可能是任意类型；把它转换成 Vec<f64> 时，Rust 要逐个检查类型、拆箱、复制。dict 转 HashMap 同理，键和值都要转换。一次调用的转换开销与元素个数成正比，元素越多，越应该避免逐元素往返。

数值计算应尽量把 NumPy 数组作为边界。rust-numpy 提供了 PyArray1<f64> 这类类型，当数组的 dtype 匹配、内存连续时，可以借用出 &[f64] 而不复制；不满足条件时则退化为复制。本文不展开 rust-numpy 的细节，只强调定位：它解决的是“大块同构数值数据如何低成本过边界”，不是让所有数据都变成数组。业务结构体、嵌套字典、变长字符串仍然需要序列化或逐字段转换，设计接口时应尽量把结构拍平成几个数组。

字节与字符串也有类似的取舍。参数写成 &[u8] 或 &str 时，PyO3 借用 Python 对象内部的缓冲区，调用期间有效、不能保存到 Rust 结构体里；写成 Vec<u8> 或 String 则会复制，换来独立的所有权。返回方向相反：返回借用切片需要绑定生命周期，通常直接返回 Vec<u8> 或 PyBytes。一个实用的原则是“入参尽量借用，出参明确复制”，并在文档里写清楚谁会持有数据。

最后是批量原则。与其让 Python 循环调用 Rust 函数一百万次，不如一次传入整个数组，在 Rust 内循环。前者每次都要跨越边界、检查类型、处理异常，固定开销乘以次数；后者只付一次转换成本，循环本身在编译后的机器码里完成。这个原则会贯穿后文的性能讨论。

开发时在虚拟环境中执行 maturin develop，它会编译并把扩展安装到当前环境，随后 Python 侧可以直接 import；发布时执行 maturin build --release，在 target/wheels 下生成 wheel；maturin publish 则用于上传到包索引。命令本身简单，真正需要设计的是“要为哪些平台、哪些 Python 版本出包”。

abi3 是第一个关键选项。CPython 从 3.2 起提供稳定 ABI，扩展只使用稳定 ABI 中的符号，就可以编译出一个跨多个 3.x 版本可用的 wheel。在 PyO3 中打开 abi3-py39，表示最低支持 3.9，产出的 wheel 标签形如 cp39-abi3，3.9、3.10 都能安装。代价是不能使用 3.10 才引入的 C API，某些新特性也只能放弃；如果项目必须依赖新版本的解释器接口，就只能按版本分别编译。

第二个关键是平台标签。没有 abi3 时，wheel 名称会带 cp39-cp39 这样的解释器与 ABI 标记；带 abi3 时变成 cp39-abi3。平台部分则取决于构建环境：Linux 常见 manylinux2014_x86_64，对应 glibc 2.17 及以上；在更新的发行版上直接编译，产出的 wheel 可能依赖更高版本的 glibc，装到旧镜像里就会报符号找不到。稳妥的做法是在 manylinux2014 容器里构建，或用 auditwheel 检查并修复标签。macOS 要区分 x86_64 与 arm64，必要时构建 universal2；Windows 则按 MSVC 工具链出包。

第三个关键是版本对齐。扩展模块与解释器的 ABI 必须匹配，cp39 的包不能装进 3.10 环境（abi3 除外），PyPy 也不能直接使用 CPython 扩展。团队应把 Python 小版本、Rust 工具链版本和 maturin 版本写进 CI 配置，避免“本地能跑、流水线打出的包不能装”这类问题。

性能边界与调用粒度

Rust 带来的是常数因子上的改善，不会改变复杂度。若算法本身是平方级，换语言也救不了；若瓶颈在数据库或网络，扩展模块同样无能为力。真正适合迁移的是“复杂度已经合理、但常数太大”的纯计算。

即使如此，跨语言调用仍有固定成本。一次 Python 到 Rust 的调用、参数转换、异常检查加起来大致在微秒量级（示意值，随参数规模变化），而一次简单的 Rust 计算可能只有几十纳秒。若按元素逐个调用，开销会完全盖过计算本身；若一次传入整批数据，固定成本被摊薄，Rust 的优势才会显现。可以用一个经验规则：单次调用里 Rust 侧的有效计算时间应至少是边界开销的十倍以上，否则优先合并接口。

测量时要包含转换成本，比较“Python 原实现端到端”与“Rust 实现端到端”，而不是只测 Rust 函数内部。timeit 适合微基准，真实数据上的火焰图更适合定位。cProfile 只能看到 Python 栈帧，Rust 内部通常显示为一个整体调用；需要 native 栈时可以借助 py-spy 的采样能力（需要符号信息），或者先在 Rust 侧埋点计时。

举一个示意的账：若一次边界往返约 2 微秒，单次计算本身约 0.2 微秒，逐元素调用时九成时间花在边界上，换语言几乎没有意义；若一次传入一万个元素，边界被摊薄，收益才接近 Rust 的真实水平。这个账不精确，但足以判断接口该粗还是细。

内存、所有权与 panic 边界

扩展模块里同时存在三块内存：Python 的引用计数堆、Rust 的分配器，以及两者共享的缓冲区（如 NumPy 数组）。分清谁拥有数据，是避免泄漏和悬垂指针的前提。

Python 对象的所有权用引用计数表达。PyO3 的 Py<T> 表示一个强引用，克隆它要调用 clone_ref 并持有 GIL；&PyAny 则是调用期间的借用，生命周期不会超过 GIL 的作用域。因此不能把 &PyAny 存进 Rust 结构体，也不能把它跨线程传递。把 Python 对象保存在 #[pyclass] 字段里时，应使用 Py<PyAny>，并尽量在持有 GIL 时释放；如果确实需要在没有 GIL 的线程析构，至少要知道 PyO3 会延迟处理部分引用计数，不要依赖析构的即时性。

Rust 侧的 Vec、String、Box 在跨越边界时通常被复制。把 String 传给 Python 会创建新的 str，把 Vec<u8> 返回给 Python 会复制进 bytes 或 bytearray；只有明确借用（&str、&[u8]）且在调用期间使用，才不复制。共享缓冲区的情形更微妙：NumPy 数组的内存由 Python 侧管理，Rust 借用时不能释放或扩容它，返回给 Python 的视图也必须保证底层数据活得足够久。这类生命周期问题编译器只能检查 Rust 这一半，另一半要靠接口约定与测试。

panic 是另一个必须明确的边界。PyO3 会在包装层捕获 panic 并将其转换为 Python 异常（通常是 PanicException），因此普通 panic 不会直接让解释器崩溃。但这不等于可以随意 unwrap()：异常类型对 Python 调用方并不友好，堆栈信息也未必完整；如果编译配置改为 panic = "abort"，或者在无法 unwind 的场景触发 panic，进程会直接退出。正确做法是把可预期的错误放进 PyResult，只在“确实不应该发生”的不变量上使用 panic!，并保证发布构建不关闭 unwind。

此外要留意引用环。Python 的循环垃圾回收器能处理纯 Python 对象之间的环，但 Rust 结构体内部持有的 Py 引用对它并不可见；当 Python 对象与 Rust 对象互相引用时，需要为 #[pyclass] 实现 __traverse__ 与 __clear__，或者干脆避免这种双向持有。长期运行的服务里，这类泄漏往往表现为内存缓慢上涨，重启后恢复，很难通过一次压测发现。

部署、可观测性与错误排查

容器部署的常见做法是把构建与运行分开。wheel 在 CI 的 manylinux 环境里构建，运行镜像只负责安装，不携带 Rust 工具链：

这样镜像更小，攻击面也更少。基础镜像的 Python 小版本必须与 wheel 匹配：运行镜像从 3.9 升到 3.10 时，非 abi3 的扩展必须重新构建，否则导入阶段就会失败。即使使用 abi3，也建议在启动时调用一个 version() 函数，核对扩展版本与预期是否一致，让问题在健康检查阶段暴露，而不是在第一个请求到来时才发现。

多进程部署还有一个容易忽略的细节。若 Python 侧用多个 worker 进程，而 Rust 扩展内部又创建了全局线程池，实际线程数会是两者相乘，容易把 CPU 打满并放大上下文切换。此时要么限制每个进程的线程数，要么让 Rust 只做单线程计算，把并行度交给进程层统一管理。扩展参数中的线程数、批大小也应做成可配置项，而不是写死在代码里。

滚动发布时还要考虑扩展与 Python 代码的版本耦合。若新版本扩展改了函数签名，而旧版 Python 代码仍在运行，调用会直接抛 TypeError；灰度期间新旧实例并存，接口应保持向后兼容，或者让扩展同时提供新旧两个入口，待全部实例升级后再移除旧入口。wheel 进入私有索引后，建议用内容哈希或构建号区分，避免缓存命中旧包导致“明明发布了却没生效”。

可观测性方面，跨语言调用不会自动传递追踪上下文。请求 ID、租户 ID 这类字段应作为显式参数传入 Rust，或者在边界处写入结构化日志，再由 Python 侧统一收集。Rust 的 log 记录可以通过日志桥接库转发到 Python 的 logging，但要注意级别映射和格式化开销；更稳妥的做法是只把关键计数与耗时通过函数暴露给 Python，由现有指标体系统一上报。

排查问题时可以按层定位。ImportError 通常指向模块名、包布局或 ABI 不匹配；导入成功但调用即崩溃，先看是否触发了 panic、栈溢出或非法内存访问，再检查 dmesg 与 core dump；线上卡顿可以用 py-spy 采样，确认线程是卡在 GIL、锁还是实际计算上。构建期的问题则要检查 PYO3_PYTHON 是否指向了预期的解释器，以及 .so 是否错误地链接了 libpython。把这些问题当作部署检查表的一部分，比事后猜测更有效。

常见坑与排查清单

混合部署的问题大多不是“Rust 写错了”，而是边界没有被当成一等公民。下面几类最常出现。

GIL 没有释放。表现为加机器、加线程都没有提升，CPU 始终只跑满一个核。用 py-spy 采样通常能看到多个线程停在等待 GIL 的位置。修复方式是 allow_threads，但要先确认闭包内没有访问任何 Python 对象；把 &PyAny 捕获进去会直接编译失败，这其实是类型系统在帮忙。

转换比计算还贵。典型写法是 Python 循环里逐条调用 Rust，或者每次传一个嵌套字典。单次调用看似很快，累计起来却不如原来的 Python 实现。应先合并接口：一次传数组、一次传字节缓冲，返回结果也尽量用连续内存。

panic 越过边界。对用户输入 unwrap()、数组下标越界、调试构建下的整数溢出，都会触发 panic。PyO3 会把它转成 PanicException，但调用方通常没有处理这种异常的习惯；若发布配置使用 panic = "abort"，进程直接退出。把可预期错误改为 PyResult，并在入口处做参数校验，是最省事的做法。

Python 版本与 ABI 不匹配。本地用 3.10 构建，镜像里却是 3.9；或者 wheel 文件名写着 cp310，却装进 3.9 的环境。abi3 能缓解这个问题，但最低版本设置错误同样会导致安装失败。让 CI 在目标 Python 版本上构建并安装测试，比在文档里写“请使用 3.9”可靠得多。

wheel 平台标签不对。在较新的 Ubuntu 上直接构建，二进制会依赖较高版本的 glibc，装进旧基础镜像后报 GLIBC_2.xx not found。应在 manylinux2014 容器中构建，并用 auditwheel 检查标签；macOS 与 Windows 也要分别出包，不能指望一个平台产物通吃。

调试手段缺失。cProfile 只能看到扩展调用的总耗时，release 构建又常把符号剥掉，出现崩溃时只剩一个地址。建议在性能分析用的构建里保留调试符号，准备好 py-spy、gdb 与 core dump 的采集流程，并在绑定层记录关键参数的摘要。

模块名三处不一致。Cargo.toml 的 [lib] name、#[pymodule] 的函数名、maturin 的 module-name 必须能对上；此外，扩展模块要打开 extension-module 特性，否则在某些平台上会尝试链接 libpython，导致导入时报符号错误。这类问题在本地开发环境不一定复现，发布前用干净容器验证一次最稳。

把上述内容固化成检查清单：调用频次与数据量是否匹配形态，热点函数是否释放 GIL，接口是否批量，错误是否都走 PyResult，wheel 是否在目标平台与 Python 版本上装过，镜像里是否残留工具链，线程数是否被重复放大。清单不长，但能挡住大部分上线后才会暴露的问题。

小结

Rust 与 Python 的混合不是“用更快的语言重写”，而是在合适的边界上做分工。进程内的扩展模块延迟最低，但耦合最深；独立服务隔离最好，但要把序列化与运维成本算进去；嵌入方向只适合特定工具场景。PyO3 把函数、模块、类型和异常映射成 Python 能理解的形式，真正决定体验的是 GIL 与数据转换：计算期间能否释放锁、一次调用搬运多少数据，往往比 Rust 代码本身更影响结果。工程上要用 maturin 把 wheel 做对，用 abi3 与 manylinux 控制兼容性，用 pytest 同时覆盖 Rust 算法与 Python 边界。落地时不妨从一个小而纯的函数开始，先跑通构建、测试与发布链路，再逐步扩大边界；比起一次性迁移一个大模块，这种做法更容易定位问题，也更容易说服团队。最后，把版本、线程数和可观测性写进部署检查表，混合系统才能稳定地跑在生产环境里。
