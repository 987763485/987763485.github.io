防腐层与上下文映射

本文属于《Go 微服务架构》第 3/35 篇
上一篇系列目录下一篇

当一个订单服务需要对接支付、库存、物流三个外部系统时，最省事的做法是把对方的响应结构直接搬进自己的代码：字段名照抄，状态码照用，错误信息原样透传。短期内这确实快，却把三个外部系统的模型悄悄焊进了自己的领域，任何一次对方升级、字段改义或者接口下线，都会沿着调用链震荡到核心业务；防腐层（Anti-Corruption Layer，ACL）就是在这个接缝上刻意加上的一层翻译与隔离，让外部模型进不来，让自己的领域模型保持干净。

本文面向已经按限界上下文组织代码、正准备或正在与外部系统集成的后端开发者。我们会先说明防腐层要解决的三类问题，再讨论它该放在分层架构的什么位置、DTO 与领域模型如何转换、契约与版本怎么管，随后把上下文映射的七种关系逐一拆开，结合团队权力结构谈选择，最后落到事件与同步调用的取舍、测试、成本边界与常见坑。

为什么需要防腐层

外部系统不会按我们的领域语言说话。支付网关关心的是商户号、渠道流水和清算批次，物流平台关心的是运单号、网点编码和签收状态，它们各自有一整套自洽的概念体系。两个上下文一旦直接对接，弱的那个往往会被强的那个同化：对方的字段名进入我们的结构体，对方的状态机进入我们的判断分支，对方的错误码进入我们的接口返回值。防腐层存在的理由，归结起来是三类压力。

第一类是下游模型污染。对接方提供的 SDK 或 JSON 结构以它自己的业务为中心，字段可能叫 user_type、biz_code、trade_status，状态用数字表示，金额用字符串表示，时间戳用毫秒表示。若把这些结构直接传进应用服务和领域服务，领域模型的词汇就会被悄悄替换。原本清晰的“订单已支付”变成对 trade_status == 2 的判断，原本的“应付金额”变成对 total_fee 字符串的除法。几个月后，团队讨论业务时说的都是对方的术语，领域模型名存实亡。

第二类是外部系统变更。供应商升级接口、调整字段语义、下线旧版本、更换鉴权方式，都是常态。没有边界时，每一次变更都要沿着调用链排查到领域层，改动面不可控；有了边界，变更被限制在一个适配器包里，领域模型不动，测试范围也清晰。变更本身不可怕，可怕的是变更的影响半径无法估计。

第三类是遗留系统。老系统可能只提供 SOAP 接口、定长报文或者需要人工导出导入的文件，字段含义靠一份多年前的文档口口相传。我们既不能重写它，也不该让它的历史包袱进入新系统。防腐层可以把这些古怪的协议和编码挡在外面，对内呈现一个符合当前领域语言的接口。

防腐层不是“多包一层显得规范”，而是有意识的成本支出：承认两个上下文存在语义鸿沟，在边界上一次性填平，而不是让鸿沟在系统内扩散。DDD 基础不在本文展开，这里只聚焦接缝。

防腐层的职责与位置

防腐层通常承担四件事，缺一不可。

翻译是核心。把对方的字段、枚举、单位、时区、标识体系转换成我方领域语言。金额从“分”的整数转换成 Money，状态从渠道码转换成领域枚举，时间从本地时间转换成带时区的时间点，用户标识从渠道会员号转换成我方的客户 ID。翻译不只是改名字，更是改语义。

隔离是目的。领域层只能看到自己定义的端口，看不到任何外部 SDK 的类型。外部依赖被关在适配器里，编译期的依赖方向始终指向内部。这样一来，替换供应商、增加灰度通道、在测试里注入假实现，都不会触碰领域代码。

适配处理协议层面的差异。对方是 REST 还是 gRPC，是否要求签名，是否分页，是否有 QPS 限制，超时和重试怎么设，这些都属于适配器的工作。适配器可以组合多个外部调用，把对方“先查再扣”的两步接口包装成一个原子语义，但不应替领域做业务决策。

校验守在门口。外部数据进来先做结构与语义校验：必填字段是否存在，枚举是否在已知集合内，金额是否为负，时间是否越界。校验失败要明确报错，而不是用零值蒙混过关。业务规则仍然属于领域层，边界只负责拒绝明显不合法、无法翻译的输入。

从分层看，端口接口由领域层定义，应用层负责编排用例，防腐层作为基础设施的一部分实现端口。依赖关系是领域层定义接口、适配器实现接口，而不是适配器定义接口、领域层去依赖。下面是一个只示意结构的 Go 例子：

DTO 与领域模型的转换

DTO 的职责是承载数据，它没有行为，也不保护任何不变量；领域模型的职责恰恰相反，它用构造函数、工厂方法和值对象守住业务规则。把两者混为一谈，常见的结果是领域对象上挂满 JSON 标签，或者 DTO 被当作实体在仓储里传来传去。防腐层要做的，是在两者之间建立一条显式、可测试的转换通道。

转换有两个方向。入站方向把外部响应或消息转换成领域对象，出站方向把领域对象转换成对方要求的请求结构。两个方向都应由防腐层负责，领域层不出现任何外部 DTO 的类型。下面是一个入站转换的示意：

手写映射看起来笨，却把每个字段的来源和语义摆在明面上，评审时能一眼看出漏了哪个字段、错了哪个单位。反射或自动映射适合纯机械的字段复制，一旦涉及枚举、金额、时间、标识转换，就应显式写出来。映射代码还要守几条纪律：可选字段要能区分“缺失”和“零值”，在 Go 里可用指针或专门的可选类型；出站映射只暴露契约允许的字段，不要把内部主键、审计字段顺手带出去；映射失败必须返回错误，不能拿一个字段残缺的对象继续往下走。

有些转换需要查库，比如渠道商品编码换成内部商品 ID。这类转换不适合塞进领域对象的构造函数，也不该让领域层依赖仓储。常见做法是在应用层编排：防腐层完成结构和值的翻译，应用服务调用仓储补齐关联，最后交给领域工厂组装。层次分清，测试才好写。

接口契约与版本

契约不只是字段列表，至少要说清楚：字段含义与单位、哪些字段可能为空、枚举的取值范围与扩展规则、错误码分类、是否幂等、超时与重试约定、分页与排序语义、以及调用频率限制。很多集成事故不是因为字段对不上，而是因为双方对“成功”“已退款”“处理中”的理解不一致。

版本管理的第一原则是不要复用旧字段表达新语义：字段名保留、含义改变，对下游就是破坏性变更。新增字段通常被认为是兼容的，但前提是消费方真的忽略未知字段；如果己方解析器对未知字段直接报错，这个前提就不成立。枚举扩展更危险：对方增加一个状态值，己方的穷尽分支如果没有默认处理，就会在运行时抛错。映射表遇到未知状态应显式失败并告警，而不是猜测默认值。

版本号放在路径、请求头还是参数里，是团队约定问题，关键是同一时间只维护少量受支持的版本，并给出明确的废弃窗口。对消费方而言，最稳妥的策略是让防腐层固定在一个已知版本上，升级时把契约测试跑一遍，确认映射表覆盖了新版本的变化。供应商发布新版本时，适配器是唯一需要改动的包，这就是隔离带来的实际收益。

错误码也需要翻译。对方返回的 E10023 对领域层没有意义，对用户更没有意义。防腐层应把它归类成领域可理解的错误类型：可重试的暂时性失败、需要用户操作的失败、不可恢复的配置错误，同时保留原始错误信息用于日志排查。若把外部错误码原样透传到前端，等于把对方的内部实现暴露给了自己的用户，后续对方一改码，前端判断全部失效。

上下文映射的七种关系

上下文映射（Context Map）画的不是部署图或调用链，而是限界上下文之间的关系，以及背后的团队协作方式。它要回答：哪些模型需要翻译，责任在谁，双方对契约有多大的话语权。Eric Evans 在 DDD 原著里给出了几种典型关系，后来被社区反复引用，逐渐固定为七种。理解它们的关键，是看清每种关系把耦合放在了哪里、把成本留给了谁。

    A[订单上下文] -->|防腐层| B[支付渠道]
    A -->|客户-供应商| C[库存上下文]
    C -->|开放主机服务与发布语言| D[多个下游]
    A -.->|各行其道| E[旧报表系统]

共享内核（Shared Kernel） 指两个上下文共同拥有并共同维护一小块模型或代码，比如统一的地址值对象、金额类型或领域事件基类。它的好处是避免重复，双方对核心概念的理解一致；代价是强耦合，任何一方修改共享部分都要双方确认、一起发布。共享内核必须小，最好有独立的版本和测试，否则它会慢慢膨胀成一个人人依赖却没人负责的公共垃圾场。

客户-供应商（Customer-Supplier） 中，下游是客户，上游是供应商。下游把需求提给上游，上游在排期和设计时给予考虑，双方通过协商确定契约。这是最健康的上下游关系，但它有前提：上游愿意为下游的需求投入，并且有稳定的沟通渠道。如果上游只是口头答应、实际从不排期，所谓客户-供应商就退化成了遵奉者。

遵奉者（Conformist） 指下游放弃自己的模型，直接遵从上游的模型。它适合上游模型稳定、语义与下游足够接近、且下游没有谈判筹码的场景。遵奉者省掉了翻译层，集成成本最低，但下游的领域语言会被上游侵蚀。选择它应该是明确的管理决策，而不是不知不觉地发生。

防腐层（Anti-Corruption Layer） 是下游主动建立翻译与隔离层，把上游模型挡在门外。它给下游最大的自主权，代价是要维护映射、契约测试和额外的运行开销。防腐层通常出现在下游无法影响上游、而上游模型又与本方领域差异较大的地方，比如对接外部支付渠道、老旧 ERP 或者第三方物流平台。

开放主机服务（Open Host Service） 是上游为众多消费者提供的一套稳定、公开、有文档的接口。它把集成能力产品化，消费者不需要各自理解上游的内部模型。开放主机服务往往和发布语言一起出现，前者是服务形态，后者是语言规范。

发布语言（Published Language） 是一套双方共享、文档化、可演进的交换语言，例如用 JSON Schema、Protocol Buffers 或 XML Schema 定义的消息格式。好的发布语言独立于任何一方的内部模型，有明确的版本和兼容规则。事件集成尤其需要它，否则每个消费者都在猜字段含义。

各行其道（Separate Ways） 指两个上下文干脆不集成，各自实现所需功能，或者通过人工流程衔接。它听起来像放弃，其实常常理性：当集成成本高于重复实现，或两边节奏完全对不上时，强行集成只会制造脆弱的接缝。判断标准是集成的业务价值，而不是“系统之间应该连通”这种直觉。

同一个系统里往往同时存在多种关系：订单对支付用防腐层，对库存用客户-供应商，对报表团队提供开放主机服务，对无人维护的旧报表系统则各行其道。映射的价值不在于给每个接缝贴标签，而在于把“谁依赖谁、谁有话语权、翻译由谁负责”摆到桌面上。

关系选择与团队权力结构

选择哪种关系，技术因素只占一半，另一半是团队之间的权力结构。上游团队是否愿意为下游排期，下游是否有能力维护翻译层，双方是否在同一个发布节奏里，这些现实条件往往比模型差异更能决定结果。

下游对上游几乎没有影响力时，只有两条路：遵奉者或防腐层。前者便宜，却把上游的变更风险直接引入领域；后者贵，但把风险关在边界内。若上游模型稳定、变更频率低、语义差异小，遵奉者是合理选择；若上游经常变、语义古怪、且下游领域是核心竞争力所在，防腐层几乎必然值得。

当下游有足够的话语权时，客户-供应商是更好的关系。它把集成从“下游猜测上游”变成“双方协商契约”，但需要制度保障：需求进入上游的排期、契约变更提前通知、双方在 CI 里跑同一套契约测试。没有这些保障，客户-供应商只是一句客气的称呼。

共享内核只适合同一级别的团队，双方要有共同的代码所有权、统一的发布节奏和明确的变更流程。跨公司、跨事业部的共享内核几乎注定失败，因为没人能为另一方的修改负责。开放主机服务与发布语言适合平台型团队：上游把接口当产品运营，下游按文档接入，通过版本和废弃策略解耦。

还要认清：防腐层不能消除组织依赖，只能让依赖可控。上游不提供文档、不通知变更、不守契约，防腐层照样疲于奔命。技术隔离必须配合契约管理和沟通机制，否则只是把痛苦从领域层转移到适配器层。康威定律在这里体现得淋漓尽致：上下文映射画出来的，常常就是组织架构图。

事件集成与同步调用的取舍

防腐层不只服务于同步调用。上下文之间用事件集成时，同样需要一个翻译边界，只是边界的位置从“请求响应之间”移到了“消息的生产与消费之间”。

同步调用的优点是确定性：同一请求里拿到结果，成功失败立即可知，一致性容易保证。缺点是时间耦合和故障传导：下游变慢，上游跟着变慢；下游超时，重试可能放大流量；下游不可用，核心链路直接中断。防腐层在同步路径上还要处理超时、重试、熔断和错误归类，这些策略应集中在适配器里。

事件集成的优点正好相反：生产方只管发布事实，消费方按自己的节奏处理，双方在时间上解耦，故障也不会立刻沿着调用链回传。代价是最终一致性、重复投递、乱序和消息积压。消费方的防腐层要处理这些问题：把外部事件转换成内部命令或领域事件，按事件 ID 去重，按业务键保证顺序，遇到无法翻译的消息转入死信队列并告警。

事件格式应当被当作发布语言来设计，而不是把内部领域事件对象直接序列化出去。一个可演进的事件至少应包含事件 ID、事件类型、发生时间、版本号、聚合标识和业务载荷；载荷只放消费者真正需要的字段，不要把内部数据库结构整表倒出去。消费方的映射代码同样要显式处理未知事件类型和未知字段，不能因为对方新增了一个事件就崩溃。

选择同步还是事件，可以问三个问题。第一，当前操作是否必须立刻知道结果？支付扣款、库存预占这类需要当场决策的动作通常走同步。第二，失败是否必须让主流程失败？发积分、写审计、通知下游这类旁路动作适合事件。第三，双方能否接受一段时间的数据不一致？能，才谈得上异步。混合形态也常见：主链路同步拿到结果，成功后再发事件驱动旁路，比纯事件编排更易排查。

防腐层的测试

防腐层代码不复杂，却容易在细节上出错，测试要覆盖三类内容：映射、契约和依赖方向。

映射测试是主体，用表驱动把每个外部状态、每种边界值过一遍：未知枚举是否报错，缺失字段是否被识别，金额单位是否换算正确，时间戳的时区是否一致，空值与零值是否被区分，数值溢出是否被拦截。映射测试不需要网络，输入是外部 DTO，输出是领域对象或错误，跑得飞快，应成为 CI 的常规部分。

契约测试解决“双方理解是否一致”。消费者驱动的契约测试把下游期望固化成契约文件，上游在 CI 中验证；一旦改了字段或语义，验证先失败，而不是线上才暴露。即使不用契约工具，也应把对方的样例响应保存成夹具，升级时回归比对。测试不要依赖真实第三方，用桩服务模拟成功、失败、超时和畸形响应，才能覆盖异常路径。

依赖方向的测试常被忽略。可用静态检查或架构测试断言领域包不导入外部 SDK、不出现外部 DTO 类型。这类测试看似形式主义，却能挡住“临时先引一下，以后再改”的退化。防腐层的价值在于长期守住边界，而边界往往就是这样一点点被侵蚀的。

性能、边界与落地步骤

防腐层会带来额外开销：对象转换、可能的序列化、额外的内存分配，以及多一跳网络调用。与网络往返相比通常可以忽略；但在极高并发的本地调用链上，反射映射和频繁分配会被放大。优化应先测量，再针对热点做手写转换或缓存元数据，不必为了性能牺牲边界。冗余成本同样真实：两套模型、映射代码、契约文档都要维护。控制成本的办法是缩小范围，只翻译真正跨越边界的概念，而不是把对方每个端点都包装一遍。

有些场景不该加防腐层。同一个上下文内部模块间传 DTO 不需要 ACL，加了只是多一层；一次性迁移脚本、临时对账工具用完即弃，抽象反而拖慢进度；上游模型稳定、语义接近且团队明确选择遵奉者时，直接使用对方模型也可接受。判断标准不是“有没有外部依赖”，而是“变更是否会伤到核心领域，翻译成本是否低于污染成本”。

落地时可以按以下顺序推进。先画上下文映射，标出每个外部上下文的变更频率、话语权和模型差异；再在领域层用本方语言定义端口，明确输入输出和错误类型；接着在适配器层实现防腐层，显式编写 DTO、映射表和错误翻译；然后补齐契约文档、版本策略和映射测试；最后给翻译失败、未知枚举、契约校验失败加上监控指标，定期回看哪些映射在腐化。核心是先把边界和语言定下来，再写代码。

常见坑

防腐层变成第二套业务逻辑。 最常见也最危险。适配器里开始计算折扣、判断订单能否取消、决定重试几次业务操作，领域层反而被架空。防腐层只做翻译、隔离、适配和输入校验，业务规则必须留在领域层；一旦发现适配器里出现“如果用户是金卡且金额大于多少”，就该把它搬回去。

映射遗漏字段。 对方新增了字段，映射表没更新，默认零值一路流进领域，直到报表对不上才被发现。缓解手段是契约测试、对未知字段的策略、以及对关键字段的非空校验，而不是指望每次升级都有人记得改映射。

双向依赖。 领域层为了图方便导入了适配器或外部 SDK，依赖方向反转，防腐层名存实亡。用静态检查守住这条线，比口头约定可靠。

外部模型直接进领域层。 领域对象上挂 JSON 标签、数据库标签，或者方法参数直接使用外部 DTO，都是同一种病的不同表现。领域模型应该只表达业务概念，序列化是边界的事。

错误码未翻译。 外部错误码透传到应用层甚至前端，对方一调整码表，所有判断失效。错误必须在边界归类，原始信息只进日志。

过度设计。 一个只有两个字段、一年也不变的配置接口，也套上端口、DTO、映射器和契约测试，成本远大于收益。防腐层是应对语义鸿沟的手段，不是所有集成的默认仪式。

小结

防腐层的本质，是在两个限界上下文的接缝上做一次有意识的翻译投资：用一层显式的映射与隔离，换来领域模型的干净和变更影响范围的可控。它适合上游不可控、模型差异大、且集成会长期存在的场景；同一个上下文内部、一次性任务、以及明确选择遵奉者的地方，则不必强加。落地时先定端口和契约，再写映射与错误翻译，最后用映射测试、契约测试和依赖检查守住边界。七种关系没有优劣，只有与团队权力结构和变更频率是否匹配。真正难的不是写出防腐层，而是长期不让它退化成第二套业务逻辑。
