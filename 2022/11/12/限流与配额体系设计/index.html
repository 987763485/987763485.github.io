限流与配额体系设计

一个接口每秒能承受多少次请求，和一个月允许某个客户用掉多少额度，是两件不同的事。前者是保护系统不被瞬时流量打垮，后者是商业合同里的数字，要计量、要对账、要能被审计。本文把这两件事放在同一张设计图上：先厘清限流与配额的边界，再讨论租户分层、计量与账期、分布式下的额度共享、公平性、429 的体验以及配额治理，最后给出一条可以分阶段落地的路径。读者应熟悉 HTTP 与 Redis 的基本用法；令牌桶、漏桶的算法推导留给同系列的其他篇目，本文只在额度共享的语境下讨论分布式取舍。

限流与配额的分工

很多团队把两者塞进同一个中间件，配置项都叫 limit，底层共用一份 Redis 计数。平时看不出问题，到了账单日或故障日就会同时暴露。把概念拆开，是设计配额体系的第一步。

瞬时保护：现在能不能进来

QPS 限流约束的是单位时间内新到达的请求数，窗口通常是秒级；并发限流约束的是同一时刻仍在处理中的请求数。两者回答的问题不同，不能互相替代。设想一个导出接口，单次请求要跑十几秒（示意值），QPS 只有个位数，可每个请求都占着一条数据库连接和一个工作协程，此时按 QPS 放行几乎不起作用，真正该管的是并发数。反过来，一个纯内存查询的接口单次耗时不到一毫秒，并发数天然很小，QPS 才是主要矛盾。

用利特尔法则看，系统中的平均请求数等于到达率乘以平均停留时间。下游变慢时，同样的 QPS 会让在途请求成倍增加，这就是“QPS 没超，服务却卡死”的常见原因。所以瞬时保护至少要两条线：入口按 QPS 削峰，执行层按并发数兜底。任何一条触发都应快速失败，而不是让请求无限排队——排队只是把拒绝推迟，并且额外占用了连接和内存。

周期额度：这个月还能用多少

日配额、月配额是累计量，窗口长、重置慢，语义接近预算。它管不住瞬时冲击：一个租户完全可以在凌晨用脚本把整月额度打光，第二天所有正常调用都被挡在门外。反过来，QPS 限流也替代不了配额：按每秒 10 次放行，一个月理论上能放过两千五百多万次，远超合同约定的量。两者是乘法关系，不是二选一。

用量计费：额度背后的账

配额是“允许用多少”，计量（metering）是“实际用了多少”，计费（billing）是“该收多少钱”。三件事的数据源可以不同，但必须能对上账。计量层记录可审计的用量事件，要求幂等、可重放、能按租户和时间段聚合；计费层在此之上套价格表、折扣、税费与账期规则。不少系统把配额计数器直接当账单，一旦 Redis 丢失或窗口错位，财务口径立刻失真。更稳妥的分工是：计数器只负责准入判断，账单以持久化的用量流水为准，两者通过日对账发现偏差。

一条请求要过几道关

把上述约束串起来，一个请求进入系统后通常要依次经过：身份识别与租户解析、周期配额预检、QPS 限流、并发信号量，最后才进入业务逻辑。顺序有讲究。身份必须最先确定，否则后面的计数没有归属；周期配额放在 QPS 之前，是因为它的判断更便宜，也更容易给出“额度已用完”这种明确原因；并发信号量放在最后，因为只有真正要占用稀缺资源时才需要它。任何一道拒绝都应返回同一个错误族，只是原因码不同，客户端才能据此决定是重试、降速还是找管理员提额。

注意最后一步：放行不等于用量成立。业务失败、参数校验不通过、下游超时，是否计入配额，必须事先定义清楚并写进文档。通行做法是“进入业务逻辑即计一次”，简单可解释；对按结果计费的产品，则要等业务成功后再记用量，并允许冲正。两种口径都能用，怕的是同一产品里混用。

租户分层与配额继承

档位是几条独立约束

产品页上通常只写一个“额度”，实现里却至少要拆成 QPS、并发、日配额、月配额四条线，外加一条超额策略。它们分别保护不同的东西，任何一条缺失都会留下缺口。

配额继承：从合同到 API key

一个租户往往有多个项目、环境和 API key。配额要有层级：合同或套餐挂在租户上，项目可以从父级划走一部分，key 再继承项目的剩余。常见两种切法。

其一是硬分割：父级把额度切成互不相交的份额，子级各用各的，父级只做总量校验。好处是账目清晰，某个项目打满不影响别人；坏处是闲置，A 项目月底剩一半，B 项目却因为自己那份用完而被拒。

其二是共享池：父级只有一个池子，子级各自设上限，但不预分额度，谁先用谁占。利用率高，代价是“先到先得”，需要给每个子级设封顶，否则一个大项目会把池子抽干。

无论哪种，生效额度都应能用一句话解释：取自身配置与所有祖先剩余额度中的最小值；被拒绝时，响应里要能指出是哪一层触发的。实现上不要在每个请求里沿树递归查询，而是在配置变更时把生效值算好写进缓存，请求路径只读一个扁平结果。覆盖项要带来源、操作人和过期时间，临时提额到期自动失效。

超额策略要写进合同

硬拒绝最好理解，也最容易引发投诉，适合免费档和成本敏感的资源。降速不是把速率降到零，而是降到一条基线，例如超过月额度后仍允许每秒若干次（示意值），保证客户还能导出数据、续费、联系支持。按量计费把超出的部分按单价结算，必须同时设置封顶和预警，否则一次配置错误可能产生一张天价账单。透支则类似信用卡：给一个信用额度，允许短期为负，到期未恢复就转为拒绝。

策略还要按资源类型区分。查询类接口可以软一些，写入和计费类接口应当硬一些；健康检查、鉴权、账单查询这类“客户必须能自救”的接口，最好完全不占配额。

变更要能复现历史

配额配置必须版本化：每次调整写入新记录，带生效区间，而不是原地覆盖。客户降档时，要明确剩余额度是清零、折算还是保留到期末；升级时多出来的额度从哪天算起。历史账单要能按当时的配额与价格重算，否则客诉时只能靠人工回忆。这一点在收入确认和审计里同样重要。

配额计量：窗口、时区与账期

精确计数与近似计数

精确计数要求每次请求都原子地改变一次计数，通常是一次 Redis 往返或一条数据库写入。近似计数则允许合并、采样或概率结构，例如本地累积一批再上报，或者用计数草图估算总量。两者的适用边界很清楚：准入判断可以近似，账单不能。近似值可以用来做容量规划、异常检测和用量预警，但不能出现在发票上。

即便是精确计数，也要区分“扣减成功”和“业务成功”。前者只说明额度被占用，后者才说明这次调用产生了价值。按调用计费的产品在入口扣减即可；按结果计费的产品要在业务完成后记账，并给失败调用留出冲正通道。

窗口怎么切

固定窗口实现最简单：键里带上日期或月份，读写各自加一。它的问题在边界：两个相邻窗口的交界处，瞬时通过量可能接近上限的两倍。对配额而言，窗口形状往往不是技术选择，而是合同条款：客户买的是“自然月 100 万次”，就不能为了实现优雅改成“任意连续 30 天”。工程上应优先保证口径与合同一致，再用突发额度、预检等手段弥补边界效应。

时区与账期

“11 月 1 日零点”在 UTC 和客户本地时间不是同一时刻，最东和最西的时区能差出二十多个小时。系统内部统一用 UTC 存储和计算，账期边界单独定义，并在控制台按客户时区展示。账期时区一旦写进合同就不要轻易改，改了必须公告并给出过渡方案。

夏令时是另一个坑：切换当天的本地日长可能是 23 或 25 小时，用“本地零点加 24 小时”推算窗口结束时间会错位。正确做法是只存 UTC 时间戳，展示层做时区转换，不要在业务逻辑里做本地时间的加减。月初、年末、闰年这些边界，应该由统一的账期库计算，而不是散落在各个服务里。

幂等、补量与回滚

计量流水必须幂等。客户端重试、网关重放、消息重复投递都会让同一次调用到达多次，扣减前要用请求 ID 或业务单号去重，去重窗口至少覆盖重试周期。账本只追加不修改：退款、补偿、故障返还都记成负数或独立的补量记录，附原因、操作人和关联工单。直接改历史数字，短期省事，长期无法审计。

补量（grant）和套餐额度要分开记：补量有来源、有有效期，可能只对某个项目生效；套餐额度随账期重置。二者相加才是可用余额。发生故障后从账本重建计数器时，要选一个明确的截止时间，并把这之前已经扣减但尚未落账的在途请求考虑进去，否则重建后会重复计数。

分布式配额：共享、预取与可接受的超发

共享计数的三种形态

最直接的做法是集中式计数：所有节点在每次请求前访问同一个 Redis 集群，按键的哈希分片，租户 ID 进键名。它的语义最准，代价是每个请求多一次网络往返，并且热点租户的键会集中到单个分片。对大客户做单独分片、把计数和明细分开，是常见的缓解手段。

第二种是本地预取，也叫额度租借。节点启动或本地额度用尽时，一次性从中心领取一批额度，例如一千次（示意值），之后在内存里扣减，用完再领。请求路径上没有网络调用，代价是额度被提前锁定：节点崩溃时，手里没用完的部分就悬空了。

第三种是分层混合：本地保留一个很小的突发桶，允许短时突发不打中心；持续流量仍然走全局计数。两层之间的换算关系必须写清楚，否则本地桶会成为绕过全局配额的后门。

预取批量怎么定

批量越大，中心压力越小，但故障时的损失越大，公平性也越粗：一个大客户可能因为在某个节点上预取了大批额度，让其他节点上的同租户请求被拒。可以用租约来约束：预取时在中心写一条带过期时间的租约记录，节点定期续租，崩溃后租约到期，未用完的额度自动回到池子。租约同时带来一个新风险——节点在租约过期后仍在服务，会把已经回收的额度再花一遍。解决办法是让节点在租约临近过期时停止放行并重新领取，或者引入单调递增的租约编号，中心拒绝旧编号的核销。

批量取值没有通用公式，可以从两个约束反推：单次故障最多损失多少额度可以接受，以及每秒允许多少次中心调用。取值应标注为估算，并通过故障演练验证。

节点故障与额度损失

节点失联后，它预取的额度有三种处理方式：直接作废，计入损耗；等租约到期后回收；由人工对账后补回。第一种最简单，但频繁发布或弹性缩容会持续漏损，客户会感觉额度“凭空少了”。第二种体验最好，实现也最复杂。第三种只适合低频的大额场景。

比回收更重要的是承认超发。多节点各自预取，最坏情况下集群可放行的量会超过名义配额，超出部分的上界大致是节点数乘以单节点剩余额度。这个上界应当被计算、被监控，并在合同或产品文档里说明“配额是软上限，计量以账单为准”。如果业务确实需要硬上限，就得放弃预取，回到每请求一次中心计数，用延迟换准确。

中心故障时怎么办

中心不可用时，QPS 限流通常选择 fail-open：用本地限流兜底，优先保可用性。付费配额则要分场景：按调用计费且金额敏感的接口，可以在无法确认余额时拒绝，避免产生无法计费的用量；普通接口可以放行并记录“待核销”流水，恢复后补扣。两种选择都要有开关和明确的告警，不能靠某个库的默认超时行为来决定。

公平性：单租户突发不应拖垮全体

全局配额挡不住“谁在用”

一个全局的每秒一万次配额，看起来公平，实际上是谁先发谁占满。某个租户的客户端陷入重试循环，或者跑了一次全量同步，就能把池子抽干，其他租户收到的全是 429。全局配额保护了系统，却没有保护租户之间的相对公平。

公平性需要两层约束：每个租户有自己的上限，所有租户共享一个全局上限。两个上限的比值决定了超卖程度。如果所有租户上限之和恰好等于全局上限，利用率会很低，因为很少有人在同一秒都用满；如果远大于全局上限，就要接受高峰期按某种规则分配，而不是先到先得。

按权重分配

按档位给权重是最直观的做法：企业档权重高，免费档权重低。全局资源紧张时，按权重分配放行名额，而不是让先到的请求全部通过。实现上可以用分层令牌桶：租户桶、档位桶、全局桶依次扣减，任何一层不足就拒绝；也可以用一个调度器按权重轮转。

权重只能解决常态下的分配。真正的难点是突发：某个租户在几秒内把速率提高两个数量级，此时按权重分配也来不及，需要更快的刹车。

隔离舱

按档位分池是最有效的隔离手段。免费档一个池，付费档一个池，企业客户独享集群或至少独享分片。这样免费档的异常流量再大，也只会打满自己的池子；企业客户愿意为确定性付费，就给他独立的爆炸半径。代价是资源利用率下降。

热点租户的单独处置

热点租户要靠监控发现：用量排名、环比突增、单租户占全局比例、重试率、错误率。发现之后，处置手段要分级：先临时降低该租户的 QPS 上限，再把它挪到独立分片，最后才考虑暂停。暂停是最后手段，因为它通常意味着客户业务中断，必须有人工确认和通知。

还有一个容易被忽略的放大器：重试。客户端在收到 429 后立即重试，会让实际到达量成倍增加，配额却没变。服务端应把重试请求单独计数，对同一租户的并发连接设上限，并在响应里给出明确的退避时间。否则限流越狠，重试越多，系统越忙。

用分布而不是均值衡量公平

只看全局成功率会掩盖问题：整体 99% 的成功率，可能意味着少数租户长期失败。应按租户统计成功率、P99 延迟和拒绝率的分布，观察是否有租户持续处于末尾。配额系统的一个关键指标是“被拒绝的租户数”而不是“被拒绝的请求数”，前者反映公平性，后者只反映容量。

降级与体验：429 之后发生什么

429 要带上可执行的信息

RFC 6585 定义了 429 Too Many Requests，语义是“请求过多”，但规范没有规定响应体格式和必须携带的头。工程上要补足三件事：机器可读的原因码、可供排查的请求 ID、以及客户端下一步该做什么。原因码至少要区分“瞬时速率超限”“周期配额耗尽”“并发超限”，因为前两者一个等几秒即可，另一个可能要等到下个月或找管理员。

Retry-After 是最重要的头，取自 RFC 7231，值可以是秒数或 HTTP 日期。优先用秒数：客户端与服务端的时钟未必同步，绝对时间容易算错。重置时间也要给，但应说明是“距重置还有多少秒”，而不是一个本地时间戳。限流相关的 RateLimit-Limit、RateLimit-Remaining、RateLimit-Reset 在 2022 年仍是 IETF 草案，各家实现的前缀和语义不完全一致，对外承诺前要确认客户端真的解析。

不要把配额超限包装成 200 加错误码，也不要一律返回 503。503 的含义是服务整体不可用，负载均衡器和客户端会按另一套策略重试，可能把流量打到别的实例，反而加剧问题；429 才表示“你的用量超了”，责任和处置都在调用方。

客户端退避与幂等

客户端收到 429 后应立即重试吗？不应该。正确做法是遵循 Retry-After，在其基础上加随机抖动，并采用指数退避，设置最大重试次数和总时限。对非幂等写操作，重试必须带幂等键，否则一次超时可能变成两笔订单。SDK 应内置这套逻辑，而不是把责任留给每个接入方。

配额预警要跑在拒绝之前

预警的价值在于给客户留出行动时间。常用阈值是额度的 50%、80%、100%（示意值），但更有用的是消耗速率预测：按当前速度，额度还能撑多久。预警要发给真正能处理的人，包括租户管理员和客户成功团队；控制台要有常驻提示，API 要能查询剩余量。对硬拒绝档位，预警尤其重要，因为一旦触顶就是业务中断。拒绝之外，降速也是一种降级手段，但实现要克制：排队会占用连接和内存，队列长度必须有上限，等待超过阈值仍然返回 429。

配额治理：申请、审批与审计

申请与审批

默认配额应当偏紧，提额走申请。申请表单至少收集用途、预估调用量和峰值、需要的期限、涉及的接口；小额度可以自动批准，大额度进入分级审批，超大规模需要架构与财务共同确认。临时活动类需求发带过期时间的临时额度，到期自动回收。审批要有明确的时限和驳回理由。

异常用量检测

配额系统天然拥有用量数据，可以顺势做异常检测：用量环比突增、单一接口占比异常、非工作时段持续调用、同一凭证从大量 IP 发起、错误率与重试率同时上升。检测到异常时，优先限速和通知，而不是直接封禁，因为误判的代价很高。规则要能解释，告警要带上下文，处置动作要留痕。

变更审计

每一次配额调整都要记录：谁、何时、把哪个层级的哪个字段从多少改到多少、依据哪张工单、谁批准的。审计日志只追加，管理面与数据面分离，大额调整双人复核。事故复盘时，这份日志能回答“额度是什么时候被放开的”。

小结

限流与配额解决的是两个时间尺度上的问题：前者在秒级保护系统，后者在账期上约束用量，二者不能互相替代。产品化的难点不在计数器，而在口径：额度如何继承、窗口按哪个时区切、失败调用是否计量、超发是否可接受，这些决定必须先写进合同和文档，再落到代码。工程上可以用 Redis 做准入、数据库做账本，用预取降低延迟，同时明确预取带来的额度损失与超发上界。公平性靠“租户上限加全局上限”和隔离舱保证，体验靠清晰的 429、Retry-After 与提前预警保证。最后，配额是治理对象，申请、审批、审计和异常检测缺一不可。
