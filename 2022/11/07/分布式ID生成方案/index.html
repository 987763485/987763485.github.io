分布式 ID 生成方案

本文属于《Go 微服务架构》第 30/35 篇
上一篇系列目录下一篇

订单号、消息 ID、分库分表后的主键，看起来只是“一串数字”，落到分布式环境里却处处是坑：重复、乱序、索引膨胀、时钟回拨。本文把 UUID、数据库自增与号段、Snowflake、Redis 与 ZooKeeper 五类做法放在同一张桌子上比较，给出一个带时钟回拨检测的 Go 实现，并讨论上线之后该盯哪些指标。适合正在做 ID 选型，或者正被 ID 冲突、索引碎片困扰的后端开发者。

五个维度：先想清楚要什么

在动手写代码之前，先把需求拆成可以打分的维度，选型就不会退化成“我觉得 Snowflake 更高级”。

  • 全局唯一：这是底线。单机自增一旦遇到多实例部署就失效；分库分表之后，每张表各自自增，主键必然冲突。
  • 趋势递增：InnoDB 的聚簇索引按主键顺序组织数据。随机主键会让插入落在 B+ 树的任意位置，引发页分裂与空间碎片，二级索引还要为每个主键存一份副本。
  • 高可用与低延迟：ID 往往在交易主链路上，生成一次如果是一次远程调用，那么 ID 服务的抖动就直接等于下单失败，延迟也会叠加到每一次写入上。
  • 信息安全：连续的整数会泄露业务量，今天的订单号减去昨天的，大致就是日订单量；编号还容易被遍历。对外暴露的编号需要不可枚举。
  • 长度可控：BIGINT 占 8 字节，36 个字符的 UUID 字符串要占 36 字节，放进索引、缓存键、URL 里，成本差好几倍。

除这五项之外，还有两个隐性问题值得提前确认：ID 是否需要携带时间信息，便于按时间范围查询与排查问题；是否需要携带分片信息，让分库分表中间件直接从 ID 路由到目标库。这两点会直接决定后面方案的取舍。

UUID：格式统一，代价落在索引上

UUID 是 RFC 4122 定义的 128 位标识，最常用的两个版本结构差别很大。

v1 把时间放在前面：60 位时间戳（以 100 纳秒为单位，从 1582 年起算）、14 位时钟序列、48 位节点标识（通常是 MAC 地址）。同一台机器生成的 v1 大致按时间递增，但 MAC 地址被写进了 ID，等于把硬件信息泄露给外部；时钟序列只有 14 位，多台机器在同一时刻仍可能碰撞。

v4 除版本位与变体位外，剩下 122 位全部随机。碰撞概率用生日问题估算，要生成大约 2 的 61 次方个才有较明显的碰撞风险，工程上可以认为不会重复；代价是完全无序。

问题集中体现在三处。其一，无序：作为 InnoDB 主键，每一次插入都可能落在 B+ 树中间的页上，造成写入放大与缓存命中率下降，数据量大之后尤其明显。其二，长度：标准写法 36 个字符，去掉连字符 32 个，存成 BINARY(16) 也要 16 字节，是 BIGINT 的两倍，而每个二级索引都要带上主键。其三，不可读也不可排序，人眼无法从编号判断先后。

因此 UUID 更适合“先有 ID，再有服务”的场景：客户端离线生成、日志与链路追踪的 trace id、对象存储的文件名。这类场景不按 ID 排序，写入也分散。如果确实要拿它当主键，至少把字符串改成 BINARY(16)，或者把 v1 的时间高位搬到最前面来改善局部性；前者解决不了无序，后者只是缓解。

数据库自增与号段模式

最朴素的做法是交给数据库：AUTO_INCREMENT 保证单表唯一，严格递增，占 8 字节，几乎零成本。它的边界也很清楚：写入集中在一个库，ID 生成和业务写入抢同一份连接与锁；一旦分库分表，每张表各自从 1 开始，冲突立刻出现。

多实例步长是常见的补救：设置 auto_increment_increment 与 auto_increment_offset，让第 i 台只生成 i、i + N、i + 2N 这样的数列，各实例互不重叠。代价是扩容时要改步长并重新分配 offset，改动期间若没停写就可能撞号，实践中出过不少事故。双主部署（一台奇数、一台偶数）是同一思路的简化版。

美团的 Leaf-segments 在这个基础上加了两件事。一是双 buffer：当前号段消耗掉一小段（Leaf 取 10%）时就异步预取下一段，正常情况下取号完全不用等数据库，消除了切换号段时的毛刺。二是动态步长：根据上一段的消耗速度调整 step，流量涨了少跑几趟数据库，流量落了也不至于浪费太多号段。

容灾要单独想。数据库短暂不可用时，双 buffer 能撑过一个预取周期；如果长时间不可用，号段耗尽之后整个服务就无法发号。常见的兜底是每个实例本地再缓存一个紧急号段，或者部署多套独立取号库并按业务线拆分。另一个容易被忽略的点是重启：进程退出时内存里剩余的号段会被丢弃，ID 因此出现空洞，这套方案只能保证趋势递增，不能保证连续。

Snowflake：把时间、机器与序列编进 ID

Snowflake 由 Twitter 提出，思路是把 64 位切成三段：1 位符号位固定为 0，41 位毫秒时间戳（相对自定义起点，可用约 69 年），10 位机器标识（最多 1024 个节点），12 位毫秒内序列（每毫秒 4096 个）。生成时把三段左移拼接，结果仍是一个 8 字节整数。

好处很直接：完全本地生成，一次取号没有网络往返；按时间趋势递增，写入局部性好；ID 自带时间，按 ID 范围扫描约等于按时间扫描。代价是它默认了两件事成立：机器标识不重复，时钟只往前走。

机器标识的分配是第一个工程问题。写死在配置文件里，扩容与迁移都要人工介入；按 IP 取模，容器重建后地址变化就会撞号；比较稳妥的是启动时向 ZooKeeper、etcd 或数据库注册一个序号，进程退出时释放，Kubernetes 里则用 StatefulSet 的固定序号。10 位还可以再切分，比如 3 位机房加 7 位机器，为多机房留出空间。

时钟回拨是第二个，也是最容易出事的问题。NTP 校准、虚拟机热迁移、人工改时间，都可能让系统时钟倒退。如果代码直接拿当前时间继续生成，就会和回拨之前同一毫秒内发出的 ID 撞车。处理方式有三类：

  1. 等待：回拨幅度很小（几毫秒）时，睡到上一次的时间戳再继续，对调用方几乎无感。
  2. 报错：回拨超过阈值就直接返回错误，让上层重试或走降级分支。这比悄悄发出重复 ID 安全得多。
  3. 借用未来：让逻辑时间继续往前推，不再跟随物理时钟。实现简单，但物理时钟没追上之前每次都要等待，等于把问题延后。

Redis 与 ZooKeeper：借用现成的协调者

如果团队已经有 Redis，用 INCR 是最省事的做法：INCR order_id 返回单调递增的整数，单线程模型保证原子性，延迟在亚毫秒级。问题出在持久化与复制上：AOF 默认每秒刷盘，主从复制是异步的，主库宕机切到从库时，已经返回给客户端的号可能还没传过去，切换之后就会重发。要缓解，可以 INCRBY 一次取一段在本地分配，把重复窗口缩小到“丢失的那一段”；也可以给 ID 加机房前缀，从结构上避免跨机房重复。集群模式下 key 必须落在同一个 slot，否则 INCR 会打到不同节点，通常用 hash tag 固定。

ZooKeeper 的顺序节点走的是另一条路：对父节点创建带 sequential 标志的子节点，服务端返回带单调序号的节点名。它由 ZAB 协议保证多数派写入，顺序是全局的，会话失效也不会让序号回退。代价是每次取号都要一次写请求，包含 leader 转发与多数派确认，吞吐和延迟都远不如本地生成，只适合低频场景，例如分配机器标识、生成批次号。

这两类方案的共同点，是把唯一性托付给一个有状态的协调者，用网络往返和可用性换来了简单与强顺序；而 Snowflake 与号段把唯一性建立在空间划分上，用机器标识管理和时钟假设换来了本地生成的低延迟。选型本质上是选愿意承担哪一种代价。

对比、监控与多机房

把前面几类方案放进一张表，差异会更直观。表中的长度指存储占用，实际以业务字段定义为准：

方案 有序性 长度 外部依赖 容灾 适用场景
UUID v4 无序 36 字符或 16 字节 无 天然去中心 客户端生成、trace id
数据库自增 严格递增 8 字节 数据库 差，依赖主从切换 单库、中小规模
号段模式 趋势递增 8 字节 数据库 较好，双 buffer 兜底 订单、分库分表主键
Snowflake 趋势递增 8 字节 无，但要分配机器号 好，本地生成 高并发交易链路
Redis INCR 递增 8 字节，常加前缀 Redis 中，切换可能回退 计数、可容忍重复的编号
ZooKeeper 顺序节点 严格递增 视实现而定 ZooKeeper 中 低频、要求强顺序

上线之后至少要盯四类指标。第一类是时钟：用 chrony 或 node_exporter 采集本机与上游的时间差，偏差超过几十毫秒就告警；Snowflake 还要单独统计回拨发生的次数与幅度，这类事件稀少，但每一条都值得回看。第二类是序列：统计每毫秒的序列使用率与取号等待时间，如果 P99 明显抬升，说明单机已经逼近每毫秒 4096 个的上限，此时扩容比调位更有效。

第三类是号段余量：当前号段剩余比例、预取失败的次数、取号 SQL 的延迟。预取失败必须在号段耗尽之前报警，而不是等业务侧报“发号失败”。第四类是正确性：抽样比对相邻 ID 的单调性，并在入库时保留唯一索引作为最后一道防线。ID 一旦重复，排查成本远高于多加一个索引。

多机房部署时，Snowflake 的 10 位机器位可以切成机房位与机器位，各机房独立生成、互不通信，跨机房调用不需要额外协调。代价是机房之间的时钟存在偏差，ID 只保证各自趋势递增，不保证全局严格单调，凡是依赖“后发的 ID 一定更大”的逻辑都要重新审视。号段方案则让每个机房独立取号，步长调大或按机房预留区间；跨机房写同一张表时，分片键要能从 ID 直接解析出来，否则路由会退化成广播，分库分表的意义也就没了。

还有一件常被忽略的事：把 ID 的生成规则写进文档，并提供解析工具，同时给规则保留版本号。出问题时，能从订单号里读出时间、机房与机器号，定位速度会比翻日志快得多；规则调整过几轮之后，旧 ID 也不至于被新工具解析错。

小结

没有一种方案在所有维度上都占优。单库中小规模，AUTO_INCREMENT 就够了；需要跨库又在意写入性能，号段加双 buffer 是最稳的折中；交易链路要求低延迟、ID 还要带时间，Snowflake 更合适，但机器号分配与时钟回拨这两件事必须先做扎实。UUID 适合不按 ID 排序的场景，不要拿它当高频写入表的主键。无论选哪一种，上线后都要监控时钟偏移、序列余量与号段存量，并用唯一索引兜底。
