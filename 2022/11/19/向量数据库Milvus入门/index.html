向量数据库 Milvus 入门

把文本、图片或音频交给嵌入模型之后，我们会得到一串浮点数。真正的难题出现在下一步：在上千万条这样的向量里，怎样在几十毫秒内找出与查询最相似的若干条，并且还要按业务字段过滤、随时增删。本文以 Milvus 2.x 为对象，讲清它的存算分离架构、数据模型、索引选型、检索接口与部署方式，并给出若干工程取舍上的建议。读完本文，你应当能独立搭起一个可用的向量库，并为自己的数据选出一套合理的索引与分区方案。嵌入模型如何训练与挑选、召回质量如何评估，不在本文范围内。

为什么需要专门的向量数据库

先看朴素的实现。假设有 1000 万条 768 维的 float32 向量，仅原始数据就是 1000 万乘 768 乘 4 字节，约 30 GB。每次查询都要与全部向量算一遍距离，单机 CPU 上难以接受，GPU 也撑不住并发与实时写入。近似最近邻（Approximate Nearest Neighbor，ANN）索引解决的就是这个问题：牺牲一点点精度，把扫描范围从全体缩小到少数候选。

在 Python 生态里，FAISS 是绕不开的名字。它把各种 ANN 索引实现得很好，但定位是算法库：索引活在进程内存里，持久化、并发写、副本与故障恢复都要应用自己补。当我们把检索做成一项长期在线的服务时，就还需要另一层东西：数据的持久化与版本、写入与建索引的调度、多副本与负载均衡、按标量字段过滤、多租户隔离。向量数据库把这些能力打包在一起，Milvus 是其中较早开源、也较为完整的一个。

还要说明一点，Milvus 不负责把文本变成向量。嵌入由外部模型完成，它只接收向量与附带字段，负责存储、建索引与检索，本文讨论的是后一半。

存算分离的架构

Milvus 2.x 与 1.x 是代际差别：系统被拆成若干无状态或半状态的组件，状态外移到三个基础依赖上，数据面只经由消息队列与对象存储流动，控制面信息集中在 etcd。理解这张图，后面很多行为就顺理成章了。

flowchart TD
    Client[客户端 SDK] --> Proxy[proxy 接入层]
    Proxy --> MQ[(消息队列)]
    Proxy --> RC[root coordinator]
    Proxy --> QN[query node]
    MQ --> DN[data node]
    MQ --> QN
    DN --> OS[(对象存储)]
    IDX[index node] --> OS
    OS --> QN
    QC[query coordinator] --> QN
    RC --> DC[data coordinator]
    RC --> IC[index coordinator]
    RC --> QC
    DC --> DN
    IC --> IDX
    RC --> ETCD[(etcd)]
    DC --> ETCD
    IC --> ETCD
    QC --> ETCD

组件可以分成三层来看。

  • 接入层只有一个角色：proxy。它接收 SDK 的请求，做鉴权与路由，把写请求打包投递到消息队列，把读请求转发给 query node 并汇总结果。
  • 协调层是四个 coordinator。root coordinator 管 DDL，比如建 collection、建分区；data coordinator 管数据节点的拓扑与 flush；index coordinator 管索引构建任务；query coordinator 管查询节点的负载与 segment 分配。它们本身不存数据，只通过 etcd 保存元数据与任务状态。
  • 执行层是三类 worker。data node 从消息队列消费插入与删除日志，把数据整理成段（segment）刷到对象存储；index node 对落盘的段建索引；query node 把段加载进内存，执行向量检索与标量过滤。

三个外部依赖各司其职：etcd 存元数据、服务注册与协调信息；对象存储（S3、MinIO、OSS 等）存日志快照、段文件与索引文件；消息队列（Pulsar、Kafka、RocksMQ）存写入日志，是写入链路的唯一入口。这种设计带来的直接好处是每一层都能独立扩缩：检索压力大就加 query node，写入量大就加 data node，建索引慢就加 index node。

数据模型：collection、partition 与 schema

Milvus 的组织方式与文档数据库有几分相似，自上而下是 database、collection、partition、entity。collection 相当于表，必须先用 schema 定义字段；partition 是 collection 内部的物理切分，用来缩小检索范围；entity 就是一行数据，由主键、若干标量字段和一个或多个向量字段组成。

partition 的价值在于把“必然用不到的段”提前排除。按月份或按业务大类切分，检索时用 partition_names 指定范围，query node 就不会加载和扫描其他分区。但分区不是越细越好：每个分区都带来元数据与段管理的开销，数量到几千的量级后，加载与调度都会变慢。通常按时间粗粒度切分，再配合标量字段过滤就够了。

索引：从 FLAT 到 HNSW

没有索引时，Milvus 对每个段做暴力扫描，行为等价于 FLAT；建索引之后，查询才走近似最近邻。索引里的 metric_type 必须与检索时一致，否则要么报错，要么距离没有意义。

FLAT 是最朴素的方案：不训练、不额外占用结构，逐个算距离，结果精确。它的定位是召回基线，适合百万级以内，或用来验证其他索引的效果。数据量再往上，扫描成本就压不住了。

IVF_FLAT 先用 k-means 把向量聚成 nlist 个簇，每个向量只归属最近的簇。查询时先找与查询向量最近的 nprobe 个簇，只在这几个簇内扫描。nlist 决定粒度，nprobe 决定查得有多宽：nprobe 越大越接近全量扫描，召回上升、延迟也上升；nprobe 等于 nlist 时退化为 FLAT。nlist 的经验取值常写成数据量的平方根量级，但这只是起点，真实取值要自己测。

IVF_PQ 在 IVF 的基础上再做乘积量化：把 d 维向量切成 m 段，每段用一个小码本量化成 1 字节。原本每段占 4d/m 字节，压到 1 字节后压缩比约为 4d/m。代价是距离计算有损，召回通常低于同参数下的 IVF_FLAT，且 m 必须能整除维度。它适合“内存不够、可以接受精度损失”的超大规模场景。

HNSW 是分层可导航小世界图，查询从稀疏的顶层逐层下降，在底层做贪心搜索。它有两组参数：建索引时的 M 控制每个节点的邻居数，efConstruction 控制建图时的候选队列长度；检索时的 ef 控制搜索宽度，且必须不小于 top-k。M 和 efConstruction 越大，图质量越好，构建越慢、内存越高；ef 越大，召回越高、延迟越大。HNSW 查询快、内存占用高、不支持高效的原地删除，更新频繁的数据要谨慎。

换成 IVF 系列只需改 index_type 与 params，例如 nlist 取 1024。索引构建由 index node 异步完成，数据量大时一次全量建索引可能持续很久，这段时间里新写入的数据仍以暴力方式可查，但延迟会明显偏高。

检索：search 与 query 的分工

Milvus 的读接口只有两个，职责分得很清楚。search 面向“相似”，输入查询向量，按距离排序返回 top-k；query 面向“条件”，输入布尔表达式，按主键或标量条件取回实体，不做任何向量排序。需要“先按条件筛，再按相似度排”时，用 search 的 expr 参数，而不是先 query 再自己算。

度量方式有三种。L2 是欧氏距离，越小越相似；IP 是内积，越大越相似，适合已经归一化的向量；COSINE 直接算余弦相似度，取值在负一到一之间，越大越相似。对归一化后的向量，IP 与 COSINE 的排序结果一致，只是数值尺度不同。选择要与嵌入模型的训练方式对齐，多数句向量模型用余弦或内积更自然。

返回结果里的 distance 字段名对所有度量方式都一样，但含义随 metric 变化：L2 下越小越好，IP 与 COSINE 下越大越好。这一点在写排序或阈值判断时最容易搞反。过滤条件的执行顺序是先按表达式算出候选位图，再在位图上做向量检索，所以过滤比例很高时，候选集可能小到让 IVF 这类按簇扫描的索引失去优势，延迟未必下降。若某一类数据经常被整体过滤，按类别拆分区甚至拆 collection 会更稳。

范围检索用于“不要 top-k、只要某个距离区间内全部结果”的场景，比如去重时找近重复项。它在 search 的 param 里额外给 radius 与 range_filter：以 L2 为例，可以理解为只保留距离落在 range_filter 与 radius 之间的结果；换成 IP 或 COSINE，边界的方向相反，需要按“相似度从大到小”重新理解。区间过宽时结果集可能很大，务必配合 limit 使用。

query 则是另一条路：

它适合按主键回表、校验写入是否成功、统计分区数据量，也适合在管理后台做条件筛选；但它不计算相似度，不要指望它承担语义检索。

部署：standalone 与 cluster

Milvus 提供两种形态。standalone 把 proxy、coordinator 与各类 node 塞进同一个进程，外部仍依赖 etcd 与对象存储，官方用一份 compose 文件把三者串起来。它适合本地开发、功能验证和百万级以内的单机场景，资源占用小，运维几乎没有成本。cluster 把各角色拆成独立服务，通常用 Helm 部署到 Kubernetes，适合千万级以上、需要多副本与弹性伸缩的生产环境。

本地体验只需两步：拿到官方 standalone 编排文件，然后启动。

启动后默认监听 19530 端口，SDK 连上即可建表。数据落在 compose 定义的卷里，删掉卷等于清库，验证阶段可以放心折腾。还要提醒，standalone 不是“缩小版集群”，它没有副本与故障转移，不要拿它承载线上流量。

资源估算的关键是内存。query node 要把段与索引常驻内存，粗略的算法是：原始向量占用为数量乘维度乘 4 字节；HNSW 还要加上图结构的开销，量级约为数量乘 M 乘 2 乘 4 字节；IVF_PQ 则压到数量乘 m 字节。以 1000 万条 768 维向量为例，原始数据约 30 GB；把图结构、growing segment 与副本余量一起算进去，按 1.5 倍预留比较稳妥。这只是示意算法，实际还要算上副本数、growing segment 与标量字段的开销。CPU 方面，检索与建索引都是计算密集型，建索引尤其吃核数；磁盘主要看对象存储，compaction 期间会短暂出现接近两倍的占用。

工程实践：写入、删除与索引时机

写入路径决定了一致性的表现。数据从 proxy 进入消息队列，data node 消费后形成 growing segment，query node 订阅到这条日志后才能查到。因此“插入返回成功”不等于“立即可检索”。Milvus 提供四档一致性：Strong 保证读到最新写入，Session 保证同一客户端能读到自己的写，Bounded 允许一个有限的时间窗滞后，Eventually 最宽松。默认是 Bounded，多数场景够用；对“写完马上要读”的流程，在 search 或 query 上显式指定 Strong 即可，不要用逐条 flush 解决可见性，那是把批处理接口当同步接口用，代价极高。

删除是逻辑删除。delete 按表达式记下删除日志，查询时结合时间戳过滤掉这些主键，真正的空间回收要等 compaction。compaction 会把多个小段合并成大段，顺带清理已删除的数据与冗余的删除日志。频繁小批量删除会让存储与查询开销同时膨胀；大批量删除之后，主动触发一次 compaction 能明显改善后续表现。

索引构建应当当成批处理任务来安排。全量导入完成后统一建索引，比边写边建高效得多；持续写入的场景里，新数据先落在 growing segment 上以暴力方式提供检索，等段封存后再由 index node 建索引。索引参数一旦调整就要重建，重建期间查询会退化到暴力扫描，最好放在低峰期，并预留足够的临时内存。

分区设计要与查询模式对齐。按月份分区，就让每次查询都带上对应分区；如果查询从不带分区条件，分区只会增加管理开销。分区数量控制在几十到几百的量级比较舒服，上千之后加载与调度都会变慢。最后一条经验是：不要照搬别人的 nlist、nprobe、ef 取值，用自己真实的数据分布与查询样本压测，在可接受的召回水平上找延迟最低的那组参数。

小结

Milvus 2.x 用 proxy、coordinator 与三类 node 组成存算分离的架构，把状态交给 etcd、对象存储与消息队列，让写入、建索引、检索三条链路各自伸缩。使用上的主线是四步：定义 schema 建 collection，按查询模式划分 partition，选一种索引并填好参数，然后用 search 做相似检索、用 query 做条件取数。索引没有万能解，FLAT 求准、IVF 求省、HNSW 求快，参数要在自己的数据上校准。工程上最容易忽略的是写入可见性与删除的滞后：前者靠一致性级别解决，后者靠 compaction 回收。把这些边界想清楚，再决定用 standalone 还是 cluster，向量库才算真正落地。
