LangGraph 状态机工作流

标题里的“LangGraph”只是一个写作由头。这个名称所指的图编排库在本文写作时尚未发布，社区对“怎样把多步 LLM 调用组织成流程”仍处于探索阶段。本文因此不谈具体库的接口，只讨论方法：用状态机描述检索、生成、校验、重试之间的跳转，让流程可读、状态可存、任务可恢复。适合已经跑通过单轮提示调用、准备把大模型接入真实业务的读者。

为什么线性链不够用

最早的一批大模型应用大多是一条直线：拼接提示、调用模型、解析输出、返回结果。这种做法在演示阶段足够，一旦业务要求“先查资料再回答”“答完再检查”“检查不过就重来”，直线就撑不住了。

以一个客服问答为例，最小可用的流程包含四步：根据用户问题检索资料；把资料与问题一起交给模型生成回答；用校验步骤检查回答是否引用了资料、是否出现不该给的承诺；校验失败时把失败原因回灌给模型重写，最多重试两次。这里有分支，检索为空时要先改写查询；有回环，校验失败要回到生成；还有次数上限。

如果把这些逻辑塞进一个函数，用嵌套的 if 与 while 表达，代码会在两周内变成谁也说不清的控制流：重试计数散落在局部变量里，失败原因只能靠翻日志猜，进程一重启任务就从第一步重来。状态机的价值不在于新鲜，而在于把“现在走到哪一步”“下一步去哪”“为什么去”变成显式的数据结构。

具体来说，状态机带来四点好处：流程可视化，画出来就是一张图，产品与算法能对着同一张图讨论；单步可测试，每个节点都是纯函数；可持久化，状态是普通字典，序列化后能落盘；可中断，任何一步之后都能停下等人确认。这四点对应 LLM 应用最贵的两件事：模型调用不能白跑，人的判断必须能插进去。

状态：把一次任务的全部上下文装进去

状态机的第一件事不是画图，而是定义状态。状态是一个普通字典，装着走到当前这一步所知道的全部信息。设计得好，节点之间几乎没有隐式依赖；设计得差，状态会膨胀成谁也不敢删的垃圾桶。

按用途划分，一份 LLM 工作流的状态通常包含五类字段。

输入与会话：用户原始问题、会话标识、历史轮次摘要、租户与权限。历史不要整段塞入，保留摘要加最近若干轮即可。

中间结果：检索到的文档片段、候选答案、工具调用记录。这一部分最容易膨胀，建议给每类结果设上限，只保留前若干条、单条截断，并记下截断标记。

错误与重试：不要只存字符串。用结构化列表，每条含节点名、错误类型与可读信息。重试计数按节点分别记，否则“生成重试两次”与“校验重试两次”会互相污染。

人工确认：一个布尔标记，加上确认人与确认意见。这个字段决定了流程能否在无人值守时自动通过某个节点。

进度与预算：当前步数、已消耗的 token、开始时间、下一个待执行节点。

所有字段必须可序列化。模型客户端、数据库连接、文件句柄、匿名函数都不能进状态，需要调用能力时从外部依赖取。这条约束直接决定了后面能不能做检查点。

状态还需要一个版本号。旧检查点配上新代码往往不报错，只会静默算出错误结果。加 schema 版本字段，加载时校验，不匹配就拒绝或走迁移函数。

最后一条经验：状态变化用增量补丁而非整体替换。节点只返回自己修改的键，引擎负责合并，日志里就能看清每一步改了什么。

图结构：节点、边与终止条件

把状态定好之后，图本身只有三个概念。节点表示一步操作，读状态、返回补丁；边表示跳转，可以是无条件的，也可以由条件函数决定；终止条件表示流程结束，通常是一个约定的结束标记。

条件边是整套设计的关键。它本质上是一个路由函数：输入当前状态，返回下一个节点的名字。前面客服例子里，“检索为空则结束、否则去生成”和“校验通过则结束、未通过且未超限则回到生成”就是两条条件边。把判断放在路由函数里，节点本身就不需要知道下一步是谁，职责非常干净。

flowchart TD
    A[开始] --> B[检索]
    B -->|有结果| C[生成]
    B -->|无结果| Z[结束]
    C --> D[校验]
    D -->|通过| Z
    D -->|不通过且未超限| C
    D -->|超限| H[转人工]
    H --> Z

终止条件要写全。除了业务上的正常结束，至少还有三种收尾方式：步数达到上限、预算耗尽、连续多步状态没有实质变化。只写一个“成功结束”的图，出问题时会在两个节点之间无限打转，把额度烧完才被发现。

最大步数是最便宜的保险，按流程长度估一个值即可：正常路径五步，上限设十二到十五步。触顶时不要把异常直接抛出，而应把未完成原因写进状态，让调用方决定重试、转人工还是降级。

还有一处常被忽略：结束标记与真实节点名必须不可能冲突。可以用带前缀的保留字，也可以在注册节点时做校验。名字撞车的后果是流程提前结束，而且日志看起来一切正常，排查起来非常费劲。

一个最小可用的引擎

理解了状态与图，实现就只剩一个循环：取当前节点、执行、合并补丁、记录、路由、落盘。下面这段代码约六十行，不依赖任何编排库。检索与生成用假想函数代替，真实项目里换成向量检索与模型调用即可。

这段代码省掉了并发、超时、重试退避与依赖注入，但已具备三个关键性质：状态是纯数据，可序列化；控制流由路由集中表达，新增分支只改路由；每次执行留下 trace，可事后复现路径。其余工程能力都能在此基础上叠加。

检查点与人工介入

每步之后落盘，换来的能力是断点续跑。检查点至少存三样东西：序列化状态、下一个待执行节点、状态版本号。写入时用临时文件加原子替换，避免留下半截 JSON。生产环境可放到数据库或对象存储，键用任务标识加版本号。

恢复的逻辑很简单：读状态、读 next、继续跑循环。真正难的是幂等。模型调用按 token 计费，重跑一次就多付一次钱；带副作用的工具，比如发消息、建工单，重放时还可能重复执行。所以检查点必须与步骤幂等一起设计。

人工介入则是在检查点上加一个闸门。在需要人确认的节点之前设置中断，把状态存好、任务标为待审，然后结束本次执行；审核人确认后，把确认标记写回状态，从 next 继续。这个过程不需要保持进程常驻，适合动辄几小时的审批场景。

这里要说清与长任务断点续跑的区别。批处理任务的检查点关心“已经处理到第几条数据”，核心是游标与分片；LLM 编排的检查点关心“推理走到哪一步”，核心是上下文与分支选择。前者可以按批次重放，后者一旦重放就要重新付费，且同一状态未必得到同一输出，所以更依赖记录而不是重算。

检查点还有兼容性问题。节点改名、字段改语义、提示模板大改，都会让旧检查点失去意义。稳妥的做法是给检查点打上流程版本，加载时版本不符就走迁移或要求重新开始。

工具调用：先约定协议，再谈执行

大模型本身不能执行任何东西，只能生成文本。所谓工具调用，是用提示约定一种输出格式，让模型把“调用什么、参数是什么”写成结构化指令，再由外部代码解析执行。2022 年秋天这套做法还没有统一标准，各家自行约定 JSON 结构，因此解析器必须像对待外部输入一样谨慎。

一种可用的约定是：系统提示列出工具名称、用途与参数结构，要求模型需要时只输出一行 JSON，即工具名加参数对象，否则输出普通文本。解析时先容错提取，去掉代码围栏与前后缀，再校验字段、类型与工具名是否在白名单内。失败时把异常转成简短说明，作为观察结果回灌，让模型重试或换工具。

白名单是硬边界。模型可能发明工具名，也可能把参数填成超长字符串或危险路径，执行层必须按最小权限校验，不能因为“提示里写过”就信任。工具返回的内容同样不可信：网页或用户文档里若有“忽略之前的指令”，只能当作数据，绝不能拼回系统提示的高优先级位置。

错误回灌要控制信息量。贴完整堆栈既浪费 token，又容易把模型带偏；回传错误类型、一句话原因和一条修复建议即可，并告诉模型已经重试了几次。

副作用要隔离。检索、查询这类只读工具可以自动执行；发消息、改订单、建工单这类写操作，要么走人工确认，要么要求模型给出幂等键，由执行层去重。更稳妥的做法是“意图与执行分离”：节点只记录准备做什么，执行放在图外的受控环节，执行前落 intent 记录，执行后落 result 记录。这样流程在两步之间崩溃，也能判断操作到底发生过没有。

调试、重放与失控防护

多步流程出问题时，最无力的场景是“用户说答错了，日志里却只有最终回答”。解决办法是逐步记录：节点名、状态摘要、发出的提示、模型返回原文、解析结果、耗时与 token 用量。按 JSON Lines 追加写入，一条一行，便于检索与统计。

有了完整记录，重放才有意义。重放不是再跑一遍，而是用录下的模型输出替代真实调用，按原路径走一遍图，从而确定问题出在提示、解析、路由还是状态合并，且不产生费用。调试解析器时尤其有用：同一段输出反复喂给解析函数，直到它能稳定处理各种边界格式。

成本统计要按任务聚合，而不是只看月度账单。平均步数、平均 token、重试率、人工介入率这四个指标，足以说明流程是否健康：步数上升往往是条件边开始回环，重试率上升可能是校验变严，人工介入率过高则说明自动化边界划错了位置。

防失控需要多层。第一层是总步数上限，前面已经实现；第二层是单节点访问次数上限，防止两个节点互相踢皮球；第三层是无进展检测，每步之后对关键字段做哈希，连续若干步不变就判定空转并终止；第四层是预算与超时，按任务设置 token 上限和墙钟上限，触顶即停。

这四层不必复杂，但必须有。模型输出带有随机性，同一段提示可能这次通过校验、下次不通过，回环一旦形成，靠人盯日志往往发现得太晚。

小结

多步 LLM 工作流的难点不在模型，而在控制流。状态机把“走到哪、去哪、为什么去”变成显式的数据与函数：状态是纯字典，节点是纯函数，分支写在路由里，终止条件写全。每步持久化换来断点续跑与人工介入，但必须同时处理幂等与版本兼容。工具调用靠提示约定加严格解析，白名单、错误回灌与副作用隔离缺一不可；再用步级记录支撑重放与成本统计，用步数、访问次数、无进展检测与预算四层护栏兜底。这套东西不依赖特定框架，几十行代码就能起步。
