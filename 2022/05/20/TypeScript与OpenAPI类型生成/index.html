TypeScript 与 OpenAPI 类型生成

本文属于《TypeScript 学习路线》第 39/74 篇
上一篇系列目录下一篇

后端把接口写在 OpenAPI 文档里，前端却仍在手抄 interface，两边靠联调时逐字段对齐，这是不少团队当下的日常。本文讨论如何把 OpenAPI 规范变成 TypeScript 的类型与客户端，让字段拼写、可空性和响应结构的问题在编译期就暴露出来，并进一步把这套链路接到服务端 handler 与 CI 门禁上。阅读本文需要熟悉 TypeScript 的基本类型操作与 HTTP 接口的常见约定，读完后应当能为自己的项目搭出一条可维护的生成链路。

为什么值得把契约搬进类型系统

一个典型的接口联调现场是这样的：后端在文档里写 user_name，前端按习惯写成 userName，类型检查一路通过，直到页面上出现一个空白的用户名。又或者后端把 age 从必填改成可选，前端仍然按 number 使用，运行时拿到 undefined 再做算术，得到 NaN。这类问题的共同点是：错误不在语法层面，也不在逻辑层面，而在“双方对同一份数据的形状理解不一致”，而 TypeScript 默认对此一无所知。

手写 interface 曾经是主流做法，它的问题不在于写得对不对，而在于没有约束的副本必然会漂移。接口少的时候，开发者靠记忆和联调可以维持；接口数量上来之后，任何一次后端字段调整都可能漏改某个调用方。更麻烦的是，手写类型往往比真实响应更“自信”：把可空字段写成非空，把字符串枚举写成 string，把错误响应直接省略。类型系统于是从保护网退化成了心理安慰。

OpenAPI 规范的价值在于它本来就在描述数据的形状，只是过去这份描述主要服务于文档渲染和 Mock。既然机器可读，就可以把它翻译成 TypeScript 类型，让“文档”和“类型”共享同一个源头。本文关注的正是这条翻译链路：从 spec 出发，生成类型，再生成或约束客户端与服务端代码。

契约优先与代码优先的取舍

在动手之前，团队要先回答一个问题：spec 是手写的，还是从代码里导出的。这就是通常所说的契约优先（spec-first）与代码优先（code-first）。

契约优先把 OpenAPI 文件当作源文件，先评审、再实现。它的好处是契约可以脱离某一种语言存在，前端可以在后端开工之前拿到类型和 Mock，多个消费方共享同一份定义，评审时讨论的是接口本身而不是某个框架的装饰器。代价是 spec 需要人维护，写 YAML 的手感远不如写代码，且容易与实现脱节，除非有测试或 CI 兜底。

代码优先则相反，服务端用装饰器或类型标注描述路由，构建时导出 OpenAPI。它的好处是契约与实现天然同步，开发者不需要学一套额外的 DSL；代价是契约的表达能力受框架限制，前端必须等后端产出 spec 才能生成类型，跨语言协作时导出质量参差不齐。

实践中更常见的是一种折中：以 spec 为唯一事实来源，服务端在启动或测试时校验实际路由与 spec 是否一致。这样既保留了契约优先的协作优势，又用自动化手段抑制脱节。本文后续的内容都建立在这个前提上：仓库里有一份受版本控制的 OpenAPI 文件，任何人改接口都要先改它。

需要强调的是，生成类型不能替代设计：工具只翻译 spec 里已有的信息，若 spec 里到处是没有约束的 object，产物也会一片宽松。

OpenAPI 3.0 与 3.1：先认清手里的规范

在写任何生成脚本之前，先确认手上这份文件是 3.0 还是 3.1。两者的顶层结构相似，都以 openapi 字段声明版本，都包含 info、paths、components 三大块，但 schema 的语义差别不小，而生成器恰恰最依赖 schema 的细节。

OpenAPI 3.0 的 Schema Object 并不是完整的 JSON Schema，而是一个受控子集。它引入了 nullable: true 来表示“可以为 null”，exclusiveMinimum 仍是布尔值，type 只能是单个字符串，不允许写成数组。这些设计在当年有其考量，但也意味着 3.0 的 schema 不能直接丢给通用 JSON Schema 校验器使用，必须经过转换。

OpenAPI 3.1 于 2021 年初发布，核心变化是全面对齐 JSON Schema。nullable 被移除，改用类型数组表达可空；exclusiveMinimum 变成数值；允许出现 $schema 声明方言；schema 甚至可以是布尔值，true 表示任意值，false 表示不可能有值。顶层还增加了 webhooks，用于描述回调式的入站请求。对类型生成而言，最重要的差异就是可空性的写法，因为它直接影响生成结果里是否出现 | null。

这份片段几乎用到了后文要讨论的所有结构：路径参数、枚举、可空字段、数组、引用和错误响应。注意 note 没有出现在 required 里，同时又被标为可空，这意味着它有三种状态：缺省、null、字符串。很多“类型过宽”的抱怨，源头就是 spec 没有把这三态想清楚。

如果项目准备迁移到 3.1，需要先确认工具链。2022 年上半年，不少生成器和文档站仍以 3.0 为主要目标，对 3.1 的类型数组、布尔 schema 支持不完整，遇到不认识的写法可能静默降级成 any。比较稳妥的做法是：新项目若消费方工具都支持 3.1，可以直接用 3.1 获得更准确的 JSON Schema 语义；存量项目则先留在 3.0，把迁移当作独立任务评估，而不是顺手在某个迭代里改掉版本号。判断支持程度的方法很朴素：拿一份包含类型数组、null 联合与布尔 schema 的最小样例跑一遍生成器，看输出是否还能看懂。

从 spec 到代码：工具的分层

围绕 OpenAPI 的 TypeScript 工具大致可以分成三层，理解分层比记住某个包名更重要。第一层只生成类型，产出一个声明文件，不包含任何运行时代码；第二层生成完整的客户端，包括请求方法、序列化、错误处理；第三层在客户端之上再包一层框架适配，例如生成 React Query 的 hooks。层数越高，约定越多，也越难替换。

openapi-typescript 属于第一层。它读取 spec，输出一个 .d.ts，里面通常包含 paths、components 等命名空间，把每个路径、每个操作、每个 schema 都映射成类型。它不生成任何函数，因此不会把请求库、框架或运行时绑定进项目。这个定位非常适合已有请求封装、只想补齐类型的前端团队。

openapi-generator 属于第二层，支持几十种语言和模板，TypeScript 侧常见的目标有 typescript-fetch 和 typescript-axios。它生成的是可以直接调用的客户端类或函数，附带模型类型和 API 类。功能全、覆盖面广，代价是生成物体量大、模板定制需要学习它自己的模板语言，升级大版本时生成结果的差异也更明显。

两条命令的产物应当被区别对待。生成目录是“构建中间物”，不应该手改，也不应该参与代码风格争论。比较常见的做法是在仓库里保留生成结果以便代码审阅时看到契约变化，同时在生成目录放一个说明文件，并在 ESLint、Prettier 的忽略列表里排除它。另一种做法是把生成放在 prebuild 或 predev 脚本里，仓库不存储产物，好处是永不陈旧，坏处是每次安装依赖后首次启动都要多等几秒，且 CI 需要保证生成器可用。

无论选哪种，都要避免“生成一次就放在那里”的状态。spec 更新而产物没更新，类型就会说谎，而且这种谎言比手写类型更难察觉，因为大家默认生成物是可信的。后文会给出在 CI 中检测这种漂移的办法。

类型映射：从 schema 关键字到 TypeScript

生成器做的事，本质上是把 JSON Schema 的约束翻译成 TypeScript 的类型构造。翻译规则并不复杂，但每一条都有边界，理解这些边界才能判断生成结果是否可信。

对象。type: object 加 properties 会变成一个对象类型，required 数组里的键是必填，其余键是可选。可选键在 TypeScript 里写成 key?: T，在默认编译选项下等价于 T | undefined，这意味着读取时仍然要处理缺省。若字段同时出现在 required 之外又标了 nullable，生成结果就是 key?: T | null，三种状态都在，使用方必须显式分支。

数组。type: array 加 items 生成 T[]；没有 items 时只能生成 unknown[] 或 any[]，具体取决于生成器的保守程度。前者更安全，后者更省事，但会把检查责任推给调用方。元组在 3.0 里没有标准写法，3.1 借助 JSON Schema 的 prefixItems 可以表达，不过 2022 年各生成器对它的支持并不齐整，遇到时应当先看产物再决定是否依赖。

枚举。字符串枚举会被翻译成字面量联合，例如 'pending' | 'paid' | 'shipped'，这是生成类型里价值最高的部分之一：拼写错误、漏处理分支都会在编译期暴露。数值枚举同理，生成数字字面量联合。需要注意的是，枚举在运行时仍然是字符串或数字，TypeScript 的联合只存在于类型层，做 switch 时仍要写 default 兜底，因为服务端可能返回规范之外的值。

组合关键字。oneOf 生成联合类型，anyOf 也生成联合类型，allOf 生成交叉类型。三者的语义差别在类型层面被抹平了一部分：oneOf 要求恰好匹配一个分支，anyOf 允许匹配多个，但 TypeScript 的联合无法表达“恰好一个”。allOf 用于组合多个 schema，常见于“基础字段 + 扩展字段”的建模，交叉之后必填与可选的合并大体正确，但如果两个分支对同一字段给出不同类型，交叉会得到 never，这类冲突应当在 spec 评审阶段就发现。

可空。3.0 的 nullable: true 应当生成 T | null。这条规则看起来简单，却是历史包袱最重的地方：早期一些生成器只处理 type 不处理 nullable，把可空字段生成成非空，前端于是少写判空。使用任何工具之前，都建议拿一个可空字段验证产物，而不是相信文档里的一句“支持 OpenAPI 3.0”。

additionalProperties。这是“类型过宽”最主要的来源。当它为 false 时，对象是封闭的；当它为 true 或缺省时，按 JSON Schema 的语义，对象允许任意额外键。部分生成器会因此补上一行索引签名，例如 [key: string]: unknown。索引签名一旦出现，这个类型就几乎可以被任意对象赋值，原本精确的字段约束被稀释，交叉类型也会变得难以推理。更隐蔽的问题是：带索引签名的类型在作为参数传入时，TypeScript 对它的检查会放松，错误因此延后到运行时。若业务上确实是字典结构，用 additionalProperties 指向一个具体 schema 是合理的，会生成 Record<string, T>；若只是忘记声明，则应当在 spec 里补 additionalProperties: false。

引用与递归。$ref 在生成时会指向 components['schemas'] 下的同名类型，递归引用也能正常工作，因为 TypeScript 的类型别名和接口都允许自引用。例如树形结构 Node 的 children 指向 Node[]，生成后依然可以正常使用。需要注意的是跨文件拆分：把 schema 拆到多个 YAML 再用 $ref 引用外部文件时，生成器需要能解析相对路径，产物里的类型名也可能带上文件前缀，团队要约定好拆分粒度，否则类型名会越来越长。

生成结果“过宽”的几种典型

第一种是缺省即任意。schema 里只写了 type: object，没有任何 properties，生成器只能给出 Record<string, unknown> 或空对象类型。这类 schema 在快速迭代的项目里很常见，本质上等于放弃了类型。

第二种是可选字段被当成不存在。有些团队为了让后端“先上线再补文档”，把所有字段都塞进 required，生成出来的类型看似严格，实际运行时缺字段，类型检查反而制造了虚假的安全感。反过来，全部标成可选则让每个字段都要判空，类型退化成 Partial<T>。

第三种是联合过宽。oneOf 里放了两个结构相似的对象，TypeScript 的联合可以赋值通过，但收窄时需要自定义类型守卫。若联合里有一个分支是 string，另一个是对象，判别起来相对容易；若两个分支只差一个可选字段，基本无法可靠收窄。这类建模问题应当在 spec 层面解决，例如引入 kind 判别字段。

第四种是格式被忽略。format: date-time 在 TypeScript 里仍然是 string，不是 Date；format: int64 仍然是 number，超过安全整数范围会丢精度。生成器不做运行时转换，也不应该做，但使用方必须知道这一点。把 date-time 直接传给日期库而不做解析，是联调后期常见的低级错误。

第五种是读写不对称被抹平。readOnly: true 的字段在响应里有、在请求体里不该有；writeOnly: true 的字段相反，例如密码。多数生成器对同一个 schema 只产出一份类型，请求与响应共用，于是要么允许发送只读字段，要么要求提供不会返回的字段。稳妥的做法是在 spec 里把请求体和响应体拆成两个 schema，用 allOf 复用公共部分，再让生成器分别产出。多写几行 YAML，换来的是两端签名都准确。

消费生成的类型：一个薄客户端

拿到声明文件之后，最直接的问题是怎么用。比较克制的做法是保留团队已有的请求封装，只用生成类型约束它的入参与返回值，而不是让生成器接管整个网络层。这样请求库、拦截器、鉴权逻辑都不需要改，生成物只承担“形状定义”的职责。

这段代码有两个刻意保留的断言。第一个在错误分支，第二个在成功分支。它们不是偷懒，而是承认一个事实：response.json() 的返回类型是 any 或 unknown，任何类型标注都只是承诺。把断言集中在少数几个边界函数里，比在每个组件里随手 as 要好得多；如果项目对边界安全要求高，可以在这两个位置接入运行时校验，后文会讲怎么与 zod 衔接。

GetOrderOk 这个类型别名值得多说一句。它从 paths 里逐层取出响应体的类型，路径、方法、状态码、内容类型四层都是字面量键，任何一层写错都会立刻报错。相比于手写 Order，它多了一层保护：如果 spec 里这个接口的响应改成了另一个 schema，别名会跟着变，而调用方若依赖了旧字段就会编译失败。这种“类型跟着契约走”的传导，正是生成链路的核心收益。

如果选择 openapi-generator 生成完整客户端，调用方式会变成 new OrdersApi().getOrder({ orderId }) 之类，序列化、查询参数拼装、基础路径都由生成物负责。此时要注意三点：生成物是否把 Date 反序列化成了字符串（多数实现不会自动转），错误是否统一抛出某个异常类型，以及取消请求、超时这些能力是否被暴露。这三点直接决定它能否替换现有封装。若答案不理想，退回“类型 + 手写薄客户端”往往更省心。

服务端：让 handler 签名受契约约束

类型生成不只服务于前端。服务端同样可以从 spec 里取到请求体、查询参数和响应体的类型，用它们约束路由处理函数。这样一来，后端改字段时编译器的报错位置从“前端联调”提前到了“提交代码”。

这里把返回值建模成一个以 status 为判别字段的联合，而不是笼统的 Order | Error。好处是调用方（路由注册处或测试）可以按状态码收窄，编译器也能检查每个分支的 body 是否与对应 schema 一致。若新增了 409 响应，只需往联合里加一个分支，所有未处理它的 switch 都会收到提示。这种建模方式比让 handler 随意返回 Response 对象要严格得多，也更容易做统一的序列化。

与运行时校验衔接

生成类型只在编译期存在，数据库里读出的对象、JSON.parse 的结果都不受它约束。OrderSchema.parse(order) 的作用是在边界处做一次真实校验，失败则抛错，成功则返回一个形状可信的值。问题是：zod schema 与生成的类型是两份独立定义，它们同样会漂移。解决办法是让编译器检查两者的双向兼容。

两行赋值看起来笨拙，却是 2022 年最实用的契约对齐手段。它们要求两个类型互相可赋值，字段增减、可空性差异、枚举取值不同都会导致其中一行失败。把这段代码放在校验模块里，任何人改了 zod schema 却忘了同步 spec（或反之），都会在类型检查阶段被拦住。若项目启用了严格的未使用变量检查，可以用 void 引用一下，或把检查写进一个永不调用的函数里。

需要提醒的是，双向可赋值并不等于完全相等。可选字段与 T | undefined 在默认编译选项下可以互相赋值，readonly 修饰也不影响赋值兼容性。但对日常的字段漂移来说，这个强度已经足够。若追求更严格的相等判断，可以写一个条件类型比较两边的键集合，只是这类工具类型本身也需要维护，收益未必抵得上成本。

错误响应也要建模

很多团队的成功响应写得很细，错误响应却只有一句 message: string，前端只能靠状态码猜。既然类型是生成的，错误体也应当进入 components/schemas，并且按状态码分别引用。前文的 Error 只有一个 code 与 message，实际项目里通常还需要 details、traceId、字段级错误列表。把这些结构定义清楚，前端才能写出可靠的提示逻辑，而不是在 catch 里打印一句“请求失败”。

服务端的统一错误处理也应当围绕这个类型展开：业务层抛出带 code 的领域错误，框架层把它映射成对应的状态码与错误体，再由一个地方保证序列化结果符合 schema。类型在这里的作用不是阻止运行时错误，而是保证错误的“形状”在前后端之间一致。一个 404 返回了 HTML 错误页，前端却按 JSON 解析，这类问题在类型层面无法发现，只能靠契约测试或边界校验兜底。

契约演进：把兼容性判断交给 CI

有了生成链路之后，spec 的每一次改动都会扩散成类型变化。这既是好事也是风险：好事是漂移会立刻暴露，风险是一次不经意的字段重命名可能让下游全部编译失败。因此需要一套判断“什么算破坏性变更”的规则，并把它放进持续集成。

先看相对安全的变更。新增可选字段通常被认为兼容：老客户端不认识它，会忽略；新客户端可以读取。前提是客户端的对象处理不会因为多出一个键而出错，例如某些做严格字段白名单校验的代码，或者把对象直接展开后逐键渲染的表格。新增接口、新增响应状态码（前提是客户端有默认分支）一般也兼容。放宽约束，例如把必填改为可选、把枚举换成字符串、把 minimum 调低，对消费方通常安全，但对服务端自身可能意味着更多分支要处理。

扩展枚举是一个容易被低估的变更。类型层面它是“联合变宽”，老代码不会编译失败，但运行时会走进未处理的分支。若前端用 switch 穷举状态且没有 default，新枚举值会让界面空白；若后端把枚举值直接映射成数据库字段，还可能触发约束错误。比较稳妥的约定是：枚举只增不减，且所有消费方必须写兜底分支；新增值要提前通知，必要时通过 feature flag 控制放量。

真正的破坏性变更清单并不长，但每一条都值得写进团队规范：删除或重命名字段；修改字段类型；把可选字段改为必填；移除 nullable；删除枚举值；删除接口或路径；修改路径参数名；删除响应状态码；改变鉴权方式；改变默认值语义。这些变更要么让老客户端编译失败，要么让它在运行时拿到不符合预期的数据。前者尚可接受，后者才是事故来源。

识别靠人眼不够，工具更可靠。oasdiff 可以比较两份 spec 并列出破坏性差异，openapi-diff 这类工具也能做类似的事，输出形式不同，思路一致：把新旧规范都解析成模型，逐层比对路径、操作、参数、schema。

生成与比对这两条命令解决的是“产物陈旧”问题。如果开发者改了 spec 却没有重新生成，或者手工修改了生成文件，git diff 会报出差异，CI 随即失败。它比任何口头约定都有效，因为检查发生在合并之前，而不是等到联调。若团队不把产物提交进仓库，则改为在 CI 里连续生成两次并比较。

一条完整的流水线大致包含四步：先用 Spectral 之类的 linter 检查 spec 的规范性，例如是否缺少 operationId、是否使用了未定义的 $ref；再运行兼容性比对，把破坏性变更标出来供评审；然后重新生成类型并跑 tsc --noEmit，确认所有消费方仍能编译；最后执行契约测试，用真实响应去校验 spec。四步的严格程度可以按分支区分：主干要求全绿，特性分支允许破坏性变更但必须打标签，等到发布窗口再合并。

版本号策略也应当与这套机制配合。规范里的 info.version 不是装饰，主版本变化意味着允许破坏性变更，次版本只做兼容扩展。与其指望人记住，不如让 CI 在检测到破坏性变更时要求同时提升主版本号。至于契约的评审流程、消费者驱动契约等内容，属于契约管理的范畴，本文不展开；运行时校验 schema 的设计细节，也另有专文讨论，这里只关心它与生成类型如何对齐。

小结

OpenAPI 到 TypeScript 的生成链路，价值不在于省下几个 interface，而在于让契约成为编译期的事实来源。本文的要点可以归为四句：先确认规范版本与工具支持，3.0 与 3.1 的可空性写法不同，生成结果不能想当然；理解 schema 到类型的映射规则，尤其警惕 additionalProperties 带来的索引签名与联合过宽；客户端保持薄封装，把断言集中在网络边界，服务端用生成的响应类型约束 handler，并让 zod schema 与生成类型双向对齐；最后把 spec diff、重新生成与类型检查放进 CI，用工具而不是记忆来判断兼容性。

落地时建议从一个接口开始，跑通“改 spec、生成、编译、测试”的闭环，再逐步扩大范围。生成物要么提交并检查漂移，要么完全不提交并在构建时生成，不要停留在两者之间。至于那些 spec 里本来就模糊的部分，生成器帮不了忙，只能回到设计层面把字段、可空性与错误结构说清楚。
