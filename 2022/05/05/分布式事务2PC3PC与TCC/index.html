分布式事务：2PC、3PC 与 TCC

本文属于《Go 微服务架构》第 27/35 篇
上一篇系列目录下一篇

把一次下单拆成库存、账户、订单三个服务之后，“要么全成功、要么全失败”这句在单库里理所当然的话，一旦跨了服务就变成了需要协议来保证的事情。本文从最朴素的 2PC 讲起，经过试图修补它的 3PC，最后落到业务层的 TCC，重点不在背流程，而在看清每种协议把风险转移到了哪里。读者需要了解数据库事务与微服务调用，读完后应能判断自己的场景该不该引入分布式事务、还要补哪些工程措施。

一个订单拆成三个服务

先看一个具体的场景。用户下单，系统要做三件事：在订单库写入一条订单，在库存库把商品的可售数量减一，在账户库把用户的余额扣掉。三个库若在同一个 MySQL 实例里，一个本地事务就能解决：任何一步失败就全部回滚。

拆成微服务后，情况变了。订单服务调用库存服务，库存服务调用账户服务，每次调用都是一次网络请求，每个服务背后是独立的数据库。此时没有哪个数据库能替我们管住另外两个库的提交，本地事务的边界到此为止。工程上把这类问题称为分布式事务：多个参与者各自持有资源，需要就“一起提交”还是“一起回滚”达成一致。

讨论协议之前，先把两个角色固定下来。协调者（coordinator）负责发起决议、收集投票、下达最终命令；参与者（participant）负责执行本地操作并投票。协调者可以是独立的事务管理器，也可以是发起调用的服务。三种协议的区别，很大程度上就是这两个角色“谁在什么时候等谁”的区别。

还有一个前提常被忽略：网络不可靠，消息会丢、会延迟、会重复，节点也可能在等待回复时宕机。所有分布式事务协议，本质上都是用日志、超时与重试去逼近一个确定结果，理解这一点，后面每一种“缺陷”都不算意外。

两阶段提交：先投票，再执行

2PC（Two-Phase Commit）是最经典的方案，顾名思义分成两个阶段。

第一阶段是准备阶段，也叫投票阶段。协调者向所有参与者发送 prepare 请求，参与者在本地开启事务、执行写操作、把 undo 与 redo 写入日志，然后锁住相关资源，回复“可以提交”或“无法提交”。此时数据并未真正生效，参与者只是承诺了“我有能力提交”。

第二阶段是提交阶段。如果所有参与者都投了赞成票，协调者写入 commit 记录，向所有人发送 commit，参与者释放锁、完成提交，并回 ack；只要有一个参与者投了反对票，或者等待超时，协调者就发送 rollback，参与者用 undo 日志回滚。协调者收到全部 ack 之后，才能把这次事务的日志删掉。

sequenceDiagram
    participant C as 协调者
    participant A as 库存服务
    participant B as 账户服务
    C->>A: prepare
    C->>B: prepare
    A-->>C: yes（已加锁）
    B-->>C: yes（已加锁）
    C->>A: commit
    C->>B: commit
    A-->>C: ack
    B-->>C: ack

流程本身不复杂，代价却相当实在，通常归纳为三个问题。

第一是同步阻塞。参与者在回复 yes 之后、收到最终命令之前，必须一直持有锁，其他事务想改同一行数据只能排队。协调者迟迟不发 commit，锁等待时间就会迅速恶化；事务越长、参与者越多，阻塞窗口越大。

第二是协调者单点。协调者在发出 prepare 之后崩溃，参与者就卡在“已投票、等命令”的状态里，既不能擅自提交，也不能擅自回滚，只能等协调者恢复后查日志。若协调者的日志也丢了，参与者可能永久悬挂，往往需要人工介入。

第三是网络分区下的不一致。协调者做出了 commit 决议，消息只送达了一部分参与者，剩下的参与者收不到命令，恢复后按超时策略自行猜测，就可能出现一部分节点已提交、另一部分已回滚的局面。这不是实现得不好，而是 2PC 在分区容忍上的固有短板。

现实中最常见的 2PC 实现是 XA 规范。它把上述角色映射到数据库驱动上：应用程序作为协调者，各数据库作为参与者，通过 XA 接口完成 prepare 与 commit。XA 的价值是把协议标准化，让不同厂商的数据库坐进同一场投票；局限也来自 2PC 本身，长事务持锁、依赖外部事务管理器、跨库性能损耗都难以绕开。因此 XA 更适合参与者少、事务短、对强一致有硬要求的场景，而不是高并发的交易主链路。

三阶段提交：把等待切成两段

3PC（Three-Phase Commit）试图缓解 2PC 的阻塞与单点问题，做法是把第一阶段再拆一刀，并把超时写进参与者的本地决策规则。

三个阶段分别是 CanCommit、PreCommit 和 DoCommit。CanCommit 阶段协调者只问一句“你有没有条件执行”，参与者检查自身状态后回答 yes 或 no，此时并不加锁、也不写日志。协调者收齐赞成票后进入 PreCommit，参与者才真正执行写操作、写日志、加锁，并回复 ack。最后 DoCommit 阶段协调者下达提交，参与者完成提交并回 ack。

sequenceDiagram
    participant C as 协调者
    participant P as 参与者
    C->>P: CanCommit
    P-->>C: yes（未加锁）
    C->>P: PreCommit
    P-->>C: ack（已加锁）
    C->>P: DoCommit
    P-->>C: ack

超时假设是 3PC 的关键。参与者在 PreCommit 之后如果长时间等不到 DoCommit，会默认协调者已经决定提交，于是自行提交；而在 CanCommit 阶段超时，则默认回滚。这样一来，即使协调者失联，参与者也有一个明确的出路，不必无限期持锁，阻塞范围被压缩了。

但它没有解决根本问题。首先，超时假设本身依赖时钟与网络延迟在合理范围内，一旦分区导致部分参与者提前提交、部分参与者还在等待，结果依然可能不一致。其次，3PC 多了一轮交互，正常路径的延迟更高。再次，参与者在 PreCommit 之后仍要持锁，只是时间略短。工程上真正部署 3PC 的系统很少，它更多是理论参照：单靠增加阶段和超时，无法在异步网络里同时拿到一致性与可用性。

TCC：把锁从数据库搬到业务

2PC 与 3PC 都把资源锁在数据库层面，TCC 换了个思路：既然数据库的长事务锁代价高，那就把“预留资源”这件事交给业务代码自己做。

TCC 对应 Try、Confirm、Cancel 三个操作。Try 做业务检查和资源预留，Confirm 确认使用预留资源，Cancel 释放预留资源。三个操作都由业务方实现，事务管理器只负责按顺序调用、记录日志、在失败时重试。

回到下单的例子。库存服务的 Try 不是直接把可售数量减一，而是把数量从“可售”挪到“冻结”，账户服务的 Try 则是把余额从“可用”挪到“冻结”。这两个动作各自是本地事务，提交很快，不会长时间持有行锁。订单服务的 Try 写入一条状态为“处理中”的订单。

Confirm 把冻结数量真正扣掉，Cancel 把冻结数量还回可售，两者都只操作本库，且都要求幂等。整个链路里，事务管理器在 Try 全部成功后依次调用 Confirm；任何一个 Try 失败，就对已成功的那些调用 Cancel。资源在 Try 阶段已经预留，Confirm 与 Cancel 理论上不会失败，实际却可能因网络抖动、服务重启而反复重试，这正是 TCC 最需要小心的地方。

TCC 的优点很明显：没有数据库层的长事务锁，资源只在业务语义上被占用，吞吐好于 XA；事务管理器也不必侵入数据库，跨语言、跨存储都能用。代价是侵入性强，每个参与方都要写三个方法，还要处理下面这些边界情况。

TCC 的三个坑：空回滚、悬挂与幂等

第一个坑是空回滚。管理器调用库存服务的 Try，请求丢了或超时未处理，管理器判定失败，转而调用 Cancel。可这时 Try 根本没执行过，Cancel 却来了。如果直接“解冻”，就会把不属于这笔事务的库存放出来，账目立刻错乱。正确做法是让 Cancel 先查流水：若没有对应的 Try 记录，就写入一条 Cancel 记录并返回成功，业务数据不动。

第二个坑是悬挂。Try 因网络拥堵迟迟未到，管理器超时后完成了 Cancel，那个迟到的 Try 才抵达并执行成功，预留的资源再无人释放，库存就永久冻结。解决办法是在 Try 执行前检查是否已有 Cancel 记录，若有则拒绝执行。空回滚与悬挂，本质是同一枚硬币的两面，都靠“先落流水、再动数据”来判别。

第三个坑是幂等与防重。Confirm 和 Cancel 都可能被重复调用，重试是分布式系统的常态。实现上通常建一张事务流水表，以事务号和阶段作为唯一键，每次操作先尝试插入，插入成功才执行业务变更，重复请求直接返回上次的结果。这张表同时也是一份对账依据，出问题时能查到每笔事务究竟走到了哪一步。

flowchart TD
    A[收到 Try] --> B{已有 Cancel 记录?}
    B -- 是 --> C[拒绝执行，防悬挂]
    B -- 否 --> D{已有 Try 记录?}
    D -- 是 --> E[直接返回成功，幂等]
    D -- 否 --> F[冻结资源并写流水]
    G[收到 Cancel] --> H{已有 Try 记录?}
    H -- 否 --> I[写 Cancel 流水，空回滚]
    H -- 是 --> J[解冻资源并写流水]

TCC 的一致性不是免费的，它把数据库原本替你做的事，变成业务代码必须自己承担的约束，流水表、唯一键、状态机与重试策略缺一不可。

三种协议横向对比

把三种协议放在同一张表里看，差异会清楚很多；具体系统仍要以自身压测与故障演练为准。

维度 2PC / XA 3PC TCC
一致性 强一致，分区时可能不一致 强一致倾向，靠超时假设 最终一致，靠补偿收敛
阻塞 准备后全程持锁，阻塞明显 持锁窗口略短，仍有阻塞 无数据库长事务锁
性能 较低，随参与者增多下降 更低，多一轮交互 较高，但业务实现成本高
侵入性 低，数据库驱动层支持 低，但落地实现少 高，每个参与方写三个方法
适用场景 短事务、少参与者、强一致 教学与理论参照 高并发交易、资源可预留

从表中能读出一条主线：一致性越强、侵入性越低，往往意味着阻塞越重；想减少阻塞，要么把一致性降级为最终一致，要么把复杂度转移到业务代码。选型其实是在选“愿意把复杂度放在哪里”。

工程建议：先问要不要，再问用哪个

第一原则是能不分布式就不分布式。如果两个操作的数据可以放在同一个库，就不要拆成两个服务再想办法让它们一致；如果业务上可以接受短暂不一致，优先考虑本地消息表或事务消息做最终一致，或者用 Saga 把长流程拆成一系列可补偿的本地事务。这两种方案的补偿粒度更粗、实现更简单，适合订单履约这类流程长、步骤多的场景。本文只讨论 2PC、3PC、TCC 三种协议本身，Saga 与异步最终一致的细节另文展开。

第二原则是能用 TCC 就别用 XA 扛高并发。XA 适合参与方少、事务短的场景，比如两个库之间的一次性数据搬迁；放在每秒数千笔的交易链路上，锁等待会成为瓶颈。反过来，如果团队没有能力维护流水表与对账任务，贸然上 TCC 只会把问题推迟到故障发生的那一天。

第三原则是必须用 TCC 时，把幂等与对账当成一等公民。幂等靠事务号加唯一键，Try、Confirm、Cancel 都必须可重复执行；防重靠状态机，明确每个事务号允许的状态迁移；对账靠定时任务，扫描长时间停在“处理中”的事务，与下游流水比对，修正悬挂或空回滚的残留。再把重试次数、补偿失败率纳入监控，才算真正落地。

分布式事务不是越强越好，而是越匹配越好：先想清楚业务能容忍多久的不一致、能承担多少实现成本，再回头挑协议。

小结

2PC 用 prepare 与 commit 两轮投票换取强一致，代价是同步阻塞、协调者单点与分区下的不一致，XA 是它最标准的工程形态。3PC 用 CanCommit 与超时假设缩短了阻塞窗口，却没有消除分区带来的分歧，更多是理论参照。TCC 把资源预留交给业务，用 Try、Confirm、Cancel 换掉数据库长事务锁，代价是侵入性与空回滚、悬挂、幂等这些必须自己处理的边界。工程上应先判断是否真的需要分布式事务，优先本地事务、消息最终一致或 Saga；确实需要 TCC 时，事务流水表、状态机、幂等键与定时对账缺一不可。
