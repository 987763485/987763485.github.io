微服务链路追踪落地

本文属于《Go 微服务架构》第 34/35 篇
上一篇系列目录下一篇

一次用户请求往往要穿过网关、订单、库存、支付和消息队列，任何一个环节变慢，用户看到的都只是一次超时。日志能说明“谁报了错”，却很难回答“请求经过了哪些服务、时间花在了哪一段”。本文从调用链的数据模型讲起，依次讨论上下文传播、埋点粒度、采样策略、存储成本与落地步骤，并用 OpenTelemetry 的 Go SDK 给出示例。本文适合准备把链路追踪接进生产系统的读者；读完后应能画出自己系统的 Span 树，并制定可执行的接入计划。Jaeger 的部署与运维留待专门文章讨论。

从一次慢请求说起：调用链为什么难以还原

假设一个电商系统在促销日出现了接口变慢：网关的 p99 从 120 ms 涨到 900 ms，错误率没有明显上升。工程师打开各服务的日志，看到的是这样的景象：网关记录了“请求耗时 903 ms”，订单服务记录了“查询订单耗时 41 ms”，库存服务记录了“扣减库存耗时 37 ms”，支付服务没有错误日志。把这些数字加起来不到 100 ms，剩下的 800 ms 不知去向。

这类问题在单体应用里几乎不会出现，一次调用栈就能说明一切。到了微服务架构，请求被拆成多个进程、线程池和网络跳转，调用栈被切断，日志之间只剩时间戳这一条线索。而时间戳并不可靠：机器时钟存在漂移，日志异步落盘的时间不等于业务发生时间，一次重试还会产生多条记录。仅凭“差不多同一秒”拼接日志，结论往往似是而非。

链路追踪要解决的正是这个问题。它为一次请求分配一个全局唯一的标识，并在请求经过的每个服务、每个组件上记录一段带起止时间的操作，再通过这些记录之间的父子关系把调用树还原出来。工程上通常把这三件事分开看：

  1. 标识与传播：如何让所有服务知道“这是同一个请求”，以及“我这一段是谁调用的”。
  2. 埋点与建模：在哪些位置记录 Span，每个 Span 带哪些属性，如何命名。
  3. 采集与使用：数据送到哪里、采样多少、保留多久、排障时怎么查。

三者缺一不可。只做标识不埋点，等于给日志加了一个字段；只在入口埋点不传播，调用链会在第一个跨进程调用处断掉；埋点齐全但采样策略粗暴，出故障时恰好没有留下证据。本文后面的章节基本按照这个顺序展开。

在展开之前，先把本文反复使用的几个词定下来。Trace 指一次完整请求的调用树，TraceID 是它的全局标识；Span 指树上的一个节点，代表一段有始有终的操作，SpanID 是节点标识；父子关系由父 Span 的 SpanID 记录在子 Span 中，从而构成树。除此之外，还有一类不构成父子关系、但需要建立因果联系的情况，例如异步消息的生产与消费，这会在讲传播时单独讨论。

还有一个容易被忽略的前提：链路追踪只能还原“被埋点的部分”。如果一段逻辑既没有自动埋点，也没有手动埋点，它在调用树上就是空白，时间会凭空消失。因此下文讨论“慢在哪里”时，实际上讨论的是“哪些位置被记录成了 Span”。明白了这一点，后面的埋点粒度与采样取舍就更容易理解。

TraceID、SpanID 与父子关系

TraceID 与 SpanID 的长度和生成方式，在 W3C Trace Context 规范里有明确规定：TraceID 为 16 字节，即 32 个十六进制字符；SpanID 为 8 字节，即 16 个十六进制字符。它们必须随机生成，不能包含时间、机器号等可推测的信息，也不能全为 0。随机性带来两个好处：一是不需要中心节点分配，任何服务都能在入口处直接生成；二是不同系统之间碰撞的概率低到可以忽略。不要用请求参数、用户 ID 或时间戳拼接“唯一 ID”，既可能重复，也会泄露业务信息。

一个 Span 记录的核心字段并不多，但每个都有明确用途。标识部分包括 TraceID、SpanID 和父 SpanID；描述部分包括名称、SpanKind、开始时间、结束时间、属性、事件和状态；此外还有资源属性，用来描述产生这个 Span 的进程，例如服务名、主机名、容器名。结束时间减开始时间就是这段操作的耗时，但这个耗时只应在同一台机器内比较，跨机器的绝对时间对齐交给后端的展示层处理。

父子关系是调用链的骨架。服务 A 调用 B 时，A 产生客户端 Span，B 产生服务端 Span，后者以前者为父，同一笔业务便在不同进程间串成一棵树。容易混淆的是耗时：客户端 Span 覆盖序列化、网络、排队、服务端处理与反序列化；服务端 Span 只覆盖请求进入之后、响应写出之前的处理。两者之差正是网络与排队开销，也是排查“服务端很快但接口很慢”的关键证据。

SpanKind 用来表达节点在调用关系中的角色，常见取值有 server、client、producer、consumer 和 internal。入口服务产生的根 Span 通常是 server，它没有父节点；调用下游时产生 client；写消息队列时产生 producer；消费消息时产生 consumer；服务内部的缓存访问、业务编排则用 internal。正确设置 SpanKind 不只是为了好看，很多后端会据此计算服务依赖图，也会据此区分“自身耗时”和“等待下游耗时”。如果把内部调用错标成 server，依赖图里就会多出并不存在的边。

从图中可以读出一条重要信息：订单服务自身只花了很少的时间，绝大部分时间耗在等待库存服务上；而库存服务的服务端 Span 有 815 ms，内部访问 Redis 只有 3 ms，说明时间既不在网络上，也不在 Redis 上，而是在库存服务自己的处理逻辑里。如果没有这棵树，仅凭“库存服务耗时 815 ms”这一条日志，排查方向会完全不同。

除了父子关系，还有 follows-from 与 link 两种表达。前者表示“后者由前者触发，但前者不等待后者结束”，适合异步任务；后者允许一个 Span 关联多个 Span，适合一批消息来自多个生产者的消费场景。实际使用时宁可用 link 保留因果，也不要把不相干的调用硬塞进父子链，否则耗时统计会失真。

重试同样要小心。失败后重试三次会产生三个并列的客户端 Span，共享同一个父节点，而不是首尾相接的链，这样总耗时里的重试成本才看得见。重试之间的退避等待若未被 Span 覆盖，会表现为父子 Span 之间的空隙，属于正常现象。

上下文传播：HTTP、gRPC 与消息队列

有了数据模型，下一个问题是：TraceID 和父 SpanID 如何从 A 传到 B。这个过程叫上下文传播，分注入与提取两步：发送方把当前 Span 的上下文写进载体，例如 HTTP 头；接收方从载体读出上下文，恢复出远程父 Span。载体形式随协议而变，内容遵循同一套规范，跨语言、跨框架才能互通。

在 HTTP 场景，W3C Trace Context 规定使用 traceparent 头，格式为“版本- TraceID-父 SpanID-标志位”。一个合法的例子是 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01，其中 00 是版本，最后两位 01 表示采样标志。另有 tracestate 头，用于承载厂商扩展的键值对，顺序有意义，一般由 SDK 维护，业务代码不应随意改写。需要强调的是，traceparent 是标准头，不要另起炉灶用 X-Trace-Id 之类的自定义头作为主通道；自定义头可以作为兼容手段，但不能替代标准，否则接入第三方组件时处处要写适配。

传播能否成功，往往卡在中间设施而不是业务代码。网关、反向代理、服务网格的数据面、API 管理平台，如果配置了请求头白名单，很可能把 traceparent 和 tracestate 过滤掉。排查“链路在某处断掉”时，第一步应逐跳确认标准头是否还在，而不是先怀疑 SDK；同时注意头名大小写与 HTTP/2 要求的小写形式。

gRPC 的传播依赖 metadata，键名同样使用小写的 traceparent 与 tracestate。使用官方拦截器时，客户端负责注入、服务端负责提取，业务代码不必手动处理。metadata 会随每次调用传输，不宜塞入过大的内容；用户身份、租户信息更适合放进 Baggage 统一管理，而不是散落在各个拦截器中。

消息队列的传播更复杂，因为生产与消费在时间上解耦。生产端发送前把上下文注入消息属性，消费端收到后提取；Kafka 用消息头，RocketMQ 用用户属性，RabbitMQ 用 headers。关键在于：提取必须发生在“处理这一条消息”的上下文中，而不是消费者启动时。消费者通常多线程、批量拉取，若只在启动时提取一次，所有消息都会挂到同一个父 Span 下，调用链立刻失去意义。

Baggage 用于携带不属于追踪元数据、但需要跨服务传递的业务键值对，例如租户标识、用户分层、灰度标记，标准头为 baggage，格式类似 tenant.id=acme,user.tier=gold。它让下游不必层层透传参数就能拿到上下文，也便于日志、指标带上租户维度。但它会随每个请求传输且跨越信任边界，因此必须控制体积，绝不能放密码、令牌、身份证号等敏感信息。建议只放少量、低敏感、稳定的字段，并加统一前缀。

传播失败最隐蔽的情况，是上下文在进程内丢失。Go 的 context.Context 需要显式传递，一旦用了 context.Background()，后面的 Span 就会变成新的根；Java 的 ThreadLocal 在切换线程池时不会自动传递；Node.js 的回调链若没有异步上下文机制同样会断。这类问题表现为“调用链在服务内部断成两截”，排查时应重点检查线程池提交、定时任务、go func 启动的协程，以及手动创建的空上下文。

为了减少这类问题，接入时应当把传播器配置成组合形式：TraceContext 负责追踪，Baggage 负责业务字段，两者都不可少。下面的初始化代码通常放在服务启动阶段，只执行一次。

OpenTelemetry 的 2022 年口径

OpenTelemetry 由 OpenTracing 与 OpenCensus 合并而来，目标是提供与厂商无关的 API、SDK 和采集协议。到 2022 年上半年，追踪规范已稳定在 1.x，Go SDK 为 1.7.0（2022 年 4 月发布），Collector 仍在 0.x 阶段迭代。指标信号在部分语言中可用，日志信号尚未稳定，本文的讨论集中在追踪上。选型时要注意：规范、SDK、Collector 三者独立演进，不能用一个版本号概括整个项目。

理解 OpenTelemetry 的关键，是分清 API 与 SDK。API 只定义接口和一个默认的空实现，库作者依赖 API 埋点，这样即使使用方没有配置 SDK，调用也不会失败，只是不产生数据。SDK 才是真正的实现，负责创建 Span、采样、排队、导出。这种拆分解决了一个长期痛点：公共库不必强迫业务选择某个后端，业务也不必为了换后端而改遍所有依赖。

SDK 的核心对象是 TracerProvider。它持有资源信息、采样器和 SpanProcessor，相当于追踪能力的容器。Tracer 从 Provider 获取，用来创建 Span。SpanProcessor 在 Span 开始和结束时被回调，最常见的是 BatchSpanProcessor：它把结束的 Span 放进队列，按批量和超时两个条件触发导出，避免每个请求都同步写网络。与之相对的 SimpleSpanProcessor 是同步导出，只适合本地调试。

导出由 Exporter 完成。OTLP 是 OpenTelemetry 原生的协议，支持 gRPC 与 HTTP 两种传输，推荐作为默认选择；Jaeger、Zipkin 等后端也有对应的 Exporter，但长期看 OTLP 的兼容性最好。下面的代码展示了一个最小可用的初始化过程，包含资源、采样器、批处理和 OTLP 导出。

Collector 通常部署在应用与后端之间，由三类插件构成：Receiver 接收数据，支持 OTLP、Jaeger、Zipkin 等协议；Processor 加工数据，例如批量、内存限制、属性增删、尾部采样；Exporter 写出数据，可送到 Jaeger、Tempo、ClickHouse 或对象存储。它既可以每台机器部署一个 agent，也可以集中部署成 gateway，前者就近接收，后者便于统一采样与出口管理。Collector 不是必须的，但一旦涉及采样、脱敏、多后端分发，它几乎是必选项。

埋点粒度与语义约定

埋点不是越多越好。Span 数量直接决定存储与计算成本，而大量低价值的 Span 只会让调用树变得难以阅读。合理的做法是先确定“必须回答的问题”，再决定在哪里埋。通常一个请求至少要能回答：入口是谁、调用了哪些下游、每个下游耗时多少、数据库和缓存访问了几次、消息是否发出、错误发生在哪一步。

入口埋点一般交给框架。HTTP 服务使用 otelhttp 包装 Handler，gRPC 服务注册服务端拦截器，消息消费者在拉取循环里为每条消息创建 consumer Span。出口埋点同样优先自动：HTTP 客户端使用带追踪的 Transport，gRPC 客户端注册拦截器，数据库使用驱动包装层，Redis 使用官方或社区提供的钩子。自动埋点的价值在于一致性强、不会漏，缺点是名字和属性往往由库决定，需要团队统一配置。

手动埋点应留给自动埋点覆盖不到、排障时却必须看的地方，典型有三类：业务编排的关键阶段，如“校验库存”“计算优惠”；不在标准协议内的外部 SDK 调用，如支付网关、短信服务；缓存与消息的业务语义，如是否命中、是否重复消费。手动 Span 不宜过细，一个函数一个 Span 会让调用树膨胀，通常以“可独立失败、可独立计时的一步”为粒度。

Span 命名是最容易被忽视的规范。名字应当低基数、可聚合，通常由“操作类型 + 目标”构成，例如 GET /orders/{id}、OrderService/GetOrder、SELECT orders。绝对不能把用户 ID、订单号、完整 URL 放进名字，否则后端会为每个请求创建一个新的“操作”，聚合视图彻底失效，索引也会膨胀。路径参数要使用路由模板而不是真实值，查询字符串应当剥离，只把必要的参数放进属性。

属性命名应遵循语义约定。HTTP 相关使用 http.method、http.url、http.status_code、http.route；gRPC 使用 rpc.system、rpc.service、rpc.method；数据库使用 db.system、db.name、db.statement；消息队列使用 messaging.system、messaging.destination。这些名字在 2022 年的规范中是稳定的，跨语言、跨后端都能被识别。业务自定义属性应加统一前缀，例如 app.，避免与标准属性冲突，也便于后端按前缀做索引策略。

属性值有两个红线。一是禁止高基数，把完整 SQL 参数、请求体、用户输入写进 db.statement，既拖垮索引又可能泄露隐私；二是禁止敏感信息，密码、令牌、身份证号、银行卡号都不能出现在 Span 里。稳妥的做法是只记录 SQL 模板和参数个数，业务字段记录枚举值或分桶结果。需要排查具体参数时，应通过日志系统在受控条件下查询。

数据库与缓存的埋点还有细节。数据库 Span 应区分 db.operation 与 db.statement，前者用于聚合，后者用于定位慢语句；连接池等待往往不计入 SQL 执行时间，若“应用耗时远大于 SQL 耗时”，就要检查取连接的排队。缓存 Span 应记录是否命中、Key 的前缀而非完整 Key，批量操作记录批量大小。producer Span 应在发送确认后结束，consumer Span 应覆盖业务处理而不只是反序列化，否则“消费慢”会被误判为“拉取慢”。

自动与手动埋点的比例取决于系统成熟度。接入初期以自动为主，快速拿到全貌；排障深入后再补关键手动 Span。无论哪种方式，都应把 Span 数量纳入评审：新功能上线后观察它为每个请求增加了多少 Span，超过预算就重新设计粒度。

采样：头部、尾部与成本

全量采集在生产环境几乎不可行。假设入口 QPS 为 2000，每个请求 20 个 Span，每秒就是 4 万个，一天约 34 亿个（示意值）。即使存储扛得住，查询与索引成本也会失控。采样用一部分数据代表整体，但采样位置与时机不同，得到的结论也完全不同。

头部采样发生在请求入口，由根 Span 决定“这条 Trace 要不要留”，并把决定写进 traceparent 的采样标志，后续服务通过 ParentBased 继承，保证一条链要么全留、要么全不留。常见策略是固定比例，例如 10%，实现简单、开销小，缺点是决策时还不知道请求会不会失败、会不会变慢。它对高 QPS 的普通请求合适，对低频关键接口却不友好：一天几百次调用的支付回调，10% 可能恰好漏掉唯一一次故障。

限流采样是概率采样的补充，按“每秒最多保留 N 条”来控制，适合流量波动大的入口。它保证突发流量不会瞬间压垮后端，但同样无法预知结果。工程上通常把两者结合：先用限流兜住上限，再在限流额度内做概率抽取。需要强调的是，采样率必须可配置、可按路由或租户区分，不能硬编码在代码里，否则每次调整都要发版。

尾部采样把决策推迟到 Trace 结束之后，由 Collector 缓冲整条链，等 decision_wait 到期再判断。条件可以是延迟超阈值、状态为错误、包含特定属性，或按比例保留正常请求。错误和慢请求可以 100% 保留，正常请求只留少量样本，排障体验接近全量。代价是 Collector 要缓存数据，且同一条 Trace 的所有 Span 必须到达同一实例，否则每个实例只看到片段。解决方法是用 TraceID 做负载均衡，并给缓冲设置内存上限与淘汰策略。

采样对排障的影响必须提前想清楚。头部采样一旦丢弃就无法补录，因此对错误敏感的核心链路通常采用“基础比例 + 错误全留”；如果只能用头部采样，应把采样率与告警联动，故障期间临时调高。尾部采样依赖完整链路，一旦某段传播断了，延迟判断就会失真。无论哪种方案，都应保留一份低频但稳定的基线样本，用于容量规划与趋势分析。

Collector 的批处理与采样紧密相关。BatchProcessor 按数量与超时打包，减少网络请求和后端写入；MemoryLimiter 在内存接近上限时拒绝新数据；尾部采样要求先聚合同一条 Trace，再走批处理导出。三者的顺序和参数需要压测，不能照搬默认值。常见错误是把批处理超时设得过长，导致采样决策窗口与导出窗口互相等待，数据延迟到无法排障。

存储、索引与信号关联

追踪数据的存储大致分三类：Jaeger 式的“索引加存储”，常搭配 Elasticsearch 或 Cassandra；Tempo 式的“对象存储加少量索引”，成本低但查询能力有限；以及 ClickHouse 这类列式数据库，适合高写入量下的聚合查询。选型与部署不属于本文范围，这里只讨论与埋点、采样相关的成本问题。

索引字段应当少而精。必备的是服务名、操作名、开始时间、耗时、状态码和 TraceID；属性中只有经常用于筛选的少量字段值得建索引，例如 http.status_code、error、rpc.service。把全部属性都建索引，会让写入放大数倍，还会拖慢查询。一个实用的判断标准是：这个字段是否会出现在排障的第一句问话里。如果不会，就让它留在原始 Span 中，需要时再按 TraceID 取回。

保留期应当分层。原始 Span 通常保留 7 天，足够覆盖大多数故障的追溯窗口；采样后的聚合数据或慢请求、错误请求可以保留 30 天；更长时间的需求交给指标和日志，而不是追踪。很多后端支持按索引或按标签设置生命周期，例如 Elasticsearch 的 ILM、Tempo 的块保留策略。分层保留的前提是采样时给数据打上可区分的标记，否则清理策略无从下手。

追踪必须与日志、指标关联起来，否则排障时仍要在三个系统之间手工复制 ID。最基础的做法是在结构化日志中固定写入 trace_id 和 span_id，日志框架的字段名要统一，采集端才能建立跳转链接。更进一步是指标 exemplar：在直方图的样本上附带 TraceID，从延迟曲线的某个点直接跳到对应调用链。exemplar 需要客户端与采集链路支持 OpenMetrics 格式，Grafana 8.x 已经可以在图表中展示并跳转。这样形成的路径是“指标发现异常，exemplar 定位样本，追踪还原现场，日志查看细节”，比从海量日志里搜索高效得多。

关联还有一个前提：时钟。跨主机绝对时间不可比，展示层应以父子关系对齐时间轴。若出现“子 Span 早于父 Span 开始”，多半是时钟漂移或时区处理错误，应先校准 NTP，再统一使用 UTC。

落地步骤：从一条关键链路到排障流程

接入不宜一次铺开，建议分五步推进，每一步都要有可验收的产出。

  1. 打通一条关键链路：选下单这类跨三个服务、含数据库访问的链路，在测试环境全量采集，确认 Span 树完整、耗时可解释。
  2. 补齐跨进程传播：覆盖同步调用与消息队列，检查网关与代理的请求头白名单，处理线程池与异步任务中的上下文丢失。
  3. 统一命名与属性：按语义约定制定规范，把 Span 名、属性前缀、错误标记写入代码评审清单。
  4. 控制采样与成本：先按 10% 头部采样上线，观察一周再调整；对错误与慢请求启用尾部采样，按月核对 Span 量与账单。
  5. 建立告警与排障流程：让告警附带 Trace 查询链接，把“先看调用链”写进值班手册，并定期演练从告警到定位的完整路径。

推进时还有两点经验：公共库与规范由平台团队维护，业务团队只写少量手动 Span；效果用 Span 覆盖率、断链比例、定位耗时衡量，而不是接入了多少服务。

小结

链路追踪的难点不在 SDK，而在数据模型、传播覆盖与成本控制的配合。先打通一条关键链路，再补齐跨进程传播，随后统一命名、引入采样、建立排障流程，是风险最低的顺序。判断接入是否成功，不看 Span 数量，而看一次故障能否在几分钟内定位到具体服务与具体阶段。
