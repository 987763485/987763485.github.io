Rust 实现简单 KV 存储

本文属于《Rust 学习路线》第 62/68 篇
上一篇系列目录下一篇

很多后端工程师都动过自己写一个存储引擎的念头。它不像分布式系统那样要处理共识、网络分区与时钟漂移，却能把索引、日志、序列化、崩溃恢复这些底层构件完整地走一遍。本文用 Rust 2021 edition 实现一个单机、可持久化的 KV 存储，只支持 set、get、delete 三个操作，重点讲清楚一个存储引擎由哪些部件组成、每个部件为什么这样设计。读者不需要读过 LevelDB 的源码，但应当熟悉 Rust 的所有权、Result 与 trait。读完之后，你应当能独立判断：什么场景适合“内存索引加追加日志”，什么场景应当老老实实上数据库。

先把需求写死，后面所有设计都围绕它展开。这个存储面向单机、单进程、读多写少的场景，例如桌面应用的本地配置、边缘设备上的状态缓存、或者某个服务的元数据。它的接口只有三个方法：

明确不做的部分同样重要。本文不实现范围扫描，因此不需要有序索引；不实现事务，因此不需要 MVCC 与写冲突检测；不实现多进程共享，因此不需要文件锁与租约；当然也不涉及复制与共识。把这些删掉之后，剩下的问题反而更清楚：如何把一次写安全地落到磁盘，如何在重启后把状态恢复出来，以及如何在文件不断变大的时候回收空间。

衡量一个存储引擎通常看四个放大：写放大指实际写入磁盘的字节数与用户写入字节数之比；读放大指一次查询触及的磁盘页数；空间放大指磁盘占用与有效数据之比；再叠加一个恢复时间，即进程重启后重建可用状态所需的时间。本文的实现会在这四项之间做明显的偏科选择：写放大接近一，读放大为零（数据全在内存），空间放大靠压缩控制，恢复时间与日志长度成正比。理解这个偏科，比记住任何代码都重要。

三种引擎的取舍

在动手之前，先把候选方案摆到桌面上。最常见的三种做法是纯内存哈希表、追加日志加内存索引、以及以 B+ 树或 LSM 树为代表的页式或分层存储。它们并不是同一层面的竞品，很多人把“内存里的 HashMap”当成存储引擎，实际上它只是索引。

纯内存的 HashMap 最快，一次 get 就是一次哈希，没有系统调用，也没有序列化开销。问题在于进程退出数据就没了。如果数据可以从别处重建，例如从数据库加载的缓存，那么它完全够用；如果数据是唯一副本，它就只是缓存而不是存储。本文的目标是可持久化，所以 HashMap 只能作为索引的一部分，不能作为全部。

追加日志的思路是：所有修改都按到达顺序追加到文件末尾，内存里维护 key 到“文件偏移加长度”的映射，读取时按偏移去文件里取。写入是顺序 I/O，一次 set 只写一条记录，写放大接近一；读取命中内存索引后只读一小段，机械硬盘上也能获得不错的局部性。代价是删除必须写一条墓碑记录，旧值留在文件里，空间会持续膨胀，因此必须有压缩。这种结构常被称为 Bitcask 模型，Riak 在 2010 年前后公开过对应的技术报告，它的适用前提正是“所有 key 的索引能放进内存”。

B+ 树把数据组织成固定大小的页，更新是原地修改，读取按页定位，天然支持范围扫描与有序遍历。代价是随机写：修改一个叶子节点要写整页，还要维护父节点的分裂与合并；为了保证崩溃一致性，通常还要再配一份预写日志，形成“日志加页”的双写。数据库如 PostgreSQL、MySQL 的 InnoDB 都走这条路，成熟但实现量大。

LSM 树把随机写转成顺序写：先写内存表与预写日志，内存表满了就冻结成不可变的 SSTable，后台再分层合并。它适合写吞吐极高的场景，但读路径要跨多层查找，压缩策略稍有不慎就会产生严重的写放大。RocksDB、LevelDB 是典型代表。

方案 写路径 读路径 范围扫描 恢复方式 实现复杂度
纯内存 HashMap 内存 内存 需额外排序 无 极低
追加日志 + 内存索引 顺序追加 一次定位读 不支持 重放日志 低
B+ 树 随机页写 + WAL 按页查找 原生支持 重放 WAL 高
LSM 树 顺序写 + 合并 多层查找 支持 重放 WAL + 清单 很高

本文选择第二种。原因不是它最强，而是它在“能讲清楚”和“真的能用”之间取得了平衡：数据结构只有哈希表和数组，崩溃一致性只依赖一个日志文件，压缩逻辑可以独立测试。把这一套写透，再去读 LevelDB 的源码，会容易得多。

记录格式与序列化

追加日志的本质是一个只能追加的字节流。要让这个字节流在未来能被正确解析，每条记录必须自描述：多长、是什么操作、key 和 value 各占多少字节、内容有没有损坏。本文采用的布局如下：

字段 长度 说明
len 4 字节 小端 u32，表示 len 字段之后的字节数
crc 4 字节 对 op 到 value 末尾计算的 CRC32
op 1 字节 1 表示写入，2 表示删除
klen 4 字节 key 的字节数
vlen 4 字节 value 的字节数，删除时为 0
key klen 原始字节
value vlen 原始字节

长度前缀放在最前面，读取方才能知道该读多少字节。它同时承担了另一个职责：识别不完整的尾部。进程在写记录的中途被杀掉，文件末尾就会留下半条记录，此时按 len 读会越界，或者读到一半遇到 EOF，恢复程序据此判断“到这里为止都是坏的”，然后截断。

校验和解决的是另一类问题：长度字段本身可能被写坏，指向一个看似合法但完全错误的位置。把 CRC32 放在头部，读取时先校验再信任内容，就能把“碰巧长度合理”的垃圾挡在外面。这里选 CRC32 而不是 SHA-256，是因为威胁模型里没有恶意篡改，只有磁盘位翻转、断电导致的半写和程序 bug；CRC32 足以发现这些意外错误，而 crc32fast 这类库在现代 CPU 上能跑到每秒数 GB，开销可以忽略。如果未来要防止篡改，应当换成带密钥的校验，而不是简单加大哈希。

序列化有两个选择：用 serde 加 bincode，或者手写字节协议。bincode 紧凑、写法省事，一个 #[derive(Serialize, Deserialize)] 就能把结构体变成字节。但它不是自描述格式，字段顺序和类型一变，旧日志就再也读不出来；默认配置下整数用定长编码，改配置又会影响兼容性。日志是要长期保存的数据，格式稳定性比开发便利更重要。本文因此手写头部，只在长度和整数上使用定长小端编码，规则简单到可以写进一页纸。

接下来是最容易含混的部分：fsync 到底保证了什么。write_all 只是把字节交给内核，数据可能还在页缓存里；进程崩溃不影响它，因为内核会继续把脏页写回，但机器断电或内核 panic 就未必了。sync_data 会等待数据与必要的元数据真正到达持久介质，返回之后才算“这条记录安全”。sync_all 还会同步文件大小、修改时间等 inode 元数据，对追加日志来说通常没有必要，sync_data 更轻。

代价是延迟。一次同步在消费级 SSD 上通常是零点几毫秒量级，机械盘上可能到几毫秒甚至十几毫秒；折算下来，逐条同步的写入上限大致是每秒数百到数千次，具体取决于设备与文件系统，这里只给数量级。很多嵌入式存储默认不逐条同步，而是依赖操作系统的周期性回写，代价是断电时可能丢掉最后几秒的写入。本文把选择做成开关：默认开启逐条同步，追求吞吐时可以关掉，并在文档里明确“关闭后不保证机器级持久性”。这是把一致性语义交给调用方显式选择。

还有两个细节常被忽略。第一，新建日志文件后要对父目录执行一次 fsync，否则文件内容虽然落盘，目录项可能还没持久化，断电后文件会“消失”。第二，追加写不是原子操作，一次 write_all 可能只写进去一部分就返回错误，文件里留下半条记录。写入方无法回滚这半条记录，只能把错误上报；真正的清理发生在下一次启动的重放阶段。

为什么不在坏记录之后继续扫描、尝试抢救后面的数据？因为追加日志没有重同步标记。长度字段一旦不可信，读取位置就可能落在某个 value 的中间，把用户数据当成记录头解析，产生看似通过校验、实则完全错误的记录。要支持抢救，就得在格式里加入固定位置的魔数、定期插入同步点，复杂度会明显上升。本文选择“从第一条坏记录起全部丢弃”，并保证丢弃只可能发生在尾部。

还需区分两种损坏。第一种是断电或进程被杀导致的半写，损坏一定在文件末尾，截断是安全的。第二种是中间某条记录的位翻转，CRC 会失败，但后面的记录其实还在。此时截断会丢掉后面的全部数据。有没有更好的办法？没有索引之外的额外信息时，无法区分“中间坏”和“尾部坏”，而继续读的风险大于收益。生产系统通常用副本或定期备份覆盖这种情况；单机小存储接受这个边界，只打印损坏偏移。

并发模型

到目前为止，写入已经被 write_lock 串行化，索引由 RwLock 保护。这个模型是否够用，取决于瓶颈在哪里。索引操作是纯内存的哈希查找与插入，耗时在微秒级；真正的大头是 write_all 与 sync_data，尤其是后者，一次就要零点几毫秒到十几毫秒。多个写线程即使同时到达，也只能排队等同一块磁盘完成同步，增加线程并不会提高写入吞吐。写路径的并发度本来就被硬件限制住了。

读路径则不同。get 先在读锁里查到偏移，再去做一次 pread，两次操作都不修改共享状态。RwLock 允许任意多个读者同时进入，只有在写入更新索引时才会短暂阻塞。对于读多写少的场景，这正是想要的形态。标准库的 RwLock 不承诺公平性，理论上写者频繁到达时读者可能饥饿；但在本文的场景里，写者已经被 fsync 拖慢，实际到达率不高，读者饥饿的概率很小。如果确实遇到，可以换成 parking_lot 0.12 的 RwLock，它提供了更紧凑的实现和可选的公平策略，API 与本例几乎一致。

另一种常见做法是单写线程加通道：由唯一一个线程独占文件与索引，其他线程通过 mpsc 发送命令，并附带一个回执通道等待结果。它的最大好处不是“无锁”，而是可以合并同步。写线程从通道里一次取出一批命令，依次追加后只调用一次 sync_data，这一批写入共享同一次磁盘同步，吞吐可以从每秒几百次提升到几千次。这就是组提交的基本思路。代价是读路径变复杂：如果读也走同一个通道，所有读都被串行化，延迟明显上升；如果读直接共享索引，就仍然需要锁，只是把写锁换成了通道。

本文默认保留 RwLock 版本，因为它简单、可读、易于测试，而且与“读多写少”的定位吻合。当写入吞吐真的成为瓶颈，并且业务能接受“一批写入要么一起成功、要么一起失败”的语义时，再引入写线程与组提交。需要提醒的是，不要在异步运行时里直接调用本文的同步接口：fsync 会阻塞整个执行器的工作线程，应当放到阻塞线程池中执行，或者干脆像本文一样使用普通线程。

最后明确一致性边界。本文只保证单条记录的原子性：一次 set 要么完整可见，要么完全不可见，不会读到半条 value。多条记录之间没有事务，连续写 A、B 两条记录时崩溃，可能只有 A 生效。这个语义足以覆盖配置更新与会话状态，但不足以支撑转账。

压缩

日志只会变长，删除只是写墓碑，旧值永远留在文件里。压缩要做的就是：把当前仍然有效的 key 各写一条 Put 记录到新文件，丢弃所有墓碑和被覆盖的旧值，然后用新文件原子地替换旧文件。压缩后的文件大小约等于有效数据量，重放时间也随之下降。

触发策略通常看空间放大：当文件长度超过有效数据总长的若干倍，并且绝对大小超过一个下限时才压缩。倍数太小会导致频繁重写，倍数太大则浪费磁盘。本文取四倍与 16 MiB 两个条件同时满足，具体数值应当按业务写入模式调整，这里只是示意。压缩可以手动调用，也可以在后台线程里按写入次数触发。

压缩最难的部分不是复制，而是与并发写入共存。复制期间不能长时间停写，否则一次压缩可能让服务卡住数秒；也不能让新写入落到即将被替换的旧文件里，否则这些写入会随旧文件一起被丢弃。本文分成三个阶段：

  1. 复制阶段：记录当前文件末尾位置，遍历索引，把每个有效 key 的当前值写入临时文件，同时在新索引里记下新偏移。此阶段不持有写锁，写线程继续向旧文件追加，读线程继续用旧索引读旧文件。
  2. 追平阶段：获取写锁，阻止新的写入，把从起始位置到当前末尾之间的记录按原样追加到临时文件，并同步更新新索引。由于这段时间通常只有几十毫秒，写线程的等待可以接受。
  3. 交换阶段：刷新并同步临时文件，执行 rename 覆盖正式文件名，同步父目录，然后在索引写锁内替换索引与文件句柄，最后释放写锁。

为了能在运行时替换文件句柄，需要给 Store 补上 path、dir 与 compact_lock 三个字段，把 log 从 File 改成 RwLock<Arc<File>>，并在 get 中于索引读锁内克隆这个 Arc。这样即使交换发生，正在进行的读仍然持有旧文件的引用，文件不会被提前关闭；索引读锁与文件读锁的获取顺序固定为“先索引、后文件”，交换阶段按“先索引写锁、后文件写锁”获取，不会形成死锁。

追平阶段的关键是“按原样追加”。这期间可能有人删除某个 key，墓碑也要写进新文件，否则重放时这个 key 会从复制阶段的旧记录里“复活”。新索引则在遇到墓碑时删除对应条目。复制阶段写入的新记录与追平阶段重复时，后写的偏移覆盖先写的，最终指向最新值，重复本身无害。

临时文件与 rename 是崩溃一致性的核心。rename 在同一文件系统内是原子的：要么看到旧文件，要么看到新文件，不会看到半个。崩溃发生在复制或追平阶段时，正式文件从未被改动，重启后照常恢复，最多留下一个临时文件，启动时删掉即可。崩溃发生在 rename 之后、目录同步之前时，文件系统可能回退到旧名字，但旧文件本身是完整的；也可能已经指向新文件，而新文件在 rename 前已经同步过。两种结果都是合法状态，这正是“先写临时文件、再原子替换”的价值。

压缩还有两个成本。其一是磁盘空间：复制期间新旧两份文件同时存在，最坏需要两倍空间，空间紧张时要先检查剩余容量。其二是写放大：每有效字节被重写一次，频繁压缩会让磁盘写入量成倍增加。因此压缩频率要与写入量挂钩，而不是按固定时间间隔盲目执行。

测试与基准

存储引擎的测试重点与业务代码不同：正常路径容易覆盖，异常路径才是价值所在。本文把测试分成三层。

第一层是编解码的单元测试。除了常规往返，还要覆盖最短记录、空 value、包含零字节的 key、恰好达到长度上限的记录；对编码结果逐个字节截断，确认每个截断点都返回 Incomplete 而不是 panic；篡改任意一个字节，确认 CRC 能发现。若引入 proptest 1.0，可以用随机 key 与 value 做往返性质测试，比手工枚举更省力。

第二层是恢复测试。先写入若干记录，不调用任何关闭方法就直接重新打开，验证数据仍在；再把文件截断若干字节模拟半写；最后翻转中间某个字节，确认截断发生在正确位置。要模拟真正的进程崩溃，可以在测试中启动子进程持续写入，主进程发送 SIGKILL，然后重新打开文件校验“已确认写入的前缀”。这类测试应放在单独的集成测试里。

小结

本文用内存索引加追加日志实现了一个单机、可持久化的 KV 存储。真正支撑它的只有三条规则：记录自描述并带校验，先写日志再更新索引，压缩用临时文件加原子替换。它适合读多写少、数据能放进内存索引的场景，不适合范围扫描、事务与多机部署。把这三条规则写进测试，比追求更多功能更能保证数据不丢。
