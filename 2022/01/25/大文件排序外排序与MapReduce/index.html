大文件排序：外排序与 MapReduce

本文属于《算法与数据结构》第 9/13 篇
上一篇系列目录下一篇

排序算法的教科书版本默认所有待排元素都在内存里，可一旦数据量超过可用内存，sort() 就不再是一次函数调用，而是一套围绕磁盘与网络展开的工程流程。本文从内存排序的边界讲起，拆解外排序的两个阶段，再把它与 MapReduce 的 map、shuffle、reduce 对应起来，最后讨论分区、倾斜与常见故障；文中规模数字均为示意值，不代表实测结果。

理解外排序的关键，是把“比较”与“搬运”分开看。比较本身仍然是内存里的操作，真正昂贵的是把数据从磁盘读进来、再写回去；因此外排序的全部设计，都是在减少搬运次数、把随机读写尽量变成顺序读写。MapReduce 之所以在批处理时代流行，正是因为它把同一套思路搬到了多机与分布式文件系统之上。

内存排序的边界

内存排序的代价模型很简单：比较次数约为 n log n，每次比较都是一次内存访问，耗时在纳秒级别。这个模型成立的前提是“所有元素同时在内存里”，一旦数据放不下，前提就没了。假设有一份 100 GB 的日志需要按时间戳排序，而机器只有 16 GB 内存，任何 sorted() 调用都无从谈起，操作系统会先想办法分配，失败后进程被杀掉。

边界并不等于物理内存总量。真正可用的是空闲内存减去系统缓存、运行时开销和程序自身的常驻部分。以 JVM 为例，排序对象还带着对象头与引用，堆内可用空间往往只有物理内存的一半左右；即便勉强装下，垃圾回收也会在排序过程中频繁触发，把 CPU 时间耗在回收而不是比较上。所以判断标准应当是“数据量是否显著小于可用堆内存”，而不是“是否小于内存条容量”。

可以用一个粗略的分界来记忆：数据量在一两百 MB、内存有几个 GB 时，直接内存排序最省事；数据量接近可用内存时，性能会明显下滑，因为换页和回收开始介入；数据量超过可用内存时，就必须转入外排序。这条线随记录大小与运行时变化，但“留出足够余量”的原则始终成立。

外排序的两个阶段

外排序的思路可以用一句话概括：先把大问题切成能装进内存的小块，各自排好，再把有序小块合并成一个整体有序的结果。对应两个阶段，通常称为 run 生成与多路归并。

第一阶段，顺序扫描输入文件，每次读入一块数据，块的大小略小于可用内存，留出输入缓冲、输出缓冲和排序本身所需的额外空间。在内存中对这块数据排序，然后顺序写成一个临时文件，这个临时文件称为一个 run，内部已经有序。继续读下一块，直到输入耗尽。若输入为 100 GB、每块 1 GB，就会得到约 100 个 run。

第二阶段，把这些 run 归并。经典做法是二路归并，两两合并，直到只剩一个文件。但更常见的是多路归并：同时打开 k 个 run，每个 run 只读入一小段到缓冲区，比较 k 个缓冲区头部的最小值，写出后从对应 run 补充。这样一遍就能把 k 个 run 合成一个。

flowchart TD
    A[输入大文件] --> B[读入一块到内存]
    B --> C[内存排序]
    C --> D[写出有序 run 临时文件]
    D --> E{还有数据}
    E -->|是| B
    E -->|否| F[多路归并 k 个 run]
    F --> G[输出全局有序文件]

从数据流看，第一阶段读一遍输入、写一遍临时文件；第二阶段读一遍所有 run、写一遍最终结果。理想情况下总 I/O 量约为输入大小的四倍，其中读两次、写两次。若 run 数量太多、一轮归并放不下，就需要多轮归并，每多一轮就多一遍读写，成本随之上升。这也解释了为什么块不能切得太小：块越小，run 越多，归并轮数越多，I/O 放大越严重。

同一套流程也能支持去重与聚合：归并时丢弃相邻的重复记录即完成去重；把相同 key 的记录合并成一条即完成聚合，代价与排序同阶。

归并路数与 I/O 成本

归并路数 k 不是越大越好，它受两类资源约束：文件句柄和读缓冲区。每个 run 都要占用一个打开的文件描述符，进程的 ulimit -n 通常是几百到几千，超过就会遇到“too many open files”。更现实的约束是内存：k 路归并需要 k 个输入缓冲加一个输出缓冲，内存总量固定时，每路分到的缓冲区约为总缓冲内存除以（k + 1）。k 取 100、缓冲内存 200 MB，每路只剩约 2 MB，顺序读的批量随之变小，系统调用和寻道开销占比上升。

因此实际系统会在“减少归并轮数”和“保持每次读写的批量”之间折中。两阶段外排序的 run 数为 R，若一轮能归并 k 路，轮数为 R 对 k 取对数的上取整。k 从 10 提高到 100，轮数明显下降；再从 100 提高到 1000，轮数收益递减，而缓冲区已经被切得很碎。工程上常见的选择是几十到几百路，配合几 MB 的缓冲区，具体数值要按记录大小和磁盘特性实测。

选择 k 路中的最小元素，不需要每次线性扫描。用一个大小为 k 的小顶堆维护各缓冲区头部，取最小与替换都是对数复杂度，比较次数远小于 k。堆里还应当记录元素来自哪个 run，这个信息在讨论稳定性时会用到。

I/O 复杂度可以这样估算：两阶段、单轮归并时，读约 2N、写约 2N；若需要 m 轮归并，读写各约（m + 1）N。这个式子说明，外排序的瓶颈几乎总是 I/O 次数，而不是比较次数。由此得到一条实践准则：尽可能使用顺序 I/O。机械磁盘的顺序吞吐可以是随机读的几十倍，差距来自寻道与旋转；SSD 的顺序访问同样更易优化。

顺序 I/O 在实现上有几个要点。读写都用大缓冲区，按块而不是按记录发起系统调用；归并时不要在每个元素上调用 seek，而是让每个 run 的读取位置单调前进；输出端攒够一个块再落盘；临时文件与输入输出放在同一块磁盘上，避免跨设备复制。反过来，任何“边归并边随机查找”的写法都会把顺序优势抵消掉。

失败恢复与临时文件

外排序的中间状态全在磁盘上，这既是负担也是机会。负担是临时文件可能很大，粗略估算需要预留与输入同量级、甚至两倍于输入的磁盘空间；机会是每个完成的 run 都是一个可复用的检查点。如果进程在归并阶段崩溃，不必从头重排，只要临时文件命名可辨识、元数据记录了每个 run 的范围与序号，就可以从已完成的 run 继续。

临时文件管理有几个容易忽略的细节。临时目录要显式指定，不要依赖系统默认值，因为某些环境的 /tmp 挂载在内存盘上，写入大文件会直接吃光内存；任务开始时扫描并清理上次残留的文件，避免磁盘被历史垃圾占满；正常结束与异常退出都要走清理逻辑，用 try/finally 或等价的钩子保证删除；输出文件先写临时名，成功后再原子重命名，防止下游读到半成品。

稳定排序在单机内存排序里常被当作默认能力，在外排序里却需要额外设计。多路归并时，若两个元素相等，堆必须优先取 run 序号较小的那个，才能保持“相同键的记录维持输入顺序”。若堆的比较只按键值，相等元素的出堆顺序取决于堆的内部结构，稳定性就被破坏了。这一点在“先按时间、再按用户”这类多键排序中尤其重要：通常做法是先按次要键排一次，再按主要键稳定排序一次，稳定性的丢失会让前一次排序白做。

从外排序到 MapReduce

把单机外排序的两个阶段放大到集群，就得到 MapReduce 的骨架。输入按块切分，每块交给一个 map 任务；map 对记录做转换，输出中间键值对；框架按 key 把中间数据分区、排序、分组，送到 reduce；reduce 对同一 key 的值序列做聚合。map 相当于“分块并做局部处理”，shuffle 相当于“按 key 归并”，reduce 相当于“合并后的最终写出”。

map 的输出不要求在分片内整体有序，只需按分区落盘；真正保证“同一 key 相邻”的，是 shuffle 阶段的分区加排序。也正因为排序藏在 shuffle 里，MapReduce 既能做聚合，也能直接产出全局有序结果。

分区、倾斜与 combiner

分区函数决定一条中间记录去哪个 reducer，常用的是对 key 取哈希再对分区数取模。哈希分区实现简单、分布通常较均匀，但会打乱 key 的全局顺序；范围分区保留顺序，适合需要全局有序输出的场景，代价是要事先知道或采样出边界。分区数一般与 reduce 任务数一致，改分区数会让同一 key 的去向改变，因此它属于作业契约的一部分，不应随意调整。

数据倾斜是分区绕不开的问题。若某个 key 的出现次数远高于其他 key，哈希再均匀也救不了它：这个 key 只能进一个 reducer，其余 reducer 早早完工，整个作业被这一个长尾拖住。示意地说，某热点词占了全部记录的很大比例，那么负责它的 reduce 任务就要独自处理这些记录。常见缓解手段有三类：给热点 key 加随机后缀做两阶段聚合，先局部汇总再去掉后缀合并；为热点 key 单独指定分区；或改用范围分区把热点拆到多个区间。

combiner 是 map 端的本地预聚合，作用是把 (word, 1) 先在本地合并成 (word, 100) 再发送，从而显著减少 shuffle 的数据量。它不是语义上的优化开关，而是有前提的：合并函数必须满足结合律与交换律，求和、求最大值、计数都可以；求平均值不行，除非中间值同时携带 sum 与 count，让 reduce 端做除法。启用了 combiner 却写了一个不满足条件的函数，结果会随执行顺序变化。

适用边界与常见坑

MapReduce 适合批处理与离线场景：数据量大、一次写入多次读取、允许分钟级甚至更长的延迟、追求吞吐而不是单次响应。它不适合低延迟查询、频繁的小幅更新，也不适合需要反复迭代的算法，因为每一轮都要把中间结果落盘。现代实现多在内存与 DAG 调度上做优化，Spark 一类系统把多个阶段串起来减少落盘，但“分片、按 key 重分布、排序聚合”的思想并未改变。

实践中最常见的坑有五个。块太小会产生大量 run，归并轮数和文件句柄压力一起上升；块太大则单块排序时内存吃紧，容易触发换页或 OOM。归并阶段频繁 seek、按记录而不是按块读写，会把顺序 I/O 退化成随机 I/O。缓冲区与堆内存估算不足，会让本来在内存里完成的操作被迫落盘。分区倾斜造成长尾，让少量任务决定整体完成时间。临时文件与中间数据打满磁盘，则会让作业在接近结束时失败。

小结

外排序的本质是用“分块加归并”把超出内存的排序问题转化为有限次顺序 I/O：先在内存中把每块排好，再用多路归并合成全局有序。归并路数要在文件句柄、缓冲区大小与归并轮数之间折中，稳定排序则要求相等元素按 run 序号出堆。MapReduce 把这套流程扩展到集群，map 负责分片处理，shuffle 借分区与排序完成重分布，reduce 完成聚合；combiner 能减少传输，但必须满足结合律与交换律。落地时优先保证顺序 I/O、预留临时空间、监控分区倾斜，并明确块大小与内存预算，这几点比任何单点调参都更重要。
