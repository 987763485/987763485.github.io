Envoy 代理原理与实践

本文属于《Docker 与 Kubernetes》第 35/51 篇
上一篇系列目录下一篇

在服务网格与云原生网关的讨论里，Envoy 几乎是一个绕不开的名字。它由 Lyft 开源，用 C++ 编写，定位是面向服务架构的高性能 L4/L7 代理，也常被各类控制面选作默认的数据平面。本文以 Envoy 1.18 至 1.20 这一代版本为准，从核心抽象讲到配置与排障，希望帮读者建立一张可以动手操作的认知地图。

本文不讨论 Istio 控制面如何生成配置，也不展开高并发网关的容量设计，这些内容留给同一系列的其他文章。这里只关注 Envoy 自身的模型：一条请求从监听器进入，经过过滤器链与路由，最终被转发到某个上游集群，中间每一步由哪些对象描述、在静态配置或 xDS 中落在什么位置。

一、Envoy 的定位：数据平面上的 L4/L7 代理

Envoy 是一个用 C++ 实现的进程外代理。所谓进程外，是指它不嵌入业务代码，而是以独立进程的形式与业务容器并排运行，业务只需把流量指向本地端口。这一设计带来两个直接好处：语言无关，任何技术栈的服务都能接入；升级与配置变更不必改动业务代码。

从网络层次看，Envoy 同时是 L4 和 L7 代理。作为 L4 代理时，它只关心 TCP 连接的建立与转发，不解析应用协议，适合数据库、消息队列这类非 HTTP 流量；作为 L7 代理时，它会完整解析 HTTP/1.1 与 HTTP/2，从而具备路由、重写、重试、熔断、限流等能力，gRPC 也可以借 HTTP/2 的帧被识别和处理。

在架构上，Envoy 把自己明确放在数据平面的位置。控制平面负责决定流量应该去哪里，并把配置下发；Envoy 负责执行，把每一条连接和请求送到正确的上游。二者通过 xDS 协议解耦，这也是它能同时服务于服务网格 sidecar、API 网关和边缘代理的原因。

二、四个核心抽象：Listener、Filter Chain、Cluster、Route

Envoy 的配置看起来庞杂，但骨架只有四个对象。理解它们之间的连接关系，比记住字段名更重要。

flowchart TD
    A[下游连接] --> B[Listener 监听地址与端口]
    B --> C[Filter Chain 网络过滤器链]
    C --> D[Route 路由规则]
    D --> E[Cluster 上游集群]
    E --> F[上游主机]

Listener 描述在哪里听：一个地址加端口，以及一组过滤器链。Filter Chain 描述用什么协议、经过哪些处理：它按匹配条件（例如目标端口、SNI、源地址）选择，链中的第一个过滤器通常是 HTTP 连接管理器，之后才是各种 L7 过滤器。

Route 描述往哪里去：它属于 HTTP 连接管理器的配置，由虚拟主机和路由条目组成，通过域名、路径、请求头等条件匹配。Cluster 描述谁来接：一组逻辑上等价的上游主机，加上负载均衡策略、健康检查、连接池和熔断参数。四者的关系可以概括为：流量从 Listener 进入，穿过 Filter Chain，被 Route 选中，最后落到某个 Cluster 的某台主机上。

三、HTTP 连接管理器与过滤器链

HTTP 连接管理器（HTTP Connection Manager，HCM）本身就是一个网络过滤器。它把字节流解析成请求与响应，并在内部再挂一条 L7 过滤器链。可以把它理解为两层结构：外层是网络过滤器，决定 TCP 字节交给谁处理；内层是 HTTP 过滤器，决定每个请求经过哪些逻辑。

过滤器分编码与解码两个方向。解码路径从下游到上游：请求先经过各解码过滤器，最后由 router 过滤器选定集群并转发。编码路径从上游回到下游：响应按相反顺序经过各编码过滤器，再写回客户端。这一顺序很关键，先加的解码过滤器在响应时最后执行，类似栈的结构。

常用过滤器包括 jwt_authn 做令牌校验、ext_authz 调用外部鉴权服务、local_ratelimit 与 ratelimit 做限流、cors 处理跨域、fault 注入故障、compressor 压缩响应。router 必须位于链尾，因为它负责终止过滤器链并把请求交给上游。

一个常见的误解是认为过滤器可以随意排序。实际上，鉴权类过滤器必须早于 router，限流通常早于鉴权或与之相邻，压缩必须在写响应之前。顺序错了往往不会报配置错误，而是行为与预期不符，这类问题只能靠逐条对照过滤器语义来定位。

四、路由匹配与重写

Route 的匹配自上而下、先到先得，第一个命中的条目生效，不会继续寻找更精确的规则。虚拟主机的域名匹配同理，精确域名优先于通配域名，通配域名中后缀更长的优先。这意味着路由表的顺序本身就是语义的一部分，而不是无意义的排列。

匹配条件可以是 prefix、path、safe_regex、connect_matcher，还可以叠加请求头、查询参数、HTTP 方法。实践中应把最具体的规则放在前面，例如先匹配 /api/admin，再匹配 /api，否则宽泛规则会把细粒度流量提前截走。

五、上游集群：负载均衡、健康检查与连接池

Cluster 是 Envoy 对上游的逻辑抽象。按主机发现方式可分为 static、strict_dns、logical_dns、original_dst 与 EDS。静态方式在配置里写死地址；DNS 方式适合外部服务；EDS 由控制面推送端点列表，是服务网格中的常见形态。

负载均衡策略有 round_robin、least_request、random、ring_hash、maglev。round_robin 适合节点同构且请求开销接近的场景；least_request 依据活跃请求数选择，能缓解长尾；ring_hash 与 maglev 提供一致性哈希，适合需要会话粘性或缓存局部性的服务。默认是 round_robin，但多数 RPC 场景改用 least_request 收益更直接。

健康检查分主动与被动。主动检查由 Envoy 按 interval 发起 HTTP、TCP 或 gRPC 探测，连续失败达到 unhealthy_threshold 就摘除主机，恢复则依据 healthy_threshold。被动检查即异常点检测，依据真实请求的失败情况判断。两者可以叠加：主动检查负责发现进程死亡，被动检查负责发现业务层面的劣化。还有一个 panic_threshold，当健康主机比例低于该值时会忽略健康状态，把流量发给全部主机，避免整体不可用。

连接池决定并发上限。HTTP/1.1 下按 max_connections 限制每个主机的连接数，超出后请求进入队列；HTTP/2 下按 max_concurrent_streams 限制并发流。队列不是无限的，max_pending_requests 用尽后新请求直接被拒绝。很多所谓的偶发 503，根源就是连接池与队列配置与真实并发不匹配。

六、熔断与异常点检测

熔断在 Envoy 中由 circuit_breakers 描述，位置在 cluster 内部。它限制的是资源用量：max_connections 限制连接数，max_pending_requests 限制排队请求，max_requests 限制并发请求，max_retries 限制重试并发，retry_budget 则按比例控制重试放大。阈值触发后，Envoy 快速失败，避免故障上游被压垮。

异常点检测由 outlier_detection 描述，同样在 cluster 内。核心参数是 consecutive_5xx、consecutive_gateway_failure、interval、base_ejection_time、max_ejection_percent。它统计真实请求的连续失败次数，把可疑主机临时移出负载均衡池，时间到后放回并观察。它与主动健康检查的区别在于：前者看业务响应，后者看探针结果。

需要强调的是，这里只讲 Envoy 原生配置的位置。如果在 Istio 中使用，这些参数会通过 DestinationRule 的 trafficPolicy 暴露出来，由控制面翻译成 cluster 配置；那套治理模型属于控制面话题，本文不展开。

熔断参数最容易被忽略的是默认值。Envoy 为每个 cluster 提供了默认上限，流量规模一大就可能先撞上默认值，而不是业务瓶颈。上线前应显式写出与容量匹配的数字，并在压测中确认拒绝究竟发生在哪一层。

七、xDS 动态配置

xDS 是一组发现服务的统称，按资源类型分工。LDS 下发监听器，RDS 下发路由，CDS 下发集群，EDS 下发集群端点，SDS 下发证书与密钥。它们各自独立推送，因此修改一条路由不需要重建监听器，增加一个端点也不需要重推证书。资源之间存在引用关系，CDS 未生效时 EDS 的端点无处可挂，这类依赖顺序问题常常表现为找不到集群。

静态配置写在 bootstrap 的 static_resources 里，启动时一次加载，改动必须重启。动态配置则由控制面通过 gRPC 或 REST 持续下发，Envoy 在内存中原子替换。静态配置适合边缘代理的固定入口和引导阶段，动态配置适合 Pod 频繁创建销毁的集群环境。

推送模型有全量与增量两种。全量（State of the World）每次下发某类资源的完整集合，Envoy 回应 ACK 或 NACK；NACK 会携带错误信息，而旧配置继续生效，这是排查配置问题时最有价值的信号之一。增量（Delta）只推送变化项，适合资源规模大、变更频繁的场景。无论哪种模型，都有版本号与 nonce 用于确认应答与请求的对应关系。

一个容易混淆的点是：ACK 只表示配置被接受，不表示上游已经就绪。集群从收到端点，到完成 DNS 解析、建立连接、通过健康检查，中间存在时间差。因此控制面推送成功与业务真正可用并不是同一件事，观察收敛应以端点健康与请求成功率作为最终判据。

八、落地形态与排障

管理接口是排障的第一入口。独立运行时默认监听 9901，在 Istio 中通常映射到 15000。/stats 输出计数器与直方图，/clusters 展示每个集群的主机状态与健康标记，/config_dump 导出当前生效的完整配置，/listeners 与 /ready 用于确认监听器状态与就绪。排查 503 时，先看 /clusters 里是否有健康主机，再看 /config_dump 里的路由是否与预期一致，最后才怀疑网络。

注意 /stats 的基数问题。默认统计会为每个集群、每条路由、每个响应码生成条目，路由数量多时指标规模迅速膨胀。应通过 stats_config 或 stats_matcher 收敛，只保留需要的维度，否则监控系统的成本会先于流量成为瓶颈。

访问日志在 HCM 的 access_log 中配置，可以输出到文件、stdout 或 gRPC 服务；tracing 通过 tracing 段配置，支持 Zipkin 等后端，采样率要按流量调整，全量采样在高 QPS 下代价很高。日志与追踪回答的是这条请求发生了什么，指标回答的是整体是否异常，三者缺一不可。

热重启是 Envoy 的一个特色。新进程启动后通过共享内存与旧进程交接监听套接字，先接管新连接，再等待旧连接自然结束。升级二进制或修改监听器配置时可以做到不中断，但要求两次启动的参数一致，且共享内存目录可写。

部署形态主要有两种。作为 sidecar 时，它与业务容器共享网络命名空间，所有进出流量经过本地端口，配置由控制面下发，适合东西向服务通信。作为边缘代理时，它独立部署在集群入口，承担 TLS 终止、路由与限流，配置往往更稳定，也更依赖静态部分。性能上，Envoy 的单核吞吐与连接数表现良好，但过滤器越多、统计维度越细，开销越大，资源规划应留出连接缓冲与突发余量。

常见坑值得单独列出。配置版本不一致会让新旧实例行为不同，滚动发布时要确认版本已收敛；路由顺序错误会把流量送进错误的集群；集群未就绪时的 503 常被误判为代码故障；超时默认值偏短，长耗时接口需要显式调大 route 的 timeout；连接池耗尽表现为排队与拒绝，要结合 max_pending_requests 观察；统计基数失控则会拖垮监控。把这六类问题做成上线检查表，能省下大量排查时间。

小结

Envoy 的复杂度主要来自配置面，而不是转发逻辑。抓住 Listener、Filter Chain、Route、Cluster 四个抽象，再理解 HCM 的双向过滤器链，大部分配置就能读懂。上游治理依赖负载均衡、健康检查、连接池与熔断四组参数，它们都在 cluster 内，调优时应显式设置而非依赖默认值。xDS 让配置可以动态收敛，但 ACK 不等于就绪，排障要回到管理接口呈现的事实。最后，sidecar 与边缘代理的侧重点不同，前者追求与业务同步伸缩，后者追求稳定与可观测，部署前先想清楚自己属于哪一种。
