混沌工程与 ChaosBlade

本文属于《Docker 与 Kubernetes》第 43/51 篇
上一篇系列目录下一篇

系统在正常路径上跑得通，并不等于它在异常路径上也能给出可预期的结果；混沌工程关注的正是后者，主动注入受控的故障，观察系统如何响应，用实验结果检验我们对高可用的假设是否成立。它不是为了制造故障，而是为了在故障真正到来之前，把隐藏的单点、错误的超时配置和失效的降级逻辑提前暴露出来。

本文围绕混沌工程的实验方法展开，先厘清它与测试、故障注入、演练的区别，再讲清实验五要素与稳态指标的选择，随后落到 ChaosBlade 的场景模型和常用命令，最后讨论实验设计、安全护栏、观测复盘以及从手工实验走向平台化的路径。文中的命令与示例基于 Kubernetes 1.22 与 ChaosBlade 1.x 的常见用法，重在方法而非某个具体版本的细节。

混沌工程要验证什么

分布式系统里，故障不是偶然，而是常态。机器会宕机，网络会抖动，依赖会超时，发布也会引入新的缺陷。既然无法穷举所有失败路径，与其等故障发生后再被动响应，不如主动做受控实验：先提出“系统在某种故障下应当保持什么状态”的假设，再注入故障去检验它。这是混沌工程的基本出发点。

它和几个相邻概念容易混淆，有必要区分。功能测试针对确定的输入给出确定的预期输出，通过与否一目了然；混沌实验面对的是没有唯一标准答案的复杂系统，重点在于观察系统是否守住稳态，而不是比对某个返回值。故障注入是一种技术手段，混沌工程则是一套包含假设、实验、观测、结论与改进的方法论；只注入故障而没有假设和复盘，称不上混沌工程。演练通常指容灾切换、应急预案这类由人参与的流程检验，关注“人是否知道该做什么”；混沌工程更关注“系统自身会怎么表现”，并且可以高度自动化。三者并不互斥，成熟团队往往组合使用。

实验五要素与稳态指标

业界把混沌工程的原则归纳为五点，本文按自己的理解逐条说明。

第一是建立稳态假设。实验开始前，用可度量的指标描述“正常”是什么样子，例如“下单接口成功率不低于 99.9%，P99 延迟低于 500 ms”。没有这条假设，实验结束后就只能凭感觉说“好像没出问题”。

第二是模拟真实世界的事件。硬件故障、网络分区、依赖超时、流量突增、配置错误，都是生产环境中真实出现过的事件。场景要来源于故障库、历史事故和架构风险，而不是为了破坏而破坏。

第三是在生产环境或接近生产的环境中进行。预发环境可以验证流程，但流量规模、数据分布、依赖拓扑往往与生产不同。条件不成熟时，至少让测试环境的拓扑、配置和依赖版本尽量贴近生产，并清楚其局限。

第四是持续自动化。一次实验只能证明某个时刻的状态，系统在迭代，结论会过期。把实验纳入日常流水线或定期调度，才能持续获得信心。

第五是最小爆炸半径。从一个小比例、一个副本、一个非核心接口开始，确认系统表现和回滚手段有效后再扩大。爆炸半径既是技术参数，也是心理门槛。

稳态指标的选择比故障工具更重要。优先选业务指标：订单创建成功率、支付成功率、登录成功率、核心接口的 P99 延迟。这类指标直接回答“用户是否受到影响”。资源指标如 CPU 使用率、内存占用、GC 次数、连接数，适合解释现象和定位瓶颈，不宜单独作为通过标准——CPU 打满但请求仍然正常，和 CPU 不高但错误率飙升，后者显然更严重。

指标还要满足三个条件：能自动采集、有稳定基线、有明确阈值。实验前先记录一段时间的基线，实验中按相同口径对比；阈值应来自 SLO 或业务容忍度，而不是拍脑袋。一个实验围绕一到两个核心指标即可，指标太多反而难以判断。

举个具体的例子：某订单服务在 Kubernetes 上运行三个副本，我们假设“任意一个副本被删除时，下单成功率不低于 99.9%，P99 延迟不超过 500 ms”。这里的数值只是示意，实际阈值应来自 SLO。实验开始时先记录十分钟基线，再删除一个副本，观察五分钟；若成功率跌破阈值或 P99 持续超标，立即停止。

故障类型与 ChaosBlade 的场景模型

常见故障可以分为几层。资源层包括 CPU 满载、内存占用、磁盘填充和 IO 压力；网络层包括延迟、丢包、乱序、端口不通和 DNS 解析异常；进程层包括进程被杀、线程阻塞；容器与 Kubernetes 层包括 Pod 删除、容器重启、节点不可调度、服务端点异常；中间件层则常表现为连接超时、主从切换或慢查询。层次越往上，越接近用户可感知的故障形态。

ChaosBlade 是阿里巴巴开源的混沌实验工具，定位是把故障注入能力做成统一命令。它用 target 加 action 的场景模型描述一次实验：target 是故障对象，如 cpu、network、disk、process、k8s；action 是具体动作，如 load、delay、fill、kill。执行 blade create 创建实验，返回一个实验 UID；执行 blade destroy 按 UID 销毁，故障随即撤销。

设计一次可回滚的实验

一次完整的实验应当先写成实验单，再动手。实验单至少包含：稳态假设与指标阈值、故障场景与参数、影响范围、预计时长、停止条件、回滚方式、观测人和审批人。下面是一个简化的流程：

flowchart TD
    A[提出稳态假设] --> B[圈定范围与时长]
    B --> C[准备回滚与停止条件]
    C --> D[注入故障]
    D --> E[观测指标与告警]
    E --> F{假设是否成立}
    F -->|成立| G[归档结论并扩大验证]
    F -->|不成立| H[立即停止并回滚]
    H --> I[登记缺陷与改进项]

范围要用标签、命名空间、副本数或流量比例精确表达，不能只说“测试环境”。时长从五到十分钟起步，并设置超时自动销毁，避免实验被遗忘。停止条件要可自动判断，例如错误率超过 5%、P99 超过 1 秒、核心告警触发；同时保留人工急停开关。回滚不只是执行 destroy，还要确认指标恢复、数据一致、没有残留进程和规则。

控制变量同样重要。一次只注入一种故障，确认因果关系后再组合网络延迟与依赖超时等场景。若同时改动副本数、配置和故障参数，即使系统表现异常，也很难判断是哪一个因素导致。实验记录中应保留当时的镜像版本、配置版本和集群状态，便于复现。

对于有状态服务，优先选择只读路径或可重放的操作，避开资金清算、库存扣减等不可逆写入。实验前备份关键数据，实验中限制写入，实验后核对账目，这些约束比故障本身更重要。

审批、护栏与观测

混沌实验应当纳入变更管理，而不是由个人在工位上随手执行。审批关注的不是“能不能做”，而是“在哪里做、影响谁、出了问题谁响应”。实验时间避开业务高峰和大促，提前通知相关团队，值班同学要知道实验的存在和停止方式。对于生产环境，建议先完成一次同场景的预发实验，并保留审批记录。

技术护栏包括：独立或隔离的命名空间、明确的目标白名单和系统组件黑名单、按比例放量、最长执行时间、自动中止、统一的服务账号与 RBAC、完整审计日志。黑名单尤其重要，监控、日志、网络插件和证书服务这些基础组件一旦被误注入故障，排障通路本身也会失效。监控和日志要先于实验就绪，否则实验就是盲人摸象。一个实用的顺序是：先能看见，再能定位，最后才谈扰动。

实验过程中要记录时间线：何时注入、何时出现异常、告警何时触发、何时回滚、何时恢复。结束后对比基线，回答三个问题：假设是否成立、系统在哪一层先失效、如果这是真实故障用户会经历什么。结论只有三种——成立、不成立、证据不足；无论哪种，都应转化为缺陷单、配置修改或预案更新。若实验没有产生任何改进项，也要检查是不是观测粒度太粗，导致问题被平均值掩盖。

从手工实验到平台化

多数团队不必一上来就建平台。先用 ChaosBlade 在测试环境做十次左右的手工实验，沉淀出场景模板、检查清单和回滚脚本，再考虑平台化。平台的价值在于把审批、编排、观测、停止和报告串起来：实验模板可复用，权限和审批可审计，指标异常能自动终止，结果能进入报表和复盘。没有这些前置积累，平台很容易做成一个漂亮的故障按钮。

平台化也不等于把所有实验都交给定时任务。高风险场景仍应保留人工确认，低风险的资源类实验可以按周调度；平台要能回答“谁在什么时候对哪些目标做了什么”，而不是只提供一个执行入口。

组织层面，混沌工程最怕变成“某个团队额外做的项目”。比较健康的做法是让业务团队自己提出假设、自己执行实验、自己修复问题，平台团队提供工具和护栏。复盘对事不对人，找到缺陷应当被鼓励而不是追责。可以先从一次 Game Day 开始，把核心链路、依赖和值班流程放在一起检验。文化上真正难的，是接受“系统一定有问题”并且愿意为发现它投入时间。

常见坑

第一，没有稳态假设。只关心“Pod 被杀后有没有起来”，却不定义成功率、延迟和错误预算，实验就退化成演示，也无法判断系统是优雅降级还是彻底失效。第二，爆炸半径失控。一次性对整层服务注入故障，或在业务高峰执行，容易把可控实验变成真实事故；标签选择器写错一个字符，就可能命中生产全部副本。

第三，实验不可回滚。忘了设置超时、没有记录 UID、故障规则残留在节点上，都会让下一次实验背锅。回滚方案必须提前演练，确认执行人不在场时也能由值班同学完成。第四，只做资源故障。CPU、内存、删 Pod 最容易演示，但真实事故更多来自依赖超时、连接池耗尽、配置错误和中间件抖动，故障类型要覆盖架构中的关键依赖。

第五，没有复盘。实验结束就结束，缺陷不登记、预案不更新、指标不调整，半年后还会踩同一个坑。还有一种隐性坑：把混沌工程当成考核工具，团队为了不出错只挑最安全的场景，实验也就失去了发现问题的意义。

小结

混沌工程的核心是实验而非破坏：先有稳态假设，再有受控故障，最后用观测数据判断假设是否成立。选择业务指标作为主要判据，把爆炸半径、停止条件和回滚方案写进实验单，并让审批、监控与审计成为默认配置。工具只是执行手段，ChaosBlade 降低了注入故障的门槛，但实验的价值仍取决于问题定义和复盘质量。从小范围、短时长、可回滚的实验开始，逐步走向自动化和平台化，比一次性追求全链路混沌更可靠。
