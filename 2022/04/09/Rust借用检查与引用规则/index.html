Rust 借用检查与引用规则

本文属于《Rust 学习路线》第 11/68 篇
上一篇系列目录下一篇

Rust 的学习曲线常被形容为一堵墙，而墙体的大部分由借用检查器砌成。很多人写完第一个 Vec 示例就被 cannot borrow as mutable 拦住，随后把 clone() 到处撒一遍，程序能跑，却始终说不清编译器究竟在保护什么。本文从所有权三原则出发，逐层拆解借用规则、非词法生命周期（NLL）与生命周期标注，再把四类最常见的编译错误逐条对照修正，最后给出一套可以落地的实战策略。读完之后，你应当能读懂借用检查器的报错，知道每一条报错背后对应哪条规则，而不是靠试错和克隆绕过去。本文面向已经能写简单 Rust 程序、但仍在与借用检查器反复拉扯的读者，示例基于 Rust 1.60 与 2021 edition。

一、所有权：借用规则的地基

三条原则

Rust 既不要垃圾回收器，也不要求手动调用释放函数，它靠一套在编译期完成的约定来管理内存，这套约定就是所有权。规则本身只有三条：

  1. Rust 中每一个值都有一个所有者（owner）；
  2. 同一时刻，一个值只能有一个所有者；
  3. 当所有者离开作用域时，值会被自动释放。

第三条是理解一切的前提。看一个最简单的例子：

String 的数据在堆上，栈上只放一个三元组：指向堆的指针、长度、容量。作用域结束时，编译器自动插入 drop 调用，释放堆内存。这套机制没有运行时开销，也没有 GC 停顿，代价是编译器必须能在编译期静态地确定每个值的生命周期，而借用检查器正是为此服务的。

值得强调的是，规则二（唯一所有者）并不是出于洁癖。假如两个变量同时“拥有”同一块堆内存，那么两者离开作用域时都会尝试释放它，这就是经典的 double free。C++ 里要靠开发者自觉遵守三法则、五法则来避免，Rust 则把这个约束提升为类型系统的一部分，让编译器替你检查。

同样的规则适用于函数传参和返回。把 String 传给一个函数，所有权就交给了函数的形参，函数结束时形参被 drop；如果希望调用方继续使用，就得把值返回出去，或者改用引用。

复制：栈上数据的例外

并非所有类型都会移动。整数、浮点数、布尔、字符，以及由它们组成的定长数组和元组，都实现了 Copy trait。对 Copy 类型赋值时发生的是按位复制，原来的变量依然可用：

一个类型能否实现 Copy，取决于它是否能在不执行任何自定义清理逻辑的前提下按位复制。包含 String、Vec、Box 的类型都持有堆资源，它们的 Drop 需要释放内存，因此不能是 Copy。这也是初学者最容易混淆的地方：&T 是 Copy 的（复制一个指针而已），但 &mut T 不是；i32 是 Copy 的，String 不是。

Clone 则是另一回事。它表示“显式地做一次完整复制”，对 String 而言会重新分配堆内存并拷贝内容。Clone 不会自动发生，必须写 .clone()。后文会专门讨论什么时候该用、什么时候不该用。

所有权与借用规则的关系

所有权解决了“谁负责释放”的问题，但只靠所有权写程序会非常别扭：每次传参都要交出所有权，再层层返回，代码会变成一条搬运链。于是 Rust 引入了借用：不转移所有权，只临时借出一段时间的访问权。借用的规则，正是本文余下篇幅的主线。

二、借用规则：同一时刻的别名约束

两种借用

在类型前面加 & 得到不可变引用（共享借用），加 &mut 得到可变引用（独占借用）。借用不改变所有权，所有者仍然是原来的变量，引用只是一个带约束的指针。两条规则概括起来很简短：

  • 在任意时刻，对同一个值，要么只能有一个可变引用，要么只能有任意多个不可变引用，两者不能同时存在；
  • 引用必须在所有者有效期内使用，不能比所有者活得更久。

第一条常被称作“共享不可变，可变不共享”（aliasing XOR mutability）。它是 Rust 无数据竞争保证的根基：如果一块内存同时存在读者和写者，且没有同步措施，就会产生数据竞争。编译器在编译期静态地禁止这种别名组合，跨线程的共享则交给 Send、Sync 与同步原语约束，两层合起来构成了 Rust 的并发安全模型。

push 需要 &mut self，而此时 first 仍然活着，编译器拒绝。报错信息里会明确指出：不可变借用发生在第 3 行，可变借用发生在第 4 行，并提示“借用在这里之后仍被使用”。

借用检查器在看什么

借用检查器并不真的跟踪指针地址，它做的是区域推断：为每个借用计算一个“活跃区间”，再检查这些区间是否违反规则。可以把它想象成在程序的语句序列上画横线，每条横线是一个借用的存活范围，规则要求：任何一条 &mut 横线不能与同一变量的其他横线重叠。

引用失效：编译器在防什么

初学者常问：既然只是借用，为什么不能一边持有元素引用一边往 Vec 里追加？原因在于 Vec 的扩容。push 可能触发重新分配，把元素从旧缓冲区搬到新缓冲区，旧缓冲区被释放。此时原来指向旧缓冲区的引用就成了悬垂指针，指向已释放的内存。C++ 里这是典型的迭代器失效，运行期才可能崩溃；Rust 直接把它变成编译错误。

同样的道理适用于 String 的 push_str、HashMap 的 insert（可能触发 rehash）、以及任何内部持有堆缓冲区的容器。借用规则看起来是在限制你，实际上是在替你记住“哪些操作会让已有指针失效”这件极容易忘的事。

反过来，如果容器操作不会导致失效，借用检查器也不会为难你。比如对 Vec 只读地遍历，同时读取另一个不相干的变量，完全没有问题。规则是精确到变量与字段的，不是一刀切地禁止一切组合。

还有一个容易忽略的细节：&mut T 既不实现 Copy，也不会在每次传参时被彻底移走，编译器会在需要时插入重借用（reborrow）。把 &mut 传给函数，函数返回后原引用通常仍可使用；但一旦把它移动进某个结构体字段或作为返回值交出去，原引用就真正失效了。理解重借用，可以解释为什么同样是传 &mut，有时“传进去还能用”，有时“传进去就没了”。

三、NLL：借用结束于最后一次使用

词法生命周期的旧时代

在 NLL 稳定之前（2018 edition 起成为默认），借用检查器是词法作用域的：一个借用的存活范围从声明处一直延伸到所在代码块的右花括号。这意味着只要引用还在作用域里，哪怕后面再也不用它，借用也算“活着”。

这段代码在旧规则下编译失败，尽管 first 在打印之后再也没有被使用。开发者的应对办法是人为加一层花括号，把引用的作用域截断。这种写法在 2018 年之前的代码里随处可见，读起来相当别扭，也让很多人误以为 Rust 的借用规则过于苛刻。

NLL 解决了什么

非词法生命周期（Non-Lexical Lifetimes，简称 NLL）把借用的存活范围从“词法块”改成“最后一次使用的位置”。借用检查器会做活性分析（liveness analysis）：如果一个引用变量在某个程序点之后再也不会被读取，那么它的借用在该点就结束了。

于是上面那段代码在新规则下顺利通过：first 的借用区间止于 println!，push 的 &mut 借用与之不重叠。这条改动看似只是放宽了检查，实际上改变了整个语言的手感。大量原本需要加花括号、加临时变量的代码变得自然，返回引用的函数、条件分支里的借用、循环里的可变借用都因此好写了许多。

NLL 的核心是 MIR（Mid-level Intermediate Representation）上的区域推断。编译器把函数体降级成 MIR，为每个借用变量分配一个区域变量，再根据使用点施加约束，最后求解出一组满足所有约束的最小区域。这套分析在 2018 edition 上线时保留了少量保守之处，后续版本逐步收紧到更精确；更完整的规则（尤其是跨函数的条件借用）则由 Polonius 原型继续探索。

另一类 NLL 没有完全覆盖的场景，是借用的产生与返回取决于条件分支：函数可能在一条路径上返回入参的引用，在另一条路径上返回新分配的值。这类写法在社区里以 Polonius 的后续工作来讨论，实际编码中通常通过重构数据结构绕开。理解这个边界，可以避免在明显无解的地方反复尝试。

四、生命周期标注入门

‘a 是区域变量，不是存活时间

生命周期标注的语法是一个撇号加名字，例如 'a、'b、'static。初学者常把它理解成“这个引用能活多久”，于是试图用标注去“延长”生命周期，结果处处碰壁。正确的理解是：'a 是一个区域变量，它表示“某个尚未确定的作用域范围”，标注的作用是声明多个引用之间的约束关系，而不是指定具体时长。

换句话说，生命周期标注不改变任何值的实际存活时间，它只是把编译器本来就能推断出的关系显式写出来，供跨函数、跨结构体时使用。函数体内的借用，编译器可以自行推断，通常不需要标注；只有出现在函数签名、结构体定义、trait 定义这些“边界”上时，才需要手写。

Rust 还有一套生命周期省略规则（lifetime elision）：当函数只有一个引用入参时，返回值默认与它同区域；当有 &self 或 &mut self 时，返回值默认与 self 同区域。这就是为什么大量方法签名不需要写 'a。省略规则只适用于常见模式，一旦模式不匹配，编译器会要求你显式标注。

‘static 的含义与误用

'static 是一个特殊的生命周期，表示“整个程序运行期间都有效”。字符串字面量天然是 'static 的，因为它们被直接写进二进制文件的只读段，程序活着它们就活着。所有不持有借用（或只持有 'static 借用）的类型，例如 String、Vec<u8>、i32，都满足 T: 'static 约束。

最常见的误用有两种。第一种是把 'static 当成“活得比较久”的修饰符，试图给一个局部引用加上 'static 来消除报错。这行不通，因为 'static 是一个精确的约束，局部变量无论如何都满足不了。第二种是看到 T: 'static 就以为“只能传字面量”，其实 String、Vec 这类拥有所有权的类型都满足该约束，Box<dyn Error + 'static> 也是常见写法。

真正需要 'static 的地方通常是线程、全局状态和 trait object：std::thread::spawn 要求闭包满足 'static，因为它可能比创建它的栈帧活得更久；把错误装箱成 Box<dyn Error> 时，默认也要求 'static。遇到这类要求，正确的做法是把数据的所有权移进闭包（用 move），或者用 Arc 共享，而不是硬凑一个 'static 引用。

六、实战策略：把冲突改造成不冲突

规则讲清楚之后，剩下的问题是如何在真实代码里与它共处。绝大多数借用错误并不是“编译器太严”，而是代码结构把本该分开的事情挤在了同一段作用域里。下面六种手法覆盖了日常遇到的绝大部分场景。

最直接的办法是让借用尽早结束。把需要的结果先算出来，或者用一对花括号把借用包起来，冲突往往就消失了：

顺带一提，let x = &String::from("tmp"); 能够通过编译，靠的是临时值生命周期延长规则：绑定到 let 的临时值会延长到与该绑定同寿命。但 let x = String::from("tmp").as_str(); 不会延长，仍然报错。这条规则的边界比较细，遇到时以编译器给出的提示为准。

用索引代替持有引用

在容器里做“读一个元素、再改另一个元素”的操作时，持有引用几乎必然冲突。改用索引，让借用变成一次性的：

索引的代价是运行期边界检查，以及每次访问都要重新计算地址；收益是彻底绕开了别名问题。在图、树、网格这类“节点互相指向”的结构里，用 Vec 加索引（也就是常说的 arena 模式）往往比 Rc<RefCell<...>> 更简单也更快。后者能表达共享所有权，但会把编译期的检查推迟到运行期，用错了照样 panic，细节留到智能指针那一篇展开。

遍历时选对借用形式

for 循环取哪种形式，直接决定了借用冲突的范围。for x in &v 得到 &T，只能读；for x in &mut v 得到 &mut T，可以修改元素，但不能改动容器结构；for x in v 会消耗 v，循环结束后原变量不可再用。想在遍历中删除元素，retain 是最省心的选择，它接收 FnMut(&T) -> bool，在内部完成删除，调用方不必持有可变引用：

如果一边遍历一边调用 nums.remove(i)，编译器会报 E0502：remove 需要 &mut self，而迭代器仍持有 &nums。这不是无谓的限制，而是必需的：删除会让后续元素前移，正在使用的迭代器下标全部失效。drain 也是同理，它把元素的所有权交出来，同时独占容器，遍历期间容器不可另作他用。

Clone 的取舍

遇到借用冲突时，.clone() 是最快的止血办法，但它不是免费的：String、Vec、HashMap 的克隆意味着一次堆分配加一次全量拷贝。判断标准不是“能不能克隆”，而是“这份数据在语义上是否应该独立”。

配置、模板、请求快照这类本来就该各存一份的数据，克隆是合理的；循环体内对大集合克隆，则通常说明结构设计有问题。一个实用的经验是：先尝试借用与索引，只有在数据确实需要独立生命周期时才克隆，并且在代码里保留一句注释说明原因。这样后续维护者不会误以为这是随手写的。

内部可变性：点到为止

有些场景确实需要在持有不可变借用时修改数据，例如共享计数器、缓存、图结构中的反向边。标准库提供了 Cell<T> 与 RefCell<T>，后者把借用检查从编译期移到运行期：

RefCell 并没有废除规则，只是把违规从编译错误变成运行期 panic：同时调用两次 borrow_mut() 会直接崩溃。它适合“借用关系在编译期无法表达、但运行期确实安全”的窄场景，不适合当成绕过借用检查器的通用手段。Rc<RefCell<T>> 的组合、Cell 的复制语义、以及 Arc<Mutex<T>> 的线程版本，都属于智能指针与内部可变性的主题，本文只做定位，不展开实现。

七、边界与心智模型

借用检查器容易被误解成“指针分析器”，其实它分析的是权限：在某个程序点上，谁有权读这块数据、谁有权写、这份权限能维持多久。把引用理解成“带期限的权限”，很多报错就不再意外——权限重叠了就冲突，权限超过了数据本身的寿命就悬空。

这也解释了为什么 Rust 的很多设计选择看起来“反直觉”：结构体带生命周期参数会让签名变复杂，于是工程上倾向持有 String；跨线程共享需要 Arc，因为权限要能被复制到多个线程；内部可变性需要 RefCell，因为编译期无法表达运行期的独占。这些都不是语法糖，而是同一套权限模型在不同场景下的推论。

需要与相邻主题划清边界。智能指针（Box、Rc、Arc、RefCell、Mutex）解决的是“所有权如何共享与转移”，以及堆分配与内部可变性的实现，本文只在策略层面提及；模块系统与 pub 可见性解决的是“谁能看到这个类型”，与借用规则正交，不要混为一谈；而工程化的错误处理、日志与异步运行时，则属于生产落地的另一条线。把这几块分开学，比一次性塞进脑子要有效得多。

小结

借用检查器不是需要战胜的对手，而是一份被编译器执行的接口契约。所有权决定了谁负责释放，借用规则决定了同一时刻谁能读、谁能写，NLL 把借用的终点从花括号收缩到最后一次使用，生命周期标注则把跨函数、跨结构体的约束写进类型。四类高频报错分别对应四条规则，读懂报错里的“occurs here”与“later used here”，就能定位冲突的两端。实践中优先缩小作用域、按字段拆分借用、用索引替代长生命周期的引用，把 clone() 留到数据确实需要独立时再用。真正难的不是记住规则，而是在设计数据结构时就预见到权限的重叠。
