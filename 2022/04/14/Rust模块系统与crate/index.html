Rust 模块系统与 crate

本文属于《Rust 学习路线》第 8/68 篇
上一篇系列目录下一篇

写 Rust 的头几天，代码往往都堆在 main.rs 里；等到文件涨到几百行，想把配置、存储、命令拆开时，就会撞上一连串问题：mod 写了却提示找不到文件，pub 加了外部还是用不了，use 和 mod 到底谁负责加载代码也说不清。这些困惑大多不是语法难，而是没有把 crate、模块树与可见性这三层关系理顺。

本文从 crate 与 package 的区别讲起，沿着 crate root、mod 的文件布局、pub 的四种写法、use 与重导出一路展开，最后落到 workspace、路径依赖与 feature 开关，并集中列出新手最常踩的坑。读者只需要写过 cargo new 生成的 hello world，了解函数与结构体的基本写法即可。读完之后，应当能为一个小型项目画出清晰的模块树，并在遇到“文件找不到”“类型不可见”这类报错时知道该改哪一行。本文以 Rust 2021 edition、Cargo 1.60 前后的行为为准。

crate 与 package 不是一回事

Rust 文档里这两个词经常交替出现，含义却不同。crate 是编译器一次处理的最小单位，也是链接的基本单位；package 是 Cargo 的概念，指一个带有 Cargo.toml 的目录。一个 package 可以包含多个 crate：最多一个 library crate，以及任意多个 binary crate。换句话说，package 是“发货单位”，crate 是“编译单位”。

binary crate 有 main 函数，最终编译成可执行文件；library crate 没有 main，编译成 rlib，供其他 crate 链接。二者的身份由 crate root 决定：src/main.rs 是 binary crate 的根，src/lib.rs 是 library crate 的根。Cargo 的默认约定是，存在 src/main.rs 就以 package 名生成同名二进制，存在 src/lib.rs 就生成同名库；额外的二进制放进 src/bin/，每个文件各自成为一个 crate。用 cargo new --lib 创建项目时，Cargo 只会生成 src/lib.rs。

crate root 这个说法值得强调：它是模块树的根节点，本身也是一个模块，文件里的每一条 mod 声明都是往这棵树上挂子节点。2018 edition 之后，crate 名可以直接作为路径的起点，extern crate 基本退出了日常代码。下面这张图展示一个同时含有库与二进制的 package：

flowchart TD
  P["package myapp（Cargo.toml）"] --> B["binary crate myapp（src/main.rs）"]
  P --> L["library crate myapp（src/lib.rs）"]
  L --> C["模块 config"]
  L --> S["模块 store"]
  S --> M["子模块 store::mem"]

图中两个 crate 同名并不冲突，因为它们属于不同的命名空间：二进制通过 use myapp::... 引用库，链接时 Cargo 会自动处理。理解这一点之后，后面所有关于 mod 的讨论都可以理解为“在某一棵模块树上添加节点”。

mod 声明与模块树

mod 是唯一负责“声明模块”的关键字。它有两种写法：一种是内联模块，用花括号把内容直接写在原地；另一种只写分号，让编译器去磁盘上找对应文件。两种写法产生的模块在语义上完全一样，区别只在代码放在哪里。

需要记住的规则是：模块的父子关系由 mod 出现在哪个模块里决定，与文件放在哪个目录没有必然联系。编译器先读 crate root，遇到 mod config; 就把 config 作为根的子节点，再去约定位置取回该节点的内容；取回的文件里如果再写 mod loader;，loader 就是 config 的子节点。整个编译过程像深度优先遍历一棵树，没有出现在树上的文件根本不会被读取。

路径有三种起点：crate:: 指向当前 crate 的根，self:: 指向当前模块，super:: 指向父模块。Rust 2018 之前相对路径的写法容易歧义，2021 edition 的代码里更推荐以 crate:: 开头的绝对路径，读起来不必关心当前文件处在树的哪一层。至于 store::mem 能否被外部调用，取决于沿途每一层是否 pub，这就是下一节要展开的可见性。内联模块适合只有几行常量或测试辅助的场景，超过一屏就应当拆成文件，否则 crate root 很快又会变回大杂烩。

文件布局的两种风格

Rust 允许两种模块文件布局，它们在编译结果上等价，只是目录观感不同：

左侧的 config.rs 搭配 config/ 目录，是 2018 edition 之后推荐的新风格；store/mod.rs 搭配 store/ 目录，是 2015 edition 延续下来的旧风格。两者的查找规则可以统一表述：当某个模块文件里写下 mod foo; 时，编译器在该模块文件所在目录下寻找 foo.rs 或 foo/mod.rs。

由此可以推出一个高频错误：在 src/config.rs 里写 mod loader;，编译器找的是 src/config/loader.rs，而不是 src/loader.rs。因为 config.rs 代表 config 模块，它的子模块要放在以它命名的目录里。很多“文件明明存在却报找不到模块”的情况，都是把子模块文件放到了 crate root 旁边。

同一模块的两种风格不能并存。如果 src/foo.rs 与 src/foo/mod.rs 同时存在，编译器无法判断该用哪个，会直接报错（E0761）。团队内部选定一种即可，常见做法是叶子模块用 foo.rs，带子模块的目录用 foo/mod.rs，这样目录里不会同时出现一个同名文件和一个同名目录。若确实需要非常规布局，可以用 #[path = "..."] 属性改写查找位置，但它会破坏“看目录就懂结构”的直觉，除迁移旧代码外不建议使用。

可见性：从私有到 pub(in path)

Rust 的默认可见性是私有。一个条目对“当前模块及其后代模块”可见，对父模块和兄弟模块不可见。这一点与许多语言相反：子模块能看见祖先的私有条目，父模块却看不见子模块的私有条目。因此把代码拆进子模块时，往往需要主动加 pub，而不是加完才发现外部访问不了。

pub 并不是只有“全开”一档，它可以带作用域：

  • pub：对 crate 外部可见，是库的公开 API。
  • pub(crate)：整个 crate 内可见，但不对外暴露，适合内部工具函数。
  • pub(super)：仅父模块可见，等同于 pub(in super)。
  • pub(in crate::a::b)：仅指定的祖先模块可见，路径必须以 crate、self 或 super 开头，且必须指向当前模块的祖先。

选择粒度时可以参考一条经验：跨模块复用但不应外泄的实现细节用 pub(crate)，只在父子之间传递的用 pub(super)，真正稳定的对外契约才用 pub。结构体的字段需要逐个标注，pub struct 不会让字段自动公开；枚举则相反，变体跟随枚举的可见性。可见性标注永远写在条目定义处，试图在调用处补 pub 不会生效。

use 与重导出

use 只做一件事：把某个路径绑定到当前作用域里的一个短名字。它不加载文件，不声明模块，也不改变可见性。初学者最常见的误解是写了 use foo::Bar; 就以为 foo.rs 会被编译，实际上如果没有 mod foo;，这个文件根本不在这棵模块树上，编译器只会报 unresolved import。

2018 edition 起，use 的路径规则与普通表达式路径统一：要么以 crate、self、super 开头，要么以外部 crate 名开头。这样 use config::Settings; 会被理解为引用外部 crate config，而不是当前 crate 的子模块，歧义因此消失。

pub use 的价值在于控制对外形状。库的内部可以按 store::mem、store::disk 细分，对外只在根上重导出几个核心类型，调用方不必记住内部层级。这种“门面”写法在标准库与常见框架里随处可见，prelude 模块也是同一思路：把常用 trait 与类型集中重导出，用户一行 use myapp::prelude::*; 即可。通配符导入要克制，它会让名字来源变得难以追踪，代码审查时也不好判断冲突来自哪里。若只想引入 trait 的方法而不引入名字，可以写 use std::io::Write as _;，这是较新的习惯写法，能避免与自有类型重名。

workspace、路径依赖与 feature

项目变大后，把所有代码塞进一个 crate 会带来两个问题：编译单元越来越大，库与可执行程序的依赖也混在一起。Cargo 的 workspace 用来解决这个问题：多个 package 共享一个 Cargo.lock、一个 target/ 目录和一套依赖版本，既节省编译时间，也避免同一依赖出现多个版本。

feature 是编译期开关，用来把可选功能从默认构建中裁掉：

代码里用 #[cfg(feature = "json")] 决定某段代码是否参与编译。从 Cargo 1.60 起，可以用 dep: 前缀声明可选依赖，避免依赖名被自动生成为同名 feature，内部实现细节也就不会泄漏成公开开关。旧写法 json = ["serde_json"] 仍然有效，只是会隐式产生同名 feature，新项目建议直接用新语法。

feature 有一个必须理解的性质：它是可加的（additive）。依赖图中多个 crate 对同一依赖打开不同 feature 时，Cargo 取并集，而不是各算各的。因此 feature 不能表达互斥选择，例如把“后端选 MySQL 还是 PostgreSQL”做成两个 feature，同时打开就会编译两份实现。互斥配置应交给上层 crate，用不同的依赖组合或不同的二进制来表达。

排查 feature 合并时，可以用 cargo tree -e features 打印依赖树，看某个 feature 是从哪条路径被打开的。workspace 中构建单个成员用 cargo build -p common，跑全部测试用 cargo test --workspace；只测改动过的成员，容易漏掉下游 crate 因公开 API 变化而编译失败。引用第三方库时，先 default-features = false 再按需开启，也是控制编译量的常用手段。

五类高频坑

第一类是模块文件找不到。最常见的原因是子模块文件放错了目录：在 src/config.rs 里声明 mod loader; 时，文件必须在 src/config/loader.rs。从 mod.rs 风格迁移时也要注意，src/store/mod.rs 改成 src/store.rs 之后，子模块仍应留在 src/store/ 目录里，不能跟着搬到 crate root 旁边。排查时顺着 mod 声明所在的文件往上推一层目录，基本都能定位。

第二类是 mod 重复声明。同一个模块名在同一父模块里声明两次，会报重复定义（E0428）；同一个文件被两棵不同的父模块同时声明，编译器会提示该文件被多个父模块加载。后者常出现在“根文件里写了一次，子模块里又写一次”的重构过程中。模块树是树而不是图，一个文件只能有一个父节点，需要共享代码时应当把它提升为公共子模块，而不是两处都声明。

第三类是私有模块里的公有类型。前面已经分析过成因，这里补充一个测试场景：集成测试放在 tests/ 目录，每个文件都会编译成独立的 crate，只能访问库的公开 API。若某个类型藏在私有模块里，即使测试与被测代码同属一个 package，也无法使用。写库时要把“对外契约”与“内部实现”分开，测试所需的东西要么走公开路径，要么改成单元测试放进源码内部。

第四类是 use 与 mod 混淆。记住分工即可：mod 决定代码是否进入编译，use 只决定名字是否好写。看到 unresolved import 时，先检查模块有没有被声明，再检查路径起点与可见性，通常不必怀疑文件名拼写。

第五类是测试模块的写法。单元测试习惯放在被测文件底部：

#[cfg(test)] 保证这段代码只在测试构建时编译，不进入发布产物；use super::* 让测试模块能访问父模块的私有函数，这正是单元测试相对于集成测试的优势。测试模块本身也是普通模块，同样受可见性规则约束，把测试写进子模块后若访问不到目标函数，多半是层级不对，而不是 cfg 没生效。

小结

本文沿着一条主线展开：crate 是编译单元，package 是 Cargo 的发布单位；crate root 是模块树的根，mod 负责往树上挂节点，文件布局只是查找节点的约定；可见性从私有出发，用 pub、pub(crate)、pub(super) 与 pub(in path) 逐层放开；use 只引入名字，pub use 决定对外形状；workspace、路径依赖与 feature 则把多个 crate 组织成一个可维护的整体。

实践中可以先在纸上画出模块树，再决定文件怎么放，这样能避免大半“文件找不到”的返工。对外公开面尽量小，内部实现用 pub(crate) 收住；feature 只做加法，不做互斥开关。遇到编译错误时按“模块是否声明、路径是否可达、沿途是否公开”三步排查，比反复改 pub 更有效。
