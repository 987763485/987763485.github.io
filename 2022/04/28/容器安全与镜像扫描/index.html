容器安全与镜像扫描

本文属于《Docker 与 Kubernetes》第 30/51 篇
上一篇系列目录下一篇

容器把应用和依赖打包在一起，交付变快了，但“这个镜像里到底装了什么”也随之变得不透明。本文沿着“构建、入库、准入、运行”这条链路，梳理容器安全的几个层次，重点讲镜像扫描工具怎么选、怎么接进 CI、结果怎么处理，以及签名、SBOM 与运行时约束如何补上扫描管不到的地方。适合已经在用 Docker 与 Kubernetes、准备把安全卡点落到流水线里的工程师阅读。读完你应该能画出一条覆盖镜像全生命周期的防线，并知道哪些做法只是心理安慰。

一、容器安全是一张分层的地图

讨论容器安全时，最容易犯的错误是把它压缩成“有没有扫过镜像”。扫描只能回答“已知的漏洞在不在”，而一个镜像从被构建到被运行，中间要经过许多可以被动手脚的环节。把这些环节摊开，至少能看到五层。

第一层是镜像构建。基础镜像从哪来、Dockerfile 里有没有把密钥写进层里、构建机有没有被污染，决定了镜像的“出身”。第二层是镜像仓库，它负责存储与分发，涉及访问控制、标签策略、推送时的扫描以及签名。第三层是运行时，容器共享宿主机内核，命名空间负责隔离，seccomp、AppArmor 与 capabilities 决定进程实际能调用哪些系统调用与特权操作。第四层是编排层，Kubernetes 的 RBAC、NetworkPolicy、准入控制与 Pod Security 标准，决定了谁能部署什么样的工作负载。第五层是供应链，包括上游基础镜像的维护者、第三方依赖、CI 的凭据与构建产物。

  A[基础镜像与依赖] --> B[构建镜像]
  B --> C[镜像仓库]
  C --> D[准入控制]
  D --> E[运行时]
  E --> F[编排与网络策略]
  A -.-> G[SBOM 与签名]
  C -.-> G
  G -.-> D

这张图的价值在于定位问题。镜像里发现了 OpenSSL 漏洞，属于第一、二层，靠重建镜像解决；容器逃逸尝试属于第三层，靠内核与运行时配置解决；有人往生产推了一个来路不明的镜像，属于第四层，靠准入控制解决。层次分清，才不会指望一个工具包打天下。下文先讲透扫描，再补签名与运行时。

二、扫描工具：Trivy、Clair 与 Grype 的定位

镜像扫描的基本动作并不神秘：把镜像的各层解包，读出操作系统包数据库（dpkg、apk、rpm），再解析语言级依赖清单（package-lock.json、go.mod、requirements.txt 等），拿这些“包名 + 版本”去漏洞库里匹配，最后输出 CVE 编号、严重级别、所在包以及修复版本。真正拉开差距的，是漏洞库从哪来、怎么匹配、以什么形态提供服务。

Trivy 是 Aqua 维护的开源扫描器，单二进制、无需服务端和数据库，第一次运行会自动下载漏洞库。它既能扫镜像，也能扫文件系统、IaC 模板和已有 SBOM，启动快、占用低，适合塞进 CI 的每个构建任务。它的漏洞数据来自各发行版的安全公告、NVD 以及语言生态的 advisory，官方还提供镜像仓库供内网离线使用。

Clair 出身于 CoreOS，是 Quay 镜像仓库背后的扫描引擎。它是客户端与服务端分离的架构，需要 PostgreSQL 保存索引，由一组 updater 定期拉取漏洞数据，indexer 把镜像层拆成特征，matcher 负责匹配。这种形态适合“仓库侧持续扫描”：镜像一入库就排队分析，之后漏洞库更新还能重算。反过来说，为了跑一次构建就拉起 Clair 全家桶并不划算。

Grype 来自 Anchore，通常与同门的 Syft 搭配。Syft 负责从镜像或目录里生成 SBOM，Grype 拿着 SBOM 去匹配漏洞，也可以直接扫镜像。这条“先出清单、再离线匹配”的路径在受控环境里很实用：SBOM 可以归档、可以审计，扫描器升级或漏洞库更新后不必重新拉镜像。

三者的差异可以归到三个问题上。其一是漏洞库口径：只依赖 NVD 的版本区间匹配，会把发行版已经回补补丁的包判成有漏洞；理解发行版 backport 的数据源误报更少。其二是层的信息：Clair 以层为单位建索引，便于增量和定位“哪一层引入的”；Trivy 与 Grype 以最终文件系统为准，层信息更多用于排查。其三是误报来源：没有修复版本的 CVE、被静态链接进二进制的依赖、镜像里根本没被调用的包，都会让报告显得吓人。

工具选型不必求全。已有 Quay 或 Harbor 且希望仓库侧持续扫描，Clair 是自然选择；流水线里要一个轻量卡点，Trivy 上手最快；需要 SBOM 驱动的合规流程，Syft 加 Grype 更顺。真正决定效果的，是后面的流程与规范。

三、把扫描接进 CI：阻断什么、多久扫一次

扫描接进 CI 之后，第一个矛盾立刻出现：几乎每个稍大的镜像都能扫出几十上百个 CVE，如果全部阻断，流水线会长期红着，团队很快就会加上 || true，防线名存实亡。可行的做法是把“有漏洞”翻译成“有可执行的修复动作”。

本文建议的阻断条件是：存在修复版本、严重级别为 HIGH 或 CRITICAL、并且是本次构建新引入的。前两条用工具参数就能表达，第三条需要差分。做法是先扫一份基线镜像（比如上一个发布版本或主干最近一次构建），把结果存成 JSON，新镜像只对“基线里没有、这次新出现”的条目报警。

例外要留出口，但必须带期限和责任人。Trivy 支持 .trivyignore，每行一个 CVE 编号，团队应在旁边注明原因与过期日期，并纳入代码评审；没有期限的忽略文件，半年后就会变成一张废纸。

扫描频率同样被低估。很多人只在构建时扫一次，认为镜像没变就安全；但漏洞库每天都在更新，三个月前“干净”的镜像，今天可能带着高危漏洞在跑。合理的节奏是三层：构建时扫，作为质量门禁；推送时扫，作为仓库的兜底；上线后按周定时重扫，把结果按镜像 digest 聚合并推给负责人。第三层往往最能暴露问题，因为此时镜像早已发布，修复只能靠重建与滚动更新。

这也解释了基线镜像为什么要统一。平台团队维护一组固定 digest 的基础镜像，定期重建、统一扫描、统一修复，业务镜像 FROM 它们而不是各自 FROM ubuntu:latest。这样一次基础镜像升级可以覆盖上百个服务。标签会漂移，digest 不会，生产环境引用 digest 是让“我部署的到底是哪份代码”可回答的前提。

四、从构建源头缩小攻击面

扫描是在事后数伤口，构建规范才是在事前少挨刀。最直接的杠杆是换一个更小的基础镜像。alpine 只有几 MB，代价是 musl libc 与 glibc 的差异，某些预编译二进制会跑不起来；distroless 由 Google 维护，只保留运行时需要的库和证书，没有 shell、没有包管理器，攻击者拿不到交互入口，排障时也进不去容器；静态编译的程序则可以直接 FROM scratch，镜像里只剩一个二进制。

第二个杠杆是多阶段构建。编译工具链、源码、测试依赖都留在构建阶段，最终镜像只 COPY 产物。这既缩小了体积，也避免了源码与 .git 目录泄露。

第三个杠杆是非 root。容器默认以 root 运行，一旦应用被拿下，攻击者就拿到了容器内的 root，配合错误的挂载或内核漏洞，逃逸成本会低很多。Dockerfile 里显式 USER 一个普通用户，Kubernetes 里再叠一层 runAsNonRoot: true 兜底，两边都做才可靠。镜像内要提前把工作目录 chown 给该用户，否则只读挂载会直接启动失败。

第四个杠杆是 .dockerignore。COPY . . 会把 .git、.env、本地 node_modules、测试报告一并塞进构建上下文，既拖慢构建，也可能把密钥固化进镜像层。层是只读的，删掉文件只是在新层里标记删除，原层仍然可以被导出，所以“先 COPY 再 RUN rm”并不安全。同理，密钥不要用 ARG 或 ENV 传入，构建期需要凭据时用挂载的 secret。

需要强调的是，distroless 与“去掉 shell”不是教条。没有 shell 意味着 kubectl exec 进去也查不了问题，团队必须提前准备好日志、指标与调试容器，临时起一个共享命名空间的调试 Pod。安全与可运维性要一起算账，否则最后会被运维同事用 privileged: true 一把推翻。

五、签名、SBOM 与准入控制

扫描回答“里面有没有已知漏洞”，签名回答“这是不是我们构建的那一份”。两者缺一不可：一个镜像可以既没有漏洞，又是攻击者塞进来的。

sigstore 体系里的 cosign 把签名绑定到镜像 digest 上，签名本身作为另一个 tag 存回仓库，命名形如 sha256-<digest>.sig，因此镜像内容一变签名即失效。它支持自管密钥对，也支持 keyless 模式：用公司的 OIDC 身份换取 Fulcio 签发的短期证书，签名事件写入 Rekor 透明日志，事后可审计，也省去密钥分发与轮换的麻烦。

签了名还得有人验。准入控制器在 Pod 创建时拦截：镜像没有有效签名就拒绝。Kyverno 的 verifyImages 规则、OPA Gatekeeper 配合 Ratify、Connaisseur 都能做这件事。落地时先以 audit 模式跑一两周，看清哪些历史工作负载过不了，再切 enforce；同时要意识到准入只覆盖 API 创建路径，节点上直接 crictl pull 或 containerd 层面的拉取绕得过它，仓库侧的访问控制仍然必需。

SBOM 是另一块拼图。SPDX 与 CycloneDX 是两种主流格式，前者偏许可证合规，后者偏安全与组件关系。SBOM 记录镜像里每个组件的名称、版本、来源与依赖关系，价值在“事后追查”：某个组件爆出漏洞时，不必逐个镜像去扫，查 SBOM 索引就能列出受影响的服务。SBOM 可以随镜像一起归档，也可以用 cosign 的 attestation 附加到镜像上，与签名一起分发。2021 年美国的软件供应链行政令之后，SBOM 从“最佳实践”变成了很多采购合同的硬性要求，提前把它纳入流水线，比临时补材料从容得多。

六、运行时：把权限收到最小

镜像做得再干净，跑起来给了 privileged: true 也等于白做。运行时防线的共同思路是“默认拒绝、按需放行”。capabilities 上，容器默认带着一批能力，多数应用一个都不需要，drop: ["ALL"] 之后再按需加回，比如要绑 80 端口才加 NET_BIND_SERVICE。seccomp 限制可用的系统调用，设成 RuntimeDefault 就能套用运行时自带的默认 profile，比放任不管强得多。AppArmor 在 1.23 仍通过注解启用，用来约束文件与网络访问。只读根文件系统是最后一道保险：应用写不了二进制，落地的 webshell 也难持久化，需要写入的目录单独挂 emptyDir。

这些零散配置从 1.23 起有了统一收口：Pod Security Standards 定义 privileged、baseline 与 restricted 三档，baseline 禁止特权容器、hostPath 等明显危险项，restricted 还要求非 root、禁止提权、drop 全部能力并限制 seccomp。给命名空间打上 pod-security.kubernetes.io/enforce: restricted 即可整段生效，再配 audit 与 warn 两个标签先观察后收紧。这也是 PSP 的替代路线：PSP 自 1.21 起废弃，1.23 上还能用但已不推荐，新集群应直接按 PSS 规划。

七、四个常见误区

第一是只扫 latest。标签会漂移，今天扫的 latest 和明天线上跑的未必是同一份内容，扫描结论对不上部署对象。扫描与签名都应针对 digest。

第二是忽略基础镜像。业务代码只占镜像的一小部分，大部分软件包来自基础镜像；平台不重建基础镜像，各团队只是在重复确认同一份旧结论。基础镜像要有固定的重建节奏。

第三是结果无人处理。报告发到群里，附一句“大家看一下”，实际上没人认领。可行的做法是指定 owner 与修复时限，把“新增高危且可修复”当作故障来跟，并在看板上按服务聚合，让积压可见。

第四是把扫描当成唯一防线。扫描只覆盖已知 CVE，硬编码密钥、过宽的 RBAC、错误的网络策略、被投毒的上游依赖，它一样都发现不了。扫描是流程中的一环，不是安全本身。

小结

容器安全是一条链，任何一环松了，其他环节的投入都会打折。构建阶段用最小基础镜像、多阶段构建、非 root 与 .dockerignore 缩小攻击面；入库阶段用 Trivy、Clair 或 Grype 做扫描，把阻断条件限定在“有修复、够严重、本次新增”，并坚持定时重扫；分发阶段用 cosign 签名、用 SBOM 留底，在准入控制器上拦截未签名镜像；运行阶段用 capabilities、seccomp、只读根文件系统与 PSS 把权限收到最小。最后别忘了给每一条告警指定负责人，工具只负责发现，修复永远是人完成的。
