等级保护 2.0 大数据扩展要求

等级保护 2.0 的基本要求面向通用信息系统，而大数据平台把数据本身变成了核心资产：一份数据会在采集、传输、存储、处理、共享交换与销毁之间流转，跨越多个组件、租户和接口。本文把大数据扩展要求公开的方向翻译成工程动作：资产梳理与分级、Hadoop 生态的认证授权、脱敏与加密、共享交换的审批与审计、平台基线与补丁。适合正在做等保建设或测评准备的数据平台团队阅读。

一、为什么通用要求不够用

等级保护 2.0 的基本要求，即 GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》，以通用信息系统为对象，按安全物理环境、安全通信网络、安全区域边界、安全计算环境、安全管理中心展开。这套框架对“主机加网络”的系统足够，放到大数据平台上却会出现三处错位。

第一是保护对象的错位。通用条款的落脚点是服务器、数据库和网络设备，而大数据平台真正的资产是数据集、数据目录、计算作业和对外数据服务。一台节点被重装，损失有限；一张明细表被复制到测试环境，损失可能无法撤回。

第二是边界的错位。传统系统的边界是网络区域，大数据平台的边界是接口与授权。JDBC 连接、REST 服务、消息订阅、文件摆渡，任何一条通道都可能把整表数据带出去，而这些通道往往由业务团队自行开通，并不出现在网络拓扑图上。

第三是审计的错位。通用要求关注登录、操作与安全事件，大数据场景更关心“谁在什么时间，用哪个账号，通过哪条路径，取走了哪些字段，取走多少行”。没有数据访问行为的留痕，事后既说不清责任，也做不了趋势分析。

需要说明的是，大数据扩展要求当时仍处于报批与试行阶段，公开可见的是方向而非定稿条文，本文因此不引条款号，也不谈控制项数量。实际建设中仍以基本要求为骨架，叠加《数据安全法》《个人信息保护法》与行业数据分级规范，取并集而非交集。

从数据活动的视角看，平台要保护的不是某一个组件，而是一条贯穿始终的链路：

flowchart LR
    A[数据采集] --> B[数据传输]
    B --> C[数据存储]
    C --> D[数据处理]
    D --> E[共享交换]
    E --> F[数据销毁]
    D --> C
    E --> C

图中的每个箭头都是一次信任传递：数据是否干净、通道是否加密、下游是否只拿到该拿的部分。扩展要求的方向，基本都能映射到这条链路上。

二、数据全生命周期：把要求落到数据活动上

按生命周期组织要求，每个环节都能找到责任人与验证方式，而不是笼统地说“加强数据安全”。下面分三段看。

采集与传输

采集环节的核心是来源可证、范围可控、通道可信。来源可证，指每个数据源都登记在资产目录里，标明提供方、责任人、更新频率与用途，外部采购的数据保留授权文件；范围可控，指按最小必要确定字段，不因为“以后用得上”就整表同步；通道可信，指采集接口要有身份认证，服务端校验调用方。

传输环节容易被低估。跨机房同步常见定时脚本调用 scp，口令硬编码在脚本里，密钥散落在多台机器上，出了问题也说不清谁传了什么。更稳妥的方式是统一走加密通道，用双向证书或短期凭据，传输任务纳入调度平台，每次执行留下源、目的、数据量与校验值。

涉及个人信息的采集，还要核对告知同意与目的限定。采集页面加了字段、同意范围没有同步更新，是检查中最常见的不一致。

存储与处理

存储的关键词是分域、加密、密钥分离。按数据级别划分存储区域，高敏数据不与一般数据混放；对敏感字段或整个目录启用加密，让数据在磁盘上以密文存在；密钥交给独立的 KMS 管理，使能管集群的运维人员拿不到密钥。

flowchart TD
    U[业务与开发人员] -->|认证与授权| S[数据服务层]
    S --> P[计算引擎]
    P --> H[存储与加密区]
    H --> K[KMS 密钥管理]
    O[平台运维] -->|只管理集群| H
    O -.->|无权取密钥| K

处理环节的坑集中在中间结果。Spark 作业从加密区读数据，join 后写到临时目录，而临时目录没有继承加密属性，敏感数据就以明文落了盘；Notebook 的本地缓存、查询引擎的溢写文件、导出的 CSV，都属于同一类泄漏面。控制手段不是禁止计算，而是把输出路径纳入统一管理：默认写入受控目录，临时目录定期清理，开发测试只用脱敏样本。用户自定义函数也要纳入白名单，来路不明的 jar 包等于把执行权限交给外部代码。

共享交换与销毁

共享交换是数据离开平台控制范围的地方。字段级授权、行级过滤和动态脱敏都能做，但审批缺失时，技术控制会被“先授权再补单”绕过去。务实的做法是把申请、审批、授权、复核、回收做成闭环：申请写清用途与字段，审批按级别判断，授权带有效期，到期自动回收。对外接口还要限制批量与频率，一天查十万次就是批量导出，限流、结果集上限、脱敏与水印要组合使用。

销毁经常被简化为删表。逻辑删除只是打了标记，底层文件、备份、快照、消息队列中的消息、缓存副本都还在。可执行的做法是明确留存期限，到期按路径清理并同步调整备份策略，介质报废走物理销毁或合规擦除，销毁动作同样记入审计。

环节 典型风险 可落地的控制
采集 来源不明、超范围采集 数据源登记、字段最小化、接口鉴权
传输 明文通道、凭据散落 加密通道、短期凭据、传输留痕
存储 混放、明文落盘、密钥同权 分域、加密区、KMS 分离
处理 中间结果泄漏、恶意 UDF 受控输出目录、UDF 白名单
共享 越权导出、授权不过期 审批闭环、动态脱敏、限流水印
销毁 只删逻辑、副本残留 留存期限、备份同步清理、介质销毁

三、平台安全：认证、授权与基线

大数据平台很少是单一产品，而是 HDFS、Hive、Spark、Kafka、调度系统与查询网关的组合，问题是身份不统一、授权各管一段、组件各自暴露管理端口。平台安全要做的，是把分散的控制点收拢成一套认证、一套授权、一份资产台账。

先有资产目录，再谈分级

没有目录就无法分级，没有分级就无法授权。梳理的最小集合包括数据集名称、责任人、存储位置、字段与敏感级别、上下游流转、对外接口和留存期限。更重要的是让结果能被机器读取，直接驱动授权与脱敏策略；只停在表格里，半年后一定过期。

Kerberos 解决“你是谁”

Kerberos 在集群内提供强认证：用户与服务都持有主体，凭票据访问服务，服务端据此确认调用方不是冒充者。它只回答身份问题，不回答权限问题。

工程上最容易出问题的是 keytab。它是服务身份的长期凭据，一旦泄漏，等同于服务被永久冒用。管理要求包括：文件权限收紧到属主可读、与代码仓库和镜像分离、按服务单独签发、定期轮换、下线服务及时吊销。票据有生命周期，长任务要配置续期，否则作业跑到一半认证过期。Kerberos 只覆盖集群内部，外部用户与 Web 前端通常由网关做代理认证，把外部身份转换成集群内主体，而不是把 keytab 发给客户端。

授权组件解决“你能做什么”

Ranger 一类组件把授权从各组件的配置文件里抽出来，做成集中策略：库、表、列、行过滤与脱敏方式按用户或组配置，并留下审计记录。它的定位是策略管理与执行点，不是身份源。策略变更要审批、纳入版本管理、定期复核；尤其要盯住“给所有人开查询”的历史策略，以及授权组件管理员这个角色，它实质上等同于数据超级权限。

多租户隔离与组件基线

共享集群要在存储、计算、队列三处同时隔离：目录权限、库表授权、资源队列与配额。只做配额不做权限，租户之间仍可互读；只做权限不做配额，一个租户的跑批能拖垮整个集群。还要堵住旁路：上层做了列级授权，用户却能直接读 HDFS 文件绕过，办法是统一入口、关闭短路读取、让文件系统权限与上层策略一致。

基线工作不炫技，却最容易被追问：完整的组件与版本台账、漏洞闭环、默认口令与示例配置清理、不必要的 REST 端口与 Web UI 关闭、必须开放的管理界面启用认证。

四、接口与共享交换：把边界画在数据出口

平台对外提供数据的方式无非几类：数据库连接、REST 接口、消息订阅、文件摆渡。每一类都要回答三个问题：调用方是谁、能取哪些字段、取走之后有没有记录。

数据库连接要区分服务账号与个人账号，禁止业务系统共用超级账号；账号按库表授权，能只读就不给写。REST 接口放在网关之后，做认证、限流与请求校验。消息订阅按主题授权，敏感主题不允许多个业务共用消费组。文件摆渡最容易被忽略，建议只允许白名单路径、落地加密、生成一次性链接并记录提取人。

共享交换的流程控制比技术控制更重要。一个可用的审批单至少包含数据范围、用途、期限、接收方与责任人；授权到期自动回收，而不是靠人记得。技术上配合字段级授权、行级过滤、动态脱敏与暗水印，出问题时能追到源头。

审计要记到字段与行数这一层。只记录登录没有意义，需要记录执行了什么查询、命中哪些表、返回多少行、是否脱敏、结果是否被下载。下面是一段策略示意，字段名仅作说明：

五、集中管控、审计与监测

集中管控的落点是账号、策略、日志、密钥：账号来自统一目录，授权策略集中管理，日志汇入统一平台，密钥由 KMS 托管。它与安全管理中心方向一致，区别在于对象是数据平台本身，还包括数据授权、数据服务与数据流出。

日志至少覆盖认证、授权决策、查询与作业、下载外发、组件审计。统一时间源、传输加密、只追加不修改，留存期限按法规与业务取较长者。很多单位有日志却不可用：时间不同步、字段缺失、只留一周，真出问题时拼不出链路。

监测的价值在于发现偏离。先用基线刻画正常：哪些账号在什么时段访问哪些表、平均返回多少行。非工作时段的大批量导出、首次访问高敏表、权限变更后立刻出现大量查询，都值得关注，告警要有人闭环。监测也要守边界，员工行为分析涉及个人信息，采集范围与查看权限都应有约束。

小结

大数据扩展要求当时仍在报批与试行，本文按公开方向给出工程落点：以数据生命周期为主线，把控制点落到采集、传输、存储、处理、共享交换与销毁的具体动作；以资产目录和分级为前置，用 Kerberos 解决身份、用 Ranger 一类组件解决授权、用统一入口堵住旁路；把共享交换的审批、脱敏与审计做成闭环，以集中日志与行为基线支撑监测。落地不必一次到位，先补台账与超级权限，再补加密与脱敏，最后用审计验证效果。
