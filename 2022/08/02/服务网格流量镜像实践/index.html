服务网格流量镜像实践

本文属于《Docker 与 Kubernetes》第 36/51 篇
上一篇系列目录下一篇

发版前最让人不安的问题，往往不是新代码能不能跑通，而是它在真实流量下会表现成什么样：长尾请求会不会超时，缓存命中率会不会掉，某个只在特定参数组合下才出现的空指针会不会被触发。流量镜像（shadow traffic）提供了一种折中的验证方式：把生产请求复制一份发给待验证的版本，原请求仍由旧版本处理并返回给用户，新版本的结果只用于观察，不参与任何决策。本文以 Istio 1.13 为基准，讲清镜像的配置方式、写请求带来的数据污染风险、影子环境的隔离做法，以及如何把镜像流量变成可比较的数据。

镜像流量能回答什么问题

上线前的验证手段大致有三层：单元测试与集成测试回答“逻辑对不对”，预发环境回答“部署起来能不能跑”，生产流量回答“在真实的数据分布和调用链路上稳不稳”。前两层成本低、可重复，但最大的缺陷是数据是造的：参数分布均匀、缓存总是冷的、下游从不抖动、用户行为规整。流量镜像补的正是这一层，它把线上正在发生的请求原样复制一份，交给待验证的版本处理，而用户的请求仍然由稳定的旧版本响应。

具体来说，镜像流量有三个高频用途。

其一是新版本验证。新版本上线前，用真实流量跑一遍，观察错误率、延迟分布、日志里的异常，以及业务层面的输出是否与旧版本一致。它比预发环境更接近真相，因为请求的参数组合、Header、Cookie、分页游标都是从线上来的。

其二是压测引流。造压测数据既费时又容易失真，而生产流量本身就是一份现成的压测脚本。把一部分真实流量镜像到扩容后的候选集群，可以在不影响用户的前提下观察新集群的吞吐上限、连接池表现和垃圾回收行为。这里要提醒一句，镜像流量只能验证“读”的容量，写路径的容量仍然需要专门的压测，原因后文会展开。

其三是灰度前预演。金丝雀发布把一小部分真实用户切到新版本，代价是这批用户承担了新版本的风险。镜像可以放在金丝雀之前：先让新版本在只读、无副作用的条件下跑一段时间，确认没有明显异常，再开始切真实用户。这一步不能替代金丝雀，但能把大部分低级错误挡在切流之前。

与金丝雀的区别可以用一张表说清：

维度 金丝雀发布 流量镜像
流量去向 一部分用户的请求发给新版本 复制一份给新版本，原请求仍由旧版本处理
用户是否感知 是，这批用户看到的是新版本 否，用户只看到旧版本的结果
新版本的结果 直接返回给用户 被丢弃，只用于记录与比对
出问题的影响面 这批真实用户 影子环境，可能污染影子数据
回滚方式 调整权重或回滚版本 把镜像比例调为零

这张表里最容易被忽略的是最后一行：镜像的“回滚”极其轻量，这也正是它适合做前置验证的原因。但轻量不等于无风险，镜像请求一旦落到生产数据库上，造成的重复写和脏数据不会因为“用户没感知”而消失。

还需要说明边界。镜像不能验证依赖真实副作用的链路，例如支付扣款、发券、发货；也不能替代容量规划，因为镜像比例通常远小于全量。本文只讨论镜像与影子验证本身，蓝绿、金丝雀、滚动的策略对比与指标门禁留给发布策略那篇。

VirtualService 的 mirror 是怎么工作的

在 Istio 里，镜像不是一个独立资源，而是 VirtualService 中某条 HTTP 路由的修饰字段。这条路由先按常规逻辑选出一个主目标，Envoy 把请求发过去并等待响应；与此同时，它再复制一份同样的请求，异步发往 mirror 指定的目标。主请求的响应原样返回给调用方，镜像请求的响应则被直接丢弃，既不参与状态码判定，也不计入这条路由的耗时。

这意味着镜像对用户是透明的：用户拿到的仍然是旧版本的结果，延迟也由旧版本决定。镜像请求失败、超时、连不上，都不会让主请求失败，也不会触发重试。反过来说，它在 Envoy 内部仍然是一次真实的上游调用，会占用连接、工作线程，产生统计，只是结果没人接收。

图里那条虚线是理解所有后续问题的关键：镜像是一条只有去程、没有回程的调用。调用方拿不到它的结果，它却真实地消耗了服务端的 CPU、数据库连接和下游配额。

还有一个实现细节值得知道：Envoy 在复制请求时，会在 Host 头后面追加 -shadow 后缀，服务端因此可以据此判断“这是一条镜像请求”。不过不同版本、不同代理实现的行为并不完全一致，本文建议把它当作粗筛手段，而不是唯一凭据。真正可靠的做法是让镜像目标本身具有独立身份，例如指向另一个 Service 或另一个命名空间，接收方从自身配置就能知道处于影子角色。

mirror 是路由级字段，一条路由只能有一个镜像目标；要同时镜像到两个版本，需要写两条带不同 match 的路由。跨命名空间引用时写全限定域名，目标在网格之外则要先定义 ServiceEntry，否则镜像会静默失败。

写请求是最大的坑：只镜像读路径

镜像最容易出的事故，不是新版本性能差，而是它把生产数据写了两遍。设想一个下单接口 POST /orders，镜像目标复用了同一份配置，数据库连接串指向生产库。用户点一次下单，v1 创建了一笔订单并返回订单号；v2 收到同一条镜像请求，也创建了一笔订单，只是响应被丢弃。用户看到一笔，后台有两笔，库存扣了两次，消息队列发出两条消息，仓库发了两件货。

这个例子里最危险的地方在于“没人看见”：用户端一切正常，主链路监控毫无异常，直到对账才发现多出来的订单。镜像请求在服务端看来和普通请求没有区别，同样的路径、Header 和请求体，它没有理由拒绝。

因此第一条纪律是：只镜像读路径。这里的“读”不能简单等同于 HTTP 方法，必须按“这次调用是否产生副作用”来判断。实践中可以用三层过滤。

第一层是方法白名单。只给 GET 和 HEAD 配镜像，其余方法走一条不带镜像的兜底路由。由于 Istio 的匹配是“首条命中即停止”，带镜像的路由必须写在前面：

第二层是路径白名单，而且要用正向列表，不要用排除列表。原因很现实：GET 并不等于安全。导出报表会写任务表，点击邮件里的确认链接会改状态，退出登录会删会话，埋点接口会写日志，某些支付平台的回调甚至设计成 GET。用排除法永远列不全，只有明确写出“这些路径允许镜像”，才能把未知风险挡在外面。这份名单最好从 OpenAPI 文档或网关路由表生成，再由熟悉业务的人逐条确认，而不是凭印象手写。

第三层是应用侧的兜底。无论网关层过滤得多仔细，服务本身都应该知道“我收到的是影子流量”，并对写操作直接拒绝。具体做法有三条，建议同时上：

  • 影子标识：镜像目标使用独立的 Service 名，或在入口注入固定 Header，服务启动时读取自身配置，处于影子角色就打开只读开关。
  • 只读账号：影子实例连接数据库时使用只有 SELECT 权限的账号。这是最硬的一道防线，代码写错了也写不进去。
  • 写操作拦截：在数据访问层或 ORM 钩子里统一拦截 INSERT、UPDATE、DELETE，以及消息发送、缓存写入、外部支付调用，命中即抛异常并打点。

对于 GraphQL 和 gRPC，方法过滤会失效。GraphQL 全部走 POST，需要解析 operation 名，只放行查询类操作；gRPC 则按方法全名过滤，只镜像 Get、List、Query 这类只读方法。这两类接口的镜像比例建议压得更低，因为请求体更大、解析成本更高。

最后要意识到，读接口也可能间接产生写：缓存未命中时的回填、浏览量计数、审计日志、懒加载的关联数据。这些写通常不致命，但会污染影子环境的统计，也会让“影子库只读”这条防线频繁报警。比较稳妥的做法是给影子环境单独关闭缓存回填和计数类写入，把这类副作用集中到一个开关里管理。

影子环境：把新版本关进笼子

即使做到了只读镜像，也不应该让新版本连生产中间件。原因有三：读请求会触发缓存回填和计数；新版本可能新增了下游调用，而这些调用在生产侧没有对应的配额；最坏的情况是代码里藏着一条不经过统一拦截的写路径，比如某个定时任务在启动时初始化数据。把新版本放进一套独立的影子环境，是用架构而不是纪律来保证隔离。

一套够用的影子环境包含四类资源：独立的数据库、独立的缓存、独立的消息队列，以及被 mock 掉的外部依赖。拓扑大致如下：

flowchart LR
    A[生产 reviews v1] --> B[生产 MySQL]
    A --> C[生产 Redis]
    A --> D[生产 Kafka]
    M[镜像流量] --> S[影子 reviews v2]
    S --> E[影子 MySQL 脱敏快照]
    S --> F[影子 Redis 独立实例]
    S --> G[影子 Kafka 独立 topic]
    S --> H[支付与短信 Mock]

数据库是隔离的重点。可用的做法是从生产备份恢复一份快照到影子实例，恢复完成后立刻做脱敏，再让影子服务连过去。脱敏要在影子副本上做，绝不能为了影子环境去动生产数据。手机号、身份证、地址、银行卡这类字段替换成格式合法但内容虚构的值；需要保持关联的字段，例如用户 ID，用令牌化处理，保证同一用户在各表里仍是同一个值，否则关联查询会全部落空。

这里有一个容易被低估的问题：影子库的数据是某一时刻的快照，而镜像流量是当下的。用户刚下的订单在影子库里不存在，新版本查不到就会返回 404，差异报告里立刻多出一大片“新旧不一致”。解决办法有两个，一是提高快照刷新频率，二是让影子服务对“查不到”的请求走只读回源，回源时仍然使用只读账号。前者简单但有窗口，后者复杂但准确，按业务对一致性的要求选择。

缓存的隔离要同时做到“不污染生产”和“不误读生产”。最省事的做法是给影子环境一个独立实例；如果资源紧张，至少要用不同的数据库编号或统一 key 前缀，并给所有 key 设置较短的过期时间。千万不要让影子服务连生产 Redis：它会把新版本的数据写进生产缓存，也会因为读到了生产缓存而让“缓存命中率”这类指标失去意义。

消息队列的隔离靠两件事：独立的 topic 前缀和独立的消费组。影子服务如果必须发消息，就发到 shadow. 开头的 topic，由影子消费者处理，消费者只做记录和校验，不触发任何真实动作。更保守的做法是直接在影子配置里关闭消息发送，把“本该发消息”这件事记到日志里。两种做法没有优劣，取决于你要验证的是消息内容还是端到端链路。

外部依赖必须 mock，尤其是支付、短信、物流、风控这类会产生真实副作用或真实费用的服务。mock 服务要满足三个要求：响应确定、可记录、可注入延迟与错误，三者分别服务于差异比对、调用核对与容错验证。需要注意的是，mock 的延迟是人为设定的，不能用它来评价新版本的性能，性能数据要取自影子服务自身的处理耗时。

影子环境的资源不必按生产一比一配置，通常百分之十到百分之三十就够，前提是镜像比例也相应受限。所有资源打上统一的标签，例如 env=shadow、batch=20220801，清理时才能一次找全。清理策略要在环境创建时就定好：数据库按批次删除或整库重建，缓存靠 TTL 自然过期，消息 topic 设置保留时长，对象存储配置生命周期规则。没有清理策略的影子环境，最后一定会变成没人敢动的僵尸资源。

观测：把镜像流量变成可比较的数据

镜像跑起来只是开始，真正的工作是把两边的表现变成可以对比的数字。观测分三层：网格层的指标告诉你“量和延迟”，应用层的日志告诉你“发生了什么”，响应体的差异告诉你“结果对不对”。三层缺一不可，只做第一层很容易得出“新版本没问题”的错觉。

网格层的数据来自 Sidecar 上报的指标。影子服务作为一个独立的工作负载，会有自己的 istio_requests_total 和 istio_request_duration_milliseconds，按 destination_workload、response_code 等标签聚合，就能得到它的请求量、错误率和延迟分位数。与主版本对比时，建议看 p50、p95、p99 三个点，而不是平均值：新版本的问题往往藏在长尾里，平均值会被大量快速请求稀释。

对比时有三个口径问题必须校正。第一，镜像请求没有客户端重试，主请求可能有，因此影子的错误率天然会高一些，不能直接把两个百分比相减就下结论。第二，镜像流量打满影子集群的连接池时，表现是 503 或上游连接失败，而不是超时，看到这类错误要先怀疑容量，再怀疑代码。第三，源侧的访问日志里通常只有主请求，镜像请求的落点要看影子服务侧的日志与指标，排查时不要盯错了地方。

应用层建议输出结构化日志，每条记录包含请求 ID、路由、方法、状态码、处理耗时和响应摘要。请求 ID 在入口生成并透传，主请求和镜像请求就会带着同一个 ID，后续可以按 ID 对齐两条记录。

响应体的比对需要额外落盘，因为网格指标不保存 body。做法是在应用层按比例采样，把主请求和影子请求的响应摘要写入对象存储，再由离线任务配对比较。整条流水线可以画成这样：

flowchart TD
    R[入口生成 request_id] --> P[主请求 v1]
    R --> S[镜像请求 v2]
    P --> L1[采样落盘 主响应]
    S --> L2[采样落盘 影子响应]
    L1 --> J[按 request_id 对齐]
    L2 --> J
    J --> N[归一化与字段级 diff]
    N --> O[差异率报表与样本复核]

比对的第一道工序是归一化，否则差异报告会被噪声淹没。需要处理的东西包括：时间戳、链路 ID、随机数与自增 ID、数组顺序、浮点数精度、分页总数。数组要先按业务主键排序再比较，金额用定点数或字符串比较，浮点字段给一个容差范围。字段缺失和字段为 null 是两回事，前者可能意味着新版本漏了字段，后者可能只是业务上确实为空，报告里要分开统计。

第二道工序是分类。差异大致分三种：预期差异，例如新版本新增了字段、调整了默认值；环境差异，例如影子库快照过期导致查不到数据；真实缺陷，例如同样的输入算出了不同的价格。前两种要在比对规则里显式排除或标注，否则真实缺陷会被大量噪声掩盖，报告发出去两次就没人看了。建议给每个接口维护一份“已知差异清单”，随版本更新。

第三道工序是抽样复核。自动化只能告诉你哪些请求不一致，不能告诉你为什么。每天抽几十条样本人工看一遍请求参数和两边响应，往往能发现规则覆盖不到的问题，比再加一层自动分析更有效。

存储成本要提前算。假设生产峰值每秒两千次请求，镜像比例百分之一，每条记录十 KB，那么每天新增约十七 GB 原始数据，压缩后大约是三分之一。这个量级用对象存储完全可以接受，但前提是只存采样数据、只保留七到十四天、并且优先保留有差异的样本。如果不做采样就全量落盘，成本会迅速超过收益。

容量：镜像流量会成倍放大下游压力

镜像不是“免费的第二份流量”。对宿主服务而言，每个请求多了一次复制、一次序列化和一次额外的上游调用；对影子服务而言，它收到的是实打实的请求；对下游而言，影子服务发出的每一次调用都是新增的。放大关系可以简单写成两行：

影子入口流量 = 生产入口流量 × 镜像比例

影子下游流量 = 影子入口流量 × 单请求平均下游调用数

第二行常被忽略。一个商品详情页可能调用价格、库存、评价、推荐四个服务，镜像百分之十的详情页流量，等于给这四个下游各增加百分之十的负载，而且这些调用与生产调用共享同一批实例。如果下游本身已经在七成水位运行，这百分之十足以把它推到过载。

所以容量控制的第一条是给影子链路设上限，而不是只靠镜像比例。如果影子实例已经用独立的 Service 暴露，可以在这个 Service 上单独配置连接池上限，让打满时快速失败而不是排队堆积：

如果仍然复用同一个 Service 的 subset，就把同样的 trafficPolicy 写在对应 subset 下，效果一致。

这段配置有两个作用：连接池上限把影子流量关在一个笼子里，异常检测则在影子实例连续出错时把它摘掉，避免一条坏链路反复超时、拖慢源侧 Sidecar 的工作线程。注意异常检测要配在影子 subset 上，不要配在共用 subset 上，否则影子的问题会误伤主链路。

第二条是限流。Istio 1.13 没有一等公民的本地限流 API，通常用 EnvoyFilter 注入 envoy.filters.http.local_ratelimit，或者让影子服务自己在入口做令牌桶，超限返回 429。限流值按影子环境的承受能力设定，而不是按镜像比例反推。

第三条是时间窗。不要在业务高峰做全量镜像，也不要在高峰扩大比例。比较稳妥的节奏是：先在低峰期用百分之一跑通链路，没有异常再提到百分之五，确认稳定后才考虑百分之十。促销、大促、发版窗口期一律暂停镜像，因为这些时段生产本身就在高位运行，任何额外负载都可能成为压垮系统的最后一根稻草。

还有一些请求根本不适合镜像。文件上传、大文件下载、长连接与流式响应，要么请求体极大，会占用 Sidecar 的内存，要么生命周期很长，镜像过去只是白白占着连接，应该在路由层按路径或按 Header 排除。

最后是开关。镜像配置应该独立成一小段可单独回滚的资源，而不是和主路由混在一个几百行的 VirtualService 里。值班手册要写清关闭镜像的具体操作：把 mirrorPercentage 改成零，或直接删掉 mirror 字段，并确认配置已下发到所有 Sidecar。这个操作最好在演练中真的执行过一次。

落地顺序与检查清单

把上面这些内容串起来，一次完整的镜像验证可以分五步走。

第一步，准备影子环境与只读白名单。影子库、缓存、消息队列、mock 全部就绪，脱敏完成；从 OpenAPI 或网关路由表生成候选读接口列表，由业务方逐条确认副作用。

第二步，同版本自镜像。让 v1 的流量镜像到另一组同样是 v1 的实例，比例百分之一。这一步不验证新功能，只验证管道本身：配置是否生效、日志是否带上了请求 ID、采样是否落盘、差异是否为零。如果自镜像都能比出差异，说明比对规则有问题，先修规则再谈新版本。

第三步，新版本小比例镜像。切到 v2，比例保持百分之一，重点看错误率、p99 延迟和差异率。这个阶段最常见的发现不是崩溃，而是慢查询、连接泄漏、日志暴涨这类“不报错但不健康”的问题。

第四步，扩大比例并形成报告。比例提到百分之五，持续一到两天，把指标、差异样本和复核结论整理成报告，明确写出哪些差异是预期的、哪些已修复、哪些仍需观察，作为是否进入金丝雀的依据。

第五步，关闭并清理。验证结束后把比例归零，删除镜像配置，按批次清理影子数据与资源。不要把一个长期开着的镜像当成常态监控，它的成本和风险都会随时间累积。

一份可以贴在团队 wiki 上的检查清单：

  • 镜像目标是否有独立的数据库、缓存与消息队列，且数据库账号只有读权限。
  • 读接口白名单是否经过业务方确认，是否排除了有副作用的 GET。
  • 影子服务的所有外部调用是否指向 mock，mock 是否记录调用参数。
  • 影子环境的资源是否打了统一标签，是否有明确的清理时间与责任人。
  • 镜像比例是否显式写出，是否避开了业务高峰与大促窗口。
  • 影子 subset 是否配置了连接池上限与异常检测。
  • 请求 ID 是否在入口生成并透传，主请求与镜像请求能否按 ID 对齐。
  • 是否演练过“一键关闭镜像”，值班同学是否知道在哪里改。

小结

流量镜像的价值在于用真实流量验证新版本，同时不改变任何用户看到的结果，这让它成为金丝雀之前一道低成本的预演。它的实现并不复杂，Istio 的 VirtualService 只需要 mirror 与 mirrorPercentage 两个字段，真正难的是边界控制。写请求必须被挡在镜像之外，判断依据是“有无副作用”而不是 HTTP 方法，最硬的兜底是影子库的只读账号。影子环境要独立、要脱敏、要有清理策略，否则镜像会变成数据污染的源头。观测上要把指标、日志与响应体差异结合起来，并接受采样带来的成本约束。最后，镜像会成倍放大下游压力，比例、限流、时间窗与关闭开关这四件事，缺一件都不应该上线。
