分布式消息队列选型

本文属于《Go 微服务架构》第 31/35 篇
上一篇系列目录下一篇

消息队列选型通常被简化成一张吞吐量对比表，但真正决定项目成败的，往往是数据模型是否匹配业务语义、积压时系统是否还站得住、以及团队半夜能不能把它修好。本文把 Kafka、RocketMQ、RabbitMQ、Pulsar 放在同一套维度下比较，先讲清“日志型”与“队列型”的根源差异，再逐项落到投递语义、顺序、延迟与事务、积压回放、运维与生态，最后给出一张可调整权重的打分表和一套决策顺序。本文假设读者已经用过至少一种消息队列，不重复安装与收发的基础操作。

先分清两种模型：日志与队列

“消息队列”这个词把两类结构完全不同的系统装进了同一个篮子。日志型系统把消息追加到分区日志的末尾，消费的本质是移动一个位点，消息不会因为被读过而消失；队列型系统把消息放进队列，投递给消费者，收到确认后删除。前者的代表是 Kafka 与 Pulsar，后者的典型是 RabbitMQ，而 RocketMQ 处在中间：存储层是一份只追加的 CommitLog，消费层却用消费组加队列位点，行为更像队列，同时保留了按位点回放的能力。

可以用三个问题快速判断一个系统偏哪边：消息被消费之后还在不在；能不能从某个历史位置重新读一遍；多个消费者是各读一份，还是分摊同一份。三个答案基本决定后续所有语义。

        L --> C1[消费者A按位点读]

        L --> R[保留期内可重放]

图中最容易被忽视的是那条确认回路。队列型的删除是一次协作：消费者确认处理完，Broker 才敢丢；日志型没有这条回路，删除由保留策略统一裁决，与消费进度无关。于是日志型天然支持多订阅与回放，代价是预留存储、顺序只在分区内成立；队列型天然支持逐条确认与灵活路由，代价是堆积受内存与分页掣肘，重放要另做设计。

理解了这一层，再看“哪个吞吐高”“哪个延迟低”才有意义，因为那些数字多半是在各自最擅长的模型下测出来的。选型的第一步不是比性能，而是确认业务要的是“一份可反复读的流水”，还是“一件必须被处理掉的任务”。

四套系统的数据模型

四套系统都能叫“主题”，但主题下面的结构差别很大，这决定了并行度、顺序边界和扩容方式。

Kafka 的主题被切成若干分区，每个分区是一串按 offset 编号的日志段文件。消费组把分区分配给组内消费者，一个分区在同一时刻只由一个消费者读取，所以分区数就是并行度的上限。消息写到哪个分区，由 key 的哈希或轮询决定，这也正是顺序性的边界。

RocketMQ 的主题在逻辑上切成若干 Message Queue，默认每个主题四个。所有主题的消息统一顺序追加到 CommitLog，单个文件默认 1 GB；ConsumeQueue 为每个队列维护一份索引，每条索引 20 字节，记录消息在 CommitLog 中的位置、大小与 tag 哈希。消费组同样以队列为单位分配消费者。

RabbitMQ 3.10 的核心是交换机、绑定、队列三件套，vhost 负责逻辑隔离。队列分经典队列与仲裁队列，后者基于 Raft 做多副本。它没有分区概念，并行度靠增加队列与消费者，单个队列的吞吐有上限。

Pulsar 2.10 用租户、命名空间、主题三层组织资源，主题再切分区。消息落在 BookKeeper 的 ledger 里，Broker 本身不持久化数据，因此可以无状态扩容；每个订阅持有自己的 cursor，独立记录消费进度。

系统 逻辑单元 存储形态 消费进度 扩容方式
Kafka 主题、分区 Broker 本地日志段 消费组提交 offset 加 Broker 并迁移分区
RocketMQ 主题、消息队列 CommitLog 加 ConsumeQueue Broker 侧消费位点 加 Broker，队列数需规划
RabbitMQ 交换机、队列 队列（内存与磁盘） 逐条 ack 加节点、加队列
Pulsar 租户、命名空间、主题 BookKeeper ledger 订阅 cursor 加 BookKeeper 或 Broker

这些差异很实际：Kafka 扩容常伴随分区迁移，Pulsar 的存储与计算可以分开扩，RocketMQ 受单机磁盘限制，RabbitMQ 堆积时要在内存与磁盘之间倒换。

投递语义与顺序性

讨论投递语义先要统一三个词。最多一次是发出去就不管，可能丢；至少一次是确认后才算完成，可能重；恰好一次是既不丢也不重。绝大多数生产系统默认落在至少一次，恰好一次则要靠额外机制去逼近。

Kafka 的生产者设置 acks=all 并开启幂等，可以避免重试导致的重复写入；消费端先处理业务再提交位点，中途崩溃就会重读，所以是至少一次。事务配合 read_committed 能把读消息、算结果、写结果、提交位点做成一个原子操作，但边界止于 Kafka 自身，管不到外部数据库。

RabbitMQ 用发布确认加手动 ack 保证不丢，代价是网络抖动、消费者超时都会带来重复投递。它没有内建的恰好一次，只能靠业务去重。

RocketMQ 同步发送加消费成功应答，失败按策略重试，超过次数进入死信队列，语义同样是至少一次。Pulsar 支持单条与累积确认，也提供事务，可以把消费、处理、生产、确认放进一个事务，但适用范围与 Kafka 类似。

端到端的恰好一次不是中间件的开关，而是“消息语义 + 业务幂等”的组合。选型时该问“它能帮我少写多少去重代码”，而不是“它是不是恰好一次”。

有序的边界在分区

Kafka 把同一个 key 的消息送进同一个分区，分区内按 offset 有序。这个保证有两个前提：生产者不能因为重试把后发的消息插到前面，幂等生产者正是为此而生；分区数不能随意增加，因为扩容会改变 key 到分区的映射，新旧消息的顺序关系就断了。

RocketMQ 的顺序消息需要生产者用队列选择器决定消息进哪个队列，消费者换成顺序监听器逐条处理。队列数通常在创建主题时定好，中途增加队列会让同一业务键落到新队列，顺序断裂；消费失败会阻塞当前队列，所以顺序队列不宜承载慢业务。

RabbitMQ 只有在单队列、单消费者时才严格有序。多个消费者并发消费同一队列，处理完成的时间自然交错。要保序可以用单活跃消费者，让同一时刻只有一个消费者工作；也可以用一致性哈希交换机，把同一业务键固定路由到同一队列。

Pulsar 同样是分区内有序，key_shared 订阅按 key 把消息分给不同消费者，兼顾并行与键内顺序。四家的结论其实一致：全局有序等价于单分区单线程，吞吐必然受限。选型时该问的是“乱序的代价有多大”，多数业务只需要业务键级有序。

延迟、定时与事务消息

Kafka 没有原生的延迟消息。常见做法是外部调度器扫表后再投递，或者按时间轮搭多级主题，比如 30 秒、1 分钟、5 分钟各一层，到期后逐层下移。能实现，但精度、可靠性与消息量都要自己扛，不建议只为了延迟需求去选 Kafka。

RabbitMQ 有两条路。第一条是 TTL 加死信交换机：消息过期后转入死信队列再消费。要注意逐条设置 TTL 时，过期只在消息到达队头时才判定，长延迟消息会拖住后面的短延迟消息，通常按档位拆队列。第二条是延迟消息插件，声明 x-delayed-message 类型的交换机，由服务端暂存并到期投递，精度可到毫秒；但它是社区插件，量大时需单独评估。

RocketMQ 4.9 只支持固定延迟级别，默认 18 级：1 秒、5 秒、10 秒、30 秒，1 到 10 分钟，20 分钟、30 分钟，1 小时、2 小时。发送时指定级别，Broker 到期后转投真实主题。它覆盖了 30 分钟未支付关单、1 小时提醒这类场景，但给不了任意时刻。RocketMQ 5.0 正在推进任意时间的定时消息，本文仍以 4.9 为准。

Pulsar 提供 deliverAfter 与 deliverAt，由消费者指定相对延迟或绝对时间，服务端跟踪到期后再投递。它不需要预先建一堆延迟主题，但延迟期间消息依然计入积压，海量长延迟会占用 Broker 内存，上线前需要压测。

事务消息的边界

RocketMQ 的事务消息是它的招牌。生产者先发一条半消息，写入内部主题但对消费者不可见；接着执行本地事务，成功则提交，失败则回滚；如果 Broker 长时间没收到确认，会主动回查生产者的本地事务状态，默认约一分钟回查一次，最多十五次。它解决的是“数据库写入”与“消息发送”这两件事的原子性，消费端仍然要自己做幂等。

Kafka 的事务是另一回事，它服务于流处理的读、算、写与位点提交，让下游在 read_committed 下看不到未提交的数据，边界不出 Kafka。Pulsar 从 2.8 起提供的事务也类似。RabbitMQ 没有对应机制，标准做法是本地消息表加定时补偿，或者用 CDC 把数据库变更投递出去。订单场景若团队是 Java 栈，RocketMQ 最省事；否则用 outbox 表配 Kafka 也能达到同样的最终一致。

积压、回放与多租户

Kafka 的积压能力取决于磁盘和分区并行度，消费 lag 是最重要的监控指标。回放只需把位点重置到某个 offset 或时间点，代价是下游要能承受重复数据。保留策略决定能回多久，扩分区会破坏 key 顺序，都要在容量规划时定下来。

Pulsar 用 backlog quota 约束单个订阅的积压，超限后按策略拒绝写入或丢弃最旧消息。分层存储能把冷数据卸载到对象存储，回放窗口很长，代价是读旧数据延迟上升。

RocketMQ 的 CommitLog 顺序写让堆积表现不错，消费进度保存在 Broker，按时间重置位点也方便；但磁盘写满同样会拒写，ConsumeQueue 损坏后的重建相当耗时。

RabbitMQ 的堆积是明显弱项。内存到达高水位会触发流控，直接阻塞生产者；消息分页到磁盘后吞吐下降。3.9 引入的 Streams 提供日志式消费，能缓解大积压，但它是另一套抽象，老队列不会自动获得这些能力。

多租户方面，Pulsar 的租户与命名空间最完整，配额、隔离、跨地域复制都有原生支持；RabbitMQ 用 vhost 隔离，简单够用；Kafka 没有租户概念，只能分集群或用客户端配额近似；RocketMQ 4.9 同样以集群隔离为主。

运维复杂度与生态

Kafka 3.2 的生产集群仍以 ZooKeeper 管理元数据，KRaft 要到 3.3 才计划转为生产可用，此时不应按 KRaft 规划生产集群。它的生态最完整，Connect、Streams、ksqlDB、Schema Registry 与各语言客户端齐全，排障资料也最多。

RocketMQ 组件少，NameServer 无状态，Broker 主从或 DLedger；Java 栈用起来最顺，Spring Cloud Alibaba 集成成熟，Go 与 C++ 客户端多由社区维护。

RabbitMQ 跑在 Erlang 虚拟机上，集群与仲裁队列成熟，管理界面和插件是加分项，适合中小规模业务消息。

Pulsar 要同时维护 ZooKeeper、BookKeeper、Broker 与 Proxy，门槛最高；换来的是多租户、跨地域复制与分层存储的原生支持。

场景对照与打分表

日志采集与流处理优先 Kafka，多租户或跨地域再看 Pulsar；业务解耦与复杂路由选 RabbitMQ；固定档位的延迟任务用 RocketMQ 最省事，任意时刻则要考虑自建调度；订单事务消息，Java 栈直接用 RocketMQ，否则用 outbox 表配 Kafka；超大积压回放选 Kafka 或 Pulsar；多租户 SaaS 优先 Pulsar，其次用 RabbitMQ 的 vhost。

先看运维，再看功能，是笔者建议的顺序。功能缺口可以加组件补，运维能力补不上：出故障时谁能看线程栈、谁能扩分区、谁能把积压追回来，这些答案比功能清单更决定生死。下面是一份示意打分，权重应由团队按现状调整。

维度 权重 Kafka RocketMQ RabbitMQ Pulsar
运维可控性 25 4 4 4 2
功能匹配 25 2 5 4 3
积压与回放 15 5 4 2 5
生态与客户端 15 5 3 4 3
多租户 10 2 2 3 5
团队熟悉度 10 4 3 4 1
加权合计 100 3.60 3.80 3.60 3.05

Kafka 与 RabbitMQ 同分却不能互换，说明总分只用于收敛讨论，最终仍要回到场景。权重稍一调整排名就变，这正是打分表的价值：把“我觉得”变成可争论的参数。

小结

消息队列选型没有通吃答案：日志型擅长流转与回放，队列型擅长任务与路由，RocketMQ 在两者之间补上了事务与延迟。先确认业务要的是流水还是任务，再用运维可控性做第一道筛子，最后用加权打分统一团队认知。版本会变，模型与边界不会。
