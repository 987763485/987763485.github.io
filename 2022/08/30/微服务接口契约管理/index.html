微服务接口契约管理

本文属于《Go 微服务架构》第 10/35 篇
上一篇系列目录下一篇

当一个接口同时被两个团队的三个服务、四种语言的客户端和若干条离线任务调用时，它就不再是某个服务的私有实现，而是一份需要被管理的协议。本文讨论微服务接口契约的三种载体、兼容性判定规则、版本与弃用策略，以及把契约放进评审、CI 和发布流程的具体做法。适合正在拆分服务、维护开放平台，或者经常被“上游悄悄改了个字段”困扰的后端工程师阅读。

一、接口契约到底是什么

很多团队把契约等同于一份接口文档，这是一个容易付出代价的误解。文档只描述了“现在长什么样”，而契约要回答三个层次的问题：结构上有什么字段、什么类型、是否必填；行为上返回什么状态码、错误体如何组织、是否幂等、分页与排序的语义是什么；演进上哪些改动允许发生、哪些必须先协商。前两层决定调用方能不能正确解析，第三层决定这份协议能不能活过下一次需求评审。

现实中的故障往往不在结构层，而在语义层。笔者见过一个典型案例：订单服务把 amount 字段的单位从“元”改成了“分”，字段名、类型、必填性全都没变，所有静态检查都通过，但结算系统把 19900 元当成了 199 元。还有一次，提供方清理了一个“三个月没人调用”的字段，结果某个只在每月 1 号运行的报表任务失败了，而这个调用方从来没有出现在任何调用链拓扑里。

因此，契约管理的目标不是让接口永远不变，而是让变化变得可预期、可检测、可协商。要做到这一点，需要三样东西：一个机器可读的载体，使工具能够比对差异；一套明确的兼容性规则，使“能不能改”不依赖个人判断；一条贯穿评审、集成和发布的流程，使规则真正生效。三者缺一，契约就会退化成 wiki 上那页两年没人更新的表格。

还需要区分本文与其他几篇的边界。OpenAPI 到 TypeScript 类型的生成、gRPC 的具体调用方式、Protobuf 的二进制编码细节，都是实现层面的问题，本文只在必要处提及。这里关心的是一份契约从提出、评审、实现、发布到退役的完整生命周期，以及人与工具各自承担什么。

二、契约的三种载体

契约的载体取决于通信方式。同步的 HTTP/JSON 接口通常用 OpenAPI 描述，gRPC 接口用 Protobuf 的 IDL 描述，异步消息则依赖消息体的 schema，常见的是 Avro 或 JSON Schema。三者的表达能力不同，兼容性规则也各有侧重，但治理思路是相通的。

2.1 OpenAPI：HTTP 接口的描述格式

OpenAPI 规范由 SmartBear 在 2015 年将 Swagger 规范捐献给 Linux 基金会后演进而来，3.0 版本于 2017 年发布，3.1 版本于 2021 年 2 月发布。3.1 的一个重要变化是 schema 对象与 JSON Schema 2020-12 对齐，nullable 被联合类型取代；3.0 与 3.1 在这一点上不兼容，团队升级时需要统一口径，否则同一份契约在两种工具里会得到不同结论。

2.2 Protobuf：gRPC 的接口定义

Protobuf 用字段编号而不是字段名来标识数据，这个设计从根上改变了兼容性的判定方式。字段名可以随意重命名而不影响线格式，但字段编号一旦发布就不能复用；删除字段时必须把编号和名字放进 reserved，防止后来者误用。proto3 在 2016 年发布，去掉了字段的 required，所有标量字段都有默认值，这也意味着“字段是否出现”和“字段是否为零值”在语义上不再可区分。

proto3 要求枚举的第一个值必须为 0，通常命名为 UNSPECIFIED，这样默认值不会意外落到某个真实业务状态上。对于枚举扩展，旧版客户端会保留不认识的枚举数字，读取时表现为未知值，但业务代码仍需处理“未知状态”分支。

2.3 异步消息的 schema

消息队列里的契约比同步接口更隐蔽，因为生产者发布消息时，消费者可能根本不在线。Kafka 生态里常见的做法是把 schema 注册到 Schema Registry，消息体只携带 schema 的 ID，消费者按 ID 拉取对应的 schema 再反序列化。Confluent 开源的 Schema Registry 提供了这套机制，支持 Avro、JSON Schema 和 Protobuf 三种格式，并为每个主题维护兼容性级别。

Avro 的兼容性规则定义得相当细。它区分向后兼容（新 schema 能读旧数据）、向前兼容（旧 schema 能读新数据）和完全兼容。新增带默认值的字段是向后兼容的，因为读旧数据时可以用默认值填充；删除带默认值的字段是向前兼容的；而重命名字段需要借助 aliases，否则等同于删除加新增。JSON Schema 没有内建的兼容性模型，通常靠工具比对 required、类型和 additionalProperties 的变化，规则不如 Avro 明确，需要团队自己约定。

这段 Avro schema 里，currency 和 channel 都带默认值，因此后续新增同类型的可选字段不会打断旧消费者。反过来，如果把 totalAmount 从 long 改成 double，Avro 的规则允许部分数值类型提升，但精度损失和下游的舍入行为必须单独评估，不能只看工具输出的“兼容”二字。

三、兼容与破坏：把判断变成清单

“这个改动兼容吗”是契约管理里被问得最多的问题，也是最容易被含糊回答的问题。要给出确定答案，先要定义清楚兼容的方向：向后兼容指新版本提供方能服务旧版本消费者，向前兼容指旧版本提供方能处理新版本消费者发来的请求。多数团队真正需要的是向后兼容，因为提供方总要先上线；但消费者升级往往滞后数月，所以两个方向都得有人负责。

3.1 逐项变更清单

把常见变更列成清单，评审时逐条对照，比依赖直觉可靠得多。下表以 HTTP/JSON 接口为主，Protobuf 和 Avro 的差异在备注中说明。

变更 通常判定 说明
新增可选请求字段 兼容 提供方需忽略未知字段，不能因多字段报错
新增响应字段 兼容 消费者必须容忍未知字段
新增必填请求字段 破坏 旧消费者不会传，直接被拒
删除响应字段 破坏 消费者可能仍在读取
字段改名 破坏 等价于删除加新增
放宽类型（int 到 long） 谨慎 取决于语言与序列化实现
收紧类型（long 到 int） 破坏 溢出与解析失败
修改字段单位或精度 破坏 静态检查无法发现
枚举新增值 谨慎 消费者需有默认分支
枚举删除值 破坏 历史数据无法解析
修改默认值 破坏 未显式传值的调用方行为改变
修改路径或 HTTP 方法 破坏 所有调用方立即失败
修改错误码语义 破坏 重试与告警逻辑失效

新增可选字段之所以安全，前提是双方都遵守“宽松读取”的原则：提供方忽略不认识的请求字段，消费者忽略不认识的响应字段。很多序列化框架默认是严格模式，遇到未知字段直接抛异常，这时“新增字段”就会变成事实上的破坏性变更。Go 的 encoding/json 默认忽略未知字段，开启 DisallowUnknownFields 后则会报错；Jackson 也有类似开关。这条约定应当写进契约，而不是假设所有人都知道。

删除字段的问题在于“没人用”这个判断几乎总是错的。可行做法是先标记弃用并观察一段时间，通过访问日志、字段级埋点或网关的响应采样确认无人读取，再执行删除。Protobuf 的做法更彻底：删除字段后立刻把编号放进 reserved，并在注释里记录删除原因和版本，避免半年后有人觉得“这个编号空着可惜”而复用它。编号复用会导致新旧数据被错误解析，是最难排查的一类线上故障。

修改枚举则介于兼容与破坏之间。新增枚举值对能正确处理未知值的消费者是兼容的，对写了 switch 且没有 default 分支的消费者就是破坏。Go 里对枚举做 switch 时如果没有覆盖全部值，编译器不会报错；Java 的 switch 遇到 null 还会直接抛异常。比较稳妥的治理方式是要求消费方对所有枚举字段保留兜底分支，并在契约评审时把“新增枚举值”列为需要通知的变更，而不是默认可行。

3.2 语义兼容比结构兼容更难

结构比对工具能发现字段消失、类型变化，却发现不了含义漂移。金额单位从元改成分、时间戳从秒改成毫秒、手机号从“带国家码”改成“不带国家码”、分页从“页码”改成“游标”，这些改动在 schema 上几乎无痕，在业务上却是灾难。治理这类变更只能靠两件事：把语义写进字段描述并纳入评审清单；对关键字段建立数据质量监控，例如金额分布、时间戳量级的突变告警。

默认值也是语义的一部分。一个 status 字段原来缺省为 PENDING，后来改成缺省为 UNKNOWN，接口签名没变，但所有依赖缺省行为的调用方都变了。这类改动应当被视为破坏性变更，至少需要版本号或显式的迁移窗口。

3.3 让工具承担重复判断

人工评审适合处理语义问题，机械比对应当交给工具。OpenAPI 生态里有 openapi-diff 一类工具，可以比较两个版本的文档并输出 breaking、non-breaking 和 unclassified 三类结果。Protobuf 生态里 buf 提供了 buf breaking 命令，按照 FILE、PACKAGE、WIRE 等不同级别检查字段编号复用、类型变更和删除。Avro 与 Schema Registry 则在注册新 schema 时直接按配置的兼容性级别拒绝不合格的提交。

工具的价值在于把“破坏性变更”从主观判断变成流水线里的红灯。但工具也有边界：它们不知道 /v1/orders 和 /v2/orders 是同一个业务概念，也不知道 amount 的单位变了。因此合理的分工是工具负责结构与编号，人负责语义与业务影响，两者缺一不可。

四、消费者驱动契约：让调用方定义期望

提供方自测通过、文档也更新了，接口上线却仍然打挂下游，这类事故的根源是验证方向反了：提供方验证的是“我实现了我以为的契约”，而不是“我实现了消费者真正依赖的部分”。消费者驱动契约（Consumer-Driven Contract，CDC）把顺序倒过来，由消费者声明它从提供方那里需要什么，提供方在发布前用这些声明验证自己。

4.1 Pact 的基本流程

Pact 是这一理念最广为人知的实现。消费者在单元测试中启动一个 mock 提供方，写下期望的请求与最小响应，测试运行后生成一份 pact 文件，里面记录交互描述、请求匹配规则和响应中消费者实际用到的字段。这份文件被上传到 Pact Broker，提供方在 CI 中拉取所有消费者发布的契约，回放请求并校验真实响应是否满足期望。

sequenceDiagram
    participant C as 消费者团队
    participant B as Pact Broker
    participant P as 提供方 CI
    C->>C: 运行消费者测试，生成 pact 文件
    C->>B: 发布契约并打上版本标签
    P->>B: 拉取待验证契约
    P->>P: 对真实服务回放请求并校验响应
    P->>B: 发布验证结果
    B-->>C: 展示哪些版本可以安全部署

Pact 的匹配规则有一个重要特点：默认只校验消费者声明过的字段，响应里多出来的字段不算失败。这正是“按需契约”的体现，消费者只对自己用到的部分负责，提供方也就获得了新增字段的自由。如果消费者把某个字段声明为精确匹配，提供方改动该字段的值就会失败，这种写法适合金额这类不允许漂移的值，但不宜全量使用。

4.2 CDC 的适用边界

消费者驱动契约适合“消费者数量有限、关系稳定、双方都愿意维护测试”的场景，比如内部服务之间。它不适合公开 API：你无法要求成千上万的第三方消费者提交契约，这时提供方驱动加版本兼容承诺更现实。它也不能替代端到端测试，契约验证的是报文形状和少量示例值，不验证业务流程、数据状态和性能。比较务实的组合是：内部核心链路用 CDC 防回归，对外接口用 OpenAPI 加兼容性门禁，端到端测试只保留少量关键路径。

还有一个组织前提常被忽略：CDC 要求消费者真的写测试。如果某个团队的消费者测试覆盖率很低，它生成的契约就只覆盖了零星调用，提供方会误以为“全部验证通过”。因此 Pact 的看板要同时展示“哪些消费者已接入”和“契约最后验证时间”，把沉默当作风险而不是安全。

五、版本策略：URL、Header 与并行窗口

兼容性规则解决的是“单个改动能不能做”，版本策略解决的是“不兼容的改动该怎么做”。只要业务在演进，总会出现必须破坏兼容的时刻，比如重构资源模型、统一错误码、替换认证方式。这时需要一条可执行的迁移路径，而不是临时给旧接口打补丁。

5.1 URL 版本与 Header 版本

URL 版本是最常见也最直白的方式，把版本写进路径，例如 /v1/orders 与 /v2/orders。优点是可见、可缓存、可路由，网关和日志天然能区分；缺点是版本号污染了资源标识，同一个订单在不同版本里有两个地址，链接分享和书签都会变得别扭，而且团队容易把版本理解成“目录”，不断开新前缀却从不清理旧前缀。

Header 版本把版本放在 Accept 或自定义头里，例如 Accept: application/vnd.example.order.v2+json。它保持了 URL 的稳定性，更符合内容协商的语义，但调试成本高，浏览器地址栏无法直接访问，缓存和网关规则也要额外配置。

选择哪一种，取决于消费者构成。面向内部服务的接口，URL 版本足够，因为调用方都是代码，改造成本可控。面向外部合作方的开放平台，Header 版本配合内容协商更常见，因为它允许同一个资源地址随客户端能力返回不同表示，也便于按应用维度统计版本使用情况。真正重要的是选定一种并写进规范，最糟的情况是三种方式并存，谁也说不清某个接口到底属于哪个版本。

5.2 并行支持窗口与弃用流程

版本一旦分叉，就产生了维护成本。两个版本并行意味着双份测试、双份监控、双份缺陷修复，因此必须给并行期设定明确的上限。常见做法是按接口的重要程度分级：内部接口并行 1 至 2 个迭代，合作方接口并行 3 至 6 个月，公开 API 可能更长。窗口长度应当写在契约里，而不是等到要下线时才临时通知。

弃用流程可以拆成四步。第一步是宣布，在新版本发布的同时发布弃用公告，写明旧版本的截止日期、迁移指南和联系人。第二步是可观测，在响应头里返回 Deprecation 与 Sunset（RFC 8594 于 2019 年定义了 Sunset 头），并给旧版本的每次调用打上标记，按调用方统计剩余流量。第三步是催促，当某个调用方的流量迟迟不降时，定向联系而不是群发邮件。第四步是下线，先对剩余流量返回明确的错误码和迁移链接，观察一段时间后再关闭路由。

这里要强调一个常被跳过的动作：统计“谁还在调用”。没有调用方维度的数据，弃用公告就只是公告，截止日期到了也只能一再延期。网关的访问日志至少要保留调用方标识、接口版本和调用量三个维度，并按周生成报表，否则治理就失去了依据。

5.3 不要用“永远兼容”掩盖治理缺失

有些团队以“我们从不删字段、从不改接口”为荣，把这当作工程素养的体现。保持兼容当然是好事，但如果它建立在“没人敢动接口”的基础上，那就是另一种失职：字段越堆越多，废弃逻辑永远不敢删，新接入方要在一堆历史包袱里猜哪个字段才是有效的。

健康的做法是把兼容当成默认要求，同时保留“有计划地破坏”的能力。具体来说：日常变更遵守兼容规则；确需破坏时走版本升级；每个版本都有明确的退役时间；退役之后真正删除代码和数据。判断一个团队是否真的在做契约管理，不看它有多少份 OpenAPI 文档，而看它能不能说清楚“当前有几个版本在跑、各自还有谁在用、下一个下线的是哪个”。

六、把契约放进研发流程

规则写在文档里不会自动生效，只有嵌进流程才会。契约管理的流程可以概括为四个卡点：评审时确认变更性质，合并时确认契约与实现一致，发布前确认没有破坏消费者，上线后确认线上行为没有漂移。

6.1 契约评审

契约评审应当发生在编码之前，而不是提测之后。评审的对象是接口设计，不是实现细节，重点看四件事：资源与命名是否符合团队规范，错误码与状态码是否覆盖了失败路径，字段的语义、单位、可空性是否写清楚，这次变更属于兼容还是破坏。评审可以很短，一次会议加一份 diff 就够，但必须有提供方和主要消费者双方在场。

为了提高效率，可以把评审清单固化成模板，让作者在提交前自检。清单里最值得保留的条目是“这次变更会不会让某个现有调用方解析失败”和“新增字段的默认行为是什么”。

6.2 契约仓库与单一可信源

契约文件放在哪里，决定了它会不会腐烂。三种常见做法各有取舍：放在提供方代码仓库里，优点是天然与实现同步，缺点是消费者难以浏览和复用；放在独立的契约仓库里，优点是跨团队可见、便于统一评审和生成文档，缺点是容易与实现脱节；放在网关配置里，优点是直接生效，缺点是表达力有限。

无论选哪种，都要保证“单一可信源”：同一份契约只有一个权威位置，其他地方要么引用它，要么由它生成。文档站点应当从契约文件自动构建，而不是手工维护。如果团队已经采用 spec-first，契约先于代码合并，实现再按契约补齐；如果采用 code-first，则由代码生成契约并提交评审。两种方式都可以，关键是合并请求里必须能看到契约的变化，让评审者有机会说不。

6.3 CI 中的提供者验证与兼容性门禁

CI 是契约治理最有效的执行点。一个典型的流水线包含三个检查：契约语法与规范检查，确保文档能被工具解析、没有未定义的引用；兼容性检查，把当前分支的契约与主干或最近一次发布的版本比对，发现破坏性变更就阻断合并；提供者验证，启动服务并用契约中的示例或 Pact 契约回放请求，确认实现与契约一致。

兼容性检查有一个实践细节：基线选谁。与主干比可以发现本次改动引入的问题，与最近一次线上发布比才能反映用户真正感受到的变化。前者防止误合并，后者防止“主干已经坏了很久却没人发现”。破坏性变更不应该只有“阻断”一种处理，流水线可以要求作者填写变更说明和迁移方案，由负责人批准后放行，这样既保留了控制，也避免了流程被绕过。

6.4 发布前检查与线上契约探测

CI 通过不代表线上一定正确。发布前的最后一道检查是灰度环境验证：用真实流量或录制的流量回放，比对响应结构与契约的差异，差异超过阈值就暂停发布。

上线后的探测则是长期防线。做法是从网关或服务网格采样真实请求与响应，用契约校验器逐条比对，统计不符合契约的比例。这里要注意方向：校验响应时应当允许额外字段，否则任何新增字段都会触发告警；校验请求时则要看是否存在契约里没定义的参数被大量使用，那往往意味着有未登记的调用方。线上探测的目的不是追求零差异，而是尽早发现“文档说一套、线上跑一套”的漂移。

七、组织：契约归谁所有

技术手段之外，契约管理最终是责任分配问题。比较清晰的分工是：提供方拥有契约和向后兼容承诺，负责在变更前评估影响；消费者参与评审，对自己依赖的字段和语义负责；平台或架构团队拥有规范、工具链和门禁，不替业务团队做决定。反模式是设一个委员会集中审批，它既不写代码也不了解业务，审批很快退化为盖章。

变更通知应当分级，而不是群发。兼容性变更进入 changelog 并推送给订阅者即可；破坏性变更必须做影响面分析，从网关日志中找出实际调用方，定向通知到团队负责人，附上迁移方案和截止日期。把这一步接进代码托管平台会更有效：契约改动自动提醒相关团队，评审记录留痕，事后可追溯。

文档与代码同源是另一条底线。契约文件应当是文档站点、SDK、Mock 服务和测试用例的共同来源，任何手工维护的副本都会在两周内过期。度量指标建议只取四个：有契约覆盖的接口比例、被门禁拦截的破坏性变更数、旧版本流量占比、弃用是否按期完成。这些指标用于发现问题，不宜直接考核个人，否则团队会倾向于把变更拆小以规避检查。

小结

契约管理的本质，是把跨团队的接口约定变成可验证、可演进的资产。选对载体只是起点，更重要的是写清兼容规则、为破坏性变更留出版本与弃用通道，并把检查放进 CI 与线上探测。消费者驱动契约适合消费者有限、关系稳定的内部核心链路；公开接口更依赖提供方的兼容承诺与版本治理。最后，契约需要明确的 owner、分级的通知机制和同源的文档，否则再完整的规范也只是墙上的标语。
