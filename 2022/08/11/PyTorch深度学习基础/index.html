PyTorch 深度学习基础

本文面向会写 Python、还没系统用过 PyTorch 的读者，写作时的稳定版本是 1.12（2022 年 6 月发布）。文章沿一条主线展开：先认识张量，再理解自动求导，然后用 nn.Module 封装模型、用 DataLoader 喂数据，最后把训练循环与验证串起来，并说明怎样把计算放到 GPU 上。读完应当能独立写出一个可运行的单文件训练脚本。本文只讲框架基础与训练流程，大语言模型的概念与 LoRA 之类的微调方法留给其他篇目。

张量：带类型与设备的多维数组

张量可以理解成带 dtype 与设备信息的多维数组，用法接近 NumPy 的 ndarray，区别是它能放到 GPU 上计算，也能记录运算过程以便求导。

创建、形状与 dtype

常用创建方式有 torch.tensor（从列表复制并推断类型）、torch.zeros 与 torch.ones、torch.arange、torch.randn。整数字面量推断为 int64，浮点推断为 float32；模型参数几乎都是 float32，手工造的数据若是 int64，矩阵乘法会直接报类型不匹配。

形状看 .shape，元素数看 .numel()。view 只接受内存连续的张量，reshape 在必要时先复制，代价是多占一份内存，日常先用 reshape。

广播、索引与 NumPy 互操作

广播从最后一维向前对齐：每一维相等、或其中一个是 1、或其中一个缺失，就能相加。形状 (4, 3) 与 (3,) 相加，后者按 (1, 3) 扩展成 (4, 3)；写成 v[:, None] 则得到列向量参与运算。广播不真正复制数据，但结果张量会实打实占显存。

索引沿用 NumPy 习惯，a[0]、a[:, 1]、a[1:3]、布尔掩码都能用。切片得到的是视图，改它会改原张量，要独立副本用 .clone()。

与 NumPy 互转靠 tensor.numpy() 与 torch.from_numpy()。CPU 上两者共享内存，改一边另一边也变；带梯度的张量不能直接转 NumPy，必须先 detach。

最后提一个容易混淆的点：以下划线结尾的方法（add_、zero_、clamp_）都是原地操作，会直接修改调用者。原地操作能省内存，但可能破坏反向传播所需的值，报错信息通常提到 modified by an inplace operation。拿不准时用非原地版本，代价只是一次内存分配。

需要复现实验时，用 torch.manual_seed 固定随机种子，同时给 numpy 与 Python 的 random 各设一次，初始化与打乱顺序才能稳定复现。

自动求导：计算图与梯度

训练靠梯度调整参数，梯度来自链式法则。PyTorch 在前向计算时记录运算，形成计算图，调用 backward 时沿图反向求导。

requires_grad 与三个注意点

把张量的 requires_grad 设为 True，它参与的运算就会被记录，结果张量的 grad_fn 指向产生它的函数，顺着 grad_fn 往回就是整张图。自己创建的叶子节点在 backward 之后把梯度累积到 .grad 里。

三点要注意：只有浮点张量能设 requires_grad；梯度是累加的，每轮迭代前必须清零；backward 默认要求输出是标量，输出不是标量时要传入同形状的 gradient 参数，相当于给每个输出指定权重。

下面的例子用 y = 3x + 2 加噪声造数据，参数随机初始化，损失用均方误差，更新直接手写。它把前向、反向、更新三步走通，也是后面所有训练循环的原型。

注意更新放在 torch.no_grad() 里：参数更新本身也是张量运算，不关闭求导会被记进计算图；对叶子张量做原地更新也必须在 no_grad 下，否则会报 in-place 操作的错误。这一小段正是优化器替你做的事，下一节换成官方封装后，循环体只剩三行。

排查梯度问题时，可以打印 w.grad.norm() 看数量级，或在模块上注册 hook 观察中间值。若某个参数的 grad 一直是 None，多半是它没有参与前向，或者被 detach 隔断了。detach 返回共享内存但脱离计算图的张量，常用来把标签、目标值与日志数据从图中摘出来。

用 nn.Module 组织模型

手写参数只适合教学。真实模型要处理初始化、设备迁移、保存加载，nn.Module 把这些杂事收进一套约定：把有参数的层注册为子模块，实现 forward，其余交给框架。

子模块、forward 与参数

继承 nn.Module，在 init 里创建层，它们会被自动登记为子模块；在 forward 里描述计算。调用时写 model(x) 而不是 model.forward(x)，因为 call 里还包着 hook 等机制，绕过去会丢功能。

nn.Linear(in_features, out_features) 内部维护形状为 out×in 的 weight 与 bias。nn.Sequential 按顺序拼接层，适合结构简单的网络。parameters() 递归返回所有需要梯度的参数，named_parameters() 附带名字，分组设置学习率时用得上。

参数初始化默认由各层自己完成。需要自定义时可以用 apply 遍历所有子模块，或对 weight 调用 nn.init 下的函数。初始化不当会让深层网络一开始就出现梯度消失或爆炸，这属于调优话题，本文不展开。

state_dict 的保存与加载

推荐保存 state_dict 而不是整个模型对象：它是参数名到张量的字典，与代码解耦；直接 torch.save(model) 会绑定类定义与目录结构，换环境容易失败。

加载时先按同样结构实例化，再 load_state_dict。默认严格匹配键名，缺键多键都会报错，确需部分加载时用 strict=False，但要确认漏了哪些层。断点续训还要存优化器状态，否则动量和步数会丢。

数据管道：Dataset 与 DataLoader

Dataset 定义一条样本怎么读，DataLoader 定义怎么组批、打乱、并行读取。两者分开之后，数据格式变化时只需换 Dataset，训练循环不用动。

自定义 Dataset

继承 torch.utils.data.Dataset，实现 len 与 getitem。前者返回样本总数，后者按整数索引返回一条样本，通常是张量或张量元组。如果样本来自文件，读取和解析都放在 getitem 里，并在这里做异常兜底，否则一个坏样本会让整轮训练中断。

batch、shuffle 与 num_workers

batch_size 决定一次前向看到多少样本。太小则梯度噪声大、GPU 吃不饱；太大则显存紧张、收敛变慢。常见做法是从 32 或 64 起步，再按显存与收敛情况调整。

shuffle=True 在每个 epoch 开始时重新打乱顺序，训练集必须开；验证集与测试集保持固定顺序，指标才可比较。num_workers 指定读取数据的子进程数，0 表示在主进程里读。进程多一些能减少 GPU 等待，但每个进程都会复制一份数据集对象，内存随之上升。笔记本或容器里设 2 到 4 通常够用，设得过大反而可能因进程调度变慢。

另外两个参数值得记住：drop_last=True 丢弃最后一个不满的批，适合批归一化等对批大小敏感的层；pin_memory=True 把批数据放进锁页内存，配合 GPU 训练时传输更快。DataLoader 默认用 collate_fn 把样本列表堆叠成批张量，样本形状不一致时需要自己实现 collate 逻辑。

一个 epoch 表示把训练集完整过一遍，迭代次数约等于样本数除以 batch_size。数据量小的时候，用 step 计数比用 epoch 更直观；打日志时同时记录损失与学习率，排查问题时很方便。汇总指标时按样本数加权，而不是对各批的损失取简单平均，否则最后一个不满批会被高估。

训练循环：损失、优化器与验证

一个 epoch 的循环固定为四步：取一个批、前向算损失、反向求梯度、优化器更新；结束后切到评估模式，在验证集上再跑一遍。

flowchart TD
    A[遍历 epoch] --> B[取一个 batch]
    B --> C[训练模式前向]
    C --> D[计算 loss]
    D --> E[loss backward]
    E --> F[optimizer step]
    F --> G[optimizer zero_grad]
    G --> H{还有 batch}
    H -- 是 --> B
    H -- 否 --> I[评估模式验证]
    I --> J[记录 train 与 val 指标]
    J --> A

循环里各步的顺序不能颠倒：zero_grad 要放在 backward 之前，或紧跟在 step 之后，绝不能夹在 backward 与 step 中间，否则刚算出的梯度就被清掉了。

损失与优化器的选择

回归用 nn.MSELoss；二分类用 nn.BCEWithLogitsLoss，它内部含 sigmoid，比先 sigmoid 再 BCELoss 数值稳定；多分类用 nn.CrossEntropyLoss，输入是未归一化的 logits，不要再手动 softmax。这三处是最常踩的坑。

优化器都在 torch.optim 下。SGD 简单，配合 momentum 与 weight_decay 是经典组合，泛化往往不错；Adam 对学习率不敏感，适合快速起步，常用学习率是 1e-3。优化器在构造时绑定参数，之后新增的参数不会自动纳入，改动模型结构后要重建优化器。

学习率也不必固定。torch.optim.lr_scheduler 提供 StepLR、CosineAnnealingLR 等调度器，每个 epoch 调用一次 scheduler.step()，让学习率按计划衰减，后期收敛通常更稳。梯度偶尔会突然变大，用 torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0) 按范数裁剪，是训练不稳定时最先尝试的手段之一。

train 与 eval 的区别

model.train() 与 model.eval() 影响 Dropout 与 BatchNorm 的行为。训练时 Dropout 随机置零、BatchNorm 使用批统计量；评估时 Dropout 关闭、BatchNorm 使用滑动平均。忘记切 eval，验证指标会抖动且偏低；忘记切回 train，下一轮训练等于没开 Dropout。

这两个调用不影响梯度是否记录，所以验证时通常还要套一层 torch.no_grad()，既省显存也避免意外建图。下面是把数据、模型、优化器与验证拼起来的完整循环。

过拟合的初步判断

把每个 epoch 的训练损失与验证损失记下来，画在同一张图上，是最直接的判断方法。训练损失持续下降，而验证损失在某个点之后回升，说明模型开始记住训练集的噪声，这是过拟合的典型形状。两者都高且下降缓慢，则是欠拟合，应该加大模型或延长训练。验证损失抖动明显时，先检查是否忘了 eval、学习率是否过大、批大小是否太小。

初步的应对手段按成本从低到高排列：增加数据或做数据增强、加 Dropout 与权重衰减、早停（验证损失连续若干轮不降时停止，并回滚到最佳权重）。调参时一次只改一个变量，否则无法判断收益究竟来自哪里。

工程上通常还会在验证损失创新低时保存一份权重，训练结束后加载表现最好的那一份，而不是最后一轮的权重。这份最佳模型与早停配合，能避免训练末期的过拟合把前面的成果覆盖掉。

把模型放到 GPU 上

GPU 擅长并行矩阵运算。迁移的写法很简单，坑却集中在设备一致性与显存两方面。

.to(device) 与设备一致性

标准做法是在脚本开头算一次 device，模型与每个批都 .to(device)。模型迁移是原地修改并返回自身；张量迁移默认返回新张量，所以必须接住返回值。只写 x.to(device) 而不赋值，是最常见的“看起来迁了其实没迁”。

报错 Expected all tensors to be on the same device 几乎都源于某个张量漏迁。容易漏的地方包括手工构造的标签、mask、位置编码，以及损失函数里的常量张量。养成习惯：凡是 forward 里新建的张量，都用 x.new_zeros(…) 或显式传 device=x.device。

另外，CPU 与 GPU 之间的数据传输要走总线，频繁来回很慢。评估时先把整个验证集算完，再取回少量标量；在每个批上调用 .item() 会强制同步，让 GPU 停下来等 CPU。

显存：先学会看数字

显存由几部分组成：模型参数、梯度、优化器状态、每层的中间激活，以及临时缓冲。Adam 会为每个参数额外保存一阶与二阶动量，所以优化器状态通常是参数量的两倍；训练峰值又远高于推理，因为激活要保留到反向传播用完。

torch.cuda.memory_allocated() 返回当前张量占用的字节数，torch.cuda.max_memory_allocated() 返回峰值，两者对比可以判断是否存在泄漏。遇到 out of memory，先减小 batch_size，再考虑梯度累积（多个小批累加梯度后更新一次，近似等效于大批），最后才动模型结构。del 掉不用的张量并调用 torch.cuda.empty_cache() 只能回收缓存，不能解决根本问题。

还要区分两类报错：显存不足是运行时的资源问题，减小批大小通常有效；device-side assert 多半是索引越界或标签超出类别数，属于数据或代码错误，改批大小没有用。

混合精度训练在 1.12 已经可用，入口是 torch.cuda.amp 下的 autocast 与 GradScaler，能降低显存占用并提速。它涉及 loss scaling 与算子精度取舍，本文只指出它的位置，具体用法不展开。

小结

本文沿着一条最小闭环走完了 PyTorch 的基础：张量负责数据表示，dtype 与 device 决定它能参与什么运算；自动求导把链式法则交给计算图，backward 之前记得清零梯度；nn.Module 把参数、前向与保存加载收进统一约定，state_dict 是推荐的持久化格式；Dataset 与 DataLoader 把读取和组批解耦；训练循环固定为前向、损失、反向、更新四步，验证时切到 eval 并关闭求导。上 GPU 只需一次设备判断，但要盯住设备一致性与显存峰值。

建议的练习路径是：先把本文的手写线性回归跑通，再换成 nn.Linear 与 Adam，然后加一层隐藏单元和验证集，观察训练损失与验证损失何时分离。这条链路走熟之后，再去看微调与推理优化的文章，就不会卡在 API 细节上。
