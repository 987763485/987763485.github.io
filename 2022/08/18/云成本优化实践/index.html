云成本优化实践

本文属于《Docker 与 Kubernetes》第 47/51 篇
上一篇系列目录下一篇

云账单每个月都在涨，但很少有人能说清钱具体花在了哪个团队、哪个业务上。本文从成本可见性讲起，依次讨论计算、存储、网络与弹性四个层面的常见浪费，最后给出一条可执行的优化顺序和一套组织机制。文章面向使用公有云与 Kubernetes、希望把成本管起来的工程师与团队负责人，读完可以搭起从账单到行动的闭环。

一、先看见，再优化：标签、分摊与单位成本

云成本的第一道难题往往不是贵，而是不透明。账单按资源 ID、区域和计费项组织，工程团队却按服务、环境和业务线思考，两者之间缺少映射。看不见归属，优化就会变成拍脑袋砍预算。

标签是账单与组织之间的桥

标签（云平台叫 tag，Kubernetes 叫 label）是建立映射最直接的手段。本文建议只保留少量稳定维度：团队、应用、环境、成本中心、负责人。维度太多，维护成本会超过收益；也不要拿请求 ID 这类高基数信息做标签，它会污染报表且难以聚合。

标签本身不会自动生效，需要配合强制手段。Kubernetes 可以用准入控制拒绝缺少关键标签的工作负载，云资源可用标签策略在创建时校验。历史资源先盘点补齐，再谈优化。仍然缺标签的部分单独列为“未分摊”，每月在成本例会上公示，让归属方主动认领。

共享成本怎么摊

直接成本按标签归属即可，真正棘手的是共享成本：控制面、监控、日志、镜像仓库、NAT 网关、入口负载均衡，这些资源服务所有人，却很难精确切分。常见做法是按比例分摊，例如按各团队的 CPU requests 占比，或按入口流量占比。规则不必追求会计级精确，但必须写下来、周期固定、口径稳定，并且能向被分摊方解释清楚。规则频繁变动会摧毁信任。

从绝对金额转向单位成本

总账单随业务增长很正常，只盯绝对金额容易得出错误结论。更有意义的指标是单位成本，例如每千次请求的成本、每个活跃租户的成本、每万元交易额对应的基础设施开销。单位成本上升，说明效率在恶化；单位成本下降，说明增长是健康的。本文建议至少定义一个与业务强相关的单位指标，并把它和账单放在同一张报表里看。

工具方面，云厂商的成本分析页面与 Kubecost 这类开源方案都能完成聚合。起步阶段不必追求大而全，一张按团队与应用聚合的日报就够用。

二、计算成本：requests、limits 与装箱率

计算资源通常是账单里最大的一块，也是最容易被“多申请一点更保险”这种心态撑大的一块。

requests 决定调度，limits 决定上限

requests 是调度依据，告诉调度器“这个 Pod 至少要这么多资源”；limits 是运行时上限，超过 CPU limit 会被节流，超过内存 limit 会被杀死。CPU 属于可压缩资源，短时超用只是变慢；内存不可压缩，超限就是 OOMKill。

常见反模式有三类。第一类是全公司统一填“1 核 2G”，导致小服务超配、大服务不够用。第二类是 requests 小、limits 大，节点被超卖，高峰时互相争抢，延迟抖动找不到原因。第三类是 requests 远高于真实用量，调度器以为节点已满，集群不断扩容，账单虚高而实际 CPU 大量空闲。

比较稳妥的做法是从监控出发：观察容器实际用量的 P95 与 P99，CPU requests 取接近 P95 的值，内存 requests 取接近 P99 并留出约两成余量（比例为示意，需按业务调整）。新服务没有历史数据时，可以先用 VPA 的推荐值起步，运行一到两周后再固化。

关键服务建议把 requests 与 limits 设为相等，进入 Guaranteed 服务质量等级，避免节点资源紧张时被优先驱逐；离线任务可以放宽，用较低的 requests 提高装箱率。

装箱率要看两层

装箱率通常指节点可分配资源中被 requests 占用的比例。这个指标要分两层看：requests 装箱率高，说明调度层面没有明显浪费；但真实利用率才决定账单是否合理。如果 requests 装箱率是七成，而实际 CPU 利用率只有一成（均为示意），问题不在调度，而在 requests 定得过高。两者一起看，才能判断该右 sizing 还是该扩容。

节点规格同样影响效率。规格太少，大 Pod 找不到合适落点；规格太多，每种规格都留下用不满的节点，形成碎片。本文建议为每个集群保留两到三种规格族，例如通用型与大内存型，并让同类负载集中，减少“每个节点剩一点”的局面。DaemonSet 与系统组件占用的资源也要计入，否则装箱率会被高估。

自动伸缩与 VPA 的边界

集群自动伸缩负责节点数量：有 Pod 因资源不足无法调度时扩容，节点长期低利用且 Pod 可迁移时缩容。扩容不是瞬时完成的，从创建节点到镜像拉取完成可能几分钟，对突发流量要预留缓冲，或者用低优先级的占位 Pod 提前保住容量。缩容则要尊重 PodDisruptionBudget，避免一次带走太多副本。

VPA 的定位是“给出建议并调整 Pod 资源”，它观察历史用量并产出推荐值，也能在自动模式下重建 Pod 应用新值。本文更推荐先用它的推荐功能做右 sizing，把结果人工 review 后写进清单；直接开启自动更新，对有状态服务、长连接服务和启动缓慢的服务都不友好。还要注意 VPA 与基于 CPU 的 HPA 不要同时作用在同一负载上，否则两者会互相追逐。

三、存储与网络：最容易被忽略的账单

存储和网络在账单中的占比通常小于计算，但浪费往往更隐蔽，因为它们不会表现为“服务变慢”，只会安静地按月计费。

闲置卷、快照与存储分层

动态存储供给降低了使用门槛，也制造了大量孤儿卷。应用删除时，PVC 可能因为回收策略被保留；开发环境为了“下次还要用”，长期挂着大容量卷。治理办法并不复杂：给 PVC 打上归属标签，定期扫描未被任何 Pod 挂载的卷，对开发与测试环境设置生命周期，到期先快照再删除。

快照按增量存储，听起来便宜，但保留策略失控后同样可观。更重要的是，快照不等于备份，真正需要确认的是能否在规定时间内恢复。本文建议快照保留期分档，日快照保留数天、周快照数周，跨区复制只留给核心数据，因为复制本身也产生流量与存储费用。

存储类型也要分层：高 IOPS 块存储留给数据库与低延迟服务，日志、备份与冷数据放对象存储即可。

跨区流量、NAT 与负载均衡

多可用区部署提升了可用性，但跨区调用会产生数据传输费用。服务间调用、数据库主从复制、缓存同步都可能跨区。可以用拓扑感知的服务路由，让流量优先留在同一可用区，同时保留故障切换能力。跨区复制要区分“必须实时”和“可以异步”，前者才值得持续付费。

NAT 网关通常按运行时长加处理流量计费，规模上来后费用不小。镜像拉取、日志外发、调用公网 API 都会经过它。访问对象存储、镜像仓库这类同云服务时，尽量走 VPC 终端节点，避免绕行 NAT；大流量任务单独规划出口，也能减少处理费。

负载均衡按实例时长与容量计费。每个类型为 LoadBalancer 的 Service 都会创建一个云负载均衡，测试环境里几个遗忘的服务就能长期产生费用。入口应尽量收敛到统一的 Ingress 网关，内部服务用 ClusterIP，只有确需公网暴露的才单独开负载均衡。日志与监控也有隐性成本：日志长期热存、指标高基数标签，费用可能超过被观测的计算资源，保留期与采样策略应与成本一起评审。

四、弹性：竞价实例与定时伸缩

弹性用不好，会同时带来账单与稳定性负担。

竞价实例与抢占式实例以大幅低于按量价格的方式出售空闲容量，代价是可能被云平台提前回收。它们适合无状态、可中断、启动快的负载，例如 CI 构建、批处理、渲染、离线推理和压测；不适合数据库、有状态中间件和长事务。使用时要做好三件事：在多种规格与可用区之间分散，降低同时被回收的概率；监听中断通知，收到后停止接新任务、保存检查点、优雅退出；关键服务保留按量实例作基线，竞价只承担增量，避免全部副本同时消失。

定时伸缩适合波峰可预测的场景，比如工作日白天流量高、夜间低，或每天固定时段跑报表。定时规则提前扩容，比等指标触发更能覆盖启动延迟；同时要注意时区、节假日和促销日，必要时用一次性规则覆盖。可预测的部分交给定时伸缩，不可预测的部分交给基于指标的伸缩，两者配合才完整。

所有这些的前提是无状态化。会话放在外部存储，本地缓存允许丢失，启动与就绪探测足够快，副本可以随时被替换。没有这个前提，弹性伸缩只会把故障放大：新副本起不来，旧副本又被缩掉。

五、优化顺序：从确定性最高的地方开始

成本优化最容易犯的错误是一上来就讨论架构改造。本文建议按“确定性从高到低、改造量从小到大”的顺序推进，每一步都先量化收益再动手。

手段 主要收益 风险与前提
清理闲置资源 账单立即下降 需确认无流量，先停用观察再删除
右 sizing 消除长期超配 依赖监控数据，压得过低会伤稳定性
提高装箱率 减少节点数量 注意碎片与大 Pod 的落点
竞价实例 降低单位算力成本 负载可中断，需分散与优雅退出
定时伸缩 匹配可预测波峰 注意时区、节假日与扩容延迟
缓存与批处理 减少重复计算 一致性与复杂度上升

清理闲置是唯一几乎无风险的步骤：无人挂载的卷、没有流量的负载均衡、长期空闲的测试集群、过期快照，先停用一周观察，再删除。右 sizing 需要监控支撑，通常收益最大也最可控。装箱率优化涉及调度与节点规格，需要与平台团队协作。弹性与架构级优化收益更大，但改造周期长、回归成本高，应放在后面。

六、组织：让成本成为持续的习惯

成本问题很少是纯技术问题。如果没有稳定的机制，一次集中治理之后，资源会在半年内重新长回来。

考核指标要选对：用单位成本与预算执行率，而不是“今年必须省下多少万”。后者容易把压力简单传导为压缩资源：该留的副本被砍掉，该做的压测被跳过，最后用一次故障赔掉多年的节省。成本应该是设计时的约束，而不是年底的运动。

预算告警要落到人。按账号、项目或 namespace 设置预算，在消耗到五成、八成、十成时分级告警，接收人写资源 owner，而不是只发给财务。月度复盘保持固定议程：看单位成本趋势、看异常波动、看排名前几的变化项、确认下月动作。先做 showback，让团队看见自己的花费，再考虑 chargeback。平台团队应提供合理的默认值、模板与报表，让“做对”比“多申请”更容易。

小结

云成本优化的起点是可见性：没有标签与分摊，就没有真正的优化对象。在此基础上，用单位成本衡量效率，依次推进清理闲置、右 sizing、提高装箱率、弹性伸缩与架构级改造。计算侧看 requests 与真实用量的差距，存储与网络侧看不会让服务变慢的隐性计费项。最后把成本放进预算、告警与月度复盘的节奏，用机制代替运动，成果才留得住。
