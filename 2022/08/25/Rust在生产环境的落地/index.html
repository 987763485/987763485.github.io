Rust 在生产环境的落地

本文属于《Rust 学习路线》第 64/68 篇
上一篇系列目录下一篇

把一个已经在线上跑了两年、每天处理数百万请求的 Go 或 Python 服务改成 Rust，听起来像一次技术冒险，做起来更像一次外科手术：语言只占其中一小部分，剩下的工作分布在运行时、日志、错误语义、构建产物和团队协作上。本文假设读者已经能写基本的 Rust 代码，也了解所有权与借用的基本规则，因此不再讲语法，而是按“一个服务从改写、上线到可运维”的顺序，把每一步会遇到的真实选择摊开讲。读完之后，你应该能判断自己的哪个服务适合迁移、迁移时先动哪一块，以及哪些坑可以提前绕开。

先把账算清：什么服务值得换

讨论技术细节之前，先要承认一个事实：绝大多数服务用 Go 或 Python 写得挺好，换成 Rust 并不会让业务变得更好。真正值得考虑的，通常是那些“机器成本或延迟尾部已经成为问题，而业务逻辑相对稳定”的组件。笔者见过两类典型候选：一是用 Go 写的规则匹配服务，单实例 CPU 长期跑在 70% 以上，GC 虽然已经很优秀，但在 P99 上仍会留下周期性毛刺；二是用 Python 写的日志清洗与字段提取服务，靠多进程堆机器，单机内存占用随并发线性上涨。这两类服务的共同点是计算密集、输入输出格式固定、对延迟敏感，正好落在 Rust 的舒适区。

反过来，有三类服务不建议动。第一类是典型的 CRUD 后台，时间几乎都花在等数据库上，换语言只是把 await 换成 .await，收益接近于零。第二类是业务规则每天变、依赖大量第三方 SDK 的服务，Rust 生态在支付、短信、云厂商 SDK 上的覆盖仍不如 Go 和 Python，缺一个库就可能拖住整个排期。第三类是团队只有两三个人、同时背着交付压力的项目，语言迁移的隐性成本会在最不该出问题的时候爆发。

即便确定要换，也不等于重写。比较稳妥的做法是先做性能剖析，找出真正的热点，只把那一段换成 Rust，其余部分维持原样。一个日处理千万级请求的网关，热点往往集中在协议解析、路由匹配和序列化这三处，把这三块抽出来做成库，收益就能拿到大半，而风险被限制在一个可以回滚的边界内。

还需要提前说明期望值。网上常见的“快十倍”说法多半来自微基准，真实服务里数据库、网络和锁竞争会把差距抹平。真实收益通常集中在计算密集的局部，端到端延迟的改善要小得多，具体幅度因负载而异，本文不给出统一比例。把预期定在“同等机器少一半、P99 毛刺消失”，比定在“全面提速”更接近现实，也更容易在迁移后向团队交代。

运行时选型：同步、异步与 tokio 的两种执行器

先回答要不要 async

Rust 的 async 常被描述为零成本抽象，但“零成本”指的是没有垃圾回收和运行时调度开销，不是没有认知成本。同步模型写起来最像传统服务：一个线程池加阻塞 IO，请求进来取一个线程，处理完归还。它的好处是调用栈直白、绝大多数库都提供阻塞 API、单个请求 panic 只影响那个线程。代价是并发上限由线程数决定，每个线程默认保留 2 MiB 的虚拟栈空间，连接数上万后上下文切换和内存都会变得难看。

判断标准可以归纳为三条：并发连接是在几百还是几万这个量级；单个请求里等待 IO 的时间占比是否远高于计算；是否需要在一个连接上做多路复用，例如 HTTP/2 或 gRPC 流式调用。前两条偏向同步，第三条基本只能选 async。很多团队的真实场景是“几千连接、逻辑简单”，这种规模用同步模型完全够用，硬上 async 反而让每个新人都要重新理解一遍 Future 的惰性。

multi-thread 与 current-thread

决定用 tokio 之后，第一个要选的不是版本而是执行器形态。#[tokio::main] 默认等价于多线程运行时，工作线程数等于 CPU 核数，任务可以在任意工作线程上被唤醒和继续执行。这个“可以迁移”的性质带来一个重要约束：交给 tokio::spawn 的 future 必须是 Send。生产中最常见的编译错误，就是在 await 前后持有了 std::sync::MutexGuard——标准库的锁守卫不是 Send，编译器会直接拒绝。这不是刁难，而是把数据竞争提前到了编译期。解决方式有两种：缩短锁的作用域，让守卫在 await 前释放；或改用 tokio::sync::Mutex，但要清楚它开销更高，也容易掩盖设计问题。

单线程运行时（flavor = "current-thread"）并不是“低配版”。它适合三类场景：CPU 密集且任务粒度细的 shard，避免任务在核间迁移破坏缓存局部性；需要与 !Send 的库打交道；以及每个 CPU 核各起一个 runtime、配合 SO_REUSEPORT 让内核做连接的场景。此时没有工作窃取，一个慢任务会直接堵住整个 runtime，因此对阻塞的容忍度比多线程更低。

容器里 nproc 常报告宿主机核数，而 CPU limit 可能只有两个核，按 nproc 开会造成线程争抢与调度抖动。上线前应读取 cgroup 配额，或把该值做成配置项。

一个阻塞调用如何拖垮整个 runtime

async 运行时只在 await 点让出线程。如果一段同步计算耗时 20 毫秒，却被放进 async fn 里直接执行，它就会实打实占住一个工作线程 20 毫秒。假设服务每秒处理 500 个这样的请求，而机器只有 4 个 worker，那么仅这一项就吃掉 10 个核·秒/秒的算力——这只是示意数字，但它说明饱和是如何发生的。更隐蔽的是后果：负责推进定时器和 IO 事件的工作线程被占满后，健康检查开始超时、Prometheus 抓取失败、日志时间戳出现跳跃，而 CPU 使用率看起来还没到 100%，排查方向很容易跑偏。

识别这类问题有两个手段。一是观察延迟分布的形状：计算阻塞往往表现为所有接口一起变慢，包括那些不访问数据库的接口。二是使用 tokio-console，它能列出每个任务的轮询耗时，长时间不让出的任务会非常显眼。退一步，也可以在 handler 入口和出口各打一条日志，用耗时字段做粗粒度的定位。

可观测性：让新服务像老服务一样可排查

span 是上下文，event 是日志

tracing 与传统的 log 最大区别在于它区分了两种东西：event 表示“此刻发生了一件事”，span 表示“一段时间内处于某个上下文”。这个区分对排查分布式问题很关键：请求上下文可以跨函数、跨任务传递，而日志行只是孤立字符串。

skip 不是可选项而是纪律。把整个请求体塞进 span 字段，会让日志体积和敏感信息同时失控；把连接池、客户端这类大结构体放进字段，则会让每次创建 span 都付出格式化代价。团队应当约定：span 字段只放低基数、可检索的标识，例如请求 ID、路由模板、用户分群，而不是用户 ID 或原始 URL。

错误处理：库用 thiserror，应用用 anyhow

Rust 的错误处理语法本身不难，难的是划边界。一个常见的坏味道是：底层库把错误统统装箱成 Box<dyn Error>，上层应用再把它转成字符串，于是调用方既无法区分“键不存在”和“磁盘满了”，也拿不到原始错误链。生产系统里，错误类型决定了重试策略、告警级别和 HTTP 状态码，它属于接口设计的一部分。

比较通行的分工是：库和对外 crate 定义具体的错误枚举，用 thiserror 生成 Display 与 Error 实现；应用层（二进制 crate）用 anyhow 聚合，沿途补充上下文。前者让调用方可以 match，后者让排障信息完整，两者并不冲突。

这个枚举可以直接作为库的公开 API，因为每个变体都携带了结构化信息，调用方可以据此决定返回 404 还是 500，也可以判断是否值得重试。#[from] 只是省去了手写转换，真正重要的是变体的粒度：把 IO 错误和格式错误分开，比统一叫 Internal 有用得多。

几条不吞错的纪律值得写进评审清单。第一，禁止 let _ = result; 和空的 if let Ok(_)，确实要忽略时必须写明理由，比如“关闭时的错误无法补救”。第二，不要在每一层都 error! 一次再往上抛，那样同一个错误会产生五六条日志，正确做法是在最终处理错误的地方记录一次，中间层只加 context。第三，错误信息里不要拼接密码、令牌和完整的请求体，Debug 输出结构体时尤其容易泄露。第四，面向客户端的响应只给错误码和请求 ID，细节留在服务端日志里，靠 ID 关联。

FFI 与渐进迁移：先把 Rust 做成库

一次性的整体重写风险极高，尤其当旧服务还在承载全部流量时。更现实的路径是让 Rust 先以库的形态进入现有进程，用真实流量验证正确性与性能，再决定是否独立成服务。

flowchart TD
    A[现有 Go 或 Python 服务] --> B[剖析并锁定热点模块]
    B --> C[用 Rust 重写为 crate]
    C --> D[导出 C ABI 的 cdylib]
    D --> E[原服务通过 FFI 调用]
    E --> F[影子流量比对与灰度]
    F --> G{输出一致且指标稳定}
    G -->|是| H[扩大流量或拆为独立服务]
    G -->|否| C

为什么从 cdylib 开始

在 Cargo.toml 里声明 crate-type = ["cdylib", "rlib"]，同一个 crate 既能产出动态库供外部调用，又能保留 rlib 让 Rust 侧的单元测试正常运行。Go 通过 cgo 调用，Python 通过 ctypes 或 cffi 调用，接入成本通常只有几十行胶水代码。

这种方式的优点是边界清晰、可回滚：动态库加载失败或结果异常，旧服务可以立刻切回原实现。缺点是引入了进程内耦合，.so 升级必须与应用一起发布，跨语言调试也更麻烦。因此它适合“热点明确、接口窄”的模块，比如协议解析、规则编译，而不适合把半个业务逻辑塞进去。

调用开销要提前评估。一次跨界调用约在微秒量级（示意值），如果原逻辑每请求调用上万次细粒度函数，逐次跨界会吃掉全部收益。正确做法是设计批量接口：一次传入数组、一次取回结果，把跨界次数压到常数级。

C ABI 边界上的四条规则

第一条，只导出 C ABI 的类型。#[no_mangle] pub extern "C" 的函数签名里不应出现 String、Vec、Result、泛型和 trait 对象，这些类型的布局不保证稳定，跨编译器版本使用属于未定义行为。字符串用指针加长度表示，结构体用不透明指针加访问函数。

第二条，内存谁分配谁释放。Rust 分配的 CString 必须回到 Rust 释放，因此每个返回堆内存的函数都要配一个对应的释放函数。调用方用 free() 去释放 Rust 的分配器内存，是这类集成里最经典的崩溃原因。

第三条，panic 绝不能跨过边界。在 2022 年的规则下，panic 展开越过 extern "C" 边界是未定义行为，编译器不会阻止，运行时也不会给出友好提示。因此每个导出函数的第一件事就是用 catch_unwind 兜住，把 panic 转成错误码。

第四条，unsafe 只出现在边界，并且必须写清前提。指针是否可能为空、长度是否与缓冲区匹配、调用方是否保证内存在调用期间有效，这些都要以 // SAFETY: 注释的形式写在 unsafe 块的紧邻位置，评审时逐条核对。

错误码的设计要留出类别：0 表示成功，负数按“输入错误、内部错误、资源不足”分段，具体信息通过 set_last_error 写入线程局部缓冲区，由调用方紧接着取走。不要把错误信息拼进返回值，也不要依赖全局可变状态跨线程读取。

用影子流量验证，而不是靠单元测试

库的单元测试只能证明“给定输入得到预期输出”，证明不了“替换后线上行为一致”。可行的验证方式是影子流量：把同一批请求同时送给旧实现和新库，比对输出与耗时，差异记录下来人工判定。初期只比对不生效，差异率降到可接受范围后再放量。这个过程中要特别关注边界输入：空字符串、超长字段、非法编码、极端数值，这些正是两套实现最容易分叉的地方。

当模块稳定、调用方增多之后，再考虑把它拆成独立服务。拆分的信号通常是：多个语言的服务都要用、需要独立扩缩容、或者库的版本升级已经开始拖累发布节奏。此时 FFI 阶段积累的测试与对账数据，会直接变成新服务的验收基线。

构建与发布：从 cargo build 到可交付镜像

release profile 的取舍

默认的 release profile 已经能用于生产，但要让产物更小、更快，通常需要显式配置：

lto = "fat" 加 codegen-units = 1 是常见的组合，代价是编译时间可能从两三分钟涨到十几分钟（示意）。对小团队来说，这个代价直接影响迭代速度，折中方案是只在发布流水线启用，日常开发用默认配置。strip 与 debug = 1 并不矛盾：前者去掉完整调试信息，后者保留行号，线上回溯依然能指到源码行。

panic = "abort" 需要单独讨论。它能让产物更小、少一层展开机制，但代价是所有 catch_unwind 失效，一个请求的 panic 会直接终止进程，tokio 任务级的隔离也不复存在。对 CLI 工具这是合理选择，对长期运行的服务则要慎重：宁可多几百 KB，也要保留“坏请求不拖垮进程”的能力。如果编排系统可靠、重启足够快，选择 abort 换取更小的镜像也说得通，关键是写进设计文档，而不是随手抄配置。

另一条路是动态链接 glibc，此时要理解兼容方向：在旧 glibc 上构建的二进制可以在新系统上运行，反过来不行。在 Ubuntu 22.04 上编译的产物，丢到 CentOS 7 上会报 GLIBC_2.34 not found。解决办法有三种：在目标发行版的基础镜像里构建；用 manylinux 这类老基线容器；或者干脆走 musl 静态链接。团队应当把这条规则写进 CI，避免有人本地构建后直接拷贝上线。

镜像体积与运行环境

多阶段构建能把编译工具链留在构建阶段，运行镜像只保留二进制和必要的运行时文件：

构建镜像通常在 1 GB 以上，运行镜像可以做到几十 MB（示意值），既节省拉取时间也缩小攻击面。使用 scratch 时记得补 CA 证书与时区数据，否则最常见的故障是“本地正常、线上 HTTPS 全部失败”；USER 10001 则保证进程不以 root 运行。

发布环节还有两件小事值得做。一是把版本号与构建时的 git 提交号编进二进制，通过 /version 暴露出来，排查时不用猜镜像是哪次提交。二是接受“二进制不能热更新”这个事实：发布只能靠滚动重启，因此启动预热、优雅停机和就绪探针必须做扎实，收到终止信号后先停止接收新请求，再等待在途请求结束。

团队落地：规范、评审与成本

学习曲线的真实形状

有 C++ 或 Go 背景的工程师，通常一两周能写出编译通过的代码，一到三个月能独立负责模块（示意，因人而异）。最难受的阶段不是所有权本身，而是它带来的设计返工：原本打算共享的可变状态，在 Rust 里必须重新划分归属，这会倒逼出更清晰的模块边界，但过程确实慢。团队应当接受这个前期投入，不要用“第一周产出”去衡量迁移成败。

降低曲线的方式有几个。让第一个人先完整踩一遍坑，把常见编译错误的处理方式写成内部笔记；用新模块而不是核心交易链路做练手项目；代码评审时优先讨论所有权设计，而不是格式细节。

评审清单与 unsafe 规范

Rust 编译器能挡住内存安全问题，挡不住业务逻辑和运维问题。建议把以下几条固化成评审清单：业务代码禁止 unwrap 与 expect，除非在启动阶段且失败即应退出；禁止空的错误分支；handler 内禁止同步阻塞调用；跨 await 不得持有 std::sync 的锁守卫；新增依赖必须说明用途与体积影响。

unsafe 的管理应当更严格。业务 crate 可以在文件头写 #![forbid(unsafe_code)]，把不安全代码集中到少数边界 crate 中；允许使用 unsafe 的地方，每处都要有 // SAFETY: 注释，说明指针来源、生命周期与对齐假设，并配套测试。FFI 边界还应在 CI 中跑 sanitizer 构建，能提前发现一部分未定义行为。评审 unsafe 代码时，问的第一个问题不是“能不能跑通”，而是“如果调用方违约会发生什么”。

依赖审计

Rust 的依赖树很容易变深，一个 Web 服务引入上百个 crate 是常态。可用的工具已经比较成熟：cargo audit 对照 RustSec 公告库检查已知漏洞，cargo deny 做许可证白名单、重复依赖与来源审查，两者都适合放进 CI 作为门禁。Cargo.lock 应当入库，保证构建可复现；升级依赖要走独立分支并跑完整测试，而不是顺手在功能分支里 cargo update。

供应链风险也值得关注：过程宏在编译期执行任意代码，来源不明的 crate 等于把构建机交出去。团队应约定只使用维护活跃、下载量足够的库，对新增依赖做一次人工过目，必要时用 cargo vendor 锁定源码。

招聘、维护与不该用的场景

招聘是最容易被低估的成本。Rust 候选人池明显小于 Go 和 Java，招到人后还要几个月才能形成生产力；核心作者一旦离职，留下的代码可能没人敢改。维护成本则体现在版本节奏上：stable 每六周发一版，依赖升级、edition 迁移、clippy 新规则都要持续投入，放着不管，工具链很快会落后一年。

因此有些场景明确不值得用 Rust。以增删改查为主、时间花在数据库上的后台服务，收益接近于零；强依赖某家云厂商 SDK 或支付 SDK 的业务，缺库会直接卡住进度；需要快速试错、一周一个版本的产品，编译时间和开发速度都是负担；只有两三个人的团队同时维护多条业务线时，引入 Rust 等于给自己增加一个长期负债。判断方法很朴素：把机器成本、延迟收益、人力成本、招聘风险四项写成一张表，如果收益项无法在一年内覆盖成本项，就不要启动。

真正适合的，通常是基础设施里那些“逻辑稳定、性能敏感、生命周期长”的组件：代理与网关、协议解析、规则引擎、数据管道、CLI 工具。它们一旦写好，几年内只需要少量维护，Rust 的确定性收益才能持续兑现。

小结

把服务迁到 Rust，难点很少在语法，而在运行时、可观测性、错误语义、跨语言边界和交付流水线这五件事上。本文建议的顺序是：先用剖析数据证明值得换，再以 FFI 动态库的形式低风险接入，验证一致后再考虑独立成服务；运行时选择与团队心智模型匹配的形态，异步服务则严守“不阻塞”的纪律；日志、指标与 panic 上报要在第一个版本就位，错误类型从一开始就划清库与应用的边界。最后，把编译时间、招聘难度和维护成本算进决策，承认有些场景确实不该用 Rust，这不是保守，而是对工程负责。
