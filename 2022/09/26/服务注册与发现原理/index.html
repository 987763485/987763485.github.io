服务注册与发现原理

本文属于《Go 微服务架构》第 13/35 篇
上一篇系列目录下一篇

微服务架构把单体拆成许多进程，调用关系从方法调用变成了网络请求。网络请求必须知道对方的地址，而地址在容器化和弹性伸缩的环境里几乎每天都在变。注册中心就是用来回答“现在有哪些实例、它们在哪里、还能不能用”的基础设施。本文从机制与语义出发，讲清楚注册、发现、一致性、健康检查这几件事，以及它们在真实故障中的表现。

为什么需要注册中心

在没有注册中心的年代，服务地址通常写在配置文件里。这种做法在物理机时代勉强可行：机器数量少、变更慢、IP 相对稳定。但一旦引入容器与自动扩缩容，实例的 IP 和端口就会随调度而变化，配置漂移几乎不可避免。

更麻烦的是故障摘除。某个实例进程还在，端口也还监听，但依赖的数据库连接池已经耗尽，请求全部超时。调用方如果只认配置文件，就会持续把流量打到这个“僵尸实例”上。注册中心的价值，正是把“实例清单”从静态配置变成动态的、可被程序读取和订阅的数据。

具体来说，注册中心要解决三类问题。第一是地址解耦：调用方只知道服务名，由注册中心给出当前可用的实例列表。第二是弹性感知：扩容时新实例自动进入清单，缩容时自动退出。第三是故障隔离：通过心跳或主动探测，把不健康的实例从清单中移除，缩短故障影响的持续时间。这三件事都伴随着时序、一致性与误判的难题。

注册：实例如何进入与离开清单

一个实例要能被发现，先得把自己登记进去。注册信息通常包括服务名、IP、端口、版本、机房与权重等元数据。服务名是逻辑标识，后几项决定调用方如何选择。注册动作一般发生在进程启动后、开始接收流量前，由框架自动完成。

进程启动成功不等于可以服务。数据库连接池尚未预热、缓存尚未加载时就注册并接收流量，会制造一批“启动即超时”的请求。因此注册应与就绪状态绑定，先自检再上报；容器环境里对应 readiness 探针通过后再加入 Endpoints。

注册之后要证明自己还活着，这就是心跳续约。客户端按固定间隔发送续约请求，注册中心为每个实例维护一个租约和 TTL。只要续约在 TTL 内到达，租约就延长；超过若干周期没有续约，实例被判定过期并移出清单。TTL 不能太短，否则网络一抖就误摘；也不能太长，否则故障实例会长期滞留。常见做法是心跳间隔数秒、TTL 为间隔的三倍左右，具体数值要结合故障发现时间和误摘率来定。

心跳是“自证存活”，存在盲区：进程卡死但心跳协程仍在运行，或者事件循环被长任务阻塞，都会出现“活着但不可用”。所以很多系统还会叠加服务端主动探测，例如 TCP 连接、HTTP 健康端点或 gRPC 健康检查。两种机制可以并存：心跳负责快速感知进程消失，主动探测负责识别逻辑故障。正常下线时，应用在关闭前主动注销，并等待一段时间让调用方刷新列表、让在途请求结束；异常退出则依赖 TTL 过期或探测失败来清理。

临时实例与持久实例的区别也在这里。临时实例的生命周期绑定会话或租约，客户端断连、租约过期就自动删除，适合无状态的在线服务；持久实例写入后长期保留，客户端消失也不会自动移除，需要显式注销或由服务端探测标记不健康，适合数据库、消息队列这类位置稳定、不能因为一次网络分区就消失的基础设施。选错类型会带来两种相反的事故：把数据库注册成临时实例，网络抖动会让它从清单里消失；把弹性扩容的 Pod 注册成持久实例，缩容后会留下大量幽灵记录。

发现：客户端、服务端与变更订阅

注册是写入，发现是读取。读取有两种位置。客户端发现把实例列表交给调用方，由调用方自己做负载均衡：SDK 从注册中心拿到地址，按轮询或随机挑一个发起连接。它的路径短、没有额外跳数，缺点是每种语言都要实现一套客户端逻辑，治理策略也分散在各处。服务端发现则在调用方和提供方之间放一个代理或虚拟 IP，调用方只访问固定入口，由代理查表并转发。Kubernetes 的 Service 就是典型：应用访问服务名，CoreDNS 解析出 ClusterIP，kube-proxy 再把请求转发到某个 Pod，调用方完全不知道实例地址。

有了列表，还要知道列表什么时候变。拉取模型由客户端定时轮询，实现简单、服务端压力可控，但新鲜度受轮询间隔限制；间隔短则请求多，间隔长则故障摘除后仍会打到旧地址。推送模型由注册中心在变更时通知订阅者，时效好，但要维护长连接、处理断线重连和事件丢失。折中的做法是长轮询：客户端发起一个带超时的请求，服务端有变更就立即返回，没有就挂起到超时，既减少空轮询，又保持准实时。

无论拉还是推，客户端都必须有本地缓存。缓存的作用不只是省一次远程调用，更是注册中心整体不可用时的兜底。调用链路上的每个请求都去问注册中心，既增加延迟，也把注册中心变成单点。合理的设计是：启动时全量拉取并落内存，之后通过订阅增量更新，定期做一次全量对账，防止增量事件丢失导致列表漂移。缓存要有版本号或 revision，收到的事件版本不连续时触发重新同步，而不是盲目合并。

订阅变更要处理“删除”与“新增”的语义。新实例可以立即放量，有预热需求的应先以低权重接入；摘除要区分“主动下线”和“疑似故障”。前者可等待在途请求结束，后者必须先摘除再观察。变更事件最好携带原因和时间戳，便于策略区分和排障。

    C->>C: 更新本地缓存

一致性：CP 与 AP 的取舍

注册中心本身是一个分布式存储，必然要面对 CAP。分区时，CP 系统拒绝写入或读不到最新值，保证多数派一致；AP 系统继续响应，但不同节点可能给出不同答案。注册数据读多写少、允许短暂陈旧但不能长期错误，不少系统因此在数据面偏向 AP，在管理面用共识算法保证配置一致。

有些实现是混合的：实例注册走 AP 复制，靠反熵和定期全量同步收敛；领导选举、配置变更走 Raft 或 Paxos。分区期间让调用方拿到稍旧但可用的列表，比直接报错更符合业务目标。

“最终一致”要给出收敛上界：心跳间隔、TTL、反熵周期与缓存刷新间隔共同决定变更多久能被所有调用方看到。预案应能回答，实例崩溃后最长多久仍有流量打过去，扩容后最长多久流量能均衡到新实例。

分区行为要单独测试。集群被切成两半时，少数派一侧的实例仍在心跳，但写入无法达成多数派；多数派一侧认为它们已过期。坚持 CP，少数派的新注册会失败，已有缓存仍可服务；偏向 AP，两侧可能各自维护清单，恢复后必须按版本号幂等合并，否则会出现“已下线实例复活”。

注册中心整体宕机时，客户端能否继续调用取决于缓存。只要持有未过期的本地列表，且不强制每次调用都同步查询，已有链路可以继续工作，新实例发现和故障摘除会暂停，系统进入“降级但可用”的状态。若 SDK 每次调用前都同步拉取，或缓存只在内存且重启即丢，注册中心一挂，调用方也跟着挂。

健康检查的误判

健康检查看到的是局部现象，不是全局真相。网络抖动是最常见的误判来源：注册中心与实例之间的链路拥塞、丢包，或节点短暂繁忙，都会让连续几次探测超时。阈值过紧，一次抖动就会摘掉健康实例；摘除又引发重试和流量迁移，进一步加剧拥塞，形成正反馈。

慢启动是另一类误判。Java 应用刚启动时 JIT 未预热、连接池未建立，首批请求可能要数百毫秒；Go 服务启动快，但依赖的下游未必就绪。只看端口是否监听，实例会被过早加入；只看首次请求是否在 100 ms 内完成，实例又会被反复摘除。合理做法是区分 liveness 与 readiness：前者判断进程是否该重启，后者判断是否该接流量，并给 readiness 足够的初始宽限期。

摘除后的恢复同样重要。实例被摘除后，注册中心应继续探测，否则短暂抖动的实例可能永远回不来。恢复时不要瞬间放全量流量，最好逐步加权预热，给连接池留出重建时间。长连接场景下摘除只影响新连接，旧连接仍可能打到“已摘除”的实例，因此还需要连接级别的排空。

参数没有标准答案，但有一条原则：分别估计误摘与漏摘的代价。误摘拿走本可服务的容量，可能引发雪崩；漏摘让部分请求失败，但通常有重试兜底。核心服务宁可放宽阈值、增加探测次数，也不要用一次超时做生死判决；边缘服务可以更激进。无论哪种，都要把摘除事件、探测结果和调用方错误率放在同一时间轴上观察。

与 DNS、Service Mesh 的关系

DNS 也是一种发现，但记录有 TTL 缓存，实例变化不能立刻反映，而且只返回地址，不携带健康状态与权重。Kubernetes 把两者结合得较好：Service 提供稳定的虚拟 IP 和 DNS 名，Endpoints 随 Pod 就绪状态更新，CoreDNS 负责解析，kube-proxy 负责转发。这套机制在集群内很好用，跨集群、跨云时仍需要额外的发现层。

Service Mesh 把发现下沉到基础设施。以 Istio 为例，控制面监听 Service 与 EndpointSlice，转换成 xDS 配置下发给 Envoy；应用只访问本地代理，由代理完成发现、负载均衡、熔断与 mTLS。好处是语言无关、策略统一，升级发现逻辑不必改业务代码；代价是多了一跳，运维和排障更复杂。sidecar 模式在 2022 年仍是主流，无 sidecar 的 ambient 模式尚处早期，不宜当作稳定方案。

Mesh 并没有消灭注册中心，只是换了位置。控制面仍需要可靠的服务清单来源，这个来源可以是 Kubernetes API，也可以是独立注册中心，两者不是互斥选项。

边界：原理、选型与负载均衡

本文讲机制与语义，不做产品横评。注册中心选型要比较一致性模型、健康检查、推送能力与运维成本；负载均衡关心拿到列表后如何挑实例，例如轮询、加权、最少连接和一致性哈希。三者有交集但问题不同：注册中心回答“有哪些实例”，负载均衡回答“这次选哪一个”，选型回答“用哪个产品承载前者”。排障时先分清问题在哪一层。

小结

注册中心把静态地址变成可订阅的动态清单，核心动作是注册、续约、发现与摘除。临时实例靠租约自动清理，持久实例靠显式管理，两者不能混用。发现要依赖本地缓存兜底，注册中心应被当作控制面而非数据面的必经节点。一致性上接受最终一致，但要给出收敛上界并演练分区；健康检查要权衡误摘与漏摘，给慢启动和网络抖动留出宽限。DNS 与 Service Mesh 是发现位置的变化，不是替代关系。
