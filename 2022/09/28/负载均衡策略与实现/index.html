负载均衡策略与实现

本文属于《Go 微服务架构》第 16/35 篇
上一篇系列目录下一篇

把流量分给多台机器，看起来只是从列表里挑一台，做对却要同时兼顾算法、健康状态、会话与超时。本文从四层与七层的差别讲起，逐一拆解常见调度算法、一致性哈希、健康检查、重试与局部性，并给出一个 Go 语言的最小实现和 Nginx 配置片段。适合准备为系统补上流量分配这一环的读者。

从连接到请求：两个层面的负载均衡

负载均衡要解决的问题很朴素：手上有一组提供相同功能的服务实例，每个请求应该交给谁。答案取决于我们站在哪一层看流量。

四层负载均衡工作在传输层，只看 IP 与端口。以 LVS/IPVS 为代表，它通常以虚拟 IP 对外，在内核网络层完成转发，把一条 TCP 连接固定到某台后端。它的优势是路径短、开销小、吞吐高，不关心连接里跑的是 HTTP 还是别的协议；代价是看不到请求内容，只能在连接建立时做一次选择。对长连接而言，这意味着一条连接上的所有请求都被绑在同一台机器上。

七层负载均衡工作在应用层，先终止或解析协议，再按请求转发。Nginx 与 Envoy 是常见选择：前者常作为反向代理与 Web 服务器，配置直观；后者常出现在服务网格与边车场景，动态配置能力更强。七层能看到路径、Header 与状态码，因此可以按请求重试、按 URI 分流、做细粒度的观测。代价是多了一次解析与转发，还要处理连接复用带来的语义问题。

这里的区别可以概括为连接级与请求级：连接级在握手时选一次，请求级可以每个请求重新选。HTTP/1.1 的 keep-alive 与 HTTP/2 的多路复用把“连接”和“请求”拆开了，如果不加处理，请求级负载均衡的效果会被长连接稀释，后端连接数也可能严重不均。

需要说明边界：网关的整体架构不在本文范围，服务注册与发现的机制也另有专文。本文关注的是，拿到候选实例之后，流量如何被分配到它们身上。

基础调度算法：轮询、加权与最少连接

轮询是最容易实现的策略：维护一个下标，依次取下一个实例。它假设所有实例性能相同、请求开销相近，实现简单且分布均匀；一旦实例规格不一致，快机器就会长期空闲。

最少连接把新请求交给当前连接数最少的实例，适合请求耗时差异大、连接数能反映压力的场景。它要求负载均衡器维护连接计数，并且对短连接不够公平：连接刚建立就结束的请求会把计数短暂抬高。最短响应时间在此基础上引入延迟统计，通常把连接数与响应时间加权成一个评分，实现和调参都更复杂。

源地址哈希按客户端 IP 取模选择实例，能让同一来源的请求落到同一台机器，配置简单，常被当作轻量会话保持。但 NAT 与运营商出口会把大量用户映射到少数 IP，造成严重倾斜，只适合作为兜底手段。

一致性哈希与虚拟节点

取模哈希的致命问题是扩容。假设有 N 台实例，请求按 hash(key) % N 选择；N 变化后，绝大多数 key 的映射都会改变，缓存类服务会瞬间出现大面积未命中。一致性哈希把实例与 key 映射到同一个哈希环上，key 顺时针找到的第一个实例就是归宿。增加或删除一个实例时，只有相邻区间的 key 需要迁移，其余映射保持不变。

朴素的一致性哈希有两个问题：实例较少时，环上的位置可能挤在一起，负载不均；实例变动时，某台机器可能承接过多迁移流量。虚拟节点解决前者：每台物理机在环上注册多个副本，副本越多分布越均匀，具体数量要按实例规模实测调整。

健康检查：主动探测、被动摘除与慢启动

主动探测由负载均衡器按固定间隔发起，建立 TCP 连接或发送 HTTP 请求，连续失败达到阈值才摘除，连续成功达到阈值才恢复。阈值是为了抗抖动：单次超时可能只是瞬时拥塞，立刻摘除会让剩余实例压力更大。间隔、超时、失败与成功阈值要一起看，探测太频繁会放大负担，太稀疏则故障发现慢。

被动摘除观察真实请求的结果，把 5xx、连接失败与超时计入异常统计。它不需要额外探测流量，但依赖足够的样本；流量稀疏时可能迟迟发现不了故障，也可能因个别慢请求误杀实例。Envoy 的异常点检测属于这一类，Nginx 开源版的 max_fails 与 fail_timeout 也是被动机制。两者可以叠加：主动探测覆盖无流量时的判活，被动摘除依据真实请求快速反应。

还需要设置摘除比例上限。若后端整体抖动，逐台摘除可能把实例全部移出，负载均衡器反而制造了完全不可用。常见做法是保留一定比例，或允许恐慌模式放行，让请求到达后端，由后端自行限流与降级。

慢启动解决恢复瞬间的雪崩。实例刚恢复时本地缓存为空、连接池未预热，立刻给它满权重会再次压垮它。慢启动在恢复后的一段时间内逐步增加权重，从较小比例升到正常值。Nginx 开源版没有对应指令，商业版提供 slow_start；Envoy 也有慢启动模式。选型时要确认版本是否支持，或改由发布系统控制放量节奏。

健康状态还与注册中心相关。注册中心负责实例的注册、租约与变更推送，负载均衡器负责把健康状态翻译成权重与候选集。注册中心判活通常较粗，负载均衡器应保留自己的被动检测，不能把注册中心的结果当作唯一真相。实例下线时要先摘流量、等待存量请求结束，再注销，否则会出现连接被重置的尾包错误；注册与发现的细节见另文。

会话保持：粘性的代价与无状态化

粘性会话让同一用户的请求固定到同一实例，常见实现是负载均衡器植入 Cookie，或按源地址哈希。它能让实例本地缓存与内存会话直接命中，改造成本低。

代价有四层。第一，负载可能倾斜，热门用户或长会话把单台机器拖垮。第二，实例故障会丢失会话，用户被迫重新登录或重做流程。第三，扩容不生效，新实例分不到已有会话，缩容又必须先迁移。第四，长连接与粘性叠加后，连接级负载均衡几乎失去调度能力。

更稳妥的方向是让服务无状态：会话数据放到 Redis 之类的共享存储，客户端只持有会话标识；或者使用签名的 Token 把必要声明放在客户端，服务端只做校验。前者依赖一次远程读取，后者要考虑吊销与过期。状态从实例内存挪走之后，负载均衡器可以自由选择实例，扩缩容和故障转移都简单得多。若短期内必须粘性，至少要为会话存储设置过期与降级路径，并在实例下线时做好排空。

重试、超时与对冲请求

超时是最容易被忽略的参数。客户端、负载均衡器与服务端各有一层超时，如果外层比内层短，内层还在处理时外层已经放弃并重试，同一请求就可能被执行多次。合理的做法是让超时预算逐层递减，并把剩余时间传给下游；预算耗尽后直接失败，而不是继续排队。

重试只应发生在安全的边界上：连接建立失败、请求尚未发出，或响应头尚未返回时可以重试；已经收到部分响应再重试，语义就复杂了。方法是否幂等同样关键，GET 与 HEAD 天然可重试，POST 创建订单必须先有幂等键或去重表，否则重试会变成重复下单。

重试放大的问题更隐蔽。客户端重试一次、负载均衡器重试一次、服务内部再重试一次，最坏情况下一次用户请求会变成八次后端调用，而且都落在同一批慢实例上。控制手段包括只在一层重试、设置重试预算、对连续失败做熔断，以及给重试加退避与抖动。

对冲请求走另一条路：请求发出后，若超过某个分位数的延迟仍未返回，就向另一台实例再发一份，谁先返回用谁，并取消另一份。它能压低长尾，代价是额外流量，而且只对幂等读请求安全；如果两份请求都产生副作用，去重必须由服务端保证。对冲比例要有上限，否则尾延迟会演变成整体过载。

局部性、容量与权重

真实集群通常按可用区分布，同区调用延迟低、跨区流量有成本，机房级故障又要求能跨区兜底。局部性优先的策略是：正常情况下只把流量分给同区实例，同区健康实例不足或负载过高时，再按比例溢出到其他区。溢出比例要设上限，否则一个区故障会把另一个区压垮。

容量信息要进入权重。静态权重表达的是机器规格，扩缩容后实例数量变化，权重却不会自动调整；按 CPU、连接数或并发请求数动态计算权重，能让分配跟随真实容量。但动态权重会带来震荡，采集延迟与实例启动都会影响判断，通常需要平滑与滞回。Kubernetes 的拓扑感知路由也遵循类似思路，把流量尽量留在同一区域，具体能力取决于集群版本与配置。

全局与局部分工也值得明确：全局负载均衡按地域与机房分配，局部负载均衡在机房内选实例。两层都要有故障转移与容量上限，不能只依赖其中一层。

小结

负载均衡不是选一个算法就结束，而是算法、健康状态、会话、超时与拓扑共同作用的结果。轮询与加权适合同构服务，最少连接适合耗时差异大的场景，一致性哈希适合有状态与缓存场景。健康检查要主动与被动结合并留出摘除上限，会话尽量无状态化，重试要有预算与幂等前提。想清这些约束再落配置，才能避免策略在故障时放大问题。
