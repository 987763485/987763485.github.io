长任务拆分与断点续跑

批量导入、报表生成、数据迁移、模型预处理，这些任务的共同点是从几分钟跑到几小时，中途可能遇到进程重启、下游限流、单条脏数据。把它们塞进一个 HTTP 请求或一个后台线程，第一次失败就会暴露问题：进度归零、副作用重复、没人知道任务究竟停在哪里。本文从拆分、检查点、状态机、恢复、并发与可观测几个方面，给出一套不依赖特定工作流引擎的长任务执行模型，适合需要自己实现任务编排的后端工程师阅读。

长任务与短请求的差异

短请求的执行模型建立在三个假设上：耗时在秒级以内、失败后整体重试的代价可以接受、执行状态只存在于一次调用的栈里。长任务把这三个假设逐一打破。一次两小时的数据迁移在第九十分钟失败，整体重试意味着前面的工作全部作废；进程被发布重启，内存里的循环变量和已打开的文件句柄一起消失；下游的限流窗口按分钟计算，失败不再是偶发事件，而是稳定出现的常态。

差异可以归为四类。其一是时间跨度，任务生命周期超过一次部署、一次扩容、一次主从切换，执行者必须在多次进程生死之间延续。其二是数据规模，输入无法一次读入内存，处理必须分页推进。其三是外部依赖，数据库、对象存储、第三方接口都有配额与超时，长任务会持续暴露在这些波动之下。其四是人的预期，操作者需要看到进度、能够取消、在失败后知道从何处继续，而不是面对一个沉默的后台线程。

由此产生几个本文反复使用的术语。作业（job）是用户提交的一次完整任务；阶段（stage）是作业中有依赖关系的处理环节；分片（shard）是同一阶段内可以并行处理的数据子集；尝试（attempt）是某个子任务的一次执行；检查点（checkpoint）是持久化的进度记录。一个分片在一个阶段上的一次执行，构成调度的基本单元。

需要强调的原则只有一条：把“做过什么”外化到持久存储，把“还要做什么”表达成可以从存储重建的计划。前者是检查点，后者是拆分。只要这两件事成立，执行进程就可以随时消失，恢复只是重新读表、重新计算待办列表。反之，如果把进度留在内存、把待办藏在循环里，任何一次重启都会把系统打回原点。

三种拆分方式：分片、阶段与批次

拆分的第一种切法按数据分片。先确定一个稳定的分片键，再把键空间切成若干段：自增主键按区间切，时间字段按天或小时切，无序的业务主键对哈希取模。分片键决定了并行的均匀程度：用订单创建时间做分片，促销日的分片会明显更大；用用户 ID 做分片，活跃用户所在的分片会更慢。工程上通常选基数大、分布均匀、且与查询条件一致的字段，并在任务开始前采样，估算每个分片的行数，必要时把过大的分片再拆一层。

第二种切法按阶段组成有向无环图。以报表生成为例，流程可以拆成抽取、清洗、聚合、渲染、上传五个阶段，前一个阶段的输出是后一个阶段的输入。DAG 的价值不只是表达顺序，更在于暴露可以并行的宽度：清洗可以按分片并行，聚合需要等待所有清洗分片完成，这是一个扇入点（fan-in）；渲染又可以按报表页并行，形成新的扇出。阶段依赖必须显式存储为边，而不是靠代码里的调用顺序隐式表达，否则恢复时无法判断前置条件是否满足。

第三种切法按批次推进。即使分片已经确定，单个分片仍可能包含几十万行，必须用游标一页一页地读。批次大小是吞吐与恢复成本的折中：每批一千行，检查点写得更频繁，崩溃后最多重放一千行；每批十万行，写入次数少，但一次失败就要重做十万行的副作用。另一种做法是按时间片切批，每处理三十秒就主动停在安全位置写检查点，使单次尝试的时长可控，避免长事务和租约过期。

三种切法通常组合使用。分片决定并行度，阶段决定依赖，批次决定检查点频率。用矩阵来理解：行是阶段，列是分片，每个格子是一个子任务，格子内部再按批次推进。调度器只需管理格子级别的状态，格子内部的重试与游标由执行器维护。一个常见错误是把批次也做成调度单元，导致任务表膨胀、调度开销超过实际计算，这一点在下一节展开。

子任务粒度与调度开销的取舍

拆分不是越细越好。设总工作量为 W，并行度为 P，单个子任务的固定开销为 c，则完成时间大致是 W / P 加上与子任务数量成正比的调度开销。子任务越细，负载越容易均衡，恢复时重放的越少；但每个子任务都要经历领取、状态写入、心跳与结果落库，固定成本会迅速累积。一个每秒处理一万行的任务，如果按每行一个子任务拆分，光是把任务 ID 写进数据库就会成为瓶颈。

固定开销来自几个地方。每次领取要做一次条件更新或队列投递；每次状态迁移要写一行记录并提交事务；每个子任务可能重新建立数据库连接、重新打开文件、重新加载模型；如果子任务跑在容器里，还要加上冷启动。把这些成本摊到子任务上，可以得到一个经验区间：单个子任务的执行时间在十秒到五分钟之间比较合适，短于十秒说明切得过碎，长于五分钟则一次失败的重放代价偏高。检查点的间隔通常取三十秒到一分钟，与心跳周期保持同一量级。

比平均开销更难处理的是长尾。十个分片里有九个在十分钟内完成，剩下一个因为数据倾斜跑了四十分钟，整体完成时间由最慢的分片决定。增加并行度不能解决长尾，反而会让更多分片争抢同一个热点。可行的办法是动态再分片：运行一段时间后采样各分片的实际速率，把明显落后的分片按主键区间一分为二，旧分片处理完剩余部分即可，不需要回滚。另一种办法是工作窃取，空闲工作者从最忙的分片尾部领取一小段，但这要求分片边界可以安全移动，实现复杂度更高。

粒度设计还受恢复语义约束。子任务的边界就是检查点的边界：如果子任务内部没有任何检查点，崩溃后整个子任务重来。因此更实用的结构是两级粒度，分片作为调度与租约的单位，批次作为检查点与幂等的单位。调度器看到的是几十到几百个分片，数据库里记录的是每个分片最近一次成功批次的游标。这样既不会让任务表爆炸，也不会让一次崩溃重放整个分片。

粒度是否合适不能靠直觉，要在预发环境记录每个子任务的排队时间、执行时间与状态写入耗时。排队时间远大于执行时间，说明并行度不够或下游被限流；状态写入占比超过两成，说明子任务太碎；执行时间的 P99 是 P50 的十倍以上，则先处理数据倾斜。

检查点：存什么、存在哪里、何时写

检查点的内容取决于恢复时需要重建什么。最小集合包括游标、已处理标识、阶段状态与计划版本。游标用于顺序推进，最常见的是键集分页（keyset pagination）的位置，例如上一批最后一条记录的主键；只存 offset 在数据会插入删除的场景里并不可靠，前面的行变动会让 offset 指向错误的位置。已处理标识用于无法用单一游标表达的场景，例如按 ID 列表处理、乱序消费，此时需要记录已完成的一批 ID，或者维护去重表。阶段状态描述当前阶段是否完成、输出写到了哪个位置；计划版本用于识别拆分方案是否变化，版本不一致时不能盲目续跑。

还有两类信息容易被忽略：计数与校验和，例如已处理行数、输出分片编号、内容哈希，用于恢复后判断是否遗漏或重复；以及写入时间与租约纪元（epoch），用于识别陈旧写入。检查点不是越大越好，把整个中间结果塞进一行记录会让每次写入都变成大事务。正确做法是把大对象写到对象存储，检查点里只保留路径、大小与校验和。

存储位置有三种常见选择。关系型数据库适合与业务数据放在一起，检查点写入可与业务写入处于同一事务，获得“副作用与进度一起生效”的原子性，代价是写放大与锁竞争。Redis 适合高频心跳与短期进度，延迟低，但要注意持久化与淘汰策略，不能把唯一的进度副本放在可能被逐出的实例里。对象存储适合中间产物与大批量 ID 清单，单个对象写入是原子的，配合临时对象加改名可实现“写完才可见”，缺点是延迟较高。

常见的组合是元数据、游标与状态放数据库，心跳与速率放 Redis，输出文件与大 ID 集合放对象存储，数据库只存引用。

写入时机只有一条硬规则：先完成副作用，再写检查点。顺序反过来，进程在两者之间崩溃，恢复时会认为这批已经处理完，实际副作用没有发生，形成数据丢失。按照“先副作用、后检查点”的顺序，崩溃只会导致重放，而重放可以用幂等来消化，这就是“至少一次”语义的来源。写入频率是成本与重放量的折中：每批都写，恢复粒度最细但事务最多；每隔若干批写一次，成本下降，崩溃后最多重放若干批。默认可以每批结束写一次轻量游标，每五到十批做一次带校验和的完整检查点。写入时使用带版本与租约条件的更新：

状态机、心跳与僵尸任务

状态机的价值在于把“任务现在处于什么阶段”变成有限、可校验的枚举。本文使用五个状态：PENDING 表示待执行，RUNNING 表示已被某个执行者领取，SUCCEEDED 表示完成，FAILED 表示不可恢复的失败，RETRYING 表示等待下一次尝试。可选地再加 CANCELLED，用于用户主动取消。状态迁移必须由协调者校验，执行者只能提交“我完成了”或“我失败了”的意图，不能直接把一行记录改成成功，否则一个网络分区中的旧执行者可以在新执行者接管后把状态改回去。

心跳与租约负责发现失联。执行者每十秒更新 heartbeat_at，协调者每三十秒扫描一次，超过三次心跳未更新的 RUNNING 任务视为可疑，租约到期后进入 RETRYING。租约时长要大于单次批次的处理时间加上一次网络往返，通常是六十到一百二十秒。心跳只能发现“没有响应”，不能阻止“暂停后又醒来”的进程继续写数据：一个被操作系统挂起的进程可能在租约过期、任务被接管之后恢复运行，此时两个执行者同时持有同一分片。解决办法是隔离令牌（fencing token）：每次领取让 lease_epoch 加一，所有写入都带上当前 epoch，存储层拒绝小于当前 epoch 的写入。心跳负责发现，令牌负责隔离，两者缺一不可。

超时分为三层。单次尝试有执行超时，防止一个死循环永远占着分片；单个子任务有总超时，跨多次尝试累计；整个作业有截止时间，到点后不再启动新的子任务，已在运行的允许收尾或强制取消。三层超时的默认值应该由数据规模推算，而不是拍一个固定数字。重试策略要与失败分类绑定：网络超时、下游 429、临时不可用可以重试，采用指数退避加抖动；主键冲突、字段格式错误、权限不足属于不可重试，直接进入 FAILED 并记录原因。

崩溃语义需要区分三种情况。执行者进程崩溃，租约到期后由协调者接管，这是最常见也最容易处理的；执行者所在机器失联，与进程崩溃类似，只是发现时间更长；协调者自己崩溃则麻烦得多，如果它只在内存里维护调度队列，重启后队列丢失，所有 RUNNING 的分片都成了无人认领的僵尸。因此协调者应当尽量无状态，队列从数据库重建，领取与续约都落在数据库的条件更新上，多实例部署时依靠租约和 epoch 保证同一分片只有一个有效持有者。

恢复：至少一次重放与去重

恢复的入口是一次扫描：找出 RUNNING 且租约过期的分片，把它们改回 RETRYING，增加尝试次数，递增 epoch，然后重新入队。扫描必须幂等，多个协调者同时扫描时，用条件更新保证只有一个能把状态改成功。已经是 SUCCEEDED 的分片不再参与调度，即使输出看起来不完整，也应该通过校验和发现问题后人工介入，而不是自动重跑，否则可能把已经发布的结果改掉。

待办列表应当从存储重建，而不是从内存恢复。子任务 ID 用作业 ID、阶段名、分片号和计划版本做确定性哈希，重复投递同一个子任务时依靠唯一索引去重。这样，协调者重启后只需要读一遍分片表，把非终态的记录重新纳入调度，不需要额外的消息补偿。消息队列可以作为加速手段，但不能成为唯一的事实来源。

重放的核心问题是副作用重复。按安全性可以把步骤分成四类：纯计算步骤，例如格式转换、特征计算，重放没有副作用；覆盖写步骤，例如按主键写结果表，重复执行结果相同，天然幂等；追加写步骤，例如写日志、发消息、插流水，会产生重复记录，需要去重键；外部副作用，例如调用支付、发送邮件，必须依赖对方支持的幂等键，或者用本地事务表加补偿。分析清楚每个阶段属于哪一类，才能决定重试策略。

去重的实现方式有几种。结果表上建唯一索引，写入使用 INSERT … ON CONFLICT DO NOTHING 或先查后写；单独维护去重表记录业务键与处理时间，定期清理；消息端使用消息 ID 做幂等消费。无论哪种，去重键都必须来自业务语义，而不是执行时间或随机数，否则重放时生成的新键无法命中旧记录。去重表的写入要与业务写入在同一事务里，否则仍然存在窗口。

部分成功是一等状态，不是异常。十个分片里八个成功、两个失败，作业整体不能标记为成功，也不应回滚成功的分片。正确做法是保留每个分片的终态，作业层聚合出“部分成功”，展示失败分片与原因，允许只重跑失败分片。这要求作业状态与分片状态分开存储，作业的 SUCCEEDED 条件是所有分片 SUCCEEDED，而不是“没有抛出异常”。

跨系统的严格一次很难做到，工程上追求的是“至少一次执行加幂等结果”，把这句话写进设计文档，比在代码里堆重试逻辑更有用。

并发控制：工作池、租约与背压

并发控制有三个层次：进程内的工作池、跨进程的分片租约、对下游的背压，三者解决的不是同一个问题。

工作池限制单个实例同时在跑多少个子任务。常见做法是固定数量的工作者从一个有界队列取任务，队列满时暂停领取，而不是无限堆积。工作者数量不能只按 CPU 核数设置，长任务大多在等 IO，一个实用的起点是下游连接池大小的七成，再根据实际等待时间调整。每个下游还应有独立的并发上限，避免一个阶段挤占另一个阶段的配额。

分片租约解决“谁来处理这个分片”。领取是一条原子语句：筛选 PENDING 或租约过期的记录，写入持有者与到期时间，把 epoch 加一，返回被选中的行。PostgreSQL 的 SELECT … FOR UPDATE SKIP LOCKED 可以让多个工作者并发领取而不互相阻塞，也不会重复拿到同一行；MySQL 8.0 可以用 UPDATE … LIMIT 1 配合条件判断，或者用领取记录表加唯一索引。核心要求是筛选、标记、返回在同一个事务里完成，不能先查后改。

背压是长任务最容易忽略的一环。下游变慢时，如果工作池继续领取分片，只会让更多任务卡在超时上，重试又进一步放大流量。正确的反应是降低领取速率：队列深度超过阈值时暂停领取；下游返回 429 时按响应头或固定窗口退避；连续失败时把并发减半，成功后再逐步加回。这种加性增、乘性减的策略不需要精确的容量模型，适合处理未知的下游上限。

限速要区分全局与局部。全局限制保护下游整体，通常用 Redis 的令牌桶或固定窗口计数实现；局部限制保护单个租户或分片，避免一个大客户占满配额。限速器本身也可能成为瓶颈，高频调用时可在本地批量预取，代价是短时间内的速率不够精确，对长任务而言通常可以接受。

可观测性：进度、速率与失败分类

长任务的可观测性首先回答三个问题：完成了多少、还剩多久、为什么失败。进度不能只按子任务个数计算：十个分片里九个是小分片、一个是千万行的大分片，按个数算会显示百分之九十，实际工作量可能只完成了一半。更准确的做法是按行数、字节数或预估耗时加权，每批完成后累加已处理量。权重可以修正，但修正后进度要单调不回退，否则用户会以为任务出了问题。

速率与剩余时间需要平滑。瞬时速率对短窗口非常敏感，一批快一批慢会让 ETA 剧烈跳动；直接用总完成量除以总耗时，又会把早期的慢速阶段永久带入估计。常用的折中是取最近五分钟的滑动窗口并配合指数平滑，给出区间而不是单点。预计完成时间超过业务截止时间时，应提前告警，而不是等到超时才发现。

失败要分类，而不是只计数。至少区分四类：瞬时故障，例如超时、连接重置、429、5xx，可以重试；永久故障，例如字段格式错误、主键冲突、权限不足，重试没有意义；资源故障，例如内存不足、磁盘写满，需要人工或自动扩容；程序缺陷，例如空指针、断言失败，需要发版修复。每类失败的告警渠道与处理方式不同，混在一个计数里，值班人员无法判断该等待还是该介入。

告警阈值应围绕“有没有进展”设置，而不是绝对数量。一个可行的组合是：连续十分钟没有分片完成则告警；失败率在十五分钟窗口内超过百分之十则告警；僵尸分片持续五分钟则告警；检查点年龄超过十分钟则告警；预计完成时间超过截止时间则提前告警。阈值要根据历史分布调整，新任务上线前先跑观察模式，只记录不告警。日志与追踪要带上作业 ID、阶段、分片号、尝试次数与租约纪元，但按批次汇总，只对失败与状态迁移打点。

一个最小实现骨架

把前面的部件拼起来，一个可运行的最小实现只需要作业表、分片表和去重表。协调者循环做三件事：扫描超时租约、领取待执行分片、写回完成或失败的结果。执行者按阶段类型调用具体处理函数，函数内部按批次推进，每批结束后提交游标。下面用 Go 写出核心结构，省略错误处理与具体业务，重点是接口划分：存储负责条件更新，执行器只负责计算与提交检查点。

这段代码结构完整，但省略了几个关键细节。Process 必须幂等，或者由下游的去重键保证重复执行无副作用；SaveCheckpoint 带 epoch 条件，租约易主后写入会失败；Heartbeat 失败意味着当前执行者不再拥有分片，继续计算只会产生无人认领的副作用。协调者的领取逻辑对应前面的 SQL，扫描逻辑是按 lease_until 过滤的定时任务。生产环境还需要取消信号、阶段依赖检查、输出产物的原子提交，以及把分片状态聚合为作业状态的视图。

边界与选型

自研的前提是任务形态稳定、故障模式清楚、团队能维护状态存储与调度循环。每天只跑一次、失败后整体重跑也能接受的任务，用定时任务加幂等写入即可；依赖成百上千、需要人工审批与可视化补偿的场景，成熟的工作流引擎更合适。选型看控制流复杂度、状态规模与运维能力：线性脚本和简单扇出适合自研，条件分支、循环、人工介入更适合交给引擎。若决定自研，应主动收窄范围，只支持 DAG 加扇出扇入和固定几种失败分类；范围越窄，状态机越容易验证。

小结

长任务的难点不在计算，而在执行者随时可能消失。本文的模型可以概括为：用分片获得并行，用阶段表达依赖，用批次控制检查点，用租约与状态机保证同一时刻只有一个有效执行者。检查点要存游标、已处理标识、阶段状态与计划版本，并且必须在副作用之后写入；恢复依赖“至少一次加幂等”，而不是追求跨系统的严格一次。并发控制要同时考虑工作池、租约与背压，可观测性则围绕进度、速率与失败分类展开。把这套模型落到几张表和一个协调循环上，足以支撑大多数小时级批量任务；控制流复杂到需要人工介入时，再考虑成熟的工作流引擎。
