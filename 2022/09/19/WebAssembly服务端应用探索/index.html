WebAssembly 服务端应用探索

本文属于《Docker 与 Kubernetes》第 51/51 篇
上一篇系列目录下一篇

WebAssembly 最初为浏览器里的高性能计算而生，如今它的沙箱模型被搬到了服务端：把一段不完全信任的代码装进几百 KB 的模块里，按需加载、按能力授权执行。本文梳理 2022 年的 WASI 现状、主流运行时与嵌入方式，讨论它能做什么、不能做什么，并与容器做一次边界清晰的对比。读完后你应当能判断：系统里哪些位置适合放 wasm 模块，哪些位置放进去只会徒增麻烦。

从浏览器到服务端：一个可移植的沙箱

WebAssembly（下文简称 wasm）是一种面向栈式虚拟机的二进制指令格式。它最初的目标，是让 C/C++、Rust 编译出的代码在浏览器里接近原生速度运行，2019 年成为 W3C 的推荐标准。随着工具链成熟，人们发现它的另一面同样有价值：模块默认只能访问自己的线性内存，除此之外的一切，包括文件、时钟、随机数与网络，都必须由宿主以导入函数的形式显式提供。

这个约束在浏览器里是为了安全，到了服务端反而变成一种架构能力。传统进程一旦启动，就继承了操作系统的全部视图：环境变量、文件描述符、信号、网络栈。要在同一进程里安全运行第三方代码，通常只能依赖语言级沙箱，或者再套一层容器。wasm 把边界画在模块这一层：一个模块能做什么，在实例化时由宿主逐项授予；没有授予的能力，在指令层面就不存在。

由此得到三个直接的好处。其一是粒度细，一个进程可以同时承载成百上千个隔离实例；其二是启动快，实例化通常只需毫秒级，不必创建进程、挂载文件系统；其三是可移植，同一份字节码可在 x86 与 ARM、Linux 与 macOS 上运行，平台差异被吸收在宿主运行时里。

需要强调的是，wasm 本身只定义了计算与内存模型，并没有定义“如何与操作系统对话”。这部分由 WASI 补上，也是服务端应用能否真正落地的关键。

WASI preview1：把系统能力变成显式契约

wasm 模块没有“文件系统”这个概念。它想读一个文件，靠的不是路径，而是一个整数：文件描述符。WASI（WebAssembly System Interface）定义的就是这套接口，由 Bytecode Alliance 推动。它在设计上刻意偏离 POSIX 的全局命名空间思路，转向能力模型。

在 2022 年，运行时普遍实现的是 wasi_snapshot_preview1 这一版，通常简称为 preview1。它的核心是一张文件描述符表：宿主在实例化时把若干目录“预打开”（preopen），映射为 fd 3、4、5 等编号；模块之后的所有路径操作都相对于这些目录进行，无法用 .. 逃逸到未授权的位置。文件读写、目录遍历、元数据查询都围绕 fd 展开，这就是沙箱边界的具体形态。

除了文件，preview1 还规定了另外几类能力：通过 clock_time_get 读取单调时钟与墙钟，通过 random_get 获取密码学安全的随机数，通过 args_get 与 environ_get 读取启动参数，以及用 proc_exit 结束实例。

有两个限制值得记住。第一，preview1 里没有 socket，模块无法自行建立网络连接，需要网络的场景必须由宿主以自定义导入函数提供。第二，接口是同步阻塞的，异步语义要由宿主的调度层包出来。规范的下一个大版本当时仍在设计与实现中，本文不把它当作可用能力。

运行时版图：wasmtime 1.0 与它的同伴

到 2022 年下半年，服务端运行时已经形成了几个稳定的选择。最常被提起的是 wasmtime：它由 Bytecode Alliance 维护，用 Rust 编写，编译后端是 Cranelift。2022 年 9 月发布的 1.0 版本是一个标志性节点：项目开始对 API 稳定性作出承诺，嵌入方不必跟着每次小版本重写代码。它同时提供 CLI 与库两种用法，并内置 fuel 计量与 epoch 中断，用来限制模块的执行。

WasmEdge 走的是另一条路线。它用 C++ 实现，主打边缘计算与云原生场景，对 WASI 之外的标准提案跟进积极，也提供面向推理的扩展接口。Wasmer 则以多后端著称，同一份模块可以选择 LLVM、Cranelift 或 Singlepass 编译，其中 Singlepass 编译极快，适合“一次执行”的函数场景。若宿主是 Go 程序，wazero 值得一提：纯 Go 实现，不依赖 CGO，部署简单。

无论选哪一个，嵌入的思路大同小异，可以概括为四层：引擎负责编译与代码缓存，模块是编译产物，存储（store）持有实例运行期的状态与资源，链接器把宿主函数注册进模块的导入表。关键习惯是“编译一次、实例化多次”：编译成本高、实例化成本低，把两者分开才能吃到启动优势。

从 Rust 到宿主：编译与 ABI

编译为 wasm32-wasi

先看一个最小例子：把一段文本规范化逻辑导出为宿主可调用的函数。配置的关键有两点：把 crate 类型设为 cdylib，否则编译器不会保留导出符号；编译目标选 wasm32-wasi，而不是 wasm32-unknown-unknown。后者没有系统接口，只适合纯计算；前者才能拿到 WASI 的导入。

产物是自包含的模块：代码、只读数据与内存布局都在里面，没有动态库依赖。把文件拷到装有运行时的机器上即可执行。

线性内存是唯一通道

跨边界调用没有想象中那么“自然”。wasm 的函数签名只允许 32 位与 64 位的整数和浮点数，Rust 的 String、Vec、结构体都不能直接出现在参数里。宿主眼中的导出函数，只是一串整数。

于是需要一个双方都遵守的约定。常见的做法是“指针加长度”：宿主先调用模块导出的 alloc，在模块的线性内存里划出一块空间，把 UTF-8 字节写进去，再把偏移量和长度传给业务函数。返回值用一个 64 位整数打包，高 32 位放结果指针，低 32 位放长度。这套约定只在 wasm32 上成立，因为那里的指针刚好是 32 位。

适合放 wasm 的位置：四类典型场景

第一类是插件系统与多语言扩展。主程序用 Go 或 Rust 编写，插件由第三方用其他语言实现，统一编译成 wasm。宿主只注册少量导入函数，例如写日志、读配置、发起 HTTP 请求，插件拿不到主机的文件描述符，也就谈不上越权。相比动态库，它不会因一次段错误拖垮进程；相比独立进程加 RPC，又省掉了序列化与连接管理。

第二类是用户自定义函数（UDF）。数据平台、规则引擎、流处理系统经常允许用户提交一小段转换逻辑，用于字段脱敏、指标计算或路由匹配。把这段逻辑编译为 wasm 后加载，配合 fuel 计量与内存上限，就能给每次调用划出确定的资源边界。这里最关键的工程要求是可复现：同样的输入必须得到同样的输出，因此要关闭对时钟与随机数的访问，或者把它们作为显式参数传入。

第三类是边缘函数。CDN 节点上同时运行许多租户的代码，冷启动直接决定体验。wasm 模块体积小、实例化快，同一租户的实例还可以复用来处理后续请求。边缘平台通常把网络能力封装成宿主函数，模块只负责请求改写、鉴权判断、响应头处理这类短逻辑。

第四类是不可信代码隔离。SaaS 产品里执行用户上传的脚本，或者安全团队分析来路不明的样本，都需要“跑了但别出事”的环境。wasm 的默认拒绝模型在这里很合适，但要注意隔离强度取决于运行时实现与宿主暴露的接口，不能因为用了 wasm 就默认安全。

反过来，几类场景目前并不合适。首当其冲的是大量系统调用：依赖 fork、epoll、mmap、procfs 的代码在 WASI 下没有对应物，移植工作量可能超过重写。依赖成熟生态库的场景也要谨慎，许多 crate 默认假设存在线程、DNS 解析与本地文件缓存，编译能过不代表运行正确。长驻服务的高性能网络 IO 同样不划算：preview1 没有 socket，宿主转发意味着额外的内存拷贝与调度开销，连接数一高就不如原生进程。需要线程并行的计算任务也受限，相关提案在 2022 年仍处于推进阶段，各运行时支持程度不一。

与容器对比：边界不同，不是替代

两者经常被放在一起讨论，但隔离的层次并不相同。容器借助命名空间与 cgroup 切分内核视图，隔离单位是进程；wasm 借助验证器与能力授予切分模块视野，隔离单位是实例。前者共享内核，后者共享宿主进程。

维度 wasm 模块 容器
隔离边界 模块与宿主接口，默认无系统调用 进程与内核视图，共享内核
启动开销 实例化通常为微秒到毫秒级 通常为百毫秒到秒级
分发体积 几十 KB 到几 MB 镜像常为几十到几百 MB
可移植性 字节码跨架构，依赖运行时 绑定内核与镜像架构
系统调用 仅 WASI 暴露的有限集合 基本完整
调试观测 工具链较新，依赖宿主导出 生态成熟，工具齐全

表中数字只是量级示意，实际取决于模块大小与主机负载。真正值得关注的是第四行与第五行：wasm 的可移植性来自“抽象掉了操作系统”，代价也正是“抽象掉了操作系统”。容器看似笨重，却保留了你熟悉的全部排障手段。

因此本文不认为 wasm 会替代容器。更现实的组合是：容器负责打包与编排一个完整的服务，服务内部嵌入运行时，用 wasm 承载租户代码或插件。容器的运维体系、网络模型、存储挂载继续生效，wasm 则把隔离粒度细化到函数一级。把两者对立起来，往往是因为把“启动快”误当成了唯一指标。

工程实践：冷启动、实例复用与可观测性

冷启动要拆成两段：编译与实例化。前者可以靠缓存编译产物消掉，后者才是每次请求的成本；多数运行时能把编译结果序列化到磁盘，重启后直接映射。

实例复用诱惑很大，但实例是有状态的：线性内存、全局变量、fd 表都会留下痕迹。稳妥的策略是“每请求一个实例，实例来自预热池”，池满时排队而不是无限创建。让不同租户复用同一实例，迟早会踩到数据残留。

限额与观测要一起设计。执行侧用 epoch 中断兜底死循环，用 fuel 约束计算量，用内存上限阻止无限分配；导入函数自身也要限流，否则模块会把压力转嫁给宿主。宿主应记录每次调用的耗时、内存峰值与失败原因，日志统一走导入函数输出，便于附上租户与调用标识。调试体验仍不如容器，常见做法是同一份逻辑在原生目标下跑单元测试，wasm 只验证 ABI 与边界行为。

小结

wasm 在服务端的价值，不在于跑得比原生快，而在于用很低的成本把不可信代码装进边界清晰的盒子。2022 年的现实是：preview1 覆盖了文件、时钟与随机数，网络与线程仍需宿主补位，组件模型与新一代 WASI 都还在推进中。选型前先问三个问题：这段代码需要多少系统调用，依赖的库能否编译到 wasm32-wasi，宿主愿意暴露哪些能力。答案清晰再落地，否则容器仍是更省心的选择。
