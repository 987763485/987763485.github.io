GitOps 工作流实践

本文属于《Docker 与 Kubernetes》第 44/51 篇
上一篇系列目录下一篇

很多团队已经能把应用打包成镜像、用 CI 跑通测试，却在“如何把变更安全地送进集群”这一步退回手工时代：有人在本地执行 kubectl apply，有人在流水线里塞一段部署脚本，集群里发生了什么只能靠翻聊天记录。本文讨论的 GitOps，是把 Git 仓库当作集群期望状态的唯一事实源，由集群内的代理持续拉取并收敛。读完之后，你应该能设计出一套可审计、可回滚、能发现漂移的仓库结构与同步流程，并知道密钥、环境晋级这些棘手环节该如何落地。本文侧重工作流与仓库治理，Argo CD 的安装与界面操作不在此展开，蓝绿、金丝雀等发布策略也另文讨论。

从“CI 里跑 kubectl apply”说起

先看一种最常见的做法：流水线构建镜像、推送到 registry，然后取一段 kubeconfig，执行 kubectl set image 或 kubectl apply -f deploy/。它在演示环境里跑得很好，规模一大就会暴露几个结构性问题。

第一，凭据扩散。集群的管理员凭据被复制到 CI 的变量里，任何一个能改流水线的人，实际上都拿到了集群的写权限。第二，状态不可追。kubectl apply 成功只代表 API Server 接受了请求，几分钟后 Deployment 是否就绪、Pod 是否在重启，流水线并不关心。第三，手动变更不可见。有人为了排查故障临时改了副本数或镜像，集群与仓库从此分叉，下一次发布又把他的修改覆盖掉，事故往往就在这种反复中产生。第四，回滚依赖重跑。想回到上一版，只能找到旧的镜像标签再跑一次流水线，而“上一次到底部署了什么”并没有一份完整的记录。

GitOps 换了一个方向：部署不再是流水线的最后一步，而是集群里一个常驻代理的工作。CI 仍然负责构建、测试、推送镜像，但它不再持有集群写权限；它只把“这次要部署的镜像摘要”写进配置仓库。集群中的 Argo CD 持续比对 Git 中的期望状态与集群中的实际状态，发现差异就同步。OpenGitOps 把这套做法归纳为四条原则：声明式、版本化且不可变、自动拉取、持续收敛。前两条说的是“怎么描述”，后两条说的是“怎么执行”。

flowchart LR
  Dev[开发者提交代码] --> AppRepo[应用仓库]
  AppRepo --> CI[CI 构建与测试]
  CI --> Registry[镜像仓库]

  ConfigRepo --> Argo[Argo CD 持续比对]

这张图里最值得注意的是箭头的方向。CI 到集群之间没有箭头，凭据链条被切断了；Argo CD 主动从 Git 和镜像仓库拉取，集群不开放入站部署接口。这就是“拉取式部署”与“推送式部署”的根本区别。

把 Git 当作唯一事实源，带来的不只是审计方便。因为期望状态是一个可以 diff 的文本，任何变更都能走 Pull Request：有人评审、有 CI 做清单校验、有提交历史可以追溯、回滚就是一次反向提交。集群的最终状态不再取决于“谁在什么时候执行了什么命令”，而取决于“仓库的某个 commit 是什么内容”。这也意味着，凡是不能用声明式描述的运维动作，都需要重新设计，或者被明确列为 GitOps 的例外。

仓库结构：应用与配置分开

实施 GitOps 的第一个决策不是装什么工具，而是代码放在哪里。这里有两个独立的问题：应用源码与部署配置是否同仓，以及多环境如何组织。把这两个问题混在一起讨论，往往会得到“什么都放一个仓库”的含糊结论。

应用仓库负责源码、Dockerfile、单元测试和 CI 配置；配置仓库负责 Kubernetes 清单、Helm values、环境参数和发布记录。分开的好处很实际。其一，提交历史的语义清晰：应用仓库的 commit 是“代码变了”，配置仓库的 commit 是“要部署什么”，排查时不用在成百上千次构建提交里找部署记录。其二，权限可以分开：能合并业务代码的人，不一定能改生产环境副本数；配置仓库可以设置更严格的 CODEOWNERS 与审批规则。其三，爆炸半径可控：配置仓库通常很小，一次误提交影响面有限，回滚也快。

也不必教条化。团队规模小、发布频率低时，单仓加 deploy/ 目录完全可行，Argo CD 只监视某个路径即可。真正要避免的是“配置散落在各个应用仓库、每个仓库一套脚本”的局面，那样无法回答“生产环境现在期望是什么”这个问题。若采用单仓，至少把部署清单放在独立顶层目录，并让 CI 只允许通过 PR 修改它。

多环境的组织方式，主流有两种：按目录和按分支。按目录是 envs/dev、envs/staging、envs/prod，每个目录一套完整的入口清单；按分支是 main 对应生产、develop 对应开发，环境差异靠合并方向体现。本文明确建议按目录。分支模型的麻烦在于：环境之间的差异变成长期分叉，修一个 bug 要往多个分支 cherry-pick；预发验证过的 commit 与生产实际部署的 commit 不是同一个，晋级过程无法用 diff 证明；更危险的是，合并错方向会把开发配置带进生产。目录模型下，一次晋级就是把镜像摘要从一个目录改到另一个目录，差异一目了然。

目录内部如何复用？Kustomize 的 base/overlay 是最轻的答案。base 放与环境无关的 Deployment、Service，overlay 只写差异：副本数、资源限额、Ingress 主机名、镜像。下面的例子把镜像固定到 digest，副本数按环境覆盖。

如果团队已经重度使用 Helm，另一条路是保留 chart、按环境准备 values 文件：values-dev.yaml、values-prod.yaml，Argo CD 在 Application 里指定 valueFiles。两种方式没有绝对优劣。Kustomize 适合“同一套清单做少量覆盖”，Helm 适合“需要参数化与版本化分发的公共 chart”。要避免的是在同一层里既用 Helm 模板又用 Kustomize 打补丁，渲染顺序与最终结果会变得难以推理。一个可维护的组合是：基础组件用 Helm chart，业务应用用 Kustomize overlay，二者在配置仓库中各自独立成目录。

无论选哪种，都要遵守一条底线：配置仓库里的清单必须是“渲染前的唯一输入”，不能依赖集群里已存在的、未被版本化的资源。若某个 ConfigMap 是手工创建后被挂载的，Git 里就没有它的定义，新集群无法从零重建，GitOps 的可复现性也就名存实亡。

Application 与 AppProject：把边界画出来

在 Argo CD 的模型里，Application 描述“把哪个 Git 路径同步到哪个集群的哪个命名空间”。它是一个自定义资源，放在 Argo CD 所在的命名空间，apiVersion 为 argoproj.io/v1alpha1。一个典型的 Application 包含三部分：source 指向仓库、修订版本与路径；destination 指向集群与命名空间；syncPolicy 描述自动同步、修剪与自愈行为。

几个字段值得展开。targetRevision 写分支名意味着跟随分支头，写 commit SHA 则完全固定；生产环境我更倾向后者，晋级时由流水线改写，避免“分支上又合并了一个提交，集群悄悄变了”。finalizers 决定删除 Application 时是否连带删除其管理的资源，生产环境应明确选择，不要依赖默认行为。prune 让 Git 中删除的资源在集群中也被删除，没有它，仓库会逐渐与集群脱节；但它也意味着一次错误的路径改动可能删掉线上对象，所以必须配合 AppProject 与审批。selfHeal 负责把手工改动纠回去，后文单独讨论。

只有 Application 还不够。默认的 default 项目几乎不设限制，任何能创建 Application 的人都能把它指向任意仓库、任意集群。AppProject 就是用来收紧这个面的：它限定允许的源仓库、允许的目标集群与命名空间、允许创建哪些集群级资源，还可以配置项目角色与同步窗口。

这里的取舍是粒度。项目太粗，等于没有隔离；项目太细，每个应用一个项目，维护成本又会反噬。较稳妥的做法是按团队或业务线划分项目，把“能去哪里”和“能用什么仓库”固定下来，再通过 RBAC 把 sync 权限授予值班人员。注意 destinations 里的命名空间支持通配符，但不要写成 *，否则项目边界形同虚设。

另一个常见误区是把所有资源塞进一个 Application。Application 是同步与健康状态的最小单位，粒度太粗会导致：一个 ConfigMap 渲染失败，整个应用变成 Degraded；一次同步要处理上千个对象，耗时且难以定位；回滚时只能整体回退。合理的拆分依据是生命周期与变更频率，例如“业务 Deployment 与 Service”一个应用，“Ingress 与证书”一个应用，“集群级 CRD 与控制器”另一个应用。拆分后可以独立同步、独立回滚，也便于把不同应用交给不同团队。

同步、自愈与同步波次

开启 automated 之后，Argo CD 的控制器会周期性拉取 Git、渲染清单、与集群比对，发现 OutOfSync 就执行一次同步。默认的轮询间隔是 3 分钟，可以通过 argocd-cm 中的 timeout.reconciliation 调整；对时效要求高的团队还会配置 Git webhook，让提交后立即触发刷新。轮询加 webhook 的组合比单纯 webhook 稳妥：webhook 丢失时，轮询仍能兜底。

自动同步里有两个容易混淆的开关。prune 决定“Git 里删掉的对象，集群里是否也删掉”。不开它，删除清单只会让对象变成孤儿，仓库与集群逐渐脱节；开了它，路径写错或渲染结果为空都可能导致批量删除，所以生产环境应配合 AppProject 的命名空间限制、对象数量告警与备份。selfHeal 决定“集群里被手工改过的对象，是否改回 Git 的样子”。它只对 Application 正在跟踪的资源生效：手工扩了副本，会被改回；手工删了 Service，会被重建；手工创建且不在 Git 里的对象，默认不会被删除，除非它与跟踪对象的归属关系被判定为多余并触发 prune。

需要注意，selfHeal 必须与 automated 一起使用，单独写没有意义。另外，它纠正的是“与 Git 不一致”，不是“与健康状态不一致”：如果 Git 里写的副本数本身就是 0，自愈会忠实地维持 0。自愈也不是万能的，被 mutating webhook 注入的边车、由 HPA 托管的副本数、由 Operator 写入的状态字段，都可能让比对结果反复摆动，这类字段应当通过忽略规则处理，而不是关掉自愈。

当应用包含几十个对象时，一次性 apply 往往不够。数据库迁移必须在应用启动前完成，CRD 必须先于自定义资源建立，命名空间必须先于其中的工作负载。Argo CD 用同步波次（Sync Waves）表达这种顺序：在资源上标注 argocd.argoproj.io/sync-wave，数值越小越先执行，默认是 0，允许负数。同一波次内的资源并发 apply，进入下一波次的条件不是“上一波已提交”，而是“上一波已健康”。

波次不是越多越好。每增加一波，就多一次健康等待与失败重试，排障时要逐波确认。实践中通常只用三到四波：基础设施（命名空间、配额）、CRD 与控制器、业务工作负载、收尾任务。若同步卡在某一波，Application 会停留在 Progressing，此时应查看具体哪个对象没有达到健康状态，而不是反复点击同步。

与波次相邻的是资源钩子（Resource Hooks）。钩子用 argocd.argoproj.io/hook 标注，分为 PreSync、Sync、PostSync 与 SyncFail，分别在同步前、同步中、同步后与失败时运行。钩子资源不会被当作应用的常驻状态，执行完是否保留由 hook-delete-policy 决定。最典型的用法是把数据库迁移放进 PreSync 的 Job，把冒烟测试放进 PostSync 的 Job。

钩子有三个坑。第一，失败会阻断同步：PreSync 的迁移 Job 失败，后面的工作负载不会更新，这是期望行为，但要把日志暴露给值班人员。第二，Job 重跑要幂等：BeforeHookCreation 会在下次执行前删掉旧 Job，迁移脚本自身仍需能重复执行。第三，不要把长任务放进钩子，它有超时限制，而且会占住整个同步流程。

最后是健康状态判定。Argo CD 为 Deployment、StatefulSet、Service、Ingress 等内置资源提供了健康检查规则，例如 Deployment 要看副本是否可用、滚动更新是否完成；对自定义资源，则可以在 argocd-cm 中用 Lua 编写 resource.customizations.health。健康状态与同步状态是两个维度：一个应用可以既是 Synced 又是 Degraded，表示清单已经提交给集群，但工作负载没有真正就绪。发布门禁、波次推进、通知告警都依赖健康判定，所以为自研 CRD 补上一段健康脚本，往往比多写几行部署文档更有价值。

漂移：如何发现，何时纠正

漂移指集群实际状态与 Git 期望状态不一致。它不一定是坏事，但一定是需要解释的事。常见来源包括：有人用 kubectl edit 临时改配置；HPA 根据负载改了副本数；准入控制器给 Pod 注入了边车或默认值；Operator 持续写入自己的状态字段；以及上一次同步只成功了一部分。前三类是“人”或“平台”造成的，后两类是系统行为，处置方式完全不同。

发现漂移主要靠三种手段。其一是 Application 的同步状态与 argocd app diff，后者会列出具体字段的差异，适合定位；其二是通知控制器，把 OutOfSync、Degraded、同步失败推送到 IM 或工单系统；其三是集群侧的 kubectl diff，用于在不经过 Argo CD 的情况下核对某份清单。只盯着 CI 绿灯是不够的，部署之后的状态必须有人持续看。

发现之后要不要自动纠正，取决于环境与变更性质。开发环境可以全自动，让集群始终贴近 Git；生产环境有两种常见策略：全自动自愈加告警，或者关闭自愈、只告警、由值班人员确认后同步。前者收敛快，但一次错误的 Git 提交会迅速扩散；后者更稳，却依赖人的响应速度。折中的做法是按应用分级：无状态服务自动自愈，有状态服务与核心支付链路手动确认。

不是所有差异都该纠正。对于控制器拥有的字段，正确做法是让双方不争抢：要么在 Git 中不声明该字段，要么配置忽略规则。下面的例子忽略由 HPA 管理的副本数，只关注镜像与资源限额。

忽略规则是双刃剑。忽略 /spec/replicas 之后，若有人手工把副本改成 0，Argo CD 不会再报差异；忽略 Secret 的某个键，等于放弃对该键的漂移检测。因此每条规则都要写明理由与负责人，并定期清理。比“永久忽略”更好的做法是“临时例外”：在工单中记录手工变更的原因、范围与过期时间，到期后要么回滚，要么把变更补进 Git，让例外重新变成受控状态。

还有一种隐蔽的漂移是“孤儿资源”：对象带着 Application 的跟踪标签，却已不在 Git 清单里。开 prune 时它们会被删除；不开时它们会一直占着资源，甚至继续接收流量。定期用 argocd app resources 核对对象列表，或者对集群做一次“从空集群重建”的演练，能暴露这类问题。后者听起来激进，却是验证 Git 是否真的包含全部期望状态的最好办法。

密钥：加密入库还是引用外部

只要讨论 GitOps，就一定会有人问：“Secret 怎么办？”第一个必须澄清的事实是：Kubernetes Secret 的 base64 只是编码，不是加密。把数据库密码、API Key 以 Secret 清单提交到 Git，等同于把凭据发布给所有能读仓库的人，而且会留在提交历史里，删除文件也无法抹掉。轮换密钥的成本，往往比一开始就选对方案高得多。

主流方案有两条路。第一条是“加密后入库”，以 Sealed Secrets 为代表：集群里运行一个控制器，持有一对密钥；开发者用 kubeseal 和公钥把 Secret 加密成 SealedSecret，密文可以安全提交；控制器在集群内解密，生成普通的 Secret 供工作负载使用。Git 里始终只有密文，仓库泄露不等于凭据泄露。

Sealed Secrets 的优点是自包含：只要 Git 和集群私钥还在，就能从零恢复，适合灾备与离线环境。它的代价也很明确。第一，私钥必须备份，丢失私钥意味着所有密文永久无法解密，控制器虽然支持多密钥并存以完成轮换，但备份责任在运维侧。第二，作用域要选对：默认的 strict 作用域把密文绑定到命名空间与名称，换一个环境或改个名字就解不开；namespace-wide 与 cluster-wide 更灵活，但泄露后的影响面更大。第三，跨集群晋级不直接：每个集群的密钥对不同，同一份密文不能同时用于开发与生产，需要分别加密，或者让多个集群共享密钥，而后者会削弱隔离。第四，密钥轮换后要重新加密并提交，流程必须纳入常规演练。

第二条是“只存引用”，以 External Secrets Operator 为代表：Git 里放 ExternalSecret，声明“从哪个密钥管理系统取哪个键”，控制器用集群身份访问 Vault 或云厂商的密钥服务，把值同步成 Kubernetes Secret。密文根本不进 Git，轮换由外部系统统一完成，审计也集中在那一侧。

这条路的优点是密钥生命周期管理成熟：轮换、审批、审计、租户隔离都能复用现有平台。代价是引入了运行时依赖：集群必须能访问外部密钥服务，身份认证要配置正确（例如工作负载身份），控制器故障时新 Pod 可能拿不到 Secret；灾备场景下，如果外部系统不可用，仅凭 Git 无法重建环境。它还把“集群需要什么权限”这个问题从 Git 转移到了身份配置上，配置错误可能导致跨环境读到不该读的密钥。

两者的取舍可以归纳为：若你希望 Git 是完整的灾难恢复源，且集群数量不多、密钥规模有限，Sealed Secrets 更简单；若组织已有集中式密钥管理、合规要求统一轮换与审计，External Secrets 更合适。混合使用也常见：业务密钥走 External Secrets，引导用的少量凭据（例如访问密钥服务的身份）用 Sealed Secrets 加密入库。无论选哪种，都要在 CI 里加一道明文扫描，阻止 .env、kubeconfig 与含 data: 明文的 Secret 清单被提交；同时限制谁能解密、谁能读取外部密钥，避免“解决了 Git 泄露，却留下更大的权限口子”。

环境晋级：一次构建，逐级提升

GitOps 的晋级模型与“每个环境重新构建一次”截然不同：镜像只构建一次，测试通过后记录其 digest，之后开发、预发、生产部署的都是同一个不可变产物。用 tag 而不锁 digest，会留下一个隐患：v1.2.3 这样的标签可以被覆盖，今天部署的和昨天部署的可能不是同一份二进制。digest 是内容的哈希，天然不可变，也让“预发验证过的就是生产要上的”这句话可以被证明。

流水线的职责到“改配置仓库”为止。构建、扫描、推送镜像，取得 digest，然后在配置仓库中修改目标环境的镜像引用，开一个 Pull Request。下面的脚本省略了错误处理与鉴权细节，重点在顺序。

Pull Request 是晋级流程的核心，而不是形式。它把“要变更什么”变成可评审的 diff：镜像从一个 digest 换成另一个，副本数、环境变量、Ingress 是否被误改，都在评审者眼前。仓库侧配合 CODEOWNERS，让生产目录必须由指定人员批准；CI 侧至少跑三道检查：kustomize build 或 helm template 能否渲染、清单能否通过 schema 校验（例如 kubeconform）、以及策略检查（禁止 latest、必须设置资源限额、必须非 root）。有条件时还可以让 CI 用只读凭据执行 argocd app diff，把“合并后会发生什么”提前展示在 PR 里。

生产和预发不应完全同权。常见配置是：开发环境自动同步，预发自动同步但保留人工回滚按钮，生产关闭自动同步、合并后由值班人员在发布窗口内手动触发，或者开启自动同步但用 AppProject 的 syncWindows 限制允许同步的时间段。审批与执行分离，既满足变更管理要求，也避免“合并即上线”带来的惊吓。

flowchart LR
  Build[构建一次并记录 digest] --> StagePR[预发环境 PR]
  StagePR --> Check[渲染与策略检查]
  Check --> StageSync[预发同步与验证]
  StageSync --> ProdPR[生产环境 PR]
  ProdPR --> Approve[CODEOWNERS 审批]
  Approve --> ProdSync[发布窗口内同步]
  ProdSync --> Observe[观察指标与日志]
  Observe -->|异常| Revert[revert 提交并同步]

回滚同样走 Git。发现异常时，对晋级提交执行 git revert，开 PR 合并，Argo CD 会把集群带回上一个 digest。这比在 UI 里点“回滚”更可取，因为 UI 回滚只改变集群状态，Git 仍指向新版本，下一次自愈或同步又会把故障版本带回来。Argo CD 的历史回滚在事故止血时可以用，但事后必须补一次 Git 提交，让事实源与集群重新一致。回滚演练要覆盖数据库迁移：如果新版本已经执行了不兼容的 schema 变更，回滚镜像并不够，这也是把迁移设计成向后兼容的原因。

多集群分发是同一套逻辑的延伸。集群通过 argocd cluster add 注册后，Application 的 destination 可以指向集群名或 API Server 地址，每个集群、每个环境各一个 Application，指向配置仓库中对应的目录。AppProject 的 destinations 列出允许的集群与命名空间，防止一个应用被误指到未授权的集群。跨集群晋级时，保持 digest 不变，只改目标目录；不要让每个集群各自构建，否则“同一版本”就无从谈起。集群数量多时，Application 清单本身也可以由脚本或模板生成，但生成结果仍要提交到 Git，而不是在运行时动态拼装，否则审计链会断在生成器里。

落地路线与常见反模式

GitOps 不适合一次性全量切换。较稳的路径是三步：第一步只读接入，安装 Argo CD、连接仓库、为现有应用创建 Application，但关闭自动同步，先观察 diff，确认 Argo CD 渲染出的清单与线上一致；第二步在开发环境开启自动同步与自愈，暴露清单缺失、密钥管理、健康检查的问题；第三步再让生产走 PR 晋级与人工触发，逐步收紧权限。每一步都应留下回退方案，尤其是 prune，首次开启前先做备份与对象清单核对。

常见的反模式值得单独列出。把 kubeconfig 放进 CI 变量，再用 kubectl apply 部署，只是给旧流程换了个名字；用 latest 标签并依赖 imagePullPolicy: Always，无法回答“线上到底是哪一版”；按环境拉长期分支，合并方向一错就把开发配置带进生产；为了“先上线”手工改集群却不回写 Git，下一次同步把修复覆盖，事故复发；对所有差异都加忽略规则，漂移检测名存实亡；以及把上百个对象塞进一个 Application，任何一个小错都让整个应用无法同步。这些问题都不是工具造成的，而是流程约定缺失造成的。

评估落地效果时，可以盯几个简单指标：处于 OutOfSync 超过一定时间的应用数量、同步失败率与平均恢复时间、从合并到生产生效的时长、以及“从空集群重建一套环境”能否成功。前三个反映日常运行，最后一个反映 Git 是否真的完整。指标不必复杂，但要定期看，否则 GitOps 很快会退化成“有一个 Argo CD 界面”的摆设。

小结

GitOps 的价值不在于多了一个部署工具，而在于把集群状态变成可评审、可追溯、可复现的代码。落地时先定仓库边界：应用与配置分离、环境按目录组织、用 base/overlay 或 Helm values 表达差异；再用 AppProject 收紧应用能去的仓库与集群，用同步波次与钩子解决顺序问题。漂移要能被发现，也要有明确的纠正策略与例外流程；密钥要么加密入库，要么只存引用，绝不能提交明文。晋级时构建一次、锁定 digest、以 PR 承载变更、以 revert 完成回滚，多集群只是同一 digest 的多次分发。把这些约定写进团队规范，比调任何参数都重要。
