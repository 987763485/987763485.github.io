Rust 模式匹配实战

本文属于《Rust 学习路线》第 6/68 篇
上一篇系列目录下一篇

模式匹配是 Rust 里出现频率最高的语法之一，从 match 到 if let，再到函数参数与 let 绑定，模式几乎无处不在。很多初学者能看懂别人的代码，轮到自己写时却总是在所有权和穷尽性检查上卡壳。本文以 Rust 1.58 为准，把常用模式逐一拆开讲，并配上可以直接运行的小例子。

需要先说明边界：本文讨论的是模式本身的写法与语义，错误处理的策略留给专门的文章；文中的代码都在 2021 edition 下编写，let-else 这类尚未稳定的语法只会作为未来方向提一句，不会出现在可运行示例里。

match 的基本结构与穷尽性

match 是 Rust 模式匹配的主干，它的形状很固定：一个待匹配的值，后面跟若干个分支，每个分支由模式和表达式组成，分支之间用逗号分隔。

这段代码里，0、1 是字面量模式，_ 是通配符模式。编译器要求所有可能的值都被覆盖，这就是穷尽性检查。如果去掉 _ 分支，编译会直接失败，报错大意是“i32 的非穷尽模式，未覆盖的值如 2”。这个检查发生在编译期，不需要运行时兜底，也不会因为漏写分支而在线上抛异常。

穷尽性检查对枚举尤其严格。只要枚举新增了一个变体，所有没有通配符兜底的 match 都会立刻编译失败，迫使开发者处理新情况。这正是 Rust 鼓励使用枚举建模状态的原因：遗漏在编译期暴露，而不是等到运行时。

另外，match 本身是表达式，每个分支的求值结果类型必须一致。如果分支体只是执行动作、不产生值，就用分号或花括号把它变成 ()，各分支仍然要对齐，否则编译器会指出类型不匹配。

字面量、范围与通配符

字面量模式匹配具体的值，包括整数、字符、字符串字面量、布尔值等。范围模式用 ..= 表示闭区间，适合处理连续区间；要注意 .. 在模式里另有用途，表示忽略剩余部分，不能拿它来表示半开区间。

u8 的取值范围是 0 到 255，上面只覆盖了 0 到 100，所以仍然需要 _ 兜底。范围模式只能用于字符与整数类型，且上下界必须是常量。字符也可以用范围，例如 'a'..='z'，这在解析器里很常见。

通配符 _ 匹配任何值但不绑定，它不会移动所有权，也不会产生未使用变量的警告。与之相对，用一个普通变量名接住值会绑定并可能移动，这一点在后面讲绑定时会展开。如果只是想让编译器闭嘴又不想绑定，_ 永远是最省事的选择。

绑定与 @

有时候既要判断值落在某个范围，又要在分支体里使用这个值，这时用 @ 把模式绑定到变量上。

n @ 0..=12 的意思是：先判断 age 是否落在 0 到 12，如果是，把整个值绑定给 n。注意绑定的是被匹配的值本身，不是范围的副本。对于 Copy 类型这样写毫无负担；对于非 Copy 类型，绑定会涉及移动，后面讲引用时会专门讨论。

@ 也可以和解构组合，例如在枚举分支里同时拿到整个变体和内部字段。写的时候把 @ 放在变量名和子模式之间，子模式越复杂越建议加括号，避免优先级带来的歧义。

解构元组、结构体、枚举与嵌套

模式不仅能判断一个值，还能把它拆开。元组模式按位置对应，let (x, y) = (1, 2) 是最常见的写法；在 match 里同样可以逐位匹配。

结构体模式按字段名对应，没有写出的字段必须用 .. 补齐。字段顺序无所谓，名字必须写对，否则编译不通过。

这里的 user 是引用，绑定出来的 name 也就自动是 &String，不需要额外加 &。.. 可以放在字段列表的开头、中间或末尾，表示“其余字段一概不管”。对于元组，(first, .., last) 这种写法能忽略中间若干项，适合处理长度已知但只关心两端的场景。

枚举解构是 Rust 里用得最多的形式。每个变体对应一个模式，携带的数据既可以是命名字段，也可以是元组字段。

模式可以任意嵌套。Some((x, y))、Message::Move { x, y }、Ok(User { name, .. }) 都是合法写法，编译器会一层层对照结构。嵌套越深，模式越长，这时更应该考虑先解构外层、再用局部变量承接内层，或者把分支体抽成函数。可读性往往比少写一行更重要。

守卫、| 与匹配顺序

有些条件无法用模式本身表达，例如“这个数大于零”或者“两个坐标相等”。if 守卫写在模式和 => 之间，可以用到模式里绑定的变量，也可以引用外部变量。

守卫的关键在于：它不参与穷尽性判断。编译器会把带守卫的分支视为可能失败，因此即使模式覆盖了全部取值，仍然需要兜底分支。上面的 _ 不能省，否则编译报错。另一个容易忽略的点是，守卫在模式匹配成功之后才求值，同一个值可能依次经过多个分支的守卫，只有全部不成立时才会落到后面的分支。

| 把多个模式合并到同一个分支，适合处理几个离散取值。

如果分支需要绑定变量，那么每个备选模式都必须绑定同名、同类型的变量，否则编译器不知道分支体里该用哪个值。范围模式和 | 可以混用，例如 'a'..='z' | 'A'..='Z' 表示所有字母。

match 按书写顺序自上而下尝试，第一个匹配成功的分支生效，后面的分支不再求值。因此具体的模式要写在前面，宽泛的模式写在后面。把 _ 放在第一行，后面的分支就永远没有机会执行，编译器会给出“不可达模式”的警告。这个顺序规则也意味着，分支的排列本身就是逻辑的一部分，不能随意调整。

引用、ref 与 mut 的绑定

匹配引用时，Rust 有一套默认的借用规则：如果被匹配的值是引用，模式里又没有显式写 &，那么绑定出来的变量默认也是引用，不会把底层数据移走。

这条规则让大多数读取场景写起来很轻，不需要到处补 &。但它只解决“借”的问题，不解决“值被移走”的问题。直接对一个拥有所有权的结构体做匹配，绑定时默认按值移动。

如果去掉 ref，name 会接管 user.name 的所有权，之后不能再把 user 当作一个整体使用，只能访问没有被移动的其余字段，这就是所谓部分移动。要避免这种局面，可以匹配 &user，也可以用 ref 明确表达“我只是借用”。

mut 出现在模式里时，修饰的是绑定本身，而不是被匹配的值。Some(mut s) 表示把值移进一个可变的局部变量，随后可以修改它；ref mut s 则表示对原值做可变借用，修改会反映到原变量上。

切片模式是解构引用的一类特殊形式。它按长度和位置匹配一个切片，[]、[a]、[a, b] 对应确定的长度，[first, .., last] 表示至少两个元素，.. 吸收中间任意多个。

这里的 first 和 last 是 &i32，因为 items 本身是引用，默认绑定模式延续到了切片内部。若想把剩余部分整体绑定出来，用 rest @ ..，rest 的类型是 &[i32]，可以继续传递或递归处理。切片模式让“取头、取尾、判断长度”不再依赖下标和边界检查，意图也更清楚。

条件式匹配：if let、while let 与 matches!

match 适合需要覆盖所有情况的场合；只关心其中一个分支时，if let 更轻。它只接受一个模式和一个分支，不要求穷尽，也可以带 else。

这里同样体现了默认借用规则：匹配 &nickname，绑定出来的是引用，原值在 if let 结束后仍然可用。若写成 Some(name) = nickname，name 会拿走 String，后续就不能再使用 nickname。

while let 把同样的判断放进循环：只要模式匹配成功就继续执行循环体，失败时退出。它特别适合不断从容器里取值的场景。

pop 返回 Option<i32>，栈非空时得到 Some，循环继续；栈空时得到 None，循环自然结束。整个过程不需要手写下标，也不会越界。

这里要区分可反驳模式与不可反驳模式。let 绑定要求模式一定匹配，let (a, b) = (1, 2) 合法，而 let Some(x) = opt 会编译失败，因为 opt 可能是 None。match 的每个分支、if let 与 while let 的模式则允许失败。至于 let ... else，截至 Rust 1.58 尚未稳定，无法让 let 在模式失败时走 else 分支；目前仍要借助 if let 加提前返回，或直接用 match。等它稳定后，这类代码会更紧凑，本文不展开。

matches! 宏把“判断是否匹配”压缩成一个布尔表达式，适合放在 if 条件或迭代器过滤里。

它的展开结果就是一个只有 true、false 两个分支的 match，所以模式写法与 match 完全一致。需要注意，传给 matches! 的表达式按值求值，非 Copy 类型可能被移动；只做判断时传引用更稳妥。

Option 与 Result 的匹配是日常代码的主角。读取值时用 match 显式处理两个分支，或者用 if let 只关心成功的一侧；判断某个枚举是否属于某几个变体时，matches! 往往比手写 match 更直白；只是判断 Option 是否为空，is_some 与 is_none 更直接。嵌套的 Some(Ok(v))、Err(ParseError { .. }) 也能一层层拆开。错误如何传播、何时该 panic，属于错误处理策略，本文不展开。

可读性、性能与常见坑

先说性能。match 不是运行时库函数，编译器会把它展开成条件分支，对整数和字符这类连续取值还可能生成跳转表。它是否比一串 if 更快，取决于模式形状、分支数量和优化级别，不能一概而论。本文的建议是：先按语义选择 match 或 if let，让代码结构清晰；确实遇到热点，再用基准测试判断，而不是凭直觉替换。

可读性方面，有几个经验值得记住。分支体超过几行就抽成函数；嵌套匹配超过两层，先解构外层再用局部变量；绑定名要能说明含义，不要一路 a、b、c；_ 表示刻意忽略，_name 仍会绑定并可能移动，二者不要混用。分支顺序按“特殊到一般”排列，读代码的人一眼就能看出优先级。

常见坑里，排第一的是移动后使用。按值匹配一个拥有所有权的值，绑定会把字段移走，之后原值只能部分访问，甚至完全不可用。

需要保留原值就匹配 &maybe，或者在模式里用 ref。第二个坑是守卫中的副作用。守卫在模式匹配后求值，可能因为条件不成立而落空，分支体根本不执行；如果把计数、日志、网络请求塞进守卫，就会产生“看起来没进分支，副作用却发生了”的困惑。守卫应尽量只做纯判断，把动作放进分支体。

第三个坑是穷尽性被通配符掩盖。_ 能让代码通过编译，但枚举新增变体时也不会提醒你。对于会持续演进的枚举，宁可逐个列出变体，让编译器在新增时报错；只有确实不关心其余情况时，才用 _ 收尾。if let 同样只处理一个变体，其余变体被静默忽略，用在状态机上要格外小心。

第四个坑是匹配顺序。范围重叠、具体模式与宽泛模式混排时，第一个命中的分支获胜，后面的分支可能永远不可达。第五个坑是引用层级。Option<&T> 与 &Option<T> 是两种不同的类型，写 Some(x) 时绑定到的都是 &T，但来源并不相同；如果误以为拿到的是 T，后续调用就会报类型错误。拿不准时先让编译器提示类型，再决定要不要解引用。此外，结构体模式里的 .. 会忽略新增字段，编译不会报错，这是便利，也是需要团队约定的地方。

小结

模式匹配的核心，是把“判断形状”和“取出数据”合并成一次表达：match 负责穷尽，if let、while let 负责单点，matches! 负责布尔判断。写模式时始终关注三件事：值有没有被移动、引用处在哪一层、分支顺序是否覆盖了真实情况。

实践上，优先匹配引用或使用 ref，让数据在匹配后仍然可用；枚举分支尽量写全，把新增变体交给编译器提醒；守卫保持无副作用，复杂逻辑放进分支体。把这些习惯固定下来，模式匹配就会从“看得懂”变成“写得稳”。
