服务网格零信任落地

本文属于《Docker 与 Kubernetes》第 37/51 篇
上一篇系列目录下一篇

零信任这个词已经被讲了很多年，但落到 Kubernetes 集群里，很多团队仍然停留在“给 Ingress 加个 TLS、给 Pod 配个 NetworkPolicy”的阶段：服务之间调用依旧是明文 HTTP，身份靠调用方自觉传递，一旦某个工作负载被攻破，横向移动几乎没有阻力。服务网格之所以和零信任天然契合，是因为它把“身份”从应用代码里抽出来，交给平台统一签发和验证。

本文以 Istio 1.11 与 1.12 为准，讨论如何把零信任的四条原则映射到网格的具体配置上：工作负载身份如何生成、mTLS 如何从 permissive 迁移到 strict、PeerAuthentication 与 AuthorizationPolicy 各自负责什么、JWT 如何接入终端用户身份，以及策略不生效时该怎么排查。读完之后，你应该能画出自己集群的信任链路，并按步骤把默认放行的东西逐个收紧。

零信任原则在网格中的映射

零信任的核心主张可以压缩成一句话：不因为请求来自内网就信任它，每一次访问都要重新验证。NIST SP 800-207 把这一思想拆成若干原则，其中与网格关系最紧密的是身份、策略决策点与策略执行点。服务网格恰好提供了后两者的落点：控制面负责下发策略，Sidecar 负责在数据面执行。

第一条原则是身份为中心。传统边界安全用 IP 和网段标识“谁”，但在容器环境里 IP 随 Pod 重建而漂移，网段也无法区分同一节点上的不同工作负载。网格改用工作负载身份，把身份绑定到 Kubernetes ServiceAccount 上，再由控制面签发短期证书。这样即使攻击者拿到了某个 IP，也无法冒充原来的服务。

第二条是持续验证。身份不是登录一次就长期有效的通行证，而是每次连接都要重新校验。mTLS 握手时双方交换证书并验证链，连接建立后证书到期即失效，配合短周期的证书轮换，可以把“凭证泄露”的时间窗口压缩到很小。

第三条是最小权限。默认拒绝、按需放行，并且授权判断要基于身份、命名空间、方法等语义信息，而不是粗粒度的网络位置。Istio 的 AuthorizationPolicy 正是为此设计的，它让“哪个服务账户可以以哪个方法访问哪个路径”成为可声明、可审计的规则。

第四条是假设网络已被突破。这条原则决定了架构的默认姿态：不假设集群内网是可信区，不假设 Sidecar 之间的流量天然安全，也不假设入口是唯一的攻击面。出口同样要管，因为数据外带往往走的是出方向。

把这四条串起来，就得到一条完整的信任链路：工作负载拿到身份，身份通过 mTLS 在每次连接中被验证，验证结果作为授权决策的输入，授权策略再按最小权限收敛。下面这条简图概括了本文要讨论的路径。

  B --> C[Sidecar 间 mTLS]
  C --> D[PeerAuthentication 定义认证模式]

  E --> F[入口与出口边界]

工作负载身份：SPIFFE ID 与服务账户

零信任的第一块基石是身份。Kubernetes 用 ServiceAccount 表示工作负载身份，但 SA 本身只是一份挂载到 Pod 里的令牌，主要用于访问 API Server；它既不直接参与服务间通信，也无法阻止同一命名空间里另一个 Pod 借用同一份令牌。Istio 在这一层之上做了转换：把“命名空间 + 服务账户”映射成 SPIFFE ID，格式固定为 spiffe://<trust domain>/ns/<namespace>/sa/<service account>。默认信任域是 cluster.local，因此 default 命名空间下的 orders 服务账户会得到 spiffe://cluster.local/ns/default/sa/orders。

这个身份不是应用自己声明的，而是平台根据 Pod 的 serviceAccountName 推导出来的。攻击者即使知道目标服务的 DNS 名称和端口，只要拿不到对应私钥，就无法在 mTLS 握手中冒充它。这一点比“给服务起个名字、在请求头里带一个 token”要可靠得多，因为后者完全依赖调用方自觉。

证书的签发链路值得展开。Pod 启动时，注入的 istio-agent 会在本地生成私钥，然后用投射到容器里的 ServiceAccount Token 向 istiod 证明“我是这个命名空间下的这个服务账户”，并提交证书签名请求。istiod 内的 CA 组件校验身份后签发证书，证书的 SAN 就是上面那个 SPIFFE ID。私钥始终留在 Pod 内，控制面只负责签名，不保存私钥。Envoy 通过 SDS 动态拿到证书，轮换时无需重启进程。

负责签发的组件在早期版本里叫 Citadel，从 Istio 1.5 起已经并入 istiod，所以现在看到 istiod 的日志里有 citadel 字样不必奇怪，那只是历史命名。签发出来的工作负载证书默认有效期是 24 小时，由 istio-agent 在到期前主动续签；这个短周期是零信任“持续验证”的具体体现，凭证即使泄露，可利用窗口也很有限。

mTLS 的模式与迁移路径

mTLS 同时解决两个问题：通道加密，以及双向身份认证。普通 TLS 只让客户端验证服务端，mTLS 要求双方都出示证书，因此服务端也能确认“调用我的是哪个工作负载”。在网格里，这个确认结果会作为属性传给授权引擎，成为后续策略判断的输入。

Istio 用 PeerAuthentication 描述“入站连接接受什么级别的认证”。它有三种模式：PERMISSIVE 同时接受明文和 mTLS，STRICT 只接受 mTLS，DISABLE 关闭该工作负载入站的 mTLS 处理。没有配置任何 PeerAuthentication 时，网格默认是 permissive，同时启用自动 mTLS：sidecar 会根据目标端是否注入了 sidecar 来选择连接方式，目标在网格内就用 mTLS，不在网格内就退回明文。自动 mTLS 解决了“能不能通”的问题，但也意味着，只要不显式收紧，明文通道会一直存在。

因此迁移的第一步不是改配置，而是观测。保持 permissive，通过指标查看每个服务收到的连接里 mTLS 的占比，找出仍在发明文流量的调用方。常见的“钉子户”有几类：集群外的虚拟机或旧系统、直接访问 Pod IP 的运维脚本、没有注入 sidecar 的 Job，以及某些绕过 Service 的直连。把它们逐个迁入网格、改走入口网关，或者确认可以下线，再进入下一步。

PeerAuthentication 与 AuthorizationPolicy 的分工

这两个资源经常被混为一谈，其实它们回答的是不同问题。PeerAuthentication 回答“进来的连接是否必须使用 mTLS”，只处理传输层身份，不看请求内容；AuthorizationPolicy 回答“这个已经通过认证的身份，能不能执行这个操作”，可以细到方法、路径和请求头。前者是门槛，后者是门内的权限表。

完整的判断顺序是三层。第一层是传输层认证，由 PeerAuthentication 决定是否接受连接、对端证书是否可信；第二层是请求层认证，由 RequestAuthentication 校验 JWT，把终端用户身份附加到请求上；第三层是授权，由 AuthorizationPolicy 根据前两层产出的身份属性做放行或拒绝。任何一层缺失，后面的判断都会失去依据。比如没有开启 mTLS 时，授权规则里的 principals 取不到值，基于身份的规则自然匹配不上。

授权策略的默认语义

理解默认语义比记住语法更重要。第一，如果一个工作负载没有被任何 ALLOW 策略选中，它的请求默认全部放行；这不是“默认拒绝”，而是“没有策略就没有限制”。第二，一旦有 ALLOW 策略选中了某个工作负载，该工作负载就进入隐式默认拒绝状态，只有命中规则的请求才会放行。第三，DENY 策略的优先级高于 ALLOW，且不能被 ALLOW 覆盖，适合用来封死少数高危操作。

这就解释了一个常见现象：有人加了一条“只允许 A 访问”的策略，结果 B 也被拒绝了，于是误以为策略写错；实际上这是 ALLOW 的隐式默认拒绝在起作用。反过来，只加 DENY 策略时，未被 DENY 命中的流量仍然按默认放行处理，安全性完全取决于 DENY 覆盖得够不够全。

如果确实要“先拒绝所有，再逐条开口”，可以放一条空规则的 ALLOW 策略。它的 spec 为空，表示选中范围内没有任何请求能命中，于是全部拒绝：

JWT 与终端用户身份

mTLS 证明的是“调用方是哪个工作负载”，它回答不了“这次请求背后是哪个用户”。只要前端服务被攻破，攻击者就能借用它的合法身份调用后端，因此面向终端用户的接口还需要一层用户身份。Istio 用 RequestAuthentication 校验 JWT，把校验结果转换为 requestPrincipals 和 claims，供 AuthorizationPolicy 使用。

RequestAuthentication 的定位需要说清楚：它只负责“如果请求带了 JWT，就验证它是否由可信签发方签发、是否过期、受众是否匹配”，并不会因为请求没带 JWT 就拒绝。校验失败会返回 401，但没有令牌的请求会照常通过认证层，只是没有 requestPrincipal。这意味着单独部署 RequestAuthentication 几乎不产生访问控制效果，必须配合要求 requestPrincipals 非空的授权策略，才真正实现“必须登录”。

还有两个实践细节。其一，入口网关校验过 JWT 之后，原始令牌默认不一定继续向后传递，如果后端也要做细粒度授权，需要显式保留令牌并让后端再次校验，或者把用户身份转换成受控的请求头，但后者必须确保该请求头在入口处被覆盖，不能由外部伪造。其二，JWT 与 mTLS 是互补关系而非替代关系：JWT 保护的是用户到入口这一段，mTLS 保护的是入口到后端、后端到后端这一段，两者都到位，信任链才是连续的。

入口与出口的信任边界

入口网关是外部流量进入网格的唯一合法通道，也是信任转换发生的地方。外部用户使用浏览器或移动端支持的 TLS，网关终止这段 TLS 后，以工作负载身份重新发起 mTLS 连接访问后端。这样后端看到的是一个明确的服务身份，而不是一个来源 IP；同时后端不需要暴露在集群外，也不必自己处理公网证书。

网关自身的身份同样来自 ServiceAccount。默认安装下是 istio-system 里的 istio-ingressgateway，因此授权策略里可以用 cluster.local/ns/istio-system/sa/istio-ingressgateway 精确指定“只允许入口网关访问”。这比按命名空间放行更可靠，因为它把“从网关进来”和“同命名空间内其他 Pod 直接调用”区分开了。

入口侧的配置重点有三个。第一，用 Gateway 的 credentialName 引用证书，启用 TLS 终止，避免 PASSTHROUGH 把解密责任推给每个应用。第二，把 RequestAuthentication 和入口级的 AuthorizationPolicy 一起放在网关上，先挡住无效令牌和明显的越权请求，减少后端压力。第三，确认没有旁路：NodePort、LoadBalancer 类型的业务 Service、以及直接访问 Pod IP 的调试端口，都可能绕过网关，需要靠 NetworkPolicy 和网络 ACL 封掉。

出口方向常被忽略，但数据外带恰恰多发出方向。默认情况下，sidecar 对未知外部主机的处理取决于 outboundTrafficPolicy：ALLOW_ANY 会放行任意外部域名，REGISTRY_ONLY 只允许注册过的服务。生产环境应使用后者，把外部依赖显式登记为 ServiceEntry：

入口与出口都收紧之后，信任边界才形成闭环。只做入口，攻击者拿下 Pod 后仍可把数据发到任意地址；只做出口，外部请求仍可绕过网关直达工作负载。两边都要有“默认拒绝”的姿态，并且都用身份而不是 IP 来描述允许的对象。

信任根、证书轮换与策略排查

网格内所有证书都锚定到同一个信任根。默认安装使用自签名根证书，有效期十年，够用但不适合作为长期方案：根私钥一旦泄露，整个网格的信任基础就没了，而且默认根证书由 istiod 自动生成，难以纳入企业 CA 的审计体系。生产环境通常改用插件式 CA，把根证书与中间证书以 cacerts Secret 的形式提供给 istiod，Secret 中需要包含 ca-cert.pem、ca-key.pem、root-cert.pem 和 cert-chain.pem 四个文件。

多集群场景要额外考虑信任域。两个集群如果使用不同的信任域，默认互不信任；可以配置信任域别名，把对方的信任域加入白名单，也可以统一使用同一个根和同一个信任域。前者改动小，后者模型更简单，选择取决于组织边界：跨公司协作通常保留独立信任域，用别名显式授权；同一公司内的多集群则更适合共享根。

工作负载证书的轮换是自动的，但自动不等于可以不管。istio-agent 在证书到期前发起续签，Envoy 通过 SDS 热加载新证书，已有连接不会中断。真正需要监控的是两条链路：一是 istiod 的可用性，如果它宕机时间超过工作负载证书的剩余有效期，新连接会因为无法完成握手而失败，已有连接在关闭前仍可继续；二是根证书与中间证书的到期时间，它们的周期以年计，最容易在人员更替后被遗忘。istiod 暴露了证书到期时间相关的指标，配合 istioctl proxy-config secret 的抽查，可以覆盖这两类风险。

轮换根证书比轮换工作负载证书复杂得多，因为新旧根之间必须有一段重叠信任期。基本思路是先让所有信任包同时包含新旧根，确认全网生效，再切换签发证书，最后移除旧根。多集群、多信任域时，各集群的推进节奏必须协调，任何一方提前移除旧根都会造成跨集群调用失败。

策略生效与排查

策略不生效时，先判断问题出在哪一层，不要一上来就改 YAML。TLS 握手失败通常表现为连接重置、503 且响应标志为 UF，常见原因是服务端已设为 STRICT 而客户端仍在发明文，或者证书校验失败。401 基本落在 JWT 层：令牌缺失时未必报错，令牌过期、签名不对、受众不匹配才会返回 401。403 则是授权层拒绝，响应体常带有 RBAC: access denied。

老资料里经常出现 istioctl authn tls-check，它的作用是读取客户端 DestinationRule 与服务端 PeerAuthentication 的配置，判断双方对 mTLS 的预期是否冲突。这条命令在 1.11/1.12 里已经不再默认提供，把它当作历史工具更合适：它只看认证配置，不解释授权拒绝；在自动 mTLS 成为默认行为之后，它给出的“冲突”提示也容易让人误判。今天排查认证问题，更直接的是查看实际下发的证书与监听配置：

可观测性、审计与分层防御

零信任不是配置完就结束，而是要能证明它一直在生效。最直观的指标是 istio_requests_total 里的 connection_security_policy 标签：按目标服务聚合，可以画出 mTLS 覆盖率曲线，任何一条回落到 none 的曲线都值得追查。把“明文连接数为零”设成告警，比人工巡检可靠。

授权层要看 403 的比例与来源。按 source_workload、destination_workload 和 response_code 聚合，可以区分“策略正常拦截”和“误伤导致的故障”。新策略上线前用 AUDIT 动作跑一段时间，对比命中记录，再切到 ALLOW，能显著降低上线风险。

审计需要两条证据链：一是策略变更，Kubernetes 审计日志应记录对 security.istio.io 资源的写操作，并纳入 GitOps 评审；二是访问记录，可在 Envoy 访问日志格式中加入 %DOWNSTREAM_PEER_URI_SAN%，把调用方身份写进日志。两者结合，才能回答“谁在什么时候改了策略”和“某个身份访问了什么”。

与网络策略、RBAC 的分层

这些机制不是替代关系，而是不同层面的防线：

机制 作用层面 主要能力 局限
NetworkPolicy L3/L4 按标签限制 Pod 进出流量 不理解身份与 HTTP 方法
网格 mTLS + 授权 L4-L7 基于服务身份与方法授权 依赖 sidecar，覆盖不到非网格流量
Kubernetes RBAC 控制面 限制谁能改资源 不管数据面请求
应用授权 业务层 细粒度业务权限 实现质量参差，需统一框架

合理做法是叠加：NetworkPolicy 先做默认拒绝，把流量收敛到必要端口；网格负责身份认证与 L7 授权；RBAC 控制策略由谁维护；应用保留与业务语义相关的最终判断。任何一层都不应被当作唯一防线。

落地步骤与常见坑

落地顺序可以概括为“先看见，再收紧，最后固化”。第一步盘点工作负载与服务账户，清理共用 default 账户的情况，确保每个服务有独立身份。第二步保持 permissive，用指标找出明文调用方，逐个迁移或登记例外。第三步按命名空间开启 STRICT，观察握手失败与 503，再推广到全网格。第四步在关键命名空间放空规则 ALLOW 实现默认拒绝，按调用关系逐条开口。第五步把 JWT 校验放到入口，把出口改为 REGISTRY_ONLY。第六步建立证书到期、mTLS 覆盖率与 403 比例的告警，定期复核策略。

常见坑集中在六处：

  • permissive 长期不收紧：自动 mTLS 让“能通”掩盖了明文仍在的事实，必须用覆盖率指标驱动收敛。
  • 误以为授权默认拒绝：没有 ALLOW 策略时流量默认放行，默认拒绝要靠空规则策略显式建立。
  • 服务账户共用：多个服务同一个 SA，SPIFFE ID 相同，授权规则形同虚设。
  • DNS 依赖：按主机名匹配的规则依赖客户端实际使用的地址，直连 Pod IP 或改写 Host 会让规则失效；出口未登记 ServiceEntry 则无法建立连接。
  • 策略冲突：多条 ALLOW 取并集、DENY 优先，网格级与命名空间级策略叠加容易产生意外结果。
  • 证书过期：根证书周期长，最易遗忘；istiod 长时间不可用会让短期证书无法续签。

每一条都对应一个可验证的检查项，建议写进上线清单，而不是停留在经验里。

小结

零信任在服务网格中的落点，是把身份、认证、授权和审计串成一条可验证的链路。以 SPIFFE ID 为身份锚点，用 PeerAuthentication 把 mTLS 从 permissive 推到 strict，用 AuthorizationPolicy 在默认拒绝之上按身份、命名空间与方法放行，再用 RequestAuthentication 接入终端用户身份。入口与出口都要设边界，证书与信任根要持续监控。落地时按“观测、收紧、固化”的节奏推进，避免 permissive 常开、共用账户和默认放行这些坑。
