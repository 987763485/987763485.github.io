TypeScript 运行时校验：zod 实践

本文属于《TypeScript 学习路线》第 38/74 篇
上一篇系列目录下一篇

接口约定写在 TypeScript 的 interface 里，运行时的数据却来自网络，编译器对后者一无所知。本文从几次典型的翻车记录出发，说明 zod 如何在运行时补上这道校验，让 schema 同时充当类型来源与文档，并给出把校验错误转成 API 响应、接入 Express、Koa 与 NestJS 的完整做法。适合已经熟悉 TypeScript、正在写 Node.js 服务端或复杂表单的读者。

问题的根源在于类型系统的边界。TypeScript 的类型在编译后被完全擦除，产出的 JavaScript 里没有任何字段信息；JSON.parse 的返回值是 any，req.body 在 Express 的类型声明里也是 any。只要数据跨过一次进程、一次网络、一次序列化，编译期的保证就归零。这不是 TypeScript 的缺陷，而是它的设计前提：类型服务于源码内部的一致性，不负责验证外部输入。

于是所有“外部”都成了缺口：HTTP 请求体与查询串、环境变量、配置文件、第三方接口的返回值、消息队列里的消息、localStorage 里上一次版本写入的 JSON。这些数据的共同点是来源不受当前代码控制，而它们的消费者却都写成了确定的类型。把 unknown 老实标在边界上，再在进入业务逻辑前收窄成具体类型，才是诚实的做法；zod 做的正是“从 unknown 到具体类型”的这一段。

手写 if 校验当然可行，但很快就会暴露三个问题。第一是重复：interface 写一遍字段，校验函数再写一遍，两边改不同步时，校验通过的数据未必符合类型。第二是遗漏：可选字段、嵌套对象、数组元素，靠人手逐个判断，漏掉一层是常态。第三是错误信息不统一：有人返回“参数错误”，有人返回英文堆栈，前端没法据此定位到具体输入框。这三点合起来，就是“校验写了，但等于没写”的典型状态。

可选性有三个容易混淆的修饰符。.optional() 表示字段可以缺失或为 undefined；.nullable() 表示值可以是 null；.nullish() 是两者的并集。数据库里允许为空的备注列应当用 nullish()，而不是 optional()，因为 null 会被 optional() 判为类型错误。.default() 只在值为 undefined 时生效，null 依然会走校验失败，这一点与很多人对“默认值”的直觉不同。

状态码的选择没有唯一答案，关键是团队内保持一致并在文档里写明。笔者的习惯是：请求体不是合法 JSON、Content-Type 不对，返回 400；JSON 合法但字段不满足业务约束，返回 422，响应体仍使用上面的结构。这样网关与监控可以按状态码区分“协议层错误”和“业务层拒绝”，排查时少一层猜测。

最后一点常被忽略：错误响应不要回显用户输入的原值。校验失败的 unitPrice 可能是任意字符串，把它放进 message 或额外的 received 字段，既可能撑大日志，也可能把敏感信息带到前端日志与错误上报系统里。只返回路径、错误码与安全文案，足够定位问题。

入参与出参分开

同一份 schema 不应同时承担入参与出参。出参通常带有 id、createdAt、status 这类服务端生成的字段，入参则不应该允许客户端指定它们；如果共用一个 schema，要么入参被迫接受不该接受的字段，要么出参校验永远失败。正确做法是分别定义，并让它们通过组合复用：

.pick、.omit、.extend、.partial 让派生关系显式可见。比起复制一份字段列表再逐个改，派生写法在源 schema 增加字段时不会自动扩大权限，这个差异在安全评审时非常重要。未声明的键在默认的 strip 模式下会被丢弃，相当于给“批量赋值”加了一道白名单，前提是不要把数据库实体直接交给 z.object。

另一个常见误区是把数据库查询结果也拿来做 schema 校验。数据库有列类型、非空约束与外键，查询结果的可信度高于 HTTP 输入；对每一行都跑一遍 schema，成本不小，收益却有限。真正需要校验的是“跨信任边界”的数据：HTTP 入参、消息体、第三方接口响应、配置文件。判断标准不是数据重不重要，而是“它是否由当前进程之外产生”。

请求处理的顺序

顺序也值得明确。一次请求进入服务后，合理的顺序是认证、限流、校验、业务：

flowchart TD
    A[请求进入] --> B[认证与限流]
    B -->|拒绝| E[401 或 429]
    B -->|通过| C[safeParse 校验]
    C -->|失败| F[422 与字段错误]
    C -->|成功| D[类型化 handler]
    D --> G[service 与数据库]

把校验放在认证之前并无不可，但未认证的请求会白白消耗解析成本，攻击者也可以借错误信息探测字段结构。先确认“你是谁”“还能不能调用”，再讨论“你传得对不对”，这条顺序在网关与服务内部都适用。

性能成本从哪里来

先说结论：在正常的请求体规模下，zod 校验的开销远小于一次数据库往返或一次外部调用，不应该成为拒绝校验的理由。真正拖慢服务的，往往是 schema 的使用方式，而不是 zod 本身。

第一个成本来自 schema 的构造。z.object({...}) 每次执行都会创建新的实例、合并字段定义，这比一次校验本身更贵。因此 schema 必须定义在模块顶层，随模块加载执行一次：

第二个成本来自校验次数。同一份数据在路由层校验过，service 里就不必再校验；反过来，如果 service 被多个入口调用，就把校验放到各入口，而不是在 service 内部重复执行。重复校验不仅浪费 CPU，还会让错误来源变得模糊：调用方明明传了合法数据，却在更深一层收到校验错误，排查方向立刻跑偏。

第三个成本来自 refine 里的副作用。下面这种写法很常见，问题也很大：

数组有一百个元素，就会产生一百次查询，典型的 N+1。正确做法是先收集所有 skuId，批量查一次库存，再用 superRefine 在内存里比对；校验函数保持纯粹，异步与批量逻辑放在调用方。类似地，异步 refine 必须配 safeParseAsync，这一点在前面已经提过，放到性能语境下更值得警惕：同步入口会直接抛错，而不是悄悄跳过。

嵌套、递归与出参校验

嵌套深度也需要控制。每增加一层对象或数组，解析就多一次函数调用与结果分配；更深层的问题是递归 schema。表示分类树时，zod 需要用 z.lazy 延迟求值，且必须显式标注类型，否则 TypeScript 无法完成推导：

递归 schema 的校验深度等于数据深度，而请求体来自外部。若不在入口限制 body 大小与数组长度，一个刻意构造的深层嵌套 JSON 就足以让解析占用大量内存与调用栈。实践上应当同时设置三层上限：反向代理或 express.json({ limit: '100kb' }) 限制请求体大小，数组用 .max() 限制元素个数，字符串用 .max() 限制长度。这些限制与业务规则无关，属于可用性保护。

最后是出参校验的取舍。对下游服务的响应做校验，能在契约漂移时第一时间发现，但也要为每个响应付出解析成本，而且对方返回脏数据时，自己的服务会从“部分可用”变成“直接报错”。比较稳妥的策略是：测试环境与预发环境全量校验出参，生产环境只对关键链路开启，或者按低比例采样；入参校验则始终全量，没有例外。

场景 建议 理由
HTTP 入参 全量校验 直接面向不可信输入
消息队列消息 全量校验 生产者版本可能先于消费者
下游响应 测试环境全量，生产采样 成本与故障放大之间的平衡
数据库查询结果 不校验 约束由数据库保证

这张表不是教条，但它能挡住最常见的两种极端：一种是“哪里都校验”，把服务写成层层包裹的洋葱；另一种是“都不校验”，把类型断言当成护身符。边界层设计的核心，是识别信任边界，只在跨越边界的地方付出成本。

复盘：五个反复出现的坑

第一个坑是在路由里直接调用 parse 却不捕获。ZodError 会沿着调用栈冒泡，Express 的默认错误处理把它当成未处理异常，返回 500。前端看到“服务器错误”，运维看到告警，实际上只是少传了一个字段。要么用 safeParse，要么在统一的错误中间件里识别 ZodError 并映射为 422，两条路选一条，不要两边都留一半。

第二个坑是在循环里逐项校验。有人写成 for (const item of body.items) { itemSchema.parse(item) }，错误信息里没有索引，前端无法知道是第几行出错。应当把整个数组交给 z.array(itemSchema).parse(body.items)，zod 会把索引写进 path，得到 items.3.quantity 这样的定位。这个差别在订单、批量导入这类场景里非常明显。

第三个坑是给“动态字段”开口子。遇到结构不固定的配置，很多人直接写 z.record(z.any()) 或 z.any()，校验层看似存在，实际什么都放行。z.record 的值类型应当尽量具体，例如 z.record(z.string()) 或 z.record(z.union([z.string(), z.number()]))；确实需要任意结构时，至少限制键的数量与值的深度，并在注释里写明为何放弃约束。

第四个坑是把形状校验当成权限校验。schema 能保证 userId 是一个合法的 UUID，却无法保证这个 UUID 属于当前登录用户。如果 userId 来自请求体，攻击者填别人的 ID 同样能通过校验。正确做法是从会话或令牌中取用户身份，请求体里的 userId 要么删除，要么与身份比对后再使用。校验解决“数据长什么样”，授权解决“这个人能不能做这件事”，两者不能互相替代。

第五个坑是测试只覆盖成功路径。schema 是业务规则的集中表达，规则改动频繁，缺少失败用例时，重构很容易把某个 min 或 refine 弄丢而无人察觉。至少为每个 schema 准备两条用例：一条合法数据断言 success 为真，一条非法数据断言失败且 issues[0].path 指向预期字段。后者比断言错误文案更稳定，文案会随措辞调整，路径不会。

小结

运行时校验不是对类型系统的不信任，而是承认类型只覆盖进程内部。zod 把 schema 变成同时服务于运行时与编译期的一份定义：z.infer 消除类型与校验的重复，safeParse 让失败成为可分支的普通结果，refine 与 transform 补齐字段关系与规范化，判别联合则让分支结构既好校验又好收窄。落地时把 schema 集中在边界层、在模块加载时构造、只校验跨信任边界的数据，并给数组、字符串与请求体设上限，就能在可维护性与性能之间取得平衡。错误映射要尽早统一，路径与错误码作为契约，文案只作展示。最后记住一条：校验负责形状，授权负责归属，两者都不可省。
