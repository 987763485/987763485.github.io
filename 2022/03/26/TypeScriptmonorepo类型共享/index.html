TypeScript monorepo 类型共享

本文属于《TypeScript 学习路线》第 37/74 篇
上一篇系列目录下一篇

一个前端仓库里同时放着工具库、组件库、类型定义和三四个应用，是 2022 年很常见的工程形态。拆开之后，代码边界清楚了，新的问题也随之出现：同一个 User 接口被抄了三份，组件库拿到的类型和接口层返回的类型对不上，CI 每次都要把全部包重新编译一遍。本文以 pnpm workspaces 为主线，讲清包怎么拆、project references 怎么配、类型包如何发布，以及多包仓库特有的坑。读者应熟悉 tsconfig.json 的基本字段，最好维护过一个以上的 npm 包。

从重复的接口到 workspace

重复定义只是症状

假设团队有四个包：@acme/types 放领域模型，@acme/utils 放日期与请求封装，@acme/ui 放组件，apps/admin 是后台应用。合并之前，四个包分属不同仓库，各维护一份 User。后台的版本是 id: string、name: string、avatar: string，组件库的版本是 id: number、nickname: string，工具库的版本干脆没有 role 字段。合并之后，把后台查询到的用户传给用户卡片组件，编译器立刻报错，维护者顺手写一个 as any，问题被压下去，直到线上出现头像空白。

这类重复不会以“重复”的形式暴露。TypeScript 采用结构化类型，只要形状兼容，两份不同的声明可以互相赋值，看起来一切正常；可一旦某一边把可选字段改成必填，错误就会出现在离修改点很远的调用处。枚举和带私有字段的类更严重，它们是名义化的，两份同名枚举之间不能互相赋值，报错信息往往让人摸不着头脑。换句话说，重复的类型定义比重复的函数更难发现，编译器不会提示“你抄了一遍”，只会提示某个调用点不匹配。

问题的根源不是缺一个公共文件夹，而是缺一条单向依赖链，以及让编译器理解这条链的配置。把类型挪到 @acme/types 只是第一步，接下来还要回答：谁可以依赖谁、构建按什么顺序进行、发布时哪些文件需要带上。

pnpm workspaces 的组织方式

本文选 pnpm 作主线，因为它的严格依赖隔离与按包过滤最贴合类型共享。先看目录结构。

根 package.json 只承担三件事：标记仓库为私有、声明全仓库共用的开发依赖、提供统一入口脚本。

执行 pnpm install 时，pnpm 把每个包链接到根 node_modules 下的符号链接中，真正的文件存放在全局内容寻址仓库里，同一个版本的包在磁盘上只保留一份。更关键的是默认的隔离布局：每个包的 node_modules 只包含它在 package.json 里声明过的依赖，没有声明的包无法被解析。这条限制在单包项目里像麻烦，在多包仓库里却是护栏：ui 偷引 admin 的模块会在编译期失败，而不是等到重构才暴露。

与 npm、Yarn 的差异

三种工具都能把多个包放进一个仓库，差别在依赖布局与生态兼容性上。

维度 pnpm npm workspaces Yarn
依赖布局 内容寻址仓库加符号链接，默认隔离 扁平提升，容易出现幽灵依赖 经典版提升，Berry 默认 PnP

npm workspaces 胜在零额外依赖，适合包少、依赖简单的仓库；Yarn 经典版稳定但已停止演进；Yarn Berry 的即插即用（PnP）能消除幽灵依赖，代价是工具适配。无论选哪个，类型共享的配置思路相通，差异主要在安装与发布环节。

包的拆分：四种角色，一条单向链

拆包不是越细越好。包的数量每增加一个，构建图、发布流程和版本矩阵都会变复杂。对大多数业务仓库来说，四种角色已经够用：类型、工具、组件、应用。关键不在数量，而在依赖方向必须单向。

@acme/types 只描述形状，不含实现。领域模型、接口契约、跨包共享的枚举与联合类型放在这里，工具函数和组件一概不放。它位于依赖链最底层，不引用任何内部包，因此可以独立编译、独立发版。@acme/utils 放与 UI 无关的纯逻辑，例如日期格式化、金额计算、请求封装，它的函数签名大量引用 types 中的模型。@acme/ui 放组件与样式，依赖 types 与 utils，但不依赖任何应用。apps/admin 负责路由、状态和页面组装，依赖前面三个包，自己标记为私有，不被任何人引用。

flowchart TD
  admin[apps/admin] --> ui["@acme/ui"]
  admin --> utils["@acme/utils"]
  admin --> types["@acme/types"]
  ui --> utils
  ui --> types
  utils --> types

这条链一旦出现反向边，构建就会变得难以解释。组件库为了一个页面级的组合类型去依赖应用，应用又依赖组件库，tsc -b 会直接报告循环引用；即使勉强绕开，发布时也会发现两个包必须同时升级，版本号再也拆不开。

判断一个类型该放哪一层，有一个简单的测试：如果删掉 ui，这个类型还成立吗？成立就下沉到 types 或 utils；只有组件 props、样式变体这类与渲染强相关的类型才留在 ui 内部。另一个误区是把 types 包当垃圾桶，用过一次的类型都往里塞。共享包只应收纳被两个以上包使用的契约，单包内部类型留在原处，否则每次改一个字段都会触发整条链重新构建，收益远小于成本。

project references：让编译器看见依赖图

在不用 project references 的项目里，多包仓库通常有两种做法。第一种是每个包独立执行 tsc，类型解析走 node_modules 里上游包的 dist/index.d.ts，因此必须先构建 utils，再构建 ui；顺序靠脚本里的 && 维持，漏一个就报“找不到模块”。第二种是在 paths 里把包名映射到上游的 src，编辑器反应很快，但 ui 的编译程序会把 utils 的源码一起吸进来，同一份类型出现 src 与 dist 两个副本，rootDir 之外的文件还会把输出目录结构撑乱。

project references 要解决的就是这两难：让编译器知道“这个包的类型来自另一个项目的源码”，同时保持每个包独立输出。配置从根目录的公共文件开始：

declarationMap 是另一个提升体验的选项。开启后，每个 .d.ts 旁边会多一个 .d.ts.map，编辑器在“转到定义”时会跳到上游包的 .ts 源码，而不是只读的声明文件。代价是声明映射里记录的是相对路径，消费方必须能拿到源码；因此内部包发布时要把 src 一并放进 files，否则映射指向一个不存在的文件，跳转仍然落在 .d.ts 上。

project references 只负责编译与类型，不做打包。ui 的产物里仍然是 import { formatDate } from "@acme/utils" 这样的模块说明符，运行时的解析交给打包器或 Node。下一节讨论的路径映射与 exports，正是围绕这条边界展开的。

路径映射、exports 与运行时的边界

paths 是编译器的承诺

paths 是多包仓库里被误用最多的选项之一，它只做一件事：告诉编译器某个模块说明符去哪里找类型。它不会改写输出，也不会影响 Node 的解析。下面这份配置让 @/lib/x 在编辑器里通得过：

源码写 import { parse } from "@/lib/parse"，编译出来的 JavaScript 原样保留 @/lib/parse，生成的 .d.ts 也原样保留。打包器如果没配同样的别名，运行时报 ERR_MODULE_NOT_FOUND；即便打包器配了，发布出去的声明文件到了消费方那里仍然是一句无法解析的 @/lib/parse。

跨包场景更应避免别名。包名加 workspace 链接已经能解决解析问题，@acme/utils 在源码、产物和声明文件里是同一个说明符，三方一致。包内深路径若嫌 ../../ 难看，优先用相对路径，或者用 exports 暴露子路径，让说明符成为公开契约的一部分。

如果历史代码已经大量使用别名，可以在打包器里配置同样的 resolve.alias 解决运行时，再用 tsc-alias 改写产物与声明文件中的说明符；更稳妥的做法是把别名限制在应用包内部，库包一律禁用，因为库包产物要给下游消费，非标准说明符会把配置负担转嫁出去。

这里有一个 2022 年绕不开的限制：TypeScript 4.6 在常用的 node 解析模式下还不读 exports。它找类型时仍然看顶层的 types 字段，子路径导入则按文件路径拼接。也就是说，运行时 import "@acme/utils/date" 能被 Node 正确解析到 dist/date.js，编译器却会去找 node_modules/@acme/utils/date.d.ts，然后报找不到声明。官方已经把对 exports 的完整支持排进后续版本的路线图，但在 4.6 上不能依赖它。

只在编译期存在的类型如何发布

类型在运行时会被完全擦除，这是发布策略的前提。interface、type 别名、泛型参数在编译后不留痕迹；enum、class、带 as const 的对象则会生成真实代码。把两者混在一个“类型包”里，消费方就分不清哪些导入是安全的。

最彻底的形态是纯声明包：包里只有一个或几个 .d.ts 文件，package.json 不写 main，只写 types。

这种包体积极小，发布快，也不带出实现细节。代价是消费方只能写 import type。一旦写成值导入，编译期可能通过，运行时会因为模块没有 JavaScript 实现而失败。为了让错误提前到编译期，消费方应开启 importsNotUsedAsValues：

这个选项会保留所有导入语句，并在“值导入实际只被当作类型使用”时报错，正好把误用挡在提交之前。再配合 ESLint 的 consistent-type-imports 规则，团队里就很难写出含糊的导入。

纯声明包还有一个构建图上的问题：它没有可编译的源码，放进 project references 也没有意义。如果希望所有包走同一条 tsc -b 流水线，可以改成用 .ts 写类型，编译后得到 .d.ts 和一个空的 .js。空实现让值导入不至于崩溃，但语义上仍然是错的，所以 importsNotUsedAsValues 依旧要开。两种做法各有适用面：包少、类型稳定时纯声明包更轻；包多、需要统一构建顺序时 .ts 源码更顺。

无论选哪种，都不要把 types 指向 src/index.ts。这等于把源码交给消费方用自己的编译选项检查：对方的 strict、lib、target 都会影响结果，编辑器变慢，类型行为也不可控。正确的入口永远是构建后的 .d.ts。

声明文件还必须自洽。公开函数不能引用未导出的私有类型，否则 declaration emit 会报 TS4023 一类错误，提示某个名字无法被命名。stripInternal 能删掉标记为 @internal 的声明，但如果公开 API 引用了它们，删完就留下悬空引用。发布前跑一次“只装产物”的消费测试，比事后排查便宜得多。

版本、发布与私有 registry

workspace 协议在发布时被改写

内部包用 workspace:* 声明依赖，发布时必须换成真实版本，否则外部消费者装不上。这个改写由 pnpm 在打包阶段完成，规则很直接：

写法 发布后
workspace:* 1.4.0（精确版本）
workspace:^ ^1.4.0
workspace:~ ~1.4.0

精确版本适合强绑定的内部包，语义化范围适合希望下游自动获得补丁的库，取舍在于是否敢让消费方不改代码就升级。

这里有一个必须记住的差异：npm 不识别 workspace: 协议。在 pnpm 工作区里用 npm 发布，要么直接报错，要么把 workspace:* 原样带出去，安装时失败。因此发布动作要统一走 pnpm：

版本策略与 publishConfig

内部包的版本策略有两种。固定模式让所有包共享版本号，依赖矩阵简单，但改一个组件也会让所有包发新版本；独立模式让各包自行演进，适合耦合较弱的仓库，代价是维护兼容矩阵。多数团队取中间：应用不发布，库包独立版本，类型包与工具包保持同步。

如果使用 Changesets 这类工具，提交时记录变更意图，发版时统一计算版本与依赖范围，能减少“改了代码忘了升版本”。关键在于让版本变更成为显式、可审查的操作，而不是发布脚本里的副作用。

CI 里的缓存与受影响包构建

多包仓库的 CI 有两笔固定开销：安装与编译；只治一笔，流水线仍会随包的数量线性变慢。

安装侧的核心是 pnpm 的内容寻址仓库。依赖包在 store 里只存一份，缓存它比缓存 node_modules 更稳定，也不会混进平台相关的二进制文件。流水线里先定位 store 路径，再以锁文件哈希作为缓存键：

--frozen-lockfile 保证 CI 不改写锁文件，--prefer-offline 让命中缓存的包尽量不走网络。缓存键只用锁文件哈希，加日期后缀会让命中率归零。

编译侧的关键是只构建受影响的包。pnpm 的过滤语法 ...[origin/main] 表示“自 main 分支以来发生变更的包，以及依赖它们的包”，前面的省略号不能省，否则只构建变更包本身，依赖它的应用不会重建，类型不兼容就会被漏掉。这个过滤器要求仓库有完整的 git 历史，actions/checkout 默认的浅克隆会让它算错，所以必须显式设置 fetch-depth: 0。

tsc -b 本身会跳过没有变化的项目，但递归执行还会跑测试、打包、lint，这些动作不受 .tsbuildinfo 管理；把范围缩到变更子图，才能省掉无关包的时间。

至于 .tsbuildinfo 是否要跨机器缓存，本文持保守态度。它记录了大量文件路径与时间戳，换一台机器、换一个检出目录都可能让它失效；失效时不会报错，只会全量重建，收益不稳定。与其冒险，不如把缓存预算花在依赖 store 上。如果仓库规模大到单机增量仍然吃力，可以引入 Turborepo、Nx 这类带远程缓存的任务编排器，让任务产物在团队间共享；这属于另一层优化，配置 project references 仍然是它们理解构建图的前提。

六个高频坑与排查手法

重复的 @types 引发类型冲突

症状通常很怪：某个 Request 类型不能赋值给另一个同名类型，AbortSignal 在两处定义里结构不同，React 组件的 props 报“缺少属性”。根源是同一个 @types 包被装了多个版本：扁平布局会提升，pnpm 的隔离布局则允许各包各装一份。

治理手段有三层。第一层是对齐版本，把全局类型的版本写进根 package.json 的开发依赖，子包不再各写各的。第二层是用 overrides 强制收敛，pnpm 在根 package.json 里读 pnpm.overrides，npm 8 与 Yarn 也各有对应字段：

第三层是缩小全局类型的注入范围。compilerOptions.types 只列出真正需要的包，例如 Node 侧写 ["node"]，浏览器侧留空；不要用 typeRoots 指向一个随手创建的目录，那等于把所有能找到的声明都塞进全局。@types/node 的大版本还要与运行时对齐，Node 16 配 16.x 的类型，混用 17.x 会引入当时还不存在的 API 声明。

路径别名在运行时失效

这一类问题的迷惑性在于本地全绿。单元测试用 ts-jest 并配置了 moduleNameMapper，编辑器有 paths，一切正常；构建产物部署到 Node 上，第一行就报找不到模块。原因在前文已经拆过：paths 不改写说明符，测试框架和打包器各自的别名配置又只覆盖自己的执行环境。

排查时直接看产物：

只要产物或 .d.ts 里出现别名，就说明有消费方会在某个环节解析失败。修复优先级从高到低：跨包改用包名；包内改用相对路径或 exports 子路径；确实需要别名时，在打包器和 tsc-alias 两处同时配置，并把声明文件也纳入改写范围。

skipLibCheck 的取舍

skipLibCheck 跳过所有 .d.ts 文件的内部检查，只检查你自己的源码如何使用这些类型。它不影响产物生成，也不等于“关掉类型检查”。在依赖树庞大的仓库里，打开它能明显缩短编译时间，因为第三方声明之间的兼容问题不该由业务仓库买单。

但它是把双刃剑。重复的 @types 冲突、第三方声明里的错误、你自己刚生成的声明文件里的问题，都会被它一并盖住。本文的建议是分场景：应用包打开，换取构建速度；库包在发布前的独立任务里关闭，确保对外声明自洽；不要因为“报错太多”就全局打开，那只是把问题推迟到消费方。

如果关闭后报错集中在某几个第三方包，优先升级或替换它们，而不是把整个仓库的检查关掉。skipLibCheck 是性能选项，不是修复手段。

声明文件缺失或入口错位

报错形式是 TS7016：“Could not find a declaration file for module”。原因可能出在四个环节：库包没有开 declaration；types 字段指向的路径不存在；files 白名单漏掉了 dist；exports 挡住了子路径而 typesVersions 没有补。还有一种隐蔽情况：main 指向 src、types 指向 dist，本地因为源码还在而正常，发布后立刻坏掉。

排查按“打包产物”而不是“源码目录”进行：

看清单里到底有哪些文件，再核对 types、main、exports 是否都指向清单内的真实文件。npm pack --dry-run 不会上传，适合放进发布前的检查脚本。

循环依赖

包级循环会让 tsc -b 直接拒绝构建，并提示引用图里存在环。即使把 references 去掉、靠模块解析绕过，运行时也会出问题：CommonJS 里可能拿到半截 exports，ESM 里可能触发暂时性死区。类型层面的循环同样不能被忽视，因为 references 检查的是项目图，不理解“这个导入只用于类型”。

解法不是加 import type 就完事，而是改变依赖方向。公共部分下沉到 types 包；如果两个包互相需要对方的接口，把接口定义在更底层，让双方都实现或引用它；再不行就承认两个包耦合过紧，合并成一个。包的数量应该服从依赖图，而不是相反。

类型包与实现包不同步

这是最隐蔽的一类。类型包手工维护，实现包另写一套，两边靠约定同步；某次实现加了必填字段，类型包没跟上，消费方在编译期看不到任何问题，运行时才拿到 undefined。如果版本范围写的是 ^，消费方还可能装到“类型是新的、实现是旧的”这种组合。

治理的核心是消灭第二份事实来源。能由实现导出的类型，就不要在类型包里重写；能由契约生成的类型，就把生成物纳入同一条构建链，而不是手工誊抄。从 OpenAPI 生成客户端类型、用 zod 在运行时校验数据，是另外两篇文章的主题，本文只强调一点：无论类型来自手写、推导还是生成，它都必须和实现同源、同版本、同一次发布。

在此基础上再加两道保险：一是类型测试，用 // @ts-expect-error 或 tsd 固定公开 API 的预期，改坏了 CI 会红；二是消费方冒烟测试，在 CI 里新建一个只装产物的小项目，导入所有公开入口并编译一次。前者防语义漂移，后者防入口与声明文件缺失。

小结

monorepo 里的类型共享，表面上是把接口挪到一个公共包，实质是建立一条可被编译器理解的单向依赖链。包按 types、utils、ui、app 四层拆分，依赖只能向下；用 project references 配合 composite、declaration、declarationMap 让 tsc -b 按图构建并保留源码跳转；用包名而不是路径别名跨包引用，并清楚 paths 只管编译期、exports 只管运行时、TypeScript 4.6 还读不懂 exports 里的类型条件。

发布环节要守住三条线：workspace: 协议由 pnpm 在发布时改写，别用 npm 发布；类型包要么纯声明并强制 import type，要么与实现同源同版本；私有 registry 的地址与凭据分开放，publishConfig 明确 scope 与访问级别。CI 把依赖 store 缓存好，用变更过滤器只构建受影响子图，主分支仍跑全量构建兜底。

最后，多包仓库的问题大多不是配置写错，而是边界没想清楚。遇到类型冲突、别名失效、循环依赖时，先问“这两个包应该互相认识吗”，往往比继续调 tsconfig.json 更有效。
