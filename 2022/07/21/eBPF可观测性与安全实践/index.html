eBPF 可观测性与安全实践

本文属于《Docker 与 Kubernetes》第 41/51 篇
上一篇系列目录下一篇

线上排障时最让人难受的场景，往往不是“没有数据”，而是“数据在错误的层次上”：应用日志只记录了自己愿意记录的事情，指标只暴露了开发者预先埋点的几个维度，真正出问题的系统调用、网络连接和文件访问，全都发生在内核里，用户态的采集器看不到。eBPF 把观测点直接下沉到内核，让一段经过验证的小程序挂在内核事件上，用很低的开销回答“这个进程到底做了什么”。

本文面向已经熟悉 Linux 与容器、但还没有系统用过 eBPF 的工程师，从执行模型讲起，依次覆盖程序类型、验证器与 map、BTF 与 CO-RE、bpftrace 的常用查询、网络数据面与运行时行为检测，最后给出生产环境的约束清单。读完之后，你应该能判断一个问题该用哪类探针、为什么脚本在测试机跑得通到线上却加载失败，以及哪些安全场景适合用 eBPF 做证据采集、哪些不适合。

本文讨论的是内核态数据源本身。可观测性的三大支柱、采样与成本模型属于另一条线索，已经在第 694 篇中展开，这里不再重复；本文关心的是这些信号最初如何从内核里被取出来。

eBPF 在内核里的位置

eBPF 最初是包过滤工具，后来演变成一个通用的内核内虚拟机。它的指令集是固定的 64 位 RISC 风格，有 11 个寄存器，其中 r10 只读，用作栈帧指针；程序不能随意跳转，也不能直接调用任意内核函数，只能调用内核为它开放的辅助函数。这个限制不是缺陷，而是整个技术能够被允许进入生产内核的前提：内核不需要相信加载者，只需要相信验证器。

一次加载大致分为四步。用户态程序通过 bpf() 系统调用提交字节码、日志级别和期望的挂载类型；内核验证器对字节码做静态分析，检查指针来源、边界、循环是否可终止、栈是否越界；通过后由 JIT 编译成本机指令；最后按照程序类型挂到对应的钩子上。整个过程不需要重新编译内核，也不需要加载内核模块。

flowchart TD
    A[内核事件：系统调用、函数入口、网卡收包] --> B[eBPF 程序]
    B --> C{验证器}
    C -->|通过| D[JIT 编译并挂载]
    C -->|拒绝| E[返回错误与验证日志]
    D --> F[map 聚合与状态保存]
    F --> G[perf buffer 或 ring buffer]
    G --> H[用户态：bpftrace、BCC、采集 Agent]

理解这张图的关键在于“两段式”：内核里的程序只做最小的事，读参数、做过滤、更新 map、把事件写进缓冲区；复杂的聚合、格式化、落盘和告警都放在用户态。这样既避免了在内核里做重活，也让程序的更新和调试不必触碰内核。map 是两段之间唯一被允许的共享内存，它既是计数器，也是配置下发和状态关联的通道。

还有一个容易被忽略的约束：eBPF 程序运行在触发事件的 CPU 上下文里，不能睡眠、不能阻塞，也不能调用可能睡眠的辅助函数。这条规则决定了后面所有的性能取舍，也解释了为什么采集器要先用 per-CPU map 累加，再由用户态汇总。

六类挂载点与它们能看见什么

程序类型决定了 eBPF 能挂在哪里、能拿到什么上下文。日常工作中最常用的有六类，它们的稳定性和开销差别很大。

类型 挂载位置 典型用途 稳定性
kprobe 任意内核函数入口或返回 追踪内部函数、补足 tracepoint 缺口 弱，随内核实现变化
tracepoint 内核预置的静态探针 系统调用、调度、网络事件统计 强，属于内核 ABI
uprobe 用户态二进制或共享库的函数 无侵入观测应用逻辑、Go 与 JVM 内部 中，依赖符号与版本
XDP 网卡驱动收包路径最前端 丢弃、重定向、四层过滤 强，但依赖驱动支持
tc 流量控制层 ingress 与 egress 限速、标记、策略执行 强，与内核网络栈一致
cgroup cgroup 钩子 按容器或进程组做资源与安全检查 强，随 cgroup v2 推进

kprobe 的能力最广，任何内核符号都可以挂，包括没有导出给模块的内部函数。代价是它绑定的是实现细节：函数改名、参数增减、内联优化，都会让脚本失效。tracepoint 由内核开发者预先埋好，位置和字段被视为稳定接口，升级内核时更安全，但覆盖范围有限，很多你想看的内部状态并没有对应的 tracepoint。

uprobe 把同样的思路搬到用户态。它按“二进制路径 + 符号 + 偏移”下探针，可以观测应用里某个函数的入参和返回值，不需要改代码、不需要重启。对 Go 程序要注意，默认编译会内联大量函数，符号表也可能被裁剪，探针不一定挂得上；观测 JVM 时则要接受解释执行与 JIT 编译后的代码路径并不一致。

XDP 和 tc 属于网络数据面。XDP 在驱动收到包、分配 sk_buff 之前执行，能拿到 xdp_md 上下文，返回 XDP_PASS、XDP_DROP、XDP_TX、XDP_REDIRECT 等动作，因此丢包成本极低。限制是只能看到二层到四层，做不了依赖连接状态的应用层判断。tc 钩子挂在协议栈内部，能看到更完整的上下文，也能在 egress 方向工作，适合做限速和策略，但每个包都要构造 sk_buff，开销高于 XDP。

cgroup 类型的程序把检查点放在进程组的边界上，容器场景里尤其有用：不管容器里换了多少个进程、改了多少次命令行，只要还在同一个 cgroup 下，设备访问、connect、sendmsg 等操作都会经过同一个钩子。

验证器、map 与辅助函数：能力的边界

验证器是 eBPF 最容易被低估的部分。它不是简单的语法检查，而是一个对所有可能路径做抽象解释的静态分析器。它会跟踪每个寄存器的类型，检查每一次内存访问的范围，确认循环有可证明的上界，并限制程序的总复杂度。较新的内核把复杂度上限提高到一百万条指令，但“可证明”这个前提没有变：任何依赖运行时数据才能确定的跳转和访问，都可能被拒绝。

初学者最常遇到的几类拒绝，背后都是同一条规则。第一类是“无效的内存访问”，比如把一个整数直接当地址解引用，或者从 map 里取出的指针没有做空值检查就使用。第二类是“不允许的循环”，早期的内核完全禁止循环，5.3 之后支持有界循环，但边界必须能被验证器推导出来。第三类是“栈越界”，eBPF 的栈只有 512 字节，大的结构体必须放 map 或者分片读取。第四类是“调用了不允许的辅助函数”，比如在 kprobe 上下文里调用可能睡眠的函数。

调试这些问题要靠验证日志：加载时打开日志级别，内核会打印每条指令的状态，能精确定位到第几条指令、哪个寄存器、期望的类型。生产环境通常只在加载失败时抓一次日志，避免日志本身成为开销。

map 是 eBPF 的持久化状态，类型选择直接影响正确性和性能。BPF_MAP_TYPE_HASH 适合按 key 聚合，但每次查找都有哈希开销；BPF_MAP_TYPE_ARRAY 查找是常数时间，适合固定索引的计数器；BPF_MAP_TYPE_PERCPU_HASH 和 PERCPU_ARRAY 为每个 CPU 维护独立副本，写入不需要原子操作，用户态读取时再求和，是高频率统计的首选；BPF_MAP_TYPE_RINGBUF 在 5.8 之后引入，多个程序可以共享一个环形缓冲区，按事件顺序读取，比 perf buffer 更省内存，也更适合高吞吐场景。

map 的容量和生命周期要提前想清楚。max_entries 在创建时固定，满了之后哈希 map 的插入会失败，而 eBPF 程序里通常没有地方处理这个错误，数据就静默丢了。键的设计同样重要：把进程名当 key，容器里同名进程会混在一起；把完整命令行当 key，则会因参数不同产生大量条目。实践中用 pid 加启动时间做关联，再由用户态补充元数据。

辅助函数是内核给 eBPF 的“系统调用表”，数量有限且按程序类型划分。常用的有 bpf_map_lookup_elem、bpf_probe_read_user、bpf_get_current_pid_tgid、bpf_get_current_comm、bpf_ktime_get_ns、bpf_perf_event_output 等。每个函数都有上下文限制，比如 bpf_probe_read_user 在中断上下文里读用户内存可能失败，bpf_send_signal 只能发送有限几种信号。写程序之前先查一遍可用列表，比写完再猜为什么加载失败要高效得多。

BTF 与 CO-RE：让程序跟着内核走

早期写 eBPF 最痛苦的事情是结构体偏移。内核结构体的字段位置随版本和编译选项变化，程序里写死 offsetof(struct task_struct, pid)，换一台机器就可能读到错误的字段，甚至被验证器拒绝。BTF 和 CO-RE 解决的就是这个问题。

BTF 是一种描述内核类型信息的数据格式，被编译进内核镜像，通常可以在 /sys/kernel/btf/vmlinux 找到。它记录了结构体、联合体、枚举、函数的布局，包括字段名、类型、偏移和位域。内核 5.2 之后支持 BTF，主流发行版在 5.15 前后已经默认开启 CONFIG_DEBUG_INFO_BTF，这是 CO-RE 能落地的前提。

CO-RE 是“一次编译，到处运行”的机制。编译时，bpftool btf dump file /sys/kernel/btf/vmlinux format c 可以生成 vmlinux.h，程序包含这个头文件后就能用内核的真实类型；字段访问被标记为“需要重定位”，编译产物里保留的是字段名和访问路径，而不是固定偏移。加载时，libbpf 读取目标内核的 BTF，重新计算偏移，把指令里的立即数改写成正确值。

这段代码里的 BPF_CORE_READ 会被展开成带重定位信息的读取序列，bpf_core_read.h 负责处理嵌套字段和指针链。要注意它只能读取内核内存，读用户态指针要用 BPF_CORE_READ_USER 或显式的 bpf_probe_read_user。

CO-RE 不是万能的。它只能修正“字段位置”这类布局差异，修不了“字段被删除”“函数签名改变”“逻辑分支重构”。所以用 kprobe 追踪内部函数时，仍然要为每个内核大版本做测试；用 tracepoint 和稳定的辅助函数时，可移植性才有保障。另一个现实约束是内核配置：如果目标机器的内核没有 BTF，CO-RE 程序无法加载，只能退回为每个内核版本单独编译，或者改用不带类型依赖的写法。

bpftrace：把问题写成一行查询

bpftrace 是把 eBPF 用成“命令行工具”的那一层。它自带一套简化的脚本语言，语法接近 awk：探针加过滤条件，花括号里写动作；变量用 $ 开头，map 用 @ 开头，内置的 count()、sum()、hist()、avg() 负责聚合。对于一次性的排障，它比写 C 快得多；对于需要长期运行的东西，还是应该落到 libbpf 程序里。

BCC 与 libbpf：从脚本到产品

bpftrace 适合交互式探索，真正要做成采集器，就得在 BCC 和 libbpf 之间做选择。BCC 把编译、加载、map 访问都封装进了 Python、C++ 等语言，写起来快，自带的一批工具（execsnoop、opensnoop、tcplife、biolatency）可以直接拿来排障。它的代价是运行时依赖较重：目标机器上要有 LLVM 和内核头文件，第一次运行要现场编译，启动慢，镜像也大。

libbpf 是纯 C 的加载库，配合 clang -target bpf 做提前编译，产物是一个 .o 文件加一个用户态程序。它依赖 BTF 做 CO-RE 重定位，运行时不需要编译器，启动快、体积小，适合做成 DaemonSet 或者嵌入到 Agent 里。代价是开发门槛更高：map 的定义、事件循环、缓冲区管理、错误处理都要自己写。业界的趋势很明确，新项目基本都走 libbpf 或者它的 Go、Rust 绑定，BCC 更多留在“临时查问题”的位置。

两者共享同一套内核接口，所以排障思路是通用的：先用 BCC 自带工具确认现象，再用 bpftrace 缩小范围，最后把稳定的查询固化成 libbpf 程序。不要一上来就写产品级代码，很多需求用现成工具加几行过滤就能回答。

tracepoint 与 kprobe：稳定性从哪里来

tracepoint 的稳定性来自契约。内核开发者用 TRACE_EVENT 宏定义事件时，同时定义了事件名、字段名和类型，这些信息会出现在 tracing 文件系统的 format 文件里。用户态程序可以读取这个文件来生成解析代码，而不必猜测布局。字段增删被视为接口变更，需要走内核的兼容性流程，所以同一个 tracepoint 在 5.15 和 6.0 上通常都能用。

kprobe 的稳定性来自“符号还在”。它按函数名或者地址下探针，函数的参数通过寄存器或栈传递，eBPF 程序用 arg0 到 argN 去取。问题在于，函数名不是 ABI：do_sys_open 可能被改名，vfs_read 的参数可能调整顺序，编译器还可能把一个小函数内联进调用者，让探针无处可挂。用 kprobe 写的脚本在测试机上跑通、到线上加载失败，绝大多数都是这个原因。

更麻烦的是语义漂移。假设你挂的是某个内核函数，读取它的第三个参数指向的结构体，字段偏移可以靠 CO-RE 修正，但如果这个函数在新版本里不再表示原来的含义，读到的值就是错的，而且不会报错。这类问题比加载失败更难发现，往往要等到报表出现异常才能察觉。

实践中的选择顺序是：能用 tracepoint 就不用 kprobe；tracepoint 覆盖不到时，优先找稳定的辅助函数或者 cgroup 钩子；确实要下探内部函数，就把内核版本范围写进代码，用 bpf_core_type_exists 或者版本判断做分支，并在每个大版本上跑一遍回归。较新的内核提供了 fentry 与 fexit，它们基于 BTF 拿到带类型的函数参数，开销比 kprobe 低，也不依赖断点指令，但仍绑定函数签名，不能解决语义漂移。

网络数据面：XDP、tc 与 Cilium 的位置

网络方向的 eBPF 程序解决的是“在每个包上做一次判断”的问题。XDP 挂在驱动收包的最前端，此时包还在 DMA 缓冲区里，尚未分配 sk_buff，所以丢弃一个包的成本极低。程序拿到的上下文只有数据指针、数据结束指针、入接口索引等少量字段，必须自己解析以太网头、IP 头和传输层头，并且每次访问前都要做边界检查，否则验证器会直接拒绝。

这段代码没有处理 IP 选项长度、分片、VLAN 与 IPv6，生产环境要按 ihl 计算头部。它说明两条规则：指针访问必须先证明不越界，返回动作必须明确。XDP_PASS 交给协议栈，XDP_DROP 静默丢弃，XDP_TX 从原接口发回，XDP_REDIRECT 交给另一个网卡或 CPU。

限速的思路通常是一个基于 map 的令牌桶或者滑动窗口。以源 IP 为 key，在 map 里记录上一次补充令牌的时间和当前令牌数，每个包到达时按时间差补充，再决定放行还是丢弃。这里有两个工程细节：map 要有容量上限并使用 LRU 类型，否则伪造源地址会把内存打满；时间基准要用 bpf_ktime_get_ns 而不是墙上时钟，避免时间跳变导致桶状态错乱。XDP 层做限速的优点是早，缺点是看不到连接状态，对需要七层语义的策略无能为力。

tc 钩子位于协议栈内部，能看到完整的 sk_buff，可以在 ingress 和 egress 两个方向工作，也可以修改包、做重定向、配合 mirred 做镜像。它适合做细粒度的策略和限速，代价是每个包都要经过协议栈的一部分处理。工程上常见的分工是：XDP 处理大流量攻击的粗粒度丢弃，tc 处理需要状态和策略的细粒度控制。

Cilium 是把这套能力产品化的代表。它以 eBPF 作为数据面，用安全标识而不是 IP 地址来表达“谁可以访问谁”，在 Kubernetes 里承担网络策略、服务负载均衡和流量可见性等职责。它同时提供 Hubble 作为观测层，把数据面的事件汇成服务之间的调用关系。本文不展开具体版本的功能差异，只强调它的定位：Cilium 把 eBPF 程序当成网络数据面的一部分长期运行，因此对内核版本、BTF、权限和升级路径的要求都比一次性脚本高得多。选型时应该先确认内核能力，再谈策略模型。

运行时行为检测：把异常变成证据

安全侧使用 eBPF 的正确姿势是“采集证据”，而不是“替代防护”。内核里能看到的原始行为包括进程执行、文件访问、网络连接、权限变更和内核模块加载，这些事件恰好是入侵链路上最难完全抹掉的痕迹。把它们按时间顺序拼起来，再和容器、Pod、镜像的元数据关联，才能回答“这个容器在做什么”。

异常 exec 是最有价值的信号之一。Web 服务进程 fork 出一个 shell，随后执行 curl 或者 base64，在正常业务里几乎没有理由出现；从 /tmp、/dev/shm 或者已删除的文件执行，也属于高置信度的可疑行为。检测逻辑通常写成“父进程白名单 + 路径规则 + 参数特征”的组合，在内核里只做字段提取和粗过滤，把判断放到用户态，方便更新规则。要注意进程名和路径都可以被伪造，单条规则只能作为线索。

敏感文件访问是另一类信号。读取 /etc/shadow、/root/.ssh/id_rsa、kubelet 的证书目录、云厂商的元数据地址，都是凭据窃取的典型前置动作。文件路径往往包含业务信息，采集时要考虑脱敏和保留周期，避免把观测系统变成新的数据泄露面。对 openat 一类系统调用，建议只记录命中敏感路径前缀的事件，而不是全量落盘，否则存储成本和隐私风险都会迅速上升。

权限与内核层面的变化同样值得关注：setuid 系列调用、能力集修改、加载内核模块、ptrace 附加到其他进程。这些事件频率低，适合全量采集。把它们和 exec 事件按进程树关联，可以还原出“从哪个入口进来、提权到哪一步、又访问了什么”的路径。这里必须强调边界：eBPF 观测的前提是内核本身可信，拥有 root 与 CAP_BPF 的攻击者可以卸载程序、篡改 map 或者干扰事件输出；因此日志要实时外发、落地到独立系统，并与审计子系统交叉校验，不能把全部信任押在采集器上。

工程上，Falco 这类工具已经把“内核事件到规则引擎”的链路做成了产品。自建时不必从零写规则引擎，但要想清楚：事件如何带上容器标识、如何避免高频事件打满管道、规则误报如何收敛。检测系统的价值不在于告警数量，而在于每条告警都能指向可复核的证据。

生产落地：版本、内存、开销与权限

把 eBPF 放进生产，第一道门槛是内核版本。5.15 是长期支持版本，Ubuntu 22.04 等发行版在 2022 年采用它作为默认内核，它具备 BTF、ring buffer、CAP_BPF 等本文依赖的能力；5.16 到 6.0 主要是性能改进，不建议把新特性当成基线；低于 5.8 的内核没有 ring buffer 和独立能力位，低于 5.11 的内核在 map 内存记账上差异明显。

第二道门槛是可移植性。CO-RE 解决了字段偏移，但没有解决内核配置差异：有的内核裁掉了 BTF，有的开启了 lockdown 模式禁止加载未签名程序，有的容器镜像里没有 /sys/kernel/btf/vmlinux。上线前应该准备一个最小探测程序，在目标节点上实际加载一次，把内核版本、BTF 是否存在、可用能力位、tracepoint 列表都记录下来，形成节点画像。

第三道门槛是验证器与资源限制。程序越复杂，加载失败的概率越高，指令数上限和栈深度都是硬约束。实践中的做法是把大程序拆成多个小钩子，用 map 共享状态；循环尽量改成固定次数的展开；不要在热路径上做字符串拼接和复杂解析。map 的容量要按基数估算，per-CPU 类型还要乘以 CPU 数量。

CPU 开销需要实测而不是猜。挂载在系统调用上的程序，每个调用都会执行一次，高频服务上很容易积累成可观的占用；bpftool prog show 能看到每个程序的运行次数和耗时。优化的顺序是：先在内核里尽早过滤，再减少 map 操作，最后才考虑采样。把 printf 留在生产程序里是最常见的错误。

权限模型在 5.8 之后清晰了很多。加载程序需要 CAP_BPF，使用性能事件和追踪点需要 CAP_PERFMON，挂载 XDP 与 tc 需要 CAP_NET_ADMIN，更老的内核则统一要求 CAP_SYS_ADMIN。容器里运行采集器时，通常要共享宿主机的 PID 命名空间才能正确映射进程，挂载 /sys/kernel/btf、/sys/fs/bpf 和 tracing 文件系统，并放宽 seccomp 对 bpf() 的限制。能只给能力就不要用 privileged。

最后是容器内的可见性。eBPF 看到的是宿主机视角的 PID，容器里的进程号需要经过命名空间转换；cgroup v1 与 v2 的路径格式不同，解析容器 ID 的代码要分别处理；短命容器可能在事件到达用户态之前就已经退出，元数据要提前缓存或者从 cgroup 快照补全。上线按节点灰度，先验证加载成功率和开销，再逐步扩大；保留总开关，异常时能卸载全部程序。

小结

eBPF 的价值在于把观测点放到数据产生的地方，用验证器换取内核的信任，用 map 和缓冲区把内核态与用户态连接起来。选探针时优先 tracepoint 和 cgroup 钩子，kprobe 只用于补足缺口，并且要为内核升级准备回归；写程序时优先 CO-RE 和 BTF，把偏移问题交给加载器；做安全时把 eBPF 当作证据采集层，而不是不可绕过的防线。

生产落地的关键不在语法，而在约束：内核版本、BTF、验证器限制、map 内存、CPU 开销、能力位和容器可见性，任何一项没确认，都可能在某个节点上以加载失败或者数据缺失的形式暴露出来。先用小工具验证假设，再把稳定的查询固化成产品，是风险最低的路径。
