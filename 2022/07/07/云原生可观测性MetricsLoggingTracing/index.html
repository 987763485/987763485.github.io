云原生可观测性：Metrics、Logging、Tracing

本文属于《Docker 与 Kubernetes》第 40/51 篇
上一篇系列目录下一篇

集群里的故障很少按教科书的方式出现：告警说延迟升高，日志说一切正常，链路里却找不到那次请求。三种信号各自躺在不同的系统里，缺少共同的坐标，排查就退化成在三个界面之间来回猜。本文从 Kubernetes 环境出发，讲清指标、日志、链路三类数据分别怎么采、采上来怎么用同一组资源属性对齐，以及采集链路的成本与保留该如何取舍。理论分层与 OpenTelemetry 规范细节不在本文展开，重点放在集群里的采集与关联落地。

三种信号在集群里的落点

Kubernetes 把一个进程拆成了镜像、容器、Pod、工作负载与节点五层对象，可观测性数据必须挂到这五层中的某一层上才有意义。指标是数值时间序列，采样频率固定、体量可预估，适合回答“有没有异常”；日志是离散事件，单条信息量大但格式随意，适合回答“异常长什么样”；链路是请求级的因果树，适合回答“异常发生在哪一跳”。三者的成本曲线完全不同：指标贵在基数，日志贵在总量，链路贵在采样前的全量开销。

这也决定了采集方式。指标可以周期性地拉，日志必须持续地收，链路只能在进程内埋点后导出。Pod 随时会被调度、重启、漂移，任何依赖 IP 或主机路径的假设都会失效，因此采集组件本身也要以工作负载的形式运行，并依赖 API Server 中的对象元数据为数据补充标签。下文按信号逐层展开，最后再把它们拼回一条排障路径。

指标：四层抓取与拉模型

集群指标大致来自四个层面。节点层由 node-exporter 以 DaemonSet 形式运行，暴露 CPU、内存、磁盘、网络等主机指标；集群对象层由 kube-state-metrics 监听 API Server，把 Deployment 的期望副本数、Pod 的就绪状态、Job 的完成情况转成指标，它不采集资源用量，只描述对象状态；应用层由业务进程自己暴露 /metrics；此外 kubelet 内置的 cAdvisor 接口提供容器级的 CPU 与内存统计。四层缺一不可：只看节点会漏掉 Pod 之间的资源争抢，只看 Pod 又看不到节点磁盘即将写满。

Prometheus 采用拉取模型，按配置周期访问目标。服务发现让目标列表随集群变化自动更新，抓取配置只需描述“抓谁、多久抓一次、保留哪些标签”。

这段配置里真正关键的是 relabel：它把 Pod 的命名空间、名称与所属工作负载保留为标签，后续所有查询、告警与看板才有统一坐标。抓取间隔与超时需要成对设置，超时不得超过间隔，否则一次慢抓取会挤占下一轮。生命周期短于抓取间隔的批处理任务会被拉模型漏采，通常改用 Pushgateway 承接最后一次汇总值。

日志：从 stdout 到后端

容器日志的源头其实只有一个：进程写到标准输出与标准错误，由容器运行时接管，落到节点上的 JSON 文件中。应用不应在容器里自己轮转日志文件；写 stdout 等于把“文件在哪、怎么轮转”交给运行时。节点上的日志目录按 Pod 与容器命名，DaemonSet 采集器只需挂载宿主目录，就能读到本节点所有容器的输出，并借助文件名反查 Pod 元数据。

采集方式有三种取舍。节点级 DaemonSet 是默认选择，资源开销与节点数成正比，与 Pod 数量无关；sidecar 适合输出格式特殊、需要单独解析或多路输出的应用，代价是每个 Pod 多一个容器；应用直接推送适合无法挂载宿主目录的场景，但会把采集逻辑耦合进业务代码。实践中多数集群采用 DaemonSet 为主、sidecar 为例外。

kubernetes 过滤器做的是与指标侧相同的事：调用 API Server 补齐命名空间、Pod、容器与工作负载标签，把一行文本变成带坐标的结构化记录。Merge_Log 会把应用输出的 JSON 字段展开为顶层字段，后续按字段检索比按正则匹配文本可靠得多。多行日志（例如 Java 堆栈）需要在采集端用 multiline 解析器合并，否则一条异常会被拆成几十条互不相关的记录，检索时几乎无法还原。

链路：SDK 埋点与 Collector 中转

链路的起点在进程内。应用通过 OpenTelemetry SDK 创建 Span，把一次请求拆成若干有父子关系的操作，并在跨进程调用时把上下文写入 HTTP 头或消息属性。SDK 负责采样决策、批量导出与资源属性填充，Collector 负责接收、处理与转发，二者的边界要划清：进程内只做与业务强相关的埋点，格式转换、脱敏、重试与扇出都放到 Collector，避免把可观测性逻辑渗进业务代码。

Span 命名要有稳定语义，通常采用“组件 + 操作”，而不是把 URL 原样拼进去，否则聚合视图会被高基数参数打散。资源属性中的 service.name、k8s.namespace.name、k8s.pod.name 应在 SDK 初始化时统一注入，Collector 端再用 k8sattributes 处理器补齐缺失项，应用代码不必感知自己运行在哪个节点上。

Collector 常按两层部署：每个节点一个 agent 负责就近接收与批处理，中心侧一个 gateway 负责尾部采样、脱敏与路由。这个分层有其必要：尾部采样必须看到同一条 trace 的全部 Span 才能判断是否保留，而 Span 会分散在多个节点上，只有在 gateway 层按 trace id 汇聚后才成立，或借助按 trace id 做负载均衡的导出器在 agent 层实现。

让三种信号对上暗号

三类数据能关联，靠的不是统一存储，而是统一的坐标。资源属性是第一层：命名空间、Pod、工作负载、集群这四个维度，在指标标签、日志字段与 Span 属性中使用同一套键名，任何一个界面看到异常，都能用同样的条件切到另一个界面。键名不统一是最常见也最昂贵的返工，改一次要重刷历史数据。

第二层是 trace id。日志里带上当前请求的 trace id，就能从一条错误日志直接跳到完整调用链。实现上可以在日志框架的上下文中读取 SDK 的当前 Span，把 trace id 与 span id 写进每条结构化日志；跨线程与异步回调需要显式传递上下文，否则取到的会是空的 Span。

第三层是 exemplar，它把指标样本与具体的 trace 连起来。启用 OpenMetrics 格式的端点，可以在直方图的桶上附带一个 exemplar，记录落入该桶的某次请求的 trace id；Prometheus 抓取后保存这个引用，Grafana 8 之后的图表可以直接从延迟曲线上的一个点跳到对应链路。

exemplar 只保留少量样本，不会显著增加存储，但它要求应用侧使用支持 exemplar 的 SDK 与暴露格式，属于“埋点时就决定”的能力。

关联的代价是标签基数。把 user_id、request_id、完整 URL 放进指标标签，时间序列数量会随请求量线性增长，轻则内存吃紧，重则 Prometheus 因内存耗尽被杀死。经验规则是：指标标签只放取值有限、可枚举的字段，用户级与请求级的信息留给日志和链路。若确实需要按用户维度聚合，应在日志后端或链路后端完成，而不是塞进指标。

采集架构与成本

把前面几节拼起来，一个典型集群的采集拓扑大致如下。指标走拉取，日志走本地文件加转发，链路走 OTLP 推送，三条线在后端汇合。

flowchart LR
  subgraph 集群节点
    NE[node-exporter] --> P[Prometheus]
    KSM[kube-state-metrics] --> P
    APP[业务应用 /metrics] --> P
    APP -->|stdout| LOG[节点日志文件]
    LOG --> FB[Fluent Bit DaemonSet]
    APP -->|OTLP| OC[OTel Collector]
  end
  P -->|remote_write| TS[(指标长期存储)]
  FB --> LS[(日志后端)]
  OC --> TB[(链路后端)]

拉取模型的优势是目标健康状态明确：抓取失败本身就是一条可告警的信号，目标消失后序列也会按规则标记为过期，不会留下永远上涨的假数据。缺点是跨集群、跨网络域时配置复杂，需要处理防火墙与联邦。远程写入解决了长期存储与多集群汇聚，但它不是抓取的替代品：写入端会丢失一部分抓取语义，远端不可用时本地会积压队列，必须配置队列容量与 WAL，否则重启即丢数据。

日志侧的选择集中在 Fluent Bit 与 Fluentd。前者用 C 编写，内存占用小，适合每节点部署；后者插件生态更丰富，适合做中心聚合与复杂路由。常见做法是节点上用 Fluent Bit 采集并做初步过滤，中心侧用 Fluentd 做解析、补充元数据与多路输出。Collector 作为统一网关的价值在于收口：指标、链路共用一套接收与处理管线，标签改写、脱敏、采样策略只需维护一份；日志也可以接入，但在 0.x 阶段其解析能力仍不及专用采集器，多数团队只把日志的转发环节交给它。

拓扑决定数据往哪里流，成本则决定这些数据能留多久。可观测性的账单通常不是被查询撑大的，而是被写入与索引撑大的。指标侧的成本几乎完全由活跃时间序列数量决定，一条序列在内存中约占数 KB，规模上去后差距是数量级的。控制手段有四个：抓取前用 relabel 丢弃无用目标；抓取后用 metric_relabel_configs 丢弃高基数标签或整条指标；对不需要长期保留的指标缩短保留期；把直方图桶的数量控制在合理范围，桶越多，序列数成倍增加。

日志侧按“必须留、可以采样、可以不采”三级分类：审计与错误日志全量保留，调试日志按比例采样或只在特定命名空间开启，访问日志可以只保留聚合结果。采样要在采集端做，而不是存下来再删，否则存储与索引的开销已经发生。

链路侧的成本由采样率直接决定。头部采样在 SDK 内按固定比例丢弃，实现简单，但会连同长尾错误一起丢掉；尾部采样在 Collector 内先缓冲整条链路，再按错误状态与延迟阈值决定保留，能保住慢请求与异常请求，代价是需要集中缓冲与更复杂的部署。常见组合是头部按 10% 采样、尾部对错误全留。

存储上采用冷热分层：热层保留 7 到 15 天，支撑日常排障与看板；冷层用对象存储承载更长时间，查询频率低、延迟高，适合合规与复盘。分层的关键是查询入口统一，让使用者在同一个界面里无感地跨层检索，而不是记住两套系统。

一次接口超时的排查路径

设想订单服务在晚间触发告警：P99 延迟超过 1 秒，错误率 2%。第一步看指标。按命名空间与工作负载过滤，确认延迟上升的是订单接口而非网关；再切到实例维度，发现只有两个 Pod 异常，其余副本正常，说明不是全局依赖故障，而是局部问题。

第二步定位实例。查看这两个 Pod 所在节点，节点指标显示磁盘 IO 等待升高，CPU 与内存却平稳；容器指标显示两个 Pod 的 CPU 限流次数在告警前十分钟陡增。假设已经具体：限流导致排队。第三步查日志。用命名空间与 Pod 过滤，再按 trace id 聚合，日志里出现成片的上下文超时记录，且都指向同一个下游调用。

第四步追链路。从日志里的 trace id 打开链路，看到订单服务的 Span 中，调用库存服务的子 Span 耗时 800 ms，而库存服务自身处理只有 20 ms，其余时间消耗在连接建立与排队上。回到库存服务的实例指标，发现其副本数在告警期间被缩容，连接池被打满。一次容量变更引发了排队与超时。

这个方法可以固定下来：指标负责“哪里”，日志负责“什么”，链路负责“为什么”。三者靠同一组资源属性与 trace id 衔接，缺任何一环，排查都会退化为猜测。日常应把这条路径固化成看板上的跳转链接，减少告警时刻的检索成本。

小结

在 Kubernetes 中做可观测性，采集只是起点，关联才是目的。指标以拉模型覆盖节点、对象、容器与应用四层，日志以 DaemonSet 为主从 stdout 收集，链路以 SDK 埋点加 Collector 中转。三者靠统一的资源属性、日志中的 trace id 与指标上的 exemplar 串成一条可跳转的路径。成本控制要分别盯住指标基数、日志分级与链路采样率，再用冷热分层平衡保留时间与开支。建议先把命名规范与标签约定定下来，再谈工具选型。
