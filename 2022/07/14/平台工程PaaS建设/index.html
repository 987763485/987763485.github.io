平台工程 PaaS 建设

本文属于《Docker 与 Kubernetes》第 46/51 篇
上一篇系列目录下一篇

不少团队在 Kubernetes 上跑了几年之后，会发现手里多了一套只有少数人敢于改动的系统：YAML 散落在几十个仓库，新服务上线要依次找五个人确认，每个团队的流水线都长得不一样，出问题时没人说得清哪一步才是标准做法。平台工程（Platform Engineering）要解决的就是这类问题。本文从组织与产品化的角度，讨论内部开发者平台的构成、黄金路径的设计、自服务与治理的平衡以及落地顺序。本文只谈能力类别，不绑定具体产品，读完后你应能判断下一步该做什么。

平台工程要解决什么问题

平台工程可以理解为：把基础设施与交付能力封装成产品，让研发以自助方式使用，并由一支专门团队对其体验负责。它要缓解三个痛点。

第一是研发自助。申请一台数据库、开通一个测试环境、接入一条流水线，如果需要走工单、等排期、反复沟通，研发就会被基础设施的节奏拖住。自助不是放任，而是把原本靠人完成的动作变成可重复、可审计的接口。

第二是认知负荷。容器、编排、网络、证书、可观测性，每一块都有独立的知识体系。要求每个业务团队都成为这些领域的专家，既不现实也不经济。平台的价值在于把复杂度收拢到少数人手里，让业务团队只面对少量稳定的概念。

第三是交付一致性。十个团队十套发布方式，意味着十套排障方法与安全策略。一致性不是要求所有人写一样的代码，而是让构建、部署、观测这些横向环节遵循同一套约定，使审计、迁移和故障处理成为可预期的工作。

要理解平台工程，最好把它和两种常见做法放在一起比较。

维度 传统 PaaS 直接使用 Kubernetes 内部开发者平台
抽象层次 应用为中心，屏蔽运行时细节 暴露 Pod、Service 等原语 在原语之上提供面向研发的抽象
自助程度 高，但仅限平台支持的形态 低，需自行拼装工具链 高，常见需求有默认入口
灵活性 低，受语言与中间件限制 高，几乎不设边界 中高，默认路径之外留有出口
一致性 强，由平台统一约束 弱，各团队自行其是 较强，通过模板与策略实现
扩展成本 由厂商决定，周期长 由团队承担，重复投入 由平台团队承担，可复用

传统 PaaS 的问题在于“只此一条路”：最佳实践固化得好，却难容纳非常规需求，业务一旦需要平台未支持的中间件或网络形态，团队只能绕开。直接使用 Kubernetes 则相反：原语齐全却没有默认答案，每个团队都要重新回答“镜像放哪、怎么做灰度、日志去哪看”。内部开发者平台取中间：提供有主见的默认值，同时保留可控的例外通道。

内部开发者平台由什么构成

内部开发者平台（Internal Developer Platform，IDP）不是某一个软件，而是若干能力叠加成的一层：对外表现为几个稳定入口，对内由平台团队维护。按研发从零到上线的路径，通常包含六类能力。

能力 解决的问题 常见交付物
服务目录 服务散落、归属不清 服务元数据、负责人、依赖与等级
脚手架模板 新项目从零搭建、规范口口相传 仓库骨架、构建配置、部署清单
环境申请 环境靠工单排队、长期不回收 按需创建、有效期、资源上限
流水线 各团队重复造构建与发布流程 共享模板、质量门禁、制品管理
可观测性入口 新服务缺少日志、指标与告警 默认仪表盘、采集配置、SLO 视图
权限与配额 权限靠个人授予、成本无人认领 统一身份、角色映射、配额与标签

这些能力本身并不新鲜，难点在于把它们连成闭环。服务目录若不与脚手架、流水线打通，就会退化成手工维护的清单；环境申请若不带配额与有效期，就会变成新的资源垃圾场。

flowchart TD
    A[开发者] --> B[统一入口]
    B --> C[服务目录登记]
    C --> D[脚手架生成仓库]
    D --> E[申请环境与配额]
    E --> F[流水线构建与扫描]
    F --> G[GitOps 同步到集群]
    G --> H[可观测性入口]
    H --> C

闭环有两层含义。数据闭环指目录里登记的服务自动获得流水线与监控，而不必去三个系统注册；反馈闭环指上线后的指标与告警回写到服务信息，排查时能顺着目录找到负责人和依赖。缺少任何一层，平台就只是工具集合，研发仍要自己记住串联方式。

六类能力不必同时具备，也不该由同一个系统提供：门户可以只是入口，背后调用各自 API；目录可先从一份受控配置起步。判断标准不是能力齐全，而是研发完成常见任务时是否还需要求人。

黄金路径：把最佳实践做成默认选项

黄金路径（Golden Path）是被平台团队验证、维护并默认铺好的路径，回答的是“想不出怎么做时，就按这个来”。它通常包含：可直接运行的模板、能通过质量门禁的流水线、默认的部署与观测配置，以及一份说明例外情形的文档。

设计黄金路径有三条原则。

第一，默认铺好，而不是额外申请。新仓库创建时就带上流水线与部署清单，研发不需要知道平台的存在；如果默认路径需要主动开启，采用率一定很低。

第二，允许退出，但让退出有成本。黄金路径覆盖多数场景，不是全部。对确实不适用的服务，应提供明确的例外流程：登记原因、指定负责人、约定复核时间。例外不是失败，失控的例外才是。

第三，把模板当作产品维护。模板一旦生成就不再变化，是很常见的错误。依赖在升级，基础镜像在打补丁，安全基线在收紧，模板必须随之演进。做法是给模板打语义化版本，生成仓库时固定版本；升级时由平台自动提交变更请求并附迁移说明，由服务负责人确认。这样既避免“模板一改，所有仓库漂移”，也避免“模板三年不更新”。

模板腐烂（template rot）是黄金路径最大的敌人。判断方法很直接：用模板新建一个服务，从创建到部署成功需要多久，中间有没有手工补的步骤。如果平台团队自己都不愿意走一遍，模板就已经失效。因此模板必须纳入持续集成，每次变更都在临时环境中真实跑通，而不是只做静态检查。

自服务与治理的平衡

平台最容易走向两个失败方向：一是为了“安全”把所有动作都加上审批，自助名存实亡；二是为了“体验”取消一切约束，半年后资源与权限一团乱麻。平衡点不在于审批数量，而在于把治理做进默认路径。

一个实用的原则是：只在不可逆或高成本的动作上设卡。删除生产数据、暴露公网入口、跨租户访问、申请超规格资源，值得人工确认；创建命名空间、开通日志采集、新建测试环境，应默认放行，用配额和有效期兜底。环境可分沙箱、预发、生产三级：沙箱只受配额约束，预发轻量确认，生产的约束放在流水线门禁里而非工单环节。

成本可见性也是治理的一部分。资源必须带团队与服务标签，账单按标签归集后回写到服务目录，让负责人在看服务状态时顺便看到花费。只做集中账单、不做事后分摊，成本就永远只是财务问题，不会变成工程决策。

安全基线同理。镜像来源限制、非 root 运行、禁止特权容器、密钥不落仓库，应由准入策略统一执行，并在脚手架中预先满足。基线若靠上线后扫描和通报来维持，平台团队就会陷入无休止的追缴。

这要求平台团队把自己当作产品团队，而不是运维窗口：明确用户是新服务团队、存量迁移团队还是数据团队，他们的路径并不相同；公开路线图，说明本季度做什么、不做什么；保留固定的答疑时间与反馈渠道；支持轮值，但把重复工单转化为产品改进项。否则平台会变成“谁声音大就先支持谁”的项目集合。

度量：不要只统计平台使用量

平台的价值最终体现在研发的交付效率与体验上，而不是平台自身的活跃度。建议围绕两组指标建立基线。

第一组是交付表现，可以沿用业界常用的四项：变更前置时间、部署频率、变更失败率、故障恢复时间。对平台而言，还应单独统计“上线时间”，即新服务从创建仓库到第一次成功服务生产流量的时长。它最能反映自助程度，也最容易暴露流程中的隐性等待。

第二组是开发者体验。每季度做一次简短调查，询问研发在环境申请、部署、排障三个环节的满意度与主要阻塞，样本不必大，但要覆盖不同团队；满意度低的地方，往往就是下一次该投入的地方。

需要警惕把“平台使用量”当作核心目标。命名空间数、流水线执行次数、门户访问量都容易上涨，也容易被制造；一旦把点击量写进考核，团队就会优化点击而非交付。度量应分层：新服务与存量服务分开，各团队看分布而非平均值，并先测基线再改动，否则无法判断变化来自平台还是业务波动。

落地路径：先做一件事

平台建设最常见的失败，是一开始就规划“大而全的门户”，用半年集成十几个系统，上线时业务已习惯绕开它。更稳妥的路径相反：先解决一个具体痛点，再逐步扩展。

第一阶段，统一部署。选定一种部署方式（例如以 GitOps 为核心的声明式同步），把试点团队的应用从手工操作迁移过来。这个阶段的目标不是自助而是一致：所有部署都能从仓库追溯到集群状态，回滚有明确动作。范围要小，两三个团队即可，平台团队亲自参与迁移并记录每个卡点。

第二阶段，补齐自助。把第一阶段反复出现的动作产品化：环境申请、流水线模板、脚手架、默认可观测性。每做一项，都用“研发是否还需要找人”来验收。此阶段可以引入配额与成本标签，但不要急着做统一门户，入口可以是命令行工具或现有的代码平台。

第三阶段，再谈门户与目录。当服务数量达到几十个、入口分散到难以查找时，门户才有价值。此时服务目录已经有真实数据，门户只是把它们组织起来。反过来先建门户、再补数据，得到的通常是一个漂亮的空壳。

flowchart LR
    A[统一部署] --> B[补齐自助]
    B --> C[服务目录与门户]
    C --> D[治理与度量闭环]

三个阶段没有严格的界限，但顺序不应颠倒：统一部署建立信任与底座，自助证明平台能减少摩擦，门户才有采用基础。每阶段都应设退出条件，例如“试点团队全部通过流水线发布”“新服务上线缩短到一天以内”，达不到就不进入下一阶段。

小结

平台工程的核心不是再建一个系统，而是把基础设施能力当作产品交付：用自助降低等待，用默认路径降低认知负荷，用统一约定保证一致性。内部开发者平台由服务目录、脚手架、环境申请、流水线、可观测性与权限配额构成，价值来自闭环而非单点能力。黄金路径应默认铺好、允许例外、持续版本化，模板腐烂比缺失更危险。治理要嵌进默认路径，只在不可逆动作上设卡；平台团队要像产品团队一样理解用户与路线图。度量应聚焦上线时间、变更失败率、恢复时间与开发者满意度，而非平台使用量。落地时先统一部署，再补自助，最后谈门户。
