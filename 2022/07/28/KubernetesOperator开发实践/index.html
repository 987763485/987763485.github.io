Kubernetes Operator 开发实践

本文属于《Docker 与 Kubernetes》第 32/51 篇
上一篇系列目录下一篇

本文从开发者的角度梳理一个 Kubernetes Operator 的完整落地流程：先理解调谐循环，再设计 CRD 接口，然后用 controller-runtime 写出可重入的控制器，最后补上清理逻辑、测试与常见坑。读者需要熟悉 Pod、Deployment 与 YAML 的基本写法，读完后应当能独立完成一个中等复杂度 Operator 的骨架，并知道哪些设计会在生产里出问题。

一、Operator 模式：把运维知识写进控制器

在 Kubernetes 里，一个 Deployment 能保证副本数，却不知道“这个数据库集群是否已经完成主从切换”。这类知识通常写在运维手册、值班脚本和人的记忆里。Operator 模式要做的事，就是把这份知识编码进一个控制器，让它像内置控制器一样持续工作。

这里有两个关键词：期望状态与观测状态。用户在自定义资源（CR）的 spec 里声明“我要什么”，控制器负责读取集群里“现在是什么”，然后推着现实往期望靠拢。整个过程不是一次性的脚本执行，而是一个不断重复的循环，社区称之为调谐（reconcile）。

flowchart TD
    A[读取 CR 的 spec] --> B[观测集群实际状态]
    B --> C{两者一致}
    C -- 是 --> D[更新 status 后结束]
    C -- 否 --> E[执行最小变更动作]
    E --> F{动作成功}
    F -- 是 --> A
    F -- 否 --> G[返回错误，交给队列退避]
    G --> A

这个循环有两个重要推论。第一，调谐必须幂等：同一份输入被执行两次，结果应当相同，因为控制器随时可能在任意一步崩溃后被重新唤醒。第二，循环是电平触发而非边沿触发：控制器不关心“发生了什么事件”，只关心“当前电平对不对”，所以丢掉一次事件并不可怕，下一次调谐会把状态补齐。

这也是 Operator 与“写个脚本定时跑”最大的区别。脚本假定世界按预定顺序变化，控制器则假定世界随时会偏离，并准备好一遍遍纠正。理解了这一点，后面所有的设计取舍都会顺理成章：接口要能表达期望，状态要能被观测，动作要能被重复执行。

二、CRD 设计：先把接口定好

CRD 是 Operator 对外的 API，发布之后每改一个字段都要考虑兼容性。笔者建议先把 CRD 当成产品接口来设计，再去写控制器逻辑，否则很容易写出“控制器需要什么就往 spec 里塞什么”的接口，用户却完全不知道怎么填。

spec 与 status 的边界

spec 是用户写的，status 是控制器写的。两者分开不只是命名习惯，更有实际约束：开启 status 子资源后，对主资源的更新不会覆盖 status，对 status 的更新也不会碰 spec，从而避免用户与控制器互相踩踏。status 里应当放观测结果，例如实际副本数、就绪副本数、当前版本、最近一次调谐时间，以及后文要讲的 conditions。凡是能从集群里查出来的事实，都不要再让用户填一遍。

版本、转换与子资源

API 从 v1alpha1 走向 v1 时，不要让旧版本直接消失。惯例是同一个 CRD 提供多个版本，指定其中一个为存储版本，其余版本通过 conversion webhook 转换。controller-runtime 的 conversion 包约定了 Hub、ConvertTo、ConvertFrom 三个方法：Hub 返回存储版本，另外两个负责双向转换。需要提醒的是，转换函数应当无损；如果新版本加了字段而旧版本表达不了，就要想清楚降级时这些数据怎么办，通常的做法是把它们放进注解。

status 之外，还可以开启 scale 子资源，把 spec.replicas 与 status.replicas、status.selector 暴露给 HPA 和 kubectl scale。这样水平伸缩不必为自定义资源单独适配，代价是 status 里必须真实维护副本数与选择器。

三、controller-runtime：Manager、Reconciler 与缓存

controller-runtime 把与 apiserver 打交道的琐碎工作收进了一个库。一个进程里通常只有一个 Manager，它持有共享的 scheme、cache、client，并负责启动所有控制器与 webhook。

Manager 启动后，所有控制器共享同一份 informer 缓存。client 默认是“读缓存、写直连”：Get 与 List 走本地缓存，Create、Update、Delete 直接打到 apiserver。这一点很关键，读操作几乎不产生网络开销，但也意味着刚写入的对象可能短暂读不到，测试里要用 Eventually 而不是立刻断言。

幂等与重入

同一个 key 可能被重复投递，甚至在开了 leader election 之后，新旧副本交接的瞬间仍可能有两个进程同时处理。控制器应当遵循“先读后写、写入前比对”的写法，能用 CreateOrUpdate 的地方不要盲目 Create；更新时依赖 resourceVersion 的乐观锁，遇到 Conflict 就重新读取再试。更关键的是外部副作用：创建云主机、发短信、调用第三方接口，都要有可查询的凭据，例如把资源 ID 记进 status，下次调谐先查再建，而不是假设自己只执行一次。

默认情况下，对象及其子资源的任何变更都会触发调谐。集群规模一大，这会产生大量无意义的循环。predicate 允许在事件进入队列之前过滤：

GenerationChangedPredicate 只在 generation 变化或对象进入删除时放行，status 更新不会自触发。但要注意它同样会挡掉注解与标签的变化，若逻辑依赖注解，需要自己组合 predicate。过滤的尺度是“宁可多调谐一次，也不要漏掉一次真实变更”，因为漏掉之后可能永远等不到下一次事件。

四、生命周期：finalizer、ownerReference 与 conditions

finalizer：删除前的收尾

Kubernetes 的删除是两阶段的。对象带有 finalizer 时，apiserver 只写入 deletionTimestamp，并不真正删除；控制器完成外部清理后再移除 finalizer，对象才消失。这就给了 Operator 一个可靠的收尾窗口。

最常见的错误是清理函数不可重入：第一次删了一半失败，第二次又从头执行，结果报“资源不存在”并永远卡住。清理动作要把“不存在”视为成功。另一个错误是把 finalizer 加在错误的分支里，导致对象刚创建就被打上删除时间戳。

ownerReference：让垃圾回收替你干活

控制器创建的子资源应当设置 ownerReference，并标记为 controller。这样父对象被删除时，Kubernetes 的垃圾回收器会级联清理子资源，通常不必在 finalizer 里手写删除逻辑。

有两个限制值得记住：跨命名空间不能设置 ownerReference；跨集群的外部资源更不在垃圾回收范围内，只能靠 finalizer 兜底。此外，一个子资源只应有一个 controller owner，多个控制器争抢所有权会导致 ownerReference 被反复改写，最终谁也删不掉。

conditions：把判断讲清楚

一个布尔字段 Ready 无法表达“为什么没就绪”。社区惯例是使用 conditions 数组，每条包含 type、status、reason、message、observedGeneration 与 lastTransitionTime。k8s.io/apimachinery/pkg/api/meta 里的 SetStatusCondition 会负责时间戳与状态迁移，避免手写时漏字段：

写入 status 一定要用 r.Status().Update，而不是 r.Update。开启 status 子资源后，后者对 status 的修改会被 apiserver 静默丢弃，表现为“代码明明改了，kubectl 里却看不到”，这是新手最容易耗费半天的坑之一。

用阶段约束顺序

复杂 Operator 往往有多个阶段：创建底层资源、等待就绪、初始化数据、对外服务。若每一步都靠“查一遍再决定”，代码很快会变成层层嵌套的条件判断。较稳妥的做法是在 status 里维护一个粗粒度阶段，调谐时只处理当前阶段及必要的回退，阶段推进必须满足明确条件。需要注意，阶段只是缓存判断结果，事实仍以实际观测为准，否则一次手工修改就会让阶段与现实脱节。

用 envtest 做集成测试

envtest 依赖 etcd 与 kube-apiserver 的二进制，通常用 setup-envtest 预先下载；它会在本地起一个真实的 API 服务器，但不启动 kubelet 与调度器。对控制器来说这刚好够用：CRD 能注册，对象能落库，status 子资源与默认值行为都和线上一致，测试速度又远快于起一个完整集群。

测试里用 Manager 启动 Reconciler，再轮询断言结果。需要注意 envtest 不会真的创建 Pod，所以断言应停在“Deployment 已被创建且字段正确”，而不是等它 Running；需要模拟下游状态时，直接在测试中更新子对象的 status 即可。

测试可以分三层：纯函数单测覆盖名称生成与规格换算，envtest 覆盖控制器与 apiserver 的交互，kind 上的端到端测试只保留少量主路径。三层用例数量大致呈倒金字塔，环境越真实，用例越少，反馈也越慢。

调试阶段，kubectl describe 看事件与 conditions，控制器日志里统一带上 request 的 namespace 与 name，再用 kubectl get --watch 观察对象流转，通常比打断点更快定位问题。

六、常见坑与工程约束

调谐里做阻塞长任务

备份、拉取大镜像、等待云厂商回调，动辄几分钟。同一个控制器对同一个 key 是串行处理的，阻塞会拖慢整个队列。正确做法是提交任务后立刻返回，把任务 ID 与阶段写进 status，用 RequeueAfter 轮询进度；真正耗时的动作应当外置成 Job，让控制器只负责观察结果。

忘记更新 status

用户看不到进度，只能猜；更糟的是 conditions 永远停在旧值，基于它做的告警就会失真。每次状态变化都应落盘，并带上 observedGeneration，让读者知道这份状态对应哪一版 spec。反过来，写入前要做差异判断，没有变化就不要写，否则会引发不必要的更新与事件。

事件风暴

每次调谐都记录一条 Normal 事件，或者更新 status 又触发自身再次入队，都会形成放大循环。事件只在状态迁移时发，并且注意 apiserver 对事件本身有聚合与限流；status 写入前比对，能从源头减少大量无效写入。

watch 太多对象

用 Owns 监听所有 Pod，或监听全集群的 Secret，缓存内存会迅速膨胀。应当按标签、命名空间或字段收窄范围，必要时用 predicate 过滤；对只读一次的外部对象，可以考虑绕开缓存，直接用 APIReader 读 apiserver。

权限过宽

图省事给 cluster-admin，等于把整个集群交给一个可能有 bug 的进程。RBAC 应按实际 verbs 生成，跨命名空间的需求单独评估。还要记得给 CRD 的 finalizers 子资源授权，否则删除对象时移除 finalizer 会失败，对象就永远停在 Terminating。

忽略并发与升级

不开 leader election 却跑多副本，重复创建几乎必然发生；即使开了，交接瞬间也需要靠幂等兜底。升级时不要悄悄改字段语义，例如把同一个字段从“副本数”解释成“分片数”，存量对象会被新控制器误读。加字段优先，改语义则通过新版本加转换来完成。

这些坑的共同点，是把控制器当成了一次性脚本。把它视为一个长期运行、随时重启、可能并发的分布式程序，很多设计自然就保守了：先写状态再动手，先查存在再创建，先收窄权限再上线。

小结

Operator 的难点不在调用 API，而在把运维判断拆成可重复执行的步骤。本文的路线可以概括为：用 CRD 把期望状态表达清楚，用调谐循环把观测与动作接起来，用 finalizer 与 ownerReference 管好生命周期，再用 envtest 把行为固定下来。落地时优先保证幂等与可观测，性能和权限可以迭代收紧。建议从一个只管理单一工作负载的小 Operator 起步，先把状态机与测试跑通，再逐步接管更复杂的中间件。
