发布策略：蓝绿、金丝雀与滚动

本文属于《Docker 与 Kubernetes》第 24/51 篇
上一篇系列目录下一篇

一次发布出问题，损失往往不在代码本身，而在“发现问题太晚”和“回滚太慢”。本文讨论滚动、蓝绿、金丝雀三种发布策略的机制与代价，以及让它们真正可用的配套：探针、优雅停机、指标门禁、数据库兼容与演练。读者应当对容器与 Kubernetes 有基本了解，读完能判断自己的服务该选哪种策略，并知道落地时最容易踩的坑。

先把“部署”和“发布”分开

很多团队口中的发布，其实混了两件事：把新版本的可执行文件放到服务器上，以及让真实用户请求进入新版本。前者是部署，后者是发布。二者合一的时候，唯一的安全阀就是整体回滚；一旦分开，就可以先部署、再小流量验证、最后全量切换，中间任何一步出问题都只影响一部分请求。

本文讨论的三种策略，本质上都在回答同一个问题：新旧版本同时存在时，流量按什么规则、以多快速度从旧版本迁移到新版本。滚动发布让迁移过程连续而细碎，蓝绿发布让迁移接近瞬时完成，金丝雀发布让迁移分阶段并可随时中止。它们没有绝对优劣，只有代价结构不同：

  • 滚动：几乎不增加资源，但新旧版本混跑时间长，回滚要再滚一次。
  • 蓝绿：切换与回滚都很快，但要双份资源，且数据库等共享状态仍是单点。
  • 金丝雀：风险最小、观测最细，但需要流量切分能力与指标门禁，工程成本最高。

还有一个常被忽略的维度：回滚的“可逆性”。代码可以回滚，配置可以回滚，流量比例可以归零，但已经执行的数据库变更、已经发出的消息、已经写下的用户数据，通常回不去。所以发布策略从来不只是流量问题，它必须和 schema 演进、消息兼容一起设计。

还有一条与策略正交的原则：缩小每次变更的批量。一次发布包含三十个改动，与一次只包含一个改动，出问题时的定位成本相差一个量级。把大变更拆成多次小发布，再用功能开关控制功能是否可见，往往比升级发布策略更有效：策略降低的是单次变更的影响面，小批量降低的是变更本身的缺陷密度，两者不能互相替代。如果团队仍是按周合并、一次性上线，应先改工作方式，再谈金丝雀。

理解这组权衡，比记住某个注解怎么写更重要，下面逐个展开。

滚动发布：Deployment 的默认节奏

Kubernetes 的 Deployment 默认就是滚动更新。它通过 ReplicaSet 管理 Pod：新版本创建一个新的 ReplicaSet，控制器逐步扩容新 RS、缩容旧 RS，直到旧 RS 归零。控制节奏的是两个字段：

  • maxSurge：允许超出期望副本数的 Pod 数量，可以是整数或百分比，默认 25%。
  • maxUnavailable：更新过程中允许不可用的 Pod 数量，默认 25%。

二者不能同时为 0，否则控制器无法推进。若 replicas 为 4、maxSurge 为 25%（向上取整得 1）、maxUnavailable 为 25%（向下取整得 1），则滚动期间最多 5 个 Pod、最少 3 个可用。这两个值决定了发布速度与容量冗余之间的交换：想快就加大 maxSurge，想省资源就加大 maxUnavailable，但后者会直接吃掉服务的冗余容量。

minReadySeconds 表示 Pod 进入 Ready 后还要稳定这么多秒，才被视为可用。它是对“启动即崩溃”类问题的廉价防线：如果没有它，一个启动后立刻退出的版本可能在几十秒内滚过全部副本，把一次可控的发布放大成一次全站故障。progressDeadlineSeconds 则在超时后把 Deployment 标记为 ProgressDeadlineExceeded，但请注意，它只改状态，不会自动回滚。Kubernetes 不会因为探针失败就把已经滚过的副本换回去，回滚仍要显式执行：

滚动发布最大的代价是“混跑”。在一段时间里，新旧版本同时接收流量，任何接口或数据格式的不兼容都会以“一部分请求失败”的形式出现，而且失败比例随滚动进度变化，很难复现。另一个隐性代价在收尾：旧 Pod 终止时如果没有优雅停机，正在处理的请求会被切断，表现为发布期间错误率的小幅上升。很多团队把这种上升当成“正常抖动”而忽略，直到某次发布恰好切断了支付回调。

蓝绿发布：把切换做成一次原子操作

蓝绿维护两套环境，蓝色跑当前版本，绿色跑新版本。新版本在绿色完成部署与验证后，把入口流量整体切到绿色；出问题再整体切回。所谓“两套环境”不必是两套集群，在 Kubernetes 里用两个 Deployment 加不同的标签，再让 Service 的 selector 指向其中一套，就足以实现：

这种做法的切换是修改 Service 的 selector，kube-proxy 与入口控制器随后更新后端，通常在秒级完成。代价是切换瞬间所有长连接断开，正在处理的请求可能被丢弃；因此蓝绿必须配合后文的优雅停机，并且要在切换前把绿色环境的容量按全量流量准备好，否则切过去就是过载。

flowchart LR
    U[用户流量] --> G[入口网关]
    G -->|当前 100%| B[蓝色环境 v1.8]
    G -.->|待切换| N[绿色环境 v1.9]
    B --> DB[(共享数据库)]
    N --> DB
    B --> MQ[(消息队列)]
    N --> MQ

蓝绿的优点很直接：切换与回滚都是入口层的一次配置变更，失败时退回旧环境的速度最快；两套环境可以并行做冒烟、压测与数据对比；出问题时旧环境仍然完整，便于排查。它的缺点同样直接：

  1. 资源翻倍。绿色环境在大部分时间闲置，除非你接受“发布时才创建、发布完就销毁”，但那样又失去了快速回滚的能力。
  2. 共享下游没有隔离。数据库、缓存、消息队列不会因为切流而分成两份，schema 不兼容时蓝绿救不了你。
  3. 配置漂移。绿色环境如果长期不用，很容易漏掉证书、环境变量、sidecar 配置，切换后才发现。稳妥的做法是两套环境由同一份模板生成，差异只允许镜像 tag。
  4. 切换不是真正的原子操作。如果切流靠 DNS 权重，客户端的 DNS 缓存会让一部分用户继续访问旧环境很久，移动端尤其明显；要接近原子，应在四层或七层入口上切换后端组，并让旧环境保留一段时间再销毁。

还有一个判断标准：蓝绿适合“新旧版本不能共存”的场景，比如依赖了不兼容的本地状态、需要整体切换的批处理任务。如果新旧版本可以共存，金丝雀通常能以更低的资源成本获得更好的风险控制。

金丝雀发布：用一小部分真实流量试探

名字来自矿井里的金丝雀。做法是先让新版本承接很小比例的真实流量，观察指标，逐步放大比例，异常则把比例归零。与蓝绿相比，金丝雀不要求两套完整环境，但要求流量可切分、指标可比较、决策可自动化。

分流有两个基本维度。按比例分流把请求随机分到新旧版本，比如 5%、25%、50%、100%，适合用户无差别、请求同质的服务。按标签分流则按用户 ID 哈希、租户、地域、设备类型或内部员工等维度固定分配，好处是同一用户始终落在同一版本，不会因为刷新页面而在两个版本间跳来跳去，会话与前端缓存都更稳定；坏处是样本可能不具代表性，内部员工往往网络更好、行为更特殊，不能代表真实用户。

flowchart LR
    S0[新版本 0%] --> S1[5% 观察 30 分钟]
    S1 --> S2[25% 观察 30 分钟]
    S2 --> S3[50% 观察 1 小时]
    S3 --> S4[100% 全量]
    S1 -->|指标越界| R[比例归零并回滚]
    S2 -->|指标越界| R
    S3 -->|指标越界| R

图中的时间只是示意。每一档放量都要回答三个问题：进入条件是什么（上一档指标稳定多久）、观测窗口多长（至少覆盖一个业务周期，支付类要覆盖高峰）、样本量够不够（低流量服务在 5% 档位跑十分钟，可能只有几百个请求，根本不足以发现小比例错误）。这三个问题不回答，金丝雀就退化成“发一点看看，感觉还行就继续”。

金丝雀有几种典型失败模式，值得逐条对照：

  1. 只按比例放量，不做一致性分流。同一用户在两版本间跳，前端本地缓存、登录态、表单草稿都可能错乱，而监控上只看到零星的客户端错误。
  2. 数据库迁移已经全量执行。金丝雀发现问题后把流量归零，代码回退了，但 schema 回不去，旧代码对着新表继续报错。这是把“可回滚的发布”和“不可回滚的变更”混在一起。
  3. 指标只看机器层。CPU、内存、Pod 重启次数都正常，但下单成功率掉了两个百分点，直到客服反馈才发现。
  4. 放量节奏靠人拍脑袋。值班同学在群里说“看着还行”，于是继续放量；没有判定器、没有超时、没有自动回滚，金丝雀只是一次时间更长的全量发布。

还要区分金丝雀与 A/B 测试。A/B 测试是产品实验，按假设分组，关注长期业务指标与统计显著性；金丝雀是风险控制，目标是尽快发现缺陷并止损。把两者混为一谈，会让金丝雀阶段被拿来做产品决策，人为延长新版本的暴露时间，风险反而更大。

流量切分落在哪一层

策略是“怎么放量”，实现则取决于“在哪一层分流”。三种常见落点各有适用边界。

Ingress 层

Nginx Ingress Controller 通过 canary 注解实现权重与定向分流：nginx.ingress.kubernetes.io/canary: "true" 开启金丝雀，canary-weight 指定百分比，canary-by-header、canary-by-cookie 按请求头或 Cookie 定向。控制器会为同一个 host 与 path 生成第二段 upstream，再在生成的 nginx 配置里做分流。

这种方式改造成本最低，适合已经用 Nginx Ingress 做入口的团队。注意几点：多个 canary 注解同时存在时有优先级（header 高于 cookie，高于 weight）；权重是整数百分比，粒度有限；注解名称在不同控制器版本间有过调整，升级前要核对文档。更关键的是，它只管入口流量，服务之间的调用、定时任务、消息消费都不经过这里。

网关层

API 网关按租户、客户端版本、请求头分流，适合移动端“按 App 版本放量”的场景。网关通常还承担鉴权、限流、协议转换，灰度规则与业务身份绑定得更自然，比如“只让 iOS 6.2 以上版本访问新接口”。风险是网关成为全局单点，规则变更需要审计、灰度和快速回滚，不能让一次灰度把全部入口配置改坏。

不论落在哪一层，都要满足三个条件：分流可观测，能查到某个请求为什么走了新版本；规则变更可回滚，且回滚本身经过验证；旁路被覆盖，定时任务、消息消费者、内部 RPC 也要有对应的灰度手段。只切 HTTP 入口而后台 worker 仍在跑旧版本，是灰度发布里最常见的漏洞。

探针与优雅停机：切流的安全底座

前面的策略都假设“新 Pod 准备好接流量、旧 Pod 能体面退出”。这个假设由探针与停机流程保证，缺了它们，再精细的放量也只是把故障切得更碎。

三类探针的职责要分清。readiness 决定 Pod 是否进入 Service 的 Endpoints，失败只是摘除流量，不重启容器；liveness 失败会重启容器；startup 探针用于慢启动应用，在它成功之前 liveness 不生效。发布场景里最重要的是 readiness，因为它直接控制“什么时候可以接流量”。

readiness 的设计有几个原则。第一，不要把下游依赖放进 readiness。如果数据库一抖动，所有 Pod 同时判定自己未就绪，入口会把全部流量摘掉，局部故障被放大成全站不可用；依赖健康应交给熔断、降级与超时控制。第二，readiness 通过不等于能扛流量。连接池预热、JIT 预热、本地缓存加载应当放在 readiness 转绿之前，否则新 Pod 刚进 Endpoints 就会产生一批慢请求。第三，启动时间要匹配参数，initialDelaySeconds 与 periodSeconds 估得太紧会导致 Pod 还没起来就被判定失败，可用 startup 探针替代一段很长的初始延迟。

优雅停机的链路比多数人想象的长：Pod 被删除后进入 Terminating，同时从 Endpoints 摘除，执行 preStop，发送 SIGTERM，等待 terminationGracePeriodSeconds，最后 SIGKILL。有两个经典陷阱：

  1. 摘除 Endpoints 与发送 SIGTERM 是并行发生的，而入口控制器、kube-proxy、客户端连接池更新后端列表都有延迟。结果就是“流量还在来，进程已经开始退出”。常见解法是在 preStop 里先睡几秒，把传播延迟熬过去。
  2. 宽限期太短会切断长请求，太长会让滚动发布卡住。应按请求耗时的 P99 与在途异步任务估算，而不是随手写一个默认值。

应用侧也要配合：收到 SIGTERM 后先把 readiness 置为失败（框架支持的话），停止接受新连接，等待在途请求结束，关闭连接池与消息消费者，再退出。Go 的 http.Server.Shutdown、Java 框架的优雅停机、Node 的 server.close 都是这个模式。只配 preStop 不改应用，进程仍会在睡完后被直接杀掉，效果有限。

会话与长连接是另一个容易被低估的变量。会话存在本地内存的服务，滚动发布会让用户随机掉登录；解决办法是把会话外置到 Redis，或者使用粘性会话。但粘性会话与金丝雀的比例分流存在冲突：你希望同一用户固定在同一版本，而不是固定在同一 Pod。WebSocket、gRPC streaming、SSE 这类长连接不会因为切流而迁移，蓝绿切换会让所有连接同时断开，形成重连风暴；滚动发布则是一批一批断。客户端的重连退避必须带抖动，否则重连会在同一时刻集中发生，把入口打垮。消息消费者没有“流量比例”的概念，灰度要靠消费组、topic 或消息头过滤；新旧版本在同一个消费组混跑时，消息格式必须双向兼容。

指标门禁：用什么判、判多久、怎么自动回滚

门禁是金丝雀的大脑。没有门禁，放量比例只是一组需要人工盯着的数字。

指标至少分三层。第一层是黄金信号：错误率（HTTP 5xx 比例、gRPC 状态码分布）、延迟分位数（P95 与 P99，不要用平均值，平均值会被大量快请求掩盖长尾）、吞吐与饱和度。第二层是业务指标：下单成功率、支付转化率、搜索无结果率、登录失败率。技术指标正常而业务指标下跌，往往是最难发现也最致命的问题。第三层是版本对比指标：同一指标在新旧版本之间的差值，而不是绝对值。绝对值受整体流量波动影响，差值更能反映版本本身的差异。

判定方法从简到繁：

  • 静态阈值：错误率超过 1% 且持续 5 分钟即失败。实现简单，但对低流量服务不敏感，对高峰期又过于敏感。
  • 同比与环比：与上一周期同一时段比较，抵消日内波动，适合有明显作息规律的业务。
  • 双样本比例检验：比较新旧版本的错误率并计算置信区间。样本量是硬约束：要检出 1% 与 1.2% 这样的差异，在常规的 95% 置信度、80% 统计功效下，每个版本需要数万个请求；低流量服务在 5% 档位等一小时也等不到。此时要么按标签定向到高流量租户，要么延长窗口，要么接受“只能发现大故障”的现实，不要把统计检验当成万能钥匙。
  • 分位数比较要谨慎。P99 需要足够样本才稳定，5% 流量下的 P99 实际上只由几十个最慢请求决定，噪声极大。低流量时优先看 P95，或者用直方图分桶后的近似值，并同时观察分布形状而不只是一个数字。

自动判定与自动回滚需要一套明确的状态机：Pending、Progressing、Healthy、Degraded、RolledBack。每个状态有进入条件、退出条件与超时，判定器独立于发布系统运行，避免“发布系统自己证明自己健康”。自动回滚要有刹车：连续失败次数、最小观测时长、人工一键中止，三者缺一不可。回滚动作本身要幂等，回滚后要冻结该版本的重试，防止“回滚、再发布、再回滚”的循环。发布期间可以抑制该服务的部分告警，避免值班被刷屏，但门禁指标本身不能被静音。

观测窗口的长度是个权衡。太短会把启动抖动当成故障，太长会让真实故障的暴露时间变长。经验上第一档十到三十分钟，后续档位随流量比例放大；窗口至少要覆盖一次完整的业务周期，比如一次批量任务或一个计费周期。周末与工作日的流量结构不同，自动放量最好避开无人值守的时段，或者让门禁在夜间更保守。查询侧也有细节：用 rate() 而不是瞬时值，窗口至少是抓取间隔的四倍，否则曲线锯齿会让判定器反复横跳。

数据库变更：唯一不能靠切流解决的依赖

蓝绿和金丝雀都能让代码在秒级回退，但数据回不去。因此发布的真正约束往往不是流量，而是 schema 兼容性。expand-contract 模式把一次破坏性变更拆成可并存的几步：先扩展，让新旧代码都能工作；再迁移数据；最后收缩，删掉旧结构。

以把 users.name 拆成 first_name 与 last_name 为例。扩展阶段新增两列，允许为空，旧代码继续读写 name，新代码同时写 name 与两个新列，读取仍走 name。迁移阶段分批回填历史数据，双写持续一段时间并校验一致性。切换阶段把读路径改到新列，观察一个完整周期。收缩阶段确认没有旧版本实例后，删除 name 列或把它改为生成列。

回填要按主键区间推进，而不是一条没有条件的 UPDATE，后者会制造长事务、锁住大量行、推高主从延迟。每批之间留出间隔，观察复制延迟与慢查询，必要时在低峰执行。ALTER TABLE 也不是免费的：MySQL 8.0 的 online DDL 在加索引、改字符集等场景仍可能锁表或消耗大量 IO，大表应使用 gh-ost、pt-online-schema-change 这类工具，它们通过影子表与增量同步降低对主库的影响。PostgreSQL 11 起新增带默认值的列不再重写整表，但加约束仍建议先 NOT VALID 再加 VALIDATE CONSTRAINT，把持锁时间压到最短。

有三类变更尤其危险。第一类是删除列或重命名列，旧代码一旦还在运行就会直接报错，必须等全量切完、旧版本完全下线后再做。第二类是修改类型或语义，比如把金额从整数分改成定点小数，新旧代码对同一字段的解释不同，双写也无法调和，只能新增字段并迁移。第三类是改变消息格式，消费者必须能同时解析新旧两种格式，且至少保留一个发布周期。

那么不可回滚的变更出错了怎么办？答案是前向修复，而不是寻找撤销按钮。删列前先做备份或保留只读副本；数据订正写错时，准备一份可重复执行的补偿变更，明确影响范围与校验方法；索引建错就再建正确的并删除错误的，不要在高峰期做反向 DDL。原则可以概括为一句话：任何时刻，线上都要存在至少一个能同时读写新旧 schema 的代码版本；数据库变更的“回滚”不是 undo，而是再发一次向前的变更。

演练、开关与发布窗口

策略与工具都齐了，仍然会在真实故障中失效，原因通常是人。发布能力必须通过演练获得，而不是通过文档假设。

回滚演练应当定期做，并且要真的执行到流量恢复为止。测量两个时间：从决定回滚到回滚动作发起，以及从发起到旧版本重新承接全部流量。前者考验决策链，后者考验自动化程度。演练要覆盖四条路径：镜像回滚、配置回滚、数据库变更的前向修复、入口分流规则回滚。只演练第一条，等于只准备了一半。

功能开关把“发布”再拆一层：代码先上线但开关关闭，出问题时关开关而不是回滚部署。它对“新功能引发业务问题”特别有效，因为关闭开关通常比回滚更快，也不受镜像拉取与调度延迟影响。代价是开关会累积，必须有归属人、过期时间与清理机制；一个没人敢删的开关，半年后就会变成无人理解的分支逻辑。开关也不能替代 schema 兼容，它管不了已经写入的数据。

值班交接要写清楚四件事：当前灰度比例与所在阶段、正在观察的指标与阈值、已知风险与待验证项、回滚命令与权限人。发布窗口内明确谁有回滚权、谁有数据库变更权，禁止“顺手发一下”。变更分级同样重要：文案与静态资源可以直接全量；无 schema 变更的服务走金丝雀；支付链路、鉴权、数据库结构属于高风险，必须金丝雀或蓝绿加人工确认与双人复核。

最后是发布窗口与变更冻结。大促、财报、节假日等重要业务活动前冻结变更，冻结期只允许修复性变更并走审批。窗口选择要同时满足流量低谷与人力在位，二者缺一不可：凌晨流量低但没人盯着，白天有人盯着但流量高，折中方案是把自动放量与人工确认结合，低峰自动跑前几档，关键档位留给值守人员确认。

小结

发布策略的本质，是在资源成本、暴露时间与回滚速度之间做交换。滚动发布最省资源，但混跑期长、回滚慢；蓝绿切换最快，但资源翻倍且共享依赖无法隔离；金丝雀风险最小，但依赖流量切分与指标门禁。选择哪一种，取决于服务能否容忍新旧共存、故障影响面有多大、团队是否具备自动化判定能力。

比策略更容易被忽略的是配套：readiness 决定 Pod 何时接流量，preStop 与宽限期决定旧 Pod 如何退出，指标门禁决定放量是否继续，schema 兼容决定回滚是否真的可逆。任何一环缺失，策略都只是表面功夫。

落地建议从低风险服务开始：先把探针与优雅停机做对，再引入按比例的 Ingress 金丝雀与最简单的错误率门禁，跑顺之后再加业务指标与自动回滚。每季度做一次回滚演练，把测到的时间写进值班手册。发布系统的成熟度，最终不体现在 deploy 命令有多酷，而体现在出事时能不能在几分钟内安全退回。
