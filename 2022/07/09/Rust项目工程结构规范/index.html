Rust 项目工程结构规范

本文属于《Rust 学习路线》第 9/68 篇
上一篇系列目录下一篇

代码能编译、能跑通，与代码能被一个团队长期维护，是两件事。本文讨论后者：在 Rust 1.60 前后、2021 edition 的语境下，一个项目应该如何摆放 crate、目录、feature 与依赖，才能让新人在半小时内找到该改的文件，让 CI 稳定地卡住质量问题。文章假设读者已经会用 cargo new 与 cargo run，讲的是工程布局与团队约定；Cargo 的基础命令与模块系统的语法细节不在本文范围内。读完之后，你应当能为自己的项目定下一份可执行的目录规范与检查清单。

一个 crate 还是 workspace

cargo new 默认给出一个 crate。对于脚本、内部小工具、单一职责的库，一个 crate 就够了：编译单元小、依赖图简单、发布时也只有一条命令。工程结构的第一条规范应当是“不要为了看起来专业而拆分”，因为 workspace 带来的是额外的认知成本：每个成员都要有自己的 Cargo.toml，依赖要在根与成员之间分工，CI 需要针对成员做缓存与筛选。

那什么时候该拆？笔者常用的判断信号有三个。其一，编译时间已经成为日常痛点，改一行代码要等整个项目重编；其二，同一个仓库里出现了“库”与“可执行程序”两类消费者，库还要被别的项目复用；其三，某些依赖只在特定产物里需要，比如命令行工具需要参数解析库，服务端不需要，混在一个 crate 里会让所有构建都拖着这份依赖。

若出现 core 反过来依赖 server，说明职责切错了，正确做法是把共用部分下沉成新的 crate，而不是用循环的路径依赖绕过去。另一条经验是把成员统一放进 crates/ 目录，根目录的文件数量可控，新增成员时也不必再改动根目录的结构。

需要记住的还有两条命令：cargo build -p server 只构建指定成员，cargo test --workspace 跑全部成员的测试。workspace 的成员共享一个 target 目录与一份 Cargo.lock，这也是后文讨论依赖锁文件与缓存的前提。

让 src/lib.rs 与 src/main.rs 并存

一个包（package）里允许同时存在 src/lib.rs 与 src/main.rs。Cargo 的约定是：src/main.rs 生成与包同名的二进制目标，src/lib.rs 生成同名的库目标，包名中的连字符在库名里会变成下划线。二者可以共存，互不冲突，这让“库加薄入口”的写法成为 Rust 项目的默认形态。

这样组织的好处很直接：main.rs 只负责读配置、初始化日志、调用库、把错误映射成退出码；业务逻辑全部留在库里。库可以被集成测试调用、被 doctest 演示、被同仓库的其他二进制复用，而写在 main 函数里的逻辑只能靠端到端手段验证。下面是笔者推荐的形态：

当仓库需要一个以上可执行文件时，src/bin/ 是最省事的手段。目录下每个 .rs 文件就是一个二进制，文件名即程序名；src/bin/tool/main.rs 这种子目录形式则生成名为 tool 的二进制，二者都不需要改 Cargo.toml。若某个二进制需要单独配置，再退回显式的 [[bin]] 段：

tests/ 下的每个文件会被编译成独立的 crate，只能调用库的公开 API，因此适合放集成测试：起一个真实的服务、连一个真实的数据库、走一遍协议。共享的辅助函数必须放在 tests/common/mod.rs，因为 tests/common.rs 会被当成另一个测试二进制去跑，里面没有测试函数时会让人困惑。benches/ 放性能基准，社区常用的 criterion 需要在清单里关掉默认的测试框架：

examples/ 的价值常被低估：它既是给使用者的最短上手示例，又会被 cargo test 编译，所以不会随 API 演进而腐烂。docs/ 不参与编译，用来放设计文档与架构决策记录（ADR），与代码同仓库、同评审流程，更容易保鲜。

feature：能力开关，不是业务开关

feature 是 Cargo 的编译期开关，它的语义是“可加不可减”。当同一个 crate 被依赖图中的多个节点以不同 feature 引用时，Cargo 会对 feature 取并集，最终只编译一份。因此 feature 只能用来增加能力，任何“关掉某项行为”的写法都会在依赖合并后失效。

设计 feature 的第一步是确定默认集。默认 feature 应当覆盖大多数使用者的常见路径，让添加依赖之后开箱可用；同时保证 default-features = false 时能得到一个最小、依赖最少的构建，供嵌入式或体积敏感的场景使用：

feature 最大的坑是组合爆炸。三个 feature 就有八种组合，CI 通常只跑默认配置，于是某些组合直到下游启用才第一次被编译。可控的做法是明确“受支持组合”的清单，并在 CI 中至少覆盖三档：默认、--no-default-features、--all-features；feature 数量多时，可用社区工具按 powerset 批量编译，把问题拦在合并之前。

比组合爆炸更危险的是把 feature 当作互斥的业务分支，例如用 enterprise 与 community 两个 feature 区分版本。两者同时被打开时，cfg 分支只会命中一个，另一套代码静默消失，而编译器和测试都不会报错。业务差异应当用类型、trait 或独立的 crate 表达，让“同时启用”在编译期就无意义；feature 只留给可叠加的能力与依赖裁剪。

依赖治理：版本、锁文件与依赖树

workspace 的成员各自写 Cargo.toml，同一个依赖很容易写成 1.0、1.0.52、0.4 三种版本。需要说明的是，本文写作时 Cargo 还没有从根清单一处继承依赖版本的机制，版本仍需在每个成员的清单里分别声明。团队可以用两条约定兜底：一是在根 Cargo.toml 里维护一段注释，记录“基准版本”；二是把 cargo tree 的检查放进 CI，出现重复版本就失败。

版本号本身也有语义。写 serde = "1.0" 等价于 ^1.0，表示允许升级到任何 1.x；写 =1.0.136 才是精确锁定。团队内部 crate 建议同时写 path 与 version：

本地开发走路径，发布到 registry 后路径失效但版本号仍然成立，使用者不会因为缺少版本字段而无法解析。

Cargo.lock 的提交策略按产物类型区分：可执行程序与部署到服务器的服务要提交，因为它记录了整棵依赖树的精确版本，能保证构建可复现、安全审计有据可查；库不提交，把解析权交给下游，避免把某一时刻的间接依赖强加给使用者。workspace 只有根目录一份锁文件，成员不需要各自持有。

排查依赖问题主要靠 cargo tree：

-d 的输出里，同一 crate 出现两个大版本往往意味着编译时间与二进制体积的双重浪费，常见原因是某个中间依赖尚未跟进升级。此时优先推动上游统一，退而求其次用 cargo update -p 把可升级的一侧拉齐；只有在确实无法协调时，才考虑在根清单里用 [patch] 打补丁，并注明原因与移除条件。

最后是一条团队约定：新增直接依赖需要在评审中说明理由，并用 cargo tree --depth 1 看一眼直接依赖的数量，超过约定阈值时，先问一句“标准库或现有依赖能不能做到”。

质量门禁：格式、lint 与文档

前三节解决“放在哪”，这一节解决“怎么保证不退化”。规范如果不落到命令上，最终都会退化成口头约定。

格式交给 rustfmt，配置尽量少。rustfmt.toml 里只写稳定选项，imports_granularity 一类需要 nightly 的选项不要放进主干配置，否则 CI 与本地会因为工具链不同而产出不同结果：

lint 交给 clippy。clippy 的 clippy::all 默认是警告级别，本地跑不会阻断，因此要在 CI 里把它提升为错误：

--all-targets 让测试与示例也参与检查，避免坏代码长期存活。

关于 #![deny(warnings)]，笔者的建议是慎用。它把“当前编译器认为可疑”直接变成编译失败，好处是本地就能拦住问题；代价有三：升级工具链后新增的 lint 会让老代码突然编译不过；下游用更新的编译器构建你的库时同样会失败；某些宏展开出的代码触发警告时，你只能用 #[allow] 去压制，而压制又可能掩盖真正的问题。更稳妥的分工是：源码里保留 #![warn(...)] 与必要的 #![deny(clippy::...)]，把“警告即错误”放在 CI 的命令行参数里，让严格程度随流水线而不是随发布物走。

文档是另一种测试。公开项至少写一句“它做什么”，再按需补 # Examples、# Errors、# Panics 三段；文档里的代码块默认会被 cargo test 当作 doctest 编译并执行，所以示例不会随 API 漂移：

示例里的 # 开头行会被隐藏但仍参与编译，用来放 use 语句，读者看到的就是最短的可运行片段。只跑文档测试可以用 cargo test --doc，它的速度通常比完整测试快，适合放在提交前的钩子里。

发布前的那一遍检查

发布是最不容易回滚的环节：crate 一旦上传，只能 yank，不能删除重发同名版本。因此把检查固化成命令，比记住清单可靠。

先确认元数据。crates.io 页面上的信息全部来自 Cargo.toml，缺字段会让包看起来不专业，也会影响被检索到的概率：

license 与 license-file 二选一，前者填 SPDX 标识符，双许可用 OR 连接；rust-version 声明最低支持的编译器版本（MSRV），并与 README 里的说明保持一致。README 会成为 crates.io 的首页，至少要有安装方式、最小可运行示例、feature 列表与 MSRV，这四样缺一样，使用者就要去读源码。

再确认打包内容。cargo package --list 列出即将上传的文件，重点看有没有把测试数据、证书、.env 一类的东西带进去；cargo publish --dry-run 会完整走一遍打包与校验，包括在隔离目录里重新编译，能在上传前发现路径依赖、缺失文件之类的问题。

workspace 的发布要按依赖顺序进行：先发 core，等 registry 索引更新后再发依赖它的 server，否则后者解析不到新版本。版本号遵循语义化版本，0.x 阶段允许在小版本里做破坏性变更，1.0 之后破坏性变更必须升主版本；同一批发布的成员建议统一版本号，减少“哪个 crate 对应哪次发布”的记忆负担。发布完成后打 git tag、更新 CHANGELOG，并核对 tag 与 registry 上的版本，这一串动作可以用脚本串起来。

小结

工程结构规范的本质，是把“这个人知道该怎么做”变成“工具和目录知道该怎么做”。本文的建议可以归成四条：能用单个 crate 解决时不要拆 workspace，拆分应以编译时间与消费方为信号；让库承载逻辑、让入口保持单薄，测试与示例才有可能被复用和执行；feature 只做可叠加的能力开关，受支持的组合要进 CI；把格式、lint、文档测试与发布检查全部落到命令上，让规范在流水线里生效，而不是停留在文档里。对于已经有历史包袱的项目，不必一次改完，从目录约定与 cargo fmt、cargo clippy 两条命令开始，收益最快也最容易被团队接受。
