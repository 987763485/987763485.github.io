读写分离与分库分表实践

单库单表撑不住业务增长时，团队往往同时面对两个问题：读请求把主库压满，写入量又让单表逼近磁盘与索引的极限。本文不复述主从复制与分片算法的原理，而是按一次真实的容量拐点，把“评估、选型、改造、迁移、验证、回滚”这条落地路径走一遍，重点讲清读写分离的延迟兜底、分片键的取舍、跨分片查询的妥协，以及双写迁移与灰度切流的具体做法。适合准备动手改造的后端工程师阅读。

一、拐点：从一次主库告警说起

那次告警来得很朴素：核心交易库的主库 CPU 连续三天在晚高峰冲到 90% 以上，慢查询日志里排在前面的全是列表页的查询语句。与此同时，订单表的数据量刚过 8000 万行，单表容量接近 200 GB，DDL 变更窗口从半小时拉长到四个小时。这两件事指向两个不同的问题：读压力与单表容量。

评估阶段最忌讳拍脑袋。我们先把指标拆成四组，连续观察两周，下面的数字均做了取整：

  • 读写比例：按业务线分别统计 QPS，交易写入约占 12%，查询占 88%，其中列表页与详情页又占了查询的七成。
  • 峰值与均值：晚高峰 QPS 是日均值的 3.2 倍，扩容必须按峰值再留 30% 余量，而不是按平均值。
  • 数据增长：订单表月增约 600 万行、18 GB，按当时增速，一年后单表将超过 250 GB。
  • 延迟分布：主库 P99 响应时间 180 ms，从库 20 ms 左右，差距主要来自主库上的写入锁竞争。

有了这四组数字，结论才有依据：读压力可以用从库分摊，写压力与容量问题则必须靠拆分。两者不是二选一，而是先后关系。我们先做读写分离，用两到三周拿到收益；同时启动分库分表的方案设计，给后续半年的增长留出空间。

评估还有一个容易被忽略的产出：改造的验收标准。我们当时定下三条硬指标——主库峰值 CPU 降到 60% 以下，列表页 P99 不超过 100 ms，迁移期间数据不一致的记录数为零。没有这三条，后面的灰度与回滚就失去了判断依据。

二、选型：先分清两件事的边界

读写分离解决的是“读请求太多”，分库分表解决的是“单库单表放不下”。前者基本无损，改造量小；后者会改变数据模型与访问方式，是一次伤筋动骨的手术。把两者混在一个项目里做，出问题时很难定位到底是哪一层引入的。

中间件层面，主流的选择大致分两类。一类是 ShardingSphere 这样的客户端方案，以 JDBC 驱动或代理的形式提供分片、读写分离等能力，应用引入依赖后按配置接入；另一类是 MyCat 这样的独立代理，应用把数据库地址指向代理，由代理完成路由与结果归并。前者的优势是少一跳网络、易于随应用发布，缺点是分片规则与应用绑定，跨语言支持弱；后者对应用透明，适合多语言栈，但多一层代理就多一份容量与高可用负担。

我们最终选择了客户端模式：团队以同一种语言为主，升级节奏可控；核心链路对延迟敏感，不希望多一次网络往返；分片规则要随业务灰度调整，改应用配置比改代理更轻。具体配置项随版本差异较大，接入方式才是选型时该关注的点。

还有一个决定值得单独说明：不要为了分片而分片。如果单表在两三千万行、写入压力尚可接受，先做索引优化、归档冷数据、加缓存，收益往往更快。我们的经验线是：单表超过 5000 万行，或单库写入 TPS 持续超过 3000，才把分库分表提上日程。数字因硬件与模型而异，关键是团队有自己的判断线。

三、读写分离：延迟量化与强一致读兜底

读写分离的配置本身很简单，难的是“什么时候不能读从库”。主从延迟不是恒定值，大事务、批量更新、从库机器规格不足、网络抖动都会让它瞬间拉长。上线第一周就遇到从库延迟 40 秒，用户下单后刷新列表看不到自己的订单。

所以第一步是把延迟变成可观测的指标。SHOW SLAVE STATUS 里的 Seconds_Behind_Master 精度有限，遇到大事务会长时间显示 0，随后突然跳变。更可靠的做法是建一张心跳表，由主库定时更新时间戳，从库读出后与本地时间比较，差值即业务视角的延迟。同时用 GTID 位点做精确判断：

WAIT_FOR_EXECUTED_GTID_SET 返回 0 表示从库已追平，返回 1 表示超时。有了它，强一致读就有三种兜底手段，按成本从低到高排列：

  1. 会话粘连：同一会话内，写操作之后的若干秒内读请求强制走主库。实现上可在请求上下文里打时间戳，读路由时判断是否在窗口内。简单有效，适合“写完立刻看结果”的场景。
  2. 按 GTID 等待：写操作返回时把当前 GTID 带给客户端，后续读从库前先等待该位点。语义最准确，代价是可能多等几十毫秒。
  3. 直接走主库：对账、支付回调、库存校验这类绝对不能读到旧数据的读，标记为强一致读，永远路由到主库，不参与分摊。

读流量的分配也要有层次，不能平均分给所有从库。我们的做法是按业务打标：商品详情、文章列表这类可容忍秒级延迟的读，轮询走从库；订单状态、账户余额这类敏感读，走主库；报表类的大查询单独指向一个只读实例，避免拖垮在线从库。

最后是故障切换后的读路由。从库提升为主库的瞬间，旧主库上尚未同步的事务会丢失，应用若还按旧拓扑读，就会读到回退的数据。切换后必须做三件事：刷新数据源拓扑、清空会话粘连状态、对强一致读降级为拒绝并提示重试。这部分逻辑应收敛在统一的数据源路由组件里，不要让业务方各自实现。

四、分片键：最不该事后补救的决定

分片键一旦定下，后续所有查询都要围绕它设计，改动成本接近重做一次迁移。我们评估了三个候选：用户 ID、订单 ID、下单时间。

按下单时间分片最省事，冷热数据自然分离，归档方便。但它的致命伤是热点：写入都落在当前时间对应的分片上，其余分片全部空闲，等于没有分。按订单 ID 哈希分布均匀，可要查“某个用户的订单列表”，请求就会扇出到所有分片。

按用户 ID 分片则兼顾了两者：同一个用户的订单集中在同一分片，列表查询是单分片操作，写入也足够均匀。代价是按订单号查询时需要先知道用户 ID，而很多入口只拿到订单号。常见解法有两种：一是让订单号生成时携带用户信息，比如取用户 ID 哈希的低几位作后缀，查询时反解分片；二是维护订单号到用户 ID 的映射表，查询时先查映射再定位。

五、跨分片查询：把代价算清楚再动手

分片之后，SQL 的写法会发生实质变化，团队里每个人都要建立“这是单分片还是全分片”的直觉。

带分片键的等值查询最理想，路由到一个分片，行为和单库一致。不带分片键的查询就只能广播到所有分片，再由中间件归并结果。归并本身不复杂，麻烦的是排序与分页：ORDER BY create_time LIMIT 20 OFFSET 10000 会被改写成每个分片取一万零二十条，再在内存里排序截取，分片越多、翻得越深，开销越离谱。

分布式事务也是同样的思路：能规避就不要引入。我们把事务边界收敛到单个分片内，跨分片的步骤改用本地消息表加补偿，接受最终一致。对账、退款这类必须原子的操作，则在业务上保证相关数据落在同一分片，比如把订单与其支付流水都用用户 ID 分片。

六、迁移：双写、影子表与灰度切流

改造代码只是前半程，真正决定成败的是数据迁移。我们把它拆成五个阶段，每个阶段都有明确的进入条件与回退动作。

flowchart LR
    A[双写开启] --> B[存量数据搬迁]
    B --> C[影子表比对]
    C --> D[只读切流灰度]
    D --> E[写切换与旧库退役]
    E --> F[回滚预案待命]

双写是第一步。应用同时向旧库与新分片写入，以旧库为准，新库的失败只记录不阻断。双写要放在数据访问层统一收口，不要在业务代码里散落两套写入逻辑，否则漏写点几乎必然出现。

存量搬迁按分片键分批进行，每批几千行，记录位点，可中断可续跑。搬迁期间旧数据仍在变化，所以每批结束后要根据主键回查一次增量，避免漏掉搬迁过程中被修改的记录。

影子表比对是保证一致性的关键。准备一张结构相同的比对表，定期对同一批主键比较关键字段的摘要值，不一致的记录写入差异表修正。比对要覆盖全量一轮、增量若干轮，差异率连续三天为零才允许进入下一阶段。

灰度切流先切读、后切写，按用户维度而非随机比例。同一个用户的所有请求必须落在同一侧，否则会出现“列表能看到、详情打不开”的怪象。比例从 1% 起步，观察错误率、延迟与差异表，再逐步放大。

回滚必须提前演练，而不是写在文档里。读流量回滚只需切开关；写回滚则要停双写、确认新库数据已同步回旧库、再切回旧路径。演练时故意在 10% 阶段制造一次失败，团队才知道真正的耗时是多少。

七、扩容与七个反复出现的坑

业务继续增长，分片也要扩容。成倍扩容最稳妥：8 个库扩到 16 个库，旧库的数据按规则整体拆到新库，路由从对 8 取模改为对 16 取模，旧数据无需逐行迁移。代价是需要一段短暂停写窗口，保证搬迁期间没有新写入落错位置。非成倍扩容要逐行重算，风险高一个量级。

最后列出我们与同行都踩过的坑：分片键选错导致热点，只能靠二次拆分补救；跨库 JOIN 在分片后无法执行，必须在应用层拼装或冗余字段；全局唯一 ID 不能再用自增，需换成雪花算法或号段服务；深翻页与模糊查询在广播后性能骤降；统计报表把在线库拖垮；事务边界跨了分片，出现部分成功；以及最隐蔽的一条——运维脚本与订正工具仍按单库连接，绕过路由直接改了一张物理表。

小结

读写分离与分库分表是两件事，先评估再选型，能靠索引、归档与缓存解决的不要急着拆分。读写分离的难点在延迟兜底与会话级一致读，分库分表的难点在分片键与跨分片查询。迁移始终遵循双写、比对、灰度、可回滚的节奏，扩容优先选成倍方案。把路由规则收进统一组件、把报表移出在线库，能避开大部分事后才发现的坑。
