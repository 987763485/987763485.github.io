服务注册中心选型实践

本文属于《Go 微服务架构》第 14/35 篇
上一篇系列目录下一篇

微服务拆到十几个之后，服务地址从配置文件搬进注册中心，选型问题就绕不开了：Consul、Eureka、Nacos、etcd 都能注册和发现，功能清单看上去也差不多，真正决定成败的却是一致性模型、健康检查口径和团队的运维能力。本文不推导注册与发现的基本机制，那部分留给同系列的原理篇；这里只做一件事，把四类方案放回真实的架构约束里，给出可执行的选型维度、典型组合与迁移路径。读完之后，你应当能在一张纸上写清楚：我们选哪个、为什么选它、迁移时先动哪一步。

一、先把问题摆正：注册中心承担了什么

三种需求被混在了一起

在多数团队的架构讨论里，“注册中心”同时背着三份工作：服务注册与发现、配置下发、分布式协调。三件事对数据的要求差别很大，却常被一句“上一个注册中心全办了”打包处理。于是出现两种错位：拿强一致的协调组件承担高频心跳注册，实例每次上下线都要走共识；或者拿最终一致的注册表当配置中心，改完半分钟才生效，运维以为没保存，又改了一遍。

本文的主轴只有一条：服务注册与发现。配置下发只作为加分项或约束来讨论，配置中心本身的对比另有专文；注册、心跳、推送的机制也已在原理篇讲过。本文关心的是决策：在同一组约束下，哪类方案更不容易在半年后变成负债。

注册表的数据性质决定了设计取向

注册表里的记录很小：一个服务名、一组地址、若干元数据。它的读写比例极度倾斜，实例上线、下线、心跳续约是写，调用方拉取或订阅是读，而读的次数远多于写。更关键的一点是，注册表的数据是可重建的派生数据：实例本身还在运行，注册中心丢了记录，客户端重新注册一次就能恢复。这与订单、账务那种“丢一条就是事故”的数据有本质区别。

数据性质决定默认立场。对账务库，默认是“宁可不可用，也不能读到错的”；对注册表，更常见的默认是“宁可短暂看到旧实例，也不要让调用链因为注册中心不可用而瘫痪”。这不是审美偏好，而是由数据可重建、错误可被调用方兜底推出来的。理解这一点，后面关于 CP 与 AP 的争论才不会变成站队。

四类方案的能力圈并不重合

把候选方案摊开看，它们最初的定位差别很大。下表只描述定位与能力范围，不涉及具体版本特性。

Eureka Netflix 的中间层服务发现 强 无 无 需自行扩展
Nacos 注册与配置一体的平台 强 强 弱 有命名空间方案

表格里的“强”与“弱”是相对定位，不是质量评价。etcd 标为“需自建”，不是说它不能做，而是它只提供带租约的键值语义，服务名怎么组织、健康状态怎么表达、客户端怎么缓存全要自己定。选型的第一步是确认自己需要哪几列，而不是比功能多少。

二、CAP 在注册中心里的真实含义

分区不是理论假设

讨论 CAP 最容易跑偏的地方，是把它当成“三选二”的考试题。在注册中心的语境里，分区很具体：机房之间的专线抖动几十秒，一个节点因宿主机故障失联，某个机架的交换机重启导致一半实例心跳中断。分区发生时，注册中心要选的其实只有一件事：继续返回最后已知的实例列表，还是拒绝返回并报错。选前者，调用方可能打到已下线的实例，但链路还在转；选后者，如果所有客户端都依赖这次查询才能发起调用，失败会瞬间扩散成全站不可用。多数注册中心的默认答案是前者，这就是偏向 AP。

“一致性”其实有两层，别混为一谈

很多争论源于把两层一致性当成一层。第一层是注册中心集群内部各副本之间的一致性：一个客户端刚注册的实例，另一个客户端能不能立刻查到。第二层是注册中心视图与服务真实状态之间的一致性：某个实例的进程已经挂了，注册中心多久才能知道。第二层任何方案都做不到实时，只能靠健康检查的窗口去逼近，它属于机制问题，不是 CAP 问题。

所以当我们说 Consul 或 etcd 是 CP 时，承诺的是第一层：写操作要多数派确认，少数派一侧不接受写，也可能读不到最新数据。它从来没有承诺过“注册表里没有死实例”。反过来，说 Eureka 是 AP，也不是说它“数据一定错”，而是说分区时它让每个分区继续用自己的副本提供服务，接受短暂的不一致。把两层分开，很多争论就能看出双方其实在说不同的事。

四个方案在这一点上的实际选择

Eureka 是典型的 AP：节点之间异步复制注册表，分区时各分区照常接受注册与查询，恢复后再收敛。它还有一个常被误解的设计叫自我保护：当续约失败的实例比例超过阈值，服务端不再剔除任何实例，因为大规模失联更可能是网络问题，而不是所有服务同时崩溃。代价是真实的大面积故障发生时，死实例会在注册表里多留一段时间，调用方必须靠重试与熔断兜底。

Consul 与 etcd 走 Raft，写需要多数派，因此是 CP。但工程上都有折中：Consul 允许显式的过期读，DNS 接口也可配置为返回稍旧的结果；etcd 提供串行化读与线性一致读两种模式。这些开关说明一件事：即使底层是 CP，读多写少的注册场景也会被调成“读可以旧、写必须一致”。

Nacos 的情况最容易被简化成一句话，而这句话往往是错的。它同时支持两类实例：临时实例靠客户端心跳，走 AP 风格的分布式协议；持久实例由服务端主动探测，走 CP 风格的共识协议。同一个注册中心里可以并存两种语义，选型时必须明确“我们注册的是哪一类实例”，否则讨论 CP 还是 AP 没有意义。

该偏 A 的地方偏 A，该偏 C 的地方偏 C

把三件事分开看，结论就清楚了。注册发现的数据可重建、错误可由调用方兜底，应当偏 A；配置是人的意图，读到旧值可能导致错误行为，因此更偏 C，但通常只要求单调读加最终一致，并不需要线性一致；选主与分布式锁必须偏 C，否则两个节点同时认为自己持锁，后果比不可用严重得多。

这也解释了为什么成熟架构里常见“注册发现用一个组件、选主用另一个组件”，而不是强求一个组件把两种语义都做到极致。听到“既能当注册中心又能当分布式锁”时，该追问的是：它靠什么在两种模式间切换，边界清不清楚，团队里有多少人理解这条边界。

三、四类方案的横向剖析

下面按“它原本为解决什么问题而生”来逐个看。同一个功能在不同方案里的实现方式差别很大，而这些差别最终都会变成运维时的心智负担。

Consul：以目录为中心，检查做在 Agent 上

Consul 的部署形态是每个节点跑一个 Agent，Agent 再连到少数 Server 组成的共识集群。服务可以写在配置文件里，也可通过 HTTP 接口提交，健康检查跟着服务走：HTTP、TCP、脚本、TTL 都支持，检查由本机 Agent 执行，Server 只保存结果。好处是检查流量走本地回环，不随服务数量增长压到中心节点；代价是每台机器、每个 Pod 都要有 Agent，节点一多，Agent 的生命周期管理本身就是一项工作。

它的接口形态最丰富：HTTP API、DNS 接口、基于 Gossip 的成员管理。DNS 让老系统不改代码就能接入，但也容易让人以为它只是个 DNS 服务器，忽略背后的目录与 ACL 体系。多数据中心是原生能力：每个 DC 有独立的 Server 集群，DC 之间通过 WAN Gossip 交换成员与目录摘要，跨 DC 查询由本地 Server 代理。代价是概念不少，ACL、Gossip 加密、证书轮换都要有人管。

Eureka：客户端自治，AP 取向最彻底

Eureka 几乎把“客户端自己管自己”写进了架构：实例定时续约，服务端只做轻量的注册表维护与节点间复制；客户端本地缓存整份注册表并定时拉增量，服务端不可达时也能靠缓存继续调用。它没有配置能力，没有强一致的协调原语，也没有原生的跨数据中心复制，跨 Region 高可用要靠部署多套。

需要客观看待的是它的维护状态。Eureka 2.0 的开发多年前就已停止，官方继续维护 1.x 分支；Spring Cloud 体系里相关模块也早已进入维护模式，新特性很少。这不等于它不能用，大量存量系统仍在稳定运行，它的简单恰恰是优点。但对 2022 年启动的新项目来说，把 Eureka 作为首选需要理由，而不是默认。

Nacos：注册与配置一体，两种语义并存

Nacos 的出发点是做“更贴近国内使用习惯”的服务与配置平台，控制台、命名空间、分组、权重、元数据这些日常概念做得比较完整。它的注册模型分临时实例与持久实例：前者靠客户端心跳，掉线后由服务端剔除；后者由服务端主动探测，客户端不说话也不会被误删。健康检查因此是“心跳加探测”的混合体，选型时按业务选实例类型，不要照抄示例配置。

推送机制上，早期用 UDP 通知客户端，丢包靠轮询兜底，后续版本改为长连接，实时性与可靠性都有改善。多数据中心不是它的原生强项：更常见的做法是每个 DC 部署一套，用命名空间做隔离，再在入口层做路由。另一个容易被低估的依赖是外部数据库，库的可用性就是注册中心可用性的一部分。

etcd：只给你积木，语义自己定义

etcd 是强一致的键值存储，给上层的原语只有三样：带租约的键、Watch、事务。它没有“服务”概念，也没有健康检查概念，实例活着就续租，租约到期键就消失。注册就是把地址写到某个前缀并绑定租约，发现就是 Watch 这个前缀。正因为不定义语义，做成注册中心的每条规则都得自己写：服务名怎么分层、多版本怎么共存、临时不可用与永久下线怎么区分。

它的优点是边界清晰、单机部署简单、Watch 是真正的流式推送而不是轮询。缺点是这些“自己定”的部分会变成团队独有的隐性知识，换人维护时成本很高。还有一个常见误区是复用 Kubernetes 自己的 etcd 来存业务注册数据，这会让集群升级、容量规划、备份恢复互相牵制，除非规模极小，否则不建议混用。

四、推送还是拉取：延迟、抖动与客户端缓存

三种通知模型

从调用方多久能看见变化来看，四类方案可归成三种模型。一是定时拉取，客户端每隔一段时间取全量或增量，Eureka 是代表；实现简单、服务端无状态，代价是感知延迟等于拉取间隔。二是阻塞查询，客户端带上次的版本号发起请求，服务端有变化才返回，Consul 属于这一类；比轮询省资源，但连接数与超时要调好。三是流式推送，服务端维护订阅关系，变化时主动下发，etcd 的 Watch 与 Nacos 的长连接都是这一类；延迟最低，代价是服务端要记住订阅关系。

推送不是免费的。订阅关系本身是状态，服务端重启、客户端重连、网络抖动都会让它短暂失真，所以成熟的实现都会保留兜底的全量同步。看到“纯推送、零延迟”的宣传，应先问兜底机制是什么，断连期间漏掉的事件怎么补。

sequenceDiagram
    participant App as 服务实例
    participant Reg as 注册中心
    participant Caller as 调用方
    App->>Reg: 注册并建立租约
    loop 心跳周期
        App->>Reg: 续约或健康上报
    end
    Caller->>Reg: 订阅服务列表
    Reg-->>Caller: 返回全量列表

客户端缓存才是可用性的底线

无论选哪个方案，真正让系统在注册中心故障时撑住的，是调用方本地的注册表缓存。这一点常被忽略：大家盯着注册中心部署了几个节点、有没有跨机房，却没问过客户端拉取失败时会不会清空缓存。缓存策略通常有三种：失败时保留旧值、失败若干次后清空、按条目过期。对注册表来说，第一种几乎总是对的，因为清空意味着调用方立刻失去所有地址，局部故障被放大成全站故障。

缓存还带来两个必须提前设计的细节。一是冷启动：进程刚起来、本地没有缓存，注册中心恰好不可用，是快速失败还是允许用镜像里的快照启动？核心链路通常选带过期时间的快照，并让健康检查在拿到新列表后放行。二是缓存里的死实例：中心已剔除而客户端还没收到通知，这段窗口只能靠重试与超时兜住。

五、选型维度表与决策路径

把前面的机制差异落到决策上，需要一张能开会用的表。下表列的是提问方式，而不是打分项，因为同一维度在不同团队里的权重差别很大。

维度 要问的问题 倾向
规模 服务数十个还是数百个，实例数是否上千 小规模优先选运维面小的方案
语言栈 是否以 Java 为主，是否有 Go、Python 多语言客户端 Java 为主可优先 Nacos 或 Eureka
是否已有 K8s 工作负载是否已全部在集群内 全在集群内优先用 Service 与 DNS
配置中心 是否还需要配置下发、灰度开关 需要则优先一体化的 Nacos 或 Consul
多数据中心 是否跨机房、跨地域部署，是否有容灾要求 有则优先 Consul 或每 DC 独立部署
运维能力 团队是否能维护共识集群、证书与 ACL 人力紧张时选组件少、依赖少的方案
网络与合规 是否跨公网、是否有等保与审计要求 跨公网必须加密并用 ACL 收口

用这张表有两个常见错误。一是把“功能最全”当成“最合适”，为只用注册功能的小团队引入需要专人维护的共识集群。二是忽略语言栈的隐性成本：以 Go 为主、只有两个 Java 服务的团队选 Nacos，会发现示例与排查资料大多围绕 Java 生态。

如果一定要给出一条路径，可以按下面的顺序排除：先问工作负载在不在 Kubernetes 里，在的话先看 Service 与 DNS 够不够；不够再问是否需要跨集群、跨 VM 的统一视图；然后问是否同时需要配置中心；最后才比运维成本。

六、典型组合与它们的边界

全在 K8s 内：先把 Service 与 DNS 用尽

如果所有工作负载都在 Kubernetes 里，最常见的正确答案是根本不引入额外的注册中心。Service 提供稳定的虚拟地址与 DNS 名，Endpoints 由就绪探针维护，Pod 不健康就自动摘除；无头 Service 还能给 StatefulSet 的每个 Pod 一个稳定域名。服务之间用 http://order-svc 这样的名字调用，解析由 CoreDNS 完成，注册表的维护责任交给了控制器。

这条路的边界也要说清楚。DNS 有缓存，TTL 决定了变更的感知速度；跨集群、跨 VPC 的调用没有现成答案，要么用服务网格的控制面，要么手工维护 Endpoints；CoreDNS 只负责解析，不做健康判断，健康语义完全依赖就绪探针。容易出问题的是最后一点：探针写得宽松，注册表里就长期挂着不可用的实例，而此时没有人会怀疑 DNS。

混合部署：Consul 或 Nacos

集群外还有大量虚拟机、物理机，或者需要跨机房统一视图时，才轮到独立注册中心。多数据中心、非 Java 技术栈、需要 KV 与 ACL 的场合，Consul 更顺手，它的服务定义可以直接写在配置里：

Java 存量为主、同时想要配置中心的团队，Nacos 的落地阻力更小，实例管理与配置编辑在同一个控制台，不必切换两套界面。代价是对外部数据库的依赖，以及跨 DC 要自己设计多套部署。

纯 Go 的小规模场景：etcd 加一层薄封装

服务数量在几十个以内、团队以 Go 为主、已经有 etcd 运维经验时，用租约加 Watch 自己封一层是可行的。关键是别把它包装成“平台”，只做三件事：注册时写入带租约的键，进程内定期续约，订阅方 Watch 前缀并维护本地缓存。健康语义就是租约，进程死了续约停止，键自动过期，不需要额外的探测逻辑。

这层封装的成本主要不在代码，而在规则：key 的层级怎么定、实例下线与临时故障怎么区分、客户端缓存何时失效。团队里必须有人能回答这些问题，否则半年后它会变成没人敢动的黑盒。

Eureka 的存量位置

已经在 Spring Cloud 体系里跑了多年 Eureka 的团队不必急于迁移，它的客户端缓存与自我保护在真实故障里表现出了韧性。合理的做法是设定退出条件：当需要配置中心、需要跨机房，或版本升级导致维护成本上升时，再启动迁移。

七、迁移与双注册

先双写，再切读

从 Eureka 迁到 Nacos 或 Consul，风险不在注册数据本身。注册表是可重建的派生数据，丢了再注册一次即可；真正的风险在调用方的发现路径，一旦切换过程中出现“新中心里没有这个实例”，调用方就会立刻报错。因此迁移的第一步不是改调用方，而是让应用同时向两边注册，读取仍然走旧中心。这样新中心的数据可以先跑一段时间，用来看它的完整性和稳定性。

双写要处理失败语义：新中心写失败不应阻塞启动，否则等于把新组件的可用性变成启动依赖；但失败必须打点告警，否则双写会静默退化成单写。稳妥的做法是给双写加开关，按服务灰度打开，先在非核心服务上验证。

按调用方灰度切读

读的切换应当以调用方为单位，而不是以服务为单位。同一个服务一半调用方读新中心、一半读旧中心，出问题时影响面可控，也便于对比两边的实例集合。切换前先做影子比对：定时从两个中心各拉一次同一服务的列表，比较地址集合与数量，差异持续为零一段时间后再切。这个脚本不复杂，却能提前发现命名空间、分组、元数据映射上的错配，而这些恰恰是迁移中最常见的坑。

收尾与回滚

切读之后，旧中心建议保留只读两到四周，覆盖一个发布周期与一次月末高峰。下线前确认没有客户端仍在拉取，看访问日志或连接数，不要只凭“应该都切完了”。回滚路径要提前演练：把开关切回旧中心，验证调用方能在缓存过期前恢复。

迁移期间还有一个隐蔽问题：两个中心对同一实例的剔除时间不同。旧中心靠心跳超时，新中心可能靠服务端探测，同一个半死不活的实例在两边状态不一致，流量分配就会偏。双注册阶段要接受这种偏差，把调用方的超时与重试配好。

八、四类典型故障的复盘

注册中心全挂，缓存撑住了，但发布没撑住

一次机房网络调整，注册中心集群整体不可达约二十分钟。调用方凭本地缓存继续调用，核心链路没有中断，这部分符合预期。真正出问题的是期间的一次发布：新实例启动后注册失败，调用方完全不知道它们存在，扩容等于没做；恢复后增量拉取补齐，但发布窗口已经错过。教训有两条：客户端在拉取失败时必须保留旧缓存；发布与注册中心的维护窗口要互斥，注册中心不可用时应当冻结发布。

健康检查误杀引发的连锁过载

某服务的探活超时设得很短，一次垃圾回收停顿让一批实例同时探活失败，注册中心把它们全部摘除。剩余实例承接全部流量，负载上升后响应变慢，探活继续失败，摘除范围扩大。根因往往不是注册中心，而是探活参数与运行时特征不匹配。改进方式是把探活超时与 GC 停顿、线程池饱和的观测值挂钩，并在摘除前先停止向该实例分配新流量。

推送风暴

大促前的批量扩容，一次上线两百个实例，订阅方在几秒内收到海量变更事件，处理线程排队，注册表更新反而滞后，注册中心的 CPU 也被广播吃掉一块。后来改成按服务合并推送、限制单次事件数量，并把扩容分批执行。推送模型不只看平均延迟，还要看峰值的放大倍数。

跨数据中心的共识代价

把两个机房的节点组成一个共识集群，看起来是“高可用”，实际把写延迟绑在了专线上。专线抖动时写请求超时、心跳续约失败、实例被成批剔除，而起点只是一次几十秒的网络抖动。注册中心应按机房自治，跨机房只做目录同步与只读查询。

小结

注册中心选型的核心不是功能清单，而是三个判断：注册表是可重建的派生数据，因此默认应偏向可用性；分区时要明确系统是返回旧列表还是拒绝服务，并把这一行为写进预案；配置与选主属于另一类数据，不要用同一个组件硬扛两种语义。Consul 适合多数据中心与混合部署，Nacos 适合 Java 存量与注册配置一体，etcd 适合规模不大且愿意自己定义语义的团队，Eureka 适合作为存量继续运行。全在 Kubernetes 内时，先用尽 Service 与 DNS；迁移时先双写、再按调用方灰度切读、最后保留只读期收尾。真正决定故障表现的，往往是客户端缓存策略与探活参数，而不是选型会上比较的那几行功能。
