Claude Code 使用指南

在终端里让模型读代码、改代码、跑测试，是过去一年多里不少团队私下尝试的做法；但把它做成边界清晰、可以日常使用的产品，2022 年年中还很早。标题所指的这类工具在本文写作时尚未定型，也没有公开可用的实现，因此本文不介绍某个具体软件，而是讨论这一类命令行 AI 编程助手的设计与用法。读者需要会一点 Python 与 bash，读完后应当能自己搭出一个最小可用的封装，也知道哪些权限不能轻易交出去。

先界定问题：它和补全助手不是一回事

2021 年起，代码模型已经可以通过 API 调用：给一段提示，返回续写、解释或者补丁。IDE 里的补全助手也已经出现，能根据光标前后的内容提示下一行。这类工具解决的是局部写作，人始终坐在驾驶位上，接受或拒绝一个片段，成本很低。

命令行助手的野心更大一些。它面对的是整个仓库和一个可验证的目标，例如“把日期格式化统一到工具函数”“修掉这个失败的测试”。为了做到这一点，它至少要承担三种职责：收集与任务相关的文件、生成一份可执行的改动、在本地执行验证。三者可以塞进一个脚本，也可以拆成几个子命令，但缺一不可。缺了收集，它只能猜；缺了验证，它无法知道自己对不对；缺了回滚，一次错误就会污染工作区。

为什么放在终端而不是编辑器里？因为仓库、构建脚本、测试与版本控制本来就在终端里。模型给出的改动可以直接落到工作区，用 git 记录，用测试判定成败。与在聊天窗口里粘贴代码相比，差别不在模型的智能程度，而在于改动是否进入了可追溯、可回滚的工程流程。补全助手优化的是输入速度，命令行助手优化的是“一个任务从提出到验收”的闭环。

本文只讨论这条链路。语义检索与多个助手的分工属于别的话题，这里不展开。

一条最小回路：读、改、验、回滚

把这类工具的所有功能剥掉，剩下的是一条闭环。任何一环缺失，它就从助手退化成自动改文件的脚本。

flowchart TD
    A[任务描述] --> B[收集上下文]
    B --> C[生成计划]
    C --> D[人工确认计划]
    D --> E[生成补丁]
    E --> F[应用到工作区]
    F --> G[运行验证：类型检查、lint、测试]
    G -->|通过| H[审查 diff 并提交]
    G -->|失败| I[回滚到检查点]
    I --> B

“读”这一步，模型并不能自己翻文件系统，翻文件的是脚本。脚本决定把哪些内容放进提示，也就决定了模型能看到的世界。这一步的质量，往往比换一个更大的模型更能决定结果。

“改”这一步，要求模型输出补丁而不是整份文件。补丁有两个好处：体积小，便于人逐行审查；应用失败时能立刻发现上下文对不上，而不是悄悄覆盖掉别人的改动。统一 diff 格式是通用语言，git 可以直接检查和套用。

“验”必须是客观信号。测试、类型检查、lint、构建，任何一项都比“模型说它改好了”可靠。验证脚本应当固定下来，由人维护，不能由模型现场生成，否则它会写一个必然通过的检查。

“回滚”是最容易被忽略的一环。回滚的成本决定了你敢给它多大权限：如果一次失败要花十分钟手工清理，人很快就会放弃使用；如果一条命令就能回到干净状态，才谈得上放手让它试。

上下文：放得准，而不是放得多

提示的容量有限，而且按 token 计费。把整个仓库塞进去既不现实，也没有必要：无关文件会稀释信号，模型很容易模仿隔壁模块的写法，把项目里早已废弃的模式又抄回来。

一份够用的上下文通常由三层组成。第一层是任务，写清楚期望行为、验收方式，以及不能碰的部分，例如“不要改数据库结构”。第二层是代码，只放与任务直接相关的片段，带路径和行号，方便模型在补丁里定位。第三层是约定，包括目录分层、命名习惯、错误处理方式、依赖限制；这些内容从仓库里的贡献指南、lint 配置和相邻的同类文件里读，比在提示里长篇描述更可靠。

找文件靠检索，但这里说的检索是朴素的文本检索。用 grep 或 rg 按符号名、错误信息、路由字符串定位，再沿调用关系向外展开一跳，通常就能覆盖一次改动的范围。命中太多时按被引用次数排序，或者优先保留测试文件，只取前若干个。每个片段按函数或类的边界裁剪，保留文件头与 import，省略的地方明确标注“此处省略若干行”。静默截断到半个函数，是让模型编造代码的常见原因。

仓库变大之后，一次收集很难准。可行的做法是分两遍：第一遍只给目录树、任务描述和两三个入口文件，让模型回答“还需要看哪些文件、各自为什么需要”；第二遍按这份清单精确收集，并设一个数量上限。清单本身也要校验，模型可能凭想象列出并不存在的路径，脚本要先检查文件是否存在，再决定是否放进提示。

还有一条约定：应用补丁后检查改动文件列表，超出预期就整体拒绝。上下文给得再准，也挡不住模型顺手改无关文件。

安全边界：默认不信任

给模型执行命令的能力，等于给它一份工作区的写权限。所有设计都应当从这个前提出发。

第一道是命令白名单。验证脚本里只出现测试、类型检查、lint、构建，以及 git 的只读查询。不要提供任意 shell，也不要把解释器直接暴露给模型。黑名单永远列不全，rm 可以换成 find -delete，curl 可以换成别的方式；只有白名单是可审计的，新增一条就要人看一次。

第二道是工作区隔离。用容器或独立用户运行，只挂载当前仓库，家目录、ssh 目录、云凭据目录一律不挂，其余路径只读。就算某条命令删错了东西，损失也限于一个可以从版本库重建的目录。

第三道是敏感文件排除。.env、私钥、证书、部署脚本里的令牌，都要在收集阶段被过滤掉。原则是让它们根本不进入提示，而不是叮嘱模型不要看。日志同样要处理：打印上下文摘要时对疑似密钥做脱敏，避免密钥顺着日志进入另一台机器。

第四道是网络。默认断网，需要安装依赖时走内网镜像并记录请求。断网防的不只是下载恶意包，也防数据外带：私有代码一旦进入外部端点，就再也收不回来。

第五道是人。提交之前必须看 diff，重点看被删除的行、新增的依赖、锁文件、CI 配置与权限相关代码。模型很少怀着恶意改代码，但它会“顺手”做很多你没要求的事。

还有一类输入值得警惕：README、issue 模板与注释里可能出现“忽略之前的指示”之类的句子。脚本应把这些内容标注为数据，系统提示里明确文件内容不是指令，但最后一道闸仍是执行层的白名单。

工程习惯：小步、检查点、计划先行

用 git 做检查点。每次任务开始前确认工作区干净，或者先提交、先 stash；助手在独立分支上工作，分支名带上起点提交号。这样“回到上一次正常状态”是两条命令的事，而不是凭记忆手工撤销。

每次只改一件事。任务描述里只放一个可验收的目标。把“重构工具函数、顺手升级依赖、再改一下 CI”混在一起，失败之后很难判断是哪一步出的问题，diff 也无法逐段审查。拆开之后，每一段都能单独验证、单独回滚，失败的经验还能复用。

让模型先输出计划。计划包括要改哪些文件、每个文件改什么、准备用哪条命令验证。人确认之后，再让它生成补丁。审十行计划比审一百行 diff 便宜，也更容易发现方向性错误。计划里出现不存在的文件或测试命令，通常说明上下文不够，应该退回收集阶段。

测试先行。先写一个能复现问题的失败测试，确认它确实失败，再让模型改实现，直到测试通过。测试是人和模型共同的目标，也是最便宜的验收标准；对重构类任务，则先确认现有测试全绿，改完仍然全绿。

失败之后做最小回滚。只撤销最后一次补丁，保留日志与报错，把失败原因压缩成一句“上次这样做导致了什么”，放进下一轮提示。不要在一次失败之后让模型“再试一次大的”，那通常会把工作区推得更远。

最后是成本控制。每轮都要重发上下文，会话越长越贵，也越容易跑偏。一个任务结束就重开，把结论写进任务描述，不要依赖聊天历史。

局限：它会自信地犯错

这类工具最危险的地方，不是明确地说“我不会”，而是用完全正确的语法写出一段不存在的东西。

最常见的是幻觉 API：编造库里没有的函数、拼错的参数名、从未存在过的配置项。代码读起来顺畅，运行即报错。类型检查与官方文档核对是可靠的拦网，所以动态语言项目尤其要谨慎，最好在验证脚本里加一道静态检查。

其次是忽略项目约定。每个项目都有自己的错误封装、日志字段、分层方式，模型倾向于写出通用的、教科书式的代码，和周围文件格格不入。lint 能挡一部分，剩下的靠代码审查，必要时把关键约定写成几条硬约束放进提示。

第三是跨文件改动不完整。改了函数签名却漏掉某个调用方，改了配置项却忘了同步文档。计划阶段就让模型列出全部调用点，验证阶段靠编译器和测试兜底。

第四是过度修改与长任务漂移。顺手重命名、调整缩进会让 diff 膨胀，掩盖真正的改动；上下文被截断后，开头定下的约束又会消失。可以在应用补丁后统计改动行数，超过阈值就要求拆分，并把关键约束每轮重复一次。

兜底顺序可以固定下来：类型检查、lint、单元测试、集成测试、人工审查。越靠前的环节越快越便宜，也越应该自动执行。

小结

命令行 AI 编程助手在 2022 年仍处于早期，产品形态远未定型，本文讨论的是这一类工具的通用结构，而不是某个具体软件。它的核心是一条闭合回路：收集上下文、生成计划、生成补丁、执行验证、失败回滚，任何一环缺失都会让工具变得不可信。上下文要准不要多，检索靠符号与报错定位，大仓库用两遍收集控制范围。安全上坚持白名单、隔离工作区、排除敏感文件、断网运行、提交前看 diff。工程上用小步任务、git 检查点、计划先行与测试兜底。把这些做扎实，模型的能力才有稳定的落点。
