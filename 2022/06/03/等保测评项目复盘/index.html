等保测评项目复盘

很多团队第一次做等级保护测评，都是从一份“整改清单”开始的：测评机构进场，开出一堆问题，运维连夜改配置、补文档，最后勉强拿到一份结论。过程看似走完了，但项目延期、预算超支、业务抱怨、同样的问题第二年再犯，几乎成了常态。本文不复述具体测评要求，而是以一个中等规模业务系统完成等保 2.0 测评的全过程为线索，复盘立项、定级、范围界定、差距分析、整改排期、证据准备、现场配合与问题闭环这些项目动作，说明谁该牵头、钱和工期花在哪里、哪些坑可以提前避开。文中涉及的数量、比例与工期均为示意，不代表任何真实项目的数据；本文也不提供法律意见，具体定级与合规判断应以主管部门和测评机构的意见为准。

立项：先把它当成一个项目

等级保护测评很容易被当成一次“安全大检查”，交给运维负责人兼职推进。这个定位一开始就错了。测评要动制度、动网络、动应用、动预算，还要在限定时间内协调多个部门，它具备典型项目的全部特征：有明确交付物、有硬性时间点、有资源约束、有跨部门依赖。用项目管理的方式组织，是后面所有环节能顺利推进的前提。

组织与分工

比较稳妥的组织结构分三层。最上面是领导小组，由分管信息化或安全的负责人牵头，职责是拍板范围、批准预算、协调跨部门资源，只在关键节点开会，不介入具体技术细节。中间是项目组，通常由信息安全部门或信息化管理部门担任项目经理，负责计划、进度、风险与对外接口。下面按系统成立执行小组，每个系统指定一名系统负责人，业务部门出业务接口人，运维团队出系统、网络、数据库、中间件各方向的责任人。

这里有两个分工原则值得强调。第一，业务部门不能缺席。测评访谈会问数据分类、账号审批、业务连续性要求，这些问题运维答不了，临时拉人更容易答错。第二，运维负责“改”，安全负责“判”，业务负责“认”。让运维自己判断某项差距要不要改、改到什么程度，容易出现两种偏差：要么过度加固影响业务，要么用“业务不允许”搪塞过去。正确的做法是安全团队给出判定与建议，业务负责人确认影响与窗口，运维执行并留证。

测评机构是外部合作方，不是项目组成员。它负责按标准测评并出具报告，不替甲方做整改决策。需要特别提醒的是独立性：如果一家机构既做整改咨询又做测评，结论的公信力会被质疑，实践中应尽量避免，确需咨询时另选一家。

预算与工期

预算一般分三块：测评服务费、整改投入、内部人力与停机成本。整改投入往往被低估，它不只是买设备，还包括软件改造、日志存储扩容、堡垒机与双因素令牌、备份介质，以及为恢复演练投入的测试环境。以示意口径看，一个中等规模系统的整改投入通常是测评服务费的数倍，内部人力折算下来也不低。立项时把这三块分开列，比笼统写一个总数更容易获得批准，也方便后续核算偏差。

工期可以按阶段估算，下图是一个示意性的推进顺序，实际项目会有重叠与回退。

  D --> E[证据准备与内部自查]

立项阶段还要产出一份项目任务书，写清目标系统、定级结果、测评范围、里程碑、预算口径、风险与假设。任务书不用很长，但必须经过领导小组确认。它的作用不是存档，而是在后续出现“这个系统要不要测”“这笔钱谁出”“业务不停机行不行”的争议时，提供一个共同的判断基准。最常见的立项失误，是把测评压给一个兼职的运维工程师，既没有预算授权，也没有跨部门协调能力，项目从第一天起就注定延期。

定级与范围：先决定“测什么”

定级和范围界定是项目里最容易“想当然”的两步，也是后期返工成本最高的两步。系统定低了，监管不认；范围划大了，预算和工期兜不住；范围划小了，漏掉的资产在测评现场被翻出来，整改都来不及。

定级看什么

定级的基本方法在 GB/T 22240-2020《信息安全技术 网络安全等级保护定级指南》中给出，核心是两条线：业务信息安全和系统服务安全。前者看信息被破坏后对客体的侵害程度，后者看服务中断后对客体的侵害程度，两条线分别定级，最终取较高者。客体包括公民、法人和其他组织的合法权益，社会秩序与公共利益，以及国家安全。听起来抽象，落到操作上就是三个问题：系统里存的是什么数据，数据泄露或篡改会影响谁；系统停多久业务受不了，谁会受影响；影响范围是单个单位、一个行业，还是更广。

定级不是安全部门关起门来填表。比较有效的做法是先由系统负责人写初稿，安全部门校准，再请业务、法务与外部专家评审。二级以上系统需要到公安机关备案，三级及以上通常还要经过专家评审和主管部门核准，取得备案证明后才进入正式测评流程。定级结果会直接决定测评要求的强度、测评周期和监管关注度，因此宁可多花两周讨论，也不要在测评前临时改级。

范围怎么划

范围界定要回答的是“哪些资产、哪些管理活动属于这次测评”。一条实用的边界是：承载定级对象业务功能的全部组件，加上支撑这些组件运行的基础设施与管理面。具体来说，至少包括业务应用及其 API、数据库与中间件、操作系统与虚拟化平台、网络与安全设备的管理面、堡垒机、日志平台、备份系统，以及机房或云环境、相关管理制度和人员操作记录。

云上系统要特别注意责任划分。云平台自身的等级保护由云服务商负责，云上的业务系统仍需由租户自己定级、备案和测评；租户不能拿云服务商的测评报告当作自己的结论。同理，托管在 IDC 的系统，机房与网络可以复用部分证明，但主机、应用、数据和管理制度仍在自己的范围内。

资产梳理的产出是一份可用于测评的清单，字段至少包含资产名称、IP 或实例标识、所属系统、等级、责任人、操作系统与中间件版本、是否互联网暴露、承载数据类型、是否在本次范围。清单不是越全越好，而是要能解释每一台设备为什么在或不在范围内。常见漏项包括：只统计生产环境却漏了灾备中心，只统计主机却漏了对象存储与云数据库，只统计总部却漏了分支机构，只统计员工访问却漏了第三方代维通道。每漏一项，现场就可能多出一条不符合项。

差距分析：把标准翻译成整改清单

范围确定后，下一步不是立刻改配置，而是搞清楚“现在差多少”。差距分析的质量，决定了整改排期是否可信。做法上可以并行四条线：文档审查、配置核查、人员访谈和工具扫描。

文档审查看制度与记录是否齐全、是否现行有效、是否与实际一致。配置核查按资产类型逐项比对基线，主机看账号、口令策略、审计服务、端口与服务、补丁，数据库看账户权限、审计开启、备份策略，网络设备看管理方式、ACL、日志外发。人员访谈用来验证“纸面制度”有没有被执行，例如账号申请走了什么流程、离职账号多久停用、备份恢复上一次演练是什么时候。工具扫描包括漏洞扫描与配置核查工具，用来发现手工容易漏掉的问题，但扫描结果只是线索，不能直接当作差距结论。

差距台账建议按“控制域加资产类型”聚合，而不是逐条抄标准。比如“日志留存不足”可能同时涉及主机、数据库、网络设备和应用四类资产，分散记录会变成几十条重复任务，聚合成一条工程任务反而更容易排期和验收。台账字段可以这样设计：编号、控制域、涉及资产、现状描述、差距、风险等级、整改建议、责任部门、预估工时、目标完成时间、所需证据。最后两列很关键，它们把差距分析和后面的证据准备、现场测评连了起来。

这一阶段有三个典型误区。第一，只做技术核查，忽略管理制度与执行记录，结果技术项改完了，管理项大面积失分。第二，把“文档里有”当成“已经落实”，制度写了双因素，实际登录只输口令，访谈一问就露馅。第三，用一份漏洞扫描报告代替差距分析，扫描器看不到权限分离、备份演练、剩余信息保护这些内容。差距分析结束时，应当能回答一个问题：如果明天就测评，哪些项能过、哪些项过不了、过不了的打算怎么办。答不上来，说明分析还没做完。

整改排期：高风险先做，证据优先

差距台账出来以后，最忌讳的是“按清单从头改到尾”。人力有限、窗口有限，必须排序。排序可以看四个维度：风险高低，即问题是否可被直接利用、是否暴露在互联网、是否涉及敏感数据；依赖关系，例如日志集中留存要先有日志平台和存储，权限收敛要先有统一身份源；实施成本与停机影响；证据价值，即该项是否属于测评必查、是否容易验证。

按这四个维度，可以把整改事项分成四档，下表是示意性的划分方式。

优先级 典型事项 判定理由 排期策略
P0 立即 互联网暴露的弱口令与默认口令、已知高危漏洞、边界开放的高危端口、核心数据无备份 可直接导致入侵或数据丢失 一周内走紧急变更
P1 本轮必做 双因素鉴别、日志集中与留存、权限收敛、备份恢复演练、剩余信息保护 标准要求明确，测评必查 四到六周，随版本发布
P2 计划内 制度修订、审批记录补齐、终端管控、补丁周期 需要组织配合，见效慢 与制度评审同步
P3 长期 可信验证、全流量审计、异地灾备中心 投入大，依赖架构调整 纳入年度规划，先给补偿措施

P0 的判断标准只有一个：现在能不能被利用。弱口令、默认账户、未修复的远程代码执行漏洞，不需要等测评，发现当天就该处理。P1 是测评的主体，也是最容易挤在一起的部分，排期时要拆到周，明确每项的责任人和验收人。P2 往往被拖到最后，但管理项在测评中占比不低，建议与制度修订同步推进，避免现场临时补记录。P3 不必强行在本次测评前完成，可以在整改报告中说明计划，并给出过渡期的补偿措施，例如网络隔离、访问白名单、加强监控。

排期还要给测评留出缓冲。一般建议在现场测评前留两周作为变更冻结期，只做配置核对、证据整理和访谈演练，不再上线大改动。新改的东西没有经过观察期，测评时反而容易暴露新问题。整改方案与测评机构沟通时，可以询问判定口径和取证方式，但不能要求对方降低标准；测评机构也不应参与具体整改实施，否则独立性无法保证。

六类高频技术整改

不同系统的整改清单差别很大，但有几类问题几乎每次都会出现。下面按控制方向梳理常见做法与坑，重点在工程落地，不逐项解释测评要求。

身份鉴别与口令策略

目标是把“每一次登录”对应到唯一的人或服务。基础动作包括：账号实名、一人一号、禁用或改名默认账户、清理长期不用的账号；口令设置长度与字符种类要求、定期更换、不得重复使用最近若干次；连续失败后锁定或延迟，锁定策略要防止被用来拒绝服务；远程管理一律走加密通道，关闭明文 Telnet 与 HTTP 管理页面；重要系统在口令之外增加第二种鉴别手段，动态口令、数字证书或堡垒机加令牌都可以。

常见的坑是应用自建账号体系绕开了统一认证。堡垒机做得再好，业务系统自己留一个后门账号，整条链路就失效了。另一个坑是口令明文存放，配置文件、启动脚本、数据库连接串里都能翻到，整改时应一并改为加密存储或密钥管理服务托管。

访问控制与最小权限

核心是最小权限、默认拒绝、权限分离。系统管理员、安全管理员、审计管理员应由不同人员担任，避免一个人既能改配置又能删日志。应用侧按角色授权，角色与岗位对应，不直接给个人开权限；数据库业务账号只授予必需的库表权限，禁止应用使用高权账号连接；操作系统通过 sudo 白名单收敛，而不是全员 root。账号的生命周期同样重要，入职、转岗、离职都要有对应的权限变更记录，离职账号当天停用。

这项工作难在持续。一次性收敛不难，难的是三个月后又长出一批临时权限。比较现实的做法是季度权限复核，由系统负责人确认在册账号与权限，复核记录本身就是测评要看的证据。

日志审计与留存

日志要解决三件事：记得全、留得住、查得到。覆盖范围应包括操作系统、数据库、中间件、网络与安全设备、堡垒机、应用系统，记录登录退出、提权、配置变更、账号增删、数据导出等关键行为。所有设备统一时间同步，否则跨设备日志拼不出时间线。日志集中采集到独立平台，采集账号只写不删，平台本身限制管理员删除权限；留存时间按《网络安全法》的要求不少于六个月，容量要按峰值估算，而不是按平均值。

审计员岗位要独立于系统管理员，审计记录定期查阅并留下查阅记录。只部署日志平台、从不看日志，在现场访谈时很难自圆其说。

入侵防范与补丁

思路是做减法加闭环。最小安装，关闭不需要的服务、端口、共享和示例应用；管理面限制源地址，只允许运维网段或堡垒机访问；建立漏洞管理流程，从发现、评估、测试、上线到验证形成闭环，高危漏洞有明确的修复时限；补丁先在测试环境验证再上生产，无法及时打补丁的用虚拟补丁、访问控制或 WAF 规则作临时补偿，并记录理由与期限；主机与终端部署恶意代码防护，保证覆盖率和特征库更新；条件允许时限制出站访问，降低主机被控后的外联能力。

数据备份与恢复演练

备份的关键不是“有没有备”，而是“能不能恢复”。至少要做到重要数据本地备份加异地备份，备份介质场外存放，备份数据加密，备份账号与生产账号分离。针对勒索软件风险，应保留一份离线或不可变副本，避免备份系统被一并加密。恢复演练建议至少每年一次，记录实际恢复耗时与数据丢失量，与业务约定的目标对比；演练不要只恢复一个文件，要覆盖数据库、应用配置和依赖服务，否则真出事时仍会手忙脚乱。

剩余信息保护

这条最容易被忽略。鉴别信息与敏感数据所在的存储空间在释放或再分配前应被清除，包括删除文件后的磁盘块、数据库回收的表空间、应用产生的临时文件与缓存、退役或返修的硬盘与终端。虚拟化与云环境下，释放的存储卷是否真正擦除，要向平台方确认。开发测试环境使用生产数据时，必须先脱敏，测试结束后及时清理。介质报废应有销毁记录，而不是随手扔进仓库。

证据准备：让配置“可被看见”

测评现场时间有限，测评人员不可能把所有配置从头翻一遍，多数判断依赖你提供的证据。证据准备的目标，是让每一项要求都能在几分钟内被定位、被理解、被验证。

有效证据通常满足三点：制度写清楚做什么，记录证明实际做了，现场配置与两者一致。三者缺一，都会被追问。截图是最常用的证据形式，建议统一规范：截取完整屏幕，包含系统标识或主机名、当前账号、时间、配置路径和关键参数；不要只截一个局部输入框；敏感信息可以打码，但不能打到无法判断配置内容；配置文件导出时保留关键行并注明来源主机。命令输出、平台报表、工单记录、会议纪要都可以作为辅助证据。

比较稳妥的做法是建立一份证据索引，按控制域和资产类型列出证据编号、对应文件、存放位置、责任人。测评人员问到某一项，直接按索引调取，比现场翻目录高效得多。常见缺陷包括：截图没有时间与主机标识，无法证明是哪台机器；制度是网上下载的模板，没有发布文号与签字；执行记录集中在测评前一周补齐，时间戳一眼就能看出；资产清单里的版本号与实际登录看到的不一致。这些问题不涉及技术难度，却最容易造成“做了但证不出来”的尴尬。

现场测评与问题闭环

现场阶段是项目压力最集中的几天，准备充分与否，差别非常明显。进场前要完成几件事：确认测评方案，包括范围、时间、人员、工具和抽样方式；准备临时账号与只读权限，避免测评人员使用个人账号或共享账号；排好访谈时间表，业务、运维、安全、人事各接口人明确；对漏洞扫描与渗透测试出具书面授权，约定速率限制与禁止操作，生产环境提前做快照或备份；确认业务低峰窗口，避免扫描影响交易。

现场通常从首次会议开始，双方确认范围、日程、接口人和沟通机制。随后并行开展文档核查、配置核查、访谈和工具测试。建议每天结束前开一个短会，把当天发现的问题逐条确认，形成问题确认单，由双方签字。当场确认事实，比报告出来后再争议有效得多。有些问题属于理解偏差，当场解释清楚就可以消除；有些确实是缺口，早确认就能早安排整改。

测评结束后的闭环同样需要管理。把不符合项按性质分类：配置类可以立即修改并补证，制度类需要走修订与发布流程，架构类需要立项或纳入长期规划。能当场改的，改完留好证据；不能当场改的，在整改报告中写清计划、责任人和补偿措施。复测前先内部自查一遍，确认整改证据与当前配置一致。需要提醒的是，任何情况下都不要干扰测评、不要伪造记录，也不要把“包过”当作项目目标；测评的价值在于暴露真实风险，而不是买一张证书。

复盘沉淀：把一次测评变成长期能力

测评通过不是终点。复盘会议建议在报告出具后两周内召开，参与人包括领导小组、项目组、各系统负责人和运维骨干。议题不局限于“过了没有”，而要回答四个问题：进度偏差出在哪，是范围变更、依赖未就绪还是业务窗口冲突；成本花在哪，哪部分超支、是否值得；问题分布有什么规律，是集中在某类资产还是某个控制域；哪些问题去年提过、今年又出现，根因是缺流程还是缺工具。

沉淀物至少包括四样：一份持续维护的资产台账，新增系统、下线系统、变更边界都要更新；一套配置基线，用脚本或配置管理工具固化，新机器上线即合规；一个证据模板库，把这次有效的截图规范、记录表单、索引结构复用下去；一张测评日历，按系统等级记录下次测评时间，提前三个月启动。更进一步，可以把测评要求映射到日常流程：上线安全检查表、变更评审、漏洞管理、日志巡检、年度备份演练，让合规成为日常动作的副产品，而不是每几年一次的突击。

人员方面，建议培养一到两名内部“等保接口人”，既懂标准又熟悉系统，能够承担日常自查、外部沟通和证据管理。外部测评机构会换，内部接口人稳定，项目的连续性才有保障。

小结

等保测评是一个典型的跨部门项目，技术整改只是其中一部分，更多工作花在定级、范围、排期、证据和沟通上。立项时明确牵头人与预算，定级时把业务和专家拉进来，范围界定以资产清单为抓手，差距分析按控制域聚合，整改坚持高风险先做并给测评留出冻结期。六类高频技术整改要以可验证为目标，证据准备做到制度、记录、配置三者一致。现场测评当天确认问题，事后分类闭环，最后把台账、基线、模板和日历沉淀下来，下一次测评才不会又从零开始。
