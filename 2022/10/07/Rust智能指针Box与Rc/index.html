Rust 智能指针 Box 与 Rc

本文属于《Rust 学习路线》第 16/68 篇
上一篇系列目录下一篇

所有权让 Rust 在没有垃圾回收的前提下管住了内存，但它只覆盖了“一个值一个所有者”这一种形态。真实程序里还会遇到递归类型、多个持有者、共享之后仍要修改、跨线程共享等情况，这时就需要标准库提供的几类智能指针。本文按 Box、Rc、RefCell、Arc 与 Mutex 的顺序讲清它们各自解决什么问题、代价是什么，再用一张对照表和一组常见坑帮助读者做选择。本文面向已经理解所有权与借用规则的读者，示例基于 Rust 1.60 与 2021 edition。

一、所有权不够用的三个时刻

Rust 默认把值放在栈上，要求类型大小在编译期已知，并且同一时刻只有一个所有者。这三条约定简单有力，却在一部分场景里显得局促。笔者把它们归纳为三类。

第一类是大小无法在编译期确定的结构，最典型的是递归类型。链表的一个节点里装着“下一个节点”，如果直接内联，编译器会陷入无限嵌套，算不出节点占多少字节。

第二类是需要多个所有者的数据。例如多个模块都要读取同一份配置，或者图结构里一个节点被多条边指向。按所有权规则只能有一个主人，其余使用者只能借，而借用的生命周期又很难跨函数、跨集合维持。

第三类是共享之后仍需修改的状态。借用规则要求不可变借用存在时不能有可变借用，当多个持有者通过共享句柄访问同一份数据时，编译器无法证明修改是安全的，于是干脆不允许。

智能指针就是为这三类需求准备的工具。它们在类型系统内部表达“我如何拥有这块数据”：独占、共享、运行时检查、跨线程。需要强调的是，智能指针并非绕过借用检查的后门，而是把所有权语义写进类型，让编译器继续替你把关。

二、Box：独占的堆分配

Box<T> 是最朴素的一种：把值从栈上搬到堆上，栈上只留一个固定大小的指针，离开作用域时自动释放。它的语义仍是独占所有权，移动 Box 只移动指针，堆上的数据不动。

加入 Box 后，Cons 的大小就是一个 i32 加一个指针，编译期即可确定。树结构同理，Option<Box<Node>> 表示可能为空的子节点。

trait object 与所有权转移

trait object 是宽指针，大小不固定，通常装进 Box 使用，于是 Vec<Box<dyn Shape>> 可以容纳不同具体类型，调用时走动态分发。若不需要所有权，用 &dyn Trait 即可；Box<dyn Trait> 的差别在于它拥有值。

Box 还允许把值从堆上移出来：对 Box<T> 解引用并 move，是少数能透过指针直接移走值的场景。把大结构体装进 Box 再在函数间传递，移动的也只是一个指针。

要提醒的是，Box 不是共享。它没有引用计数，也没有内部可变性；需要两个地方同时持有，只能借，或者换 Rc。把 Box 当成“堆上的万能容器”，在需要共享时到处传引用，往往会把生命周期标注搞得异常复杂。如果值只在当前函数内使用、生命周期不超过调用栈，直接放在栈上反而更简单。

三、Rc：单线程的引用计数

当一份数据需要多个所有者、数量又在编译期未知时，用 Rc<T>。它在堆上分配“值 + 强计数 + 弱计数”，每次 Rc::clone 让强计数加一，每次 drop 减一，减到零时释放值。

Rc::clone 的语义

Rc::clone(&rc) 不是深拷贝，只复制指针并把计数加一，开销是常数级。标准库惯用 Rc::clone(&rc) 而非 rc.clone()，是为了让读者一眼看出“这里只是多了一个共享持有者”，而不是复制底层数据。两者行为一致，前者只是更清晰的意图表达。

只读共享，不跨线程

Rc<T> 只提供不可变访问，通过它拿不到 &mut T（唯一持有者时可用 Rc::get_mut，那是另一回事）。这恰好符合“共享即只读”的直觉：多个持有者同时改同一份数据，没有同步机制必然出问题。要在共享前提下修改，就得请出 RefCell。

Rc 的计数是普通整数而非原子操作，所以它没有实现 Send 与 Sync。把 Rc 送进线程的代码会在编译期被拒绝，这是好事：数据竞争被挡在编译期，而不是留到运行时排查。跨线程的共享版本是后文的 Arc。

四、RefCell：把借用检查挪到运行时

RefCell<T> 提供内部可变性：即使手上只有 &RefCell<T>，也能修改里面的值。它把借用规则从编译期搬到运行期，用计数器记录当前的借用状态。

borrow() 返回 Ref<T>，相当于不可变借用；borrow_mut() 返回 RefMut<T>，相当于可变借用。规则与编译期一致：可以有多个不可变借用，但可变借用必须独占。违规不会被编译器拦下，而是在运行时 panic。

panic 的边界

最容易踩的坑是守卫的生命周期比预期长。borrow() 返回的守卫遵循普通变量的作用域规则，语句结束并不会立刻释放。若在同一作用域里先 borrow() 再 borrow_mut()，哪怕逻辑上已经用完，程序照样 panic。解决办法是用花括号缩小作用域，或者显式 drop。

borrow 与 borrow_mut 的返回类型不是 Result，冲突直接 panic。希望自行处理冲突时，用 try_borrow 与 try_borrow_mut，它们返回 Result。生产代码里，如果冲突可能由外部输入触发，优先用 try 版本，别让进程挂在 panic 上。

RefCell 同样不是线程安全的。它常与 Rc 组合成 Rc<RefCell<T>>，这是单线程下共享可变状态的经典写法：Rc 让多处持有，RefCell 在共享的前提下提供修改。图结构、观察者回调与测试替身里都能见到这个组合。

五、循环引用与 Weak

引用计数有个天然缺陷：只在计数归零时释放，而环状结构会让计数永远不归零。父节点用 Rc 持有子节点，子节点又用 Rc 指回父节点，两者的强计数都大于零，即使外部已无人使用整棵树，它们也互相撑着。这不是未定义行为，只是内存泄漏，但对长期运行的服务同样致命。

办法是把其中一条边改成弱引用。Weak<T> 由 Rc::downgrade 得到，不增加强计数，只增加弱计数；使用时调用 upgrade，数据还在就返回 Some(Rc<T>)，否则返回 None。典型做法是父持有子的强引用，子对父只留弱引用。

这样整棵树的存活由外部对根节点的强引用决定，根一释放，子节点依次归零，父指针不会拖住任何东西。访问父节点时 upgrade 一下，拿不到就说明它已销毁，比悬垂指针安全得多。Rust 1.60 起 Rc::new_cyclic 稳定，可以在构造时拿到自身的 Weak，省去先建空节点再回填的两步；它只是语法便利，理解强弱边的分工才是关键。

六、Arc 与 Mutex：把共享带到线程之间

Arc 与原子计数

Arc<T> 是 Rc<T> 的原子版本，结构相同，计数改用原子操作，因此可以在线程间安全地 clone 与 drop。代价是每次增减都有原子指令开销，单线程场景没必要用它。

Arc 只解决“多个线程共同拥有”，不解决“同时修改”。它给出的仍是 &T，跨线程的只读共享已经够用，比如只读配置、编译后的路由表。

Mutex 与锁的粒度

需要修改时，用 Mutex<T> 包裹数据。lock() 返回守卫，守卫离开作用域自动解锁，同一时刻只有一个线程能拿到它。Rust 把数据装在锁里面，不锁就碰不到数据，这比“锁和数据分开声明”更难出错。

锁的粒度要贴着数据，而不是贴着函数。常见错误是进函数就加锁，然后在锁里做网络请求、写日志、计算大对象，把并发硬生生压成串行。正确做法是只在读写共享数据的那几行持有守卫，并让它尽快离开作用域。

lock() 返回 LockResult，因为锁可能被毒化：持锁线程 panic 时，标准库把锁标记为 poisoned，提醒后来者数据可能不一致。多数业务代码选择 unwrap 直接 panic，或用 into_inner 取出数据继续用，取舍要看这份数据被中断后是否还可信。

死锁的两种来源

死锁通常来自两处：同一线程对不可重入的 Mutex 重复加锁，以及多个线程以不同顺序获取两把锁。前者常见于持有守卫时又调用了一个要加锁的方法；后者需要在项目里约定全局的加锁顺序。Rust 的所有权系统帮不上忙，死锁只在运行时发生，排查时可以附到进程上查看各线程栈，或干脆减少锁的数量、改用消息传递。

常见组合

Arc<Mutex<T>> 是最常见的跨线程共享可变状态写法：Arc 管生命周期，让每个线程各持一份句柄；Mutex 管访问，保证同一时刻只有一个线程修改。把 Arc clone 给工作线程，线程内 lock 后操作数据即可。锁的持有时间越短，吞吐越高，但也要避免把一次逻辑上完整的更新拆成多次加锁，那样会破坏一致性。读多写少时可以把 Mutex 换成 RwLock，但要留意写者饥饿与实现差异，别把它当成无条件的性能优化。

七、怎么选：对照表与常见坑

选择可以拆成三个问题：是否共享，是否修改，是否跨线程。

类型 线程范围 所有权 可变性 典型场景
Box<T> 随 T 独占 需可变借用 递归类型、trait object
Rc<T> 单线程 共享 只读 图、树、共享配置
RefCell<T> 单线程 独占 运行时可变 回调中改状态
Rc<RefCell<T>> 单线程 共享 运行时可变 共享可变图结构
Arc<T> 多线程 共享 只读 跨线程只读配置
Arc<Mutex<T>> 多线程 共享 互斥可变 共享计数器、连接池状态

只有一个持有者时，用 Box 或直接把值放在栈上；多个持有者且单线程，用 Rc；多个持有者且跨线程，用 Arc。不改就直接共享，要改就在单线程加 RefCell、跨线程加 Mutex。这两个问题组合出的答案，基本覆盖日常场景。还有一个容易忽略的维度是成本：Rc 与 Arc 的计数维护不是免费的，小对象在热点路径上频繁 clone，开销可能超过直接复制。

坑一：Rc 跨线程编译失败

把 Rc 放进 thread::spawn 的闭包，编译器会报 Rc<i32> cannot be sent between threads safely。原因不是刁难，而是 Rc 的计数增减不是原子操作，两个线程同时 clone 会让计数错乱，导致提前释放或永不释放。遇到这个错误不要用 unsafe 绕过，换 Arc 即可。

坑二：RefCell 运行时 panic

already borrowed: BorrowMutError 往往出现在“遍历集合的同时修改集合”这类逻辑里，编译器放行，运行时才炸。排查时看 panic 信息里的借用类型，找到仍然存活的守卫，缩小它的作用域。对外接口若可能被重入，改用 try_borrow_mut 并把冲突转成业务错误。

坑三：Mutex 毒化

线程在持锁期间 panic，锁被标记为 poisoned，后续 lock() 返回 Err。若数据本身自洽，比如只是一个计数器，可以在 Err 里调用 into_inner 继续使用；若数据可能被写坏，应当把错误向上传播，由上层决定是否重建。不要无脑 unwrap，也不要为了绕开毒化而吞掉 panic。

坑四：过度 clone

借用检查一报错就 clone，是新手最常见的止痛药。克隆 Vec 或 String 会复制整块数据，热路径上代价可观；Rc::clone 虽然便宜，滥用也会让所有权关系变模糊。更好的做法是先想清楚谁应该拥有数据，能不能用引用或切片传参，确实需要共享再引入 Rc 或 Arc。Arc 的 clone 带原子操作，高频路径上同样值得斟酌。

小结

智能指针的价值不在于“让代码通过编译”，而在于把所有权关系显式写进类型。Box 表达独占的堆分配，适合递归类型与 trait object；Rc 表达单线程的多所有者只读共享；RefCell 把借用检查推迟到运行时，补上共享前提下的可变性；Arc 与 Mutex 把这套组合搬到多线程。遇到环状结构时用 Weak 打断强引用链，遇到跨线程报错时先检查类型是否实现了 Send。按“是否共享、是否修改、是否跨线程”三个问题依次判断，比记住一堆类型名字更有效。
