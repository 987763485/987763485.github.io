链路追踪 Jaeger 实践

本文属于《Go 微服务架构》第 35/35 篇
上一篇系列目录下一篇

链路追踪的理论、Span 模型与埋点方法，已经在《微服务链路追踪落地》里讨论过。真正把 Jaeger 跑起来，问题会更具体：all-in-one 能不能上生产，collector 与 query 要不要拆，存储选 Cassandra 还是 Elasticsearch，采样策略写在哪里，排障时在 UI 里怎么点。本文以 2022 年的 Jaeger 1.3x 为基准，按组件、部署、存储、埋点、采样、查询的顺序走一遍，给出可直接运行的配置与 Go 示例。读完应能独立搭起开发环境，并为生产画出可落地的拓扑。

Jaeger 的组件与一次追踪的旅程

Jaeger 由 Uber 在 2015 年开源，2017 年进入 CNCF，2019 年毕业。到 2022 年，稳定版本停在 1.3x 系列，架构仍是经典的五件套：客户端 SDK、agent、collector、query 与存储。认清这五个角色的边界，后面的部署与调优才有落脚点。

客户端 SDK 负责在进程内创建 Span、维护上下文、按采样策略决定留不留，并把数据发出去。Jaeger 自家的 client 库此时已进入维护状态，官方建议新项目改用 OpenTelemetry SDK，再由 OTLP 导出。这个转变值得注意：Jaeger 从此更像一个后端，埋点的标准交给了 OpenTelemetry。

collector 是无状态服务，接收上报的数据，做校验、补充标签、批量写入存储。它能同时接多种协议：OTLP 的 gRPC 与 HTTP，以及 Jaeger 自己的 gRPC 与 HTTP。因为不保存状态，collector 可以水平扩容，前面挂一个四层负载均衡即可。

query 也是无状态的，它只读存储，对外提供 16686 端口的 Web UI 和 16685 端口的 gRPC 查询接口。UI 上看到的一切，包括服务列表、调用链和依赖图，都来自 query 对存储的查询，所以 query 慢通常是存储慢，而不是 query 本身的问题。

存储是唯一有状态的部分。1.x 支持 Cassandra 与 Elasticsearch，另外还有用于本地体验的内存和 Badger。选型会在第三节展开。

agent 是历史组件。早期部署里，它在每台主机上以守护进程运行，监听 UDP 6831 与 6832，把客户端发来的小包聚合成批，再用 gRPC 转发给 collector，同时代理采样策略接口。它的价值是 UDP 开销小、客户端不必知道 collector 地址、批量转发省网络；代价是每台机器都要装、要配、要升级，容器化之后主机边界模糊，这层代理的收益越来越小。2022 年的新部署一般让 SDK 直接用 OTLP 发到 collector，agent 只在沿用老客户端时保留。

把这条链路画出来：

flowchart LR
    A["应用进程 + OTel SDK"] -->|"OTLP 4317 / 4318"| B["collector"]
    C["老客户端"] -->|"UDP 6831"| D["agent（历史组件）"]
    D -->|"gRPC 14250"| B
    B --> E["存储：Cassandra / Elasticsearch"]
    F["query + UI 16686"] --> E
    B -->|"5778 采样策略"| A

一次追踪的旅程大致是：请求进入网关，SDK 生成根 Span 并按策略决定是否记录；后续每次跨进程调用都带着 traceparent 头；各服务的 Span 通过 OTLP 批量送到 collector；collector 写入存储；排障时在 query 的 UI 上按 TraceID 取回整棵树。任何一段缺失，链路上就会出现断点或空洞。

部署：all-in-one 与生产环境的拆分

部署形态只有两种：单机的 all-in-one 与拆分部署。

all-in-one 把 collector、query、agent 和内存存储打包进一个进程，一条 docker run 就能起。它适合本地开发和 CI 里的集成测试，不适合任何有真实流量的环境，因为数据存在进程内存里，重启即丢，也没有副本与容量规划可言。

这里有两个细节容易踩。第一，1.x 的 OTLP 接收器默认关闭，必须用 COLLECTOR_OTLP_ENABLED 打开，否则 SDK 连 4317 会一直失败。第二，6831 是 UDP 端口，映射时要写明 udp，否则 agent 收不到老客户端的数据。

生产环境把 collector 与 query 分开。collector 面向应用，按写入量扩容，放在内网，不暴露公网；query 面向人，读压力不大，但一次查询可能扫很大时间范围，需要限制时间窗与并发。存储独立部署，单独做备份与容量监控。这样拆的好处是故障域清晰：写入拥堵不会拖垮 UI，UI 上的慢查询也不会影响采集。

存储：Cassandra 与 Elasticsearch 的取舍

存储是 Jaeger 里唯一需要长期运维的部分，也是选型时争议最大的部分。1.x 支持两种主流后端，二者都能水平扩展，但脾气完全不同。

Elasticsearch 的优点是查询灵活。Span 里的每个 tag 都会进索引，排障时按状态码或用户 ID 过滤是家常便饭，这类查询在 ES 里几乎零成本。collector 首次启动会自动创建索引模板，Span 按天写入 jaeger-span-2022-10-31 这样的索引，服务与操作名另存一份 jaeger-service-日期，供 UI 的下拉框使用。按天分索引的好处是删除历史数据只需删索引，比按条件删除快得多。

代价在写入。ES 的写入放大明显，分片数在建索引时就固定，估少了后面只能重建。经验上按每天数据量除以单分片 30 GB 到 50 GB 估算分片数，副本至少一份；refresh 间隔可以放宽到 30 秒，因为追踪数据不需要秒级可见。保留期用 ILM 或 curator 定时删除，开发环境三天、生产七到十五天是常见做法。

Cassandra 的优点是写吞吐高、扩容线性，适合 Span 量极大且团队已有运维能力的场景。缺点是查询受限：它按 trace id、service、operation 与时间的组合建表，想按任意 tag 过滤就要提前设计，临时加一个查询条件往往要改表结构。依赖图、服务列表这些功能都依赖特定的读写模式，运维不到位时问题会出在超时与压缩上。

一句话的取舍：团队熟悉 ELK、排障以标签过滤为主，选 Elasticsearch；写入量已经大到 ES 扛不住、且有 Cassandra 运维经验，再考虑 Cassandra。

错误标记也值得留意：OpenTelemetry 的 RecordError 与 SetStatus 会被 Jaeger 映射成 error=true 标签，UI 上标红，Search 里可直接过滤；只打日志不标 Span，等于放弃了这条通道。

采样：概率、remote sampling 与按服务限流

采样决定哪些 trace 被记录，而且发生在 SDK 端，不是 collector 端。数据一旦发到 collector，就已经是要存的数据了，把采样寄托在 collector 上，等于让网络和写入先承担全部成本。

Jaeger 1.x 的策略有几种。const 表示全采或全不采；probabilistic 按比例采，参数是 0 到 1 之间的小数；ratelimiting 按每秒新开 trace 的数量限流，适合流量波动大的服务；remote 表示从远端拉取策略。策略可以按服务、按操作配置，SDK 定期向 collector 的 5778 端口拉取，缓存一段时间后生效。一份典型的策略文件如下：

remote sampling 的好处是策略集中管理、改完不用重启应用；代价是多一个依赖，SDK 拉不到策略时会退回本地默认值，这个默认值要提前想好。按服务限流时还要注意：ratelimiting 限制的是每秒新开的 trace 数，不是 Span 数，一个 trace 里 Span 再多也只算一次。

查询：从服务列表到最长 Span

UI 的使用可以按“先找、再看、后比”三步走。

找 trace 靠 Search 表单。service 与 operation 是核心组合，只选服务不选操作，结果会被各种内部调用淹没；再往下是 tag 过滤，格式为键值对，error=true、http.status_code=500 都是常用条件；时间范围默认一小时，跨天排障要手动改；Duration 可以设最小值和最大值，查慢请求时把最小值设成 p99 的门槛，比翻列表高效得多。

手上已有 TraceID 时直接粘进搜索框，不用走表单。TraceID 通常来自三条路：网关的访问日志、错误响应体里回传的字段，或者前端上报。把 TraceID 打进日志，一行代码就能换来一条从日志直达调用链的通道。

打开一条 trace，默认是时间轴视图，每行一个 Span，横条长度代表耗时，缩进代表层级。找最长 Span 有两个办法：切到 Span Table 按 Duration 排序，第一行就是；或者在时间轴上找最宽的那条。找到之后不要停在“它最慢”，要继续看它的子 Span：子 Span 也慢，问题在下游；自身很宽而子 Span 很窄，时间花在自身逻辑或未被埋点的代码里。

客户端 Span 与服务端 Span 的差值值得单独看。两者之差是序列化、网络与排队的时间，差值突然变大通常意味着网络抖动、连接池排队或对端线程池打满，而不是业务代码变慢。Compare 功能可以并排比较两条 trace，一条正常、一条异常，Span 的增减与耗时差异一目了然，排查“多发了一次调用”“重试变多”这类问题特别好用。

最后要接受 UI 的边界：它适合逐条排查，不是指标系统，延迟分位数与错误率趋势应交给 Prometheus 或存储侧的聚合查询；依赖图需要额外跑 jaeger-spark-dependencies 任务，从 Span 中汇总服务间的调用关系与错误率，写回依赖索引后才能在 UI 的 Dependencies 页看到。指望 UI 回答“这周支付服务的 p99 是多少”，方向就错了。

成本：高 QPS 下的存储压力

先做一个示意估算，数字只为说明量级。假设 50 个服务，忙时每秒 2000 个请求，平均每个请求 6 个 Span，全量采集就是每秒 12000 个 Span。一个 Span 在 Elasticsearch 里连同索引开销按 1 KB 估算，一天约 1 TB；采样率降到百分之一，一天就降到 10 GB 量级。这个差距解释了为什么生产环境普遍在百分之一到百分之十之间取值。

写入侧的压力集中在三处：collector 的队列与批量、ES 的 bulk 并发、磁盘的顺序写。collector 队列满时会丢弃新数据，指标里体现为丢弃计数；ES 的 bulk 队列满时 collector 会重试，重试堆积又反过来撑爆队列。调优顺序应该是先确认存储写得动，再调 collector 的 worker 数与批量大小，最后才考虑加副本。

Span 自身的体积也值得控制。把整条 SQL、整个请求体塞进 tag，单条 Span 可能涨到几十 KB，存储成本翻十倍不止。大字段应放日志，Span 里只留标识与关键维度。属性名也要克制，动态生成的键会让 ES 的字段数膨胀，最终拖垮集群。

保留期是另一个杠杆。追踪数据用于排障，七天通常够用，合规要求长的场景可以只把错误 trace 抽样后转存。Jaeger 1.x 本身没有冷热分层，长期留存要靠存储侧的能力或另外归档。如果确实需要“留下所有错误、只留少量正常”，可以在应用与 collector 之间加一层 OpenTelemetry Collector，用尾部采样处理器缓冲完整 trace 再决定去留，代价是内存与维护复杂度上升。

小结

Jaeger 的组件边界很清楚：SDK 负责产生与采样，collector 负责接收与写入，query 负责查询与展示，存储负责长期保存，agent 是容器化时代逐渐退场的过渡件。部署上，all-in-one 只用于开发，生产把 collector、query 与存储拆开，各自扩容。存储选型看团队能力与查询模式，Elasticsearch 胜在灵活，Cassandra 胜在写入。埋点交给 OpenTelemetry，用 OTLP 导出，手动 Span 只补关键分支。采样在 SDK 端解决，用 remote sampling 集中管理，按服务与操作差异化配置。最后，把 UI 当成排查工具而不是监控大盘，延迟与错误的趋势交给指标系统。
