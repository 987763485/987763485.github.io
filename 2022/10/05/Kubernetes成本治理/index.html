Kubernetes 成本治理

本文属于《Docker 与 Kubernetes》第 48/51 篇
上一篇系列目录下一篇

成本治理这件事，在虚拟机时代靠“少开机器”就能解决大半，到了 Kubernetes 却变得隐蔽：账单只显示节点开销，真正的浪费藏在 requests 的虚高、装箱留下的碎片、长期 Pending 的存储卷，以及没人认领的负载均衡器里。本文从 Kubernetes 的对象与调度层出发，梳理一条从成本模型、配额约束、右 sizing、弹性伸缩到闲置识别和组织机制的完整链路，适合已经跑起集群、开始被账单追问的平台与研发团队阅读。读完本文，读者应当能为自己的集群建立一套可度量的成本口径，并知道每一项治理动作该落在哪个对象上。

成本从哪里来：节点、可分配资源与 requests

讨论 Kubernetes 成本，第一步是把“账单金额”翻译成“调度资源”。云上的账单来自节点，而节点能被 Pod 使用的资源并不是全部。以一台 8 核 32 GiB 的节点为例，kubelet 会预留一部分资源给系统进程，还要扣掉 kube-reserved、system-reserved 与 eviction-threshold，剩下的才是 Allocatable。调度器只看 Allocatable，不看机器标称容量，也不看容器里进程真实吃了多少 CPU。这条链路可以概括为：

节点成本 → Allocatable → requests 之和 → 实际使用

四个环节每一层都在缩水，而成本只认第一层。也就是说，只要节点开着，无论上面的 Pod 是满负荷还是空转，账单都一样。真正的成本杠杆，是让“为 requests 付费的容量”尽可能接近“实际使用”，并让节点数量跟随真实需求。

理解这一点，就能理解两个常用指标。装箱率衡量节点上 requests 之和占 Allocatable 的比例，它决定了要买多少节点；利用率衡量实际用量占 requests 的比例，它决定了买来的容量是否被浪费。两者都低，说明 requests 虚高且节点闲置；装箱率高而利用率低，说明资源被“预订”了却没人用，是最常见的隐性浪费。

资源碎片则来自另一个方向。调度器按 Pod 的 requests 做二元打包，一个请求 3 核的 Pod 放不进两台各剩 2 核的节点，哪怕集群总空闲有 4 核。碎片让扩容提前发生：明明总算力够用，却因为形状不匹配而多开一台节点。治理碎片通常从统一 requests 规格、减少超大 Pod、按规格划分节点池入手，而不是简单提高装箱率。

还有一个容易被忽略的细节：CPU 与内存的成本性质不同。CPU 可以超卖，多个 Pod 争抢时只会变慢；内存不可压缩，超卖会触发 OOMKill 或节点驱逐。因此 CPU 的 requests 可以适度贴近 P95 使用量，内存的 requests 则应留出安全余量。把两者用同一套比例去压缩，往往先出事故，再退回保守配置。

配额与边界：ResourceQuota、LimitRange 与 namespace 划分

成本治理的第一道制度是“谁可以用多少”。Kubernetes 提供的原语是 namespace、ResourceQuota 与 LimitRange 三者组合。namespace 是分摊的边界，可以按团队、按环境或者按业务域切分，尽量让一个 namespace 对应一个成本中心，这样账单能直接按 namespace 的 requests 汇总，不必逐 Pod 反查。

ResourceQuota 限制 namespace 的总量，常用字段包括 requests.cpu、requests.memory、limits.cpu、limits.memory、pods、services、persistentvolumeclaims 等。这里的关键点是：配额统计的是声明值，不是实际用量。一个 namespace 配额 40 核，并不意味着它能用满 40 核算力，而是意味着 40 核的“预订额度”被占住。如果团队只写 limits 不写 requests，配额可能统计不到，或者被默认值悄悄放大。因此配额必须与 LimitRange 搭配：LimitRange 为容器设定 defaultRequest、default、max，以及 requests 与 limits 的比例上限，避免“单个容器申请 32 核”或者“requests 1 核、limits 64 核”的畸形配置。

治理中的一个常见误区，是把配额当作硬性封顶就完事。配额太松，团队没有压力；太紧，业务发布被 403 拒绝，最后所有人都在申请提额。更合理的做法是按历史 P95 用量加两成左右缓冲设定配额（示意值），每季度校准；同时给配额使用率建立监控，超过八成预警，让提额成为一次有数据支撑的评审，而不是默认动作。

标签规范是账单归属的另一半。namespace 只能表达一层归属，跨团队的共享服务、同一团队的多条产品线仍然需要标签区分。建议至少约定 team、app、env、cost-center 四个标签，并在准入层强制校验，例如通过 OPA Gatekeeper 或 Kyverno 拒绝缺失标签的 Deployment。标签一旦成为准入规则，账单系统就能按 team 聚合，资源目录也能反查到负责人。反过来，如果标签靠自觉，半年后必然出现一批无主负载，账单只能记在“其他”名下。

右 sizing：VPA 的推荐模式与风险

右 sizing 的目标不是把 requests 压到最低，而是让 requests 落在一个既保证调度与稳定性、又不长期闲置的区间。手工调参依赖经验，规模化之后需要工具，VPA（Vertical Pod Autoscaler）是当时最直接的选择。它由 Recommender、Updater 与 Admission Controller 三部分组成：Recommender 读取历史用量给出建议，Updater 决定是否驱逐 Pod 以应用新值，Admission Controller 在新 Pod 创建时写入建议值。

VPA 的 updatePolicy 有 Off、Initial、Recreate 三种模式。Off 只产出 recommendation，不改变任何 Pod，是最安全的“只读顾问”；Initial 只在 Pod 创建时设置一次，不主动驱逐；Recreate 会在建议变化时驱逐并重建 Pod。Recreate 的风险在于它把调参变成了滚动重启，对长连接、批处理和有状态服务都不友好；而且在 Kubernetes 1.23 至 1.25 中，Pod 资源的原地调整仍未稳定，VPA 只能靠重建生效。因此生产上更常见的组合是：VPA 以 Off 模式跑推荐，人工评审后修改 Deployment 的 requests；或者只对无状态、可容忍重启的服务开启 Initial。

第二个问题是监控数据的选择。VPA 默认用历史用量的高分位数做推荐，方向是对的：用峰值会把偶发尖峰固化进 requests，用均值又会在每天的高峰被限流或者 OOM。实践上建议取最近 7 到 14 天的 P95，CPU 可以更低一些，内存则要看 OOM 记录，必要时用 P99 或者最大值兜底。对于有明显周期性的业务，按工作日与周末分别统计，比一个统一窗口更准确。

第三个问题是冷启动与突发。新服务没有历史数据，VPA 的推荐会偏保守或者剧烈波动；有突发流量的服务，P95 也覆盖不了秒杀、定时任务和大促。对这类负载，requests 应按“能承受的并发下限”设置，把突发交给 HPA 与节点池的快速扩容，而不是把 requests 抬到峰值。需要强调的是，VPA 与 HPA 不应同时作用于同一个资源维度：如果 HPA 依据 CPU 扩副本，VPA 又不断调整 CPU requests，二者会互相追逐，副本数与 requests 都稳定不下来。常见的分工是 VPA 管内存、HPA 管 CPU，或者 VPA 只出建议、由人做最终决策。

弹性：HPA、Cluster Autoscaler 与节点池

弹性解决的是容量随时间变化的问题，但弹性本身不省钱：缩容阈值保守、扩容过于灵敏，集群就会长期停在峰值容量。

HPA 依据指标调整副本数。CPU 利用率以 requests 为分母，requests 虚高会让 HPA 误以为负载很低而不扩容，压得过低又会频繁抖动，所以 HPA 的前提仍然是 requests 可信。Kubernetes 1.18 之后 HPA 支持 behavior 字段，可以分别设置扩容与缩容的稳定窗口。缩容默认有 5 分钟稳定窗口，这个值对成本很关键：太短，流量略降就缩容，随后又扩容，节点反复创建销毁；太长，低谷容量迟迟不释放。对日周期明显的业务，把缩容窗口设为 10 到 15 分钟通常更划算（示意值）。

Cluster Autoscaler 负责节点层：Pod 因资源不足而 Pending 时增加节点，节点长期低利用时缩容。缩容比扩容难，它要求节点上的 Pod 都能安全驱逐、不被本地存储与严格亲和性绑住，并且 PDB 允许中断。默认情况下，节点利用率低于五成并持续一段时间才会进入移除候选（具体以启动参数为准）。如果 PDB 的 minAvailable 设成 100%，或者单副本 StatefulSet 没有控制器管理，节点就永远缩不掉，账单便固定在峰值。

节点池是调和这对矛盾的手段。把无状态在线服务、批处理、有状态中间件分到不同池，各自设定策略：在线池保留缓冲，批处理池可以更激进地缩容，中间件池不做自动缩容。竞价实例适合放进独立的、可中断的节点池，配合多种实例规格分散中断风险，并确保工作负载能处理回收通知与优雅退出。把关键服务与竞价节点混在同一池里，省下的钱往往会以一次故障的形式还回去。

闲置识别：从低利用率节点到过度副本

成本治理不能只靠感觉，需要一张可定期执行的检查清单。以下几类闲置最值得优先排查。

低利用率节点：用 kubectl top nodes 看实际用量，再对比 Allocatable。连续多天 CPU 与内存都低于三成的节点，要么是 requests 虚高导致装箱率低，要么是节点池配置过大。要区分“节点空闲”与“节点预留”，后者可能承担故障域或者峰值缓冲，不能一刀切。

长期 Pending 的 PVC：Pending 的 PVC 不产生计算费用，但会占住配额，也常常意味着存储类配置错误或者工作负载早已下线。定期清理不再挂载的 PV 与快照，比事后对账更有效。

未挂载的负载均衡器：Service 类型为 LoadBalancer 时，云控制器会创建外部负载均衡器。删除工作负载却忘了删 Service，或者 Service 没有 Ready 的 Endpoint，都会留下持续计费的实例。检查地址为空、Endpoints 为空的 Service 应成为例行任务。

过度副本：HPA 的最小副本数长期高于实际需要，或者手工设置了远超流量的 replicas，是最容易被忽略的浪费。判断依据不只是 CPU，还要看每副本承载的请求量、队列长度与延迟余量。一个每副本每秒只处理个位数请求、延迟却远低于 SLO 的服务，通常可以直接减半。

闲置类型 识别信号 处置动作
低利用率节点 实际用量长期低于三成 调整节点池下限，合并负载
Pending PVC 长时间未 Bound 核对 StorageClass，清理废弃声明
空负载均衡器 Service 无 Endpoint 或地址为空 删除无用 Service，改用 ClusterIP
过度副本 每副本请求量低、延迟余量大 下调 replicas 或 HPA 最小值
已完成 Job Pod 与日志长期堆积 设置 ttlSecondsAfterFinished

组织机制：预算、评审与设计约束

技术手段能发现浪费，能否持续收敛取决于组织机制。最基础的是预算告警：按 namespace 或者 team 设置月度预算，达到五成、八成、百分之百分别通知不同角色。告警要发给负责花钱的人，而不是只发给平台团队，否则平台只能一次次代为解释。

月度成本评审应有固定议程：本月总成本与环比、各 team 分摊、单位成本（例如每千次请求成本、每万订单成本）、Top 5 增长来源、上月治理动作的回收情况。单位成本比绝对金额更能反映效率，也能避免把业务增长误判为浪费。评审的输出应当是具体动作与负责人，而不是一份报告。

更进一步，把成本作为非功能需求写进设计评审。新服务上线前回答几个问题：峰值 QPS 与单副本容量是多少，requests 如何得出，是否需要 HPA，数据保留多久，是否使用缓存与异步削峰。回答不了这些问题，就不该直接上生产。

治理还要留出安全边界。节省比例只能作为示意，不能成为硬性 KPI；一旦把压降比例压到团队头上，最容易发生的动作是偷偷调低 requests、关闭副本、缩短日志保留，最后以稳定性事故收场。合理的做法是考核单位成本与资源效率，并允许团队为可靠性支付溢价。

小结

Kubernetes 的成本治理，本质上是把账单逐层拆回对象：节点成本经过 Allocatable 变成可调度容量，requests 决定容量如何被预订，实际使用决定预订是否值得。先用 namespace、ResourceQuota 与 LimitRange 划清边界，再用 VPA 的推荐与可信的监控数据做右 sizing，用 HPA 与 Cluster Autoscaler 让容量跟随负载，最后用固定清单清理闲置资源。技术动作之外，预算告警、月度评审与设计评审中的成本约束，才是让效果不反弹的保障。衡量治理成效时，优先看单位成本与装箱率，而不是某一次节省的绝对金额。
