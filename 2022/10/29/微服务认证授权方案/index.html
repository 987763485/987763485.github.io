微服务认证授权方案

本文属于《Go 微服务架构》第 18/35 篇
上一篇系列目录下一篇

服务拆到十几个之后，认证与授权常常变成一堆散落的中间件：网关校验一次 JWT，服务之间再塞一个内部请求头，异步任务里干脆没有身份。本文把这件事拆成三条身份线和两类决策，依次讨论 OAuth 2.0 与 OIDC 的分工、JWT 的校验与撤销、服务间的工作负载身份、RBAC/ABAC/ReBAC 的取舍、策略决策点的位置，以及令牌在同步与异步链路中的传播。读完之后，你应该能画出完整的认证授权链路图，并清楚每一处该验证什么、不该相信什么。

认证、授权与三种身份

先把两个经常被混用的词分开。认证（authentication）回答的是“你是谁”，输出的是一个可信的主体标识；授权（authorization）回答的是“你能做什么”，输出的是一个允许或拒绝的判定。前者发生在请求进入系统的早期，后者发生在每一次访问具体资源的时候。很多事故的根源，是把认证的结果当成了授权的依据：只要令牌签名有效，就默认这个调用方可以访问所有接口。

在微服务里，“谁”其实有三个不同的答案。

第一条是用户身份。它代表一个真实的人，通常由浏览器或 App 发起交互式登录，生命周期以天计，需要处理多因素认证、注销、改密后踢出等场景。用户身份的凭证只应代表用户本人，不能顺手拿来代表调用它的服务。

第二条是服务身份。它代表一段代码，也就是某个工作负载，由平台签发，生命周期以小时甚至分钟计，用来回答“这个请求是不是真的来自订单服务”。它解决服务间调用的相互认证，和用户是否登录无关。

第三条是设备身份。它代表一台终端，比如办公笔记本、POS 机、车载模块或摄像头，通常用证书或出厂密钥建立，关注设备是否合规、是否被篡改、是否在允许的范围内接入。物联网与移动办公场景里，这条线往往比前两条更关键。

三条线各有凭证体系与失效节奏。工程上常见的错误是互相借用：用服务的客户端密钥去换用户令牌，用用户的 access token 做服务间调用，或者把设备证书当成用户登录的替代品。一旦借用，审计日志里就分不清“是张三点的，还是张三的客户端在后台刷的”。

从架构上看，完整链路包含主体、凭证签发方、策略决策点与执行点，后文的各种协议本质上都在安排这四个角色。还有一个维度是上下文：同样一句“读取订单”，由用户、定时任务或事件触发，风险完全不同，应当分别准备凭证，而不是共用一张长期令牌。

OAuth 2.0 与 OIDC：授权与认证各归其位

OAuth 2.0 经常被当成“登录协议”，这是最常见的一处概念错位。RFC 6749 的标题是“授权框架”，它解决的是资源所有者如何把一部分权限委托给客户端，让客户端在不接触密码的前提下访问资源。协议定义了资源所有者、客户端、授权服务器、资源服务器四个角色。令牌是委托关系的凭证，它证明“某个客户端获得了访问某类资源的许可”，并不证明“某个用户此刻完成了登录”。

授权码流程与 PKCE

授权码流程是 Web 应用的默认选择。浏览器被重定向到授权服务器，用户完成登录与同意，授权服务器把一次性授权码带回客户端，客户端再用授权码加自己的密钥在后台换回令牌。access token 因此不会经过浏览器地址栏，也不会留在浏览历史里。

公共客户端（单页应用、桌面程序、移动 App）没有能力保守客户端密钥，授权码一旦被截获，攻击者就能拿去换令牌。PKCE（RFC 7636）就是为这个场景设计的补丁：客户端在发起授权请求时生成一个随机串，把它的 SHA-256 摘要随请求发出，换令牌时再出示原始随机串。授权服务器比对摘要，确认换令牌的一方就是发起授权的一方。授权码因此变成“截获了也用不了”的一次性凭证。

客户端凭据与令牌交换

服务到服务的调用没有用户参与，用的是客户端凭据模式：服务用自己的 client_id 与密钥直接向授权服务器申请令牌。这类令牌的 sub 应当是服务本身，scope 应当只覆盖它需要访问的下游接口。把客户端密钥写进镜像或配置文件是常见做法，但更稳妥的方式是让平台在运行时注入，并定期轮换。

当调用需要“以用户身份”访问下游时，问题就出现了。网关手里的用户令牌 audience 是网关自己，直接转发给订单服务，等于让订单服务接受一张不属于它的令牌。RFC 8693 的令牌交换可以解决这个问题：调用方拿现有令牌换一张新令牌，audience 指向目标服务，scope 收窄，subject 仍是原用户，并可用 actor 声明表示“谁在代为调用”。

access token 与 ID token 不是一回事

OIDC 在 OAuth 2.0 之上补了一层身份认证，核心产物是 ID token。两者长得都像 JWT，用途却严格分开。

access token 是给资源服务器看的。它的 audience 是某个 API，内容以 scope、权限为主，客户端不应当去解析它的业务含义，更不应当把它当作“用户信息”使用。资源服务器验证它，是为了决定这次调用能做什么。

ID token 是给客户端看的。它的 audience 是客户端自己的 client_id，包含 sub、iss、aud、exp、iat、auth_time、nonce 等声明，用来告诉客户端“这次登录发生在什么时候、认证了哪个用户、有没有被重放”。它绝对不能发给下游 API，因为下游不是它的受众，拿着它也无法做出正确的授权判断。

由此可以回答那个反复出现的问题：OAuth 2.0 不是认证协议。仅凭 access token，资源服务器无法知道用户是刚输入了密码，还是三天前的会话被静默续期，也无法知道登录时有没有做多因素认证。这些属于认证事件，只有 ID token 里的 auth_time、amr 以及授权服务器保存的会话状态才说得清楚。需要登录能力时应当使用 OIDC，校验 nonce 与 auth_time，而不是自己往 access token 里塞一个 username 字段。

JWT：格式、校验与撤销

JWT（RFC 7519）定义了一种把声明序列化并签名的格式，三段用点分隔：头部描述算法与密钥标识，载荷存放声明，签名保证前两段没有被篡改。它常被用作 access token 与 ID token 的载体，但本身既不是认证协议，也不是授权模型，只是一张可以自校验的纸。

校验顺序比算法选择更重要

签名算法优先选非对称的 RS256 或 ES256，由授权服务器持有私钥，资源服务器只拿公钥。HS256 并非不能用，但它要求验证方也持有签名密钥，服务一多，密钥就会扩散，任何一处泄漏都等于可以伪造任意令牌。

真正的事故多数不是算法被攻破，而是校验漏了步骤。合理的顺序是：先按 kid 从受信任的 JWKS 端点取公钥，绝不信任令牌头部自带的 jku 或 x5u 地址；再限定允许的算法集合，拒绝 none 以及不在白名单里的算法；然后验签；最后逐项校验 iss、aud、exp、nbf、iat，并留出几十秒的时钟偏移容忍。只有这些都通过，才进入业务侧的权限判断。

过期、刷新与撤销

access token 的有效期应当短，五到十五分钟是常见区间。代价是频繁刷新，收益是泄漏后的暴露窗口可控，权限变更最多在一个令牌周期内生效。refresh token 可以长一些，但必须绑定客户端、一次性使用并在每次刷新时轮换；授权服务器要记录用过的 refresh token，一旦发现重复使用，就判定为泄漏，吊销整条令牌链。

撤销是 JWT 的固有难点。自包含意味着资源服务器不必查询存储，也就无法知道某张令牌已被提前作废。工程上有几种补法：缩短有效期，让影响变小；对高风险操作调用内省端点（RFC 7662）实时确认；在网关维护按 jti 的短期黑名单，登出和封禁时写入；或在用户维度维护令牌版本号，改密、踢人时递增，资源服务器比对版本。几种手段可以叠加，但黑名单本身也是一份需要高可用与一致性的状态，不能包治百病。

最后是载荷的边界。JWT 适合放标识与授权声明：主体、受众、过期时间、scope、租户；不适合放密码、密钥、完整个人资料、内部拓扑，也不适合放频繁变化、导致令牌不断重签的大对象。确需机密内容时可以用 JWE，但要承担密钥管理与排障成本，多数场景下只放引用更稳妥。

服务间认证：从共享密钥到工作负载身份

用户身份解决“人”的问题，服务互相调用时还要回答另一个问题：这个请求是不是真的来自订单服务？很多系统在这一步退化了，要么靠内网 IP 白名单，要么靠所有服务共用的 API Key，要么干脆不验证。这三种做法在边界被突破后都会失效：IP 可以伪造或复用，共享密钥泄漏就是全员失守，而默认信任正是零信任要拆掉的东西。

mTLS 与工作负载身份

mTLS 让双方在建立连接时都出示证书，证书里的身份就是服务身份。它比令牌更难冒充，因为私钥不在网络上传递，TLS 握手本身还提供了通道加密。问题在于证书的签发、分发、轮换与吊销，手工签一批一年期的证书，很快就会变成一张谁也不敢动的清单。

SPIFFE 把这件事标准化了。它规定了一种身份标识，形如 spiffe://example.com/ns/orders/sa/ordersvc，其中 example.com 是信任域，后面的路径通常对应命名空间与服务账号。基于该标识签发的凭证叫 SVID，可以是 X.509 证书，也可以是 JWT。SPIRE 是实现这套标准的组件：每个节点上运行 agent，先做节点认证，确认机器属于集群，再做工作负载认证，确认进程确实以某个服务账号运行，然后签发短期 SVID 并自动轮换。

这段载荷说明了关键点：服务身份的受众是明确的下游服务，而不是“所有服务”。接收方校验信任域、自身 audience 与有效期，就能确认调用方是谁、凭证是不是给自己用的。X.509-SVID 则把同样的身份写进证书的 URI SAN，配合 mTLS 使用。

Kubernetes 自带的服务账号令牌也是一条路径。从 1.20 起，绑定服务账号令牌的投射方式默认启用，支持 audience 与过期时间，由 kubelet 投射到 Pod 并自动轮换，比早期永不过期的 Secret 令牌安全得多。但它本质仍是 bearer token，只证明持有者拿到了投射文件，不证明进程身份，适合作为补充而非 mTLS 的替代。

每次请求都要验证

零信任的核心不是“用了 mTLS”，而是“不因为请求来自内部就放行”。这里有一个容易忽略的细节：TLS 只在连接建立时验证一次，而 HTTP 连接会被复用，一个连接上可能跑着成百上千个请求。只在握手时确认身份，连接建立之后的授权仍然缺失。因此服务间调用需要两层：传输层用 mTLS 确认对端身份，应用层或网格层对每个请求再判断一次，检查调用方是否有权访问这个方法、这个资源。

这也是本篇与《服务网格零信任落地》的分工：那一篇讲 Istio 里 PeerAuthentication 与 AuthorizationPolicy 的具体配置，本篇关心方案层面的选择——何时用 mTLS，何时用服务令牌，身份由谁签发，信任域怎么划。

授权模型：RBAC、ABAC 与 ReBAC 的取舍

认证解决了“是谁”，接下来是“能做什么”。授权模型的选择直接决定策略是否顺手、审计能否讲清楚，以及未来加需求时会不会推倒重来。

三种模型的边界

RBAC 把权限授予角色，再把角色授予主体。优点是直观：管理员看得懂“财务角色可以导出报表”，审计也能沿角色追溯，角色还可以继承形成层级。问题是角色会膨胀。一旦出现“华东区财务”“华东区财务（只读）”“华东区财务（仅限本部门）”，角色数量就随维度组合爆炸，最后没人说得清某个角色到底能干什么。

ABAC 改用属性描述：主体属性、资源属性、动作、环境条件，策略是对这些属性的布尔表达式。比如“部门相同、资源密级不高于主体密级、且在工作时间”才允许访问。表达力明显更强，能覆盖 RBAC 难以表达的动态条件。代价是属性来源必须可靠，策略数量增长很快，而且结果依赖运行时上下文，事后解释“为什么这次被拒”需要完整的决策日志。

ReBAC 把授权建模成关系图。它不问“你是什么角色”，而问“你和资源之间有没有一条可达的关系路径”：文档属于文件夹，文件夹属于项目，项目成员可以读。谷歌的 Zanzibar 论文把这套模型工程化，用关系元组存储用户与对象的关系，查询时做图遍历。它适合文档共享、组织层级、多租户协作，缺点是实现复杂，还要处理一致性：刚撤销的权限如果不能立刻生效，就会出现“已移除的成员还能看到文件”。

模型 擅长表达 主要成本 典型场景
RBAC 岗位职责、固定权限集 角色爆炸、难以表达资源归属 后台管理、内部系统
ABAC 属性组合、环境条件 属性治理、策略测试与解释 风控、数据分级访问
ReBAC 层级、共享、委托关系 图存储与一致性、实现复杂 文档协作、多租户

实践中很少只用一种。比较稳妥的路径是：用 RBAC 建立粗粒度基线，回答“这个人在系统里是不是财务”；用 ABAC 或 ReBAC 处理细粒度判断，回答“他能不能看这一张凭证”。两者叠加时要注意顺序，先粗后细，任何一层拒绝都应直接拒绝，避免“细粒度放行覆盖粗粒度封禁”的漏洞。

无论选哪种模型，都不要把判断写死在各处 handler 里：散落的 if 语句无法统一审计，也回答不了“谁能访问这张表”。授权逻辑应当收敛到少数可测试、可版本化的地方。

策略决策点放在哪里

授权逻辑需要一个执行点（PEP）和一个决策点（PDP）：执行点拦截请求，把主体、资源、动作、环境打包成一次询问；决策点根据策略给出允许或拒绝。真正需要设计的，是这两个点放在哪里。

最轻的做法是把决策库嵌进应用进程，比如 Go 服务引入 Casbin。延迟最低，没有额外网络跳数，适合规则稳定、语言统一的团队；代价是策略分散，升级引擎要重新发版。第二种是 sidecar，每个 Pod 旁跑一个策略引擎，应用通过回环地址询问，或由网格的 ext_authz 代问。决策在本地完成，策略由控制面统一下发，语言无关，但每个 Pod 多一个容器。第三种是集中式 PDP，所有服务把上下文发给一个高可用策略服务。它最容易保证一致、方便审计，却多了一次远程调用，必须计算延迟预算并准备降级。

三种位置没有绝对优劣，关键是想清楚延迟、一致性、故障模式。远程决策要设置几毫秒到几十毫秒的超时；决策结果可以缓存，但 TTL 要短，并在权限变更时主动失效，否则会出现“已撤权还能访问”的窗口。故障时放行还是拒绝要按接口分级：低风险读接口可短暂放行并告警，写接口和资金类操作必须拒绝。

策略即代码是让这套东西可运维的前提。策略与应用代码同仓库，走同样的评审与流水线；每条策略配单元测试，用真实请求样本断言允许与拒绝；发布时打包成带版本号的 bundle，由控制面分发，出问题能回滚。决策日志同样重要，每次判定至少记录主体、资源、动作、命中的策略编号与结果。

这段 Rego 把“什么算允许”变成可测试、可 diff、可追责的文本。

令牌传播：同步链路与异步消息

身份在入口被确认后，还要跟着请求走完后半程。这一段最容易出现两类问题：下游无条件相信上游塞进来的身份；异步链路里身份直接丢失。网关自身的路由、限流与插件体系属于另一个话题（参见《API 网关设计与实现》），这里只把它当作策略执行点。

网关到下游

网关完成认证后，往下游传递身份有三种做法。第一种是原样透传用户的 access token。它实现简单，但令牌 audience 是网关，下游要么放弃 aud 校验，要么为网关开例外，两种选择都削弱校验。第二种是令牌交换，为每个下游换一张 audience 正确、scope 收窄的令牌，代价是多一次换取开销，需要缓存与过期管理。

第三种是网关注入内部头，比如 X-User-Id。它只有在两个条件同时成立时才安全：网关剥离客户端自带的同名头，防止伪造；网关与下游之间用 mTLS 或签名证明来源。少了任何一条，能直连下游的人都能自称任意用户。即便成立，下游也应保留对原始令牌的校验能力用于高风险操作。

异步消息里的身份

消息队列把同步调用拆成生产和消费两个时刻，身份问题随之变形。生产者发消息时带着用户上下文，消费者处理时可能已是几小时后，用户早已下线，令牌也已过期。把 access token 塞进消息体是最差的做法：它会过期，还会把令牌扩散到 broker、消费组和死信队列。

更合理的做法是传“身份引用”而不是“身份凭证”。消息体记录发起者标识、租户与这次操作的授权依据（例如决策编号），再由生产者用自己的服务身份签名。消费者以自己的身份向 broker 认证，验证签名，再按系统上下文重新授权：这个消费者能否处理这类事件、这个租户的数据是否允许它访问。

这里要区分两个概念。用户上下文描述“谁发起了这件事”，系统上下文描述“现在谁在执行”。后台对账、定时清理、事件重放都只有系统上下文。混为一谈会出现两种极端：后台任务持有万能用户令牌，权限大到无法审计；或者消费者无条件信任消息里的用户标识。正确的方式是两条都记录，审计日志写明发起者与执行者，授权判断分别针对两者进行。

确实需要以用户身份在异步链路中执行时，可以用短期委托令牌，明确 scope、audience 与有效期。如果任务可能排队很久，就不要把令牌放进消息，而应在消费开始时重新申请，把凭证生命周期压在实际处理的时间窗内。

常见漏洞与防护

认证授权的漏洞大多不是密码学被攻破，而是校验少了一步、权限多给了一点。下面几类在评审中反复出现。

算法混淆是第一类。攻击者把头部改成 HS256，诱导使用通用 JWT 库的服务把 RSA 公钥当作 HMAC 密钥验签，伪造的令牌就能通过；更粗暴的版本是把 alg 改成 none。防护方式是固定允许的算法集合，按密钥类型校验，绝不根据令牌头部决定算法。

头部注入是第二类。kid 被拼进文件路径或数据库查询，可能造成路径穿越；jku 与 x5u 让令牌自带公钥地址，验证方一旦拉取，轻则密钥被替换，重则被引去访问内网。防护原则是：kid 只在本地密钥集合里索引，JWKS 地址由配置写死，令牌里的外部地址一律不访问。

声明校验缺失是第三类。最常见的漏项是 aud，导致一个服务的令牌在另一个服务通用；其次是 iss，在多租户或多身份源环境里，不校验签发方等于接受任何一家签发的令牌。exp 与 nbf 要留合理的时钟偏移，但不能大到让过期形同虚设。

生命周期失控是第四类。access token 设成一天甚至永久，refresh token 不轮换、不绑定客户端，登出只清前端。正确的组合是短 access token、一次性 refresh token、服务端可撤销的会话记录，以及改密、封禁时的全量失效。

令牌泄漏是第五类，常发生在不起眼的地方：日志完整打印 Authorization 头，错误上报把请求头一起打包，前端把令牌拼进 URL 查询参数，使它进入浏览器历史、代理日志和 Referer。防护要从采集侧做：日志中间件脱敏敏感头，接口禁止用查询参数传令牌，前端尽量用 HttpOnly Cookie 或内存存储。

权限过宽是第六类。scope 写成通配、后台只有一个 admin 角色、服务账号拥有整库读写，短期省事，长期让最小权限原则失效。scope 应按资源与动作切分，默认拒绝，敏感操作单独授权，并定期复核长期未使用的权限。

最后一类是混淆代理。下游用自己的高权限身份执行用户请求，却不检查用户本人是否有权访问该资源，攻击者找到一个入口就能借刀杀人。防护的关键是让授权判断始终围绕原始主体，服务身份只证明“谁在调用”，不能替代“用户能做什么”。高敏感接口还可以引入发送方约束：DPoP 把令牌绑定到客户端密钥，mTLS 绑定令牌则绑定到证书，二者都能让被窃取的 bearer token 失去价值。

小结

微服务认证授权，本质上是在三条身份线上分别建立可信凭证，再把授权判断收敛到少数可测试的决策点。OAuth 2.0 负责委托，OIDC 负责认证，JWT 只是载体；三者混用是多数设计问题的起点。服务之间用 mTLS 或 SPIFFE 一类的短期身份，且每次请求重新判断。授权模型从 RBAC 起步，按需叠加 ABAC 或 ReBAC，策略以代码形式评审、测试与分发。令牌在同步链路中按受众换发，在异步消息里传身份引用而非凭证；算法白名单、受众校验、短有效期与日志脱敏应当成为默认配置。
