Rust 迭代器与闭包

本文属于《Rust 学习路线》第 18/68 篇
上一篇系列目录下一篇

写 Rust 一段时间之后，会发现几乎每一段业务代码最后都落在“遍历一个集合、挑出需要的元素、变换成另一种形状”上。迭代器与闭包正是为此准备的两件工具：前者把遍历抽象成可自由拼接的流水线，后者让每一步变换都能就地描述，不必单独写函数。本文从 Iterator trait 出发，依次讲清三种取得迭代器的方式、常用适配器与消耗器、自定义迭代器、闭包的捕获与 Fn 系列 trait，最后用词频统计和惰性读文件两个例子把它们串起来。示例基于 Rust 1.64 与 2021 edition，读者只需了解所有权与借用规则即可跟上。

一、Iterator：惰性是设计的起点

Rust 的 for 循环并不认识数组、Vec 或 HashMap，它只认识一种东西：实现了 Iterator 的类型。标准库把“逐个取出元素”收敛成一个极小的约定，核心只有两行。

Item 是关联类型，由实现者指定，调用方不必写泛型参数就能知道元素是什么。next 接收 &mut self，因为推进游标本身是一次修改；返回值用 Option 表达“还有”与“没有了”两种情况，而不是额外提供一个 has_next 方法。这种设计把“取元素”与“判空”合并成一次调用，也避免了“忘记判空就取”的错误。

需要注意，标准库并不要求迭代器在返回 None 后继续保持 None，后续行为由具体实现决定。绝大多数适配器耗尽后会一直返回 None，但自己实现时不要依赖这一点；确需保证时可用 fuse 固定行为。

惰性是这套设计的另一个支点。写下 v.iter().map(|x| x * 2) 时，没有任何元素被乘以二，得到的只是一个描述“将来要做什么”的结构体。只有调用 next、进入 for 循环，或者交给 collect、sum 这类消耗器时，计算才真正发生。惰性带来两个直接好处：一是可以把多个步骤拼成一条链，中间不产生临时集合；二是可以表达无限序列，只要调用方按需取用，程序就不会真的跑不完。for 循环本身就是最朴素的消耗器，编译器会把它展开成对 IntoIterator::into_iter 的调用加上反复的 next。

惰性也常被误解为“性能更好”。适配器本身几乎不引入额外开销，链式写法通常能编译成与手写循环相当的机器码，但这是零成本抽象的目标而非承诺；真正决定性能的是每一步做了多少工作，而不是用了几个点号。

二、iter、iter_mut 与 into_iter

同一个集合有三种取迭代器的方式，区别只在“元素是什么类型”和“集合还能不能用”。

iter 借用集合，产出 &T，调用结束后集合原封不动，可以再遍历一遍。iter_mut 可变借用，产出 &mut T，适合就地修改元素；因为它持有可变借用，遍历期间不能再读这个集合。into_iter 则按值取得集合的所有权，产出 T 本身，遍历之后原变量已被移动，不能再使用。

for 循环的三种写法正好对应它们：for x in &v 等价于 iter，for x in &mut v 等价于 iter_mut，for x in v 等价于 into_iter。编译器看到的是 IntoIterator 的三个实现，分别是针对 &Vec<T>、&mut Vec<T> 和 Vec<T> 的。

数组要单独说明：2021 edition 下按值调用 into_iter 产出元素本身，这是 Rust 1.53 起随 edition 切换的行为；2018 edition 为兼容旧代码，该调用仍被解析为借用，需写 IntoIterator::into_iter(arr) 才能拿到值。HashMap 的三种迭代器分别产出 (&K, &V)、(&K, &mut V) 和 (K, V)，顺序不做保证。

选择哪一种，判断标准很朴素：只需要读就用 iter，需要改就用 iter_mut，之后不再需要这个集合并想省掉克隆就用 into_iter。很多“借用冲突”的报错，根源就是在本该用 into_iter 的地方写了 iter。

三、适配器：一条不产生中间集合的流水线

适配器接收一个迭代器，返回另一个迭代器。它们全都惰性，调用时只构造新结构，不做实际计算，因此可以任意串联而不产生中间 Vec。下表列出本文会用到的常用适配器。

适配器 作用 产出类型
map 逐个变换元素 U
filter 保留谓词为真的元素 原元素
filter_map 变换与过滤合并，返回 Option U
flat_map 变换后展平一层 内层元素
take / skip 取前 n 个 / 跳过前 n 个 原元素
zip 与另一迭代器配对 (A, B)
chain 首尾相接 原元素
enumerate 附带下标 (usize, T)
peekable 可预读下一个元素 原元素

map 与 filter 最常用，也最容易被写成两步：先 map 成 Option，再 filter 掉 None，最后 map 解包。filter_map 把这三步压成一步，闭包直接返回 Option，是解析文本时最顺手的工具。

flat_map 处理“每个元素又能展开成多个”的场景，例如把若干句子拆成单词、把 Vec<Vec<T>> 拉平。它与 map 加 flatten 等价，后者在读代码时语义更清楚，前者在链式调用里更紧凑。

take 与 skip 是处理无限序列和分页的常用手段。(0..).filter(|n| n % 2 == 0).take(5) 只会计算到第五个偶数，后面的数根本不会生成。zip 把两个迭代器按位置配对，长度不等时以短的一方为准，不会报错，这一点在处理两个来源的行时值得记住。chain 用于拼接同类型的序列，enumerate 在需要下标时比手动维护计数器更安全。peekable 则给了“看一眼再决定”的能力，词法分析里判断某个符号是否属于当前 token 时很好用。

适配器链的顺序会影响语义与开销：把 filter 放在 map 之前通常能少做无用的变换，把 take 提前可以让后面的步骤少跑几轮。惰性并不自动等于高效，它只是把“什么时候算”的决定权交给调用方。

四、消耗器：让流水线真正跑起来

消耗器是链尾的那一次调用，它驱动 next 直到结束，把结果收敛成一个值。collect 最通用，能把元素收进 Vec、String、HashMap、BTreeSet，甚至收进 Result<Vec<T>, E>：只要中途遇到 Err，整个收集就提前结束并把错误返回，这在批量解析时非常省事。

fold 是通用形式，sum、count、max 都可以用它表达。它接收一个初始值和一个闭包，闭包的参数是“累积值”和“当前元素”，返回值成为新的累积值。需要一边遍历一边构造 HashMap、拼接字符串或者统计多个指标时，fold 比先 collect 再二次遍历更直接。

any、all、find、position 属于短路消耗器：一旦结果确定就停止推进，后面的元素不会被访问。这一点在无限迭代器或昂贵的计算上很关键，也意味着它们不能用来做“必须全部执行”的副作用。反过来，count、sum、max 一定要跑完整条链。

collect 的目标类型由标注、返回值或后续用法推断；推不出来时编译器会报“type annotations needed”，用 let v: Vec<_> = ... 或 collect::<Vec<_>>() 指明即可。

五、自定义迭代器与 impl Iterator 返回类型

有些序列本身就是“算出来”的：分页游标、递增的编号、某个范围内的偶数。与其先把它们铺进一个 Vec，不如实现 Iterator，让调用方按需取值，内存占用与序列长度解耦。

关键是把“进度”放进结构体字段，next 只负责推进状态并返回当前值。这样写之后，map、filter、take 等适配器立刻全部可用；若希望 for x in &evens 也能工作，再为 &Evens 实现一次 IntoIterator。可选实现 size_hint 给出长度下界，让 collect 一次分配到位。

函数返回迭代器时，类型往往写不出来。(0..n).map(|x| x * x) 的具体类型是标准库里一串又长又带闭包占位符的结构体，无法在签名中书写。这时用 impl Iterator<Item = u32> 作为返回类型，把具体类型藏起来，调用方只依赖 trait。

如果返回的迭代器借用了参数，需要在 impl Trait 后补上生命周期，例如 fn words<'a>(s: &'a str) -> impl Iterator<Item = &'a str> + 'a。另一个限制是：同一个函数的不同分支必须返回同一个具体类型，不能在 if 里返回 map、在 else 里返回 filter。遇到这种情况，要么用 Box<dyn Iterator<Item = T>> 做动态分发，要么用 chain 之类的方式把两支合并成一种类型。

六、闭包：语法、推断与捕获

闭包是可以捕获环境的一段匿名函数。语法是竖线包住参数，后面跟表达式或代码块；没有参数时写成 ||，需要多行时加花括号。

与普通函数相比，闭包最大的便利是类型推断：参数和返回值通常不必标注，编译器会根据第一次调用或使用位置推出具体类型。代价是闭包一旦被推断成某种类型，就不能再用另一种类型调用它。

闭包如何拿到外部变量，由编译器自动决定，优先级大致是：只读就用不可变借用，需要修改就用可变借用，需要交出所有权就移动。move 关键字强制第三种方式，把捕获的变量按值搬进闭包。把闭包交给新线程、存进结构体或者作为返回值时，通常必须写 move，否则闭包会借用栈上的局部变量，生命周期撑不到使用点。

这三种捕获方式对应三个 trait：FnOnce 表示只能调用一次，因为它会消耗捕获的值；FnMut 表示可以多次调用并修改捕获的变量；Fn 表示只读捕获，可以并发共享。它们之间是包含关系：实现了 Fn 的闭包也实现了 FnMut 与 FnOnce，实现了 FnMut 的也实现了 FnOnce，反之不成立。写接收闭包的函数时，按需要的最小能力约束即可：只调用一次用 FnOnce，会修改状态用 FnMut，只读用 Fn。约束越宽松，能接受的闭包越多。

七、组合实战：词频统计与惰性读文件

把前面的零件拼起来，最典型的需求是统计一个文本文件的词频。要点有两个：用 BufReader 按行读取，避免把整个文件读进内存；用 entry 接口累加计数，避免先查再插的两次哈希。

lines 同样惰性，循环每推进一步才读一行，内存里始终只有当前行。line? 不能省：lines 的元素是 io::Result<String>，读盘失败会在这里暴露而不是被静默跳过。取前几名时，把 HashMap 转成 Vec 再排序即可。

惰性让这类代码天然支持“只处理前若干行”：给 lines 接上 skip(1).take(1000)，就是跳过表头、只读一千行的流式版本，文件再大也不会撑爆内存。另外，lines 会去掉行尾换行符与紧邻的回车符；若依赖原始字节，应改用 read_until。

八、常见坑与排查思路

第一个坑是迭代器被消耗后不能复用。next 会推进内部游标，collect、sum 会把迭代器整个吃掉，之后再调用就是编译错误。需要在链中途“借用”一下而不消耗，可以用 by_ref，例如 iter.by_ref().take(3)；需要重复遍历，就先把结果收进集合，或者每次重新调用 iter。

第二个坑是遍历时修改集合。for x in &v 持有不可变借用，循环体里 v.push(x) 需要可变借用，编译器直接拒绝。正确的做法是先收集要增删的元素，循环结束后再统一处理；或者改用 retain、drain 这类本身就设计为“边遍历边改”的方法，它们内部会保证借用合法。

第三个坑是 collect 的目标类型推断不出来。链式调用中间没有类型信息时，编译器不知道要收成 Vec 还是 HashSet，只能报错。加上标注或用 turbofish 即可。sum 也有类似问题，空集合求和时无法推出数值类型，同样需要标注。

第四个坑是闭包捕获引起的借用错误：闭包按引用捕获了某个变量，主流程随后又要可变借用它，冲突就出现了；把闭包 move 进新线程还要满足 Send 与 'static，借用局部变量的闭包无法通过。排查时先看捕获了什么，再决定是提前克隆、用 move 交出所有权，还是缩小闭包作用域。

最后一个易忽略的点是“写了适配器却没有消耗器”：整条链只构造了结构体，什么也不会发生，编译器通常给出 unused 警告。看到结果为空时，先确认链尾有没有 collect、for 或别的消耗器。

小结

迭代器把遍历抽象成 next 与 Item 两点约定，惰性让多个步骤拼成一条不产生中间集合的流水线；iter、iter_mut、into_iter 决定元素是借用还是所有权，适配器描述变换，消耗器驱动计算并收敛结果。闭包让每一步变换就地书写，捕获方式与 Fn、FnMut、FnOnce 决定它能被调用几次、能否跨线程。实践中建议先用链式写法把意图写清楚，遇到借用冲突时回到“谁持有、持有多久”上分析，而不是急着克隆；大文件与无限序列则优先用 BufRead 配合 take、skip 流式处理。
