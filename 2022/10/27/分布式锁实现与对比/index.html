分布式锁实现与对比

单机程序里一个 mutex 就能解决的事，一旦换成多台机器、多个进程，就变成了要在网络分区、进程暂停与时钟漂移之间做取舍的问题。本文先厘清分布式锁必须满足的语义，再依次拆解 Redis、ZooKeeper、etcd 与数据库四类实现，重点讲清 Redlock 的争议与 fencing token 的作用。读者需要了解 Redis 基本命令与 Go 语法，读完后应能为自己的业务选择合适的方案，并知道该补哪些兜底措施。

分布式锁到底要保证什么

先从一个具体场景说起。订单服务部署了三个副本，每个副本都有一个定时任务，每五分钟扫描一次超时未支付的订单并关闭。如果没有协调，三个副本会同时扫到同一批订单，重复发短信、重复释放库存。最简单的办法是让同一时刻只有一个副本在干活，这就是分布式锁要解决的问题。

把需求写细一点，一把合格的分布式锁至少要满足五条性质。第一是互斥，任意时刻最多一个持有者；这是锁的本分，也是后面所有争议的起点。第二是无死锁，持有者崩溃或网络断开后，锁最终能被别人拿到，通常靠过期时间实现。第三是可释放，加锁者能主动解锁，且只能解自己的锁。第四是高可用，锁服务本身不能成为单点，节点故障后仍能对外服务。第五是可重入，同一线程或协程重复加锁不会把自己挡在门外；这一条是可选项，取决于业务是否需要，实现上要额外记录持有者与重入次数。

多数实现用租约（lease）来表达“无死锁”。客户端申请锁时附带一个有效期，到期自动释放；业务没做完就续期。租约把“永久持有”换成了“限时持有”，代价是引入了时间这个不可靠的维度。续期间隔通常取有效期的三分之一左右，留出重试余量；续期失败要立刻停止业务，而不是继续写。

问题恰恰出在这里。进程可能因为垃圾回收、虚拟机迁移、页交换而暂停数秒甚至数分钟，暂停期间它既不能续期，也感知不到锁已经过期。等它恢复，代码还沉浸在“我持有锁”的假设里，继续修改共享数据。与此同时，另一个客户端早已拿到锁并开始操作。互斥就这样被打破了，而且没有任何一方察觉到异常。

sequenceDiagram
    participant A as 客户端 A
    participant R as 锁服务
    participant B as 客户端 B
    A->>R: 加锁成功（TTL 10s）
    Note over A: 发生长 GC，暂停 15s
    R-->>R: 锁到期自动释放
    B->>R: 加锁成功
    Note over A: A 恢复，仍以为持有锁
    A->>R: 继续写共享资源
    B->>R: 同时写共享资源

这个时序图里没有任何一行代码写错，锁服务也忠实地执行了租约，但两个客户端还是同时进入了临界区。这说明“基于超时的锁”天生无法单独保证正确性，除非引入额外的机制来识别过期持有者。后文的 fencing token 就是为此而生。

顺着这个思路，可以把分布式锁的用途分成两类。一类是效率型：加锁只是为了避免重复劳动，比如同一份报表被多个副本重复生成，偶尔重复一次无非浪费一点算力。另一类是正确性型：互斥是数据正确的前提，比如扣减库存、转移资金，一旦两个持有者同时写就会出错。两类用途对实现的要求完全不同，效率型可以容忍锁偶尔失效，正确性型不能；很多事故的根源，是把效率型的方案用在了正确性的场景上。

Redis：SET NX PX 与唯一 value

Redis 是最常见的锁服务，原因很直接：大多数系统本来就有 Redis，加锁不过是再写一个 key。早期做法是 SETNX 加 EXPIRE 两条命令，问题是这两条命令不是原子的，SETNX 成功之后客户端崩溃，key 就永远不会过期。Redis 2.6.12 起，SET 命令支持 NX 与 PX 选项，一条命令同时完成“不存在才写入”和“设置过期时间”，这个问题才算解决。

value 必须是一个全局唯一的随机串，不能用固定值。原因在释放：如果 A 的业务超时、锁已过期并被 B 持有，A 醒来后直接 DEL，删掉的就是 B 的锁。带上自己的随机串，释放前先比对，才能做到“只解自己的锁”。比对和删除必须是原子的，否则比对通过之后、删除执行之前锁刚好过期，仍会误删。Redis 没有原生的 compare-and-delete，标准做法是一段 Lua 脚本。

单实例 Redis 方案有一个绕不开的缺陷：主从复制是异步的。客户端在主节点写入锁，主节点还没来得及把这条命令同步给从节点就宕机，哨兵或集群把从节点提升为主，锁就凭空消失了。两个客户端于是可以同时持有同一把锁。这个窗口在正常情况下很短，但它存在，而且不取决于客户端写得好不好。要缩小它，只能用 WAIT 命令等待副本确认，但 WAIT 只能保证“至少一个副本收到”，不能保证故障切换后这个副本一定被选中，也不该在每次加锁时都付出这个延迟。

正因为单实例不够，Redis 作者 antirez 提出了 Redlock，试图用多个独立实例把可用性提上去。围绕它的争论，是分布式锁领域最值得读的一课。

Redlock 与那场著名的争论

Redlock 的思路是把锁同时写到多个互相独立的 Redis 实例上，通常取 5 个，不要求它们之间有复制关系。客户端记录开始时间，依次向每个实例发送带 TTL 的 SET NX，只要在多数派（3 个）上成功，并且总耗时小于 TTL，就认为加锁成功；锁的有效期要减去已经消耗的时间和一段时钟漂移的余量。释放时向所有实例发送 Lua 删除脚本。这样即使个别实例宕机，只要多数派还在，锁服务就可用。

看起来比单实例稳妥，但 2016 年 Martin Kleppmann 的文章《How to do distributed locking》对它提出了尖锐批评，核心有两点。

第一点是时钟与暂停。Redlock 的安全性依赖一个假设：各节点的时钟漂移有上界，且进程不会在持有锁期间暂停超过 TTL。Kleppmann 指出，这两件事在真实系统里都不受程序控制。客户端可能在拿到锁之后、写数据之前被 GC 暂停，暂停时间超过 TTL，锁在多数派上过期，另一个客户端拿到锁并完成写入；前一个客户端恢复后浑然不觉，继续写。此时 Redlock 没有任何机制能发现“我已经不是持有者”。更麻烦的是，Redlock 用“开始时间 + TTL - 耗时 - 漂移”计算有效期，这个计算本身就依赖本地时钟，而本地时钟可能被 NTP 调整跳跃。

第二点是没有 fencing token。Kleppmann 认为，凡是靠超时释放的锁，都必须假设持有者会在某个时刻失去锁而不自知，因此锁服务应当发放一个单调递增的编号，让被保护的存储层拒绝旧编号的写入。Redlock 不提供这样的编号，所以它只能用于效率型场景；把它当成正确性的保证，是错误的用法。

antirez 随后写了《Is Redlock safe?》回应。他的辩护大致有三层：其一，任何带自动过期的锁都建立在时间假设上，Redlock 的时间假设并不比其他算法更强，只是把漂移写进了公式；其二，客户端在长时间暂停后不应假设自己仍持有锁，业务在写之前可以先检查锁是否还在，虽然这个检查和写入之间仍有窗口；其三，fencing token 需要存储层配合，不是所有场景都能改造下游，因此不能用“没有 fencing 就不算锁”来否定 Redlock。

这场争论没有统一的胜负，但有一个被双方默认接受的结论：Redlock 不是线性一致性的锁，它不能替代 fencing token 所提供的那种保护。如果业务只是想让多个副本别同时跑同一个任务，Redlock 够用；如果业务一旦出现双写就会造成资损，那么无论用几个 Redis 实例，都必须在下游加一道防线。本文的建议很明确：不要把 Redlock 当作“更强的单机 Redis 锁”无条件推荐，选它之前先回答一个问题——锁失效但旧持有者仍在写，后果是什么。

还有一点常被忽略：Redlock 的部署成本不低。要五个独立的 Redis 实例，最好分布在不同机器甚至不同机架上，运维复杂度接近一套小型共识系统，而它换来的并不是强一致。很多团队评估之后会发现，要么退回单实例加业务兜底，要么直接选 etcd。

fencing token：让下游拒绝过期持有者

上一节反复提到一个场景：锁已经不属于 A，A 却还在写。要堵住它，不能指望 A 自己醒悟，只能让被写入的一方有能力识别。fencing token 就是这个识别凭证。

做法是让锁服务在每次成功加锁时发放一个单调递增的整数，客户端带着它去访问下游存储。存储侧记住自己见过的最大 token，凡是携带更小 token 的写请求一律拒绝。这样即使 A 在暂停后恢复、带着旧 token 写入，存储也会因为 B 已经用更大的 token 写过而拒绝 A。互斥的保证从“锁服务”转移到了“数据所在的地方”，而后者才是真正需要保护的对象。

sequenceDiagram
    participant A as 客户端 A
    participant L as 锁服务
    participant B as 客户端 B
    participant S as 存储服务
    A->>L: 加锁
    L-->>A: 成功，token = 33
    Note over A: 长 GC，锁过期
    B->>L: 加锁
    L-->>B: 成功，token = 34
    B->>S: 写入，token = 34
    S-->>B: 接受，记录 max = 34
    Note over A: A 恢复
    A->>S: 写入，token = 33
    S-->>A: 拒绝（33 < 34）

关键在于单调性由谁保证。如果锁服务本身是单点，一个计数器就够了；如果是 Redis，可以用 INCR 生成，但要注意“取号”和“加锁成功”必须绑定，否则并发下先取到号却没拿到锁的客户端会白白消耗编号。更稳妥的做法是选一个本身就有全局递增序的系统：ZooKeeper 的顺序节点编号、etcd 的 revision，都天然单调。

Kleppmann 还提醒过一个细节：token 的单调性必须是全局的，至少对同一把锁的所有竞争者成立。用随机 UUID 当 token 不行，用时间戳也不行，因为时钟会回拨。顺序节点的编号、etcd 的 revision 之所以可用，是因为它们由单一的逻辑序列产生，不依赖物理时钟。

把 fencing 想透之后，会发现它其实改变了我们对“锁”的期待。锁不再是一张通行证，而是一张带序号的号码牌；真正决定谁能写的是数据的当前状态，而不是客户端手里的凭据。这个视角对后面几种实现同样适用。

ZooKeeper：临时顺序节点与 watch

ZooKeeper 的锁 recipe 建立在两种节点之上：临时节点（ephemeral）随会话存活，会话断开就自动删除；顺序节点（sequential）在创建时由服务端追加一个单调递增的序号。把两者合起来，就是临时顺序节点。

以 /locks/order-10086 为父路径，每个竞争者创建 /locks/order-10086/lock-，服务端会返回完整路径，比如 lock-0000000042。客户端取父路径下的所有子节点并排序，如果自己是最小的那个，就获得了锁；否则监听比自己序号小的前一个节点。前一个节点被删除时，watch 触发，客户端重新检查自己是否成了最小节点。

sequenceDiagram
    participant A as 客户端 A
    participant Z as ZooKeeper
    participant B as 客户端 B
    A->>Z: 创建 lock-0000000041
    B->>Z: 创建 lock-0000000042
    A->>Z: 取子节点，自己最小
    Note over A: 获得锁
    B->>Z: 取子节点，监听 41
    Note over A: 会话结束或主动删除
    Z-->>B: watch 触发
    B->>Z: 重新取子节点，自己最小
    Note over B: 获得锁

这里有个经典陷阱叫羊群效应（herd effect）。如果每个等待者都监听父节点，任何一个子节点变化都会唤醒所有人，大家同时去查子节点列表，锁服务瞬间承受成倍的读压力。正确做法是只监听前一个节点，一次变化只唤醒一个等待者，形成一条链式的唤醒队列。Curator 的 InterProcessMutex 已经把这个细节封装好了；如果自己用原生 API 写，务必按上面的方式做。

会话失效是 ZooKeeper 锁的失效边界。客户端与集群之间的网络断开超过会话超时（session timeout），服务端就会删除该会话的所有临时节点，锁随之释放。问题在于客户端此时可能并没有死，只是网络分区或者进程被暂停；它恢复后仍然以为自己持有锁，于是又回到前面说的“旧持有者仍在写”。ZooKeeper 并不能免疫这个问题，它的顺序节点编号可以充当 fencing token，但前提是下游愿意校验。

ZooKeeper 的优点是语义清晰、有现成的 recipe、顺序节点天然提供单调编号；缺点是运维一套 Zab 集群并不轻松，写操作要经过 leader，吞吐有限，会话超时的调参也很讲究——太短容易误判，太长则故障后锁释放慢。它更适合已经有 ZooKeeper 依赖的系统，比如仍在使用 Kafka 旧版本或 Hadoop 生态的团队；为了一把锁单独引入一套 ZK，通常不划算。

etcd：lease、事务比较与 revision

etcd 的锁建立在三个原语上：lease（租约）、txn（事务）和 revision（全局版本号）。lease 是一个带 TTL 的租约，客户端通过 KeepAlive 定期续约，租约过期后，挂在其上的 key 会被自动删除。把锁 key 绑定到 lease 上，就得到了“持有者失联后自动释放”的语义。

加锁的动作由一次事务完成：如果这个 key 的创建版本为 0（也就是从未存在），就写入；否则读取当前值。etcd 的 txn 支持 If、Then、Else 三段，比较条件可以针对 key 的 create revision、mod revision、value 或 version。用 create revision 判断“从未存在”，比先 GET 再 PUT 更稳妥，因为整个过程在服务端原子执行。

etcd 的 revision 是集群范围内单调递增的，每次写事务都会推进它。锁 key 被写入时所在事务的 revision，天然可以作为 fencing token；后拿到锁的客户端一定拥有更大的 revision。这一点比 Redis 的 INCR 更干净，因为“取号”和“写入”是同一个事务。

etcd 与 Kubernetes 的关系值得单独说一句。K8s 的所有集群状态都存在 etcd 里，kube-apiserver 是唯一直接读写 etcd 的组件。控制器管理器与调度器的选主，用的是 coordination.k8s.io/v1 的 Lease 对象，通过定期更新 renewTime 来表明存活；节点心跳也用了同样的 Lease 机制，kubelet 周期性更新自己对应的 Lease。也就是说，K8s 内部大量“谁说了算”的问题，最终都落在 etcd 的租约与版本号上。这也解释了为什么 etcd 的延迟和可用性会直接放大到整个集群：它是控制面的地基。

etcd 的代价与 ZooKeeper 类似：Raft 集群需要奇数个节点，写操作要多数派确认，跨地域部署时延迟明显；运维要关注磁盘 fsync 性能、快照与碎片整理。它的优势是 API 现代、客户端成熟、与云原生生态贴合，如果系统已经跑在 K8s 上，用 etcd 做锁几乎是顺手的事。

数据库：唯一索引与 SELECT FOR UPDATE

如果业务数据本来就在一个数据库里，那么最省事的锁可能就是数据库自己。常见有两种做法。

第一种是唯一索引。建一张锁表，锁名上有唯一约束，加锁就是插入一行，释放就是删除这一行。插入成功即持有锁，主键冲突即加锁失败。

这张表把租约也表达出来了，过期行需要有人清理，可以起一个定时任务删除 expires_at 已过的记录，或者在加锁失败时检查并抢占过期行。清理任务本身要做成幂等的，多个实例同时清理也无妨，删除条件里带上过期时间即可。

第二种是行锁。在一个事务里对目标行执行 SELECT ... FOR UPDATE，其他事务想改同一行就得排队，直到前一个事务提交或回滚。锁的生命周期与事务完全绑定，不需要额外维护过期时间，也不会出现“锁过期了但事务还在跑”的情况，因为事务没结束锁就不会释放。

这两种方式的边界很清楚。它们只在同一个数据库实例内有效，跨库、跨服务就无能为力；行锁会占用连接，事务越长，连接池越紧张，高并发下很容易把数据库拖垮；MySQL 的 InnoDB 在可重复读隔离级别下，对没有命中索引的条件可能加间隙锁，锁范围比预期大，需要看执行计划确认。此外，FOR UPDATE 拿到的是数据库内部的锁，客户端崩了连接断开，事务回滚，锁自然释放，这一点反而比 Redis 省心。

数据库锁适合“锁的范围与某个事务天然重合”的场景，比如扣减单行库存、状态机流转。它不适合做跨系统的协调锁，也不适合持有时间长的业务锁。至于用 SELECT ... FOR UPDATE NOWAIT 快速失败、用 SKIP LOCKED 做任务队列，都是 MySQL 8.0 之后可用的手段，属于同一类思路的延伸。

Redis Redlock 多数派写入，但不是线性一致 需要多次往返，延迟随实例数上升 高，要维护多个独立实例 依赖时钟假设，暂停超过 TTL 即失效
ZooKeeper 写经 leader，顺序一致 写受 leader 限制，读可扩展 中高，要维护 ZK 集群 会话过期即释放，客户端可能不自知

数据库 单库内强一致 受连接与事务长度影响 低，无需新组件 连接断开事务回滚，锁自动释放

读这张表要抓住一条主线：一致性越强，往往意味着写路径上的协调越多，延迟与运维成本也越高。Redis 单实例最便宜，但它的一致性最弱；etcd 与 ZooKeeper 能提供顺序保证，代价是要维护共识集群；数据库在单库范围内几乎免费，出了这个库就无能为力。

选型可以先按用途分流。效率型场景，比如定时任务防重、缓存重建，用已有的 Redis 做单实例锁就够了，把唯一 value、Lua 释放和续期写对，再接受“极小概率重复执行”的事实。正确性型场景，先看能否把保护下沉到数据层：单库事务能覆盖就用行锁；能改下游就用 etcd 或 ZooKeeper 加 fencing；两者都做不到，就说明架构上还缺一道防线，不要指望换一把“更强的锁”来解决。

先问能不能不加锁

锁是协调手段里最重的一种，它把并发变成串行，也把可用性绑在了锁服务上。动手之前先问一句：这件事能不能用幂等代替互斥？

很多“必须加锁”的需求，本质是“同一请求被执行了两次”。给操作分配一个业务唯一键，在数据库上建唯一索引，重复插入自然失败；或者用状态机做条件更新，把 UPDATE task SET status = 'running' WHERE id = ? AND status = 'pending' 的影响行数当作是否抢到的依据。消息消费场景则用去重表或消费位点，保证同一条消息只生效一次。幂等的细节在别处已经展开，这里只强调结论：能用唯一约束和状态机解决的，不要引入分布式锁。

真正需要锁的，是那些“必须串行、且无法用一条语句表达”的操作，比如跨多个资源的复杂计算、需要先读后写的业务规则。即便如此，也应尽量把锁的范围压到最小。

粒度、超时与重试

锁的粒度决定并发度。能按订单号加锁，就不要按商户加锁；能按商户加锁，就不要用全局锁。分段锁是常见的折中：把资源分成固定数量的段，每段一把锁，既限制了竞争范围，又不会让锁的数量随对象无限膨胀。

超时设置有两个方向。TTL 要大于业务耗时的 P99，否则正常业务也会被误判为过期；但也不能无限大，否则持有者崩溃后锁迟迟不释放。获取锁本身要有超时，用 context.WithTimeout 包住，等待超过阈值就快速失败或降级，不要无限自旋。重试要带退避与抖动，避免大量客户端在同一时刻反复冲击锁服务。

还有一点是公平性。多数分布式锁不保证先来先得，Redis 的抢占式加锁在竞争激烈时可能让某个客户端长期饿死；如果业务对顺序敏感，要么选带排队语义的 ZooKeeper 顺序节点，要么在应用层加随机退避，不要指望锁本身提供队列的能力。

续期失败必须当作“失去锁”处理：停止写入、回滚已做的部分、向上报错。最危险的做法是续期失败后继续执行，心里想着“也许还能再撑一会儿”。

监控锁等待

锁的问题往往不是“锁坏了”，而是“锁等太久”。至少要采集四类指标：获取锁的等待时长分布、获取失败率、持有时长分布、续期失败与过期抢占次数。前三类能暴露热点 key 与长事务，最后一类直接对应正确性风险。

日志里要带上锁名、持有者标识与 token，出问题时才能还原是谁在什么时候持有了锁。对正确性型业务，可以加一条断言：写入前检查自己是否仍持有锁，虽然这不能消除窗口，但能把问题暴露得更早。压测时专门注入长 GC、杀掉锁服务主节点、模拟网络分区，观察业务是快速失败还是悄悄双写，这比任何纸面分析都有效。

锁服务不可用时怎么办

这是选型时最容易被跳过的问题。正确性型业务应当 fail closed：拿不到锁就拒绝服务，宁可短时不可用，也不能双写。效率型业务可以 fail open：拿不到锁就跳过本次任务，等下一轮，或者记录日志后继续，反正重复执行的代价可控。

把这条策略写进代码而不是文档，并且在监控上区分“锁服务故障”和“业务自身故障”。很多团队在故障演练时才发现，自己的锁客户端在连接超时后默认返回“加锁成功”，把最需要保护的地方变成了最薄弱的一环。

小结

分布式锁的本质不是一条命令，而是一组关于时间、故障与一致性的假设。互斥、无死锁、可释放、高可用与可选的可重入，五条性质决定了实现的复杂度；租约解决了死锁，却引入了“过期持有者仍在写”的经典问题。Redis 单实例适合效率型场景，Redlock 提高了可用性但没有消除时钟与暂停带来的风险，不应被无条件推荐；ZooKeeper 与 etcd 用共识换来了顺序保证，顺序号与 revision 可以充当 fencing token；数据库唯一索引与行锁则在单库范围内最省心。工程上优先用幂等与唯一约束消灭锁，确需加锁时控制粒度与超时，用 fencing 把最终判断放到数据层，并监控等待与抢占。
