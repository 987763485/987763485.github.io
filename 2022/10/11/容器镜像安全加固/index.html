容器镜像安全加固

本文属于《Docker 与 Kubernetes》第 31/51 篇
上一篇系列目录下一篇

镜像扫描能回答“这个镜像里有没有已知漏洞”，却回答不了“这个容器运行时究竟有多大权限”。本文把容器镜像的加固拆成构建期、镜像内容、运行期、编排与供应链几个层面，逐项给出可落地的 Dockerfile 与 Kubernetes 配置，并解释每个开关背后的取舍。适合已经能构建镜像、在 Kubernetes 上运行服务，准备把安全基线从“建议”变成“默认”的工程师阅读。读完之后，你应该能按一条有先后的路线，把非 root、只读根文件系统、能力裁剪、签名与准入、网络策略逐层落到集群里。

一、先明确防线：加固在防什么

谈加固之前，先把威胁模型说清楚。容器不是虚拟机，它与宿主机共享内核。攻击者一旦在容器内拿到代码执行，下一步通常是四件事：读取挂载进来的凭据，尤其是 ServiceAccount token；在可写目录里落地工具或篡改程序；寻找可提权的配置，例如特权容器、危险的 capability、可写的宿主机路径；以当前容器为跳板，访问内网里的其他服务。加固的每一项配置，本质上都是在切断这四条路径中的一条或几条。

由此可以归纳出四条原则。第一是最小镜像：镜像里没有的二进制，攻击者就无法直接调用；没有 shell，拿到命令执行后也少了一个称手的入口。第二是最小权限：进程以非 root 身份运行，能力集为空，禁止提权，根文件系统只读。第三是默认拒绝：网络策略先拒绝全部流量，再按需放行；准入控制先拒绝未签名镜像，再维护白名单。第四是可验证：镜像里有什么要能列出清单，镜像由谁构建、是否被篡改要能验证。

这四类措施分布在一条从源码到运行的链路上，每一段都有独立的失败模式。

flowchart LR
  A[源码与依赖] --> B[构建]
  B --> C[镜像仓库]
  C --> D[准入控制]
  D --> E[运行中的 Pod]
  B -.-> F[SBOM 与签名]
  F -.-> D
  E -.-> G[运行时检测]

图中每个箭头都是一道关口。构建决定镜像的内容与身份，仓库负责存储与分发，准入控制决定“能不能进集群”，运行期配置决定“进来之后能做什么”，运行时检测负责发现前面几层没有拦住的异常。任何一层单独使用都不够：只做签名，签的可能是一个臃肿且以 root 运行的不良镜像；只做检测，则是在事后追查，损失已经发生。

还需要强调一点：加固不是把开关全部打开。只读根文件系统会让习惯写本地缓存的程序启动失败，distroless 会让排障少一个 shell，严格的准入会在紧急发布时挡住热修复。每项措施都有成本，合理的做法是让默认值安全，同时保留少量、可审计、有期限的例外。本文每讲一个配置，都会说明它解决什么问题、可能破坏什么，以及如何验证它生效。

本文只讨论镜像与 Pod 配置的加固细节；镜像漏洞扫描与流水线集成属于另一条线的话题，这里不重复工具选型与漏洞库比对。

二、构建期：把不需要的东西留在构建机

镜像的绝大部分风险在构建阶段就已注定。最终镜像包含哪些二进制、以什么身份运行、基础层来自哪里，都取决于 Dockerfile 里的几个决定。构建期加固的目标很朴素：让最终镜像只含运行所需的最小集合，并且可复现、可追溯。

基础镜像：alpine、distroless 与 scratch

选择基础镜像，本质上是在选择“默认带进来多少东西”。常见的三个档位各有明确的适用边界。

alpine 以体积小著称，使用 musl libc 与 BusyBox。包管理器 apk 与 shell 仍在镜像里，攻击者进入容器后仍有可用的工具链。另一个代价是 libc 差异：某些预编译二进制或依赖 glibc 的运行时在 alpine 上会跑不起来，或者出现难以定位的兼容性问题。把应用静态编译，或者确认依赖链完整支持 musl，是用好 alpine 的前提。

distroless 由 Google 维护，提供 static、base、cc、java、python3、nodejs 等变体，只有运行时需要的库、证书与时区数据，没有 shell，没有包管理器。它的 nonroot 标签预置了非 root 用户，默认 UID 为 65532。distroless 适合“运行时不需要在容器里做任何运维操作”的服务。代价是排障方式要换：不能 docker exec 进去敲命令，得用临时容器、调试镜像或者把日志与指标做足。

scratch 是彻底的空镜像，只适合完全静态链接的程序。用了 scratch，就要自己负责 CA 证书、时区数据、用户信息这些容易被忽略的东西。Go 与 Rust 的静态二进制是典型场景，但程序一旦需要动态库或系统证书，问题就会推迟到运行期才暴露。

选择时不要只看体积。更重要的是“运行时需要什么”：需要 JVM 就选 java 变体，需要 Node 就选 nodejs 变体，需要 glibc 就别硬上 alpine。基础镜像一旦确定，就把它当成平台资产统一维护，而不是让每个服务各自挑一个。

多阶段构建：让工具链止步于构建阶段

多阶段构建的价值不只是减小体积，更重要的是把编译器、包管理器缓存、构建脚本、测试工具这些“构建期资产”挡在最终镜像之外。最终镜像只通过 COPY --from 拿到产物，构建阶段的文件系统不会进入运行镜像。

一个常见的误区是“多阶段构建等于安全”。如果最终阶段仍然 FROM ubuntu，再把整个应用目录拷进去，基础系统里的包、shell、包管理器一个不少，多阶段只是省了编译器。真正决定攻击面的是最终阶段的基础镜像与拷贝内容。

示例里的 <DIGEST> 是占位符，实际使用时必须替换为真实摘要。-trimpath 去掉构建机上的绝对路径，-ldflags="-s -w" 去掉符号表与调试信息，两者都能减少镜像里泄露的构建环境信息。静态编译让程序不依赖目标系统的 libc，这才使 distroless 的 static 变体成立。

固定 digest：标签会漂移，摘要不会

latest 会变，版本标签也可能被重新推送。同一个 api:1.4.2，今天拉到的和下周拉到的可能不是同一份内容。对于生产环境，这种不确定性本身就是供应链风险。摘要由镜像内容计算得出，只要内容不变，摘要就不变，因此 image:tag@sha256:... 才能精确表达“我要的是这一份”。

固定 digest 有两个层次。第一层是 Dockerfile 里的 FROM，基础镜像与构建镜像都应该带摘要；第二层是部署清单里的 image 字段，生产环境应按摘要引用，而不是按标签引用。标签可以保留给人看，摘要用于机器校验。

摘要固定之后，升级就变成一次显式的提交：更新 Dockerfile 与部署清单里的摘要，走代码评审，再重新构建、扫描、签名。这条路径比“重新打一个 tag 推上去”慢，但留下了变更记录。多架构场景要固定 manifest list 的摘要，而不是某个平台子清单的摘要，否则不同架构的节点会拉到不同的内容。

去掉非必要内容与 .dockerignore

“去除非必要包”有两层含义。第一层是运行镜像里不要装编译工具、测试框架、调试工具、文档与包管理器缓存。第二层是不要在镜像里留下构建期的秘密，例如 .npmrc、私钥、云厂商凭据、数据库口令。第二层更容易被忽视，因为文件在后续层里被删掉，并不等于它不存在：镜像分层是不可变的，前面的层仍然可以被拉下来查看。

如果确实需要在构建时使用凭据，应该用 BuildKit 的 secret 挂载，而不是 ARG 或 COPY：ARG 的值会出现在镜像历史里，COPY 进去的文件会留在层里。Docker 20.10 默认仍可能走旧构建器，使用 --mount 前要设置 DOCKER_BUILDKIT=1。

.dockerignore 同样重要。它决定哪些文件会进入构建上下文，既影响构建速度，也影响“会不会误拷”。至少应该排除版本库元数据、依赖目录、环境文件、密钥与证书、测试数据、本地构建产物。

需要提醒的是，.dockerignore 只控制构建上下文，不控制 COPY 的目标。即使排除了 .env，COPY . . 仍可能把其他敏感文件带进去。最稳妥的做法是显式 COPY 需要的目录与文件，让带进镜像的东西可以逐行列出来。

三、非 root：一条从构建贯穿到运行的约束

非 root 是性价比最高的一项加固，也是最容易被“先跑起来再说”绕过去的一项。它要在两个地方同时成立：镜像里的 USER 决定进程默认身份，Pod 的 securityContext 决定这个身份不能被覆盖。

构建期先把用户定下来。不要依赖 useradd 的默认 UID，它在不同基础镜像里可能不同；应显式指定 UID 与 GID，例如 10001，并让所有服务尽量复用同一段 UID 区间，便于审计与卷权限管理。distroless 的 nonroot 标签已内置 65532，直接 USER nonroot:nonroot 即可；USER 最好写数字，因为名字需要在 /etc/passwd 里能解析。

文件所有权也要在构建期解决。需要写的目录通过 COPY --chown 或构建时的 chown 交给运行用户，配置文件设为只读，不要让程序以 root 身份启动后再降权。入口脚本先 chown 再 su-exec 的模式要求容器以 root 启动，等于把最大的钥匙留在入口。

运行期用三个字段把身份钉死：

runAsNonRoot 是断言：镜像若以 root 启动，kubelet 直接拒绝；runAsUser 显式指定身份，避免镜像里的 USER 被改掉；runAsGroup 决定主组，影响新建文件的组归属。三者一起用才是双保险。卷场景再加 fsGroup，让挂载卷对运行用户可写；大卷可配 fsGroupChangePolicy: OnRootMismatch，避免每次启动递归改权限。

还有两个连锁问题。第一是端口：非 root 不能绑定 1024 以下的端口，应用应改为监听 8080 之类的高位端口，而不是加 NET_BIND_SERVICE。第二是家目录与临时目录：精简镜像可能没有可写的 HOME，某些运行时会往 $HOME 写缓存，需要设置 HOME=/tmp 或挂载可写目录。

验证不能只看配置。进入 Pod 后读取 /proc/1/status 的 Uid 与 Gid，比看 YAML 更可靠；distroless 没有 shell，可以起临时容器共享进程命名空间来查看。若容器起不来，先看事件里的 CreateContainerConfigError，多半是 runAsNonRoot 与镜像 USER 冲突。

四、SBOM：给镜像留一份可审计的配料表

扫描回答“现在有没有已知漏洞”，SBOM 回答“里面到底有什么”。漏洞库每天更新，三个月前扫过的镜像今天可能已经带高危漏洞，但没有 SBOM，连“里面有没有这个包”都要重新拉镜像解包。SBOM 把这件事变成一次生成、长期查询。

格式上，2022 年主流是 SPDX 与 CycloneDX。SPDX 由 Linux 基金会维护，2.2.1 版被 ISO/IEC 5962:2021 采纳，结构围绕包、文件与许可证，适合法务与采购审查。CycloneDX 是 OWASP 项目，2022 年发布 1.4 版，以组件与依赖关系为中心，和漏洞匹配、VEX 的衔接更自然。两者都能表达包名、版本、来源与许可证，差别在侧重点。

许可证这一项常被当成法务问题而跳过。工程上至少要能识别每个组件的许可证表达式，对 NOASSERTION 的条目人工确认，对 GPL、AGPL 这类有传染性的许可证设置评审门槛。策略可以是允许清单或禁止清单，但必须有负责人和例外记录。SBOM 给出的是证据，是否合规仍需法务判断。

来源追溯是 SBOM 的下一层。SBOM 说明“有什么”，证明说明“谁在什么环境下构建的”。cosign 支持把 SBOM 作为 attestation 附在镜像摘要上，也支持 SLSA 来源证明。前者让 SBOM 与镜像的对应关系可验证，后者把构建平台、源码提交、构建参数串起来。两者都不保证镜像没有漏洞，但能提高替换一个包再推上去的成本。

五、签名与准入：让“推得上去”变成“验过才能跑”

签名解决完整性与来源问题，不是漏洞问题。它回答两件事：这份镜像是不是由持有某把密钥或某个身份的人构建的，以及从仓库拉下来的内容有没有被替换。签名对象必须是摘要，不能是标签；标签可以移动，摘要不会。

私钥不能放在构建机上。更合适的做法是把它交给 KMS 或 Vault，cosign 通过 --key 指向 KMS URI，让签名动作发生在密钥边界内。轮换密钥时，公钥要同步更新到准入策略，旧公钥保留一段时间以验证历史镜像。

密钥模式之外还有 keyless 模式。cosign 借助 Fulcio 签发短时证书、借助 Rekor 记录签名事件，签名者身份来自 OIDC。2022 年这条路径仍带实验性质，使用时需要设置 COSIGN_EXPERIMENTAL=1。它省去了长期密钥的保管，但把信任转移到身份提供方与透明日志上：校验时不仅要验签名，还要限定签发者与主体，否则任何人用任意账号签的镜像都可能通过。内网环境还要评估公共实例的可用性，必要时自建或改用密钥模式。

签名的价值在准入控制处兑现。策略控制器在 Pod 创建时校验镜像签名，未签名或签名不匹配就拒绝。sigstore 的 policy-controller、Kyverno 的 verifyImages、Connaisseur 都能做，选型时重点看三件事：能否按命名空间配置、能否校验 attestation、失败时是否 fail closed。

这段策略表示：shop 路径下的镜像必须带有与指定公钥匹配的签名。真实环境中还应加上 attestation 校验，例如要求存在 SBOM 或来源证明，让签名与内容绑定。

落地时有两个细节容易踩坑。第一是签名时机：cosign 的签名存放在仓库里，必须先推送再签名；如果准入策略覆盖所有命名空间，CI 推送后紧接着的部署就会被拦下。可行做法是推送到 staging 仓库签名并验证，再按摘要提升到生产仓库，或者让 CI 推送后立即签名，把未签名窗口压到最短。第二是故障处理：策略控制器不可用时应拒绝而不是放行，同时保留一条带审计的 break-glass 流程，事后补签并复盘。

还要重复一句：签名只证明“谁签的、内容没变”，不证明“内容安全”。一个以 root 运行、带着 shell 的镜像也可以被签得很漂亮。签名必须建立在前面几步的加固之上，否则只是给不良镜像发了一张证书。

六、运行期：securityContext 与运行时约束

这一节给出一个完整的 Pod 配置，再逐项解释。Pod 级与容器级 securityContext 有分工：Pod 级设置用户、组、fsGroup、seccomp 等共享属性，容器级设置能力、只读根文件系统、提权开关等独立属性。

allowPrivilegeEscalation: false 设置内核的 no_new_privs 标志，让 setuid 程序无法通过执行获得更高权限。它与 capabilities.drop: ["ALL"] 是一对：能力清空之后，容器里的 root 也不再拥有 CAP_CHOWN、CAP_NET_RAW 这类能力，很多传统提权手法会失效。确实需要绑低位端口时，才添加 NET_BIND_SERVICE 并记录原因；大多数服务改成监听 8080 更简单。

readOnlyRootFilesystem: true 把容器根文件系统挂成只读。它挡住的是“在容器里落地工具、篡改程序、写 webshell”这一类动作，代价是程序必须把可写路径挪到卷上。常见失败点是 /tmp、应用缓存、Java 临时文件与 Python 字节码缓存，处理方式分别是挂载 emptyDir、调整缓存目录、设置 PYTHONDONTWRITEBYTECODE=1。日志写标准输出，不写文件。

seccompProfile: RuntimeDefault 使用容器运行时的默认系统调用过滤。它在 Pod 级设置，对该 Pod 的所有容器生效；需要更严格时可以指向节点上的 localhost 配置文件，但分发与版本管理会成为新的负担，建议先用 RuntimeDefault 覆盖大多数负载。验收时进入容器读 /proc/self/status，确认 Seccomp 不是 0，并检查 CapEff。

AppArmor 在 1.23 到 1.25 这段时间仍通过注解配置，例如示例中的 runtime/default。它按容器名指定，写错容器名就不会生效；节点上必须真的有对应 profile，否则只是“配了但没执行”。seccomp 管系统调用，AppArmor 管文件与网络访问，两者互补。

最后别忘了“不写什么”。不写 privileged: true，不挂 hostPath 的 /var/run/docker.sock，不用 hostNetwork、hostPID、hostIPC，不设置 procMount: Unmasked。这些字段一旦出现，前面的裁剪都可以被绕过。limits 不属于狭义的权限控制，但能限制被入侵容器拖垮节点的能力，应纳入基线。

七、只读之后：可写目录与最小 ServiceAccount

打开 readOnlyRootFilesystem 之后，第一个问题不是安全，而是程序还能不能启动。答案是把确实需要写的路径显式挂成卷，其余一律只读。示例里的 /tmp 用 emptyDir 的内存介质，适合临时文件，容量计入容器内存，必须设 sizeLimit；缓存目录用磁盘介质，同样要设上限，否则一个异常写入就能把节点磁盘填满。emptyDir 的生命周期与 Pod 绑定，Pod 删除即清空，不能当持久化存储用。

如果目录需要特定属主，可以在 initContainer 里准备，但 init 容器同样要遵守非 root 与能力裁剪，不能成为绕过加固的后门。更简单的做法是依赖 fsGroup 与镜像内的目录权限。配置与证书用 ConfigMap、Secret 挂载，设置 defaultMode: 0440，避免被同 Pod 的其他进程随意读取。

凭据是只读文件系统之外的另一条大路。每个工作负载使用独立的 ServiceAccount，RBAC 只授予真正需要的动词与资源；默认的 default ServiceAccount 不应挂到业务 Pod 上。automountServiceAccountToken: false 关掉自动注入，应用不访问 API Server 时就没有 token 可偷。确实需要访问时，用 projected volume 挂载带 audience 与 expirationSeconds 的令牌，并把 RBAC 收紧到单个资源、单个动词。1.24 起不再自动创建长期 token Secret，旧的“读 Secret 拿永久 token”也应清理。

八、编排层底线：NetworkPolicy 与 Pod Security Standards

网络策略第一条应是默认拒绝。NetworkPolicy 是白名单模型：一旦 Pod 被 policyTypes 覆盖，未被规则允许的流量就会被丢弃；多条策略之间是并集。它依赖 CNI 实现，Calico、Cilium 支持完整，某些简单 CNI 只支持 ingress 或完全不支持，上线前必须确认。

示例先拒绝命名空间内所有进出流量，再只放行 ingress-controller 到 8080、DNS 解析与到数据库的 5432。kubernetes.io/metadata.name 标签由 1.21 起自动写入，用命名空间名做选择比自定义标签更稳。策略只约束 Pod 流量，不加密、不认证，也不覆盖 hostNetwork 的 Pod；需要加密与身份时，要另上 mTLS 或服务网格。

Pod 层面的底线由 Pod Security Standards 统一表达。1.23 起 Pod Security Admission 进入 beta 并默认启用，1.25 起稳定，同时 PSP 被移除。三个档位中，baseline 禁止特权容器、宿主机命名空间、hostPath、未受限的 seccomp 与 AppArmor，能力只能使用默认集合；restricted 在此基础上要求非 root、禁止提权、drop: ["ALL"]、seccomp 使用 RuntimeDefault 或 Localhost，并限制卷类型。

迁移时不要把 enforce 一步开到底。先把 warn 与 audit 设为 restricted，用 kubectl apply --dry-run=server 或真实发布观察告警，逐项修工作负载，再切换 enforce。enforce-version 要显式固定，否则集群升级时策略会跟着变，可能在毫无代码变更的夜里挡住发布。豁免名单要短、要有负责人和期限；PSA 只管 Pod 规格，不管镜像来源、RBAC 与网络，不能替代前面的措施。

九、供应链收口：构建隔离、依赖锁定与仓库治理

前面几节都在管“镜像长什么样”，这一节管“镜像怎么来的”。构建机共享、依赖漂移、仓库谁都能推，再严格的运行期配置也只是在给一条不可信的产物加锁。供应链加固的目标是让产物的每一步都有边界、有记录、有复核。

flowchart LR
  S[源码与锁文件] --> B[隔离构建环境]
  B --> P[SBOM 与来源证明]
  B --> G[cosign 签名]
  P --> R[私有仓库]
  G --> R
  R --> A[准入校验]
  A --> K[运行集群]

构建环境首先要隔离。CI 的构建任务应跑在临时、可重建的 runner 上，不与生产共享 Docker daemon，也不把宿主机的 docker.sock 挂进构建容器。能上 rootless BuildKit 就上，构建步骤的网络访问默认收紧。构建镜像与基础镜像一样按摘要固定，凭据通过 OIDC 或短期 token 获取，不要长期放在 CI 变量里。只有受信任的流水线身份才持有签名私钥。

依赖锁定是第二道。Go 用 go.sum 与 go mod verify，Node 用 lockfile 加 npm ci，Python 用带哈希的 requirements.txt 或锁文件，Rust 用 Cargo.lock 加 --locked。私有代理可以加速，也可以充当审计点，但要确保它校验上游校验和，而不是原样透传。对关键服务，定期演练“从锁文件重建”，确认锁文件真能复现依赖。

仓库是第三道。私有 Harbor 要开 TLS、按项目做 RBAC、给 CI 单独的 robot 账号并只授予 push 与 pull、开启 immutable tag 与推送时扫描。签名与 SBOM 都存在仓库里，复制与备份要连它们一起做；镜像保留策略至少保留当前在跑的摘要与最近若干个发布版本，清理前先确认没有部署引用，也要注意仓库垃圾回收或按标签清理可能把签名清单一并收走。保留与删除都应有记录，避免取证时发现镜像已经没了。

十、落地顺序：四步走，不要一次全开

加固的次序比清单本身更重要。本文建议按四步推进，每一步都有明确的验收标准，前一步稳定后再进入下一步。

第一步，非 root 与最小镜像。盘点所有生产镜像的基础镜像与 USER，把能换的换成 distroless 或 alpine，统一 UID，补上 runAsNonRoot 与 fsGroup。验收标准是生产 Pod 全部以非 root 运行，镜像里没有 shell，或者 shell 的使用有登记例外。这一步收益最大、阻力最小，大多数应用只需要改端口与目录权限。

第二步，只读根文件系统与能力裁剪。先加 emptyDir 把可写路径挪出去，再开 readOnlyRootFilesystem、drop: ["ALL"]、allowPrivilegeEscalation: false 与 RuntimeDefault seccomp，AppArmor 用 runtime/default 兜底。先在测试命名空间用 restricted 的 warn 与 audit 观察，再灰度到生产。验收标准是所有工作负载通过 restricted 的 Pod 规格检查，例外有记录。

第三步，签名与准入。把签名接进流水线，先在生产命名空间用告警模式跑一段时间，确认没有漏签、没有因镜像提升导致摘要变化，再切 enforce。验收标准是新发布的镜像全部有签名与 SBOM，未签名镜像无法进入受保护命名空间，break-glass 有审计记录。

第四步，运行时检测。前面的步骤是预防，检测负责发现绕过。用 Falco 或 Tetragon 观察异常进程、敏感文件写入、异常外联与 seccomp 拒绝，把告警接进值班流程并演练。验收标准是关键告警有 runbook、有误报收敛机制，而不是“装了 Agent 就算完成”。

这个顺序的理由很直接：先缩小攻击面，再限制爆炸半径，然后保证进入集群的东西可信，最后用检测补盲。反过来做，先上签名会把不安全的镜像“认证”一遍，先上严格准入会让大量未改造的负载停摆。每完成一步，把指标留下来：非 root 覆盖率、只读覆盖率、签名覆盖率、例外数量与平均修复时间。这些数字比“我们上了安全基线”更能说明问题。

小结

本文从构建期、镜像内容、运行期、编排层与供应链五个方向，梳理了容器镜像加固的可操作项。核心思路是先减少镜像里的东西，再减少进程能做的事，然后用签名与准入保证进入集群的产物可信，最后用运行时检测补上预防的盲区。落地时按“非 root 与最小镜像、只读与能力裁剪、签名与准入、运行时检测”的顺序推进，每一步都用可观测的指标验收。加固的终点不是一张全部打勾的清单，而是一套能持续发现例外、收敛例外并留下证据的机制。
