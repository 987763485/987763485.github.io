vLLM 推理加速实践

先把标题说清楚：标题里的这个名字，指的是一类“把大模型推理服务做得更快”的引擎，截至本文写作时它还没有公开可用的版本，社区里关于它的讨论多停留在设计思路上。因此本文既不涉及它的命令、参数与接口，也不会给出任何版本号或吞吐数字。本文要回答的是一个更朴素的问题：在 2023 年初已经能拿到的工具之上，一个自回归大模型的推理服务，怎样才能把同一张显卡的吞吐压榨出来。读者需要了解 Transformer 的基本结构、Python 与 PyTorch 的常规用法，读完之后应当能判断自己的服务卡在哪一环，并知道有哪些手段可以试。

先把账算清：prefill 与 decode

两个阶段的瓶颈并不相同

自回归生成可以切成两段。prefill 阶段把整段 prompt 一次性送进模型，做的是长度为 L 的矩阵乘，乘加单元几乎排满，属于算力受限；decode 阶段每次只推进一个 token，却要把全部权重以及这条序列的 KV Cache 从显存里读一遍，计算量很小，属于显存带宽受限。

用一组示意的数字感受一下差距。假设模型有 70 亿参数、以 fp16 存放，权重约 14 GB，每生成一个 token 至少要把它完整读一遍；若显卡带宽按 2 TB/s 计，单条序列的理论上限就在每秒一百多个 token 的量级，而这已经是忽略了计算开销的乐观估计。真实系统还要加上 KV Cache 的读写、kernel 启动与采样，能拿到的只会更少。反过来看 prefill，同样一份权重被整段 prompt 复用了几百上千次，带宽压力被摊薄，瓶颈落在算力上。

算术强度决定优化方向

用算术强度（每读一字节能换来多少次浮点运算）来看更清楚：prefill 的强度高，优化靠更快的矩阵乘、更好的 kernel 与低精度计算；decode 的强度低，优化靠“一次多干点活”，也就是把多条请求拼进同一个 batch，让同一份权重被多条序列共享。这是后文所有吞吐手段的共同出发点。

一句话概括：prefill 拼算力，decode 拼带宽，而提高 decode 效率最直接的办法是增大“有效批大小”，即同一轮前向里真正参与计算的 token 数。

连续批处理：让批大小动起来

静态拼批浪费在哪

最直观的做法是攒一批请求一起送进去，等这批里最长的序列生成完，再收下一批。问题有两层：一是长度差异被 padding 抹平，短请求全程陪跑；二是整批结束之前新来的请求只能排队，显卡在长尾阶段空转。示意一下，四条请求分别需要 40、200、210、220 个 token，静态批的耗时由 220 决定，前三条的大部分算力都花在了填充位上。并发越高、长度越参差，浪费越明显。

按迭代调度

2022 年 Orca 给出的思路是按迭代调度（iteration-level scheduling）：把调度粒度从“一批”缩小到“一次 decode”。每一轮前向结束后重新组批，已结束的序列立刻退出并归还显存，排队的新请求立刻补位。任意时刻批里都是仍然活着的序列，padding 只剩尾部很少一点。

flowchart TD
    A[新请求进入等待队列] --> B{显存是否够分配}
    B -- 够 --> C[加入运行批次]
    B -- 不够 --> D[等待或抢占低优先级序列]
    C --> E[执行一轮 decode]
    E --> F{序列是否结束}
    F -- 是 --> G[释放 KV Cache 并返回结果]
    G --> A
    F -- 否 --> B
    D --> B

调度策略里的取舍

先来先服务实现简单，但一条超长请求会长期占位，后面的短请求全被拖住；按剩余长度排序能把长度相近的请求聚在一起，代价是短请求可能被饿死，需要加等待时间上限兜底。显存不足时还要能抢占：把某条序列的 KV Cache 换到 CPU 内存，或者直接丢弃、等有空位时用已生成的 token 重算。换出省显存但费带宽，重算省内存但费算力，选哪个取决于请求的长度分布。另外批大小并非越大越好，它会直接推高每 token 延迟，这一点后文再谈。

复用的三个层次

最省事的是前缀共享：同一套 system prompt、同一份文档做问答，前缀部分的 KV 完全一致，可以只算一次，多条序列引用同一块显存，用引用计数管理生命周期。第二层是多轮对话，历史轮次的 KV 直接续用，只对新增内容做 prefill，这也是聊天类服务能把首 token 延迟压下来的关键。第三层是采样分支，beam search 或一次生成多个候选时，前面相同的部分共享一份 cache。

碎片从哪来

如果按“最大可能长度”为每条序列预留连续显存，实际用量往往远小于预留；不同长度的序列反复申请释放，还会留下外部碎片，最后总量明明够却分配失败。工程上的方向是把 cache 切成固定大小的块，用一张映射表把逻辑位置翻译成物理块，按需追加、不要求连续；配合块级引用计数，共享与回收都变得自然。这一思路在 2023 年初仍处在研究与早期实现阶段，本文只把它当作方向，不展开具体系统。

显存不够时：量化、并行与卸载

权重量化：把带宽一起省了

decode 是带宽瓶颈，权重从 fp16 压到 INT8，读取量直接减半，理论上的 token 速率上限也跟着翻倍，所以量化在推理端的收益比对训练端更直接。工程上有两条路：训练后量化（PTQ），用少量校准数据统计激活范围，把权重和激活一起量化；以及只量化权重、激活仍用 fp16 的轻量做法，实现简单、精度损失也小。INT4 通常要配分组量化，每组一个缩放因子，否则精度掉得厉害。需要留意反量化的开销：如果 kernel 在每次乘加前都反量化一遍，省下的带宽又被算力吃掉，收益会明显打折。至于把 KV Cache 也量化，当时还只有零星尝试，不建议在有精度要求的场景里贸然使用。

张量并行与流水并行

单卡放不下时，FasterTransformer 这类实现支持张量并行：把注意力的头、前馈层的列切到多张卡上，每层做两次 all-reduce。通信量与批大小、隐藏维度相关，卡间有 NVLink 时比较划算，跨机走普通以太网往往得不偿失。层间切分即流水并行，通信少，但会引入气泡；decode 阶段每步都要把整条流水走一遍，气泡占比很高，一般只在权重实在放不下时才用。

卸载与算子融合

DeepSpeed-Inference 支持把部分权重放到 CPU 内存甚至 NVMe，只在用到时搬进显存。它能让单卡跑起更大的模型，但每步都要走 PCIe，带宽比显存低一个数量级，延迟明显变差，适合离线批处理而不适合在线对话。另一条路是算子融合：把 LayerNorm、残差、激活融进同一个 kernel，减少 kernel 启动次数与中间结果的往返读写。在 decode 这种每步计算量极小的场景里，这类开销占比很高，融合的收益也就格外明显，这也是 TensorRT 与 FasterTransformer 的主要卖点。TensorRT 对 LLM 的支持在 2023 年初还不完整，动态 shape 与 KV Cache 的处理需要自己补不少工作。

方案 主要手段 适合的场景
FasterTransformer 融合 kernel、张量并行、INT8 单机多卡、模型结构固定
DeepSpeed-Inference 张量并行、权重卸载 显存不足、可接受较高延迟
ONNX Runtime 图优化、算子融合、量化 跨平台、CPU 与 GPU 混合部署
TensorRT 强融合、FP16 与 INT8 shape 稳定的离线服务

延迟指标：TTFT、TPOT 与吞吐

三个指标各管一段

首 token 延迟（TTFT）从请求到达到第一个 token 产出，主要由排队时间与 prefill 决定；每 token 延迟（TPOT）是 decode 阶段相邻 token 的平均间隔，也就是用户感知到的“打字速度”；吞吐则是单位时间服务的 token 数或请求数。三者互相牵制：批越大，权重被摊得越薄，吞吐越高，但每条序列每步要等更久，TPOT 随之变长。prefill 与 decode 混跑时，一个长 prompt 的 prefill 会把正在 decode 的序列卡住，TTFT 与 TPOT 同时抖动，这是很多服务“时快时慢”的根源。

按场景定目标

交互式对话盯着 TTFT 与 TPOT，通常希望 TTFT 在几百毫秒、TPOT 在几十毫秒的量级（示意，实际取决于模型与硬件），此时批大小要保守，甚至可以把 prefill 拆到单独的副本上做，避免两种负载互相干扰。离线摘要、批量标注只看吞吐，可以尽量加大批、开大 cache。混淆两者是常见的错误：拿离线跑出的吞吐数字去承诺在线体验，用户只会觉得卡。此外一定要看分位数，平均值好看而 p99 很差，说明调度里存在长尾阻塞，需要回到抢占与排队策略上找原因。

举一个示意的场景帮助建立直觉：某服务在批大小为 8 时 TPOT 约 40 ms，把批加到 32 之后吞吐明显上升，但 TPOT 会涨到 100 ms 以上（数字只用于说明趋势）。如果产品要求“像人打字一样流畅”，这个交换就不划算；如果这批请求来自后台的摘要任务，那就完全值得。同一个引擎，服务两种流量，本来就该有两套参数。

服务化：队列、超时与监控

请求的生命周期

一个能用的推理服务至少包含网关、队列、调度器与执行器四层。网关做鉴权、限流与参数校验；队列吸收突发流量，避免瞬时并发把显存直接打爆；调度器决定谁先进批、这一批放多大；执行器持有多份模型副本，并负责 cache 的分配与回收。多模型部署时，显存要按模型池化：常用模型常驻，冷门模型按 LRU 换入换出，换出前必须把它的 KV Cache 一并清掉，否则换出等于没换。

超时、取消与优雅退出

客户端断连是最容易被忽略的显存泄漏源：连接没了，序列还在生成，KV Cache 一直占着，时间一长整个服务就分配不出新请求。执行器应当在每轮 decode 之前检查取消标记，及时中止并释放。超时同理，超过上限的请求要中止并返回已经生成的部分，而不是放任它跑完。进程退出时先停止接单，把在跑的批处理完再释放显存，否则重启的那几秒里会出现一片失败。这些细节不涉及模型结构，却决定了服务在真实流量下是否稳定。

该盯哪些指标

队列长度与等待时间、实际批大小分布、KV Cache 占用率、TTFT 与 TPOT 的分位数、GPU 利用率与显存余量、OOM 与抢占次数。前几项反映调度是否健康，后几项反映容量是否够用。建议把每个请求的输入输出长度也记录下来：长度分布一变，之前调好的批大小上限往往就不合适了，容量规划要跟着数据走，而不是跟着感觉走。扩容的触发条件也建议用队列长度与排队时间，而不是 GPU 利用率：推理服务的利用率天然忽高忽低，按利用率扩容要么频繁抖动，要么永远来不及。

小结

大模型推理的吞吐问题，本质上是被 decode 阶段的显存带宽卡住的：算力并非不够，而是每一步只算一个 token，权重读得多、用得少。连续批处理把批大小变成动态的，是收益最大、也最值得先落地的一步；KV Cache 的前缀共享与分块管理，决定了一个服务能扛多长的上下文和多高的并发；量化、张量并行与卸载是显存不足时的补充手段，各自都有明确的代价。上线之前先把 TTFT、TPOT 与吞吐的口径定清楚，再按场景做取舍，比盲目调大批参数有效得多。
