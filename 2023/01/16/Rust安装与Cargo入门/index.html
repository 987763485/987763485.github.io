Rust 安装与 Cargo 入门

本文属于《Rust 学习路线》第 1/68 篇
上一篇系列目录下一篇

装好 Rust 只是第一步，真正的日常操作几乎都发生在 Cargo 里：新建项目、拉取依赖、切换工具链、跑测试、查文档，全靠它。本文面向刚决定学 Rust 的读者，假定你会用命令行、写过至少一门编译型语言，但没有碰过 rustup 与 Cargo。文中从工具链安装讲到第一个项目的构建流程，再逐节拆开 Cargo.toml，最后给出几条日常命令与常见故障的排查方向。读完应当能在本机跑起一个带第三方依赖的项目，并知道每条命令背后改动了哪些文件。本文以 Rust 1.66、2021 edition 的行为为准。

rustup：把工具链当成可切换的软件包

Rust 的发布节奏是六周一个稳定版，因此“我装的 Rust 是哪个版本”这件事需要专门管理。rustup 就是官方提供的工具链管理器，它负责下载、安装、切换与升级编译器，也负责给工具链增删组件。它自己不参与编译，只决定 cargo、rustc 这些命令最终落到哪一套二进制上。

官方把发布通道分成三条：

  • stable：每六周发布一次，只包含已经稳定的语言特性与标准库接口，生产项目默认用它。
  • beta：比 stable 早一个周期，用来提前验证下一版会不会破坏现有代码。
  • nightly：每天构建，可以启用尚未稳定的特性，代价是行为可能随时变化。

安装方式各平台统一，Linux 与 macOS 用一条脚本，Windows 下载 rustup-init 可执行文件。安装完成后，~/.cargo/bin（Windows 为 %USERPROFILE%\.cargo\bin）会被写入 PATH，里面出现 rustup、cargo、rustc、rustdoc 等程序。需要说明的是，这些多半不是真正的编译器，而是 rustup 放置的代理程序，运行时才根据当前设置转发到具体工具链。Windows 上还有一条额外要求：默认使用 MSVC 工具链，需要机器上装有 Visual Studio 的 C++ 生成工具，否则链接阶段会失败，这一点后文还会提到。

rustup update 值得养成定期执行的习惯，它会把 stable、beta、nightly 各自升到最新，并顺带更新已安装的组件。组件是工具链的可选部分，最常用的两个是 rustfmt（代码格式化）与 clippy（静态检查），它们随工具链一起被管理，因此也能按工具链分别安装。若某个项目需要 nightly 才能编译，用 rustup override set nightly 在该目录留下一个标记即可，离开目录后自动回到默认通道，比全局切换安全得多。临时试一次则可以用 rustup run nightly cargo build，不改变任何持久设置。

至于版本号里的 edition，它和工具链版本是两件事。edition 写在项目清单里，决定语言层面的兼容规则，一套 1.66 的工具链完全可以编译 2015、2018、2021 三种 edition 的代码。新手容易把二者混为一谈，遇到“这个语法在我机器上不认”时，先看清单里的 edition 再怀疑编译器版本。

四条命令构成最基本的循环：

cargo build 把可执行文件放在 target/debug/hello_cargo，cargo run 在需要时先构建再启动它，cargo check 则跳过了代码生成与链接，只验证语法、类型和借用。check 的速度通常比 build 快数倍，改代码时反复执行它最划算，等到要运行了再 build。cargo test 会用测试配置重新编译一遍，把标注了 #[test] 的函数收集起来逐个执行，最后打印通过数量；即使项目里一个测试都没有，它也会编译并报告零个测试，可以当作一次完整的构建检查。

target/ 是 Cargo 的工作目录，编译产物、依赖的中间文件、增量缓存的元数据全在里面，体积很快涨到几百 MB。它可以随时删除，重新构建会再生成，所以 cargo new 默认写好了忽略规则。想手动清理用 cargo clean，只清某个包用 cargo clean -p 包名。

debug 与 release 是两套编译配置，产物分属 target/debug/ 与 target/release/。调试构建把优化关掉、保留调试断言与整数溢出检查，编译快、运行慢，适合开发；cargo build --release 打开高级优化、关掉断言，运行快但编译明显更久，适合交付。日常最容易犯的错是拿 debug 产物去测性能，数字会差出一个量级。

dev-dependencies 是另一张表，只服务于测试、示例与基准，正常构建时完全不会被编译。断言库、临时目录工具这类东西放这里最合适，它们不会进入最终产物，也不会增加使用者的编译负担。与之类似的还有 build-dependencies，供构建脚本使用，入门阶段遇到的机会不多。

Cargo.lock 与清单分工明确：清单写“允许什么版本”，锁文件记录“这次实际用了哪个版本”以及每个包的校验和。它由 Cargo 自动生成和维护，不要手改。二进制项目应当把它提交进仓库，保证每台机器、每次发布都装出一模一样的依赖；库项目提交也无妨，只是下游会忽略它。想升级依赖时执行 cargo update，它会在清单允许的范围内挑新版本并重写锁文件；只想动某一个包，用 cargo update -p serde --precise 1.0.152 这类写法定点升级。

日常命令：让 Cargo 替你改文件

除了构建，Cargo 还接管了一批原本要手工编辑清单、手工跑工具的事情。这些子命令从 1.62 起陆续稳定，1.66 上都可以直接用。

cargo tree 打印整棵依赖树，是排查“这个包到底是谁带进来的”的首选。加 -d 只显示重复版本，同一个 crate 出现两个大版本时，这里会直接列出来；-i serde 反向查询哪些包依赖了 serde；--edges dev 只看开发依赖。依赖图膨胀时，先用它定位来源，再决定是升级还是换库。

cargo fmt 调用 rustfmt 统一代码风格，默认直接改文件，加 --check 只检查不修改，适合放进持续集成。cargo clippy 跑静态检查，覆盖大量写法建议与潜在缺陷，默认只警告；在流水线里通常写成 cargo clippy -- -D warnings，把警告升级为失败。刚接手旧项目时不要急着全量开启，先跑一遍看数量，再分模块清理，否则一次改动会淹没在几百条提示里。

cargo doc --open 用 rustdoc 生成本项目与全部依赖的 API 文档，输出到 target/doc/ 并自动打开浏览器。离线查第三方库的接口比翻网页快，写注释时遵循文档注释规范，生成的页面里就能直接看到示例。只想看自己的 crate 加 --no-deps，构建会快不少。

依赖源与离线构建

默认情况下，Cargo 从 crates.io 拉取依赖：先取索引，再按索引里的地址下载压缩包，并用锁文件中的校验和验证内容。索引与下载地址都可以在配置里替换，配置文件的位置有两处，全局的 ~/.cargo/config.toml 与项目内的 .cargo/config.toml，后者优先，且适合随仓库分发给团队。

离线场景分两种。临时断网时给命令加 --offline，Cargo 只用本地缓存解析，缺包就直接报错；想长期离线，在配置里写 [net] offline = true。准备阶段先在有网环境执行 cargo fetch，把锁文件里所有包下载到本地缓存，之后构建就不再访问网络。对构建机完全隔离的环境，还可以用 cargo vendor 把依赖源码复制到项目内的 vendor/ 目录，并在配置中把源指向该目录，代价是仓库体积变大，升级依赖时要重新执行一次。

几个高频问题

装完就用、用着就卡住的情况，绝大多数落在下面四类里，按报错出现的阶段判断能省很多时间。

第一类是命令找不到。安装脚本提示成功，新开终端敲 cargo 却报 command not found，通常是 PATH 没有生效：脚本只修改了 shell 配置文件，当前会话还没重新加载。Linux 与 macOS 上执行 source $HOME/.cargo/env，或者直接重开一个终端；Windows 上检查用户环境变量里是否包含 .cargo\bin，改完需要注销或重启。确认时不要只看 cargo --version，用 rustup which cargo 看它解析到哪个路径更可靠，也能顺带发现多个 Rust 安装互相遮挡的问题。

第二类是链接器缺失。代码通过了类型检查，却在最后一步报 linker cc not found 之类的错误，说明编译前端已经完成，卡在把目标文件拼成可执行文件。Linux 上装好 gcc 或发行版对应的构建工具包即可；Windows 上如果提示找不到 link.exe，就是缺少 MSVC 链接器，安装 Visual Studio 的 C++ 生成工具后重新打开终端。这类错误与语法无关，改代码再多次也没用，先看报错里提到的是哪个程序。

第三类是编译慢。第一次构建要把所有依赖从源码编一遍，耗时几分钟很正常，之后的增量编译只重编受影响的 crate。增量并非万能：改动 Cargo.toml、切换特性、修改编译配置都会让缓存大面积失效；清理过 target/ 之后也要从头再来。日常把 cargo check 作为主力，只在需要运行时才 build；同时确认 target/ 不在被杀毒软件实时扫描的目录里，这在 Windows 上影响非常大。release 构建本来就慢，不要拿它当开发循环。

第四类是版本冲突。报错里出现“expected type from crate A, found type from crate A”这种看似矛盾的句子，一般是同一个库的两个不兼容版本同时存在于依赖树中，两边的类型虽然同名却互不兼容。用 cargo tree -d 找出重复项，再看是谁引入了旧版本：能升级就统一升级，不能升级就暂时接受并存，并在边界处做显式转换。另一个常见变体是清单放宽了版本但锁文件没动，表现像“依赖明明装了却用不到新接口”，这时用 cargo update -p 定点推进再试。

小结

Rust 的入门门槛有一半在工具链上：rustup 负责“用哪套编译器”，Cargo 负责“怎么构建这个项目”，两者分工清楚之后，剩下的命令都是组合。记住 new、build、run、check、test 这五条即可覆盖日常循环，target/ 随时可删，debug 与 release 的产物不要混用。清单写允许的版本范围，锁文件锁定实际版本，前者提交评审，后者提交仓库。把 cargo fmt 与 cargo clippy 放进提交前的习惯，再遇到问题时先看报错停在哪一阶段，多数故障都能在几分钟内定位。工具链熟悉之后，就可以把注意力放回语言本身了。
