多云与混合云架构

本文属于《Docker 与 Kubernetes》第 49/51 篇
上一篇系列目录下一篇

多云、混合云、分布式云经常被混着用，但在架构决策上，它们的收益与代价完全不同。本文从概念边界讲起，依次讨论驱动因素、跨云网络、身份与密钥、数据引力、以 Kubernetes 为底座的受限可移植性、统一运维与成本，最后给出一条务实的落地路线。读者读完应能判断自己的业务需要哪一种形态，以及跨云之后必须额外承担哪些工程成本。

三个词，三种架构

先做一次概念切割。这三个词在日常对话里经常互换，但在架构评审里它们指向不同的资源所有权、控制面数量与失败模式。混用会直接导致方案错位：用多云的思路设计混合云，通常多花一份网络与治理成本；用分布式云的思路承诺多云，则会在第二个供应商进场时发现所谓“统一”并不存在。

多云：两个以上公有云

多云（multi-cloud）指同时使用两个或两个以上公有云供应商的基础设施与平台服务，这些云之间通常异构：对象存储接口、托管数据库、身份与权限模型都不一样。典型形态是“主云加备云”或“按业务线分云”，前者为了容灾与议价，后者常见于并购之后的历史遗留。

“买了两家云的主机”不等于多云架构。只有当跨云部分被当作一套系统来设计——统一的身份、统一的网络编址、明确的流量走向、可执行的切换预案——它才构成架构，否则只是两份互不相干的账单。

混合云：公有与私有的连续体

混合云（hybrid cloud）指公有云与私有云组合，并通过网络互联与统一管理，使工作负载可以在两侧迁移或分工。关键词是“连续”：私有侧承载稳态的、数据敏感的、与遗留系统紧耦合的部分；公有侧承载弹性峰值、面向互联网的前端，以及需要快速获取的托管服务。

混合云最容易失败的地方不是网络，而是“两侧被两套流程管理”。如果私有侧变更走工单、公有侧走 GitOps，两侧的镜像仓库、证书与监控各自独立，那么所谓的混合只是一条临时数据通道，故障时无法互相接管。

分布式云：同一供应商的能力延伸

分布式云（distributed cloud）是供应商视角的形态：同一个供应商拥有并运营，把公有云能力延伸到地理上分散的位置——中心区域、城市节点、客户机房、边缘站点——对外呈现统一控制面与统一账单。它与混合云的关键差别是“同构”：分布式云的站点运行同一套软件栈，运维责任在供应商；混合云的私有侧通常由企业自运维，版本与能力都可能落后。

判断方案属于哪一类，只看三个问题：基础设施归谁所有；控制面有一个还是多个；各处能力是否同构。

维度 多云 混合云 分布式云
资源归属 多个公有云供应商 企业私有云加公有云 单一供应商，多地部署
控制面 每云一套，需自行统一 两套，需要桥接 一套，供应商统一
同构程度 低，接口与模型各异 中，私有侧可自选栈 高，站点同构
主要收益 容灾、议价、避免单点 数据可控、兼容遗留 低延迟、数据本地化、运维省心
主要代价 治理与网络复杂 两侧流程容易割裂 供应商锁定最深

表中最后一行值得反复看：三种形态的代价方向不同，但没有一种没有代价。架构选择本质上是挑选自己最能承受的那一种代价，而不是寻找“最优解”。

为什么是多云：驱动、包袱与代价

多云很少是纯粹的架构理想，多数时候是一组约束叠加的结果。把约束讲清楚，才能判断哪些跨云投入是必要的，哪些只是在为“看起来先进”付账。

合规与数据驻留

第一个硬约束是数据放在哪里。分类分级之后，往往会出现“某些数据不得离开特定区域”或“不得由特定主体处理”的要求；跨国企业还要面对法域冲突，同一份数据，一个地方要求留存，另一个地方要求删除。技术上的应对是把“数据位置”变成架构的一等属性：资源命名、标签、网络分区、备份策略都能表达“这份数据属于哪个区域”，并让流水线在部署时校验。

这里只讲工程原则：位置约束应由平台强制，而不是靠文档提醒。出境相关的评估与合同安排属于法务与合规判断，本文不提供法律意见。

供应商锁定

锁定分两层。技术锁定是接口与数据格式的锁定：用了某家云特有的消息队列、数据库扩展、函数运行时，迁移就要重写。商业锁定是议价能力的锁定：用量越大、承诺期越长，换供应商的沉没成本越高。

多云常被当作议价工具，这在采购上有效，但真正的议价能力来自“可迁移的证明”，而不是“有第二家云的账号”。如果备云上从未跑过生产流量，切换预案只是一份文档，谈判桌上没有分量。

容灾与故障域

可用区设计已经把单机房故障隔离得不错，但区域级故障、账号级事故、控制面故障依然会发生。多云的容灾价值在于把故障域从“一个供应商”扩大到“多个”，代价是你必须自己承担原本由供应商承担的一致性责任。

常见误区是把“多可用区”当成“多云”。多可用区解决机房与网络设备故障，共享同一个供应商的控制面、身份系统与账单；供应商的区域级服务出问题，多可用区救不了。

成本议价与规模

第二家云带来的价格对比与承诺分散后的谈判空间，是很多企业启动多云的现实动机。但收益必须和跨云成本一起算，否则省下的钱会以流量费与双份闲置容量的形式流回去。

并购与历史包袱

最常见的多云其实是“被并购造出来的”。被收购团队带着自己的云账号、流水线、监控进来，短期整合成本高得惊人，于是形成事实上的多云。这类技术债不在网络层，而在身份与数据层：两套账号、两套权限模型、两份客户主数据。正确顺序是先统一身份，再统一网络与数据通道，最后才谈应用迁移；反过来做，往往在迁移中途发现权限映射对不齐。

代价清单

把代价写进设计文档，比事后解释更有用：

  • 复杂度：排障要跨两套控制台、两套日志、两套指标，平均修复时间上升。
  • 技能：团队要同时掌握两套网络模型与权限语义，深度都会变浅。
  • 安全面：多一套边界就多一套暴露面，基线漂移更难发现。
  • 责任边界：跨云链路出问题，两家供应商都指向对方，你需要自证。
  • 一致性：跨云没有共享的强一致存储，任何“跨云事务”都要靠应用层补偿。

如果读完清单仍认为多云必要，接下来的问题就不是“要不要”，而是“先做哪一层”。

网络：跨云的第一道门槛

跨云的绝大多数“架构问题”，最后都落到网络上：延迟、带宽、地址、解析、计费。先把网络打通并量化，后面的身份、数据、容灾才有讨论基础。

三种连通方式

  • 公网加站点到站点 VPN：最快可用、成本最低，适合容灾复制与非核心链路。缺点是抖动与丢包不可控，隧道吞吐受网关设备限制。
  • 专线：时延稳定、可承诺带宽，适合数据库复制与同步调用。缺点是交付周期以周计，费用与距离相关，通常只保证到云接入点这一段。
  • 云交换或第三方互联：多家云接入同一交换平台，减少中间段数。本质仍是专线，多了一层中立接入。

工程上通常组合使用：专线承载稳态数据面，VPN 作为备份路径，公网只承载端到端加密的少量流量。

延迟与带宽要先量化

跨云同步调用的可行性由往返时延（RTT）决定。同城两朵云之间的 RTT 通常在个位数毫秒量级，跨地域可能到几十毫秒；这些数字随线路与距离变化，只能作量级参考，上线前必须实测。一个粗略的判断标准是：一个请求若串行经过 N 次跨云调用，感知时延大致是 N 乘以 RTT 再加处理时间。超过两三次串行跨云调用的同步链路，就应改为异步，或把依赖下沉到同一朵云内。

带宽规划要看全量与增量。平时只跑增量日志，占用很低；一旦重建副本，全量传输会把专线打满，影响同链路上的其他业务。因此要给复制流量单独限速或排队，并把“重建一次副本要多久”当作必须回答的容量问题。

出口费用

跨云流量的计费方向不对称：入方向通常免费或低价，出方向按流量计费。出方向流量会同时出现在三处：跨云调用、跨云复制、跨云备份恢复。最容易被忽略的是恢复——备份写过去很便宜，灾难时读回来很贵，而且往往在最需要速度时被带宽与预算同时卡住。可行做法是把“恢复成本”写进容灾预案：明确要拉取的数据量、可接受的时间，以及是否允许备云直接以副本对外服务而不回传。

统一地址规划

跨云互联最容易被低估的是地址。两家云的默认网段经常重叠，一旦重叠就只能靠 NAT 或重建子网解决，而重建意味着改应用配置、防火墙规则与白名单。可执行的规则大致如下：

  • 全局地址计划在引入第二朵云之前定好，按“云或站点、区域、环境、用途”分段，预留增长空间。
  • 禁止使用云商默认网段，禁止业务团队自行申请，地址由平台统一分配并登记。
  • 私网互联优先，公网暴露只保留入口层；跨云服务间调用走私网地址。
  • 地址段纳入 IaC 管理，创建前做重叠校验，冲突时直接失败而不是告警。

跨云 DNS 与服务发现

DNS 是跨云架构里最不起眼、故障时又最致命的一层。它要解决三件事：私有域名在两侧都能解析、解析结果指向就近或可用的端点、切换时 TTL 足够短。可行架构是每朵云部署本地解析器，把私有域转发到统一的权威区，权威区由平台管理；切换时修改权威记录，TTL 设为分钟级。服务发现不要依赖某一家云的私有 DNS 作为唯一入口，否则那家云出问题时，另一侧连名字都解析不出来。

还要注意注册中心的跨云一致性。把一套注册中心跨云部署，等于让它的一致性协议跑在几十毫秒的链路上，选举与心跳都会变脆。更稳的做法是每个云内自治，跨云只在入口网关做端点发现。

身份、权限与密钥

网络打通之后，第二个必须统一的是身份。多云环境里最容易出安全事故的地方不是边界防火墙，而是“同一个人在两朵云里有两套账号、两套角色、两套审计日志”。

统一身份提供方与联邦

目标是让“人”和“工作负载”都只有一个权威身份源，云账号只是这个身份的被授权方。做法是把企业目录作为统一身份提供方（IdP），通过 OIDC 或 SAML 联邦到各家云，云侧不再维护独立密码；入职、转岗、离职只在一处变更，权限随组关系自动收敛。

联邦之后仍要解决角色映射：IdP 的组如何对应云侧角色，谁有资格申请，审批记录存在哪里。较稳的模式是“组到角色”的静态映射加最小权限，禁止把管理员角色直接绑到个人；临时提权走有时限的流程，过期自动回收。

工作负载的身份要单独设计。给每个工作负载发长期密钥是最常见的坏实践：密钥一旦进入镜像或配置仓库，就等于永久泄露。更稳妥的是让工作负载使用平台签发的短期身份（例如基于 ServiceAccount 的令牌交换），由平台统一对接各云凭证服务，业务代码不接触长期密钥。

密钥管理的差异

各家云的密钥管理服务概念相似、细节差别不小：密钥层级与轮转策略、是否支持自带密钥材料、审计日志粒度、跨区域复制行为，以及加密上下文能否参与授权判断。跨云时不要假设“换个客户端库就行”，至少要确认三件事：密钥的根在哪里、轮转由谁触发、删除是软删除还是立即生效。

务实的收敛方式是定义平台级密钥抽象：业务只声明“我需要一个用于某类数据的密钥”，由平台决定落在哪家云、如何轮转与备份。抽象层要保留云侧原生审计能力，不能为了统一把审计日志收进业务无法追查的黑盒。

数据：引力、复制与出境

多云的所有权问题，最终都会变成数据问题。计算可以随时重建，数据不能。

数据引力

数据引力指数据一旦积累到一定规模，与之相关的计算、分析、备份就会自然向它靠拢。跨云时的表现很直接：把一份 TB 级数据集复制到另一朵云，一次全量传输要占用专线数小时到数天；此后每次分析都要跨云读取，延迟与出口费双重叠加。结果是“数据留在原地，计算过去”，而不是相反。因此布局前先问三个问题：谁是写方，谁只读，读的频率与时效要求是什么。写方唯一、读方就近缓存，通常比双向复制更可控。

复制与一致性

跨云复制只有异步一种现实选择。同步复制要求两端在同一故障域内，跨云链路的 RTT 与可用性都不满足；强行同步的后果是写延迟随链路抖动放大，链路一断业务就写不进去。异步复制必须接受有界的不一致窗口，并把它翻译成业务语言：切换时可能丢失最近若干秒的写入，这个数字要写进预案，也要在演练中验证。对账是必要补充：切换后按业务主键比对两侧，找出缺口再补偿。

跨云备份与跨云复制是两件事。复制是“保持一份可用副本”，误删会同步过去；备份是“保留多个时间点”，需要独立保留策略与不可变存储。勒索软件场景下，能救命的往往是备份而不是复制。

数据出境的原则

数据跨云流动经常同时是跨境流动。工程上能做的是把“流向”变成可观测、可拦截的事实：给数据打分类分级标签，记录每次跨区域复制的源、目的与用途，对高等级数据默认拒绝、例外审批；技术上配合区域内静态加密、跨云传输端到端加密，以及密钥不随数据出境。

是否构成出境、需要履行哪些程序，取决于法域与具体业务，属于合规判断；本文只讨论如何用技术手段让约束可执行、可审计，不提供法律意见。

可移植性：Kubernetes 是底座，不是承诺

跨云讨论里最容易被过度承诺的词是“可移植”。Kubernetes 确实让“同一份部署描述跑在两朵云上”成为可能，但它统一的是编排语义，不是运行环境。

它统一了什么

Pod、Deployment、Service、ConfigMap 的含义在各家托管集群里一致；基于清单的部署、Helm 模板、GitOps 同步流程都能复用；有状态应用的 Operator 模式也基本通用。这让“把无状态服务搬到另一朵云”从数月缩短到数周，人员技能可以复用。

它没有统一什么

集群之下的差异依然存在，而且集中在最容易出事的地方：

  • 网络：CNI 实现、负载均衡器的注解与行为、入口控制器默认配置、网络策略支持的字段。
  • 存储：存储类能力差异很大，快照、扩容、多挂载语义并不一致，跨云迁移卷通常只能“备份再恢复”。
  • 身份：集群如何对接云身份系统、如何为 Pod 换取云凭证，各家做法不同，往往需要平台层封装。
  • 控制面：托管集群的版本节奏、升级窗口、审计能力由供应商决定，跨云无法用同一套升级策略。

因此“可移植”的准确含义是：应用层可以较少改动地重建，而不是“迁移零成本”。真正的成本在数据、在流量切换、在验证，不在改 YAML。

托管服务的锁定最难解

越是省事的服务，锁定越深。托管数据库、消息队列、对象存储的接口与语义，抽象层只能抹平调用方式，抹不平一致性模型、备份恢复方式、扩容行为与故障表现。把托管数据库换成自建，工作量不在换驱动，而在补上高可用、备份、监控、升级这些原本由供应商承担的能力。

务实的态度是分层管理锁定：核心交易数据尽量使用通用形态，保留可导出的备份与清晰的表结构；分析、缓存、异步类服务可以接受较深的托管依赖，因为它们更容易重建。每处深度依赖都要写清“退出时需要做什么”，这比追求彻底中立更现实。

运维与成本：两本账要一起算

跨云之后，运维从“一套体系”变成“一套体系加一层翻译”，成本从“资源账单”变成“资源账单加协调成本”。

统一可观测性

目标不是把所有数据塞进一个系统，而是让排障只有一个入口。先统一标签规范：云、区域、集群、服务、环境五个维度必须齐备，指标、日志、追踪共用同一套标签；再把指标与日志集中到长期存储，追踪按需采样并保证跨云上下文能串起来。两个细节容易漏：一是时钟，跨云时钟偏差会让日志排序与追踪时间线错乱；二是采样，跨云链路的数据量往往超出预期，入口按服务分级采样比事后删数据省钱。

配置管理与 IaC 的多 provider 管理

一套 IaC 管多云可行，但状态文件不能合并。合理切分是“一个仓库、多个状态”：按云与按环境隔离状态与凭据，把一次变更的爆炸半径限制在一朵云的一个环境内。再加两道门禁：计划阶段人工审阅跨云资源的增删，漂移检测每天跑一次并对差异告警。要避免的陷阱是为了“统一”而自研一层云资源封装，最后既没省工作量，又让所有人看不懂底层创建了什么；抽象只应覆盖高频且稳定的少数资源。

故障域与演练

先列故障域清单：单个可用区、单个区域、单朵云、单个云账号、专线、统一 DNS、统一 IdP。每项都要回答“发生时影响什么、如何发现、如何切换、如何切回”。其中专线与 IdP 被放大得最厉害：专线断了，跨云复制与调用同时失效；IdP 挂了，两侧运维可能都登不进控制台。

演练分层推进：先桌面推演，把流程与责任人过一遍；再断专线、禁用云账号做受控实验；最后才是真实切流。切换与切回要成对演练，很多团队只练切换，结果切回来才发现数据已经双向分叉。

两本账

显性账单包括跨云流量费、备云常驻容量、专线月租、两套可观测性后端的存储费。备云容量不必按生产同等规模预留，按“能承接核心链路”的比例规划即可。隐性账单包括两套基线带来的安全评审、跨云变更的协调会议、排障时多跳一层的沟通，以及团队为了同时掌握两套体系而变浅的技术深度。隐性成本不出现在账单上，却决定多云能否长期维持。

一个简单判断是算“跨云溢价”：把同一套工作负载在单云与跨云形态下的总成本做对比，包含人力折算。如果溢价超过业务对容灾与合规的估值，就该回到单云加多可用区，把钱花在备份与演练上。

落地路线：先备份与容灾，再谈双活

多云建设最常见的失败是顺序错了：一上来就追求应用双活，结果身份没统一、地址没规划、数据没有可恢复的副本，双活只练成两套互不相干的系统。

合理顺序是四步。第一步统一身份与地址，这是后续所有工作的前置条件。第二步让数据“可离开”：建立跨云备份、定义保留策略、每季度做一次真实恢复，用恢复结果校准 RTO 与 RPO。第三步做温备容灾：备云保留最小可用栈，数据异步复制，入口通过 DNS 或网关切换，平时不承载生产流量但保持可部署。第四步才是选择性双活，只针对无状态、读多写少的核心链路，数据层仍保持单写。

多数团队不需要真正的多云主动-主动。主动-主动要求两朵云同时承接写入，要么依赖跨云强一致（链路做不到），要么在应用层做冲突解决与数据合并，复杂度上升一个数量级。如果 RTO 以小时甚至天计，温备加演练已经足够；如果单云多可用区加跨云备份能覆盖绝大多数故障，那么把预算投向备份的不可变性、演练频次与自动化切换脚本，收益远高于再建一套双活。真正需要主动-主动的场景通常有明确外部约束：监管要求两地三中心且其中一地必须在另一家云、超大流量需要多入口就近接入，或供应商级故障被判定为不可接受。即便如此，也应先确认“哪个服务真的需要”，而不是整体架构一起上。

小结

多云、混合云、分布式云是三种不同所有权与控制面结构的形态，选择它们等于选择不同的代价。跨云的技术难点集中在网络、身份与数据三处，其中数据最难，因为复制只能异步、备份不能替代复制。Kubernetes 提供了可复用的应用层底座，但可移植不等于零成本迁移，托管服务的锁定需要逐项评估退出路径。运维上要统一可观测性与 IaC 的切分方式，成本上要同时算显性账单与隐性协调成本。落地顺序应当是先统一身份与地址，再把备份与容灾做成跨云，最后才考虑有限范围的双活。
