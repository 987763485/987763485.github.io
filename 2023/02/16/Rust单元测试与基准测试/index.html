Rust 单元测试与基准测试

本文属于《Rust 学习路线》第 25/68 篇
上一篇系列目录下一篇

写测试的成本，往往不在写断言，而在“这段测试该放在哪、怎么跑、跑得慢不慢”。Rust 把测试能力直接编进了工具链：cargo test 一次收集单元测试、集成测试与文档测试，#[test] 只是普通属性，不需要额外的测试框架与配置文件。本文按 Rust 1.67、2021 edition 的口径，把这三类测试的边界、测试代码的组织方式、常用运行参数，以及基准测试在稳定版上的现实选择讲清楚。读者应当已经能读写基本的 Rust 函数与结构体；本文不涉及异步测试框架，也不重复某个具体项目的实现细节，讲的是方法本身。

测试从哪一层开始

先建立一个朴素的模型：测试的价值与它离代码的距离成反比，与它离真实环境的距离成正比。近的跑得快、定位准，但覆盖不到组装后的行为；远的更可信，但慢且脆。Rust 的三类测试恰好对应这条谱系。

需要先摆正一个观念：测试不能证明程序正确，它只能固定你已经想到的行为。一个函数没有测试，不代表它有 bug；一个函数测试全绿，也不代表它在边界上没问题。测试的真正产出是一份可执行的约定——以后有人改动代码，这份约定会立刻告诉他把什么弄坏了。带着这个预期写测试，就不会陷入“追求覆盖率数字”的误区。

Rust 的测试代码与生产代码一起编译检查，示例里的类型错误、借用错误在 cargo test 阶段就会暴露，这让测试顺带承担了部分文档职责。

单元测试：断言、should_panic 与 Result

单元测试是一个带 #[test] 属性的普通函数。测试运行器在编译期扫描这些属性，把它们收集成一组可执行的目标，因此函数不能带参数，也不能有返回值（返回 Result 是唯一例外，后文再说）。习惯上把测试放在被测代码同一个文件底部，用一个条件编译的模块包住：

#[cfg(test)] 是关键细节：这个模块只在执行 cargo test 时参与编译，正常的 cargo build 与 cargo build --release 会把它整段裁掉。这意味着测试可以随便使用只在开发期存在的依赖，也不会让发布产物体积变大。use super::*; 把父模块的名字全部引入，若嫌范围太宽，也可以只 use super::parse_port;。

三个断言宏的分工值得记牢。assert! 接受一个布尔表达式，失败时只打出表达式原文与位置；assert_eq! 与 assert_ne! 要求两侧类型实现 PartialEq 与 Debug，失败时会同时打印左值与右值，定位快得多。参数顺序上，本文建议把期望值写在左边、实际值写在右边，这样输出里的差异方向不会让人读反。三个宏都支持在末尾追加格式化参数，失败时用它补充上下文，往往能省下一次调试。

#[should_panic] 用来断言“这段代码应当 panic”。契约中确实用 panic 表达不可恢复错误的函数（比如越界访问、违反不变量），适合用它固定行为。加上 expected = "..." 后，只有 panic 消息包含该子串才算通过，这能避免“因为别的原因 panic 也算过”的假阳性。要注意它匹配的是消息文本，消息一改测试就红，所以只截取稳定的片段。更常见的做法是让函数返回 Result，测试用 ? 传播错误，由运行器报告失败——fn ... -> Result<(), E> 是测试函数唯一合法的返回形式，前提是错误类型实现了 Debug。同一个测试不能既标注 should_panic 又返回 Result，两者表达的是相反的期望。

最后是一条组织纪律：一个测试只验证一件事。把五个断言塞进一个函数，失败时你只知道“这个函数坏了”；拆成五个测试，失败列表本身就是一份缺陷清单。

测试组织：夹具、临时目录与状态隔离

Rust 没有 @Before 之类的注解，测试夹具就是一个普通函数。需要一份配置时，写 fn sample_config() -> Config，在每个测试里调用；需要带清理动作时，把资源包进结构体并实现 Drop，测试结束（包括断言失败导致的 panic）时析构函数会执行。临时目录是这条路径最典型的应用：tempfile crate 提供的 TempDir 在离开作用域时递归删除目录，成功失败都不必自己写清理代码。本文只把它当作“用完即删的目录”来定位，具体 API 请查其文档。

按模块可见性规则，子模块可以访问祖先模块的私有项，所以 mod tests 里的 use super::*; 能直接调到私有辅助函数，不必为了可测性把它改成 pub。这条规则带来一个判断标准：单元测试测私有细节，集成测试测公共契约。如果某段逻辑必须从 crate 外部才能验证，通常说明它已经是一个对外承诺；反过来，若为了让集成测试够得着而把内部函数提成 pub，公共 API 就被测试需求污染了。遇到这种纠结，更好的处理是把纯逻辑抽成独立函数或独立小模块，让它天然可测。

状态隔离比夹具更容易被忽视。cargo test 默认多线程并行执行，测试之间的先后顺序不作保证，任何进程级的共享状态都会变成随机失败的来源：全局单例、共享的连接池、进程环境变量、当前工作目录，都属于这一类。对策是把依赖变成参数——路径、时钟、外部客户端都从外面传进来，每个测试自建一份实例；确实需要独占资源的测试，留到后面用运行参数串行化。测试里也不要靠 sleep 等待另一个线程的结果，那种写法在 CI 的慢机器上迟早会抖。

集成测试与文档测试

tests/ 目录：站在使用者一侧

集成测试放在项目根目录的 tests/ 下，Cargo 把其中每个 .rs 文件当作一个独立的 crate 编译，再链接你的库。这条规则带来两个直接后果：一是测试里必须像外部用户那样 use 库名::...，只能碰到 pub 的项；二是文件之间不共享作用域，一个文件里的辅助函数，另一个文件看不见。

多个测试文件都要用的辅助代码，放到 tests/common/mod.rs 里，各文件用 mod common; 引入。注意不能直接写 tests/common.rs：那会被当成又一个集成测试 crate，编译出来一个没有任何测试的目标。mod.rs 的形式让它只作为子模块存在，这是 Cargo 约定里少数需要记住的坑。

按文件拆分还有一个运维上的好处：每个文件是一个独立的测试目标，可以只跑其中一个，见后文的 --test 参数。常见的分法是按功能域拆，比如 tests/parse.rs、tests/storage.rs，失败时一眼能看出是哪一块坏了。

文档测试：注释里的代码会被执行

/// 文档注释里的代码块，默认会被 cargo test 当作测试编译并运行。运行器把每个代码块包进一个隐藏的 main 函数，所以块里不需要自己写 fn main。这个机制的好处很实在：示例与真实 API 同步演进，改了签名忘了改文档，CI 会直接失败。

不是所有示例都适合真跑。连数据库、起监听端口、依赖外部服务的片段，加 no_run：仍然编译，保证类型正确，但不执行。纯示意或依赖特定平台的片段加 ignore：既不编译也不运行，代价是它可能悄悄过期。二者都只是降级手段，能写成可执行的就别降级——文档测试最大的价值恰恰在那句“会被执行”上。

文档测试也有它的局限：块内看不到私有项，错误处理要写成 unwrap 才够短，涉及 async 的示例还得额外包一层运行时。因此本文的建议是把文档测试用在“对外 API 的最小可用示例”上，复杂场景交给集成测试。

--test-threads=1 是一个诊断工具，不是长期方案。当一组测试并行时偶发失败、串行时稳定通过，基本可以断定存在共享状态，此时应当去修隔离，而不是把串行参数写进 CI 配置——那会让整个测试套件的耗时随规模线性增长。必须独占资源的测试（绑定固定端口、操作固定路径），拆到单独文件并对该文件串行，比全局串行更细粒度。

基准测试：从 nightly bench 到 criterion

标准库很早就带了一个基准测试属性 #[bench]，写法与 #[test] 对称，用 test::Bencher 反复调用被测函数并统计耗时。问题在于它依赖 #![feature(test)]，到 Rust 1.67 仍然只在 nightly 上可用；坚持稳定版的团队因此用不上官方基准，为一两个基准把项目切到 nightly 又不划算。这个空档存在了很多年，也正是第三方基准库生长的土壤。

目前的主流选择是 criterion。它的定位不是“更快的计时器”，而是“把测量当成统计问题”：每个基准会被反复采样，报告给出估计值与置信区间，并能与上一次运行的基线比较，从而区分“真的变慢了”与“机器当时的噪声”。这些能力在稳定版工具链上就能用。

black_box 是基准代码里最容易被忘记的一行。优化器完全可以在编译期算出常量表达式的结果，把待测逻辑整个删掉，于是你测到的是一个空循环。把输入与输出都过一遍 black_box，是让测量有意义的最低要求。另一条纪律是只测稳定的东西：基准受 CPU 频率、后台负载、编译选项影响很大，本文不给出任何具体耗时数字，读者应当在自己的目标机器上建立基线，只与同一台机器、同一编译配置下的结果比较。配置了 harness = false 之后，cargo bench 就会编译并运行这些基准目标，报告由 criterion 输出。

覆盖率与 CI 中的位置

覆盖率回答的是“哪些行被执行过”，不回答“断言是否有效”。在 Rust 生态里，基于 LLVM 插桩的工具（如 cargo-llvm-cov）可以在不修改源码的情况下产出行覆盖与区域覆盖报告；早期常用的 tarpaulin 走的是另一条实现路径。这类工具适合放在 CI 里看趋势：覆盖率突然掉一截，往往意味着新代码没带测试；但把某个百分比设成硬门槛，很快会诱导大家写只调用不断言的测试。

CI 中更值得固定的是一条命令加三个前置检查：cargo fmt --check 保证格式一致，cargo clippy -- -D warnings 拦住常见错误，cargo test 跑完全部单元、集成与文档测试。由于文档测试默认包含在 cargo test 里，示例腐烂的问题会被自动兜住，这一点在评审时经常被低估。

小结

Rust 的测试体系没有太多魔法：#[test] 收集用例，三个断言宏负责比较，#[cfg(test)] mod tests 把单元测试留在源码旁边，tests/ 目录从外部视角验证公共 API，文档注释里的代码块顺带成为可执行示例。组织上的要点只有两条——用普通函数做夹具、用 Drop 做清理；让测试彼此独立，不依赖执行顺序与进程级共享状态。运行层面，名字过滤、--nocapture、--test-threads 与 --test 足以应付日常调试。至于性能，官方 #[bench] 长期停留在 nightly，criterion 是稳定版下的现实选择；基准数字只在同一台机器上有意义，比较趋势即可，不要拿它当结论。
