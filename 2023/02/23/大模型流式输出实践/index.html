大模型流式输出实践

大模型一次生成几百个字，往往要花十几秒。这十几秒里，界面是空的，用户不知道程序是在算、在等网络，还是已经卡死。本文讨论如何用 HTTP 流式传输把这段等待拆开：从分块传输与 SSE 的协议细节，到增量解析、首 token 延迟、服务端解耦、背压、断线续传、代理缓冲，再到前端渲染与取消。读者读完应当能独立实现一条可观测、可中断、可续传的流式链路，并知道每个环节最容易踩的坑。

一、流式输出的价值与代价

传统的一次性响应要求服务端把整段文本生成完，再一起写回。模型生成是逐 token 推进的，一秒可能只产出几十个 token，于是服务端的连接大部分时间在“算”，而不是在“传”。客户端只能等，等到最后一个字才拿到任何东西。

流式输出改变的是发送时机，不是计算速度。生成器每产出一小段，就立刻编码、写出、刷新，让字节尽早离开服务端。总耗时几乎不变，但第一个字到达的时间从“全部算完”提前到“第一个 token 算完”。

感知延迟比总时长更重要

假设一次生成需要 12 秒，首 token 在 0.8 秒后到达，此后平均每 40 毫秒产出一个 token（均为示意值）。从总耗时看，流式与非流式都是 12 秒；从用户感知看，前者 1 秒内就有内容滚动，后者要盯着空白界面 12 秒。交互设计里说的“响应性”从来不是“完成时间”，而是“多久能确认系统在工作”。流式正是用可控的传输开销，换取了这种确认。

对对话、代码补全、长文摘要这类以阅读为主的场景，这笔交易几乎总是划算的：用户可以在前几句就判断方向对不对，随时中断，省下后面的等待和费用。对必须整体校验后才能使用的场景，比如要解析成固定结构的输出，流式带来的收益就有限，因为半截 JSON 无法使用，最后仍然要等完整结果。

流式把错误变成了过程

代价首先体现在错误处理上。非流式请求失败，返回一个 5xx，客户端重试即可；流式请求一旦发出响应头，状态码就固定为 200，之后模型超时、上游限流、内容被安全策略截断，都只能在这条已经打开的通道里表达。客户端必须有能力区分“正常结束”“被截断”“中途出错”三种收尾。

其次是资源占用。一个流式连接可能持续几十秒，服务端的工作协程、连接槽位、内存缓冲都被拉长占用。并发上去以后，连接数而不是算力，往往先成为瓶颈。

最后是可观测性。一条请求在日志里变成几十个分片，若不专门记录首 token 时间、token 数、结束原因，出了问题只能看到“慢”，看不出慢在排队、慢在生成，还是慢在写出。后文按协议、解析、指标、服务端、客户端、运维的顺序，把这几个环节逐一拆开。

二、HTTP 分块传输与 SSE

流式输出并不是某种新协议，它建立在两个已有机制之上：HTTP/1.1 的分块传输负责“长度未知也能边算边发”，SSE 负责“在字节流上划出事件边界”。理解这两层，才能判断问题出在传输还是解析。

分块传输：长度未知时先发再说

HTTP/1.1 的响应通常带 Content-Length，客户端据此知道何时读完。但流式响应的总长度在开始时根本不知道，于是改用 Transfer-Encoding: chunked。响应体被切成若干块，每块前面用十六进制写明本块字节数，块与块之间用 CRLF 分隔，最后以一个长度为 0 的块收尾，之后还可以跟可选的尾部字段。

这个设计的要点是：服务端每写完一块就可以调用 flush，把数据推入内核发送缓冲区，不必等整体结束。客户端则按块长度逐段读取，读满一块交给上层，再读下一块。分块只是传输层的封装，它对内容格式一无所知，里面装 JSON、纯文本还是事件流，全由应用层约定。

需要注意，chunk 是传输层的切分单位，不是业务单位。一次 write 可能被合并成一个大 chunk，也可能因为缓冲区水位被拆成多个；TCP 层还会再切一次。因此任何“一个 chunk 就是一个 token”的假设都会在真实网络里失效。

SSE：在字节流上约定事件

SSE（Server-Sent Events）把 text/event-stream 这种内容类型规定为一串以空行分隔的事件。每个事件由若干字段行组成，字段名与值之间用冒号分隔：data: 承载负载，event: 指定事件名，id: 给事件编号，retry: 建议重连间隔。以冒号开头的行是注释，常被用作心跳。

浏览器端的 EventSource 会自动解析这些字段、自动重连，并在重连时带上 Last-Event-ID 请求头。这套语义是 SSE 相对“裸 chunked 加自定义分隔符”的最大优势：断线续传的骨架已经由规范定义好了，不必自己发明。

但 SSE 只规定了服务端到客户端的单向推送，没有规定请求体，也没有规定客户端如何发送消息。它的定位是“服务器向浏览器广播”，而不是“双向会话”。把它用在需要提交长提示词的场景，就必须绕道，这一点在下一节展开。

事件格式与几个易错点

第一，data: 的值要去掉冒号后的一个前导空格，但不应去掉全部空白，否则正文开头的空格会丢失。第二，一个事件可以有多行 data:，客户端要用换行把它们拼起来。第三，空行才是事件结束标志，只收到半行时不能派发。第四，id: 的值不能包含空字符，且它会成为下一次重连的 Last-Event-ID。

第五，注释心跳不能省。中间层和负载均衡常常按“多久没收到字节”判断连接是否存活，模型在长提示词上预填充时可能十几秒不产出 token，此时定期发送一行冒号注释，可以避免连接被误杀。

实践中的常见组合是：传输层用 chunked，应用层用 SSE 的事件格式，但客户端不用 EventSource，而是用 fetch 读取响应流后自行解析。这样既保留了事件格式的清晰边界与编号语义，又摆脱了 GET 与请求头的限制。

三、接口形态：别被 EventSource 绑住

流式补全的提示词动辄上千字，必然要放在请求体里。这直接撞上 EventSource 的三个限制：只支持 GET，不能设置请求头，不能携带请求体。把提示词塞进查询串不仅长度受限，还会进入代理与浏览器历史日志，既难看又不安全。

EventSource 的自动重连是双刃剑

EventSource 收到连接关闭后会自动重连，并带上最后收到的事件编号。对新闻推送这类“重放即可”的场景，这很方便；但对生成类接口，自动重连意味着服务端可能被重复触发一次完整生成。若客户端又没有去重，用户会看到两段内容交错拼接。因此即使使用 EventSource，服务端也必须把“重连”与“重新生成”区分开，这一点在第七节详述。

四、增量解析：从字节流到 token

流式链路里最容易出 bug 的一层，是把“网络到达的一段字节”误当成“一个完整的业务消息”。真实情况下，切分发生在三个层次，且彼此不对齐。

三层切分

第一层是 TCP 分段，大小由 MSS、拥塞窗口和发送缓冲区决定，完全不可控。第二层是 HTTP chunk，服务端每次 flush 形成一个块，但中间件可能合并，也可能再拆。第三层是应用层事件，由空行分隔，一个事件可能跨两个 chunk，一个 chunk 也可能包含三个事件。

正确的做法是只认应用层边界：字节追加进缓冲区，找到分隔符就消费一个，剩下的留着。上层拿到的永远是完整事件，而不是“碰巧一起到达的字节”。

UTF-8 边界与行边界

中文在 UTF-8 里占三个字节。一个 chunk 很可能在第三个字节前被截断，若直接对每块调用 decode()，就会得到替换字符，表现为输出里随机出现问号或方块。Python 的 codecs.getincrementaldecoder 与 JavaScript 的 TextDecoder 都提供了保留半个字符的能力，这是解析流式中文的必备开关。

行边界同样要小心。SSE 允许 \r\n、\n、\r 三种换行，简洁起见多数实现只处理 \n\n，但若上游或代理改写了换行，解析就会一直等不到分隔符。稳妥的做法是先统一换行，再按空行切分。

五、首 token 延迟与吞吐指标

流式接口的性能不能只看“总耗时”。一条请求从发出到结束，至少可以拆成四段可观测的时间，每一段变慢的原因和优化手段都不同。

四个指标

首 token 延迟（Time To First Token，TTFT）指从请求发出到第一个增量到达的时间。它包含排队、鉴权、提示词预填充、首 token 采样与网络往返，是用户感知最强的一个数，也是流式改造最该盯住的数。

生成速率通常用每秒 token 数表示，更细的观察是 token 间隔（Inter-Token Latency，ITL）的分布。平均值会掩盖卡顿：如果平均间隔是 40 毫秒，但每十几个 token 就出现一次 500 毫秒的停顿，阅读体验依然很差，因此要看 p95 而不只是均值。

端到端时长是从请求发出到收到结束标记的时间，它约等于首 token 延迟加上全部 token 的生成时间，再加上尾部传输。这个数决定了用户需要占用连接多久。

有效吞吐是单位时间内系统实际交付的 token 总量，通常按并发连接汇总。它与单请求速度存在取舍：把更多请求塞进同一张卡，单请求的 ITL 会变长，但整体吞吐可能上升。流式场景下用户对 ITL 敏感，因此不能只按总吞吐做调度。

在哪里打点

客户端与服务端都要打点，但含义不同。客户端记录的 TTFT 包含 DNS、连接建立、代理转发与浏览器调度，是用户真实感受到的值；服务端记录的则从收到请求开始，能区分“排队等资源”和“模型算得慢”。两者相减，差值就是网络与中间层的开销，这个差值如果突然变大，通常意味着代理开始缓冲了。

计时要用单调时钟，并把每个增量的到达时刻都记下来，事后才能算出间隔的分位数。需要强调的是，token 数与字符数并不等价。中文在不同分词器下，一个 token 可能对应一个或两个汉字，前端按字符渲染、后端按 token 计费与限速，做容量规划时必须统一口径，否则估算会偏差很大。本文出现的所有速率与延迟数字都只是示意值，用于说明量级关系，不代表任何具体模型或服务的实测结果。

六、服务端：生成与写出解耦

最直接的实现是在生成循环里直接写 socket：算出一个 token 就 yield 一次。小流量下这样没问题，并发一上来就会暴露两个问题。

第一，生成与写出互相拖累。写操作可能因为客户端接收慢、内核缓冲区满而阻塞，生成循环随之停住，本该用来算下一个 token 的时间被浪费。第二，无法插入与生成无关的字节，比如心跳、进度事件、取消确认，因为循环的节奏完全由模型决定。

用有界队列连接两个任务

解耦的办法很朴素：生成任务只负责产出入队，写出任务只负责出队并发送。两者通过一个有界队列连接。队列有界是关键，它让“消费慢”这件事能够反向传递，而不是被无限内存吞掉。

解耦带来的三个新问题

其一，内存。队列里堆的是尚未发出的文本，容量乘以并发数就是最坏情况下的额外内存。其二，多一次入队出队会带来微小的调度开销。其三，也是最容易被忽略的：取消的传播。客户端断开后，写出任务会收到异常，但生成任务还在跑，如果不通过 cancel 事件或任务取消把它停掉，服务端会继续消耗算力生成没人要的内容，成本照付。

因此，解耦不是把两个循环拆开就完事，还必须约定三件事：队列满时是等、是丢、还是断开；客户端消失时如何通知生成侧；结束事件是否一定要发出。这三条约定，就是下一节要讨论的背压策略。

七、背压与慢消费者

背压这个词听起来抽象，落到流式输出上其实很具体：生成端产出的速度超过了链路能运走的速度，多出来的部分必须有地方放，或者有办法让对方慢下来。

背压从哪一层来

最底层是 TCP 接收窗口。客户端读得慢，窗口缩小，服务端内核发送缓冲区填满，write 开始阻塞或返回部分写入。往上一层是代理：nginx 默认会缓冲上游响应，客户端慢只会让 nginx 的缓冲区变满，上游短时间内毫无察觉。再往上是浏览器：事件循环被长任务占住时，即使数据已经到了，回调也无法执行，ReadableStream 的队列随之堆积。最后是应用自身：一边流式接收一边同步写日志、做全文持久化，磁盘抖动也会把消费速度拖下来。

这四层里，只有最上面一层能直接控制，所以判断“客户端慢”，不能只看写失败次数，还要看队列深度与写等待时间。

三种应对：阻塞、合并、断开

阻塞是最符合直觉的做法，也是有界队列的默认行为：队列满就让生产者等。它保证不丢内容，代价是生成停顿，GPU 空转，整体吞吐下降。对单请求而言这没问题，对共享算力的服务就是浪费，因此需要给等待设上限。

合并是流式场景特有的手段。文本不能像视频帧那样丢弃，但可以把多个待发 token 合成一个事件再发。内容一字不少，只是粒度变粗，客户端看到的是“一次蹦出好几个字”。在客户端只是渲染跟不上时，合并比阻塞更划算，因为它减少了事件数量与渲染次数。

断开是最后手段。给写操作设一个总超时，比如连续若干秒无法写出一个事件，就认定该消费者已经失联或不可服务，主动关闭连接并停止生成。判定依据应当是“写不动”，而不是“总时长超限”，否则正常的慢速长文生成会被误杀。

慢消费者要能被看见

无论采用哪种策略，都要把队列深度、单次写等待时长、因超时断开的连接数暴露为指标。一个实用的告警规则是：队列深度的 p95 持续接近容量上限。这说明系统长期处于背压状态，要么扩容，要么调小单请求的最大输出长度，要么在入口处限流。若只看平均延迟，这种慢性拥塞很容易被掩盖。

八、断线重连与续传

移动网络切换、笔记本合盖、代理空闲超时，都会让一条正在传输的流突然断掉。此时用户已经读了一半内容，最糟的体验是刷新后从零开始，既浪费时间又重复计费。

先分清三种语义

第一种是重放：客户端重连，服务端从头再发一遍。实现最简单，但用户会看到内容跳回开头，且如果服务端重新生成，两次结果可能不一致。

第二种是续传：客户端告诉服务端“我已经收到第 N 个事件”，服务端从 N+1 继续发。这要求服务端在生成时保留一份近期输出，并能在客户端回来时找到对应会话。

第三种是重新生成：把已收到的文本作为上下文拼进新提示词，让模型接着写。它不需要服务端保存状态，但结果会漂移，措辞与前面不连贯，费用也更高，只适合对连续性要求不高的场景。

多数产品应当选第二种，第一种可作为降级，第三种只在无法保存会话时使用。

用事件编号做断点

SSE 的 id: 字段天生适合做断点。服务端为每个增量编号，客户端记录最后成功渲染的编号；重连时把编号放在 Last-Event-ID 请求头里（用 EventSource 时浏览器自动带，用 fetch 时要自己加）。服务端收到后，若会话仍在保留窗口内，就把缓冲区里编号更大的事件补发；若会话已过期，则回一个明确的“无法续传”事件，让客户端决定是重放还是提示用户。

保留窗口是成本与体验的平衡点。窗口太长，长文并发时内存吃不消；窗口太短，用户在地铁里断网一分钟就续不上。一个可行的做法是只保留最近若干秒或最近若干千字符的输出，超出部分宁可让客户端重放。

幂等键与去重

重连请求必须带幂等键，服务端据此判断“这是同一个生成任务的续传”还是“用户又点了一次”。否则用户手抖点两下，就会得到两条并行生成，账单翻倍。

客户端也要去重。续传时服务端可能从略早的位置补发，重复的事件会使用户看到重复句子。按事件编号做一次“小于等于已渲染编号就跳过”的判断，成本很低，却能消掉绝大多数重复。结束事件同样要有编号并参与去重，否则一次重连可能触发两次“完成”回调，把统计和后续流程弄乱。

九、前端：逐步渲染与中断取消

服务端把字发出来只是第一步，用户看到的是浏览器渲染的结果。这一层做不好，前面所有的延迟优化都会被抵消。

不要在每个 token 上重渲染

一个中文字大约对应一到两个 token，若每来一个 token 就更新一次状态，一秒几十次重渲染足以让低端设备掉帧。常见的做法是把增量先累积到缓冲区，用 requestAnimationFrame 或一个短定时器合并提交，大约每帧或每几十毫秒写一次 DOM。这样既保持了“正在打字”的观感，又把渲染次数降到可接受的范围。节流的粒度要与阅读速度匹配：太快没有意义，太慢会显得卡顿。

增量 Markdown 的代价

如果输出是 Markdown，整篇重新解析的代价随文本长度增长，长回答会越写越慢，形成明显的尾段卡顿。可行的优化是分块渲染：以空行为界把文本切成块，已完成的块缓存渲染结果，只重新解析最后一块。这样每次解析的规模基本恒定。

另一个坑是未闭合语法。流到一半的代码围栏、加粗标记、表格分隔行，单独解析会得到错乱的结构。要么在解析前补齐闭合符号，要么把尾块当作纯文本显示，等下一个边界到达再正式渲染。

取消要一路传到模型

用户点“停止”时，前端应调用 AbortController.abort() 中断 fetch，同时请求服务端取消对应任务。只做前者，服务端仍会继续生成，费用照付；只做后者，浏览器还在等一个不会再有数据的连接。

取消之后不要清空已显示的内容，那是用户已经读到的成果，应当保留并标记为“已停止”。组件卸载时也要清理定时器与 reader，否则回调会写入已卸载的组件，轻则报警告，重则内存泄漏。

十、流开始后的错误、成本与观测

状态码已经发不出去

鉴权失败、参数错误、额度不足，这些都应该在写出响应头之前判断，返回正常的 4xx 或 5xx，客户端可以按普通请求处理。一旦第一个字节发出，状态码就锁死为 200，后续任何问题都只能以带内事件表达。

推荐约定一个独立的事件类型承载错误，并在其后紧跟一个结束事件说明原因。结束原因至少要区分正常停止、达到长度上限、上游异常、客户端取消四种。客户端据此决定是保留部分结果、提示重试，还是自动续传。切忌用“连接关闭”当作成功信号，那会把网络故障误判为完成。

断开不等于不计费

多数按 token 计费的服务，只要 token 已经生成就计入用量，客户端提前断开并不会让这部分免费。因此取消必须尽快传播到生成循环，最大输出长度也要有上限，避免一个跑飞的请求把额度耗光。

观测要覆盖整条链路

最少要记录：请求标识、首 token 时间、总时长、输出 token 数、结束原因、是否发生重连。把这些按阶段打上标记，才能在故障时判断问题出在排队、生成、代理还是客户端。首 token 时间的 p95 比均值更有诊断价值，因为它直接对应“用户觉得卡”的那部分请求。

最后是内容安全。流式日志很容易把完整提示词与输出写进磁盘，涉及隐私时应默认脱敏，或只保留长度与哈希，不要为排查方便而全量留存。

小结

流式输出的本质，是把一次长事务拆成可观察、可中断、可续传的字节序列。协议层用 chunked 解决长度未知，用 SSE 约定事件边界；解析层只认应用层分隔符，并始终保留跨块的解码与缓冲状态；指标层盯住首 token 延迟与间隔分布，而不只是总耗时。服务端把生成与写出用有界队列解耦，让背压可见、可传导、可断开；客户端合并渲染、逐块解析 Markdown，并把取消一路传到模型。最后别忘了代理缓冲这个隐形杀手，以及流开始之后只能靠带内事件表达的错误。把这些环节都补齐，流式才不只是“看起来快”，而是真正稳定可用。
