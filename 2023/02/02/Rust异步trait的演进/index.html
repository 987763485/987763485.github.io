Rust 异步 trait 的演进

本文属于《Rust 学习路线》第 34/68 篇
上一篇系列目录下一篇

在 Rust 里写异步代码，迟早会撞上一堵墙：想在一个 trait 里声明 async fn，编译器却告诉你这不允许。本文从这行报错出发，拆开 async fn 的语法糖、对象安全的约束、async-trait 宏的展开结果，再一路讲到 GAT 与 RPITIT 在当时的进展。读完之后，你应该能判断某个抽象该用宏、该手写装箱、还是干脆换成枚举，也能明白为什么这个问题拖了这么久还没有定论。

要理解报错，得先看清 async fn 到底是什么。它并不是一种新的函数种类，而是编译器做的语法糖：一个返回 Option<String> 的异步函数，会被展开成“返回某个匿名类型”的普通函数，那个匿名类型实现了 Future<Output = Option<String>>。这个类型是编译器生成的状态机，把局部变量和每个 .await 的中间状态都塞进一个枚举，由 poll 一步步推进。换句话说，异步函数的返回值是一个结构体，只是它的名字我们写不出来。

问题就出在“写不出来”。在普通函数里，fn load() -> impl Future<Output = String> 是允许的，impl Trait 在返回位置早在 1.26 就已稳定，调用方不需要知道具体类型，单态化时编译器自己清楚。但 trait 定义是一份契约，它要能被不同的实现者填充，还要能被 dyn 使用。impl Trait 出现在 trait 方法的返回位置，意味着每个实现返回的类型都可能不同，而这恰恰是 dyn 无法接受的：虚表里的函数指针必须有一个固定的返回布局，调用方才能预留栈空间、才知道该按什么尺寸读返回值。

于是就有了那个两难：想要抽象，就得让返回类型可命名；想要零成本，就得让返回类型保持匿名以便内联。稳定版 Rust 在这两点之间没有桥，只能二选一，或者借助宏把其中一半工作搬到编译期之外。

有人会问：既然装箱能解决问题，为什么编译器不干脆在 trait 里自动装箱？从语言设计的取向看，这样做会破坏一致性。async fn 在普通函数和固有方法里是零成本的，调用方拿到的是一个可以内联的状态机；如果同一个关键字写进 trait 就悄悄变成一次堆分配，那么“这段代码有没有分配”就不再能从语法上看出来。Rust 一贯的做法是把分配摆在明面上，Box::new、Vec::new、Arc::clone 都是如此。这也是官方宁愿等 RPITIT 成熟、也不愿先给一个“能用但隐式分配”的过渡版本的原因之一。

async-trait 做了什么

社区最早、也是最广为接受的答案是 async-trait 这个 crate。它由 David Tolnay 在 async/await 落地前后发布，思路很直接：既然 trait 里不能写 async fn，那就让属性宏在编译前把 async fn 改写成“返回装箱 future 的普通函数”。用法几乎是零成本的迁移：

实现侧同样被改写：原来的函数体被塞进一个 async move 块，外面套上 Box::pin。于是每个方法都变成“接收借用、返回一个装箱的、带 Send 约束的 trait 对象”。

这里有几个值得注意的细节。第一，方法上凭空多出一个 'async_trait 生命周期，所有入参借用和 Self 都被要求“活得比这个 future 更久”，Self: 'async_trait 这一条尤其关键，它保证 future 里捕获的 self 引用不会悬空。第二，Send 是默认加上的，因为绝大多数异步运行时都要求 future 能跨线程搬运；如果确定只在单线程上跑，可以写 #[async_trait(?Send)]，让展开结果去掉 Send，这时装箱的是 dyn Future 而不是 dyn Future + Send。第三，也是它能成为事实标准的原因：改写后的方法没有泛型参数，返回类型是具体可命名的 trait 对象，所以 trait 重新变得对象安全，Box<dyn ConfigSource> 又能用了。

代价同样明确。每次调用都会发生一次堆分配，因为要 Box::pin 把匿名状态机搬上堆；每次 poll 都要经过虚表间接调用，编译器无法把具体的 poll 内联进调用方。对于一次方法调用背后就是一次数据库查询或 HTTP 请求的场景，这点开销完全可以忽略；但如果是每帧、每个元素都要调用的细粒度接口，比如一个异步的迭代器或序列化器，装箱就会成为实实在在的瓶颈。此外，宏接管了方法体，跳转定义和错误信息都会变差，编译期也多了一次过程宏展开。

宏能做到与做不到的事

理解宏的边界，比记住它的用法更有价值。#[async_trait] 只做一件事：把 async fn 改写成返回装箱 future 的普通函数。它不会、也无法改变语义层面的约束，所以有几件事不在它的能力范围内。

其一，它不能让 Send 变成可选事实。宏默认加上 Send，如果你的实现里跨越 .await 持有了 Rc 或裸指针，报错会出现在宏展开的位置，错误信息指向一段你从未写过的代码，定位成本明显上升。这类问题的根源是实现本身不满足跨线程要求，宏只是把矛盾提前暴露出来。

其二，它不能让含泛型方法的 trait 变成对象安全的。改写只处理返回类型，方法上的泛型参数仍然存在，dyn 依然不可用。想同时拥有泛型方法与动态分发，只能把泛型方法拆到另一个 trait 里，或者改用枚举。

其三，它不处理“返回 impl Future 的普通方法”。宏只识别 async fn 语法，手写的 fn foo(&self) -> impl Future 会被原样保留，然后在稳定版上触发另一个报错。同一个 trait 里混用两种风格时，这一点容易踩坑。

其四，属性宏之间有顺序问题。同一个 trait 叠加多个会改写方法体的宏时，展开顺序会影响最终结果，必要时把 #[async_trait] 放在最内层，让它在其他宏处理完之后再改写方法体，避免被外层宏提前消费掉。

这段代码的签名在当前稳定版上完全合法，不需要任何 feature（HttpClient 与 Error 是示意类型，换成项目里的真实类型即可）。它把三件事同时摆到了明面上。

第一是生命周期。fetch 的返回值借用 self 与 key，所以返回类型必须带上一个不小于这两者的生命周期参数，+ 'a 就是为此而写。省掉它会编译失败，因为 Box<dyn Trait> 的默认生命周期约束是 'static，而这里捕获的引用显然不是静态的。为什么只用一个 'a 而不是给 self 和 key 各配一个？因为一个 trait 对象只能带一个生命周期上限，而 future 同时捕获了两者，取交集后最省事的写法就是让调用方保证两者都覆盖同一个区间。代价是约束偶尔偏严：传一个临时字符串进去，它的生命周期会被拉到与 &self 一样长，个别调用点需要先 let 绑定一下。

第二是 Send。它决定了这个 future 能不能被丢进工作窃取队列，从线程 A 创建、线程 B 轮询。tokio 的多线程调度器、async-std 的默认执行器都要求任务满足 Send + 'static，所以只要接口可能被 spawn，就必须在返回类型里写明 + Send。反过来，如果这个 trait 只在当前线程上用 block_on 驱动，去掉 Send 会放宽实现方的要求，某些内部持有 Rc 或 RefCell 的实现才能通过编译，这类别名通常叫 LocalBoxFuture。

第三是装箱点。Box::pin 写在实现里而不是调用处，意味着分配发生在每次方法调用时。手写方案的性能与 async-trait 完全一致，二者是同一个东西的两种写法。手写的好处是签名显式、可以按需追加约束（例如再要求 + Sync）、不依赖过程宏、对 IDE 与错误信息更友好；坏处是每个方法都要重复一遍生命周期样板，改签名时两处必须同步，而且很容易漏掉 + 'a 或 Self: 'a 这类细节。

如果既想避免堆分配，又不想引入泛型参数，还有一条中间路线：把可能的几种 future 形状包进一个枚举，手动实现 Future 并在 poll 里按分支转发。生态里常见的 Either 类型就是这种思路的产物，两个分支分别持有两种 future，poll 时 match 一下即可。它适合“分支数量有限、且确实在意每次分配”的场景，比如中间件返回值只有“继续”和“短路”两种；但不适合作为通用抽象，因为每增加一种形状就要改枚举、补一个转发分支，维护成本会随组合爆炸而上升。

GAT：先解决生命周期，再谈抽象

看起来问题解决了：返回类型可命名、不需要装箱、静态分发可以内联。但真正落地时会撞上第二个障碍：实现方要怎么填这个关联类型？理想写法是 type Fetch<'a> = impl Future<Output = Option<String>> + 'a;，也就是在关联类型的位置使用 impl Trait。这个能力（type alias impl trait，TAIT）当时仍在不稳定阶段，稳定版写不了。于是实现方只剩两条路：要么老实装箱，type Fetch<'a> = Pin<Box<dyn Future<Output = Option<String>> + Send + 'a>>;，绕一圈又回到堆分配；要么手写状态机结构体，把 async 块展开成自己实现的 Future，工作量和出错概率都很高。

所以 GAT 在这一议题里的定位需要说清楚：它提供了“关联类型可以带生命周期参数”这块地基，让异步 trait 的抽象在类型层面有了正确的形状，GAT 的稳定公告里也把异步 trait 列为重要用例；但它本身并不等于“trait 里可以写 async fn”，也不解决对象安全，更不解决实现的易用性。它是必要条件，不是充分条件。

GAT 自身也有边界：带 GAT 的 trait 同样不是对象安全的，所以它只能服务静态分发；每个实现都要重复 where Self: 'a 这类约束，写多了相当啰嗦。它把“类型形状”这一层补齐了，却没有补齐“实现侧不必手写类型”这一层。

但 nightly 上的状态离“可用”还有距离，至少有三个明确的问题。其一，不能用于 dyn。含 async 方法的 trait 在 nightly 上依然不是对象安全的，写 Box<dyn ConfigSource> 会直接报错。其二，Send 约束无法表达。设想一个泛型函数 async fn warm_up<S: ConfigSource>(s: &S)，它内部调用 s.fetch(k).await，得到的 future 是不是 Send？编译器答不上来，因为返回类型是匿名的，调用方也没法在 where 子句里写“这个方法的返回类型实现了 Send”。而 tokio 的 spawn 恰恰要求 Send。这个矛盾在当时的讨论中没有定论：自动加 Send 会把合法的单线程实现排除在外，不加又让库作者无法写出通用的跨线程封装。其三，trait 里的默认实现、泛型方法、以及与 impl Trait 参数混用时的边界规则，都还有细节在调整。

对象安全与分发的取舍

为什么 dyn 这么重要，值得为它牺牲零成本？因为对象安全（object safety）的规则决定了 trait 能不能作为“运行时接口”使用，而很多架构恰恰需要运行时替换实现。规则本身不复杂：方法不能返回 Self、不能带泛型参数、不能返回 impl Trait、不能使用 GAT。这些限制都指向同一件事：虚表需要一张固定布局的函数指针表，调用方在编译期就要知道每个槽位的签名和返回值的尺寸。

在异步场景里，这条约束与“零成本抽象”的诉求正面冲突，于是产生了四种典型做法，各自的取舍可以并排比较：

方案 每次调用开销 能否 dyn 实现侧样板 典型场景
async-trait 宏 一次堆分配 + 虚调用 poll 可以 几乎为零 业务层接口、存储与客户端抽象
手写装箱 future 同上 可以 每个方法一段签名 不想引入过程宏、需要自定义约束
GAT 关联类型 视实现而定，可为零 不可以 需要可命名的 future 类型 泛型库内部、性能敏感的静态分发
枚举分发 一次 match 跳转 不需要 新增实现要改枚举 实现集合封闭、热路径

如果实现集合在编译期就已知，枚举往往是被低估的选项。它把动态选择压缩成一次分支跳转，没有堆分配，也没有虚表，而且 match 的穷尽性检查能在新增变体时提醒你补全逻辑：

代价是封闭性：枚举一旦发布，别的 crate 就无法为它增加变体，所有转发分支也要手写。社区有过程宏能根据枚举自动生成这层转发代码，省掉样板，但不改变“集合封闭”这个本质。反过来，如果扩展性优先，比如允许第三方注册自己的存储后端，那就只能用 Box<dyn Trait>，装箱开销是必须付的入场费。

四个问题帮你选型

面对具体接口时，可以按顺序问四个问题，多数情况下答案会自己浮出来。

第一个问题：实现集合在编译期是否封闭？如果只有内存与 Redis 两种缓存后端，且短期内不会增加，枚举就是最省事的答案；如果这是一个给下游用的扩展点，答案必然是多态。

第二个问题：是否需要跨 crate 扩展？枚举无法被外部 crate 增加变体，trait 可以。这是封闭与开放的分水岭，比性能更值得优先考虑，因为架构改动的成本远高于一次函数调用。

第三个问题：单次调用的工作量有多大？一次远程请求、一次磁盘读写、一次复杂的数据库事务，装箱的那点开销占比极低，用 async-trait 换来的可读性完全值得。反之，如果这是一个在循环里对每个元素调用的解析器或编码器，静态分发带来的内联收益会很明显，此时应当用泛型加关联类型，或者干脆把接口设计成批量方法。

第四个问题：是否需要把实现放进集合、字段或跨语言边界？Vec<Box<dyn Trait>>、结构体里的 Arc<dyn Trait>、以及 FFI 回调，都要求类型擦除，装箱不可避免。这类需求往往在项目后期才出现，所以在设计初期就给接口留一个“可装箱”的版本是务实的做法。

还有一个容易被忽略的成本项：泛型单态化会让编译时间和二进制体积随实例数量增长，而 dyn 把这部分成本挪到了运行时。枚举介于两者之间，match 分支会随变体数量线性增长，但不会为每个调用点复制一份代码。三个方案在“编译期成本”和“运行期成本”之间的位置不同，选型时最好一并考虑，而不是只看微基准。

生态中的绕行模式：tower 与 axum

框架作者比业务开发者更早撞上这堵墙，他们的解法往往比“加个宏”更有信息量。最有代表性的是 tower 的 Service trait，它的形状刻意避开了 async fn：

这个设计比 async fn 更底层，拆开看有三层考虑。第一，把“准备好”和“处理”分成两个方法，中间件才能在过载时向上游施加背压，这是纯 async fn 表达不了的语义。第二，Future 作为关联类型，由实现方填充，抽象本身没有装箱，泛型组合时依然是静态分发。第三，关联类型可以在写 dyn 时被显式指定，所以 Service 仍然是对象安全的，中间件栈可以用 trait 对象拼起来。

代价转嫁给了实现者：在稳定版上你写不出 async 块的类型名，所以实现 Service 时通常把 Future 填成 BoxFuture 或 Either。写 dyn Service 时更啰嗦，因为所有关联类型都要写出来，形如 Box<dyn Service<Request = Req, Response = Res, Error = E, Future = BoxFuture<'static, Result<Res, E>>>>。tower 生态里那些 BoxService、BoxCloneService、Either 之类的类型，本质上都是“用一个具体类型把关联类型钉死”，让调用方少写一点。这套设计在异步语法稳定之前就已成型，所以它是被约束逼出来的，而非事后补救。

axum 走的是另一条路。它的 Handler trait 只有一个关联类型 Future，由宏为“签名为 async 的函数”批量生成实现，把用户写的异步函数包装成统一的路由元素。也就是说，类型擦除发生在框架内部，用户侧看到的仍然是普通的 async fn handler(...)。在需要多个实现的扩展点上，不少框架干脆直接用 #[async_trait]，比如 tonic 的代码生成器就会为 service trait 生成带该属性的定义，让使用者实现时不必关心装箱。

把这几个案例抽出来，可以看到三条反复出现的模式：

  • 用户面 API 尽量保持 async fn 的原样，让写代码的人没有负担；
  • 抽象面（需要多实现、需要放进集合、需要跨 crate 扩展）用关联类型或装箱，把成本集中到一个明确的位置；
  • 需要背压、流式或“先检查再调用”的语义时，回到手写的 poll 形态，而不是硬套 async fn。

这三条并不互斥，同一个框架里往往同时存在。理解了它们，读框架源码时就不会被“为什么这里不写成 async”困扰。

现状盘点与未来方向

把本文写作时的状态压缩成一份清单，大致是这样：

  • GAT 自 1.65 起稳定，可以表达“关联类型带生命周期”，但不解决实现侧的命名问题，也不解决对象安全；
  • trait 中的 async fn 与 RPITIT 在 nightly 可用，支持静态分发，不支持 dyn，Send 约束无法在泛型代码中表达；
  • async-trait 是事实标准，生产环境广泛使用，展开结果是装箱 future；
  • 手写 Pin<Box<dyn Future + Send + 'a>> 与宏展开等价，适合不想引入过程宏或需要自定义约束的场合；
  • 含异步方法的 trait 在稳定版上依然不是对象安全的，想动态分发就必须装箱。

据此可以给出几条偏保守的工程建议。抽象层默认用 async-trait，除非有明确的性能证据表明装箱是瓶颈；只有在这种情况下，才考虑把接口改成泛型加关联类型，或者退回枚举。需要跨线程 spawn 的接口，一开始就在返回类型里写清 Send，不要等到运行时报错才补。公开 crate 的 API 要谨慎暴露装箱细节，因为一旦语言侧稳定，宏展开的结果会与原生实现不同，Box<dyn Future> 这样的类型出现在公开签名里会增加迁移成本。反过来，如果只是内部使用，选择哪种写法的影响有限，可读性和团队熟悉度更重要。

至于未来，能确定的是方向，不能确定的是时间表与语法。需要解决的问题摆在明面上：dyn 场景如何支持（是否为装箱单独提供一种写法）、Send 约束如何由调用方声明、trait 中 impl Trait 的捕获规则如何与普通函数统一。这几项在社区讨论中都有多种备选方案，彼此还会互相影响，本文不预测具体版本，也不建议把生产代码押在 nightly 特性上。比较现实的预期是渐进迁移：语言侧先支持静态分发，动态分发继续靠装箱，async-trait 因为最低支持版本（MSRV）和生态惯性的原因，还会在很长一段时间里与原生写法并存。

如果想自己跟进进展，有三个比较可靠的入口：nightly 的版本说明与 unstable book 中对应的 feature 页面，官方博客的版本公告，以及语言团队公开的设计讨论。阅读 nightly 示例时要留意 feature gate 与所属版本，这类示例的签名在相邻的 nightly 之间发生变化的概率不低，直接抄进生产代码很容易在下一次工具链更新时崩掉。更稳妥的做法是先在独立分支上验证，确认展开后的类型与 Send 行为符合预期，再决定是否替换现有实现。

小结

trait 中的 async fn 在本文写作时仍未稳定，稳定版只有两条路：要么装箱把返回类型变成可命名的 trait 对象，要么改用枚举做静态分发。async-trait 与手写 Pin<Box<dyn Future + Send + 'a>> 本质是同一件事，前者省去样板，后者把生命周期与 Send 约束摆在明面上。GAT 在 1.65 补上了关联类型的生命周期形状，RPITIT 在 nightly 上让静态分发自然起来，但 dyn 支持与 Send 表达仍是未解的问题。选型的核心不在于微基准上的几个纳秒，而在于实现集合是否封闭、是否需要跨 crate 扩展。实践建议是：业务抽象用 async-trait，热路径与封闭集合用枚举或泛型，公开 API 谨慎暴露装箱细节，并且始终以稳定特性作为交付基线。如果你正在维护一个被多个 crate 依赖的异步库，不妨把抽象收敛到少数几个接口上，让装箱成本集中在可度量的位置，而不是散落在每一条调用链里。
