API 安全设计与测试

本文面向正在设计或维护对外、对内接口的后端与测试同学，讨论 API 安全在设计与测试两个阶段分别要落实哪些控制。读完你会得到一份威胁类型清单、一组设计期的结构性约束，以及一套以授权为核心的测试方法。微服务之间的认证授权细节另见相关篇目，威胁建模本身的方法论也不在这里重复，本文只把镜头对准单个 API 的安全设计与其验证。

先把风险摆清楚

API 的攻击面和传统网页页面不一样。它没有浏览器和表单的天然约束，调用方可以是任何一个脚本或程序，返回的是结构化数据，一旦越权，被批量读取、批量篡改的代价会被放大。社区里对这一类失效模式有公开的整理，OWASP 的 API 安全相关工作把常见风险归成若干类别，本文只借用这些类别的名称与防御含义，用来搭一个讨论框架，不复述任何攻击步骤，也不给出条目编号。

从防御视角，值得优先关注的风险大致是这几类。最典型的是对象级授权缺陷：接口本身校验了调用者是谁，却没有校验这个调用者是否有权碰他正在请求的那条记录，只要把路径或查询里的标识符换成别人的，就可能读到不属于自己的资源。与之相邻的是功能级授权失效：普通角色可以调用本应只有管理员才能访问的端点，比如把某个删除或批量导出的接口当成自己的权限。批量赋值则是另一类问题：服务端把客户端提交的字段原样绑定到数据模型上，于是提交一个本不该由客户端决定的字段，比如把用户状态直接改成管理员，就被写进了库。限速缺失让接口可以被高频调用，用于猜测、爬取或拖垮依赖。敏感信息过度返回指响应体里夹带了前端并不需要、也不该被看到的字段。影子接口与僵尸接口指的是文档里早已声明下线、代码里却仍在运行的端点，它们不在评审视野内，却继续暴露着老逻辑。

下面这张表把风险和最常见的防御落点对齐，便于后文逐项展开。

风险类型 本质 主要防御落点
对象级授权缺陷 认了人，没认物 服务层做所有权校验
功能级授权失效 角色与端点权限错位 端点级权限声明
批量赋值 客户端字段被原样绑定 字段白名单与 DTO
限速缺失 无约束的高频调用 速率限制与配额
敏感信息过度返回 响应超出必要范围 序列化脱敏与字段裁剪
影子与僵尸接口 无人认领的存活端点 资产台账与下线流程

这些风险没有一个能靠”前端把按钮藏起来”解决。真正的控制要么落在设计阶段的代码结构里，要么落在运行期的策略里，最后都要能被测试验证。理解这一点，是后面所有内容的出发点。

设计阶段：把控制放进结构里

设计阶段的目标，是让越权、批量赋值这类问题在代码写出来之前就没有容身之处，而不是等上线后再用外部手段去挡。

认证方案的选择要匹配调用方。浏览器里的前端与第三方集成、服务与服务之间的调用，适合的令牌方式并不相同，本文不展开选型对比，只强调令牌生命周期必须被认真处理：签发要带上主体与用途，访问令牌保持较短有效期，刷新令牌可撤销，退出与权限变更能真正让旧令牌失效。一个常见的疏漏是令牌只负责证明身份，而把”这个人能不能碰这条数据”完全留给下游临时判断。

第一条硬规则是：授权必须在服务层做，而不是在前端或客户端做。前端能把危险按钮隐藏，却挡不住任何人直接构造请求。只要权限判断没有发生在真正执行操作的那一层，它就不算存在。

这里刻意让越权返回 404 而不是 403，是为了不把”这条记录存在但不属于你”这个信息泄露给调用者。所有权校验最好像上面这样，把用户标识直接并进查询条件，而不是先无条件取出来再用 if 比对——后者一旦漏写一个分支就是缺陷。

第二条硬规则针对批量赋值：不要用请求体去填充完整的持久化模型，而是为每个端点定义一个只包含合法字段的输入结构。

DTO 同时也是输出的裁剪工具。响应序列化时同样按白名单挑字段，让密码散列、内部标识、关联对象这些前端用不到的东西根本不进入返回值，这比先序列化再想办法删更安全。

输入要校验，也要规范化。校验的是类型、长度、取值范围与格式；规范化处理的是同一含义的不同写法，比如路径里的编码、大小写、多余空白。校验与授权判断看到的必须是同一份规范化之后的数据，否则攻击面就藏在”两处解析结果不一致”的缝隙里。

关于令牌生命周期还有两个容易被忽略的点。一是访问令牌要绑定用途与受众，避免一个为某个服务签发的令牌被拿去调用另一个服务；二是权限变更后旧令牌要能真正失效，较短的有效期要配合撤销或内省机制，被吊销的账号才会失去访问能力。错误响应也建议固定成一种结构：可对外的人类可读信息、稳定的错误码、仅用于排查的关联标识各归其位，堆栈与依赖细节只进服务端日志。

运行期控制：让策略持续生效

设计阶段把代码写对之后，运行期还要有一层即使代码有疏漏也能兜底的策略。这一层和网络层的微隔离、零信任的持续验证是不同的东西，它针对的是接口本身被滥用。

速率限制与配额是最直接的一道。限速关心单位时间内的请求次数，用来抑制高频猜测与抓取；配额关心一段周期内某个主体总共能用多少，用来给批量导出、发送短信这类有真实成本的操作设上限。两者都应当按调用主体和资源分别统计，而不是只按来源地址，因为同一地址背后可能是一个多租户的网关。下面的示意实现用令牌桶对每个用户单独限流，其中的阈值都是举例，需要按业务实测确定。

审计日志决定了事后能否还原真相。日志要记下谁、在什么时候、用什么身份、对哪个资源、做了什么、结果如何，尤其要把授权失败的尝试也记下来——它们往往是探测行为的第一信号。日志本身也是一份敏感数据，落库和送分析平台之前要脱敏：令牌、密码、身份证号这类字段不能原样写入，必要标识用不可逆或可授权的替代形式。密钥与令牌的签名材料要有明确的轮换周期和轮换流程，旧材料在被所有依赖方弃用之前不能过早下线，轮换动作本身要进审计，避免”谁改了、改坏了没有”无从追查。

运行期还要持续回答一个问题：现在到底暴露了哪些端点。影子接口来自新写却从未进入文档的路由，僵尸接口来自已声明下线却仍在服务的旧逻辑，它们共同的风险是不在评审与测试的视野里。稳妥做法是把框架实际注册的路由定期导出一份，和接口契约逐条比对：多出来的要么补进文档与测试，要么按下线流程真正摘掉；下线要有弃用标记、观察窗口和最终停用，而不是悄悄留着，清点结果也应进资产台账供安全与合规复盘。

测试方法：让授权缺陷无处可藏

前面这些控制是不是真的生效，只能靠测试证明。API 安全测试的重心不是找注入点，而是穷举权限组合，验证每一条”谁不该碰什么”的约束确实被拒绝。本文不重复威胁建模本身的做法，只讲如何把它的产出转成用例：建模给出的每一个风险，都应落成至少一条断言它被拦住的测试。

权限矩阵遍历是核心手法。把角色作为一行、端点或资源操作作为一列，格子填上预期结果（允许、拒绝、或按所有权而定），然后逐格验证。这张矩阵既是测试计划，也是评审材料。

角色 \ 操作 读自己的订单 读他人的订单 批量导出 改用户角色
普通用户 允许 拒绝（404） 拒绝 拒绝
管理员 允许 按策略 允许 允许
未登录 拒绝（401） 拒绝（401） 拒绝（401） 拒绝（401）

遍历的价值在于覆盖负例：越权、错角色、缺字段、批量赋值这些”应当失败”的用例，往往比正常流程更有检出率。测试账号应当自带多种角色与不同归属的数据，才能把所有权校验真正测出来。

契约测试保证实现不偏离接口约定，响应里多冒出来的字段、请求里被悄悄接受的字段，都会在契约层暴露。模糊测试在这里是防御手段：向参数喂入类型错误、边界值、异常编码，观察服务是否返回稳定的错误码、是否泄露堆栈或内部信息、是否把非法输入原样落库。它关心的是失败得是否干净，而不是去绕过任何防护。

敏感信息过度返回适合用契约断言来测：把实际响应的字段集合与契约声明的字段集合做差集，任何多出来的键都当作缺陷，疑似个人信息的字段尤其要盯。用例本身也要有结构，一条越权测试至少应包含数据准备、以低权限身份发起请求、断言状态码与响应内容三部分，并能在没有手工登录态的情况下自动取得所需令牌，否则很难长期稳定地进流水线运行。这些用例一旦写成就该作为每次变更的回归门禁，因为越权与批量赋值这类缺陷极易在重构时悄悄回来。

测试的边界与小结

安全测试的底线是授权与数据。任何用例都要有书面确认的测试范围、测试账号与数据准备方式，范围之外的端点一律不碰；生产环境不用于此类测试。运行环境要与生产隔离，优先使用只读副本或数据脱敏后的影子库，写操作只落在可丢弃的测试数据集上，读取也不针对真实用户数据。这条边界比测试技巧更重要。概括来说，API 安全的可控部分是把授权做进服务层、把字段收进白名单、把失败做成稳定错误、把调用限进配额，再用权限矩阵和流水线把这些约束一条条钉死验证。设计给出结构，运行期给出兜底，测试给出证据，三者缺一，所谓安全就只是承诺。
