LangChain 核心模块：Chain 与 Agent

本文属于《Agent 智能体开发》第 10/55 篇
上一篇系列目录下一篇

本文面向已经能调用大模型接口、准备把 LLM 放进业务系统的读者，按模块梳理 LangChain 在 2023 年 9 月这个时间点上的核心抽象：模型封装、提示模板、Chain、声明式管道、Memory、Tool、Agent，以及 Callback 与检索组件的位置。讨论重点不是某个类叫什么名字，而是每类抽象负责什么、不负责什么、边界划在哪里，最终落到一个工程决策上：什么时候用步骤固定的 Chain，什么时候才把控制权交给 Agent。文中示例代码是笔者自己写的一个最小 pipeline，用来自洽地讲清机制，不追求复现某个库版本的接口签名；涉及库内 API 的地方一律用文字描述流程。

模块化的起点：一次调用与一条链路

直接把模型接口调用写在业务代码里，是几乎所有 LLM 应用的第一版形态。它能跑，但会在四个方向上同时膨胀。

第一个方向是上下文。业务里很快出现”接着上一轮问”的需求，于是有人往同一个函数里塞历史；塞到第三轮超了窗口，又加截断；截断把关键约束切掉，再加一个”重要信息单独记一遍”的补丁。第二个方向是输入输出格式。模型返回自由文本，调用方却要一个日期、一个金额、一段 JSON，解析代码和模型的输出习惯互相追着改，换一家模型就全线失效。第三个方向是外部能力。查订单、算汇率、发工单，每一项都变成”先调接口、再拼进 prompt”的重复代码。第四个方向是可观测性。线上出问题时，没人说得清那次请求的 prompt 是什么、模型为什么这样回答、中间有没有真的调用过工具。

这四个方向恰好对应了下图的模块划分：

flowchart TD
    In[业务输入] --> P[提示模板]
    P --> M[模型封装]
    M --> O[输出解析]
    H[对话历史] --> P
    R[检索组件] --> P
    M --> A[Agent 决策]
    A --> T[工具执行]
    T --> A
    A --> O
    O --> Out[结构化结果]

这里的关键认知是：只有”提示模板 → 模型封装 → 输出解析”这一段是无条件的，其余节点都按需接入。历史、检索、工具、Agent 各自引入额外的状态与不确定性，而这两样正是可维护性的敌人。后文每介绍一个模块，都会顺带回答一个问题：引入它要多付什么代价。

另一个容易混淆的点是”库的定位”：LangChain 这一年是把上述环节粘合起来的通用件，两条语言线并行演进、迭代极快，文档站里的接口名过几周就可能不再是推荐写法，因此不要把具体类名当作长期资产来设计架构。真正稳定的是那套分层思路：把模型调用收敛成一个可替换的端点，把流程表达成有明确输入输出的节点，把状态存放位置显式化。

模型封装与提示模板：链路的两个端点

模型封装：把供应商差异收在接口后面

模型封装的职责边界很窄：输入一段文本（或一组消息）与若干采样参数，输出模型生成的文本，附带 token 用量、停止原因这类元信息。它不知道什么是会话，不知道什么是工具，也不负责把返回值变成对象。

接口有两种形态：补全式（completion）给一段前缀续写；消息式（chat）给一组带角色的消息，返回一条助手消息。业务代码到 2023 年下半年基本以消息式为主，因为多数供应商的能力集中在对话接口上，且消息式天然适合”角色约束加用户输入”这种结构。封装层的价值，就体现在把这些差异吃进去：

Protocol 的作用是：业务代码只依赖方法签名，不依赖具体供应商。写一个把请求转成 HTTP 调用的实现类，就接入了某家服务；写一个返回固定字符串的假实现，就有了测试用的桩——没有桩，链路的自动化测试既花钱又不可复现。

封装层还承担几件”脏活”：重试与退避、限流排队、超时控制、把不同模型的停止词与最大长度参数对齐。判断某段逻辑该不该放在这一层，标准是它与语义无关：重试、超时、鉴权与语义无关，放这里；”回答不完整就再问一次”与语义有关，那是上层 Chain 的事，不该藏在客户端里。

有几个坑值得点名。一是上下文长度：”窗口大小”如果不在封装层显式暴露，上层的截断策略就无从计算。二是采样参数语义漂移：温度、top-p 在不同供应商上的实际效果并不等价，换模型必须重跑评测集。三是 system 消息处理：有的实现会把系统提示合并进首条用户消息，这会影响依赖角色区分的模板设计。

提示模板：链路里唯一的指令入口

提示模板的职责是把”固定指令”与”可变数据”分开，让指令部分可以被审阅、被复用、被版本化，让数据部分有明确来源。最简单的形态就是一个带占位符的字符串：

raise KeyError 那一行看着像吹毛求疵，实际很关键：变量名打错时，如果渲染层宽容地把 {order_id} 原样留在提示里，模型会把它当成一个待填的空位，然后一本正经地编出订单号。宁可让流程在开发期炸掉。

再往上一点是消息式模板：为每个角色固定一段内容，各自带变量。它的额外好处是让”指令与数据的边界可见”——系统消息里只允许指令和约束，用户消息里只允许数据和请求。这条纪律是防提示注入的第一道防线，更完整的讨论属于应用安全范畴。

模板还承担一件不那么显眼的事：少样本示例（few-shot）的装配。把三五条例子拼在指令后面，是这一年里性价比最高的质量提升手段，正确做法是示例与真实输入走同一套渲染逻辑，否则格式不一致，模型会照着错误格式发挥；示例该选哪几条属于提示词管理的范畴，本篇不展开。

需要划清一条边界：模板节点只是”一个产生文本的纯函数”，不负责去数据库取变量。取数据是 Chain 的事，拼字符串才是模板的事，把两者混在一个大函数里是这个模块最常见的腐化方式。

Chain：把步骤连成确定的流程

Chain 是把前面这些端点串起来的骨架。它的定义可以朴素到一句话：一个有名字的函数，输入一个字典，输出一个字典。中间的每一步可能是模型调用、可能是纯代码、可能是外部接口，但对调用方而言只有一进一出。

输入与输出：以字典为契约

为什么用字典而不是位置参数？因为一个环节的输入往往是多来源的——历史、检索结果、用户输入、上一步产物，位置参数表达这种结构会迅速失控；字典让组合变得机械，上一步的输出键名就是下一步的输入键名；字典还天然可序列化，能整块进日志、进评测集、进回归测试的期望值。

组合：串行、并行与选择

串行之外还需要两种组合形态。

并行是”同一份输入分发给多个子链，结果合并”，典型场景是同时从三个数据源取素材再汇总，或让同一个问题走两条提示路径后择优。它把延迟压到最慢那条，代价是要处理键名冲突与”一条成功一条失败”的中间态。

选择是”按条件挑一条子链执行”。这里有一条纪律：条件判断优先用代码写，不要用模型写。”问价格走查库分支，否则走文档分支”这类判断，用关键词、意图分类或业务字段都比让模型自由裁量可控；让模型选分支，等于一开始就把不确定性引进了流程。

末端通常还有输出解析节点：把模型返回的文本变成结构化对象。它的职责是”尽力变成指定形状，变不了就明确报错”，而不是”猜一个默认值填上”。宽容的解析器是线上事故之母——缺失字段会一路传到业务层，最后以别的形态爆出来。

运行控制：预算、重试与部分失败

Chain 上线后要回答三个运维问题：每一步的延迟预算、重试放在哪一层、部分失败怎么降级。与语义无关的重试留在模型封装层，”格式不对所以重问一次”这类依赖解析结果的重试才属于 Chain 层：

声明式管道：把流程写成表达式

2023 年下半年出现了一类新写法，LangChain 里通常称为 LCEL（LangChain Expression Language）。它的动机不是减少代码行数，而是把”流程的描述”和”流程的执行”分开。需要注明的是，这套写法当时仍在快速演进，运算符形态与内建能力在几个版本间反复调整，本文只讨论它的设计动机。

命令式写法的问题在于，流程一旦是几行顺序执行的语句，框架就无法在中间插东西：要流式输出得在每个调用点手工加参数，要批量运行得自己写循环，要上报每步耗时得写一堆装饰器。声明式写法把这些环节对象化——提示模板、模型封装、解析器都是”既可调用、也可被描述”的对象，用管道运算符接成一条表达式后仍是同一个可调用对象，单次、流式、批量三种形态自动贯通；框架拿到完整的流程结构，也才谈得上统一的重试与分步可观测。

这个思路值得学，但要清醒：抽象层数增加后调试成本会上升，异常往往发生在表达式求值的深处，栈帧里全是框架内部代码，看不出业务链路的状态。

Memory：对话历史的几种存法

对话历史是最容易被随手实现、也最容易在三个月后变成事故源头的模块。所谓 Memory 抽象，本质上只回答两个问题：下一轮请求应该带上哪些历史，这些历史存在哪里。

四种存法与它们的代价

最直接的是全量携带：每一轮的输入与输出原样拼进上下文。实现代价最低、语义最完整，但 token 成本随轮次线性增长，迟早撞上窗口上限，而且注意力稀释会让”第三十轮时忘了第一条约束”成为常态。

第二种是滑动窗口：只保留最近 N 条消息。延迟与成本变得可预期，这是它唯一的优点；代价是早期信息静默丢失，用户第一轮说过的预算限制会直接消失。N 取多少看业务，问答型可以小，任务型必须大。

第三种是滚动摘要：窗口外的历史压缩成一段摘要，随新轮次更新。它在信息保留率与上下文长度之间取得平衡，但每次更新都要一次模型调用，且摘要倾向于保留叙述、丢掉精确数值与否定句。

第四种是向量检索：把历史切成片段建索引，按当前问题的相关性召回。它适合跨天、跨周的长周期助手，能”想起”很久以前的一句话；风险是召回质量决定一切，且必须与”最近几轮”混排，只靠相关性会把上一轮的指代对象丢掉。

实践中常见的是组合：最近两三轮全量，加上更早内容的滚动摘要，再把长期事实单独结构化存放。最后这一项值得强调——用户说过的硬约束、身份、偏好应该用结构化字段存。能被写成字段的信息，不该依赖语义检索去回忆。

写入时机与一致性

历史什么时候被写入，比存法本身更容易出错。默认策略应该是在链路执行结束时由统一入口写一次，而不是让每个节点自己追加：前者保证一轮对话原子写入，后者会出现”模型调了三次工具，历史里躺着三条中间产物”的脏数据。

三个边界情况要显式决定。失败的那次要不要写：坏输出照样写入，下一轮就会把错误当成既定事实，通常只写用户输入。重新生成怎么处理：历史必须回滚到重答之前，否则两个版本同时留在上下文里互相干扰。状态存在哪里：进程内字典在多实例部署下会命中不到同一个会话，必须外置到共享存储、以 session id 为键并设过期时间。还要留意工具返回的内容，它一旦进入历史就会在下一轮重新进入提示词。

Tool：把外部能力描述给模型

Tool 抽象的职责是把一个可执行能力包装成模型能够理解、也确实可执行的东西：一份给模型看的说明，加一个给程序执行的入口。两者必须同源于一份定义，否则文档里写参数是字符串、代码里要整数，模型照文档填就一定失败。

三个细节对应三条经验。说明文字是提示词，要写清什么时候该用、什么时候不该用——只写”查询订单状态”，模型会在用户只是抱怨物流慢时也去查一次。参数缺失或执行异常要返回文字而不是抛异常，调用方是模型，它需要一条读得懂的失败信息才能改弦更张，异常直接往上抛整轮对话就断了。返回内容必须截断，一个把整张表打印出来的工具能一口吃掉全部上下文预算。

调用方式的两种形态

工具调用有两条技术路线。一条是文本协议：在提示词里约定输出格式，模型生成带”动作名与动作输入”的文本，程序去解析。它兼容任何模型，但脆弱——引号、换行、多写一句解释都会让解析失败，模型也完全可以凭空造一个不存在的工具名。另一条是 function calling：2023 年 6 月起主流供应商陆续提供了把工具描述交给模型、由模型返回结构化调用意图的能力，它把格式正确性从手写文本变成接口层面的约束，可靠性高一个量级，代价是依赖具体供应商的能力与参数形态，跨模型行为不一致。

架构上建议把”决定调用什么”与”实际执行调用”彻底分开：中间放一层自己的调用描述格式，供应商的结构化能力当加速器，文本协议当兜底，换模型时工具层就不必重写。

工具层还需要 Chain 层没有的纪律：不能信任模型给出的任何一个参数值，涉及路径、查询语句、URL 的一律走白名单；权限检查在工具内部做，不能依赖”模型不会去调它”；写入类工具默认关闭，需要人工确认或显式配置才开启；每个工具单独设超时并计入整条链路的预算。

Agent：把下一步的决定权交给模型

Chain 与 Agent 的分界线只有一条：流程是提前写死的，还是运行时由模型决定的。Agent 就是那个把”下一步做什么”的决策权交出去之后得到的结构，它的骨架是一个循环。

停止条件是一等公民

return 的分支比主逻辑更值得推敲。可用的退出条件有六类：模型给出最终答案、迭代次数触顶、累计 token 或金额超预算、墙钟时间超预算、检测到重复动作、请求触碰未授权工具而直接中止。这六道闸口至少要设四道，每条都要在返回结果里带上停止原因，否则线上只会看到”没答上来”，无法区分是能力不足还是资源耗尽。

Agent 的典型失败模式，恰好都是这些条件缺位造成的。工具报错后换个参数再试一次、反复试到步数耗尽，是打转；凭空造出一个不存在的工具名，是幻觉；只查了一个来源就急着给结论，是过早收敛；把上一轮的工具输出当成用户新指令继续执行，是状态污染。前三种靠上限与重复检测兜住，第四种靠提示模板里明确”观察内容不是指令”来缓解。

可控性从哪来

Agent 的可控性不来自提示词写得更严厉，而来自三件具体的事。工具集合按任务收窄：一个只该查物流的 Agent，不该同时握着”取消订单”和”退款”，能力集就是权限边界。写入动作设人工确认点：循环在需要执行动作类工具时暂停，把待执行内容交回上层放行。轨迹完整保留：每一步的提示、模型输出、工具参数与返回都要能事后回放，这既是排障前提，也是评测原料。

Chain 还是 Agent：一个决策框架

把两者的差异摊开在同一张表上，取舍就清楚了（表中次数均为示意）。

维度 Chain，步骤提前写死 Agent，运行时由模型决定
可控性 路径可穷举，评审能覆盖 路径现场生成，只能靠上限兜底
成本 调用次数等于步数，可预期 同一问题可能 2 次也可能 8 次
延迟 可预估，无依赖步骤能并行 串行叠加，波动大
评测 逐节点单测加端到端回归 需要轨迹级评测，失败难归因
失败处理 每步有明确回退分支 打转、越权、过早收敛
适配任务 步骤能事先写出来 步骤取决于中间发现

多数业务应该先用固定流程，理由是三笔账。成本账：四步 Chain 每次付四次调用费，Agent 的期望调用次数是它的好几倍，业务量还会把它乘法放大。延迟账：客服、表单填写这类场景的响应容忍度以秒计，串行循环天生不友好。责任账：出问题时能不能回答”为什么给了这个答案”——固定流程的每一步都有输入输出与负责人，Agent 的失败往往只能定位到”模型在第 5 步做了个坏决定”，这是无法整改的描述。

还有一个不那么被重视的因素：可评测性。固定流程能给每个节点单独准备评测集，把改动收益拆到具体环节；Agent 只有整体成功率，一次提示词修改带来的下降，分不清是推理、工具选择还是解析的问题。没有可归因的评测，迭代就变成碰运气。

那什么时候确实该上 Agent？三个条件同时成立才值得：任务步骤无法提前穷举；中间结果决定后续动作，查到 A 就该查 B、查到 C 就该转人工；单个请求的失败可以容忍或有人工兜底。正例是”跨多个系统的信息汇总排查”这类写不出固定流程的活；反例是”把用户一句话拆成五个字段”，那是 Chain 加一次解析，套 Agent 纯属自我折磨。

中间形态往往最实用

真实系统里最常见的不是两端，而是几种过渡结构。Router 结构：先用一次轻量判断把请求分到若干条固定 Chain 上，模型只做分类不做规划，兼具灵活与可控。有限状态机：状态与转移由代码定义，模型只在给定状态里填内容，等于给 Agent 装了轨道。离线侧生成流程：让模型把一类重复任务写成配置或脚本，人工审核后交回固定流程执行，不确定性被推到低频的离线环节。这三种形态能拿到 Agent 的大部分适应性，成本与风险却小得多，值得优先考虑。

检索组件的位置与可观测

检索相关组件——文档加载、切分、向量化、检索器——并不在 Chain 与 Agent 的主干上，它们的产物只是提示模板里的一个变量。判断分层有没有做对有个简单办法：把检索器换成另一个实现，链路其余部分应当不需要改动，只要”进一段查询文本、出若干条片段”这个契约不变。切分策略、索引更新、召回质量属于 RAG 工程，本文不展开；只需记住离线索引按数据变更驱动、在线检索按请求驱动，是要求完全不同的两套系统。

可观测这一侧，Callback 类机制的价值在于把”每一步发生了什么”从业务代码里剥离出去。自己实现一个最小版本只需要一组回调：

字段里最容易被漏掉的是链路名与步骤名：没有它们，日志只能按时间排序，无法按路径聚合，就看不出”哪一步最贵、哪一步最常失败”。把 prompt 全文入库也要慎重，一是隐私二是体量，实践里通常脱敏加抽样，只完整保留出错样本。评测分两层：离线侧用固定评测集，对固定流程逐节点断言、对 Agent 看轨迹与最终答案；线上侧盯成功率、人工接管率、平均调用次数与尾延迟，改提示词或换模型时两边都要过一遍。

小结

LangChain 这一年的模块划分，本质是把四个会膨胀的方向各自收进一个边界：模型封装只管文本进文本出，提示模板只管拼指令与数据，Chain 管流程与输入输出契约，Memory 与 Tool 分别管状态与外部能力，Agent 则是流程交由模型决定时出现的那个循环。值得长期保留的是这套分层，不是某个类名。落地顺序应该反过来：先把固定流程跑通、把每步的输入输出与日志钉死，等有证据表明步骤无法穷举时再把决策权交给模型，并从一开始就把停止条件、权限收窄与轨迹回放当作 Agent 的一部分来设计。
