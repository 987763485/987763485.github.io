Rust RefCell 与内部可变性

本文属于《Rust 学习路线》第 17/68 篇
上一篇系列目录下一篇

所有权与借用规则让 Rust 在编译期就挡住了数据竞争，但也带来一个具体的困扰：有些值明明只有一个所有者，我却要透过共享接口去修改它的内部状态。标准库对这个困扰的回答是内部可变性（interior mutability），而 RefCell 是其中最常用的代表。本文面向已经熟悉借用规则的读者（相关细节见第 724、755 篇，这里不重复），讲清楚 RefCell 的运行时机制与代价、Cell 与它的分工、与 Rc 的组合用法、常见坑，以及什么时候你应该退回所有权清晰的设计，而不是继续往外套 RefCell。

为什么需要内部可变性

Rust 对修改的编译期规则很简洁：要改一个值，必须持有它当时唯一的 &mut 引用。但有一类场景恰好卡在这条规则的边界上：值的所有者并没有变，也不存在真正的并发修改，只是代码要透过共享接口访问它，类型上无法向编译器证明”没有同时存在的其他可变引用”，于是被一刀切地拒绝。

先看一个最典型的记录需求：

测试代码里对象经常以共享引用的形式传来传去，接口签名被限定在 &self；写 draw_count 违反借用规则，可记录行为恰恰是这个 Mock 存在的意义。类似的场景还有：懒填充的解析缓存、统计计数器、事件系统里的观察者列表、图遍历中的 visited 集合。它们的共同点是：对象对外仍呈现不可变接口，内部状态确实在演化。

内部可变性就是让类型自己表达这种需求的能力：把数据装进特殊容器（Cell、RefCell，最底下是 UnsafeCell），由类型实现的 &self 方法决定内部如何修改。编译器”共享引用与可变引用不同时存在”的约定并没有被废除，只是检查从静态分析搬进了容器的运行时计数器，于是失败方式从编译错误变成运行时 panic。这就是这套机制全部的取舍：用一点运行时开销和一类延迟暴露的错误，换取接口上的自由度。

RefCell 的运行时借用计数

RefCell 包住一个值，对外只暴露安全 API。它的核心是内部的一个借用计数（用普通非原子的整型标志状态实现），大致有三种形态：空闲、N 个共享借用、1 个独占借用。borrow() 与 borrow_mut() 分别对应编译期的 &T 与 &mut T，返回 Ref<’_, T> 和 RefMut<’_, T> 这两个智能指针代理。代理实现了 Deref，可以读甚至改内部值；Drop 时把计数归还——释放时机完全跟着 guard 的作用域走，和 MutexGuard 是同一种 RAII 风格。

规则与编译期几乎一致，违规的代价却变了：

独占借用是排他的：还有共享借用没释放时调用 borrow_mut 会直接 panic；反过来，独占借用存续期间调用 borrow 同样 panic。

编译期借用违规在 cargo check 阶段就会被抓住，而 RefCell 的违规要等运行到那一行才暴露——这是内部可变性最实在的代价。为了缩小 panic 面，标准库还提供 try_borrow 与 try_borrow_mut，借用冲突返回 Result 里的 Err，由调用方决定怎么处理；当”借不到”本身是业务分支的一种，优先用这一族方法。

这个非原子计数器还带来两个约束。一是成本：每次借用要读改写计数并做一次分支检查，远比锁的开销便宜，但不是零成本；二是边界：RefCell 不实现 Sync，不能跨线程共享，跨线程的共享修改是 Mutex 与 RwLock 的工作（后文有选择矩阵）。

顺带一个控制借用窗口的写法习惯：guard 若不绑定命名变量，在当前语句结束时就释放；想要更短的窗口，可以把借用包进一个块，或者显式 drop(guard)。过长的借用是多数冲突 panic 的直接来源。

Cell 与 RefCell 的分工

cell 家族的另一位成员 Cell 走了不同的路：不做借用计数，也不给代理，只有”整体读写值”这一种玩法——get、set、replace、take 这些方法。正因为没有中间引用阶段，它也不可能发生借用冲突；代价是你拿不到 &mut T，没法直接在原地调用内部值的方法。

两者的分工可以按下面的思路划：

  • 字段类型实现 Copy，读写都是整值（计数器、开关、上次访问的下标）：用 Cell。一次读写一个值，无 panic 风险，还省掉一个计数器。
  • 需要持有 Vec、String、HashMap 这类聚合值并通过其方法修改（push、insert），或一个对象内部多处、多字段要分别借用：用 RefCell。
  • Cell 也支持非 Copy 类型，但可用手段只剩 replace、take 这种”整个换新”，粒度很粗；真走到这一步，通常说明 RefCell 才是更合适的形态。

两个使用细节。get 要求 T: Copy，take 要求 T: Default——take 会留下一个默认值占位，读完若不想留占位，得自己 set 回原值。所以 Cell 更适合”值本身承载状态”的场景，而”状态藏在对象内部方法里”的场景属于 RefCell。一句话概括：Cell 用值语义绕开借用，RefCell 用运行时计数复刻借用。

选择矩阵：从直接可变引用到 Mutex

选容器之前先问清三个问题：数据归谁所有、修改发生在单线程还是跨线程、需要多细的修改粒度。下表把几个常见选项放在一起对比：

场景 选择 违规的失败方式
单线程，修改点清晰，只有一个可变入口 直接传 &mut T，不套壳 编译错误（最早暴露）
单线程，Copy 字段整值读写 Cell 不会冲突
单线程，必须透过 &self 在多处修改内部集合 RefCell 运行时 panic 或 Err
跨线程共享，读写均衡 Arc<Mutex> 阻塞等待、锁中毒
跨线程共享，读多写少 Arc<RwLock> 阻塞等待、锁中毒

值得注意的是 Mutex 与 RwLock 本质上就是”多线程版的 RefCell”：同样把合法性检查搬到运行时，只是手段不同——Mutex 用 OS 等待实现互斥（跨线程的竞争 panic 解决不了，只能等），RwLock 允许多读者并存、写者独占。它们还有一个 RefCell 没有的状态：中毒。线程在持锁期间 panic，锁会被标记中毒，后续 lock() 返回 Err，提醒你数据可能停在 panic 现场的中间态。

另外注意，矩阵第一行才是默认答案：Vec、HashMap 走 &mut 修改，本就不需要壳；RefCell 只在接口形态被限定成共享只读时才登场。也不要为了”单线程里多读者更高效”去选 RwLock——这层顾虑属于多线程场景专属。

与 Rc 组合实现共享可变状态

第 762 篇讲过 Box 与 Rc：Rc 让一个值有多个所有者，但每个持有者只能通过 &Rc 看到只读视图，同一份数据的多个副本没法各自 push。Rc 与 RefCell 组合，就得到单线程下经典的”共享可变对象”模式：Rc 回答”谁拥有”，RefCell 回答”怎么改”。所有权规则本身不再重复，看组合之后的效果：

每个 Task 持有一份 Rc 克隆，run 时写进同一个 RefCell 包住的 Vec——若按”不共享”的写法直接传 &mut Vec，这种多处写入的结构是写不出来的。

两个配套提醒。其一，Rc<RefCell> 既不 Send 也不 Sync，交给 std::thread::spawn 会直接编译失败；要跨线程共享这份可变状态，等价形态是 Arc<Mutex>，换掉的正是”单线程”这个前提。其二，节点之间若互相引用成环（双向链表、树里指回父节点的引用），Rc 的计数不会归零，内存泄漏；解法仍然是 762 篇里的 Weak 断环，RefCell 只负责让环上的写入可行，不负责解决环本身。

内部可变性的抽象契约

把 cell 家族的共同点提炼出来，大致是三条约定：修改入口是 &self；合法性由类型自己决定（要么整值替换，要么运行时计数）；所有字段的可变性最终可以追溯到一个 UnsafeCell。标准库把 UnsafeCell 定为唯一允许把 &T 变成可写指针的官方入口，不安全被集中锁在 cell 类型把关的那扇门后面，用户面对的仍是安全 API。

这套契约在社区与标准库的实现讨论中曾被设想为正式抽象，常被称作 InteriorMutable trait：编译器据此识别内部可变容器，并统一禁止它们实现 Sync。但截至 Rust 1.68，这样一个公开 trait 并未稳定存在，它只是作为隐含约定发挥作用——每个 cell 类型各自通过内含 Cell 或裸指针字段让自己不是 Sync，标准库对外只暴露现成的容器。

对普通读者的推论很直接：若要自定义内部可变类型，稳定做法是自己包 UnsafeCell 并加入非 Send、非 Sync 的标记（例如一个 PhantomData<*mut ()> 字段），同时自行保证任一时刻至多一个可写引用——这个约定一旦违反，后果不再是 panic，而是未定义行为。所以除非 std 的组合形态确实不满足需求，优先选用现成的 Cell 与 RefCell，UnsafeCell 应当是最后手段。

常见坑

坑一：重入借用冲突。panic 最常见的形状，是持有 RefMut 的方法内部又调用了会借用同一个 cell 的逻辑。

修法是三选一：提前 drop guard、把 borrow_mut 的窗口缩进块里，或者先算好要写入的值再一次性写。若结构上确实需要”只借用一个字段”，可以用 Ref::map、RefMut::map 把整体借用投影到子字段，降低冲突概率——但这只缓解症状，回调里再借同一容器的设计本身就该警惕。

坑二：想把借用出来的引用跨函数返回。borrow() 返回的代理握着计数，解引用得到的 &T 生命周期绑定在 guard 上：

guard 在语句结束就释放，引用活得比它长，编译器拒绝得很干脆。出路取决于需求：能拷贝就返回拥有值的克隆；确实要返回视图，就返回 Ref<’_, i32> 本身（配 Ref::map），让计数跟着返回值活。但调用方从此要知道”这一次借用期间别人借不到”，这通常已是设计开始别扭的信号。

坑三：异步任务里跨 await 持有 RefMut。两层问题叠在一起：RefMut 不是 Send，future 因此也发不出去，在 tokio 的多线程运行时上 spawn 会报”future cannot be sent between threads safely”一类的错；即便勉强在线程内跑完，await 期间计数照样持有，并发任务借到同一容器时得到的是 panic 而不是等待，排查起来比锁竞争更隐蔽。正确姿势是让借用窗口不进 await：先取出或克隆需要的值，await 之后再重新借用。

坑四：把 RefCell 放错上下文。写进静态变量或交给 thread::spawn，编译器报不满足 Send 或 Sync——这不是报错的 bug，而是边界在提醒你应该换成 Arc<Mutex> 或多线程专用形态。

何时该回到所有权清晰的设计

RefCell 的本职是化解接口形态的约束，不是逃避所有权设计上的问题。出现下列信号时，先停下加壳的手，回头重排结构：

  • RefCell 在扩散：新字段都倾向再套一层，函数签名里爬满 &Rc<RefCell>。这说明”共享可变”成了常态，对象没有明确的所有者。可行的重构是把变更收拢到唯一持有 &mut 的入口，其余部分退化为只读视图。
  • try_borrow_mut 的 Err 成了常规分支：调用方开始”借不到就重试或跳过”。借用冲突是架构层面的真实矛盾，运行时只是让它换个形态爆发。
  • 频繁需要把 Ref、RefMut 交给调用方：等于让整条调用链陪跑运行时借用检查。
  • 套壳只是为了缓存派生数据，而这份缓存本可以有清晰的失效时机：把派生值放到调用方结构里，或改成显式的刷新方法，往往比隐式缓存更好推理。

几个常用的替代招式：让数据与行为同处一地，变更走 &mut self 方法，只读接口返回克隆或切片；把大状态拆成各自有单一所有者的小状态，借用关系自然变浅；多个模块要共同维护一份统计时，与其共享可变对象，不如各自把增量发给汇总者，单线程用返回值累加，跨线程用 channel 消息传递。

给一条干脆的界线：加 RefCell 的理由若是”trait 签名限定成 &self””测试替身要记录””懒缓存”，且借用窗口缩得进单个函数，用它；理由若是”好几个模块说不清谁拥有这份数据”，别用它，先解决所有权。

小结

内部可变性把编译期的借用契约搬到运行时执行：RefCell 用非原子计数管理 borrow 与 borrow_mut，冲突即 panic，try_borrow 一族把冲突降级为普通的 Err；Cell 则用整值读写绕开借用，适合 Copy 状态。单线程内需要透过 &self 修改就用 RefCell，跨线程就换 Mutex 或 RwLock；Rc 管所有、RefCell 管修改，Rc<RefCell> 是单线程共享可变对象的标准形态，但它不 Send 也不 Sync，环状引用仍需 Weak 来断。InteriorMutable 到 1.68 仍只是标准库的隐含约定而非公开 trait，自造容器要直面 UnsafeCell 的未定义行为风险。最后记住那条纪律：RefCell 化解的是接口形态的约束，化解不了所有权的含糊——当你发现自己在到处补借用窗口时，多半是该重排结构的时候了。
