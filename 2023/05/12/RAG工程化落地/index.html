RAG 工程化落地

本文属于《Agent 智能体开发》第 24/55 篇
上一篇系列目录下一篇

RAG（检索增强生成）的原型很好做：把文档切开、算 embedding、塞进向量库，再接一个问答提示词，一个周末就能跑通 demo。但让它服务于真实用户——几十万名员工或者外部客户——问题才会真正暴露：文档每天在变、权限模型复杂、答错了没人能追责、成本随流量线性上涨。本文面向跑通过 RAG 原型、准备推向生产的读者，梳理从数据接入到运维监控的工程链路。检索与 embedding 的原理、分块策略选型、重排序模型细节，本博客另有专文（《Embedding 与语义检索》《RAG 分块策略与召回优化》《RAG 检索重排序实践》），本文不重复，专注工程化与运维这一层。

从 demo 到生产的差距

先回答一个问题：为什么能答对十几条测试题的 demo，上线两周后就没人用了？因为 demo 与生产系统的差异不在模型能力，而在系统属性。我把它归纳为六条：

  1. 数据是活的。demo 用静态语料；生产知识库每天新增、修改、下线文档，索引要跟随变化，且要能度量”知识落后了多少天”。
  2. 权限是硬的。demo 默认所有文档对所有问题可见；生产上，薪酬制度不能出现在客服机器人的回答里，HR 文档不能被外部用户检索到。
  3. 失败是常态。demo 只演示成功路径；生产上检索不到、检索到过时版本、多篇文档互相矛盾都是高频事件，系统必须有明确定义的降级行为。
  4. 质量必须可度量。demo 靠手工试几个问题；生产需要离线评测集和线上指标，否则任何一次改动都是盲改。
  5. 成本必须可控。每次问答都是真金白银的 token 费与向量检索费，没有缓存和预算控制的系统会烧穿账单。
  6. 变更必须可回滚。提示词、分块参数、embedding 模型、索引版本的任何一项变更都要能灰度、能退回。

一条典型的生产链路大致如下：

flowchart LR
    A[文档源] --> B[解析与清洗]
    B --> C[切分流水线]
    C --> D[Embedding 批量计算]
    D --> E[向量索引 + 关键词索引]
    F[查询] --> G[权限过滤与混合检索]
    E --> G
    G --> H[上下文拼装]
    H --> I[LLM 生成]
    I --> J[引用校验与返回]

本文按这条链路逐段展开。工程上还有一个提醒：2023 年上半年的 LangChain 正处于 0.0.x 版本的高速迭代期，几乎每周都有破坏性变更，把它当胶水层可以，但务必锁定具体小版本，核心链路不要绑死在它的抽象上，否则一次升级就会让你重做集成测试。

文档接入与解析

数据管道的第一个决策是：接什么格式、解析到什么程度。企业知识库的文档来源通常有四类：在线协作文档、Office 文件、PDF、网页或 Markdown，解析成本差一个数量级，应按”解析收益”排序接入，而非一视同仁。

优先接入结构化源头。协作文档和 wiki 有导出 API，能直接拿到带层级的正文，应走自动同步；Markdown 与 HTML 用通用解析器即可。Office 文件建议转成带结构的文本，例如用 python-docx 提取段落与表格，而不是先转 PDF 再 OCR——绕一圈反而丢信息。PDF 是最麻烦的：双栏排版、页眉页脚、脚注混排在纯文本里，不处理就会污染检索结果。2023 年，unstructured 这类开源库已能覆盖大部分常规版式，可以先拿它做基线，再针对自家文档集修补。

表格是重灾区。PDF 里的表格被展平成文本后，行列关系全丢，”2022 年 Q3 华东区销售额”可能变成一串没有上下文的数字。务实的做法有两种：能拿到源文件（Excel、docx）就按单元格逐行转成”行首列 + 列名 = 值”的文本化格式；只有 PDF 就用表格识别工具还原结构，转成 Markdown 表格后作为独立 chunk 存储，并打上 type: table 元数据。识别不出的复杂合并单元格表格，宁可标记”未解析”进人工队列，也不要静默塞进错误内容——语言模型会把错误检索结果编成流畅的答案，垃圾进、垃圾出，在 RAG 里代价比传统搜索更高。

图片与 OCR 的取舍。图表、截图、扫描件需要 OCR，是否值得做取决于三个问题：图里的信息是否只存在于图中？OCR 准确率能不能支撑检索粒度？成本和时效能不能接受？纯扫描版的历史档案值得批量跑 Tesseract 或商用 OCR 建库；而”多数结论正文已有、图片只是配图”的场景，给图片生成文字描述的收益低于成本，直接索引图注和所在段落上下文即可。判断标准只有一个：解析投入是否换来可验证的召回提升。

清洗与切分流水线

切分策略本身（固定窗口、语义切分、层级切分、重叠取舍）已有专文讨论，这里只谈把切分做成一条工程流水线需要满足什么条件：可配置、可复现、可回溯、可重放。

先说清洗。解析出的文本进切分之前要过一遍归一化：统一编码与空白字符、剥离页眉页脚和水印文本、剔除每页重复出现的模板段落、把软换行合并成完整段落。跨文档的重复内容也在这一步处理——企业知识库里同一份制度常有三四个副本，按段落做指纹（内容哈希或 simhash）去重，保留权威版本并把副本重定向过去，能显著减少”检索回来五条几乎一样的上下文”这种浪费 token 的情况。

切分作为流水线阶段，核心设计要求有四条：

  1. 参数外置。chunk 大小、重叠量、按标题切还是按 token 切，全部放进配置，与代码一起版本管理，不允许散落在各处硬编码。
  2. 产物确定性。同一份文档、同一版配置，重跑必须产出完全相同的 chunk 集合。chunk_id 应由 doc_id、内容哈希和序号推导，而不是数据库自增 id——这是幂等重放和增量对账的基础。
  3. 元数据随行。每个 chunk 继承文档级元数据（acl、updated_at），再附加自己的定位信息：页码、标题路径、文档内序号。标题路径对检索质量影响很大，把”报销制度 > 差旅费”这样的路径拼进 chunk 头部，比只存正文更容易被向量检索命中。
  4. 配置指纹入库。把解析器版本、切分配置哈希写进每个 chunk 的元数据。将来评估”换分块参数有没有变好”、排查”这条答案来自哪个版本的切分”，都靠这个字段。

索引构建与增量更新

索引层最大的工程矛盾是：embedding 计算慢且贵，而用户期望文档更新后几分钟内就能被搜到。解决方案是把全量构建和增量更新分开设计。

全量构建发生在首次上线或任何”会改变向量空间”的配置变更时：换 embedding 模型、换切分策略、大范围重新解析。要点是批量与限速：批量接口按每批几十条提交，失败重试做指数退避；十万级 chunk 要跑数小时，必须支持断点续传，记录已完成的 chunk_id 而不是从头再来。产物先写入新索引，验收通过后再切换，不要在旧索引上原地覆盖。

增量更新处理日常变更：对象存储事件、消息队列或轮询 updated_at 驱动增量流水线，只重跑受影响的文档。这里有两个容易被忽视的正确性问题：

  • 改前删旧。文档更新后，旧版 chunk 必须先标记删除再写入新 chunk。向量库不支持按元数据删除时，用”tombstone + 检索侧过滤”：给旧 chunk 打 deleted: true，检索时过滤，后台物理清理。漏了这步会同时命中新旧两版内容，埋下上下文冲突。
  • 删除要传播。源文档下线时索引里对应 chunk 必须删除，并对账”源系统有效文档集合”与”索引文档集合”是否一致。事件会丢，对账兜底。

模型版本管理要用索引别名。embedding 模型从 A 换成 B，两套向量绝不能混在同一索引里——不同模型的向量空间不可比，混用会让相似度分数彻底失真。正确姿势是新旧索引并存构建，新索引全量就绪并通过离线评测后，把别名原子切过去，旧索引保留一段时间用于回滚。Milvus、pgvector、Elasticsearch 的别名或表切换机制都能实现这个模式。

索引层还要监控两个滞后指标：从文档变更到索引可见的端到端延迟（p95 应在可接受范围，例如小时级），以及积压深度（待处理队列长度）。数据时效性出了事故，多数不是更新逻辑写错了，而是更新任务静默失败了三天没人看监控。

检索层：混合检索、过滤与权限

检索服务是 RAG 里直接面向查询延迟、工程约束最密集的一层。生产检索要同时满足三件事，优先级即排列顺序：权限错了是事故，过滤错了是劣化，召回差一点通常还能靠生成层弥补。

为什么要混合检索。纯向量检索对”精确字面匹配”天然偏弱：产品型号、错误码、法条编号、人名，用户要的就是字面命中，embedding 相似度却可能把它们和一堆”语义相近”的文档搅在一起。反过来，纯关键词检索理解不了同义词和口语化提问。2023 年的主流做法是两路并行：向量检索（kNN）加关键词检索（BM25），再用倒数排名融合（RRF）合并。RRF 不需要校准两种分数的量纲，实现只有几行，对分数分布变化也稳健，适合起步：

过滤要下推到引擎。元数据过滤（时间范围、文档类型、业务线）尽量交给向量引擎在检索时执行，而不是捞回一批结果在应用层 filter——后者会出现”Top 20 过滤完只剩 3 条”，召回深度不可控。主流向量引擎都支持带过滤条件的向量检索（选型对比见专文），这里只要求：过滤语义在索引层实现，评测集专门覆盖”带过滤条件的查询”。

权限控制必须进索引，而不是进提示词。最常见的错误设计是：检索全部文档，然后在提示词里叮嘱模型”不要引用薪酬类文档”。这不安全也不可靠——敏感内容已经进入上下文和日志，模型也随时可能不听话。正确做法是把上一节的 acl 元数据写进索引，查询时把用户身份翻译成过滤条件强制下推：

上下文拼装与 token 预算

检索返回的是散落的 chunk，生成模型吃的是一段有序上下文，拼装逻辑直接决定答案质量与 token 成本，工程上做四件事。

第一是去重与合并。多路召回后，候选里常有来自同一文档相邻位置、内容大量重叠的碎片。拼装前应按内容哈希去重，并把同一文档相邻序号的 chunk 合并成连续段落——一段连贯上下文，远好于三条碎片各占一份预算还打断语义。

第二是token 预算控制。用 tiktoken 在组装时精确计数，给系统提示、用户问题、历史轮次、每篇文档的引用格式各留固定额度，剩余预算分配给检索上下文，超出预算按相关性分数从低到高截断。要点是把预算做成配置项并记录每次请求的预算构成，排查”为什么答案漏了某文档”时先看它是不是被截断了：

第三是上下文内的元信息呈现。每个 chunk 以带编号、标题、更新时间、来源 URL 的形式给模型，例如”[3] 报销制度（更新于 2023-04-18）……”，并在指令里要求答案中的每个事实性论断标注编号。这既是引用功能的基础，也给模型提供了判断新旧的依据。

第四是长上下文的取舍。2023 年中，GPT-4 已提供 32k 上下文窗口版本，”干脆把所有文档都塞进去”重新有了诱惑力。工程上仍不建议：成本和延迟随输入 token 线性涨，检索范围不收敛时”针在草堆”问题反而更严重，全量塞入还让权限过滤和时效策略无处安放。长上下文适合当兜底——检索置信度低时放大预算——而不是替代检索。

引用与可追溯性

引用不是”让答案看起来更可信”的装饰，而是人机协作的基础设施：用户靠引用核对答案，领域专家靠它发现知识库错误，事故复盘靠它定位问题环节。工程上要把可追溯性做穿整条链路。

从编号到出处的闭环。上一节给每个上下文 chunk 编了号，生成侧要求模型用编号标注论断，返回前服务端做校验与展开：把”[3]”映射回 doc_id、标题路径、源 URL，组装成结构化引用列表随答案返回。校验必须做，因为模型会产生两类典型错误——引用不存在的编号（上下文只有 5 篇却标注 [7]），以及编号存在但论断与该文档无关。前者直接剥离，后者在严格模式下触发重新生成或降级话术。

粒度选择。内部知识助手的引用应落到段落级（标题路径加原文摘录），方便核对；对外部客户的合规场景则要确认引用文本可否外显——原文可能含内部批注，必要时引用列表只展示标题与版本，段落级证据仅在内网审计视图可见。

请求级溯源日志。每次问答落一条完整日志：查询原文、召回候选与分数、过滤条件（含权限）、最终上下文及其 chunk_id、提示词版本、模型与参数、token 用量、答案与引用校验结果。这份日志是评测、失败分析和审计的共同数据源。注意两点：日志含敏感文档内容，存储要加密脱敏、分级访问；溯源 id 要贯穿前端，用户点踩某条答案时，反馈必须能定位到这条日志。

最后提一个容易被低估的收益：有了引用与溯源，”答案错了”从一个无法处理的投诉变成一个可归因的工程问题——是文档本身错了、检索没召回对的、召回了但被截断了、还是模型无视上下文自由发挥。这四类问题的修法完全不同，没有可追溯性就只能整条链路一起调参。

评测体系：离线集与线上指标

RAG 系统的任何改动——换模型、调分块、改提示词——都必须回答”比原来好还是坏”。这要求离线评测集和线上指标两套体系同时存在，各司其职。

离线评测集从真实查询长出来。冷启动时从使用日志和客服问题里抽几百条查询，请领域作者标注”答案应来自哪些文档”。指标分两层：检索层看命中率（前 K 条结果包含标注文档的比例，即 recall@K）和 MRR，便宜且稳定，适合每次改动必跑；生成层看答案质量，贵且波动，适合版本发布前跑。

生成层评测的组合拳。2023 年的现实是：完全自动化不可靠，纯人工太慢，要三者结合。其一，事实一致性核对——用另一个模型判断答案论断能否被检索上下文支持，即”忠实度”检查，LLM-as-judge 当时已被广泛使用，但要清楚它有偏长偏褒的倾向：固定裁判模型与提示词，把分数只当趋势不当绝对值。其二，规则化断言——对标注了”必须提及”要点的查询做关键词与编号检查，确定性高、成本低。其三，人工抽检——对自动判”通过”的样本按小比例复核，防止评测体系自身腐化。SelfCheckGPT 这类基于多次采样一致性的无参考检测也可纳入，给高风险答案打置信分，代价是推理成本翻倍。

线上指标回答”系统在真实世界里健康吗”。核心看板我建议至少包含：无答案率（触发兜底话术的比例，突增通常意味着检索或数据出问题）、引用点击率与”引用不符”反馈数、用户显式反馈（赞/踩及理由分布）、端到端延迟分位数、单查询平均成本。离线评测好而线上指标差，一般说明评测集已经脱离真实查询分布，要重新采样扩充。

评测要跟着数据更新跑。索引每次大范围重建、embedding 模型切换、每周例行增量之后，都应触发评测集回归，结果入库形成时间序列。评测集本身也要维护：新上线的高频文档应补进查询集，已下线文档的标注要及时清理，否则指标会被”该检索不到的检索到了”污染。

失败模式与降级设计

生产 RAG 的失败可以穷举为三类，每类都要有明确定义的降级行为，原则只有一条：宁可说”没查到”，不可编一个流畅的错误答案。

检索不到。查询超出知识库范围，或表述与文档措辞差异太大。降级链路：先放宽召回看置信度，仍不足则返回兜底话术并把查询记进待补充清单——无答案查询是知识库建设最有价值的需求信号。禁止的行为是检索为空仍让模型凭参数化知识自由回答，那等于在最不可靠的场景关掉安全带。

上下文冲突。同一主题的新旧两版文档同时被召回——旧文档没删干净、或者”作废通知”与原文并存。防线依次是：增量更新时的删除传播、上下文里的更新时间元信息让模型有裁决依据、提示词中明确”以更新时间较新的内容为准，矛盾不可调和时说明分歧”。同时制度类文档应保证同一主题只有一个生效版本入库。

幻觉。检索到了正确文档，答案却包含上下文里没有的内容。治理手段就是前面贯穿的三件事：强制引用编号并做生成后校验、忠实度检查打低分、高风险场景（涉及金额、日期、合规条款）把答案置信度与人工审核队列挂钩。幻觉率只能压低不能归零，所以面向用户的界面要始终展示引用，让核对成本低于被误导成本。

缓存与成本控制

RAG 的账单由三块构成：embedding 计算、向量检索服务、LLM 生成 token，其中 LLM 占绝对大头，优化应从查询流量结构入手——知识助手类流量的头部重复率远高于直觉，缓存收益可观。

分级缓存的次序：查询归一化后先命中答案缓存（相同或近似问题直接返回，TTL 与知识库更新节奏挂钩）；未命中再查检索缓存（embedding 向量与召回结果各一层，按查询哈希加权限维度做 key）；都没有才走完整链路。关键约束是失效策略：缓存 key 必须包含索引版本与切分配置指纹，别名切换、全量重建时整批作废，否则会出现”制度已更新、答案还是旧的”这类最恶劣的事故。权限维度也必须进 key，不同用户组共享缓存等于越权。

生成侧的成本控制：按任务分层用模型，多数检索证据充分的请求用便宜模型即可，复杂多跳问题再升级到更强模型——路由判定可以基于召回条数与分数分布这类廉价信号；上下文预算收紧（前文的 pack 逻辑）本身就是成本开关；批量离线任务用批处理接口错峰提交。监控上把”单查询平均 token 成本”做成时序指标，成本突增往往先于质量劣化暴露问题，例如检索退化导致上下文每次都塞满预算。更细的 token 计费与成本核算方法已有专文，此处不展开。

灰度发布、回滚与运维监控

RAG 系统的”发布物”是一组组合：提示词版本、检索配置（召回深度、融合权重）、上下文预算、模型与参数、索引版本。任何一项单独变更都可能改变端到端行为，所以灰度的最小单元应当是整个组合，而不是某段代码。

落地方式是”配置版本化加流量分桶”：把上述组合登记为一个具名版本，线上同时挂两到三个版本，按用户或会话 ID 哈希分桶路由，新桶先接 5% 流量。观察窗口里对照新旧桶的线上指标——无答案率、点踩率、延迟、成本——离线评测通过但线上指标劣化的版本要有自动熔断回退。回滚能力靠三件事保证：索引别名随时可切回旧版本（前文的多版本索引留存）、提示词与配置在配置中心留有历史、答案缓存按版本隔离所以回滚不会读到新版本缓存。切记数据更新流水线与发布解耦：索引重建这类不可逆操作应在灰度确认后才对全量流量生效。

运维监控在本文各节指标之上，补齐系统视角的四块：检索服务与向量引擎的健康度和延迟分位数；更新流水线的积压、失败率与端到端数据时效（”最老的未处理文档距今多久”应做成分文档源的看板）；外部依赖的配额与异常——embedding 与 LLM 都是远程 API，限流、超时要能触发降级（缩短上下文、退回纯关键词检索、必要时只读缓存）；以及成本与用量日报。对用户而言”知识是旧的”与”知识是错的”体验几乎等价，文档从源系统到可检索的滞后必须像服务可用性一样被监控和告警。

小结

把本文串成一张检查清单：解析按收益分级、表格与权限元数据进中间格式；切分流水线做到确定性、幂等、配置指纹入库；索引多版本加别名切换，删除传播有对账；检索权限强制下推、混合召回用 RRF 起步；上下文用 token 预算精确装配并带编号；引用做生成后校验，日志全链路可溯源；离线评测跟改动跑、线上指标跟发布跑；三类失败各有降级，宁可拒答不可编造；缓存 key 绑定索引版本；发布以配置组合为单元灰度可回滚。RAG 的工程化没有银弹，它的本质是把”检索系统的数据运维”和”生成系统的质量治理”两套老练的工程实践接到同一条链路上。先把评测集和可追溯日志建起来，后面每一次优化才有据可依。
