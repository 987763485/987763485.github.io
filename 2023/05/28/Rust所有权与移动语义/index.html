Rust 所有权与移动语义

本文属于《Rust 学习路线》第 10/68 篇
上一篇系列目录下一篇

很多初学者把 Rust 的所有权当成一组要背的语法规则：什么时候该报错、什么时候该补一个 clone()、& 和 mut 怎么排列组合。这样学很容易停在“能编译，但说不清为什么不编译”的状态。本文换一个角度，把所有权看作描述资源归属的语义模型：每个值在同一时刻只有一个主人，主人到期就负责把资源释放干净，移动就是把这份责任交给下一个人。读完你应该能解释移动在内存层面改了什么、String 为什么不能是 Copy 的、结构体被部分移动后还能借用哪一部分、Drop 按什么顺序发生，以及怎么反过来用所有权表达设计意图。内容以 Rust 1.69（2023-04-20 发布）的稳定语义为准，适合写过一些 Rust 代码但还没把这套模型理顺的读者。

所有权模型：先讲语义，再讲规则

要理解所有权，最好先把它放回“内存资源由谁负责释放”这条主线里看。C 语言把责任完全交给人：谁 malloc 谁 free，忘了就泄漏，重复就崩溃。Java 和 Go 把责任交给运行时：对象进堆，垃圾回收器在不确定的时刻统一回收，程序员不再关心“谁负责”，代价是运行时开销与回收停顿。C++ 走的是 RAII：资源生命周期绑在栈对象的作用域上，离开作用域就析构，再用移动构造让“交接责任”这件事可以写得很自然。差别在于 C++ 的这一切都靠约定，编译器不强制，悬垂引用和二次释放仍是常见事故。

Rust 的选择是把 C++ 的 RAII 约定升级为编译期的语言规则。它的具体表述就是那三条：每个值都有一个所有者；同一时刻只能有一个所有者；所有者离开作用域时，值被丢弃（drop）。这三条规则看起来平淡，但它们组合起来的实际含义是：变量不只是“能读到一块数据的入口”，同时还是“这块数据的析构责任凭证”。在别的语言里，赋值或传参只是复制一个访问路径；在 Rust 里，赋值或传参会把责任凭证一并转移过去，原来的路径同时作废。理解了这一层，绝大多数“为什么这里报错”的问题就不再需要背规则了。

三条规则各自在挡什么问题

第一条规则“每个值都有一个所有者”，挡的是无主资源：资源必须有一个明确的释放责任人，否则只能靠运行时兜底，也就是垃圾回收。第二条“同一时刻只能有一个所有者”，挡的是二次释放：两个变量都认为自己负责释放同一块堆内存，作用域结束就会析构两次，这是 C/C++ 里最经典的内存破坏成因；Rust 不做二次释放防护，它直接从语义上否认“两个所有者”可以存在。第三条“所有者离开作用域时值被丢弃”，挡的是泄漏，并让释放时机可预测：栈帧退出的那一刻。

把三条规则连起来看，还能推出几个有用的结论。移动必须是廉价的，因为它是赋值和传参的默认行为，若每次移动都复制堆数据，函数调用就变成性能黑洞；所以移动被定义成“栈上几个字复制加源变量失效”，堆内存一个字节不动。移动也只能是编译期标记，运行时没有“这个变量已作废”这种概念可表达，只能由借用检查在静态分析里完成。至于借用，它是在“唯一所有者”这条硬约束上开的口子：允许多人临时读写，但不给他们释放责任，因此借用不改变所有者，也就不触发移动。引用的具体规则是另一篇文章的主题，这里不展开。

值的生命周期与资源归属

在这个模型里，每个值都有一段生命周期：从被构造出来，到所有者被丢弃为止。它决定的是这个值在哪些位置仍然合法可用；&'a T 这样的类型把“这段有效期内可用”直接写进了类型，生命周期标注本身另有专文，本文只在需要说明“移动会让旧绑定提前失效”时使用这个概念。

移动的真实含义

先从最常见的例子开始。

String 这个类型在栈上只有三个 usize：指向堆缓冲区的指针、长度、容量，在 64 位平台上是 24 字节。执行 let s2 = s1; 时，编译器确实把这 24 字节按位复制到了 s2 的位置上——从机器指令角度看，它和 i32 的赋值几乎没区别。区别发生在两件事上：其一，堆缓冲区没有被复制，s1 和 s2 里的指针字段值相同，指向同一块内存；其二，s1 在编译期被标记为“已移走”，它不再是一个可用的变量。

flowchart TD
    A["s1 栈槽 指针/长度/容量"] --> B["堆缓冲区 'hello'"]
    C["s2 栈槽 指针/长度/容量"] --> B
    A -. 编译器标记为已移走，禁止再读 .-> D["作废"]
    C --> E["s2 离开作用域时释放堆缓冲区"]

如果只做第一项而不做第二项，结果就是二次释放：两个变量都会在离开作用域时调用析构。所以“源变量作废”不是故意给程序员添麻烦，而是这个语义模型自洽的必要条件。反过来说，如果一个类型的移动真的把值复制了一份、源变量仍然有效，那它就不需要作废源变量——这正是 Copy 类型的定义，下一节会细讲。

移动的成本到底在哪里

很多从 Go 或 Java 过来的读者会本能地觉得“移动一个字符串肯定很贵”。实际情况是，一次 move 的运行时成本就是几条 mov 指令：不涉及堆分配、不涉及 memcpy、不涉及引用计数，也没有标志位需要在运行时维护。它甚至在机器码里常常完全消失，因为 Rust 允许直接按目标位置构造值，参数移动进来往往只是调用方把值放进寄存器或参数槽，被调方接手责任。

真正要付代价的是“源变量作废”带来的写法调整：你不能既把一个 Vec 交给函数，又在后面继续用同一个 Vec。这时通常三条路——传引用（&Vec<T> 或 &[T]）；传之前 clone() 一份，真的复制堆数据；让函数把所有权还回来。选哪条取决于语义而不是语法：函数是要“消费”这个值，还是只“看一眼”或“改一改”。这个判断习惯一旦建立，接口签名本身就带上了所有权信息，这是本文后面讲设计模式时的主题。

移动发生的时机

值得列一下哪些位置会触发移动，因为很多报错来自没意识到这里有移动：把非 Copy 的值赋给新变量；作为实参传给按值接收的函数；return 一个按值类型的表达式；在 match 里用不带 & 的模式绑定字段；塞进结构体字面量、元组或 Vec；把循环写成 for x in v（2021 edition 下这会移动整个 v）；以及调用 drop(x)——std::mem::drop 的签名是 fn drop<T>(_x: T)，它靠移动拿走所有权，然后什么都不做，让值在调用结束时析构。

还有一个高频误解：变量被移走之后，它是不是就“废了”？不是。作废的是当前这个绑定，不是这个名字。

这段代码在 1.69 里完全合法。编译器禁止的是“在同一位置重复取出同一个值”，而不是“重复给同一个变量赋值”。分清这两件事，遇到 E0382 时的第一反应就不会是加 clone()。

Copy 与 Clone 的边界

上一节留了一个问题：按位复制之后源变量必须作废，否则就会二次释放。那么 i32 为什么可以 let a = b; 之后继续用 b？答案是 Copy。

Copy 是一种“我保证按位复制是安全的”承诺

Copy 是标记性 trait，不要求写任何方法，只要求类型已经实现 Clone（它是 Clone 的子 trait）。类型一旦 Copy，编译器就把赋值、传参、返回这些位置上原本要做的移动换成按位复制，并且不作废源变量。这个替换是静默的：代码里不会出现 .clone()，但确实复制了一份。

于是判断一个类型该不该是 Copy 的标准非常清晰：这个值的全部状态是否都住在它自己的栈空间里。i32、bool、char、f64、裸指针、[i32; 4] 这样的定长数组、字段全为 Copy 的元组和结构体都满足条件——复制栈位之后两个值互相独立，谁都不欠谁释放责任。反过来，任何“栈上只放句柄、真正的资源在别处”的类型都不能是 Copy：String、Vec<T>、HashMap<K, V>、Box<T>、File、MutexGuard，它们都拥有一个需要析构的东西。

有一个特例值得单独记：引用 &T 永远是 Copy 的。复制一个引用只是复制了“读写权限的凭证”，不改变所有者，也不涉及释放责任，所以可以随便复制多少次。这解释了为什么 &x 能反复出现在参数列表里而从不触发 E0382，也是“借用比移动灵活”的根源。

String 为什么不是 Copy 的

这个问题几乎每个学 Rust 的人都问过，值得给三条互相独立的理由。

第一条是语义上的不可能。String 的栈内容是“指针 + 长度 + 容量”，按位复制出来的两个值指向同一块堆缓冲区：源不作废就有两个所有者，违反唯一归属；源作废那就不是“复制”而是“移动”，Copy 的定义当场失效。总之 String 怎么标记都当不了 Copy。

第二条是成本上的不可接受。假设编译器允许“隐式深拷贝”——赋值时偷偷分配新缓冲区并复制内容，那么每一次 let 都可能是一次堆分配加一次 memcpy，循环里一个看起来无害的临时变量就能吃掉大量带宽。Rust 的原则是便宜的操作默认发生、昂贵的操作必须写在脸上，所以深拷贝被要求显式调用 clone()。C++ 里拷贝构造默认深拷贝造成的按值传递大对象事故，正是这条原则想避免的东西。

第三条是生态上的分工。Copy 表示“逐位复制即等价于构造新值”，Clone 表示“能复制，但你可能得付钱”，标准库只需决定每个类型站在哪一边：Vec<T> 实现 Clone（复制堆缓冲区并逐项 clone）而不实现 Copy；Rc<T> 的 clone 只做计数加一，但它也不实现 Copy，因为引用计数的增减是有语义的动作，不该静默发生。

三者的对照

操作 栈上 堆上 源变量 成本 出现方式
移动 按位复制 不动 作废 常数 默认，静默

还要提醒一句：clone() 的成本不能一概而论。Vec 的 clone 要重新分配并逐项复制，&str 的 clone 只是复制胖指针，Rc 的 clone 是一次计数加一，i32 的 clone 等于没做事。所以看到 clone() 不该条件反射地优化，而该看它作用在什么类型上。

部分移动与借用的相互作用

所有权模型里还有一个容易被忽略的性质：一个结构体不是一个原子，它的每个字段都是独立的值，有独立的归属。这就带来了“部分移动”。

部分移动：字段各奔东西

这里的规则可以总结成一句话：字段随便拆，整体从此作废。p.email 和 p.age 依然是合法表达式，但 p 作为一整个值不能再传给函数、不能再被移动，也不能被 &p 借用——&p 隐含“p 是一个完整的、有主的值”，而它现在有一部分主人已经在外面了。理由也很实在：如果 Person 实现了 Drop，析构函数会假定所有字段都在原地可读；如果允许把 p 整体移走，就会搬走一个含未初始化空洞的结构。

age 这样的 Copy 字段永远不参与部分移动：let a = p.age; 之后 p 依然完好，因为 p.age 那里发生的是复制而不是易主。元组同理，let (x, y) = tuple; 之后能不能继续用 tuple，取决于有没有把非 Copy 的元素按值取走。

从结构体里把值取出来的几种正规姿势

想“从结构体里拿走一个字段但不破坏结构体”，有两条正路。最干净的是解构，一次性把想要的字段都取出来，剩下的显式丢弃；不能整个解构时，把字段类型设计成 Option<T> 用 take()，或者用 std::mem::replace 填一个占位值回去。

Option::take 这个模式在 Rust 里非常常见，因为它把“所有权已经不归我了”这件事写进了类型：字段是 None 就表示这个资源已经被移走，后续代码读到 None 时会被类型系统提醒。相比在 C++ 里把指针置空然后靠人记住“这个对象不能再用了”，这是一次明显的进步。

借用与移动互相挡路的地方

部分移动和借用检查的交叉，是新手报错密度最高的区域。这里只讲所有权侧的原因，引用本身的规则不重复。

一个方向是“先借用，再移动”。

编译器拒绝得很合理：r 是一条指向“完整 p”的引用，而 p.name 被移走意味着那块内存的内容要被当成另一个值的所有权凭证带走，r 看到的世界就此塌了一角。Rust 不允许在有人借用的时候变更归属。

另一个方向是“从借用后面把值移走”，这是 E0507 与 E0508 的地盘。

& 给的凭证只有读写权限，没有释放责任，所以绝不允许把背后的值移走——移走了就出现“新主人负责释放，而原主人根本不知道有这回事”的悬空状态。定长数组那一行则说明：即便你拥有整个数组，按索引取元素也拿不到所有权，因为索引这个操作的产出是一个借用。想真正拿到堆上元素的所有权，得用 Vec::remove、Vec::drain、into_iter，或者把元素类型写成 Option<T> 再 take。

最后一条硬规则：实现了 Drop 的类型，它的任何字段都不能被移出，哪怕没有任何人在借用。

理由前面说过：Drop 实现随时可能读到任何字段，允许字段被移走就等于给它一个未初始化的输入。确实需要“析构前拆走成员”时，标准库给的工具是 std::mem::ManuallyDrop，它把释放责任显式交还给你，代价是必须用 unsafe 手工接管。

Drop 顺序：责任什么时候真正兑现

前几节反复说“所有者离开作用域时值被丢弃”，但“离开作用域”有不少细节。析构顺序（drop order）不是学术趣味，它直接决定锁什么时候放开、文件什么时候关闭。

基本规则：局部变量按声明的逆序析构

同一作用域内的具名变量，遵循“后构造的先析构”这个栈式次序。

选择逆序的理由是依赖关系：后声明的变量更可能借用或依赖先声明的东西，先析构后面的，才能保证它构造时看到的东西还活着。实现 Drop 时也应遵守这个假设——不要在字段的 drop 里访问另一个可能已析构的变量；同一个类型的字段则随整个值一起处理，字段的 Drop 在结构体的 drop 方法返回之后按声明顺序执行。

临时值的析构时机则更早：出现在语句里、没有被绑定到变量的值，在该语句结束时（也就是那个分号处）析构。

两次加锁的区别只在于守卫有没有绑到变量上：第一次产生的 MutexGuard 是临时值，语句结束就析构，锁随之释放，临界区只覆盖那条自增；第二次把守卫交给变量 g，g 的作用域到函数末尾，锁也就被占到末尾。临界区的长短不靠注释约定，而由“值住在哪个作用域”决定。同样的道理适用于文件句柄、事务连接与写缓冲：把资源包成带 Drop 的值，释放时机就变成了可见的语言事实。

提前释放与几个易混写法

需要显式提前结束责任时，有几种写法，它们的所有权行为差别很大，也是阅读源码时最容易看错的地方。

let _ = 变量; 要格外小心：下划线模式不做绑定，所以对位置表达式来说不发生移动，源变量照常可用——它既不是“丢弃”也不是“忽略”，实际上什么也没做。而如果右值是一个新建的临时值，let _ = String::from("tmp"); 就等价于“构造出来然后在这条语句末尾丢掉”，临时值不会被延长到作用域结束。想让值活到作用域末尾就写 let _x = ...，想立刻释放就写 drop(...)，两种意图都别用 let _ 混着表达，否则读代码的人只能靠背细节来判断。

还有两个边界情况：static 与 const 里的值永不调用 Drop；进程正常退出时运行时也不会挨个析构全局数据。所以不要依赖析构函数去落盘关键状态，显式调用 flush 之类的接口才是可靠做法。

函数边界：移出去再移回来

函数签名就是一次归属交接的声明：按值参数意味着所有权移进来，调用方的变量当场作废；按值返回意味着所有权移出去，接住的人成为新主人。这两步都只是栈上的常数代价，所以“返回一个大 Vec”在 Rust 里根本不值得犹豫，真正要决定的是调用方之后还需不需要这个值。

麻烦出现在“函数想把值用完再还回来”。三条正规出路：把需要的部分借用进来而不是整个移进去；返回元组把所有权带回来；把字段做成 Option<T> 用 take 取走，原位留下 None 作为“已被搬空”的类型化标记。

标准库里这类接口随处可见：Vec::pop、String::into_boxed_str、Mutex::into_inner、Vec::into_iter。它们的共同点是签名明说“这一步会把东西搬走”，让调用方在编译期就不得不面对归属变更。

归属的多种形态：所有权与智能指针

三条规则描述的是唯一所有者，但真实程序里常常需要多个位置访问同一份资源。标准库没有改规则，而是用带 Drop 的普通类型把归属模型扩展出几种形态。

类型 归属形态 复制/移动时发生什么 释放时机
T（栈值） 唯一所有者 移动，源作废 所有者离开作用域
Box<T> 唯一所有者，值在堆上 移动堆指针，语义不变 所有者离开作用域
&T / &mut T 借用，不是所有者 引用本身是 Copy 不负责释放
Rc<T> / Arc<T> 多个共享所有者 克隆只让计数加一 最后一个持有者消失

要点在于：Box 完整保留了唯一归属，它只改变数据住在哪里，所有权规则与移动语义原封不动；真正突破“同一时刻只能有一个所有者”的是 Rc 与 Arc，代价是释放时机从“作用域结束，编译期可证”变成“计数归零，运行时才知道”，并多出一整类问题——循环引用让计数永不归零，需要 Weak 打破；多个所有者要改同一份数据还得配合 RefCell 或 Mutex。经验法则因此很清楚：默认用唯一所有权，结构上确实需要共享时才引入计数指针。内部可变性与 Send/Sync 的取舍是别篇的主题。

用所有权表达设计意图

前面都是“规则如何约束写法”，反过来看更有价值：所有权是一种把资源归属写进类型的表达工具。

最直接的是 RAII。把文件句柄、套接字、事务、锁守卫包进一个带 Drop 的类型，此后代码里就不该再出现手工关闭；谁持有这个值、它的结束边界在哪里，就把释放时机说清楚了，编译器的析构顺序保证兑现。

其次是让“消费”体现在接收者上。

fn exec(self) 而不是 &self，等于在接口上宣布“这个查询对象到此为止”，重复调用不需要任何运行时状态检查就被禁止了。沿同一条思路可以走得更远：让不同状态对应不同类型，必填字段吃进构造函数，配置不全的对象压根构造不出来，“不合法状态无法表达”这件事就交给了类型系统。这与借用规则、生命周期标注并不冲突：借用回答“谁能读写”，生命周期回答“引用有效多久”，而所有权回答“谁负责收尾”。

从 C++、Go、Java 视角对照

维度 Rust C++ Go Java
默认赋值 移动，源失效 拷贝构造（可被优化） 整体按值复制 复制引用
移动 语言内置，编译期标记 std::move 后源仍可析构 无此概念 无此概念
释放时机 所有者作用域结束，静态可知 手写析构，需遵守规则五 GC GC
悬垂引用 编译期拒绝 靠约定与工具链 GC 下少见，但逃逸的指针仍存在 不存在裸引用

三点最容易迁移错的观念。C++ 的 std::move 是一次真正会执行的构造调用，移动后的对象仍处于“有效但未指定”状态，可以继续赋值也会被正常析构；Rust 的移动不是函数调用，它把源变量从当前绑定里抹掉，所以 C++ 里靠 moved-from 兜底的写法在这里换成了重新赋值。Go 程序员要把“值复制”和“归属转移”拆开：Go 的赋值同时做两件事（复制数据且原变量仍有效），Rust 的移动只转移不复制，想要复制得显式写 clone()。Java 程序员的转变在于：Rust 的变量默认就是那块数据本身，不是指向堆对象的引用，let a = b; 不会让两个名字共享一个对象；要共享语义得显式上 Rc，而“可随意复制的只读凭证”对应的是 &T。

典型报错与心智修正

报错 真实含义 首选修法
E0382 use of moved value 同一个值被取出两次 改借用；用完再重新赋值；确实要两份才 clone
E0382 borrow of moved value 移走之后又去借它 调整顺序，把借用在移动之前
E0505 cannot move out because borrowed 有人借用时变更归属 缩短借用范围，或只 clone 需要的字段
E0507 / E0508 想从借用或索引后面移出值 remove / drain / into_iter / take
E0509 想拆开实现了 Drop 的类型 字段改 Option<T> 配 take，或 ManuallyDrop
E0204 / E0184 想让带堆资源或有析构的类型 Copy 保留 Clone，调用点显式复制

这些报错背后的三条心智修正比修法本身更重要。第一，编译器说的不是“语法用错了”，而是“这块资源的释放责任现在有两个候选人或者没有候选人”，先问这一步之后谁是主人，再决定怎么改。第二，clone() 不是万能补丁，它把一次责任交接换成一次真实复制，循环和热点路径上要优先考虑改借用或调整归属方向。第三，签名先由语义决定：消费、修改、旁观分别对应 self、&mut self、&self，当你犹豫按值还是按引用，通常说明还没决定“谁负责收尾”。

小结

所有权的实质不是变量可见性，而是释放责任的唯一化：一个值一个主人，主人作用域结束就兑现析构。移动是这份责任的交接动作，栈上按位复制、堆上原地不动、源变量作废，代价极低但要求你把资源去向写明白。Copy 把“复制栈位就够”的类型从移动里摘出来，Clone 把昂贵的复制交还给显式表达，借用则在唯一主人之上临时开放读写而不改变归属。部分移动说明归属可以按字段拆解，drop 顺序说明责任何时兑现，函数边界上的进出说明接口就是归属声明，智能指针给出共享归属的有限扩展。落到实践上就几条：把每个签名当资源交接合同来写，用 Option<T> 表达“已被搬空”，用 self 表达“到此为止”，遇到 E0382 先追归属再考虑复制。
