Rust 中的零拷贝优化

本文属于《Rust 学习路线》第 51/68 篇
上一篇系列目录下一篇

在高性能 Rust 服务里，”零拷贝”是被提到频率最高的优化词之一。但拷贝并不只发生在系统调用边界上：一次随手的标准库接口选型、一轮迭代器链末尾的 collect，都可能把大块内存在总线上重新搬一遍。本文从拷贝的真实成本讲起，依次讨论切片借用、Cow、引用计数缓冲、mmap、内核内数据搬运、缓冲复用、序列化与 unsafe 的边界，最后落到”如何用 profiling 确认真的需要零拷贝”。适合写过 Rust、正在做 IO 密集或高吞吐服务的读者；读完应当能对自己项目里的内存复制点做出判断，并给出对应的改法。

谈拷贝时我们在谈什么

先把”拷贝”定义清楚。在机器层面，一次拷贝就是一串读-写指令：把源地址的一段字节搬到目的地址，通常由 memcpy 或 memmove 完成。”零拷贝”这个词容易被用玄，它并不是说数据永远不动，而是让一份数据从产生到消费的整个路径上，尽量少的经历多余的加载-存储穿越和地址空间切换。

拷贝的成本大致分三层。第一层是内存带宽。当代 CPU 的算力远高于主存带宽，搬一个大缓冲区会把读写总线占满，与其他计算抢资源；表面上”一行 memcpy”的代价，实际是许多缓存行来回穿越的总和。第二层是缓存污染。拷贝同时触碰源和目的两套内存：源端被读进缓存，可能挤掉真正的工作集；目的端更麻烦——刚拿到的匿名内存首次触碰会触发缺页，内核要把它零填充，随后写分配策略又把缓存行读进来再覆盖，等于白读一遍。第三层是地址翻译与页管理压力。大块搬运横跨许多页，TLB 与页表都要被翻动，后续正常访问也得在地址翻译上多付一点钱。

跨越内核边界时，成本还要加倍。普通的 read 调用把内核页缓存里的内容搬进用户缓冲区，至少是一次内核到用户的复制；随后把数据 write 到套接字，又是一次用户到内核的复制。经典语境里说的”零拷贝”，最初针对的正是这两次穿越；而本文会看到，Rust 的类型系统连用户态内部的复制也能消掉不少。下面这张图是”读文件再发往网络”最常见链路，标出了拷贝发生的位置：

切片与借用：语言自带的天然防线

Rust 的所有权与移动语义另有专文展开，本文不重复；只取其中与零拷贝最相关的一块：视图。&[T] 与 &str 的本质是”指针加长度”，拿借用不搬一个字节。对 Vec 做区间索引、对字符串做 split，得到的都是同一段内存上的视图；视图可以层层传递、反复切分，底层的字节始终躺在原地。这意味着”拿一个大缓冲、把其中的片段传来传去”这种常见模式，在 Rust 里天然就是零拷贝的，许多语言要么整份复制，要么直接传裸指针加长度、把安全性交给运气。

最直接的应用点是函数签名。只读取数据的函数，参数就该写成切片，而不是拥有所有权的容器：让所有方和临时视图都能零成本地调用。下面的例子对比两种写法——反面版本强迫每个调用方先准备一个自己的 Vec，正面版本连”取一段”都是免费的：

Cow 与延迟复制

切片解决了”完全不修改”的场景。可一旦修改掺和进来，视图就不够用了：你也许要在借来的数据上改点什么，也许根本不用改。std::borrow::Cow 把这个不确定性打包进返回值：Cow::Borrowed 装一个引用，Cow::Owned 装一份自己造的值。它的名字取自写时复制（Copy-On-Write），但请注意它和文件系统里的写时复制不是一回事：Rust 的 Cow 不是运行时机制，不会自动帮你延迟任何事，它是一种写法上的约定——由作者在每个分支诚实地判断”这里是否真的需要一份新数据”。

最典型的用例是归一化、裁剪一类的操作：输入已经合规就原样返回，不合规才拼装新值。

调用方拿到 Cow<'_, str> 之后，只读使用完全免费：它 Deref 到 &str，当普通字符串用即可。真要把值接管到一个长期位置，再调用 into_owned——借用态会复制一次，拥有态则原地收下。和”永远返回 String“的写法相比，Cow 把复制决策交给了数据本身：不改写的比例越高，省下的内存流量越多。

两个坑要点破。其一，把签名改成 Cow 不等于优化：若函数体内先调用 replace 之类必然产出 String 的方法，只是给复制套了一层枚举壳；Cow 的价值必须靠显式写出不改写的快路径来实现。其二，快路径的判断本身也要读一遍数据——上面例子里的 contains 就是一次全串扫描，对超长且多数输入都要改写的负载，先扫再复制反而更亏。收益取决于不改写分支的真实占比，这是测量的活儿，呼应最后一节的原则。

Bytes 式引用计数缓冲：便宜的 clone 与切分

切片和 Cow 都默认”内存的主人是别人，我只是看看”。异步网络服务里却常有一类它们都处理不了的场景：一条报文的头部和正文要交给两个不同的消费者，数据必须在处理函数返回后继续存活，而你不想深拷贝两份。这时需要第三种结构——共享所有权的引用计数缓冲，生态里 bytes crate（写作时 1.x 早已稳定）的 Bytes 就是代表。

Bytes 的内部形态可以理解为”引用计数分配块加一个视图句柄”：结构体自己只有指针、长度和元数据位置，字节躺在共享堆上。这个设计带来两个零拷贝的关键行为。第一，clone 只把原子引用计数加一，一个固定指令数的动作，与缓冲区大小无关——而 Vec<u8> 的深拷贝成本随长度线性上涨。第二，slice 以及 split_to、advance 这类切分操作产生的仍是同一段内存上的新句柄，O(1) 完成，不搬字节、不重分配。内存的释放交给最后一个持有者：每个句柄析构时把计数减一，归零的那次才真正回收。

可变的一侧由 BytesMut 承担：它是写入端与建造者，freeze 之后冻结成不可变的 Bytes 发出去。接收循环里的标准模式是：一个 BytesMut 持续累积读到的字节，凑齐一条报文就 split_to 切出、冻结、投递下游，剩余字节与容量原地保留，下一轮读取直接落进旧内存。物理分配次数因此远少于报文数量，报文在组件间的转交全是句柄与计数操作。

代价也要说清楚。引用计数是原子操作，高频克隆时计数器的缓存行争用会成为新热点，等于把内存带宽换成了同步开销，通常划算但不免费。更常见的问题是”切片钉住整块”：任何一个片段句柄还活着，整段底层内存就不能释放，把大缓冲的一小截切片存进长期缓存是隐蔽的驻留型泄漏——长存的字段应当复制成独立小值，或定期对缓冲做压缩整理。

藏在迭代器链与解析里的复制

工具讲完，对手是我们自己：业务代码里最常见的拷贝来源不是玄学，而是迭代器链和字符串处理里那些顺手的标准库方法。几个熟面孔：切片上的 to_vec 是一次整段元素复制；&str 上的 to_string 是一次新分配加整段复制；collect::<Vec<u8>>() 把迭代器吐出的每个字节写进一块新分配。它们单看每一步都不大，可一旦嵌进 map、flat_map 的逐元素闭包，就变成了”每个元素分配一次、链条末端再拼接一次”。

审计这类问题不需要高级工具：全局搜 to_vec、to_string、Vec::from、collect::<String>，逐个看调用频率与数据大小；重点盯逐元素闭包内部——那里出现分配就是红旗，先问一句能不能一路只传引用、到真要拥有值的地方再收集。

另一半问题是字符串解析。很多协议与文件格式本质是字节的：分隔符、长度前缀、魔数，全是 ASCII 字符。习惯做法是第一步先把字节转成 String 再 split，但这一步亏在两处：复制了一次全部内容，还附带一次完整的 UTF-8 校验——校验必须逐字节扫描才能确认编码合法，本身就是一趟读取。更经济的顺序是直接在 &[u8] 上解析：按字节分隔切帧，字段一路以 &[u8] 视图传递，只在确实要按文本理解某个字段时，才用 str::from_utf8 就学校验——它返回借用输入字节的 &str，不产生复制。这招能成立的依据是 UTF-8 的自同步性质：ASCII 字节不可能作为多字节字符的后续部分出现，所以在字节流里按 ASCII 分隔符搜索、切分，不会把一个字符从中间劈断。

若字段文本可能不合法、需要兜底，可以把 Cow 和 from_utf8_lossy 组合起来用：合法时借用原字节，非法时退化为新建的 String——复制只发生在少数坏数据上，而不是全部输入上。

mmap：让页表替你搬数据

要把文件内容变成内存可访问的数据而不做用户态复制，还有另一条路：mmap 在进程的虚拟地址空间与文件之间建立映射，访问触发缺页时，内核把页缓存中已有的页直接挂进页表，或为这页调度磁盘读取——数据从未”复制”到用户缓冲，两边共享同一块物理页。读一个文件并顺序扫描，走 read 是把页缓存内容往你的缓冲区里抄一遍再读抄本；走 mmap 则直接读原件。Rust 侧常用 memmap2 crate（写作时为 0.7 系列），Mmap 通过 Deref 给出 &[u8]，于是前文基于字节切片的解析代码可以原样复用。

但 mmap 的适用边界很硬，坑至少有四个。第一，缺页有成本：每新跨过一页都要付一次陷入内核的代价，对”读一遍就扔”的流式负载，read 大块搬运还有内核预读配合，反而更可预测；mmap 适合的是随机访问、超大文件、只碰部分数据、多进程共享只读映射这类场景。第二，文件被外部截断是致命的：映射只记录建立时的范围，若另一进程把文件截短，访问超出部分的页时内核投递的不是可恢复错误而是 SIGBUS，进程直接死亡，Result 拦不住它；纪律是被映射的文件不许原地截断，更新走”写新文件、原子改名、重新映射”。第三，生命周期纠缠：视图与 Mmap 绑定，塞进长命结构体或跨任务传递时借用错误家常便饭，用 Arc 包住映射能让视图独立生存，但那等于承认前文 Bytes 方案在这里更合身。第四，并发可见性没有承诺：其他进程的修改会在不确定的时刻被你看到，页与页之间没有原子性，可能读到新的长度头和旧的文件体，一致性快照要在应用层用版本号或双缓冲自己保证。

内核之内：sendfile 与 copy_file_range 的思路

对”静态文件发往套接字”这条路，还有一个与用户态类型完全无关的经典零拷贝答案：让内核自己搬。普通的”读文件再写 socket”两步走，数据路径是磁盘、页缓存、用户缓冲区、套接字缓冲、网卡，两次穿越内核边界、两次复制。sendfile 把中间一段省掉：内核直接从页缓存把数据交给套接字发送缓冲；在支持收集-散射写法的网卡上甚至可以更进一步——发送缓冲里只登记”引用页缓存中的哪些页”，让网卡自己 DMA 取数，用户线程从头到尾只有一个系统调用，碰都不碰载荷。copy_file_range 是同一思路的姊妹：把”文件到套接字”换成”文件到文件”，数据全程留在内核，在支持文件块共享的文件系统上还能退化成为纯元数据操作。

这两个都是操作系统接口层面的能力，Rust 里不需要专门的框架：libc crate 直接暴露原始绑定，循环推进偏移、处理部分写入这些活儿由我们自己负责。下面是一个 Linux 口径的完整示例，展示内核内搬运用起来是什么形状：

复用与池化：网络缓冲和对象池的边界

零拷贝收益的另一半在”别分配”。前文说过，新内存的首次触碰隐含着一轮缺页加零填充，这本身就是一次看不见的复制。请求驱动的服务里最扎眼的浪费，是每个请求新分配一个读缓冲、用完即弃：分配器的空闲链管理、元数据维护、偶发的归还内核页，全被请求量放大成常驻成本。修法朴素但有细节：把缓冲区挂在比请求更长寿的循环上，复用时用 clear 而非 drop——clear 只把长度归零、容量原地保留，下一轮写入落在早已缺页完成的物理页上，整个循环稳态后几乎不再触发新分配。

异步场景下同样的思路落在 BytesMut 上更顺：读满、切出一条报文、freeze 交给下游，自己留着剩余容量继续下一轮。判断复用是否真的划算，关键看缓冲区生命周期和循环生命周期是否匹配：两类请求必须并发处理时，硬共用一个缓冲等于把吞吐串行化，这时宁可维护一小簇缓冲轮转，或者干脆回到”克隆只加引用计数”的方案。

对象池是复用思想的放大版，但在 Rust 生态里它的适用面比名声小，失效场景值得列出来。其一，分配器本身就是一个池：主流分配器带线程本地缓存，小块对象的分配释放已经很便宜，自建池叠在上层，取出归还的记账很可能比一次 malloc 还贵。其二，池对象复用前必须复位：清零一个大缓冲恰恰是一次 memmove 级别的复制，容易”省了分配、请回复制”互相抵消。其三，跨线程归还要求池带锁或队列，热点路径上的争用往往劣于分配器的线程本地快路径。其四，借出的对象若以引用形态散落各处，随时可能有人没还；包上引用计数，池子又退化成泄漏。真正值得池化的场景相当窄：构造本身昂贵（预填充的大缓冲、初始化好的压缩上下文、现成的会话连接），且并发形状与池容量匹配。条件不齐，就别让池子进代码。

序列化：字节直读直写与中间结构的取舍

报文路径上”反序列化等于复制”似乎是默认假设，但它只在一种做法下成立。第一条路是结构体加 derive 宏：serde 家族负责编解码，生产力最高；代价是解码把每个字段物化成新的拥有值——String、Vec 挨个分配，热路径上”报文一份、模型一份”的双重表示本身就是一次全量复制。第二条路是字节直读直写：按协议手工做偏移运算，整数字段用 from_le_bytes、to_be_bytes 这类显式字节序方法逐段读出，只在真要长期持有值时分配。第一条路用复制换便利，第二条路用啰嗦换零拷贝，没有普适的胜者。

serde 其实还提供了骑在两条路中间的选择：借用式反序列化。只要结构体字段类型写成 &'a str、&'a [u8]，并且报文格式保证字符串字段在输入中就是连续字节（bincode、MessagePack 一类二进制格式通常满足），配合 #[serde(borrow)]，解码出来的值可以直接指向输入缓冲区，跳过字段物化：

字节直读路线上有两个必须避开的陷阱。一是别把字节缓冲整体转成结构体引用：普通结构体不保证字段顺序与填充布局，网络字节流也没有对齐承诺，这类”视图化”从前提上就不成立，逐字段按约定的字节序解码才是正解。二是协议尽量设计成”小头部加长前缀正文”：网关类程序只关心头部时，读完头部把正文作为 Bytes 切片原样转交，复制面积就只剩头部。权衡顺序也清楚：内部服务模型走第一条路，转发与高频路径评估第二、三条路，别为了零拷贝把字节运算撒到所有角落。

unsafe 的边界与正确性责任

前面的手段多数停留在类型安全区内，但零拷贝走到深处——把字节缓冲解释成结构、自研引用计数缓冲、包装内存映射——最终要靠 unsafe。这条边界值得单独讲清楚，因为零拷贝恰恰是最容易引入未定义行为的代码种类：编译器在 unsafe 里假设以下四件事你已全部兑现，兑现不了就是未定义行为，而不是”碰巧能跑”。

第一，对齐。构造 &[T] 要求起始地址是 align_of::<T>() 的倍数。字节缓冲只保证按字节对齐：把某个任意偏移处当成 &[u32] 读，偏移不是四的倍数时，无论你的目标平台此刻是否容忍非对齐访问，都已经是未定义行为——编译器有权假设对齐成立并据此优化。加上前面说的布局不确定性，”把字节流当成结构体”整条思路应当直接放弃，改用显式逐字段解码。

第二，范围有效。std::slice::from_raw_parts 接一个裸指针加长度，你给出的整段地址范围必须落在同一个已分配对象之内，且在引用的整个生命周期内保持可读。越界一字节——包括 mmap 场景里越过映射末尾——契约就破了，而且这类越界读取不一定立刻崩溃，它可能只是安静地把相邻内存当数据用。

第三，别名规则。可变引用必须独占：同时存在两个指向重叠区域的 &mut，即使你没写任何会让它们相遇的代码，也已经违反借用规则。想原地把一块缓冲切成两半分别处理，正解是安全出口 split_at_mut——它向借用检查器证明两半不重叠；如果连 split_at_mut 都表达不了你的需求，通常说明该换设计（多一层间接、或允许一次复制），而不是该加 unsafe。

第四，初始化。拿到指针不等于有合法值：未初始化内存不是任何类型的有效实例，用 MaybeUninit 表达”这里有空间但还不是值”，先写后读，读取前确保每个字节都被有意义地填过。

四条守则汇成一条工程纪律：unsafe 集中安放在一个小模块里，对外暴露安全的函数签名，把”调用方必须保证什么、本模块自己保证什么”逐条写进文档注释，再用覆盖边界长度、非对齐偏移的单元测试兜住。未定义行为难以事后排查，所以零拷贝改造里每一行 unsafe 都应当是被测量逼出来的，而不是风格偏好。

Profiling 先行：确认真的存在拷贝热点

以上所有手段都是解药，前提是病真的存在。拷贝的成本随数据尺寸与调用频率增长，而大多数程序的多数位置对拷贝根本不敏感；零拷贝改造却普遍让代码变难读——Cow 的分支、缓冲的生命周期、unsafe 的契约，都是留给未来的维护债。所以正确的顺序永远是：先测，定位，再改，改完复测。

信号有三类，对应三类工具。第一类，CPU 时间确实花在复制上：用 perf record 采集运行中的程序再绘制火焰图，glibc 的 memmove、memcpy 变体若以宽大色块盘踞图上，就是最直接的证据，cargo flamegraph 把这条流水线封装成了一行命令。第二类，复制占比不高但内存子系统吃紧，说明是隐形拷贝在污染缓存：看 perf stat 里的硬件事件，LLC-load-misses 与 dTLB-load-misses 若随流量异常上涨，往往意味着大块数据正在层级存储间反复搬家。第三类，分配本身是热点：可以用计数 GlobalAlloc 统计进程生命期内的分配次数与字节数，或者引入 dhat 这类堆分析 crate——高频且大对象的分配点，正是缓冲复用与引用计数方案的目标猎物。

两条注意。其一，微基准里数据常年待在缓存中，复制的真实代价会被系统性低估，结论要用接近生产的流量形状复核。其二，一次”理论上省掉一次拷贝”的改动如果在指标上毫无动静，说明瓶颈另有其处——可能是系统调用本身，可能是锁等待——应当回滚改动继续找，而不是叠加更激进的零拷贝。这里也要和跨语言性能对比的话题划清界限：本文不比 Rust 与其他语言谁更快，只比同一个 Rust 程序改前与改后。

小结

零拷贝的本质不是”不许拷贝”，而是让每一次字节的移动都有存在的理由。切片与借用消掉只读场景的复制；Cow 把复制推迟到真正需要改写的那一刻；Bytes 式引用计数缓冲用一次计数操作替代跨所有权的深拷贝；mmap 让页表替数据搬家，sendfile 一类接口把复制点挪出用户态；缓冲复用与克制的池化消掉分配隐含的复制；借用式序列化与集中安放的 unsafe 则守住最后那段边界的正确性。所有这些手段的入口都是 profiling：没有测量背书的零拷贝改造只是自我感动。建议的动手顺序按风险排：先审计迭代器链与逐元素分配，再谈 Cow、Bytes 与缓冲复用，最后才碰 mmap 与内核接口——越靠后的手段，越需要用数据说话。
