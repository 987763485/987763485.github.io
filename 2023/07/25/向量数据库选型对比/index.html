向量数据库选型对比

Milvus 的接口用法在入门那篇讲过，索引、分片、副本与监控怎么运维也在部署那篇展开过。本文只做另一件事：选型判断。先把需求侧的六项约束写成可判定的条件，再分清四种产品形态的责任边界，然后沿索引、元数据过滤、混合检索、多租户、一致性与写入实时性、运维成本逐条比对，最后给一次从需求倒推的推演和一张决策清单。本文不给基准测试数字与排名；不能确定在你所用版本上已经可用的能力，一律写成需要核实并实测。

选型前先落实六项约束

选型失败最常见的原因不是产品不好，而是比较开始得太早。手上只有一句“要做向量检索”，就把五六款产品的功能表逐格打勾，这种比法几乎必然得出“功能最多的最好”，而功能最多通常意味着依赖组件最多。正确的顺序是先把自己的约束写成可判定的条件，让多数候选直接出局。

数据规模：算字节而不是报条数

规模要换算成字节，内存和磁盘只认字节。原始向量的下界是条数乘维度乘分量字节数，float32 是当时的常见默认，每个分量 4 字节。

一千万条 768 维向量的裸数据就是一个可观的内存量，还没算 HNSW 的邻接表、IVF 的聚类中心与倒排链、原始向量副本和元数据列。工程上要在下界上乘一个放大系数，系数只能拿真实数据建一次索引量出来；量化压缩能让内存下降一到两个数量级，但那是结构性差异的说法，不是对某款产品的承诺。年增长率、保留策略和副本数也要一起代入。

查询负载：QPS、top_k 与延迟预算

平均 QPS、峰值 QPS、延迟口径必须分开写下来。写“要快”没有意义，要写成“检索阶段 p95 不超过某个预算”，而预算通常从上往下倒推：端到端体验目标扣掉模型生成、网络与序列化、重排序，剩下的才是向量检索的份额。另外两个容易漏的变量是 top_k 和批量形态：k 取 10 与取 100 的代价不在一个量级，一次一条与一次打包一百条对分片与线程模型的要求也完全不同。

过滤复杂度：这是最容易被低估的一格

很多团队把过滤当成“加个 WHERE 的事”，但它对选型的影响比索引类型还大。可按四档自评估：完全没有过滤；低基数枚举，比如文档语言、状态字段；高基数，比如按部门标识、权限标签集合做等值或包含判断；范围与逻辑组合，多字段 AND/OR 嵌套。基数越高、组合越复杂，“先取近似 Top-K 再过滤”就越危险，原因见后文过滤一节。还要写清选择率：筛掉 99% 与筛掉 1% 的两个条件，最优执行路径可能刚好相反。

一致性要求：谁需要立刻看见新数据

三个问题：写入后多久必须能被检索到；同一客户端写完立刻查，是否必须看见自己刚写的那条；相似查询的结果是否必须可复现。它们决定你能否接受最终一致，也决定要不要为强一致付协调与刷盘的代价。

团队运维能力与变更频率

最后一项约束常常最诚实：团队里有没有人值班、能不能处理一次跨节点的数据不一致、有没有做过备份恢复演练。变更频率也要评估——embedding 模型换一次就是全量向量重建，这是选型阶段必须演练过的动作。如果受合规约束必须私有化部署，托管服务这一整类候选直接出局。

四种形态对应四种责任边界

先按形态分类再排开比较，更有助于决策。形态决定的是责任边界：内存归谁管、索引正确性归谁管、扩缩容归谁管、数据丢了谁负责。

    A --> C[现有数据库的扩展]
    A --> D[对象存储加工自建索引]
    A --> E[托管 SaaS]
    B --> B1[Milvus 2.2 / Qdrant 1.x / Weaviate 1.x]
    C --> C1[pgvector 0.4 挂在 PostgreSQL 15 上]
    D --> D1[FAISS / hnswlib / ScaNN / DiskANN 库]
    E --> E1[Pinecone 等托管服务]
    C --> F[事务与备份复用原有数据库]
    D --> G[全部工程责任自己承担]
    E --> H[依赖外部网络与供应商]

专用向量数据库：为向量重写了存储与执行

Milvus、Qdrant、Weaviate 的共同点是把向量当成一等公民：索引面向向量，搜索请求原生带近似语义与 top_k，元数据过滤走自己的执行路径，分片与副本按向量分布设计。价值是一次性解决向量检索的工程问题，代价是多出一个全新服务，有自己一套配置、指标、升级流程与故障模式。架构差别也不小：Milvus 2.2 是存算分离、依赖对象存储与消息队列的分布式架构，另有单机部署形态；Qdrant、Weaviate 更偏单机或简单集群起步。要区分“产品支持分布式”和“你能负担分布式运维”，这两句在很多评审里被混着用。

现有数据库的扩展：pgvector 把向量变成一列

pgvector 是 PostgreSQL 的扩展，把向量作为列类型放进普通表，索引用 ivfflat 或 HNSW（0.4 版本已支持 HNSW）。它的杀手级优势不是检索性能，而是复用：数据、事务、权限、备份、连接池、监控全是现成的，过滤就是一句普通 SQL，不必跨系统同步两份数据。当向量只是既有业务表上的附属检索维度时，这个优势往往压倒一切。局限同样清楚：受所在数据库单实例规模的天花板约束，内存型索引与业务负载同处一个进程容易互相干扰；能不能装进你在用的托管数据库，取决于对方的镜像与白名单，必须逐个核实。

对象存储加工自建索引：把库当零件用

第三类不采购数据库，只采购一个检索库：FAISS、hnswlib、ScaNN、DiskANN，向量文件放对象存储或本地磁盘，在自己的进程或自建服务里加载索引，元数据另存，过滤与归并在应用代码里做。上限最高——索引结构、内存布局、分片粒度、冷启动策略全部可控；下限也最低——增删改的索引语义、并发与内存管理、持久化与恢复、多租户隔离全是你的责任，这些代码还会长期留在仓库里等人接手。选它之前要诚实回答一句：我们要的是一个检索引擎，还是要维护一个检索引擎。

托管 SaaS：把责任换成了依赖

Pinecone 这类托管服务把容量、副本、扩缩容、可用性都收进供应商，你只面对一个 HTTP 接口和命名空间，适合快速起步、团队小、不想碰基础设施的场景。要计入的代价有四类：查询跨越外部网络，延迟下界由网络决定；数据必须出门，敏感场景常在第一关就过不了；配额、限流、可用区分布只能靠文档与工单了解；长期依赖——数据可以导出，但你为它写的调用与容错逻辑很难平移。这些不是缺点，是交换条件。

一句话概括形态差异

专用库解决“向量检索怎么做才好”，扩展解决“能不能不新增一个系统”，自建解决“我要完全控制”，托管解决“我不想养这套东西”。认清这四种责任边界，多数候选会自动出局。

索引类型：内存、召回与构建时间的三角

索引类型同时决定四件事：常驻内存、召回上限、建索引耗时、查询可调精度。这四项不可能同时最优，改善一项通常要付另一项，所以本文把它画成一个三角形。

flowchart TD
    M[内存占用低] --> Q[查询召回高]
    Q --> B[构建时间短]
    B --> M
    X[没有任何索引能同时占住三个顶点]

HNSW：用内存换低延迟与高召回

HNSW 是图索引：把向量组织成多层可导航的小世界图，查询时从上层稀疏图粗定位、到底层稠密图细搜索，每次扩展多少候选由 ef（或 ef_search）控制，构建时每个节点连多少条边由 M、efConstruction 控制。它查询路径短、单跳代价小，同等召回下延迟表现好，且支持增量插入，不必为新数据重建索引。代价是图结构通常连原始向量一起常驻内存，参数调大会同时推高内存与构建时间。删除在图索引上普遍是标记而非物理擦除，长期高频增删会让索引质量退化，重建的控制手段各家不同，需要核实。

IVF 系列：先聚类再探桶

IVF 走的是另一条路：训练阶段把全量向量聚成 nlist 个簇，查询时只与最近的 nprobe 个簇做暴力比较。内存上可以只存聚类中心加压缩编码，因而天然适合量化。IVF_FLAT 在簇里保留原始向量，召回高、内存高；IVF_PQ 把向量切成子段量化成码本 ID，内存能下降一到两个数量级，但距离变成近似距离，召回损失要靠重排补救；IVF_SQ8 一类标量量化用更少位宽表示分量，在压缩率与精度之间相对居中。弱点是训练需要足够多样本，数据量太小或分布漂移时聚类质量不稳，nlist、nprobe 还要随规模重新评估；新增数据会先进入尚未合入正式索引的增量区，这段精度较低的行为要写进召回评估。

DiskANN 类：把大头放磁盘

当规模大到内存装不下、又不愿为此摊开太多分片时，磁盘索引是一等选项。DiskANN 这类设计把图与向量放在 SSD 上，内存只保留压缩编码与导航结构，用少量随机读换很大的单机容量。它的价值是内存成本，代价是延迟强依赖本地 SSD 的随机读性能与页缓存命中，冷启动、混部争抢 IO、云盘抖动都会直接反映到 p99。所以判断依据不是“支持不支持磁盘索引”，而是两个具体问题：数据能不能装进内存并留出安全余量；装不进时，能不能给它独占的本地 NVMe。

元数据过滤：前置与后置决定了结果对不对

过滤最容易出正确性问题。分歧只有一个：过滤条件在搜索过程的哪个阶段生效。

两种顺序的机制与后果

后置过滤先按相似度取回 top_k 个候选，再丢掉不合格的。实现简单，但结果条数没有保证：条件筛掉 99% 数据时，取回 20 个可能只剩 0 个。更隐蔽的是分布偏差：近似索引返回的候选本身就不均匀，某些租户、类别、时间段会被系统性筛薄，你以为召回率是 0.9，过滤条件下的有效召回却远低于整体口径。

前置过滤先用条件确定合法候选集合，或在搜索过程中同步判断，再在这个子集上做近邻搜索。结果条数有保障，代价是过滤集合与图或倒排结构的交集可能不连通：HNSW 上如果只剩一小片孤立节点满足条件，贪心搜索甚至到不了那里，于是延迟上升或召回下降。两种顺序都不免费，问题是在你的过滤形态与选择率下，这套实现会退化成哪种行为。

所以要分别测带过滤的召回率与结果条数达标率：只看整体 recall@k 的评测在过滤场景下几乎无效，因为它被大量无条件查询主导。

各形态在这件事上的天然差异

pgvector 这类扩展把过滤交给宿主数据库执行器：WHERE 与向量索引扫描如何配合、不满足条件时是否继续往下扫，取决于数据库的扫描策略。0.4 引入的迭代式索引扫描就是为“过滤后结果不足”准备的，代价是用扫描轮数换结果完整性。这类能力是否在你的版本与索引类型上生效要核实，对低选择率过滤的成本要实测。

专用向量数据库通常把元数据当独立子系统：哪些字段建了索引、过滤是在数据块级别剪枝还是在图遍历时逐点判断、多条件组合支持到什么程度，这些细节让同一句过滤在不同产品上的性能差距非常大。通用规律是等值且低基数的字段（比如租户 ID）适合做数据布局切分，比事后过滤更有效；范围条件与数组包含更接近逐点判断。各产品支持到哪一档、语法是什么，本文不列表，请以官方文档核实并用自己的数据实测。

自建索引时这件事完全回到你自己手上：常见做法是先由外部存储算出合法 ID 集合，再映射到索引内部。索引本身不认识过滤条件时，“过滤后不足 top_k 怎么办”就得自己回答，通常手段是放大候选数、按过滤集合分片建索引，或按租户拆索引，三种手段都会明显放大成本。

混合检索与多租户

向量加关键词：三种做法对应三种代价

纯向量检索有一类稳定的失败模式：专有名词、型号、代码片段、精确数字在语义空间里未必相近，靠 embedding 召不回来。把关键词通道（BM25 一类稀疏检索）与向量通道组合是很多 RAG 场景的刚需，组合位置有三种：引擎内双通道，同一存储里同时维护稀疏与稠密索引，一条请求里两路各出一批结果再融合；应用层融合，关键词走既有搜索引擎、向量走向量库，结果在业务代码里融合；召回后重排，先任一路召回再交给交叉编码器，细节属于重排序那篇文章。

怎么选看三个问题：融合策略是否需要反复调整，需要的话应用层最灵活、引擎内最省往返；关键词索引的中文分词与自定义词典能否覆盖你的领域，不能覆盖则“支持混合检索”打勾也没用；两路分数如何归一化，只能靠评测集定。年代约束也要强调：2023 年年中各家对稀疏向量、全文检索与融合排序的支持程度差别很大，有的仍在预览，务必核实你所用的版本。

多租户：隔离粒度决定成本曲线

多租户有两种完全不同的动机：业务上真需要按客户隔离数据与配额；或者想用租户维度把搜索空间切小，让高基数过滤变成数据布局问题。两者的最优粒度不一样。

粒度从粗到细大致是独立实例、独立数据库或集合、分区或命名空间、同一索引里的租户字段。越粗隔离越强、爆炸半径越小，但对象数量随租户数线性膨胀，索引、分片、元数据、连接的开销都跟着放大；越细越省资源，但一个大租户就能把邻居的延迟拖下去。

Milvus 的 collection 与 partition、Qdrant 的 collection 与 payload 分区、Weaviate 的 class、pgvector 的表与 schema、托管服务的命名空间都能承载租户概念，但语义与代价并不等价：能否独立扩缩容、能否单独删除或迁移、大租户会不会形成热点、租户数有没有上限，都要逐项问清。租户上千且规模悬殊时，“每租户一个集合”和“每租户一个字段值”会导向完全不同的运维体验。

一致性、持久化与写入实时性

这三件事常被合并成“支不支持实时更新”一句，其实可以分三层评估。

第一层是写入可见性：数据写进来了，什么时候能被检索到。常见做法是写入即进入可搜索的内存区，但这个区还没合入正式索引，搜索时怎么处理它直接决定新数据的召回质量。工程上更该关心“搜得到但搜不准”的窗口有多长，能不能用参数或显式操作压缩。

第二层是读取一致性：同一查询在不同节点、不同时刻返回的结果是否一致，是否保证读己之写。有的产品把一致性级别做成可选项，越强通常意味着越多的协调或等待；有的产品只描述默认行为，不给显式选择。这层要对照前文约束判断：更新后五分钟可检索就够，就不必为强一致付常驻代价；若要求改完立刻生效（比如权限撤回要进入检索过滤），就必须专门验证。

第三层是持久化与恢复语义：数据落在哪里、多久落一次盘、进程崩溃后丢多少、恢复要多久才能重新服务。这三问决定备份恢复演练怎么做，具体操作属于部署那篇文章，但选型时要当成约束——向量索引通常能从原始数据重建，重建时长是恢复时间的下界，而恢复时间是唯一在你最需要时才暴露的指标。

运维成本与二次开发

依赖组件数量与故障面

只数“要不要多部署一个服务”不够，要数完整链路：某些架构的向量库除自身进程外，还依赖对象存储、消息队列、元数据存储与若干角色节点，每一环都要有监控、告警、容量规划与升级流程，任何一环出问题都表现为检索不可用。嵌入式形态依赖复用既有数据库那一套，这项优势明显；托管服务则把依赖换成外部不可控项。评估方法很实际：把候选方案画成组件图，逐个问谁值班、谁是单点、备份在哪、上次演练什么时候，答不上来的格子就是隐性成本。

扩缩容、备份与再平衡

关注三件事：扩容是否在线、是否需要数据重分布、重分布期间查询是否降级；缩容与冷热分层是否可行；备份恢复走原生快照还是靠导出重建。这几项的差别在选型时看着抽象，出一次事故就非常具体。

许可、客户端与可替换性

Milvus、Qdrant 采用 Apache-2.0，Weaviate 是 BSD 系许可，pgvector 跟随 PostgreSQL 许可，托管服务是商业条款，具体条款与例外请以仓库和官网核实；许可影响的是你能不能分发、能不能做二次闭源改造。此外看客户端语言是否覆盖你的技术栈、REST 与 gRPC 是否完整、有没有批量导入与运维工具，这些决定能不能改；若要把某款产品深嵌核心链路，值得花一天读它的接口设计，再判断将来换掉的代价。

从需求倒推的一次推演

把前面的维度串起来走一遍。场景：企业内部知识问答，初期约八百万条 768 维向量，年增三四倍；峰值 QPS 几十量级；过滤既按部门与密级做高基数筛选，又按更新时间做范围限定；新文档发布后几分钟内可检索就够；团队三名后端，无分布式存储值班经验；数据不得出内网。

第一步排除：数据不出网，托管服务出局；养不起多组件集群，重量级分布式评为高风险，但规模会涨，不能直接划掉。

第二步检验最省的那条路：嵌入式方案运维成本最低，就拿它做定量检验。按第一节的式子算出单机内存需求的量级，还要留出数据库自身的共享缓冲、业务负载以及重建期间双份索引的空间；估算若接近机器规格上限，今天能跑不代表明年能跑。

第三步看过滤，这是本场景真正的杀手：高基数密级标签加时间范围是选择率偏低的典型组合，必须实测带过滤的召回率与结果条数达标率；结果不足时靠迭代式扫描能凑齐，却会拉长扫描成本，这笔成本能否被延迟预算吸收只有实测知道。

第四步留出口：结论不写成“永久选某一款”，而写成带条件的判断——当前规模下用低成本方案，同时约定触发重建或迁移的量化条件（内存水位、过滤后召回率、p95 延迟、重建耗时），并把向量访问收在一层检索接口之后，换引擎只改适配层。第五步把候选缩到两三个，用同一份评测集、同一套硬件、同一组过滤条件各跑一遍，测召回、延迟、内存峰值与构建时长。得到的不是排名，而是“在我们的约束下谁先撑不住”。

决策清单

不排序，只列必答题，每一项都填自己的数字与实测结果。

  • 规模：当前条数、维度、含索引与元数据的字节量，一年后与三年后的估算。
  • 负载：峰值 QPS、top_k、检索阶段 p95 与 p99 预算、是否有批量查询。
  • 过滤：属于哪一档、典型选择率、带过滤的召回率与结果条数达标率。
  • 索引：各候选索引的内存与构建时长实测、哪些参数查询期可调、删除堆积是否退化。
  • 实时性：新数据可见延迟、可见但不准的窗口长度、更新与删除语义。
  • 一致性：是否需要读己之写、权限撤回多久生效、崩溃后允许丢多少数据。
  • 多租户：隔离粒度、单租户热点、租户数量上限、能否单独删除与迁移。
  • 混合检索：稀疏与关键词通道在目标版本是否可用、融合策略能否反复调整。
  • 合规与运维：数据是否必须留在自有环境、组件清单与值班归属、在线扩缩容与重分布、备份恢复演练耗时。
  • 生态与退出：许可条款、客户端语言、运维工具；换引擎要改几处代码、评测集能否复用、能否双跑对比。

小结

选型顺序应该是先约束后产品：把规模、负载、过滤、一致性、运维能力写成可判定的条件，让候选自己出局，剩下的再细比。形态差异比功能差异重要，因为它决定责任边界；索引类型是内存、召回与构建时间的三角，取舍取决于你能给出多少内存与多少本地磁盘；元数据过滤决定结果对不对，必须在真实选择率下测带过滤的召回；混合检索、多租户、写入实时性与一致性要按所用版本核实，不能用宣传语代替文档。最后一句：横向对比要用自己的数据、自己的评测集、自己的硬件实跑一遍，数字不进表格就不算结论。
