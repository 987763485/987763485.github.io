Rust 操作数据库 sqlx 实践

本文属于《Rust 学习路线》第 41/68 篇
上一篇系列目录下一篇

写 Rust 的 Web 后端时，数据库访问层通常是要最先定下来的东西。本文以 2023 年 7 月时处于主线位置的 sqlx 0.6 为准，讲连接池管理、query! 宏的编译期校验原理、行映射与类型对应、事务、错误转换与迁移，最后讨论它与 diesel 的选型取舍。适合已经会用 tokio 与 async/await、准备在项目里引入 sqlx 的读者；读完应能搭出一个既异步、又在构建期就被检查过的数据访问层。

sqlx 的定位

sqlx 是一套异步的数据库工具集，写作本文时以 0.6 系列为主线。它与传统 ORM 的差别可以从两点看：第一，全链路异步，构建在 tokio 或 async-std 这类执行器之上，等待数据库响应时不占用线程；第二，query! 这类过程宏可以在编译期连接真实数据库，校验 SQL 的表名、列名、参数个数与结果类型，写错字段名在 cargo build 阶段就会报错，而不是等到线上查询失败。

它的名字也说明了它”不是什么”：sqlx 不生成实体代码，不做查询构建器 DSL，也不替你设计表结构。常见分工是：手写 SQL 与结果映射用 sqlx，表结构演进用它的迁移工具，异步运行时复用 tokio 生态，与 axum 这类框架配合时连接池直接放进共享状态。

引入时先在 Cargo.toml 里把特性选对。sqlx 的运行时与 TLS 实现在 0.6 需要显式指定，后端数据库也各自对应一个 feature；缺了 macros 就没有查询宏，缺了 migrate 就用不了迁移宏。

后端 feature 可以只开实际用到的那一个，全开会把四个驱动的编译都拖进构建时间。下文的示例均以 PostgreSQL 15 为主，MySQL 8.0 的差异会单独说明。

连接池与连接管理

sqlx 把连接池做成了一等公民：PgPool 是引用计数句柄，克隆廉价，整个应用共享一个即可，Web 框架里通常放进共享状态随请求传递。取连接、超时、回收这些策略都由构建池时的选项决定。

选项里值得注意的是 acquire_timeout：0.6 把早期版本含义含混的超时改名为”从池中取得连接的最长等待时间”，池满时协程排队，超过这个时间返回 PoolTimedOut，而不是无限阻塞。idle_timeout 与最大存活时间用来回收老化连接，过代理或防火墙的环境里尤其有用；还可以在关池连接前执行重置语句，避免连接带着脏会话状态回到池里。

如果几条语句必须落在同一个连接上（比如都要用到会话级状态），就显式 acquire() 拿到 PoolConnection 再复用；但大多数场景直接对池执行就够了，一次查询即一次取还。

实践中的坑集中在容量与占用上。其一，所有服务实例的 max_connections 之和不要超过数据库上限，多副本部署最容易忽略这一点，宁可把单池调小并加连接数监控。其二，池不能救慢查询：一条语句长期持有连接，等价于从池里偷走一个槽位，慢查询堆积后新请求全部卡在取连接上，表象是接口整体超时。其三，connect() 会立即建初始连接，配置错误当场暴露；connect_lazy 推迟到首次使用，但启动即失败总好过让第一个用户替你发现问题。

query! 宏与编译期校验

查询宏家族有三个入口：query! 返回带类型字段的匿名记录，query_as! 把结果映射到你自己的结构体，query_scalar! 只取第一列。它们的参数写法与普通 API 一致，用 $1、$2 这类占位符并按位置传参，MySQL 则写成 ?。

编译期校验的原理并不神秘：过程宏在展开时读取 DATABASE_URL 环境变量，连接数据库把这条 SQL 交给后端解析，拿回每一列的名称与类型，再据此生成结果结构体。也就是说，宏并不自己”猜”类型，而是让数据库告诉你类型。

flowchart TD
    A[写出 query! 与占位符] --> B[cargo build 展开宏]
    B --> C{连接 DATABASE_URL
让后端解析 SQL}
    C -->|解析成功| D[生成列名与类型的
匿名记录结构体]
    C -->|表不存在/列名错/参数不符| E[编译期直接报错]
    D --> F[运行时校验实际返回类型
不符则报类型不匹配]

收益很直接：拼错列名、少传参数、表被改名，都在编译阶段暴露；结果字段是静态类型，不需要再手工逐列取值加类型标注。代价同样明确：构建机必须能访问一个 schema 正确的数据库，cargo build 也因此多了网络往返，宏开得越多编译越慢。

于是有了离线模式：提交前用 sqlx-cli 生成查询缓存文件（0.6 时代是一个 sqlx-data.json），CI 里设置环境变量 SQLX_OFFLINE=true，构建时只读缓存、不连库；还可以用 prepare 的 check 模式检测缓存与代码是否漂移。改完 SQL 忘了重新生成，校验的就是旧查询的形状，这点要靠 CI 兜住。SQLite 项目也可以把 DATABASE_URL 指向一个含迁移的库文件，让宏直接对着它校验。

行映射与类型对应

query! 的匿名记录适合就地取值，但数据要跨层传递时，更好的做法是定义业务结构体。两条路：query_as! 在编译期把查询结果和你的结构体字段做匹配校验；或者使用普通 query_as::<_, T>() 配 FromRow 派生，只在运行时按列名取值。

FromRow 按字段名与列名一一对应，SQL 里请用 AS 把列别名对齐；列对不上会在运行时以缺列报错。这也是 query_as! 宏版本存在的意义——同样的错误它挪到了编译期。

类型对应以 PostgreSQL 为例整理如下，MySQL 的大方向一致，细节以各自后端文档为准：

数据库列 Rust 类型 需要的 feature
INT / BIGINT i32 / i64 内置
TEXT / VARCHAR String 内置
BOOL bool 内置
BYTEA Vec<u8> 内置
TIMESTAMP chrono::NaiveDateTime chrono
TIMESTAMPTZ chrono::DateTime<Utc> chrono
JSON / JSONB serde_json::Value 或 Json<T> json
UUID uuid::Uuid uuid
NUMERIC rust_decimal::Decimal decimal

几个反复踩到的点。可空列在宏推导里就是 Option<T>，反过来把非空列写成 Option 也能编译，等于放弃了约束检查，不建议。JSON 列想映射成自定义结构，包一层 Json<T> 并要求 T 实现 Serde 序列化，json feature 别漏开。TIMESTAMP 与 TIMESTAMPTZ 是两个不同类型，列定义和 Rust 类型要一次定死。至于把字符串列映射成自定义枚举，0.6 下需要自己为枚举实现编解码，多数项目更省事的做法仍是存字符串、在业务层转换。

事务与 PoolTransaction

事务从池或连接上开启：pool.begin() 返回一个 Transaction 值，它同样实现了执行器接口，把语句发到 &mut tx 上就都落在同一个连接、同一个事务里。提交是显式的 commit()；如果不提交就离开作用域，sqlx 会在析构时补发回滚，这一点让”提前返回即回滚”的错误路径天然安全。

写通用函数时会遇到类型问题：Transaction<'_, Postgres> 带着生命周期，作为函数参数或结构体字段存储时不如 Pool 顺手。sqlx 提供了别名 PoolTransaction<Postgres>，即 'static 生命周期的事务，适合需要在多层之间传递的场景；只在一条调用链里用的话，借用版本的 &mut Transaction<'_, Postgres> 就够。0.6 的执行器大多要求 &mut，忘记写 mut 会得到一串 trait 不满足的报错，这是新手最常见的卡点。

需要留意的还有两条。事务期间它独占池里一个连接，长事务等于长期占坑，前面说过的池耗尽问题在事务上会被放大；另外事务不会跟着池”自动续上”，同一个 Pool 上的两次独立查询分属两个连接、两个事务，跨语句的原子性只能靠显式 begin 来保证。隔离级别等开启选项各后端略有差异，以你锁定版本文档为准，这里不展开。

错误处理与类型转换

sqlx 对外统一抛 sqlx::Error，它是一个顶层枚举：数据库原生错误包在 DatabaseError 里，可以进一步取后端返回的错误码、约束名等细节；fetch_one 没查到行返回 RowNotFound，这是”查不到”而不是空值，语义上更接近错误分支；池等待超时是 PoolTimedOut。剩下还有协议、类型转换等变体，多数框架层代码只需要关心前三类。

实践建议有三条。第一，用 fetch_optional 替代”fetch_one 加 RowNotFound 分支”，把”可能没有”显式写进返回的 Option，代码意图更清楚。第二，在仓储层就把 sqlx::Error 转成业务错误枚举，用 thiserror 包装、? 自动转换，别让 HTTP 层直接 match 数据库错误变体——那是把库的方言泄漏给接口。第三，错误码（如 PostgreSQL 的 23505 唯一冲突）适合做少量有业务含义的判定，把整张码表搬进项目是另一个话题，本文不展开。顺带一提，rows_affected 对 UPDATE 返回的是实际改动的行数，MySQL 默认口径下”值没变”的行可能不计入，判存在性时想清楚语义再写。

迁移：migrations 目录与 migrate!

schema 演进交给 sqlx 的迁移体系。约定很简单：仓库里一个 migrations 目录，每次变更一个带时间戳前缀的 SQL 文件，按名字排序依次执行；库里会有一张 _sqlx_migrations 表记录已应用版本与文件校验和。

应用侧可以在启动时用 sqlx::migrate!("./migrations") 把迁移目录编译进二进制再执行，部署产物不带散文件；也可以完全依赖发布流水线跑 cargo sqlx migrate run，应用启动只校验版本是否一致。两种模式取舍看团队：前者省事但多实例并发启动时迁移与应用交错，后者把变更窗口集中、可控性更好，笔者倾向在生产上后者。

要注意的坑：其一，0.6 时代没有 down 迁移，改了已经应用过的 SQL 文件，校验和对不上会在下次运行时直接报错，正确姿势是追加新迁移修正，而不是回头编辑旧文件。其二，query! 的编译期校验依赖数据库 schema 与迁移同步，本地忘跑 cargo sqlx migrate run，宏报的”表不存在”其实是在提醒你迁移没跟上。其三，大表加索引、回填数据这类长操作放进迁移前，想清楚锁与耗时，必要时拆成多个小迁移，让发布可以分批推进。

prepared statement 与性能注意

普通 query() 与宏版 query! 在 PostgreSQL 后端走的都是扩展查询协议，语句会被 prepare；sqlx 在每条连接上维护 prepared statement 的缓存，同一段 SQL 文本反复执行时能命中缓存、省掉重复解析。需要手工复用一个语句对象时，用 pool.prepare 或 prepare_cached 拿到 PgStatement 再多次执行。缓存是连接级的，连接重建后自然清空。

性能上几个反复出现的模式值得警惕。最典型的是 N+1：循环里逐条 fetch_one 会把池占满、把延迟叠加，集合查询尽量用 ANY($1) 这类数组参数一次取回，MySQL 没有等价的数组占位符，只能按 id 个数动态拼占位符再 bind（宏版写不出这种运行时拼接，得退回普通 query()）。其次是取数范围：fetch_all 会把结果全部读进内存，大结果集应改用 fetch 配合 Stream 逐行流式消费，但游标会占住连接直到流结束，未消费完之前别再在其上发起第二个查询。再就是编译期宏的代价集中在构建端，线上路径里宏生成的查询与普通查询没有额外开销，性能评估的重点仍然是索引、连接数与查询形状，而不是宏本身。

与 diesel 的取舍

Rust 数据库访问层另一个绕不开的名字是 diesel。两者都强调编译期安全，但来源不同：diesel 的安全来自查询构建器 DSL——先跑 diesel print-schema 把表结构生成为 Rust 类型，之后每个 DSL 调用都在类型系统里检查；sqlx 的安全来自数据库本身——你写原始 SQL，构建期拿真实库校验。前者的代价是代码生成与 DSL 学习成本，后者的代价是构建期对数据库的依赖，离线模式可缓解。

维度 sqlx 0.6 diesel 2.0
SQL 表达 手写原始 SQL 类型化 DSL 为主
编译期校验 连真实库校验 靠生成的 schema 类型
异步 原生 async 主体同步，异步扩展尚年轻
代码生成 不需要 print-schema 必须
动态查询 运行时拼接退回普通 API DSL 天然可组合
迁移工具 sqlx-cli 内置 diesel CLI

异步这一条在 2023 年权重很高：diesel 2.0 三月发布，但连接模型是同步的，面向 tokio 的异步支持由单独的社区库承担，成熟度还在爬坡。从 HTTP 入口到数据库整条链路都跑在 async 任务上的服务，sqlx 是目前更顺的选择；反过来，团队偏同步栈、查询以按类型拼装为主、又不希望构建依赖数据库，diesel 的类型化 DSL 更省心。补充一句边界：本文只站在使用者角度讲行为与原理，过程宏本身如何实现、怎样写自己的 derive，不在讨论范围内。

小结

sqlx 用一套朴素的设计换来了很实在的收益：SQL 你自己写，异步原生跑，错误尽量在编译期暴露。实践主线上，连接池进共享状态、acquire_timeout 与总连接数要做容量核算；查询宏优先，配 FromRow 与准确的类型映射，可空列用 Option；事务显式 begin、commit，靠析构回滚兜底；错误在仓储层收敛成业务枚举，别让 sqlx::Error 穿透到接口层。迁移没有 down 方向，旧文件不可改写，这一点要从第一天就遵守。构建期依赖数据库是宏模式的阿喀琉斯之踵，离线缓存与 CI 的 prepare check 建议第一时间配好。选型上不必站队：链路全异步、以手写 SQL 为主选 sqlx；类型化构建器、同步栈选 diesel，两者都能把”编译过大约就对了”往前推一大步。
