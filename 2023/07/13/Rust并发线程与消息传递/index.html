Rust 并发：线程与消息传递

本文属于《Rust 学习路线》第 30/68 篇
上一篇系列目录下一篇

并发程序的难点从来不是”把任务分给多个线程”，而是”让多个线程在同一份数据上不打架”。很多语言把这件事交给运行时的自觉，数据竞争要等到线上事故才暴露。Rust 的取舍不同：它把大部分并发错误提前到编译期，用类型系统告诉你哪些值可以安全地跨线程流动。本文面向熟悉所有权与借用、第一次接触并发模块的读者，围绕标准库的 thread::spawn、mpsc 通道、Arc<Mutex<T>> 与 Send/Sync 展开，讲清它们如何配合、各自的边界在哪。异步运行时的话题留给 tokio 相关文章，所有权与智能指针的基础也不再重复。本文以 Rust 1.70 的稳定语法为口径，不使用 unstable 特性。

一、thread::spawn 与 JoinHandle

Rust 标准库的线程模型直白得近乎朴素：std::thread::spawn 接收一个闭包，在新线程上运行它，返回一个 JoinHandle。除了闭包捕获的数据，新线程与父线程默认没有任何共享。

JoinHandle<T> 里的 T 就是闭包返回值类型。join 的签名返回 Result<T, Box<dyn Any + Send>>：子线程正常结束给你 Ok(T)，panic 给你装着载荷的 Err。也就是说 join 不只是”等待”，还是一次跨线程的错误交接——这正是第八节要展开的话题。

这里有一个容易被忽略的陷阱：主线程退出时，进程就结束了，它不会等任何后台线程。

程序输出往往是一片空白。子线程是脱离（detached）的，标准库不为它提供隐式 join。要等它，只能显式调用 join，或者用别的方式保证主线程不先走。这一点和某些语言的守护线程语义不同。

spawn 对闭包有一条硬性约束：不能持有对父线程栈上变量的引用。因为新线程可能在父线程栈帧销毁之后仍在运行，引用悬垂会破坏内存安全，编译器干脆禁止这种写法——这正是下一节 move 语义登场的地方。

二、move 闭包与所有权转移

新线程不能借用父线程局部数据，那闭包想用到外部变量怎么办？答案是：把变量所有权整个搬进闭包，这就是 move 关键字的作用。

如果不写 move，闭包默认按最小权限捕获变量：能用引用就用引用。一旦某个变量需要跨越线程边界、活过父线程的作用域，编译器就会报错，提示你缺少 move 或生命周期不满足 'static。加上 move 后，闭包把它捕获的变量所有权一次性拿过来，父线程随后再也用不了这些变量。

这是最常见的并发报错之一。意思很直白：闭包要在新线程上活着，而它借用的 data 归主线程所有，主线程一走 data 就没了。修法要么加 move 转移所有权，要么改用后面会讲的 Arc 共享所有权。

move 语义决定了 Rust 并发的第一原则：默认不共享，要共享就显式转移所有权。它把”谁拥有这份数据、谁负责释放它”在编译期钉死。搬动只是所有权转移：堆上的内容不会复制，变的只是栈上的指针与长度字段，对 Vec、String 这类拥有堆内存的类型开销极小。

并非所有类型都能这样搬。Rc<T>、RefCell<T> 不是 Send 的，被 move 进新线程会直接被编译器拦下（第五节细说）。当多个线程确实要读写同一份状态时，转移所有权就不够了：要么用消息传递把数据一份份发过去，要么用下一节的 Arc<Mutex<T>>。本文先讲消息传递，因为它是 Rust 更推崇的并发风格。

三、mpsc 通道：用消息传递替代共享

Rust 的并发口号是”不要通过共享内存来通信，而要通过通信来共享内存”。标准库 std::sync::mpsc 提供多生产者、单消费者通道（multiple producer, single consumer）：调用 mpsc::channel() 得到一对端点，Sender<T> 负责发送，Receiver<T> 负责接收，T 是流过通道的消息类型。

三个关键点。第一，Sender 可 .clone()，每个克隆是同一通道的独立入口，这就是”多生产者”的由来；Receiver 则不能克隆给多个线程消费，否则消息落到哪个消费者不确定。第二，消息是”移动”进通道的：tx.send(x) 之后 x 归通道所有，发送方再也用不了它，与第二节的 move 一脉相承，也是没有数据竞争的根本保证。第三，接收端迭代 rx 会阻塞直到所有 Sender 都被 drop，别忘了 drop(tx)，否则接收循环可能永远等下去。

Receiver 还提供粒度更细的方法：recv() 阻塞取一条，try_recv() 不阻塞、取不到立刻返回 Err(RecvError)，recv_timeout(Duration) 给阻塞加上限，便于把”等待消息”嵌进更大的事件循环。

sync_channel 的容量 n 是缓冲区上限：超过时 send 阻塞，把生产速度”压”到与消费一致，这种机制叫背压（backpressure）。它把”生产者跑太快”的失控变成可预测的节奏，代价是生产者线程可能被挂起。若不希望阻塞，Sender 提供 try_send：缓冲区满时立刻返回 Err(TrySendError::Full(msg))，把消息原样还给你，由你决定丢弃、重试还是降级。无界通道没有容量概念，谈不上 Full，但接收端已关闭时 send 会返回 Disconnected。选哪种通道，本质是在”吞吐优先”与”内存可控”之间权衡。

四、Arc<Mutex>：需要共享状态时

消息传递优雅但并非万能。当多个线程频繁读写同一份可变状态（共享缓存、统计计数），用消息传递反而绕。Rust 的共享状态方案是 Arc<Mutex<T>>，把两个原语叠在一起各司其职。

拆开看：Arc<T> 是原子引用计数指针，多线程各持一份，计数增减用原子指令，最后一个持有者 drop 时才释放堆上数据；Rc 计数非原子、跨线程会出错，多线程必须换 Arc。Mutex<T> 是互斥锁，把数据 T 锁在里面，任何时刻只有一个线程能拿到锁。

微妙之处在于 lock() 返回的不是 T，而是 MutexGuard<T>——实现 Deref/DerefMut 的智能守卫。你像用 &mut T 一样用它（*num += 1），离开作用域时由 Drop 自动解锁。这把”配对调用 lock/unlock”变成”守卫的生命周期就是临界区”，从类型层面消灭了忘记解锁这类 bug；反之若让守卫活得比预期久，就会意外延长持锁时间。

锁粒度

最危险的写法是把整个结构体塞进一把大锁，所有互不相干的操作都要排队——这叫粒度过粗，并发会退化成串行。锁粒度指临界区覆盖的数据范围与持锁时长，理想是”覆盖数据尽量小、持锁时间尽量短”。

Stats 把两个计数器分属两把锁，命中路径和错误路径互不阻塞。缩小粒度还有更直接的手段：只在真正修改数据的那一两行持锁，把耗时的准备工作（计算、I/O）放到锁外做，算完再进锁写结果。反过来，拆多把锁又要当心”按不同顺序获取多把锁”造成的死锁，需要约定固定的加锁顺序。共享状态不是不能用，而是要克制：能靠消息传递避免的共享，就不要引入锁。

五、Send 与 Sync：编译器如何拦截数据竞争

前面反复出现”不是 Send 会被拦下”，这一节讲透这层机制。Send 和 Sync 是两个 marker trait（标记特征），没有任何方法，纯粹是给类型贴的”标签”，供编译器在跨线程操作时检查。

Send 表示这个类型的所有权可以安全转移到另一个线程：thread::spawn 要求闭包 Send，进而要求它捕获的数据 Send。绝大多数拥有独占所有权的类型自动 Send，例外是 Rc、裸指针、绑定线程资源的句柄等。Sync 表示 &T（共享引用）是 Send 的，即多个线程可同时持有只读引用而不出问题；形式化一点，T: Sync 大致等价于 &T: Send。

关键在于：数据竞争不是靠运行时运气避免的，而是编译期由类型系统证明不存在的。看两个典型报错。

Rc 的计数增减不是原子操作，两个线程同时改会竞争，所以标准库干脆不给 Rc 实现 Send，逼你换用原子的 Arc。RefCell 的借用标志读写也不是原子的，跨线程共享会有竞争，因此不是 Sync；要在多线程里做内部可变，得换成 Mutex<T> 或原子类型。这就是第四节用 Arc<Mutex<T>> 而不是 Arc<RefCell<T>> 的原因——后者通不过 Sync 检查。

Send/Sync 通常自动成立：成员都 Send，含这些成员的 struct 也 Send。手写 unsafe impl Send 只在极少数底层封装里才需要，一旦手写就把安全责任从编译器转移到你自己身上。理解了这两个标签，前四节里”为什么这样能编译、那样不行”就有了统一答案。

六、scoped thread：借用父线程数据的合法方式

spawn 的闭包只能 move、不能借用父线程栈上的数据。但有些场景确实想让子线程临时借用父线程局部变量而不必搬走所有权。thread::scope 提供这种能力，1.63 起进入稳定版。

data.chunks(4) 产出借用切片，子线程直接引用而不需要 move——这在普通 spawn 下会被生命周期拒绝。thread::scope 之所以安全，是因为它有硬性保证：作用域返回前会 join 掉所有子线程。既然借用者都在 data 存活时结束，悬垂引用不可能发生。核心思路是用结构化作用域把”借用存活期”和”子线程存活期”绑在一起，从而免去 'static 约束。

代价是子线程不能逃逸出作用域，无法把 handle 存到 scope 之后再 join。对照记忆：spawn 适合长期存活、自带数据的后台线程，scope 适合”算完马上回收”的临时并行任务。

七、线程池与 worker 模式

为每个任务 spawn 一个线程是浪费：线程创建有开销，数量失控还会拖垮调度。线程池的思路是预先固定一批 worker 线程，让它们从一条共享任务队列取活干，完成后再领下一个。这正是 mpsc 的典型应用——Receiver 不能克隆给多个消费者，于是把它包进 Mutex，让每个 worker 轮流短暂锁住取一条任务。

Job 用 Box<dyn FnOnce() + Send + 'static> 表示”能跨线程搬运、只执行一次、不借外部数据”的闭包，这是任务能进队列的类型前提。worker 循环里最关键的是持锁范围：只在 recv() 那一瞬间锁住 Receiver，拿到任务立刻解锁，于是漫长的执行过程不阻塞其他 worker 取活——这是第四节锁粒度原则的落地。所有 Sender 都不再存活时 recv 返回 Err，worker 自然退出，这就是优雅关停信号。

八、跨线程 panic 与传播

线程之间是隔离的：子线程里一个未捕获的 panic 不会直接让主线程也 panic，它只终止子线程本身。但如果没人 join 它，这个崩溃就悄无声息地丢了，主程序还以为一切正常。前面提过，join 返回 Result，正是把子线程成败交回父线程的通道。

downcast_ref 从 Box<dyn Any + Send> 里还原 panic 载荷的具体类型：panic!("文本") 携带 &'static str，自定义载荷可能是别的类型，取不出时应回退到通用处理。实践中有三种态度：一是 join().unwrap()，把子线程 panic 升级为主线程 panic，适合”子任务失败则整个流程没意义”；二是像上面这样 match，记录日志后决定继续还是中止；三是对线程池这类不该因单个任务崩掉的场合，用 catch_unwind 包住每个任务，防止一个 panic 击穿 worker。还要留意 Mutex 的副作用：某线程持锁期间 panic 会让锁”中毒”（poisoned），后续 lock() 返回 Err，提醒你数据可能停在半修改的中间态——此时盲目 unwrap 守卫反而危险。

九、何时改用 async 而不是开线程

线程是操作系统的重资源，每条约占固定栈空间，成千上万个并发连接硬扛会把内存和上下文切换压垮。当并发单元多、且大部分时间在等待（网络、磁盘）时，async/await 更合适：许多 future 复用少数几个线程，等待时让出执行权而非阻塞线程。反过来，CPU 密集、需要真正并行计算，或要调用阻塞的同步代码时，就该用线程。本文的 thread/mpsc/Arc<Mutex> 处理”真并行”与”跨线程共享”，tokio 那套异步 spawn/channel 处理”高并发 I/O 多路复用”，两者是分工不是替代：瓶颈在等待用 async，瓶颈在算用线程。

小结

本文沿着”默认不共享、要共享就显式转移”这条主线走完核心工具：thread::spawn 与 JoinHandle 起线程、收结果，move 把所有权搬进线程，mpsc 用消息传递替代共享、有界通道提供背压，Arc<Mutex<T>> 为共享可变状态提供受锁入口，Send/Sync 在编译期挡下数据竞争，thread::scope 让借用父线程数据成为可能，线程池演示了这些原语的组装。实践建议三条：优先用消息传递表达数据流向，确实共享才上锁并缩小锁粒度；别滥用 spawn，量大且以等待为主的任务改用 async；认真对待 join 的 Result 和中毒的锁，别让子线程 panic 无声消失。
