Rust trait 对象与动态分发

本文属于《Rust 学习路线》第 14/68 篇
上一篇系列目录下一篇

Rust 没有内建的继承，也没有垃圾回收堆上的接口指针，但”对某种行为编程、运行时再决定具体实现”的需求照样存在，它在 Rust 里的答案就是 trait 对象与动态分发。本文从静态分发与动态分发的本质差异讲起，拆到宽指针的内存布局与 vtable 的内容，逐条解释对象安全规则，再讨论所有权形态、向下转型、性能代价，以及插件式架构和 async 方法在 2023 年遇到的边界。适合已经熟悉泛型与 trait bound 的读者（泛型与约束本身另见《Rust 泛型与 trait》一文），读完你应当能对着任何一条与 dyn Trait 相关的编译错误，说出它踩中了哪条规则。全文以写作时最新的稳定版 Rust 1.70 为口径。

静态分发与动态分发：两条调用路径

编译器会为每个遇到的具体类型把 broadcast 单独生成一份，这叫单态化（monomorphization）：程序里同时用了短信通道和邮件通道，就会得到 broadcast::<Sms> 与 broadcast::<Email> 两份特化代码，调用处是对已知地址的直接调用，可被完整内联。这就是静态分发——调用目标在编译期定死，运行期几乎没有额外开销，是 Rust”零成本抽象”的典型样本。

第二种是 trait 对象：

dyn Notify 是一个类型，但它不是具体类型：编译器不知道它背后的数据有多大、方法该跳到哪里，所以它只能待在指针里被携带。调用处拿到的 t 没有编译期已知的具体类型，只能在指针附带的一张表里查出 notify 的实现地址再跳转——这就是动态分发。

两者的本质差异在于”调用目标何时确定”。静态分发为每个具体类型各确定一次，机器码份数随类型数增长；动态分发只有一份调用代码，把”用哪个实现”的决策推迟到运行期，代价是查表和一次间接跳转。表达力上它们也不等价：Vec<T> 要求元素同为 T，想把短信和邮件混进同一个集合是无能做到；Vec<Box<dyn Notify>> 天然容纳异质集合。很多时候我们选动态分发并不是因为它快，而是因为需求里那个”异构”恰恰只有它能直接表达。

这里先拆一个迷思：静态分发未必总是赢家。如果 notify 内部本来就在做网络 IO，间接跳转省下的几个周期不成比例；反过来，泛型在几十处被不同实例化时，机器码副本近乎线性膨胀，编译时间与二进制体积都要付账。性能问题后面专门讨论；本节只需记住：单态化站在静态分发一侧，vtable 站在动态分发一侧，后面所有章节都围绕这两个词展开。

从裸 Trait 到 dyn：一段弃用史

老读者可能记得，早期的 Rust 里 trait 对象不写 dyn：Box<Notify>、&Notify 直接裸用 trait 名当类型。这种写法有两个麻烦。其一是歧义：trait Foo: Bar 里的 Bar 是父 trait 约束，fn f(x: &Bar) 里的 Bar 是类型，fn f<T: Bar> 里的 Bar 又是约束——同一书写形式承担三种角色，读者必须靠上下文判断。其二是命名压力：trait 名与类型名共享命名空间，裸用堵死了未来为这类形态保留关键字的路。

RFC 2113 给出的解法是引入 dyn 关键字，把”此处是动态分发的 trait 对象”显式写在类型位置上。Rust 1.25 在 2018 年春天接受了 dyn Trait 语法，同时用 bare_trait_objects lint 把裸写法标记为弃用；稍后的 1.27 把 dyn 正式保留成关键字，2018 edition 的迁移工具可以把旧代码批量改写。到今天（Rust 1.70），裸写法仍然能编译，但会收到一条”加上 dyn”的警告；官方文档与主流代码库已完全转向新语法，读旧书旧博客时见到 &Trait 自行在脑中补上 dyn 即可。

顺便澄清两点。第一，dyn 只出现在类型位置：Box<dyn Notify>、&dyn Notify 是类型，而 fn f<T: Notify> 里的 T: Notify 是约束，那里轮不到 dyn 出场，写 T: dyn Notify 反而是错的。第二，dyn 修饰的是分发方式，不是”值可变”——&dyn Notify 照样是不可变借用，可变性由 &mut 决定。至于组合形态，dyn Notify + Send + Sync 合法，它把自动 trait 并入对象类型，只影响指针能否跨线程搬运，不改变方法调用的查表机制；而混入普通 trait，如 dyn Notify + Default，在 2023 年仍不受支持，会直接报编译错误。

最后立一个贯穿全文的提醒：trait 对象类型本身不是 Sized 的，值必须被 &、Box、Rc 之类的指针托着。这不是语法禁忌，而是内存布局层面的硬约束——下一节用指针的字节数说清楚。

trait 对象是宽指针：数据指针加 vtable 指针

vtable 是编译器生成的静态数组，每个”具体类型配上 trait 对象类型”的组合一张。String 当 dyn Notify 用与 Sms 当 dyn Notify 用的表不是同一张，但每一张都在编译期一次性生成、放进程序的只读数据段，运行期只付查表的成本，没有构造成本——动态分发并不自带反射。

表里装了什么？内部布局属于编译器私有细节，没有稳定 ABI，但大致构成是：一项 drop 胶水，告诉持有者如何销毁这个它已不知具体类型的值；具体类型的大小与对齐，因为类型擦除之后，持有 Box<dyn Notify> 的一方不知道值占多少字节，销毁、扩容、移动都得回表来问；然后是 trait 中每个可分发方法按声明顺序排列的实现函数指针；当对象叠加了多个约束时，还会连带存放次级表的指针。注意”可分发方法”这个限定——被对象安全规则排除的方法根本进不了表，这正是下一节的主题。

一次 n.notify(msg) 在指令层面的流程大致是：从宽指针取出 vtable 地址，按方法在表中的固定偏移读出函数指针，把数据指针作为第一个参数（也就是 self）放进寄存器，执行一次间接调用。x86 汇编里它长得像 callq *0x18(%rax)——目标地址不在指令里编码，要到执行那一刻才知道。查表本身几乎免费（表项在只读段，缓存友好），真正埋下性能伏笔的是这个间接跳转和它带来的内联失效，我们到性能一节再算细账。

回到”为什么必须把值装在指针里”。dyn Notify 是不定长类型（早年的叫法是 DST，动态大小类型）：大小编译期未知，不能占据栈上的变量槽，不能直接做数组元素。Rust 的处理方式是把信息拆成两半——值的本体放在堆上或别处，指针这边携带定长的”地址加元数据”。切片的元数据是长度，trait 对象的元数据是 vtable 指针。所以 Box<dyn Notify>、Rc<dyn Notify>、&dyn Notify 都存在且各占 16 字节，而裸的 dyn Notify 只作为这些指针的指向类型出现。理解了”宽指针等于值地址加类型擦除后的自我描述”，后面关于所有权、生命周期、向下转型的讨论都只是它的推论。

对象类型还可以带上已经写死的泛型参数：Box<dyn Fn(usize) -> String>、Box<dyn AsRef<str>> 都合法，因为参数在类型里已填好，方法签名不再依赖调用现场。Fn、FnMut、FnOnce 三大闭包 trait 对象是策略回调的标准载体：

每个闭包的具体类型都是编译器生成的匿名类型，天然无法写进 Vec<具体类型>，Box<dyn Fn> 几乎是唯一的收纳方式。

还有一个方向相反的对照值得记牢：dyn Trait 与 impl Trait 看着都是”某个实现 trait 的东西”，impl Notify 是静态分发的入口，编译期对应唯一具体类型，可以被内联、可以不装箱；dyn Notify 承认”背后可能是任何实现”，于是必须装进指针、必须查表。后面做取舍时，这条”impl 面向单一类型、dyn 面向开放集合”的分界线会反复用到。

对象安全：哪些 trait 做不成 trait 对象

trait 对象不是无条件的。决定 dyn Trait 是否合法的规则叫对象安全（object safety），违反它的 trait 一旦写进类型位置，编译器就报 E0038。为什么需要这组规则？vtable 表项最终要落成固定的函数指针，签名必须能写成不依赖具体类型的形式。&self 接收者没问题，具体类型信息可以藏进宽指针的第一个参数；可一旦方法签名里出现”具体类型本身”或”调用现场新引入的类型参数”，统一的函数指针就表达不了它。逐条看：

第一，返回 Self 的方法不可分发。fn clone_me(&self) -> Self 看起来平平无奇，但对调用方来说，返回值槽的大小取决于具体类型——String 是 24 字节，单元结构体可能只有 0 字节，dyn Notify 的调用方根本无法预留正确的返回空间。这条规则是”一夫当关”式的：trait 里只要有一个方法裸返回 Self，整个 trait 就不能做成对象。

第二，带类型参数的方法不可分发。fn parse<T: std::str::FromStr>(&self, s: &str) -> T 若要进表，就得为所有可能的 T 各生成一份实例，vtable 的项数必须是有限的固定值，泛型方法直接破坏这一点。

第三，Self 出现在接收者以外的位置不可分发。这一点比多数人以为的严格：不仅 fn merge(&self, other: Self) 不行，连 fn eq(&self, other: &Self) 这种全指针形态也不行——两个 trait 对象里裹的可能根本不是同一个具体类型，方法签名原本保证的”两边同型”前提在动态分发下失守。标准的 PartialEq、Clone（clone 返回 Self）、Default（default 返回 Self）都因此倒在这条线上，不是”故意不给用”，而是表格式分发的机制决定了无法安全地用。

第四，trait 自身带 Self: Sized 约束的不可分发，因为对象类型恰恰不是 Sized。但方法级的 where Self: Sized 是合法的逃生舱：带这个约束的方法被豁免出对象安全要求，不进 vtable，也无法通过 trait 对象调用，却不妨碍 trait 本身做成对象。

第五，关联常量合法但经对象访问不到；关联类型必须写死或可推断：Box<dyn Iterator> 会因 Item 未指定而报错，必须写 Box<dyn Iterator<Item = u32>>。

Iterator 是这套规则的绝佳标本：它明明挂着 collect、map、chain 一大堆泛型方法，却能正常塞进 Box<dyn Iterator<Item = u32>>——答案写在 1.70 的标准库源码里：这些泛型适配器方法全部带着 where Self: Sized 边界，对象接口里真正可分发的只剩 next 和 size_hint。另外，trait 自身带类型参数不破坏对象安全，Box<dyn AsRef<Path>> 合法，因为 as_ref 本身不是泛型方法，参数已被填成 Path。

实践中被对象安全卡住时，标准出路有三条：给”破坏者”方法加 where Self: Sized，承认它不属于对象接口；把 trait 拆成两层，精简的对象安全核心用于 dyn，便利方法通过扩展 trait 或泛型 impl 补给具体类型；或者改用枚举收纳这些特殊方法。好消息是 1.70 的 E0038 通常会点名是哪个方法、因为返回 Self 还是因为泛型，顺着方法名找过去，十有八九就是上面几条之一。

Box、Rc 与引用：所有权形态和生命周期默认值

同一个 dyn Notify，至少可以由三种指针携带，区别不在语法，而在谁拥有那个值、它能活多久。

Box<dyn Notify> 把值移进堆，所有权独占地交给 Box，是异构集合的标准形态：Vec<Box<dyn Notify>> 里的渠道被通知完就随容器 drop，回表调用各自的胶水即可。需要调用 &mut self 方法时，直接对 Box<dyn Notify> 取可变借用，Box 的解引用链会把借用规则原样传递下去。

&dyn Notify 是借用：值仍然住在栈上、别人的 Box 或 Rc 里，引用只是临时视图。优点是不产生堆分配，缺点是生命周期的账要自己算——把 &String 隐式转成 &dyn Notify 是一次 unsizing 强制转换，编译器会自动做；但想把这种引用塞进结构体字段长期持有，就得给结构体标生命周期参数，并保证引用比数据短命。

Rc<dyn Notify> 提供单线程共享所有权，多处持有同一个渠道，最后一个释放者触发销毁；要跨线程就换成 Arc<dyn Notify>，同时约束必须写成 dyn Notify + Send + Sync——否则编译器连把 Arc 往线程间 move 这一步都不放行。Send、Sync 不进 vtable，只影响类型的线程能力；Arc 计数更新的原子开销与动态分发无关，别把两笔账混在一起。

向下转型：Any、TypeId 与 as_any 模式

动态分发把具体类型擦除了，但总有想把它们找回来的时候：消息处理器收到一个 &dyn Any 要按类型分流，或者要从 Box<dyn Notify> 里把原来的 String 取回去。标准库的工具是 Any trait，核心只有一句：trait Any: 'static，配一个返回 TypeId 的方法。那个 'static 约束的道理很直接——类型标识的比较必须在此后任何时刻都有效，若类型内部含有引用，就无法保证比较发生时它指向的数据还活着，所以 Any 只收留 'static 的类型。

这个模式值得节制使用。as_any 必须写进 trait 本身，一个干净的行为抽象被迫带上类型自省的后门，下游拿到 &dyn Notify 就能对具体类型分支，抽象的意义被稀释。更要紧的是：如果你发现代码里到处都在 downcast_ref 分流，说明”异构行为”其实是个封闭集合，用 match 直接表达可能比动态分发加类型标签更诚实——这正好衔接下一节的取舍。

动态分发的性能账单：查表、间接调用与内联失效

把前面零散的伏笔集中收一次账。静态分发下，t.notify(msg) 编译成 call 目标函数，地址在链接期就刻进指令；动态分发下，它变成”载入 vtable 指针、按偏移载入函数指针、间接 call”三步。机时的差异藏在三个层面。

第一层是间接调用本身。直接调用的目标恒定，分支预测几乎白送；间接调用的目标随对象变化，预测器只能靠执行历史赌一把，当循环遍历的异质集合里实现交替出现，预测失败的代价是流水线冲刷。这一层对本来就做 IO 或大计算的方法无关痛痒，对一个只是累加计数器的微型方法却可能被放大数倍——函数体越短、调用越频繁，查表与跳转的相对占比越高。

第二层比第一层更狠：内联失效。编译器看不见具体实现，就无法把方法体折进调用点，也无法沿调用链做常量折叠、边界检查消除、循环展开。一个能整个内联掉的 notify 在静态分发下等于零成本；同样的方法进了 vtable，就永远是一次真实的函数调用。这才是”零成本抽象”与”运行期成本”的真正分界线：静态分发把抽象消化在编译期，动态分发把抽象留在运行期。想确认自己付了多少，可以用 cargo rustc -- --emit asm 导出热循环的汇编，数一数其中 load 加间接 call 的次数，对照 vtable 偏移就能认出动态分发的足迹。

第三层是指针追逐的缓存账：从 Vec 元素到 Box 指向的堆值，再跳到只读段的 vtable，再跳进函数体，链路上多了两次独立于数据的访存，比指令数本身更难优化。

rustc 并非完全无能：当类型推断能把候选收敛到唯一实现时（例如刚 Box::new 出来就立刻调用的局部对象），它可以做有限的去虚化，把间接调用折成直接调用。但别把优化押注在这上面——对象一旦进入容器、穿过函数边界，类型早被擦得干干净净。

实战建议是：绝大多数应用的性能瓶颈根本不在分发这一层，先测量、后动手。当 profile 确实指着一个热点的查表函数时，再按性价比排序选择出路：把该集合改成枚举分发；热循环内部用泛型或 impl Trait 保持静态分发，只在系统边界用 dyn；或者给对象加一个小的类型标签字段，手写 match 自己”表”一遍——本质是自己维护一个编译器能静态优化的 vtable，代价是把封闭性重新焊死。动态分发不是性能毒药，它只是把一部分成本从编译期搬到了运行期，而你要做的不过是确认这笔搬运费到底值不值。

dyn 还是枚举：一套选择框架

一句话版本：变体集合封闭且稳定，用枚举加 match；集合开放、需要跨编译单元扩展，用 dyn。我们把两边的写法摆在一起看。

枚举分发有几项 trait 对象给不了的好处。一是不装箱：Vec<Channel> 元素定长连续，缓存友好，没有逐个堆分配的开销。二是可枚举性：match 能编成跳转表，编译器知道全部变体，甚至能把每个分支内联进同一个函数，把”分发”整个消化掉。三是穷尽检查带来的重构安全：新增变体后，所有相关 match 处立刻编译失败，改动清单编译器替你列好。四是能力完整：枚举是 Sized 的具体类型，Clone、PartialEq、序列化想加就加，对象安全那堵墙对它不存在。

代价是封闭。核心 crate 的作者写死了 enum 的变体表，第三方就无法增加新渠道——加变体等于改核心类型，还会波及其它维护者的 match。dyn 恰好反过来：核心只定义 trait，任何 crate、任何时间编译出的实现都能塞进 Vec<Box<dyn Notify>>，核心代码一行不改；但你失去了枚举的一切——不能对”实现”做 match，只能经 trait 方法观察，每个对象一般还要单独装箱。

策略模式是两者交锋的经典中场。策略若是设计阶段就点齐的固定几种算法，用枚举承载更稳：零分配、静态分发，分支还便于被上层内联吸收；策略若由配置或插件在运行时装载进注册表，HashMap<String, Box<dyn Strategy>> 几乎是不二之选。同一条判断线也适用于中间件链、GUI 控件表、请求管线：类型数量随业务增长、各团队各自贡献实现的场合，枚举会把所有人逼进同一个文件的合并冲突里，而 dyn 天然支持各写各的。

还有第三条路：混合分层。对外签名保持 Box<dyn Notify>，对内用一个枚举实现这个 trait——枚举变体做真正的分发，trait 对象只是扩展性的门面；或者反过来，热路径内部走单态化，只在系统边界装箱。一个值得参考的直觉是：把 dyn 当作模块边界上的”接口协议”，边界内部尽可能是具体的、静态的。成熟代码库里两种分发往往并用，真正糟糕的是无意识的选择——要么被”面向接口”的 OO 肌肉记忆牵着把一切都 Box<dyn>，要么因为性能焦虑在明明需要开放扩展的地方硬写泛型，最后发现集合根本装不下两种类型。

插件式架构与 async 方法：2023 年的两条边界

dyn 是 Rust 插件架构的基石——动态库导出实现、宿主塞进 Vec<Box<dyn Trait>>，理论很顺，但这条路有一条铁律：vtable 布局是编译器的私有事务，没有稳定 ABI。一个用某个 rustc 版本编译出的 cdylib 插件，它的对象能被宿主当作 trait 对象使用的前提，是双方用足够接近的编译器版本、一致的 trait 定义与编译配置；rustc 升级可能改变表项顺序或附加元数据，旧插件与新宿主之间一次看似无害的 cargo update 就可能在运行期炸出难以诊断的崩溃。常见的自保实践：宿主与插件锁定同一工具链、在同一份工作区里构建；或者把插件边界退到 C 函数指针表、序列化消息、进程间 RPC 这一层，两侧各自使用 Rust 对象，只在边界转换。把”插件必须与宿主同编译器”写进架构决策记录，能省掉未来几次通宵排障。

另一条边界是 async，这也是 2023 年写 trait 对象绕不开的话题。异步生态已经相当成熟，tokio 事实上是异步运行时的标准，但 trait 对象与 async 方法彼此不合：截至本文写作时的稳定版 1.70（1.71 也近在眼前），trait 里不允许出现 async fn，这个能力在编译器的推进清单上，但此刻尚未稳定，生产代码不能把它当已交付的特性。

为什么不兼容？机制上还是对象安全那一套。async fn 脱糖后返回一个 impl Future——不可名的不透明类型，其状态机的尺寸与字段还依赖 Self 和输入的生命周期。vtable 表项要求签名能写成固定的函数指针类型，而”返回一个只有实现者自己知道长什么样的类型”恰恰违反了这一点：调用方在编译期既无法为返回的 Future 预留空间，也无法描述它的类型。简言之，trait 对象抹掉了具体类型，Future 却需要具体类型来定型，两者在语义上互相拆台。

于是 2023 年的实际答案是 async-trait 宏：

它把 async 方法改写成返回 Pin<Box<dyn Future<Output = ...> + Send + 'xxx>> 的普通方法，方法体变成构造装箱的 future。类型从”不可名的 impl Future”变成”可名可存的 Box 宽指针”，vtable 就能引用它了。代价也是双层的：每次调用都要在堆上装箱一次状态机，多一层解引用；宏默认还往签名里钉上 Send，想关掉需要显式改边界。对普通的服务调用路径，这点分配通常不值一提；对被海量热路径反复调用的轮询原语，它可能足以让你重新掂量抽象本身。按写作当日的口径，async 方法与 dyn 的兼容只能靠装箱，没有第二条路。

小结

trait 对象把”调用谁”的决策从编译期搬到运行期：数据指针与 vtable 指针拼成 16 字节的宽指针，vtable 按”具体类型加 trait”的组合在编译期静态生成，调用即查表加间接跳转。对象安全决定谁能进表——裸返回 Self、方法带类型参数、Self 出现在接收者之外、trait 依赖 Sized 自身，都会让整个 trait 做不成对象，where Self: Sized 是最常用的豁免开关。持有方式划出能力边界：Box 独占、Rc 与 Arc 共享、引用只是视图，而 Box 与 Rc 里的对象默认背上 'static 的约定，报错时先想生命周期默认值。需要找回具体类型就用 as_any 加 downcast，分支一多就该反思枚举。性能上，动态分发对小而热的方法最不友好，内联失效往往比查表本身更贵；变体封闭用枚举加 match，需要开放扩展才用 dyn，插件路线还要记住 vtable 无稳定 ABI、必须与宿主同工具链。至于 async，2023 年的今天请默认它不能出现在 trait 里，装箱 future 是当前唯一务实的桥。最后给出我的建议：先看变体集合开不开放，再看调用点热不热，两个问题答完，工具自然就选出来了。
