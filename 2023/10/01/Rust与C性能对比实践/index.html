Rust 与 C++ 性能对比实践

本文属于《Rust 学习路线》第 57/68 篇
上一篇系列目录下一篇

选型讨论里出现最多、支撑数据往往最薄的一句话，就是”Rust 比 C++ 快”。本文不给基准数字，只谈方法：在 2023 年 10 月的条件下（Rust 以 1.72 为口径，C++ 以 C++20 为主，GCC 13 与 Clang 16 这一代编译器），一次站得住的性能对比应该长成什么样，哪些差异确实来自语言，哪些其实不该算在语言头上。读者假定两种语言都写过项目代码，也用过 cargo bench 与 Google Benchmark。

先划边界：本文只讨论同一份计算逻辑用两种语言表达时的开销结构。FFI 与跨语言调用的成本在《Rust FFI 与 C 互操作》里另有讨论，嵌进 Python 进程的胶水开销是《Rust 与 Python 混合部署》的主题，这里不重复。

把对比实验设计出来，再谈结论

对比的可信度由实验设计决定，不是跑分工具。动手前要固定三件事：问题量级、构建选项、测量与报告方式。

问题要在同一个量级上

太小的基准测的是函数调用与进程启动，太简单的会被优化器折叠成常量。可用的做法是让单轮任务落在毫秒级，把输入准备移到计时区之外：用固定种子的伪随机序列生成，生成过程不计耗时，但要保证被计算的函数不被常量传播看穿，例如让输入来自命令行参数。

只测一种形状同样不行。同一份逻辑在顺序访问、随机访问、密集算术、指针追逐四类负载上表现完全不同：前者测编译器，后者测缓存。混成一个综合分，结论对任何一种负载都不成立。

构建选项要对齐

最容易犯的错是拿 Rust 默认的 release（opt-level = 3）去比 C++ 常见的 -O2。要么两边同档，要么两档都跑，看结论会不会翻转——会翻转，说明测的是优化器策略而不是语言。

另外，-march=native 与 -Ctarget-cpu=native 会让结果只在生成它的那台机器上成立，跨机器报告时不要用。链接库也要对齐：都链同一个第三方分配器，或者都不链。

噪声要小到可以讨论

然后是测量本身。笔记本到温度阈值就降频，不适合跑基准；台式机也该固定调频策略，用 taskset 把进程绑到指定核上；虚拟化环境的时钟与 steal time 会污染尾延迟。正式计数前跑几轮预热，让分支预测、页缓存与分配器稳定下来。

统计上报告分位数而不是平均值：平均值被长尾拖走，而选型关心的是最坏情况。每轮留下原始数值与离散程度，再安排一个同语言对照组——同一实现只改一个无关变量再跑一次——它的差值就是噪声底，小于这个底的差异不值得解读。

还有一点常被省略：时间与内存要分开看。吞吐、单次延迟、尾延迟是三件事；峰值驻留与分配次数是另外几件。”更快但更费内存”可能只是缓存命中率变化，却被记成语言的功劳。

零成本抽象：同一个词，两种承诺

“零成本抽象”在两个社区里都被反复引用，含义却不重合。C++ 的说法接近”用不到的部分不必付费”：模板只在被使用时实例化，抽象层能在优化后消失。Rust 的说法多一层约束：抽象不得引入隐藏的运行时代价，没有隐式拷贝、隐式分配、不知不觉的动态派发，这些都被所有权系统拦在编译期。

内存布局与分配器：看不见的第三个变量

布局上两种语言的保证不同。C++ 对非填充相邻字段保证声明顺序；Rust 的默认表示不保证字段顺序，只有 #[repr(C)] 与 C 一致。Rust 还有空值优化：Option<&T> 与裸引用同宽，Option<NonZeroU32> 与 u32 同宽，判别值借用本来无效的位模式。枚举尺寸取最宽变体加判别式，常能省掉一个字段；C++ 的 std::variant 下界更硬。这类差异能在编译期核对，不必跑基准。

更敏感的是分配器，它是独立于语言的第三个变量。Linux 上两边默认都走系统的 C 分配器；C++ 可以链接或预加载别的实现，也可以用 C++17 的 std::pmr 固定在单调缓冲区上，Rust 可以全局替换，也可以用 arena 集中分配短命对象。一边链了第三方分配器、另一边没有，测的就是分配器而不是语言。容器扩张同理：两边动态数组都按倍增扩容，差别在搬家用 memcpy 还是逐元素移动——这类事实看分配次数比看墙钟时间稳定。

边界检查与迭代：越界检查贵不贵

“Rust 每次访问数组都要做边界检查，所以慢”是流传最广的说法之一。前提对，结论错。

先把契约摆正。Rust 下标越界会 panic，get 返回 Option；C++ 下标越界是未定义行为，at 抛异常。所以”带检查的 Rust”去对”不检查的 C++”，比的不是同一种东西。诚实的对比要么两边都检查（get 对 at），要么两边都不（不安全块里的裸下标对 operator[]）。默认契约的差别是真实的工程差别：它决定越界是崩溃、是可恢复错误，还是悄无声息的内存破坏，但不属于性能差异。

检查真正变贵的地方通常不是那一次比较，而是它挡住了后续优化：无法证明不越界的下标会让向量化器放弃整段循环；迭代器写法把长度与访问方式一起交给编译器，检查与分支多在循环外一次完成。两边都有逃生舱：Rust 要写显式不安全块，C++ 什么都不用做，代价是把正确性交给开发者自己承担。

移动语义与所有权：重复拷贝少在哪里

两种语言都有移动语义，但”什么时候退化成拷贝”的默认答案不同，这决定性能特征稳不稳。

C++ 的 std::move 只是强制转换，把左值转成右值引用。它本身不移动任何东西——写漏了、类型没有移动构造、或者签名按值收了一个 std::string，都会安静地退化成深拷贝。Rust 反过来：赋值给另一个名字、作为实参传下去就是移动，原名立刻不可用；要复制必须显式 clone，只有 Copy 类型才隐式复制。于是”隐藏的重复拷贝”这类事故在 Rust 里很难悄悄发生，在 C++ 里要靠经验和审查去防。

差距出现在写法被打破时：Rust 里返回指向临时数据的切片，生命周期不满足就编译不过，作者被迫回去改数据结构；C++ 里返回悬垂的 string_view 未必被拦下。反过来，C++ 的 shared_ptr 要在控制块上做原子加减，Rust 的 Arc 同样，但更常见的替代是借用——不拥有就不必计数。测量这类差异，最直接的指标是动作本身：数 memcpy 与 memmove 的次数与搬运字节。

模板与泛型：单态化的两种形态

C++ 模板与 Rust 泛型走同一条路：为每种具体类型生成一份专用代码。两边的快路径上没有虚表与运行时类型检查，参数还能折叠成常量，函数更容易内联。代价也相同：代码体积膨胀，指令缓存压力更大，编译与链接时间变长——这不是某种语言独有的税，而是同一种技术交换出来的账。

区别在控制代码生成的手感。C++ 模板住在头文件，实例化点散在各翻译单元，重复实例化由链接器合并，显式实例化声明能把某几份固定下来。Rust 的泛型在 crate 内单态化，不想膨胀时可以把参数种类收敛成有限个枚举，或者改成接收 trait 对象，用一次间接调用换一份共享代码。

还要警惕一种偏差：两边的抽象深度不一样。C++ 侧手写特化循环、Rust 侧用一整条迭代器链，于是”抽象有成本”的结论出来了，可它测的是代码风格。公平的实验问同一个问题：这段热点生成了几份机器码、有没有被内联。内联过头会变慢这件事，两种语言都会发生。

错误路径：异常与 panic 各按什么计价

异常与 panic 的成本要拆三处看：快路径上表示”可能失败”的额外状态，展开表与清理代码带来的体积，以及罕见路径走一遍的代价。C++ 基于表的异常在抛出之前几乎不收钱，但编译器要为可能抛出的调用点保留清理路径，函数常常因此失去优化机会；noexcept 能换回一部分。Rust 的 Result 把失败放进返回值，通常只是一两个寄存器的事，检查是一次可预测的分支；panic 需要展开支持，设成 abort 能去掉展开表，代价是放弃捕获。

两边都能在热路径上做到几乎免费，差别在于这条路径写不写在签名里、编译器看不看得见。测错误路径要格外小心：基准输入必须保证每轮走同一条分支，一次偶然的抛出或者 panic 会把整组数据的尾延迟带跑。更稳妥的做法是把成功路径吞吐、失败代价与二进制体积分开记录。C++ 还有关掉异常这一档，之后错误处理只能靠返回码与输出参数，形态上反而更接近 Rust。

生态差异：并行算法与 SIMD 的可得性

这一项是生态差异，不是语言差异。C++17 给一批标准算法加了执行策略，std::par_unseq 一行就能把循环交给线程库，但要链接对应的并行后端、要求循环可向量化，各家实现覆盖并不齐。C++20 与 C++23 的 sender 与 receiver 模型当时刚进标准，主流实现还停在参考库阶段。Rust 标准库没有并行迭代器，事实标准是数据并行库 rayon。

SIMD 这一侧两边都不轻松：Rust 的可移植 SIMD 当时仍属 nightly 特性，稳定版能用的是 std::arch 里按指令集各写一遍的内联函数或第三方封装；C++ 也是架构内建函数加自动向量化。自动向量化出自同一族优化器，而 Rust 里引用与可变引用互斥这条规则会被编译成”这些指针不别名”的信息交给后端，C++ 要靠 __restrict 一类扩展才有同样表述。差别落在编译器能推断什么上，不在语言快慢上；对比时应把向量化是否发生当成一个显式变量。

瓶颈常在缓存与数据结构

真实项目里做性能定位，热点清单通常长这样：访问模式（结构体能否塞进一条缓存行）、算法与数据形状（哈希查找换成有序数组上的二分）、分配策略（每请求一次分配换成 arena 或缓冲复用）、分支的可预测性、编解码与拷贝次数。这几项在两种语言里都能改，收益通常远大于换一种语言。

微基准最容易让人跳过分诊，错误结论常常这样长出来：

flowchart TD
    A[挑一个小而能跑的问题] --> B[只换语言 不换数据结构]
    B --> C[输入规模与缓存效应放大差异]
    C --> D[取一次平均值当结论]
    D --> E[写进选型报告]

更根本的原因是，多数业务负载的时间花在等待上：等磁盘、等网络、等锁，也等一次缓存未命中把访存的真实代价暴露出来，语言在这些地方几乎不改变量级。真正值得比较的是另一组更稳的东西：内存安全缺陷有没有被编译期堵住，数据竞争是否可能通过，改一次数据结构要付多少审查成本，构建能否复现。性能对比该摆在这里：用它做排除，而不是用它做选择。

小结

本文没有给出跑分表，因为脱离实验条件之后那些数字没有意义。可以带走的是几条判断方法：先固定问题量级、优化等级与分配器，再谈差异；把时间、内存与动作计数分开报告；抽象的成本到反汇编和代码体积里去看，不要到语言名字里去看；边界检查与隐式拷贝的差别，本质上是默认契约的差别。同一类工程问题上，两种语言通常落在同一档，可见差异更容易来自数据结构、缓存与团队约束。选型时值得比较的是可维护性、并发安全与工程成本，性能对比只负责排除”语言会不会成为瓶颈”这个前提。
