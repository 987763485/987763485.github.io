安全资产台账建设

资产台账是很多安全工作的第一块地基，却常被当作“合规作业”来应付：突击盘点一次、导出一张表格、三个月后无人维护。本文讨论的就是这件事本身——安全视角下的台账要登记什么、数据从哪里来、如何保证质量、责任归给谁、怎么和 CMDB 与 ITSM 打通、如何长期活着。面向安全工程师、运维负责人和承担合规职责的同学，读完应能拿出一个可落地的资产模型和一套从采集到治理的做法。文中数字均为示意值。

资产台账为什么是所有安全工作的前提

三个高频问题的共同前置条件

第一类是漏洞影响面判定。2021 年 12 月那个日志组件漏洞暴露出来的真正问题，不是“扫描器测不测得出来”，而是“我们到底有哪些地方在用这个组件”。当时多数团队的真实过程是：先在内网搜文档，再挨个问研发负责人，最后靠老运维的记忆补一轮，折腾三天结论仍然不完整。原因很简单——判定影响面需要的是一次横跨主机、容器镜像、应用服务、依赖组件与云资源的关联查询，而这种查询能力只能由资产台账提供。扫描器回答得了“哪些端口看起来有这个问题”，回答不了“这个业务系统是否依赖它”。

第二类是应急响应。处置阶段要连续回答三个问题：影响范围有多大、可以隔离哪些东西、需要取证哪些目标。范围决定策略——隔离一台核心数据库和一台测试机的代价完全不同，而判断代价需要分级、责任人、依赖关系三类信息。没有它们，指挥只能在“全停”和“什么都不停”之间选择。台账在应急中的价值不是“知道有哪些机器”，而是“能在五分钟内圈出一个可处置的集合”。

第三类是合规取证。等级保护测评、商用密码应用评估、内外部审计，都会要求提供资产清单以及每一项的责任人、重要程度和变更记录。难点不是“有没有一份清单”，而是“清单能不能被证明是当时的真实状态”：只在测评前突击填写、没有来源标记与时间戳的表格价值有限，而记录了采集来源、字段更新时间与责任人确认动作的台账，本身就构成证据链的一部分。

台账与清单的差别

一张资产清单（list）和一份资产台账（ledger）的差别不在数据量，而在三个能力：能不能查（任意字段组合可检索）、能不能追（谁在什么时间依据什么填的）、能不能刷新（过期数据会不会自动暴露出来并被处理）。三者缺一，剩下的就只是一次性快照。安全团队最常见的挫败感恰恰来自“明明去年盘过”，而那次盘点的产物从生成那一刻就开始失真。

先界定资产范围

一条判定标准

笔者用一个粗糙但好用的标准：凡是能被访问、能被利用、能承载数据、能带来合规义务的东西，都是资产。这是风险视角而不是采购视角——问的是“攻击者能碰到什么、数据在哪里、出事之后谁负责”。它的副作用是把历来由业务自己掌控的东西也拉进台账，比如研发自购的公网测试机、外包开通的 SaaS 试用账号；这类东西恰恰是事故高发区，范围界定阶段就要确认它们是登记对象，登记方式交给后面的采集与责任机制。

九类资产与最小登记单元

台账设计中最常见的错误是把“类别”当成分类学问题去追求完备。真正决定可用性的是每一类的最小登记单元，也就是这条记录代表什么；单元定错了，后面所有字段都会错位。

类别 最小登记单元 最容易被漏掉的部分
主机 一台可启动的机器 已关机但磁盘仍在的虚拟机、快照
容器与镜像 运行实例与镜像分开登记 基础镜像里打包的第三方组件
网络设备 一台可登录的网络设备 分支小设备、无线接入点
应用与服务 一个可独立部署的服务 定时任务、运维脚本、内部小工具
API 一个接口或接口组 内部调用且未鉴权的接口
域名与证书 一个域名 / 一张证书 历史解析记录、免费期临时证书
账号与权限 一个账号 服务账号、外包与离职遗留账号
数据资产 一个数据集或一个库 备份文件、临时导出报表
SaaS 与云资源 一个实例或一个租户 对象存储桶、消息队列、函数

三点需要展开。容器与镜像要分成两类记录：运行实例生命周期以小时计，登记它只能用于当下排障；镜像与仓库才需要长期治理，因为一个镜像会被复制进成百上千个实例。两者都要登记，但时效策略完全不同。

域名、账号、数据这三类最容易被漏。域名是暴露面的起点而不是解析配置的一部分，“还在解析但后端没人记得”的老域名风险很高。账号常被以“归身份系统管”为由排除，但它有持有人、有权限集合、有生命周期，离职邮箱仍可用、外包 SaaS 账号仍有效，不登记就无从治理。数据资产的登记则要克制：台账只记“这个数据集存在、在哪个位置、责任人是谁”，分级规则由数据分类分级体系给出，不属于本篇范围。

影子资产从哪里来

范围定完之后的第一个现实问题是“少了一批”。未登记资产来自三个渠道：下线时没人注销（占大头）、临时环境长期化（说好用两周的集群活了两年）、绕过流程自建（业务自己开的云账号与域名）。治理手段分别是生命周期闭环、默认到期与续期、采集侧交叉验证——只要采集面足够独立，绕过流程建起来的东西仍会被某个来源发现。

资产模型与字段设计

七个维度

一条资产记录要支撑前面说的三类判定，至少需要七个维度的信息：唯一标识、分类分级、责任人、暴露面、位置、依赖关系、生命周期状态。缺任何一个，都有一类问题回答不了。下面先看一条完整记录，再逐项讲设计要点。

唯一标识：别拿 IP 当主键

asset_id 由台账自己生成，不复用，也不要把机房、系统名编码进去。外部标识全都会变——IP 重分配、实例重建、域名换后端——所以关联关系、漏洞记录、工单引用都必须挂在这个稳定 ID 上，否则一次变更就断链。外部标识用列表存，一条记录可以同时有 CMDB 编号、云实例 ID 和容器标识，按任一外部标识都能回到同一条记录。

分类分级与责任人

分类回答“这是什么”，用于圈范围；分级回答“出事有多疼”，用于排优先级。业务重要度、数据敏感度、暴露程度要拆成三个独立字段：一旦合成总分，就答不出“公网可达但数据不敏感”这类组合查询，而这恰恰是应急时最有用的筛除条件。分级规则由数据定级体系给出，台账只存结论和来源。

责任人必须存账号而不是姓名：姓名会重名、会改、会随组织架构失效。主责任人维护字段并接收告警，所属团队在人员流动后兜底，安全接口人提供沟通渠道；这个字段要带确认时间，因为“被登记为责任人”和“承认自己是责任人”是两件事。

暴露面与位置

暴露面只记“内网 / 外网”不够，至少要记哪些网络可达、开了哪些端口与协议、访问是否需要认证：它决定同一个漏洞在不同资产上的处置顺序，也是缩小影响面时的主要筛除条件。位置记环境、云或机房、区域、集群、命名空间，用途是批量圈定——某个集群本身出问题（宿主机漏洞、网络故障、跨越合规边界）时，要能立刻列出这个位置上的全部资产。

依赖关系与状态

依赖用有向边表示，别写成文字备注，并至少分三种：调用依赖、部署关系、数据流向。影响面分析主要用前两种，数据泄露评估用第三种，混在一张表里查询结果一定出错。生命周期状态的取值必须受控，用枚举而不是自由文本；这个字段一旦缺失，僵尸资产在数据上和正常资产长得一模一样。

字段设计的三条约束

第一，每个字段都要能回答一个问题，说不出“用来查什么”的删掉。第二，每个字段都要有来源：要么有采集渠道，要么有人负责登记，两者都没有的字段最后一定是空值。第三，必填字段越少越好——笔者见过字段总数接近三百的模型，两年后可选字段的填写率不到 5%（示意值），真正被查询用到的只有十来个。

实践上只把六项设为必填：唯一标识、名称、分类、主责任人、生命周期状态、网络可达性。其余按类别逐步补齐，允许为空但要标记为“未采集”。

采集方式与各自的盲区

一句话概括这一节：没有任何单一渠道能给出完整而正确的台账。可用的台账一定是多源融合的结果，而且使用者必须清楚每个来源缺了什么、偏向了哪边。

云厂商 API

回答“云上资源客观存在及其配置”，实例、磁盘、托管数据库、对象存储桶、负载均衡、安全组都能拉到，还带创建时间这类客观字段。盲区有三处：账号没纳管就完全看不见（子公司、业务自购、个人开的账号），这是最大盲区；接口只给资源不给业务归属，标签不填就无从判断；看不见云里跑的应用和容器内的组件。漂移方向是“存在但没人认领”。

CMDB 同步

回答“流程登记过的资产与它的业务归属”，优势恰恰是技术采集拿不到的东西：系统名称、业务线、开发团队、运维归属。盲区在于它反映的是流程状态而不是实际状态：新增靠工单触发、变更常常不回写、已删除的资源常常仍在库里。漂移方向是“账面上有、实际可能早没了”，也就是僵尸记录，所以 CMDB 的记录不能直接当作“已确认”。

扫描发现

回答“此刻可达、且有响应的东西”，端口、服务指纹、证书、主机名靠它补齐。盲区包括：不响应的目标（已关机、被防火墙屏蔽、只监听本机地址、没有探针的隔离网段）一律看不见；扫得到端口却给不出业务归属与数据；域名、账号、SaaS 完全不适用。扫描本身也有风险，只能在授权窗口内限速执行并关闭高危插件，本文只涉及存在性确认与配置核对。漂移方向是“扫到的才算数”，会系统性低估不可达但确实存在的资产。

代理与流量

回答“实际在跑什么、谁在访问谁”，这是唯一能补齐依赖关系与实际 API 调用面的渠道：调用边、访问频次、真实暴露的接口集合，都能从流量与探针上报里得到。盲区是没装探针就看不见、加密流量只能拿到元数据、完全离线的资产（备份介质、冷存储）不可能有流量。它的漂移方向最危险——“有流量的才重要”会让没人访问但风险高的资产（开着调试端口的老服务、还解析着却没人用的域名）从台账里消失。

人工登记

回答“只有人知道的事”：业务归属、数据敏感度、停用原因、临时环境的计划回收时间。它是唯一能填出分级的渠道，也是最不可靠的：会漏、会错、会过期，填写质量与考核无关时几乎必然走低。漂移方向是“填的那天是什么就是什么”。

融合：把来源变成置信度

融合的关键不是“谁覆盖谁”，而是把来源组合本身变成一个质量字段，让下游能判断该不该相信这条记录。

三类冲突必须留给人处理，规则很难自动判定：CMDB 说还在、云 API 说没了（下线未登记）；扫描发现了、CMDB 与云端都没有（影子资产）；同一个地址对应两条记录（地址复用还是重复登记）。同时要区分两种失真：真实世界变了而台账没变（漏登），和台账留着而真实世界已经消失（僵尸）；前者让人不知道该防什么，后者白白扩大范围并消耗责任人信任，两者需要分别度量，一个靠补采集，一个靠补生命周期。

数据质量治理

多源采集之后会遇到四个问题：重复、缺字段、过期、以及错得离谱但看起来正常。

去重与合并

同一台主机被云端、CMDB 和扫描器各登记一次，是最常见的脏数据。合并要按证据强度分层，弱证据只提示、绝不自动合并：

合并要保留证据链：谁被合进谁、依据哪个字段、什么时间，并且必须可回滚。自动合并出错的代价通常大于重复本身——责任人一旦收到不属于自己的告警，就很难再相信台账给出的结论。

缺失字段与时效性

空值要区分三态：未采集（有渠道但还没跑）、不适用（这条资产本来没有这个维度）、确认没有（采集结果为空）。三态混成一个空字符串，覆盖率统计就失去意义。时效性按字段而不是按整条记录设 TTL：端口与暴露面以天计，业务归属以季度计，序列号几乎不变；到期未刷新的字段自动降级为“待确认”并生成核实任务，而不是继续被当成事实。

异常检测

台账自己就能产生告警。价值最高的五条规则：无责任人且暴露面含公网；分级为高却没有任何技术来源印证；证书临近到期而责任人已离职；同一段地址上端口数短期明显增加；来源只剩人工登记且连续两个季度没被技术来源证实。前四条对应事故，第五条是台账开始腐烂的信号。

责任归属机制

责任人是台账里唯一不能靠采集得到的字段，也是台账能否长期活下去的关键。

三种状态与限时认领

责任人维度只有三种状态：有主、待认领、无主。把“无主”当成显式状态而不是空值，才能统计它、推送它、关闭它。

flowchart TD
    A[采集发现资产] --> B{能否自动定责}
    B -->|标签或工单已有| C[有主]
    B -->|无法确定| D[待认领]
    D --> E[按团队与网段推送认领任务]
    E --> F{认领期限内是否有人确认}
    F -->|确认| C
    F -->|无人确认| G[上升到部门负责人指定]
    G -->|指定完成| C
    G -->|仍无人负责| H[无主]
    H --> I[收敛暴露面并进入回收流程]
    I --> J[限期下线或补登记]

关键在最后一步：无主不等于放着不管。无人认领的资产要主动降低风险——去掉公网可达、关掉非必要端口——同时进入回收流程。这个口径要提前和业务、运维定下来，写明处置窗口与例外申请入口，否则第一次真去关停时一定遇到阻力；反过来，无主资产若能无限期挂着而不产生任何后果，无主数量必然持续上升。

责任人变更

组织变动是主要触发方式：离职、转岗、团队拆分都应由人事与组织架构数据驱动，而不是等责任人自己说。不建议把离职者的资产自动转给上级作为终态——上级往往确实不负责，自动转入只能当缓冲，仍要走一次认领或指定流程。另一种是周期性确认：按分级设不同频率，高等级资产建议每季度确认一次，动作包括“资产还在、归我、暴露面与分级没变”。确认记录本身就是数据质量的证据；频率太低数据会烂，太高会被批量乱填，宁可少填也要确认。

最后一条设计原则：责任字段用来派活和沟通，不用来追责。台账一旦被当成事后定责的工具，责任人就会把分级往低调、把资产数量往少了报，数据可信度随即崩塌——这一点比任何技术手段都更能决定台账的真实性。

与 CMDB、ITSM、漏洞管理和 SOC 的集成

核心命题只有一句：台账不应该变成第四个孤立库。要么它是 CMDB 的安全视图（在同一份数据上扩展字段），要么它是独立库但与其他系统双向集成。最糟的中间形态是各系统各维护一份资产表、定期导出对账——这条路一定会失败，因为对账没有权威方。

两种形态的取舍很清楚。在 CMDB 上扩展，好处是只有一套数据、责任链条现成，代价是模型受其约束、字段刷新受其流程拖累。独立台账只存安全视图并引用 CMDB 的记录号，适合 CMDB 不可改或覆盖不足的情况，代价是要自己维护同步与冲突处理。经验上，CMDB 覆盖度高于八成时选前者（示意值），否则先建独立台账，把力气花在补覆盖上。

flowchart LR
    ITSM[ITSM 变更工单] --> LED[资产台账]
    SRC[云 API 与扫描流量] --> LED
    LED --> VM[漏洞管理平台]
    LED --> SOC[SOC 告警富化]
    VM -->|按 asset_id 回写处置状态| LED
    SOC -->|回报真实暴露面| LED

四条集成关系的要点：

  • 与 ITSM：工单是唯一写入通道，上线、变更、下线都由工单驱动台账而不是事后补录；每条状态变化都应能追溯到某张工单。
  • 与漏洞管理：台账提供资产集合与定级输入（分级加暴露面），漏洞平台提供漏洞记录与修复状态，两边通过稳定 ID 关联。不要把漏洞明细抄进台账，也不要让漏洞平台反过来维护资产归属；发现、定级、SLA 与披露由漏洞管理工作自己负责，本篇只保证“受影响集合查得出来”。
  • 与 SOC：台账主要用作富化数据源，把日志里的地址与实例号反查成分级和责任人，让分析师不必在群里问“这是谁的系统”。检测规则与响应编排属于 SOC 建设本身，台账不参与检测逻辑，但直接影响误报处理效率。
  • 与数据安全：分级规则由数据分类分级体系给出，台账只存结论、等级与来源。

生命周期闭环

台账只有在和资产的实际生死挂钩时才会自己更新。状态机不必复杂，但必须显式。

flowchart TD
    R[申请与规划] --> G[已登记]
    G --> P[运行中]
    P --> C[变更中]
    C --> P
    P --> D[待下线]
    D --> X[已注销]
    G --> Q[待确认]
    Q --> P
    Q --> D
    P --> N[无主]
    N --> D

上线登记。最可靠的做法是把登记做成拿不到资源的门槛，而不是事后补录：资源申请、IaC 模板、发布流水线强制注入归属标签与责任人，缺字段直接失败。

变更同步。差异有三个来源：工单、采集比对（扫到的端口或证书与台账不符）、探针上报（出现台账里没有的调用关系）。三者都应自动生成一条确认任务给责任人，而不是由安全团队直接改数据——后者会让台账变成“安全部门自己填的表”，责任人从此不再对数据负责。

下线注销。这是全流程最难的一步：下线没有收益、只有成本，还常常牵连数据处置。两个办法真正有效：临时资产默认到期，申请时就填存活天数，到期自动进入待下线，要继续用就得续期；注销动作必须与数据处置确认绑定，确认数据按既定策略处理过才允许置为已注销。没有到期机制，僵尸记录只会单调增加。

用台账回答两个实际问题

某漏洞影响了谁

这个查询要分四步，一步都省不掉。

差别在第三、四步。按资产逐条派单，责任人会收到十几条几乎相同的任务，最后一条也不会被认真处理；按人聚合成一张工单才可能被执行。“确认不受影响”必须写明依据（哪个来源、哪次核实、哪个版本），否则下次同类漏洞爆发时又从头查一遍——台账的复用价值恰恰来自这些否定结论。

某域名还有没有用

这是另一类问题：存活性判定，依赖的字段完全不同。

判断链条是：是否还有解析、后端是否有服务响应、是否有真实访问、证书是否仍在续期、责任人能否说明用途。五种信号组合出四个结论：在用；只剩历史解析（应注销）；无人能说明（转无主流程）；有流量但业务不承认（影子资产，立刻查用途与承载数据）。

两个问题对应台账的两种查询模式：影响面判定依赖边与组件版本，存活性判定依赖流量与时间字段。只考虑前者，台账在“清理”这件事上就毫无用处，而清理恰恰最耗人力。

度量指标与常见失败

三个指标的坑都在分母上。覆盖率如果把“录入了多少条”当分母，就只剩数量增长的意义，永远好看；正确做法是用相对独立的采集面（另一组扫描窗口或另一个账号视角）的发现集合当分母，并承认它只是下界估计。准确率靠随机抽检，一次几十条足够（示意值），且要覆盖不同来源。及时率的分母是变更事件总数，工单数与采集比对差异数都能提供。再加一项无主资产占比，它比前三项更早反映健康度。目标值不宜定高：覆盖率九成、准确率九成、及时率八成（均为示意值）比“百分之百”更容易真正达到。

常见失败模式值得逐条对照：

  • 一次性盘点。产物是一张表，没有配套的写入通道，三个月后人走茶凉。
  • 字段设计过重。可选项太多等于没有，最后所有人填“其他”，统计结果反向失真。
  • 只登记不关联。数据躺在库里查不出来，等于没有台账。
  • 台账被用作定责工具。责任人压低分级、少报数量，数据可信度归零。
  • 只覆盖主机。域名、账号、SaaS 全部缺位，而事故常常出在这三类上。
  • 与安全流程脱钩。漏洞管理和 SOC 都不查台账，失去使用反馈，半年后退化成又一张表。

小结

资产台账的建设难点不在技术，而在两件事：让数据自己保持新鲜，以及让人愿意对数据负责。前者靠多源采集加交叉验证、按字段设时效、把差异自动变成确认任务；后者靠限时认领、周期确认，以及一条不可妥协的原则——责任字段用来派活和沟通，不用来追责。

落地顺序建议保守：先选三类资产（主机、域名与证书、云资源），只设六个必填字段，先跑通一个问题（某漏洞影响了谁），再逐步扩类别、扩字段、扩查询。台账的成熟度取决于它被使用的频率而不是字段数量——一个每周都被真实查询打中一次的台账，数据质量不需要人催。
