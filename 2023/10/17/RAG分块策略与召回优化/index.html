RAG 分块策略与召回优化

本文属于《Agent 智能体开发》第 25/55 篇
上一篇系列目录下一篇

本文讨论 RAG 里最容易被低估的一环：文档该切成什么粒度，以及如何在召回侧把对的块捞回来。前提是你已有可用的嵌入模型与向量库，本文聚焦分块策略选型、元数据设计与查询侧优化，适合正在做知识库问答的读者。

分块决定了召回的上限

RAG 的检索阶段不是在“文档”与“问题”之间做匹配，而是在“块”与“问题”之间做匹配：答案所需的信息若没被完整切进某一个块，那么无论换多强的模型、加多好的重排器，召回集合里也不会有它——检索只能从已有的块里挑，挑不出不存在的完整性。后续优化只是在“块已经切好”的约束下做近似，分块是唯一能改变约束的环节。

向量检索还有个特殊性：一个块只能有一个向量，而模型输出的往往是这段文本的“平均语义”。块过长，多个主题挤进同一个向量彼此稀释，问题只命中其一则相似度并不突出；块过短，句子虽然完整，支撑它的前提与指代却被切去了别的块，向量跟谁都有点像却谁都不够像。分块要处理的正是这个矛盾。

flowchart TD
    A[原始文档] --> B[分块]
    B --> C[嵌入与索引]
    C --> D[向量召回]
    E[用户查询] --> F[查询改写]
    F --> D
    D --> G[去重与邻近扩展]
    G --> H[按预算截断]
    H --> I[提示词拼装]
    B -.-> G

图里那条虚线容易被忽略：分块产出的不只是文本片段，还有父块编号、前后邻块、章节路径这些结构信息，后面的扩展与拼装全靠它们。只把分块理解成“字符串切片”，是多数项目后期难以维护的根因。

固定长度与重叠窗口

最朴素的做法是按 token 数定长切分，相邻块之间留出若干 token 重叠。优点是可控：块大小、块数量、单块向量成本都能提前估算，也不依赖文档有没有结构。最容易犯的错是按字符数切分——一个汉字通常占一到两个 token，代码与英文片段密度又完全不同，拿字符串长度当预算会让实际输入越过模型窗口。稳妥做法是用所选模型的分词器计数：

重叠窗口解决的是“关键句正好横跨切分线”的问题，代价有三点：存储与索引成本随重叠比例上升；同一段文字被两个块包含，两条记录一起排在前面，不去重就浪费了上下文名额；重叠并不能修复语义割裂，只是把割裂点随机化。定长切分适合没什么结构的文本，如聊天记录与工单描述；对 Markdown 手册、合同条款，它常把列表从中间切断、把表格切成碎片。

按结构、语义与递归切分

按结构切分

文档自带结构信息：Markdown 的标题层级、HTML 的标签树、解析后的章节号、代码文件的函数边界。按结构切分就是沿这些边界下刀，并把章节路径写进块文本前缀与元数据，这样即使块里不含标题也知道它在讲什么。

结构切分还要为特殊元素开小灶：表格整块保留，按行拆分时把表头复制到每一行，否则单看一行没有列名；列表按项切；代码按函数边界切并保留签名。它的短板是块长方差大，必须再叠一层长度上限。

语义切分

不按符号而按内容：先切成句子，逐句嵌入，在相邻句子相似度骤降处下刀，并给块长设上下界。切出的块长短不一但主题集中。代价是索引阶段要多跑一遍全量嵌入，在线增量入库还得管队列与限速；阈值也敏感，同一段落在不同模型下边界不同；主题平稳漂移的长论述仍会切出超长块。

递归切分

先大后小、逐级降级：维护一个分隔符优先级序列，先按段落分隔（连续空行）切，单块仍超预算就降到换行，再降到中文句末标点、逗号，最后才按字符硬切。它是结构切分与定长切分的折中，也是当时主流框架里切分器的常见形态。

四种策略常要组合使用：

策略 适用文档形态 主要风险 建议起点

层级分块与父子块检索

块越小定位越准，上下文却越薄，这是一对天然张力。层级分块把两个角色拆开：小块（一句或两三句）做匹配载体，父块（段落、小节乃至整节）做上下文载体。向量库里只索引小块并带上父块编号，命中的小块只负责定位，真正进入提示词的是它的父块。

附带好处有三点：去重时按父块折叠，避免同一章节被拆成多条记录重复占位；父块本身已覆盖兄弟块，拼装时不必再大范围扩展邻块；“块大小”不再直接决定上下文长度，调参更平滑。代价是索引存储翻倍，父块粒度本身又成了一次分块决策。

块大小、输入窗口与中文分句

块大小由窗口决定，不由审美决定

每个嵌入模型都有最大输入长度，超出部分通常被静默截断：不报错，只是尾部内容压根没进向量。所以第一步是用所选模型的分词器统计长度分布，看 P95 与最大值是否越界。当时可用的选择大致两类：通用短文本模型窗口在几百 token 量级（示意），块就得相应切小；支持长输入的模型能吃到上千 token（示意），但真把块塞满窗口，向量区分度反而下降。

三点实操注意。其一，附加文本（章节路径、标题、日期）也占预算，别按正文上限切完再追加。其二，嵌入窗口与生成窗口是两笔独立的账，召回装得下十个块，不等于提示词里还留得下问题与指令。其三，换嵌入模型必须重建索引，不同模型的向量空间互不兼容。

中文分句与标点处理

结构切分与递归切分的下层都依赖句子边界，而中文分句比英文更容易出错。常见坑有四个：数字里的句点被当终止符，把版本号切成两段；省略号与连续标点被重复切开；引号、括号收尾时真正的边界在标点之后；标题行与表格行本不是句子，却被当成句子切碎。工程上先归一化（全角半角统一、空白折叠、去掉标记符号），再用带保护的规则切分，并把过短碎片回粘：

元数据设计与检索过滤

块入库时要带上一组字段，它们决定检索能过滤什么、生成能引什么、上线后能审计什么。最小集合是：来源标识、章节路径、更新时间与入库时间、语言、文档类型、权限标签，加上为拼装与评测服务的父块编号、前后邻块编号和原文起止偏移。

过滤要区分前过滤与后过滤：前过滤把条件交给向量库，在候选集里筛完再取前 k 条；后过滤先取前 k 条再到应用层丢弃不合条件的，看着省事，实则因大量结果被丢弃而凑不满名额，表现为“只有特定部门文档能答的问题，系统回答不知道”。设计字段要守住一条原则：过滤条件得能落到扁平字段上。

权限标签最讲一致性：索引时按文档可见范围写死标签，查询时按用户身份展开可查标签集合，两侧口径要由同一份配置生成，对不齐就是越权泄露，默认应当匹配不上即拒绝。时效过滤同理，时间要显式存在元数据里。

上下文拼装：邻近块扩展、去重与截断

召回拿到的是离散块号，直接按分数顺序塞进提示词并不理想，要分三步。

第一步是邻近扩展。命中块往往只覆盖答案的一部分，纳入它的前后邻块能补回被切掉的前提；扩展要设上限（示意：每处最多前后各一块），并把扩展块标为“补充上下文”而非独立证据，否则召回一条就吞掉整节。

第二步是去重。重叠造成的文本重复按归一化后的文本哈希判，同一段落被两个父块覆盖按 parent_id 折叠，多查询造成的同源重复按文档加区间判。把同一文档里相邻的块并成连续区间，就只消耗一次预算：

第三步是排序与截断。拼装顺序按文档先后而不是按分数排，把最相关的那块放在靠近问题的位置即可，往中间硬插会打断论证链条。截断按剩余 token 预算从低分区间开始丢，保留的每个区间都要完整。

查询侧优化：改写、多查询与 HyDE

召回不好，有时责任不在文档侧而在查询侧：用户输入往往短、带指代、缺少领域限定词。

查询改写与补全，是把对话里的“它”“上面那个”换成具体实体，把口语问法改成文档里更可能出现的表述，必要时补上同义词与缩写；改写前的原查询要一并送进检索再合并，免得改写跑偏时全线落空。

多查询，是让模型生成若干语义等价、表述不同的查询（示意 3 条），分别检索后按名次融合。常用的倒数排名融合只依赖名次不依赖分值，绕开了不同查询分值不可比的问题：

HyDE 是让模型先就问题写一段假设答案，再用这段假设文档的向量去检索真实文档，把“短查询对长段落”的错位换成“长文本对长文本”。术语提示充分的领域它能改善召回，但假设文档自带错误前提时会把检索带偏，还多付一次调用，是否保留必须由评测说话。查询侧只负责把候选集合做对、做大，把候选排到最前是重排序的工作。

用离线评测集比较分块方案

体感比较不出分块方案。准备五十到两百条真实问题（示意），每条由熟悉业务的人标注答案出现在原文哪一段；标注的是原文字符区间而不是块编号——块编号随策略变化，按块标注等于每换一次分块就重标一遍。

跑法上固定嵌入模型、向量库、前 k 条与查询处理，只改分块参数，一次只动一个变量。除 Recall@k 外还要看命中块的平均长度（上下文够不够）与总块数（索引成本）。指标测不出“块切太碎导致模型没法作答”，所以要补人工评分：抽样若干条按“是否足以作答”打一到三分（示意量表）。线上被问错的问题，是评测集最好的补充来源。

常见误区

第一，一味追求小块。小块向量干净、指标好看，但答案的前提常在上一段，模型于是自行补全，答得流畅却夹带并不存在的事实；该问的是“一个块能不能独立支撑一个问题”。第二，忽略表格与代码块：表格按行切碎就失去列名，代码从函数中间切断就失去签名，应把它们当原子单元，超长时按行列或函数边界拆并复制表头。第三，把重叠当补丁却不去重。第四，元数据只存来源不存结构。第五，换嵌入模型不重建索引。第六，靠一次提问的观感定策略，改来改去回到原点。

小结

分块是 RAG 里少数能改变问题约束的环节：检索只能从块里挑，挑不出没切进去的完整性。落地顺序建议是先用递归切分加长度上限跑通基线，再为表格与代码开专用切分器，最后才试父子块与语义切分这类更贵的方案，每一步都用同一份评测集验证。块大小由嵌入窗口和“块能否独立作答”共同决定，元数据要覆盖来源、章节、时间与权限，拼装时记得邻近扩展、区间合并与按预算截断，查询侧只负责把候选做对，排序交给重排。
