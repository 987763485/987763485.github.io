Rust Web 框架 axum 实战

本文属于《Rust 学习路线》第 40/68 篇
上一篇系列目录下一篇

axum 是 tokio 团队维护的 Rust Web 框架，本文以 0.6 为准。它的特点不是“快”，而是抽象诚实：路由、中间件与处理器全部还原成 tower 的 Service 与 Layer。全文依次讨论路由组合、提取器、状态共享、错误处理、中间件分层、优雅关停与测试。0.7 最近已经发布，但配套的中间件 crate 与示例仍在迁移，所以下面所有代码都按 0.6 的公开 API 给出；签名形式不完全确定的地方，只用文字描述流程。

设计取向：服务、组合与函数即处理器

axum 与 actix-web 的差别不在跑分，而在抽象层。actix-web 的处理器体系围绕自己的 Actor 模型与专用 trait 构建，686 那篇已经讲过它的运行模型，本文不重复；axum 直接把 tower 的 Service 当作唯一抽象：路由器是 Service，套上中间件之后还是 Service，交给服务器监听端口，也不过是把一个 Service 适配成“每个连接一份”的形式。

第一个体现是 handler 即函数。axum 没有把 URL 绑到方法上的属性宏，路由就是把函数作为参数传进去：

任何异步函数，只要参数都能从请求里提取出来、返回值能转成响应，就自动满足 Handler 约束，不需要实现 trait，也不需要写宏。好处是报错点集中在函数签名上：类型没实现 FromRequestParts 时，编译器会直接在这个函数上给出诊断，而不是在路由注册深处报一堆 trait 长错误。代价是要习惯“函数即路由”：处理器是被当作值传递的普通函数。

第二个体现是提取器的顺序性。只读路径、查询与请求头的类型实现 FromRequestParts，可以出现在参数列表的任意位置；消费请求体的类型实现 FromRequest，只能作为最后一个参数，而且最多一个。这不是风格约定，而是由 Request 的所有权决定的——body 是一个流，读掉了就没了。

路由与 Router 的组合

Router 是路径到处理器的映射表，能力可以归为三类：注册单条路由、把若干路由合成一棵树、把子树挂到某个前缀下。稍具规模的 API 靠后两类组织，而组合方法都返回新的 Router，所以装配读起来像搭积木而不是写配置：

同一路径上按方法分发靠的是 get(list).post(create)：get 返回一个方法路由对象，继续点 post 是往同一条路径追加方法，而不是注册新路径。需要更细的控制时用 routing::on 指定单个方法，或用 routing::any 让所有方法走同一个处理器——后者对 REST 接口通常是坏味道，因为它放弃了方法级语义。

merge 把两棵树在当前位置拼接，前缀不变；nest 把一棵完整的子树挂到某个前缀之下：

nest 之后子路由注册的路径相对于前缀，匹配成功后处理器看到的路径又会被剥掉前缀。坑在斜杠：前缀末尾不写多余的 /，集合资源统一用 /，单个资源用 /:id，整棵树保持一致，能避开绝大多数“本地能通、加了网关就 404”的问题；要处理带斜杠的变体时，显式注册两条路由更稳妥。

提取器：路径、查询与请求头

提取器把请求里的原始字节变成业务能用的 Rust 类型，价值在于把参数校验前移到类型系统。路径参数用 Path<T>，T 可以是元组或实现 Deserialize 的结构体；段数与占位符不一致时是运行时 400 而不是编译错误，得靠测试兜住。

Query<T> 背后的反序列化按“一个键对应一个值”的语义工作，所以可选参数最省心的写法是 Option<T> 配 #[serde(default)]；真正的多值参数不要指望直接解成 Vec<T>，要么解成 HashMap 再自己拆，要么引入专门按 query string 语义处理的 serde 后端 crate。

需要鉴权信息时，先取 HeaderMap 再手工解析最稳，它对版本升级完全免疫；0.6 还提供 TypedHeader<T>，能把常见的 Authorization 头解成类型，但跨版本迁移时容易出问题。自定义提取器实现 FromRequestParts 即可，注意 Rust 1.72 还没有稳定的 trait 内 async fn，要挂 #[async_trait]：

多个提取器按声明顺序依次执行，任一个失败就立刻短路，把它的 rejection 转成响应返回。所以我们不需要在 handler 开头写一串 if let 做参数检查：把非法值挡在类型层，是 axum 工程组织里第一个应该建立的直觉。

JSON、表单与请求体上限

最常见的请求体提取器是 Json<T> 与 Form<T>，两者行为差别很大，值得放在一起对比。

Json<T> 会先检查 Content-Type 是不是 JSON，不是就拒绝；这条规则在联调阶段很烦，但能挡掉一类真实的跨站请求，建议保留。缺请求体、UTF-8 非法、类型不匹配、语法错误、请求体超限，这几种失败默认都返回带说明文本的 4xx，其中超限对应 413、Content-Type 不对对应 415。

Form<T> 只接受 urlencoded 编码，不支持嵌套结构，表单里写 a[b]=1 不会自动变成结构体；文件上传要打开 multipart 特性后使用流式提取器，应当边收边校验或落盘，而不是整块读进内存。

真正容易出事的是上限。axum 对请求体有一个默认上限，量级在两兆字节附近，对普通 JSON 接口足够，对上传接口则可能是事故源头。限制通过 DefaultBodyLimit 这一层设置，可以全局设，也可以只挂在某条路由上：

两条建议。其一，上限按路由分层设，把上传接口的限制放在它自己那棵子树上，别让一个全局大上限保护所有接口；其二，若想区分“请求体太大”和“请求体格式不对”，就不要直接用 Json<T>，而是先按字节取出请求体、自己判断长度，再手动反序列化。

状态共享与依赖注入式的 handler 签名

axum 没有容器，共享状态靠 State<T> 提取器，T 必须 Clone，因为每个请求都会拿到一份克隆。所以正确写法是把 Arc 放进状态结构体里；需要互斥的可变数据也要显式用 Arc<RwLock<_>> 包一层，让克隆只增加计数而不是复制数据。

FromRef 是 0.6 里让状态设计变清爽的关键：有了它，State 不再要求 handler 拿到整个应用状态，而是只声明它需要的那一小块。于是“一个 handler 的参数列表就是它的依赖清单”这件事第一次真正成立——需要连接池就提取 State<Pool>，需要配置就提取 State<Config>，业务代码看不到 AppState 这个上帝对象。

这段签名有两个要点。其一，截至本文写作时，Rust 1.72 与 1.73 都还没有稳定的 trait 内 async fn，接口式依赖注入仍然要靠 #[async_trait]，代价是每次调用多一次装箱，而这个开销对 HTTP 处理器不值得优化。其二，State<Arc<dyn UserRepository>> 要求 AppState 为它提供 FromRef 实现，测试时把实现换成一个返回固定数据的 mock，路由与中间件一行都不用改。这就是 axum 版的依赖注入：没有运行时反射，全靠类型层面的函数签名。

错误处理与 IntoResponse

axum 的错误处理哲学是每个 handler 自己决定怎么把错误变成响应，框架只提供 IntoResponse 这个口子。常见做法是让所有 handler 返回 Result<T, AppError>，再给 AppError 实现一次这个 trait，把状态码与对外文案集中在一处：

实现方式值得说明：IntoResponse 只有一个把自身转换成 Response 的方法，而 (StatusCode, Json<_>)、HeaderMap 加 body 这类元组和类型本身就实现了它，所以上面最后一行只是把组合好的值再转换一次。自己实现时容易忽略一点：一旦选择实现它，框架就不知道你原本想返回什么状态码，每个分支都必须显式给出状态；漏掉的状态码会退化成默认的 200。

? 的传播靠 From：为 RepoError、serde_json::Error 各写一个 From 转成 AppError，handler 里就可以直接问号。提取器失败走的是它自己的 rejection，默认文案是人读的纯文本；如果项目要求所有错误都是同一个 JSON 结构，就把入参声明成 Result<Json<Login>, AppError>，手动把 rejection 映射进来。

最后是 #[debug_handler]：Handler 的实现由宏生成，签名写错时报错会淹没在泛型展开里，挂上它，错误会回到函数签名本身。

中间件分层：Tower layer 与函数级中间件

axum 不发明中间件机制，直接复用 tower 的 Layer：一层中间件就是把一个 Service 变成另一个 Service 的构造函数。请求穿过各层的路径如下：

flowchart TD
    A["TCP 连接"] --> B["HTTP 报文解析"]
    B --> C["最外层 layer"]
    C --> D["内层 layer"]
    D --> E["Router 路径匹配"]
    E --> F["提取器按顺序执行"]
    F --> G["handler 业务逻辑"]
    G --> H["IntoResponse 生成响应"]
    H --> I["逆序回到外层并写回连接"]

顺序只需记住一条：链式调用里越晚写的 layer 越靠外，请求先经过它、响应最后经过它。layer 作用于这棵 Router 上的所有路由，包括后来 merge 进来的部分；只想覆盖当前已注册的几条路由时用 route_layer，做“某些路由免鉴权”时选错就会出现公开接口被拦或者内部接口漏防。与框架无关的通用层直接从 tower-http 取，日志用 TraceLayer、跨域用 CorsLayer，没必要自己写。

需要共享状态用 from_fn_with_state，否则用 from_fn。中间件里提前读到的信息若想传给 handler，放进请求的扩展位最干净，因为 next.run 传的是整个请求。分层建议：观测、跨域、压缩放最外层的通用 layer，鉴权与限流放函数级中间件，参数合法性仍交给提取器和 handler。

运行时、启动与优雅关停

axum 0.6 的 Server 建在 hyper 与 tokio 之上，它自己不管理线程：#[tokio::main] 起的是多线程运行时，并发度由运行时的 worker 线程数决定，而不是框架层面的 worker 概念。这一点和 actix-web 需要显式安排 worker 与 CPU 核数不同，是迁移时最容易找错地方的一处。tokio 运行时本身的模型，802 那篇已经讲过，这里只说服务怎么挂上去：into_make_service 把 Router 变成一个“每个连接产出一个服务”的工厂，serve 把它交给监听器。

handler 需要知道对端地址（限流、审计常用）时，要在工厂上显式声明连接信息类型，之后才能用 ConnectInfo<SocketAddr> 提取。

关停是生产环境里最容易漏的一块：

with_graceful_shutdown 接收一个 Future，它完成时服务器停止接受新连接，并把存量请求跑到结束。这里有三个坑。其一，进程管理器发出的信号不止 SIGTERM，只监听 ctrl_c 的服务在编排环境里往往是被强杀的；其二，如果某个 handler 卡在下游超时上，关停会一直等，要用 tokio::time::timeout 给一个兜底超时；其三，spawn 出去的后台任务不会跟随关停，退出前要主动通知它们并等待收尾，连接池也应在服务停止之后再释放。

用请求驱动 handler 的测试

因为 Router 本身就是 Service，测试不需要真实端口：把一个请求直接喂给它，拿响应回来断言。前提是把装配抽成一个纯函数，让 main 与测试共用同一棵树：

oneshot 来自 tower 的 util 特性，它把一次调用当成一个请求走完整个 layer 栈和路由匹配，中间件、提取器、错误映射都会被真实执行，这是这类测试最有价值的地方：测的是装配后的服务，不是被 mock 过的业务函数。要注意 oneshot 不经过 into_make_service，拿不到 ConnectInfo，测依赖对端地址的逻辑时要在请求的扩展位里手动塞一个进去；带请求体的用例只需把 Body::empty() 换成序列化出来的字节，并设置 Content-Type。

分层建议：业务规则用直接 await handler 的单元测试覆盖，它本来就是普通异步函数；状态码、响应结构、鉴权是否生效用请求级测试覆盖；只有要验证端口与代理行为时才起真实进程。

小结

axum 的所有设计都服务于把 Web 服务还原成可组合的函数与类型：路由是 Router 的组合，参数是提取器，依赖是 handler 签名，错误是一次 IntoResponse 的实现，横切关注点是 tower 的 layer，启动与关停交给 tokio 运行时。写 axum 项目的顺序不是先找配置项，而是先想清楚这几层各放什么：参数校验前移到类型、状态按最小依赖切分、错误集中映射。

工程组织上有两条约定值得抄：每个模块只导出一个 router()，整棵树由 build_app 组装，main 与测试共用同一份装配代码；状态用 FromRef 拆分，handler 只声明它真正需要的依赖。

与 actix-web 的取舍，一句话足够：要 Actor 模型与更成熟的周边生态选 actix-web，要 tokio 官方系与 tower 的可组合性选 axum。
