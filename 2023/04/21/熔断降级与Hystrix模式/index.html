熔断降级与 Hystrix 模式

本文属于《Go 微服务架构》第 24/35 篇
上一篇系列目录下一篇

微服务之间的调用一旦形成网状依赖，单个下游的抖动就可能沿调用链放大成整体故障。Netflix 开源的 Hystrix 把隔离、熔断、降级封装成成套的模式，本文拆解这些模式的动机与要点，并说明它进入维护模式之后该如何吸收其思想。限流算法、Sentinel 实操与落地流程另有专文，本篇只聚焦 Hystrix 的模式本身。

Hystrix 要解决的问题

单体时代模块间是进程内调用，一个模块出问题最多是逻辑异常；拆成微服务后，同样的调用变成跨进程同步请求，出现两类新问题。

第一类是依赖故障引发的级联雪崩。订单同步调库存，库存同步调商品；商品因慢查询把响应从几十毫秒拖到数秒（示意）时，库存线程大批阻塞、线程池耗尽，订单的调用随之堆积，连无关的营销接口也被拖垮。故障没有变大，只是”等待”被一层层传染了。

第二类是资源耗尽。同步 RPC 的每次调用都占用调用方的线程与连接，完成前不归还；下游变慢意味着在途请求变多，线程池、连接池会先于 CPU 到达上限。更糟的是很多失败并没有明确失败——连接还挂着、响应还会来，只是迟迟不来；没有边界的等待会把局部故障拖成全局事故。

Hystrix（HYSTrix 与 circuit breaker 的组合词）的应对是：不让调用无限期等待，即超时；不让失败的调用继续占用资源，即熔断与快速失败；失败也要有输出，即降级回退。再配以舱壁隔离限制单个依赖的资源、请求缓存与折叠削减重复。它的核心假设很务实：故障是常态，把”故障时怎么办”写进每次调用的定义里。

断路器三态与滑动窗口统计

超时是被动防线，断路器是主动防线。它沿用”过载即跳闸”的电闸思路：断路器是一个三态有限状态机——关闭（Closed，正常放行并统计）、打开（Open，拒绝所有请求直接走回退）、半开（Half-Open，放一小批试探请求，用其结果决定恢复还是继续拒绝）。

    C -->|试探成功| A
    C -->|试探失败| B

半开不是”恢复观察期”，而是一次昂贵的试验：只放行有限请求，整体成功则闭合并清零统计窗口，仍有失败则立即重开。

判断该不该跳闸不能靠瞬时错误率——单个毛刺就会触发熔断、让系统在跳与恢复间震荡。Hystrix 的答案是滑动窗口统计：把时间切成小格子，滚动记录最近一段时间内的请求数与失败数，只在窗口上计算错误率，平滑抖动又让老数据退出。跳闸需同时满足两个条件：窗口内请求数达到最小样本量，且错误率超过阈值。常见默认值举例（示意，实际须按压测调）：10 秒窗口内至少 20 个请求、错误率过半才打开；打开后冷却约 5 秒进入半开。

还有两个细节：”错误”的定义可配置——超时、连接失败通常计入，业务异常可选择排除，避免把正常业务失败误判成依赖故障；统计按依赖维度分组，同一个下游命令共享一个断路器而非全局一个，爆炸半径恰好圈在出问题的依赖上。一句话分清方向：限流防”进来的流量太多”，熔断防”出去的调用太慢”，两者互补，限流算法本身不在本文展开。

Fail-fast 与降级回退

断路器打开后请求并没有消失，只是换了结局：不再排队，立刻失败。快速失败是与其让第 1001 个调用者继续为大概率无响应的下游排队，不如直接返回；它解决”不亏待自己”，回退（fallback）解决”怎么交代业务”——调用失败时返回的兜底逻辑。

回退要当作独立的设计决策，而非异常处理的副产品。质量从好到差大致是：返回缓存的上次结果，用户几乎无感；返回降级数据，比如推荐挂了返回热销榜；返回中性默认值；最后才是干脆地返回空或错误码。常见坑是回退又依赖远程服务——故障时兜底路径往往也在恶化，回退反成新阻塞源；回退应只依赖进程内状态或本地数据，写得薄而硬，因为它自身抛异常会触发再次回退、形成递归。另外回退不等于吞异常：失败仍要计入监控，否则故障会被兜底数据掩护住，等缓存过期才集中爆发。

舱壁隔离：线程池与信号量

船坞让一艘船漏水时不至于整艘沉没。同理，每个依赖的调用应占用自己的一份资源配额，而非共享一个大队列。Hystrix 提供两种舱壁。

线程池隔离：每个命令键拥有独立线程池，调用被提交到专属线程池执行，调用方线程等结果。隔离彻底——下游卡死耗尽的只是它自己的线程，其他依赖毫发无伤；且执行跨线程，超时后调用方可以真正脱身。代价是线程切换与队列开销，以及池数量随依赖数线性增长：池大了失去隔离意义，池小了正常流量都可能被自己拒掉。

信号量隔离：不起新线程，只在调用方线程上用计数器限制该依赖的在途并发数，超限直接走回退。几乎没有切换开销、配置简单，但隔离弱一档：只限并发量、无法在超时后释放被占住的线程，适合响应很快或访问本地资源的依赖。

超时与重试的相互作用

超时是一切容错的起点：没有它，断路器等不到错误样本，舱壁令牌还不回来。但超时与重试叠加，是生产环境著名的事故源。

第一个坑是超时预算层层失配。A 对 B 设 800 毫秒超时，B 内部对 C 也设 800 毫秒（示意），A 的等待就会覆盖 B 的完整处理，超时形同虚设。预算应沿调用链递减、且能容纳下游”超时加回退”的全部耗时；必须让下游比上游先死心——上游先放弃，下游只是白白执行。

第二个坑是重试与超时相乘造成的流量放大。单次超时 800 毫秒、重试 3 次（示意），最坏一个请求占用约 2.4 秒；下游因过载才变慢时，重试等于把流量放大三倍砸回去，火上浇油。Hystrix 对此保守：命令层重试交给上层组件（Netflix 体系里由 Ribbon 在负载均衡层做），且明确警告重试存在时，超时计时器必须覆盖整个重试过程而非单次尝试，否则舱壁容量核算全错。实践里还要加退避与抖动；对参数非法、断路器已打开这类错误坚决不重试。

定超时的常用做法：取下游历史 P99 耗时（示意 300 毫秒）乘安全系数设为超时，余下交给回退。过短误杀偶发慢请求，过长失去快速失败意义——它应是被测量校准的参数，而非模板里的常数。

请求缓存与请求折叠

前面的模式都在处理失败，Hystrix 还顺手处理重复：一次页面渲染查同一个商品十余次，这类情况很常见。请求缓存让同一作用域内相同缓存键只真正执行一次，其余复用结果。两个陷阱：一是作用域边界——缓存绑定在请求上下文上，异步环境里传播不对就会出现”每线程各一份缓存”，与 Go 的 context 传递是同一类工程问题；二是新鲜度——缓存放大了故障时旧数据的占比，写后读敏感的业务要慎选键与生命周期。

请求折叠解决”短时间内很多请求问同一件事”：在一个很小的合并窗口（十毫秒量级，示意值）内把相同命令合并成一次批量调用。高频小请求场景收益可观，代价是一小段固定延迟，且要求下游真有批量接口——没有批量接口硬折叠就是伪批量。两个机制本质是读优化，对写请求毫无意义，只在”重复率高、单次代价大”的依赖上值得启用。

Hystrix Dashboard 与 Turbine 的思路

容错机制最怕”配了但没人知道有没有生效”。Hystrix 把运行数据暴露成可观测面：每个实例经流式端点持续输出所有命令的指标快照——成功、失败、超时、短路（被断路器拒绝）、资源池占用等——Dashboard 订阅该流，画出以命令为单位的气泡图；实例一多，逐个订阅不现实，Turbine 就把一群实例的指标流合并成一条集群级汇总流，监控侧只消费这一条，在当时解决了指标数据的收敛问题。启示有二：”短路”应单列为独立指标，被熔断拒绝与被超时杀掉的请求混在一起，会掩盖快速失败救下了多少资源；断路器的决策依赖运行时统计，统计管线就是容错系统的一部分——指标丢了，断路器是在盲跳。

2023 年的现状：维护模式与后继者

必须交代前提：Hystrix 已不是被推荐的新项目选型。Netflix 于 2018 年宣布其进入维护模式，只修缺陷、不做新功能——它深度绑定的线程池隔离开销偏大，而 Java 生态整体转向异步与非阻塞；Spring Cloud 也在同年弃用 Hystrix 作为熔断实现，推荐转向 Resilience4j。

Resilience4j 是最直接的继承者：断路器、限流、舱壁（它就叫 Bulkhead）、重试、超时被拆成可自由组合的装饰器，默认不再强制线程池隔离——理解 Hystrix 的模式，等于拿到 Resilience4j 的词表。阿里开源的 Sentinel 走另一条路线：以流量控制、熔断降级、系统保护为中心，规则维度更细、控制台开箱即用，实战配置与落地另有专文，这里只需知道三态断路器与滑动窗口统计在其熔断规则中有对应物。Go 世界则用 sony/gobreaker 一类极简断路器配合 context 超时与有限并发。库会过时，模式不会——后来的每个库，几乎都是在修正 Hystrix 的某几个决策。

什么时候不该上熔断

熔断不是防腐剂，以下场景强行上手只会引入新的故障面。

其一，不具备”失败可回退”的条件。交易链路的扣款、下单调用，断路器打开后回退只能抛错，与直接失败相比没有增益倒有损害：半开放行的试探请求可能撞上已恢复的下游，制造重复扣款疑虑。这类强一致操作该用幂等、对账与人工兜底。

其二，调用是异步任务或消息投递。队列生产端本就该容忍延迟，熔断的”拒绝”语义反而制造丢弃；该保护的是消费端，且背压与限流更对症。

其三，故障偶发而非持续劣化。滑动窗口要求错误有时间聚集性；每万次随机失败一次的依赖（示意），一次重试就能抹平，断路器只会把毛刺放大成一段人为降级。

其四，可观测性还没建好。指标缺位时上熔断，等于装了个读不出仪表的安全阀，跳闸没人知道，恢复全靠猜。

小结

本文沿 Hystrix 拆解了一组容错模式：假设故障必然发生，用超时终止等待，用三态断路器与滑动窗口统计实现快速失败，用回退给失败一个业务上可接受的出口，用舱壁限制单个依赖的爆炸半径，用缓存与折叠削减重复，用 Dashboard 与 Turbine 让决策看得见。Hystrix 已进入维护模式，但它的概念词表被 Resilience4j、Sentinel 与 Go 生态原样继承，学模式远比利旧库划算。落地建议：先测量下游的失败分布与长尾，再决定保护谁、用什么模式、失败后给用户看什么。
