领域驱动设计 DDD 实战

本文属于《Go 微服务架构》第 6/35 篇
上一篇系列目录下一篇

领域驱动设计的概念清单并不长，难的是把它们翻译成目录结构、包依赖、一次事务的边界和一段能被同事评审的代码。本文以一个企业差旅中台为例，从事件风暴推到限界上下文，再推到聚合、实体与值对象、领域服务与仓储、领域事件，最后落到 Go 项目的目录组织与一次完整的实现推演，并给出常见误用清单和「什么时候不该用 DDD」的判据。适合已经读过入门材料、准备在真实项目里落地的后端工程师；术语复述不在本文范围，本文只谈落地时的取舍。

案例、范围与几条边界

为了让推演有据可依，本文自始至终使用同一个业务：某制造企业的差旅中台。员工提交差旅申请单，系统按职级与目的地标准校验花费，预占该成本中心的年度差旅额度，走一到两级审批，通过后允许在合作供应商处预订机票与酒店；行程结束后提交报销，系统把预占转为实扣，并生成给财务系统的月度结算单。选它作案例，是因为它同时具备建模要处理的四种复杂度：明确的业务不变式、多个团队与外部系统、规则每年随政策调整、数据要长期留存并支持审计。

先说清本文与相邻主题的分工。实体、限界上下文、统一语言这些基础概念本文假定读者已经掌握；上下文映射关系的类型学属于另一个题目，本文只谈这些关系在代码依赖层面的表现；微服务该拆到多大是服务治理的问题，本文只关心「先在代码里立住边界」；读写模型分离则是另一篇的主题。

还需要声明两条写作立场。第一，DDD 是关于「复杂度放在哪里」的决策方法，不是框架，「装了某个库就完成 DDD」的说法都值得怀疑。第二，落地顺序是从业务不变式出发倒推代码结构，而不是先画六边形再把业务往里塞。本文示例使用 Go 1.20，仓储以关系型数据库为例。

从事件风暴到限界上下文

事件风暴：把流程拆成命令、事件与不变式

建模工作坊的价值不在于贴了多少便利贴，而在于逼出三样东西：业务事件的时间顺序、触发事件的命令、命令执行时必须成立的规则。我们的做法是让业务方（差旅专员与财务各一人）、技术负责人和两名开发围在一面白墙前，用颜色区分四类便利贴，全程禁止出现表名、字段名和接口名。

第一步铺事实：按过去时态写领域事件，例如「差旅申请已提交」「额度已预占」「申请已批准」「行程已完成」「报销已核算」「结算单已生成」。第二步补命令：谁在什么角色下触发了它——「员工提交申请」「部门主管批准」「财务触发核算」。第三步找规则：在每个命令旁边追问「什么情况下这条命令必须被拒绝」。这一步是整场工作坊的重头戏，也是后续聚合边界的唯一可靠来源。差旅案例问出的拒绝条件有：金额超出该职级该目的地的标准上限；当期额度剩余不足；出发日期早于当前日期；同一员工存在区间重叠的未结束行程；审批通过后要改行程；报销金额大于预占且未附说明。

flowchart TD
    A[员工填单] --> B[提交申请]
    B --> C{政策校验}
    C -->|不通过| D[驳回并说明条款]
    C -->|通过| E[预占成本中心额度]
    E -->|额度不足| F[退回补充说明]
    E -->|成功| G[一级审批]
    G --> H[超标准时二级审批]
    H --> I[申请批准]
    I --> J[允许供应商预订]
    J --> K[行程完成]
    K --> L[报销核算]
    L --> M[预占转实扣]
    M --> N[月度结算生成]

第四步把规则按「由谁独自保证」分组，这一步直接产出聚合。比如「额度总和不能被透支」只涉及额度账户自身，属于一个聚合内部的不变式；「提交时必须同时满足政策上限与额度充足」涉及两个聚合，只能靠流程编排与最终一致解决。把这条区分做清楚，后面所有关于聚合大小的争论都能提前结束。

第五步固化统一语言。工作坊结束时输出一张术语对照表，左列是业务方的说法，右列是代码里的名字，并规定「同一概念全公司只允许一个英文词」。差旅案例里花最多时间澄清的两个词值得注意：「额度」在 HR 口中指职级出差标准（Policy），在财务口中指成本中心预算（Budget），系统里必须拆成两个概念；「预占」与「扣减」是两种状态，不能都叫 freeze。术语表进版本库，放在 doc/ubiquitous-language.md，评审时对不上术语表的命名按缺陷处理——这件事的收益主要来自三个月后的第二次迭代。

从规则分组到限界上下文：边界要先于服务

把上面问出来的不变式按「由谁独自保证」聚类，自然得到几个模型单元：申请单（行程、金额、状态、审批记录）、政策（职级标准、目的地档位、生效区间）、额度（成本中心、期间、预占与实扣）、履约（供应商订单、退改签）、结算（月度账单、凭证号、过账状态），再从外部借两个模型：组织架构与人员职级（HR 系统是唯一权威来源）、账号与权限（来自统一身份平台）。

判据是问题域而不是部署单元。我们的分类结论：申请单与额度是核心域（业务竞争力所在，规则每年变，值得投入建模成本），政策是支撑域（企业自己维护但通用性较强），履约与结算是通用域（复杂度主要由外部系统承担，我们只做适配），组织人事完全外包。核心域写丰富的领域模型，通用域用尽可能薄的适配代码——把火力集中在核心域，是控制落地成本的关键手段。

接下来给每个限界上下文定职责与所有权。产物是一张两列表：上下文名称，以及「它独自保证哪些规则」。

限界上下文 独自保证的规则 权威数据
request（申请单） 状态机迁移合法性、通过后行程不可变更、区间重叠检查 申请单及其审批记录
budget（额度） 预占与实扣之和不超过当期预算、期间锁定后禁止写入 额度账户与占用流水
policy（政策） 标准上限计算、政策生效区间的选择 职级标准表
settlement（结算） 月度账期闭合、结算单与凭证一一对应 结算单
org（组织，外部） 无规则，只提供人员、成本中心、职级的当前视图 HR 系统

注意「独自保证」这四个字的分量：一条规则只能有一个上下文有权最终判定它是否成立。额度是否够用只有 budget 能回答，request 需要这个答案时只能向它提问或异步等它回应，绝不允许在自己代码里再算一遍 available = limit - reserved - spent。这一句看似平淡，实际杜绝了落地中最常见的一类腐化：同一条规则在两个模块各写一份，某天政策变了只改了一处。

上下文映射在代码依赖里长什么样

映射关系如果只停留在架构图上，一周后就会被 import 语句推翻。我们的做法是把每条关系翻译成一个可检查的代码约束，让 CI 承担 enforcement 的角色。

最核心的一条是依赖方向。上下文之间只允许「消费方声明接口、提供方实现适配」这一种依赖形态，即依赖倒置：request 包内定义自己需要的额度查询接口，budget 包或者 infrastructure 层提供实现。Go 的包级别可见性用 internal 目录配合得很自然：每个上下文独占一个子树，外部只能通过显式导出的 port 接口访问。

对应的依赖图与几条硬规则如下。

flowchart TD
    api[platform/httpapi] --> req[request]
    api --> stl[settlement]
    req --> bud[budget]
    req --> pol[policy]
    req --> org[platform/hrclient]
    stl --> bud
    per[platform/persistence] --> req
    per --> bud
    per --> pol
    per --> db[(关系型数据库)]

图的读法是箭头指向被依赖的一方。注意 platform/persistence 指向各领域包而不是相反：仓储实现要实现领域包里声明的接口，所以它依赖领域，领域不知道仓储存在。这条方向是整洁架构里「依赖规则」在 Go 项目中最直接的体现。

规则一：上下文包之间禁止双向 import，图上任何一条边都要能在评审里说明理由。规则二：每个上下文独占自己的表，跨上下文读数据要么调用对方导出的接口，要么订阅对方事件在本地留一份只读副本；跨 schema JOIN 视为破坏边界，评审直接拒绝。规则三：platform/hrclient 必须把 HR 系统的数据结构翻译成我们自己的类型——HRUserProfile 不允许出现在 request 包内，Employee 是我们自己的定义，字段少而稳定；这层翻译代码也是日后更换 HR 供应商时唯一要改的地方。规则四：事件引起的反向依赖不能出现在编译期，request 发布「申请已批准」后，budget 若要动作只能通过订阅回调或独立进程，绝不允许 budget 反向 import request。

把规则交给机器执行比写进文档有效。CI 里加了一段轻量检查：用 go list 导出包依赖，再比对白名单。

这段脚本不到十行，却把「整洁架构的依赖规则」从口头共识变成了构建失败——新来的同事第一次提交就撞上了它，比任何文档都有效。

聚合、实体与值对象

聚合设计：不变式边界决定一致性半径

聚合不是「一张主表加几张从表」，而是一次事务写入的最小完整单元。我们把它拆成三条可执行的准则，每条都能用一句问题来检查。

准则一，不变式的边界就是聚合的边界。所有「必须同时成立」的规则，涉及的成员必须在同一个聚合里，由同一个聚合根在同一个方法里检查。申请单聚合内的规则有：状态只能按合法路径迁移（草稿 → 已提交 → 审批中 → 已批准/已驳回 → 已完成）、已批准不能再改行程、审批记录数不能超过政策要求的级数、出发日期不得早于填单日期。这些规则作用在同一份内存对象图上，所以天然属于一个聚合。

准则二，聚合要小。判断标准不是字段个数，而是「一次命令要加载和锁定多少对象」以及「两个并发命令撞在同一个聚合上的概率」。初版设计里我们犯过一个典型错误：把额度账户、所有成本中心的占用明细、关联申请单的快照全塞进同一个聚合，理由是「预占时要校验总额」。压测暴露两个问题：一次预占要加载几百行明细，聚合重建耗时数十毫秒；月底集中提交时同一成本中心的申请全部串行化，乐观锁冲突率超过 30%。改造方案是把明细拆出聚合，聚合根只保留「当期预占额与实扣额」两个累计值，明细退化为可独立查询的流水表，二者靠「写流水必须同时更新累计值」这条原子操作保持一致，加载代价从数百行降到一行。

准则三，跨聚合永远用 ID 引用，不用对象引用。申请单聚合里不持有 BudgetAccount，只持有 BudgetID 和 RequestID 这样的强类型标识。这样做的收益不只是避免图爆炸，更重要的是它强制你承认跨聚合的规则不可能在内存里检查，只能通过流程保证。

聚合根在代码里的形态值得给一段完整示例。注意所有修改都必须经过方法，字段一律小写不导出，构造只能走工厂函数与仓储重建函数。

这里有两个取舍需要说明。第一，Submit 把「政策上限」和「需要的审批级数」作为参数接收，而不是在方法内部去查政策：跨上下文查询属于应用服务的编排职责，聚合只用传入的事实做决定，从而保持纯粹、可以脱离数据库单测。第二，版本号自增放在聚合内，因为「一次状态迁移就是一次版本推进」本身是聚合语义；仓储只负责拼 WHERE 条件。

跨聚合的强一致要老实承认做不到，然后用最终一致补。提交申请单既要状态迁移又要预占额度，我们让本地事务只修改申请单聚合并登记一条待发布事件，预占由 budget 侧消费事件后完成，失败则发出「预占失败」事件把申请单退回草稿。整条补偿链路要幂等，做法是给每条命令带业务幂等键（申请单 ID 加版本号），budget 侧用唯一索引拒绝重复预占。

实体与值对象：Go 里的具体写法

值对象在代码里的第一特征是「构造即合法」：任何 Money、Trip 的实例，只要存在就满足自身规则，不需要外部再校验一次。第二特征是不可变，所有「修改」都返回新实例。第三是按值比较，不看标识。Go 里用私有字段加构造函数实现前两条最自然。

标识用强类型而不是裸 string，这件事的收益在编译期就兑现：func Reserve(b BudgetID, r RequestID) 不会因为参数顺序写反而静默出错。

实体（比如聚合内的 Approval）与值对象的写法差异只在两点：它有标识、它可变，因此 Equal 按 ID 比较而非按字段比较，且必须通过聚合根的方法间接修改——外部拿到 []Approval 切片直接改字段是破坏封装的写法，我们让仓储重建时切片只在包内可见，对外只暴露只读视图 Approvals() []ApprovalView。

值对象还有一个落库细节：它往往对应多列（Money 对应 amount 与 currency），转换代码应当集中在一个 mapper 里。散落的 row.Cents / 100 换算曾造成过一次分位与元位混淆的线上问题，代价是把「值对象与列的映射只允许出现在持久化层的一个文件里」写进评审清单。

领域服务、应用服务与仓储：三条职责线

三者最容易混淆，用「是否携带业务规则、是否有状态、是否碰外部世界」三个问题区分即可。

构件 承载什么 禁止出现什么 Go 归属
聚合根 单聚合内的不变式与状态迁移 查询数据库、调 HTTP、发消息 request 包内
领域服务 无法归给单个聚合的规则（跨聚合计算、纯规则推导） 事务控制、DTO 转换、I/O request 或 policy 包内
应用服务 用例编排：取聚合、传事实、提交事务、发事件 任何 if 判断业务是否合法 application 包内
仓储 聚合的加载与保存、乐观锁、唯一性查询 业务规则、部分字段更新 platform/persistence

仓储的接口属于领域，实现属于基础设施，接口只到聚合粒度。这条限制值得展开：仓储不是通用 CRUD 抽象，Get 与 Save 就够了，多余的 UpdateStatusColumns、PageByCondition、CountGroupByOrg 一旦出现在仓储接口上，就说明有人正把聚合拆成字段来操作，不变式会被绕过。列表与报表根本不该走仓储，它们走独立的读模型查询端口，直接返回行数据，不构造聚合。

实现侧把版本冲突翻译成语义错误，这是仓储的职责而不是业务层的职责。

应用服务应当薄到「读一遍就像流程图的注释」。它接收命令 DTO，转换为值对象，加载聚合，把外部事实作为参数交给聚合方法，保存，登记事件，提交事务。判断是否用错层的经验做法：把应用服务里的代码逐行标注——凡是被标成「这条判断是业务规则」的行，都应该搬进聚合或领域服务。

领域服务只在「规则天然跨聚合且无法归属任一方」时才写。差旅案例里真正合格的领域服务只有一个：把一张报销单的金额按成本中心分摊到多个额度账户的 Allocation 计算——纯函数，输入若干聚合的状态快照，输出分摊方案，不改状态、不落库、不发事件。凡是名字带 Service、内部却挨个加载聚合再写库的类，本质都是应用服务，改名即可。

领域事件：让模块之间只共享时间线

领域事件在本文的语境里只有一个作用：把「A 已经成立」这一事实与「因此要做些什么」的决策分离。它是内存里的一等对象，落库与投递只是传输形态。三点约定能避开大部分坑。

其一，命名一律用过去时态的业务陈述，描述事实而非意图：TravelRequestSubmitted、BudgetReserved、ReservationRejected、SettlementClosed。其二，载荷是事实的最小集合，不要塞接收方可能需要的查询条件——一旦载荷里出现「为了让你少查一次库」的字段，两个上下文就开始隐式耦合。我们的 BudgetReserved 只有四个字段：申请单 ID、额度账户 ID、金额、幂等键。其三，发布必须与业务写入同事务：事件先写进本库的 outbox_message，事务提交后由中继投递并重试。

有了这三条约定，模块解耦才真正发生：结算上下文要新增「按部门汇总实扣」的需求时，只需订阅已有的 BudgetReserved 与 SettlementClosed，request 与 budget 不必改一行代码。反过来，一旦发现加一个下游消费者需要上游修改事件载荷，就说明边界划错了——通常是两个上下文该合并，或者上游该发布更细粒度的事实。

分层与整洁架构：目录只是依赖规则的投影

上一节的包结构已经隐含了分层。整洁架构的依赖规则只有一句话：源代码的依赖方向必须指向高层策略，即从外圈指向内圈，HTTP 与数据库在最外圈，领域在内圈。目录树只是这条规则的投影，所以判断分层对不对，看 import 而不是看目录名。

组合根（composition root）是唯一允许知道所有具体类型的地方，放在 cmd 下或一个独立的 wire 包里。好处是换数据库、换消息中间件、把 HTTP 换成 gRPC 时改动集中在一个文件，测试里替换内存仓储也只需重新装配一次。

三条经验值得记下来。第一，层数不是指标：把 interfaces 拆成 controller、facade、assembler、translator 四层，结果一半代码是字段搬运，我们的做法是允许只有一层，只要依赖方向正确。第二，DTO 与聚合是两种东西，DTO 只在最外圈出现，跨过 HTTP 层就消失，绝不能把聚合根直接序列化进响应体，否则字段改名立刻变成对外契约事故。第三，先做模块化单体再谈进程拆分：上文那套包边界与 CI 检查在单体内建立的成本几乎为零，确有独立部署或团队所有权需求时，把一个包连同它的表与订阅者搬出去即可；边界没立住就拆进程，只是把耦合换成跨网络的耦合。

端到端推演：从一句需求走到一次提交

最后用一条真实迭代需求走完全流程，检验前面每一步是否闭环。需求原文：「员工提交差旅申请后，如果金额超过该职级该目的地的标准上限，需要增加二级审批，并且提交时就预占额度，而不是批准后才预占。」

第一步回到事件风暴的语言：这句话里有两个新事实（「超出标准上限」「额度已预占」提前发生）和一个新规则（超上限时的审批级数）。第二步定位不变式归属：「超出多少算超上限」由 policy 计算，「状态如何迁移、需要几级审批」由 request 聚合保证，「预占不超过当期余额」由 budget 保证。三条规则分属三个上下文，因此这一需求必然涉及跨聚合协作，只能走事件编排，不能靠一个大事务。第三步按顺序落代码，一次 PR 的改动清单如下。

sequenceDiagram
    participant U as 员工
    participant A as 应用服务
    participant R as TravelRequest 聚合
    participant P as policy
    participant B as budget
    U->>A: 提交申请
    A->>R: Get(id)
    A->>P: Quote(职级,城市,区间)
    P-->>A: 上限 + 需要的审批级数
    A->>R: Submit(ceiling, levels)
    R-->>A: 状态迁移成功
    A->>A: 登记 BudgetPreoccupyRequested
    A->>B: 事务提交后异步消费并预占
    B-->>A: 预占失败时发 BudgetPreoccupyRejected
    A->>R: 回退为草稿并记录拒绝原因

第四步是评审关注点：审批级数由 policy 传入而不是聚合自己查（保持聚合无 I/O）；预占失败的回退路径必须与提交路径共用同一幂等键，避免一张申请单被预占两次；数据库迁移与代码同 PR 提交。测试分两层：聚合层用纯内存单测覆盖状态迁移矩阵（草稿提交、重复提交、批准后改行程、金额为负、区间重叠），编排层用内存仓储跑通「预占成功」与「额度不足被退回」两条链路，后者断言申请单最终状态与 outbox 表里的事件条数。

这一轮迭代改动了七个文件，但没有新增任何一层，也没有修改任何已有接口的语义——这就是边界立住之后应有的样子。

常见误用：六种看起来像 DDD 的写法

误用形态 可观察的症状 纠正做法
把仓储当 ORM 仓储接口里出现列级更新、分页、分组统计方法 仓储只保留按聚合取与存；列表与统计走独立读模型查询端口
贫血模型 聚合只有 getter，规则集中在 XxxService 的 if 里 把判断搬回聚合方法，应用服务只留编排；用「Service 里有没有业务 if」自查
巨型聚合 一个聚合根挂着十几张从表，并发写冲突率两位数 回到不变式重新分组，跨聚合一致性交给事件与幂等
为 DDD 而 DDD CRUD 后台也建四层目录、事件总线、十来个上下文 先评估规则复杂度；简单场景用事务脚本加清晰分层即可
事件当变更日志 事件名是 t_request_updated，载荷是字段字典 用业务事实命名与最小载荷，字段变化不发布事件
人人都是聚合 每个 struct 都继承 AggregateRoot、都有 version 只有独自承载不变式的对象才是聚合根，其余是实体或值对象

还有一类误用发生在语言层面：同一概念出现多个名字（TravelRequest、TripApplyForm、expenseApply 并存），说明统一语言只写在文档里、没落到代码。这种分裂半年后会变成最贵的债，因为新人无法判断哪个才是权威模型。

什么时候不该用 DDD

DDD 的成本是真实的：工作坊要拉上业务方、聚合与事件这些抽象要学习、一次需求改动涉及多个包、评审标准变严。只有业务规则本身的复杂度撑得起这些成本时才划算。可以用四个问题判断：核心不变式是否需要反复修改；同一条规则是否已经出现在多处（重复即信号）；系统是否要被多人长期维护（一次性脚本不算）；业务方与开发是否已经说不通同一句话。四问里有两问答「是」，落地 DDD 的回报通常能覆盖成本。

反过来，这些场景我们明确不用：内部导出报表、字典维护、审批流表单渲染、对接第三方的一次性同步任务、原型验证期的功能、规则不超过三五条且预计一年不动的模块。这些地方直接用「controller 调 service 调 dao」加上严格输入校验和充分测试，更快也更省。混合策略才是真实项目的常态：我们的差旅中台里只有 request 与 budget 写了完整聚合与领域事件，policy 是普通规则查询服务，settlement 一半是脚本式批处理，履约上下文干脆只做适配转发。把火力集中在核心域，比全面铺开更接近 DDD 的本意。

小结

本文沿着一条实现路径复盘了 DDD 落地：事件风暴问出的「什么情况下命令必须被拒绝」，是聚合边界唯一可靠的来源；限界上下文的价值在于一条规则只能有一个权威判定者，跨上下文的重复计算就是腐化的开始；上下文映射最终要翻译成 import 方向、包归属、独占表与 CI 检查，否则它只是一张海报；聚合遵循不变式边界、小聚合、跨聚合用 ID 引用三条准则，跨聚合一致性交给事件与幂等键。实践建议只有一条：先在单体内把包边界与依赖检查立住，只对核心域投入丰富模型，每次需求都回到术语表与不变式这两处起点。
