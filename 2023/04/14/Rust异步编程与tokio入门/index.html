Rust 异步编程与 tokio 入门

本文属于《Rust 学习路线》第 33/68 篇
上一篇系列目录下一篇

Rust 的异步编程在语法上只有 async 与 await 两个关键字，但要真正用好它，必须理解它背后的 Future 模型、执行器与 IO 驱动器的分工，以及由此带来的一系列工程约束。本文面向有 Rust 基础、准备用 tokio 写网络服务或并发工具的读者，从语义讲起，一路覆盖任务模型、取消、锁的选择、阻塞的规避、Stream 与优雅关停，并整理最常见的几类编译错误。写作时最新的稳定版本是 1.68（2023 年 3 月发布），文中所有特性均以该版本与 tokio 1.x 为准。

Future 的本质：惰性求值与被驱动

很多从 JavaScript 或 Go 转过来的读者，第一个坑就踩在“异步代码什么时候开始执行”上。在 JavaScript 里，创建一个 Promise 的瞬间，executor 就已经开始推进它了；在 Go 里，go 语句一执行， goroutine 立刻开始运行。Rust 两者都不是：async 函数调用返回的是一个 Future 值，这个值只是把“尚未完成的计算”描述出来，一行函数体都不会执行。

执行器对某个 Future 的推进方式就是反复调用它的 poll 方法：返回 Ready 表示计算完成，产出 Output；返回 Pending 表示“现在还没好，请在事情发生变化的时候叫醒我”。叫醒的机制保存在上下文参数里，即 cx.waker()，异步操作在数据就绪时通过它唤醒执行器，执行器再安排下一次 poll。整个模型里没有回调注册表、没有内部线程，只有一个“问进展—没进展就登记唤醒—有进展再来问”的循环。

既然 poll 是推进的唯一途径，惰性就很好理解了：没有人调用 poll，状态机就停在初始状态，什么副作用都不会发生。这个设计带来几个实际的好处。其一，构造异步调用的成本几乎为零，不会因为忘记等待而偷偷启动后台任务；其二，Future 是可以组合的值，可以放进数据结构、用 join 或 select 拼接，直到你决定驱动它；其三，未完成的工作不会隐式占用线程，等待中的任务只占内存。代价则是那条著名的新手警告：调用 async 函数却不写 .await、也不把它交给执行器，程序会安静地什么都不做，编译器只给一个未使用返回值的提示。

还有一个细节值得提前说明：poll 的第一个参数是自钉住的引用。一个 async 函数的状态机往往同时持有指向自己局部变量的引用，比如先取一个本地缓冲区的借用、在下一个挂起点恢复时还要用它，这种“自引用结构”一旦被移动，引用就会悬垂。Pin 就是在类型层面禁止移动，保证状态机地址稳定。对多数使用者来说，async/await 已经把 Pin 的簿记完全屏蔽掉了，只有在手写 poll 或给接口做手动装箱时才会直面它；至于生命周期本身如何跨越 await，我们会在文末的报错一节具体展开。

async/await 的语义与边界

async/await 是语法糖，这一点在 Rust 中比在很多语言里都更“诚实”：它脱掉糖之后仍然是那个惰性状态机。一个 async 函数约等价于一个返回实现了 Future trait 的匿名类型的普通函数：

await 关键字则做了三件事：向执行器声明“这里是挂起点”，请求推进被等待的 Future，并在其完成后取出产出值。关键在于，挂起不等于阻塞线程。当前任务在 await 处返回 Pending 后，工作线程立刻被释放去 poll 其他任务；等被等待的操作就绪、任务被唤醒时，执行器再次 poll 这个状态机，从挂起点继续往下走，局部状态一直妥善保存在状态机里。正因为如此，Rust 才能在少量线程上调度成千上万个任务，而不需要每个等待都占一个内核线程。

语法边界方面有几点必须注意。在 Cargo.toml 里给 tokio 1 号大版本开启所需 feature 是这一切的前提，日常学习阶段直接开 full 最省事，上线前再按模块裁剪。await 只能出现在 async 上下文中，包括 async 函数、async 闭包（1.68 仍不稳定，日常可用 async 块代替）以及 async 块本身，普通同步函数里想等待只能借助 block_on 一类的入口，而且 block_on 只适合测试与程序入口，不能在执行器内部嵌套调用。另一个常见误区是把 async fn 当作“启动后台任务”：它不会，它只是描述计算，真正把计算交出去的是 await（在当前任务里顺序推进）或 spawn（交给执行器并发推进），两者的区别留到运行时一节细谈。

执行器与反应器：谁在驱动，谁在叫醒

上一节说 Future 必须被 poll 才能前进，那么是谁在 poll？答案是执行器（executor）。它维护一个就绪任务队列，不断取出任务调用其 poll 方法；任务返回 Pending 后就不再管它，直到该任务注册的 waker 被触发，才把它重新排回队列。而“事情发生变化”这件事—— socket 可读、定时器到期——本身不会凭空通知到 waker，需要有人监听操作系统的事件，这就是反应器（reactor）的职责。

反应器在 Unix 上通常建立在 epoll 或 kqueue 之上，tokio 底下用的是 mio 这一层封装：异步 IO 句柄注册 interest，反应器把就绪事件收集起来，逐个触发对应任务的 waker。定时器则是第三类基础设施，tokio 用专门的驱动线程维护时间轮，到期时同样通过 waker 唤醒任务。把三者放在一起，一个网络任务的完整生命周期大致如下：

flowchart TD
    A[任务被 poll] --> B{操作就绪?}
    B -- 是 --> C[状态机继续执行]
    B -- 否 --> D[向反应器或定时器登记 waker]
    D --> E[让出工作线程]
    E --> F[事件到达, waker 触发]
    F --> G[任务重新入队]
    G --> A

这个分工解释了一个初学者常见的困惑：为什么 futures crate 里也有 block_on，却不能直接拿来跑 tokio 的网络程序。因为 block_on 只是最简单的执行器，它没有配套的反应器；一个等待 socket 的 Future 对它调用 poll，永远返回 Pending，waker 永远不会被触发，整个程序就挂死了。纯计算型的 Future（比如不依赖就绪事件的组合子链）用 block_on 没问题，一旦涉及异步 IO，就必须让执行器和反应器住在同一个运行时里。tokio 的 Runtime 正是这样一个打包：任务调度器、IO 驱动、定时器驱动三件套齐备，#[tokio::main] 宏做的就是把 main 函数的状态机交给这样一个运行时去驱动。

实践建议是把 block_on 限制在单元测试与二进制入口，不要在运行时内部再嵌套一个 block_on 或手动 poll 循环，那等于在一个调度器里再塞一个阻塞式调度器，轻则吞吐骤降，重则死锁。

tokio 多线程运行时与任务模型

tokio 1.x 的运行时形态有两种：单线程与多线程。单线程模式下所有任务在一个线程上轮转，适合本地工具、测试和需要确定性的逻辑；默认的 #[tokio::main] 是多线程模式，它会按 CPU 核心数启动若干 worker 线程，每个 worker 手里有自己的本地任务队列。

多线程调度的核心是工作窃取（work stealing）。当某个 worker 的本地队列空了，它不会闲着，而是随机挑其他 worker 的队列，从尾部偷取一半任务过来。这套机制让负载自动摊平：某个 worker 上恰好堆积了一串长任务，不会导致其他 worker 无活可干，也避免了单一全局队列在高并发入队时被锁竞争拖慢。与此配合的是本地优先策略——自己队列里的任务缓存友好、刚挂起又很快就绪，因此运行时先跑本地队列，其次去偷别人的尾部，最后才碰全局注入队列，新 spawn 的任务则常从全局队列兜底进入调度。理解这套机制的价值在于明白为什么异步任务应当短小：一次 poll 应当很快返回，长循环或不加节制地连续 await 已就绪的操作会让同线程的其他任务挨饿，必要时用 tokio::task::yield_now().await 主动让出。

顺带一提，任务与线程的取舍（什么时候该开 OS 线程、消息传递怎么组织）在之前的并发篇里已经讲过，本文只讨论异步这一侧：在 tokio 里，任务的创建与销毁成本远低于线程，几十万个等待中的任务只是几十万个状态机对象，这正是异步适合高并发 IO 场景的根本原因。

同类任务一次性派生很多时，管理散落的句柄会很繁琐，tokio::task::JoinSet 是更顺手的容器：spawn 把任务塞进去，join_next 每次弹出最先完成的那个，集合 drop 时剩余任务统一取消，正好和稍后优雅关停的写法衔接。另一对容易混淆的关系是 await 与 spawn：先后两行 a().await、b().await 是串行执行；想让两者并发又不想付出跨任务通信的开销，可以在同一任务里用 futures::join! 同时驱动两个已构造的 Future，它们可以合法借用局部数据，不受 ‘static 约束；错误场景则用 try_join!，任一分支先出错就整体返回，适合“要么都成、要么早退”的并行请求。

任务取消、select! 与超时

Rust 的取消不是“给任务发信号”，而是“不再驱动它”。当一个表示 Future 的值被 drop——包括其所在的 JoinHandle 被丢弃、select! 里落败的分支、timeout 到期后内部 Future 被抛掉——它的状态机连同其中所有局部变量一起析构，任务就停在最后一个挂起点上。这个定义带来两条重要认知。第一，取消点是 await 边界而非任意指令：任务只可能在自己正挂着的时候消失，正在执行的同步代码段不会被拦腰砍断。第二，取消是暴力的：状态机的局部变量按普通作用域规则析构，Drop 实现会运行，但不会有任何“收尾逻辑”自动帮你把做了一半的事情补完。

由此引出取消安全性（cancellation safety）的概念：一个 Future 被中途丢弃后，系统状态是否仍然自洽。危险的典型是“进度藏在借用状态里”的操作，比如从 Stream 上按 poll 推进的读取，若某次 poll 消费了内部缓冲区的一部分数据才返回 Pending，而你在 Pending 时把它丢掉，那部分数据就无声蒸发了。tokio 文档明确标注了哪些 API 在挂起点被丢弃会丢数据，常见的规避手段一是把有风险的调用整体包进一个独立任务，宁可丢任务也不丢半口数据；二是避免手动 poll，尽量用 next 这类每次调用要么完整产出一个条目、要么不产出的高级接口。select! 是取消最常发生的现场：

select! 随机挑一个分支先 poll，一旦某个分支完成，其余分支的 Future 当场被 drop，也就是被取消。多数循环里这是期望行为；若分支之间有优先级或副作用顺序的要求，可以给 select! 加 biased; 前缀改为从上到下依次 poll，但注意这会牺牲公平性。

选锁：异步 Mutex 与同步原语的分工

异步代码里出现锁，要先问两个问题：临界区里有没有 await？锁的持有时间跨不跨线程？这两个问题把选择清晰地切成四象限。

临界区内没有 await、只保护一小段纯内存状态的，用标准库的 Mutex 或 RwLock 就够了。同步锁在无竞争时只是一次原子加解锁，代价近乎为零；tokio 的异步锁则为“挂起等待”准备了队列与 waker，无竞争路径反而略贵。这类场景的标准写法是进锁、取出或克隆需要数据、立即出锁，再做别的事：

反过来，临界区里确实要 await——比如持锁完成一段“读取—请求—写回”的互斥流程——就必须换成 tokio::sync::Mutex 或 RwLock。这不是风格问题而是正确性问题：std 锁的 MutexGuard 不是 Send，一旦它跨越 await 活在状态机里，整个 Future 就不再 Send，多线程运行时上 spawn 直接编译失败；而 tokio 的锁在竞争时不霸占线程，它把任务挂进等待队列，waker 在锁释放时把它唤醒，锁的移交随 await 的完成一起发生。异步锁还有两点脾性与 std 不同：它不可重入，同一个任务里对同一把 tokio Mutex 连续 lock 两次会自锁死；它的 RwLock 写者优先，读锁不会饿死写者，但读端特别密集时要留意排队效应。若某个同步上下文里确实需要拿异步锁，较新的 1.x 版本提供 blocking_lock 一类入口，但它会阻塞当前线程，使用要克制。

还有第三条路常被忽略：竞争本身也许就是设计信号。与其让一堆任务抢一把大锁，不如把状态收进一个专属任务，其他任务通过 mpsc channel 给它发消息，用消息传递代替共享可变状态——通道与 Send/Sync 的基础用法之前的并发篇讲过，这里只强调它在异步世界里同样成立，而且天然回避了跨 await 持锁的所有麻烦。简单说：短临界区用 std 锁，跨 await 用 tokio 锁，长期竞争考虑改成通道消息。

异步上下文里的阻塞：危害与出路

worker 线程是运行时的稀缺资源：数量只有核心数个，上面轮转着成百上千个任务。在这个前提下，任何一次阻塞都不只是当前任务慢，而是整条线程上所有任务一起停摆，连定时器都可能被拖得迟到。最常见的阻塞源包括：同步文件 IO（std::fs）、CPU 密集的循环、第三方同步网络库（例如阻塞式的 HTTP 客户端）、std 线程 sleep，以及看似无辜的“在异步代码里调用 block_on”。日志刷新、加解密这类纯 CPU 函数如果单次耗时长，也会造成同样的问题。

出路有两条，适用场景不同。第一条是 spawn_blocking，把阻塞工作整体交给专门的阻塞线程池，默认上限是 512 个线程，可通过 Runtime 的 max_blocking_threads 调整：

它返回的仍是 JoinHandle，await 它就是把结果异步地取回来；代价是数据要 move 进闭包、结果要搬回来，别把它当免费午餐，短小的操作直接在异步侧做完更划算。第二条是 block_in_place，适用于“身处异步函数深处，无法把调用者改成同步”的场景：它把当前 worker 线程临时转换成阻塞线程，运行时再从空闲资源里补一名 worker，等阻塞调用结束线程归还。注意它只存在于多线程运行时，且会扭曲 JoinHandle 与任务局部存储的语义，封装旧同步库时才考虑，新代码优先 spawn_blocking。文件 IO 有现成的替身：tokio::fs 的操作内部就托管给阻塞池，写成异步调用即可；定时与等待则永远用 tokio::time。一句话总结本节：异步代码的第一性能守则，是不让任何一次 poll 长时间不返回。

Stream 与异步迭代

Future 表达“一次完成的一件事”，但异步世界里更常见的是“陆续到达的一串东西”：网络流上的报文、通道里的消息、逐行读取的日志。承担这个角色的是 Stream trait，它相当于异步版的 Iterator：Iterator 的 next 同步地要么给元素要么给终止信号，Stream 的 next 则返回一个会产出 Option 的 Future——现在没有元素不等于结束，可能只是还没到，等待本身不占用线程。

其三是定时器：interval 每 tick 产出一个 Instant，轮询任务因此可以写成流的形式并入 select!。其四是自定义生成器：async-stream crate 的 stream! 宏允许在 async 块里用 yield 产出元素，把“边算边给”的逻辑写得很直白；自己手写 poll_next 也能做，但要同时管好 waker 注册与状态字段，非必要不手写。与取消一节呼应：从流上 next 出来的条目是完整交付的，落败的 select! 分支即便丢弃了 next 的 Future，也不会吃掉半个元素，这让“多路复用若干流”的循环在取消语义下依旧干净。顺带说，有界通道的容量参数就是最简单的背压旋钮：满队时发送端的 send 会挂起任务，快的生产者自然被慢的消费者拽住；设计管道时最好一开始就想清楚缓冲由谁承担、满了之后是等待还是丢弃，否则异步代码再漂亮，也可能在压力下把内存吃穿。

优雅关停

服务进程收到 SIGINT 或编排系统终止信号时，理想的行为是：不再接受新工作，把在途请求做完，再退出。异步模型恰好为这套流程提供了自然的表达——用广播信号通知所有任务，用 JoinHandle 收拢所有收尾。一个可以直接套用的骨架如下：

常见编译错误诊断

异步代码的报错常常比同步更绕，这里把最高频的四类整理成对照表式的笔记。

第一类是“调用了 async 函数却什么都没发生”。没有编译错误，只有 unused 警告，因为 hello() 只是构造了 Future。修法就是把 await 补上，或把返回的 Future 交给 spawn；review 时看到一个 async 调用后面既不跟 await 也不跟 spawn，基本可以断定是漏了。

第二类是借用跨越 await 导致无法 spawn。典型报错如下：

根因是 spawn 要求 ‘static：任务会在别的线程上活到未来某个不确定的时刻，绝不能引用主栈上的数据。修法是让被 move 进任务的数据由任务自己拥有：需要的字段 clone 出来、大块状态包进 Arc，或者改用 LocalSet 放弃跨线程窃取。若只是想在当前作用域里并发地跑几个借用局部数据的 Future，用 join! 或 select! 组合它们，而不是 spawn——它们在同一任务内推进，不要求 ‘static。

第三类是非 Send 状态跨越 await，报错关键词是 future cannot be sent between threads safely。最常见的情形是 std 锁的 MutexGuard 或 RefCell 的 RefMut 挂在状态机里活过挂起点。MutexGuard 的修法上一节讲过：缩短作用域、先克隆数据再 await，或换成 tokio 的锁。RefMut 同理——它的运行时借用规则本文之外的旧文有专门展开，这里只给异步侧的结论：Ref 与 RefMut 都不是 Send，跨 await 持有它们，多线程任务直接编译失败；单线程上侥幸通过也埋着 BorrowMutError 的运行时风险。正确姿势是把借用做成“同步的小段”：take 出数据、完成 await 后再放回，或者干脆把可变状态归口到一个 actor 任务。顺带一提，连 async 块本身不小心捕获了 Rc、裸指针之类非 Send 类型，也会撞上同一族报错，排查思路一致：沿错误信息里点名的类型找捕获源。

第四类是 Future 与具体类型纠缠：把不同 async 函数的返回值塞进同一个 Vec，或想让 trait 方法返回“各自的” Future。每个 async fn 的状态机类型都不同，静态集合装不下它们；回到第二节的话题，1.68 里既不能用 async fn in trait 让多态方法自然返回，也就注定要在“装箱 dyn Future”与“重构设计”之间做选择——能用枚举穷举的分支就穷举，真正开放的多态集合再上 async-trait 的装箱，别为用不上的灵活性付堆分配的代价。

小结

Rust 异步的骨架可以压缩成几句话：Future 是惰性的状态机，不 await、不 spawn 就什么都不发生；await 让出的是任务而不是线程，执行器负责推进，反应器负责在 IO 就绪时叫醒，二者必须同住在一个运行时里；tokio 的多线程 runtime 用工作窃取摊平负载，任务应短小、少阻塞；取消靠 drop，所以 select!、timeout 与关停逻辑都要以“可安全丢弃”为前提自检；锁的选择看临界区是否跨越 await，阻塞代码用 spawn_blocking 隔离，优雅关停靠 watch 广播加 JoinHandle 收拢。把这些语义一次理顺，之后读任何异步库的文档都会顺得多。异步 trait 的等待与替代方案属于另一个话题，本篇在 1.68 的世界线里就讲到这里。
