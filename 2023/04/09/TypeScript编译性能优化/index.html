TypeScript 编译性能优化

本文属于《TypeScript 学习路线》第 41/74 篇
上一篇系列目录下一篇

本文面向已经被 tsc 慢到无法忍受的前端与 Node.js 开发者，目标不是把编译提速变成玄学，而是建立一套可量化、可定位、可验证的优化流程。读完你会知道一次 tsc 到底在忙什么，如何用官方自带的诊断开关把耗时拆开，增量编译与项目引用分别解决哪一类问题，以及在大型仓库里如何安排开发机与 CI 之间的编译分工。文中的配置项、命令行开关与特性口径均以 2023 年 3 月发布的 TypeScript 5.0 为准，更晚发布的规划不纳入讨论。

先看清 tsc 在做什么

很多同学习惯把 tsc 当成一个”把 TS 变成 JS”的转译器，于是当它变慢时无从下手。事实上，运行一次完整的 tsc，编译器大致做了三件事：程序构建、类型检查、以及产物输出。这三段耗时的成因完全不同，能用的优化手段也完全不同，因此调优的第一步是理解时间究竟花在了哪一段。

程序构建（Program Construction）是最容易被忽略、却经常最耗时的一段。tsc 会从 tsconfig.json 里的 files 或 include 出发，沿着每一个 import 递归地发现全部被引用的模块，把整个程序的文件依赖图搭建起来。这一段内部又分三个子步骤：读取磁盘内容、做词法与语法分析生成 AST、以及模块解析（为每一个 import 的说明符找到真实的目标文件路径）。当模块解析策略或 paths 映射配置得不当时，单个说明符可能触发大量候选路径的尝试，解析时间会迅速膨胀。在一个没有做项目拆分的巨型仓库里，为了校验少数几行改动，编译器常常要把成百上千个源文件与依赖重新构建成同一个 Program，这份成本几乎全是重复劳动。

类型检查（Type Checking）是类型安全的价值所在，也是计算量的主要来源。检查器要逐个推断变量、函数参数与返回值的类型，在每一处调用点做赋值兼容性检查，并在控制流里完成类型收窄。它的开销并不简单地与代码行数成正比，而是更依赖”类型复杂度”。几个层层嵌套的泛型、一条递归的条件类型、一个特别长的联合类型，都可能让检查器在同一段类型上反复做约束求解与类型实例化，结果是一行代码花费的时间，可能超过上千行普通赋值语句的总和。换句话说，类型检查的瓶颈往往不在”多”，而在”深”与”绕”。

产物输出（Emit）包括转译出 .js 与生成声明文件 .d.ts。单纯的转译相对便宜，它做的是语法降级与类型擦除，几乎不需要额外的推理。但一旦打开 declaration，编译器必须把检查器推断出来的类型”读回来”，逐一序列化成 .d.ts 文本。这一步把原本可以解耦的类型检查与产物生成强行耦合在了一起：为了产出一份完整、准确的声明文件，编译器实际上必须完成整个程序、包括被依赖模块的完整类型推断。这正是”声明产出很贵”的直接原因，也是很多库项目在开启声明产出后编译时间陡增的根源。

理解了这三段，你就能把”编译慢”这句模糊的抱怨，翻译成”是程序构建慢、是类型检查慢，还是声明产出慢”这类可以被验证的具体问题。

用诊断开关量化耗时

没有数据之前，一切优化都是猜测。TypeScript 内置了两档诊断开关：--diagnostics 给出概览，--extendedDiagnostics 给出更细的分解，两者都会在编译结束后把统计信息打到标准错误输出上。它们是排查性能问题的第一选择，因为不需要引入任何额外工具就能看到编译器自己报的数字。

--extendedDiagnostics 的输出可以按前面说的三段来读。程序构建相关看 Files、Lines of Typescript、Parse Time、Resolve Module Time；类型检查相关看 Total Node Count、Check Time；输出相关看 Emit Time、Source Maps Time。如果内存吃紧，Total Memory Used 与 Process Runtime 也能提示你进程整体是不是逼近了瓶颈。

一个实用的判读思路是做减法与做对比。若 Parse Time 与 Resolve Module Time 加起来占了大头，说明问题在程序构建，优化方向是缩小 Program 规模、清理 paths 与解析策略，而不是去动类型。若 Check Time 独占鳌头，那多半是类型复杂度在作祟，要从泛型、条件类型、过宽的推断上想办法。若 Emit Time 明显偏高，且你并不真的需要 .d.ts，那么在纯应用的编译里关掉 declaration 就能立刻见到收益；若确实需要声明，则要往下看声明产出为什么贵、能不能拆到独立的构建阶段。

当粗粒度的计数还不足以定位时，可以用 --generateTrace 生成一份调用级别的追踪文件。它会把每个阶段、每个文件的耗时与调用关系落成 JSON，供离线分析工具深入排查”到底是哪一处赋值兼容性检查最费时间”。这类追踪适合在 --extendedDiagnostics 已经指向类型检查、但你不知道具体是哪段类型在爆炸时使用；日常迭代中并不必每次都开启，因为它本身也会给编译增加记录开销。

需要强调的是，量化不等于迷信单次数字。文件缓存冷热、是否有其他进程抢占 CPU、磁盘速度，都会影响读到的绝对值。比较可靠的做法是在同一台机器、同样的冷启动条件下，改动前后各跑一轮 --extendedDiagnostics，观察的是同一指标的变化趋势，而不是某个孤立的毫秒数。把这条流程固化下来，你的优化就从”感觉快了一点”变成了”Check Time 从 X 降到了 Y”这样可以说清楚、也可以回滚的结论。

增量编译：incremental 与 tsbuildinfo

前面提到程序构建的很大一部分成本是重复劳动：明明只改了几个文件，编译器却把整个 Program 重建一遍。--incremental 就是冲着这个痛点来的。开启后，tsc 会在第一次完整编译时，把程序的”指纹”写进一份 .tsbuildinfo 文件，记录每个输入文件的版本、依赖关系，以及哪些文件已经检查过、结果如何。下一次编译时，编译器读取这份信息，只重新处理自上次以来真正发生变化的部分，未改动的文件可以直接复用之前的解析与检查结果。

这里有一个务实的细节：.tsbuildinfo 是构建产物，不该进版本库，也不该和源码混在一起污染目录。把它放到 node_modules/.cache 或专门的缓存目录，既方便 CI 做缓存键管理，也避免误提交。需要注意的是，incremental 单独立项时主要优化的是重复运行 tsc 的场景，它并不能解决”一个巨型 Program 本身就难拆”的问题，也无法让并行成为可能。真正想把大仓库切开、让不同的改动只触发局部重建，要靠下一节的工程引用。

增量还牵出一个容易被忽视的坑：缓存失效的判断依赖文件内容指纹。如果你的构建流程会在 checkout 之后修改文件的 mtime 或内容占位（例如某些代码生成步骤每次都重写一遍同样的文件），编译器会认为文件变了，从而让增量形同虚设。排查”明明开了 incremental 却还是慢”时，一个有效的动作是对比连续两次的 .tsbuildinfo，看看它记录的变化文件数量是否符合预期。

还有一种常被混淆的情形是 tsc --watch。watch 模式把 Program 常驻在内存里，文件一变就只重算受影响的部分，它省的是”进程启动加冷构建”的成本，和 .tsbuildinfo 在两次独立运行之间复用磁盘缓存是两个互补的机制：前者适合长时间开着的本地开发会话，后者适合反复冷启动的脚本与 CI。理解这一区别，就不会误以为”用了 watch 就等于做了增量”，也不会把两者当成可互相替代的东西。

项目引用与 –build 的跨项目增量

当仓库大到单个 Program 难以承受时，正确的思路不是把 tsc 调得更猛，而是把项目切开。TypeScript 的 Project References 允许你把一个逻辑上的大工程拆成若干有明确边界、彼此通过声明文件依赖的子项目，再用 --build（等价于 tsc -b）按拓扑顺序统一驱动它们。

要参与引用，子项目需要把 composite 打开，它强制该子项目产出声明文件、隐含开启增量，并要求文件集合是封闭可枚举的。父项目通过 references 指向子项目目录，而不是把子项目的源码也 include 进来。

tsc -b 的增量是跨项目的：它读取每个子项目的 .tsbuildinfo，判断某个子项目是否需要重建；只有当它的输入、或它所依赖的子项目产出的 .d.ts 发生变化时，才会触发这个子项目的重新检查与声明产出，其余子项目原样跳过。于是”改了 packages/core 里一个内部实现细节但对外签名没变”这类改动，往往只需要重编译 core 自身，依赖它的 web 因为看到的 .d.ts 没有变化而无需重建。这正是大仓提速的关键：让每次改动的影响面，收敛到真正依赖了变化接口的那几个子项目里。

代价是边界要划清楚。项目引用要求你把依赖方向理成无环，跨包只能消费对方导出的公开类型而非内部源码，这在一开始会打乱”反正一个 tsconfig 全塞进来最省事”的习惯。但正是这份约束，把程序构建从”一个巨型 Program”降成了”若干小 Program 加一层增量调度”，也让后面要讲的并行与按需检查有了立足点。

削减类型负担的几个配置开关

除了增量与拆分，还有一批”配置就能见效”的开关，它们大多作用在程序构建与类型检查这两段上。理解它们各自削减的是哪一段成本，才能用得不留隐患。

skipLibCheck 决定要不要跳过对所有 .d.ts 声明文件的类型检查。默认情况下，编译器不仅检查你自己的源码，还会检查拉进来的每一个依赖包的声明文件是否自洽。而这些第三方声明大多已经由它们的作者验证过，再查一遍对发现你代码里的错误几乎没有贡献，却实实在在消耗检查时间。对应用类项目打开 skipLibCheck 通常能立刻削掉可观的一段 Check Time，是性价比极高的默认选择。要清楚它的边界：它跳过的是”声明文件自身的内部一致性检查”，你在自己代码里使用这些库类型时的赋值兼容性检查仍然照常进行，因此它并不牺牲你这一侧的类型安全。

types 与 @types 的收敛针对的是程序构建里”自动引入全局类型”这一段。默认不设 types 时，编译器会把 node_modules/@types 下所有包都塞进全局作用域，哪怕你的项目根本用不到其中大半。每一个被塞进来的包都是程序构建要读取、解析、纳入依赖图的真实文件。把 compilerOptions.types 显式列成当前 tsconfig 真正需要的少数几项，能显著减少进入 Program 的 .d.ts 数量，从源头削减构建成本。在多套 tsconfig 并存时，让”跑测试的配置”才引入测试相关的全局类型、”构建产物的配置”不引入，也是同一思路。

isolatedModules 本身不是提速开关，但它为提速铺路。它要求每个文件都能被独立转译，禁止那些必须知道周围文件类型才能安全编译产物写法。满足这条约束后，你就可以放心地把”类型检查”和”转译”分给不同工具去做：转译交给只做单文件语法降级的快速工具，类型检查交给 tsc。后面开发态用快速转译、CI 才跑完整检查的分工，前提正是项目满足 isolatedModules。开启它还能提前暴露一批会在转译工具下出错的写法，避免线上才发现。

declaration emit 之所以贵，前面已经从机制上讲过：它要求产出前完成完整的类型推断。能给的务实建议是把它按需要分层。纯应用、纯脚本的项目如果没有外部消费者，往往不需要 .d.ts，直接不产出声明即可省下整段序列化与它逼迫的完整检查。确实要发库时，则尽量让每个可发布包只对自己这一层做声明产出，配合项目引用把声明生成推给 tsc -b 的增量调度，而不是在每次本地改动时都全量重生成所有声明。类型复杂度越高、被引用越广的包，声明产出的边际成本越大，这也再次说明”控制类型复杂度”不只是检查的事，也是产出的事。

开发态与 CI 的编译分工

一个关键的认知转变是：并非每一次运行代码都需要完整的类型检查。开发时你反复做的是”改一点、跑一下、看效果”，此时最需要的是快速拿到能执行的 JS，而不是让 tsc 把整个 Program 重头检查一遍。把这两件事的时机分开，是大型 TS 项目体验提升最明显的一招。

开发态交给 transpile-only 的快速工具。ts-node 有 --swc 与 transpileOnly 这类只转译不检查的运行方式；SWC 与 esbuild 这类工具本身就只做单文件的语法降级与类型擦除，天生跳过类型检查，转译速度极快。它们能秒级把 TS 变成可运行的 JS，让本地起服务、跑脚本、热更新的反馈循环大幅缩短。前提正是上一节说的 isolatedModules：这些工具逐文件转译，看不懂需要跨文件类型才能成立的写法，所以项目要先满足这个约束。

完整的类型检查则交给 CI 与显式的检查命令。把 tsc --noEmit（配合 skipLibCheck 与合理的项目划分）作为流水线里的一道门禁，配合编辑器里的实时诊断，你在开发时靠 IDE 得到即时反馈、在提交与 CI 阶段得到一次严格的全量把关。这样既保住了类型安全，又不让全量检查阻塞最频繁的开发循环。

由此引出把类型检查并行到 CI 的做法。既然项目已经用引用切成了互有向无环依赖的子项目，tsc -b 本身就带着跨项目的增量与调度信息，CI 完全可以按子项目或按受影响范围把检查拆成多个并行的任务：改动只落在 packages/core 时，只对 core 及真正依赖它的下游做检查；也可以利用多核，在不同进程里并行跑彼此无依赖的子项目。相比在 CI 里单进程串行检查整个巨型 Program，这种”按依赖图切分、只检受影响部分”的策略，能把检查时间与仓库规模之间的耦合显著松开。要落地它，缓存是关键一环——把各子项目的 .tsbuildinfo 与依赖作为 CI 缓存键保存，命中时才有真正的增量收益，否则每次冷启动仍要把整个图重建一遍。

这里要把握一个度：transpile-only 快，是因为它把类型安全的责任推迟到了别处，而不是取消了它。开发时跳过的检查，一定要在提交前的某个环节补回来，否则只是把错误从本地搬到了线上。分工的正确形态是”开发求快、门禁求全”，两者缺一不可。

值得一提的是，开发态切到 transpile-only 并不意味着你失去了类型反馈。编辑器背后的语言服务（tsserver）本来就在内存里持续做增量的类型检查，边打字边给出诊断，与运行代码时的转译是两条互不阻塞的路径。也就是说，你在写代码时靠语言服务得到即时提示，在运行脚本时靠快速转译得到秒级启动，在提交与 CI 时靠一次 tsc --noEmit 得到严格兜底。把这三者想清楚，就不会再纠结”要不要每次跑都全量检查”，而是让它们各就各位。

大型仓库的类型依赖收敛

单点开关解决局部问题，真正让大仓编译长期不失控的，是把类型依赖关系本身收敛好。这里的”依赖”既指源码之间的引用，也指类型层面谁看得见谁。

第一是把依赖方向理成清晰的层次。底层工具包不反向依赖业务包，业务包之间尽量通过明确定义的接口而非互相 import 内部文件。层次一旦清晰，项目引用的切分就自然，tsc -b 的增量与 CI 的按需检查才能精准命中。反过来，一个充满循环引用的仓库，很难拆成能独立检查的子项目，只能整体重来。

第二是控制类型的传播范围。跨包暴露的类型尽量精确、收敛，能用具体类型就不要用宽泛的推断结果对外扩散。一个内部包的类型如果以非常复杂的形式泄漏到了公共 API 上，检查器和声明产出都会被这份复杂度连累，且这份代价会在所有下游包里被重复支付。把公共边界上的类型写窄、写明确，是降低下游编译成本的杠杆。

第三是把类型定义从实现里适度解耦。对体量大的共享类型，考虑放进单独的、变更频率低的类型模块，让实现改动不轻易牵动类型图。这与减少”巨型 barrel 文件”是同一件事的两面：聚合入口越臃肿，任何一处小改动可能牵动的检查面就越大。收敛的目标不是少写类型，而是让每一次改动波及的类型检查范围，尽可能贴近它真实影响的范围。

第四是让类型与实际运行时保持对齐。@types 里声明的接口应当匹配你真正安装的那个库版本，否则会出现类型允许、运行时却不存在（或相反）的漂移，逼着开发者在别处用断言或额外包装去对冲，既埋返工隐患，也让本可精确的边界类型退化成宽泛形式，间接加重检查。把依赖版本、@types 版本与 types 白名单一起纳入审阅，是大仓里容易被忽略却省心的一环。

最后，大仓性能不是一次优化就一劳永逸的事，要把它变成可观测的长期指标。可以把一次全量 tsc --noEmit 的耗时纳入 CI 常规上报，给核心子项目设一条软性时长基线：当某次改动让检查时长明显偏离基线时，PR 上就能看到信号，作者会主动去查是类型复杂度上去了、还是依赖图被撑大了。这类护栏不直接提速，却能防止性能在日常合入里被一点点蚕食，而不是等到某个版本突然崩了才补救。

常见反模式与返工陷阱

很多”编译慢”其实是写代码时的习惯攒出来的，识别这些反模式能避免日后大改。

巨型 barrel 文件是典型。把整个包的导出全部集中到一个 index.ts 里层层 re-export，看似方便引用，实际会让任何对这个包的任何一处使用，都把整张导出图拉进检查范围。看似只 import 了一个函数，编译器却要把这条聚合链上所有声明都纳入并检查，程序构建与检查成本都被放大。务实的做法是按功能拆分出口，避免无节制地层层再导出，尤其是不要把跨层的重聚合当作默认风格。

过度 infer 是另一类隐性成本。让检查器从非常宽泛、层层推导的初始化里自动推断出一个庞大的类型，常常比显式标注一个窄接口更慢，也更脆：一旦实现微调，被推断出的类型结构剧烈变化，触发大范围重新检查，甚至把内部细节暴露到公共 API。对边界上的函数与对外返回的结构，主动写一个明确的类型注解，往往比追求”少写几个字”的自动推断换来更稳、更省的编译。

any 泛滥则是一个会反噬速度的陷阱。短期看，到处 any 让报错消失、好像检查也变轻了；但 any 在赋值兼容性检查里几乎不受约束，却会污染它流经的类型推断，逼着你在别处补更多显式标注来对冲，最终把代码推向”要么满屏 any 失去安全，要么某天收紧时一夜爆出一堆错误”的两极。收紧 any 的那次重构往往代价高昂，是典型的返工来源。更稳的路线是从一开始就用精确的类型、unknown 加窄化来替代随手 any，把成本摊在平时，而不是攒到最后一次偿还。

这些反模式的共同点，是把”编译慢”和”改起来慢”绑在了一起：类型图一旦失控，检查时间与改动波及面会一起恶化。反过来，好的类型边界既让 tsc 省劲，也让增量与并行真正能用得上。

把手段串成一条排查路线

前面分别讲了定位、增量、拆分、开关、分工与收敛，落到具体项目时需要一条能照着走的主线：先测量、再归因、按归因选手段、最后把手段固化进流程。下图是这条路线的骨架。

flowchart TD
  A[编译变慢] --> B[跑 extendedDiagnostics]
  B --> C{哪一段占比最高}
  C --> D[程序构建段]
  C --> E[类型检查段]
  C --> F[产物输出段]
  D --> D1[收敛 types 与清理 paths]
  D --> D2[用项目引用拆小 Program]
  E --> E1[开启 skipLibCheck]
  E --> E2[降类型复杂度并加显式标注]
  F --> F1[应用项目关闭 declaration]
  F --> F2[库项目用 build 增量产出声明]
  D1 --> G[开发用 transpile-only 与 CI 全量分工]
  D2 --> G
  E1 --> G
  E2 --> G
  F1 --> G
  F2 --> G
  G --> H[CI 缓存 tsbuildinfo 并按子项目并行]

走一遍一个常见场景。某应用仓库改动后本地与 CI 都变慢，先跑 --extendedDiagnostics，看到 Check Time 很高、同时 Files 与 Lines of Typescript 的数量远超手写源码规模——这提示有大批 .d.ts 被拉进了检查范围。此时第一步不是去动业务类型，而是开 skipLibCheck、把没有显式约束的 types 收敛到当前确需的全局类型，通常就能把构建与检查两段同时削下来一截。若 Check Time 仍然偏高，再看是不是少数热点泛型在放大成本，对这些边界类型补显式标注、把过度推断换成窄接口。确认全量检查的时间已经可以接受后，把开发态切到 transpile-only 的快工具、把完整检查固化成 CI 里的 tsc --noEmit 门禁，并给 CI 配上 .tsbuildinfo 与依赖缓存，让增量真正命中。

这条路线的重点是顺序：先归因再动手，避免在没搞清慢在哪一段时就盲目堆开关或大规模重构。每一次改动都回到同一份 --extendedDiagnostics 上做前后对比，把结论写成能复述、能回滚的因果，而不是”加了个配置感觉顺了”。

小结

tsc 的耗时可以拆成程序构建、类型检查、产物输出三段，三段的病因和药方不同，所以优化的起点永远是先用 --diagnostics 与 --extendedDiagnostics 归因，而不是凭感觉堆开关。incremental 与 .tsbuildinfo 消除重复劳动，项目引用与 tsc -b 把大仓切成能独立增量的小 Program，skipLibCheck、types 收敛、按需的 declaration 产出则直接从检查与构建里削成本。开发与 CI 要分工：开发态用满足 isolatedModules 前提的 transpile-only 换即时反馈，完整类型检查固化到 CI 门禁并按依赖图并行。最后，巨型 barrel、过度 infer 与 any 泛滥这类反模式会把编译慢和改起来慢绑在一起，值得在日常就收敛。把这套流程固化下来，性能就从玄学变回了一组可测量、可验证的工程决策。
