Seata 分布式事务实战

本文属于《Go 微服务架构》第 28/35 篇
上一篇系列目录下一篇

微服务拆分之后，一次下单往往要跨订单、库存、账户三个库，本地事务管不住这条链路。本文以 Seata 1.6 系列为例，讲清 TC、TM、RM 三个角色如何协作，AT、TCC、Saga、XA 四种模式怎么落地、坑在哪里，以及事务分组、Spring Cloud 集成、故障排查与选型的工程经验。读完后应能判断该用哪种模式，出问题时也知道从哪查起。

为什么本地事务不够用

假设一个简化的电商系统：订单服务写 order 库，库存服务写 stock 库，账户服务写 account 库。用户下单时，三个库要同时成功或同时失败。单体时代一个本地事务就够了；拆成微服务后，每个服务只能管住自己的数据源，本地事务边界和业务边界不再重合。

工程上常见的补救办法有三类。第一类是“先做再说”，中间某一步失败就留给人工或定时任务修数据，短期省事，长期对账成本极高。第二类是把三步串行调用，失败就反向调用补偿接口，这实际上是在业务代码里手写两阶段提交，异常分支一多就没人敢改。第三类是借助消息队列做最终一致，适合允许延迟的场景，但用户点了支付却看到“处理中”，体验上未必能接受。

Seata 的思路是把这些分散的本地事务编排成一个全局事务：由发起方声明事务边界，由独立的协调者记录全局与分支状态，各服务的数据源在提交前向协调者登记，失败时按统一规则回滚。它不要求所有参与者换成同一种数据库，也不要求业务改造成消息驱动。

三个角色：TC、TM、RM

Seata 的运行时只有三个角色，理解分工，后面所有模式都好懂。

  • TC（Transaction Coordinator，事务协调者）：独立部署的 Seata Server，维护全局事务与分支事务的状态，负责驱动提交或回滚，并保管全局锁。它是唯一有状态的中心。
  • TM（Transaction Manager，事务管理器）：全局事务的发起方，通常就是业务入口方法所在的服务。它向 TC 申请开启全局事务，拿到 XID，并在业务结束时发起全局提交或回滚。
  • RM（Resource Manager，资源管理器）：管理分支事务的资源，通常由数据源代理承担。它把本地事务的执行结果注册到 TC，并在第二阶段执行提交或回滚。

XID 是串起整条链路的粘合剂，由 TM 申请，随调用一层层传下去，每个 RM 用它把分支事务挂到同一个全局事务上。排查问题时，第一件事永远是在日志里找到 XID。

AT 模式：两阶段与 undo log

AT 是 Seata 最常用的模式，卖点是业务几乎零侵入：你照常写带本地事务注解的业务方法，只在外层加一个全局事务注解。

它的第一阶段并不是“准备”，而是一次完整的本地事务。RM 代理数据源后，会解析业务 SQL，把更新前的数据记成 before image，更新后的数据记成 after image，然后把业务 SQL 与一条 undo_log 记录放在同一个本地事务里提交，同时向 TC 注册分支并申请全局锁。本地数据此时已真实落库。

第二阶段分两种情况。全局提交时，TC 通知各 RM 异步删除对应的 undo_log，这一步非常轻，通常不阻塞业务。全局回滚时，RM 根据 undo_log 里的 before image 生成反向 SQL 把数据改回去，回滚前会先比对当前数据与 after image：两者不一致说明记录被全局事务之外的操作改过，此时回滚会覆盖别人的写入，于是放弃自动补偿并告警。

全局锁与写隔离

AT 第一阶段已提交数据，多个全局事务之间可能互相踩踏。Seata 用全局锁解决写冲突：分支事务在本地提交前，必须按“资源、表名、主键值”向 TC 申请锁；拿不到就重试，仍失败则回滚本地事务，全局事务随之失败。锁的持有者是 TC 而不是数据库，所以它能跨越不同的库。

这里有一个取舍：默认读隔离级别是读未提交。因为 A 事务的第一阶段已经提交，B 事务此时能读到 A 尚未全局提交的数据；一旦 A 全局回滚，B 读到的就是脏数据。加读锁的代价太大，Seata 没有这么做。

如果业务不能接受，有两种做法。一是把全局事务内的查询改成加锁读，并给方法加全局锁注解，让查询也去 TC 抢锁，直到前一个全局事务结束；二是把这类强一致读放到全局事务之外，用版本号或状态字段做业务层判断。前者简单但放大锁竞争，后者更可控，我们更推荐。

锁冲突是 AT 最常见的线上问题。热点行会让大量全局事务排队，此时应换用 TCC 做资源预留，或用缓存预扣加异步落库，而不是一味调大锁重试时间。

TCC：三个方法与三个坑

TCC 把一次业务操作拆成 Try、Confirm、Cancel 三个方法，由业务自己定义资源预留与释放的语义。相比 AT，它没有 undo_log，也不依赖 SQL 解析，隔离性靠预留资源实现，代价是侵入性强。

Try 里做的是冻结库存而不是扣减，Confirm 把冻结转为真实扣减，Cancel 解冻。三者都必须幂等，因为 TC 会重试。

三个经典坑必须显式处理：

  • 空回滚：Try 根本没执行，Cancel 却先到了。常见于 Try 因网络超时未到达、而全局事务已判定失败。解法是在 Cancel 里先查是否有 Try 记录，没有就记一条空回滚标记后直接返回成功。
  • 悬挂：Cancel 比 Try 先执行，之后迟到的 Try 又把资源冻结了，这笔资源再也无人释放。解法是 Cancel 留下的标记要能被 Try 读到，Try 发现已有回滚记录就拒绝执行。
  • 幂等：Confirm 与 Cancel 都可能被重复调用，必须用控制表加唯一键，或状态机做前置判断。

实践上通常建一张 tcc_transaction 表，以 xid 与 branchId 为唯一键记录 TRY、CONFIRM、CANCEL 三种状态，三个方法都先插记录再判断状态。另外要留出预留时间：Try 冻结的资源若长时间不 Confirm，需要超时释放任务兜底。

Saga 与 XA：另外两种取舍

Saga 面向长流程。它把全局事务拆成一串本地事务，每个正向操作配一个补偿操作，由状态机驱动。Seata 的 Saga 实现支持用 JSON 定义状态机，适合订单履约、跨企业对接这类耗时以小时计的流程。

Saga 没有锁，吞吐好，但隔离性最弱：中间状态对外可见，补偿也可能失败。所以补偿接口必须幂等、可重试，并考虑补偿时业务已被别人改过的情况。流程要显式建模，这既是负担也是好处。

XA 是数据库原生协议，Seata 把 XA 数据源作为 RM，第一阶段执行 prepare，第二阶段才 commit 或 rollback。它的强一致最彻底，但分支事务从 prepare 到全局结束一直持有数据库锁，长事务会拖垮连接池与锁等待。因此 XA 只适合短小、低并发的场景，比如跨库转账这类每一步都很快的操作。四种模式的对比可以这样记：

模式 侵入性 隔离性 锁粒度 典型场景
AT 低 默认读未提交 全局锁按行 常规短事务，已有数据库
TCC 高 靠资源预留 业务自定义 高并发扣减，需要强隔离
Saga 中 无锁，最弱 无 长流程，跨系统，可补偿
XA 低 强 数据库锁 短事务，强一致，并发不高

事务分组与高可用部署

客户端配置里最常见的一个概念是事务分组。它是一层逻辑映射：应用声明自己属于哪个分组，分组再映射到 TC 集群的名字，客户端据此从注册中心找到可用的 TC 列表。应用因此不需要知道 TC 地址，运维换集群只改映射。

TC 要高可用，关键是去掉本地状态。生产上把存储模式设为数据库，全局事务、分支事务、全局锁都落到同一套库中，多个 TC 节点无状态对等，客户端任选一个连接，某个节点挂掉后重连其他节点即可继续。数据库本身要做主从或集群，它是新的单点。1.5 之后还提供 raft 存储模式，状态在 TC 集群内部同步，省掉外部库，但对节点数有要求，中小规模先用数据库模式更稳妥。

部署顺序上，先起注册中心与 TC，确认 TC 已注册，再启动业务应用；缩容时反过来，先停应用再停 TC。

与 Spring Cloud 集成要点

引入 seata-spring-boot-starter 后，自动配置会读取上面的配置，创建 RM 与 TM 客户端，并把容器里的数据源包装成代理数据源。有两个容易忽略的点。

第一，自动代理只对标准单数据源生效。项目里若用了动态数据源、多数据源或自己创建的连接池，需要手动包一层代理，否则分支事务不会注册，undo_log 也永远不会写。判断方法很直接：发起一个全局事务，看库里有没有新增 undo_log 记录。

第二，XID 必须跨服务传递。默认情况下，Feign、RestTemplate、Dubbo 等常用调用方式都有拦截器把 XID 放进请求头或上下文，接收方再取出并绑定到当前线程。如果用了自研的 HTTP 客户端、消息队列或线程池，就要自己传递：发送前从上下文取 XID 写入报文，消费或异步执行时再绑定。异步场景尤其容易漏，主线程回滚了，子线程里的分支事务还蒙在鼓里。

调用链路上，全局事务注解只加在最外层的入口方法上，内层服务不要再开新的全局事务。入口方法的超时时间要覆盖整条链路，它决定了 TC 判定超时回滚的时刻。另外，异常被捕获后不再抛出时，TM 会认为一切正常而提交，因此要么继续上抛，要么显式标记回滚。

常见故障与排查

线上问题大多能归到四类，按下面的顺序查。

一是分支事务没加入全局事务。表现是 TM 日志里只有一条分支注册，下游写入没有被回滚。先看下游日志里有没有绑定 XID，再看调用是否走了带拦截器的客户端。

二是 undo_log 缺失。回滚时 RM 报找不到 undo_log，或根本没有回滚动作。检查该库是否建表、表名大小写是否一致、数据源是否被代理。

三是全局锁冲突。日志出现锁冲突或获取全局锁失败，说明两个全局事务在争同一行。到 TC 的 lock_table 按表名与主键查持有者，结合 global_table 的启动时间定位业务。偶发冲突可以接受，持续冲突要改业务：缩短全局事务、把热点操作移出全局事务，或换 TCC。

四是超时回滚。全局事务超时后 TC 主动回滚，业务却以为已提交，要核对超时时间与下游耗时。

排查路径是：从 TM 日志拿到 XID，到 global_table 与 branch_table 查状态，再到各 RM 的 undo_log 查分支记录，最后对照业务表数据。把 XID 打进 MDC 让日志串起来，比事后猜高效得多。

模式选型建议

选型不要从模式出发，而要从业务的不变式出发：失败时数据能否容忍短暂不一致，补偿逻辑写不写得出来。

常规的“一次请求改多个库”，直接用 AT，侵入小、回滚自动；高并发扣减、需要资源预留的库存、优惠券、余额，用 TCC；跨系统、长流程、参与方不受自己控制，用 Saga；只有强一致不可妥协且事务足够短，才考虑 XA。一个系统里不要同时铺开四种模式，最好控制在一到两种。另外，框架能保证流程正确，保证不了业务语义正确，定时对账才是最后一道防线。

小结

Seata 的工程价值在于把分布式事务的协调逻辑从业务里抽出来，交给 TC 统一管理。AT 用 undo_log 换低侵入，TCC 用资源预留换隔离性，Saga 适合长流程，XA 强一致但锁太久。部署抓住事务分组与共享存储，集成盯住数据源代理与 XID 传递，排障顺着 XID 查三张表。先跑通 AT，再按业务压力演进，是我们推荐的路径。
