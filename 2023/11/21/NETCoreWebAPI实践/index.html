.NET Core Web API 实践

本文面向写过几段 C#、但对 ASP.NET Core 还不够熟的开发者，按一个业务接口的尺度，把 Web API 从跑起来到会踩坑的关键环节走一遍：启动流程、风格取舍、依赖注入、中间件顺序、模型绑定与验证、配置与日志、错误响应、认证授权、异步与性能，最后落到测试和容器化部署。读完你应当能搭出一个结构清楚、错误返回一致、可以上线的接口服务，并知道哪些位置写错会在生产环境出问题。文中以 2023 年 11 月 14 日发布的长期支持版本 .NET 8 为口径。

新建一个 Web API 项目只要两行命令。dotnet new 的 webapi 模板默认生成 Minimal API 风格的项目，习惯控制器风格的可以在创建后自行加入 Controllers 目录。

理解这段代码的关键，是把它拆成两个阶段。CreateBuilder 返回的 WebApplicationBuilder 有四个入口：Services 是依赖注入容器，Configuration 是配置来源，Logging 是日志设置，WebHost 控制服务器与绑定地址。四个入口都必须在 Build() 之前写完，因为 Build() 会把 Services 冻结成容器，之后再注册会直接抛异常。

Build() 返回的 WebApplication 同时充当管道配置器和宿主。app.Run() 是阻塞调用，它启动 Kestrel、监听端口，一直等到进程收到退出信号才返回；若需要在 Run 之后做清理，可改用 StartAsync 配合 WaitForShutdownAsync。配置按 appsettings.json、appsettings.{环境名}.json、环境变量、命令行的顺序层层覆盖，后者优先级更高，因此同一个镜像只要改一个环境变量就能换连接串。

取舍的依据主要有三条。第一条是规模：十几个端点、参数简单时，Minimal API 的“一个文件看完一条业务线”是实打实的收益；端点数到几十上百，或者一组接口要共享多个过滤器、绑定规则、版本化策略时，控制器的结构感更省事。第二条是能力覆盖面：控制器背后是一整套 MVC 管道，[FromForm]、[ModelBinder]、动作过滤器这类扩展点成熟稳定；Minimal API 的参数绑定是按需推断的，遇到表单上传、复杂类型绑定时手段更少。第三条是类型化结果：两种写法都能返回 Results/TypedResults，但 ActionResult<T> 配合 ProducesResponseType 在约束返回结构上更直观。

务实的做法是二者共存：核心资源型接口用控制器，健康检查与一次性端点用 Minimal API，不必为了统一整体重写。

依赖注入的生命周期与常见误用

容器的注册方法看似只有三个，语义差别却很大。AddSingleton 让整个进程共用一个实例；AddScoped 每个请求一个实例，同一请求内多次注入拿到同一个对象；AddTransient 每次注入都新建。要维持一次请求内状态一致的数据库上下文、工作单元属于 Scoped；无状态且创建昂贵的 HTTP 客户端封装适合 Singleton；轻量、用完就该丢开的辅助对象适合 Transient。

中间件管道：顺序、自定义中间件与认证授权的接入位置

app.Use* 与 app.Map* 注册的不是事件，而是一条首尾嵌套的调用链。每个中间件拿到 HttpContext 和下一个处理器的委托，可以在调用下游之前改请求、之后改响应，也可以直接短路；排在前面的先看到请求、后看到响应。

flowchart TD
    A[请求进入] --> B[异常处理中间件]
    B --> C[HTTPS 重定向]
    C --> D[响应压缩]
    D --> E[路由匹配]
    E --> F[认证]
    F --> G[授权]
    G --> H[业务端点]
    H --> I[响应写出]

标准管道的次序是：异常处理最靠外，好让后面所有环节抛出的异常都能被接住；然后 HTTPS 重定向与响应压缩；再静态资源；接着路由；路由之后依次认证、授权，最后才是端点。UseRouting 必须早于 UseAuthorization，写反了轻则框架报错，重则授权策略不生效、接口裸奔，这是迁移时最容易留下的安全问题。

自定义中间件有两种写法。简单的直接用 app.Use，复杂的单独成类：构造函数接收 RequestDelegate，再提供一个 InvokeAsync。

注册时写成 app.UseMiddleware<RequestTimingMiddleware>()。两个细节要注意：中间件默认是 Singleton，构造函数里注入的服务必须也是 Singleton，需要请求级服务时就像上面那样把它声明为 InvokeAsync 的参数；在 next(context) 之后再往 Response.Headers 写值并不安全，响应可能已经开始发送，加响应头要放进 OnStarting 回调。

认证与授权是位置最敏感的一环。用 JWT 做无状态认证时，注册写在 Services 阶段，策略也集中定义，免得散落到各个控制器上：

管道里对应写成 app.UseAuthentication() 再 app.UseAuthorization()。之后控制器上加 [Authorize(Policy = "OrderReader")]，Minimal API 用 .RequireAuthorization("OrderReader")。密钥不要提交进版本库，开发期用 user-secrets，生产环境从环境变量或外部密钥系统注入。最后，ClaimsPrincipal 里的声明来自令牌，凡是要查库才能决定的权限都得放在策略或服务层，不能信客户端传来的字段。

模型绑定与验证：把失败响应做成一致的

请求进来后的路径是：路由选定端点，绑定器把 JSON、查询串、表单、路由参数还原成 CLR 对象，验证器再跑一遍 DataAnnotations 或外部验证库，全部通过才进入业务方法。绑定环节最容易出的问题是“来源猜错”。加了 [ApiController] 之后框架会按约定推断：复杂类型默认读请求体，简单类型默认读路由或查询串。某个参数既要从头里读又要从体里读时，必须显式标注 [FromHeader]、[FromBody]，否则模型是空的，验证却报出一堆“必填字段缺失”，看错误信息猜不到真正原因。[ApiController] 还会在验证失败时自动短路返回 400。

自动返回的 400 默认是 ProblemDetails 结构，团队内部一般会希望固定成一种形状，这时覆盖 InvalidModelStateResponseFactory 就够了：

要点不在换字段名，而在一致性：所有接口共用一种错误结构，前端就只需写一次错误处理，看 status 决定流程，看 type 决定文案，看 errors 决定哪个输入框标红。另一句经验是：验证只描述形状，不描述意图。[Required]、[Range] 负责挡住畸形输入；至于优惠券对当前用户是否可用、库存够不够，属于业务规则，应写在服务层并返回 422 或 409 这类语义状态码。

之后注入哪个接口，取决于要不要热更新。IOptions<T> 是 Singleton，值在启动时定死；IOptionsSnapshot<T> 是 Scoped，每个请求读到的都是最新值；IOptionsMonitor<T> 也是 Singleton，但除了 CurrentValue 还提供变更通知，适合“配置变了就重建连接”的后台组件。常见错误是在 Scoped 服务里注入 IOptions<T> 却期望它跟着环境变化，或者把 IOptionsMonitor<T> 的值取出来存进字段，热更新后读到旧值。

异常处理与错误响应约定

未捕获的异常如果直接冒泡到管道外，客户端会拿到一个内容不可控的 500。约定很简单：管道最外层放一个异常处理中间件，把异常翻译成前面定好的 ProblemDetails 形状，并且永远不把堆栈或内部消息返回给客户端。

关键区别在于“已知”和“未知”走不同分支：业务异常不该打 Error 日志，也不该触发告警；未知异常要记完整堆栈，对外文案必须模糊。状态码也要定规矩，别让同一个错误在不同接口里一会儿 500、一会儿 200 带错误字段：输入形状不对用 400，没登录用 401，无权限用 403，不存在用 404，冲突用 409，业务规则不通过用 422，被限流用 429，其余才是 500。异常不是控制流，不要用抛异常来表达“没找到”。

异步、线程池与性能要点

ASP.NET Core 的线程池按“少量线程服务大量并发”设计，一个请求占着线程睡两秒，等于把这份容量白烧掉。最常见的三类错误是 .Result、.Wait() 和 async void：前两者把异步变成同步阻塞，高并发下会造成线程池饥饿；async void 的异常无法被管道捕获。接口方法应当一路 async/await 到底，不要中途退化。

CancellationToken 的传递同样重要。控制器和 Minimal API 的参数里写上它，框架会在客户端断开时触发取消；再把它一路传给 EF Core 的异步方法、HttpClient 与下游服务，用户关掉页面之后服务端就不再白跑。只在确实需要并行时用 Task.WhenAll，把一段逻辑包进 Task.Run 不但不省线程，还增加了调度成本。

性能上有几处稳定收益：JSON 序列化统一用 System.Text.Json，热点类型用源生成减少反射；响应体大的接口开压缩；读多写少的数据用 IMemoryCache 或输出缓存，需要跨实例共享才考虑 Redis；出站 HTTP 一律走 AddHttpClient，由工厂管理 handler 生命周期并复用连接，别在请求里 new HttpClient；数据库连接池有上限，慢查询与未关闭的阅读器会迅速耗尽它。这些优化都应当先测量再动手。

测试与容器化部署

接口层的测试建议走真实管道，而不是直接调用控制器方法。WebApplicationFactory<T> 会在内存里启动整个应用，注册、中间件、绑定、验证、错误格式全都跑一遍，只把网络换成测试服务器。Minimal API 用了顶层语句，要在 Program.cs 末尾补一行 public partial class Program { }，测试项目才有入口类型可引用。

替换依赖要用 ConfigureTestServices，它在应用自身注册之后执行，才能覆盖掉真实的 DbContext 或外部客户端。另外测试服务器不走真实网络，UseHttpsRedirection 会把请求跳到不可达的地址，测试环境要绕开它。部署用多阶段构建，构建阶段要 SDK，运行阶段只要运行时，镜像会小很多；下面以项目目录作为构建上下文：

小结

本文按一个请求的生命周期把 ASP.NET Core Web API 串了一遍：Build() 之前只谈注册，之后只谈管道；中间件的顺序里藏着安全，异常处理的分支里藏着可运维性；生命周期选错会把请求级状态提升成全局状态；异步一路到底、令牌一路传下去，是线程池扛住并发的底线。落地时先定三件事：错误响应的结构、日志字段与跟踪号、依赖注入的生命周期规范，把这三样写进模板项目，后面的分歧会少很多。
