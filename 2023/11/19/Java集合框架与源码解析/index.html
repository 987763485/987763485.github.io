Java 集合框架与源码解析

集合是 Java 代码里最常被“会用但没选对”的一层：人人都写 List 和 Map，但容量怎么长出来、哈希如何定位、遍行为什么抛异常、并发下换哪个容器，才真正决定性能与正确性。本文以 JDK 17 与 JDK 21 为口径，沿接口族谱往下走，讲清 ArrayList、LinkedList、HashMap 及几个派生类型的行为，再谈键契约、fail-fast、并发集合与容易踩坑的创建方式。

接口族谱：先问要不要映射，再问要不要顺序

Java 集合框架是两棵独立的树。左边一棵以 Iterable 为根，Collection 继承它，List、Set、Queue 再继承 Collection，Deque 又继承 Queue；右边的根是 Map，不在 Collection 体系内，只能靠 keySet、values、entrySet 三个视图变成集合来遍历。这个结构决定了选型的第一问：需要的是键到值的映射，还是一串元素？

flowchart TD
    Iterable --> Collection
    Collection --> List
    Collection --> Set
    Collection --> Queue
    Queue --> Deque
    List --> ArrayList
    List --> CopyOnWriteArrayList
    List --> LinkedList
    Deque --> LinkedList
    Deque --> ArrayDeque
    Set --> HashSet
    HashSet --> LinkedHashSet
    Set --> TreeSet
    Map --> HashMap
    HashMap --> LinkedHashMap
    HashMap --> ConcurrentHashMap
    Map --> TreeMap

第二问是顺序与唯一性。List 保留索引与重复元素；Set 靠 hashCode 与 equals 判重，本质是一个只用键的哈希表；Queue 关心进出顺序，Deque 允许两端进出；TreeSet 与 TreeMap 还要求键可比较。第三问才落到具体实现，差别在数据布局、扩容与比较方式。

把这几问串起来，可以得到一张速查表：

需求 优先选择 备注
按下标读写、末尾追加 ArrayList 随机访问常数开销最小
只从两端进出，或当栈用 ArrayDeque 不要因为“是队列”就选 LinkedList
键值映射，不关心顺序 HashMap 允许一个 null 键
遍历顺序要等于插入顺序 LinkedHashMap 也能改成按访问顺序
要按键排序或做区间检索 TreeMap 键必须可比较
去重且不关心顺序 HashSet 内部就是一个 HashMap
多线程共享同一份数据 ConcurrentHashMap 或 CopyOnWriteArrayList 别用同步包装硬扛

还有一层关系容易被忽略：Comparator 不在族谱里，却同时影响 List.sort、TreeMap 与 TreeSet 的行为，后文会再遇到它。

ArrayList：底层数组与扩容策略

ArrayList 的存储字段只有一个 Object[] 加一个记录元素个数的 size。之所以是 Object[] 而不是泛型数组，是因为类型擦除后无法创建 E[]，读元素时靠强转把类型补回来。

不带参数的构造器不会立刻占住内存：内部数组先指向一个共享的空数组，直到第一次添加元素才建立长度为 10 的数组，省掉的正是那些最终没装东西的列表的开销。

扩容发生在 size 等于数组长度时。新容量取旧容量加上它右移一位的结果，也就是 1.5 倍；若本次要求的最低容量更大，就直接采用需求值，避免连扩两次。搬移是一次连续数组拷贝，旧数组随即变垃圾。取 1.5 而非 2 倍，是拷贝次数与空闲槽位的折中。

预分配的价值是跳过中间所有扩容台阶：要放 10 万个元素时从 10 开始会拷十几轮，总量虽均摊，但每轮都搬运一整段引用，容易在热点路径上形成毛刺。同理，转换别的集合时优先用带集合参数的构造器或 addAll，批量添加会一次算清“当前元素数加待加数量”需要的容量，比循环调用 add 少好几轮扩容。

随机访问是 O(1)，几乎任何场景都占优；代价在中间位置。add(index, e) 与 remove(index) 要把插入点之后的元素整体挪一格，工作量与尾部长度成正比，所以“中间插入多就该换链表”这个直觉要慎重，下一节解释。另外它不是线程安全的，并发 add 会覆盖彼此。

LinkedList：双向链表的真实位置

LinkedList 的节点存三个字段：元素、前驱、后继，列表本身再维护首尾指针与 size。它同时实现 List 与 Deque，这正是误用的源头：看见“链表”就以为中间插入便宜。

先看作为 List 的成本：按下标的操作都要先遍历过去，get(i) 与 add(i, e) 也不例外，定位是 O(n)，只有定位后的断链重接才是 O(1)。ArrayList 的中间插入确实要移动元素，但那是连续的数组拷贝，硬件最擅长这类工作；LinkedList 的遍历却是指针追逐，每一步都可能 cache miss。每个节点又是独立对象，除引用外还有对象头与对齐开销，散落在堆上也加重 GC 负担。综合下来，绝大多数“中间频繁插入”的实测仍然是 ArrayList 更合适。

真正划算的是它作为 Deque 的那半张脸：addFirst、addLast、removeFirst、pollLast 这类两端操作都是常数时间。但只需要队列或栈语义时，ArrayDeque 通常是更好的选择：循环数组、两端常数时间、没有节点分配、内存紧凑，代价是要扩容且不允许放 null。老的 Stack 类继承自 Vector，属于遗留 API，写栈请直接用 ArrayDeque。

那么什么时候真的需要链表语义？答案是外部已经握着某个节点的把手、要 O(1) 把它摘下来，典型内部结构就是 LRU 的双向链表。在 Java 集合里更稳妥的做法是用 LinkedHashMap 的访问顺序，或自定义节点。

HashMap：数组加桶、哈希扰动与 resize

HashMap 的存储是一个节点数组，每个槽位放一条链表的表头。落到同一槽的键串成链；遍历顺序不保证与插入顺序有关，也不应被依赖。

槽位下标不是取模，而是数组长度减一与哈希值做按位与，因此长度必须是 2 的幂：构造器传入 17，实际会向上取整到 32。2 的幂还带来第二个好处，resize 时会用到。

扰动就是把哈希值与它右移 16 位的结果做异或。定位只取低位若干位，如果一批键的 hashCode 差异集中在高位、低位却雷同，不扰动就会全部挤进同一个桶。一次位运算换来明显更均匀的落点。

负载因子默认 0.75，阈值是容量乘以它：容量 16 时装到 12 个元素就 resize。resize 让容量与阈值同时翻倍。重分布不重算哈希，而是用哈希值与旧容量按位与是否为 0 把每个桶拆成两组：一组留在原下标，另一组移到旧下标加旧容量。链表因此可以整段切开，这又是 2 的幂容量带来的便利。

桶内链表长到 8 时，HashMap 先检查表容量：不足 64 只做扩容，把键分散开；容量不小于 64，才把这桶转成红黑树，节点升级为树节点。收缩时树节点数降到 6 及以下就还原成链表，8 与 6 之间留缓冲以免在临界值上反复转换。为什么阈值取 8？官方注释按泊松分布估算，正常哈希下桶内长到 8 属于极小概率事件，出现了就该怀疑哈希质量差或有人制造冲突。树化因此是防御性兜底，不是性能优化手段。

结论是优先把 hashCode 写好，比调初始容量与负载因子有效得多。要放 n 个元素又不想中途扩容，初始容量按 n 除以 0.75 向上取整，构造器会圆到最近的 2 的幂。还要牢记 HashMap 不保证线程安全：并发 put 会互相覆盖，扩容期间的并发读写可能看到不一致的结构。

键的契约：equals、hashCode 与可变 key

HashMap 定位一个键分两步：先用 hashCode 选桶，再用 equals 在桶内比对。契约只有一条硬约束——equals 判相等的两个对象，hashCode 必须相同。反过来 hashCode 相同而 equals 不同是允许的，代价只是冲突变多。违反硬约束则致命：逻辑相等的键落进不同桶，get 找不到、containsKey 为 false，put 又把它们当成两个键。

手写容易漏字段，可交给 Objects.equals 与 Objects.hash。String、包装类、java.time 下的类型与 BigDecimal 都不可变，本来就是好键。

最隐蔽的坑是可变 key：对象放进 HashSet 或当作键之后，修改参与 hashCode 的字段，等于把自己藏进了错误的桶。此后 get、containsKey、remove 全部失效，而它仍被内部数组强引用，回收不掉，表现为内存泄漏。需要“键不再被外部引用就自动清理”的语义，那是 WeakHashMap 的职责。

LinkedHashMap 与 TreeMap：顺序与有序是两件事

LinkedHashMap 在桶结构之外，再给所有节点串一条贯穿的双向链表，所以迭代顺序可控。默认按插入顺序；构造时把 accessOrder 设为 true，每次 get 命中都会把节点移到链尾，链头就是最久未访问的那个。再配合 removeEldestEntry 钩子，十几行就能得到一个 LRU。

两个提醒：accessOrder 下连 get 都是写操作，多线程共享必须外部同步；钩子只数条目数，不看权重，要按内存淘汰请交给成熟的缓存库。需要“遍历顺序等于插入顺序”的集合时，LinkedHashSet 就是一个只用键的 LinkedHashMap。

TreeMap 是另一回事。它维护一棵红黑树，实现 SortedMap 与 NavigableMap，因此能按键做区间检索，firstKey、floorKey、ceilingKey、subMap 每个都是 O(log n)，明显优于“先塞进 HashMap 再排序”。比较规则优先用构造器传入的 Comparator，没传则要求键实现 Comparable，否则第一次 put 就抛 ClassCastException，默认排序下 null 键也会抛。还有一点：TreeMap 判定同一个键看比较结果为 0，不看 equals 与 hashCode。TreeSet 只是它的薄封装，元素当键、值共用一个哑对象。

fail-fast：ConcurrentModificationException 从哪来

ArrayList 这类实现内部有一个 modCount，任何结构性修改都让它加一。迭代器创建时记下期望值，每次 next 与 remove 之前比对，不一致就立刻抛 ConcurrentModificationException。

要理解它的定位：这是防单线程误用的断言，不是并发检测机制。它不保证一定抛——刚好删到只剩末尾元素时就可能漏检；把捕获这个异常当成并发控制手段是错的，竞态更常表现为数据悄悄丢失。安全的写法还有倒序按下标删，或边遍历边往新集合里加。

并发遍历的正解是换容器：ConcurrentHashMap 与 CopyOnWriteArrayList 的迭代器是弱一致的，看到某时刻的快照，不抛异常，但也不保证读到并发写入。

并发集合：换代之后的选择

Hashtable 与 Vector 的问题不只是慢。它们每个方法都 synchronized，一把锁罩住整张表，读与读之间也互斥；遍历依赖 enumerate 这类遗留 API，而 keySet、entrySet 的迭代仍需调用方自己加锁。现在只该在维护遗留代码时遇到。Collections.synchronizedMap 之类包装本质相同，只是把监视器挪到一个专门的互斥对象上，遍历时照样要手动锁住整个集合。

ConcurrentHashMap 的演进思路是把锁的粒度一路缩小。早期实现把表切成若干段，每段一把锁，并发度约等于段数。后来改成与 HashMap 同形的数组加桶结构：空槽用 CAS 直接占位，不加锁；槽位非空才对该桶头节点加锁；扩容由多个线程协作，各自认领一段桶搬迁；读取基本无锁。

粒度变小不等于复合操作安全，containsKey 加 put 仍是竞态，要用 putIfAbsent、compute、merge 这些原子方法；映射函数里不要再递归修改同一个 map，这种自修改会被检测到并抛异常。此外 size 与 mappingCount 是汇总出来的估计值，别当精确快照；它也不允许 null 键与 null 值，因为并发下 get 返回 null 无法靠 containsKey 消除歧义。

CopyOnWriteArrayList 走的是另一个方向：不减少冲突，而是彻底复制。读直接读当前数组引用，无锁；写在新数组上完成后一次性替换引用。迭代器因此是创建时的快照，既不抛异常也读不到后续改动。边界很清楚：每次 add 都复制整个数组并短暂占两份内存，列表长或写频繁时成本迅速上升。它适合监听器列表、灰度规则这类读远多于写、能容忍短暂旧数据的场景；CopyOnWriteArraySet 是它的去重封装。生产者消费者场景请交给 BlockingQueue，别用集合加轮询。

创建集合的坑：Arrays.asList、List.of 与不可变视图

Arrays.asList 返回的不是 ArrayList，而是一个固定大小的视图，底层直接持有传入的数组。add 与 remove 抛 UnsupportedOperationException，但 set 可以，而且会改到原数组。它还有个类型陷阱：

Java 9 起的 List.of、Set.of、Map.of 才是真正的不可变集合：不接受 null，Set 与 Map 遇到重复元素或重复键直接抛异常；它们自己实现查找逻辑，通常比等价的 HashSet、HashMap 更省。Java 10 的 copyOf 系列做防御性拷贝，注意入参已是同类不可变集合时可能直接返回它自己。与之相对，Collections.unmodifiableList 只是包装视图，底层被改它就跟着变，不是不可变副本。要不可变就用 of 与 copyOf，空集合用 Collections.emptyList()。另外 stream 收集到 toList 的结果在规范上没承诺一定可变，需要可变的就明确写 toCollection。

Java 21 还给这一族接口补了 SequencedCollection 与 SequencedMap：List、Deque、LinkedHashSet 等统一提供 getFirst、getLast、addFirst、removeLast 与 reversed 视图，写与具体容器无关的通用代码时有用，但它只是接口层的补充，底层结构没变。

小结

几句可执行的话：默认组合是 ArrayList 加 HashMap；知道规模就预分配；LinkedList 只在真正需要两端进出时才值得，普通队列交给 ArrayDeque；HashMap 的性能关键在 hashCode 分布，树化是抗冲突兜底；键要不可变，两个方法交给 record 生成；遍历中改集合就交给迭代器或 removeIf；并发共享用 ConcurrentHashMap 与 CopyOnWriteArrayList，别再用 Hashtable 与 Vector，也别指望同步包装替你锁住遍历；Arrays.asList 是视图，List.of 才是不可变。
