Rust 集合类型：Vec 与 HashMap

本文属于《Rust 学习路线》第 7/68 篇
上一篇系列目录下一篇

Vec 与 HashMap 是 Rust 里用得最多的两个集合。它们看起来只是“放进去、取出来”的容器，但内存布局、扩容策略与哈希器选择会直接决定代码的性能特征，甚至决定它在恶意输入下是否安全。本文回答三个问题：什么时候必须预分配、为什么迭代时不能顺手 push、默认哈希器该不该换。文中 API 以 2023 年 10 月发布的 Rust 1.73 稳定版为准；迭代器与闭包的语义、结构体与枚举的定义语法不在本文展开。

Vec 的连续内存布局

Vec<T> 是拥有所有权的动态数组，概念上只有三个字段：指向堆缓冲区的裸指针、元素个数 len、已分配容量 capacity。在 64 位平台上它们各占一个 usize，Vec<T> 本身固定 24 字节，传给函数时移动的就是这 24 字节，堆上数据不会跟着复制。

元素按下标紧挨存放，v[i] 的地址就是基地址加偏移，随机访问 O(1)，顺序扫描对 CPU 预取友好；代价是在中间插入或删除，必须把它之后的元素整体前移或后移，因此是 O(n)。len 与 capacity 的区分是理解 Vec 的前提：前者决定循环走多少轮与允许的最大下标，后者决定还能不重新分配地容纳多少元素，中间的空闲区可能未初始化，永远不能按下标去访问；越界会直接 panic，想要可空的结果就用返回 Option<&T> 的 get(i)。T 必须是 Sized 的，标准库要按固定步长算偏移。

push 在 len < capacity 时只是把元素写到末尾、len 加一，成本是常数；一旦满了就要申请更大的缓冲区、把已有元素全部搬过去、再释放旧的。标准库的策略是“翻倍”：新容量取现有容量的两倍与需求量中的较大者。于是连续 n 次 push 只扩容 O(log n) 次，搬迁总量与 n 成正比，摊到每次 push 上仍是常数，这就是均摊 O(1) 的来历。两个后果要记住：扩容是整段搬迁，push 之后从同一个 Vec 借出的 &T 可能已经指向被释放的旧缓冲区；元素很大时它们全挤在同一段连续内存里，这时在 Vec 里放 Box<T> 之类的指针类型更划算。

预分配：with_capacity 与 reserve

既然扩容要整段搬迁，知道最终规模时就该一次申请够，让全程只分配一次。Vec::with_capacity(n) 构造一个 len 为 0、capacity 至少为 n 的空 Vec，适合“数量已知、内容后填”的场景，传入 0 与 Vec::new() 等价，不会分配堆内存。reserve(additional) 要求还能再放下 additional 个元素，由于顺带应用翻倍策略，实际分配通常更多；reserve_exact 尽量精确地只扩到 len + additional，元素较大又在意内存占用时更省。shrink_to_fit 把容量往 len 的方向收，但只是提示，实现可以什么都不做。

最后一行的门道在于 collect 会读取迭代器的长度提示：上界可确定时先把容量备好，所以 (0..n).collect::<Vec<_>>() 通常只需一次分配，extend 同理。

增删操作的复杂度差异

Vec 的接口虽多，复杂度却只分两类：动末尾的是常数，动中间的是线性，下表中的 n 表示当前元素个数。

操作 复杂度 说明
push / pop 均摊 O(1) 只在末尾动作，扩容时才搬迁
insert(i, x) / remove(i) O(n - i) 其后元素整体后移或前移
swap_remove(i) O(1) 用末尾元素补位，不保序
drain(range) O(n) 移交区间所有权，迭代器被丢弃时仍会执行
retain(f) O(n) 原地压缩，保留元素相对顺序不变
splice(range, it) O(n) 换入新元素、换出旧元素，需要重算长度

末尾动作便宜、中间动作昂贵，这一点决定了实现选择。若业务不要求顺序，用 swap_remove 取代 remove 能把一次 O(n) 的删除降到 O(1)：把待删位置与末尾元素交换再 pop，代价是不再保序。retain 按谓词原地过滤，对返回 false 的元素就地析构、返回 true 的向前压缩，不额外分配，闭包只拿到 &mut T，能改元素内部但不能把元素移走；它与 into_iter().filter(..).collect() 的差别是复用同一块缓冲区并保留容量。drain(range) 交出区间元素的所有权并返回 Drain 迭代器，妙处在于即使提前 drop 或根本不消费，它析构时仍会析构剩余元素、把后面前移并修正长度，所以 v.drain(..); 等价于 v.clear()。splice(range, iterable) 先交出旧区间再填入新内容，换入与换出的个数可以不同，内部要重算整段布局，成本同样是 O(n)。

其次是干脆不借用、按下标走：下标是 Copy 值，不构成借用，读写同一个 Vec 不再冲突，但要自己保证下标有效；长度在循环中变化时，正向遍历加插入会让每个新元素被再次访问，所以要么倒序，要么只处理进循环时记下的原始长度。

其余情形各有对应写法：边遍历边判断是否删除，交给 retain，压缩由标准库完成；要同时读写互不重叠的两段，用 split_at_mut、split_first_mut 这类方法把一段可变借用切成两半；要整体重写内容，可以先用 std::mem::take 把 Vec 临时搬走，借用自然结束，算完再放回原处。

还有一个静默陷阱：持续 push 时，别处存下的下标仍然有效，读到的却已经是新缓冲区里的数据。索引只在 Vec 不再增长时才可靠，把“位置”当成“身份”是这类 bug 的共同成因。

Vec 作为返回值与切片的分工

集合在函数边界上怎么传是最常见的分歧，原则只有一句：产出集合就返回 Vec<T>，消费集合就接受 &[T]。

返回 Vec<T> 意味着把整段缓冲区的所有权交给调用方，不需要 Box 或引用计数再包一层。不能写的是返回指向局部 Vec 内部元素的引用：函数结束时 Vec 析构、堆缓冲区释放，借出的 &T 或 &[T] 都会悬垂，借用检查器会直接拒绝这类签名。所以要么把数据造出来交出去，要么把输入借过来改写。

参数侧的收益更实际：签名写成 &[T] 而不是 &Vec<T>，调用方就能传 Vec、数组、Vec 的某一段乃至 Box<[T]>，全部靠一次解引用强制转换完成，clippy 也会对后者提出提示；要改变长度才写 &mut Vec<T>，只改写已有元素用 &mut [T]。两者的分工在于谁拥有内存：切片只是一个指针加一个长度，生命周期必须挂靠某段实际存在的数据，从输入里切出来返回合法，把本地构造的结果切成 &[T] 返回不合法。as_slice() 零成本地视图化；into_boxed_slice() 交出没有容量字段的 Box<[T]>，capacity 大于 len 时会重分配一次来收缩，只在确定不再追加时才用。

HashMap 的哈希器与碰撞 DoS 的取舍

HashMap 的完整类型是 HashMap<K, V, S = RandomState>，第三个参数 S 是哈希构建器。标准库把它做成类型参数，等于明说哈希器可以换。

RandomState 使用 SipHash-1-3（标准库自 Rust 1.60 起从 SipHash-2-4 换成它），并以进程启动时取到的随机种子作密钥，同一个 key 在不同进程里哈希值不同。它换来的是一条抗哈希碰撞拒绝服务的防线：哈希表的性能前提是桶里元素很少，而碰撞是可以构造的，攻击者只要知道哈希函数且没有密钥，就能批量造出哈希相同、值却不同的 key，把 O(1) 的点查拖成接近 O(n) 的线性扫描；服务只要把外部提交的字符串当 key 存进表，就可能被少量请求打爆 CPU。2021 年公开的 Hash-Ghosts 议题还提醒过，带密钥的算法若在长度处理上有缺陷，实际防护也可能弱于预期。

防线是有价格的：SipHash 带密码学强度，比只求分布均匀的通用哈希慢上一截，所以点查位于绝对热路径、key 又完全可信时（内部整数 id、程序自己生成的字段名），换用更快的哈希器是合理的。做法是接一个第三方实现，用 BuildHasherDefault 把哈希器写进类型参数，下面以 rustc-hash 的 FxHasher 为例，需要在 Cargo.toml 里引入该依赖：

构建、查询与 Entry API

HashMap::new() 与 HashMap::default() 都不分配桶空间，首次插入才真正分配；with_capacity(n) 按预计元素数预留，内部会换算成桶位，所以 capacity 通常大于 n。读路径首选 get(&k)，它返回 Option<&V>，参数是 &Q：正因为 String: Borrow<str>，用字符串字面量就能查 String 键的表；要改值用 get_mut，连键带值一起拿用 get_key_value。insert(k, v) 会返回被替换掉的旧值。索引语法要当心：只读的 map[&k] 在键不存在时直接 panic，可变的索引却会先插入一个 V::default() 再返回，两个方向并不对称，读操作别图省事用方括号。

低效写法是 if !map.contains_key(&k) { map.insert(k, v); }，查两遍也哈希两遍；Entry API 把它压成一次定位，返回的位置对象上接什么，决定命中与未命中怎么办。两个细节最容易踩：or_insert(v) 的参数是普通表达式，即使命中也照样求值，昂贵的初值必须换成 or_insert_with(|| ...)；entry(k) 按值消费 key（借用 key 的写法当时尚未稳定），key 之后还要用就得先克隆。

迭代顺序与自定义 key

keys()、values()、into_iter() 的顺序既不稳定，也不保证跨运行一致：种子每进程随机，桶位还随扩容重排。别把它当输出格式，也别因为本机几次都有序就依赖它；真要有序，就把键收集到 Vec 里排序，代价是 O(n log n)。

自定义 key 要同时满足 Hash 与 Eq，结构体上派生这两个 trait 通常就够，但不变量只有一条：相等的 key 必须哈希相同。凡参与相等比较的字段都要参与哈希；反过来在哈希里多喂一些 Eq 不看重的字段同样危险，本该命中的键会查不到。浮点类型当不了 key，原因在类型层面：f32 与 f64 实现了 Hash 和 PartialEq，却没有实现 Eq，因为 NaN != NaN 破坏了自反性，硬塞进去只会让 trait bound 检查失败。想要近似语义就换表示，量化成定点整数最直白，或者用 total_cmp 建立全序再配一个与位模式一致的 Hash。

容量、rehash 与 BTreeMap 的取舍

哈希表的 capacity() 是桶位数、len() 是元素数。装载率逼近上限时触发扩容，所有元素要重新哈希、重新排布，比 Vec 那次整段搬迁更贵，所以 with_capacity 与 reserve 对哈希表同样值得，shrink_to_fit 也仍是提示。剩下的问题只有一个：要不要顺序。

维度 HashMap BTreeMap
key 约束 Hash + Eq Ord + Eq
点查 均摊 O(1) O(log n)
迭代顺序 不稳定 按 key 升序
范围查询 不提供 range 支持
扩容代价 全表 rehash 局部节点分裂
典型场景 计数、去重、倒排索引 排行榜、时间窗口、稳定输出

key 本来就实现了 Ord、又需要天然有序或按区间取值，BTreeMap 更省心；只要平均意义上最快的点查，就留在 HashMap。至于既要 O(1) 点查又要按插入顺序遍历，标准库当时并没有对应类型，常见做法是 HashMap 配一个 Vec 记下顺序。元素只有几个时，两者的常数差异并不稳定，别凭直觉下结论，压测说了算。

小结

Vec 的性格来自连续内存：末尾操作均摊 O(1)，中间操作 O(n)，扩容是整段搬迁，所以知道规模就用 with_capacity 或 reserve，把引用与下标的风险压到最低。HashMap 的性格来自哈希器：默认 RandomState 用带种子的 SipHash-1-3 挡住碰撞型拒绝服务，只有 key 完全可信且点查极热时才值得替换；Entry API 把两次查找压成一次定位，迭代顺序不可依赖，浮点当不了 key。两者配合的惯用形态就是用 HashMap 聚合、落到 Vec 上排序与输出，把这几条边界记牢，集合这一层就很少再出意外。
