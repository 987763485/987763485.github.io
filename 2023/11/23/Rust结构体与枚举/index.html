Rust 结构体与枚举

本文属于《Rust 学习路线》第 5/68 篇
上一篇系列目录下一篇

结构体和枚举是 Rust 里组织业务数据的两个基本工具：结构体回答“一件东西由哪些部分组成”，枚举回答“一件事正处在哪种情形”。本文从结构体的三种形态讲起，说明可见性、更新语法与 Default、方法接收者的选择，然后把重点放在枚举变体携带数据上——这是把状态机写得既难出错又好演进的关键。读者假定已会写变量、函数与控制流，本文只谈数据建模；match 的完整模式语法、借用与生命周期各有专文。示例以 Rust 1.73 为口径，2021 edition。

结构体不止一种写法

最常遇到的是具名字段结构体：每个字段都有名字、有类型，字段的顺序无所谓。它是 Rust 里表达“一条记录”的默认手段，也是本文其余讨论的基准形态。

三种形态的取舍标准很清楚。具名字段可读性最好，字段名本身就是文档，三个以上字段基本都该用它；代价是构造时要写全名字。元组结构体适合“语义就是那几个值，名字反而多余”的场合，例如像素、坐标、长度单位；字段一多，.0、.1 就退化成谁也看不懂的下标，这时该改回具名字段。单元结构体不携带数据，实例只用来表明类型，常见于标记类型和给空类型实现 trait 的场景。

字段类型必须逐个写全。let 可以靠推断，结构体定义不行，因为定义处在模块边界上，需要一眼看出布局与接口。另外结构体是名义类型：两个字段完全同名同型的结构体不能直接赋值或传参，必须显式转换，这也是新手常在函数签名前困惑的来源。

pub 的粒度也容易被误解。Rust 没有 private 关键字，不写 pub 就是私有，而私有的判定范围是“当前模块及其子模块”，不是“当前结构体”。把结构体本身声明为 pub，字段仍然是私有的，外部模块只能拿到它、把它传来传去，不能读写内部。

于是“字段全 pub”与“字段私有加构造函数”就构成封装光谱的两端：前者是数据载体，后者是不变式的守门人，这个取舍留到后面专门讨论。

构造、更新语法与 Default

字段少的时候逐个写出来还行，字段一多就出现两个麻烦：初始化代码冗长，以及新增字段时所有构造点都要改。Rust 用结构体更新语法（functional update）缓解后者：

..base 必须放在最后，且 base 与目标结构体类型一致。这里有个与所有权相关的细节：更新语法按字段搬运值，实现了 Copy 的 port、workers、tls 被复制过去，String 这种非 Copy 字段则整体移动进新结构体。所以上例中 base 之后不能再整体使用，单独读 base.host 也会被借用检查拒绝。这不是更新语法独有的坑，具体机制见所有权专文。

字段较多、且有合理零值时，更省事的做法是派生 Default：

#[derive(Default)] 对整数给 0、对布尔给 false、对 String 给空串、对 Option<T> 给 None。它适合“零值就是合法配置”的结构体；如果某些字段留空意味着程序写错了（比如超时必须为正数），就别派生 Default，改用显式构造函数配合校验，让非法状态在类型层面无法构造。私有字段还有一层限制：.. 更新语法只能在该字段可见的地方使用，因此跨模块的私有字段结构体，几乎一定要有一个 pub fn new。

方法、self 的三种接收者与关联函数

行为写在 impl 块里，与数据定义分开。方法的第一个参数是接收者，它决定了这个方法对实例做什么，也是 Rust 与许多语言差别最大的地方：

三种接收者的选择有明确规则。&self 用于查询，代价最小，调用方不受影响；&mut self 用于就地修改，调用期间原实例不能同时被读；self 用于“这一步之后这个值就该结束”的情形，例如把中间结构体转成响应对象、消费完一个 builder。写成 self 就拿到所有权，方法返回后原变量失效，这恰好能防止状态被继续使用，但用错会让调用方莫名其妙，所以只在确实需要消费时用。还有一种 self: Box<Self> 的写法，主要出现在通过堆上的 trait 对象递归转移状态时，属于动态分发话题，本文不展开。

调用点比定义点宽松。对 &mut self 方法，写 c.step() 就够了，编译器会自动补 & 或 &mut 并按需解引用；但接收者的语义不会被绕过——into_snapshot 消费 self，所以 main 里要先 clone 才能继续用 c。方法名与字段名可以相同，访问时靠有没有括号区分。同一类型可以写多个 impl 块，把构造函数、行为、trait 实现分组到不同位置是常见做法。

字段私有与封装的取舍

Rust 的封装单位是模块而不是结构体，这条规则决定了取舍的实际手感：私有字段对本模块及其子模块可见，对模块外不可见。同一个文件里的单元测试模块通常写作 mod tests 并用 use super::*，它属于子模块，因而天然能读写私有字段——封装并没有阻碍测试，只是挡住了模块之外的随手改。

实践中有两种常见姿势。一种是数据载体：配置结构体、数据库行映射、序列化用的 DTO，字段全 pub，没有不变式，构造完就只读或整体替换。另一种是带不变式的领域类型：字段私有，只暴露 new 之类的构造入口和表达业务意图的方法，把“非法值根本无法存在”写进构造函数。两者的区别不在字段数量，而在于“字段组合起来是否可能不合法”。

不建议做的是给每个字段配一对 getter 和 setter：那等于花一遍封装的代价，把收益还回去，外部仍然能任意改写，还多一层方法调用。真要暴露可修改性，让方法返回 &mut 或者干脆把字段设为 pub 更诚实。反过来，一开始把字段设为 pub 也不算错误决策——收紧可见性只需去掉一个 pub，所有越权访问立刻按行变成编译错误，成本远低于运行时才暴露的问题。字段是否 pub，本质上是在选择“这个类型出错时由谁负责”。

如果枚举只能表示“是哪一种”，它就只是一个带名字的整数。Rust 枚举的关键在于每个变体可以自带数据，而且不同变体带的数据可以完全不同：

Option 与 Result 也是枚举

标准库里的 Option<T> 和 Result<T, E> 没有任何特殊语法地位，它们就是普通枚举：

Option 把“可能没有值”写进类型，替代了空指针：想取里面的值必须先处理 None 分支，编译器不允许把 Option<String> 当 String 用。Result 则把“可能失败且有原因”写进类型，两个变体各自携带成功值与错误值。它们与自定义枚举的唯一区别，是被语言赋予了额外便利：if let、? 和组合子方法都优先为它们服务。

这个红利有一个常见的自我破坏方式：随手写 _ => {}。兜底分支让穷尽性检查失效，新增变体被静默吞掉，前面说的定位能力全没了。合理的做法是只在本就有意忽略的地方使用通配，并写清为什么可以忽略。更精细的模式组合、嵌套解构与守卫条件属于模式匹配的专门内容，本文不重复。

let else 的 else 块必须以 return、continue、break、panic! 之类的方式结束当前路径，不能只是一个普通表达式；因此它天生用于校验式提前返回，而不是分支业务。顺序上读起来像先声明前提、再写正事，配合 Result 的错误提前返回，函数体通常只剩一条主干。

把枚举当状态机用

把前面几件事合起来，就是一个可编译检查的状态机。约定是：状态用带数据的枚举表示，迁移写成消费 self、返回新状态的方法，非法迁移返回 Err。

flowchart TD
    Created[已创建] -->|pay| Paid[已支付]
    Paid -->|ship| Shipped[已发货]
    Shipped -->|confirm| Done[已完成]

两处细节支撑了整套约束。第一，迁移方法接收 self 而不是 &mut self：原状态被消费掉，调用方只能使用返回的新状态，不会拿到“改了一半”的实例。第二，每个 match 都写全了其余变体，没有通配兜底——将来加一个“退款中”变体，pay 和 ship 立刻报错，逼作者显式回答“退款中的订单能否再支付”。状态与数据绑在一起，迁移写成函数，合法性就同时有编译期和运行期两道防线。

newtype 与几个常见误区

单字段的元组结构体有个专门名字，叫 newtype。它的用途是给语义不同的同类值分家：

u64 在两个类型之间不会自动互通，传错顺序、把订单号当用户号使这类事故被挡在编译期，而它只是同一底层值的另一层名字，运行期没有额外结构。想让包装类型好用，可以给它实现需要的 trait，或者把字段设为私有、只开放受控的转换方法。

几个反复出现的误区值得记下。最典型的是用多个布尔字段描述互斥状态，合法组合靠文档约束，正确性靠运气。其次是只把枚举当常量列表，enum Status { Created, Paid } 不带数据，数据依旧摊在结构体字段里，非法组合原样回来。再次是接受 Option<Option<T>> 或连续几个 Option 字段——嵌套的可选值几乎总意味着状态该拆成枚举。另外，字段一旦写成 &str 或 &T，定义就要带生命周期标注，多数业务类型更该拥有自己的数据。最后，给全 pub 字段配一整套运行时校验也得不偿失：校验只能事后补救，类型设计可以事前拦截。

小结

结构体负责“由哪些部分组成”，三种形态按字段数量与语义清晰度选择；pub 的粒度是模块，字段可见性决定了出错由谁负责。构造上，更新语法与 Default 解决冗余，但要记住非 Copy 字段会被移动。方法靠接收者表态：&self 查询、&mut self 就地改、self 消费，关联函数负责构造。

枚举的真正价值在变体携带数据：状态与它专属的数据绑死，非法组合无法被表达；Option 与 Result 是这条规则最日常的两个应用。match 的穷尽性检查让改模型变成一次可编译验证的重构，前提是不要滥用通配分支。if let 处理单一情形，let else 处理前置解包后提前退出。建模时的默认动作是：先问“这些字段组合起来有没有非法状态”，有，就把它拆成枚举。
