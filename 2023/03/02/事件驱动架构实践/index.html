事件驱动架构实践

本文属于《Go 微服务架构》第 5/35 篇
上一篇系列目录下一篇

很多团队引入消息队列的起点很朴素：把一个慢操作挪到后台，或者让两个服务别再互相调用。可一旦消息开始流动，问题就不再是”发出去”这么简单：这条消息是事实还是请求，消费者能不能重复处理，字段改了老消费者会不会崩，出问题又该从哪查起。本文从这些困惑出发，梳理事件驱动架构的几个关键决策：事件与命令的区分、事实的不可变性、契约与 schema 演进、发件箱与 CDC、投递语义与顺序、编排与协同、事件溯源的边界，以及可观测性与治理。

事件、命令与查询：先把三种消息分开

很多所谓”事件驱动”的系统，拆开看其实是把 RPC 换了个壳：订单服务发一条 OrderCreated，库存、积分、物流各自收到后执行一个必须成功的动作，发送方也默认它们会这么做。这条消息名义上是事件，实际上每个消费者都在完成一次分布式调用，却没有超时、没有重试策略，也没有返回值。

要避免这种混淆，先把三类消息分开。命令（Command）表达”请做某事”，命名是祈使句，比如 ReserveStock、ShipOrder；它有明确的接收者，可以被拒绝，拒绝理由要能返回给发起方。事件（Event）陈述”已经发生的事实”，命名用过去式，比如 OrderPlaced、PaymentCaptured；它没有接收者列表，发布者不知道也不该关心谁在听，消费者只能决定自己如何反应，不能拒绝。查询（Query）只读，不改变状态，也不需要经过消息通道，把它做成”发一条消息再等回复”，除了增加延迟和故障点几乎没有收益。

三者的差别不只是命名，而是耦合方向：命令把”要做什么”的知识放在发送方，事件把这份知识放在接收方。下图展示同一笔下单在三者中的流向差别。

图里有一点值得注意：库存服务返回给下单接口的是命令的受理结果，对外广播的才是事件。这个转换点是”请求”变成”事实”的地方，也是事务边界所在：库存扣减提交之后，StockReserved 才成立，在此之前它只是一个意图。

把命令伪装成事件是最常见的错误。判断方法很简单：如果消息名是过去式，但消费者收到后必须执行一个可能失败、失败后要有人负责的动作，那它其实是命令，应该有明确的接收方、超时和失败处理。反过来，发布事件后阻塞等待某个消费者的结果，则是把广播通道用成了点对点调用，既失去松耦合，又引入了消息系统本不该承担的时序假设。

事件建模：事实一旦发出就不能改

事件建模的第一步是决定”一条事件代表多大的事”。粒度太细，比如字段级的 OrderAmountChanged，消费者重建状态要订阅一大堆类型，顺序稍乱就出错；粒度太粗，比如把整个订单快照塞进事件，消费者被迫依赖发布方的内部结构。稳妥的做法是按业务事实划分：一次下单、一次支付成功、一次发货，每个事件描述一个对外有意义的状态跃迁。

一条事件至少应该携带这些信息：全局唯一的事件标识、事件类型与版本、业务发生时间与记录时间、产生它的聚合标识与聚合版本，以及业务载荷。聚合版本很关键，它让消费者能够判断是否漏掉了中间事件，也让幂等处理有据可依。

载荷里放什么，取决于消费者要做什么，而不是数据库里有什么。把整行数据序列化后丢进 topic，看起来省事，实际上把表结构变成了公开契约：加一个内部标记字段，所有消费者都会看到；改一个字段类型，所有消费者都要跟着改。更隐蔽的问题是语义泄漏，status = 3 这种只有发布方知道含义的编码，会让每个消费者都复制一份状态映射表，最终没人敢改。

不可变是事件的第二条铁律。事件一旦发布，就不能修改内容，也不能删除。发现金额算错了，正确做法是发布一条纠正事件，让状态按”错误发生—错误被纠正”的完整历史演进，而不是回头把原事件改成对的。这不只是审计偏好：消费者可能已经基于原事件做了投影、发了通知、扣了款，篡改历史会让这些副作用失去解释。删除同理，如果确实要清理，应该用保留策略在存储层做，而不是让业务语义上出现空洞。

第三点是区分事实与解释。事件应该描述发生了什么，而不是发布方认为这意味着什么。InventoryDeducted 是事实，InventoryShouldAlert 是判断；前者所有消费者都能用，后者只对特定消费者有意义，应该放在消费侧。把判断塞进事件，等于让发布方替所有消费者做决策，时间一长，事件里会堆满只有一两个消费者关心的字段。

最后是时间。事件里通常有两个时间：业务发生时刻和写入时刻，补录、批量导入、离线重算都会让两者相差很大。消费者做超时判断、窗口聚合时用哪个时间，必须写进契约。笔者的建议是，业务时刻服务业务语义，写入时刻服务运维排查，不要混成一个字段。

生产者与消费者的契约

事件一旦跨出进程边界，生产者和消费者之间就存在一份契约。很多团队把它等同于字段列表，这不够。完整的契约至少四层：结构，即字段名、类型与必填性；语义，比如金额是否含税、时间用哪个时区、PaymentCaptured 是否包含部分退款；时序，比如同一聚合的事件是否保证按版本递增到达；投递保证，比如是否可能重复、窗口多长。只约定结构，消费者就只能靠猜。

所有权也要明确。生产者拥有 schema，变更前评估影响；消费者承担”宽容读取”的义务，遇到不认识的字段就忽略，遇到缺失的可选字段就用默认行为。

结构描述通常有三种选择：JSON 上手快、可读性好，但约束弱；Avro 依赖 schema 注册中心，读写各用自己的 schema 解析，缺省值处理得比较自然；Protobuf 用字段编号标识，体积小、跨语言支持好。三者没有绝对优劣，关键是能在流水线里自动检查兼容性。

兼容性分三类：向后兼容指新消费者能读旧数据，向前兼容指旧消费者能读新数据，两者都满足称为全兼容。对事件流来说，最现实的目标是向前兼容，因为历史事件一直躺在 topic 或事件存储里，消费者升级总有先后。操作层面有几条规则值得写进团队规范：

  • 只新增可选字段，不新增必填字段，也不修改已有字段的类型
  • 字段编号或字段名一旦发布就不再复用，删除的字段要标记为保留
  • 枚举新增值时，消费者必须有未知值分支，不能直接按穷举处理
  • 不改变字段语义，包括单位、精度、时区和是否含税
  • 金额一律用最小货币单位的整数，避免浮点误差和精度变更

版本号放在哪里也有取舍。写进类型名（如 OrderPlacedV2）便于精确订阅，但类型会膨胀；放进载荷的 event_version 字段，类型稳定，代价是所有消费者都要读它；写进 topic 名则把保留策略、权限和消费组位点一起绑到版本上，迁移成本最高，除非需要强隔离，否则不推荐。

演进不能只靠约定。CI 里做 schema 兼容性检查是最低要求；再进一步是契约测试，生产者为每个事件维护样例消息，消费者在测试里回放，验证解析与业务分支，样例既是文档也是回归基线。上线新版本时建议双发过渡：新旧版本同时发布，新消费者先切换，观察一段时间确认没有消费方依赖旧版本后再停掉旧的。双发期间要监控两边的消费位点。

事务性发件箱与 CDC

事件驱动系统里最经典的一个坑，是业务数据和事件不在同一个事务里。典型写法是先提交订单，再调用消息客户端发送 OrderPlaced。如果进程在两步之间崩溃，订单落库了但事件没发出去，下游永远等不到；如果反过来先发消息再提交，消费者可能收到一个指向不存在订单的事件，读到空数据后把消息丢弃，同样丢事实。

事务性发件箱（Transactional Outbox）的思路很直接：把要发布的事件和业务数据写进同一个数据库事务。业务表更新和 outbox 表插入要么一起成功，要么一起回滚，事件的存在性由此与业务状态绑定。真正的发送交给一个独立的转发器（relay），它读取 outbox 中未发送的记录，投递到消息系统，成功后标记为已发送。

写入侧的关键是”同一个事务”，代码里不应该出现两次独立的数据库连接。

转发器有两条技术路线。第一条是轮询发布：定时查询未发送记录并逐条投递。它实现简单，不依赖数据库日志格式，缺点是存在固有延迟，高频轮询又会给数据库增加压力。第二条是读取事务日志，也就是常说的 CDC：用 Debezium 这类工具订阅数据库的预写日志或复制流，把行变更转成事件。它延迟低、对业务库侵入小，但引入了需要独立运维的组件，还要处理全量快照与增量流的衔接、表结构变更和位点管理。数据量不大时轮询足够，已经有 CDC 平台时复用它更划算。

选择 CDC 时有一个容易忽略的问题：CDC 捕获的是行变更，不是业务事件。orders 表的一次更新会变成字段级的变更记录，消费者拿到的是列的新旧值，需要自己还原出”订单已支付”这个含义。直接把行变更当事件对外发布，等于把表结构变成公开契约，前面几节的建模原则就全部失效了。稳妥的做法仍然是在业务层写 outbox，让 CDC 只负责搬运 outbox 表，事件的结构与语义由业务代码决定，CDC 只是一个更可靠的传输手段。

转发器还要解决并发与清理。多实例部署时，可以用 SELECT ... FOR UPDATE SKIP LOCKED 让每个实例领取不同的行，也可以按主键区间分片，避免重复投递同一批记录。投递成功与标记成功之间仍然可能崩溃，所以重复是设计的一部分，消费端必须幂等。outbox 表会持续增长，需要按时间分区并清理已发送记录，否则索引膨胀会拖慢写入。大字段也不要塞进 outbox，事件载荷保持精简。

投递语义：重复不可避免，幂等才是答案

讨论投递语义时先要把三个词说清楚：至多一次允许丢失，至少一次允许重复但不丢，精确一次要求端到端不重不漏。前两者消息系统能单独提供，第三者从来不是某个组件能单独承诺的，必须由生产、传输、消费三段共同保证。

以 Kafka 为例，幂等生产者用生产者标识和序列号让 broker 对重试写入去重，事务把一批写入与位点提交绑在一起。但边界止于 Kafka 自身以及同样支持事务的下游。绝大多数消费者的处理结果是写进业务数据库，这次写入与 Kafka 事务并不在一起，所以整体看仍是至少一次。真正让结果正确的，是消费端幂等，而不是配置里的某个开关。

幂等有三种常见实现。第一种是让操作天然幂等：把”余额加 10 元”改成”把余额设为 110 元”，把”状态置为已支付”改成带条件的更新，重复执行结果不变，这要求事件携带目标值或聚合版本。第二种是去重表：用事件标识做主键插入，插入成功才执行业务逻辑，插入与业务写入放在同一个事务里。第三种是状态机条件更新，只允许从特定状态跃迁，重复事件因为状态不再匹配而被忽略。

去重表要设过期策略，否则会无限增长；过期窗口必须大于消息系统的最大重投间隔，也要覆盖人工重放，否则半年后重建投影时重复处理仍会发生。重放前应确认消费逻辑对历史事件仍然幂等，或者换一个消费组名重新构建。

顺序是另一个容易被过度承诺的维度。全局有序意味着单分区单消费者，吞吐和可用性都要让步，绝大多数业务并不需要。真正需要的是按聚合有序：同一张订单的创建、支付、发货必须按顺序处理，不同订单之间无所谓。做法是用聚合标识作为分区键，消费者按分区串行处理；分区数变更会改变键到分区的映射，所以顺序保证应尽量落在聚合版本号上。

失败处理要区分错误类型。超时、连接中断、下游限流可以退避重试；数据格式错误、业务前置条件不满足则重试无益，只会堵住整个分区。后者应该投递到死信队列，记录原因和原始消息，由人工或专门的修复流程处理。死信队列不是垃圾桶，要有告警、有负责人、有重放工具。

编排与协同：流程的知识放在哪里

当一笔业务需要多个服务协作时，有两种组织方式。编排（Orchestration）设一个协调者，它知道完整流程，按顺序调用各参与方，记录每一步状态，失败时决定重试还是补偿。协同（Choreography）没有中心，每个服务订阅自己关心的事件，处理完再发布新事件，流程隐式分布在各个服务里。

差别不在技术，而在”流程知识”放在哪里。编排把流程集中在一个状态机里，读代码就能看到全貌，加一步、改超时、插入人工审核都比较直接；代价是协调者与所有参与方耦合，容易长成什么都管的服务。协同把知识分散到消费者，新增参与方只需订阅，发布方不用改；代价是端到端没有单一视图，出问题要在多个服务的日志之间拼图，隐含依赖也容易形成环。

选择可以看三点：流程是否需要强审计，比如涉及资金与合规审批，要随时回答”卡在哪一步”；参与方是否分属多个团队、发布节奏不一致；是否有明确的超时与补偿要求。多数系统是混合的：跨团队的宏观流程用编排，团队内部的派生动作（发通知、算积分、更新报表）用协同。

两个反模式要避免。第一个是把事件当 RPC：发布者发完事件后死等某个消费者的回复，或者消费者处理完再发一条”回复事件”给指定方，通道承担了请求—响应的语义，却没有 RPC 的超时和错误码。第二个是无限延伸的事件链：一个事件触发三个服务，每个服务又各发两个事件，深度到了五六层。控制手段是给链路设预算，超过一定深度就改为显式编排，并在事件目录里标注每个事件的直接下游。

补偿事务的具体设计属于另一条独立的技术线，本文不展开。这里只强调一点：编排者记录的状态必须足够支撑恢复，包括每一步的输入、输出和时间，否则协调者重启之后就无从判断该重试还是该补偿。

事件溯源：只在算得清账的地方用

事件溯源（Event Sourcing）常被和事件驱动混为一谈，其实两者解决的问题不同。事件驱动说的是服务之间如何通信，事件溯源说的是聚合状态如何存储：不保存当前状态，只保存导致状态变化的事件序列，需要时按顺序重放得到当前状态。一个系统可以大量使用消息队列却完全不涉及事件溯源。

它真正划算的场景有几个共同点。第一是审计要求强，业务需要回答”这个状态是怎么一步步变成现在这样的”，而不只是”现在是什么”。第二是状态机复杂，状态之间的合法迁移本身就是领域知识，用事件表达比用一堆布尔字段和状态码清楚得多。第三是需要回溯重算，比如定价规则变了，要按新规则重放历史事件，看看结果差异。第四是同一份事实要被多种读模型使用，事件流天然是投影的输入。

不适合的场景同样明确。以增删改查为主、状态变化没有业务含义的系统，引入事件溯源只会增加一层间接。查询复杂、报表繁多的系统，读模型的重建成本会很高。团队没有相应的运维能力时，事件存储的容量规划、快照策略、重放演练都会成为负担。还有一类常被忽略的成本：schema 升级之后，旧事件仍然要能被重放，这意味着每一个历史版本的解析逻辑都要长期保留，测试矩阵会随版本数量增长。

如果决定使用，建议把范围限制在少数核心聚合，其余部分仍用状态存储加发件箱发布事件。快照是常规优化手段，按固定事件数或固定时间间隔生成，重放时从最近快照开始，但快照只是缓存，删掉之后系统仍应能重建。删除与隐私要求也要提前设计，常见做法是把敏感字段加密后写入事件，需要删除时丢弃密钥，而不是真的去改历史事件。

可观测性：把一次业务事实追到底

事件驱动系统的故障往往不是”报错”，而是”慢了””少了””重复了”，传统的接口监控很难覆盖。可观测性要围绕事件的完整生命周期来建：谁产生的、经过哪个 topic、被哪个消费组处理、最终写进了哪张表。

追踪上下文要随消息传递。生产者在发送时把 traceparent 写进消息头，消费者取出后继续同一个 trace，这样一次下单引发的所有异步处理能串在一条链路上。异步场景有一个细节：消费者一次批量拉取多条消息时，不应该把它们都当成同一个父 span 的子节点，而应该为每条消息创建带链接（link）的 span，指向各自的生产者上下文。

指标方面，除了通用的请求量、错误率、耗时，还要盯住几个事件特有的量：消费延迟，也就是最新生产位点与已提交位点之间的差值；单条消息的处理耗时分布；重试次数与死信数量；发件箱中未发送记录的年龄；以及端到端延迟，从事件的业务发生时刻算到读模型可见时刻。最后这个指标最接近用户感受，也最容易在链路变长时悄悄恶化。

日志要结构化，至少带上事件标识、聚合标识、topic、分区和位点。排查路径通常是：从业务单据找到聚合标识，再找到事件，按位点定位消费组，最后看那段时间的延迟和错误；缺一个关联字段，这条路径就断了。指标与日志之外还应有一层对账：按日比对生产侧事件计数与消费侧处理计数，差异超阈值就告警。它不能替代实时监控，却是发现”静默丢失”的最后一道网。

演进与治理：让变更可预期

事件一旦被多个团队消费，它就成了一种公共设施，治理的目标不是审批，而是让变更的影响可预期。最小的一套治理包含四件事：一份事件目录，记录每个事件的类型、结构、语义、所有者、下游消费者、保留期和投递保证；一条变更流程，规定谁可以改、改之前要通知谁、什么情况算不兼容；一个弃用机制，旧版本先标记、再双发、再通知、最后在约定日期下线；以及一套自动化检查，把 schema 兼容性和契约测试放进流水线。

目录的价值在故障和规划时体现得最明显。线上出现重复扣款，能立刻查到有哪些消费者订阅了支付事件；准备改一个字段，能列出所有受影响的下游和它们的负责人。没有目录，这些信息只存在于个别人的记忆里。目录不需要一开始就很完备，可以从核心的十几个事件开始，随着消费者增加逐步补齐。

工程细节也属于治理：topic 按领域而不是按服务命名；分区数预留增长空间，因为减少分区几乎不可能；保留策略与重放需求匹配；生产与消费权限按主体授予，避免任意服务都能向核心 topic 写入；涉及个人信息的事件要评估脱敏或字段级加密，事件往往长期保存，比在线数据库更敏感。

最后是度量和复盘。可以跟踪几个简单指标：事件类型与消费者数量的增长、每个事件的 schema 版本数、从发现不兼容到修复的时长、死信队列的积压趋势。这些数字比”我们上了事件驱动”更能说明架构成熟度。演进的方向也不是事件越多越好，而是每条事件都有明确的所有者、明确的语义和明确的下游。

小结

事件驱动架构的核心不在消息中间件，而在几个建模与一致性决策。先把命令、事件、查询分开，让”请求”和”事实”各自走合适的通道；把事件当作不可变的事实来建模，粒度按业务跃迁划分；用显式的契约和兼容性检查管理 schema 演进；用事务性发件箱或 CDC 消除双写，用幂等消费应对必然出现的重复。流程组织上，编排换来确定性，协同换来扩展性，按团队边界和审计要求取舍。事件溯源只适合审计强、状态机复杂、需要回溯的核心聚合，不要因为用了消息队列就顺手引入。最后，把追踪上下文、消费延迟、端到端延迟和对账补齐，事件流才是可运维的。
