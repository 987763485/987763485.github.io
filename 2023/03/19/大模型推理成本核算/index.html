大模型推理成本核算

推理成本是多数大模型应用真正的主要开销，却常常被一句“按 token 计费”轻轻带过。本文把一次推理拆成算力、显存、网络、存储与运维几笔账，讨论输入输出不对称、上下文长度、批处理、量化、缓存与 GPU 利用率如何改变单位成本，再给出按请求、按千 token、按活跃用户三种核算口径，以及容量规划、预算告警与成本归因的落地方法。文中数字全部是示意值，只用于演示计算过程，不代表任何厂商的真实报价。

为什么推理成本需要单独核算

很多团队立项时只算了一笔训练账：租一批卡、跑几周、得到一个模型，就认为成本已经结束。上线之后才发现，账单的大头在推理侧，请求量翻一倍，账单就跟着翻一倍。把推理成本单独拿出来核算，不是为了做一张好看的报表，而是因为它是随业务增长近似线性变化的成本项，也最容易被产品决策无声放大。

训练账与推理账的性质不同

训练是资本支出：采购一次、摊销较长周期，任务可以排队、可以抢占、失败可以重跑。推理是运营支出：按天按小时结算，请求有明确的延迟预期，用户等上三秒就开始怀疑服务不可用。优化目标也不同：训练追求单位算力下的收敛速度，推理追求单位成本下的有效吞吐；训练多花一周通常可以接受，推理多花三百毫秒可能直接掉转化率。麻烦的是推理的成本曲线是连续的，没有阶跃点提醒你去看一眼。

一次推理到底花在哪四层

第一层是 GPU 计算时间，也就是卡时。第二层是显存占用，它不直接出现在账单上，却决定同样的卡能装下多少并发；显存被 KV Cache 占满时，算力再有富余也接不了新请求。第三层是结算口径上的 token 费用，对外是接口账单，对内是业务线之间的转移计价。第四层是网络、存储与运维：传输、日志与对话历史的留存、监控值班、冗余容量与故障切换。后两层在小规模时几乎看不见，规模上来后往往占到总成本的两三成。

显存与上下文：成本的物理底盘

推理成本不能简单按调用次数计，根源在显存：它决定单卡能同时服务多少请求，也决定 GPU 计算时间能摊薄到什么程度。

权重、KV Cache 与激活值

一张卡上的显存大致分三块。第一块是模型权重，约等于参数量乘以每个参数的字节数：16 位浮点下每个参数 2 字节，70 亿参数约 14 GB，130 亿参数约 26 GB。第二块是 KV Cache，即生成过程中缓存的键值对，随上下文长度与并发数线性增长，是长对话场景的主要消耗者。第三块是激活值与临时缓冲区，规模相对固定，但长上下文与大批处理时会明显抬升。

KV Cache 的大小可以直接算出来。以 32 层、32 个注意力头、头维 128、16 位精度为例，每个 token 的缓存量为 2 乘以层数乘以头数乘以头维再乘以 2 字节，约 0.5 MB；2048 个 token 的上下文就是 1 GB，16 路并发就是 16 GB。加上 14 GB 权重，一张 80 GB 的卡还剩下大约 50 GB 给激活值、碎片和预留。

上下文从 2048 拉到 8192，同样并发下 KV Cache 涨到四倍，单卡装不下，只能降并发或者加卡。长上下文真正的成本来源不是多一点计算，而是少很多并发。

上下文长度如何同时推高显存与延迟

上下文变长在三个地方同时加价。显存上，KV Cache 线性增长，直接压缩可用并发。计算上，预填充的注意力计算量与长度的平方成正比，长度翻倍算力大约翻四倍。延迟上，首 token 时间随预填充变长而上升，往往要靠流式输出与进度提示缓解。

要区分两个阶段：预填充把整段输入一次算完，是标准矩阵乘，GPU 利用率高；解码逐 token 生成，每步只处理一个位置，算术强度低，瓶颈从算力转移到显存带宽。预填充怕长输入，解码怕长输出，这个区分是后面讨论输入输出不对称的基础。

长上下文的成本该怎么摊

长上下文这么贵，是不是应该一律截断？不一定。判断标准是这段上下文是否改变了答案：检索到的十段文档全塞进去，可能只有两段被引用，剩下八段纯粹在买显存和首 token 延迟。可行的做法有三条：按任务设定上下文预算，超预算先做摘要或重排；对长文档场景单独定价；把可复用的长前缀固定下来做缓存。

输入与输出 token 的不对称

按量计费的接口几乎都对输出收更高单价，很多人以为这只是定价策略，实际上它反映的是物理事实：输入可以并行，输出只能串行。

解码为什么慢

生成阶段每产出一个 token，都要把整个模型的权重读一遍。以 70 亿参数、16 位精度为例，权重约 14 GB；显存带宽按每秒 2 TB 计（示意值），读一遍权重的理论下限约 7 毫秒。也就是说，单请求单步解码在算力上远没跑满，时间几乎全花在搬数据上，生成 100 个 token 的理论下限就是 0.7 秒。

这就是访存受限，两个推论随之而来：增大批大小几乎不增加权重读取量，所以把多个请求拼成一批是性价比最高的优化；量化把要搬的字节数直接减半甚至减到四分之一，对解码特别有效。

预填充为什么便宜

预填充把 n 个 token 一起送进矩阵乘，一次读权重、算 n 个位置，算术强度随 n 增长。同样 70 亿参数，处理 2048 个输入 token 的计算量约为 2 乘以参数量乘以 token 数，即 29 TFLOP（示意估算），按有效算力 300 TFLOPS 计约 0.1 秒，折算到每个输入 token 比逐个解码低一个量级。

所以输入便宜、输出贵是架构决定的：相同长度下，输出的单位计算成本可以是输入的数十倍，具体倍数取决于批大小、量化方式与硬件。

输入输出比决定了成本结构

设输入 token 数为 A、输出为 B，比值 R 等于 A 除以 B。R 很小的开放问答，成本主要由输出驱动；R 很大的文档摘要、检索增强问答与代码审查，成本主要由输入驱动。两类优化的手段完全不同：前者压输出长度、做流式截断、考虑蒸馏；后者压上下文、做检索重排与前缀缓存。

批处理与并发：单位成本的分母

单位成本等于总成本除以有效产出，推理场景里这个分母几乎完全由批处理与并发决定，也是同一张卡在不同团队手里成本相差数倍的原因。

批处理摊薄了什么

单请求解码时 GPU 每步只算一个 token，算力单元大量闲置。把 8 个请求拼成一批，权重仍然只读一遍，计算量增加有限，吞吐却接近 8 倍。批处理摊薄的是权重读取这一次固定开销，而不是计算本身。

但收益递减：批大小从 1 到 8 吞吐提升明显，从 32 到 64 边际收益变小，显存占用与单请求延迟却继续上升。原因是显存带宽终会被占满，KV Cache 也随批大小线性增长，迟早撞上容量天花板。批大小不是越大越好，它有一个由显存和带宽共同决定的上限。

从静态批到迭代级调度

最早的实现是静态批处理：攒够一批请求一起开始，等最长的那个生成完再整批返回，短请求要陪长请求等到最后，GPU 在尾部空转。2022 年 OSDI 上有论文提出迭代级调度，每生成一步就重新组批，完成的立刻退出、排队的立刻补位，把空转压到很小。到 2023 年初，这类调度还主要停留在论文与自建实现里，显存分块管理、请求抢占与公平性都要自己解决。

并发、延迟与吞吐的三角

三者不可能同时最优：并发上去排队变长、尾延迟变差，为了压尾延迟留冗余，利用率又下来。排队论里有个基本关系，系统中平均并发数等于到达率乘以平均停留时间，它提醒我们并发不是越多越好，而要与到达率和可接受的停留时间匹配。若单请求平均耗时 2 秒、峰值到达率每秒 20 个请求，正在处理的请求就有 40 个，这还没算排队的安全余量。

实践做法是画出吞吐与延迟的曲线，取拐点作为工作点：拐点前加并发几乎线性提升吞吐，拐点后吞吐趋平而延迟陡增。拐点通常在 GPU 利用率七成到八成之间，具体位置要实测，不能照搬。

GPU 利用率与排队：被忽视的隐性成本

三种利用率口径

监控面板上的 GPU 利用率至少有三种含义。第一种是时间利用率，即这段时间卡上是否有任务在跑，只要队列里总有请求它就接近百分之百，最容易被做高。第二种是 SM 利用率，反映计算单元的实际忙碌程度，解码阶段通常很低。第三种是显存带宽利用率，解码阶段往往很高。三者放在一起看才有意义：SM 低、带宽高是访存受限，该做批处理与量化；SM 高、带宽低是计算受限，该看序列长度与模型结构。

还有第四个数，显存容量占用率：它不进利用率报表，却经常是真正的瓶颈，占用过高后碎片化会让稍大的请求分配失败。

排队与尾延迟

成本核算必须区分平均与尾部。平均延迟好看、P99 难看是推理服务的常态，请求长度分布的长尾很重，少数超长请求就能把尾部拖长。为尾延迟买保险的代价是常驻冗余：峰值并发需要 40 路，按 1.3 倍预留就多备三成卡，这部分要摊进单位成本，不能当作没用到就不花钱。冗余卡在故障切换时是救命的，在平时是沉没的，两笔账要分开记。

碎片与切分

一张大卡跑小模型，利用率可能只有一成。A100 支持把一张卡切成若干隔离实例，分别服务不同模型或租户；切分能提升装箱率，代价是实例之间不能共享批处理，是否划算要实测。

把利用率折进单价

有效单价等于名义单价除以有效利用率。名义上每卡时 12 元（示意），若有效利用率只有三成，摊到有效计算上的成本就是 40 元。这个换算能把很多争论一次说清：与其争论卡贵不贵，不如先看利用率是多少、瓶颈在哪里。

量化与蒸馏：用精度换成本

量化省的是带宽和显存

量化把权重从 16 位压到 8 位或 4 位，显存占用按比例下降，更重要的是解码时每次要搬的字节数同比下降，而解码本来就是访存受限，所以吞吐提升往往接近压缩比。2022 年公开的两条路线值得了解：一条是训练后量化，用校准数据逐层最小化量化误差，可以把大模型压到 4 位而尽量保住效果；另一条是混合精度分解，把少量异常值用高精度计算，其余走 8 位矩阵乘。两者都不需要重新训练整个模型。

代价也明确：量化误差在长尾任务上更容易暴露，数学推理、代码生成、多语言的退化幅度并不一致，4 位量化还对校准集敏感，换领域就要重新验证。因此量化不能只看吞吐，必须配一套固定评测集，量化前后各跑一遍，确认关键指标没跌破阈值再上线。

蒸馏换的是模型规模

蒸馏用大的教师模型生成数据或软标签，训练一个小的学生模型。成本结构很特别：教师推理、数据生成、学生训练与评测都是前期一次性投入，换来此后每一笔推理更便宜。任务边界清晰、输出格式稳定的场景，蒸馏性价比高于量化；开放式生成则很难追上教师。

盈亏平衡怎么算

是否值得做量化或蒸馏，可以用一个简单的不等式判断：一次性改造成本除以单请求节省额，就是需要多少请求才回本。假设改造与验证投入折合 20 万元（示意），单请求成本从 0.02 元降到 0.012 元（示意），就要 2500 万次请求回本。日均 20 万次约四个月回本，日均只有 2 万次则要两年多，不如先做批处理和缓存。

这个算式还有个隐含前提：节省必须真的落到账单上。量化后显存省了、并发上去了，但流量没变、卡也没退，节省的就只是理论容量，账面成本一分没少。核算时要盯住退卡数与账单降幅这两个硬指标，而不是压测时的吞吐数字。

缓存：把重复计算变成存储

结果缓存最简单也最容易出错

把相同输入直接短路、返回历史结果，是成本最低的优化。命中率来自两类重复：系统提示与模板高度一致的请求，以及内部批处理任务的重跑。实现上要解决三件事：键怎么构造，模型版本、温度、完整提示都要进键；数据怎么隔离，多租户下不能串号；有效期怎么定，知识更新后旧答案会变成错误答案。温度大于零时同样的输入不保证同样的输出，缓存会改变产品行为，必须在产品层面确认。

前缀缓存省的是预填充

很多请求共享一段很长的前缀：系统提示、工具定义、固定示例、同一份长文档。每次都为这段前缀重跑预填充，等于反复为同样的计算付费。前缀缓存的做法是把它的 KV Cache 算一次、存下来，后续请求直接复用，只对新增部分做预填充。

收益与共享前缀的长度成正比。假设前缀 3000 token、新增 200 token，复用后预填充计算量降到约十六分之一（示意估算），首 token 延迟同步下降。到 2023 年初，这还不是推理框架的开箱能力，前缀识别、缓存键管理与显存回收都要自己在服务层做，是否值得取决于前缀长度与额外的显存开销。

语义缓存要更谨慎

按向量相似度匹配历史问题，命中率比精确匹配高得多，但误命中会直接给出错误答案，还很难被监控发现。可行的边界是只用于低风险、可人工纠正的场景，设较高的相似度阈值，命中后标注来源并保留抽检；涉及账户、金额、权限的请求一律不走。

缓存的经济性判断

缓存不是免费的：它占用显存或存储，需要失效策略，也增加链路复杂度。判断标准仍是那个不等式，命中率乘以单次成本要明显大于存储与维护成本。经验上命中率低于一成时不值得自建，超过三成收益可观。还要防止把超时重试也算成命中，那会让看板很好看、账单很难看。

三种核算口径：按请求、按千 token、按活跃用户

同一套系统用不同口径算出来的成本可以差出几倍，差异不是算错了，而是口径服务的目的不同，混用就会得出互相矛盾的结论。

按请求：适合容量与稳定性

单请求成本等于总成本除以成功请求数。它最贴近运维视角，适合做容量规划、限流阈值和 SLA 定价。缺点是对请求长度完全不敏感，200 token 的问答和 8000 token 的文档分析被算成同一个数。修正办法是按长度分桶统计，再按实际流量加权。

按千 token：适合结算与横向比较

每千 token 成本等于总成本除以处理的 token 总量，输入与输出分别计算。它最贴近计费视角，适合对外报价、对内转移计价与模型间横向比较。缺点是忽略了每个请求的固定开销，请求越短摊得越薄，短请求的每千 token 成本会显著偏高。

按活跃用户：适合订阅与预算

每活跃用户成本等于总成本除以周期内的活跃用户数。它最贴近业务视角，适合订阅制定价、部门预算和增长决策。缺点是高度依赖使用强度，重度用户可能消耗十倍于轻度用户，平均值会掩盖结构性亏损。通常还要配一个辅助指标，即每活跃用户的日均请求数与 token 数，用来解释单位成本的变化来自价格、模型还是用户行为。

口径 分母 适合回答的问题 主要失真点
按请求 成功请求数 要几台机器、限流设多少 长短请求混算
按千 token token 总量 该收多少钱、哪个模型更省 忽略每请求固定开销
按活跃用户 活跃用户数 订阅价定多少、是否亏损 使用强度差异

口径换算与对账

三个口径可以互相换算，前提是拿到平均每请求 token 数与每活跃用户的日均请求数。换算公式本身不难，难的是让三张报表对得上。差异通常来自四处：重试与失败请求是否计入、缓存命中是否计入、截断与超长请求如何归类、固定成本如何分摊。这四条规则必须写进文档，否则每个季度都会为两个数为什么不一样吵一次。

容量规划与预算告警

从业务指标推导卡数

容量规划的顺序是从业务到硬件，而不是反过来。活跃用户数乘以人均日请求数得到日请求量；再乘以峰值系数（示意取 4）折算成每秒请求数；乘以单请求平均耗时得到需要同时处理的请求数；最后按显存与算力两个约束分别估算卡数，取较大者，再乘冗余系数。

算出来的卡数只是起点，接下来要问三个问题：显存够不够装下峰值并发对应的 KV Cache，长请求占比上升时单卡容量会掉多少，故障切换时剩下的卡能不能扛住。任何一个过不了就得加卡，代价要回到单位成本里。

预算告警要分层

只设一条月度总预算几乎没有用，它总在月底才响。有效的告警至少分四层：日预算绝对值，用来抓突发；单位成本漂移，每千 token 成本周环比涨超过一成，说明结构变了而不是量变了；租户或业务线占比突增，用来抓异常调用与爬取；模型占比变化，大模型调用占比一旦抬头，账单会先于请求量变化。每条告警都要带归因维度，否则最后会被所有人静音。

预留成本开关

降级手段要预先做好并演练过，包括切换到小模型、压缩上下文、关闭非必要的缓存写入、对低优先级流量限流排队。它的价值在于把成本失控变成体验降级，前者是事故，后者是策略。

成本归因到业务线

标签在网关统一打

成本归因的前提是每次调用都带得走标签，至少五个维度：租户、功能、模型与版本、调用入口、是否命中缓存。标签必须在网关统一注入，不能让各服务自己拼，否则同一个业务会有三种写法，最后无法聚合。提示模板的版本也值得记，它经常是成本突变的真正原因。

分摊规则要稳定可复算

直接成本直接归属，比如某个业务独占的微调模型与向量库。共享成本包括常驻副本、闲置容量、平台人力与监控，按 token 量或请求量加权分摊。规则一旦定下就不要频繁改，宁可粗糙也要稳定，因为业务方要用环比看自己的优化是否有效；每次调整都要给出新旧口径对照，避免数字跳变引发争论。

成本项 归因方式 示意权重
独占模型推理 直接归属 100%
共享推理集群 按 token 量分摊 按实际
闲置与冗余容量 按预算份额分摊 按实际
平台人力与工具 按活跃业务线均摊 均分

治理闭环

归因的目的不是分账，而是让每个业务线看到并对自己的单位成本负责。可行的节奏是月度复盘三个问题：涨了多少、为什么涨、下个月做什么，再把优化项写成有 owner、有预期收益的条目，下个月回看兑现率。没有这一步，成本看板很快变成没人看的墙纸。

小结

推理成本的核算起点是显存，落点是单位成本。输入与输出不对称、上下文长度、批处理与并发、量化与蒸馏、缓存、利用率与排队，六个杠杆最终都作用在同一个分母上，即单位时间内真正完成的 token 数。口径要按用途选：按请求看容量，按千 token 看结算，按活跃用户看订阅。容量规划从业务指标倒推，预算告警分层设置，成本归因打通到业务线，三者合起来才构成闭环。文中数字都是示意值，落地时请用自己的账单与日志重算一遍。
