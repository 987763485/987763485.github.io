TypeScript 5 装饰器迁移

本文属于《TypeScript 学习路线》第 52/74 篇
上一篇系列目录下一篇

TypeScript 5.0 于 2023 年 3 月 16 日发布，这是第一个把 TC39 标准装饰器作为默认语义的稳定版本。对多数项目而言，升级编译器本身并不难，难的是接受“同一个 @ 符号背后换了一套规则”：参数从三个变成两个，字段装饰器从打标记变成返回初始化函数，元数据不再自动发射。本文按“差异、影响、迁移”三层展开，先逐条对比新旧语义，再讨论依赖注入与 ORM 框架为什么暂时不能跟着走，最后给出一份可以分阶段执行的迁移清单。读者应当已经用过 experimentalDecorators，或者正在维护一个被装饰器深度绑定的代码库。

一、两套装饰器为什么能并存

1.1 一段持续八年的先行实现

装饰器并不是 TypeScript 发明的语法。2015 年前后，TC39 有一个关于类成员注解的提案，TypeScript 1.5 按当时的草案把它实现了出来，并放在 experimentalDecorators 开关后面。这套实现后来被 Angular、NestJS、TypeORM 等框架大量采用，逐渐成为事实标准：方法装饰器拿到原型、属性名与属性描述符，类装饰器拿到构造函数，参数装饰器再拿到参数下标，配合 emitDecoratorMetadata 与 reflect-metadata，框架可以在运行时推断出构造参数的类型。

问题在于，提案本身在这八年里被反复重写。早期版本允许装饰器返回描述符，也允许顺手修改成员的属性特性；后来的设计把模型收敛成“用返回值替换被装饰的元素”，并引入一个统一的 context 对象承载元信息，参数装饰器则被整体去掉。到 2022 年 3 月，这套新设计进入 TC39 的 stage 3。TypeScript 5.0 在 2023 年 3 月 16 日发布，成为第一个默认启用它的稳定版本。

所以今天的局面不是新版取代旧版，而是两套语义长期共存：旧版因为生态依赖太重不能删除，新版因为标准化必须默认开启。

1.2 一个编译开关决定整套规则

选择哪套语义，不由单个文件决定，也不由单个包决定，而由所在 tsconfig 的 experimentalDecorators 决定。它为 true 时按旧语义降级并检查旧签名；缺省或为 false 时按标准语义处理。两种模式之间没有混用通道，同一个编译单元里，不能一部分装饰器走旧规则、另一部分走新规则。

这一点对迁移的影响很大。单仓多包的项目可以用项目引用，让每个包拥有自己的 tsconfig，于是“新包用新语义、老包不动”在工程上是可行的；但如果整个应用只有一个 tsconfig，就只能整体切换，而这通常意味着要等框架先完成改造。

还有一个容易误判的地方：@ 语法在两种模式下都能写，报错发生在类型检查阶段，提示往往是“装饰器签名无法解析”这类信息。它看起来像类型库出了问题，实际是装饰器函数的形状与新语义对不上。

1.3 5.0 里标准装饰器的边界

需要明确的是，TypeScript 5.0 提供的是装饰器语法与对应的降级转换，并不包含装饰器元数据。当时与元数据相关的 Symbol.metadata 仍是另一个独立提案，没有进入 TypeScript 的实现范围。这意味着任何依赖“在运行时读取装饰器写入的信息”的设计，都得自己维护注册表，而不能指望语言层面提供统一的元数据容器。

同样需要说清的是，5.0 并没有删除旧装饰器。experimentalDecorators 依然可用，官方也没有给出移除时间表。这既是生态的现实，也是迁移可以采用渐进策略的前提。

二、标准装饰器的调用形状

2.1 两个参数：value 与 context

旧版装饰器的参数是位置化的：类装饰器收到构造函数，方法装饰器收到原型、属性名、描述符，参数装饰器再追加一个下标。装饰器想判断“我装饰的到底是什么”，只能靠参数个数和类型去猜，写法上满是防御性判断。

标准装饰器把这一切压成两个参数。第一个是 value，即被装饰的元素本身：类是类本身，方法是方法函数，getter 是 getter 函数，字段则是 undefined。第二个是 context，一个描述该元素的普通对象，带有 kind、name 与 addInitializer；如果装饰的是成员，还会额外带上 static、private 与 access。

从这个形状可以看出标准装饰器的核心约定：它不修改传入的东西，而是返回替代品。返回 undefined 表示不改变，返回一个函数表示用它替换。这条约定贯穿所有成员类型，也是后面所有差异的源头。

2.2 context 的六个字段

kind 是六选一的字符串：class、method、getter、setter、field、accessor。它替代了旧版里“看第二个参数是不是字符串、第三个参数有没有 get”的一堆判断，装饰器可以先按 kind 分支，再决定后续逻辑。

name 是被装饰成员的名称，类型为字符串或 symbol。装饰匿名类或默认导出的类时它可能是 undefined，日志里要处理这种情况。

static 与 private 分别表示成员是否为静态、是否为私有。旧版装饰器根本没有私有成员的概念：以 # 开头的成员不会以字符串形式出现在属性名里，装饰器拿到的 key 与运行时真正的私有名对不上，于是大量库干脆不支持私有字段。

access 正是为了解决这个问题。它是一个带有 get、set、has 的对象，其中的函数已经绑定好接收者，装饰器不需要知道成员叫什么，也不需要拼出 # 前缀，就能在实例上读取或写入该成员。对于想在装饰器里做校验、缓存、懒加载的库来说，这是旧版完全不具备的能力。

addInitializer 是最后一个，也是最容易被低估的一个。它接收一个回调，把“稍后要做的事”登记到当前元素的初始化流程里。旧版装饰器想在类定义完成后做点事情，通常只能在装饰器函数体里直接改原型；新版要求把这类副作用推迟到明确的时机，顺序因此变得可预期。

关于时机，可以这样记：类装饰器登记的回调在类完全定义之后执行，此时静态字段与静态块都已求值；方法、getter、setter 装饰器登记的回调在类定义阶段执行一次，早于任何实例创建；字段与 accessor 装饰器登记的回调跟着实例走，在每个实例构造、对应成员初始化之后执行。这套顺序在规范里有明确规定，但不同工具链的实现细节值得用一个小例子打印时间线来确认。

运行后会看到静态字段的回调先于实例字段的回调，而且实例字段的回调每次构造都会触发一次。把 label 换成更细的标记，就能画出自己项目里的真实顺序，再拿它和框架内部的假设逐一对照。

2.3 装饰器表达式的求值顺序

两套语义在求值顺序上是一致的：同一个目标上的多个装饰器，表达式从上到下求值，应用从下到上执行。这个细节在迁移时容易被忽略，因为“装饰器工厂先执行、装饰器函数后执行”这条规则没变，变的是它们之间传递的数据。

真正变化的是组合方式。旧版里多个方法装饰器共享同一个描述符，后执行的装饰器看得到前一个改过的东西，也可以各自往这同一个对象上写；新版里装饰器依次接收前一个的返回值，包装变成函数层面的链式替换，不再有共享的可变中间对象。理解这一点，才能解释为什么“改描述符”的写法在新语义里无处落脚。

三、五类成员上的行为差异

把两套语义放在一起看，差异并不是均匀分布的：类装饰器只是换了参数形状，方法与访问器丢了修改描述符的权力，字段装饰器则彻底换了模型，参数装饰器干脆消失。下面按成员类型逐个拆开。

3.1 类装饰器

旧版类装饰器接收构造函数，可以返回一个新类替换它，也可以直接往原型上挂方法。新版行为一致，拿到类本身与 context，返回新类即替换。区别在于 context 里没有 static、private、access 三个字段，类本身不存在“是不是静态”的问题；name 在匿名类或默认导出场景下可能是 undefined。

真正需要注意的是类型层面的静默兼容。一个只声明了一个参数的旧装饰器，在新语义下依然能通过类型检查，因为它只是忽略了第二个参数；只要它不依赖描述符，运行结果往往也正确。这会造成“迁移已经成功”的错觉。反过来，任何把第二个参数当作属性名来用的代码，运行时拿到的都是一个对象，然后在意想不到的地方抛错。

3.2 方法与访问器

旧版方法装饰器拿到 PropertyDescriptor，这既是它强大之处，也是混乱之源：它可以把 value 换掉，也可以顺手把 writable 改成 false、把 enumerable 改成 false，甚至删掉整个属性重新定义。

新版只给函数本身，返回值替换函数，属性特性不再可改。可枚举性、可写性由类定义时的语法决定，装饰器无权干预。依赖“把方法变成不可枚举”的库在迁移时会直接失效，只能在类定义完成后用 Object.defineProperty 重定义一遍，例如放进类装饰器或静态块，代价是失去类型层面的保障。

访问器的差异更明显。旧版 getter 与 setter 共享同一个描述符，装饰器要靠 descriptor.get 是否存在来判断当前装饰的是哪一个，写在同一个访问器上的两个装饰器还会互相覆盖。新版的 kind 直接告诉你是 getter 还是 setter，两者各自独立替换，语义清楚得多。

3.3 字段与 accessor：变化最大的一类

字段是两套语义分歧最大的地方。旧版字段装饰器在类定义时被调用，第一个参数是原型，第二个是属性名，没有第三个参数，返回值被忽略。它能做的事只有打标记：往原型上挂点东西，或者用 reflect-metadata 记一条类型信息，等框架在实例化时来读。字段本身的值，装饰器是碰不到的。

新版字段装饰器的 value 是 undefined，但允许返回一个初始化函数。这个函数在每次实例构造、该字段完成初始化之后被调用，入参是当前的初始值，返回值成为最终值。也就是说，装饰器第一次可以真正参与“值”的决定，而不只是旁观。

这里有个必须记住的细节：初始化函数一定要把入参原样返回，或者在它基础上加工，忘记 return 会把字段覆盖成 undefined。这种写法在类型上完全合法，只能靠测试发现。

accessor 关键字是随标准装饰器一起可用的新语法。它声明一个自动访问器：编译器生成一份私有存储与一对 getter、setter，装饰器拿到的是包含 get 与 set 的对象，可以返回包含 get、set、init 的对象，同时接管读写与初始值。旧版没有对应物，只能用 getter、setter 手写再加字段装饰器来模拟，代码量差一个数量级。

私有字段同样是这次的收益点。标准装饰器可以装饰 # 开头的成员，并通过 context.access 安全访问；旧版遇到私有字段时，属性名与运行时名字对不上，装饰器基本无能为力。

3.4 参数装饰器没有了

旧版支持参数装饰器，它接收原型、方法名与参数下标，典型用途是给构造参数打标记。NestJS 的构造函数注入、@Inject 指定 token、@Body 与 @Param 取请求数据，全都建立在它之上。

标准提案没有保留参数装饰器。原因不难理解：装饰器的模型是用返回值替换被装饰的元素，而一个参数无法被替换成别的东西，硬塞进来会破坏整套规则。于是所有依赖参数位置的声明式写法，在新语义下都无法表达，只能上移到类或方法上，或者改成显式的运行时调用。

这是应用侧暂时不能迁移的最直接原因，比元数据缺失更硬。元数据没了还能靠显式 token 补，参数位置没了，框架的整套声明式 API 都要重新设计。

四、emitDecoratorMetadata 的退场

4.1 元数据从哪里来

旧版装饰器之所以能让依赖注入看起来“不需要配置”，靠的是编译器的额外输出。开启 emitDecoratorMetadata 后，只要一个声明上挂着装饰器，编译器就会为它生成 design:type、design:paramtypes、design:returntype 三类元数据，通过 reflect-metadata 提供的接口挂到类或方法上。

框架据此在容器启动时读取构造参数的类型，再按类型查注册表，使用者只需要写一个类，不必显式声明依赖。代价有三点：产物体积增加，每个装饰过的声明都要带上元数据调用；运行时要引入 reflect-metadata 这个 polyfill；类型信息本身只是尽力而为，接口、联合类型、泛型参数在运行时都会退化成 Object，容器只能报错或者猜。

4.2 标准装饰器为什么不带它

标准装饰器的设计目标是让装饰器成为一项纯 JavaScript 能力，而不是 TypeScript 的私有扩展。元数据属于类型系统，一旦写进语言标准，就意味着所有引擎都要理解 TypeScript 的类型，这显然不现实。所以标准语义里没有 design 系列键，装饰器要拿信息，只能从 context 里拿，或者由使用者显式传入。

在配置层面，这两件事是绑死的：emitDecoratorMetadata 必须与 experimentalDecorators 同时开启，只开前者会直接报配置错误。TypeScript 没有提供“标准装饰器加元数据”的第三条路，这也意味着任何以元数据为卖点的库，在标准语义下都失去了根基。

4.3 替代方案：把类型变成显式的值

没有元数据之后，依赖注入并不是做不了，只是要把隐式的类型改成显式的 token。注册时给一个 token，解析时按 token 查，这也是许多框架后来走的路线。

实际项目里有三条可选路径。显式 token 改动最小、语义最清楚，缺点是每个依赖都要写一遍；在 addInitializer 里手工登记，适合自研的小容器，把构造函数与 token 的对应关系写进表里，解析时按 token 查；编译期生成则是用脚本扫描源码里的装饰器与类型标注，产出一份注册代码，运行时只读这张表。前两种是运行期方案，第三种把成本挪到构建期，适合依赖数量大、又不愿意手写 token 的项目。

需要提醒的是，这三条路都换不回旧版元数据的一个隐含优势：容器可以在启动时一次性校验整张依赖图。手写 token 的方案必须自己补一轮启动检查，否则漏注册的问题会推迟到第一次调用才暴露。

五、依赖注入与 ORM：生态为什么慢半拍

5.1 2023 年 3 月的现实

框架侧的迁移不是改几行代码的事。以 NestJS 为例，它官方模板里的 tsconfig 明确要求 experimentalDecorators 与 emitDecoratorMetadata 都为 true，模块、控制器、提供者的注册全部依赖参数装饰器与 design:paramtypes；Angular 的依赖注入同理，组件与服务的构造参数靠元数据解析；TypeORM 的实体装饰器依赖字段装饰器在原型上打标记，再配合元数据推断列类型；class-validator 则把校验规则挂在属性上，同样离不开元数据。这些框架只要还没完成改造，使用它们的应用就不能关掉开关。

所以一个项目能不能迁移，第一件事不是数自己写了多少装饰器，而是看依赖树。排查顺序可以这样定：tsconfig 模板里有没有那两个开关；package.json 里有没有 reflect-metadata；框架文档里有没有“必须开启”的说明；node_modules 里有多少包的声明文件直接声明了装饰器类型。四条里命中任意一条，应用层就应当继续留在旧语义。

5.2 库作者的双模式写法

对自研库、内部 SDK、工具函数来说，迁移可以先行一步，而且不必逼着使用方一起改。做法是让同一个装饰器函数同时接受两种调用形状，用第二个参数是不是带 kind 的对象来分流。

这段代码有两个细节值得强调。第一，函数的返回类型必须写成 any，因为两条分支一个返回替换函数、一个返回描述符，联合类型无法通过检查。第二，两条分支能做的事并不对等：旧版分支可以改描述符，新版分支不能。如果库的卖点恰好是把方法变成只读，那就得为两种模式准备两套实现，甚至为旧版保留一个降级开关。

还有一条底线：双模式装饰器不能依赖只有一侧才有的能力。在标准分支里读元数据永远拿到空值，在旧版分支里找 context 参数也永远拿不到。把“只在某一侧可用”的功能写进公共逻辑，是最常见的翻车方式。

5.3 同一仓库里的隔离

混合使用的前提是隔离。推荐按包隔离：需要旧语义的包保留原来的 tsconfig，新包单独一份，通过项目引用串起来。不要在一个包内部一半新一半旧，那样通常不会立刻报错，只会在运行期留下难以复现的差异。

包边界也要划在语义边界上。一个包对外暴露的装饰器如果同时支持两种模式，它的类型声明就得写得足够宽松，这时使用方很难从类型上看出自己该用哪种；更稳妥的做法是导出两个入口，一个给旧语义，一个给标准语义，让使用方按自己的 tsconfig 选择。

六、一条可执行的迁移路线

flowchart TD
  A[盘点装饰器使用点] --> B{是否依赖框架}
  B -->|是| C[保持旧语义 等框架升级]
  B -->|否| D[拆出可独立迁移的包]
  D --> E[自研装饰器改双模式]
  E --> F[补运行期行为测试]
  F --> G[切换该包 tsconfig]
  G --> H[灰度观察一到两个版本]
  C --> H

第一步是盘点，不要凭印象。用正则把所有以 @ 开头的装饰器用法捞出来，按类、方法、访问器、字段、参数分类，再标注每个装饰器的来源：框架、第三方库还是自研。参数装饰器的数量是最关键的指标，只要它大于零，这个模块就不能直接切换。

第二步是分类。把模块分成三类：完全依赖框架的应用层、部分依赖的基础设施封装、完全不依赖的工具库与纯数据结构。第三类可以立刻迁，第二类要先给自研装饰器加双模式，第一类只能等。

第三步是改造自研装饰器。把旧版里读描述符、改原型的逻辑，改写成返回值替换加 addInitializer 的形状，同时保留旧分支。改造时顺手补上类型标注，尤其是工厂函数的返回类型，否则泛型信息会退化成 any。

第四步是测试。装饰器的行为差异大多发生在运行期，类型检查帮不上忙。至少要覆盖四件事：返回值是否被正确替换、初始化顺序是否符合预期、私有字段能否通过 access 访问、继承链上的方法是否还能正常调用。

第五步是切换配置，只改目标包的 tsconfig。关掉 experimentalDecorators，把 target 提到 ES2022，跑一次完整构建。如果冒出一批签名错误，说明还有遗漏的旧式装饰器，回到第三步继续改，不要用类型忽略注释压过去。

第六步是灰度。装饰器相关的问题往往在特定调用路径才触发，先在小流量或内部环境观察一到两个发布周期，再推广到全部调用方。

两种包的配置大致如下，注意它们必须存在于不同的 tsconfig 中，靠项目引用组合。

七、构建配置：target 与 useDefineForClassFields

7.1 target 决定字段语义的默认值

useDefineForClassFields 的默认值跟 target 绑定：target 为 ES2022 或更高（含 ESNext）时默认为 true，更低时为 false。它不是装饰器的开关，却决定了字段的初始化语义，而字段恰好是标准装饰器改动最大的地方，两者必须一起看。

差异可以概括为一句话：为 true 时字段用 Object.defineProperty 定义，直接落在实例上；为 false 时字段用赋值语句初始化，如果原型链上存在同名 setter，就会被调用。这个差别在普通类里几乎看不出来，一旦有基类访问器，或者派生类用字段覆盖基类属性，行为就完全不同。

迁移时务必把这两件事拆成两个提交：先统一字段语义，再切换装饰器语义。混在一起，一批测试失败之后无法判断是哪一边造成的，回滚也只能整体回滚。标准装饰器在两种字段语义下是否都能产出符合预期的代码，取决于具体的编译器版本，最稳妥的做法是显式设为 true，让字段行为与提案一致，而不是依赖默认值。

target 还影响产物体积。标准装饰器需要编译器生成一组辅助函数，用于收集装饰器、应用替换、执行初始化器；target 越低，辅助代码越多，产物可读性也越差。如果运行环境允许，把 target 提到 ES2022 是整次迁移里性价比最高的一步。

7.2 工具链要对齐

只升级 typescript 是不够的。ESLint 的解析器要能理解新语法，否则会在装饰器位置直接报解析错误；SWC、esbuild、Babel 各有自己的装饰器实现，版本不同步时会出现 tsc 检查通过、打包产物行为不同的情况。建议在 CI 里保留一条用 tsc 编译产物跑集成测试的路径，把它当作行为基线，其他工具链的产物都要与它对齐。

类型层面也值得加一层保护。标准装饰器的签名是泛型的，写错时编译器通常能给出具体错误；但如果装饰器工厂返回 any，这层保护就没了。给工厂函数显式标注返回类型，比事后在运行期调试便宜得多。

八、几个高频坑

把上面这些差异落到实际项目里，出问题的位置其实相当集中，下面几条按遇到概率排序。

  1. 以为 @ 语法没变就等于写法兼容。语法确实没变，语义全变了，而且错误分散在各个文件里，很难一次看全。
  2. 单参数的类装饰器静默通过类型检查，然后在运行期忽略 context。审计时要把所有类装饰器逐个看参数个数，只看编译是否通过没有意义。
  3. 字段装饰器的初始化函数忘记 return，字段被覆盖成 undefined。这类问题类型系统完全允许，只能靠测试拦住。
  4. 旧版字段装饰器的返回值会被忽略，新版却会把它当作初始化函数调用，于是老代码里随手返回的东西会在实例构造时抛错。
  5. 依赖描述符的库：只读、不可枚举、改写 getter，这三类需求在新语义下都做不到，必须换实现方案。
  6. 参数装饰器残留。这是最硬的阻断项，见到就应停下来，先确认框架是否已经支持。
  7. 配置残留。老 tsconfig 里还留着 emitDecoratorMetadata，却把 experimentalDecorators 关掉了，编译器直接报配置错误，容易被误判成版本不兼容。
  8. 私有成员。不要用字符串拼 # 前缀去访问，用 context.access，既安全也不依赖压缩后的名字。

小结

标准装饰器不是 experimentalDecorators 的升级版，而是另一套语义：两个参数、一个 context、返回值替换、初始化器延后执行、元数据不再自动发射。TypeScript 5.0 把选择权交给 tsconfig，一个开关决定整套规则，同一个编译单元里无法混用。对应用侧来说，只要依赖注入或 ORM 框架还依赖参数装饰器与 design 系列元数据，就应当继续留在旧语义；对库作者来说，双模式装饰器配合按包隔离的 tsconfig，是当下最现实的过渡方案。迁移顺序应当是先盘点分类、再改自研装饰器、再补运行期测试，最后才动配置；字段语义与装饰器语义分两次提交，避免问题纠缠。等框架生态完成改造，这些准备工作会让切换退化成一次配置变更。
