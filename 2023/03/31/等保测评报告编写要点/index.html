等保测评报告编写要点

测评报告是等级保护测评项目里唯一会被反复翻开的交付物：备案时要交，监督检查时要看，整改立项时要引用，下一个测评周期还要拿它做对比。本文从报告的实际读者出发，讲清楚报告的骨架与结论逻辑、测评对象和范围怎么描述、符合性判定怎么写、问题描述怎样做到可复核、证据如何组织、风险与整改建议如何分级，以及复测闭环和常见写作问题。适合第一次独立撰写报告的测评人员、负责迎评的系统负责人，以及需要审阅报告的合规与运维同事。

一、先搞清楚报告写给谁看

很多初次写报告的人，会把它写成测评过程的流水账：哪天进场、访谈了谁、跑了哪些工具，按时间顺序铺一遍，末尾补一句结论。这样的文档作者自己看着踏实，换一个人读却几乎不能用，因为读者要的不是过程，而是判断。

测评报告本质是一份结论性文件，它要回答三个问题：被测对象是什么、对相应等级的安全要求满足到什么程度、不满足的地方怎么办。过程记录与证据材料都为这三个答案服务。凡是不能支撑结论的内容，要么进附录，要么不写。

1.1 四类读者，三种读法

第一类是委托方的系统负责人。他关心能不能通过、还差什么、要花多大力气，最常读的是整体结论、问题清单和整改建议。第二类是主管部门与备案受理方。他们关注范围是否覆盖完整、依据是否准确、结论是否有支撑，读法是抽查：随手翻到一条问题，看证据能不能对上。第三类是整改实施方，通常是运维和开发人员。他们需要知道问题出在哪台设备、哪个配置项、改成什么样子算改完，因此位置、现象、验收标准对他们最重要。第四类是三五年后的复测人员，也可能是你自己。系统已经换过一茬人，上一版报告就是唯一的起点，编号能不能接得上，直接决定下一轮的工作量。

同一份文档要同时满足这四种读法，靠的不是写得更长，而是分层：结论层给判断，明细层给事实，附录层给证据。三层之间用编号互相引用，读者想停在哪一层都可以。

1.2 一份稳定的报告骨架

报告的结构不必逐字套模板，但骨架应当稳定，这样读者换一个项目也不用重新适应。比较通用的组织方式如下。

第一部分是项目与委托信息，写明委托方、测评机构、测评类型（首次测评、复测或监督检查中的测评）、实施时间与报告版本。这部分最容易出错的是日期与版本：实施时间要和证据采集时间对得上，版本号要能追溯修订。

第二部分是测评依据与范围，列出所依据的标准与文件，写清本次测评覆盖的业务、组件和责任边界。依据只写标准号与标准名称，不要凭印象复述条款内容。

第三部分是被测系统描述，包括业务功能、网络拓扑、部署方式与定级情况。

第四部分是测评过程与方法说明，交代访谈、配置核查、工具测试、文档审查各自覆盖了什么，哪些结论来自哪种方法。

第五部分是单项测评结果，按层面组织，逐项给出判定、事实与证据引用。

第六部分是整体测评结论，说明汇总规则和最终判断。

第七部分是问题与风险分析，把不符合与部分符合的条目展开成可读的问题描述，并给出风险等级。

第八部分是整改建议，按紧急程度分层。

第九部分是附录，包括证据索引、访谈记录、工具输出摘要与缩略语表。

flowchart TD
  A[项目与委托信息] --> B[测评依据与范围]
  B --> C[被测系统描述]
  C --> D[测评过程与方法]
  D --> E[单项测评结果]
  E --> F[整体测评结论]
  F --> G[问题与风险分析]
  G --> H[整改建议]
  H --> I[附录与证据索引]

篇幅上有个经验：结论、问题、建议应占主要篇幅，过程描述压缩到能自证方法可靠即可。见过不少报告把网络拓扑写了十几页，问题描述只有干巴巴两行，读者读完仍不知道系统哪里不行。

二、测评对象与范围：把边界写到纸面上

等保测评的对象是定级对象，而不是一个笼统的系统。定级对象有明确边界：它由若干业务应用和支撑它们的主机、数据库、中间件、网络设备、安全设备组成，部署在特定机房或云上，由特定组织运维，并与外部系统存在数据交换。报告里的对象描述，就是要让没到过现场的人也能在脑子里画出这张图。

2.1 三段式：业务、组件、责任

第一段写业务。业务名称、业务性质（对外服务还是内部管理）、服务对象与规模区间、承载的数据类型，特别要说明是否涉及个人信息、是否涉及重要数据。数据类型不是套话，它直接决定后面风险分析和整改建议的落脚点。

第二段写组件。应用与接口、数据库、中间件、操作系统、虚拟化平台或云平台、网络与安全设备、运维通道（堡垒机、VPN）、备份与灾备设施、终端与移动端。每一项最好给出角色和大致数量级，但数量必须来自实际盘点，不能凭拓扑图推测。

第三段写责任。自建机房要说明物理环境由谁保障；托管机房要说明门禁、供电、消防的责任划分；云上系统要说明 IaaS、PaaS、SaaS 各层分别由云服务商和租户承担哪些安全职责，依据是云服务商公开的责任共担说明与合同约定。这一段写不清，后面的不适用判定就会站不住脚：物理环境的要求对纯云上租户是否适用，取决于责任边界，而不取决于测评人员方便不方便。

2.2 三张清单决定范围是否可信

范围描述的可信度，最终落在三张清单上：资产清单、人员清单、接口清单。资产清单要与证据里的主机名、IP、系统标识对得上；人员清单要覆盖系统负责人、运维、开发与安全管理岗位，访谈对象应能在清单里找到；接口清单要列出与第三方系统、上级平台、支付与短信通道的交互，因为边界处的访问控制与数据完整性往往最薄弱。

纳入范围要写，排除范围也要写，并且写清排除的理由与影响。例如灾备中心尚未启用、本期不纳入，就应当注明启用后需在下一周期补充测评，而不是默默不提。

2.3 常见遗漏

实际项目里被漏掉的，往往不是核心应用，而是围绕它的支撑设施：数据库实例与数据库账号、堡垒机与运维终端、日志集中采集平台、备份介质与恢复演练记录、移动端应用与小程序的后端接口、云上的对象存储与内容分发、第三方接口的鉴权方式。这些组件一旦遗漏，报告给出的整体符合就是有条件的，而这个条件没有写出来，等于把风险留给了读者。

2.4 不适用不是省略

某个要求在当前对象上没有对应场景时，应判定为不适用并说明理由，例如该对象不提供无线接入。错误写法有两种：留空让读者猜，或者为了省事直接写符合。前者让汇总表对不上，后者是结论错误。还有一种更隐蔽，是把没测写成不适用。前者是工作量问题，后者是事实判断问题，不能混。

三、单项结论与整体结论：两套逻辑

单项结论回答“这一条要求满足了吗”，整体结论回答“这个对象总体上达到相应等级的保护能力了吗”。两者相关，但推不出彼此。把它们当成同一套逻辑，是报告失真最常见的根源。

3.1 四种单项结论的准确含义

符合：该要求涉及的措施存在、配置正确、在实际运行中有效，且有证据支持。

部分符合：要求可以拆成若干子项，部分子项满足，部分子项缺失或失效。

不符合：主要要求未满足，或者虽有措施但经核实无效。

不适用：对象中不存在该要求所针对的场景，并且写明了理由。

两个容易走偏的地方。一是把已配置当成符合。策略配置了，但日志里看不到生效记录；口令策略设了，但存在绕过路径；这类情况属于措施无效，不能判符合。二是把有制度文件当成符合。制度只证明写了，不证明做了，执行情况要通过访谈、记录和抽样验证。这两种偏差在文档类要求上尤其常见。

3.2 判定句写成三段式

一条单项结论最好同时给出三样东西：判定、事实、证据。判定用标准术语，事实用一句话讲清满足什么、缺什么，证据指向附录编号。

反例是只写判定，不写事实。读者看到”部分符合”四个字，既不知道哪部分符合，也不知道差在哪里，只能去翻证据。判定句写完整，能省掉后面大量沟通。

3.3 整体结论不是算术平均

不能因为不符合项占比低就给出整体符合。理由至少有四条。

第一，不同要求对安全结果的影响不同。边界防护、身份鉴别、安全审计上的缺失，通常比文档格式上的缺失更直接地影响安全能力。

第二，要识别系统性缺失。同一类问题在多台主机、多个系统上重复出现，说明技术基线或管理流程整体失效，不能按条数摊薄成百分比。

第三，补偿措施要看有效性。存在替代控制且经验证有效，可以降低风险，但不能自动把不符合改成符合；补偿措施本身也需要证据。

第四，范围完整性是前提。范围漏掉了组件，汇总表再整齐也没有意义。

因此整体结论的写法应当是：先给判断，再给理由，最后给限制条件，例如在本次测评范围内、以整改前的状态为准。这三句话缺一句，结论都容易被误读。

3.4 汇总表怎么设计

汇总表一般按层面分行，列包括测评项类别、符合、部分符合、不符合、不适用，以及主要问题编号。最后一行合计。设计上有三条硬要求：合计必须与单项明细逐条对得上；正文引用的数字必须能在附录里找到对应记录；不适用项要有理由栏或者引用说明。

这里要提醒：具体数量以实际测评记录为准。不同系统、等级与标准版本对应的要求项并不相同，汇总表的数字不能照抄其他项目。表格整齐是形式，能对上是底线。

四、问题描述：让另一个人能照着复核

问题描述是报告里最见功力的部分。一段好的描述，应该让没去过现场的复核人员仅凭文字和证据编号，就能判断这个结论成立。

4.1 四要素：现象、位置、证据、影响

现象是看到了什么。是配置项的值、是缺失的记录、还是访谈中的回答。现象只写观察结果，不写推测。

位置是在哪看到的。主机名或设备名、IP、组件与版本、配置路径或菜单路径、账号角色。位置的精度标准是能再次打开。

证据是凭什么这么说。证据编号、截图编号、配置片段编号、访谈记录编号。

影响是会导致什么。落到该要求所保护的安全属性上，说明可能后果与前提条件。

在此之上再加两项会更完整：复现路径，即按什么步骤能看到同样的现象；判定，即对应哪种单项结论。复现路径对运维特别有用，他们照着走一遍就能确认问题是否真实存在，也能判断整改后是否真的改掉了。

4.2 含糊描述的典型症状

含糊不是文笔问题，而是信息缺失。下面几组对照能说明差别。

含糊写法 缺什么 改法
部分主机未开启审计 哪些主机、审计哪一项、比例多少 列出主机标识或引用清单编号，写明审计策略字段与当前值
口令策略较弱 弱在哪里 给出最小长度、复杂度、有效期、历史口令数量的实际取值
日志留存不足 实际多久、要求多久 给出实际留存天数与日志平台的配置位置
管理制度不完善 缺哪份、缺哪条 指出制度名称与缺失环节，如发布、评审、修订

表格里第三列是改法，不是让作者把话说得更长。改法的共同点是把形容词换成可核对的事实。

4.3 一个可套用的模板

模板不是让人填空交差。每一栏都要有具体内容，宁可多花十分钟核实主机名，也不要在报告里写某主机、某系统这类模糊指代。

4.4 影响一栏的边界

影响要写得有依据、有节制。写可能导致什么，不写具体攻击步骤、工具名称与参数；写数据类型的敏感程度，不写具体个人信息；不把单点配置缺失夸大成系统将被完全控制。同时也不能反向缩水成存在一定安全风险这种没有信息量的话。

判断标准很简单：一个有经验的运维读完影响，应该知道先修哪一个、为什么先修它。如果读完仍然没有优先级感，说明这一栏还没写到位。

五、证据组织：截图与配置摘录的规范

证据是报告的骨头。结论可以写得漂亮，但没有证据支撑的结论在复核时一文不值。证据组织要解决三个问题：找得到、看得懂、信得过。

5.1 编号、索引与引用

证据体系通常有三层编号：问题编号、证据编号、附录索引。问题编号按层面加序号，证据编号跟在问题后面，附录索引按编号排序并给出所在页码或附件名。三者必须闭环：正文每条判定都能指向证据，每份证据都能被至少一条判定引用，附录里不出现孤儿证据。

一条问题至少一份直接证据。直接证据是能单独支撑判定的材料，例如策略配置界面加参数导出；访谈记录、拓扑图属于间接证据。不能用间接证据支撑技术判定，也不能让一条证据同时证明三件不相关的事。

5.2 截图六要素

一张合格的截图要尽量包含：系统或设备标识、界面路径、采集时间、关键参数、操作账号（脱敏后）、采集人。这六项不一定都出现在同一张图里，缺的部分要在图注里补齐。

常见毛病有几种：只截一个弹窗，没有主机名，读者不知道这是哪台机器；把多张图拼在一起却不标注顺序和来源；用手机翻拍屏幕，反光、摩尔纹、时间都看不清；截图里带着真实口令、密钥或个人信息。这些问题都不难避免，难的是每次都记得。

一条经验：一张图只证明一件事。想让一张图同时证明口令策略、审计配置和账号权限，结果往往是三件事都看不清。

5.3 配置与日志摘录

命令行输出要带提示符与主机名，让人知道在哪台机器上执行。配置片段要带文件路径与前后几行上下文，孤零零一行参数无法判断它属于哪个配置块。日志要带查询条件与时间范围，只贴几行日志，读者无法判断这是全量还是抽样。

导出类证据保留原始格式，不要为了排版转成图片；原始文件与报告一起归档，正文只放摘要和编号。图片无法二次检索，也无法验证是否被修改，原始配置两者都可以。

5.4 脱敏的边界

脱敏要统一规则、可逆可查、保留判定所需信息。IP 可以保留网段、隐去主机位；账号保留角色、隐去姓名；口令与密钥一律替换为固定占位符；个人信息只保留类型，不保留内容。脱敏后要能看出问题依然存在，例如口令策略截图里最小长度这个字段必须清晰可见。

脱敏还要留痕：谁脱敏、按什么规则、原件在哪里。否则复测时无法判断是配置变了，还是图被人改过。

5.5 保存与移交

证据目录按项目、系统、层面三级组织，文件名带编号与日期，归档后设为只读并计算校验值。移交时给清单并双方签字，写清份数、格式与存放位置。保存期限按合同与机构制度执行。

六、风险分析与整改建议：从不符合到怎么办

6.1 不符合是事实，风险是判断

不符合回答要求是否满足，风险回答如果不满足会怎样、可能性多大。两者不能互相替代：一条不符合可能风险很低，因为对象在内网、有补偿控制、数据不敏感；另一条不符合可能风险很高，因为对象直接暴露在互联网、承载个人信息。

把风险等级直接等同于不符合的严重程度，是最省事也最容易出错的做法。读者拿到的将是一份没有优先级的清单，整改只能按编号顺序推进。

6.2 分级的五个维度

影响对象的重要性、暴露面、利用前提、现有补偿措施、数据敏感度。这五个维度不需要打分，但每个等级都要能说出理由，例如该服务对互联网开放且承载个人信息，同类缺陷在边界设备上重复出现，因此定为高风险。

flowchart TD
  A[不符合项] --> B{是否对互联网或第三方开放}
  B -- 是 --> C{是否涉及身份鉴别或数据访问}
  B -- 否 --> D{是否有经验证的补偿措施}
  C -- 是 --> E[高风险]
  C -- 否 --> F[中风险]
  D -- 是 --> G[中风险或低风险]
  D -- 否 --> H[中风险]

这张图只是决策的骨架，不是评分公式。同样的分支，在不同业务上得出的等级可能不同，理由比等级本身更重要。

6.3 建议分三层

立即整改：不改就可能被直接利用，或者整改成本很低。例如关闭不必要的公网映射、启用口令复杂度、修正明显错误的访问控制规则。

计划整改：需要变更窗口、预算或采购。例如部署日志集中采集、补充备份设施、替换已停止维护的组件。

长期建设：涉及架构与制度。例如区域划分调整、安全管理制度体系重构、运维流程改造。

每条建议写四件事：做什么、在哪做、验收标准、建议时限。再补一个责任角色，方便委托方分派。四件事里最容易漏的是验收标准，而它恰恰是复测的依据。

6.4 建议必须可验收

加强安全管理、提高人员安全意识、完善相关制度这类建议，写了等于没写，因为没人能判断是否完成。可验收的建议是动词加对象加结果：把审计日志接入集中平台并设置留存期；对数据库账号启用复杂度校验并限制失败次数。时限可以给区间，但要与整改难度匹配。

问题 不可验收的建议 可验收的建议
日志未集中采集 完善日志管理 将主机与应用日志接入集中平台，设置留存期与告警规则，提供接入清单
口令策略较弱 加强账号安全 启用复杂度校验，设置最小长度、有效期与历史口令数量，导出策略截图
备份未演练 重视备份工作 每季度执行一次恢复演练，记录恢复时间与数据完整性校验结果

七、复测与整改闭环

报告交付不是终点。整改是否真的发生、是否真的有效，需要在复测里验证，否则整份报告就停在纸面。

7.1 整改反馈表

委托方按问题编号逐条填写：整改措施、完成时间、责任人、验证方式、附件。核对时看两件事：措施是否直接对应问题，证据是否支持措施。一条措施覆盖五条不相关的问题，通常说明并没有真正整改。

7.2 复测范围怎么定

原问题逐条复测；整改引起的变更做回归，例如组件升级后复测版本与关联策略；同类资产抽样，确认整改是普遍执行，而不是只改了点名的那一台。抽样规则要写进报告，避免复测结论的适用范围被默默放大。

7.3 复测结论的写法

分已整改、部分整改、未整改三种，各附新证据编号。原证据不覆盖、不删除，新旧证据并存，读者能看到变化过程。报告升版时写修订说明：改了哪些结论、依据是什么、由谁复核。

7.4 闭环的三个断点

只交整改说明不交证据；复测只测原来那条，不管变更引入的新问题；版本管理混乱，复测报告与原报告对不上号。这三个断点任意一个存在，闭环就是名义上的。

八、常见写作问题清单

8.1 结论与证据不匹配

判定为符合，证据只显示配置页面，没有生效记录；判定为不符合，证据却是一张看不出问题的截图；一条证据被反复引用到不相关的多个结论上。改法是逐条核对，证据不足就补采，补不到就调整判定。

8.2 描述含糊

大量使用部分、相关、适当、存在隐患这类词，没有主机、没有字段、没有取值。改法是把形容词换成事实，把范围换成清单，把推测换成观察。

8.3 范围遗漏

漏组件、漏责任边界、漏第三方接口，最后整体结论的适用范围被悄悄放大。定稿前用资产清单反向核对报告目录，凡是清单里有、报告里没有的，都要有解释。

8.4 口径与体例不一致

同一事实在摘要与明细里说法不同；层面名称与术语混用；模板残留了上一个项目的系统名；把工具扫描结果直接当结论；把未发现写成不存在；整改建议与问题编号对不上。定稿前按问题编号把正文、汇总表、附录、建议表四处对齐，是最有效的一道检查。

小结

测评报告的价值不在篇幅，而在每个判断都能被复核、每条建议都能被执行。结论层说清判断与理由，明细层写实现象、位置、证据与影响，附录层保证证据可查。范围写到边界与责任，单项结论区分符合与措施无效，整体结论看关键项与系统性缺失，不能做算术平均。四要素描述、证据闭环、风险分级与可验收建议决定报告能否推动整改，复测与版本管理则把它变成可持续的安全记录。
