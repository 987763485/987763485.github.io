零信任架构落地实践

零信任作为理念并不新鲜，NIST SP 800-207《零信任网络架构》已给出正式参考模型，但真正动手改造会发现：难点在顺序与取舍。本文面向正在改造的安全、运维与平台团队，专注讨论落地步骤与工程取舍，不重复总论与服务网格内的实现细节。

边界的迁移：身份成为新的边界

传统架构的默认信任来源是网络位置：接入办公网或 VPN 后流量被默认可信，横向移动几乎无阻力。云端部署、远程办公与供应链攻击让“边界完整、内部干净”的前提不再成立。零信任把信任来源换成每次请求携带的可验证证据：你是谁、什么设备、请求什么资源，每一跳都重新认证、重新授权。

身份由此取代防火墙成为边界锚点，至少有三个类别，必须分开设计生命周期：

  • 人的身份：员工、外包与合作方，锚定在统一身份源与目录服务上，认证配多因素，账号状态变更实时进入决策。
  • 设备的身份：受管终端凭证，注册时由 MDM 或终端代理签发，携带合规基线状态，退役即吊销。
  • 工作负载的身份：服务间调用凭证，应由平台自动签发的短期证书承担，而不是散落在配置文件里的长期共享密钥。

三类身份都要有签发、轮转、吊销的闭环。多数事故并非认证强度不够，而是生命周期失管：离职人员账号仍可登录，退役机器证书仍能调接口。所以落地第一步往往不是产品选型，而是先把身份台账与轮转机制建起来。

设备状态与合规基线

同一套凭证，在干净的受管终端与被恶意软件感染的私人电脑上风险完全不同，设备状态必须作为授权的输入维度。基线不必贪多，有效项包括：是否受管、操作系统补丁级别、磁盘加密与锁屏、终端防护是否在线。终端代理周期上报到设备状态服务，聚合成带时效的标签集合，决策时作为声明交给策略引擎。简化策略片段如下：

访问代理与策略引擎的位置

参考模型把系统拆成决策点与执行点：决策点即策略引擎，集中回答“这个主体能不能对这个资源做这个操作”；执行点是代理、网关或应用内拦截组件，截下请求、拼装上下文、执行判决；再加身份源、设备状态服务与日志管道构成最小闭环，设计要回答两个位置的问题。

第一个问题是代理的形态。面向人的访问：应用层反向代理承接 Web 应用与 API、替换 VPN 入口，传输层隧道网关处理数据库、远程桌面等不走 HTTP 的流量。服务之间在集中网关与边车间选择：集中式策略与日志一致性好、改造范围小，但位于关键路径且并非所有协议都能穿透；边车适合东西向，但要求应用改造或平台注入，推进慢。现实方案多为混合：南北向集中，东西向在关键链路试点再扩面。

第二个问题是策略引擎故障时的执行点行为。默认拒绝最安全，但一次故障就让全公司访问中断；默认放行加告警可用性好，却等于在最坏时刻放弃边界。可行的折中是把资产显式分级：敏感系统在引擎不可达时拒绝新会话、存量会话维持到超时；低风险系统降级放行并告警。分级要写进资产台账并经业务方确认。引擎还要做多副本高可用，判决结果带版本号做短时效缓存，短暂故障时靠最后一次合法判决维持存量访问。

最小权限与动态授权

边界迁移后，授权粒度也要跟着迁移。很多团队上完统一认证，权限模型还是“能不能登录”，登录后能读什么仍由年久失修的菜单权限决定。最小权限应表达为主体、资源、操作、时间窗与条件的五元组，例如“财务组成员在工作日、从合规设备查看某类报表但不可导出”。建议属性与角色混合：角色承接稳定的组织映射，属性承接部门、岗级等动态条件；纯属性表达力强但难审计，纯角色在临时项目组里会迅速膨胀。

动态授权是把授予做成带时效的：默认权限只覆盖日常最小集，敏感操作走临时提升——审批通过后获得数小时有效的扩展权限，到期自动收回，天然留下记录。验证也不能只在建连时判一次：设备状态过期、身份被停用、出现异地登录等风险信号时，应触发重新认证、降权或断会话，靠短时效令牌、会话 TTL 与重校验实现。要警惕代理只解决传输层边界，数据级授权仍是应用自己的责任，混为一谈会出现“代理判决通过、应用默认放行全部数据”的空洞。

微隔离与网络出口收敛

员工侧边界容易被理解，东西向流量却常被漏掉，而数据中心与云上才是横向移动的真正舞台。微隔离的关键在推进方法而非设备选型：先按应用、环境、敏感级给主机与工作负载打标签；再开流量可视化，用真实连接数据推导哪些组确实需要通信，形成白名单草案；然后在单个分组内把默认改为拒绝并逐组扩面。从全局默认拒绝直接开始的项目，多以大规模故障和整体回滚收场。

两个现实约束。一是历史兼容：健康检查、广播协议、只认源 IP 白名单的老系统不认识身份，应单独识别、记入例外清单并设复查时间，而不是留下永久放行规则。二是执行层主从：主机防火墙、容器网络策略与设备 ACL 并存，必须明确哪一层是最终判决者，否则排障时互相推诿。与微隔离配对的是出口收敛：关闭服务器与办公终端的直连外网，对外访问统一经正向代理执行白名单并留日志；出口日志会暴露无人认领的对外调用，相当于一次免费的依赖盘点。代价是切断直连必有应用报错，所以同样先观察后强制，保留带审批的临时放行通道。

日志与策略可观测

零信任把决策密度提高到每次访问判一次，日志设计必须跟上。最小事件集有四类：认证事件（成败与所用因子）、授权判决事件（请求上下文、命中策略标识与版本、结果与原因）、会话事件（建立、降级、终止及原因）、设备状态快照（判决时引用的基线值与采集时间）。判决日志的价值常被低估：传统审计回答“谁访问了什么”，零信任下更常问的是“这次为什么被拒绝”，日志因此要记录输入声明、命中策略版本与输出结果，让每个拒绝可复现、可解释。简化事件示意如下：

分阶段落地：先可视，再收口，后自动化

组件按什么顺序串起来，是落地成败的分水岭。总原则：任何强制手段上线前先以观察模式跑完一个完整业务周期，每个阶段都有明确的完成标准与回退点。分期如下：

flowchart TD
  A[阶段0 盘点：资产与身份台账] --> B[阶段1 可视：代理与日志观察模式]
  B --> C[阶段2 收口：敏感应用走代理，MFA 与基线分级强制]
  C --> D[阶段3 动态：临时授权，会话再评估，微隔离默认拒绝]
  D --> E[阶段4 常态：策略版本化与指标化运营]
  C -.回退：保留旧入口一个迁移窗口.-> B
  D -.回退：单分组关闭默认拒绝.-> C

阶段 0 是盘点而非选型：三类身份存量、应用清单与分级、东西向流量与出口依赖。阶段 1 只做可视化：计划收口的链路部署代理与日志，策略处于观察模式、判决只记录不执行，产出设备达标率与策略误伤率基线。阶段 2 收口，从高价值、低复杂度的应用做起：敏感系统强制多因素与设备基线、Web 入口切到代理、出口收敛，旧通道保留一个迁移周期。阶段 3 引入动态性：临时授权与工单联动、会话再评估、微隔离在已验证分组转默认拒绝。阶段 4 是常态运营：策略版本化、灰度发布、指标复盘、僵尸策略清理。每阶段结束回答两个问题：本阶段用什么数据证明了什么，下一步出问题退回到哪里。跳过观察期直接强制、把四阶段压成一次性切换，是两个最常见的错误。

迁移中的兼容与回退

改造是新旧并存期，兼容与回退要提前写进方案。先处理“过不去”的系统：没有客户端能力的遗留设备、只认源 IP 的老接口、私有协议流量，为其建立正式例外清单，逐条注明负责人、补偿措施与复查期限。例外本身不可怕，没有记录、无人认领的例外才可怕。用户侧回退的核心是入口不断：迁移期旧 VPN 与新代理并存，按应用逐个切流量，出问题单独切回。平台侧回退靠分层开关：全局、分组、单应用三级都能独立切回观察模式，无需发版。最后把预案做实：明确引擎不可达时的降级路径与决策人，演练中真的拔掉一次主节点验证——没演练过的回退方案不可信。

常见失败模式

第一种是把零信任当成一个产品：采购统一认证加访问代理，部署完就宣布上线，但策略引擎只有几条粗粒度规则，判决日志没人看。产品提供的只是执行点，零信任的实质在策略与数据——没有策略运营的组织，买什么工具都只是换个入口。

第二种是只上统一认证、没做策略。登录体验集中了，授权模型却原封不动：长期令牌、全量功能可见，只是把密码墙换成单点登录墙，还多了一个入口单点故障。

第三种是跳过观察期追求一步到位：按理想架构图全网一次性强制，触发大规模故障后整体回滚，回滚冲出的临时规则从此固化，项目信誉耗尽被搁置。

第四种是只管人、不管机器与工作负载。服务间仍用共享长期密钥与源 IP 白名单互调，攻击者拿到任一容器即可平推；三类身份缺一类，等于边界留了一个不查票的门。

第五种是把零信任做成一次性项目：策略不版本化、例外不复查、指标不运营，一年后系统退化成没人敢动的黑盒。判断落地健康与否的标尺，是最近一次僵尸策略清理与回退演练发生在何时。

小结

零信任落地的本质，是把信任来源从网络位置迁移到身份、设备与上下文的持续验证：先建好三类身份台账，让设备状态以带时效的声明进入决策，把引擎故障行为写进资产分级，权限收紧到五元组、授予带上时效与审批。推进顺序没有捷径——盘点、可视、收口、动态、常态，每一步用观察期数据换取强制许可，每一条强制都预留回退开关。把零信任当产品的人，最终要回来补策略运营的课；把它当机制建设的人，才能得到跟着请求走的边界。
