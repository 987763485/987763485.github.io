向量检索服务部署

前面我们在别的文章里聊过 Milvus 的接口用法、几种向量库的选型对比，以及 RAG 系统的整体工程化，都属于“选好了用什么”的层面。本文要谈的是选完之后怎么把它变成一台能长期稳定运转的生产服务：独立集群还是嵌入现有数据库、索引与分片怎么设计、数据怎么写入与重建、冷启动多久、查询参数怎么调、租户怎么隔离、监控看什么、容量怎么估、切换怎么灰度。适合已经跑通原型、准备上生产的后端与基础架构工程师。需要说明，本文聚焦部署与运维，不再重复各产品的 API 细节与横向对比结论，涉及数字的地方均为便于计算的示意值，不是基准测试结果。

服务的两种形态：独立集群还是嵌入现有数据库

向量检索服务落地时最先要回答的问题，是它以什么形态存在于系统里。粗略分只有两种：一种是以 Milvus、Qdrant、Weaviate 为代表的独立集群，检索能力由专门的服务承载；另一种是以 pgvector 为代表的嵌入式方案，向量作为现有数据库里的一列，检索复用原有数据库的进程、事务与运维体系。

独立集群的好处是“专机专用”。向量索引吃内存、吃 CPU、启动慢，这些特征和典型的在线事务负载冲突很大，拆出来之后检索侧可以独立扩缩容、独立设置内存规格、独立调整索引参数，不会被主业务的流量高峰拖累。代价同样是所有分布式系统的老代价：组件多了一个，Milvus 2.2 这类架构还依赖对象存储和消息队列，故障模式、升级流程、备份策略都要单独建一套。更麻烦的是数据链路：原文存在业务库里，向量存在检索集群里，两者之间要靠同步管道维持一致，删除、更新、回滚都要跨系统协调。

嵌入式方案正好反过来。以 pgvector 0.4 为例，向量和业务行在同一张表里，写入在一个事务里完成，删除跟着行走，备份沿用数据库现有的机制，一致性几乎是免费的。部署上不需要新增任何服务，运维团队也没有陌生感。限制在于规模与调优空间：索引跟普通表一样受单库容量和连接池约束，检索负载与业务查询互相抢占资源，索引类型和参数调节的丰富度也不如专用引擎。pgvector 0.4 开始支持 HNSW 与 IVFFlat 两类索引，能力上补齐了一大块，但把一个大表的所有查询都推向向量近邻搜索时，缓冲池与锁的行为仍需要按数据库的方式来分析。

选择标准其实不复杂。数据量在百万级向量以内、查询并发不高、团队已有成熟的 PostgreSQL 或 Elasticsearch 运维体系、且向量与源数据必须严格同生共死的场景，优先嵌入现有数据库。数据到千万级乃至更大、需要精细控制索引类型与内存布局、查询 QPS 高且延迟敏感、需要多租户隔离和独立扩容的场景，值得养一个独立集群。还有一个常被忽略的过渡策略：先用嵌入式方案把业务跑通、把数据管道与评测集建起来，等规模真的越线，再把检索层迁到独立集群。

索引类型选择：内存、延迟、召回的三角

部署服务之前要定索引，而定索引本质上是在三个量之间做取舍：占用的内存、查询的延迟、返回结果的召回质量。这三者构成一个三角，工程上通常不可能同时拿到最好，只能沿着三角形移动。

最省心的全量暴力检索，也就是 Flat 类索引，召回恒等于一，延迟与内存开销都随数据量线性增长。它的正确用法不是“小数据凑合用”，而是作为一切评测的对照基准，以及在数据子集足够小时作为兜底路径。很多过滤场景下，对候选集合直接暴力扫反而比走图索引更快，这一点后面调参时还会提到。

IVF 类索引把向量空间聚成 nlist 个簇，查询时只扫描 nprobe 个最近的簇。它的内存友好之处在于可以配合标量或乘积量化压缩向量，把每个向量的存储从几百字节压到几十字节，代价是量化误差会侵蚀召回。调优的主旋钮是 nprobe：调大它召回上升、延迟近似线性上升。IVF 对数据分布比较敏感，簇的均衡程度、向量是否归一化都会影响效果，所以重建参数要在有代表性的数据上离线验证，不要照抄文档默认值。

HNSW 是分层可导航小图，查询沿着图逐层下降逼近目标，通常能在同等召回下拿到最低的延迟，因此成了 2023 年各家引擎的默认推荐。它的账要算在内存上：图结构中每个节点要保存 M 条出边，一层一层加起来，索引体积往往是裸向量的数倍。举例来说，1000 万条 128 维 float32 向量的裸数据约 5 GB，M 取 16、每向量约 48 字节邻居信息时，图结构再加 2 GB 上下，加上杂项开销，按 8 GB 做规划比较稳妥，这些都是示意计算，实际以引擎的统计为准。查询侧的旋钮是 ef（或各产品里等价的名字，如 efSearch、检索时候选队列长度），调大换召回，延迟同样随之上升。

2023 年中的版本里能用的磁盘方案还很少，多数引擎的核心路径仍是内存索引，所以“索引装不装得下”是部署时最硬的约束。合理的做法是：用一小份有代表性的数据加一个查询评测集，在候选索引上跑召回-延迟曲线，选定类型和参数后再按内存模型放全量，而不是反过来先上全量再发现问题。选型时也要给自己留退路：暴力检索、IVF、HNSW 三条路径最好都能在配置里切换，线上降级与故障排查时需要这个开关。

分片与副本设计，连同容量估算一起做

单机的内存与核数总有顶，分片就是把数据切成多份、每份独立建索引、查询时并行扇出再归并结果。部署服务时要回答三个问题：按什么切、切成多少片、每片放几个副本，而这三问的答案很大程度上由容量估算决定，所以建议放在一起做。

切分方式常见的有两种。一种是引擎内部的哈希分片：向量按主键或某种哈希均匀落到各分片，每个分片不知道自己以外的数据，查询必须广播到所有分片，各片返回 top-k 再归并。它的好处是分布均匀、运维简单，代价是查询放大——每次请求都要碰全部分片，端到端延迟取决于最慢的那一片，分片数越多尾延迟越难压。另一种是应用层的分区路由：按租户、业务线或时间把数据划成互相独立的分区，查询带着分区键只打向相关分区。Milvus 的 partition、Qdrant 的 collection 划分都能承载这种思路。它的收益是查询只扫命中范围、天然支持租户隔离，风险是分区键选得不好后出现大小片，某个热分区把单机打满。实践中两者常常叠加：先按业务维度分区，分区内部再交给引擎分片。

副本的作用主要是两点：扛读扩散和故障容错。向量服务的读远多于写，同一个分片挂两三个副本可以把 QPS 摊开，滚动维护时也能保持可用。要注意副本间是有可见性窗口的新旧关系，不是强一致镜像，写完立刻读的场景要确认引擎的读写一致性语义。放置副本时尽量跨故障域——跨机架或至少跨节点，同机的副本在节点故障时一起消失，等于没有副本。

写入与索引构建：全量重建、增量与删除

原型阶段大家只关心“把向量插进去”，生产上写入路径的设计才是运维负担的大头。主流引擎的写入模型如今相当一致：新来的向量先进入内存里的增长段（growing segment），用暴力检索保证立刻可查，攒够阈值后在后台刷盘建成正式索引段。理解了这个“两段式”，就能理解写入侧的三个关键流程。

全量重建是最重、也是最可靠的操作，触发条件通常是 embedding 模型或维度变更——模型一换，新旧向量不在同一语义空间，老索引没有任何挽救价值，必须全量重算。适合的场景还包括索引类型或关键参数变更、数据损坏、以及清理长期积累的碎片。重建的正确姿势是“建新房、搬家、原子换门牌”：在后台按新版本构建索引文件或新 collection，构建期间线上照常读旧索引，完成后做一次切换。要记住重建是资源大户，构建任务的并发与内存要有专门配额，别让一次重建把在线节点的内存顶穿。

增量写入是常态，运维上要盯两件事。一是增长段的数量与大小：写入速率超过后台建索引速率时，未合并的小段越积越多，查询要扫的段数上升，延迟缓慢爬升，这种“慢性病”往往在上线几周后才暴露，所以要把段数纳入监控。二是重建的时机：当段的分布与初始假设偏离太远，找低峰期做一次段整理。

删除是向量索引里最容易被轻视的操作。多数引擎采用标记删除：向量还留在索引结构里，只是带着删除标记，查询命中时被过滤掉。这意味着删除比例高了之后，索引返回的候选里有很大一部分是无效的，等效召回被稀释，延迟也会因为要补齐 top-k 而变高。所以删除率是个要监控的量，超过一定比例就要触发段的合并重建（compaction），把墓碑真正清掉。业务侧的更新最好走“按主键替换”而不是“先删后插”，后者在中途失败时会留下既删了又没有的窗口。

冷启动与内存加载：把“起得来”当成一等指标

关系型数据库重启是秒级的事，向量检索服务重启动辄几十分钟，这是部署时最容易低估的运维差异。原因很直接：索引主体在内存里，进程重启后要么从本地盘重新读入索引文件，要么从对象存储拉取再装载，千万级向量的 HNSW 图装载时间以十分钟计是常事，冷启动期间服务要么不可用、要么只能命中部分分片。

这带来一连串部署决策上的连锁反应。第一，自动扩缩容在独立集群上要非常克制：按 CPU 或内存利用率弹出的新实例，在装载完成前对流量毫无贡献，autoscaler 只会看到“利用率低”而把刚起起来的实例再缩掉，来回抖动。第二，Kubernetes 的就绪探针必须挂在“装载完成”这个状态上，而不是进程存活；存活探针反而要给足宽容时间，别让 kubelet 在装载中途杀掉正在启动的 Pod。Milvus 2.2 这类引擎有显式的 collection 装载语义，把装载动作放在就绪检查里做成幂等步骤比较稳妥。第三，滚动升级的节奏由装载时间决定：一次杀一个副本、等它装载完成再动下一个，副本数太少时滚动窗口就是发布窗口，这也是容量规划里副本数下限的来源之一。

缩短冷启动的手段有限，主要是三招。并行加载：确认引擎是否支持分段或多线程读入，默认配置未必拉满。本地缓存：把从对象存储拉取索引的中间副本落在本地盘，重启时核对校验和后续用，牺牲一点磁盘换重启速度。预热查询：服务就绪后先用缓存好的样本查询打几轮流量，把页缓存、连接池、图遍历的分支预测这类“二次冷启动”消化掉，再放进负载均衡。如果业务对恢复时间有硬指标，就把“单副本冷启动时间”做成定期演练的测试项，随索引增长盯住它的趋势，不要等到真实故障时才知道要多久。

查询参数调优与过滤条件的代价

服务跑起来之后，查询路径上能拧的旋钮集中在两类：候选量参数和过滤策略。它们共同决定了召回质量与延迟的平衡点。

候选量参数就是前文说的 nprobe、ef 这一族。调优的正确流程是先定召回目标再定参数：用评测集离线扫一遍参数网格，画出召回率对 P99 延迟的曲线，在预算内选点。经验规律是延迟随候选量近似线性增长，而召回收益递减——从 90% 提到 95% 可能只要把 ef 翻倍，从 95% 到 98% 可能要翻好几倍。生产配置可以把默认值定在性价比拐点附近，对延迟敏感的接口调小，对质量敏感的离线任务调大，多数引擎允许请求级覆盖参数，这比全局调参灵活得多。

过滤条件是查询侧最大的暗礁，因为 pre-filter 与 post-filter 的代价完全不同。post-filter 先做近邻搜索再扔掉不满足条件的结果：实现简单、检索开销固定，但选择性强（比如只放行某个租户最近一小时的数据）时，top-k 结果里可能一大半被过滤掉，返回条数不足，召回质量断崖式下跌，还得靠自动扩大候选重试来兜底，延迟反而失控。pre-filter 先算出满足条件的向量集合，让图遍历或簇扫描只在合法集合内进行：结果数量有保障，但过滤集合会破坏索引的空间局部性，极端情况下性能退化到近似暴力扫描。2023 年的引擎对两条路径的实现程度不一，有的只对特定索引支持 pre-filter，部署前要在自己的过滤形态下实测，而不是相信通用宣称。

工程上的规避手段比调参更有效。把高区分度、查询必带的过滤字段前置到分区层——租户、业务线这类条件用分区路由解决，让过滤集合从“全库的一小撮”变成“整个分区”，检索时不再需要昂贵过滤。剩下的低区分度条件（时间范围、状态标记）交给引擎的过滤实现，并给每条查询路径设置候选数上限与超时：超时就返回已有结果并打上降级标记，让上游知道这次召回可能不完整，这比让请求排队拖垮整个服务健康得多。pgvector 这类嵌入方案里，过滤可以借 SQL 的 where 子句表达，要注意优化器选错执行计划的问题，必要时强制走向量索引或拆分查询。

多租户与命名空间隔离

SaaS 化的检索服务几乎必然面对多租户问题：不同客户或业务线的数据不能互相看见，而向量索引又不像行级权限那样可以随手加上。部署层面有三种隔离强度可选，代价曲线差别很大。

最强的是物理隔离：每个租户一套独立的 collection 或索引，查询路径天然不可能越界，噪声邻居的影响也被索引边界挡住。问题在数量上——collection 不是免费的，每个都有自己的元数据、增长段、装载状态与内存占用，几百个以上的小租户会让集群的调度与装载时间显著恶化，小租户的索引还普遍建得又碎又慢。这条路只适合大客户：数据量大、SLA 独立、付得起独占资源的租户单独开，剩下长尾走共享路径。

中间一档是逻辑分区：同一套服务内按租户键分区，查询强制带分区条件。Milvus 的 partition、以及“把租户字段建成带过滤索引的标量列”都属于这一类。它共享大部分基础设施，隔离强度取决于过滤是否被强制执行——服务层必须把租户上下文注入到每条查询里，绝不能信任调用方自带的过滤参数，否则一次代码疏忽就是数据串门事故。最弱也最省的是单集合加字段过滤：所有数据一个索引，租户条件只是一个普通过滤，成本最低，但前面讲的过滤代价问题会全部浮现，尤其租户数量多、单租户数据少时，等效于每个查询都在做高选择性过滤。

折中的常见配方是：隔离机制与路由键合一。用同一个高区分度字段（租户 ID）做分区路由，让“隔离”顺便解决“查询只扫相关分区”，一个机制背两个职责。配额与限流要跟着租户走：按租户统计 QPS 与延迟，对异常流量先限自己而不是让全局降级；内存账也要能按租户归集，定价与容量谈判都需要这份数据。最后提醒命名空间的设计要给未来留位：租户 ID 一旦定下很难改，版本、区域、环境这类维度最好一开始就进路由键的元数据，而不是散落在 collection 命名的字符串约定里。

监控指标与告警：召回、延迟、内存三件大事

向量检索服务的监控要覆盖三个平面。

服务平面是常规的四个黄金信号：QPS、P50/P95/P99 延迟、错误率、饱和度。这里特别强调 P99 而不是均值：分片扇出的架构下，端到端延迟由最慢分片决定，一次后台段合并、一次页缓存缺失都能把尾部拉出毛刺。看板上要把“引擎内检索耗时”与“端到端耗时”分开设指标，前者涨了查索引，后者涨了查网络与排队。所有请求应带上候选参数、命中分区、是否降级等标签，否则线上参数变更后你无法回答“新参数真的更慢吗”。

资源平面盯内存与磁盘 IO：分片级内存水位是最该告警的量，建议软阈值 75%、硬阈值 88%，超硬阈值前先触发再平衡或禁写而不是等 OOM；其次是内存压力导致的换页速率、增长段数量、未合并的小段数、删除标记占比、后台构建任务的积压时长。这几个“索引健康”指标是向量服务特有的，它们缓慢恶化时业务无感，爆发时就是延迟雪崩，趋势告警比阈值告警更有效。

质量平面最容易被省掉，但对检索服务恰恰是生命线：召回质量会悄悄退化。可行的做法是在线影子评测——每天从真实流量里抽样一批查询，异步用暴力全量扫描算一遍“参考答案”（示意比例：抽千分之一即可，成本远低于想象），与线上 top-k 比对算近似召回率与排序相关性，按租户与查询形态分桶。召回率的缓慢下移往往先于一切资源指标暴露问题：数据漂移、删除墓碑积累、增量段积压都会在这里现形。告警规则示例：

指标名是示意，落地时换成各引擎真实暴露的名称。经验上最值得建立的一条纪律是：任何索引参数、过滤策略、引擎版本的变更，都必须同时看服务平面与质量平面的前后对比，只看延迟而不看召回的发布，等于蒙眼开车。

一致性、备份恢复与灰度切换

先说一致性的定位。向量检索服务应当对外承诺最终一致，而不是强一致：写入成功到全量可查之间存在可见性窗口，增长段转正、副本同步、分区路由生效都需要时间。部署文档里要把这个窗口测出来并写进接口约定，让上游业务知道“刚删的内容还可能被查出来多久”。对一致性敏感的删除操作，可以在服务层加短期 bloom 或黑名单过滤作为补丁，但这是缓解不是根治。真正的事务一致性留在源数据库，向量侧把它当作下游缓存来对待。数据同步管道要保证幂等与顺序：按主键重放插入应当无副作用，同一主键的删除与插入乱序到达时要有版本号裁决，否则会出现旧向量覆盖新向量的幽灵。

备份策略取决于一个判断：向量是不是可以重建的派生数据。只要源文档和 embedding 模型版本被完整保存，向量理论上总能重算，所以最小的备份承诺其实是“源数据 + 模型版本 + 索引参数”三件套。但中小规模下把索引本身也纳入快照更划算：千万级向量全量重建加装载可能要几个小时，而对象存储上的索引文件快照通常快得多。独立集群一般把索引落在对象存储，天然带版本与复制能力，重点核对的是元数据服务与 WAL 的备份是否同步；嵌入数据库则完全复用既有备份体系，这是它运维上最省心的一点。无论哪种，恢复演练必须做，演练的验收标准就是前文说的冷启动时间与恢复后召回抽检。

灰度与索引切换是部署运维中风险最高的动作，因为它同时动数据和查询路径。稳妥的流程是五步：

flowchart TD
    A[双写: 新旧索引同时接收写入] --> B[后台重建: 新索引灌入全量历史]
    B --> C[影子流量: 复制线上查询到新索引]
    C --> D{延迟与召回达标}
    D -->|否| E[回到重建或调参]
    E --> B
    D -->|是| F[按租户逐步切流]
    F --> G[全量切换: 旧索引保留观察期]
    G --> H[观察期结束: 下线旧索引停双写]

第一步双写先行，保证新索引构建期间不丢增量；影子流量阶段用真实查询比对两套索引的结果，召回与延迟达标才允许切流；切流按租户或按百分比推进，查询服务通过别名或路由表指向当前生效的索引版本，切换本身只是改一个指向，回滚也就是改回去。最容易犯的两个错误：一是切换后立刻销毁旧索引，观察期应当覆盖至少一个完整的业务周期；二是忘了停双写，让两套索引长期并存吃双倍内存，直到某次容量告警才想起它们的存在。引擎大版本升级也套用同一路径，只是“新旧索引”换成“新旧集群”，多一道数据导出导入的成本，所以版本升级要攒着做，别追每一个小版本。

小结

向量检索服务的部署，本质是在内存、延迟、召回这个三角之下再做三层外推：形态层决定你养不养得起独立集群，小规模贴着业务库走是务实选择；数据层的核心是理解增长段、标记删除与重建的节律，把段数、删除比、装载时间当成一等公民来监控；流量层的关键词是路由与灰度，租户条件前置成分区，任何索引变更都走双写、影子与逐步切流。容量估算给出预算，压测回放给出真相，影子评测守住召回底线。把这些做扎实，向量检索服务才能成为敢在深夜报警时叫醒你的生产设施。
