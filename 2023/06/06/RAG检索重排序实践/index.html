RAG 检索重排序实践

本文属于《Agent 智能体开发》第 26/55 篇
上一篇系列目录下一篇

很多检索增强生成（RAG）系统的质量波动，第一跳的检索链路往往负有相当责任：双塔向量检索捞回来的 top-k 文本块，主题相近却答不上问题的居多，直接塞进提示词，大模型再强也无米下锅。重排序（rerank）的思路是在召回与生成之间插入第二个打分器：用更贵但更强的模型只对召回候选做精排，把“相关”与“能回答”区分开。本文面向已跑通向量检索链路的工程师，讨论重排环节的模型选择、参数决定、评测归因与上线运维。

为什么是“召回 + 重排”两阶段

把检索看成“从百万级语料里挑出五段证据”的任务，会发现它天生是两个矛盾的阶段：候选集合大到任何精细模型都跑不起，最终结果又小到必须有一个挑剔的环节负责把关。两阶段检索就是对这个矛盾的工程化拆解。

第一阶段召回，用的多是双塔（bi-encoder）向量检索：文档向量在离线阶段算好，在线时只需把查询编码成一个向量，再去近似最近邻索引里比较。每个候选的边际成本近似一次向量内积，这是它能在亚线性时间内扫过百万级语料的原因。代价是文档表示与查询无关——文档进索引时并不知道自己将来会被什么问题问到，只能把“可能被问到的所有语义”压缩进一个固定向量。

第二阶段重排，用的多是交叉编码器（cross-encoder）一类“读题打分”的模型：查询和候选文档拼成一条输入，一次前向输出相关性分数。文档表示是查询感知的（query-aware），能捕捉细粒度的匹配关系，但每个候选都要完整跑一遍模型，只能用在候选已经变小的地方。

由此得到两阶段的第一条性质：召回决定上限，重排决定上限内的次序。设最终交给大模型的是重排后的前 k2 个片段，那么“相关片段进入最终列表”的概率不可能超过召回池的 Recall@k1——重排无法把召回没捞到的文档变出来。这决定了参数顺序：先确定 k1 让候选池覆盖率够高，再让重排在池内排序。

第二条性质是错误模式互补。双塔打分只看“两个向量像不像”，重排模型则可以对比“查询问的具体约束，文档有没有精确回应”。否定、数量、时间范围、实体角色这类信息在固定向量里很容易被主题相似度淹没，交叉编码器恰好对这些模式敏感。边界说明：分块策略、向量库选型与检索服务部署不在本文范围，召回在这里被抽象成一个“输入查询、输出 k1 个候选及其分数”的黑盒。

双塔与交叉编码器：表达能力差在哪

双塔的形式是 score(q, d) = sim(f_q(q), f_d(d))：两个编码器各自独立地把文本映射为向量，相关性由向量相似度给出。关键限制在于文档向量不依赖查询：同一份 f_d(d) 要同时服务“退货政策是什么”“退货运费谁承担”“能不能到店退”三类问题。向量维度有限、注意力没有交互，模型只能押注在文档的“整体主题”上。

交叉编码器的形式是 score(q, d) = g([q; d])：q 和 d 拼接成一条序列，同一个 Transformer 自始至终对两段文本做全交互注意力——查询里的每个词可以关注文档里的每个词，且这种交互发生在每一层。于是“查询中的条件与文档中的例外条款是否冲突”这类判断可以在前向计算中被真正实现。它没有可预计算的表示，无法建索引，只能逐对在线计算。

两者之间还存在一个折中位置：以 ColBERT 为代表的后期交互（late interaction）模型，把文档编码成词多向量集合存进索引，查询时用 MaxSim 一类算子做逐词级匹配，保留了部分 token 级交互，代价是存储量从每文档一个向量膨胀为每 token 一个向量。可见双塔与交叉编码器之间存在连续的“交互深度-在线成本”谱系，选型本质是在谱系上找位置。

对 RAG 场景还有一个容易被忽略的事实：重排器能利用的信息不止文档正文。标题、章节层级、表头、来源与更新时间，都可以拼进交叉编码器的输入参与打分，而这些结构化信号在双塔的固定向量里几乎放不进去。双塔模型本身的评测与选型属于 embedding 评测的范围，本文不重复。

两种模型的对照可以总结成一张表：

维度 双塔召回 交叉编码器重排
交互发生时机 仅最后的向量相似度 每层注意力全交互
文档表示 查询无关，可离线索引 查询相关，必须在线算
单候选成本 约一次向量比较 约一次前向推理
可扫描规模 百万级 几十到几百
擅长的错误类型 主题级匹配 条件级、约束级匹配
典型失效 主题相近但不能回答 输入被截断、长文档读不全

第一是截断。这类模型的上下文上限多为 512 个子词（subword）token，查询只占几十，余量全部给了文档；一旦分块偏长或拼接了元数据，尾部内容会被直接切掉。被切掉的部分如果恰好是答案所在，模型会给出一个自信的错误低分。中文场景要特别注意：子词切分下的 token 数不等于字符数，按 512 个字符配窗口会在中文语料上系统性截短。

第二是对长文档的处理策略，实践里主要有三种。其一是首段截断，直接把文档前若干 token 塞进窗口，实现最简单，适合分块本身较小的场景（块越小截断损失越小，但单块语境也越少）。其二是滑窗最佳匹配：把文档按固定长度 w 的窗口、步长 s 滑动切开，每个窗口与查询拼接送打分，取窗口间最高分作为文档分——monoBERT 一类早期工作就采用这种“切段、逐段打分、取最优”方案，它把“文档里有没有答案”诚实地转成了“文档的某个窗口里有没有答案”。其三是先句级后段级：先用便宜的信号选出与查询最相关的句子，重组为一段“浓缩文档”再送模型。

第三是池化方式对分数可比性的影响。取 max 是“最佳窗口”语义，对答案只在一小段里的精确问答友好；取前几个窗口分数的均值，语义变成“整体相关”，对综述型问题友好。两者分数分布不同，池化方式一旦改变，跨文档的分数就不再同分布，任何依赖绝对阈值的下游逻辑都要重校。因此笔者建议把“重排器版本”定义为四元组：模型检查点、输入拼接模板、max_length、池化方式——任何一项变化都按一次模型升级对待，走第八节的回归评测。

候选数 k 的选择：质量、延迟与成本

重排是逐候选计算的任务，k1（送进重排器的候选数）几乎线性地决定这条链路的在线成本，是最值得算清楚的参数。

质量方面的规律是收益递减：k1 太小，相关片段进不了候选池，重排无从下手；k1 增大，池子覆盖率上升，但每加一个候选带来的边际覆盖越来越小。这里不存在普适最优值，建议用“覆盖率驱动”的定法：先在自建评测集上统计不同 k1 下“相关片段至少有一个在池中”的比例（池级 Recall@k1）；再选定一个业务可接受的覆盖目标——例如让 95% 的查询在池子里有可用证据——读出满足目标的 k1；最后实测该 k1 的延迟与成本，超预算就通过缩小窗口或引入轻量粗排来压 k1。

三类配置的性格汇总在下表，具体数值必须以自测为准：

配置倾向 k1 较小 k1 中等 k1 较大
池覆盖率 低，证据常漏 够用 高，长尾问题受益
延迟与算力 友好 可控 与 k1 成正比上升
对重排模型的依赖 弱（没得选） 中 强（靠它筛掉干扰）
适合场景 实时性苛刻 通用问答 延迟宽松、离线批处理

注意区分：k1 是重排输入数，k2 是重排输出数（交给生成的片段数）。k2 通常由提示词预算决定，不改变重排计算成本，主要改变生成侧的 token 开销与“噪声证据挤占注意力”的风险，两者应分开调参。

LLM 参与重排：做法与偏差

把候选片段交给 LLM，让它直接判断相关性甚至输出排序——这条路走得通，但每一段都有明确的坑，适合按用途拆开看。

LLM 重排的三种基本形态。点对点判别（pointwise）：对每个候选单独发一次判断，问法类似“给定查询与该片段，片段能否回答查询”，取模型输出“能/不能”一类标签的概率或文本作为分数，与 monoBERT / monoT5 的“把排序化为单文档相关性分类”思路同构。成对比较（pairwise）：每次给两个候选让模型选更相关的一个，用比赛积分类算法聚合，比较次数随候选数平方增长，只适合很小的 k1。列表式（listwise）：把 k1 个候选编号后一次性给模型，要求直接输出一个排列。2023 年 4 月公开的一组工作（以 ChatGPT 作为重排器的 RankGPT 为代表）验证了这条路的可行性，并给出关键的工程补丁：一次装不下全部候选，于是用长度为 w 的滑动窗口、步长 s 做“集式”重排，多轮窗口传递排列结果，得到近似全局的排列。

已知偏差与对策决定了 LLM 重排能否被信任。位置偏差：模型有把输入靠前的候选继续排在前面的倾向，也就是说候选进入提示词的顺序会污染输出——对策是把候选乱序后再送入，或对同一批候选做多次乱序调用、对排列结果取共识。冗长偏好：较长、语气笃定的片段容易拿到虚高判断。指令遵循的不稳定：温度不为零时排列结果不满足反对称与传递性，聚合算法需要容错。长度与成本：listwise 的输入是 k1 个完整片段，token 开销随 k1 与片段长度相乘增长，滑窗版本还要再乘上窗口数，在线延迟通常不可接受。

因此 2023 年比较务实的定位是把 LLM 重排用在三个地方。其一是离线标注与蒸馏：用 pointwise 或 listwise 方式对评测集、训练对做大规模相关性标注，再拿标注去微调一个小的交叉编码器上线，让 LLM 出知识、小模型出算力。其二是疑难查询的兜底精排：只有当常规链路置信度低时才触发，k1 控制在十几个以内。其三是评测辅助：作为“机器评审”参与对比实验，但它本身也是有偏差的测量工具，需要与人工抽检校准。另外一条现实捷径是托管重排服务：Cohere 在 2023 年 3 月提供的 Rerank API，传入 query、documents 与 top_n 即可返回带相关性分数的排序结果；代价是片段文本要出网，数据合规与网络往返都要纳入评估。

级联排序与服务编排

把前面的部件接成可运维的级联（cascade）链路，典型形态如下：

flowchart TD
    A[查询] --> B[向量召回 top-k1]
    A --> C[关键词召回 BM25]
    B --> D[分数融合与归一化]
    C --> D
    D --> E[交叉编码器重排]
    E --> F{重排超时或失败}
    F -- 是 --> G[降级：按召回分数截断]
    F -- 否 --> H[去重与多样性调整]
    G --> H
    H --> I[截取 top-k2 交给生成]

编排层的设计原则有四条。第一，每段有独立的延迟预算与降级路径：重排超时后退回“按融合分数直接截断”是比失败更好的选择，降级应当是默认能力而不是异常处理。第二，候选以标识符贯穿全链路：各段之间只传 doc id 与分数，文本统一按 id 从存储取，避免同一文档出现两个版本。第三，版本信息进响应：每个结果携带“重排器四元组版本 + 召回配置版本”，否则线上出问题无法归因。第四，可观测切面：每段记录输入输出规模的差值，这些计数比任何单条日志都更早暴露问题。

分数融合、归一化与多样性

难点在于不同来源的分数不可比：余弦相似度落在 [-1, 1]，BM25 是无上界的词频型得分，交叉编码器的 logit 又自成一个区间，直接加权求和等于让尺度最大的来源支配结果。做法有三类。第一类是查询内归一化：min-max 或 z-score 把每个来源压到同一区间再加权；这类变换依赖来源候选全集的构成，集合一变归一化结果就变，只适合每个来源都取满 k 个候选的规整情形。第二类是排名型融合，代表是 Reciprocal Rank Fusion（RRF）：文档的融合分是它在各来源排名 r 上的 1/(k + r) 之和（原论文取 k = 60）；它只消费名次，对尺度差异天然免疫，也丢弃了分差信息。第三类是干脆不做分数融合：多来源候选合并成一个大池子直接交给重排器统一裁决——2023 年的重排链路里融合的存在感正是在下降：它只负责“别漏”，排序交给更强的下游。

想把重排分数与新鲜度、权威性等业务先验加权时，同样要先归一化（softmax 或分位数映射）并记录映射方式。单调变换不改变单查询内部的排序，但会改变跨来源加权的结果——先归一化再加权与先加权再归一化是两个不同的算法。

去重针对另一种退化：候选池塞满近似重复——文档多副本、模板化页脚、分块重叠造成的相邻块高度相似、站点互抄。对 RAG 这是实打实的伤害：k2 个位置被同一句话的不同拷贝占满，真正的证据被挤出提示词。

去重放在重排之后、截取 k2 之前，成本三档：完全重复用规范化文本的哈希；近似重复用字符级 shingle（n-gram 集合）的 Jaccard 相似度，超阈值的保留重排分高者，阈值需用标注样本标定；语义级重复复用召回阶段已有的文档向量算余弦，省一次前向。多样性调整的代表是 MMR：每步选“与查询的相关性减去与已选集合最大相似度”加权和最大的候选，权重 λ 控制倾斜，λ 取 1 即退化为纯相关性排序；RAG 常从 0.5 到 0.9 起步，最终以端到端评测为准。代价是多样性与单点相关性此消彼长，nDCG 可能略降而答案质量上升，评测必须看最终列表。

评测：重排前后的对比方法

重排环节的评测目标不是“这个模型排得好不好”，而是“加上或换掉这一步重排，链路变好了多少，变化能否归因到重排本身”；embedding 模型本身的评测属于另一篇评测文章的范围。

方法上是严格的对照实验：固定召回配置与候选池，只改变池内次序。对每个查询取同一份 k1 候选，分别按“融合分数排序”与“重排分数排序”生成两个 top-k2 列表，在同一份标注上计算指标。Recall@k2 衡量重排的挑选能力，其天花板就是池级 Recall@k1——若重排前后没有差距，多半是召回没捞到，该修召回而不是调重排；MRR 看第一个相关证据被推到多前，对只喂两三个片段的短提示场景尤其敏感；nDCG@k2 在带分级相关性（如 0/1/2/3 四档）时最能反映“好的在前、次好的次前”。下文是重排评测特有的两点。

第一点：标注必须覆盖重排可能翻上来的区域。若标注只来自旧链路的 top 结果，重排新提拔的候选全部按“未标注=不相关”计，nDCG 会系统性惩罚新链路——这是重排评测最典型的陷阱。解法是池化标注（pooling）：用多种召回（向量、BM25、不同 embedding 版本）与多种重排各出一个 top-x 列表，合并去重后送标；标注员对“查询-片段”对独立打分，不做比较排序，避免被列表顺序锚定。未进入任何池的文档仍按 0 计，跨系统比较必须用同一份池化标注。

第二点：比较要成对且冻结其他变量。重排器四元组、k1、k2、融合权重、分块全部固定，只切换排序来源；逐查询计算差值再检验，比看总体平均分稳定。回归门槛也按这个粒度定：新版本上线前，在冻结评测集上要求整体指标不降，且“原列表首条相关而新列表首条不相关”的查询占比不超过发布单里事先约定并记录在案的阈值。

规模上，重排环节的自建标注集不必追逐公开榜单的量级：数百到数千条真实业务查询、带池化分级标注的样本，对迭代的价值远高于在无关分布的公开数据上跑分。离线 nDCG 的提升只是获得上线资格，线上阶段以第九节的灰度指标为最终裁判。

线上灰度与延迟监控

重排器的任何改动——换模型、改模板、调 max_length、换池化方式、动 k1——都是一次发布，要走完整灰度，因为它同时改变质量分布与延迟分布。

推进顺序是影子流量、小流量灰度、放量三步。影子阶段把生产查询复制一份打到新版本，只记录不返回，对比两版本 top-k2 的重合度、分数分布位移与实测延迟差，最适合验证“输入构造改动是否只是形式变化”。灰度阶段按查询维度哈希分流而不是按用户，每个台阶观察足够长的时间窗再放量。回滚条件——触发指标、阈值与自动回滚动作——在发布单里事先写明，而不是等值班同学现场判断。

监控上要单独盯四组信号。延迟：除端到端分位数外必须分段计时，召回、重排、生成各有 P50/P95/P99，否则“整体变慢”无从归因；重排段再细分批队列等待与推理时间，等待飙升通常是凑批容量不足而不是模型变慢。稳定性：降级触发率（超时回退到召回顺序的比例）是最重要的护栏指标，持续攀升往往先于用户投诉。分布：记录每查询重排分数统计量（最大值、首尾差、进入 k2 的最低分）随时间的漂移，固定版本下的漂移通常指向语料或查询分布变化。质量：把采纳率、点踩率与引用点击按链路版本切开统计；重排的线上收益大多只能通过“触发降级的流量与正常流量”的对照间接估计，对此要有预期。

最后是可回放的决策日志：每个查询保留候选 id 列表、各段分数与版本四元组，服务坏 case 归因、离线重放评测与灰度对照，存储上按采样保存以控制成本。

部署要点：批处理、缓存与 GPU

自建交叉编码器的部署矛盾很集中：单条查询要算几十上百个短前向。解法主要在三处。

批处理是第一杠杆。同一查询的多个候选与多个窗口天然构成批量结构，务必合成一个 batch；服务层面再用动态批处理（dynamic batching）把不同请求凑在一起：设短暂的最大等待窗口与按 token 总量封顶的凑批规则，GPU 利用率与尾延迟都会明显改善——上限按 token 数而不是条数设，是为了让显存峰值可控。第二是控制序列长度：候选按长度排序、窗口切到上限以内、padding 对齐到常用桶，都能减少无效计算。第三是量化与图优化：2023 年把这类模型导出为 ONNX 并在 CPU 上运行已经成熟，MiniLM 这类层数少、体积小的蒸馏交叉编码器在中低并发的内部知识库场景常常不值得配 GPU；fp16 与算子融合则是 GPU 路径的常规操作。容量规划用一条公式打底：峰值 QPS × k1 × 平均窗口 token 数 ≈ 所需 token 吞吐，再对照单卡自测吞吐折算实例数。

缓存要先算命中率再做。候选级缓存的键是（查询, 文档）对，自然流量里同一查询命中同一文档的机会不多，直接做 pair 级缓存通常不划算。更实用的三层是：其一，对归一化后的查询（去空格、小写化、纠错）缓存整个重排结果，FAQ 类场景命中率可观，TTL 要显著小于语料更新周期并绑定语料版本号失效；其二，缓存召回候选，短窗口内复用同一查询的向量检索结果、重排照常执行，质量不受损还能削平召回服务尖峰；其三，对离线任务（批量标注、蒸馏数据生成）做全量 pair 缓存。托管 API 的响应可按前两层思路缓存，但网络往返与数据出网要先过合规评估。

GPU 资源管理有两条例行手册级经验：重排与生成任务对显存和凑批策略的需求完全不同，同机共享一张卡时要给重排设独立批队列与并发闸门，避免被大 batch 生成任务饿死；模型版本以“制品 + 四元组”登记，同一进程内禁止混用两个检查点。向量检索服务本身的部署与扩容不在本文范围——重排段与召回段是两个独立扩容的部件，容量评审时要分开谈。

小结

两阶段检索的本质是把“扫得动”和“排得准”分开：双塔召回负责覆盖率，其 Recall@k1 是一切下游指标的上限；重排负责把池内的正确证据提前，交叉编码器靠查询感知的全文交互获得这种能力。工程上最要紧的四个决定是：输入构造（截断与滑窗池化方式定义了分数的含义）、k1（用池覆盖率驱动，而不是抄别人的数字）、链路次序（融合→重排→去重→截取，降级有兜底）、可归因的评测（池化标注 + 冻结变量的成对对照）。LLM 参与重排在 2023 年更适合做离线标注与疑难兜底，在线主力仍是小尺寸交叉编码器，必要时用托管 rerank API 换运维成本。重排的每一次参数改动都是发布：版本四元组进响应、灰度看降级触发率、监控分段计时，做到这些，重排才会从“玄学调参”变成可以持续迭代的质量部件。
