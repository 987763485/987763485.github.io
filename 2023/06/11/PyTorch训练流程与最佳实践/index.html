PyTorch 训练流程与最佳实践

如果你已经理解了张量与自动求导这些基础概念，却在真正上手训练任务时依然拼不出一个可靠的训练脚本，那么欠缺的往往不是概念而是流程。本文以 PyTorch 2.0 为基准，把一次完整训练从数据加载到断点续训的工程细节串起来，涉及混合精度、梯度累积、检查点、分布式概览等实践主题。基础概念本篇不再重复，适合已经具备 PyTorch 入门知识、准备承担真实训练任务的读者。

一次训练的骨架

无论后面的技巧怎么变化，一次训练都可以映射到同一副骨架：数据集、模型、损失函数、优化器、训练循环、验证、保存。先看一个 epoch 的执行顺序：

    E --> F[backward 反向传播]

    H -- 是 --> I[验证集评估]

DataLoader 与数据管线

训练变慢时，先别急着怀疑模型，先看数据。最典型的症状是 GPU 利用率反复跌到谷底——算力在等数据。DataLoader 的职责，是把“读盘、解码、增强”从主线程的串行操作变成多 worker 的流水线：

参数不是越大越好。num_workers 开得过多，进程间会争抢磁盘随机 IO 与内存，吞吐反而下降；pin_memory 只在配合 non_blocking=True 拷贝时才有意义。判断瓶颈的方法很朴素：nvidia-smi 看利用率曲线，或利用 torch.profiler 区分时间花在数据侧还是计算侧。工程上收益最大的通常不是调参数，而是改造数据本身——把耗时的图像解码、分词等预处理离线成中间格式缓存下来，让 __getitem__ 尽量只做轻量的读取与增强；也不要在 __getitem__ 里建立数据库连接或做跨网络请求。

混合精度训练

默认的 fp32 训练并没有把硬件潜力用满：矩阵乘法在张量核心上以半精度执行效率更高，而且 fp16 的参数量与激活占用相对 fp32 直接减半，同样的卡能塞下更大的模型和批次。问题在于 fp16 的表示范围窄，小梯度容易下溢成零，所以 PyTorch 用 autocast 加 GradScaler 的组合来解决：前者在算子层面自动选择精度，后者把损失放大后再反向，更新前再缩回去。

写法上有几个坑。要做梯度裁剪，必须先 scaler.unscale_(optimizer)，否则裁剪的是放大后的梯度，阈值形同虚设。scaler.step 内部会检测到 inf/NaN 并自动跳过本次更新，所以不能省略 scaler.update()，两者要成对出现。数据类型上，fp16 配 GradScaler 是稳妥默认；如果硬件较新，bf16 的动态范围与 fp32 相当，通常可以不用缩放，但对设备有要求，换 dtype 前先在目标机器上验证。验证阶段同样可以套 autocast 来省显存。

梯度累积与大等效批次

批次越大，梯度估计越稳、硬件利用率越高，但显存占用也随批次近似线性增长，往往先撞上的是显存墙而不是需求本身。梯度累积的思路是：用多个小批次（micro-batch）连续做前向与反向，梯度在参数上自然累加，攒够若干步再执行一次优化器更新，从而用小显存模拟出大批次。

注意损失要除以累积步数，保证累加后的梯度量级与直接算大批次一致。有几个局限要心里有数：其一，BatchNorm 的均值方差统计量仍然只在每个 micro-batch 上计算，和真正的大批次并不等价，必要时可换用 GroupNorm 等替代；其二，等效批次变大后学习率通常需要同步放大，常见做法是按线性比例粗略上调再配合 warmup，不要沿用原批次的小学习率；其三，在 DDP 下每个 micro-batch 都会触发一次梯度同步，通信开销不小，可以用 model.no_sync() 上下文包住除最后一步以外的累积，只在末次同步。末尾没凑满的残余步要么丢弃要么单独结算，注意各条路径行为一致。

学习率调度与 warmup

学习率是训练超参里最敏感的一个，而“什么时候调、怎么调”与“调多少”同等重要。固定学习率训到后期往往在最优解附近震荡，收敛变慢；直接上衰减又可能在初期把训练带偏。实践中广泛使用的配方是线性 warmup 加余弦衰减：开头一小段把学习率从零线性抬升到目标值，之后按余弦曲线平滑降到接近零。

warmup 的道理在于训练初期参数是随机的，Adam 类优化器的二阶矩估计也还没建立起来，此时就施加满额学习率容易让早期梯度方向被噪声主导，甚至直接发散；先用小步长“热车”可以显著降低这种风险。

调度按迭代步推进而不是按 epoch，步数要在训练开始前根据数据集大小与累积步数换算清楚，这是做总步数预算时最容易算错的地方。调用顺序上要遵守 PyTorch 的约定：scheduler.step() 放在 optimizer.step() 之后，先调会有警告且第一步行为不一致。LambdaLR 返回的是相对倍率，基准学习率仍以优化器构造时传入的为准，日志里记录当前学习率时从 optimizer.param_groups 读，不要自己再算一遍。多个参数组会被同一个 lambda 缩放，需要差异化倍率时再分组处理。

检查点与断点续训

只做推理的话保存模型权重就够了，但要做“断了能接着训”的检查点，需要保存的是整个训练状态：模型参数、优化器动量等状态、调度器状态、GradScaler 内部计数、当前 epoch 与全局步数，以及各处的随机数发生器状态。少恢复任何一项，续训出来的曲线都可能和一次跑完对不上。

保存节奏上，短训练按 epoch 存即可；数据量大、一个 epoch 要跑很多天的长训练，应按全局步数间隔保存，否则一次硬件故障损失的是整个 epoch 的工作量。除周期性检查点外，通常再维护一份按验证指标挑选的“最优模型”，并把指标值一并记下，避免事后对不上号。恢复时用 load_state_dict 逐项载回，并把循环起点设为保存时的 epoch 与步数。原子写入与“推理导出用干净的 state_dict、训练检查点用完整字典”这两条纪律，能避免大多数事故。若使用 IterableDataset 流式读数据，其读取位置默认不在检查点里，续训会从头读数，需要自己在数据集侧记录偏移。

可复现性与显存控制

让训练可复现

只调一次 torch.manual_seed 是得不到可复现结果的。数据侧，DataLoader 的 worker 各自持有独立的随机数发生器，shuffle 的顺序与增强采样的随机性都依赖它们；算子侧，部分 CUDA 核函数为了吞吐默认走非确定路径，同一份代码两次运行可能逐位不同。追求严格复现的组合拳是：入口处统一设置 torch.manual_seed 与 CUDA 种子，开启 torch.use_deterministic_algorithms(True) 让非确定算子换成确定实现或干脆报错，并把 cudnn 切换为确定性的算法选择；同时需设置 CUBLAS_WORKSPACE_CONFIG 环境变量，否则部分运算在确定性模式下会直接抛错。代价是某些算子失去快速路径、速度下降，因此现实中的建议是：调试与消融对比时严格复现，生产长跑只求“统计意义上可复现”，不必为逐位一致牺牲吞吐。

显存占用控制

显存不够是训练里最常撞的墙，排查与压缩有固定的先后顺序。先确认没有“漏”：循环里累指标要用标量，中间结果出了作用域就该放手，验证段必须包在 torch.no_grad() 或 torch.inference_mode() 里，否则验证也会建图。再动结构性手段：开启混合精度、减小 micro-batch 并用梯度累积维持等效批次、对深层网络的激活做梯度检查点（torch.utils.checkpoint，用重算换存储）、冻结暂不需要更新的子网络并把其参数 requires_grad_(False)、换用状态更省的优化器。要澄清一个常见误解：torch.cuda.empty_cache() 只是把缓存池里空闲的段归还给驱动，它治不了“张量被引用没释放”这类真泄漏，频繁调用反而会因为反复申请释放拖慢训练。定位大户可在程序退出时打印峰值分配报告，占用无非激活、参数与优化器状态三块，压哪一块取决于模型形状。

分布式训练概览

单卡跑到瓶颈后，最常用的是数据并行。DDP（DistributedDataParallel）的模型很直白：每张卡持有完整的模型与优化器状态副本，一个批次被切给各卡分别前向反向，backward 结束时通过 all-reduce 把梯度求和平均，再各自同步更新。它的扩展效率好、改动小，是多卡训练的默认选择；限制也恰恰来自“完整副本”——单卡必须装得下整个模型的参数、梯度与优化器状态。

FSDP（Fully Sharded Data Parallel）则走向另一个极端：参数、梯度与优化器状态都按分片摊在所有卡上，前向算到哪一层才临时把那一层的完整参数聚合过来，算完即弃。这让总显存装得下的大模型成为可能，代价是更复杂的通信与工程细节。在 2.0 里，FSDP 已在 torch.distributed.fsdp 下以稳定 API 提供。两者的定位一句话概括：模型放得进单卡就用 DDP，放不进再考虑 FSDP。

配套习惯有几条：分桶必须用 DistributedSampler 而不是 shuffle=True，否则各卡读到重复数据；日志、保存检查点这类副作用只在 rank 0 上做，DDP 下各副本参数一致存谁都一样，但多进程同时写同一个文件会互相踩；全局步数的语义要统一，进度条与学习率调度都按“所有卡合计的批次数”来算。落地前建议先在两卡小环境把正确性与恢复流程验证通过。

日志、指标与 torch.compile

训练要看得见

一次训练至少应该留下这些记录：训练与验证的损失曲线、当前学习率、吞吐量（每秒处理样本数）、显存峰值占用。曲线用 TensorBoard 的 SummaryWriter 落盘最省事，写标量时以全局步数为横轴而不是 epoch，这样改过批次大小或累积步数后曲线仍然可比。指标层面的教训是：损失下降不等于模型变好，最终要按任务选定准确率、AUC 等业务指标在验证集上定期评估。除了可视化工具，建议把每个评估点的指标同时以 JSON 行的形式追加到日志文件里，方便训练结束后离线聚合与多次实验对比；日志行带上时间戳、步数与配置摘要，出问题回溯时才知道当时的运行环境是什么。

torch.compile 初现

2023 年 3 月发布的 PyTorch 2.0 带来的最大变化是 torch.compile：通过 torch._dynamo 从 Python 字节码层面捕获计算图，再交给编译后端生成优化后的内核，主要目标是消解 Python 侧的调度开销。写作本文时它刚推出一个季度，生态还在适配期，要有清醒预期：首次运行有一次性的编译冷启动时间；模型里存在数据依赖控制、不支持的算子等情况会触发图断裂，回落到逐算子执行；动态形状的处理仍偏早期，变长输入场景要多验证。稳妥的用法是在已经跑通的管线上只加一行 model = torch.compile(model)，先对齐数值正确性，再对比吞吐与收敛曲线，确认可用后再进入生产配置，而不是在实验代码里一上来就依赖它。它值得列入观察清单，但本文的骨架流程不建立在它之上。

小结

PyTorch 训练的流程可以浓缩为一副稳定的骨架，混合精度、梯度累积、调度器、分布式都是往骨架上做加法，加之前要先把骨架跑通、把数据管线的瓶颈排掉。工程上最值得沉淀的是三类纪律：训练状态要完整可恢复，检查点连同优化器与随机种子一起存；数字要可归因，日志、指标与配置摘要一一对应；优化要有顺序，先无风险的结构手段，再谈新编译器。把以上内容固化成一份团队内开箱即用的训练模板，下一篇训练任务就能把精力真正花在模型本身。
