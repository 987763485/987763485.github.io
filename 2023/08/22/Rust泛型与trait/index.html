Rust 泛型与 trait

本文属于《Rust 学习路线》第 13/68 篇
上一篇系列目录下一篇

泛型和 trait 是 Rust 抽象机制的两根支柱：前者让同一段逻辑服务于多种类型，后者描述“一个类型能做什么”。真正写出可复用的代码，靠的是把两者组合起来——用 trait bound 约束泛型、用关联类型固定每次实现的产物。本文从语法出发，梳理约束的几种表达、关联类型与泛型参数的本质区别、impl Trait 的适用边界，以及单态化带来的成本模型。适合已经掌握基本语法、准备深入阅读标准库设计的读者。

两个细节值得留意：给泛型类型写方法时，impl 后要重新声明 T，写成 impl<T> Wrapper<T>，尖括号不能省略；Wrapper<i32> 与 Wrapper<String> 是两个互不相干的具化类型，编译器不会因为定义只有一份就允许它们互相传值，泛型参数一旦具化就是类型身份的一部分。

再回头看 larger_of：函数体里写了 a > b，而这个操作只有实现了 PartialOrd 的类型才具备。如果一开始不加任何约束、直接定义 fn larger_of<T>(a: T, b: T)，编译会在函数体内报错，提示运算符不适用于 T。根源在于：泛型意味着任何类型都可能流进来，而函数体只敢做任何类型都支持的操作。想放宽可用操作的集合，就必须把要求显式声明——给类型参数加 trait bound，告诉编译器“我只接受实现了这些 trait 的类型”。约束写在哪、怎么写，是下一节的主题。

三种写法可以混用，选择上的经验法则是：约束短且少时内联，一旦类型参数多于一个、每个都带约束，或者约束本身变复杂，就应当移到 where。复杂约束指的是这类情形：

为什么复杂约束要放到 where？首先是排版：内联写法会把 T: Iterator, T::Item: Display 一起挤进函数名旁边的尖括号里，参数列表被推到很远的位置，签名几乎没法读；而 T::Item: Display 这种针对关联类型的嵌套约束本身就长，放进尖括号更难解析。where 子句一行一条约束，独立成行，增删和审阅都方便；rustc 的风格指南同样建议约束较多时统一使用 where。还有一点与后文相关：无论约束写在哪，校验都发生在泛型被具化的调用处，这与单态化机制有关，留到那里一并说明。

关联类型与泛型参数的本质区别

trait 里经常出现一个关联类型，最典型的是 Iterator 的 Item。一个自然的疑问是：为什么它不写成泛型参数 Iterator<T>？两者都能把“产出什么元素”表达出来，差别在于同一个类型能否对同一 trait 做多次实现。先看假想的泛型参数版本：

Iterator<Item = u32> 这种写法是为关联类型指定取值的语法糖，等价于 T: Iterator, T::Item = u32，日常代码里大量出现，值得认识。另外，关联类型支持默认值（如 type Item = u32），但默认值在实现选择场景下有被忽略的风险，标准库基本不用，日常设计建议强迫实现方显式写出。

与关联类型默认值对称，泛型参数也能提供默认值，让“最常见的具化”不必每次手写：

Add<Rhs = Self> 解决的场景非常直观：a + b 绝大多数发生在同类型之间，实现方写 impl Add for Point 即可，不必每次重复 Add<Point> for Point；而要支持 Point + i32 这类混合运算，再显式写 impl Add<i32> for Point，两种实现互不冲突——这正好用上前一节说的“泛型参数允许多次实现”。结构体的默认参数则纯粹为了减少样板：默认值只是书写便利，Registry 与完全展开的写法是同一个类型。

需要注意两个坑：函数与方法的泛型参数不支持默认值，写 fn f<T = i32>(x: T) 会被编译器拒绝，因为调用处本就能从实参推断出 T，默认值没有介入的机会；默认值只影响“省略时填什么”，不放松约束检查，带 bound 的方法仍按具体具化类型逐一校验。

这个例子揭示了它最大的意义：filter 产生的适配器类型名字冗长且属于实现细节，写显式返回类型既难看又把手脚伸进库的内部；impl Iterator 让你公开能力、隐藏类型。但它有明确的适用边界，按 1.71 的口径逐条看：其一，函数只能返回一种具体类型，两个分支返回不同的迭代器组合会直接编译失败——真要按条件返回不同类型，只能装箱成 Box<dyn Iterator<Item = u32>> 做类型擦除，那进入动态分发领域，对象安全与 vtable 的讨论在 trait 对象那篇深入文章里。其二，返回 impl Trait 的函数内部不能递归调用自身（类型定义会循环）。其三，trait 的方法签名里不能使用 impl Trait 作为参数或返回类型——无论哪个位置，trait 定义内的 impl Trait 在此前的版本中都不被允许，这项能力在本文写作时尚未进入稳定版，涉及 trait 泛型方法时要老老实实写类型参数。

一句话概括：参数位是泛型的语法糖，适合“不关心名字的一次性约束”；返回值位是类型封装工具，适合“隐藏适配器、闭包等写不出名的具体类型”，但只承诺单一类型。

单态化与零成本抽象

泛型代码最终以什么形态运行？Rust 的答案是单态化（monomorphization）：编译器不为泛型生成一份“通用代码”，而是为程序里实际用到的每一种具化生成一份专用机器码。larger_of 被 i32 和 f64 各调用一次，编译产物里就有两个特化版本，各自内嵌对应类型的比较与拷贝指令：

flowchart TD
    A[泛型函数 larger_of] --> B[编译器单态化]
    B --> C[版本一: T = i32]
    B --> D[版本二: T = f64]
    C --> E[直接生成整数比较指令]
    D --> F[直接生成浮点比较指令]

没有运行时类型查询，没有装箱拆箱，没有通过 vtable 的间接跳转——泛型调用与手写两份专用函数的产物基本一致。这就是“零成本抽象”在泛型上的体现：你不为抽象本身付运行时代价，代价转移到了别处。第一份成本是编译期：具化的种类越多，生成的函数副本越多，优化与链接的工作量随之上升，二进制体积也会膨胀。第二份成本是错误信息的错位：bound 的校验推迟到具化点，于是 “the trait bound … is not satisfied” 经常报在调用行而不是泛型定义处，读报错时先想清楚这一层；具体报错样例与修法参见编译错误速查那篇，不在本文展开。

实践建议是克制而非回避：放心用泛型组织通用逻辑，但别把只在单一类型上调用的大段代码写成泛型，也别让过深的嵌套把实例化数量与报错复杂度一起推高。性能疑义交给基准测试，不凭感觉在静态与动态之间摇摆。

Sized 约束与 ?Sized

泛型参数还背着一条你未必注意到的隐式约束：T: Sized。编译器要求类型参数在编译期有确定的大小，否则栈上布局与移动语义都无从谈起。于是 i32、String、[i32; 4] 都能作为 T 传入，而 str、[i32] 这类不定长类型不能直接按值传——它们只能以 &str、Box<[i32]> 等指针形式存在。

这条默认约束在写“接收任意引用的泛型”时会变得碍事。分清两件事：Wrapper<&str> 是合法的，因为约束加在 T 上，而 &str 本身是定长的胖指针。真正需要放开限制的场景，是希望 T 自己就可以是不定长类型，例如把 str 装进 Box<T>：

?Sized 是 Rust 里独一份的特殊 bound：它不是“要求实现某个名为 Sized 的 trait”，而是撤销隐式的 Sized 要求，语法上也没有强制“必须不定长”的反向写法。由于不定长值无法直接落栈，?Sized 几乎总是与 Box、&、Rc 一起出现；dyn Trait 同样是不定长类型，尺寸信息由胖指针携带，这又与 trait 对象那篇文章相接。

孤儿规则：扩展他人类型的边界

trait bound 打开了泛型的能力空间，但不是所有想要的组合都能合法拼接。Rust 用孤儿规则（orphan rule）限制 trait 实现的位置：写 impl Trait for Type 时，trait 和目标类型之中至少要有一个来自当前 crate。因此 impl Display for MyType（类型是本地的）合法，impl MyTrait for Vec<u8>（trait 是本地的）也合法；但若你在自己的 crate 里给第三方类型实现第三方 trait——比如给 Vec<别的crate的T> 实现 Display——编译器会拒绝，这是没有主人的“孤儿实现”。

限制的存在理由是类型一致性：若两个互不相干的 crate 都能给同一类型实现同一 trait，链接到一起时 a + b 到底走哪份实现无从裁决，泛型代码的 bound 解析也会随之歧义化。对泛型写作者的直接影响是：你无法替别人补全“让它们的类型满足你的 bound”这一环。常规的出路是 newtype 包装——用本地元组结构体裹住外部类型，包装类型归你所有，想实现什么 trait 都可以：

小结

泛型与 trait object 的取舍可以压缩成一句话：编译期已知具体类型就用泛型与 trait bound 拿静态分发的零成本抽象，需要把不同类型装进同一容器或跨 crate 边界擦除类型时，才为 dyn Trait 的间接性付费。回到本文的脉络：泛型函数与泛型类型解决“代码写一遍”，trait bound 用内联、where 与 impl 块三种形式解决“能做什么”，复杂约束务必进 where；关联类型与泛型参数的分水岭是“同一 trait 能否多次实现”，产出唯一选关联类型、角色多样选泛型参数；impl Trait 参数位是语法糖、返回值位藏类型但只承诺单一具体类型；单态化把运行时代价换成编译期膨胀与调用处报错；Sized 是泛型参数的默认隐式约束、?Sized 负责撤销；孤儿规则划定了扩展他人类型的边界，newtype 是标准解法。把这七条放在心里，再回头看标准库的 trait 设计，多数选择都有迹可循。
