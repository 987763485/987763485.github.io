Rust 常见编译错误解析

本文属于《Rust 学习路线》第 24/68 篇
上一篇系列目录下一篇

Rust 的编译错误不是惩罚，而是一份写得相当详细的诊断报告。本文不重复所有权、借用、生命周期的原理（那部分见笔者的相关篇目），只做一件事：把日常最容易撞上的报错按“错误族”归档，逐条给出报错文本、触发原因与修法，形成一份速查表。适合刚被 cargo build 挡在门外、想知道下一步该改哪一行的读者。读完应能看懂 rustc 的每一行输出，判断错误属于哪一族，并选出修法。

先学会读 rustc 的报错

rustc 的每条错误都有固定骨架，拆成四段来看会快很多。下面是一段真实输出的骨架：

第一段是标题行 error[E0502]: ...。方括号里的编号是最重要的检索线索：rustc --explain E0502 会打出官方说明，错误索引里的条目稳定，而标题后的具体措辞在不同小版本之间会微调，所以要记的是编号与关键词而不是整句原文。第二段是位置行 --> src/main.rs:4:56，它指向错误暴露的位置，未必是错误产生的位置——借用与生命周期问题的产生点常在前面几十行。第三段是带竖线的代码上下文：波浪线标记当前被指控的代码，短横线配合 immutable borrow occurs here、mutable borrow occurs here、immutable borrow later used here 三类标注把冲突的三方分别指出，阅读顺序是先看最早那一处。第四段是 note 与 help 行：note 解释为什么这么判，help 给出可尝试的改法，有时还附带一段可粘贴的代码骨架。

还有一类尾部信息容易忽略：约束不满足时会有 required by a bound 之类的话，指明约束来自哪个函数签名；错误来自宏展开时，位置行下面会多一段展开路径，提示要改的是调用处而不是生成代码。

借用冲突族：E0499、E0502、E0506、E0507

这一族数量最大，几条报错都源自同一条规则：同一时刻要么多个共享借用、要么一个可变借用。差别只在于冲突的借用还活着时你做了什么。下表按关键词速查：

错误码 报错关键词 触发原因 首选修法
E0499 cannot borrow … as mutable more than once at a time 两个可变借用重叠 缩小第一个借用的范围；两个互不重叠的切片用 split_at_mut
E0502 cannot borrow … as mutable because it is also borrowed as immutable 共享借用未结束就开可变借用 先把共享借用的结果算完取出值，再开可变借用
E0506 cannot assign to … because it is borrowed 借出去之后又给原变量赋值 先结束借用，或者改用索引与临时变量
E0505 cannot move out of … because it is borrowed 借用还活着时整体移走宿主变量 把使用借用的语句提前，或改成传引用
E0507 cannot move out of … which is behind a shared reference 想从共享引用背后把值拿走 就地克隆，或把入参换成拥有所有权的类型
E0508 cannot move out of type … , a non-copy array 想从数组里按下标移走单个元素 克隆该元素，或对数组整体 into_iter

最小复现与最常见的两种修法：

修法一：缩小共享借用的范围，把使用它的那句挪到 push 之前。优先选它，因为不改变程序结构：

修法二：用索引代替引用，让“借用”变成“一次性的读取”。Vec、HashMap 遍历中要修改容器时，这条尤其好用；把 for item in &v 换成 for i in 0..v.len()，每次按下标读写，借用就不再横跨整个循环体。修法三是把冲突的两步拆成两个函数，让每个函数只持有一种借用。E0506 在循环里最常见，读报错要看最早那条 ... borrow occurs here 标注指向 for 头还是上一次赋值；同一对象确实读写重叠时，可用 std::mem::take 取空、处理完再放回。E0507 要按宿主的形态分情况：引用背后的值移不出来，就地 clone() 最省事；容器里的元素用 remove() 或 into_iter() 取；Option 里的值则改成 take()，这也是 E0505 的常用出口——先让借用结束，再谈移动。

值被移动后继续使用：E0382 一族

E0382 的标题行有两种常见形态：use of moved value（直接又用了原变量）和 borrow of moved value（用 & 去借已经送出去的值）。位置行指向“第二次使用”的那一行，而上下文里一定会有一条 value moved here 标注在第一次赋值或传参处——修这个错，永远先去看那个更早的位置。

修法按侵入性从小到大排：第一，把函数签名从收 String 改成收 &str，调用处写 consume(&s)，这样根本不发生移动——这是最常见的正解：只读的函数不要收所有权。编译器的 note 也会主动提醒这一点，措辞落在 consider changing this parameter type 一类。第二，调用前 s.clone()，用一次堆分配换取可读性，热路径外可以放心用。第三，若这个类型本来就适合按位复制，为它实现 Copy（要求同时实现 Clone），前提是它不持有堆资源。第四，重组控制流：if 分支里移动了变量、分支外又使用，报错会同时标注移动点与使用点，此时把移动推迟到分支结束以后，或在每个分支里都给出该变量的值。

E0382 在循环里出现时标题不变，但标注会变成 value moved here, in previous iteration of loop，并额外标出 inside of this loop——它说的是每轮迭代都要重新移动同一个变量。解法是让被移走的东西在循环内部构造，或者改成克隆、改成借用。

返回值与生命周期族：E0106、E0515、E0597、E0716

这一族的报错读法与借用族相反：位置行往往不是病根，病根在函数签名或某个临时值上。下面按关键词逐个看。

E0106 的标题是 missing lifetime specifier，出现在签名里有多个引用入参、返回类型又含引用、而编译器无法用省略规则推断的情况。它的 help 会把可选的生命周期组合逐个列出让你选；要回答的问题只是“返回值指向哪个入参的数据”，选定后加标注即可。

E0515 的关键词落在 cannot return reference to local variable 或 to temporary value 上，意思是返回的引用指向了栈帧内部的地址，函数一返回宿主就没了。这是设计问题，加生命周期标注救不了它。三条正规修法：返回所有权（把 &String 换成 String）、返回 &'static 的常量数据、或者让调用方提供存储（签名收 &'a mut String，函数只写入缓冲区）。

E0597 与 E0716 是同一件事的两个时间方向：借用活得比被借的东西长。E0597 的标题是 ... does not live long enough，标注里会同时出现 borrowed value does not live long enough、dropped here while still borrowed 与 borrow later used here 三处，把宿主析构点和使用点夹在两端；修法要么让使用提前，要么让宿主延后析构。E0716 的标题是 temporary value dropped while borrowed，专指借用了一个没名字的临时值，例如 let line = config.read().as_str(); 这种把临时对象的引用往外传的情形，它的 help 会直接建议 consider using a let binding to create a longer lived value。两者的通用修法有三条：把临时值先绑到有名字的变量、把使用它的那句写进同一个表达式（分号之前）、或者调整顺序让借用与使用紧挨在一起。

E0621 是标注放错位置：返回类型引用了某个生命周期，而决定它的那个入参类型上没有标同一个标注，标题会是 explicit lifetime required in the type of ...。它不是让你多写，而是提醒你把标注补到正确的参数上；反过来，随手在不需要标注的位置加 &'a str 也常常引出这一条。

trait bound 不满足：E0277 怎么读

E0277 是所有报错里信息密度最高的一条，标题行固定形态是 the trait bound `X: SomeTrait` is not satisfied，其中反引号里的两半分别是“哪个类型”和“缺哪个约束”。往下读三行就够定位了：紧跟位置的 the trait `Hash` is not implemented for `Key` 说明缺哪个实现；note: required by a bound in ... 指出约束来自哪个签名；help 有时直接给出补法，甚至建议加一个 derive。

按 note 行的来源，E0277 的修法分几种情形。类型确实不该改、约束也合理，那就为它实现 trait，或者在调用处做一次转换（例如函数要 String 而你手上是 &str）。泛型函数里约束写多了，就把它拆到 where 子句并按需精简。约束来自标准库函数（HashMap::new 要求 K: Hash + Eq，println! 要求参数实现 Display）时，一般要改的是类型而不是约束：给自定义结构体实现 Display，或退一步用 {:?} 走 Debug。

同族还有两条常被归到一起的报错。E0599 的关键词是 no method named ... found for ... in the current scope，多半是因为 trait 没进作用域——方法定义在 trait 上，就必须 use 它才能以点号调用；help 会提示 items from traits can only be used if the trait is in scope。E0034 的关键词是 multiple applicable items in scope，父子 trait 或两个 trait 有同名方法时出现，用 Trait::method(&x) 这种全路径形式消除歧义即可。

类型不匹配与转换：E0308 与 From、TryFrom

E0308 的标题行是 mismatched types，位置行下面会给出 expected `Vec<u8>`, found `&[u8]` 这样的对照，还常有一条 note: function defined here 把期望的来源指向某个签名。读它的关键是判断“期望从哪来”：函数签名、let 标注，还是上一个表达式。分支结构里 if 与 else 类型不一致、循环外初始化的变量与循环内赋值类型不一致，都会汇合到 E0308。

转换手段要按“是否可能失败”选，而不是随手写一个。From/Into 是无损且必然成功的转换，String::from(&s)、s.into() 走这条路；TryFrom/TryInto 用于可能失败的窄化，返回 Result，例如把 i64 收进 u8 时写 let b = u8::try_from(v)?;，报错会被它自己的 Error 类型挡住，需要处理；as 只用于内置数值类型之间的显式转换，它会截断高位且不报错，最容易埋 bug。字符串侧的对应关系是 &str 到 String 用 to_string()、to_owned() 或 into()，String 到 &str 用 as_str() 或直接借用。

还有一对兄弟报错值得记住。E0282 与 E0283 的标题都是 type annotations needed，出现在 .collect()、.parse() 这类要靠上下文反推类型的位置，note 行会用 type must be known at this point 指着推不出来的那一侧。修法是把类型补回到能补的地方：变量加标注、collect 写成 collect::<Vec<_>>()、parse 写成 parse::<i32>()。运算符不匹配是它的另一种表现：两个 &str 用 + 相连、没有实现 Add 的结构体相加，报的是 E0369；而 i32 与 f64 混算因为没有对应的 Add 实现，报的反而是 E0277。看到这两类，都是先显式统一类型再运算。

Sized 与 trait 对象：E0038 与 dyn 相关报错

Sized 缺失会以 E0277 的形式出现，标题落在 the size for values of type `str` cannot be known at compilation time，help 里补一句 the trait `Sized` is not implemented for `str` 。触发点有三类：函数参数直接收 str、[T] 这类动态大小类型，局部变量声明成动态大小类型，或把 str 传给默认要求 Sized 的泛型参数。通用修法都是“套一层指针”：&str、Box<str>、Rc<[T]>；要让泛型接受动态大小类型，把 T: Sized 的隐式约束放松成 ?Sized。

E0038 是 trait 对象专属：写 &dyn Trait、Box<dyn Trait> 时，如果这个 trait 不满足对象安全（方法返回 Self、带泛型方法、把 Self 用在参数位置），编译器会拒绝，并用一条 note 把责任指到破坏规则的那个方法定义上——这也是读 E0038 的关键：标题说 trait 不行，位置却告诉你其实是哪个方法不行。修法不是硬标注解，而是重构：把破坏对象安全的方法拆到另一个 trait 里，静态分发仍然用它；或者把返回 Self 改成返回 Box<dyn Trait>；实在需要具体类型时改用枚举做分发。另外在 Rust 2021 下裸写 Box<Error> 不再被接受，help 会提示补 dyn。

? 与返回类型不符：E0277 的组合形态

? 的报错集中在两处。一是所在函数的返回类型不对，标题里会出现 `?` can only be used 一类关键词，说明该函数返回 () 而不是 Result/Option——要么把签名改成 Result，要么就地 match 掉。二是错误类型对不上，此时依然是 E0277，只是缺的 bound 变成 MyError: From<io::Error>：? 会用 From 转换内层错误，而标准库的错误类型之间并没有这条实现。

三条正规修法按侵入性排列：map_err 手工包装（最轻，适合一两处特殊转换）；为聚合错误类型实现 From（适合错误种类稳定的模块，配合 thiserror 这类 derive 库可以省掉样板）；把返回类型放宽成 Box<dyn std::error::Error>（适合上层与 main，标准库已为常见错误类型提供了进入 Box<dyn Error> 的转换）。main 自 1.61 起可以直接返回 Result，因此顶层不必再手写 match。

循环引用与 Drop 相关误区

递归数据结构会给出两个特殊报错。E0072 的关键词是 recursive type ... has infinite size，Node { next: Option<Node> } 这种自包含定义触发它，修法是用 Box<Node> 或 Rc<Node> 把嵌套换成指针。E0509 出现在试图从实现了 Drop 的类型里整体移出字段时，标题包含 cannot move out of type，此时改用 Option 加 take()。

Drop 顺序引发的报错则多为 E0597：局部变量按声明逆序析构，如果被借用者在借用者之前析构，报错的 note 行会写明 dropped here while still borrowed，最快的修法是对调两个变量的声明顺序，或显式 drop(借用)。需要提醒的是 Rc 环不是编译错误：父子互相持有能正常通过编译，泄漏发生在运行期，编译器不报错不代表结构没问题，这类地方要主动把一侧换成 Weak。

小结

本文按族梳理了 rustc 的高频报错：借用冲突看 E0499、E0502、E0506、E0507，移动后使用看 E0382、E0505，返回值与存活期看 E0106、E0515、E0597、E0716，约束与类型看 E0277、E0308、E0282，动态大小与 trait 对象看 E0038 与 Sized 类报错。读报错的固定动作是四步：记住编号、看位置行上下最早出现的那处标注、读 note 找约束来源、按 help 给的方向选最小改动。修这类错误时的优先顺序建议是：缩范围、改借用、加转换，最后才 clone；unsafe 不属于修法，它只是把问题从编译器那里挪到自己身上。速查表会过时，但“编号加关键词”这个检索习惯不会。
