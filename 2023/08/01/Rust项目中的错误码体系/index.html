Rust 项目中的错误码体系

本文属于《Rust 学习路线》第 22/68 篇
上一篇系列目录下一篇

本文讨论一条容易被跳过、却最影响线上协作的链路：一个库函数返回的 StoreError，经过几层折叠，如何变成调用方看到的 {"code": "ORD-ST-3007"}。适合已经写过 Result<T, Box<dyn Error>>、开始对服务对外接口负责的人。读完应该能拿出三样东西：一份错误分层模型、一张错误码表、一个稳定的错误转换器。

为什么要把库错误映射成对外错误码

大多数 Rust 项目的错误代码是这样长起来的。最初 src/error.rs 里只有一个枚举、几个变体，够用。后来加了数据库、上游调用、缓存，变体从 5 个涨到 40 个，中间层又开始用 anyhow::Error 打包上传。到这一步，进程内部的错误表达很丰富，对外接口却只有一种呈现：把某个错误的 Display 字符串塞进响应体的 message 字段。

这种“用文本当契约”的做法迟早爆雷。笔者在库存服务里见过真实例子：下游把超时错误原样写进 500 响应，message 是 connection closed before message completed。前端为了区分提示写了一个按文本包含关系判断的分支。半年后底层连接库升级，文案换了说法，分支静默失效，可重试的瞬时故障被提示成“下单失败，请稍后再试”，用户大量重复提交。文本不是稳定契约：它为人而写，会随依赖版本变化，而调用方的代码恰恰依赖它不变。

错误码解决的第一件事，是给调用方一个可编程分支的枚举值。客户端拿到 ORD-INV-5001 就知道该提示“该规格库存不足”，拿到 ORD-UP-2004 就知道该退避重试。这些分支写在一个字符串常量上，可搜索、可统计、可写进联调文档，而且我们能承诺它三年不变。

第二件事是划清责任边界。一次失败可能涉及五六个组件，调用方只需要一句话：“这件事算谁的、你该做什么”。库存不足属于调用方可修，连接池耗尽属于我方容量问题，对外只给一个“暂不可用”级别的码，不解释是哪个池子。

第三件事是可观测性。日志文本无法稳定聚合，错误码可以：值班看到 ORD-ST-3007 从零突增到每分钟两百次，比看到刷屏的乱串消息有用得多。这部分在第 8 节展开。

错误码也不能由状态码替代。HTTP 状态码有限、颗粒很粗，400 与 422 的边界几乎不可判定；同一个 409 里可能藏着“库存不足”与“这张券已核销”两种完全不同的处置。也别用 code: 0 这种全局大杂烩：所有错误挤在同一个数字上，等于没有分层。

所以本篇的核心命题是：库错误回答“哪里出了什么问题”，对外错误码回答“调用方现在该做什么”。两者隔着几个抽象层，把前者折叠成后者本身就是设计工作。

错误的四层模型

要谈映射，先要谈分层。笔者在项目里用四层，切分依据是一条：这一层的错误，是给谁看的。

领域错误（domain）表示业务规则不成立：库存不足、状态机不允许这次迁移、金额超出限额。它与传输和存储无关，换成命令行程序也依然存在；数量最少但语义最贵，每一个都要能在产品文档里找到对应说明。

应用错误（application）是“一次用例执行失败”的原因集合，也是用例边界的收口层。它把领域错误与基础设施错误归拢成同一种类型，补上只有用例才有的信息：能不能重试、属于哪个 trace、涉及哪个业务对象。它还负责判定责任归属：同一个超时，发生在扣库存那一步与发通知那一步，答复并不相同。

基础设施错误（infrastructure）来自存储、上游 RPC、消息队列、缓存。它是错误发生的现场，首要职责是把底层库的错误作为 source 逐层包好，保留因果链。它不该知道“订单”——StoreError 里出现 order_not_found 这类业务词，说明分层已被污染。

对外协议错误（wire）只存在于进程边界。它是那个 JSON 响应体、那个 gRPC Status、那个错误码字符串与状态码的组合。请求一进进程它就消失，请求一出进程它才出现。

四层的关系是自下而上折叠，而不是互相转换：

flowchart TD
    L[底层库错误 StoreError UpstreamError] --> I[基础设施错误 InfraError]
    I --> A[应用错误 AppError]
    D[领域错误 DomainError] --> A
    A --> W[对外协议错误 WireError]
    W --> R[HTTP 响应体 或 gRPC Status]

从这个图里能读出三条纪律。

其一，折叠只能向上，不能向下。基础设施错误可以在应用层被解释成“服务暂时不可用”，但不能把领域错误降级成一条内部警告、悄悄替用户把库存扣下去。向下解释往往意味着掩盖。

其二，每层只允许紧邻感知下两层。如果 HTTP handler 里出现 match store_err { StoreError::PoolTimeout => ... }，说明协议层越过应用层直接理解存储细节，换一次驱动就要改一遍接口代码。跨层感知是体系腐化的开始。

其三，依赖方向必须单向。领域模块不得引用基础设施的错误类型，基础设施也不得引用领域，能缝合两者的只有应用层。这条纪律由编译器把关：谁 use 了谁的类型，谁就依赖谁。

每一层该携带什么信息

分层之后，第二个问题是每层的错误值里放什么。下表横着看是字段、竖着看是层级，空白表示该层不该有这个字段。

字段 领域错误 应用错误 基础设施错误 对外协议错误
可读消息 有 有 有 面向用户的文案
稳定错误码 有 有 有 唯一对外的那一个
因果链 source 可无 有 必有 无
可重试标志 由码决定 有 有 有
trace 关联 id 无 有 无 有
业务上下文键 有 有 无 视情况
传输状态码 无 无 无 有

下面逐条说明为什么这样分配。

可读消息给人看，不给程序判断。每层保留一句完整、能独立读懂的话，例如 库存行加锁失败，sku=9021。但它不进对外响应体：内部消息里常有表名、主机名、SQL 片段，泄出去是信息暴露。对外给的是由码决定的用户文案。

稳定错误码四层都有，命名空间不同，只有边界那一层的码进响应体。这一点容易被误解成“码只在最后生成”：其实内部有码，日志才能按码聚合，第 8 节的分布监控才成立。

因果链 source 是标准库 Error trait 的内建能力。领域错误往往没有原因，“库存不足”不是哪个底层错误导致的，而是规则判定结果；基础设施错误必然有原因，因为它本身就是对底层错误的包装。

可重试标志回答“客户端再来一次有没有意义”。取值应完全由错误码推导，不能从文本猜。显式放进错误值，是为了让网关、SDK、队列消费者共用同一份判定。

trace 关联 id 只在应用层产生与传播：入站请求头带来就沿用，没带就生成，之后写进日志字段与响应头。领域层不该知道它，否则领域代码就染上了传输上下文。

业务上下文键是结构化的排障线索，如 sku_id、tenant_id、attempt，以字段形式存在而不是拼进消息文本，日志后端才能索引。而传输状态码只在协议层出现，因为只有它知道自己走的是 HTTP 还是 gRPC。

这一节的用法是：评审“加个错误”的改动时按字段提问——码是什么、消息是什么、原因链是谁、能不能重试、上下文键放哪。五个问题答完，错误就设计完了。

错误码的设计原则

有了分层，接下来是给码定规矩。下面五条按重要程度排序，第一条几乎无法挽回，后面四条能靠工具补救。

稳定是第一位属性

一个错误码发出去就成了一份公开契约，约束强度不低于函数签名。原则是：一个码只有一个语义，语义变了就发新码，绝不让同一个码的含义悄悄漂移。

举个会踩的坑。最初 ORD-UP-2004 定义为“上游调用超时”，后来有人加了句“上游返回 5xx 也算”，于是一个码横跨两种处置：超时应退避重试，某些 5xx 却表示请求已处理、重试会造成重复。若当时按语义拆成 2004 与 2005，各自策略都能写清楚。

因此码的增删改要纳入变更评审：新增当作向后兼容的小版本，删除或改语义当作破坏性变更。第 9 节给出具体做法。

用命名空间分段

推荐的结构是三段：{服务}-{子域}-{四位数字}，例如 ORD-INV-1001。服务前缀解决跨团队撞号，子域前缀让日志里一行码就能定位出处，数字段承载类别。

数字段建议这样划分：

号段 类别 谁的问题 调用方典型处置
1xxx 参数与前置校验 调用方 改输入，不重试
2xxx 上游依赖不可用 依赖方 退避后重试
3xxx 存储与基础设施 我方 稍后重试，或降级
4xxx 权限与可见性 调用方身份 换凭据，不重试
5xxx 领域规则不成立 业务状态 换选择或换时间
7xxx 限流与配额 我方容量 按提示时间重试
9xxx 服务端内部缺陷 我方 不重试，带 trace 报障

每个号段内部要预留空洞，不要连着编满：1001 之后跳到 1010，是为了让 1002 到 1009 容纳评审时才想到的同族情形。

不要把内部实现细节编码进码

这里有个容易误读的地方：足够具体才能指导处置，但足够具体不等于暴露实现。标准是——调用方拿到码之后能做的事会不会因此变化；不会，就不该进对外码。

“库存行加锁失败”与“连接池水位达到上限”，调用方的处置完全相同：稍后重试。给它们两个码，除了把内部拓扑告诉外面没有收益。内部码表可以细，对外码表必须粗。

我们的做法是把码表分成“可对外”与“内部专用”两个集合，由转换器把关。ORD-ST-3007（存储不可用）允许出现在响应里；ORD-ST-3012（连接池水位）只在日志与监控里存在，对外折叠成 3007。折叠关系写死在映射表里。

另一类暴露是权限错误：对不存在的资源给 404、对无权的资源给 403，等于把“这个资源存在”泄漏给越权尝试者。这类取舍必须显式写进码表注释。

与 HTTP、gRPC 状态码的映射

状态码与错误码是两层粗细：状态码给网关、SDK、重试库这些通用中间件看，错误码给业务客户端看。规则是允许多个码共享一个状态码，绝不允许一个码对应多个状态码。

错误码类别 HTTP 状态 gRPC 状态 可重试
1xxx 参数校验 400 / 422 INVALID_ARGUMENT 否
4xxx 权限 403 PERMISSION_DENIED 否
4xxx 未认证 401 UNAUTHENTICATED 否
2xxx 上游超时 504 DEADLINE_EXCEEDED 是
2xxx / 3xxx 依赖不可用 503 UNAVAILABLE 是
5xxx 乐观锁冲突 409 ABORTED 是，重试整个事务
5xxx 业务规则不成立 409 FAILED_PRECONDITION 否
7xxx 限流与配额 429 RESOURCE_EXHAUSTED 是，按 Retry-After
9xxx 内部缺陷 500 INTERNAL 谨慎，仅幂等接口

这张表必须存在于代码里而不是文档里：第 5 节的转换器会把它编译成 match，并由测试保证不漂移。

顺带说明，本文只谈 Rust 侧的组织方式，服务框架里 IntoResponse 之类的具体接线属于实现细节，不在这里展开。

把码表当代码管理

三条落地手段：码常量集中定义，不散落在各模块字面量里；加测试断言全表无重复码，把两个人挑了同一个编号挡在 CI 里；新增码同步补文档条目，让码表与接口文档同源。

用 newtype 与 thiserror 组织库错误

原则讲完，落到 Rust 代码。2023 年这一层有两个成熟工具：thiserror（1.0 系列）在库内部定义可匹配的具体错误类型，anyhow 在应用顶层收集错误。分工很明确：可复用的 crate 不要对外返回 anyhow::Error，调用方无法对不透明的错误包做 match，那等于强迫所有人解析文本。

展示文本与码的一致性

最后一条纪律：#[error("...")] 的文案里不要出现错误码。码是结构化字段，由映射表决定；文案给人读。两者混在一起，改文案就改了码。一致性靠测试保证。

panic 与 Result 的分界

错误码体系只对“会被外部看见的错误”有意义，所以必须回答另一个问题：什么情况下根本不该走 Result。

Rust 里 panic! 的语义是程序自身的假设被打破：它终止执行、回溯到线程边界或进程，不参与调用方的分支判断，因此天然无法承载契约。判据不是“严重不严重”，而是“它是否可能由外部世界引起”。

可能由外部引起的一律 Result：网络与磁盘读写、用户输入与外部数据反序列化、上游返回、配置缺失、依赖下线。无论多么“离谱”，都是运维现实的一部分。

配套的几条纪律：

情形 处置 理由
解析用户输入失败 Result，码 1xxx 外部可解释
上游 5xx Result，码 2xxx 外部可解释
配置缺失 Result，启动即失败 不该拖到请求路径
穷尽 match 的漏分支 unreachable! 实现缺陷
数学与状态机不变量 debug_assert!、assert! 违反即 bug
全局单例初始化 允许 expect，仅启动阶段 失败无重试意义

expect 只出现在 main 与初始化路径，是这套体系里少数合理的直接终止：启动阶段失败的信息由运维系统承载，而不是由错误码承载。

还有一个必须提前定下的部署约束。若编译为 panic = "abort"，栈展开被禁用，在请求边界捕获 panic 的兜底写法无法生效。这个选择改变了 9xxx 段的含义：unwind 下是“捕获到的内部缺陷”，abort 下是“进程重启”。

锁中毒、异步任务 panic 后 JoinHandle 返回错误这类回收手段属于并发范畴，本文不展开；只强调一点：这些回收点必须显式生成一个 9xxx 码并打日志，否则可观测性上会出现空洞。

日志级别与错误码的对应关系

日志这一环只有一条中心原则：级别由码决定，不由来源决定。按来源分配会让告警淹没在正常业务失败里；按码段分配，级别就成了码表的一个属性，可以集中评审。

把第 5 节提到的静态码表补全成这样：to_wire 的 match 只负责产出码本身，状态码、重试提示、日志级别、是否告警都从表里查。

收益是消除双份真相。若 match 与这张表各自维护状态码和文案，改一处忘另一处是必然的；现在只有码由 match 决定，第 9 节的灰度也只需动这张表。

级别与告警的建议对应如下。

码段 默认级别 告警 理由
1xxx 参数与校验 info 否 调用方写错，非我方故障
4xxx 权限 warn 否，走安全审计 需留存，不该叫醒值班
5xxx 领域规则 info 否 业务正常结果，只进分析
2xxx 上游依赖 warn 突增才告警 单点超时是常态
3xxx 存储与基础设施 warn 是 影响面通常全局
7xxx 限流与配额 info 否，看趋势 由容量策略决定
9xxx 内部缺陷 error 是，出现即告警 每次都是 bug

第二条纪律是只在折叠点打一次日志。异常语言里常见每层 catch 都打印的习惯，Rust 里不要照搬：? 传播本身不产生日志，否则一个错误经过四层就复现四行，还会让按码计数虚高。中间层要补的是上下文，写进字段，或者干脆不打。

% 打印 Display、? 打印 Debug，tracing 0.1 两个都支持。这里刻意不做 Debug 全展开，因为它会把原因链变成多行文本；把 cause 压成一行比保留美观更重要。

错误码分布与可观测性

有了按码的日志，第二步是把它变成可告警的指标。核心是一个按码与状态打标签的计数器：码表是有限集合，基数可控，这正是相对日志文本的又一次胜利。

告警规则建议三条，它们覆盖的正是错误码体系自身会失效的三种方式。

第一条，9xxx 段出现任何一次即告警。这类码的语义是“内部缺陷”，量级不重要，出现本身就是信号。

第二条，某个码的占比突破阈值。以分钟窗口统计各码占比，它比绝对数量更适合当值班触发条件——绝对量随流量涨跌，占比不会。

第三条，“无码失败”计数。请求既没产生成功响应也没产生任何码，说明映射漏了：可能 panic 未被捕获，也可能新增变体走了兜底臂。这是体系的自检，缺了它，码表失真只会由客户先发现。

还有 SLO 的一条口径：错误预算按对外协议层统计，不按领域错误统计。库存不足、状态不允许是使用服务的正常结果，把它们算进失败率，任何一次促销都会耗尽预算。只有 3xxx、9xxx 这类“我们没履行契约”的码进预算；2xxx 取决于对外承诺有没有包含依赖可用性。

排障动线至此闭环：告警给出码，码在表里查得级别与责任段，trace id 串起一次请求，cause 那一行给出完整因果链。四步里没有一步需要读消息文本。

变更、灰度与客户端兼容

错误码会演进，体系的价值取决于演进时是否不破坏调用方。三种变更要分开处理。

变更类型 兼容性 做法
新增码 兼容 正常发布，同步文档与 SDK 常量
废弃码 条件兼容 双码并行至少两个发布周期，旧码继续发
改语义或删码 破坏性 发新码，旧码保持原语义；只允许在大版本移除

“双码并行”是最实用的一招。假设要把笼统的 ORD-INV-5001 细分成缺货与冻结两种，而客户端 SDK 版本参差，直接改语义会让旧 SDK 给出错误提示。做法是新增 ORD-INV-5006 表示冻结、5001 保持原语义继续发一段时间，等监控显示旧码比例降到阈值以下再收口。

灰度要用码分布当回滚依据。新映射按租户或流量百分比放量时，观察两套规则下各码的占比曲线：如果 ORD-INT-9001 或“无码失败”计数在灰度侧抬头，说明新规则漏了情形进兜底，回滚这张表即可，不必回滚业务代码。

最后是客户端如何处理未知错误码。这几乎必然发生：客户端早于服务端发布，或者服务端新增了码。规则四条，缺一不可。

第一，必须有显式的未知分支，#[non_exhaustive] 能防止 SDK 作者漏写。第二，未知码按“语义未知的失败”处理：不重试、保留原始码上报、展示兜底文案。第三，绝不因为无法识别就把响应当成成功。第四，未知码要计数上报服务端，它是发现文档与实现不一致的通道。

小结

本文把 Rust 服务里的错误拆成四层：领域、应用、基础设施、对外协议，切分依据是“这一层的错误给谁看”。每层信息的分工是——消息给人读，码给程序分支，source 给排障，重试标志给策略，trace id 给跨系统对齐。码以稳定为第一属性，用命名空间分段，只把评审过的子集对外；与状态码的关系是多码对一状态可以、一码对多禁止。代码层面用 thiserror 与 newtype 保证库内错误可匹配、外部错误可收敛。

三条最容易失守的地方：不要在 match 里随手写 _ => 500，把穷尽性留给编译器；只在折叠点打一次日志；把状态码、级别、告警都做成码表的属性，避免两份真相各自漂移。体系的成熟度不在文档多细，而在客户端遇到没见过的码时，行为是否依然可预期。
