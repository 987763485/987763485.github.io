Rust 宏实现 ORM 映射

本文属于《Rust 学习路线》第 29/68 篇
上一篇系列目录下一篇

结构体与数据库表之间的映射代码是典型的”写一遍、抄一百遍”的样板：每个模型都要维护列名清单、行到结构体的解码、结构体到行的编码，改一个字段就得同步动四五处。本文要做的，是把这件事交给一个 derive 过程宏：用户在结构体上写属性，宏在编译期生成全部映射实现，报错直接指向写错的字段。这不是一篇 ORM 库使用教程，而是一次宏作者的完整 walkthrough——从 DSL 设计、syn 解析、quote 生成、错误报告到输出测试，每一步都给出可以照着写的代码。读过本文第 682 篇（声明宏与过程宏总览）的读者可以直接从这里开始；如果你还没写过 proc-macro，本文会尽量把入口处的概念补完整。

从样板代码到 derive 宏

先看没有宏的世界。假设我们有一个用户表和对应的 Rust 结构体，做最朴素的映射大概要写这些东西：一个把查询结果行逐列读进结构体的 from_row 函数，一个把结构体字段摊平成参数列表的 to_values 函数，一份与结构体字段顺序绑定的列名常量，外加主键、可空、忽略字段之类的特殊分支。字段少的时候这不算什么，但一个中型项目里几十张表、每张表十几列，问题就变成了：列名以字符串形式散落在三四个地方，重命名一个字段时编译器无法提醒你漏改了哪处 row.get("user_name")，拼错的列名要到运行时才炸。

我们用编译期代码生成来消除这类漂移。核心思路是把结构体本身当作唯一事实来源（single source of truth）：字段声明了就存在，类型写了就代表列类型，属性补充结构体表达不了的元信息（表名、列名覆盖、主键、忽略）。宏在编译期读取这份声明，生成实现某个 Model trait 的代码，让行与结构体之间的转换从”手写且容易过期”变成”生成且始终一致”。

Rust 的过程宏有三种形态：derive 宏、属性宏、函数式宏。生成映射实现这类需求，derive 宏是自然的选择，理由有三。其一，derive 宏只能”附加”代码、不能改动输入的结构体本身，误用面小；属性宏可以重写被标注的条目，威力大但一旦写错会让用户的类型定义变得面目全非，调试成本高。其二，Model 这个 trait 本身应当定义在一个普通 crate 里，用户 use 进来后 #[derive(Model)] 直接按名字引用，与 serde::Serialize 的用法一致，接口干净。其三，我们需要的是给”任意实现了某种形状的结构体”生成同构的代码，这正是 derive 宏的甜区。代价是 derive 宏拿不到对原字段的改写权，所有配置都必须通过辅助属性（helper attribute）传进来——这就引出了本文的第一件事：设计 DSL。

设计目标 DSL

先写下我们希望用户最终写出来的代码，后面所有实现都是为了让它成立：

设计 DSL 的每一步都是取舍，我们把取过的舍讲清楚。

属性分两层：结构体级的 #[table(...)] 和字段级的 #[column(...)]。这两个名字必须登记在 derive 宏的声明里（#[proc_macro_derive(Model, attributes(table, column))]），否则用户代码会因为”未知属性”被拒绝。登记还有一个容易被忽视的副作用：这两个属性名从此被我们的宏占用，同一个条目上其他宏就不能再使用同名属性，所以名字要取得足够具体，避免与日志、序列化生态的惯用名撞车。

为什么用 name = "user_name" 这样的键值对，而不是位置参数 #[column("user_name")]？因为字段级配置将来一定会长出布尔开关（primary_key、ignore）和带值的选项，键值对形式从一开始就为扩展留好了位置，而且可读性好。位置参数适合参数顺序即语义的函数式宏，不适合配置型属性。

表名与主键的策略也值得单独说。表名允许缺省：不写 #[table] 时，宏把结构体名 User 转成 snake_case 的 users 作为默认表名。这是一个”约定优于配置”的口子，但要记住转换规则一旦发布就是接口的一部分，改它等于破坏兼容。主键支持多个字段标注 primary_key，即复合主键；我们不对”没有主键”报错，因为只读映射的表（日志流水、外部同步表）本来就没有主键，强制要求反而是噪音。

字段名到列名默认同字，即 name 字段对应 name 列——注意这里故意不做 snake_case 转换的强制：用户结构体字段本来就是 snake_case，列名多数时候与之一致，不一致的少数情况用 name = "..." 覆盖即可。规则越少，宏越可预测。

最后是克制。DSL 每多一种表达方式——嵌套属性、条件编译字段、类型级注解——解析与校验的代码就要多长一截，报错面也要同步扩大，否则语法合法但语义荒谬的输入会一路滑到生成的代码里才炸。本文的 DSL 停在”表名、列名、主键、忽略”四个概念为止，接下来的所有实现围绕这四种形态展开。

proc_macro 是编译器自带的 crate，它只提供一个不透明的 TokenStream 类型，连”取第一个 token”都要自己迭代，做 AST 解析基本等于徒手搓词法器。syn 把这件事变成了类型驱动的遍历：parse_macro_input!(input as DeriveInput) 之后，结构体名是 input.ident，字段躺在 input.data 里，属性是 input.attrs 与 field.attrs，全部是强类型。特征 full 打开完整语法集（含表达式解析，本文实际只用到 derive 特征就够，但后续扩展几乎必然要用 full，索性一步到位）；extra-traits 给 AST 节点补上 Debug/PartialEq，为第七节的单元测试埋下伏笔。版本口径方面：截至本文写作时，syn 1.x 仍是生态主流；2.0 虽然已于 2023 年 3 月发布，但属性解析接口从 parse_meta 换成了直接基于记号流的形式，大量在维护的宏 crate 还在迁移途中，我们按 1.x 的 API 写。

quote 负责反向输出。quote! { ... } 宏接受一段”长得像 Rust 代码”的模板，把 #变量 插值点展开成记号流——插值不是字符串替换，而是按 ToTokens trait 递归展开，所以只有实现了 ToTokens 的类型才能进去：syn 的 AST 节点可以，String、Ident、LitStr 可以，Vec<T> 配合 #(#vars),* 的重复语法也可以。用 proc_macro2 而非直接用 proc_macro 的原因很朴素：前者在普通 cargo test 里可用（proc_macro 类型被编译器锁死在宏展开上下文），这让解析与生成逻辑可以在单元测试里直接调用，细节见第七节。

中间表示与手工校验

expand_model 不直接对着 DeriveInput 生成代码，而是先物化出一份中间表示（IR）。这个决定值得解释，因为它是宏项目能不能长期维护的分水岭：DeriveInput 是借用结构的视图，带着生命周期，遍历它做生成会把”用户写了什么语法”和”我们理解出什么语义”两件事搅在一起；IR 则是纯拥有型的、字段名与业务概念对齐的普通 Rust 结构，可以脱离记号流单独构造、单独断言：

这个启发式的盲区要心里有数：type MaybeName = Option<String> 之类的别名在宏展开阶段早已抹平，宏只看语法、不做语义分析，MaybeName 会被当成非可空列处理。这不是实现偷懒，而是过程宏的能力边界，后面坑一节还会回到这里。

运行时契约与生成 trait 实现、构造函数

生成的代码要实现点什么？先把运行时 crate orm_core 的契约立起来。设计上刻意与任何具体数据库驱动解耦——我们的宏只负责”结构体与行列之间的双向映射”，怎么把行取出来是调用方的事：

字段类型到列类型的映射，宏层面只需要一张写进文档的表，值的转换则全部走 FromValue/IntoValue 两个 trait 的实现，由类型系统自动分发：

Rust 字段类型 列类型 NULL 的行为
i32 / i64 INTEGER 拒绝，报 TypeMismatch
f64 DOUBLE PRECISION 拒绝
bool BOOLEAN 拒绝
String TEXT 拒绝
Option<T> 与 T 相同 NULL 解码为 None
chrono::NaiveDateTime TIMESTAMP 拒绝

关键一步是：生成的解码代码不对字段类型做语法匹配（”看起来像 Option 就特殊处理”），而是把字段类型原样塞进 <#ty as FromValue>::from_value(...) 的调用里，让可空性由 trait 选择决定——FromValue 为 Option<T> 准备的实现天然接受 Value::Null。这样连类型别名的盲区都在值转换路径上被消掉了：MaybeName 单拼写上是别名，但 <MaybeName as FromValue> 在选实现时看的是它真正指向 Option<String>，NULL 照样能解。语法启发式只保留给确实需要”展开期就知道”的信息（比如列 DDL 类型）。

下面是生成部分的核心。expand_model 把 IR 摊平成实现代码，逐字段拼 from_row 的结构体字面量——这就是”构造函数”的由来：每个字段的初始化表达式由宏按列名生成，整个结构体一次性构造，缺列、错类型都会落到 ModelError：

这段生成代码里埋了几个有意为之的细节，逐个拆开。第一，所有外部路径都写成 ::orm_core::... 绝对形式，而不是生成一个 use orm_core::...——用户哪怕在自己的模块里 use serde_json::Value，也不会让生成的 ::orm_core::Value 解析到错误的东西。第二，Vec::from([...]) 代替 vec![...]：vec! 是标准库宏，展开位置在用户模块，理论上可被用户的同名宏遮蔽；数组转 Vec 则只需要语言本身。第三，泛型结构体走 split_for_impl，impl<'a, T: Debug> 三段各归其位，不写它的宏在遇到泛型模型时会在编译期直接翻车。第四，LitStr 与 quote_spanned! 都显式携带 span，第六节讲错误定位时会看到它们的价值。第五，is_option 标志在这里其实没参与值转换——它留给将来的 DDL 生成（CREATE TABLE），值转换交给 trait 分发。

顺带一提 INSERT 语句的拼装：有了 TABLE、COLUMNS、to_values 三件套，运行时的通用函数就能产出 INSERT INTO users (id, user_name, ...) VALUES ($1, $2, ...)，列名与值的对齐由生成代码保证，不需要宏再管。宏的职责到”元数据与双向转换”为止，SQL 方言拼写放在运行时更容易换后端。

再看生成代码的形态与可观察性。宏展开后的产物与手写实现完全等价：TABLE、COLUMNS 是编译期内联的常量，from_row 里是一串直接调用的类型转换，没有运行时反射、没有字符串查表，性能上不值得任何优化讨论。真正需要”看见展开结果”的场合是调试生成代码自身的类型错误——这时用 cargo expand（dtolnay 的第三方子命令）把某个模块展开成可读的 Rust 源码，比对着编译错误脑补输出结构高效得多。宏作者应该在开发环境里常备它。

让编译错误指向用户的代码

宏库的质量差距，一半体现在报错上。先看不好的宏长什么样：解析里到处 .unwrap()，#[column(name = 42)] 一进来，用户看到的是一句 proc-macro derive panicked，定位指向 orm_macros/src/expand.rs 的行号——除非用户去读你的源码，否则根本不知道自己哪里写错了，而且一个 panic 还会吞掉同文件里其他合法的 derive 展开。

正确的框架在入口那几行已经给过：expand_model 返回 syn::Result<TokenStream>，失败时 err.to_compile_error() 把 syn::Error 转换成一段 compile_error!("...") 调用，由编译器作为普通类型错误在原始用户 span 上报出，同时不阻断同文件其他条目的编译。写错误的第一原则是：每个 syn::Error::new 的 span 必须来自用户 token。第四节示例里 lit.span()、path.span() 都是这么用的；只有确实没有自然归属（比如”这个宏不支持元组结构体”这种整体性错误）才退到 Span::call_site()，让红线落在 #[derive(Model)] 那一行。配好之后，一次编译的效果是这样的：

第二类错误发生在生成的代码里，比运行时契约更隐蔽：字段类型没实现 FromValue（比如 Vec<u8> 出现在模型里）、ignore 字段的类型没实现 Default。这类错误不是你校验出来的，是编译器在给生成代码做类型检查时报的——默认情况下它们会指向宏展开位置，一屏 expected ..., found ... 却看不出是哪个字段。解法就是上面反复出现的 quote_spanned! { f.span() => ... }：让该字段的初始化表达式整体继承用户字段声明的 span，编译器的诊断会精确落到那一行。syn::Ident::new("...", span) 重建标识符时同理，别随手 Span::call_site()。

两个 2023 年 8 月还绕不开的现实约束。其一，想输出警告而不是错误是做不到的：proc_macro::Diagnostic 仍未稳定，宏作者手里只有”报错”和”沉默”两个选项，所以校验要严格但错误信息要写得像文档——一句”是什么”、一句”怎么改”，最好带一个合法示例。其二，syn::Error 的 span 参数在 proc-macro 环境下受编译器 API 限制，不能跨函数传递来源位置信息（Span::located_at 之类是 nightly 的），复杂宏里”错误挂在哪个 token”要靠生成顺序自己安排，没有运行时机制兜底。

测试宏的输出

宏代码也是代码，但它的”返回值”是一串记号流，测试思路要换一个层次。能这么做的地基在前面已经打好：内部逻辑全部围绕 proc_macro2::TokenStream 与 syn 的 AST 类型编写，expand_model 是个纯粹的”结构体进、记号流出”的函数，proc_macro::TokenStream 只在 lib.rs 入口转手一次。于是单元测试分成三个梯队。

第一梯队测 IR：给定一段源码字符串，断言解析与校验的结果。syn::parse_str 允许我们不经编译器、直接把源码文本变成 DeriveInput：

第二梯队测生成结果。直接把 expand_model 的输出与期望记号流逐字符对比是灾难——to_string() 的空白与括号细节多到没法维护。可行的折中：一是断言”关键子串存在”（生成的代码里出现 "user_id"、出现 impl :: orm_core :: Model for User），二是引入 prettyplease（dtolnay 出品，2021 年即可用）把输出美化成合法 Rust 源码再与 golden 文件对比。我个人通常停在第一种，输出结构稳定后再上 golden。

第三梯队是 trybuild：把宏装进真实编译管线，用整个 .rs 文件做”应该编译通过 / 应该报这些错”的验收。前两个梯队都验证不了诊断信息落在哪个 span，而 span 恰恰是我们第五节投入最多的地方，这一层无可替代：

compile_fail 用例的错误输出保存在同名的 .stderr 黄金文件里，第一次跑用 TRYBUILD=overwrite 环境变量生成，之后每次编译对比。两个注意点：.stderr 里含编译器自己的措辞与排版，rustc 升级可能让”我们没改、测试却红”的情况发生，CI 里要把工具链钉死；黄金文件要人工过一遍再提交，编译器给出的 span 画线丑是常态，接受丑、但位置必须对。

常见坑与能力边界

卫生性（hygiene）。 过程宏生成的标识符默认带”宏内部上下文”：quote! 里手写的临时变量（比如生成的 __row）用户代码引用不到，用户在同一个模块里也叫 __row 也互不干扰——这是好事，宏的私货不会污染用户命名空间。但反过来，当你故意要生成一个用户可见、可调用的名字时，卫生性会变成拦路虎：标识符必须携带 Span::call_site() 才能”逃出”宏上下文。format_ident! 默认就给了 call_site，这也是拼生成函数名（__orm_load_user 这类）要用它而用 Ident::new 时要显式传 span 的原因。derive 宏生成的 impl 块本身不受卫生性影响——trait 与类型走的是路径解析，所以 ::orm_core::Model 这种绝对路径写法永远安全。

span 丢失。 比 hygiene 更常见的事故：所有地方都图省事写 Span::call_site()，结果是生成代码里任何类型错误都笼统地指向 #[derive(Model)] 那一行，四个字段红了用户也不知道是哪个。规则很机械：凡是从用户代码里读出来的东西（Ident、LitStr、Type），原样带着 span 塞回输出；凡是要新建的东西（生成的字符串字面量、临时标识符），显式挑一个语义上最近的 span，如 LitStr::new(&name, field_ident.span())。stable 的 proc_macro2::Span 不能反查行列号，构造时没带对，事后没有任何补救手段。

命名冲突。 除了前面说的绝对路径防遮蔽，还有三个具体的坑。辅助属性名 table、column 一旦被我们的 derive 登记，用户在同一个结构体上就不能再用别家宏的同名属性，起名字时要预判生态；还要小心一个编译器不替你把关的场景——#[derive(Model, Serialize)] 同时存在时，属性会原样传给条目上的每一个 derive，某个宏若对不认识的选项直接报错，两个毫无关系的库就能通过撞名的属性互相打架，所以宏的解析逻辑对”不是我的属性形态”至少要宽容跳过，文档里也要写清占用的属性清单。生成的关联常量 TABLE/COLUMNS 与用户自己手写的同名 inherent 常量并存时，显式 User::TABLE 会优先解析到 inherent 成员，排查”常量值不对”时要想到这里；derive 宏与 trait 同名（都叫 Model）不冲突——一个在宏命名空间、一个在类型命名空间，但 use 时要分别导入，门面 crate 的 re-export 两行都要写。

异步 API 的生成。 如果想在 Model 里加一个 async fn load(...)，2023 年 8 月的 stable 会直接拦住你：trait 里的 async fn 与 -> impl Future 都还未稳定（生态在等编译器侧的工作落地，当时只有 nightly 实验开关）。可行的形状有两种。其一，trait 方法返回装箱 future，生成的 inherent 方法里用 async move 块填内容——async 块本身在 edition 2021 是稳定的：

其二，学 sqlx 0.6 的做法：derive 生成一个持有参数的 builder 结构体，为它实现 std::future::IntoFuture（1.64 起稳定），用户 await 这个结构体即可。两种都不需要”trait 里的 async”，代价是签名可读性下降。这解释了为什么当时主流异步库的派生宏都生成”可以 await 的结构体”而不是 async 方法——不是设计洁癖，是语言约束。

可选字段与默认值。 Option<T> 在 INSERT 场景有语义歧义：字段值是 None，到底该写 NULL 还是该干脆不出现在列清单里、让数据库默认值生效？多数真实表里是后者（带 DEFAULT 的列、自增主键）。处理方式是加一个 #[column(default)] 标记，生成的 to_values 直接跳过该列，让 INSERT 语句的列清单天然不含它；Option 的可空解码逻辑不变。另一个连带问题是被 ignore 的字段：它必须能 Default::default()，否则 from_row 构造不出来。可以校验期就拒绝，但更友好的做法是交给编译器报错并靠 quote_spanned! 把位置钉在字段上——第六节的设计正是为此铺的路。

泛型的边界。 我们给 impl 加了 #impl_generics，但生成的代码要求每个参与映射的字段类型实现 FromValue，对泛型字段 T 而言这个约束不会凭空成立。要么在 IR 阶段给泛型参数注入 trait bound（serde 的 bound 属性就是给用户提供的手动逃生门），要么文档里写明”带泛型的模型需要自己加 where T: FromValue + IntoValue“。我们选了后者——宏替用户猜 bound 是长期维护的噩梦。

panic 与构建稳定性。 第六节反对宏内 .unwrap() 的理由还有一个工程层面的：proc-macro 展开中途 panic 会让增量编译缓存处于不干净的状态，同事可能遇到”改了代码，旧报错还赖在终端里”的幽灵诊断，只能 cargo clean -p 对应 crate 才能恢复。宏内不设防的 unwrap 不只是报错体验问题，它会拖慢整个团队的构建，这是把错误处理做成 Result 贯穿全链路的又一个理由。

与 sqlx、diesel 的既有做法对照

写完自己的一圈，再回头看两个成熟方案，能看清各自的取舍点在哪里（这里只对照设计，用法本文不展开，sqlx 的实践见第 822 篇）。

sqlx 的重心根本不在 derive 上：它的招牌 query! 是函数式宏，把 SQL 字符串当输入，连库（或离线签名文件）在编译期校验查询并合成结果结构体——事实来源是 SQL 与数据库本身，结构体是产物。我们的宏方向恰好相反：事实来源是结构体，SQL 由它派生。query! 路线换来的是”数据库改列名，编译期就报错”的强保证，代价是编译依赖数据库可达性；结构体路线没有这层校验，胜在编译自洽、离线可构建。sqlx 的 #[derive(sqlx::FromRow)] 与我们的 from_row 生成最接近，它也刻意不做列名配置——字段名必须对上列名，对不上就自己写解码，这种”能不加 DSL 就不加”的克制值得所有宏作者学习。

diesel 则把映射拆成了两半：table! 宏与 CLI 从数据库 schema 生成一个模块级的列定义（diesel print-schema 产物），#[derive(Queryable)] 只负责把查询结果的元组按位置对应到结构体字段——没有属性 DSL，位置就是配置。于是 diesel 的列名安全由生成的 schema 代码保证（改列名后重新生成，编译即报），代价是两份事实来源（schema 模块与结构体）需要人工保持一致，Insertable 才用字段名对上列名。对照之下我们的”结构体 + 属性”单一来源方案最省事，但也最依赖宏自身校验的完备性——每一个没校验的 DSL 角落，都是运行时才炸的隐患。

三条路线没有抽象的优劣：数据模型以数据库为准、变更频繁，sqlx 的编译期连库校验无可替代；以 Rust 类型为中心、要离开数据库构建，diesel 的生成 schema 加派生映射最稳；表不多、模式稳定、只想消灭样板，本文这种属性驱动的 derive 宏成本最低。

小结

本文从一个 derive 宏的完整生命周期走了一遍 ORM 映射的代码生成：DSL 要克制，四个概念够用即可；项目要拆开，proc-macro crate 只当入口，运行时契约住在普通 crate；解析要经过中间表示，把语法与语义分层，错误用 combine 攒齐再一次报完；生成代码用绝对路径、Vec::from 数组构造、split_for_impl 带泛型这些手法提高健壮性；诊断信息靠 syn::Error 加用户 span 落回源代码，比任何 README 里的”常见问题”都有效；测试分 IR、记号流子串、trybuild 三层，第三层专管 span 这种前两层看不见的东西。坑的部分请记住三句话：卫生性是屏障也是墙，span 一旦丢失就无法找回，异步生成在 2023 年 8 月仍受 trait 限制、IntoFuture 是当前最干净的绕行。如果你想把它变成能用的库，下一步是给 #[column(default)] 补上 INSERT 分支、加 DDL 生成，然后用 trybuild 把每条校验规则钉住——宏的可靠性，永远是测试用例的数量堆出来的。
