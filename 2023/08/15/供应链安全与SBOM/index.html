供应链安全与 SBOM

当一个开源组件爆出高危漏洞时，团队最难回答的往往不是怎么修补丁，而是”我们受不受影响、哪些系统受影响”。答案不在应用代码里，而在依赖、构建、发布这条供应链上。本文梳理供应链风险的主要类型，讨论 SBOM 解决的问题、主流格式与生成方式，以及制品签名与构建治理如何配合。

供应链风险的主要类型

与传统漏洞不同，供应链攻击的目标不是你的代码，而是你所依赖的一切：第三方包、上游作者、构建机器、镜像仓库。按攻击环节，风险可粗分为四类。

依赖投毒

恶意包伪装成正常依赖进入项目，常见手法是拼写仿冒，以及接管低关注度的包注入恶意代码。2018 年 npm 上的 event-stream 包在维护权转让后被加入针对加密货币钱包的恶意模块，就是此类风险的公开案例。它说明：依赖树的边界是由信任划定的，不是由代码评审划定的。引入一个包，等于引入它的作者与全部间接依赖未来的维护走向。

上游维护者账号被盗

2023 年年中，npm 上若干被广泛引用的日志与颜色输出类包，因维护者账号被劫持而发布了带毒版本，从投毒到清理的窗口极短。公共仓库只验证”这个人有没有发布权限”，不验证”这个版本的代码是否恶意”，合法账号发布的恶意版本同样拦不住。防御可做：发布启用双因素认证、新版本观望几天再升级、关键依赖收敛到白名单源。

构建环节被污染

2020 年 SolarWinds 事件中，攻击者渗透厂商的构建与发布管道，恶意代码随官方安装包分发；2022 年 12 月，LastPass 披露攻击者通过被盗的个人 GitHub 账号访问其开发环境。共同点是攻击者直接走到生产者的工作现场：源码干净、制品已被污染，代码审计完全感知不到。构建环境隔离与凭据治理应当作一等公民，而非”内网机器不用设防”。

镜像与基础环境

企业用内部镜像代理公共仓库的包，用基础镜像构建容器。一旦镜像被投毒，所有使用它的构建同时中招，爆炸半径远大于单个恶意包。操作系统基础层与运行时同样是供应链的一部分：长期使用”latest”基础镜像，等于把每次构建的信任委托给一个你并不盯着的上游。

SBOM 到底解决什么问题

SBOM（软件物料清单）借用制造业的说法，指一件软件所包含组件的清单：组件名、版本、来源与唯一标识、依赖关系，再配上许可证声明等字段。NTIA 早在 2015 年就提出过清单”最小要素”；2021 年后美国政府又把提供 SBOM 写进软件采购要求。

首先要澄清：SBOM 是资产清单，不是漏洞清单。它回答”这个制品里有什么”，不回答”这些东西现在有没有出事”。从清单到”我们受影响吗”还差两步：把组件与漏洞情报源对齐，再判断该组件在本产品中是否真的可被触达——组件被打进镜像，与调用它的功能被启用，是两回事。社区为此发展出 VEX 机制，记录”包含该组件但漏洞不可利用”这类判定；把判定混进清单，它会退化成第二份漏洞库。

拿到清单之后的漏洞分级、修复排期与应急响应，属于开源组件漏洞治理的范畴，本文不展开。本文关心清单本身：怎么建、怎么保真、怎么与签名和构建治理配合。没有可信的清单，后面所有治理动作都建立在猜测之上。

主流格式：CycloneDX 与 SPDX

SBOM 要有用，必须机器可读且生态互认。当前最常遇到的是两家。

CycloneDX 于 2017 年前后诞生于应用安全工作，是 OWASP 生态项目，用 JSON 或 XML 表达，为安全管道设计：支持依赖关系图与清单序列号，安全扩展跟进较快，多数扫描器以它为默认输出格式。

SPDX 最初用于在不同项目间交换许可证信息，现为 Linux 基金会项目，已成为国际标准（ISO/IEC 5962:2021）。它对许可证、版权、文件级标注的支持最完整，适合正式交付与审计归档。

定位差异可概括为：CycloneDX 面向安全自动化，SPDX 面向合规与法律交换。进扫描器与门禁流水线的优先 CycloneDX；交付客户、合规重的场合用 SPDX。工具普遍支持互转，关键是清单格式稳定。

SBOM 的使用场景

清单建起来之后，收益出现在三个场景。

第一，漏洞影响范围的快速判定。2021 年 12 月 Log4Shell 爆发时，各家最痛的问题是”哪些系统带了这个组件”。若每个已交付制品都留有与摘要绑定的 SBOM，按包标识查询存量清单，分钟级即可拉出受影响的产品与版本。清单给出的是”包含”名单而非”受影响”名单，但这一步已把响应速度从周级压到小时级。

第二，许可证核查。许可证字段按产品线聚合，供发布前抽查，高风险许可证出现在对外交付包里时提前拦截；合规判定规则参阅许可证合规的专门文章。

第三，交付要求。外包与受监管客户逐步把”随版本提供 SBOM”写进合同。关键是清单必须与制品摘要一一对应；没有绑定关系的泛化清单缺乏证据效力，反而误导排查。

签名与来源验证

SBOM 解决”有什么”，还要解决”是谁给的、半路有没有被换过”。

制品签名：用 sigstore 生态的 cosign 对镜像或二进制做非对称签名，签名与制品一起存入制品库，消费方部署前用公钥校验：

SBOM 也可作为附件随制品一起签名留存，避免”制品是真的、清单是过期拼凑的”。

透明日志：签名只证明发布时刻，防不住”先发干净版本、被盗后重签”。Rekor 这类仅可追加的公共日志把每次签名事件写入带默克尔证明的记录，任何人可核验某制品何时被谁签过，提供不可抹除的时间线证据。

SLSA：Google 在 2021 年联合社区发起的建设项目，目标是提升构建环节的完整性——要求构建产出可校验的溯源声明，记录输入、命令与输出的因果关系；构建在隔离受控的环境中完成；并以分级思路让组织逐级向”构建平台可信、溯源不可伪造”靠拢。本文只讲目标与框架，等级细则以项目文档为准。

要泼一盆冷水：签名验证的是”发布者身份与传输完整性”，不是”代码善意”。上游账号被盗后发布的恶意版本，照样带着合法签名。来源验证是缩小信任范围的手段，不是消除信任本身。

内部制品库与最小依赖原则

最朴素也最见效的一招，是让所有依赖只从一个受控入口进来。内部制品库承担两个角色：代理公共仓库，缓存并审计流入的包；托管自产制品，管住流出的版本。配套纪律：新包走白名单审查，评估维护状态与间接依赖规模；定期与上游比对制品摘要，防代理层动手脚；对库存量做恶意特征扫描；CI 与本地一律走镜像源，禁止从公网拉包。版本固定同样要立规矩：锁定文件进版本库，构建禁用浮动版本，依赖升级的提交要能逐条审出变更。

每个依赖都是一个他人的、会持续变化的信任决策，依赖数量本身就是攻击面。引入之前先问：标准库能不能做？需求是否真实存在？值不值得为它承担长期盯梢成本？存量也要定期清理——历史上引入、如今无人调用的包不会自己消失，只会在某天替别人背锅。

构建环境隔离与权限

治理要点三句话：环境专用、凭据最小、发布分离。构建器一次性使用、用完即销毁，构建镜像本身纳入 SBOM 管理；凭据只给需要的读取权限，令牌按仓库与时效收窄，杜绝一个机器人账号通吃所有代码库与制品库；”编译打包”与”发布对外”切成两个环节，发布凭据不下放到构建器，发布动作要求复核，重要版本加灰度观察期。

开发者个人环境同样在供应链之内——LastPass 事件的入口就是一个被盗的个人账号。个人设备上的长期密钥、私人仓库复用的公司代码片段，都应按供应链资产纳管：短期凭据、集中签发、定期轮换。

组织流程：谁产出、谁留存、变更怎么办

SBOM 落地要把角色钉死在流程里。一个可运转的最小闭环如下：

flowchart TD
    A[代码与依赖变更] --> B[构建产出制品与SBOM]
    B --> C[清单与制品摘要绑定并签名]
    C --> D[存入内部制品库留存]
    D --> E[漏洞与许可证情报接入]
    E --> F[新漏洞命中存量清单则告警]
    F --> G[触发修复与新一次构建]
    G --> A

产出责任在开发侧：谁构建制品，谁负责让清单与制品同源生成，禁止事后对着线上环境补一份。留存责任在平台侧：清单与制品同库、同生命周期保存，保留期对齐产品维护周期，记录生成时间与方式。消费责任在安全侧：把上游漏洞数据映射到存量清单，输出影响范围，并把含不可达豁免的判定结论回写进系统。

变更处理的硬规则：任何改变制品成分的动作——升级依赖、更换基础镜像、调整打包脚本——都必须让清单随下一次构建重新生成、重新签名、重新留存；旧清单随旧版本退出在用目录，审计记录不删除。清单若与制品演进脱钩，时间一长就退化成没人敢信的摆设。

小结

供应链安全的本质，是把”信任别人”这件事变得可度量、可收缩、可审计。四类风险各有打法，共同前提是你得先知道自己有什么。SBOM 正是这份家底：它是资产清单而非漏洞清单，CycloneDX 管安全自动化，SPDX 管合规交付；生成要靠多路径交叉，并清醒对待传递依赖与二进制识别的局限；再配上制品签名、透明日志与 SLSA 式的构建分级，把内部制品库、最小依赖、构建隔离这些旧纪律立起来，供应链治理才算有了地基。建议先挑一条核心产品线，把”制品与清单绑定”这一件事做扎实。
