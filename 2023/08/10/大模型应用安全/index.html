大模型应用安全

大模型应用的上线速度常常快过安全评审：原型跑通后接上检索、工具与前端，一周就对外提供服务，而这类应用的风险面与传统 Web 服务并不完全重合。本文梳理它特有的风险面，逐项说明形成原理与纵深缓解手段，覆盖提示注入、越权检索、输出处理、工具过度授权、模型供应链、容量与成本、演练组织和日志治理，适合负责这类应用架构与后端的工程师阅读，读完能拿到一份可对照的上线前检查清单。

风险面全景与责任边界

传统 Web 应用的安全模型建立在三个前提上：输入可枚举、权限在代码里判断、执行路径确定。大模型应用把第三个前提抽走了——同样的输入在不同上下文里会产生不同输出，程序接下来做什么，往往由模型用自然语言表达意图、再由编排层执行。控制流入口变成自然语言之后，安全设计要做的第一件事是重新划定信任边界。

责任边界也要划清。模型提供方负责模型本身：语料合规、对齐训练、内置的内容安全能力。应用方负责包装层：提示怎么组装、检索取哪些数据、允许调用哪些工具、输出送到哪里、日志留下什么。从事故分布看，绝大多数问题出在包装层而不是权重文件里，而包装层恰好是我们可以改的部分。

图中每一条边都是一个风险面，缓解思路却是同一条：把跨界的数据当成不可信输入，加一道闸门。上下文里每段文本都归入不可信集合——用户输入、检索到的第三方文档、工具返回结果，甚至模型上一轮自己的输出。这个“信任梯度”是后文所有措施的出发点；反过来，要坚持的可信部分要放到模型影响不到的地方：硬校验在代码里，权限在服务端，确认在人手里。

与相邻主题的分工：接口层认证授权与限流见《API 安全设计与测试》，RAG 数据管道与检索服务化见《RAG 工程化落地》，资产梳理与攻击面枚举见《威胁建模》。本文只谈这类应用特有的部分：模型会被上下文里的文本说服、输出天然不确定、能力由自然语言触发。

合规口径需要先讲清楚。《生成式人工智能服务管理暂行办法》已于 2023 年 7 月 13 日公布、本月 15 日施行，也就是写作时点已公布、即将施行。面向公众提供服务的应用，其安全评估、内容标识、投诉处理与数据留存等要求要在工程实现上提前留出接口，本文只讨论怎么把义务落到系统里，不逐条解读条款。风险分类可参照 OWASP 在 2023 年发布的面向大语言模型应用的风险清单，它按风险所在的位置归组；本文采用类似视角，按落地顺序组织，不逐条对照条目编号与排名。

提示注入：形成原理与纵深缓解

原理：指令与数据共用同一条通道

提示注入之所以是大模型应用特有的问题，根源在于输入通道没有类型。一段上下文里，前一句是我们写下的规则，后一句是外部文本里夹带的祈使句，模型看到的只是同一维度的一串 token——没有编译器帮忙区分哪句是系统规则、哪句是被处理的资料。

更麻烦的是间接注入。攻击者不需要碰到你的接口，只需要把一段文字写进你能检索到的地方，比如一篇会被索引的网页正文或一份上传的附件。检索把它取回来放进上下文，模型读到它，就可能照着它行动。于是注入面不再等于入口接口，而等于全部上下文来源的并集：新增一个数据源，就等于新增一个注入面，必须走同一套准入流程。

第二要接受的现实是：不存在百分之百可靠的前置过滤。既然挡不全，纵深缓解的目标就要重新定义——不是“让模型永远不被说服”，而是“即使被说服，它能造成的最大影响也被压到可接受范围”。差距来自权限、确认和输出处理，不来自提示词写得更长。工程上有两条识别办法：把每次工具调用追回到它由显式业务分支触发、还是由模型自由生成触发，后者占比越高影响面越大；给上下文各段文本按来源分级，低可信来源参与决定的动作一律走更严格的闸门。

缓解一：指令与数据分离

分离的做法不是“在提示里更郑重地写一遍规则”，而是尽量用结构与代码替代自然语言约定。

  • 用消息角色而不是字符串拼接。系统规则放在独立的 system 字段，用户输入放在 user，工具结果作为单独的角色回填；把全部内容拼成一个自由文本块交给补全接口，等于自己拆掉唯一的分隔手段。
  • 外来内容先降维。第三方文本不要原样进上下文，先抽取成受约束的结构化字段（标题、时间、编号、有限长度正文），字段要有白名单与类型校验——抽取这一步本身也可能被影响。
  • 硬校验下沉到代码。不能越过的红线写在编排层：允许的表、主机、语句类型、金额上限、是否可逆。提示里的“请务必遵守”是尽力而为，代码里的判断才是边界。
  • 会话内规则不可由模型自改。模型能写入的“记忆”或“配置”字段都可能成为持久化的注入载体，模型自行总结的内容不得进入权限相关的判断。
  • 输出同样按输入处理。回答不是我们自己程序的返回值，动作之前要校验、出口之处要转义、执行之时要降权，细节见后文输出处理一节。

提示模板与变量的版本管理见《大模型提示词管理》与《提示词版本化管理》；本文关心安全边界：模板可以演进，但“哪部分由代码常量提供、哪部分由外部文本提供”这条线要守住。

缓解二：二次确认与人工闸门

对不可逆或跨信任边界的动作（转账、删除、发消息给第三方、修改线上配置），无论提示写得多么严格，都应该有一道模型拿不到的人工确认。原理很简单：把决策权交回给持有真实身份的人，让注入文本无法替人点击。

实现上要注意三点。第一，确认必须绑定具体内容：展示“要做什么、对谁做、影响多大”，而不是一句笼统的是或否。第二，确认令牌要一次性、短时有效、与参数摘要绑定，否则会出现确认后参数被后续轮次替换的问题。第三，只对高风险动作确认，否则用户会退化成无条件点“继续”，闸门反而失效。

consumeConfirm 里重新计算摘要这一步是关键：它保证“用户确认的那件事”和“代码即将执行的那件事”是同一件事。如果只校验令牌是否有效而不校验参数摘要，注入就可能在确认之后偷换参数。

工具与插件：最小权限与过度授权

风险来自两处相乘

工具让大模型应用真正有了“手”，也因此，工具设计上的过度授权会把提示注入从“改写一段文案”升级为“执行一个动作”。风险量级大致是注入可能性与工具能力半径的乘积：能力半径不压小，前面所有缓解措施的收益都会被吃掉。

典型的过度授权形态有几种：万能执行器接口被挂进工具列表；工具用服务账号访问下游，而该账号权限远大于当前用户；工具描述含糊，模型在不需要时也会调用；一次授予的能力在整个会话里一直有效，用户换了话题也没收回。

设计原则

  • 一工具一权限点。粒度对齐业务动作，一个动作对应一个 scope 并声明最小权限集合；不提供通用执行器，那等于把权限判断交回模型。
  • 权限从调用者派生。执行时用用户身份换取短时降权凭据，最终权限取用户权限与会话声明能力的交集，而不是服务账号权限。用户本来不能读的数据，经过模型也不应该能读。
  • 参数用结构化模式约束。字段名、类型、枚举值、路径前缀、主机白名单、行数与金额上限全部在代码里校验，失败直接拒绝并记录原因。
  • 结果回填前脱敏。返回值会重新进入上下文，既是数据也是新的注入面，只回必要字段、限制长度、去掉堆栈与调试信息。
  • 执行环境隔离。模型生成的代码或命令在受限容器里运行：只读根、受控出网、低权限用户、短超时与资源上限，默认不自动执行。

这段代码的价值在顺序：能力检查、参数检查、凭据降权、确认检查都在真正执行之前，任何一步失败都不接触下游。若写成“先执行再判断”或“判断放在提示里”，前面几节的防御都不成立。

坑主要有三个。工具描述本身也是注入面：把第三方插件的自描述文本直接拼进系统提示，等于允许外部作者给模型下指令，描述、示例与返回格式都要准入审核。自动重试会放大影响：调用失败后由模型自行换参数重试，会把一次被拒的尝试变成十次，重试次数与参数变化幅度都要限死。能力授予的生命周期要短：任务切换时重新协商，而不是一个长会话从头带到尾。

数据泄漏与越权检索

大模型应用把组织的私有数据聚合成流畅的回答，这既是它的价值也是它的危险之处：不懂内部命名规则的人，只要能用自然语言提问，就可能问到不该对他可见的内容。因此本节的核心不是“别让模型说出去”，而是“模型根本看不到它不该看的东西”。

权限过滤要在检索层完成

最常见的错误实现有两种。一种是全量取回再靠提示约束：内容一旦进入上下文，泄漏渠道就不再只有回答这一条，日志、缓存、多轮追问都可能把它带出来。另一种是先按相似度取前 K 条再按权限过滤：候选不足会拖累答案质量，而且“检索到了但无权查看”与“根本没有相关数据”的表现不同，用户可以据此推断敏感文档是否存在。

正确做法是在数据摄取时就把访问控制信息写入元数据，检索请求携带调用者身份，由向量库在候选生成阶段完成过滤。检索封装层要做三件事：强制注入租户条件、拒绝缺失身份上下文、断言返回结果都在权限集合内。

配套的摄取规则同样重要：权限变更要同步到索引，删除要做软删加索引标记，避免库里已删而向量库仍可召回的时间窗；权限模型无法表达的片段宁可不入索引。另外要警惕嵌入本身：向量在特定条件下可能被近似还原出原文，证件号、密钥这类字段不应进入向量，要独立存储、按需展示。

多租户隔离的三种取舍

方案 隔离强度 成本与运维 主要风险
每租户独立索引或集合 高 集合数量随租户增长，冷启动与备份压力大 路由错误会串到别的集合
共享索引加强制过滤 中 资源利用率高，运维简单 一处漏过滤即跨租户，测试覆盖难
大租户独占加小租户共享 中高 需要分级策略与迁移工具 分级判断失误导致降级隔离

无论选哪种，过滤逻辑都要下沉到检索封装层，禁止业务代码自己拼过滤条件；缓存键要含租户与权限指纹，否则一次命中就可能把 A 租户的回答给到 B；模型服务与向量库的凭据也不得跨租户共用。

会话持久化与数据回流边界

除了回答本身，数据外流还有三条常被低估的通道：请求日志、会话存储、用于微调或评测的数据集。用户提问里会夹带手机号、证件号甚至误粘贴的密钥，原样存档后，日志往往比业务数据更容易被查看，就成了最薄的那面墙。原则是默认最小留存、敏感字段写入前掩码；线上对话回流进训练或评测集要有授权与用途记录，评测集要可追溯、可撤销；使用第三方接口时确认数据处理条款与不留存选项，调试流量不走生产数据。

输出处理：送到出口之前都要过闸门

模型输出的字符串会流到三个方向：前端渲染、下游系统、重新回到模型上下文。三处风险不同，共同前提只有一条——它是外部输入，不是内部返回值。

出口一：前端渲染

很多应用直接把模型生成的 Markdown 转成 HTML 展示，这里要控制两件事。第一是标记白名单：标题、段落、列表、加粗、代码块这些结构性元素够用，原始 HTML、内联样式、事件属性与脚本一律不允许，交给 sanitizer 处理，配置见下。第二是链接与图片：模型给出的地址可能是编造的，也可能指向钓鱼站点，外链要加 rel="noopener noreferrer"、显示真实域名并对陌生域名给出提示，图片按需代理而不是让浏览器直接去取。另外，模型文本可能长得像系统公告，要用视觉边界把它与真实界面元素区分开。

出口二：下游系统

这是更常见的真实事故点：模型输出被编排层拼进查询语句、Shell 命令、模板、工单标题、告警文本或导出文件。每个出口的逃逸规则不一样，一个通用清洗函数覆盖不住。原则只有一条——结构化传递，不做字符串拼接：查询走参数绑定，命令走显式参数数组，模板用自动转义引擎，写日志前转义换行与控制字符以免伪造审计条目，导出表格时对以公式符号开头的单元格做前缀处理。进入下游之前还要过字符集、长度与字段模式校验，失败就丢弃并记录，而不是截断后照发。

出口三：内容安全与代码执行

内容闸门建议做两层：输入侧拦一道，输出侧再拦一道，命中后返回统一兜底文案，不回显原文。模型给出的安装命令、脚本片段或配置修改默认只展示不执行；确需执行时走前面说的最小权限与沙箱路径，由人复核后触发。模型给出的地址不做自动访问，必须抓取时走受控出网代理、白名单域名并禁止内网地址段——地址来自模型输出，不改变它是外部输入的本质。

模型供应链

大模型应用的依赖面比传统服务多两类特殊对象：权重文件与训练生态的库和镜像，都可能带可执行内容。

权重方面的第一条原则是来源可核验：只从组织批准的仓库或内部制品库取模型，记录来源地址、修订标识、许可证与模型卡。第二条是序列化格式——以 pickle 保存的权重在加载时会执行任意代码，等于把可执行文件当数据读取；优先使用安全张量格式，必须加载旧格式时先在隔离环境做静态检查。词表与配置也可能声明自定义加载代码，那类开关默认关闭，白名单例外要评审。第三方微调适配器同样在范围内：很小的参数增量就能改变模型行为，来源与评测记录要和基座模型同等对待。

库与镜像方面，训练与推理生态的传递依赖很重：锁定文件要纳入版本控制、构建走私有镜像源、定期做组件清点与漏洞跟踪；GPU 基础镜像常自带解释器与预编译库，来源与更新频率单独评估。与组件漏洞治理的分工是：盘点、成分分析与升级流程属通用实践，本文只强调新增项——权重、词表与配置、微调适配器，以及加载即执行的序列化风险。

可用性与成本：限流、配额与降级

资源消耗由输入长度、输出长度与推理步数决定，而这三个量在很多路径上受外部文本影响，成本与可用性因此成了真实攻击面。超长上下文、整篇大文件丢进摘要、多轮检索不断加高提示、循环不止的智能体流程、把输出上限调到最大，都能把单次请求的成本抬高一到两个数量级：托管接口表现为账单，自研集群表现为排队与延迟恶化。缓解要从“每个请求都要有预算”出发，由代码强制执行，而不是写在提示里指望模型自律。

  • 双向计量：输入按分词后的 token 数统计，输出按实际生成长度统计，都记到用户、租户与业务动作三个维度。
  • 硬上限：单请求输入长度、输出上限、单次会话的工具调用次数与推理步数，超限即截断或终止，并返回可解释的错误。
  • 分层限流：先按用户与租户限制请求速率与 token 速率，再做全局并发闸与有界队列，队满时快速失败而不是无限排队。
  • 降级与缓存：非关键任务走更小模型或只检索不生成；重复问题的缓存键必须包含租户与权限指纹。
  • 及时取消：客户端断开要传导为上游请求取消，否则流量退了算力仍在烧。

观测上要能看出异常形态：每请求成本分布、输入长度长尾占比、步数分布、重试率与队列等待时长，只报请求数与平均延迟看不出成本型问题。

评估与红队演练的组织方式

行为依赖上下文，安全结论也就依赖上下文，一次性验收没有意义，要变成有授权的周期性演练。范围、时间窗、禁止触碰的对象与数据、停止条件都要事前书面确认；只在测试租户与合成数据上做，不用真实用户数据，不碰生产里的他人资产。演练的项目管理与规则约定见《红蓝对抗与演练实践》，本文只讲这类应用特有的细节。

用例由“风险位置”与“业务动作”交叉生成：注入、越权检索、输出处理、成本滥用四类，分别覆盖工具调用、渲染、导出、计费等出口。每条用例记四样东西：构造场景的说明（存内部工单，不进公开文档）、期望成立的安全不变量、判定方式、结论与整改项。安全不变量是这里的关键词，它把“回答得好不好”换成可判定的命题，例如“任何工具调用都必须携带用户作用域凭据”“任何返回内容不得含其他租户标识”“任何被拒绝的动作不得产生下游写入”。

结论要落成文档且能复现：记录模型与权重版本、提示模板版本、采样参数、检索配置与用例编号，否则无法判断是修复了还是碰巧通过。修复后把用例并入回归集，在模型升级或模板大改时重跑，形成模型、提示版本、用例三个维度的回归矩阵。

日志脱敏与留存

日志最需要小心：它天然要记录提示与回答，而这两处正是敏感内容最集中的地方。原则是记决策不记原文——记谁在什么上下文下请求了什么动作、命中哪条校验、为什么被拒、最终执行了什么，参数用哈希或掩码摘要保留可关联性，排查时凭关联标识回到受控存储。

脱敏要发生在写入之前，不能指望查询时再过滤。实践中用规则加实体识别两层：规则覆盖手机号、证件号、卡号、常见密钥样式与内部标识符，实体识别补上自由文本里的人名地名；命中后做掩码而非删除，保留位数信息以便排查。留存策略做成配置项：分级存储、按用途设保留期、到期可验证删除，日志查询本身也要鉴权并留审计——集中了各租户提示内容的日志库，往往比业务库更值得防护。公众服务场景的留存义务以正式文本与法务口径为准，本文不写死期限。

上线前安全检查清单

清单按风险位置分组，每项都要能指出证据在哪里。

  • 权限与工具：工具权限点清单已评审；执行使用用户派生的短时凭据；参数校验与白名单在代码里；不可逆动作有人工确认；步数与调用次数有上限。证据是工具注册表与权限服务日志。
  • 数据与检索：摄取时写入租户与权限元数据；过滤在候选生成阶段生效并有断言测试；缓存键含权限指纹；权限变更与删除能在索引上收敛。证据是越权检索用例的回归结果。
  • 输出与出口：渲染走白名单过滤；下游传递结构化且不拼接；日志写入前脱敏；导出文件处理过控制字符。证据是出口清单与对应用例。
  • 供应链：模型来源与许可证入清单；权重指纹校验；不启用远端自定义代码；依赖锁定与镜像摘要固化。证据是模型清单与构建记录。
  • 容量与成本：用户、租户、全局三层限流生效；输入输出预算与取消传导可用；成本指标可视化。证据是限流错误响应与监控面板。
  • 演练与合规：演练范围经授权；不变量用例通过；未决项有责任人与期限；面向公众服务的评估、标识与投诉入口已就位。证据是演练报告与整改工单。

小结

大模型应用的安全工作不是给模型加铠甲，而是把它周围的包装层重新设计一遍：上下文里每段文本按不可信处理，指令与数据用结构和代码分离，能力按最小权限派生、由高影响动作的人工确认兜底，检索在候选生成阶段挡住越权，输出在每个出口分别校验与转义，权重与依赖按供应链资产纳管，成本与容量由预算强制约束，最后用有授权、有不变量、有文档的演练把它变成常态。业界公开清单可以拿来分类，即将施行的管理办法要留出合规接口，但真正决定线上表现的，是每一条闸门有没有落到代码里、有没有可复现的证据。
