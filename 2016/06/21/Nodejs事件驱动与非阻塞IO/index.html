Node.js 事件驱动与非阻塞 IO

事故开始：请求不多，CPU 不高，接口却慢了三倍

那天下午，我们那台 4G 内存的机器上跑着刚换上去两个月的服务，版本是当期 4.4.x 的 LTS。每秒请求数没涨，CPU 平得像画上去的，下单接口的平均耗时却从一百多毫秒爬到了接近一秒。第一反应是有人塞了重逻辑，于是先排除计算密集，做法很土：在响应两端打时间戳，看时间花进哪一段；再挂一个计数器，进请求加一、出请求减一，每秒打一次。

这段只是把”还有几件事没办完”变成一个能看的数字。十几分钟后出现反常组合：活跃请求压在两位数高位，每个请求几乎都要待上接近一秒，可循环没被谁连续占住。

这个探针每隔 100 毫秒醒一次，把间隔减去 100 打出来；谁在循环里占住几百毫秒，差值立刻变大，而当天最大只有几毫秒。两个观测放一起，结论就从”算得慢”变成了”等得久”。

口径先交代：数字都来自同一台 4G 内存机器的粗略观察，只反映相对量级，不是基准数据；代码一律 ES5，四月底刚放出来的那个新版本还在观望，没上生产。

算一笔内存账：为什么”每连接一个执行体”在我们这台机器上先撑不住

我们的直觉来自以前维护的老服务：一条连接来了就交给一个独立执行体，读请求、查库、拼页面、写回，全在它那份内存里按顺序走完。

贵的是起步价。线程除了栈还要线程结构和调度信息，进程更贵，还要独立地址空间和内核侧结构；这些钱跟它此刻有没有活干无关，只要活着就交。而 Web 请求的一生基本都在等：等对端发数据，等数据库回结果，等磁盘递文件。于是同一台 4G 机器上，每请求一个进程的做法在并发爬到几百量级时先出问题的是可用内存；换成单进程加事件循环，同样这份内存能挂住的连接数多出一档。

先撑不住的是内存，不是算力：耗时由等待构成的接口，这个模型对我们有利。

JavaScript 这一侧只干两件事：把回调交出去，以及结果回来时被调用一次。它没有”在这儿等 20 毫秒”这种动作，语言本身也不提供。真正去等的是下面那一层，也就是随 Node 带进来的那套 IO 驱动：它把 socket 挂到操作系统给的等待机制上，知道什么时候事情成了，再把结果连同当初存下的回调送回 JS 侧。我们的说法是：JS 接单交货，底层跑腿。

这个分工有两层含义我们没立刻想到：一是”单线程”只约束 JS 那半边，底层在做什么用 JS 的线程数数不出来；二是回调什么时候被调用，决定权不在我们写的函数里，而在那一层的进度表上。顺带说一句，那些看起来更省心的写法当时还藏在一个命令行开关后面，我们没敢在生产开。

什么叫做”没有占住循环”：一个能跑的对照

我们对”非阻塞”的理解一开始是错的，以为它等于”用了回调”。后来一个小服务才发现判定标准其实是行为上的：从旁边一直敲另一路毫不相干的请求，看它要不要等。

观察方法是开两个终端：一个反复请求 /sync 或 /async，另一个每隔 50 毫秒请求一次最后那条，只看返回的时间戳。跑 /sync 时另一路的间隔被打散，最长的一次接近读文件本身的耗时——读取发生在 JS 这一侧，循环整个被占住，旁边那条连回应都轮不上。换成 /async，另一路基本保持 50 毫秒一格。

这个对照后来成了我们的判断标准：不看写法，只看这段时间里循环还答不答应别的事。答应就是没占住；不答应，满屏回调也照样是阻塞。

我们以为全都走 epoll，后来发现不是

第一次看到”Node 靠 epoll 撑起并发”这种说法时，我们顺手理解成了所有 IO 都走 epoll。这个错是被一个本地文件读出来的。

差别在于能不能被问一句”你好了没有”。TCP 连接、accept、socket 上的读写在操作系统眼里都是可以等待的东西：登记进去，某个连接可读了就通知一次，一次通知能覆盖很多个。这类操作确实挂在循环上，所以几千条空连接对我们那台机器几乎不构成负担。

普通文件没有”就绪”这个状态：去读它，要么给结果要么不给，操作系统也没法提前说这次读什么时候能成。这类活只能交给一小撮另开的工人去做阻塞调用，做完把结果送回循环，当期随 Node 4 一起带的 IO 库就是这么安排的。还有一批看着像 IO、其实也走这条路：要问系统解析器的域名解析，以及一部分加密计算。我们的转弯就在这儿——读本地图片慢，居然能把整个服务拖住。

线程池被占满的现场：毫不相干的接口一起变慢

第二次事故离第一次不到两周，形状很怪：登录接口只要一个随机串，不解析域名也不读文件，平均耗时却翻了几倍；而这次没有循环被占住的迹象——间隔探针稳定得很，CPU 照旧不高。

排查手法是按”走哪条路”把接口分开埋点：一路是纯内存加网络 socket，一路是读文件、解析域名、加密计算。埋完当天就有规律：只有后一路在排队，排队时长跟同时发起的读取数量差不多成正比；前一路里碰到加密的那几个接口跟着一起慢。合起来只剩一个解释：工人数量有限，活比人多，登录要的那个随机串排在队尾。

这类问题最难的地方在于病灶和症状不在同一个接口上。我们后来的固定看法是：耗时上涨、循环探针正常、CPU 不高、socket 那路也不慢，就先去数同一时刻有多少读取和解析正在飞。

UV_THREADPOOL_SIZE：改得动，但不是白拿

知道工人数量有限之后，我们第一反应是这个数字写死在库里。一试就知道不是：它由环境变量决定，当期默认值是 4。

坑在于它必须在进程起来之前就位。我们最早把赋值写在入口脚本第一行，重启完现象一点没变，白折腾了半个晚上——工人数量在进程启动时就按环境定下来了，JS 跑到那一行早就晚了。挪到启动命令前面以后，排队确实缓解了。

但别把它当成免费的。工人从 4 加到 8 之后 CPU 那条线开始抬头，本来互不相干的两个读取在磁盘上也开始互相抢——核数没变，那块盘每秒能完成的读写次数没变，加工人只是把排队窗口从 4 挪到 8，并没有把活本身变快。所以它只是把某类等待压回去一点的旋钮，每挪一次都要回头看另外两路。

真要在算的东西，就请它出门

排错到最后总会碰到一类没法靠”改成异步”解决的任务：图片要压一遍，报表要拼一个很大的结构。这类活在循环里没有解——循环只有一个人，他算的时候谁都叫不动。办法是把它请进一个单独的子进程。

两边各用三条 API：派一个出来、把活递过去、收一次回话再断开。换来的是主进程一路都在接单，旁边的请求不再因为一张图集体变慢；代价是每处理一次多一笔进程启动和传话的开销。按同一台机器的粗略观察，单个任务完成得慢了，但整台机器”一卡卡一片”的现象消失了。

传话这块栽过一次：来回只能传能序列化成 JSON 的东西，一个大 Buffer 递过去等于复制一份，我们以为是传引用，结果内存先撑不住。所以现在消息里只放路径，让干活的进程自己去读。至于多核怎么吃满是另一件事，部署那篇讲过用一组进程分摊监听，它解决的是核数利用率，不是把计算从循环里请出去。

用途我们的分法很粗：要给一个外部时间点的，用 setTimeout；要把一段长活儿切成几片、中间腾出位置回应别人的，用 setImmediate。切片的写法我们在讲回调流程控制那篇里推过，这里只补一句选哪个函数。至于微任务与 nextTick 插在哪、什么时候排空，另有一篇讲过，不重复。

非阻塞不等于并发上限

这个模型让你能同时挂着很多连接，却没告诉你同时”办”多少件合适。我们真在这儿翻过车：有一段时间循环探针漂亮、活跃请求数不高，下游数据库的连接池却被同一时刻涌过去的几百个查询打满了。怎么压住同时进行的数量，五月份那篇已经写过做法，这里不重讲；只划一条线——事件驱动解决的是”等得起”，不是”办得动”。

这个模型让我们付出的三样东西

代价是我们一条条撞出来的。头一样是调用栈在回调处断掉：出问题时留下的栈只有最后那一小段，当初谁发起的这次读取、经过哪几层，栈里一个字都没有。第二样是错误没人接：回调里抛出去的东西不会沿调用路径回来，这一层没写处理，它就一路冒到进程外面，我们把整个服务弄停过就是这一条。这两条的纪律我们在讲错误处理那篇里写过了，这里不重复清单，只说第三样——链路长了以后没人知道卡在哪一层。

土办法很简单：给每条进来的链路发一个 id，往下传，每段进出各打一次。

有了这两样东西，”慢在哪一层”从一个猜不出答案的问题变成一行日志比对：同一条 id 的几次打点之间隔了多久，一眼就看出来。id 要靠参数或对象往下带，回调里忘带就断了，但比每次出事临时加日志强。

domain：我们没走的那条兜底路

当年确实有人拿 domain 去兜回调之间的错误传递，我们没用过。原因不复杂：它朝着被替换方向走的信号已经够明显，而线上稳定性不该押在一个正在倒计时的机制上。

症状对着层级的一张表

症状 先查哪一层 动作
接口慢、CPU 高、探针跳 JS 侧被同步调用占住 用第四节的对照法
接口慢、CPU 不高、socket 那路正常 线程池排队 数在飞的读取与解析
文件类接口整片变慢 磁盘与工人数量 先降读取并发
不碰文件的接口也慢 加密或解析挤进同一条队 与批量读取分开看
连接不多但内存先涨 执行体的起步开销 数进程与线程
本机循环很空、下游报警 同时处理的数量 查下游池子、限并发
说不清这次是谁调的 链路的可见性 补 id 与分段打点

这张表的作用只有一个：把”该往哪一层看”变成不用想的动作。至于这个模型什么时候合适——耗时由等待构成的活用它，由计算构成的先请出门再谈；它值不值那三份代价，我们的答案是需要长期排查的业务值，跑一次算一次的脚本别用。
