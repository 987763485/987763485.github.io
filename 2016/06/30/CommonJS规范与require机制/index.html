CommonJS 规范与 require 机制

一次 require 拿到 undefined 的事故

六月最后一个礼拜,组里那个内部排期工具包 taskq 惹出一场骚动。写的时候只想着给页面用,同事在 2016 年这个 6 月里用 webpack 把它打进页面,跑得很顺,谁也没多想。第二天另一个同事要在 Node 脚本里复用它,var taskq = require('taskq') 之后第一行就打挂,报错是 TypeError: Cannot read property 'create' of undefined。扒开看源码,毛病在最外面那圈 UMD 包装:导出分支和浏览器分支的活儿搅在一块,工厂函数只在检测到浏览器全局的那条路上 return,Node 里 self 不存在,module.exports 就接到了 undefined,页面里正常恰恰因为浏览器有这个全局。组里当天就吵起来,吵的不是这一行代码,是”我们写的包到底该按哪套规矩发布”。

先把边界划清,免得跟已有笔记重复。Node 怎么把文件找出来、module.paths 怎么上溯、缓存与循环依赖怎么回事,那部分我写在另一篇里,这里一行不再讲。ES6 模块语法本身、构建工具怎么接、tree shaking 的原理也早讲过一遍,我不重做那三种写法的对比。这篇只留两样我自己的东西:规范条文与各家实现之间的差额,以及新写一个包该按哪套发的判断。

CommonJS 是一摞规范,不是一个

CommonJS 这个名字容易让人以为它是一条规矩,实际是好几条规范摞在一起的总称,各自演进,互不管辖。跟我们发包相关的是两条:Modules 和 Packages。Modules 约定几个名字的形状——module 上的 id、exports、filename、loaded,module.paths 给谁看,以及 require 这个函数该返回什么、同样的标识符该不该命中同一份导出。它写的是名字的含义和职责,不是文件怎么找出来。Packages 约定的是一个目录怎么才算一个包:有没有 package.json,main 字段指向哪儿,没写 main 时 index.js 的地位,还有 bin、tests 这些习惯位置。规范另外还有 Async、System 之类的部分,当期基本没碰。条款编号我记不准,也不在这儿抄错,下面全按内容讲,不写第几条。

分层看清了,坑也就明白:我们照着 Node 的行为写代码,以为那就是 CommonJS,其实手上这套”行为”是规范、Node 实现、打包器私货三层混合的结果,规范只覆盖最里面一小块。

规范写的、Node 实现的、打包器自加的

这篇最想留下的是这张差额表。我原本把 require 的每个行为都归到”规范里应该有”,扒开看一遍才清楚,很多东西是实现自己加的,被工具链当成默认规矩传下来,打包器又摞了一层私货。同一台机器上粗略观察:换个工具就得重新对一遍表。

行为或字段 规范写了 Node 实现加了 打包器自加的
不以文件分隔符开头的标识符按模块名解析 写了这个约定 落地成具体算法 沿用 Node
.js/.json/.node 后缀补全 没规定这几种后缀 Node 自己定的三类 跟着 Node,再加自己的后缀表
node_modules 逐级上溯 只提了查找路径这个概念 Node 的具体目录策略 基本照抄
package.json 的 main Packages 部分写了 实现了,含缺 index.js 报错 认,优先级各写各的
顶层 this 等于 module.exports 未规定 Node 包装函数造成的 不适用,没有全局
require.cache 与重复 require 命中同一份 要求同标识符同导出 Node 用缓存实现 自己一套模块表
bin 目录与全局安装时的软链 Packages 只提目录习惯 npm 做的事,不是 require 不参与
browser 字段 从来没这条 Node 直接忽略 2016 年打包器自加的约定
jsnext:main 从来没这条 Node 直接忽略 工具为区分 ES6 源文件自己加的

最后两行是重点。browser 和 jsnext:main 既不是规范也不是 Node 的行为,纯粹是工具链叠在实现之上的约定,可我们写 package.json 时觉得它们本来就是模块系统的一部分。心里没底时我只信一条标准:这行为换一家实现还认不认。认,大概率是规范;不认,就是私货。

AMD 与 CommonJS:差在什么时候要依赖

两套规矩最实在的差别是加载时机,不是写法。CommonJS 是同步取,执行到那一行才要依赖,拿不到当场挂掉。AMD 把依赖写在门口先声明,加载器提前把文件拉完、回调里再执行。

Node 里同步无所谓,文件就在本地磁盘上。浏览器不是这么回事,2016 年我们在页面上仍然是一个接一个的 <script> 标签,同步 require 网络路径上的模块等于把渲染打挂。所以 AMD 那套依赖前置声明在浏览器里是真有用的机制,不是花架子。RequireJS 的配置与 shim 专文讲过了,这里只留结论:同一个包要同时发给 Node 和老式页面,同步和异步语义没法共存,只能靠 UMD 的分枝交给两边。

模块作用域的三个细节坑

exports 与 module.exports 的关系、文件怎么被找出来,那部分我在另一篇里写完了,不重复。这里只补三个当年仍让我判断失误的性质。

一是模块文件顶层的 this 不等于全局对象,它等于 module.exports。顶层写 this.foo = 1 就是往导出对象上挂属性;同一份代码放进 UMD 的立即执行函数里,this 是什么全看外面传了什么,这就是页面里正常、Node 里行为两样的来源。二是别给 exports 整体赋值,它只是实现为方便给的局部变量,你把它指向新对象,原先那条链接就断了,require 拿到的还是老东西:

三是 require 不是全局变量,是函数参数。模块文件被包进形如 function (exports, require, module, __filename, __dirname) 的函数里执行,require 是这条参数的局部量,机制一句带过。用处在于:严格模式下、或者在 eval 与回调里以为能摸到 require,答案是不能,得让它待在这个包装函数的作用域里。规范只说模块可以通过 require 取依赖,从没承诺它在词法上是全局的,这条又是 Node 的实现形状。

四条选型判据

吵完那一架,我们把判断压成四条,每条都带上当期我们站哪边。一是目标运行时:包得在 Node 脚本里被 require,出口就必须是 CommonJS 产物,这条没商量;只在页面里跑、页面还是一个接一个 <script> 标签的,用 UMD 或 AMD。二是要不要被打包器做静态分析:要,就留一份全静态语法的 ES6 源文件给 jsnext:main 指,同时承认这字段只有部分工具认,别当能力承诺。三是要不要发 npm 给外部用:发外部就只留一个入口、行为可预期,花哨字段收进构建脚本;内部包可以并存三个字段,工具链我们能一把抓。四是团队对 ES6 语法的接受度:2016 年年中组里一半人还在写 ES5,构建链也没全过一遍,所以源码可以写 ES6,发布产物必须是转译后的 ES5 CommonJS,谁 require 都不需要额外前提。四条判完基本就唯一确定,剩下的分歧全是口味。

一张横向对照

维度 CommonJS AMD UMD ES6 模块
语法形态 require 加 module.exports define 加依赖数组与回调 外面一圈探测分支,内层任选一套 import 与 export,静态结构
加载时机 执行到那行同步取 依赖前置,加载器先拉完再执行 看命中哪个分支,两套时机都有 标准里是提前解析,引擎跟上才算
2016 年年中的运行时支持 Node 原生,浏览器要工具 RequireJS 这类加载器可用 两边都能吃,靠包装 浏览器不支持,Node 也不支持
能否静态分析 难,require 可以写在条件里 更难,依赖是运行期的字符串数组 谈不上,分支本身就是动态的 语法上能,但当期只有工具认它
我们当时的用法 Node 侧与发布产物的默认形态 老页面的 define 入口 同时发 Node 和浏览器的包 只写在源码里,产物一律转成前者

表里第四行措辞我特意收着:”语法上能静态分析”是标准文本的性质,2016 年年中真吃到这份好处的只有少数工具,靠的是转译和自建字段,不是运行时。

新写一个包该按哪套发布

情形 发布形态 一句话理由
只给 Node 脚本用 纯 CommonJS,main 指产物 没有第二个消费者,别加私有字段
要给老页面 <script> 直接引 UMD,只挂一个全局名 检测分支照抄可靠模板,工厂无条件 return
同时给 Node 和浏览器 UMD 打底,browser 指浏览器版 两套语义靠分支分头交给两边
内部工具且要参与静态分析 额外留 ES6 源文件给 jsnext:main 字段只有一部分工具认,不能当承诺
发 npm 给外部 单入口 CommonJS 产物,不裸发源码 外人只该有一个能预期的行为
页面全是 AMD 加载 干脆只发 AMD 没有 Node 消费者就不必兜底

这半年我最大的收获不是记住了哪套语法,而是把”规范写的”和”实现做的”分成两栏存放。分不开的时候,报错只会出现在别人机器上,而且一定出现在你跑过十遍的那条路上。
