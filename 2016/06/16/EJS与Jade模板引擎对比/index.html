EJS 与 Jade 模板引擎对比

一个列表页，两份脚手架

六月中旬，组里接了个新的后台项目，一堆 CRUD 加几张报表列表。第一天搭架子，我用 express-generator 分别跑了 --view=ejs 和 --view=jade，各生成一份扔在两个目录里，结果变成两天的争论：一个认定 EJS 长得像 HTML，谁都能上手改两行；另一个认定 Jade 缩进干净写得快，尖括号本来就是噪音。两人谁也说不服谁，我做决定，心里没底。第三天我索性把同一个订单列表页在两边各写一遍，用同一台机器、拉同一批人来看，把差异一条条记在纸上。

先把范围划死：只比服务端渲染这一层

比的对象只有一层：Express 里 app.set('view engine', 'jade') 或者 'ejs' 设好之后，res.render('order/list', data) 走到响应结束之前那一小段。引擎在这层就是取值、转义、循环、分支、拼字符串。

边界外的提前挡掉：浏览器里拼 HTML 字符串的前端模板另有专文；Express 4 的视图机制、把模板编进包、后端渲染对搜索的影响各有专文；多引擎横评和”默认转义不等于安全”那套论证，去年十二月那篇讲完了，本文不复用它的框架与推荐矩阵。我们的困惑很具体：同一个页面谁改动量小，改版时团队代价落在谁头上。

EJS 多出来的是尖括号、属性引号、成对的闭合标签；它省掉的是”把这张表重新翻译一遍”这个动作，结构原封不动，设计稿能直接搬。Jade 多出来的是缩进层级——最后那个 span 我一开始挂错了父级，渲染出来少一整列，找两分钟才发现是少缩两格。它省掉的是所有标签名和闭合，二十来行 HTML 骨架在它那儿没有存在必要。同一台机器、同一批人的粗略观察：这一页从零写完，EJS 十来分钟，Jade 二十分钟出头，而 Jade 那二十分钟里将近一半在跟缩进较劲。

转义方向：一个默认往里收，一个默认往外放

这是最容易写反的地方，也是我们在生产上被打乱过一次的原因。

Jade 的规则是 = 默认转义、!= 才不转义，#{} 插值也走转义，想原样得写成 !{}；EJS 是 <%= 转义、<%- 不转义。放开安全的那一下，两边动作幅度完全不同：Jade 是在等号前加感叹号，加没加肉眼看得出来；EJS 是把等号换成减号，<%= 和 <%- 在满屏尖括号里只差一个字符。

事故长这样。上线两周后运营反馈，列表有几行的备注列把表格撑破了，后面的列整体往右跑，状态标签掉到表格外。按当期的笨办法走：把那个客户的备注原文从库里捞出来存成 txt，一眼看到里面嵌了换行标签和带内联样式的 span。确认 HTML 原样输出了，问题就在模板那行。

定位到那一行费手：orders 几十条一屏刷不完，我把循环临时改成只取第一条，再按列拆开逐段注释，一遍遍跑，注释到备注列时表格恢复正常，就它了。Jade 看编译产物更快，转义过的地方外面包一层转义函数调用，!= 那行是裸拼接；EJS 直接看页面源码，&lt; 是转义了，< 是没转义，顺着错位往回找模板行号。

后来的规范是，需要原样输出的字段一律在后端拼好加白名单，模板里不许出现 <%- 和 !=。真正的差别在评审：EJS 的 diff 里 <%= 改成 <%- 是一行里一个字符的位移，评审的人十有八九滑过去；Jade 的 = 改成 !=，整行很短，一眼就能看到。这一条后来成了我们倒向 Jade 的一个不大不小的理由。

编译与缓存：第一次慢，后面快

两种引擎都不是把模板当字符串现拼，而是先编译成一个函数，之后每次 res.render 就是它带数据跑一遍。编译这步花钱，Express 用 view cache 管着：开发环境默认关，每次请求重新编译，为的是改完刷新就能看到；NODE_ENV 设成 production 之后自动打开，编译结果留在进程内存里。同一台机器、同一批人的粗略观察：那个列表页冷着时单次渲染是几十毫秒量级，进程跑热了落到个位数毫秒。

教训是设忘了。有台机器上线时环境变量没配全，NODE_ENV 是空的，一次报表页被几个同事同时刷，模板在每个请求上重编译，CPU 直接被打挂，平均耗时从几毫秒涨到几百毫秒；直到发现耗时跟请求次数线性相关才扒开看到底——临时脚本里打印 app.get('view cache')，值是 undefined。修完多了两件事：部署脚本把 NODE_ENV 当必填项校验；上线后用内部地址把所有页面各跑一遍。

客户端复用：一份模板能不能同时在浏览器里跑

EJS 的模板文件在浏览器眼里就是一段普通文本，读进来照样编译，前后端共用同一份文件，前端篇讲过这种用法，这里不展开。Jade 不行，它的编译产物是函数，浏览器里没有那套解析器，要用就得先把 .jade 编成一个只依赖运行时的函数塞进页面。我们真试过一次，代价是包体积涨一截、模板一改就要重跑编译、断点打在编译产物上跟源文件对不上、运行时版本还得跟编译器版本咬齐。这些不是不能付，但要为它专门养一套流程。我们的页面本来就靠服务端渲染，这项价值有限，但纯前端项目里它是 EJS 的一个明确加分项。

复用能力：mixin、block 与 include 的粒度差

EJS 只有 include，传参当期靠渲染上下文碰运气，同名变量会互相盖掉。一次改版要”把三处共用的表头抽出来”：Jade 那边新增一个 mixin 文件、三个页面各改一行引用，四个文件；EJS 那边也能把表头拆成片段，但三处的列宽和筛选项不一样，得给每个页面各配一组变量，连页面带局部一共七个文件。同一台机器、同一批人的粗略观察：一边一小时出头，一边三个多小时，差距大半在 EJS 要人工保证多个页面的变量名不打架。

协作成本：设计稿的 HTML 往哪边搬

设计给的是能直接打开看的 HTML。搬进 EJS，动作是原样粘进去、把写死的地方换成 <%= %>，改动集中在几十行里的几个点；搬进 Jade，动作是整页重写，标签名、属性、层级全部翻译成缩进。那次后台改版是列表加筛选项加批量操作，同一批页面两套各走一遍，同一台机器、同一批人的粗略观察，EJS 侧约三天，Jade 侧约六天。

六天里有一块不是模板语法的锅，是评审。Jade 的 diff 按缩进层级铺开，改一个子节点，下面整片都要重排，评审的人看到一大坨上下文变化，看不出语义改动究竟在哪。当期也还没有能统一两种模板语法的格式化工具，只能靠约定。

工程约束：缩进、lint 与模板里的业务逻辑

Jade 文件当期没有像样的 lint。踩的坑是 tab 和空格混用：一个同事的编辑器对 .jade 默认插 tab，另一个插两空格，两人改完同一个文件之后编译直接失败，报 unexpected token "outdent"。最后是靠 .editorconfig 把 indent_style 和 indent_size 定死才断掉，规范篇另有人写过一条相关的检查，这里不重复。

一次迁移尝试，和它为什么只走了一半

老的客服后台是几年前用 Jade 起的，骨架很整齐。这次想统一成 EJS，理由是接手的人多半只会改 HTML。清单摊开：四十多个模板文件，外加六个 mixin，一次全量替换。真动手是先从列表页开的刀，两个页面搬完就发现不对。

语义丢失在两处。mixin 是带参数的，改成 include 之后只能靠上下文变量传值，一个片段被五个页面用时，五个页面都得备齐同一组变量，名字还不能撞；block 更麻烦，EJS 当期没有对应的”父模板留口子”写法，我们改成把公共骨架抽成一个 include、页面内容前后各引一次，结果 <head> 里那些按页面不同的元信息没了落点，只能一个个手补，评审的人也没法判断有没有改漏。

同一台机器、同一批人的粗略观察：迁完那两个页面花了五天，比预估慢一倍。剩下的大半最后没动，只在新增页面时统一用 EJS，老页面谁接需求谁顺手搬。这个半迁状态不体面，但当时算过一笔账：重写一遍的成本，比这些页面往后被改的次数省不下钱，就停在半路上了。

结尾：只回答 EJS 还是 Jade

这张表只回答选型这一件事，不搬去年那篇的推荐矩阵。

判据 EJS Jade 我们最后选了哪个，为什么
设计稿 HTML 直搬 能，原样粘 要整页重写 EJS，切图产出占比最高
转义写反的可见度 一个字符之差 感叹号显眼 Jade，评审能逮住
报错行号 常错位的 JS 行号 就是文件行号 Jade，新人不至于抓瞎
跨页面复用 include 碰运气 mixin 带参数 Jade，改版动的文件少
代码块与邮件 原样保留空白 空白被语法吃掉 EJS，这类页面另立清单

拼到最后，新项目我们定的是 Jade 打底、清单页和邮件页用 EJS。理由不在语法谁漂亮，在这类后台的两种活儿上：一次大改版要传参复用、要报错可读，Jade 占住；一天动一次的展示页，EJS 直接搬，谁都能改。这不是”哪个引擎更好”的答案，只是我们这摊活的成本分配。
