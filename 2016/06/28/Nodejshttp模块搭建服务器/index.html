Node.js http 模块搭建服务器

事故现场：偶发的 502，日志里干净得可疑

六月份，后台不再是”跑个脚本导数据”了。三个原生 http 接口挂在负载后面，页面直接调。问题很偶发：客户报”有时候点保存没反应”，接入层一天十几个 502，而进程 PID 从早到晚没变，日志里搜 error、搜 timeout，一个都没有。

第一反应是怀疑上游。问完一圈才意识到更难堪的事：没有证据证明这些请求进过我们的进程。于是加了个最笨的探针，进来打一行、结束打一行。

它只在 res.end 被调用时补一行日志。

跑一天，现象分两类。第一类有 [in] 没有 [out]：同步读取抛了异常，我们没接住，一个字节都没写，连接就悬着。第二类连 [in] 都没有——请求卡在调下游那一步，接入层先超时记成 502，我们写完一个没人听的响应。

合起来是同一句话：响应没发完就异常，或者没在限定时间内发完。所谓”日志干净”，只是出事的请求走不到打日志那一行。之后我们把”要么写出响应、要么明确失败”当成硬规矩。

req 上到底能拿到什么

请求对象上稳定可用的东西不多，我们最后只依赖 req.method、req.url、req.headers、req.httpVersion 和流式的请求体。req.url 含 path 和 query，不含主机名与协议；httpVersion 是字符串 '1.1'，不是数字。

拆 query 用 url 模块，第二个参数传 true 就直接给你解析好的对象：

url.format 是反方向。querystring 用来解 a=1&b=2 那种字符串，也用来构造 POST 体。url.parse 出来的 query 值全是字符串，?page=2 拿到的是 '2'，它和 undefined、空字符串构成三种”没传”。我们把它当数字用，写出过翻页永远停在第二页的 bug。

headers 上踩过一个更蠢的坑。头名字大小写不敏感，但 Node 给你的键统统是小写。有人顺手写 req.headers['Content-Type']，拿到 undefined，判断成”客户端没传类型”，把 JSON 请求当表单解析，报一连串莫名错误。把键打印出来才看清：取值一律小写。

还有一点：头是”到达即完整”的，请求体才是流，所以读 body 不该在处理函数开头同步等，得挂事件。

发响应：状态码必须在第一次写入之前定好

响应有三条通道——res.statusCode、res.setHeader、res.write/res.end，它们有先后约束，而这个约束靠运行时”默默坏掉”来惩罚你。

写错顺序是这样撞出来的：先 res.write(...)，再在某个分支里补 res.statusCode = 400。写的时候不报错，抓包一看状态行是 200——头在第一次写入时就已序列化到 socket 上，之后改什么都只是改内存里那个属性。

setHeader 可以分次设、能用 getHeader 读回来；writeHead 一次性把状态码和头都定了，一调用就代表”头发出去了”。

长度两种给法：算得出来就设 Content-Length，算不出来就干脆别设，Node 会用分块传输编码，靠一个零长块告诉客户端”完了”。这里有个坑：设了 100 却只 end 了 90 字节，客户端一直等剩下那 10 个字节，连接挂着不断，监控上一切正常。我们的土规矩是凡设 Content-Length 就用 Buffer.byteLength 现算。

中文乱码是另一件事：没带 charset 时客户端会用自己猜的编码去解，解法是把 charset=utf-8 写进 Content-Type。顺带一提，str.length 对中文算出的字节数是错的，这个差值正好让上面那个”永远等不完”复现。

静态文件：先把目录穿越堵住

我们的服务最初只干接口，后来加了个给老页面发静态资源的路径，代码只有一行诱惑：把 URL 路径拼到根目录上读文件。

这个坑是实打实被试出来的。最初的写法相当于 path.join(root, req.url)，有人在路径里塞 ../../etc/passwd，decodeURIComponent 之后 %2e%2e%2f 变成真的 ../，任意文件可读；看到测试同事贴来的截图才承认，是自己把用户输入直接当路径用了。修法是三道闸：拒绝空字节、normalize 之后用 path.relative 判断结果还在不在 root 内、只允许 isFile()。前缀字符串比较不可靠，/publicevil 会假装在 /public 下面。

为什么不用 fs.readFile？读满整个文件再发，一个大文件就把内存顶起来，同时来几个下载请求进程就飘了；换成流之后内存平稳。至于 pipe 内部做了什么，那是流那篇讲的事，这里只说用法。

gzip 是谈出来的，不是无条件开的

接口 JSON 越来越大，决定上压缩。用 zlib.createGzip，按 Accept-Encoding 决定要不要压：

要点有三个。第一，压了就不能再设原来那个 Content-Length，字节数变了，要么走分块传输，要么等压缩结果算完再设。第二，Vary 不能省，否则中间层缓存会把给错编码的响应喂给别的客户端。第三，别什么都压：已经是压缩格式的二进制再压没收益，还白烧 CPU，小于一两千字节的响应直接跳过。

至于压完延迟怎么变，我们只做过同机粗略观察：小响应开压缩是净亏，大 JSON 是净赚。当期没更好的办法，就把开关做成按路径配置。

几个要点。第一，累加的是 Buffer 不是字符串，编码问题留到解析那一步处理，避免一个多字节字符被切成两半时拼出乱码。第二，超限之后不能简单 return：请求体还在源源不断地来，不继续消费就堆在缓冲里，要么结束响应让连接断掉，要么继续 resume 排空但不留内容。第三，error 必须接。

更要紧的是”每个入口都必须有上限”这句意识。我们后来有一份土检查清单：收不收 body、上限多少、超了返回什么、由谁兜，四问答不上来的接口不许上线。

客户端早走了，我们还在那儿写

原生 http 给我们的是事件，不是开关：req 上有 close 和 aborted，res 上有 close 和 finish。当期没有”整体请求超时”的现成开关，只能自己挂计时器。

事故里第二类现象的修复方式就是计时器：

计时器管两件事：到点必须发一个响应；到点之前请求结束就得清掉，不清的话计时器本身就是内存泄漏。headersSent 是关键判断——头已经发出去了，就只能 end 或断连接，没法再改 504。至于 res.finished，是从内部对象顺来的属性，后来改自己维护 done 标志位。

没接 close 的现象：用户保存后立刻关页面，或接入层超时断连，我们这侧完全不知道。处理函数照旧跑完，向下游发了请求，把结果写进 res，写完发现对面没人。有一次下游按次计费，月底账单对不上，追下来就是这类请求贡献的。

keep-alive 的两面

浏览器到我们是长连接，我们到下游也是长连接，两边都会咬人。

先看客户端这一侧。Node 的 http 客户端默认经过 http.globalAgent，它负责连接复用。压测时延迟抖动很大（同机粗略观察，只反映相对量级），怀疑过 GC，最后落在排队上。能拧的旋钮就两个：

maxSockets 太小请求排队，太大把下游打出限流；agent: false 每次新建连接，隔离最好但握手开销大，我们只在调用量小的内部接口上用。keepAlive 要显式打开才复用，默认不开——我们一直以为协议层 keep-alive 就等于客户端自动复用，这条踩过。

服务端那侧的约束是：单域名在浏览器里大概只有 6 条并发连接，静态资源按域名分片就是这个道理；接口一慢，这几条全被占住，页面其余请求排队。

最难缠的是关停：server.close() 只停止接受新连接，存量连接一直挂着，进程不退出。当期没有一把关掉它们的办法，只能自己记账：

具体现场是发布时老进程收不到退出信号、被脚本强杀，日志最后一行都没留。先 close 再逐个 destroy，进程才走得干净。

当客户端的时候

事故里第二类现象的根子在这。我们调下游用的是 http.get，最初只写了个成功分支：

第一坑是 host 和 Host 头不是一回事：host/hostname 决定连到谁的 IP，Host 头决定对面把请求当成哪个站点。我们内网走 IP 直连，下游按域名路由，请求通了却一直 404，最后才想到在 headers 里显式填 Host。

第二坑是异常都挂在请求对象上：连接被重置是 ECONNRESET，写的时候对面已经关了是 EPIPE，两种都从 creq.on('error') 出来。我们一开始没接这个事件，异常一路冒到进程顶层，正是事故里”有 [in] 没 [out]“那一类。

第三坑是超时，当期没有现成开关，只能 creq.setTimeout 再自己 abort，秒数是我们自己拍的。第四坑是别只拿状态码就返回，连接会一直占着，agent 的额度就是这么耗光的。

不起域名也能测

最后讲我们怎么测这套东西。最省事的是让系统分配端口，自己打自己：

listen(0) 把端口交给系统，回调里用 server.address().port 取回真实端口。测试之间不抢端口，也不用本机装什么。

另一半做法是把处理函数单独导出、手造 req/res 桩。它只适合验证”给定输入该回什么状态码和 body”这种纯逻辑。我们被它骗过一次——桩对象上忘了实现 headersSent，于是”超时分支该断掉已发头的连接”这条逻辑在桩里永远走不到，测试全绿，线上照样挂。后来的规矩是：桩只测逻辑，行为一定要再跑一遍真 server。框架层的测法另有一篇。

症状对照表

最后是一张这几个月攒下来的对照表，左边是现象，右边是现在的第一个去处。

症状 先查哪一处
进程活着，日志干净，偶发 502 有没有未接住的异常；是不是卡在调下游
浏览器转圈、curl 不返回 res.end 有没有调到；Content-Length 是否偏大
中文响应成方块 Content-Type 里有没有 charset=utf-8
取到的头是 undefined 键是不是写成了大写
下游拿不到 body 请求体有没有被一次读满、有没有超限丢弃
发布时老进程不退出 存量 socket 有没有记下来关掉
调下游偶发无回调 error 有没有接、超时有没有 abort
静态目录读到奇怪文件 有没有做越界校验

原生 http 给的东西很少，少到必须自己把”每个请求都要有结局、每个外部调用都要有时限、每个入口都要有上限、每个连接都要有人关”这四条写进代码。什么时候必须换框架？我们的判断线是：当你开始在同一份代码里重写参数匹配、公共前置逻辑和错误兜底这三样，说明已经在手写框架了，那就用它，别把原生当信仰。
