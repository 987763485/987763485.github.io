Express 3 框架入门实战

开头：一次自作主张的升级

先划边界。4 的队列机制、app.use 前缀语义、express.Router 那套，我在《Express 4 中间件机制完全解析》（2016-04-26）里讲过，这篇不重复；Node 0.10/0.12 的环境与 require 解析归 2016-05-15 那篇，只一句引用；EJS 还是 Jade 的取舍归 2016-06-16 一篇；进程守护与部署归运维那篇；中间件写法的六个坑归 2016-05-24 那篇。这篇只干一件事：扒开一套 2016 年年中还在跑 Express 3 的老代码现场，讲清楚 3 自己长什么样、为什么还留着、真要把老代码升到 4 会撞上什么。

2016 年 6 月初，我被拉去接手一套 2013 年上线的内部后台。原来唯一能改动它的同事离职两个月，组里就我一个碰过 Node，活落到我头上。第一周只是跑起来了事，事故出在第二周：我按新项目习惯顺手升了依赖，在项目根目录执行了 npm install express --save。装完重启，服务没起来，控制台一行红字：

app.configure is not a function。那一刻我才反应过来，package.json 里那句 "express": "3.x" 是这套代码能跑起来的前提。回退、重装、重启，服务活了，但那十分钟我是真抓瞎——不知道这 API 什么时候没的、代码里还有多少地方依赖它。

为什么 2016 年了还在跑 3

先摆口径：2016 年年中，Express 4 已是主流，3 只剩存量。我两个新项目都开在 4 上。这套老后台留在 3，不是它比 4 好，是具体理由摁着不让动。翻完老代码，我列了这几条：

  • 只剩一个人会动，现在那个人走了。 前后只有两位同事改过，约定全在脑子里，文档停在 2014 年。动框架版本等于让不熟的人同时改两层。
  • 模板写法跟 3 绑死。 视图全是 Jade，布局直接用 Jade 自身的 extends/block，还有走第三方 partials 中间件的老路子。这些在 3 里都顺，换到 4 布局要单独处理，页面有四十多个。
  • 代码里到处是 express.* 命名空间的调用。 express.bodyParser、express.cookieParser、express.session、express.methodOverride 全在 app.js 里挂着，好几处还把 express.bodyParser() 的返回值拆给别的中间件用。
  • 验收环境锁系统版本。 客户机器只认某个老版本系统，Node 装到 0.10 就上不去了（细节在 2016-05-15 那篇，不展开）。框架升大版本，得连带确认它在老 Node 上还跑得动。
  • 没人能签字。 后台改了要重新走验收，升级到 4 不是一行 diff 的事，是没人愿意背的回归工作量。

这几条摞在一起，结论很清楚：3 在这套代码里不是技术选型，是一笔账。结尾有判据表。

3.x 的最小可跑骨架

把业务剥掉，一个 3.x 的入口长这样。这是我照着 app.js 手敲的最小版本，跑在本机 Node 0.10 上：

逐段标一句”这段到 4 里会变成什么”（4 的机制在 2016-04-26 那篇讲过，不展开）：

  • var app = express();——4 里写法一样，这行不用动。
  • app.set('view engine', 'jade')——4 里也这样设，区别在布局得靠别的办法，模板取舍归 2016-06-16 那篇一句带过。
  • express.favicon()、express.logger()——4 里没有了，要装 serve-favicon 和 morgan。
  • express.static(...)——4 里换成独立包 serve-static 挂上去。
  • express.json() / express.urlencoded()——4 里合并进 body-parser 包。
  • express.methodOverride()——4 里换成 method-override。
  • app.get / app.post 路由——4 里签名没变，变化的是它们排在哪里，见下文。
  • app.use(app.router)——4 里 app.router 这个属性直接删了，写了会报错。
  • app.listen(...)——4 里一样。

app.configure 按环境分支注册是 3 的标志性形态，4 里这个 API 整个被删，真实代价单独开一节讲。

中间件还挂在框架命名空间下

也是新老代码长相上最好认的差别：3 时代内置中间件全住在 express.* 底下，require('express') 一次拿全；后来这几个中间件各自拆成独立包，4 里用谁就得单独 npm install 谁。对照表：

3.x 里的写法 后来对应的独立包 备注
express.bodyParser() body-parser json + urlencoded + multipart 三合一
express.cookieParser(secret) cookie-parser 解析 Cookie 并签名
express.session(...) / express.cookieSession(...) express-session 默认内存存储那条警告也带过去了
express.methodOverride() method-override 表单 PUT/DELETE 靠它
express.static(...) serve-static 单独装
express.favicon() serve-favicon 单独装
express.logger() morgan 名字都换了
express.errorHandler() 无直接替代品 一般自己写错误中间件

读老代码我习惯全文搜 express.，搜出几处，升级就要补几个包。这套后台搜出 6 处，每处还得确认参数签名变没变。写法上的坑 2016-05-24 那篇列过六个，不复述。

单独说 express.bodyParser：JSON、urlencoded、multipart 文件上传三个解析器打包在一起。老代码里很多人（包括我前任同事）根本不用文件上传，也照模板挂它，因为”教程里都这么写”。方便，代价在下一节。

app.configure 的真实代价

app.configure(env, fn) 的问题不在丑，在于把注册顺序藏进了环境名里。生效顺序由注册先后决定，分支注册等于本地和线上跑两条序列。这套后台就在这上面翻过车。

五月底某天，测试同事说线上登录后进不去，本地却正常。看两遍代码没头绪，最后发现的现象是：线上有 session，本地没有。排查过程：

  1. 先怀疑登录接口，本地打断点，req.session 明明在；
  2. 对比两边启动日志，线上多打了一行 deprecated 警告，本地没有——说明进的不是同一个 configure 分支；
  3. 去线上看环境变量，NODE_ENV 是 production，本地我从没设过，默认走 development 分支；
  4. 打开 app.js，express.cookieParser 和 express.session 写在 app.configure('production') 块里，development 块只有 express.errorHandler——当年某次上线前临时挪过注册位置，本地这份再没人管。

本地跑的序列和线上根本不是同一条，代码却看着是同一份。app.configure 让分叉名正言顺：分支里随便 app.use，没人提醒顺序变了。4 删掉它之后，大家改在文件顶部读 process.env.NODE_ENV 再决定挂什么，分支至少摊在明面上。

显式 app.use(app.router)

老代码里有这么一行，卡在所有内置中间件之后、路由文件 require 之前：

第一次看到 app.use(app.router) 时我不明白它在干嘛。讲到这一层就够用了：每条 app.use 注册的东西变成一个带路径正则的 layer，请求按注册顺序逐个尝试，命中就把剥掉前缀的 url 交给下一层。app.router 自己也是个 layer，装着所有 app.get/app.post 注册进来的路由。显式挂它，等于亲手决定”路由”这一层排在队列哪一格。

这也解释了上面的顺序：静态资源挂在 router 前面，命中的请求走不到路由；session 类中间件也得挂前面，业务路由才拿得到 req.session。这一行的位置常是当年某次修 bug 挪出来的，动之前得想清楚挪的是谁——我读过的一些 3 的老教程甚至把它写在最前面。

4 里 app.router 这个属性没了，路由自动排在当时已注册的中间件后面（机制在 2016-04-26 那篇讲过，不重复）。升级要记住的只有一件事：老代码靠这行手工卡出来的相对次序，到 4 里得靠调语句位置重排一遍。

一次 bodyParser 写满 /tmp 的事故

六月中旬一个周三上午，测试环境整个打挂，不止这套后台，同一台机器上别的服务一起出问题。我先看磁盘：

/tmp 满了。老机器 /tmp 分区本来就小。谁在写？ls -lt /tmp 看一眼，全是 Express-Upload- 开头的临时文件，时间戳对上后台”批量导入名单”的入口。那功能一年用不了几次，业务同事那天早上传了十几个大 Excel。

凶手就是 express.bodyParser()。三合一里 multipart 那部分，默认把每个上传文件先落到系统临时目录再删。问题是那个入口根本不需要文件解析——表单传文本，Excel 走另一个自解析的接口。照模板挂 bodyParser，等于给每个请求开了落盘口子，碰上异常中断的请求，临时文件就留在 /tmp 没人清理。日积月累，加上那天集中触发，分区写满。

当期改法两条，都不动框架版本：

一是拆开三合一，通用接口只开 json 和 urlencoded；二是真要收文件的路径单独挂 express.multipart，临时目录指到数据盘，跟 /tmp 分开。清掉残留文件后机器恢复。以上是我在同一台机器上的粗略观察。教训跟 3 还是 4 关系不大，但它解释了为什么那行顺手挂的 bodyParser 没人敢随便删：你得先知道它在替谁干活。

express.session 的内存警告

3 的 express.session() 不指定 store 时用的是内置内存存储，控制台会打一条警告，大意是 memory store 只建议开发环境用、别拿到生产上（各小版本措辞略有出入，完整英文原文我贴不全）。这条 warning 第一次重启就糊在屏幕上，直到某次重启全员被踢下线，我才意识到它一直在响。

为什么会泄漏：每个会话一个对象，常驻内存，过期了也不一定回收。一天几百个登录不算多，但这台机器还跑着别的服务，内存本来就紧张。为什么老项目不急着换方案，讲一下我们的决策：

  • 换 express-session 加 Redis 存储？机器上多一个 Redis 就多一个运维对象，客户验收环境根本不给装。
  • 换 MongoDB 存储？这套后台数据库都是 MySQL，为 session 引入 NoSQL，动静太大。
  • 最后选了最保守的一条：改用 express.cookieSession()，会话数据签名后直接放 Cookie，反正 payload 只有一个用户 id 和权限标记；再把存活时间缩短，重启踢人的问题也随之变小（Cookie 在客户端，服务端重启无所谓）。

这条路线不装新包、不加服务，只改了 app.js 里两行注册。它是权宜之计——Cookie 体积上限、每个请求都带着会话数据这些毛病都有——但对一个”只求别再出事”的存量项目，改动面小就是最大的道理。

没有 Router 时怎么拆路由文件

express.Router 是 4 的东西，3 里没有这个对象（当年有个要手动开 feature flag 的试验版，我们没敢用）。老项目拆文件靠最土的办法：路由文件导出一个函数，把 app 递进去。这套后台的结构是：

app.param 是这套写法里唯一能把公共前置逻辑抽出来的口子：路径里出现 :userId，回调先跑，把查出来的用户挂到 req 上，后面每个路由省一次查询。它按参数名生效，升级时要挨个核对。

没有 Router 的代价很直白：所有路由平铺在同一个 app 上，没有子路由级的中间件。某模块想单独鉴权，要么每个回调手动调检查函数，要么给路径加统一前缀再靠中间件正则去圈。老代码里两种都有。那行注释也不冤枉人——next(err) 忘写的地方，出错时错误处理压根轮不到。

一个请求在 layer 链里怎么走

把前面几节串起来，按这套后台的注册顺序画出来：

flowchart TD
    A[请求进来] --> B[express.static]
    B -->|没命中| C[express.bodyParser]
    C --> D[express.cookieParser]
    D --> E[express.session]
    E --> F[app.router]
    F --> G[业务路由 如 /user/:userId]
    G -->|next 传了 err| H[express.errorHandler]
    G -->|正常| I[res.render 或 res.send]

再说一遍讲到那层就够：注册顺序就是队列顺序，命中意味着剥掉前缀往下传；layer 内部正则怎么构造，细节我没跟到底，不瞎说。要留意 express.errorHandler 在 3 里也靠注册位置决定生效范围——挂在 router 后面才接得住路由 next(err) 抛出的错。

坑攒到一起就是这张表，也是本文真正想留的东西：

阻障 现场表现 工作量
内置中间件要逐个装 express.* 下的调用全部变 undefined，每个都得装独立包并对参数 挂一处测一处
app.configure 直接报错 启动就 TypeError，环境分支全要重写 入口文件大改

结尾：什么样的老项目还能拖

维度 可以继续用 3 必须马上走 我们已经踩过的信号
人 还有碰过这套代码的老同事 唯一维护者已经离职 接手人只读过文档
需求 基本冻结，只补安全洞 新需求持续压进来 导入功能开始牵扯框架
环境 运行时锁死升不了 机器要换新 Node 验收环境还停在 0.10
告警 控制台干净 启动一屏 deprecated 警告 内存存储 warning 一直响
事故 半年没出过事 出过一次全站打挂 /tmp 写满那次

把话说明白：2016 年年中，Express 3 不是任何新项目该选的推荐项，它是存量项目过渡期里的一笔账。能继续放的，把三道闸装好；该走的，别等下一次 app.configure is not a function 才动手。
