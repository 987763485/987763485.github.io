MongoDB 聚合查询实践

一次把进程打挂的统计

6 月 3 号晚上九点多，群里贴出一张 504 的截图。那个报表页是我 2015 年底写的，逻辑很直白：find() 把最近一个月的订单全捞出来，forEach 里逐条往一个 JS 对象上累加。那天数据涨到 5 万条上下，Node 进程 RSS 到 800M 左右，接口跑一次四十多秒，数字都是同一台机器上的粗略观察，机器是 4G 内存的小规格云机，只当量级看。nginx 60 秒的读超时把连接掐了，运营看到的是空白页。

先把边界说清楚，本文不重讲这些：Node 的 stream 与背压机制另有一篇；回调并发上限与超时包装在 5 月 22 日那篇写过了；进程守护、cron 起 --eval 这类部署细节一句带过；前端页面怎么渲染也不在这里。文档模型、索引、分片这些基础只用一两句话铺垫，不做 MongoDB 入门巡礼，重点是我那天踩的坑：聚合管道怎么用才不会翻车。

复盘下来，5 万条文档在 JS 里过一遍，BSON 转 JS 对象吃掉一大块堆，分组的哈希表又是第二份拷贝。真正的错误是这件事根本不该在 Node 里做。线上是 MongoDB 3.2，默认存储引擎已经换成 WiredTiger，聚合管道能直接把分组求和的结果吐出来，我们要的是一张汇总表，不是一箱原始订单。

聚合管道的心智模型

把它想成流水线：文档从集合这头进去，穿过若干阶段，每个阶段只做一件事，输入一个文档集合、输出一个新的文档集合，上一段的输出就是下一段的输入。find 是把符合条件的文档原样交给你，聚合是把文档加工成另一种形状再交给你，这一句就是两者最本质的区别，其余都是细节。

flowchart TD
  A[orders 集合] --> B[阶段一 match 过滤]
  B --> C[阶段二 group 分组求和]
  C --> D[阶段三 sort 排序]
  D --> E[结果游标]

顺带记三个当年心里没底的点。除 $out 外的阶段基本边算边往游标里吐，得按游标消费，别指望一次拿到一个大数组；阶段顺序不同、结果一样但代价差几倍，$unwind 那节有实测口径；输出文档的形状跟原集合结构没关系，这就是它能替掉那 5 万条内存遍历的原因。

3.2 这一版能用的管道阶段就这么些：$match、$group、$project、$sort、$skip、$limit、$unwind、$out、$geoNear、$redact、$sample，加上这版新加的 $lookup。

常用阶段速过

$match：尽量往前提，顺便确认它吃不吃索引

$match 是唯一能明显减少后续工作量的阶段，放最前面，进管道的文档就少，后面的 $group 才不容易撑爆内存。吃没吃索引不是靠猜：过滤条件要写成能命中索引的形式，等值字段和范围字段建在同一个复合索引上，用 explain 看有没有走 IXSCAN，后面有实测片段。有个坑值得记：把日期写成 $where 那种函数判断，或者拿字符串去比 Date，索引直接废掉。

$group：_id 是复合键，累加器决定你要的形态

分组的键统一挂在 _id 上，可以是单个字段，也可以是一个对象当复合键，跟 MySQL 的 GROUP BY 列清单一个意思，只是形状变了。常用累加器就那几个：$sum、$avg、$push、$addToSet、$first、$last。要计数就用 $sum: 1，一条文档加一，这是当期唯一稳的计数路子。$push 把整组塞成数组，看着方便但很容易造出巨型文档，16MB 那节再说。另外 $first、$last 只保证按进来的顺序取首尾，想按时间取最后一条必须先 $sort，否则结果每次都变。

$project / $sort / $skip / $limit

$project 干两件事：挑字段和算字段。1 是包含、0 是排除（_id 默认带出来，要它消失就显式写 "_id": 0），右边给表达式就是新算出来的字段。包含和排除不能混着写，除了排除 _id 这一个例外，我第一次就撞在这条上。$sort、$skip、$limit 直白，位置很关键：先 $sort 再 $skip/$limit，分页才稳定；$sort 越靠前要排的文档越多，能用索引省掉就别在管道里排。

金额字段存的是分（整数），管道全程 $sum 整数，最后才 $divide 出元。早先存的是浮点元，5 万条加起来末位跟 MySQL 对不上，差了十几块，才知道是累加顺序带来的浮点误差。

日期切分是这一节真正要说的。能用的切法就两种：$year/$month/$dayOfMonth 把 Date 拆成数字，或者拿 $substr/$dateToString 把时间拼成字符串。麻烦在于这版日期操作符按 UTC 算，没有时区参数可用，而我们是东八区：北京时间 0 点到 8 点这一截，UTC 还停在昨天，每天头八小时的单会被归到前一天，5 月 31 号晚高峰有几单跑进 6 月报表就是这段。

当期两种口径。一是库里只存 UTC，管道里手工加 8 小时的毫秒数再切日期，数据干净但偏移散落各处容易漏。二是入库那一刻就冗余一个 day 字符串字段，按东八区格式化好，报表直接按 day 分组。我们最后定了后者，历史数据跑脚本回填，口径写进文档：天粒度报表以 day 为准，createdAt 只做范围过滤。改完后跟 MySQL 对账连续两周没差过。

$unwind 的两个坑

$unwind 把数组字段拆成多条文档，一个三件商品的订单拆成三条。

第一个坑：字段不存在、值是 null 或者空数组时，这条文档会直接消失，不报错。我们统计”有商品行的条数”和”订单总数”差了 3000 多条，扒开看是取消单的 items 存成空数组，$unwind 之后无声蒸发。3.2 里这个阶段带两个选项：preserveNullAndEmptyArrays 把缺失和空数组的文档留着，includeArrayIndex 顺带输出下标。这两个参数在你那个小版本里能不能用别猜，测试环境跑一遍就知道。就算开了保留，后面补一段 $match 把 null 单独算一支，也比靠默认值明白。

第二个坑是顺序。有一版我把 $unwind 放在 $match 前面。订单 5 万条、items 平均 8 件左右，展开就是 40 万条文档进管道，过滤条件白算一遍。同一条需求，$match 在前两秒出头，$unwind 在前十一秒上下（同一台机器上的粗略观察，只当量级）。口诀就一句：能让文档变少的阶段往前放，会让文档变多的往后放。

$lookup：3.2 新增，能用但别当 JOIN 用

报表还要带商品名。订单只存 sku，名字在 products 集合，这步以前只能在 Node 里循环查或者把名字冗余进订单。$lookup 是这版新加的，省掉一次往返，也算 3.2 值得升的理由之一。

它能做的：同一个数据库内，把左表文档和右表匹配到的文档组成数组，挂到你指定的字段上。它不能做的：跨数据库；指定匹配走哪个索引；结果仍是数组，要变单值还得 $unwind 一遍。我们拿 5 万条订单关联 2 万条商品粗略对比过，同机跑三遍取中间值：$lookup 写法十四秒上下，应用层先把 sku 到名字的映射读进内存再组装四秒左右，订单里预冗余 productName 直接查一秒多（同一台机器上的粗略观察，只当量级看）。右表缺索引时它的代价随左表条数线性放大，跟关系库 JOIN 一个道理，但你没法给它指定执行计划。

结论写进了组内规范：能预冗余就预冗余，只有历史数据补齐和低频报表才用 $lookup，别拿它当关系型 JOIN 天天跑。

结果集与内存：两半问题

撞墙撞在两个地方，解的是两个不同的问题，别混。

一处是单个结果文档超 16MB。这是 BSON 的硬上限，跟管道无关，但管道特别容易自己造出来：$push 或 $addToSet 把一个分组的上万条原样塞进数组，算到最后吐不出来。当期报错文案里出现的是 exceeds maximum allowed BSON object size 那一类，小版本不同措辞略有出入。这堵墙 allowDiskUse 没用，只能改形状：累加用 $sum，别把明细堆进数组，非要看明细就按更细的键分组，或者 $out 到另一个集合再翻。

另一处是某个阶段超出内存限制。$group、$sort 这类要等上游全到齐的阶段在服务端有内存配额，超了就断，我们那次的原文是 Exceeded memory limit for $group, but didn't allow external sort. Pass allowDiskUse:true to opt in.。传 { allowDiskUse: true } 允许中间状态落临时文件就通了。代价是慢：同机粗测从两秒出头变八九秒（粗略观察，量级口径），所以只在预计算任务里开，在线接口宁可把 $match 范围收窄。

还有第三半是客户端。batchSize 管每次从服务端取多少条，服务端该算的照样算，它不解内存，解的是别把结果一次全灌进 Node 进程。我原来那次 toArray 一把梭，5 万条转成 JS 对象全压在堆上，改成按批消费后 RSS 稳在一百多兆。

看到 IXSCAN，且 totalDocsExamined 跟 nReturned 一个量级，索引就吃到了。四条经验。一，复合索引把等值条件放前、范围条件放最后一位，我们那版 createdAt 在前的索引帮不上 channel 的等值过滤。二，抓瞎那回就是索引建在 createdAt 上而查询传了字符串，直接退回 COLLSCAN。三，$sort 字段如果在同一个复合索引里，能省掉一次阻塞排序。四，explain 只给第一段的计划，后面的阶段和内存它不讲。

$out 把报表预计算成另一个集合

在线接口算不动的报表，最后都挪成了定时任务。每小时跑一遍前面天 × 渠道 × 状态那条管道，加一段 $out 把结果整体写进 daily_report，页面只查这个集合，接口从四十多秒掉到几十毫秒（同机粗略观察）。

坑在于 $out 会整体替换目标集合。先写临时集合再改名听着安全，可要是直接 $out 到页面正在查的那个名字上，替换那一瞬间加上聚合跑挂留下的空窗，页面会读到半截甚至空表，我们第一版就这么干的，凌晨报表页空了二十分钟。当期两步规避很朴素：管道先 $out 到 daily_report_tmp，跑完确认条数对得上，再用一个极短脚本把旧集合挪成备份名、把临时集合改成正式名。切换那几秒可能读到旧数据，报表能接受，比空窗好。结果集合的索引要重建，_id 是那个复合键，按 day 查得自己补。定时任务只是 cron 里一条 node --eval 起脚本，细节不展开。

Node 侧完整可跑示例

驱动是 mongodb 2.x 这一代，Node 跑在 4 LTS 上（6.0.0 刚放出，还没上生产）。aggregate 三个参数：管道、选项、回调，回调拿到的是游标不是结果数组。

关游标记两条：each 收到的 doc 为 null 才算跑完，这时先 cursor.close() 再 db.close()，漏掉 close 进程挂着不退；每条错误分支都要把库关掉。跑出来的输出。

回调套三层看着难受，后来用 bluebird 的 promisify 包了一层，这里不展开。

从 MySQL 搬过来的语义差异

报表从 MySQL 挪过来的头两周，栽的全是语义差，成表记一下。

MySQL 里的东西 聚合里的当期写法 我们踩的那一下
HAVING 分组之后再接一段 $match 以为累加器能带条件，白跑一遍
COUNT(*) $group 里写 $sum: 1 找计数阶段找了半天
GROUP BY 列清单 全部塞进 _id 这个对象 少写一个键，结果少一个维度
隐式类型转换 类型必须严格对上 拿字符串日期比 Date，$match 空结果，抓瞎一下午
LEFT JOIN $lookup 保留左表，右表给空数组 后面跟 $unwind 就变成内连接，条数莫名变少

补一句：_id 一定存在，聚合结果不给它也会带着，$project 里显式写 "_id": 0 才去掉。

Map-Reduce 的当期定位

它还能用，db.runCommand 那套写法我们留着没删。改回管道的判据就一句：三段聚合写不出来的逻辑才考虑它。真实缺点是慢和占内存，JS 函数逐条跑，结果还要先落临时集合再合并，同一张报表比聚合管道慢三四倍（同机粗略观察），而聚合是在服务端 C++ 里执行的。原先三段改完，代码少了两百行，出错也好定位。

什么时候用哪条路

情况 选什么 一句理由
几万条以内、口径天天变、就一个页面要看 聚合管道直出 少养一张结果表
条数上到几十万、每次打开都要算 $out 预计算集合 把代价挪进定时任务
只是给几个已知 id 补名字，或者口径得在应用层判断 应用层组装 管道磨三小时不如循环十行

那条 504 的接口最后是这么收场的：在线的那半截只查 daily_report，聚合挪进每小时一次的定时任务，allowDiskUse 只在任务里开。Node 那 5 万条遍历一行没留。
