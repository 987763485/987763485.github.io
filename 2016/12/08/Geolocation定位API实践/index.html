Geolocation 定位 API 实践

去年做连锁门店的移动端列表页，需求很朴素：按距离排序，卡片上显示“距你 1.2 公里”。第一版直接拿 getCurrentPosition 回调里的经纬度算直线距离，前端排完序渲染。楼下测试时数字看着合理，上线一周后客服转来一条反馈：用户站在门店门口，页面显示 800 米。

排查出两层原因。第一层是坐标系：浏览器给的是 WGS-84，门店坐标是从国内地图服务商后台导出的 GCJ-02，两套坐标在国内相差几百米，混在一起算，误差比门店的服务半径还大。第二层是精度：那次请求返回的 coords.accuracy 是 1200，意思是浏览器自己只敢保证这个点在一公里出头以内，我却把它当成了精确值。

真正花时间的不是记住 API，而是知道它什么时候不准、不准到什么程度，以及不准时给用户看什么。

门店列表里的那 800 米

先把需求拆开看。门店列表要的是“谁离我近”，本质上是一次排序，排序键是用户位置与门店坐标之间的球面距离。距离本身不需要多准，但排序键必须可比：如果用户坐标偏了八百米，而最近两家门店之间只隔三百米，顺序就会翻掉，用户看到的“最近门店”其实是第二家。

这里的坑在于，定位误差在页面上是不可见的。号码显示得越具体，用户越会当真。“距你 1.2 公里”和“距你 1234 米”给人的信任度完全不同，但底层可能是同一个精度只有 1200 米的点。所以第一版真正的问题不是算错了，而是把一个粗糙的估计当成确定值展示，还拿它做了排序。

后面三节分别处理基准对齐、精度判断和高误差时的文案。

navigator.geolocation 的三个方法

接口挂在 navigator.geolocation 上，2016 年主流浏览器都是这个入口，不需要前缀。三个方法各司其职。

getCurrentPosition(success, error, options) 是一次性取值：调用后浏览器向系统要一个位置，成功或失败后回调一次就结束。适合“打开页面时定位一次”的场景。

watchPosition(success, error, options) 是持续订阅：返回值是一个数字编号，位置变化时反复触发 success；失败时触发 error，但订阅不会因为报错自动结束，只要页面还在，它仍可能继续尝试。第一次回调通常来得很快，浏览器会先交出缓存点。

clearWatch(id) 用 watchPosition 返回的编号取消订阅。不调用它，订阅会一直挂着，移动端上就是持续的定位模块唤醒与电量消耗。

两个回调的签名是固定的，参数顺序别记反：

position 上只有 coords 和 timestamp 两个字段。coords 里真正可靠的是 latitude、longitude、accuracy 三个；altitude、altitudeAccuracy、heading、speed 在手机上可能为 null，桌面端基本全是 null，不要拿它们做分支判断。timestamp 是定位数据的产生时刻，不是回调执行的时刻，命中缓存时可能是几十秒前。

PositionOptions：三个参数的真实含义

第三个参数看起来简单，实际上三个字段的含义和字面意思都有偏差。

enableHighAccuracy 不是“提高精度”的开关，而是“允许浏览器使用更耗电的定位源”。移动端上它意味着优先启用 GPS 而不是 Wi-Fi 与基站；桌面端上基本没有可切换的硬件，设成 true 往往只是让等待变长。它不能保证结果更准，只保证浏览器愿意花更大代价去试。

timeout 是从调用开始到回调的最长等待时间，不是“这次测量最多算多久”。设成 0 或者不设，行为由浏览器自行决定，可能立刻返回缓存，也可能一直等下去。工程上要显式给值，比如十秒，让失败变成可预期的分支。

maximumAge 允许复用多久以内的缓存位置，单位毫秒。0 表示不复用缓存，必须重新测；不设则浏览器可以随意给一个旧点。这个参数常被忽略，但它对首屏速度的影响比 enableHighAccuracy 更直接：门店列表这种场景，一分钟内的缓存完全够用，把 maximumAge 设成 60000 能省掉一次完整的定位等待。

三个参数要组合着看。想要“快”就用低精度加长缓存；想要“准”就开高精度、把 maximumAge 归零、timeout 放宽。两者都要时只能分两次回调：先用缓存点把列表渲染出来，再等高精度结果回来做一次静默更新。

室内为什么慢也在这里。GPS 信号被楼板挡住，浏览器退到 Wi-Fi 与基站，要扫描周边热点再发给定位服务查询；enableHighAccuracy 为 true 时它会先试 GPS 直到超时才回退，室内的等待往往直接吃满 timeout。

错误对象与三种兜底

错误回调拿到的是一个 PositionError，有用的只有 code。message 是浏览器给的英文描述，各浏览器措辞不一，既不能展示给用户，也不能拿来做判断。

三个错误码对应三种完全不同的处境，兜底方式不能混。

PERMISSION_DENIED，值为 1，表示用户拒绝了授权，或者当前上下文根本不允许定位。这种情况下重复调用 API 只会立刻再失败一次，再弹一次浏览器自己的授权框是不可能的——被拒绝之后，页面没有第二次机会。正确做法是记下这个状态，把“重新定位”换成“手动选择城市”。

POSITION_UNAVAILABLE，值为 2，表示定位源不可用：系统定位服务被关掉、设备在飞行模式、桌面浏览器连不上它依赖的定位服务。这类不是用户针对页面的选择，提示应指向系统设置，同时切到 IP 定位或手选。

TIMEOUT，值为 3，表示在 timeout 内没拿到位置。它最像“临时故障”，值得放宽时间重试一次；第二次仍然超时，就不要再试了，直接降级。室内场景里这个码出现频率最高，重试一次往往还是同样的结果。

把三种情况塞进一句“定位失败，请重试”，用户点十次也不会成功。

权限模型与安全上下文

授权的界面不属于页面。浏览器自己弹地址栏下方的提示条，用户选“允许”或“阻止”，页面插不上手。用户选过之后浏览器会记住，同一个源再次调用不再询问；被阻止过的源，页面无法主动把授权框再叫出来，只能引导用户去地址栏左侧的站点设置里改。所以首次定位前要有一句自己的说明，而不是等浏览器弹框让用户猜。

第二个限制是安全上下文。2016 年的情况是，Chrome 从 50 版起就在非安全上下文里直接让 getCurrentPosition 失败，返回的是 PERMISSION_DENIED；Firefox 50 同样只在 HTTPS 或 localhost 下放行；Safari 10 也要求 HTTPS。也就是说在 http:// 的测试环境里，代码写得再对也拿不到坐标，而且错误码指向的是权限，很容易误导排查方向。

支持面也不能一概而论。IE 11 有这套接口，背后走的是 Windows 系统定位服务，行为与规范有出入，组策略可以直接关掉它。Android 4.4 的 WebView 更特殊：WebView 默认拒绝网页的定位请求，宿主应用必须在 AndroidManifest.xml 里申请定位权限，并实现 WebChromeClient.onGeolocationPermissionsShowPrompt，在回调里显式同意，网页才会收到位置。嵌在 App 里的页面如果一直失败，先查宿主这一层。

坐标系：WGS-84 与 GCJ-02

回到开头那 800 米。浏览器给的是 WGS-84 坐标，GPS 芯片输出的原始值；国内地图服务商使用的底图是 GCJ-02，俗称火星坐标，是在 WGS-84 上做了一次非线性偏移的结果。两套坐标在国内的差值不是固定常量，随经纬度变化，量级在几百米，城区里常见三四百米，个别位置更大。所以“知道了偏移量就统一加个固定值”这条路走不通。

更麻烦的是还有第三套：百度地图用的 BD-09，在 GCJ-02 上再偏一次。同时接了地图展示和定位的项目，第一件事是给每个数据源标上基准。

转换的方向性也要说清楚。WGS-84 到 GCJ-02 有公开的近似算法，用一组基于经纬度差的多项式做偏移，工程上够用；反方向没有解析逆运算，只能迭代逼近：先猜一个点，正向偏移后与目标值比较，把残差补回去，两三次即收敛到米级。下面这段是反解的形状，正向函数按公开算法实现即可。

调用边界比算法本身更重要。我们的做法是把转换收敛到一个模块，只暴露两个函数：入库存 WGS-84，渲染给国内地图前统一转 GCJ-02。用户坐标和门店坐标都走同一条路，绝不出现一边转一边不转的情况。设备侧也一样：navigator.geolocation 的基准在不同系统上不一致，我们在 iOS 10 与 Android 4.4 WebView 上实测就对不上，只能靠自测确定。

精度、Haversine 与排序阈值

coords.accuracy 是以米为单位的半径，表示浏览器认为真实位置有较大概率落在以返回点为中心的这个圆内。它是这组坐标的有效期说明。规则很直接：精度超过 500 米的结果只用来决定“大概在哪个商圈”，不参与精确排序；超过 2000 米直接丢弃，走降级。

距离用 Haversine 公式算球面大圆距离，不需要投影。半径取 6371 公里，误差在门店场景里可以忽略。

排序时要给误差留余量。两家门店的距离差小于用户精度时，谁在前都没意义，可按“距离减精度”再排一次，或把并列的几家标成“附近”。展示阈值同理：500 米内写“就在附近”，一公里内写“约 800 米”，再远写公里数。数字越粗越不容易被打脸。

watchPosition 的节流与清理

watchPosition 的默认回调频率不可控，设备一动就可能连续触发，每次都重算全量距离并重排 DOM，低端安卓机上会明显卡顿，更主要的问题是耗电。我们加了两道闸：两次处理至少隔 10 秒；新点与上次处理的点相距不足 50 米就丢弃。任一闸放行才处理。

停止订阅的时机要覆盖全。页面切到后台时用 visibilitychange 判断 document.hidden，隐藏就 clearWatch，回到前台再重新订阅；路由切换、组件卸载时也要清；pagehide 里再兜一次。移动端切后台后定时器会被节流，定位订阅却不一定停，不清掉的话用户关页面前电量一直在掉。

降级方案与 PC 端的现实

定位失败之后给什么，比定位本身更影响体验。我们准备了三级：先试 IP 定位，服务端按请求 IP 查库，拿到城市级坐标，误差几公里到几十公里，快且不需要授权，但代理和移动网络出口会把它指到别的城市；再退到用户手选城市，最稳，代价是多一次交互；已登录用户可用手机号归属地兜底，但归属地是开户地，不是当前位置，只能决定默认展示哪个城市。

隐私上要有取舍。IP 定位不需要同意，却把位置暴露给服务端日志，页面上应有一句说明；浏览器定位的授权是显式的，反而更干净。手选城市不采集位置，没有隐私成本，值得放在显眼位置而不是藏在失败提示里。

PC 端要单独说。桌面浏览器没有 GPS，Chrome 靠扫描周边 Wi-Fi 把热点信息发给 Google 的定位服务换坐标，国内网络下这个请求经常不通，结果就是长时间等待后返回 POSITION_UNAVAILABLE。此时的提示不能写“请开启 GPS”，用户没有这个开关；应该写“浏览器无法获取位置”，并把手选城市放在旁边。IE 11 走 Windows 定位服务，能不能用取决于系统设置和组策略，同样不能假设可用。

小结与速查表

定位 API 的代码量很小，难点全在边界：精度是半径不是误差上限，坐标系要先对齐再计算，权限被拒之后没有第二次机会，后台的订阅必须主动关掉。把这几件事写进封装层，业务代码只处理“有坐标”和“没坐标”两种状态，门店门口显示 800 米这种事才不会重演。
