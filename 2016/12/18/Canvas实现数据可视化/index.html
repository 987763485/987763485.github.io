Canvas 实现数据可视化

2016 年秋天，我接手订单后台首页的改版。运营在需求单上只写了三行：一张订单趋势图，支持近 7 天与近 30 天切换；鼠标移上去显示当天单量和金额；点击某一天跳到订单列表并带上日期筛选。看起来是图表库拖一个配置项就能交差的事，最后却写成了一个小型绘图引擎。本文记录这个过程：如何在 Canvas 上把数据变成像素，如何处理断点、负值、上万点的抽稀，以及交互和动画怎样不拖慢主线程。适合已经会画线、但还没写过完整图表的读者。

从一张订单趋势图说起

需求本身不复杂，难的是它要长得和设计稿一模一样，还要接进现有的路由和状态管理。

为什么不用现成的库

团队评估过引入图表库。功能上它完全够用，问题出在三个地方。第一是定制：设计稿的 tooltip 是自定义排版，要显示环比箭头和两张小卡片，库的 formatter 能拼 HTML，但样式、定位、边界翻转都要和库的内部实现较劲。第二是体积：完整包压缩后仍有几百 KB，而首页为这一张图多加载这么多脚本，首屏时间要往后挪。第三是行为：点击柱子要跳路由并携带筛选参数，意味着要把图表事件接到我们自己的状态上，封一层适配的成本不比直接画低。

库当然也能做这些事，本文不展开它的配置。真正让我下决心的是另一件事：这个页面后面还要加库存周转图、退款率图，形状都很简单，不是折线就是柱状。与其为每张图读一遍库文档，不如写一个只服务这几张图的小引擎，行为完全可控。

目标与边界

我给自己定了四条约束：

  • 只依赖 Canvas 2D，不引入任何第三方运行时；
  • 折线图与柱状图两种形态，支持多序列、null 断点、负值；
  • 交互按数据索引命中，不逐像素试探；
  • IE 11 能跑，所以代码用 ES5 写，不依赖 Path2D 这类它没有的接口。

最终是两个文件，一个管比例尺与布局，一个管渲染与交互。下面按“坐标、比例尺、布局、绘制、交互、性能”的顺序展开，每节给出可以直接运行的片段。

画布、像素与坐标系

Canvas 有两个尺寸，这是所有清晰度问题的源头，也是必须一开始就定下来的约定。

一个是 CSS 尺寸，由样式表决定，用户看到的就是它；另一个是位图尺寸，即 canvas 元素的 width/height 属性，决定实际有多少像素可画。浏览器把位图按 CSS 尺寸拉伸显示。两个尺寸相等时，在 dpr 为 1 的屏幕上刚好一一对应；在高分屏上物理像素是 CSS 像素的两倍或三倍，位图被放大，线条和文字就糊了。

做法没有悬念：位图尺寸乘以 dpr，再用 setTransform 把绘制坐标系缩回 CSS 像素。

这段代码有三个容易漏掉的点。

第一，给 canvas.width 赋值会重置整个上下文，包括变换矩阵、样式和裁剪区。所以必须先改尺寸再 setTransform，顺序反了等于没设。

第二，缩放之后代码里的坐标仍然是 CSS 像素，布局、比例尺、命中检测共用同一套单位，不必在每个地方乘 dpr。这是把复杂度关进一个函数的关键。

第三，dpr 要封顶。dpr 为 3 的手机上，一张 1200×400 的图画出来是 3600×1200 的位图，内存是 dpr 为 2 时的两倍多，肉眼却几乎分不出差别。我们封在 2，代价是大屏手机上略软一点，换来滚动时更稳的帧率。

半像素不是玄学

画一条 1px 的竖线时，如果给它整数坐标，比如 x 等于 100，线宽会向两侧各扩 0.5，落在 99.5 到 100.5 之间，跨了两个物理像素，浏览器只能各画一半透明度，结果是一条两像素宽的浅灰线。常规解法是加 0.5，让线心落在像素中心。

比例尺：从数据域到像素域

图表的本质是一次映射。数据有它的取值范围，称为 domain；绘图区有它的像素范围，称为 range；比例尺负责把前者线性压到后者。折线图的 y 轴范围是反的，数值大的在上面、像素值小，所以 range 从下往上写。

这里有个约定：domain 必须有限且非退化。全为 0、只有一个点、混进 null 时，max 减 min 会得到 0 或 NaN，整张图就空了。处理办法是先过滤非有限值，空数组用 0 到 1 占位；max 等于 min 时向两侧各撑开一个单位。

让刻度落在 1、2、5 上

直接拿数据的最小值和最大值当轴范围，会得到 37.2、138.6 这种刻度，读起来费劲。目标是让相邻刻度的差落在 1、2、5 乘以 10 的整数次幂上，这也是手绘图表时的老习惯。

算法分四步：先按目标刻度数估一个原始步长；取它的数量级；把归一化后的系数向上取到 1、2、5、10；再按步长把两端向外取整。

返回的 decimals 用来格式化标签，步长是 0.5 就保留一位小数，步长是 1000 就不带小数。不要用 parseFloat 之后再 toString，浮点误差会让 0.3 显示成 0.30000000000000004。

柱状图的 y 轴还有一条规则：domain 必须包含 0，否则柱子长度不再和数值成正比。折线图没有这个约束，可以贴着数据范围画，起伏更明显。

时间轴

时间轴不能按数值步长切，因为一天不总是 86400000 毫秒，月份长度也不固定。做法是准备一张候选间隔表，从 1 分钟、5 分钟、15 分钟、半小时、1 小时、3 小时、6 小时、12 小时、1 天、2 天、1 周，一直到 1 个月、3 个月、1 年，选第一个让刻度数不超过上限的间隔。

确定间隔后，不能从第一个数据点开始累加，否则刻度会落在 10:17 这种位置。要先把起点对齐到单位边界：小时对齐到整点，天对齐到零点，月对齐到 1 号，再按单位递推。跨夏令时的日期在本地时区里可能少一小时或多一小时，按本地时间构造 Date 再取整，比直接加毫秒安全。

标签格式随跨度切换：同一天内只显示时和分，跨天显示月和日，跨年才带上年份。判断依据是刻度数组的首尾，不是数据本身，因为轴的范围被 nice 过，可能比数据宽出一天。

布局、坐标轴与网格

绘图区不是整块画布。四周要留给刻度标签、轴标题，折线图顶部有时还要放图例。这些留白统称 padding，但它的数值不能拍脑袋写死，左边的宽度取决于 y 轴标签有多宽，底部的宽度取决于 x 轴标签有多高。

先算布局，再画

布局是尺寸、字体和刻度的函数，跟动画帧无关，所以只在尺寸变化、数据变化、样式变化时算一次，结果挂在实例上。绘制函数只读布局，不做测量。

计算顺序有一个循环依赖：y 轴标签宽度决定左边距，左边距决定绘图区宽度，绘图区宽度又决定 x 轴刻度密度和底部高度。打破它的办法是分两遍。第一遍只算 y：y 轴刻度只依赖高度，先定 domain、步长和标签，量出最宽的一个，左边距就有了；第二遍用剩下的宽度算 x 轴刻度和标签高度。如果底部高度变化超过一行，最多再迭代一次就够了，不要写成 while 循环等它收敛。

布局对象一旦生成，每帧只做两件事：清屏、按它画。这一点直接决定了拖拽时会不会卡，因为 measureText 和刻度计算在移动端并不便宜，放在 mousemove 里每帧跑一遍，掉帧是必然的。

轴、网格与标签对齐

网格线和服务于阅读的参考线只画横向，刻度值跟着 y 轴走。竖向网格在折线图里会把画面切碎，除非是时间序列且需要对齐日期，这一点按设计稿来。

y 轴标签用 textAlign 为 right、textBaseline 为 middle，画在轴左侧固定距离处，这样不同位数的数字右端对齐，视觉上贴着轴线。x 轴标签用 textAlign 为 center、textBaseline 为 top，纵坐标是绘图区底部加 8。这两个基线值写错，标签会整体偏移半个字高，比字体大小不对还明显。

零线要单独加重，颜色比网格深一档，因为它是柱状图和面积图的基准，读者会下意识找它。

标签重叠是绕不开的。30 天数据在 600px 宽的容器里，每个标签约占 30px，加上间距就不够了。抽稀有两种策略：等间隔抽取和贪心避让。等间隔是算出最小间距除以刻度间距，向上取整得到步长，每隔 step 个画一个；贪心是从左到右，谁放得下就放谁。

我选等间隔，因为时间轴的标签代表等距的时间，随机丢掉几个会让人误判密度。贪心适合类目轴，标签长短不一，能多显示一个是一个。等间隔也有尾巴问题：末位刻度可能被跳过，读图的人看不到最新一天。检查末位与上一个已画标签的距离，不够就减少一档刻度数重算，而不是硬塞。

折线图：路径、断点与面积

折线看着最简单，坑却集中在两处：缺失值怎么处理，以及填充区域的边界。

一条路径画完

一个序列只开一次路径，顺序遍历点，遇到有效值就 moveTo 或 lineTo。用一个布尔量记住笔是否落下，遇到 null 就抬笔，下一个有效点重新 moveTo。这样断点两侧不会被一条直线连起来。

为什么不默认把断点连起来：那等于替用户编造了一段数据。订单系统里某天没有数据，可能是真的零单，也可能是埋点漏了，画成直线会把两种情况混为一谈。所以断点默认断开，另外提供一个 connectNulls 开关，由使用方显式打开。

断点还带来一个细节：孤立点只有 moveTo，没有 lineTo，stroke 出来什么都没有。当某个点前后都是断点，或者整个序列只有一个点时，要额外画一个小圆点，否则这个数据在图上等于不存在。

面积与渐变

面积图的路径是折线再加两段：从最后一个点垂直落到基线，沿基线回到第一个点，闭合。基线取 0 所在的 y 位置；如果 domain 不含 0，就取绘图区底部，并在轴标题里写清楚，免得读者以为面积正比于数值。

有断点时不能一条路径填到底，否则填充会把缺口跨过去。正确做法是把连续的有效点切成若干段，每段单独构成一个闭合路径分别填充。段与段之间的渐变要对齐同一个坐标系，不能每段重新按自己的包围盒建渐变，否则颜色深浅会跳。

渐变对象按布局缓存，布局不变就复用；它依赖绘图区的上下边界，尺寸一变必须重建。

线宽 2px 时整数坐标就够清晰；1px 细线按前面的规则对齐设备像素。lineJoin 用 round，折线拐角不会出现尖刺。

柱状图：band、分组与堆叠

折线的 x 是连续的，柱状的 x 是离散的。同一个日期在折线里是一个坐标，在柱状里是一段有宽度的区间，所以需要另一种比例尺。

band 比例尺

band 比例尺把 n 个类目分到一段像素区间里，每个类目拿到一个起点和一个带宽。两个参数控制留白：inner 是类目之间的间隙占步长的比例，outer 是两端留白占步长的比例。

indexAt 是后面命中检测要用的反向映射，和 linear 的 invert 是同一个思路：能正着算，就一定能反着算，不要靠遍历。

默认 inner 取 0.2，柱子之间留一点缝；如果设计稿要求柱子紧挨着，把 inner 设成 0，但相邻柱子的边界要落在设备像素上，否则两段半透明的边缘叠在一起会出现一条深色细线。简单办法是每根柱子的宽度向下取整，右边留 1px 空隙。

分组与堆叠

分组柱是一个 band 里再切一刀。先算出组的带宽，再按序列数做一次等分，每根柱子拿到 groupWidth 除以序列数，中间再留一点缝。三个序列以上就不适合分组了，颜色和图例都难认，这时应该换堆叠。

堆叠柱要维护正负两个累加器，正值往上叠，负值往下叠，否则一正一负会互相抵消，柱子长度对不上任何真实数值。

圆角只加在数值一端：正柱顶、负柱底，用 arcTo 拼路径，2016 年的浏览器还没有 ctx.roundRect。半径要夹在柱宽和柱高的一半以内，堆叠时只给最外层那一段加，中间保持直角。

还有一个细节：数值很小但非零时，高度可能不到 1px，看起来像没有数据。给非零值保底 1 个设备像素，并在 tooltip 里给出精确值。

绘制顺序、合批与命中检测

一张图每帧要画的东西不少，但顺序是固定的，状态切换也是可以合并的。

分层与顺序

从下到上依次是：背景、网格、坐标轴、面积填充、折线或柱子、十字辅助线、高亮标记。tooltip 不放 Canvas，用绝对定位的 DOM 节点盖在上面。理由很实际：DOM 里的文字可以被选中、可以用 CSS 排版、可以超出画布边界，也不用自己做文本换行和测量。

同一层内部的绘制要按样式分组，而不是按数据分组。所有网格线进一条路径，stroke 一次；所有同色的柱子进一条路径，fill 一次；坐标轴和刻度线再单独一笔。这样每帧的 beginPath 从上百次降到个位数。

beginPath 本身不贵，贵的是状态切换和阴影、模糊这类效果。合批的收益是减少调用次数、让同色图元一次填充；不同颜色的柱子塞进一条路径没有意义，最后还是要分开 fill。不要给每个点加 shadowBlur，它会让帧率掉一个数量级。

命中检测：反查索引，不逐点试

很多人第一反应是用 isPointInPath 遍历每个点，或者给每个数据点建一个小圆去试。这条路在小数据量下能跑，但有三个问题：需要为每个点构造路径，开销是 O(n)；线本身只有 2px 宽，鼠标稍微偏一点就选不中；Path2D 在 IE 11 里没有，isPointInPath 只能针对当前路径判断，循环时还得反复重建路径。

图表的命中是二维问题降成一维：用户只关心“鼠标离哪个日期最近”，y 方向不必精确。所以只做 x 轴反查：

时间序列的 x 通常等距，可以直接用除法算索引，O(1)；但遇到不规则采样或者数据被抽稀过，就必须二分。二分的前提是 xs 有序，这一点在数据入口处校验一次，不要每帧都检查。

柱状图的命中更简单：用 band 的 indexAt 算出类目下标，再判断是否落在柱子的实际矩形内。分组柱要先减掉组内的偏移，堆叠柱还要判断 y 是否落在这一段的高度区间里。这些判断都是几次减法，不需要路径。

isPointInPath 也不是完全不用，它适合形状不规则的图元，比如以后要加散点或者自定义标记。用的时候把路径缓存成 Path2D，判断时传进去，只在支持 Path2D 的环境启用，IE 11 下降级为矩形近似。这是能力检测，不是版本判断。

交互与动画

图表卡不卡，一半看绘制，一半看事件。鼠标每秒能触发上百次 mousemove，如果每次都同步重绘，主线程就被占满了。

用 rAF 合并移动事件

思路是把事件处理和绘制解耦：mousemove 只记录坐标，然后预约一帧；如果在帧到来之前又来了新事件，直接覆盖坐标。这样一帧最多画一次，而且始终画的是最新位置，不会像定时器节流那样出现拖影。

十字线与 tooltip

十字线是一条竖直虚线，画在吸附后的数据点 x 上，而不是鼠标的原始位置。吸附让用户感觉“选中了某一天”，也让 tooltip 的内容和线对得上。横向辅助线可选，多序列对比时有用，单序列时容易和折线混在一起，默认关掉。

高亮点画一个白底彩边的圆，半径 4 到 5 像素。顺序上它必须在折线之后画，否则会被线盖住。

tooltip 用 DOM，定位用 transform，避免改 left/top 触发重排。默认放在光标右上方，超出容器就翻到左边，上方放不下就翻到下方。

offsetWidth 会强制布局。如果每个 mousemove 都读一次，等于每帧多一次同步布局。我们只在索引变化时更新内容，并把每个索引对应的宽高记下来，下次直接查表。tooltip 的宽度基本由最长的那一行决定，配上 white-space: nowrap 之后，缓存命中率很高。

点击选中复用同一套命中逻辑，记下索引、重画高亮、把整条数据通过回调抛给业务层。再点一次取消选中。选中状态要存在实例上，画布里存不住，因为重绘随时会发生。

只补间 y 值

切换 7 天和 30 天时直接换数据会闪，加个过渡，但不要做全量动画：x 由比例尺决定，动画期间比例尺不动，只把 y 值从旧值补到新值。两边的点数通常不同，长度不一致时缺的那一端直接取目标值，不做插值。

打断靠 token：新动画一开始，旧循环在下一帧检查时退出，不需要额外取消。起点的 from 取当前插值结果，而不是上一组目标值，这样连续切换不会跳回原点。

轴的范围在动画开始时直接切到目标值，不参与补间，否则刻度标签会跟着数字抖动。代价是数据增长时柱子可能短暂超出绘图区，用 clip 裁一下就好。

点数超过五千时我直接关掉动画。插值和重绘的开销叠在一起，中低端手机上会掉到十几帧，不如干脆地切换。

大数据、响应式与导出

订单量按小时聚合，30 天七百多个点，还算轻松。退款率图按分钟取数，一个月接近四万点，直接 lineTo 四万次路径太重，而且大部分点落在同一个像素列里，画了也看不见。

按像素列取 min/max

绘图区宽 1000px，四万个点平均每个像素列挤了四十个。这一列最终只显示一两个像素高，正确做法是保留这一列的最大值和最小值，其余丢掉。极值不能丢，因为读者看折线就是为了找尖峰和低谷，等间隔抽样很可能正好跳过那个尖峰，图形会骗人。

输出最多是像素列数的两倍，四万点降到两千以内。抽稀只在数据或布局变化时做一次，结果缓存起来，交互帧直接用。注意入参必须按时间有序，否则同一列里先遇到谁后遇到谁不确定，折线的走向会乱。

分块与离屏缓存

抽稀之后如果还是很多，可以分块画：每帧画两千个点，用 rAF 排队，先让用户看到前半段，再补齐。分块时相邻块要重叠一个点，否则接缝处会缺一小段线。

静态层则能实打实省时间。网格、坐标轴、刻度文字每帧都一样，把它们画到一个不挂到文档里的 canvas 上，交互时只 drawImage 一次。这个离屏 canvas 同样要按 dpr 建位图，尺寸变化或主题切换时重建。内存代价是 dpr 的平方，封顶 2 之后一张 1200×420 的缓存约占 8MB，可以接受。

响应式与导出

窗口 resize 要监听，但侧栏折叠不会触发 window 的 resize，容器宽度变了窗口却没变。2016 年没有可靠的容器尺寸监听接口，我们的办法是在 rAF 循环里比较 clientWidth 和缓存值，一帧只读一次，变化了才重排。

重排的完整链路是：重设位图尺寸、重设变换、重算布局、重新抽稀、重画。dpr 也要重新读，把窗口从高分屏拖到普通屏，或者用户改了页面缩放，devicePixelRatio 会变，沿用旧值就会糊。

导出走 toDataURL，但不要直接导当前画布：上面可能有十字线和高亮，而且分辨率被 dpr 封顶了。正确做法是新建一个临时 canvas，按需要的倍率设置尺寸和变换，填上白色背景，完整重画一遍，再取数据。

下载用 a 标签的 download 属性，IE 11 不支持，退回到 msSaveBlob 或者新窗口打开让用户另存。背景一定要显式填白，透明背景的图贴进文档或邮件客户端，常常变成黑底。

可访问性、降级与模块收束

Canvas 对屏幕阅读器是一块位图，里面的文字读不出来，图表又承载关键信息，不能只给看得见的人用。

隐藏数据表与降级

每个图表旁边渲染一张视觉隐藏的数据表，caption 写图表标题，表头用 th 并标 scope，行列分别是日期和各个序列。数据更新时同步更新表格。CSS 用绝对定位移出视口，不要用 display: none，后者会让辅助技术也读不到。

canvas 本身给 role=”img” 和一句 aria-label 概要，说明趋势和极值，详细数值由旁边的数据表承担；canvas 加 tabindex 让键盘能聚焦，左右方向键移动选中索引，选中时更新一段 aria-live 文本。这不是完整的键盘图表方案，但覆盖了 WCAG 2.0 里“信息不能只通过视觉传达”的基本要求。

降级分两层。canvas 标签内部的文字只在完全不支持 canvas 的浏览器里显示，IE 11 用不到；真正要处理的是 getContext 返回 null，或者创建画布失败，这时直接把隐藏的数据表显示出来，并在容器里给一句“当前浏览器不支持图表，以下为数据明细”。

模块划分

代码最后拆成七个部分，彼此不互相调用内部状态，只通过布局对象和数据数组衔接。

模块 职责 关键实现
scale 数值与时间映射 linear 的 domain/range、band 的 indexAt、1/2/5 步长
layout 计算边距、绘图区、刻度 两遍测量、measureText、结果缓存
renderer 网格、轴、折线、柱子 按样式合批、单路径多子路径
decimator 大数据抽稀 像素列 min/max、按布局缓存
interaction 命中、十字线、选中 x 轴反查、二分、矩形判定
animator 数据切换过渡 只补间 y、token 打断
exporter 图片导出 临时画布、倍率重绘、白底

性能上我只在自己的机器上做过粗略对照，条件说清楚：Chrome 54，画布 1200×420，dpr 为 2，两条序列共两万个点，用脚本模拟鼠标横向拖动五秒，取每帧绘制耗时的中位数。不抽稀、不缓存时约 28ms 一帧；按像素列抽稀后降到 5ms 左右；再把静态层放进离屏 canvas，悬停帧又降了约三成。这些数字只适合同一台机器上的相对比较，换设备、换浏览器都会变，不要当成基准。

小结

手写图表引擎并不神秘，核心是把几件事拆干净：坐标只在一个地方乘 dpr，比例尺负责双向映射，布局只算一次，绘制按样式合批，命中走索引而不是遍历。折线和柱状两种形态覆盖了大部分后台报表，断点、负值、圆角、抽稀这些细节才是工作量所在。

要一张标准图，用库更省事；一旦交互和视觉都贴着业务走，几百行、行为可控的小引擎反而更好维护。
