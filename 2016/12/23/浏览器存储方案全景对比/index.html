浏览器存储方案全景对比

一个后台，四种存储

去年下半年，我们接手了一个运营后台的维护。这个后台不算复杂：一个登录页、一个订单列表、一个内容编辑页，外加一个需要弱网可用的巡店模块。但它的浏览器存储用得相当随意。登录态放在 cookie 里，编辑页的草稿每次输入都写 localStorage，巡店模块的离线数据放在 IndexedDB，用户偏好（侧边栏折叠、列表每页条数、上次停留的筛选条件）塞在 sessionStorage。四套方案由四位同事先后加进来，每一套单看都能跑通，合在一起却开始出问题。

第一个投诉来自内容编辑。运营同事写了两千多字的推文，中途清理了一次浏览器缓存，回来草稿没了。我们的「自动保存」确实写了 localStorage，可它只写了一份，也没有任何提示告诉用户数据只存在本机。第二个问题更隐蔽：同一篇稿子在两个标签页里打开，A 标签页改了标题，B 标签页保存正文时把旧标题一起覆盖回去，因为两边各自持有一份完整快照，谁后写谁赢。第三个问题是偏好：用户在 A 标签页把侧边栏收起来，新开的 B 标签页又是展开的，因为 sessionStorage 按标签页隔离，而我们把它当成了「用户设置」。

这三个故障指向同一件事：选存储方案时，团队只看「能不能存下」，没有看「存多久、谁能看见、丢了会怎样、写入要付多少代价」。本文不打算再讲一遍各个 API 怎么调用——localStorage、IndexedDB 与 cookie 的读写，本站已有专文——而是把七种与浏览器存储相关的能力摆在一起，按生命周期、容量、同步性、跨标签页行为和安全边界做一次选型对比，最后给出一个可以直接照搬的组合方案。如果你正在为一个中型前端应用决定「这条数据该放哪」，本文应该能帮你少踩几个坑。

全景：七种能力各自的位置

先把范围划清。浏览器里能「留下东西」的机制不止七种，但 2016 年能在生产环境里讨论的，基本就是 cookie、localStorage、sessionStorage、IndexedDB、WebSQL、Application Cache，以及随 Service Worker 出现的 Cache Storage（Chrome 已支持，其他浏览器跟进中）。前四个是存储，后三个更接近缓存或者已经退场的方案。它们最容易混淆的地方不是 API，而是生命周期：谁决定数据什么时候消失。2016 年底的主流版本大致是 Chrome 54/55、Firefox 50、Safari 10 和 IE 11，下文的可用性判断以此为准。

这张表里最值得先说的是 cookie。它本来就不是数据库，而是 HTTP 协议的一部分：浏览器每次向同域发请求，都会把匹配的 cookie 塞进请求头。登录态放这里是对的，因为服务端每个请求都要校验它；把草稿放这里则是灾难，4KB 的上限和每次都上传的开销都不允许。localStorage 和 sessionStorage 是同一个 API 的两个生命周期版本，前者跨标签页共享，后者只在当前标签页内可见，二者都以字符串形式保存值，都同步执行。IndexedDB 是唯一按「数据库」设计的方案：异步、事务、可以建索引、能存二进制。WebSQL 曾经是它的竞争者，现在只剩存量项目。Application Cache 是缓存整个页面资源的旧机制，更新逻辑反直觉，已经被判定出局。Cache Storage 的定位是给 Service Worker 用的缓存容器，能力不小，但在 2016 年还不能当成跨浏览器的通用方案。

还有一个容易被忽略的维度是作用域。cookie 按域名和路径划分，默认不区分端口和协议；localStorage、sessionStorage、IndexedDB 按同源划分，协议、域名、端口任一不同就是另一份数据；sessionStorage 还要再叠加一层标签页隔离。Application Cache 跟着 manifest 走，Cache Storage 按源加缓存名管理。很多「换了个端口就读不到数据」的 bug，根源都在这里。

cookie 与 Web Storage：顺手方案的硬边界

cookie：协议状态，不是仓库

cookie 的规则在 RFC 6265 里，最硬的一条是 4KB：单条 cookie 的名字、值和属性加起来大约 4KB，超出部分浏览器直接截断。它还会随每一个同域请求发送，包括图片、脚本和 XHR，所以在带宽有限的网络里，往 cookie 里塞 JSON 是双重浪费：既占请求头，又让服务端日志和调试变得难读。

三个属性决定它的安全边界。HttpOnly 让 document.cookie 读不到，XSS 无法直接偷走会话；Secure 限定只在 HTTPS 下发送；SameSite 限制跨站请求是否携带，较新的浏览器（Chrome 51 起）支持，取值为 Strict 或 Lax，能挡掉相当一部分 CSRF，但不能替代 token，因为旧浏览器不认这个属性。域名与路径决定可见范围：Domain 写成 example.com 时所有子域共享，Path 设为 /admin 时只在该路径下发送。这里有个常被忽视的攻击面叫 cookie tossing：只要有一个子域被攻破，攻击者就能从子域写一条 Domain 指向父域的 cookie，浏览器在请求头里可能同时带上两条同名 cookie，服务端解析顺序不同就会读到被污染的值。防御办法是给 cookie 名加 __Host- 一类前缀（较新浏览器支持），或者至少不要让不可信子域与主站共享父域 cookie。

会话 cookie 与持久 cookie 的区别只在有没有 Expires 或 Max-Age。前者关闭浏览器即失效，后者写到磁盘。登录态通常用 HttpOnly 加 Secure 的会话 cookie，再配一个较短的 Max-Age 做兜底。至于 4KB 够不够，取决于你把什么塞进去：一个会话标识、一个 CSRF token、一点灰度标记足够，把用户资料整个序列化进去就一定不够。另外每个域还有数量上限，IE 大约 50 条，超过之后新 cookie 会挤掉旧的，而且不会报错，这一点在灰度发布按标记写 cookie 时尤其容易踩到。

Web Storage：同步的字符串仓库

localStorage 和 sessionStorage 的模型极简：字符串键、字符串值、同源隔离、5MB 量级。所有值在写入前被隐式转成字符串，读出来再自己解析。它没有过期时间，没有索引，没有事务，也没有容量查询接口。判断能不能用，只看三条：数据小、可以丢、写入不频繁。

同步是它最大的代价。setItem 和 getItem 都在主线程执行，浏览器还要把值序列化后落到磁盘。存一个几十 KB 的配置没什么感觉，存一个 2MB 的 JSON 就会在低端机上卡出可感知的掉帧；每次输入都把整个文档 JSON.stringify 再 setItem，等于把编辑器的性能上限锁死在存储上。更麻烦的是它没有异步版本，Web Worker 里也拿不到 localStorage（worker 没有 window），想把写盘挪到后台线程只能改用 IndexedDB。

另一个误解是「同源共享等于所有标签页实时同步」。localStorage 确实同源共享，但一个标签页写入后，其他标签页不会自动更新内存里的变量，只有监听 storage 事件才能感知，而且事件不会在写入的那个标签页触发。sessionStorage 则连共享都不是：它按标签页隔离，复制标签页时可能被复制一份，关闭即消失，适合存放「一次填写流程」的临时状态，不适合当用户偏好。

同源隔离还有一个实践后果：把站点从 HTTP 迁到 HTTPS、或者从 www 换成裸域，旧数据会全部读不到，因为协议或主机变了就是另一个源。做迁移时不能只改 nginx 跳转，还要在旧源上留一个过渡页，把 localStorage 里的关键数据读出来，通过 postMessage 或一次表单提交带到新源，否则用户的偏好和未同步草稿会安静地留在旧源里。

容量上还有一个历史包袱。5MB 是量级，不是标准：不同浏览器按字符数或字节数计算，UTF-16 下一个汉字可能按两个字节甚至更多计。我们曾用 localStorage 缓存一份三万条的城市数据，Chrome 里勉强写入，IE 11 直接抛 QuotaExceededError。这件事的教训不是「IE 容量小」，而是任何接近容量上限的写入都必须包一层 try/catch，并且准备降级路径。

IndexedDB：离线数据的主力

如果一条数据要长期留在客户端、体积超过几百 KB、还要能查询，IndexedDB 是 2016 年唯一合理的选择。它是异步 API，所有操作以请求为单位，结果通过事件回调返回，不会阻塞主线程；写入在事务里完成，事务分只读和读写两种，可以跨多个对象仓库；数据按对象仓库组织，可以给字段建索引，按范围或游标遍历。

它和 Web Storage 的根本差异在三个地方。第一是异步：打开数据库、读写记录都要等事件，代码结构比 localStorage 啰嗦，但换来的是大块数据不卡界面。第二是结构：对象仓库加索引，让「按时间倒序取最近 50 条待同步记录」这种查询不用把整个数组读进内存再排序。第三是类型：除了普通对象，还能直接存 Blob、File、ArrayBuffer，图片和音频不必先转 base64，省掉约三成体积和一次编解码。

版本升级是 IndexedDB 最容易出错的部分。数据库有一个整数版本号，打开时声明期望版本；如果高于现有版本，触发 upgradeneeded，在这个回调里建仓库、建索引、迁移旧数据；如果低于现有版本，直接报错。所有结构变更都必须在这里完成，而且要考虑用户从版本 1 直接跳到版本 4 的路径，不能只写「从 3 到 4」。

这段代码的重点不是记住写法，而是把版本判断写成增量条件，保证任何旧版本都能逐级补齐。升级函数里不要做网络请求，事务会在异步等待时自动提交，之后的操作全部失效。

事务还有一条容易忽视的规则：只要事件循环里没有新的请求，事务就会自动提交。中间插一个 setTimeout 或网络回调，后续操作就会抛 TransactionInactiveError。批量写入要在同一个事务里连续发请求，而不是等一条的回调回来再发下一条。游标遍历大表时也要控制每批数量，一次性把十万条读进内存，和用 localStorage 没有区别。

兼容性要说清楚。IE 10 起有 IndexedDB，但 IE 11 仍不能把 Blob 直接放进对象仓库，只能存 ArrayBuffer；Safari 在 10 之前的实现问题很多，Safari 10 上跨标签页并发打开同一个数据库还可能触发阻塞事件。生产代码必须监听 blocked 和 error，给用户一个「请关闭其他标签页」的提示，而不是让回调永远挂着。移动端的差异更大，iOS 10 的 Safari 与微信 X5 内核各有各的脾气，桌面 Chrome 通过不代表手机上没问题，关键路径要在真实机型上验证。

两条退场路线：WebSQL 与 Application Cache

WebSQL：标准停止之后

WebSQL 在 2010 年就被 W3C 停止推进，规范不再维护。它的 API 是同步的 SQLite 封装，写起来比 IndexedDB 舒服，Chrome、Safari、Opera 都实现过，Firefox 从未支持。2016 年它还能在部分浏览器里跑，但没有任何新特性，也没有跨浏览器保证。新项目不该用它，原因不是「快被删了」，而是代码会在 Firefox 用户那里直接不可用，而 IndexedDB 能覆盖同样的场景。存量项目如果要迁移，先抽象一层数据访问接口，再按浏览器能力切换实现，不要在两个 API 之间做运行时双写，双写只会制造两份不一致的数据。

Application Cache：manifest 的更新陷阱

Application Cache 的设计目标是让页面离线可用：HTML 标签声明 manifest，浏览器按清单缓存资源，之后即使断网也能打开。问题在更新模型。manifest 文件本身被缓存，浏览器只有在 manifest 字节发生变化时才去拉新资源；页面加载时先命中旧缓存，新版本在后台下载，用户要刷新第二次才看到新内容。更糟的是，只要清单里有一个资源 404，整个更新就会失败，而失败往往没有明显提示。开发者为了「立刻生效」去调 swapCache 或改 manifest 注释，进一步把缓存状态搅乱。

这套机制已经被判定出局，主流浏览器都计划移除，只是时间表不同。新项目不要再用，存量项目应当尽快把离线能力迁到 Service Worker 的缓存策略上。但要说清楚：2016 年 Service Worker 只有 Chrome 支持得比较完整，其他浏览器还在跟进，Cache Storage 不能当成通用方案。真正跨浏览器的兜底仍然是「在线优先，离线时给出明确提示」，而不是假设每个用户都有可用的离线缓存。另外，Service Worker 只在 HTTPS 下可用，IE 完全不支持，这两条限制在 2016 年没有变化。

容量、配额与存储被清掉之后

各方案的量级要先心里有数：cookie 每条 4KB、每个域几十条；localStorage 与 sessionStorage 是 5MB 量级；IndexedDB 与 Cache Storage 共用源的配额池。Chrome 的配额与磁盘剩余空间挂钩，Firefox 首次申请 50MB 后按需增长，IE 的限额更保守。配额不是承诺：磁盘紧张时，浏览器可能驱逐整个源的数据，顺序不公开，代码无法阻止。

QuotaExceededError 要单独处理。写入时捕获，先判断错误名再降级；不要无脑重试，重试只会把主线程拖死。正确顺序是删过期键、按 LRU 删一批、重试一次，仍然失败就退回内存并提示用户导出。Safari 的无痕模式历史上对任何 setItem 都抛这个错，可以用一次探测写入判断存储是否可用，不要假设「能读就能写」。

LRU 清理需要一点元数据：维护一个索引键，记录每个业务键的体积和最后访问时间；体积用字符串长度乘 2 估算，不精确但足够排序；启动时扫一次，写入失败时再扫，平时不扫，避免每次写都变成 O(n) 的全量遍历。IndexedDB 里则把 lastAccess 建成索引，用游标按时间删最旧的记录。索引本身也占空间，记录粒度要到「一组键」而不是每个字节。

清理与降级是产品问题，不只是代码问题。用户手动清缓存、在 Safari 里管理网站数据、关闭 Chrome 无痕窗口，都会让存储归零。Safari 一向比 Chrome 保守，无痕模式几乎不给持久化机会；WebKit 社区还在讨论对长期不访问站点的本地数据做限制，2016 年尚未成为默认策略，但方向已经很清楚。同一思路更早的体现是 Safari 默认拦截第三方 cookie，这让依赖第三方 cookie 的统计脚本很早就得换方案。产品层面必须接受「客户端存储随时可能消失」：服务端是唯一事实来源，草稿要有导出，检测到存储为空时从服务端拉回或明确提示，而不是静默显示空白。

主线程成本与序列化代价

localStorage 的同步不仅指 API 返回同步，还意味着字符串序列化和磁盘写入都发生在主线程。一次 JSON.stringify 处理 1MB 对象，在普通笔记本上要几十毫秒，解析回来差不多；如果每次按键都做一遍，输入延迟立刻可感。可行的做法是防抖到 500ms 以上、只序列化变化的字段，或者把草稿整体交给 IndexedDB。IndexedDB 的序列化仍在调用线程完成，但磁盘 IO 是异步的，至少不会让一次写盘卡住渲染。

Worker 能分担计算，但不能分担 localStorage：Worker 里没有 window，localStorage 和 sessionStorage 都不可用，IndexedDB 可用。把大对象 postMessage 给 Worker 同样要结构化克隆，数据量越大复制成本越高，所以「用 Worker 包一层」不是免费的性能优化。真要处理大文件，优先存 Blob，让浏览器自己管理二进制，避免在字符串和二进制之间反复转换。

序列化的坑比性能更隐蔽。JSON 往返会丢类型：Date 变成 ISO 字符串，读回来还是字符串；Map 和 Set 变成空对象；undefined 在对象里被直接丢掉，在数组里变成 null；函数和 Symbol 消失；RegExp 变成空对象；NaN 和 Infinity 变成 null；循环引用直接抛 TypeError。我们吃过一次亏：草稿里保存了撤销栈，栈里带函数引用，JSON.stringify 在用户输入到第两百步时抛错，自动保存静默失败，用户以为一直在保存。

解决办法不是自己写序列化器，而是给数据加版本和边界。存储前只挑需要持久化的字段，把 Date 统一转成时间戳，Map 转成数组，循环引用在入库前断开；读取时用 reviver 或迁移函数还原。每个键都带一个 version 字段，读取时按版本逐级升级，升级函数只增不改。这样即使半年后数据结构变了，老用户本机上的旧草稿也能被正确读出来。

跨标签页同步与安全边界

storage 事件与它的边界

localStorage 写入后，其他同源标签页会收到 storage 事件，事件对象里有 key、oldValue、newValue 和 url。三个细节必须记住：事件不在写入的那个标签页触发；事件是异步派发的，短时间多次写入可能被合并；sessionStorage 的变化不会跨标签页通知。实践里不要用事件传大数据，事件只当「有新版本」的信号，收到后按版本号去 localStorage 或 IndexedDB 读最新快照。冲突策略要先定：整篇覆盖是最差的，按字段合并或加乐观锁才可控。我们最后给草稿加了 revision，保存时带上读到的版本，服务端发现落后就返回冲突，前端再让用户选择，这比「谁后写谁赢」诚实得多。

BroadcastChannel 更直接：同源页面建一个命名频道，postMessage 广播，语义比 storage 事件清楚，也没有「必须先写存储才能发消息」的副作用。但它是较新浏览器才有的能力（Chrome 54 起），IE 和当时的 Safari 都不支持，2016 年只能作为增强通道。兼容做法是能力检测：有 BroadcastChannel 就用，没有就退回 storage 事件；再退一步用 setInterval 每 2 到 5 秒对比一个 revision 键。轮询有延迟也费电，后台标签页还会被节流，所以只适合「最终一致」的偏好同步，不适合协同编辑。

XSS 之下的存储边界

所有能被 JavaScript 读到的存储，在 XSS 面前都是明文：localStorage、sessionStorage、IndexedDB、Cache Storage，以及没有 HttpOnly 的 cookie。攻击者只需要一段注入脚本，就能把 token、草稿、离线数据打包发走。HttpOnly 的价值是让会话 cookie 不出现在 document.cookie 里，降低被直接外带的概率；但它挡不住「以用户身份发请求」——XSS 已经在你页面里，不读 token 也能操作。

所以敏感数据的放置顺序应当是：会话放 HttpOnly 加 Secure 的 cookie，再配 CSRF token；短期、可撤销的凭据才考虑 Web Storage，并且要有服务端撤销机制；长期密钥、支付信息不要下发到浏览器。客户端加密只能提高门槛：密钥最终要能被 JS 取到，XSS 同样能取到，它防的是「别人翻看这台电脑的磁盘」，不是防「页面被注入」。真正有效的还是 CSP、输出转义、依赖审计，以及尽量短的会话有效期。还有一点常被忘记：第三方脚本与你同源运行，能读同样的 localStorage 和 IndexedDB，接入统计、客服或 A/B 测试 SDK 时，等于把存储的读取权限部分交给了对方，选型时要把这笔账算进去。

选型矩阵与迁移路径

把前面的结论压成一张表。选型时先看数据量和生命周期，再看同步性与安全边界，最后才考虑 API 顺不顺手。

方案 数据量 生命周期 随请求发送 同步性 跨标签页 安全边界
cookie 4KB 每条 可设置，默认会话 是 由浏览器同步管理 共享 HttpOnly 挡读取，仍受 CSRF 影响
localStorage 5MB 量级 永久，可被清理 否 同步，阻塞主线程 共享，需事件通知 XSS 可读
sessionStorage 5MB 量级 标签页关闭为止 否 同步，阻塞主线程 标签页隔离 XSS 可读
IndexedDB 配额级 永久，可被驱逐 否 异步 共享，需自行协调 XSS 可读
WebSQL 配额级 永久 否 同步 共享 XSS 可读，标准已停止
Application Cache 资源级 由 manifest 决定 否 异步 共享 可被缓存替换，已退场
Cache Storage 配额级 代码显式管理 否 异步 共享 2016 年仅 Chrome 完整可用

表里没有「性能」一列，因为性能取决于用法而不是方案本身：localStorage 存 10KB 很快，存 2MB 就慢；IndexedDB 单条写入比 localStorage 慢，但批量与大数据下优势明显。真正要问的是写入频率和数据规模。

如果还是拿不准，按顺序问三个问题：这条数据每个请求都要带给服务端吗？丢了会不会影响用户？需要按条件查询或存二进制吗？第一个回答「是」，用 cookie；第二个回答「无所谓」，用 localStorage；第三个回答「需要」，用 IndexedDB。三者都不沾，说明这条数据也许根本不该存在客户端。

上线前至少用真机跑一遍这些场景：Safari 无痕模式里能否写入、IE 11 存 Blob 是否失败、两个标签页同时编辑会不会互相覆盖、清除网站数据后首屏是否报错、存储写满时有没有提示。这些问题在 Chrome 的普通窗口里一个都复现不出来，却恰好是用户投诉最多的几类。

flowchart TD
  A[每个请求都要带给服务端吗] -->|是| B[cookie 加 HttpOnly 与 Secure]
  A -->|否| C[丢了会影响用户吗]
  C -->|不会| D[localStorage 存小体积偏好]
  C -->|会| E[IndexedDB 存大容量数据]
  E --> F[需要离线打开页面吗]
  F -->|需要| G[Cache Storage 2016 年仅 Chrome 可用]
  F -->|不需要| H[在线优先 本地缓存兜底]

回到开头那个后台，我们最后的组合是这样的。登录态只放 HttpOnly、Secure 的会话 cookie，有效期 30 分钟，前端不再碰 token；用户偏好放 localStorage，键名统一加 ops:pref: 前缀，值里带版本，读不到就用默认值，丢了不可惜；草稿以 IndexedDB 为主，输入停顿 800ms 写一次，另外在页面隐藏和 beforeunload 时往 localStorage 写一份很小的最后快照，因为卸载阶段的异步事务不可靠，而同步写入更可能完成；巡店离线数据放 IndexedDB，单独建 syncQueue 仓库，用 status 索引取待同步记录，失败按指数退避重试；静态资源缓存只在支持 Service Worker 的浏览器上做增强，2016 年这项能力仍以 Chrome 为主，其他浏览器走普通 HTTP 缓存。

迁移分六步，顺序不能反。第一步盘点：把所有 localStorage 键、cookie 名、IndexedDB 仓库列出来，标上体积、读写位置、丢失后的影响。第二步定命名空间和版本：统一前缀加工号，值里保留 version，之后所有新代码只认新键。第三步抽访问层：读、写、删三个方法，内部按数据类型路由到 cookie、localStorage 或 IndexedDB，业务代码不再直接调 API。第四步双写灰度：新键先双写一段时间，读路径优先新键、缺失时回退旧键，确认无异常再扩大范围。第五步一次性迁移：用迁移标记保证只跑一次，分批搬数据，避免一个长事务锁住数据库。第六步清理与监控：旧键保留一个版本周期再删；上报 QuotaExceededError、blocked 事件和存储为空的比例，后者往往意味着用户正在丢数据。

这套方案不复杂，但它把「哪些数据可以丢、丢了怎么办」写进了代码，而不是留给用户的清理习惯。

小结

浏览器存储的选型，本质是四个约束的权衡：数据多大、要活多久、写入是否频繁、泄露或被清掉的代价有多高。cookie 是协议状态，只适合小段需要随请求发送的数据；Web Storage 是同步的字符串仓库，适合小、可丢、低频的偏好；IndexedDB 是唯一能承载大容量、查询和二进制的方案；WebSQL 与 Application Cache 已经是退场选项；Cache Storage 在 2016 年仍要限定在 Chrome。跨标签页同步优先用 storage 事件，较新浏览器可以用 BroadcastChannel 增强，但永远要留轮询兜底。最后，客户端存储都假定「随时会消失」，服务端才是事实来源。
