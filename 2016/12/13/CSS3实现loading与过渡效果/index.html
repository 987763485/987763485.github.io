CSS3 实现 loading 与过渡效果

本文属于《HTML 与 CSS》第 51/62 篇
上一篇系列目录下一篇

列表页切换筛选条件，是最容易暴露加载体验问题的地方：旧内容先消失，中间空一下，新内容再出现。用户说不出哪里不对，只觉得卡。本文不讨论 spinner 怎么画，也不逐条讲 transition 的属性，只谈加载与过渡在真实页面里怎么编排：状态怎么划分、类名什么时候加、请求回得太快或太慢怎么办。适合已经会写 transition 与 animation、但页面一接真实数据就露怯的开发者。

从一次筛选切换说起

去年做的一个后台订单列表，顶部有”全部 / 待付款 / 已发货”三个筛选。最初的实现直白得很：点击后把列表容器清空，发请求，回来再拼 HTML。上线后客服转来一条反馈，说这个页面”点起来一顿一顿的”。

把操作录屏慢放，问题很清楚。点击的瞬间旧内容消失，容器塌成一条空白，大约两百毫秒后新内容才撑开；如果网络快，loading 图标只闪了一两帧，看起来像画面抖了一下；如果用户手快，连点三次筛选，先发的请求后回来，会把最后一次的结果覆盖掉。

这三件事分别对应三个不同层面的问题：状态没有显式表达、过渡没有起点和终点、请求没有身份。它们都不是 CSS 属性写得不对，而是编排得不对。下面按这个顺序拆。

把加载拆成几个状态

先别急着写样式。一个会发请求的区域，任何时刻只应该处于有限个状态之一：idle（还没请求或刚被重置）、loading、success、empty、error。把 empty 从 success 里分出来很重要，”查到了零条”和”查到了三条”对用户的意义完全不同，前者需要引导，后者只需要渲染。

flowchart TD
    A[idle 初始] -->|切换条件| B[loading]
    B -->|有数据| C[success]
    B -->|零条| D[empty]
    B -->|超时或报错| E[error]
    C -->|再次切换| B
    D -->|再次切换| B
    E -->|点击重试| B

离开为什么没有过渡

很多人第一次踩的坑，是给列表项写了 transition: opacity 200ms，删除时却直接 removeChild，发现元素是”啪”地消失的。原因不复杂：过渡要求元素还在渲染树里，并且存在”变化前”和”变化后”两个可插值的值。display: none 会让元素直接退出渲染树，没有中间帧；把节点摘掉，连插值对象都没了。

第一条可行路径，是把”消失”交给 visibility 与 opacity 配合，让元素留在原地：

visibility 是一个很特殊的属性：它没有中间值，但切换可以被延时。离开时把 visibility 推迟到 200ms 之后，元素在淡出的全程仍然可见；进入时延时为 0，立刻显示。这条路径的代价是元素仍然占着布局位置。如果这块内容本来就该让位，还得再补一次高度收拢，或者干脆换第二条路。

第二条是先加 class，等 transitionend 之后再 display: none 或移除节点。要注意两点：一次过渡里每个属性都会各触发一次 transitionend，得判断 event.propertyName；过渡被打断时事件不会来，所以清理逻辑必须配一个 setTimeout 兜底，否则元素会永远留在 DOM 里。

两条路可以混用：容器用 visibility 做廉价显隐，内部真正需要让位的高度变化，交给量高后的显式过渡。

最快回来的请求最麻烦

请求 30ms 就返回，是最难处理的场景。此时如果立刻渲染，loading 只存在一两帧，用户看到的是画面闪了一下，比老老实实等 300ms 更让人不安。解决办法是给 loading 设一个最短展示时长，用请求开始的时间戳补足：

300ms 是个经验值。低于 100ms 的等待，人眼几乎分辨不出是”加载过”还是”卡了一下”，与其让它闪，不如让它稳；再长又会拖慢本来很快的请求，所以只补差额，不无条件延时。

同一段代码也解决了中断问题。用户连续切三次条件，listSeq 自增三次，前两次的回调醒来时发现序号对不上，直接返回。用 xhr.abort() 也可以，但 abort 会走 onabort 或 onerror，一定要用一个标志区分”主动取消”和”真的失败”，否则用户每切一次条件都会看到一次”网络异常”的提示。至于动画打架，原则是切换时先把上一轮的 class 清干净再开始新一轮，不要在半路叠加第二套过渡。

遮罩与骨架，按请求的性质选

这两种反馈手段经常被混着用，其实分工很清楚。

遮罩保住的是布局。旧内容还在，只是被压暗或被一层半透明层盖住，容器高度不变，滚动位置不跳。它适合”同一批数据的替换”：切筛选、翻页、改排序。用户的注意力本来就在原位置，遮罩只是告诉他”这一块在换”。

骨架保住的是结构感。它适合首次进入、结构可预测的页面：列表第一屏、详情页头部。骨架的价值在于提前把行高、头像尺寸、文字块位置占住，数据落进已有的格子，视觉上不位移。骨架最怕”不像”：占位块和真实行高差几个像素，数据一到整页内容往下跳一截，比没有骨架更难受。

选择上还有一个容易忽略的维度：用户此刻在做什么。他在读已有内容、只是顺手刷新，就别用遮罩盖住正文，改用角落的小提示或顶部细进度条；他刚点了”查询”、明确在等结果，遮罩反而给了他确定的边界。骨架屏的具体画法本站已有专文，这里只强调一句：骨架的尺寸要从真实组件里量，不要凭感觉写死。

一个页面里同时有三处在加载

真实的后台首页，往往是列表、统计卡片、推荐位各发各的请求。这时最容易犯的错，是搞一个整页遮罩，等最慢的那个请求回来才放开。结果快的两个区块早就好了，用户却什么都不能点。

我的做法是每个区块自己维护状态：容器上有自己的 data-state，遮罩只覆盖自己的盒子。整页级的提示只留给”连页面骨架都还没拿到”的首屏。

局部遮罩有两个细节。一是遮罩层要不要吃掉点击。默认应该吃掉，防止用户在加载中重复提交；如果只是”刷新”这类可逆操作，可以让遮罩 pointer-events: none，让用户还能滚动、还能点别的区块。二是不要把已经可用的内容一起压暗。比如只有表格右下角的分页在加载，就别盖住整张表。遮罩的范围应该等于”这次请求会影响的范围”，多一分都是干扰。

别在过渡里改布局属性

过渡期间最扎眼的不是动画不流畅，而是页面在抖。常见来源是给 height、top、margin、width 加过渡：这些属性每一帧都要重新计算布局，元素一动，后面的兄弟节点跟着动，长列表上很容易掉帧；它们还会影响滚动锚点，用户正在看的位置会被推走。

能只动 transform 和 opacity 就别动别的，这两个属性在当年主流浏览器上可以走合成层，不触发布局。要位移用 translate，要淡入淡出用 opacity，旋转缩放也用 transform，一条规则覆盖大部分入场效果。

真正难的是”展开一个面板”这类需求，高度必须变。height: auto 不能过渡，因为 auto 不是可插值的长度。很多人退而求其次，用 max-height 从 0 过渡到一个足够大的值，能跑，但有两个坑：过渡的实际速度取决于那个”足够大”的值，内容只有两行时会觉得前大半段时间都在等；过渡结束后 max-height 仍远大于内容高度，遇到内部内容变化，就会出现”该滚动却不滚动”的怪现象。

切 class 的时机

有一类”过渡不生效”的 bug 和 CSS 无关：同一个同步任务里先 remove 旧 class 再加新 class，浏览器只看到最终样式，中间状态被合并掉了，自然没有起点。

还有两个和事件有关的习惯。transitionend 会冒泡，在容器上监听时要确认 e.target 是预期的元素；同一个元素多个属性同时过渡会触发多次，清理逻辑要么判断 propertyName，要么加一个只执行一次的标志。任何依赖 transitionend 的关键逻辑都要有超时兜底，因为过渡被 display: none、切到后台或者用户快速连点打断时，这个事件不会来。

低端机与可访问性

同一套过渡在开发机上丝滑，到了 Android 4.4 的 WebView 或者某些定制内核上就可能变成幻灯片。当年的低端机对大面积半透明层、阴影和 filter 都很敏感，尤其 filter: blur()，移动端支持参差，放进过渡里几乎必然掉帧。我的降级策略是默认只保留 opacity 的淡入淡出，把位移、模糊、阴影都当作增强，用能力类统一关闭：检测到低端设备时给 html 加一个 is-low-end，CSS 里把动画时长压到接近 0。

动效的另一面是可访问性。prefers-reduced-motion 这个媒体查询在规范里已经出现，部分浏览器的新版本开始支持，但覆盖面很窄，只能当渐进增强，必须准备特征降级：它不生效时页面仍要完整可用，只是动画多一些。

语义上，加载中的区域加 aria-busy="true"，结束后移除，屏幕阅读器会把这一块当作正在更新，不会读到半截数据。空态和错误态的文案放在带 aria-live="polite" 的容器里，让状态变化被读出来。遮罩出现时，被盖住的内容不该还能被 Tab 聚焦，实际做法是给遮罩下的可交互元素临时加 tabindex="-1"，或者把焦点收回到触发按钮上。加载动画只是辅助，不能成为唯一的信息来源。

小结与场景速查

加载体验的问题，八成不在 CSS 写得对不对，而在状态和时序没有编排清楚。先把状态穷举出来，让一个 data-state 决定长什么样；再决定状态之间怎么过渡，离开也要有终点；最后处理请求的身份与最短时长，别让快请求闪、慢请求乱。

场景 用什么 注意点
列表切筛选、翻页 容器内遮罩 保留旧内容撑住高度，只盖受影响的区域
首次进入列表或详情 骨架 占位尺寸从真实组件量，别和最终行高差太多
表单提交 按钮内联 loading 并禁用 不要整页遮罩，用户还要看得到自己填的内容
多区块各自请求 每块自己的状态 慢请求不能拖住已经可用的区块
面板展开收起 量高后过渡，或只做位移与淡入 别用 height: auto，慎用大值的 max-height
空态与错误态 原地替换并给重试入口 配 aria-live，别只弹一个会自动消失的提示

如果只能记一句：让用户感知到的等待，比让动画好看更重要。300ms 的最短展示、一次干净的淡出、一个不盖住可用内容的遮罩，这三件事的收益远大于把缓动曲线再调顺一点。剩下的动画细节，留给真正需要它的场合。
