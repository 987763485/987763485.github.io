Node.js 中的异步流程控制库

起点：二十个城市、三个接口、第九层缩进

去年冬天我接了个内部报表脚本的活。需求一句话就能说完：把二十个城市各自的销量、库存、门店客流三个接口拉下来，聚合成一份 CSV，每天早上定时跑一次。接口本身不大也不新，唯一”麻烦”在于三个接口来自三个团队，返回结构谁都不像谁，字段对齐得靠人肉查文档。

真正让人难受的不是丑，是接下来三件事同时找上门。第一，错误处理在每一层都要重写一遍，而且语义还不统一：有的层失败了应该整单放弃，有的层失败了只丢一个城市，写到后面我自己也说不清哪条分支该往下传。第二，并行做不到。二十个城市 × 三个接口，串行跑一轮六分钟；可这段结构的”下一步”物理上挂在”上一步”的回调里，想并行就得把整棵树一边拆一边改计数器。第三，中间想插一步就得整体挪动。产品后来加了一句”销量数据要按门店再查一次归属大区”，我只能在最深那层再往里嵌，缩进从九层变十一层，diff 看起来像把整个函数重写了一遍。

压死骆驼的是失败重试。要”每个接口最多重试两次、间隔递增”，我第一反应是在每个回调里加个计数器，加了三个之后发现重试的回调和正常的回调在同一个函数里抢 pending 的递减权，报表偶尔少几行也不报错。这个脚本我前后改了四天，最后决定不再自己扛，去把当时社区在用的那几套流程控制方案正经过一遍。这篇就是那次过完一遍之后的记录，重点是每一步我们实际摔在哪，不是功能对照表。

版本口径先钉住，免得后面对不上：全文基于 Node 4 LTS（这一条线是 2015 年 9 月放出的，V8 4.5，原生 Promise 可用，严格模式下 function* 可用；Node 5 是特性分支，我们生产没上）、async 1.5.x（2.0 那一支刚刚放出候选，我们没上生产）、bluebird 3.x、co 4.x。示例一律写成当期能直接跑的 ES5 形态。

先把地基讲清：error-first callback 只是习惯，不是保证

聊库之前，得先说清 node 这套异步约定到底提供了什么、没提供什么，因为后面所有库都是在补这里的缺口。

约定本身很短：绝大多数异步函数的最后一个参数是回调，回调的第一个参数是错误对象，后面的参数才是数据。

判断成功用的是 err 是否为 falsy，不是 === null。这一点很容易被忽略：有的库失败时给的是字符串，有的给自定义 Error 子类，有的把”没找到”也当错误抛给你，还有的作者忘了 return，在同一个回调里既调了 cb(err) 又往下执行又调了一次 cb(null, data)。约定的强度完全取决于作者的自觉，语言层一个字都没管。

麻烦就在这里。它只是一套习惯，不是类型、不是接口、不是语法：编译器不知道第二个参数是数据，运行时也没有任何东西保证回调恰好被调用一次。于是”统一处理错误”这件事在纯回调世界里没有抓手——你没法 try/catch 一个还没发生的异步错误，也没法用一个 catch 兜住整条链路，因为每一次异步跳转都是一次全新的函数调用，同步栈早就没了。上面那个脚本每个层级重写一遍 if (err)，不是我不会写代码，是这个范式本身不提供”错误往上传”的通道。

所以后来所有方案，本质上都在补三件事：错误怎么自动冒泡、完成时机怎么统一、并发怎么受控。看清楚这三件事，选库这件事就没那么玄学了。

async 1.5.x：它给的是高阶函数，不是一套新范式

async 当时是我们最先落地的一套，因为它最”不侵略”：它不改变你已有的写法，回调还是 error-first 回调，只是把”编排”这件事变成一组现成的高阶函数。理解这一点很重要，很多后来的误用都是把它当成一个”新运行时”来用。

三类 API 各自解决什么

集合类是对数组做的：eachSeries / eachLimit / map / mapLimit / filter / reject / reduce / sortBy / groupBy / times，形态基本是”JS 数组方法 + 异步回调 + 前面加 Series 或 Limit 决定跑法”。控制类是流程本身：series、parallel、waterfall、whilst / doWhilst、until / doUntil、queue、cargo、priorityQueue、auto、retry。工具类是组合子：compose、applyEach / applyEachSeries、seq、nextTick。当年我们只在前两类上投入，第三类里 compose 用过一次就被撤了，因为组合出来的错误栈基本读不动。

条件循环、retry 与 auto：用了半年才敢放开的那几个

whilst / doWhilst 和 until / doUntil 是条件循环的异步版，条件是同步函数、动作是异步函数，两者分开传。我们拿它做过分页拉取：只要”还有下一页”就再拉一页，doUntil 那一版还顺手解决了”第一页总要拉”这个边界。retry 则把第 3 节那种手写计数器收走了，签名是 async.retry({ times: 3, interval: [200, 800, 2000] }, task, cb)，interval 给数组就是递增退避。看着省事，但它只判断”报错了没有”，不判断”这个错误值不值得重试”：超时值得重试，参数写错重试三次只是把同一个网关多打三遍。我们后来都先在 task 里把不该重试的错误咽掉（转成带标记的成功返回），才敢在外面套 retry。

auto 接的是一个对象，每个 key 是一条任务，任务的第二项是一个数组写明”我要等谁”，库自己做拓扑排序，互不依赖的就并发跑。报表这条链后来长成”销量和库存互不相干、但都要在合并之前完成”这种形状，用 series 就得人为排一个假顺序，用 auto 则把依赖图直接写在代码里，新人扫一遍 key 就知道全貌。代价也很直白：它默认把并发打开了，第 11 节那类限流事故在这条路上更容易发生，所以 auto 里的每条任务我们都包一层 mapLimit，或者干脆接进自己的 queue。

queue 解决的是”任务源是流动的，而且要限并发”。我们的接口不是二十个城市一次给完的，城市列表本身是查出来的，中间还有失败重投，parallel 那套”全部发起再等齐”根本不合适。cargo 和 priorityQueue 的适用面各自很窄，得分清：cargo 是按批装载，push(loading, weight) 攒够一个重量阈值 pivot 就把一批数组交给唯一的 receiver，它没有并发数的概念；queue 是按并发数派发单条。上游给了批量接口（一次能查五十条）就用 cargo，只有一条条查的接口但要限并发就用 queue。priorityQueue 每条任务带一个数字优先级、小的先跑，我们只在”告警城市插队”这种场景用，用它得小心低优先级被长期饿死。

我们在 async 上踩的三个坑

第一个是 drain 的语义。drain 说的是”队列空了且当前没有正在跑的任务”，不是”我的任务集完成了”。我们有一版把 drain 当”完成”用，后来加了失败重投（在 drain 里把失败任务再 push 回去），于是 drain 触发了两次，报表写了两遍。正确做法是把”最终产出”这一步挂在业务自己的计数器或 promise 上，drain 只当”没活了”的信号。第二个是 push 的参数位置：q.push(task, cb) 的第二个参数是这条任务的完成回调，只收 err；async 1.5 的 worker 调 callback(null, data) 时那个第二个参数会被丢掉，所以想把结果交给调用方只能靠闭包或自己传容器，别指望 push 的回调帮你带回数据。第三个是我们最贵的一条，也是第 11 节那场事故的伏笔：并发数设高不是性能问题，是会不会惹事。

Promise 路线：它包的是值，不管并发

Promise 解决的是另一件事：把一个”现在还没有的值”包起来，让后续步骤变成对象上的方法调用，而不是把函数塞进别人的参数里。这是值的包装，不是并发管理。这句话我大概花了两周才真正理解。

嵌套被拉平这件事大家都会讲，但对第 2 节那个”约定没有保证”的缺口，真正的答案是第二行：错误沿链往后冒，直到遇见最近的 catch。中间任何一步 throw 或者返回一个 reject 的 Promise，后面的 then 全部跳过，rows.push 也不会执行。你只需要在链尾处理一次。

顺带记一笔当期最常见的误用，因为它和第 2 节那套约定直接相关：.then 的返回值决定下一步拿到什么。return 一个值，下一步就拿到那个值；return 一个 Promise，链子会等它；什么都不 return，下一步拿到 undefined；而如果在 then 里面又混着写了回调式的 API 又没有把它包成 Promise 返回，链子就在那一步提前结束——外面那个 .catch 从此管不到回调里的错误。我们那份”一部分步骤已经是 Promise、一部分还是回调”的混合脚本就是这么静默地产出错数据的，症状和第 1 节一模一样，只是缩进不见了。

三个必须记住的麻烦。

第一，当时未处理的 rejection 是静默的。那条”终端里给你打一行警告”的机制在 2016 年 4 月还没有落到 Node 默认的运行时行为上，一个被 reject 又没人接的 Promise 什么都不做，进程照跑。这个洞只能靠纪律补：团队里定成”每条链结尾必须有 catch，最外层的 catch 里必须写日志并给非零退出码”，code review 按这条看。第二，已经发起的 Promise 不能被取消。parallel 的语义因此变成”全部发起再等齐”，二十个城市三个接口就是一次打出六十个连接。要限并发，Promise 自己给不了，必须另找手段（async 的 queue / mapLimit，或者 bluebird 的 Promise.map 带 concurrency）。第三，Promise.all 是一失败全失败，但其它请求还在跑，你既拿不到部分结果，也停不下来。当期能用的对策是把单个任务包成”永远 resolve、内部带错误标记”的形态，最后再筛：

原生 Promise 在 Node 4 上已经可用，功能就是规范里那一圈。bluebird 提供的是原生之外的那部分能力，下一节单说。

bluebird 3.x：卖点是性能与栈，代价是方法名对不上文档

2016 年我们把 bluebird 引进来，理由其实特别朴素：排错时看不到源头。原生 Promise 和回调一样，异步边界一跨，栈就断了；一个 TypeError 出现在 then 里，你只能看到从那个微任务起手的几帧，是谁发起的这条链完全看不出来。bluebird 的长栈追踪把这个洞补上了——在创建任何 Promise 之前打开，链上每一跳的调用位置都留在错误里：

代价是内存：每条链都留一份栈，任务量大的批处理脚本会明显吃得多。我们的用法是开发和排查环境打开，线上关闭。性能这块只能自述：报表脚本从原生 Promise 换成 bluebird 之后，我们那台机器上整轮跑的时间短了些，但差异远没有”能看清栈”这件事有价值，我也没做过严谨基准。

另一个卖点是它把三种异步形态接成了一套：Promise.promisify(fn) 把单个 error-first 函数变 Promise 版，Promise.promisifyAll(require('fs')) 直接批量造出 fs.readFileAsync 这一批带后缀的方法，Promise.resolve 能吃 thenable。扩展能力是当时真正离不开的部分：Promise.props（对对象里每个值等 Promise，报表按字段聚合特别顺手）、Promise.map 带 { concurrency: 4 }（原生做不了限并发映射）、Promise.each、Promise.delay、Promise.timeout(p, 5000)、Promise.retry。

诚实地说，它的代价也都是真的。promisifyAll 出来的方法名和官方文档、和 IDE 里的自动补全、和同事搜到的 StackOverflow 答案都对不上，新人读代码要先在脑子里做一次后缀翻译；它替换掉全局 Promise 之后，和第三方库里那些”自定义 thenable”互相纠缠，then 被调用两次、catch 不触发这类怪事都出现过，最后只能把某个库单独换回原生形态；还有一个纯粹是人的问题——.then 一层太便宜，于是代码里到处顺手加一层，链子越拖越长，没人看那个唯一的错误分支。bluebird 3.x 是当期主流，但我们最终的用法收敛成”脚本里可以用，Web 服务里除非要用 map 的并发限制，否则用原生”。

thunk 与 generator：把异步写成同步的那条路

第三条流在 2016 年初的热度很高，值得单独讲，因为它是当时唯一能”让代码读起来像同步”的合法手段。

先说 thunk 这个词在 node 语境里的窄含义：把一个”还需要一个回调才能执行”的调用，变成一个”只吃回调”的一元函数。

它只是参数预应用，不是新语法。配合 generator 的 yield，就能把 yield thunk 的写法变成”看起来一行一步”的同步形态——这就是 co 那条流。

关键年代事实要写准。Node 4 的 V8 已经支持 generator，但只在严格模式下：模块顶部没有 'use strict'，function* 直接是 SyntaxError，这个坑我们在存量 0.10/0.12 的项目里撞过，那些版本连 generator 都没有。co 这边当期主流是 4.x，而 co 4 已经把入口收窄了：co(fn) 只返回一个 Promise，不接受旧版那种”最后再传一个回调”的形态；能 yield 的东西也只收 Promise、Promise 数组、生成器函数和函数那几种，thunk 那套自动包装不再是它主推的路径——上游库自己提供 thunk 风格接口时才用得上，否则得靠转换层。当时好几篇流传的文章还按旧写法举例，同事照着写，一下午卡在 co 那句 object yielded that can't be used 上：你 yield 了一个回调风格的函数调用，它返回的是 undefined，co 不认。

generator 路线的三个真实麻烦

第一，并发还得自己写。yield 天生串行：一行 yield 一个接口，二十个城市三个接口就是六十次顺序往返，第 1 节那个六分钟的脚本一点没变快。要并行必须显式把 Promise 塞进数组或者 Promise.all 一起 yield——上面那版 yield [a, b, c] 就是干这个的。这件事的可怕之处在于它不报错：写成串行和写成并行，功能一模一样，只是慢十倍，而新人几乎必然先写成串行，然后再回头抱怨 node 慢。

第二，调试栈断在生成器边界。报错的时候你看到的是 next() 那一帧，而不是”哪一条 yield 抛的”。bluebird 的长栈在 generator 里也不总能对齐，因为协程被 co 手动驱动，中间那些 resume 帧把因果关系抹平了。我们排一个空数据问题，最后是靠在每个 yield 前加一行 console.log 找到的——这跟当年调试回调地狱的手法其实没有任何区别，只是屏幕上的行数少了。

第三，语法和工程环境配合麻烦。必须 'use strict'，这和当时团队 JS 风格检查里若干条规则会互相绊；存量环境还停在 0.10/0.12 的项目根本跑不动 function*，同一份模块要跨版本只能先转译。转译本身没问题，但 Babel 那一层的配置和构建脚本是额外成本，为了少写几个回调把整条构建链拖长，在我们那儿不划算。

结论就落在下一节。

选型：三条判据，和我们最后落地的组合

我们不再问”哪个库最好”，改问三个能客观回答的问题。

第一，接口给的是回调还是已经返回 Promise。 这决定了成本最低的那条路。存量内部 SDK 全是 error-first 回调，硬上 Promise 就要写一堆 promisify，那种情况下直接用 async 的集合和控制函数反而更短；反之如果依赖已经返 Promise，还要限并发就找 map 带 concurrency 或者 mapLimit，别把已经包好的值再拆回回调。

第二，要不要限并发和重试。 要，就只能选有 queue / Limit / retry / timeout 这些能力的方案，纯 Promise.all 那条路走不通——它连”半个失败”和”上限几条”都不表达。第 11 节那次限流事故之后，这条从”加分项”变成了”硬性判据”。

第三，团队里有多少人看得懂。 generator 加 co 那套，对不常写 node 的同学门槛明显更高：要严格模式、要理解协程何时被驱动、要知道 yield 数组才是并行。跨团队协作的仓库我们宁可停在 Promise 上，代码长一点没关系，读不动才是真成本。

最后落地的组合很朴素：新写的代码统一 Promise（需要扩展能力时在脚本里允许 bluebird）；需要限流、重投、流动任务源的地方用 async 的 queue；只在批处理脚本、而且作者明确知道并行要手写的那部分，用 generator 加 co。三条不冲突，因为它们管的是不同层。

错误处理这条暗线：三种范式各有各的吞错姿势

这节是整件事的暗线，也是我建议读这篇的人优先看的部分。缩进好不好看是表面，错误去哪里才是真的。

回调里，忘了 if (err) 就是吞掉：错误对象被赋给一个没人读的形参，程序继续往下走，产出一份看起来正常的错数据。Promise 里，忘了 catch 就是静默：链在某一跳结束，什么都不会发生，进程甚至不会退出。generator 加 co 里，try/catch 确实能接住 yield 抛出来的异步错误，但它只覆盖 yield 这一行的同步边界——如果你在一个没有交出去的裸回调里 throw，或者在 setTimeout 里忘了处理，那个错误不会走协程的通道，它直接变成进程级异常。

三种吞错方式有一个共同点：都不报错。所以我们后来把纪律写在范式之外：每条链结尾必须有错误处理；任务脚本必须写日志加非零退出码，让外面的 cron 和 CI 能看见失败；process.on('uncaughtException') 当年就被认定为不该依赖的手段——它只是给你一个”在已经不确定状态的进程里再多活一会儿”的机会，用它兜住业务错误等于把问题藏得更深，我们只允许它做一件事：把最后一行日志同步写完然后退出。

第二个事故：串行改全并行，线上被第三方限流

报表脚本上了 queue 之后跑得很稳，直到我们把并发从 4 改成”不限”。

动机很正当：六分钟太慢。测试环境一切正常，甚至很漂亮。线上第一次跑，六十个请求挤在几十秒里出去，第三方接口直接给我们打了限流，返回一堆带着 200 状态码的错误体——那还是最糟的一种失败，err 是空的，我们的错误统计完全没记到东西，报表成片是空行。产品第二天来问”数据呢”，我们才在网关日志里看到那一片 429 和限流提示。

修法不是把并发退回 4 了事。三件事一起做了：并发数变成配置项，每个外部依赖单独一个 queue 单独一个上限（销量和库存不是一个团队的服务，绑一起只会互相拖累）；失败要退避重试，间隔递增再加一点抖动，避免所有任务同步重试；识别那些”200 但是错误体”的假成功，在封装层里显式转成错误。

限流那一步落到代码上就是几条队列各管各的，上限从环境里进来，本地和 CI 给不同值：

当时最实在的一句教训：异步流程控制库替你写的是编排，限流和退避没人替你决定。 它能让六十个请求漂亮地同时发出去，但它不知道对面是一个会限流的第三方。并发数这个参数在我们这儿从此不叫”性能参数”，改名叫”礼貌参数”。

收尾：消灭缩进这个诉求，诚实的答案是什么

回头看第 1 节那个诉求——“把缩进干掉”。诚实的答案是：缩进只是表象，它当时之所以贵，是因为嵌套结构同时锁死了两件东西，一件是错误路径（每层都得自己决定错误往哪走），另一件是背压策略（你根本没法表达”最多同时跑四条”）。库把这两件东西从”每次重写”变成”选一次”：waterfall 给出错误冒泡的形态，queue / mapLimit 给出并发上限的形态，Promise 给出”值的下一步”，generator 给出”读起来像同步”的形态。缩进确实是顺手没了，但那不是收获，是副产品。

真正贵的部分库没替你付：未处理 rejection 得靠纪律，假成功的错误体得靠封装层，限流和退避的参数得靠人对上游负责。我们的版本是 2016 年 4 月的这一套——async 1.5.x 管编排，Promise 管值的传递，generator 只在脚本里用，async 2.0 那一支还在候选阶段我们没上生产。库让编排可写，纪律才让编排可控。这两句差一个字，我们花了四天加一次线上限流才分清。
