代码分割与按需加载实践

那段故障出现在 2016 年 3 月底的一个周四晚上。测试环境干干净净，线上却随机报错：某个页面点开编辑抽屉，控制台甩出一句找不到模块。同一台机器上，有人一点就倒，有人刷新三次没事。问题一沾随机，第一反应都是浏览器缓存。顺着这条线挖下去，比对两个发布版本的编号表，结论比缓存脏麻烦得多：出问题那个模块在这次构建里换了一个编号，而引用它的异步块还是用户浏览器里上一版那份，记的是旧编号。触发点只是入口多引用了一个很小的公共组件。

前一篇讲打包与按需加载的文章，配置字段和 require.ensure 的写法已经过了一遍，本文不重复。这篇往下挖一层：分割之后产物里多了什么，运行时靠什么把一个块找回来，编号为什么这么不稳定。开头那场事故的机理藏在后面，绕一圈再收。

分割和加载是两个动作

编译期做第一个动作：从入口遍历依赖图，把模块切成若干份文件，决定谁和谁待在同一个文件里。它的结果在产物目录里数得出来：几个文件、多大、谁包含谁，构建结束那一刻就定死了。

运行期做第二个动作：代码真跑起来时，决定这一刻要不要去取某一份文件，取回来怎么接进已经跑着的环境。它的结果只能看网络面板的时间轴——一次往返、一段排队、一次合并。

讨论时两件事总被混着谈。拆开之后就知道，切分只改变文件形状，首屏快不快取决于你切出去那块首屏要不要用。

运行时那份东西

先说一个我误解掉的事：产物不是一段段能独立跑的脚本，每个块外面都套着一层加载引导。2016 年那会儿我把产物打开看过形状，只说我们当时读到的是什么：一个块整体是一个函数调用的形式，最外层递进去一张表，表里每一项是一个模块编号对应一个工厂函数，工厂函数就是模块代码被包一层函数，参数里塞给它取依赖的入口和导出对象。

那张表之外还有两样东西住在公共的运行时里：模块编号到工厂函数的查找表，和哪些块已经加载过的标记。异步块取回的链条画出来是这样：

flowchart TD
  A[执行到切分点] --> B[查已加载块标记]
  B --> C[未加载: 插入 script 标签取回该块]
  C --> D[块外层引导把工厂函数合并进查找表]
  D --> E[回调执行, 从表里取模块]
  B --> F[已加载: 直接执行回调]

关键在最后两步。异步块插进文档，浏览器把它当一个普通脚本执行；它外层那段引导做的事，就是把本块的工厂函数合并进公共运行时那张表，补上已加载标记，回调才有东西可查。块与块之间不靠全局变量说话，靠共同引用同一份运行时。这份运行时必须先于所有块执行，标签顺序错了就是白屏。

模块 ID 从哪来，为什么会漂

这条链里编号是唯一的接头暗号，回调取模块、块之间合并工厂函数用的都是它。它必须各方一致，偏偏最容易变。

webpack 在 2016 年这套 1.x 里分配编号的依据，不是文件名也不是路径哈希，而是模块在依赖图里的位置：从入口出发按遍历顺序累加。这策略简单、编号短、没有额外成本，代价是一致性极度脆弱。入口多加一行引用，遍历顺序从那一行起整体后移，后面所有模块的编号统统漂一位。漂位在纯同步产物上不算问题：模块和查表逻辑在同一个文件里，一起构建一起发布，天然对齐。可只要一个模块被切进异步块，它就有自己的生命周期：文件能在浏览器里活很久，编号却写死在那份文件里。改的是主包，漂的是编号，埋雷的是三个月前发布的那个异步块，三个条件凑齐才炸。这就是线上随机、本地复现不出来的原因。

排查值得记，构建输出早把答案给我们了，只是没人看：命令行当时能把依赖图摊平列出，模块路径和归属块一目了然。

两个版本各跑一次，一比就知道某条路径的序号动没动。更土也更直接的做法是在产物里搜模块路径字符串，工厂函数附近就是它分到的号。

让编号稳定：当时可行的几种办法

先声明一句，这一节是几种当时能用的做法，不是标准答案。我们没找到可以直接拿来即用的确定性编号方案，2016 年这一块基本靠发布纪律补。三条办法都在削同一个东西：漂位的波及面。

第一条，把最容易引发漂移的模块从会变的块里抽出去，收进单独一块。抽公共块的配置前一篇给过，这里只说机制意义：那是在缩小编号表的变更范围，不是在减体积。

第二条，把入口写薄。入口只做聚合和挂载，业务依赖通过一层中间文件引进去，效果是入口遍历顺序的变动少多了。我们后来把改入口当成需要专门评审的改动，就因为这一层一动，全图编号跟着动。

第三条最靠得住：别指望编号不变，让文件名跟着内容变。发布时把块的文件名带上内容哈希，2016 年这个占位符写 [chunkhash]，同时让引用它的那份运行时一起换。它的价值不在消除漂移，而在保证编号和产物成对：新主包引不到旧块，旧主包也引不到已经不存在的文件。

粒度怎么定：三条判据

真写代码时的问题更朴素：切几刀，切在哪。三条判据，都能当场验证。

第一条，只有特定交互之后才用得上的代码才值得切出去。点编辑按钮才需要的富文本、点开报表才需要的图表装配都够条件。反过来，第一屏就要执行的代码切出去，只是把下载推迟几毫秒，往返成本照付。

第二条，切出去那块加载要花一次网络往返，用户等不等得起。口径很粗：触发之后屏幕上要有可见变化吗。用户点了要立刻看到结果的地方，切分等于在点击和结果之间插一段网络时间，弱网下能插到一秒以上，这类我宁可留在主块里。

第三条，切得太碎时文件数量的成本高于体积收益。这条有个硬前提：2016 年浏览器对单个域名只有约六条并发连接，HTTP/2 还没在浏览器里默认打开，多文件就是排队，每个文件还要各付一次请求头。

从三个切到十七个那次就是第三条的账单。后台列表页我照着组件一个个往下切，表头、筛选条、分页、行内下拉、批量操作条各成一块。单看每个文件都瘦了，首包也小了。真实网络跑一遍总耗时反而涨：十几个小块同时发起，六条连接占满，剩下的排队；更难受的是块之间有先后，取回 A 的回调里才发起 B，时间轴上出现两截瀑布。回退到按交互边界切的四个块，首包大一些，从进页面到可操作的时间却最短。从此每次切分我都要先写出理由，写不出理由就是纯成本。

机制层会翻车的几个位置

异步块里再引异步块。嵌套合法，但每深一层就多一次串行往返，第二层要等第一层回调执行才发起。超过两层我就回头重划边界，通常做法是合成一块或把公共部分提回主块。

同一模块同时被同步和异步引用。归属是编译期定的：模块进了主块，异步块再引用它就是从已有表里查号，不会重复下载。坑是反过来——你以为主块里有，其实它只被异步路径引用，于是它待在异步块里，首屏那段代码去查就查不到。我们的做法是把首屏要用的模块显式从入口引一遍，归属钉死，不靠推测。

切分点写进循环或高频事件回调。每次触发都走一遍查标记再决定要不要取，块早就加载完了这判断还在反复跑，还连带新建闭包。滚动、输入、鼠标移动这类回调里，我只留一个已加载的布尔标记，取回逻辑写在标记外面执行一次。

加载失败时的表现最让人没安全感。我们的观察是：script 标签请求失败时回调根本不会被执行，也就没有可靠的错误参数可接；System.import 那种直接返回承诺的写法在 2016 年还是草案，没上生产。所以失败得在调用处自己兜住，当时能落地的是超时加降级两层。

超时是保险丝，因为我们接不到 script 的失败信号；真正干活的是 fallbackToSyncPath：退到一条不依赖异步块的可用路径，哪怕只是提示用户刷新，也比点了没反应强。

首屏与二屏：分割点该怎么挑

把首屏必须的和滚下去才需要的分开，跟按需加载是同一套机制的两种用法。这块的原理性优化前面几篇已经写过，本文只讲分割点该怎么挑。

判断顺序三步，顺序比结论重要。先看这块代码是否影响首次可见内容，影响的一律不进异步块，这是底线，不看体积。再看体积：不影响首屏而且明显大的，切出去收益直接。最后看复用范围：被三个异步块共用的中等模块，再切出去就是多造一个公共块和一堆引用关系，这种我留在其中一个块里或干脆留主包。第三步是产物组织问题，把它的洁癖放到体验判断前面，就会切出技术上整洁、点击要等一秒的布局。体积怎么量化、压缩收益怎么排序，那篇讲构建产物分析的聊过，这里不铺开。

和加载器那条路差在哪

SeaJS、RequireJS 那一路也叫按需，但两个按需不是一回事。加载器那条路是运行期按模块 id 取文件，id 到文件的映射靠配置或约定维护；打包器这条路是编译期决定谁和谁在同一个文件里，运行期只按编号查表。前者把关系交给人和运行时维护，后者把关系由构建固化进产物。

判据三条。依赖复杂度：模块上百、引用网状、还要处理路径别名时，我愿意让构建期把关系算完，运行期只查表。构建链是否就位：加载器那条路不需要打包步骤，接手没有构建的老项目时当天见效；打包器这条路得先有 node 环境和一条构建命令。谁维护映射：加载器的映射散在配置里，挪一个文件就要补一处，半年后没人补就报 404；打包器的映射在产物里，重新构建就自动一致。

当时很多项目两条路混着用，最容易出的问题很具体：同一个库在两条链上各有一份——加载器按自己的映射从静态域名取一份，构建又按依赖图把它算进产物，用户下载两份，全局状态还各说各话。我们的原则是让构建产物成为唯一入口，加载器那条路的映射全部指向已有块，指不了就不许混。

回到那次线上事故

那次故障的修法就是把第三条做彻底，落到两处。发布纪律：每次发布把异步块文件名换成内容哈希，让引用这些块的运行时和主包一起换，产物目录里上一版保留一段时间不清。入口结构：入口文件的改动升级成要两个人看的变更，合之前先跑一次模块列表比对，确认编号漂到哪。

事后我归纳成一句判断：代码分割的收益是体积层面的，风险是引用一致性层面的。体积收益当场算得出来，一致性风险却只在旧产物遇上编号表时才暴露，一暴露就是线上随机故障。做分割之前先把一致性手段想好，比想清楚要切几刀更要紧。
