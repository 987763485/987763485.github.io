Node.js 文件系统 fs 模块详解

今年三月我们吃过一次很蹊跷的亏：一个生成配置的 node 脚本在本地跑得好好的，放到服务器上却隔三差五吐出半截 JSON，下游服务 JSON.parse 直接炸。查了两天才想明白，写入方还没写完，读取方已经凑上去读了——文件在那一瞬间真实存在，内容却只有一半。后来我整理 fs 相关的笔记，开头都先写这句：fs 的坑几乎都在”你以为它做完了，其实它做了一半”。它给你一套看起来人畜无害的 API，但不会替你把”完成”这件事定义清楚。

三种 API 形态，先认清自己手里有什么

fs 的每个操作基本都有两张脸。同步版像 readFileSync、writeFileSync、readdirSync，调用即阻塞，返回值就是结果，出错靠抛异常，你用 try/catch 接。异步版是回调风格，约定是错误优先：第一个参数永远是 err，为 null 才去看第二个参数的数据。

要说清楚的是当期没有的东西：Promise 版的 fs API 在 2016 年 4 月的 Node 4 上还不存在，fs.promises 要到之后好几年才进标准库，await 读文件更是想都不用想的未来语法。想在异步流程里用 Promise，只能自己包一层，或者靠第三方库替你包。我们当时的包装函数就十行，new Promise 里调异步版，err 走 reject，数据走 resolve，全文如下：

同步还是异步：给一条硬判据

这个问题不需要争论，看进程是谁就行。同步版在启动阶段、命令行脚本、构建任务里完全合理：这些场景里事件循环本来就没有别的活要干，阻塞就是阻塞呗，代码还直白——拿结果、判断、下一步，不用套五层回调。写迁移脚本时我全用 readdirSync 加 statSync，一百个目录遍历下来干净利落。

反过来，在任何长驻服务的事件循环里用同步读文件，等于自我 DDOS：Node 是单线程跑回调的，一次同步读进行期间，所有排队中的请求、所有定时器全部原地罚站，你读多大的文件，客户端就等多久。我们当时没有压测工具，就用一行 console.time 自证：同一个几百 KB 的文件，循环里同步读五十次和异步读五十次，服务顺带处理另一个计时任务的输出节奏，肉眼就能看出同步那版里中间的活全挤在末尾一起吐出来。具体几毫秒我不写，机器不同数字就没参考价值，结论是定性的：同步读期间事件循环上没有第二条回调在跑，这是语言层面保证的，不用测也该信。

判据就一句：这段代码所在的进程，同一时刻还有没有别人在等它。没有别人，用同步；有别人，用异步。

编码与 Buffer：转码发生在哪一步

readFile 不带编码参数时返回的是 Buffer，一袋原始字节，不是字符串。很多诡异问题出在没意识到这一步：

反过来 writeFile 只有收到 Buffer 时才不转码，原样落盘；给它字符串，它按编码（默认 utf8）转成字节再写。所以”读进来什么写出去就什么样”要靠 Buffer 进 Buffer 出才成立，中间只要碰了字符串，就赌上了编码一致。

把 Buffer 当普通字符串拼更是想当然：buf1 + buf2 走的是隐式 toString，得到的是类似字节列表转文本的怪东西，不是拼接内容，必须用 Buffer.concat。还有个更阴的场景：分块读取时按固定字节数切块，utf8 的中文占三个字节，切点落在字符中间，拼回去就是一个替换字符或者乱码。当期解法两条，要么干脆整块读完再一次性转码，要么交给流那一侧的解码器去处理断字符（机制在 stream 那篇，本文不碰）。顺手说个历史包袱：encoding: 'binary' 这个名字从 Node 早期就有，它其实一直是 latin1 的别名，拿它当”二进制”用恰好无损是因为逐字节映射，不是因为它懂二进制；新代码写 latin1 更诚实。

目录操作：一条条都是断头路

fs 对目录的支持是这套 API 里最”当期凑合用”的部分，每一条都得单独记：

  • fs.mkdir 不支持递归创建。给它 a/b/c 而 a/b 不存在，直接 ENOENT。要么自己一层层建，要么上 mkdirp 这个包，构建脚本里几乎人手一个。
  • fs.readdir 不递归，只给一层的名字列表，而且返回的连相对路径都不带，要自己拼。想遍历整棵树只能手写递归，还得用 lstat 防符号链接转圈。
  • fs.unlink 只能删文件，对目录返回 EPERM 或 EISDIR 一类的错；fs.rmdir 只能删空目录，非空就报错。
  • 删掉一棵树——比如清理构建产物——当期没有一条 API 能做，通行做法是 rimraf 这个包，或者自己递归：先 readdir，逐个判断是目录就递归删、是文件就 unlink，最后 rmdir 自己。

复制文件：三条路各付什么价

先堵死一条：fs.copyFile 在 2016 年 4 月还不存在，那是之后好几年的事，别翻到现代教程就照着写。当期复制一个文件就三条路。

第一条，readFile 加 writeFile。两行代码，心理最踏实，代价是文件多大内存就吃多大。批量复制时更糟：十几个大文件并发读进来，回调还没落盘，峰值内存就是所有文件之和。小工具里图省事用 readFileSync 循环复制整个资源目录，本地跑没事，上了 512M 内存的小机器就看着它涨——这是我们真金白银的复盘，别学。

第二条，createReadStream 接 createWriteStream，中间一个 pipe，一句话的事，内存稳得住。它为什么稳、错误为什么要单独接，都让给 stream 那篇讲，这里只留一句口诀：文件可能上百 MB 的，走流，别把大文件整个 readFileSync 进内存。

第三条，调外部命令 cp。Linux 机器上系统自带的 cp 经过多少年打磨，语义比多数手写循环可信。要不要这么干，第 11 节给判据。

元信息与错误码：别再用 existsSync 走捷径

stat 和 lstat 的区别只在符号链接：stat 跟随链接看目标，lstat 看链接本体。要判断”这是不是个软链”只能用 lstat，遍历目录防环也是它。拿回来的 Stats 对象上常用的就几样：isFile()、isDirectory() 这两个方法判断类型，size 给字节数，mtime 给最后修改时间——做增量构建靠的就是比对 mtime。

判断文件存在，新人爱用 fs.existsSync 或者回调版 fs.exists，捷径看着甜，实际是坑。第一，存在和”你能读能写”是两件事，权限不对时 exists 照样返回真，下一句 readFile 照样挂。第二，检查和打开之间文件可能被别人删掉或创建，这个竞态在长驻服务里迟早撞上。当期正规做法是直接发起 open 或 readFile，回来按 err.code 分类处理：

ENOENT 到 ENOTDIR 都好理解，值得单独说的是 EMFILE：一个进程同时打开的文件描述符打满了上限。它是当年构建脚本里的常客——并发回调撒出去几百个 readFile，谁也没 close，或者 watch 句柄攒了一堆没关，报的就是一句莫名其妙的 EMFILE。遇到它先怀疑自己开得多关得少，而不是去调系统上限。

路径与 cwd：一个纪律问题

__dirname 是当前脚本文件所在的目录，模块加载时就定死；process.cwd() 是进程启动时的工作目录，取决于你在哪儿敲的命令。用相对路径写 fs.readFile('data/config.json')，它按 cwd 解析——同一段代码，从项目根跑没事，被别的脚本从上层目录调用就漂了，报 ENOENT 还找不到北。

拼接一律用 path.join，别手写 + '/' +：Windows 的分隔符不一样，重复斜杠、尾部斜杠这些边角 path.join 都替你收拾了。path.resolve 的语义是”从当前工作目录出发把它解成绝对路径”，多个参数像 cd 一样逐级叠，碰到绝对参数则重新开始；它解决的是”给我一个去哪都成立的完整路径”。fs.realpath 用于把软链全部解开拿到真实位置，只在一种场景下需要：你要比较两个路径是不是同一个文件，或要把用户传进来的链接路径归档到真身。

watch：诚实版说明

fs.watch 听着是最顺手的监听入口，用过的都知道要降低期待。它底层直接对接系统的文件事件机制，而各家机制的粒度和脾气完全不同：同一份代码，mac 中 FSEvents 和 Linux 中 inotify 给你的事件次数、eventType 的内容经常对不上；一个最典型的例子是多数编辑器保存文件走”原子保存”——先写临时文件再 rename 覆盖，于是你在 watch 回调里看到的是”文件被删了”跟着”又有文件被建了”，而不是”它变了”。

fs.watchFile 是另一极端：纯轮询，定时 stat 比对，跨平台行为倒是稳定，代价是开销明晃晃摆在那，盯的文件一多 CPU 就跟着交房租。

当期稳妥的做法是把 watch 当”提示”而不是”事实”：监听父目录而不是单个文件，这样即使文件被删了重建句柄也不丢；回调里自己加防抖，收到事件后延迟一小段再处理，把一次保存引发的连环事件合并成一次；最后必须准备兜底——事件不可靠或进程错过了一段时，直接全量重扫目录比对 mtime。我们构建工具里的 watch 模块最后就是三层：事件只做触发器，防抖收敛，真正判断”哪个文件变了”靠重扫。把正确性押在事件上，迟早翻车。

权限与属主：运维侧的两种抱怨

fs.chmod 改权限位，fs.chown 改属主和属组，后者需要进程本身有资格（一般得 root）。fs.access 当期就能用，拿它探测”我到底读得了写得了吗”，比 existsSync 讲道理——它按真实的权限位和当前用户判断，返回错误就是不行。

坑主要在部署机上，两种抱怨最常见。一是 umask：脚本里 writeFile 新建文件的权限是默认模式被进程 umask 削掉一层的结果，写代码时按 0666 想的好好文件，落盘变成 0644 甚至更紧，下一个用户执行就 EACCES。要确定权限就在写完显式 chmod，别猜 umask。二是属主：用 root 跑完整建，产物全部归 root，运维再用普通账号去改去清理就动弹不得，最后要么 sudo 一路陪跑要么重跑一遍。发布脚本里跑完补一句 chown，或者干脆别用 root 跑构建，比事后救火省事。

原生 fs、外部命令还是第三方包：三条判据

fs 的 API 面很大，但很多活当期根本不该在 fs 里解决。用 child_process 调外部命令是一条正经路：exec 一个 cp -R 或 rsync，特别是从本地往服务器同步大目录，rsync 的增量传输和权限保留手写多少行都追不上。shelljs 这类包是另一条：它的价值不在能力，在于脚本读起来像 shell，cp、mkdir、rm('-rf') 一眼就懂，团队里前端和运维都能接手。

我们的三条判据。一，看动作在系统层有没有更成熟的实现：同步大目录、改权限这一类，外部命令打磨了二十年，别用 JS 重写。二，看部署环境允不允许加依赖：线上机器跑的是运维的账号，多一个包多一条安装链路，这种情况下宁可手写递归也要只用原生 fs。三，看这段逻辑要不要被别的模块 require：会被复用的代码必须可测试、行为可预期，这时第三方包里被大量使用过的 mkdirp、rimraf 比自己写的递归放心。三条都不沾的小脚本，怎么省事怎么来，不用有负罪感。

小结：回到那半截 JSON

开头那个事故的根因不是哪个 API 用错，是写入不原子：writeFile 分很多个 write 系统调用落盘，读取方恰好在中间插了一脚，看到的就是半截文件。当期可执行的修法只有一条：写入方先把新内容写进同目录下的临时文件，写完并确认回调成功，再用 fs.rename 挪到正式名字上。同一目录内的 rename 是原子的，读取方看到的要么是旧文件要么是完整的新文件，不存在中间态。

临时文件加点前缀避免被 readdir 当成正式产物，这是细节；把”写完再改名”当成默认写法，才是这条纪律的价值。回头看这一整篇，同步与异步、Buffer 与流、watch 与轮询、原生与外部命令，选错了顶多是慢、是多写几行；而”以为做完了其实做了一半”选错是会半夜来电话的。所以比起任何 API 选择，更要紧的是把 fs 的每次完成当成没确认过就不算数的事。
