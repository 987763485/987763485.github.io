Express 4 中间件机制完全解析

这个月线上那次事故，起因小得不值一提：给后台接口加一层登录校验，本地测了一下午都正常，第二天灰度就发现有个路由能绕过校验直接返回数据。查了两个小时，最后的问题出在一行代码的位置上。那两个小时里我把校验函数翻了三遍，把会话配置翻了两遍，甚至怀疑过代理层转发时丢了 Cookie，谁都没去看 app.js 里那几行 app.use 的先后顺序。而它恰恰是唯一的原因：那个绕过校验的路由，注册在校验中间件之前。

那次之后我逼着自己把 Express 4 的路由相关源码读了一遍，读完有个挺解脱的结论：Express 提供的能力就一件事——维护一个按注册顺序排列的函数数组，请求进来时依次调用。它不做依赖注入、不管执行顺序编排、不检查你有没有把链条走完，一切所谓架构，都是你自己在这个队列上排出来的。这篇就把这个队列讲透：它怎么排、路径怎么匹配、错误怎么往后传、req 与 res 从哪来，以及为什么你写的中间件不生效。版本口径先钉住，免得有歧义：全文基于 Express 4.13 一线、Node 4 LTS 为主，npm 2.x 与 3.x 混用；Express 3 那条线在存量项目里还活着，本文只在讲”内置中间件被拆出去”时和它对比。Node 6.0.0 恰好是 2016 年 4 月 26 日这天刚放出来的，我们不会立刻上；官方那边在往前推进，但 4 之后的那个大版本当时还没有可用版本，我们也没敢跟。

中间件是什么：一个签名，三条约定

中间件的识别标准在 Express 里只有一个函数签名：三个参数，(req, res, next)。前两个不用讲，第三个 next 是整件事的核心，而新人对它的理解十有八九是偏的：next 不是”返回”，不是”结束当前这个函数”，它的含义是把控制权交给队列里的下一个函数，而当前函数剩下的代码还会照常跑完。

围绕这个签名有三条约定，违反任何一条的症状都不一样，但都不算”报错”，所以很容易误判方向。

约定一：既不 next() 也不响应，请求就挂住。 这是新人犯得最多的一个错，而且它失败得极其安静：没有异常、没有日志、状态码都没设，浏览器转到超时。原因回到那句”Express 只维护队列”——它调用你的函数，函数返回了，队列就停在当前位置，后面的中间件永远不会被调用，也没有任何兜底逻辑替你回一个 500。我见过最曲折的一次，是同事的中间件里有个分支没走到 next，只有带某个查询参数的请求会挂；测试用例覆盖不到那条分支，本地点半天没事，一上灰度就被健康探针的超时揪出来。自查最快的办法：在函数最后一行补一个无条件 next()，看请求是不是立刻通了；通了，说明问题就是某个分支漏了出口。

约定二：调了 next() 又继续响应，就是重复输出。 next() 是同步把下一个函数跑完再回来的，所以你在它后面写的响应代码会执行第二次；一个响应意味着一次响应头写入，于是当期日志里会出现那句很硬的 Cannot set headers after they are sent。这条纪律没有第二种解释：next() 之后的那一行开始，不该再有任何事发生；要交棒就写成 return next()，把函数当场收掉。

约定三：Express 不知道你是不是异步。 它只是调用你的函数，然后看 next 有没有被调到；函数自己返回，不等于处理完成。所以异步回调里必须记得调 next，哪怕你的函数已经 return 了。这里先埋一个后面要还的债：正因为 Express 不看返回值，异步回调里抛出的错误它也抓不到——这一点在错误处理那一节会展开，它是当期 bug 密度最高的一处。

队列长什么样：顺序先于语义

app.use 做的事朴素到可以一句话说完：往应用级的处理器数组尾部追加一项。app.get('/api/user', fn) 也是追加，只不过追加的那一项额外记住了”我只接受 GET，只匹配这个路径”。请求进来时，Express 从数组第 0 项开始逐项尝试：路径对不上的跳过，方法对不上的跳过，对得上的就调用它的函数。这个循环只认顺序，不认语义——它不会因为某个函数看起来”理应更早执行”就把它提前，也不会检查你是不是把解析请求体的东西放在了读请求体的代码后面。

app.use 的路径语义：前缀、剥掉的 req.url 和 originalUrl

这一节是把”我明明挂了为什么没进”讲清楚的地方，因为答案九成藏在挂载路径的语义里。

第一件事：app.use('/api', fn) 里的路径是前缀，不是精确匹配。命中的边界是按路径段算的，/api/user、/api/order/list、连 /api 本身都算命中；/apix/user 不算。所以你以为”/api 底下所有接口都会经过校验”，实际是”URL 开头是 /api 的都会经过校验”，这两句话在很多团队里被当成同一句用，直到有人注册了一个 /apiconfig 之类的路径。

express.Router：把一段队列打包成可复用单元

express.Router() 当期的定位一句话能说清：它就是把一段中间件队列打包成可复用单元，本身是一个带 use / get / post 的小型分发器，注册规则和 app 上完全同构，同样只认顺序、同样是前缀语义。所以我们把 /api/user、/api/order 两条线各自拆进 routes/ 目录，app.js 里只留挂载。

还有一点关于 next 的作用范围：router 里调用 next() 只走到本队列的下一项，本队列跑完，控制权回到 app 的主队列继续往后。想从 router 内部直接跳出这一整层，当期可以写 next('router')；只想跳过当前路由剩下的回调，写 next('route')。这两个字符串是 Express 4 里的正式约定，不是我们 hack 出来的。

拆 router 的边界我们试过两种：按 URL 前缀拆和按职责拆。当期最终选前者，因为鉴权那一段直接挂在 app 上就够，不值得为它多开一层——层级每多一层，顺序的可读性就掉一截。

错误处理中间件：四参数、跳过与收口

错误处理是本文最该单独讲的一节，因为它和普通中间件是两套查找规则，而这套规则写在函数签名里。

错误处理中间件的签名是四个参数：(err, req, res, next)。Express 判断你是不是错误处理器，靠的是注册时读函数对象的 length 属性（形参个数）——fn.length === 4 就算错误处理器，三个参数的同一个人畜无害的函数只会进普通队列。这个判定不看函数名、不看注释、不看你在里面怎么写 if (err)。后果非常直接：少写一个参数，错误永远不会走到你这里，你收到的是那个默认页面，还以为是错误处理器有 bug。

传播规则也要讲准：next(err)（传任何非空参数）会让 Express 从当前位置向后找下一个四参数处理器，中间所有普通中间件和路由回调全被跳过；找不到就落到内置的默认错误处理器上。默认处理器当期行为是：NODE_ENV 不是 production 时，把 500 状态码连同错误堆栈一起写进响应体；production 下只回状态码和很短的提示，堆栈只进日志。这套行为有两个理由让我们一定要自己写一个：一是我们的接口全是 JSON，默认那一下返回的是 HTML，前端 JSON.parse 当场失败，用户看到的是白屏而不是错误提示；二是上报——线上必须有把 err.stack 落到日志平台那一手，默认处理器管不了这个。注意它只向后传播、不回头，所以错误处理器必须注册在可能出错的中间件之后，放在队列开头等于没放。

再补一句当期真实、也最坑人的事实：别指望 try/catch 兜住路由里的错误。你自己写的 try 块不在那个调用栈上——处理器是 Express 在它自己的分发循环里调用的，你在 app.js 外面包一层什么都抓不到。而异步里抛出的错误当期根本没有自动捕获这回事：回调里 throw，进程直接以未捕获异常退出，日志里连请求路径都没有。结论只有一条纪律：所有异步回调的第一个分支必须显式 next(err)。

把 err.status 挂到错误对象上再交给 next(err)，是我们当期统一的错误表达形式：业务层只负责造一个带状态码和文案的错误对象，收口的四参数处理器负责回什么形态。这样接口层不必每个回调都写一遍 res.status(404).json(...)，也避免了”响应过一次又走到错误处理器”这个重复输出场景。

Express 4 把内置中间件拆出去了：迁移视角

Express 4 相比 Express 3 最主要的变化之一，是把一批原来挂在 app 上的内置中间件拆成了独立包，要自己 require 回来。3 那条线里 express.bodyParser()、express.logger()、express.cookieParser() 都是框架自带的命名空间，4 之后这些名字都不在框架里了，对应关系得背：

Express 3 挂在 app 上 Express 4 需要的独立包
express.bodyParser() body-parser
express.logger() morgan
express.cookieParser() cookie-parser
express.compress() compression
express.methodOverride() method-override
express.errorHandler() errorhandler
express.static() 仍在框架里，不用装

为什么拆：3 的内置中间件和框架版本被焊死在同一个包里，想单独升级解析实现就得跟着框架一起动；另外那个 bodyParser 其实同时打包了 JSON、表单和文件上传三件事，多数项目只用其中一个，却每次都要为上传那条分支装原生依赖；拆出来之后各包独立发版。代价是所有老代码要改一遍 require，而且 npm install body-parser morgan cookie-parser compression --save 之后版本号归各包管了，得靠 npm-shrinkwrap.json 把当期确认可用的那一套钉住——这是我们 2016 年上半年的常规做法，别指望 ~ 能替你挡住小版本里的行为改动。

拆完之后的注册顺序比在 3 里更有讲究，因为现在每一段都是独立包，谁先谁后完全由你写：

morgan 放第一段，是因为它把日志记录挂在响应的结束事件上：放在别人后面，被前面短路掉的请求就不出现在访问日志里，排查时你会以为那个请求从没来过。compression 必须在 express.static 之前，不然 CSS、JS 这些静态产物就是裸着发出去的。express.static 放在 body 解析之前，是为了让图片请求根本不进后面那条链路——它命中就直接 end 掉，后面的鉴权和解析都省了；反过来把它放在鉴权之后，就会出现”用户要登录才能拿 CSS”这种荒谬现象。cookieParser 那一条最直白：req.cookies 是它写上去的，任何读它的中间件排在它前面就是永远读到 undefined，而这种情况不会在任何地方留下报错，只是判断分支静默走进”未登录”。

req 与 res 是在原生对象上扩展出来的

前面反复出现”req.body 是别人挂上去的”，这里把这条线一次说清：你在中间件里拿到的 req 和 res，就是 node 原生 http 模块那两个对象（IncomingMessage 与 ServerResponse 的实例），Express 在它们身上又加了一层自己的方法和属性。分层理解到位，很多”为什么这个写法也能跑”和”为什么那个报错”就都有解释了。

原生那一层仍然全部可用：res.end、res.write、res.writeHead、res.statusCode、req.headers、req.method、req.connection。Express 加的那一层里，req 侧有 req.query、req.params、req.ip、req.hostname、req.fresh、req.stale、req.accepts、req.get，res 侧有 res.status、res.set、res.send、res.json、res.jsonp、res.sendFile、res.render、res.redirect、res.vary。这两层的实际差别在”谁替你做了什么”：res.end('ok') 只写正文，Content-Type 没人管、Content-Length 不算，浏览器经常把一段 JSON 当纯文本显示；res.send('ok') 会把类型和长度都设好，给字符串按 HTML 发，给对象按 JSON 序列化。但知道原生那一层还在、还可用很重要：真要流式输出，或者要绕开框架替你做的编码判断时，那是唯一的出路。

res.send 与 res.json 的差异当期就有三处，很容易写混。第一，参数是数字时语义完全不同：res.send(200) 把 200 当状态码，响应体是空的；res.json(200) 把 200 当正文，发出去是 200。第二，res.json 走 JSON 序列化路径，会按 json spaces 设置格式化，当期非 production 环境默认带缩进，res.send 给字符串时不会。第三，res.send 对 200 响应会带上 ETag，配合 req.fresh 能做条件请求；一旦你显式设过 Cache-Control: no-cache，req.fresh 的结果就会和预期不同——这类两个字段互相影响的坑，只有把 req 属性和 res 方法当成同一层来看才不会踩。

还有一个当期会直接撞上的硬报错：res.sendFile 必须给绝对路径。写成 res.sendFile('public/index.html') 会当场失败，提示大意是要求文件系统的绝对路径，正解是 path.join(__dirname, 'public/index.html')。而它失败的方式不是抛异常，是通过回调或者 next(err) 把错误交给你——找不到文件时你拿到的是一条 ENOENT，所以只要用了 sendFile，要么给它传回调，要么保证队列末尾有四参数处理器收着，否则用户拿到的是默认那一下。至于 res.render，它依赖 app.set('view engine', ...) 指定的模板引擎，当期我们视图用的是 Jade 和 EJS 两套，渲染出错同样是走 next(err) 进错误处理器，不是在你眼前抛。

写中间件的三条纪律

把前面的机制翻译成能贴在墙上的规范，就三条。

其一，明确自己是终点还是过路，而且所有分支都要有出口。 不响应的中间件必须以 next() 收尾，且每一条 if / try / 回调分支都得走到 next 或响应之一。这不是”最佳实践”，是队列模型的直接推论：你不出口，链条就断在你这里。我们后来的 code review 里对中间件只问一句话：”这个函数有几条退出路径？”数不清的不合。

其二，除非你确定要就地回应，否则不要把错误咽掉。 在中间件里 catch 了异常又只 console.log 一下，等于自己造了一条挂住的请求：客户端等到超时，日志里什么都没有，运维以为服务挂了。正确姿势是 return next(err)，把决定权交给最后一层那个四参数处理器——它负责状态码、负责日志上报、负责决定给不给前端看堆栈，这件事只该有一个地方做。

其三，需要配置项的中间件，用工厂函数返回中间件的形态。 这是当期所有中间件包的统一形态（bodyParser.json(options)、compression(options) 都是调用一次拿到一个函数），自己写也照这个来：

排障手册：中间件没生效的七种情况

这一节是本文真正会被翻来复用的部分。每条只给两样东西：现象，以及先看哪一行代码。它们全都来自前面那套队列模型，不是七条孤立的技巧。

情况一：中间件看起来完全没跑，请求返回正常。 先看它在 app.js 里的注册行，往上数——有没有哪一行在它前面就已经 res.send / res.json / res.redirect 了。队列里有人在它之前当了终点，它就永远轮不到。最典型的凶手是 express.static：命中静态文件直接结束响应，后面的日志与统计中间件全部不执行。

情况二：一部分请求进来了，另一部分没进。 先看挂载路径那个字符串。把 app.use('/api', fn) 和实际请求 /apiconfig/list 对照着看，前缀边界差一个斜杠就是全进或全不进。这类问题打一行 console.log(req.originalUrl) 在服务入口，一屏就能看出来。

情况三：函数里逻辑都对，但 req、res 像是错位的。 先数签名的参数个数。你要写普通中间件，却写成四个参数（多带了一个没用到的 err），Express 就把你登记成错误处理器，普通请求根本不叫你；反过来你要写错误处理器却只写三个参数，错误就永远不往你这走。这条是本文最贵的一个坑，因为它没有任何提示，函数就是安静地不被调用。

情况四：路由在子文件里写得好好的，访问却是 404。 先看主文件里那行 app.use('/api', router) 在不在、位置对不对。router 不挂载就只是一段没人引用的数组；挂载行漏了，症状和路径写错一模一样，很容易又回头去查前缀。

情况五：next 被调用两次。 当期表现要么是一句 Cannot set headers after they are sent，要么是响应内容重复出去一段。先看哪一行代码：找到那个异步回调，九成是超时分支和正常分支都调了 next。开发期可以套一层断言把这个问题当场暴露，别等线上日志：

生产环境别开这段：它把可控的重复输出换成了进程级异常，不值。它的价值只在于让开发期一次跑出来。

情况六：错误明明发生了，你的四参数处理器却没进。 现象通常很难看：接口返回的是默认那一下，或者干脆等到超时，日志里是一条未捕获异常。先看抛出错误的那个异步回调——是不是 throw 了，或者干脆把错误 if (err) { console.log(err); return; } 这样吞掉了。异步分支里的错误当期没人替你转成 next(err)，这一条和约定三是同一件事。

情况七：/health 这类探针接口被鉴权拦住。 现象很有迷惑性：浏览器一切正常，监控却持续报服务不可用。先看鉴权中间件里那句判断——探针不带 Cookie，被 401 掉了。修法不是把探针注册到鉴权前面（那样等于把顺序当配置用），下一节会讲正路。

顺带一条通用手法：把每个中间件的入口打一行 req.method + ' ' + req.originalUrl + ' -> ' + 名字，跑一次出问题的请求，看这行日志停在哪一段，停住那一段的下一项就是没被调用的那个。这比读源码快一个数量级，因为问题几乎从来不藏在实现里，都藏在注册顺序里。

把顺序约束套回自己的项目

讲到这里可以看见，前面那些排障条目和分层其实是同一件事的正反面：中间件的依赖关系只有”谁先注册”这一种表达方式，所以分层必须按依赖顺序排下来。我们那个 Express 4 应用最后收敛成三层，app.js 里就一段，注册顺序即文档：

这个排法有两条硬规矩。第一条是第三层只许读前两层准备好的字段：业务路由里要用 req.body，bodyParser 就得在上面；要用 req.cookies，cookieParser 在上面；要用 req.session，会话中间件在上面。第三层里不许再出现任何”补字段”的中间件，因为下面两层跑完之后没有回头路。第二条是收口只留一个错误处理器：注册多处四参数处理器，等于有多个地方在决定错误响应长什么样，而错误只向后传播，最后那个可能永远轮不到——所以我们规定这段必须写在 app.js 末尾，谁往中间插代码都要被拦下来重看一遍顺序。

分层带来的最大收益不是整洁，是排查成本：出问题时先定位”哪一层没到位”，再看那一层里的注册顺序，两步就能把范围圈死。

小结

回到开头那次事故。靠得住的修法是给鉴权中间件自己加命中判断，不匹配的路径直接放行：

我们没有采用”把那个路由注册到鉴权之前”那种改法。它能生效，但它把安全约束写成了数组下标：以后每加一个公开接口，都要靠”记得写在前面”这条口头规矩兜着，而线上那个绕过鉴权的洞，正是这么来的。把判断写进中间件内部，规则就变成了代码里能被读、被 review、被单测的东西。

回头看这一路讲的：next 是交棒不是返回、不出口就挂住、四参数才被认作错误处理器、挂载路径是前缀而且会剥掉 req.url、req.body 和 req.cookies 都是别人的产物、内置中间件拆包之后顺序要自己管。这些事没有一条是”Express 的功能”，它们全是同一个模型的不同侧面。Express 不提供架构，它只提供一个按注册顺序执行的函数队列；架构是你自己在这个队列上排出来的。 排得好，app.js 那三十行就是文档；排不好，它就是一串谁也不敢动的顺序。
