前端代码评审 checklist

那张评审清单发下去两周以后，评审又变回了原来的样子：打开页面看两分钟，点个通过。有次线上出问题，复盘翻记录，同一个改动合并之前有四个人打开过页面，说法都差不多——扫了一眼，没看出毛病。没人觉得自己该被追责，因为流程里没有一步要求谁做一件具体的、可交接的事。清单解决的是”看什么”，这个问题上一篇已经写完了，八个组加上分级定义，这篇一条都不复述。这篇要处理的是另一件事：评审这个动作怎么在团队里跑起来，怎么不塌回成形式。问题不在不知道看什么，在于流程没有把人钉在各自的位置上，谁都不知道自己这一轮具体欠什么。

评审是一种要付利息的开销

先把两笔成本摊开，不承认它们，后面的设计都会跑偏。第一笔是评审者的小时数。一个前端一天的有效编码时间本来就碎，被拉去看两份大变更，损耗远大于表面上那二十分钟。第二笔是作者的等待时间，这笔更容易被低估：分支多活一天，冲突概率、上下文重建成本和合并时的心理负担都在涨。等待是要付利息的，拖着拖着本金就被吃掉。

所以流程设计的目标不是评审得越严越好，而是用最少的人时拦住最贵的错误。它决定后面每一个取舍：为什么要机器先过一遍、为什么变更要拆小、为什么响应时间要有约定，全是在还利息。凡是让评审变贵却不增加拦截率的规矩，都是坏规矩。

提审之前，作者自己先做三件事

这三件事有严格的先后顺序，不是三件并列的好脾气建议。第一件，本地把 lint 和测试跑一遍，风格类和明显错误让工具先报掉，确认过了再提。第二件，把变更说明写成人能读的两三句话：这次改动是什么、动到了哪些地方、怎么验证的。第三件，把不该进这次提交的杂改动拆出去：顺手做的格式化、跟需求无关的空行和重命名。

重点在第一件为什么排最前。作者不自查，评审者就变成人肉 lint，注意力结构会被瞬间改写：风格问题最好找、最便宜、最能让人产生”我在认真看”的感觉，于是二十分钟全花在数空格上，逻辑问题原地保留。任何人掉进那份 diff 里都会这样，让机器先干掉机器的活，是替评审者保住注意力。第二件排第二，是因为评审者第一步就要拿说明和改动范围对照，说明含糊，他只能自己猜背景，猜就是损耗。第三件看着最轻，实际最要命：PR 里混进无关改动，评审者立刻开始区分”哪些才是这次要看的”，一分区，正确性的注意力就散了。

变更尺寸决定有没有人真读

我们自己的观察，不引任何调研数字：几十行到一百来行的变更，评审者是逐行读的；几百行往上基本没人真读，实际行为是拉到最后看最后一屏，再抽查中间两屏。这不是态度问题，是注意力上限。所以尺寸必须管，办法笨但有效：把一个需求拆成可独立合并的几步。比如一个表单页改造，拆成先动数据结构、再动渲染、最后动交互校验，每一步合进去都能单独跑，出事能立刻定位到哪一步。

另一条纪律是纯机械改动单开一次提交：重命名、格式化、批量替换路径，这类没有逻辑变化的东西永远不跟功能改动混在同一个 PR 里。但要说清楚，机械改动也过评审，不是免检——只是评审者的任务不同，他只需确认”这批确实全是机械改动”，抽查几个文件、看 diff 形态均匀就算完。这个确认很快，前提是你把它单开；混在功能改动里，谁也确认不了。

评审者读一个 PR 的动作顺序

上一篇末尾顺带提过流程，这一节把它当主题展开。拿到一个 PR，我建议的顺序是三步。第一步，只看变更说明和文件列表，判断两者是否一致：说明写的是改造列表页，文件列表里却多出不相干模块的改动，先停下来问，别急着读代码。经验上，”顺手改的”往往是问题源——它不在作者的验证计划里，也不在评审者的预期里，两处都不罩着它。第二步，看结构：新增了什么文件、动了哪个公共层、改动落在哪几块，在脑子里搭出形状。第三步才是逐行读。顺序颠倒的代价很具体：直接扎进第一行 diff，读三十行还不知道全局，只能回头重读，人时翻倍。

还有一个更硬的约定：第一遍只提会影响正确性和上线安全的问题，风格类的留到第二遍，或者干脆不提。第一遍的注意力是稀缺资源，拿它标空格属于高射炮打蚊子；而且第一遍就被一长串风格评论淹到的作者，下次会开始攒提交。顺序比速度重要。

评论怎么写才不吵架

评审的产出物就是评论，评论写坏了，前面所有设计都白搭。原则一句话：评论要指向位置和后果，不指向人。”这里在接口返回空数据的情况下会直接抛错，我倾向改成先取一层再判空”——这句话里没有”你”，也没有”不对”，只有位置、条件、后果和一个带倾向的方案。对比”这不对”：作者除了反问或不服没有别的动作可选，讨论滑向立场之争，人时继续烧，什么也拦不住。

级别必须写在句子开头——必须改还是顺手建议，定义在上一篇文章里，这里不重述，只说怎么表达，因为作者要据此判断这件事阻不阻塞合并。没有标记的时候，作者只能按最严重的理解来，于是一周只敢出两个 PR，尺寸约束立刻被摧毁。有了标记，流程还要允许欠账：作者可以公开回复”这条我下个迭代处理”，但必须写在评论区而不是口头说，三个月后翻记录能找到人找得到理由，这叫留痕。欠账不可怕，无痕的欠账才可怕。

响应时间约定的理由要讲透

我们当时定得很朴素：工作时间里提出的 PR，半个工作日内要有第一轮人看；超过一天没动静算异常，评审者说明原因，是出差还是赶发布，说出来大家就能补位。为什么是半天？因为前面拆小变更的全部收益，都建立在”拆了能快合”上。分支活得短的前提是评审响应快，否则你花力气把一个五百行的 PR 拆成五个小 PR，每个等两天，总等待反而变长了，作者很快会得出”还不如攒一次提”的结论——尺寸约束被等待时间反向击穿。响应时间和变更尺寸是一组互相咬合的约束，只定一头，另一头一定退化。跨天无响应要说明原因，也是同一个道理：异常暴露出来，流程才有东西可修。

机器卡点的顺序比内容重要

卡点本身不稀奇，稀奇的是顺序。当时的排法是：服务端的 git hook 先拦住直接 push 主干，改动一律走 Pull Request 或 Merge Request；然后是 CI 跑 lint 和测试，环境用 Node 4 这条 LTS 线，构建任务就是仓库里那套 Gulp 的活；CI 不绿，合并按钮按了也不生效；最后才是人做的评审，绿了加上评审通过才许合。

谁来评审：owner 制和轮值制各管一件事

两种做法的差别用文字说清楚。模块 owner 制的好处是背景知识在场：谁改到结算那块的公共逻辑，owner 一眼知道会影响哪几个页面，他回答的问题是”这个能不能上”。坏处是 owner 会越看越快，三个月后他看自己模块的评审基本等于签收。轮值制的好处正好相反：轮到的人没有背景知识，他读不懂的那一段，恰恰是文档和命名真正的欠账，他回答的问题是”别人看不看得懂”。坏处是每个人都在看自己陌生的代码，单位人时里拦住的深水问题少。我们的结论是两条都要：owner 必须到场，另外至少配一个非相关的人做一轮粗看。新人评审老代码不要嫌浪费，这是当时能找到的最自然的知识传递渠道——新人带着”为什么这里要这样写”的问题进场，老人被迫把当年的理由说一遍。

还有一条被事故教育出来的原则：同一个人连续通过两次本该拦住的事故，改的是流程，不是人。要么说明清单没覆盖那种错误，要么说明那个环节被卡点顺序挤掉了时间。认定”这个人不行”把他换掉，新来的照样放行同一个错误，因为坑本来就在流程里。

度量只看两三个数，多的必然变形

评审这种事一旦被度量，数字很快会长成奇怪的东西，所以只看两三个。第一是评审平均间隔时间：从 PR 提出到第一轮人来看的时间，它直接反映响应约定有没有兑现，涨了就是流程在憋。第二是每个 PR 平均提出的问题数：持续走低说明评审在形式化，突然走高说明尺寸约束松了或者混进了大 PR。第三也是最值钱的：把当月每一次线上回滚摊开，逐条问一句”这次评审本来能不能拦住”，算一个占比，它回答的是整个流程值不值。

一条红线：别用”提出条数”考核人。旁边有团队做过，两周内就长出刷条数——一个人对着一个 PR 写十几条纯风格评论凑数，评审者变便宜，作者变慢，两头都亏。月度复盘的写法也有讲究：把当月两次回滚摆出来，逐条问评审时为什么没拦住。答案如果是”不知道要看”，就补进那张清单；如果是”知道要看但没时间查”，那是流程的问题，改排期、改卡点或者改尺寸，补清单没用。分清这两类答案，是复盘唯一的干货。

一个季度落地，和一次彻底的失败

最后讲节奏，这里踩过最大的坑。第一版是错的：把全套规矩一次性推了下去，尺寸上限、响应时间、轮值、卡点、度量一周内全上。结果所有人开始攒着几个需求一起提，攒到五百行往上——反正每份都要等足一轮，不如少等几轮。评审质量断崖式下跌，尺寸约束第一天就死了。全套规矩同时落地，等于给每个人制造同一笔利息，而利息是会被绕过去的。

第二版按季度推。第一个月只推两件事：作者提审前三件事，和 CI 不绿不许合。这两条不动任何人的时间表，只把机器该干的活挪给机器，阻力最小，第一个月就当还旧账了。第二个月才引入尺寸约束和半天响应约定，这时候大家已经适应了走 PR，拆小变动的收益立刻看得见——拆了真能当天合。第三个月谈轮值和复盘，人时预算前两个月已经省出来了，这时候谈”多一个人粗看”才不显得贪。每加一条卡点，都开一次短会问它挤掉了什么：挤掉的是机器能干的时间还是人思考的时间，是前者就好，是后者就把这条改轻。

流程不是把评审变得多严，是让每个环节只做自己那一份事，且这份事能被追查。清单管看什么，这篇管怎么跑。缺了后者，复盘会上大家讨论的还是函数名取得准不准——那两行真正会炸的代码，依旧没人看。
