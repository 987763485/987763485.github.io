堆与优先队列的实现

本文属于《算法与数据结构》第 11/13 篇
上一篇系列目录下一篇

去年夏天我接手了一个内部的任务调度器。它的数据结构朴素得不能再朴素：一个数组存任务，每条任务带 priority 字段，调度循环每轮遍历整个数组，挑出 priority 最小的那条执行，执行完从数组里删掉。几十条任务时一轮扫描连一毫秒都不到，谁也不会去想它。

问题出在业务扩张。调度器后来接了四个租户，每个租户又按项目拆了队列，待办任务从几十条涨到八千多条。单核占用本来稳定在 5% 左右，涨到 30% 以上，而且随队列变长还在爬。我在挑选函数前后打了时间戳，八千条任务时单次挑选要 0.6 毫秒，而调度循环每秒跑三百多轮。

真正合适的结构是堆：插入和取出都是 O(log n)，而且不要求整体有序，只要保证”当前最小的那个永远在堆顶”。这篇文章把这次替换完整写一遍，包括我当时写错的几个地方。

事故：每轮扫全表找最小

第一反应是”排好序不就行了”。我加了一个缓存：数组变动时排一次序，之后每轮直接取第一个。想法没错，但任务插入远比我想的频繁：回调、重试、定时补投，每秒都有几十条新任务进来，每次插入都要把整个数组重排一遍。Array.prototype.sort 在 V8 里处理八千个元素要几毫秒，比原来还慢，等于把 O(n) 的扫描换成了 O(n log n) 的排序，只是把开销挪到了另一个地方。

第二个念头是插入时保持有序，取出 O(1)，但每次插入平均要挪四千个元素，最坏还是 O(n)。插入和取出只要有一边是线性的，整体就没救。

堆把两边都压到 O(log n)。它的思路不是让整个数组有序，而是只维护一个弱得多的性质：父节点不大于子节点。于是插入时只需要沿着一条从叶到根的路径往上比较，删除堆顶时只需要沿着一条从根到叶的路径往下比较，两条路径的长度都是树高，也就是 log₂n。八千条任务，树高约 13 层，最多比较十几次。

改完之后的效果：单次挑选从 0.6 毫秒降到 0.01 毫秒以内，单核占用回落到 6% 上下，代码还短了一些。

堆的定义与数组表示

堆是一棵完全二叉树，并且满足堆序：每个节点的值都不大于它的两个孩子，这叫最小堆；反过来，每个节点都不小于孩子，叫最大堆。完全二叉树的意思是，除了最后一层，每一层都被填满，最后一层的节点全部靠左排列。这个约束看起来只是为了整齐，实际上它决定了堆能用数组存。

因为完全二叉树没有空洞，节点的位置是确定的。假设数组是 [10, 20, 30, 25, 40, 50, 60]：下标 0 是 10，左孩子在 1（值 20），右孩子在 2（值 30）；下标 1 的左孩子在 3（值 25）。父子关系不用存，靠下标算：

  • 下标 i 的左孩子是 2i + 1，右孩子是 2i + 2；
  • 下标 i 的父节点是 floor((i − 1) / 2)，代码里直接写 (i - 1) >> 1。

最后一条有个坑：i 为 0 时，(0 - 1) >> 1 在 JS 里得到的是 −1，不是 0。所以任何要访问父节点的循环都得先判断 i > 0，不能只依赖算出来的下标，否则 heap[-1] 会是 undefined，和数字一比就悄悄出错。

为什么不用指针式的节点对象？我试过一版 { value: 10, left: null, right: null }，功能一样，但八千条任务时慢了将近一倍。原因在内存不在算法：每个节点都是独立对象，遍历要在堆内存里跳来跳去，缓存命中率低，GC 也要多扫几千个对象。数组是连续内存，父子相邻，末尾天然就是最后一个叶子，插入和删除都在末尾发生。

还有一点容易被误解：堆只保证父子之间的大小关系，兄弟之间没有任何约束，左孩子比右孩子大完全合法。所以堆不是有序数组，直接遍历得到的序列没有意义，想按顺序取完只能一次次弹出堆顶。这一点在 Top K 那里还会用到。

两个核心操作：siftUp 与 siftDown

堆的所有行为都建立在两个函数上：一个把元素往上挪，一个把元素往下挪。有的书叫 swim 和 sink，指的是同一件事。

siftUp 用在插入。新元素先放到数组末尾，此时它可能比父节点小，破坏堆序，于是和父节点交换，一直换到父节点不比它大为止。siftDown 用在删除堆顶和建堆。元素被放到某个位置后，它可能比孩子大，于是和较小的那个孩子交换，一直换到两个孩子都不比它小为止。

两段代码都不长，但我建议一开始就写成”暂存 + 单向移动”的形式，而不是每次真的交换两个元素。交换要做三次赋值，暂存只做一次。

几个边界值得单独说。siftUp 的循环条件必须是 index > 0，因为根节点没有父节点，而 (0 - 1) >> 1 是 −1，访问 heap[-1] 不会报错，只会拿到 undefined，比较结果永远是 false，循环会继续往下跑。我第一次就写错了，直到某次插入最小值，堆顶莫名其妙变成 undefined。

siftDown 的循环条件写成 index < half，而不是 index < size。数组后半段全是叶子，叶子没有孩子，走进循环只会白算一次 left。用 half 直接排除掉叶子，少一层判断。right < size 也不能省：节点可能只有左孩子。

两个函数都返回调整后的最终下标，平时用不到，调试时能直接看出一次插入挪了几层。

建堆为什么能从中间往前做

如果手上已经有一个无序数组，最直接的做法是新建一个空堆，把元素一个个 push 进去。n 个元素，每次 siftUp 最多走 log n 层，总代价 O(n log n)。但还有一个更快的做法：原地把这个数组调整成堆。

为什么起点是 (n >> 1) - 1？因为下标大于等于 n / 2 的节点全是叶子，而叶子本身就是一个合法的堆，不需要调整。第一个可能需要调整的，是最后一个叶子的父节点。

为什么从后往前？这是算法成立的关键。siftDown 的前提是被调整节点的左右子树都已经是堆。从后往前时，叶子的父节点先调整，两个孩子都是叶子，天然是堆；再往前一个节点，子树刚调整过，也是堆，每一步的前提都满足。反过来从前往后不成立，根节点下沉时下面还是一团乱麻。

至于为什么是 O(n) 而不是 O(n log n)，不需要展开求和，看两层就够：一半的节点是叶子，一步都不用动；四分之一的节点最多下沉一层；八分之一的节点最多下沉两层。越往下节点越多，但每个节点要走的距离越短，两者抵消，总工作量是线性的。

我在十万个随机整数上测过：buildHeap 约 12 毫秒，逐个 push 约 60 毫秒。建堆只遍历一次，不产生中间对象，之后所有批量初始化的地方我都用这个版本。

空数组时 (0 >> 1) - 1 是 −1，循环一次都不进；单元素同样；两个元素时只调整下标 0，正好。

pop 有一个很容易写错的地方：末尾元素摘下来之后，如果堆已经空了，就不能再写 items[0] = last。我最初漏了这个判断，单元素堆弹一次之后 size 变成 1，堆里多出一个”幽灵元素”，之后每次 pop 都返回它，调度器开始重复执行同一条任务。

重复优先级不是错误。siftUp 里判断的是 heap[parent] <= item，相等时直接停下，所以插入一堆相同优先级的任务，结构依然合法，pop 也正常。但”先入队的先出”并不能保证，下一节会说。

优先队列封装：比较函数与稳定性

上面的 Heap 只认数字，真实任务是对象，比的是 priority。把比较逻辑抽出来，就成了优先队列：

_siftUp 和 _siftDown 就是把前面的两个函数搬进原型，把 heap[parent] <= item 这类比较换成 this.less(heap[parent], item)，其余完全一样。

比较函数的约定必须写清楚：负数表示第一个参数优先，正数表示第二个优先，0 是平手。这和 Array.prototype.sort 一致，团队里不用记第二套规则。要让优先级大的先出，写 function (a, b) { return b.priority - a.priority; } 即可。

稳定性是个真问题。二叉堆本身不稳定：相同优先级的两条任务在堆里的相对位置，会随着后续的插入、弹出不断变化，谁先浮到堆顶取决于中间经历了多少次调整。我在日志里见过后创建的补偿任务先于先创建的重试任务执行，业务方以为是丢了消息。要修就得显式记录入队序号，也就是上面 seq 的用法：优先级相同时比较序号，先入队的先出。

代价是每个元素多包一层对象。几千条任务下可以忽略，换来可预测的顺序很值；不在乎顺序就去掉 seq。

典型用途

调度器是最直接的一个：任务按优先级入堆，每轮弹一次，新任务随时推进来，取和插都是 O(log n)。改完之后，调度循环里再没有出现过与队列长度相关的耗时。

Top K 是另一个高频场景。求一亿条记录里最大的 100 条，不必全排序，维护一个大小为 100 的最小堆：比堆顶大就替换堆顶并下沉，比堆顶小直接丢掉。最后堆里就是最大的 100 条，只是无序。复杂度 O(n log K)，K 远小于 n 时接近线性。方向别搞反：求最大 K 个要用最小堆，我第一次写反，跑出来的是第 101 大到第 200 大。

合并 K 个有序链表也是同一个套路。每个链表当前的头节点入堆，弹出最小的接到结果尾部，再把它的下一个节点入堆，直到堆空。K 个链表、共 n 个节点，每次操作 O(log K)，外部排序的多路归并用的也是这个结构。

Dijkstra 用堆维护未确定节点中距离最小的那个，细节属于图论，这里只提一句。

几个把我坑住的 bug

选错孩子。 siftDown 必须和两个孩子里较小的那个交换。我一开始只和左孩子比，右孩子更小时，换上来的左孩子仍然比右孩子大，堆序就破了。症状很隐蔽：连续 pop 的序列大部分有序，偶尔冒出一个明显偏大的值。后来每次下沉后加断言检查父子关系，才定位到。

下标越界。 少写 right < size，节点只有左孩子时就会去读 heap[left + 1]，拿到 undefined。undefined >= item 是 false，于是循环继续，把 undefined 换到父节点位置上，堆里凭空多出一个空值。循环条件写成 index < size 也会让叶子进循环。

比较函数返回布尔值。 写成 return a.priority > b.priority，返回的 true / false 被当成 1 和 0，而 1 表示”第一个应该排后面”，于是所有元素都被认为不小于对方，堆退化成插入顺序。这个 bug 最阴，不报错，只是顺序不对。约定必须记牢：负数在前，正数在后，0 是平手。

最大堆当最小堆。 比较符写反，或者复制代码时忘了改方向。症状是调度器总先跑最低优先级的任务，而且看起来”很有规律”，很容易被当成业务逻辑问题排查半天。

测试用例与朴素实现的对照

测试不用框架，几个断言就够，但要覆盖三类：乱序插入后的弹出顺序、重复值，以及空堆与单元素。

最后一组断言专门盯幽灵元素：单元素弹出后长度必须回到 0。

再和朴素实现对照：同一批随机任务，扫描版每次 O(n)，堆版 O(log n)，一万条任务取一万次，前者约 1.8 秒，后者约 90 毫秒。但差距要到几千条才明显，一百条以内两者都在微秒级，堆的封装反而多一层调用开销。选结构看规模，不必为了一个 log n 提前上堆。

操作与复杂度速查

操作 复杂度 易错点
peek O(1) 空堆返回 undefined，调用前先判断
push O(log n) 先 push 再取 length − 1
pop O(log n) 空堆与单元素；末尾元素不能盖回空堆
buildHeap O(n) 起点是 (n >> 1) − 1，方向必须从后往前
全表扫描取最小 O(n) 队列上千条后成为瓶颈
