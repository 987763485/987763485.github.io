HTTP Basic 与 Digest 认证

上周，我们组维护的内部监控面板被安全同学叫停。他当着我们的面打开抓包文件，选中一个请求，复制 Authorization 头的后半段，在终端里跑了一条 base64 解码命令，管理员账号和密码就整整齐齐地躺在屏幕上。更尴尬的是，这个密码和几位同事的办公系统密码是同一个。我们一直觉得“浏览器都弹登录框了，应该是加密的吧”。这篇文章就从这次事故讲起：Basic 认证到底发生了什么，Digest 想解决什么、又没解决什么，以及 2016 年给一个内部系统加访问控制时，应该怎样选。

事故开场：弹了登录框不等于加密

监控面板部署在内网，前面是一台 Nginx，用 auth_basic 加了一个账号。浏览器第一次访问弹出原生登录框，输入之后一切正常，于是“有登录框”就成了我们心里的安全底线。安全同学的问题很直接：这个登录框是浏览器画的，不是你的页面画的；它只负责收集账号密码，不负责保护它们。

抓包结果很说明问题。同一个局域网里，用 ARP 欺骗或者在一台共享的跳板机上抓流量，都能看到完整的请求头。Basic 的凭据就是一段 base64，谁抓到谁就能解开。我们把面板改成 HTTPS，给每个人开独立账号，又把密码从代码仓库的部署脚本里挪走，才算补上第一层。至于要不要上 Digest，团队争论了一下午，最后还是放弃了，原因后面会写。

401 握手：一次完整的 Basic 往返

HTTP Basic 的流程短得惊人。客户端第一次请求不带任何凭据，服务端返回 401，并在 WWW-Authenticate 头里说明认证方式与 realm。浏览器看到这个头，弹出原生对话框；用户提交后，浏览器把用户名和密码用冒号拼起来，做 base64，塞进 Authorization 头重发。同一源、同一 realm 的后续请求会自动带上这个头。

base64 不是加密

YWRtaW46MTIzNDU2 看起来像密文，其实只是把 admin:123456 换了一种写法。Base64 是一种编码，用 64 个可打印字符表示二进制数据，目的是让数据能安全地穿过只支持文本的协议。它没有密钥，也不需要密钥，任何人都能还原：

编码解决的是“能不能传”，加密解决的是“给谁看”。把两者混为一谈，是 Basic 认证最常见的误解。RFC 7617 明确要求 Basic 认证必须配合 TLS 使用，否则用户名和密码在链路上等同于公开。注意是“必须”，不是“建议”。如果只能走 HTTP，就不应该使用 Basic，哪怕只是内网。内网里同样有抓包、有日志、有代理，也有被攻陷的机器。

realm 与凭据缓存：为什么“退出登录”这么难

WWW-Authenticate 里的 realm 不是随便起的装饰。浏览器把“源 + realm”当作一个保护空间，凭据按这个空间缓存。源相同（协议、主机、端口一致）、realm 相同，浏览器就会在后续请求里主动带上 Authorization，不再弹框；realm 换了，才会重新询问。所以同一个面板下不同路径共用一个 realm，登录一次就处处通行；两个应用即使同域，只要 realm 不同，用户就要输两遍密码。

更麻烦的是退出。HTTP 没有为 Basic 定义注销动作，浏览器也没有清除某个 realm 凭据的标准接口。页面里的“退出登录”能清掉自己发的 cookie，却清不掉浏览器缓存的 Basic 凭据。常见的土办法是让退出接口返回 401，并把 realm 换成一个新字符串，逼浏览器丢掉旧凭据，但各浏览器处理不一致，有的仍然复用。共享电脑上问题更大：会议室机器上一个人登录后关掉标签页就走了，凭据还在浏览器进程里，无痕窗口能缓解，但很多人不会记得开。我们后来的做法是限制访问网段，并把会话改成服务端可失效的 token。Basic 在这里不是“不够安全”，而是“无法表达退出”这个语义。

Basic 的适用边界

Basic 并非不能用，只是适用范围很窄。它适合内部工具、机器对机器的接口调用（CI 拉构建产物、webhook、健康检查），以及已经放在 VPN 或 IP 白名单后面的服务；用户数少、身份可信、不需要精细的登录体验。前提是 TLS、访问控制、独立账号和日志四件事都到位。

它不适合面向终端用户的主站。没有可靠的退出，没有登录页来承载验证码、二次验证和找回密码，浏览器原生弹框不可定制，共享账号也无法按人审计；移动端 WebView 对 401 弹框的处理还各不相同。另外，不要把凭据写进 URL，https://user:pass@host 会进入历史记录、代理日志，也可能通过 Referer 泄漏。

Digest 的动机与 response 计算

Basic 的死穴是每次请求都带着密码原文。Digest 换了个思路：密码不出门，双方各算一遍。服务端先给一个随机数 nonce，客户端用用户名、realm、密码算出 HA1，再用请求方法、URI 算出 HA2，最后把 HA1、nonce、请求计数 nc、客户端随机数 cnonce、qop、HA2 串起来做一次 MD5，得到 response。服务端手里有同样的材料，算出来一比就知道对不对。

Digest 的服务端校验：比 Basic 贵在哪

服务端不能只算一次 response 就完事，它还要管 nonce 的生命周期。常见做法是让 nonce 自包含：时间戳加一段用服务端密钥算出的 HMAC，Base64 后发给客户端；收到请求时拆开、验签、看时间戳是否超过有效期。这样不用存 nonce，多台机器共享同一个密钥即可。过期后返回 401，并带上 stale=true 和新 nonce，浏览器会自动用新 nonce 重算，不会再弹框；没有这个字段，用户会莫名其妙地被要求重新登录。

校验 response 时，服务端按用户名取出 HA1，不必保存明文密码；但 HA1 本身也成了等价于密码的凭据，泄漏后同样能被直接使用。

nc 的校验是另一块成本。服务端要按“用户名 + nonce”记录已经见过的最大序号，拒绝不大于它的请求，才能挡住重放。可浏览器会并发发请求，多个标签页也会各自计数，序号到达顺序未必递增；记录得太严会误杀正常请求，放得太松又挡不住攻击。实际实现往往要允许一个小窗口，或者按 cnonce 分别计数，再配一个带过期时间的 Redis 键。再加上负载均衡、时钟偏差、代理改写请求头，Digest 的代码路径比 Basic 多出一个数量级。

主流浏览器从 IE 到 Chrome 都支持 Digest，真正的问题不是能不能用，而是细节不一致。调试也不轻松。地址栏访问能弹框，XHR 的 401 却常被前端框架吞掉；curl --digest 能看到握手，但不一定复现浏览器的字段顺序，出问题只能逐项对公式。

Digest 的局限：它只解决了“密码不出门”

Digest 保护的是请求里的凭据，不是响应内容。页面数据、接口返回的 JSON 仍然明文躺在连接里，能被同样的抓包看到。所以 Digest 不能替代 TLS；一旦上了 TLS，Basic 的密码也不会在链路上暴露，Digest 的收益就只剩“服务端和中间代理看不到密码原文”这一点。这点收益抵不上 nonce、nc 与 HA1 存储的成本。

MD5 是第二个问题。MD5 的碰撞攻击在 2004 年就已公开，虽然碰撞不等于能直接伪造 Digest 的 response，但 MD5 计算太快，抓到一次挑战和响应后，攻击者可以拿字典离线穷举，弱密码很快失守。RFC 7616 加入了 SHA-256 和 SHA-512-256，可 2016 年浏览器对它们的支持面很窄，实际能互操作的仍然只有 MD5 加 qop=auth。你在服务端写 algorithm=SHA-256，不少客户端会直接放弃认证，或者退回 MD5，算法协商于是变成了兼容性赌博。

还有实现差异。qop 可以取 auth 或 auth-int，后者要算请求体哈希，浏览器支持很少；有的客户端不发 nc，有的 cnonce 格式不合规范，有的代理会把 WWW-Authenticate 头剥掉。RFC 7616 虽然定义了协商规则，落到具体浏览器和 HTTP 客户端上仍是一堆例外。我们当时评估的结论是：为一个内部面板引入 Digest，维护成本高于它挡住的风险。

重放、暴力破解与替代方案

抓包之后最直接的动作是重放。Basic 的 Authorization 头在密码修改前一直有效，攻击者不需要解密，原样再发一次就能通过。Digest 把窗口缩窄到 nonce 的有效期，但如果服务端不校验 nc，同一个头在窗口内仍然可以反复使用。TLS 挡得住链路中间人，挡不住已经拿到请求的终端、日志或代理。防重放最终要落在服务端的序号、一次性票据或短时效 token 上，而不是换一个认证头。

暴力破解分两种。在线猜测靠限流、失败计数和账户锁定来挡，配合 401 峰值的监控；离线字典则是抓到一个挑战和响应后，在本地用 GPU 跑哈希，服务端的限流完全帮不上忙。Basic 抓到的是 base64，连跑字典都省了；Digest 至少要多算一层，但 MD5 太快，密码若是 123456，区别只是几毫秒。密码强度、唯一性和定期轮换，在这里比认证方案本身更重要。

面向终端用户、需要登录页和可靠退出的系统，用服务端 session 或有时效的 token；session 能主动失效，token 适合 API 和移动端，但要设计过期与吊销。机器对机器的内部接口，Basic 配 TLS、IP 白名单和独立账号已经够用，代价最小。老系统里的 Digest 不必急着拆，但要接受它只支持 MD5 加 qop=auth 的现实，并把它放在 TLS 后面。无论选哪种，明文 HTTP 上的认证都只是把密码交给路过的人。

方案 传输安全 抗重放 实现复杂度 适用场景
Basic + TLS 依赖 TLS，base64 本身不提供保护 弱，凭据可反复使用 低，一个头加一次比较 内部工具、机器对机器、白名单后的服务
Digest（MD5 + qop=auth） 不传密码，但不保护响应体，仍需 TLS 中，nonce 加 nc，取决于服务端校验 高，nonce 生命周期与序号状态 有合规要求又不能改客户端的遗留系统
