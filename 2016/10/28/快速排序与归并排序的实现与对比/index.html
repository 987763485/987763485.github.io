快速排序与归并排序的实现与对比

本文属于《算法与数据结构》第 8/13 篇
上一篇系列目录下一篇

十月底，运营后台的订单列表出了一次不大不小的事故：十万条记录，点一下”按金额排序”，页面直接白屏十几秒，用户以为系统崩了。事后复盘，卡顿只是表象，真正的问题藏在两处——比较函数写错了，以及我们默认 Array.prototype.sort 是稳定的。这篇文章从那次事故出发，把快速排序和归并排序各写一遍，讲清楚分区怎么写、递归有多深、稳定到底意味着什么，最后给出一张按场景选型的表。适合已经会写循环和递归、但没认真实现过排序的读者。

事故：十万条记录把页面卡住了

那是一个典型的后台列表页，数据一次性从接口拉回来，前端自己做筛选和排序，图的是交互快。订单量从几万涨到十万以后，排序开始明显变慢，直到某天同事点了一下金额列，Chrome 转圈转了十几秒，标签页提示”页面无响应”。

我先用 Performance 面板录了一段，火焰图里耗时几乎都堆在 Array.prototype.sort 这一帧下面。但引擎的排序本身不会这么慢，慢的是它反复调用的那个比较函数。翻代码，问题有两个。

第一个是返回值写错了：

sort 要求比较函数返回负数、零、正数，分别表示”排在前面””相等””排在后面”。布尔值会被转成 1 和 0，所有”小于”都变成了”相等”，结果既不正确，又依赖引擎对相等的处理，换一个环境就是另一副样子。

第二个问题更隐蔽：比较函数里每次都在解析日期字符串。

十万条数据，比较次数在百万级，每次比较解析两个字符串，等于凭空造了几百万个 Date 对象。把时间戳预先算好存进字段，再比较数字，这一项就省掉了一大半时间。

真正让我警觉的是第三件事。业务方要”先按时间排，再按金额排，金额相同的保持时间顺序”，我们就先排时间再排金额，理所当然地认为第二次不会打乱第一次。上线后大部分时候看着对，偶尔有几条同金额订单时间颠倒，查了半天才承认：sort 在规范里并不要求稳定，把业务正确性押在”它应该稳定”上，本身就是 bug。

那次事故之后，我把快排和归并各手写了一遍。理由很实际：只有自己实现过，才知道哪些代价是必须付的，哪些是可以用别的方式绕开的。

快速排序的分区：Lomuto 与 Hoare

快速排序的骨架只有三步：选一个基准值，把数组分成”小于基准”和”不小于基准”两段，再对两段递归。真正容易写错的是中间那步——分区。

Lomuto 分区：好写好懂，交换偏多

最常见的教科书写法是 Lomuto 分区，用最后一个元素做基准，一个指针 i 维护”已确认小于基准”的边界，另一个指针 j 从左往右扫描：

这段代码的好处是只需单向扫描，边界条件简单，p 就是基准值的最终位置，不会出现在递归区间里。坏处有两个：一是交换次数偏多，每个小于基准的元素都可能被换一次，即使它本来就在正确的位置上；二是所有等于基准的元素都被留在右侧，下一轮递归还要再处理一遍。数据里重复键一多，这个缺点会被放大，后面讲三路快排时再展开。

Hoare 分区：交换更少，边界更绕

Hoare 的原始方案是双向扫描：左右两个指针向中间靠，左边找不小于基准的，右边找不大于基准的，交换，直到相遇。

Hoare 分区的交换次数明显更少，而且两个指针在遇到等于基准的元素时会停下来交换，等于基准的值被分散到两侧，重复键多的时候反而比 Lomuto 均衡。代价是边界极容易写错：返回值是 j 而不是基准下标，递归区间是 [lo, j] 和 [j + 1, hi]，写成 j - 1 会漏元素或者死循环；内层用 do...while 而不是 while，是因为要先移动再比较，否则指针可能不动。我第一版就栽在 j - 1 上，数组长度二十以内看不出来，上千条时结果里混着几个错位的值。

基准值怎么选

取端点最省事，但最怕有序输入；取随机位置能压低触发最坏情况的概率，代价是每次多一次随机调用；三数取中取首、中、尾的中位数，既避开有序陷阱，也不需要随机数，还能顺手缩小递归区间。

我在业务代码里最终用的是”中间元素 + 三数取中”的组合，理由不是理论最优，而是它对我手上那批数据的分布最不敏感。

最坏情况：有序、全相等与端点基准

快排的平均复杂度是 O(n log n)，但这句话有个前提：每次分区都能把数组切得比较均匀。只要基准值每次都落在端点附近，分区就会退化成”一次只确定一个元素的位置”，递归 n 层，比较次数接近 n²/2。

最典型的触发条件就是数据已经有序。想象十万条按时间排好的订单，基准取最后一个元素，那么每次分区，其余所有元素都小于基准，i 一路加到最后，只把基准换到了末尾——位置本来就在末尾。区间从十万变成九万九千九百九十九，下一轮重复同样的故事。十万条的平方是十的十次方，除以二也是五十亿次比较，浏览器不卡死才怪。逆序输入是同一个问题的镜像。

第二个陷阱是全部相等。用 Lomuto 分区时，判断条件是 arr[j] < pivot，等于基准的元素一律不进左段，于是左段为空，每次同样只削掉一个元素。这一点很反直觉：数据越”整齐”，Lomuto 越慢。Hoare 分区在这里好得多，因为两个指针遇到等于基准的值都会停下来交换，最终从中间切开。

针对这两种情况，工程上有三套应对手段，可以叠加使用。

第一是随机化基准。每次分区前随机选一个下标，和区间首元素交换，再拿首元素当基准。这样”输入恰好触发最坏情况”就变成了一个概率事件，而且这个概率与输入的顺序无关——即使有人故意构造数据，也算不准随机数。代价是每次分区一次随机调用，以及结果不可复现，调试时稍微麻烦一点。

第二是三数取中。取首、中、尾三个元素，比较后把中位数换到区间首部当基准。对于已经有序的输入，首、中、尾的中位数正好是整个区间的中位数，一次就切在正中间；逆序同理。它不需要随机数，行为可复现，只是对抗不了刻意构造的数据，不过在业务系统里几乎遇不到。

第三是遇到大量重复键时改用三路分区，这一条留到后面单独讲。这里只需记住结论：随机化和三数取中解决的是”划分位置偏”的问题，解决不了”键值大面积相等”的问题，后者必须靠三路。

递归深度与调用栈

手写快排之前，我一直觉得递归深度是个理论指标，直到用十万条有序数据测试，控制台抛出 RangeError: Maximum call stack size exceeded，我才意识到栈是有限资源。

ES5 没有尾调用优化。规范层面，真正的尾调用优化要到 ES2015 的严格模式才被写进去，而 2016 年主流浏览器的实现并不把它当作可以依赖的能力，业务代码更不能假设它存在。所以”递归调用写在函数最后一行”并不会自动折叠栈帧，每深入一层就实实在在压一个帧。十万层递归，每层哪怕只占几百字节，也是几十兆的栈空间，浏览器给不了。

解决办法不是把递归改成显式栈——那样代码会难读很多——而是调整递归的顺序：每次分区后，先递归处理较短的一半，较长的一半用循环继续处理。

这样栈深度就降下来了：每次真正压栈的调用，处理的区间不超过当前的一半；长区间被 while 循环消化，不占新栈帧。栈深度最多是 log₂n 量级，十万条也就十七八层。这个技巧常被称作”手动尾递归优化”，更准确的说法是”保证递归只发生在较小的一半上”：它不改变比较次数和时间复杂度，只把栈空间从最坏 O(n) 降到 O(log n)，对排序这种会被数据规模放大的场景是必须的。

顺带一提，递归到很小的区间时（比如长度小于十六），快排的分区开销和函数调用开销已经超过了收益，业界通常直接切插入排序。这个阈值怎么来的、为什么小数组插入排序更快，后面讲常数的时候一起说。

归并排序：从分治到合并

归并排序的思路比快排更”笨”也更可靠：把数组从中间劈成两半，各自排好，再把两个有序段合并成一个。它没有分区那种”切得匀不匀”的赌博，任何输入都是稳定的 O(n log n)，代价是需要一块额外的空间。

关键在合并。两段各有一个指针，每次比较指向的值，把小的放进结果并后移；某段走完后，把另一段剩下的整体接上。每个元素只被搬一次，所以合并是线性的。

第一，aux[i] <= aux[j] 的等号不能省。相等时优先取左段，而左段在原数组中本来就位于右段之前，这样相同键值的元素相对顺序不会变。如果写成 <，相等时取右段，稳定性立刻丢掉。这是归并排序最容易写错、也最难在测试里发现的一行。

第二，辅助数组只分配一次。教科书示例常写成 slice 出左右两半再 concat，代码短，但每一层递归都在造新数组，n log n 级别的临时对象会给垃圾回收造成很大压力。

第三，递归深度是 log₂n，比快排的最坏情况温和得多。十万条数据只有十七层，不需要”小的一半递归”那套技巧。归并的空间开销主要在那块长度为 n 的辅助数组上，而不是栈。

自顶向下与自底向上

上面是自顶向下的写法：先递归拆分，再合并回来。它直观，也方便做两种常见优化——区间长度小于阈值时改用插入排序，以及合并前先比较 arr[mid] 和 arr[mid + 1]，如果前者不大于后者，说明两段本来就有序，整段可以跳过。对于近乎有序的数据，这个判断能把大量合并省掉。

自底向上则完全不用递归：先把相邻的两个元素看成两段长度为一的有序段，两两合并；再把长度翻倍，继续合并，直到段长覆盖整个数组。

两种写法的时间复杂度和稳定性完全一样，差别在工程侧。自顶向下更贴近”分治”的直觉，优化点也更多；自底向上没有调用开销和栈深度顾虑，边界虽绕，但行为可预测。我在浏览器里用自顶向下，在栈受限的旧脚本引擎里用自底向上。

稳定性：字段排序背后的隐含假设

回到开头那次事故。业务方的需求翻译成技术语言是”按金额升序，金额相同的按时间升序”，我们的实现是”先按时间排一遍，再按金额排一遍”。这个做法成立的前提是第二次排序稳定：金额相同的元素，必须保持第一次排序留下的时间顺序。

稳定排序的定义就是这样：键值相等的元素，排序后的相对次序与排序前一致。它不是什么附加特性，而是”多关键字排序”这套组合拳能否成立的基础。没有稳定性，想按两个字段排序，就只能写一个同时比较两个字段的比较函数：

这当然也行，而且往往更直接。但现实里的排序经常是分步来的：用户先点了金额列，又点了时间列，或者筛选条件变化后只对子集重排。每一次点击都是一次独立的排序，如果底层不稳定，前一次的用户意图就会被无声地抹掉。

那么为什么快排默认不稳定？因为它的交换是长距离的。分区时，一个远处的元素可能被直接换到前面，跨过了若干与它相等的元素；这些相等元素之间的相对顺序就此改变，而且改变的方式取决于数据分布，无法预测。你没法通过”小心一点”让快排稳定，除非把元素扩展成”值 + 原始下标”再比较，而那本质上已经是在模拟稳定排序了。

归并能稳定，是因为它从不做长距离交换。合并两个有序段时，元素是按顺序被”挑选”进结果数组的，相等时取左边那一段，而左段在原数组中整体位于右段之前。只要递归的拆分不改变元素归属，这个性质就一路保持到底。换句话说，归并的稳定性来自”合并时的取舍规则”，不是运气。

还要区分”稳定”与”正确”：如果比较函数本身不自洽——同一对元素一会儿返回正数一会儿返回负数——再稳定的算法也救不了结果。稳定性只保证相等元素不乱序，管不了谁和谁相等。另外，稳定性只在一次排序过程中有意义：数据在两次排序之间被过滤、拼接或重新拉取，原始顺序已经变了，再谈稳定就是空话。那次事故里有一半错乱其实是分页拼接造成的。

复杂度之外的常数：比较次数、空间与缓存

两个算法都是 O(n log n)，但”同阶”不等于”同速”。真到了十万条这个量级，常数项和内存访问模式的影响，往往比复杂度本身更能决定体感。

先看比较次数。归并每层最多比较 n 次，一共 log₂n 层，总量在 n log₂n 附近，且与输入顺序无关。快排的平均比较次数约为 n log₂n 的 1.4 倍，因为基准值要和区间内几乎每个元素比一次。所以在”比较”这项开销上归并更省，前提是比较本身便宜。

空间差距更明显。快排原地排序，除栈帧外不申请数组，栈深度 O(log n)；归并要一块长度为 n 的辅助数组。十万条引用就是八十万字节，不算大，但带来持续的写入和更高的缓存压力。

缓存局部性是快排的主场。分区是线性扫描，地址连续，CPU 预取能发挥作用，交换也发生在同一块内存里。归并的合并阶段有三个指针在动：读左段、读右段、写结果，位置彼此相距很远，每写一个元素都可能触发一次缓存行装载。数据量超过缓存容量后，这个差距会明显放大。

小数组为什么用插入排序更快？它虽然是比较次数 n² 级别的算法，但常数极小：没有递归，没有辅助数组，内层就是一次比较加一次移位，短数组的逆序对本来就少。n 小于十几时，n² 和 n log n 的差距被常数项淹没，快排”选基准、分区、递归”的开销反而成了负担；归并同样如此。

所以工程上的排序实现几乎都是混合体：大区间用快排或归并，小区间切插入排序。这个阈值不是神圣数字，八到十六之间都有人用，取决于比较函数的成本和机器的缓存行大小。我用十二，纯粹是因为当年在一台老笔记本上试出来的手感，没有任何普适性。

三路快排：重复键太多时

前面提过，Lomuto 分区在全部元素相等时会退化成 O(n²)。这不是极端个例：订单状态、用户等级、评分只有几档，这类低基数字段在业务数据里到处都是。十万条订单按状态排序，可能九万条集中在三个值上，二路分区会把它们反复切来切去。

三路快排的思路是把区间切成三段：小于基准、等于基准、大于基准。等于基准的那一段直接确定位置，不再参与递归。

三路分区的收益很直接：所有元素相等时，一次分区就处理完，复杂度降到 O(n)；只有 k 种取值时，约为 O(n log k)。代价是分支更多，没有重复键时比二路略慢，实现也更绕。

我的选择标准很简单：如果排序键的取值种类明显少于元素个数（状态、枚举、评分、日期），就用三路；如果是金额、时间戳这种几乎唯一的键，就用二路加三数取中。判断依据是数据的基数，不是数据量。

近乎有序的数据：三种算法的方向性

后台系统里有一类数据天然近乎有序：按时间追加的日志、只改了几行的配置表、增量同步过来的列表。这类输入最能拉开三种算法的差距。

插入排序的表现直接由逆序对数量决定。完全升序时，每个元素只和前一个比较一次就停下，总共 n - 1 次比较、零次移动；只有少数元素错位时，移动次数与逆序对总数成正比，可以低到线性。但它的方向性很强：完全逆序是最坏情况，每个元素都要一路挪到最前面，比较和移动都是 n²/2 量级。

归并排序对方向不敏感，任何输入都是 n log n。不过加了”两段已有序就跳过合并”的判断之后，近乎有序的数据会让大部分合并被直接跳过，实际工作量大幅下降，接近线性。这个优化在自顶向下的写法里很自然，代价只是一次比较。

快排的方向性取决于基准值怎么选。取端点时，升序和降序都是最坏情况；三数取中能同时化解这两种完全有序的输入，但如果数据”整体有序、中间插了几个极大值”，仍可能选到偏斜的基准。随机化则把方向性彻底打散，代价是结果不可复现。

所以结论可以这样记：数据几乎有序、且乱序很少时，插入排序最快；不确定有序程度、又需要稳定时，归并加有序跳过最稳；数据规模大、分布未知、只要求平均表现时，快排加三数取中或随机化。三者不是替代关系，很多排序库就是把它们拼在一起用的。

实测方法：在同一台机器上比较

网上关于”哪种排序更快”的结论经常互相矛盾，很大一部分原因是测量方法不同。要让比较有意义，至少要做到下面几件事。

第一，固定变量。同一台机器、同一个浏览器版本、同一份数据、同一个比较函数，一次只改排序算法这一个因素。跨机器比较绝对毫秒数没有意义，只能比相对关系。

第二，计时只包住排序本身。数据拷贝、结果校验、日志输出都放在计时区间外面，否则测到的是”拷贝加排序”。

第三，先预热再计时。第一次执行时脚本还在解释执行，随后才被优化，前几轮的数字明显偏大，通常丢弃。

第四，多轮取中位数。垃圾回收的停顿会让个别轮次异常长，平均值会被这些尖峰拉高，中位数更能代表常态。

performance.now() 的精度比 Date.now() 高。轮数取奇数，比如九轮或十一轮，方便取正中间那个值。汇报时要把数据规模、分布、比较函数、轮数一起写出来——只给一个”快了三倍”的结论，别人无法复现。

还有一点容易被忽略：测试数据要覆盖多种分布。随机、完全升序、完全逆序、大量重复、近乎有序，这五种跑下来，才能看出算法的短板。只测随机数据，等于只考了快排最擅长的科目。

与原生 sort 的关系

事故查到最后，绕不开一个问题：既然浏览器自带 sort，为什么还会出这种事？答案是，原生 sort 只承诺”把数组排好序”，没有承诺”相等元素保持原序”。

翻规范可以看到，sort 的约定只有两条：调用比较函数决定次序，返回同一个数组。至于相等元素怎么排，规范留给了实现。2016 年我们用的 Chrome 里，V8 的 sort 同样不保证稳定；换一个浏览器、换一个版本，同一份数据里相等元素的顺序就可能不同。开发机上看着正常，用户那里错乱，根因就在这里。

不同引擎的实现策略也不一样，同一份数据在相等元素上的顺序可能完全不同，但都”合法”，因为规范没有约束。能依赖的只有比较函数的契约：返回负数、零或正数，且关系自洽——自己和自己比为 0，a 比 b 为负则 b 比 a 为正，传递性成立。返回布尔值、NaN，或在比较函数里修改数组，结果就变成实现定义。

如果确实需要稳定，有两个办法。一是自己写归并；二是在原生 sort 外面包一层”装饰—排序—去装饰”，把原始下标作为第二关键字：

代价是多一次遍历、一批临时对象，以及比较时多一层属性访问。数据量在几千条以内，这点开销可以忽略；上万条时，自己写归并反而更划算。

写完这两个算法，我对事故的结论也变了：卡顿源于比较函数里解析日期，错乱源于对稳定性的错误假设，但更深一层，是我们把排序当成了不需要理解的黑盒。黑盒可以用，前提是知道它承诺什么、没承诺什么。规范没写的东西，不能拿业务正确性去赌。
