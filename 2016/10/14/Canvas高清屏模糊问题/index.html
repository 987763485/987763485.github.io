Canvas 高清屏模糊问题

事故：一条分隔线在两个屏幕上长得不一样

上周给运营后台的素材列表换了一版样式。设计稿要求每行之间有一条 1px 的浅灰分隔线，左侧缩进 16px。行高跟着缩略图走，行内还有一条进度条，用 DOM 拼边框别扭，索性整块交给 canvas 绘制。

在公司的老 ThinkPad 上看，线条是干净的 1px。回到自己的 MacBook Pro 上一看，每条线都胖了一圈，颜色从 #e5e5e5 散成一片更浅的灰，整整 2px 宽，边缘像蒙了雾。设计走查的第一条意见就是：”分隔线太重，压过正文了。”

第一反应是线宽写大了，于是改成 0.5：

刷新之后更糟。线确实细了，却变成两条并排的浅灰，像拿 20% 透明度的笔刷了两下，比 2px 实线还脏。到这一步才明白，问题不在”线有多粗”，而在”线落在哪里”。

两套坐标系：CSS 像素与设备像素

要解释这件事，得先把两个长度单位分开。

CSS 像素是布局和脚本里的逻辑单位。getBoundingClientRect() 的返回值、lineWidth = 1 里的那个 1、CSS 里写的 width: 600px，用的都是它。设备像素是屏幕真正能点亮的物理点，Retina 屏上 1 个 CSS 像素覆盖 2 × 2 个设备像素。两者的比值就是设备像素比：

2016 年的 Chrome、Firefox、Safari 都已经提供这个属性，IE 从 10 起也有。dpr 不一定是整数：Windows 上 125% 缩放给出 1.25，150% 给出 1.5，安卓机里 2.75、3.5 也不罕见。写死 dpr === 2 的判断迟早会翻车。

canvas 身上挂着两套尺寸，必须分开看：

  • HTML 属性 width / height 决定 backing store（后台绘图缓冲）的大小，单位是设备像素，所有绘制指令最终都落在这块位图上。
  • CSS 的 width / height，或者由布局算出来的盒子尺寸，决定它在页面上占多大，单位是 CSS 像素。

浏览器把 backing store 贴到 CSS 盒子上时，两边尺寸对不上就做一次缩放。属性默认值是 300 × 150，只写 style="width: 600px"，等于让浏览器把 300 宽的位图拉到 600 宽，必然糊。反过来，把 backing store 按 dpr 放大、CSS 尺寸保持不变，才是高清屏的正确姿势。这套按 dpr 设尺寸的模板，《Canvas 动画与粒子效果》在讲 resize 时已经写过，这里不再重复，本篇只关心”尺寸对了之后，为什么线还是糊”。

半像素偏移：1px 线为什么要落在 x + 0.5

stroke() 不是”沿着路径铺一条线”，而是以路径为中心，向两侧各扩 lineWidth / 2，再对覆盖到的像素做抗锯齿。这条规则决定了线的视觉宽度和清晰度。

假设 dpr = 1，在 y = 100 处画一条 lineWidth = 1 的水平线。它的实际覆盖范围是 99.5 到 100.5，横跨第 99 行和第 100 行，每行各被覆盖一半。浏览器按覆盖率给透明度，两行各以 50% 的 alpha 画上 #e5e5e5，肉眼看就是一条 2px 宽、颜色变浅的灰带。把 lineWidth 改成 0.5 更糟——线只覆盖 99.75 到 100.25，仍然横跨两行，只是每行的覆盖率降到 25%，颜色更淡、边缘更散，于是出现了”两条并排浅灰”的效果。

正确的做法是让线的两条边正好压在像素边界上。把中心移到 y = 100.5，覆盖范围变成 100 到 101，正好一整行，颜色就是 #e5e5e5 本身，一条锐利的 1px 线。这就是那句流传很广的”1px 线要画在 x + 0.5”的来历。

水平线和垂直线的处理完全对称，只是偏移的轴不同：水平线调 y，垂直线调 x。矩形边框要四条边都对齐，得整体内缩半个线宽：

斜线没有完美对齐这回事。任意角度的边缘不可能同时压在水平与垂直的像素网格上，抗锯齿是必需代价，别为了锐利把它改成阶梯。

规则可以总结成一句：中心坐标加上半个线宽，必须落在像素边界上。dpr = 1 时，lineWidth 是奇数就把中心放在 x.5，是偶数就放在整数 x；lineWidth = 2 的线中心在整数上，覆盖 99 到 101，正好两整行，同样锐利。只记住”1px 要加 0.5”是不够的，换到 3px 边框又会写错。

到了 dpr = 2，情况多了一层。如果按上一节的做法 ctx.scale(dpr, dpr) 之后再画，所有坐标和线宽都以 CSS 像素计，1 个 CSS 像素等于 2 个设备像素，此时 lineWidth = 1 必然是 2 设备像素宽，再怎么偏移也细不下去，只能接受”看起来是 2px”或者改用 0.5：

这里偏移的是 hair / 2 而不是固定的 0.5。原因还是那条通式：边缘要落在 1 / dpr 的整数倍上，中心就得再退半个线宽。反过来，不 scale、直接在设备像素坐标里画，lineWidth = 1 加 0.5 偏移的老规则原样成立，这也是不少老项目的选择——坐标系只有一套，心算简单。

还有个更省事的办法：细线根本不用 stroke，用 fillRect。填充矩形没有中心扩散，给定左上角和宽高，边界就是边界：

文字模糊：font、textBaseline 与小数坐标

线条调好之后，同一个画布上的文字还是发虚，这几乎是必然的，因为文字比线条多踩几个坑。

第一个坑是 font 的写法。它和 CSS 的 font 简写同源，必须带上字号和字体族，缺一不可：

只写 ctx.font = '14px' 不会报错，但整条赋值被忽略，画布继续用上一次的字体，通常是默认的 10px sans-serif。”我明明设了 14px，字却小得可怜”，而且 10px 的中文字形本身就挤，笔画糊成一团。

第二个坑是 textBaseline。默认值是 alphabetic，y 指的是西文字母的基线，中文字形的底部还要往下压一点，于是”垂直居中”的直觉完全不准。改成 middle 能凑个大概，但各浏览器对它的解释有细微差别，中英文混排时尤其明显，垂直位置按字号乘个经验系数更稳。

第三个坑是小数坐标。fillText('总览', 10.3, 20.7) 会让字形落在半个像素上，浏览器只能做亚像素定位加抗锯齿，笔画边缘立刻糊成一片。把坐标取整就能明显改善：

如果已经 scale(dpr, dpr)，取整到 CSS 像素仍然是设备像素的整数倍，够用；要求更细的话，取整到 1 / dpr 的倍数。

那为什么按 dpr 放大了 backing store，文字还是不如 DOM 里的文字锐利？原因有三层。一是字形栅格化本身有 hinting，同一字号在不同 dpr 下的笔画对齐策略不同，canvas 拿不到 DOM 那套次像素抗锯齿；二是 font-weight 写了 600、300 这类字体文件里并不存在的字重，浏览器只能合成加粗或变细，边缘自然发毛；三是某次 resize 重置了上下文状态，字体悄悄退回默认值，字号变小再被 CSS 放大，糊得毫无道理。-webkit-font-smoothing 只作用于 DOM 文本，对 canvas 无效，别把它当解药。

还有物理限制：中文字号小于 12px 时，横竖笔画只有一两个设备像素，怎么调都糊，只能放大字号或换更粗的字重。

drawImage：整数倍才是舒服的缩放

列表里的缩略图也出过问题。运营上传的图动辄 4000px 宽，按 64 × 64 画进格子，全都像隔着毛玻璃。原因是 62.5 倍的非整数缩小，浏览器只做有限次采样，大量原始像素被跳过，细密的纹理先变成噪点，再被抹平。

放大则相反，整数倍最清楚。24 的图标画到 48 是干净的 2 倍，画到 36 就开始发虚，因为每个源像素要摊成 1.5 个，插值出来的中间值肉眼可见。能用矢量重画就别放大位图，实在要放大，宁可放大到 2 倍再交给 CSS 缩回去。

另外，drawImage 读的是自然尺寸，与 CSS 显示尺寸无关：标签写了 width="64"，img.width 是 64，naturalWidth 仍是 4000，拿错值当源矩形，结果差得很远。

CSS 二次拉伸：属性尺寸和显示尺寸对不上

有一类模糊跟绘制代码完全无关，纯粹是 CSS 造成的。

现象是：本地怎么调都清晰，一放进窄屏卡片就整体发虚，连 1px 线都变成两像素灰边。量一下，canvas.width 是 600，offsetWidth 却是 480——width: 100% 把它压扁了。backing store 还是 600 宽，浏览器只能非整数比例重采样，全图一起糊。

max-width: 100%、flex 里的 flex: 1、外层容器的 transform: scale(0.9) 都会造成同样的结果：CSS 盒子尺寸和”属性尺寸 ÷ dpr”不相等，浏览器默默补了一次缩放。

为真就说明画布被二次拉伸了。处理办法只有一条：让 backing store 跟着盒子走，盒子变了就把 width、height 按新的 clientWidth * dpr 重设。注意重设属性会清空画布并重置上下文状态，按 dpr 重建的那套流程在前一篇里写过，这里不再展开。不想每次都重画，也可以反过来约束 CSS：给画布固定宽高，容器用 overflow: auto 兜住。

最隐蔽的是子像素尺寸：width: 33.33% 算出 480.33，backing store 取整成 960，显示却是 960.66 个设备像素，多出的 0.66 就是那层洗不掉的雾。要么让容器宽度落在整数上，要么别在两处分别取整，误差会叠加。

缩放与屏幕切换：画布什么时候该重建

浏览器缩放和换屏是两件事，结果却一样：画布没重建，位图被系统放大。

按 Ctrl 加号缩放时，Chrome 会把 devicePixelRatio 一起改掉，125% 下 2 会变成 2.5，可 canvas 的 width 属性不会自己跟着变，位图被拉伸，刚调好的 1px 线又灰了。外接显示器、把窗口从 Retina 屏拖到 1080p 屏更隐蔽：窗口的 CSS 尺寸没变，resize 不触发，dpr 却从 2 掉到 1，画布还在按 2 倍输出，白占一倍像素，显示出来还发虚。

image-rendering：不是万能药

image-rendering 常被当成救命稻草，其实它只管一件事：canvas 元素被 CSS 缩放时，浏览器用什么算法重采样。pixelated 在 Chrome 里可用，Firefox 认 -moz-crisp-edges，Safari 只认 -webkit-optimize-contrast，同一份样式得写三行。

它适合像素画、二维码，能让放大后的方块保持硬边；用在照片上满屏锯齿，用在文字上笔画缺角。更关键的是它治不了半像素偏移：线本来就在两行之间各占一半，再硬的采样也救不回来。

真正控制 drawImage 插值的是另一个开关 ctx.imageSmoothingEnabled = false，它只管绘制图片时的采样，管不到 CSS 层，两者别混。

打印与截图：换个出口就换一套尺寸

打印是另一套账。屏幕上的 dpr 管不到纸：A4 宽约 794 个 CSS 像素，300dpi 下要两千多个像素，画布只按 2 倍准备，打出来全是锯齿。Chrome 打印时 devicePixelRatio 一般还是屏幕值，指望它自动升级会落空。

所以只能在打印前主动把画布放大重画。Firefox 和 IE 有 beforeprint 事件，Chrome 当年还不认，只能退到 matchMedia('print')：

一个清晰度自检

绕了一圈，我给自己写了个自检页：并排画四样东西——1px 横线、1px 竖线、10px 的棋盘格、两行同样的文字（一行整数坐标，一行小数坐标），再把 canvas.width、clientWidth、devicePixelRatio 三个数打到画布上。截图放大到 400%，哪一组糊一目了然。

收尾：模糊原因排查表

排查这件事，顺序比经验重要：先量 CSS 尺寸，再看属性尺寸，最后才动绘制代码。九成的模糊不在 API 上，而在坐标有没有落在像素边界上。

现象 根因 处理
1px 线变 2px 浅灰 描边落在两行像素中间 中心加半个线宽，或改 fillRect
Retina 上线偏粗 线宽按 CSS 像素计 lineWidth 取 1 / dpr
文字边缘发毛 font 缺字体族、坐标带小数 补全 font，坐标取整
整块画布均匀发虚 CSS 尺寸与属性尺寸不符 按 clientWidth * dpr 重建
缩略图糊成一片 非整数倍缩小 矩形取整，两级降采样
换屏后变糊 dpr 变了但没重建 轮询 dpr，变化即重建
打印、导出不清楚 分辨率不足 打印前按倍数重画

从那条灰扑扑的分隔线开始，这套规则被我用到后面所有的静态绘图和涂鸦板上，返工明显少了：模糊大多不是画得不对，而是没算清线该落在哪一行像素上。
