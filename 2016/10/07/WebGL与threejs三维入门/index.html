WebGL 与 three.js 三维入门

2016 年秋天，我接了一个小活：给一家做智能硬件的客户做产品展示页，鼠标拖动可以转动机身，页面上还要能换配色。需求听上去不复杂，我选了 three.js——它在当年的三维库里文档最全，例子最多，遇到问题也最容易搜到答案。这篇文章记录的是从“页面全黑”到“能交付”的那段路，适合刚把 three.js 引进项目、还没弄清渲染链路的人看。读完之后，你至少能判断问题出在容器、相机还是资源加载上。

一个全黑的页面

第一版写完，我在本地打开，页面一片全黑。准确地说不是黑，而是一块什么都没有的区域：背景是页面本来的白色，中间本该出现模型的地方空空荡荡。控制台偶尔冒一句 WebGL not supported，刷新又消失了；换浏览器、换手机，症状各不相同——有的报不支持，有的什么都不报，只是安静地不画。

那天下午排查出的顺序，后来成了我的固定套路：先看渲染器有没有创建成功，再看画布有没有尺寸，最后才怀疑相机、灯光和模型。问题出在第二步。渲染器挂在一个 <div class="stage"> 里，CSS 只写了 width: 100%，没写高度；div 里除了绝对定位的 canvas 什么都没有，高度自然被撑成 0，渲染器也就得到一块 0×0 的画布。WebGL 确实在画，只是画进了面积为 0 的地方。

坑很小，却把整条链路暴露得很清楚：画布要有像素尺寸，场景要有相机，相机前面要有东西。任何一环断了，结果都是空白。下面按这条链路走一遍。

WebGL 到底是什么

WebGL 不是三维引擎，而是一套 JavaScript 能调用的绘图接口，规范由 Khronos 维护，浏览器负责实现。它做的事一句话能说完：把顶点送进显存，用着色器决定每个像素的颜色，然后画三角形。立方体、球体、模型、粒子，最后都是三角形；所谓三维，是在投影到二维平面时算出来的。

最小绘制流程只有三步：准备顶点，每三个浮点数是一个点的 x、y、z；写两个着色器，顶点着色器把模型坐标变换到裁剪空间，片元着色器给三角形内部的像素上色；发起一次绘制调用，告诉 GPU 用哪些顶点、按什么图元画。这次调用就是后面要反复提到的 draw call。

WebGL 不提供相机、光照模型和模型加载，连“场景”都没有，只认缓冲区、纹理、着色器和状态机。画一个带明暗的立方体，得自己算矩阵、写光照公式、管理缓冲区绑定。我用裸 WebGL 写过旋转立方体，两百多行，一半是矩阵和状态管理，改一个参数要同步四五个地方。

three.js 封装的就是这一层：相机抽象成 PerspectiveCamera，光照抽象成 AmbientLight 和 DirectionalLight，几何体与材质分开，Scene 把物体组织成树，渲染时替你算矩阵、排顺序、管理着色器。你写 scene.add(mesh)，剩下的它负责。代价是包体变大、多一层黑箱，但对产品展示很划算。

三件套：场景、相机、渲染器

three.js 的入口只有三个对象，理解了它们的分工，后面的 API 都只是往里填东西。

Scene 是容器也是一棵树，往里加网格、灯光、辅助线，渲染时按树遍历，本身没有尺寸。PerspectiveCamera 是观察者，决定从哪里、朝哪个方向、以多大视野看这棵树。WebGLRenderer 是执行者，持有一个 canvas，把场景和相机交给 GPU。

最容易出错的是渲染器和容器的关系。渲染器不关心 CSS 布局，只知道画布的显示尺寸和像素缓冲尺寸。setSize(width, height) 把 canvas 的 style 宽高设成这两个值，再按像素比设置 canvas.width/height。尺寸来自高度为 0 的容器，画布就是 0 高，浏览器不报错，你只看到空白。

更隐蔽的是相机。aspect 用 clientWidth / clientHeight 计算，高度为 0 时得到 Infinity，投影矩阵直接失效。所以那天的现象不只是画布为零，相机也坏了。后来我改成先判断尺寸再初始化：

第一个立方体

三件套凑齐，再放一个 Mesh 进去，就能看到东西。Mesh 由几何体和材质组成：BoxGeometry 描述形状，参数是宽、高、深；材质描述表面如何与光交互。几何体只有顶点，颜色、粗糙度、贴图都在材质里，这个拆分决定了后面复用资源的思路。

材质我踩过一个典型的坑。第一版用了 MeshBasicMaterial，它不受光照影响，直接按颜色画，所以加再多灯也没有明暗，立方体像一张纯色纸片。要体积感应该用 MeshLambertMaterial，按顶点算光照，开销小；要高光再用 MeshPhongMaterial，按像素算，贵一些。

灯光同理：AmbientLight 给均匀底光，避免背光面全黑；DirectionalLight 给方向，决定哪几个面亮。只用环境光太平，只用平行光暗面死黑，两个一起最省事。下面是完整页面，ES5 写法，全局 THREE，不经构建工具：

相机与坐标系

透视相机的四个参数，调画面时改来改去的就是它们。fov 是垂直视野，单位是度，45 到 60 比较接近人眼，越大越像广角。aspect 必须等于画布宽除以高，写死 1.6 在方形容器里就会变形。near 和 far 是近远裁剪面，外面的物体不参与渲染；不要随手写 0.001 和 100000，深度精度会被拉开，远处出现闪烁的接缝，也就是 z-fighting。

lookAt 决定朝向。相机默认看向自身坐标系的 -Z 方向，调用 camera.lookAt(target) 之后它会转向目标点。这个方法改的是相机的旋转，不改位置，所以先设 position 再 lookAt，顺序反了画面就不对。

坐标系的约定也要记住：Y 轴朝上，X 向右，Z 朝屏幕外。3ds Max 导出的模型常是 Z 轴朝上，直接加载会“躺”在地上；给模型套一个父级 Object3D，在父级上转 -Math.PI / 2，别改模型自身旋转，否则会和交互旋转混在一起。

正交相机在两类场景里比透视相机合适。一类是需要严格比例的产品三视图、爆炸图，另一类是图表化的展示，物体不该有近大远小。它的构造参数是左右上下四个边界加近远平面：

让立方体转起来，只需把渲染调用放进 requestAnimationFrame。rAF 的调度语义另有专文，这里只记住：它在下一帧之前回调你，频率跟着屏幕刷新走，可能 60 次每秒，也可能 30 次。

跨域是第二个坑。图片在 CDN、页面在另一个域名，CDN 没返回 Access-Control-Allow-Origin，浏览器就拒绝把图片交给 WebGL，模型表面是黑的。两件事都要做：服务端加 CORS 头，请求时带 crossOrigin。后者不设，即使服务端允许也拿不到像素；setCrossOrigin 写在 load 后面同样无效。

第三个坑是尺寸。WebGL 1 对非 2 的幂次贴图有限制：不能生成 mipmap，也不能重复平铺，three.js 会警告并重采样，画面可能糊掉，产品图尽量做成 256、512、1024。另外它默认把贴图上下翻转（flipY 为 true），因为图片原点在左上，UV 原点在左下。用 canvas 生成纹理发现图案倒了，先看这个开关，别急着改 UV。

性能

三维页面的性能瓶颈，八成不在三角形数量，而在 draw call。每一次 renderer.render 里，每个可见的 Mesh 通常对应一次绘制调用，CPU 要为此做一次状态检查与提交。场景里放两百个独立的小零件，即使每个只有十二个面，也可能是两百次调用，帧率照样掉。合并同材质的静态物体、复用几何体和材质，是当年最有效的手段。

灯光和阴影要单独算账。每多一盏灯，着色器计算就多一份；Lambert 按顶点算还扛得住，Phong 按像素算，灯一多就明显。阴影更贵，每盏投影灯都要把场景额外渲染到阴影贴图，贴图从 1024 提到 2048，显存和带宽翻倍。我只让主平行光投影，贴图固定 1024，接受一点锯齿。

真机卡的时候，我的顺序是：先关阴影看帧率，再逐盏关灯，再降像素比，最后才动几何体。前三步都只改一行代码，能快速二分；合并几何体要改结构，放最后。2016 年的中端安卓机跑三万个三角面加 2048 阴影贴图，掉到二十帧很正常。

移动端它默认支持单指旋转、双指缩放，但页面也会跟着手指滚动，两者打架。给 canvas 加 touch-action: none，把触摸事件完全交给控件。也不要再绑一套 mousedown 旋转逻辑，两套一起跑会出现转速翻倍、松手不停。

兼容与降级

WebGL 的支持率在 2016 年已经不错，但企业内网、老安卓机和部分集成显卡仍然会失败。检测不能只看 canvas.getContext 是否抛错，要连 WebGLRenderingContext 一起判断，因为有的浏览器存在这个构造函数却拿不到上下文：

检测失败时不要留空白。我的做法是默认渲染一张静态产品图，检测通过后再用 canvas 覆盖；初始化出任何异常就把静态图露出来，并在角落提示“当前浏览器不支持三维预览”。

移动端还有两个现实问题。一是显存，iOS 对纹理尺寸敏感，单张 4096 的贴图在旧机器上可能分配失败，产品图控制在 1024 到 2048 比较安全。二是上下文丢失，切后台久了或显存吃紧，浏览器会回收 WebGL 上下文，画布变白且不报错。要监听 webglcontextlost 并阻止默认行为，等 webglcontextrestored 后重建；当年最省事的做法是直接刷新页面。WebGL 2 在新版本浏览器里开始支持，本文仍按 WebGL 1 写，接口和坑都适用。
