SeaJS 模块化开发实战

去年十月我们写了一篇 RequireJS 的实操笔记，把 AMD 那条路上 paths 与 shim 的配置细节讲得比较满。这篇补另一块拼图：SeaJS 这套实现真正动手时是什么手感。规范层面 CommonJS、AMD 与 CMD 三家的差异另有专文，这里一个字不重讲；只看模块怎么写、加载器怎么配、combo 怎么合并请求、构建怎么接。以下口径基于 SeaJS 2.2 这一系列。

页面接入的最小骨架

一个页面接 SeaJS，源码里只出现两处东西：一个 script 标签，一个入口调用。

seajs.use 里的路径按配置规则解析，加载器把入口模块取回来执行，入口模块里的 require 再按需拉后面的依赖。页面只挂一个 script、只声明一个入口，这件事在当时的收益很朴素：脚本顺序不再手写了。接 SeaJS 之前我们的页面尾部常是一排并列 script 标签，jQuery、插件、业务脚本各一行，谁先谁后靠人记，挪一个位置就可能炸一个线上报错。改成单一入口后，顺序问题被推迟到模块内部就近声明，页面模板里那一长串标签消失了，code review 时也再没有出现过”这行为什么在上面”的争论。

模块标识与路径推导

上手 SeaJS 最容易踩的一层是标识到路径的推导：每个 require 最终都会变成一个 URL，加载器按 URL 去重和缓存。四条规则要用熟。

第一，以 ./、../ 开头的相对标识，基准是当前模块自身的 URL，不是页面地址。组件整个目录搬家时它跟着走，但跨多级目录的 ../../ 写多了会乱，我们约定只允许相对引用同目录文件。第二，裸名标识如 require('jquery')，走 config 里的 paths 映射，在 base 之下解析。第三，seajs.config 必须在 seajs.use 之前执行——入口模块都开跑了才配置，先发出去的请求按默认规则解析，同一份代码会被下载两遍。

加载器配置项

先补一句接入上的差异：RequireJS 要在 script 标签上用 data-main 声明入口，SeaJS 没有这个属性，入口解析全在 seajs.use 与配置里完成，模板层少一处耦合。

base 是裸名标识解析的根，paths 在根之上再拼一段目录，两者配合让业务代码写 require('app/order-page') 就够。alias 给第三方库和版本切换起逻辑名：团队整体把 jQuery 从 1.x 换到 2.x 的那次，改的就是 alias 一行，业务代码里的 require 一行没动。

map 干的是”不改代码改地址”的活，函数收到推导完的 URI，返回改写后的 URI。实操里它最常见的用途是把线上请求指到本地调试目录：配置里留一个开关标记，命中时把 CDN 域名替换成本机端口，改动先在本地过一遍再走发布。排查线上资源问题时，也可以反向映射到备份地址，验证是不是发布漏了文件。

preload 在入口模块执行前先把列出的依赖加载好，适合每个页面都会用到的公共依赖，比如 jQuery。别把”大概常用”的模块也塞进去，预加载不分页面，用不上就是浪费首屏带宽。debug 打开后走调试版加载器，报错带模块 URI，线上必须关掉，它和下一节的 combo 是绑在一起开关的。

combo：把请求数压下来

开发期一条业务线随随便便拆出几十个模块文件。2016 年浏览器还没默认用上 HTTP/2，HTTP/1.1 下一个域名的并发连接数只有大约六条，几十个小文件挨个请求，排队就能把加载时间吃掉大半。combo 就是绕开这件事的：把命中规则的同目录模块拼成一次请求拉回来。

combo 可以直接给真值全局开启，也可以像上面这样给一条只命中特定路径的规则，后者能把合并范围圈住，当时用得更普遍。comboSyntax 两段分别是”目录与文件清单之间的分隔符”和”文件之间的分隔符”。按上面这份配置，入口拉了 app 目录下三个模块，实际只发一次请求，路径形如 /assets/js/app/??main.js,dateformat.js,highlight.js，响应是三个文件拼起来的串。

combo 是这条线上排错量最大的部分，三条纪律拿损失换回来。

一、合并只吃同目录同前缀，目录切太碎等于没合。我们一度按组件把模块拆进十几个只有两三个文件的小目录，combo 规则收不齐，页面照旧几十个请求。后来按业务域收敛成几个大目录，保证入口模块落在同一条前缀里。

二、一旦开了 combo，map、alias 的改动要同步验证。合并串是在标识推导完成之后才拼出来的，本地改了 alias、服务器目录结构没跟着动，线上拼出的 URL 就整批 404。我们有次发布后页面白屏，最后查到是 map 规则还在按旧目录匹配，而本地调试时 combo 是关着的，两边现象完全对不上。

三、combo 返回的是拼接串，模块顺序错了会报”模块未定义”。报错文案和缺文件时一模一样，但根因是依赖被排到了后段，先执行的那段找不到它。排错标准动作：先关 combo 复现。关掉就好，问题在拼装，回去查目录规则与文件顺序；关掉还坏，再单独查那个模块本身。

构建与发布

SeaJS 的分工很明确：开发期一个模块一个文件，改动小、review 清楚；发布期用官方那套构建工具（sea-cmd、spm 系的命令行在当期就是干这个的）把同前缀的模块合并、压缩成少数几个包。产物料里的 define 带着显式模块名，整包拉回来加载器也能逐个注册，业务代码不需要感知合并这件事。

坑在标识上。发布后模块的路径与 ID 都变了，alias、paths 若还指向开发期目录布局，症状通常是两类：线上页面去请求没被合并的小文件，服务器上没有，一排请求红掉；或者线上加载了合并包、本地调试加载散文件，同一模块两边各执行一遍，又回到”事件绑定两次”的老问题。我们的解法是把发布映射——哪个目录合并成哪个包、alias 和 map 各自怎么跟着改——收敛进一份配置文件，构建工具和页面配置读同一份源头，改一处两边都变。这份文件当时和业务代码一样过 review。

构建链跑在 Node 4 LTS 上，npm 2.x 到 3.x 的扁平安装偶尔会让同一构建包出现两个版本，发布机的依赖我们用 npm-shrinkwrap 锁住。同期 2016 年也有团队开始用 webpack 1.x 那类打包工具把加载与构建一起接走，打包器内部机制另有专文不展开；SeaJS 这边的产物只需要保证合并包与模块命名稳定，就能和任何后续构建衔接。

选型与迁移

把时间放在 2016 年 2 月。SeaJS 这个时点还被不少国内团队用着：文档是中文的，核心很小，工厂里写 require 的手感对 CommonJS 出身的人友好，上手成本低。同时演变的走向也明显，CommonJS 语法和 npm 系包管理越来越重，SeaJS 自家的构建工具链当时也在往这个方向靠。团队面对的真实问题不是哪种规范更好，那是专文的事，而是手上的代码往哪走。

三条路各有代价。继续 SeaJS 加自建构建：改动最小，combo 规则、标识约定、review 流程全部沿用，顾虑只是工具链节奏慢下来。迁去 RequireJS：若存量代码已是 AMD 数组式，重写是单向机械的；疼点在原来靠 shim 喂进来的非 CMD 库，SeaJS 这条线没有对应概念，包装模块都得手写，它那边 paths 与 shim 的配置细节另有专文，这里只谈判据。试打包工具：配置概念和 SeaJS 的运行时解析完全不是一个量级，迁移等于重来。

判据归成四个问题，逐个写进评估文档。依赖关系复不复杂：页面入口彼此独立、模块复用稀的，SeaJS 加 combo 已经够用。要不要 npm 生态：新组件优先去 npm 找包、构建要吃扁平的 node_modules，SeaJS 自带工具链在这就会跟你较劲。有没有构建链：没有专人维护构建就别轻动打包工具。维护者还在不在：当时 SeaJS 的发版节奏确实慢了，该作为风险写进计划，但说它已经停止维护不是那个时点的实况。

小结

SeaJS 把复杂度压在加载器配置和 combo 规则上，模块文件本身因此干净。代价是不对等：alias 配错同库载两遍，map 一改线上 404，combo 规则一误伤几十个模块。配置是最顺手也最脆弱的一层，最管用的经验就一句话：配置变更像代码变更一样进评审。
