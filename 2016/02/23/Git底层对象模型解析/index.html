Git 底层对象模型解析

今年一月下旬，我们四人小组的主前端仓库涨到了两三 GB。症状很具体：一次 git status 要等十几秒才吐结果，编辑器冷启动加索引要等小半天，新人入职克隆一份代码要跑接近半小时。那段时间全组统一的猜测是”仓库用久了，Git 变慢了”，有人甚至翻出脚本想把老历史裁掉一半。没有人说得清这几 GB 到底存在哪里，也说不好为什么慢的偏偏是这三个动作。

二月初我实在受不了，把那个 .git 目录一层层扒开了。看完之后很惭愧：所谓”Git 的玄学”，全部可以还原成几条小学徒也能验证的数据结构事实——仓库里只有四种对象，对象的编号是从内容算出来的，分支只是装着四十个字符的文本文件，慢是因为几千个小文件摊在目录里等挨个统计。把这几条想通，开头三个症状会一处一处被解释掉，一点悬念都不留。这篇文章就按我当时的认知顺序讲：四类对象、对象 ID 的来历、工作区到对象库的三层、松散对象与 pack、引用系统，最后回到那次膨胀事故收尾。边界先说清楚：本文不讲变基、合并与冲突解决的命令（那部分见变基篇），不讲分支模型与团队协作规矩（见分支管理篇），不做集中式与分布式的对比迁移（见 SVN 对比篇），也不写命令手册——每条命令只在需要回答”它动了哪一层”时出现。还是老约定：文中所有哈希都是 a1b2c3d 这样的占位符，不指向任何真实仓库，也不对应真实计算结果。

先亲手拆开一个提交链：四类对象

“仓库里只有四种对象”这句不是我编的口诀，是 git cat-file -t 能返回的全部答案。从库里随手挑一个 ID 问它类型，回你的只可能是 blob、tree、commit、tag 这四个词。下面这条链，你在任何真实仓库跟着敲一遍都对得上。

blob 存一个文件的内容，仅此而已。没有文件名，没有路径，没有权限位，没有修改时间。同一份内容，放在 src/index.js 是它，挪到 docs/index.js 还是它，谁写的、哪天写的都不参与计算。

tree 存一份清单。每行三样东西：权限模式、名字、对象 ID。名字可以是文件也可以是目录；指文件时那个 ID 是 blob，指目录时是另一棵 tree。所以整棵目录树是被拆成一串清单互相指着，没有任何一个对象里存过”完整路径”这种字符串。

commit 指向一棵 tree，再补上来龙去脉：那棵 tree 的 ID、零个或多个父 commit 的 ID、作者与提交者两个身份、两个时间戳、提交信息正文。第一次提交父是零个，之后每笔至少一个父，合并提交两个。

tag 这里说的是附注标签，它自己就是一个对象，内容包含它指向的对象 ID（通常是一个 commit）、标签名、谁打的、什么时候打的、说明文字。轻量标签不是对象，只是 refs/tags/ 下一个装着四十个字符的文本文件，别把两者混在一起谈。

顺手纠正一个流传很广的说法：一次提交存的不是”这次改了哪些行”。Git 每次记的是一棵完整的新 tree，没改动到的文件和目录，它的 ID 原样出现在新清单里——内容没变，ID 就不会变，对象也不必再造。所以一次只改一个文件的提交，实际新增的对象只有那一个 blob、那一笔 commit，加上从根目录一路到该文件路径上那几级 tree：只有路径上每一级清单变了，才需要造一棵新 tree；深层没动的目录一个对象都不新增。这就是提交和分支便宜到离谱的原因。

最后一句判断，请现在就接受下来：Git 的仓库是那座内容库，工作区只是它的一次展开视图。你把工作区的文件全删光，只要 .git 完好，一条 git checkout . 就能全部原样摆回来。这不是”从备份恢复”，而是照着 tree 清单按 ID 把字节取回来重放一遍。方向感一旦建立，后面所有”我的文件到底存在哪”的问题都不会再问错。

对象 ID 是从内容本身算出来的

对象的编号不是服务器下发的序号，也不是自增主键，而是对对象内容做一次 SHA-1，拿结果当名字。关键在”内容”两个字的范围：算进哈希的不只是字节本身，前面还拼了一段类型加长度的头部。

一个内容为 hello git 加一个换行的 blob，Git 实际是这么算的：把字符串 blob 10、一个空字节、十个内容字节连起来，对这十八个字节求 SHA-1。

Linux 上把 shasum 换成 sha1sum。三条命令回你同一个四十位十六进制串：第二条是在手算验证，第三条走 Git 的正路。加上 -w 才真正落成对象：

不带 -w，Git 只报编号、不留字节；带上 -w，对象库当场多一个文件。这两者的差别就是”算个哈希”和”造一个对象”的差别。

编号由内容唯一决定，往下能推出三条我们每天在用、却很少有人点破的结论。

一，仓库不需要独立的校验和文件。任何一个对象被改掉一个字节，它的 ID 就变，而它的父对象里记的还是旧 ID，指针当场断裂。git fsck 做的事情就是顺着可达性把每个对象的 ID 重算一遍，和它所在的文件名比一下。数据完整性是结构自带的，不是后期打的补丁。

二，分布式协作能安全进行。两台机器各自离线提交，不用向任何人申请编号；只要内容一致，算出来就必然一致。冲突只会发生在”同一个路径有两个不同 blob”这种语义层面，绝不会发生在”两个仓库抢同一个对象号”这种存储层面。这也是克隆之后两边历史能直接对齐的根因。

三，改历史只能生成新对象。想”原地修改”一笔提交，它的 ID 必然变化，所有指向它的 tree、commit、ref 全得跟着改，代价等于把这条线后面的历史整个重写一遍。所以 --amend、变基这类动作在对象层面的真面目是：造一批新对象，把某个 ref 挪到新链上，旧对象一个都没删，安安静静躺在库里等回收。

至于”两份不同内容撞出同一个 ID”，2016 年的工程答案是不用考虑。SHA-1 输出 160 位，随手碰出重复的概率小到进不了讨论范围。理论上找碰撞属于哈希算法强度的问题，是密码学在研究的事；Git 把类型和长度一起算进头部，跨类型撞车还得先凑出相同长度，比纯内容碰撞更难。当时的社区态度很明确：SHA-1 做内容寻址够用，真出现整体性问题就换算法，这不是仓库日常运维会碰上的东西。

留一个你能亲手验证的事实：任何仓库里，空文件的 blob ID 都是同一个值。在 /tmp 再 git init 一个空仓库，把 probe.txt 用 -w 写进去，拿到的 ID 和第一个仓库里完全一致。内容寻址没有命名空间这回事，因为根本不存在”哪个仓库的那个 ID”——只有那一个 ID。

三个区域与中间那层索引

工作区、暂存区、对象库。三个区域里只有一个真的存内容，就是对象库。暂存区叫索引更准确：它是一张表，记”路径 → blob ID”，再附上每个文件的 stat 快照。

三列之后才是路径。第一列模式，第二列这条路径当前对应内容的 blob ID，第三列 stage 版本号，正常状态永远是 0。索引里一个字节内容都没有。所以”暂存区是一份等着提交的副本”这个理解是错的，它等的是一份清单。

git add 拆开只有两步：把当前内容算成 blob 写进对象库（库里已有就跳过），再把这行”路径 → ID”写进索引、顺手刷新 stat。因此同一个内容连续 add 两次，索引那一行被覆盖一次，对象库一个字节都没多。

索引里那些大小、mtime、inode 快照不是装饰，它们是 git status 的快路径依据：先看 stat 变没变，没变就认定内容没变，变了才真去算一次哈希。整套比对是三份——索引对 HEAD 的 tree，得出已暂存的改动；工作区对索引，得出未暂存的改动；工作区里不在索引中的路径，得出 untracked，这一份必须真的遍历目录树。想通这一点，”status 慢”就不再神秘：它的开销主体是条目数乘以一次系统调用，跟仓库用了多久毫无关系。我们那个仓库当时索引里挂着几万个 node_modules 的条目，光是遍历就够终端转十几秒。

把”哪条命令动了哪一层”摊开成一张表，很多困惑会当场消失。

那个时期，切换分支和恢复文件这两件语义完全不同的事共用 git checkout 一个命令，是新手困惑的主要来源；但在对象层面它动了哪一层始终清楚。后来 Git 才把这两件事拆成两条命令，那是 2019 年的改动，本文按当时的用法写。

git rm --cached 值得多说一句。删掉索引里的一行，文件完好地在原地待着，你马上会在 status 里看到它转成 untracked。之前提交进去的那个 blob 仍然躺在对象库里，只是暂时没有 ref 能走到它——它是否真被回收，取决于后面讲的 gc 规则。

git reset -- <path>（不带 --hard）撤销暂存的表现同样自洽：索引退回 HEAD 那一版，工作区没被碰过，于是所有改动立刻显示成”未暂存”。只有加上 --hard，命令才第三次把手伸进工作区。

最后一个结构细节：stage 列平时是 0，合并冲突时同一路径会出现 1、2、3 三行，分别是共同祖先版本、我方版本、对方版本，加上工作区那个实际文件，索引一次容得下四个版本。冲突怎么处理不在本文范围，但你哪天看到 git ls-files -s 里同一路径排了四行，别以为索引坏了。

松散对象与 pack：库里的两种形态

先看看对象库在磁盘上到底长什么样。

ID 的头两个十六进制字符当目录名，剩下三十八个当文件名，文件里装的是那段”类型 空格 长度 空字节 内容”经过 zlib 压缩的结果。没有增量、没有索引、没有针对小文件的优化。这种形态叫松散对象：写一次就是一个文件。

问题出在数量级。一次改动三十个文件，就是三十个 blob 加若干棵被改到的 tree 加一笔 commit；一天几十笔提交、几条分支跑下来，.git/objects 下面能堆出几万个文件。这时 git status、git log、git fsck 全都在做海量 open/close 系统调用，时间被寻道和目录遍历吃干净。

先量一下，再决定治什么。

count 与 size 是松散对象的数量和总大小（KB），in-pack 与 size-pack 是已经进包的对象数和包大小，packs 是包文件个数，garbage 是不像对象的杂文件数。这四个字段是排查膨胀时最先要看的东西，我后面会回到它们。

打包的动作：

跑完之后，.git/objects/pack/ 下多出一对文件：.pack 装对象，.idx 装这些对象 ID 到包内偏移的有序索引。有了 .idx，Git 查一个 ID 在不在包里、在包的哪个位置，不用把整包读一遍。gc 顺手还会整理 ref、把冗余的包合并；当时常用的开关是 --aggressive，代价是慢，跑几分钟属正常。Git 自己也会在 fetch 之后按 gc.auto 的阈值触发一次轻量打包，但那只是兜底：阈值定得高、动作保守，产物目录一旦提交过，它一点忙都帮不上。

包真正的价值在增量。打包时 Git 会把内容相近的对象排到一起，挑一个当 base，其余的只存”相对 base 改了哪里”的 delta 指令；配对靠路径名、对象类型、大小这些线索来排序凑对。所以同一个文本文件改了十几版，在包里不是十几份完整内容，而是一份 base 加一串串小差异。文本为主的仓库常能压到松散对象总和的几分之一。反过来说，两张不同的位图之间几乎找不到公共子串，压不出增量，只能一份一份存——这就是二进制文件在 Git 里特别占地方的结构性原因，不是配置问题。

这里要分清两层机制，很多人把它们搅成一团。对象复用是”没变的内容整个不再存一遍”，属于对象模型本身，从写入那一刻就生效；delta 压缩是”相近的内容只存相对差异”，只在打包时发生。松散对象阶段完全没有 delta，每个对象各自 zlib 一份，所以同一份历史在松散状态和打包状态的体积能差好几倍，gc 前后 count-objects -v 里 size 与 size-pack 的对比就是这个差额的账单。

传输走的本来就是 pack。

git fetch 的时候，本地把对方缺的对象边算边打成一组 delta，通过一条连接推过去，对面落盘的就是一个包文件。所以”传输高效”和”本地一堆松散对象把 status 拖慢”是两件不相干的事：前者由 pack 机制保证，后者只能靠你在本地跑 gc。新人克隆慢通常是包本身太大加上带宽，跟本地碎片化无关，别把这两个原因混成一个。

引用系统：分支就是四十个字符

对象库是一座内容仓库，可名字全是哈希，人读不动。引用系统做的事就是给这些 ID 配人类可读的名字，而这些名字在磁盘上就是普通文本文件。

三条回你同一个 ID。第一条把那个文件原样打印了出来：

除了四十个十六进制字符和一个换行，这个文件里什么都没有。标签同理，git tag -a v1.2.0 -m '...' 造的是一个附注标签对象，refs/tags/v1.2.0 里仍然只是一个 ID。

HEAD 装的是一个路径字符串而不是 ID，切分支的本质就是这一行文本被改写。于是下面几条判断可以直接落地。

建分支极快。git branch feature/list 只是在 .git/refs/heads/ 里新建一个文本文件、写四十个字符，不复制任何对象，不动任何工作区文件。切分支的开销全部来自”按新旧两棵 tree 的差异调整索引和工作区”，跟历史长度无关，跟这条分支”包含多少提交”同样无关。

这也是我希望大家现在就换掉的心智模型：分支不是装提交的容器，是一根指着提交的指针。提交不在分支里面，分支只是别人能走到这条链的一个入口。所以删分支删不掉对象；某个对象能不能被回收，只看还有没有别的 ref 走得通它。误删分支之后找回，靠的是 reflog 里记着的那个旧 ID，而不是”从分支里捞东西”。

.git 根目录下还有一批同性质的过程文件。

这些文件解释了 Git 为什么能把”中途停住”续上：状态写在磁盘里，不靠进程内存。

reflog 值得单独点一句。它对 HEAD 和每个分支记一条本地操作流水，git reflog 打印出来每行末尾都跟着一个 commit ID，默认保留一段时间。这根救命绳纯粹是本地资产：它不是对象、不在可达链里、不会随 clone 传播，别人克隆不出你误删的那条链。所以”reset --hard 之后本地还能捞回来”和”共享仓库里指望 reflog 救全员”是两回事，后者从来不成立。

然后是 packed-refs，一个专门用来坑新人的东西。

分支和标签一多，Git 会把一部分 ref 收进根目录下一个 packed-refs 文本文件，一行一个 ID 加一个名字，refs/heads/ 目录里对应的那个文件就没了。所以在目录里翻不到某个分支，绝不代表这个分支不存在。别信 ls，信 git show-ref 或 git branch -a。

最后把命名空间统一一下：远程跟踪分支在对象层面和普通分支是同一回事，也是一个 ID 配一个名字，只是名字落在 refs/remotes/origin/... 底下。origin/master 读到的是”上一次和远端通信时，远端的 master 在哪个提交”。它是一个本地 ref，不是远端的实时快照。这个区分能解释掉一多半”我明明看到分支存在，为什么 pull 下来什么都没有”。

两三 GB 的复盘：按这个顺序查

回到开头那次事故。现在零件齐了，排查就是一条固定顺序，每一步都能用一两条命令出结论。我把当时踩过的弯路按正确顺序重排一遍。

第一步，先定位这几 GB 到底在哪。

如果 objects/pack 占了九成，那是对象问题，继续往下；如果 .git/index 有几百 MB，那是索引条目太多，病根在未忽略的产物目录；如果 .git 其实不大而工作区巨大，慢的是编辑器遍历文件系统，跟仓库体积是两码事。我们那个仓库是第一和第二种同时中招，当时没人想到要看 index，全组围着 pack 转了半天。

第二步，看包碎不碎。

packs 上百、count 上万就是碎。碎包的代价是每次查对象要在几十个 .idx 里各走一遍，size-pack 本身反而不一定大。这时先跑一次 git gc 看条数和体积掉多少。我们第一次 gc 之后 .git 从 2.7 GB 降到 2.1 GB，碎片确实吃掉了一块，但显然不是主因。

第三步，查不该进库的东西进过没有。这一步最容易自欺，因为文件早从工作区删干净了，ls 什么也看不见，只能问历史。

把”曾经新增过的路径”按出现次数排出来，产物目录一眼就能认出来。我们的 dist/ 在历史里出现过几千次，而 npm 2 到 3 那段时间依赖是尽量扁平装的，一个中等项目的 node_modules 动辄几万个文件，只要整个进过一次历史，这几万个 blob 就永远躺在包里。

直接按大小揪出大对象：

第四步，看同一路径的大二进制是不是被反复提交。图片、字体、压缩包这类文件每改一次就是一个全新的 blob，旧内容不会自动消失。判断依据很直白：同一条路径在历史里挂着几十个不同 ID，每个都是几百 KB。

第五步，看有没有遗留的 ref 把大对象钉住。对象只要被任何一条可达链指到就活着。三年前的实验分支、已经废弃的标签、远程跟踪 ref，都能让一批大 blob 一直占着包。

清理动作要分清层次。删分支、删标签只是撤掉 ref，对象一个都不少；撤完必须接着跑：

--prune=now 的意义是打破默认保护：gc 平时会保留近期（按当时的默认策略是两周之内）写入的对象以防你反悔，加上这个参数才真的把不可达对象从磁盘抹掉。如果做完体积还是没降，去查 reflog——它自己也是一串把旧 ID 钉住的东西。

最重的那一步，也是我们当时真正需要的：文件已经提交进历史，可达链还在某条分支上，删 ref 加 gc 全都救不了。2016 年要把这些字节彻底抹掉，唯一手段是重写历史。

代价必须写在脸上，三点一条都不能省：所有被改写的提交 ID 全部变化，分支和标签都要重指；其他人不能简单 pull，要么重新克隆，要么做一次极其小心的一次性强对齐；命令自己会留 refs/original/ 这份备份 ref，回滚靠它，可回滚之后不把它删掉再 gc，字节就一个都收不回来。那段时间社区也在流传 BFG 这类专清大文件的脚本，但我们当时没人敢在多人协作的主仓库上跑第三方工具，通行做法就是 filter-branch 加一份完整冷备份。我们最后是从一个 bare 仓库的备份重做的，全组重新克隆，占掉半个下午。

收尾前把结果验一遍，别只信 du：

verify-pack 能把包内每个对象的原始大小和压缩后占用列出来，用它确认”那几个大 blob 真的不在包里了”，比看目录大小踏实。

从原理回看实践：我们钉下来的几条约定

把前面几层串起来，团队规矩就不是拍脑袋定的了。

一，产物一律进 .gitignore，而且必须在第一次提交之前就配好。理由直接回到对象模型：一个文件只要进过索引、提交过一次，它的内容就成为历史中的对象，之后 git rm --cached、之后手工删除，字节都还在库里。所以”先提交再补 ignore”这个顺序的错误不可逆，成本要等到仓库膨胀那天才结账。我们那份 ignore 里长期漏了 dist/，就是这次事故的主因。

二，大二进制不该进 Git。增量压缩对它几乎无效，内容寻址又让每个版本都是全量。当时可行的思路就两条：资源放文件服务器，仓库里只留地址；或者这类资产干脆交给集中式工具管，SVN 在这件事上确实更合适，这里不展开。

三，.gitattributes 里的 export-ignore 可以用，但当时用得很少，作用是导出的 archive 里排掉测试目录，跟仓库体积无关，别把它当瘦身手段。

四，把仓库体积当回归项盯着。我们给当时的 CI 加了一个极便宜的 shell 步骤，把每个月的数字存下来：

size-pack 超阈值就报警。绝对值不重要，趋势重要。膨胀从来不是某一天突然发生的，而是 packs 从 1 涨到 80、包体积每月涨三百兆那样一条曲线，有月度记录就能提前看见。

五，评审时看一眼这个改动有没有引入新的大文件。git diff --stat 对二进制只给一行 Bin 0 -> 4194304 bytes，最容易被眼睛滑过去。

三条主线收住：内容寻址决定了库里存什么、为什么改不了；指针式引用决定了分支和标签为什么这么轻、删除为什么不等于删数据；增量打包决定了文本历史能压多狠、二进制为什么压不动。合起来其实就一句话——Git 的仓库是一座按内容命名的对象库，你天天看到的分支、提交、工作区，都只是指向它的光标。

理解到这一层，开头那三个症状就不神秘了：git status 十几秒、编辑器建索引半天、克隆跑半小时，分别是索引条目太多、库里可达对象太多、pack 太大这三件事的可见结果，没有一处需要”Git 用久了会变慢”这种解释。至于当初那份想把老历史裁掉一半的脚本，看完本文就知道它在对象层面根本不成立：历史是一条靠 ID 串起来的链，裁掉中间一环，后面每一环的父指针都指向空处。真要减体积，减的是不可达对象和包结构，不是历史本身。剩下的事只有一件：别再让产物进第一次提交。
