Git 版本控制入门与常用命令

add、commit、push 我是在别人的仓库里照着敲会的。排成自己的一条动线，是去年接手一个多人项目之后：那里每天都有推上来几十个文件、信息只写一句 fix 的提交，也有人改乱之后靠 checkout 和 reset 硬救，救活了却说不清为什么。我的困惑不在命令存不存在，而在同一个目的有三条命令都走得通，而我不知道该选哪条。

本文假定你会基础的增删提交推送。变基与合并的语义、冲突怎么解、分支怎么摆、提交信息格式、内部对象结构，本仓库另有专文；我管的是命令面本身。

一次性配置：把新人第一天的成本降下来

名字、邮箱、编辑器

作者字段跟着提交推出去、被别人拉下来，而它不追认：等你发现邮箱配错，错的历史已经在别人的克隆里，所以第一天那十分钟就该配对。

core.editor 决定哪些地方弹编辑器：不带 -m 的提交、add -e 改补丁、变基时那份待办清单。默认落到 vi；只想临时换一次，用 GIT_EDITOR 顶掉更省事。

配置分三层：系统级、~/.gitconfig、仓库里的 .git/config，读取由外向内，后读到的赢，仓库级覆盖全局。某个仓库需要单独的换行策略或单独的邮箱，就在克隆里不带 --global 配一次。git config --list 把三层混在一起、看不出来源。

core.autocrlf：混合团队里要开会讨论的一条

Windows 写出的文件是 CRLF 换行，Mac 和 Linux 是 LF，这个开关决定索引里存什么、工作区放什么。

坑在于 true 和 input 不是同一个约定：两个人各按一种提交，索引就一半 LF 一半 CRLF，此后每次比对都拖着一堆文字一模一样却标了改动的行。而且它只管新检出和新写入的内容，已经混进仓库的换行不会自动整理，得重新检出、重新暂存一遍才生效。

更稳的做法是把约定写进仓库，不靠每个人的本地配置：仓库内统一 LF，加一份 .gitattributes。

这几行进仓库之后，core.autocrlf 配错也破坏不了索引内容。

颜色与别名

color.ui 用 auto 不用 always，否则把 log 重定向进文件会带上一堆转义垃圾。别名只是字符串替换、不替你补参数：git unstage 漏了路径就退化成 git reset HEAD，整个暂存区一起回退；lg 把 --all 写死了，看单条主线时得手动去掉。带 ! 开头的别名能跑 shell 命令，也最难排查。

看清状态与差异

git status -sb 当默认：-s 一行一个文件、只留状态字母，-b 在最上面补一行分支与它的上游，形如 ## master [origin/master: ahead 2]，ahead/behind 的计数就在那一行。短格式省掉了未跟踪的细节，提交前该看一眼完整输出；目录太吵可以配 status.showUntrackedFiles no。

log 固定这条组合：--oneline、--graph、--decorate，最后这个把分支名和标签写在提交旁边，不加上只看见哈希、分不清哪条线是哪条线，比分支才补 --all。条件能叠着筛，--since=2.weeks.ago --author=chunle -- src/ 一次限住时间、人和路径，--until 同样接受自然写法。看补丁用 -p，最近两条是 -2，git show <提交> 看单个提交、配路径只看那一个文件。

git add <文件> 的语义是整个文件，按下去就全进索引。想只提交其中一半，粒度得降到块。

提交与修正

commit -a 把所有已跟踪文件的改动直接提交，两个边界：没跟踪过的新文件它不认识；它会绕过你在索引上做的挑选，已经 add -p 挑好一半再用 -a，另一半也一起进去。所以它只适合改动集中在几个老文件时。

--amend 修正最近一次提交，能换信息、补漏掉的文件、改作者。它换的是提交本身而不是追加一条修补，于是纪律只有一条：推出去之前才可以动。已经推给别人之后再改完重推，对方拉下来会看到两条分叉。为什么改一下就换了身份，另见对象模型那篇。

两个 -m，第一个当标题、第二个当正文，比在编辑器里手敲空行稳妥，也适合写进脚本。钩子要说清楚：--no-verify 跳过提交前的检查钩子，钩子挡的通常是格式和不该进仓库的文件，信息格式本身另见提交规范那篇。它能救命，但不该顺手用：你在本地绕过去的检查，通常只是推到别人机器或流水线里再炸一次。

撤销与找回的命令面

丢弃工作区改动是 git checkout -- <文件>，拿索引内容覆盖桌面。取回旧版本是 git checkout <提交> -- <文件>，注意这条会同时改写索引，文件一落地就已经暂存，不必再 add。reset 三档各自动到哪一层：

想留改动就别用最后一档；它为什么能决定这三层的取舍，指向对象模型那篇。

clean 删的是未跟踪文件，Git 从没存过副本，删掉之后没有任何命令能找回，所以固定两步走。加 -x 会连被忽略的文件一起删，体积大的项目里这一条足够毁掉一个下午。

stash 收走未提交的改动、压进一个栈，工作区回到干净状态。

先存起来再只提交一半这个动作，没 -k 就得手工来回搬。apply 只应用不出栈，pop 应用完再弹出：怀疑会冲突就用 apply，冲突了原始记录还在。stash@{2} 按栈位置数，每次入栈出栈全体挪一位，今天记住的编号明天就指向别的东西。这也是我不拿它长期存放改动的原因，另外两条更硬：记录只在本机、不进远端，重装就没了；换人接手还得传文件。结论是隔夜的改动应该变成一个提交，哪怕信息写”半成品，别合并”。

远端协作的命令

git remote -v 看每个远端名下的读写地址；换地址用 git remote set-url origin <新地址>，它改配置、不动历史，比删了重加安全。git remote show origin 列出哪些本地分支已建立跟踪，排查时比 -v 有用。

fetch 与 pull 的差别：pull 是 fetch 加上把结果合并进当前分支，中间那步合并不是你决定的，而是默认行为。你在本地提交了两个、别人也推了两个，pull 直接把两边并起来，历史里多出一个信息为 Merge branch 'master' of ... 的合并提交，谁都不想为它负责，却要永久留在图上。所以我先 fetch，看一眼 status -sb 的 ahead/behind，再自己决定怎么并——并与变基的语义在变基那篇。

--prune 清掉别人已删分支留下的空引用，可配 remote.origin.prune true 让每次 fetch 自动带上。push -u 建立跟踪，之后裸 git push 和 status -sb 才知道该跟谁比；不带 -u 的裸推送在 Git 2.0 之后按 simple 只推当前分支，而更早的默认会把所有同名分支一起推上去，当年不少”我只想推一个分支”的事故就来自这里。删远端分支用 git push origin --delete <分支>。

标签：git tag -a v1.2.0 -m "发布说明" 打带信息的，-s 那种还要配好签名密钥，团队没签名流程就不必勉强。git push --tags 是风险操作，它把本地所有标签一次推光，包括试手打的和早该删的，而标签推上去得请别人一起清才干净，发布时点名推一个。--follow-tags 只带当前提交可达的标注标签，比 --tags 克制得多。

文件与目录

改名用 git mv 旧 新，移动和更新索引一次做完。即便如此 git blame 在新文件的旧行上还是指向改名之前，查历史要补 --follow，怎么追让变基那篇讲细。

一个极常见的误解：已跟踪的文件事后写进 .gitignore 不会自动停止跟踪，Git 照旧提交它的改动。要让它安静，必须先 --cached、再补忽略条目，顺序反了等于白做。

.gitignore 的写法记四条：开头带 / 只从仓库根算起，末尾的 / 只匹配目录，** 跨任意层，! 取反且写在后面才生效。有个反直觉的边界：父目录整体被忽略时，你没法用 ! 把它里面的某个文件重新包含进来，得先放行目录。怀疑哪条规则在起作用，别靠猜：

-v 的输出指到具体行号，”这文件为什么加不进去”多半当场结案。真要提交被忽略的文件用 git add -f。

排查类命令

只看一段用 git blame -L 10,20 src/list.js，默认 blame 整个文件在长文件里翻不动；加 -w 忽略空白改动，否则一次排版能把整段作者变成格式化的人。想知道这行代码是哪次提交引入或删掉的，用 git log -S 'renderRow' --oneline：它比较这个字符串在改动前后出现的次数，添上和删掉都命中，一条命令同时回答”哪版开始有”和”哪版没了”，再配 -- <路径> 缩小范围。

合并提交的统计输出，当时还没有专门的开关，--stat-with-merges 这类选项尚未出现。看单个合并提交我直接用 git show -m <提交>，它按父提交拆成几段分别给补丁，不够就退回 git diff <提交>^1 <提交>。至于找回被自己删掉的提交，reflog 是唯一入口，动线在变基那篇，本文不重复。

复盘：一次 git add .

去年三月新同事入职第一天，本地跑通之后 git add .、提交、推送，一气呵成。推上来的提交里带着三百多个调试数据文件，还有一整个 node_modules——刚换到 npm 3 的机器装出来的，扁平结构全在仓库根下，上万个文件。仓库体积当场翻几倍，别人拉下来从几秒变几分钟，钩子跑一次像卡死。

处理顺序有讲究：先 git rm -r --cached node_modules 停止跟踪，这一步不动桌面，谁的本地环境都不会塌；再补 .gitignore，把 node_modules/ 和调试数据的目录一起加上；然后提交这个修正，最后才讨论历史要不要洗。洗历史意味着别人已有的克隆全部作废或重走一遍变基，代价远大于一个臃肿仓库；我们没洗，只把提交前先跑一次 status -sb 写进检查清单。

教训不在他手生，而在命令太顺手。add . 的语义是当前目录下所有没被忽略的东西，它默认 .gitignore 已经写全，而这个假设在第一天不可能成立。同样的便宜还有 commit -a：替你省掉一次 add，也替你省掉”这一次该不该带上”的判断。命令很顺手，代价在事后。

速查表

我想干什么 用哪条命令 一句边界
看改动与离上游多远 git status -sb 省掉未跟踪细节
看下次提交会包含什么 git diff --staged 与 --cached 等价
只提交文件里的一部分 git add -p 拆不细就手改补丁
取消暂存但保留改动 git reset HEAD -- <文件> 工作区不动
丢弃工作区改动 git checkout -- <文件> 索引内容覆盖桌面
取回旧版本的文件 git checkout <提交> -- <文件> 落地即已暂存
收走改动、留下暂存 git stash -k 别拿来隔夜存放
应用指定那条不出栈 git stash apply stash@{2} 编号会随栈位移
修正最近一次提交 git commit --amend 推送之前才可以
先看会删掉哪些文件 git clean -dn 未跟踪的删了找不回
只拉不改工作区 git fetch --prune pull 会替你合并
建立跟踪目标 git push -u origin <分支> 裸推送才有依据
停止跟踪但保留文件 git rm --cached <文件> 光写忽略条目没用
查哪条忽略规则生效 git check-ignore -v <文件> 输出带来源行号
找代码何时出现或消失 git log -S '关键字' 引入与删除都命中

小结

这些命令没有一条是新东西，排成动线靠三个判断：改动现在在哪一层（桌面、索引、历史），我想让它去哪一层，这条命令默认会不会替我做第二个动作。diff 的三层、reset 的三档、pull 里藏着的那次合并，问的都是同一件事。配置那部分更像投资：.gitattributes 里钉死一次换行，此后所有人的本地开关都伤不到仓库内容。
