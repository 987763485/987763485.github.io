Git 提交规范与 Conventional Commits

开年这次线上事故复盘，因为有人提交信息里只写了一个 fix，我们靠着 diff 反查了半小时才确认那个修复是哪天上线的。这篇文章要讲的约定式提交格式，就是那场复盘之后我们团队定下来的：<type>(<scope>): <subject>，加上空行、正文和 footer。格式本身是从 AngularJS 仓库的提交信息指南上抄的，我们做了本地化改造，加了几条自己的条款。要说明的是，业界当时还没有把这类写法正式命名为 Conventional Commits，那是未来的事，后来才有人把它整理成规范文本；眼下没有统一标准，这套约定只是我们团队内部的说法，写出来供同样被烂提交记录折磨的人参考。

范围也先划清楚：这篇只谈提交信息本身——格式怎么定、怎么校验、和发布说明与版本号怎么联动。分支模型、变基合并那些是另外的问题，本文不展开。

为什么要在意提交信息

代码自己会讲”怎么实现”，但它永远讲不了”为什么改”。这个为什么，就落在提交信息里。git log 实质上是团队的二手文档：新人接手一个模块，读代码之前先翻 log，想知道这个目录这半年被谁动过、每次动是为了什么。发布前更现实——测试和运营会问”这次到底上了哪些改动”，如果 log 里全是 update，没人答得上来，只能挨个 diff 去问作者。跨人接手时，blame 指到某一行，那一行对应的提交信息就是第一现场，现场写不清，排查的人只能重走一遍你的推理。

五种写法对应三种典型乱象。”update””临时”这类词等于什么都没说，时间隔得久了连作者自己都想不起改了什么；”fix bug”说修了 bug，但 bug 是什么、影响到哪个功能，一概不知；最后那条一整句中文没有主语，三件事挤在一行，想按主题搜索都搜不到。这些提交在写的那一刻只省了十几秒，代价摊在之后每一次发布和排查里。更隐蔽的一层伤害是搜索：git log --grep 按关键词找回调，命中 update 的频率远比你想象的高，等于历史直接不可检索。

边界靠判据而不是感觉：改完之后用户能多做什么，选 feat；本该正确的行为变得正确，选 fix；代码结构变了但外部行为一点没变，才是 refactor。refactor 和 perf 同时出现时按主要目的选一个，别造 perf(refactor) 这种组合。chore 是兜底项，用多了说明前面的类型没想清楚。

scope 是改动落在哪个模块，取值必须有出处：要么是我们约定过的模块清单，要么直接取源码目录下的顶层目录名，禁止自由发挥。同一个模块今天写 order、明天写 订单、后天写 orders，按 scope 过滤 changelog 时就废了。确实一次改动跨了多个模块，允许省略 scope 写成 feat: xxx，但这种情况一周里不该出现几次。

subject 的纪律：动词开头，说”做了什么”而不是”怎么做的”；末尾不带句号；不要写主语，提交信息里没有”我”。长度我们不写死数字，团队口头约定是 git log --oneline 下一屏能看到完整的一句话，超了就是 subject 里塞了正文该干的事。给几个通过和不通过的手感对比：

正文和 footer 各管什么

正文回答的是动机：改之前是什么行为、为什么要改成这样、有没有需要交代的取舍。这些内容不该挤在 header 那一行里，也不该指望 reviewer 去 diff 里考古。写正文时把 header 和被修改文件列表挡住自读一遍，能看懂为什么改，才算合格。

不兼容改动必须显式标记。不管 type 是 feat 还是 refactor，只要这次改动会让老的调用方式失效——比如我们内部组件库某个初始化参数换了含义——正文之后的 footer 段以 BREAKING CHANGE: 开头写清影响面和迁移办法。这个标记是后面所有自动化里权重最高的信号。

footer 另一个用途是挂引用。需求单号走我们内部工单系统的编号，格式团队自己约定，能对上检索就行，不必神话某一种写法；如果代码推到托管平台，Closes #123 这类行能让平台把 issue 和提交关联起来、合入后自动关单。两者都有就各写一行。没有单号的情况宁可省略 footer，也不要编一个看着像的。四条段齐全的一条提交长这样：

校验怎么落地

先分清服务端和本地。本地钩子挂在 .git/hooks 或者用 npm 上的 husky 写进 package.json，体验好，当场就能拦住；但 git commit --no-verify 一秒绕开，心虚的人还会直接改钩子文件，甚至有人从 IDE 的提交面板走快捷提交根本不经过编辑器。服务端的 pre-receive 钩子在 push 时整批检查提交信息，不合格的推送整个拒掉，这是底线，绕不开。服务端那份脚本要注意两件事：一是推送可能一次带来几十个提交，得按区间逐个校验而不是只看最新一条；二是拿到的原始信息里夹着以 # 开头的注释行和 diff 统计，解析前先剥掉，否则误杀率很高。本地负责快速纠偏，服务端负责兜底，只装一头都会漏。

和版本号的联动

规则本身很简单：footer 里带 BREAKING CHANGE: 的提交走主版本，哪怕它只有一个；有 feat 没破坏性变更走次版本；全是 fix 和 chores 走补丁版本。一次发布里多个类型同时出现时按破坏性 > feat > fix 的优先级取最高档，这条判断链要在发版文档里写死，不然每次都要现场辩论。麻烦不在规则在执行——提交时没人能替你判断某个 feat 到底破不破坏兼容，所以落地方式是一半工具一半人：工具按标记聚合出建议版本号，发版前的短会上由发布人对照 changelog 草案拍板。标记漏写了，代价就是版本号骗人，这个锅没有任何工具能替你背。

几个边界问题的结论

历史提交怎么办？ 不改。重写全仓库历史会让所有人重新 clone，收益配不上动静。规范从下一个版本标签起对新提交生效，老 log 该烂继续烂，changelog 生成器配置起始标签即可。

中英文混排怎么办？ 我们定的口径是 header 的 type、scope 必须英文（正则只认英文枚举），subject 用中文写——团队工作语言是中文，硬憋英文句子只会写出 nobody fix some bug 这种双输。scope 用英文模块名，中文模块名进不了工具链。

美术切图和配置文件算不算 chore？ 纯静态资源替换、构建配置、依赖升降级，chore 没问题。但美术资源如果是新功能的一部分——比如活动页整套视觉——跟着功能提交走 feat，scope 指向那个活动模块，别把它拆成孤零零一条 chore，changelog 里看不到它。

临时调试提交怎么处理？ 加 log、改回再改好的那种碎提交，结论是不允许单独进主干：和功能提交合并成一条合规信息之后再推。具体怎么合并历史是分支管理那篇文章的事，本文只管标准——进了 master 的每一行 log 都得经得起上面那套正则。

合并提交和回滚提交算不算违规？ 托管平台自动生成的 Merge branch ... 这类合并提交在校验脚本里直接放行（按两个父提交的特征识别），强令所有人改写默认信息是自找麻烦。回滚优先用 git revert 生成的记录，它的固定格式加进白名单；手工写的回滚按 fix 记，正文必须写清回滚了哪一条提交、为什么回滚。

改了别人写的规范外代码顺手补齐怎么办？ 顺手把相邻代码改成合规格式属于 style，单独一条提交，别夹在 feat 里——这条纪律和格式本身同样重要，diff 里混进几十行无关格式变更是评审时最容易吵起来的场景。

落地遇到的阻力

实话实说，推这个格式遇到的第一反应是”写个提交还要填格式，浪费时间”。我们的处理是三步降级。第一步只强制 feat 和 fix 两类，其余类型随便用甚至不用，先把”header 有一行结构”的习惯立起来；第二步钩子只 warn 不阻断，跑两周，让不规范的信息在终端里刷脸熟，两周后才切 exit 1；第三步把格式模板塞进提交编辑器的默认内容，git config commit.template 指到一个写好注释的模板文件，鼠标一划就能看见每段该填什么。

另一类阻力是 review 时靠人肉提醒，谁想起来谁说一句，既不可持续也伤感情，这也是校验脚本必须存在的原因——机器说”不合格”没有情绪成本。需求单号拿不到时的降级口径单独强调一遍：省略 footer，绝不编造，宁可让 changelog 里少一条引用线索。

复盘那一夜值回票价

回到开头那次事故。线上问题确认后，要回答”这个修复是哪天上的、上线时带着什么改动一起来的”，log 里只有 fix 一个词，时间线对不上发布标签。我们几个人对着两个文件反查 diff，从修改痕迹猜意图，来回核了半小时才确认这个修复当时是搭在另一个功能提交里一起进的分支——这正是乱象的完整形态：一条提交干了两件事，两件都没说清。复盘会开到后半程没人再觉得格式是形式主义，约定式提交就是那晚定下来的。第二天我们把钩子脚本挂上仓库，先 warn 后阻断的节奏也从这里开始。一条规范的提交信息平时看不见收益，它只在最贵的那一刻付账；平时每条写足，关键时刻整个 log 都会替你回答。

提交信息自查表

格式不是给审核的人添堵，是给三个月后的自己和接手的同事留一份能读的账本。仓库规模到一定量级之后，提交信息就是团队之间唯一稳定的通信协议，我们定得晚，不如定得糙但今天就开始。
