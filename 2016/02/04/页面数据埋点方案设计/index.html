页面数据埋点方案设计

埋点不是”在代码里塞几个上报调用”，它是数据口径的设计工作。去年给一个导购页加埋点，产品同学说了句”把点击都记下来”，前端就对着每个可点元素补了几十个调用，字段想怎么写就怎么写。三个月后做来源归因，发现同一个”点击”有四种记法，有的带商品编号，有的只有中文描述，数据基本没法用，只能推倒重来。

今年我把埋点从头梳理了一遍：先确定要回答什么问题，再反推字段，然后才轮到 SDK 和上报链路。代码都是 ES5 风格，可以直接往下抄。上报通道的取舍在另一篇错误监控的文章里已经对比过，这里只讲埋点特有的部分。

先分类问题：埋点要回答什么

我现在的习惯是先问一句”这条数据将来会被谁、用什么方式查出来”，答不上来的埋点一律不加。按用途分，页面数据要回答的问题就三类。

第一类是流量与来源：页面多少人看过、多少人第一次来、从哪个页面哪个位置点进来。最小字段集是页面标识、会话、来源地址、渠道参数，它决定 PV/UV 和来源路径的口径，是所有分析的底座。

第二类是行为：点了哪个按钮、列表滚到多深、在某个模块前停留多久。这类问题必须具体到业务模块去问”我想知道用户在这块干了什么”，字段最杂，是命名规范失守的重灾区。

第三类是转化漏斗：从看到商品到下单，每一步走完多少人、流失在哪一步。它最难，因为漏斗要把同一个人按顺序的一组事件串起来，用户标识、时间戳口径、步骤定义全被绑上来。

三类问题字段侧重完全不同：流量类吃环境信息，行为类吃元素信息，漏斗类吃标识与时序。先分清问题再定字段，能挡掉一大半”为采集而采集”的冲动需求。

三条实现路线的取舍

确定了要采什么，下一层是怎么采。可行的路线我收敛成三条，团队按场景挑，不搞全站一刀切。

第一条是代码埋点：在业务逻辑里显式调用上报函数。好处是字段可控、语义精准，比如”加入购物车”，前端明确知道接口成功后才算有效事件，就能把商品编号、价格、接口结果一起带上。代价是加埋点要改代码发版，周期长，且散落在业务代码里没人能一眼看全。

第二条是标记埋点：在 HTML 元素上挂 data-* 属性声明”这是什么”，由一层事件代理统一采集。比如给可点元素挂 data-track 和 data-item-id，在容器上监听点击，从 e.target 向上找最近的带声明属性的元素，读属性拼事件。UI 和数据口径绑在同一处，加埋点改的是模板不是逻辑，验收对着 DOM 就能查。代价是只能采到”点了什么”，接口成败之类的语义还得回代码埋点补。

第三条是全量录制：前端不做筛选，把点击、输入焦点、滚动原样录下来发出去，分析时再定义事件。这在当时是刚出现的思路，但流量和存储成本高，输入焦点的录制直接踩隐私红线，原始流也没有业务语义，商品编号还得离线反查拼接。我们只在内部工具上试水，业务线没推。

路线 字段能力 改动成本 覆盖方式 主要风险
代码埋点 最强，可带业务上下文 改逻辑、发版 逐个补，易漏 散落难维护
标记埋点 限于元素静态信息 改模板属性 代理统一收，不易漏 语义深度不够
全量录制 只有原始交互 接入一次 天然全覆盖 成本、隐私、无语义

我们的组合是：曝光和点击默认走标记埋点，转化类事件走代码埋点，录制定期小范围开着，校对前两条漏了什么。

数据模型：一条埋点事件的解剖

这就是整套方案的骨架。一条上报数据拆成五个层面，每个层面先把口径钉死。

事件是数据的行。每个事件必须有全局唯一的英文标识、能读懂的中文名、精确的触发时机定义、以及版本号。时机要写到没有歧义：”点击收藏按钮”和”收藏接口返回成功”是两个事件，不能都叫 collect。版本号是为字段变更准备的：同一标识下 v1 与 v2 的属性集可以不同，分析侧按版本分桶，新旧数据不会混算。

属性是事件的列。每个属性登记三样：类型（字符串、整数、布尔、金额一律带单位）、是否必填、枚举值列表。价格和库存必须写清单位，”元”还是”分”混过一次，漏斗金额就能差一百倍。枚举属性禁止开放填写，新增枚举值等同于改表结构，要走评审。

主体回答”这是谁”。登录用户有用户 ID，未登录访客只有存在 cookie 里的匿名 ID。核心口径是归一：用户登录后，把这台设备的匿名 ID 和行为绑到用户 ID 名下，服务端维护映射表。这一步不做，漏斗里登录前后的行为串不起来，UV 和转化率都会虚。

会话回答”这算一次访问吗”。当时没有现成标准，我们用时间间隔切：同一主体两次事件间隔超过三十分钟判为新会话，生成会话 ID 写进 cookie。口径朴素，但必须全团队只有一份，写进字典，不允许各业务自己定。

环境是每条事件的公共前缀：UA、屏幕宽高、设备像素比、referrer、页面路径、会话与主体标识，由 SDK 自动带，业务代码一行不写。

命名与字段字典

模型定了，接下来是让它三年不烂的东西：命名约定和字典维护流程。

事件名统一小写下划线，结构是”模块_对象_动作”或”对象_动作”，动作放最后且用固定动词表：view、click、submit、success、fail。这样事件列表按对象聚类、按动作排序，一眼能扫。禁止中文事件名——上报时标识要拼进 URL；也禁止拼音缩写，cn_gwc_btn 这种东西半年后没人猜得出是”国内购物车按钮”。

字典是全组的一份共享文档，每个事件、每个属性都要在里面有一条记录才能上线。三条硬规矩：字段类型变更、属性删除、枚举加值必须走评审，因为下游报表在按老口径算；埋点清单作为需求交付物和页面功能一起验收，谁提的需求谁登记、谁维护，人员流动时交接的就是这份清单；QA 的测试用例里包含”该触发的触发几次、不该触发的有没有触发”。填完清单才准开工，大半冲动需求死在这一步。

SDK 设计：入口、队列与兜底

对外只有一个入口：track(event, props)，业务代码只见这一个函数，环境字段、标识补齐、队列管理全在 SDK 内部。

事件先进内存队列，不是一条一报。flush 条件有三：队列够条数、超时、页面即将卸载，卸载时残留立刻发出。每条事件生成”时间戳加自增序号”的唯一 ID，服务端按 ID 去重，重试造成的重复上报就能被吃掉。

send 的实现就是打点请求，GET 与 POST 的边界另一篇已经说过，这里不展开。要说的是失败兜底：请求失败时把这批事件写进 localStorage 的固定键，下次初始化读回来重新入队。要防两件事——localStorage 有容量红线，兜底队列设条数上限，装满丢最老的；无痕模式里它直接抛异常，读写必须 try/catch，埋点不能把页面带崩。cookie 随每个请求上行，只放标识类小字段，不放事件正文。

再留一个采样率开关：初始化时可传百分比，按匿名 ID 哈希分桶决定这个用户的事件发不发。大流量页面全量入库撑不住存储，客户端采样比服务端丢弃省事，口径要提前和看报表的人讲清楚。

曝光的触发条件是元素进入视口。当时没有标准化的可见性回调，做法是滚动加位置计算：监听 scroll 并节流，用 getBoundingClientRect 判断元素相对视口的位置，露出超过一半才算曝光，每个元素一个会话只记一次。文档级可见性用 document.visibilityState，2016 年初只有部分浏览器支持，检测不到就降级用 onload 加窗口焦点事件近似。

位置类数据：坑位与滚动深度

列表页的行为分析离不开”第几个位置”。约定是给每个列表项挂齐 data-item-id 和 data-index，index 由模板渲染时写入而不是采集时数 DOM——异步补位、分页追加都会让序号漂移。点击代理把命中元素的 id 和 index 原样进属性，坑位效果按 index 分组算。

滚动深度不采连续值，采分段阈值：25%、50%、75%、100% 四档，跨过一档补一条事件。连续值要高频上报、灌满队列，也没法直接聚合；分析侧要的是”多少人看到底部”这类分档结论，阈值法一条事件对应一个结论。实现上只发新跨过的档位，回滚不重发。

上报的边界

通道本身的选择另一篇已经讲透，这里只留埋点特有的几条。其一，GET 打点走查询串，批量后的 payload 比错误上报长得多，来源地址与商品编号一拼就顶到上限，所以要预设字段裁剪顺序：先砍可选环境字段，再截长文本，标识和核心属性永远保。其二，批量接收接口只回 204，不写响应体，回执靠服务端对账。其三，时间戳双写：客户端时钟漂移普遍存在，纯按客户端时间排序会把”先进页再下单”排成倒序，漏斗乱掉；但同一会话内的事件间隔又只有客户端时间能表达，所以顺序以服务端接收时间为准、间隔用客户端时间。最后一条红线：用户输入的内容一律不原样上报，字典里没登记为必填的文本字段一概不发；确有分析价值的，截断并过敏感处理才允许进队列。

上线前的验收

埋点验收手段很原始：真机挂代理抓包，对着页面操作，逐条核对请求里的触发次数和字段值；抓包姿势去年十一月那篇实践文章写过，不赘。每个需求配一张自测清单，盯三类情况：不该触发的场景有没有触发（如禁用态按钮）、一次操作有没有重复触发、单页应用局部刷新时曝光有没有重算——Backbone 那类路由切换不会重新走 onload，页面级 view 事件要在路由钩子里手动补，或按路由算一次。字段废弃走登记不走删除：字典里标记废弃日期，确认没有报表引用后 SDK 才停发。

复盘：一次虚高的活动页转化率

有个活动页报表里”点击领券”到”领券成功”的转化率好得反常，查出两个洞叠在一起。一是点击埋点绑在卡片容器上，内部按钮的点击冒泡后又触发容器处理器，一次真实点击上报两条；二是后续 tab 被预加载进 DOM 但默认隐藏，一进页面所有 tab 的曝光埋点全触发，分母虚高。修法三条：容器处理器校验事件目标，冒泡链上只认最里层一个声明节点；曝光判定加可见性检查，宽高为零或不可见的排除；SDK 加去重窗口，一秒内同主体同事件同元素只留第一条。

埋点需求交付模板

方案讲完，落到协作层面就是一张表。提埋点需求必须按模板填，前端照表实现，QA 照表验收，字典照表登记。

栏目 填写要求
事件标识 英文小写下划线，全局唯一
中文名 业务同学能读懂的动作描述
触发时机 精确到接口成功或失败，不留歧义
属性列表 每个属性带类型、必填性、单位或枚举值
验收方式 触发次数预期、抓包核对项、自测清单条目
负责人 提出人即维护人，变更由同一人登记

这张表看着像形式主义，实际是把数据口径从口头默契变成签字文档。埋点方案的成败从来不在那几十行 SDK 代码，而在半年后还有人能对着字典说清每个数字是怎么来的。
