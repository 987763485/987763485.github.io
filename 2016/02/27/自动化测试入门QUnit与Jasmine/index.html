自动化测试入门：QUnit 与 Jasmine

我写 jQuery 写了两年多，第一次认真往前端测试里钻，是被一个插件坑的。我给一个滚动加载插件加了两个配置项，在浏览器里手点一遍，看着都对；上线第二天运营反馈另一个页面的初始化没生效。我所谓”测过了”，其实就是把最容易的一条路径走了一次。后来我才明白这不叫测试，叫刷新页面。

这篇把 QUnit 与 Jasmine 这两套当时都在用的框架摆在一起比：断言怎么写、异步怎么等、替身能力谁强，再讲怎么从双击就能打开的测试页面走到能在无人值守下跑的形态。读者默认跟我当时一样：写过 jQuery，从没写过测试。模块加载体系另有专文，构建与产物优化不在这篇的边界里，npm scripts 里加一条 test 命令只是顺手的事，不展开。

先承认难：前端测试为什么落不了地

后端的函数进参数出返回值，断言把输入输出锁死就完事。前端难落地有三个原因，全是我当时撞上的。一是可测的东西被 DOM 与浏览器行为绑住：方法的返回值常常要等元素渲染完、事件回调跑完才拿得到，你得先给测试搭一小块真实页面。二是需求变更快：上周定的交互这周改版，跟着改用例的成本肉眼可见，很多人就是在这一步收手的。三是断言写得脆：顺手把具体 class 名、按钮文案、提示语钉进断言，改版即红灯，用例从保险丝变成绊马索。

起步策略我给一条，按可测性从易到难排：先测纯函数与工具方法——格式化、校验、计算这类不碰 DOM 的代码，占业务逻辑的大头，回归价值最高；再测状态机式的交互——展开收起、选中未选中、加载中到完成，断言状态流转，不碰渲染细节；最后才碰渲染——真要钉 DOM 结构，也用夹具圈出一小块来钉。第一步收益最高：纯函数连浏览器都不需要，写起来跟后端一样干脆。

分层的现实边界：三级台阶，多数团队停在第一级

文档里测试分层总画成三级台阶：函数与模块级的单元测试；页面级集成——把几个模块拼起来在浏览器里跑一遍真实交互；真机与多浏览器兼容。现实里这三级的边界很硬。第一级只要一个 JS 文件加几行断言；第二级要处理异步、事件绑定、DOM 夹具，成本立刻上一个台阶；第三级拼的是你装了几个浏览器、手边有几台手机，跟测试框架关系已经不大。

2016 年这会儿，多数团队——包括我待过的——就是停在第一层：把纯函数和工具方法的回归网织起来，页面级交互靠人工点关键路径，兼容性交给测试同事的机器清单。这不是偷懒，是投入产出比：第一层的用例跑得快、失败得准，维护成本几乎不随项目规模涨；越往上走，环境抖动的假红灯越多，人很快就不信红灯。认清自己停在哪一层，比照着文章把三层都铺一遍重要得多。

QUnit：从 test 到 assert.async

QUnit 是跟 jQuery 同源长出来的测试框架，jQuery 自己的测试代码就是它最好的说明书，当时在用的是 1.x 这一系列。最小单元是 test()：第一个参数是给人读的用例名，第二个参数收一个测试函数，断言全挂在传进来的 assert 对象上。

断言这组 API 里要说清四个的分别。ok 只验真值；equal 严格相等，比标量用它，assert.equal({}, {}) 永远红；对象和数组的结构对比要交给 deepEqual，它递归逐层比；propEqual 同样比对象，但只认自身属性、不算原型链继承来的，验字面量构造出来的结果更严。expect(n) 写在函数开头，声明这条用例该执行几条断言，条件分支多的时候防漏跑——断言数不够，用例直接判失败。

异步是显式的：assert.async() 返回一个 done 函数，回调里调它才算这条跑完。旧的 stop() / start() 当时也还在大量文档和代码里并存，语义一样：告诉 QUnit 别急着收尾。

组织用例靠 module：一个 module 圈一组用例，moduleStart / moduleDone 两个钩子在每条用例前后执行，用来搭环境、打扫战场。DOM 夹具的位置是写死的：页面里放一个 id 为 qunit-fixture 的容器，QUnit 在每条用例之间把它还原成初始内容，用例往里怎么折腾都互不污染——这直接解决了”上一条用例留了脏东西”这个最恼人的问题。跟 jQuery 插件一起测是它的甜区：runner 页面里依次引入 jquery、qunit、插件源码，把要挂插件的 markup 写进 fixture，用例对 fixture 里查出来的元素调插件方法，断言插件挂上去的数据或切换后的状态。

Jasmine：把用例当句子读

Jasmine 当时在 2.x 这一系列，走 BDD 路线：describe 聚合一组相关行为，it 描述一条具体行为，用例名写成 should 开头的句子，读起来像需求文档。断言不从参数进来，直接在函数体里 expect 一个值，再链上想验的方法。

toEqual 做结构比较，对应 QUnit 的 deepEqual；toBe 是同一性比较，数字、布尔这类场景用它；toMatch 拿正则验字符串；toBeTruthy 只问真值，用在”存在即可”的场合，别拿它当相等用。beforeEach / afterEach 在每条 it 前后各跑一次，夹具和对象重建放这里，别在每条用例开头重复。内置 matcher 不够用时可以自己注册：比较逻辑写成函数，交给 jasmine.addMatchers，失败消息自己措辞——但先想清楚是不是真缺。

Jasmine 真正的杀手锏是替身。jasmine.createSpy 凭空造一个能记录调用的函数，spyOn 把已有对象上的方法偷梁换柱，之后能断言它被调了几次、参数是什么，再用 and.callFake 换上假实现。and.returnValue 这个取固定返回值的写法，我当时用的 2.x 上已经有了，但不少老文档和从 1.x 迁过来的代码还在写 andCallFake 那种旧形式，版本一多容易踩混——我的习惯是不管哪版统一用 and.callFake 返回常量，这个形态新旧都认，不赌版本。

还有一块必须靠框架本身：时间。jasmine.clock() 能把时钟冻住，install 之后 setTimeout 不再走真实时间，tick(n) 手动推进 n 毫秒、到点的回调立刻执行——setTimeout 节流、debounce 到底有没有生效，从”等一秒”变成一条断言。异步用例直接给 it 的函数加 done 形参，Jasmine 见到带形参就等 done，跟 assert.async 一个意思。

两套并排：差异在哪，我怎么选

对比轴 QUnit 1.x Jasmine 2.x
断言风格 assert 对象逐个调用，直白 expect 链式，读起来像句子
异步处理 assert.async 拿 done，旧 stop/start 并存 it 形参直接要 done
函数替身 无内置 spy，手工替换或配 sinon createSpy / spyOn 内置
与 jQuery 生态 同源，fixture 直接伺候插件测试 中立，靠自身 beforeEach 夹具
失败输出 简洁，指到具体断言行 详细，带整句行为描述
CI 报告形态 reporter 选择相对少 第三方 reporter 更全

结论：给 jQuery 插件写测试，QUnit 更顺——fixture 自动还原、和 jquery 同屏、上手没有仪式；想把用例当文档读、交互逻辑大量依赖”某个函数被没被调用”，选 Jasmine，替身内置、BDD 命名直接可读。也有人用 Mocha 配别的断言库，本文不铺开。

怎么跑：从双击页面开始，到无人值守

当时最常见的起步方式是一个静态 runner 页面：普通 HTML，把 QUnit 的样式与脚本、被测源码、spec 文件依次用 <script> 引进来，双击在浏览器打开就有一屏绿。它的价值不在自动化，在于把写测试的成本降到跟写脚本一样——很多人第一步就卡在仪式感上，先绕过它。

把这套东西搬到浏览器外面执行的 runner 脚本各家都有，我不点名，按类别统称。真正要分清的是：能在浏览器里跑，不等于能在无人值守下跑。前者是人盯着的验收；后者要求启动浏览器、执行 spec、把结果吐成机器可读的形式、失败时以非零状态退出——这四件事缺一条，流水线都接不上。

Karma：把”跑测试”外包给一份配置

Karma 当时在 0.13 这一代，解决的正好是上面那句话：它启动真实浏览器或无头浏览器（PhantomJS 是当时的主流搭配）执行 spec，产出可被 CI 消费的结果，失败让命令返回非零。配置文件里最常动的是四个字段：files 列出喂给浏览器的源码与 spec 及加载顺序，browsers 声明用哪些浏览器跑，reporters 决定结果长什么样、落到哪，singleRun 控制跑一次退出还是守着不退出。

junit 这类 reporter 把结果落成通用 XML，CI 平台普遍认它，这是”可被消费”的关键一环。本地开发把 singleRun 关、autoWatch 开，改一次源码刷一次结果。多浏览器同跑是招牌，我的现实用法是 CI 只留一个无头浏览器，多浏览器验证发版前手动拉一轮。

覆盖率：报告容易，有效断言难

覆盖率当时靠 Istanbul 这个量级的工具出报告，Karma 侧装个插件就能统计每份源码的行与分支。它能回答”哪些代码测试根本没碰到”，这在老项目里是真问题。但它回答不了”断言有没有效”：一条只写 ok(true) 的用例照样把整个函数标绿。我见过一个模块覆盖率报得好看，改配置项照样漏测，因为用例全走默认值那条路，分支统计只算了走没走过。

所以我把报告当清单用：先看关键分支有没有对应用例，再看每修一个 bug 有没有补一条回归用例，这两条比总数字更能预测它拦不拦得住事故。至于把覆盖率卡成门禁——阈值这类选项当时还很粗糙，多半要自己写脚本读报告再判，别一上来就定 90%。

mock 后端：拦截请求，或者干脆不依赖它

接口没好或返回不稳定，测试得自己造后端。一条路是用 sinon 1.x 的假请求：useFakeXMLHttpRequest 把浏览器的请求对象换成假的，拦下请求返回预设响应；日常更省事的是 sandbox，假请求、假定时器、spy 用完 restore 一把清干净。

另一条路更稳：把数据访问抽成可注入的函数，测试时传一个返回固定数据的假函数进去，压根不碰网络层。它不依赖浏览器内部实现，出错堆栈短、看得懂；拦截那条一旦和别的库同时动 XMLHttpRequest，排查费劲。但被测代码自己发请求、你又改不了它的构造方式时，只有拦这一条可走。

复盘：三百多条用例，半年后没人跑

前年接手一个项目，测试目录下躺了三百多条 QUnit 用例，半年没人跑。翻下去看，病因全写在断言里：按钮 class 名叫 price-btn-red，文案”立即抢购”钉死在 expect 里——改版时样式和文案一起换，一屏红灯，没人修，于是没人跑。

修法四条。只断言行为与状态：点完加购数量该变 1、库存为零该不可点，不碰 class 与文案；易变文案集中放常量文件，页面和 spec 同取一份。红灯当天处理：要么是代码错，要么用例过期，过期就改断言或直接删用例，隔夜的红灯会让人学会无视一切非绿色。CI 只跑快的那批：纯函数与状态类用例每次提交都跑，碰 DOM 的慢批次每天夜里一轮。新 bug 必补一条用例，这是最便宜的补网方式。半年后用例反而删到两百出头，剩下每一条我都敢信。

结尾：从零起步的五步

一、挑一个纯函数模块。判据：读它的源码不需要浏览器里任何全局。二、项目根建 test/spec 目录。判据：往里放文件这件事不让你多想一步。三、做一个静态 runner 页面，跑通第一条断言。判据：双击打开能看到一条绿色。四、接 runner。判据：断言失败时命令行的返回码非零。五、进 CI。判据：第二天早上你没开浏览器，也知道昨晚红没红。

五步走完再谈覆盖率、多浏览器和门禁；顺序反过来，多半是配置调两天、用例写三条，然后继续刷新页面。
