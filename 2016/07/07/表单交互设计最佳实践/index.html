表单交互设计最佳实践

先把边界说清楚，免得跟仓库里另外几篇打架。input 类型清单、required、pattern 这些原生属性和 ValidityState 那堆成员，《HTML5 表单新增 input 类型与校验属性详解》已经列全，我不重抄；jQuery 取值、勾选联动、提交完整流程，《表单元素操作与表单验证实战》讲过，也不重讲；input 与 propertychange 的兼容差异，那篇实时监听一句话就能引用。这篇只写改版时定的规矩和落到代码上的那几行。

从一次报名表的抓瞎说起

2016 年 6 月末，市场部临时塞过来一个活动报名表，七个字段：姓名、手机、邮箱、公司、职位、参会人数、验证码。上线第二天后台只收到 200 多条，客服那边却说”一半人打电话讲提交没反应”。我们把手机和办公网都接上，Safari 和 Chrome 各跑一遍，又录下操作扒开看，才找到三个断点。第一个在报错：邮箱写错后红字贴在输入框下面，可它在首屏之外，一滚就看不见，用户以为页面卡住直接退出。第二个在提交按钮：按下毫无变化，弱网下请求转四五秒才回，用户以为没点上又戳两下，后台就进了两条重复数据。第三个在验证码倒计时：有人把页面切到微信里另一个会话再回来，倒计时归零了重发按钮却是灰的——那台是 Android 4.4 自带 WebView，Chromium 33 一线。

这三个断点没一个是因为缺了哪个 HTML5 属性，全是交互上没替用户想下一步。

校验时机：我们定的三条规矩

校验时机是这篇的核心，早报错和晚报错都烦，中间那个点得靠约定。

先看三种时机会造成什么打扰。blur 校验容易被做过头：邮箱没写完、光标移开就被红字怼回来。输入中校验更吵，每敲一个字符跑一遍正则，刚敲到 y@gm 就标红，纯噪音。提交时全量校验看着省事，可一旦有错，用户得从顶部挨个扒开找，找不着就以为提交坏了。

我们最后定的三条规矩：

  1. 第一次离焦才报错。focus 期间怎么写都不标红，blur 落定才校验，把打扰压到切字段那一刻。
  2. 报错后改成边输边清错。字段已处错误态时不再重复标错，每次输入查一次，写对了立刻撤掉红字，不用等离焦。
  3. 提交时全量校验并滚到第一个错处。点提交跑一遍整个表单，有错就定位第一个出错字段并聚焦，绝不让用户自己找。

错误文案的写法纪律

报错文案最容易写飘。规矩是每句都得让用户知道下一步做什么，而不是只宣布”你错了”。下面几行是那次改版前后对照，含糊那列全是当时写在页面上的。

含糊文案 我们改成什么 为什么
输入有误 手机号是 11 位，你写了 10 位 告诉用户差在哪，他才知道补一位
格式不正确 邮箱里没写 @，检查一下 “格式”太抽象，直接点名缺的符号
该字段为必填项 这一栏要填，不能空着 机器话换成人事，去掉”字段”
验证失败 验证码不对，注意区分数字 0 和字母 O 给出最常见的错法，用户能自查
系统繁忙，请稍后再试 没提交上，你的内容还在，点一下再发 明确数据没丢，并给出重试动作
密码强度不够 再加一个数字或符号，别全是字母 说清”怎么才算够”，不是再猜

服务端错误码别原样吐到界面上，code: 4002 这种用户一头雾水，做个薄映射表，映射不了的兜底成”没提交上，点一下再发”。

必填与选填的标注取舍

七个字段里真必填的只有四个。我们定的规矩：必填不打星号，选填在 label 后补”（选填）”。星号遍地等于没有星号，一屏六个红星看着就累。

label 绝对不能省。很多人图省事把 label 写成 placeholder，placeholder 一输入就消失，用户填到一半忘了那栏要写什么。

点 label 能聚焦输入框靠 for 指向 id：

坑在两个地方。一个是 for 和 id 对不上，或页面有多个同名 id，点了没反应——分步表单把几步拼一起最容易撞 id，后来给每步 id 加了步号前缀。另一个更隐蔽：label 上盖了绝对定位的东西，比如装饰图标或透明遮罩，看着点的是 label 其实点到遮罩，聚焦不动。处理要么给遮罩 pointer-events:none，要么在 label 的 click 里手动 focus。

移动端键盘与输入辅助

type 换键盘这事，当期得按”哪些真能换、哪些换了没用”看，不能推广成结论。手机号 tel 能换数字键盘但不校验，字母组合也照样过，所以自己补长度检查；邮箱 email 多数浏览器能换出带 @ 的键盘，原生校验在旧 WebView 上残缺。

number 是踩坑后从人数两栏撤掉的：小数、负号、科学计数写法都躲不掉，步进小箭头误点还会悄悄改值。人数退回 tel 配数字键盘再加一道 JS 只留数字，反而干净。

autocomplete 当期能用，off/on 和最基础的 name 值稳，后面细分新值别指望。autocorrect、autocapitalize 这类非标准属性 iOS Safari 上会听话关首字母大写，微信内浏览器和旧安卓 WebView 基本当没看见——按我们手头这台是这样。

长表单的分步与草稿

字段一多，我们按”用户会不会在这里停一下”切步骤，不按后台表结构切。报名切三步：是谁、怎么联系、确认信息。某一步当场答不上来、要去翻或问人，就该拆，让他带草稿走人，比堆一屏里劝退强。

更要紧的是哪些字段绝不该进本地存储。身份证、验证码、银行卡、密码这类明文一律不落 localStorage，它明文可读，共用电脑或扒开缓存就能看到；真要跨步骤保持就留在内存变量里，提交前才发出去。当时没更稳的端上加密手段，能做的基本就是不存。

提交体验：按钮到底怎么点

提交按钮最后选了”按下变 loading 文案”，没选”一直置灰”。置灰的问题是用户不知道能不能点、为什么不能点，校验还没跑时一个灰按钮配一堆没标红的字段，纯粹让人心里没底。

防重复提交上了三道，每道都有失效场景。第一道，点下去把按钮 disabled 改文案，挡住手滑连点，但挡不住回车抢先提交，也挡不住拿到 focus 后连按空格。第二道，加标志位，请求没回来直接 return：

第三道是弱网。前两道都在前端，弱网下请求迟迟不回，用户等得不耐烦刷新重填再交一遍，服务端照样进重复数据——这个前端拦不住，只能求后端在 POST 带一个提交令牌做幂等。

submit 事件和回车提交的关系得盯住：表单里只要有能提交的按钮和输入框，输入框按回车就触发 submit，它绕开按钮 click。所以校验和防重逻辑全挂在 submit 上，不只挂按钮点击，否则回车就成了漏网的口子。

颜色不能只靠红色。红色对色盲不友好，投影仪一打还发灰。错误除了变红，还要加文字前缀或当期常用的字体图标，让人不靠颜色也能看出”这栏不对”。移动端另外定了两个数：输入字号和可点区域按切图标注留够，别让用户戳半天戳不中。

空值与默认值

日期该不该默认填当天，最后选不填。看着省事实际坑人：用户没注意，默认值直接交上去，后台进来一堆同一天报名。默认值只在”绝大多数人就是这个答案”时才用，否则宁可空着、逼用户看一眼。

下拉首项统一写成一句要用户动作的话，比如”请选择参会身份”，而不是让第一个真选项顶着。要点是首项 value 必须是空串，校验才能认出”还没选”。

一次改版复盘

三条规矩里第一条定错了。”第一次离焦才报错”听着稳妥，实际卡在手机号那栏：很多人手机号一次性粘进去、没敲完就 Tab 走，离焦瞬间被标红”位数不对”，可他压根没填完。后来把手机号改成”写完 11 位才校验”，明显没写完时先不报错，等位数够或点提交再判——规矩得按字段输入方式细分，不能一刀切。

下表是那版”字段—交互决定—当期谁不支持”的对照：

字段 交互决定 当期谁不支持
邮箱 离焦宽松校验，报错后边输边清 IE 原生校验残缺，微信内浏览器
手机号 tel 换键盘，改”满位才校验” tel 不校验，得自己补
参会人数 撤掉 number，退回数字键盘 部分输入法小数/步进误触
验证码 记结束时刻，切回来重算 旧安卓 WebView 后台挂起走偏
底部提交栏 聚焦时收起、失焦恢复 各机型推屏量不一致

贴在需求评审里的检查清单

下次评审直接照着打勾。

  1. 每个必填项能不能一句话说清”不填会怎样”，报错文案有没有写明下一步动作。
  2. 校验时机是不是”首次离焦报错、报错后边输边清、提交全量并滚到第一个错处”。
  3. 错误除了变红，有没有第二个非颜色信号（文字前缀或字体图标）。
  4. 每个 label 的 for 有没有对上唯一 id，绝对定位的东西有没有挡住点击。
  5. 手机号、邮箱换键盘后，自己那套校验有没有补上。
  6. iOS 拉出键盘，最下面一栏还看不看得见，固定底栏会不会挡住输入。
  7. 提交按钮走的是 loading 文案还是灰按钮，回车这条路径能不能绕开防重。
  8. 验证码倒计时切页面再回来还对不对，服务端没回执时重发按住了没有。
  9. 身份证、验证码这类敏感字段确认没进 localStorage，草稿有过期时间。
  10. 日期、下拉的默认值是不是逼用户看过一眼，而不是悄悄替人选了。

清单能全打勾，交互上基本不会出大乱子。剩下的坑，等真机跑一遍才知道。
