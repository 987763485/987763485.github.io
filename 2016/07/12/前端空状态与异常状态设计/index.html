前端空状态与异常状态设计

那天早上，订单列表页什么都没有

2016 年 7 月 5 号上午，客服转来一个投诉：一个商户老板说我们后台挂了，订单页打开是一片白，一条单子都看不到。我第一反应是不可能，前一晚还在测试环境跑过一遍。但截图确实摆在那儿，表头下面一块白，连个报错都没有。

扒开看，请求是成功的，返回 200，data 是个空数组。真实原因是他上午手滑，把时间筛成”今天”、状态筛成”已取消”，而他当天确实没有取消单，页面就把这块白给了他。在他看来”什么都没有”和”服务打挂了”是同一件事，页面没给任何一句话来推翻这个判断。那天改了六处代码，但真正值得记的是：我们压根没把”这个页面能有几种状态”当成一个需要设计的东西。

先说边界：这篇只讲状态的枚举、判定优先级和代码分工，不讲视觉。loading 动效与骨架屏的 CSS 写法，讲 CSS 实现那篇已经写透了，这里一行动画代码都不贴；错误的采集与上报，讲监控那篇讲过了，不重讲。示例按当时最土的 ES5 回调写。

把状态拆开：一个列表页到底有几种

我们最后定了六个分支：

  1. 首次加载中：请求发出去了，还没有可展示的结果。
  2. 加载失败：传输层出问题，超时、5xx、连接被打挂，压根没拿到业务数据。
  3. 业务返回空数组：请求成功、码正常、data.length === 0，这是”真空”。
  4. 筛选或分页后为空：结果同样是空数组，但用户带着条件进来。
  5. 无权限：403 或鉴权类业务码，数据存在，只是不给这个人看。
  6. 部分数据降级：主列表回来了，旁边的汇总数字、状态字典挂了。

**”空”和”错”是两条完全不同的分支，一次都不许混。**错是”我们不知道有没有数据”，空是”我们确定没有”。把错显示成空，用户以为生意真的这么差；把空显示成错，用户以为服务出问题，于是反复刷新、打电话。

再看互斥：这六个状态在判定条件上并不互斥。无权限的响应里 data 常常也是空数组，筛选后为空和业务空在响应体上长得一模一样。条件重叠，渲染却只能出一个，所以必须有一张按顺序判定的表来仲裁。

判定优先级：顺序错了就把”未登录”显示成”暂无数据”

定这张表之前心里没底，表本身是对着真实响应一条条试出来的，从上往下判，命中就停：

顺序 判定 落到哪个状态
1 本地有没有 token 未登录，跳登录
2 请求本身成没成 加载失败
3 码是不是鉴权类 无权限
4 码是不是参数类 参数错，回表单
5 长度是否为 0 空 / 筛选后为空
6 辅助字段是否残缺 部分降级

第一条在最上面，因为 token 在本地就能读出来，不必花一个请求去问后端。顺序放后面，等于用一次失败的请求去发现”这人根本没登录”，再把它呈现成一个让人摸不着头脑的空状态。同事的账号在另一个浏览器登出后，回到页面看到的是”暂无数据”。

状态流转图

箭头就是上面那张表的执行顺序，降级那条边是后来补的。

flowchart TD
    START[进入页面] --> P0{本地有 token?}
    P0 -->|没有| S_LOGIN[未登录]
    P0 -->|有| S_LOADING[加载中]
    S_LOADING --> R{请求成功?}
    R -->|失败| S_ERROR[加载失败]
    R -->|成功| C{返回码类型}
    C -->|鉴权| S_FORBID[无权限]
    C -->|参数| S_BADPARAM[参数错]
    C -->|正常| D{数据长度}
    D -->|大于 0| S_LIST[渲染列表]
    D -->|等于 0| F{带条件?}
    F -->|是| S_FILTER_EMPTY[筛选后为空]
    F -->|否| S_EMPTY[业务空]
    S_LIST --> G{辅助字段残缺?}
    G -->|是| S_DEGRADE[部分降级]
    G -->|否| DONE[正常]
    S_ERROR --> RETRY{重试}
    RETRY -->|未达上限| S_LOADING
    RETRY -->|达上限| S_GIVEUP[退让提示]

代码分层：状态是一个值，不是一堆 if

改之前那一版太典型，坑也踩得实在：order-list.js 这个 controller 有六百多行，拿到响应先判是不是 403 弹个层，再判是不是空、塞一句”暂无数据”，中间还夹一个是不是筛选导致的。三个判断散在三个地方，其中一个写在模板里。

问题不是不优雅，是改不动。加一种状态得先把所有分支读一遍才敢下手；空值和空长度在几种组合里互相兜底，没人说得清哪条实际生效；后端把空数组改成 null 的那天，页面直接白屏。我们的做法是把状态收成一个字符串：判定层只输出一句 view.setState(...)，模板层只认这一个值。状态名定死在常量表里。

文案负责说下一步，不负责安慰人

页面能给的东西只有三样，第三样最重要：现在能做什么。我们和设计同学吵了两天，最后写死一句话贴在工位上：**只写”暂无数据”等于没做设计。**它不告诉用户是没有还是看不见，更不告诉他该点哪里；反过来一个状态给三个按钮同样让人抓瞎，所以一个状态只给一个主操作：

状态 主操作
加载失败 重新加载
业务空 去新建第一条
筛选后为空 清空筛选条件
无权限 联系管理员
参数错 回到出错的输入框
部分降级 重试失败的辅助区块

两个要点。”业务空”和”筛选后为空”的动作相反：一个让用户创造数据，一个让用户去掉限制，合成一个必然有一个动作是错的。”当前条件”四个字也必须有，把条件原样显示在空状态下面一行之后投诉少了一截（这是我们自己那次的粗略观察，口径是那个月客服工单的分类数量）。

重试按钮：三种写法只有一种是对的

重试最容易写错，因为它要回答”重试期间页面算什么状态”。2016 年 6 月底，运营同事反馈”重试按钮点了三次，后台收到十个请求”。扒开看，按钮绑了点击就发请求，请求没回来时按钮还可点；用户切走再切回来，组件又初始化一次，把在飞的请求丢在外面。这些响应依次回来互相覆盖，显示哪个全看运气。

现在这版把三件事做全了：先把状态置回加载中，再禁用按钮，再限制次数。

最容易漏的是第一条：重试期间必须把状态置回加载中。只禁按钮不改状态，屏幕上一直挂着”加载失败”，用户以为没反应，于是更用力地点。自增号防的是旧响应覆盖新结果。

退让也要设计：达到上限后不再自动重试，提示里给出”联系管理员”这个出口。还有一次是失败后加了定时器自己重试，页面在后台标签挂一整晚，接口被自己的页面轮了几个小时。后来定了规矩——自动重试只发生在用户看得见这个页面的时候，页面隐藏就清掉定时器。

加载中的那一屏：一句文案还是一个骨架

怎么画不在这里讲，只讲用哪种、什么时候升级。

默认用一句”正在加载”，什么页面都能用。骨架屏这个说法当时刚从国外传进来，2016 年上半年我们只在订单列表和商品列表试过，因为只有它们结构固定；行数不固定的页面别做，格子跟真实结果差太多，加载完整页跳动，比空白还难受。规矩定成结构稳定才用占位，否则就用一句文案。

更要紧的是超时升级，”加载中”挂着不动跟白屏没区别。当期阈值：1.5 秒以内什么都不显示，避免一闪而过；超过 1.5 秒显示”正在加载”；超过 8 秒换成”加载有点慢，请稍候”；超过 15 秒判成失败并给出重试。依据是那阵子我们后台的响应时间分布，多数列表接口在 1 秒内，而”页面卡住”这类投诉到打电话大概要等十几秒（这是我们自己那次的粗略观察，口径是网关日志按接口聚合的耗时中位数和长尾，样本不到一个月）。

接口错误码约定：状态模型的另一半在后端

前端单干撑不起这套东西。2016 年 7 月中旬，我们和后端把响应体谈成一个约定：错误分四层，每层只对应前端一个状态，不许跨层。

层 后端怎么回 前端落到哪个状态
传输层 HTTP 500、网关超时、无响应 加载失败
鉴权层 HTTP 401、403，或业务码 4001、4003 未登录 / 无权限
业务空 码为 0，列表字段是空数组 空 / 筛选后为空
参数错 码在 1000 段，另带一个字段名 参数错

响应体三段固定成 code、message、data，其中 message 只给我们排查用，不往页面贴，文案由前端按状态自己出。

echoFilter 是这次约定里我最满意的一条：后端把生效的筛选条件原样带回来，前端拿它判有没有条件，比在本地猜”用户是不是筛过”可靠得多。约定写成文档之后，加新接口不用再讨论”这种情况算失败还是算空”。

403 被渲染成空列表：查了三天的排查

6 月下旬，一个连锁品牌的分店账号说看不到总部给的订单，数据同学怀疑是同步延迟。前端查了一天，列表确实是空的，看着完全符合”数据没同步”。直到我把 XMLHttpRequest 那层手写的封装扒开看，才发现里面有一句非 200 也照样按成功往下回调——403 就是这样变成空数组的。

三天的排查，根因是十行拦截代码把状态码吃了：把”我拒绝你”翻译成”这里没东西”，鉴权问题就伪装成了数据问题。修完加两条规矩：封装层不许把非 200 归成成功；判定表里鉴权分支排在长度分支前面。

监控只引用一句，采集与上报那篇写透了：我们把”空数据率”当指标看了一整周，把日志里”码为 0 且列表为空”的占比和”带条件的空”分开算。空集中在带条件的请求上，是筛选太严；无条件请求上也抬头、失败计数同时上涨，就是接口真挂了（口径是我们自己那次的粗略观察，只统计三个主要列表接口）。

上线之后又改了两处

这套模型 7 月中旬上线，站稳之前被改过两次。

第一处是”筛选后为空”。初版判的是当前表单值，很快发现用户翻到第 5 页时结果为空也被算成它，给的动作是”清空筛选条件”，一点跳回第 1 页，用户以为搜索坏了。后来把分页拆出来：条件为空但页码大于 1，动作是”回到上一页”。

第二处是把未登录从列表状态里拿掉：没有 token 应该直接跳登录页，它留在枚举里，就有人在没登录时又渲染了一次空列表。

两处都好落地，反而是”部分降级”最难，难不在前端。它要求接口说清”哪部分挂了”，而后端当时的做法是辅助字段查不到就悄悄留空，前端无法区分”这单没有备注”和”备注接口挂了”。最后我们逼着接口加了一个字段列出残缺区块，这事排了两个月。结论是：降级不是一个前端状态，是一种需要接口配合的能力，接口不配合时宁可不显示辅助区块，也别让整页空。

收尾：一张对照表，不是视觉规范

最后把状态按”触发条件—唯一主操作”收在一处。它只回答”该干什么”，不回答”长什么样”，颜色和插图不在这里定。

状态 触发条件 该给的唯一主操作
加载中 请求已发出且未超时 无，只给一句文案
加载失败 传输层不成或超时到阈值 重新加载
业务空 码为 0，无条件，长度为 0 去新建第一条
筛选后为空 条件还在且结果为 0 清空筛选条件
无权限 403 或鉴权码 联系管理员
参数错 参数段业务码 回到出错的输入框
部分降级 主列表有但带残缺标记 重试失败的辅助区块

回头看那个早上，那位老板看到的不是一个 bug，而是一个没人负责回答的问题。把状态枚举出来、把顺序定下来、把动作绑到状态上，剩下的只是把那一片白换成一句带下一步的文案。它让”页面看起来像挂了”第一次变成一个能核对、能改、能负责的分支。
