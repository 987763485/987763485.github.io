Drag and Drop API 文件拖拽上传

事故现场

7 月 18 号下午，同事在后台附件页做批量上传测试。需求是他提的：给工单挂附件，一次能拖几十个。他从资源管理器里全选，四十多个 mp4，总量两百多兆，直接甩进我们那个虚线框。

松手之后页面就没反应了，指针变成等待，输入框点不进去，整个标签页像被钉住。四五十秒后 Chrome 弹出”网页无响应”，缓过来时列表里只多了 6 个文件。翻后端日志，那个时间点一条上传请求都没进来——请求根本没发出。

这套拖拽上传是我一周前拿零散脚本拼的，能跑，但没考虑一次进来几十个文件会怎样。几天后把它扒开看了一遍，才找到真正的坑不在拖放 API，在我自己写的那个循环里。

先把边界划清楚

本文只讲文件投递和分片传输的性能与兼容。元素拖放排序、落位移动节点那套，2014 年 9 月那篇写过，dragenter/dragleave 高亮闪烁的计数办法也在那篇，不复述。图片缩放压缩、EXIF 方向、后端协议，归 2014 年 4 月那篇预处理。<input type="file"> 的基础操作归表单两篇，回调并发上限的实现归 2016 年 5 月那篇。

拖文件和拖元素是两条通道

两套东西共用同一组事件名，走的通道却不一样。排序那种是把页面上的节点搬来搬去，靠 dragstart 里 setData 存 id、落地时 getData 取回，整条链路里 dataTransfer.files 一直是空的。

文件投递正好反过来：从桌面往浏览器里拖，操作系统把文件列表塞进 dataTransfer，不给任何 setData 的机会；getData 拿到的往往是文件名或一个 URL，真正要的东西全在 files 上。

两套逻辑别塞进同一个处理函数，判空判错方向能查半天。

最先得挡住浏览器把页面换掉

最容易踩坑的一枪：拖进去一松手，整个后台页面被那个 mp4 替换了，地址栏变成 file:///Users/xxx/Downloads/xxx.mp4，人当场抓瞎。

浏览器对”文件放到窗口里”本来就有默认行为，就是当链接打开。不在 dragover 和 drop 上 preventDefault，松手那下默认行为一定执行。dragover 不挡，浏览器压根不认为这是合法放置目标，drop 反而不触发。

只在容器里阻止不够。拖到容器外面松手，照样整页跳转，所以 document 上再兜一道。

dragenter 上要不要挡，各内核表现不一致，我这边统一挡了再说。

先判一下：拖进来的到底是不是文件

用户也可能选中一段文字拖进来，或者从别的页面拖一张图。这时候 files 是空的，循环跑了个空，界面什么都不发生，看起来像”没反应”。判断依据是 dataTransfer.types。

types 里那个字符串标准写法是大写开头的 Files，但当期各内核大小写不统一，Chrome 一线给 Files，有的给全小写，别硬比。判不出文件时也别直接拒掉，宁可退回 input。

一次 drop 拿全量：files 和 items 不是一回事

e.dataTransfer.files 是 FileList，进来 40 个就是 40 条，每项是个 File，能拿到 name、size、type。多数场景够用。

但 files 上判不出”这一项能不能转成目录”，得看 items。DataTransferItemList 的长度和 files 一致，每项有 kind 和 type，kind === 'file' 时再 getAsFile()。各内核这块进度不一：items 有没有、getAsFile 稳不稳、webkitGetAsEntry 在不在，三个答案各不相同，只能当增强用，别当唯一入口。

真正的坑是这个列表是活对象。我在 drop 里 for 循环处理 items，循环体里发请求、写 DOM，回调回来再读 items[i] 就成了 null，日志里一片 Cannot read property 'getAsFile' of undefined。drop 一结束，dataTransfer 里那批东西就被浏览器回收了，你留的引用是个空壳。

FileList 和 DataTransferItemList 都不是数组，slice.call 拷一份是必须动作，不是洁癖。所有后续逻辑只碰这两个副本。

拖进来是文件夹：只有 webkit 系能接

同事经常把一整个文件夹直接拖进来。files 在这种情况下拿到什么各内核不一致，多数只剩散文件甚至为空，指望它不现实。

webkit 系那条路是 webkitGetAsEntry，拿到 FileSystemEntry 再递归读目录。IE 没有，entry 相关的一律不存在，所以先做能力检测，不过就退回 <input type="file">。

readEntries 一次最多回 100 条，这个当期限制是真的，几百张图的目录里会明显只拿到前 100 个，得反复调到返回空数组才算读完。递归套递归本身也吃时间，所以我加了上限：一次最多收 200 个，超了提示走压缩包。

假死的根因：循环里同步转 base64

扒开看很不体面，问题全在我自己那十几行：drop 里 for 循环，每个文件 new FileReader()、readAsDataURL 拿到 base64 塞进数组，全部读完再 JSON.stringify 成一个 body，一次 xhr.send 发出去。

单个文件这么写完全没感觉，40 多个视频就炸了，三个原因叠在一起。FileReader 回调是异步，但我为了读完再发，把整批串成了一条长链，主线程一直在解码、拼字符串、复制字符串。base64 让体积涨三成，200 兆的原始文件在内存里先有一份二进制、又有一份 270 兆的字符串，JSON.stringify 时再生成一份完整结果，峰值能到原始的三倍。一次请求发几百兆，xhr.send 还要把它序列化进网络层，又是一次全量拷贝。

改法是边分片边发，任何时刻内存里只留当前几片，转码这步整个去掉。改造前后的数字，同一台机器、同一网络下的粗略观察，只当量级看：

最该记住的是第一行：42 秒和 0.4 秒的差别不在网络快慢，在于有没有把主线程压在本地转码上。用户感觉到的”卡死”跟服务器没关系。

base64 的代价和当期的正解

canvas 缩放压缩、EXIF 方向那套我 2014 年 4 月那篇写过，不重复。只补批量场景的结论：转 base64 塞 JSON 是图省事，代价很实在。

体积涨约三分之一，编码本身的开销，没得优化。更麻烦的是带不了边界：一个 JSON 里放 40 个 base64，服务端没法流式处理，必须整包收完再 JSON.parse，几百兆一次解析，那边一样卡。multipart 天生分段，每段自带边界和文件名，能一段一段读；裸 body 只能放一个文件，长度类型得自己用头带。

当期正解是 FormData 直接把 File 塞进去 send，浏览器自己拼 multipart，不落 base64、不 stringify：

后端那边是 Express 加 multer 收的，不细说。补一句：fetch 当期在 IE 和旧 WebView 上不可用，要上得引 whatwg-fetch 加 Promise polyfill，我们没上；navigator.sendBeacon 当时刚出现，还没用。axios 我们还没引，这里就用原生 XMLHttpRequest。

分片大小与并发上限

Blob 上有 slice，File 继承它，切片不需要把文件读进内存：file.slice(start, end) 返回的还是个 Blob，直接 append 进 FormData 就能发。分片取固定大小，一片一个 xhr。

服务端认哪一片，靠 FormData 带上 index、count、name，再补自定义头 X-Attachment-Id；单片也可以带 Content-Range。两种都发，日志里好核对。

并发上限的写法我在 2016 年 5 月那篇回调文里写过，本文不复述实现。这里只说一件事：上传场景下这个上限必须比下载场景取得更小。平时加载资源敢开 6 个并发，那是下行；上行本来就窄，同一网络下粗略观察，3 个 2 兆的片同时推就基本占满了。再多开只会每片变慢、onprogress 更新变稀、超时变多，最后一起重试，反而更慢。几十个文件共用这一条队列。

进度、速度，以及”到 100% 不等于传成功”

进度来自 xhr.upload.onprogress 的 loaded 和 total，total 就是这次要发的字节数。单片好办，麻烦的是把几十上百片聚合回这一批：按字节聚合，别按片数，最后一片经常是残缺的。

速度取两次 progress 的差值除时间差，别用累计平均，弱网下反应太慢；我做了 800ms 窗口平滑。低于 1KB/s 显示”网络很慢”而不显示 0，否则用户以为死了。

还有一点那次排查里最容易看漏：onprogress 到 100%、status 200，只代表字节到了服务端，不代表附件可用。服务端还要把临时片落到最终目录、拼接、校验，真要算完成得等它返回 id 并回填到列表里。我们的做法是每片返回 {"ok":true,"index":3}，片齐了再调一次 merge，成功才把行状态改成”已上传”；中途刷新靠这个 id 重新拉状态。

失败重试与断点：只重发那一片

分片之后重试的单位从整个文件变成一片，这是分片最实在的收益。

有一次复盘把我看出一身汗：同事在弱网下拖了 30 多个文件，中间有一片超时。当时是整文件重发——一个 40 兆的 mp4 从头再推一遍。这一推把上行管道整个占住，别片的 onprogress 长时间不动，又被判成超时，跟着重发。互相踩踏，最后整批打挂，一条完整的都没落下来。

现在片的失败只重发该片，start 和 end 都在参数里，服务端按 index 占位。重试时 loaded 要处理：新 xhr 从 0 开始，聚合进度会倒退。我给每片留了 _loaded 基线，重发时先把上一次的 loaded 扣掉再加回来，界面上不出现负数。

重试上限当期定的是 3 次，退避 1.5 秒起步、每次翻倍。放弃条件两条：次数用完，或者单片累计耗时超过 20 秒。413 这种明确拒绝不重试，重试也没用。

秒传与完整性：哈希得分块喂

工单附件重复率很高，同一个宣讲视频被不同人传三四遍。服务端按 hash 去重能省不少事，hash 得前端算。

一次 readAsArrayBuffer 读 300 兆，等于把整个文件再复制一份进内存，跟前面 base64 那个坑是一类问题。当期做法是 spark-md5 一类的库，配合 blob.slice 一块一块读，每块算完就丢，增量喂给哈希对象。

同一台机器上粗略观察，200 多兆的整个哈希大概 2 到 4 秒，800KB 一片、循环三百多次，堆内存基本不涨；一次读全文件那版，标签页直接冲到 1G 以上。都是同机粗测，只当量级看。

代价还是要认：全量哈希得在发送前跑完，等于每个文件多一趟完整读取，弱网下这段等待用户感觉得到。折中是首片先传、后台同时算 hash，算完调 merge，服务端发现相同 hash 就把附件指向已有文件，返回”秒传”。抽样（只算头中尾各 1 兆）也试过，快是真快，但两个同大小文件可能撞车，撞一次就是丢附件，这风险没敢担，还是全量。

取消与 413：服务端那一层拒绝

取消就是 xhr.abort()，作用在正在飞的那几片上，剩下的从队列里剔除即可。它的即时效果只到”本地不再发字节”这一层：服务端收到的半片还躺在那，得靠超时清理；abort 之后 status 是 0，别当失败去重试，否则用户点了停止你还在那反复推。

另一次排查是被 413 折腾的。同事拖了个 90 兆的录屏，界面上直接”失败”，status 413，responseText 是一段默认错误页，细节什么也拿不到——这一层是 nginx 那侧的 client_max_body_size 挡掉的，压根没进到我们的应用。当期前端拿不到原因，只能猜。后来让应用层自己返回带 code 的 JSON，才算看清是谁拒的。

结论是前端先把大小卡住比后端拒绝友好得多：拖进来的瞬间就知道”这个 90 兆传不了，请压一下或者走网盘”，不用等几十秒看进度条跑满再告诉他失败。

兼容与降级路径

这张表是当期实测的结论，支持面只能按当期看，不能说”都支持”：IE 9 拖文件基本不可用，IE 10/11 能拖但 dataTransfer.files 跟 Chrome 有差，Android 4.4 的 WebView 是 Chromium 33 一线、触屏上没有这套拖放，iOS 9 Safari 也没有桌面式拖放。

环境 拖拽上传 多文件选择 上传进度 取消 降级入口
IE 9 不可用 可用 无 upload.onprogress 可 abort 仅 input，不显示进度
IE 10/11 可拖，files 有差 可用 可用 可用 拖入失败提示走 input
Chrome 51 一线 可用 可用 可用 可用 无
Android 4.4 WebView 触屏无拖放 可用 可用 可用 只放按钮，不显示拖拽框
iOS 9 Safari 无桌面式拖放 可用 可用 可用 只放按钮，accept 收窄

判定别靠猜浏览器，靠能力检测：dataTransfer 有没有、files 能不能读到、slice 在不在、upload.onprogress 能不能绑。缺哪项就关掉那块界面，心里没底一律退回 input。

附件上传页当期定的参数

最后把这页的参数抄一份，方便下次核对，别靠记忆。

参数 当期取值 依据
分片大小 2 MB 单片 1 秒上下推完，重试代价小；再小请求数暴涨
并发数 3 同机同网粗测，超过 3 每片变慢、超时变多
单文件上限 50 MB 走完约 3 分钟，再大用户等不住
单次批量上限 50 个 / 300 MB 那次 40 多个打挂过，留余量
重试次数 3 次，退避 1.5s 起翻倍 超过 3 次多是网络或权限问题
单片放弃阈值 累计 20s 弱网整批重传互相踩踏，宁可显式失败

这套数字不是标准答案，是修完那次事故在同一条线上跑出来的经验值。换网络换机器，并发和分片大小都得重跑一遍再定。
