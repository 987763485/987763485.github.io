JavaScript 大数运算实现

本文属于《算法与数据结构》第 3/13 篇
上一篇系列目录下一篇

从一批对不上的订单说起

7 月 13 号下午，财务和运营在会议室里对账。运营从后台导出的六月订单报表，比后端给的订单表少了一批单，按订单号去重之后，差的不是零头，是实打实的一百多单。我先以为是导出窗口没对齐，对着两张表抓瞎半天，扒开看才发现更难看的：报表里那批订单号末两位稳稳地变成 0，个别连第三位也没了。订单号是 19 位雪花 ID，接口按 JSON 数字传的，前端 JSON.parse 一过，超范围那几位就被抹平了；页面又把坏值当原始值提交回后端改状态，等于我们前端自己把账改错了。

这件事的范围先钉死。浮点加减那点舍入误差是另一篇文章要展开的事，本文不做 IEEE 754 的舍入巡礼，也不重复讲数值与进制转换。这里只谈一件事：整数超出安全范围之后前端怎么办。语言层面直接支持大整数的能力 2016 年还没有，只能回到最朴素的办法——把数字当字符串自己算。

把边界钉住：2^53 是怎么来的

双精度浮点用 64 位存一个数：1 位符号、11 位指数、52 位尾数，加上隐含的最高位，有效位一共 53 位。这 53 位能表示的连续整数只到 2^53，再往上，两个相邻可表示的数之间就不止差 1，整数开始跳着出现。ES6 把这个上限做成静态属性 Number.MAX_SAFE_INTEGER，值是 2^53 - 1，即 9007199254740991，配套判断函数是 Number.isSafeInteger。这俩都属 ES6，Node 4 里直接能用，老浏览器要么补 polyfill 要么自己写死常量，我们当时写死常量。

9007199254740991 是 16 位，雪花 ID 是 19 位，差着两三个数量级，撞上只是时间问题。哪些字段会撞，我把业务表过了一遍：毫秒时间戳最安全，哪怕一路推到 2286 年也还是个安全整数，就算先乘 1000 当微秒用，2016 年这几十年也远没到线；真正的雷区是两类，一是自增计数器和各种 ID、任务号、卡券码，二是把金额按分存的整数字段——分本身位数不大，可一分一加总就是汇总报表，报表最容易出事。上面这些位数和上界，都是我在同一台机器上粗略观察加手算的结果，不当基准数据用。

JSON.parse 这条路为什么必丢

JSON.parse 看到 "id":1234567890123456789 里的数字字面量，直接交给引擎的双精度解析，中间不存在”这字段是 ID，请按整数保留”这种概念。精度在解析那一瞬间就丢了，业务代码拿到的已经是坏值，而且不报错、不打日志、不给提示。这比算错更可怕——算错还能查，静默改坏只能靠对账发现。

字符串形式安全，原因很朴素：字符串走的是逐字符拷贝，压根不经过浮点表示，多少位都原样留着。所以当期跟后端约定的改法就两条。

第一条是把 id 类字段在协议里改成字符串输出。最干净，代价是全链路同步：接口文档、后端序列化、前端类型、日志格式、测试数据、埋点上报都得一起改，改漏一处就出现同一个订单号两种表示，下游做映射的人要骂人。

第二条是换解析器，2016 年当期已经有 json-bigint 一类实现，它在真正解析前把数字 token 扒开看，超范围的保留成字符串再交给业务。好处是前端自己能落地，坏处是多一个依赖，且解析入口必须收口——凡是 JSON.parse 的地方都得换过去，漏一处坏值照样进页面。它两种返回形态不一样，得先定死用哪种。

我们最后选的是第一条的变体，理由放在后面讲。顺带一句：Number.toString 和进制转换跟本文要解决的问题是两回事，不重复展开。

手写字符串加法

语言层面 2016 年还没有可用的大整数，加法只能自己在字符串上做，思路就是小学竖式：右对齐、逐位相加、进位往左走。先把绝对值相加和去前导零两个零件写出来。

while 条件里带着 carry > 0，最高位的进位才不会漏。符号交给外层：同号绝对值相加，异号退化成绝对值相减，谁大取谁的符号。

跑一遍验证，输入输出都按字符串比对。

位数上千之后怎么样：我拿两个 1200 位的十进制串相加，同一台机器上跑 1 万次大概 4 秒出头，摊一次零点几毫秒，纯属同一台机器上的粗略观察，别当基准数据；结论是线性复杂度，位数乘次数才是代价，展示层那几个 ID 完全无所谓，真要把上千位的循环堆到页面上是能把页面打挂的。

手写字符串乘法

乘法还是学校那个竖式：一位乘一位，乘到第几位就整体往左挪几位。实现上不用真的去加部分和，开一个进位数组，把每位乘积累加到它该在的格子里，最后一遍统一进位。

两个坑：格子累加完的值能远大于 9，进位那一遍得用 Math.floor(v / 10)，不能像加法只判满十；数组按 la + lb 开，最高位可能空着，靠 strip 收拾。

诚实说复杂度：单位乘法 la * lb 次再加一遍进位，两个 n 位数相乘就是 n 的平方。够用范围也就是 ID 和金额分那几十位——同一台机器粗略观察，上面几个几十位的乘法跑一万次不到两秒。真要在浏览器里做上千位乘法，比如给报表做精确合计，不该手搓，直接上库。

比较与减法

这两个看着比加法简单，实际最容易写错，坑不在循环里，在边界条件上。比较只要先去前导零再比长度，等长时字典序跟数值序一致，这点直接白捡。

减法真正麻烦的是三件事：借位要连着上一轮一起扣、结果可能为负、0 和 -0 得归一。我第一版把借位写成”这一位不够减就借一次”，没把借走的那个 1 从当前位扣掉，逻辑看着自洽，跑一遍就露馅——subAbs('1000', '1') 期望 999，实际给我 1009。抓回来靠的还是对照：安全范围内的输入用 Number 算一遍当标准答案，跟字符串实现逐组比，错的全是连续借位那一类，把 x 改成”当前位减去 borrow”才对得齐。

结果为负不能靠 subAbs 硬算，得在外面比完大小换方向，符号跟大的一方，就是上一节 bigAdd 的异号分支。剩下是 -0：走到”小的减大的再加负号”那条路会输出字符串 '-0'，Number('-0') 看不出问题，日志里 0 和 -0 两种写法混着，下游做字符串匹配就查不到了，所以一律靠 strip 归一成 '0'，bigMul 里也补了一句判断。

除法与取模的现实结论

除法我没写通用版。竖式除法麻烦在”试商”：每位先猜一个商数，回乘回减，猜大了还得退回来，再叠上余数和借位，是那几天里最容易踩坑的一段，收益却最低。业务里真需要的除法八成是除以 10 的幂，金额分转元就是最典型的一个，而除以 10^k 在字符串层面根本不用算，小数点往左移 k 位就行。

通用除法和取模，当期我的结论就是别自己造，直接用库，2016 年 bignumber.js、big.js、decimal.js 都挺成熟。另外别指望 Math.pow 或 parseInt 绕过去——它们自己就走浮点，parseInt 遇到长数字串照样丢。

库的用法与坑

不比较库的优劣，只讲使用纪律，因为踩的坑都一样。第一条最要命：构造入参必须是字符串。new BigNumber(9007199254740993) 看着精确，这个数字字面量在进构造函数之前就已经变成 9007199254740992 了，库再准也救不回一个废掉的入参。所以我们把构造统一包了一层，只让字符串进来。

第二条，链式调用不改动原值，a.plus(b) 返回新对象，a 还是原来的 a；忘了接返回值是最常见的一处失误，跑一遍数字纹丝不动，还当是库算错，心里没底。第三条，展示口径统一：金额一律走 toFixed(2) 指定位数输出，别把库默认形态直接上页面；取整口径要跟后端说清，两边不一致就出现”前端 12.35 后端 12.34”。浮点 toFixed 自己的四舍六入，见另一篇。第四条，金额单位重新约定：分是整数、元是字符串，接口里金额全按字符串传，前端不参与合计，Number(x) 把结果转回去这种事在评审里直接否掉。最后，一个项目只认一个入口，包一层 money 模块。

精度不等于舍入

一句话纪律：浮点的加减舍入误差是另一篇文章要展开的事，本文只谈整数超出安全范围之后怎么办。0.1 + 0.2 这类问题跟上面这套是两条线，别混在一起改。

前端和后端的分工

对账之后我们把哪些运算绝不该在前端做，写成表贴在评审文档第一页。

运算 归谁 前端做法
金额汇总、报表合计 后端 只展示字符串，不参与加法
库存扣减、余额变更 后端 只提交请求，不本地预测结果
单价乘数量的预览 后端出预览接口 前端传字符串，回的还是字符串
格式与位数校验 前端 判纯数字、判长度、判是否安全整数
展示格式化 前端 千分位与补零自己实现，口径跟后端一致

展示这栏多说一句。要做到前端和报表一模一样，千分位和补零得自己写，一个正则加一个补零循环，十几行的事。当期有人提议顺手引 moment 干这个，被我否了：它管的是时间，为一个千分位多背几十 KB 依赖不值。

一次回归防护

测试框架当期用 Mocha 加 Chai，不重讲写法，只讲断言挑哪几条：边界本身要写成用例，哪天有人手滑改了常量立刻能发现。

位数不超过 15 的用例都拿 Number 再算一遍当对照组，这是最省事的验法。线上加了个巡检项：从接口原始报文抓一批订单号，比对报文里的数字串和页面 JSON.parse 之后的值，看末两位是否变成 0、两边长度是否还相等。纯字符串比对，挂了直接报警，成本比月底再对账低太多。整套东西跑一遍很快，坏值想混进主干就当场挂给你看，不至于月底再对着报表抓瞎。

三个当期真实取舍

摆在桌上的方案就三个，我们按决策依据挑，不按爽不爽挑。

  • 改协议，id 全线按字符串走：最正确也最慢。要动的不只是后端序列化，还有接口文档、日志格式、测试数据和埋点，跨团队排期，最快一个版本周期。依据是能一次性根治，不留第二处坏值入口。
  • 前端兜底解析，换解析器：最快，一周内能上，只动前端这块地。依据是救急有效，但洞很明显——只堵了这一个解析口，别的入口、后端自己再解析一次的地方还漏着，属于止血不属于治本。
  • 后端返回时就把 id 转成字符串：最后选的是这条。它是第一条的窄版本，改动集中在响应序列化那一层，只碰 id 类字段，不用重写协议；前端配套只需一条评审规矩：id 按字符串处理、不许参与算术。依据是收益跟第一条接近，代价只有三分之一。

还得承认残余风险：老报文和历史导出的文件仍是数字形式，那部分只能靠巡检项继续盯，改不动，这块一直心里没底。

什么时候必须动字符串

最后一张表贴在工位上，判断只看位数和是否参与运算这两条。

情况 用什么
位数不超过 15，只做展示或排序 Number 就够
毫秒时间戳，连乘 1000 一起用 Number 就够
订单号、雪花 ID、卡券号这类标识 字符串，绝不参与算术
金额分做加减与汇总 后端算，前端只展示字符串
前端确实要精确加减乘 上面这套字符串实现或库
除以 10 的幂做单位换算 字符串移小数点
通用除法、取模 直接用库，别自己造

2016 年这一步走完，报表对不上的问题没有再复现。语言层面大整数能力当时还没有，往后会怎么补是后话；眼下能做的就是把边界钉死、把入口收口、把不该在前端算的东西还回去。
