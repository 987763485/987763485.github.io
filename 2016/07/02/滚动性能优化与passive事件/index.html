滚动性能优化与 passive 事件

六月底那次「越打日志越卡」

六月最后一周，图文列表页（一屏两张卡片、往下刷的那种）在安卓机上滑动时一顿一顿。iPhone 6 上手感正常，Android 4.4 那批机器上手指拖下去，页面先不动，等半拍才跟着走一小截，再停，再走。卡片带图片懒加载，滚动回调里做可见性判断和埋点上报。

我先按老办法抓瞎：在 scroll 回调第一行加一行日志，把 window.pageYOffset 打出来，想看触发频率。结果越打越卡，日志刷到后面页面直接挂住好几秒。把日志摘掉，同一台机器同一份数据，滑动立刻顺一点。这个反差不讲道理，但信号明确：回调正占着合成之前的那段时间。后来我把计数打到页面上、把布局读取挪出回调，跑了几遍才凑出一份能上线的改法。

先把边界说清

边界先说清。滚动库与自定义滚动实现、-webkit-overflow-scrolling 的选型见《iScroll 实现移动端滚动》《移动端滚动方案优化》，这篇不做库对比；offset/client/scroll 属性含义见《DOM 尺寸与位置：offset/client 与 scroll》，这里只谈在滚动回调里读它们的代价；touch 事件模型和 300ms 延迟见《移动端 touch 事件与手势基础》；节流实现见《JavaScript 防抖与节流的实现与应用》；合成层理论见《CSS3 过渡动画原理与性能》《CSS 过渡与动画性能再探》。这篇只讲滚动监听自身，和 passive 这个当期还停在提案阶段的选项能推进到哪一步。

为什么 scroll 监听会卡：合成之前要先问一遍 JS

当期我是这么建模的（各家引擎进度不一，细节未必处处准确，但够用来判断该不该加监听）：手指拖动屏幕，理想情况下由合成器直接把图层平移，不需要主线程参与；可如果页面上挂了 touchstart、touchmove、wheel 或 scroll 相关监听，引擎不敢假设这次滚动能放心交给合成器，因为监听里可能调用 preventDefault() 把默认滚动拦掉。于是它得先把事件派发到主线程，等我的 JS 跑完，看我拦不拦，才决定这一帧怎么画。

这条链上有两处代价。一是等待：主线程忙的时候，合成器每帧都得等一遍答案，画面落后于手指，用户感受到的「半拍」多数不是 JS 算得慢，而是这个等。二是回调时长：回调里读一次布局信息就触发同步重排，等待从几毫秒涨到几十毫秒（同一台机器上的粗略观察，不同机型差很多），这份延迟直接加在用户能感知的那条路径上——日志也在主线程上打印，它同样算在这一段里。

preventDefault 与 passive：把「我不拦」这件事先说给引擎听

preventDefault() 是让监听者否决默认行为的口子。滚动、缩放、橡皮筋效果都是默认行为，监听里一调，浏览器就得照办。问题在于，浏览器无法从函数源码上保证我不调它，只能每次都问。

EventListenerOptions 那份草案的思路，是把答案从「运行时问」挪成「注册时就说明白」：注册时把这个监听声明成不会调用 preventDefault()，也就是 passive，引擎就能在派发之前放心地把滚动交给合成器，不必等主线程回话。必须写清楚：到本文这天，passive 还是提案，Chrome 要到 51（2016 年 7 月下旬）才把它打开，Safari 和 Firefox 的支持面各家不一样，IE 全线不支持。也就是说，它对我手上这批线上流量还不是一个能指望的能力。

能立刻确认的是另一件事：addEventListener 的第三个参数接受一个选项对象，从 Chrome 49（2016 年 3 月）起在桌面一线可用；传 true/false 的老写法照旧工作。于是代码可以写成「先探测，探测到了才传对象」，在测试版和开发者渠道上当场受益，其余浏览器原路退回。这不算解决安卓 4.4 的卡顿，但至少提前把接口摸清楚。

特征检测：把 passive 是否被读这件事写进代码

思路来自 Object.defineProperty 探测选项对象的老技巧：草案里那个 passive 选项如果被浏览器读取，就必须访问对象的这个属性，我把它做成一个 getter，访问一次就记一笔。

跑一遍几种环境，supportsPassiveOption 的结果是：Chrome 49、50 上是 false——它们认选项对象，草案里当时已实现的那几个会读，但 passive 还没打开，getter 不触发，这是正确结果不是检测坏了；Chrome 51 开发者渠道是 true；Safari 9、Firefox、Android 4.4 的 WebView（Chromium 33 一线）都测不出 true；IE 11 和 Edge 13 走的是 catch 那条路。

还要防一件事：某个引擎如果把选项对象当普通配置去遍历自有属性，getter 也会被触发一次，检测说支持、实际不生效。外部没法完全排除，所以口径放保守：检测只决定要不要额外传这个选项，不保证性能收益，页面行为一律不依赖它。真当依赖，就是拿草案阶段的能力去赌线上。

false 那一路就是当年的普通写法（捕获阶段关闭），行为跟改动前一模一样。这样即使草案落地，要做的也只是让检测多命中一点，不用翻箱倒柜找散在各处的监听。

touch-action：当期真正能立刻用的一手

如果只能选一个当天就能上线的手段，我选 touch-action。它把「这个元素上的触摸手势允许做什么」写在 CSS 里，引擎在开始处理手势前就知道答案，不必派发事件问 JS。

值一共这几个：auto 默认；none 触摸手势全交给 JS；pan-x 只许横向平移；pan-y 只许竖向平移；manipulation 只保留滚动和点击，把双击缩放与捏合掐掉。桌面 Chrome、Edge 13 认这套；IE 系要写带前缀的 -ms-touch-action，而且它的旧枚举拼写跟标准有差异——IE10 把「两个方向都能平移」写成 pan，标准里对应的是同时写 pan-x pan-y；IE10/11 还允许一行里给多个值。iOS 9 Safari 当期不支持，Android 4.4 的 WebView 也当不支持来验收，那两条路径只能靠下面的少监听与 rAF 合并。

pan-y 常能替代 JS 拦截的原因很直白：我在滚动回调里十次有八次不拦默认行为，只是「怕拦不住才注册的监听」。手势方向写在 CSS 里之后，这个方向上的滚动根本不经过我的函数，监听能不挂就不挂。

两个限制别忽略：它管的是触摸手势，对 wheel 和桌面端滚动条没用，桌面上该卡还是卡；它也不影响键盘滚动。

布局读取：滚动回调里最贵的那行代码

我那个列表页的回调干的事很普通：读当前滚动位置，算哪些卡片进了可视区，把图片地址填上去，顺手更新一下”回到顶部”按钮。真正致命的是前三步里混着布局读取。

含义不复述，只说代价。offsetTop、offsetHeight、scrollHeight 这些属性一旦在样式已经变脏的时候被读，引擎必须立刻把待处理的样式和布局算完才能给答案，这就是同步重排。回调里读一次，就把这帧什么时候画往后推一次。同一台机器上的粗略观察（数字只用于比较相对量级，不代表基准）：只读 window.pageYOffset 时回调几乎感觉不到；回调里读一次 offsetTop，日志时间戳的间隔就从跟手变成肉眼可见的一顿。

getBoundingClientRect 和 scrollTop 的差别我也在同一台机器上扒开看过：两者都会触发那次强制布局，不是我原本以为的一个安全一个危险；区别在于前者一次就返回矩形，不用再顺着 offsetParent 往上加，净耗时低一些。所以别写成哪个 API 绝对便宜，重点是同一次计算里少读几次、读到就存下来。

改法就两条：把布局读取从事件回调里搬走，非读不可的挪到 rAF 里统一读一次；搬不走的先缓存，别在循环里反复读同一个属性。读和写也别交替——先写完样式，再统一读。

rAF 合并：scroll 只置脏标记，计算留到下一帧

这是我最后真正上线的写法。事件回调里只记一个布尔和最新位置，重活压给 requestAnimationFrame，一帧最多干一次。

startLoop 里那句 rafId === null 是关键：滚一秒可能派发上百次事件，但帧就 60 个（同一台机器上的粗略观察，实际会掉到 30 以下），把计算钉在帧边界上，多出来的那几十次只花置标记的成本。

为什么它比节流更贴合滚动这种连续事件：滚动是不停到来、结果只看最后一次的事件流，节流是照一个时间窗丢掉中间态，窗口偏大拖慢跟手的反馈，偏小又省不下多少计算；rAF 顺着浏览器出帧节奏合并，天然对齐一帧一次。节流什么时候该用？事件本身低频、或者省的是真金白银的计算量（发请求、写 localStorage），这种场景仍然要节流，实现细节走《JavaScript 防抖与节流的实现与应用》。我这个场景两者叠加过，跑一遍发现瓶颈是布局读取不是次数，节流就撤了。

顺带一提 jQuery：项目里事件多用 jQuery 2.x 绑的，on() 不透传第三个参数，这一处只能退回原生绑定。

滚动该不该提层

合成层理论那两篇讲透了，这里只说滚动这一句：给滚动容器加 will-change: transform，是把这块要单独成层提前告诉引擎，免得滚动过程中临时提层造成抖动；代价是占显存、层数一多反而拖慢。我的口径是只给那种整页就它一个长列表的容器加，卡片内部一律不加，加完必须回真机跑一遍确认没有更卡，心里没底就先不加。

没有 devtools 的时候怎么定位

真机连不上调试口时我用的土办法有三个。一是回调里打时间戳，把相邻两次的间隔攒成数组，滚到末尾后用隐藏按钮把最大值和次数渲染到页面上——这办法本身就影响性能，只用于定位，看完就摘。二是把回调计数直接打到一个固定定位的角落里，手指边滑边看，数字涨得飞快而页面不动，就说明合并没生效。三是远程调试，一句带过：桌面 Chrome 用 USB 连安卓能挂上调试，当期我配一次折腾半天，所以前两个仍是主力。

桌面这边，Chrome 当期那个面板还叫 Timeline（改名 Performance 是之后的事），录一段滚动能看到每帧的耗时条：脚本运行、样式重算、布局、绘制各占一种色块。我那页录出来最直观的是布局那栏红条成片，扒开看调用栈停在我读 offsetHeight 的那行。改完之后红条从每帧多次变成每帧一次。

症状对应先试哪一手

症状 先试哪一手 备注
手指拖了页面半拍才动 把监听里所有布局读取搬走 搬不动就缓存，别在循环里读
越打日志越卡 立刻摘日志 日志占主线程，只用于定位
横向滑动整个页面跟着抖 touch-action: pan-y 桌面 wheel 场景无效
回调一秒上百次、CPU 一直高 rAF 合并 + 脏标记 低频且计算昂贵时才考虑节流
滚动时卡片图片切换瞬间掉帧 检查是否临时提层 只对单一长容器考虑 will-change
想提前用上新写法 Object.defineProperty 检测 命中就传，不命中退回 false

最后把话说回本文那个标题上：passive 这项提案能力解决的是”合成之前不必等 JS”，2016 年 7 月初它只在测试版和开发者渠道里能试，Chrome 正式打开要到 51。所以它是”以后能省心”，不是”今天能上线”的开关。今天要上线的东西，是少监听、不读布局、rAF 合并和 touch-action。
