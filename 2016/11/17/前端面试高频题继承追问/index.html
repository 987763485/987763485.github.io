前端面试高频题：继承追问

上周帮团队面一个两年经验的候选人，简历上写着“熟悉 JavaScript 面向对象与继承”。我从 new 开始问，一路问到 ES6 的 class extends，四十分钟里他答对了七成，但每次都在同一个地方卡住：知道写法，说不清机制。这篇就按那场面试的追问顺序整理一遍，把每个问题背后的考点和容易踩的坑写清楚。七种继承写法、原型链的查找过程、Object.create 的用法、class 的基础语法，站内都有专文，本文不重复，只写“被追问时该怎么说”。

一场从 new 开始的面试

我的习惯是先不问继承，问 new。原因很简单：继承的所有写法最终都要落在“构造调用”上，如果一个人说不清 new 干了什么，后面讲 Child.prototype = new Parent() 时一定是背的。

候选人答得挺流利：创建一个空对象、把原型指过去、执行构造函数、返回这个对象。我让他把“原型指过去”具体化，他说“就是 __proto__ 指向 Parent.prototype”，然后补了一句“其实 new 里面就是 Object.create 嘛”。这句补充暴露了问题：他知道结论，但没分清哪一步是规范行为、哪一步是实现细节。

后面的追问更明显。我问“改完 prototype 之后 constructor 去哪了”，他愣了几秒说“应该还在吧”；我问“instanceof 是怎么判断的”，他答“看原型链上有没有”，再问“跨 iframe 为什么失效”，他就开始猜；最后我让他对比 class extends 和 ES5 的寄生组合式，他把 class 说成“语法糖，Babel 一编译就一样了”。

这场面试让我确认：“熟悉继承”四个字几乎不携带信息。会背写法的人多，能沿着追问链走下去的人少。下面九个问题，就是那条链。

追问一：new 到底做了哪四步

规范里的 [[Construct]] 可以拆成四步，面试时按这个顺序说最稳：

  1. 创建一个新的空对象；
  2. 把这个对象的 [[Prototype]] 指向构造函数的 prototype 属性；
  3. 以这个新对象为 this，执行构造函数体；
  4. 如果构造函数返回的是对象，就返回它；否则返回第 1 步创建的对象。

第 3 步有个常被忽略的细节：this 的绑定发生在执行构造函数体之前，所以构造函数里给 this 赋值，赋的就是那个新对象。至于 Object.create，它只是第 2 步的一种实现手段，不是 new 的全部。用 Object.create 手写时，第 3 步必须显式 apply，第 4 步必须自己判断返回值。

还有个小坑：原生 new 遇到 prototype 为原始值时，会退化成 Object.prototype，手写版则会直接抛错。主动说出这个差异，比背四步更加分。

追问二：prototype 与 __proto__ 各挂在谁身上

这两个名字长得像，位置却完全不同。一句话区分：prototype 是函数才有的属性，__proto__ 是每个对象都有的内部指针。

prototype 是函数对象上的一个普通属性，值为对象，这个对象默认带一个指向函数自身的 constructor。它只在“这个函数被当作构造函数用”时才有意义。普通对象没有 prototype，({}).prototype 是 undefined；箭头函数也没有，(() => {}).prototype 同样是 undefined，对象字面量里简写的方法也没有。

__proto__ 则是对象内部的 [[Prototype]] 的访问器，定义在 Object.prototype 上，所以几乎任何对象都能读到它，包括函数——函数也是对象，它的 __proto__ 指向 Function.prototype。这条链的尽头是 Object.prototype.__proto__ === null。

追问三：constructor 为什么会丢

constructor 不是魔法，它只是 prototype 对象上一个普通的、默认不可枚举的属性。函数声明时引擎顺手写好，一旦你把整个 prototype 换掉，新对象上就没有这个属性了。

注意第二行结果是 true 而不是 undefined。因为 new Parent() 造出的对象，其原型是 Parent.prototype，上面有 constructor: Parent，属性查找顺着原型链就找到了。所以问题的本质不是“丢了”，而是“指错了人”。

影响分三层。最轻的是调试：控制台里实例的构造函数名变成 Parent。中间是类型判断：老库用 obj.constructor === Foo 做分支，实例会被分到父类。最重的是拿 this.constructor 去 new 的写法，比如序列化恢复和插件系统，会造出父类实例，行为直接错掉。

追问四：instanceof 是怎么判断的

规范里的算法只有一句话：取右操作数的 prototype，然后沿着左操作数的原型链一路向上找，找到就返回 true，找到 null 还没找到就返回 false。所以它检查的是“原型链上有没有这个对象”，跟构造函数本身没有关系。

最后两行是重点。instanceof 每次都会重新读右操作数当前的 prototype，所以它在运行时是“活的”，不是编译期绑定的。这也解释了为什么“先 new 再改 prototype”的实例会突然不属于原来的类。

跨 iframe 失效的原因也在这里。每个窗口有自己的一套内置构造函数，iframe 里的 Array 和主窗口的 Array 不是同一个函数对象，两个 Array.prototype 也不是同一个对象。主窗口的 arr instanceof Array 检查的是主窗口的 Array.prototype，而 iframe 里造出来的数组，原型链上挂的是 iframe 那一份，自然对不上。同理，instanceof Object 在跨窗口时也可能翻车。

绕过的办法：Object.prototype.toString.call(obj) 返回 [object Array] 这类字符串，不受窗口边界影响；判断数组则优先用 Array.isArray。至于 Symbol.hasInstance，它是 ES6 的知名符号，允许自定义 instanceof 的行为：

追问五：组合继承为什么调了两次父构造函数

因为组合继承把两件事分开做了：实例属性靠构造函数调用继承，原型方法靠原型链继承。而“原型方法”那一步用的是 Child.prototype = new Parent()，这一句本身就是一次构造调用。

两次调用的后果不只是多跑一遍代码。父构造函数里的副作用会执行两次，比如往实例上挂监听、发请求、递增计数器；new Parent() 造出的那个对象还会成为 Child.prototype，父类的实例属性在原型上留了一份“影子”，所有子类实例共享它，一旦有人改它，污染会扩散到全部实例。这也是为什么 colors 这种引用类型属性在组合继承里特别容易出问题。

寄生组合式的省法很直接：第二步不要 new Parent()，改成 Object.create(Parent.prototype)。原型链该连的连上了，父构造函数一次都不多跑，原型上也不会残留实例属性。省下的是一次构造调用的副作用和一份多余的对象内存，语义上则干净了——原型只放方法，实例只放数据。

顺带说一句：ES6 class extends 内部也是用类似 Object.create 的方式接原型，不会构造父类实例。这句话能把两段知识接起来，面试官通常会顺着问下去。

追问六：Object.create(null) 有什么不一样

它造出来的对象，原型是 null，原型链到此为止。普通对象字面量的原型是 Object.prototype，所以能直接用 hasOwnProperty、toString、isPrototypeOf；Object.create(null) 的对象一个都没有。

用它做字典的好处有两个。第一，for...in 不会遍历到原型上的东西，也不需要每次加 hasOwnProperty 过滤。第二，键名不会被原型污染：普通对象上写 obj['toString'] = 1 只是覆盖，但写 obj['__proto__'] = {...} 会真的改掉原型；空原型对象上，__proto__ 就是一个普通字符串键，存什么都安全。当年做配置合并、缓存表、按 id 索引的数据时，我倾向于用它。

代价也要说清楚：没有现成方法，有人顺手写 dict.hasOwnProperty(k) 就会报错；某些库假设入参是普通对象，会读 constructor 或做 instanceof Object 判断，传进去就翻车；JSON.stringify 正常，但 dict + '' 会抛错。它不是“更好的对象”，只是“没有包袱的容器”。

追问七：class extends 和 ES5 继承的真实差异

说“class 只是语法糖”是不准确的。相同的部分确实很多，但有几处是 ES5 写不出来的语义：

第一，不存在变量提升。class 声明有暂时性死区，声明前访问直接抛 ReferenceError；ES5 的函数声明构造器是提升的。第二，子类构造函数必须先 super，否则 this 未初始化，任何对 this 的读写都抛错。第三，super 是词法绑定的，不是 Parent.prototype.say.call(this) 的语法糖：它绑在方法定义时的 [[HomeObject]] 上，把方法摘下来单独调用，super 依然指向原来的父类。第四，静态方法会被继承，Child.__proto__ === Parent，所以 Child.create() 能跑，而且里面的 this 是 Child。

第五，class 不能当普通函数调用，Parent() 直接抛 TypeError，这是 ES5 构造器做不到的约束。第六，class 内部默认严格模式，方法不可枚举。这几条里面试官最爱问第二和第三，因为它们直接影响“能不能用 call 模拟”。

追问八：Babel 6 把 class 编译成了什么

2016 年上线的项目基本都要过 Babel 6，所以这题很实际。babel-preset-es2015 的输出大致是：_classCallCheck 拦住无 new 调用，_createClass 把方法定义成不可枚举，_inherits 接原型并把子类函数挂到父类函数下，构造函数里的 super() 变成 _possibleConstructorReturn。

_possibleConstructorReturn 解决的就是 new 那题的返回值规则：父构造函数返回对象时，子类必须用那个对象当 this。_inherits 则把子类原型接到父类原型，同时把子类函数自身的 __proto__ 接到父类函数，后者是为了静态方法继承。

差异也明显：Babel 6 继承内置类型是坏的，class MyArray extends Array 编译后 length、map 都不对，因为 ES5 没法构造内部槽；super 变成 _get 加 call，不再是原生词法绑定；TDZ 只能部分模拟。业务里写 class 没问题，但别拿它继承 Array、Error。

追问九：mixin 与组合，为什么组合更常见

继承表达的是“是一个”，而业务里大量关系其实是“有一个能力”。硬用继承，很快会出现为了复用两个方法而拉一条四层深的链，改父类一个方法，所有子类跟着抖。mixin 是折中：把能力写成独立对象，混进原型。

mixin 解决了表达力，没解决耦合：方法仍摊在原型上，命名冲突和来源不清依旧。更稳的是组合——实例持有能力对象，通过它调用。

能力可以单独测、单独换，来源一眼可见，也不用在原型上打架。我的判断标准是：共享状态和生命周期才用继承，只共享行为就用组合；层级超过两层，先怀疑设计。

九个追问压成一张表，复习时看第三列比看第二列有用，因为面试翻车基本都翻在“以为对”的地方：

追问 考点 易错回答
new 四步 原型绑定与返回值规则 返回原始值也会替换实例
prototype 与 __proto__ 谁挂在函数、谁挂在对象 函数的 __proto__ 指向自己的 prototype
constructor 丢失 属性继承而非消失 改原型后 constructor 是 undefined
instanceof 沿原型链找右值的 prototype 认为它比较构造函数

空原型对象 没有继承来的方法 直接调 obj.hasOwnProperty
class 差异 super 绑定、静态继承、不可调用 一句“语法糖”带过
