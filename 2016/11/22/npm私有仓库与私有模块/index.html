npm 私有仓库与私有模块

今年三月，后台三个项目同时赶一个报表需求，我在其中一个仓库里修了日期格式化的 bug，两周后另外两个项目原样复发了同一个问题。本文记录我们从”复制粘贴工具函数”走到自建 npm 私有仓库的全过程：怎么命名、怎么选型、.npmrc 怎么写、token 放在哪、发布与安装各有哪些坑，以及 401 与 404 的排查顺序。适合正在被多仓库共享代码困扰、又不想把内部代码发到公共 npm 上的团队。

事故：一份 formatDate 复制了三遍

三个仓库的 src/utils/date.js 几乎一模一样，是谁先从谁那里复制出来的已经没人记得。需求要按客户所在时区显示”昨天 23:00 到今天 07:00”这样的区间，我在 A 项目里改了 formatDate，先把本地时间换算成 UTC 再格式化，自测通过就发了版。

两周后 B 项目的运营反馈：跨月那天的数据少了一小时。我打开 B 项目的仓库，那份 date.js 还是老版本。C 项目更麻烦，有人在那份副本上单独加过”财务口径”的判断，直接覆盖会把他的改动冲掉。修一个 bug 要开三个分支、发三次版、通知三拨人，还得记住哪份副本被谁动过。

我们试过两种替代方案。git submodule 让三个项目各自锁一个 commit，升级要改三处指针，CI 还得配 SSH key；npm link 只解决本机联调，新同事和 CI 上仍要从 git 拉。最后只剩一条路：做成私有包，让 registry 管版本。障碍是这些工具函数里写着内网接口地址、几个测试账号和一份业务口径的常量表，不能出现在公共 npm 上。

私有包的命名：scope、private 与 access

npm 从 2.7 起支持 scoped package，Node 6 自带的 npm 3 已经能正常处理。我们把包命名为 @company/utils，scope 是 @company，在公共 registry 上它必须挂在一个用户或组织名下。scope 不只是前缀，它同时决定三件事：包的命名空间、发布时的可见性，以及 .npmrc 里按 scope 分流 registry 的写法。

private: true 经常被误解。它只做一件事：挡住误发布，npm publish 会直接报错退出。它不提供任何访问控制，也不会让包真的变”私有”。决定可见性的是发布时的 --access 参数：

仓库选型：从公共 scope 到自建 registry

摆在我们面前的有四条路，成本差别很大。

第一条是公共 registry 加 scope 映射，零运维，但 restricted 要付费、public 就等于开源，只适合本来就打算开源的包。第二条是同一 registry 的付费私有包，按成员收费，权限、审计、CI token 都由官方提供，代码仍托管在别人那里，适合不想碰运维、合规上允许外部托管的小团队。

第三条是自建轻量 registry。当年最流行的是 sinopia，但它在 2015 年之后就停止维护。社区把它 fork 出来继续做，也就是 verdaccio，2016 年才刚起步，版本号很小，文档和插件都不齐。它的优点是单进程加本地存储，写一份配置文件就能跑，支持 htpasswd 账号和包级 ACL，还能配 uplink 去上游拉公共包。缺点是单点、没有高可用、数据就是磁盘上的目录，适合二十人以内、内网可控的团队。

cnpmjs.org 是国内另一条常见路径。它自带 MySQL 存储、Web 管理界面、scope 支持和 upstream 代理，部署比 verdaccio 重，但功能完整，不少公司用它同时做内网镜像和私有包。它的权限模型偏简单，出问题时得去翻服务端日志。

第四条是 Nexus 3 或 Artifactory。如果公司已经有制品库在管 Maven 和 Docker，直接开一个 npm hosted 仓库加一个 proxy 仓库最省事：账号接 LDAP，权限按角色配，审计日志齐全，备份跟着现有流程走。代价是要有人维护 JVM 服务和存储，对小团队来说太重。

我们的判断很朴素：二十人以内、只要求”能发能装”，verdaccio 够了；上百人、已经有制品库，别再造一个，用 Nexus；要跨语言统一治理、对审计有硬要求，才轮到 Artifactory。

.npmrc：项目级、用户级与不能提交的 token

npm 读配置有三个层次：项目根目录的 .npmrc、用户目录的 ~/.npmrc、全局的 $PREFIX/etc/npmrc，优先级从高到低。项目级适合放”这个仓库必须用哪个源”，用户级适合放凭据。

always-auth=true 是私有 registry 最常见的坑。默认情况下 npm 只在发布请求上带认证头，GET 下载 tarball 时可能不带，Nexus 一类服务会直接回 401。打开它，所有请求都带 token。内网用自签证书时还要配 strict-ssl=false 或指定 cafile，否则会卡在证书校验上。

token 会失效，而且失效时的表现很含糊：发布或安装报 401，有时只说 tarball 拉不下来。常见原因有三种：改过密码、管理员在服务端吊销过、registry 重装后用户库被清空。verdaccio 早期的 token 存得比较随意，重装后配置不当会全部失效，我们第一次迁移就踩了这个。

发布：版本号、files 与不可逆的操作

npm publish 做四件事：按 files 白名单挑文件打成 tarball、跑 prepublish 脚本、上传 tarball、写 registry 元数据。整个过程没有预演，发错了只能发新版本补救。

版本号必须严格递增。同一个版本第二次发布会报 403，提示不能覆盖已发布的版本。所以发布前先 npm version patch（或 minor、major），它会改 package.json、打 git tag，再执行 npm publish。手动改容易漏，流水线里更要用脚本统一。当年还没有 lock 文件，版本号是唯一的锚点，更不能图省事复用。

files 是白名单，写进去的才打包：

默认总会带上 package.json、README、LICENSE 和 main 指向的文件，.git、node_modules 永远排除。白名单的好处是新增的调试文件、测试快照不会意外泄露。

.npmignore 是黑名单，和 .gitignore 有三处差异：两者同时存在时 .npmignore 优先，.gitignore 完全不参与打包；.npmignore 不存在时才回退读 .gitignore；README、LICENSE 和 package.json 总会被打包，ignore 写什么都改不了。我们最初只维护 .gitignore，结果 test/fixtures 里一份带真实内网地址的配置被打进了包，这就是后来改用白名单的原因。

发布权限与善后也要说清。npm 用 npm owner add 授权，Nexus 用角色，verdaccio 用包级 ACL。包一旦被下游依赖，删除代价极高：官方 registry 早已收紧 unpublish，只允许发布后很短的时间内删除，超时只能联系支持；删掉之后所有写死旧版本的安装都会 404。想撤内容用 npm deprecate，它只给安装者一条警告，包还在。最后记住，私有不等于加密，有读权限的人都能下载 tarball，密钥和证书不要放进包里。

安装：scope 怎么解析，404 从哪来

安装只有一条命令 npm install @company/utils，但解析 registry 的顺序值得记住：先看项目 .npmrc，再看用户级，再看全局；请求 @company/utils 时，找到 @company:registry 就用它，否则回落到 registry。所以”公共包正常、私有包 404”几乎总是 scope 映射缺失。

新同事入职最常见的报错是 404 Not Found: @company/utils。排查按这个顺序走：npm config get registry 看默认源；npm config get @company:registry 看 scope 映射有没有值；npm config list 确认读到了哪几个配置文件；最后确认账号有读权限。没权限时 Nexus 可能回 404 而不是 401，故意不暴露包是否存在，这一点很容易把人带偏。

CI 上的 404 多半是环境残留：镜像里打进了旧的 ~/.npmrc，或者流水线用了另一套变量。把配置生成放在安装之前，别依赖镜像里的文件。

依赖里的私有包是同一回事。package.json 里写 "@company/utils": "^1.2.0"，任何装这个项目的人都必须能访问 registry 并有读权限，否则他拿到的是 404，而不是”缺少依赖”这种更友好的提示。npm 3 的扁平化会让同一个包的两个版本同时存在，排查版本问题时用 npm ls @company/utils 看真实依赖树，别只盯着 package.json。有人会用 git 地址依赖绕过配置，代价是丢掉版本语义、缓存和 files 白名单，我们不推荐。

代理与镜像：缓存上游与离线环境

私有 registry 通常还兼一个职责：替内网缓存公共包。Nexus 的 proxy 仓库第一次收到 lodash 请求时回源官方 registry，把元数据和 tarball 存下来，之后的请求直接命中本地。Artifactory 的 remote 仓库同理，verdaccio 的 uplink 也是这个模型。

Nexus 3 还可以建一个 group 仓库，把 hosted 和 proxy 合成一个 URL，客户端只配一个 registry 就能同时装私有包和公共包。这很方便，但 scope 映射更清晰：私有包走内网，公共包走上游，出问题时一眼能看出请求去了哪。

排查网络问题三个命令够用：npm config get registry 确认当前源，npm ping --registry=http://npm.company.com 检查连通和鉴权，curl -I 直接看 tarball 地址的响应码。npm ping 成功而安装失败，多半是 tarball 的 host 与 registry 的 host 不一致，token 没跟过去。

网络隔离的环境要提前准备。registry 不可达时 npm 会重试几次再失败，报 ETIMEDOUT 或 ECONNREFUSED，看起来像包不存在。可行的做法是：在能出网的一侧把依赖全量缓存进私有 registry，或者用 npm pack 把 tarball 带进内网再 npm publish。只靠 ~/.npm 的本地缓存不可靠，换台机器就没了，缓存键还和 registry 地址绑定。

常见故障：六类报错与排查顺序

这张表是运维一年攒下来的，按顺序看基本能定位到具体一层，不用从头猜。

现象 排查顺序 常见原因
401 Unauthorized 先 npm whoami --registry，再确认 _authToken 是否存在、是否过期，最后问管理员有没有吊销记录 改过密码、token 被吊销、always-auth 没开、http 与 https 混用
403 Forbidden 先看账号是否在 owner 或对应角色里，再看版本号是否已存在，最后确认 scope 归属 没有发布权限、版本号重复、scope 属于别的组织
404 Not Found 先 npm config get @company:registry，再 npm config list 看哪层配置生效，最后验证读权限 scope 映射缺失、请求打到了官方源、账号无读权限
tarball 下载失败 先看报错里的完整 URL，再 curl -I 请求它，最后确认 token 有没有随该 host 发出 tarball host 与 registry 不同、代理拦截、自签证书
装到的还是旧版本 先 npm view @company/utils versions 看服务端，再清缓存、删 node_modules 重装 本地缓存、镜像未同步、版本号没有递增
发布成功但下游看不到 先 npm view 看目标 registry 的 latest，再确认 CI 发布到了哪个源 发到了另一个 registry、publishConfig 覆盖了配置

可以看到，一半的问题落在配置层而不是服务端：token 和 scope 映射只要有一处不对，报错就会指向”包不存在”这个假象。

方案对比与收尾

方案 成本 适用团队 注意
公共 registry + public scope 零运维 本来就打算开源的包 --access public 之后无法收回
公共 registry + 付费私有包 按成员付费 二十人以内、不想碰运维 代码托管在外部，合规要先过
verdaccio 一台机器加磁盘 二十人以内的小团队 sinopia 已停更，verdaccio 刚起步，无高可用
cnpmjs.org 一台机器加 MySQL 需要 Web 管理与内网镜像 权限模型简单，排查靠服务端日志
Nexus 3 / Artifactory 已有制品库时的增量成本 上百人、多语言制品统一治理 要专人维护，配置项多

回到开头那个 bug。私有包上线后，@company/utils 从 1.0.0 发到 1.8.x，三个项目统一改依赖升级，日期问题只修了一次。真正花时间的不是建仓库，而是把命名、scope 映射、token 和发布权限讲清楚，让每个人知道 401 该找谁、404 该看哪一行配置。如果团队只有几个人，先别急着上 Nexus，一个 verdaccio 加一份写清楚的 .npmrc 模板就够了；等到制品类型变多、审计有硬要求，再换也不迟。
