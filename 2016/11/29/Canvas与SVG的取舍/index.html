Canvas 与 SVG 的取舍

同一个组织架构图，我先用 Canvas 写了一版，又用 SVG 重写了一版，两次都踩了坑：前者把点击、悬浮和读屏全部变成手写几何题，后者在节点涨到几千之后开始拖不动。本文不教怎么画图，只谈这两种技术各自把成本花在哪里，以及一个具体需求该往哪边靠。读完之后，你至少能说清楚自己选它的理由，而不是因为”大家都这么用”。

事故：一张组织架构图的两次实现

去年秋天，我接手公司内部人事系统里的一张组织架构图。需求听起来并不复杂：按部门层级展示员工，点击节点打开详情抽屉，悬浮显示岗位与工号，支持折叠展开，还要能通过键盘和读屏访问。第一版我选了更熟悉的 Canvas：节点和连线都要自绘，绘制 API 顺手，样式也好统一。

真正开始写才发现，绘制只是整件事的三分之一。Canvas 上不存在”节点”这个对象，它只有一帧像素。鼠标移到某个位置，我需要自己把屏幕坐标换算回画布坐标，再遍历所有矩形判断落点；悬浮态要靠 mousemove 持续命中检测，并在状态变化时重绘整棵树。键盘访问更麻烦：画布不可聚焦，只能在上面铺一层绝对定位的透明按钮，位置还得随折叠同步。读屏软件读到的是一张位图，除了我写在 aria-label 里的一句”组织架构图”，什么也拿不到。

第二版换成 SVG，事件、焦点、语义几乎立刻到位：每个节点就是一个 <g>，点击监听直接挂在元素上，tabindex 让它进入 Tab 序列，<title> 提供名称，悬浮用 CSS :hover 就够了。那段时间我很满意，直到一家客户导入几千名员工，默认全部展开。页面先是滚动发涩，接着拖拽平移时明显掉帧，折叠一个中层部门要等上半秒。打开开发者工具，DOM 节点数过了五万，样式重算和布局的耗时压在每一帧上。

两次返工让我承认一件事：Canvas 与 SVG 不是新旧关系，它们把成本放在了相反的位置。选错不会立刻报错，只会在需求长出来的那一天集中爆发。

两种模型的本质

Canvas 是立即模式。我调用一次 fillRect 或 stroke，像素就被写进位图，浏览器不记得这里曾经画过一个矩形。下一帧想把某个节点变蓝，只能清空再重画整个场景。它没有场景图，没有元素，没有可查询的结构，只有一块画布和当前像素。所谓”对象”，是我自己在数组里维护的一份数据。

SVG 是保留模式。写进文档的每个 <rect>、<text>、<path> 都是真正的 DOM 节点，浏览器替我们保存这棵树，也负责在属性变化时重新计算样式、布局和绘制。我不需要重画整张图，改一个 fill，只有那个节点及其影响范围需要更新。

这两种模型决定了成本的方向：

  • Canvas 的重绘成本随画布面积、绘制指令数增长，和”有多少个可交互对象”没有直接关系。画一万个点和画十个点，差别主要在指令数上，而不在 DOM 上。
  • SVG 的节点成本随元素数量增长，每个节点都要参与样式计算、布局和命中测试，哪怕它这一帧完全没变。

可以这样类比：Canvas 像一块白板，每次改动都擦掉重画，画完就只剩画面；SVG 像一叠剪好的纸片，每片都能单独挪动、单独上色，但纸片多了，整理这叠纸本身就变成了工作。所以”Canvas 一定更快”和”SVG 一定更清晰现代”都不成立，该问的是：这个场景里，重绘更贵还是节点更贵。

事件与命中检测

Canvas 只会在整个画布上派发事件。event.target 永远是那一个 <canvas>，浏览器不知道你画了什么形状。要在节点上响应点击，得自己做三件事：换算坐标、判断落点、触发逻辑。画布被 CSS 缩放过或内部做过平移缩放时，换算还要乘上逆矩阵。

这段代码只解决了矩形。圆形头像、折线连接、旋转过的标签都要单独写判定；支持缩放后，还得先把点变换回场景坐标。节点叠在一起时，遍历顺序就是层级顺序，改层级等于改数组顺序，很容易出错。悬浮还要在 mousemove 里反复比较命中结果，或维护一张热区表。

SVG 把这件事交给了浏览器。每个 <rect>、<circle>、<path> 都是独立的事件目标，click、mouseover、focus 按元素冒泡，event.target 直接告诉我点到了谁。命中测试由渲染引擎完成，形状、旋转、transform 都不需要我关心。上千个节点挂同一个监听即可，交给父级 <g> 做事件委托。

复杂度的差别不在性能，而在代码量。Canvas 的命中检测是一套自己维护的几何系统，和绘制逻辑是两份需要同步的真相；SVG 里绘制即结构，结构即事件目标，只有一份真相。

可访问性与可搜索性

对读屏软件来说，<canvas> 是一个没有内部结构的替换元素。回退文本只在浏览器不支持画布时显示，正常渲染后不会被朗读；aria-label 能给整张图一个名字，却给不出节点之间的层级关系。要做无障碍，只能在画布外维护一份并行的 DOM 列表，并保证位置、顺序、展开状态同步，这份逻辑最容易在迭代里悄悄腐烂。

SVG 内联在文档里，天生就是可访问性树的一部分。给根节点加 role="img" 和 <title>，读屏会把它当作一张有名字的图；希望逐个节点可读时，就给每个 <g> 加 role="button"、tabindex="0" 和 <title>，再补上键盘的回车与空格处理。文字本身是真正的文本节点，读屏可以按阅读顺序念出来，用户也能用浏览器的查找功能定位到某个名字。

各家读屏对 SVG 的支持并不整齐，2016 年桌面端好于移动端，具体行为必须实测。节点极多时逐个加 tabindex 会让 Tab 序列变成灾难，更合理的是提供并行的列表视图。

可搜索性同理：SVG 文本在 DOM 里，搜索引擎和页面查找都能命中；Canvas 的字只是像素，两者都不存在。图里文字承载业务信息时，这比清晰度更值得在意。

缩放、清晰度与文本

SVG 是矢量的，放大不丢信息。把架构图放大到三倍，线条和文字仍然锐利，因为浏览器是在新的尺寸上重新光栅化，而不是把旧位图拉大。不需要监听缩放，也不必准备多套资源，同一份图放进 A4 打印依然干净。

Canvas 是一张位图。它在创建时就把像素数量定死了，CSS 放大只会把已有的像素拉大，边缘立刻发虚。要让它在高分屏上清楚，必须按设备像素比设置画布尺寸，再在绘制时统一缩放；窗口尺寸变化或用户缩放页面后，还得重新设置并重画。具体怎么算、半像素怎么对齐属于另一个话题，这里只需记住：Canvas 的清晰度是”每次都要主动维护”的状态，SVG 的清晰度是”默认就有”的属性。

文本的差别更直接。SVG 的 <text> 是文本节点，可以选中、复制、被查找、被翻译插件处理，字体变化后浏览器重新排版即可；Canvas 的 fillText 画完就是像素，用户无法选中半个字，也无法用 Ctrl+F 找到它。还有一个坑：自定义字体加载完成后 Canvas 不会自动重画，文字会停在后备字体的形状上，必须监听字体加载事件再补一次。SVG 没有这个问题，字体就绪后浏览器自己会重排。

性能分界：对象数量、重绘频率、改动比例

性能讨论最容易变成站队，我的经验是把它拆成三个可以观察的量。

第一个是对象数量，即场景里有多少独立元素。SVG 的成本几乎线性地压在这上面：每个节点都要参与样式计算、布局与命中测试，节点数上去之后，即使画面完全静止，滚动和缩放也会变慢。Canvas 不关心你有多少”对象”，它只关心这一帧发出了多少绘制指令、覆盖了多少像素。

第二个是重绘频率。Canvas 每改一点都要重画整帧，所以它的成本要乘以每秒帧数；SVG 只在相关属性变化时更新局部，静止时几乎不花力气。每秒重绘六十次的 Canvas，和只在点击时改一个 fill 的 SVG，不在同一个成本模型里。

第三个是单帧改动比例。Canvas 适合整屏都在动的场景，比如拖拽平移、粒子动画，反正要全画，改动比例接近百分之百。SVG 最适合”少数元素在变”的场景，比如悬浮高亮一个节点、折叠一个分支，此时只有局部需要重算。当改动比例很低、元素又很多时，SVG 的优势最大；当改动比例接近全屏、帧率要求又高时，Canvas 更稳。

把这三个量放在一起，可以得到一个粗略但实用的判断：少量对象、交互密集、需要语义与焦点，选 SVG；大量对象、高频重绘、整屏变化，选 Canvas。我不给具体数字，”多少节点算多”取决于设备、节点复杂度和浏览器版本，唯一可靠的办法是在目标机型上实测：打开时间轴，看脚本、样式、布局、绘制四段耗时。我在架构图项目里就是靠这一步发现，拖慢页面的不是连线，而是几千个节点上的阴影滤镜。

动画：属性变化与逐帧重绘

SVG 的动画思路是”改变属性，让浏览器补间”。给节点加一段 CSS transition，之后只改 transform 或 fill，中间帧由浏览器生成；transform 和 opacity 还能走合成层，代价较低。缺点是元素一多，每一帧的样式重算依然按元素计费，几百个节点同时做复杂动画就会吃力。SMIL 在当年已被 Chrome 标记为不推荐，我没有在新项目里用它。

Canvas 的动画思路是”每帧重画”。中间状态都由代码算出，再整帧画一遍。控制力最强，也最费 CPU：哪怕只动一个点，整屏也要重画。它适合元素多、运动密集、样式简单的场景。判断标准还是上一节那三个量。

混合方案

两次返工之后，架构图的最终版本是混合的：连线与网格背景放在底层 Canvas，节点与文字用 SVG 叠在上面。平移缩放时，两边共用同一个变换参数；Canvas 负责画几千条线，SVG 只保留当前视口内的节点。这样既躲开了五万个 DOM 节点，又保住了事件、焦点和文本。

混合的代价是两套坐标系必须严格对齐，任何一边的缩放取整方式不同，文字就会和连线错开半个像素。另一个诱惑是 <foreignObject>：它把 HTML 塞进 SVG，看似能复用现成组件。但它在 IE 上完全不工作，部分浏览器对 CSS 和事件的支持也不完整，我只在内部工具里试过。

典型场景的判断

把上面的维度落到具体需求上，我的结论是：

  • 图表：几十个点的折线、柱状图用 SVG，文字能选中，悬浮提示好挂；上万散点或高频刷新用 Canvas。
  • 地图：底图瓦片本身就是位图，标记和弹窗用 SVG 叠加；轨迹密集或热力层用 Canvas。
  • 图标：SVG，配合 <symbol> 与 <use> 复用，颜色还能跟随 currentColor。
  • 涂鸦：Canvas，笔迹是连续位图操作，SVG 会积累大量路径节点。
  • 小游戏：Canvas，整屏每帧重绘正是它的主场；WebGL 只是 Canvas 的另一条上下文，本文不展开。
  • 打印导出：要矢量打印选 SVG；Canvas 只能按倍数放大画布再导成图片，终究受像素限制。

收尾：一张决策表

选型时我通常先填这张表，再看哪一列更像自己的场景：

维度 Canvas SVG 建议
事件 手写命中判定 元素即目标 交互多选 SVG
无障碍 并行 DOM 原生语义 读屏选 SVG
清晰度 依赖 dpr 重绘 矢量无损 缩放打印选 SVG
性能 随重绘面积 随节点数 高频选 Canvas
文本 像素不可选 可选可检索 检索选 SVG
适用 密集逐帧 稀疏交互 实测决定

两张表都不能替代实测：按对象数量、重绘频率、单帧改动比例判断，再在目标设备上跑时间轴。选错也不必推倒重来，混合往往才是最终形态。
