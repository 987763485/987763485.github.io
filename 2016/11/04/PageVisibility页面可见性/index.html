Page Visibility 页面可见性

上周处理了一个很典型的线上问题：用户把下单页挂在后台，半小时后切回来，页面上一串“网络异常，请重试”的提示，Network 面板里躺着几十个还没结束的请求。这类问题不需要什么高深技巧，缺的只是让代码知道“用户现在看不见我”。本文讲 Page Visibility API 在当时浏览器里的用法、前缀与特征检测，以及在轮询、动画、音视频上怎么暂停和恢复。页面卸载与往返缓存那一套事件不在本文范围，另有专文。

事故：后台标签页在偷偷发请求

出问题的页面有两个“活物”：一个每 30 秒拉一次订单状态的 setInterval，一个用 requestAnimationFrame 驱动的小球动画，外层还套了一个 setInterval 在算时间。

用户的操作很普通：点了“提交订单”，等结果的时候切到另一个标签页看文档。半小时后切回来，看到的是三件事。

第一，轮询每 30 秒一次，半小时大概 60 次。网络不好时请求超时，失败回调弹一个 toast，提示叠满一屏，把订单结果盖住了。

第二，动画的时间基准是 setInterval 里累加的帧数，切回来时一次性补了几十秒的差值，小球直接瞬移出画布。

第三，后端把那几十次轮询算进了“订单状态查询”的监控，下午三点的曲线出现一个尖峰，值班同学一度以为有人在刷接口。

复盘时我把责任分成两半：一半是轮询和动画根本没有“暂停”的概念，另一半是我们默认了“定时器在后台还按原频率跑”。后一半是错的，后面单独说。

Page Visibility API 的三件套

API 本身很小，只有三个东西。

  • document.hidden：布尔值，页面完全不可见时为 true。
  • document.visibilityState：字符串，取值 visible、hidden，以及预渲染状态 prerender。
  • visibilitychange 事件：挂在 document 上，状态变化时触发。

三个值要分清。visible 是用户能看到；hidden 是标签页被切走、窗口被最小化、屏幕被锁、移动端切到别的 App；prerender 是浏览器提前把页面渲染好放在后台，用户还没点进来。prerender 在 2016 年主要是 Chrome 在做，遇到它的时候页面已经在跑脚本了，但用户一次都没看见。

规范里 hidden 的定义是“visibilityState 不是 visible”，所以预渲染状态下 document.hidden 同样是 true。这个细节对我们有利：只关心 hidden 的代码天然会把预渲染当成隐藏，不会在用户没看见的时候发请求、放声音。

前缀与特征检测

什么时候触发，什么时候不触发

会触发 hidden 的情况，比想象中多：切换标签页、最小化窗口、锁屏、移动端切到其他 App、从当前页打开一个新标签并让新标签获得焦点。这些情况下用户确实看不到当前页面，暂停是合理的。

不会触发的情况同样重要。窗口被另一个窗口挡住但没最小化，操作系统一般不会告诉浏览器，页面依然是 visible。把窗口拖到第二块屏幕、调整窗口大小、页面内部滚动到别的位置，也都不算隐藏。iframe 里的 document.visibilityState 跟随的是顶层文档，不是它自己有没有滚出视口，所以别拿它做“元素曝光”统计。

移动端要更保守。部分 Android WebView 在宿主 App 切到后台时并不派发这个事件，微信里不同版本的内核表现也不一致，iOS 上锁屏偶尔只给卸载类事件、不给 hidden。结论是不能把 visibilitychange 当成唯一的清理入口，至少要有一条兜底：在轮询回调里比较 Date.now() 与上一次执行的差值，如果远大于设定间隔，就认为刚刚从后台回来，先做一次状态校准再继续。

该暂停什么，怎么暂停

按“停了会不会丢数据”把页面上的活动分三类。

可以放心停的：轮询、动画、非关键的埋点上报。这三样在后台跑，除了耗流量和耗电没有别的收益。轮询用 clearInterval 停掉，恢复时先手动执行一次再重启，用户切回来就不必再等一个完整的间隔。

需要判断的：视频和音频。不要一律 pause。后台继续放音频是产品的正当需求，音乐、播客类页面靠的就是这个；视频则通常应该暂停，因为用户看不见画面。即使暂停，也要记住 currentTime，恢复时接着播，而不是从头开始。

不能简单停的：WebSocket 和长连接的心跳。心跳停太久，中间的代理或负载均衡会把连接判成空闲而切断，用户回来时手里握着一条已经死掉的连接，下一次发消息必然失败。所以隐藏时不要把心跳停掉，而是把间隔拉长，比如从 20 秒拉到 55 秒，仍留在多数网关 60 秒的空闲阈值之内；恢复时立刻补发一次心跳做探测，失败就走重连。

还有一个反模式要单独说：恢复时算出 (now - lastTick) / interval，再 for 循环补发 N 次请求。轮询要的是“最新的一次状态”，不是“每一次状态”，补发除了制造并发没有任何意义。正确做法是把这段时间折叠成一次立即执行。

不要用 blur 和 focus 代替

这个坑我们真踩过。第一版图省事，用 window.onblur 暂停轮询，理由是“用户切走了才会失焦”。上线第二天就有客服转来的反馈：页面不动了，订单状态一直停在“待支付”。

blur 表达的是“键盘焦点离开了这个窗口”，不是“用户看不见这个页面”。点一下浏览器地址栏、点开开发者工具、在页面里的 iframe 中输入文字，都会让顶层 window 收到 blur，而页面明明就在眼前。我们的下单页右侧嵌了一个客服 iframe，用户点进去问一句话，轮询就停了，这是最典型的误伤。

focus 也不可靠。页面加载时它不一定触发，从后台切回来时它和 visibilitychange 的先后顺序在不同浏览器上并不一致。拿它当恢复信号，偶尔会出现“先恢复后暂停”的错序。

所以这两个事件只能当辅助信号，比如失焦时把动画帧率降下来，但不能用它们决定要不要发请求。判断“用户能不能看见”，只有 visibilityState 说了算。

后台定时器会被降频

即使你什么都没做，浏览器也不会让后台页面的定时器按原频率跑。当年的主流版本会把后台标签里 setTimeout 和 setInterval 的最小间隔抬到 1 秒，同一时刻到期的定时器还会被合并成一批执行；离开得越久，某些版本放得越宽。这件事有三个后果。

第一，你以为“没停”，其实只是“变慢”。我们最初没有停轮询，心想浏览器总会帮忙省电。实测下来，后台半小时仍然发出了近百个请求，只是间隔从 30 秒变成了 30 秒加抖动。流量和监控尖峰就是这么来的。

第二，“每 200ms 一次”的高频逻辑在后台退化成一秒一次，界面上看不出来，业务语义已经变了。想用轮询做“准实时”的方案，得重新评估。

第三，恢复的瞬间会有一批定时器同时到期，回调扎堆执行。我们的页面上，轮询、埋点 flush、配置拉取三个定时器几乎同时触发，弱网下互相抢连接，最慢的一个拖到八秒才回来。

结论很直接：不要对后台定时器的频率做任何假设。要么在 hidden 时明确 clear 掉，把控制权拿回来；要么保留定时器，但所有“经过了多久”的判断都基于 Date.now() 的时间戳，而不是基于回调执行了几次。写 count++ 再判断 count > 10 的代码，在后台一定是错的。

恢复时怎么处理状态

恢复比暂停难，因为要做决定。我的做法是记录隐藏时刻，回来时按离开时长分档处理：

30 秒以内回来，页面上的数据大概率还有效，什么都不做最省，也不会让界面闪一下。30 秒到 5 分钟，拉一次关键接口，把订单状态、库存、价格这些会变的东西更新掉。超过 5 分钟，情况可能已经变了：订单被支付、被取消、商品下架。这时要考虑整块重渲染，甚至在页头提示“数据可能已过期，点击刷新”。但不要无脑 location.reload()，用户填了一半的地址表单会全部丢失，这比数据旧更让人恼火。

恢复瞬间的并发也要处理：恢复、点“重试”、定时器到期，三个入口可能在同一秒进来，各发一次就是三次重复查询。给刷新函数加一个 in-flight 标记，后来者直接返回，等第一次的结果落地后统一更新界面。

这个守卫很土，但它把“恢复瞬间三连请求”压成了一次，也顺带解决了用户连点重试按钮的问题。

埋点：离开不等于结束

最后一个容易犯错的地方是统计。不少团队把 hidden 的时刻直接当成“用户离开页面”，用来算停留时长，结果数据一直偏低而且碎片化。原因很简单：切走可能只是回一条消息，十几秒后回来；锁屏可能只是接了个电话；而移动端进程被系统杀掉时，一个事件都不会有。

我的建议是成对上报，而不是单点上报：

  • hidden 时发一条 pause，带上时间戳和页面内的会话 id。
  • 恢复时发一条 resume，服务端按会话 id 把两条配对，累加出真正的可见时长。
  • 只有 pause 没有 resume 的会话，单独标记为“未正常结束”，不要混进平均停留时长，否则均值被拉低，你还找不到原因。
  • 恢复时不要重复上报一次页面浏览，否则 PV 直接翻倍。用 sessionStorage 里的标记判断是不是同一次会话内的恢复。

发送方式也有讲究。hidden 之后页面可能很快被冻结或丢弃，普通的异步 XHR 有被中断的风险。较新的浏览器提供了 navigator.sendBeacon，可以在隐藏时把事件放进队列，由浏览器负责发完；不支持的就退回同步 XHR，但只能发很小的包，别在里面塞一整段日志。

这套东西的目标不是把数据做漂亮，而是让“用户真的在看”和“页面还开着”变成两个可以区分的量。前者才是产品该优化的指标。

场景对照表

把这半年遇到的场景整理成一张表，贴在团队文档里，新页面接入时逐条对一遍：

场景 该做什么 不该做什么
切到后台 30 秒内回来 什么都不做，继续原有节奏 立刻整页刷新
切到后台超过 5 分钟 拉一次关键数据，提示可能过期 补发积压的每一次轮询
页面隐藏期间 明确清掉轮询与自建动画计时器 指望浏览器自动降频省电
恢复瞬间 单入口加锁，多次触发合并成一次 轮询、埋点、配置三路并发
页面内 iframe 获得焦点 忽略 blur 用 blur 判断页面隐藏
移动端切到其他 App 停轮询，心跳拉长间隔 直接断开长连接
后台继续放音频 保持播放，记住播放位置 一律 pause
统计停留时长 pause 与 resume 配对，标记异常结束 把 hidden 当作会话结束
老浏览器与 WebView 用 'hidden' in document 做特征检测 写 document.hidden === false

这张表里没有一条需要新框架或新工具，全部是十几行代码的事。真正花时间的不是写，而是想起来要写——以及在上线前，真的把标签页切走半小时，再切回来看一眼。
