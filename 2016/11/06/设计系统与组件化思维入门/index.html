设计系统与组件化思维入门

去年到今年，我陆续接手三条业务线的后台：商家管理、内容审核、数据报表。它们由三个小组分别维护，技术栈一半是 React 15，一半是 Vue 2，样式各写各的。今年夏天做账号打通，用户第一次能在三套后台之间跳转，问题全暴露出来。本文记录我们怎么从“三套弹窗”走到一份能维护的组件清单，适合被重复 UI 拖住、又不想一上来就造组件库的团队。

一个“确认删除”的四种间距

账号打通上线第二周，客服转来一张截图：同一个商家，在商家后台点“删除商品”弹出的确认框，和跳到内容后台点“删除素材”弹出的框，长得完全不像一家人。我们把这半年的截图翻出来量了一遍，光是“确认删除”这一种交互，就有四种内边距：16px、20px、24px，还有一种上下 24px 左右 16px。按钮文案三种：“确定”、“确认”、“删除”。主按钮颜色两种，一种走品牌蓝，一种走危险红，而两个红还不是同一个红。

更麻烦的是行为。商家后台点确定后按钮变成“处理中”，禁用但不变文案；内容后台弹一个全屏 loading；报表什么都不做，请求回来才关闭，用户在这两秒里可以连点五次。三条线都觉得自己对，因为各自都接过需求，各自都改过 bug。

我最初想直接写一个通用 Modal，三条线都换掉。真动手才发现，报表的确认框要求用户手输素材编号才能删，商家后台要提示“该商品有 3 个订单待发货”。这些差异不是谁偷懒，是业务真的不一样。问题不在“没人写组件”，而在三条线没有共同的词汇：同一个东西，有人叫 Modal，有人叫 Dialog，有人叫弹层；同一个“危险操作”，有人用红按钮，有人用红文字。

这次事故之后我们定了一条规矩：先别写组件，先把大家嘴里的词对齐。组件化的第一步不是抽象，是命名和盘点。

先盘点，再抽象

盘点的方法很笨：花一周把三条线近三个月的上线页面截图收集起来，逐个数按钮、输入框、弹窗和提示。数字很难看：按钮 47 种写法，输入框 31 种，弹窗 19 个实现，轻提示 12 种，其中 5 种是用 setTimeout 加绝对定位拼的。47 种按钮里视觉上能区分开的只有 5 类，剩下 42 种是同一类东西在不同页面上的漂移。

盘点的产出不是代码，是四张清单：出现位置、出现次数、与其他实现的差异点。第三列最关键，它逼我们回答“这个差异是业务需要的，还是历史遗留的”。判断标准有三条：

  • 差异只影响颜色、尺寸、圆角，归为同一组件，用属性表达；
  • 差异影响内部结构，比如有没有图标、有没有副标题、有没有额外的输入区，考虑拆成两个组件或加 slot；
  • 差异只在一个页面出现一次，先不做，留在页面里。

按这个标准过一遍，19 个弹窗收敛成 3 个：普通确认框、带表单的对话框、纯展示的大图预览。12 种轻提示收敛成 1 个，因为它们的差异全是位置和时长，属于配置。输入框收敛成 2 个：单行文本和带前后缀的组合输入。

还有一个反直觉的发现：调用频率分布极不均匀。前 6 个组件覆盖了大约八成的调用点，剩下四十多个“组件”每个只被用了一两次。这直接决定了投入顺序——先把这 6 个做扎实，长尾那些宁可继续散落在页面里。抽象一个只用过一次的东西，等于把一次性的偶然固化成长期负债。这份表每季度更新，比设计稿更能说明系统实际长什么样。

组件的边界：什么该做，什么不该做

盘点之后最容易走的另一个极端，是把什么都做成组件。我们中间试过一版“商品卡片”，为了兼容三个页面，props 加到 17 个：是否显示价格、是否显示销量、标签最多几个、图片比例、点击跳转方式。新人改它要先读四十行默认值。这不是复用，是把三个页面的差异塞进一个文件里打架。

后来我们用三个问题判断边界：它在三个以上互不相干的位置出现过吗？它的语义稳定吗——“按钮”“输入框”“对话框”是稳定的，“带角标的横向商品条目”下个版本可能就没了；它有独立于页面的状态吗？有加载、禁用、错误的适合收进组件，纯粹的结构拼接用一个样式类就够了。

第三条最容易被忽略。我们有个“空状态”区块，做成组件接收图标、标题、描述、按钮文案四个参数。用了半年发现，四个业务的文案和图标各不相同，组件唯一贡献是把 text-align: center 包了一层，最后降级成一个样式类。组件不是越多越好，标准是它有没有消除重复的决策，而不只是重复的标签。

“可复用”和“必须复用”是两件事。一个组件可以被复用，但当下的页面只有一处用它，硬抽出来只会让读代码的人多跳一次文件。我们现在的做法是：第一次写在页面里，第二次出现时复制，第三次出现时才抽。这个“三次法则”很土，却避免了我们早期最大的浪费——为想象中的复用付设计成本。

输入、输出与受控的取舍

组件对外只有两件事：接收什么，发出什么。输入分三类：配置，比如 type、size，组件据此选样式；数据，比如输入框的 value、列表的 dataSource；插槽，用来填补结构上的不确定，比如对话框的正文区、卡片的右上角操作区。React 里是 children 和具名 prop，Vue 2 里是默认 slot 和具名 slot，叫法不同，思路一样：结构交给调用方，样式和交互留在组件里。

输出统一走事件，不让父级去改子组件的内部状态。对话框关闭、输入变化、分页跳转，都通过回调抛出去。旧代码里就有组件直接改 props 上的对象字段，两个页面共享一份引用，A 页面删一行，B 页面跟着少一行，查了两天。

真正要讨论的是受控与非受控。输入框完全受控，数据单一来源，但父级忘记回写，输入框就像卡住一样打不出字；每次按键都触发父级重渲染，长表单会变慢。完全非受控则拿不到实时值，联动校验很别扭。

我们的取舍按“是否需要实时干预”分。搜索框、金额输入这种要即时校验的做受控；普通文本项用非受控加初始值，提交时统一取值。对话框显示与否必须受控，因为开关时机往往由请求结果决定。分页器半受控：当前页可由外部指定，也可自己维护，但切换一定抛事件。这套规则写在组件文档第一屏，比实现细节更重要。

状态矩阵：一个按钮有八种样子

今年三月出过一次重复下单：按钮提交后只是“看起来”禁用了，颜色变了，点击处理没动，用户连点三次，后端收到三个请求。这让我们意识到，“禁用”不是一种颜色，而是一组行为与视觉的约定。

每个交互组件固定列八项状态：默认、悬停、按下、聚焦、禁用、加载、错误、空。不是每个组件都有八项，但只要存在，就必须同时定义视觉和行为。按钮的加载态，视觉上是文案旁边一个转圈、宽度不跳动；行为上拦截点击、不触发第二次提交、保留焦点。输入框的错误态，边框变色加一行说明，说明文字要被读屏软件关联到输入框。

状态 视觉 行为
默认 常规底色与边框 可点击、可聚焦
悬停 底色加深一档 不改布局、不弹提示
按下 再深一档并轻微位移 松开才触发，允许移出取消
聚焦 可见轮廓，不能只靠颜色 键盘可达，Tab 顺序正确
禁用 降透明度并去阴影 不响应点击，不进入 Tab 序列
加载 转圈或骨架，尺寸锁定 拦截重复提交，保留可读文案
错误 边框与说明文字同时变化 说明与控件关联，提交时汇总
空 占位说明加一个主操作 不显示“暂无数据”就完事

这张表最初只有视觉列，是前端同学坚持加了行为列，理由是“设计稿画不出点击之后发生什么”。后来它成了整份规范里最有价值的一列，把讨论从“灰色好不好看”拉回“用户能不能操作”。

命名与 API：别为每个业务加开关

组件 API 比实现更容易留债。我们最早的主按钮用 type 表示外观（primary、danger），又透传原生按钮的 type=“submit”，同一个属性名承担两件事，业务方写 type=“submit” 时按钮变成默认样式。后来外观改成 variant，type 还给原生语义。

第二类债是布尔开关。为了不改调用方，表格加过 showDelete、showEdit、isOrderDetail 这类属性，半年后攒了九个布尔值，组合五百多种，没人知道哪种对。现在的规矩是：凡是“这个业务要不要某东西”，改成数据驱动或插槽，把判断交给调用方；只有影响组件自身形态的才允许布尔，比如 disabled、loading。

尺寸也别用数字。size=“14” 下一个人会问是字号还是高度。我们用 sm、md、lg 三档，文档写死每档像素，不开放任意值。命名尽量用业务无关的词：danger 比 delete 好，删除以外的危险操作也能用；ghost 比 link 好，它描述外观而不是用途。

文档、示例与版本

每个组件一页文档，固定四段：用途（何时用、何时不用）、禁止用法（配真实误用截图）、可访问性要求（焦点可见、键盘可操作、读屏文案）、属性与状态表。示例代码不手抄，构建时从 example 目录抓进来编译，示例坏了构建就红，这是文档不腐烂的唯一办法。视觉 token 的消费另有专文，组件只引用，不自己定义色值。

版本按 SemVer：修 bug 走 patch，加属性走 minor，删属性或改默认行为走 major。废弃不搞突然死亡：文档标“已废弃”，开发环境打一次警告，至少留两个 minor 再移除。升级成本要提前算，我们给 major 配了 codemod 和对照表，三条线分三个月升。指望一次统一，结果通常是某个业务在发版前夜回滚。

推广与治理：先服务，再抽取

别先建平台，先服务一个业务。我们选调用点最多的商家后台，把 6 个组件做进去，陪跑两个迭代，坑都在真实排期里修。第二个业务接入时组件已稳，推广从“我们去推”变成“别人来问”。设计评审看结构：有没有用已有组件、差异是否必要；代码评审看实现：有没有绕开组件写私有样式、为业务加开关。两边各一人把关就够，不设委员会。维护人由两位前端轮值，避免组件只属于一个人，也避免谁都不管。

什么时候不该做设计系统

三种情况别做：团队不到十人、只服务一个业务、半年内看不到第二个接入方，此时做设计系统只是给自己加一层审批。业务差异极大时，强行统一会把差异挤进 props，得到一个谁都不敢改的巨型组件。维护成本也要算：组件、文档、评审、升级四条线都要人，缺一条就烂尾。小团队更实际的做法是一份 CSS 变量加十来个组件，够用也改得动。

收尾：一张能贴墙的表

下面是现在的主干清单，新人入职第一周要背下来。

组件 状态 关键属性 常见误用
按钮 默认、悬停、按下、聚焦、禁用、加载 variant、size、loading 只把禁用画成灰色，不拦点击
输入框 默认、聚焦、禁用、错误 value、defaultValue、status 受控却不回写，输入像卡住
对话框 打开、加载、错误、关闭 visible、onOk、onCancel 关闭时不清表单，下次带旧值
提示 出现、消失 type、duration 用全局提示代替字段级错误
表格 空、加载、错误、选中 dataSource、rowKey 用数组下标当 key

写到这里，我的结论比两年前朴素：设计系统不是一套组件，而是一组被团队共同承认的约定。组件只是载体，真正省时间的是“遇到确认删除时不用再问该用哪个词”。
