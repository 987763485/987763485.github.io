Page Lifecycle 与页面生命周期

2016 年秋天，我们把一个售后表单改成移动端优先，上线三天就收到客服转来的投诉：用户填到一半切去微信回消息，回来页面已经重载，内容全没了。我起初以为是自己监听错了事件，翻了两天文档才明白，在移动端，unload 这类事件根本不能当作保存的依靠。

本文按我踩坑的顺序，把 load、DOMContentLoaded、beforeunload、unload、pagehide、pageshow、visibilitychange 的触发时机与可靠性讲清楚，最后给出一套 2016 年就能落地的保存方案。适合正在做表单、编辑器与埋点上报的前端同学。

一次丢数据的复盘

出问题的页面是一个售后申请表单，七个字段，其中两个是长文本。产品的要求很朴素：用户填到一半去接电话、回微信，回来还能接着填。我当时的实现是在 window 上监听 unload，回调里用同步 XMLHttpRequest 把表单序列化后发给后端。桌面端自测时它工作得不错，关标签页能存上，我就当作完成了。

上线后问题来了。Android 用户切到微信再切回来，页面白屏重载，草稿为空；iOS 上表现更奇怪，有时能存上，有时连请求都没发出去。桌面端也不是全好，用户点后退回到列表页再点进来，草稿同样没了。客服把这些反馈汇总过来时，我第一反应是接口偶发失败，查了日志才发现：请求根本没到达服务端，不是失败，是没发。

那次排查让我把问题拆成三件事分开看：事件到底有没有触发、触发时页面还有没有执行代码的机会、请求有没有在页面被销毁前离开浏览器。这三件事在桌面端与移动端上的答案完全不同，而 unload 只在最理想的那一种组合里成立。

事件全景：谁在什么时候触发

先按时间线把这几个事件摆好，后面的取舍才有依据。一次正常的首次打开大致是：HTML 解析到脚本与样式就绪时触发 DOMContentLoaded，图片、样式、iframe 等子资源加载完后触发 load。这两个事件与“离开”无关，但它们是初始化的分界线：DOMContentLoaded 之后 DOM 可操作，load 之后才谈得上资源完整。

用户开始交互之后，事件分成两条线。

第一条是可见性线：切标签、切应用、锁屏、最小化，都会让页面从可见变为隐藏，触发 visibilitychange。这条线在页面生命周期里可以反复来回，是最碎也最及时的信号。

第二条是卸载线：真正要离开页面时，桌面浏览器先给 beforeunload，可以在这里弹确认框，然后 pagehide，最后 unload。pagehide 在 2016 年的 Chrome、Firefox、Safari 上都已经可用，它的特殊之处是带一个 persisted 属性，用来表示页面是被销毁还是被放进往返缓存。

如果是后退或前进回到一个被缓存的页面，load 不会再触发，取而代之的是 pageshow，此时 event.persisted 为 true；如果是全新加载，pageshow 也会触发，但 persisted 为 false。这一点很关键：很多初始化逻辑写在 load 里，从缓存恢复时它不会跑第二遍。

顺序上还有两个容易忽略的细节：visibilitychange 通常早于 pagehide，所以在移动端它往往是最后一个一定能跑到的回调；unload 在 pagehide 之后，但它能否执行，取决于浏览器是否决定销毁这个页面。

还有一件和绑定时机有关的事：如果脚本放在 body 末尾，DOMContentLoaded 可能已经错过，此时要用 document.readyState 判断；pageshow 在首次加载时同样会触发，绑定得足够早才不会漏掉从缓存恢复的那一次。我们的做法是把生命周期监听统一放进头部的一个小脚本，业务逻辑通过回调注册，避免各处零散绑定。

beforeunload 的正确用途只有一个

beforeunload 是唯一能让浏览器弹出“确定要离开吗”的事件，但它比想象中受限得多。首先，它只在用户有过交互（点击、输入、滚动）之后才会被浏览器认可，纯脚本跳转通常不会给弹窗机会。其次，弹窗文案不由你决定，Chrome、Firefox、Safari 都显示自己的通用句子，returnValue 里写什么都一样，所以别在里面写“您的草稿将丢失”这种期望被读到的内容。

代码上就是两行：判断脏状态，返回一个非空字符串。

真正的问题是移动端：Android Chrome 对 beforeunload 基本不弹，iOS Safari 在切应用、锁屏、从任务列表划掉时也不会给确认的机会。把它当成桌面端的误关保护可以，当成保存时机的兜底一定失望。更不要在一个可能被阻塞的弹窗里发请求，用户点“取消”之后请求已经发出去了，状态却还是脏的，下一次提交就重复了。

unload 为什么指望不上

unload 看起来最像“页面关闭时执行”的钩子，实际却是这批事件里最不可靠的一个。

第一是往返缓存。Chrome 与 Firefox 会把离开的页面整体存进内存，用户点后退时原样恢复，JS 状态、滚动位置都在。既然是恢复而不是重建，unload 自然不触发，load 也不触发。我的表单页正是死在这里：用户后退再前进，草稿从来没有被保存过。

第二是移动端的进程回收。页面切到后台后，系统在内存紧张时直接杀掉渲染进程，没有任何事件，也没有任何回调。这不是浏览器的 bug，是移动操作系统的内存管理方式，前端没有办法拦截。

第三是请求来不及发完。就算浏览器决定走正常卸载流程，unload 里发出的异步 XMLHttpRequest 也会随页面销毁被中断；我最初改用同步请求绕开中断，代价是关闭时界面卡住，而移动端依旧连执行的机会都没有。navigator.sendBeacon 在 2016 年的 Chrome 与 Firefox 上已经可用，它把请求交给浏览器在后台发送，解决了“发不出去”的问题，但解决不了“没有触发”的问题：进程被杀掉时，那段代码根本没有执行。

所以我后来的结论很干脆：unload 用来清理计时器、断开 WebSocket 这类“尽力而为”的事可以，用来保存用户数据不行。

pagehide 与 pageshow：bfcache 的两个门

pagehide 是卸载线上唯一值得依赖的事件。桌面端关闭标签、跳转、刷新时都会触发，移动端切应用时也常能触发。它的 persisted 属性告诉你页面接下来是被销毁（false）还是被放进往返缓存（true）。

bfcache 的现实影响比多数人以为的大。点后退回到列表页时，页面不会重新请求 HTML，DOMContentLoaded 与 load 都不会再跑，计数器、轮询定时器、长连接都停在离开前的那一刻。如果后端数据在这期间变了，用户看到的是旧快照，而他以为页面刚打开。我的做法是在 pageshow 且 persisted 为真时做一次静默刷新，同时重置那些假设页面刚初始化的标记，比如清掉 loading 状态、重新拉起轮询。

还有一个坑：不要假设进了 bfcache 就安全。浏览器随时可能因内存压力清掉缓存，页面里如果有 unload 监听、开着未提交的 IndexedDB 事务，也会直接失去缓存资格。2016 年各家实现差异不小，能做的只是把两条路径都覆盖。

visibilitychange：最后一个一定跑得到的信号

visibilitychange 是这套事件里最接近“一定触发”的一个。切标签、切应用、锁屏、下拉通知栏、最小化窗口，都会让页面变为隐藏并触发它。它不承诺页面会被销毁，也不承诺之后还能回来，但它是页面失去执行机会之前最稳定的一次回调。

对保存来说，这个信号的价值在早。用户在移动端切走应用的那一刻它就触发，此时进程还活着，网络栈正常，请求发得出去；等系统真的决定杀进程，往往已经过去几十秒甚至几分钟。把保存放在这里，等于把窗口从进程被杀前的一瞬提前到了用户离开的第一时间。

代价是它触发得太频繁：下拉一下就隐藏，切回来又可见。所以回调里不能直接提交，要先判断数据是否真的有变化，再做防抖。这个事件的状态值与兼容写法同批另有一篇专文，此处只把它当作生命周期的一环使用。

保存策略：输入防抖加两道兜底

最终落地的方案分三层。

第一层是输入防抖。长文本的 input 事件后 800 毫秒把内容写进 localStorage，只做本地落地，不发请求。这一层保证即使后面所有事件都没跑到，用户重新打开还能恢复。

第二层是 visibilitychange 上报。页面变为隐藏时立刻提交，不等防抖，同时记下提交时的内容版本号。

第三层是 pagehide 再补一次。persisted 为真时跳过，为假时用 sendBeacon 发出去。三层共用同一个版本号做幂等键：服务端只接受版本号比已存草稿更大的请求，重复到达的直接丢弃，于是“防抖一次、隐藏一次、卸载一次”最多只有一次真正落库。

两个细节：flush 里把 dirty 置为 false 只是本地去重，服务端仍要按版本号判重，因为请求可能丢；另外别在 visibilitychange 里做重活，移动端留给回调的时间很短，序列化大对象会拖慢切后台的响应。

恢复也要讲顺序。页面重新加载时，先读 localStorage 里的草稿填回表单，再拉服务端版本比对，取版本号大的那个；如果用户是从 bfcache 回来的，本地草稿与内存状态都在，就不该覆盖，只做一次服务端校验。这个判断放在 pageshow 里比放在 load 里可靠，因为缓存恢复时 load 不会再来一次。

Page Lifecycle 提案：方向对了，2016 年还没落地

Chrome 团队在 2016 年提出了 Page Lifecycle 统一 API 的设想，想在 document 上补三个状态与对应事件：freeze 表示页面被挂起、定时器与任务队列暂停，resume 表示恢复执行，discarded 表示页面被浏览器丢弃、下次需要重新加载。目标是把今天靠一堆事件拼出来的状态机，变成浏览器明确告知的一件事。

需要说清楚：这套 API 在 2016 年还只是提案，没有任何浏览器实现，Firefox 与 Safari 甚至没有公开表态。所以生产代码里没有监听 freeze、resume、discarded，只在团队文档里记了一笔方向：等它落地，visibilitychange 与 pagehide 的很多判断可以简化，被冻结的页面也不必再猜自己是不是还活着。

这套划分的借鉴意义在于：页面不是“打开”与“关闭”两个状态，中间还有可见、隐藏、冻结、丢弃；按这个模型去想保存时机，比按事件名去背清单可靠得多。

怎么验证保存真的发出去了

这类问题最难的是“看起来好了”。我的清单分四组，全部在真机上做，不只看桌面 Chrome。

桌面端：切到别的标签页停十秒再回来，看 Network 里有没有草稿请求；最小化重复一次；直接关标签页，看请求是否在关闭前发出。

移动端：Android 与 iOS 各一台，切到微信再切回、锁屏三十秒再解锁、从任务列表划掉应用。最后一种最容易被忽略，也最容易丢数据。

bfcache：从列表页进入详情页，点后退再点前进，确认页面状态是否保留。开发者工具的 Network 面板能看出页面有没有重新请求 HTML。

判断请求是否到达不能只看前端回调。我们给草稿接口加了埋点日志，按用户 ID 和时间查服务端记录，前端再用 sendBeacon 的返回值做粗判。只有服务端有记录，才算保存成功。

事件与可靠性对照

事件 触发时机 可靠性 适合做什么
DOMContentLoaded DOM 解析完成 高 绑定事件、初始化 DOM
load 子资源加载完成 高，bfcache 恢复时不触发 依赖图片尺寸的初始化
beforeunload 即将离开，桌面端可弹确认 低，移动端基本不弹 桌面端误关提醒
unload 页面销毁前 很低，缓存恢复与进程回收都不触发 尽力而为的清理
pagehide 页面隐藏或卸载 较高 最后一次上报，配合 sendBeacon
pageshow 页面显示，含缓存恢复 高 判断 bfcache、刷新数据
visibilitychange 可见性变化 最高 保存、暂停与恢复

一句话总结：把保存放在 visibilitychange 与 pagehide，把保护交给 beforeunload，把 unload 当成可选项，把 load 只当作初始化的一次机会。2016 年的浏览器给不了“页面一定会通知我”的承诺，能做的只是多留一条后路。
