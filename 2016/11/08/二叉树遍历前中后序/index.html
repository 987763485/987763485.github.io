二叉树遍历：前中后序

本文属于《算法与数据结构》第 10/13 篇
上一篇系列目录下一篇

上周五下班前一个小时，权限配置页被测试打回来：左侧权限树的父子顺序全乱，勾选父节点时子节点没有跟着联动。接口返回的是一个扁平数组，每个元素带着 id 和 parentId，前端同学图省事，直接按数组顺序画了出来。那天晚上我把遍历重新写了一遍，这篇就是当时的笔记：三种深度优先的访问顺序、递归与迭代的写法、层序，以及怎么从遍历序列把树还原回去。

事故：扁平数组不是树

接口给的数据大概是这样，顺序完全取决于数据库怎么返回，父节点可能排在任何子节点后面：

前端直接 forEach 往 DOM 里塞，看到的结果是“导出报表”跑到了“订单管理”上面。正确的做法是先按 parentId 把扁平数组组装成树，再对树做一次遍历，按访问顺序渲染。组装那一步是哈希表的事，遍历这一步才是本文的主题。后来我养成了一个习惯：凡是树形 UI，先问清楚数据是扁平的还是嵌套的，再决定在哪一层做排序。

当时我的第一反应是按 id 排序再渲染，试了一下发现没用：id 只保证唯一，和层级没有关系，父节点 1 的孩子可能是 3 和 7，排完序父子还是不相邻。树里的先后只能由遍历定义，这也是我后来坚持“先建树、再遍历”的原因。

用对象表示一棵二叉树

二叉树的最小表示只要三个字段：值、左孩子、右孩子。空节点用 null 表示，不额外造一个“空节点对象”，否则判断会没完没了：

这棵树里 A 是根，B、C 是它的两个孩子，D 挂在 B 的左边。空的地方就是 null，遍历时遇到 null 直接返回，这是所有递归写法共同的终止条件。节点的值在实际项目里别只放标题，最好连 id 和类型一起带上，渲染时要用它做 key，遍历时也要靠它认出当前处理的是谁。业务里常见的权限树、目录树是多叉的，把 left 和 right 换成一个 children 数组即可，遍历的骨架不变。这里不展开用数组下标表示完全二叉树的做法，那是堆的领域，另有专文。

递归三序：只差一行

递归写遍历，三个函数的骨架完全一样，区别只在“什么时候访问节点”。所谓访问，就是把它记下来或者渲染出去，下面用往数组里追加元素来代替。

拿上面那棵树跑一遍：前序是 A B D C，中序是 D B A C，后序是 D B C A。前序的第一个元素一定是根，后序的最后一个元素一定是根，中序里根把左右子树分成两段，这三条性质后面重建树的时候还要用。

选择哪一种，取决于你想在什么时候处理父节点。渲染目录要先有父再有子，用前序；表达式树求值要先算完两个操作数，用后序；二叉搜索树要按顺序输出，用中序。三个函数只差一行的位置，但把这一行挪错，业务语义就完全变了。

递归的调用栈：深度是真的会爆

递归能工作，是因为每次调用都在调用栈上压一帧，帧里存着参数和返回地址。树有多深，栈就有多深。V8 的栈空间有限，一棵几万层的单链树就能让 RangeError: Maximum call stack size exceeded 出现在控制台里，而且报错的位置往往在渲染函数里，看起来和遍历毫无关系。

业务树的深度通常没到阈值：权限树三四层，商品分类五六层，组织架构撑死十几层，所以大多数时候递归写得快也读得懂。但不能假设它永远这样。我遇到过一次导入历史数据，某个节点的 parentId 指向了自己，组装时没有校验，结果造出一条两万层的链，遍历直接崩在渲染之前。还有把目录树做成通用结构的产品，用户能无限建子目录，深度由用户决定，代码里却没有任何一处按深度设防。

防御有两个方向：一是组装树时检测环、限制最大深度，把脏数据挡在渲染之外；二是把递归换成显式栈的迭代写法，栈放在堆上，深度只受内存限制，每一帧只是一个对象引用，比调用栈的帧轻得多。下面几节都是第二个方向，顺序和递归版必须完全一致，否则渲染出来还是错的。

迭代前序：先压右再压左

前序最简单。用一个数组当栈，先把根压进去，然后循环：弹出一个节点就访问它，再把它的右孩子、左孩子依次压栈。因为栈是后进先出，左孩子后压就会先出来，正好符合“根、左、右”的顺序。

空节点不压栈，省掉了弹出后再判空的分支。每个节点进栈一次、出栈一次，时间复杂度和递归版一样是线性的。这段代码我第一次写反了压栈顺序，输出变成 A C B D，一眼看像对的，因为根确实在最前面，但左右颠倒了。后来养成习惯：写完先拿那棵四节点的树对一遍，再往业务数据上套。

迭代中序：一路向左

中序稍绕一点。思路是把“当前节点”这个概念留住：只要节点不为空，就压栈并往左走；走到空时，说明左边到底了，弹出栈顶访问，然后转向它的右子树，重复这个过程。循环条件是节点不为空或者栈不为空，两者缺一不可。

拿 A、B、C、D 那棵树逐步推一遍。先把 A、B、D 依次压栈，D 的左边是空，弹出 D，输出 D，转向 D 的右孩子，是空；此时栈里是 A、B，再弹出 B，输出 B，转向 B 的右孩子，也是空；接着弹出 A，输出 A，转向 A 的右子树 C；C 压栈后左边为空，弹出 C 输出，右孩子为空，栈也空了，循环结束。结果是 D B A C，和递归版一致。

注意内层循环结束后不要急着把 node 置空，它已经被赋成右孩子了。我第一次把右孩子的赋值写在弹出之前，结果死循环，浏览器直接卡死，最后靠断点才看出来。另外，栈里存的应该是节点引用而不是值，业务节点的值可能重复，只留一个值，弹出来之后就没法继续往下走了。

迭代后序：记住上一个访问的节点

后序是三种里最容易写错的，因为父节点要等两个子树都处理完才访问，而栈只能告诉你“现在在哪”，看不出“右边走完没有”。

单栈的做法是：仍然一路向左压栈，但弹栈之前先看栈顶的右孩子。如果右孩子存在，而且不是上一次访问的节点，说明右子树还没走，把当前节点转向右孩子；否则才可以弹出、访问，并把它记成“上一个访问的节点”。

为什么非要 lastVisited？因为右子树非空时，从左子树回到父节点、和从右子树回到父节点，栈顶是同一个节点，光看右孩子是否为空区分不了这两个时刻。lastVisited 记的是真正被输出过的最后一个节点，只要栈顶的右孩子等于它，就说明右边刚走完，可以访问自己了。

另一种写法是双栈：先按“根、右、左”压栈得到一份序列，再整体反转。代码更短，但多一个数组，还要额外解释为什么反转之后就成了后序。我最后留在项目里的是单栈版，因为打断点时栈里的内容和递归走过的路径一一对应，排查顺序问题更省事。

层序遍历：队列与每层长度

深度优先用栈，广度优先用队列。层序真正的难点不是“用队列”，而是“怎么知道一层结束了”。做法是在每轮循环开始时记下队列里剩余的节点数，这个数就是当前层的节点数，本轮只处理这么多个，新加进来的都属于下一层。

这里用 head 下标代替 shift。shift 每次都要把后面的元素往前搬，节点一多就是白白的时间开销，用一个只增不减的下标读队列，效果一样，代价小得多。上面那棵树跑出来是三层：先是 A，然后是 B 和 C，最后是 D。

层序在业务里用得比想象中多：权限树默认只展开前两层，就是按层取；找两个节点的最近公共祖先，先按层序记下每个节点的父节点，再往上爬比较直观；算树的宽度，也是数每层有多少节点。它没有递归三序那种一行之差的美感，但输出的结构天然适合渲染和分批加载。

由遍历序列重建

只给前序是还原不出来的：A B D C 里，D 到底挂在 B 的左边还是右边，序列里没有任何信息。要唯一确定一棵二叉树，必须有一条中序，因为只有中序能划出“哪些节点在左、哪些在右”。

前序加中序的做法是：前序的第一个元素是根，在中序里找到它，左边一段就是左子树的中序，右边一段是右子树的中序；两段的长度回到前序里，就能切出左子树和右子树的前序，然后递归。

这段代码有两个前提：节点值互不相同，否则 indexOf 找到的可能是另一个同名节点；切分区间不能错，尤其是 slice 的右边界不含，左子树的前序是 1 到 index + 1，右子树从 index + 1 开始。indexOf 每次都是线性扫描，整棵树重建下来是平方级的；节点上千以后，可以先用一个对象把值到下标的映射建好，把这一步拉回线性，导入大权限表时这点差别很明显。后序加中序完全同理，只是根从后序末尾取，切分区间跟着挪一位。

前序加后序不行，最小的反例只有两个节点：前序 A B，后序 B A，B 既可以是 A 的左孩子，也可以是右孩子，两棵不同的树给出了完全相同的两条序列。缺了中序，就没有任何信息能区分这两种形状。判别依据其实很朴素：每个节点在序列里只出现一次，能确定的只有“谁是根”，确定不了它挂在哪一侧。我在一个导入功能里见过有人只存前序和后序，以为信息很全，结果导进来的树结构全变了，权限继承跟着错，查了半天才发现问题出在这里。

实际用途与对照表

表达式树求值是最典型的后序：数字是叶子，运算符是内部节点，必须先算出左右子树的值，才能算自己。目录与权限树基本都用前序，父节点先渲染，子节点才有地方挂；层序则适合“逐层展开”的交互和分批加载。序列化与反序列化常用前序加空节点标记，写入时按前序拼接，读取时按同样的顺序递归下降，遇到标记就返回空，一棵树就能完整地进出字符串；没有这个标记，光靠前序连左右都分不清，读到叶子也不知道该回头了。

把这些顺序放在一张表里，写代码之前先对一遍：

遍历 访问顺序 递归的时机 迭代要点 典型用途
前序 根、左、右 进入节点就访问 栈，先压右再压左 复制树、序列化、目录渲染
中序 左、根、右 左子树回来再访问 一路向左压栈，弹出后转右 二叉搜索树有序输出、中缀表达式
后序 左、右、根 两个子树都回来才访问 单栈加 lastVisited，或双栈反转 释放节点、表达式求值、统计目录大小
层序 逐层从左到右 没有天然的递归形式 队列，每轮记下当前层长度 按层渲染、找最近公共祖先、算宽度

那次权限树的事故最后改了三处：接口侧保证 parentId 一定指向已存在的节点，前端组装时检测环并限制最大深度，渲染改成先建树再前序遍历。改动不大，但从那以后，看到“扁平数组直接渲染成树”的写法，我都会多问一句：这个顺序到底是谁保证的。
