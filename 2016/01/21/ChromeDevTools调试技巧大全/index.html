Chrome DevTools 调试技巧大全

一个偶发报错，我盯了四十分钟控制台，同事打开 Sources 三次点击就锁定了那一行。差距不在功能多少，在于脑子里有没有”该走哪条路”的地图。菜单按面板划分，问题却不按面板出现，所以我按要解决的问题来组织：每个问题下列出可选的几条路，说清取舍。口径是 2016 年 1 月的 Chrome 47 稳定版；移动端是 iOS 9 的 Safari 与 Android 4.4 之后基于 Chromium 33 一线的 WebView。后来改了名的面板、现在才加进来的功能一律不写。快捷键按 Windows/Linux 的 Ctrl 系写，macOS 换成 Cmd 系。

定位报错：四条路按能不能复现来选

选择依据只有一条：错误能不能稳定复现，你能不能改源码。

最省事的一条是在 Console 里读。报错行右侧带文件名与行号，点一下 Sources 就跳过去，栈帧从上往下读，最上面是抛出点。局限是看不到当时的变量值，异步边界还会把链掐断——回调里抛的错不会把注册那一层串回来。

第二条是 Sources 左上角的暂停开关，旁边藏着 caught 与 uncaught 两个复选框。只勾 uncaught，异常真要冒出来时才停，适合偶发崩溃；两个都勾，任何被 try/catch 吞掉的异常都会停——老代码里探测性捕获很多，jQuery 的选择器分支也在吞异常，一次加载能停几十次。

第三条是黑盒脚本。设置里能把某些文件标记为不参与调试（当时这个设置项的英文叫 Blackbox scripting），命中的文件不会自动停下，调用栈里也折叠它的帧，适合压缩过的库和 CDN 上的第三方脚本。坑在通配符：我把 */js/* 写宽过一次，自家打包产物一起被挡掉，排查方向偏了半小时。

第四条是断点。

debugger 明确、能进代码评审，代价是要改源码重新部署，忘删的风险全在人身上。条件断点不动源码，专门对付循环里第 1200 次才错那种情况；代价是每命中一次就求值一次，表达式里别放有副作用的调用。

停下来还要把值取出来。Watch 面板可以加表达式。切栈帧时 Scope 会换成那一层的变量，但变量一多，展开很费眼力——按 Esc 唤出 Console 抽屉，把顶部上下文切到某个栈帧，就能直接按名字敲这一层的变量。

控制台 API：把 alert 换掉

这几条路都离不开”把值打出来看一眼”，而很多人手里只有 alert。它阻塞线程，弹一次就把渲染、定时器、动画全冻住，你看到的”加了 alert 才正常”多半是时序被它改写；对象一律变成 [object Object]。

替代品按用途分。看结构用 console.table，对象数组打成带表头的表格、能按列排序，但上百行时它自己也拖慢渲染；看次数用 console.count，这是判断”渲染为什么两遍”的第一招；分层用 console.group 配 groupEnd；console.time 与 timeEnd 能量一段同步代码的耗时，粒度远不如时间轴，胜在随手。

临时把手：$_ 是上一条表达式的返回值，$0 是 Elements 当前选中的节点，$1 到 $4 是最近选中过的几个。取舍一句话：看结构用 table，看次数用 count，看有没有发生用 monitorEvents，要看现场才回 Sources 打断点。

样式为什么没生效：先看谁赢，再看谁在打架

起点选错会绕远。我一般先开 Computed，它给的是最终值，右侧标出这个值由哪条规则给出，点一下跳到 Sources 对应那行；确认最终值确实不对，再回 Styles 看输掉的那条。被划掉的属性表示它匹配上了但被更高优先级覆盖，鼠标移到覆盖者身上就能看到是谁压的它。

要分清两种”看不到”：划掉是”写了但没赢”，压根没出现是”选择器没匹配上”，该去查类名、结构和媒体查询断点；还有一类是属性写错或引擎不认识，升优先级永远解决不了。

第三条路是伪类。Styles 右上角的设置菜单里能勾选强制某些状态（当时这个入口是 state 伪类强制，可选 :hover、:active、:focus、:visited）。边界要看清：强制只影响 CSS 匹配，不触发 JS 注册的 mouseenter 回调，靠脚本做的那部分交互看不出来。

第四条是 DOM 断点，对付”样式刚写进去就被改回来”。

最后是纪律。在 Elements 里改值复现问题极快，但改动只在内存里，刷新就没，而且你改的是规则副本，不是磁盘上那个文件。我的做法是改到对的值，把规则文本复制出来回编辑器落地，再刷新确认。

渲染与性能：只有时间轴能给答案

样式问题看结果，执行问题看时间。卡顿的本质是”时间去哪了”，只能录下来看。当时的面板叫 Timeline：录制、复现交互、停止，看一帧帧泳道。认颜色是第一步。

一帧里紫蓝绿排得密，说明开销在样式与布局，不在网络。最常见的成因是强制同步布局：正常情况下布局每帧集中做一次、画在帧末尾，但你在脚本里读了几何属性、紧接着又改样式，浏览器为了给出准确读取值必须立刻算完布局，于是时间轴会在黄色 Script 段中间插进一根紫色 Layout，随循环次数放大成一片。定位办法是点那根异常条，下方的调用栈会指到那句读取。

想看清哪块在重绘，用 Rendering 面板的绘制闪烁开关（Paint flashings）：打开后每次重绘的区域闪一下色块，只该刷局部的列表把整屏刷绿，问题就露出来。另一条路是 Layers 面板，能看合成层的划分：元素独立成层通常来自 3D 变换或 will-change 这类提示，2D 的 translate 不能稳定提层，所以”加个 transform 就好了”要落回 3D 写法验证；层也是显存换来的，几十上百个元素全提层，滚动顺了，低端机的内存与合成开销就上来。

还有一类”点下去半天没反应”，只能在时间轴里看到一根很长的黄色 Script 条：单次同步执行的脚本把这一帧之后的输入处理全推迟了。

网络面板：看得很清楚，改不了一个字节

网络面板是浏览器处理之后的视图，它把请求与发起者、与渲染节点对齐在同一根时间轴上，这是代理工具给不了的；反过来，改请求体、给请求做断点、装根证书解密跨设备流量，只有代理工具能做。这套分工在本仓库 2015 年 11 月那篇抓包实践里写透了，缓存与 304 的判定结论我不重复。

模拟弱网用右上角的 Throttling 下拉，它只在浏览器侧把数据到达时间拖慢，不会真的丢包，重复提交这类问题模拟不出来。跳转后日志被清空是最常见的困扰，勾上 Preserve log，重定向和表单提交之后的请求就还留在列表里；代价是跳转前那条会话也留着，得分清哪段属于哪个文档。

想知道”这个请求是谁发的”，把 Initiator 列调出来：静态资源指向引用它的文档，脚本里发的请求可以逐级展开到调用栈，一次点击跳到发请求那行——排查莫名多出来的请求就靠它。点开一条请求看时间线，各段含义如下。

判”服务器慢还是网络慢”，切在 Waiting 与 Receive 之间比。状态显示 blocked 多半是被扩展拦下或页面卸载时取消，不是服务器给的结果；缓存命中的条目网络耗时接近零，是不是 304 还得打开头部看。

右键某条请求可以 Copy as cURL，把会话复制成命令行请求交给后端重放；但浏览器会替你补一批请求头，复制出的命令与那次真实请求并不完全等价，重放成功不代表线上没问题。同族动作还有 Copy response 与 Copy value。

内存与泄漏：那时候只能手动打快照

当时没有实时画内存曲线的面板，所以用最笨但可靠的办法：打三次快照对比。

同类对象的计数随操作次数一路上涨，说明有引用没放开。真正定性泄漏的是带 DOM 节点的条目：列表里出现 detached 字样的，就是节点已经从文档里摘掉、但还被脚本握着，点进去看保留链，通常是事件回调或数组缓存记住了它。

顺手能看的读数只有 performance.memory，它在部分版本的控制台里可用，能读到堆内存用量与上限；我通常写个循环每秒打一次，看它有没有只涨不落。它只能定性、不能定位，别当依据。两条坑：大页面打快照会卡住好几秒，不先强制回收就直接比，容易把”还没收”看成”收不掉”。

移动端复现：模拟管尺寸，真机管时序

通往手机有两条路，选错很费时间。第一条是设备视图：选机型或自己填宽高、设备像素比、用户代理，再叠一层网络档位。它擅长回答尺寸类问题——布局在 320 宽的视口下破没破、meta viewport 有没有生效。它回答不了触摸与时序：真机上事件的触发顺序、滚动惯性、软键盘顶起视口时的重排，模拟都不给；何况手机上的 WebView 是 Chromium 33 一线的内核，桌面 47 的行为差异它压根模拟不出来。我的规矩是：能远程调试就别用模拟。

Android 侧用数据线连上手机并打开 USB 调试，在桌面 Chrome 地址栏进 chrome://inspect，列表里会出现设备上可调试的页面，点 inspect 就开一个远程面板，Elements、Sources、Console 全都在。前提要说清：设备上跑的要是可调试的 WebView，也就是应用的调试版本，发布版看不到内容，这是很多人卡在第一步的原因。

iOS 靠 Mac 上的 Safari 网页检查器：真机插上数据线并在设置里打开网页检查器，或者起模拟器，再从 Mac 的 Safari 开发菜单选中那台设备的页面。能力上和远程调试接近，只是没有设备视图那一层。

几个省掉鼠标动作的入口

命令菜单最该记住，找不到入口时先敲它，再翻齿轮。

面板设成独立窗口比挤在小抽屉里好用。看资源与存储用资源与应用那一栏——这块面板在 45 前后才从 Resources 里拆出来，我机器上两个入口都还在，里面有 Cookie、localStorage、IndexedDB，改一个键值刷新一次来验证分支逻辑最省事。

工作区：把面板里的改动落回文件

Sources 的设置里能把本地目录挂成工作区，URL 与磁盘路径建立映射之后，你在面板里改 CSS 或 JS 并按 Ctrl+S，就直接写回那个文件。限制也很硬——它只适合”浏览器拿到的文件就是磁盘上的文件”这种静态站点。页面一旦是服务端模板渲染的，或者资源经过构建步骤，两边对不上，映射会错乱；带 source map 的压缩产物同理，源文件结构一变动就整片错位。我只在纯静态页面上开，用完就解绑。

复盘：一个只在真机上点不准的按钮

有个列表项右侧挂着删除图标，桌面一切正常，真机上用户抱怨”要点两下”。我先在设备视图里把宽高和像素比调成那台手机的数值，热区尺寸是对的——这条路到此为止，问题不在尺寸。连上远程调试后在 Elements 里选中图标，用 console.dir 看它绑的事件，确认脚本监听的是 click；点击确实来了，只是慢：真机上第一下要先消化那段三百毫秒左右的点击延迟，加上图标只有二十多像素见方，指尖偏一点就命中外层。同时还能看到一层系统给的灰底高亮，把视觉反馈又拖了一次。

高亮和热区按上面这段收掉；那段点击延迟，当时项目里普遍靠 FastClick 这类库去掉，但它有适用边界，在有滚动的容器里反而容易出乱子。复盘留下两条结论：尺寸类问题交给模拟，时序与事件类必须上远程调试；真机排查先用 monitorEvents 确认事件来没来，比一上来改 CSS 快得多。

收尾

几乎每个问题都有两到三条路，差别不在能不能做到，在于代价和可信度。黑盒脚本让栈干净了，也可能把自己的代码一起藏掉；强制伪类画得出样式，画不出交互；模拟能定住尺寸，定不住时序；面板能看清请求，改不了一个字节。所以我的顺序一直是：先问这一步的结论能不能代表真实环境，再挑那条最短的路。
