FIS 构建工具的特色与实践

这篇从源码与架构的角度，整理我用 FIS 这一年多的理解：它把什么问题当成核心矛盾、用了哪几个抽象去解。公司从 2014 年底把原来那堆 Grunt 脚本往 FIS 上迁移，到 2016 年 1 月几个主力项目已经跑在这套工具上。我为搞清一个”改了 CSS 图片路径却不生效”的怪问题，把 fis 的 lib 目录翻了一遍。

fis 2.x 是我们当前生产在用的版本，fis 3 是较新的大版本，配置模型有变化，我们还在观望，下面示例都是 2.x 的行为。国内用 FIS 的团队比用 Grunt、Gulp 的少得多，文档读两遍常常不如直接读源码。

它解决的是哪类问题

Grunt 和 Gulp 的抽象单位是”任务”：给一组输入文件，套上插件处理，写到输出目录。这套抽象做”把 a 变成 b”很顺手，但它天生不知道 dialog.js 依赖 dialog.css，也不知道模板里那行 require 需要被换成产物地址。

前端工程里最容易坏的一环恰恰是引用关系。我数过几种典型的路径失控：CSS 里的相对路径图片、JS 里字符串拼出来的 url、模板里写死的绝对路径。构建一旦改变文件的物理位置和文件名，只要有一处没跟着改，页面上就是裂图和 404。

FIS 的取舍是把”资源定位”当成第一类概念，而不是把”任务”当成第一类概念。每个资源在构建后都有一个逻辑名字和一个物理地址：逻辑名字是代码里写的引用方式，物理地址是带指纹、可能带域名的最终路径。构建时生成一张资源定位表，模板输出时查表替换，”路径必须一致”于是从靠人仔细变成靠工具保证。

require 有两层含义。第一层是取这个资源的定位地址，构建后被替换成带指纹带域名的真实路径；第二层是声明一条依赖，被引用的资源进入当前资源的依赖列表，参与后面的打包。引用和依赖收集是同一个动作。把 jQuery 这类公共库写成绝对依赖，将来换版本、并入公共包，模板不用动。

两个内置变量：__uri 展开成当前资源所在目录的定位地址，用来拼与自身同级的图片；__ctx 展开成站点上下文根路径，应对站点挂在子目录下的情况。

CSS 里的图片路径走同一套机制：构建时 FIS 解析样式表，把 url() 里的相对路径按当前资源重新计算，图片加哈希、换目录，样式表那行会自己跟着变。路径重写发生在依赖分析的同一轮里，而不是事后补一遍正则。

依赖分析与按需打包

顺着模板里的 require，FIS 递归收集依赖，每个资源在产物表里带一个 deps 数组，记录它依赖哪些资源 id。这张表是构建的中枢：按需加载、合并打包、页面输出几条 script，都从这里算出来。

配置里给资源声明 pack，它就被打进某个包文件，加载这个包相当于同时加载包内所有资源，页面只引一条标签。

HTML 输出阶段，那几行 require('a.css')、require('b.css') 会被替换成同一条包地址。打包按资源集合算，不按后缀算，混合依赖自动拆成多条。

粒度上，按页面维度生成打包表比全站打一个大包靠谱。全站大包看着请求数最少，实际上任何小改动都会让整包指纹变化。我的做法是首页、列表页、详情页各配包前缀，公共 jQuery 和基础样式单独成包，把变化频率相近的资源放在一起。

后端模板里的 require 由谁替换

最早引起争论的是：页面不是纯静态的，HTML 由 Java 侧的 FreeMarker、Velocity 或 PHP 侧的 Smarty 渲染，那模板里那行 require 谁来替换？答案是 FIS 不参与线上渲染，它只产出带指纹的物理文件和一张资源定位表，替换发生在 HTML 出口那一层。做法有两种：一是把定位表交给后端，模板引擎渲染时查表输出，Java 侧有个读表小工具，用自定义指令把逻辑地址换成真实地址；二是构建阶段就把 HTML 模板当资源处理，先由 FIS 展开 require，后端只渲染动态部分。

我们两种都在用。路径确定的组件模板走第二种，构建时就展开干净；按登录态动态决定引用范围的页面级模板走第一种，运行时查表。判断标准是：构建期能不能确定这个引用。选了运行时查表，这张表就成了线上依赖，只推静态文件不同步表，就会出现新资源上线、老地址仍被引用，同步动作要写进发布脚本。

parser 决定用什么语法解析这个文件，读源码会发现它其实是 <资源类型>:parser.<后缀> 这样一组键。optimizer 是压缩器，值一般是 fis.plugin('xxx') 的返回值，插件就在这个位置插进流水线。两者构成 FIS 的编译环节，区别是它按文件生效而不是按任务生效。

rpath 控制资源发布到输出目录后的位置，这是把开发时目录结构和上线 URL 结构分开的关键。domain 给资源地址加域名前缀，静态资源分域、上 CDN 全靠它。query 给地址追加查询串，常见用途是版本号。useHash 决定是否在文件名里插入内容指纹，开了它线上就能把过期时间拉得很长。

pack 是打包归属。release 控制资源要不要出现在产物里，配合取反模式可以把调试文件挡在门外。deps 属性用来手工补依赖，静态分析看不见的运行时拼接引用就靠它显式告诉工具。媒体环境是当时版本做”一份配置、多套环境”的手段：

执行时带上媒体名，该媒体下的规则叠加覆盖基础规则，让日常开发保持不压缩、不加域名，把指纹和分域留给上线。

发布闭环的四个开关

命令这一层很简单，值得说的是每个开关背后多做了什么。

-w 是 watch，常驻进程，按依赖图只重建受影响的部分，改一个组件不会全量重跑。-d 指定输出目录。-m 开启打包合并，即真正去算包。-p 是发布模式，只有它让 optimizer 生效、才给资源算内容指纹，不加就一直是未压缩的原始文件。我的纪律是本地不带 -p，CI 上线固定 fis release -mp -d ./dist。上线前我会让 CI 跑一次不带 -w 的全量构建，把产物目录和那张定位表一起归档，回滚时连文件带表一起退回上一个版本。

指纹解决缓存，域名解决分片：带哈希的文件名可长期缓存，不必再靠查询串赌更新；域名前缀把静态资源分到多个主机，绕开单域名大约六条并发连接的限制。这两项只需在配置里给几个值，改动就顺着定位表传到每个引用点。

与 Grunt、Gulp 的分工差异

这三者放在一起比，很容易变成”谁插件多谁赢”，但它们其实不在同一层。Grunt 和 Gulp 是任务编排器，价值是流水线和可自由拼接的插件，对你的目录结构、引用写法、模板语言都不做要求。FIS 是带依赖分析的整体方案，要求你按它的写法组织模板和配置，换来路径、依赖、打包、指纹由同一个内核统一算。

自由度上前两者更宽，奇怪的构建需求都能拼出来，成本是引用关系要靠人维护。迁移成本上，把 FIS 换成别的意味着模板写法重做、后端查表层重做，比把 Grunt 换成 Gulp 大得多。至于当时也在接触的另一类打包工具 webpack，2015 年我们看它时它走的是另一条路线：以 JS 模块为入口递归构建，对后端模板语言还没有现成路子，而这正是我们这类项目最在意的一环。

两段踩坑复盘

一是改了 CSS 里的图片路径，本地一切正常，发出去的产物里引的还是旧地址。我几乎要把解析器逐行打印，最后发现问题不在解析层，而在资源定位表被缓存：构建为了快会复用上次算好的定位信息，我只改了被引用文件本身，引用方那条记录没有失效。办法粗暴但有效——清掉输出目录完整跑一次 release。后来我加了条规矩：凡是路径、域名、指纹这类定位属性的改动，一律全量重出。

二是更难查的那种。有内容是后端直接拼字符串输出的 HTML，没走模板渲染，浏览器里看到一行原样吐出的 require，样式直接没了。前端查了半天构建产物都没问题，最后定位到”HTML 出口不止一个”。修法是让所有 HTML 出口统一走同一套模板渲染。教训是：资源定位这套机制只有在所有引用都经过查表的前提下才成立，留一个手工输出的后门，整套设计就在后门那里失效。

局限

按 2016 年 1 月这个时点判断，这套工具的短处得说清楚。文档以中文为主，对内省事，对外沉淀少。插件生态比 Grunt、Gulp 窄一大截，不常见的需求没有现成插件，得自己按它的接口写。出现构建疑难网上搜不到答案，只能读源码，这等于把工具知识锁在个别人身上，我自己就扮演了这个不太健康的角色。跨端能力依赖它自家约定，后端一旦换模板语言，改造成本高于换一套任务脚本。fis 3 还在观望期，短时间内我们不敢把线上项目往上推。

选型参考

现状 我的建议
已有成熟的 Grunt/Gulp 体系，构建问题主要是压缩拷贝这类机械活 继续用任务编排器，别为了换而换，收益抵不上重写配置的代价
组件化诉求强，路径失控造成过线上事故 资源定位与依赖分析正好命中痛点，值得投一次迁移
静态资源要做内容指纹、分域与长缓存 这类需求在 FIS 里是配置项级别的，比在任务流里补丁式实现省心
后端模板语言不是 Node 生态，团队里没人能读源码 谨慎，运行时查表那层要自己搭，出问题时没人兜得住

小结

FIS 在我心里的位置是”把文件路径上升成工具职责”：它让引用、依赖、打包、指纹、分域从同一张表里长出来，最容易出事故的引用关系不再靠人盯。代价是你得按它的约定写模板，生态窄、出问题要读源码，团队里必须有一个人真懂它内部怎么跑。在我们这套项目结构里，组件目录加资源定位确实消灭了一整类线上问题，这笔账我觉得划得来。
