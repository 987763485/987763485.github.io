Git 分支管理与团队协作规范

为什么分支规矩是沟通契约

团队里只有三个人的时候，分支怎么切都无所谓，反正喊一声就知道谁在动哪份代码。人到了七八个，同一个仓库里同时躺着十几条分支，问题就来了：没有人答得出这条分支是给哪个需求开的、基线是从哪次提交拉的、什么时候该合回去、谁负责删掉它。吃亏多次之后我才想明白，分支名和它的基点本质上是一种契约——你开一条分支，就等于向全组宣告”这块代码未来两周由我按这个范围改”。契约写得含混，后面所有合并、发布、回滚都在为这句话还债。

前端仓库比后端多了两层约束。一是发布窗口固定，多数业务每周只有一个上线时段，晚合上去的改动就顺延一周；二是线上出问题时热修复不能等窗口，而与此同时新需求还不能停。同一份代码要同时服务”正在开发的””等着发布的””线上跑着的”三种状态，这正是各种分支模型想解决的问题。所以挑模型之前，先把这三个状态在我们的流程里各自对应哪条分支说清楚，比背命令重要得多。

三种当时常见的模型摆开比

先给一张机制对照表，四列回答”历史长什么样、怎么发版、怎么回滚、对构建流水线提什么要求”，这才是选型时要看的东西。

维度 Git Flow GitHub Flow 简化版三分支
历史形状 master 与 develop 两条长线，feature/release/hotfix 短分支进出 只有 master 一条线加一堆短命分支 master 与 develop 两条长线，release 按需临时切
发布方式 release 分支验收完合 master 打标签 合入即可发，随时部署 develop 上完版本检查临时切 release，合 master 打标签
回滚方式 master 历史干净，找到上个合并节点恢复旧标签版本重新发布 快速做一条反向改动的分支再发一版 同 Git Flow，但记录少更依赖标签齐全
对 CI 的要求 develop 和 master 两条线都能触发构建，release 切出后要有预检 合入前必须全绿，发布要能一键化，门槛最高 至少 develop 常驻构建，master 发布构建

Git Flow

教科书里最常画的那套：日常开发在 develop 上汇合，发布前从 develop 切出 release 分支只做版本检查不改功能，验收通过合回 master 打标签，再倒回 develop；线上急修从 master 切 hotfix。它把三种状态明确摊给三条分支，和我们的固定发布窗口对得上。代价是命令多、仪式重。扩展脚本本身有两个时代的用法：早一些的 0.5.x 一代把 feature、hotfix 做成独立命令，后来 1.9.x 一代统一成 git flow 加子命令的样式，旧新混装在内网机器上，光敲命令就能敲错。后来只允许发布负责人用扩展，其他人按原生命令手工切分支——分支模型归根结底是命名和基点的约定，不是工具。

GitHub Flow

只有 master，永远处于可发布状态，改动全走短分支加合并请求，流水线绿了就许合，合完随时部署。它省掉了”等窗口”这件事，但前提是有足够可靠的自动构建与冒烟检查，让任何人任何时刻上线都不心惊胆战。我们当时不具备，发布又必须和后端一起发车，随时可发反而变成随时可出事。值得偷师的是它对分支存活的态度：以天计，不留两周孤儿分支。

简化版三分支

最后落地的形态：master、develop、feature 是常驻约定，release 和 hotfix 按需切、用完即删。不养长期 release 分支，发布日在 develop 上走版本检查清单，确认要发了才切一条短命分支冻结改动。取舍很清楚，命令少了、新人上手快，但丢掉了工具强制的仪式感，基点对不对、标签补没补全靠评审人肉把关，后面的检查项全是给这里打的补丁。

分支命名与生命周期

命名模板定死四种前缀：feature/需求单号-简述、bugfix/需求单号-简述、hotfix/缺陷单号-简述、release/版本号。单号一律取工单系统里的编号，作用是让任何一条分支都能反查到需求与排期，简述用一两个英文词，比如 feature/FE-1024-order-list 这种粒度。

禁止中文和空格不是洁癖。分支名会出现在构建脚本、流水线的工作目录路径、构建产物的下载地址里，中文和空格意味着这些环节处处要加引号和转码，而每台机器的默认编码还不一定一致。写的人只多打几个字符，麻烦却让后面每个工具分摊，这种成本最容易在文档里被忽略。

禁止用人名当唯一标识，是因为 feature/zhangsan 这种分支反查不到需求，也看不出什么时候该删；人一换组或离职，分支就没了主人，谁都不敢碰，仓库里堆满僵尸分支。负责人该记录在工单里，而不是编码进名字里。

生命周期是我们卡得最硬的一条：feature 分支存活上限两周，超了就先合回。现实里确实有大需求两周做不完，解法是拆而不是拖——把已完成且不影响入口的部分先回合 develop，功能入口先不放开，剩下的继续做；实在拆不动的，从原分支再切子分支接力，原分支当场删掉。拖着的分支每天都在和 develop 拉远距离，最后受苦的是合并那天的自己和评审的人。

保护分支与合入路径

master 和 develop 设为受保护分支，这是内网自建 GitLab 上项目设置里的分支保护项，能限制普通开发者直接推送和合并，权限收紧到发布负责人一个人。推不上去，是所有规矩里最有效的那条，因为其余条款违反时还有商量余地，这条在服务器上直接拦。

合入一律走页面请求：GitHub 上叫 Pull Request，我们内网那套 GitLab 当时叫 Merge Request，同一类东西两种叫法，文档里统一用后者，免得新人对着界面找错按钮。评审门槛定两条：任何合入至少一个非作者的评审人签字；动到公共组件或构建脚本的，两人。流水线通过是合入的前置条件，红的构建不接受”先合进去我再修”这种话，说过一次之后这个口子就再也关不上了。

禁止直接在 master 上改东西，哪怕是一行文案。hotfix 也必须从 master 基点切出专用分支再合回，理由不是代码质量，而是 master 的历史必须每条都有出处：突然多出一个没有合并记录的提交，下一个人就说不清这个线上版本包含哪些改动，回滚时连基准都找不准。

需求与分支的对应

原则是一条需求一条分支，站会上报单号就够了。但需求经常大到一个人两周吃不下，我们的办法是需求下再切主题分支：主 feature 分支作为该需求的汇合点，子主题各切各的，做完一个先合进主 feature，需求整体再合 develop。子分支不直接对 develop，避免同一条需求的半成品互相踩。

另一类是公共基础改动，比如抽一个通用组件、改埋点封装。这类改动单独开分支、单独评审、优先合回，不挂任何业务需求。挂在业务需求下的后果是它跟着需求一起被搁置，而另一个急需它的团队只能在 develop 外面干等，等出来的往往是第二份重复实现。

hotfix 流程完整走一遍

线上白屏这类急修，第一步不是改代码，是定位”线上跑的到底是哪个版本”：从页面加载的静态资源版本号反查发布记录，找到对应标签，比如 v1.3.2。基点必须选标签而不是 master 最新提交，因为 master 上可能已经合进了尚未发布的版本检查收尾提交，从那里切出去修，等于把没验收过的改动带上线上。

流程上有两个硬规定。第一，同一条 hotfix 分支要走两条合并请求，一条进 master、一条回 develop，工单上两条记录都勾掉才算修完，评审人看不到第二条就不签字。第二，修完当天删分支，不让它过夜变成第二个基线。”回合漏掉”这件事后面复盘会单独讲，它造成的不是冲突，而是下个版本上线时线上修复被静默覆盖，用户以为老毛病复发，其实代码根本没带上新补丁。

打标签与版本口径

发布用附注标签，不用轻量标签：

两者的区别在于附注标签是仓库里一个独立对象，带说明、带打标签的人和日期，能被校验；轻量标签只是一个指针，谁随手一指都看不出来，版本检查的中间提交被误标成正式版本的事故，多半坏在这上面。

版本号的口径要两处一致：标签是对外发布名，package.json 里的 version 字段是包内可见名，发布提交里两者同时升、一起合进 master，评审检查项里专门有一条对不上就不许合。已经发出去的标签从此不再动——编号发现写错了也只能升一个新版本重新发，因为线上日志、构建产物、别人的问题报告里都可能已经引用了它。

环境分支的陷阱

很多团队会顺手把部署环境做成常驻分支：daily 给日常测试、pre 给预发、prod 对应线上，看似每个环境都有一份确定的代码。实际运行半年，三条线各自漂移，配置差异越攒越厚，攒到想统一版本时差距已经大到没人敢一次合完；更隐蔽的伤害是线上修的问题进不了 daily，测试环境长期验证不了修复，下一轮又”复发”一次。

后来我们的结论只有一句话：分支层面只保留代码主干，环境与代码无关——配置和代码分离，环境差异在构建或运行时用环境变量注入。具体怎么拆配置、怎么注入，是构建体系那类文章的事，本篇只负责把”环境不该有常驻分支”这条立住。

规范怎么落地而不沦为文档

约定全部写进仓库根目录的 CONTRIBUTING.md，控制在一屏内：四种前缀、基点表、合入路径、hotfix 双合并、标签口径，别的都不写，写得比这长的文档没人读。

评审人拿三句固定问话过每笔合并请求：分支名对不对得上工单，基点切没切对，该不该回合 develop。违规的成本设计成由当事人自己承担：基点切错就删掉分支重切一遍，听着苛刻，但分支里本来就不该有珍贵历史，重来只是几条命令，比发布事故后全体人陪跑便宜太多。

新人入职第一天的练习也照着这份文档走一遍闭环：切一条练习分支、发一笔合并请求、导师签字合入、删分支。十分钟，先让规矩在手上过一遍，比开会念一遍有效。

复盘：那次没回合 develop 的 hotfix

有一轮线上订单页白屏，hotfix 当天修完、合了 master、打了新标签，唯独漏了回合 develop。两周后新版本上线，白屏”复发”，产品第一反应是当初就没修对。排查只花了几分钟：拿那条修复提交用 git branch --contains 一看，develop 上根本没有。补一条把修复带回 develop 的合并提交、重新发布，当天恢复。

真正花功夫的是改流程，加了两道闸。工单模板里 hotfix 类型强制两条合并记录的链接都填上才能关单；发布脚本在构建前多查一步，develop 若不包含 master 最新标签的提交就直接中止。前者靠人、后者靠机器，缺一道都会漏。这件事之后，组里再没人觉得”回合”是可选动作。

分支职责表

分支 允许谁推 从哪切 合到哪 生命周期 可否强推
master 仅发布负责人，走合并请求 release/ 或 hotfix/ 合入 不外发 常驻 否
develop 任何人，一律走合并请求 feature/ 或 hotfix/ 合入 master（发布时） 常驻 否
release/版本号 版本检查负责人 develop master 与 develop 双回合 数天，发布即删 组内约定不可
feature/单号-简述 需求负责人及参与者 develop develop 上限两周，超先合回 他人拉取后不可
hotfix/单号 修复者 线上版本对应的标签 master 与 develop 都要 当天完成即删 否
bugfix/单号 修复者 develop develop 一周内 他人拉取后不可

单独说一句”可否强推”：分支被人拉取过之后改写历史再强推，就是在别人本地制造凭空分裂，宁可删分支重切也不强推救场。规矩不产生秩序，被检查、被计价的那部分才产生。
