CommonJS、AMD 与 CMD 规范对比

我手上的项目里同时躺着三种模块写法。服务端那摊 Node 代码用 require，页面上几个脚本是 RequireJS 的 define，同事带过来的组件也是 define，但里面又能再写 require。我第一次把一段 CommonJS 代码塞进浏览器，页面一片空白，控制台连报错都没有，模块就是等不到。翻完三份文档和几个实现的源码，我发现让我困惑的从来不是语法，而是大家把”规范”和”实现”混在一句话里说。

这篇文章把 CommonJS、AMD、CMD 各自解决什么问题、约束在哪里、写法差异出现在哪一行讲清楚，读到后面会看到取舍结论。RequireJS 的 paths 与 shim 怎么写，《RequireJS 模块化开发实战》那篇讲透了，本文只引用不重述。

第一件事：把”规范”和”实现”分开

规范是一份文档，规定一个模块该长什么样、怎么声明依赖、怎么把东西交出去。实现是一个 JS 文件，它按某份规范去解析模块、发起请求、维护一张依赖表。

CommonJS 是一组约定，形成顺序其实是反的：Node 早期为了在服务端组织代码先有了 require 和 module.exports 这套写法，用熟了才回头整理成规范文本，所以它每条规则背后都站着”文件就在本地磁盘上”这个前提。AMD（Asynchronous Module Definition，异步模块定义）反过来，它为浏览器起草：模块要到网络上去取，取回来才能执行，规范一开始就得回答”依赖还没到怎么办”。CMD（Common Module Definition）是国内某套加载器实现（SeaJS）在实践中总结的近似规范，动机不是解决新问题，而是觉得 AMD 那条”依赖必须前置”的规矩不合直觉。

实现层面的名单更长：Node 自己是一种实现，RequireJS、curl.js 是 AMD 的两种实现，SeaJS 是 CMD 的实现。同一个 define 在两种加载器下的行为差别，往往比两份文档的差别还大——先确认你在跟哪份文档说话，再确认加载器是哪个。

骨架：六条对比轴

对比三套规范我固定用这六条轴，它比语法本身更能解释差异从哪来。

对比轴 CommonJS AMD CMD
依赖声明时机 执行到哪一行才 require 前置声明，函数执行前依赖必须齐 就近取用，用到时才 require
加载时机 同步语义 异步 异步加载、同步执行
导出形态 module.exports 可整体替换 define 回调的返回值 module.exports 赋值
模块标识 相对路径加扩展名解析 依赖 paths 映射的字符串 ID 相对路径，风格接近 CommonJS
循环依赖 拿到半成品（已执行部分） 依赖未就绪时直接报错或拿到 undefined 拿到半成品，行为更接近 CommonJS
按需 require 天然支持，写在任何分支里都行 靠 require([...], cb) 单独走 支持，且写法与普通 require 一致

这张表最有解释力的是第一行和最后一行，它们是同一件事的两面：依赖能不能在代码执行中途出现。CommonJS 说能，读磁盘是同步的。AMD 说不能，网络请求不能让你卡在当前这一行等它回来，声明因此必须前置。CMD 说”能，而且让你写得像能”，require 写在函数体内部，规范上仍保证被 require 的模块此刻已加载好。

CommonJS：同步语义为什么在服务器上站得住

require 是普通函数调用，调用完立刻拿到导出对象，在服务器上毫无心理负担：模块文件就在本地磁盘，不用等网络。同样语义搬到浏览器，问题就变成”当前这一行 JS 停在这里，等一个响应回来”，整个页面的执行都被挂住。这一句就是三套规范分叉的源头。

__dirname 是当前文件所在目录的绝对路径，__filename 是当前文件绝对路径。require('./util') 这种不带扩展名的标识符，解析顺序有规定：先按原样找 ./util 文件，找不到依次补 .js、.json、.node 试，还不行就把它当目录，读里面的 package.json 看 main 指向哪个文件，main 缺失或无效时再找该目录下的 index.js。这套顺序解释了为什么很多包的入口只是空壳——真东西在 main 指过去的那层。

AMD 的标准形态就一行：

它跟 CommonJS 最刺眼的区别是依赖被提前成了一个数组。这个数组不是语法糖，是给加载器看的：加载器读到模块定义时函数体一行都还没执行，却可以立刻把 ./a 和 ./b 的请求发出去，等依赖都到位才调用工厂，把结果按数组顺序塞进参数。依赖若写在函数体里，加载器就没机会提前安排请求——它得等代码跑到那一行才知道要什么。所以”依赖前置”不是审美选择，是异步加载唯一可行的信息交换方式。

代价也很直接：顶层拿不到同步返回值。require 一个 AMD 模块不能写成 var a = require('./a') 然后下一行就用，只能 require(['./a'], function (a) { ... })，把后续逻辑整体搬进回调，这就是 AMD 代码里到处是回调的原因。换来的是 CommonJS 在浏览器里做不到的按需加载：只在点开面板时才用的模块，可以从 define 的依赖数组挪进点击回调的 require(['./panel'], cb)。

模块标识这块，AMD 允许匿名和具名两种。匿名模块不写 id，加载器按请求它的 URL 反推标识，日常该用这种；具名模块把 id 写死在文件里，只在少数场合用。id 到实际地址的映射靠 paths，不遵守 AMD 直接挂全局的老脚本靠 shim 补声明，写法在《RequireJS 模块化开发实战》里讲全了，这里不重复。规范层面只需知道：AMD 的标识是字符串 id，不含”相对路径怎么解析”的强制约定，规则由各实现（RequireJS 2.1.x、curl.js）自己定，这也是同一份模块换个加载器就要改路径写法的原因。

CMD：就近依赖，一个看着更像 CommonJS 的写法

SeaJS 是国内团队做的一套加载器实现，它在实践中提出了 CMD 这份近似规范。最直观的差别在写法上：

工厂函数签名接收 require、exports、module 三个参数，require 写在真正用到它的那一行。这就叫就近依赖，读起来更贴近直觉：不必在文件顶上先列清单，在哪里需要就在哪里取。

关键的一点是 CMD 并没有取消异步问题：require('./a') 能在这一行同步返回，前提是加载器早知道 ./a 要下载并提前取回来了。实现上靠把源码转成字符串、扫描其中的 require 调用来重建依赖表（SeaJS 2.x 一代的自动模块转换）。所以 CMD 与 AMD 的分歧不是”要不要异步加载”，而是”依赖信息靠作者声明交出，还是靠工具解析源码猜出”，后者的代价是静态可分析性变差。我的判断是：代码迟早要交给构建工具处理，显式声明更耐折腾。

CMD 传播范围有限，我只给一句现象描述：用它的团队集中在国内，围绕它的构建插件、测试工具和第三方库的兼容产物都比 RequireJS 那侧少一大截。写组件库时这个差别直接反映到工作量上——你得自己维护一份多加载器都能消费的产物。

这套模板牺牲了什么很清楚。一是可读性：业务代码裹在工厂函数里，外面再套一层立即执行函数和三个分支，新人打开文件先要解一遍壳。二是静态可分析性：依赖在三个分支里各写一遍，工具收集依赖图就得同时认出三种写法，漏一处产物里就缺一个模块。分支一多，文件顶部比正文还长。所以我给团队定的规矩是只有对外发布的库文件才套 UMD，业务代码不许写这三段检测。

浏览器里跑 CommonJS：当年的两条路

想让 require('./a') 在浏览器里工作，路子只有两条，思路相反。

第一条是运行时模拟：加载器先把全部模块预取进内存（或打进一个文件），require 被调用时不再发请求，直接从已就绪的表里返回。语义跟 Node 一致，代价是预取全部取消了按需，首屏要付所有模块的钱。

第二条是构建期转换：工具在发布前把整棵依赖图静态收集好，按拓扑顺序把模块包进一个运行时壳，每个模块的 require 替换成”从壳内注册表里取”，靠这条链维持”取到的一定已经执行过”的假象；不确定性挪到构建期，运行期只剩查表。我的判据很朴素：需不需要在运行时按用户行为决定下不下载某块代码。需要就留在 AMD，不需要就交给构建期转换，依赖图发布时定死，出问题能在构建日志里看到。本仓库《ES6 Module 模块系统与构建工具》那篇给过工具选型结论，这里不重述。

和 ES6 模块的关系：只说方向，不剧透结局

ES2015 在 2015 年 6 月定稿，import 和 export 是其中的模块语法。到 2016 年 1 月，浏览器和 Node 都还不能直接运行它，项目一律靠转译工具（Babel 6 一代）降级成 CommonJS 或 AMD 发布。所以这里不是”要不要立刻换”，而是”新语法想解决老规范的哪个病”。

差别集中在两点。一是静态结构：import { parse } from './a' 在编译期就确定依赖了谁、取了哪个名字，而 require 可以跟变量、可以写进 if，运行前定不下依赖图。二是绑定关系：ES6 导出的是活的绑定，源模块内部改了值，导入方读到新值；CommonJS 的 module.exports 是一次取值拷贝，导出方整体替换后导入方手里还是旧对象。第二条正好解释了前面”整体赋值会断开 exports“那个坑。

方向上我判断是静态化：三套规范都没法在编译期交出完整依赖图，这正是各自怪招的根源（AMD 的前置数组、CMD 的源码扫描、CommonJS 在浏览器里预取全量），静态声明把这张图交了出来。最终由谁来收集它，不是本文要猜的事。

复盘：一个模块的三次改写

去年有个日期格式化模块，我最初按 CommonJS 写，exports 上挂四个方法。页面要接进 RequireJS 就改成 AMD，两个月后另一个用 SeaJS 的组件库要复用它。三段需求凑一起，最后落成一份 UMD，中间踩的全是同一份源码在不同加载器下的失败模式。

第一是 this。裸 <script> 下模块顶层的 this 是 window，在 Node 里是 module.exports，被 UMD 的立即执行函数套住后变成传入的 root。我原本有一行把方法绑到 this 上，换加载器就换了绑定对象，报错还指向别的文件。第二是循环依赖拿到半成品。A 与 B 互相引用，CommonJS 下各自都拿到对方”已执行部分”的对象，代码跑得通；改成 AMD 后一方在依赖数组里读到 undefined，因为它执行时对方工厂还没被调用，不报错，只在某个分支才炸。第三最阴：改 AMD 时我把 module.exports = {...} 换成 return {...}，漏掉一处 exports.foo = ... 的挂载，而 exports 赋值在 AMD 语义下完全被忽略，那个方法静悄悄不存在了两周才被点出来。三次改写没有一次是逻辑错，全是规范的边界条件。

结尾：按场景给的推荐

场景 推荐写法 一句话理由
Node 服务端 CommonJS（module.exports） 磁盘同步可得，且这是 npm 生态的默认语言
传统多页站点脚本 AMD（RequireJS 2.1.x） 页面各自一个入口，运行时按需取模块最省事
组件化页面 构建期转换 CommonJS 语义 依赖图在发布时定死，避免运行期一堆回调
要发布给多种加载器的库 UMD 模板 一份产物覆盖 Node、AMD、全局三种消费方式

只留一句结论：新项目的模块写法应该往”能在编译期交出依赖图”那一侧靠，运行时装配留给确实需要按需加载的场景。三套规范不是同一问题的三个答案，而是三个不同前提下的答案——分清前提，选型就不需要摇摆。
