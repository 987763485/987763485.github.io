Markdown 写作规范与实践

接手团队内部文档仓库那阵子，我遇到一类很难解释的故障：同一份文件，我本地预览整整齐齐，同事在代码托管页面上打开少一段，粘进内部 wiki 之后表格干脆原样吐出一串竖线。后来我才把因果理顺——Markdown 不是一个解析器，而是一堆各自演化的实现，我写的不是文档，是某个解析器的方言。这篇文章不讲语法是什么，讲的是同一个写法为什么在不同地方行为不同，团队该定哪几条规矩把成本提前付掉。代价只在三处还回来：渲染不一致、比对全是噪声、搬家直接失效。

同一个文件，四种解析结果

分歧的根源是 Markdown 有两份源头加一层扩展。最早一份是 John Gruber 在 2004 年定下的原始约定，它只靠一份说明文档和一个参考实现说话，没有正式规范文本，边界情况全凭实现者猜。第二份是 CommonMark，2014 年底才启动的规范化努力，想把输入该产出什么结构写成可测试的条文，写这篇文章时它还在推进，各处实现跟进快慢不一。这两份之上又叠了 GitHub 自己扩展的 GFM，表格、任务列表、删除线、自动链接识别这些天天在用的东西全来自这一层，原始约定里一个都没有。最后还有一层是博客生成器、内部 wiki、编辑器插件各自的解析器，还会再做一点取舍。

于是一份普通文件至少要过四类解析器的手。只有 GFM 那套在托管平台上安全，只有原始约定那套在多数实现里不出错，中间的差集就是坑。我后来定了条最粗的判据：一份文档只要会出现在两个以上地方，就只能用交集里的写法。

硬换行的三种流派

想把两行文字挤到一块有三种做法：行尾两个空格、行尾一个反斜杠、空一行分成两段。三者都能”看起来换行”，代价不同。行尾两空格是原始约定承认的，也最脆：它不可见，比对里看不出这行被改过；编辑器一开保存时清理行尾空白，你排好的换行就会莫名并回一行，还没人知道是谁干的。行尾反斜杠属于扩展，不认识它的解析器会把它原样留在句尾。空行分段所有实现都认，代价是语义变重，渲染出的间距也不是一回事。

我的规矩是段落优先，正文禁止行尾两空格。除了可见性还有一条渲染层面的理由：段落间距由样式表说了算，一处改动全站生效；硬换行只换行不分段，不产生新间距，于是同一段里出现两种行距，视觉上像坏了。

代码围栏要守的四条

波浪号与三个反引号语法等价，但波浪号在项目里极少见，唯一效果是让检索失效：同事拿反引号全文搜代码块会漏掉一半，所以只用反引号这一种。围栏必须标语言，这不是审美问题是行为问题：未标语言的块在一些高亮器里被当纯文本吐出，读者无从判断这段示例还可不可信，而标语言的成本只有两个单词。

缩进式代码块（四格空格）与围栏的优先级不一样，它要求连续缩进且中间不能有空行，某行少一格就不再属于代码块，读者看到代码凭空断了一截。往列表里嵌代码时缩进量要按列表项内容宽度来，差一格就跳出列表，这张图比文字好讲：

关键全在”三格”，它对齐列表标记之后正文的起点：多打一格，那行成了代码块里的代码块；少打一格，围栏不再属于列表项，后续条目的编号被重置。规矩因此是列表里放代码一律用围栏并统一缩进三格，不与四格缩进式混用。

表格的代价

表格是 GFM 加进来的，原始约定里根本没有。以表格为主体的文档天生站在兼容性最差的一侧：解析器不认识它时竖线被原样吐出，这不是丑一点，是信息整个丢了结构。单元格里的竖线必须转义，否则那一列从竖线处断开，后面的内容飘到表外。

列宽对齐也不值得做，把竖线排成直线只让自己看着舒服，代价是每改一个字都要重排一遍。判据是内容与用途：列数超过四五行、单元格里出现整句，或者这份表格可能被贴进 wiki 和邮件，我就改截图或附导出文件。表格在纯文本里是脆资产，越关键的信息越不该指望它跨解析器活着。

链接与引用式写法

同一处链接两种写法：网址直接跟在括号里，或者只写引用标记、网址集中放文末。长文档我强烈建议后者，理由不是好看是维护：网址散在正文里，改一次要通篇搜还容易漏；集中之后改动只有一次，正文一个字不动，比对里只看得到真正变了那行。

相对路径是另一颗雷，基准点不统一。以上级目录开头的写法在托管页面点得通，因为基准是文件所在目录；同样写法进了博客生成结果可能是死链，因为生成器的地址由配置里的路径模板决定，源文件的目录层级不一定保留。我们的做法是文档间跳转按从仓库根算起的形式写，提交前人工点开验证一次；图片统一放固定资产目录。还有一条没道理但有用：图片一律写替代文字，表格崩掉时读者至少能从替代文本里知道那张图原本在讲什么。

列表：起始数字与松紧

数字列表有两个争议。一是源码里写递增数字，还是全写同一个起始值让解析器自己排：前者读纯文本直观，后者比对干净，往中间插一条时递增写法要把后面所有行的数字都改一遍。但有些实现尊重首项数字，有些完全按你写的显示，两边对不上时读者以为是笔误。

二是松散与紧凑列表，更隐蔽。条目之间留空行，解析器会把条目内容包成一层段落节点；不留空行，内容直接是文本。到了样式层面就是行距：被段落包住的那份额外吃到上下边距，同页两个列表一高一矮，而排查的人多半先去翻样式表。规矩很简单：普通条目之间不留空行，确实需要多段或嵌套时才刻意留。

标题层级的纪律

两条没商量：一份文档只允许一个一级标题，层级不许跳。跳级的坏处不在当前页，在下游——目录生成、读屏软件都按层级树工作，从二级直接掉到四级，那棵树就断一截，读者也会误以为四级标题是章节起点。

跟生成器有关的那条更具体：本站用的博客生成器会把文档头信息里的标题渲染成页面顶部的一级标题，正文再写一遍就有两个一级标题，主题的层级样式跟着乱——我拿这篇文章自己验证过，删掉正文首行那个井号才恢复。规矩因此定死：标题已在头信息里的文章，正文第一个标题必须是二级。内部 wiki 不认头信息，标题得由正文提供一级。

中文文档里的特殊字符

中文让一批原本不值得讨论的规则变得要命。先说强调标记紧贴汉字：两个星号包住中文一般没事，下划线成对就不一定，各实现对词边界的判定不一样，有的把汉字也当字母，下划线于是被视作词内普通字符原样留着，加粗并没有出现。我们规定只用星号。同理，a_b_c 这类夹下划线的标识符裸写进正文，某些实现真会把中间那截变斜体并吞掉两个下划线，所以标识符只许放行内代码。

再说尖括号。HTML 内联在 Markdown 里是允许的，凡写成标签样子就被真当标签处理：我用尖括号括起一个不存在的元素名当占位符，渲染结果里那一段整块消失，因为浏览器把它认成未知标签。占位符要么行内代码，要么换方括号。最后是全角半角与中英文间距，这条纯粹是维护成本：两种括号并存，检索与替换都得各写一遍，约定是中文用全角、代码用半角、中英文之间加一个空格。

把规范交给脚本

规矩写在文章里没人遵守，写进检查才有用。编辑器这层能统一的只有”都支持纯文本”：我用 Sublime Text，同事一套 Vim 一套 Emacs，三方能对齐的仅是装个预览插件边写边看、保存时清理行尾空白。可视化写作工具当时还很原始，能指望的是规则器——markdownlint 这一类检查器刚开始出现在持续集成里，报出的问题都很实在：围栏必须带语言、一级标题不许重复、标题不许跳级。前两条不必等工具：

交付与协作

文档位置跟着代码走：接口说明、部署步骤、排错记录放进代码仓库的文档目录，和改动同一次提交，不再漂在网盘或者邮件里。文件名用英文小写加连字符，中文标题只在文档内部出现，因为托管平台对中文文件名的处理不一致；图片放独立目录，按文章分层。

给非技术同事的交付物按另一条判据：内容含表格、任务列表或多层嵌套，就从生成结果导出一份 PDF 发过去，别指望对方那边有能用的解析器，发时说明这是快照，以仓库那份为准。

一次复盘：内部 wiki 上表格全崩

代价最大的一次事故。我们把一份写满对照表格和操作清单的规范文档搬进内部 wiki，第二天同事来问：为什么整章全是竖线，为什么每个待办项前面是一对方括号装着空格的字符。打开原始数据一看，表格和任务列表都没被解析——那套 wiki 的解析器只认原始约定，GFM 那层扩展一个都不接，勾选框以源码面目示人。之后加了一条最硬的红线：关键信息不许依赖扩展语法，表格改成有序列表或截图，待办用文字写清状态。

写法红黑榜

推荐写法 避免写法 原因
空行分段 行尾两空格硬换行 不可见，被清理后换行凭空消失
围栏且标语言 未标注的围栏 不认识的高亮器当纯文本输出
列表内缩进三格 列表内四格缩进式 差一格就跳出列表，编号被重置
条目间不留空行 随手留空行 松紧不同导致段落包裹，行距忽大忽小
引用式链接 行内长网址 集中一处易改，比对噪声少
简单列表或截图 复杂表格 扩展语法在非兼容环境整块失效
只用星号做强调 下划线做强调 中文词边界判定不一致，可能不生效
标识符放行内代码 裸写带下划线或尖括号 被当语法，吞字符甚至整段消失
正文首标题用二级 正文再写一级标题 头信息已提供一级，页面会重复

小结

这些规矩没有一条在讨论哪种写法更漂亮，全是在给解析器的差异打补丁：原始约定与推进中的规范化不完全一样，托管平台多出的扩展不是到处都有，生成器还会再加一层。共同接受的交集比很多人以为的窄，所以团队规范应该写成只用交集，剩下的用脚本兜住。如果你也开始管一份文档，我建议先只定四条：段落优先、围栏必标语言、正文不写一级标题、关键信息不依赖扩展语法。这四条覆盖了我上面所有的事故。
