webpack 入门：entry、output 与 loader

2015 年下半年我们开始试 webpack，到 2016 年初这套东西总算在项目里跑顺了，可以把当时的配置模型梳理一遍。这篇不谈代码分割、不谈拆包策略，只把 entry、output、loader、resolve、plugins、dev-server 和 devtool 这几块地基讲清楚——它们是 2016 年 webpack 1.x 配置文件里全部的骨干，理解了这五六个字段，看别人的配置就不再像看天书。

先把结论摆在前面：webpack 和 Grunt、Gulp 的差别不在转换能力，而在世界观。后两者眼里的单位是”文件”，你告诉它搬哪些文件、依次做什么转换、落到哪儿；2016 年我们用的 webpack 眼里的单位是”模块”，你只说从哪个文件起跑，剩下的依赖它自己顺着 require 去找。这个差别看着只是写法不同，实际连锁出一堆问题：入口只有一两个、产物数量不由你点名、静态资源必须另外想办法、指纹的语义也和 gulp-rev 不一样。本文就沿这条因果链往下讲。

为什么会去看 webpack：2015 年末的三个痛点

在此之前我们的前端构建是 RequireJS 加 r.js 那一套，仓库里已经有一篇《RequireJS 模块化开发实战》把合并、压缩、路径映射讲完了，这里只引它的结论：AMD 的问题不在语法，而在于依赖关系是写在运行时的，构建期想要拼对顺序就得靠 r.js 再解析一遍，两边解析结果稍有出入线上就要炸。另一篇《ES6 Module 模块系统与构建工具》的结论也引一句：import/export 是静态可分析的，但 2016 年初的浏览器还不能直接执行它，必须靠转译工具先降级成通用模块语法。

webpack 在 2016 年初吸引我的，正是它把”分析依赖”这件事在构建期一次做透，而且只有一套解析器。三个痛点让它值得折腾：

第一，手写依赖数组太脆。RequireJS 时代每个模块头部都要写一串依赖名，改实现忘了改声明，本地一切正常，上线才炸。而 2016 年这套 webpack 里我只管 require，图是它自己长出来的。

第二，非 JS 的东西进不了管道。Gulp 的流式管道做图片压缩很顺手，但产物跟模块系统是两个世界；它的 loader 机制在 2016 年允许我把 CSS、SCSS、图片都当成依赖来引，一条链就通了。

第三，CommonJS 在浏览器里当年还得靠 browserify 转一层，配置零散；Gulp 加 browserify 那套我们试过，增量重建慢得难受，结论在《Gulp 流式构建实战》里已经说过，不再重复。

也要说清代价：webpack 在 2016 年的学习曲线比 Grunt、Gulp 陡，报错很不友好，一个 loader 配错能给出三屏栈，内部对要不要整体切过去是有分歧的。这篇就是为了让后来人少走这段弯路。

心智模型：从入口出发长出一张图

上手 webpack 第一步是把脑子里的”任务流”换成”依赖图”。2016 年这套心智模型只有四句话：

一切皆模块。入口文件、它引的 JS、引的 CSS、引的图片，在 2016 年这套 webpack 眼里都是模块，差别只是由谁来解读——JS 是内置就能认的，其余要靠 loader 转成它能认的形式。

从 entry 出发。入口就是图的根，2016 年这一版 webpack 从根开始读源码、找 require、递归下去，把访问到的文件塞进图里。没被任何入口引用的文件就等于不存在，产物里不会有它，这跟”把 src 整体编到 dist“的思路完全反着。

产物是打包结果而不是文件复制。图走完之后，2016 年的 webpack 把节点按入口聚合成一到几个输出文件，每个块内部自带一个迷你模块加载器，运行时按编号找到对应模块。所以产物文件名跟源码文件名对不上是正常现象，别指望改一个源文件就对应改一个产物文件。

loader 只做转换，不做打包。这是后面所有坑的根源。loader 是函数，进去一段源码出来一段源码，它不认识依赖图，也不知道自己会被谁调用；把模块们连起来这件事始终是 webpack 内核在 2016 年自己干的活儿。

用一张图概括这条流水线，配置项各自挂在不同环节上：

entry 的三种形态

配置里最先到手的就是 entry。webpack 在 2016 年只接受三种写法：字符串、数组、对象。三种不是”由简到繁的进阶台阶”，而是对应三类真实工程形态，选错了后面全歪。

output：产物落在哪、叫什么、从哪被访问

output 这块字段不多，但每一个都能让构建直接失败或者线上 404。先给一份能跑的：

path 必须是绝对路径。这是 2016 年我们第一个撞上的报错，写相对路径时终端甩出的是 “path without an output directory” 这类话，指不到根因。规矩只有一条：写 path.resolve(__dirname, 'dist')，永远别写 'dist'。原因很直白——配置文件是被别的进程 require 进来的，process.cwd() 取决于你在哪个目录敲命令，2016 年我们用两种姿势跑同一条配置，产物就落进了两个不同目录，只有 __dirname 是稳的基准。这条坑复盘还会碰到。

filename 里的占位符要认全。[name] 取 entry 的键名，单入口字符串形态下它是 main，这也是很多人第一次看到 main.js 却找不到出处的原因。[hash] 是整个构建的哈希，跟单个文件内容没关系——只要有任何一个文件变了，所有用 [hash] 的文件名一起变，2016 年我们把 [hash] 当指纹用被 CDN 坑过一次，复盘细说。[chunkhash] 才是按输出块内容算的哈希，改一个页面的源码只有那个页面的产物名变。另有 [id] 取模块编号，日常用不到。

publicPath 是所有异步加载与资源引用拼 URL 时用的前缀，它不参与文件名生成，只影响”运行时去哪里取”。三种典型场景：站点部署在域名根路径，'/' 就够；部署在子目录，例如内部平台把整套前端挂在 /web/order/ 下，这里必须写 '/web/order/'，少一个斜杠或者写成 'web/order'，2016 年那种需要再拉文件的场景会立刻 404；上了 CDN，就写 'https://cdn.example.com/static/' 这样的绝对前缀。一句提醒：publicPath 给运行时看，output.path 给构建进程写文件用，改一个不改另一个，就是本地一切正常、线上白屏。

chunkFilename 只在异步加载出来的块上生效，filename 管不到它们，所以那部分块的名字必须在这里给。这块的细节属于另一篇《webpack 初识：打包与按需加载》，2016 年 2 月会写，这里按下不表，只要知道”入口块用 filename、非入口块用 chunkFilename”这一句分工就够了。做组件包时还会用到 library 与 libraryTarget，把产物暴露成变量、CommonJS 模块或 UMD。

loader 是函数链：从右往左跑

loader 是 2016 年 webpack 最被低估的一层，也是坑最密的一层。它的本质就是一个函数：进去一段源码、出来一段源码，对依赖图一无所知，也不负责把模块连起来。所谓 CSS、图片能被 require，全靠它在中间翻译——把 .scss 变成 JS，把 .png 变成导出 URL 字符串的 JS，内核再按普通模块处理。

url-loader 与 file-loader 的取舍就在那个阈值。limit=8192 意思是 8 KB 以下转 base64 内联，超过就等价于 file-loader 走文件。base64 的膨胀比例仍在三分之一上下，2016 年我们把 limit 调到 32768，请求是少了几个，首屏那个 JS 胖了一截，白屏反而变长。定下的规矩是图标类小图内联、内容图与字体一律走文件。

expose-loader 管的是那个年代很现实的一类问题：老库没有模块化，只往 window 上挂全局。两种处理我们都用过——靠它硬挂，或者用 ProvidePlugin 与 imports-loader 把全局引用改写成模块引用。结论是能不碰就不碰，非用不可的老插件就在入口顶部挂一次，别在每个模块里散着写。

最后强调那句最容易被忽略的话：loader 不做打包。它只是转换器，链子末端交出来的必须是 2016 年 webpack 内核认得的 JS。理解了这一点，就能理解下面三个坑为什么会长成那样。

loader 的三个真实坑

坑一：只装了 style-loader，没装 css-loader，或者反过来。症状非常迷惑——装反顺序时报的是”找不到 loader”，缺 css-loader 时报的是解析错误，缺 style-loader 时构建居然能成功，产物里 CSS 变成一段导出字符串的 JS，但页面上样式就是不上，2016 年那次我查了一下午，最后靠把产物头部注释打开才看见 CSS 内容确实在里面。职责分清就不乱：css-loader 负责”读懂这段 CSS、把里面的 url() 变成依赖、导出一段字符串”，style-loader 负责”拿到这段字符串、往 <head> 里插标签”。

坑二：对 node_modules 也跑了 babel，构建慢到不能忍。我们那阵子依赖有百来个包，test: /\.jsx?$/ 一条通吃，2016 年那台机器上 webpack 把每个第三方包都当 ES6 源码转译一遍，全量构建从十几秒涨到一分多钟，--watch 改一行要等半天。修法就是加 exclude：

坑三：链式顺序写反。'css!style' 是典型反例：css-loader 收到 style-loader 的输出——那已经是一段导出字符串的 JS——它当 CSS 去解析，报错位置完全对不上源码。同类还有把 SCSS 写成 'sass!css'，症状是语法错误。定位手法在 1.x 时代很原始：把链子一段段拆开加回来。真正省事的预防是按执行顺序分行写，再加一条纪律：链子最右段必须是最贴近源文件语言的那个 loader。

extensions 里那个开头的空字符串是 1.x 的真实要求，不是笔误。2016 年这一版 webpack 在解析时会把候选名字按这个数组逐个拼上去试，空串代表”原名不加扩展”，缺了它，指向目录的 require('./common') 就解析不到 common/index.js，报的是找不到模块。这一条是我后来帮新人排错时命中率最高的一个点：本地写 extensions: ['.js']，一切目录式引用全崩，错误信息却指向业务代码。

root 给一个绝对路径基准，之后 require('js/common/util/date') 这种从 src 起算的写法就能成立，跨层引用不用数 ../。modulesDirectories 是查找依赖目录的清单，1.x 里默认只有 node_modules，我们因为还留着几个 bower 装的库把它写成两个。这两个字段名和后来的写法完全不是一回事，2016 年抄网上的配置要留意来源时间，很多帖子已经把字段换掉，粘过来只会得到一句 Cannot resolve module。

alias 是我们用得最狠的一个，价值有两层：一是把 src/js/components 缩成 c，组件引用变成 require('c/button')，挪目录只改一处配置；二是替换依赖，某个第三方包打了补丁、或者同一个库在仓库里有两份拷贝时，2016 年我们就靠 alias 把它按到指定文件上。注意它的值要给绝对路径，给相对路径的话基准又是 process.cwd()，和 output 那节是同一个坑。

plugins：管生命周期钩子的那一层

分层先说清楚，这是最容易混的认知：loader 管转换，发生在”读到一个模块”这个环节；plugin 管生命周期，拿到的是编译过程的钩子，能介入”图构建完了””产物要输出了”这类节点，作用对象是整体而不是单个文件。判断该写哪一个有一条粗尺子：只跟单文件内容有关就是 loader，一旦需要知道别的文件、需要跨模块汇总、需要往产物外面写东西，那就是 plugin。

DefinePlugin 做的是编译期文本替换，不是运行时赋值。源码里写 __VERSION__，产物里直接被换成字符串字面量，所以零开销；也因为是文本替换，值必须 JSON.stringify，漏掉它注入的就是一个未加引号的标识符，产物当场语法错。还有个副作用值得记：很多库靠 process.env.NODE_ENV === 'production' 包住自己的断言和警告，2016 年我们在发布链路里把它置成 production，那些调试分支才被剥干净。

BannerPlugin 只干一件事：往每个产物头部塞一行文本。我们放版本号，图的是线上出问题时在浏览器 Sources 面板里一眼看出跑的是哪次构建。头部塞构建时间戳会把指纹语义打乱，这个坑和当年在 Gulp 里踩的是同一个，复盘那节讲。

HtmlWebpackPlugin 我们用的是 2.x，用处是把产物 script 标签写进 HTML，chunks 指定这个页面引哪些块。多页站点里一个入口配一份 template、给一个 filename，HTML 侧就再也不用手工同步文件名，这对带 hash 的文件名几乎是必需项。NoErrorsPlugin 只在开发期挂：编译报错时它不让错误产物落盘，dev-server 因此继续跑上一轮那份能用的代码，配合热替换很稳，生产链路不该带它。

UglifyJsPlugin 与 OccurrenceOrderPlugin 是 2016 年 webpack 自带的两个优化插件，不用额外装包。前者压缩，后者把模块按出现频次重排编号，让高频小模块拿到短编号。这一代内置压缩器只吃 ES5 源码，所以前面必须有 babel 把语法转干净，否则报错会落在完全不相干的压缩环节。

开发闭环：2016 年初的 webpack-dev-server 1.x

先把一个认知钉住，它解释了很多”见鬼”的现象：2016 年初这一版 webpack-dev-server 的产物在内存里，不落盘。所以你在项目目录 ls dist 看到的是上一次构建的旧文件，浏览器里跑的却是内存里那份新代码。要落盘就走正常构建命令，两条路各管各的。

命令行姿势是当年最常用的：

--inline 决定它把客户端脚本打进页面、改完自动刷新，不加就只是一个静态服务，得自己按刷新。--hot 打开模块热替换，配置里要同时挂 HotModuleReplacementPlugin，只写一处时经常出现”参数给了却没生效”的错觉。收益在小改动上很直观：改一个组件样式或一个纯函数，页面状态不丢，2016 年做表单页时全靠它省下重填时间；代价是模块得自己写接受更新的接口，没写的会退化回整页刷新，这在当年是默认行为，不用当故障查。

--history-api-fallback 给用了 pushState 路由的页面兜底，把找不到的路径回落到 index.html，否则刷新一次就 404。它要配 publicPath 一起想：前缀写错时回落指向错误的 HTML，症状是刷新后白屏但地址栏一切正常。

接口代理靠配置里的 proxy，这是当年替代”改后端跨域头”的常规做法：

changeOrigin 处理的是 Host 头，很多后端按域名做站点识别或跳转，不加它就得到一串 302。当年也有同事用 Nginx 在本机反代，两条路都通，差别是 dev-server 把代理和编译绑在同一个进程里，改后端地址只动一处。另外这个 devServer 字段只对 dev-server 生效，写成顶层配置不会报错、也完全不生效，这类静默失效在 1.x 时代不止一处。

devtool：调试体验和构建代价的取舍

devtool 决定 map 怎么生成，不同取值在”能不能看到源码””报错指到第几行””构建多慢”三个维度上是完全不同的组合。2016 年我们只轮转四个取值，先给结论：开发用 cheap-module-eval-source-map，要精确到列时临时换 source-map，生产用 hidden-source-map，eval 只在等构建的间隙凑合用。

eval 最快，它把每个模块包进 eval 调用、末尾挂 //# sourceURL，代价是 map 只到行、看不到转译前的源码，断点全打在 babel 产物上。cheap-module-source-map 的差别只在 cheap 这一层：不生成列信息，构建因此快一大截，而 module 前缀能透过 loader 拿回一点原始源码。cheap-module-eval-source-map 是两者合体，开发期性价比最高，也是我们 --watch 下的默认值。source-map 给的是最完整的独立文件 map，能定位到列、能还原原始 SCSS 与 ES6，代价是时长和内存都上去；hidden-source-map 生成的 map 与它一样，只是产物里不写 sourceMappingURL，浏览器看不到、错误上报平台能拿去还原栈，这正是我们要的形态。

场景 2016 年选的 devtool 为什么这么选
日常 --watch 开发 cheap-module-eval-source-map 能看近似源码，构建代价可接受
排查 loader 转译出的怪代码 source-map 需要列信息才定位得准
CI 构建、map 只给上报平台 hidden-source-map 产物干净，还原能力留在内网
只想快速看逻辑不追根因 eval 最快，但只能看到转译后的行

最后一条纪律要写进发布脚本：map 不能公开部署。sourceMappingURL 指向一个公网可访问的 map，等于把未压缩的源码连目录结构一起发出去，内部接口名、注释、变量全在里面。我们的做法是 .map 只上传内部制品库、dist 里不留，顺带在 Nginx 上把 \.map$ 的公网访问拒掉。

多入口的工程结构与按环境拆配置

目录上我们没有发明什么，2016 年这套结构就是从 Gulp 项目平移过来的：src/js/page 一个页面一个入口，src/js/common 放反复引用的工具与组件，src/sass 按 partial 组织，src/static 放压根不该进依赖图的原始文件。变化在配置那一侧：入口一多，开发与发布的差异就写不下去了，一开始靠满屏 if (process.env.NODE_ENV === 'production')，半年后那份文件没人敢动。

后来收敛成”配置是函数”，把公共部分抽出来，环境差异留在外面：

两份文件加 --config 传参，比一个文件塞满分支好读，2016 年我们靠这个办法把配置从三百多行压回一百出头。另一条经验来自入口形态：多页站点一个 HTML 引一个入口，HtmlWebpackPlugin 按入口数量循环生成，模板共用、filename 与 chunks 各给各的。至于入口之间怎么共享公共依赖、产物要不要合并，那是拆包策略的事，本文不碰，另一篇《webpack 初识：打包与按需加载》2016 年 2 月会讲。

复盘：从 Gulp 流程搬过来时踩的三件事

配置抄得再快也没用，坑都在认知差异上。三件真事按代价从大到小记在这里。

第一件，静态资源压根没有入口。Gulp 那边一条 gulp.src('src/static/**').pipe(gulp.dest('dist/static')) 就把 robots.txt、验证文件、第三方 SDK、几张运营图搬进产物目录。换成 webpack 之后这些文件凭空消失了——没人 require 它们，图里就没有节点，2016 年我们花了一阵才接受”图里没有的东西不会出现在产物里”这条设定。修法不是把它们硬塞成入口，那会让公共代码被拖进一个巨大的块，而是引一个纯搬运的插件：

它挂在输出环节的钩子上把文件复制过去，不参与图、不做转换。这条分工值得记：搬东西就是搬东西，2016 年别为了”全都交给 webpack”把静态资源伪装成模块。

第二件，指纹语义对不上，CDN 缓存没按预期刷新。gulp-rev 是按每个文件内容算 hash，改一个 CSS 只有它的文件名变；我们把 output.filename 写成 [name].[hash].js，想当然当等价替换。实际行为是 [hash] 属于整次构建，任何文件动一下，所有 JS 的名字一起变，CDN 上每个 URL 都是新的、全部回源，缓存等于没有。更难看的是有一次发布只跑了构建、没重跑生成 HTML 的那一步，页面仍指向上一批 hash，线上直接 404 一批 JS。修法有两条：文件名换 [chunkhash]，让它回到”按输出块内容算”的语义；发布脚本把 HTML 与产物绑成同一个原子步骤，HtmlWebpackPlugin 在构建内完成替换，杜绝只更新一半。

第三件，output.path 写了相对路径。那天我把配置从 'dist' 改成变量拼接，本地怎么都对，CI 上产物却出现在仓库根和 node_modules 旁边两个位置，报错还是那句指不到根因的 “path without an output directory”。根子就是前面那条：配置被别的进程 require 进来时，相对路径按调用方的 process.cwd() 展开，CI 脚本多一层 cd 就换一个落点。修法只有四个字，__dirname。后来我们把”绝对路径”写进配置评审清单，output.path、resolve.root、alias 三处一律 path.resolve，2016 年再没复发过这类事故。

三件事合起来是一个结论：webpack 与 Gulp 在 2016 年不是同类工具，把它的配置当”另一种 gulpfile”来抄，坑就一定兑现。
