SVN 与 Git 的对比及迁移

我们组从 2013 年起一直用 SVN，到 2015 年底已经攒了一套还算稳定的协作习惯：谁改哪个目录、版本号怎么写进工单、发布分支怎么切，大家都心知肚明。所以当隔壁组开始用 Git 并把代码评审搬到 Pull Request 上时，我们没有立刻跟——不是抗拒，是想认真评估迁移到底能换回什么、会丢掉什么。这篇就是把那次评估和随后的迁移过程摊开写一遍。它不教 Git 命令，变基、分支模型、冲突解决另有专文，我只讲对比维度与迁移工程本身，面向已经在用 SVN、正要把迁移摆上桌面来讨论的团队。

结论先放在这里：工具层面的差异可以用脚本弥合，版本模型层面的差异只能靠改变协作口径来弥合，协作习惯层面的差异必须靠人来扛。最难的是最后一条，第一周效率下降几乎是必然的。

根本差异：一个真相源与每个副本都是真相源

SVN 是集中式。服务器上那份仓库是唯一真相，所有提交都要经过它，版本号由它统一分配，呈全局单调递增：r1234 之后一定排着 r1235，不管谁提交、在哪个目录提交。带来的日常手感是——没网时你只能编辑文件，不能提交；svn checkout 只把当前版本的工作副本拉下来，传输量小，检出很快；svn update 拉的是从你当前版本到最新版本的增量，服务端替你把合并做完。

Git 是分布式。每个人克隆下来的都是一份完整历史。提交只在本地完成，不碰服务器，所以离线也能提交、能建分支、能看日志、能改写自己的历史。代价是首次 clone 要把整仓连同所有历史拽进本地，仓库越大这一步越慢，检出速度反而不如 SVN 的按需拉取。日常同步时 git fetch 把别人的新提交拉到本地仓库，合并动作在你机器上做，服务器只做转发和存储。

这一层差异不决定优劣，只决定你每天做什么动作。如果你的工作流高度依赖”提交到服务器才算数”，集中式的心智模型会一直跟着你。

SVN 的真实优点

评估迁移时最容易犯的错，是默认 SVN 只有缺点、Git 只有优点。先把这套东西真正好用的部分写清楚。

第一是全仓库原子提交。SVN 的提交单元是”一次对整棵树的改动”，版本号覆盖整个仓库。一个需求同时改前端目录、后端目录和配置目录，提交完就是 r4521，一个动作、一个数字，要回滚就回滚 r4521，跨目录的改动不会裂成半套状态。Git 里你得靠一次提交把所有目录一起收进去，习惯没养成时容易漏文件。

第二是路径级权限控制。SVN 的服务端配置能直接把某个子目录设成只允许某些人读写，一句配置搞定。Git 服务端能控制的粒度是”谁能往哪个分支推”，落到目录级别的写保护得自己写钩子脚本去补。

第三是大二进制文件不会让工作副本膨胀。SVN 的工作副本只存当前版本，历史都在服务器上。美术资源库里有几百兆的图片和音频，日常检出仍然只占当前版本那么大。Git 的克隆把每次提交的二进制全带上，仓库体积随提交次数增长。

第四是 svn lock。对 PSD、AI 这类没法合并的二进制文件，锁定意味着”我在改，别人只能读”，改完释放。二进制本来就没有合理的自动合并可言，与其两个人改完对着冲突发呆，不如提前排队。

第五是全局版本号的沟通成本。工单里写”问题出在 r4521”，所有人一眼就知道是哪一次改动，数字带顺序。策划、测试、项目经理不需要理解 Git 也能对上号。

Git 的对应强项与代价

Git 换回来的第一件东西是廉价的本地分支。建一个分支就是创建一个指向某次提交的引用，几毫秒、不占服务器空间，可以随手开、用完扔。SVN 的分支本质是把目录复制一份，复制大目录很慢，于是大家的习惯是能不建就不建，试验性改动只能挤在主干上做。

第二是本地完整的离线历史。断网时你依然能看日志、比对任意两个版本、把提交拆开或合并。SVN 断网时这些操作全废。

第三是把工作现场暂存起来的能力。手上改到一半、临时要切去修另一个 bug，可以先 stash 把改动收进栈里，切回来再恢复。SVN 里只能手工拷贝或者把半成品提到分支上。

第四是自动定位引入问题的提交。bisect 这类能力让你用二分法在上千次提交里找出一处回归。

第五是评审与合并请求工作流。每份克隆都带完整历史，把分支推到服务器、发起一次带 diff 的评审请求、别人评完再合入，这条链路很自然。

代价也要写清楚。Git 历史可以在本地改写，推到共享分支之后还去改会把别人的副本变成孤儿，团队必须立规矩。仓库体积与首次克隆时间会随历史增长。新人要理解工作区、暂存区、本地仓库、远端仓库四个概念，比 SVN 陡一大截。

版本模型对不上的地方

这是迁移真正的难点，不是工具层面的坑，是模型层面的坑。

SVN 的 trunk、branches、tags 只是目录约定，在服务器看来和别的目录没区别，把分支目录整个删掉也算一次正常提交。Git 的分支和标签是仓库内部的引用对象，不是文件系统里的目录，git checkout 切分支时工作目录内容整体替换，这个动作 SVN 里没有对应物。所以在 SVN 里”我进 branches/feature-x 目录改东西”这句话，迁到 Git 之后要重新表述成”我切到 feature-x 分支再改”——动作像，语义完全不同。

更要命的是全局版本号。SVN 的 r1234 单调递增，天然带排序和比较。Git 的提交标识是一串哈希，不排序、不递增，两个哈希摆在一起看不出先后。这意味着工单和需求单里所有”参考 r4521 的改动”这类信息，迁完 Git 之后要么失效要么改口径。我们的做法是在提交信息末尾附上 SVN 旧版本号做过渡，同时在需求单里把”版本号”字段改成”提交说明关键词加日期”，跟测试组沟通了两周才把新写法推下去。

三条迁移路线

路线只有三条，选哪条要看团队规模和历史价值。

第一条是 git-svn 双轨共存。本地在 Git 里工作，要提交时通过它的 dcommit 动作把改动落回 SVN 服务器。适合一个组内部先小范围试点，不影响别人。代价是同一时间只能有一套工作流——本地建的 Git 分支没法推给同事共享，dcommit 会把它们压平成一次 SVN 提交，分支结构在服务器侧完全看不见。我们有个前端先跑了一个多月，自己用着顺，但推不动整个部门。

第二条是全量转换，用 svn-all-fast-export（社区里常按脚本名叫 svenscript）这类工具，或者 svn2git 这种上层封装，把 SVN 仓库连同历史一次性读出来写成 Git 仓库。速度快、历史干净，缺点是要事先备好作者映射表和分支目录规则，跑完还得逐条核对。

第三条是切点迁移。旧仓库转成只读留档，新仓库从当前工作快照起，历史不带走。最省事，代价是丢掉全部历史，追溯老问题得回旧仓库翻。适合历史价值不高的团队。

我们选第二条：三年攒下来的提交记录和问题单是排查回归的主要线索，扔不起。

全量转换要处理的四件事

第一件是作者映射。SVN 提交人写的是内部账号，Git 提交要名字加邮箱。转换脚本会给你一份未映射账号清单，照着建映射文件，一行一个。

邮箱要提前跟本人确认，别拿内部账号硬拼域名，将来做归属统计会乱。

第二件是分支与标签目录识别。脚本不知道 branches/ 下哪个子目录算分支、哪个只是第三方拷贝。要在规则文件里写清哪些前缀转成分支、哪些转成标签，剩下按普通目录走。规则漏一条，那部分历史就散落在目录里变不成分支。

第三件是 svn:ignore 属性转 .gitignore。SVN 的忽略规则挂在目录属性上，Git 放在仓库文件里，脚本能带出来的有限，角落里的属性得手工清点。

第四件是二进制与大文件。Git 仓库不适合堆二进制，历史越长体积越夸张。当时 Git LFS 刚出现，还是个新东西，我们都在观望，没敢往生产里投。多数同行的做法也差不多：把大资源整体移出代码仓库另存，仓库里只留引用路径。

迁移后的第一周会踩的坑

脚本跑完只是开始，第一周真正难的是操作习惯。原来 SVN 里上班第一件事是 update，顺带把别人昨天的改动拿进来，谁改了啥看一眼日志就清楚。换成 Git 后本地仓库不会自动同步，得自己拉，很多人一上午在自己那份副本上干活，下午才发现同事早就改过同一块，重复劳动就是这么来的。我们靠两条规矩止血：把同步动作写进开工检查项；每日站会最后留半分钟，每人说一句”我这块动过”。

.gitignore 漏项。挂在目录属性上的忽略规则转过来只覆盖了一部分，没覆盖的直接被打进仓库，提交里突然多出编译中间文件。我们在钩子里加一条”命中构建产物路径就拒绝提交”，把常见漏网模式拦在前面。

首次 clone 很慢。SVN 检出只拉当前版本，Git 把整仓历史全塞进本地，历史一长新人拉一次半小时不奇怪。临时缓解可以用浅克隆，只拉最近若干次提交先让人开工，但浅克隆不能拿来开发：它没有完整历史，做不了二分定位。我们的做法是在内网放一份预热镜像让新人从镜像拉，同时把仓库瘦身列入待办。

权限模型换了。SVN 是”这个目录谁能读写”，Git 变成”谁能往哪个分支推”，原来的目录级写保护直接失效，得靠服务端钩子去补。

习惯了 TortoiseSVN 右键菜单的同事一开始很难接受命令行，可以先用 SmartSVN 或 SourceTree 这类图形客户端过渡两周。

混合期的沟通策略

美术同事留在 SVN 是常态，他们改的是不能合并的二进制，锁定和覆盖的语义比合并语义更贴合。跟他们说得最多的一句是”为什么不再锁文件”：前端代码能合并所以不需要锁，他们那侧继续用 SVN 的锁。资源同步靠一条导出脚本，他们从 SVN 导出到共享目录，脚本把变化的文件拷进前端仓库并生成一次提交。当时没有专门的自动化平台，就是一段 shell 加定时任务，简单但够用。

跟非技术同事解释的版本写法是”日期加提交说明关键词”，SVN 时代写 r4521 就行，这套改口径沟通了两周才顺过来。

一段复盘

那个项目第一周开发效率明显掉了一截：提交动作变多、评审要走合并请求、SVN 里不会出现的合并冲突开始出现。第二周开始回升，第四周基本回到迁移前水平。

真正止血的三条约定都不复杂。主干只接受合并请求，不许直接推；合并请求当天处理，不许挂着过夜；每天开工先同步远端，把重复劳动的窗口压到最短。三条全是习惯层面的，跟工具无关，但只有换成 Git 之后我们才被迫把它们写下来。

一张决策表

情况 建议
团队小、仓库以二进制为主、评审需求弱 留在 SVN
工单沟通靠版本号，跨部门协作频繁 留在 SVN
分支用得频繁、试验改动多，能接受学习曲线 值得迁
想引入评审工作流，代码为主且历史有价值 值得迁
一部分人想要新流程，一部分人离不开 SVN 先双轨
项目要重启，旧历史只读留档即可 切点迁移

一句收尾：迁移成本主要在人的习惯，不在工具。脚本一晚上跑得完，习惯要改一两个月。
