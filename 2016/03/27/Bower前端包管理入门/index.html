Bower 前端包管理入门

去年冬天我接到一个活，把老管理后台里的 jQuery 从 1.x 升到 2.x。动手才发现项目里同时有三处声明着版本：package.json 管构建工具，bower.json 管前端库，另外还有一个没人认领的 lib/ 目录，躺着十几个 jQuery 插件，说不清是谁哪年拷进来的。升级那天改了三处里的两处，漏了第三处，上线后监控开始报错，查下去是同一个页面加载了两份 jQuery，插件挂在旧的那份上。那段时间团队里同时有人主张全部迁回 npm，也有人想把 bower 这层推广到更多项目，两边都能讲出道理，谁也说服不了谁。这次事故让我正视真正的问题：当时为什么要在 npm 之外再养一套包管理，以及为什么现在没人愿意继续养它。

bower 当初凭什么存在

2012 到 2014 那几年，npm 的包主要伺候的是 node，浏览器库撞上三道墙。头一道是很多库根本没发 npm，作者觉得前端库没必要进 node 的包体系；第二道是发了的包里面掺着 node 专用代码，入口脚本、命令行工具混在一起，摘浏览器要用的部分很别扭；第三道是入口本身，npm 的 main 指向 CommonJS 实现，你想直接丢进页面的那个打包好的文件反而藏在别的深层路径里。bower 的答案是做一层很薄的东西：把给浏览器用的库从 git 仓库或压缩包取下来，原样放进本地目录，不关心模块规范、不合并、不编译。它也没有自建内容分发的野心，注册表基本就是仓库索引加一点元数据，包的真相一直在仓库本身。论功能它比 npm 少得多，但薄恰好是它能活几年的原因。代价也来自这层薄：它对模块规范完全无视，装进来的 AMD 写法、CommonJS 写法和全局变量风格原样混在同一个目录里，喂给加载器时还得靠补救措施一层层收拾，这层混乱老项目都见过。

bower.json 的字段各管什么

bower.json 和 package.json 字段名像，语义却不是一回事。name 与 version 没什么争议，version 主要是给人看的，bower 实际靠仓库的 tag 认定版本。麻烦出在另外几个字段上。

main 声明包里哪个文件是给浏览器的成品，可以写数组列多个。问题是作者认定的成品和使用者想引的经常不是同一个文件：有包把 main 指到未压缩源码，有包把 js 和 css 一起列出来逼构建任务再过滤一遍，还有的干脆不写 main，只能靠硬编码路径。我们那会儿的做法是构建脚本读 main，读不到的落回手写清单，于是每个 main 缺失的包都变成胶水脚本里的一处隐性配置。

ignore 作用接近 npm 的发布排除，把测试、示例这类目录从取用范围里裁掉。dependencies 与 devDependencies 的分法照抄 npm，只是纯前端项目里运行和构建的界限比 node 侧模糊，分类经常取决于这个库谁在用。

吵得最多的是 resolutions。两个依赖各自要同一个库的不同版本时，npm 那套语义化依赖乐意让 1.x 和 2.x 各装一份相安无事，bower 的立场却是扁平目录里一个包只许存在一份，它的策略是要求单一版本，自己选不出来的时候就把选择权直接丢回给你：交互式地停下问你用哪个，答案写进顶层 resolutions。这条规则的实际含义是冲突从不会悄悄解决，反面是自动化流水线上任何一次别人升级依赖，都可能让所有人重新做一次版本选择。更麻烦的是传递依赖：你的直接依赖各自写了范围，它们包里的清单又带来下一层范围，交集为空时报错只说哪两个包在争，不告诉你要改哪一处声明，新人常常以为重装一次就好，其实那次重装只是把同一个问题再问一遍。我们后来习惯把要紧的依赖写成精确版本，让 resolutions 只兜真正的冲突，把做决定的成本前置，换流水线不被突袭。

版本范围与 overrides

依赖项一样支持语义化范围，~、^、>=、通配符都可用，语法直接沿用 npm，区间符号怎么取舍那笔账和写 package.json 时相同，这里不重复展开。

私有库：直接吃 git 地址

内网里 bower 比注册表活得久的主要原因，是依赖项可以直接写 git 地址：内网仓库、带 tag 的引用、压缩包都行。

owner/repo 那种简写原本指向公开托管站点，我们把内网 git 服务配成同构的命名，两类依赖才能混在一份清单里。写的时候省事，后果要在流水线上还。第一个后果是构建机必须持有能读这些仓库的 git 凭证，机器重装后安装报错，第一反应往往错怪网络。第二个后果是 bower 靠 tag 认版本，一旦仓库打了 tag 但包内 bower.json 的 version 字段没同步，范围解析时两个语义对不上，resolutions 钉住的那个版本可能根本没有对应 tag，换个机器就装失败。我们后来的规矩是私有库的 tag 名与 version 必须一致，且由同一条发布命令产出，否则就把它写成固定引用而不是范围。另外直接吃 git 也让查版本变贵：注册表上能一眼看到的信息，仓库里未必有对应 tag，升级前得先去内网仓库翻一遍提交记录，这些隐形成本平时看不见，出问题时全得还。

和 npm 的分工怎么判

到 2016 年，某个库走 bower 还是走 npm，已经不再是平起平坐的选择题。我们的判断依据有三条。第一条看这个库最终要不要经过模块加载器或打包器进页面：只在 node 侧用的工具毫无悬念走 npm，浏览器侧的趋势是库越来越直接发 npm 包并带浏览器可用的文件，走 bower 只是多绕一层历史通道。第二条看作者有没有发 npm 包：有就优先 npm，作者发布时两边会先后更新，而 npm 那份通常先到；只有 bower 有、npm 上没有，往往是个库已经不活跃维护的信号。第三条与技术无关，看团队里谁负责合并与上线：bower 到构建之间的胶水必须有人维护，如果没人愿意认领这段脚本，就不该再往 bower 添新依赖，因为添进去的那天就是把它留给下一个人接盘。

2016 年 3 月的实况是 npm 正在把前端库的发布通道吃掉，bower 的位置在缩，但存量项目的依赖不会一夜迁完。所以我们的清单分两类：新增默认 npm，存量留任，且每个留任都要说得出理由。

迁移的三步写法

迁移不是一次切换，是三步交接。第一步盘点，把 bower ls 列出的包名逐个去 npm 上搜同名包，看版本落后的多不多，这一步真正的产出是一张三类表：两边都有且版本齐的、npm 上有但明显落后的、压根没有的。热门库到 2015 年底大多已经两边都发，剩下的那一小撮才决定你还要不要把 bower 留在工具链里。第二步把能对上的依赖改成 npm 安装，构建任务里从 node_modules 取文件，这一步有个当年新增的路径坑：npm 3 尽量把依赖扁平提到 node_modules 顶层，脚本里写死深层子路径会扑空，可靠办法是按包名解析入口字段再拼路径，别硬编码目录层级。第三步处理剩下的：只有 git 来源或者压根没发 npm 的库单独留着，继续在 bower 里托管或者干脆手工 vendor，并在清单旁写上留任理由——底线是不能再允许任何一个库的来源处于没人认领的状态。

过渡期最怕的是 bower 和 npm 同时在装同一个库，各产一份还都被打进产物，开头那种事故原样复发。办法是在构建脚本里加一条重复检查：收集进 vendor 的文件名归一化去掉版本与路径，同一库名出现两次就让构建失败。这条检查技术含量很低，但它拦住的就是本文开头那次事故。

排错经验几条

最常见的是 bower install 卡在某个包不动。它取包走 git，卡点通常不在注册表而在代理和凭证：配了系统代理的机器上 git 自己那份代理配置没跟上，或者内网仓库的密钥没加载，表现就是挂着而不是报错。碰到时先手动克隆同一个地址试一次，基本能立刻分辨问题在哪层。

其次是同一库被两个包各要一个版本。处理顺序我们有共识：先看两边范围能不能一起升上去取交集；升不动再用 overrides 改掉其中一方的依赖声明；实在没办法才用 resolutions 硬钉单一版本。硬钉的代价是它没解决任何一方不兼容的可能，只是让机器不再问你，钉完必须把用到了该库的页面跑一遍。

然后是缓存。bower 把取过的仓库缓存在本地，tag 被强推重写也不会重新拉取，于是出现别人机器好使、我这里永远是旧版本，而清单明明一致。当时对这类现象的第一反应就是 bower cache clean，清完再装，成本极低。

最后是 bower update 和 bower install 的语义差别，新人最常在这里翻车：install 按清单办事，本地 bower_components 里已有且落在范围里的版本它不动；update 才会把版本往范围顶端去满足，并且把结果写回清单。想升级却跑 install，会得到一次毫无动静的成功；跑 update 又是整套一起动，只想动一个包必须显式带上包名。这套手感和我们从 npm 带来的直觉不一样，我们花了大概一个季度才纠正过来。

收尾

回头看，bower 这一层之所以会出现，是因为当时发布渠道和浏览器可用性之间没打通，作者发版本和页面拿到文件之间需要一条专门的通道。这个缺口后来由 npm 包加打包器合上，工具本身已经不是必需。但有一件事不会被工具带走：把资源依赖显式列成清单，并且让清单和合并顺序、落地路径绑定。只要页面还在加载多个库，这个工作每天都要做，只是换工具做。开头那三处清单并存的事故，根因不是用了 bower，而是有一处清单从来没和构建绑定过。
