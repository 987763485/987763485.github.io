代码评审中的常见问题清单

那次事故本身不复杂：一个列表页在接口偶发返回空值时整片白屏，从发现到回滚花了四十分钟，影响的是活动入口。复盘时把提交记录翻出来，代码评审是有两个人看过的，也都点了通过。被讨论最多的是那个新抽出来的工具函数名字取得准不准、参数要不要换个顺序。真正会炸的是两行，一句对接口返回结果没做任何校验的取值，和一个没写错误分支的回调。那两行没人注意。

这件事让我确认了一个不太舒服的判断：问题不在评审有没有做，而在评审这个过程中没有清单。人的注意力落到一段陌生的 diff 上会自己找事做，而风格问题最显眼、最容易判断、也最容易让人产生”我在认真看”的错觉。注意力被这些东西吃掉之后，风险还留在原地。

机器能查的一律不占用评审注意力

清单存在的前提是评审时间很贵。分号、缩进、未使用的变量、缺少基数参数的 parseInt，这些在 2016 年已经能让工具报出来，规则文件锁进仓库、构建任务里跑一遍就清掉了，评审时再提一次就是把人的注意力花在不要钱的地方。我们的纪律是凡检查器能报出来的问题，评审里出现就算流程有漏。

把机器能查的部分清掉之后，剩下的才是评审真正要面对的：这段逻辑对不对，边界情况下页面什么表现，改动影响到谁，上线出事了怎么退。这四类东西工具报不出来，因为它们需要背景知识。所以下面这八组核对项不是拿来打勾的表格——真的一边看代码一边逐条勾选，注意力照样会跑偏。它的正确用法是评审开始前扫一眼，提醒自己该带着哪几个问题进入这份 diff。

正确性与边界

这组最容易看出作者有没有跑过异常路径。异步回调只写成功分支是最常见的写法。

对着这四行要问两句：接口报 500 或者超时的时候页面是什么状态；res.data 少一层的时候会不会直接抛。第二个问题接着牵出 JSON.parse 和接口结构未校验——把返回体当可信数据直接取值，在评审里属于一眼就能认出来的征兆。

空值判断也要多看一眼。当时满仓库都是 if (arr && arr.length)，这句本身没错，错在同一段代码里另外两种写法同时存在：有人写 if (arr.length > 0)，有人直接 if (arr)。于是”空数组到底算不算有效数据”要读者自己猜。同理，null 与 undefined、空字符串与数字 0 混在一起时，出现 == 或者对返回值直接取反，都是该问一句的地方。

循环里的闭包捕获是 ES5 场景的经典雷。

看到 var 的循环里创建回调，就问一句这个回调执行时 i 是多少。最稳的改法是用 IIFE 把 i 当参数传进去；改用 let 要先确认转译后的产物是不是还保留了每轮绑定的语义，.babelrc 里一条 presets: ["es2015"] 并不能保证这件事，所以看的是构建输出而不是源码。

还有两条每次都要问：日期与字符串的比较有没有依赖时区；parseInt 有没有显式传基数。后一条工具能报，但只在规则打开时才报，我见过太多评审因为规则文件里没开这条而整批漏过去。

兼容性

这一组是前端评审比后端多出来的一整块，因为代码最终要跑在没人控制的浏览器里。判据只有一句：这段代码在不支持它的浏览器里是降级还是白屏。

JS 侧看到新 API 就查有没有声明 polyfill。Array.prototype.includes、Object.assign、dataset、classList 一次传多个参数，在当时的 IE 上都有问题。Promise 更明显：Babel 只转语法、不管内置对象，polyfill 必须显式引入。代码里出现了 Promise 而入口没引入，评审就该问一句有没有在老内核上测过。

CSS 侧看三样。前缀齐不齐——当时已经靠 PostCSS 加 Autoprefixer 按 browserslist 生成，所以人手工写前缀反而是个征兆，说明这段没走构建流程。flex 有没有考虑 IE10 的旧语法，calc() 和渐变在老内核上的兜底在哪。然后是条件注释与 hack：一行 _height 或者 *width 塞进新写的组件里，通常意味着当初绕过某个 bug 时没写原因，两年后没人敢删。

最后一条判据是 UA 判断。从 navigator.userAgent 里挑字符串来决定功能分支，比特性检测脆得多，新内核一改 UA 就全部命中。评审时看到就问能不能换成特性检测，换不了的必须写明判断依据。

性能征兆

这组的原理都有专文，评审里只需要认出征兆。

最强的一条是在循环里交替读写布局。

看到循环里出现 offsetHeight 或者 getBoundingClientRect，就问一句这一轮读取会不会触发强制同步布局、循环跑多少次。

其余几条扫得很快：scroll、resize、input 直接绑了重活没做节流；每次数据变更都重建大段 DOM 而不是复用节点；图片按原始尺寸输出给一个小容器；选择器写成 * 或者一串过宽的层级；动画改的是 top、left 而不是 transform。最后这条提出来成本很低、收益很确定。

可维护性

这组最容易吵，因为几乎每条都能被反驳”现在也能跑”。函数长到一屏半且职责混杂；一个 PR 同时改了样式、埋点和另一个模块；魔法数字没有来源说明；复制粘贴出来的近似代码块；注释写的是做了什么而不是为什么；临时调试的日志和 debugger 留在仓库里。还有一种是把东西挂到 window 上跨模块取用——挂的一方不知道有多少人在读，改的一方不敢动。

这一组我的建议是绝大多数按建议改提。评审里真正拦得住的是”这个 PR 做了三件事”和”调试代码留着”这两条，因为它们的代价由别人承担。函数长短属于口味加经验的混合体，硬拦只会让人下次不提。

安全

这组不做分级，直接给红线：未经转义的字符串不许进入 innerHTML。属于必须改，没有讨论空间。

这里的 query 来自地址栏。修法是走文本节点或者统一过转义函数——评审只看这一句有没有转义。

跟着的几条同样按必须改看：URL 参数直接拼进跳转目标，location.href = getQuery('url') 是最典型的开放重定向；eval 与 new Function 处理外部输入；把密钥、内部接口地址、测试账号写进会被打包进产物的源码；新增外链脚本没固定到可控来源也没写校验。前端代码是整个交给用户的，这类东西进了仓库就等于进了对方的控制台。

可测性

这一组当下不影响功能，两周后想补测试才发现补不了。征兆都跟”一加载就干活”有关：模块初始化时就发请求或者读 DOM；依赖全局状态，导致用例之间互相影响；纯逻辑和副作用写在同一个函数里，输入输出拆不出来；当前时间和随机数直接内联，断言写不出来。

要说清一件事：可测性差不是测试的问题，是实现的问题。评审里提这条听起来像增加工作量，所以更要当场问。代码合进去两周以后没人愿意为了”能写测试”去重构，那时候的代价是整块重写。

上线风险与回退

这组是前端评审里最常被整段跳过、代价最大的一组。原因是它的每一条都不在当前这份 diff 里，需要评审者带着部署和依赖的记忆来问。

先问改动有没有影响缓存：产物有没有带版本号或 hash，同名文件会不会被 CDN 留住旧版本，这点另有专文，一句带过。然后问最要命的一条：公共组件动了吗。改了一个被十几个页面引用的组件、却只自测了当前页面，这种 PR 的通过理由通常是”我看了 diff，只加了一个分支”。评审时要求作者列出影响面和验证过的页面，比看代码本身管用得多。

接着是跨端依赖：接口字段有没有依赖还没上线的后端版本，新字段缺失时前端有没有兜底。当时常见的事故就是前端先发、后端还在灰度，页面取到 undefined。然后是开关与灰度：这个功能能不能只放一部分流量，出问题时怎么关掉。如果答案是要重新发一次版才能关掉，这一条就该按必须改提。

最后两问：回退方案是什么，以及发布顺序会不会错。我见过一次评审全部通过、代码本身没有问题、事故纯粹来自静态资源和页面分两次发布、中间隔了半天。这类风险在 diff 里完全看不出来，只能靠问。

交付细节

这一组是前端特有的，后端评审通常没有对应项。也正因为看不出技术含量，它在评审里最容易整组消失，所以必须单列。

图片有没有 alt，表单控件有没有跟 label 关联，只用图标做按钮的有没有可访问文本——这三条对读屏用户是直接的功能缺失。然后是文案与错别字，尤其带数字和单位的提示语。埋点参数有没有漏或写错，当时的办法是让作者把埋点表格里的 id 和参数名列进变更说明，评审照着对照。loading 与空状态有没有做，只有成功分支的界面在慢网络下看起来就是坏了。移动端再加两条：输入法弹起时布局会不会塌，滚动区域和页面滚动会不会抢手势。最后一条最容易被忘：日期显示有没有处理时区，运营在后台看到的是 UTC，用户看到的是本地时间。

必须改与建议改怎么分级

清单之外还需要一根分级杆子，否则同一份清单会被两个人用成两种强度。我们的定义很窄：会导致线上错误或数据错误、安全漏洞、兼容性白屏、不可回退的，是必须改；风格、可读性、可维护性、可选的性能改进，是建议改。这四条之外的，一律不许标成必须改。

实操层面就是评论里把级别写进句子。写成”这条必须改：query 没转义就进了 innerHTML”，作者只能改；写成”建议改：这个函数可以拆成两个”，作者可以回一句下个迭代处理，合并照样往下走。没有这个约定时，讨论会滑向”你到底觉不觉得这是问题”，级别不写清楚，作者只能按最严重的理解处理，于是一周只敢出两个 PR。

反过来，全部按必须改提，等于没有必须改。真遇到必须改那一条时，别人已经没有预算给你了。我现在的做法是给自己一个额度：最多两条必须改，超出就先想清楚这条有没有掉进那四个条件里。

流程上的几个细节

剩下的都是流程。PR 大小：几百行以上没人真正在看，当时我们把单个 PR 压在几百行内，宁可拆成几个能独立合入的顺序提交。评审前作者自查三件事：先跑检查器，先把功能自测一遍并截图贴上，再写一段变更说明讲清动了哪些地方、影响面、验证方式。这三件做完，评审者不必花时间猜背景。

评审者这边，先读变更说明和关联需求再看代码，一上来就读代码会把注意力浪费在”这段是干什么的”上。讨论只在评论区留字，不留口头——线下说完没人记录，三个月后 blame 出来的是一句”按讨论修改”。响应时间约定当天回，因为评审拖过一天作者的上下文就丢了，重看的成本远高于回看。服务端 hook 拦住直接 push 主干这条路也要开上，不然所有流程都靠自觉。

最后回到清单本身。它不该只在评审时使用。我们把这份清单发给作者，要求在提 PR 之前自己照一遍，附上影响面与回退说明。同样的注意力花在评审发生之前、花在自己的代码上，比事后一条条挑出来便宜太多，也少吵很多架。
