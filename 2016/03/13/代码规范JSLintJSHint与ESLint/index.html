代码规范：JSLint、JSHint 与 ESLint

去年冬天，一个 PR 的评论区里两位同事吵了起来。一方在工具函数里写了个 ==，lint 报红，他坚持这段没有问题，认为报错是工具太死板；另一方不肯放行，说绿灯是合并的最低要求。吵到最后，两个人争的其实不是这一行代码，而是一个谁也没认真回答过的问题：这个工具到底是在查错，还是在管风格。这篇文章就从这个分歧说起。规范条目本身另有《前端开发规范落地实践》写过，这里不重复命名、目录、CSS 那些约定，只讲 JS 这一层我们拿什么工具去扫、配置怎么写、怎么接进构建，以及迁移路上踩过的坑。

三个工具不是一回事

在把第二个项目从 JSHint 往外搬的时候，我们才真正想明白三者的差别不在规则数量，而在它们看代码的层次。这个差别决定了接入难度，也决定了各自的脾气。

JSLint：作者认为对的那套选项

JSLint 是三者里最早的，Douglas Crockford 写的。它的设计前提相当强硬：作者认定一套正确写法，其余都是陷阱，工具的职责就是把陷阱逐个指出来。所以它的配置项极少，大量规则根本不给你关闭的开关。我们试过拿它去扫一个老项目，一次跑出上千条，其中缩进必须用空格、变量必须声明在函数顶部这类规定完全没法谈，只能整体接受或整体不用。它确实能抓住真错误，代价是让整个团队按他一个人的标准重写代码。对一个要渐进落地的团队来说，这个选项一开始就是死的。

JSHint：从 JSLint 源码里分出来的开关盒

JSHint 的出身就是 JSLint 的源码，卖点只有一句话：把选项拆开，让项目自己声明。环境用开关声明，browser、node、jquery 各管各的；es5、strict 有独立开关；连 asi 这种争议规则也能关掉。我们终于能按项目写配置了。但它读取的仍是文本层面的信息，它对你代码的理解停在”这行字符合了某个模式”，而不是”这行在语法树里意味着什么”。所以更复杂的结构性规则它写不出来，自定义规则的生态也一直没做起来。

ESLint：先解析成语法树，再挂规则

ESLint 是另一种思路：先把 JS 解析成抽象语法树，规则在树上匹配节点。这一步改变了一切。检查缩进和检查未定义变量变成同一类事情，都是在遍历树时对节点做断言；规则可以做成插件外挂；连解析器本身都能换，新语法换个解析器就能进同一个检查器。这是 2016 年的它能吃下 ES6、能长出插件生态的根本原因，也是 JSHint 追不上的地方。一句话概括三者的分工：JSLint 听作者的，JSHint 听项目的，ESLint 允许你自己定规则。

坑在 predef。每加一个依赖就追加一行，删的人一个没有。我们那份清单最后长到四十多项，评审时根本说不清哪个变量还在用。更糟的是一次拼错的全局名被顺手加进清单，undef 从此对这个错误视而不见，引用它的所有代码全部放行，这个 bug 花了我们半天才定位。后来定了条规矩：往 predef 写任何一项，必须带一行注释说明来源，来源不明确的不予合并。规矩不重，但清单在之后半年缩掉了三分之一。

.eslintrc：从声明环境到声明规则

ESLint 的配置是另一套语言。env 对应 JSHint 的环境开关，globals 对应 predef，重心则落在 rules——每条规则自己声明严重级别，当时很普遍的做法是用数字表达三个档位："off" 或 0 关闭，1 是 warning，2 是 error。

对照 JSHint 迁过来时有两个新东西。一是规则的值可以写成数组，第一项是级别，后面是规则自身的参数，semi 和 quotes 就是这样，风格规则第一次有了协商空间。二是 extends，继承一份现成规则集再逐条覆盖。我们起步就是 eslint:recommended 加自家几条松绑；eslint-config-airbnb 那时候已经开始有人用，我们试过，它对 React 和模块语法的取向太重，套在纯脚本项目上水土不服。

第一次迁移我们犯了个反直觉的错：把 no-undef 设成 1，想着先温和提醒，别把大家吓跑。结果 CI 上一片黄色警告，构建永远绿，半年内没人认真读过一条。没人看的警告等于没有。后来我们把语义类规则全部压到 2，只给”将来可能改主意”的留 1。数字是机制，不是装饰。

ES6 语法与那行 Parsing error

真正让我们对 ESLint 改观的，是在一个已经开始写 import 和 class 的项目里第一次跑它，屏上直接甩出 Parsing error: The keyword 'import' is reserved。第一反应是这工具不行，后来才想明白：不是规则严，是解析器根本不认识这些字。ESLint 默认解析器当时只认 ES5，而我们的代码已经回不去了。

但还有一个更磨人的现实：规则集本身对新语法的支持参差不齐。class 里的方法被老规则误判成未使用函数，模块相关的规则一半是坏的，报出来的错误里相当一部分是工具自己的锅。你得逐条判断哪些该改代码、哪些该等工具，这活儿没人能替你批量做。升级方面我们按团队的保守策略来了：ESLint 1.x 已经用了挺久，2.0 是刚放出来的，配置方式有 breaking 变化，插件命名和 extends 的写法都有调整，构建任务、编辑器插件、CI 脚本得陪着一起动，所以没急着升，先观望，等生态跟上来再评估。

JSCS：两个工具一起跑的那段日子

风格这一半，ESLint 当时管得并不好，所以我们和很多人一样，另外跑一个独立的风格检查工具 JSCS，专门管空格、缩进、大括号位置、链式调用换行这类事情。ESLint 的 indent 规则对续行的判断经常出错，JSCS 在这类问题上更稳，两边配合看起来挺合理。

麻烦在于两个工具就是两套规则集，边界没划清就会互相打架。我们有一整周是在统一大括号风格时，一边要求换行、一边禁止换行，按哪边改另一边都红，改代码的人在两种报错之间来回横跳。最后的划界办法很粗暴：ESLint 里凡涉风格的项，semi、quotes、indent、brace-style 全部置 0，这一半整个让给 JSCS，ESLint 只管语义。粗暴，但有效，至少错误能收敛。

代价是双份。检查时间翻倍，配置文件各写一份且语法完全不同，新同事来了要先解释哪条报错来自哪个工具。这个局面谈不上优雅，我们当时也隐约觉得边界早晚要重画，只是没人知道更好的做法，只能先在共存状态下把日子过下去。

编辑器里的即时提示也要收口

当时队里一半 Sublime Text、一半 WebStorm。Sublime 靠 SublimeLinter 加对应的 eslint 或 jshint 子插件，WebStorm 要在设置里手动勾选启用并指定配置文件路径。麻烦不是装插件，是配置散落在各人机器上：有人指到了自己 home 目录那份旧文件，有人干脆没开，同一个提交里每个人看到的报错不一样，改三处推上去 CI 还报十处。

收口办法只有一个：所有编辑器插件一律读仓库根目录那份配置，编辑器里没提示也照常提交前跑命令行的那一份。即时提示是提速手段，不是标准；标准只有 CI 跑的那一份。这和上一篇”配置以仓库为准”是同一个道理，工具换了，理没换。

存量项目落地：三步走，和一次惨败

几万行的老项目当天上 lint 是不可能的。我们最终走通的三步：第一步，只开最想要的两三条规则，其余显式关掉，先让 CI 变绿；我们开的是 undef、unused 和 no-alert，让工具第一天就抓到真 bug，团队才愿意继续用。第二步，用 ignore 把还没动的目录圈出去，.eslintignore 或 gulp 任务里的 glob 都行，检查范围只覆盖正在改写的模块。第三步，每轮迭代缩小一点 ignore，直到圈空。

这个次序是拿一次惨败换来的。上一个项目我们第一天花一整天把 globals 全部声明、所有规则开成 error 推上 CI，第一次跑出一千八百多条，第二次还是那些，到第四次有人开始给编辑器关插件，半个月后那个项目的 lint 名存实亡。一次性面对一千八百条错误不是纪律，是噪音，噪音教给人的不是改错，而是无视工具。换成三步走后，第一周 CI 只红过六次，六次全被改掉了，这才算落地。

争议规则该不该开

分号、eqeqeq、no-unused-vars 这三条吵得最凶，各自都有具体的麻烦。

semi 最典型。有人主张省略分号，反正构建工具会处理；有人认定自动插入分号的陷阱太多，必须每条都写。这个分歧没有逻辑解，因为要不要算陷阱取决于目标浏览器和团队对风险的承受度，谁也说服不了谁。eqeqeq 看起来是明显该错的，但 x == null 是同时判空的标准写法，一刀切以后豁免注释堆了一堆；我们一度把它降成 warning，又在团队里约定只允许和 null 比较时用 ==，配置表达不了这条，只能靠评审补，很别扭。no-unused-vars 的麻烦在回调签名：function (err, data) 里 data 没用就报黄，于是有人改名有人加注释豁免，两种做法混着来反而更难读。

我们的结论是一条原则：能被机器决定的交给机器，统一写进配置，别再靠人自觉；影响可读性但没有对错的东西，比如引号，也要统一，只是统一的重点在全员一致，而不是哪种写法更好。配置里选了双引号不代表它更好，只代表它赢了那次投票。把这层意思讲透之后，类似的争吵确实少了很多。

小结

这三个工具的分工在几年里一直在变：早先是”选哪个”的问题，2016 年的我们已经把它变成”用 AST 级的工具搭一套自己项目的规则集”。JSLint 的影响退缩到少数构建脚本，JSHint 还守着大量存量项目，ESLint 的生态刚长起来，我们自己也还在观望 2.0。

最后把定位说清楚：linter 是评审的第一道闸，不是评审本身。它能回答的只有”这段代码不符合约定”，逻辑对不对、测试够不够、抽象好不好，还得靠人。规范内容怎么写、评审流程怎么走，另有专文展开；这篇的任务，只是让检查器这一层能跑、能绿、能接进流水线。
