前端构建产物分析与优化

2016 年开春那阵子，手上一个后台项目刚做完一轮改版。本地构建一路绿灯，产物躺在 dist 目录里安安静静，我连进去点开看过都没有。上线当天下午运营就在群里说首页转圈久，我远程连过去打开 Chrome 的 network 面板，勾掉缓存重刷一遍：加载时间六秒多，瀑布图末尾一个 JS 文件孤零零顶在那儿，Size 列写着 1.2 MB 往上，后面还跟着几个五百来 KB 的同伙。

那一刻我承认，之前所有关于”大不大”的判断全是凭感觉。我觉得这个包不至于，我觉得那张切图还行，我觉得 gzip 反正开着。真实情况是：产物里装了什么、每块占多少字节、用户到底下载了多少，我一个问题都答不上来。后来我给自己立了条规矩，先量化再动手。这篇文章就是把那套量化的土办法记下来，用的全是当时命令行里就有的东西。

至于块怎么切、require.ensure 怎么写、公共块插件怎么配，前面那篇聊过了，这里不重复；静态资源版本号与缓存刷新、雪碧图和 base64 的取舍、切图标注的协作流程也各有专文，我只在需要的前提位置提一句。

度量这件事，别只盯输出面板最后那张表

2016 年初我们用 webpack 打包，跑完构建终端会留一张按块统计的表：块名、体积、有没有告警。这张表只到块的粒度，看不出块里到底是谁把字节吃掉的，所以我做的第一件事是把它榨干，让构建工具把模块清单直接吐出来。

三个选项各管一段。--display-modules 把每个被打进来的模块连同它属于哪个块列出来，这是找大头的原始数据；--display-chunks 反过来按块列模块，适合看某个块被谁塞满了；--display-error-details 在我把某个路径写错、模块解析失败时能把它到底找了哪几个目录都打出来，省下大量瞎猜时间。清单一长，终端就翻不动了，所以真正该做的是把它写成文件再离线分析。

这份 JSON 里有模块名、字节数和所属块，比肉眼翻日志靠谱得多。清单到手之后，那会儿我没能找到合适的可视化分析站点，也不打算把内部项目的产物统计传出去，就写了个几行的脚本排序，每周构建完跑一次。

第一次跑完这个排序我有点意外：占了前几排的不是业务代码，是两个我几乎想不起来为什么在项目里的包，还有一个日期库的语言数据目录。这就是只看块级报表的坏处：数字看得见，来源看不见。

stats.json 还能再挖两层：块内归属与重复拷贝

排序只是第一层。这份清单里块和模块的引用关系都在，往下多写十几行就能回答两个更值钱的问题：这个块是被谁填满的，同一个包是不是被装了两份。

归属那段输出来是这样的形状：一个块总共几百 KB，前两行加起来占了一半还多，而那一半跟这个页面的业务毫无关系，只是入口文件顺手引了个工具集。这种结论靠肉眼翻日志翻不出来，只有把模块按块重新聚合才能看见。

重复拷贝那段是我们真的查出过东西：一个基础库被两个上层依赖各自内嵌了一份，两份都进了包。判据要放准确一点，同一份清单里同一个包出现多条嵌套路径，才叫重复；只是文件多、路径深不算是问题。另外有笔账得说清楚，清单里的字节是未压缩的原始数，对传输预算时心里得带上一层压缩比，否则你会觉得某个包怎么比线上大三倍，那是正常的。

命令行三板斧：分目录、揪大文件、掐构建耗时

在写任何分析脚本之前，我更推荐先用几条最笨的命令扫一遍输出目录，两分钟就能建立整体印象，不需要任何依赖。

du -sh dist/* 看的是钱都花在哪一间：我们的经验是如果图片或者字体目录跟 JS 目录一个量级，那优化重点压根就不在代码上。ls -lhS 按大小倒序，最大的文件直接顶到第一行。find 那条带 -size +200k 的，我把它当成产物体检的固定动作，超过阈值就逐个点开看，多数时候能揪出没压过的切图和误入的生产包。最后那条找 .map 的，是我专门留给一类事故的准备动作，后面单独讲。

构建耗时也是量的一部分。time 掐一下，我们那个项目从一分钟出头慢慢爬到三分多钟，改一轮样式等两轮，一天下来打断的思路比省下的时间多。我的处理是区分两类构建：日常开发只要产物能跑就别做任何压缩和指纹计算，发布前那一轮才走完整流程。靠的是把两条命令分开命名，让”快”和”该上线了”是两个不同的动作。

用户下载的字节不是源文件字节，中间隔着压缩

源文件体积是磁盘账，传输体积才是用户账。文本类的 JS 和 CSS 压缩比很高，一份 800 KB 的包 gzip 之后常见落在 190 KB 上下，这个反差足以改变优化优先级：先动那个未压缩时看着不大、压缩后依然不小的东西。

把这条循环存成一个小脚本，跟构建放一起，每次发布顺手输出两列数字。源文件和压缩后各自排一次序，经常会出现名次互换：某个包源文件最大，压缩后反倒退到第三，因为里面有大段可以被压扁的字符串表；某个 CSS 源文件平平，压完还是那么厚，说明里面确实全是没法再挤的选择器。

想量得更贴近真实，就从线上直接测下载字节。

这条比本地算出来的数字多算了传输编码和响应头的账，也顺手验证了服务端有没有真的开压缩：同一份文件，不带 Accept-Encoding 跑一次，带上了再跑一次，两个数字一样就说明压缩没生效，这比看配置文件直观。要提醒的是有两类文件压缩基本没收益：已经压过的图片，还有字体里已经压过的那部分，它们的源文件字节就是用户下载的字节。所以看到图片目录把总量撑起来的时候，指望传输层救场是不行的，得回到文件本身。至于那个据说能省更多字节的新编码算法，2016 年 3 月还只停留在草案讨论里，浏览器默认用的仍是 gzip，这条账暂时只能按 gzip 算。

瀑布图要会读：清单里有的，用户不一定下载

dist 是全量构建产物，某一次首屏真正下载的只是其中一部分，所以本地量完还得回浏览器对一遍账。这一步的价值在于把”产物很大”和”用户等很久”这两件事拆开看，它们高度相关但不是同一件事。

我的固定动作有三下。第一下勾选禁用缓存再刷新，否则 Size 列里混着一堆来自本地缓存的零，你会误以为什么都没下载。第二下按开始时间排序看瀑布，找那个”最晚开始、又最厚”的文件，它通常就是加载时间的天花板——首屏总时间往往不是被一堆小文件拖长的，而是被一个又大又晚到的文件顶住的。第三下把总时间用页面性能计时接口取一次，别用肉眼数秒表，人眼在六秒和八秒上分不细。

再补一个当年的排障心智模型：还是老版 HTTP 在跑，浏览器给单个域名的并发连接就那么六七条，请求一多，后面的就得排队。所以在瀑布图里看到某个文件开始得很晚，先别怪网络，看看它前面是不是排了十几个小请求。这也是为什么优化时既要看单个文件多厚，也要看首屏这一屏一共有几个文件，两个数得一起压，只压一头都会把另一头的成本顶上去。图片这类资源可以摊到别的域名上错开队列，但摊得太碎，域名解析和握手的账又会爬回来，我们的做法是资源域名控制在两三个，不为省一两条连接再拆。

慢网复现也用得上这个面板：切成较低的传输档位再走一遍，本地千兆下毫无感觉的项目，换个档位经常立刻看见谁最慢。这一步不产出优化，它只是让你确认自己针对的不是猜出来的瓶颈。

常见的五个大头，逐个给判据

体积异常不是玄学，来源翻来覆去就那么几类。下面每一条我都给了”怎么确认是它”的判据，判据比结论有用。

整包引入一个只提供两三个函数的库

判据是上面那个排序脚本：某个第三方模块在清单里排得很靠前，而你在全项目搜它的引用，只有零星两三处。CommonJS 的引用等于整份拽进来，那个年代最典型的例子就是日期库，为了格式化一个时间把一堆语言的规则数据一起打包。我们的处理很笨：要么把入口收窄只引用需要的部分，要么就换个小一级的库，实在不行自己拷贝那两三个函数进项目并写明来源和版本。

同一个依赖被装了两份

前面提过用依赖树命令排查，这里只补一条产物侧判据：在 stats.json 的模块清单里，同一个库的名字出现两次、路径不一样，就是重复装包了。2016 年那套扁平化的安装目录也躲不过这件事，两个直接依赖各自要不同的主版本，谁也提不上去，就只能各留一份。确认之后要么统一版本，要么承认这笔双份体积。

图片字体原样扔进 dist

判据是那条按大小倒序的 find。切图产物经常 oversized：设计给的是大尺寸的稿子，导出时按最大规格出，前端拿到就直接用，谁也没停下来想这一张在实际渲染位置根本用不到那么多像素。流程和标注怎么配合另有一篇讲，本文只留一句判据：图片体积要跟它的实际显示尺寸和压缩率一起看，脱离尺寸谈画质都是空话。

sourcemap 误发布到线上

这一条我单独展开，因为它是当年最容易犯的错，而且犯了还不容易被发现。

dist 里出现后缀为 .map 的文件，通常是两个原因叠的：一是发布用的配置从开发配置复制过来，那个生成映射的选项忘了关；二是用了处理映射的加载器，即便没主动开选项，它也会把源文件里已有的映射注释一起搬过来。这类文件的个头非常可观，我们那次一个入口的映射就有 4 MB 多，四个加起来接近 7 MB，把发布目录撑到没法看。

它坏在两个地方。第一是磁盘和部署账，发布包变大、同步变慢。更要命的是第二点：压缩后的 JS 末尾会留一行指向映射文件的注释，浏览器开发者工具一打开就会去下载它。也就是说用户不一定受害，但任何一个在线上按了 F12 的人，都得替你把那几 MB 拉一遍，我同事就是在客户现场演示时撞上这个，页面卡得没法解释。顺带还有一个泄露问题，映射里带着源码结构，对外开放的项目不该让它被公开访问。我后来把这件事做成了硬检查，只留映射在服务器上单独存放，线上目录里一个 .map 都不许有，判据就是那条 find。

mock 数据、测试桩、调试日志一起进了生产包

判据有两条。一条是在产物目录里搜关键字，.map 之外还值得搜一遍调试输出和 mock 相关的标识。

另一条是回到源码看入口：如果开发用的假数据是无条件引用的，那它一定在依赖图上，图上有的就没有不被打进来的道理。当时的办法是加个开关。

开关写进条件语句后，还要靠压缩那一步把死代码带走，2016 年初这些工具各管各的，条件写得不够直白，它就未必删得干净。稳妥做法还是让生产入口压根不引用 mock 文件，开关只是第二道保险。

优化手段按收益排一遍，每条都说降了多少

下面这个顺序是我们按投入产出比的直观感受排的，数字都来自同一个后台项目，量级可信但别当成通用基准。

第一档是外置公共依赖与抽公共块。jQuery、几个基础库这类东西从业务包里挪出去，配上线上统一的公共块，首屏 JS 从 1.2 MB 降到 780 KB，而且以后发版用户不必重下这一部分。具体拆法前面聊过，这里不重复。

第二档是异步块只把非首屏那部分延后。编辑器、图表、导出这三类挂到交互之后再取，主块再降 260 KB 左右，代价是首屏之后的第一次点击会多等一个请求。

第三档是图片降尺寸与格式选择。图标类继续用 PNG，照片和纯装饰底图换 JPEG 并把质量参数往下压，那张被引用两次的 1.8 MB 底图压到 240 KB，全站图片目录从 2.9 MB 降到 1.1 MB。这一步完全不依赖构建工具，收益却比多数代码层面的手段大。压缩率的判断我后来只留一条经验：肉眼在正常观看距离看不出差别为止，再往下压就是自嗨。那个宣传压缩率更高的新格式，2016 年的兼容清单里还有大半引擎不认，要么准备回退路径，要么先别把它算进收益。

顺带把小图标的两笔账记在这儿，原理留给雪碧图那篇专文，本文只留判据：单个几十 KB 以下的图标，内联进样式的代价是字节数大约涨三成、但省掉一次请求；数量多了以后拼成一张，省请求的同时牺牲缓存粒度。定阈值别拍脑袋，就按”这个图标会不会单独改版”来分——会单独改版的不要拼进大图，改版必然连带的才值得拼。

第四档是 CSS 合并与去掉没用到的规则。把已经不在模板里出现的类名对应规则删掉，再合并重复声明，一个 460 KB 的样式表降到 210 KB。2016 年还没有能把首屏关键样式自动抽出来的成熟工具，我们靠手工维护一个小骨架样式文件，先让首屏那点内容能渲染，剩下的大表延后。

第五档是 JS 压缩与去掉调试输出。压缩插件的写法前面给过，这里只补一条选项：变量名压短之外，把断点残留语句和 console 调用一并丢掉。这一步对我们那个包从 780 KB 降到 520 KB，其中大半是删掉未引用函数和压平结构带来的。

最后一档是字体子集化，单独讲。

字体子集化：当年能走多远，风险在哪

中文项目里字体常常是隐形大头，一套正文用的字体文件光骨架就要 800 KB 到 1 MB 多，而页面上实际出现的汉字可能不到一千个。把”页面真正用到的字符集”喂给工具做子集，是 2016 年已经能看到、但只有少数人在用的路子，当时刚出来那类会扫描 HTML 再裁剪字体的工具，我见到同事试着跑，效果确实诱人：一个 1.1 MB 的字体裁完变成 90 KB 上下。

风险也很实在，我把它们按严重程度排：

  • 动态渲染的文字不在扫描结果里。列表数据、用户名、后端拼出来的文案，工具抓取的时候不知道，用户浏览器里没有这个字的字形，只能退回系统字体，看起来就像样式崩了。
  • 图标字体不属于子集化范围。那一类靠私有码位映射，按可见字符集裁剪等于把图标裁没了。
  • 页面改版后字符集变了，旧子集不会自动跟着变，得把它当构建产物重新生成，而不是手工拷一份放着。

我们的处理是：子集只用在确实固定的标题和品牌字样上，正文一律系统字体；生成子集的那一步进构建流程，字符集来源包括后台导出的样例文案；上线先按小流量灰度几天，专门看有没有字形缺失。那会儿的做法远谈不上成熟，我不敢把它推荐成通用方案，只能记一句”确实在个别场景省下了很大一块”。

产物要配合缓存出指纹，压缩要在服务端开对

优化后的字节能不能真的省下来，取决于用户是不是每次都要重新拿。缓存刷新的策略另有一篇，这里只讲产物侧要配合的两件事：文件名带内容指纹，以及文本类资源在服务端开压缩。

那时候做不了的事：摇树

这一节写”我们当时指望不上什么”，免得把后面的努力当成理所当然。2016 年 3 月还谈不上有可用的摇树。webpack 2 那时只是个 beta 版本，没上生产；import 与 export 这种静态模块写法在浏览器和工具链里都还没有统一落地；压缩工具面对 CommonJS 的动态引用也不敢替你下结论，路径能拼、引用能藏在条件里，删错了就是线上白屏。所以那时想减体积只有三条笨路：不引，换成小库，或者自己按需拷贝。前面所有关于”整包引入”的判据，本质都是在补这个洞，只不过用的是人而不是工具。

把体积当成回归项，而不是一次一次的突击

发布前那张产物检查清单，逐项打勾

门槛脚本管得住单文件，管不住整体现状，所以我们另外留了一张短清单，发布流程里逐项过。它不长，但每一项都对应过一次真实事故。

  • 输出目录里搜不到映射文件后缀，一行配置检查加一次文件搜索双保险。
  • 按大小倒序过一眼，没有前二十名里认不出来的文件；认不出来就得说清它是谁引入的。
  • 图片目录总量与上一版对比，涨了要能解释为什么涨。
  • 产物目录里搜一遍调试输出关键字，结果为空。
  • 字体目录要么为空、要么每个文件都在预期清单里，没有顺手拷进来的完整字库。
  • 需要强缓存的块，文件名都带指纹；带不了指纹的，单独说明原因。
  • 服务端压缩已生效：抽一个 JS 文件用两条命令对比下载字节，数字应当明显不同。
  • 模块统计文件随版本存档，出问题时能对回来是谁什么时候把体积做上去的。

这张表前半段后来都写进了脚本，剩下手工的就两项：认不出来的文件，和解释不清的涨幅。它的用处不是防住事故，是把”看体积”从某个人的自觉变成流程里的公共动作，新人来了照着勾就行。

一次复盘：首屏 3 MB 多的真因不是框架

回到开头那个项目。当时群里的第一反应是”框架太重了，要不要换”，我坚持先量化，结果三条真因跟框架一点关系都没有。

排查顺序是我现在会重复的顺序：先看文件清单，再看 network 瀑布，最后才回头翻构建配置。文件清单告诉你哪些字节存在，瀑布图告诉你用户实际下载了哪些，构建配置解释它们为什么在那儿。跳着看只会吵起来。

这个项目查出来是三件事叠在一起。第一件是 sourcemap 没关，dist 里躺着 6.8 MB 的映射文件，那行指向映射的注释还在线上被开发者工具去下载；关掉之后发布包瘦了一半多。第二件是一张没压过的底图被样式表引用了两处，源文件 1.8 MB，压缩到 240 KB；这里要多说一句，同一个 URL 引用两次只会产生一次下载，所以它的问题不是重复传输，而是这一张本身太大，把它算成”重复引用导致的双倍体积”是错误结论，这也是为什么每一步都得回看瀑布图核对。第三件是某个 UI 库整包引入，实际只用其中日期选择和两个表单控件，按需拷贝出来之后少了 400 KB 左右。

三件事做完，首屏资源从 3.1 MB 降到 1.2 MB，按 gzip 算的实际下载从 1.1 MB 降到 400 KB 左右，办公网实测加载时间从六秒多回到两秒半。没有一个数字是夸张的十倍改善，但运营不再在群里说话了。

判据速查

症状 先量什么 判据
单个 JS 文件特别大 模块排序清单 第三方模块霸占前排，全项目引用只有两三处
图片字体目录撑爆 dist 按大小倒序的文件列表 超出实际显示尺寸、没压过
dist 里出现成堆映射文件 找 .map 后缀 发布配置里生成映射的选项没关
压缩后依然很厚 本地算压缩字节 内容本身不可压，或者总量确实太多
版本间体积悄悄上涨 门槛脚本对比 新依赖整包进了主入口

小结

回头看，我把那段时间的动作收敛成四步。度量清单是第一步，块级报表、模块排序加命令行扫目录，先把”多大、谁大”变成数字；大头定位是第二步，五个来源逐个给判据，别凭感觉猜；按收益排序动手是第三步，先做图片这种不动代码就能降一档的事，再做外置依赖与压缩，最后才碰字体子集化这类有风险的；设门槛防回归是第四步，把体积当成回归项交给脚本看住。

这套东西没有一处依赖当时的新工具，全是配置项、shell 命令和一个小 node 脚本。它真正解决的问题也不是字节本身，而是让”要不要优化、优化到什么程度、有没有变回去”这三个问题都有数字可答。先量化再动手，这句话我在后来很多个项目里都靠它止住了争吵。
