前端Mock数据与联调方案

年初一个项目，后端接口要三周后才可用，前端靠十几行手写的假数组把页面铺满。真接口来的那天，我连着改了两天字段名，测试第二天提了七个 bug，全是假数据把边界掩盖掉造成的。那时我才明白，问题不在于有没有假数据，而在于它以什么姿势插进代码里。结论是 mock 要当成架构问题处理，插入点选错了，后面所有纪律都补不回来。

先把四种诉求拆开

我们口头都说”要 mock”，拆开是四件不同的事，混着谈就会拿一种方案硬吃四种需求。

一是前端等接口，本质是并行开发，要的只是一份能渲染、改完即时生效的样本。二是接口不稳定、异常分支难复现：偶发的超时、半截 JSON、500、401 在联调环境怎么点都点不出来，要的是稳定重放某种失败。三是边界数据拿不到：空列表、五百条、权限为空、三十二字符加四个生僻字的昵称，真实库里恰好没有，页面崩的往往是这些，要按维度枚举着造。四是验证性能：长列表渲染耗时、一次回两万条会不会僵住，要量级可调，且必须能在真浏览器里跑。

四件事对应四个层次：并行开发放数据访问层，异常重放放本地假服务，边界枚举靠契约生成样本，性能验证只能在真链路做。

mock 的四个插入点与各自代价

同一个返回假数据的动作可以插在四个位置：越靠上改动越小，越靠近真实链路越可信。

一、数据访问层注入

把每个接口调用收进一个函数，比如 fetchUserList(params, callback)，页面只认这个名字、不认它背后是谁，测试与联调各注入一份实现，生产构建只留真实现。这是最干净的一层，代价是分层纪律：有人在组件里直接写请求调用，这层就被绕过、mock 跟着漏，所以我们把”页面代码不许直接发请求”写进评审检查项。

二、库级拦截

jQuery 那一代最顺手：给 $.ajax 挂 dataFilter，在响应进 success 之前动手脚；或用 mockjax 按 URL 模式注册假响应；单测里用 sinon.js 1.x 的 fake XHR，它能吞掉请求，顺便断言发过几次、参数是什么。Angular 1.x 的对应做法是 $httpBackend，靠依赖注入在测试里换掉。好处是不用起真服务，页面开起来就能跑。代价是拦截层不是真浏览器网络：没有跨域行为、状态码处理对不上、超时与中断语义不一致、预检不会出现。这一层验过的东西到真链路全要重验，所以我只把它留给单测。

三、本地假服务

用 Node 起一个进程按路径返回固定 JSON。最省事的是把假数据写成文件、用 express.static 挂到某个前缀下，请求 user/list 就读 mock/user/list.json；要延迟、随机状态码、分页切片就再写十几行路由。这一层最值钱的地方是它确实是个真服务：跨域、状态码、慢响应、大响应体都是真的，性能验证只能走这里。代价是多维护一个进程、要处理端口与跨域。

四、代理层改写

开发代理把某个路径前缀指到本地假服务，其余照走测试环境，页面与接口在浏览器看来同源。线上问题复现交给抓包工具的本地映射与远端映射，机制在《Fiddler 与 Charles 抓包实践》里讲过，不重复。代价是它只存在于你这台机器：规则没写进仓库，同事既不复制你的成功也不复制你的失败。所以代理规则算调试手段，只有开发代理的转发配置必须进仓库。

数据契约先行

接口还没定就急着造假数据，是后面所有返工的源头。我们改成先出一份字段表：字段名、类型、能不能为空、枚举取值、单位、分页口径，一份表对应一个接口。这张表同时是三样东西——后端的实现依据、前端的断言依据、mock 的生成依据。它不进任何平台，放在仓库里跟代码一起走版本，docs/api/ 下一个接口一个文件。

规则三条。谁改：前后端都能提，但只能改同一份文件，评审通过才算数。怎么评审：写这个接口的人和用这个接口的人一起，五分钟看四点——可空性、空值怎么表示、时间格式、分页字段名。谁生成：假数据由这张表推导，不是前端照着想象手写。

人手写假数据会自动写出自洽的世界：数组永远有元素、字段永远存在。契约表逼你把”这个字段可能为空”显式写一次，写出来了，样本里就得真有一条为空。

造假数据的纪律

随机数据看着丰富，实际最难用：今天正常、明天报错，分不清是代码还是数据问题。我的纪律是能固定就固定：默认走固定种子，甚至直接把固定样本提交进仓库，每次跑出来的字节都一样；随机只留给压测边界，比如要五千条列表。

维度上按这几类各留一份样本，缺一类就算 mock 没做完：分页（首页、末页、总数为零、总数恰好被整除）、排序（空值参与排序、返回顺序与请求顺序不一致）、时间戳（跨时区、闰年二月、1970-01-01）、空值（null、空字符串、空数组、字段缺失，这四种在页面上是四种表现）、超长（一千字不带换行的备注）、特殊字符（尖括号、引号、反斜杠）、多语言（简中、繁中、英文、长单词的德文，用来撑破布局）。

异常态比正常态更常被漏。我固定留五个异常样本：401 未登录、403 无权限、500 服务错误、挂到二十秒再断掉的超时、正文只发一半就断开的半截 JSON。最后那个最有用：当时的请求封装里，解析异常常常根本没被抛给回调。

开关设计：三层判据

假数据怎么进代码不是难点，怎么保证它出不去才是。我用三层判据，一层比一层宽松，越宽松越危险。

最安全的是构建期替换：开关做成构建时常量，生产构建时它是字面量 false，整段条件被压缩器丢掉，假数据不进产物。验收判据就一条——打开浏览器看源码，搜不到 mock 目录里的任何字符串。中间一层是环境加白名单：host 在开发域名列表里，接口前缀在白名单里，两个条件是”与”。最危险的是运行期 URL 参数，给测试同学一个不改代码的临时开关，它必须校验来源域名、只在开发 host 上认，否则一条带参数的链接就能把假数据带到线上。

还要注意开关状态不能写进 cookie 或本地存储：带过一次参数之后，后续页面全会命中 mock，我们把它限制在当前页面，刷新即失效。白名单与域名判据也不许只写在 mock 模块内部——模块一旦被打包进产物，线上那个函数依然存在，只等人给它一个参数。运行期开关上线的事故我见过两次，成因都是这一个，所以硬规矩是构建期必须删掉一大半。

跨域与登录态：mock 最真实的麻烦

假服务和页面不同端口就是跨域。简单请求可以靠响应里的 Access-Control-Allow-Origin 放行；一旦要带 Cookie，通配就不能用了，必须回具体来源并把允许凭据那项置为真，带自定义头还要多回一次预检。假服务最容易漏掉这几行头，症状只是控制台一句模糊报错。

登录态更麻烦：假登录 Cookie 的域是开发域，真接口在另一个域，页面就带着假登录态去调真接口，服务端一律回未登录。当时只有两种绕法。一是开发代理转发，同源之后 Cookie 没有跨域问题，这是我推荐的默认做法；二是改本机 hosts 把测试域名指到 127.0.0.1，让假服务监听那个域名的 80 端口，好处是域完全一致、连 Cookie 的域属性都不用改，坏处是只影响你这台机器。

遗留接口里还有 JSONP。它靠回调函数名包正文，假服务得回一段函数调用文本：回调名从查询参数里原样取出拼进去，响应类型写成 JavaScript，否则页面永远等不到回调。顺便把边界说清：fetch 的规范当时已经有了，但浏览器支持不齐、还要挂 polyfill，我们线上仍以 XHR 封装为主，Promise 同样要补 polyfill，所以 mock 断言全写在 XHR 那一层。

与本地开发服务的接线

mock 能不能长期活下去，取决于改一条数据要付多少代价。目录按接口前缀分文件：mock/user/list.json 对应 user/list，映射规则只有一条，路径直接拼上去。约定越笨越好，接手的人不用问假数据在哪。异常样本单独放 mock/_error/，下划线开头，跟真接口样本一眼分开。

免重启这件事价值最大。假服务每次请求都从磁盘重读文件，保存就能刷新看效果；若启动时一次性读进内存，人会攒着改，验证质量立刻掉。启动命令也要写进脚本，否则最后没人起。

联调阶段的动作

联调不是把开关一关了之，它有具体动作。字段对不上的定位顺序：先回契约表核名字与类型，对不上就是契约漂移，走评审改表；表对得上而值不对，再看序列化差异。当期最常见四类：时间是字符串还是毫秒数、带不带时区；布尔用 0/1 还是真 true/false；命名一边下划线一边驼峰；数字 ID 被发成字符串导致比较永远不相等。前两类靠归一化层吃掉，第三类必须由契约表定死一种，别指望前端到处兼容。

第二个动作是让 mock 与真接口跑同一套断言，只写三条：列表长度等于分页大小的期望、必填字段存在且类型对、分页边界不许多也不缺。两边都过，切换才有依据；只在真接口上跑，出问题时分不清是数据错还是断言错。

第三个动作是逐个记录从假到真：接口名、最后一次 mock 通过的时间、切真时间、切真后的第一个问题。灰度节奏是每天切三五个，切完当天要有人在测试环境点一遍；不要一次全切，全切之后没人能回答问题是哪个接口带来的。

两次复盘：mock 全绿，真接口一上线就炸

第一次是空数组。mock 里列表永远给 []，空列表分支走的是”长度为零显示占位文案”。真接口在无数据时返回 null，那句取长度的代码直接抛错，整块区域白掉。修法不是补一层判空，而是给契约表加空值表示法条款：数组为空发 [] 还是 null、字符串为空发空串还是不带这个字段，逐接口写清楚，写不清的就现场抓一份真响应来定。

第二次是分页字段。前端自己习惯 page/size，mock 照抄了这个命名，后端那套是 offset/limit。联调第一天列表能出数据，翻页却全部回到第一页，因为后端不认识 page，取了默认值。这个最难发现，它不报错，只是行为悄悄不对。修法两条：mock 生成器必须从后端给出的示例响应反推形状，而不是前端手写；联调第一条规则改成先看一份真响应再改代码。

两次的共同点：mock 全绿从来不代表通过，它只代表我脑子里的假设自洽。mock 的价值恰恰是把假设写在纸上，逼后端来推翻它。

选哪个插入点

诉求 层次 是否进生产 谁维护 失效风险
前端等接口、并行开发 数据访问层注入 构建期剔除 前端 有人绕过访问层直接发请求
断言请求次数与参数 库级拦截 不进 前端 与真浏览器行为不一致
异常分支稳定重放 本地假服务 不进 前后端共同 假服务与真接口漂移
边界与多语言样本 契约生成器加假服务 不进 前端 样本被手改
大列表性能验证 本地假服务走真链路 不进 前端 只有本机端口
线上问题临时复现 代理层改写 无关 个人 规则不进仓库

顺序上我的建议是：先有契约表，再做数据访问层，再补本地假服务，库级拦截只留在单测里，代理改写只当调试手段。
