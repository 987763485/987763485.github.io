前端页面静态化方案

前一年冬天，我们组接了一个跨年活动页。页面本身不复杂：一张 banner、一个商品列表、几段规则文案。但两件事把我们磨得没脾气。一是协作。那个页面挂在后端一个 Java 应用里渲染，运营想改一行文案，得提需求、等后端改模板、测试、重启服务，前后折腾半天。二是抗压。活动开始前十分钟，预告页被流量冲了一下，接口超时，整页白屏，运营在群里直接拉了急诊。

后来把这一页重新做了一遍，用的办法现在回头看仍然觉得解气：把页面做成生成好的静态文件。一个构建动作同时解决协作和抗压：改文案只动一个数据文件，走一次一键发布；抗压的部分变成 nginx 直接吐出的几个 HTML 文件，怎么刷都刷不挂。

这篇按入门的视角把整件事讲一遍：静态化到底指什么、怎么生成、怎么部署、哪些页面适合哪些不适合、中间埋着哪些坑。产物怎么瘦、版本号与缓存刷新各有专文，这里只带到相关的那一句。

先把”静态化”这个词的误会排掉

重要的定义先说清楚：本文讲的静态化，指的是最终对外提供的是已经生成好的 HTML 文件。浏览器请求这个地址时，服务端不再执行任何生成逻辑——不查库、不渲染模板，直接从磁盘把文件读出来还回去。判断标准就这一条：这次请求有没有触发生成。

顺带排掉两个误会。一个是以为静态化等于”页面死了、没交互了”。完全不是。HTML 是静态的，但页面里加载的 JS 和 CSS 照常工作，点击、弹层、表单提交都不受影响，静态的只是文档本身，不是页面的行为。另一个是以为”内容不变就行”——每次请求现算一遍再返回相同内容，那不算静态化，算重复劳动。

定义清楚了，再往下看路线。同样是”给一个静态文件”，生成的时机可以落在三个不同的地方。

生成动作发生在构建期、发布时，还是运行时

第一种是构建期生成：发布流程里用一个 node 脚本把数据喂给模板，一次性产出 HTML，交付物就是现成的文件，线上服务器只见文件，不知道模板长什么样。

第二种是发布或更新时由服务端渲染一份快照：内容还是服务端应用在维护，但每发布一篇文章、每次商品变更，服务端把它渲染一次，结果写成 HTML 落到磁盘或者推到 CDN，之后访问都读文件，直到下次内容变更再覆盖一份。我们那会儿拿 Hexo 写博客就是这条线的，先生成好整个目录再部署。

第三种是运行时缓存：第一次请求照常现算，顺手把响应结果写成缓存文件，后续请求直接命中缓存，到失效时间或者被主动清掉之后，下一个进来的请求再重算一次。

三者的差别落在两个维度上：源站压力和失效难度。构建期生成把压力全部挪出生产，源站零负担，但每次变更都要走一遍构建发布，失效粒度是整批。发布时快照把生成时机和访问时机解耦，源站只在内容变化时算一次，失效可以精确到单个页面，可控性好。运行时缓存最省事、内容时效最好，但它留了个洞：缓存失效的那一刻，撞进来的请求要现场等生成，整点集中过期遇上流量高峰，源站照样被打穿。所以我们当年只敢把它用在访问量不大的辅助页面，高峰场景不靠它。

本文主干讲第一种：构建期生成。活动页这类场景正好落在它的适用面上。

构建期生成：一个模板引擎加一个 node 脚本

这件事不需要框架。我们那会儿的做法就是模板引擎加一个 node 脚本，引擎用 Handlebars、doT、EJS 都行，活儿是一样的：模板加数据，换回 HTML。模板把公共头尾拆出来，页面模板只写自己的正文。

生成用的数据从哪来

常见来源两种：调接口把列表全量拉回来，或者直接从库里导一份 JSON。用哪种都行，但要紧的是把”拉数据”这一步在构建里做容错。

最容易发生的事故长这样：拉取接口超时，返回了半截空数据，脚本不知情，照样把空数据渲染出去，产物生成成功、发布成功，等人打开页面才发现商品列表是空的。所以拉完数据要先过一道校验，页数对不对、每个页面的列表长度够不够，任何一条不满足就用非零退出码结束，拒绝生成。

另一个要保护的是上一次的产物。我们的做法是脚本先往一个临时目录写，全部生成完、校验通过后，再删掉旧输出目录、把临时目录整体挪过去。中途失败时，线上躺着的还是上一版完整文件，而不是半新半空的残局。删目录用 rimraf 这类库抹平跨平台差异就行。

全量重生成还是增量重写

页面数量少的时候别犹豫，全量。构建期生成的全部逻辑都建立在”一次算全套”上，增量是规模逼出来的话题，判断依据就两个数：生成一次要花多久、发布频率多高。

我们的活动页几百个以内时，全量生成是秒级的事情，做增量纯属负收益。等页面数上千、全量跑到分钟级，而每次变更实际只影响其中几个页面，才值得让生成器记住上次的数据快照，对比出受影响的页面清单，只对这几个跑模板渲染和写文件。还有个更划算的折中：生成保持全量，部署只传变化的那几个文件，交给 rsync 去比对差异，经常就解决了一大半痛点。

部署：nginx 直接发文件，但兜底路径要留着

产物就位之后，部署简单到不好意思写：目录交给 nginx。

请求命中文件就直接返回，命中不了才转发给兜底服务。命不中时的第一反应是回 404，但高流量场景我更推荐上面这种第二条路：文件缺失时交给一个动态渲染服务现场算。我们当时确实在 6001 端口养着一个 node 应用，只负责把没生成到文件的页面现渲染。代价是走这条路的那部分请求会变慢，但慢总比白屏强，文件缺失本身是异常，正常流量走不到这里。静态化不等于放弃兜底，这条动态路径就是保险丝。

缓存头的部分只说必要的一句：文件名里带了版本号的产物可以放心设很长的过期时间，没带版本号的 HTML 就别设太长；版本号怎么打、缓存怎么主动失效，交给专文讲。

哪些页面适合静态化，哪些不适合

入门阶段最值得练的是判断力，两个自查问题很好用。

第一个问题：同一个地址，对不同用户返回的内容是否必须不同？不需要不同——活动页对登录和未登录用户是同一份——那就基本可静态化；必须不同，比如”我的订单”，这页的 HTML 根本没法提前存在，只能静态化外壳或者放弃。第二个问题：内容最晚多久必须变？”改完文案半天内生效”能满足，”保存那一瞬间就生效”满足不了。对时效要求到毫秒级的，发布周期这个环节就卡死了。

再补两个加分项：访问是否集中，流量越陡，静态文件的抗压价值越大；有没有 SEO 要求，搜索引擎抓纯 HTML 永远是最省事的。反过来，强个性化的页面、要拿到登录态才能确定内容长度的页面、每次请求都必须展示实时状态的页面，适合度低。归成一句：页面越不依赖”你是谁”和”哪一秒”，静态化适合度越高。

页面上”每人不同”的那块，怎么留

新人最容易卡住的问题：活动页里有块”我的优惠券余量”，每人不同，是不是整页就得退回动态？不用。

做法是在模板里给这类区块留一个空容器，把接口地址标在属性上。

静态文件里只有容器外壳，页面加载后 JS 读 data-api 发起请求，把结果填进去。首屏这一小块会空一瞬，但页面其余部分不受它牵连。

配套的纪律是把哪些区块必须动态直接标注在模板上，写明各自的接口和加载失败时展示什么。不做标注，动态块会在模板里悄悄繁殖，最后整页只剩一个壳是静态的、其余全靠加载后填，那样的静态化做了跟没做一样。我们的规矩是一个页面里动态块不超过两三块，能收回静态内容的坚决收回来。

踩过的四个坑

一是改动成本。静态化之后运营改一行文案要走一次发布，自助性反而变差了。对策是把发布做成一个动作：脚本串起拉数据、生成、部署，两分钟跑完，数据文件本身让运营可以直接编辑、改动提交到 git 里留痕。门槛降到这个程度，协作问题才算真解决，否则只是把被人催的对象从后端换成了你自己。

二是时间被固化进文件。我们一度把”本页面更新于某时刻”直接写进模板，后来发现那行字永远不变——模板取的是生成时刻不是访问时刻，固化下来的就是生成时间。凡是当前时间、随机推荐这类内容，不能直接写在模板里，要么加载后用 JS 动态填，要么干脆别写。

三是环境互相污染。有一次测试环境生成的产物里被打进了带测试域名的绝对链接，发布流程顺路推到线上后，页面有几位资源请求打到了测试环境。从那以后页面内链接一律相对路径，实在绕不开的绝对域名收进模板变量，生成时按环境配置注入，模板本身一个字的环境信息都不写死。

四是网络抖动传导到产物。某次拉取接口自己的重试把超时吞了，某个字段整批为空，生成却”成功”了。后来除了前面说的数量校验，又加了一道抽样检查：生成完在产物 HTML 里 grep 几个必填的词，找不到就让构建失败。听着笨，但它是十分钟就能写出来的最后一道防线。

一次复盘：页面没挂，接口挂了

夏天那次活动，上线前压测整条链路都过了。正式开抢时活动页稳稳当当，一次白屏都没有；挂的是页面里那个必须动态的库存查询接口，高峰的请求量是日常的几十倍，我们只按日常的十倍准备了容量。

复盘结论写得很直白：静态化的收益边界，止于它覆盖的那部分内容。那份 HTML 被覆盖了，确实刷不挂；但被留在覆盖范围之外的动态区块才是真瓶颈，静态化一点没帮到它。后来的办法是给库存接口自己加缓存层、把刷新频率放宽，那是另一个故事。但这个教训值得记：做完静态化，别把整个页面当成已解决，要沿着没覆盖的角落逐个再看一遍。

收尾

静态化不是什么大架构，它是一笔交换：用”内容变更要过一次发布”的时效，换”访问绝不触发生成”的确定性。活动页、列表页、落地页这类页面几乎总是值得换。整套东西的入门门槛很低：一个模板引擎、几十行脚本、一段 nginx 配置，当天就能跑通。跑通之后把力气花在两头，前端那头保证数据拉取有容错，后端那头保证兜底路径还活着。
