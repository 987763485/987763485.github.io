Git 分支策略：Git Flow 与 GitHub Flow

两套发布节奏撞在同一套规矩上

我们组当时只有 master 和 dev 两条长期分支，跟绝大多数团队一样。真正难受的是上线前那几天：dev 上攒了两周的改动要合进 master，合完发现构建不过，回 dev 改，改完再合，一次合并来回折腾两三天。我当时以为分支模型天生就这么疼。后来同时接手两个项目才看明白，同一套规矩套在两种发布节奏上，两边都难受。一个是交付型老项目，客户装固定版本，一年出两三个补丁包，dev 那条线早就没人合了，纯属摆设；另一个是每周发好几版的线上业务，冻结期只有一两天，走一遍完整仪式反而把发布拖慢。分支策略不是选”先进”还是”保守”，它跟的是发布节奏：多久发一版、要不要同时维护几个老版本、上线窗口是自己定还是别人定。这三个问题答完，该用哪套基本就定了。分支模型的机制差异和各分支职责在讲协作规范那篇里已经列过，本篇不复述那张表，只讲命令层面怎么落地、两种模型的成本差在哪、怎么从旧状态迁过去。

先把两个名字讲清楚是什么

Git Flow 这个名字来自 Vincent Driessen 在 2010 年写的那篇讲分支模型的页面，页面描述 master、develop 加 feature、release、hotfix、support 几类分支的分工与流转方向。它配套的命令扩展也叫 git-flow，两者常被混着说：一个是约定，一个是实现约定的脚本。GitHub Flow 是 GitHub 早年发在帮助页上的一套简化流程，主张只有一条主干加一堆活得很短的分支，改动通过 Pull Request 评审合入主干，合并之后尽快部署。

要先强调：这两套都不是 Git 的内置功能。Git 对分支名没有任何意见，它只维护若干指向提交的引用；有没有 develop、前缀叫什么，对底层对象毫无区别。所以两者都是约定，约定只能靠人和工具执行。到 2016 年两套都流传了好几年，也被吐槽了好几年：嫌 Git Flow 繁琐的多是发布频繁的团队，嫌 GitHub Flow 不够用的多做版本交付，两边抱怨的是同一件事——流程成本要摊到发布节奏上才算得清。

Git Flow 的命令面与每条命令的副作用

它在本地做三件事：确认或创建 develop（起点一般是 master 的第一个提交），把 HEAD 切到 develop，再把两个分支名和各类分支前缀写进 .git/config 里一段 gitflow 配置。第三件事最要紧也最易被忽略：这个配置文件是本地私有的，推不到远端，别人 clone 也拿不到，所以每个人的 git flow 都是各自独立配置的。这一点后面会变成一个坑。

start 从 develop 切出 feature/order-list-export 并切过去，仅此而已。finish 实际做四步：先 checkout develop，把特性分支以非快进方式合入并生成一个合并提交，删掉本地特性分支，再把 develop 推给远端。finish 之后本地已经没有那条分支，代码只活在 develop 的历史里。

start 从 develop 切出 release/1.4.0，此后这条分支原则上只收修 bug 的提交。finish 是动作最多的一步：先 checkout master，把 release 分支非快进合进 master 并打上 v1.4.0 附注标签，再 checkout develop 把同一条分支合回 develop，最后删掉 release 分支。一次 finish 同时动两条长线和一条标签，三样都要 push 才算真做完，而脚本不会替你全推上去。这一步没走完就会出事，后面有复盘。

hotfix start 的基点是 master 上最新的标签，不是 develop 也不是 master 的头提交，这个基点选择是它比手工切更靠谱的地方。finish 与 release finish 类似：合 master、打补丁号标签、回 develop、删分支。support start 给已交付的老版本拉长期维护线，从指定标签切出 support/v1.3，允许这条分支长期存在，专接老客户的补丁。

工具本身那个年代的坑

git flow 不是 Git 自带命令，要装。当时常见两条路：mac 上 brew 装，或者拉源码 make install。装的人一多就冒出第二个问题——这不是同一个实现。最初那一代扩展把特性、修复做成 git feature、git hotfix 这样的独立命令，后来才统一成 git flow 加子命令的写法；社区里还有一份维护得更活跃的分支版本，包名常写作 git-flow-avh，多了不少交互和推送选项。命令签名看着一样，行为不一样。

真踩到的是分支前缀不一致。默认前缀在不同实现、不同版本里可能是 feature/，也可能是 features/，而前缀存在各自本地的 .git/config 里，仓库无法统一约束。于是有人 finish 时脚本去找 features/xxx，可这条分支是另一种实现按 feature/xxx 建的，直接报分支不存在；更难看的是远端两种前缀并存，评审页面上分不清哪些是正式流程产物。最后我们把工具降级成可选：文档里只写命名规范和基点，命令自己敲；谁想用扩展自己装，但 init 之后必须手工把前缀改成组内统一写法，合入一律以页面请求为准。

不想装工具的手工版

这四条就是 feature start 与 finish 的等价手工版，差别只在基点和分支名得自己保证。值得单独讲 --no-ff。如果 develop 上别人没合入过新提交，特性分支第一次合回去本来可以快进，即把 develop 的引用直接挪到特性分支头上，历史图里完全看不出曾有过一条分支。加上 --no-ff 会强制生成合并提交，把分支形状留在历史里，这是有用的：一条需求对应一个合并提交，它的两个父提交一边是 develop 的旧位置、一边是特性分支的头，要整块回滚就用 git revert -m 1 <合并提交> 一次撤销这条需求的全部改动，不必逐笔 revert，也不会漏掉中间某一笔。代价是多一层分叉，嫌乱的人可以不接受，但 release 合 master、hotfix 合两条线我建议坚持：线上某个版本包含哪些改动，就是靠这些合并提交反查的。合入时用普通合并还是变基是团队要提前定死的规矩，操作细节另有一篇讲。

GitHub Flow 的命令面

然后在协作平台对着 master 发一条 Pull Request。评审过程中要改，本地继续提交再 push 同一条分支，请求会自动更新，不用关掉重发。有写权限的人直接在主仓库切分支；外部贡献者或权限收紧的团队先 fork 到自己名下再发请求，同步上游靠 git fetch upstream，之后把主干更新合进自己的分支。合并之后改动就在主干上，部署紧接着推上线。

两个前提容易被忽略。一是分支存活以小时或一两天计，不留活过一周的分支——分支短冲突就小，评审也来得及看。二是”合并即意味着可发布”这句话有代价：它要求构建和自动测试挡得住坏提交，否则主干一旦被红着的改动污染，下一个合进来的人就成了替罪羊，而你连一条隔离中的 release 分支都没有，只能赶紧再发一版盖掉。我们当时自动化覆盖还不够，两套的成本差就是这么直白。

两种模型的成本差在哪

先说合并成本。Git Flow 的特性分支活得久，攒到最后一次性合回 develop，冲突集中爆发；更麻烦的是 develop 与 master 两条长线要双向同步，hotfix 和 release 各要合两处，漏一次就出现”线上修好的问题下个版本又复发”。GitHub Flow 分支短，冲突当场解决，但压力换到了别处：主干必须一直可用，这要求测试和构建真的在干活。

再说发布控制，这是两者最实质的分野。Git Flow 的 release 分支能把”这一段只许修 bug、不上新功能”变成物理隔离——冻结的东西是一条真实分支，评审时一眼看得出提交范围。做版本交付的团队很需要这层隔离：要给客户装、要维护多个老版本、验收期长短由外部定。GitHub Flow 没有它，只能靠小步快发摊薄风险，或者靠特性开关把未完成的改动关在门后，两者都不免费。

然后是心智负担和回滚。分支种类一多，新同事光记规矩就要几天：什么从哪切、合到哪、谁能动 master、标签什么时候打。记不住的下场不是挨骂，是流程悄悄退化。回滚上，Git Flow 的 master 干净，找到上一个合并提交或旧标签就能退回，但两条线并存让人多问一句”线上到底是哪个版本”；主干即发布产物时回滚更直接，重发上一版或加一条反向改动的分支就行，前提是你随时能发。

什么时候选哪个

判据是几个能查证的问题。团队能不能持续部署、自动测试能不能真挡住坏提交：能，就用 GitHub Flow 那套短分支加评审，省掉一大半仪式；不能就别硬上，随时可发会变成随时可出事。要不要同时给多个大版本打补丁、上线窗口是不是外部（客户、合作方发版日）定的、有没有明确的验收冻结期：占了两条，Git Flow 的 release 与 hotfix 就值得为它付复杂度。多数团队落在中间：一条主干、一条预发布分支、一堆短特性分支，发布时在预发布分支上冻结，验收过了合主干打标签。这形态当时也有人起过别的名字，我倾向别追名词，看清它合不合自己的发布节奏就够。

迁移怎么写

如果你现在的状态是”长期 dev 加一大堆本地分支”，要往短分支流程挪，我建议三步，顺序不要打乱。

第一步只动约定，不动工具：写死分支命名模板和存活上限，写死基点——哪类分支从哪切、合到哪。这一步成本是零，收益是能立刻在评审里问出”这条分支为什么活了三个星期”。

第二步把 PR 设成唯一合入路径：主干和预发布分支设成保护分支，普通成员推不上去；服务端没有保护分支功能，就挂一个更新钩子脚本，检查推送是不是合并请求产生的引用更新，不是就拒绝。这条是所有规矩里最有效的，因为其他条款违反时还有商量余地，这条在服务器上直接拦。

第三步把发布从”分支合并”改成”打标签触发”：构建脚本监听标签推送，见到符合版本号格式的标签就出包部署。发版和合并从此解耦，发布记录就是标签列表，回溯线上版本不再靠问人。

要提醒的是，迁移最难的不是命令而是评审响应速度。分支活得短的前提是当天有人看请求；一条 PR 挂三天没人理，人就会自然地去开长分支，或者干脆直接推主干，流程退回原点。所以第二步之前，得先保证评审人够、时段明确。

两次踩坑复盘

第一次是用了 Git Flow 但没人执行 release finish。有一阵子的发布是这样的：从 develop 切 release 分支，验收通过，手工合进 master、出了包，唯独没跑 finish——于是 master 上没有对应标签，develop 也没收到那批收尾提交。三个月后要确认某个客户环境跑的是哪份代码，git tag 列表里根本没有那三个版本，只能拿构建产物的文件时间去猜，还猜错过一次。之后我们把发布收进构建脚本：合主干、打标签不再由人手敲，人只提交一个发布请求，标签由脚本生成并推回，构建以标签为准。人不碰标签，标签才终于和产物一致。

第二次是反过来，硬推 GitHub Flow。那个项目还在收 IE 兼容的维护补丁，客户要的是”这版只改两处样式，别的不动”。主干只有”现在”这一个状态，兼容改动和下周要上的新功能挤在一条线上，历史读起来分不清哪些算交付内容。折腾一个季度，又退回一条长期维护分支。

这两件事合起来教会我的只有一句话：流程服务于发布节奏，不是拿来供的，也不是拿来显摆专业的。

小结

三种形态各归其位。Git Flow 适合版本交付、多版本并行维护、发布窗口由外部定，它用仪式换隔离。GitHub Flow 适合持续部署、测试兜得住的团队，用主干一直可用来换掉全部仪式。中间形态——主干加一条预发布分支加短特性分支——是多数团队最后实际收敛到的地方，不必给它找名字。一句话判据：先数清自己多久发一版、同时维护几个版本，再去决定分支有几条；顺序反过来，写出来的就是没人执行的规范。
