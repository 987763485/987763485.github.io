HTTP 长连接与 keep-alive

事故：偶发的 ECONNRESET，重试一次就好

八月上旬，内部订单服务开始偶发 ECONNRESET，一天几次，每次都是调下游的那一段报错：socket hang up。诡异的地方在于重试一次必定成功，手工复现不了，压测也压不出来。

我们先把下游的访问日志拉出来对时间，发现报错那几次，下游根本没收到请求。再看本机的连接状态，发现出问题的请求都走了一条复用的连接。顺着抓包才看明白：负载均衡那边的空闲超时被运维从六十秒调成了三十秒，而我们的连接池还按六十秒留着连接。池子里一条已经闲置四十秒的连接，在我们看来还能用，实际上对面早关了；请求写进去，收到的就是一个 RST。

这类故障的特征很好认：低频、集中在业务低峰、重试必好、下游日志里没有记录。它跟”下游挂了”长得完全不一样，第一次遇到时我们查了下游一整天。

第一次定位花了三个小时，转折点是抓了一次包：看到客户端发请求之后立刻收到 RST，而不是超时。超时会把我们引向”下游慢”，RST 才指向”对面已经没有这个连接”。从那以后，遇到偶发连接错误，先分清是超时、RST 还是 DNS，这三类的排查路径完全不同。

keep-alive 在协议层到底是什么

HTTP/1.1 默认就是持久连接：一次 TCP 连接上可以连续发多个请求，响应按顺序回来，连接不主动断。要看它有没有生效，只看一个头：

Connection: keep-alive 是 HTTP/1.0 时代需要显式带上的协商头。到了 HTTP/1.1，不带 Connection: close 就默认保持；服务器想关，回一个 Connection: close，双方在这一次响应之后各自关连接。

所以排查时不要只搜 keep-alive 这个词。HTTP/1.1 的响应里可能根本没有它，连接照样是复用的。反过来，某些中间层会自己加一个 Connection: keep-alive，那只是它跟客户端之间的约定，不代表后端也是长连接。

还有一个常见误解：Keep-Alive: timeout=5, max=100 这行只是提示，不是合同。它告诉对端”我大概会留五秒、这条连接最多跑一百个请求”，对端可以不听，中间层可以改，浏览器也可以用自己的策略。我们曾经按 timeout=5 去推算连接池的寿命，结果在一条经过代理的链路上完全对不上。

HTTP/1.0 的客户端默认每次新建连接，要复用必须显式带 Connection: keep-alive，服务端还得回一个同样的头，并且在响应里给出 Content-Length。老代理和嵌入式设备大多停在这个版本。我们对接过一个跑在打印设备上的小 HTTP 客户端，它发的是 1.0，我们回了 1.1 的响应却没有长度，它便一直等到我们关连接才认为响应结束，每打一张单子都要多等几秒。给这个路径补上长度之后，它才开始真正复用。

一个 Connection: close 救了老代理

七月底排查另一个问题时，我们发现有个老代理把上游返回的 Connection 头原样转给了客户端。按规范它不该这么做：Connection 是逐跳头，只对相邻两方有效，代理转发前应该把它剥掉。它没剥，客户端看到的是后端和代理之间的约定，不是客户端和代理之间的。

后果是客户端以为连接要关，每次请求都新建，长连接等于没开。我们没法立刻换代理，就让后端在这个路径上显式返回 Connection: close，至少避免客户端误判成”半开”状态。这个补丁不好看，但比让客户端在错误的假设上复用连接安全。

顺带说一句 Proxy-Connection。这是个非标准头，早期一些代理用它协商，行为各家不一样。看到它出现在线上日志里，先怀疑链路里有个年迈的中间设备，不要拿它当标准去写代码。

逐跳头也不止 Connection 一个。Keep-Alive、TE、Trailer、Upgrade、Proxy-Authorization 都属于这一层，代理不该原样往后传。我们在一次联调里见过 Upgrade 被透传，后端以为客户端要升级协议，回了个 101，客户端一脸茫然地挂在那里。后来”链路上有代理时，响应头按逐跳规则过一遍”被写进了上线检查单。

服务端什么时候会把连接关掉

我们自己的 Node 服务也管着长连接。当期跑的是 4.4 的 LTS，服务端对空闲长连接有一个默认的关闭时间，大约五秒；Node 6 上可以用 server.keepAliveTimeout 调，4.4 没有这个公开属性，只能接受默认值或者自己在 socket 上动手。

顺序不能反。头一旦发出去，再改 Connection 只是在改内存里的对象，线上仍然是原来的值。我们有过一次事故：一个导出接口要跑十几秒，代码想在结束后关连接，结果 setHeader 写在 write 之后，告警日志里一切正常，连接却一直挂到空闲超时才回收。

还有一种是被动的关闭：客户端先走了。服务端在 req 上收到 close，这时再写响应已经没人接。res.write 不会抛错，返回 false 也只是背压信号，很容易写出”日志显示成功、用户什么都没收到”的代码。

响应没有长度，连接就不能复用

长连接要成立，客户端必须知道这次响应的正文到哪里结束。两种方式是合法的：带 Content-Length，或者用分块传输编码并在末尾给一个零长块。两样都没有，客户端只能读到连接关闭为止——这条连接自然也就不能复用。

我们写过一个返回 204 的接口，图省事只写了 res.statusCode = 204; res.end();。204 本来就没有正文，这样写没问题。真正出问题的是另一个接口：手动拼响应，设了 Content-Type 却忘了长度，也没有走默认的分块输出，Node 在 end 时判断这个响应无法界定边界，于是给客户端发了 Connection: close。前端那边每次请求都新建连接，压测时端口很快见底。

规矩后来很简单：要么让 Node 自己算，用 res.end(body)；要么自己用 Buffer.byteLength 算准了设 Content-Length；两者都不做，就别指望复用。

服务端也不会无限复用。除了空闲时间，还有连接上跑过的请求数、写缓冲是否排空等因素，任何一项到了边界就关。客户端如果假设”连接会一直留着”，就会在边界处踩到同样的 RST。我们从不假设连接寿命，只假设它随时可能消失。

中间层空闲超时与客户端复用的时差

回到开头那次事故。链路上每一层对”空闲多久算死”都有自己的答案：

  • 负载均衡：三十秒（运维刚改的）
  • 我们的连接池：六十秒
  • 操作系统：TCP keepalive 默认两小时，基本指望不上

只要客户端的复用窗口比中间层长，就一定会出现”拿一条对面已经关掉的连接发请求”的窗口。这不是谁写错了，是两个超时没有对齐。

keepAliveMsecs 管的是 TCP 层探测的间隔，不是”连接最多活多久”，别指望它直接解决。真正要控制的是池子里连接的闲置时长，当期 Node 没有现成的”闲置超过 N 秒就丢掉”的开关，我们是在借出连接时看时间戳，超时就自己销毁再建。这段代码不好看，但比偶发 502 好。

第二条是给幂等请求加一次重试：GET、PUT、DELETE 遇到 ECONNRESET 或 socket hang up 时重发一次，非幂等的 POST 不重试，避免重复下单。重试不是万能药，它只是把”连接正好死了”这种偶发情况挡在用户看不见的地方。

一条连接同一时刻只跑一个请求

长连接省的是握手，不是并发。HTTP/1.1 的一条连接上，请求和响应是串行的：前一个响应没结束，后一个请求即使发过去了，响应也得排队。这个约束叫队头阻塞。

我们遇到过一次很典型的：页面上一个慢接口和一个快接口被浏览器分到了同一条连接上，快接口等了慢接口两秒多。排查时看服务端日志，快接口的处理时间只有几毫秒，可前端记录的时间是两秒五。差的那两秒不在处理里，在排队里。

这也解释了为什么静态资源要和接口分开域名、为什么慢接口要把自己的连接占住。单域名能开几条连接是浏览器定的，另一篇讲过，这里只说结论：长连接不等于”随便发”，它只是把建立连接的成本摊薄了；请求本身还是得排队。

管道化为什么没人开

HTTP/1.1 规范里其实允许管道化：客户端不用等上一个响应，连续把多个请求写进同一条连接。听起来能解决排队，实际没人用。

原因在中间层。管道化要求代理严格按照请求顺序回响应，只要有一个中间设备乱序或者提前关闭，客户端就无法把响应和请求对上。当年浏览器试过，后来陆续关掉了；我们自己的服务端也没有为此做任何优化。2016 年再说”开启管道化提升性能”，基本是纸上谈兵。

真正要并发，还是多开连接或者把请求合并。前者受浏览器限制，后者会带来缓存和错误处理的麻烦，各有权衡。

短连接把端口用光的那次压测

还有一次反向的事故：一个脚本每发一个请求就新建连接，压测跑到几千并发时开始报 EADDRNOTAVAIL，本机连不出去了。

原因是客户端主动关闭连接后，socket 会留在 TIME_WAIT 状态一段时间，默认是两分钟上下。大量短连接会把本地的临时端口占满。查看办法很土：

数字一直往上涨，就说明连接没有被复用。改成 keep-alive 之后，这个数字稳定在一个很小的范围内，压测才跑得下去。

服务端也会积累 TIME_WAIT，但通常由客户端先关连接，所以压力更多落在发起方。谁先关，谁承担这段等待，这也是长连接的一个隐性收益：连接被复用，关闭次数就少了。

什么时候不该开长连接

长连接不是无条件的好。三种情况我们会主动关掉：

第一，健康检查。负载均衡每几秒来探一次，探完就走，给它留连接没有意义，反而占着服务端的连接数。检查路径上直接回 Connection: close。

第二，一次性的大文件下载。传完就结束，客户端也不会再用这条连接，保持它只是让服务端多记一个空闲 socket。

第三，请求量极低、来源分散的内部工具。复用的概率太小，维护连接池的复杂度超过省下的握手。

判断标准很朴素：这条连接在关闭之前，还有没有很大概率再跑一个请求。有就留，没有就关。

怎么在线上确认复用真的发生了

不要只看配置。配置里写了 keep-alive，链路上任何一层都可能把它变成短连接。我们后来固定用两个办法验证。

第一个是 curl -v，看输出里是 Re-using existing connection 还是每次 Connected to：

两次请求打同一个地址，第二次如果还显示 Connected to，说明复用没生效，或者服务端回了 Connection: close。

第二个是看连接状态的数量。压测时服务端 ESTABLISHED 的数量应该远小于请求数；如果两者差不多，连接根本没被复用。这两个观察比读任何文档都直接。

长连接这件事，协议层只给了”默认保持”这四个字，剩下的全靠链路上每一层的超时、代理的行为和客户端的池子对齐。对齐了，省下的是握手和端口；对不齐，换来的是偶发的 RST 和查不出原因的 502。
