JS 中的浮点数精度问题

本文属于《算法与数据结构》第 2/13 篇
上一篇系列目录下一篇

三件 19.9，页面显示 59.70，活动却不触发

八月底，运营配了一个”满 59.7 减 5”的活动。客服转来一条投诉：用户买了三件单价 19.9 的商品，结算页上总价明明写着 59.70，结算时却没有减 5 块。

我们复现的时候一眼就看出来问题不在活动配置。三件 19.9 相加，后台算出来的总价是 59.699999999999996。页面用 toFixed(2) 显示成 59.70，看起来够了；活动判断用的是原始值，59.699999999999996 >= 59.7 是 false，于是没减。

用户看到的是 59.70，系统判断的是 59.699999999999996。两边都没有撒谎，只是中间隔着一个二进制。

定位的时候我们只加了一行日志：把三件商品的价格原样相加，打印 JSON.stringify(total)。屏幕上显示的是 59.70，日志里却是一长串 9。从那一刻起，问题就从”活动规则配错了”变成了”数字本身就不是看到的那个”。

0.1 在二进制里是无限循环

十进制里，三分之一写不完，只能写成 0.3333…；二进制里，十分之一写不完。0.1 的二进制展开是 0.0001100110011…，0011 无限循环。

双精度浮点数只有 53 位有效二进制位，存不下无限的展开，只能在某一位截断，再按规则舍入。所以变量里那个”0.1”，其实是一个和 0.1 非常接近、但不完全相等的数：

这不是 JS 的 bug。按 IEEE 754 双精度存储的语言都会得到这个结果，换一门语言、换一台机器，只要用的是同一套浮点规则，输出就一样。JS 特殊的地方在于它只有一种数字类型，整数和小数共用双精度，所以这个问题在业务代码里出现得特别频繁。

哪些小数能精确表示

判断标准很简单：约分之后，分母是不是 2 的幂。

  • 0.5 = 1/2，能精确表示。
  • 0.25 = 1/4，能精确表示。
  • 0.75 = 3/4，能精确表示。
  • 0.1 = 1/10，分母含 5，不能精确表示。
  • 19.9 = 199/10，同样不能。

凡是日常价格里带一位、两位小数的，大多数都落在”不能精确表示”这一边。这不是偶然，十进制的小数位对应的是 10 的幂，而计算机存的是 2 的幂，两套进制天生对不齐。

手算一遍 0.1 的二进制

理解这件事，最好的办法是自己乘一遍。把小数部分不断乘 2，取整数位，直到小数部分变成 0 或者开始循环：

  • 0.1 × 2 = 0.2，取 0
  • 0.2 × 2 = 0.4，取 0
  • 0.4 × 2 = 0.8，取 0
  • 0.8 × 2 = 1.6，取 1，余 0.6
  • 0.6 × 2 = 1.2，取 1，余 0.2
  • 0.2 又回来了，循环开始

取出的整数位连起来是 0.000110011…，0011 无限重复。双精度在某个位置截断，存下来的就不是 0.1。0.5 只乘一次就结束，所以它能精确表示；0.1 永远结束不了，所以它不能。这个手算过程比背结论有用。

整数在双精度的有效位数范围内是精确的，加减乘只要不超出这个范围，结果就可信。问题几乎都出在除法和带小数的输入上。大数超出有效位数之后的行为，另一篇讲大数运算时写过，这里只关心日常金额。

四种运算，危险程度不一样

  • 加法：误差会积累，量大了就显出来。金额累加是重灾区。
  • 减法：两个很接近的大数相减，有效位会被抵消掉，剩下的部分误差占比很大。1.0000000000000002 - 1 的结果只剩下一个极小的尾数。
  • 乘法：误差按比例放大。19.9 × 3 就是例子，单价的末位差跟着乘了三倍。
  • 除法：除不尽就必然截断。0.3 / 3 在 JS 里得到 0.09999999999999999，不是 0.1。

这不是说减法、除法不能用，而是说别在它们后面直接做等值判断。金额走整数分，等于把加减乘都变成了整数运算；除法只在换算单位时出现一次，而且可以用取整和取余代替。

金额：整数分是唯一稳妥的日常方案

金额一旦涉及加减和比较，我们一律换成整数分。19.9 元存成 1990 分，三件是 5970 分，和 5970 分比较，=== 就是可靠的。

toFixed 用的是变量里那个二进制值，不是我们以为的十进制字面量。经典的例子：

原因是 1.005 在双精度里略小于 1.005，舍入时往下去。toFixed 还负责补零和返回字符串，它是个格式化函数，不是金额计算函数。我们在展示层用它没问题，在计算层用它”修精度”就错了。

还有一个细节：toFixed 的返回值是字符串。有人拿它转成数字继续算，parseFloat(str) 又回到浮点，前面那一步等于白做。

舍入方向：先想清楚负数和点五

金额取整最怕边界。Math.round 的规则是向正无穷方向舍入点五：Math.round(2.5) 是 3，Math.round(-2.5) 是 -2，不是 -3。用它处理负数金额，方向会和平时的”四舍五入”直觉相反。

Math.trunc 是 ES6 的方法，当年 IE 上没有；要截断小数，得写 x < 0 ? Math.ceil(x) : Math.floor(x)。Math.floor(-0.5) 返回 -1，也不是”抹掉小数”的意思。

我们的金额舍入函数只接受整数分，不处理小数，这些问题被挡在了转换层之外。但算折扣时还是遇到过一次：折扣率乘出来是 1234.5 分，按”四舍五入”应该 1235，代码用了 Math.floor，每单少收一分钱，一个月对账差了几块钱。舍入方向要写进函数注释，不能靠调用方猜。

展示和计算分开

那次活动事故之后，我们定了一条很粗但有效的规矩：金额从接口到存储到计算，全程整数分；只有渲染到页面那一刻才转成元。

这条规矩把问题从”每次计算都小心”变成了”转换一次、之后都安全”。落地时有两个检查点：

  • 接口返回金额时，字段名带单位，比如 total_cents，让调用方一眼看出不是元。
  • 组件里不允许出现 price * 100 或者 total / 100 这类字面量，转换统一走工具函数。

工具函数本身要测。我们给它留了几组用例："0.1"、"19.9"、"1.005"（应当报错）、"0"、"-0.01"。最后一组是负数的符号处理，写反了会把负数变成正数，比精度问题更严重。

累加：误差会攒起来

一次加法的误差在极小量级，看起来无所谓。但把几万条数据累加，误差会一点点攒起来，最后可能落到小数点后好几位。做报表的同事遇到过：同一批数据，前端累加和数据库求和差 0.01，两边都觉得自己对。

浮点累加没有”正确”的顺序，只有误差大小的差别。数量级相差很大的数相加，小的会被大的吃掉。要减小误差，可以先把数按绝对值排序、从小到大加；要求更高时用 Kahan 求和，用一个补偿变量记住被舍掉的部分：

序列化会把误差带出去

JSON.stringify(0.1 + 0.2) 得到的是 "0.30000000000000004"，不是 "0.3"。这个字符串发到后端，后端按字符串解析，误差就从浏览器带进了数据库。

反过来也一样：后端存了 19.9，序列化成 JSON 传过来，前端拿到的是 19.9 最接近的双精度值。显示没问题，参与计算就有末位差。接口两边约定用整数分，能同时解决序列化和计算两个问题。

什么时候该换工具

整数分能解决金额，解决不了所有小数场景。比例、税率、坐标、统计量这些量，本身就没法用整数表达。

两种情况我们会换工具。第一种是要求十进制精确运算，比如财务对账，会引入一个十进制运算库，把数存成系数和指数，按十进制规则算。第二种是超大整数，用字符串或者专门的库，那是另一篇的主题。普通页面上的进度条、图表比例，用普通浮点加容差比较就够了，没必要上重武器。

判断标准是误差会不会被业务规则放大。金额差一分钱会触发对账失败，那就不能将就；进度条显示 99.99999%，没人会追究。

还有一种情况是跨语言传输：前端用浮点算完，后端用十进制类型存，序列化那一层没对齐，误差换了个样子继续存在。约定单位比约定精度更可靠——两边都说”分”，比两边都说”保留两位小数”更难出错。
