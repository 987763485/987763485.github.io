JavaScript 手写 new 与 instanceof

一个 shim 把日期弄坏了

八月初，接手一个 2013 年写的表单库。它当年为了兼容 IE8，自己带了一份 inherit 和 create，凡是 new X() 都走它的 create(X, ...)。新页面里有个日期范围控件，我把 new Date() 换成 create(Date)，本地 Chrome 上一切正常，到了测试同事的机器上，toISOString 直接抛 TypeError: this is not a Date object。

查了半天才发现，Date 被当普通函数调用时返回的是一个字符串，不是日期对象。create 拿到字符串，按”返回值不是对象就退回实例”的规则，返回了那个用 Object.create(Date.prototype) 造出来的空壳。这个空壳的原型看着是 Date.prototype，身上却没有日期对象该有的内部槽，任何方法一调就炸。

同一天还炸了 Boolean：create(Boolean, false) 拿到 false，退回空壳，valueOf() 抛错。那次之后我们定了一条：手写的 create 只服务自己写的构造函数，内置的一律用 new。这不是风格问题，是能力边界。

那天下午我们用最笨的办法定位：把出问题的调用一处一处从 create 换回 new，换到第三处，日期就正常了。再打印就清楚了：Object.prototype.toString.call(new Date()) 是 [object Date]，换成手写版是 [object Object]；可 create(Date) instanceof Date 偏偏是 true。原型链接得再对，也造不出内部槽。这件事让我们第一次意识到，instanceof 和”它真的是不是”是两个问题。

那个库里有四十多处 create 调用，我们花了一周才换完。中间加过一个很难看的临时分支：Ctor 是内置构造函数就走 new，否则才走手写版。它确实能挡住日期和布尔，但把”这段代码到底在干什么”搞得更不清楚，最后还是全部删掉了。

四步之外，最容易漏的是返回值

new 的四步——建空对象、接原型、把 this 绑过去、返回——另一篇已经写透了，这里不重抄。真正手写时，第二版才补上的是返回值规则：构造函数 return 一个对象，这个对象会顶替刚建好的实例；return 原始值，等于没返回。

把 return this 写在构造函数末尾是常见写法，它返回的就是 obj 本身，isObj 为真，结果一样；所以这个分支平时看不出来，只有当构造函数真的返回另一个对象时才暴露。

构造函数返回 new 的结果 手写版要做什么
不写 return 新实例 返回 obj
return this 新实例 返回 obj
return 数字、字符串、布尔 新实例 忽略返回值
return 对象或函数 那个对象 顶替 obj
return null 新实例 null 不算对象

我们漏过的是最后两行。null 在 typeof 里是 'object'，当年写的判断是 typeof result === 'object'，于是 return null 被当成对象返回，调用方拿到 null，报错点离构造函数十万八千里。

还有一处更少见：构造函数返回一个函数。函数的 typeof 是 'function'，不是 'object'，第一版只判断了 typeof result === 'object'，于是 new Weird() 拿到的是 Weird 的实例，不是构造函数返回的那个函数。修法就是上面那行 isObj，把 function 也认成对象。

参数是怎么丢的

第一版还有一个错，错在 apply 的第二个参数：

arguments 里第一个是 Ctor 自己，构造函数拿到的是 [Ctor, 真正的第一个参数, ...]。单参数时不容易发现，因为构造函数大多只用第一个形参；等一个双参数的构造函数把 Ctor 当成 name 存进去，页面上就出现 function Foo() 这样的名字。

正确写法是 Array.prototype.slice.call(arguments, 1)，把第一个剔掉。apply 的第二个参数只要求是类数组，直接传 arguments 在多数引擎里也能跑；我们仍然用 slice，因为后面还要检查长度、还要把参数转给别的函数，留一个真数组省事。

内置构造函数模拟不了

create 修好返回值之后，我们还是不死心，试过让它支持内置构造函数，结论是做不到。

Date 是第一个反例。它被当作函数调用时返回字符串，这是语言规定的，不是实现细节。Boolean、Number、String 同理，作为函数调用返回原始值。也就是说，Ctor.apply(obj, args) 这一行对它们根本不产生”往 this 上写东西”的效果。

Promise 是另一个方向的反例。它要求必须用 new 调用，Promise.apply 直接抛 TypeError: Constructor Promise requires 'new'。2016 年我们用 Promise 做请求封装，要是谁把它塞进 create，得到的是一行看起来莫名其妙的报错。

Array 则是个容易让人误判的中间项。Array(3) 作为函数调用返回一个长度为 3 的数组，和 new Array(3) 一样，所以 create(Array, 3) 看起来能用。Error 也类似，作为函数调用返回的是货真价实的错误对象。我们一度拿这两个当”内置也能支持”的证据，直到 Date 和 Boolean 把结论推翻。能跑通是巧合，不是规则。

bind 过的构造函数也进不来

ES5 的 Function.prototype.bind 还有个更少见的边角：绑定后的函数没有 prototype 属性。

原生 new 对绑定函数有特殊处理，会穿过绑定去用目标函数的原型；手写版只看到 Bound.prototype 是 undefined。这说明手写实现永远在追规范的特例，追不完。

这些差异的根子在于 [[Construct]]：new 触发的是对象内部的一个方法，不是”调用函数再拿返回值”。用户态代码可以模拟用户态构造函数，模拟不了语言自带的这批。

第一版在真实代码里误判过

手写版修好之后还误判过一次。有个模块的构造函数没写 prototype，它继承自 Object，Ctor.prototype 就是 Object.prototype。手写版沿原型链往上找，任何普通对象都能碰到 Object.prototype，于是 isInstanceOf({}, Ctor) 返回 true。原生的 instanceof 一样会返回 true——这是规范行为，不是手写版的 bug——但调用方把它当成了”是不是这个类的实例”，判断就错了。

这也是我们后来把”类型判断”和”原型判断”分开说的原因。instanceof 问的是原型链，不是身份；构造函数没有自己的 prototype 时，它就没有区分能力。

另一个不可靠的东西是 constructor。很多人用 obj.constructor === Foo 代替 instanceof，原型一被替换，constructor 就指向 Object：

手写 instanceof 至少还沿着原型链找，比 constructor 稳一点，但也就一点。顺带一个相关的坑：Object.create(null) 造出来的对象连 hasOwnProperty 都没有，obj.constructor === Foo 会直接抛 TypeError；手写 instanceof 对它返回 false，原生也一样，要沿 Object.getPrototypeOf 走才有答案。

它测不出跨窗口的对象

手写版和原生版在一个地方必然一致地错：跨窗口。

页面里嵌了一个 iframe，iframe 里 new Array() 出来的数组，拿到外面 instanceof Array 是 false，因为两边的 Array.prototype 不是同一个对象。手写版同样返回 false，这不是 bug，是 instanceof 的定义决定的。真要判断数组，用 Array.isArray，它在规范里按内部类型判断，跨窗口也成立。

这也是我们后来不再到处手写 instanceof 的原因：它回答的问题是”这个对象的原型链上有没有这个函数的 prototype“，不是”这个对象是不是某种东西”。这两个问题大部分时候答案一致，在跨窗口、多套运行环境、原型被改过的时候就会分叉。

我们真正被咬是在一个嵌入报表页里。宿主页面用 instanceof Array 判断接口返回的数组，接口数据由 iframe 里的脚本生成，结果每个数组都被判成”不是数组”，走了对象分支，表格渲染成一堆 undefined。改成 Array.isArray 之后正常；Object.prototype.toString.call 也能用，但那套判断另一篇列过清单，这里不重复。

prototype 被换掉之后

还有一个现场：构造函数先造了对象，后来有人把 Ctor.prototype 整个换掉。老对象还挂在旧原型上，新对象挂在新原型上，instanceof 对老对象返回 false。

这不是手写版的缺陷，原生也一样。我们的规矩是：原型上只加方法，不整体替换；要换就换一个没有任何实例的构造函数。

继承 helper 的连带故障

老库里还有一个 inherit(Child, Parent)，内部就是 Child.prototype = Object.create(Parent.prototype) 再补 constructor。它本身没错，错在调用时机：有个页面在 inherit 之后又给 Parent.prototype 整体赋了一个新对象，Child 的原型还挂在旧的 Parent.prototype 上。表现是 Parent 新加的方法，Child 实例一个都调不到。

这类问题不是 new 或 instanceof 的错，是”原型是共享对象”这件事被忘了。我们后来在 code review 里加了一条：只要看到 X.prototype = 这种整体赋值，就去搜有没有已经建立过继承关系的子类；有就改成往原型上加属性。

三种写法各自适合什么，我们内部有一张很短的对照：

写法 适合 不适合
new Foo() 需要 instanceof 的类、原型上挂方法 构造函数要返回另一个对象
Object.create(Foo.prototype) 只借原型、不想跑构造逻辑 需要初始化参数
工厂函数 返回组合对象、隐藏实现 调用方依赖 instanceof

还有一条命名约定：构造函数首字母大写，只作提示，语言不强制。当年那个表单库里就有小写的构造函数，混在普通函数里，谁也没看出它必须配 new；漏了 new 时 this 绑到全局，属性写到了 window 上，排查时看半天以为是模块加载顺序的问题。

用 console.assert 而不是测试框架，是因为那个库压根没有测试入口，引入一套框架的成本比这二十行高得多。代价也要说清楚：IE9 的 console 只在开发者工具打开时才有，IE8 干脆没有；直接跑会先死在 console 上。我们把它包在一个 if (window.console) 里，老浏览器上这组断言等于不跑，只能靠人眼在支持的环境里过一遍。

写到这里再回头看，手写 new 与 instanceof 的价值不在代码本身：那几十行不会让程序更快，也不会让兼容性更好。它的价值是逼你把”原型链””返回值””内部类型”这几个词从模糊印象变成可以复述的规则。真到了业务里，能用 new 就用 new，能 Object.create 就 Object.create，判断数组用 Array.isArray。手写版可以留在测试用例里，别留在业务代码里。

收尾的表

现象 先查哪里
日期对象一调方法就抛 this is not a Date 有没有用普通函数调 Date
构造函数 return 了对象，实例却是空的 返回值判断漏了对象顶替
return null 之后调用方拿到 null 把 null 当成了对象
换过 prototype 之后 instanceof 变 false 老实例还挂在旧原型上
iframe 里的数组 instanceof 为 false 跨窗口原型不同源，改用 Array.isArray
手写 instanceof 传错右边不报错 少了可调用校验
构造函数的 prototype 就是 Object.prototype instanceof 对任何对象都为 true
老 IE 上手写版直接报错 __proto__、Object.create 的兼容

这张表只有一个结论：new 和 instanceof 背后各自有一条语言规则，手写一遍能帮你记住规则，但记住规则不等于可以在业务里替代它们。那次 shim 事故的代价是三天的排查，换来的就是这条边界感。
