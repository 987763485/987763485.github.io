问题出在 mid 没有取整。(0 + 3) / 2 是 1.5，list[1.5] 是 undefined，再读 .price 就抛错。数据条数是奇数时不一定触发，偶数时几乎必炸，所以本地那几组用例恰好绕过去了。

我们是在控制台看到错误栈指向 list[mid].price 那一行，才回头检查 mid 的。把除法换成 Math.floor 之后，原来那两组用例仍然全过——它们本来就没覆盖奇偶差异。后来补了奇数条、偶数条、空数组三组，才算把这类问题圈住。

修法只有一行：Math.floor((lo + hi) / 2)。但这行背后是二分查找最容易被忽视的一件事——它不难在思路，难在边界和取整。下面把常用的几种写法和坑一次写清楚。

二分的唯一前提：有序，而且顺序对得上比较

二分只认一件事：你用来比较的键，在整个数组里是单调的。升序也好，降序也好，只要单调，就能每次砍掉一半。

它不会替你检查这件事。数组没排好，二分照样返回一个下标，只是那个下标没有意义。我们有过一次更隐蔽的事故：列表按”价格”排好序，但比较函数用的是格式化后的字符串价格，"100" 排在 "99" 前面，数组看着有序，实际不是按数值单调。二分找出来的位置偶尔偏一格，用户投诉”筛出来的价格不对”，查了两天才对上。

所以调用二分之前，先确认两件事：数据真的按这个键排过；比较时用的类型和排序时一致。字符串和数字混着比，JS 会悄悄转换，结果更难查。

坏处是它不适合找边界。数组里有重复值时，它返回的可能是中间任意一个，不是第一个也不是最后一个。价格筛选要的恰恰是”第一个大于等于”，闭区间版本满足不了。

左闭右开：边界变体的统一写法

找边界的场景，我们统一用左闭右开 [lo, hi)，hi 初始是 arr.length，循环条件是 lo < hi，退出时 lo 就是答案。函数不返回 -1，而是返回”应该插入的位置”，范围是 0 到 arr.length。

它找的是第一个”键不小于 target”的位置。数组里没有 target 时，返回的是它应该插入的位置；所有元素都小于 target 时，返回 arr.length。调用方必须处理这个越界值，不能拿回去直接取数组元素。

价格筛选页就漏了这一步。输入的最低价高于所有商品时，lowerBound 返回 list.length，后面的代码拿它去取 list[idx].price 做二次判断，页面又白了一次。正确做法是先判断 idx === list.length，直接显示”没有符合条件的商品”。二分返回的是位置，不保证那个位置有元素，这两个概念调用方要自己分开。

死循环的三种来源

二分写错，最常见的后果不是答案错，是页面卡死。三种写法我们真都写出来过：

第一种，lo = mid 配 mid = Math.floor。当区间只剩两个元素时，mid 等于 lo，lo 不动，循环永远在同一个位置打转。

第二种，while (lo <= hi) 里把 hi 写成 mid。lo 和 hi 相等时，mid 等于它们，如果走的是 hi = mid 分支，区间没有缩小，下一轮一模一样。

第三种，mid 取了 Math.ceil，却在另一个分支写了 hi = mid。取整方向必须和移动方向配套，不然总有一边会原地踏步。

避免办法不是背口诀，是给循环一个明确的不变量：每一轮之后，区间一定比上一轮小。写的时候盯着这个条件，比记”左加右减”可靠。

mid 用 Math.floor，别用位运算

JS 里经常能看到 (lo + hi) >> 1。它能用，但有两个问题。

一是可读性。位运算的意图不明显，新人要停下来想一下才知道是在取平均。

二是 32 位截断。位运算会把操作数转成 32 位有符号整数，数组长度一旦超过这个范围，结果就会错。日常业务数组到不了这么大，但工具函数会被复制到不知道什么地方去。位运算的这套规则在那篇讲位运算的文章里写过，这里不展开。

我们统一写 Math.floor((lo + hi) / 2)。有人担心 lo + hi 溢出，在 JS 里这个担心不成立：数组下标远小于 Number.MAX_SAFE_INTEGER，两个下标相加不会丢精度。lo + Math.floor((hi - lo) / 2) 这种写法更稳，但除非代码要移植到别的语言，我们不再多写这一层。

一个变体：第一个坏版本

还有一种题面看起来不像二分，本质是同一个模板：版本号从 1 到 n，某个版本之后全是坏的，找第一个坏版本。

把 isBad 看成”键大于等于某个阈值”的谓词，它和 lowerBound 是同一个结构：满足条件就收缩右边界，不满足就跳过 mid。识别出这个结构，就不用为每道题重新推一遍边界。

我们真正在业务里用过的是”找第一个失败的构建”和”找第一个超过配额的时间点”，都是这个形状。写之前先问一句：条件是不是单调的？一旦不单调，二分就不成立。

二分答案：搜的不是下标

有一类问题没有数组，答案是一个数，但判断某个数行不行很容易，而且可行性随数单调。比如仓库有若干批货，要按顺序装进若干辆容量相同的车，问车的最小容量。

直接求容量很难；判断”给定容量能不能装下”很容易，而且容量越大越容易装。这就满足了二分的条件：在答案空间里二分。

要点在上下界。下界取单件最大值，比它小的容量连一件货都装不下；上界取总量，一辆车总能装完。二分答案最常见的错误就是下界取 0 或者上界取错，正确答案在区间外，怎么搜都搜不到。写之前先用两个极端值验证 canShip 的返回值，再开始二分。

变体：旋转过的有序数组

有序数组从某个位置切开、前后两段交换，变成 [5, 6, 7, 1, 2, 3]。普通二分”中间和两头比”的直觉不再成立，但每一轮至少有一半是有序的，还是能砍半。

判断哪一半有序，用 nums[lo] <= nums[mid]。等号不能少：区间只剩一个元素时，lo 和 mid 相等，没有等号会误判成右半段有序。数组里有重复值时，这个写法会遇到无法判断的情况，需要单独处理；业务里没真用过旋转数组，写它纯粹是为了练边界感。

变体：找局部峰值

再有一种变体，数组不整体有序，只要求找任意一个”比左右都大”的位置。思路是看 mid 和 mid + 1 的斜率：上升就往右找，下降就往左找。

它不需要数组有序，只需要”沿着上升方向一定能走到一个峰”。这类题的意义不在业务，而在提醒自己：二分依赖的不是”有序”这个词，而是”能根据一次比较排除一半”这个性质。

在实数上二分：循环条件不能写等号

二分不只能用在数组下标上。比如求一个数的平方根，或者找一个刚好让某个函数超过阈值的参数，答案空间是连续的实数。

这时候不能写 while (lo <= hi)，因为实数区间里几乎不会恰好相等；也不能写 while (lo < hi)，浮点精度到一定程度后 mid 和边界会相等，循环要么提前停，要么停不下来。

递归版本可以写，但没必要

二分也能递归写：算 mid，命中返回，否则把一半交给下一层。读起来更接近定义，但每次递归都要压栈，JS 引擎对尾调用没有普遍优化，数组一大就有栈溢出的风险。迭代版本只有一个循环，状态就是 lo 和 hi 两个数，调试时打断点也更容易。我们一律写迭代。

什么时候不该用二分

二分不是”查找就用”。四种情况我们会选别的：

  • 数据是链表。不能随机访问，每次取中间都要走一遍，二分退化成 O(n)。
  • 数组很小。几个、十几个元素，从头扫一遍比二分加取整更快，代码也短。
  • 频繁插入删除。维护一个有序数组的代价比查找省下的时间高，考虑别的结构。
  • 只查一次且数据没排序。排序 O(n log n) 之后再做一次 O(log n) 的查找，不如直接线性扫一遍 O(n)。

判断标准是整体成本，不是单次查找的复杂度。二分省的是”多次查找”里的每一次，前提是排序的成本已经被摊薄。我们有个只有八个元素的配置数组，有人写了二分，连边界断言一共四十行；后来换成 indexOf 两行，运行起来没有任何可感知的差别。代码量也是成本，只是它不出现在复杂度里。

二分查找的代码量很小，小到让人以为不需要测试。实际恰恰相反：它每一条边都踩在边界上，取整、比较符、开闭区间，任何一处差一点，结果就从”偶尔错”变成”经常错”。写完先跑那五组边界数据，比在线上等用户报错便宜得多。
