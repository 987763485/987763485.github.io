字符串匹配算法：indexOf 与 KMP

本文属于《算法与数据结构》第 6/13 篇
上一篇系列目录下一篇

高亮关键词，卡在了匹配上

八月中旬，日志检索页加了一个关键词高亮。页面一次展示一份四兆左右的日志，用户输入一个词，命中的地方加黄底。第一版很直接：用 indexOf 从前往后找，找到一个就包一层标签，再从上一次的位置继续。

单词搜索还算能忍，半秒左右。可运营习惯一次贴三个词进来，三份循环叠在一起，页面要卡两三秒，输入框都跟着掉帧。我当时的判断很武断：indexOf 是逐个字符比，最坏情况太慢，应该上 KMP。

花了一个下午把 KMP 写出来，接到页面上，结果没有变快多少。真正的大头不在匹配，在每命中一次就重建一小段 DOM，几千次下来，浏览器光排样式就花掉了大半时间。算法只优化了整件事里很小的一段。

这件事没白做。KMP 后来在别的地方派上了用场，也让我第一次认真算清楚”朴素匹配到底差在哪”。下面先把算法写对，再说它在什么情况下值得用。

朴素匹配：最坏的情况不是乱写的

朴素匹配就是逐位对齐，从每个位置尝试一次：

大多数时候它很快：第一个字符不符就直接跳下一位，实际比较次数接近 O(n)。最坏情况出现在大量重复字符上，比如在 aaaaaaaaab 里找 aaab。每一次对齐都要先比三个 a 再失败，然后右移一位，再比三个 a。文本长度是 n，模式长度是 m，最坏就是 O(n·m)。

四兆文本里找一个十个字符的模式，如果文本恰好是重复字符，最坏比较次数能到千万级。这个数量在 JS 里不算灾难，但足够让一次搜索从毫秒掉到几百毫秒。真正的问题是：失败之后，我们已经知道前面那一段是什么了，朴素匹配却把知道的信息全扔了，从下一个位置从头再比。

拿小一点的例子数一遍更直观。文本是九个 a 加一个 b，模式是 aaab。从位置 0 到 5，每个起点都要先匹配三个 a、再在第四个字符上失败，共六次对齐、每次四次比较；位置 6 才匹配成功。文本长度 10、模式长度 4，比较次数二十多，接近 n·m。文本再长十倍，这个乘积就跟着长十倍，而不是像线性算法那样只长一倍。

KMP 的核心：失败时别回头

KMP 只做一件事：利用已经匹配过的前缀，决定失败之后模式串能往后滑多少，文本指针不后退。

拿模式 ababaca 举例。当它在某个位置失配时，我们要问：已经匹配的那一段里，最长的”既是前缀又是后缀”的部分有多长。这个长度就是下一次可以保留的匹配长度。

先看前缀表：

位置 0 1 2 3 4 5 6
字符 a b a b a c a
前缀表 0 0 1 2 3 0 1

读法是逐行看前缀：

  • 到位置 2，前缀 aba 的最长相等前后缀是 a，长度 1。
  • 到位置 4，ababa 的最长相等前后缀是 aba，长度 3。
  • 到位置 5，字符变成 c，ababac 没有任何相等的前后缀，长度回到 0。

假设文本匹配到 ababa 之后，下一个字符不是 c。朴素匹配会从这次对齐的下一位重新开始；KMP 看前缀表，知道 ababa 的最长相等前后缀是 aba，于是把模式串往后挪两位，让 aba 对齐到文本末尾那三个字符，继续比。文本指针一步都没退。

拿文本 abababacaba 和模式 ababaca 实际走一遍，能看清它省在哪：

步骤 文本位置 i 模式位置 j 发生了什么
1 0 到 4 0 到 4 ababa 逐字符匹配
2 5 5 文本是 b、模式是 c，失配
3 5 3 j 跳到前缀表 table[4] 的值 3，i 不动
4 5 到 8 3 到 6 从 b 接着比，一路匹配到模式末尾
5 9 7 返回起点 9 - 7 = 2

朴素匹配在第 2 步失配后，会从文本位置 1 重新开始，把已经确认过的 baba 再比一遍。KMP 一次都没有回头。

为什么跳到 table[j - 1] 不会漏掉答案？因为已经匹配的那一段文本，等于模式的前 j 个字符。前缀表给的是这段里最长的相等前后缀长度 k，也就是说，模式的前 k 个字符，和刚才那段文本的最后 k 个字符相同。把模式往后挪，让这 k 个字符对齐，是唯一可能继续匹配的位置；挪得比这更少，反而会把已知相同的部分错开。这不是严格证明，但足够说服自己：跳过的位置里不可能藏着答案。

把前缀表写出来

构造前缀表的过程本身也用了这个思路：当前字符匹配，长度加一；不匹配，就沿着表往回跳，直到匹配或者回到零。

这段代码值得对着 ababaca 走一遍。k 始终表示”当前位置之前，最长相等前后缀的长度”；失配时的 k = table[k - 1] 是在找次长的候选，而不是从头再来。

搜索主体

有了表，搜索就是两个指针的事：

复杂度是 O(n + m)：构造表 O(m)，搜索时文本指针只前进不后退，O(n)。空间是 O(m)，存那张表。跟朴素匹配比，它用一点额外空间换掉了最坏情况下的重复比较。

很多教程把前缀表整体右移一位，首位写 -1，叫 next 数组，失配时代码写成 j = next[j]。两种写法等价，下标差一位；混着抄就会在边界上错位，症状是模式第一个字符失配时死循环或者跳过匹配。我们统一用前缀表本身，因为构造时不用处理 -1 这个哨兵，读起来少一个特例；代价是失配时写 table[j - 1]，多一个减一。团队里只留一种写法，比两种都”看得懂”重要。

要找全部出现位置，改动很小：匹配成功之后不直接返回，而是记下位置，然后让 j 跳到 table[j - 1]，继续找重叠的匹配。

在 JS 里，原生 indexOf 往往更快

写完之后我做了对照：同一段文本、同一个模式，分别用 naiveSearch、kmpSearch 和原生 indexOf。

结论不太给面子：在绝大多数真实日志上，原生 indexOf 最快，KMP 和朴素匹配差不多；只有把文本换成大量重复字符的构造数据，KMP 才明显领先。这些观察都在同一台机器上、只反映相对量级，不是基准数据，但方向很清楚。

原因不神秘。原生 indexOf 在引擎内部实现，省掉了 JS 层的函数调用和逐字符 charAt 的开销，引擎还会针对常见情况做优化。KMP 的 O(n) 是渐近意义上的优势，常数项却比不过原生代码。用 JS 手写 KMP 去替换 indexOf，大多数时候是负优化。

这也是”算法复杂度”最容易骗人的地方：O(n) 比 O(n·m) 好，是在 n 足够大、常数项可比的前提下。真实场景里 n 可能只有几万，原生实现一次比较只要几个机器指令，你的 KMP 每次循环都要付 JS 的解释开销。

顺带说一句 BM。Boyer-Moore 从模式末尾往前比，失配时按坏字符和好后缀规则整段跳，平均情况下比 KMP 跳得多。不少标准库的长字符串查找会采用这一族启发式，具体到某个引擎、某个版本用哪种实现，不在我们能控制的范围里。知道这件事的实际意义是：不要假设原生 indexOf 就是逐字符朴素匹配——它可能已经用了更聪明的办法，手写的 KMP 未必追得上。

什么时候它真的有用

不是完全没用。我们后来在两个地方用了 KMP。

第一处是流式扫描。数据一块一块到达，不能回头重扫；朴素匹配在失配后需要回退文本指针，而块已经处理过去了。KMP 的文本指针单向前进，天然适合这种场景。我们在一个解析自定义协议的模块里用了它，每次喂一块，保留住 j 和前缀表，跨块继续。

第二处是自己实现匹配、不能用原生方法的环境。比如要同时返回每个匹配的起止位置、还要在匹配过程中做额外判断，原生 indexOf 只给起点，拿不到中间状态。

但如果只是”在一段字符串里找一个词”，直接用 indexOf，不要手写 KMP。判断标准不是”哪个算法更高级”，而是”原生方法够不够用”。

两个 JS 特有的边界

第一个是编码单位。JS 字符串按 UTF-16 码元计数，charAt 取的是一个码元，不是”一个字符”。indexOf 返回的也是码元下标。对于中文，一个汉字通常占一个码元，没问题；对于表情符号这类增补平面字符，一个字符占两个码元。

KMP 按码元比较，匹配结果和 indexOf 一致，偏移量也一致。真正的坑在于：如果模式串从一个代理对中间开始，它可能匹配到”半个字符”。我们没在业务里遇到过，但写通用文本工具时得记住，按码元切分和按字符切分不是一回事。字符串长度那篇讲过 length 和视觉宽度的差别，这里只强调匹配下标同样按码元算。

第二个是空模式。原生 indexOf('') 返回 0，我们的 KMP 也返回 0；kmpAll 对空模式返回空数组，这是自己定的约定，要在文档里写清楚，不然调用方会以为函数坏了。

四组用例

KMP 这种带下标的代码，最容易在边界上错一位。我们留了四组用例，改完跑一遍：

  • 空模式：kmpSearch('abc', '') 返回 0，和 indexOf 一致。
  • 模式比文本长：返回 -1，循环不能越界。
  • 重叠匹配：kmpAll('aaaaa', 'aaa') 返回 [0, 1, 2]，匹配成功后 j 要回跳，不能直接归零。
  • 代理对：含表情符号的文本，返回的位置和 indexOf 一致，按码元算。

第三条最容易漏。很多实现匹配成功后把 j 置 0，普通的词看着没问题，一旦模式自身有重叠，就会少报位置。kmpAll 里那行 j = table[j - 1] 就是为它写的。

前两组防越界，第三组防漏报，第四组防编码假设。四组都不长，但把当年那个下午踩过的坑都圈进去了。

多个关键词，别一个一个跑

回到日志高亮。三个关键词各跑一遍全文，等于把文本扫了三遍。即使每次都是原生 indexOf，总量也上去了，何况每命中一次还要动 DOM。

我们最后的做法不是换算法，是换策略：一次遍历文本，同时记录每个关键词当前匹配到第几个字符，命中就记位置。这实际上是把多个模式的前缀状态并在一起，思路和多模式匹配算法一致；更正规的做法是建一棵字典树，把词表挂上去，一次扫描同时走所有分支。当期我们没有上那么重的结构，只做了”首字符索引 + 逐词验证”，在词表只有十几个、文本四兆的场景下够用。

这段代码的复杂度依然依赖 indexOf，最坏情况下退化成”每个首字符命中都做一次完整比较”。它解决的是”少扫几遍全文”，不是”单次匹配的下界”。我们把两件事分开算，才知道该优化哪一头。这段经历留下的判断顺序是：先看能不能少扫几遍，再看单次匹配能不能用原生，最后才考虑手写 KMP。顺序反了，就会像我那个下午一样，把时间花在不是瓶颈的地方。

收尾的表

场景 用什么 理由
在一个字符串里找一个词 原生 indexOf 实现经过优化，常数项小
找全部出现位置 indexOf 循环或 KMP 数据量小用前者，需要单次扫描用后者
文本分块到达、不能回退 KMP 文本指针只前进
大量重复字符的构造数据 KMP 避开朴素匹配的最坏情况
多个关键词同时找 字典树或多模式匹配 避免把文本扫很多遍
需要匹配中间状态 手写 KMP 原生方法只给起点

KMP 值得学，不是因为它该出现在每个搜索框后面，而是因为它把”失配之后还能利用什么信息”这件事讲透了。真正用的时候，先量一下瓶颈在哪；量完你可能会发现，最慢的那一步跟算法无关。
