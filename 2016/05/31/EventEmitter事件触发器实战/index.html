EventEmitter 事件触发器实战

上周三傍晚的一个改动，把线上服务打挂了。

一、事故：一个没人听的 error

2016 年 5 月 25 号下午五点四十左右，我把一个文件转码脚本接进了 Web 服务：来一个请求，读一个文件，转完写回去。脚本原本跑在命令行里，出错只打一行字。搬到服务上之后，我在包装函数里加了这么一句：

emit 是我自己写的一个小封装，就是 EventEmitter.prototype.emit。测试走的是”文件存在”那条分支，绿的；”文件不存在”我没跑。

第二天早上九点，同事说监控面板上昨晚有一段红色。我扒开看，服务在 18:03 重启过，标准错误里最后几行是：

进程退出码 7。同一份日志往上翻几十行，还夹着一句我没印象的提示：

Uncaught, unspecified "error" event 是 0.10、0.12 的措辞，4.x 仍会出现：emit('error', x) 没人监听时，x 是 Error 就直接抛 x，不是 Error 就套一层这个壳再抛。我传的是 err.message，走第二条路。

全貌是：emit('error', ...) 执行时那个 emitter 上根本没有 error 监听器（on('error') 挂在流上，emit 打在另一个对象上），Node 把它当未处理异常抛到栈顶，进程当场挂掉。那句泄漏警告，则是流量高时每个请求往同一个共享 emitter 上挂监听器攒出来的。

心里没底：这两件事是巧合还是同一个根因？跑一遍最小复现才明白，是两个独立的坑，一个关于 error 的语义，一个关于监听器的生命周期。

先划边界：本文只说 Node 这一侧的 EventEmitter，浏览器 addEventListener 那一套跟它不是一回事，这里一行都不涉及。

四、emit 是同步的：这决定了你所有的时序假设

这段是读 events 源码才确认的：emit 不是”发消息给事件循环、下一轮再处理”，它就是普通函数调用，按注册顺序在当前调用栈里把每个监听器同步跑一遍，全部返回它才返回。

三个推论：一，emit 的成本等于所有监听器同步执行的总成本，监听器里写个死循环，卡住的是调用 emit 的人。二，监听器里抛异常，emit 当场抛，后面的代码不再执行。三，顺序就是 on 的顺序，没有优先级参数。

还有个不对称：多于一个监听器时 emit 会先克隆数组再逐个调用，所以监听器里 removeListener 掉排在后面的那个，本次照样会调到。我第一次遇到”明明摘掉了却还是跑了”，排查了半小时。

五、监听器泄漏：那句 warning 到底在说什么

先给结论：Node 4 上你看到的原文是这样一整块，事件名不在里面：

默认上限 10 个，写死在 EventEmitter.defaultMaxListeners 上，同一个事件名下第 11 个监听器注册时打印一次。它只是打印，不改变行为，第 100 个照样挂上、照样跑。

我那天成因特别蠢：一个进程级 bus 被所有请求共用，每个请求都执行一次 bus.on('error', handler)，很快 error 上就是几百个同一份函数。压根没考虑这个 emitter 的生命周期比一次请求长得多。特征也典型：内存不立刻爆，但每次 emit 要同步跑几百个回调，接口越来越慢。

removeListener 和 setMaxListeners 解决的是两件不同的事，别混。前者解决”这个回调我用完了”：

必须传同一个函数引用。我那时 bus.on('error', function () {...}) 配后面一句 bus.removeListener('error', function () {...})，摘了个寂寞——两个匿名函数不相等，什么都摘不掉。这是泄漏最常见的写法，不报错、不异常，只是越跑越慢。

setMaxListeners(n) 解决的是”我确实需要超过 10 个”，比如连接池上挂几十个消费者。但它是提高报警阈值，不是消除报警：监听器数量随请求量线性增长时，调到 1000 只是把爆掉的时间往后推，属于拿它当遮羞布。我的顺序是先用 listenerCount 打点，不回落就是生命周期问题，改代码；确认稳定在高位、来源清楚才调上限，且调在具体实例上，不动全局默认值。

六、error 事件的特殊性，和它的兜底写法

error 是唯一的保留事件名，emit 里有一段专门针对它的分支：找不到监听器时不返回 false，而是抛出，这就是第一节事故的机制。其它事件名没这待遇，emit('typo') 没人听就静静返回 false。

继承 EventEmitter 的类只要对外 emit('error') 就等于埋雷：调用方忘了挂监听器，进程就没了。我的办法是不指望调用方，在工厂函数里先挂一个兜底：

代价要讲清楚：兜底一挂上，error 就永远打不挂进程，错误同时从”当场崩、日志带栈”降级成”一行 console.error”。还没接监控的老项目里我认，稳定优先；真需要报警的服务里我更希望它崩——悄悄打一行日志能拖三天。取舍点在于错误是否致命：致命就让它抛，非致命才兜底。在兜底监听器里再判断一次、遇到某类错误重新 throw，那是跟同步 emit 较劲，我不推荐。

七、once 的两个坑：不回收，和”只回一次”

第一个坑：once('error') 不会因为它是错误分支就自动回收。任务成功时 error 从没触发，监听器就一直挂着，listenerCount('error') 只增不减。我在轮询任务上写过共享 emitter 配 once('error')，一天几万次下来就是第五节那个警告。反方向也一样：once('end') 的摘除发生在第一次触发时，流被复用时第二次就没人在听了。

八、实战：把一个后台任务拆成三方

坑填完，我们把一个真实的东西挪到事件上：一个”导出报表”的后台任务。原来是一坨串行回调，拉数据的、转码写文件的、统计上报的，全在同一个函数里互相调用，改一处要看三处。拆成三方之后，它们只认事件名：

flowchart TD
  A[Producer 生产者
按页拉数据] -->|emit task:data| B[Consumer 消费者
转码写文件]
  B -->|emit task:written| C[Counter 统计器
计数与耗时]
  A -->|emit task:done| C
  A -->|emit error| D[兜底 error 监听]

实现（ES5，Node 4 直接跑）：

一是统计器的顺序：task:done 最后才 emit，可它触发时计数已经是 3——前面三次 task:data 的整条链全在那一次 emit 的调用栈里同步跑完了。”同步”在这里成了好处：不用额外等待，顺序天然是对的。

拆完最大的收益是加人不用改老代码：后来要加一个”每写满 100 页就上报一次进度”的角色，只需要 new Monitor(bus)，Producer 和 Consumer 一个字没动。代价是事件名成了隐式接口，拼错不报错。

九、真实重构之后踩到的三个新坑

上面那个任务不是玩具。原始版本是回调串了六层的服务：拉数据、鉴权、转码、切片、写盘、清理临时文件，每层把下一层当参数传进去。改成事件驱动后老问题消了一半，但立刻冒出三个新问题。

第一个，事件名拼错，静默失败。emit('task:writen') 少打一个 t，不报错、不崩、不写日志，只是没人干活，排查时只能抓瞎。事件名是运行期的字符串，Node 无从判断。防护两件事一起做：事件名收成常量，再包一层 emit，用返回值兜住。

emit 没有监听器时返回 false，这个返回值我从前从来没检查过。它分不清”忘了挂”和”本来就可以没人听”，但对 task:written 够用。

第二个，忘了 removeListener 导致重复消费。消费者重构成可重复调用的 attach()，某天热更新脚本调了两次，同一个 task:data 被处理两遍，文件写重复了。防护是让注册幂等，注册前先数：

第三个，状态重入：同一个事件被 emit 两次。task:done 在成功和超时两条路径里各触发一次，统计器打了两行，运维以为跑了两遍。防护是消费端加布尔门，让第二次进入留痕：

三个坑同一个根因：事件把调用关系换成了约定，而约定不会被运行时检查。事件好读，代价是要自己把约定钉死。

十、给事件加超时

事件驱动最难接受的是没有天然回调：发起方 emit 完就返回，任务成没成、什么时候成，它一概不知道。要一个”最多等 N 秒”的兜底，就得自己造一个临时监听器加一个定时器，两条路谁先到终点谁收尾：

三个细节我都踩过：removeListener 必须在两条路径上都调，否则回到第五节的泄漏；clearTimeout 忘了写，成功之后定时器照样点一次；unref() 不写，任务早结束了进程还活着。这里用 on 加手动摘除而不是 once，是为了超时时也能把成功监听摘干净。

5 月 22 号那篇讲回调的超时写法不重复，分工很清楚：回调的超时包在回调函数自己身上，只保护一次调用；wait 保护的是”某个事件到底会不会来”，管的是解耦之后的责任交接。

打一整天，只上不下就是生命周期问题，按第五节处理。其次是 console.trace，在监听器第一行加一句就能看清是谁在这次调用栈里 emit 的。

然后是 process.on('uncaughtException')。它当期确实能拦住没人听的 error，把进程从打挂里救回来，但立场要想清楚：它是兜底，不是方案。它一挂上，所有异常都不再终止进程，进程很可能停在内部状态已经坏掉的地方继续接活。我们只让它打日志、上报、主动退出，由部署那篇讲的进程守护拉起来。

最后是 domain。当期不少人拿它兜异步错误，但它官方文档里就明确写着不推荐、接口还在改。我用过一版，异常被吞成看不见的东西，后来整块拆掉了。反面案例，别当方案。

十二、一次 emit 到底贵不贵

写了个最粗糙的基准，扇出不同数量的空监听器，跑一千次 emit 计时：

这是同一台机器上的粗略观察：一台跑满后台任务的开发本，本机 Node 4，6.x 还没上生产，口径是 1000 次 emit 的总耗时，只用来判断量级。

结论两条。空监听器上 200 个扇出比 1 个贵几十倍，但摊下来单次 emit 是微秒级，事件机制既不免费也不贵。问题从来不在 emit：监听器里一做同步字符串拼接、同步写日志，量级立刻跳到毫秒。

十三、什么时候该用，什么时候别用

场景 该用 EventEmitter 直接回调更清楚 我们踩过的反例
一次调用一个结果 别用 一个 cb(err, res) 就能说清 换成事件后超时和重试散在三个文件里
一个动作多方关心 用，照第八节那样拆 每方都要传函数，签名越来越长 进度靠回调链上抛，加一个监控角色要改四层
生命周期比一次请求长 可以用，但必须自己摘 不涉及 请求级往共享 bus 上挂，攒到几百个
要把错误传给别人 只走 error 且保证有人听 错误直接给调用方更省事 第六节的兜底让一次故障安静了三天
事件名多到五六个以上 先收成常量再上 不涉及 task:writen 拼错一个字母，任务静默跑空

我的口径是：一条链说得清的调用关系就别转成事件，只有在”不知道谁会关心”或”不改老代码就要加一个角色”时才上。上之前先回答三个问题——这个 emitter 活多久、error 谁在听、监听器什么时候摘；想不明白，早晚回到第一节那段日志。
