Node.js 中的回调与异步流程控制

事故回放：三千个 id 一次性全发出去

2016 年 5 月 18 号下午，运营催一个批量导出接口。前一天临时加的：前端传一批用户 id，服务端逐个调第三方取明细，拼表落 CSV。本地拿两百个 id 跑过一遍，四五秒出结果，心里没底也没当回事。

上线后对方第一次点就传了 3000 个 id。我的写法是拿到数组一个 for 循环全发出去，回调里 push，凑够数再往下走。结果页面转了四十多秒，第三方返回大片限流错误，内容缺了一小半；进程内存涨到 1G 上下（同一台机器上的粗略观察，只有量级意义）。

根因不复杂：三千个请求同一瞬间打出去，配额不是我这边能定的；每个在途请求攥着一份响应体，堆起来就是内存尖峰。那之后我把”并发必须有上限”当默认前提。

本文只讲不引库时怎么写才对、怎么写会炸。库的 API 巡礼与选型、Promise 与生成器两条路线，2016 年 4 月那篇《Node.js 中的异步流程控制库》已写透，这里不重复；事件循环的阶段与队列另有专文，碰到机制只带一句。

先分清：这是写法问题还是配额问题

最容易犯的错，是把所有慢都当成代码写得烂，一路改写法，改三版发现耗时没动。区分办法很土但管用：把链路上每个外部调用单独拎出来跑一遍，测两个数——单发耗时，和同时发 N 个的耗时。

单发就慢，是下游慢或数据量大，改写法收益有限，该减调用次数、让对方支持批量、或者缓存结果。单发快、一并发错误率就抬头，是撞了配额，加并发只会更慢，得压下去。只有本地 CPU 占一大块，才是写法问题，循环里的同步操作、反复拼字符串、大对象拷贝都算这类。

再看错误长什么样：限流类成批出现、带明确状态码；超时类说明在途太久；内存告警或进程被重启，是持有数据太久。三类改法完全不同，抓瞎时先把错误分个类，能省大半无用功。

串行还是并行：先画依赖图

哪些能一起发，先把调用关系画成依赖图，一眼看出哪是链条、哪是扇出：

flowchart TD
  A[拿用户列表] --> B[查每个用户的基础档案]
  B --> C[查订单汇总]
  B --> D[查余额汇总]
  B --> E[查第三方标签]
  C --> F[拼装导出行]
  D --> F
  E --> F
  F --> G[写 CSV]

规则很朴素：同一节点的直接下游、彼此不读对方结果、也不共享要写的东西，就能并行。上图 C、D、E 互不依赖，同时取比排队快三倍；A 到 B 得先有 id 列表，B 到 F 得先有档案，这几步硬串行。还有一点容易看漏：只把单用户的三接口并行、用户之间仍排队，总耗时还是单用户耗时乘用户数——要并行的是”用户 × 接口”这个矩阵。

改并行前先答三个问题。一，下游配额：没给并发说明就按最小一档试，边加边看错误率。二，幂等：并行让重试机会变多，写操作要问同一请求发两次会不会留两条记录，扣款类得先确认有没有幂等键。三，结果顺序是否重要：要看顺序就不能谁先回来谁先写，得按索引回填。

递归回调推进长列表时的栈

列表类任务当期常用递归回调推进：处理完一个，回调里调自己下一个。列表短没事，长到几千上万就出事。我碰过两回：几千行逐行调接口，跑到两千多行报栈溢出；另一回没报错但内存稳步涨，扒开看是每层递归都把当行数据留在闭包里，栈不退引用就不退。

Node 4 默认栈深在几千层量级（同一台机器上的粗略观察）。异步回调链本来不撑栈，问题在同步分支：递归路径里只要有一条”没有真异步操作、当场调下一层”的分支——命中缓存、当行为空跳过——栈就一直往上叠，叠到上限就崩。

写法上记两条：每推进固定条数（我取一两百，看不出耗时差）就 setImmediate 让出一次，栈深被钉死在单批大小；让出时把当批局部变量释放掉。为什么让出就能放栈、内部怎么排队，机制见《JavaScript 事件循环机制解析》，本文只讲怎么写。

内存侧：闭包把大 Buffer 留住了

那次事故另一半原因在内存。每个任务的闭包捕获当次响应体，本意拼完就丢，但任务是一次性发出，三千份响应体同一时刻全是活的；更要命的是中间结果挂在模块级数组上，边完成边 push，函数早就返回了，那数组还攥着每份原始 Buffer。RSS 涨到 1G 上下就是这么来的（同一台机器上的粗略观察，只有量级可信）。

当期没有像样的堆分析工具，两个土办法都有效。一是用完置 null，转换完立刻断开对原始数据的引用。

看着多余，但长任务里确实让存活集变小——前提这变量没被别的闭包共享，否则置 null 只改了本地指针。二是分块取数：别把三千条一次揽进来，每两百条一批，一批落盘一次、清一次中间数组。

改完再看同一台机器上的内存曲线，峰值从 G 级掉到几百兆量级。问题一般不是”总量太大”，而是”活着的中间态太多”，压成滑动窗口就解决大半。

流式的边界

分块落盘要用流，只说两个写法后果。一是 write 的返回值不看、闷头往里灌：底层写得慢、缓冲堆起来，调用方不知道，上游就按自己速度继续生成，内存照旧涨——信号就在那个返回值上，看到 false 该停手等事件再续。二是在 data 回调里做重活：这条后面还有下一条排队，重活占住这一轮，后续数据全在内存里等处理，表现是延迟一层层往后叠、进程看着卡住。背压规则和 objectMode 交给流式那篇。

超时缺口：第三方挂住会把并发占满

限了并发之后没过两周，同一个导出又打挂一次。这回不是请求多发，是第三方一个接口整个卡住：不返回也不断开，请求就一直挂在途。并发额度是 5，五个格子全被挂死的占着，后面几千个任务排在永远不触发的队列里，页面转了一分多钟没结果，进程却什么错都没报。

当期 http 客户端的整体超时不好配。timeout 挂的是建立连接这件事，对方握手后拖着不发数据、或只发一半，它管不到；agent 上的超时也只覆盖 socket 空闲。所以只能自己包一层定时器：

called 跟 limitRun 里的闸门同理：定时器和响应回调谁先到算谁，另一边必须闭嘴，不然同一任务被 cb 两次，计数就乱。abort() 是关键——不主动断开，挂住的请求还占着在途名额，光报个超时没用。

timeout 到底覆盖哪一段别猜，当期验证办法很直接：本地起个故意不响应的服务器，收到请求后始终不 write，或写一半头部就停住，看自己的定时器有没有触发、timeout 事件有没有来，两种表现一眼能分开。整条流程外包一层超时、直接丢结果我也试过，那只救页面，不救在途。

错误处理的三条纪律

被吞掉的错误最难查。当期我定了三条纪律。

一，每个回调进门先看 err，非空就当场结束，别碰第二个参数。二，错误分支不要继续往下 emit：err 发出去后还接着发 end、或还往回调塞一份空结果，调用方就会既走成功又走失败，比不报错还难查。三，透传时保留原始 message，包一层可以，但得把原错误挂上去或拼进文案：

并发上限的默认值怎么定

最后说这个数从哪来。算法很朴素：先问下游总配额，除以我方实例数得理论值；再在同一台机器粗测，从理论值的三分之一往上加，每档跑一遍，看错误率和耗时拐点在哪，停在拐点下面留三成余量。对方给的是”每秒多少次”还是”同时在途多少条”，两种口径不能混着算——我一开始把每秒 20 当成在途 20，实际并发远高于预期，照样被限。

实例数容易忘掉：本地一个进程、线上四个，同一份配额就是四等分。所以这数不该硬编码，我做成配置项，压测改一行就能重跑。别指望固定数字，同一台机器上的粗略观察只能定量级，上限永远是配额除以实例数算出来的，换了下游就得重算。
