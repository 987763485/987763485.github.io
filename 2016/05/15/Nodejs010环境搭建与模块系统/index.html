Node.js 0.10 环境搭建与模块系统

一场 node -v 引发的事故

2016 年 5 月上旬，组里把我塞进一个 2013 年起步的内部后台项目，交代的话是”先把测试跑起来，再谈改代码”。这个项目我第一天就没跑起来。

它的 package.json 里躺着这么一行：

我当时心里没底，觉着 0.10 是上一代的东西，顺手装了 Node 4。npm install 一跑，带原生编译的依赖全挂：

扒开 buildlog.txt 看，满屏是 V8 头文件里的 Handle、Persistent 类型对不上——这些依赖的源码是按 0.10 那版 V8 接口写的，新头文件根本不认。折腾两天，我只能承认：这个项目的开发环境得照着 0.10 搭。

先把边界交代清楚。这篇只讲 Node 自己那套 CommonJS 实现在 0.10 上的样子，浏览器端模块化演进我不再巡礼；libuv 事件循环的阶段划分、宏任务微任务的先后留给事件循环那篇；fs 的 API 形态和编码权限另有专文，只在需要时提一句；Express 3 的内部结构是 2016 年 6 月那篇的事；进程守护和 PM2 属于运维那篇。

2016 年为什么还要搭 0.10

这不是怀旧，是几条很硬的现实。

第一，线上还在跑。生产机上是 2013 年装好的 0.10，运维排期排到第三季度，我一个小前端没资格单独提需求。本地换个大版本开发，等于亲手把”我这边好好的”和”线上跑不起来”之间的距离拉大。

第二，原生模块的 ABI 绑死。要 node-gyp rebuild 的包，编译产物直接对上某个版本的 V8 与 Node 内部接口，同一份源码在 0.10 上能过、在 4.x 上就编失败；反过来升依赖版本，又要牵连一串调用它的老代码。

第三，出问题要能原地复现。线上半夜打挂一个请求，手里没有同版本运行时就只能凭想象猜，这种抓瞎我上一周刚尝过。

第四，客户环境动不了。后台要交付给几家单位内网部署，对方机器上的 Node 是三年前的统一镜像带的，不可能要求每一家都升。

所以决策是：开发、测试、交付验证全部锁 0.10，同时把 4.x 当一条观察线，量新代码离它有多远。注意定位——0.10 在 2016 年绝不该是新项目的选择，它只是存量项目的维护线。

.nvmrc 里只写一行版本号，nvm install 不带参数时会读它；这文件跟代码一起提交，比口头约定可靠。

第二个坑：全局包跟着版本走。我在 4.x 下全局装了 gulp，nvm use 0.10 之后命令直接找不到——nvm 的每个版本是独立前缀，全局包不共享。要么各版本装一遍，要么 nvm install 0.10 --reinstall-packages-from=4，但混着旧全局包往往更添乱，我倾向重装后用 npm ls -g --depth=0 清点。

第三个坑：nvm alias default 0.10 要想清楚再敲，它改的是新 shell 默认落到哪个版本。我一度设成 0.10，结果所有新项目掉进旧版本，原生模块编挂、测试跑不动，两天没查出是 alias 干的；后来恢复成当期主线，只在项目目录靠 .nvmrc 切。另外 PATH 与 shell 的命令路径缓存会骗人：切换后 node -v 还是旧的，先 hash -r（zsh 是 rehash）再 which node，看它指向哪。

按事实列一遍：0.10 默认没有全局 Promise，0.12 起才默认可用；语法层面没有箭头函数、模板字符串、class、解构；Object.assign、Array.prototype.find / findIndex、String.prototype.startsWith、Number.isNaN 这批 API 全缺。补齐靠 es5-shim / es6-shim 一类兼容包，在入口最早处 require 一次：

同理，fs 的异步 API 想要 Promise 化得自己包一层（fs 的形态文件系统那篇讲过）；stream 的 pipe 不把源端错误传到目标端，两端各挂 error，漏一个就把进程打挂。再提醒一句 process.nextTick：它在 0.10 上的队列处理和后来不一样，递归能把 I/O 饿死——异步链全押在它上面时，压测会看到响应被拖住。写法上会踩到什么说到这，阶段归属留给事件循环那篇。

老项目的 npm 处境

0.10 随包带的是 npm 1.x，目录形态和现在完全两回事：每个包把依赖再装一层进自己的 node_modules，树嵌套到底，没有扁平化也没有 dedupe 命令。

这套形态有三个后果。第一，同一个包在树里出现很多份，各配各的版本，路径长得离谱——在 Windows 上部署过一次，深路径撞上线，我以为是代码坏了。第二，npm update 把整棵树重解一遍，装出来的和昨天不一样，我还看不出差异在哪。第三，老项目没有锁文件，package.json 只写 express: 3.x 这种范围，每次重装都在赌运气。

当期能用的锁手段是 npm shrinkwrap：把当时 node_modules 里那棵树的每层包名、版本、来源地址写进 npm-shrinkwrap.json，之后 npm install 照它还原，团队里不再各装各的。要讲清它锁什么、不锁什么——它锁依赖树的版本与来源，不锁 devDependencies（默认一并写进去，我装完手工删掉开发段），不锁安装脚本编出来的二进制，更不锁 Node 版本：同一份锁文件换个运行时，node-gyp 照样编挂。所以我的三件套是 npm shrinkwrap 加 .nvmrc 加下面的版本断言；锁文件生成后先跑 npm ls，确认没有 invalid 再提交。

CI 上是两条并行矩阵：0.10 是守护线，任何提交必须绿，它代表线上真实行为；4.x 是观察线，挂了不拦合并，只用来量升级距离有多远。当时用 Travis CI 的 node_js 列表把两个版本各跑一遍。差别主要不在业务代码，而在依赖装不装得上、测试框架跑不跑得起来。两条线结果都得贴进合并说明，不许只报”我本地能跑”。

模块系统：require 到底怎么把文件找出来

这才是本文的正题。Node 这套 CommonJS 实现和浏览器里加载器的差别，全在”模块从哪来、拿到的是不是同一个”两件事上。

module.exports 与 exports

每个文件都不是裸执行的，Node 把代码包进一个函数作用域，形参里有 module、exports、require、__filename、__dirname。规则只有一句：真正交给引用方的是 module.exports，exports 只是开局时指向它的对象。

那个经典失效就在这：一旦对 module.exports 重新赋值，exports 还指着老对象，此后往它上面写的东西全丢；反过来给 exports 整体赋值也一样断开，函数里的形参重赋值影响不到外面。两种方向的错我都见过，症状都是取回来是 undefined 或者半套。团队约定一个文件只用一种：导出单个函数或类走 module.exports =，多个属性走 exports.xxx =。

解析顺序与 module.paths

require('express') 这类裸名按三段找：先查内置模块名单，命中就用原生实现，不查磁盘；没命中就从当前目录的 node_modules 开始逐级向上拼父目录再试；带 . 或 / 前缀的直接按文件路径解析。后缀补全顺序是 .js、.json、.node。

目录式模块

require('./logger') 不带后缀也指不到文件时，Node 把这个目录当模块：先看目录里 package.json 的 main 字段，没有就退回 index.js，再试 index.json / index.node。main 指到 lib/legacy-admin.js 这种入口在老项目里是常态，动它等于动所有引用方的落点；我遇到过它指向已删掉的文件，报错只说 Cannot find module './utils'，一层层扒开看才看见是 main 的锅。另外 browser 字段只给前端打包工具在浏览器构建时换实现用，Node 运行时不认，别指望它在服务端做环境分流。

__dirname 与 process.cwd()

这两个是路径翻车的源头。__dirname 是当前文件所在目录，跟文件写死；process.cwd() 是进程启动时的工作目录，随你从哪儿敲命令而变。

真实翻车现场：本地从项目根起服务一切正常；线上部署脚本是 cd /opt/apps && node legacy-admin/bin/www.js，process.cwd() 变成 /opt/apps，模板和邮件签名文件全读不到，页面 500，日志只剩一句 ENOENT。同一份代码换个启动目录就找不到配置，是我修得最没脾气的一类 bug。规范定下来：模块内部相对资源一律 __dirname，只有读”用户传进来的路径”或项目根约定才碰 process.cwd()。

require.cache 与”热重载”的坑

模块第一次加载后，导出对象挂在 require.cache 里，同一路径再 require 拿到同一引用——这就是模块级变量能当单例状态的原因。有人据此做”不重启就生效”：

三个坑。第一，key 是绝对路径。写 require.cache['./routes'] 什么也删不掉、还不报错，让人误以为生效了，务必用 require.resolve 取 key。第二，删父不删子：./routes 自己 require 进来的模块还在缓存里，模块级状态、注册的监听、定时器一概不重置，重载两次拿到的是新外壳包旧状态，比不重载还怪。第三，线上千万别这么干——旧闭包和旧句柄没人回收，同一台机器上粗略观察，几十次重载后内存一路涨、文件描述符下不来；开发期想看效果就重启进程。

第二条治标，改完还是互相知道对方，能拆就拆。真出现 undefined 又找不到源头，我在顶层打一行 console.log(Object.keys(exports))，用土办法确认拿到的是不是空壳。

0.10 到 4.x 的升级阻障表

观察线跑了两周，挡在中间的坑大致是这几类，按动手先后排：

阻障 0.10 这条线上的现状 上 4.x 要动什么
原生模块 按当期 V8 接口写死，node-gyp 编译就失败 换仍在维护的版本或补兼容层重编，逐包试
npm 形态 随包是 npm 1.x，嵌套安装、没有 dedupe Node 4 带 npm 2，Node 5 起内置 npm 3 才扁平化与 hoisting；树一变，靠相对路径摸兄弟包的代码要重看
Promise 假设 全局没有 Promise，靠兼容包或自带实现 4.x 有原生 Promise，混用时的 thenable 行为差别要跑一遍
模板引擎与中间件 写法挂在主包里 早拆成独立包，require 路径与初始化两处都改
测试框架 老 API 与配套断言库 升级带破坏性改动，用例得改一轮
process.nextTick 递归能把 I/O 饿死 队列行为不同，压测重做

最后的折中

这个项目最终定的结论是：继续锁 0.10，只打安全补丁，今年不升。判断依据三条——业务不再加新功能、只在几家内网单位手里、依赖树里那两个原生包源码已经没人维护。硬升等于把风险从”版本旧”换成”业务坏”，后者更难交代。

兜底措施跟着一起定：engines 与 .nvmrc 不许改；服务只监听内网地址，入口做参数校验；依赖冻结在 npm-shrinkwrap.json，装不上就原地排查而不是随手升版本；每次只升带安全修复的那一个包，升完在 0.10 守护线上跑一遍再合。监控和进程守护另有一篇运维文，这里不展开。真正的升级留给下一次带前端重构的窗口一起做，那时改模板和改中间件的痛能一次付掉。

哪些项目该锁 0.10，哪些必须走 4.x

情况 结论
有原生模块且上游无人维护、客户环境动不了 锁 0.10，只打安全补丁
纯 JS 依赖、没有 node-gyp、近期不再改 可以先升到 0.12 这条维护线
还在加功能、要上 ES6 语法和新工具链 4.x，当期主流是它
新项目 4.x，0.10 不该出现在这里
要接外部服务的新 SDK 4.x，旧线的兼容成本一年比一年高

Node 6.0.0 是 2016 年 4 月底刚放出的，我还没把它上生产，本文升级判断只算到 4.x 这条线。这个老后台什么时候能摘掉 engines 里那行 0.10.x，得等运维排期和依赖维护同时凑齐；在那之前，把 0.10 环境搭准、把 require 解析吃透，是我每天真正能使上劲的地方。
