Socket.io 实时通信实战

从一次 F5 开始

2016 年 4 月中旬，组里那套内网工单系统摊上了件事：新工单派下来，页面不会自己变，非得按一次 F5 才看得见。毛病不致命，但架不住人多——组里三十来号人，每人一小时刷十来次，运维群里抱怨了两周，而刷新间隔里进来的单照样没人认领。

我的第一反应是把轮询改成五秒一次，一个 setInterval 就完事。试了两天就打挂了：三十来个人每五秒拉一遍列表接口，日志里同一条查询刷屏，响应从几十毫秒拖到两百多毫秒。于是我决定认真试一次长连接。

先声明边界：事件循环阶段与 nextTick、微任务在《JavaScript 事件循环机制解析》讲过了；HTTP/1.1 单域名六条并发连接性能篇讲过了；EventEmitter 自身的 API 与 error 语义另有专文；Express 中间件队列不是本文重点（io.use() 看着像，跟 Express 那套没关系）；进程守护与 nginx 部署配置留给后面那篇运维文章，本文只讲到”为什么多进程会坏”这一层。剩下的篇幅花在机制上：socket.io 分几层、每层管什么、出事扒开看哪一层。我这一年正把零散脚本换成工程化流程，更在意换个人接手能不能跑一遍就懂。

为什么不裸用 WebSocket

原生 WebSocket 在 2016 年这个节点上，可用性远没有文档写得好看。当期 IE 10/11 的实现是残缺的：二进制帧支持磕磕绊绊，一些边缘场景拿不到 close code，帧大小限制还卡在实现里；Windows XP 上的 IE 8/9 干脆没有。移动端，Android 4.4 自带 WebView 的内核还在 Chromium 33 一线，WebSocket 能用，但后台 tab 被系统冻结之后连接会静默断掉，前端完全抓瞎。

更麻烦的是原生 API 只管”连接建立之后”，建立之前和断开之后全留给你：

  • 断线重连：原生没有，得自己写 setTimeout 加退避，还得防重连风暴把服务端打挂；
  • 降级：被代理或防火墙拦掉时要能退回长轮询，等于自己实现一套轮询协议；
  • 心跳：公司代理、负载均衡任何一层设备都能悄悄掐掉”看起来还活着”的连接；
  • 粘性与多进程：一上线就要面对”这条连接到底在哪个 worker 上”。

这四件事凑一起，工作量比业务代码还大。engine.io 把传输层的脏活收走了：可用时上 WebSocket，被拦掉就自动退回长轮询，心跳、重连、分包都归它；socket.io 再在上面加一层协议，管房间、命名空间、带回调的 emit。本文按 socket.io 1.4 一代的写法记，engine.io 是 1.x。

最小可跑

第一步只要求”能连上、能收到一条消息”，别急着上房间和鉴权。服务端最关键的一点：挂在原来那个 http.Server 上，不要让它另起端口。

io.listen(server) 是我踩过坑的地方：让 socket.io 自己开端口（写成 socketio.listen(3001)），页面请求立刻撞同源——端口不同即是不同源，跨域要额外配 CORS；cookie 也别扭，端口不同 session 传不利索，鉴权做到一半才发现服务端拿不到工号。

这个路径由服务端动态提供，客户端拿到的永远是服务端那一版库。手抄 CDN 版本号是埋雷：服务端升了、客户端还是老版，协议对不上的报错极难定位，往往表现成”一直 polling 不 upgrade”。让服务端发文件，两边版本天然一致。

连接生命周期

当期客户端的事件顺序大致是 connecting 到 connect，断开时先来 disconnect，然后是 reconnect_attempt、reconnect 或 reconnect_failed。重点在 disconnect 的原因参数。

这些原因能区分不少东西：io client disconnect 是页面自己调的断开，属正常；forced close 是服务端踹人，多半进程重启过；ping timeout 是心跳没等到回音，通常中间设备掐的；transport not supported 与 client not handshaken 卡在握手，去看鉴权和降级。

重连参数我最后定成：

reconnectionDelay 是初始等待，之后按指数退避往上翻，reconnectionDelayMax 封顶，randomizationFactor 让每台机器的间隔左右抖动，免得三十几台同时醒来冲击服务端。reconnectionAttempts 设 8 是我拍的数：排下来大约半分钟，半分钟还连不上基本不是客户端的问题，继续重试只会把标签页变成重连机器，不如放弃并提示刷新。

有一次排查让我对”掉线”改观。页面看着还在已连接，列表却不更新，我扒开看了一下午，最后发现连接活得好好的、服务端也在 emit——问题在我这边监听的名字写成 ticketNew，服务端发的是 ticket:new，统一事件名时漏改一处。名字对不上不报错，它就是订阅，没订到就静默丢掉。教训是怀疑掉线之前，先在服务端 emit 处加行日志确认消息发出去了、名字是什么。以为掉线其实没掉，是这类问题里最常见的一种。

心跳与代理超时

engine.io 的心跳靠两个参数配合：约定的 pingInterval（1.x 默认 25 秒左右）和 pingTimeout（默认 5 秒）。服务端每隔一个周期发探测包，超过 pingTimeout 没等到回应就把连接判定为死掉并断开。数字不难改，难的是它和中间那层代理的关系。

工单系统前面挂了 nginx，反代的就是 101 那个升级响应。proxy_read_timeout 默认 60 秒，指两次从后端读到数据之间最多等多久。心跳 25 加 5 看着够不着 60，真正出问题的是轮询降级那条路：连接退回长轮询后，没消息时服务端会挂住请求等数据，这个”挂住”在代理眼里就是后端迟迟不返回，60 秒一到 nginx 切断，客户端断开重连、重连再降级。当时的现象是每隔一分钟准时掉线，reason 是 ping timeout，心里完全没底，直到把 access log 的时间戳和掉线时间戳对到同一秒，才确认是代理先动手。

处理是代理侧读超时抬高到心跳周期的两三倍，同时把 pingInterval 显式写死，不依赖默认值。

消息可靠性

emit 默认不可靠：没有回执，发出去就发出去了，客户端那一瞬间正在重连或切页，消息就永远丢了，服务端一无所知。服务端 handler 的第二个参数是回调，客户端 emit 的最后一个参数是函数时，socket.io 自动编一个 ack id 塞进包里，服务端调用回调时把 id 带回来对账。

ack 只解决”有没有收到”，不解决”收到几次”。重试三次意味着服务端可能被同一条消息打三次，认领重复执行会造成两人抢同一单。所以每条消息带 msgId，客户端再去重：

msgId 必须由服务端生成且唯一，我用的自增 id 在多实例下会撞号，这点和下一节连着。

namespace 与 room

一个连接口服务好几种业务时用 namespace 切开。io.of('/ops') 得到独立命名空间，有自己的 connection 事件、中间件和房间表，客户端写 io('/ops') 连它，互不打扰，不用靠事件名前缀防碰撞。房间是命名空间内部的分组，本质是服务端内存里 socket id 到房间名的映射，客户端不参与。

in(room).emit 只发这个房间。房间名 join 之后改不了，换组只能 leave 再 join，两步之间掉线会留下脏映射，所以我包成 switchQueue 一个入口。

有一次”没人收到”折腾我大半天：emit 前打了日志，消息确实广播了，发的房间是 queue-1，join 时拼的是 queue:1。发错名字不报错，in() 匹配到零个 socket，emit 静悄悄完成，两端都觉得自己没错。后来 emit 前用 ops.clients() 查数量，为 0 就打警告，房间名也定死只能由一个函数生成。

握手鉴权

鉴权要卡在连接建立之前，不能让没工号的人先把连接占上再靠事件校验。io.use() 在握手阶段跑，一次性，不像事件那样反复触发。

后续所有事件都能拿到这份身份，不必每条消息带工号。一个坑：跨域时浏览器不带自定义头，headers['x-emp-id'] 拿不到，只能退回 query 参数；同源时头更方便，它不进 access log。

connect_error 这一代还没有，中间件抛错在客户端就表现为 error 事件，err.message 是服务端那个字符串。别原样显示给用户，跨版本包装类型不一致，只认前缀更稳。

扒开看：两层结构

出问题该看哪一层，取决于这两层各管什么。engine.io 管传输，socket.io 管协议，中间靠一个 ondata 的口子接起来。

flowchart TD
  A[业务代码 emit on] --> B[socket.io 协议层]
  B --> C[engine.io 传输层]
  C --> D[WebSocket 帧]
  C --> E[HTTP 长轮询 GET POST]
  D --> F[nginx 反向代理]
  E --> F
  F --> G[Node 进程]

engine.io 做的事：探测可用传输，先按 polling 起步再尝试 upgrade 到 websocket；维护 sid 会话；把一次 payload 切成”总片数-序号-类型”的分片帧，二进制靠它封装；跑心跳。socket.io 在它上面加的是消息语义：包类型字节、namespace 路径、ack id。一条 ticket:new 到传输层只剩 message 帧里的一个字符串。namespace 是包体前缀的一段路径，房间完全不下线，只活在服务端内存，网络上仍是逐个 socket 单独投递。

upgrade 这步抓包最直观，这是我在内网机器上抓到的请求头：

EIO=3 是 engine.io 协议版本，sid 早在轮询阶段就分配好了——websocket 这条不是新连接，是拿着 sid 换传输。Connection: Upgrade 与 Upgrade: websocket 两行合起来才是完整声明：前者说这条连接要换传输协议，后者说换成哪个。Sec-WebSocket-Key 名字带 key 却不是密钥也不是凭证，只是一个随机数的 base64；服务端把它与固定字符串拼接后算一次摘要回填到 Sec-WebSocket-Accept，用来确认对面看得懂这套握手，把不认识这些头、只会原样转发的中间设备筛掉，鉴权一点不靠它。服务端回 101，之后这条 TCP 上不再是 HTTP 文本。

排错先分层：抓不到 101、一直停在 polling，查 engine.io 和代理；101 之后收不到消息，查 socket.io 的事件名、namespace、房间。

多进程为什么坏

单进程跑到两百多个连接时，一次广播已经开始拖响应。想靠 cluster 开几个 worker 分担，机制上立刻撞墙：一条 socket 是 TCP 连接，只落在某一个 worker 的某个 fd 上，房间表和 sid 映射也都是各进程内存里的私有对象。在 A worker 上执行 io.sockets.emit，B worker 上的三十个人一个都收不到，广播打不全，而且没有任何报错。

补的方向有两个。nginx 侧 ip_hash 让同一台机器始终落到同一 worker，解决重连之后房间没了、客户端库版本对不上，但它是粘性不是广播，跨 worker 依旧发不到。真让广播打全的是 socket.io-redis 这类 adapter：每个 worker 订阅一份 Redis 的 channel，emit 时本地发一份、往 channel 发一份，别的 worker 收到再转给自己挂着的 socket。代价是多走一跳网络、房间状态要序列化、并发下仍有毫秒级乱序。部署配置留给后面运维那篇。

广播的量级

io.sockets.emit 是无条件全量，一次调用发给每一条连接；in(room).emit 只发命中的人。

我拿一个脚本起了几百个客户端跑了一遍，下面都是同一台机器上的粗略观察，不算基准数据：虚拟机、Node 4 单进程，三百来个连接时，一条两百字节的 JSON 全量 emit 大约四十毫秒才写完最后一个 socket；同一条消息只发进一个三十人的房间，耗时几乎感觉不到。连接数翻到八百，全量广播时 CPU 明显吃满，接口响应从几十毫秒涨到几百毫秒，进程内存一路往上爬。结论粗糙但够用：消息一多，先把 emit 收到房间粒度，别无脑广播。

开销大头不在序列化：编码一次 emit 只做一次，贵的是每个连接各付一份写缓冲。

排错对照表

症状 原因 处理
一直 polling，不 upgrade 代理不认识升级头，或两端版本不一致 补代理配置；库改由服务端提供
每分钟准时断开重连 代理读超时短于心跳周期 抬高读超时，显式写死心跳
房间消息收不到 房间名拼错，匹配到零个 socket 房间名由函数生成，emit 前查数量
鉴权失败还能连 只在事件里校验，握手阶段放行 校验挪进握手这一步，失败抛错
切回页面就断 后台被冻结，心跳没等到回音 监听页面可见性变化后主动重连

什么时候不该上长连接

长连接不是默认选项，新项目先过这张表再决定。

场景 代价 当期更合适的做法
一天变几次的低频数据 白养几百条连接 定时任务加轮询
公司代理拦升级 退化成轮询，请求比 REST 还密 走普通接口轮询
弱网移动端 重连风暴、后台冻结、费电 拉取为主，别挂常连
消息不能丢也不能重 ack 只到”收到”这一层 落库加接口重试
只需打开时最新 复杂度全花在没人看的推送上 首次加载查询

工单页正好在中间：变化不算频繁，但每次都要人在场才不漏单，这才轮到长连接。
