Node.js 部署与 PM2 进程守护

凌晨三点半，没人知道进程已经死了

2016 年 5 月中旬的一个周四早上，运营过来拍桌子：昨夜开始，报价单导出页面一直在转圈。那是一台 2 核 4G 的 CentOS 6 虚机，跑的就是一个 nohup node app.js & 起的 Express 应用，输出重定向到 app.log。ssh 上去 ps -ef | grep node，进程不在了。日志翻到底，最后一行是 FATAL ERROR: ... process out of memory，时间戳凌晨三点四十几。从挂掉到第二天上午，七八个小时没人知道。原因扒开看，是导出接口一次把整张表读进内存，跟部署方式无关。真正让我心里没底的是另一件事：服务能不能活，全看有没有人恰好在那个点打开页面。

同期还搭进两起。一起是改了代码忘了重启，线上跑的还是旧逻辑，最后靠重启机器才恢复；另一起是例行维护重启后，nginx 自己起来了，Node 服务没起来——因为压根没写开机自启。三起事故指向同一个缺口：nohup 只负责把进程扔到后台，不负责它活着。

先把边界说清。Socket.io 多进程下的广播与适配器，5 月 10 日那篇已讲，本文只留部署侧要开的这一行 nginx 配置；Express 中间件的六个坑是 5 月 24 日专文，这里只用一句”模块级变量在多实例下各算各的”；nvm 装老版本在 5 月 15 日那篇，libuv 在事件循环篇，产物缓存与静态化各有专文，都不重讲。这篇只谈一件事：怎么把一个 Node 进程放到机器上，让它活得久、看得见、起得来、换得掉。

当期能用的候选，一个个过

nohup 加一段 shell。最省事，也最脆弱。我们写过一版 start.sh，判断完端口占用再包一层 while true; do node app.js; sleep 2; done。进程死了确实会再来，但它不懂为什么死：启动即崩时这个循环刷屏刷到磁盘吃紧，机器重启它自己也不在。

forever。公司另一个小接口用的是它，强在会重启、能记 pid。但它只管单进程，多核要手动开多份；日志切成一堆带时间戳的文件，翻着抓瞎，也没有查询接口。

Node 自带的 cluster。主进程 fork 出跟 CPU 数一样的 worker，共享同一个监听端口。它解决多核，不解决挂了拉起，更不解决开机自启，业务入口还要改代码。

upstart。CentOS 6 的 init 就是它，写一份 /etc/init/app.conf，start on startup 加 respawn，拉起与自启一次覆盖。缺点是语法隐晦，日志只能指到一个文件，CentOS 7 上已经不是它了。

systemd。CentOS 7 才是 systemd，Restart=always 配 RestartSec，写得比 upstart 清楚。问题是当时那批老机器大半还是 6，一份逻辑要在两个发行版各维护一版。

supervisord。Python 那一套，进程组、日志轮转、web 界面都齐，跨语言是最大优点，运维同事本来就熟。减分项是多一个环境依赖，且它管进程不管 Node 的多核，还得配 cluster。

nginx 反代加手工多实例。开 4 个进程监听 4001 到 4004，upstream 里写四行。端口冲突没了，负载也分开了，但进程列表是手抄的，加一台机器要改两处，重启仍要靠上面那些脚本。

Docker 当时是 1.10 一线。我确实拿它跑过两天，结论放在最后一节，不写成展望。

PM2 上手：我们真用到的那几条

先在项目根目录试 pm2 start app.js -i 0。-i 0 是按 CPU 数开 worker，2 核 4G 上就是两个进程，这一步把 cluster 那段入口代码省了。之后每天用的就四条：pm2 list 看状态，pm2 logs 看输出，pm2 restart 整个换一遍，pm2 reload 一个个换。restart 会让服务空白一小会儿，reload 不会；改配置换依赖用 restart，日常发版用 reload。

开机自启最终靠两步：pm2 startup 生成一份 upstart 或 systemd 的启动脚本（CentOS 6 出 upstart，7 出 systemd，这一步只是生成文件并回显一条要你复制执行的命令），pm2 save 再把进程列表冻到 ~/.pm2/dump.pm2，重启后守护脚本读这份 dump 恢复进程。坑我们踩过：只 startup 不 save，或者 save 之前新加的服务还没 start 上，重启后就是空的。

cluster 与 PM2 怎么分工

划分很简单：多核交给 PM2 的 -i，不再自己写 cluster 入口。-i 0 按 CPU 数开 worker，2 核 4G 上开 2 个；写死 -i 4 也试过，结果只是 RSS 涨、请求排队，所以原则是 worker 数不超过核数。worker 之间不共享内存，同一个模块在每个进程里各加载一份，模块级变量也就各算各的——Express 中间件那篇里那个计数器就是这个坑。要记住的是：任何进程内的状态都不是全局的，做统计要么落库要么走 redis。端口复用由主进程负责，它拿到监听句柄再派给子进程，机制细节在事件循环篇。已经写了 cluster 入口的应用，把那段代码摘掉，只留 app.listen，让 PM2 去 fork。

零停机 reload 的真实代价

pm2 reload quote-api 是逐个 worker 换：起一个新的，接过来，再等老的把手上请求跑完后退掉。代价有两条，我们都被咬过。

第一条是内存。切换那一刻新老 worker 同时在世，2 核 4G 上原来两个各 300 多 M，reload 时瞬间变四份，峰值接近 1.3 G，这是同一台机器上的粗略观察。内存本来吃紧的话，reload 等于自己触发 OOM，比原来的事故还难看；只能挑低峰发版，或先把实例数减一半。第二条是老 worker 退不掉：只要还挂着一条没断的连接，PM2 就得等。我们那个页面有长轮询，一次 reload 后 pm2 list 里老进程长时间停在 stopping。解法不在 PM2 上，在应用要有超时、反代别把连接拖太长。

长连接多进程要粘性会话和广播适配器，那套东西 5 月 10 日那篇讲完了，本文只留部署侧这一行：nginx 的 upstream 里加 ip_hash，让同一个用户落回同一个 worker，否则长轮询会随机拿到不同进程的会话。

copytruncate 是关键：PM2 握着文件句柄，若用默认的 rename 再新建，日志会继续写进那个已被改名走的旧文件，新文件一直是空的。我们一度想靠 pm2 delete 再 start 来释放句柄，后来发现那等于每次轮转都把服务重启一遍。

应用侧的取舍是另一件事。一开始我们用 morgan 把访问日志写到 logs/access.log，加了 worker 后两个进程写同一个文件，行会交错，看着像乱码。最后改成 morgan 只输出 stdout，文件交给 PM2 接、轮转交给 logrotate：应用少一套文件逻辑，多实例同写一个文件的问题也没了，代价是访问日志和其他 console.log 混在一个 out 文件里，grep 得靠关键字。

开机自启这一步为什么老是起不来

第一次配好 pm2 startup 后重启验证，pm2 list 是空的。翻 upstart 日志只有一行 /usr/local/bin/node: No such file or directory。原因扒开看：startup 生成的脚本按绝对路径执行 node，而那个路径取自生成脚本那一刻的环境。我们的 node 是 nvm 装的，登录 shell 能用是因为 .bashrc 改了 PATH，守护脚本不走 .bashrc，两边不是同一个 PATH。那两天只能把 pm2 describe quote-api 和 pm2 env quote-api 的输出抄在本子上对，才发现登录 shell 的 PATH 和进程实际拿到的差了两段——当时没别的手段，就是抓瞎式一条条查。

当期只有两种可靠解法。一是写绝对路径，把解释器固定到 nvm 下那个具体版本，别指望默认 node。二是把 PM2 本身指到同一版本：切好版本再 pm2 delete、start、save，保证守护进程和 worker 用同一个二进制。混着用最糟——守护进程挂在 4.x，脚本里又叫 0.10 的 node，报错完全不指向真原因。还有一点：startup 回显的那条命令要手工用 root 执行一次，漏了就是脚本生成了但服务没注册。

nginx 是 1.8 一线，我们最后落到这么一段，只保留真正解决问题的几行：

几个点。X-Real-IP 和 X-Forwarded-For 不传，应用日志里全是 127.0.0.1，那次排查我们连是哪个客户在打导出都不知道。client_max_body_size 默认 1m，附件上传被 nginx 413 挡掉，报错到不了 Node。proxy_read_timeout 是长轮询的生命线：应用侧超时 70 秒而 nginx 只等 60 秒，永远是 nginx 先断开。静态目录走 alias 由 nginx 发，别让 Node 读磁盘上的 js 和 css——产物命名与缓存在构建产物篇，静态页搬走在静态化篇，这里只记一句：同一台 2 核 4G 上，静态文件归 nginx，Node 的 CPU 才留给接口。

灰度与回滚：两台机器加一次摘流

线上只有两台机器，能做的是最土的灰度：两台都在 upstream 里，发布时先摘掉一台。五步固定。一，备份，上一版目录 cp -a 成带时间戳的副本，代码不到 100 M，成本可忽略。二，只发 A 机，pm2 reload，再从公司网外 curl 健康检查接口，接口里只读一个 DB 计数和一个内存水位，非 200 就停手。三，把 A 加回 upstream，nginx -t 通过才 nginx -s reload，观察 error 日志五分钟。四，同样发 B 机。五，回滚触发条件：健康检查连续两次失败，或 error 日志里同一个异常一分钟内超过十次，就把这台从 upstream 注释掉，另一台顶上，同时把备份目录 mv 回来再 pm2 restart。全程最快六分钟。前提是两台代码互不影响，带状态的活儿得先挪出去。

关于 Docker，当时的判断不漂亮

2016 年上半年我们用 1.10 把两个小服务装进去跑过，三个问题很实际。镜像体积：带编译工具链的基础镜像拉下来 700 多 M，加上 node_modules 随便上 G，机器间分发只能靠 tar 拷。内核：CentOS 6 那批机器内核太老，跑起来莫名其妙，7 上面才正常，而我们主力是 6。内网拉取：registry 在公司网络外面，一次 pull 十几分钟还经常断，自己搭又是一摊事。所以结论不是”以后要上”，而是一句范围明确的话：2016 年这套东西，新起的独立服务可以试，已经有用户、依赖本机日志路径和老内核的服务不上——容器带来的可复现性收益，抵不过它在老发行版上排查问题的成本。

结论表

场景 我们当时的选择 理由
手上只有 CentOS 6 的机器 PM2 管进程，upstart 管开机 不改代码就能多核
CentOS 7 的新服务 PM2 加 systemd 配置比 upstart 好读
只要多核、不要别的 cluster 自己写 少一个外部依赖
运维已经管别的项目 supervisord 跨语言和轮转现成
内存已经吃紧的应用 别用 reload，改低峰 restart 瞬时翻倍会自己触发 OOM

最后留一句踩完全程才写下的话：PM2 只解决进程活着，不解决服务可用。它能让崩了的 worker 几秒后回来，能开机自启，能接住日志，但内存一直涨的那个接口、超时链没对齐的反代、没有健康检查就切流量的发布脚本，它一样都管不了——可用性是这三件事叠出来的，进程只是最下面一层。那台 2 核 4G 后来还是被 OOM 打过一次，只是这次是凌晨四点零二分，pm2 list 里多了一行重启计数，而我在告警里先看到了它。
