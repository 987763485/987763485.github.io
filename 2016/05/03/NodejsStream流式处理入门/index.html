Node.js Stream 流式处理入门

四月刚过完一个加班的夜。组里那个小脚本白天被排在一边没人敢动：夜里把各服务落的日志转码合并成一份，开发机上跑得好好的，搬到线上当晚进程就被 kill，运维贴来 dmesg 截图，里面明晃晃一行 Out of memory。回头读代码，元凶就一行：fs.readFileSync 把每个日志文件整个读进内存，再拿字符串加号拼起来。单个文件几百兆，机器内存一共 1GB，几个文件叠一块，堆先撑不住，内核挑了最肥的那个进程下手。

修的方向当然不是换台大内存机器。这件事让我第一次认真去看 node 里的流，它的唯一存在理由一句话就能说完：不要等所有内容到齐才开始处理。数据分段到达，处理一段消耗一段，内存里始终只驻留当前这一小截。听起来简单，真把管道搭起来，坑全在第二层：数据是怎么被要出来的、对方消费不过来谁负责、错误为什么要每个流单独管。这篇把这几件事一次说清。版本口径先立好：我们线上跑 Node 4 LTS，Node 6.0 上周刚放出，V8 升级带来的原生语法更完整，但生产不可能立刻切过去，示例一律按当期能跑的写法来。

四种流，先把名字和职责钉住

Stream 这个词在 node 里其实指向四个基类。Readable 管读，数据从源头进管道；Writable 管写，数据从管道出去落到底层；Duplex 是双工，两头都能走；Transform 是一种特殊的输出由输入换算而来的流。

要点在于这四个都是基类，业务里你几乎不直接构造它们，拿到手的都是实例：fs.createReadStream 回来的是 Readable，fs.createWriteStream 回来的是 Writable，zlib.createGzip() 是 Transform，喂进明文吐出压缩字节，进什么出什么；net.Socket 是 Duplex，TCP 的收发是两条腿，一边被塞数据不影响另一边被消费。Duplex 和 Transform 常被混着说，一句话分开：Duplex 是两条独立的腿，读写互不推导；Transform 是换算，输出必须由输入算出来。名字钉住之后，下文讲”读”都发生在 Readable 端，讲”写”发生在 Writable 端，中间的加工归 Transform。

然后是那个著名缺陷：pipe 不转发错误。error 事件不顺着管道走。上游读到一半磁盘出错，它自己 emit 了 error，下游的写流毫不知情，半截文件就躺在那里，进程退出码还是零。我们那次日志归档被截断就是这么来的，事后看修复方式土得可以：链上每一个流都单独挂 error 监听。

当期社区的标准解法是靠 pump 那类第三方小工具：一次把错误挂到链上所有流，出错时把管道拆干净再把错误交给你，当时大家普遍用它代替裸 pipe。要说清楚的是，收口这类事情靠的都是第三方库，内置的 pipeline、finished 这类helper这时候还没有，2016 年只能自己写或者引库。

读的两种模式：data 驱动与 readable 驱动

Readable 端的数据有两种到达方式。第一种是数据驱动：挂上 data 和 end，node 自己往你手里塞，每个 chunk 到齐触发一次 data，源头读完触发 end。写法最省事，处理是同步的时候没有问题。第二种是可读驱动：监听 readable 事件，在事件里自己调 read 按需取。

第二种模式的价值一句话：你能决定一次取多少，于是背压上你有了主动权。消化不动就不调 read，数据停在流的内部缓冲里；加工完了再取，这就是按需取。data 模式是你被投喂，readable 模式是你去取。

经典陷阱恰恰出在 data 模式碰上异步处理。一旦挂了 data，流进入 resume 状态，除了你显式 pause 它不会停；如果你的处理是写库、发请求这种慢活，数据到达比处理快，内存照涨，流等于没救场。当时常见的土办法是在 data 事件里自己暂停：

能用，但粗糙得明显：这个 chunk 已经到了你手上才 pause，缓冲早先就发生在流内部，你只是挡住了下一批；取多少的粒度被事件锁死；错误分支忘了 resume，管道就永远挂住。处理一旦是异步的，正经姿态是换可读驱动，每次取自己消化得动的量。

背压讲到底：两个返回值

背压说得玄，拆开就是两个返回值。读侧：流的实现内部调 push(chunk)，返回 false 意味着内部缓冲已经越过阈值，生产者该歇一歇，等消费追上再继续产。写侧：write(chunk) 返回 false 意味着底层缓冲满了，应该停下，等 drain 事件再继续写。

highWaterMark 该设多少

先纠正一个流传很广的误解：highWaterMark 是缓冲阈值，不是”一次读多少”的保证。它决定的是生产者该不该歇，并不承诺你每次拿到的 chunk 正好是这个大小。

默认值很小，而且文件流和 socket 流不一样，字节流按字节比，对象流按个数比。调大意味着用内存换吞吐：生产和消费的唤醒轮次少，缓冲队列长；调小意味着轮次多、驻留浅。

当期可执行的判断是：内存敏感的环境优先调小，小机器、一次并发握着几十上百个流的场景，阈值会被并发数乘成驻留；纯吞吐的批处理可以调大。但不要凭感觉把它调到几兆，然后指望这能减少磁盘次数——每次从磁盘取多少不完全由它决定，调大往往只是把内存驻留抬高。改之前先量，别改完靠想象验收。

objectMode：流里跑对象

流默认只装得下 Buffer 和字符串；构造时传 objectMode: true，chunk 就可以是任意对象。要点三条。

第一，read 的语义变了：普通流里 read(n) 是”给我 n 个字节”，对象流里应该不传参或传 null，意思是”取一个对象”，参数的单位从字节变成了对象。第二，highWaterMark 在对象模式下按对象个数算，默认也就是十几个的量级，阈值的含义从”攒了多少字节”换成”攒了多少个”。第三，代价：没有缓冲合并——字节流里碎块可以被攒成大块再往下走，对象模式里每次 push 的东西原样一个个出去；跨序列化边界还容易出错，对象流后面接错一条按字节处理的流，报的就是 Invalid non-string/buffer chunk。

当年 Gulp 3.9 那类构建工具正是靠对象模式的流在内存里搬文件对象，任务组织那一层另有一篇写过，这里不展开。

手写一个 Transform

下面这段是本篇最该被抄走的：一个把字节流按行加前缀的 Transform，顺带演示”块尾是半行”怎么办。

三条纪律。其一，_transform 每处理完一块必须调用 callback()，流的实现在等这个信号才喂下一块；忘了调，整条管道卡住，不报错也不动，是最难查的一类假死。其二，出错走 callback(err)，别在里头痛 throw，错误优先回调是当期约定的正道。其三，半行这种跨块的残尾自己存，源头结束后 _flush 是把它交出去的最后一站。

再记一笔当期真实的 API 代际：最老派 require(‘stream’).Stream 手工继承的写法已经过时；上一段 util.inherits 四个基类是当期常见姿势；而 Node 4 这一代开始，把方法直接当选项传进构造器是新写法，new Transform({ transform: function (chunk, enc, cb) { … } })、new Readable({ read: function () { … } }) 都成立，少掉模板代码。新代码用后两种，读到老仓库里的手写继承也不必修。

编码与二进制的边界

流里默认流动的是 Buffer，字节语义，不问字符。对一条可读流调 setEncoding(‘utf8’)，之后交到你手上的 chunk 就是字符串。

这个方法存在的理由是分块边界不照顾字符：一个汉字在 utf8 里占三个字节，两个 chunk 的切点可能正落在半个字上，逐块自己 toString，半个字就变成乱码。setEncoding 由流内部把没收齐的字节暂存下来，跟下一块拼上再解码，这正是它替你扛的事。开头的 readFileSync 整块读再 toString 倒是没有拼边问题——所有字节到手才解码——代价是全进内存。要走流又要字符语义，setEncoding 是干净的那条路。

结束、生命周期与幂等

三个收尾事件，含义各不相同。end 出现在可读侧：源头的数据处理完了。finish 出现在写入侧：交给它的最后一块已经 flush 到底层。close 表示底层资源（比如文件描述符）释放了，出现时机不作保证。最常见的误用是把”任务完成”挂在可读流的 end 上——上游读完，下游队列里可能还压着一截没落盘，完成时机永远看链条最后那条流的 finish。

写侧还有一条纪律：先 write，后 end，想带尾料就 end(chunk)。end() 之后继续 write，会撞上 write after end 错误。所以多个源共用一条写流时，必须数清楚谁是最后一个，只有它能叫 end。

真实坑清单

每一条都有过故事，排一遍给后来人省点夜。

  • 只挂上游 error、不挂下游：症状是截断的文件加正常的退出码。pipe 不转发错误，链上每个流单独挂，或者干脆用 pump 那类库。
  • 忘记调用 callback：_transform 或异步分支漏掉一个回调，管道假死、零报错。定位手法：管道第一段插一个计数日志，看这块数据走到哪一段停住。
  • 在 data 里做异步事又不暂停：看着像流式，实际数据到得比消化快，内存照涨。要么老实 pause 加 resume，要么换 readable 驱动。
  • objectMode 里把 null 当普通数据 push：null 是结束哨兵，推进去流当场结束，后面的对象全丢。想传空值就在上游过滤掉，别拿哨兵当货。
  • 多个消费者共享一个源想”重放”：流不能倒带，读完就是读完，要再来一遍只能重建流；真要同时喂两路，要么先落一份中间产物，要么边过边双写。
  • 用流发 HTTP 响应时惦记 Content-Length：流式响应事先不知道总大小，走的是分块传输，和带长度的响应在浏览器侧的表现不一样。HTTP 细节不展开，记住长度得你自己提前算出来才有。

小结

回到那晚的 OOM。流解决的是两类问题：数据比内存大，以及不想等全量到齐的边到边处理。用稳它，记住三件事就够了：error 每个流单独挂，背压看 push 和 write 的返回值，完成时机盯最后一条流的 finish。

反过来说，什么时候不要用它。几 KB 的配置文件，整个读了就是；内容解析之后还要随机访问、反复取字段的，流的单向通过反而碍事，不如 buffer 起来或者存进别处；跨网络的大量小写入，攒成一次大块写出去常常比分小片快。收尾的判断就一句：流解决的是”数据比内存大”和”边到边处理”这两类问题，不是所有 IO 的最优写法。
