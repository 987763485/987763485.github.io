SVG 路径与贝塞尔曲线

把折线数据变成平滑曲线，听起来只是换一个命令字母，实际动手才会发现控制点、坐标系、填充规则处处是坑。本文从一次曲线跑出画布的事故讲起，把 <path> 的几何讲清楚：直线与曲线命令、二次与三次的换算、弧线的参数、折线平滑的算法，以及调试和瘦身时真正有用的几个手段。

一次把折线图画出画布的事故

去年年底，我给内部报表工具加了一个「导出 SVG」按钮。图表本体是 Canvas 画的，导出时没截位图，而是按同一份数据重新生成 <path>，缩放清楚，也方便同事改颜色。

第一版很老实，一个点一个点连成折线。产品看了一眼说太硬，问能不能像 Excel 那样带点弧度。我就在导出脚本里加了一步平滑：对相邻三个点算一组 Catmull-Rom 控制点，拼成 C 命令。

结果文件打开，曲线从画布左上角甩出去，绕了一个巨大的弧再回来，只有中间一小段落在图表区。

我先怀疑数据里有 NaN，打了半天日志，数值全正常。真正的原因在坐标系：图表数据是归一化的，x 和 y 都在 0 到 1 之间，绘制时才乘上宽高。我在归一化空间里算控制点，忘了乘回去，于是 0.37 这样的数被直接写进了 viewBox="0 0 820 460" 的路径。控制点只有零点几个像素的偏移，端点却在几百像素之外，曲线自然被拉成了怪物。

这个错后来我又犯过一次，方向相反：量的是图层内的局部坐标，忘了叠加图层位移。两次的共同点，都是把「点在哪」当成了理所当然。

路径语法的最小集合：M、L、H、V、Z

<path> 只有一个属性要紧，就是 d。它是一串命令加参数，命令是单个字母，参数是数字，空格和逗号都能当分隔符。大写字母表示绝对坐标，小写表示相对坐标。

真正需要背下来的只有五个：M 移动、L 直线、H 水平线、V 垂直线、Z 闭合。

M 20 80 把画笔放到 (20, 80)，不画线；L 120 20 画一条斜线；H 220 只给 x，y 沿用上一个点，所以是一条水平线；V 80 同理是竖线；Z 从当前点连回子路径起点并闭合。Z 之后如果还要接着画，下一个 M 必须显式给坐标，否则会从闭合处继续。

同样的形状用相对命令写：

l 100 -60 的意思是「向右 100、向上 60」，参数是增量。两段路径渲染结果一样，但后者对整体平移是免费的：只改第一个 m，整个图形跟着走。这也是导出工具偏爱相对命令的原因——它们本来就按「从上一个点走多远」遍历图元，增量小、位数少。

另一个原因是压缩。增量数值小，gzip 的效果比绝对坐标好；一些工具导出后还会做坐标量化，误差也不随画布尺寸累积。手工写路径时我仍建议先用绝对命令把形状摆对，稳定后再转相对命令，否则调试时要在脑子里做累加。

三次贝塞尔：两个控制点各管什么

C x1 y1 x2 y2 x y 一共六个参数：前四个是两枚控制点，最后两个是终点。起点就是当前点，不必重复写。

拆开看只有两个直觉值得记住。第一，它离开起点时的切线指向第一个控制点，到达终点时的切线方向来自第二个控制点。想要「起步陡、收尾平」，就把第一个控制点放在起点上方，第二个放在与终点等高处。第二，控制点本身不在曲线上，整条曲线落在这四个点构成的凸包里——曲线出画布时，先看控制点有没有越界，比盯着曲线看快得多。

控制点离端点越远，曲线被拽得越狠；两个控制点与端点共线且等距，画出来就是直线。

S 是 C 的简写：省略第一个控制点，由上一段的第二控制点镜像得到。画连续波形时，C 加一串 S 比全写 C 短一半，形状还天然连续。

二次贝塞尔：Q、T 与转成三次的公式

Q x1 y1 x y 只有一个控制点，四个参数。它的形状比三次「软」，因为两端的切线强度被同一个点绑死了：控制点离起点近，离终点就远，两头不可能都陡。

T x y 是 Q 的延续，控制点由上一段的控制点镜像而来。上面这条路径画出来是一段上拱接一段下沉，做简单的波浪分隔线很够用。

二次转三次是常做的换算。设起点 P0、控制点 Q、终点 P2，等价的三次控制点为：

  • C1 = P0 + 2/3 × (Q − P0)
  • C2 = P2 + 2/3 × (Q − P2)

2/3 这个系数保证两条曲线在任意 t 上位置完全重合；反过来把三次降成二次只能拟合，做不到无损，所以我不做这个方向。

什么时候用二次？TrueType 字体轮廓是二次的，一些工具导出的圆角、箭头也是二次；要并进一条统一用 C 的路径，就在中间加一层转换。手写图标时二次也省事，一个控制点心算得过来，对称拱形、气泡尖角都够用。要 S 形或多段变速，直接上三次，别拿两段二次硬拼：拼接点的切线虽然连续，曲率会突跳，放大后一眼就能看出来。

弧线 A：七个参数与两个 flag 的四种组合

A rx ry x-axis-rotation large-arc-flag sweep-flag x y，七个参数，是 path 里最长也最容易写错的一条。rx、ry 是椭圆的两个半径，相等就是圆弧；x-axis-rotation 是旋转角，画正圆时填 0；后面两个 0/1 是 large-arc-flag 与 sweep-flag；最后两个是终点。

一对端点加一组半径，其实能画出四条不同的弧，两个 flag 就是在挑其中一条：

这里的半径 80 正好是弦长的一半，大弧与小弧退化成同一个半圆，于是只有 sweep-flag 起作用：0 从下面绕，1 从上面绕。把半径改成 60，large-arc-flag 的差别才显出来，0 走短的那截，1 走绕远路的那截。四种组合我没法纯靠脑补确定，一律先在调试页里点一遍。

一个必须知道的兜底：半径小到画不出连接两端的弧时，浏览器会按规范把半径等比放大到刚好够用，不报错。我第一次画环形进度条，半径写小了 8 px，弧看起来「没按我给的半径来」，查了半天以为是浏览器 bug。rx 或 ry 为 0 时整段退化为直线，起点与终点重合时这一段直接不画。

手写折线转平滑：Catmull-Rom 转三次贝塞尔

那次事故的收尾就靠这个函数。曲线必须穿过每一个数据点，每点的切线用前后邻点的连线方向近似，这就是 Catmull-Rom 样条。

已知连续四点 P0、P1、P2、P3，要画 P1 到 P2 这一段，等价的三次控制点是：

  • C1 = P1 + (P2 − P0) × k
  • C2 = P2 − (P3 − P1) × k

k 是张力系数，标准 Catmull-Rom 取 1/6。

三个取舍。张力上，k 越大曲线甩得越开，1 是标准值，0.8 稍紧，适合点密的折线；超过 1 过冲明显。

端点上，代码里用的是「复制端点」：第一段令 P0 = P1，最后一段令 P3 = P2。代价是首尾切线短了一半，收尾略显平缓；另一种做法是反射，令 P0 = 2 × P1 − P2，端点更冲。图表场景我选复制，因为坐标轴两端不能有多余的凸起。

过冲上，Catmull-Rom 不保证单调：三点先陡降再走平，控制点会越过数据范围，把曲线鼓到轴外。现在的做法是算出控制点后把 y 夹到整份数据的值域内，x 不处理，代价是最高点附近略平。

控制点可视化调试

事故之后我写了个单页调试工具：一条 C 路径，两个控制点各画一个圆，mousedown 后跟着鼠标走，d 属性用同一套拼串逻辑实时重算，旁边用 pre 显示当前值。难点不在拖动，而在承认设计工具的手柄和代码里的坐标不是一回事。

Sketch 和 Illustrator 里，选中一个锚点会看到两根带圆头的手柄。它们是相对锚点的偏移量，拖一侧另一侧会镜像联动，容易让人误以为控制点天生是成对的。导出成 SVG 后，偏移量被换算成绝对坐标，联动关系消失，四根手柄变成四个独立数字。更麻烦的是图层变换：设计稿里的坐标是图层局部的，导出时可能保留 transform，也可能被烘焙进路径，两种结果的 d 完全不同，量出来的手柄位置和渲染结果会差一个位移。

所以调试页只认文件里字面的坐标，不做换算。这样「我拖到这里」和「d 里写着什么」就是同一个数，比在设计工具里反复导出快得多。

沿路径取点：getTotalLength 与 getPointAtLength

这两个方法都在 SVGPathElement 上，做描边进度、沿路径摆元素时绕不过去。getTotalLength() 返回路径在自身用户坐标系里的总长度，getPointAtLength(n) 返回距离起点 n 处的点。注意两点：长度单位是用户单位，不是屏幕像素，viewBox 缩放后视觉长度会变；返回值是路径自身坐标系里的坐标，路径上的 transform 不会替你算进去。

拿到总长，画进度就只剩一行几何操作：stroke-dasharray 设成总长，stroke-dashoffset 设成 len * (1 - progress)。这里不展开动画写法，只说性能：这两个方法都要现算几何，长路径上每次调用都有成本。我曾把 getPointAtLength 放进 mousemove 做吸附，一条两千多段的路径卡到十几帧，后来改成按固定步长采样成点数组缓存，命中判断在数组上做最近点搜索，才恢复正常。

采样还有个副作用：步长固定时，曲率大的地方点显得稀；沿路径摆刻度或标签时，按弧长均匀采样比按参数 t 靠谱。

填充规则：nonzero 与 evenodd

画环形图标时我又踩了一次坑：外圈一个圆、内圈一个圆，两条子路径都从 12 点方向顺时针画，结果中间没镂空，整个变成一个实心圆饼。这不是路径画错了，是填充规则选错了。

fill-rule 有两个值。nonzero 是默认值：从待判定点向右发一条射线，数路径穿过的方向，顺时针加一、逆时针减一，总数不为零就填。evenodd 不管方向，只数穿过次数，奇数填、偶数不填。上面两个同向的圆，内圈区域的绕数是一加一等于二，nonzero 判为非零，于是填实；换 evenodd，内圈区域穿过两次，留空。

修法有两条：把内圈的 sweep-flag 反过来，让两条子路径反向，nonzero 也能镂空；或者直接写 fill-rule="evenodd"。我在导出脚本里选了后者，不用关心子路径方向，代价是自交路径要小心：evenodd 会把自交围出的每一块交替填充与留空，五角星中心就会空出来；nonzero 下的五角星是实心的。

顺带一句：fill-rule 只管填充，不影响描边；stroke 永远沿路径画，自交处也不会镂空。

精度、体积与选型

导出文件的体积，八成浪费在小数位上。0.1 px 的误差在 2 倍屏上也看不出来，所以统一保留一位小数就够。前提是全程用同一个取整函数，四舍五入而不是截断：截断会让整条路径系统性偏向左上，相邻段的控制点各自取整还会在接缝处产生微小折角。

具体做法有这几条：坐标用 toFixed(1) 或手写 Math.round(v * 10) / 10；小于 1 的数省略前导零，.5 比 0.5 省一个字节；不要输出 -0；相对命令本身就能把大坐标变成小增量；连续的同类命令可以省掉后面的字母，L 1 2 3 4 等价于两条 L，M 后面多出来的坐标对按 L 处理。这些手段加起来，同一张折线图从 46 KB 压到 19 KB，gzip 之后差距不到 2 KB，真正省下的是解析时间。

可读性上我保留两份：生成脚本带注释和分组换行，压缩产物单行无空格。改样式只改脚本再重新生成，绝不在压缩产物上手改——那串数字里错一个逗号，整段路径就错位。

选型上，判断顺序基本是固定的：

需求 命令 注意
直角折线、表格线 M L H V Z 相对命令省字节，Z 会补一条闭合线
单峰过渡、对称拱形 Q / T 一个控制点，两端切线强度绑死
两端切线要独立控制 C / S 控制点离端点越远，曲线越冲
圆弧、圆角、环形进度 A 半径不足会被自动放大，两个 flag 共四种组合
数据折线平滑 Catmull-Rom 转 C 张力与端点处理决定首尾形状

常见错误也能对回小节：曲线甩出画布，先查控制点坐标系（第一节、第六节）；圆角半径「不听话」，是 A 的半径被放大了（第五节）；环形图标不镂空，是填充规则（第九节）；文件偏大，是精度没统一（本节）；手柄对不上，是设计工具的局部坐标（第七节）。把这五条记住，path 的日常问题基本就覆盖了。
