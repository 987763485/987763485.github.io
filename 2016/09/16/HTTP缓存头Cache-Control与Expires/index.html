HTTP 缓存头：Cache-Control 与 Expires

一次换图事故让我把 Cache-Control 与 Expires 从头读了一遍。本文只谈这两个头：过期时间从哪里开始算、两个头打架时谁说话、共享缓存为什么看另一个字段、no-cache 到底等于什么。适合已经会写 max-age=3600、却说不清它从哪一刻开始计时的前端与运维同学。

一张没换名的图，和一条写错的 Expires

2016 年 9 月的一个周一，运营把首页轮播的第一张图换成中秋活动版。我们按老流程直接覆盖服务器上的 banner.jpg，文件名、目录、尺寸都没变，发布脚本跑完，我在浏览器里按 F5，新图正常。第二天上午，运营群里开始出现两种截图，一部分用户看到的是新图，另一部分还是上一版。

我先怀疑 CDN 没刷，去问运维。对方回得很快：“响应里加了 Expires，不会有问题。”我让他把响应头贴出来：

问题就在 Expires 这一行。运维的原意是“北京时间 9 月 19 日上午 10 点过期”，于是把本地时间 2016-09-19 10:00:00 后面直接加了 GMT。可 10:00 GMT 换算成北京时间是当天 18:00，缓存比预期多活了 8 小时。运营早上 9 点多换图，正好落在这段窗口里。

为什么只有一部分用户中招？因为 Expires 是绝对时间，每个人拿到缓存副本的时刻不同，副本剩下的寿命就不同：前一天晚上访问过的人，手里那份要到 18:00 才过期；当天早上第一次访问的人，拿到的是更新后的响应。看起来像“部分用户看到旧图”，本质是同一张图在两个时刻被缓存了两次，而我们没给浏览器任何“去问源站”的理由。

Expires 是绝对时间，不是“多久之后”

Expires 的值是一个 HTTP-date，格式在 RFC 7231 里定死为 IMF-fixdate：

星期、日 月 年、时分秒，最后必须是 GMT。历史上还有 RFC 850 与 asctime 两种老格式，规范要求接收方兼容，但发送方只该输出上面这一种。写配置时最容易犯的错是星期写错、月份用中文缩写，或者漏掉 GMT，这些都会让整个头变成非法日期。

关键在于，它描述的是“某一个时刻”，不是“多少秒之后”，所以既依赖服务端把时区换算对，也依赖客户端把这个时刻和“现在”比较对。

时区：最容易错的一步

Expires 里的 GMT 不是装饰，它规定这串数字按 UTC 解释。我们的服务器在 UTC+8，运维在配置文件里看到的是本地时间，于是很自然地拼出“本地 10:00 + GMT”，实际描述了一个晚 8 小时的时刻。这类错误不报错，响应完全合法，浏览器照单全收，要到有人发现内容不对才暴露。

时钟偏差：影响没有想象中大

直觉上，用户把系统时间调快一年，Expires 的时刻早就过去了，缓存应该立刻失效。但按 RFC 7234 的算法，新鲜度寿命是两个头的差值：Expires 减 Date。两个值都来自同一个响应，都按 UTC 解释，本机时钟根本不参与这个减法。浏览器算的是“这份副本已经活了多久”，不是“现在几点”。

真正受本机时钟影响的是副本在本地存了多久、If-Modified-Since 的比较和日志时间戳。所以“用户时钟不准”通常不是缓存事故的主因，配置写错才是。

0 与非法值

Expires: 0 很常见，它并不是合法日期。RFC 7234 明确要求缓存把非法日期（尤其是 0）解释为“已经过期”，效果接近“立刻过期、每次都要验证”，很多老配置用它关缓存。但“已经过期”不等于“不许存”，缓存照样存下响应，只是用之前要回源确认，这和 no-store 是两回事。把 Expires: 0 当成语义清晰的写法去推广，不如直接写 Cache-Control: no-cache。

max-age 是相对时间，基准是 Date

Cache-Control: max-age=600 的意思是“从这份响应生成算起，600 秒内是新鲜的”。单位是秒，只写整数，不写毫秒。它不关心今天是几号，也不关心服务器在哪个时区，所以不会重演上一节那种“本地时间拼 GMT”的错误。这也是我们后来约定优先用 max-age、Expires 只作兼容兜底的原因。

那么“生成时刻”由谁提供？响应里的 Date 头。浏览器拿到响应时，先看 Date，再看自己已经存了多久，用 max-age 减去这段时间，剩下的才是能直接用的时长。带 Age 的响应尤其明显：CDN 存了 500 秒的 max-age=600 资源，到浏览器手里只剩约 100 秒寿命，而不是重新拿到 600 秒。

很多人以为每次请求都重新计时，在 CDN 后面配了 10 分钟却只观察到 2 分钟，就是 Age 把账扣掉了。

Date 缺失或不准会怎样

RFC 7231 要求源站必须发送 Date。一旦缺失，缓存只能退回“收到响应的本地时刻”作基准，这个时刻包含传输和排队时间，链路慢时误差会明显放大。

更常见的是 Date 存在但不准。源站时钟快 5 分钟，max-age=300 的响应一进缓存就是过期状态，每次都要回源验证，缓存等于白配；时钟慢 5 分钟，同一份资源的实际寿命接近 600 秒。这类问题在单机上很难察觉，接上 CDN 或多机时钟不同步才表现为“同一张图有的人新有的人旧”。所以配缓存之前，先确认机器在跑时间同步。

两个头同时出现，谁说话

规范给的答案很干脆：响应里同时有 Cache-Control: max-age 和 Expires 时，接收方必须忽略 Expires。Expires 是 HTTP/1.0 时代的产物，Cache-Control 是 HTTP/1.1 补上的，后者优先，是为了让新配置能覆盖旧配置。所以 Expires 在过去、max-age=3600 的响应，实际寿命是 1 小时。

s-maxage：给共享缓存单独下命令

s-maxage 只对共享缓存生效，也就是 CDN 和反向代理这类“一份副本服务很多人”的缓存；浏览器仍然只看 max-age。两者可以同时出现，而且允许不同：

这份资源在 CDN 上新鲜一小时，在浏览器里只新鲜一分钟。代价不对称：CDN 回源的代价是源站带宽，一小时一次就能吸收绝大部分流量；浏览器回源只是回 CDN，代价很小，让它勤快点问，内容出问题时受影响的人就少。

s-maxage 还隐含了 proxy-revalidate 的语义：共享缓存里的副本一旦过期，必须回源验证，不能拿旧内容顶。所以给 CDN 配它，等于声明“过期就必须问源站”。

public 与 private：谁能存

private 表示这份响应只属于某一个用户，共享缓存不得存储，浏览器自己的缓存可以存。public 相反，它明确允许共享缓存存储，哪怕默认情况下会被拒绝。

默认会被拒绝的典型是带 Authorization 的请求。RFC 7234 规定，共享缓存不得把对这类请求的响应直接拿来复用，除非响应里带了 public、s-maxage 或 must-revalidate。所以后台接口返回当前用户的订单列表，只要不加 public，CDN 就不会把它当公共资源；反过来，带用户信息的接口写了 public, max-age=600，等于把 A 的订单发给 B，比缓存陈旧严重得多。

Set-Cookie 类似：规范没有直接禁止缓存带它的响应，可共享缓存一旦存下来，就会把同一个 Cookie 发给所有访问者，所以 CDN 默认跳过这类响应，我们也不该去覆盖。

no-cache 不是“不缓存”

这是我最想纠正的一条误读。no-cache 字面是“不要缓存”，规范里却是：可以存，但每次使用之前必须回源验证。它限制的是“能不能直接用”，不是“能不能存”，名字是历史包袱。

真正禁止存储的是 no-store。带这个指令的响应不许被写进任何缓存，已经落盘的临时副本也要尽力清理；它的目标是敏感数据，比如支付结果页、带身份证号的接口。

两者之间还有两个容易混的：

  • max-age=0：允许存，但存下来就已经过期，所以每次使用前都要验证。日常效果和 no-cache 接近，区别在于它表达的是时间而不是意图。
  • must-revalidate：新鲜期内照常直接用，一旦过期，禁止在拿不到验证结果时拿旧副本顶。没有它，缓存遇到源站超时或断网可以继续返回旧内容；有了它，只能报错或等待。

所以 max-age=60, must-revalidate 读作“一分钟内随便用，之后必须问源站，问不到就别给”。而 no-cache, must-revalidate 是我们给 HTML 入口页的标准组合：永远验证，且验证失败时不拿旧页面糊弄用户。两者的差别不在新鲜期，而在过期之后缓存还有没有“自作主张”的空间。

版本化文件名才配得上一年

max-age=31536000 是一年。它安不安全，取决于 URL 会不会跟着内容变。app.3f9c2a.js 这种把指纹写进文件名的资源，内容一改文件名就变，旧 URL 上的长缓存既挡不住新版本，也不会再有人请求它，一年完全合理。反过来，banner.jpg 这种名字固定的文件配一年，就是开头那场事故的放大版。

即便用了指纹，也有两个前提。其一，同一个 URL 的内容不能再改，包括回滚：回滚时把旧文件名指回旧内容，长缓存的用户会看到回滚前的版本，直到缓存自然过期。其二，HTML 不能跟着一起长缓存。入口页的 URL 是稳定的，用户会收藏、会被外链，它必须保持短寿命，才能把新的资源 URL 递出去；HTML 一旦长缓存，用户不是看到旧图，而是永远发现不了新版本。

我在 2016 年见过有人提 immutable，那是当年才提出的新提案，支持面很窄，作用是让用户主动刷新时也不发条件请求，但不能当成标准能力写进通用配置。

浏览器面板里则是另一套语言。Status 是 200 且 Size 显示 from disk cache 或 from memory cache，说明强缓存命中，没有发出请求；显示 304，说明请求发出去了，源站确认副本还有效。304 不是“缓存命中”，它是一次完整往返，只是省了响应体。must-revalidate 只约束过期之后能不能拿旧副本顶，不改变验证方式。

判断 CDN 命中，看两次请求之间 Age 是否变大、X-Cache 或 Via 是否标了命中：Age 大于 0 就说明不是源站现做的。

三个真实的误配

Expires 用了本地时间

就是开头那次。修复不是把 8 小时减回去，而是让 toUTCString() 生成，同时在发布检查里加一条：Expires 减 Date 必须等于配置的秒数，不等就拦住发布。

把 no-cache 当成 no-store

用户中心的页面被配成 no-store，理由是“里面有手机号，别缓存”。结果是每次前进后退都整页重拉，表单填一半返回就全没了。改成 no-cache 后体验恢复，安全性也没有下降，因为每次使用前都会回源确认。反过来的错误更危险：一个返回手机号的接口被配成 no-cache，以为“不缓存”，其实副本还留在磁盘上，这种才该用 no-store。

CDN 与源站各说各话

源站给图片写了 max-age=86400，CDN 侧又单独配了 10 分钟。运营改图后刷了 CDN，以为万事大吉，可用户浏览器里还压着一天的副本，第二天依旧有人看到旧图。修法是让两者关系固定：CDN 的 s-maxage 不短于浏览器的 max-age，换图必须换文件名，刷 CDN 只解决“别人家的缓存”，解决不了用户手里那一份。

收尾：一张决策表

资源类型 推荐头组合 失效方式
带指纹的 JS、CSS public, max-age=31536000 改文件名
图片、字体（带版本号） public, max-age=31536000 改文件名或版本号
入口 HTML no-cache, must-revalidate 每次回源验证
公共接口 JSON public, max-age=60, s-maxage=300 等过期或刷 CDN
含用户数据的接口 private, no-store 不缓存，每次请求
名字固定的运营图 public, max-age=300 改名，或发布时刷 CDN

表里没有一处写 Expires。不是它不能用，而是它要求每个写配置的人都把时区换算对，而 max-age 不要求。能用相对时间表达的事情，就别用绝对时间。
