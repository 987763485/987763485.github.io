Canvas 实现涂鸦板

给客服后台做批注白板，桌面端一次验收就过，手机上却把一笔画成了短线，还顺手把页面滚走了。本文按修复顺序记录坐标换算、事件统一、笔迹平滑、橡皮擦、撤销栈、分层与导出，也记录那些只有真机才暴露的细节。

事故开场：桌面正常，手机断线

去年年底，我们给客服后台加了一块批注白板。工单详情页右上角一个按钮，点开是一张铺满容器的 Canvas，客服在客户发来的截图上圈重点、写几个字，导出图片回传。桌面端验收很顺利：鼠标按下、拖动、松开，线条跟手。

上线第三天，客服主管发来一段录屏。iPhone 上画一笔，笔迹不是一条线而是一串小短线，中间隔着明显空隙；更糟的是画到一半，整个页面跟着手指往上滚，画布被推走，后半截笔迹落在了别的元素上。安卓测试机类似，只是断得更碎。

我们第一反应是性能，数了一遍重绘次数和路径数量，没有异常。真正的原因有三个：取坐标只用了 clientX/clientY，没有减掉画布位置；移动端只监听了鼠标事件，真正触发的是触摸事件，模拟出来的坐标既延迟又不连续；touchmove 默认带动页面滚动，我们没有阻止。三个问题叠在一起，才表现成”笔迹断成一节一节”。

坐标换算：先减掉画布位置

第一个坑最基础。坐标有好几套：clientX 相对视口，pageX 相对文档。画布不在页面左上角，直接拿 clientX 当画布坐标等于整体平移了一段，越靠右下偏得越多。

正确做法是用 getBoundingClientRect() 取画布位置再从 clientX/clientY 里减掉。反直觉的是，它返回的已经叠加过滚动，所以不要再加 window.pageYOffset。最早那版两者都加，页面在顶部时正常，往下滚多少就偏多少。

另外也不要缓存 rect：弹层一滚、软键盘一弹就过期，每次取点现算，一次事件的开销可以忽略。

再就是位图尺寸。画布的 width/height 属性是位图尺寸，CSS 的宽高是显示尺寸，不一致时浏览器会缩放。按 dpr 把位图放大，再把上下文整体缩放，后续绘制都按 CSS 像素写，取点函数就完全不用关心 dpr：

这套尺寸只在初始化和窗口变化时设一次。给 canvas.width 赋值会清空画布并重置上下文状态，包括刚设好的 scale。高清屏的半像素细节另有专文，这里只交代一句：坐标统一用 CSS 像素，dpr 只影响位图。

事件统一：两套事件，一个入口

桌面用鼠标，移动用触摸，这是 2016 年的现实。Pointer Events 在桌面 Chrome 上能用，但 Safari 没跟上，移动端拿它当唯一方案等于放弃 iOS。所以我们两套都写，外面包一层 start/move/end 接口。

用 'ontouchstart' in window 选一套绑就够。两套都绑，带触摸屏的笔记本会落笔画两遍：先 touch，浏览器再补一组 mouse，原地叠出一条更深的线。

鼠标这侧有个易漏点：mousemove 和 mouseup 要挂到 document。指针拖出画布后画布收不到事件，松开也收不了笔，下次落笔就从断点连过去。触摸不用，touch 事件始终派发给 touchstart 的那个元素。

touchmove 里的 preventDefault() 是止住滚动最直接的手段，前提是监听器可取消。当时 Safari 对 addEventListener 第三个参数支持不整齐，我们一律只传布尔值。另外别把它挂到 document 上，否则整页的点击和双击缩放都会失效。

touch-action: none 从更早的位置解决同一个问题：告诉浏览器这块区域不参与平移和缩放，手势一开始就不被接管。但当时 iOS Safari 支持不完整，老安卓 WebView 直接忽略，所以两层都上：

基础笔迹：一笔一条路径

事件统一之后，画线反而简单。落笔 beginPath() 加 moveTo()，移动时逐个 lineTo()，抬笔 stroke()。lineCap 与 lineJoin 都取 round，lineWidth 取 2 到 3 个 CSS 像素——再细，图缩小后会消失；再粗，圈选小字会糊成一片。

“每笔一条路径”不是风格问题，是正确性问题。stroke() 对整条路径一次性上色，样式取调用那一刻的值。共用路径的话，用户换红色再画一笔，重绘时旧的黑线会一起变红，橡皮的 destination-out 也会把整条路径一起擦掉。

半透明画笔还有个坑：每收到一个点就 stroke()，圆头在接缝处重叠，透明度叠加，一条均匀的灰线会变成深浅相间的珠链。所以当前这一笔要画在独立的覆盖层上，每次清空重画。

采样与平滑：中点二次贝塞尔

线不断了，却变成了折线。touchmove 名义上每帧一次，可手指快速划过时相邻两点可能隔几十像素，直接 lineTo 就是拿直线去连，圆弧看着像被削了几刀。

常见做法是中点二次贝塞尔：相邻两点的中点作曲线端点，原始采样点作控制点。曲线在每个中点处自然相接，切线连续，不会出现折角，也不需要引入额外的平滑算法。

平滑只解决”点太少”，不解决”点太脏”。手指按住不动时，硬件仍会报出零点几像素的抖动，全收进来笔尖会鼓出小疙瘩。我们加了一道阈值：新点与上一个采纳点的距离小于 3 个 CSS 像素就丢弃。1 像素等于没过滤，太大则小字被削成直线段，3 像素是五台测试机上试出来的折中。

橡皮擦：真橡皮与假橡皮

橡皮有两种做法：假橡皮换一支白色笔画上去，真橡皮把像素的 alpha 清掉。

假橡皮成本几乎为零，把 strokeStyle 改成白色就行。问题是”白色”是个具体颜色，只在这张画布本来就是白底时成立：导出透明底 PNG 后，白线贴到深色聊天窗口里就是一条白杠；画在客户截图上，白色会把底图一起盖掉，看着像擦干净了，其实什么都没了。

destination-out 只保留目标中与源不重叠的部分，源的颜色无关紧要，只有 alpha 起作用。它的副作用是作用于整张画布，包括背景网格和底图，这就是我们后来分三层的原因——橡皮只能落在笔迹层。

两者在撤销栈里的待遇完全不同。假橡皮是普通笔画，记录的是”我在这里画了白色”，重放到另一张底图上必然错位。真橡皮记录的是”我在这里擦了一下”，擦掉什么取决于当时画布上已有什么，所以重放必须严格按顺序从头执行。

撤销栈：存操作，不存像素

动手前算过账：画布 1040×780、dpr 为 2，位图就是 2080×1560，一张 ImageData 约 13 MB，撤销 30 步就是 390 MB，还没算垃圾回收的压力。这个方案在手机上活不过两笔。

存像素的好处只有实现简单：进栈 getImageData，撤销 putImageData。代价是不可序列化，没法存进工单，还和 dpr 绑定，换台设备打开就错位。

存操作是我们的选择：每次落笔生成一个对象，记录类型、颜色、线宽和点数组。一屏批注几十笔、几千个点，序列化后只有几十 KB。

分层画布：三层各管一件事

最初只有一张画布，每次 touchmove 都把全部历史笔迹重画一遍。圈到第十几个重点时，笔尖明显滞后手指，中低端安卓机上能拖出小半厘米。

改成三层之后，每层只负责一件事：

  • 背景层：画布底板和浅色网格，初始化时画一次，窗口尺寸变化时重画，运行期不再动。
  • 笔迹层：所有已提交的笔画，只在抬笔、撤销、重放时变化。
  • 当前层：一张绝对定位、叠在笔迹层之上的透明画布，只放正在画的这一笔。

于是 touchmove 要做的事变成：清空当前层，用积累的点重画这一笔。开销只和当前这一笔的点数有关，和之前画了多少笔无关。抬笔时把当前层整张拷进笔迹层，再清空当前层：

setTransform 那一行是踩过坑的：两个上下文都做过 scale(dpr, dpr)，直接 drawImage 会再乘一次缩放，内容放大成四倍。拷贝时把变换重置成单位矩阵，按位图坐标一一对应，才不会错位。

分层还让橡皮有了边界，只作用于笔迹层。至于”只在需要时重绘”，我们只加了一个判断：点数组没变就不清屏。

导出：透明底还是白底

导出只取笔迹层，拿到的 PNG 天然透明，贴到深色界面里不会出现一块白板。要白底时不要改画笔颜色，在临时画布上先铺白再叠笔迹，顺序反了就盖住了。

尺寸要换算：位图是 CSS 尺寸的两倍，导出的 PNG 也就大两倍，像素数四倍。1040×780 的批注导出来是 2080×1560，线条多时五六百 KB，手机流量下回传并不友好。我们按目标宽度重画，导出边长压到 1600 以内，留档才存原尺寸。

线条和抗锯齿像素是 PNG 的天敌，压缩率很低；同样内容存成白底 JPEG、质量 0.85，体积约十分之一，代价是细线周围有轻微噪点。对外回传用 JPEG，留档用 PNG。

toDataURL 是同步的，大画布上要两百毫秒以上，记得先显示”正在生成”。iOS 上位图面积过大时它可能返回空字符串，导出尺寸上限必须卡死。

触摸端：那些只在真机上出现的细节

多指最先冒出来。两根手指同时按下，touches[0] 在两点之间来回跳，笔迹拉出一条横线。修法是记住第一根手指的 identifier，每次从 changedTouches 里找同一个标识，找不到就忽略这批事件。

手掌误触是同一类问题的放大版。Touch.radiusX 理论上有用，但 iOS 取不到，安卓实现也不一致。我们退回一条简单规则：手指数大于一就结束当前笔并忽略后续事件，直到全部抬起。牺牲了双指缩放，换来的是一条确定的边界。

画到边缘时坐标会跑出画布甚至变成负值。我们选择不裁剪，视觉上就是笔迹贴边停住；强行夹回边界的话，手指在画布外移动会沿边缘拖出一条直线，更难看。

切后台回来笔迹变空白，是排查最久的问题。不是我们清空的，是 iOS 在内存紧张时回收了画布的后备存储，canvas 还在，像素没了。现在每次提交后把笔迹层 toDataURL 存一份快照，监听 visibilitychange，回来时检查画布是否全空，是则用快照重画。不优雅，但管用。

最后是收笔。touchend 和 touchcancel 都要处理，后者在来电、系统手势、通知弹窗时触发。只监听 touchend，被打断的那一笔会一直处于”按下”状态，下一笔的起点直接连到断开处，用户看到的是凭空多出一条长线。

收尾：问题与处理对照

上线两周后回看，真正花时间的不是 Canvas API，而是事件、坐标和内存。踩过的坑整理成表：

问题 症状 处理
坐标未减画布位置 笔迹整体偏移，越靠右下偏得越多 每次事件用 getBoundingClientRect() 现算
重复叠加滚动偏移 页面滚动后笔迹错位 rect 已含滚动，不再加 pageYOffset
只绑鼠标事件 手机上笔迹断续、延迟 按 ontouchstart 绑定触摸事件
未阻止默认滚动 画布被手指带走 touchmove 里 preventDefault，配合 touch-action: none
每段都 stroke 半透明笔颜色深浅不一 整笔一次成型，或画在独立当前层
采样点直接连线 圆弧变成折线 中点二次贝塞尔平滑，3 像素阈值去抖
白笔当橡皮 透明底导出露白杠 改 destination-out，橡皮只作用于笔迹层
撤销存 ImageData 几十步后内存爆掉 存操作数组，限 30 步并烘焙早期操作
只监听 touchend 来电后多出一条长线 touchcancel 一并收笔
后台回来画布空白 笔迹凭空消失 定时快照，visibilitychange 时校验重绘

如果今天重做一遍，我会先把坐标和事件这两层写成一个与业务无关的小模块，再动笔迹和撤销。涂鸦板看着是画图需求，实质上是一个高频输入采集问题。
