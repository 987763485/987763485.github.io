Canvas 动画与粒子效果

桌面六十帧，千元机像翻页

八月底做一个数据产品的活动页，背景想要”缓慢上升的光点”，设计稿上是一片星空。用 Canvas 写了百来个粒子，桌面浏览器上很稳，拿两台千元机一看，肉眼可见地一顿一顿，滑动时更明显。页面没有别的动画，问题只可能在这张全屏画布上。

排查下来是三样东西叠在一起：粒子数一百二十个、每个粒子每帧一次 beginPath 加 arc 加 fill 还带 shadowBlur、画布的实际像素是 CSS 尺寸的四倍。单看哪一样都不算过分，合起来就吃光了低端机的预算。这篇把最后稳定下来的做法写一遍：尺寸、时间步长、粒子池、绘制方式、降级和销毁。requestAnimationFrame 本身怎么用，另一篇已经讲过，这里只把它当驱动源。

画布尺寸不是 CSS 尺寸

Canvas 有两套尺寸。CSS 决定它在页面上占多大，width 和 height 属性决定它有多少像素。只写 CSS 不写属性，属性默认是 300×150，浏览器会把这张小图拉伸，粒子边缘全是糊的；反过来只写属性不写 CSS，画布会按像素尺寸把页面撑开。

高 DPI 屏上还要乘 devicePixelRatio：属性尺寸写成 CSS 尺寸的 dpr 倍，再用 ctx.scale(dpr, dpr) 把坐标系缩回 CSS 像素，后续代码就都按设计稿的坐标写。

给 width 赋值会重置整个上下文状态：变换、fillStyle、lineWidth、globalAlpha 全部回到默认值。我们第一版在 resize 之后只重设了 scale，忘了 globalAlpha，结果窗口一拖动，粒子透明度全变成 1，整片背景亮了一档。所以 resize 之后要把绘制相关的状态重新设一遍，或者把设置集中到一个函数里，resize 完调一次。

dpr 也不是越高越好。有些手机的 dpr 是 3，全屏画布的像素数是 CSS 面积乘九，低端 GPU 的填充率本来就紧。我们给 dpr 设了上限 2，画质看不出差别，像素却少了一半多。iOS 对画布总像素还有硬上限，超过之后拿到的是一张空白画布，也不报错，所以 dpr 不能无脑乘，画布尺寸由内容决定时尤其要小心。

还有一个初始化顺序的问题：容器还没布局完时，getBoundingClientRect() 返回的宽高是 0，画布会变成 0×0，之后的绘制全部丢掉，控制台里一条错误都没有。把初始化放到 DOM 插入之后，或者在 resize 里判断宽高为 0 就直接返回。

时间步长：帧数不是时间

按每帧加固定速度，60 帧和 30 帧的设备上粒子速度差一倍；低端机一慢，粒子像被粘住。要用两帧的时间差：

dt 除以 16.67 得到一个按 60 帧计的倍率，速度仍按每帧多少像素写，迁移成本低。上限 32 毫秒是为了切标签页回来：时间差可能是几秒，不夹住的话粒子会瞬移出屏幕，再集体重生，看起来像闪了一下。

还有一个坑：rAF 回调的时间戳和 Date.now() 不是一个时间原点，混用会算出负数。第一版在回调里用 new Date().getTime() 减去自己记录的 rAF 时间戳，在部分安卓 WebView 上第一帧的 dt 是个很大的负数，粒子直接不动。统一用回调参数就正常了。

粒子池：别在每一帧里 new

第一版每帧检查粒子是否死亡，死了就 splice 掉再 new 一个补上。一百多个对象不算多，但每帧都产生垃圾，低端机一触发 GC 就是十几毫秒的停顿，表现出来还是卡。而且循环里 splice 会让下标错位，偶尔漏掉一个粒子，过几帧才补上。

改成固定长度的池：启动时一次性建好，粒子带一个 age 和 life，到寿命不删除，重置参数后接着用。

池的大小在初始化时定死，运行中不增不减；需要改密度时重建整个池，而不是在半路补几个。这样帧循环里没有分配，GC 的压力就平了。

刚上线时还有一个尴尬：用户打开页面，上半屏是空的，粒子要过两三秒才飘上来。原因是初始化时每个粒子都按 spawn 的默认位置放在底边下方，再一起往上走。把初始的 y 改成在整个屏幕高度里随机取，第一批粒子就直接铺满画面；重生时才用底边。这个区别要单独写一个初始化函数，不然每次重生也会落在屏幕中间，看着像凭空出现。

飞出边界之后

粒子向上飘，出了顶边怎么办。一种做法是从底边重新进来，横向位置随机；另一种是原地绕回，从底边同一个 x 进来。前者自然，后者在粒子密集时会出现一条竖线。我们选前者，但加了一个限制：重生时不要落在离上一个重生点太近的位置，否则连续几帧会在同一处冒出几个粒子，看着像喷泉。

左右出界不用管，粒子本来就在可视区外，横坐标越界不影响画面；但速度不能让它们一直往一个方向跑，否则池里的粒子会慢慢全堆到一侧。我们的做法是给横向速度一个很小的随机扰动，每次重生时重新取，长期看是均匀的。

还有生命周期。粒子不是永远活着，age 超过 life 就视为死亡，透明度在最后一段逐渐降到 0，避免突然消失。这个淡出不要每个粒子每帧单独算一个 alpha 再单独绘制——算本身不贵，但 alpha 各不相同就没法合批，绘制调用会翻倍。我们最后只分了三档透明度，按档分组画。

绘制：一次路径胜过一百次

Canvas 2D 画圆，最直接是每个粒子 beginPath、arc、fill。一百二十个粒子就是一百二十次绘制调用，桌面上无所谓，低端机上就是主要开销。能合批的合批：颜色和透明度相同的粒子放进同一条路径，最后 fill 一次。

arc 前面要先 moveTo，否则相邻两个圆之间会被一条直线连起来，填充出一片奇怪的形状。这个细节文档里写了，我们第一版还是漏了，画面上多出一堆三角形。

比合批更彻底的是预渲染一张小图：用一个离屏 canvas 画好带柔边的圆点，主循环里只做 drawImage。drawImage 比路径填充快，尤其是粒子带柔边的时候。代价是每个粒子不能单独改颜色，只能靠 globalAlpha 调透明度；活动页的粒子本来只有一种颜色，这个限制可以接受。

shadowBlur 是最贵的一项。设计稿上的光晕看着像阴影，我们一开始真的用了 shadowBlur = 8，每个粒子都加一层模糊，帧率明显掉下来。后来把光晕直接画进预渲染的小图，一次性解决。渐变也一样：不要每帧 createRadialGradient，那是在每帧分配对象并重新算颜色；要么预渲染，要么缓存起来。

给低端机留一档

粒子数量按屏幕面积估算，但不能只按面积。我们的做法分三档：桌面和高端机用基准数量，dpr 大于 2 的按面积折算后取小值，低端机再砍半。判断低端机在 2016 年没有可靠 API，最后用的是启动后几帧的平均帧间隔：连续几帧超过 33 毫秒，就把粒子数量降一档，并关掉多余的光晕。

降级只降不升，不然在临界点上会来回切，画面忽多忽少。降级的动作放在帧循环里做一次就够，重建粒子池时复用已有对象，只是把多余的重置成不活跃。

分辨率也可以降。dpr 从 2 降到 1.5，像素少四成多，画质在手机上几乎看不出来；这比减少粒子更有效，因为填充率的压力主要来自像素数。我们的顺序是先降 dpr，再减粒子，最后才关动效。关掉动效意味着背景变成一张静态图，那是兜底，不是首选。

页面藏起来就停

活动页会被切到后台，也会被锁屏。rAF 在页面不可见时本来会暂停，但恢复时的时间戳会跳，第一帧 dt 很大。前面用 32 毫秒夹住了，粒子不会瞬移，可显式的停止仍然要做：有些 WebView 切后台时不暂停，或者暂停了但别的东西还在跑。

监听 visibilitychange，藏起来就 cancelAnimationFrame，回来时把 last 清零再重新请求。last 不清零的话，恢复后的第一帧会拿一个很大的 dt，虽然被夹到 32，但那一次更新仍然比正常大一倍，粒子会轻轻跳一下。

还有销毁。这个背景组件被复用到弹窗里，弹窗打开时初始化，关闭时只把 canvas 从 DOM 里移除，没有取消循环。第二次打开又初始化一次，两个循环同时画同一张画布，粒子速度翻倍，CPU 也翻倍。后来补了 destroy()：取消 rAF、移除 resize 和触摸监听、把粒子数组和 canvas 引用都置空。SPA 里组件反复挂载时，这种漏法很常见。

全屏画布别挡住按钮

背景画布用 position: fixed 铺满视口，最容易出的问题不是性能，是点击。画布是 <canvas> 元素，默认会接收鼠标和触摸事件；它盖在内容上面时，下面的按钮、链接全部点不到。桌面调试时我们用键盘 Tab 能聚焦，没发现；手机上用户点”立即参与”没反应，客服报上来才知道。

两种改法：把画布放到内容下面（z-index: -1，并给内容一个定位上下文），或者给画布加 pointer-events: none。我们选后者，因为画布需要盖在部分内容上做氛围，但交互全部由下层接管；波纹的监听挂在 document 上，按画布的位置换算坐标，不依赖画布本身收到事件。

交互：只推最近的几个

鼠标移动时粒子被推开，是这类背景常见的交互。做法不复杂：算鼠标到每个粒子的距离，小于半径就给一个反向的速度增量。一百多个粒子，每帧全量算距离完全够用，不需要空间划分。真正要注意的是不要每帧累加速度：鼠标停着不动时，如果每帧都加一次，粒子会被弹飞。我们的做法是只改位置，或者给速度设上限并每帧衰减。

触摸端要考虑 touchmove 的默认行为。活动页允许滚动，手指在画布上滑动时既要推粒子，也要让页面滚，不能 preventDefault。第一版在 touchmove 里阻止了默认行为，结果整个页面滑不动，用户以为卡死了。后来只监听 touchstart 和 touchend，在点上生成一圈波纹，滑动仍然交给浏览器。

点击生成波纹也有预算：连续快速点击会叠加很多波，每帧都要画。我们限定同时最多三个，新的来了就顶掉最旧的；波纹的生命周期短，半秒左右，用户不会注意少了一个。

重设尺寸后状态丢失 透明度、颜色回到默认 resize 后重设上下文状态
按帧加固定速度 低端机上变慢 用时间差，单帧上限 32 毫秒
每帧 new 和 splice GC 停顿、漏掉粒子 固定粒子池，到寿命后重置
每个粒子单独绘制 绘制调用过多 同色合批或预渲染小图

切后台后恢复 粒子跳一下 visibilitychange 停循环、清时间戳

粒子动画不难写，难的是把每一帧的预算花在哪里想清楚。桌面上的六十帧不代表手机上也能跑，画布上的一百个圆背后是一百次状态切换和像素填充。先把尺寸对齐、把分配挪出循环、把最贵的绘制换掉，剩下的才是调参数。
