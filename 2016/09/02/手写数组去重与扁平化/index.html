手写数组去重与扁平化

权限树拍平之后，菜单出现了两遍

九月初，后台的权限配置改成树形。保存时要把树拍平成一维的权限 id 数组提交给接口，页面加载时再把接口返回的一维数组还原成树。

第一版拍平很简单：接口给的树节点是对象、孩子挂在 children 里，我们先用一个映射把节点转成 [id, 子节点...] 的嵌套数组，再遇到数组就递归展开、遇到数字就收下。上线后，拥有多个角色的运营账号看到的菜单出现了重复项：同一个”订单导出”权限在树里挂在两个父节点下，拍平后出现两次，后端按数组逐条写入，用户登录后菜单就渲染两遍。

问题不在拍平，拍平本来就该保留重复；错在我们没有在提交前按 id 去重。这篇把两件事放在一起写：怎么把嵌套数组压平，以及怎么按一个键去重。平铺数组的几种去重写法，另一篇已经列过，这里不重复，只写这次真正用到的部分。

递归拍平：先能跑，再谈边界

最直接的版本是递归，遇到数组就往下走，遇到值就收集：

Array.isArray 是 ES5 的方法，比 instanceof Array 可靠：跨 iframe 传来的数组，instanceof 会判断失败，Array.isArray 不会。这一点在讲手写 instanceof 的那篇里提过，这里直接用现成的。当年的项目还要照顾 IE8，它没有这个方法，兜底是 Object.prototype.toString.call(item) === '[object Array]'，效果一样，只是每次判断多一层调用。

这个版本能处理常见的树形结构，但三个边界都没管：嵌套深度、循环引用、超深递归。前两个会给出错误结果，第三个会让页面直接崩。另外还有两处不显眼的地方：数组里的空位，以及调用方传进来的类数组，后面各说一段。

边界一：只要拍平到某一层

有些场景不想全拍平。比如表格的展开行，第一层是分组，第二层才是数据，拍平一层就够。加一个深度参数：

depth 为 0 时返回的是原数组的浅拷贝，数组元素原样保留；depth 为 1 只展开一层。语义要和调用方对齐，不然”拍平”和”拍平一层”会混成一个需求。

空位和类数组：Array.isArray 管不到的地方

用手写下标循环拍平，碰到稀疏数组时会把空位当成 undefined 收集进去。[1, , 3] 的长度是 3，下标 1 上什么都没有，可 list[1] 读出来就是 undefined，out.push 便真的往结果里放了一个 undefined。这些值到了接口层，要么变成字符串 "undefined"，要么让后端的 id 校验直接报错。

如果业务上”空位”应该被跳过，判断得写成 i in list，不能写成 item === undefined——后者会把真正的 undefined 元素也一起丢掉，而这两者在需求里未必是同一个意思。我们最后的选择是保留真正的 undefined、只跳过空位：

另一半是类数组。arguments、querySelectorAll 返回的 NodeList、jQuery 对象，Array.isArray 都返回 false，拍平会把它们当成一个普通值原样塞进结果，而不是展开。遇到这种输入，调用方先用 Array.prototype.slice.call(list) 转成真数组再传进来，别让拍平函数去猜。

path 只在当前分支上保留，所以同一个子数组被两个父节点共享时，两次都会展开，不会被误判成循环。这个细节很重要：[a, a] 里的 a 是共享引用，不是环，不该被丢掉。

检测到环之后我们选择”跳过”，不是抛错。配置数据里出现环，通常意味着上游构造有问题，但页面还得能打开；跳过至少能显示其余部分，错误留给日志。

边界三：递归会爆栈

一万层嵌套的数组，递归走不到底就会抛 RangeError: Maximum call stack size exceeded。这种数据在业务里不该出现，可一旦出现，页面就白屏，连错误提示都来不及渲染。

改成显式栈，用循环模拟递归：

栈里每一帧记录”当前处理到哪个数组的第几个位置”，展开子数组就压入新帧，处理完弹出。它不依赖函数调用栈，嵌套再深也只占堆内存。

这个版本没有做环检测。要加的话，得在压栈时记录当前路径，或者在帧里带一个父链。我们最终没有把它和环检测合在一起：业务里处理树形配置用递归加 path，处理用户上传的任意嵌套数据用迭代版，两个场景分开，代码各自简单。

拼结果的两个坏习惯

最早那版递归里，我写的是 out = out.concat(...)，每一层返回新数组、上一层再拼起来。它能跑，但元素被反复复制，嵌套越深、数组越大，开销涨得越快。改成把同一个 out 传下去、只做 push，路径就短了。递归函数返回新数组看起来更”函数式”，在这种一次性收集的场景里并不划算。

另一个习惯是 Array.prototype.push.apply(out, chunk)，想一次把整个子数组推进去。子数组小的时候没问题，元素一多就会抛 RangeError: Maximum call stack size exceeded——apply 的第二个参数会展开成实参，实参数量有上限，各引擎不同，但都经不起大数组。真要批量追加，还是写循环，或者按固定大小分批 apply。

去重：别再数一遍八种写法

平铺数组去重，无非 indexOf、排序后相邻比较、对象哈希、filter 这些路子，各自的比较口径和兼容性另一篇写得很全。这次的需求多了一个条件：数组元素是对象，要去重的键是对象的 id，不是对象本身。

indexOf 对对象是按引用比较的。两个 {id: 3} 字面量不是同一个对象，indexOf 认为它们不同，去重直接失效。按 JSON.stringify 做键也不可靠：对象键的顺序不同会得到不同字符串，undefined 会被丢掉，遇到循环引用还会抛错。

所以这里要的是一个”按函数取键、再用键做哈希”的去重：

keyFn 不传时按元素本身做键，适合数字和字符串；传了 keyFn 就按返回值做键，适合对象数组。遇到对象键直接抛错，是因为 String({}) 全是 [object Object]，不报错的话会把所有对象错误地合并成一个。

键里的几个坑

第一是类型。1 和 '1' 在对象里会变成同一个键，所以 key 里拼了 typeof 前缀。数字 1 的键是 number:1，字符串是 string:1，两者不会互相覆盖。

第二是 NaN。NaN === NaN 是 false，用 indexOf 去重去不掉它；但 String(NaN) 是 'NaN'，哈希键相同，所以哈希法反而能把它们合并。这两种行为哪个”对”取决于业务定义，我们选的是合并，因为权限 id 里不会出现 NaN，而统计数组里重复的 NaN 通常就是同一个缺失值。

第三是 -0。String(-0) 是 '0'，和 0 同键，去重后只剩一个。0 === -0 本来就是 true，这个结果和 === 的口径一致。

第四是 __proto__。用普通对象做哈希表时，键名恰好是 __proto__ 会碰到原型上的特殊属性。我们的键带了 string: 前缀，不会正好等于 __proto__；再加上 Object.create(null) 创建的无原型对象，这层风险就没了。IE8 没有 Object.create(null)，当年的兜底是用普通对象加前缀，原理一样。

组合起来用

权限树的处理分三步：拍平、去重、排序。

顺序很重要。先去重再排序，比较次数少；先排序再去重，保留的是排序后的第一个，和”保留原顺序的第一个”不是一回事。我们的需求是保留菜单本来的顺序，所以去重必须在排序之前。

uniqueBy 保留的是第一次出现的元素。要保留最后一次，可以从后往前遍历，再把结果反转；或者用哈希记下每个键的最后下标，最后按下标取值。两种写法都可以，关键是需求里说清楚”重复项保留哪一个”，不然前后端各按各的理解，数据对不上。

排序这一步同样会咬人

组合那段里按 order 排序，比较函数必须返回数字。更常见的一个坑是直接调 ids.sort()：不带比较函数时，元素先转成字符串按字典序排，[3, 10, 21] 排完是 [10, 21, 3]。权限 id 从个位数涨到两位数那天，菜单顺序就乱了，测试还未必发现，因为用例里只有个位数。

还有一个当年的现实问题：规范没有要求 sort 稳定。元素少时各引擎多半用插入排序，看起来稳定；超过某个阈值换成快速排序，相等元素的相对顺序就可能变。我们的权限项有 order 相同的情况，两次加载出来的菜单顺序不一样，用户以为权限被人改过。最后的做法是给比较函数补一个 id 兜底，相等时按 id 排，顺序才算固定。稳定排序是后来才写进规范的，2016 年不能指望。

反方向：把一维数组还原成树

保存提交的是 id 数组，加载时接口返回的是带 parentId 的平铺记录，页面还得把它还原成树。这件事不要每插一个节点就去原数组里找父节点，那是平方级的；两遍循环就够：

第一遍建索引，第二遍挂接。父节点排在子节点后面也没关系，因为索引已经全部建好。parent !== node 是防脏数据里出现自己指向自己；父 id 找不到时我们把它当根节点放进 roots，而不是悄悄丢掉——菜单少一块比多一个顶层项更难排查。

两个方向的前提是同一套 id 口径。拍平时接受重复 id，还原时重复 id 会在 byId 里互相覆盖，最后只有一个能挂上孩子。所以去重那一步不是可选项，它是还原能正确工作的前提。

测试用例

这几个函数我们留了一组用例，改完跑一遍：

  • flatten([1, [2, [3]]]) 得到 [1, 2, 3]。
  • flattenDepth([1, [2, [3]]], 1) 得到 [1, 2, [3]]。
  • flatten([1, [], [2, []]]) 得到 [1, 2]，空数组要被跳过。
  • 自引用数组不进入死循环，返回其余元素。
  • flattenDepth 超过指定层数的部分仍以数组形式保留。
  • buildTree 在记录乱序、父节点后到时仍能还原层级。
  • buildTree 遇到找不到父节点的记录，把它放进根列表而不是丢掉。
  • uniqueBy([1, '1', 1], null) 得到 [1, '1']。
  • uniqueBy([NaN, NaN], null) 得到一个 NaN。
  • 对象数组按 id 去重，重复项保留第一次出现的那个。
  • 不传 keyFn 却传对象数组，应当抛错，而不是悄悄合并。

第三组用例是空数组。递归版本里空数组不会 push 任何东西，结果正确；迭代版本压栈后立刻弹出，也正确。这种”看起来不会错”的地方，反而是改代码时最容易碰坏的。

这组用例放在页面初始化前跑，用最普通的断言函数，不引测试框架。当年的构建流程没有现在这么顺，为几个纯函数装一套 Runner 不划算；等函数搬进公共库，再补正式的单测。

收尾的表

场景 用什么 注意
普通嵌套数组 递归拍平 数据可信、层级不深
只展开到某一层 flattenDepth 深度语义要和调用方对齐
数据可能含环 递归加路径检测 共享引用不能被误判
层级可能极深 显式栈迭代 不依赖调用栈
对象数组按字段去重 uniqueBy 加 keyFn 键必须是原始值
去重后保留顺序 哈希法从头遍历 保留第一次出现
需要保留最后一次 逆序遍历或记下标 需求要写清楚

拍平和去重都不难，难的是先把数据形状和”重复”的定义说清楚。同一个 id 出现两次，是数据错误还是业务允许？保留第一条还是最后一条？这些问题答不上来，代码写得再短也只是把错误藏得更深。
