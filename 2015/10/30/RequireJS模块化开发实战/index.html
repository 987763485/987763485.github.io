RequireJS 模块化开发实战

2015 年末，把 RequireJS 用熟仍是很多前端项目的日常：老页面靠它组织 jQuery 插件，新项目又在观望 CommonJS 与打包器。本文从实战与源码两条线切入，先讲清楚 data-main、require.config、define 与 shim 怎么写才不出错，再钻进 RequireJS 内部看它如何维护模块状态、如何靠一个当年的小技巧判断”当前正在执行哪个脚本”。适合手上还有 RequireJS 项目、或者正评估要不要迁移的人读完。

RequireJS 到底解决了什么

在把一堆 <script> 标签按顺序排好、靠全局变量互相引用的年代，前端的模块化痛点很朴素：加载顺序不能错、全局命名空间不能碰、异步加载又拿不到依赖就绪的信号。AMD（Asynchronous Module Definition）就是为浏览器设计的规范，它允许你声明”我需要哪些模块，等它们都到位了再执行我的工厂函数”。RequireJS 是这套规范最主流的运行时实现，2.1.x 一代在本篇写作时已相当稳定。

它和 CommonJS 的思路差异一句话说清：CommonJS 假设模块同步可得（Node 从磁盘读，很快），AMD 承认模块要下载（从网络取，不确定何时到）。至于 CMD 与 SeaJS，那是同期另一条路线，本文只在需要对照时提一句，主体仍是深挖 RequireJS 自身。

RequireJS 的对外接口只有两个函数。define 用来声明一个模块，require 用来消费模块并触发加载。二者签名几乎一样，区别在于语义：define 里的工厂函数返回值会作为模块的导出被缓存，require 的回调只是拿依赖跑一段副作用逻辑，不产出可复用的模块。

实践里强烈建议用匿名模块。命名模块把 id 写死在文件里，一旦 baseUrl 或目录结构调整，文件和配置里的名字会对不上；匿名模块的 id 由 RequireJS 依据请求它的 URL 归一化得出，只维护 paths 一处即可。命名 id 真正的用武之地是 require 回调里做 require(['math/add'], ...) 之外的动态跳转，或者打包时手工指定合并产物的名字。

依赖数组的回调参数顺序严格对应数组顺序，这点没有回旋余地。若依赖很多想避免记顺序，可以用 require 传 CommonJS 风格的 exports/require 特殊名，但那会牺牲可读性，一般不推荐。

模块状态机与依赖解析（源码视角）

RequireJS 内部把每个模块维护成带状态的对象，粗粒度看有三种：未定义（还没执行过 define，只登记了请求）、定义中（工厂正在执行或依赖尚未齐备）、已定义（有可复用的 def 导出值）。当 require 或 define 请求一个模块，核心逻辑大致是：查注册表；命中已定义就立即回调；未定义则发起 <script> 加载并把请求压进队列；加载回来后执行该文件里的 define，把工厂暂存为”定义中”，再递归确保其依赖全部就绪，最后调用工厂、把返回值置为”已定义”、通知等待它的调用方。

这套解析是深度优先且带环检测的。makeRequire 值得单独一提：工厂函数第二个参数若要 require，RequireJS 并不直接把全局 require 丢给你，而是通过 makeRequire(context, ...),造出一个绑定了当前模块上下文的新 require。这样模块内部写的 require('./helper') 会以”当前模块的 URL”为基准解析相对路径，而不是全局 baseUrl。理解了 makeRequire 就理解了为什么同一句相对 require 在不同模块里指向不同文件。

flowchart TD
  A[require 请求模块] --> B{注册表命中且已定义}
  B -- 是 --> G[直接执行回调]
  B -- 否 --> C[插入 undefined 队列]
  C --> D[创建 script 标签加载]
  D --> E[文件内 define 暂存工厂]
  E --> F[递归解析依赖后置为 defined]
  F --> G

匿名 define 如何知道”自己是谁”

这是 RequireJS 当年最著名的兼容技巧之一。匿名 define 的工厂不带 id，加载器必须知道”此刻正在执行的这段脚本对应哪个请求”才能给模块命名。在支持 HTML5 async/defer 且能正确触发 onload 的浏览器里，加载器在插入 <script> 前记下预期路径，onload 回调里把刚暂存的匿名 define 认领给这个路径。问题在旧版 IE：动态插入脚本时 onload 触发时机不可靠，多个脚本几乎同时回来时，define 被调用的顺序和 <script> 插入顺序对不上，认领就会错位。

RequireJS 的对策是主动去”问”当前正在执行的脚本是谁。它利用 document.currentScript（现代浏览器）以及更早的 interactive 态：在 IE 里，正在执行的 <script> 其 readyState 会短暂处于 interactive。核心思路是遍历 document.getElementsByTagName('script')，找出 readyState === 'interactive' 的那个，读它的 src 得到当前模块 URL；找不到再退而检查刚触发的加载事件。这就是为什么你在源码里会看到一段专门轮询 script 标签 readyState 的代码，它本质是为 IE 兜底的”这是谁在调用我”探测器。非浏览器或 Node 环境跑 r.js 时这段则靠别的途径确定上下文。

shim 为什么要在依赖执行后轮询全局

明白了 shim 的语义就明白它为什么要轮询。一个往 window 上挂全局的老脚本没有 define，RequireJS 无法从”工厂返回值”得知它就绪，只能靠执行完后去检查 exports 声明的那个全局是否存在。于是加载流程变成：先确保 deps（如 jquery）都”已定义”，插入 shim 脚本、等它 onload/interactive 执行完，再反复轮询判断 exports 对应的全局是否出现或函数返回真值，出现了才把这个模块置为”已定义”并放行下游。

这解释了两个现象。第一，shim 的 deps 只对”经由 RequireJS 加载的 shim 脚本”生效，如果你在页面顶部用普通 <script> 直接引了 jquery 又想 shim 一个插件，依赖顺序并不会被保证。第二，如果 exports 写错（比如全局挂载点变了），轮询会一直拿不到就绪信号，最终超时并在控制台报模块未定义——这类报错的根因常常不是路径，而是 exports 判据失效。

循环依赖与 exports 延迟写法

AMD 的异步语义让循环依赖变得棘手：A 依赖 B、B 又依赖 A，深度解析时一方还没”已定义”就被另一方读取，拿到的就是 undefined。RequireJS 给的解法是工厂用 exports 对象、把成员挂到它上面，而不是最后 return 一个整体。因为 exports 引用在工厂一开始就确定并注入依赖，即便对方此刻只看到半成品对象，后续挂载也能被它观察到：

要点是”先挂 exports、后 return“这一延迟写法。用 return {...} 一次性返回，在环里另一侧读到 undefined 时你的模块尚未定义完成，缓存里就没有可用引用；而往注入的 exports 上逐属性赋值，引用本身从一开始就存在，读方即使拿到空壳，等定义收敛后也能读到填充好的字段。话虽如此，循环依赖多是设计信号，能用一层聚合模块或事件解耦就别留环。

模块化开发期一个模块一个文件，上线时几十个 <script> 请求会撞上当期”单域名约 6 条并发连接”的天花板，需要用 r.js 合并压缩。r.js 基于 RequireJS 核心做静态分析，把入口模块沿依赖图收集成一个文件。典型配置写在 build 文件里：

optimize 控制压缩（uglify 一代最常见，可设 none 只合不压）。modules 允许一次产出多个合并包，name 是入口，include 强制并入指定模块，exclude 把某些模块留给别的包（比如把 jQuery 单独打成 common 包），stubModules 把插件替换成占位实现以减小体积。把 jQuery 插件这类 shim 依赖打进单个文件，做法是给它建一个 vendor 模块、在 shim 里声明好 deps 与 exports，让入口 include 它。

合并粒度与版本号之间要权衡。全合一个包，任何一处小改都让整包 hash/版本号变化，用户重下全部；按”稳定的库层 / 半稳定的组件层 / 频繁变动的业务层”分几个 modules，配合产物文件名带版本或内容指纹，业务改动只刷新业务包，库层继续命中强缓存。代价是包间依赖要理顺、exclude 要保证同一模块只出现在一个产物里，否则运行时重复定义。上线后用 data-main 指向合并产物、paths 相应精简，运行期不再逐模块请求。

相对路径解析到意料外位置 忘记 makeRequire 以当前模块 URL 为基准 显式以 baseUrl 起算或用 paths 别名，少写跨目录相对 require

2015 年末的 AMD 处境

得诚实写一句判断。到了 2015 年末，AMD 的光环已经过去：CommonJS 生态加上 browserify，以及正在被越来越多人接受的 webpack（彼时还是 1.x 一代），让”把模块图交给打包器静态解析、同步 require 写法”成为新项目更自然的选择。define 那套异步加载语义在打包场景里变得多余——依赖既然已在构建期确定，运行期就不再需要”等模块下载”的回调舞蹈。

但存量项目和 jQuery 插件生态仍然大量依赖 RequireJS，它的 shim 与运行时容错在这些地方依旧稳。所以本文定位是”把手上的 RequireJS 项目做扎实，并在迁移前给你一个可评估的底”：如果团队还停在运行时装配、且强依赖异步按需加载，RequireJS 能继续服役；如果已经转向构建期打包，那 define/require 这层就该逐步收敛到 require/module.exports，或干脆交给 2015 年还处在 1.x 一代的 webpack 的 entry/output 去管。

小结

RequireJS 的实战面在于配好 data-main、baseUrl/paths/shim，优先用匿名 define，让 paths 成为唯一的地址来源。它的架构面更值得记住：模块以未定义/定义中/已定义三态流转，makeRequire 决定相对路径基准，interactive/readyState 探测解决匿名模块”我是谁”的认领难题，shim 靠执行后轮询全局判就绪，循环依赖靠延迟写 exports 兜底。打包时用 r.js 的 modules/include/exclude 分层，在合并粒度与版本号之间替缓存做取舍。技术没有永远的先进，把当前这套用透、并知道边界在哪，比赶一个新名词更重要。
