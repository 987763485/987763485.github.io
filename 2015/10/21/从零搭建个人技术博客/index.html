从零搭建个人技术博客

本文面向想拥有一块自留地、但还没接触过静态博客生成器的同学，完整记录我用 Hexo 3 从一个空目录做到线上可访问站点的全过程：环境怎么装、站点配置里哪几项真正要紧、站点与主题两个配置文件各管什么、生成与预览的产物在哪、部署到 GitHub Pages 或自己的 Nginx 服务器要怎么走，以及遇到 404、样式丢失、时间戳不对这类怪问题时的排查顺序。读完你应该能照着命令把同样的流程在自己的机器上复现一遍。写作侧的 Markdown 规范不在本文范围，这里只管”把博客跑起来并部署出去”。

为什么选静态博客生成器

我的需求很朴素：写技术笔记、能归档、能分类、手机上看得舒服，而且不想为了一堆破服务器付钱、不想装数据库、不想半夜起来重启 PHP。静态博客生成器正好卡在这个需求上：我用 Markdown 写文章，工具在本地把整个站点渲染成一组静态的 HTML、CSS 和图片文件，我只要把这堆文件推到哪里，哪里就是博客。托管可以是 GitHub Pages，也可以是一台最便宜的 VPS 上的一坨 Nginx 静态目录，没有数据库、没有运行时、没有可被攻击的动态接口。代价是内容不会自己变：每篇文章改完都要重新生成、重新推送一次，评论和访问统计这类动态能力得靠第三方脚本外挂。对个人技术博客来说，这个代价几乎可以忽略。

一个值得提前想清楚的问题是中文标题与文件名 slug 的关系。new_post_name 默认是 :title.md，也就是说文章文件名直接取自你输入的标题。如果标题是中文，文章 URL 里的 :title 也会是那串中文，经浏览器转码后变成一长串百分号编码，分享和引用都很难看。我的取舍是：front matter 里的 title 随便用中文，但建文件时用英文或拼音短语当标题，或者建完手动把 _posts 下的文件名改成短 slug，front matter 里的 title 字段保持中文。文章 URL 稳定、好看、可分享，比文件名”原样忠实”重要得多。

本地预览、生成产物与 hexo clean

写完先别急着部署，起本地服务看一眼：

hexo server 是在内存里渲染给你看的，不产生文件。真正要上线时执行 hexo generate，生成器会把 source/_posts 里每篇 Markdown 套上主题的布局模板，连同分页、归档、标签页一起写成静态文件，全部落进 public/ 目录：首页 index.html，文章页按 permalink 规则生成目录和 index.html，标签与归档各有自己的分页，主题的资源文件被编译复制进 public/css、public/fonts 等位置，带资源目录的文章会多出同名文件夹。要记住一条纪律：public/ 是产物，永远不要手改它，任何改动都应该改 source 或配置，然后重新生成。

本地预览和线上表现不一致时，我按下面顺序排查：先看是不是改了配置没重新生成；再看是不是缓存捣鬼。Hexo 为速度做了读缓存，改主题、改 permalink、调时区这类全局性变更后，旧缓存常常让新配置”看起来没生效”，这时执行：

hexo clean 会清掉缓存和整个 public 目录，是解决”明明改了却没变化”这类怪问题的第一板斧。我后来养成了习惯：凡是部署前，先 clean 再 generate，宁可多花几秒。

    A[Markdown 文章与站点配置] --> B[hexo generate]
    B --> C[public 静态目录]
    C --> D[推送到 gh-pages 分支]

经典坑：站点与主题各有一个 _config.yml

第一次换主题时我在配置里翻来覆去找不到某个开关，后来才明白 Hexo 有两个 _config.yml：站点根目录那个管全站渲染（标题、URL、permalink、分页、启用哪个主题）；themes/主题名/_config.yml 那个管主题自己的呈现（导航菜单、页脚、每页摘要长度、要不要显示归档计数），后者只被主题模板读取，和前者互不干涉。想改首页每页条数去翻主题配置、想加导航菜单去改站点配置，都是白费功夫。改之前先问自己：这个开关影响的是”生成什么”还是”怎么显示”，前者归站点，后者归主题。

主题的目录结构同样值得搞清楚。以默认主题 landscape 为例：layout/ 下放的是各类页面的模板，首页、文章页、归档页分别对应不同文件，partial/ 是复用的片段；source/ 下的静态资源会被原样并入站点产物，主题样式在 source/css/style.styl，用 Stylus 写，hexo generate 时编译成 public/css/style.css；_config.yml 里的键被模板直接引用；scaffolds/ 定义新建文章的模板。覆盖关系有一条实用规则：站点 source/ 下如果出现与主题 source/ 同名的文件，站点的会赢。所以想小范围改样式，不必 fork 整个主题，在站点侧放一个同名文件覆盖过去即可；但改 layout 模板这种结构性内容，还是直接改主题文件、或者从社区主题仓库拉一份自己的副本来得干净。

部署路线一：GitHub Pages

GitHub Pages 是零成本路线的首选，规则围绕仓库命名：用户主页仓库必须叫 用户名.github.io，这个仓库的 gh-pages 分支内容会发布到 http://用户名.github.io/；个人主页仓库也可以直接发 master 分支。另一种形式是项目页，仓库可以随便起名，站点挂在 http://用户名.github.io/仓库名/ 路径下。绑定自定义域名则在仓库根放一个 CNAME 文件写上域名，再把域名解析指过去。

部署思路有两种。第一种是把 public 当产物手动推上去：hexo generate 之后，进入本地维护的 pages 仓库目录，清空旧内容，把 public 里的文件整体拷贝进来提交推送。好处是不依赖任何插件，坏处是每次操作繁琐。第二种是让 Hexo 自己管部署：Hexo 3 把部署也拆成了插件，装一个 git 部署器后在站点配置里声明类型、仓库和分支，以后一条 hexo d 即可完成生成加推送：

无论哪种方式，有一个坑都绕不开：换成自定义域名后，站点配置里的 url 必须同步改成绑定的域名，否则模板按旧的 用户名.github.io 拼出来的绝对路径资源在新域名下全部找不到，页面框架在、样式和图片全挂，看起来像 404 又像被盗了版。同理，如果站点挂在子路径（项目页的 /仓库名/），url 和 root 都要带上这层前缀，改完照例 clean 再 generate。

RSS 与站点统计这类需求

订阅需求当期就有现成解法：官方插件体系里有生成 feed 的生成器，装上之后站点会多出 feed 文件，主题模板里补一个订阅入口即可。访问统计则不必自己写后端，挂一段第三方计数脚本进模板页脚就能看个大概，精度有限但够用。我当时的判断是这两类需求都不构成换框架的理由，静态站外挂脚本是老而可靠的模式，后续想认真做统计再考虑自己用 Node 起一个小收集器。

排错清单

把这一路撞过的坑整理成表，顺序按”症状到处理”来查：

症状 原因 处理
文章页线上 404，本地正常 只推送了部分产物，或 permalink 变更后旧链接失效 clean 后全量 generate，整体重推；确认新 permalink 规则
页面文字在、样式全丢 url 与实际访问域名或子路径不一致，资源拼成错误绝对路径 把 url、root 改成与访问地址一致，再 clean 重新生成
deploy 时报权限错误 SSH 公钥没加到 GitHub，或当前账号无仓库写权限 补公钥、确认权限；急上线就直接手动推 public
发布时间与写作时间差 8 小时 站点配置未设 timezone，文章时间按 UTC 解读 设置 timezone 为 Asia/Shanghai，clean 后重新生成
本地 hexo server 正常，线上空白页 本地内存渲染用不到线上那层路径前缀，产物里资源引用 404 核对 url、root 与仓库名或域名前缀，重新生成部署

排查时养成”先复现再看路径”的习惯：404 和样式丢失九成九是路径拼错，打开浏览器开发者工具的 Network 面板看哪个请求挂了，比盲改配置快得多。

小结

静态博客生成器的价值，在于把”写作”和”发布”拆成两段：我负责在 source/_posts 里积累 Markdown，工具负责把它变成可部署的静态产物。环境上认准 Node 4.x 加 hexo-cli 的安装路线；配置上记住站点和主题各有一个 _config.yml，管的东西互不重叠；部署前永远先 clean 再 generate；url 和 root 要与最终访问地址严格一致，这是绝大多数线上怪病的病根。把这几条内化成习惯，搭博客这件事就从玄学变成了体力活，剩下的时间都可以花在真正重要的事情上——把笔记写好。
