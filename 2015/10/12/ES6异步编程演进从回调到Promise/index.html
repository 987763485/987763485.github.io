ES6 异步编程演进：从回调到 Promise

本文是编年史系列的一次阶段性收束：ECMA-262 第 6 版定稿不到四个月，异步生态正卡在”回调 → Promise 标准化 → Generator 协程尝鲜”的中间态，值得把 2009 年以来这条路怎么走到的、沿途踩过的坑、以及此刻摆在桌面上的选型，放在一起复盘一遍。分工先说清：单线程与任务队列的机理，《JavaScript 单线程与异步编程模型》与《JavaScript 事件循环机制解析》已经讲透；jQuery Deferred 那些私有语义，它的专篇也写过了；Promise 的横向选型与 Generator 的语法细节，本系列前面写过，本文一概不重复。本文的镜头对准三件更有纵深感的事：回调作为契约为什么靠不住、标准与实现从哪一天开始分裂、以及迁移途中最容易付学费的三个坑。

但真正的病灶不在参数形状，而在信任。回调是一次彻底的控制反转：你把”拿到结果之后做什么”这段最要紧的逻辑，交到一个第三方手里，而对方拿走的义务只有口头约定。把契约逐条摊开，你会发现没有任何一条是强制的：

  • 回调可能被调用零次。底层超时、进程半路异常、实现者忘了触发，你的后续逻辑就无声蒸发。
  • 可能被调用多次。轮询包装器、重复触发的事件源，都可能在同一个”应该只结算一次”的场景里回调你两遍。
  • 可能带着错误的参数被调用。err 里塞个字符串、成功时 err 不为 null，全靠对方自觉。
  • 可能同步调用，也可能异步调用。同一个 API 在缓存命中时同步执行回调、未命中时异步执行，你的代码两条路径交替走，这类”有时同步有时异步”的 bug 在 2014 年前后的社区讨论里被反复解剖，症状就是错误栈和用户感知的时序时对时错。
  • 回调里抛出的异常没有上层调用栈可接。浏览器里落到 window.onerror，Node 里直接崩进程，错误被”吞”或者被”炸”，唯独不会被”传”。

async.waterfall 这类工具库把嵌套拍平了，但要看清它治的是缩进，不是契约：每个任务依然可以违约，只是违约的伤害被更深的闭包藏起来了。2015 年我们回头看，回调时代真正缺的不是格式化工具，而是一套”结果对象”的强制语义。

Promise 的价值：把异步结果变成可组合的一等值

Promise 做的事，说到底是把”未来的结果”升格成一个可以拿在手里传递的对象，然后围绕它立三条铁律：状态机单向转移、只结算一次、链式传递。状态机长这样：

flowchart TD
    A[pending 等待中] -->|resolve 或被采纳| B[fulfilled 已成功]
    A -->|reject 或回调抛出异常| C[rejected 已失败]
    B --> D[结算后状态永久固定 再调用无效]
    C --> D

至于状态转移为什么必然发生在微任务边界、then 回调如何排队，前作已经展开过，这里一句带过。值得单独说的是这三条铁律各自消灭了上一节的哪一类违约：单向状态机消灭”被调用多次”；构造函数出口消灭”被调用零次也没人知道”；而”同步还是异步”这一条，Promise/A+ 当年就明文要求 then 的回调必须异步调度，哪怕 promise 已经结算完毕，回调也至少推迟到当前轮次的末尾。当年这个规定的动机说得很直白：别让调用方区分得出同步还是异步。

链式传递的规则值得慢慢重申一遍，因为后面的坑几乎都从它长出来：then 的回调执行完之后，结果只有三个去向——普通值、thenable（包括 promise 本身）、抛出的异常；前者直接结算新 promise，中者被递归采纳直到穿透成具体值，后者转成 rejection。这条穷举保证是错误能沿链跨层传播的全部原因，也正是”忘记 return”能让链条安静错位的原因：你没 return，就等于交了一个”普通值 undefined”出去，链子完全按规则走，走得通情达理，也走得无声无息。

笔者在 2015 年做过一次同机同口径的粗测，结论只敢给到量级：一层 Promise 包装相对裸回调的额外分配开销在绝大多数业务链路上可以忽略，真正拖慢页面的是链上顺手做的 JSON 解析与同步布局。所以当年”Promise 慢所以不用”的顾虑，实测下来基本不成立；性能讨论应该看自己的口径，别抄别人的数字。

标准与实现的分裂：从 Promise/A+ 到 ES6

今天回看，Promise 这条线其实有两条平行史：社区规范史和语言标准史，它们在 2015 年交汇，但交汇得比想象中晚。

起点是 2009 年前后 CommonJS 社区的 Promises/A 提案。它只规定了三件事：promise 有 then 方法、then 收成功和失败两个回调、then 返回新 promise。问题恰恰出在没规定第四件事——then 返回的新 promise 到底怎么由回调返回值决定。这条含糊让 jQuery 1.7 的 then 可以”合规地”丢弃返回值（前作分析过它的私有语义），也让同期各家实现各写各的。2012 年，社区把规范从 CommonJS 里拆出来收紧成 Promise/A+：只描述 then 的行为，明确决议流程、明确采纳 thenable、明确回调异步调度，同时刻意砍掉了进度通知、取消和多值传递这些”实现间达不成一致”的能力。A+ 不是一份完整的 API 标准，它是一份最小公约数，正因为小，各库才背得动。

然后是语言这一侧。TC39 在第 6 版里把 Promise 收进标准时，选择了兼容 A+ 的形态：一个合格的 ES6 Promise 必然同时满足 Promise/A+，反过来不成立。ES6 新增的关键贡献是两个协议而不是一堆方法：thenable 协议——任何带 then 方法的对象都能被 resolve 采纳，$.ajax 返回的 jqXHR 因此在原生 Promise 链里可以被直接接力；迭代器协议——Promise.all 与 Promise.race 接收 iterable 而不是硬编码数组。协议化的好处是生态不用等标准扩充方法表。

定稿前夜的库生态大致是这样一个格局，钉住它有助于理解后来谁存活了下来：when 是最早一批成熟实现，围绕它的文档与讨论喂养了后来参与标准化的社区成员；q 由 CommonJS 运动的推动者 Kris Kowal 维护，deferred 与提升（uplift）机制影响了很多后继库；RSVP 与 Ember 深度绑定，长期作为其调度层存在；bluebird 则以 Node 侧的批量包装、可调试扩展和工程化文档，拿下了当时最大的一块生产份额。ES6 定稿之后，这些库的”公约数部分”迅速贬值——标准已经替你定义了 then 该怎么工作——竞争场只剩下扩展能力与调试体验，选型问题因此从”哪家语义对”变成了”哪些能力我还缺”。

代价同样明显：ES6 只定义了构造函数、resolve/reject/all/race 静态方法与 then/catch 实例方法，仅此而已。done、finally、spread、timeout、retry、按类型过滤的 catch、长栈追踪、Node 风格 API 的批量包装，一个都不在标准里——done 与 finally 在当时均非标准，这一句必须在 2015 年反复强调，因为不少从 bluebird 迁移回来的代码默认它们人人都有。于是出现了很拧巴的局面：语言标准落地了，选库问题不但没消失，反而更精细了。下表是笔者当时整理的对照，可以直接当今天的检查单用：

浏览器现实也在逼迫选型。原生 Promise 在 Chrome 32、Firefox 29、Safari 7.1 之后可用，IE 全线缺席，直到今年随 Windows 10 发布的 Edge 12 才是微软第一个有原生实现的浏览器；而我们的移动端底线是 Android 4.4 的 WebView 与 iOS 7/8，这两个环境都没有 Promise。所以 2015 年的标准动作仍然是上 polyfill：要么用 es6-shim 或 core-js 做特性检测与补齐，要么整体引入 bluebird。当年有一个流传不广但必要的细节：早期 Chrome 的原生实现带过不符合 A+ 的中间版本，靠谱的 shim 会做行为探测再决定是否覆盖全局，而不是见 window.Promise 存在就跳过。另外别养成”全站换成 bluebird 的 Promise”的习惯——全局构造函数一旦被替换，instanceof、与其他库返回的 native promise 的互操作、以及调试器里的栈都跟着变，2015 年已有同事踩过这个坑：bluebird 替换全局后，某个只认原生 then 参数形态的老旧埋点库静默失效。稳妥做法是局部引用，变量名就叫 P 或 PromiseB，边界处靠 thenable 协议自然互转。

还有一个与调试直接相关的分裂：原生 Promise 对未处理的 rejection 在 2015 年几乎沉默——catch 忘了写，错误就无声消失，控制台是否提示完全取决于引擎版本；bluebird 则会在下一轮检测出”未被处理的失败”并打出警告，配合长栈追踪能把异步现场还原到可读的程度。这个差异在当时足以左右选型。

迁移路上最常见的三个坑

坑一：忘记 return，链条在中途断开

2015 年的 code review 里，Promise 相关的驳回意见有一半是这一条：

时序画出来一目了然：

sequenceDiagram
    participant C as 链条下游
    participant T as 中间 then 回调
    participant R as 内层请求
    C->>T: 上游 fulfilled，执行回调
    T->>R: 发起内层请求，未 return
    T-->>C: 回调返回 undefined，链条立即结算
    C->>C: 下游 then 与 catch 提前开始
    R-->>T: 内层稍后才完成或失败
    T->>T: 结果无人接收，失败漂成未处理 rejection

症状有两个面：下游拿到 undefined 而不是订单，业务在离案发点很远的地方崩；内层请求失败时没有 catch 接得住它，在原生实现里无声消失。修复只有一个词：return。当年排查这类问题的土办法是给链尾补一个 .done()（bluebird 语义，非标准）或者手动加一个 console.error 的 catch，让漂移的错误至少冒一次头。根因层面记一句话就够：then 返回新 promise 这件事是免费的，但”把内层 promise 接进这条新链”必须靠 return，JS 不会替你隐式串联。

机制一句话：co 拿到 generator 对象，每 yield 出一个 promise（或 thunk），等它结算后再调 next 把结果送回去；thunk 那条支路靠 thunkify/thenify 把 error-first 函数转成 function (cb) 形态。同期 bluebird 的 Promise.coroutine 走的是同一条路，只是接受的值限定为 promise，与既有 Promise 链的互操作更顺。

台阶是真台阶，账单也是真账单，2015 年要不要上车，得把下面几笔都算完：

  • 错误栈更难读。异常穿过运行器与 next 调用，栈帧里混进调度器的内部函数，定位成本比裸 Promise 链高；bluebird 的长栈追踪能缓解，但它与 coroutine 的组合当时也不算完美。
  • 语义是约定不是标准。yield 一个数组算并行、yield 一个嵌套 generator 要不要委托，这些行为跟着 co 的版本走，换运行器就要重新对表；语言标准化的是语法形状，异步语义并不归它管。同期被认真讨论过又被撤掉的还有一件——Object.observe 今年已被 V8 与规范双方放弃，这提醒我们 2015 年”看起来会赢”的 API 该收的收回、该死的死，没人能保证 generator 编排是例外。
  • 前端要付转译税。原生 generator 在桌面新版 Chrome/Firefox 与 Node 4 上可用，但 IE 与 Edge 12 没有，Safari 7 一代也不行，转译仍是前端主流路径；Babel 5 把 function* 降级成 regenerator 状态机后，包体要背上运行时的固定开销，量级是几 KB，具体多少以自己项目的打包统计为准，别引用二手数字。
  • 团队的学习成本要有人买单。function*、yield、next(value, err) 的双通道、转译产物里 try/finally 的边角行为——审查这些代码需要全组都跨过同一条线。当时 TC39 已经有更早期的草案在讨论”在 Generator 之上再加一层语法糖”，状态是连时间表都没有的阶段零草稿，本文不展开，但它说明生态的方向：所有人都在给这套机制讨要更便宜的写法。

笔者在 2015 年的判断是：编排密集的 Node 服务（大量串行依赖加少量并行）值得在 Node 4 环境试点 coroutine；前端存量项目在没解决转译基建前不急于切换，Promise 链加严格的 catch 纪律已经够用。语法糖的收益要在三年的维护周期里折现，不是在新语法发布的那个月。

演进时间轴与选型结论

把整条路钉在时间轴上，方便回看自己走到哪一格：

flowchart TD
    A[2009 CommonJS Promises/A 提案] --> B[2011 jQuery 1.5 引入 Deferred]
    B --> C[2012 Promise/A+ 收紧为最小公约数]
    C --> D[2013 bluebird 与 co 先后成型]
    D --> E[2014 Chrome 32 等浏览器原生 Promise 落地]
    E --> F[2015-06 ECMA-262 第 6 版定稿]
    F --> G[2015-09 Node.js 4.0 LTS 合并 io.js]

对照 2015 年 10 月的现实约束，选型可以按四条约束走：

项目处境 建议
必须支持 IE，不能上转译 原生 Promise 不可用：挂 es6-shim/core-js 补齐，或局部引入 bluebird；jQuery Deferred 链可继续存量维护，但新旧边界用 thenable 协议互转，不混用语义
现代浏览器为主，底线含移动端旧 WebView es6-shim 或 core-js 做一次覆盖判断，之后代码按原生语义写；不替换全局 Promise
Node 4.0 新服务 原生 Promise 起步；IO 密集、调试压力大时局部用 bluebird 换长栈追踪
Node 0.10/0.12 存量服务 bluebird 统一胶水层，promisifyAll 划清可用边界；Generator 编排可先试点 coroutine

还有一个与库无关的结论值得单独强调：以上任何一栏，团队都应当先统一”一条链一个终点 catch、中间 promise 必须 return、失败语义不许沉默”这三条纪律。2015 年的经验是，Promise 事故的多数根源从来不是选了哪个库，而是纪律没立住。

小结

复盘这几年，异步编程的核心矛盾其实始终是同两件事：契约与错误传播。回调时代契约只存在于文档和自觉，错误传播根本不存在；Promise 用状态机、只结算一次和 then 边界收敛了契约，用链式下传的 rejected 状态接住了错误传播，但把 finally、取消、Node 胶水这些能力留在了标准之外，于是 2015 年的我们仍然要选型、要 polyfill、要手写 race 超时。Generator 与运行器把阅读顺序扳正了过来，代价是转译税与约定成本，值得上，但要按项目的三年维护周期折现。两条可执行的建议带走：第一，把你写的每一个异步 API 的返回值变成 promise（内部再野的回调都收敛在那层包装里），拒绝再交付需要调用方处理 err 参数的新接口；第二，给每一条链显式的失败终点——最后一个 catch 或者 bluebird 的 done，并给项目装上未处理失败的检测，无论靠库的警告还是 Node 4 的 unhandledRejection 事件。契约和错误处理都不靠自觉，靠结构，这是从回调走到今天最值得固化的肌肉记忆。
