ES6 Module 模块系统与构建工具

ECMAScript 6.0 规范在今年六月定稿，模块声明终于第一次写进了语言标准，但浏览器和 Node 引擎看起来都还没有跟上的意思。本文把 ES Module 与当前主流的两套体系 CommonJS、AMD 放在语法形态、加载时机、绑定语义这些维度上逐条对比，聊聊在 2015 年末这个时间点，我们究竟要靠什么路径才能真正用上这套新语法。适合正在纠结”要不要现在就上 ES6 模块”的前端同事，读完你应该能拿到一份能落地的选型结论。

规范已经落地，引擎还慢半拍

先把时间线摆清楚。2015 年 6 月 17 日，ECMA 大会批准了 ECMAScript 6.0 正式版规范，Module、import、export 这些概念从各社区自发的约定，变成了写进标准册子的语言特性。对前端来说这意义重大：JavaScript 诞生近二十年，一直没有官方模块系统，Node 用 CommonJS，浏览器用 AMD 或者一堆全局变量，同一份代码想在两个环境跑，得靠转译器在中间做翻译。

但”进规范”和”能运行”是两回事，这才是眼下最尴尬的地方。截至本文写作的 2015 年 10 月，浏览器还没有实现 <script type="module"> 这种带模块语义的脚本加载，Chrome、Firefox、Safari 对模块标签的支持都还停留在引擎团队的日程表上，正文里我们也不指望它近期能用；直接在新式 script 标签里写 import，浏览器只会给你一个语法错误。Node 这边同样没有开放 ES Module 入口，刚发布不久的 Node 4 LTS 依然只认 require，.js 文件里出现 import 会被解析器当场拒绝。

所以当前想用 ES Module 语法，只有转译或者打包这一条路：先用工具把模块语法降级成 CommonJS 之类引擎认得的形态，再交给现有的加载体系去跑。语法是新的，运行时是旧的，中间这一段落差要靠构建工具链来填，这也是本文后半部分要重点讨论的。

三种写法，三种心智模型

先简单过一遍三套体系长什么样。CommonJS 是 Node 和 npm 生态的通用语言，一个文件即一个模块，用 require 同步加载，用 module.exports 导出，路径可以拼接、可以写在 if 分支里，一切皆表达式。AMD 是为浏览器设计的异步规范，模块用 define 包裹，依赖以数组声明、以函数参数注入，由 RequireJS 这类加载器在运行时异步取齐依赖再执行工厂函数，加载器本身的实现细节这里先一句带过，后面会有专门篇幅。ES Module 则把依赖和导出都做成了语言级别的声明。

静态结构对动态加载

三者的分水岭不在关键字长什么样，而在”依赖关系什么时候确定”。CommonJS 和 AMD 的模块加载本质上都是运行期的一次函数调用：代码执行到 require('./a') 或者加载器把依赖送进 define 工厂的那一刻，程序才知道自己到底用到了谁。这意味着在静态的源码文本上，工具想数清楚一个项目真正用到了哪些导出，几乎是不可能的，因为路径可以由变量拼出来。

ES Module 走的是另一条路。import 和 export 是声明，出现在模块顶层，路径是写死的字符串字面量，绑定关系在模块求值之前就已经由引擎确定。用一句常被引用的话概括：CommonJS 和 AMD 描述的是”怎样去拿到东西”，ES Module 描述的是”我需要什么”。结构静态化之后，未使用的导出可以在编译期被识别，工具链对代码的理解能力上了一个台阶，这是后面谈 tree shaking 的前提。

绑定语义：拷贝还是活引用

这是三套体系最容易被忽视、又最容易在排错时咬人一口的差异。CommonJS 导出的是值的拷贝：module.exports 被赋值给缓存里的那份对象，而 require 回来后再解构，拿到的是一份快照，源模块后来怎么改，解构出来的变量都不感知。

ES Module 则是实时绑定的引用，业内一般叫 live binding：导入的不是值本身，而是指向源模块内部那个绑定的”传送带”，源端更新，使用端立刻可见。

需要注意两点。一是这种实时性靠的是”引用绑定”而不是对象属性读取，想改导入的绑定在 ES Module 里根本不允许，import 进来的名字如同只读常量，写入会在解析期报错；二是上面这段 ES Module 示例眼下只能在转译器里跑，Babel 转成 CommonJS 之后会用属性访问的方式模拟 live 语义，行为接近但不完全等价，调试时要留意这层翻译带来的失真。

循环依赖的不同下场

模块一多就绕不开循环依赖，三套体系的处理哲学差别不小。CommonJS 的规则是”加载即执行，执行过的进缓存”，遇到环的时候不会死循环，但你会拿到一个半成品：先执行的那个子模块只完成了部分导出。

这种”部分初始化对象”的语义很实在，坑也很实在：bug 的表现取决于 require 的先后顺序，重构时调换两行代码就可能让下游拿到 undefined。ES Module 的设计思路则不同，规范把导入声明做了提升处理，绑定在任何代码执行前就建立完毕，函数声明跨环调用通常没问题，但对顶层变量过早访问会撞上暂时性死区的约束。只是这套行为目前没有真实引擎供我们试验，只能从规范条文和转译器的实现里去推断，把它当作设计目标看待比较稳妥。

2015 年末，我们只有一条路可走

既然后果是”引擎都不认”，那就要看今天就能用的转译路线。目前把 ES Module 语法变成可执行代码，主流做法是转译，代表工具是 Babel。以本文写作时的 Babel 5 为例，命令行转译可以直接这么用：

--modules 这个参数本身就是个隐喻：模块语法只是”输出的外壳之一”，转译器先把 ES Module 拆成普通语句，再套上目标体系的外衣，输出 CommonJS、AMD 还是 UMD 全凭构建时指定。这也意味着接入现有的 Gulp 或 Grunt 流程毫无障碍，转译只是流水线里新增的一道工序。webpack 在 2015 年也刚被越来越多的人接受为打包入口，同样能配合转译消化 ES6 源码，配置细节这里按下不表。

Node 侧还有一种临时试验途径：Babel 5 提供的 babel-core/register 会在 require 链上挂钩，实时转译被引入的源码，配合 nvm install 4.2 切到刚合并回来的 Node 4 LTS，就能在小工具脚本里先体验模块语法。但要强调这只是开发期的取巧手法，入口文件自己仍然不能写 import，挂了 hook 之外的路径一律按普通 CommonJS 处理，把它端上生产只会让冷启动和排错都变得不可控。

另一股值得关注的力量是 rollup，它是今年刚冒出来的新工具，思路与转译器不同：直接以 ES Module 作为输入格式，打包时利用静态结构分析，理论上可以把没被引用的导出去掉，输出再选 CommonJS、AMD 或 UMD。它现在还带着明显的实验色彩，生态和稳定性都谈不上成熟，但它验证了”静态结构对工具友好”这件事确实有商业价值，值得放进观察名单。

转译这座桥上的几个坑

桥是好意，但走上去才知道有颠簸，这里复盘三个我们实际踩过的。第一是 live binding 的翻译失真：转译器用对象属性访问来模拟实时绑定，跨模块读取是实时的了，可一旦你在代码里试图写入导入的绑定，规范里应该在解析期报错的事情，转译产物里往往变成一个难查的运行时赋值失败，代码评审时要靠人肉拦住。第二是循环依赖的行为错位：转译后的 CommonJS 产物遵循的是上一节讲的”半成品缓存”语义，和 ES Module 规范设计里提升绑定的语义并不重合，同一个环形依赖，今天转译跑通不代表将来原生运行也跑通，架构上还是应该把环拆掉而不是赌语义。第三是调试链路的成本：断点打在源码的 import 语句上、栈里却是转译器的产物函数名，source map 覆盖不全的项目体验更差，我们的做法是把转译产物目录整体排除出调试搜索范围，只允许在源码层设断点。这些坑都不大，但每一个都直接影响”现在就上”的信心，也正是团队选型时要把过渡期拉长的原因。

静态结构的红利：tree shaking 是可能性，不是现成能力

有了静态可分析的依赖关系，就引出了近两年被反复提起的 tree shaking 思想：模块的导入导出既然在编译期全部可见，构建器就完全可以判断哪些 export 从未被任何地方 import，打包时把这些”枯枝”摇掉，产物只留真正用到的代码。这在长尾依赖很重的大型页面上想象空间很大。

但必须把话说清楚：截至 2015 年末，这条链路还没有真正闭环。规范只是给了这个可能性，转译器为了忠实还原 live binding 和副作用语义，降级时往往保守处理；打包器普遍还把模块当黑盒整体保留；社区里的库几乎都还没有提供可供静态分析的 ES Module 入口文件。也就是说，现阶段指望靠它减包是缘木求鱼，更现实的做法仍然是传统的按需引入与压缩。合理的心态是：语法先按 ES Module 写，把”将来能被分析”的位置留出来，等工具链追上来再收割红利。

选型对比表

把前面的分析浓缩成一张表，方便评审会上直接引用：

维度 CommonJS AMD ES Module（2015 年现状）
语法形态 require 与 module.exports，皆表达式 define 包裹，依赖数组加回调参数 import 与 export 语言级声明

绑定语义 导出值拷贝，解构即快照 参数注入结果，近似拷贝 对源绑定的 live 引用

我们的结论与迁移过渡做法

综合上面的对比，我们团队给出的选型结论如下。Node 端服务与 npm 包维持 CommonJS 不动摇，这是生态共识，没必要对抗现实。浏览器里的存量 AMD 项目继续按 RequireJS 的方式维护，不为赶时髦而强行翻新，这类改造的投入产出比很难打正。新的浏览器端公共库源码尝试直接按 ES Module 语法书写，构建时用转译输出多格式产物。

至于为什么值得现在就改写法，可以看一段最直观的对照：AMD 里依赖名只是回调参数，拼错、多引、少引都要等到运行才暴露；ES Module 的导入是顶层声明，转译器和检查工具在构建期就能核对每个绑定是否存在。

迁移过渡期我们定了三条纪律：新模块一律按 ES Module 语法写，转译产物进版本库外的构建目录，避免源码与产物混淆；跨体系边界的所有共享代码统一走 UMD 发布，消费方各取所需；AMD 存量只在被动重构时顺手换写法，不做一次性大迁移。工具链上把 --modules commonjs 固化进构建脚本，先在非关键项目里跑一个迭代周期，验证转译产物的调试体验后再全面推开。

小结

ES Module 是 JavaScript 模块化的第一个官方答案，它的价值不在关键字多好看，而在把依赖关系从运行期的动态查找变成了编译期的静态结构：live binding 修正了拷贝语义的快照陷阱，静态声明给了工具分析和 tree shaking 一个可以生长的地基。但落到 2015 年 10 月的工程现实，浏览器不支持、Node 不认、打包器刚起步，语法红利要经过转译这道桥才吃得到，桥本身还有调试失真这样的小疙瘩。我们的选择是用今天的工具为明天的标准预付成本：新代码写 ES Module，产物转 CommonJS，共享库 UMD 兜底，AMD 存量不动。等引擎陆续上牌桌的那天，源码里一行都不用改——这才是这场语法迁移真正的意义。
