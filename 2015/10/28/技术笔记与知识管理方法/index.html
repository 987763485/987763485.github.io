技术笔记与知识管理方法

工作两三年之后，我存下来的技术笔记已超过两千条，可半夜排查线上问题时，还是想不起”我是不是遇到过这个”。这篇文章记录我把笔记体系推倒重来的过程：先讲踩过的坑，再讲换过来之后的几条原则，最后给一套可以直接抄的目录结构与命令。适合同样被”存了很多却用不上”困住的前端，读完你能拿到一套可检索、可版本控制的笔记做法。本文只谈方法，不展开 Markdown 的语法细节，也不涉及博客如何部署。

收藏不等于学会

先说一段不太光彩的自我复盘。我的第一套笔记体系是典型的”剪藏流派”：读到有用的网页，一键存进印象笔记或者为知笔记，看着堆叠的笔记本标题，心里生出一种”这些知识归我了”的错觉。可剪藏进去的内容九成是别人写的教程，我在里面只是个搬运工。剪藏堆成山，绝大多数条目存进去那天就是它最后一次被打开。稍后读工具那边同样糟糕，Pocket 前身 Read It Later 的列表和 Instapaper 的待读区都攒过几百条未读，它们更像一摞我舍不得扔的旧杂志。

第二套体系是”按技术栈分目录”。我在本地建了一棵很讲究的树，jQuery、Backbone、AngularJS、Node 各占一个目录，再往下按”入门””进阶””踩坑”分层。分类美学上挑不出毛病，问题出在跨栈的那类条目上。有一次一个滚动相关缺陷同时牵扯事件委托与浏览器兼容，它到底该归哪个目录？我纠结着复制了三份，此后每一份都不再更新。还有一个更隐蔽的代价：笔记躺在硬盘上，代码躺在 GitHub 上，两边各自漂移。等我重写工具脚本时，笔记里记的用法还是旧的，反而把我带偏。

这两套体系共同的病根是：我把”整理”当成了目的，把”分门别类摆得好看”当成了生产力。而笔记真正的价值只在被检索到的那一刻才兑现。

换过来之后的三条原则

第一条，可检索性优先于分类美学。我不再纠结一个条目”属于哪一类”，而是确保它能被几个关键词找到。分类是昂贵且需要人工维护的索引；关键词只要写进正文，检索时自然命中。一个条目能同时被五个词命中，目录树却逼我二选一。

第二条，输出倒逼整理。判断一段笔记值不值得留下来，我现在的标准是”它能不能变成一篇博客、一次分享或者一段能跑的代码”。只有能对外输出的东西才会被认真核对，也只有认真核对过的东西才配进长期库。这个博客本身就是我笔记体系的出口之一：从排查记录里挑出讲得清的，补上上下文发出去，剩下的才归档。

第三条，笔记必须是纯文本，并且能被版本控制。纯文本意味着它能被 grep，能被 diff，能被任何一个编辑器打开，十年后还能读。它意味着我的笔记仓库和代码仓库用同一套 git 工作流，不需要额外维护一个封闭的数据库。

顺带说一句，我不太信”换个笔记软件就能解决问题”这类说法。这三条原则里没一条依赖具体软件：换编辑器不影响文件，换订阅服务不影响已经抄下来的条目，整个仓库换台机器也只是多一次 clone。工具给的是输入速度和阅读体验，骨架得靠自己那套约定撑住；约定一旦写进某个封闭格式，将来搬家时才知道什么叫成本。

云端笔记软件在我体系里的位置

把话说清楚：我不是弃用了云端笔记软件，而是把它们的职责缩窄了。印象笔记和为知笔记现在只干一件事——收纳那些非我原创、又确实需要留档的外部素材，比如一份设计规范的截图、一张同事整理的兼容表、一次评审的白板照片。它们的检索是服务端的，我没法拿 grep 去查，所以这类内容我一律不指望它参与知识主干。

OneNote 在我这儿扮演类似的角色，但更偏手写与自由摆放。开会时随手画的关系草图、临时贴上去的界面标注，这些内容天生就不是结构化的，硬塞进 Markdown 反而别扭，放 OneNote 里按页面摊开正合适。它的短板和前面两个一样：不能 diff，不能全文检索进我的仓库，所以我从没把它当过技术知识的存放处。

分工就此明确：要用关键词命中、要跟代码一起演进、要我能改能核对的，进本地仓库；外部素材、图形化草稿、只在近期有用的碎片，进云端。混乱往往从”这条到底该放哪”开始，而这个问题本身问错了——该问的是”它将来怎么被找到”。

一个可以直接抄的目录结构

下面这套结构我用了大半年，够简单，也够撑得住。核心是”一文件一知识”，文件名里带日期与关键词，正文头部放 tag，别的一概不要。

命名规则三条。日期用 YYYY-MM-DD，它天然把文件按时间排开；关键词用英文连字符连接，检索时敲英文比敲中文省事；扩展名统一 .md，编辑器与 grep 都好处理。

一条合格的笔记长什么样

结构定完之后，真正决定这套东西有没有用的，是每条笔记里写了什么。我现在要求一个 topics/ 条目至少回答四个问题：我当时观察到什么现象，我的结论是什么，这个结论的依据在哪，以及我还没弄明白什么。

现象这段最容易被省掉，却偏偏最关键。只写”某浏览器的某事件要放在文档上代理才生效”，半年后我看到这句话根本想不起自己踩的是什么坑。写清现象，等于给未来的我留一个可对照的锚点。依据我不追求学术严谨，通常就是”官方文档某节的原话”或者”本机某个版本上试了三次都这样”。留一个”还没弄明白什么”，是给下次更新预留接口——一条看起来完全正确的笔记，往往就到此为止再也不动了；而一条自己承认有疑问的笔记，我下次撞上相关问题时自然会回来看它。

关于代码，我写进笔记的永远是最小可复现片段，而不是从项目里剪切出来的三十行。最小片段能独立跑，能改两行验证猜想；从项目里剪出来的代码脱离上下文就是废纸，而且项目一改它就错，正是前面说的”笔记与代码不同步”的病根。

还有一个习惯是”绝不剪藏整页，一定要自己重写”。看到一篇讲得透的文章，我读完关掉，凭记忆把要点写成自己的条目，再回去核对有没有写歪。这个过程慢得多，可慢正是它生效的原因：读别人写的会以为自己懂了，能用自己的话讲出来才算数。写不出来的那些，被我原样丢回稍后读列表，等真想弄懂再说。

至于 inbox/，它是我容忍混乱的地方。临时想法、别人随口给的提示、来不及归类的片段全扔进去，但每个文件都带日期，每周固定清空一次：值得留的按上面标准重写进 topics/，其余直接删。清空是整套里唯一需要毅力的环节，一旦 inbox/ 积压，它马上变成第二个剪藏堆。

--grep 在提交信息里找关键词，-S 找”哪一次提交把这段字符串加进来或删掉”。有次我想不起什么时候改过防抖的实现，git log -S 直接把我带到那次提交，还能顺手看当时的改动，比翻笔记本高效太多。我给自己定了条纪律：提交信息里必须出现这次涉及的 tag 或者关键词，否则提交后自己也找不到，这层索引就废了。

代码片段放哪里

片段是最容易被塞错地方的一类。我最后按”能不能公开、有没有归属”分了两种去处。公开、自解释、不牵扯任何项目上下文的，丢 Gist。Gist 本身也是 git 仓库，能 clone 能改，还能一行嵌进博客，省了我自己维护一份代码。

和公司、项目绑在一起的片段，留在 notes/snippets/ 里。判断标准很朴素：一旦片段牵扯内部接口、鉴权逻辑或还没打算公开的写法，Gist 就是危险的地方——它会被搜索引擎抓到，我不会指望设成私有就万事大吉。放在 snippets/ 里则跟着笔记仓库走，示例能当场跑，改完就是一次提交，和文档不会脱节。

三类场景，三套维护成本

把”知识”分场景，比按技术栈分目录有用的多。它直接对应”我要花多少力气维持它”。

场景 存放位置 检索方式 维护成本
临时排查 项目 issue 草稿或 logs/ 时间近、关键字 grep 低，记完即归档
长期知识 topics/ 关键词全文检索与 tag 中，随理解更新
代码片段 公开用 Gist，私用 snippets/ 文件名与函数名 grep 中高，需跑通验证

临时排查寿命最短。线上问题从复现到定位，过程值得留档，但结论一旦提炼进 topics/，原始记录基本不再回看，所以成本最低，写时不必苛求整洁。长期知识是主干，值得慢慢磨，更新频率随认知变化。片段最娇贵：不跑通的片段是负资产，所以我要求 snippets/ 里每个文件能单独执行，哪怕只是拼一段验证脚本。

读、记、用、输出的闭环

工具只是把这个闭环跑顺的载体，我按环节分工。输入端，Feedly 攒订阅，这一年它转收费闹得挺大，我顺势把一部分订阅迁到了 Inoreader 和自建的 Tiny Tiny RSS，避免被单一服务的定价绑住。读不完的先丢 Pocket 和 Instapaper。消化端，值得留的一律手抄进 notes/，绝不剪藏整页——剪藏的代价就是前面说的”存进去不再打开”。记录时用的是 Sublime Text 加 Vim，两者都只对纯文本友好，恰好对上前面这套约定。输出端，博客与团队分享是终点，也是筛选器。

flowchart TD
    A[订阅与稍后读] --> B[读到值得留的]
    B --> C[手抄进 notes 仓库]
    C --> D[写 tag 与关键词]
    D --> E[需要时 grep 检索]
    E --> F[写成博客或分享]
    F --> G[反馈与二次理解]
    G --> C

这个环里最要紧的是最后那条回边。输出之后往往会发现讲不清的地方，回到 topics/ 把那个条目重写一遍，闭环才真正转起来。少了这条边，笔记库就退化成又一个剪藏堆。

小结

先说边界。它只管个人知识，不该往团队身上套：共同知识得放在别人也能改、也能找的地方，塞进我私人的仓库只会变成一道壁垒。它的检索也有天花板，grep 认字不认意，同义词得我自己提前埋进正文，条目上万之后全文扫描会慢下来，那时我宁可先把 tag 收敛成一份受控词表，再谈别的办法。

我这套方法的核心只有三句：能检索的才是资产，分类只是虚荣；存进库之前先想清楚它什么时候会被 grep 到；让输出当守门人，没被用过没被讲过的知识不要长期占位置。工具会换，从 Feedly 换到 Inoreader，从某个编辑器换到另一个，但纯文本加 git 这套底座大概率能用很多年——它不依赖任何一个厂商还在不在。如果你也受够了”存了一堆却找不到”，不妨先建一个只放十几个条目的 notes/ 仓库，把 grep 跑通，再谈规模。
