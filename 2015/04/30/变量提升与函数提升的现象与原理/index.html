变量提升与函数提升的现象与原理

提升（hoisting）这个词已经被讲得足够多了，但真正在维护老代码时救命的，往往不是它的名词解释，而是三条能拿来判案的东西：报错类型、登记顺序、以及团队怎么把它的活动范围压到最小。执行上下文两个阶段的完整推导我在《JavaScript 作用域链与执行上下文》里写过，这里只取其中一条结论当前提：进入一个函数作用域时，声明会先被登记进表里，赋值要等到执行阶段才发生。所谓”提升”就是这两步之间的时间差。本文要谈的是这个时间差在具体代码里怎么变成 bug，以及 2015 年的工具链能怎么把它拦在提交之前。全文只用 ES5，浏览器那一侧按 Chrome 40、Firefox 35 与 IE 8 到 11 这一套来讲；文中每个”输出什么”的例子都在本地 node 里实跑过，涉及浏览器历史差异的地方我会标清那是当年的事实、不是本机复现的结果。

现象与两种报错

第一类常见的成因是拼错名字、忘了写 var 造成隐式全局、以及在严格模式里访问块内声明的名字。第二类几乎都是”函数表达式还没赋值”或”同名 var 把它盖成了非函数”。第三类留给严格模式下的非法绑定名那一类问题，callee、caller 的展开在旧文《arguments 对象与 callee、caller》里。

文案要提醒一句，各家各版本不一样：我在这台机器的 node 上拿到的是 f is not a function，Chrome 40 给的更接近 undefined is not a function，IE 9 及以下干脆是 Object doesn't support this property or method，中文控制台还有另一套。所以排查时认错误类型，别拿错误字符串做匹配，日志聚合系统里按类型分组比按文案分组稳得多。

登记顺序：谁覆盖谁

同一次进入函数作用域，登记顺序是固定的三步：先 arguments 对象与形参，再函数声明（带着函数对象写入），最后才是 var 变量名——而且 var 只在同名绑定还不存在时才置为 undefined。写成口诀：初始值看声明，最终值看赋值。三道判断题，建议先自己答再看推演。

题一

输出 function。第二步函数声明把 foo 写成那个函数对象；第三步的 var foo 发现名字已存在，直接跳过，连 undefined 都不会覆盖上去。

题二

输出 number / 1。登记阶段 foo 确实是函数，但执行阶段第一句 foo = 1 是真正的赋值表达式，它按书写顺序把函数盖掉了。声明的优先级只管登记，不管执行。

题三

第一行打印的是那个函数对象，不是 undefined——var 写在前面没用，带值进场的是函数声明。再补两个形参方向的例子：function f (x) { function x () { return 'fn'; } return x(); } 返回 fn（函数声明盖掉形参），而 function f (x) { var x; return x; } 传 'param' 仍然返回 param（var 谁也不盖）。这三条顺序一旦记牢，”同名到底谁赢”就不再靠猜。

真会咬人的四个场景

一、循环变量泄漏。 var 的作用域是整个函数，for 拦不住它：

同一个函数里两个循环共用一个 i 还算可控，失控的是嵌套——把内层循环误写成同名，外层立刻被改写：for (var i = 0; i < 3; i++) { for (var i = 0; i < 2; i++) {} out.push(i) } 实测只 push 一次，因为内层结束时 i 已经是 2，外层的 i < 3 再也续不上。这条 bug 的长相是”数据莫名少一截”，不报错，最难查。规矩很简单：一个函数里循环计数器不复用，名字带上语义（rowIdx、colIdx），全部在顶部一次声明完。

二、块内函数声明。 这是本文唯一只能讲”当年各家不一样”的地方，下面的描述是 2015 年的历史事实，不是我能用 node 复现的东西：

if 不是作用域，所以 send 到底登记在哪、什么时候拿到函数体，规范当时是空白。Chrome（V8）走的方向是把名字提到函数作用域但先给 undefined，执行到那一行才填上函数对象；Firefox 把声明圈在块里，出了块这个名字就查不到，直接引用是 ReferenceError；老 IE 则是连函数对象一起提到函数甚至全局顶部，条件走哪条分支都能看到 send，某些形态下还额外漏一个名字到外层。同一个文件在三个浏览器上能给出三种结果。这几家分别从哪个版本号开始变成这样，我手上没有可靠的对照表，所以只写方向、不写版本号，你要护住的项目请拿这段自己在目标环境上跑一遍。严格模式给了唯一明确的答案：块内函数声明只在该块内可见，所以把上面这段改到严格模式里，块外的 typeof send 一律是 undefined，调用 send() 则是 ReferenceError: send is not defined（这条我在 node 上实测过，行为与严格模式规范一致）。规矩：条件分支、循环体里不写函数声明，要按环境挑实现就写成”顶部 var send;，块里 send = function () {}“，或者干脆用惰性函数定义。

三、同名函数重复声明。 合并脚本之后最常见的一种”我明明改了上面那份代码却没生效”：两份同名函数声明都登记进同一张表，后来者赢，而”后来”指的是扫描顺序而不是调用顺序；全局作用域里更狠，它直接盖掉 window 上那个属性。同名函数声明与函数表达式混在一起时也一样，表达式那份在赋值那一刻把函数声明盖掉（var go = function () { return 'expr'; }; function go () { return 'decl'; } 之后调用得到 expr）。排查手段很笨但有效：全文搜函数名，只允许一处声明；跨文件的重名交给 undef 检查（见下一节）。

typeof 探测：好用，但不精确

引用一个没登记的名字会抛 ReferenceError，而对它做 typeof 不会：

这就是”用 typeof 探测可能未定义的变量”这条惯用法的由来，也是老代码里 if (typeof jQuery !== 'undefined') 这类判断的底层依据。但要清楚它的边界：typeof 分不开”压根没声明”和”声明了但还没赋值”，两者都返回 'undefined'——var a; 之后 typeof a 一样是 undefined。如果这段代码的正确性依赖”到底有没有登记过这个名字”，typeof 给不了答案。在全局作用域下还有一个更准的手段：in 判断属性，'a' in window 对 var a（哪怕未赋值）为真、对从未声明的名字为假，我在 node 里对全局对象实测同样成立。代价是它只适用于全局挂载，且要求那个名字确实是全局属性。

两个只提一句的历史注脚

函数名与参数名本身也是这张表上的条目，所以具名函数表达式的名字、以及 arguments.callee 拿到的自身引用，都和登记阶段脱不开关系；IE 的 JScript 会把具名函数表达式额外泄漏一个名字到外层作用域，这条已经写在《arguments 对象与 callee、caller》里，不重述。

团队规约：把提升关进笼子

机制讲到这里就够了，剩下的是纪律。

顶部集中声明，工具来保证。 “一个函数一个 var 语句、全部写在顶部”是那个年代 JSLint 的默认主张，JSHint 把它做成可选规则。相关选项名（JSHint 2.5.x 时代）：onevar 要求同一作用域只有一次 var；latedef 检查”在定义之前就使用”，取值 nofunc 表示变量仍然要先定义后使用、函数声明豁免这一条；undef 对没在任何作用域声明过的名字报警，这是抓拼错名字与隐式全局、也就是抓 ReferenceError 那一类的关键；immed 要求立即调用必须整体包在括号里，防止 ASI 在合并脚本时出岔子；funcscope 保持默认不打开，就是不允许”块里声明、块外使用”。一份能直接放进项目根目录的配置：

unused 会列出声明了却没用的名字，用它来揪出那份被覆盖的同名函数非常省事；noarg 顺手管住 arguments.callee。接入方式走 grunt-contrib-jshint 或 gulp-jshint，编辑器里配 SublimeLinter。ESLint 那时候还是个刚出头的新工具（1.0 还在路上），它把 vars-on-top、no-inner-declarations 这两条做成了独立规则，方向完全一致，但在 2015 年 4 月我不建议把它当项目主检查器。

函数声明可以放后面，var 一律顶部。 这条规则值得单独论证，因为它依赖一个具体事实：只有函数声明是带着函数对象一起登记的，所以”先写 init() 再往下翻找 function init () {}“这种把入口放在文件最上面、实现往下排的布局才安全可读。一旦你把某个函数声明改成函数表达式，或者文件里开了 latedef: "func"，这个豁免立刻消失——return go(); 写在 var go = function () {} 之前就是 TypeError。所以规约写成两句才完整：入口与流程用函数声明、可以后放；一切数据、配置、循环计数用 var，只在函数顶部出现，要么声明与赋值同行、要么保证那行一定执行。

换成函数表达式的代价。 有些团队为了”读代码时顺序等于执行顺序”，规定一律 var fn = function () {}。换来的是显式和可 grep，丢掉的是提升带来的排布自由，还多一个坑：同名覆盖时表达式那份会赢（前面第三节的例子），排查时容易误判。我的选择是函数声明为主，只在需要把函数当值传递、或要藏进闭包时才用表达式。

严格模式挡得住什么、挡不住什么。 能挡的：写一个没声明的名字会当场抛 ReferenceError（非严格模式下它静静变成一个全局属性，这是提升类 bug 最阴的变种）；块内函数声明被明确圈在块里；with、重复形参、arguments.callee 一并禁掉。挡不住的：var 的提升完全不受严格模式影响——这是最常见的误解。在函数开头写 'use strict' 之后，console.log(a); var a = 1; 照样打印 undefined，实测如此。严格模式管的是绑定规则，不是登记时机，别指望它替你解决提升。

块级声明还要再等。 循环泄漏和块内函数声明这两类问题，根治办法是让 {} 真的成为一层作用域。标准化里这块已经有方案，草案阶段写作 let 与 const，但 2015 年 4 月的浏览器基本给不了可靠可用面，转译器也还没进主流构建，所以我连一份能上线的例子都不打算写在这里。工程上此刻只能靠上面那两条规约加 JSHint 兜住，这是现实约束，不是设计偏好。

排查提升 bug 的操作清单

线上出现 undefined、not a function 或”值莫名其妙不对”时，按这个顺序走：

  1. 先看错误类型，把方向定死在”没登记”还是”登记了但值不对”，再顺着栈帧进函数。
  2. 把可疑变量在函数顶部统一声明成 var name = undefined;，跑一遍。如果原来报 ReferenceError，说明这个名字根本不在链上（拼错或作用域层数不对）；如果报错消失、行为改变，说明原代码在某条分支上没走到赋值。
  3. 全文（含合并前的各源文件）搜同名声明，确认只有一份；重点看两份函数声明和”函数声明 + 函数表达式”混合这一种。
  4. 拆掉块内函数声明：把 if 里的 function x () {} 改成顶部 var x;、块里 x = function () {}，跨浏览器立刻一致。
  5. 判存优先用 typeof name === 'undefined'，需要区分”没声明”和”没赋值”时改用 'name' in window，别拿两者互相代替。
  6. 在函数（或文件）头部加 'use strict' 再跑一遍，看差异出现在哪：差异基本就落在隐式全局、块内声明、callee 这三类上。
  7. 最后把上面这份配置接进构建，让 onevar、latedef: nofunc、undef 替你守住第二次。

小结

提升的全部机制只有一句话：进作用域时先登记声明、执行时才赋值；带值进场的只有函数声明。由此得到能判案的三件事：报错类型告诉你名字有没有登记（ReferenceError 没有、TypeError 有但值不对），登记顺序告诉你同名谁赢（arguments 与形参、函数声明、var 依次落地，但最终值看赋值顺序），块内函数声明告诉你为什么同一段代码在三个浏览器上有三种结果。落到工程上就是几条纪律：var 集中在函数顶部、循环计数器不复用、块里不写函数声明、同名声明全项目只允许一份、严格模式照开但别指望它管住提升，再用 JSHint 把这几条变成机器检查。这套东西谈不上什么巧妙，但能让一类”不报错的错值 bug”从排查清单里彻底消失。
