JavaScript 模块化模式的七种写法

从 2013 年到 2015 年，前端项目里的代码组织方式大致都落在这七种写法的谱系上：函数作用域、对象字面量、立即执行函数返回对象、命名空间函数注入、依赖参数注入、AMD、CommonJS。写法大全类的文章已经很多，本文换一个视角：每一种写法只回答三个问题——它靠什么语言机制实现封装与依赖解析；它导出到运行时的到底是一个什么对象；它在架构上买到了什么、又欠下了什么。文中所有 JavaScript 逻辑均在 Node 里实跑过，结论以实测为准；涉及 DOM 与浏览器的部分会明确标注验证边界。IIFE 的五种语法变形与自动分号插入的坑，旧文《IIFE 立即执行函数表达式》已经讲透，本文一律不重述，直接当积木用。

先把谱系的骨架交代清楚。模块化要解决的是两件事：封装，即内部状态如何只许自己人碰；依赖解析，即一个单位用到的外部能力由谁来备齐。ES5 语言能给出的封装原料其实只有一种——函数作用域加闭包，七种写法的全部差异在于“把哪部分成员关进去、把什么交出来”；而依赖解析则是一条从约定到机制的演进线：从依赖全局查找，到把清单写进实参位，再到把清单写成声明交给加载器或打包器。后面每一种写法，都可以放进这两条轴的某个坐标里。

写法一：函数作用域——模块化的动机，而不是模块化

机制上它只借了一个语言特性：函数作用域。var 声明激活在函数执行环境的变量对象上，执行结束、没有闭包引用留存，整个作用域连内部变量一起回收。'use strict' 再补一刀，漏写 var 的赋值从“悄悄挂全局”变成抛错。这是 ES5 里唯一可靠的隔离单元——块级作用域要到语言层面讨论 let，眼下没有。

但它导出的东西在运行时是“什么都没有”：立即执行的返回值被直接丢弃，外部连一个句柄都拿不到。成员完全不可达，意味着这个单位不可复用、没有 API、无法测试（连入口都没有）。它还有第二个问题：匿名立即执行把“定义的时刻”和“执行的时刻”焊死在一起——脚本一加载完，逻辑就跑了，此时页面上的 DOM 可能还没就位，全局依赖可能还没加载，只能再靠 window.onload 或 jQuery 的 ready 回调把真正的初始化推迟出去，执行时机又成了一个新的耦合点。所以严格说，它不是模块，而是模块化的动机：后面六种写法做的事情全部是同一次修补——在保住这层隔离的前提下，把一部分成员放出去，同时把外部依赖收进来，并且让“什么时候跑”重新可控。把“包一层函数”当成模块化终点的项目，往往在第二个页面要复用同一段逻辑时被迫把代码复制一份。

写法二：对象字面量——没有墙的表面

机制：对象字面量在脚本执行时求值一次，产出一个普通对象，var 把它绑成全局对象上的一个属性。成员访问是动态的属性查找，语言层面没有任何公开与私有的区分——下划线前缀只是给同事看的注释。导出物就是一个人人可写的对象引用，this 的指向由调用点决定（SearchModule.init(el) 里 this 是模块本身，把方法摘出来单独调就丢了）。

三个结构性缺陷，我都在 Node 里复现过。其一，状态可被外部改写：SearchModule.keywords = [] 任何一行脚本都做得出来，模块内部精心维护的数据没有任何防线。其二，无法创建多实例：字面量只求值一次，赋值只是传引用——实测 var m2 = Module 之后 m2 === Module 为 true，在 m2 上 push 一个元素，另一边立刻看见。其三，初始化数据其实是共享引用：写在模块体内的数组和对象字面量，“每个实例”拿到的都是同一个数组，改一份就是改全体。

它买到的：把散在全局的变量归拢成一个可读的 API 面，零成本、零依赖。欠的：封装相关的每一样。多人协作时这种“欠”会具体化：每个负责人守着一个全局对象，对象上的方法名就是团队接口约定，但这份约定没有任何强制力——绕过入口函数直接改内部数据，语法完全合法，错误往往要到很久之后、某条没被回归覆盖的调用路径上才暴露，而且定位时“谁改的”无从查起。这也是 Addy Osmani 在《Essential JavaScript Design Patterns》里把 Module 一节建立在闭包之上的原因：字面量形态只是引子，社区真正需要的是一堵有门的墙。

写法三：立即执行函数返回对象——真私有，和两个坑

社区叫它 Revealing Module Pattern：闭包保留私有变量，return 出去的对象是白名单 API。

机制：闭包捕获的是变量的绑定而不是值的拷贝。导出的函数只要引用着 count，那个变量对象就不会被回收，每次调用沿作用域链读到的是同一个绑定的当前值。导出物是一个普通对象，但成员分两类：函数持有活的作用域链，值是死的拷贝。

坑一，导出基本类型是快照。实测：执行 Counter.bump() 之后，Counter.count 仍是 0，而 Counter.getCount() 返回 1。给对象属性赋值是一次 [[Put]]，把当时 count 的值拷进去，此后闭包内的 count 与这个属性再无任何联动。想要“实时只读值”，只有两条路：导出 getter 函数（如上），或者用 ES5 的 Object.defineProperty 在导出对象上定义访问器。导出函数引用才有实时性，这是 Revealing Module 最容易被写错的一处。

坑二，你无法从外部重置或劫持私有状态。实测：把 Counter.bump 重新赋值成一个空函数后调用 Counter.bumpTwice()，getCount() 从 1 涨到 3——bumpTwice 内部走的是闭包直引的 bump，不是 Counter.bump 这个属性。这有两个面相：防御面上，内部调用链不会被外部 monkey patch 污染，方法互调永远引用内部名；代价面上，测试想“换掉实现”“重置状态”，从对象表面下不了手，必须由模块自己提供 reset 之类的入口。所以导出的函数引用同时带来实时性和不可替换性，这是一枚硬币的两面。

它买到的：真私有状态加显式 API。墙有两层也要看清：闭包挡住的是内部变量，而导出对象本身仍然人人可写，ES5 里甚至可以用 Object.freeze 把 API 面焊死——但冻结同时关掉了测试端替换实现的路，和生产代码“可插桩”的诉求正面冲突，实际项目里很少真冻。欠的部分更关键：模块仍挂在全局、可能撞名；依赖仍从全局抓取，模块自身不声明依赖；天生单例——getInstance 的补丁在《JavaScript 命名空间与模块化演进》里写过，不展开。

写法四：命名空间函数注入——把挂点工程化

机制：fn 收到的是末端节点的对象引用本身，而对象是可变的；于是任意文件都能对同一个节点增量挂成员。合并安全靠的不是这个函数，而是“对象可变 + 存在才复用”的性质——实测两次注入后 open 与 close 都在，第二次注入没有覆盖第一次。它替团队解决的真是两件事：其一，手写三层 App.ui = App.ui || {} 的重复样板；其二，加载顺序耦合——文件之间不再争“谁先声明 App”，只要 App.module 工具本身最先执行，其余文件随便排序。手写 || 被整体抹掉的那次事故和完整演进过程，《JavaScript 命名空间与模块化演进》已经复盘过，这里不重述。

私有性为零：命名空间下的一切可读写，实测 App.ui.count = 1 这种改写工具毫无办法，注入函数拦不住任何属性赋值。依赖仍是隐式的，一个文件用了谁只写在代码字面里；App.ui.dialog.xxx 压缩后仍是三段属性访问，属性名是压缩器的禁区。还有一个递归式的尴尬：App.module 工具本身也必须最先加载，管理顺序的工具自己又是一个顺序依赖——依赖树的根从来还是 <script> 标签的排列，这套写法只是把树的中间部分理顺了。它在谱系里的定位是写法二的工程化版本：API 面依然全公开，但挂点管理自动化了。适合文件多、人手杂、但短期不打算上工具链的项目。

写法五：依赖参数注入——用形参把引用焊死

这就是 jQuery 风格的依赖注入，三个作用各有各的机制，我逐条拆开。

第一，固定引用。实参传递做的是值拷贝，拷的是“当时全局 jQuery 持有的对象引用”。此后任何脚本重分配全局名都波及不到内部。实测：注入完成后把 jQuery 置为 null，闭包里 $ 仍指向原对象，版本号读出来还是 1.11.1。页面里多版本 jQuery 打架、有人手滑写了 jQuery = {}，对这份代码都不构成影响。

第二，查找与压缩收益。自由变量沿作用域链逐层向外找，全局属性引用最终要落到全局对象上，浏览器里那个对象背后还挂着一整层 DOM；形参激活在最内层作用域，第一跳就命中。更实际的是压缩：只有局部名敢被改成一个字母，(function ($) {...}(jQuery)) 里的 $ 可以被随便缩短，而裸写的 jQuery 引用出现一百次就是一百次不可压缩的属性名加一百次全链查找。这里不贴微基准数字——差别的量级属于旧文《资源合并与压缩的收益分析》的口径，本文只给方向。

第三，undefined 形参。早期全局 undefined 可写，把它遮蔽成形参是防御；ES5 内核里它已不可写，这层遮蔽退化为省字节和历史惯性（详见《IIFE 立即执行函数表达式》）。

架构上这是第一次“依赖出现在代码形态里”：实参位就是这份代码的依赖清单，测试时传一个假的 $ 进去即可替换。但它仍然没有任何加载器：jQuery 尚未定义时注入的就是 undefined，错误要到第一次调用才爆；脚本标签的排序纪律一分没少。把它和写法六放在一起看会更有意思：形参列表已经是依赖声明的雏形，工厂拿到依赖的方式也和 AMD 回调一模一样——两者之间只差一个“谁来备齐实参”的角色，这个缺口正是加载器要站进去的位置。UMD 模板与 jQuery 插件语境在《jQuery 插件开发模式与实战》里给过，不复述。

前一篇《JavaScript 命名空间与模块化演进》已经把 paths、shim、urlArgs、data-main 和 r.js 的坑清单数过一遍，那都是配置层的账。这一节只从实现层看：加载器内部到底维护了什么，让 define 敢把依赖写在最前面。

注册表与状态机。 加载器有一张核心表：模块 id 对应 { deps, factory, exports, 状态 }。状态大致是：占位（已发起请求，脚本在途）→ 已定义（define 执行完，依赖未解析）→ 解析中 → 就绪。所有请求走同一个 need，每个请求方把回调塞进该 id 的等待队列。队列一物两用：既是依赖就绪后的通知渠道，也是并发请求的去重器。这一条我有切身体会——写下面这个极简注册器时，第一版没做占位去重，format 被注入了两次脚本、工厂执行了两次；改成“发起请求即占位、后到者只排队”之后，实测每个模块的工厂恰好执行一次。RequireJS 的核心数据结构就是这条路。

匿名模块 id 的推导。 define(['b'], factory) 没有名字，加载器怎么知道它是谁？做法与直觉相近：模块一律按动态 script 标签逐个注入，注入顺序记在一个队列里；同源脚本按注入顺序执行，于是 define 执行的那一刻，从队列头部取出的那个 id 就是它自己——它自己就是那个正在执行的脚本。相对 id（./format）用发起方的目录段拼出绝对 key，注册表只认最终 key。这个机制的前提是“按请求顺序注入且按注入顺序执行”，所以具名 define('id', [...], fn) 才要求显式写出 id。

依赖数组既声明又触发。 define 一执行，加载器立刻递归 need 每一个依赖项；全部就绪，才按声明顺序把导出物作为实参喂给工厂，工厂的返回值进入注册表。“依赖就绪才执行”把全局脚本排序问题变成了图遍历问题，这是 AMD 的本质收益。极简注册器（40 行以内，只用动态 script 注入与回调队列，不引入任何新式异步机制）：

这个核心的纯逻辑部分在 Node 里实测过（loadScript 换成异步回调）：依赖先于使用方执行、return 与 exports 两种导出语义、二次 require 命中注册表同一实例且工厂不再执行。动态 script 注入那一段依赖 DOM，没有实测，机制描述以 RequireJS 的公开行为为准。

return 与 exports 是互斥语义。 工厂返回值不为 undefined 时整体替换导出物，否则用默认的空 exports 对象——工厂里的 this 就是它，或者把 'exports' 写进依赖数组让注册表把这个缺省对象当虚拟依赖注入。前者是“组件式导出”，后者是“增量导出”，混着写，exports 上的东西会被 return 整个丢掉。判定条件就是注册器里那一行 r === undefined，语义分支仅此一处。

define.amd 是探测签名。 加载器在 define 函数对象上挂一个 amd 属性，库用它区分“真正的 AMD 加载器”和别的同名全局函数：typeof define === 'function' && define.amd 成立才走 define(['jquery'], factory)，否则退回全局分支。库因此能一份源码同时服务加载器和 <script> 标签，UMD 的完整模板见《jQuery 插件开发模式与实战》。

循环依赖，朴素版直接死锁。 用上面的注册器实测 a 依赖 b、b 依赖 a：双方都进入解析中、各自等对方就绪，回调永远悬空。RequireJS 2.1 的处理工程化得多——让工厂提前执行，未就绪的依赖以 undefined 传入，所以纪律和旧文《JavaScript 命名空间与模块化演进》一致：依赖只在方法体内访问，绝不在模块顶层解引用；真出现双向依赖，抽公共部分才是解法。

注册表对导出值不设类型限制。 defs 里存的是任意值：工厂返回函数，模块就是函数；返回构造函数，模块就是类。jQuery 官方的 AMD 适配走的就是函数路线——define(function () { return $.noConflict(); })，把全局引用交还给加载器管理，页面上同时跑多个 jQuery 版本时互不干扰。这一点和写法三的“白名单对象”形成对照：导出物形态在 AMD 里完全交还给工厂自己决定。

架构上 AMD 买到：依赖显式化、异步加载、按页面切分产物、依赖可 mock。欠的：一套非标准全局语法，一个运行时加载器的体积与心智，上线前必须过的 r.js 构建，以及开发期模块逐个请求、整张依赖图串行等待的启动成本——“运行时解析图”意味着首屏之前先有一段解析过程，这笔账要原样记在写法六的负债栏里。

写法七：CommonJS——同步 require 与打包器的前编译之路

机制第一层：模块不是顶层作用域。Node 读入文件后把它包进一个函数再执行，这件事不用猜，require('module').wrapper 里能直接读到包裹函数的前缀：(function (exports, require, module, __filename, __dirname) {。换句话说，CommonJS 就是让运行时替你写写法五：exports 是形参，初始指向 module.exports 上那个缺省空对象；require 也是注入的函数，根本不是全局。再做个小实验就能看见包裹的边界：在模块文件顶层写 this === module.exports，实测为 true——运行时把包裹函数的 this 也指回了导出对象，这正是早期 Node 模块允许 this.foo = ... 写法的由来。封装靠函数作用域，依赖解析靠注入的 require，两样都是本文前面出现过的积木，只是第一次由平台代劳。

机制第二层：require 返回的是 module.exports 的值。实测过对照：一个文件先写 exports.area = ... 再把 exports 重分配成一个函数，外部 require 拿到的仍是含 area 的对象——你改掉的只是形参别名，没有动真身；想整体替换导出物，必须给 module.exports 赋值。这和 AMD 里“return 与 exports 互斥”是同一个坑的两副面孔。

机制第三层：同步语义加缓存。require 当场返回，靠的是取资源的途径（文件系统）本身同步；解析结果按绝对路径缓存，同一模块第二次 require 返回同一实例——实测 === 成立。同步加缓存，意味着 CommonJS 模块事实上都是单例。

机制第四层，也是最值钱的一条：循环依赖拿到的是半成品，而不是死锁。实测 a 依赖 b、b 反过来依赖 a：b 执行 require('./a') 的那一刻，拿到的是 a 已经填了键的对象——实验里只有 {"name":"ca"} 这一个属性，后面的东西还没执行到。关键是这个半成品与最终对象是同一个引用，所以“把引用存进变量、留到方法体里再用”是安全的（实测 a 的方法后来能正常读到 b 补上的值），而在顶层立刻解引用就会踩空。AMD 朴素版死锁、CommonJS 给半成品，这是两套依赖解析策略在循环场景下最直观的分野。

浏览器为什么用不了裸 CommonJS：同步 require 要求资源当场可得，浏览器端等价物只有同步 XHR（阻塞主线程，已被标准废弃）或本地文件字典，都不现实。Browserify 5/6 在 2015 年的定位就是把这件事搬到编译期：沿入口文件的 require 调用静态递归出依赖图，每个模块包成工厂函数、连同路径写进一个字典，再带上一份同步 require 的模拟实现——产物是一个“全世界已经就位”的 bundle。结构示意：

架构对照就清楚了：AMD 在运行时解析依赖图，CommonJS 在构建期解析；AMD 产物是“加载器 + 拆分模块”，Browserify 产物是“微型运行时 + 整块 bundle”。按需加载、多页共享、按路由切分，AMD 是原生能力，CommonJS 侧要靠拆 bundle 或换工具；反过来，同构代码用 CommonJS 写一份，Node 里直接 require 跑单测，浏览器侧打包，Underscore 1.7、lodash 2.4 这一代库已经在用 UMD 同时兼容两边。写哪边取决于团队的主战场，而不是哪边更“先进”。

收口：七种写法的对照与 2015 年的选型

把七种写法放到同一张表上，逐格对照它们买到和欠下的东西：

写法 私有性 依赖显式化 可测试性 多实例 加载顺序管理 构建期成本 运行时开销
函数作用域 全私有但无出口 无 无入口，不可测 否（一次性执行） 无 无 无
对象字面量 无，属性全开 无 差，状态共享 否，引用相同 无 无 无
IIFE 返回对象 闭包真私有 弱，靠实参位 中，须模块自备 reset 否，天生单例 无 无 闭包常驻
命名空间注入 无 无，靠挂载约定 中，可整体替换节点 否 半自动（建段自动，排序手动） 低 属性链查找
依赖参数注入 函数级 中，清单在实参 良，依赖可换假物 否 无，顺序靠人 无 一层作用域
AMD（RequireJS 2.1.x） 模块内私有 强，deps 数组声明 良，依赖可 mock 模块单例，实例看工厂 强，加载器递归解析 高，r.js 必经 加载器加请求数
CommonJS（Node / Browserify） 包裹函数私有 强，require 调用点 良，Node 原生生态 缓存即单例 构建期解析完毕 高，重打 bundle bundle 内近无

以 2015 年 4 月的工具链，选型结论是务实的三条线。老项目渐进改造：从写法五和写法四起步，一个焊死依赖引用、一个管住挂点，不动任何工具链就能先吃到全局查找收敛和合并安全，一个月后再看要不要上加载器。新项目页面超过十张上下、多人并行、需要按页面切分产物：AMD，RequireJS 2.1.x，代价预算留给 r.js。Node 与浏览器要共享同一份业务代码：CommonJS 加 Browserify 5/6，让单测跑在 Node 里，打包器负责伺候浏览器。SeaJS 2.x 的 CMD 在机制层与 AMD 只差一个执行时机，旧文已述，不再展开。

还有一层关系值得点破：这七种写法不是互相替换，而是层层叠加。AMD 的工厂函数本体就是写法三加写法五——一个函数作用域，依赖靠形参注入；Browserify 的包裹机制是写法一加写法五的机械化量产，连括号都是运行时替你加的。把这一层看清，渐进改造的胆量就来了：迁移到加载器并不推翻已有的封装习惯，只是把“谁来备齐实参”“何时执行工厂”两件事从人手里交给了机器，模块体内部的写法几乎一字不用改。

至于标准方向：ES6 模块语法已经定稿、“ECMAScript 2015”要等 6 月批准，静态结构加实时绑定的导出在机制上优于现有两路——但 2015 年的浏览器给不出原生实现，traceur 与 es6-module-loader 都还是转译加 polyfill 的早期形态，import 写出来也没法在页面里跑。所以本文的代码全部停在 ES5，这不是保守，是当下唯一诚实的写法。
