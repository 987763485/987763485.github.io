JavaScript 惰性加载与函数定义技巧

两三年前做一个后台项目，首页要初始化几十个下拉组件、日期控件和图表占位块，首屏脚本跑完要卡一下。当时读到惰性函数这个概念，像捡到宝一样在代码里到处用，结果线上没出问题，测试环境先炸了一串诡异的用例。后来把这几年相关的写法统一复盘了一遍，本文就是那份踩坑记录加修正后的姿势。惰性求值与急切求值概念层面的对比、memoize 缓存的推导，我在旧文《JavaScript 惰性求值与缓存优化》里写过，这里不重复，只谈”函数定义与执行时机”这一层。类比一句：Haskell 那套完整的惰性求值语义 JavaScript 学不来，我们能借用的只是”推迟到真正需要时再做”这个思路。

两者差别可以拆成三点。首字节成本：写法一的判别发生在脚本解析时，写在什么位置就开始付什么位置的成本，首次调用零开销；写法二把成本推到第一次调用，还要多分配一个新函数对象。分支次数：两个写法之后所有调用都是零分支，但写法一从生到死只有一次分支，写法二在第一次调用里可能多走几个 if。可读性：写法一翻开文件就能看到当前环境用的是哪个实现，写法二要先读完判别条件才知道覆盖后长什么样，排查问题时容易看漏。

复盘后的结论是：能写成载入时判别的，一律不要写成自重写。环境能力在脚本加载那一刻就是确定的，没必要等第一次调用。只有一类场合不得不使用自重写：判别条件依赖调用时才拿到的对象。典型是取事件源的 Event.getTarget，标准浏览器有 event.target，IE8 只有 event.srcElement，而事件对象要等事件真的触发才存在，载入时根本无法判别，只能等第一次真实事件到来时按参数形状定分支：

自重写函数的四个坑

坑一：外部持有旧引用。这是最阴的一个。有人把函数引用提前存进变量或对象里，比如 var old = addEvent;，之后 addEvent 被首次调用重写，old 依然指向那个带判别的老实现。我用 node 验证过：正常路径调用两次加旧引用调用一次之后，判别分支进了 2 次，重写后的快路径走了 3 次，且 old === addEvent 为 false。翻译成现象就是”测试里看起来生效了，实际有个调用方永远没换过来”，代码读起来一切正常，行为却对不上。凡是被外部缓存过引用的公共函数，禁用自重写，改回载入时判别或闭包缓存。

坑二：单元测试的 mock 被静默覆盖。顺序不同结果不同：先 mock 再调用，mock 挡住了首次调用，真实现没被重写，恢复现场后下一个用例还要再付一次判别成本；先调用再 mock 看似安全，但有些用例走了 old 引用（坑一），断言的函数和执行的不是同一个。复盘出来的规矩是：自重写的惰性函数不直接对外层做断言，要测它覆盖前和覆盖后的内部实现，或者干脆别用这种写法给可测试代码用。

坑三：具名函数表达式与严格模式。为了在重写后的函数里递归调用自己，有人写 var f = function g() { ... g(); };。现代引擎里 g 只在函数内部可见，实测外部 typeof g 是 undefined；但 IE8 会把 g 泄漏到外层作用域，多出一个全局函数名，跟已有变量悄悄打架。另一条相关红线：严格模式（'use strict'）禁用 arguments.callee，所以别指望靠它自调用，自重写请显式覆盖外层变量并用 apply 转调。

坑四：重写自身时丢 this。如果 addEvent 挂在对象上、调用方写的是 obj.addEvent()，重写的转调就必须用 apply(this, arguments)。我用两个宿主对象各挂同一实现做了对比：转调裸调用 f(el, type, fn) 时 this 直接丢失，重写版里访问 this.log 抛 TypeError，宿主记录是空数组；换成 apply(this, arguments) 后，通过 widget 调用记到 click:widget，通过 panel 调用记到 click:panel，接收者完整保住。前面 getTarget 的例子里参数本身就是 event，用不用 apply 影响不大，但方法型 API 必须写对。

复盘结论清单

值得惰性化的场景，三条同时满足才算净收益：单次成本高（实测毫秒级以上）、有可能永远用不到、判别条件稳定且与环境或配置一次性绑定。

不值得甚至有害的场景：成本极小却多背一次分支判断的；把初始化时序藏进调用路径，导致两处代码对”谁先跑”产生竞态的；让调试断点和测试桩找不到真正执行的那份实现的——坑一和坑二的本质都是这个。

最后留一条我现在的务实标准：能测出首屏差异才做惰性。用秒表加 DOMContentLoaded、load 时间戳做前后对比，差值进不了用户的感知，就老老实实写最直接的那个版本。聪明的写法换不来收益时，可读性才是省下来的那个成本。
