CSS3 transform 位移缩放旋转与矩阵

本文属于《HTML 与 CSS》第 45/62 篇
上一篇系列目录下一篇

transform 是当年做动效时写得最多、也最容易被当成免费午餐的属性。多数教程停在”怎么把元素挪个位置”，但项目里真正咬人的是另外三件事：为什么同样的位移写 transform 不卡、写 top 就卡；把元素提到 GPU 层上要付什么代价；以及”卡”怎么量化。本文按函数与矩阵讲一遍语法，重心一路压在性能上。渲染管线与重排重绘的完整定义见《减少重排与重绘的实践清单》，CSS 与 JS 动画的整体选型见《CSS 动画与 JS 动画的性能取舍》，本文都不重复，只从 transform 属性内部往下挖。

transform 快的根源：它不动布局盒

先把最本质的一条钉住：transform 不改变元素在文档流中的位置。变换发生在盒子已经算好之后，它只改”画在哪儿、画成什么形状”，不改盒子本身的几何信息。所以邻居不会被推动，父容器不需要重新排版——这正是它比 left / top 动画快的全部原因。

flowchart TD
    A["样式计算"] --> B["layout 布局：算出每个盒子的位置和尺寸"]
    B --> C["paint 绘制：把像素填进图块"]
    C --> D["composite 合成：把各层按位置拼到屏幕"]
    D --> E["显示器"]
    L["改 left / top / width / height"] --> B
    T["改 transform / opacity"] --> D

left 每改一次都要从 layout 走满一整条链；transform 主要落在最后一步合成，layout 这一环被整个跳过。但它并非零代价：元素自身仍然要重绘，圆角、渐变、文字的纹理都得重新栅格化，省掉的是”重算布局”这笔最贵的开销。

顺便解释一个常被问到的现象：加了 transform 之后读 offsetLeft 仍是原值，而 getBoundingClientRect() 已经跟着变了——前者交布局盒，后者交变换后的视觉盒。

位移与缩放：百分比参照自身，原点做锚

translate(x, y)、translateX()、translateY()、translateZ()、translate3d(x, y, z) 里的百分比一律参照元素自身尺寸，不是父容器。所以经典居中写法 position: absolute; left: 50%; -webkit-transform: translate(-50%, -50%) 的位移量只跟自己的宽高有关：一个 200px × 120px 的盒子，translate(-50%, -50%) 换算成矩阵就是 matrix(1, 0, 0, 1, -100, -60)，这是我按矩阵复合实算的。这个性质在性能上有实际好处——位移量像素确定，不需要 JS 去读尺寸，也就不会为算位置触发一次同步布局。

translateZ 和 translate3d 在没有透视（perspective）时肉眼看不出任何变化，但会影响浏览器是否给元素建合成层，所以那串 translate3d(0, 0, 0) 的黑魔法并非全然心理作用，代价见后文讲 3D 与合成层的一节。

scale(sx, sy)、scaleX()、scaleY() 绕着 transform-origin 缩放，原点默认是 50% 50%，也就是盒子中心。浏览器实现原点的方式，是在整个函数序列两侧各补一次平移：M(origin) · 你的矩阵 · M(-origin)。我拿一个 200px × 120px 的盒子写 transform: scale(2) translateX(50px) 实算了两种原点的结果：

transform-origin 左上角落点 右下角落点
0 0 (100, 0) (500, 240)
50% 50% (0, -60) (400, 180)

两组的宽高增量完全一致，变的只是锚点位置：原点决定”钉在哪儿”，不决定”走多远”。但序列里一旦有 rotate，原点就直接决定运动弧线了，所以下面讲顺序时，演示例子都定在原点上看。

最后一个坑：scale(0) 把矩阵退化成行列式为 0 的不可逆矩阵（我算过它的 ad − bc = 0）。当年把它和 perspective 写在一起，某些 WebKit 版本会在透视除法里碰到除零，算出 Infinity 之后元素干脆整个消失。想”收起来”请用 scale(0.001) 或改用 opacity。

旋转与斜切：单位、轴、默认值

rotate(angle) 在 CSS 里必须带单位，deg、rad、grad 都行，写成 rotate(30) 的后果是整条 transform 声明被静默丢弃——不报错、不降级，样式表里明明写了，页面上就是没反应，排查很费时间。另外因为 CSS 的 y 轴朝下，正角度看起来是顺时针。

rotateX() / rotateY() 是 3D 的，rotate3d(x, y, z, angle) 用一个轴向量加一个角度表达任意旋转，rotate3d(0, 0, 1, θ) 等价于 rotate(θ)。要注意的是 rotate3d(1, 1, 0, 45deg) 和 rotateX(45deg) rotateY(45deg) 是两件不同的事：前者绕着元素平面对角线一次性转 45°，后者绕两条直角轴各转 45°，复合出来的姿态完全不同。我离线复算了两者投影到 2D 的部分，a 分别是 0.853553 与 0.707107；实际项目里别背公式，直接读 getComputedStyle(el).transform 返回的 matrix3d 十六个数最靠得住。

skew(ax, ay)：第一个角度斜一个方向、第二个斜另一个方向，第二个参数默认是 0deg，所以 skew(30deg) 只斜一个方向，不能理解成”两个方向都斜 30 度”。第二个参数一旦要写，必须是角度，skew(30deg, 0.1) 这种写法整条声明作废。斜切矩阵的 a 与 d 都是 1，两个正切值填进 b 与 c 这两个位置（哪个方向进 b、哪个进 c，读一次 getComputedStyle 比背公式快），行列式 ad − bc 等于 1 − tan(ax)·tan(ay)，skew(30deg, 10deg) 我算得约 0.898，小于 1，说明斜切会压缩图形面积。

matrix(a, b, c, d, e, f)：六个数各管什么

matrix() 把 2D 变换压成六个数字，它对应的矩阵写法是：

分工很清楚：a / b / c / d 这个左上 2×2 负责缩放、旋转、斜切这三件事（它们本来就分不开），e / f 负责平移，而且永远是像素——即使你在函数序列里写的是百分比，换算到 matrix 也是 px。

拿到一个 matrix 怎么判断它是什么：b 和 c 都是 0 就是纯缩放，a、d 是横纵倍率；a 等于 d、b 等于 -c、并且 ad − bc = 1 就是纯旋转；ad − bc 本身是面积倍率，等于 0 就是退化矩阵。

三条换算例子（数值来自我用 node 手写的 3×3 矩阵乘法复算）：

函数写法 等价矩阵 说明
translate(20px, 30px) matrix(1, 0, 0, 1, 20, 30) e/f 就是位移
scale(2) matrix(2, 0, 0, 2, 0, 0) 行列式 4，面积翻 4 倍
rotate(90deg) matrix(0, 1, -1, 0, 0, 0) b 是 +1、c 是 −1

第三行的符号特别容易记反，我是这样自证的：取点 (1, 0)，按 x' = a·x + c·y、y' = b·x + d·y 算，a = cos90° = 0、b = sin90° = 1，得到 (0, 1)，也就是原来的横轴被转到了向下的方向——屏幕坐标里正是顺时针 90°，与 matrix(0, 1, -1, 0, 0, 0) 对上。

还有一个只在 matrix 上成立、写进函数序列就不成立的差异，值得单独记：单个 matrix() 里的 e/f 不受同一个函数里 a/d 的影响。matrix(2, 0, 0, 2, 20, 30) 的平移量就是 20/30，它等价的是 translate(20px, 30px) scale(2)，不是 scale(2) translate(20px, 30px)。两种顺序我都算过：前者得 matrix(2, 0, 0, 2, 20, 30)，后者得 matrix(2, 0, 0, 2, 40, 60)。可如果你把 matrix(1, 0, 0, 1, 20, 30) 挂在 scale(2) 后面，那 20/30 照样被前面的缩放乘成 40/60。

实践中 matrix 的价值在于复合结果一次写死：JS 里不用每帧拼一长串函数名，也不必担心顺序写错；配合 getComputedStyle 读回最终矩阵，还能做”先量两端位置、再用一个 translate 补过去”这类当时流行的动效技巧。

顺序不可交换：本文最该记住的一条

transform 的函数序列不能换顺序，因为每个函数都是一次矩阵左乘，写在后面的那个函数工作在前一个函数建立起来的局部坐标系里。最典型的例子：

再看平移与旋转的对照 demo。同一个 100px 见方的方块，都写”移动 120px 加转 90°”，顺序不同结果差出十万八千里：

.b 这种写法做出来就是”绕某个父级原点做轨道运动”的效果：想让元素绕着一个点公转，就把 rotate 写在前面、translate 跟在后面，转过的角度决定公转相位。反过来写则是”滑到位再转身”，这是绝大多数 UI 想要的。

可交换的例外只有两种，我都算过：等比缩放与旋转可交换，scale(2) rotate(30deg) 和 rotate(30deg) scale(2) 都是 matrix(1.732051, 1, -1, 1.732051, 0, 0)；但非等比缩放不行，scale(2, 3) rotate(30deg) 得到 b = 1.5、c = −1，而 rotate(30deg) scale(2, 3) 得到 b = 1、c = −1.5，正好互换。纯平移之间可交换，且顺序不影响任何东西。

落地结论三条：

  1. 要”屏幕像素位移”，就把 translate 写在最前面（最外层），它的 px 值就是最终落屏的位移，不会被后面的缩放或旋转搅动。
  2. 要”绕自身原点转”，就把 rotate 写在最后面（最右），前面先做完平移，转身动作干净。
  3. transform-origin 与顺序相互纠缠：它被展开成两侧的补偿平移，所以不改变位移增量、只改变锚点；可只要序列里有旋转，锚点一换、弧线整个换。做翻转、时钟、雷达扫描这类动效时，先把原点定死，再倒推函数顺序，不要边写边试。

3D 与合成层：GPU 提升的代价

perspective 有两种写法。写在父元素上，子元素共享同一个消失点，透视中心是父元素的原点，转起来自然；写成 transform: perspective(600px) 只作用于元素自己，消失点定在自身原点，多个元素同时转就各斜各的。做 3D 菜单优先第一种。

transform-style: preserve-3d 是让子元素继续留在父元素 3D 空间里的开关，默认值 flat 会把子元素压平贴回父元素所在平面——翻转卡片不写它就会半程翻不动，或者整块板子像纸片一样塌过去。backface-visibility: hidden 是必需的另一半：不加的话正面那层背对观众时仍然会画，你看到的是镜像糊在背面上，字是反的。这两条语法上互相独立，缺一个卡片就废了。

再往里一层才是性能话题。translateZ(0)、translate3d(0, 0, 0)、will-change: transform 都会强制建合成层，让元素带上自己的纹理，动画期间合成器只挪纹理位置。will-change 是当时较新的写法：Chrome 36 起支持，Firefox 靠后的版本才补上，IE 与旧 Android 根本不支持——不过被忽略也只是”没建层”，功能不受影响，可以当渐进增强。

但层要收租金，而且按层数收：

  • 每层一块纹理，纹理尺寸按元素变换之后的外接包围盒算。1000px 见方的元素 scale(3)，纹理面积直接放大 9 倍；rotate 与 skew 撑大包围盒，同理吃显存。
  • 超过设备纹理上限就前功尽弃。当年低端 Android GPU 常见上限 2048，部分机型只有 1024 甚至 512，超了的元素退回非合成路径，加速收益清零，还白搭一次建层开销。
  • 层数不设上限时内存与显存一起暴涨，典型症状是整页滚动都掉帧——合成器每帧要拼几十上百块纹理。
  • 旧 Android WebView 与 iPhone 4/4S 那一档的 iOS 上，无脑全站加 translateZ(0) 实测比不加还卡。

所以”什么时候值得提升为层”要有判据：只给有持续动画或频繁过渡的少数元素提升，一次动效里超过十来层就该回头查。hover 这种瞬时过渡，Chrome 40 一般会在动画开始时自动建层、结束后撤掉，不必手动加；真要手动控制，就在容器 :hover 时给子元素切一个带 will-change: transform 的类，transitionend 之后撤掉，纹理随层一起释放。

顺带一个当年很烦的画质副作用：合成层上的文字按建层那一刻栅格化，scale 动画过程中会糊，结束后才重新光栅化（而且不一定立刻做）。长驻缩放的图标用背景图更稳。

兼容性：2015 年 4 月的现实

环境 transform 支持情况 要注意什么
IE9 2D 完整支持，不需要前缀 没有 3D；transition / animation 整个属性被忽略
IE10 / IE11 2D + 3D，无需前缀 will-change 不支持；IE11 的 3D 细节仍有毛病
Android 2.1 – 2.3 只有 2D，且必须写 -webkit-transform 3D 完全不支持，perspective / translateZ 被直接丢掉
Android 4.x 原生浏览器 2D + 3D 可用 仍建议保留 -webkit- 一行
iOS Safari 7 / 8 2D + 3D 可用 preserve-3d 和 overflow: hidden、border-radius 同时用会退化成 flat，翻转卡片在 iOS 上的经典坑；-webkit-backface-visibility 要写
Chrome 40 / Firefox 35 / Safari 7 / 8 基本全支持 前缀留 -webkit- 一份就够

2015 年能用的探测手段只有两条：Modernizr 的 csstransforms3d（靠一个带前缀的探针元素量尺寸判定，本身有误差，最好配合真机），或者同一个声明写两行、带前缀与不带前缀各一份。条件式的特性查询规则当时还没影，自定义变量也同样不存在。另外 progid:DXImageTransform.Microsoft.Matrix 那套老滤镜写法从 IE9 起就完全不需要了，别再往样式表里塞。伪元素写 :after 单冒号比 ::after 稳，IE9 认前者。

怎么量：DevTools 与一段计时脚本

感觉不可靠，读数才可靠。Chrome 40 的 DevTools 里对应的位置是这样：

  • Timeline 面板（2015 年它就叫 Timeline）用 Frames 视图，能看到每帧的 Layout、Paint、Recalculate Style 记录条数与耗时。
  • Settings → Renders 里勾上 Show paint flashing rectangles（重绘块会闪绿）、Show layout borders（布局边界）、Show layer borders（层边界，顺便数层）、Show FPS counter。
  • 独立的 Layers 面板看当前页面有几层、每层纹理多大，层爆炸一查就现形。

判断标准一句话：动 transform 的时候不该出现 Layout 那条紫色记录；出现绿色闪烁块说明它还在 paint。

再做一次粗颗粒的对照实验，1000 次改 left 与 1000 次改 transform，用 console.time 和帧间隔统计掉帧。注意老浏览器 requestAnimationFrame 的入参可能不是数字，度量脚本里自己兜一下，用法与兼容性细节在《DOM 动画与 requestAnimationFrame》里已经写完，这里不展开。

桌面 Chrome 上两者都能跑满，差距在低端机上一眼看得出；left 那一路 Timeline 里 Layout 记录连续不断，transform 那一路只有首尾两次。据此定一份动效写法优先级，团队里照抄：

  1. 首选用 transform / opacity 做动画，配合合成层，最好情况连 paint 都能省掉大半。
  2. 其次是改 width / height / left / top / margin——每改一次一次布局，只在桌面、少量元素时可接受。
  3. 最差是 box-shadow / filter / 大面积背景相关的动画，布局也许省了，但绘制范围巨大，逐帧重画一整圈模糊非常贵。

对应到 transition 的写法：只列真正要插值的属性，绝不要写 all。

小结

transform 的速度来自它不动布局盒，代价在别处：它照样触发重绘，它的动画要靠合成层兑现，而层按包围盒吃纹理。语法上记住三件事就够：translate 的百分比参照自身、rotate 必须带角度单位、skew 的第二个角度默认 0deg。矩阵上记住 matrix(a, b, c, d, e, f) 里前四个管缩放旋转斜切、后两个管像素平移，并且单个 matrix 的 e/f 不被自己的 a/d 放大。最值钱的一条是顺序不可交换：scale(2) translateX(50px) 走 100px，translateX(50px) scale(2) 走 50px，要屏幕像素位移就把 translate 写最前面。性能收口靠判据不靠直觉：只给真正持续动画的少数元素提升为层，will-change 用后即撤，动效优先落在 transform 与 opacity，再用 Timeline、重绘闪烁和层边界面板把结论验一遍——前面那段 1000 次改性的对照脚本值得存档复用。
