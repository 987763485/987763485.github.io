JavaScript 相等运算符 == 与 === 的坑

== 与 === 的差别，绝大多数文章写成了一张怪例清单：背下 [] == ![] 是 true、0 == false 是 true，遇到没见过的组合照样不会推。但 ES5 规范里这件事只有两段伪代码——11.9.3 的 Abstract Equality Comparison 与 11.9.6 的 Strict Equality Comparison，前者十条、后者七条，没有一条需要“记住”，全部是顺序执行的控制流。本文就按规范把这两段算法走一遍：先看清 === 其实是 == 的第一步这一委托关系，再按分支顺序把每个转换点标出来，然后拿它把怪例逐条推平，包括 == 不满足传递性这种真正值得警惕的结论。抽象转换操作 ToPrimitive、ToNumber、ToString 本身长什么样、hint 如何决定 valueOf 与 toString 的优先级、显式转换家族各自的坑，笔者在《JavaScript 数据类型与类型转换详解》里已经完整推导过，本文把它们当作下层函数直接调用，只引用结论，不再重复展开；文中所有比较结果都在 Node 里实跑过。

两段算法的委托关系

先看结构：=== 走 11.9.6，== 走 11.9.3，而 11.9.3 的第一条就是“两边类型相同时，直接执行 x === y”。换句话说，抽象相等不是另一套判定标准，它是“严格相等加八个转换步骤”。看懂这层委托关系，两个运算符就从“两套要背的规则”塌缩成“一套规则加一层预处理”。

第二段里最值得注意的一点：第 4 到第 9 条没有任何一条直接返回 true 或 false，它们只做一件事——把某一边改写后重新回到第 1 条继续匹配。所以整个算法的形状是“一路把两边往同一个类型上推，推到能走第 1 条为止；推不动就落到第 10 条 false”。所有怪例都是这条流水线的正常产物，不需要例外解释。

第 1 条：类型相同时比什么

第 1 条把同类型的情况整包交给 11.9.6，于是那两处反直觉结果同时出现在 == 与 === 上，实测 +0 === -0 为 true、+0 == -0 为 true、NaN !== NaN 为 true、NaN == NaN 为 false。它们不是实现的 bug：4a 与 4b 是把 IEEE 754“NaN 与任何值都不相等”原样搬进规范；4d 与 4e 在 NOTE 里被明确标注为“两者不是同一个值”，规范另有 SameValue 算法把它们分开。工程含义有两条：判 NaN 不能靠相等运算，x === 0 也分不出正零负零，真要区分得看 1 / x 的符号。

String 走第 5 条，比较的是 UTF-16 码元逐个相同，规范不做任何 Unicode 归一化。所以组合字符 é（单码元）与分解形式 e 加 Combining Acute（两个码元）用 === 判是 false，实测两者 === 与 == 都是 false，长度一个是 1 一个是 2。用户输入框、剪贴板与接口传来的文本很可能落在不同形式上，判等前要不要 normalize 是业务层的事，运算符不会替你做。

Boolean 走第 6 条，直接按 true/false 比，true === 1 是 false、true == 1 却是 true，差别完全来自后面第 6/7 条的转换。Object 走第 7 条，只比引用，内容再像也不等：[] == []、{} == {}、[1] == [1]、new String('a') == new String('a') 四个实测全是 false。这一条很多人推错，是因为误以为 == 一定会把对象压成原始值——不会，两边同为 Object 时压根进不了第 8/9 条。

第 2、3 条：null 与 undefined 的封闭小圈子

null == undefined 实测 true，null === undefined 实测 false，前者走的是第 2 条这条独立通道。关键是这个圈子完全封闭：第 10 条把 null/undefined 与其他一切类型的组合直接判 false，转换规则根本不给它们别的路径。实测 null == 0、null == false、undefined == 0、undefined == false、NaN == undefined、null == 'null'、undefined == 'undefined' 全是 false。这条性质是第四节 x == null 写法的规范依据，也是它可靠的唯一原因——圈子外面进不来。

第 4 到第 9 条：分支顺序本身就是语义

十条的顺序不是排版，是语义，有三处必须看清。

第一，第 6/7 条排在第 8/9 条前面。Boolean 一旦参与就立刻被压成 0 或 1，这个动作比 Object 的 ToPrimitive 更早发生。第二，第 8/9 条只处理 String 或 Number 碰上 Object，而且调用 ToPrimitive 时不传 hint——旧文里“hint 缺省时普通对象按 number 方向、Date 按 string 方向”那条结论，就是从这里开始被具体比较表达式消费的。第三，每条改写之后都回到第 1 条重新匹配，所以像 [] == true 这种要跑完整两轮流水线：第 7 条把 true 变 1，第 9 条把 [] 压成 ''，第 5 条把 '' 变 0，最后比的是 0 == 1，堂堂正正地 false（实测）。

把 == 会用到的分支整理成一张速查表，左边与右边各按六种语言类型取组合，同类型只列一次。

左边类型 右边类型 命中 实际执行的比较
同类型（六种皆然） 同类型 1 直接跑 x === y
null undefined 2 true，仅此一条
undefined null 3 true，仅此一条
null 或 undefined Boolean / Number / String / Object 10 false，任何转换都不触发
Number String 4 x == ToNumber(y)
String Number 5 ToNumber(x) == y

这张表可以直接当排查手册用：遇到一个推不出结果的 ==，先定左右类型落在哪一行，改写一次，再回表查下一行，两三跳必然收敛到第 1 条或第 10 条。Boolean 对 Object 不在表里单列，因为它先命中第 6 条变成 Number，再落到第 9 行。

最后一个怪例不在算法里，值得单独立一案：document.all == null 在老 IE 上实测是 true，而 typeof document.all 返回的是 'undefined'。拿 11.9.3 这张表推是推不出 true 的——Undefined 或 Object 碰 Null，按第 10 条应当判 false。唯一诚实的解释是 document.all 根本不是 ECMAScript 值，它是 host object，不受第 8 章的语言类型定义约束，浏览器为了不让依赖它的存量页面崩掉而留了个规范之外的口子。2015 年 4 月的今天这件事还没有正式说法，只有当年事实：只有 IE 及其内核的环境会这样，Node 与标准浏览器里复现不出来，写在这里是为了立一条方法论——表推不出来的东西，先怀疑值到底是不是语言值，而不是怀疑表。

引擎层面：== 到底慢不慢

2015 年的 V8 与 IonMonkey 都不是逐条执行规范算法的解释器。当一行 == 两边的类型组合长期固定——绝大多数代码就是这样——引擎会为它做类型推断与内联缓存，把 11.9.3 那十条折叠成一条已知的转换路径，只在类型来回变化时才退回慢路径跑完整的转换流程。=== 少了几个分支，理论上确实省一点，可省下来的那点开销跟一次 ToPrimitive 可能触发的用户函数调用完全不成比例，更别提跟比较本身在流水线里的权重比。工程口径是：== 相对 === 没有可以拿来当理由的性能优势，也没有需要绕开的性能劣势，“用 === 更快”这个流传甚广的说法在当年已经站不住。真正的选型理由是可读性与可推断性：=== 的结果只由两个值本身决定，读代码不必在脑子里跑一遍转换表；== 的结果还取决于两边当前各是什么类型，上游接口把数字改成字符串，比较的语义就静默变了，而它照样返回 true，测试不一定拦得住。性能之争可以收场，语义之争是长期的。

规范为什么要留两套算法

== 不是设计失误，是兼容策略，四条转换分支各有它的历史客户。第 4/5 条的 String 与 Number 互转对着表单与 URL 参数——input.value 取出来永远是字符串，age === 18 会永远 false，宽松转换让海量直接比较的老页面能跑起来。第 6/7 条的 Boolean 压成 0/1，对着早期的开关量与真假混乱的宿主值。第 8/9 条的 Object 压成原始值，对着数组、包装对象与 toString 重载。TC39 想收紧时，动任何一条都要碎一片存量代码，于是 2015 年的现实是两套算法并存：== 保留全部转换，=== 提供一个干净的默认选项，选择权交给人和 linter。

=== 自己剩下的两处不完美——NaN === NaN 为 false、+0 === -0 为 true——ES6 草案里给的办法是补一个静态方法 Object.is，用规范的 SameValue 把这两处对齐到“同一个值”的直觉。2015 年 4 月它只有个别引擎实现，不能当可用 API 写进代码，判 NaN 的当前写法还是 typeof x === 'number' && x !== x。顺带一句展望：ES6 会加进第七种类型 Symbol，拿这张表一推就知道它不需要重新学——新类型与所有现存类型的组合全部落在第 10 条，两个不同的 Symbol 跟任何值都不会 ==，只有同一个 Symbol 与它自己相等。

收口：能进代码库的判等规约

算法讲完了，落成六条团队约定。

第一，默认一律 === 与 !==。第二，唯一允许 == 的写法是 if (x == null)，它的正当性完全来自第 2、3、10 条那三行——null 与 undefined 的相等圈子是封闭的，0、''、false、NaN、[] 一个都进不来。实测把 [0, 1, '', '0', ' ', false, true, NaN, undefined, null, [], {}, [0], 'abc', function () {}] 逐个跑 v == null 与 v === null || v === undefined，两列结果逐位一致。等价的啰嗦写法也摆在这里，团队选一支统一即可：

== undefined 同理成立，但 == true、== ''、== 0 一支都不许豁免。第三，表单与 URL 参数在边界处一次转干净：var age = parseInt(value, 10); 或 var age = Number(value);，之后一律 ===；反要比文本就把两边都 String()。别让“到底哪边是字符串”取决于上游什么时候改过字段类型——实测 Number(' 18 ') 是 18，'18' === 18 是 false，parseInt('18', 10) === 18 是 true，这三行就是规约的全部理由。第四，布尔不写 if (flag == true)。实测 var flag = 'yes' 时 flag == true 是 false 而 !!flag 是真：想表达“非空”就写 if (flag)，想区分“未设置”与“假值”就写 flag === true，别拿宽松比较当三态处理。第五，数组与对象的判等只有三条正路：比引用（a === b，问的是不是同一个对象）、比关键字段（a.id === b.id）、比结构（长度加逐字段，或序列化后比字符串）。序列化那条有坑，实测 JSON.stringify({a: 1, b: 2}) === JSON.stringify({b: 2, a: 1}) 为 false——键顺序按插入顺序走，两边必须由同一个构造函数产出才可靠；跨结构的深度比较交给 underscore 的 _.isEqual，别自己手写。第六，工具链兜住机械项：JSHint 的 eqeqeq 规则直接把豁免外的一切 == 拦在提交之前（ESLint 1.x 刚起步，同名规则也是 eqeqeq，愿意上就一并配上），代码评审里加一条检查点：看到 == 就要求作者当场背出第 2、3、10 条，背不出来就改成 ===。机器能查的不要消耗人工评审，人工评审只查机器查不了的语义。

小结

=== 是七条控制流，== 是十条控制流，而 == 的第一条就把同类型整包委托给 ===——这才是两个运算符的真实关系，也是本文速查表能成立的根子。剩下的十一条转换分支没有一条是特例，它们只规定“什么时候调用哪一个下层抽象操作、调用完回到哪一条重新匹配”，[] == ![]、d == +d、new String('a') == 'a' 全是这条流水线的正常产物；唯一的例外 document.all 恰恰因为它不是语言值。真正需要写进脑子里的结论只有一个：== 不满足传递性，因此任何依赖它的推理都不安全，工程上默认 ===、只豁免 x == null，其余交给 linter。以后再碰到推不出来的等式，回到第 1 条起手，按表往下走两三跳，一定能收敛。
