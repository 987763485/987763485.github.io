jQuery 链式调用与隐式迭代原理

项目里最常见的两类 jQuery 疑问，其实答案是同一个。第一类是控制台报错：$('p').css('color').addClass('red') 抛 undefined is not a function，链子莫名其妙断了。第二类是性能：页面上只有几十个元素时一切正常，列表一渲染到 500 行，each 里的循环就明显卡手。两件事看着不相关，本质都是”链式调用靠 return this 续命，隐式迭代靠每次迭代真的去碰 DOM”这两个机制的结果。本文按这两个机制往下拆，所有结论都对着 jQuery 1.11.3 的未压缩源码逐条核过，jQuery 2.1 在这几处机制完全相同。文中所有”实测”，指在 node 里加载 jquery-1.11.3.js 配一个最小 DOM 环境跑出来的结果，量的是返回值类型、实例个数、写入次数这类机制性的事实，不涉及具体毫秒数——那个数字换台机器就变了，说它没有意义。

链式没有任何魔法，每个方法在末尾把调用者自己交回去，于是下一个点号还能继续点。翻 jQuery 1.11.3 的源码，addClass 的实现末尾就是这一句（节选）：

隐式迭代：方法体里那句 this.each

上面 addClass 的函数形式分支已经露出端倪：jQuery 大量方法的内核是 return this.each(function(){ ... })，而实例方法 each 只是把活转给静态方法：

jQuery.each 里真正起作用的是这一句：

callback.call(obj[i], ...)——回调的 this 被换成了集合里的原生 DOM 元素，不是 jQuery 对象。这就是”隐式迭代”的全部机制：你写 $('li').addClass('x')，是 jQuery 替你 for 了一遍；你写 $('li').each(...)，回调里拿到的是原生节点，this instanceof jQuery 为假（实测），$(this) instanceof jQuery 为真（实测）。所以链式里要重新包一层 $(this) 才能继续用 jQuery 方法——这个坑与参数顺序、return false 中断语义在《jQuery 的 each 与 $.each 的区别》里已经写透，这里不重复，只谈代价。

代价就是包装次数。我把 jQuery.fn.init 换成一个计数用的透明壳子，在 1000 个 li 上实测新建 jQuery 实例的次数：

写法 新建实例次数
$rows.attr('data-i', 'x') 批量赋值 0
$rows.css('color', 'red') 批量赋值 0
$rows.each(fn)，fn 里一次 $(this) 1000
fn 里两次 $(this)（分别 attr 和 addClass） 2000
fn 里 var $t = $(this)，复用 $t 1000

批量版的 attr/css/addClass 是在 for 循环里直接拿 this[i] 操作原生元素，一次包装都不做；而一旦进 each 回调，包装就得自己付钱。同一份源码里 jQuery 自己也踩过这个坑：toggleClass('name') 的实现是 return this.each(function(){ var self = jQuery(this); ... })，实测 100 个节点产生 100 次实例化，而同样语义的 addClass/removeClass 是 0 次；wrap('<div>') 更夸张，100 个节点产生 800 次。读源码的价值就在这里——链式方法名看着一样平，内部成本能差一个数量级。

写成大白话：带值调用（css('color', 'red')）时 chainable 为真，返回集合本身，链式继续；只传名字（css('color')）时走读分支，返回 fn(elems[0], key)——第一个匹配元素的值。实测确认：两个 p 分别设成红和蓝，$('p').css('color') 与 $('p').eq(0).css('color') 完全相等、与 $('p').eq(1).css('color') 不同（读的是当前样式值，具体字符串形态由浏览器序列化，本次环境给出 rgb(255, 0, 0)）；同时 $('p').css('color') === $('p') 为假，返回值上的 .addClass 属性是 undefined，链式当场断掉。html()、val()、attr(name) 同理，源码里都是 this[0] 或 elems[0] 的读分支。

有一个例外必须点名，否则容易被同事问倒：text() 读的是整个集合拼接后的文本。因为它传给 access 的 key 是 null，bulk = key == null 为真，于是走 fn.call(elems) 这一支，回调里是 jQuery.text( this )。实测两个 p 分别是 first 和 second，$('p').text() 得到 firstsecond。它仍然返回字符串、仍然打断链式，只是不再”只取第一个”。空集合上的读行为也值得记：$('#nope') 这种一个元素都没匹配到的集合上，.attr('name')、.val()、.css('color') 都返回 undefined（走 emptyGet），只有 .text() 给的是空字符串。插件里判空要留意 undefined 和空字符串的差别。

链断了怎么回去：pushStack、prevObject 与 end()

getter 打断链式，拆成两句就能救回来。但另一种情况拆句没用：链走到一半，集合本身被换掉了，想回到上一层只能靠栈。这就是 pushStack 的职责：

注意 jQuery.merge( this.constructor(), elems )：先造一个空实例，再把新元素 merge 进去。也就是说 find、filter、eq、slice、map 这些方法一律不改原集合，它们返回一个新栈，旧集合只是被 prevObject 引用住。实测：$ul.find('li') 之后 $ul.length 仍是 1，$li.prevObject === $ul 为真，$li.end() === $ul 为真；$li.filter('.a') 之后 $li.length 也不变。end() 不是重新查询，是把那个引用交回去，成本接近零。

要把”上一层”并进当前集合而不是退回，用 andSelf()。1.11 时期它还在，源码末尾附近就是这一行：jQuery.fn.andSelf = jQuery.fn.addBack;（1.11.3 第 10293 行、2.1.4 第 9152 行）。addBack 是 1.8 引入的正名，andSelf 此时只是它的别名，尚未从发布版里删掉。实测 $ul.find('li').filter('.a').end().andSelf().length 是 4（1 个 ul 加 3 个 li），find('li').addClass('x').end().hasClass('list') 为真。新项目里建议直接写 addBack，两个名字在 1.11 与 2.1 上指向同一个函数，别名只是给旧代码留的退路。

有一个 end() 的小陷阱值得单独说：根集合有没有 prevObject 取决于选择器走了哪条分支。$('#box') 命中的是 ID 快捷分支，直接 return this，没有 prevObject，此时 end() 交出 this.constructor(null)，是个空集合（实测 $('#box').end().length 为 0）。而 $('p') 这种普通选择器走 rootjQuery.find( selector )，于是 prevObject 指向 $(document)——实测 $('p').end().length 是 1，一个”消失的 document 集合”突然出现在链尾。别把 end() 当成”永远安全”的撤销键。

顺带一句不可变的另一面代价：新集合通过 prevObject 持着旧集合，把一条长链的结果存进全局变量，等于沿途每一层集合都被引用着不能释放；同理，链上每一步都在新建实例，find().filter().not() 每步一次分配。链条长度的问题在《jQuery 遍历节点的方法梳理》里算过账，这里只补机制：能一步选择器解决的，就不要用多步链式去换可读性。

隐式迭代慢在哪里：迭代次数乘以写入次数

回到那个几百行的列表。$('li').css('color', 'red') 看起来只是调了一次，但在 1000 个 li 的页面上实测（我给 CSSStyleDeclaration.prototype 上的 color setter 加了计数器），它是 1000 次内联样式写入——隐式迭代把它展开成 N 次 DOM 写。真正让页面卡顿的不是这 N 次赋值本身，而是它们和读操作交错时逼出来的强制同步布局：一旦在循环里读了 height()、offset()、scrollTop() 这类要量盒子的属性，浏览器必须把之前排队的样式写入立刻结算。所以写 jQuery 时把”写”和”读”分开成两段，不要交替。

三种对策，按性价比排：

一，把 N 次写入换成 1 次 class 切换。 样式规则本来就在 CSS 里，用后代选择器套住子元素（例如 .list-ready li { color: red; }），JS 只改容器：

实测同一批 1000 个 li：$('#list').addClass(...) 写 1 次 className，$rows.addClass('hit') 写 1000 次，$rows.each(fn) 里逐个 $(this).addClass(...) 也是 1000 次写入外加 1000 次对象分配。addClass 在 1.11 里有个贴心优化：源码注释写着 “only assign if different to avoid unneeded rendering”，实测对已经有该 class 的 1000 个节点再 addClass 一次，写入次数是 0。所以重复触发同一个状态切换，jQuery 不会造成额外的样式写入。

二，非要用内联样式时，别把隐式迭代翻了个面又做一遍。 这条要澄清一个常见误解：css({ color: 'red', width: '10px' }) 传对象看着像”批量”，但源码里 access 遇到对象类型的 key 是 for (i in key) 逐个属性再递归调一次 jQuery.access，每个属性仍然把整个集合走一遍。实测 100 个节点设两个属性，分开两次 css() 与一次对象写法，样式写入次数都是 200。所以对象写法的收益是少几次方法调用、少几行代码、可读性更好，不是少一半 DOM 写入。真正减少写入的只有第一条：把 N 次写入换成容器上的一次 class 切换，让 CSS 规则去作用到后代身上。

三，新增节点先在文档外拼好，一次性插入。 用 document.createDocumentFragment() 或在字符串阶段就拼完再 .html()，把 N 次插入压成一次回流；这是插入路径的老话题，具体清单旧文已列，本文不重复。

小结

链式的全部机制就是每个方法末尾的 return this，而 $(...) 交给你的是一个「数字索引 + 原型方法」的实例，靠 init.prototype = jQuery.fn 这一行才直接拥有一身方法；它有 length 属性但不是数组，.size() 只是 return this.length 的一次函数调用。隐式迭代则是方法体内那句 return this.each(...)，callback.call(obj[i], ...) 把回调的 this 换成原生 DOM 元素，所以 $(this) 的每一次包装都要真金白银地付——实测 1000 个节点上每多一次包装就多 1000 个实例，而 jQuery 自己的 toggleClass、wrap 也在这条路上留下了实测数字。arguments.length > 1 决定了 css、attr、val、html 是写还是读，读操作只回第一个元素的值（text() 例外，它拼接整个集合），链式到此为止；要用 console.log(this instanceof jQuery) 这样的自查方法确认，而不是猜。pushStack 保证筛选类方法不改原集合、把旧集合记到 prevObject，于是 end() 近乎免费、andSelf()（1.11 里它还是 addBack() 的别名）能把上一层并回来。性能上的结论很朴素：迭代次数乘以写入次数才是真实代价，能用一次 class 切换就别做 N 次内联写入，能一次读写分段就别交替进行。
