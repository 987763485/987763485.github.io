jQuery 的 attr 与 prop 的区别

很多人第一次撞进 attr 和 prop 的区别，都是被一行”看起来没问题”的代码坑的：全选按钮点过一遍之后，再点”取消”，页面上的勾选框无动于衷，可打开控制台一看，标签上的 checked 明明已经消失了。本文就从这张勾选框讲起，先把 attribute 与 property 这两个词到底是什么说清楚，再给出”什么时候用哪个”的口诀。文中所有数值结论都是实测的：把 jQuery 1.11.3 的未压缩源码加载进 node 里的一个最小 DOM 环境跑出来（jQuery 2.1 在这几处的行为完全一致）；只有标注为”历史事实”的条目是当年老 IE 上的既成行为，无法在今天的通用环境里复现，会单独说明验证边界。

HTML 到 DOM 的两份东西

一个页面先是一段 HTML 文本。浏览器解析标签时，尖括号里写的那些”键=值”变成了节点上的 attribute，挂在 element.attributes 里；解析完成后构建出的 DOM 节点是个 JS 对象，对象身上的字段叫 property。名字听起来是一对，实际上它们是两份东西：attribute 属于 HTML 源码，property 属于内存里的实时状态。最典型的例子就是 value：

ipt.value = 'def' 只动了 property，标签上的 attribute 纹丝不动——这是全文最基础的一张对照表。用户往输入框里打字，动的同样是 property；attribute 上的 "abc" 是”初始值”（重置表单时就靠它），property 上的才是”当前值”。jQuery 的 attr() 走 getAttribute 那条通道，prop() 走对象字段那条通道，所以两者读出来的东西可以不一样，而且都”对”——它们回答的根本不是同一个问题。

attr 与 prop 是怎么分家的

这段历史值得知道，因为它解释了为什么老代码里两种写法混在一起。jQuery 1.0/1.1 时代只有 attr，它的策略是”先试着读 DOM property，读不到再退回 attribute”。于是 $(cb).attr('checked') 的返回值完全取决于标签状态：勾选过给字符串 'checked'，没勾给 false，类型飘忽，业务代码没法稳定地比较（以下这段沿革来自官方迁移说明与更新日志，属历史事实）。1.6 想把这个不统一彻底掰成布尔值，结果把 attr('value') 也一起改成了 property 语义，页面上一片哀嚎，1.6.1 又紧急回退。最终方案是 1.6 引入 prop()，把两条通道拆开，到 1.9 拆干净：attr 只碰 attribute，prop 只碰 property，各回各家。我们现在用的 1.11.x 已经是拆完之后的稳定状态，边界清楚，反而比 1.6 到 1.8 那段好讲。

什么时候用哪个

入门阶段背两张清单就够了。

该用 prop 的（读写的是”当前状态”）：checked、disabled、selected、readOnly、multiple 这些布尔状态；value、selectedIndex 这些随用户操作变化的字段；nodeName、nodeType、tagName 这些节点元信息。href 也在这里排个特殊：prop('href') 拿到的是解析后的绝对 URL，实测 attr('href') 给原样的 "page.html"，而 prop('href') 给 "http://example.com/blog/dir/page.html"——要拿能直接用的链接就用 prop。

该用 attr 的（读写的是”HTML 源码里看得见的东西”）：自定义属性 data-*、role、aria-* 这些无障碍与语义属性（2015 年的浏览器里它们大多还没有对应的 DOM property，prop('aria-pressed') 实测返回 undefined）、href 与 src 的原样字符串、以及所有 HTML 标签上写了但 DOM 对象上没有对应字段的东西。class 两种都能读写，不过改 HTML 语义的活儿归 attr 更顺——类名的日常增删改查和 hasClass 的性能注意点，旧文《jQuery 操作 class 与样式的方法》已经讲透，本文不再展开。

读不到时的返回值也不同：attr 读一个不存在的 attribute 给 undefined（1.11.3 源码里就写着 “Non-existent attributes return null, we normalize to undefined”），prop 读一个不存在的 property 也给 undefined，但布尔状态给 false、字符串状态给空串——实测 attr('readonly') 是 undefined，prop('readOnly') 是 false。由此推出一条判空纪律：判断”有没有、是不是”，请直接拿 prop 的返回值走真值判断，不要去和字符串 'undefined' 较劲。把 attr 的结果拼进字符串再比较，undefined 会变成 "undefined" 四个字母，实测这种比较真的能返回 true，白白制造一个误判分支。

表单提交的坑：布尔属性”存在即为真”

HTML 规范里，checked、disabled、selected 这类是布尔属性：标签上写了这个属性名就算数，值是什么无所谓。disabled="false"、disabled=""、disabled="abc" 统统等于禁用——“false”这个字符串恰恰是”存在”，不是”假”。这条规则不是 jQuery 发明的，但它正好和 jQuery 的一个雷咬合：

jQuery 内部只做了抹平，没改语义

jQuery.attr 和 jQuery.prop 各带一张钩子表，jQuery.attrHooks 与 jQuery.propHooks。在 1.11.3 里，这两张表的自有键少得可怜：现代环境下 attrHooks 只有 type（处理老 IE 上 radio/checkbox 改 type 会丢 value 的怪病），propHooks 只有 tabIndex（没显式设置时按可聚焦元素推算默认值）。剩下的兼容补丁都是条件挂载的，源码片段贴两段关键的：

再回头看开头那个 bug。老代码写全选是 $(cb).attr('checked', 'checked')，取消是 attr('checked', false)，问题出在两头。一头是”取消”：在用户交互过的浏览器上（尤其当年的 IE8/9），attribute 只是默认值，摘掉它不会改变已经变”脏”的勾选状态，界面照旧勾着——这是历史事实，实测环境无法完全复现，甚至 1.11 的 removeAttr 内部对布尔属性还有一手”顺手把 property 置 false”的兜底。另一头是”全选”，这个我在实测环境里就复现出来了：先用 checked property 模拟用户点过，再用原生 setAttribute('checked', 'checked') 想把它勾回来，读回来仍是 false——attribute 加上了，状态纹丝不动；而一旦参数传成字符串（比如从服务端渲染的变量里来的 'false'），attr('checked', 'false') 实测会把 attribute 重新加上甚至直接勾上，想取消反而选中。两头都不可靠，所以结论没有第二种写法：读写勾选状态，只认 prop。

data-* 的三条路与一条缓存

自定义数据有三种读法。$('#row').attr('data-x') 读的是标签原样字符串；$('#row').prop('dataset').x 走浏览器原生接口，但注意 dataset 是 IE10 才有的东西，IE9 及更早 prop('dataset') 是 undefined（历史事实），要兼容就不靠它；$('#row').data('x') 走 jQuery 内部的数据缓存，首次读取时把 data-x 做一次 JSON 式类型转换存进缓存，之后不再回头看标签。最后这条是初学者最容易撞的坑，实测序列如下：

收口口诀

把三条线背下来，80% 的场景不会再纠结：改”状态”用 prop，改”HTML 里看得见的东西”用 attr，业务自定义数据用 data 或 attr('data-*')，并记住前者有缓存、后者才实时。 最后单独提醒一条红线：表单的值永远用 val() 读写。val() 内部走的就是 property 通道，而实测表明用户输入之后 attr('value') 读到的还是初始值，拿 attr('value', '新值') 去改当前值也不保证生效（实测写入后 val() 读回来仍是用户输入的内容）——val() 与 attr('value') 从来不是一回事。分不清的时候做个小实验：在控制台里把同一个元素的 attr 和 prop 结果并排打出来，两份值不一致的那一刻，就是你真正理解这对概念的那一刻。
