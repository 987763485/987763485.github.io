JavaScript 发布订阅模式实现

页面顶部一个搜索框，输入变化时要做三件事：列表组件重新拉数据、面包屑替换”搜索：手机”那一段、埋点模块上报一次行为。最省事的写法是在 keyup 回调里连着调三个函数，当天能上线，两周后开始疼。本文从零手写一个 ES5 发布订阅器，讲透 slice 复制、try/catch 隔离、this 约定、off 的三种清空、once、命名空间与 listenTo 记账，再给出三组对比与一张选型表。

一个搜索框，三个下游

先看不带总线的写法。

三个问题迟早出现在评审里。其一，搜索框必须持有下游引用，三个变量得比它先初始化，少一个就是 undefined is not a function。其二，新增下游要改上游——产品要求关键词变化时连地图中心一起挪，地图模块的作者就来改搜索框。其三，单测防抖逻辑得先造三个假对象。

ES5 手写一个能用的发布订阅器

数据结构与完整实现

存储是普通对象：键为事件名、值为回调数组。函数不能当键，因为对象键只能是字符串、得额外挂编号。数组保留订阅顺序，”先订的先跑”对业务有意义，比如埋点要排在 DOM 更新之前。

off 的三种清空形态是刻意的：按函数身份摘单个、不传 fn 时清空该事件、不传 type 时整个总线归零。最后一种是核弹，组件不该碰别人的订阅。清空时顺手 delete events[type] 而不是留空数组，让 _events 的键集合恰好等于”当前真的有人听的事件集合”。

once 没有独立存储，只是注册一个 wrapped：先把自己摘掉再转发参数与 context，所以三次 emit 只执行一次（实测如此），代价是原函数从没进过字典。

emit 必须先复制数组再遍历

我在 node 里跑了两个场景，都确实错位。场景一：依次订阅 a、b、c，b 的执行体里 off 掉 a，数组从 [a, b, c] 变 [b, c]，i 前进到 2 时下标已空，c 被整轮跳过——实测输出 a, b，带 slice 的实现输出 a, b, c。场景二是 once 不加复制：x、y、z 三个订阅，x 触发时把自己摘掉，数组变 [y, z]，i 命中 z，y 永远收不到这次通知——实测输出 x, z。

这类 bug 不是崩溃而是静默漏通知：某次广播少跑了一个组件，页面表现为”就是没刷新”。反过来，遍历期间 on 新增的订阅不插进本轮（实测下一轮才生效），即 emit 的广播范围由调用那一刻的订阅者决定。

一个订阅者抛错，不该拖垮整条广播

try/catch 必须包在循环内部、每个回调外面。包在循环里，一个回调炸了只影响它自己；包住整个 emit，第一个抛错后面全部不执行，等价于上面那个漏通知的 bug。jQuery 的回调队列正是后一种行为，细节见《jQuery的Deferred与Promise模式》。订阅者是独立关注点，隔离是必须的而非可选。

隔离之外还要上报，不能静默吞掉：那句 console.error 在生产环境换成错误收集接口，但别把回调参数整个序列化上传，里面可能塞着 DOM 节点。catch 之后也不要重新 throw。

回调里的 this：约定用，但别依赖

context 是 on 的第三个参数，让回调以某对象身份执行。不传时 ctx 是 undefined，非严格模式下 apply(undefined) 把 this 绑到全局对象（实测 typeof this 为 object）。这默认值有害：this.xxx 拼错不报错，只静默读到全局属性。建议约定不依赖 this，ES5 里闭包更可靠：

this 由 bind 固定后，on 的第三参数就成了可选糖。另有一条实测结论：once 用 fn.apply(this, arguments) 转发 context，this 不会丢，但它包过一层之后 off(type, 原函数) 就摘不掉了，只能靠 on 返回的取消函数。

on 返回取消函数，和经典 off(type, fn) 各有代价

两种方式都保留。经典式符合直觉、和 DOM 与 jQuery 的 API 一致；缺点有两个：同一函数在多个事件上订阅时必须把 type 传对，写错就摘不掉且毫无提示；匿名函数无法用它退订，Bus.on('x', function () { /* 处理 */ }) 写完就丢了句柄，这是内存泄漏的头号来源。

取消函数式解决的正是这两点：句柄交到你手里，闭包记得自己属于哪个事件、是哪条记录，且幂等（实测第一次返回 true、第二次返回 false，不会误删别人的订阅）。

代价是句柄要自己存。订阅散落在各初始化分支时，最后还得补一张”我订了什么”的账本，那就是 listenTo。

重复订阅不去重，这是刻意的

同一函数 on 两次，实测执行两次；off(type, fn) 一次把两份全摘掉（按 fn 身份过滤，不是只删一个）。结论是默认不去重：去重要在 on 里遍历比较，O(1) 变 O(n)，更关键的是它会掩盖”重复订了两次”这个本该去查调用链的问题。真要防重，业务层加一句 if (this._bound) { return; } 更干净。

实测它不误伤名字恰好是前缀的事件：search 与 search:change 并存时 off('search:') 只摘掉后者。另外别占用原生事件名（click、change、load），DOM 侧命名纪律见《自定义事件dispatchEvent实战》。

对比一：全局单例总线还是每实例一份

最常见是一个全局对象走天下，_events 加三个方法三十行写完，但项目变大后问题逐个浮出。命名冲突：两个团队各定义了 user:login，语义不同却共用一条通道。跨模块串扰：谁都能 emit 或 off()，一个模块的调试代码能清空别人的订阅。测试难隔离：用例共用同一个全局字典，前一个残留的订阅污染后一个。无法回收：总线活到页面关闭，它持有的回调连同闭包上层的组件对象永远摘不掉。

换成构造函数造多个实例就收敛了：搜索模块有 searchBus、购物车有 cartBus，测试时 new Emitter() 拿一个干净的，跨模块协作只在两个总线之间显式转发一次。

适用规模 三五个模块的小页面 中型多团队页面 组件库、MVC 对象

对比二：和 DOM 事件系统怎么分工

DOM 事件的载体是元素树：监听器挂在节点上，靠捕获与冒泡沿树传播，路径由节点物理位置决定；传的是 Event 对象，数据只能塞进 detail；只能在 DOM 节点上触发。发布订阅的载体是普通 JS 对象：没有传播阶段，参数想传几个传几个（实测 emit('search:change', '手机', 2, 'header') 三个参数原样到达）。

分工因此清楚：UI 交互与”元素上发生了什么”用 DOM 事件，数据与状态变化用发布订阅。 用户点按钮是 DOM 事件；”点击后订单变成已支付、所有关心订单的区块都该刷新”是发布订阅。后者硬塞进 DOM，就得先造一个谁都摸不到的隐藏 div 当信箱——别把 DOM 事件总线当万能总线。

三条失效场景：组件被移出文档树或克隆时冒泡路径悄悄变了，而订阅关系不受影响；纯逻辑模块根本没有元素可挂；跑在 Node 里单测时 document 都不存在。反过来，需要 preventDefault 或冒泡委托给父级时，发布订阅帮不上忙。DOM 侧 createEvent、CustomEvent、dispatchEvent 的写法与 IE 兼容差异，另有一篇《自定义事件dispatchEvent实战》专讲，本文不重复。

另一点：emit 是同步的，循环跑完才返回；需要”本轮结束后再消费”就自己 setTimeout(fn, 0)，排队机制见《JavaScript事件循环机制解析》。

对比三：jQuery.Callbacks、Backbone.Events 还是自己写

页面里已经跑了 jQuery 1.11，很多人第一反应是 $.Callbacks，但它不是发布订阅：它创建的是一条回调列表，没有事件名。一个实例只表示”一组可被 fire 的函数”，要表达三种事件就得建三个实例、再用变量名记住哪个是哪个。四个标志位（once、memory、unique、stopOnFalse）管的是触发策略，其中最实用的 memory 恰恰是发布订阅做不到的：事件发生之后才来的迟到者仍能立刻拿到上次值。所以它适合”一个异步操作的多个观察者”，不适合”多种事件的广播中心”；它的 remove/empty 可直接解绑。

Backbone.Events（1.1.x）是完整发布订阅，除 on/off/trigger 外还有手写版没有的 listenTo 与 stopListening，解决的是解绑的责任归属：Bus.on(type, fn) 之后”记得解绑”挂在 Bus 上，而 Bus 不认识订阅者，销毁时无从下手；listenTo 把账记到订阅者自己身上，销毁前一句 stopListening() 就把挂在外面的订阅全摘干净。

方案 依赖成本 可测试性 解绑便利性 体积 适用
手写 30 行 Emitter 零依赖 好，每用例 new 一个 需自建账本，靠 on 返回取消函数缓解 约 1 KB 未压缩 组件库、要在 Node 跑
$.Callbacks 需 jQuery（1.11 全量约 95 KB） 一般，全局库状态 remove/empty 直接可用 已在包里，增量为 0 已用 jQuery，只需一组回调
Backbone.Events 需 Underscore 1.7 或 lodash 2.4（约 4 KB） 好，混入即隔离 listenTo/stopListening 最省心 约 2 KB 已有 MVC 结构、生命周期复杂
自建 Bus 实例（本文） 零依赖 最好，作用域可控 记账式 listenTo 加前缀退订 约 1.5 KB 中大型单页、多团队协作

结论：已有 Backbone 就别再混入自研 Events，两套 _events 结构不兼容会互相覆盖；只有 jQuery 且不需要事件名时 $.Callbacks('once memory') 更省；要零依赖又多事件广播，用本文这份。lodash 2.4.1 没有事件模块，但它的 _.extend 可以顶替 Underscore 那份，混入写法不变。

内存与生命周期：最容易踩的一节

订阅关系是强引用。Bus.on('search:change', function () { that.render(); }) 里，Bus 的数组持有那个匿名函数，函数闭包持有 that，that 又持有它的 DOM 节点和整份数据。组件从页面上 removeChild 掉，不等于它从内存里消失了——只要 Bus 还指着它的回调，垃圾回收就动不了它。这类泄漏在单页应用里表现为”切了十页之后开始卡”，堆里全是早已不在 DOM 上的视图对象，与《DOM事件移除与内存泄漏》同理。

对策分三层。第一层，组件提供 destroy，里面显式退订——前提是你拿得到句柄，所以订阅那一刻就把取消函数存下来，或走 off('search:') 的前缀卸载。第二层，记账式 listenTo，把”我在谁那里订了什么”记在自己的数组里，销毁时批量解绑：

三个细节：倒序遍历是因为 splice 会改变后续下标，正序删会漏（与 emit 的索引问题同类）；三个参数都可选，stopListening() 全清、stopListening(bus) 只断某个源、stopListening(bus, type) 只断某个事件；账本清空后 delete this._listening。

实测记账有效：两个 Widget 各自 listenTo 同一事件，w1.destroy() 里调一句 stopListening() 之后，总线的 _events['search:change'] 从 2 条降到 1 条，w1._listening 变回 undefined；再广播一次只有 w2 计数加一——总线不再持有 w1 的引用。

第三层是工程约束：路由或页面销毁的收尾钩子里把该页面的私有总线一并处理掉；若坚持全局单例，”切页清总线”得是固定流程的一步。命名空间前缀在这一步很关键——它清理的是事件名而非函数句柄，一行覆盖一个模块的全部订阅。

选型结论与规约

要不要为搜索框引入总线，按规模给结论：

场景 建议 理由
一个模块、下游固定不超过两个 直接函数调用 总线的调试成本高于解耦收益
一对多通知且下游会持续增加 发布订阅，每模块一个 Bus 实例 上游零改动，新下游自行订阅
组件对外通知（选项卡、弹窗、日期控件） 混入 Events 到原型，或派发 DOM 事件 事件跟着组件生死，不用全局账本
组件间数据同步且组件反复创建销毁 listenTo/stopListening 记账 销毁时能一键摘干净
页面已重度使用 Backbone 直接用 Backbone.Events 别再混一套结构不兼容的实现
只需要”完成时通知一组人” $.Callbacks('once memory') 要的是回调列表，不是事件名

三条规约值得进团队规范。事件名常量化：用一个冻结对象集中维护，拼错字符串只静默失配，这是发布订阅事故率最高的 bug。别在总线上传大对象：只要有一个长命订阅者把参数存进闭包，那份数据就跟着它活下去，所以参数只传 id 与状态。别在 emit 里同步做重活：广播是同步循环，回调里跑大循环或触发强制同步布局，会直接算进用户那次输入的耗时，重活要么拆片，要么自己 setTimeout 让出主线程。

小结

核心是 on/off/emit 三个方法，但决定能不能进生产的是四个细节——emit 里那行 slice(0)（不复制会静默漏通知，实测跳过 c 与 y）、每个回调一层的 try/catch、off 的三种清空粒度、on 返回取消函数。三组对比各有边界：全局单例省事但命名冲突与测试污染躲不掉，实例化或混入才谈得上隔离；DOM 事件管元素与传播、发布订阅管对象与状态；$.Callbacks 是没有事件名的回调列表，Backbone.Events 靠 listenTo/stopListening 把解绑责任挪回订阅者身上。最贵的坑是强引用：组件销毁必须同时是订阅注销。
