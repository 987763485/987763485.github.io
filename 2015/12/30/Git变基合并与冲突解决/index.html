Git 变基、合并与冲突解决

写这篇文章的念头来自今年冬天的一次事故。同事对我们四个人共同开发的 feature 分支做了一次 git rebase -i，把三十多个乱糟糟的提交压成十个，然后 git push --force。我本地还攥着旧的提交链，一次 git pull 之后，同一处改动在图里出现了整整两份，后续每次合并都要多解一堆冲突。那段时间我一直说不清楚一件事：为什么同一段冲突标记里的 --ours 和 --theirs，在合并时和变基时含义是反的。等到 2015 年快过完，Git 2.6 已经是不少团队里常见的版本，2.7 也刚刚发布，可很多人对 Git 的日常使用仍然停在 commit 与 push 的层面，把变基当成一条”能对齐上游”的神秘咒语。我想把合并、变基、冲突解决这三件事从对象层面讲透，因为它们其实是同一张图上的三种手术。

这篇文章不做环境搭建，也不讲分支怎么起名、团队走什么流程，那些内容另有文章。它只回答三个问题：历史到底长什么样；合并与变基各自在图上动了哪一步；冲突发生时，标记块里谁的话说了算。文中的每条命令都附上当时终端里的真实输出形态，你可以拿一个练手仓库逐步复现。先约定记号：所有提交哈希都是随手编的占位符，形如 a1b2c3d，不指向任何真实仓库；示例分支名 master、feature/search、hotfix 只是常见叫法。

历史先是一张有向图

谈变基与合并之前，先把脚下的地面夯实：Git 的历史不是时间轴，而是一张有向无环图，后面每一个操作都是在这张图上做小手术。

一个 Git 提交对象只存四样东西：整棵工作区快照的指针（tree）、父提交指针（parent，可以零个、一个或多个）、作者与提交者信息及时间、提交说明。哈希是对这些内容整体算出来的，动一个字节哈希就变。这个事实提前决定了”重放”的命运——变基即使一个字没改你的 diff，也会产出新哈希，因为 parent 与提交时间戳变了。

普通提交只有一个 parent。合并提交有两个 parent：第一父指向你执行合并时站着的分支，第二父指向被合入分支的顶点。这个次序在后文讲 git revert -m 1 时有直接的用处。

分支本身只是一个可移动的指针，指向某个提交；HEAD 指向你当前所在的分支，每次提交把指针往前挪一步。git checkout 直接指向某个提交哈希、脱离所有分支，就是终端会警告你的分离头指针状态。指针体系里还有几个临时记号要交代清楚：HEAD^ 指第一父提交，HEAD^2 指第二父（对非合并提交无意义），HEAD~3 沿第一父链往回走三代。ORIG_HEAD 则由 merge、rebase、reset 这类命令在移动 HEAD 之前自动写下，记录”动手之前我在哪”——合并搞砸了，git reset --hard ORIG_HEAD 是最快的撤退路线。

回合点的另一面是回滚。撤销一个功能用 git revert -m 1 e5f6a78，它会生成一个反向提交；-m 1 指定以第一父（合并时你站着的主线）为保留侧，含义是”从主线视角撤掉第二父带进来的内容”。不加 -m 时 Git 直接拒绝工作：

这里的坑在于：revert 之后，feature 的那些提交还挂在图上，只是内容被反向补丁抵消了。过两周你修好这个功能再次合入，合并基点按图算仍是当年那个公共祖先，Git 认为这些提交早就进过主线，不会把旧内容重新带回来——除非新的修复提交恰好重新触碰同一批行。整个过程不报任何冲突，代码却悄悄少了。补救办法二选一：想整体回来，就 git revert 那个回滚提交本身；想继续往前走，就确保新提交完整覆盖旧改动涉及的所有行。我的经验是，凡是 revert 一个合并，提交说明里必须写清楚缘由和后续合入的注意事项，否则下一个人合并时得不到任何提示。

三方合并：基点、冲突与 diff3

两边都有分叉时，Git 做的是三方合并，三份输入：两条分支最近的公共祖先（merge base）、你这侧的顶点版本、对方那侧的顶点版本。基点不用猜：

算法以基点为参照逐块比对两份差异：一块只有单方改过，直接采纳；双方改的是不同的块，两边都要；只有双方把同一块改成不同结果，Git 才停下来标记冲突。所以”冲突只在双方都改了同一处时出现”这句话要抠字眼：这个同一处是相对基点的区域概念，不是同一个文件更不是同一个行号——你改文件头部的函数、同事改底部的大函数，一样干净合入；一方在中间插入导致后面行号集体偏移，也不算撞车。真正常见的冲突面是同一个函数体被两人改写、一方改名一方修改的改名删除冲突，以及双方各自新增同名文件的添加添加冲突。

正是这次”换号重放”划出了变基的红线：它在改写历史。只要别人已经从远端拉走过旧的提交链，他手里的链就与你的新链哈希对不上；他下次拉取时，Git 会看到两条血脉并把它们合并成一张图——同一改动出现两份，本文开头那场事故就是这么来的。于是纪律只有一条：只改写还没发表的东西。对纯本地的分支变基对齐上游是值得推广的好实践，历史保持直线清爽；对已经推送、可能被任何人拉取过的公共分支变基则是禁止项，共享分支上游动了，唯一正确的姿势是用合并把它拉下来。

edit 处理”中途某个提交写错了一行”：停住、改完、继续，后续提交在新基础上重放，撞上要冲突就按第七节的规则处理。reword 我常用于给混进主线之前的提交补说明——“改bug”不是合格的提交说明，它是写给三个月后查代码的人的文档。一句提醒：这三个动作全部改变提交对象内容、全部换哈希，所以 -i 的作用范围必须都是未发表的提交，整理别人已经拉走的分支不在此列。

冲突中的三个出口：git merge --abort 与 git rebase --abort 把你毫发无损地送回动手前的 ORIG_HEAD 状态，力气白费但东西都在；变基途中 git rebase --skip 表示放弃当前正在重放的这个提交——手滑的调试提交可以这样跳过，但敲下去之前务必确认跳的不是你要的改动；拿着解决结果前进就是 --continue。

开启后，你手工解决的每一次冲突，Git 都把”这段冲突文本对应这份解决结果”记录在 .git/rr-cache 里；同样的冲突文本再次出现时自动套用旧方案并告诉你它干了这件事。长寿分支反复同步上游、一段重放链多次中断重来，都是它的适用场景。要认清它复用的是什么：是解决方案本身，不是某种聪明算法，它不理解意图。如果两次冲突你未必想给出同样的答案，别开它——让机器替你默默按第一次的选择解决第二次，比冲突可见地摆在那里更麻烦。

强推的安全边界：–force-with-lease

本地分支改写历史后再推送，远端会因为非快进而拒绝普通 push。这时裸 --force 应当换成带租约的强推：

它的语义是”有条件的覆盖”：只有远端分支还停在我本地远程跟踪记录的位置，才允许覆盖；若同事在你上次取回之后推过新提交，远端与你的预期不符，推送直接被拒：

这个选项规定的早期版本就已经进了主线，Git 2.6 时代没有理由继续裸推。裸 --force 的危险在于盲目：它不问远端现在是什么，一律用本地顶掉，撞上”同事刚推了我还没取回”的窗口，覆盖掉的就是别人的工作，找回的责任全落在 reflog 上。--force-with-lease 把”我确定没人动过”从祈祷变成前置条件，条件失败无非重新取回、重新对齐，成本可控。

服务端还有第二道保险：仓库设置 receive.denyNonFastForwards = true 后，服务器拒绝一切覆盖式推送。我们内网自建的 GitLab 在发布分支上启用了这个设置，再加 pre-receive 钩子拦住向发布分支的强推，CI 侧的规则写死：发布分支只接受快进。理由说到底是可复现性——构建产物对应的提交必须能从主线线性解释，审计要求哪怕只是”向下一个接手的人解释清楚上过线的是什么”，也会被一次悄无声息的强推破坏。

后悔药：reflog、reset 与 stash 的边界

abort、ORIG_HEAD 都是”进行时”的解法，事后永远有效的是 reflog：HEAD 的每一次移动都留底，分支指针也有各自的日志。

分支指针被 reset 或被变基带走、想回到旧链时，先给旧位置命名，别急着动 HEAD：

两条链在图上比完、确定要留哪条之后，再 git checkout feature 加 git reset --hard feature-old 整体回退。为什么”丢掉”的提交通常找得回来：提交对象只有不再被任何引用指向才进入不可达集合，而 reflog 默认把它保留九十天再等回收，除非有人跑了激进的 gc 加立刻清理，那种情况才是真没了。

stash 不在这套恢复体系里，别把它当长期存放点。它不进提交图，只是把改动压成 refs/stash 下的临时栈，默认连未跟踪文件都不收；pop、drop、切分支都可能造成误用，条目也不带提交说明供日后审读。我吃过教训：半天的改动丢进 stash，两周后翻出来 pop，彼时的上下文早蒸发干净，还要不要每段都得重读代码重新猜意图。现在我改不动的方向是：做一半的提交就带着 WIP 前缀说明提交到主题分支——提交有哈希、有时间、进 reflog，任何人任何工具在任何时间点都找得回；stash 只配活到当天收工。

一次事故复盘：共享分支上的 rebase -i

回到开头那件事，完整复盘。十二月初，四人共用的搜索 feature 分支挂了三十多个”改样式 again”式的提交，一位同事没忍住，本地 git rebase -i 压成十个，然后 git push --force。第二天我像往常一样 git pull，Git 看着它的新链和我的旧链，认为这是两股血脉，合并成了一张图：

同一改动两份，且两份不完全相同——捏合时他顺手修掉了一个小问题。此后每个涉及的冲突都变成三方的：我的旧副本、他的新副本、上游的新改动，不同文件里解的方向还不一致，同一行代码的命运交给了运气。恢复步骤按顺序：

  1. git reflog 找到拉取前旧链的最后位置，立刻 git branch feature-legacy 把旧链钉住；
  2. git diff feature-legacy origin/feature 比较两条链的内容——输出只剩那个顺手的小修复，说明捏合没丢任何人的工作；若出现无关的内容差异，就是他捏合时弄丢了东西，得从旧链逐个补摘回去；
  3. 我在切换点之后自己新写的提交，用 git format-patch 存成补丁，分支 git reset --hard 到新链之后再用 git am 重放;
  4. 四个人都确认对齐到新链后，删掉 feature-legacy。

事后团队约定三条规矩：分支在”第二个人拉取过”之前才允许变基改形状；一旦多人上车，同步一律合并，历史整理的权利收归合入主干那一刻由维护者执行；强推必须带租约，且推之前群里吼一声。这场事故教我的不是”别用变基”，而是边界感：冲突是正常协商，它发生在人面前，逼你逐次思考；”两份历史真相”是事故，它不声不响，渗进后续每一次合并。前者烦人，后者要命。

冲突之后的调试：bisect、–follow、blame

冲突余波里最阴的一类是语义冲突：两处改动文本上不打架、合并安静放行，逻辑上却互相拆台，等你发现时图上已经隔了几十个提交。这时 git bisect 在图上做二分定位：

起点是坏版本、终点是最后已知的好标签，check.sh 行为正确返回 0、出错返回非零；没有脚本就手动配合，它检出哪个版本你测哪个，然后回答 git bisect good 或 git bisect bad，最后它指认第一个坏提交。在满是合并的历史里跑二分，有时会停在合并提交上——错误恰好出在它手工解决冲突的那一段。这时用 git log --cc e5f6a78：它只显示与两个父都不同的块，也就是解决冲突时人亲手写下的部分，机器自动合并的内容一概不出现，嫌疑立刻缩到几行。

另外两条命令负责回答”该问谁”。git log -p --follow src/utils/debounce.js 跨改名追完整变更史，半年前改过名的文件不会在改名点戛然而止变成空白页。git blame -L 120,160 -M -C src/pages/search.js 里，-M 识别文件内移动、-C 识别跨文件拷贝——大重构之后裸跑 blame 会把每一行都算到重构者头上，带上这两个参数才追得到逻辑的最初作者，冲突涉及业务边界时直接找人，比对着代码猜快得多。

该用 merge 还是 rebase

标题里的问题，答案不是口号，是四个变量：

考量 倾向 merge 倾向 rebase
历史清晰度 接受回合点，主干上每个功能边界可见 主干一条直线，一事一提交
是否已共享 别人拉取过，只能合并 纯本地未发表，随便整理
冲突次数 长寿分支、上游提交多，一次合并集中解决 少量提交重放，冲突逐提交处理
审计要求 需要”谁何时合了什么”的现场证据 整理发生在合入之前，进主干后不再动

按我自己的决策顺序展开：本地分支对齐上游用变基，feature 合入主干用 --no-ff 合并，个别提交修 bug 用 cherry-pick -x，成批搬提交用 --onto；只改写未发表的历史，要覆盖远端就带租约。冲突现场先弄清自己是 merge 还是 rebase，看清标记分布再动手；事后无论出了什么岔子，记住最后一句：reflog 永远在，移动任何指针之前先把旧位置命名钉住——回头的底气来自先钉住，而不是祈祷不出事。

三件事讲完：历史是图，合并与变基是图上两种形状手术，冲突是两张理解在基点前的对质。命令是死的，图是活的，下次再撞见冲突，先画出那两条链再决定听谁的。
