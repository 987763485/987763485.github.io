npm 常用命令与 package.json 详解

package.json 我起初是照着别人项目抄的，抄了半年才承认自己讲不出每个字段凭什么在那儿。npm 命令也一样，装得上、跑得通就以为懂了。让这两件事分层的是今年底把构建机从 Node 4 换到 Node 5 的那次试验：同一份 package.json，两台机器装出来的 node_modules 结构完全不同，npm ls 也从一棵嵌套塔变成一片扁平目录加几条冲突提示。

年代口径先摆明

本文行为都基于 npm 2 与 npm 3：Node 4 这条 LTS 线自带 npm 2.14，Node 5 从 2015 年 10 月底起带 npm 3。最大差别不是命令名，而是 node_modules 的排布策略。npm 2 讲”谁的依赖归谁”，每个包下面再开一层自己的 node_modules，路径过长报错和同一个库被装十几份都是日常。npm 3 改成尽量往顶层提，能提的提到根目录只留一份，只有版本冲突塞不下时才在父包下面补一层。

影响有两处。一是 npm ls：npm 2 那棵树如实反映谁依赖谁，扁平化之后顶层一片整齐，但你查不出某个包究竟被谁引入，只能靠 --depth、--all 反复试。二是 peerDependencies 的提示变廉价了：npm 2 遇到同伴依赖不满足是直接报错中断的，npm 3 只打一行 UNMET PEER DEPENDENCY 警告然后照样装完，于是绝大多数人开始无视它，插件与宿主版本对不上被推迟到运行时才炸。

语义化版本：区间符号怎么选

package.json 里的版本号几乎从来不是精确值，而是区间。约定很直白：修订号是向后兼容的问题修补，次版本是向后兼容的新功能，主版本才允许不兼容。符号决定你愿意让安装器走到哪一层。

1.2.3 锁死三个数字；~1.2.3 放开最右边那一段，接受 1.2.x 里不小于 3 的修订号，不会给你 1.3.0；^1.2.3 把次版本和修订号都放开，等价于 >=1.2.3 <2.0.0；>= 这类比较符得自己配一个 < 才是完整约束，只写下界等于没有上界；* 是全放行，装当期最新版，除了临时试验别留在提交记录里。

^ 的坑在 0.x。约定把 0.x 视作”还不稳定，每次次版本都可能破坏接口”，所以 ^0.2.3 不等价于 <0.3.0，而是收紧到只允许 0.2.x，^0.0.3 更是锁死到那一个版本。这个特例在 2015 年踩得最狠：新出的构建工具、加载器、插件正集体停在 0.x，0.9 跳到 0.10 就把配置字段改名是常事，而大家凭直觉写 ^，以为它和 1.x 行为一致。笔者的对策是凡是 0.x 一律精确版本，或安装时直接加 --save-exact。

依赖分三类，各给谁装

分类标准只有一条：这个包在服务器上跑业务代码时会不会被 require 到。会的进 dependencies，只在构建、测试、出文档时用到的进 devDependencies，因为 npm install --production 会把后者整个跳过。当年最常见的错位是把 Gulp 插件写进 dependencies——那是 2015 年的构建流程里还在大量使用的一类专业工具，线上根本用不到，写错位置只会让部署包变大、装得更慢。

--save 写进 dependencies，--save-dev 写进 devDependencies，--save-optional 写进 optionalDependencies，最后这个只适用于”装失败也不该让整次安装失败”的原生扩展，别拿来给必需依赖兜底。--save-exact 把区间写成精确版本，前面的 0.x 问题靠它一次解决。npm 3 里 --save 已是默认行为，--save-dev 仍要显式写。

peerDependencies 是第三种语义：不是”我要它”，而是”我假设宿主已经装了它且版本得对”，插件库声明一段同伴区间，自己不把它装进依赖树。npm 2 会拦，npm 3 只警告。警告没人看，就得靠流程补——构建脚本里读一次 npm ls 的退出码，比在 README 上写”请自行确保版本匹配”可靠。

其余字段逐个说：用途与误用

main 与 browser

main 是别人 require('包名') 时落到的入口，默认包根下的 index.js，只在 CommonJS 的解析规则里生效。入口是编译产物时要确认它真在发布包里，否则报错出现在使用者机器上，你自己在仓库里一切正常。当年已开始有前端库补一个 browser 字段做浏览器专用入口，同一份能力在 Node 走 fs、在浏览器换一份实现，靠这两个字段分岔；但它由构建工具解析，不是 Node 的行为，写上不会自动生效。

bin

bin 声明命令行入口，键是命令名，值是脚本路径；全局安装时 npm 会在可执行目录里建软链指过去。

本地安装时它不进全局 PATH，而是落到 node_modules/.bin 下面——这正是 scripts 里能直接写工具名的原因。发布命令行的包还得留意 shebang 行和文件权限，缺一样链接建好了也执行不了。

scripts

scripts 是唯一”字段名可以自定”的部分，npm run 之后跟名字执行，三条规则最容易忘。

一是 pre、post 前缀会自动挂钩：存在 pretest 时 npm test 先跑它，install、publish 这些保留名同样有前后钩子，能省一层编排脚本，代价是没人记得钩子存在。二是传参要用 -- 分界，npm run build -- --minify 里的 --minify 才传给那串命令，漏掉斜杠就变成传给 npm 自己。三是命令名优先从 node_modules/.bin 解析，别在脚本里写死安装目录的长路径。

files 与 .npmignore

两者决定发布时带不带源码、测试和报告。规则是 files 白名单优先：写了它就只按它挑，没写才轮到 .npmignore 做黑名单，而黑名单只要漏加一个新目录，临时文件就跟着发出去。另有几项必定被带上或排除，比如 package.json、README、LICENSE 和名为 test 的目录——这也是当年推荐把测试放在 test/ 的原因之一。

engines、private、preferGlobal

engines 声明能跑在什么 Node 版本上，默认只是声明，npm 看了并不拦你；要让版本不符直接安装失败得打开配置项 engine-strict，所以别把它当环境保障，真要约束构建机得靠 CI 先判版本。private 置真即禁止 npm publish，内部项目都该写上，这是防误发的第一道闸。preferGlobal 如今只剩提示作用，npm 见它会打一句建议全局安装的警告，不再影响安装方式。

keywords、repository、bugs、bundledDependencies

keywords 只影响搜索命中，堆一串无关热词是自欺欺人。repository 要写成对象带 type 与 url，bugs 带 url 或 email，价值在于别人引用你的包时能找上门反馈，抄一份不带 url 的模板等于没写。bundledDependencies 是数组，列出的包连同 node_modules 里的副本一起打进发布 tarball，使用者不再去 registry 取，适合内部包整体交付或离线环境；代价是体积明显变大、被捆绑的包无法单独修补。

npm init 的骨架缺什么，name 有什么规矩

npm init -y 只保证 JSON 合法，不保证这包能发布：main 默认写 index.js，scripts.test 是一句注定失败的占位命令，license 默认 ISC，版本号从 1.0.0 起跳，description、keywords、repository、bugs、engines 全空。补齐顺序是先改 name 和 version，把 test 换成真能跑的命令，再决定要不要 private。

name 的合法字符限制真会拦住发布：不能以点或下划线开头，字母一律小写，不允许空格，URL 不安全的字符都不行，纯下划线也不合法。老写法里 @用户/包名 那种形式在新版 npm 上会直接报错，迁移时得手动改。作用域包 @team/foo 在 npm 上 2014 年就有了，团队拿私有 scope 发内部包是很自然的用法，只是当时私有包要付费，所以更多团队把它留给真正不想公开的工具，其余走普通名字，或者干脆用 Git 地址安装。

版本怎么锁：这活儿当时还得靠 shrinkwrap

话先说透：npm 2 和 3 时代没有自带的锁文件，重复安装的可控性全押在区间符号和 npm-shrinkwrap.json 上，而现实是很多人压根没锁——把 ^ 提交进仓库，然后在 CI 里 npm install，等于每次构建都重新解一遍依赖树。

--dev 到 npm 3 这一代才补上，npm 2 只能锁生产依赖，而前端项目把大半工具放在 devDependencies，”锁了个寂寞”是真实体验。生成后要像源码一样纳入版本控制，文件必须留在包根，安装时 npm 优先读它而不是重解区间。风险也得写清楚：里面除了版本号还有每个包的 resolved 字段，那是一个具体下载地址，连着内网代理地址一起提交出去，换一台机器或者从公网 registry 拉就可能装不动。所以内部项目用它锁构建，对外发布的库要谨慎——发布前排除它、把区间放宽交给使用者，是当时的通行做法。

另一半是安装参数。npm install --production（旧式的 -production 单横线写法仍可用）跳过开发依赖，构建机用它省一半时间；但一旦 shrinkwrap 没用 --dev 生成而流水线又要跑测试，就撞上”开发依赖不在锁里”的空档。锁的范围和装的范围必须一起定。

常用命令按场景挑

查依赖现状用 npm ls --depth=0，只看顶层，扁平化之后这是最快确认”装没装、装成了哪个版本”的办法。要看整棵树再加 --all，输出会长得没法读，配合管道 grep 更实用。npm ls 发现缺失或未满足的同伴依赖时返回非零退出码，这一点可以被流水线借去当校验。

npm outdated 该在升级前先跑，按”当前 / 期望 / 最新”三列给结果，没有输出代表都到顶了；它只看区间允许的最新版，^1.2.3 的包即使已经出了 2.0.0 那一列也不显示——跨主版本从来不在 npm update 的职责里。npm update 在 npm 3 上的行为让人不舒服：它顺带去满足新区间，却不一定按你的期望刷新 package.json，对已写成精确版本的包也不动。可靠做法是显式重装并写回区间：npm install pkg@^1.2.3 --save 由你指定接受哪一段，npm update pkg 只是往已有区间里填；要跨主版本就用这条把 @2 写进去，装完跑一次 npm ls --depth=0 确认顶层只剩一份。

npm dedupe 在扁平目录上很有用，把树里重复的、能往上提的版本重排一遍，减少同一库的多份副本。npm 3 已经尽量扁平，但冲突回落到父目录时留下的重复依然不少，升完依赖顺手跑一次，UNMET PEER DEPENDENCY 常常跟着少几条。npm view <包名> versions 一次列出全部可用版本，判断”这段区间里有没有我要的那版”比翻网页快；查单个字段用 npm view <包名> <字段>，比如装之前先看它声明了哪一段 peerDependencies。

npm link 把本地目录挂成全局链接，再链到另一个项目，开发”宿主 + 自家插件”这类成对项目时省事。坑在于链接状态下模块解析路径和真实安装不一致，被链接的包引用宿主依赖时可能命中全局那一份，于是”本地好使、CI 挂掉”，用完记得 npm unlink 清干净。npm cache clear 在 npm 3 里必须带 --force，因为清空缓存被标成了危险操作，这个参数决定命令能不能执行。

发布侧两条：npm unpublish 撤包，被安装到一定数量之后会受限；真要停维护，npm deprecate 给旧版本挂一句弃用提示更合适，比把包删掉让所有人构建失败体面得多。

一次线上构建崩掉的复盘

十一月底那次事故到现在还在构建脚本里留着注释：构建机重装依赖之后，Sass 编译报未知函数，本地却一切正常。样式任务依赖一个 Sass 封装包，package.json 里写的是 ^ 区间，它自己又依赖绑定原生二进制的那个包，也是 ^；构建脚本用的是裸 npm install，仓库里没有 shrinkwrap，那天就解到了刚发布的一个修订版，参数名改了。本地之所以正常，只因为那套 node_modules 是两周前装的。

修复分三步。第一步把出问题的两个包用 --save-exact 改回精确版本；第二步补跑一次 npm shrinkwrap --dev，把生成的文件提交进仓库，让流水线跟着它装；第三步跑 npm dedupe 加 npm ls --depth=0，确认顶层每个包只剩一份、没有回落到下层的重复副本。让人后背发凉的是最后那条结论：同一天两次构建完全可以装出两棵不同的树，而区间符号写的就是 ^，谁都没做错任何事。

字段速查表

字段 什么时候必须写 常见误用
dependencies 线上运行会被 require 把构建工具写进来
devDependencies 只在构建、测试时用 生产环境还去装它
peerDependencies 插件对宿主版本的假设 npm 3 只警告，于是不看
version 每次对外发布 手改数字、不守语义化
name 必填 大写、点或下划线开头
main / browser 包会被别人引用 指向没进发布包的路径
bin 提供命令行工具 忘了 shebang 与执行权限
scripts 有统一构建入口 写死 node_modules 长路径
files 要控制发布体积 只靠 .npmignore 做黑名单
engines 对 Node 版本敏感 当成强制保障，没开 engine-strict
private 内部项目 忘了写，误发
preferGlobal 命令行包的提示 以为它能决定安装方式
bundledDependencies 离线或内部整体交付 当常规省流量手段

小结

这一代 npm 要懂的不是命令本身，而是选择的代价：^ 让你少提交几次，也让你无法预测构建结果；把工具放对 devDependencies 让部署包小一半，生产安装参数得跟着改；--save-exact 治 0.x 的乱跳，代价是升级要手动。字段里没有废项，只有你没决定用它来做什么。shrinkwrap 在当年不是可选步骤，它是把区间这个决定真正落地的唯一办法。
