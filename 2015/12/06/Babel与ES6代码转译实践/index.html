Babel 与 ES6 代码转译实践

Babel 6 是 11 月中旬放出来的，到这篇文章为止还不到一个月。我在上周末把团队里两个还挂在 Babel 5 上的项目做了升级，第一个晚上构建一路绿灯，产物丢进浏览器却直接报语法错误——源码里的 class 和箭头函数原样躺在输出文件里，一个字都没被转译。这篇就是那次事故之后的一周复盘，重点不在”ES6 有哪些新语法”（模块语法本身的取舍我在《ES6 Module 模块系统与构建工具》里已经写过），而在升级之后这套工具在项目里到底怎么落地：配置文件怎么写、哪些东西转不了、体积怎么算、发布链路怎么接。

先把时间线摆正

Babel 这个项目对国内开发者有过一次认知干扰：它最早叫 6to5，2015 年 2 月才正式更名 Babel，随之把 6to5-* 那批包名换成 babel-*。那次改名只是换了招牌，内核还是同一条路线。11 月的这次 6.0 不一样，它是一次架构层面的重构，版本号后面跟着的是分层方式的改变，老项目升级时踩的坑基本都来自这里。

也正因为刚发布不到一个月，外围生态当时是断裂的：预设要单独装，各家构建工具的接入层还没跟上，网上搜到的多数教程仍然是 5 的写法。所以这篇复盘里有些结论是”我们花了半天才确认这是工具本身还没跟上，不是我们配错了”，希望对正在升级的人有点参考价值。

分层之后，core 不再负责转译

Babel 5 的形态是”一个全能核心加一堆开关”：语法转换全部编在核心包里，配置用 optional、only、stage-0 这类全局档位去粗粒度地开。Babel 6 把它拆成了三层。最底下是 babel-core，只负责解析成 AST、遍历、再生成代码，外加一套插件 API；中间是插件，每一个语法转换都是一个独立的小包，箭头函数归箭头函数，解构归解构；最上面是 preset，而 preset 本身没有一行转换逻辑，它只是一份插件清单，装上一个 preset 等于一次性把它的插件列表拉进依赖树。

这个分层带来两个立刻能感觉到的变化。

第二，也是这次事故的根因：默认什么都不做。Babel 5 拿到源码会主动把 ES6 往下转，Babel 6 的 core 里没有 ES6 转换能力，.babelrc 里没写 preset、或者写了 preset 但对应的包没装，转译环节就是一场空——命令行照样退出码 0，文件照样生成，内容等于复制。

升级踩坑实录

产物”什么都没转”怎么定位

排查过程值得记一下。当时我先怀疑是缓存，删掉 lib 重跑，一样；再怀疑是浏览器没刷新，换无痕窗口，还是一样。最后做了个最笨的动作：把某个产物文件和它的源码逐字节对比，两者行数完全相同，只有文件头多了一行 "use strict"。这基本就把结论钉死了——转译没发生。回头看 .babelrc，presets: ["es2015"] 写得清清楚楚，但 node_modules 里根本没有 babel-preset-es2015 这个目录：6 把 preset 拆成了独立包，升级时我只装了 babel-core 和 babel-cli。补装之后一切正常。

这类失败模式最难受的地方在于工具不报错。后来的版本对找不到的 preset 会明确抛错，刚发布的那阵子没有这个待遇，只能靠”对比产物行数”这种土办法确认。我现在给团队定的规矩是：改完 Babel 配置，第一件事是在产物里搜一个 =>，搜得到就说明没转。

语法能转，新 API 转不出来

这是升级那周被问得最多的一个问题：既然装了 es2015 预设，为什么 Promise 在老浏览器里还是 undefined？因为转译器干的是改写语法，它不会凭空长出运行时。

要分开看两类东西。class、箭头函数、解构、模板字符串、默认参数这些属于纯语法形态，降级只需要在 AST 上做等价改写：class 变成构造函数加原型赋值，箭头函数变成 function 并在外层缓存 this，解构变成一串属性读取。改写产物只用到引擎早就支持的能力，运行时无需注入任何代码，所以这类转换可以按需挑插件，转完体积小、行为可预测。

Promise、Map、Set、WeakMap、Symbol、迭代器协议这些是另一类：它们是标准库里的对象和协议，源码文本上只是普通的标识符，转译器看不出你希望它变成什么。生成器更麻烦，function* 得被编译成一台显式状态机，运行时还需要配套的辅助函数才能跑。这些都得靠注入实现，也就是 polyfill。

这里有个必须写进团队约定的结论：polyfill 会动全局。整包 polyfill 的做法是往 window 上挂缺失的构造函数，甚至改内置对象的原型。应用这么做没问题，一个库如果把 polyfill 打进产物，等于替所有使用方决定了宿主环境该长什么样：轻则和页面里已有的另一份实现打架、版本互覆，重则把宿主原本更正确的原生实现覆盖掉。所以库的产物里不应该出现整包 polyfill。

体积这笔账与按需方案

应用可以直接引一次 babel-polyfill，在入口最前面加载即可。库需要另一套写法：用 babel-plugin-transform-runtime 配合运行时的 babel-runtime 包。这个插件做两件事，一是把转译产生的辅助函数从”每个文件内联一份”改成从 babel-runtime 引入，二是把 Promise、Map 这类新 API 的引用改写成指向 babel-runtime 内部的 core-js 模块，全程不碰全局。代价是产物多了一层依赖，运行时对象要从模块里取。

三条路子摆在一起看更清楚：

维度 babel-polyfill 整包 手工按需引 core-js transform-runtime + babel-runtime
全局污染 会改全局与内置原型 不改全局，只引需要的模块 不改全局，走模块引用
产物体积 明显过重，不管你用了几种 API 最省，但要人工核对 中等，helper 不再重复打包
与宿主已有实例复用 视加载顺序，可能互覆 可以只补真缺的 用自带实例，与宿主互不干扰
该用在哪 自己的应用入口 对体积敏感的页面 要发到 npm 或给别人集成的库

我们的处理是给每个包先问一句”谁消费它”：只进自己应用的，polyfill 整包一把梭；发给别人用的，一律 transform-runtime，并把 babel-runtime 写进 dependencies 而不是开发依赖——这一点我一开始放错了位置，导致使用方装完包立刻报找不到模块。

产物口径：source map、watch 与 babel-node

转译链路上线之后，调试链路得同步定口径，不然线上出了错根本对不回源码。source map 有两种给法：默认加 --source-maps 是外挂，产物目录里每个文件旁边多一个 .js.map；--source-maps inline 则把 map 以 base64 直接续在 JS 尾部。我们的选择是发布产物用外挂、本地调试用内联，理由是内联让文件胖一圈且 diff 全是噪声，外挂需要额外保证 .map 被部署上去、能被调试工具按相对路径找到。线上收集到的压缩堆栈如果对不回源码，多半是 .map 没跟着产物一起部署，这一步值得在部署脚本里检查两者成对。

--watch 的体验比 Grunt 那一代全量重跑好得多，配合把 lib 加进 .gitignore 基本就够用。babel-node 要说句反话：它方便，但它每次启动都全量转译、没有缓存，报错栈里还混着转译细节，我们只允许它在本地脚本里出现，进程管理器里的线上入口一律指向 lib 下的产物。

只转自己代码的那条边界

node_modules 默认不参与转译，命令行和 register 钩子都是这个行为。这在绝大多数情况下是对的：第三方包早该发布降级好的产物，把自己的构建时间花在别人已经编译过的代码上毫无意义。

但它会在一种情况下咬人——内部包图省事直接把 ES6 源码发上了 npm。我们有个工具包就是这么发的，接入之后浏览器立刻在旧内核上炸掉。两条修法：一是在配置里显式把那个包加进转译范围，命令行用 --only 指定路径，.babelrc 语境下用 include/ignore 控制插件到底作用在哪些文件上；二是推包自己去补构建脚本。我们最后走的是第二条，只把 --only 当成临时止血。

要提醒的是第一条的真实代价：一旦把第三方源码纳入转译，--watch 的首次全量会明显拖慢，增量重编译也会把那批文件的改动一并牵进来。这里我不给具体数字，各机器差别太大，但体感上是”启动后要等一会儿才能确认改动生效”那种级别。更麻烦的是 include/ignore 作用范围写错方向时，症状和 preset 没装很像——产物看着正常，老浏览器里照样报错，排查起来很费时间。边界这件事本该由包的作者定，不该让每个使用方各自兜。

浏览器目标怎么定

2015 年 12 月这个时间点的支持面并不乐观：Chrome 46 只覆盖了 ES6 的一小部分，Safari 9 和 iOS 9 的 Safari 是半套，Android 4.4 的 WebView 还停在 Chromium 33 一线、能不能升得看系统，IE 9 到 11 基本没有，Edge 也才刚出零星实现。清单里只要还留着这些目标，ES6 源码就必须整套降级。

结论很朴素：es2015 预设整包打开基本是必须的，别指望某个目标浏览器能免掉它；有 stage 提案语法再叠一个对应档位的预设。当时也没有工具能按目标支持面自动挑插件——那个思路要等到后来才落地——我们能做的全就把 es2015 整包挂上。整包开带来的冗余主要是重复注入的 helper 和模块壳，靠前面说的 transform-runtime 收一部分，剩下的当作过渡期成本接受。

收尾：库与应用两份清单

绕了一圈，落到可以直接抄的两份配置。

发给别人用的库：presets 只写 es2015，如果只需要模块降级就换成点名 transform-es2015-modules-commonjs 插件；plugins 加 transform-runtime；babel-runtime 放 dependencies，babel-core、babel-cli 放 devDependencies；绝不打包整包 polyfill；产物外挂 source map；main 指 lib，prepublish 里构建，files 只留 lib；单测用 mocha --require babel-register。

自己维护的应用：presets 写 es2015 加需要的 stage 预设；入口第一行加载 babel-polyfill；本地 --watch --source-maps inline，上线构建外挂 map；node_modules 保持不转，内部包发 ES6 源码的一律推它补构建；线上入口指到产物目录，babel-node 只留在本地脚本里。

Babel 6 这次升级没有让 ES6 变得能原生跑，它做的事是把”转哪些语法”的决定权交回给了配置者。代价是一整轮生态重装和几个不报错的坑，收获是配置终于能如实反映项目真实用到的语法——这份透明度，我认为值。
