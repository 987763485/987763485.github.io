页面模板引擎对比

这一年我经手的页面里，至少有三个列表页换过模板引擎：有的为了把渲染挪进构建流程，有的因为后端同事不再愿意多写一块视图，有的纯粹是老模板的缩进被改崩了。到 2015 年末，能同时在 Node 和浏览器跑的引擎已经多到必须摆上同一张台面才能选。本文不比谁更时髦，只把当时真在用的七个按同一组维度过一遍：artTemplate 3.x、Handlebars、doT.js、EJS 2.x、Jade、Mustache、Nunjucks。

口径先声明：性能一节不给倍数，只讲差距从哪来。Handlebars 的 4.0 刚放出不久，线上还锁在 3.x，例子全按 3.x 写。框架层 JSX 那条路本文不碰。

先把问题立住

选型前先问一句：HTML 到底谁生成。后端一把梭是路由拿到数据直接渲染整页返回，浏览器只负责展示；前端渲染是接口只吐 JSON，骨架在浏览器里拼。两条路对引擎的要求几乎相反。

服务端那条关心首屏、关心不依赖 JS 也能出内容、关心模板能不能继承一套后台骨架。客户端那条关心同一份数据能不能被多个片段复用、模板能不能编译成函数打进包里。还有第三种：Node 做同构渲染，它对两端共用这项要求最苛刻，也最能淘汰选手。

不管站哪条路，引擎都要同时解决三件事，缺一件就退化成字符串拼接。一是数据绑定，把值填进占位符并展开循环；二是片段复用，公共头尾、表格行只写一遍；三是转义，把用户文本变成安全的 HTML 片段——它最容易被忽略，也最容易变成事故单。

八个对比维度

把这一年踩过的坑归成八个维度，表格只列要看什么，判断放在正文里说。

维度 要看什么
编译时机 每次渲染重新解析，还是编译成函数复用
语法形态 逻辑写在模板里，还是全交给 JS
转义默认值 默认转义还是默认原样，原始输出用哪种记号
片段复用 只有 include，还是支持继承与宏
错误可读性 报文件名加行号，还是压缩过的匿名函数
运行时体积 浏览器要多背多少 KB 解释器
两端共用 同一份模板能否被两端都吃下
构建接入 有没有稳定的编译入口能批量跑

真正决定选择的是前两项。编译时机决定运行期要不要带解释器，也就决定体积与首帧成本；语法形态决定复杂度往哪压——压在模板里，半年后面对满屏指令；压在 JS 里，就要养一个专为渲染造的视图对象。剩下六项是这两项的下游：能编译成独立函数的，体积和构建接入好谈；只在服务端解释执行的，两端共用直接判死。错误可读性平时不看，出故障时才决定你能否半小时内定位到具体哪一行。

逐个点评七个选手

每家的语法都照当时装进项目的版本写，数据统一是一个数组，字段只有名字和一段可能带 HTML 的描述。

artTemplate 3.x

中文团队普及率最高的一家，靠两件事：压缩后的运行时确实小，{{ }} 比尖括号好认。它天生为浏览器准备，编译入口明确，容易塞进构建流程。

each 的参数写法在两三代之间动过，落笔前对着项目里那份文件看一遍；转义跟编译选项绑在一起，别赌默认值。短板是片段复用，include 只有最朴素的形态，跨页面继承骨架要靠构建脚本拼。

Handlebars

立场最鲜明的一家：模板里不许出现算术和分支，只能用块状指令和注册的 helper。限制换来的是模板能被非前端角色读懂，也敢让设计同学直接改。

强项是 partial 与 helper 生态，{{#each}} 自带 else 分支。代价是运行期要带整个运行时，precompile 的产物是一段描述而非独立函数。逻辑一出模板，视图对象就得提前把要不要显示算成布尔字段，这是 logic-less 路线共同要还的账。

doT.js

把模板编译成纯字符串拼接函数，快到常被当作其他引擎的对照基准。代价是语法对人不友好：插值要带 it. 前缀，控制结构就是裸的 JS 语句块。

它不做任何转义，插值就是原样拼接，安全全靠调用方自觉，XSS 一节再单独说。片段复用只能靠自定义模板加字符串替换。我的结论是只用在数据量大、模板由前端独占的场景；几十人改模板的后台项目，它的语法三个月就变成债务。

EJS 2.x

语法形态最像 JS 的一家，因为它基本就是把 JS 块塞进 HTML。对已经有服务端视图的老项目来说迁移成本最低，几乎不用换心智模型。

include 的写法在 2.x 几个小版本之间改过，我们升到 2.4 之后才统一成函数调用形式，这是老项目接入时最容易卡住的一处。浏览器端产物仍要带解释器；转义靠 <%= 与 <%- 区分，一个字符之差，评审看不出，线上就是问题。

Jade

缩进式语法的代表，名字要写清楚：这一版它就叫 Jade，包名、文档、社区讨论一律是这个写法。它天生是服务端视图引擎，模板比同结构的 HTML 短一半，标签名、属性括号、闭合标记都能省。

compileClient 是它在两端共用这项上的优势，产物是纯函数，浏览器不用带引擎。短板同样直接：缩进即语法，一份模板被三个人改过，空行和层级就成了最难查的 bug；属性写法离 HTML 太远，非前端角色要专门学。

Mustache

规范先行的一家：先有语言无关的模板规范，再有各语言实现。好处是同一份模板能在 Node、Java、PHP 之间原样搬；坏处是它压根没有逻辑，连循环里的索引都拿不到。

注意为了拿序号先做了一次 map，这就是复杂场景硬塞逻辑的真实样子：要格式化，要么预先算好塞进视图对象，要么写自定义 lambda。{{ }} 转义、三撇号原样这条规矩是它定的，其他家大多沿用。

Nunjucks

Jinja2 风格，服务端模板该有的东西基本给齐了：继承、块、宏、过滤器、循环元信息。

extends 与 macro 是这份名单里最强的两项，共用骨架页的后台站收益明显。默认转义加上 | safe 显式放行，是安全默认值做得最干净的一类。代价是浏览器端要带运行时，产物也不是独立函数。

性能这块要说实话

网上流传的跑分我一条都不引用：绝大多数测的是编译一次加渲染一次空对象，跟真实页面无关。差距来源只有两处。

第一处是解析字符串做几次。运行时解析是每次把源码交给引擎：读、切词、生成函数、执行。引擎若按模板 id 缓存了结果，第二次以后只剩执行；每帧传一个新字符串进去，就每帧付一遍编译的钱。预编译把这笔钱搬到构建期，而它省下的那笔，只在模板字符串被下发到浏览器时才存在。

第二处、也是更大的那一处不在引擎手里。拼出来的 HTML 塞进 innerHTML，浏览器要重新解析、建节点、算样式、排版，数据量一上去就把渲染耗时盖住了。换引擎用户感觉不到；把一次插两千行改成插二十行，用户立刻感觉得到。

所以大列表的正解是换策略而不是换引擎：不变更的表头与筛选区做成一次性片段缓存；变更的行按主键定位，只重渲染那一行；再往上是分批追加、滚到底再取。这些跟用哪家无关，也都得自己写增量逻辑。

XSS：默认转义不是保险箱

几乎每家都有两种输出记号：转义的插值，和原始输出的变体。Mustache 与 Handlebars 用三撇号，EJS 用横杠替等号，Jade 在等号前加感叹号，artTemplate 用 @，Nunjucks 靠 | safe 放行。一旦走原始输出，那段内容就被当作 HTML 塞进页面。

落地的规矩三条：默认走转义记号，原始输出要在评审里单独指出来源；确实要显示富文本就过白名单清洗，把允许的标签列出来；doT 这类完全不转义的，清洗放在数据进模板之前。

工程化：模板放哪、怎么编进包

客户端模板集中在 src/templates/，一个片段一个文件，文件名就是模板 id，不做第二层映射——出故障时要能从报错里的 id 直接找到文件。服务端视图另放一处，混在一起迟早有人把带 include 的服务端文件编进客户端包里。

坑在这里：把 toString() 的结果抄进产物，只在生成的函数不引用引擎内部辅助时成立。模板一旦用了片段包含或转义辅助，抄出来的函数在浏览器里就是未定义引用。后来我们让构建任务先把包含关系解开，再在产物里带上极小一份辅助实现；嫌麻烦就退回精简运行时那条路，Handlebars 的 precompile 加 runtime 正是这个思路。

刷新靠 watch 重生成模块，页面走不带缓存的地址；上线产物文件名带内容指纹，模板改一个字就换一个地址。别把模板 id 和指纹混进同一套命名，两者生命周期不同。

跟模块加载器的接口只说一句：模板编译成 define 模块后，业务模块把它当普通依赖声明，模板不再是运行时要额外请求的资源。加载器自身的配置细节，仓库里 2015 年 10 月那篇已经写完，不再重复。

一次迁移的复盘：同一套列表页从 EJS 到 artTemplate

动机不是性能榜，是两条具体的：一是页面要在浏览器里跑，EJS 的运行时体积当时不好接受；二是模板里的 <% %> 块被后端同事当 HTML 改过两次，缩进崩了。

代价按实际顺序记。改动量最大的是循环：JS 语句块换成指令后，能直接调用的数组方法没了，取值必须写成 {{item.name}}，forEach 那种回调写法无处安放。第二大头是 helper：原先在模板里直接调工具函数，新语法不能随手调，我们选了注册进引擎的全局上下文，代价是模板对环境的隐式依赖多了一层。第三块是构建脚本，读文件、编译、拼模块那层逻辑跟着引擎换了一遍。

回归测试花得比写代码多。include 的语义两边不一样，靠包含拼起来的公共块要重新组织；转义默认值也变了，原来原样输出的简介字段被编成实体字符，界面上冒出一堆 &amp;。这些都不在编译期报错，只能人眼看页面。教训是模板迁移必须预留全站回归时间，当成小改动必然超期。

推荐矩阵

场景 我此刻会选 一句话理由
后台管理 Nunjucks 继承与宏能把骨架成本压到最低
内容站 Jade 服务端整页渲染，不需要浏览器端运行时
组件化页面 artTemplate 3.x 编译产物小、构建接入直接
Node 服务端渲染 EJS 2.x 视图里就是 JS，迁移心智成本最低
跨语言复用模板 Mustache 有语言无关规范，能原样搬
模板由非前端改 Handlebars logic-less 加 partial，改不坏逻辑

这份矩阵基于这批项目的条件：模板最终编进包、跑在浏览器、由两三个前端维护。条件一变结论就得重推——模板要给 PHP 侧共用，artTemplate 立刻出局；首屏必须由服务端出，客户端那一列就不用看。

小结

比选谁更重要的是先把流程建起来：模板存放与 id 规则定死，编译挂进构建任务，转义记号写进评审清单。流程立住之后，换引擎是一次代价明确的迁移；立不住，换引擎就是一次没有终点的重写。
