Gulp 流式构建实战

我们项目组把 Grunt 换成 Gulp 是在一年前，真正开始把 Gulp 用顺，是这个月的事。

中间那段过渡期挺难受。最初我以为 Gulp 只是把冗长的 Gruntfile.js 换成短一点的 gulpfile.js，配置少了、插件名字好听了些，仅此而已。等把 Sass、图片压缩、JS 合并、版本注入都搬上同一条管道，问题开始成片冒出来：终端里任务明明跑完了，产物却是空的；watch 触发两次，第二次把第一次的输出覆盖掉；CI 上 dist 偶尔混进没压缩的文件，本地怎么都复现不出来。后来我才明白，这些坑都不是插件的 bug，而是我没搞懂这类工具到底在解决什么问题——管道里流动的不是文件，是内存里的对象；任务调度不是”排个数组按顺序跑”，而是”看谁返回了流、谁返回了 Promise”。

这篇不是入门教程，会写 gulp.src().pipe().dest() 的人不需要我教。我想记的是机制层面的东西：vinyl 对象到底长什么样、任务返回值的三种合法形态、插件内部 file / encoding / callback 的约定怎么用、gulp.watch 为什么会把整条管道重跑一遍，以及我们最后怎么把 CI 上那个飘忽的构建顺序摁住。版本口径先说清，免得有歧义：全文基于 Gulp 3.9.0、Node 4 LTS（这一条线是 2015 年 9 月放出的）、npm 2.x 与 3.x 混用的环境；Gulp 4 那时还在长期开发，正式版本没有发布，我们生产上不可能等它。

先说清楚为什么不是 Grunt：配置驱动为什么会输到代码驱动

我们组最早那套是 Grunt。模型很直白：一个 Gruntfile.js 里摆着 sass、concat、uglify 若干段配置，每段描述”输入哪些文件、输出到哪里、参数是什么”，任务之间靠 tasks: ['clean', 'sass', 'concat', 'uglify'] 这个数组排顺序。真跑起来时每个任务都老老实实从磁盘读、往磁盘写，中间产物落在 .tmp/ 一层层传下去。为了让配置不至于复制十几遍，还得学它的文件展开语法：

expand / cwd / dest / ext 这一组字段，就是 Grunt 在配置层里”手动实现了一遍文件对象”。它解决的问题是真的：少写重复。代价也很实在。第一，每步都要走一遍完整的读写往返，构建时长基本和中间产物数量成正比；第二，配置能表达的东西有限，逻辑一旦超出 DSL（比如”只有本次改动涉及模板时才重跑模板任务”），要么塞进 grunt.event，要么在 Gruntfile 里写函数拼配置对象，最后那份配置比代码还难读；第三，任务数组是全局串行，互不相关的任务也不能并行，除非额外引 concurrent。

Gulp 3.9 把主语换掉了：不是”任务读文件”，而是”文件流进任务”。一次 gulp.src 造出一个可读流，流里每一项是 vinyl 文件对象，内容已在内存里；后面每个 pipe 只对它做一次变换；只有最后的 gulp.dest 真正落盘。于是同一份 CSS 从编译到压缩再到打指纹，全程只在磁盘上出现一次。更重要的是表达方式：

取舍要摊开讲。Grunt 的配置驱动有个被低估的优点：那份配置是可以被工具读的，新人看 Gruntfile 就知道全部输入输出，CI 临时插任务改数组即可。Gulp 把流程写进代码之后，gulpfile 会长成一个小应用：有公共函数、有环境分支、有自己的 bug，而 bug 只能靠读代码发现。我们的纪律是两条——gulpfile 里不许出现业务逻辑，只允许”文件从哪来到哪去”和开关判断；超过 20 行的复用片段必须提成 gulp/ 下的独立模块。灵活性是有账单的，账单就是可读性得你自己维护。

vinyl：管道里流动的不是文件，是对象

Gulp 3.9 底层用 vinyl-fs 把磁盘文件包装成 vinyl 实例。第一次把它打印出来，我才知道自己以前一直猜错：

字段 类型 作用 我踩过的坑
cwd string 流的”当前工作目录”，gulp.src 相对路径的基准 一般不用动，默认 process.cwd()
base string 决定输出保留多少层目录 忘记设，dest 把所有文件平铺进同一个目录
path string 文件绝对路径 手工字符串截取，导致 relative 与 base 不一致
relative getter path 相对 base 的部分，dest 拼输出路径靠它 只改 path 不改 base，产物跑到 dist 外面
contents Buffer / Stream / null 文件内容 当字符串用；赋成 string 之后下游插件行为诡异
stat fs.Stats mtime、size，做增量判断的唯一依据 用它比对却忘了 Git 检出会把 mtime 全部刷新
history array path 的修改轨迹，gulp-rename 会往里追加 自定义插件改路径后想找回原名，靠它

三个判定方法是插件的分支入口：isNull()（目录，或 read: false 拿到的空壳）、isStream()（contents 是 Stream）、isBuffer()（默认，contents 是 Buffer）。gulp.src 的 buffer: false 看着美好，实际是个生态炸弹：一半插件只写了 Buffer 分支，收到流就报错或者静默把文件丢掉。我们只在处理几 MB 的图目录时试过一次，最后乖乖回到 Buffer 模式。

顺带把 Gulp 3.9 的四个动词钉住：src 造流、task 注册并必须返回这条流、dest 收尾写盘、watch 监听变更后重新触发任务。另有一条社区公认的插件纪律，理解了它就理解了整个生态：好的插件既不读盘也不写盘，它只接一个 vinyl、改一改、往下游走，gulp.dest 是唯一该写盘的地方。所以看到参数里接受 glob 的插件要警惕——它内部又开了一条流，任务完成时机就脱离了你的掌控。

错误二：改了内容却忘了重新构造文件对象

file.contents 是 Buffer，不是字符串。想改内容，只有一条正路：读出字符串、生成新 Buffer、整体赋回去。

第二种误写尤其阴险：gulp.dest 写出去的内容看着是对的，但任何在下游调用 file.contents.indexOf(...) 或做长度运算的插件都会拿到意外结果——字符串的 length 是字符数，Buffer 的 length 是字节数，我们那份带中文注释的 CSS 两者相差接近三分之一，压缩插件因此算错过切片位置。改路径同理：别手工截取字符串，交给 gulp-rename，它走 vinyl 自己的 setter，会把 history 和 relative 一起维护好；只改 path 的话 base 还停在原地，输出目录结构会歪。

第三种变体是”只读不改”：拼好了新字符串却忘了赋回 file.contents。这类症状一定是”改动没生效也没报错”，把 file.contents.length 打在管道中段，一眼就看出是哪一步没写回去。

source(...) 造出来的 vinyl，contents 是 Stream——这正是 isStream() 分支存在的现实原因，buffer() 之后才进入多数插件期待的形态。这两行胶水写反顺序，报错会是”file.contents.pipe is not a function“之类，完全指不到根因。

用 through2 自己写一个插件：file、enc、cb 各自的时机

官方插件覆盖不到的时候只能自己写。我们的真实需求很小：给每个 CSS 产物头部注入一行版本注释，方便线上出问题时在浏览器里直接看到是哪个版本。Gulp 3.9 生态里写插件的最低成本路径是 through2——它是 Node 原生 Transform 流的一层糖，帮你把”该在什么时机调用回调”这件事收敛成一个函数签名。

三个参数的时机务必钉死：

  • file 是当前 vinyl 对象。改它之前先想清楚要不要 file.clone()：同一条流被分叉（同时 dest 到两个目录）时，两个分支拿的是同一个引用，一侧改了另一侧就脏。我们的规矩是凡有副作用的插件，进入前先 clone。
  • enc 在 Buffer 模式下基本是摆设（值取决于版本与来源），别拿它当解码依据，要编码就显式写 toString('utf8')；流模式下它才有意义，但也仅对你 pipe 出的子流有效。
  • cb 是这一轮的”我处理完了”，三个去向直接决定文件命运：cb(null, file) 放行下游；cb(null) 等价于把这个文件过滤掉，这是所有”只处理某类文件”插件的正确写法，比你自己造空流干净得多；cb(err) 让整条流以错误结束。忘调 cb 最难查：3.9 没有超时机制，表现是任务永远不结束、终端光标停在那行、CI 上跑到超时才被杀。碰到卡死，先看最后一个日志是哪条管道的起点，再去那个插件的回调里补计数。

第二个函数（flush）在源头不再有文件之后调用一次，用来输出汇总或校验完整性，同样必须调 cb()，否则照样挂住。我们拿它统计本次通过的文件数与总字节，配合 --verbose 一眼看出”这次只重编 2 个”还是”又全量 40 个”。

gulp.watch 的粒度：默认整条管道重跑，宽 glob 等于全量编译

gulp.watch 的语义是”匹配到变更后重新执行指定任务”，注意是任务，不是”那一个文件”。这一句理解到位，优化方向就清楚了。

第一条写法的问题最直白：改一行 JS，sass 也被拉起来全量编译。Sass 入口有十几个时，每次保存等三四秒，节奏当场断。慢的根源在于任务里的 gulp.src 又是一整组 glob——它不知道哪个文件变了，只知道该读哪些文件。拆分只解决一半，另一半在 event 上：回调形态能拿到 { type, path }，type 取 add / change / unlink。

这段里有四个只有踩过才知道的点。其一，glob 与输出目录重叠会自燃：写一次触发一次变更、再触发一次编译，无限循环。规矩是 watch 的 glob 永远只覆盖源目录。其二，partial 依赖是个真窟窿：局部编译拿不到”哪些入口 import 了它”这张依赖表，所以上面把下划线开头的文件一律回落到全量。我们试过一版基于 sass 返回的 stats.included 建索引，能用，但嵌套 import 与带 media query 的 @import 边角太多，最后妥协成”改 partial 全量、改入口单编”——明知是权宜之计，可它比正确方案便宜一个数量级。其三，{ interval: 500, timeout: 0 } 是防”半个文件”的：编辑器保存常常先截断再写入，监听器收到两次事件，第一次读到空文件，产出零字节的 CSS 把好那份覆盖掉，症状是”保存后偶尔空白，再存一次就好了”。其四，watch 回调里 return 流没有任何意义：运行器不看这里的返回值，完成时机与错误传播都脱离掌控，所以 watch 链路上的管道必须自带错误处理（见下一节）。gulp.start('name') 是 3.9 里唯一能”从回调内部触发任务”的口子，不受依赖图约束、也不保证顺序，用之前要清楚自己在打洞。

watch 里报一次错，任务就静默失效：plumber 与 PluginError

先看一段没有任何错误处理的管道：

写错一个括号、终端打一堆红字、进程直接退，这其实是最理想的情形——至少你知道出事了。真实情形是：第一次报错之后进程没退，watch 还挂在那里，光标停着，但你改任何文件都不再触发编译。没有报错、没有日志、没有退出码。一个同事以为是 Gulp 卡死，把 Node 重装了一遍。

机制在流的错误传播上：管道里任何一环 emit('error') 而没人接住，Stream 会拆掉自己的可写端、任务以失败告终；Gulp 3.9 的运行器在 watch 场景下不退出进程，但那条被拆掉的管道永远不会恢复。于是任务从这一刻起是死的，而 gulp.watch 还活着——“看起来还在监听，其实什么都不做”。

gulp-plumber 补的就是这个洞：把下游 error 事件截下来交给你的处理函数，然后让这条管道正常结束而不是拆链，下一次触发仍是干净的管道：

放置位置有两种流派。放在 src 之后第一段最省事，但只兜得住”从这一段往后”的错误，而且第一个报错的插件之后，后续插件本轮就拿不到这个文件了（我们 emit('end')）；每个易出错的插件前各挂一段 plumber，好处是能精细控制”这一步出错降级成什么样”，代价是链条读不动。结论：常规任务用第一种，watch 链路上的任务一律用第二种。

errorHandler 里 this 指向当前流，emit('end') 与 emit('error', err) 的差别就是”这一轮到此为止”和”把错误继续往上扔”。要说明白：plumber 吞掉了错误，它保的是开发期的连续性。生产构建里如果只用 plumber 又忘了把错误码交给最终的 done，CI 会因为构建成功而通过——我们后来在生产链路的 onError 里加了一句 process.exitCode = 1，才算把这个洞堵上。

错误栈丢失这件事要单独说。插件跑在异步流里，一个裸 new Error() 的 stack 只记录从构造函数到当前同步帧的那几层，真实调用位置（哪个文件、哪个任务、哪条 glob）早就掉出栈外了。终端里那种”Error 后面跟着 25 帧 Node 内部函数”就是这么来的——栈是完整的，信息是空的；gulp --stack 打开后帧更多，但大多是运行器和 Stream 实现的内部帧，对定位毫无帮助。真正有用的从来是 fileName 与 message 这一对，所以自定义插件必须把 file.path 塞进错误对象，不带就是让用户去猜。

排查”watch 静默失效”的过程记下来给后来人：先在 gulp.watch 的回调形态里加一行 gutil.log('触发：' + event.path)，确认监听层还活着；活着但产物不动，说明任务链断了，往管道中段插一个 .pipe(through2(function (f, e, cb) { gutil.log('过了：' + f.relative); cb(null, f); }))，看它停在哪一段，停住那段前面的插件就是元凶。这比读源码快得多，因为错误分支往往藏在第三方依赖里。

gulp-sass 2.x 与 node-sass 3.x：当年的能力边界

样式这块我们用的是 gulp-sass 2.x 配 node-sass 3.x。这一组的速度确实比 Ruby Sass 一代好太多，但边界要认清楚。

语法面只到 LibSass 那一档。 node-sass 是 LibSass 的 Node 绑定，能力面就是它当时的实现：@import、@extend、%placeholder、@each / @if / @function 这套 Sass 3.4 时代的语法都在，模块化那套新写法（把依赖声明成命名空间的 @use / @forward）当时还不存在。目录组织只有一条能落地：下划线前缀区分 partial，入口文件收敛 @import 顺序。跨目录复用变量靠 includePaths：

sass.logError 的行为正好是 plumber 的反面：格式化打到控制台、结束这一条管道、不抛给运行器。watch 场景里用它最省事，不炸链也不用装额外插件；但它把错误码咽掉了，生产链路必须换成会真正失败的写法，否则脚本 exit 0 而产物里少两个 CSS 文件。

没有增量编译。 这是我最不满意的一点。gulp-sass 每拿到一个入口，就把整棵 @import 依赖树重新解析、重新编译，既不认”上次编过什么”，也不写缓存。入口有二三十个、每个拖七八十个 partial 时，一次全量几秒起步，而 watch 默认又恰恰是全量——上一节那些”只编改动入口”的权宜之计，本质是在应用层替它补一个不存在的增量能力。缓解手段我们用了三种：入口拆细（宁可多个小 CSS，别一个大入口拖全站）、把几乎不变的库样式提前编成纯 CSS 直接 concat 进来、把 includePaths 收紧（一堆宽路径会让每次解析多做无谓的目录查找）。

二进制绑定是环境类事故的主要来源。 node-sass 装的时候要先找一个预编译的 .node 绑定，找不到就退回 node-gyp 现场编译。于是三种情况会在团队里反复出现：

对应的处置：升级 Node 之后（比如我们从 0.12 切到当年 9 月发布的 Node 4 LTS 那条线）必须 rm -rf node_modules && npm install，或更轻一点 npm rebuild node-sass；内网机器把预编译包放镜像站；package.json 里用 ~ 锁住 node-sass，别让它跟着 gulp-sass 的小版本飘。npm 3 的扁平化还有个连带效应：node-sass 被提到顶层后，某些插件按相对路径找绑定的逻辑会失败，同一仓库在两台机器上装出两种目录树——这就是”我这儿能跑”的标准成因。我们的办法土得可以：npm ls --depth=0 把目录树贴进 issue，比互相猜环境快得多。同期比较过的另一条路是 gulp-postcss 5.x 配 Autoprefixer 6.x，它只处理编译后的 CSS、不碰 Sass 语法；我们把”加前缀”这件事从 Sass 链路里剥出来交给它，浏览器目标就收敛成一份 browserslist 配置。

开发闭环：browser-sync 2.x 的 proxy 与 server 两种姿势

选型只有一句话：改的是纯前端产物就 server，页面由后端渲染就 proxy。server 自己起静态服务，baseDir 加 routes 就能把 node_modules 挂成一个 URL 前缀，不用碰后端，缺点是接口全靠 middleware 或假数据顶。proxy 把已有站点挂上来，会话、Cookie、路由全是真的，代价是它会改写 HTML 注入客户端脚本，直接返回 JSON 或长轮询的接口偶尔被波及；多端联调时滚动同步与点击同步还会让后端冒出一堆重复请求，我们一般先关掉。

两个必须记住的差别：CSS 走 stream，是当样式规则替换进 DOM，页面不重载、滚动位置和 JS 状态都保留，这是它最大的体验收益；JS 与 HTML 只能 browserSync.reload，而 reload 必须在任务结束之后调（.on('end', browserSync.reload)），放在函数开头就等于刷新了一次空产物。

实时通道这块也有账要还：2.x 靠 socket.io 那条长连接下发指令，症状因此很特别——改了 CSS 页面不动、reload 也没反应，服务本身却是活的。排查先看 Network 里那条 socket 握手成没成功，公司代理与端口防火墙会让它退化成轮询甚至直接失败；其次是多站点并行时 port / ui.port 撞车。2.x 起有了 create() 才谈得上一个进程跑多个实例，早先全局单实例连两个站点都开不了。

产物策略：sourcemap 放哪，指纹怎么打

sourcemaps.write() 的参数有无决定两件事，不是”要不要 map”，而是”map 以什么形态存在”：

内联的长处是没有额外请求、本地断点直接可用、拷来拷去不会丢；短处是体积明显涨（map 常常比 CSS 本体还大），而且”未压缩前的源码”就明晃晃挂在产物里。我们的分工是：开发链路一律内联，发布链路写独立文件且 .map 不上传公开 CDN，只留给错误上报平台做还原——sourceMappingURL 指向一个能公开访问的 map，等于把未混淆源码发出去，JS 侧尤其明显。

顺序上有三条铁律：sourcemaps.init() 必须在所有会改写内容的插件之前；上游 map 是别人产出的（比如 browserify 那条分支）要加 { loadMaps: true } 读进来接着往下叠；sourcemaps.write() 必须紧邻 gulp.dest，写在中间会让后面所有插件拿不到 map。

指纹走 Gulp 生态自己的 gulp-rev / gulp-rev-collector，思路是”内容 hash 进文件名 + 一张 manifest + 替换引用”：

四个坑挨着说。replaceReved: true 不是可选项：不加它，第二次构建会拿着已被替换过的文件名再 rev 一遍，产物里出现双重 hash 或干脆找不到 key，构建就不幂等。rev() 之后原文件不会被删除，旧的 app.js 和新的 app.a1b2c3.js 并存，要么前面 clean 干净，要么用 gulp-filter 只让带 hash 的进最终目录。manifest 的 key 是相对 base 的路径，base 设错就整表对不上、HTML 里一条引用都不会被换——和第一节讲 base 是同一根因。最后回到那个版本注释插件：hash 从内容算出来，注释里带构建时间戳就是”每次内容都变、每次全量失效”，换成短提交号之后测试环境的缓存命中率才真正起来；而取短提交号在 CI 上也不稳（浅克隆时 git rev-parse 会失败），要留一个读 CI 环境变量的兜底。

踩坑复盘：CI 上混进 dist 的未压缩文件

有一次发布包在测试环境炸了：dist/assets/ 里同时存在未压缩、带 console 的 app.js 和 app.7f3c1a.js。本地复跑十遍都正常，CI 上偶发。第一反应是插件有问题，第二反应是缓存脏了，都错。真正的原因在任务图里：

Gulp 3.9 里数组依赖的语义是”这几个依赖并发跑完，主任务才开始”，官方从没承诺顺序。本地机器快、文件少、del 一次几十毫秒，冲突窗口碰不上；CI 那台机器核数不同、node_modules 冷装、磁盘还慢，copy 就经常赶在 clean 删完之前往 dist 里写，把刚删掉的目录又建出来。更糟的是 scripts 里有一个我忘了 return 的子步骤（第一节那种”提前完成”），于是 rev 起跑时读到的是上一轮残留的未压缩 app.js，给它算了 hash、又写进 HTML——未压缩文件不是这次构建产的，是上一次留下的，这一点当时怎么都想不通。手工 gulp.start 则完全没有失败传播：rev-html 出错，主任务照样报 finished。

修复分三步走，顺序很重要：

  1. 全量补 return。给每个任务套上前面那个 timed 包装，把”没返回流”变成日志里看得见的一行。这一步之后，dist 里”偶尔少文件”的问题一起消失了。
  2. 把有严格先后的链路显式串行。当时 Gulp 4 还在长期开发、正式版本没有发布，没有可用的原生顺序编排，社区标准做法就是 run-sequence 1.x：

它内部还是靠 gulp.start，但把顺序、完成回调和提前终止管住了。别把它当万能药：run-sequence 嵌在任务里、任务里又调 run-sequence，我们做出过一个三层嵌套，出错时日志完全看不出跑到哪层，最后规定只允许在入口任务里调一次。

  1. 把”临时”和”交付”彻底分开：中间产物全部落 .tmp/，只有最后一个 publish 任务从 .tmp 写进 dist，clean 只删 .tmp。这样即便顺序漂移，也不可能把未压缩的旧文件留在 dist 里——进 dist 的唯一路径就是那个已经过了 rev 的任务。

验收手段也跟着补上：CI 脚本里加一条 find dist -name '*.js' ! -name '*.min.js' | head 之类的粗查，再对比产物文件数与 gzip 后体积，异常直接失败。”相信任务顺序”这件事，最终得靠产物检查兜底，不能靠调度的正确性。

flowchart TD
    A[dist 入口任务] --> B[clean 删 .tmp]
    B --> C1[copy 静态资源]
    B --> C2[scripts 转译压缩]
    B --> C3[sass 编译]
    C1 --> D[rev-assets 打指纹]
    C2 --> D
    C3 --> D
    D --> E[rev-html 替换引用]
    E --> F[publish 从 .tmp 写进 dist]
    F --> G[产物检查 文件数与体积]

Gulp 3.9 任务组织的取舍

组织方式 顺序保证 失败传播 可调试性 我们的用法
task(name, [deps]) 依赖并发、顺序不定 依赖失败则主任务不跑；但”提前完成”能骗过它 差，日志看不出谁先跑 彼此独立的准备任务
单一长管道 强，流内天然串行 error 沿链上冒，一处断全链断 好，插一段日志即可 常规转换，尽量把一步拆成一条链
run-sequence 1.x 强，且允许局部并行 中间失败即停，错误只回给回调 中，嵌套深了难读 只在入口任务用一次
gulp.start 手工触发 无 完全丢失 差 只留给 watch 回调
巨型单任务全塞 强 一处错全断，难定位 差 不推荐

小结

绕一大圈，Gulp 3.9 教我的其实只有三条，而且都能翻译成纪律。第一，任务的完成时机只由返回值决定：每个 gulp.task 都必须 return，做不到就显式调 done；这条立不住，所有”偶发”问题都会反复回来。第二，管道里流通的是 vinyl 对象不是文件：改内容走 Buffer，改路径走它提供的 setter，跨生态用 source stream 适配，而 dest 是唯一该写盘的地方。第三，并行是默认、串行是特例：3.9 不提供顺序保证，当年的答案就是 run-sequence 加”中间目录与交付目录分离”，最后再靠产物检查兜底。对我们手上这个项目来说，2015 年冬天的现实就是 Gulp 3.9、Node 4、插件自己写、顺序自己管。把这几件事做扎实，构建脚本才算从”能跑”进到”敢在 CI 上跑”。
