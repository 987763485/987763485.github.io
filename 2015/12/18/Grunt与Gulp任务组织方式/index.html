Grunt 与 Gulp 任务组织方式

去年这个时候，我们组的 Gruntfile.js 有五百二十行。它不是一天长这么高的：新加一条业务线就多一段 copy，换一次资源目录就多一个 target，谁都不愿动别人那部分，文件便像年轮一样往外长。年底改版出了事——我调 sass 输出路径，跟同事改 uglify 的提交撞在同一个 initConfig 块里，解冲突时我手工把两个 files 数组的元素顺序顺了一遍。CI 是绿的，测试环境上去样式少了一半，查两小时才发现症结不在配置内容，而在数组里谁先谁后。

从那次起我不再把构建脚本当配置，而是当代码：要有模块划分、命名约定、别人看得懂的执行顺序。两个工具的文档都只讲怎么写第一个任务，没讲二十个任务、四个人同时改时该怎么办。这篇只谈组织；入门部分《Grunt 构建工具入门与实践》已经写过，不重复。

长到四百行之后会出现的三个症状

第一个是合并冲突。任务定义和编排混在同一段代码里，两人各加一条流水线，改动十有八九落在文件末尾那几行，Git 判断不了同一行上谁对。我解过的冲突里超过一半，双方改的本毫不相干，只因物理上挨着。

第二个是改名牵一发动全身。任务名在 Grunt 里是数组元素，在 Gulp 里散在 watch 分组和别人的依赖列表中，没有东西帮你查一致性。build:admin 改成 build:backend，漏掉一处引用不报错，只让某个监听从此静默失效。

第三个是新人看不懂执行顺序。书写顺序跟执行顺序无关：Grunt 要翻 default 数组，Gulp 要看依赖声明，两边都得在脑子里做一次拓扑排序才拼得出流程。我接手过一个六百行的 gulpfile，作者已离职，deps、run-sequence 和嵌在任务里的 gulp.start 三种编排并存，我花三天才敢确认谁先谁后。

三个症状同一个根源：构建脚本被当成一份配置在写，而不是当成一个模块在维护。

Grunt 侧：让 Gruntfile 只剩骨架

配置按插件分文件

Grunt 的 initConfig 可以多次调用，每次只往全局配置上合并你写了的那些键，所以配置完全能拆出去——一个插件一个文件，导出一个对象，主文件负责拼：

任务下沉到 tasks 目录

有个细节值得写成约定：子文件里不要注册 default。loadTasks 与 initConfig 谁先执行，取决于主文件里那两行的书写顺序，同名任务后注册的会静默覆盖先注册的，表现是 default 队列莫名少了两步。所以规则定为：子文件只注册带自己前缀的任务，编排全在主文件。

自动装载最终要写死清单

load-grunt-tasks 和 matchdep 扫 devDependencies，把匹配 grunt-* 的包全部 loadNpmTasks 一遍。省事是真省事，代价却在协作里显形：一个从没被引用的插件被谁顺手装进来，它的任务就进了构建；~ 范围内的自动升级还会让同一个仓库在不同时间装出不同插件集合，构建不可复现，而没人怀疑到装载机制上。

所以我们退回显式清单：三人以下的小项目用 load-grunt-tasks，超过就在主文件里把插件一行行写出来并收紧版本范围，换来一份可 review 的能力白名单。

target 只用三个后缀

多目标机制本身不难，难的是命名。出现 build2、build-new 就说明没有约定。我们只用三个词，含义写死在 README 里：

target 后缀 含义 产物落点 谁消费
:dev 可调试，不压缩，带 sourceMap .tmp/ 本地 watch
:debug 与 dev 同，但保留日志与测试钩子 .tmp/ 联调环境
:dist 压缩、去注释、注入 banner dist/ CI 与发布

规则是 target 只描述产物形态，不描述业务线。concat:admin、concat:portal 这类命名一旦多起来，列表就爆炸；把业务线差异收进 glob 或常量，target 数量才稳得住。

Gulp 侧：函数是复用单元，任务只是入口

不要把每条管道都注册成任务

gulp.task 在 3.9 这一代混了两个用途：它既注册一个命令行能调的名字，也被当成”定义一段逻辑”。它没有复用能力——写好一条 sass 到 css 的管道，另一条任务想在中间多插一步，只能整段 src().pipe() 复制再改，改的时候必漏。我的做法是把可复用管道写成普通函数，任务只负责把它接到具名入口上：

判断标准定得很机械：可能出现”两条任务同一段处理、参数不同”的，抽进 lib/ 做函数；只有一条任务用的胶水留在 gulpfile。这条线画清之后，gulpfile 长期压在一百二十行以内。

deps 只保证顺序，不保证完成时机

gulp.task(name, deps, fn) 的第二个参数保证的是”依赖任务已经启动”，不是”它的活已经干完”。文档这点写得含糊，团队里几乎每人要踩一次才记住：任务函数里有异步却没把流返回出去，Gulp 就认为它完成了，下一条立刻开跑。

于是”任务必须 return 流”成了纪律，写进 review 清单当硬性检查项：末尾有 gulp.dest 的必须挂 return，不返回流的异步操作要么显式 this.emit('end')，要么改成返回流。我们还在 lib/ 里加了个极小的包装兜住忘写 return 的情况，它只能警告不能救回，真正的保障仍是 review，但日志里多一行显性噪音，解释一遍纪律就传开了。

run-sequence 的代价

需要严格串行时，3.9 的通用解法是 run-sequence 1.x：

数组表示组内并行、组间串行，这是当时唯一能把”阶段”表达清楚的写法。代价有三条。编排从声明退化成回调，cb 忘了传进程就不退出，watch 里表现为改一次文件卡十秒。错误传播不直观，中间某条失败时后面的组跑不跑，取决于 1.x 的具体小版本，我们的对策是不依赖它的中止行为，而在每条任务末尾自己校验、失败就 process.exit(1)。并行度也控不了，组内同时跑多少条管道没人管。

Gulp 4 会把阶段编排做成任务系统的一部分，但截至写这篇它还挂在长期开发分支上，不知道什么时候能稳定。所以 2015 年末做生产决定时 run-sequence 仍是唯一选项。

中间产物策略反过来决定任务粒度

Grunt 每一步都写磁盘，Gulp 中间不落盘。这个差异看着是实现细节，实际它规定了任务该切多细。

Grunt 侧可以切得很碎，碎有碎的价值：.tmp/a.js 存在，出问题时我直接打开它看，一眼判断是上游拼错了还是下游压坏了。代价是中间文件越来越多，必须有人清。约定是 .tmp/ 永不提交进仓库、CI 每次从 clean 起建、本地产物异常时第一步永远是先 clean 再重跑。

Gulp 侧正好相反：管道越长，中间状态越不可见。五步 pipe 之后产物不对，你没法打开某一步的结果，因为它从来没存在过。所以粒度要往小切，切法不是拆任务而是拆管道——两三步之后 gulp.dest 落一次盘，把不可见的流变成可见的文件。这在 Gulp 圈子里不算政治正确，但四个人维护的项目，可诊断性比构建快两秒重要。lib/ 里的函数因此要能控制是否中途落盘。

六个入口任务，其余都是内部的

除这六个之外一律加下划线前缀，比如 _sass:dist、_manifest:build。前缀不是装饰，它是给 grunt --help 和给 reviewer 的信号：列出可用任务时一眼能分辨哪些是给人敲的、哪些只是编排的零件。下划线任务当然也能调，但那属于明知故犯，出了问题自己负责。

再配一张权限表，放在 README 的构建章节：

入口 CI 允许调用 允许写 dist 允许驻留进程 负责人
build 是 否 否 全员
dist 仅发布流水线 是 否 发布值日
dev 否 否 是 个人
lint 是 否 否 全员
test 是 否 否 全员
clean 是 否 否 全员

“允许写 dist”那一列救过我们一次：有人把一条写 dist 的内部任务挂到 build 上，CI 跑完，dist 里躺着没压缩的产物，半成品直接上了线。此后往 build 加任务都得先回答：它会不会碰 dist。

环境差异往哪里注入

一个脚本要伺候本地、联调、预发、生产四套环境，注入方式只有三种。分工是：路径、域名、常量集中进 config/env.js，由主文件读进来摊到配置顶层供模板引用；单次的临时分支用 grunt.option，也就是 grunt dist --env=staging 这种写法，不改任何文件就能换条链路；需要跨进程传给下游 shell 的条件才用 process.env.NODE_ENV。三条各管一段，不许叠起来判断同一个条件。

Gulp 侧没有 grunt.option 这种内置开关，常见做法是引 yargs 解析命令行，再与 gulp-util 的 gutil.env 合流，后者本身也只是 process.argv 的便捷读取。无论哪种，规则一样：入口只允许一个，配置里不许出现”先看参数、再看环境变量、最后看默认值”的三级回退链，那种代码半年后没人记得哪一级生效。

一次发布缺文件的复盘

十一月那次发布，dist 少了三个静态目录。改动只有两行，diff 看上去人畜无害：有人把发布链路里的 run-sequence('clean', 'copy', ...) 换成了 gulp.start('clean', 'copy', ...)，理由是这两个任务互不相关，没必要串行。

问题在于这两件事有交集。clean 删的是整个 dist，copy 写的是 dist 的子目录，两条管道各自异步跑，谁先落地看磁盘心情。那次是 copy 先写完、clean 后把整个目录端掉。本地跑十次有九次是好的，因为本地数据量小、copy 起步慢半拍，这恰好是它最阴的地方。

flowchart TD
    A[dist 入口] --> B[clean 删除 dist]
    A --> C[copy 写入 dist 子目录]
    B --> D[产物缺三个目录]
    C --> D
    D --> E[发布脚本报文件不存在]

这类 bug 难查的根源是它没有栈。报错发生在下游发布脚本，它只说”文件不存在”，你顺着这条线去查复制逻辑、查 glob、查权限，永远查不到上游那条本该排在前面的任务。语法错误在写下的那一刻就暴露，顺序错误要等特定负载才现形。

修的时候 Gulp 侧退回 run-sequence，把 clean 单独提到第一组；Grunt 侧那条链路本靠 registerTask 的数组顺序保证，但有人在内部任务里用 grunt.task.run 拉起了别的任务，绕过了编排，于是补一条规则：内部任务不得自行拉起其他任务，顺序只在入口那一层声明。两处修法本质相同——把并发从”看起来安全”变成”确实没有交集”。

多人协作的三条硬约束

工具层面的拆分只解决一半，另一半靠约定，而约定必须是能被检查的那种。

第一，新增或改名任务必须同时改 README 的任务表，同一个 PR 里没动表格的构建脚本变更不予合并。这张表是唯一一份入口清单。

第二，禁止在 dev 与 watch 链路里做发布动作。改完顺手推上去确实省事，但 watch 是驻留进程，随时可能被触发，把不可复现的产物带进 dist。落成的检查项是：凡写 dist 的管道都不许出现在 dev 的依赖里。

第三，构建脚本的 review 只看五件事，别在语法风格上耗时间：这条任务 return 流了吗；它写的是 .tmp 还是 dist；target 后缀在不在那三个词里；有没有偷偷 loadNpmTasks 或 require 新依赖；有没有拉起别的任务。五条写进 review 模板，逐条打勾。

顺便一句，当时也有团队只用 npm scripts 串这些活，我试过一个星期就退回来了——不是它不行，是插件生态那时还在 Grunt 与 Gulp 这边，好几个步骤找不到独立的命令行入口。

落到目录结构

两个工具各给一份当时真在跑的结构，字段省略，只留骨架。

两份结构的共同点是四条：入口文件薄、常量集中、可复用单元是普通模块、内部产物与对外产物分目录。工具换了，这四条不变。

小结

这一年最大的转变，是我不再问”这个需求 Grunt 有没有插件”，而是问”它该放进哪一层”。拆文件、收入口、定后缀、写权限表，没有一项让构建变快；换来的是下一个人改脚本时不必花三天读懂前任的编排思路。任务组织的标准不是优雅，是可交接。
