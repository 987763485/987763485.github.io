前端错误监控与异常上报

这篇文章要讲的不是”接一个错误统计平台”，而是把整条链路从零搭一遍：浏览器里到底能采集到什么、为什么很多错误天生就采不全、上报通道怎么选、服务端怎么接、落库之后怎么去重和反解。我们线上那套最早只是几行 window.onerror 加一个日志接口，后来被几个查不动的事故逼着长成现在的样子，这里记录设计与取舍。

先说清楚动机。服务端有日志、有告警，出了 500 能顺着堆栈查下去；而前端挂了是无声的——页面白了一块、按钮点了没反应，用户不会来给你提工单，他只会被动流失。没有上报之前，我们排查线上 JS 报错全靠运营同学口头转述和一句”点不动”，效率低得离谱。错误监控本质上就是给前端补一套堆栈日志。既然要自己搭，就要先把当时浏览器能给我们的原料摸清楚。

窗口端采集：我们到底能拿到什么

window.onerror 的真实签名与返回值

window.onerror 的完整签名是五个参数：message、script、lineno、colno、error。前三个在当时的浏览器上表现稳定；列号在老内核上不是缺失就是偏移一位；错误对象则在绝大多数主流浏览器里拿不到——只有少数较新的 Blink/WebKit 内核开始传它，IE 全线不提供。这意味着：别指望白拿堆栈，能依赖的只有 message 和行号。

fishStackFromMessage 是个丑陋但必要的活。部分内核当年会把函数调用轨迹拼在 message 里，我们用几条正则从文本里捞函数名和行号，当作 error 对象缺席时的补偿。返回 false 表示不拦截浏览器默认的错误打印，不能让采集把异常吞进黑洞。

IE 上还有第二层差异：运行时异常只触发属性赋值式的 window.onerror，用 window.addEventListener('error') 注册的监听在 IE 上只会被资源加载失败触发，Firefox 与 Chrome 则两边都触发。所以我们把分工固定下来——运行时错误只走属性赋值，资源加载只走捕获阶段监听，免得同一条错误被计两次。

跨域脚本只会留下 “Script error.”

业务脚本放 CDN 之后，大部分 JS 都是跨域加载的。浏览器安全策略对这类脚本做了特殊处理：如果脚本在获取时没有拿到跨域读取授权，它内部抛出的任何异常到不了完整信息，window.onerror 只能收到一条毫无信息量的 Script error.，行列号全是 0，堆栈彻底消失。我们刚上线采集时，面板里清一色是这句话，完全无从查起。

解法要两端配合：页面里的 script 标签加上 crossorigin="anonymous" 属性，脚本域名侧必须响应 Access-Control-Allow-Origin 头。缺任何一端，浏览器都按不透明跨域加载处理，信息照样降级。

两个细节值得单独强调。动态插入的脚本必须在赋值 src 之前设置 crossOrigin，请求一旦按默认策略发出去，事后补属性就晚了。另外如果 CDN 还没配 CORS 头就提前加了 crossorigin，浏览器会按 CORS 失败直接中断下载，页面当场缺脚本，所以务必先确认响应头，再逐页放量。老 IE 对 crossorigin 属性基本无感，这部分用户仍然只看得到 Script error.，这个洞只能在矩阵里如实记下来。

window.onerror 只管”没人接、一路冒到全局”的异常。业务代码自己 try 掉的、框架内部消化掉的那部分永远不会上报，采集面必须手动扩。

上报通道：三条路的取舍

数据在本地攒够一批就要发出去，当时能选的通道各有硬伤。

用得最广的是 Image 对象发 GET 打点：参数拼成查询串，赋值 src 的瞬间请求就发出去。它天然跨域、不走 CORS、不关心响应，发完即忘。payload 受 URL 长度限制，过一层代理和服务器就被截；收不到回执，成功与否只能靠服务端对账。

XHR 能 POST 更长的体，但跨域带凭证要开 withCredentials，一旦开启，接收端就不能再用通配的头，CORS 配置麻烦一圈；更麻烦的是页面正在关闭时发出的 XHR 会被浏览器取消，偏偏”离开页面那一刻炸的错误”最值钱。

navigator.sendBeacon 当时刚出现在少数浏览器里，卖点正是页面卸载时交给浏览器尽力送达，可覆盖面撑不起主力位，只能当特征检测后的加分项。分发逻辑写得很朴素：

通道 payload 长度 跨域 页面卸载时 能否读回执 当时可用性
Image GET 受 URL 上限约束 天然可用 未必发得完 否 全量
XHR GET/POST POST 不受 URL 限制 需配 CORS 易被取消 能 全量
sendBeacon 中等 看端点配置 尽力送达 否 仅少数浏览器

服务端：把上报请出业务主集群

为什么必须独立端点

上报流量的特点是量大、突发性强、纯写入几乎无读取。把它挂进业务主集群，一旦某个 bug 爆发，上报会在几分钟内挤满连接队列，把业务本身拖垮——监控反手把线上带进坟场，比漏报严重得多。所以端点必须独立：低配机器甚至一层 nginx 就够，只回空响应、只写日志，分析全部离线做。

数据侧治理：去重、限流与隐私

错误指纹

去重靠指纹，指纹的前提是归一化：message 里带着 id、地址、引号内容这类每次都变的量，直接哈希会把同一个错误裂成成百上千个”新错误”。做法是先把数字、十六进制指针、引号串替换成占位符，再拼上行列号一起哈希：

行列号进指纹时要留一分心：各家内核的行列基准并不完全一致，同一个错误在两种浏览器上报出来的行号可能差一。聚类时允许按 message 加文件先合流，行列只作参考位，宁可多合也不错合到没法回溯。

采样与抑制

限流分三层。客户端维护会话内的指纹计数，同一指纹短时间只发首条，累计数随下一次上报捎带；页面级按 UA 与路径哈希分桶，大流量页面只放固定比例；服务端再按滑动窗口合并一次。三层各管各的：第一层省带宽，第二层保存储，第三层兜住统计口径。

隐私与长度上限

上报参数里永远不许出现用户输入。表单内容、凭证、带身份信息的地址，一旦进日志就是泄露事故，长文本还会把上报撑爆。我们只允许字段白名单过线：页面路径、脚本文件、行列号、UA、发版号。message 截到几百个字符为止。发版号尤其要强调——不知道这条报错来自哪一批构建，反解和二分定位全是猜。

source map：反解发生在服务端

构建产物经过压缩合并，上报里的行列号指向那个单行文件，本身没有可读性。正确的分工是：上报只带压缩后的文件位置，文件用内容哈希命名；日志落库之后在服务端离线反解，把行列映射回源码。

哈希命名很重要：同一 URL 的产物随发版更换内容，反解必须按构建批次取对应 map，而不是拿最新的去解旧报错，否则解出来全是张冠李戴。所以归档动作要在发布时完成。我们当时流水线仍以 gulp 为主（webpack 在 2015 年才开始被团队接受，核心项目尚未切换），发布最后一步把 map 拷进内网存储：

紧接着要删掉线上 JS 里的 sourceMappingURL 注释。source map 文件绝不能发布到公网——它带着完整源码、变量名和目录结构，挂出去等于把代码免费送给竞争对手和扫描器。map 只允许内网的反解服务读取，公网一份都不留。

复盘：那次只在 iOS 消失的上报

有一次发版之后，面板上 iOS Safari 的错误量近乎为零，但用户反馈页面在 iPhone 上确实坏了。我们先怀疑内核不支持 window.onerror，又怀疑采集脚本没加载，都排查不下——用桌面端 UA 模拟访问一切正常。

最后拿真机抓包才看清真相，问题有两层，叠在一起。第一层：上报域名被挂进了 CDN，路径规则把它当静态资源处理，返回了一个跳转；浏览器跟随重定向时把 POST 降级成了 GET，请求体里的整批 payload 就此丢失，端点收到的全是空查询。第二层更隐蔽：降级后的 GET 如果查询串完全相同，iOS Safari 会按它偏激进的缓存策略直接复用响应，同一台手机从第二条上报起根本没再发请求，错误于是凭空消失。

修复逐条对应：上报端点改走独立域名、绕开 CDN 的重写规则；响应侧强制加不缓存的头；客户端拼参数时附加随机数与时间戳，让同一指纹的每次请求在传输层都是不同的 URL。补完当天 iOS 的曲线就回来了，报错集合恰好指向那次发版的新增代码。复盘文档里记下两条教训：上报是写请求，不能被任何中间层当成静态资源；曲线上”没有”不等于”不发生”，先怀疑链路本身。

采集能力矩阵

最后把各个采集点的真实能力收拢成一张表，也是新人接手这套系统时该先背下来的东西。

采集点 能拿到的信息 可用浏览器 跨域限制
window.onerror 运行时错误 message、脚本地址、行列号；错误对象基本拿不到 全部内核；IE 无列号 跨域脚本只剩 Script error.
addEventListener 捕获阶段 失败资源的标签类型与地址 现代内核与 IE 9 及以上 无
try/catch 包装 完整异常对象与自身堆栈 全部 无
Promise 收口约定 被兜住的拒绝原因 取决于页面所用实现 无
unhandledrejection 未被处理的拒绝 当时只是提案，不可依赖 无
资源加载 error 事件 地址，拿不到状态码 同捕获阶段 无

小结

回头看，这条链路上每一个环节都是被查不动的事故推着补的：拿不到堆栈，逼出了 message 正则；满屏的 Script error.，逼出了 crossorigin 和 CORS 的配合；上报凭空消失，逼出了独立域名和禁缓存。设计上的结论其实就两条。其一，采集是尽力而为，矩阵里写明的空洞要如实反映在面板上，别让读报表的人以为它全知全能。其二，上报链路自己就是最脆弱的代码，它平时没人测、坏了没人告警，所以它反而最需要一条端到端的心跳——我们后来在日常构建里固定注入一条合成错误，从采集一路验到入库，看到那条假错误落进面板，才敢说今天的”没有上报”意味着”真的没有错误”。
