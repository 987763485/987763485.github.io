ES6 Set 与 Map 数据结构

本文属于《算法与数据结构》第 5/13 篇
上一篇系列目录下一篇

Firefox 40 上周刚发布，ES6 的标准文本也定稿整整两个月了，Set 与 Map 终于从”尝鲜语法”变成值得认真选型的东西。但它们在 2015 年 8 月的处境很特别：Babel 能转的只是语法，这两个类是 runtime，转译帮不上忙，polyfill 又有实打实的体积与语义折扣。本文按对比与选型的思路走：先数对象当字典的三个痛点，再给四种结构的选型表，然后是与 ES5 手写方案的对照、五个常见坑、三个实战件，最后诚实地交代引擎现状。适合正纠结”这版要不要上 Set/Map”的同行。

拿对象当字典的三个痛点

我们在 ES5 里习惯把 {} 同时当 Record 和字典用，字典这一用就暴露出三处不适：

其一，键只能是字符串（Symbol 虽然进了 ES6 定稿，运行时普及还早）。属性访问那一刻做一次隐式 ToString，dict[1] 与 dict['1'] 是同一个槽位。《JavaScript 数组去重的几种实现》里我把这个现象叫键类型退化，靠 typeof 前缀才补回来——字典如此，查重的 Set 更需要。

其二，原型链污染判重结果。seen['toString'] 沿原型链摸到一个函数、一个真值，元素被当成”已见过”悄悄丢掉；直接 seen.hasOwnProperty(k) 还可能被值叫 'hasOwnProperty' 的元素炸出 TypeError。防御要靠 Object.create(null) 加 hasOwnProperty.call，两层都写全才安生。

其三，size 要手算。Object.keys(dict).length 是 IE9 起的待遇，IE8 得 for...in 自己数，还得防原型键。一个”现在有几条”的问句要背这么多纪律，说明结构本身没长这张嘴。

Map 的键可以是任意值、自带 size、has/get/set/delete 语义明确，三个痛点一次消掉；Set 则是”只关心有没有”的 Map 退化版。

四种结构：语义边界与选型表

先划清语义，再上表：

WeakSet 与 WeakMap 只收对象键，且不阻止键被垃圾回收：引用消失、记录自动蒸发，所以它们没有 size、不可遍历、没有 clear——能枚举就等于续命，弱语义与可枚举在规范里互斥。”跟着对象生命周期走”的元数据是它们唯一的主场。

你的需求 选它 理由
普通映射，键本来就是字符串 id 继续用 {} 老写法够用，JSON 直通，无 runtime 成本
键是对象（实例、DOM 节点） Map 免掉隐藏 id 与字符串化
值的集合、要判重和集合运算 Set 语义自带，size 白送
对象上的私有状态/元数据，希望随对象销毁 WeakMap 不泄漏，不用手动清
需要序列化、遍历全量、调试时看整体 对象或数组 Weak 系列不可枚举，直接出局

键怎么算相同：三种相等性与边界用例

Set 判重、Map 找键用的是 SameValueZero，与另外两种比较摆在一起才看得清：

比较方式 NaN 与 NaN +0 与 -0 谁在用
=== false true indexOf、$.inArray 这类老判重代码
Object.is（SameValue） true false ES6 新增，仍是 runtime
SameValueZero true true Set 的 add/has、Map 的 set/get/has/delete

它就是 === 修好 NaN、再抹平正负零；ES5 里要手写同语义比较，判据是 a === b || (a !== a && b !== b)，别抄区分 ±0 的 Object.is。边界自查：

写法 结果 原因
s.add(NaN) 两次 size 是 1 认定 NaN 与自身同值
m.set(0,'a') 后 m.set(-0,'b') m.get(0) 得 'b'，size 是 1 正负零同槽
m.set(1,'a') 后 m.set('1','b') size 是 2 键不做 ToString
new Set([{a:1},{a:1}]) size 是 2 只比引用，不看内容
对象键存进去后改它的属性 仍然 get 得到 比较引用，改内容不挪位

第三行最容易翻车：dict[1] 与 dict['1'] 原来共用一个槽，换成 Map 变两条，size 从 1 变 2。query、表单来的键永远是字符串，所以同一含义可能是数字也可能是字符串的键要在入口 String(k) 归一——对象替你兜住了，Map 不会。

与 ES5 手写方案对照，以及什么时候仍然该用老写法

ES5 时代这三件事各有土办法：去重用数组 indexOf 线性扫或哈希表加类型前缀；带对象键的映射靠 refId 发号（defineProperty 挂不可枚举的 __uid__）再外层字典；防止节点泄漏靠显式 dispose 清理。jQuery 项目里还有 $.inArray，比较语义同样是 ===，NaN 照样漏。Set/Map 把这套簿记折叠成原生语义，复杂度也从 O(n) 查表变 O(1)，这是真进步。

但老写法在三种场合仍是正解：目标环境兜不住——IE 11 全无、Android 4.4 WebView（Chrome 33 内核）与 iOS 8 的 Mobile Safari 不可指望，而 shim 是有体积成本的，一个 H5 页不为这几个类背 runtime；要 JSON 直通——JSON.stringify(map) 得到干瘪的 {}，配置数据落 localStorage 还得是普通对象；WeakMap 的 polyfill 是假的——2015 年 es6-shim、core-js 只能拿”给对象挂隐藏 id、外层再开字典”来模拟，键不会被真弱引用拖走，对象被冻结（Object.freeze）时连挂 id 都失败，内存照漏不误。用弱语义换”自动回收”的项目，上了 shim 等于没上，这条务必写进评审结论。

把”发号器”写全，顺带看清假 WeakMap 的骨架

民间写法与 shim 是同一个骨架。2015 年没有任何 polyfill 能造出真弱引用，es6-shim 与 core-js 的 WeakMap 就是这种”挂 id 加全局表”的模拟实现。三处语义损失跑不掉。回收：put 过一次，对象就被 store 拽住，模拟版是一条稳步上行的内存曲线，也没有 API 能批量清。冻结对象：Object.freeze、seal、preventExtensions 过的对象挂不上 id，兜底分支要么抛错要么退化成线性查找。私有性：id 是整数，日志与序列化时都会漏出来，”外部不可见”这个卖点不成立。

回收这件事在 2015 年验不干净：页面里无法主动触发回收，devtools 也不给 WeakMap 列内容，”还有多少元素挂着状态”这类审计问题答不了。土办法是把一批节点摘出文档、断掉引用，连拍两张 heap snapshot 比 detached DOM 节点数。同一台机器同一口径粗测，只看相对量级：原生那页几轮换血后能落回去，shim 那页一路往上。

五个常见坑

NaN 与 -0。 最终规范把 Set/Map 的比较定为 SameValueZero：多个 NaN 算同一个值（add(NaN) 两次，size 是 1，治愈了 indexOf 派的顽疾），+0 与 -0 算同一个键。早期实现在这两处不齐过，2015 年写代码别把业务压在”区分正负零”上，真有这需求就自己补键。

Set 不按内容去重。 new Set([{a:1}, {a:1}]) 里是两个不同的对象引用，都会留下。值级判重仍然是业务字段的事，回到 keyFn 那条老路。

Map 的遍历顺序是插入序。 forEach 与迭代按 set 的顺序走，先删再加会排到队尾。多数时候这是特性不是坑，但别拿它当”按 key 排序”用。

过 JSON 这一关

Map 与 Set 的条目不在自有可枚举属性上，序列化器按可枚举属性取值，自然什么都看不见，JSON.stringify(map) 得到 {}，整份数据静默丢掉。

为什么用数组而不是转普通对象？对象那层会把所有键字符串化：{1: 'a'} 与 {'1': 'a'} 合流，NaN 键变成 "NaN"。pairs 把键原样放在第一列，1 出来还是数字、'1' 还是字符串，读写一一对应。

对象键这一类是真没救：JSON 表达不了引用，只能给节点或实例设计稳定业务 id，运行态维护一张”id 到实例”的注册表（这张表自己不持久化），落盘写 id、读回来按 id 找回对象。说白一点：不是”Map 不支持 JSON”，是”引用不支持 JSON”。

引擎现状与引入成本

诚实的账：Firefox 是最早认真做 Map/Set 的浏览器，13 版就有；Chrome 从 38 起算较完整的实现，但”较完整”离”放心用”仍有距离——构造器吃可迭代参数、Array.from、展开语法衔接这些边角都还没齐。IE 11 完全没有，Edge 12 刚起步，移动端照旧看 Android 4.4 WebView 和 iOS 8 的脸色。所以当下的引入路径是：语法层面 Babel 帮不上忙（这是 runtime 类不是语法），运行时从 core-js 或 es6-shim 二选一，按页面里实际用到的类裁剪体积；WeakMap 在 shim 环境按”隐藏 id 模拟”对待，别指望回收。团队规范里我建议先开绿灯的是 Set 查重与 Map 做对象键缓存这两类纯内存场景，涉及序列化、弱引用生命周期审计的，再等一个季度。

小结

Set/Map 解决的是对象当字典时的键字符串化、原型污染、手算 size 三件事，Weak 版本再送你一条”随对象生命周期自动清理”。选型顺序：键是字符串又要 JSON，用回 {}；键是对象，Map，节点元数据且不需要枚举，WeakMap；判重与集合运算，Set。坑背五个：SameValueZero 对 NaN 和 ±0 的并档、Set 不比对象内容、Map 是插入序、Map 不接 JSON、WeakMap 调试不可见。最后强调 2015 年 8 月的特殊性：这两个类靠 polyfill 而非转译，shim 的体积成本与 WeakMap 的模拟折扣，是它们与”原生可用”之间真实存在的价格标签。
