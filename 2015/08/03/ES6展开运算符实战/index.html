ES6 展开运算符实战

ECMA-262 第 6 版在六月中旬刚定稿，浏览器还没跟上，但 Babel 5 已经能让我们把展开运算符 ... 用进日常代码。本文不打算罗列语法特性，而是算三笔账：... 在三个位置上到底做了什么、它和 apply、concat、slice 的开销差在哪个量级、以及转译产物会把我们带回哪些老问题。读完你应该能在代码评审里说清”这里用展开是赚了还是亏了”。注意对象字面量里的展开当时还是提案，本文会单独标注状态。

对象位置的展开要单独说清楚状态：它不在 ES6 定稿里，是 TC39 上还在 stage 1 的”Spread and Destructuring Properties”提案，离定稿很远。Babel 5 默认不认这个写法，要显式打开可选转换器：

这个开关是实验性质，转出来的代码是”键值逐个赋值”，不经过迭代器协议。对象展开的合法替代品是 ES6 正文里的 Object.assign（配合 core-js 补 runtime）：Object.assign({}, defaults, opt)。本文后续讲”合并配置”时会两者都出现，但请把它们当作提案糖与原语来对待。

还有一个必须分开的方向：... 写在函数形参位时是 rest（剩余参数收集），方向是”多个实参收成一个数组”；本文只讲相反方向的 spread（展开），rest 留给同系列《ES6 默认参数与剩余参数》那篇去写。两者共用记号，转译路径和行为差别都很大，混为一谈是评审里最常见的争论源头。

它做了什么：apply 的语法改写与迭代协议消费

位置二最好理解：f(...args) 语义上就是把数组拆成逐个实参，相当于 f.apply(f, args)，只是 this 的取法更细。Babel 5 的转译产物也确实走 apply，后面会看到。

位置一就不是 apply 能类比的了——数组字面量里的展开消费的是迭代器协议：引擎拿 list[Symbol.iterator]()，反复 next()，把每个 value 按顺序塞进正在构造的新数组。这意味着 ... 能摊开的不只是数组：Set、Map、字符串、任何自己挂了 Symbol.iterator 的对象都可以；但普通对象和 NodeList 不行，因为它们在那个年代的引擎里根本没有迭代器方法。这一点是后文好几个坑的总根源。

浅拷贝的属性也要讲明白：[...matrix] 拷出来的一维元素还是原引用，{ ...obj } 或 Object.assign 同样只拷一层。展开不是深拷贝的解决方案，谁在 code review 里把它当深拷贝用，就等着共享引用的 bug 吧。

Math.max 能吃多少个参数：apply 的上限会咬人

Math.max.apply(null, hugeArray) 是把数组拆成实参的经典写法，也是经典事故：参数个数超过引擎上限就抛 RangeError: Maximum call stack size exceeded，因为每个实参都要占一份调用栈。上限没有规范值，各引擎在几千到十几万之间浮动。

我手上这台机器同一口径的粗测（io.js 3.x，只求相对量级）：apply 在几万个元素时稳定炸栈；原生 Chrome 43 的 Math.max(...huge) 能正常算完，因为实现内部是循环压栈前的优化路径，不逐个占用 JS 栈帧；可一旦这段代码经过 Babel 5 转译，产物退回 Math.max.apply(undefined, huge)，上限问题原样复发。这是我强调”看转译产物”的第一个理由：同一行源码，原生和转译后是两种风险等级。给个不丢人的兜底写法：

展开、concat、slice 的开销账

位置一每次执行都会构造一个新数组：开一段内存、跑一遍迭代器、逐项 push。和老写法比，我在我手上这台机器（io.js 3 与 Chrome 43，同一口径各跑五遍取中位，只看相对量级）粗测的印象是：

写法 粗测量级 说明
a.concat(b) 基准 原生一条路径，最快
[...a, ...b]（原生） 与 concat 同量级，略慢 走迭代器，逐项协议调用
a.concat(...listOfArrays) 慎用 转译后即 concat.apply，同样撞参数上限
slice() 克隆单个数组 与展开同量级 语义有别，见下文稀疏数组一节
Babel 转译后的展开 视产物而定，见末节 数组情形就是 concat，不亏

结论并不玄乎：常规规模下展开和 concat 的差距吃不掉一次 DOM 操作，选型看语义和可维护性，不用看计时器；真正的性能分界线是上面那条参数上限，它不是”慢一点”而是”直接抛错”。热路径上反复 [...cache, item] 重建大数组才是真开销，那种场合一个 push 或 Object.assign 的变更策略比换语法有用。

五种写法逐项对照

计时之外更要紧的是：这几种写法语义不等价，选错了不是慢，是错。”2015 可用性”指不依赖转译、当场就能跑的情况：

写法 返回什么 新建数组 稀疏空位 参数上限风险 2015 可用性
[...a, ...b] 新数组 是 读成 undefined，结果致密 转译后是 concat 多参，规模极大时留意 只有部分引擎原生
a.concat(b) 新数组 是 按当时规范跳过空位，结果变短 只有多参用法有 全部
a.slice() 之后再 push 先克隆后原地改 第一步新建 保留 逐个 push 没有 全部
Array.prototype.push.apply(a, b) 新长度，不是数组 否 读成 undefined，致密 有 全部
for 循环 push 无 否 看写法 无 全部

两处容易看漏，也是评审里最常争的。concat 只展平一层数组参数：a.concat([1, [2]]) 里那个 [2] 原样留作元素，a.concat(...[[1, 2], [3, 4]]) 才得到四个元素，把”多维摊平”寄托在 concat 上就得自己再套一层循环。push.apply 返回的是 target 的新长度，一个数字，有人把它”优化”成 var merged = Array.prototype.push.apply([], list)，merged 当场变成 list.length，这类改写评审时很难一眼抓出来。

展开与 Object.assign 怎么分工

两者重叠的部分比想象中小，按场景切一遍，评审时就不必每次重吵。

场景 2015 年该用哪个 理由
数组拼接、中间插一段 数组字面量里的展开 转译产物就是 concat，不亏
合并若干配置对象 Object.assign 到空对象上 ES6 正文特性，polyfill 就能跑
给已有对象补默认值 Object.assign 直接改 target 不新建对象，代价是 target 被动了
类数组转真数组 slice.call，或带 polyfill 的 Array.from 展开在这里最容易翻车

两个不重叠的点值得单独记。其一，assign 用在数组上是按下标覆盖，不是追加：Object.assign([1], [2, 3]) 得 [2, 3] 而不是 [1, 2, 3]，源的自有键就是 '0' 和 '1'。其二，assign 忽略 null 与 undefined 这两个源，Object.assign({}, null) 安静返回空对象；展开遇 null 是硬失败，[...null] 抛 TypeError。来源不确定的数据（接口返回、本地存储）因此这样分工：对象那侧让 assign 兜着，数组那侧先判空再展开。

另有一句：提案版展开走”新建属性”、assign 走”赋值”，两者并不完全等价。

反直觉的一点：数组那一支不需要任何 runtime，所以只有非数组输入才会把 helper 拖进 bundle。只展开数组就一条依赖都不欠；一旦写了 [...new Set(list)] 或 [...arguments]，polyfill 就从可选变必须。

最后一层：... 是语法不是 API。IE 11 与内核停在 Chrome 33 的 Android 4.4 WebView 在解析阶段就抛 SyntaxError，整个脚本一行都不执行，core-js 与 es6-shim 帮不上——缺 API 可以 typeof 探测、可以补，缺语法只能全量转译。

小结

... 在 2015 年 8 月的正确打开方式：数组字面量里放心用，转译产物就是 concat，赚的是可读性；函数调用位用得着但记住它转译后是 apply，大数组先想想上限；对象字面量里的展开还是 stage 1 提案，代码评审时单列一类，能走 Object.assign 就先走 Object.assign。JSX 的 {...props} 属 JSX 语法，与提案无关。语义上永远记住三条：浅拷贝、消费迭代器协议、每次重建新数组。标准刚满月，语法可以尝鲜，runtime 必须靠 polyfill 兜底——把这盘账算清楚，展开运算符就不再是”看着时髦”而是”用得明白”。
