ES6 Generator 函数入门

ES6 定稿不到两个月，Generator 是这批新语法里最让人跃跃欲试、也最容易被误用的一个：function* 加 yield 看起来就是”同步写法写异步”的魔法，可它同时也是一台需要手动上弦的状态机。本文按我这两个月在 io.js 和浏览器转译两条链路上踩过的坑来写：先讲清楚 next 参数到底喂给了谁，再看惰性和无限序列怎么用，然后是 2015 年做异步流程控制的现实选择（co + thunk、bluebird 的 coroutine），最后列坑清单，并给出”什么时候不值得用”的判断。异步模型本身不再展开，事件循环和 Deferred 各有一篇旧文。

迭代器与生成器：先用一句话说清关系

生成器函数被调用时不执行函数体，而是返回一个迭代器对象（同时可迭代），你手里所有 next()、return() 的方法都挂在这个返回值上；for...of 消费的也是它。迭代器协议、Symbol.iterator、yield* 的委托规则我在同系列《ES6 迭代器与 for…of》那篇里写，本文只讲语法与它自己的控制流，用到转发时补一个用例。

function* 与 next(value)：反直觉的点在暂停位上

第一次读这段代码的人十个有九个以为 next(5) 的 5 会变成这次的结果——错。next 的参数是喂给上一个暂停点上的 yield 表达式的返回值，像往机器里续料；而它自己的返回值才是机器当前吐出的 { value, done }。再补三条语义：函数体 return 的值只在 done: true 那次出现；无参调用 next() 相当于 next(undefined)，于是上一个 yield 拿到 undefined；第一次 next 的参数无处安放，被直接丢弃。这个”错位一步”的心智模型一旦建立，后面 co 那套”yield 一个取数任务、下一个 next 把结果灌回来”的机关就一目了然。

光记结论容易反弹，我习惯用一段带标签的 log 把机器拆开看：

控制台按时间先后的输出是这样：

  1. [main] 拿到迭代器，函数体一行没跑
  2. 第一次 next() 推到第一个暂停点，先打 [gen] 进入函数体
  3. 主线程打 [main] 第一次 → {"value":"first","done":false}，无参数可放
  4. 第二次 next('给 x 的值')：参数不进返回值，它变成 x，唤醒时才打 [gen] x = 给 x 的值
  5. 主线程打 [main] 第二次 → {"value":"second","done":false}
  6. 第三次喂 y，函数体 return 前打 [gen] y = 给 y 的值，主线程收到 finished

关键在第 3 与第 4 步之间：停在 yield 'first' 上时 var x = ... 只执行了一半，下一次 next 带值回来才补齐。yield 没有固有值，它的值由唤醒它的那一次决定。时序如下：

sequenceDiagram
  participant M as 主线程
  participant G as 生成器函数体
  M->>G: next() 首次驱动
  G-->>M: 停在第一个 yield，交回 first
  M->>G: next(给 x 的值)
  Note over G: 参数落在上一个 yield 的返回值上
  G-->>M: 停在第二个 yield，交回 second
  M->>G: next(给 y 的值)
  G-->>M: 走到 return，done 为 true

2015 年的现实：co + thunk 与 coroutine

生成器语法本身不提供异步能力，是”可以中途暂停的函数”这个形态让库能把 yield 出去的东西当成待办任务、完成后再 next 唤醒。当年做流程控制的主力是 TJ 的 co，配 thunk 风格回调。一段可读的完整例子：

thunk 与 Promise：被 yield 的东西不一样

co 3 与 co 4 的分裂点就在”允许 yield 什么”上。两种写法长得像，工程后果差很远：

对比项 yield 一个 thunk yield 一个 Promise
何时开始取数 库把回调传进来才发 包装函数一调用就开跑
忘记驱动 什么都不发生，不发请求 请求已出门，没人看结果
依赖 co 3.x 加手写 thunk 原生 Promise 配 shim
并发组合 自己拼，或引 co-gather Promise.all 一行
出错时的栈 多一层回调，落在 fs 内部 能追到创建处，未处理有警告
走向 co 4 已不收 thunk 与原生 API 同族

最容易咬人的是第二行：new Promise 的执行体立即就跑，readJson('a.json') 一被调用 I/O 已经出门，写成”调用了但没 yield”就是白白发一个请求；thunk 那派”不驱动就绝不产生副作用”，与生成器自身的惰性同构，代价是这套风格已在退场。

要不要为流程控制引入整个 bluebird

bluebird 的 coroutine 看着省心，但它是一整个 Promise 实现：

维度 co 加 thunk co 加 Promise bluebird 的 coroutine 裸 Promise 链
新增依赖 co 一个包 co 加 shim 无（已在用） 无
错误传递 回调首参 err reject 传到 catch 同 Promise，另有取消 手写易漏
超时与取消 没有 没有 timeout 现成 自己实现
排错体验 最差，回调栈 尚可 longStackTraces 最易读 尚可
转译依赖 需 Babel 5 与 runtime 同上 同上 不依赖生成器语法

结论按场景：已经在用 bluebird 的项目，Promise.coroutine 是零额外依赖的正解，排错也比 co 好一档，我们后台脚本最后就统一到它；纯 io.js 的一次性任务，co 4 加原生 Promise 更轻；只有全站把 co 当约定的老仓库才值得维持 thunk。专门为”能用生成器”引 bluebird 不划算：它带自己的 Promise 实现，promisifyAll 又给每个 API 加一个 Async 孪生方法，一个模块里两条取数路径并存。

坑清单

按踩中的概率排序。

忘记 next，一切都不会发生

生成器是”草稿不是支票”。最阴的案例是一个纯副作用的生成器被调用后忘了遍历，单元测试里加了断言才抓到。经验法则：调用生成器函数的同一行内，必须能看见驱动它的东西——next、for…of 或 co 三者之一。

this 与箭头函数的组合

对象方法简写里的生成器，直接调用 timer.tick() 时 this 正常；但 co 是拿生成器函数去裸调用的，co(timer.tick) 里 this 丢了，要 co(timer.tick.bind(timer))。想按箭头函数的词法 this 绕过去？不行——规范不允许箭头函数是生成器，() => {} 里写 yield 直接语法错误。这条在 2015 年很扎眼，因为当时社区已经流行”回调一律写箭头函数保 this”，唯独生成器方法享受不了。

return / throw 提前终止与异常穿透

next 之外还有两个入口：it.return(v) 强制结束，it.throw(e) 把异常从当前暂停点注入函数体。由此两条坑：其一，生成器内部不 catch 的话，异常会在 next 的调用点同步抛出，堆栈长得像”调用方错了”，排查时先找 try；其二，try/finally 的 finally 只有迭代真正走完或被显式 it.return() 才执行，半途弃用迭代器，清理代码就是不跑——引擎对这两个方法的支持当年还不齐，转译路径由 regenerator 兜住，行为反而更一致。

输出顺序是清理在前、抓到在后：throw() 等价于在暂停那一行写 throw，try 罩得住；return() 像提前 return，finally 照样走完。没人管的是第三种：迭代器被扔掉，函数体永远停在暂停处。我们 5 月的连接泄漏正是这个形状——外层超时后直接放弃生成器对象，连接从来没还过。修法是别把”放弃”写成”丢弃”：超时方持有迭代器并调 it.return()，或者在生成器内部用 try/finally 罩住取数段；后者不依赖调用方收尾，我们最后统一到这条。

一个迭代器只能用一次

迭代器只有一条向前走的执行位置，走完 done 就恒为真，继续 next() 只会继续拿到 { value: undefined, done: true }，想重来必须重新调用生成器函数。两类 bug 因此常见：把迭代器当”数组”存到成员上，第二次遍历是空的；for...of 与手写 next() 混用同一个迭代器，手写那次吃掉队头元素，for...of 于是从第二个开始。规矩是一个迭代器只允许一个驱动者。

转译体积膨胀

这是转译成本，不是语法缺陷：Babel 5 把每个 function* 改写成 regenerator 生成的状态机函数——一个 _marked 内函数加状态变量加 switch 跳转，源码行数翻数倍，页面还要整体带一份 regenerator 运行时（babel-core/browser-polyfill.js 或 core-js 会打包带它）。粗测印象，只看相对量级：一两个小生成器无所谓，满屏生成器时产物体积明显压不住。

三个特征对三种体验。变量被集中提到函数顶部，所以断点停在 case 上时源码行号对不上；_context.next 存下一个状态号、return 就是暂停、_context.sent 收 next 的参数，这就是”错位一步”在产物层的实现；每个生成器还要多包一层闭包加一个 switch，栈里于是冒出 _callee$。对策只有一条：产物别手读，编译时带 --source-maps inline。

体积只有同机粗测的相对量级，不给绝对数字：一个七八行的生成器转出来大约三十行，运行时那份是与个数无关的常数项。Babel 5 的 --optional runtime 能把这些辅助换成对外部模块的引用、多入口共享一份，浏览器端我们没敢配——共享包版本一错，全站生成器一起挂。真要抠体积，只能把生成器关在少数几个流程控制模块里。

环境与开关：诚实的现状

Node 侧：0.12 里 function* 要 --harmony-generators 才认；io.js 从 1.1 起默认打开，现在（3.x）这条基本不构成问题，但 Symbol 相关的迭代器边角仍有开关闭着，老脚本升级时注意别只测语法。浏览器侧：我手上 Chrome 43 能原生跑基本的 function* 与 yield 交还，Firefox 40（8 月 11 日发布，也就是本文写完次日）又推进一批，IE 11 与 Edge 12 想都别想，移动端 Android 4.4 WebView 与 iOS 8 直接出局。所以生产结论和系列前几篇一样：语法靠 Babel 转译，迭代器与 Promise 运行时靠 core-js 或 es6-shim，两件事缺一不可。Babel 只转语法、不发 runtime，是当年新同学最常撞的墙。

什么时候不值得用生成器

给几条我现在的否决线：两步以内的异步，.then() 链或一层回调更直白，犯不上为它拉 regenerator 运行时；纯同步的状态推进，闭包加相位变量人人会读，生成器的惰性反而制造”忘了 next”的新 bug 类别；移动端 H5 对包体积逐 KB 计较的项目，转译膨胀要单独评估；团队里超过一半人还没建立”next 参数喂上一个 yield”的心智模型时，语法红利兑不了现。反过来，多步顺序异步且每步都要用前面结果的代码，才是生成器稳赚的主场。

小结

Generator 的全部机关就一句话：函数能停、能醒、醒时带数据进来，next 的参数落在上一个 yield 的返回值上。围绕它的坑也是三件套：惰性（不驱动就不执行）、this（对象方法与箭头函数的路被堵死）、转译（体积与运行时成本）。2015 年 8 月的实用姿势是 io.js 里直接吃、浏览器里 Babel 加 core-js 兜底，拿 co + thunk 或 bluebird coroutine 做多步异步；单步小场景和体积敏感的项目，就让它先在玩具分支里待着。
