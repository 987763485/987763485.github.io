CSS3 transition 过渡动画原理与性能

本文属于《HTML 与 CSS》第 48/62 篇
上一篇系列目录下一篇

上一篇《CSS3 过渡与动画性能再探》算的是动画在引擎里的账单：哪一段花钱、怎么量、怎么把一个跑了两年的定时器改掉。本篇不碰度量，把镜头收到 transition 这条规则本身：四个长期属性怎么配对、什么样的值才算”可插值”、引擎凭什么判定”发生了变化”、三个事件各自在什么时刻派发。这些是规范结构层面的东西，但它们直接决定你会不会撞上”改回同一个值动画就不播””transition: all 把 width 也一起动了””delay 写了却没效果”这一类莫名现象。适合已经写过不少 transition、但解释不清它为什么生效或不生效的同学。

四个长期属性和简写的配对规则

transition 由四个长期属性组成，初始值记住就行：transition-property 初始 none、transition-duration 初始 0s、transition-timing-function 初始 ease、transition-delay 初始 0s。这四条都是逐元素的、不可继承的，所以样式表里给父元素写 transition 不会传给子元素——当年有人问我下拉菜单为什么不 animate，根因就是这个，类挂在 <li> 上而 transition 写在 <ul> 上。

简写 transition 把一个”单条过渡描述”打包，语法顺序是属性、时间、缓动、时间。真正会咬人的是那条时间规则：简写里第一个出现的 <time> 被当作 duration，第二个被当作 delay。这和 animation 简写是同一条约定，前作《CSS3 animation 与 keyframes 动画实战》里给过一张位置表，本文不重抄，只强调 transition 上最常见的翻车写法：transition: opacity 200ms ease 100ms 是对的，transition: opacity 100ms 200ms 就把 delay 当成了 duration、把 duration 当成了 delay，结果 duration 变成 100ms、delay 变成 200ms，动画比你以为的短一半、又晚一截才开始。另一半翻车是干脆没写 duration——duration 取初始值 0s，引擎认为”这一帧就完成”，transition 存在但不播，控制台一句提示都没有，只表现为”改了没动画”。排查顺序应当是先看 duration，再看 property 有没有命中，最后看两端的计算值是否真的不同。

多条过渡用逗号列表写，四个长期属性各自也可以是列表，这时按 CSS Transitions 的重复填充语义配对：某个列表短于另一个时，它的值从头重复；长于另一个时，多出来的部分被截断。也就是说下面这段的效果是 opacity 用 2s、left 用 5s、top 又回到 2s：

transition: all 我一般不建议上生产，三个原因一个比一个麻烦。第一，all 的命中集是”任何可插值属性的变化”，width、height、left、top 这些每帧要重算布局的几何属性全在里面，你改 padding 它动、改 font-size 它也动，账单完全不可预知（分档的账在上一篇的逐属性账本里）。第二，命中个数不定，duration 列表的配对结果也不定，调试时无法从样式表读出”这条到底几秒”。第三，transitionend 按每个结束的属性各派发一次，收尾不加 propertyName 过滤就会重复执行。真要图省事，把 all 只挂在开发期的临时开关选择器上，别提交进主干样式。

什么样的值才算”可插值”

引擎创建过渡之前要回答一个问题：这两端的值我能不能算中间态。规范把答案分成了两类。

连续类型可以插值：长度（px、em、% 这类能求值的量）、角度、数值、颜色（按分量插值）、transform 的函数列表（两端结构一致时逐函数对齐插值）、阴影列表（个数一致时逐个插值）。这些属性你可以期待一条平滑的曲线。

离散类型不能插值，只能在进度过半时跳变：display、background-image 里两个不同的 url()、以及任何”无法定义中间态”的值。所以想做一个淡入的背景图切换，直接过渡 background-image 是不行的，它会在 50% 那一刻啪地换掉，观感就是一下闪屏。当年的正解是两个图层各放一张图、各自过渡 opacity。

visibility 是个特例，值得单列，因为它的行为常被当成 bug。规范不给 visibility 做插值，但给它加了一条特殊规定：过渡期间只要进度不是恰好 0% 或 100%，它就取”可见”。于是 visibility: hidden 到 visible 的过渡，观感是”立刻变可见，然后等 opacity 淡完”；反过来 visible 到 hidden 时，元素在整个过渡期间保持可见，最后一刻才真正消失。这正是把 visibility 和 opacity 写进同一条 transition 做弹层淡出的机制依据：淡出过程看得见，结束后真的不再接收点击。

transform 有两处坑。第一处是函数列表两端不匹配。写 transform: translateX(10px) 过渡到 transform: rotate(45deg)，函数种类和个数都对不上，这时 CSS Transitions 的口径是把两端各约成矩阵再对矩阵插值。我在 Chrome 44 上看到的中间态是一条带旋转兼错切的走位，不是跳变。注意这跟关键帧那边不是同一条规则：animation 在结构不匹配时按离散处理、直接过半切换（《CSS3 animation 与 keyframes 动画实战》给的实测口径是”跳变”）。两份规范各写一条，记混就会在 review 里说错话。稳妥做法始终是两端列表结构一致，连 translateZ(0) 这种只为提层加的尾巴函数也要两端都有。

第二处坑是简写属性的展开。margin: 0 过渡到 margin: 10px，引擎实际处理的是四个子属性；transition-property: margin 这种写法在当年的引擎上支持得七零八落，我踩到过一次”列了简写却不动”，从此一律写具体子属性，或者干脆依赖 all（但上一节说了 all 的代价）。同理 background、border 这些简写也别当过渡目标。

触发时机：引擎比的是计算值

这是 transition 语义的核心，也是所有”莫名不播”的解释器。引擎在样式重算时留下两份快照：变更前的计算值与变更后的计算值。只有当某属性在这两份快照里不同、该属性可插值、transition-property 命中它、并且 duration 大于 0 时，一条过渡才会被创建。比的是计算值而不是样式表里的字面量——width: 10em 到 width: 160px（当前字号 16px）在引擎眼里是同一个值，不播。

从这个模型直接推出三条。

第一条，首屏不触发。元素第一次计算样式时没有”变更前的计算值”可比，规范明确这时不做过渡。两个用途：入场动画该交给 animation，别指望”类一挂上就播”；真要让首屏那一刻有动画，就得先把起始值写成一条真实声明（而不是靠继承或用户代理默认），等样式落地后再改目标值。

第二条，同一帧内的多次修改只比较最终值。引擎不是在每次赋值时插一条过渡，它是在这一帧样式结算时看首末两端：

sequenceDiagram
  participant JS as 脚本
  participant S as 样式结算
  participant T as 过渡时间轴
  JS->>S: 本帧先写 width 等于 10px 再写 20px
  S->>T: 只取基线值与最终值 20px 相比
  T-->>JS: 基线本就是 20px 时无值差 不建过渡
  T-->>JS: 基线是 5px 时只建一条 5px 到 20px 的过渡

第二条的后半句就是”改了没动画”的常见根因：值改一圈又改回来，或者加了类又在下一次赋值时去掉，结算时首末一致，引擎判定无需过渡，于是既不播也不发 transitionend。依赖事件驱动的流程会在这种情形下卡死——上一篇给的超时保底正是为它准备的。

第三条，摘掉 transition 声明本身不会触发过渡，但进行中的过渡会就此终止。这也是我们主张静止态不留过渡声明、只把 transition 写在状态变化类上的原因：静止态没有声明，就没人能在你不知情的情况下把某个几何属性也拖进动画。

transition 和 animation 的分工与优先级

分野一句话能说清：transition 由属性值的变化驱动，是”两个状态一次插值”；animation 由关键帧时间轴驱动，自己定义路径。由此派生的能力差别在《CSS3 animation 与 keyframes 动画实战》开头推过（多关键帧、循环、负 delay 切相位、fill-mode 管两头、play-state 冻结都是 animation 的），本篇只补优先级。

同一个元素的同一个属性同时被两种机制命中时，animation 产出的计算值优先——过渡要比的是”变更前后的计算值”，而动画期间的计算值已经被关键帧接管，transition 插不到中间去。我这边在 Chrome 44、Firefox 40、iOS 8 Safari、Android 4.4 的 WebView（内核 Chrome 33）上看到的表现一致：动画在跑时，你对同一属性切类名看起来”没反应”；只有关键帧撤销、属性回到基础值那一刻，transition 才接管这次变化。IE 线按前作的口径补前缀就行，我不拿它的表现推断别人，反之也一样。

工程上我给的处置不是”记优先级”，而是把冲突消掉：一个元素上参与动画的属性，只允许一种机制驱动，在样式表里用注释或类名前缀写明这条属性的主人。这条规则和上一篇的所有权纪律是同一件事的两面——那篇管”谁在写”，这篇管”谁能插值”。

三个事件的语义与前缀

草案里定义了三个时刻：transitionrun 在过渡被创建时派发（delay 期间也算已创建），transitionstart 在 delay 结束、真正开始插值时派发，transitionend 在完成时派发。必须注明 2015 年 8 月的现场：前两个基本没有引擎支持，我在上面那四个环境里一个都监听不到，可依赖的只有 transitionend；”delay 一开始就要上报”这类需求只能靠 JS 自己打点。

transitionend 的事件对象上有三个有用字段：propertyName（哪个属性结束了）、elapsedTime（已经过的秒数，注意 delay 不计入）、以及伪元素过渡时的 pseudoElement。事件名分家：WebKit 一线是 webkitTransitionEnd（中间那个大写 E 是全系列里最容易敲错的一个字符），IE 那一线的大小写写法各家有过出入，较新的 Chrome 才会连无前缀名一起派发。

被打断时的语义再明确一次：中途改值不派发 transitionend，引擎以当前计算值为新起点重建时间轴。它既不是补发结束，也不是错误，规范里就是没这件事。上一篇写过它造成的线上事故和超时保底写法，本篇只补语义。

缓动函数的手感与 steps 的分步

曲线本身的机制——两个端点固定在 (0,0) 与 (1,1)、x1 与 x2 必须落在 0 到 1 之间否则整条声明非法、y 允许越界用来做回弹——在《CSS3 animation 与 keyframes 动画实战》里推过一遍，ease 那几个关键字等价于哪组四个数也在那篇。这里只讲 transition 侧的手感调法：它的曲线是一次性的，对时长的依赖比 animation 更强。

跟手的感觉基本来自两个动作：时长压短、前段给足速度。120 到 240 毫秒这个区间里，位移类过渡用 ease-out 或自定义的 cubic-bezier(0.2, 0.7, 0.3, 1)，开头就走掉大部分路程、尾巴慢慢到位，观感是”响应快、落点稳”；反过来拿 ease-in 做出现类动效，会让人觉着界面在犹豫。进出也值得不对称：展开 220ms 无延迟、收起 160ms 再给一点 delay，连续点击时就不会两段叠在一起糊成一团。这些数都不是绝对的，我按同一台机器的相对感受定，换项目就重调。

steps() 在 transition 上同样可用，而且它解决的问题和 animation 那边不一样。用 transition 做雪碧图分步移动，语义是”一次交互放一段片子”，比如点一下按钮播完 10 帧然后停在末帧，等下一次点击复位——这是 animation 的 infinite 循环给不了的形状：

steps(10) 等价于 steps(10, end)：跳变发生在每段末尾，所以第一格显示满 80 毫秒，最后一段结束时正好落在 -640px。换成 steps(10, start) 则一上来就跳进第一格，差别只在第一帧会不会闪一下——当年素材对不齐时我是改 start/end 而不是改图。另外 steps() 不改变属性档位：background-position 每帧仍然要重绘，只是省掉亚像素中间态。

一个完整的小例：悬停展开、点击保持的菜单

把上面几条落到一个可运行的例子里：一个”更多”菜单，悬停时展开，点击可以钉住（触屏上悬停不可靠，这是当时的常规处理），钉住态用一个不同的过渡时间与一条 steps 角标。

这个例子把前几节的点都塞进去了：过渡只挂在状态变化类上；visibility 与 opacity 同列，靠特殊语义做到淡出可见、收起后不可点；两端 transform 列表结构一致，translateZ(0) 这个尾巴两边都有；三条属性分别给时长，propertyName 只认 opacity；void offsetHeight 只在打开那一帧付一次；取消钉住时同帧改两个类，引擎只比最终值，所以看到的是一条过渡而不是两段接力。

小结

transition 的四个长期属性里，duration 为 0 就等于没过渡，简写里两个时间值的先后顺序是唯一要背的东西；逗号列表按”不足重复、超出截断”配对，所以 transition: all 的实际时长不可预知，显式列出属性才可控。可插值性决定动画成不成立：长度、角度、数值、颜色和结构一致的 transform 列表是连续的，display 与 background-image 的 url 只在过半时跳变，visibility 靠一条特殊规定配合淡出，transform 两端列表不匹配时按矩阵插值——最后这条和关键帧那边的离散处理不同，别记混。触发只看一件事：变更前后的计算值有无差异。于是首屏不播、同帧批量改只看最终值、改回原值既不播也不发事件；需要起始态就用一次强制同步布局提交基线。两种机制同时命中一个属性时 animation 说了算，但工程做法是从源头消掉冲突。事件侧只有 transitionend 可靠，jQuery 的 .one("webkitTransitionEnd transitionend") 能处理双名重复，冒泡过滤、propertyName 过滤和超时保底仍要自己写。缓动与 steps 是手感问题：短时长配 ease-out 就叫跟手，steps 给的是”一次交互放一段片”的形状，它不改变属性所在的代价档位。
