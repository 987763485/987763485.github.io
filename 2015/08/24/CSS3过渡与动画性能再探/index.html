CSS3 过渡与动画性能再探

本文属于《HTML 与 CSS》第 49/62 篇
上一篇系列目录下一篇

“transform 和 opacity 便宜”这句话，在这个系列里已经出现过三次：《CSS3 animation 与 keyframes 动画实战》用它推导了写法纪律，《减少重排与重绘的实践清单》把它列成一条清单项，《CSS 性能优化：减少重排与重绘》把它归到”以合成为主”那一档。本篇不打算再论证一次这个结论，也不把那张按”布局、绘制、合成”粗分三档的表照抄一遍。我要做的是三件前作没做透的事：把一条动画的引擎账单算到”合成层”这一格，说清它究竟在替谁省钱、又把成本推给了谁；给一套今年 8 月手上真能用的度量手段，先确认钱花在哪一段再动手；最后把一个线上跑了两年、用定时器逐帧写 top 的抽屉动画改造成 transition，把改造里所有会咬人的细节写下来。适合已经会写动画、但说不出”什么时候动画反而更贵”的同学。

一条动画的账单：从样式计算到合成

先把一条动画在一个引擎帧里要走的路画出来。这里的分段口径沿用前作，但比前作多画了”分层”和”光栅化”这两格——前几篇都停在 layerize 就跳到合成了，而真实项目里最贵的一笔账恰恰藏在这两格里。

这条链上有三段是每帧都要重复付费的。第一段是样式计算：不管属性是什么，只要动画在推进，引擎就得算出这一帧的计算值。这段的代价跟元素数量、规则数、层叠深度有关，跟属性无关，所以它是一条”固定税”——把 transition 写在一个命中 600 个后代的容器类上，光这笔税就够疼，这件事《CSS 性能优化：减少重排与重绘》在 style 段讲透了，本文不再展开。

第二段是几何与内容失效：改 width、top、margin 时，布局要重算，然后绘制要重画，然后重画结果还要重新上传给 GPU。改 background-position、box-shadow、border-radius、filter 时，布局这一格跳过了，但绘制与上传这两格照付。第三段才是合成：属性落在 transform 与 opacity 上、而且宿主元素确实有独立层时，布局与绘制两格一起跳过，合成器只是把那张已经存在的纹理换个位置贴一次、或者换个 alpha 混一次。

所谓”便宜”，说的就是第三段把前两段的重复劳动一次买断了。而断约的代价是：买断的前提是先有那张纹理，纹理是要占显存的，纹理失效重画仍然要钱，只是不在每帧的钱里。这个”前提”正是下面一整节的主题。

合成层为什么便宜，代价又落在哪

引擎在什么条件下肯给你一层

不是所有元素的 transform 都能走合成。引擎决定”给不给这个元素一层”有一套内部规则，2015 年我在 Chrome 上能稳定观察到的提层条件大致是这些：带 3D 的变换（translateZ、translate3d、rotate3d、matrix3d，也包括祖级 preserve-3d 的上下文）；对 transform 或 opacity 做动画或过渡；will-change 显式声明将要修改的属性；overflow: scroll/auto 且开启滚动加速的容器；video、canvas、WebGL、插件这类天生自带后备存储的元素；带 filter 的元素；以及 position: fixed 在部分场景下的滚动加速。IE 一线和老 Android WebView 有自己的取舍，行为不能互相推断。

这里有个当年坑过我、也坑过同事的细节：提层是会传染的。一个合成层的祖先，如果绘制顺序上被这个层”穿过”了，就会被连带提升，甚至它自己的其他子节点也可能被隐式提升。所以你在列表项里给一个角标提了层，整张卡片的背景图可能就被复制成一张独立纹理。这在 DevTools 的层边界可视化里一眼能看出来，靠肉眼猜是猜不准的。

will-change 值得单独说。它的语义是”我待会儿要改这个属性，你提前把准备做好”，而准备做的事通常就是提层。但 2015 年 8 月这个时间点，它的实现面真的很窄：Chrome 36 之后可用，Firefox 那边也有实现，Safari 与 iOS Safari 完全没有，IE 全系不支持，刚出来的 Edge 12 也不支持。也就是说写了等于没写的环境占大头，而且它还有另一个坑：will-change: all 是合法且极其危险的值——它会让引擎把尽可能多的准备都做上，等价于给这个元素挂满层。正确的用法是三个动作连在一起：临动画开始前设 will-change: transform，动画结束后改回 will-change: auto 或把声明删掉，并且不要把它写在常驻选择器里。它是个”提前几帧的提示”，不是一个样式标签。相比之下 translateZ(0) 那套 hack 支持面广得多，代价是它把提层变成了永久状态、还会污染 transform 列表（下面重构案例会再遇到这个污染问题）。

层的账单是显存和层数

一张层的纹理大小不是元素的 CSS 尺寸，而是它的绘制边界盒乘上设备像素比，还要向上取整到纹理尺寸。这意味着三件事。第一，一个 375 宽、整页高的滚动容器被提层后，纹理高度可能远超屏幕，直接顶到 GPU 的单纹理尺寸上限（当年常见的是 2048 或 4096 这条线），超了就退化成软件绘制或者切块，加速收益当场蒸发。第二，devicePixelRatio 是 2 或 3 的机型上，显存按平方倍涨，一台千元机的 GPU 预算可能还没有你桌面试验机上那半张卡的四分之一。第三，iOS 上合成层后备存储的总内存是有硬顶的，超了以后 WebKit 的行为不是”降级”而是直接把页面打回白屏或者整屏重绘，我这边在 iOS 8 的长列表页上撞到过一次，现场表现是”往下滚到某一屏突然白一下再全量重画”，当时完全想不到根因是前面几十个提层的小图标。

所以层数与显存这两个乘数必须一起算。给一个元素提层省的是”每帧重画”的钱，花的是”常驻显存加一次上传”的钱。动画只跑三百毫秒、元素只有几十像素见方，这笔交换很可能亏本；动画常驻循环、元素占半屏，这笔交换稳赚。

一个层爆炸的负向案例

去年做一个消息列表页，视觉稿要求每一行入场做淡入加右侧滑入。需求本身完全落在合成射程里，于是当时的我给了一个”看起来很专业”的实现：每一行的 li 都写 transform: translateZ(0) 常驻，入场时切一个改变 opacity 与 translateX 的类。桌面 Chrome 上丝般顺滑。

真机上一进列表就露馅了。四十行数据一次性渲染，加上被连带提升的祖先层，页面上同时挂着一百多个合成层；低端 Android 上第一次快速滑动列表，帧间隔从我这边同一台测试机的十几毫秒直接跳到四十毫秒以上，掉帧比改成动画之前用 top 的版本还难看。原因不是主线程忙，恰恰相反，脚本几乎是空的——忙的是 GPU 进程：层数一多，每次滚动的合成开销、纹理上传的带宽、显存被换入换出的代价全部叠加起来，合成器自己变成了瓶颈。这就是层爆炸：省错了地方的钱，最后被记账到更贵的地方。

后来的改法是把”常驻提层”改成”只在动画期提层”：入场时通过类名给 translateZ，transitionend（以及保底定时器）之后把类摘掉，静止的列表行回到普通绘制路径。再配上”可见区域之外的行不做入场动画、直接终态”的规则，同一口径下帧间隔回落到和桌面同一量级。结论一句话：提层是定位救急的工具，动画结束能收回就收回——这条纪律在《CSS3 animation 与 keyframes 动画实战》的无障碍一节末尾提过一次，本篇把它的原因算清楚了。

度量：先看哪一段花钱

前作给过一句”拿不到帧数据就别说优化”。本文想补的是具体怎么拿。2015 年 8 月我手上可用的入口是这四个：Chrome DevTools 的 Timeline 面板、about:flags 与 DevTools 设置里的渲染调试开关、chrome://tracing，以及页面内自己写的帧间隔打点。前两个已经有人在《CSS 性能优化：减少重排与重绘》里提过勾选哪几项，我这里讲的是”勾选之后怎么读”。

Timeline 面板的读法

Timeline 面板录下来之后，先看右侧的 Frames 条，一帧一根横条，它的宽度就是这一帧的真实时长；明显宽于其余帧的就是掉帧点（不同 Chrome 版本对掉帧帧的着色和标注略有出入，但宽度这条判断标准一直是可用的）。然后按下面这个顺序看：掉帧那一段里，主线程泳道上是哪一类柱子占时长——Recalculate Style 占大头，问题是样式重算范围，解法在压 class 挂载点和选择器命中面；Layout 一根一根密集出现，问题是几何属性动画或者读写交替；Paint 面积大、频次高，问题是绘制属性动画（阴影、圆角、滤镜、渐变）；主线程很空但帧还是慢，问题多半在合成与显存，这时候 Timeline 已经帮不了你，要换工具。这个判读顺序是我们排查动画问题的固定动作，因为它把”该改哪一段”变成可观测事实，而不是猜。

顺带一个口径提醒：Timeline 里看到的动画帧时长包含合成线程的活动，而页面内 JS 打点只能看到主线程，两者不一致的时候往往正是”主线程没锅”的信号。

分层与绘制的可视化入口

about:flags 里当年可以直接开的渲染调试项是分层边框与绘制矩形这一类开关：打开后合成层的边界会在页面上画出实线框，重绘的脏矩形会用半透明红框闪一下。DevTools 设置里的渲染分组也提供了同类开关（画布局边界、绘制闪烁、显示绘制矩形），两处的入口名字我记不完全一致，效果都是同一类。对动画而言，这几个开关真正的答案只有两个问题：第一个问题是”我以为提层的元素，到底有几层”——层爆炸用眼睛数就能确认，不需要任何数据；第二个问题是”这段动画每帧到底闪了多大一块矩形”——transform 动画应该几乎看不到闪烁，改 background-position 的逐帧动画会看到矩形一格一格闪，改 box-shadow 的会看到比元素本身大一圈的模糊区在闪。这两个问题回答完，优化方向基本不用讨论了。

需要强调：分层调试视图看到的是”当前有多少层”，不是”动画期间层的纹理有没有重复上传”。后者要更底层的工具。

chrome://tracing 的粗读法

真要看 GPU 进程，2015 年能用的是 chrome://tracing。它的输出对不熟引擎的人非常劝退，但读动画问题只需要三步。第一步，在开始录制前只勾选与渲染相关的类别（保守做法是先用默认集，别全勾，全勾出来的日志会淹掉你关心的那两秒）。第二步，操作页面触发动画，停止录制，然后在左侧进程树里找到渲染进程与 GPU 进程这两条泳道——它们是不同进程，时间轴对得上但归属不同。第三步，只比较事件的宽度：渲染进程主线程上有没有和每一帧等频的 Layout/Paint 事件；GPU 进程里有没有成片的纹理上传（当年我看到的标签名大致是 texture 一类的字样）和绘制命令。粗读的结论只可能是三种：主线程每帧有事、GPU 每帧要重画、GPU 只是搬运。三种结论分别对应”改脚本”、”换属性”、”减层数”三类完全不同的修法——这就是为什么我说度量应该是第一步而不是最后一步。

这个工具的缺点也要写清楚：日志噪声大、不同版本事件名会变、它对动画本身的干扰不小（录制时帧率会掉），只适合在真机复现不了、需要知道”是不是 GPU 侧的问题”时用一次，不适合当回归手段。

低端机与微信内 WebView 接不上调试器，那只能用页面内的打点。下面这段 ES5 可以直接贴进测试页，它统计的是相邻 rAF 回调的间隔，输出 P95 与超时帧计数，口径和《DOM 动画与 requestAnimationFrame》里那套验收线一致，本文只补两个前作没写的点：分桶直方图（只给一个均值会把”稳定 30fps”和”60fps 里插着几个空帧”混为一谈）和”静止对照帧”（先测一段什么都不动的空闲帧，再测动画帧，两者相减才知道动画到底吃多少）。

局限必须写清：rAF 回调跑在主线程，它量的是”主线程拿到帧的节拍”。而 CSS 动画在支持离主线程推进的引擎上，脚本卡住时画面照动——这时候 rAF 打点会报出一堆超时帧，可用户看到的动画是顺的。所以这个工具适合用来对比”同一实现改前改后”的相对量级，不适合当成真实帧率仪表；跨实现类型的绝对比较，还是要回到 Timeline 的帧条上。所有数字我都只取相对量级，不做跨机型、跨版本的换算，这一点在本系列是纪律。

逐属性账本

有了分段和度量口径，可以把常见动画属性按”每帧重复付费的次数”记一遍。下表是本文自己的账本口径：写”合成”的前提是宿主元素有独立层，否则它会退回到”绘制”那一档；这一列的前提条件正是前几篇文章里没写全的地方。

属性 每帧走到的最深一段 前提与备注
width / height / top / left / right / bottom 布局，其后必带绘制与纹理更新 每帧牵动祖先与兄弟，代价随页面复杂度涨
margin / padding / border-width 布局 同上；改 body 级字体与盒属性会波及全页
font-size / line-height 布局 涉及文本测量，单帧成本高于纯盒属性
color / background-color 绘制 跳过布局，脏矩形面积决定代价
background-position 绘制 雪碧图逐帧动画的本命属性，每帧必重画
box-shadow / border-radius 动画 绘制（模糊与抗锯齿额外贵） 脏矩形比元素本身大一圈；阴影模糊是高斯卷积
filter（blur/brightness） 绘制，当年多数实现还要临时位图 前缀与实现差异大，低端 Android 上很容易成为瓶颈
transform 合成 前提：元素已在独立层；两端函数列表不匹配时按矩阵插值，观感会歪
opacity 合成 同上；半透明叠加还会增加混色开销
will-change 不触发动画，只影响分层决策 提前占显存；写成 all 等于层爆炸开关；Safari/IE 当时无实现
transition 的 timing-function 不改变上面任何一段 它只决定插值系数；steps() 让中间态消失但不减少重画次数

关于最后一行多说两句，因为这里容易得出一个错误结论。把 ease 换成 steps(10) 并不能省钱：属性仍然是逐帧被改变的，只是变化是阶跃的。它省掉的是”亚像素级的连续中间态”，也就是说 steps() 对 background-position 这类绘制属性的每帧代价几乎没有改善，但它对视觉上的抖动容忍度有改善——一帧一格的画面即使掉帧也看不出错位，而连续插值一旦掉帧就能看出跳。这也是当年做逐帧 sprite 动画时我们的真实取舍：不是图性能，是图稳定。

这里有两个实现细节值得单独讲，因为它们都是踩过才知道的。

一是起始值必须被”提交”一次。如果元素刚被插入文档就在同一帧里挂上 is-open，某些引擎认为它没有”变更前的计算值”可比，动画直接不播，观感就是”抽屉瞬间跳到终点”。当时的两种解法：读一次几何属性强制同步结算（void el.offsetHeight;），或者把目标值推到下一个 rAF 里再写。两种都能用，代价不同：前者买一次强制布局，后者多等一帧。我在一帧内还要做别的测量的场景用后者，纯粹要保证首帧不动的用前者。这个”读一次把它刷出去”的手段的机制解释——为什么批量改样式时同帧只比较最终值——留给下一篇专讲 transition 机制的文章，本文只声明它在重构里是必需步骤，并且它在动画开始前只付一次，不在每帧的账上。

二是 translateZ(0) 只写在终态类里，不写在基础样式里。写在基础样式上等于永久提层；写在 is-open 上，抽屉合起来后 transform 回到 translateY(0)，动画结束后再把 is-animating 摘掉，过渡与提层的意图一起收走。轮播那边同理，滑动结束后把非当前帧的 translateZ 撤掉，层数就不会随帧数累积。这个写法还留了一个小尾巴：起始列表是 translateY(0) 一个函数、终点列表是 translateY(320px) translateZ(0) 两个函数，两端的函数列表在长度上不匹配，按 CSS Transitions 的口径引擎会把两边先约成矩阵再插值，中间态就可能带上一点错切的味道。视觉上抽屉这点位移看不出来，但在做大位移或缩放的场合这是能看出的，解决办法是让两端列表结构一致——基础样式也写 translateY(0) translateZ(0)，代价则是这个元素从静止起就带了提层意图。这笔取舍我在表格里记的是”合成”那一档，实际项目里到底值不值，得用分层视图数一下层数再定。

transitionend 为什么不可靠

transitionend（以及 animation 那边的 animationend）是所有收尾逻辑的挂点，但有五处派发行为需要提防。前作已经讲过”值不变不触发”和”事件名前缀”这两条，本文把剩下的补齐，并给出对应的处置。

第一，前缀。WebKit 一线派发的是 webkitTransitionEnd（注意中间那个大写 E），IE 那一线的事件名大小写写法各家有过出入，只有较新的 Chrome 才会同时派发无前缀的标准名。绑定要么用特性检测挑一个，要么干脆多个名字一起绑、靠标记位去重。

第二，多个属性多次触发。一个元素上写了 transition: transform 280ms, opacity 200ms，引擎会派发两次 transitionend，事件对象的 propertyName 分别是 opacity 和 transform。收尾逻辑如果不看 propertyName 就会被执行两遍——轻则重复摘类，重则状态机跑偏。更麻烦的是 transition: all：你根本不知道它会派发几次。

第三，会冒泡。子元素的过渡结束同样会到达父元素监听器，必须用 e.target === el 过滤，否则一个卡片里三个子元素的过渡会把你父层的收尾逻辑触发三遍。

第四，也是最隐蔽的：被打断就不发。过渡在中途被删除 transition 声明、被 display: none、被同名属性写成相同值覆盖掉时，引擎不会派发一个”我被打断了”的事件，什么都不发。我们线上出过的一次事故就是连续点击开合按钮：第二次点击在第一次动画途中改了同一个 transform，第一次的 transitionend 永远不到，而挂在那上面的”恢复滚动锁定”逻辑没执行，页面滚动条被永久禁掉。

第五，严格说不是”不发”而是”可能不发”：个别老内核（我遇到的是老版本 Android 原生浏览器）在特定属性上漏发。这不需要理由，只需要承认。

兜底写法

因此当时的通用写法是：事件和定时器双保险，加标记位保证只落地一次，加 propertyName 过滤保证不被其他属性打扰，超时时长从计算样式里读出来再加余量而不是硬编码。下面是抽屉那次改造后定下来的工具函数，注释里逐条对应上面那几处坑。

这个函数解决的是”流程不能被事件丢失饿死”，但它不解决”过渡被打断”——那种情况本来就该走新的收尾。所以调用侧还要有一条纪律：新的开合请求进来时，先把上一次的等待句柄作废并立即把上一次的状态落定，再开始新一次动画。否则两次动画的收尾顺序会交错。这条所有权规则（同一属性同一时刻只能有一个写主）在《CSS 动画与 JS 动画的性能取舍》里定过，本文补的是它在 transitionend 丢失场景下的具体形状。

sequenceDiagram
  participant JS as 脚本
  participant B as 引擎
  participant C as 合成器
  JS->>B: 提交起始值 读一次几何属性
  JS->>B: 挂上过渡类并写入目标值
  B->>C: 建立时间轴 逐帧给出计算值
  C--->B: 每帧搬运纹理 不回调主线程
  B-->>JS: 派发 transitionend 可能丢失
  JS->>JS: 保底定时器到点照常收尾

改造后的收益，用我这边的口径记一句：同一台 Android 4.4 测试机、同一个抽屉、同一套打点，帧间隔的 P95 从”超出两帧预算的帧成片出现”降到”和空闲帧基本同一量级”，主线程在动画期间几乎没有事件。具体毫秒数换台机器就变了，所以结论只写成排序：改属性档位带来的收益远大于把定时器换成 rAF；而这两步都不做、只把 16ms 改成 10ms 的”提速”，是当时最常见也最没用的错误尝试。

移动端的四个专门坑

这四个都是今年这两个月里在真机上撞到的，共同特点是：桌面完全正常，所以桌面测试等于没有测试。

第一个是绘制属性的叠加。低端 Android 上，filter: blur() 或者大半径 box-shadow 叠在大圆角元素上做动画，单帧重绘就能吃掉整帧预算。而且这些属性当年多带 -webkit- 前缀、各家实现路径不同（模糊有的走临时位图、有的走滤镜描述），Android 4.4 的内核是 Chrome 33，别拿桌面 Chrome 44 的表现推断它。务实做法：阴影与模糊只在静止态存在，动画期间用一张烘焙好的图片或者半透明渐变代替；圆角元素上做 transform，别同时改 box-shadow。

第二个是 iOS 上 overflow: hidden 与 transform 的裁剪冲突。父容器靠 overflow 裁切、子元素做 3D 变换或动画时，iOS 上会出现”内容跑出圆角”的现象——不是算错了，而是被提升的子层根本没参与父级的裁剪。当年社区流传两种 hack：给裁剪父级加 -webkit-mask-image: -webkit-linear-gradient(#fff, #fff)，或者给父级也提一层。我在 iOS 8 上验证过前一种能生效、代价是这个容器被迫走独立合成路径；后一种在个别机型上反而把裁剪问题变成显存问题。结论不是选哪个 hack，而是别把裁剪和动画放在有依赖关系的父子两层——把圆角和 overflow 直接写在做动画的那个元素自己身上，问题少一大半。

第三个是首次进入页面时的动画抖动。表现是元素先闪一下默认位置再飞到位。根因基本都在渲染阻塞链上：外链样式还没全部到达时脚本已经跑起来切了类，动画的起始值来自用户代理默认样式而不是你以为的那一条；或者 transition 声明写在基础样式上，元素插入 DOM 时从”无值”过渡到”有值”。修法也是两条：动画相关的类只在确认样式就绪后再挂（最土但可靠的做法是等 load 事件，或者由样式表末尾一行 .ready 之类的标记类驱动）；transition 声明只挂在状态变化类上，静止态不保留过渡。这条改完，抖动消失，还顺手把”每次改样式都走一遍过渡”的隐性开销去掉了。

第四个是 -webkit-overflow-scrolling: touch 与内部动画打架。开启触控滚动加速后，滚动容器自己成为加速层，这时容器内部的 fixed 定位元素、或者也在做 transform 的子元素，会在滚动过程中抖动、错位甚至被裁掉；快速甩动时还会遇到惯性滚动结束后内容重绘。这些在 iOS 7/8 上都稳定复现过。当时的处置口径：确定要做惯性滚动的容器内部，不再嵌套常驻 transform 动画；表头一类需要固定的东西放到滚动容器外面，而不是靠容器内的 fixed；如果两者必须共存，只能真机验收，不能靠规范推。

顺带一句现场约束：这些坑里有一半是在微信内 WebView 里被用户反馈出来的。那时候安卓微信里的页面跑的是腾讯那套 X5 内核（也有回落到系统 WebView 的情况），它接不上我们的调试器，也没有远程 inspect 的便利手段，只能靠页面内打点加用户复现描述定位。这意味着度量工具的选择不只是”哪个更好用”，还要包括”现场接不接得上”。

与 JS 动画的边界

“目标值在写代码时就确定用 CSS，只有运行时才知道的用 JS”这条判据，加上桌面三者可用、移动端 CSS 优先、jQuery.animate 别上大量元素的实测结论，都在《CSS 动画与 JS 动画的性能取舍》里，本文不重复。这里只补一句前作说得太轻的话：有三种情形必须回到 JS，不要因为”CSS 便宜”硬凑。

滚动驱动是第一类。CSS 里没有”滚动进度”这个输入源，靠 scroll 事件逐帧写值只能走 JS——而且 iOS 的 scroll 事件在滚动期间会被节流，写出来的东西本身就是断续的，这时候反而要用 transform 把抖动压下去。物理惯性是第二类，速度到落点的连续求解、随时反手拽回，贝塞尔曲线表达不了。逐帧依赖数据是第三类，图表追赶、数字滚动、路径依赖接口返回值，插值端点在运行时才存在。这三类的正确解法仍然是混合：JS 算，CSS 播，所有权按前面那条规则交接。

还有一类边界值得单独点名：动画中途改目标值。transition 被打断时确实会从当前计算值继续，但你无法为”剩余路程”指定时长和曲线，观感是速度突变；@keyframes 更是从头定死。凡是要在播放中持续改目标的东西，就别提 CSS 了。

小结

本文的八条可执行清单，都是前面推出来的，不与前作的清单重复：

  1. 任何动画优化之前，先用 Timeline 的帧条确认钱在样式计算、布局、绘制还是合成哪一段；判读顺序在本文第三节，改错的代价是白改一轮。
  2. “transform 和 opacity 便宜”是有前提的：宿主元素必须有独立层。静止的、小块面积的动画元素不要常驻提层，动画结束后收回 translateZ 或 will-change。
  3. will-change 只在 Chrome/Firefox 有实现、Safari 与 IE 全无，写它必须同时写降级路径；永远不要写 will-change: all；它是临期提示，不是常驻声明。
  4. 层数是账单的一部分：一个层的显存按边界盒乘设备像素比计，超过单纹理上限就退化；快速滚动掉帧而主线程空闲时，先怀疑层爆炸而不是脚本。
  5. 逐帧动画优先改属性档位而不是改计时器精度：把 top 换成 transform 的收益，比把 setInterval 换成 rAF 大；两者都做才是完整方案。
  6. transitionend 会因前缀、多属性、冒泡、被打断、个别内核漏发而不回来。收尾一律用”事件加超时保底加标记位去重”，并按 propertyName 过滤；调用侧要有一条”新请求进来先落定旧状态”的规则。
  7. 首屏动画抖动先查渲染阻塞链和 transition 声明的挂载位置，再考虑别的；transition 只挂在状态变化类上，静止态不留过渡。
  8. 移动端坑不做桌面推断：iOS 8 上裁剪与 transform 冲突、-webkit-overflow-scrolling: touch 与内部动画打架、Android 4.4 内核只到 Chrome 33、微信内 WebView 接不上调试器——这四条决定了验收必须是真机加页面内打点。
