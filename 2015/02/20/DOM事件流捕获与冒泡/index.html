DOM 事件流：捕获与冒泡

前年到现在，我围绕事件委托写了三篇：《jQuery 的 on、off 与事件委托》讲库的 API 选型，《DOM 事件对象与事件委托》讲事件对象本身，《DOM 事件委托的边界情况》讲哪些事件接不住。留言里被问得最多的一类问题，其实都落在同一个地方：一次事件到底是怎么在树上走的？先走哪条路、后走哪条路、在哪一步可以被掐断、掐断之后还剩什么。委托的收益与选型前文都论证过，这里不再重复；本文把镜头拉回传播模型本身，只讲事件流的机制、顺序与边界。读者默认你已经会绑定事件、知道委托是什么，我们要弄懂的是它凭什么成立。

一趟下行与上行：三个阶段

一次点击不是”发生在某个元素上”，而是”沿着一棵树走完整一趟”。DOM Level 2 Events 把这趟路切成三个阶段：从 window 出发沿祖先链向下走的捕获（capturing）、到达目标节点自身的目标阶段（at target）、再沿同一条路向上回到 window 的冒泡（bubbling）。拿一个三层嵌套的结构看完整路径：

flowchart TD
    W[window] --> DC[document]
    DC --> HTML[html]
    HTML --> BODY[body]
    BODY --> OUTER[div outer]
    OUTER --> MID[div middle]
    MID --> INNER[span inner 目标]
    INNER -.冒泡回程.-> MID
    MID -.冒泡回程.-> OUTER
    OUTER -.冒泡回程.-> BODY
    BODY -.冒泡回程.-> HTML
    HTML -.冒泡回程.-> DC
    DC -.冒泡回程.-> W

实线是捕获下行，虚线是冒泡回程。两条结论要先记下。第一，捕获与冒泡是同一条路径的两个独立通道，绑在哪个通道上就在哪个通道收得到，互不串门。第二，window 与 document 也在这条路径上，所以无论目标节点埋得多深，只要事件真的派发了，绑在路径顶端的监听器一定先收到——这就是”外层抢先”的全部机制来源。

第三个参数：useCapture

addEventListener(type, handler, useCapture) 的第三个参数就是通道选择开关：传 true，处理器只注册到捕获通道；传 false 或者省略，注册到冒泡通道（目标阶段除外，下面会讲）。它是布尔语义，传数字或其他杂值会被按真假转换；想同时收两个通道，只能对同一个函数绑两次。

上面 demo 里第 4、5 两行是本文最想强调的一点：在目标元素上，捕获监听器和冒泡监听器的执行顺序按绑定顺序，而不是先捕获后冒泡。规范里捕获与冒泡的区分只在路径上的祖先节点生效；到了目标节点自身，两种注册方式的所有处理器会被一视同仁地按登记次序各跑一遍。你把 inner 那两行的注册顺序互换，输出就换成先 5 后 4。这个行为在 IE 9 到 11、Chrome 40、Firefox 35、Safari 7/8 上实测一致。很多人背了”捕获先于冒泡”就以为目标元素上的捕获处理器永远压过冒泡处理器，这是排查执行顺序类 bug 时的头号误判来源。

eventPhase、currentTarget 与 target

事件对象上的 eventPhase 告诉你处理器此刻站在趟路的哪一段：常量 1 是捕获、2 是目标、3 是冒泡（规范里对应 Event.CAPTURING_PHASE 等三个名字，但老浏览器不一定给这些常量名，直接用数字更稳）。currentTarget 是当前这个处理器注册在哪个节点上，target 是被真正命中的最深节点。捕获与冒泡阶段 currentTarget 一定比 target 位置高，只有在目标阶段两者相等：

两点边界要提。其一，currentTarget 只在派发期间有值，把事件对象存进异步回调里再读，标准浏览器会给 null——这条纪律《DOM 事件对象与事件委托》里已经说过，本文不展开。其二，IE 8 及更早的事件对象根本没有 eventPhase 和 currentTarget，因为那里压根没有两个通道，这一节的内容对老 IE 整体不适用，见后文。

掐断这趟路：stopPropagation 与 stopImmediatePropagation

stopPropagation() 掐的是后续路径：从调用点起，事件不再向树的其余部分前进，但当前节点上还没跑完的同阶段其余监听器照常执行。它掐的是整条剩下的路，不分通道——所以在捕获阶段调用 stopPropagation()，目标元素和冒泡通道上的所有处理器都收不到这次事件，一趟路的下行、目标、上行被一起作废：

sequenceDiagram
    participant D as document 捕获
    participant O as outer 捕获
    participant I as inner 目标与冒泡
    participant B as 上层冒泡
    D->>D: 收到, 继续下行
    O->>O: 调用 stopPropagation
    I-->>I: 从未被派发
    B-->>B: 从未被派发

stopImmediatePropagation() 比它多掐一层：连同当前节点、当前阶段里排在你后面的监听器也不执行。典型现场是同一个按钮上先后绑了 analytics 和业务逻辑两个 click 处理器，业务逻辑里调了这一句，analytics 就静默失踪。症状是”重新绑定顺序就能复现或消失”。这个方法 IE 9 才引入，IE 8 及以下完全没有；老代码在 IE 8 上的等价做法是一个节点每类事件只留一个总分发器，由分发器自己决定要不要遍历剩下的处理器列表——把多播的控制权收回手写代码里，这也是各家库在老 IE 上实现同序语义的通用路数。另外老 IE 里对应的属性是 window.event.cancelBubble = true，效果相当于 stopPropagation，对”同元素后续监听器”无计可施。

阻止传播与阻止默认动作是两件事

这组概念每年都要被人混一次，摆在一起说清：stopPropagation 管的是事件走不走完这趟路，preventDefault 管的是浏览器做完派发之后要不要执行动作本身（跳转、提交、勾选、滚动）。两者正交，互不包含。最容易踩的坑是：在冒泡链上调用 stopPropagation 以为链接就不跳了——照跳不误，因为默认动作看的是事件有没有被 cancel，跟你把传播掐在哪一段毫无关系。反过来 preventDefault 也完全不影响后续节点收不收得到事件。

取消默认动作在 2015 年有三套写法，各归各的模型管：

  • DOM2（addEventListener）：只认 e.preventDefault() 方法调用，处理器的返回值没人看，return false 什么都阻止不了。
  • DOM0（el.onclick = fn 与内联 onclick="..."）：按约定返回 false 等价于取消默认动作——注意，只是默认动作，不阻止传播。el.onclick = function () { return false; } 之后链接不跳了，但事件照样冒到 document，这是很多人觉得 return false “时灵时不灵”的原因。
  • 老 IE（attachEvent）：返回值一律不读，只认 window.event.returnValue = false。

跨浏览器写法还是老一套双保险，调方法、属性兜底，再用 e.cancelable 判断这个事件允不允许取消（并非所有事件都可 cancel，不可 cancel 的事件调 preventDefault 是空操作）。

IE 8 及更早：只有单程的路

微软在 IE 9 之前实现的是自己的事件模型，与 DOM 标准几乎处处不同：

  • 绑定用 attachEvent('onclick', fn) 与 detachEvent，事件名必须带 on 前缀。
  • 没有捕获阶段，事件只在目标与冒泡上走，eventPhase、currentTarget 都不存在，目标元素之外只有 srcElement（相当于 target）。
  • 处理器里的 this 指向 window，不是绑定元素。
  • 同一元素同类型多个处理器的执行顺序与标准相反，后绑的先跑；attachEvent 与 onclick 属性赋值混着用时顺序更乱，跨浏览器排查顺序问题必须以 IE 8 虚拟机实测为准。
  • 事件对象挂在 window.event 上，只在处理器执行期间有效。

捕获阶段到底什么时候用

排除了误用，捕获阶段真正不可替代的用法有这么几类。

外层抢先。 需要在目标及其下游的处理器跑之前记录或改写现场时，捕获是你唯一保证先跑的位置——下游谁能掐传播、谁改了 DOM 状态，都发生在你之后。埋点统计就属于这类：业务代码里第三方组件（日历、富文本编辑器）随手 stopPropagation 是常态，绑在冒泡通道上的统计代码会无故失踪，绑在捕获通道上则一个都漏不掉。

全局错误兜底。 2015 年能用的通道是 window.onerror，它在任何脚本错误冒不出处理器的地方兜底。搭配 window 上的捕获监听器，还能把”出错前最后一次用户操作”一起带上去：

拦截跳转与提交该用哪个阶段。 结论前面已经给了：拦默认动作只认 preventDefault，与阶段无关，捕获、目标、冒泡三个位置调用效果相同。要选阶段的依据只有一条——你想排在谁前面。想在所有业务处理器过手之前拦下误点的链接，把 preventDefault 绑在 document 或 window 的捕获通道；只想管自己容器内的那一次点击，绑在容器冒泡通道就够。表单提交的拦截别指望传播模型：submit 在老 IE 上不冒泡、form.submit() 根本不派发事件，绑 <form> 本身是 2015 年唯一靠得住的做法，这在旧文里论证过。

小结

事件流模型的全部骨架就是：一趟下行、一段目标、一趟上行；useCapture 选通道；目标阶段按绑定顺序一视同仁；stopPropagation 掐的是剩余路程且不分通道，stopImmediatePropagation 多掐同节点后续监听器且 IE 8 没有；preventDefault 与传播彼此独立；老 IE 只有冒泡单程，this、顺序、事件对象来路全不一样。把这几条装进脑子，委托、埋点、错误兜底都只是这条趟路上的不同站位而已。至于事件对象上还有哪些属性差异、委托怎么写生产级代码，去看《DOM 事件对象与事件委托》；哪些事件进不了委托管道，去看《DOM 事件委托的边界情况》。本文讲的是它们共同的地基。
