JavaScript 日期与时间处理实战

日期处理的文章大多写成 API 手册：getMonth 从零起算、setDate 能进位、注意闰年。这些结论都对，但背下来之后还是会踩到新的坑，因为坑不在 API 层，在实现层。本文换个角度，从 Date 对象内部到底存了什么讲起，把规范里的换算链摊开，让每个反直觉的行为都能被推导出来：为什么月份要减一、为什么 getTimezoneOffset 的方向是反的、为什么同一个字符串在不同浏览器解析出不同结果、为什么 setInterval 会越来越慢。读完你手里会有一条清晰的换算链、一组 ES5 可用的解析与格式化函数，以及一套“什么时候用时间戳、什么时候才落时区”的分工原则。文中的断言都在 Node 里按东八区与纽约时区实测过，实测值和浏览器年代以 2015 年初为准。

Date 实例里只有一个数

ES5 规范 15.9 章把 Date 定义成一个几乎没有状态的包装对象：每个实例只有一个内部属性 [[DateValue]]，它是一个 Number，含义是“距离 1970-01-01 00:00:00 UTC 过去的毫秒数”。除它之外没有年、月、日、时区任何一个字段。范围被限制在 ±8.64×10^15 毫秒（约前后 27 万年），精度 1 毫秒，超出或解析失败就取 NaN，这样的实例叫 Invalid Date，任何 getter 都返回 NaN。

于是整个 API 面被这一句话决定了形状。getTime() 是把 [[DateValue]] 原样交出来，这是唯一一个不碰时区的读取方式；而 getFullYear、getHours 这一族本地 getter，规范写的是两步算法：先做一次“本地时间换算”，再从换算结果里取出对应的字段。

flowchart TD
  A[系统时钟] --> B[DateValue 内部毫秒数]
  B --> C[getTime 原样返回]
  B --> D[LocalTime 本地时间换算]
  D --> E[getFullYear 与 getHours 等本地 getter]
  B --> F[getUTCFullYear 与 getUTCHours 等 UTC getter]
  D --> G[getTimezoneOffset 由同一次换算反推]

这条链给出本文最重要的一个分工原则：时刻与时区无关，格式化才与时区有关。同一个 1425018471000，也就是北京 2015 年 2 月 27 日 14 点 27 分 51 秒、UTC 06:27:51，在北京的浏览器和在纽约的浏览器里 getTime() 完全相同，不同的只有 getHours（纽约是 1 点）。所以传输和存储应该用毫秒时间戳或带时区标记的 UTC 串，把时区留到展示层最后一步再落，中途任何时候把它“洗掉”都会出错。

对象到原始值那一套 valueOf 与 toString 的推导规则，笔者在《JavaScript 数据类型与类型转换详解》里完整走过（结论是 Date 在无 hint 时偏偏按 string 走），本文只取一句：比较日期一律显式取数字，别指望隐式转换。

四种构造入口与两套进位

new Date() 取当前系统时间。new Date(milliseconds) 直接把数字塞进 [[DateValue]]，不做任何换算，这是最干净的一个入口。new Date(y, m, d, h, m, s, ms) 走反向路径：先按本地时区把这几个字段拼成一个时刻，再存成毫秒——月份从 0 起算，1 月是 0。第四个入口 new Date(dateString) 最危险，下一节单独讲。

0 基月份不是哪个工程师的恶趣味，它是进位机制的副产品。规范里年月日是通过 MakeDay 这套纯算术从时间戳里拆出来的，月份作为一个 0 到 11 的“索引”参与进位最省事：加满 12 就进位到年。正因为进位发生在这一层，构造参数越界不会报错，而是自动顺移：

这是好事：算“三个月后的今天”“上月最后一天”这种需求，直接 setMonth(d.getMonth() + 3) 或者 new Date(y, m + 1, 0) 就拿到了上月末，完全不需要手写那张每月天数表和闰年判断。用 new Date(y, m + 1, 0) 取月末这一招，笔者建议写进团队规约，比 getDaysInMonth 之类的自制函数可靠得多。

需要防的是相反方向：字段读出来时它是 0 基的，写回构造器时还是 0 基的，中间只要有一次“当成 1 基”的错觉，日期就整体偏一个月，而且偏得很安静——不报错、不产生 Invalid Date，只有业务方看出来。写日期加减的代码时，在 getMonth 与 new Date 旁边各标一句“此处 0 基”比什么都管用。另外 getYear 返回的是年份减 1900（2015 年给 115），这是历史遗留，别用。

字符串解析：唯一实现相关的入口

规范 15.9.3.1 和 15.9.4.2 对构造器和 Date.parse 只提了一个强制要求：能识别 ISO 8601 的简化形式。紧接着原话是“其他格式属于实现相关行为”。也就是说，new Date(字符串) 是唯一一个规范明确允许各家实现自行其是的入口。当年所有日期 bug 的产地都在这里。

先说 ISO 形式内部那条最别扭的不对称：只有日期没有时间的形式，按 UTC 零点解析；一旦带上时间，就按本地时区解析。

同一天在纽约的机器上更难看：new Date('2015-02-03') 的本地结果是 2 月 2 日 19:00，getDate() 直接回退一天。东八区只是运气好，因为偏移方向和日期边界的方向刚好抵消到同一天。一个“活动开始日期”字段这样解析出来，跨时区做倒计时就早 8 小时或者差一整天。

再看非 ISO 形式。new Date('2015/02/03') 走实现相关分支，各家行为是本地零点，和上面那个 UTC 零点差了整整 28800000 毫秒——同一个日期，斜杠与连字符两个写法差 8 小时，光看代码很难察觉。自定义格式就更不能碰了：'2015-02-03 14:00'（空格分隔）在 Chrome 40 与 Firefox 35 上能解析，在 iOS 7/8 的 Safari 上返回 Invalid Date；带 T 与 Z 的 ISO 串在 IE8 及更早版本里同样解析失败。这些差异全是规范那句“实现相关”授权出来的，不是谁的 bug。

时区：分钟、反方向、不可设置

getTimezoneOffset() 返回“UTC 时间减去本地时间”的分钟数，所以东八区是 -480，西五区是 +300。方向和直觉相反，但看它的规范定义就顺了：它等于 (t - LocalTime(t)) / 60000，也就是把上一节那条换算链倒过来除以一个 60000。由此还能推出一个容易忽略的事实——它是按这个时间戳算出来的，不是环境常量。换两个不同时刻的实例，答案就会不一样：纽约的浏览器里 2 月 15 日那个时间戳返回 300，7 月 15 日返回 240（夏令时期间）。所以任何时候想用偏移量，都要从目标时间上现取，不要在页面加载时缓存一份。

客户端时区在 2015 年依然是不可设置的。没有 API，V8 里连 setTimezoneOffset 这个方法都不存在（typeof 出来是 undefined），网上流传的给 Date 原型打补丁的写法，本质上是在重写所有 getter，工程上不可维护。改系统时区只是测试手段，不是产品手段。要显示别地时间，只剩手动加偏移这一条路：

手写 format：2015 年绕不开的一步

先说为什么当年的三个现成方案都不能用。toISOString() 输出的是 UTC 串（本地 14:27 得到 2015-02-27T06:27:51.000Z），不带本地时区信息，而且 IE9 才有；Intl.DateTimeFormat 当时 IE11 只算部分支持、中文 locale 数据在若干浏览器上残缺，写进主干代码等于放弃 IE8；toLocaleString() 是各浏览器输出差异最集中的地方，同一个时间能给出 2/27/2015, 2:27:51 PM 或 2015/2/27 14:27:51 之类完全不同的形态。顺带一句，Date.prototype.toString 的输出格式在 ES5 里同样是实现相关的（到 ES6 才被钉死），它只能用于调试打印。展示一致性要求高的场景，比如报表表头、倒计时、对账单日期，只能自己格式化。当时很多团队的做法是手写一个 format 丢进公共库，或者在 Underscore 模板里挂个 helper，本文给一个能直接抄走的 ES5 实现：

小结

Date 只有一个内部状态，剩下的都是它的投影：getTime() 读到的是本体，本地 getter 读的是“本体加时区换算”的结果，于是时刻与时区无关、格式化才与时区有关成为全文的分工基线。构造器的 0 基月份和自动进位是同一套日历算术的两面，用好了能省掉整张月末天数表；字符串解析是规范明确授权各家自行其是的入口，'2015-02-03' 按 UTC 零点、'2015/02/03' 按本地、空格分隔形式在当年的 Safari 直接失效，所以自定义格式一律手工拆字段重建。getTimezoneOffset 给的是方向相反且随时间戳变化的分钟偏移，客户端时区不可设置，跨时区显示只能手动加偏移，而且产物是只能用于展示的假 Date。格式化在 2015 年绕不开自己写：toISOString 只有 UTC、Intl 支持残缺、toLocaleString 各家不同。比较用 +date，跨天除法要 Math.round，当天零点用构造器而不是取模。计时上 Date.now() 需要 +new Date() 降级，setInterval 的漂移只能靠排班式 setTimeout 补偿，能拿到 performance.now 就用它。把这些行为归位到“时间戳、换算、展示”三层，日期这活儿就从背 API 变成了推链条。
