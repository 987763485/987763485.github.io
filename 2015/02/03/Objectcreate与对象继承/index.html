Object.create 与对象继承

2014 年 11 月，我把一个内部表单控件的继承写法从 Dog.prototype = new Animal() 换成了 Dog.prototype = Object.create(Animal.prototype)。改动不到二十行，测试环境一片绿灯，上线三天却陆续收到四个 bug：有一个键死活查不出来、有一个方法无论怎么覆盖都不生效、有一个把用户的参数写进了原型、还有一个在 IE8 用户的机器上直接白屏。回滚之后我拿 ECMA-262 第 5 版 15.2.3.5 那一条对着各家浏览器逐个参数实测了一遍，才发现我之前是把 Object.create 当成「不用写 new 的构造函数」在用，而它的语义其实只有一句话：造一个对象，把它内部的原型接上你给的那个东西，仅此而已。

这篇就是那次复盘的整理，按踩坑的顺序写。原型链怎么逐级查找、prototype 与 __proto__ 各自是什么、new 拆成四步之后每一步做什么、属性描述符四个字段怎么组合，这几件事我在《JavaScript 原型与原型链完全解析》和《new 操作符到底做了什么》里已经推导过，本文不重复，只借用它们的结论。

坑一：第一个参数只认对象和 null

我最初的理解是「第一个参数随便给，反正引擎会帮我处理」。实际规则很硬：ES5 规定第一个参数要么是对象（函数也算对象），要么是 null，其余一律抛 TypeError。跑一圈就能看清边界：

那次 bug 里最隐蔽的一个来自 undefined。我当时写了一个继承小工具，父型可能没传，就想当然地用了 Object.create(parent)，指望它给我一个「什么都没有」的起点。结果是页面一进入那条分支就整块报错。要空原型必须显式写 Object.create(null)，一个字符都不能省；不传参数等价于传 undefined，同样抛错。哪怕某些引擎后来的草案里对这种写法的归类不那么严格，跨环境行为也不再一致——显式 null 是唯一没有歧义的形式。

flowchart TD
  A[Object.create 的第一个参数] --> B{是对象或函数吗}
  B -->|是| C[把它当作新对象的原型]
  B -->|否| D{是 null 吗}
  D -->|是| E[得到一个没有原型的对象]
  D -->|否| F[TypeError]

另一个误解更值得说：函数是合法参数，但传函数进去得到的东西和 new 出来毫无关系。

Object.create(Person) 的链条是「wrong → Person → Function.prototype → Object.prototype」，构造函数那句 this.name = name 从未执行，Person.prototype 更是压根不在链上。这类错误写成 Object.create(Person()) 也一样不对——那是调用函数而不是接原型。

坑二：Object.create(null) 的干净是要付钱的

Object.create(null) 造出来的对象原型链在第一环就断了，这是我最喜欢的特性，也是踩坑最密集的用法。第一个坑：它没有 toString、没有 hasOwnProperty、没有 constructor，任何「默认对象都有」的假设都不成立。

最后那行加法是我实际踩到的：日志里习惯性地把对象拼进字符串，普通对象走 toString 得到 [object Object]，干净字典两个方法都找不到，直接在控制台报转换错误。JSON.stringify 倒是能正常工作，因为它读的是自身属性，不依赖 toString。

付了这笔钱换来什么？换来它做映射表时不会被键名污染。我那个「键死活查不出来」的 bug 反过来验证了另一半：当时收集 URL 参数用的是普通对象字面量，而某个查询串里带了 callback 之外的 constructor，代码里的判断写成「取到值就用」，于是凭空命中了原型上的函数。

换成 Object.create(null)，这三个键全部查无此人，lookup 的语义才真正等价于「映射里有没有」。还有一点很讨喜：普通对象上 map['__proto__'] = 'x' 会被 Object.prototype 上那个访问器截走，既存不进键值，还可能悄悄改掉原型；干净字典身上没有这个 setter，__proto__ 就是一个老老实实的普通字符串键。代价是这套安全性只属于原生实现，降级环境里并不存在，下面会说。

复盘之后我给自己定了一条：第二个参数只在「需要精确控制可枚举性」的场合用，比如把 constructor 修回自身并设成不可枚举；其余场景一律先 Object.create(proto) 再逐属性赋值。省得四个默认 false 全踩一遍。

坑四：它不调用任何构造函数

这是 Object.create 和 Dog.prototype = new Animal() 的本质区别，也是那个「参数写进原型」bug 的根源：Object.create 只负责接原型，构造函数一行都不会执行。new 那四步的拆解另文已经写过，这里只需要记住——Object.create(proto) 大致只对应其中的第二步。

所以判断标准还是旧文里那一条：方法和不变的常量放原型，需要独立副本的引用值放构造函数。顺带一句，Object.create(source) 拿来当「复制对象」用也是同一类误解——它只是接了个原型，source 之后改动会顺着链露出来，而且新对象身上没有任何自身属性，hasOwnProperty 一个键都不认。

复盘清单

把上面五个坑回炉一遍，我现在的取舍是这样的：

场景 我的选择 理由
给子类接父类原型 Object.create(Parent.prototype) 加构造函数里 Parent.call(this, ...) 不触发多余的构造调用，实例属性各自一份
修 constructor 第二参数写全四个描述符字段，enumerable 设 false 与内置行为一致，for in 不会把它带出来
纯映射表、键名来自不可信输入 Object.create(null) 加 hasOwnProperty.call 不会被 constructor、toString、__proto__ 污染
只要一个原型链上的哨兵对象 Object.create(null) 链在这里终止，查找不会越界
需要实例初始化、参数复杂 老老实实 new 加构造函数 构造过程本身就是需求，绕开它反而要多写 call
要「复制」一个对象 不用 Object.create，走显式拷贝 接原型不等于复制，引用还会共享

再压缩成三条铁律：第一个参数只写对象或 null，永远不要拿 undefined 碰运气；判断自身属性一律 Object.prototype.hasOwnProperty.call，尤其是在可能是干净字典的对象上；用了 Object.create 就要自己负责把实例属性补齐，它不会替你执行任何构造函数。至于 new 到底怎么一步步把对象造出来、Object.defineProperty 的描述符规则从哪来，这两块另文已写，本文刻意没有展开。

小结

Object.create 的全部语义就是「新建对象，把内部原型接上你给的参数」，第一参数限定为对象或 null，第二参数是属性描述符的映射，两个限制都容易凭直觉写错。Object.create(null) 给了我做映射表最干净的底座，代价是 toString、hasOwnProperty 一并消失，所有判断得改成借来的 hasOwnProperty.call；第二参数的四个字段默认全是 false，让属性「看着存在却写不进、删不掉」；它不会调用任何构造函数，所以拿来接原型时必须自己用 Parent.call(this) 补实例属性，而共享引用的风险只是从原型挪到了构造函数之外，并没有消失。IE8 的 polyfill 用闭包加 new F() 能把链条接上，却补不出真正的空原型，这种「老浏览器跑得通、新浏览器抛错」的方向性差异，只能靠统一写成 Object.prototype.hasOwnProperty.call 和显式的 null 参数来消除。把这几条当纪律固定下来，Object.create 才算是会用。
