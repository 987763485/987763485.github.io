JavaScript 作用域链与执行上下文

上一节我们把 this 拆成了四条绑定规则，这一节换一个更底层、也更常被讲混的对象：执行上下文与作用域链。它们决定了两件在排查线上问题时最要命的事——一段代码此刻”能看见哪些变量”，以及”这些变量活多久”。绝大多数看起来玄学的 bug，比如赋值赋到了别人身上、闭包里的值全是最后一次循环的结果、递归跑一万层就爆栈，本质都是这套机制在按规矩办事，而写代码的人对它有一处误解。

所以本文的写法还是那套老规矩：先把机制讲到底层，把每条规则的边界和优先级说清楚，给出判断题让你自己先答一遍；然后把几种常见写法放到一起做对比和选型，明确什么场景该用哪一种、代价是什么。全文只使用 ES5 语法，代码都在 Chrome 40、Firefox 35、IE 8/9/11 上跑过。涉及引擎实现细节的部分，我只讲方向性结论，不去断言某个具体版本的性能表现——2015 年这个时间点，各家内核还在快速演进，把今天测出来的倍数写进文档，半年后就是误导。

执行上下文：进入一段可执行代码就建一张记录

ECMA-262 第五版把 JavaScript 代码分成三类：全局代码、函数代码、以及 eval 代码。每进入其中一类，引擎就创建一个执行上下文（Execution Context），里面至少要放三样东西：变量对象（记录当前作用域能直接访问的绑定）、作用域链（决定往上找谁）、以及 this 的值。

三种上下文的区别就在”变量对象从哪来”和”作用域链怎么排”：

  • 全局上下文只有一个，在脚本开始执行前由引擎建好。它的变量对象就是全局对象本身，浏览器里就是 window。这意味着全局作用域里 var 出来的变量，其实是挂在 window 上的属性——这个事实是后面很多麻烦的源头。作用域链里只有它自己一层。
  • 函数上下文每调用一次函数就新建一个，同一个函数被调用三次，就有三张互相独立的记录。它的变量对象初始是 arguments 对象加上一组形参，作用域链在最前面插入这一份，后面接上定义它的那个上下文的作用域链。注意最后这半句：链条接的是定义时所在的环境，不是调用时的环境。
  • eval 上下文只作为历史注脚提一句：eval 里再执行代码时也会建上下文，非严格 eval 直接借用调用它的那个函数的变量对象，所以它能在原地往别人家的作用域里塞变量。这个能力后来被认定是设计缺陷，ES5 的严格模式给它加了独立作用域，ES6 草案（当时还叫 Harmony，靠 traceur 这类转译器体验）更是打算把它彻底圈起来。实践中你不需要用它，本文只在讲”污染”那一节把它请出来当反例。

这些上下文不是散放着，而是按调用顺序压进一个栈，通常叫执行上下文栈（ECStack），也就是大家说的调用栈。下面这张时序图走一遍两层嵌套调用，把”压栈—出栈”和变量的可见性对上：

sequenceDiagram
  participant S as 执行上下文栈
  S->>S: 页面脚本开始 压入全局上下文
  S->>S: 调用 init 压入 init 上下文
  S->>S: init 内调用 bind 压入 bind 上下文
  S-->>S: bind 返回 bind 上下文出栈
  S->>S: init 内注册回调 栈内仍是全局与 init
  S-->>S: 回调触发时才压入新的匿名上下文
  S-->>S: init 返回 init 上下文出栈
  Note over S: 栈回到全局上下文 被引用的活动对象仍存活

最后一行那句 Note 是本节最重要的补充：上下文出栈不等于它的变量消失。栈只是执行流程的记录，变量对象是一份可以被引用拖住的数据结构。这个区别在讲闭包那一节会展开。

另外两条现实约束值得现在就说。第一，这个栈深度有限，而且各浏览器给的额度不一样，桌面 Chrome 大致能到几千到一万层，IE 明显更低，移动端浏览器又比桌面同版本低一截，超出就抛 RangeError: Maximum call stack size exceeded。所以”数据规模未知的时候不要写成递归”不是风格洁癖，是可用的经验。第二，异常同样会出栈。try 里抛错、一路 catch 到某一层，中间那几张上下文全部作废，这就是为什么在 catch 块里读到的一切，都是最近一次还在执行的那层作用域的值。

变量对象与活动对象：把创建和执行分开

规范里的名词有点绕，但拆成两阶段就清楚了。函数上下文刚创建时，那张表叫变量对象（Variable Object，VO），里面只有 arguments 对象和一组形参名；等到这一步走完，引擎在表上补上 this（以及各内核历史上私有的 caller 之类），补全之后的这份表就被叫做活动对象（Activation Object，AO）。所以 VO 和 AO 不是两张表，是同一张表的两个状态：登记完形参是一个状态，登记完声明是另一个状态。写代码的人只需要记住一句：这张表是分批填的，而填表发生在两个截然不同的时刻。

创建阶段做三件事，顺序固定：

  1. 拿到 arguments 对象。哪怕你没写任何形参，它也在。
  2. 按声明顺序处理形参：为每个形参名建立一个绑定，值就是这次调用传进来的实参；没传的参数值为 undefined。
  3. 扫描函数体，把函数声明和 var 变量声明登记进这张表。函数声明连同函数对象一起写入；var foo 只保证”foo 这个名字存在”，只有在同名绑定还不存在时才置为 undefined。

执行阶段才做赋值：foo = 1 这种真正的初始化，以及把表达式算出来、把函数调起来。

所谓”提升（hoisting）”，就是这两阶段时间差的口语说法。它不是什么魔法，只是”登记”和”填值”分了两步。理解到这里，就能推出几条铁律：var 声明提升到函数顶部，但等号右边的值不提升；function 名字和函数对象一起提升；if、for、try 里的 var 一样提升到函数顶部，因为 2015 年的 JavaScript 根本没有块级作用域这一层。

同名的博弈：四种声明谁赢

创建阶段那三步里藏着一套优先级。把它写成一句话：arguments 最先落地，函数声明可以覆盖同名的形参，而 var 声明谁也不覆盖。展开成规则清单：

  • 形参与函数声明同名：函数声明赢，因为它在第二步之后才写表。
  • 形参与 var 同名：形参赢，var 看见名字已经存在，直接跳过。
  • 函数声明与 var 同名：登记阶段写进去的是那个函数对象（它是唯一带着值来的声明），执行阶段走到赋值表达式时才被右边的值覆盖。所以口诀是”初始值看声明、最终值看赋值”，两条语句谁写在前面并不影响登记这一步。
  • 要分清函数声明与函数表达式：只有 function foo () {} 这种独立成语句的声明参与登记；var foo = function () {} 里的右边不过是一次赋值表达式，foo 在创建阶段只是 undefined。这一条差别就是”调用一个写在后面的函数表达式变量会报 undefined is not a function，而调用后面声明的函数没事”的全部原因。
  • 重名形参（非严格模式允许 function f(a, a) {}）：最后一次实参生效，而 f.length 只算到第一次出现的位置。

下面几道判断题建议先自己给出答案再看解析，它们都覆盖了我踩过的坑。

题一：console.log(typeof foo); function foo () {} console.log(typeof foo); 打印什么？
两个都是 function。函数声明连同对象在创建阶段就进了表，所以第一行 log 时它已经可用。

题二：var foo = 1; function foo () {} console.log(foo); 输出什么？
输出 1，而不是函数。创建阶段先登记了 foo（值来自函数声明），执行阶段第一句赋值把 1 写了进去。这正是”初始值看声明、最终值看赋值”的意思。

题三：console.log(foo); var foo = 1; function foo () {} 第一行打印什么？
打印那个函数对象，不是 undefined。很多人以为”var 排在前面所以赢”，其实登记顺序不影响函数声明的优先级——它在扫描阶段就带着值写进表了。

题四：下面这个函数返回什么？

解析：var value 的声明在创建阶段就登记进 AO，与 if 走哪条分支无关；else 分支提前 return 时，赋值从未发生，所以是 undefined 而不是报错。这道题的关键在于把”提前返回”和”没声明”分清楚——提前返回只跳过了执行阶段的赋值。

题五：function f (a) { var a = a || 'default'; return a; } 传 f('') 返回什么？
返回 'default'。形参 a 是空串，|| 判定它是假值，于是把默认值盖了上去。这是 || 做默认值的典型误伤，后面的选型章节专门讨论它。

题六：function f () { console.log(typeof a); return; var a = 1; } 打印什么？
undefined。return 之后的 var 依然被登记（扫描是整段函数体一起扫的），只是永远不会被赋值。

还有一个特殊变体值得单独一提：块里的函数声明到底登记在哪一层。

这是我在本文里唯一不敢说”三个浏览器结果相同”的片段。块内的函数声明在 ES3/ES5 早期是个规范空白：有的内核把它提到函数顶部，于是第一行就是 function；有的内核真把它圈在块里，于是 flag 为 false 时它压根没登记，第二行反而变回 undefined。老 IE 的行为又和上面两种都不一样，还会额外泄漏一个名字到外层。规矩因此非常简单：条件分支、循环体里不要写函数声明。需要按环境挑实现，就写成”先 var 声明变量、后赋值函数表达式”，或者干脆用惰性函数定义——那套写法我在《JavaScript 惰性求值与缓存优化》里已经给过完整实现，这里不重述。

作用域链在定义时就定死了

现在进入本文最容易误解的一节。函数上下文的链头是它自己的 AO，后面接的是这个函数被定义时所在上下文的链，一层层往上，最后一定以全局对象收尾。它跟这次调用是谁发起的、以什么形式发起的，一点关系都没有。

三段调用里 this 各不相同：第一段走成员绑定拿到 host，第二、三段分别是默认绑定与显式绑定（判定过程见《this 指向的四种绑定规则详解》，本文不重复推导）。但函数体里没有一处用到 this，它读的是 tag，而 tag 沿链在 makeGetter 的活动对象上就被命中了，压根轮不到全局那个 tag。this 是动态的、跟着调用点走；作用域链是静态的、跟着书写位置走。两套机制互相独立，谁也不参与谁的判定——这句话是本文最想让你带走的东西。

标识符解析：越深越慢，以及局部缓存为什么有效

一个名字沿链一级一级往上找，找到即停。所以代价由两件事决定：命中在第几层，以及这一层是什么形态。全局作用域那一层最亏——它通常是真正的对象，查找要走属性查找流程，比函数作用域那种按槽位取的绑定慢一截。这就是”document 用得多了要缓存”这条老规矩的底层理由。

至于”引擎会怎么优化这些查找”，2015 年这个时间点我给的口径是：只讲方向，不讲结论。原因是各内核的作用域实现路径差别很大，而且都在演进。大致能说的是：现代内核会给作用域链上的变量做”上下文槽位”式的存储，同一个函数里对同一个名字的重复引用可以被固定成一次寻址；深链上的引用与全局属性访问的相对代价，会随着内联、方法 jit、以及某些情况下触发的去优化而变化。于是”闭包里的变量访问一定比局部变量慢””全局变量访问慢十倍”这类说法，都不能一概而论——它们在某个版本、某段代码形态上成立，换个内核、加个 try/catch 或者一次 eval 就可能反过来。真要下结论，就在你要支持的那几个内核上自己测：预热、多轮、取中位数、让结果参与运算防止整个循环被当成死代码删掉，这套姿势我在《arguments 对象与 callee、caller》里写过一份能直接抄的计时片段，不重复贴了。

比性能更要紧的是深链本身的可读性代价。链上每一层都是一个可能的覆盖点，层数一多，”这个名字到底来自哪一层”就变成了需要通读全文才能回答的问题。下面的污染章节会给出两个真正会让链查找结果失控的写法。

展望一句：ES6 草案（Harmony 阶段，靠 traceur 转译体验）会带来块级作用域声明，届时 {} 里的绑定真正独立成一层，with 与 catch 的这类差异会一起被规范掉。但 2015 年 2 月，别在项目里赌它。

闭包：被引用的活动对象不肯退场

前面所有铺垫都是为这一句：闭包不是”函数记住了变量”这种拟人化的东西，而是”某个函数的作用域链指向了一份活动对象，这份对象因为被引用着，不能随着出栈而释放”。回到本文的时序图：init 返回时它的上下文出栈了，栈上只剩全局——但只要那个注册给 click 的匿名函数还活着，init 的活动对象就还活得好好的，它上面的 settings、list、临时数组全都算活着。

然后是那个每年都要重新踩一遍的循环题：

按前几节的语言解释：var i 的绑定在外层函数（或者全局）的活动对象上，只有一个；五个回调的作用域链都指到那一份，所以它们读到的必然是同一个、循环结束后的值。加一层立即执行函数，等于给每轮多插一个上下文，形参 captured 在创建阶段第二步就被赋值成当时的 i，形成五份互不相干的私有状态。这个技巧跟 IIFE 的语法变形是两件事，后者（各种前缀写法的差异、ASI 拼接事故、模块模板）在《IIFE 立即执行函数表达式》里已经讲全，本文只借用它的作用域效果。

闭包的代价也要如实说：链上被留住的不只是你需要的那个变量。规范层面，整个活动对象都在链上；实现层面，内核会按槽位保留，未被引用的变量在某些引擎里可以被丢掉，但这个”某些”当年并不可靠，所以别把”局部变量反正会被回收”当成设计依据。真正省心的做法只有一条：闭包只捕获它需要的东西，大数组、DOM 列表这类要么提前裁成需要的数字，要么在销毁入口显式断掉引用（list = null），后者跟事件解绑是同一件事的两端，细节见《DOM 事件移除与内存泄漏》。

四组对比与选型

机制讲完了，这一节回答”那到底该怎么写”。四组都是日常会碰见的岔路口，每组给一份取舍表和一句结论。

隐藏状态：全局挂载 / 闭包私有 / IIFE 传参模块

同一个”记住当前选中项”的需求，三种写法：

方案 隔离强度 可测试性 调试成本 多实例 内存回收 适用场景
全局挂载 无，任意脚本可读写 差，状态跨用例残留 低，控制台直接看 需自造命名空间 挂到 window，页面活着就活着 一次性埋点标记、调试开关
闭包私有 强，只能走 API 中，需要额外 reset 入口 中，值看不见 否，天生单例 随模块引用存活 单例工具、配置缓存、计数/节流
IIFE 传参 强 + 外部依赖可替换 良，可注入假的 storage 中 改造工厂函数后良 显式销毁接口可断开 有外部依赖的库代码、需要 mock 的模块

选型结论：默认走方案二，它是成本最低的隔离；只要这段状态和 window、document、第三方库有交互，就升到方案三，把依赖从形参注进来，测试时可以换掉——这也是 jQuery 源码自己在用的一层。方案一我只留给自己：调试期间临时看一眼的东西、以及确定不会有第二个脚本撞名的常量。团队协作里把它当”禁止项”处理更省事，因为它的失效方式不是报错而是静默串值，排查一次的时间够写三遍方案二。想同时要多实例、又要有继承，那就别用闭包藏状态，改成构造函数把状态挂在实例上，这是《this 指向的四种绑定规则详解》里那条路线的正面。

默认值：x = x || 10 还是 typeof x === 'undefined'

|| 的判据是假值集合：0、''、false、null、undefined、NaN 全在里面。所以只要默认值语义是”没传就用默认”，|| 就是错的；只有当默认值语义是”给我一个可用的东西，脏值也归正”，|| 才对。用 typeof 而不是 x === undefined，是为了防外层把全局 undefined 覆写掉——那是历史遗留（IE 8 及以下的 undefined 是可写属性），ES5 之后已经不是问题，但 typeof 顺带还能兜住”名字压根没声明”的情况，成本一样，我就统一用它。

写法 对 0 与空串与 false 能否区分”没传”和”传 undefined” 可读性 备注
短路赋值 误伤 否 高，一眼看完 语义是”归正脏值”时才对
typeof 判断 不误伤 否（两者同义） 中 默认选择的写法
arguments.length 不误伤 是 低，下标脆弱 唯一能表达”根本没传”的工具，代价是牵动 arguments

选型结论：可选配置项一律 typeof 显式判断；参数超过三个就改成配置对象，把默认值集中写成一个 defaults 再合并，这样”哪个字段允许 0/false”变成表格里能审的东西；只有第三种（arguments.length）留给真正的双语义场景，比如函数需要区分”调用者忘了传”和”调用者显式传了 undefined”，这时它是唯一能表达这个区别的工具，代价是它牵动 arguments 的那笔开销，方向见旧文。

动态代码：eval / new Function 还是静态查表

方案 编译时机 作用域影响 性能 安全 可调试性
eval 每次调用 非严格时直接借用当前活动对象，令该函数难以优化 最差 注入面最大 栈里只有 eval 帧，定位困难
new Function 每次调用 链上只有全局，不碰当前作用域 差，但比 eval 少一层伤害 同样有注入风险 稍好
静态查表 加载时一次 无 好，属性访问而已 白名单可控 名字与断点都在

选型结论：默认静态查表。需要”按类型分派”的时候，一个键值对象加一次 hasOwnProperty 校验（别忽略这一步：'constructor' in formatters 会是真，直接下标取会拿到 Object 的构造器）就够，比任何动态代码都快也安全。new Function 只在真的必须生成代码结构时才用，比如模板编译器那一类，而且参数名与代码体都得自己过一遍白名单校验；它能比 eval 少污染当前作用域，仅此而已，不构成”用它更安全”的理由。解析数据这件事从来不该用 eval：JSON.parse 是 ES5 就标准化的（IE 8 要用 json2 兜底，但那是 2015 年很成熟的兼容路径），语义清楚、失败就抛错，比 eval('(' + text + ')') 那种写法可靠得多。

递归展开作用域链：一路下钻还是改成循环

维度 递归 循环 + 显式栈
可读性 与树形定义同构，最短 需要多写一个数组，但一眼可知过程
栈风险 高，深度未知就是未知 无，数组只吃堆内存
每层内存 一份活动对象 + 链 一份数组元素
标识符解析 链逐层变长，深层读外层更贵 恒定一层
调试 栈信息天然完整 需要打印自己的 stack 数组

选型结论：深度已知且小（比如 DOM 层级、语法树解析这类，通常几十层封顶）用递归，它写得最短、栈信息最完整；深度由数据决定的一律改循环 + 显式栈，因为浏览器给的额度不是常数——桌面与移动、各家内核都不同，而且用户页面的数据量从来不受你控制。递归里还有一个跟本文主题直接相关的开销：链的长度是按调用栈叠上去的，越深的层里读一个外层配置变量，要走的级数越多；把每层真正需要的东西当参数传下去（像上面 walk 的 depth 那样），比让它去链上找更稳定，也更便宜。另外别指望尾调用优化来救你：2015 年初只有个别内核在严格模式下试探性地做了一点，跨浏览器不可依赖。

落到工程上的六条规约

把上面的机制与选型压成能贴进 wiki 的检查项：

  1. 函数顶部的 var 只写声明、把赋值留在原处，或者干脆声明与赋值同行但保证这行一定会执行；不要靠”提升到函数顶”来解释一个提前返回后面还读得到的值。
  2. 条件分支、循环体里不写函数声明；按环境挑实现时用”变量 + 函数表达式”，或者惰性函数定义那套写法。
  3. 项目里禁止 with；catch 的形参必须带语境命名，用完显式断开引用。团队配置里把 with 和 undef 两条检查打开，比约定管用。
  4. 私有状态默认用闭包，外部依赖用形参注入；全局挂载只允许出现在一次性调试里，并且写在 PR 描述里说明为什么。
  5. 可选参数默认值一律 typeof x === 'undefined'；三个以上参数改配置对象，把允许 0/false 的字段集中在 defaults 表里接受审阅。
  6. 数据规模未知的遍历一律循环加显式栈；热函数里的全局引用做一次局部缓存，但任何”快了多少倍”的结论都要在你真正支持的那几个内核上重测，别抄别人的数字。

最后回到本文最想让读者建立的直觉：一段代码里能出现哪些名字，在你写下这个函数的那一刻就已经定好了，跟它将来被谁调用、挂在哪个对象上、被 bind 到哪个上下文毫无关系；而这份”能看见的名单”会不会一直活着，取决于有没有函数还引用着它。this 决定的是”我这次代表谁”，作用域链决定的是”我能叫到谁的名字”。这两句话各管一半，混着记就会一直踩坑。至于链条在引擎里具体怎么被寻址、哪些写法会让一次查找变慢，那是一个必须用实测回答的问题，本文刻意没给出任何”某版本快几倍”的数字——2015 年写下来的这种数字，往往到 2016 年就已经是错的。
