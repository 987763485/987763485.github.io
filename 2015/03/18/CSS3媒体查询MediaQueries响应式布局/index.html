CSS3 媒体查询 Media Queries 响应式布局

本文属于《HTML 与 CSS》第 31/62 篇
上一篇系列目录下一篇

媒体查询大概是 CSS3 里被抄得最多、也误解得最多的一段。去年我们把三个桌面站点改成响应式，上线后冒出的那些工单，查下来没有一条是”媒体查询有 bug”，全是把 device-width 当 width 用、按机型罗列断点、指望 media 属性省流量这三件事造成的。Media Queries Level 3 到 2012 年 6 月才成为 W3C 推荐标准，支持面到 2015 年初仍是一道分界线。本文只讲媒体查询本身：语法细节、断点取法、加载策略、老浏览器降级，各做一次对比、给一个结论。viewport 各字段语义在《HTML5 meta viewport 与移动端适配基础》里拆过，rem 的推导与构建期换算在《移动端适配方案：流式与弹性》和《rem 布局与视口适配》里写透了，本文都不重复。

语法结构：媒体类型、逻辑符号与三个非法写法

骨架是「媒体类型 + and + 特性」：特性一律带圆括号，多个条件用 and 连接（逻辑与），多个查询组用逗号分隔（逻辑或），两个符号不能互换，也不能写成 &&。媒体类型常用的只有 all、screen、print 三种，CSS2.1 里的 aural、handheld 到当时已经没人用。省略类型等于 all，所以 @media (min-width: 600px) 在打印时也生效，纸上会凭空少一栏。

not 取反的是整条查询，不是最近那个特性。only 容易被当成噪音，其实是兼容闸门：不支持媒体查询的老浏览器会把整条规则当普通样式解析，只有靠 only 这个它们看不懂的词打头，才让整条丢弃、保住为它们准备的默认样式。三个非法写法在老代码里最常见：

关键特性辨析：五个读数陷阱

width 与 device-width

width 匹配布局视口宽度，即 CSS 真正拿来排的那个数；device-width 匹配设备宽度，取屏幕在 1 倍缩放下的 CSS 像素宽度，与 screen.width 同源。差别在两处：不写 viewport 元标签时布局视口是 980 或 1024，min-width: 600px 会命中，手机直接吃到平板那档样式，而 device-width 仍是 320；用户双指放大之后布局视口不变、只有视觉视口变，所以 width 稳定，device-width 完全不理会缩放，在带缩放的设备上它与 CSS 像素不成比例。结论：断点一律用 width，前提是模板里那行 width=device-width, initial-scale=1。max-device-width 只在”纯 CSS 识别手机”的历史代码里见过，平板误判、桌面高分屏漏判，新代码不要写。

min-width 与 max-width：方向决定声明顺序

媒体查询之间没有权重高低，同一档属性谁生效只看规则在文件里的先后，后写覆盖先写。于是书写方向必须和声明顺序配套：移动优先，min-width 由小到大排；桌面优先，max-width 由大到小排。

混用方向的代价是改一档忘改另一档：单一方向里新增一档只需考虑更宽那档，混用则每条规则都要重推一遍区间交集，测试矩阵立刻翻倍。所以一个项目只许一种方向。

orientation 判的是宽高比

orientation: portrait 的条件是布局视口高度大于等于宽度，landscape 相反，读的是宽高比而非重力方向。于是两类现象看着像 bug 其实合规：4 比 3 的 iPad 竖屏 768x1024 与横屏 1024x768 比值差别远小于手机，同一套 portrait 样式在平板横屏上”看着还是竖屏”；比例越接近 1 的平板，地址栏一收放就能让判定来回翻；固定横屏设备或键盘弹出把布局高度压到小于宽度时，portrait 会突然失效。真要按形状分排版，用 min-aspect-ratio 与 max-aspect-ratio，比值写成 4/3 这种整数斜杠形式，比 orientation 精确。

同一个意思当时有三代写法，兼容性各覆盖一段：

min--moz-device-pixel-ratio 的双横线不是笔误，是 Firefox 当年的真实拼写，写成单横线不生效。min-resolution 是标准属性，Chrome 与 Safari 早期就支持、Firefox 16 以后可用，但 dppx 单位部分内核不吃，dpi 那条要保底。IE 这条线单独记：IE8 及以前连媒体查询整体都不解析，IE9 认 min-width 这类特性却吃不准 resolution 查询，所以 IE9 及以前基本做不了 dpr 分档；IE10、IE11 认 min-resolution 但不认 -webkit-min-device-pixel-ratio。Android 上 dpr 常见 1.33、1.5、1.77 这类小数，分档要用区间而非等值比较。

特性不做单位换算

媒体查询里的长度值是独立世界：不参与运行时缩放，也不看根元素字号。em 在特性里相对文档初始字号（通常 16px）；rem 在 MQ Level 3 里根本没定义，Chrome 与 Safari 当时不认、Firefox 认，别在断点上用它。px 与 em 的差别只在用户改了浏览器”字体大小”时出现：px 断点纹丝不动、正文却被放大，原本合适的一档直接溢出；em 断点随初始字号一起往宽屏方向推，内容与断点的相对关系保住。所以桌面站用 em 断点配 px 度量，移动页面因根字号已被脚本按视口算过，断点只能统一 px。

对比一：断点从哪来——机型表、分辨率档位、内容自然断点

第一派按具体设备型号取：把在测机型逐台记下理想视口宽度，320、375、414、360、601、768 全写进 CSS。问题是 2015 年初移动端 CSS 宽度已经是一条连续分布，Android 阵营月月加新值，永远补不完，而断点数直接乘在测试矩阵上，成本超线性。第二派按主流分辨率档位取，即 320、480、768、1024，或沿用 Bootstrap 3 的 768、992、1200：所有人张口对得上号、与框架栅格天然对齐，但数字来自统计众数而非页面本身，常出现”刚过 768，标题一行只放三个半字”这种没人负责的尴尬宽度。第三派按内容自然断点取：不预设数值，把窗口从宽往窄拖，拖到布局崩坏——侧栏挤成一团、标题折成三行、上下留白大于左右——那个宽度就是断点，取整写下来。

取法 覆盖新机型 与设计稿沟通 崩坏风险 适用项目
机型罗列 极贵，月月加档 低，逐台对齐 清单外全靠兜底 强还原度活动页
分辨率档位 便宜 中，档位要解释 档位边界易挤压 用框架的后台与官网
内容自然断点 最省，与机型无关 贵，需设计侧认可 最小，断点即崩坏点 内容站、图文混排

结论是第三派为主、第二派兜底：先用自然断点定出两到三档结构切换点，再用 320 与 768 这两个存量最大的档位校验有没有漏掉极端窄屏，档位数量三档封顶。不要罗列几十个设备断点——机型清单三个月后就成技术债，自然断点两年内不用改。断点只管结构切换，缩放交给流式或弹性。

对比二：分文件加载、单文件写满 @media、服务端 UA 嗅探

第一条路把 CSS 拆成多份，用 <link> 的 media 属性挂查询：

直觉是手机不匹配 960 那条，desktop.css 就不会下载，流量省了。当时的实测结论正相反：除 IE6、IE7 这类老内核，所有主流浏览器都会下载带 media 属性的样式表，只是不匹配时不参与样式计算、不阻塞渲染。也就是说 media 属性省的是解析与应用成本，不是网络流量——分文件的价值在于把无关 CSS 挪出关键路径、让首屏更早稳定。

第二条是不拆文件、一份 CSS 写满 @media：下载量最大，但一次请求、无阻塞顺序问题、缓存最简单，而且它是唯一能被 respond.js 补的形态。第三条是服务端按 UA 嗅探输出不同 CSS：首屏字节最少，代价全在工程上——UA 表要一直维护，新机型一发布就得跟；内嵌浏览器（微信、QQ 那批带 MicroMessenger 标记的 X5 内核）与系统浏览器行为不一致，误判就直接给错样式；同一 URL 返回不同内容还得处理 Vary，否则 CDN 会把手机版本缓存给桌面用户。

方案 首屏渲染成本 网络流量 误判风险 维护成本
link media 分文件 低，不匹配的不阻塞 不省，仍全下载 低 中，请求数增加
单文件写满 @media 略高，全量解析 全量下发 最低 最低
服务端 UA 嗅探 最低 最省 高，UA 表长期落后 高，含 CDN 协商

移动端首屏对 CSS 体积敏感：3G 一次往返几百毫秒，样式表没解析完就白屏。落地选择：桌面与平板共一份主 CSS（内部写满 @media），移动端另出一份精简表；UA 嗅探只留在无法上响应式的老活动页。打印样式的四种挂载见《CSS 打印样式表 print 实践》。

对比三：媒体查询在三条适配路线里各管什么

先钉前提：只有模板里有 width=device-width, initial-scale=1，媒体查询拿到的 width 才是设备的 CSS 像素宽度；不写这行，布局视口是 980 或 1024，所有断点整体错位，手机上永远只命中最宽那一档。三条路线里媒体查询的位置完全不同，选型看设计稿口径与像素对齐要求：

路线 媒体查询承担什么 断点数量 设计稿尺寸对齐 像素对齐
纯媒体查询加百分比流式 切结构，度量靠百分比自算 两到三档 一套稿通吃，标注换算成百分比 与视口无关，1px 与图标天然准
rem 加媒体查询切根字号 只做档位兜底，缩放交给根字号脚本 一档甚至零档 逐像素照抄二倍稿标注 缩放后细线变粗，需钉 px 白名单
固定宽度加 viewport 缩放 基本不用 零档 只对齐一种稿宽 浏览器插值缩放，位图与文字发虚

判断是：内容型页面选第一条，媒体查询是主角，负责”两栏变一栏”这类结构切换，百分比负责连续变化，用户调字体的偏好也保得住；应用型与强还原度活动页选第二条，媒体查询退居二线只做兜底，缩放全交给根字号脚本，代价是可访问性与构建链复杂度，rem 路线的推导见那两篇旧文；第三条只是桌面页临时平移的凑合做法。三者关系一句话：媒体查询管”结构在哪个宽度该变”，流式与弹性管”两个断点之间怎么缩”。

对比四：老浏览器降级——respond.js、条件注释、还是不做

IE8 及以前的桌面 IE 完全不解析 @media，整条规则被丢弃；Android 2.x 系统浏览器同样不支持 MQ3。

respond.js 的原理是把断点搬到 JS 里重放：扫描 <link> 的 media 属性与外部样式表里的 @media 块，用脚本比较窗口宽度，命中的规则再写回文档。它有效，限制也一堆：只认外部样式表，写在 <style> 里或元素 style 属性上的一律看不见；受同域限制，样式表放 CDN 就得挂它自带的跨域代理，多一跳请求；min/max-device-width 与 device-pixel-ratio、min-resolution 这类它没法用宽度模拟的特性不会被转换，倍图分档在 IE8 上直接失效；它还要在 DOMContentLoaded 之后重解析一遍 CSS，跨档靠定时器轮询补，首屏多一次可见重排。

第二条是条件注释，把老 IE 关进一份不写查询的样式表。不支持媒体查询的浏览器只拿到最外层基础样式，所以这条路必须配桌面优先，否则 IE8 在宽屏上显示一栏窄版：

方案 首屏成本 覆盖的查询 风险 适用
respond.js 一次脚本加一次重排 外部样式里的 width 类特性 跨域与 device 类特性失效 桌面站，要求 IE8 跟窗口缩放
条件注释单独样式 无额外脚本 由你手写档位 多一份表要长期同步 桌面优先站点
不做降级 零 无 IE8 停在默认档 移动专题页

务实结论是第三条用得比想象多，判断依据只有一条：这批老浏览器是不是目标流量。我们的移动专题页从 2014 年下半年起就不给 IE8 做任何事——手机上没有 IE8，桌面上它的流量已掉到百分之一以下，为它挂 respond.js 换来的是首屏一次重排和一条随时腐化的跨域代理。后台与官网这类”必须能用”的桌面站才保留条件注释加桌面优先。

调试与联动：matchMedia 而不是自己比宽度

断点要在脚本里联动（切导航形态、按需初始化轮播、埋点上报档位）时，正确工具是 window.matchMedia，它和 CSS 走同一套解析，读数天然一致：

兼容性：IE9、IE10 有 window.matchMedia，但监听部分的实现各家不一致，addListener 与 addEventListener('change') 两条都得写并真机验一次；IE8 完全没有这个 API，只能像上面那样降级比宽度；iOS 5 以上、Android 4.0 以上可用。Firefox 当年还有个毛病：查询命中了、回调却不触发，所以初始化必须主动查一次。

为什么不建议用 window.onresize 自己比 window.innerWidth：一是 iOS 横竖屏切换时 innerWidth 的上报时机晚于 resize 触发，回调里读到的是旋转前的值，档位判断跟着错一档（事件时机详见《HTML5 meta viewport 与移动端适配基础》），而 matchMedia 的命中由浏览器在样式重算阶段给出，不用你猜读数何时才准；二是输入法收起、地址栏折叠都会发 resize 而宽度没变，自己比宽度还得额外写一层”变化才处理”；三是双指缩放会改动 innerWidth，媒体查询的 width 认的却是布局视口，不受手势影响。

落地示例：移动优先三档形态

内容列表页的最小完整形态，纯 ES5、不依赖 jQuery：320 到 600 为手机、600 到 960 为平板、960 以上为桌面，两个查询加一档基础形态，全部来自内容自然断点。桌面站则按对比四改成桌面优先。

三点交代：data-tier 挂在根元素上，CSS 能用 html[data-tier="tablet"] 补一条查询之外的形态；srcset 与 sizes 当时不能当跨浏览器能力用，Chrome、Safari 实现各有出入，换图只能靠 JS 或 picturefill；@media 里的 600、960 与 JS 里那两个数必须同源。

选型结论表：断点策略 × 适配路线 × 降级方案

决策项 内容站（资讯、图文、官网） 应用型站点（活动页、内嵌 H5、后台）
断点取法 内容自然断点为主，320 与 768 校验 一档甚至零档，缩放交给度量
书写方向 桌面站可桌面优先，方便老 IE 一律移动优先
特性选择 width 配 em 断点，尊重字号偏好 width 配 px 断点，别碰 rem 断点
交付方式 单文件写满 @media 移动端另出精简表，桌面表不引
适配路线 媒体查询加百分比流式 rem 加根字号脚本，断点只兜底

内容站要的是字号偏好与结构切换，所以 em 断点、流式度量、少量档位；应用型要的是还原度，断点退到最少。共同禁区是机型断点罗列、靠 media 省流量的幻想、拿 max-device-width 判手机。

小结

媒体查询有三层容易被跳过。读数层：width 与 device-width 差在哪、orientation 判的是宽高比、特性里的长度值不做单位换算。策略层：断点从内容来而不是从机型表来，media 属性只省渲染不省流量，移动端多数情况不做 IE8。联动层：matchMedia 与 CSS 同源查询，自己拿 resize 比宽度会在 iOS 旋转时读到旧值。最后仍要回真机——模拟窗口看得出崩坏点，看不出加载时机。
