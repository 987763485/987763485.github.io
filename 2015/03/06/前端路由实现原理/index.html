前端路由实现原理

写单页应用绕不开路由，但很多文章把路由讲成了”改一下地址栏”的小技巧，低估了它的分量。路由真正难的地方不在”怎么把 URL 换掉”，而在”换掉之后这一切换要花多少代价”：一次点击背后是匹配、取数、建 DOM、重排重绘，还有一整套卸载旧视图、恢复滚动、补发埋点的收尾工作。这篇文章就从性能与调优的角度，把 Hash 路由和 History API 路由这两条实现路线拆开讲清楚，再讨论路由表的匹配算法、分发渲染的开销构成、频繁触发时的节流、埋点统计的补发，以及落到工程上的选型结论。凡是涉及 location、history 这些对象本身的属性清单，以及 pushState、replaceState 三个参数逐个怎么填，我在《location 与 history 对象详解》和《HTML5 History API 打造无刷新单页应用》里已经写过，这里不重复，只把笔墨放在路由的实现与代价上。文中的代码全部用 ES5 语法书写，块级绑定、箭头函数、异步编排原语这些眼下还没进标准的东西，一个都不碰。

为什么需要前端路由

传统多页应用里，URL 和视图是一对一绑死的：/list.html 就是列表页，/detail.html 就是详情页，浏览器请求一个路径就吐一个文档。历史栈、地址栏、前进后退、收藏夹、可分享链接，这些能力全部由浏览器免费打包提供，前端一行代码都不用写。代价是每次切换都要整页刷新，白屏、重新加载脚本、重新拉数据，体验是断的。

AJAX 成熟以后，我们完全可以在同一个文档里用异步请求换内容，把切换做成”不刷新”的。但一旦内容不再跟着 URL 走，浏览器免费提供的那套能力就全丢了：地址栏停在你进站时的首页，用户刷新就回到首页，收藏夹里存不住当前看的那条数据，后退按钮要么没反应要么退出了站点。前端路由要解决的，正是在”内容不刷新”和”URL 要跟着变”之间重新搭一座桥。

剥开实现细节，无刷新切换其实只解决两件事。第一件是浏览器历史栈：视图切换要能在历史里留下记录，让后退、前进真的能回到上一个视图，而不是把用户甩出站点。第二件是可分享、可回退的 URL：任何一个视图状态都要能编码进地址栏，别人点开这个链接看到的是同一个视图，用户刷新也停在同一个视图，而不是被弹回首页。所有路由方案——Hash、History API、iframe 的 hash hack——本质上都是在用不同代价满足这两条，区别只在于用哪个字段承载状态、用哪个事件感知变化、需要服务端配合到什么程度。

从性能视角看，选型的第一步是认清两种模型的开销分布。多页应用首屏最重（每次都重新下载 HTML、CSS、JS），但切换之间彼此隔离、内存干净；单页应用首屏之后靠缓存省下重复下载，切换只换局部，但把历史、分享、卸载这些责任全搬到了 JS 里，一旦处理不当就是内存泄漏和路由栈膨胀。路由不是免费午餐，它只是把开销从”网络 + 整页重绘”挪到了”匹配 + 局部重绘 + 收尾清理”，而后两样是可以调优的，这正是本文的主线。

Hash 路由的实现

Hash 路由是 2015 年国内大量项目仍在用的方案，原因很简单：它零服务端改造、兼容到 IE7/IE8。它的原理是把状态塞进 URL 的片段标识符（# 后面的部分），靠监听片段变化来驱动视图。关键前提是：片段永远不发送到服务器，浏览器只在本地把它交给页面自己解析。于是无论用户把 hash 改成什么、刷新多少次，服务器收到的请求路径始终是那一个，它永远只返回同一个 HTML 入口，剩下的交给前端。这条性质既是 Hash 的优点（服务端什么都不用配），也是它的天花板（爬虫只看得到那一个空壳 HTML，首屏 SEO 基本为零）。

Hash 路由的事件入口是 hashchange。这里有一段必须知道的兼容史：hashchange 在 IE8 及更新版本里才有，IE7 根本没有这个事件；而 IE8 的早期实现还有个恼人的 bug——在文档尚未 load 完成之前修改 hash，hashchange 不会如期触发，只在真正切换时才响一次，首屏那种”进来就带 hash”的场景容易被漏掉。所以一个稳妥的封装要做到三件事：优先用标准事件、IE7 降级到轮询、加载完成时手动补一次初始检查。下面这段 ES5 代码把三种入口的差异抹平：

Hash 里的状态通常不止一个路径，还要带上查询串，比如把列表的第 2 页、热门筛选编码成 #/list?page=2&filter=hot。麻烦点在于：location.hash 拿到的整串里既有”路径”又有”查询”，标准库没有现成的切分，得自己解析。查询串的 key=value 拆分逻辑我在《location 与 history 对象详解》里写过一份，这里只做片段特有的那一步——按第一个问号把 hash 切成路径段和查询段：

History API 路由的实现与差异

History API 用 pushState 改地址栏、用 popstate 感知前进后退，是 Hash 的”现代替代”。它的三个参数怎么填、state 的容量上限、首次加载也会触发一次事件这些基础，都在《HTML5 History API 打造无刷新单页应用》里讲透了，这里只从路由实现的角度补三点关键差异。

第一，本质差别在承载字段。Hash 把状态放在片段里，URL 长这样：/app#/list?page=2；History 能改的是真正的 pathname 和 search，URL 是干净的 /app/list?page=2，不带井号。别小看这个井号——真实路径会被爬虫抓取、可收录，观感上也和普通网站无异，这是 History 相对 Hash 最大的价值。代价是 pushState 里那个 title 参数，2015 年仍然被所有主流浏览器直接忽略，写了不生效，标题还得靠 document.title 自己同步。

第二，事件触发时机不同，这一点直接决定路由代码怎么写。改 location.hash 会立刻触发 hashchange；而调 pushState、replaceState 本身不派发任何事件——它们是”你主动改地址”，浏览器认为你已经知道发生了什么，不需要再通知你。popstate 只在用户前进、后退（或用 history.go 跳转）时触发。所以 History 路由必须走两条独立入口：点击拦截里”改地址 + 主动渲染”是一路，前进后退时靠 popstate 回调”读状态 + 恢复视图”是另一路，两路要汇聚到同一个渲染函数，否则代码会打架。Hash 反而简单，因为它把这两件事合并到了同一个 hashchange 上。

第三，读取当前视图的状态来源不同。popstate 回调里能拿到 event.state，即当初 pushState 塞进去的那个对象；但用户直接刷新或粘贴一个深链接进来时，根本没有 state（是 null），这时唯一可靠的信息是 location.pathname 加 location.search。工程做法是把视图状态尽量编码进 URL 本身、state 只存不便分享的临时量（比如滚动偏移），恢复时优先读 event.state、为空则回落到解析 location。这套”URL 优先、state 补充”的原则保证了链接的可逆——这是分享和直达不出错的底线。

刷新 404 是 History 路由绕不过的坎，而且它的根因完全不在前端。用户在 /app/list/2 刷新，浏览器老老实实向服务器请求这个路径，而服务器上压根没有对应文件，于是返回 404——Hash 方案因为片段不出门所以永远碰不到这个问题，History 则必须让服务器把这个前缀下的所有请求都兜底到同一个入口 HTML，再由前端路由决定渲染什么。这是服务端配合，不是纯前端能自己解决的。Apache 上更稳妥的写法是先用 RewriteCond 判断”请求的不是真实文件、也不是真实目录”，再重写兜底，避免把静态资源和真实接口一起误伤：

Nginx 侧一行 try_files 就能达到同样效果：先试真实文件、再试目录、都没有就落到 index.html。接口路径一定要放在这个兜底前缀之外，否则 AJAX 请求会被返回一坨 HTML、JSON 解析失败，报一个莫名其妙的错。

判断兜底配没配对有个土办法：直接在新标签页打开一个深层路由（比如 /app/list/2?type=hot），能正常渲染就说明服务端配对了；404 就说明无论前端怎么写都会漏。

把两条路线的一次切换放到时序里对照，触发时机的差异就一目了然：Hash 靠改片段被动等 hashchange，History 则要”主动改地址 + 主动渲染”和”被动等 popstate“两条路并行。

路由表匹配机制

不管 Hash 还是 History，最终都落到同一件事：把一个路径字符串映射到该执行的处理函数。路由表怎么组织、匹配怎么跑，是切换耗时里唯一纯前端可控的一段。最朴素的做法是”规则数组 + 遍历匹配”：每条规则把形如 /user/:id 的模式预编译成正则，命中就按捕获组把参数名和值配对，末尾再挂一条通配 * 做兜底。

这套实现跑 /user/42 得到 { id: '42' }，跑 /file/a/b.txt 得到 { splat: 'a/b.txt' }，跑未注册路径返回 null。它的复杂度是 O(规则数)：每次匹配都要把规则从头试一遍，命中第一条为止。规则少时无所谓，规则一多、且真正命中的那条排在数组尾部时，线性扫描就成了切换延迟里实打实的一段。

另一种做法是以路径片段建一棵简单的 trie（分段字典）：把每个片段当作一层节点，普通片段进 children 字典，:id 参数位进一个专用的 param 指针，* 记成节点上的 wildcard。查找时按片段逐层下钻，命中的是字典里的那条边，匹配耗时只跟路径深度有关，不再跟规则总数有关。

两种实现对同一组规则给出的参数是一致的：/user/42 都是 { id: '42' }，/post/2015/03 都是 { year: '2015', month: '03' }，/file/a/b.txt 都是 { splat: 'a/b.txt' }。差别全在耗时。我在本机跑了一组对照：注册 500 条 /moduleN/item/:id 规则，反复去匹配”恰好命中最后一条”的最坏路径，数组遍历要把 500 条正则全试一遍，而 trie 只需下钻三层。量级差异非常明显——数组遍历约 556 毫秒，trie 约 10 毫秒，差了五十多倍。当然这是被放大到 500 条、5 万次循环的极端场景，真实项目规则数往往在几十条，绝对差值在微秒级，用户基本无感。它说明的是趋势：规则一旦上百、或匹配是热路径（比如高频前进后退），从”线性扫描”换成”分段下钻”能把匹配这一段开销从 O(规则数) 压到 O(片段数)。

另一个省开销的点，是正则在注册时前置编译、只 new RegExp 一次，而不是每次匹配都现场编译。上面数组实现的 add 里就编译好了，匹配时直接 exec。对照实测：同样 2000 次最坏匹配，预编译约 8 毫秒，每次现场 new RegExp 约 127 毫秒，差了十几倍。原因不神秘——构造正则对象要走一遍词法分析、编译状态机，这是每条规则、每一次匹配都要重复交的税；而 exec 只是拿现成的状态机跑字符串。把编译挪到路由表初始化阶段，用一点内存换匹配时的稳定低耗时，是划算的。

分发与渲染的性能代价

匹配只是链路里很小的一段。一次真正的路由切换，背后是一条不短的流水线：先卸载旧视图（解绑它在 document 上注册的委托、清掉它起的定时器、断开它对 DOM 节点和数据对象的引用），再匹配新路由，然后拉数据（一个或几个异步请求），拿到数据构建 DOM，插入文档触发重排重绘，最后更新标题、恢复滚动、补发埋点。这条链路上每一段都有自己的开销来源，也都有各自的调优抓手。

卸载旧视图是最容易被忽略、却最容易埋雷的一段。事件监听忘了 removeEventListener、定时器忘了 clearInterval、渲染函数闭包长期引用着大块数据对象，路由切走了、内存却没放下来，来回切几次就是一次泄漏累积。这一块的成因和排查我在《DOM 事件移除与内存泄漏》里专门写过，一句话概括：谁绑定的谁负责解绑，视图对象要提供一个显式的 destroy 钩子把外部引用清干净。路由层负责在切换前调用上一个视图的 destroy，这是纪律问题不是性能技巧。

构建 DOM 这段，重排重绘是主要开销。若一段新内容要创建几十个节点，直接往活文档里一个个 appendChild，每插一个都可能触发一次重排。正确做法是用 document.createDocumentFragment() 把节点先在内存碎片里攒齐，最后一次性插入，只触发一次重排——这个碎片批量插入的手法在《DOM 增删改查与文档碎片 DocumentFragment》和《DOM 操作性能：批量插入与重排优化》里讲得细，路由场景里直接复用即可。更进一步，若新旧视图共用同一个容器，只替换容器的 innerHTML、让浏览器复用外部结构，比重建整棵子树要省得多；能不碰布局就不碰布局。

取数这段，省一次请求就是省下最实在的等待。首屏常常是服务端已经渲染好、数据已在页面里，前端路由若对首个视图再无脑发一次异步请求就是双倍网络开销；合理做法是首屏直接复用服务端输出的数据，只有后续切换才走取数。同理，一个视图若依赖多个接口，能在一次请求里合并就别拆成串行的多次往返。

脚本加载这段，是”切换变快”最见效的地方。一个路由对应的视图代码没必要在首屏全量下载——用户可能根本不点进去。路由级懒加载的做法是：进入某路由时才动态注入它对应的脚本，且要防止同一路由被重复请求。ES5 里没有现成的异步编排原语，用一个”加载状态字典 + 回调队列”就能实现——正在加载时把后续回调压进队列，加载完成统一触发，已加载过的直接同步回调：

实测这段的去重逻辑：同一 URL 连调两次，只创建一个 script 元素；加载完成后队列里两个回调都会被触发，之后再调直接命中 loaded 同步返回。对首屏来说，这意味着”没访问过的路由”完全不占下载，切换时才付出一次脚本请求的代价，是延迟加载换首屏瘦身的典型权衡。代价是首次进入某个路由时多等一段脚本下载，需要配合加载态占位，别让用户对着空白发呆。

历史栈的体积也是开销的一部分，它影响后退体验和 state 内存占用。搜索翻页、筛选这类”同一视图反复微调”的操作，如果每步都 pushState，历史栈会被十几条几乎相同的记录塞满，用户要点十几次后退才能离开，浏览器还得为每条记录存着 state 副本。对这类不该进入后退轨迹的变化，用 replaceState 替换当前记录而不是新增一条，既保持 URL 与视图同步，又让历史栈保持精简——这也是 History API 相对 Hash 的一个可操作优势，因为 Hash 里改片段总是产生一条新历史。

频繁触发的节流

用户快速连点后退、前进，或在移动端来回滑动时，hashchange、popstate 会短时间连发一大串，每个回调都跑一遍”匹配 + 取数 + 渲染”的话，既浪费又会造成视图抖动和请求风暴。这时要上节流：一段窗口内只真正执行一次，中间触发丢弃或合并到最后一次。路由场景里我自己实现一个 ES5 的 throttle，不去引第三方库——Underscore 1.7.0 那时确实已经有 _.throttle，但为一个函数背一个依赖不值当。

实测它的行为：在同一时刻连点五次，立即执行第一次（leading），中间三次被丢弃，约一个窗口之后再补执行第五次（trailing）——既保证了响应即时，又只渲染用户真正停下的那个视图。把节流函数套在 hashchange 上即可：window.addEventListener('hashchange', throttle(onHashChange, 50), false);。

这里要特别提醒一点：路由切换的节流窗口不能设太长、尤其 trailing 延迟不能贪大。节流和防抖（debounce）不是一回事，若为了少渲染把执行整个推迟到”停止操作 300 毫秒之后”，用户在快速后退时会明显感到画面跟不上按钮——点了半天地址栏已经变了，视图还停在旧内容上，甚至出现一段说不清该显示哪个视图的白屏。路由的体感优先级是”响应即时”高于”省下几次渲染”，所以窗口取几十毫秒、并且务必保留 leading 立即执行第一次，是最稳的取舍。要压缩的是重复渲染，不是首帧响应。

埋点与统计

单页应用里有个隐蔽但影响数据大盘的问题：PV 统计会大面积漏报。绝大多数统计代码只在页面 load 事件里发一次 PV，而单页应用全程只 load 一次，后续几十次路由切换在它眼里根本不是一”页”。结果就是用户明明看了十几个视图，后台却只记到一进站那一条。补法很直接——路由切换时手动补发一次 PV，把这”虚拟的一页”告诉统计服务。

Hash 模式下的补发最简单，因为片段不出门，服务器压根不知道用户换了视图，只能靠前端自己上报。可以用自建 beacon（一张 1 像素 GIF 配合查询串）打点，也可以调用统计脚本自己提供的页面跟踪接口。自建打点在 ES5 里就是一行 Image()：

实测拼出来的上报串形如 /beacon.gif?p=%2Fuser%2F42%3Ftab%3Dinfo&t=...&r=778944，路径和中文标题都正确编码、随机数保证每次都是新请求。用 Image() 而非异步接口的历史原因（2015 年那会儿 JSONP/CORS 还得费事）：图片请求不受同源限制、不占 XHR 并发、失败也无感，是埋点最省事的通道。用 Google Analytics 的话则改调它的页面跟踪方法，把虚拟路径作为参数传进去，原理一致。

document.title 的同步也归到路由收尾里：切换后根据匹配到的路由设定新标题，这既服务浏览器标签页显示，也保证埋点里带出去的页面名是对的。这一步是纯前端能完全掌控的，别指望 pushState 那个被忽略的 title 参数替你完成。

方案选型与结论

把上面这些代价摊开，最后收口到选型。三个方案横向比，维度要落到可度量的开销和成本上，而不只是”好不好看”。Android 端的兼容性要单独点出来：Android 2.3 的自带浏览器基本没有可用的 pushState，2.4 到 4.3 支持残缺、行为不稳，到 4.4 换了 Chromium 内核才算可靠——这在 2015 年”机型碎片化”的移动场景里是个硬约束。

维度 Hash 路由 pushState 路由 传统多页跳转
兼容性 IE7 需轮询、IE8+ 原生事件 IE10+、Android 4.4+ 才可靠 全平台，无特殊要求
URL 观感 带 #，较丑 真实路径，干净 真实路径，干净
服务端改造成本 零，永远只返回一个 HTML 必须配兜底 rewrite，否则刷新 404 每个 URL 对应真实文档
SEO 片段不被抓取，基本为零 真实路径可收录 天然可收录
刷新 / 直达 片段不请求服务器，稳 依赖服务端兜底正确 各文档独立，稳
可分享性 能分享，但带井号观感差 与正常链接无异 正常链接
历史栈控制粒度 改片段必产生新记录，粒度粗 push/replace 可选，粒度细 由浏览器全权管，不可干预
首屏开销 一个入口 HTML，之后本地切换 一个入口 HTML，之后本地切换 每次跳转整页重载
切换开销 匹配 + 取数 + 局部重绘 同左，但可用 replace 精简历史 全页重下载重渲染

结论按场景给。需要兼容 IE9 及以下、又要照顾 Android 老机型的移动端 H5，或者站点部署在静态托管 / CDN 上、运维根本改不动 rewrite 配置——这种现实约束下选 Hash，别硬上 History API，因为刷新 404 会直接让深链接全军覆没。能控制服务端、允许放弃老 IE、又在意 URL 观感与可抓取性的中后台或产品页，选 History API，它换来的干净路径和 SEO 潜力是 Hash 给不了的。纯内容型、要求每一页都能被搜索引擎完整收录、又不追求切换动效的站点，老老实实多页跳转反而是最省心也最利于收录的方案，单页那套卸载、补发 PV、懒加载的收益对它并不成立。

至于为什么 2015 年国内大量项目仍停在 Hash，答案不在技术优劣而在成本：其一，要兼容的浏览器还停在 IE8/9 和一堆 Android 2.x/4.x，pushState 覆盖不到，降级逻辑两套并存反而更累；其二，很多团队的静态资源甩在 CDN 上，服务端兜底配置不归前端管、也懒得跨部门去改，Hash”零服务端改造”这条省下的是实打实的沟通成本；其三，后台类系统压根不在意 SEO，Hash 那个”丑”和”不被收录”的缺点正好无关痛痒。权衡下来，Hash 是当年综合成本最低的解，这不是它更先进，而是它把责任压到了最少的外部配合上。

踩过的性能坑

最后复盘三个真实踩过的坑，都是”跑通”和”跑得顺”之间的那段距离。

第一个是往 Hash 里塞超长参数。最初图省事，把一个长列表的筛选条件、排序、甚至一段序列化后的数据全编码进 #/list?... 里，URL 一口气涨到上千字符。两个后果：地址栏被撑爆，用户复制分享时浏览器悄悄截断；埋点用 1px gif 上报，而 GET 请求的 URL 有长度上限，服务器和统计网关在几 KB 处就把超出部分丢了，导致这批”重参数”的页面 PV 采集残缺、参数解析报错。教训是片段里只放”值得分享”的精简标识——ID、页码、关键筛选——大对象该进 state、该进缓存、该进后端会话，别拿 URL 当存储，它既不是为存数据设计的，也有一道看不见的长度天花板。

第二个是 pushState 调用频次过高在旧版 Safari 上的卡顿。有段代码在搜索框的每次输入都 pushState 一下把关键词同步到地址栏，看着是”实时反映状态”，实则在一个 300 毫秒的停顿里往历史栈塞了七八条记录。iOS 7 的 Safari 上，高频 pushState 会带来可感知的掉帧，历史栈也迅速膨胀到用户要点很多次后退才能退出。改法是输入过程一律用 replaceState 只更新当前记录，只有真正提交搜索才 pushState 留下一条历史——既保住了 URL 同步，又把历史栈体积和调用频次压回合理范围，卡顿随之消失。这跟前面”历史栈体积”讲的是同一件事，但这里更强调的是”旧 WebKit 上 pushState 本身不免费”。

第三个是滚动位置的恢复。单页应用切视图时文档高度变了，如果不处理，用户从列表第 20 屏点进详情、再后退回来，列表却停在顶部，得重新往下滚，体验很割裂。做法是维护一张”路径到滚动偏移”的映射：离开某路由时记下它的 scrollTop，进入时把记录值喂给 window.scrollTo 还原，没记录就回到顶部。

实测映射逻辑符合预期：为 /list 记 820、为 /detail/1 记 45，恢复时分别取回这两个值，而没进过记录的 /home 回落为 0、自然滚到顶。要注意的是这张表只增不减会随访问路由变多而占用内存，对长期驻留的单页应用要给它一个上限或随历史淘汰，别让它变成另一种意义上的泄漏。三个坑归到一处，其实都指向同一条经验：路由的每一环（URL 承载、历史栈、滚动、内存）都是有代价的资源，写得顺的项目不是功能全实现了，而是把这些资源的用量都控制在了用户感知不到的范围内。
