函数式编程思想在前端的应用

写页面的时候我有一种感觉：函数式这个话题在前端已经快要变成一套”话术”了。会上说”我们用函数式的方式重构一下”，落到代码里往往只是把三个 for 循环换成了 map，第二天又在滚动回调里把共享对象改得满天飞。这篇文章不想再讲一遍 map/filter/reduce 怎么用，也不想再推导一次柯里化——那些内容《JavaScript 函数式编程入门：map/filter/reduce》和《JavaScript 柯里化与偏函数应用》已经写透了。我想谈的是另一件事：函数式的思想在 JavaScript 这门并不函数式的语言里，到底能以什么形式活在前端工程里，以及每一种形态要付出什么代价。全文代码都是 ES5，能直接放进 2015 年的项目里跑；文中所有计时数字都是我自己在一台开发机的 node 命令行里实测出来的，量级可以信，绝对值请你在自己的目标设备上重测。

先划清界限：这是思想借用，不是范式纯化

之所以要先说这一段，是因为很多争论源于对 JavaScript 定位的误解。JavaScript 的函数确实是一等公民：能当参数传、能当返回值传、能存进对象、能随时创建。但”函数是一等公民”和”这是一门函数式语言”之间差着好几件基础设施。

第一，没有尾调用优化。截至本文写作时，主流引擎（V8、JavaScriptCore、IE 的 jscript9 与它的后继者 Chakra）都不做尾调用消除；今年定稿的 ES6 把”proper tail calls”写进了规范，但规范归规范、引擎归引擎，短期指不上。所以递归深一点的算法在旧设备上照样爆栈，社区的标准解法是蹦床（trampoline），把”调用栈上的递归”变成”外层循环里的一串 thunk 队列”——这个妥协本身就说明这门语言在深层递归上是不设防的。

第二，语言层面对不可变的支持几乎是零。var 随便重赋值，对象属性随便增删，数组可以原地 splice，ES5 只给了 Object.freeze 和 Object.seal 两个粗粒度工具，而且 IE9 以下要靠 polyfill 模拟，性能与语义都要打折。没有持久化数据结构（persistent data structure）的语言支持，意味着”每次生成新对象”这件事在我们的技术栈里只能是手写浅拷贝，而不是免费的构造树共享。社区已经有 Immutable.js 3.x 这类库在做这件事，但它是额外的依赖和额外的 API 心智，本文不展开。

第三，没有模式匹配、没有惰性序列、没有代数数据类型，函数组合只有 Array.prototype.reduce 这一条最原始的通道可用。

所以我的立场很明确：我们从函数式里借的是三条纪律，不是整套教条——把副作用推到边界上、把数据当不可变的东西对待、把复杂逻辑拆成可组合的一元小函数。借用是有代价的，下面每一节都会把代价一起报出来。

一，撤销/重做几乎不要写代码。 因为每次更新产生的都是新对象，”历史”就是一串引用，不需要快照，也不需要深拷贝：

我们那个表单向导页靠这七行做了”上一步不丢数据”，代价只是历史数组里多了几个对象引用。如果状态是原地改的，同样的功能必须每次 JSON.parse(JSON.stringify(state)) 存快照——在老 IE 上那玩意慢得能把用户点”上一步”的耐心耗光。

二，引用比较就是变化检测。 state.keyword !== oldState.keyword 这类字符串比较，或者 next !== prev 这类引用比较，是成本最低的脏检查。AngularJS 1.2/1.3 的 $digest 要轮询所有被观察的表达式，Backbone 则要求你手动 model.set 才能触发 change 事件——两个阵营长期在争”到底谁的更新更可靠”。不可变加显式更新，把这个问题降维成了”比较两个指针”，谁都不会忘。

三，不会出现”改了一个字段整页不重绘”。 页面数据被多个地方共享引用时，原地改字段的那个模块永远不会通知别人；而一旦更新必须产生新引用，拿不到新引用的那段代码就再也看不到后续变化，”改了却没人重绘”这种事故至少从静默失败变成了能被看见的问题。JavaScript 没有编译期检查，这一条靠的是约定加评审，但约定本身就已经能挡掉绝大多数漏更新。

第三行才是关键：不可变的成本不在”对象小”，而在”结构大”。改一个 8 个字段的状态对象只要 0.08 微秒量级，但改一个 1000 项列表里的一项要把整份数组拷出来，单次就是几十微秒。如果你的列表有 1 万项，用户每敲一个字都要重建整份数组，输入防抖窗口一过就是几毫秒的纯拷贝，而这还没有把后面 map 产生的新数组算进来。

所以”何时不该用”我有一条明确红线：每帧或每个高频事件里重建万级数组的路径，不要用全量拷贝的不可变结构。 这种地方要做的是把列表从状态对象里拆出去单独管（列表项本身仍然不原地改，只 slice 出被替换的那一段做局部拷贝，其余共享引用——这已经是手写版的结构共享），或者直接让列表走”命令式增删 + 显式通知”。

另外两笔账：GC 压力和旧浏览器。前者的实测数字很难看——我用 10 万元素的样本数据连续跑 200 次 filter().map() 并把结果留在数组里，堆占用增量两次分别测得约 98.6 MB 与 113.6 MB，平均每份中间结果约 0.5 MB 到 0.6 MB（66666 个字符串引用）。这些垃圾最终会被回收，但页面长时间开着、用户在几个列表间反复切换时，主线程就会被打断去清扫，表现是”滚动忽然一顿”。后者没法用数字说话：IE8/9 的对象分配与 GC 本来就比同时代的 V8 慢一个量级，而不可变风格把每次交互的对象创建次数放大了好几倍，同一个页面在 IE8 上更卡是必然的。我的处置办法是：状态对象（几十到几百个键的量级）一律不可变，列表项数组在超过几千项时退回”局部拷贝 + 显式通知”，并在代码里写明这是性能妥协而不是洁癖问题。

这种写法带来的最大收益不是”少写几个变量”，而是它逼你把抽象层级统一。一条管道里的每一步都必须是同一层级的”做什么”：onlyOnSale、bySoldDesc、topTen、toRowData、toHtml，读起来像需求文档。反过来，如果某一步的名字里出现了 and（比如 filterAndSort），或者某一步里混进了字符串拼接和 DOM 读取，就说明两个层级被压在了一个函数里，管道立刻不可读、不可复用、不可单测。我给自己定的检查方式是：把管道里任何一步单独拿出来，它必须仍然是一个能写在文档行首的动词短语。

但组合是有账单的，而且账单在调试时到期。管道每多一层，出错时调用栈就多一帧匿名函数，栈里全是 reduce 的回调和没有名字的包装层，参数还得手动展开 arguments 才看得见。加上组合子天生鼓励”一行五步”，新同事读这条管道时得先在脑子里把数据流方向跑一遍。两个对策我认为有效：

第一，每一步必须具名。Fn.pipe(a, b, c) 里的 a/b/c 必须是 var onlyOnSale = function ... 这种有名字的变量，不能是就地写的匿名函数。具名之后调试栈里能看到 at onlyOnSale，这比什么工具都管用。

第二，插一个 tap 进管道看中间值。实测 Fn.pipe(HotSteps.onlyOnSale, Fn.tap(function (x) { seen = x.length; }), HotSteps.topTen) 作用在那份 15 条样本上，seen 拿到 12（过滤掉 3 条下架），输出仍然是截好的 10 条，把 tap 整行删掉结果一字不变——tap 只观察不改数据。线上要留证据时把 tap 换成打点上报即可，排查完删掉这一行，管道恢复原样。

真觉得一行太挤，就把管道拆成语句：var onSale = onlyOnSale(items); var sorted = bySoldDesc(onSale); ...。这不是背叛函数式，这是让 review 通过。顺便一提，Underscore 1.7.0 已经内置 _.compose（没有 _.flow，方向只有从右到左），lodash 2.4.1 两个都有（_.flow 与 _.compose），所以真要上产线我建议用库的版本——但请先读一眼它的实现，别把”库里有”和”我知道它干什么”混为一谈。

高阶函数：把 DOM 和事件包起来

once、debounce、throttle、memoize 这四个是前端最常用的高阶函数。原理与逐个 demo 在《JavaScript 防抖与节流的实现与应用》里讲透了，记忆化那套”参数拼 key、缓存失效策略”的推导在《JavaScript 惰性求值与缓存优化》里也写过了，本文不重复推导，只给最小实现并且立刻把它们组合起来用。

实现细节上有两处是刻意的。定时器回调写成了命名函数表达式（function later() {...}）而不是匿名函数，也不要想着靠 callee 去引用外层函数——严格模式下访问它会直接抛 TypeError，而 'use strict' 是我们所有新文件的标配。顺带提醒一个老坑：IE8 对命名函数表达式的处理不符合规范（会额外留下一个同名绑定，循环里创建时容易得到同一个函数引用），所以我这里的 later 都是在外层函数里定义一次、不在循环里生成，绕开了那口锅。

真正想说的是它们怎么组合。滚动加载这个需求同时需要三种约束：滚动事件本身要节流；窗口尺寸变化后要重算阈值，这该防抖；整套绑定只能做一次，否则页面切换后再进来就会有多份监听器叠加。

这套写法天然可复用的原因很朴素：包装器自己就是纯函数，输入函数、输出函数，不碰 DOM、不读全局，所以它能被搬去任何项目；也因为它能被脱离浏览器测试。我实测的行为数据是这样的：每 10 毫秒触发一次、连续 20 次（跨约 200 毫秒）的情况下，debounce(fn, 60) 让 fn 执行了 1 次，throttle(fn, 40) 执行了 7 次（含末尾补的那次）；每 5 毫秒触发一次、共 15 次的情况下，throttle(fn, 30) 执行 4 次。这几个数字同时也是测试的断言依据——测试只需要一个计数器加一个定时器，不需要 jsdom：

最后一个提醒：包装之后的函数是新引用，必须存成变量才能在 off 时摘掉；每次绑定时现调 Hof.debounce(...) 会造出 N 份互不相干的实例，off 摘不掉，还会让多个元素共用同一份待执行参数。《JavaScript 防抖与节流的实现与应用》里那四条上线事故清单值得贴在显示器边上。

数据流视角：事件 → dispatch → 新 state → render

把前面几条拼起来，就得到一个在 2015 年很值得讨论的写法：页面状态是一棵不可变的树，事件不直接改 DOM，而是派发一个 action；action 经纯函数产生新 state；新 state 交给一个渲染函数画出来。

实测（把 jQuery 换成一个只记录赋值的假对象后，原样跑上面这个文件）：连续 dispatch 四次——写入 12 条列表、把关键词改成 abc、再改成同样的 abc、最后发一个无人认识的 action——订阅者只收到 2 次通知；改关键词时 page 顺带回落到 1，最终 state 是 {"keyword":"abc","page":1,"items":12}；再发一个 DELETE_ITEM，新数组的第一项变成原数组的第二项，而原数组的长度与元素引用一个都没动。写入同值时 update 直接返回原引用、dispatch 因此判定”无事发生”，这就是前面那句”引用比较即变化检测”落地之后的样子。

这个模型在工程上给了三件好东西：状态是一棵普通对象树，于是可以序列化（写进 location.hash 让列表页可分享、可前进后退）、可以回放（把 action 序列存下来就能重现用户操作）、可以时间旅行（配合前面的 past/future 双栈）。

必须把话说在前面：这是演示性质的小实现，生产上不要照抄。 最致命的一条是 render 全量重绘 innerHTML——它会丢掉输入框焦点、丢滚动位置、丢掉所有绑在子节点上的事件与 $.data，而且没法增量。真实项目里我仍然按区域做局部更新，只是把”更新条件”从”我记得哪里变了”换成”这一块的输入引用变了”。

放到当时的行业语境里看，这条流水线也不是我发明的：MVC 双向绑定这条路线（AngularJS 1.2/1.3 的 $digest、各家的 observable）走的是”记住依赖、自动脏检查”；而”状态不可变 + 显式派发 + 单向渲染”是 Facebook 在 2014 年提出的 Flux 理念里最核心的一块，社区从 2014 年底就一直在这两种模型之间争论不休。我不会假装知道哪个会赢，但不可变 + 显式 dispatch 这两条即使完全不换框架也能用，这正是本文想给的：它是一项可以随时开始、随时停下的改造，而不是押注。

反面讨论：函数式风格在浏览器里要付的账

只讲好处就是布道，这里把账摊开。

闭包与内存。 每个包装函数都持有一份闭包，debounce 的闭包里挂着 args 和 ctx，而 args 里往往有事件对象和它背后的整棵子树。IE 的循环引用问题（JS 对象与 COM 对象互相引用）会显著推迟这种结构的回收，《DOM 事件移除与内存泄漏》推导过那条可达链，这里只补一句：定时器与闭包也要进清理清单——解绑前先把定时器清掉、把 args 与 ctx 置空，页面卸载前把攒着还没执行的那一次补掉（clear/flush 这两个入口的实现见《JavaScript 防抖与节流的实现与应用》）。

this 语义的丢失。 把 obj.method 当回调传出去，this 就没了：

函数式风格越彻底，这种”方法是对象成员”的写法就越碍事。解法只有两条：给 map 传第二参数 thisArg，或者干脆把方法改成不吃 this 的自由函数（function labelsOf(cart) {...}）。后者是我更推荐的方向，但必须承认它对已经写了几千行原型方法的项目是个改造成本。

可读性与团队成本。 一行五步的管道对新人的负担是真实的：他得先理解 pipe 本身，再理解每一步，还得在脑内确定方向（compose 还是 pipe？）。这种代码在 review 时最容易产生”看起来对其实顺序反了”的通过。我们的约束是：工具函数集中在一个 utils/func.js 里并配文档注释，业务代码里管道不超过 6 步，超过就拆函数。

调试栈帧。 组合子越多，栈越深且帧名越没有意义。前面说过对策（每步具名加 tap），这里给数字：五级 pipe 跑 100 万次调用，reduce 版 25.2 ms、我改写的 for 版 23.7 ms，而手工嵌套 inc(dbl(inc(dbl(inc(x))))) 只要 1.0 ms——约 25 倍。而且 reduce 版和 for 版几乎一样快，说明成本来自”多出来的函数调用与包装层”本身，而不是 reduce 这个 API。这条实测结论很有指导性：想靠”把 reduce 换成 for“来给组合子提速是无效的，只有减少包装层数才行。

中间数组与循环。 同样 10 万元素做”筛出 active 再取 name”：filter().map() 链式 1.32 ms，合并成一次 reduce 1.05 ms，一次 for 0.32 ms。倍率约 4.1 倍和 3.3 倍。绝对值在桌面 node 上都不值一提（我甚至跑了 60 帧、每帧重建 1 万条的 filter+map，每帧约 0.115 ms，占 16.7 ms 帧预算的 0.7%），但请注意两件事：一是老 IE 与低端移动浏览器要按数倍折算，我这里没条件给出可信的对照数字；二是上面那 4 倍里真正贵的是留下的引用——200 份中间数组就吃掉约 100 MB 堆（我两次跑分别得到 98.6 MB 与 113.6 MB）。所以我的取舍标准从来不是”哪一段快 0.3 毫秒”，而是”这份中间数据会不会被留在闭包里”。

结论是：把函数式用在决策路径上（状态、计算、组合），把命令式留在渲染与循环的最后一厘米（DOM 写入、每帧热路径）。 这两件事在同一份代码里共存，一点都不矛盾。

决策清单：什么情况引入哪一条

情况 引入 不引入
新写的工具函数、校验、格式化、URL 拼装 一律纯函数化，放 app/calc/，配单测 不在里面读 DOM、不写时间与随机数
每帧执行、计算密集的热路径（滚动、动画、长列表） 命令式循环、局部拷贝、手写具名闭包 不做全量不可变拷贝、不上多级管道
页面状态（表单值、筛选条件、分页、加载态） 不可变加显式 dispatch，用引用比较做变化检测 不原地改字段再”手动记得通知别人”
处理步骤超过 3 步的数据转换 pipe/compose 加每步具名，必要时 tap 3 步以内直接写语句，别为了优雅而组合
事件与定时相关的约束（只一次、合并、采样） once/debounce/throttle 组合，包装结果存成引用 不共用一份实例、不在绑定时现造包装器
参数顺序不匹配、要提前绑业务 id partial 或手写闭包 不用 callee 取外层函数，不给流程库传包装函数
面对”纯洁度”的技术债（想全项目改成 FP） 只改有 bug 或有测试缺口的模块 不为风格做重构，不搞范式竞赛

如果只能记一句，那就记这个改造顺序：先分层（把 DOM 读写赶到边界）→ 再纯化（让边界内的函数不吃全局）→ 再不可变化（状态更新产生新引用）→ 最后才谈组合子和管道。顺序倒过来做的项目我见过不止一个：先上一堆组合子，结果每层包装里都在偷偷读 DOM，测试没法写，调试栈又长，最后大家一致宣布”函数式不适合我们”。不适合的不是函数式，是那个顺序。

小结

JavaScript 不是函数式语言：没有尾调用优化、没有语言级不可变、没有持久化数据结构，ES6 今年定稿但引擎实现是另一回事。所以我们借的是三条纪律。分层是把副作用赶到边界上，边界内的计算层可以只比较字符串就测干净——我实测的四条 QUnit 断言全部只依赖输入输出。不可变在 ES5 里靠手写的 extend/update，换来时间旅行、引用比较和漏更新的大幅减少，代价是拷贝成本随结构变大而线性上升：改一个 8 字段对象是 0.08 微秒量级，拷一份 1000 元素数组是 29 微秒，所以万级列表的高频路径要退回局部拷贝。组合把五步数据转换写成一行可读的管道，实测与 compose 等价、1 万条列表 0.75 ms，但包装层的调用开销约 25 倍且调试栈变长，对策是每步具名加 tap。高阶函数是 DOM 与事件的适配器，once/debounce/throttle/memoize 本身是纯函数所以可复用可脱离浏览器测，实测 20 次触发防抖执行 1 次、节流 7 次。最后，事件—状态—渲染这条单向流水线在 2015 年还只是个讨论中的方向，但”不可变 state 加显式 dispatch”这部分不用换框架就能拿走。所有这些都不该为了纯洁度而做：小工具纯函数化、热路径留命令式、状态走不可变、组合子只在三步以上引入，顺序按分层到纯化到不可变到组合来推，这篇文章的价值就落地了。
