JSON.parse 与 JSON.stringify 的细节

JSON 在 2015 年已经是浏览器之间交换事实的标准格式，但日常讨论大多停在”它有时会报错”这一层。这篇写给第一次系统接触 JSON 的读者，讲清三件事：JSON 的语法和 JavaScript 对象字面量到底差在哪、JSON.parse 与 JSON.stringify 的可选参数各自能做什么、哪些值会在序列化时被静默改掉。文中的每条结论都在 Node 上实跑过，输出与代码块里写的一致。

JSON 只是 JavaScript 字面量的一个严格子集

最容易搞混的一点：能写进 JavaScript 的对象字面量，不等于能被 JSON.parse 吃下。JSON 的键必须带双引号，字符串只认双引号不认单引号，不允许尾随逗号，不允许注释，值只能是数据——undefined、函数、正则字面量都不在其中，数字也不允许前导零和十六进制。

eval 能吃下它，是因为它按 JavaScript 语法求值，而 JSON 只按自己的语法解析。上面那段里还有两个彩蛋：0x1f 被求值成 31，012 在宽松模式下被当成八进制求成 10——这两处即便侥幸解析成功，值也已经不对了。

结论很干脆：JSON 描述的是数据，不是程序。手写配置时那种”看着顺眼就行”的习惯，一到 JSON 上就失效。另外三个细节也实跑过：JSON.parse 会忽略首尾空白，但尾部多一个字符就报错；"0"、"false"、"null" 各自都是合法的 JSON 文本；空字符串 "" 抛 SyntaxError（Unexpected end of JSON input）。

外部数据不要交给 eval

拿 eval 解析接口返回，等于把陌生人的字符串放进自己的执行环境。

(...) 那对括号是必须的：eval('{"a":1}') 会把开头的 { 当成语句块的开始，直接抛 SyntaxError: Unexpected token ':'。加上括号后它变成表达式，才有返回值。

JSON.parse 的价值正在于它只做解析、不产生任何求值行为，性能也因此可预期。用一份 4.78 MB、26000 条记录的接口数据实测：JSON.parse 13 ms，eval 16 ms，两者都不慢，但前者拿到的结果永远是数据。2015 年仍有大量老代码在 $.parseJSON 和 eval 之间摇摆，其实 $.parseJSON 早年也是一层 eval 封装，jQuery 1.9 之后基本已经退化成原生 JSON.parse 的别名，统一换成原生即可。

JSON.parse 的返回值不一定是对象

JSON.parse 返回的是一个 JavaScript 值，可能是对象、数组，也可能是数字、字符串、布尔或 null。服务端回一个数组或一个裸数字时，直接 data.list 就是 undefined。

想让 replacer 跳过却又要缩进，必须写 null 或 undefined 占位，实测两种写法结果一致。而 JSON.stringify(value, 2) 里的 2 会被当成第二个参数（replacer）而不是缩进——它不是函数也不是数组，于是被整个忽略，输出依旧一行到底，space 得挪到第三位才生效。格式化输出在调试和展示配置文件时很有用——比 console.dir 在 IE 里那种不可复制的结果友好得多。

四个分支都要走一遍：键不存在时 getItem 给 null；值恰好是 null 时存进去的是字符串 "null"、取回来是 null；被别的代码截断或手工改过则抛 SyntaxError；"" 同样抛。用 load(key) || 默认值 兜底看着省事，实际会把存进去的 0、false、"" 这些合法值当没存过——实测 JSON.parse("0") 拿到 0，0 || { id: 9 } 直接给出兜底对象。存之前也应先确认数据是纯的：值为 undefined 的键会消失，JSON.stringify(undefined) 返回 undefined，再被 String() 转成 "undefined" 存进去，下次读必然抛异常。存储层本身的配额、命名空间与跨标签页同步，旧文《localStorage 与 sessionStorage 本地存储实战》已经写透，这里不重复。

接口这边只补一句：所谓 dataType: 'json'，做的事无非是把响应文本交给 JSON.parse，成功回调里拿到的是解析后的值。反过来说，只要这一步没被显式要求——比如没写 dataType、让 jQuery 跟着响应头去猜类型——而服务端回的是 Content-Type: text/plain 却装着 JSON 内容，回调里拿到的就是一串字符串，data.list 得到 undefined。这时别指望框架替你兜住，最稳的做法是在成功回调里显式 JSON.parse 并用 try/catch 接住脏数据。跨域 JSONP 那套”把响应当脚本执行”的原理和风险，在《jQuery 的 getScript 与 getJSON》里已经讲过，不再重复。

__proto__ 这个键名很能说明 JSON.parse 比 eval 安全在哪：

同一个字符串，JSON.parse 把 __proto__ 当普通键放进对象，eval 却按 JavaScript 字面量语义把它当成设置原子的入口。数据能改原型，下游代码的判断就会整体跑偏。不过也别把 JSON.parse 当护身符：拿到结果后 target.__proto__ = obj.__proto__ 这类手工展开照样会污染。

最后一处属于服务端：JSON.stringify 不转义斜杠，</script> 会原样出现在输出里，如果这段 JSON 被直接内嵌到 <script> 标签中，标签提前闭合，后面的内容就成了页面脚本——这是 XSS 的一条现成通路。服务端输出时把斜杠转义成 \u002f（</script> 变成 <\u002fscript>，解析回来的值不变），或者干脆走 application/json 响应头、让前端自己 JSON.parse。同理，U+2028、U+2029 也不会被转义，它们在 JavaScript 里算行终止符，嵌进脚本时同样会截断语句。

小结

JSON 是 JavaScript 对象字面量的严格子集，键加双引号、不认单引号、无尾随逗号、无注释、只放数据；eval 能吃下的东西多，但那是执行代码而非解析数据，外部输入一律交给 JSON.parse。parse 的返回值可能是任意 JSON 类型，判 null 和判 typeof 都省不掉；reviver 自内向外逐键调用，返回 undefined 即删键，很适合还原日期和剥离敏感字段。stringify 的 replacer 传数组是全局白名单（父键必须一起列出）、传函数是逐键过滤，space 收数字或字符串、上限 10 个字符。被静默吃掉的值要背下来：undefined、函数在对象里丢键、在数组里变 null，NaN 与 Infinity 一律变 null，不可枚举属性、方法、原型属性不输出，包装对象拆成原始值，Date 靠 toJSON 变字符串——也正因如此，任何对象自定 toJSON 就能控制自己的输出，同时让 JSON 式深拷贝悄悄改值。循环引用主动抛 TypeError，用已见数组拦截会误伤共享对象，更稳的是拍平成 id 与 parentId。深拷贝只在数据本就是纯 JSON 时才划算，要保留 Date 和原型得手写递归。localStorage 必须成对使用并 try/catch 兜住四种脏数据，别用 || 兜底。IE7 靠 json2.js 补，而 __proto__ 与 </script> 这两处差异，恰好说明了为什么解析数据这件事不该交给执行代码的引擎。
