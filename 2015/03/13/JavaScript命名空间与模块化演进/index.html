JavaScript 命名空间与模块化演进

这是一次复盘，不是写法大全。2013 年接手的那个中后台项目，页面上挂着十几行 <script>，四个人并行开发，谁都能在自己文件顶上写一句 var util = {...}。两年里我们从全局变量地狱一路推到 RequireJS，每一档都付过学费。下面按阶段来：先摆坑，再写当时的解法，最后补一句事后才想明白的结论。IIFE 的语法变形与作用域推导，旧文《IIFE 立即执行函数表达式》已讲透，本文只把它当一块砖用。

起点：全局变量地狱里的三类事故

事故一，同名函数被后加载的脚本覆盖。 我们的 util.js 里写着 var util = { trim: ..., ajax: ... }，后来运营同事在页面上插了一个第三方统计工具，它的包体里也有一句 var util。<script> 顺序是统计工具在后，于是我们所有调 util.ajax() 的页面集体报错，而本地复现不出来——因为本地那个统计工具被注释掉了。var 声明在全局作用域里等价于给 window 挂属性，后执行的赋值直接改写前一个，浏览器一声不吭。

事故二，for 循环的 var i 泄漏改写外层循环。 一个多层表格渲染函数里，外层用 i 遍历行，某天下沉进去的一段公共代码里也写了 for (var i = 0; ...)。因为 var 只认函数作用域、不认块，两个 i 是同一个变量，内层循环把外层计数器直接推到末尾，结果只渲染出第一行。这类 bug 最难查，因为代码各自看都”没问题”。

事故三，调试时在全局执行了同名声明。 有人在 Chrome Console 里为了临时改逻辑，敲了一句 var dialog = {...} 覆盖模块里的实现，本地看着好了，提交时忘了删，另一份文件里的 dialog 也被拖下水。Console 是全局作用域，这个纪律我们是用一晚上线上故障换来的。

排查到最后，靠的不是读代码，而是一段体检脚本：在公共库加载完、业务脚本执行前打一次全局快照，之后随时比对，凡是多出来的名字都是”有人在往 window 上扔东西”。

这是老项目里排查全局污染最实用的土办法：十几行、无依赖、能直接贴在 Console 里跑。两句提醒：for in 在 IE8 上枚举不全 window 的宿主属性，它只能查自己人写的变量；运行中新挂的名字有一部分是正当的（定时器 id、异步注册的插件），比对结果要人工分诊，别当自动化门禁用。

复盘结论：全局污染的根源不是”变量名起得不好”，而是所有人共享同一个可变作用域。靠约定名字（加项目前缀）只是把撞车概率压低，没有把共享拆开。

第一档：命名空间对象与自动建段

最早一步我们只做了一件事：把散在全局的变量收进一个 App 底下。写法看着不起眼，但里面有个坑。

为什么必须 App = App || {} 而不是 var App = {}？因为四个人的文件会被合并成一个大包，var App = {} 在第二个文件里执行时，会把第一个文件已经塞进去的成员整体抹掉。IE8 还额外坑一层：var 重声明本身不报错也不重置，但不少人写的是 App = {}（漏 var）或带初值的声明，合并后行为取决于谁先跑。内层同理，每一层都要”存在就复用，不存在才建”。

层数一多，每个文件手写三行 || {} 就腻了，于是有了自动按点建段的工具函数。它最关键的一条不是能建，而是拒绝覆盖已有的非对象成员：

当年有同事把 App.version 写成字符串，另一个模块 namespace('version.helper') 想往下挂东西。有了这句 throw，问题在页面加载第一帧就暴露；换成悄悄覆盖，就是三天后一个说不清的 undefined。

复盘结论：命名空间只解决”撞名”，解决不了别的。它欠下的账我们后来都还清了——

  • 加载顺序耦合：App.namespace 定义在 core.js，那么所有依赖它的文件必须排在它后面。合并列表一旦有人插队，全站崩，而且报错点离起因很远。
  • 无法真正私有：App.ui.dialog._render 加了下划线照样能被调用。另一位同事觉得这个私有方法”更好用”，直接在外部调它，后来我重构内部实现，他那边静默失效。
  • 全局查找变慢：App.ui.dialog.xxx 压缩后仍是三段属性访问，而局部变量能被压缩器改成单字母，热点路径上差别能量出来。
  • 跨模块依赖全靠注释：文件头上写”依赖 util.js、需先加载”，注释会撒谎，代码不会。
  • 属性名不能混淆：压缩工具不敢乱改 App.util.parseId 这种挂在对象上的名字，只有局部变量能被缩短，命名空间方案在体积上先天吃亏。

第二档：用单例把状态收进闭包

上面”无法真正私有”这一条，只有闭包能解。我们的做法是把模块实例收进一个 IIFE，外部只拿到 getInstance。

这档买到的正好是命名空间付不起的那一条：queue 和 push 不在任何全局对象上，外部只能走 flush() 这个被设计过的出口，下划线从”请求你别碰”变成”你碰不着”。代价也实在——Logger 仍挂在全局、仍可能撞名；它是单例，测试想重置状态得自己加 reset，全页共享一份队列，模块化程度没往前走一步。所以在当时的坐标里，单例是命名空间的补丁，不是它的替代品。

2015 年的选型桌：AMD 与 CMD

到 2014 年底，脚本数量涨到让排序变成一份全职工作，我们开始正式看模块加载器。当年国内能选的主要是两家：RequireJS（AMD，2.1.x）与 SeaJS（CMD，2.x）。

两者的核心分歧不在语法，在执行时机。AMD 是依赖提前执行、异步拉取后统一回调，模块体一开始就拿到完整的依赖对象，代价是哪怕你不用它也得等它加载完；CMD 是就近 require、按需执行，读起来跟同步写法一样自然，代价是模块体可能在”手上依赖一个都没确认”的状态下就开始跑，还把依赖关系藏进了函数体，工具想静态分析就得解析 AST。当年国内讨论很多：一则是 SeaJS 出自国内团队、文档是中文、上手门槛低，二则是这个时机之争确实没有标准答案。我们把同一个模块照两种写法各写一遍，性能差距小到不值得为它做决定；最后真正把我们推向 RequireJS 的是它的优化器 r.js 更成熟——而 r.js 恰好是工程里那件苦差事的主角。

补一句 CommonJS：Node 那边是同步 require，浏览器拿不到同步的文件系统读取，必须靠打包或转换才能用，所以本文浏览器端的代码里没有裸 CommonJS 写法。

第三档：RequireJS 的工程坑复盘

这一节是我们实际花得最久的一段。

坑一：非模块化的老插件不认 define。 页面依赖 jquery.cookie、bootstrap 的 tab 插件、公司内部的几个老工具，全都是直接往全局挂东西的老脚本，写进 paths 只会拿到 undefined。答案是 shim，它只声明依赖和外挂出口，不会把老脚本改造成模块：

两个细节踩过才知道：exports 那句是给”只在初始化时读一次”的老脚本用的，不写 shim 可能判定它还没就绪；shim 里的依赖名要和 paths 的 key 完全一致，写成 'jquery-1.11' 就是加载不到。另外 define(['jquery', 'jquery.cookie'], function ($) {...}) 里 jquery.cookie 不占形参位，它只是副作用挂载——我第一次把第二个形参当 cookie 用，查了半小时。

坑二：缓存击穿。 上线后改了 js/app/util.js，IE 和 CDN 还吐旧的。urlArgs 是给所有模块 URL 统一加版本号最省事的办法，但副作用致命：开发期每次刷新都带新版本号，几十个模块全部回源，本地慢到令人发指。最后的做法是开发期不带 urlArgs、靠 Grunt 0.4 起本地静态服务并禁缓存，只在构建产物里注入版本串。版本号与 CDN 缓存怎么配合，旧文《静态资源版本号与缓存更新》写得更细。

坑三：r.js 打包后 name 与相对 baseUrl 错位。 这是最坑的一个，因为它在开发期完全看不出来。

三个具体的坑：name 多写了 js/ 前缀，r.js 不报错，它按 baseUrl + name 去找 js/js/main.js，找不到就产出一个空壳；appDir 与 dir 不小心指到同一个目录，源码被构建产物覆盖，而 keepBuildDir: false 时它会先清目录；还有相对 baseUrl 到底相对 build.js 还是相对 appDir——是后者，团队里每个人都要被绕一次。paths 里那句 empty: 则是让 jQuery 不打进 bundle、又不阻塞依赖声明。

坑四：循环依赖拿到 undefined。 a.js 依赖 b.js，b.js 又依赖 a.js，两个模块的工厂函数都会有一方拿到尚未导出的 undefined，报错位置却在调用点。

我们的规矩是：依赖只在函数体内访问，绝不在模块顶层解引用。真出现双向依赖，正确解法是把公共部分抽成第三个模块——延迟技巧只会把架构问题藏得更久。

坑五：data-main 与脚本执行顺序。

RequireJS 的 script 标签本身就是异步语义，data-main 指向的文件要等加载器 ready 之后才被注入执行。这意味着页面里任何行内 <script> 都不能假设 App 已经存在。我们出过一次事故：运营在活动页插了段行内脚本打埋点，直接读 App.pageId，快网络下正常、慢网络天天报 undefined。后来的统一约定是行内脚本只允许调 require(['app/boot'], function (boot) { boot.track(); })，把顺序问题交回加载器。

坑六：多页面项目的配置复制。 我们有三十多个页面，各有各的入口模块，但 paths 和 shim 完全一致。错误做法是在 build.js 里再抄一遍 paths——两份配置迟早漂移，漂移一次就是线上一个模块 404。正确做法是构建期用 mainConfigFile 让 r.js 直接读运行时那份配置：

迁移那一周的账

改动量比想象的小，比想象烦。约 40 个业务文件把 var X = (function () {...}()) 的外壳换成 define([...], function () {...})，属于机械操作；shim 与 paths 一次性写完；三十多个 HTML 里那十一行 <script> 换成一行 data-main。真正花时间的是三件事：给所有私有方法补 exports、把散落的隐式全局挨个揪出来（加上 'use strict' 后一次性炸出九个漏写 var 的赋值），以及循环依赖的两处重构。整体三个人两周，其中一周在跑回归。

开发期与上线期的落差要提前讲明白，否则第一天部署就发懵：开发期一个页面几十个请求——加载器、入口、每个模块各一个，还要串行等依赖图，本地比原来的合并包慢得多；构建后合并成一个文件、一个请求，冷启动反而更快。这落差是加载器的固有成本，不是配置写错了。

调试是当时最难受的一环。r.js 压缩后的产物报错基本靠猜，source map 在 2015 年初的支持还很不成样子：Chrome DevTools 刚把支持补利索，Firefox 与老版本 IE 指望不上，r.js 生成的 map 对不回源码我们也碰到过好几回。最后的妥协是留两套产物——测试环境部署未压缩版（optimize: 'none'、不混淆），线上才走压缩版。合并压缩的收益与代价，旧文《资源合并与压缩的收益分析》量化过。至于 webpack，2015 年初它还是 1.x，讨论热但真正当主力的团队很少，我们没上；ES6 的模块语法连规范都还没定稿，本文所有代码只能停在 ES5。

收口：五档方案对照与升级建议

方案 私有性 依赖显式化 按需加载 构建工具链成本 团队上手成本 旧插件适配成本
全局变量 无 无 无 无 零 无
命名空间对象 无，靠下划线自觉 无，靠脚本顺序 无 低，只要合并 极低 无
IIFE 单例 好，闭包真私有 弱，靠参数注入 无 低 低 无
AMD（RequireJS） 好，模块内私有 强，define 声明 是，异步按需 高，r.js 必须配好 中，配置项多 需 shim，逐条验
CMD（SeaJS） 好，模块内私有 较强，就近 require 是 中，优化工具偏薄 中，中文资料多 同样需要包装

务实建议按项目阶段来，而不是越新越好：

  • 单页活动、两三段脚本、一两个人维护：老老实实全局变量加前缀就行，上加载器纯属给自己找事。
  • 五个文件以上、开始有第二个人并行：先做命名空间对象，同时把”全局命名空间体检”变成常驻的调试动作，这一步零工具成本，收益最大。
  • 出现”配置被外部改掉””状态被别处污染”这类说不清的 bug：给这个模块单独上 IIFE 单例，不用全项目改，只把最脏的那块收进闭包。
  • 十几到几十个模块、多人并行、上线要排序：这才有理由上 RequireJS。前提是先跟团队把 r.js 那套配置项和 mainConfigFile 讲一遍，加载器不是装上就好的东西。
  • 已经在写 SeaJS 的项目不必为”AMD 与 CMD 谁更先进”迁移：我们那次对照实测的差距可以忽略，迁移的收益全在生态和优化工具上，而不是语法上。

回头看，真正救过我们的从来不是”用了哪个加载器”，而是把依赖关系从注释和排序里搬进了代码本身。全局变量拆不散，是因为所有人共用一个可写的 window；命名空间挡不住误调，是因为成员始终暴露在外。一条依赖必须写进模块自己的声明里、一份私有状态真的只活在闭包里，这才算开始有模块化；加载器只是把这件事变成机器能校验的形式。
