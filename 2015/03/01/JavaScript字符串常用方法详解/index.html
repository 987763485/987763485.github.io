JavaScript 字符串常用方法详解

字符串方法的数量不多，业务代码里的 bug 密度却一点不低：归一化少写一个 trim、文案截断把 emoji 切成半个、模板填充时昵称里带了个 $&。共同点不是”方法不会用”，而是没把它们组合成可靠的工具函数。本文按工程实践的角度过一遍 ES5 的字符串方法，每个方法配一个真实场景，文末收敛成一份能搬进公共库的 S 命名空间；文中输出都在 Node 里实跑过，IE 差异属历史事实另行注明，正则部分只做最小引用，详见旧文《JavaScript 正则表达式入门与实战》与《正则表达式进阶：回溯与性能》。

字符串是不可变的：先把取值口径统一

第一个要建立的认知是”改不了”。字符串一旦生成，任何”修改”都是产生一个新串，原串纹丝不动：

下标语法是后来才被规范承认的：IE7 完全不认，s[0] 只给 undefined；IE8 认了，但在兼容模式下不够稳。要支持老 IE 就统一用 charAt，它越界返回空串而不是 undefined，代价是空串拼进字符串里静默通过、发现不了。务实口径是：越界自己判 i < s.length，别指望返回值替你报错。

因为不可变，循环 += 在老 IE 上是经典问题：每追加一段都可能把整串重分配一遍，n 段就是 O(n²) 的内存搬运，当年拼一个两千行的表格能在 IE8 上卡十几秒。现代 V8 有 cons string，实测 20 万次单字符拼接 6 ms、join 2 ms，差距可忽略；老 IE 没这优化，所以拼接一律走数组：

写这个 polyfill 有三处要跟原生对齐，都实测过：传 undefined 按字符串 'undefined' 处理；fromIndex 超出串长直接返回 -1；fromIndex 为负数时今天的引擎一律当 0（'abcb'.indexOf('b', -2) 得 1，即从头找），lastIndexOf 传负数则直接 -1。老引擎的折算口径不同，业务里别依赖负数下标。

$$ 这一条是真正的坑，因为它只在”替换文本来自变量”时才炸，而且炸得毫无声响：

坑就隐蔽在最后一行：单个 $ 只有后面不跟 & ` ' $ 或数字时才恰好是字面量，所以”本地测试没问题”不等于安全——昵称是 "$1 房间" 或 "$&" 时，字符串形式会产出第三种东西，且不报错。这也是 replaceAll 用 split/join 更稳的原因：join 不解释 $，'100'.split('0').join('$&') 得 '1$&$&'，字面照搬。结论：替换文本只要可能来自外部输入，就别用字符串形式，改用函数形式。

函数形式的回调签名是 (整段匹配, 分组1, …, 分组n, 偏移量, 原串)，实测参数顺序为 ['user_name=chunle', 'user_name', 'chunle', 0, 'user_name=chunle']；后两个参数是 ES5 才加的，IE8 只能拿到匹配与分组，用到就先测。下面三个工具都靠它：

最后一行是固有短板而不是 bug：连续缩写会被逐个拆开。解法不是写更复杂的正则（那属于正则篇），而是两端约定——接口字段禁止连写缩写，或者在回调里查一张 ABBR 表，命中就整体小写不加下划线。反向的 underscoreToCamel 写 s.replace(/_([a-z0-9])/gi, function (all, ch) { return ch.toUpperCase(); })，实测 'user_name_list' 得 'userNameList'，这个方向没有缩写歧义。

为什么不用一行正则？实测 '1234.567891'.replace(/(\d)(?=(\d{3})+(?!\d))/g, '$1,') 得 '1,234.567,891'——逗号插进了小数部分。先用 indexOf('.') 与 slice 把两段分开、只动整数段，是这个函数唯一要说明的设计。

最小版的 {{key}} 替换旧文给过，这里补的两点是工程必需：未命中的键收集成数组返回，让调用方决定报错还是兜默认值，而不是静默留白；坚持函数回调，昵称 $&和$$ 才能原样进文案。要输出到 HTML 还得先转义：用映射表配 replace 函数，把 & < > " 与单引号分别换成对应实体，实测 escapeHtml('<a href="x">Tom & Jerry</a>') 得 '&lt;a href=&quot;x&quot;&gt;Tom &amp; Jerry&lt;/a&gt;'。

补齐 ES6 才有的能力：repeat、padLeft、padRight

补零、对齐、缩进这三件事，repeat/padStart/padEnd 要到 ES6 才有，2015 年只能自己写，而且实现必须处理”填充串比缺口长”：

Math.ceil(need / pad.length) 会多生成一段填充，所以必须再 slice(0, need) 裁掉：padLeft('ab', 7, 'xy') 裁过是 'xyxyxab'（正好 7 个字符），不裁就得到 'xyxyxyab'（8 个）。两处提前返回也省不得——need <= 0 防目标长度比原串短时把内容截掉（padLeft('12345', 3, '0') 原样返回）；pad === '' 防除零，Math.ceil(need / 0) 是 Infinity，传进 strRepeat 被 parseInt 折成 NaN 再归 0，填充静默失效，这种不报错的错最难查。

三个真实用法：订单号补零 padLeft('7', 12, '0') 得 '000000000007'，字符串排序于是等价于数值排序，这是导出文件命名最常见的动机；日志等级对齐 padRight('WARN', 5) + ' ' + msg，让 INFO 与 ERROR 的正文落在同一列；生成缩进直接 strRepeat(' ', depth) 打头，配置树打印就靠它。

码元与字符的往返也是这一族的事：

BMP 之内的字符可以无损往返：逐个 charCodeAt 再 fromCharCode 拼回去与原文相等（实测含中文的 '前端p2p' 成立）。但 fromCharCode 只认 16 位码元，高位直接丢，所以处理不了代理对：String.fromCharCode(0x1D306) 拿回来的是低位 0xD306 那个私用区字符，实测 === '𝌆' 为 false。'𝌆'.length 是 2，两个码元分别是 0xD834 与 0xDF06，要靠 ((hi - 0xD800) * 0x400 + (lo - 0xDC00) + 0x10000) 才还原得出 0x1D306。ES6 的 String.fromCodePoint 与 codePointAt 正是为收掉这层手工换算准备的，当年只能自己包一个小函数，别在业务里散写公式。

trim 与大小写：老 IE 缺 trim，locale 不请自来

trim 也是 ES5 才有、IE8 没有，polyfill 一行，但字符类要显式列全：

实测现代引擎的 \s 已经覆盖 U+00A0（不换行空格）、U+3000（全角空格）与 U+FEFF（BOM），所以 '　前端　'.trim() 得 '前端'；老 JScript 的 \s 集比标准小，会漏掉全角空格与 NBSP，而中文站最常见的手滑恰恰是从 Word 里复制出一串全角空格——这两个码位必须显式列出。表单归一化的固定起手是 value = value.trim()，再谈校验，否则后端收到 'admin ' 会让权限判定静默失败；埋点同理，不然同一个关键词会统计成两个值。

长度不等于宽度：中文截断与 URI 编解码

'中'.length 是 1，'前端p2p'.length 是 5，视觉上却占 7 列；'𝌆'.length 是 2，只算一个字符。所以 slice(0, 10) 截出的文案既不合排版宽度，还可能把代理对劈成半个——实测 '𝌆'.slice(1) 返回孤立的低位代理 '\udf06'，split('') 也切成两个残缺码元，页面上就是方块或问号。旧文《JavaScript 正则表达式入门与实战》给过一行式的宽度估算，这里给能处理代理对的遍历版与基于它的截断函数：

列表页标题、下拉选项、通知摘要天天用它，max 要从 UI 反推（一行放得下几个双宽字符），而不是随手写个 10。顺带修正上一节 padRight 的短板：按 length 补空格在中文列里对不齐，改成补 width - displayWidth(s) 个就能排出整齐的文本表格（实测 '订单号' 与 'username' 都落到 10 宽）。

URL 编解码的分工只有一句：encodeURI 保结构，encodeURIComponent 保值。

拼参数一律用后者：前者会把值里的 &、=、# 原样留下，一个 ?next=http://b.com/x?id=1 就能搅乱查询串。反向的 decodeURIComponent 遇到畸形输入会抛 URIError（实测 %zz 与残缺的 %E5%89%8D%E 都抛 URIError: URI malformed），而解码处正是用户输入进来的地方，必须包 try/catch——上文 decodeParam 就是这么写的，退回原文比整个函数抛错好得多。decodeURI 不解 %26 这类分隔符级编码，别用它解参数值。

先说明一点：这里的 startsWith 与 endsWith 是我们自己的 ES5 函数，语言层的同名方法要到 ES6 才进标准，当年不能直接挂在字符串上。mask 只用 slice 配 repeat，比写一条”保留前三位后四位”的正则更容易在评审里讲清楚，也更难写错——实测 '13800138000' 得 '138****8000'，位数不足 11 的输入原样返回，既不抛错也不被截半。

工具集背后是三条纪律，都是这两年改 bug 改出来的。一，可能来自外部的字符串先归一化再判断，trim、大小写、编码的顺序固定，别在每个调用点各做一遍。二，判包含一律写 !== -1，取最后一个分隔符一律 lastIndexOf，位置可能来自未命中的 indexOf 就先用变量接住判一次，别让 -1 流进 slice。三，替换文本只要可能含 $ 就改函数回调，宁可多写一个 function，也别在线上看见 Hi {name} 这种文案。字符串方法是前端最便宜的工具箱，便宜在于：写对了就一辈子不用再回头看它。
