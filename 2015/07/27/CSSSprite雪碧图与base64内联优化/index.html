CSS Sprite 雪碧图与 base64 内联优化

本文属于《HTML 与 CSS》第 62/62 篇
上一篇系列目录下一篇

图标请求太多，是 2015 年页面优化里最琐碎也最绕不开的一环。可选路线其实就三条：雪碧图合图、base64 内联进 CSS、iconfont 字体，前两条是本文主角。这次把工具链层面一次讲完：spritesmith 在 Grunt/Gulp 里怎么配、模板产物长什么样、mixin 怎么封装坐标，再把 base64 的体积账、gzip 账与缓存账摊开算清楚，最后给一张能直接拿去用的选型判定表。手写 background-position 的基本功，可参笔者 2013 年底写的《CSS精灵图与图文混排排版技巧》，本文不重复。

图标请求问题的三种解法

HTTP/1.1 下浏览器对同一域名通常只维持约 6 个并发连接，Chrome 43、Firefox 39、iOS 8 Safari 都是这个量级。一张页面上如果有几十个 1 KB 的图标，就是几十次请求往返，每次还有请求头、响应头的固定开销。当年把静态资源拆到 g1 到 g4 多个子域名做”域名分片”是常规操作，但那只是扩大并发数，单张图片的请求成本并没有消失。真正把请求数从几十降到一，三条路：

  • 雪碧图：构建期把一批小 PNG 拼成一张大图，CSS 用 background-position 取子区域；
  • base64 内联：把图片编码成 data URI 直接写进 CSS，零额外请求；
  • iconfont：把单色图标做成字体文件，用伪元素 content 渲染，2013 年起已经流行。

三条路解决的是同一个问题，分歧在体积、缓存粒度、渲染成本和可维护性上。iconfont 本文只做定位对比：它天然矢量、免倍图、颜色可控，但表达不了多色图标，字体渲染边缘也不如位图锐利，多色 Logo 和照片质感的小图仍然要回到位图方案。

flowchart TD
  A[页面小图标过多] --> B{是否首屏必需}
  B -->|是| C{单图是否小于 2 KB}
  C -->|是| D[base64 内联进 CSS]
  C -->|否| E[按模块出雪碧图]
  B -->|否| F{是否全站高频复用}
  F -->|是| E
  F -->|否| G[单文件 URL 加延迟加载]

请求数要连着连接数一起算

单域名约 6 条连接是硬约束，同一连接上的请求还要排队。30 个图标摊到 6 条连接是 5 轮往返，一轮城域网约 30 ms、3G 上 300 ms 到 500 ms 常见，光排队就吃掉一秒多；合成一张后轮次变成 1，这才是合图的真正收益。

域名分片是另一笔账：拆到 4 个子域名把上限抬到约 24，代价是多几次 DNS 解析，连接摊薄后单张大图反而下载更慢，当年建议 2 到 4 个就收手。分片治的是多图并行，治不了小图标串行。发起时机也影响收益：

sequenceDiagram
  participant B as 浏览器
  participant S as 静态域名
  B->>S: 请求 HTML
  S-->>B: HTML 到达
  B->>S: 请求样式表
  S-->>B: CSS 到达并开始构建 CSSOM
  Note over B: 解析到 background 规则才发起图片请求
  B->>S: 请求 sprite.png 第二轮往返
  S-->>B: 图片到达，图标这才可见

雪碧图的真实代价

合图不是免费的，代价有四块，很多文章只讲第一块。

解码内存是宽高的平方。 PNG 落盘是压缩过的，但浏览器渲染时要解码成 RGBA 位图，占用约为宽乘高乘 4 字节。一张 1024×1024 的雪碧图文件可能不到 200 KB，解码后却是约 4 MB 内存；dpr=2 的 2x 图解码面积再翻四倍。这些是我按同一口径的粗估，只给相对量级，不是基准数据。结论只有一个：单张图的上限要盯着宽高，不是只盯着文件体积，低端 Android 的 WebView 在大图上确实会掉帧甚至杀进程。

坐标是全局耦合的。 任何一个图标的尺寸变化，都会让它之后的所有坐标整体位移；拼接时相邻图标之间还要留 padding，否则缩放渲染时边缘互相渗透。手写并维护几十个坐标必然出错，这就是”雪碧图必须交给工具生成”的根本原因，而不是为了省事。

缓存粒度变粗。 更新一个图标，整张图缓存作废，全站用户重下一张大图。所以实践上按模块拆图：全站公共图标一张，每个业务模块各一张，在请求数和缓存粒度之间取中间态。

色深是被整批绑定的。 源图里两张是 256 色 PNG-8、其余真彩 PNG-24，合图要么全升 24 位、体积上涨，要么全降 8 位、渐变图标发脏。纪律：同一张表的源图同格式、同色深、同一条压缩参数。

两个真实踩坑

第一个是邻边渗透。上面说的边缘互相渗透，机制是双线性插值取样时边界像素混进相邻区域；padding 从 2 提到 4、源图再补一圈透明边，transform: scale() 下的渗色才压住。

第二个是 background-position 的百分比语义。百分比不是图片宽高的百分比，而是”容器尺寸减图片尺寸再乘以百分比”。有次容器宽度写成百分比、模板又输出百分比坐标，同一张图在不同宽度下取到不同子区域，看着像坐标算错，其实是参考点变了。此后规范禁止模板输出百分比坐标。

把 spritesmith 接进构建

2015 年主流是 grunt-spritesmith 与 gulp.spritesmith 两兄弟，底层同为 spritesmith，支持多种排列算法和自定义模板。

算法选择是个工程决策：binary-tree 拼出来的图最省，但坐标散乱难排查；top-down、left-right 规整，出问题时对着图一眼能定位。笔者的习惯是开发期用 top-down，上线构建切 binary-tree。

分支落点：IE 8 与高倍屏

IE 8 不认 min-resolution 也不支持 background-size，天然只走 1x 分支，这反而是最省事的回落：默认规则里的 1x 表和坐标正确，IE 8 就不需要额外代码。反过来给它喂 2x 又忘了它无法缩放，图标只露出左上角一小块——这 bug 我见过两次，成因都是只在 Chrome 里看过效果。

base64 内联的账

编码层面的账可以算准：base64 每 3 个字节输出 4 个字符，体积恰好膨胀约三分之一，一个 2 KB 的 PNG 编码后约 2.7 KB。别指望 gzip 救回来——PNG 本身已经是压缩数据，base64 化后再压缩收益很小。

比体积更要紧的是另外三笔账：

  • 缓存账：内联后图标与 CSS 文件同生共死，改一行样式，整个 CSS（连同里面所有内联图标）缓存失效重新下载；独立图片文件则有细粒度缓存。
  • 首屏账：关键 CSS 在渲染关键路径上，每多一个字节都在推迟首次渲染。往首屏 CSS 塞一串 base64，等于把一批背景图变成了阻塞资源。
  • 兼容账：IE8 的 data URI 上限约 32768 个字符且只在 CSS 背景里可靠工作，Android 2.x 老浏览器对超长 URI 的支持只有约 2000 字符。

所以 base64 的适用面很窄：小于 2 KB、首屏就要显示、全站复用率高、数量又少的图标（比如导航上的下拉箭头）值得内联，收益是消灭了一次”CSS 到达后背景图才开始请求”的闪烁窗口；其余场景内联都是负收益。

三条硬阈值

同时满足才允许内联的三条阈值：

阈值 上限 依据
单图落盘体积 2 KB 编码后约 2.7 KB，体积代价开始可见
单个 data URI 字符数 8000 距 IE 8 约 32768 字符上限留足余量
关键 CSS 内联总量 6 KB 再涨就挤压样式表自身的首屏预算

gzip 要单独算：CSS 文本压缩率经验上约四分之三（同产物同机粗测，只看相对量级），base64 段是高熵字符流、几乎压不动，混进样式表会拉低整体压缩率。解析侧成本不在解码快慢而在可读性——塞进几 KB base64 后样式表的 diff 完全不可用，所以内联要收进单独的 _inline.scss，构建时才合进关键 CSS。阈值交给脚本，别靠人记：

选型判定表

把两个维度（单图大小、是否首屏关键）和两个背景条件（复用率、颜色复杂度）合在一起，给出笔者项目里长期执行的一张表：

场景 方案 一句话理由
单图小于 2 KB，首屏必需，数量少 base64 进 CSS 省一次请求且无加载闪烁，体积代价可控
同模块十个上下图标，全站复用 按模块雪碧图，走构建生成 一次请求，坐标交给工具
单图大于 20 KB，低频装饰图 单文件 URL 加延迟加载 大图进雪碧图会绑架所有人的缓存
单色线性图标，要动态改色改尺寸 iconfont 矢量免倍图，一个字体文件搞定
运营活动图，一周改三次 单文件 URL 改动频繁，合图缓存反复作废

四个维度定标尺

四个维度定成可判读的口径，避免评审时各说各话：

维度 判读
模块图标数 N N 大于等于 8 才值得合图，N 小于等于 3 收益不足
单图 1x 体积 大于 20 KB 不进合图，小于等于 2 KB 且首屏才内联
全站复用率 R R 大于等于 3 要细缓存粒度走雪碧图，一次性使用走单文件
是否首屏可见 是则宁可付体积代价消灭第二轮往返，否则延迟加载优先

套一遍：某页 14 个 16 px 图标、2 张 24 KB 背景、1 个下拉箭头。图标复用率高，出一张模块雪碧图；箭头首屏必需又只引用 1 次，走内联；大图保留 URL，进视口再加载。请求数从 17 降到 2，这组数字是同产物同机粗算，只说明判定过程。

请求数与合并压缩的整体收益分析，《资源合并与压缩的收益分析》一篇算过总账；浏览器侧的缓存行为，详见《浏览器缓存机制全景》。格式压缩本身（PNG-8 还是 PNG-24、要不要 WebP），《图片格式选择：JPG、PNG 与 WebP》讲过，雪碧图合图前先把每张源图压到位，比纠结排列算法收益大得多。

移动端要注意的三件事

第一，首屏 CSS 里不要塞大 base64。2015 年 3G 还在当道，首屏 CSS 体积本身就是主要矛盾，图标内联只做导航栏那几个，其余一律走图片或 iconfont。

第二，盯住整页图片内存。iOS 7/8 的 Safari 对单页可用内存卡得紧，一张超大 2x 雪碧图在 iPhone 5 这类设备上有真实的崩溃风险，按模块拆图在移动端的意义比桌面端更大。

第三，WebView 差异。Android 4.4 的 WebView 已换成 Chromium 33 内核，background-size 与 dppx 媒体查询没有问题；存量的 Android 4.3 及以下还是老 Android WebKit，缩放与媒体查询表现参差，稳妥策略是给这部分设备直接回落 1x 图，不为它们写第三套模板。

小结

三条路线各守一段边界：雪碧图吃”多而小的复用图标”，base64 只吃”极小且首屏”，iconfont 吃”单色矢量”。雪碧图的工程落点在工具链——spritesmith 出图出表，模板做坐标与倍图换算，mixin 隔离业务代码，业务侧永远只写图标名。base64 的账要算三笔：膨胀三分之一、缓存粒度归零、首屏 CSS 变重，算完再决定内联谁。移动端把宽高当内存看、把首屏 CSS 当预算看，这两条纪律比任何具体技巧都持久。
