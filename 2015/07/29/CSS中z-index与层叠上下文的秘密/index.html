CSS 中 z-index 与层叠上下文的秘密

本文属于《HTML 与 CSS》第 21/62 篇
上一篇系列目录下一篇

z-index 在很多人心智里是一条数轴，数字大就盖住数字小。但浏览器实际管理的是一棵树：层叠上下文（stacking context）嵌套成层级，比较只发生在同一棵树杈内部。想通这一点，”子元素 z-index: 9999 干不过父级 z-index: 1“”transform 让 fixed 弹层错位”这些怪事就都是同一个答案。本文按笔者 2014 到 2015 年的踩坑实录展开，最后给一套能直接落地的 z-index 分层约定和调试手法。先说明一句：层叠上下文与 BFC 不是一回事，前者管绘制顺序，后者管布局，BFC 的触发条件与遮挡关系见《BFC块级格式化上下文原理与应用》，本文不再重叠。

层叠上下文是一棵树

先看让无数人熬夜的最小复现：

结果 .panel-tip 永远压在 .header 下面，无论它写多大。原因：.panel 的 z-index 非 auto，创建了一个层叠上下文；.panel-tip 的 9999 只在这个上下文内部排序，出不了这个门。.header 与 .panel 在根上下文里比较，2 大于 1，于是整个 .panel 子树（连同里面的 9999）一起被压住。z-index 的比较从不跨上下文进行，这是全部怪象的总根源。

顺带记住 auto 与 0 的差别：定位元素 z-index: auto 不创建新上下文，它的定位后代继续参与祖先的排序；写成 0 就创建了。”没写数字一切正常，补个 0 之后弹层突然被盖”就是这么来的。另外 2015 年在 Chrome 43、Firefox 39 上，flex 项目的 z-index 不需要 position 也生效，这是 Flexbox 规范定的行为，排查时别漏。

创建层叠上下文的条件

2015 年主流浏览器上，下面这些声明会让元素成为层叠上下文的根：

  • 根元素 html 本身；
  • position 非 static 且 z-index 非 auto；
  • opacity 小于 1；
  • transform、filter、perspective 等非 none——CSS Transforms 与 Filter 效应里明确它们创建层叠上下文，当年各家的 filter 前缀实现基本一致；
  • will-change 指定了 opacity、transform 等属性时提前创建（2015 年 Chrome 与 Firefox 已支持，Chrome 约 36 起）；
  • 老 IE 另有一套：拥有 hasLayout 的元素在 IE6/8 里会表现出类似独立层的行为，属于私有实现，写代码时当它是历史包袱，排查老 bug 时又必须知道。

对照上一节的坑，很多”我什么都没写 z-index”的元素其实是被动创建者：设计上随手一条 opacity: 0.9 的装饰层、为了 GPU 加速加的 transform: translateZ(0)，都在悄悄改写整棵层叠树。

把这几类触发声明摊开对照，多出来的一列是排查时真正要小心的：

触发声明 创建上下文 改写 fixed 包含块
transform、perspective 非 none 是 是
filter 非 none 是 否
opacity 小于 1 是 否
position 非 static 且 z-index 非 auto 是 否

两列同时为”是”的是双坑行：transform 与 perspective 一边收编层级、一边改写 fixed 的参照物，看着像两个 bug，其实来自同一行声明。

一个上下文内部的绘制顺序

CSS 2.1 规定同一个层叠上下文内部按下面的顺序绘制，越靠后越在上：

  1. 上下文根元素的背景与边框；
  2. z-index 为负值的子层叠上下文，按值从小到大；
  3. 常规流中的非定位块级后代；
  4. 浮动元素；
  5. 常规流中的行内内容；
  6. z-index 为 auto 或 0 的定位后代与 z-index: 0 的子上下文；
  7. z-index 正值的子上下文，按值从小到大。

“定位元素盖普通元素、正值盖负值、背景垫底”这些口诀都只是这张表的投影。它还能解释一个细节：第 3 步的块盒在第 4 步浮动之前绘制，但普通块盒宽度不考虑浮动，所以文字（第 5 步）会避开浮动而行——这恰好是 BFC 那篇文章里”区域不与浮动重叠”的另一半真相。

为什么第 7 步让子元素失效

第 6、7 两步要连起来读：子上下文是一张不可拆分的卡片，它连同内部所有后代被当一个整体排序，卡片里的 9999 只是内部编号，外层只比卡片根的数字，拿两个兄弟上下文走一遍：

第 7 步取 1 和 2，.b 连内部那个 3 一起盖住 .a 里的 9999。被比较的数字只有两种：同上下文内的兄弟数字，以及子上下文根的数字，隔一层就失去意义。还有一点：第 6 步这一组按文档顺序绘制，DOM 靠后的在上，两个元素都写 z-index: 0 也不等于层级相同。

坑一：弹窗被父级上下文压住

线上最贵的一次事故：订单列表页的详情弹窗，在页面上永远被右侧悬浮工具条盖住半截。检查 DOM 后原因是弹窗组件被塞进了表格容器里，而那个容器为了做滚动有 position: relative 和 z-index: 1，工具条在根上下文里 z-index: 5。按层叠树的逻辑，弹窗写 99999 也没用。

修法两条，选了一条执行：把弹窗挂载点移出一切业务容器，统一 appendTo(document.body)，让弹层参与根上下文排序：

另一条是把容器 z-index 改回 auto，但那会让容器内其他定位子元素的相互关系重新洗牌，回归测试成本更高。工程结论：模态框、tooltip、下拉面板这类”要盖住全世界”的东西，DOM 位置上就该属于 body 的直接子树，这是结构问题不是数字问题。顺带区分：如果弹窗是被 overflow: hidden 裁掉而不是被盖住，那是包含与裁剪问题，跟层叠无关，两者的修复方向完全不同。

坑二：transform 让 fixed 失效并顺带改层叠

移动端页面做过一次”性能优化”：给页面根容器加 transform: translateZ(0) 期望提升滚动流畅度，结果吸底按钮不再贴住视口，而是跟着内容滚走了，弹层关系同时全乱。两件事同源：按 CSS Transforms 规范，带变换的祖先会成为其后代 position: fixed 元素的包含块，fixed 退化成相对该祖先定位；而这个祖先同时创建了新的层叠上下文，原本在根上下文排序的弹层全部被收编。

2015 年主流浏览器对这个行为已经统一：Chrome 43、Firefox 39、iOS 8 的 Safari 都按规范执行，但 iOS Safari 在 transform 祖先内的 fixed 元素上仍有重绘错位的零星 bug。实践守则：要做 GPU 提升，把 transform 加在真正做动画的元素上，动画结束再撤掉；绝不要给包含 fixed 内容的祖先容器加常驻 transform。含 transform 的祖先链，排查层级问题时应当作”这里有隐藏上下文”处理。

最小复现可以直接贴进空白页面跑：列表页里 .page、.list、.item 三层嵌套，卡片点开”更多”，菜单永远被右下角工具条咬掉半截：

层叠树的形状是：

flowchart TD
  R[根上下文 html] --> L[list 因 transform 成为卡片 按 0 参加排序]
  L --> M[menu 1000 只在 list 内部有效]
  R --> T[toolbar z-index 30]

排查按这个顺序走，不要跳步：

  1. 先分清遮挡还是裁剪：看 .menu 的 computed style 与 getBoundingClientRect()，尺寸位置都正常、只是看不见，才进层叠排查。
  2. 确认包含块：.menu 的定位祖先是 .item，top: 100% 相对它算，位置没错，剩下的是绘制顺序问题。
  3. 沿祖先链找上下文触发点，第一个命中就是 .list 的 transform。
  4. 现象至此可以解释：.list 是一张卡片，按 z-index: 0 那一组参加排序，toolbar 的 30 在第 7 步，整张卡片连同里面的 1000 一起被压。
  5. 决定动哪一边：给 .list 补 z-index 会让列表内部所有定位元素重新洗牌，回归面大；把 .menu 移到 body 直接子树只动一个组件。事故里选了后者。
  6. 别试”把工具条降到 0”：它和 .list 落在同一组，组内按文档顺序绘制，工具条在 DOM 里靠后，照样盖着。

坑三：opacity 动画期间兄弟层级被吞

一个淡入的遮罩层，动画期间内部的关闭按钮被外部元素穿透盖住，动画结束后又恢复正常。查了很久才定位：jQuery 的 fadeIn 在中间帧把元素 opacity 设成小于 1 的值，按规范这一刻元素创建了层叠上下文，内部定位元素的排序范围被整个收进去；到 1 时上下文消失，层级恢复。视觉上的表现就是”闪一瞬间的错层”。

替代方案是把半透明做进颜色而不是元素：用 rgba 背景色，元素自身 opacity 保持 1，就不会碰层叠树。老 IE 里 filter: alpha(opacity=...) 的行为与标准 opacity 不同，不会以同样方式创建上下文，这也是同一份代码在 IE8 里”看不出毛病”的原因之一。

z-index 的工程治理

9999 与 1000000 是技术债的写法：它们不解决层级问题，只保证下一层出现时所有人继续加码。项目里从 2014 年起执行一张分层常量表，业务代码禁止出现裸数字：

层级 常量 值
下拉菜单、tooltip @z-dropdown 100
固定头、固定导航 @z-fixed-header 200
遮罩 @z-mask 290
模态弹窗 @z-modal 300
全局 loading、toast @z-toast 400

配套三条纪律：每一层之间空出量级，新增组件只会落到某个空档，不会逼着全表重排；组件内部相对排序只用个位数，禁止碰全局常量；弹层类组件必须挂在 body 直接子树（见坑一），常量治理管数字，挂载规则管树，缺一不可。落地难点不在写变量而在评审：常量表放进样式表的第一个文件，400 以上不再分配，给第三方控件（日历、地图、客服浮窗）留升空间；同层要再细分就用常量加个位数，别新起一个层级名。

Chrome 40 前后的 DevTools 已经能在 Esc 抽屉里打开 Layers 面板，看到 transform、opacity 触发的合成层。注意合成层与层叠上下文是两个概念，但触发条件高度重合，用它反查”谁悄悄创建了上下文”很有效。更粗暴也更好用的是全页描边，控制台直接跑：

配合排查心法，一条流程走完大部分遮挡 bug：

flowchart TD
  A[元素 A 被 B 盖住] --> B{A 与 B 在同一上下文吗}
  B -->|否| C[沿 A 的祖先链找隐藏的 z-index opacity transform]
  C --> D[把问题组件移出该祖先或收掉触发声明]
  B -->|是| E[比较同层 z-index 再查绘制顺序表]

层边界与重绘闪烁清单

Chrome 43 前后能落地的三步，按排查顺序：

  1. 打开合成层描边与重绘闪烁两个开关。入口在 flags 页与 DevTools 设置之间挪过几轮，找不到就搜 layer 和 paint；开启后每个合成层带彩边与层号，重绘区域闪绿框。
  2. Layers 面板看层树，切到 3D 视角把层沿 z 轴散开，反查”这一层凭什么被单独合成”，transform、opacity、fixed 通常是答案。
  3. 与前面的描边脚本交叉验证：层树看不见 z-index: auto 的定位元素参与同一个上下文，脚本也看不见哪层真的走了 GPU，两份现场叠起来才不被误导。

Firefox 39 没有等价面板，只能靠描边脚本；IE 11 的 F12 看不到层树，当时普遍插一个高层级诊断块，看谁压谁。

IE 的现实

这些不是历史笑话，2015 年 7 月的今天，IE8 还活跃在政企客户的回归测试矩阵里。IE7 及更早版本里，给装饰层写负 z-index 垫到内容下面，有时会被父元素背景吃掉、有时又蹿到不相干元素上面，行为与元素是否拥有 hasLayout 直接相关；当年的通用解法是给参与层叠的父容器补一条 zoom: 1，让它拿到 hasLayout、形成稳定的独立层。IE8 里带 hasLayout 的元素即使没有 position 也会表现出隐式的层关系，浮动的列表项盖住绝对定位内容这类事并不罕见。给当年测试同事的一句话总结：凡是参与层叠讨论的元素，显式写 position 与 z-index，并且给共同父级触发 hasLayout，不给 IE 的自由发挥空间。

小结

层叠上下文是一棵树：z-index 只在同一棵树杈内比较，子元素的 9999 出不了父级 z-index: 1 的门。创建它的条件里，position 加 z-index 是明面上的，opacity、transform、filter、will-change 是暗桩，老 IE 的 hasLayout 是另一套私有规则。几个坑共用一个根因：弹窗要挂 body 而不是跟容器嵌套；transform 提升只加在动画元素本身；半透明优先用 rgba 而不是 opacity；blur(0) 这类看不出效果的 filter 残留要当 bug 清掉；负 z-index 必须先给容器一个上下文根。工程上用分层常量表管数字、用挂载规则管树、用描边脚本、祖先链脚本和 Layers 面板做现场勘查。把树画出来再调层级，比把数字调大快得多。
