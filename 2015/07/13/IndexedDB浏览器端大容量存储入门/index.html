IndexedDB 浏览器端大容量存储入门

本文属于《HTML 与 CSS》第 54/62 篇
上一篇系列目录下一篇

localStorage 那套键值盒子在《localStorage 与 sessionStorage 本地存储实战》里已经被坑过一轮，移动端离线与列表快照的取舍则在《移动端离线存储与缓存》里讲过。本文补上另一块：当你要在浏览器里存几万条结构化记录、存图片二进制、存没提交完的草稿队列时，IndexedDB 怎么用、它在 2015 年 7 月的浏览器矩阵里长什么样，以及事务、版本号、事件回调这三处最容易翻车的地方。面向第一次碰 IndexedDB 的前端，全文代码只用 ES5，读完能直接搬走一套骨架。

为什么 localStorage 先撑不住

前作里那条”约 5 MB、整个源共享”的容量口径只是表面理由，真正让人在半年迭代里被迫换路子的是下面四件事，它们加在一起才构成”该上 IndexedDB”的信号。

第一，它是同步的。读一个大 JSON 会直接占住主线程，写也一样，低端机上写几百 KB 就能看见滚动掉帧。桌面端把整个列表缓存进一个键，刷新时读回再整份解析，代价是首屏那段不可点的时间；换成 IndexedDB 则是异步事务，这段时间还给用户。

第二，它只能装字符串。一个两万条的数组，每写一次都要整份序列化再整份反序列化，改一条也得重写全串。IndexedDB 走结构化克隆，存的就是对象本身，日期、数组、嵌套结构原样取回，还能直接把 File、Blob、ArrayBuffer 当作值放进去，不必转成 base64 让体积再涨三分之一。

第三，它没有查询能力。键值对只能按 key 精确取，想”按更新时间取最近二十条”或”取所有 status 为 draft 的条目”，必须把整张表读回内存再自己 filter——这就把第二点的序列化成本又乘了一遍。IndexedDB 把排序与范围筛选交给存储层，游标只把你要的那几条交回来。

第四，跨标签页共享同一池子带来的连锁反应。前作写过 storage 事件的派发规则，它是同步派发的：一个页签在循环里连续写十次，同源其他页签就被连续打断十次，数据量大时这条路本身就成了问题。IndexedDB 的并发靠事务与 versionchange 协商，也有坑（见第六节），但读写不再挤在主线程上。

一句话判断口径：配置项、标记位、几十个键继续用 localStorage；一旦需要”很多条、能查、可能是二进制”，就该换。

心智模型：从键值对换成”仓库加索引加事务”

第一次写 IndexedDB 的挫败感，八成来自拿键值对的心智去套它。它更接近一个嵌在浏览器里的对象仓库集合：一个 origin 下可以有多个数据库（Database），每个库里若干对象仓库（Object Store，作用相当于表），每条记录（Record）是一个值和它的键（Key），键可以来自记录自身的某个字段（keyPath），也可以让数据库自己发号（autoIncrement）。索引（Index）不是新表，而是”按记录里某个字段的值再排一遍序”的视图，从索买进拿到的还是原记录。所有读写都必须挂在事务（Transaction）上，事务是原子单位，也是生命周期最短的那个东西。

flowchart TD
  A[Database 一个 origin 下多个库] --> B[Object Store 对象仓库]
  A --> C[Transaction 事务]
  C --> B
  B --> D[Record 一条记录]
  D --> E[Key 来自 keyPath 字段或 autoIncrement]
  B --> F[Index 按某字段重排的视图]
  F --> E

和 Web SQL 对比会更清楚它的思路。Web SQL 是关系表：写 CREATE TABLE、给列定类型、用 SELECT ... WHERE ... ORDER BY 表达条件，值和结构是分开的。IndexedDB 是”面向文档加索引”：一条记录就是一个完整对象，字段可以缺失、可以是数组（配 multiEntry 索引），条件表达不用 SQL，只能靠”键范围加索引加游标”这一套。它天生没有 join 也没有 WHERE，跨仓库的关联只能把 id 存进字段再查第二次；多条件组合与模糊搜索不是强项，硬做得自己拼复合 keyPath。选型时想清这条，能避免一半的”写到一半发现查不出来”。

2015 年 7 月的现实矩阵

下表按项目必须覆盖的档位整理，口径是”有没有前缀可用”，不是”好不好用”。

前缀要一次问清楚，别在代码里到处写 window.indexedDB：

{ READ_WRITE: 'readwrite' } 这个兜底是给老 Firefox 与旧 Chrome 的：它们的 IDBTransaction 上曾挂过 READ_WRITE、READ_ONLY 这类常量，规范后来改成传字符串模式，这个空对象能让老内核读常量时不抛。新代码直接传 'readwrite' 就行。

检测也别只判对象存在：Modernizr 3 的 indexeddb 测试会真去开一个库，而且是异步的，只能用回调读结果。

事件加回调的手感，和 jQuery 习惯的冲突

idb.open(name, version) 返回一个 IDBOpenDBRequest，它不是数据库，是一个”会发事件的对象”。你要在上面挂三个处理函数：onupgradeneeded（本地版本低于你要的版本，或者库还不存在时进来，这里是唯一能改表结构的地方）、onsuccess（拿到了 IDBDatabase）、onerror（打不开）。顺序上 onupgradeneeded 先于 onsuccess，而且升级事务在 onupgradeneeded 里能拿到。

这套手感和 $.ajax 差别很大。$.ajax 是一个请求一个结局，成功或失败两条路，你写完就忘了。IndexedDB 里请求对象、事务对象、数据库对象各自都会发事件，一次”读十条数据”要挂的四五个处理函数是分层的：请求的 onsuccess 给你结果，请求的 onerror 会向上冒泡到事务，事务的 onabort 与 oncomplete 才代表真正落库。忘掉 oncomplete 是最常见的一类 bug——单个请求 onsuccess 了并不表示数据已经持久化。拼写也有坑：onupgradeneeded 写成 onupgradeneested 不会报错，回调只是永远不触发，你只在 onsuccess 里读到 NotFoundError，排查方向当场就跑偏了。

但要写清楚前提：2015 年 7 月这条路上并没有 Promise 可用。Chrome 与 Firefox 39 已经内置，IE 全系到 Edge 12 都没有，Android 4.4 那个 Chrome 33 的 WebView 也不保险。要用就得引 es6-shim 或 core-js 这类 polyfill，还要确认它补的是构造函数还是全部方法。本文示例一律保持回调风格：调用点只有两三个时，回调比多引一个依赖更省事。

版本号与 schema 迁移

库的结构只能在建库时定，和 localStorage 那种”塞进去再说”完全不同，因此自带一个严肃的版本号问题。规则是三条：open 时不传版本号会拿到当前版本且不触发升级；传的版本号必须严格大于本地版本才会进 onupgradeneeded；版本号只增不减，降级一律以 VersionError 失败。线上的库版本号一旦发出去就收不回来，别学 localStorage 那样随手改。

onupgradeneeded 里的正确姿势是按 oldVersion 逐级补齐，每个分支都写成”从这一级往前进一步要做什么”，并且判断幂等：

漏建索引这一条要单独强调：createIndex 只在升级事务里能调，一旦版本号发出去忘了建，后来所有 objectStore(...).index('byStatus') 都是 NotFoundError，唯一的补救是再涨一个版本号在 onupgradeneeded 里补建。这意味着新版本第一次访问要补跑一次全量索引构建，数据量大时最好在页面上给一句”正在升级本地数据”，同时把 onupgradeneeded 里做的事压到必要范围。

事务活不过这一轮同步代码

这是 IndexedDB 最反直觉也最经典的一个坑。规则一句话：所有已排进队列的请求跑完、且当前这轮同步代码不再提交新请求时，事务自动提交。也就是说，事务的生命周期不看你什么时候拿到结果，只看你在同一个同步执行块里排了多少请求。

sequenceDiagram
  participant C as 业务代码
  participant T as 事务
  participant D as IndexedDB
  C->>T: transaction() 创建事务
  C->>T: 同步排队请求一
  C->>T: 同步排队请求二
  T->>D: 依次执行
  D-->>T: 请求 onsuccess
  Note over T,D: 本轮同步代码结束且无待处理请求时自动提交
  D-->>C: tx.oncomplete
  C->>T: 异步回调里再用同一个事务发请求
  T-->>C: TransactionInactiveError

事故现场通常长这样：

setTimeout、$.ajax 的回调、任何一次跨异步的续写都是同一类问题，postMessage 也一样。正确做法是把顺序调过来：先取数据，再在一个同步块里把全部请求排进同一个事务。

由此推出三条实操结论。第一，游标遍历是安全的：cursor.continue() 和 advance() 本质是往同一个事务里再排一个请求，事务因此保持活动；但如果你把 continue() 放进 setTimeout，遍历就死在中途。第二，别在 onsuccess 里做跨异步的续写，渲染逻辑攒到 oncomplete 之后一次性做。第三，事务是原子的：同一个读写事务里十五条 put，一条因主键冲突失败就整批回滚，这也正是缓存写入一律用 put 而不用 add 的理由。

读写骨架

建库与建索引见上一节，这里给完整可跑的读写部分：主键取一条、键范围取一批、游标翻页。

getAll 写起来最舒服，但 IE 系到 Edge 12 都没有它，所以要么用能力判断，要么统一走游标：

游标倒序翻页最实用。注意索引游标上 cursor.key 是索引值、cursor.primaryKey 才是仓库主键，混了就会翻出重复或漏一条。

想跳过整页可以 cursor.advance(n)，但翻页语义还是”记住上一页最后一条的排序键”最稳，因为 updatedAt 可能重复。二进制场景顺手补一个：待上传的图片可以把 File 直接存进去，浏览器按结构化克隆保存真实字节。

容量与速度：只承认自己测出来的相对量级

配额这件事我不打算给任何”权威数字”。各家实现的默认配额、是否按磁盘空间比例、是否需要申请，口径互不相同，同一浏览器在无痕模式、磁盘将满、私有模式下还会再变。规范只保证一件事：装不下时报配额类错误，你可以据此逐出旧数据。所以做法和前作探测 localStorage 一样：自己测、自己留预算、写失败就逐出，别把某个网页上的”50 MB”抄进设计文档。

速度也一样。下面这两段是同一台机器同一口径的粗测，只看相对量级，不要拿去和别人的数字对比：

粗测只承认两条相对规律，而这两条在任何机器上都成立：批量事务明显快于逐条事务，因为每条事务都要走一次提交与落盘；带索引的范围查询明显快于”整表游标扫一遍再自己筛”。毫秒数换台机器就作废，别引用。

三种手段放在一起的横向口径：

维度 localStorage IndexedDB Web SQL（已废弃）
读写方式 同步 异步事务 异步回调
能存的值 只有字符串 对象、数组、日期、Blob、File 标量列与 BLOB
查询能力 无 键范围与索引游标 完整 SQL
结构变更 无所谓 必须升版本号走迁移 需 ALTER TABLE
原子性 无 事务保证 事务保证
覆盖范围 IE 8 起普遍可用 IE 10 起，老 Android 无 iOS 与 Android 4.x 内置，IE 与 Firefox 无
合适用途 配置项、标记位、小快照 大量结构化记录、二进制、待提交队列 只用于迁移历史数据

什么时候干脆别上

选型表反过来写更有用。这几条判断是笔者一年下来比较笃定的口径：

场景 选择 理由
主题、语言、列宽、开关标记 localStorage 几条键而已，同步读反而省事
一次性表单流程的中间状态 sessionStorage 关掉就该消失
用户草稿、几万条列表快照、待提交队列 IndexedDB 要容量、索引与原子性
图片与文件二进制的暂存 IndexedDB 结构化克隆直接存 Blob
服务端要参与判定的任何状态 服务端 客户端存什么都不可信
要求跨设备一致的收藏与设置 服务端加接口缓存 本地按 origin 隔离，换设备就没
需要全文检索或多条件组合筛选 服务端 索引模型撑不住
只支持 Android 2.3 与 4.0 的项目 Web SQL 过渡或退回 localStorage 这一档根本没有 IndexedDB

还有一条容易被忽略的：IndexedDB 仍然是缓存，不是数据库。系统回收、用户清数据、无痕模式、磁盘写满都会让它变空，所以每次读取都按”可能读不到”写，读到也要标明它是几点的数据——这条心法和移动端那篇是同一个。

库的取舍与兜底链路

2015 年还能叫得上名字的封装基本只有 idb-wrapper（npm 包名 idb-wrapper）这一支，它的调用形状大致是这样：

它把建库、升级、请求回调压成函数调用，读代码的人轻松，代价是事务边界看不见。而第六节那个坑，恰恰只在你能看见事务边界时才踩不到：封装库里”一次 put 一个请求”看着无害，实际上你没法把二十条排进同一个事务，性能与原子性两头都丢。笔者的实践是裸写，或自己包一层不超过一百行的薄壳，并且这层壳必须把事务对象交给调用方（留一个 withStore(names, mode, fn) 之类的入口），而不是把事务藏在里面。当年别的封装要么太新要么太旧，不值得为少写几行回调去引。

IndexedDBShim 是另一类东西，它用 Web SQL 假装出 IndexedDB 的接口，覆盖老 Android 与 iOS 7。它能让代码跑起来，却不能让语义一致：事务原子性、键范围排序、结构化克隆对 Blob 的处理都是模拟的，容量口径也换了。非核心路径（比如兜住列表快照）可以用，但不要让它承担待提交队列这种”丢一条就是事故”的数据。探测与兜底建议排成一条明确的链：

小结

IndexedDB 和 localStorage 的差别不是容量数字，而是三个模型级的差别：值是结构化克隆的对象而不是字符串、查询靠仓库与索引而不是整表读回内存、读写必须在事务里而事务只活”这一轮同步代码”那么长。上手期真正花时间的是三件事：onupgradeneeded 与 versionchange 那套版本号迁移纪律（漏建索引就得再涨一个版本，别的页签不让路就永久阻塞）；事务里一次性排队（异步回调里复用事务必然 TransactionInactiveError）；以及把 open 的请求事件、请求回调、事务回调三层拼对。兼容性上，2015 年 7 月的现实是桌面主流内核都能用，IE 10 只是残片子集、IE 11 与 Edge 12 缺 getAll、Android 2.3 与 4.0 压根没有，兜底链必须留——而兜底只保证”有内容可看”，不保证容量与原子性。

判断口径留到最后：数据量超过若干 MB、需要按字段排序筛选、要暂存 Blob 或离线待提交队列，就上 IndexedDB；配置项与标记位继续用 localStorage；服务端要参与判定的任何东西都不许落在客户端。配额与耗时不要用别人的数字，同一台机器同一口径的粗测，只承认相对量级。
