CSS Reset 与 Normalize.css 的选择

本文属于《HTML 与 CSS》第 19/62 篇
上一篇系列目录下一篇

样式表的第一行该写什么，2015 年仍然是团队里能吵起来的问题。一边是 Eric Meyer 的 Reset CSS 2.0，把浏览器默认值全部抹平，从零重建；一边是 Normalize.css 3.0.x，保留有用的默认值、只修补各家不一致的地方。这不是”哪个更先进”的问题，而是”我的项目里，浏览器默认值是资产还是负债”的问题。本文把两者的来历与代价摊开，给一张落到具体规则的对比表、一套在 Less/Sass 里混合使用的工程做法，以及被 reset 顺带牺牲掉的可访问性与结构层级。适合在起新项目、或者要给老项目统一样式入口的同学。

Reset 的思想史：三步走到”抹平一切”

现代 reset 的做法不是一次成型的，它经过了三个节点。

第一步是 Douglas Bowman 在 2004 年前后为 Yahoo! UI Library 写的那份 reset。他的出发点很朴素：不同浏览器给 h1、ul、body 的默认 margin 与 padding 不一样，导致同一个页面在不同机器上首屏位置就不同。解决办法是把这些盒子模型相关的值统一清零，让所有开发者从同一条起跑线开始。

第二步是 Tantek Çelik 的”reset reloaded”。他在做 Typekit 相关排版实践时把 reset 收窄了一轮，核心变化是不再逐个属性写死，而是让元素 font: inherit、把字号统一成 100%——目标从”消除差异”变成了”消除继承的不确定性”。这一步很关键：它把粗体、斜体、标题字号这些语义带来的视觉差异也一并抹掉了，只留一个干净的排版底面。

第三步是 Eric Meyer 的 Reset CSS 2.0（2011 年 3 月定稿）。它把前两步合成一条超长选择器列表，margin: 0; padding: 0; border: 0; font-size: 100%; font: inherit; vertical-align: baseline 一次作用到从 div 到 section 的所有元素，再补上 body { line-height: 1 }、ol, ul { list-style: none }、table { border-collapse: collapse } 这些针对性规则。今天大多数人说的”reset”，就是这一份或者它的变体。

HTML5 新元素也在那条列表里，所以配合 html5shiv 时还要补一句 display: block——这是 2015 年仍能在项目里见到的写法。

抹平一切的代价

Reset 的收益是确定性，代价是你重写了整个 UA 样式表。具体会疼在四个地方：

  • 列表变成没有 marker、没有缩进的纯文本堆。所有导航、目录、富文本正文里的有序列表都要靠 utility class 把样式还回去。
  • strong 与 em 的粗体斜体消失。编辑用富文本编辑器写出来的强调，在前台看不出重点——这条对内容站是致命的。
  • 标题层级在视觉上被压平。h1 到 h6 同样字号，DOM 里结构清晰，页面上完全读不出来，得自己重建一套字号梯度。
  • 表单与按钮的代价最直接：fieldset、legend、label 被清成零边距零边框，加上常见的 border: 0 变体写法一路命中控件，原生外观、内边距、焦点环一起消失，等于把按钮当文字重做一遍。顺带一提，Meyer 2.0 还给 mark 写死了黄底黑斜体，本意是让高亮语义跨浏览器一致，但多数项目并不想要这份”一致”。

这些代价在后台系统里几乎无痛——反正每个组件都要重写。在内容站里就是持续失血。

Normalize.css 的三条原则

Normalize.css 由 Nicolas Gallagher 发起、Jonathan Neal 维护，2015 年主流版本是 3.0.x（支持 IE 8+），Bootstrap 3.3 与 HTML5 Boilerplate 5.x 用的都是它。它的思路不是”抹平”，而是三件事：

  1. **保留有用的默认值。**标题字号、列表 marker、strong 的粗体都留着，因为它们承载语义。
  2. **只修浏览器的 bug 与不一致。**比如把 body 的 margin 归零（各家确实不一样），给 h1 明确写 font-size: 2em; margin: .67em 0（解决 Firefox 在 article/section 上下文里缩放 h1 的不一致），给表单控件统一 font: inherit; margin: 0（Safari 的继承问题），把 button 与 select 的 text-transform 归回 none（Firefox 会给按钮文字加粗体大写），再清掉 Firefox 的 ::-moz-focus-inner 内边距。
  3. **把每条规则写进注释。**源码里每个选择器上面都注明”为什么需要这一条”，出问题能查到是谁的锅。这份文档化是它最被低估的优点。

它还顺手处理了移动端：html 上的 -webkit-text-size-adjust: 100% 与 -ms-text-size-adjust: 100% 就写在 3.0.x 的第一段，横竖屏字号跳变这个坑省掉了。

具体规则对比

选型靠的不是印象，我把日常最容易碰到的几条列出来：

规则 Reset CSS 2.0 Normalize.css 3.0.x
h1 字号 font-size: 100% 加 font: inherit，标题回到正文字号 保留 2em 并统一 margin，跨浏览器一致但仍是标题
ul 的 list-style list-style: none 且 padding 清零，marker 消失 不动 marker 与缩进，语义列表照常渲染
button 的边框与外观 通用列表里 border: 0，按钮看起来像文字 保留原生边框与背景，只清 margin、统一 font: inherit，再修 Firefox 的 ::-moz-focus-inner
盒模型 不涉及，各家默认 content-box 3.0.x 也不动 box-sizing，全局 border-box 仍要自己写
img 的 vertical-align 所有元素被统一写成 baseline，图片下方那点基线空隙留着 只给媒体元素写 vertical-align: middle，img 仅去掉边框，空隙同样要自己处理
table 强制 border-collapse: collapse、间距归零 不碰表格，各家实现无致命差异

倒数第二行值得多说一句：图片与相邻文字底部不齐，是 inline 排版的经典问题，两边都没替你解决。要么 img { vertical-align: middle }，要么让图片 display: block，这是必须写进自己那层的规则。

怎么选：三个判据

判据一，重样式还是重语义。后台与组件密集型产品，表格、按钮、表单全靠自定义皮肤，reset 的”从零开始”正好合用，反正一切都要重建。内容站、文档站、博客——尤其带富文本正文的——用 normalize，别让 strong 和有序列表在编辑手里失效。

判据二，目标浏览器里有没有老 IE。两条路都要为 IE 8/9 留兜底，但 reset 通配写法多，在 IE 7 那一档的怪异表现更难预期；normalize 的规则逐条写明针对哪个浏览器，排查成本低一些。

判据三，是否移动为主。移动端要额外处理图片自适应、横竖屏字号跳变、表单控件在 iOS 上的外观。normalize 已经带了 text-size-adjust，起点更靠近移动端需求；选 reset 的话这几条得自己补齐。

flowchart TD
  Q1[页面里有没有富文本与语义列表] -->|有| N[以 Normalize 为底]
  Q1 -->|几乎没有| Q2[组件是否全部自定义皮肤]
  Q2 -->|是| R[以 Reset 为底]
  Q2 -->|否| N
  N --> M[再补一层项目自己的局部 reset]
  R --> M

混合做法的工程实现

实践中我很少只用其中一个。常见形态是：normalize 打底，再加一小层项目自己的局部 reset，只清真正会碍事的东西。入口文件保持单一依赖链，别把两份全局 reset 叠在一起。

box-sizing: inherit 这条配合根元素上的 border-box，比直接 * { box-sizing: border-box } 的好处是第三方组件（比如 jQuery UI 1.11 的日期选择器）想退回 content-box 时，只要在自己的根节点写一次即可覆盖下去。Sass 项目把 @import 换成同名文件的 @import "normalize" 就行，顺序意义一致。

通配 reset 的代价与 2015 年的争议

* { margin: 0; padding: 0 } 这类一行通配至今还有人手写。它在 2015 年的争议有两层。

一层是性能。Paul Irish 在 2011 年那份 *, *:before, *:after { box-sizing: border-box } 被广泛复制，随之而来的是”通配选择器会不会让样式重算变慢”的担心。我的结论与当时的主流一致：影响存在但很小，真正贵的是选择器最右侧那一段的匹配成本，通配本身不匹配任何东西、只在继承链上生效，把它当性能问题去讨论是找错了理由。反过来说，也不该声称”通配零成本”——大 DOM 页面上要的是实测，不是口号。

另一层是工程代价，这才是我劝人少用通配的原因：通配的优先级作用面覆盖全站，会把第三方库和富文本内容的初始态一起清掉，出问题时很难定位是 reset 还是组件的锅；*:before, *:after 一并清零 padding，依赖伪元素做间距的小图标会莫名塌陷。用”根元素声明加 inherit”或者范围限定在容器类上，比全局通配更好收拾。

被顺带牺牲的两件事

一是内容结构。把 h1 到 h6 压成同一字号之后，编辑写出来的层级在页面上不可见，视觉与语义脱钩。常见的坏结果是有人为了让小标题”看起来像标题”，直接给正文段落加 h3——层级被当成样式工具用，对读屏软件和搜索引擎都不利。正确做法是在自己的层里重建字号梯度：

小结

Reset 与 Normalize 的差别不在”谁更现代”，而在默认值对你的内容有没有价值。Eric Meyer 2.0 这条线从统一差异走到抹平一切，代价是列表、粗体、标题层级、表单外观全部要重建；Normalize 3.0.x 选择保留有用默认值、逐条修 bug 并把理由写进注释，代价是它不解决排版体系，图片基线空隙、盒模型、字号梯度还得自己补。我的建议是以 Normalize 为底、加一层小得多的局部 reset，用根元素 box-sizing 加 inherit 替代全局通配，并且把焦点样式与正文链接下划线当成不许动的资产。选 reset 也可以，前提是你的项目里所有组件都要重写皮肤。无论哪条路，团队约定那一层工具类的边界要写清楚。
