HTML5 输入框 inputmode 与移动端键盘优化

本文属于《HTML 与 CSS》第 15/62 篇
上一篇系列目录下一篇

先把最关键的一句话放在前面：截至 2015 年 7 月，inputmode 只是一个提案。它在 WHATWG 的邮件列表与 face to face 讨论里还在争论取值集合与命名，桌面与移动端的任何一款浏览器都没有实现它。所以这篇不打算给你一段”加上就生效”的代码，而是分两层讲：提案要解决的问题是什么，以及今天真正能拿到的收益在哪里。

优化只有两条主线：让用户少打字——少按若干字符、少切符号层、少一次回删重打；别让键盘破坏页面——不遮挡输入框、不错位吸底按钮、不引发多余的重排。下文每个点都尽量落到可度量的代价上：输入字符数、键盘切换次数、被拦掉的失败提交、一次键盘事件触发的重排次数。

论据口径也要说清：我没有条件覆盖 iOS 7/8、Android 4.x 各 ROM 与 Windows Phone 的键盘测试，本文未做真机验证。所有平台差异都标注了来源类型（规范口径、浏览器文档、历史事实、社区公认经验），不写成”实测”。可以复现的那部分——pattern 的匹配语义、位移与节流片段的逻辑——属于纯计算，我在 node 下跑过，结果写进正文。

一、键盘为什么值得单独优化

软键盘不是一个控件，它是一块会临时抢走屏幕的硬件。竖屏上它连候选栏一起吃掉 30% 到 50% 的高度（社区公认经验，具体数值随机型与输入法变化很大），布局区被腰斩，手指还要在更小的目标上更准地落点。

虚拟键盘的错误率明显高于实体键盘（社区经验，不引用具体百分比），成本结构也不同：实体键盘上打错一个字母是”按一次删除”，虚拟键盘上是”发现错、移回视线、删几次、重打、再确认”。代价分三层：击键次数（email 键盘把 @ 与 . 摆在主层，一个邮箱少两到四次切层）、键盘切换次数（每多一次切换就多一次点击，还要多算一次候选栏出现与消失的高度变化）、失败提交次数（pattern 拦下用户却不说原因，用户重试几次便离开）。表单流失里属于”填不对但不知道为什么”的那部分几乎都能靠标记层与文案消掉——这是定性判断，百分比我给不出。优化次序也就照代价排：标记层、约束层、脚本层，越往后越贵。

二、type 与键盘形态的映射矩阵

这张表是本文最实用的产出。type 决定语义与校验，在移动端它顺带决定了软键盘形态，而这层映射没有任何内核按规范承诺过（规范口径只写”应当给出合适的输入辅助”）。以下按 2015 年 7 月的版本面整理，来源标在每格之后。

type iOS Safari 7 / 8 Android 4.x 原生浏览器与 WebView IE Mobile（Windows Phone 8 / 8.1）
text 全键盘带候选栏（历史事实） 全键盘，候选栏随输入法（社区经验） 全键盘带候选栏（浏览器文档）
email 主层常驻 @ 与 .，无空格键（社区经验） 各家不一：多数只给 @，. 常在符号层（社区经验） 全键盘带 @（浏览器文档）
url 带 .com 快捷与 /，无空格（社区经验） 部分内核带 .com，不保证（社区经验） 全键盘带 / 与 .（浏览器文档）
tel 拨号盘，数字加少量符号，无候选栏（历史事实） 数字键盘（社区经验） 数字键盘（浏览器文档）
number 数字键盘，没有小数点也没有负号（历史事实） 数字键盘，. 与 - 随 ROM（社区经验） 数字键盘，符号随输入设置（社区经验）
search 全键盘，回车位常显示”搜索”（社区经验） 全键盘，回车文案由内核决定（社区经验） 全键盘，回车仍是”完成”（社区经验）

四个当时最容易踩的坑。

第一，iOS 上 number 没有小数点与负号，温度、金额、体重这类字段在 iPhone 上填不完整。通行折中是改用 tel：拨号盘带得上小数点与减号，代价是完全不做数字校验，语义交给后端与脚本兜住；留在 text 上拿 pattern 赌一次键盘切换也可行，但那条路不可靠，见第三节。

第二，email 与 url 的收益只在 iOS 上稳定，Android 各 ROM 表现不一，所以”邮箱字段一定少两次切层”这种话只能说一半。收益是真的，但别把某一家的键盘截图写进设计文档。

第三，tel 是当时唯一”只要键盘、不要校验”的合法出口。它故意什么都不校验（规范口径：国际号码无法用一条规则约束），所以想要数字键盘又必须保留自定义校验时，tel 加自己的正则比 number 可控。

第四，number 与服务端字段类型耦合：值会被内核清洗，用户敲进字母时 value 读回来是空字符串而不是原文，min / max / step 真的会参与拦截。要区分”没填”和”填了但看不懂”得读 validity.badInput，但 validity 在 IE9 及更早根本不存在、IE10 才有，Windows Phone 的 IE Mobile 又是另一条实现线——以 IE9/IE10 为基线的项目不能把它当可用 API，只能在检测之后当增强（浏览器文档与历史事实）。校验体系的完整讲解在旧文《HTML5 表单新增 input 类型与校验属性详解》，本文只借结论。

顺手记两件做不到。回车键上的文案（”搜索””下一步”）在 2015 年没有任何属性能控制：enterkeyhint 这样的写法此刻连规范草案都算不上，只能靠 type="search" 在部分平台换一个搜索样式的回车。ime-mode 与本文目标无关：它是 IE 与旧 Gecko 的专有属性，管的是输入法自身的开关（历史事实，已废弃），不是键盘形态。

三、pattern 的双刃

pattern 最容易记错的是它匹配整串。规范给的等价形式是自动加锚并把内容当成分组（规范口径），属性里写 [0-9]{6}，语义就是 JS 里的 ^(?:[0-9]{6})$，不需要也不该自己补 ^ 与 $。我在 node 下跑了对照，差异很直观：

输入值 属性 pattern 语义 裸正则 /[0-9]{6}/
123456 通过 通过
1234567 拒绝 通过
a123456 拒绝 通过

同一个坑的另一变体是分支：换成 ab|cd 时，按 /^ab|cd$/ 理解会放过 abcdef 与 xxxcd，因为锚点被 | 拆给了两个分支；正确做法是依赖属性自带的 (?:)，JS 兜底时把它写全。正则语法细节见旧文《JavaScript 正则表达式入门与实战》。

第二件事是它会被部分移动内核拿去选键盘。流传最广的技巧是 pattern="[0-9]*"，社区长期记作 Android 侧的技巧——但它是未标准化的历史技巧，只在 Android 的若干内核上有效，iOS 不保证。更有说服力的是本博客旧文《移动端输入法弹出与布局问题》里记着相反的机型观察：两份结论并存恰恰是它的真实状态，这件事不属于任何内核的承诺，只能按你自己的目标机型判定，绝不能塞进公共组件当默认行为（社区经验，来源不可靠）。

第三件事是可用性代价。pattern 拦下输入时用户只看到一个红框、没有解释；当时 title 只在部分平台作为提示气泡出现，iOS 不弹（历史事实）。所以行内文案才是稳定那条：报错时在字段下方写清”要 6 位数字”，比任何原生气泡都便宜；title 仍然要配，聊胜于无，桌面端能看见。

最后一条也是跑出来的：pattern 表达不了数字合法性。[0-9.]* 在整串语义下放过 ... 与 1.2.3，却把 -1.5 挡在外面。当”数字键盘的门票”可以，当”金额校验”不行——数值合法性必须在 JS 里清洗后判一次、服务端复查一次。

四、约束属性：另一半收益也在标记层

maxlength 是最直接的减击键手段：验证码给 6、手机号给 11，用户不必数长度，粘贴进来的超长串也会被截掉。但它只算体验层：当时若干移动内核在输入法组词期间会绕过截断，还有部分老内核压根不生效（历史事实），tooLong 也因此几乎恒为假。长度约束真正的落点在服务端与数据库字段定义上。

required 配 :invalid 与 :required 能画出必填标记，但纯 CSS 做不出”提交以后才报错”的分寸，用户敲第一个字符红框就跟着光标闪——这条结论借旧文《HTML5 表单新增 input 类型与校验属性详解》。

autocomplete 当时可用的取值是 on、off 加一组字段名含义（name、tel、email、url、cc-number 这类，规范口径）。取舍要显式做：关掉自动填充少一类”选错历史候选”的失败，代价是把一次点选换成十几秒手打。姓名、地址、邮箱没理由关；验证码与敏感字段要关，同时明白 off 只是建议不是命令——当年它就已经会被某些内核忽略（浏览器文档口径），别当安全控制。

iOS 上还有一组非标准属性：autocorrect="off"、autocapitalize="none"、spellcheck="false"。用户名、口令、代码片段、优惠码一定要关——自动首字母大写产出的是”看起来填对了”的脏值，修正成本是一次回访加一次重置。这三个属性都不在规范里，Android 的 WebView 多数直接忽略（社区经验），于是要接受”iOS 少一类脏数据、Android 靠服务端兜住”的不对称结果。

五、inputmode：提案到底想解决什么

type 的困境是一个属性管了三件事：值的类型语义与随之而来的校验、控件形态、软键盘形态。而需求往往只要第三件——“这里要数字键盘”。用 number 换就白背了值清洗与 step 校验，还白背了 iOS 那个缺小数点的面板；用 tel 换，语义又变成电话号码。语义与键盘耦合在同一个属性上，正是当时每个数字字段都要写一段注释解释”为什么手机号用 tel”的根因。

提案的思路是把这两件事解耦：新增一个只表达”该给什么输入辅助”的属性，由输入法决定键盘布局，不参与值的语义与校验（提案讨论口径）。当年草案里讨论过的取值集合大致是 verbatim、latin-name、latin-prose、full-width-latin、kana-name、numeric、tel、email、url 这一批，覆盖了拉丁全键盘、日文假名、全角输入这些 type 完全表达不了的形态。这批取值属于提案阶段，命名与集合还会变，2015 年 7 月没有任何浏览器实现它们。同样不存在的还有 inputmodechange 一类事件，不要为它预留分支。

那么当下怎么办：别让键盘需求散落在每个页面的 type 与 pattern 选择里，把它收成一份配置，标准落地时只换翻译表。

这份表的价值不在它多精确，而在它把”未标准化的赌注”集中到一处：将来 inputmode 落地，只需给每个 profile 补一个取值、让 type 退回它该管的语义；哪天发现某个内核不认 pattern 选键盘，改的也是这张表而不是十七个页面。

六、键盘遮挡：三种做法与它们的代价

先描述现象，不谈 API。键盘弹出时内核要么压缩视觉区域高度，要么把整页顶起来，两种都让布局视口与屏幕的对应关系失效。iOS 更麻烦：它是用平移实现的，position: fixed 的参考系不跟着动，吸底按钮停在旧位置、看起来跑到屏幕中间（历史事实，当年的经典问题）。至于加载后 window.scrollTo(0, 1) 这行像玄学的代码，原因很具体：iOS 点击状态栏回顶只在文档可滚且滚动位置为 0 时不生效，留出 1 像素余量，状态栏点击才有可操作的对象。它和键盘无关，但同一份”视口与滚动位置不可信”的判断管着这两件事（社区公认经验）。

把输入框与提交按钮放回可视区，当时可用的路子就三条，代价各不相同：

做法 优点 代价
focus 后调 scrollIntoView 一行代码，偏移由内核算 触发重排；偏移不可调，元素紧贴边缘；iOS 推下去后不回弹
监听输入后手动算偏移 能留间距，能连提交按钮一起照顾 输入过程中高度会变（候选栏、textarea 换行）要反复算；读几何量时容易写出交错的强制重排
表单容器回到文档流，不用 fixed 最稳，位移交给正常滚动 要改结构，吸底与弹层两种形态都得重做

输入框在弹层里还多一层：弹层自己是 overflow: auto 时，scrollIntoView 滚的是外层文档而不是弹层内部，结果一格没动；当时的做法是让弹层自己承担滚动、把弹层节点放到文档流末尾（body 之后）、遮罩作为不参与定位的独立兄弟层。完整推导在旧文《移动端输入法弹出与布局问题》，本文不重复铺陈。

容易被当成小事的是性能。键盘弹出会连触 focus、blur，Android 上还带出窗口 resize（历史事实），而回调里只要出现”读几何量再写样式”的交错，就是一次强制重排。对策不是加更多判断，而是把读集中、把写收敛成一次：

这两段用 DOM 桩在 node 里跑过：表单 8 个字段（含 1 个隐藏、1 个禁用），几何读取 6 次、scrollTo 恰好 1 次，最大越界 120 像素时位移返回 144，键盘没遮住时返回 0 且不滚动。作为对照，把读与写交替着逐字段做，同样 8 个字段在模型里产生 8 次强制重排——差别不在算法，而在谁触发了同步布局。节流那一头：连发 12 次 resize，窗口取 200 毫秒时回调执行 3 次（不节流是 12 次），足够覆盖”键盘动画加视口滞后”的一两次校正。

七、输入法对输入流程的影响

还有一层代价在组词期间。中文输入法下 keyup 与 input 拿到的常常还是拼音串，实时校验会提前报红，实时位移会把候选栏出现误判成遮挡。更棘手的是 Android 4.x 的部分内核在组词结束时不触发 compositionend（历史事实），靠它解除屏蔽的写法在那批机器上会把校验一直锁死，反而不如不做；而在 input 里改写 value（补空格、加格式）本身会打断组词，用户眼前的拼音直接消失。

到”键盘与输入法怎样影响输入流程”这一层为止。标志位方案与光标位置的保存恢复，旧文《DOM 实时输入监听 input 事件》已写透；触控事件序列与点击延迟不在本文范围，见旧文《移动端 touch 事件与手势基础》。

八、收口清单

上线前逐项过一遍，每项都要能回答”省下了什么代价”：

  • 每个输入项是否显式选了 type，选的是想要的键盘而不是顺手留下的 text？数字与金额字段是否确认过 iOS 上小数点与负号能不能打出来？
  • pattern 是否只用整串语义、分支有没有被 (?:) 包住？拦下用户时行内文案有没有说清规则，title 只当补充？
  • autocomplete 是否逐字段显式决定，而不是全表 off 或全表不管？iOS 专有属性只当增强，服务端有没有同样的清洗？
  • 键盘弹出后提交按钮是否可见？依赖 scrollIntoView 的话，不回弹与偏移不可调这两条代价是否接受？
  • focus / blur / resize 回调里是否做到”读集中、写一次”，resize 有没有节流？
  • inputmode 有没有被写进任何一行业务代码？键盘需求是否已经收进一张可替换的 profile 表？

标准落地之前，收益只能从标记层和一件件可度量的代价里抠。inputmode 值得记下的是它的问题划分方式——把”给什么键盘”从”值是什么类型”里拆出来；写法上 2015 年还是老规矩：type 打底、pattern 补充、JS 兜底，等标准到了只改一张表。
