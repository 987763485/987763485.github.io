ES6 class 类与继承

class 是这批 ES6 新语法里争议最大、也最容易”学了新语法、没懂旧机制”的一个。笔者先把立场亮出来：class 就是语法糖，Babel 转译出来的产物仍是 function 加原型操作；但它不完全是糖——方法不可枚举、必须用 new 调用、内部严格模式这几条是 ES5 写法做不出来的真实差异。本文从 2015 年 9 月的现场出发，把 ES5 的四步原型写法与 class 逐项对应，然后重点讲清”哪些地方 class 和手写原型不一样“、转译下继承内置类型的局限、混入为什么仍然要手写，最后给一段完整的 ES5↔class 对照。底层机制不再重讲：原型链查找的推导在《JavaScript 原型与原型链完全解析》，七种继承写法的工程取舍在《JavaScript 继承的几种实现方式》，new 的四步拆解在《new 操作符到底做了什么》，本文直接引用它们的结论。

先回顾 ES5 的四步写法

给一个子类接上父类，2015 年之前的标准动作是四件事：父行为挂 Parent.prototype；子构造里 Parent.call(this, args) 搬实例属性；子原型用 Object.create(Parent.prototype) 拼接（而不是 new Parent()，原因前作里那个选项数组互相污染的事故就是教训）；补写 constructor 指回子构造。Node 里可以用 util.inherits 把后两步合并掉。

这套写法能跑，问题在表达力：四步散在四个位置，”继承”这个意图要靠读者自己从赋值语句里反推。class 改变的只是”把意图写集中”。

生产环境仍要 Babel 5 转译——当时的浏览器稳定版对 class 的支持基本为零。转译后的产物能回答”class 到底是什么”：

还是函数、还是原型，只是方法通过内部的 Object.defineProperty 挂上去。两个实践代价：一来报错栈和 typeof Dog 与 ES5 无异，class 不会给你任何”类系统”的运行时设施；二来 _createClass 这类辅助函数依赖 Object.defineProperty，IE8 及以下跑不了转译后的 class，老项目支持计划里要单列这条。

（现场补一句：部分 Chrome 已能解析 class，但 IE 没有、Firefox 次年才跟上，能解析不等于能当基线。）

带上 extends 的产物

extends 一出现，转译器要处理的不只是”把方法挂回原型”，还有”父类构造可能返回另一个对象”这一段，语法糖就厚在这里：

三个 helper 各顶一句 class 语义，也就各顶一处代价：

helper 对应的 class 语义 代价
_inherits 子类原型、子类构造函数分别接住父类 老引擎缺 setPrototypeOf 时退化成一圈 for...in 抄静态属性，不可枚举的抄不到，父类后加的也不跟着动

转译挂在构建的哪一环

接进工程走 gulp-babel、grunt-babel 或 browserify + babelify，两笔账要认：helper 默认按文件内联，两三个 class 的小模块转完能多出几十行（同机粗测的印象，精确比例没意义）；断点打在类方法里实际停在 _createClass 的 value 函数上，--source-maps 因此是必备。可读性记在源码这侧，长度和调试成本记在产物那侧。

真实差异：这几点不是糖

方法不可枚举

Dog.prototype.bark 在 class 下不可枚举，for...in 和 Object.keys(Dog.prototype) 都看不到它；ES5 直接赋值挂的方法是可见的。依赖遍历原型方法做自动注册、做 mixin 拷贝的老代码，迁到 class 后要改用 getOwnPropertyNames。Babel 用 defineProperty 保持了这一语义，转译前后一致。

必须用 new 调用

Dog('rex') 直接抛 TypeError，ES5 构造函数的”忘了 new”——this 掉到全局、属性悄悄挂到 window——在 class 上不存在了。这条我认为是 class 最实用的差异：那类忘写 new 的诡异 bug 从”靠自觉”变成了”语法层拦截”。

内部自动严格模式

类体无论外层脚本是否严格模式，一律按 strict 执行。平时没感觉，但两个老代码习惯会被炸出来：给未声明变量赋值不再静默创建全局而是抛错；八进制字面量之类的宽松语法直接报语法错误。

方法没有 prototype

类方法自身不再是构造函数，new obj.method() 会失败。影响很小，但当年有个依赖”把带静态属性的方法对象当命名空间”的冷门技巧会失效。

this 不会自动绑定

这是新手最大的坑。把方法当回调传出去，this 就丢了：

2015 年的标准解法是在构造器里显式绑一次：this.handleClick = this.handleClick.bind(this);。箭头函数的词法 this 是另一条路，它的语义和坑在系列前作《ES6 箭头函数与 this 绑定》里专门讲过，这里不展开。

三种修法的成本对比

“能跑”之外还有费用，三种写法各有各的账：

做法 this 从哪来 每实例开销 子类覆盖 什么时候选它
构造器 bind 实例属性，锁死 一个函数对象 遮蔽原型方法，父子同名要小心 方法要当回调传出去，默认选它
构造器里箭头函数 词法捕获构造器的 this 同上，一实例一份 实例属性，覆盖不了也共享不了 类只有一层、方法很短
调用处 bind 或包一层 调用点决定 类侧零开销，代价摊在调用点 保留原型覆盖语义 回调注册点很少

另有一条省事却最坑的做法：绕开类体往原型上补箭头函数（Widget.prototype.onTick = () => console.log(this.count);）。原型上的箭头函数被所有实例共享同一份词法 this，它属于定义处的作用域，跟实例毫无关系；类体里的方法因此只能是普通函数，把箭头函数写成”类属性”（handleClick = () => {}）则是还在路上的提案，当时只有实验性开关，生产别开。

构造器里 super 必须先调用

extends 的类在构造器里必须先 super() 才能碰 this，否则 ReferenceError。道理在机制层：子实例的”对象本体”要由父类构造创建，Babel 产物里的 var _this = _super.call(this, ...) || this 就是这句话的直译。super 与 _super.call 的分工细节，前作《JavaScript 继承的几种实现方式》的寄生组合式一节已经推导过，不再重复。

原生引擎抛 ReferenceError（this 还没初始化）；同一份源码转译后，这行落在 _possibleConstructorReturn 之前，_this 还是 undefined，抛 TypeError。两边都不静默失败，但报错文本完全不同，第一次遇到容易怀疑转译器写错了——机制上是同一条规则，把赋值挪到 super() 之后就完事。

_possibleConstructorReturn 那条”是对象就返回对象”也值得记住，class 与 ES5 在这里一起中招：

Sub 的构造器看着在给 b 写字段，实际全落在 a 上：父类构造一旦动了返回值，子类的 this 就不由自己说了算。

继承的边界：内置类型与混入

extends Array、extends Map 这类内置继承在 2015 年请直接按”不可用”处理。原生层面只有极少数引擎能做到；转译层面，Array 作为普通函数调用时会忽略传入的 this 另起一个新数组——这正是 ES5 借用构造函数继承内置类型失败的根因，class 转译后走的还是这条路，length 的自动维护等特殊内部行为全部落空，push、slice 看起来在、行为不可靠。注明一句：这是转译到 ES5 的局限，不是 class 语法本身的问题，等引擎原生支持后 extends 内置类型才是成立的。当年的替代方案是组合优于继承：实例内部持有一个数组字段，包一层方法转发。

混入同样没有原生语法，标准里没给，Babel 5 只留了一个实验性开关，生产别碰。可行做法是手写”类的类”——接收基类、返回加了行为的子类：

换成 ES5 那套”把行为拷到目标原型上”也要手写，但要记住前面那条”类方法不可枚举”：for...in 一个都拷不到，朴素赋值 Target.prototype[name] = src.prototype[name] 会把 getter/setter 拷成数据属性，得用 getOwnPropertyNames 配 getOwnPropertyDescriptor 再 defineProperty，并跳过 constructor。冲突方向也得定死：拷贝式照 _.extend 那样直接覆写，是后混入的赢（前作讲过这条）；套娃高阶类里是最外层那个赢。两种混着用，同名方法到底生效哪一个只能逐条画原型链——语法没提供仲裁。

static、getter/setter 与 Symbol 方法名

static、get/set 都在标准内，可以放心写：访问器方法在原型上照常成对定义，转译产物也是 defineProperty 带 get/set。要点只有一个：访问器挂在原型上，实例自己不能再放同名数据属性，构造器里 this.size = 0 这类初始化要留意是否触发了 setter。计算属性名配 Symbol.iterator 之类的写法（[Symbol.iterator]() {}）是标准内的，但 Symbol 本身在 2015 年 9 月只有 Firefox 给得比较全，Node 4 要部分开关，转译也补不了这个运行时能力——它只适合作为”了解标准”的语法说明，别写进要跑的业务代码。

访问器另有一个”成对才成立”的坑：

原型上的访问器以”一条描述符”为单位被覆盖，子类写同名 set 就把父类的 get 一起挡住；构造器里的 this.size = 0 走的正是 setter，想绕过得换字段名。

私有状态：闭包版与 class 版 Emitter

到这一版标准，类没有私有字段，_events 那样的下划线只是命名约定，对象外面照样读写。同一个 Emitter 两种写法摆在一起，价钱差别看得最清楚：

闭包版把 events 藏得干干净净，代价也要摆明：函数每个实例一份、不共享，原型上没有东西可覆盖，继承与 instanceof 一起失效，调试时点开对象只剩两个方法。所以它不是”更好的写法”，而是”要真私有就必须付的价钱”。更多时候折中在模块层——module.exports = new Emitter();，状态封在模块作用域里，类照旧写。

什么时候别用 class

两条判断。只有一个实例、或本质是”造一个配置好的对象”时，工厂函数比 class 短得多也清楚得多，别为了统一风格硬套类。需要私有状态时尤其别用 class——它到这一版标准为止都没有私有字段，下划线前缀只是命名约定，属性在外面照样读写；要真私有就用闭包，前作讲作用域时给过模块模式的写法，class 内部同样可以用：把状态放进构造器所在闭包，方法只留接口。

单例是这套语法最别扭的一类目标：类没有静态数据属性，Logger.instance 要么在构造器里赋值、要么在类体外补一行，就是写不进类体；再叠上”父类构造返回旧对象、子类的 this 跟着换人”那个坑，一个闭包三行搞定的事摊成了三处阅读点。同理，一组没有状态、也不需要实例的函数就当命名空间用 module.exports 导出，包成类只是让调用方多写一次 new。最后一条留给回调：jQuery 的事件处理、Express 的中间件这类要求 this 由调用方决定的函数，别为了”看起来现代”改成类方法，前作”这四种写法请保留 function”的结论对 class 同样成立。

小结

把 class 当两样东西看：作为语法糖，它把构造函数、原型方法、静态属性、原型链拼接集中到一个语法块里，转译产物仍是 function，机制没有新东西，前面几篇讲原型链和继承的结论全部适用；作为”不完全的糖”，方法不可枚举、强制 new 调用、内部严格模式、方法没有原型、this 不自动绑定、构造器里 super 先行，这六条是 ES5 写法给不了或给不稳的。边界要记牢：转译下别继承内置类型，混入还得手写，私有状态继续交给闭包。在 2015 年的项目里，笔者的建议是库和类的密集场景用 class 统一写法换取可读性，零散对象和单实例场景不必跟风——语法是新的，工程判断还是老的。
