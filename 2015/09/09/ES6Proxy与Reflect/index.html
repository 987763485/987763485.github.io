ES6 Proxy 与 Reflect

ECMAScript 2015 在 6 月 17 日定稿，满打满算才过去两个多月，Proxy 与 Reflect 是这一版里最抽象、也最容易被讲错的一对 API。本文写于标准刚出炉、引擎基本没跟上的当口：截至 2015 年 9 月，任何浏览器的稳定版都还没有新标准的 Proxy 实现，Node 侧同样没有，所以文中只讲机制、语义与用途，并把结论摆在前头——它现在不能上生产。适合已经读过我上一篇访问器劫持、想知道”下一代的写法长什么样、为什么还不能用、眼下该用什么”的人。getter 与 setter 的具体写法不在本文重复。

defineProperty 拦的是属性，Proxy 拦的是操作

上一篇《Object.defineProperty 与数据劫持入门》把访问器劫持这条路线走完了：值搬到闭包变量里，用 Object.defineProperty 把已有属性就地换成访问器，赋值顺手派发通知，配合 setTimeout 做同轮合批。那篇文章里已经承认了它的失效面——新增键感知不到、数组下标和 push 拦不住、冻结过的对象改写会抛错。这里只把那条线画清楚：defineProperty 观察的对象是”一个属性”，所以它必须在一个属性已经存在（或者你能提前把它造出来）的前提下才能工作。凡是键集合开放的、操作类型不止读写的场景，它就完全帮不上忙。

具体办不到的事，笔者能列出来的有这么几类。新增键：给没被劫持过的键赋值走的还是普通数据属性路径，一次通知都不会有。delete：删属性时不会调用 setter，访问器对这个操作毫无感知。原型链上的读写：defineProperty 只能改对象自己的属性描述符，而”沿原型链找上去、命中原型上的 getter”这一整段语义是引擎内部的，改不了。in 操作符：它只查属性存在性，不经过访问器。函数调用与 new：一个函数被调用时的参数、this、返回值，都不是属性。数组的索引与 length：list[0] = x 是索引赋值，push 改的是 length，这也是为什么上一篇要用”遮蔽原型方法”这种妥协手段。

Proxy 换了个切入点：它拦的不是属性，而是对象上的操作。规范里每个对象都有一组内部方法——[[Get]]、[[Set]]、[[HasProperty]]、[[Delete]]、[[DefineOwnProperty]]、[[OwnPropertyKeys]]、[[GetPrototypeOf]]、[[SetPrototypeOf]]、[[IsExtensible]]、[[PreventExtensions]]、[[Call]]、[[Construct]]。这些内部方法一直是对象语义的一部分，ES6 做的第一件事是把它们开放给 JS 代码：你给出一个目标对象和一个处理器对象，引擎在你写 proxy.foo 的时候不再直接走默认逻辑，而是先调用你那个 get 方法。这就是所谓元编程——代码得以重新定义语言自己的默认行为。

两者的分工可以这么记：defineProperty 是”这个键的读写我接管了”，Proxy 是”这个对象上发生的任何一类操作我都接管了”。前者的粒度在键，后者的粒度在操作类型，跟键名无关，所以新增键天然被覆盖，delete 和 in 也在拦截面里。

flowchart TD
    A[脚本里的一次 JS 操作] --> B{接收者是不是 Proxy}
    B -->|不是| C[内部方法按默认语义作用于对象]
    B -->|是| D[按操作类型查 handler 上的同名陷阱]
    D -->|没定义该陷阱| C
    D -->|定义了| E[调用陷阱函数]
    E --> F[用 Reflect 转发一次默认行为]
    F --> G{返回值是否违反不变式}
    G -->|违反| H[抛 TypeError]
    G -->|不违反| I[把结果交回调用方]

图上”用 Reflect 转发一次默认行为”这一步不是必须的，你可以完全不理 target 自己返回一个值；但它几乎是每个正经陷阱都要写的一行，原因在第三节。

13 个陷阱：哪个操作命中哪个 trap

new Proxy(target, handler) 造出一个代理对象。handler 是一个普通对象，它的方法名决定了拦哪类操作，规范一共定义了 13 个陷阱。这张表笔者是照着规范抄的，建议直接背下”操作”和”陷阱”两列的对应关系：

proxy.key、proxy[expr] [[Get]] get target、key、receiver
proxy.key = v [[Set]] set target、key、value、receiver
key in proxy [[HasProperty]] has target、key

Object.defineProperty(proxy, ...) [[DefineOwnProperty]] defineProperty target、key、descriptor

三个容易看漏的点。第一，Object.keys 会连打两个陷阱：先用 ownKeys 拿到键的名单，再对名单里每个键调 getOwnPropertyDescriptor 来判断可枚举性，所以只实现 ownKeys 而不管描述符，会得到一个空数组。第二，apply 和 construct 要求 target 必须是可调用的对象，拿普通对象去代理函数、然后调用，引擎直接抛 TypeError；反过来，代理一个函数时 [[Call]] 的默认转发要用 Reflect.apply，不能写 target.apply(...)，理由和第三节同源。第三，construct 的返回值必须是一个对象，规范在这条上有硬性检查。

因为陷阱名就是 handler 上的普通字符串键，整个 handler 用 ES5 的对象字面量就能写出来，不需要任何新语法。这一点很重要，它是”Proxy 不是语法问题”的第一层证据：

数组也能代理，代价是”操作变多了”。list.push(x) 在代理上会依次命中：get 取 push 方法、get 取 length、defineProperty 或 set 写下标、set 改 length。也就是说一次 push 会穿过好几层陷阱，语义上完整，开销上完全不是白来的（第六节谈这个）。

Reflect：把默认行为重新拿回手里

Reflect 是 ES6 新增的一个全局内置对象，不是函数、不能用 new，它把上面那些内部方法原样导出成静态函数，名字与 13 个陷阱一一对应。为什么要有它？笔者归纳三条，按重要性排序。

第一条：让陷阱里能转发默认语义，而不用手工重实现。没有 Reflect 的年代，你写一个 get 陷阱想做”记录一下日志然后照常返回”，最后那一步只能写 return target[key]。这行代码看着没问题，实际是一份重新实现的属性查找逻辑——它不会沿原型链找访问器、不会区分数据属性和访问器、this 绑错对象。规范作者显然不希望开发者自己去重写 [[Get]]，于是把默认行为作为一个函数交给你调用。看一段对比，就知道差距：

第二条：返回布尔，而不是抛错。ES5 里”严格模式下写失败要抛 TypeError“这个规则折磨过不少人：给一个 writable: false 的属性赋值，严格模式抛、非严格模式静默失败，同一个动作在不同文件里行为都不一样，因为你根本不知道那个属性是谁在什么时候定义的。Reflect.set、Reflect.defineProperty、Reflect.deleteProperty 统一改成返回 true / false，不抛错也不看当前是不是严格模式。这使得”我试着写一下，写不进去就走另一条路”这种逻辑第一次可以放心写出来：

第三条：receiver 参数，以及它和原型链的关系。这是三个理由里最烧脑但最能体现设计水平的一个。Reflect.get(target, key, receiver) 的第三个参数决定”读取访问器时把 getter 的 this 绑到谁身上”。陷阱里收到的 receiver 永远是你手上那个代理对象（而不是 target）。如果忽略它，直接 target[key]，那么原型上那个 getter 里的 this 就变成了 target，代理就”漏”了：

不变式：陷阱不是你想返回什么就返回什么

如果陷阱可以任意返回，语言就会自相矛盾：Object.isExtensible 说不许加键、Object.keys 却列出十个新键，x in obj 是 false 而 obj.x 有值。规范因此在第 9.5 节给每个陷阱钉死了一组”Essential Internal Methods 不变式”，引擎在把你的返回值交出去之前先校验一遍，违反就抛 TypeError。这一段值得单独讲，因为它是”标准设计”的口味所在：Trap 的自由度是表达层的自由，不是一致性上的自由。

笔者挑最常踩的几条。数据属性如果同时是 writable: false 和 configurable: false，get 陷阱返回的值必须和 target 上的值 SameValue 相等，set 陷阱也不能把不同的值写进去后还返回 true。has 不能谎报：target 上有个不可配置的自有属性，陷阱就不能说它不存在；target 若是不可扩展的，它身上有的键 has 就必须承认。deleteProperty 对不可配置属性只能返回 false。ownKeys 必须包含 target 全部不可配置的自有键、不能重复，target 不可扩展时还必须一个不多一个不少。getOwnPropertyDescriptor 不能把真实存在的不可配置属性说成不存在。isExtensible 更不能撒谎说一个可扩展的对象不可扩展——这条是防止有人用代理伪造”看起来被冻结了”的对象。

这个报错很值得亲手撞一次：它告诉你”代理不能篡改事实，只能篡改访问事实这件事”。想造一个把 id 改成 999 的视图，正确姿势不是用 get 骗人，而是造一个以你为 target 的中转对象，或者干脆给 target 换个原型。理解了不变式，也就理解了为什么 Proxy 天生适合做”包装”和”记账”，而不适合做”谎言”。

顺带一提，规范还提供了 Proxy.revocable(target, handler)，返回代理本体和一个 revoke 函数；调用 revoke 之后，代理上的任何操作都抛 TypeError。它的用途是把”授权过期”这件事做到语言层——比如把一个对象交给第三方回调，用完当场拔掉。这条 API 一样要等引擎。

用途：五个现在就能把思路写清楚的小场景

场景讲五个，都按新标准语义写。它们共同的现实约束是：眼下没有引擎能跑，所以每一段后面都补一句”2015 年 9 月可行的替代做法”。

默认值字典与懒初始化

get 陷阱最直白的用法：读一个不存在的键时不是给 undefined，而是当场造一个默认值并缓存，之后每次读同一个键不再重复构造。

代价要写清楚：counts.missingKey 永远不会是 undefined，has 陷阱没实现时 'a' in counts 反而还是 false，读得到却查不到，这种不一致在别的代码眼里就是 bug。要补就 has 和 getOwnPropertyDescriptor 一起补。替代方案：一个包了 bump(key) 方法的普通对象，或者读之前 obj[k] = obj[k] || 0。

只读视图与私有键

两个陷阱配合就能造出”外面改不动、里面还是活对象”的视图：set、deleteProperty、defineProperty 三个一律返回 false（非严格模式静默失败，严格模式由调用方抛），get 里挡掉以 _ 开头的键。

这里有个坑只有踩过才知道：readOnly 出来的代理和原对象是同一个数据，readOnly(obj) === obj 是 false，但 readOnly(obj).list.push(1) 照样改掉了 obj.list——因为 list 读出来是原始数组，它自己没有被代理。要做深层只读，得在 get 里对读到的对象再套一层，同时缓存包装结果，否则每次读同一个属性都拿到一个新的代理对象，=== 全崩。替代方案：Object.freeze（它不可撤销，而且是浅冻结，嵌套对象照样可写，还会把属性一次性变成不可配置），或者返回一份浅拷贝（但它从此不再同步）。

透明映射：把属性读写接到 localStorage 后面

target 甚至可以是一个不存在的对象：代理不持有数据，get / set / has / ownKeys 全部翻译成 localStorage 调用。这样业务代码里 store.userPrefs = {...} 就是在写磁盘，Object.keys(store) 就是枚举存储里的键。实现思路是 get 做 JSON.parse(localStorage.getItem(prefix + key))、set 做 JSON.stringify 后写回、ownKeys 遍历 localStorage 的键并过滤前缀。代价相当明确：每次读属性都是一次同步 I/O 加一次 JSON 解析，比内存访问慢几个数量级；ownKeys 里还得返回合法名单，否则违反不变式；写失败（配额满、隐私模式）时 Reflect.set 那一步要自己兜住。这个场景用 defineProperty 也能做一个封闭键集合的版本，但键一旦是动态的就没法预定义，正是 Proxy 独有的能力。

2015 年 9 月的引擎现实

这一节是本文的年代底线，写得难看也得照实写。

浏览器。 新标准的 Proxy 与 Reflect 在 2015 年 9 月没有任何浏览器的稳定版实现，Chrome、Safari、IE 全都没有。Firefox 从 18 起自带的是旧版 Proxy API：调用形式是 Proxy(target, handler)，不写 new；陷阱集合也不一样，除了 get / set / has 之外还有 keys、enumerate、fix、hasOwn、delete，函数调用靠 create 而不是 apply 和 construct。更重要的是参数签名：旧 API 的陷阱不接收 target，get 的签名是 function (key, receiver)。Mozilla 已经明确要在后续版本里移除这套旧 API。所以下面这段能在 Firefox 控制台跑通的东西，语义是旧的，而且注定作废：

fix 这个陷阱值得一提：它允许你返回一份全新的属性描述符集合，把对象”定死”成你想要的样子。它之所以被从新 API 里拿掉，正是本节上一部分讲的不变式思想——一次陷阱调用就篡改了整个对象的事实，语言一致性保不住。旧 API 到 new API 不是改个函数名，是能力被削减了。

Node 侧。 就在今天，2015 年 9 月 9 日，Node.js 4.0 作为 LTS 发布，io.js 与 Node 合并，V8 升到 4.5，官方文档里的 ES6 支持度大约四成出头，Proxy 和 Reflect 不在这四成里。更早的 io.js 3.x 和 Node 0.12 上，node --v8-options | grep harmony 能翻出一个 --harmony_proxies 开关，打开得到的是 V8 里那份老 harmony 代理，同样是旧语义。换句话说：Node 也不能跑 new Proxy。

转译工具帮不上忙。 现在能用的转译器只有 Babel 5.x（npm install -g babel@5，跑 babel src -d lib，构建侧是 gulp-babel、grunt-babel、browserify 加 babelify，浏览器里用 <script> 直接引 browser-polyfill.js）。但 Babel 的工作是语法降级：箭头函数、模板字符串、类、解构这些能被翻译成 ES5 等价写法的东西。new Proxy(target, handler) 不是语法，它要求引擎在 obj.key 这一步去调用你的函数——这个行为不在 JS 代码里，在 C++ 的属性访问路径里。转译器无法凭空造出运行时语义，所以 Proxy 一行都降不了级。能做的只有 polyfill 级别的模拟：core-js 0.x 里带了一个 es6.proxy 模块，用 Object.defineProperty 加一层包装对象去逼近新 API 的行为；tvcutsem 那个 harmony-reflect 库更进一步，它导出一个 ES6 风格的 Reflect，在带旧 Proxy 的引擎上把 Proxy(target, handler) 补丁成新语义。模拟的代价必须写在脸上：模拟出来的”代理”不是真的代理，Array.isArray、instanceof、Object.keys 这些走原生内部方法的检查可能对不上号，深层递归的 receiver 传递会断，性能也不乐观。harmony-reflect 自己在 Node 里还有个已知限制——require 只改写当前模块的全局，跨模块传过去的模拟代理可能仍按旧语义工作。这些坑都够工程上喝一壶，所以它只适合内部工具、原型验证，不适合线上链路。

别拿实验特性当饭吃。 Chrome 里曾经有过 Object.observe，浏览器原生做变更通知、自带合批，看着正是访问器劫持想要而不得的东西。但它从头到尾躲在实验通道后面，语义反复变动，谁也没承诺它稳定，2014 年笔者就决定不为它写兼容代码，2015 年依然如此。这里插一句历史：Proxy 自己在 2012 年一度被从 ES6 草案里整体撤掉，2013 年才以今天这套新 API 的面目回来。一个进了标准的东西都可能中途夭折，何况一个连标准都没进的东西。判断标准只有一个：稳定版引擎里有实现、有厂商兼容性承诺，两者缺一率就当它不存在。

性能与成本：什么时候不该用它

先声明口径：下面这一段笔者没有跑过基准，也没有数字可以提供，全是定性推理，量级判断来自引擎的工作方式而非测量。

一次属性读在普通对象上，引擎大致是在一个已知形状的对象上按偏移取内存（V8 用隐藏类把对象形状固定下来，再把访问点编成内联缓存）。换成代理以后，obj.key 这一步必须跨出引擎、进入一段用户代码：它要构造参数列表、调用你的函数、等你返回、再做不变式校验。这条路径上没有可预测的形状，编译期推不出来，内联缓存基本退化，每一次读都是实打实的函数调用；如果陷阱里再调 Reflect.get，等于又叠一层。所以量级上”至少多一次函数调用、缓存命中归零”是稳妥的说法，而陷阱里做了字符串拼接、JSON.stringify 或者日志，代价还能再涨一个台阶。

由此推出三条不该用的场景。第一，大数组的热循环：一个每帧遍历几千项的渲染或物理计算，代理化之后每一项都要穿两层陷阱，这属于最不该碰的地方。第二，被高频读的属性：滚动监听、鼠标轨迹、每帧都读的样式值。第三，深层对象整体代理：为了”观察一切”把整棵树套满代理，读写会顺着代理链一层层往下穿，同时制造大量小对象。反过来，代理适合配置对象、表单模型、存储映射这类读得少、改得少、语义要求高的场合——那里省下的 bug 比多出来的开销值钱得多。

迁移成本也得算。旧 API 到 new API 是签名级别的改动：少一个 target 参数、陷阱名换掉、fix 没了、函数调用从 create 改成 apply 加 construct。今天基于旧 API 写的所有东西，等新版落地那天都得回炉，而且回炉方向是”能力变少”，不是”能力变多”——这一点决定了它只能当学习材料，不能当基座。

sequenceDiagram
    participant U as 业务代码
    participant P as Proxy 对象
    participant H as handler 陷阱
    participant R as Reflect 默认行为
    participant T as target
    U->>P: state.name = 'chunle'
    P->>H: set(target, 'name', 'chunle', receiver)
    H->>R: Reflect.set(target, 'name', value, receiver)
    R->>T: 真正写入
    T-->>R: 成功
    R-->>H: true
    H->>P: 返回 true，引擎校验不变式
    P-->>U: 赋值完成

图上从业务代码走到 target 再返回，一共八步跨越，这就是”每个操作都贵一点”的直观来源；普通对象上这几步全在引擎内部完成，不落进用户代码。

如果现在就要做数据劫持

把 2015 年 9 月真正能选的几条摆在一起。这张表笔者建议打印贴在显示器边上。

方案 新增键 delete 数组下标 原型链 函数调用 现在可上生产 主要代价
Object.defineProperty 访问器 不能 不能 不能 不能 不能 可以（IE9+） 键必须预知，通知风暴
手写 getter / setter 约定 不能 不能 走显式 API 不能 不能 可以（全环境） 调用点全改，靠纪律

选择逻辑跟上一篇的结论一致，只是多了一条时间轴：字段封闭、需要即时通知、要求 IE9 以上，用 defineProperty；字段开放、能容忍一个轮询周期，用脏检查；跨环境库，老老实实写显式 setter 约定，别赌任何新 API。Proxy 现在唯一值得投入的是把语义吃透——它的 13 个陷阱和不变式规则已经定稿，不会再大改了，现在学会，落地那天可以直接用；反过来，今天基于旧 API 写的代码是负资产。

具体动作清单，笔者给自己列了五条：把 handler 的 13 个陷阱过一遍并记住哪几个必须成对实现（ownKeys 与 getOwnPropertyDescriptor）；在手头项目里继续用 defineProperty 并明确写下它的边界；把 Firefox 控制台的旧 API 当沙盘玩，只验证思路不提交代码；Babel 继续用于语法降级，但不要指望它解决运行时行为；每两周看一次兼容性表的 Proxy 与 Reflect 两行有没有从红变绿。

小结

Proxy 把拦截点从”某个属性的读写”上移到了”对象上的操作”，13 个陷阱对应 13 类内部方法，因此新增键、delete、in、原型链、函数调用和数组索引第一次统一进了拦截面；Reflect 存在的意义是让陷阱能把默认行为转发出去、让写操作返回布尔而不是抛错、并通过 receiver 参数把 this 正确送回代理本身。规范用不变式给这份自由划了红线：代理只能改变”怎么访问”，不能改变”事实是什么”，越界就 TypeError。用途上，默认值字典、只读视图、变更流水、配置契约层、存储透明映射这五类是收益最清楚的，但共同前提是引擎不支持。2015 年 9 月的实情是：新 API 没有任何稳定版实现，Firefox 里是注定作废的旧 API，Node 4.0 的 V8 4.5 不带 Proxy，Babel 只能转语法、造不出运行时语义，polyfill 只是能力不完整的模拟。所以本文的判断是：现在读它、练它、写进设计文档的思路里，但不要写进任何要上线的代码，眼下要做数据劫持就照上表选一条能上生产的路。等到稳定版浏览器真把 Proxy 和 Reflect 落地，我们再回来谈工程化的那半边——那篇文的日期，不会是这个。
