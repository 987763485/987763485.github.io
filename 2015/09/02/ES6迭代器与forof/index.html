ES6 迭代器与 for...of

ECMA-262 第 6 版定稿已经两个半月，规范里那套迭代协议我认为比 class、模块更值得先学——因为它解决的是一件每天都在做错的事：怎么把一串东西正确地遍历一遍。这篇从工程角度把迭代器协议、for...of 和转译代价讲清楚，读完你能自己写一个可迭代对象，也能判断什么场景该继续用 for。要提醒的是，这套东西在 2015 年 9 月的浏览器上还不能直接指望，正文里的写法都要过 Babel 5；顺带一提，第 6 版按新的年度发布制也有人叫它 ES2015，本文沿用时下更熟的 ES6。

先把 for 家族的账算清楚

ES5 那五种循环的语义和性能，我在《JavaScript 中的循环与迭代方式》里算过一遍，这里只把结论摆出来，看看它们各自的错在哪：

四类毛病分别是：for 要求被遍历的东西有索引和 length（所以 Map、Set、生成器序列都不吃）；for...in 只认”键”，还会把原型链上的可枚举属性一起端上来，必须 hasOwnProperty 兜底，而且枚举顺序不保证；forEach 把中断权交出去了；各库的 each 又是四套方言。真正缺的不是又一个 API，而是一个统一的说”我有一串东西”的接口。

迭代器协议长什么样

ES6 给的答案是一个约定，不是语法：一个对象只要有一个方法，调用它返回的迭代器实现了 next()，next() 每次返回 { value, done } 这个形状，它就能被遍历。挂在那个方法上的键是 Symbol.iterator——这个 Symbol 本身（注册表、唯一性、well-known symbols）我打算另开一篇细谈，这里只把它当协议名用。

for...of 就是把这段过程写成循环，展开后的控制流是这样：

flowchart TD
  A[取 Symbol.iterator 得到迭代器] --> B[调用 next]
  B --> C{done 是否为真}
  C -->|否| D[取出 value 执行循环体]
  D -->|下一轮| B
  C -->|是| E[正常结束]
  D -->|提前退出| F[调用迭代器的 return 再退出]

两个细节后面要用到。第一，协议规定迭代器”取完即完”，游标在它自己身上，不会重置；第二，return() 是可选方法，专门给提前退出用的——循环体里 break、从函数里 return、抛出异常这几种让循环提前断开的走法，引擎都会补调一次 return()，好让你清理文件句柄、连接、定时器这类资源。这是 forEach 和 jQuery each 给不了的能力。

协议的价值：一套遍历打通所有数据源

先强调我的立场：这套东西的价值八成在协议、两成在语法。哪怕你不写 for...of，只要给自定义数据结构实现 Symbol.iterator，它就同时能被 for...of、展开语法 [...x]、Map 与 Set 的构造函数（new Map(pairs)）以及 Array.from 消化掉，因为大家都认同同一个约定。语言里第一次出现了”能遍历”这个统一接口，而不是每种数据各配一套遍历函数。

按规范和当时的实现，能直接喂给 for...of 的有这几类：

数据源 遍历出来的是什么 当年可用的便利
Array 按下标的每个元素（含空洞处的 undefined） 原生就有，转译最快
String 每个码点，不是码元 代理对场景的唯一解
Map [key, value] 数组，配合 keys() / values() / entries() 需要 polyfill
Set 每个成员，插入顺序 需要 polyfill
TypedArray 每个数值 规范里有，实现还参差，我没敢依赖
自定义对象 / generator 由你的 next() 决定 协议的全部意义所在

至于 NodeList 和 arguments 这两个类数组：协议本身没有替宿主对象做保证，2015 年我手上的稳定版浏览器里它们多数不能直接 for...of，只能先转真数组或者显式借数组的迭代器。这一节的账要算在宿主实现头上，不是协议的错。

for…of 与 for…in 的分工

名字只差三个字母，语义几乎是反的。这张表我贴在工位上：

对比项 for…in for…of
遍历什么 可枚举属性名（键） 迭代器吐出的值
适用对象 普通对象 Array、String、Map、Set 等实现了协议的东西
原型链 会走到，必须 hasOwnProperty 兜 不涉及，只看 next()
能否 break 能 能，且会触发迭代器的 return()
拿索引 键本身就是下标的字符串 拿不到，要自己计数或用 entries()
稀疏数组 静默跳过空洞 把空洞当 undefined 给出来
顺序 实现决定，不保证 由迭代器定义，数组保证下标序

结论一句话：遍历对象用 for...in 加过滤，遍历数据用 for...of。它们不是替代关系，别再拿 for...in 遍历数组了。另外 for...in 不会枚举 Symbol 键，所以给对象补协议时不用担心循环里突然多出一个 Symbol.iterator 让你处理。

polyfill 这件事要说准：Symbol、Symbol.iterator 与新增的内置迭代器都属于运行时能力，浏览器上没有就是没有，得靠 core-js 或 es6-shim；页面里图省事可以直接引 Babel 5 自带的 browser-polyfill.js。上完 shim 之后请务必实测一遍 Map / Set 能不能直接 for...of：迭代方法属于这份标准里最后才稳定的那部分，各家 shim 的覆盖差别就在这儿，我在这个细节上被绊过一次。

性能与类数组的取舍

粗测的做法还是 2013 年那篇里那套：二十万元素的数组取前后差值、跑五轮去掉最高最低，只用来比量级。我的结果大致是：下标 for 记作 1，协议版转译产物大约在 2 到 3 倍，原生 for...of 落在中间，forEach 和 jQuery 的 each 也在 2 倍上下。别把这几个数字当基准，机器和引擎差得太远；可靠的结论只有一条：每轮多一次函数调用这件事是真的，热点路径上传统 for 仍然最快，和两年前一样。

四个会咬人的坑

第一，字符串按码点遍历，和 length 不是一套。 这既是好事也是坑：

按码元切会把一个字符劈成两个坏字符，这在处理用户输入、做字符统计和截断摘要时是真的会出事的。但请记住上一节：转译器若把它展开成下标循环，码点语义就退回码元了，这条别开宽松模式。

第二，活集合边遍历边改。 拿 getElementsByTagName 这类动态集合做遍历、循环体里又删节点，会漏数据——这个坑和《DOM 增删改查与文档碎片 DocumentFragment》里那个是同一个，换成 for...of 一点也不会好转，因为活的是集合本身。老规矩不变：先把集合固定成静态数组，再改文档。

第三，对象默认不可迭代。

原生引擎报的是 “is not iterable”，转译产物里多半变成 “obj[Symbol.iterator] is not a function”，同一件事两种文案，别被带偏。想让它可迭代就照第五节那样给构造函数原型补一个 Symbol.iterator，别为了绕过报错去用 for...in——那是把”我有值要按顺序吐”这件事换成了”帮我枚举键”。

第四，一次性迭代器与 break 的收尾。 同一个迭代器对象遍历完就永远 done，break 之后剩下的项也不会回来；而提前退出时 return() 会被调用（原生如此，转译产物按上面那版结构也会调），所以这个方法是放清理逻辑的地方，别把它当普通读取用。

小结

for...of 的语法价值很有限，就是少写一个索引；迭代器协议的价值大得多：它第一次让”能遍历”变成一个可以实现、可以传递的接口，Array、String、Map、Set 和我们的自定义结构因此能共用同一套消费代码，break 之后还能靠 return() 干净收尾。工程上我现在这么定：遍历数据优先把它接进协议、写 for...of，遍历对象继续 for...in 加 hasOwnProperty，明确的热点循环留传统 for，类数组暂时继续 slice.call。2015 年 9 月这头，Symbol 与迭代器还依赖转译加 polyfill，io.js 3.x 上大致能跑（下周 9 月 9 日它就要和 Node 合并成 4.0，届时得重新测一轮），所以上线前请照目标浏览器逐个实测，别照规范表过日子。
