ES6 let 与 const 块级作用域

let 与 const 看起来只是两个新关键字，但它改的是作用域这件事的结构：绑定挂在哪一层、什么时候创建、什么时候可用、能不能再赋值，这四件事在规范里各有一条独立规则。本文想从引擎与语义实现的角度把它讲透，而不是停在”少用 var”的口号上：先说清 var 的三个老问题在语义层面卡在哪，再走一遍词法环境与声明绑定这套结构，看清楚每轮迭代新建绑定和暂时性死区（TDZ）分别是这套结构的哪个推论；最后回到 2015 年的现实——这些东西在 Babel 5 的产物里变成了什么，我们为此付出什么。前提照旧：ECMA-262 第 6 版 2015 年 6 月定稿才三个多月，当时的主流稳定版浏览器要么没有、要么不完整，生产靠转译。文中的规范推导以定稿文本为准，报错文案按各引擎实际给的不同处理，我没有拿字符串去匹配过。

var 留下的三个老问题

一、函数作用域泄漏。 var 的作用域是整个函数体，{} 拦不住它，所以循环计数器、分支里的临时量在函数结束前一直可见。这类问题的典型症状是”同名变量在函数后半段被悄悄改掉”。

三、重复声明静默覆盖。 同一个作用域里 var a = 1; var a = 2; 完全合法，两份声明合成一份绑定，后一次的赋值把前一次盖掉；跨文件合并之后同名就更难查。这在 let 环境下是错误：

三个问题对应到语义层面是同一件事：var 只有一种宿主——函数（或全局）作用域，而块、循环、重复声明这些结构在它面前都只是”看起来有边界”。

语义结构：词法环境与绑定的三步

规范里作用域不是一张哈希表，而是**词法环境（Lexical Environment）**的链。每个词法环境由两部分组成：一个环境记录（Environment Record），加一个对外层环境的引用。函数调用、模块、块各会推入一层环境；块这一层是 let/const 带来的新增结构，ES5 里块只是语句分组，不产生任何环境。

环境记录里存的是绑定（Binding）。名字是键，绑定是值的那个槽。关键在一行声明被规范拆成三个动作：

var 与 let 的全部差异，都能从”这三步分别发生在什么时候”推出来。var 的 CreateBinding 在进入函数作用域时就一次性做完（那就是提升），InitializeBinding 留到执行到那一行；let 的 CreateBinding 推迟到控制流进入那个块时，InitializeBinding 紧跟声明语句。块级作用域和暂时性死区不是两条独立的规定，它们是同一次推迟的两个推论。

还有一处结构差别值得记：全局 var 的绑定挂在全局对象上（浏览器里就是 window 的属性），全局 let/const 挂在全局环境记录里一个专门的对象环境”声明绑定”区，不会变成全局对象的属性。

这一条在迁移时很容易撞到：第三方脚本用 window.cfg 读你声明的全局配置，你把它改成 let，对方静默读到 undefined。反过来，这也是 let 少见的”帮你把全局命名空间收紧”的收益。

TDZ：把”创建”与”初始化”分开之后

TDZ 常被描述成”在块里用还没声明的变量会报错”，这个说法太浅。准确一点：从进入块、绑定已创建，到执行到声明语句完成初始化，这段时间里读这个绑定就是非法的。之所以要有这段禁区，是因为块级绑定的创建与初始化被拆开了，而引擎不能把一个 uninitialized 的槽当 undefined 交出去——那样一来写错顺序就只是拿到 undefined，和 ES5 的老 bug 一模一样，块级声明想修的问题修不掉。

var size 提前读是 undefined，let count 提前读是报错，从未声明的 notThere 也是报错。三种情况里只有 var 那一种是静默的，而 let 报的是一个已经声明过、只是还没初始化的名字，跟”拼错名字”那类 ReferenceError 是两种不同的 bug，看栈帧就能分开处理（提升让名字先登记、赋值后落地，推导见《变量提升与函数提升的现象与原理》）。真实报错场景我按遇到频率排三个：

一是函数默认参数。参数表是独立的一层作用域，写 function f(a = b, b = 1) 调用时会撞到”b 还没初始化”，而 function f(a = a) 是自我遮蔽的经典形态：默认表达式里的 a 解析到参数自己那层绑定，外层的同名变量被挡住了，直接 ReferenceError。

二是块内后置声明。为了”顶部先给入口”把 let 挪到函数底部、或在条件分支里 let 之后又在块外读它，都会撞 TDZ。

const 锁的是绑定，不是值

const 唯一多出来的规定是：绑定初始化之后不可再 SetVariable。它管的是”这个名字不能再指向别的东西”，跟那个东西内部怎么变毫无关系。

这是本文真正想给的东西。转译器面对的不是”把关键字换掉”，而是要在只有函数作用域的 ES5 上重建块级结构，手段是两条：改名与加层。

形态与内部命名会随小版本变化，我这里描述的是机制。由此有三笔账要算清。

第一笔，运行时保护没了。产物里 const 就是 var 加一个下划线前缀，没有任何一句检查。给一个 const 重新赋值在原生引擎上是 TypeError，在转译产物上是静默成功。这一条我要写在最显眼处：转译帮你保住语义，不帮你保住纪律，const 的保护在老浏览器上只剩 ESLint 和代码审查。

第二笔，性能与体积。纯块级（无闭包捕获）基本只有改名的开销，产物规模也几乎不变；一旦循环体里有闭包捕获循环变量，转译要按轮多一次函数调用与一份闭包分配。这是定性的相对量级判断：同一台机器上同一份循环，改写前后能感到差异，但它不会出现在”整个页面加载”这种口径里；我不会给基准数字，因为各家引擎的差异比这一点开销大得多。真要省，就把带闭包的循环写回 ES5 的显式包装、或者让热路径避开每轮建函数。

第三笔，调试。产物里满屏是 _i、_tmp、_loop，在老式调试面板里断点看到的名字和源码不一致，watch 表达式按源码写会失配；source map 当时各家支持程度差别很大，IE 那一侧基本指望不上，线上排查仍以读产物为主。这条不是不能忍，但要提前告知识库和值班同学。

另外转译器保守得合理：当它无法确定某个块级绑定的捕获关系（块里有函数声明、循环变量被循环外引用、label 与 break 参与控制流），可能给出近似语义或直接报错。所以我项目的规矩是转译前后各跑一遍单元用例，块级声明相关的用例专门覆盖”循环里存回调”这一种。

团队规约：默认 const，要改才 let

我们的落地版本分三步，供参考。

第一步只加不改：构建里挂上 Babel（babel src -d lib --watch，或 gulp-babel、grunt-babel、browserify 加 babelify），新写的文件允许 let/const，老文件一律不动，禁止在同一个函数里混用两套声明风格。第二步把规则交给工具。ESLint 在 2015 年 7 月发到 1.0，配 babel-eslint 作为解析器才能读 ES6 语法，当时还靠 ecmaFeatures 逐项打开特性，no-var、prefer-const、block-scoped-var 这几条规则已经齐了：

prefer-const 只报”声明之后从未重新赋值”，它不改代码，改代码的人得自己想清楚这个名字是不是常量；block-scoped-var 是给还没换掉 var 的文件用的，报”在块里声明、块外用”，等于在 ES5 语义下提前演练块级规则。JSCS 那边九月份刚宣布并入 ESLint，样式检查往 eslint 一路收拢，这也是今年能看到的变化。第三步是收掉 var：只对新代码开 no-var，历史文件走 overrides 关掉，别一次性全量打开——全量打开的结果是提交里出现一堆为过检查而做的无意义改动。

约定本身只有三句：默认 const；确实要重新赋值才 let；var 只允许出现在还没迁移的老文件顶部。

上线前的六条自查

  1. 全局配置改成 let 之后，确认没有第三方脚本靠 window.xxx 读它。
  2. 循环里存回调的地方，转译前后各跑一遍，看产物是不是真的按轮建绑定。
  3. typeof 探测的名字在当前作用域里有没有 let 声明过，避免探测抛错。
  4. for (const ...) 配自增会 TypeError，改成 let 或改 for-of。
  5. 需要不可变的数据就显式 Object.freeze，并想清楚要不要递归；不要指望 const 替你锁值。
  6. 老浏览器里 const 没有任何运行时保护，纪律靠 ESLint，审查靠看 diff 里的重新赋值。

关于流传的说法要澄清一句：有些资料说旧版 IE 的 JScript 把 let 当保留字、因此 obj.let 之类写法会出问题。这条我找不到权威出处，也无法在这台机器上复现，所以不作为本文依据；可以确定的只有一件事——老引擎对 let/const 是解析期语法错误，跨浏览器只有转译这一条路。

小结

let 与 const 的价值不在关键字好看，而在语义结构上多了一层块级环境，并因此把绑定的创建、初始化、赋值三件事拆开了：块级作用域来自”进入块才创建绑定”，TDZ 来自”创建与初始化之间有间隔”，循环里闭包各拿各的值来自”每轮迭代复制出一份新绑定”。const 只多管一件事——绑定不再可写，所以它是可读性工具而不是安全工具，锁值还得靠 Object.freeze 且要自己递归。转到工程侧，转译能在 ES5 上重建这套语义，代价是三笔：老浏览器里 const 失去运行时保护、带闭包的循环每轮多一次函数调用与分配、调试变量名和源码不一致。因此我给的路线是：先接 Babel、再上新文件、再用 ESLint 1.x 的 no-var 与 prefer-const 逐步收口，最后把六条自查放进 code review 清单。至于原生引擎什么时候能替我们省下这些代价，按 2015 年 9 月这个进度，还得再等一阵。
