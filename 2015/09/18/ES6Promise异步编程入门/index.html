ES6 Promise 异步编程入门

回调的问题一句话就能说清：错误处理散落在每一层、控制权交给了被调用的函数、你无法信任对方一定会按约定调你的回调。Promise 把”未来的结果”变成一等公民来收拾这个局面，但 2015 年 9 月的现实是：标准刚定稿三个月，原生实现覆盖不全，jQuery Deferred 已经遍布存量代码，bluebird、Q、RSVP 各有一摊用户。本文不打算再讲一遍 Promise API——那是文档的活——而是把当时能用上的四套方案摆在一起横向比较，给出选型结论，重点写混用两套 then 的实际事故和几条保命的写法纪律。jQuery Deferred 的内部实现与微任务队列在《jQuery 的 Deferred 与 Promise 模式》和《JavaScript 事件循环机制解析》里已经讲透，本文直接引用结论。

原生 Promise 在 2015 年 9 月的真实覆盖率

先划引擎底线。原生 Promise 从 Chrome 32、Firefox 29 起可用，Node 0.12 起内置，合并后的 Node 4.0 LTS（本月 9 号刚发布，V8 4.5）里开箱可用；IE 全线没有，刚起步的 Edge 12 才第一次带上它，Android 4.4 那个基于 Chrome 33 的 WebView 要显式开关、iOS 8 的 Mobile Safari 指望不上。所以”原生”两个字在生产里等于”没有”，桌面端勉强、移动端必须配 polyfill：core-js、es6-shim，或者 Babel 5 自带的 babel-core/browser-polyfill.js 三选一。这里有个容易忽略的坑：polyfill 补的是构造函数和 all/race 这些静态方法，个别老实现（比如某些框架内嵌的私有版本）只有 then 没有 Promise.all，上线前值得跑一段探测代码确认静态方法齐不齐。另外要分清两条线：ECMA-262 第 6 版定稿的 Promise 与 Promise/A+ 规范在核心语义上等价，差异主要在附加能力，下文按 Promise/A+ 语义讨论的部分四家都遵守。

四套方案逐一过招

原生 Promise：语义最干净，构造函数里 throw 自动转 rejected，then 回调抛异常自动传染给下游，回调一律异步执行。代价是覆盖面如上，以及当时标准里就是没有 finally、没有取消。

jQuery.Deferred：前作已经把它的三组特性讲透了——then 接受成功、失败、进度三个参数；回调里抛异常不会被自动捕获成失败状态而是冒泡到全局；有 progress/notify 通知轨和 state() 查询；deferred 与 promise 能力分离。它最大的历史包袱是 jQuery 1.8 之前 then 不返回新对象、回调返回值被丢弃，链式转换只能靠 pipe。

Q：最早严格贴着 Promise/A 规范做的库之一，Q.Promise、Q.nfcall 把 Node 风格回调转 Promise 的工具很全，语义接近原生。它的 then 是延迟执行的，异常自动捕获，这些与原生一致；差异在 API 命名（q/all、q/timeout 走模块风格）和体积，2015 年已明显不如 bluebird 活跃。

bluebird：当时功能最全的一家。promisifyAll 一键把整套 Node API 变成 Promise 风格（fs.readFileAsync 这类），longjohn 配合它能打出穿透异步边界的完整调用栈，coroutine 支持用生成器写同步风格的异步代码，还有 finally、spread、timeout、promisify 一堆原生没有的方法。代价是体积在四家里最大，学习曲线也最陡——它的方法表能占两页文档。

RSVP：Tileman 为 Ember 写的那一家，API 贴着 Promise/A+ 走，额外补了 RSVP.filter、RSVP.map、RSVP.rethrow，体积比 bluebird 小。选它的项目大多因为在 Ember 生态里，独立选型时它的存在感不如前两家。

表里”执行时机”一行值得多说两句：jQuery Deferred 在已经 resolve 之后挂 done 是同步立刻执行的，原生 Promise 的回调无论何时都排到本轮主任务之后——这正是前作讲过的微任务队列差异，同一份”看起来只是换了构造函数”的代码，加了一个 done 之后的同步语句顺序可能完全不同。

“非标扩展方法”单独警告：finally、done、spread、timeout、retry 在 2015 年 9 月全是库的私有加法，没一个是标准，还同名不同义——bluebird 的 finally 透传上游值，spread 只有 Q 和 bluebird 有，finally 还在 TC39 议程上没进规范。把这些能力封进工具函数，业务链只跑 then/catch/all/race 四件套。体积按完整包压缩未 gzip、同机粗测的相对量级：bluebird 最大，q 和 RSVP 小一档，es6-shim/core-js 只取 Promise 部分最小——只要链式语义就用最便宜的填充，要超时重试和长调试栈再上 bluebird。原生没有窥探状态的口子，调试只能学 state() 的思路，在关键节点插打点函数。

选型结论与混用事故

结论分三种项目。新建的 Node 服务：直接用 Promise/A+ 语义，bluebird 按需引入——需要 promisifyAll、超时重试、调试栈时用它的超集，只需要基本链式就用原生。需要支持 IE 或老移动端的页面：polyfill 选 core-js 或 es6-shim，别指望原生。已有一堆 $.ajax(...).done(...) 的 jQuery 项目：继续用 Deferred，不要半途换库。

then 回调返回的不是 Promise，链就不等，全速跑掉，把没完成的异步甩在身后；被甩掉的 success 回调里出的错，链尾收口也接不着。

标准展开见到带 then 的返回值，就把成败交给对方回调——对方不吭声，它永远 pending。挂起的链无错误、无日志，catch 对 pending 无能为力，是最难排查的线上故障；防御两道：先过前作的 duck typing，但验的是接口不是契约，进链前再配下文要讲的超时保险丝。

三个设计决定：回调一律经 setTimeout 排队，绝不”已完成就同步执行”——jQuery 同步/异步分叉的病根前作已讲透，自造实现必须抹平；回调抛异常转下游 reject；这个迷你 promise 没实现 thenable 展开，只在自己工具内部流转、绝不喂标准链——用途只有一个：在缺 all/race 的老私有实现里搭下一节工具。

错误收口的职责边界：then 的第二参数不等于 catch

“链尾收口”上一节点过名，这里给更细的颗粒度：then(a, b) 里的 b 和挂在后面的 catch，接的根本不是同一批错误。

口诀：then 第二参数”管进不管出”——接得住上游 reject，接不住第一参数自己抛的异常，也接不住它启动的异步操作后续失败（除非把那个操作 return 出去）；catch 两者都接。所以链主体一律单参数 then、末端统一收口；双参数只留局部降级——失败就地给兜底值、链继续：

2015 年 9 月原生没有任何”漏网 rejection”检查工具，finish 约定加 grep 式评审是唯一防线；再挂 bluebird 的 onPossiblyUnhandledRejection 集中上报不冗余——钩子兜住忘挂 finish 的链，finish 兜住钩子被禁用的环境。

这些场景，别上 Promise

选型讨论了一路，反过来也得画线。其一，一次性回调、下游没有链：包成 Promise 只是多养构造函数和队列，观察者仍只一位——结果没有后续链条就别包。其二，取消是第一需求：前作说死了，abort 是 jqXHR 的能力，Deferred 不容回头，原生无解，bluebird 的 cancel 也只让 Promise 自己变失败态；”离开页面立刻全停”仍得靠标志位加各层清理，这苦活谁都得干。其三，UI 硬依赖进度的旧代码：进度轨在原生 Promise 里根本不存在，强行转链必然丢 notify，就是前文进度卡死的病根；要么 Deferred 用到底，要么进度走普通回调这条第二通道。轮询、推送这种”一个操作、N 次结果”，与一次性状态语义不匹配，别硬凑。

迁移策略：新模块起步，边界处收口

存量 jQuery 项目转向标准 Promise，按四步走。第一步，新模块先上、老代码不动：新增模块一律单参数 then 加链尾 catch；已有 Deferred 链的模块禁止半途改风格——半改的模块同时带两套心智，是最危险的中间态。第二步，只在边界处 promisify：ajaxPromise、promisify、桥接全部收敛进一个 lib/promise-bridge.js，其他文件不许用 jQuery 对象 new Promise——两套 then 的接触面压进单文件，排查范围随之缩。第三步，链只走单程：Deferred 经桥转成标准 Promise 后到末端只用标准语义，喂回 jQuery 挂 done 一律评审打回；带 then 的来路不明对象先过 duck typing、挂上超时保险丝再进链。第四步，加载期探测：把”填充齐不齐”变成运行时检查而不是测试用例——

构建链上注意两条线的分工：Babel 5 只转译语法（模板字符串、class 之类），从不提供 Promise 运行时——

运行时必须另有出处：core-js、es6-shim 或 Babel 自带的 babel-core/browser-polyfill.js，且要排在业务 bundle 之前——顺序颠倒时第一行 new Promise 就是 ReferenceError，只在老浏览器上复现、最容易漏测。Node 侧不用折腾：io.js 3.x 与本月刚发布的 Node 4.0 内置原生实现。

小结

2015 年 9 月做异步方案选型，实际是在”标准刚定稿、引擎没跟上”的缝隙里做决定：原生 Promise 语义最好但覆盖率最低，移动端一律配 polyfill；jQuery.Deferred 在存量项目里继续成立，但它的异常不捕获、已完成时同步执行、进度三参数这三点与 Promise 心智有实质冲突，绝不混用两套 then；要额外能力就上 bluebird，promisifyAll、超时重试和 longjohn 调试栈在当年都是硬需求，Q 和 RSVP 则各守一小块生态。写法上记住五条纪律：return 每一个新 Promise、then 里 throw 就是 reject、链条保持扁平、链尾收口、unhandled rejection 靠约定和库兜底。工具会换，纪律不会作废。
