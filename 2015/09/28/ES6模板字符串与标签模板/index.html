ES6 模板字符串与标签模板

模板字符串大概是 ES6 里最容易”用起来”的一块语法：它把多行文本和插值收进一种写法，还顺带给出一个把字符串当函数调用的机制——标签模板。本文面向已经在项目里写过几百行 + 拼接的读者，讲三件事：它相对 ES5 的三种老写法到底好在哪、标签模板的机制与两个可以直接上线的例子（HTML 转义与简单 i18n）、以及它跟当时那批模板引擎的分工边界。年代前提要先摆明：ECMA-262 第 6 版在 2015 年 6 月 17 日定稿，到今天才三个多月，主流稳定版浏览器没有一个能完整跑这套语法，线上仍然要靠 Babel 5 转译成 ES5。文中的转译产物只描述形态，不保证与你手上那个小版本的输出逐字符一致；涉及浏览器版本进度的地方，我给方向不给具体版本号，因为没有可靠的对照表。

插值里放的是完整表达式

不合法的仍是”语句”：${var x = 1}、${if (a) b = 1}、${for (...)} 一律语法错误。要在插值里做分支，只有三元、逻辑短路或者调一个函数进去，这反而逼着把片段渲染写成小函数，是好事。

和 + 拼接最实质的差别在隐式转换的落点。+ 是二元运算符，从左往右一路判类型，只要左边已经是字符串，右边的加法就会被拉进字符串世界：

${} 内部是独立的求值环境，表达式按原本的运算符做完，结果再走一次 ToString。数组、对象这些也照 ToString 走，所以 ${[1, 2]} 是 '1,2'，${{}} 是 '[object Object]'，跟 '' + [1, 2] 一样——不要指望模板字符串对对象更聪明，需要可读输出就给对象写 toString，或者显式调 JSON.stringify。null 与 undefined 会被转成 'null'、'undefined' 两个字面词出现在界面上，这是”数据没取到”最常见的暴露方式，实际项目里插值前面加一次判空仍然值得保留。

String.raw：反斜杠的另一种落点

模板字符串有个内置标签叫 String.raw，它返回插值做完、但反斜杠保持原样的结果：

在 ES5 里同样的东西必须写双反斜杠，正则尤其痛苦：'\\d+\\.\\d+' 这种字符串读三遍才能确认它匹配什么。String.raw 把”字符串里看到的”和”正则里想要的”对齐了，这是它最正当的用途。Windows 路径、LaTeX 片段、shell 命令都属于同一类。

两个限制要记牢。第一，String.raw 仍然会做插值，${} 里该怎么算还怎么算，它只影响反斜杠。第二，它是运行时的一个函数，不是语法。转译器能把反引号拆成字符串拼接，但代码里出现的 String.raw 这个名字得由运行时提供，所以在旧浏览器上要引入 polyfill（core-js、es6-shim，或者 Babel 5 自带的 babel-core/browser-polyfill.js）。在 Node 4 里它已经是内置的，可以直接用。

标签模板的机制

把模板交给一个函数处理，就是标签模板：函数写在反引号前面，返回值由你自己决定。

三条规则：第一个实参是字面量片段数组，比插值多一个；从第二个实参起，依次是每个插值求完值的结果；strings.raw 是同一组片段的”原始反斜杠”版本。这里我用 arguments 遍历插值而不是 ...values，因为剩余参数不是我这篇的主题，等它写完再统一换。

值得单独留意的是插值的求值时机与类型：所有 ${} 在调用标签之前就求完值，而且没有转成字符串，类型原样交进来。所以插值里写 1 + 2，标签收到的实参是数字 3，不是字符串 '3'。这既是机会（你可以在标签里按类型分派格式化策略，下面 i18n 例子里那个 toText 就是这么做的），也是责任（String(...) 这一步要么你做要么不做，模板本身管不了）。

实战一：把插值统一转义成 HTML 安全文本

这是标签模板最实用的一个落点。前端把用户输入拼进 HTML，靠”每个人都记得转义”是靠不住的：一个 300 行的渲染函数里漏掉一处 ${nickname}，就是存储型 XSS。把转义收进标签，规则变成”只要这个字符串是用 safe 生成的，插值就一定是安全的”，审查面从”逐个插值看有没有转义”缩成”看这个模板有没有用 safe 打头”。

要点在于只转义插值、不转义字面量：模板里的 <p> 是作者写的标签，必须原样保留；${} 里的东西是外部数据，必须收口。写 ES5 拼接时这两者混在同一个 + 链里，一眼看不出谁是数据，这正是漏转义的来源。

边界也必须说清楚，否则这个例子容易被当成免死金牌。第一，它只处理”文本节点”上下文。用 safe 输出属性值时，外围引号是模板里写死的，这一环没问题，但 URL 本身还得校验协议，javascript: 与 data: 转义是拦不住的；事件处理属性、内联脚本、CSS 表达式这些上下文的转义规则和 HTML 文本完全不同，一个通用函数覆盖不了。第二，如果插值进来的是一段富文本 HTML，那你需要的是白名单过滤而不是转义，safe 会把它整段显示成文字，业务上就错了。第三，前端转义不能替代服务端那一层：数据入库前的校验、服务端渲染时的输出编码、日志与接口返回的转义，都在另一个进程里，浏览器上的这个标签帮不上忙。它解决的是”客户端拼 DOM 字符串这件事容易漏”，不是 XSS 的全部。

实战二：一个小 i18n 标签，顺带做数字格式化

第二个例子处理文案。i18n 的麻烦不在翻译，在于语序：中文里”文件夹数量”在”邮件数量”前面，英文正好相反，而模板字符串的插值顺序是写死的。所以占位符要带下标。

这个写法的好处是翻译键由源码里的英文字面量自动拼出来，不用维护一份外部 id 表；数字插值统一走千分位。坑也很具体：占位符数量与插值数量不等时，我这里选择”缺就填空串”，实际项目里更该抛错——文案错位是那种上线后没人报、只有客服转单的 bug。另外翻译键里带换行与缩进时，strings.join('%s') 会一起进键，所以模板要么写在一行，要么在拼键前做一次空白归一。想把转义和文案叠起来是 safe`${t`...`}` 这种嵌套，但要小心 safe 会把 t 的返回值再转义一遍，出现 &amp;amp; 这种二次编码，两个标签的职责要在文档里划清。

它和模板引擎怎么分工

2015 年做客户端渲染，模板引擎的选择大致是 Handlebars、Underscore 的 _.template、doT.js 这一档。把它们和模板字符串放在一起比，比的是”模板放在哪儿、谁能改”：

维度 模板字符串 模板引擎
适合的长度 一屏以内的片段、属性值、URL、日志文案 整块 DOM 结构、带循环与分支的组件
循环嵌套 靠 map 加 join，深了就没法读 {{#each}} 之类块语法，结构清楚
谁能改模板 前端同学（改一处要跑构建） 后端与设计能把纯文本文件搬来搬去
转义策略 自己写标签决定 Handlebars 默认转义、doT 自己管，策略是库定的
预编译 谈不上，本来就是代码 支持离线编译，运行时只吃编译产物
依赖体积 零 一个库，几十 KB 量级

我的取舍很机械：片段用模板字符串，结构用模板引擎。给一个 class 名拼三段、组装一个查询串、日志里带上三个变量，这些用模板字符串最省事，读起来比 + 清楚一个量级；一整个带表格和分组的列表视图，塞进反引号里写 map 嵌套，两个星期后没人敢改，这类东西还是交给 Handlebars 的预编译产物。模板放在 HTML 里也有现成路子——<script type="text/x-template"> 老而弥坚，HTML5 的 <template> 标签在当时的引擎上进度不齐，IE 一侧基本指望不上，用之前要准备好降级。

引擎侧的现实是：这套语法在当时的主流稳定版浏览器里没有一个可以放心裸奔——Firefox 对模板字符串的支持相对早，Chrome 一侧还要陆续补齐，IE 11 完全没有，Android 4.4 的 WebView 基于很老的 Chromium，iOS 8 的 JavaScriptCore 也弱。更要命的是反引号在旧引擎里是解析期的语法错误：文件里只要有一个没转译的反引号，整个脚本不会执行，而不是”这段代码不跑”。所以别把 ES6 语法混在共享的老工具文件里，也别指望用 try/catch 兜住——它兜不住 SyntaxError。要么全项目转译，要么按目录切分并保证产物一致。

小结

模板字符串解决的是两件很具体的事：多行文本不用再把换行写成转义，插值表达式在自己那对花括号里算完再转字符串，避免了 + 从左往右一路被类型拽走。String.raw 补上反斜杠这一类”看到的和想要的对不上”的场景，但它是运行时函数，旧浏览器要 polyfill。标签模板的价值不在语法新奇，而在把一条输出规则收进一个函数：HTML 转义与 i18n 文案这两个例子，都是把”每个人都别犯错”换成”只有一个地方需要正确”。用它的前提很清楚——片段短、逻辑在内、由前端维护；结构长的模板仍然交给 Handlebars 或 _.template 那类引擎。最后重申年代现状：这套语法在 2015 年 9 月只能靠转译上线，反引号进了 IE 是整个文件解析失败，构建产物要按目录切干净。
