Fiddler 与 Charles 抓包实践

Fiddler 和 Charles 都属于”坐在浏览器与服务器中间”的那类工具，用法差别却比想象中大。本文不抄两家菜单，只从性能与调优的角度，把笔者这一年真正用来下结论的功能串起来：缓存有没有命中、gzip 有没有生效、弱网下首屏怎么劣化、真机怎么抓、CORS 怎么定位。

两个工具各自的位置

Fiddler：Windows 上的系统代理式调试

Fiddler 启动后把本机代理指向自己监听的 8888 端口，凡走系统代理的流量都先经过它，所以抓到的不只是浏览器，桌面客户端、命令行、局域网里手动指过来的手机都能进来。用得最多的是四块界面。Inspectors 看请求头、响应头和正文，右侧能在原文、图片、十六进制视图之间切换，排查编码问题靠后两个；Timeline 把请求按发起时刻与持续时间画在同一把时间尺上，并发有没有跑满、谁排在队尾一眼可见；Statistics 按体积和耗时排序，谁吃掉首屏流量第一眼就是它；Composer 把会话拖进去改方法、改头、改正文再发一次，做对照实验省事。

AutoResponder 做本地映射与离线联调：把线上资源换成盘里的文件，前端就能在真实页面壳子里调自己的版本，接口还没上线时也能拿它造响应。Rules 里几个开关要理解清楚再按。Remove all responses 只保留头、扔掉正文，适合验证接口返回空时页面会不会白屏，但它和断网不是一回事，超时与空响应走的是不同分支。Simulate If-Modified-Since 让传输量骤降、时间条缩成一小截，看着很美，其实页面自身的缓存策略并没被检验。解密 HTTPS 要装 Fiddler 自己的根证书并让系统与浏览器信任它；没装好的症状是会话一片空白或只剩一条 CONNECT，很多人据此认定抓不到加密流量。

Charles：Mac 侧的对应能力

Charles 在 Mac 上承担同样角色。SSL Proxying 决定哪些域名和端口参与解密，没加进列表的站点只看到 CONNECT 隧道和乱码正文。Throttle 分别设下行带宽、上行带宽、时延和丢包率，时延要按往返估，别把界面数字当单程。Map Local 换成本地文件，Map Remote 指到另一台机器，Rewrite 按规则增删改请求头、响应头和状态码。Breakpoints 能在请求发出前和响应回来前各停一次让你手改，这种半途插手的灵活性最顺手。Repeat 相当于 Fiddler 的 Composer。它还能把会话存成文件、分组、写备注，联调时发一份给后端比截图清楚。版本号笔者没把握，只按当时的一线版本说。

两者不冲突。Windows 上主力用 Fiddler，它对系统代理与证书体系贴合更好；Mac 上和真机联调用 Charles，Throttle 配手机一起用最方便。命令行侧的 mitmproxy 也能做同样的中转，脚本化改包灵活，只是没有图形化的时序与体积视图。

缓存命中到底有没有发生

先把两组头分清。强缓存看 Cache-Control，存量服务还在发 Expires，它决定这次请求要不要出网络门；协商缓存看 ETag 与 Last-Modified，资源过期后浏览器带上 If-None-Match 或 If-Modified-Since，服务器认为没变就回 304。于是抓包会遇到三种状态：真 200 是完整正文从网络进来；304 省了正文但没省往返；第三种是本地缓存直接命中、浏览器压根没发请求，代理工具反而抓不到。这就是最大的判定陷阱：看到 200 不能推出缓存没做好，得先看它有没有网络耗时和响应体大小；看到 304 也不能当成强缓存命中，它是一次完整往返，弱网下照样要付往返成本。

压缩、连接数与静态资源这笔账

gzip 到底有没有生效

只看响应声明了压缩还不够，要核三件事。请求有没有 Accept-Encoding；Vary: Accept-Encoding 在不在，缺了它分发层可能把压缩版和未压缩版混着回给不同客户端；实际字节数确实变小了，要和服务器上的原始文件对比才算数。最容易踩的坑是中间层吃掉压缩：某些企业网关、老代理或安全设备转发时会重新拼包并抹掉 Content-Encoding，浏览器收到一大坨未压缩正文，直连源站却明明是压缩的。这时分别直连和走本机代理各取一次头，对比就露馅。

两条命令只差一行输出，问题就不在业务代码。压缩有适用边界：文本类收益明显，已经压过的图片和字体再套一层只是浪费 CPU，个别配置把这些类型也塞进白名单，于是响应体比原始文件还大。图片转 base64 内联会把体积抬高约三分之一，内联小图省请求，内联大图亏本。

keep-alive 与并发连接

这套心智的底座是 HTTP/1.1：单域名大约六条并发连接，请求多了就排队。把 Timeline 摊开，若看到一段空白等待排在请求尾部，通常是连接数打满而不是服务器慢。长连接有没有生效很好查：响应头里有没有 Connection: keep-alive，同域名连续请求的建连耗时是不是接近零；把请求按连接分组，看握手与等待的拆分，就知道是不是每条都在重新握手。服务端空闲超时设得过短（比如两秒）时，首屏请求会被拆成好几轮建连，这问题只在真链路下看得见。顺带说一句，HTTP/2 规范在 2015 年 5 月才定稿，浏览器端还没真正支持，所以那时候只能减请求数、合理分域名，多路复用这条路上还没有。

合并与域名分片要算账

域名分片的收益前提就是那六条连接。四五个域名通常已经够，分太多反而亏在解析和新建连接上；核对办法是数每个域名的请求数与建连次数，新增域名带来的若是大量冷连接而不是排队下降，说明已经过头。合并同理：散碎文件打包成大文件能显著减少请求数，2015 年这套构建流程里 webpack 还属于刚开始被接受的阶段，多数项目仍靠 Grunt 或 Gulp 拼合压缩；但粒度过粗会让一处小改动毁掉整包缓存，改完那条请求又变回完整下载。雪碧图是一个道理：

弱网与真机：先把档位讲道理

弱网模拟我会先设一档”有意义的慢”：下行几百 kbps 量级、上行几十 kbps、往返时延几百毫秒、丢包从百分之一试起。关键是别只调带宽。很多人把弱网简化成带宽变小，结果只复现出下载慢；真实移动网络要命的是时延和丢包，握手与头部开销被放大之后，小文件多的页面比大文件少的页面更惨。档位原则是每次只动一个变量，并留下带备注的会话文件，否则三轮之后自己都忘了上一档改了什么。运营商实测数字我没有可靠来源，不当经验写在这里。

真机抓包很简单：手机与电脑连同一个无线网，在手机的网络设置里把 HTTP 代理改成手动，填电脑局域网地址和 8888 端口，再在电脑端允许来自局域网的连接，手机流量就进来了，弱网档位同时生效。iOS 还要让手机信任那张根证书，装上描述文件后再去通用设置里打开开关，否则抓到的仍是密文。限制也很明确：部分应用做了证书校验或不走系统代理，抓不到；Android 上某些内置内核对代理响应不一致；HTTPS 解密本质是用自己的根证书换掉信任链，只能在自己的测试机上做。被 Rewrite 或 Breakpoints 改过的响应同样不能当线上事实引用。

抓包工具与浏览器自带的 Network 面板不是替代关系。后者看到的是浏览器处理之后的视图，优势是把请求与页面发起者、渲染节点对齐，本地缓存命中标得最清楚；代理工具的优势是拿到拦截与改写前后的原始报文，看得见连接层细节，还能跨设备、跨浏览器、跨应用。笔者的用法是先看单页时序，再看真实链路的头与体积，两边数字对不上时，通常是压缩、改写或分发层在中间动了手脚。

CORS 排障：把预检看清楚再改代码

带自定义头或把 Content-Type 写成 application/json 的跨域请求，会先发一个 OPTIONS 预检。它在代理工具里是独立一条会话，要单独打开：请求侧看 Origin 与它申报的方法和头字段；响应侧看 Access-Control-Allow-Origin、-Methods、-Headers 与 Access-Control-Max-Age。预检失败时真正的请求根本不会发出去，控制台只给一句含糊报错，很多人回头改业务代码，其实服务器压根没回应这个探测方法，或者被网关挡掉了。另一类误判是预检响应常常不带 Access-Control-Allow-Credentials，而正式请求需要它，于是浏览器抱怨允许来源写成了通配：要凭据就得回具体来源并把凭据那项置为真，缺一都不行，无脑回 * 又指望带 Cookie 的方案本身不成立。还有一种是中间层没把 Origin 纳入缓存键，表现为换个站点访问就偶发失败，只能对比两次请求的响应头。存量接口改不了响应头的环境，JSONP 还能撑一阵，但它只支持取数据、没有错误细节。

用一张时序图收尾

首次请求与刷新时的差别只在有没有条件头、有没有正文，网络成本却天差地别。下面是核对这两条分支的思路。

sequenceDiagram
    participant B as 浏览器
    participant P as 代理工具
    participant S as 源站

    B->>P: GET 资源，首次请求不带验证器
    P->>S: 原样转发请求
    S-->>P: 200 带完整响应体与实体标签
    P-->>B: 200 正文写入本地缓存
    Note over B: 缓存记下实体标签与最后修改时间

    B->>P: 再次进入，请求带上条件头
    P->>S: 条件请求
    S-->>P: 304 只有头部没有正文
    P-->>B: 304 浏览器改用本地副本
    Note over B: 仍消耗一次往返，弱网下不等于零成本

小结

两个工具定位不同：Fiddler 更贴 Windows 的代理与证书体系，AutoResponder 与 Composer 擅长造响应和重放；Charles 更贴 Mac 与真机联调，弱网档位、改写、断点和会话备注最有价值。性能视角下有三条硬规矩。状态码要和网络耗时、响应体大小一起读，200 未必是重新下载，304 也不是零成本。压缩与缓存都要在同一条真实链路上验证，源站自己试一把通过不代表用户拿到同样的头。改包工具留下的规则一定要收干净，笔者见过整份性能报告建立在一处忘关的本地映射上。工具给的是证据，别让它替你做结论。
