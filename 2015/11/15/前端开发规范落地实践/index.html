前端开发规范落地实践

两年前我们写过一份二十多页的前端开发规范，贴在内部 wiki 上，读完的人不多，长期照做的更少。这篇复盘讲我们怎么把那份文档拆成代码，塞进编辑器、Git 钩子和构建任务里，让规则不再靠人自觉。中间踩的坑比结论多，尤其是一次性格式化老代码把提交历史冲乱那件事，代价我们花了半年才消化掉。适合正在靠人工评审约束风格、或者准备对存量代码动手的团队先读一遍再决定怎么开工。

规范为什么会烂掉

先说一个让人不太舒服但必须承认的结论：规范只要还依赖人自觉，就一定会退化。

这不是态度问题，是机制问题。一份放在 wiki 上的文档，它对新人的成本是”要先读完二十几页才能开始写代码”，而对老员工的成本是”每次改动都得回忆一遍条款”。人在这两种成本面前都会选择绕过。更要命的是三个人凑在一起的放大效应：一个人用两个空格，一个人用四个空格，第三个人用 Tab，于是同一个文件里三种缩进混着出现，后面任何人碰这个文件都会顺手把自己那套改回去，一次小小的改动就能在 diff 里造出上百行无关变更。评审的时候谁也说不出错，因为规范确实写了，只是没人执行。

所以我们的出发点变了：不再问”怎么让大家记住规范”，改成问”哪条规则可以在什么位置被机器自动检查或自动修正”。能自动的进工具，不能自动的降级成建议，只留在评审里口头提醒。按这个思路，落地被分成三层。

三层机制各管一段

三层分别管三个时间点。编辑器层管”正在敲字的时候”，让错误尽量不产生；提交层管”离开本机之前”，让不合格的代码出不了这台机器；构建与持续集成层管”合进主干之前”，兜住前两层被绕过的所有情况。三层不是冗余，而是覆盖范围不同：编辑器配置只影响装了插件的人，本地钩子可以用一条参数跳过，只有构建与流水线是所有人都绕不开的。

编辑器层：把规则放到眼睛前面

这一层的基石是一个叫 EditorConfig 的小东西，仓库根目录放一个文件，支持它的编辑器会自动读取，把缩进、换行、字符集、行尾这些最基础的东西统一掉。

它只解决空白字符这一类问题，不管语义，这个定位要搞清楚，别指望它替代检查器。语义部分靠编辑器装的 JSHint 插件，它读的还是仓库里那一份配置，所以你在编辑器里看到的波浪线和钩子里跑出来的报错是同一条规则，不会出现两边打架。

至于保存时自动格式化，当时的做法是让编辑器插件去读同一份配置决定缩进宽度，并把团队设置导成文件放进仓库，新同事克隆下来就能对齐。我们刻意没有做”保存即全文件重排”，原因见后面格式化那个坑。

提交层：pre-commit 是本地最后一道闸门

Git 的钩子放在 .git/hooks/ 下，但这个目录不进版本库，所以我们把钩子源文件放在仓库里，配一个安装脚本。

钩子返回非零，提交就中断，这是它的价值，也是它的天花板：git commit --no-verify 一秒绕过。所以钩子只做”便宜且高信号”的检查，跑得很短，几秒钟出结果，不然大家真的会去查怎么跳过它。真正的兜底在下一层。

构建与持续集成层

Grunt 里把检查挂成任务，串进默认流程，流水线上一次构建就会跑到。

检查器的口径要说清楚：我们主力用的是 JSHint 2.8，规则文件 .jshintrc 锁在仓库里；JSLint 太严苛，我们只在自己写的构建脚本上偶尔用。ESLint 当时刚出 1.x 不久，规则数与插件生态都还很薄，我们只在个别新项目上观望，暂时不往团队主流程里投——配置怎么写、怎么和 JSHint 共存，这些等它站稳再说。

流水线里的规则是：jshint 失败即红灯，红灯即阻断合并，没有”这次先过下次再说”。这一条是整层机制生效的唯一前提，一旦允许红灯合入，上面所有东西都会在半年内退化成装饰品。

我们踩过的坑

这一节是本文真正的价值所在。每条都是付过学费的。

一次性格式化让 git blame 全部失效

刚有检查器那天我们很兴奋，写了个脚本把整个 src 目录按新规范重排了一遍，一次提交就把存量文件几乎全部改了一遍行。爽了三周，然后开始查一个诡异回归，打开 blame，屏幕上每一行的作者都是那次格式化提交。谁写的、为什么这么写、当初关联哪个需求，全断了。老同事对代码的直觉本来靠”这块是谁的地盘”来路由，这个路由也断了。

后来的做法改成”改哪块格式化哪块”：只在正在修改的文件里做对齐，禁止纯格式化提交混进功能提交。确实要动整块时，单独提一次，提交信息里写明是排版调整，方便后续有人知道去 blame 的上一层找。教训是：规范落地的收益是长期的，提交历史也是长期的，别为了前者把后者烧掉。

文档说两空格，脚本没锁

最离谱的一段时间，wiki 上白纸黑字写两个空格缩进，但仓库里的 .jshintrc 没提交进版本控制，各自机器上有一份本地默认。新人配了四个空格，钩子照样放行，因为本地配置压根没这条。文档和脚本各说各话半年，谁也没发现。

修法很朴素：配置只有一份，就是仓库里那份，文档不再重复写具体的缩进数值，只写一句”以仓库配置文件为准”。规则和解释分离，规则归机器持有，文档只负责说为什么。

CRLF 引发整文件 diff

Windows 同事提交的文件是 CRLF，Mac 那边一编辑，编辑器按 LF 保存，于是一个只改了两行的文件在 diff 里显示全文重写，冲突时也几乎没有可解读性。这类变更还会顺着合并跑到别的分支上。

两端一起做：.gitattributes 里把文本文件声明成按 LF 入库，EditorConfig 的 end_of_line = lf 保证编辑器写出来的是 LF，钩子再兜一层检出 CRLF 就拒绝。三处都指同一个方向，才真正安静下来。

Tab 与空格混用

比 CRLF 隐蔽，因为它在编辑器里看起来完全正常。混用的文件在有人按 Tab 缩进那部分时，整段会跳位。根因往往是某个人从别处复制了一段带 Tab 的代码粘进空格缩进的文件。我们把 indent_style 明确写进配置，编辑器保存时统一转换，钩子对新增行做检测。另外发现一个细节：Markdown 里的两空格缩进不能被无脑转换，所以 EditorConfig 对 md 文件单独关掉了行尾清理。

评审时间全花在风格上

有阵子代码评审能吵四十分钟，吵的是花括号换不换行、单引号还是双引号。真正该问的问题一个没出来：这段逻辑有没有测试，异常分支怎么处理，接口超时了页面会是什么状态。

我们定了条纪律：凡是工具能报出来的问题，评审里一律不提，提了算评审人的问题——说明流程有漏。风格之争消失之后，评审时间没有减少，只是终于花在算法与测试覆盖上了。这也是把检查前移到钩子里的最大收益，它省的不是算力，是人的注意力。

文件名大小写只在服务器上炸

本地是 Windows 或 Mac，文件系统不区分大小写，utils/Date.js 和 utils/date.js 都能引用到，页面跑得好好的。部署到 Linux 测试机就 404，而且往往只在某条懒加载路径上炸，测试还不容易覆盖到。图片资源更麻烦，切图时叫 Banner@2x.png，引用写成 banner@2x.png，问题拖到线上才露头。

规则是：文件名一律小写加连字符，钩子和构建脚本里额外做一次”同一目录内忽略大小写后重名”的检测。这个检查器报不出来，是我们自己写的十几行脚本补的，属于典型的”规范落地不能只靠通用工具”。

注释里的指令和配置文件打架

有人习惯在文件头写 /* jshint -W030 */ 关掉某条规则，有人用 /* global _: false */ 声明全局依赖。这两类注释本身是好东西，但写多了就变成局部越权：文件里加一行注释就能让钩子和构建一起闭嘴，规则等于没有。而且同一个变量在一处用配置文件声明、另一处用注释声明，读者要在两个地方拼真相。

我们的约定是：配置文件持有全局规则，注释里的指令只允许用于确实无法规避的三方库场景，且必须紧跟一行说明原因。构建脚本里另有一条检查，统计全仓库的局部关闭注释数量，这个数一路上涨时就说明规则定得不合身，该改规则而不是继续加豁免。

规则的边界：哪些值得硬拦

不是所有规范都该做成阻断。判断标准是两条：违反后造成的代价是否由别人承担，以及规则本身是否有歧义。有歧义的、纯口味的，一律只做建议。

规则 强度 执行位置
未定义变量、可疑的全局赋值 阻断 pre-commit 与流水线
调试语句残留 阻断 pre-commit 与流水线
行尾符与缩进风格 阻断，可自动修 编辑器与 pre-commit
文件名大小写与重名 阻断 流水线检查脚本
单文件产物体积超阈值 阻断 流水线
未经审批的外链资源 阻断 流水线
可能的拼写错误标识符 警告 流水线
回调嵌套层数过深 警告 流水线
命名风格偏好 建议 仅评审提醒
注释密度与文档注释 建议 评审

这里要特别说一句外链资源。页面里直接引用别家域名的脚本或图片，除了协议与可用性问题，还会把首屏交给别人支配。我们把”新增外链域名”设成硬拦，必须走一次审批，这一条拦掉过好几起线上故障。

三件定了但不在本文展开的事

提交信息的格式、分支的命名、评审怎么走完一个流程，这三件我们也定了规矩，同样在钩子和流水线里有对应检查。但它们在工具之外牵扯更多协作习惯，值得各自单独一篇细说，这里就不展开了，避免把一篇文章写成两件事。

一次提交的拦截链路

把上面三层串起来，一次提交实际走的路是这样的。

flowchart TD
    A[执行 git commit] --> B{pre-commit 钩子}
    B -->|检查器报错| C[提交中断 退回修改]
    B -->|通过| D[写入本地仓库]
    D --> E[推送到远端]
    E --> F{流水线跑构建任务}
    F -->|红灯| G[阻断合并 通知提交人]
    F -->|绿灯| H[打包与体积检查]
    H -->|超阈值| G
    H -->|通过| I[部署到测试环境]
    C -.-> J[改完再提交]
    J -.-> A

注意图里有两个退回点。这是有意的：本地退回让改错的成本留在写代码的人身上，流水线退回保证本地退回被绕过之后仍然有东西接住。两层同时存在时，绝大多数问题在第一层就消掉了，第二层每天只报很少的错，这时候大家才会真的信任它。

小结

回头看，这件事的转折点不是装了哪个工具，而是我们把”规范”的定义换掉了：规范不再是那份文档，而是仓库里那份配置、那个钩子和那条必须绿的流水线。文档退化成解释，解释为什么这么定，具体数值由工具持有，两边才不会再各说各话。

几条经验值得抄走。第一，别一次性格式化存量代码，历史值钱。第二，配置进版本库，文档不重复数值。第三，钩子要快，慢的钩子等于没有钩子，因为人一定会去找跳过它的办法。第四，工具能报的问题禁止在评审里讨论，把人的注意力留给工具报不出来的东西。第五，接受通用检查器的空白，像大小写重名这种就得自己写几十行脚本补上。最后一句最实在：允许红灯合入一次，整套机制就开始失效，这一条守不住，前面都白做。
