Sass 工程化配置与目录结构

本文要解决的不是「Sass 怎么用」，而是「Sass 怎么摆」。如果你已经会写变量和 mixin，但目录越加越乱、改一个颜色要在编辑器里全局搜索三次，这篇应该有参考价值。读完你会得到一套能直接抄的目录骨架、几条抽象层的命名规矩，以及 node-sass 接入构建工具的最短配置。

从散文件到工程

我们团队早期的样式目录大概是这样：一个 common.scss、几个以页面命名的文件，再加一个谁都不敢动的 reset.scss。同一组变量在三四个文件里各有一份，新同事进来问的第一个问题永远是「这个文件该放哪」。这种状态里，Sass 只把嵌套语法借给了我们，工程能力一点没用上。

把样式当工程做，要回答三个问题：编译链路是什么、文件如何分层、抽出来的东西怎么命名和复用。下面逐条给做法。

编译链路：从 Ruby Sass 到 node-sass

为什么换

Ruby Sass 是 Sass 的原始实现，功能上完全够用。我们把链路换成 node-sass 3.x（也就是 LibSass 的 Node 绑定），动机有三个：一是不再需要在新同事的机器和构建机上装 Ruby 环境，Windows 下这一步尤其折腾；二是 CI 里本来就有 Node，加一个 npm 依赖比长期维护两套运行时便宜；三是 LibSass 是 C++ 实现，编译整个样式目录的速度在当时确实比 Ruby 快一截，watch 模式下的手感差别明显。Less 与 Stylus 也各有用法，但本文只谈怎么把 Sass 组织成工程，不做横向比较。

最常见的一类坑：原生扩展和 Node 版本对不上

node-sass 不是纯 JavaScript 包，它带一个按 Node 版本编译的二进制扩展。这带来的现象非常固定：本地跑得好好的，换到 CI 或者同事那台刚升级过 Node 的机器上，加载模块时直接抛错，大意是当前环境的绑定文件找不到。我们的应对不算巧妙但够用：把 Node 版本写进项目约定，切版本用 nvm，见到这类报错先重编译而不是改代码。

第二条命令跑不起来，基本就能确认问题出在二进制。再配上一份提交进仓库的 npm-shrinkwrap.json，至少能保证团队里装到同一个产物。这一条值得写进入职文档第一行，因为它每次 Node 大版本升级都要复发一次。

目录骨架：七层加一个入口

分层思路在社区里流传已久，我们按自己的项目裁剪成七层，根目录约定为 styles/：

各层职责说清楚：abstracts/ 是唯一不产出 CSS 的一层，只放变量、mixin、函数，被引入后只会在别处展开，自己一条规则也不输出；vendors/ 放第三方源码，比如 normalize.css 的 scss 版本，我们不改它，只做引入；base/ 放重置、全局排版和通用工具类，是整个项目的地基；components/ 放独立可复用的小块，一个按钮、一个卡片；layout/ 放页头、侧栏、页脚这类骨架；pages/ 放只属于某个地址的样式；themes/ 放成体系的覆盖配色。main.scss 只做一件事，按顺序写 @import。

判层的方法只有一句话：换到另一个页面还用不用得上。用得上就进 components，只有这一页用就进 pages。

partial 与下划线约定

文件名前加下划线，是 partial 的标记：编译器看到 _buttons.scss 就知道它不该被单独编译成一份 CSS，只会作为被引入的片段。所以整个目录里唯一不带下划线的 .scss 文件应该只有 main.scss 一个。下划线不影响引入写法，@import 'components/buttons' 能命中 _buttons.scss，团队里统一用这种不带下划线的路径，少一层心智负担。

引入顺序就是覆盖顺序

Sass 会把各文件按引入顺序拼成一棵样式树再输出，同名选择器谁靠后谁赢，所以 @import 的顺序直接决定最终产物里的层叠关系。抽象层必须最先：components/ 里一旦引用了变量，加载顺序反了就是未定义变量，编译当场失败。之后的顺序是 vendors、base、components、layout、pages，最后压轴 themes，正好符合通用在前、特殊在后、覆盖垫底的层叠直觉。

抽象层的三条规矩

变量必须带命名空间

Sass 的变量作用域相当宽，abstracts/ 全量引入之后，一个 $width 能把整个项目污染掉。我们的规矩是所有全局变量必须带前缀：颜色用 $c-，层级用 $z-，断点用 $bp-，间距用 $gap-。

前缀不是装饰。曾经有人加过一个 $primary: 16px 表示主间距，和谁都不撞名，但读代码的人一定以为是主色。命名空间同时解决撞名和望文生义两件事。

断点与栅格用 map 加循环生成

Sass 3.3 之后的 map、map-get、@each 在 node-sass 3.x 里完全可用，正好用来消灭复制粘贴。

输出是四条 .grid--xxx 规则。要加一档只改 map，不动循环。断点同理写进 map，再包一层 @mixin respond-to($key) 用 map-get 取值，让 768px 这个数字在全站只出现一次。

mixin 不要写成万能开关

一个 mixin 收五六个参数、内部套一串 @if 分支，短期省事，半年后没人敢调。我们的尺度是：一个 mixin 只做一件事，参数不超过两个，其余走变量。需要多种形态时，写成几个语义化的 mixin 互相调用，而不是给同一个 mixin 加开关。

placeholder、extend 与 mixin 的产物差异

这三者常被当成同一件事的三种写法，其实编译产物完全不同。@mixin 是复制，每次调用把正文展开一遍；%placeholder 配合 @extend 是合并，编译器把调用者的选择器追加进同一条规则的选择器列表。

声明少时看不出差别。一旦占位符里塞了几十条属性又被几十处引用，选择器列表会明显变长，压缩后的 CSS 体积反而占优，这是 @extend 唯一划算的场景。

真正麻烦的是组合爆炸。@extend 在带上下文的选择器里工作时会做交叉匹配，产物中出现你没写过的选择器。举个我们踩过的例子：一个占位符被 .nav a 引用过，同时页面里又有 .sidebar .card，编译后就可能冒出 .sidebar .card a 这类规则，把侧栏里所有链接的样式改掉。跨文件使用时尤其失控，因为被引用的那条规则挂在谁下面，写的人未必记得住。经验做法有两条：@extend 只用于 %placeholder，绝不去 extend 一个真实类名；一个占位符被引用的地方超过十来处，就回头看看它是不是该改成 mixin。

source map、Autoprefixer 与语法纪律

source map 怎么开

node-sass 3.x 自带 source map 选项，命令行传 --source-map 并给出输出路径：

用 API 就是 sourceMap: true。Sass 的 map 指回的是被拼接之前的各个 partial 源文件，浏览器开发者工具里点一下样式就能落到 _buttons.scss 的第几行，这是从散装时代过来的人最容易忽略的收益。顺带把 sourceComments 关掉，那种在 CSS 里留一行文件行号注释的老办法会让产物明显变大。

前缀不要自己手写。Autoprefixer 6.x 已经改用 browserslist 读目标清单，把清单写进 package.json，Grunt 和 gulp 两条链路读同一份：

清单只有一处，加不加前缀就变成配置问题而不是体力问题。当年手写前缀的典型翻车现场是弹性盒：旧规范、WebKit 中间稿和新规范的属性名互不相同，三代混在一起很难对齐，IE 10 那一代还额外需要 -ms-flex 一类的版本前缀。要明白 Autoprefixer 只补已知的版本前缀，它不会替你补一个不存在的特性，所以这类布局的兜底方案仍然要靠浮动加负边距写一份能活下来的默认样式。

两种后缀不要混用

.scss 是花括号语法，.sass 是缩进语法，编译器能分别处理，但一个项目里混着用一定出事：缩进文件靠空格表达层级，换个人来改就得先猜它用哪种语法，一旦缩进错位，整片规则静默挂错父级，比语法报错更难查。我们的规定是目录里只允许 .scss。

六个真实踩过的坑

抽象层内部相互引入

_mixins.scss 里为了用某个函数，顺手引了 _functions，而 _functions.scss 又回头引了 _mixins。Sass 的引入是文本级展开，循环引用要么让变量反复覆盖，要么直接报递归过深，而且报错位置常常指向一个无辜的语法行。规矩：abstracts/ 内部一律不互相引入，全部由 main.scss 按顺序装配。

同名变量后被覆盖

变量在 _variables.scss 定义了一次，某个页面文件里又图方便重新赋值，编译不报错，产物却是后一份的值。排查半天通常因为引入顺序变了。做法是全局变量只允许出现在一个文件里，页面级覆盖请用带命名空间的局部变量，写在规则块内部靠作用域生效。

全局变量改一处全站炸

把 $c-primary 改成市场部要的新蓝色，听起来只是一行改动，实际会连带按钮、链接、边框、占位符所有引用点。所以我们把语义变量和色值分开两层：先定义色板 $c-blue-5，再定义语义 $c-primary: $c-blue-5，换肤改语义层，色板保持稳定。

把 grid 当成可用手段

CSS Grid 这一年在规范上还在推进，除了 IE 的一套旧实现，主流浏览器还没落地。真要写多栏布局，浮动、负边距和表格式布局才是当期能上线的方案，别把未来的语法当现在的工具箱。

媒体查询的旧浏览器兜底

断点写得很整齐，但 IE8 完全不认 @media，所有分支会当成无效声明丢掉，页面塌成移动布局。这一层不在样式工程里解决，而是构建时在条件注释里塞一份默认样式或者引入 respond.js 这类脚本，把兜底归到 polyfill 注入里去管。

图片与字体资源的路径基准

这块只提一句工程约定：资源目录写在 abstracts/_variables.scss 里统一给一个 $img-path，components 层一律用相对它拼出来的地址。否则构建产物一旦从 build/css 挪到 dist/css/，全站背景图会一起报 404，而这种问题在本地预览里看不出来。

目录职责总览

目录 放什么 是否产出 CSS 谁可以引用它
abstracts 变量、函数、mixin 否 所有层
vendors 第三方样式源码 是 只被入口引用
base 重置、全局排版、工具类 是 components、layout、pages
components 按钮、卡片等独立小块 是 layout、pages、themes
layout 页头、侧栏、页脚骨架 是 pages、themes
pages 单页面专属样式 是 themes
themes 成体系的配色覆盖 是 不再被引用

引用方向只能从上往下。components 去引 pages、base 去引 components，都是把地基盖在屋顶上，早晚要出问题。

小结

样式工程化的收益不在语法，而在约定：链路统一到 node-sass 3.x 之后，环境问题和 Node 版本要一起管；目录切成七层加一个入口之后，新文件该放哪不再靠问人；抽象层有了命名空间、map 生成和 mixin 的尺寸限制之后，改名和换肤才有可操作性；placeholder 与 mixin 的产物差异、引入顺序和构建双路径，则决定了你会不会在上线当天发现某处样式莫名其妙地生效。这些约定第一天写完要多花半天，之后每一次改动都在还债和省钱之间站在省钱这边。
