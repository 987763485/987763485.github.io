jQuery 的 ajax 系列方法详解

这篇不逐个抄 $.ajax 的参数表，只顺着一次请求的链路问一句话：这么写快不快、稳不稳。文中以 jQuery 1.11.3 为准，ajax 这一层在 jQuery 2.1.3 里是同一份实现，结论通用；jQuery 3.x 才有的改动不在本文范围。标了「实测」的结论都在本机 Node 里加载真实的 jQuery 1.11.3、配本地假服务器与假传输层跑出来；浏览器与服务端的历史行为则标明是文档依据。

分层：可控的入口只有一个

jQuery 的请求 API 分三层。最底层是 $.ajax，别的写法最终都汇到它那里；中间是简写方法 $.get、$.post、$.getJSON、$.getScript 和元素上的 $.load；最上面是全局治理用的 $.ajaxSetup 与 $.ajaxPrefilter。

简写方法的问题不在功能，而在签名太短，短到没地方放 timeout、cache、contentType、error。$.get 与 $.post 能传的只有 url、data、回调和 dataType，接口一慢、开始返回脏数据，连插超时的地方都没有。$.load 把请求和渲染绑死，HTML 直接灌进 DOM，没有错误回调也没法在插入前处理，只适合原型和内部小工具。$.getScript 与 $.getJSON 的用法、时间戳破缓存和 JSONP 的坑，旧文《jQuery 的 getScript 与 getJSON》已经讲透，这里不重复。

结论：简写方法只适合一次性的简单请求——拖一段配置、点一下按钮取个时间戳。业务代码统一走 $.ajax，因为只有它能把超时、缓存、内容类型和错误处理一次说清。$.ajaxSetup 改的是全局默认值，风险单独说；$.ajaxPrefilter 克制得多，可以只按 dataType 拦一道，适合给全站加令牌头：

url 与 data：序列化方式先决定服务端能不能解析

$.ajax 默认 processData: true，对象形态的 data 会交给 $.param 序列化。jQuery 1.11.3 默认是「非 traditional」模式，数组会被写成带方括号的形式，这一点实测结果如下：

方括号在 URL 里必须转义，a[] 写成 a%5B%5D，参数一多长度膨胀得很快。更要紧的是服务端怎么解析：a=1&a=2 这种重复键 PHP 只留最后一个，a[]=1&a[]=2 才收成数组；而 Rails、Django 认的正是方括号，把 traditional: true 打开反而收不到。另一个差别必须记住：traditional 遇到嵌套对象会直接写成字符串 [object Object]（上面第四行实测到了），所以它只适合扁平键值加数组的老接口，别当通用开关。null 与 undefined 都会序列化成空值，实测 $.param({ a: null, b: undefined, c: 0, d: false }) 得到 a=&b=&c=0&d=false——键不会消失，而服务端收到的空串和 0、false 是三回事。

GET 时序列化完的 data 是拼到 URL 后面的（源码里只要 s.hasContent 为假就把 s.data 追加到 s.url），URL 长度于是成了硬约束。IE 的上限按 MSDN 记载约 2083 字符、路径部分不超过 2048；服务端侧，Apache 2.2 与 2.4 的 LimitRequestLine 默认 8190 字节，ASP.NET 的 httpRuntime 里 maxQueryString 默认 2048。这些是当年的文档数字，本机测不出来，但结论够硬：几十个 ID、一段富文本这类长参数必须走 POST 放请求体。我用 6296 字符的 GET URL 实测过，jQuery 发得出、Node 服务器也收得下——限制不在前端代码里，而在链路某一环的默认配置里，一旦踩到就是 414 或者静默失败。

cache 与 ifModified：破缓存是把双刃剑

cache: false 只做一件事：给 URL 追加一个 _ 参数，让它每次都变成新地址。源码里只对没有请求体的方法生效，追加的值是自增计数器（var nonce = jQuery.now() 起步），实测两次请求分别是 /echo?a=1&_=1792267185538 与 /echo?_=1792267185539。还有个默认值容易忽略：dataType 为 script 或 jsonp 时 jQuery 自己就把 cache 关了（源码 script 预过滤里 if ( s.cache === undefined ) { s.cache = false; }），实测同域 dataType: 'script' 的请求到服务器时确实带着 _=。

代价在于这个 _ 把浏览器强缓存和 CDN 命中一起打穿了：URL 每次都不同，缓存全是未命中，静态化的字典接口、图片列表统统回源。旧文《HTTP 缓存机制与缓存策略》复盘过一次 $.ajaxSetup({ cache: false }) 合进主干、源站带宽涨到六倍的事故，那份账不重算。结论是全站关缓存永远错，真要关就在单个请求上关。

正路是让接口本来就可缓存，再打开 ifModified: true。jQuery 会按 URL 记住上次的 Last-Modified 与 ETag，下次带上 If-Modified-Since、If-None-Match，服务器回 304 时它把这算作成功，textStatus 给成 notmodified。实测连续两次 ifModified: true 的请求，第一次 success 带数据，第二次 textStatus 正是 notmodified、数据为 undefined。304 不免费：它省的是响应体，一次完整的往返一分不少。在当年 300 毫秒以上往返的无线链路上，协商只适合内容确实很少变、而客户端必须知道最新版本的资源；能靠版本号定版的，宁可用强缓存加指纹文件名。

timeout：管得到等响应，管不到建连接

timeout 的实现很朴素：一个 setTimeout 到点调用 jqXHR.abort("timeout")。这一行还藏着另一个事实——它写在 if ( s.async && s.timeout > 0 ) 里，同步请求的 timeout 是被整个忽略的。实测一个 500 毫秒才响的接口配 timeout: 150，152 毫秒进 error，textStatus 是 timeout，xhr.status 是 0。

边界要说清：计时器在 JavaScript 层面，从调用 send 之前起跑；一旦浏览器卡在 DNS 解析或 TCP 握手阶段，脚本层只能喊一声 abort，而老浏览器对「连接尚未建立时 abort」的处理并不一致，套了代理的链路上请求可能已经在路上。所以 timeout 是止损手段，不是精确的耗时预算。更要紧的是超时之后要不要重试：默认什么都不做，用户看到的就是一次失败；自动重试又得把幂等当前提——查询类 GET 可以重试，POST 提交重试可能就是重复下单。本文的规则是只对 GET 重试一次，POST 交给按钮禁用加服务端幂等令牌，代码在第 9 节。

async、global、processData 与 contentType

async: false 会把主线程停住直到响应回来：输入框不能打字、动画停帧，IE 在慢接口上还会弹「停止脚本」的提示。它是历史遗留，本文只给一个结论——新代码里不要出现这个参数。顺带一句，我在本机做机器验证时用同步请求把进程直接卡死了：客户端和假服务器在同一个事件循环里，同步 XHR 一挂，服务端的回调永远排不上队。

global: false 让这次请求不参与全局事件（第 11 节展开），埋点、心跳、轮询这类高频请求都该关掉它，既省掉事件派发，也避免它们把全局 loading 条搅乱。

dataType、accepts 与 converters：解析这一步也要钱

dataType 同时决定两件事：发给服务器的 Accept 头，和拿到文本之后怎么转。dataType: 'json' 时源码给的 Accept 是 application/json, text/javascript, */*; q=0.01，而 accepts 与 converters 都是 $.ajaxSettings 上的普通对象，可按项目改。转换链最终交给原生 JSON.parse，解析细节、脏数据分支与大 JSON 的耗时见旧文《JSON.parse 与 JSON.stringify 的细节》。

对稳定性影响最大的是没写 dataType。jQuery 会看响应头的 Content-Type 猜类型，猜不出来就当文本。实测服务器把 {"a":1} 用 Content-Type: text/plain 发回来、请求里没写 dataType，回调拿到的是字符串而不是对象，所有 data.list 都是 undefined。所以要么服务端老实标 application/json，要么前端显式写 dataType: 'json'，两头至少一头明确。反过来，接口挂了、网关返回一个 HTML 错误页而前端写着 dataType: 'json'，实测进的是 error，textStatus 是 parsererror，errorThrown.message 形如 Unexpected token '<', "<html><bod"... is not valid JSON。这条报错比 500 难懂，所以 parsererror 要单独上报，别和网络错误混在一个桶里。

script 与 jsonp 走 <script> 注入而不是 XHR，代价是没有状态码、失败只能靠超时兜底，细节见旧文《jQuery 的 getScript 与 getJSON》。这里只补两个参数：jsonp 是回调参数名，默认就是 callback（源码 $.ajaxSetup({ jsonp: "callback" })），服务端约定叫 cb 时改它一处即可；jsonpCallback 用来固定回调函数名，默认 jQuery 生成带随机后缀的名字。固定名字换来的是 URL 稳定、CDN 能缓存，代价是同页并发请求的同名回调会互相踩，只有确定这个接口一次只请求一次时才固定它。

跨域的两个参数：xhrFields 与 beforeSend

带 Cookie 跨域靠 xhrFields: { withCredentials: true }。jQuery 只是把这些键原样赋到 XHR 实例上（源码 for ( i in options.xhrFields ) { xhr[ i ] = ... }），能不能带取决于浏览器。当时的支持面必须说清：Firefox 从 3.5 起、Chrome 与 Safari 都支持 withCredentials，IE 9 走的是 XDomainRequest，它压根不支持凭据，IE 10 才回到标准 CORS。jQuery 自己也是这么判的：support.cors 取自 "withCredentials" in xhr，不满足就不接受跨域的 XHR 传输。所以「跨域带 Cookie」在 2015 年还不是能无条件写的参数，兜底仍是同域反向代理与 JSONP，选型见旧文《AJAX 与跨域请求实践》。

beforeSend 能拿到 jqXHR 与最终配置，是加自定义头最后的口子：xhr.setRequestHeader('X-Trace-Id', id)。代价是同这些头在跨域请求上会把浏览器推到 OPTIONS 预检，多一次完整往返，弱网下用户感觉得到。jQuery 在这里的处理值得学：同域它会自动加 X-Requested-With: XMLHttpRequest（实测假服务器确实收到），跨域则刻意不加，源码注释写得很直白，就是为了不惹预检。最后一句留给 mimeType：它走 xhr.overrideMimeType，当年只有 Firefox 实现，想用它纠正服务端乱发的 Content-Type 是靠不住的，得在源头改响应头。

并发上限与请求数：真正的瓶颈在这儿

同一域名下的并发连接数是浏览器写死的。当时的通行数字：IE 6 与 7 每主机 2 条，IE 8 起提到 6 条，Chrome 40 与 Firefox 35 都是 6 条，更早的 Safari 是 4 条。这些来自各家文档与当年压测的经验值，本机复现不了。它意味着一件很具体的事：一个页面发十几个 AJAX，第 7 个开始就排队，而排队的等待和一条慢接口的耗时一样贵。Firefox 的 network.http.max-persistent-connections-per-server、IE 的 MaxConnectionsPerServer 是浏览器配置，和 jQuery 无关，别指望在 $.ajaxSetup 里配出来。

对策按收益排：

  • 合并请求。用户、权限、配置、未读数、广告位这五个小接口在后端或网关层聚合成一个，一次往返拿全；聚合层只要一个负责拼装的 BFF 节点，收益直接落在连接数上。
  • 结果加内存缓存与 TTL。同一份数据在页面存活期内只回源一次，还能把并发请求收敛成一个，代码见下一节。
  • 轮询别用固定 setInterval。请求慢于间隔就会堆积：我用假的 2500 毫秒响应配 1000 毫秒固定间隔实测，8 秒内发出 8 次、峰值 3 个在途；改成这次回来之后再排下一轮，同样 8 秒只发 3 次、峰值稳定在 1 个。
  • 分域并行只在确实排起队的页面做。多开一个域多一次 DNS 解析（可配 dns-prefetch 提前解），老 IE 上还能把 2 条连接变 4 条；但域多了连接池和 Cookie 头都在变贵，两到四个是收手点。

一份封装：内存缓存、TTL、并发去重、超时重试一次

下面这段是本文的产出，纯 ES5，只用回调和 setTimeout。它把前面几条调优结论压进一个入口：命中缓存不发请求、同键并发只发一次、超时只重试一次且只重试幂等的 GET、失败统一交给一个 error。

用假的传输层跑了一遍，实测结果：首次请求走一次网络、第二次同键请求命中缓存（textStatus 给成 cache，网络次数仍是 1）；三个并发同键请求只发一次网络但三个回调都拿到数据；第一次超时第二次成功时网络次数为 2 且成功回调只走一次；两次都超时时网络次数停在 2、错误回调一次、不会无限重试；parsererror 与 POST 的 error 都不重试，网络次数各为 1；TTL 30 毫秒、等待 80 毫秒后再请求，网络次数变回 2，clear() 之后缓存清空。

错误处理与重复提交

error 的三个参数是 (xhr, textStatus, errorThrown)，textStatus 是分流的关键：timeout 是超时（xhr.status 为 0）、error 是网络或 HTTP 层的失败、abort 是被取消（实测手动 abort() 之后 fail 的状态就是 abort，always 仍会执行）、parsererror 是没解析成、notmodified 是协商命中。parsererror 的成因无非三类：网关把 500 渲染成 HTML 错误页、响应头没给 Content-Type、返回体前面带了 BOM。返回值上还能链式挂 done、fail、always，它们的语义与坑在旧文《jQuery 的 Deferred 与 Promise 模式》里已经讲透，这里只把它们当回调使用。

分层要提前定：HTTP 状态码留给传输与服务端错误，业务失败留给响应体里的码。最怕的是「业务失败也回 200」，那样全局的 ajaxError 一条都不会报，线上只看到一片成功。可行的约定是：4xx 与 5xx 交给 xhr.status，成功响应里再判 data.code，两处都过才算成功；上报时把 status、textStatus、URL 和 code 一起带走。兜底放在全局事件上，ajaxError 抓失败、ajaxComplete 记总次数：

进度、加载态与全局事件

下载进度挂 xhr.onprogress，上传进度挂 xhr.upload.onprogress。当年的现实是：onprogress 只有 Firefox 实现较早，IE 全系不支持，XDomainRequest 连事件名都和标准 XHR 不同，上传进度在多数浏览器就是拿不到。所以大文件要么分片要么做假进度；分片不只报得出进度，还把一次长请求切成几个短请求，绕开排队与超时：

file.slice、FormData 这类 XHR Level 2 的能力当年只有 Chrome 与 Firefox 可用，IE 上要退回 Flash 或者干脆不做，这段代码的定位是支持就用、不支持就退回假进度。渲染上，success 回调里不要往 DOM 一条条追加，先在 DocumentFragment 里拼好再插一次，见旧文《DOM 增删改查与文档碎片 DocumentFragment》与《DOM 操作性能：批量插入与重排优化》。

六个全局事件 ajaxStart、ajaxSend、ajaxSuccess、ajaxError、ajaxComplete、ajaxStop 都由 jQuery 触发在 document 上，直接 $(document).on(...) 就能接。两个特性必须知道。第一，ajaxStart 与 ajaxStop 只在在途请求数 0 变 1、1 变 0 时触发，并发再多也只响一次，驱动顶部进度条正好；实测三个请求并发时是两次 send、三次 success 与 complete、一次 stop。第二，global: false 的请求被整个跳过，实测回调照常跑而全局事件一条没触发；还有个顺序细节，ajaxStop 比单请求的 complete 更早，用它收尾进度条时别假设业务回调都跑完了。

埋点用 global: false 是对的，但要留个心眼：统计口径若挂在 ajaxStart 上，这类请求就进不了统计，「明明发了请求却没人算它」的 bug 多半从这儿来。

收口 checklist

  • URL 长度：参数会不会把 GET 的 URL 顶过两千字符？超了改 POST。
  • 序列化：数组要不要 traditional、嵌套对象有没有被写成 [object Object]，和服务端的解析方式核对过没有。
  • 可缓存性：这个接口能不能被浏览器与 CDN 缓存？有没有在某个地方偷偷设过 $.ajaxSetup({ cache: false })？
  • 合并与去重：同一屏是不是发了五个能合成一个的请求？同一份数据有没有 TTL 缓存和并发去重？
  • 超时与兜底：timeout 设了没有？超时后是重试还是报错？POST 的重试和重复提交怎么防？
  • 全局事件：高频与埋点请求是不是关掉了 global？加载态有没有被它们搅乱？
  • 内容类型：POST JSON 是不是同时做了 JSON.stringify 和 contentType: 'application/json'？dataType 与响应头的 Content-Type 至少有一头是明确的？
  • 错误分层：parsererror、timeout、abort 有没有分开统计？业务码为失败时也走了 ajaxError 上报？
