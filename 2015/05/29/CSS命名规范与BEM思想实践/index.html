CSS 命名规范与 BEM 思想实践

本文属于《HTML 与 CSS》第 24/62 篇
上一篇系列目录下一篇

CSS 没有作用域、没有模块系统、也没有声明依赖的语法，但一个中型项目的样式表动辄上万行、十几个人同时改——这恰好是大型代码库的处境。所以本文不讲 BEM 的语法（三行就写完），而把样式表当成需要架构的库来讨论：命名规范承担模块边界与依赖声明两个职责，@import 顺序承担依赖方向，BEM 是这套体系里成本最低的一种伪作用域实现。特异度三元组怎么算、!important 落在哪一档、同分为何只能由顺序决胜，我在《CSS 层叠、优先级与特异度计算实战》里逐条推导过，本文不重述。

三年之后的样式表：病灶不在写得丑

打开一个跑了三年的项目的 CSS，画面几乎都一样：同一条规则存在好几份，后写那份是上一个开发改不动时补的；改后台工单列表的按钮颜色，前台活动页的导航跟着变了，因为两处都叫 .btn，各自被容器框进了重叠的命中范围；没人敢删行；样式表体积只增不减。

这四个症状来自同一个根因：选择器把 DOM 结构当成了依赖。.sidebar ul li a span 的真实含义是”我依赖侧栏里存在一条从容器到 span 的完整路径”，而这个依赖没写在任何地方——不在文档里、也不在注释里。改版时把 <ul> 换成 <ol>、把列表项拆成两层，或者只给链接文字加一层包裹，样式就断了，而断掉的那行代码一个字都没改过。

特异度失控与这个根因是互相喂养的。路径式选择器命中范围太宽，改样式的人怕误伤，本能反应是把自己那条写得更深——多套两层容器，命中范围收窄的同时特异度也变高了；下一个人想覆盖，只能更深或者补 !important。于是结构层级被当成了权重货币：DOM 层级既承担语义又承担优先级，谁都动不起。反过来，当所有规则都是单层类名、特异度恒等于 (0,1,0)，谁也无法靠写得深压制别人，冲突只剩顺序这一个维度可谈。

而”没人敢删行”是同一件事的另一面：删除的唯一依据是证明无人依赖，路径式选择器依赖的却是一整棵 DOM 子树，静态扫不出来。这条留到最后一节。

分层：把样式表拆成有向依赖

架构的第一步是分层，而分层的本质是规定依赖方向。五层，从最稳定到最易变：

flowchart TD
  A[基础层 变量与排版] --> B[布局层 栅格容器]
  B --> C[组件层 一个 block 一个文件]
  C --> D[皮肤主题层 modifier]
  D --> E[页面补丁层 债务 需限量]

这份引入顺序本身就是架构决策，理由两层。一是老问题：同特异的规则由先后决胜，所以层叠顺序就是依赖方向——上层可以覆盖下层，下层永远不许引用上层。有人把 themes 挪到 components 之前，整套覆盖关系当场失效，表现是”一小块颜色莫名回到默认值”，排查极难受。二是编译期依赖：_variables.scss 必须在用到它的文件之前导入，Sass 的变量作用域是词法的，这条比层叠顺序更硬。

页面补丁层要单独说。它是不诚实的：补丁必然要写成带容器类的选择器才生效，等于把结构依赖重新请回来；可删掉这一层并不会让需求消失，只会让补丁散进组件文件，从此没人知道哪些是特例。所以口径是给它一个合法位置，然后限量：文件头写清覆盖哪条规则、为什么不能改组件本身，条数由构建脚本打印，涨了要在评审解释。

BEM 的三个角色：包、私有字段、显式契约

block 是包，也是命名空间。.card 声明了”这个组件对外只承诺 .card 这一个可被外部选中的名字”，其余都是实现细节——这一句就是模块边界。

element 是私有字段。.card__title 里的 __ 不是装饰，它是一段写给同事看的注释：这块归 card 私有，外部不要选中它。要改标题字号就去组件文件里改，别在页面样式里另选一条 .card__title，因为它随时可能被重构掉。也因为选择器里不含结构信息，移动 DOM、加一层 wrapper、把 <h3> 换成 <div>，样式都不会断：耦合范围写进了名字里，而选择器不再声明依赖。

modifier 是显式契约。.card--feature、.nav__link--active 把”这个组件支持哪些变体”变成一份可枚举、可搜索、可 review 的清单；对比”给 .card 外面套一层皮肤容器、靠后代继承颜色”，后者的变体是隐式的，只有知道那层容器存在的人才知道有这一档。

三个角色共同保证一件事：绝大多数选择器只有一个类，特异度恒为 (0,1,0)，覆盖只能靠层叠顺序，不能靠拼权重。

状态、行为与工具类的前缀约定

is-* 与 has-* 表示状态。is-loading、is-active、has-error，一眼能看出这是运行时可切换的状态而不是内容类型。只有一条要强调：状态类挂在被着色的那个元素身上，不要挂在兄弟或祖先上，否则会出现”我要覆盖它，可它的类在别的节点上”的僵局。

js-* 表示”这个类被 JavaScript 依赖，CSS 不许动它”。它是纯锚点，只出现在 HTML 里，样式表里搜不到。这一条把”改类名导致脚本报错”的风险从口头约定变成 grep 一次就能验证的事实。

u-* 是工具类，必须白名单管理：它是原子化的表现层依赖，天生反组件化。只收录与颜色、字号无关的几何与显隐声明（u-mt、u-hidden、u-text-right），清单写死在 _utilities.scss 一个文件里，新增走评审。允许随手加，下场一定是 .left20、.red-text 泛滥，同一块区域被三个工具类和一条组件规则三方争抢。

状态类与 BEM 的配合有一个例外：

.card.is-active 是两个类的组合，(0,2,0)，这是整套规范里唯一允许的双类串联。原因是 is-active 单独写会命中页面上任何带这个类的元素——表格行、标签页、卡片都可能叫 is-active，一条裸规则会把卡片的改动广播到全站；带上 block 类名，是给这个全局状态补上最小的上下文限定。全用 modifier（.card--active）也能避开这个例外，代价是多维状态组合爆炸。我的取舍：组件自身的固定变体用 --mod，由 JS 切换的运行时状态用 is-* 加 block 限定。

流派对照与选型

四种写法的差别，用六个维度排一张表。

方案 耦合方式 可扩展性 上手成本 HTML 体积 对 JS 协作的约定 删样式的可判定性
传统（id 起点 + 深层嵌套） 依赖 DOM 路径 差，覆盖靠加深 零 最小 无约定，类名两用 不可判定
OOCSS 依赖”对象”类（.media、.span4） 中，对象之间互相干扰 低 中 无 差，得全局搜对象
SMACSS 依赖文件分类加模块名 良好，state 与 theme 有归宿 低 小 弱，靠 state 档约定 中，按目录缩小范围
BEM 只依赖类名本身 好，组件天然隔离 中高 最大 强，js- 前缀显式声明 好，类名与文件一一对应

三家的关注点本来就不同：OOCSS 讲结构与皮肤分离、把复用单位做成”对象”类；SMACSS 管文件怎么分类（base、layout、module、state、theme 五档）与 @media 怎么拆到各层；BEM 只解决一件事——用名字表达作用域。所以它们不冲突。我们的最终姿势是用 SMACSS 的五分类决定文件放哪、按什么顺序导入，用 BEM 决定组件内部的选择器怎么写，传统写法只锁在 pages/ 那一层。

要不要上 BEM，判据是组件数量与协作人数。两三个人维护、样式表三四百行的落地页，上 BEM 纯属自我折磨——类名变长的成本全压在自己身上，收益却要多人共改一份 CSS 才显现，那种场景用 SMACSS 分类加朴素命名就够。反过来，组件超过几十个、两个团队共用一套样式表时，block 作为命名空间的价值压过一切：他们同时改 .card 与 .order-table 永远撞不了车，因为类名前缀本身就是彼此的边界。

落地踩坑复盘

坑一，类名冗长这笔账要自己量。 我造了两个千行 DOM 的样例，用 Node 的 zlib 各压一遍：只把列表行根节点的类名换成 BEM（每行多 21 字节），raw 从 54,999 涨到 75,999 字节，gzip -9 之后从 2,650 涨到 2,804 字节；另一份样例把一行里三个类名全换掉，raw 多 47,000 字节，gzip 只差 179 字节。网络账基本不成立，重复串被 deflate 吃掉了；但可读性代价是真实的：<li class="order-table__row js-sortable u-mt"> 在模板里换行了。缓解只有两条：block 名取短；只给被样式选中的元素配 element 类。

坑二，element 的嵌套必须限死一层。 出现 .card__body__title 的那一刻，命名就退化成 DOM 路径的另一种写法，只是把空格换成下划线。规约里写死一个类名最多一个 __、最多一个 --，这条能被正则校验。

坑三，后代选择器与 element 的边界。 .card__title em 能不能写？组件内部的排版本来就得给 em、strong、li 设样式，每个都补一个 element 类既啰嗦又没意义，所以规则是允许 block 内部有限耦合：一个选择器最多一个类，后面最多再挂一层类型选择器，且只限排版标签（em、strong、a、li）。跨 block 一律禁止——.card .nav__link 要被评审拦下，它把两个组件的依赖连起来了，而 BEM 给 block 的承诺恰恰是”组件之间不写选择器”。

坑四，Sass 的 & 拼接有排查代价。

省事之外有三个代价。源码里看不见 card__title 这个字面串存在过，全局搜类名只能搜到 &__title，IDE 的跳转与补全失效；下一节那个检查脚本必须跑在编译后的 CSS 上而不是 sass/ 源文件，否则抽出的类名是残缺的；新人得在脑内做一次字符串拼接才知道最终类名，放错层级时产出的类名谁也没预期到。处理办法是一个 block 只在该文件顶层出现一次、嵌套不超过一层。另外别用 @extend 表达复用：%placeholder 被 extend 十几次后，产物里会挂出一条几十个选择器的巨型规则，把要消除的耦合换个形式请回来。

坑五，半 BEM 化是最糟的状态。 一半人写 card__title、一半人写 .detail .box ul li span，特异度就分裂成两个档位：路径派随手能写出 (0,4,2)，类名派再单层也压不过，只能补 !important。此时”全部同分、只由顺序决胜”这条核心机制失效，整套体系比不用还差，因为规范文档还挂着、大家还以为它有效。所以推进节奏只有两种：一次性迁完一个目录（components/ 整体切过去、pages/ 保留旧写法），要么先不动。

可检测性：能被机器校验的规范才会被遵守

上面的约定只要依赖自觉，三年内一定烂掉；只要能被脚本扫出来，就能进构建。我用 Node 0.10 写了个百行以内的骨架，做三件事：从 HTML 抽用过的类名、从编译后的 CSS 抽选择器里的类名、取两个方向的差集。

团队规约清单

可以直接贴进 wiki 的版本，共十条。

  1. 类名格式 block、block__element、block--modifier、block__element--modifier；一个类名最多一个 __、最多一个 --。
  2. block 名与文件名一致，components/_card.scss 里只允许 .card 作为顶层选择器。
  3. 一个选择器最多一个类；block 内部有限耦合是唯一例外——后面最多挂一层类型选择器，仅限 em、strong、a、li，跨 block（.card .nav__link）一律拒绝。
  4. 状态类用 is-* / has-* 且挂在被着色的元素本身；与 block 类串联（.card.is-active）是唯一允许的双类组合；组件固定变体用 --modifier，运行时状态用 is-*，两者不混用。
  5. js-* 只做行为锚点，样式表里出现 js- 开头的类即视为违规。
  6. 工具类只允许 u- 前缀、只写在 _utilities.scss、只允许几何与显隐声明，新增走评审。
  7. !important 只允许两处：带对方版本号注释的第三方定点覆盖、白名单内的常驻工具类。
  8. @import 顺序固定为 base → layout → components → themes → pages，改动这一顺序的提交必须单独说明理由。
  9. pages/ 是债务层：每个补丁文件头部写清覆盖哪条规则、为什么不能改组件本身，条数由构建脚本打印。
  10. 类名一致性与结构耦合两条检查进 CI，脚本不通过不算完成。

小结

值得花时间的不是 BEM 的语法，而是这一件事：CSS 的不可维护来自选择器把 DOM 结构变成隐式依赖，特异度失控只是这层依赖被当成权重货币之后的并发症。命名规范的作用，是把模块边界（block）、私有实现（element）、对外契约（modifier）与依赖方向（@import 层序）写进可读、可搜、可校验的地方。规范能不能落地，取决于它能不能被机器扫出来。
