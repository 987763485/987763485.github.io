JavaScript 内存泄漏的常见场景

一个页面挂了一下午，内存从 60 MB 涨到 400 MB，最后标签页自己崩掉。这种事故我们碰过好几回，每一次都先怀疑事件绑定，因为事件处理器闭包造成的那条可达链旧文《DOM 事件移除与内存泄漏》已经推导得很干净，照着查通常就有结果。但这几年真正难查的泄漏，反而大多不在事件上：一个漏写的 var、一个忘了关的定时器、一份只进不出的缓存、一行没删的 console.log。这些场景的共同点是代码看起来“没毛病”，而且都能通过代码审查，只有跑起来才暴露。本文按事件之外的八个泄漏场景复盘，最后收在定位手段和一份团队可执行的 checklist 上，每个场景都写清现象、当时怎么定位、根因在哪、修完之后学到什么。所有代码停在 ES5，因为眼下 ES6 规范还没定稿。文中几个内存数字是拿 Node 的 --expose-gc 加 process.memoryUsage().heapUsed 跑最小模型量出来的，V8 的回收时机和浏览器并不一致，它们只能作方向性佐证，不能当浏览器指标读；凡是浏览器和 IE 那边的结论，我会标明是历史事实还是文档依据。

意外产生的全局变量

现象：页面越挂越大，而且刷新前无从下手；同一段业务代码，跑一小时涨几十 MB。

定位：先把全局污染的量测出来。旧文《JavaScript 命名空间与模块化演进》里那份基线快照体检脚本能列出新增的全局名字，这里不重复整段实现；日常我只需要一个数：

我们的案例里，每展开一次高级筛选，全局计数加一，顺着新增的名字回代码找，找到的是一个陌生的 b。

根因有三条，全都是语法层面的漏：

var 只认函数作用域；未声明的赋值等价于给全局对象挂属性；链式赋值里只有最左边那个受 var 保护。挂在 window 上的东西活到页面关闭为止，它引用的大对象自然一个都回收不掉。Node 上最小模型能复现这套语义：非严格模式下漏写的变量确实出现在全局对象上，this.resultSet 落到了全局；严格模式下前者抛 ReferenceError，后者抛 TypeError；var x = y = 100 让全局的 y 变成 100。

修复与复盘：函数顶部统一写 'use strict'，构建期用 JSHint 兜住——把 undef 打开，未声明的赋值直接报错；unused、latedef 一起开；确实需要的宿主名字进 predef 白名单。implied 那条思路（JSLint 的 implied globals，JSHint 里由 undef 承担）本质是同一件事：任何隐式全局都当错误处理，不留“看着无害”的余地。团队约定之后，这类泄漏归零，代价是第一次加严格模式时一次性炸出九处漏写。

被遗忘的定时器与回调

现象：单页里切走一个带轮询的组件，请求还在按周期发，堆内存台阶式上涨，每次“销毁”都留下一截。

定位：给 setInterval 打个调试补丁，把创建的 id 和调用点登记下来，操作完对比登记表有没有对应清理。这类补丁只在调试期挂，绝不上线。找到嫌疑之后再用堆快照确认闭包还在。

根因：定时器 id 只是个数字，回调函数才是引用主体。回调闭包持有组件私有状态，组件“销毁”往往只是移除了 DOM 和断了外部引用，那个数字没人接，clearInterval 一次都没执行，于是整份状态被定时器稳稳拖住。Node 模型很直观：八个组件，每个内部一份三万行的数据加一个周期任务，把组件引用全部丢弃但没有 clearInterval，堆上稳定停在约 34 MB；补上统一清理，回落到约 7 MB。

修复与复盘：clearInterval 必须与创建成对写在 destroy 里，靠人记不住，就把登记做成机制：

顺带一个语法账：想在工具里靠 arguments.callee 自引用是走不通的，严格模式下取它会抛 TypeError，Node 实测确认。需要自引用就用具名函数表达式（上面那个 stop 就是同样的思路），可读性也更好。

闭包“过度捕获”

先说明边界：事件处理器闭包造成的泄漏属于旧文《DOM 事件移除与内存泄漏》，这里不重讲，只谈同一机制在非事件场合的普遍形态。

现象：堆快照里某个数组的 Retained Size 大得离谱，展开引用链，末端是一个只有几行的回调。

定位：看回调到底引用了外层作用域里的哪些名字。真正拖住内存的从来不是回调本身，是它顺手抓走的那些大对象。

根因：局部变量整份进了闭包。

Node 模型量的差：八个回调，每个捕获一份三万行的对象，堆上约 33 MB；只把需要的字段提前抽出来，同样的八个回调约 3 MB。

修复与复盘：传值而不是传对象，parseInt 那种“提前把字符串换成数字”的写法搬到闭包上就是同一个道理。

写回调时问自己一句：这个函数未来只需要外层的什么？答案越具体，捕获越少。大的列表数据尽量在函数入口就抽成 id 数组，别让原对象活到回调执行那一刻。

无上限的缓存字典

现象：给搜索建议加了 memoize，一周后同一页面内存翻几倍；缓存对象看起来人畜无害。

定位：把缓存容量暴露出来，Object.keys(cache).length 定时打印，或者直接看堆快照里字符串键的数量随操作次数线性上涨。缓存不主动看是看不见的。

根因：只进不出。旧文《JavaScript 惰性求值与缓存优化》讲透了 memoize 的原理与失效策略，这里不重复推导，只补一条当时被我们忽略的：容量。Node 上两份对比很清楚——不带上限地塞三千条，堆一路涨到约 347 MB，把字典引用置空后立刻回落到约 3 MB，说明回收本身没问题，问题是那条引用一直在；同样的负载换成上限 50 的 LRU，插入一千两百条之后常驻仍是 50 条、约 15 MB，完全不随操作次数增长。

修复与复盘：

delete 那一句是重点：只把 key 从数组里挪走而留着 store 上的属性，值照样不可回收。复盘结论一句话：缓存必须有失效策略，而失效策略包含容量。想不出上限该设多少，就说明它不该做缓存。

console.log 也是泄漏源

现象：只有开发者工具开着时内存才涨，关掉就正常。这个坑 2015 年真实存在，属于控制台侧行为，不是 JS 语义。

定位：把 console.log 注释掉再压一遍长跑，增长曲线明显变平，嫌疑就锁定了。

根因：控制台为了让你事后展开查看，会保留打印过的对象引用。你 log 了一个几百 KB 的响应体，它就替你把这几百 KB 留到页面关闭。我在 Node 上复现不出来：打印整份大数组后置空引用，堆照样回落到约 4 MB。这条要标清楚依据：它是浏览器开发者工具的既有行为，官方问题跟踪里讨论过多次，不是我实测出来的浏览器数字。另一半是 IE 的兼容坑（历史事实）：IE 8/9 在开发者工具没打开时 console 对象根本不存在，调一句 console.log 就抛错，把整段业务打断。

修复与复盘：统一走一层安全包装，只补缺失的方法，不覆盖已有的（IE 8 下 console 一旦存在，它的方法覆盖不掉，这是当年的老规矩）：

打印时优先打字段而不是打整个对象：console.log(res.total) 比 console.log(res) 温柔得多。上线产物里不该留着 console，构建期用 uglify 的 drop_console 去干净。至于“排查时靠 console、排查完就删”，这条纪律比任何工具都管用。

DOM 引用泄漏

现象：反复打开关闭同一个浮层，堆快照里游离节点（Detached DOM tree）越攒越多，每个还拖着一整棵子树。

定位：DevTools 堆快照的类型过滤框输入 Detached，数量随操作次数上涨就是它。

根因：节点从文档树上摘掉，不等于没人引用它。JS 里存了一份，它和子树就都还在。innerHTML = '' 只清子节点，清不掉外部那份引用。库这边的数据缓存也是同一个道理：jQuery 把 .data() 存在内部字典里，节点摘掉后账还在。

修复与复盘：顺序决定成败，先清引用与数据，再摘节点：

.remove() 与 .empty() 会连带走 jQuery 内部的清理，.detach() 是刻意保留数据的，手动 removeChild 则什么都不清，这三者的差别要用 .data() 存过东西就得记着；事件解绑那套 API 对照见旧文，不重复。手边没工具时，用一个引用登记字典做纪律也能兜住：

老 IE 的循环引用（历史事实）

现象：IE 7/8 上页面开着不动，内存也是一条向上的直线，同一个页面换到 Chrome 与 Firefox 却基本平稳。

定位：当年没有工具可依赖，只能开任务管理器盯着那个进程的内存数字，把同一个操作重复三十遍看它回不回落。方法粗，但足以判断“是不是只有 IE 涨”，从而把嫌疑收窄到回收算法。

根因（历史事实）：IE 7/8 的 DOM 节点是 COM 对象，DOM 与 JS 各用引用计数、两边计数器不通，一旦元素属性上挂了闭包、闭包又引用该元素，环就永远归不了零。完整的推导和 attachEvent 场景下的规避写法，旧文《DOM 事件移除与内存泄漏》已经写过，这里不重复。

修复与复盘：当年的标准做法是在 onunload 阶段统一解绑并把引用置空。两个代价必须写清楚：一是 onunload 在移动浏览器上并不可靠，iOS Safari 的前进后退缓存（bfcache）会让它根本不触发，2015 年这个问题已经有公开讨论；二是它把清理时机推到页面退出，页面内做的操作照样累积。真正靠得住的还是“绑定时存引用、销毁时立刻解绑”，onunload 只是 IE 8 及以下的一道补丁。IE 9 起改用标记清除，这个环本身不再是问题，可达链依然成立。

第三方组件与注册型泄漏

现象：接了埋点 SDK 或某个内部组件之后开始涨，业务代码一行没改。

定位：把注册中心的长度打出来。全局 Bus 的 handlers 数组、自己维护的 getElementById 结果字典、window.name 的字符串长度，这三个数字一打，泄漏点基本藏不住。

根因：注册型接口的通病——on 是公开的，off 得你自己记得。发布订阅的实现不重讲，只看这一条泄漏面：组件初始化时往全局数组 push 一个回调，组件销毁时没人调用对应的 off，那个回调连同它捕获的组件状态就永远活在数组里。同类的三处小账：匿名函数挂上去就摘不下来，原生监听与 attachEvent 都必须先存住函数引用才能解绑；把 getElementById 的结果长期缓存在模块级字典里，节点删了引用还在；window.name 能存很大的字符串，而且按当时的文档说法，它在同一个窗口标签内的整页跳转里都不会丢，我在 Node 上试了把两百万字符塞进 globalThis.name，照样稳稳存着，用完置成空串比留着省事。

修复与复盘：往全局注册的每一个回调，都要在组件的 destroy 里找到它的对偶；缓存字典缓存 id 而不是节点；引入第三方组件时先看它暴露了什么注销接口，没有就把它包一层再上。

定位手段

工具部分按 2015 年能用的写，别拿后来的面板名字套。Chrome 40 这一档：Profiles 面板选 Heap Snapshot，拍 Take Heap Snapshot，配合 Comparison 视图按增量排序；要看趋势就选 Heap Timeline，反复操作观察节点数量是否只升不降；Timeline 面板的 Memory 指标给出已用 JS 堆、节点数、监听器数三条曲线；Retained Size 用来看某个对象真正拖住了多少；Elements 面板选中节点后在 Console 里用 $0 直接引用它，验证是谁在持有。Firefox 35 这一档：about:memory 看显式分配与 JS 堆，about:config 里打开 GC/CC 日志，看回收是否真的跑过（这段是 Mozilla 文档依据，不是逐项实测）。IE 8/9/10 这一档：没有可用工具，只能任务管理器粗测加重复操作看增长，这是当时的现实。工程手段：performance.memory.usedJSHeapSize 做趋势上报，Node 上这个属性不存在，侧面印证它当时只有 Chrome 支持，而且是非标准接口，只能用于观察、不能用于逻辑判断，上报时取增长斜率和峰值就够。

最后一条容易被跳过：不复跑，就不知道自己修的是根因还是症状。

收口 checklist

  1. 每个函数顶部 'use strict'，构建期 JSHint 开 undef、unused、predef 白名单。
  2. 隐式全局当错误处理：漏写 var、this.xxx、链式赋值三处逐行过。
  3. 每个 setInterval 都能在同模块的 destroy 里找到对应 clearInterval，走登记表不靠人记。
  4. 写回调前先确定它真正需要外层哪几个字段，只捕获这几个。
  5. 任何缓存字典都要有容量上限与淘汰动作，delete 要真的执行到。
  6. 上线产物剥离 console，本地一律走安全包装函数。
  7. 移除节点前先清数据与引用，remove、empty、detach 的差异按场景选。
  8. 全局注册中心只允许成对的 on 与 off，第三方组件没有注销接口就不直接接。
  9. 匿名函数不绑定：先存引用，再谈解绑。
  10. 每个高频浮层每季度跑一次二十次复现流程，堆快照对比留档。

这十条里没有一条是“高级技巧”，全是最普通的成对与显式：创建与清理成对、注册与注销成对、引用与释放成对。内存问题从来不是回收器不够努力，而是我们写出了它拆不断的引用。
