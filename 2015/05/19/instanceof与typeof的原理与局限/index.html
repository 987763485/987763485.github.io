instanceof 与 typeof 的原理与局限

写 JS 不满一年的人，做类型判断学到的头两样工具基本都是 typeof 和 instanceof。然后你大概会在两个地方栽跟头：先是 typeof null === 'object' 让你怀疑人生，接着某个嵌了 iframe 的页面里，[] instanceof Array 活生生返回 false。不少人从此把这两个运算符当成两套”背结论”的玄学。其实各自的判定逻辑只有一句话：typeof 看值的种类标签，instanceof 沿原型链找 prototype。把这一句话吃透，所有坑都能自己推出来。本文面向刚被上面两行代码困惑到的读者，把两个运算符一次讲透，最后收口成一套能直接抄进公共库的 ES5 判定工具和一份”该用哪个”的决策清单。文中所有返回值都在 Node 里实测过，个别只有老 IE 才有的行为会单独标注为历史事实。

typeof 是运算符，不是函数

第一件事，把”typeof 是个函数”的直觉扔掉。typeof 是一元运算符，后面跟一个操作数，返回一个字符串。它看起来像函数调用，纯粹因为后面常跟一对括号，而那对括号其实是分组运算符：

还有一个非常实用的特性：对一个从未声明过的变量，直接引用它会抛 ReferenceError，但 typeof 不会，它安静地返回 'undefined'。这是规范明确保证的行为，也是特性探测必须写成 typeof jQuery === 'undefined' 而不是 jQuery === undefined 的全部理由——后者在页面没引入 jQuery 时直接报错中断脚本。

typeof 的精度到哪里为止

先解释那句最扎眼的 typeof null === 'object'。这要回到最早的 JavaScript 实现：当时引擎把值存在机器字里，低位打一个类型标签，对象的标签恰好是 0；而 null 在底层就是一个空指针，机器字全是零，低位标签自然也是 0。类型判断函数只看来得及看的低位标签，于是把 null 认成了对象。后来引擎重写了内部表示，但这个结果已经被海量存量代码依赖，规范只好默认它。注意这只是历史实现层面的解释，不是规范故意刁人，更不是”null 本来就是对象”。

typeof 分不清对象内部的种类。数组、日期、正则、错误对象、new String('a') 这样的包装对象，一律返回 'object'——它的粒度到”是不是对象”就停了。对象层之外还有一处不可靠：宿主对象不归 ECMAScript 规范管，各家实现想怎么返回就怎么返回。老 IE 里 typeof document.all 返回 'undefined'（它在别的浏览器里是 'object'），同一个宿主函数在不同 IE 版本间还有返回 'object' 与 'function' 不一致的情况，这些都标注为当年的历史事实，今天 Chrome 与 Firefox 里复现不出来。

把上面的局限加起来，结论只有一个：typeof 只适合判断原始类型加函数。六种语言类型里，'undefined'、'boolean'、'number'、'string'、'function' 五个返回值都靠谱，'object' 这一档它什么都告诉不了你。

instanceof：沿原型链往上找 prototype

instanceof 管对象层，它的判定只有一句话：A instanceof B，就沿着 A 的原型链一级往上走，看能不能碰到 B.prototype。碰到就是 true，走到链尾 null 还没碰到就是 false。

flowchart TD
    A[A instanceof B 开始] --> B{A 是对象吗}
    B -->|不是| C[直接 false，不做转换]
    B -->|是| D[取 A 的原型]
    D --> E{等于 B.prototype 吗}
    E -->|相等| F[true]
    E -->|不等| G{取到 null 了吗}
    G -->|没有| D
    G -->|到了链尾| C

文字化走一遍 [] instanceof Array：空数组的原型（内部那个 [[Prototype]]，调试时可借 __proto__ 观察）正是 Array.prototype，第一跳就命中，true。换成 [] instanceof Object：第一跳是 Array.prototype，不相等；再往上，Array.prototype 的原型是 Object.prototype，命中，true。原型链的术语与推导在《JavaScript 原型与原型链完全解析》里已经讲全，本文直接拿”沿链找 prototype“这个结论用。

认得出”是对象”，认不准”是哪种对象”。 d instanceof Date 可以判日期，但 x instanceof Object 几乎恒真是句废话；而且只要有人把自己的构造器原型接到 Date.prototype 上，他的实例就能冒充 Date。它对内置类型之间的鉴别力太弱，也挡不住恶意或无心的原型嫁接。至于将来——注意是展望——ES6 草案计划提供 Symbol.hasInstance 让类自定义 instanceof 行为，2015 年 5 月的今天完全不可用，本文所有结论不依赖它。

到底该用哪个：决策清单

  • 判原始类型（string、number、boolean、undefined）和函数：用 typeof。这是它的主场，也是它唯一的主场。
  • 判数组：用 Array.isArray，IE 8 配上面的垫片；永远别用 instanceof Array。
  • 判自己构造出来的实例：用 instanceof，但心里装两条戒律——左右两边必须都是对象，以及跨 realm 会失灵。
  • 判内置对象的种类（Date、RegExp、Error、arguments……）：用 Object.prototype.toString.call 的标签。
  • 判 null 或 undefined：x == null，等价性由旧文论证背书。
  • 判 DOM 节点：nodeType，浏览器实现差异不让规范背责。
  • typeof null === 'object' 与 instanceof 的原始值 false 是语言既成事实，防御方式是判类型前先 x == null、先确认 typeof 过了对象关，而不是绕开工具。

小结

typeof 读值的类型标签，粒度停在”原始类型加函数”，null 的 'object' 是历史实现的遗产；instanceof 沿左边的原型链找右边的 prototype，机制干净，但对原始值直接 false、对裸对象失灵、跨 realm 整段作废、还随时可能被改写原型的人掰弯。两者都不是错的，只是各自的答案只在它的适用域内成立。工程上的答案因此清楚：typeof 管原始类型与函数，Array.isArray 管数组，toString 标签管内置对象种类，instanceof 留给自定义类型，公共工具函数沉到库里统一维护，业务代码里不再手写零散的判断。
