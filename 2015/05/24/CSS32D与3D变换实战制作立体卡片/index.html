CSS3 2D 与 3D 变换实战：制作立体卡片

本文属于《HTML 与 CSS》第 46/62 篇
上一篇系列目录下一篇

各 transform 函数与 matrix(a,b,c,d,e,f) 的对应关系、变换顺序的矩阵推导、合成层与层爆炸的性能判据，我在《CSS3 transform 位移缩放旋转与矩阵》里已经写完；@keyframes 与 animation-* 逐个属性的讲解在《CSS3 animation 与 keyframes 动画实战》里；滤镜与混合模式在《CSS3 滤镜 filter 与混合模式 blend-mode》里。本文一律不复述，只做一件事：把 2D 的 rotate 和 3D 的 rotateY、perspective、transform-style、backface-visibility 组合成两个能直接抄走、能跑的作品——一张点击翻转的立体卡片，一个可以鼠标拖拽的立方体。每一层结构为什么这么摆、每个数值从哪来，都给出可运行的写法。

开工前：前缀、底线与本文范围

本文用到的四个属性在 2015 年 5 月都属于”要写前缀才安心”的那一类：-webkit-perspective、-webkit-transform-style、-webkit-backface-visibility 和 -webkit-transform。前缀写法在前、标准写法在后，同一个声明块里成对出现，顺序不能颠倒——层叠规则是后来者胜，把标准写在前头等于让带前缀的那行去覆盖它，老 WebKit 拿到的是自己不认识的标准声明，整条丢掉。浏览器本来就会丢弃不认识的声明，所以两份都写不会出问题，只多一份体积。

底线部分：IE9 只有 2D，rotate、scale、translate 都能用且不需要前缀，但 perspective、rotateY、translateZ 一律失效；IE10 与 IE11 支持 3D 且无需前缀。Android 2.x 原生浏览器完全没有 3D 支持，写了等于没写；Android 4.x 与 iOS 7、iOS 8 都需要 -webkit- 前缀一行。结论是：3D 部分必须当成渐进增强，卡片和立方体在老环境里要有一个能用的平面版本，后文单独给方案。

作品一：点击翻转的立体卡片

结构：为什么必须有三层

三层各管一件事，少一层就会撞到具体问题。

.card 是视口：给它尺寸（宽、高）和 perspective，它自己不动。透视写在它身上，等于给里面所有 3D 内容定了一个共同的消失点。

.card-inner 是被翻转的那个面：它承担 transform: rotateY(180deg) 和 transform-style: preserve-3d。之所以要单独有这一层，是因为”被旋转的元素”和”承载尺寸与透视的元素”必须是两个不同的盒子。旋转发生在父级的坐标系里，父级又是透视的来源；如果直接在 .card 上写 rotateY，那么 .card 自己被翻，而它的 perspective 对它自身无效（perspective 只作用于子元素），你就只能把透视再往上推一层，最后仍然回到”两层”结构。此外两个面要靠绝对定位叠在同一位置，.card-inner 让它们有共同的定位上下文，尺寸则由外层固定。

.card-front 与 .card-back 是内容面：绝对定位、铺满、各自实色背景、各自 backface-visibility: hidden，背面再叠一个 rotateY(180deg)。

CSS：六个选择器一次配齐

逐条讲理由。

perspective: 600px 写在 .card 上。 数值的含义是观众的眼睛到元素所在平面（z = 0 那一层）的距离，越小透视越夸张、翻转中途变形越明显，越大越接近正交投影。600px 配 260px 宽的卡片是个不出错的中间值；想更平一点就推到 800px 到 1000px。写在父级上还有两种好处：容器里同时放十张卡片翻转，它们的消失点都汇聚在同一个位置，画面才不散；消失点的位置由父级的 perspective-origin 决定，默认 50% 50% 即 .card 自身中心，想让人从斜上方看就把它往上或往下推。反过来写成 transform: rotateY(180deg) perspective(600px)，透视就变成每个元素各有一份、原点定在自身，多张卡一起翻会各斜各的。

.card-inner 必须有 preserve-3d。 默认值 flat 会把子元素压回父元素所在平面。压平之后两个面变成 .card-inner 这个平面上的两张普通贴图，你翻的是那张已经被拍扁的板子，背面内容会以镜像糊在正面上。这一条和前缀一样，-webkit-transform-style 在前。

两个面都要 backface-visibility: hidden。 这个属性作用在元素自身、不参与继承，写在 .card-inner 上只管得到它自己那块透明的板子，管不到两个面。只给 .card-back 加，正面转到背对观众时照样绘制，你会看到反字的正面压着背面；只给 .card-front 加，翻过去之后背面是空的。这是成对出现的两条声明，缺一个卡片就废了。

transform: rotateY(180deg) 只放在触发态上。 放在 :hover 让桌面用户零成本试出效果，放在 .is-flipped 类上给触屏和 JS 用；两行合写一个选择器组，别只留 :hover——触屏设备上没有 hover。

transition 里列属性不要写 all，理由在旧文里已经说过：只插值真正要变的属性，把重绘范围压到最小。注意 -webkit-transition 那行里过渡的属性名也要带前缀（-webkit-transform），写成 transition: transform 去前缀匹配在老 WebKit 上是无效的。

className 的字符串拼装只在这张卡片只有一个类名时安全（class="card"）。项目里卡片往往挂着 .card、.card--wide、.js-flip 好几个类，就换 classList（Android 4.x 与 IE10 可用，IE9 不行）或者直接走 jQuery 1.11：

用 jQuery 的话，$.fn.toggleClass 内部处理了 className 的分词，比手写 indexOf 稳。另外点击翻转要和 hover 共存，否则鼠标一进一出就把用户的点击状态冲掉了。

四个会咬人的细节

  1. 翻到一半文字锯齿、边缘抖一下。 iOS 7、iOS 8 的 Safari 上，翻转过程中的文字会先糊再清、背面偶尔闪一条边。当时的通用缓解是给两个面补 -webkit-transform: translateZ(0)（背面写 translateZ(0) rotateY(180deg)；位移是 0 的时候顺序不影响结果，但只要给 translateZ 填上非 0 值，它就得摆在旋转后面才沿自己的法线走，规矩见旧文的顺序一节）把面提成独立层，再配合 -webkit-backface-visibility: hidden。这是”用显存换观感”的权宜之计，一层一份纹理，卡片多的页面别这么写，代价与判据在旧文的合成层一节。
  2. 容器塌陷。 两个面都是绝对定位，脱离了文档流，容器高度必须由 .card 显式给。内容长度不可控时用 min-height 兜一个值，或者让 JS 读取较高那面、把 height 写回 .card。否则在降级版里（后文）内容会溢出到卡框外面。
  3. overflow: hidden 与 3D 冲突。 在 .card-inner 上写 overflow: hidden 想让内容不外溢，结果是 preserve-3d 被静默作废——按规范，非 visible 的 overflow 属于会强制扁平化的分组属性之一，同样性质的还有 opacity 小于 1 和 -webkit-filter（滤镜那篇里也提过它会让元素自成一层）。要做圆角裁切，把 overflow: hidden 放在最外层 .card，或者干脆在面上用 border-radius 加实色背景，不要裁 3D 子元素。iOS 上 overflow: hidden 加 border-radius 再叠 preserve-3d 会退化成 flat，这个坑旧文的兼容性表里记过一笔。
  4. 背面文字还是透出来，按这个顺序排查。 先看 .card-inner 有没有 preserve-3d（含 -webkit- 那行），没有的话先修它；再看它有没有被 overflow、opacity、filter 中的任何一个强制扁平化；然后确认两个面各自都写了 backface-visibility，注意这个属性不继承，写在父级上不算；最后核对 .card-back 的 rotateY(180deg) 有没有被抢掉——同特异度时后写的赢，所以基础态别写在触发态后面，更要小心某个 transform: none 之类的重置规则顺手把它抹平。getComputedStyle(el, null) 读回 webkitTransform 能直接看到最终矩阵，比猜快。

作品二：可旋转的立方体

结构：一个盒子和六个面

.stage 供透视，.box 是立方体本体（preserve-3d），六个 .face 绝对定位铺满 200px × 200px。边长取 200px，半程就是 100px。

数学：为什么必须 translateZ 半程

六个面各自的变换，数值我按边长 200、半程 100 手算核对过：

读法只有一条：先转身、再沿自己新的法线走出去。translateZ 写在 rotateY 的右边，它作用在已经转好角度的局部坐标系里，所以每面都朝自己的外侧移动 100px。取正面验算：rotateY(0) 后局部 z 轴仍指向观众，translateZ(100px) 把它推到屏幕前方 100px，正好是前表面。右面 rotateY(90deg) 之后局部 z 轴指向屏幕右侧（CSS 里 y 轴朝下、正角度顺时针，这条我在旧文用矩阵自证过一次），再 translateZ(100px) 就贴到右边。上面 rotateX(90deg)：把 (0,0,1) 代入 y' = -z·sin90° = -1、z' = 0，法线变成朝上，落点 y = -100px，也就是几何中心上方 100px，正是顶面；rotateX(-90deg) 同理落到底面。中心到各面恰好 100px，边长 200px，对得上。

不写 translateZ 会怎样？ 六个面全都躺在 .box 所在的 z = 0 平面上完全共面，转起来你看到的是几条重叠的边、偶尔糊成一条线，也就是穿模。半程平移是把”一张纸”变成”一个盒子”的唯一动作，任何正多面体都是同一套做法：旋转定朝向、translateZ 定内切半径。

nth-child 写法能少写六个类名：

那能不能把 100px 写成 translateZ(calc(200px / 2))？2015 年不建议。calc() 本身从 IE9 起就支持，但 IE9 恰恰不支持 3D 变换；Chrome 与 Firefox 当时把 calc() 嵌进 3D 函数里的实现并不稳定，translateZ(calc(...))、rotate(calc(...)) 在部分版本被整条丢弃——而 transform 一旦被丢弃是静默的，页面上只剩”立方体塌成一片”。自定义属性与条件式的特性查询规则这一年还只在草案里，都不能依赖。所以数值只能写死，用预处理器管住它：

让它转起来：自转加拖拽

自转交给 animation。关键帧与 animation-* 各属性逐个怎么算，旧文已经写完，这里只放立方体需要的两个角度：

两端都保持同一个 rotateX(-20deg)，立方体微微俯视地绕竖轴转。这里必须留神：animation 的优先级高于 transition，它会接管 transform，你在拖拽逻辑里用 JS 写的 transform 会被关键帧盖掉。所以自转和拖拽二选一，用 .box--auto 这个类名切：开始拖就摘掉它。

拖拽的实现，ES5（里面的 on() 就是作品一那个兼容封装，末尾清单里会重复一份，方便只抄立方体）：

mousemove 挂在 document 而不是立方体上，否则鼠标拖快了滑出元素就断。rotX 夹在 ±90 之内是下面那条顺序问题的直接后果。

顺序在立方体上是看得见的差别。 上面写的是 rotateX(a) rotateY(b)：右边的 rotateY 先作用在未倾斜的局部竖轴上，左边的 rotateX 再把整个已经转过的立方体绕屏幕横轴俯仰一次——横向拖永远绕立方体自己的竖轴自转，竖向拖永远绕屏幕横轴俯仰。反过来写成 rotateY(b) rotateX(a)，俯仰先做、偏航后做，此时立方体自身的竖轴会绕屏幕竖轴画一个圆锥，观感是斜着晃。我按 CSS 的旋转矩阵离线复算了同一个姿态：rotateX(45) rotateY(180) 把正面法线送到 (0, 0.707, −0.707)（朝下朝后），rotateY(180) rotateX(45) 送到 (0, −0.707, −0.707)（朝上朝后），两者差得很远，矩阵推导的规矩旧文的顺序一节已经写完。

为什么选前者：内层那一项的旋转轴会被外层带偏，所以要被带偏的是幅度有界的那个。rotateX(a) rotateY(b) 里被带偏的是竖轴，而 a 夹在 ±90 之内，最多倾斜 90°；换成反过来写，被带偏的是俯仰轴，而偏航 b 是无界累加的，b 超过 90° 后竖向拖拽就变成在屏幕平面里滚。增量更新的写法就这么定下来：每一帧只替换右边那一项的数值，rotateX 永远留在外层；若坚持 rotateY rotateX，rotX 的增量得绕已经偏转过的轴重算，很麻烦。还有一个欧拉角躲不开的固有现象：a 接近 ±90 时，立方体自身的竖轴转到指向观众，横向拖看起来就是在屏幕平面里滚而不是转——这不是 bug，所以代码里把 rotX 夹在 ±90 之内观感最稳。

排序与遮挡：z-index 在这里说了不算

同一个 preserve-3d 上下文里的元素，绘制顺序按变换后的深度排，谁离观众近谁在上面，z-index 不参与这个比较。这也是立方体不必给六个面手动叠 z-index 的原因。但一旦某个元素被扁平化（overflow、opacity 小于 1、filter 任一命中），它就退出深度排序、回到 2D 层叠世界，靠文档顺序和 z-index 定胜负——这是”明明在后面的面盖住了前面的面”最常见的根因。

不透明面之间排序错乱、背面挡住正面，修法按顺序：确认六个面都是实色背景且没写 filter；给每个面加 backface-visibility: hidden，背对观众时整个面不画，比 z-index 更可靠；确认 .box 的 preserve-3d 没被强制扁平化；最后才考虑把半透明的面（像上面 rgba(43, 103, 165, .85)）改成实色，因为半透明时浏览器无法靠”挡住”来省绘制，深度相同的面还会互相透。想只露某个面时，用 visibility: hidden 或 display: none 摘掉它，别指望 z-index: -1。

不支持 3D 时怎么退

prefers-reduced-motion 这个媒体特性在 2015 年还不存在，等它进浏览器是好几年后的事，当时能做的等价物是把开关交给 JS 和用户：默认不挂自转类名，页面上放一个”开始旋转”的按钮，点了才加 .box--auto；对晕动敏感的用户可以自己选择不动。

检测能力用 Modernizr 的 csstransforms3d，它给 <html> 挂 csstransforms3d 或 no-csstransforms3d 类名，样式按类名分支。要提醒的是它的实现方式：造一个探针元素、写 translateZ(1px)、量布局尺寸是否变化来判定。探针本身要带前缀写，而部分老 Chrome 与 Android 浏览器会报”支持”却在真机上把 3D 丢掉，所以最好再用媒体特性交叉确认一次：

降级后的平面版要照样可用：两个面上下堆叠、都可见，点击只显示一个。

配套把 .card 做成 button 或者补 tabindex="0"、role="button"、aria-pressed，键盘回车也能翻——翻转是个状态，键盘用户有权进入这个状态。还有一点可以省事：rotateY()、translateZ() 这些 3D 函数在不支持的环境里是非法值，整条 transform 声明被丢弃，所以平面版不需要再额外去覆盖翻转与过渡，浏览器自己就退回原样。

性能：只提三条结论

推导和测量方法在《CSS3 transform 位移缩放旋转与矩阵》里，这里只落三条和本文直接相关的。一，别把几十个立方体同时挂上自转：每个持续动画的元素都要一个合成层和一份按变换后包围盒算的纹理，一多就撞设备纹理上限、退回软件路径，反而更卡；页面里同屏超过十来层就该回头查。二，只动 transform 和 opacity：本文两个作品的过渡与拖拽都只改 transform，不碰 left / top / width。三，别在 3D 容器上加 box-shadow 或 filter：两者都让容器自成一层并逐帧重绘大范围模糊，阴影要做就预先画好交给伪元素的 opacity（做法见旧文的 hover 卡片一节）。will-change: transform 当时 Chrome 36 起支持，IE 与老 Android 完全不支持，被忽略也只是没提层，可以当渐进增强，用后要撤。
