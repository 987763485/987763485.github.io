CSS 性能优化：减少重排与重绘

本文属于《HTML 与 CSS》第 61/62 篇
上一篇系列目录下一篇

关于减少重排与重绘，条目清单《减少重排与重绘的实践清单》已经逐条列过，渲染流水线本身《浏览器渲染流程详解》也讲透了。本文不再抄一遍清单、也不再走一遍解析到上屏的通用流程，只做一件事：站在源码与机制的角度，解释为什么某类 CSS 写法在引擎里贵、贵在哪一步。读完你应该能回答”因为引擎做了 X，所以 Y 写法触发了 Z”。

把代价拆成三段：style、layout、paint

一次样式变动之后，引擎要重算的是三段，而不是笼统的”一次重排”。style 段做选择器匹配、层叠与继承，算出每个元素的最终计算值；layout 段把盒子的宽高与坐标在布局树上算清楚（Blink 内部这棵树叫 LayoutObject，更早的 WebKit 叫 RenderObject，属引擎实现事实）；paint 段生成绘制指令并光栅化成像素。改一条 CSS 声明，最坏情况把三段全走一遍，最好只走 paint。

于是判据清楚了：一笔改动的贵贱，不取决于这条规则本身，而取决于两个乘数——受影响元素的数量，和它触发的阶段深度。color 只走 paint，width 要走 layout 加 paint，把一个状态类挂到大容器上则让整棵子树在 style 段重算。把这两个乘数压下去，是 CSS 机制优化的全部着力点。

style 段：贵在被标脏的元素数量

样式重算的经验值与实验我在《CSS 选择器性能误区》里量过，这里只补机制。引擎匹配选择器时从最右段（关键选择器 key selector）向左验证，所以候选集由最右段决定、再向左过滤：

#nav > ul > li > a.current 的候选由 a.current 决定，再逐段向左验证祖先，命中面比一个平展的 .nav-link.is-active 大。通配 *、.btn *、属性选择器 [data-x] 只有处在关键段位置时才持续收费，一次性 Reset 属于首屏结一次账（通用工程常识）。结构伪类 :nth-child 的代价不在匹配本身而在失效标记——插删一行会把后续兄弟序号全部作废、连累一片重算；:not() 的成本与普通类条件相当，不必株连（引擎实现事实加规范）。

真正的放大器是”往大容器挂类”和过度嵌套：嵌套越深、命中元素越多，一次改动的 style 重算范围越膨胀。测量口径按 2015 年的叫法：Timeline 面板里的 Recalculate Style 事件，看它占多少帧时间、由哪次 class 或 DOM 变动触发；Profiles 面板可对一次交互采样，看样式重算调用栈的深浅。这比争论”某条选择器字符串快几毫秒”有用得多。

顺带纠正一个流传谣言：!important 对性能几乎无影响。它只改变声明参与层叠时的胜出次序，匹配与重算一步不少；特异度比较是每元素个位数次的整数比较，根本不是热点（引擎实现事实）。它真正的代价是可维护性——覆盖它要更重的选择器，逼出升级竞赛。至于特异度怎么算，《CSS 层叠、优先级与特异度计算实战》讲透了，本文不重复。

layout 段：脏标记如何沿布局树传播

layout 之所以贵，机制在传播方向。布局树里每个盒子知道”我占多大地方”，父盒子和后续兄弟的坐标都建立在这个前提上。改一个子元素的 width，引擎把它标脏，再把脏标记向上传到父链、向下传到子树，直到撞上一个边界——一个有固定宽度的祖先，或一个 position: absolute/fixed 的祖先——才停下来。这就是”改一个孩子、牵动一路祖先重算”的原因（引擎实现事实）。

按进入的阶段给属性分档（口径承接《减少重排与重绘的实践清单》，此处只补边界与机制）：

  • 只走 paint：color、background、outline、box-shadow、opacity，不动几何，布局结果仍然有效。
  • 必走 layout：width、height、margin、padding、border-width、top、left、font-size，动了就得重算坐标。
  • 特殊档：position 改的是元素是否脱离流，牵动兄弟与整页回流；float 影响同行文本的回绕；line-height 改的是行盒数量；letter-spacing、word-spacing、text-transform（大写会改变文本宽度）都落在 layout 的文本测量里；字体加载完成会触发二次布局，即当年的 FOUT 抖动（历史事实加规范）。

transform 为什么绕开 layout：它在布局完成之后做变换，不改变”盒子占多大地方”，矩阵推导见《CSS3 transform 位移缩放旋转与矩阵》，本文不重讲。

缩小 layout 范围，本质是把改动关进独立的布局上下文：

position: absolute/fixed 让子树自成一体，float 的影响也局部。当年最凶的是表格：嵌套表格叠加长内容会让 layout 灾难性变慢，因为自动表格布局要先量一遍每列内容、再按约束回推行高列宽，等于两遍测量（CSS 2.1 表格布局模型加历史事实）。table-layout: fixed 当时被当作性能手段，正是因为它把两遍压成一遍。IE 的 hasLayout 是同一时代另一套内部机制，如今只作历史事实看待。必须点明：contain 与 content-visibility 这类”用声明圈住重算范围”的属性在 2015 年还不存在，当下能做的只有”限制改动范围加减少元素数量”两条土路。

paint 段：面积与效果类型的账

paint 的成本是重绘面积乘以单像素指令开销。大面积阴影、渐变每帧重画很吃 paint：box-shadow 的模糊是一层高斯卷积，background-attachment: fixed 在滚动时整层背景要重绘（iOS 上其实现还不可靠，属历史事实）。border-radius 叠 box-shadow 要额外做抗锯齿裁剪，圆角越大越贵；-webkit-text-stroke 是整圈描边；filter 当年多带 -webkit- 前缀、Firefox 的 filter: blur() 另走 SVG 语法，且会生成临时位图再处理，兼容性参差。这些属性各自的用法在《CSS3 滤镜 filter 与混合模式 blend-mode》《CSS3 圆角、阴影与边框新特性》《CSS3 渐变 linear-gradient 与 radial-gradient 实战》里都有专文，本文只把它们归到”按面积与效果计价”这一档。

合成层：为什么 transform 与 opacity 便宜

opacity 与 transform 动画便宜，是因为元素已经光栅化成层，动画只是让合成器搬运这张纹理、改它的透明度，layout 与 paint 都不重走。代价是提层要真实吃显存：每层的位图按边界盒乘设备像素比占内存，层数越多越贵，给一堆静止元素滥挂 translateZ(0) 只会造成层爆炸。will-change 在 2015 年 Chrome 36 之后已可用、Firefox 也支持、IE 全系不支持，它只是告诉引擎”我待会儿要动”，用错同样吃内存，不能当常驻开关。层数与连带提升的推导细节见《浏览器渲染流程详解》，本文不重复。

文件层面：下载与解析也是机制代价

CSS 的账有一部分落在网络与解析上，而且当年是真问题。@import 会串行：被导入的样式要等它所在的文件下载并解析后才被发现、再发一轮请求，把渲染阻塞拉成一条串行链，所以 2015 年仍主张用 <link> 并行取代（引擎行为加历史事实）。渲染阻塞的样式表数量直接决定首帧能多早出现。media 属性里的样式表照样会被下载，只是不参与初始渲染，媒体查询这层在《CSS3 媒体查询 Media Queries 响应式布局》里讲过。未被命中的规则对 style 段的运行期几乎无成本（它不进任何元素的计算值），但它照样占下载与解析——所以 CSS 压缩的真实收益在下载与解析两段，不在选择器匹配段（通用工程常识）。

度量与定位：先确认热点在哪一段

拿不到帧数据就别说优化。2015 年的工具口径是 Timeline 与 Profiles 两个面板：Timeline 按帧画 Recalculate Style、Layout、Paint 三类柱子，看哪类占时长最多，就知道钱花在 style、layout 还是 paint；在 Settings 的 Renders 分组里勾选 Paint flashing 看脏矩形范围、Layout borders 看布局框、Show paint rectangles 看绘制区域（这三项是当年 DevTools 的渲染调试开关，属历史事实）。

前后对比可以用 console.time 加时间戳，口径沿用旧文那两条纪律：先预热、多次取均值、只认量级。

再给一个能量化的指标：”一次交互波及多少元素”。用一条统计脚本数出容器子树规模，就能预判 style 重算的范围。我在仓库外造了一个示例页——一个 300 项的列表加一张 200 行、5 列的表格——实测：给挂满 300 项的容器加一个状态类，需要重算的范围（含后代）是 601 个元素；那张表格整棵子树 1206 个元素、单元格 1002 个。这类数字只能靠静态数 DOM 得到；渲染成本本身我无法在真实浏览器里逐帧测量。

务实结论：大多数页面的瓶颈在下载与 JS，不在 CSS 机制。CSS 机制优化的收益集中出现在三类场景——大 DOM、频繁交互、老 Android——在小页面上死抠选择器毫秒是本末倒置。

一张可查的总结表

改这类属性或写法 走到哪一段 范围如何控制
color、background、box-shadow、opacity 仅 paint 减小脏矩形面积，别整屏重绘
width、height、margin、top、font-size layout 加 paint 关进 abs/fixed 上下文，压小子树
:nth-child、深层嵌套、大容器挂状态类 style 重算 让”改谁只重算谁”，压低命中数
transform、opacity 动画 以合成为主 只给真正会动的元素提层
自动表格布局 layout 两遍 table-layout: fixed 压成一遍
@import、多块渲染阻塞 CSS 网络加解析 <link> 并行，压缩只留首屏关键样式

一句话收口：CSS 性能不在单条规则字符串的长短，而在一次变动沿 style、layout、paint 走多远、拖多少元素一起走。把阶段选浅、把范围关小，就是这套机制能给的全部杠杆。

关于结论来源，本文的机制性论断分别标注为规范（CSS 2.1、CSSOM）、引擎公开文档与实现事实（Blink 布局树、合成器）、历史事实（2015 年的 @import、hasLayout、will-change 支持面、DevTools 面板）与通用工程常识，均为该层面推演，不是本人真实浏览器逐帧实测的数据；文中元素数量是对示例页用脚本静态统计所得。本地环境无法完成真实浏览器的渲染成本测量，凡涉及毫秒与帧的表述都应回到你自己页面上的 Timeline 记录去复核。
