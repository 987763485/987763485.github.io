JavaScript 闭包从原理到实战

写下这篇的日期是 2015 年 6 月 17 日，就在这几天，ES6 规范定稿的消息刷了屏。但对我们这些明天还得在 IE 8 上把按钮埋点跑通的人来说，新规范里那套块级作用域声明，在相当长一段时间里只能看、不能上线。所以本文所有代码停在 ES5：var、function、this、原型、闭包。全文面向”听说过闭包、每次面试都答不准”的读者，讲法尽量平实，覆盖面尽量完整：从一句定义推到四个实战场景，再收在六个陷阱和一组实测数字上。所有”先猜输出”的例子都在本机 Node 里逐条跑过，输出与文中一致；涉及浏览器历史差异的地方我会标明那是当年的事实，不是本机复现的结果。

先把定义说准，再破三个误解

一句话版本：闭包是”一个函数”加上”它诞生时所在的那层作用域”的组合。这句话里有三个词要咬住。

第一个是”诞生时”。函数在哪一层作用域里被写出来，它就永远带着那层作用域走，跟它将来被谁调用、挂到哪个对象上、交给哪个定时器都没有关系。第二个是”作用域”，不是”变量”，也不是”对象”——它是一整层可访问的名字集合，函数拿走的是这一层的引用，不是拷贝。第三个是”组合”：闭包这个东西不是一个语法结构，你在代码里找不到一个叫 closure 的关键字；它是函数与作用域绑定之后自然产生的那个产物。

于是有了本文最想纠正的一个认知：JavaScript 里任何函数都是闭包。全局函数的作用域链走到全局对象，成员方法的作用域链也照样从它被定义时那一层往上串。区别只在于寿命和可见的名字：绝大多数函数用完就丢，它那层作用域跟着一起没了；只有当函数活得比它的出生作用域更久时，我们才特意叫它”闭包”——因为这层作用域被它硬生生拖住了，关在里面出不来。

围绕这个定义，有三个流传很广的误解，我按见到频率从高到低排。

误解一：”在函数里再定义一个函数才叫闭包。”这是把最常见的产生方式当成了定义。把一段匿名回调交给 setTimeout、交给 addEventListener、交给数组的 forEach，都是闭包，而且它们没有出现在任何函数体里定义函数——有的是写在文件顶层、只是被当作值传出去。反过来，在函数里定义的函数如果没引用任何外层名字、也没活过外层调用，它就是个普通嵌套函数。

误解二：”闭包就是私有变量。”私有状态只是闭包的一种用法，还是最常被举例的那一种，以至于很多人以为这就是全部。工厂函数、回调里保住上下文、一次性初始化、把配置缓存起来——这几条用法跟”私有”没什么关系，反而更常用。本文会用三个实战场景说明这件事。

误解三：”闭包是性能问题，能不用就不用。”这是最有害的一句。它是把”内存泄漏的传闻”和”标识符解析的开销”两件事揉成的一个直觉，而这两件事都能被实测驳回。我把数字放在后面一节，先给结论：访问一个闭包变量和访问一个形参、一个全局变量，在同一个量级上；闭包真正要付的账，是它把出生作用域留到了什么时候、留了多少东西。

为什么会有闭包：从三个需求推出来

一，做一个计数器，外界能”数一次”和”读当前值”，但不能直接把 999 塞进去。二，一个按钮被点了几次，页面里可能同时存在好几个这样的按钮，各记各的数。三，一份配置只能初始化一次，第二次调用别重新计算，也别重复发请求。

现在到了本文唯一需要借用底层结论的地方，我一次说完、不展开：函数的作用域链在它被定义的那一刻就确定了下来，而一份作用域只要还被某个函数引用着，它就不会随着函数返回而销毁。前一句是”静态作用域”的规矩，后一句是垃圾回收的基本事实。完整推导——变量对象与活动对象的两个阶段、执行上下文栈怎么压与弹、被引用的活动对象为什么退不了场——我在《JavaScript 作用域链与执行上下文》里逐条走过，这里只借这两句结论当砖。

陷阱三：在循环里定义函数，时间和内存是真账

不是玄学，实测。两份代码做的事完全等价（求和校验都是 20），区别只在函数定义在哪：A 每个循环轮新建一个闭包并留在数组里；B 函数定义在循环外，循环里只收集数据。

本机 Node（V8 内核，预热三轮、跑 9 轮取中位数）结果：一百万条时 A 约 71.6 ms、B 约 7.5 ms，差了 9 倍多；换 --expose-gc 量持有量，十万条时 A 的堆增量约 11050 KB、B 约 894 KB，差了 12 倍。方向性结论：“每轮一个新函数”的开销主要不在函数调用，而在创建函数对象、为每轮分配一份作用域、以及这份作用域被你留在数组里的代价。所以规矩是：只有当每轮确实需要各自的状态时才在循环里造闭包（要私有，就得付钱）；如果逻辑完全相同，把函数提到循环外，用参数区分轮次。至于”提到循环外是不是就不算闭包了”——当然算，函数照样带着它出生的作用域，只是那份作用域里没有每轮新增的东西。

陷阱六：老 IE 上的 DOM 循环引用（历史事实）

IE 6/7/8 这一代，DOM 节点是 COM 对象、JavaScript 对象走另一套引用计数，两边计数器不互通。一旦”元素属性上挂着闭包、闭包又引用这个元素”，环就永远归不了零——内存表现为一条只升不降的直线，同一个页面在 Chrome 与 Firefox 上却基本平稳。这是当年的真实事故，也是”闭包导致内存泄漏”这句话最早的出处之一。机制推导与规避写法在《DOM 事件移除与内存泄漏》里已经写过，旧文《JavaScript 内存泄漏的常见场景》也把这一条标为历史事实单独复过盘，本文都不重讲。今天（2015 年）还剩的实际影响是两件事：IE 9 起改用标记清除，环本身不再是问题，但可达链照样拖住内存；以及很多老项目仍在兼容 IE 8，那批 onunload 里统一解绑的代码还得上着。

必须说清测试环境：这是本机 Node（V8 内核）测的，浏览器里还要算上 DOM 与宿主对象的差异，各内核、各版本的结果都会变；这些数字只作方向性参考，不能当浏览器指标读，更不能抄进你的团队文档当常数——旧文里那个口径同样适用：真要下结论，就在你真正支持的那几个内核上自己测。

那”闭包变量访问慢”的说法从哪来的？它对得上的是更古老的账：早期引擎的作用域链真是按对象属性一级级查找的，深链确实贵，所以才有”把 document 缓存成局部变量”这条老规矩。而现在能测到的事实是（见陷阱三与陷阱四）：闭包的成本在”创建与保留”，不在”读取”。所以正确的认知是三句话——闭包不慢，它只是让一层作用域活得久一点；要付的账是那份作用域的大小与寿命；真要优化，砍掉捕获的东西（陷阱四）、别在循环里批量造函数（陷阱三），比换掉闭包这个写法本身有用得多。

第一句：”闭包需要三个条件——函数嵌套函数、内部函数引用外部变量、外部函数把内部函数返回出去。” 这个背法不够准确，三处都有反例。不嵌套也是闭包：把匿名函数交给 setTimeout，它照样引用着外层变量：

第二句：”typeof 一个未声明的变量不报错，所以可以用它判断闭包里的变量存不存在。” 前半句对，后半句的用法容易歪。实测：

typeof 沿的是作用域链，在闭包里它先命中闭包那层，链上找不到才退到全局。所以”闭包里用 typeof 判断变量存在”这句话本身没错，但要清楚它判不了两件事：一是”没声明”和”声明了没赋值”，两者都是 'undefined'（需要区分时改用全局上的 in 判断，实测 true / false，这条与旧文《变量提升与函数提升的现象与原理》口径一致）；二是它兜不住成员访问——typeof box.list.length 在 box.list 不存在时照样抛 TypeError，实测报 Cannot read properties of undefined。typeof 的保护只在”单一未解析的名字”这一种形态上成立。

第三句：”闭包只能读外层变量，不能写。” 错得最直接，本文机制一的第二行输出就是写出来的结果（101 变 107）。闭包对外层绑定有完全的读写权。真正的坑不在能不能写，而在写到哪一层：

输出 11 21 形参层=1 21。writeOuter 每次都写到外层那份 outer 上（11、21）；shadow 的形参名叫 outer，它在自己那层把值改成 1，外层纹丝不动——peek 仍然给 21。内层的形参、内层的 var 都会在链上更早的位置命中同名绑定，这就是”我明明写了 count += 1 怎么没生效”的全部原因。还有一处更细的分别：改属性与换绑定不等价。

内层函数如果只是 cfg.theme，它读的是”当前 cfg 指向的那个对象”，所以重新赋值之后所有闭包一起看到新值；反过来，你以为在改共享状态、其实是替换了引用，别人的那份就不会变。

第四句：”闭包会一直持有 arguments。” 需要拆成两句才站得住。内层函数有自己的 arguments 对象，它跟外层的是两个东西；外层的 arguments 只有在被你显式抓住时才会被拖住。实测对比（每份 20 万条对象的数组作为实参传入）：

什么时候用闭包，什么时候别用

该用的场景，按性价比排序：

  1. 需要一份外部改不掉的状态：计数器、开关、”当前选中项”、只初始化一次的配置。
  2. 需要多实例各自的状态：工厂函数返回白名单方法，一次调用一份作用域。
  3. 需要造专用函数：把配置、前缀、格式化规则固定进作用域，业务调用点少传一半参数。
  4. 需要把上下文带进回调：var self = this，或者把上下文当参数交给闭包。
  5. 需要一次性的东西只做一次：once、惰性初始化、时间戳节流里那几个私有变量。
  6. 需要不污染全局的一小段临时状态：套一层立即执行函数，比往 window 上挂名字干净。

不该用、或者要用别的写法：

  1. 需要继承、需要实例之间共享方法：走构造函数加原型，每实例一份闭包方法的内存代价不值得。
  2. 需要跨模块共享、可被替换与 mock 的状态：把它做成显式参数注进来，或者交给加载器，别藏在闭包深处让测试够不着。
  3. 状态可能被外部误改，但逻辑本身要求可插桩：闭包的”碰不着”在这里是缺点，必须自己留一个 reset 出口。
  4. 循环里批量造函数：先确认每轮真的需要独立状态，否则把函数提到循环外用参数区分（实测差了 9 倍时间与 12 倍内存）。
  5. 大列表、DOM 集合被回调顺手引用：先裁成需要的字段再进闭包，销毁时显式断开（置 null、解绑、清定时器成对写）。
  6. 单文件里”闭包私有”与”构造函数实例”混着写：这不是性能问题，是可读性问题——读代码的人得先猜每一层的名字与 this 归谁，选一种风格贯穿到底。

学习路径我给一条明确的顺序，也是本文写作的顺序。第一步，把作用域与执行上下文啃下来：变量住哪一层、什么时候登记、什么时候销毁，链在定义时怎么定死（《JavaScript 作用域链与执行上下文》就是为这一步准备的）。第二步，再理解闭包：它没有新增任何机制，只是”函数带着出生作用域走”这个既有事实的可见结果；这一步要把机制一、二、三背到能默写，陷阱一和陷阱二就不再需要记技巧。第三步，才谈模块化与工程：私有状态、工厂、模块白名单、加载器，全是闭包在结构层面的应用；顺序倒了，人就会把闭包当语法糖来背，面试一追底层就断在”活动对象”这个词上。第四步，加上性能与内存的实测习惯：任何”某某写法慢十倍”的说法，都在你真支持的环境里自己测一遍再写进文档。

最后一句与本文开头呼应。ES6 的块级声明马上就要让”用一层立即执行函数换一份作用域”这个技巧的必要性下降——但那是草案里刚定稿的东西，此刻 IE 9、IE 10 上还跑着我们的埋点，Chrome 40、Firefox 35 的可用面也还没铺开，转译器进主流构建更是没影的事。所以 2015 年的正确姿势没变：把闭包当成本语言的基本事实来用，把新语法当展望来看。
