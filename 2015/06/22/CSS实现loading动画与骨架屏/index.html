CSS 实现loading动画与骨架屏

本文属于《HTML 与 CSS》第 50/62 篇
上一篇系列目录下一篇

等待态是界面里最没存在感、又最容易被写坏的一块。转圈的画法谁都会抄一段，但真放到项目里，问题立刻变成另一批：一个列表页同时跑几十个转圈，低端 Android 上整个界面发黏；占位灰块的尺寸和真实内容差一截，数据一到，页面猛地一跳，用户刚找好的阅读位置没了；loading 亮起来不到一百毫秒就灭掉，闪一下像故障。这些和”会不会写 @keyframes“没有关系，是呈现工程的问题。本文假设你已经把 animation 的时间轴玩明白——属性逐个的讲解、fill-mode 的坑、渲染管线里哪些属性走合成，在《CSS3 animation 与 keyframes 动画实战》里已经拆过，这里一律不重复。我们从选型讲起：一个请求没回来之前，界面到底该拿什么陪用户等，怎么让它不卡、怎么和真实布局对齐、怎么在 2015 年 6 月这个浏览器矩阵里活下来。

三种表达：你知道多少，就说多少

等待态在信息量上分三等。spinner 转圈只说”还在处理”，耗时完全不可知；进度条说”总共这么多、已经走了这么多”，用户能自己估出剩余时间；骨架屏信息最多——内容未到，版式先到。选哪种表达，本质是回答”你对这次等待知道多少”。

按场景套判据基本够用。首屏进入，结构是设计稿里定死的，最适合骨架屏打底、只再留一个全局转圈；局部刷新（点筛选按钮换一块列表），在触发它的控件旁边挂一个小尺寸 spinner 就好，把整块区域盖成灰反而放大”我在等”的焦虑；分页加载”加载更多”，按钮位置原地转圈直到新内容插入；只有上传、下载、解码大图这类总量可测的场景才配得上进度条——总量测不准的进度条比没有更糟，每次假意停在 90% 都是在透支信任。反过来，骨架屏也有前提：版式固定、高度可预知。一个模块连渲染完长什么样都没定，就别给它画骨架，老老实实转圈。

纯 CSS 转圈的四种画法

border 画环：最常用，也最挑环境

原理一句话：给元素四条等宽边框，把其中一边的颜色置成 transparent，旋转起来，缺口扫过圆周，就是转圈。

为什么用 transform: rotate 而不是拿 background-position 转一张圆弧图：旋转只是改矩阵、让合成器搬运已画好的纹理，布局和绘制都不必重做；background-position 也能做出转，但每帧都要重绘受影响的像素，在当年那批双核手机上是肉眼可见的消耗，这笔账《CSS 动画与 JS 动画的性能取舍》里算过。锯齿要留心：border-radius 需要 IE9 才有；圆环的边缘抗锯齿会在旋转中随角度反复暴露，高分屏压得住，低分屏就是一圈沙沙的颗粒。而在 border 与 border-radius 双双失效的环境（IE8、Android 2.x）里，这套写法会退化成一个方块缺口在转，观感全错，所以这条路线必须配静态降级，后面细说。

三点跳动：负 delay 错峰

移动端 App 下拉刷新里常见的三点跳动，用三个圆点加错开的相位，”进行时”的感觉比转圈更强。关键在于错峰靠的是负的 animation-delay。结构上外层容器只负责定位、自己不带任何变换——如果给容器加动画，伪元素会跟着父元素一起位移，三个点的相位就全乱了；两个圆点用 ::before/::after，中间那颗用一个空 <i>：

负 delay 的语义在《CSS3 animation 与 keyframes 动画实战》里讲过：它不是”少等一会儿”，而是让动画按”过去某时刻就已开始”计算，元素一出现就直接落在周期的中段。三个点如果全用正延时，起步各有一段静止，错峰感要等第一轮才建立；改成 0、-0.2s、-0.4s，显示瞬间相位就已经错开。

SVG 描边环：效果好，环境最差

把圆环换成 SVG 描边，让虚线沿圆周走，就是这两年设计圈很喜欢的”呼吸环”：

数字对得上才叫无缝：半径 20 的圆周长是 2πr，约 125.7px，stroke-dasharray: 30 95.7 里一段划线加一段间隔正好拼成一周，stroke-dashoffset 走完 125.7 就回到原位，循环没有跳点。兼容是它的死穴：<svg> 标签要 IE9 才有，iOS 7/8 上 SVG 的 CSS 动画时灵时不灵，Android 4.x 的 WebView 基本不可靠。结论是：描边环只能当锦上添花，底下必须站着一个 border 版兜底，别把主流程押在它上面。

进度条：把 width 换成 scaleX

定量进度条最常见的写法是 JS 每帧改填充条的内联 width。width 是几何属性，每变一帧都走一遍布局，进度更新一密，主线程就跟着抖，等于把重排撒进了整个等待过程。正确姿势是铺一条满宽的填充条，用 transform: scaleX() 加 transform-origin: left 表示进度：

代价是 scaleX 需要前缀：Android 4.x 要 -webkit-，IE10 要 -ms-，IE9 及以下两个都没有，只剩 filter 那套 Matrix 老启发式硬做缩放，不建议投入，给个静态比例条更诚实。另一个代价是变形：条纹背景会被横向拉伸、宽度接近 0 时条纹密成一片。想要 Bootstrap 3 那种斜纹滚动的不确定进度条，周期数值要自己配平：把 repeating 渐变画在一张 40px 见方的背景图上，动画让图沿横轴平移恰好一个图宽，图案就天衣无缝地滚起来。

终点 40px 恰好等于 background-size 的宽，一个周期走完图像严丝合缝回到起点——位移差多少，循环就跳多少，数值自洽是这类动画的全部功课。渐变的完整画法《CSS3 渐变 linear-gradient 与 radial-gradient 实战》里讲透了，只提醒一句：这条动画走的是重绘档，比 width 便宜、比 transform 贵，窄窄一条没问题，别把它铺满全屏。真实进度坚持用宽度表达的，用百分比写内联 width 加节流，别在 onprogress 回调里逐字节写样式，清单在《减少重排与重绘的实践清单》；想用原生 <progress> 拿语义的见《HTML5 progress 与 meter 进度展示》，各内核外观定制差异那篇已谈。

占位骨架：2015 年刚从 App 设计里走出来的新做法

“骨架屏”这个叫法放到今天还为时过早。这套做法 2014 年底随 Facebook Paper、LinkedIn 的 iOS App 设计被讨论开：内容到达之前，先用灰色圆角条摆出版式的骨架，再让一道高光横扫过去。它传到 Web 也就这半年，微博、微信的网页端陆续出现类似处理，中文圈连名字都没统一，叫法还是”占位灰色块””闪光占位””内容骨架”混着用。它出现的原因非常实际：移动网络下首屏数据动辄一两秒，纯色空白页让用户以为页面挂了。骨架把”等待”换成”正在成形”，感知时间能砍下来接近一半。我写下它，是因为我认为它会留下来，而不是因为它已经是标准实践——恰恰相反，绝大多数团队还没做，坑也还没被踩清楚，下面两个就是最先会撞上的。

第一，占位必须与真实内容等高，这是骨架屏的全部工程难点。灰块差 10px 不算什么，数据一到整块内容往下顶，页面猛地一跳，用户滚动位置直接丢失；列表里每行都差一点，跳动感会叠加成”这页很晃”。动手前先从设计稿量出几何：头像 40px、标题行 18px、段落行 14px、行间距 10px，照抄进占位样式，真实组件落地后并排对比一遍。这和《图片懒加载与预加载实现》里”img 必须写 width 与 height”是同一条纪律——一个管图片到位，一个管数据到位。

第二，闪光的实现选什么属性。骨架的”闪”是整个容器的 background：一条透明到半白再回透明的渐变，配 background-size: 200% 100%，动画只改 background-position。不用 left 平移一条高光带，是因为 left 是几何属性，每帧重排，代价高一个档位；background-position 只走绘制。数值周期要自己配平：背景图宽是容器的两倍（记作 E = 2W），按百分比定位规则，100% 对齐 100% 的偏移量是 p 乘 (W 减 E)，即 p = 1 时图左缘停在负 W，高光中心（在图的正中间）恰好落在容器左缘；终点 p = -1 时偏移 +W，高光中心到达 2W，而图案以 E 为周期平铺，2W 处正是下一枚高光回到容器左缘——终点即起点，一个周期走完，无缝循环。中途 p = 0 时高光落在容器右缘，此后半段它在体外移动，正好留出一拍喘息，节奏反而是对的。

想让几块灰错峰地闪，给其中两块负 animation-delay（-0.4s、-0.8s）即可，别复制三份 keyframes。骨架里的图片位配合懒加载只说一句：图片未到位时先放占位色块、宽高照真实尺寸写死，机制在懒加载那篇里，这里不重讲。另外骨架的 CSS 必须内联在首屏 HTML 里——外链样式表还没下载完，骨架屏就根本没机会出现，”先给版式”的承诺瞬间落空。做法与《首屏时间优化实战》里”首屏关键 CSS 内联”是同一条，整体方案见那篇，这里只给骨架片段的内联示例：

一个实用结论：本文这套代码只需要 -webkit- 与无前缀两条线，-moz-、-o- 可以从清单里划掉。真正要花钱的是降级——原则依然是”动画只是装饰”：拿不到动画时，”正在加载”这件事本身必须可见。首选静态文字，不依赖任何新属性；文字都渲染不利索的场景再考虑 GIF。GIF 的代价要算清楚：256 色色板做不了柔和灰阶，Retina 屏上发虚；逐帧动画的体积随帧数线性膨胀，一个 32px 转圈十几帧就是几 KB，CSS 三行解决的事，GIF 要背流量，而且没法跟随主题换色。雪碧图加 steps 逐帧走能省掉重复像素，但 background-position 每帧重绘的账还在，综合不如 GIF 加缓存。用 Modernizr 的 cssanimations 检测挂类名分支，是目前最干净的做法：

性能与时序：数量、最小可见时长、计数撤除

数量控制：同屏同时运行的无限动画，建议不超过个位数。每个转圈元素都是一条动画时间轴加每帧重算，若为了提层还占着一份合成纹理，列表几十行一起转时在 iOS 上的内存压力很具体——合成层超预算的后果《CSS3 animation 与 keyframes 动画实战》里写过。更合理的组织是”区域级一个转圈”：整块列表共用一个居中的 spinner，而不是每个卡片各转各的。动画属性黑名单照旧：不碰 width/height/top/left；也别给转圈加一大圈模糊 box-shadow——阴影每帧参与绘制，动画里的大阴影就是每帧多刷一遍模糊计算。

时序上，三件事必须用 JS 管住。第一，最小可见时长：请求 80ms 就回来时 loading 亮一下灭掉，闪得像 bug；出现后至少驻留约 300ms 再撤。第二，失败也要撤：loading 挂在 success 上、error 分支忘了收尸，界面就永远转圈，统一挂 complete 最简单。第三，并发计数：三个请求共享一个 loading，必须全部落地才停，第一个回来就撤等于撒谎。下面这段 ES5 加 jQuery 1.11 的控制器，三件事一起管住：

选型收口

形态 适用场景 实现成本 性能风险 兼容性
spinner 转圈 不确定等待、局部刷新、分页加载 低，十行 CSS 数量失控时每帧重算叠加；大阴影动画 IE10+，更老环境换 GIF 或文字
进度条 上传下载等可测总量的等待 中，要配平周期数值 width 动画每帧重排；条纹滚动每帧重绘 scaleX 需前缀，IE10 起可用
占位骨架 版式已知的首屏与卡片列表 中高，几何必须严格对齐 大面积 shimmer 重绘偏贵；动画越多风险越高 animation 与渐变都要，IE9 退静态灰块

一句话选型：spinner 是对未知的最低承诺，进度条要求你真的知道总量，骨架屏要求你真的确定版式。知道多少就说多少，说多了都是假的。

小结

这篇没有讲新的动画属性，讲的是更琐碎也更常咬人的事：等待态是三种承诺的选型，是出现与消失的时序，是占位几何与真实布局的严格对齐，也是浏览器矩阵里一条退得回去的路。转圈谁都会抄，但让它在该出现时才出现、全页面同时转的不超过一个、骨架块和真内容一寸不差，这三件事才是”实现”的全部内容。骨架屏眼下还带着试验味，连叫法都没定下来；但”用结构换耐心”这个思路，值得在你的下一个列表页里试一次。
