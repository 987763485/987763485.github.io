CSS 清除浮动的几种方案对比

本文属于《HTML 与 CSS》第 28/62 篇
上一篇系列目录下一篇

2015 年了，页面骨架里仍然到处是浮动。清除浮动这件事，网上教程多如牛毛，但大多写成属性说明书，看完仍然会掉坑。本文换个写法：以一次线上事故和这些年的故障复盘为主线，讲清楚塌陷是怎么发生的、每种清除方案是被哪个坑逼出来的、代价各是什么。至于布局方式从表格到浮动再到 Flexbox 的整体演进与选型，旧文《CSS 布局方式演进史》已经讲过，这里不重复。

从一次线上事故说起

三月底改版上线，首页导航栏出了个蹊跷的故障：测试环境一切正常，生产环境导航下面紧挨着的 banner 被菜单项盖住了一半，banner 上的按钮点不到，用户反馈”页面错位”。

排查绕了一大圈。第一反应是 z-index 打架，翻遍层叠上下文没找到嫌疑；后来把 Firebug 和开发者工具的 computed 面板打开，才看到真相：导航容器 .header-nav 的高度是 0。

机制其实很简单，但人在坑里的时候看不见：浮动元素脱离了常规流，父元素的 height: auto 只按常规流里的子元素计算高度。.header-nav 里唯一的常规流内容就是清一色 float: left 的 li，于是父元素认为”我这儿没东西”，高度塌成 0，后面的 banner 正常顶上来，而浮动的菜单项还按原位绘制——自然就压在 banner 上面。

更迷惑人的是 border 和 background 的露陷方式。容器当时写了 border-bottom 和一条背景色。塌陷后高度为 0，边框照样画：上下两条边叠在容器最顶端，背景也只涂这 0 高的窄条。从视觉上就是”导航的边框和底色凭空消失了，菜单浮在半空盖住内容”。截图发给同事，谁也看不出问题出在容器身上。

还有一个细节值得写进复盘：为什么开发阶段没发现？因为容器里原本有一个隐藏的 span 占位文案，属于常规流内容，容器靠它撑出了高度。改版时文案被删，一段”看起来没问题”的布局代码就在一夜之间失效了。塌陷从来不是浮动引起的，是”容器碰巧有非浮动内容”这种巧合掩盖了它。

三个连带的坑

事故之后我把当年踩过的坑翻了一遍，塌陷只是最显眼的一个，它还有三个容易连带的坑。

其一，相邻的非浮动块会被浮动的宽度”躲闪”。 浮动脱流，但行盒仍然要避开它。于是会出现一种诡异画面：后面那个块级容器整体浮不动分毫、背景照常铺满，可它里面的文字到了浮动元素那一侧就自动缩短——当年叫它”文字环绕”。做两栏时如果只浮动左栏、右栏老老实实待着，右栏背景会直接铺到左栏底下，全靠文字绕开，看源码根本想不通为什么。

其二，外边距合并和塌陷会叠加出场。 先说规范层面的事实：浮动盒不参加常规流的外边距合并，所以两个相邻浮动兄弟之间的 margin-top 各算各的、互不合并。但反过来，当一个浮动元素是容器的第一个子元素、且容器与它之间没有 border 或 padding 隔开时，容器自己的 margin-top 会”穿透”容器被带到最前面，整个容器连带边框一起被顶下去，而浮动元素纹丝不动——外边距合并叠上高度塌陷，间距忽大忽小的悬案多半是这两兄弟合谋的。IE6/7 在这个场景下的行为更混乱，属于历史事实，当年唯一的解法是给容器统一加一行 padding-top 或者 1 像素 border 把通路堵死。

其三，IE6/7 的 hasLayout（历史事实）。 这是 IE 私有渲染引擎的内部属性，不写进任何标准，但支配着老 IE 的行为：一个元素只有”拿到布局”，才会把浮动子元素的高度算进自己。触发方式要么是 width、height、float 这类属性顺带拿到，要么是当年的祖传一行 *zoom: 1（星号 hack，只有 IE6/7 认）。代价不小：拿到 hasLayout 的元素在 IE 里会变成后代元素的包含块，导致 position: fixed 的后代在 IE6/7 下行为失准，z-index 的层叠也动不动出乱子。另一个历史包袱 _height: 1%（下划线前缀只有 IE6 认）原理相同，2015 年接手祖传代码还会见到，新项目绝对不要再写。至于要不要支持 IE6/7/8，这是由项目方和访问数据决定的事，不由前端单方面拍板——本文后续所有方案都默认”可能要背 IE6/7”，不需要背的可以把 IE 相关条目直接划掉。

方案逐个过：从最笨的到推荐的

额外空标签 clear

这是最早的解法，也是唯一一个在所有历史浏览器里都 100% 可靠的做法——clear 属性从 CSS 1 就存在，IE6 到 Chrome 40、Firefox 35、iOS 7/8、Android 4.x 无一例外。

代价同样明确：它是一个无语义的垃圾节点，DOM 里凭空多一个 div；结构与补救分离在 HTML 和 CSS 两个文件里，看 HTML 看不出”这里在清浮动”；最要命的是 JS 动态插入 DOM 的时候，追加内容的人十有八九记得补那个 clear div，事故就藏在”上线三个月后某个异步模块渲染出来的那一刻”。

父级 overflow: hidden

原理是创建一个新的块级格式化上下文，浮动子元素高度被算进来——这段机制旧文《CSS 布局方式演进史》里已经展开，我只讲代价，而且每一条都对应过真实故障：

  1. 它会裁掉一切溢出的东西。 导航里的下拉菜单（哪怕绝对定位在容器内）、卡片上的 box-shadow、表单元素的 focus outline，统统被切。当年有个项目下拉菜单在 Chrome 里”只露出一行”，查了半天才想起父级是 overflow: hidden 清浮动。
  2. 在 IE6/7 里它自己还不够。 触发 hasLayout 的 *zoom: 1 要配上，而 zoom 又会带来上面说过的 fixed 后代与 z-index 副作用。
  3. 改成 overflow: auto 时，容器变成滚动容器。 内容只要溢出一点点，哪怕 1 像素的四舍五入，就会冒出一条滚动条；轮播、表格这类内容宽度不稳定的容器里简直是重灾区。
  4. 好处是 BFC 顺带把首子元素 margin 穿透也修掉了。

一句话：只在”这个容器本来就允许裁剪”的地方用它，比如图片外框、缩略图网格。

父级 overflow: auto / display: table / display: flow-root

overflow: auto 与 hidden 同族，把”裁掉”换成”给你条滚动条”，多数时候更糟，不作首选。

display: table：

表格格式化上下文能把内部浮动包住，但它有性格：元素宽度会像表格一样收缩包裹内容，必须手动写 width: 100% 才恢复块级观感；与父级、兄弟之间的外边距合并行为随之改变，页面节奏跟着乱；而且它不能和 *zoom: 1 这类 hasLayout hack 混用，老 IE 上两种机制打架，表现因引擎版本而异。

display: flow-root：这是理论上最正确的答案——专为”只建立 BFC、不带裁剪、不改宽度”而设计。但必须写清楚：这个属性在 2015 年还不存在，IE、Chrome 40、Firefox 35 全都不认，写了也只是被忽略。这里记下它只是为了别把”后世的正确答案”当成”当年可用的方案”。

:after clearfix，本文的主方案

原理：伪元素生成的盒子排在容器所有子元素之后，它 clear: both，就会被顶到浮动元素的下方；父元素看到”流里有个够高的后代”，高度随之撑开。全程不加一个真实节点，不裁任何内容。

为什么是 :after 而不是 :before：浮动元素排在 before 伪元素后面，:before 清了也白清；只有排在浮动序列末尾的东西才能把它们全部包住。

为什么 display: table 版本比 display: block 版本更常见：其一，content: "" 配 block 会参与行盒计算，某些引擎下容器底部多出约一行行高的空隙，height: 0 能压掉但又是一层 hack；其二，table 显示的元素自成格式化上下文，顺带把首子元素 margin 穿透容器的问题也修了；要彻底一点，业界通行的完整版会连 :before 一起写 display: table，两个伪元素一前一后把上下文封死。注意 IE8 及以下不认双冒号写法，统一用单冒号 :after 是当年的安全选择。

工程上有两种用法，各有取舍：给容器挂 class="clearfix"，好处是随贴随用、一眼可见，坏处是依赖每个人记得贴，DOM 改版漏贴一次就复现事故；用 mixin 在需要的选择器上生成，把”包住浮动”变成样式层对容器的显式声明，类不会漏，代价是 HTML 里看不出这个容器清过浮动，排查时要搜样式表。大团队里我倾向后者，配一条评审规则（见文末规约）。

用预处理器输出

Sass 3.x 里两种写法容易混：

@include 把规则原样复制到每个使用处，产物直白，体积线性增长可预期。@extend %clearfix 是把所有用到它的选择器合并进同一条规则，产物看似更省，但要警惕：占位规则一旦带上多个属性、再被多层选择器继承，选择器组合会膨胀，产物反而变大变难读。clearfix 这种单伪元素规则两种都安全，团队统一用一种即可。

定义时带括号，这个 mixin 本身不会被输出成 .clearfix 类；调用也必须带括号。当年不少人把不带括号的 mixin 当类引用，产物里凭空多出一堆无用规则，就是这么来的。

干脆不浮动

inline-block 天然没有塌陷——元素还待在流里。但把它当浮动替代品，会撞上两个真实代价：

一是 HTML 源码里的空白字符会渲染成大约 4 像素的间隙。三种对策各有坑：父元素 font-size: 0 再在子元素里恢复字号——容易漏恢复，还会殃及容器里正常文字；标签之间塞 HTML 注释——源码丑、模板引擎不一定配合；margin-right: -4px 硬抵——间隙大小跟字号和浏览器缩放有关，写死数值换个字体就崩。二是默认基线对齐导致一行里高度参差，必须统一 vertical-align: top。另外给块元素加 inline-block 在老 IE 上还要补 *display: inline; zoom: 1，等于把 hasLayout 又请回来了。所以它适合按钮组、导航项这种组件内小范围使用，不建议扛整页骨架。

至于 Flexbox：2015 年 6 月的现实是 Chrome 40+、Firefox 35+、iOS 8、Android 4.4 基本可用，但 IE9 及以下完全不支持，IE10 还是另一套中间语法。内部系统或移动 H5 已经砍掉老 IE 的项目，可以用它从根上告别清浮动；把它当整站通用方案，目前还不配。

一张表收尾

方案 兼容范围 新增 DOM 裁剪内容 修 margin 穿透 可维护性 推荐度
clear 空标签 IE6 起全兼容 是 否 否 差 兜底专用
overflow: hidden IE6+（需配 zoom: 1） 否 是 是 中 看场景
overflow: auto 同上 否 出滚动条 是 中 低
display: table IE8+ 可靠，IE6/7 与 hack 冲突 否 否 部分 中 低
display: flow-root 2015 年尚无浏览器支持 否 否 是 — 不可用
:after clearfix IE6+（zoom: 1 配套） 否 否 是 好 首选
inline-block 替代 IE6+（老 IE 需 hack） 否 否 不涉及 中 小范围

结论：首选 :after clearfix 并以 mixin 输出；容器本身就该裁剪内容或做滚动区域时，overflow: hidden 正好一石二鸟；必须照顾老浏览器的页面，保留一个 clear 工具类作为动态插入 DOM 场景的兜底；inline-block 只在组件内部小范围用，别拿它扛骨架。

复盘规约

把这次事故和历年故障换成五条团队约定：

  1. 容器必须显式声明”我包住浮动”——统一走 clearfix mixin，新建布局类选择器默认带上，不靠自觉。
  2. 内容容器里不放浮动。文字环绕现象说明浮动是为图片绕字设计的，不是为分栏设计的。
  3. JS 动态插入 DOM 时，禁止假设”外层已经有 clearfix”。插入点在哪一层、影响不影响容器高度，要在 code review 里单独确认。
  4. 评审看到 overflow: hidden，先问一句”这里会不会有下拉菜单、阴影、focus outline 被裁”。这一问当年省过至少两次回炉。
  5. 新项目里尽量用布局层与内容层分离的结构（外容器定宽、内层排内容）替代”到处浮动到处清”，从源头减少清浮动的点位。

小结

塌陷的根因只有一句话：浮动脱流，父元素只按流内子元素算高度； border 和背景会在塌陷的 0 高盒子上照常绘制，这就是事故截图里”边框消失、内容被盖”的全部真相。围绕它的每种清除方案，都是在”兼容性、垃圾节点、内容裁剪、hasLayout 副作用”四者之间做交换：clear 标签赢在兼容、输在结构；overflow 赢在简洁、输在裁剪；clearfix 是目前综合最优的解，预处理器让它从”记得贴的类”变成”默认带上的声明”。display: flow-root 代表未来，但那是以后的事了。
