CSS3 多列布局 column-count 与分栏

本文属于《HTML 与 CSS》第 34/62 篇
上一篇系列目录下一篇

多列布局（CSS Multi-column Layout）是 CSS3 里最容易被误会的一族属性：看着像能做栏，实际只有两三个场景真正划算。2015 年年中，CSS Grid 的现代语法连稳定实现都还没有，Flexbox 要同时伺候 -ms-flexbox 与 -webkit-box 两套旧语法、IE9 完全不支持，栅格需求仍由 float 把持。可就在这套环境里，多列是唯一能纯 CSS 做到”报纸式纵向填充分栏”的手段：内容先填满第一列，才轮到第二列。这个方向性差别 float、inline-block、display: table、Flexbox 都给不了——它们全是横向排列。本文讲清机制，重点放在性能与调优：哪些场景划算，哪些场景代价大，以及怎么量。

先声明：兼容性整理自规范与 Can I use 的公开数据，示例结构做过静态检查，但没有做浏览器实机验证，所以全文不写”某方案快多少毫秒”这类数字，只给自测方法。

多列的本质：列盒是引擎生成的匿名块

给块级元素加上 column-count，它就建立了多列上下文：内部并没有你写的栏，而是引擎按可用宽度切出 N 个匿名列盒，再把子元素依次灌进去。内容流是纵向的——第一列装不下才溢出到第二列顶部，全部列装满后容器才继续往下长。

所以它解决的是”连续内容怎么折成几栏读”，不是”几个独立模块怎么并排”。《CSS 布局方式演进史》称多列为”被跳过的中间路线”，指的正是它不竞争页面骨架、只服务文字流。

属性族：逐个属性配一个最小例子

columns：简写与两个 auto

columns 是 column-count 与 column-width 的简写，两个值不分先后：

两个属性的初始值都是 auto，都 auto 时就是单列，即普通块容器。同时给出列数与列宽时，列宽的语义是最小宽度：可用宽度记作 W（已扣内边距），gap 取 column-gap 的计算值，列数 n = min(column-count, max(1, floor((W + gap) / (column-width + gap))))，每列实宽再回算成 (W - (n - 1) * gap) / n。间距参与取整这点容易忘：gap 越大，同样的 column-width 越早掉到更少的列。各家在取整细节上有出入，这条公式用来说明行为，不用来写像素级断言。

column-gap：默认 normal 约等于 1em

normal 按 1em 落实，所以字号大的正文默认栏距比你以为的宽。栏距只存在于列与列之间，最后一列右侧不带间距；column-gap 不接受负值。

column-rule：不占列宽的分隔线

简写顺序是 宽度 样式 颜色，与 border 一致。注意 column-rule-width 初始值是 medium，而 column-rule-style 初始是 none，所以只给宽度或只给颜色都不会有线，样式必须显式写。关键特性是规则线画在栏距里，不参与列宽计算：1px 的线不会让某栏比别栏窄 1 像素，float 里那个”加边框要配 box-sizing 或手动减 1 像素”的坑在这里不存在。用渐变在容器背景上画分隔线那套路数，结论已在《CSS 实现自适应等高列布局》推过，不重复。

column-span：当时只有 all 有用

column-span 只有 none 与 all。跨列元素会切断所在列盒：它之前的内容平衡排布，之后的内容重新从下一列顶部开始平衡，规则线在它的位置断开。这是”分栏里放通栏标题”唯一的纯 CSS 写法。约束在支持面：写作本文时只有 WebKit 系与 IE10 以上认它，Firefox 不认，标题会退回”待在某一条列里”。设计上要能承受这个退化。

break-inside：三个写法一起写

avoid 要求引擎不要在块中间断开，对”一条 FAQ””一个图注”几乎必写。当时的前缀现实就是三条并列：老 WebKit 只认带前缀的，IE 与打印走 page-break-inside，标准属性留给新内核，不认识的那条会被安静丢弃。

column-fill：balance 与 auto，被忽略的那个开关

balance 均分内容求等高；auto 则是填满为止——给定容器高度后第一列按该高度装满，剩下的进第二列。上面这个 .reader 就是很多人不知道用法：固定高度加 auto 配横向滚动，能做”像翻页一样横着读”的面板。但实现不一致：当时 IE10 以上与 Firefox 认 auto，Chrome 与 Safari 多数情况仍按 balance 处理（Blink 有长期未修的分栏填充问题）。所以它只能当增强，不能当唯一交互路径；哪版真正生效请以你自己的页面为准，本文没跑过。

三个陷阱：顺序、分页与滚动

一，左右并排的表单字段不能用多列。 这是把多列当栅格用最常见的事故。源码里”姓名、手机、城市、邮箱”四个字段，视觉要 2 行 2 列，多列给的是纵向填充：第一列装”姓名 + 手机”，第二列装”城市 + 邮箱”，读起来变成上下配对，Tab 顺序与视觉分组彻底错开。这类需求只能用 float、inline-block 加行容器或 display: table。多列只在内容本身是线性流、分栏只是把它折起来读时才安全。

二，长列表配 column-count 会打乱分页语义。 分页或无限滚动每追加一批条目，整个列盒就重新平衡一次：原本”第一页 20 条等于两列各 10 条”的视觉承诺失效，条目在列间整体漂移，用户得回头扫上一列；”第 3 页第 5 条”这类说法与屏幕位置不再稳定对应。列表要分栏就交给行容器，哪条属于哪一行写死在结构里，别交给引擎均分。

三，column-fill: auto 加固定高度的分栏滚动看着聪明其实脆。 固定高度在小屏会裁内容，横向滚动的可读性也远不如纵向。真要横向翻页读长文，宁可上脚本按页切内容。

降级分两层。第一层不在结构上做强行模拟：长文分栏在 IE9 与 Android 2.x 上退回单列，把行长压进可读范围即可，这比手工把内容劈成两列诚实得多。

第二层是等宽并排内容的平面版，float 与 inline-block 两套：

inline-block 的空白间隙与基线问题已在《CSS 布局方式演进史》展开，不复述。要提醒的是这两套降级与多列填充方向相反：float 版横向配对，多列版纵向填充，同一份内容在两边读序不同。所以降级只适合条目彼此独立、顺序不承载语义的内容；表单与编号步骤这类有顺序语义的，别在同一页面混用两套。

性能账：什么时候划算，什么时候贵

分栏是布局计算，别放进高频交互

改一次 column-count 等于让整棵子树重新排版：列盒数量变了，每个子块要重新决定落在哪一列、断在哪里。这是典型的重排（reflow）触发点，比改颜色、改阴影贵一个量级。第一条纪律因此是：不要在滚动、拖拽、resize 回调里动态改列数，栏数交给 @media，浏览器自然只在合适时机算一次。用脚本写 element.style.columnCount 再配 resize 监听，等于把一次布局摊成几十次，中间夹的 offsetHeight 读取还会造成强制同步布局。同一个坑在《DOM 操作性能：批量插入与重排优化》里以 float 多列的形式复盘过，结论是读写交错会把线性开销放大到接近平方，那份账单不复述。

balance 要预知内容高度，长文是最贵的输入

column-fill: balance 的目标是各列尽量等高，而要均分高度，引擎得先知道内容总高，再迭代试排出断点方案。内容越长、参与断开的块越多，试排越吃力；容器若是流体宽度（响应式页面默认如此），窗口每变一次宽度就重跑一遍。这是多列在桌面站最容易被感知为”卡”的地方，而且它不是 bug，是算法固有代价。对策按代价从低到高：

  • 只在打印样式里分栏：打印布局只算一次，没有 resize 骚扰，收益最高、成本最低。
  • 限制分栏容器长度：只给正文首屏那段分栏，后面小节恢复单列，试排输入规模立刻降下来。
  • 用 column-fill: auto 加固定高度：断点由高度直接给出，跳过猜等高的迭代——前提是这颗开关在你的目标浏览器上真有效。
  • 固定容器宽度：流体宽度是分栏最贵的组合，定宽居中版好算得多。
  • 别在分栏容器里做动画：容器内每次动画都推着引擎重跑分栏；动效交给 transform。

断裂、图片与规则线的绘制成本

图片跨列断开会拆成两段绘制，滚动时容易看到边缘错位，视觉上也像 bug。表格同理，而且表格在分栏里的断行行为各家差别很大，建议干脆不要把表格放进分栏容器。给 figure、li 写 break-inside: avoid 能挡住断裂，但这是往试排里多塞一条约束：块越大，越容易把某列顶出多余空白，甚至让”尽量等高”退化成”某列特别短”。所以图文混排的长文里，宁可让图整块落到下一列顶部，也别让半屏高的块参与平衡。至于分隔线，column-rule 由引擎画在栏距里、零额外节点，float 方案则要么让边框吃掉列宽，要么多套一层元素——省掉的这一层 DOM 就是多列的固定收益。

与 float 方案的成本对照：节点数是可以数的

以最合适的场景之一”两列 FAQ”为例，60 条彼此独立的问答：

  • 多列版：1 个 .faq 容器加 60 个 .faq-item，合计 61 个 div，零行容器，列的切分由一行 columns: 2 决定。
  • float 行配对版：1 个 .faq、30 个 .faq-row、60 个 .faq-cell，合计 91 个 div。多出的 30 个节点正是那 30 个行容器（60 条两两配对）。

按 <div class="faq-row"> 加闭合标签 27 字节计，30 个行容器约 810 字节未压缩体积；我在 node 里生成这两份 HTML 字符串统计过，同样的差异 gzip 后只剩 32 字节。所以真正的收益不在字节，而在结构与维护成本：条目从 60 增到 61，多列版什么都不用改，float 版要么手工重排 31 组配对、要么留一个空格外；栏数从 2 改到 3，多列版改一个数字，float 版要重算百分比宽度并同步间距。另一条 float 路线是只加两个列容器把内容劈成两半（63 个 div），节点更省，但”哪条属于哪一列”从此写死在结构里，内容一增删就得重新平衡。上面这些数都是逐个数出来的，不是凭印象。

结论一句话：文章、长文本、章程、报纸式阅读流加打印，用多列；卡片网格、等高组件、表单并排字段，不要用多列。 多列是排版方案的候选，不是布局方案的候选：内容是一条线性流就折它，模块彼此独立就别折。需要等高的那部分，去看《CSS 实现自适应等高列布局》。

小结

多列的机制一句话：引擎生成匿名列盒，内容纵向填充，默认尽量等高。属性族里天天用的是 columns、column-gap、column-rule 三个；column-span 受 Firefox 支持限制，break-inside 要三行并列，column-fill: auto 依赖实现且各家不一致。性能故事同样单纯：分栏属于布局计算，balance 要先知道内容总高，于是长文加流体宽度加频繁改栏数是它最贵的组合；栏数交给媒体查询、分栏范围限制在正文、最强一档留给打印，代价就压得住。它与 float 的取舍不必比像素，上文的节点统计已经给结论：结构更平、改栏数更便宜，但给不了横向配对与等高控制。把它当排版工具而非布局工具，这条边界认清之后，多列就不再是”CSS3 里没人用的属性”。
