JavaScript 类型检测的完整方案

上一篇《instanceof 与 typeof 的原理与局限》把两个运算符的机制讲透了，那部分本文不再重复，只引用它的结论。机制之外还有半件事：工程里真正耗时的从来不是”typeof 返回哪个字符串”，而是”这个判断该交给哪种手段、它判不了的那一半谁来补”。本文就站在这个位置上，把类型检测拆成四个互不替代的问题，说清每种手段的适用边界，对照 underscore 1.7.0 与 jQuery 1.11.3 的真实实现，最后交出一套 ES5 的判定工具集和一张选型决策表。文中所有结论、包括两个库的行为差异，都在 Node 里跑断言验证过；只有当年 IE 才有的行为会明确标注为历史事实。浏览器基线是 IE 6 到 IE 11 加上 Chrome 40、Firefox 35 这一代桌面浏览器：ES6 刚刚在 2015 年 6 月定稿，生产代码仍然只能用 ES5，所以本文所有代码都是 var 加函数。

类型检测是四个问题，不是一个

把”检测类型”当成一个动作，是所有混乱的起点。实际需求是四种，它们的答案由不同手段给出，互相不能替代：

问题 问的是什么 手段 判不了什么
Q1 它是哪种原始类型 typeof 一切对象内部的种类
Q2 它是哪个内置对象 Object.prototype.toString 标签 自定义类型、宿主对象
Q3 它是哪个构造函数的实例 instanceof / isPrototypeOf 原始值、跨 realm 的对象
Q4 它是不是某个业务形状 鸭子类型、品牌标记 需要语言层保证的场合

Q1 要判 string、number、boolean、undefined 这四种原始值再加上 function（函数严格说是对象的一种，但 typeof 能单独把它认出来），这是 typeof 唯一可靠的主场。Q2 要判 Array、Date、RegExp、Error、arguments 这些内置对象，typeof 一律给 'object'，得靠标签——顺带说一句，Map 与 Set 此刻还停在规范草案里，浏览器基本用不上，标签法也就判不到它们。Q3 是”这个对象是不是我用 new 造出来的那种”，只有原型链能给答案。Q4 最容易被忽略：我要的不是语言层的种类，而是”它有没有 then 方法””它是不是我库里那个 Widget”，这一层的判据是我自己定的接口约定，语言层根本不知道我的类长什么样。

每种手段的工程边界

机制细节在前一篇已经写完，这一节只列”用的时候要知道”的部分。

isPrototypeOf 是 instanceof 的等价手写版，Foo.prototype.isPrototypeOf(obj) 与 obj instanceof Foo 在同一个 realm 里给出完全相同的答案，区别只在左边写法更啰嗦、右边可能被 TypeError 伺候。它和 instanceof 共享同一个致命边界：跨 realm 一样返回 false，实测 iframe 里造的数组对主页面的 Array.prototype.isPrototypeOf 同样说不。所以换写法解决不了问题，要解决的是”跨 realm 时靠什么”。

constructor 判断（obj.constructor === Array）看着省事，实际比 instanceof 更脆，三条实测理由：原型被整体替换后它会和 instanceof 给出相反的答案，旧实例的 constructor 仍指回原来的构造器、instanceof 却已经变成 false，两个判据各错一半；对象字面量继承来的 constructor 指向 Object，任何改写原型而忘了补 constructor 的类，其实例会被认成普通对象；Object.create(null) 的裸对象根本没有 constructor（实测 undefined），而老 IE 的宿主对象同样经常缺这个属性，读它就等着抛错。最后还有一条：{constructor: Array} 这样的字面量能直接伪造它，实测 fake.constructor === Array 为 true 而 Array.isArray(fake) 为 false。结论是 constructor 只能当作提示，不能当作判据。

数组判定不需要讨论，一律 Array.isArray：它对跨 realm 可靠（实测 vm.runInNewContext('[1,2]') 返回 true），标签法只是它的兜底。IE 9 起可用，IE 8 要垫片：

toString 标签有个必须写进规约的历史坑：IE 6、7 里 Object.prototype.toString.call(null) 与 .call(undefined) 返回的是 '[object Object]'，不是 [object Null]、[object Undefined]（历史事实，今天的引擎复现不出来）。这意味着凡是基于标签的判定，在老 IE 上会把空值认成对象。工程规则因此只有一条，而且必须前置：任何类型判断之前，先处理 value === null || value === undefined。要么显式判，要么交给 value == null 这一句，要么像下面的工具集那样把它封进标签函数里，别让它散落在业务代码的每个分支。

DOM 节点用 nodeType 加 nodeName，不要用 instanceof Node 也不要信标签。原因有两层：老 IE 里 toString 对同一个 div 给 [object Object]，别的浏览器给 [object HTMLDivElement]；而跨 iframe 传进来的节点，对主页面的 Node 构造函数 instanceof 必然 false。nodeType 是个数字属性，走的是 Q4 的路子——按接口特征认人，恰好是唯一在两个方向都稳的判据。将来 Symbol.toStringTag 会让对象自定义标签，宿主判定的口径有望统一，但 2015 年 6 月的今天指望不上。

纯对象。参数归一化里的 defaults(options) 必须只接受字面量对象，否则一个 Date、一个数组、一个组件实例都会被当成配置项逐键合并。完整条件有四条：非空、标签是 Object、原型链能走到 Object.prototype、不是宿主对象。实测五种输入的判定差异：

输入 标签 T.isPlainObject 说明
{}、{a: 1} Object true 字面量，链顶是本 realm 的 Object.prototype
new Foo() Object false 原型上没有 isPrototypeOf，判定为自定义实例
Object.create(null) Object true 裸对象，字典语义，按普通对象放行
[1, 2] Array false 标签这一关就挡掉，不进原型检查
new Date() Date false 同上

前四种口径与 jQuery 的 isPlainObject 一致（实测对比过），差别在于跨 realm：别的 realm 里 new Foo() 的实例标签是 Object、链顶是那个 realm 的 Object.prototype，constructor.prototype 上有 isPrototypeOf，于是所有同类实现都会把它误判成普通对象，jQuery 也一样。这是 2015 年无人能绕开的边界，写文档时要坦白。

defaults 里还有一条容易写错的：合并嵌套对象时不要回填源对象。实测先写 src[key] = defaults({}, src[key]) 再 target[key] = src[key]，两者指向同一个新对象，后续深合并就把默认配置本身改脏了；正确写法是只往 target 上放副本，实测 base.nested 在合并后仍保持 {x: 1}。

slice.call 在真数组和 arguments 上是引擎的快路径，比手写循环快；对”普通对象挂下标”这种伪装类数组则慢一个数量级，规模越大越明显。老 IE 上还有更硬的一堵墙：对某些宿主集合调 slice.call 会直接抛异常（历史事实）。jQuery 1.11.3 的 makeArray 走的正是后一条路——先 isArraylike( Object(arr) )（第 413 行，特意把原始值包一层，否则 in 就抛了），再交给 jQuery.merge 的下标 while 循环（第 451 到 456 行），第 459 行还留了一段注释，为 IE 9 以下把 NodeList 的 length 读成 NaN 的情况补了兜底。工程口径于是很清楚：入口转 arguments 用 slice.call，转任意类数组用手写循环。

jQuery 1.11.3 的取向不同：它把标签先翻译成小写名字再比较。jQuery.type 对空值直接 obj + ''（得到 'null'、'undefined'），对象和函数查 class2type 表，其余退回 typeof。这张表在 567 行只登记了九个名字，没有 Arguments，所以实测 jQuery.type(arguments) 是 'object'——一个 underscore 能答对、jQuery 答错的例子。isFunction 是 type(obj) === 'function'，它上方 252 到 254 行的注释解释了来历：自 1.3 起不再支持 DOM 方法与 alert 这类宿主函数，它们在 IE 里返回 false（issue 2968）。在那之前，源码里为了兜住老 IE 中 typeof 报 'object' 的宿主函数，写过 typeof obj === 'object' && typeof obj.call === 'function' 这种特征检测，1.11.3 已经不这样写，只留下注释作为痕迹（历史写法）。其余几个：isWindow 是 obj != null && obj == obj.window，靠自引用认窗口，实测替身对象通过；isNumeric 写成 !isArray(obj) && (obj - parseFloat(obj) + 1) >= 0，实测 isNumeric('0x10') true、isNumeric([2]) false、isNumeric('') false，是典型的”用算术做校验”，可读性差但能挡脏值；isArraylike 是模块私有函数，入口不做防御，实测对 'abc' 和 5 直接抛 TypeError，因为它第一句就是 "length" in obj，而 in 的右边必须是对象——公共 API 要暴露这个能力，得像本文的工具集那样先挡原始值。

两家最常被拿来对比的是”undefined 算不算对象”。实测口径是这样：_.isObject(undefined) 与 _.isObject(null) 都是 false，因为 isObject 走 typeof，而函数是 true；jQuery 根本没有 isObject，最接近的写法是 jQuery.type(x) === 'object'，它对 undefined 同样 false，对函数也是 false。答案的分歧点其实在函数上，来源是两套口径：ES 规范把函数视为对象的子集，underscore 照这个语义让 isObject 接纳函数；[[Class]] 把 Function 单列成一个标签，jQuery 照标签分类，函数就不再是”object”。同一句”它是不是对象”，问 Q1 与问 Q2 会得到不同答案，这正是第一节要拆四个问题的现实意义。

什么时候干脆不要判类型

工具集越顺手，越容易在每个函数门口都摆一道校验，最后代码长成防御性迷宫。我的口径是收敛到边界：只在公共 API 的入口校验参数，报错要响、要带上下文；模块内部的函数靠约定和单元测试，不重复判类型，内部校验出错时该修的是调用方而不是加一条分支。同理，typeof x === 'object' 这种半吊子检查（null 也过）应该直接删掉，而不是补一句 null 判断继续留着。判类型换来的安全感是有价的：每个 if 分支都要有测试覆盖，每个 isArrayLike 分支都要有人记得下标语义，多一条分支就多一条会腐烂的路径。真正需要区分的只有 Q4 那种”接口形状”的判断，以及跨 realm 边界上必须容错的地方，其余场景，写清楚函数只接受数组，比写一段”数组和类数组都行”的检测便宜得多。

小结

类型检测不是一个动作而是四个问题：原始类型问 typeof，内置对象问标签，实例归属问 instanceof 或品牌标记，业务形状问接口探测。四者的边界各不相同，越界的判据就会给出看似合理的答案——constructor 在原型替换后与 instanceof 相反，标签在老 IE 里把空值认成对象，isArraylike 在原始值上抛 TypeError。underscore 与 jQuery 的实现差异告诉我们，同一句”是不是对象”在两套口径下会有不同答案，所以库里落地的判定函数必须逐个写清语义、逐个跑断言。业务代码不该自己发明判断，把它交给一份测过的 T，四个问题各归各位，剩下的分支就该被删掉而不是继续堆。
