JavaScript 继承的几种实现方式

上个月给内部表单控件库做重构，我把一个类的继承写法从 Dog.prototype = new Animal() 换成了寄生组合式，代码少了不到十行，却顺手修掉了两个线上问题：一个是下拉框的选项数组在两个控件之间互相污染，另一个是有个控件的 render 方法在某次热更新之后死活取不到。这类问题的根源不在业务逻辑，而在于我们对「继承」这两种字的实现方式选错了。

ES5 里能写出来的继承方案有七种，网上把七种罗列一遍的文章很多，但几乎都不回答工程师真正要问的那两个问题：这种写法会在真实项目里引出什么 bug，什么场景才该用它。这篇就按这个口径来写。prototype、__proto__、constructor 三者的关系和属性沿链查找的规则，《JavaScript 原型与原型链完全解析》里已经推导过；new 的四步拆解在《new 操作符到底做了什么》；Object.create 的第一个参数校验、第二个描述符参数和 IE8 下的 polyfill 在《Object.create 与对象继承》。这三篇的结论本文直接拿来用，不再重讲。下面所有输出都在 Node 0.12 与 Chrome 42 里跑过，代码全部是 ES5，IE8 需要额外注意的地方我会单独标注。

一、原型链继承：共享来得太容易

最省事的写法，直接把一个父实例赋给子原型：

arr 根本不在 sub2 自己身上，它在子原型那份唯一的对象上。所有子实例读写的是同一个数组，sub1.arr === Sub.prototype.arr 实测为 true。这就是我在开头说的选项数组污染的成因——下拉框 A 往 options 里 push 一项，下拉框 B 也跟着多了一项，而且这类 bug 复现路径依赖实例化顺序，测试环境很难稳定重跑。

第二条缺陷更硬：无法向父构造函数传参。

new Sub2('bob') 的参数在子构造里没人接，父构造只在建立原型那一次被调用过，拿到的是 undefined。想传参只能把父构造里那几行赋值在子构造里重抄一遍——那已经不是继承了。

工程上我的判断是：这种写法只在「父构造完全没有引用类型属性、只有纯函数行为」时才可用，而这种父构造几乎不存在。真要用，就把 Sub.prototype = new Super() 换成第六条那种只接原型不调构造的做法。它唯一的优点是 instanceof 两条链都对，代价是共享风险失控，不划算。

二、借用构造函数：参数能传，方法全复制

为了传参，把父构造当普通函数调一次，this 指到子实例上：

三行输出对应三个缺陷。第一，say 是构造时新建的闭包，每个实例一份。我数了一下：连开 100 个实例，函数对象就产生 100 个；同样的方法挂到原型上，100 个实例拿到的是同一个函数对象。表单控件一屏十几个还好，列表类组件一次实例化几百行，内存和 GC 都得掂量。第二，也是这篇文章里最想提醒的一条：SuperA.prototype 上的方法子类一个都拿不到。因为继承是靠 call 搬运构造体内的赋值完成的，原型链压根没接上，父类后来在原型上补的方法（库最常见的扩展方式）全部丢失，只剩 Object.prototype 上那几个原生方法可用。很多老代码里「明明父类有这个方法，子类调就是 undefined」，八成是这个原因。第三，a1 instanceof SuperA 为 false，任何靠 instanceof 做类型校验的公共逻辑都会静默放行。

它适合的场景很窄：只需要复用父类「实例属性」那段初始化逻辑，且不依赖父原型上的行为。写 Super.call(this, args) 做属性委托时，务必确认父构造没有把行为挂在原型上。

三、组合继承：最常见的写法，也是最贵的

前两条合起来，既接原型又调构造，这就是《JavaScript 高级程序设计》里那种标准组合继承：

callCount 把缺陷量化了：造第一个实例，父构造跑了两次；造两个实例，跑了三次。多出来那次发生在建立原型的时候，它把一份默认的 name 和 arr 留在了 SubC.prototype 上。实测 SubC.prototype 的自有键是 name、arr、constructor，而 SubC.prototype.name 是 default、c1.name 是 alice——同一份语义的属性存在两个位置，实例属性遮蔽原型属性。

遮蔽本身不会报错，所以它藏得住。真正的代价有两处。一处是内存和构造开销：父构造每次实例化跑两遍，父类属性越多浪费越明显；如果父构造里有副作用（往全局注册表 push、new Date() 打时间戳、发一次埋点请求），那次「建原型」的调用会白跑一遍副作用，我在旧项目里见过因此多上报一次曝光的例子。另一处是排查成本：读到 this.arr 时你不知道取到的是实例上那份还是原型上那份，改动时容易误伤。

组合继承在 2013 年前后是各家库的主流写法，兼容性最好、instanceof 正确、方法共享也正确，团队里新人一眼能看懂。问题只在多出来的那次父构造调用。要是父构造没有副作用、属性也不多，它能用；但既然第六条只是把 new Super() 换成接原型这一行，就没有理由继续留着它。

四、原型式继承：没有构造函数的继承

不写构造函数，直接以一个现有对象为原型造新对象：

Object.create(o) 是它的标准版，参数规则与 IE8 的缺失怎么处理，《Object.create 与对象继承》里写全了，这里只当工具使。

要注意它把第一条的共享问题放大了：没有构造函数，就没有「每个实例自己初始化一份」的机会，所有差异都得靠调用方手动赋值，而所有引用属性天然就是 base 上那一份。同时因为没有具名构造，b1.constructor 落到 Object，任何 constructor 判型的代码都会误判。

它的合理定位是「一份模板配多个只读副本」：配置对象、主题色板、默认参数表。只要副本不写回引用属性，它比任何继承都简洁。反过来，一旦每个副本要往模板里的数组或对象写东西，它就是最难查的那类 bug——三个地方看起来毫不相关的代码共享了同一个数组。

它本质上是在手写组合：接原型靠 object()，加行为靠工厂里那几行赋值，而加进去的方法每个副本一份（实测 p1.mark === p2.mark 为 false），第二条的复制缺陷一条没躲开。

那它什么时候值得用？「对象不是你写的那个」的时候。第三方库返回一个实例、宿主给的对象、DOM 节点，你没法改它的原型（改 DOM 节点的原型在老 IE 上直接抛错，跨 iframe 改宿主原型的可见性也别扭），只能包一层工厂往外挂方法。jQuery 的对象增强、各类 wrap 适配器走的都是这个路子。除此之外不要用它，它没有构造语义，做不了正经的类层次。

六、寄生组合式继承：本文的默认写法

把第三条那次多余的父构造调用去掉：原型只做链接，属性初始化只在实例化时跑一次。

三条实测结论。第一，父构造只跑一次，Animal.count 造一个实例就是 1，Dog.prototype 的自有键干净得只剩 constructor，Object.getPrototypeOf(Dog.prototype) === Animal.prototype 为 true。第二，sleep 挂在父原型上，两个实例拿到同一个函数（d1.sleep === d2.sleep 为 true），第三条的复制开销也没有了。第三，Dog.prototype.constructor = Dog 这一行的实际影响比很多人以为的小：修与不修，d1 instanceof Dog 都是 true。因为 instanceof 沿原型链找 Parent.prototype 这个对象，跟 constructor 这个普通属性没有任何关系。它只影响两种代码：显式写 obj.constructor === Dog 判型的，以及调试时靠 obj.constructor.name 认对象的。前者在老库里不算罕见，所以这一行还是得写，但要写对理由——它是给「读 constructor 的代码」兜底，不是给 instanceof 兜底。

IE9 以上可以直接 Dog.prototype = Object.create(Animal.prototype)，加上 constructor 一行更短；上面 F 那三行等价，且不依赖 Object.create，IE8 也不用背 polyfill。团队里我建议统一用 inheritProtoType(Child, Parent) 这个辅助函数，理由不是性能而是可读性和收敛——把写法收进一个函数，新人不会写歪，日后要换实现只改一处。

八、七种写法对照表

写法 能否向父构造传参 方法是否共享 父构造调用次数 引用属性共享风险 instanceof 可靠性 新人上手成本
原型链继承 否 是 接原型时 1 次 高，全实例共用 父子都对 低
借用构造函数 是 否，逐实例复制 每实例 1 次 无 对父类失效 低
组合继承 是 是 每实例 2 次 中，原型留一份默认值 父子都对 低
原型式继承 无构造函数 是 不调用 最高 只认 Object 中
寄生式继承 靠工厂参数 否，逐对象复制 不调用 高 只认 Object 中
寄生组合式继承 是 是 每实例 1 次 无 父子都对 中
混入 不适用 是（同一函数对象） 不调用 低，但浅拷贝会共享嵌套引用 不参与 低

九、工程结论：我们团队的继承规约

第一条，默认且推荐写法是第六条寄生组合式，统一走 inheritProtoType(Child, Parent) 辅助函数，constructor 那行必须写在辅助函数里。

第二条，构造函数与原型只在定义阶段写完，运行期禁止整体替换 Sub.prototype。这条不是洁癖，是实测过的事故：

一次整体赋值，旧实例的 instanceof 当场变成 false，它还挂在被抛弃的那个旧原型对象上，调出来是三年前的行为；新实例则直接失去 tip。这两个方向同时坏，日志里还都看不出关联。要加方法就 Sub3.prototype.newMethod = fn 逐个追加，别拿对象字面量覆盖。

第三条，继承深度上限两层。到第三层还想要更多行为时，一律改混入或委托，理由见第七节的真实重构。

第四条，类型判断。库内部用 instanceof，跨 iframe 与宿主对象的场景不可靠，那部分规则在《instanceof 与 typeof 的原理与局限》里已经讲透，本文不重复。

第五条，不要为了「看起来面向对象」造基类。判据很简单：如果一个基类只提供两三个空方法和一个 init，删掉它，把需要的行为做成混入或者一个返回对象的工厂。基类的价值在于约束契约，不在于让 new 看起来名正言顺。

回头看开头那两个 bug：选项数组污染来自第一条那种「拿父实例当原型」，render 取不到来自第二条那种「父原型上的行为接不住」。这两个缺陷都不是靠多读一遍原型链的推导能避开的，只能靠把每种写法的失效边界摊开对照。这也是我把选型结论写死成规约的原因——继承写法这种东西，团队里只要允许两种以上，迟早有人踩到边界之外的那一侧。
