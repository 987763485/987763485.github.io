HTML5 与 SEO：结构化数据与微数据

本文属于《HTML 与 CSS》第 7/62 篇
上一篇系列目录下一篇

结构化数据常被当成 SEO 的玄学清单，但它在工程上其实是页面信息架构的一部分：内容模型里有哪些字段，哪些字段值得让机器读，用什么语法写出去，写错了怎么在构建期拦住。本文以课程详情页为例，讲三种标注语法的选型依据、内容模型到 schema.org 的字段映射设计，以及服务端生成与 Grunt 构建期校验的落地流程，适合正在给内容型页面上富摘要、但被“到底标哪个属性”折磨的模板开发者。结论先放在这：语法站内只选一种，映射集中管理，标注必须由服务端输出。

三种语法与一个选型结论

浏览器与爬虫读 HTML 时只有文本，结构化数据要做的是在文本之外再给出一份“带类型的键值对”。2015 年的今天，主流语法有三种，都服务于同一套词汇表。往前追脉络：2004 年前后微格式社区用 class 名做标注（hCard、hCalendar），受限于 HTML 4 只能拿 class 当属性用；2009 年 Google 推出富摘要（Rich Snippets），最初只认评论、事件、商品三类；2011 年 Google、Bing、Yahoo 联合发起了 schema.org，把各家词汇统一，Yahoo 自家的 Search Microformat 与 Bing 的支持也逐步并入这套体系；2013 年 11 月 schema.org 增加 JSON-LD，成为继 microdata、RDFa 之后的第三种语法。至于 Open Graph（Facebook 2013 年公开文档）与 Twitter Cards（2012 年起），它们服务的是社交分享卡片，语义目标与搜索标注不同，不要混为一谈，但也互不冲突。

三者的工程差异如下：

维度 microdata RDFa 1.1 JSON-LD
写在哪 现有标签的属性上 现有标签的属性上 独立的 script 块里
是否需要感知 HTML 结构 需要，itemscope 的嵌套跟着 DOM 走 最需要，还要理解前缀与关系 完全不需要
与模板引擎的配合 改动最小，模板里加属性即可 同类，但团队要先学一套表达力过剩的规范 极好，一个数据对象一次生成

选型结论很朴素：内容型页面（详情页、列表页）就地用 microdata，标注贴着可见内容走，模板改动最小、不容易出现“标了但页面上没有”；由服务端集中渲染、字段来源复杂的页面用 JSON-LD，在数据层一次生成；同一个页面绝不混用，混用后两份标注一旦互相矛盾，解析器怎么合并各家策略并不一致，测试工具里看到的也未必是你想要的那份。本文两种都给出可运行的写法。

架构主线：内容模型到 schema.org 的映射

标注的源头是内容模型，不是页面。先把这一层关系想清楚，再动手写模板：

flowchart TD
    A[内容模型 数据库字段] --> B[schema-map 映射表]
    B --> C[服务端模板]
    C --> D[microdata 就近标注]
    C --> E[JSON-LD 集中生成]
    D --> F[测试工具抽查]
    E --> F
    F --> G[抓取结果记录与复盘]

第一步是定主类型。课程详情页描述的是“某个时间、某个地点、以某个价格提供的一次活动”，用 schema.org 的 Event 最贴合，当时搜索引擎富摘要对 Event 的支持也成熟。第二步是把业务字段逐个映射到类型下的属性。这张映射表是本文的核心交付物，站内的模板、校验脚本、日后新增页面都消费它：

业务字段 页面元素 itemprop 期望类型 取值写法
课程标题 h1 标题 itemName 文本 与页面可见标题逐字一致，去掉促销口号
课程简介 摘要段落 description 文本 纯文本，剥掉 HTML 标签，80 字内
封面图 头图 img image URL 绝对地址，指向真实课程图而非站标

日期、数字的格式必须写到“能被解析”的精度：搜索引擎读的是属性值而不是你的人类文案，3 月 2 日开课 它解析不出，2015-03-02T09:00+08:00 可以。价格、评分同理。这张表建议放进 wiki 并随代码仓库走，任何字段格式变更先改表再改码。

microdata 实操：就近标注

microdata 的全部规范属性只有五个：itemscope、itemtype、itemprop、itemid、itemref，前三个解决九成场景，语义标签与 time 元素的用法旧文《HTML5 新特性总览与语义化标签实践》已讲透，这里只落在标注上。一个完整的课程详情页主体：

主块上写 itemref=“teacher-card”。语法上合法，但当时各家解析器对它的实现参差不齐，嵌套引用时的属性归属规则也不直观。笔者的建议：能不用就不用，宁可调整模板里 DOM 的包含关系。另外注意 scope 上的 itemid：它给实体一个全局唯一标识，通常直接用详情页的绝对 URL，与 canonical 指向一致即可，不要自造编号体系；站内所有 image、url、sameAs 类属性一律写绝对地址，相对路径在部分解析器里会丢上下文。

JSON-LD 实操：服务端集中生成

如果详情页由 Node 服务端整体渲染，字段又全部来自同一个数据对象，JSON-LD 更省心。关键纪律是：永远用序列化生成，绝不手写字符串拼接出来的“JSON”。

模板里输出一行 <%- courseLd %> 即可。注意 JSON.stringify 不会转义斜杠，用户提交的简介里只要出现 </script> 字面量，脚本块就会当场断掉，连带整页解析，这是 JSON-LD 少数“出错会影响展示”的姿势，必须用 \u003c 这类转义兜底。另外要守住两条：第一，标注数据与页面可见数据来自同一个 course 对象、渲染两条路径（HTML 与 JSON），不要让运营改文案时只改一处；第二，JSON-LD 不能替代可见内容——搜索引擎要的是“页面上确实有这条信息”，只出现在脚本里、页面上找不到的标注，有被判垃圾的风险。富摘要与结构化数据标注助手（Data Helper）当年之所以好用，也是因为它在可见内容上画框。

前端必须负责的那部分 SEO

以下四件事都长在 HTML 里，SEO 同事提需求也改不动，只能前端做。title 与 description 每页唯一：拼接时把页名放前、站点名放后，title 控制在三十个全角字符内、description 八十以内，这是当时的经验值，要注明搜索引擎各端显示宽度并不固定，截断位置随字体与布局浮动。canonical 自 2009 年起被支持，带参数列表页统一指回无参 URL，注意大小写与协议也要一致。hreflang 只在多语言站点用，一行 link 声明语言与地区对应关系，不涉翻译就别加。移动端适配与 viewport 相关的旧文《HTML5 meta viewport 与移动端适配基础》已经写过，移动版与桌面版同 URL 时标注数据两边都要输出，属性写法与桌面端完全一致。

最后是最重要的一条工程结论：robots.txt 只约束抓取路径，与结构化数据没有任何关系，它挡不住“标注缺失”。2015 年初的主流搜索引擎抓取 HTML 时并不可靠地执行 JavaScript，脚本里渲染出来的标注约等于不存在——结构化数据必须是服务端输出的一部分，HTML 里没有，一切免谈。

坑与复盘

以下几个坑，每一个都对应真实的返工：

  • 把 itemprop 标在 display:none 的元素上补字段。隐藏文本滥用是当时的敏感区，一旦被发现，惩罚落在页面而不是某条属性。页面上看不见的信息，要么诚实地用 meta 与 content 承载机器值并展示人话，要么别标。
  • 标注价格与实际售价不符。促销期模板里的原价忘了更新、price 标了划线价而页面卖折扣价，都会触发富摘要被撤——这是当时真实存在的惩罚机制，且申诉周期以周计。价格字段与订单系统同源，别让它独立腐烂。
  • 没有评论却标了 aggregateRating。评价数为零时整块不输出，宁缺毋滥，工具会直接报缺失。
  • 日期时区导致前台差一天。服务端存的是 UTC，JS 里随手 toISOString() 会把北京时间早上九点的课标成 UTC 凌晨，落在前一日。映射表里写明：日期字符串必须由内容模型直接带偏移量输出，前端不做二次换算。
  • 把 schema.org 的类型层级当成填空作业。Thing 往下几十层继承，属性表一大串可选，但富摘要的真实最小集很小：Event 认名称与开始时间，Offer 认价格与币种。先满足必填，可选属性等数据可靠了再开。
  • 单页应用的标注。前端路由接管后 URL 变了、HTML 没变，服务端输出的标注停留在初始页，抓取结果自然对不上。无刷新路由与标注的兼得方案，旧文《HTML5 History API 打造无刷新单页应用》的思路仍然成立：详情类页面保留服务端直出，别为了无刷新把爬虫要的信息交给 JS。

小结：五步法与最小清单

落地步骤归纳成五步：一，盘点内容模型，列出值得让机器读的字段；二，选定主类型并产出字段映射表，写清每个字段的格式精度；三，按页面形态选语法，内容页 microdata 就近标注、集中生成页 JSON-LD，单页只用一种；四，映射表进代码、构建期跑 schema-check；五，上线后用测试工具抽查并留档。最小可用清单则是给赶工期同事的底线：一个页面一个主类型，必填字段三到五个，每个日期带时区、每个价格带币种，评分无评价不标，全部标注服务端输出，最后一次工具校验留记录。结构化数据这件事没有捷径，但也确实不难——它更像数据字典而不是营销话术，做进去就是一份资产。
