HTML5 表单新增 input 类型与校验属性详解

本文属于《HTML 与 CSS》第 8/62 篇
上一篇系列目录下一篇

《HTML5 新特性总览与语义化标签实践》里表单只占一节概述，本文是它的展开专篇：逐个拆开每个新增 input 类型”读回来的值到底是什么”，讲清 Constraint Validation API 的触发时机与两个短路条件，最后给出一个 ES5 的 FormValidator 封装与 IE9 及更早的降级路径。适合被”浏览器不是会校验吗”坑过的同行，读完该能回答：原生校验的边界在哪，什么时候必须自己接管。传统取值与逐项校验流程见旧文《表单元素操作与表单验证实战》，本文不重复。

支持矩阵：先把 2015 年 1 月的盘面钉死

谈表单支持面，”现代浏览器”这个词是有害的，它把差异极大的五种实现压成了一个结论。下表是全文所有讨论的前提，只写当时能实测到的行为。

类型 Chrome 40 / Opera 26 Firefox 29+ IE 10 / 11 Safari 7 / iOS 8 Android 4.x
number range 控件与校验齐全 齐全 齐全，无内建样式 齐全 齐全，样式弱
email url search tel 校验生效 校验生效 校验生效 校验生效 校验生效
color 无取色面板的文本框 退化成 text 退化成 text 退化成 text 不可用
date time datetime-local 有控件与弹层 值归一化但无日历 仅这三个且不弹日历 支持，控件由系统绘制 支持，弹层不可控
month week 有原生控件 无 退化成 text 无 无
<datalist> 可用 4+ 可用 10+ 可用 iOS 当时不支持 可用但交互别扭

三点补充。第一，color 这行容易看错：Opera 有真正的取色面板，而 Chrome 在 2015 年 1 月只是把它当作一个必须填十六进制的文本框，点上去是文本光标，可视化取色仍要另引 JS。第二，datetime（不带 local 的那个）规范里有定义，但没有一个主流内核实现过，后来被删掉，不必再写。第三，”值归一化”与”有可用控件”是两件事：Firefox 29 之后认识 date，value 强制成 YYYY-MM-DD，但用户看到的仍是带斜线占位的文本框，只能自己敲——这决定了日期一节的结论。

探测支持度也别读 element.type，IE8 与 IE9 把不认识的类型一律报成 text。可靠的探测分两步：

逐个类型拆开看：值到底是什么

类型名只是入口，真正影响后端的是读回来的值。重点看三件事：值可能被改写、可能变成空串、可能带上前端没写过的格式。

number：step 与空值陷阱

合法性由三个属性共同决定：(value - min) 必须能被 step 整除，否则 validity.stepMismatch 为真；超出上下界则是 rangeUnderflow / rangeOverflow。反直觉的是默认基准：不写 min 时基准是 0，所以 step="3" 配 value="4" 不合法。步长取 0.01 这类二进制无法精确表示的小数时，当时各实现对 stepMismatch 的判定并不一致，所以金额字段稳妥的做法仍是前端按”分”存整数。

最关键的陷阱在取值：用户在 number 里敲了字母，input.value 读回来是空字符串而不是原文——规范给数字类型定义了值清洗算法，非法值一律抹平。于是 parseFloat(el.value) 得到 NaN，更糟的是”用户明明填了东西，你却告诉后端这项为空”。要区分”没填”与”填了但看不懂”，必须读另外两个属性：

valueAsNumber 与 valueAsDate 是配套的一对读写接口：前者给数字类型，后者只给 date、month、week（其余类型读回来是 null，写入抛异常），存在的意义就是让脚本绕开字符串解析。

range：不能为空，只能整条换皮

range 没有空值状态。min、max 默认是 0 与 100，而 value 缺省是 50 不是 0——这个默认值常被忘掉，于是滑块一进来就停在中间。也正因为它永远能读出一个数字，给 range 加 required 是无效的：valueMissing 永远为假。想表达”用户必须主动拖过一次”，只能自己记初始值来对比。

样式是另一个战场，轨道与滑块在 2015 年没有统一接口：

-ms- 那几行是 IE10 引入的私有伪元素，::-ms-fill-lower 能单独给滑块左侧上色，WebKit 做不到；IE 的 ::-ms-track 必须把 color 设成 transparent 才让位给自绘样式，Firefox 又走第三套前缀。一个滑块要好看，同一份视觉规则得写四遍。

email / url / tel：宽松得超出预期

email 只要求”@ 两侧各有非空白字符”，所以 a@b 合法，foo@bar 这种没有顶级域的写法一路通过。这不是缺陷而是刻意保守：RFC 5322 的全量文法浏览器实现不了也不该实现。邮箱的真实关卡是验证邮件，前端这层只拦住”少了 @“这类手滑。加 multiple 后值是逗号分隔的列表，浏览器逐项校验，任何一项非法整个字段就 typeMismatch。

url 严格要求带协议名：example.com 不合法，http://x 合法。用户填网址十有八九不写协议，所以它的价值主要在移动端键盘，提交前得自己补。

tel 故意什么都不校验，因为国际号码无法用一条规则校验：国家码可带 + 或前导 00，分隔符可以是空格、连字符、点，还有分机写法。规范作者宁愿把它定义成”只影响键盘的文本框”，也不给出一个必然错的语法。所以手机号与座机的规则必须自己写。

search：一行前缀决定像不像搜索框

search 与 text 的差别集中在 WebKit 私有样式上：默认渲染成圆角胶囊并带内边距，-webkit-appearance: textfield 能拉回普通输入框，右侧清除按钮由 ::-webkit-search-cancel-button 控制，要显式恢复它的 appearance 才出现；另有 ::-webkit-search-results-button 与 ::-webkit-search-decoration。IE 侧是另一套：文本框默认带那个 ×，不想要就写 input::-ms-clear { display: none; }。两套伪元素互不相通，搜索框外形别指望原生样式。

日期时间族：值一定是 ISO，控件一定不可控

第一个要记住的事实：date 的 value 永远是 YYYY-MM-DD 这个 ISO 形式，提交给后端的是它，而不是页面上显示的”2015年1月18日”或”01/18/2015”。显示格式由内核按语言渲染，值与显示是两层。这消灭了”前端传来 2015/1/8 还是 01-18-2015”这类老问题，但前提是该类型被原生支持——不支持的内核里它退化成 text，什么格式都可能来，所以只要依赖 ISO 就得配一条文本兜底路径。

datetime-local 的坑是时区歧义。值形如 2015-01-18T21:54，没有时区后缀，规范说它表达的是用户当地的墙上时间；而这个字符串塞进 new Date() 时 2015 年各内核口径不统一，有的按本地时区、有的按 UTC。要传后端就拆字段自己拼：

min / max / step 在日期类型上照样生效，但步长单位是秒：date 默认 86400（一天），month 是 2592000，datetime-local 是 1 秒。给 datetime-local 写 step="60" 才是整分钟语义，写 step="2" 会被 Chrome 那个只到分钟的面板判成 stepMismatch。

现实结论要讲明白：iOS Safari 的日期控件是系统绘制的滚轮，CSS 一行作用不上；Android 4.x 弹系统对话框，盖住页面且样式属于 ROM；Chrome 桌面版的日历弹层在 Shadow DOM 内部，2015 年没有可定制的口子。所以设计稿对日期控件有要求，就回到 type="text" + readOnly + JS 日期选择器，桌面后台用 jQuery UI 的 datepicker，联动写法见旧文《jQuery UI 组件使用实践》。

Constraint Validation API 的三个层次

这套 API 是零散成员的组合，按”能不能用”分三层看最清楚。

判定层：element.checkValidity() 返回布尔，element.validity 是只读对象，字段就是失败原因且可以同真——valueMissing、typeMismatch、patternMismatch、tooLong、rangeUnderflow、rangeOverflow、stepMismatch、badInput、customError，加上总结性的 valid。表单级有 form.checkValidity()，但它只报第一个非法字段。

文案层与资格层：element.validationMessage 是浏览器准备弹出的那句话，语言跟着内核界面走，中文系统上是”请填写此字段”，setCustomValidity(msg) 能改写它；element.willValidate 表示控件是否参与校验，隐藏域、disabled、readOnly 与 button/submit/reset/image 都是 false。有个必须记住的推论：readOnly 的控件完全不校验，required 加在只读字段上是零效果。

样式层：:valid、:invalid、:required、:optional、:in-range、:out-of-range 能把校验结果直接画到界面上，IE10、Firefox 4、Chrome 与 Safari 5 之后都有实现。同列表里常出现的 :indeterminate 不属于校验，它描述复选框那个既非选中亦非未选中的中间态（只能由脚本的 indeterminate 属性置上）与 progress 的不定进度。

:invalid 有个体验问题：用户敲第一个字符时 email 已经非法，红框会一路跟着光标闪。Firefox 用私有伪类 :-moz-ui-invalid 规避，只在它认为合适时着红，而 Chrome 当时就是实时判定。也就是说纯 CSS 做不出”提交后才报错”的克制，仍需 JS 控制类名。

触发时机与三个会咬人的机制

机制比属性重要，因为事故几乎都出在时机上。

flowchart TD
  A[用户点提交] --> B{form 上有 novalidate}
  B -- 有 --> C[浏览器不校验 直接提交]
  B -- 无 --> D[逐个跑约束检查]
  D --> E{有非法字段}
  E -- 是 --> F[在该字段派发 invalid 并弹气泡]
  E -- 否 --> G[正常提交]
  H[脚本调 checkValidity] --> F
  I[输入过程中的 input 事件] --> J[不触发校验 不发 invalid]

第一，invalid 只在提交路径与显式调用 checkValidity() 时触发，用户在 input 里敲错不会有任何校验事件。这是公认的坑：监听 invalid 做实时提示，只在点提交那一刻生效一次。要做实时，只能在 input 里自己调 checkValidity() 或直接读 validity。

第二，setCustomValidity() 是开关而不是提示语：只要传进非空字符串，customError 就为真、valid 就为假，而且浏览器会认为该字段已被脚本接管，其它原生提示一概不弹。忘记清空是致命的——用户明明改对了仍然提交不了。

第三，关掉原生气泡的正确姿势是 novalidate，不是把 required 删掉：required 与 type 在移动端决定了软键盘形态与必填语义，删掉等于丢掉标记层的收益；novalidate 只关掉拦截与气泡，标记一个都不用动。单个按钮还能用 formnovalidate 单独豁免，比如”存草稿”：

但 novalidate 有个副作用：带上它之后 form.checkValidity() 直接返回 true，什么都不检查，所以只能逐个控件调 el.checkValidity()。同理别用 el.willValidate 过滤控件——此时它恒为 false，筛出来是空数组。这两个短路是同一条规范逻辑的两面，我在项目里两次栽在同一处。

FormValidator：把原生规则接进自己的 UI

需求收敛成四件事：整表检查、错误显示在字段旁边、文案中文化、输入时自动清除。规则继续写在 HTML 属性上不复制到 JS，避免两边漂移——这是封装最大的价值。

用法只有一行 new FormValidator('apply', { onValid: submit })。四点说明。第一，checkable 跳过 readOnly，就是把”readOnly 不校验”落到代码里，否则只读字段带着 required 会让整表永远通不过。第二，input 与 change 都绑，因为下拉与日期控件在部分内核上不发 input。第三，handler 里先解除接管再清样式，顺序反了会出现红字消失但 valid 仍为假。第四，check() 不在第一个错误处 break 而是整表刷一遍：残留的旧提示比少报一个错误更让人困惑。

IE9 及更早：没有 validity 时的降级

IE9 与更早的内核完全没有 Constraint Validation API，checkValidity 与 validity 都是 undefined，提交时也不拦任何东西。降级思路是标记层不动、用属性重跑一遍规则，让同一套 HTML 在新旧内核上表达同一份意图。正则语法不在此重复，见旧文《JavaScript 正则表达式入门与实战》。

注意读 el.getAttribute('type') 而非 el.type：IE9 会把未知类型规范化成 text，只有内容属性留着作者写的原值。另外 new RegExp 对畸形模式抛错，try 不能省——降级路径里一次异常会让整表校验静默失效，比报错更难查。这份降级没有复算 stepMismatch，需要时在 JS 里补一条：把 (值 - 基准) / 步长 四舍五入取整后再回代与原值比较，别直接对浮点取模，否则 0.1 这类步长会被二进制误差绊倒。这套降级与 FormValidator 共用同一个入口：把 reason(el) 换成 legacyReason(el)，提示、聚焦、提交拦截全部复用。

移动端的附带收益与它换来的问题

新增类型在移动端的好处是实在的：email 键盘带 @ 与 .，少两次切换符号层；url 带 .com；tel 与 number 直接给数字区；search 的确认键显示为”搜索”。这些不用一行脚本，是标记层白拿的收益。

但 number 在 iOS 上有具体问题：弹出的是纯数字键盘，没有负号也没有小数点，”温度””金额”这类字段在 iPhone 上输不完整。通行替代是 type="text" 配 pattern="[0-9]*"（只在 iOS 生效，把键盘切成九宫格），要小数与负号就用 type="tel" 再在 JS 里自己校验。键盘弹出引起的页面位移、fixed 错位与不回弹，旧文《移动端输入法弹出与布局问题》里有完整适配层，本文不重复。

坑清单

placeholder 不能当 label 用：它一输入就消失，用户填到一半会忘记这一栏是做什么的，当时读屏软件对它的支持也不稳定。规则是 label 必须在，placeholder 只作格式示例；IE9 连 placeholder 都不支持，需要 JS 垫片。

required 与一切原生校验都只是体验层，不是安全层。老内核直接忽略，脚本可以关掉，HTTP 请求更不必经过浏览器。服务端必须重新校验，而且校验通过不等于可以输出——回填进 value 属性的用户数据仍要转义引号与尖括号，否则绕过校验的字符串进了 HTML 就是注入。

autofocus 在 iOS 上无效（焦点必须由用户手势带来），在桌面 Chrome 上又会把页面滚到该字段，长表单打开就莫名跳到中部。要自动聚焦就自己写 focus()，且只在判定为桌面后执行。

autocomplete 关不干净：off 在 2015 年的 Chrome 上就已经会被忽略，密码框尤其如此。它的语义是建议而非命令，别当安全控制。

pattern 是整体匹配。规范的等价形式是 ^(?:pattern)$，不必自己加 ^$；但分支必须用 (?:) 包住，pattern="ab|cd" 等价于 ^(?:ab|cd)$，按 /ab|cd/ 理解是错的。

中文输入法下的长度口径不统一。maxlength 按字符截断，一个汉字算 1、一个代理对（生僻字）算 2；而 validity.tooLong 在当时的 Chrome 与 Firefox 上几乎恒为假，因为浏览器直接把输入截住而不置该位，只有脚本写超长 value 时才可能看到。数据库那边按字节算，一个汉字在 UTF-8 里是 3 字节——前端的 20 字与后端的 20 位是两个约束。

<datalist> 只给建议不限制取值，配 required 也不保证值在列表内；name 与 id 建议同名，否则 form.elements 与 getElementById 会指向不同控件。

小结

一张选型表收尾，中间是 2015 年值得写的标记，右边是校验的落点：

字段 标记怎么写 校验落在哪
手机号、验证码 tel + pattern 前端正则，服务端复查
邮箱 email（必要时 multiple） 原生只拦手滑，确认靠验证邮件
数量、金额 number + 按分存整数 读 valueAsNumber，别看 value
网址 url 自己补协议后再校验
滑块、评分 range 记初始值判断是否拖过
日期区间（桌面后台） date + min / max 范围交给原生
日期（要样式或跨移动端） text + 只读 + JS 组件 格式与范围全自己校验
颜色 仍走 JS 取色组件 十六进制自己校验
可输入的候选项 list + <datalist> 服务端必须验值域

团队规约三条：第一，标记层保留 type 与 required，表单统一加 novalidate，错误气泡一律自己画；第二，校验规则只写一份，放在 HTML 属性上，JS 只负责读取与展示，新旧内核共用同一个入口；第三，前端校验通过永远不改变”服务端必须再校验再转义”这条底线。原生校验的边界到此为止：它擅长定义意图、优化输入，不擅长呈现与承诺——分清这两件事，HTML5 表单新特性才真正可用。
