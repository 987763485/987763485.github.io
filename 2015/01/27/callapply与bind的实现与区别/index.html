call、apply 与 bind 的实现与区别

call 和 apply 是 ES3 就进规范的老方法，任何内核都能用；bind 到 ES5.1 才写进规范，浏览器侧 IE 9 才有原生实现，IE 8 一律要挂 shim——这条时间差在 2015 年初仍然会咬人。至于 this 的四种绑定规则、bind 的 polyfill、柯里化的参数预设、arguments 转数组的性能代价，前几篇都推过了，本文不重讲那些推导，只处理剩下的工程问题：这三种调用方式怎么选，参数包装、apply 的展开上限、bind 的偏应用顺序这些细节是什么坑，以及 bind 在事件解绑、new 调用、函数元信息上的三个真实陷阱。适合还在维护 IE 8 兼容页面的同事。

语义与签名：三处容易被忽略的细节

先把签名摆清楚，后面的分歧都从这里长出来。

方法 签名 是否立即执行 返回值 版本与兼容底线
call fn.call(thisArg, a, b, c) 是 原函数的返回值 ES3，全内核可用
apply fn.apply(thisArg, argsArray) 是 原函数的返回值 ES3，全内核可用
bind fn.bind(thisArg, a, b) 否 一个新的绑定函数 ES5.1，IE 9+；IE 8 需 shim

三种写法在 this 判定上都属于显式绑定，算法与优先级《this 指向的四种绑定规则详解》已经给过，这里只补三个评审里常被漏掉的细节。

第一个参数会被包装

传进去的 thisArg 不是”原样塞给函数”的：非严格函数先做一次 ToObject 装箱，null / undefined 换成全局对象，严格函数原样保留。规则旧文讲过，这里只取那些反直觉的后果。

最坑的是第一个结果：probe.call(42) 里 this instanceof Number 是 true。函数里只要有 this instanceof Array 这类分支，或者拿 typeof this === 'object' 判断”调用方传没传上下文”，传原始值与传对象的表现就完全不同。另一个后果是给 this 挂属性会挂空——非严格函数里 this.count = 1 写进的是这次调用临时造的包装对象，函数返回即失效。包装对象只在需要方法时露面，this.length 能用，this + 1 走的却是 valueOf。借用泛型方法时第一个参数传什么，见后面那份清单。

apply 的第二个参数并不”随便给”

规范口径是：null 与 undefined 等价于没有参数；其余必须是对象，实现会读它的 length 并按下标逐个取值。真数组、arguments、DOM 集合都满足，标量不满足。

麻烦在早期内核并不一致。老 Firefox 曾把非数组当成”一个参数”塞进去，fn.apply(ctx, 5) 表现得跟 fn.apply(ctx, [5]) 一样，这个私有能力让一批代码误以为 apply 能吃标量，换到别的内核当场抛错；IE 8 的 JScript 对没有 length 的对象则倾向于给 0 个参数，静默丢掉实参——不报错比报错危险。结论：第二个参数只给真数组或 arguments。

bind 的偏应用是从左往右追加

bind 除了定死 this，还会预置参数，而预置参数永远排在调用实参之前，不做按位替换。

推论很实际：要固定的参数必须是形参列表的前几位。想固定中间那一位，bind 没有占位符能力，硬绑只会把它后面的参数全顶位，这时该用《JavaScript 柯里化与偏函数应用》里带占位符的 partial。

call 与 apply 的选型，和 apply 的展开上限

选型规则就一条：参数能静态列出就用 call，参数已经在数组或 arguments 里就用 apply。后者的意义不是性能，而是别把数组拆成手工展开。

apply 要把数组元素逐个压进这次调用的参数槽，数组一长就撞上栈限制：V8 报 RangeError: Maximum call stack size exceeded，Firefox 报的是 too many arguments to apply 这一类，IE 8 更干脆，直接栈溢出、整段脚本中止。阈值跟栈大小、元素类型都有关，几万到十几万个元素这个量级就可能出问题，别把这个数抄进代码当常量——正确做法是根本不一次展开超长数组。两个最常见的受害者：两个最常见的受害者：

方法借用：一份清单

借用的本质是：这些泛型方法只把 this 当”接收者”读，不要求它是某个类的实例——只要有 length 和数字下标就能借。清单里右边那列的注意事项比左边重要。

bind 的用法边界与三个陷阱

bind 值得用的场景很窄：把方法交出去当回调，而这个引用还要在别处复用（尤其拿去解绑）。除此之外它并不比具名闭包更清楚，下面三个陷阱全来自越过这条边界。

陷阱一：事件解绑解不掉

removeEventListener 按函数引用比对，绑定时那个对象已经找不回来，监听器连同闭包引用的实例就留在内存里。泄漏链条《DOM 事件移除与内存泄漏》走过，这里只留正确写法：

规约：bind 只做一次，引用存到实例上，绑与摘复用同一个引用，destroy() 里成对解绑。jQuery 侧 $.proxy 会复制 guid，但同一句调两次仍然解不掉，只能靠命名空间整体 off 兜住（差别柯里化那篇写过）。另外 IE 8 没有 addEventListener，attachEvent 下回调的 this 是 window，这套写法在 IE 8 上落不了地，取舍见复盘。

陷阱二：被 new 调用时忽略绑定的 this

ES5.1 就是这么定的：绑定函数被 new 调起时 [[BoundThis]] 让位给新建对象，[[BoundArgs]] 照旧前置，等于一个合法的”半截构造”。合法不等于好——Dialog 这个名字加上 bind，会让读者以为它绑定了上下文，实际用的时候上下文凭空消失且不报错。规约：不要把 bind 的结果当构造函数，要预设构造参数就写显式工厂函数。另外 IE 8 上若用的是没处理 new 的 polyfill，这条语义根本不成立，新建对象的属性会写到 that 上，下面实现里专门给了验证。

陷阱三：length 与 name 被改写

原生 bind 会正确重算 length，name 加 bound 前缀。麻烦出在两类会读元信息的代码上。一是按 fn.length 决定行为的库：Express 4 识别错误中间件写死了 fn.length === 4（柯里化那篇还原过它被 partial 破坏的现场，bind 少绑一个参数是同一个坑），自家流程库里 if (cb.length > 1) 这类分支同样会被偏应用骗过去。二是拿 name 做日志字段、注册表 key 的代码：bound run 中间带空格，当 key 时容易对不上，报错栈里多出的 bound 前缀还常让人以为代码里真有个叫 bound run 的函数。

真实的兼容约束在这里：Function.prototype.length 与 name 在 IE 9 及更早的 JScript 里拿不到，IE 8 下 fn.length 就是 undefined。也就是说 IE 8 上既没法验证 polyfill 把 length 修没修对，也不能靠 length 写跨内核的判断——这类判断要么带兜底默认值，要么把参数个数做成显式的 arity 传进去。

顺带一句前瞻：TC39 草案里同时有绑定函数（::）与箭头函数两个方向，都想把 this 交给语法而不是交给 bind 调用，但 2015 年 1 月都还在早期阶段，本文代码不依赖它们。

数组方法的 thisArg 通常比 bind 省

forEach / map / filter / some / every / reduce 都留了 thisArg，由实现内部复用同一个上下文。凡是”只想把手上的 this 递给回调”的地方，先想这个参数，再想 bind。反过来，jQuery 的 $.each、$.map 没有这个口子，那才是 bind 或 $.proxy 的用武之地。

一份 bind 的实现：用原型链处理 new

上一篇的归一化版本用 Function('binder', ...) 造壳拿 length，内部靠 this instanceof binder 分辨 new，再让 binder.prototype 与 bound.prototype 互相指认。下面这段是照 ES5.1 语义写的简化版，走另一条路：用 fBound.prototype = new fNOP() 承接原型链，少一层内部函数，调试栈也更短。new 的判定用 this instanceof fBound 而不是 fNOP——target 没有 prototype 时 fNOP.prototype 就是 Object.prototype，用它判定会把普通调用误认成 new。还有一点：别图省事写成 fBound.prototype = target.prototype，那样新建对象与原函数共享同一个原型对象，一处改动另一处可见。

length 用形参占位这条沿用上一篇，因为 IE 8 的 Object.defineProperty 不能作用于普通对象，只有这一条路。要注意 new Function 在开了 CSP 的页面里会被 eval 策略拦掉，那种项目只能退回普通 function fBound () {}，接受 length 是 0。

表里 setTimeout 那行多说一句。HTML5 定时器规范允许从第三个参数起向回调传实参，Chrome 与 Firefox 都实现了，IE 8 只认前两个，多余参数直接忽略——这不是报错，而是参数无声消失，很容易被误判成自己逻辑写错。兼容口径：还要支持 IE 8 的页面，setTimeout / setInterval 的回调一律零参数，靠 bind 预设或闭包捕获。

一次 IE 8 上的全量替换复盘

一个后台项目（老代码，jQuery 1.9，仍要支持 IE 8）做过一次”统一风格”改造：把散落的 var that = this; 全替换成 bind，理由是”看起来更现代，也不用每个回调记一个别名”。几百处机械替换，评审时没人反对。上线第二天 IE 8 上整片失效：标签页切不动、表格排序没反应、弹窗关不掉，而 Chrome 和 IE 11 一切正常。

原因很直白：Function.prototype.bind 在 IE 8 上根本不存在，项目既没引 es5-shim，也没有自带 polyfill。这类写法解析阶段不报错，运行到才抛 TypeError，而抛错点埋在事件回调深处，被 IE 的脚本错误对话框吞成一行”该行脚本有错误，是否继续”，用户只看到”点了没反应”。每处独立抛错、控制台没有统一线索，定位花了一整天才确认是同一个根因。

最后的处理分三层。第一层，构建里统一引 es5-shim 的 bind 子集——只补 Function.prototype.bind，不做全量 shim，免得顺手改动 Object.prototype 上的行为，代价是 Array.prototype.indexOf 之类仍要自己兜底；shim 排在所有业务脚本之前，只对 IE 8 及以下条件加载。第二层，收敛用法：只在事件处理器与异步回调这两类”必须把 this 交出去”的地方保留 bind，其余退回 that——that 在任何引擎上都不会变，而 bind 的可用性取决于部署顺序，某个入口模板漏引就是整片故障。第三层，构建期加一条检查：产物里出现 \.bind\( 就打警告，要求确认该页 shim 已在位。

这次改造真正的收获不是”bind 好不好”，而是两条纪律：兼容基线决定 API 的可用性，风格统一不能凌驾于”这个 API 在基线上存不存在”；polyfill 要当部署件管理，写进构建而不是靠脚本顺序。至于可读性收益，坦白说没预期的大——半年后回头看，that 的版本在断点里反而更容易看清上下文是谁。

小结

call 与 apply 的差别只有”参数怎么给”：能静态列出就用 call，参数已在数组里就用 apply，别手工展开，也别拿性能差异做选型；apply 要展开数组压栈，长数组得分块或退化成循环。bind 换来 this 和一段参数前缀，代价是产物是新函数、length 与 name 被改写、被 new 时忽略绑定的 this，而且 IE 8 上根本不存在。方法借用只适用于”读接收者”的泛型方法，会写 this 的一律传真对象。三条团队规约：能传 thisArg 就不 bind；bind 只做一次并存到实例上，绑与摘复用同一个引用；任何声称兼容 IE 8 的分支合入前，先确认这个入口页的 shim 已加载——最后这条不用来 review 代码，用来 review 部署。
