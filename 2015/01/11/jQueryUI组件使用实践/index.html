jQuery UI 组件使用实践

后台系统的日期区间、可拖拽的看板、带自动完成的多选框，这些需求在 2015 年初的桌面端高度重合，可选的方案却不少：jQuery UI、Bootstrap 3 的组件、公司自研的 jQuery 插件，偶尔还要面对 EasyUI、KendoUI 这类成套商业库。本文基于 jQuery UI 1.11（2014 年 9 月发布），先把选型结论给出来，再做一次三方案横向对比，最后用五个最常用的组件给出完整可运行的落地写法与坑清单。适合还在 jQuery 1.x 线上维护后台、正纠结”要不要引 jQuery UI”的同学，读完你应该能回答：这个组件该不该用它，以及用了之后怎么不后悔。

先给结论：一张选型表

别先读对比再决策，把最常见的八种需求摊开，每个给出推荐方案、一句理由和一个风险，后面的章节只解释这张表。

需求 推荐方案 理由 风险
后台表单的日期区间 datepicker 双实例联动 当时唯一成熟的区间联动方案，互相设 minDate / maxDate 即可 只有单月视图，双月并排要自己拼；中文需另引 i18n 文件
模态框 项目里已有谁就用谁 Bootstrap 的 modal 更轻；需要拖拽、缩放、按钮编排才值得上 dialog dialog 的 DOM 残留与销毁要自己管
可拖拽排序的面板 sortable Bootstrap 完全没有对应物；原生 HTML5 拖放 IE8 不支持，坑见旧文《HTML5拖拽API实现元素拖放排序》 触摸设备上拖拽和页面滚动互相抢事件
标签页加折叠面板 按项目风格二选一 tabs 自带内容懒加载与键盘导航，Bootstrap 的 tab 只有样式切换 与 hash 定位的联动都要自己做映射
带自动完成的输入框 autocomplete 远程数据源、键盘导航、高亮模板全部开箱即用 建议词渲染成 HTML 时有注入风险
移动端页面 两个都不要 Zepto 没有 widget 体系，jQuery UI 的触摸支持也只是基础 硬用会出现滚动与拖拽打架、点击迟钝
视觉高度定制 借行为不借样式 用 widget factory 自研组件，皮肤类完全自己写 自己的皮肤类要长期有人维护
无障碍严格合规 自研并专项投入 jQuery UI 有完整键盘导航和部分 ARIA，只能当底子，过不了严格审计 不专项投入就没有合规，仅此而已

表格之外补一句：EasyUI、KendoUI 这类成套库功能确实全，但前者样式年代感强、后者要商业授权，Validform 只解决表单校验这一件事；预算和形象都敏感的团队，反而更应该把 jQuery UI 和自研的边界想清楚。

jQuery UI 1.11 的功能面与主题

先把这套库 1.11 版本的事实边界钉住。它要求 jQuery 1.7.2 及以上，从这一版起放弃 IE6 / IE7，但 IE8 仍然在官方支持范围内，所以还要兼容 IE8 的项目继续留在 jQuery 1.x 加 jQuery UI 1.11 是唯一解。组件一共十五个：accordion、autocomplete、button、datepicker、dialog、draggable、droppable、resizable、selectable、sortable、menu、progressbar、slider、spinner、tabs。1.11 对触摸设备的支持明显改善，底层靠 widget 自带的 $.ui.mouse 把 touch 事件翻译成鼠标事件，点选类组件（datepicker、tabs、menu）在平板上基本可用，但复杂拖拽（draggable、sortable）在移动端仍不推荐，原因见坑清单。

所有组件共享 widget factory 这一套约定：用 $.widget("namespace.name", {...}) 定义，生命周期钩子是 _create、_init、_setOption，实例销毁走公开的 destroy 方法（内部覆写 _destroy）。调用统一走字符串参数，读配置 $('#el').tabs('option', 'active')，批量改配置传对象，控制状态用 'enable' / 'disable'。事件命名从 1.9 起就是”组件名加事件名”的大写风格，比如 tabsbeforeactivate、tabsactivate、sortupdate、autocompleteselect，1.9 之前带 ui. 前缀的旧事件名早已废弃，老教程里抄来的 ui.tabsselect 在新版本上什么都不触发。

样式走 ThemeRoller：官网可视化调好配色后整包下载，或直接在定制下载页只勾选用到的组件打 custom build，这是控制体积的正规手段——全量打包并不便宜，量级见下文对比。主题 CSS 建立在几个状态类之上：ui-widget 是根容器，ui-state-default、ui-state-hover、ui-state-active、ui-state-disabled 描述交互状态，ui-corner-all 管圆角。自己的样式要覆盖它们，优先级是绕不开的话题，实践建议放在坑清单里说。另外一条很多人第一次都会漏：效果类能力（hide('scale')、switchClass、effect('highlight')）全部在 effects 核心文件（下载包里的 jquery-ui-effect.js）里，只勾 widget 不带它，这些调用会静默退化成直接显隐。

横向对比：jQuery UI、Bootstrap 3 与自研插件

Bootstrap 3.3（2014 年 10 月发布）提供 tab、collapse、modal、dropdown、tooltip、popover、alert、button 这组组件，但没有日期选择器，也完全没有任何拖拽排序能力——社区靠另引 bootstrap-datepicker 之类的插件补洞。三个方案在七个维度上的对照如下（体积是我本机拉包用 gzip 压出来的粗略量级，只作同口径比较，不是官方数字）：

维度 jQuery UI 1.11 Bootstrap 3.3 自研 jQuery 插件
功能完整度 十五个 widget，datepicker 与 sortable 独一份 上述八类，缺日期与拖拽 投入多少做多少
样式可控度 绑死主题类名体系，改造要走定制主题 CSS 优先，改起来最顺手 完全可控
体积量级 全量 js 约 250 KB，gzip 后七十多 KB；三个 widget 的 custom build 能压到几十 KB js 约 36 KB，gzip 约 10 KB 单组件几 KB 以内
无障碍 键盘导航完整，ARIA 覆盖部分组件 modal 的焦点处理尚可，其余一般 从零开始，最容易漏
IE8 可用性 官方支持 官方支持（js 要求 jQuery 1.9.1 以上） 自己定
移动端可用性 基本不可用 触摸原生友好 不上桌面代码即可
升级成本 1.11 刚发布，1.x 内接口稳定 版本节奏快，类名改动频繁 没有升级，只有维护

按团队背景给一句判断：后台项目多、页面几十上百个、公司没有专职视觉、IE8 还必须活着，选 jQuery UI，它的功能面和键盘行为是自研短期内补不齐的；全站已经倒向 Bootstrap 的视觉体系、只缺模态框和标签页，就别再引入第二套组件库和主题类名，缺的日期控件单独补一个小插件；设计师对像素敏感、要用的组件不超过三四个，直接用 widget factory 自研，借它的生命周期和状态管理，皮肤完全自己写。三条路的成本差异不在引入那一刻，在一年后谁还愿意维护。

五个常用组件的落地写法

以下代码全部基于 jQuery 1.11 与 jQuery UI 1.11 的 ES5 写法，可直接运行。每个例子后配一个注意点。

dialog：内容懒加载的模态框

注意点：close、destroy 与 remove 是三件事。close 只隐藏，生成的 .ui-dialog 包装结构、遮罩层和全部事件都还在，下次打开还是旧内容；destroy 解绑事件并把原元素还原回文档流，但打开期间挂到 body 上的遮罩节点不一定按你期望的时机消失，关闭后最好检查一遍；直接 remove() 是把 DOM 从插件鼻子底下抽走，data('uiDialog') 和挂在旧节点上的处理器全部悬空，同一页面再插入同 id 的节点时会出现”新框被旧实例劫持”的怪现象。正确顺序永远是先 destroy 再 remove。

sortable：跨容器面板排序

面板的标记必须带 id="panel-3" 形式的编号，serialize 才能吐出 panel[]=3&panel[]=1&panel[]=2 这样的参数。与后端的映射约定很简单：数组下标即新顺序，后端按顺序重写每行的 sort 字段；如果接口要 JSON，改用 sortable('toArray') 拿 id 数组自己拼。注意点写在坑清单第 6 条：helper: 'clone' 拖出来的是一份克隆，面板里若有 iframe 或表单，拖动瞬间的焦点与滚动位置会丢，这是当时所有拖拽方案的通病。

datepicker：两个实例做区间联动

dateFormat 里的 yy-mm-dd 是 jQuery UI 自己的记号体系，yy 是四位年，跟 moment 那套 YYYY-MM-DD 不是一回事——如果业务侧还要做日期运算，moment 2.x 当时已经成熟，但那是另一笔引入成本。想禁掉周末用 beforeShowDay 返回 [false, '类名', '提示']。核心局限在第一条：它是单月日选择器，区间联动靠 onClose 回填选项，没有双月并排视图，也没有面板内的区间高亮，需要这些就得自己拼两个实例的布局；2014 年出现的轻量选择器 pikaday 在移动端和体积上更灵活，但功能面更薄，可以列为对照组。

tabs：埋点与懒加载挂在激活事件上

tabs 也支持在标签 href 上直接写远程地址由内置 ajax 加载，但每个标签只拉一次且不好做失败重试，要按访问刷新就自己管懒加载。beforeActivate 在切换前触发且返回 false 可以取消切换，是埋点和权限拦截的统一入口；与 hash 路由的完整联动超出本文范围，一句带过。

autocomplete：远程数据源与注入防护

source 传函数时收到的 request.term 就是当前输入，response 是渲染回调，远程、本地数组、混合过滤都走这一个口。风险点在 _renderItem：建议词来自服务器，用户能搜什么它就含什么，把 item.label 未经转义拼进 HTML 等于把注入通道敞开，所以必须像上面这样先 escapeHtml 再打高亮标签。select 里取 ui.item.value 而不是输入框最终显示的 label，否则带 <strong> 的文本或”名称（编码）”这类展示串会被当成提交值。防抖的实现是插件开发的常规话题，本文不重讲。

坑清单

复盘一年下来踩过的坑，按出现频率排：

主题类名冲突。 自研样式和 ui-state-hover、ui-widget-content 撞车是最高频的问题，表现为按钮悬浮没反应、激活态颜色丢失。用 !important 或叠选择器把优先级顶上去能救急，但会滚成军备竞赛——更干净的取舍是整包保留主题类名、自己的样式一律收在命名空间前缀下，或者干脆不用下载的主题、只留结构类。这是层叠与特异度的常规账，按项目情况算即可。

effects 是独立文件。 第一次在项目里用 $('#x').hide('scale') 或 switchClass 却没动画，九成是打包时没带上 effects 核心 jquery-ui-effect.js。调用不报错、直接跳到终值，静默得很难查。

触摸设备上的拖拽冲突。 1.11 的 touch 适配把触摸翻译成鼠标事件，代价是手指按下移动时拖拽和页面滚动抢同一个手势，sortable 列表在触屏上滚都滚不动。移动端别上拖拽，需要滑动能力另寻方案，我在《Zepto移动端库实战》里写过迁移的路子。

zIndex 堆叠管理。 dialog 打开时递增全局 $.ui.zIndex 计数器，遮罩与框体层级是它管的；如果页面自己把吸顶导航写成了 z-index: 9999，模态框会被压在导航下面。定一份全项目统一的层级表，或在 dialog 选项里显式给 zIndex，二者选一。

IE8 下补间动画掉帧。 switchClass 这类走 effects 的动画在 IE8 上仍要经 filter 处理透明度，长列表里逐个动画必然掉帧，直接降级为无动画；jQuery 动画本身的队列与打断规则，旧文《jQuery动画showhide与fade系列》和《jQuery自定义动画animate实战》已经讲透，这里不重复。

实例化两次与销毁。 用 html() 重渲染容器后没先 destroy，旧实例的引用和事件悬在已移除的节点上，症状是一次点击触发两次、面板点击空白。最稳的老写法是实例化前判存在：if (!$('#x').data('uiTabs')) { $('#x').tabs(); }，节点要移除时先 destroy 再 remove。widget factory 自身会挡住同元素的重复初始化，但它挡不住”DOM 被你自己换掉了”。

务实的边界：借行为与干脆不用

用得最深的姿势其实是只借 jQuery UI 的行为层：用 $.widget("custom.xxx", {...}) 定义自家组件，白拿它的配置合并、生命周期、事件触发和重复初始化保护，皮肤类完全自己写，一行主题 CSS 都不引。$.widget 与手写 IIFE 插件的取舍我在《jQuery插件开发模式与实战》里对比过，结论没变：组件超过两个、要公开方法、要状态管理，就值得上 factory。反过来，三种情况我建议干脆不用：需求在移动端，这条前面已经说死；有无障碍审计的硬指标，jQuery UI 只能当底子；页面里要用的组件超过五个，那就不是选型而是建站，维护成本要重新评估——此时成套的 EasyUI 或商业的 KendoUI 反而是更诚实的选项，预算换时间。

小结：引入前必答的五个问题

jQuery UI 1.11 在 2015 年初的位置很清楚：桌面端后台的功能库，datepicker 和 sortable 几乎没有对手，代价是主题体系、体积和一套你必须遵守的 widget 约定。动手之前把五个问题写进技术方案：目标浏览器里有没有 IE6 / IE7（有就别引，1.11 已不支持）；要用到几个组件（五个以上先评估维护）；皮肤是否必须定制（必须就借行为不借样式）；有没有触摸场景（有就划清桌面边界）；一年后谁来维护（没人接盘的组件库会变成第三套历史包袱）。这五个问题都有答案，jQuery UI 用起来才不后悔。
