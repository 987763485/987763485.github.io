Web Workers 把耗时计算移出主线程

本文属于《HTML 与 CSS》第 56/62 篇
上一篇系列目录下一篇

页面上一次点击要等六七百毫秒才有反应，排查半天发现是前端自己在算东西——这类问题在 2015 年已经不算罕见。Web Worker 给了我们第二个线程来跑纯计算，但它不是免费的：消息要序列化、数据要拷贝、结果要配对，用错了反而更慢。本文站在性能与调优的角度，讲清三件事：怎么判断”该不该上 worker”、上 worker 的三条落地路线（整体搬迁、分片协作、零拷贝传输），以及围绕它的工程约束和踩过的坑。代码全部 ES5，支持面按 2015 年 1 月的真实浏览器情况来谈。事件循环与单线程模型在旧文《JavaScript 单线程与异步编程模型》里已经讲透，本文不重讲；大列表的渲染瓶颈则是另一回事，参见《大列表渲染优化思路》，那是”画不过来”，本文谈的是”算不过来”。

先定位：主线程被长任务阻塞的表现与测量

上不上 worker，先用证据说话。主线程被长任务阻塞的典型表现有三种：点击后按钮状态迟迟不变（输入事件在排队）、滚动掉帧（合成器还算争气，但跟滚动绑定的脚本逻辑会明显一顿一顿）、输入框打字丢字符。这三个症状的共同点是：网络是好的，服务器是快的，卡的是浏览器自己执行的那段脚本。

2015 年可操作的测量手段就那么几样。Chrome DevTools 的 Timeline 面板里，脚本执行段显示为一大块黄色，超过 50ms 的连续黄色块基本就是嫌疑犯，面板顶部 FPS 折线在那一段会直接跌平。想留数据的话打点最朴素也最可靠：

至于 window.performance.timing，它量的是导航与资源加载阶段，对”脚本跑了多久”这件事帮不上忙，别拿它当性能打点用。经验阈值方面，我们团队内部有一条约定：单段同步计算预期超过 50ms 就应该考虑拆分或外移。要强调这只是团队约定，不是任何规范——它的依据是让 60fps 的帧预算保持在 16.7ms 上下，50ms 的阻塞足以丢掉三帧，用户已经能感觉到不跟手了。低于 10ms 的计算，我劝你不要碰 worker，原因下一节量化给你看。

成本模型：消息传递到底贵在哪

Worker 换回的是主线程的帧率，付出的是三样东西：消息序列化、跨线程数据拷贝、结果回传后重新排进主线程任务队列的唤醒延迟。前两条发生在 postMessage 送出去的那一刻，浏览器对消息体做结构化克隆（structured clone），逐字段复制；第三条取决于当时的渲染压力和任务队列长度，你无法保证回调下一帧就跑。

由此推出本文最重要的一个判断口径：**worker 的收益等于”省下的主线程阻塞时间”减去”序列化与来回传递的开销”，当数据量小、计算快时，这个差值是负的。**把一万个元素的数组丢进去排个序，序列化本身可能就要十几毫秒，而主线程排序也许总共才 30ms——你只省了渲染阻塞，总耗时反而变长。所以只有两种情况值得上 worker：计算本身就够长（几百毫秒到秒级），序列化成本占比可忽略；或者任务跑在后台期间用户界面必须保持流畅，哪怕总耗时增加也认。

worker 版把同一份 data 传进去，计数逻辑留在主线程原样跑。预期结果是：主线程版总耗时短，但期间帧数为 0——rAF 回调本身就在主线程排队，排序不结束它一次都不会执行，页面彻底冻住；worker 版总耗时略长，帧数却能保持在接近 60。两个指标一起看，才是”值不值”的完整答案。这个实验只认趋势不认绝对值，换台机器、换个浏览器版本，数字都会变，但两条曲线的相对关系不会变。

还要说清 worker 里能有什么、不能有什么。worker 没有 window、没有 document、没有 localStorage，全局对象是 self；同步 XMLHttpRequest 在 worker 里被明确禁止，调了直接抛 TypeError，异步 XHR、setTimeout、WebSockets、importScripts 都在。它本质上是一个只有计算和网络、没有页面的执行环境。

路线一：把纯函数整体搬进 worker

最常规的用法：挑一个不碰 DOM 的纯函数，整个搬到 worker 里。拿一个真实场景举例——后端返回一棵嵌套很深的组织机构树，前端要把它扁平化成列表再过滤，数据大时解析加遍历接近 400ms。

    W-->>M: 出错时回传 error 字符串, 主线程重建 worker

三个设计细节都是坑换来的。其一，消息必须带自增 id：主线程可能在同一 worker 上同时挂多个任务，没有 id 就无法把结果和回调对上。其二，超时兜底必须有，因为 worker 一旦死循环，terminate() 是唯一的手段，而单条消息无法撤回，超时就只能牺牲整个 worker。其三，错误对象跨不了线程，Error 实例传出来会丢栈信息，必须在 worker 里转成字符串，主线程再造回来。

路线二：不用 worker 的救急做法——分片

如果你的计算撑不起 worker 的序列化成本，或者目标环境里 worker 不可用，还有一个廉价得多的手段：把大循环切成片，每片跑 10 到 20ms，片与片之间用 setTimeout 交还控制权，让渲染和输入事件插得上队。这就是旧文《JavaScript 单线程与异步编程模型》里事件循环的直接应用——注意它仍然是主线程在跑，所谓”异步”只是让出渲染机会，计算的总时间不变甚至略增，这点要和真 worker 划清界限。

用时间预算而不是固定条数做切片条件，是因为不同数据项的计算成本不均匀，固定条数会让某些片意外超长。分片方案有两个 worker 没有的好处：处理函数可以直接读写 DOM、可以闭包引用任何页面状态，迁移成本几乎为零；而且取消只要不再调 done 往下走即可，天然可中断。它的天花板也很明确：片内一旦超时，卡顿照样发生，救急可以，扛不动真正的长计算。

路线三：Transferable 零拷贝搬运二进制

处理图像像素、大字节流这类任务时，序列化拷贝可能比计算本身还贵。好在当时 Chrome 和 Firefox 已支持 Transferable：postMessage 的第二个参数传入一个数组，列出消息里要”移交所有权”的 ArrayBuffer（MessagePort 也在名单里），浏览器不再复制内容，而是把底层内存直接挂到对侧，原侧的引用当场失效。Safari 当时对这个特性支持不完整，务必探测后降级回拷贝路径。

这里的原则是传 ArrayBuffer，不传数组。同样四百万个字节，传普通数组要克隆四百万个数字，传 ArrayBuffer 配合 Transferable 则是纯指针移交，耗时从秒级掉到接近零。代价是语义变危险了：buffer 一旦移交，两侧永远只有一侧能用，任何”发出去还想留着原件”的代码都会踩雷。另外注意，ImageData 对象本身不可移交，能移交的只有它背后 Uint8ClampedArray 的那块 buffer，移交后原 ImageData 即作废。

支持面与工程约束

按 2015 年 1 月的真实情况划线。Dedicated Worker：Chrome、Firefox、Safari 5 以上、Opera、IE10 以上均可用，这是本文所有方案的前提。移动端：Android 2.x 的原生浏览器不支持，Android 4.x 上的 Chrome 可用；iOS Safari 从 iOS 5 起支持 dedicated worker。Shared Worker 当时只有 Chrome 和 Opera 支持，任何方案都不要依赖它。探测要同时防”构造即抛错”的环境：

同源是硬规定：worker 脚本必须与页面同协议、同域名、同端口，跨域的脚本 URL 构造时就抛错。真要复用别处的逻辑，只能在 worker 内用 importScripts('/lib/shared.js') 引同源资源；社区有人把脚本转成 base64 塞进 blob URL 来绕构造限制（window.URL.createObjectURL(new Blob([...]))），当时 Firefox 与 Chrome 可行、IE 有缺陷，而且 blob worker 里的 importScripts 行为不一致，只当了解，不建议进生产。

工程上有四件事要提前安排。第一，worker 文件单独管理：放统一的 workers/ 目录，构建流程里把它当独立入口压缩，文件名同样走内容指纹加 hash 的策略——这套版本机制在旧文《静态资源版本号与缓存更新》里已经讲过，worker 脚本不例外，因为它一样会被强缓存。第二，共享代码走 importScripts，注意它同步阻塞 worker 启动、每个脚本按标准 HTTP 缓存规则处理，改内容同样要换 URL，否则老 worker 引老库。第三，调试：Chrome DevTools 的 Sources 面板顶部有 Threads 列表，选中 worker 线程就能给它下断点，worker 里的 console.log 会带着线程标记打到页面控制台；Firefox 的开发者工具当时也能attach worker。第四，数量与生命周期：worker 创建一次大概要一两毫秒到十几毫秒，别在每个请求里新建，常驻复用；页面卸载前显式 terminate()；要做 worker 池时，核数靠 navigator.hardwareConcurrency 探测（当时只有部分浏览器提供），拿不到就保守地按 4 处理，池大小取 cores - 1，给主线程留一颗核。

    A -->|是| C{单次预期耗时超过 50ms 吗}
    C -->|否| B
    C -->|是| D{数据量大到序列化占大头吗}
    D -->|是, 二进制| E[worker + Transferable]
    D -->|是, 普通对象| F{计算本身远大于序列化吗}
    F -->|否| G[交给服务端做]
    F -->|是| E
    D -->|否| H{需要中途取消或保帧率吗}
    H -->|是| I[worker + 序号与超时设计]
    H -->|否| J[setTimeout 分片]
    E --> K{目标内核支持 dedicated worker 吗}
    I --> K
    K -->|否| J
    K -->|是| L[按路线一落地]

图的出口只有三个：worker、分片、服务端。走不出”纯计算且超过 50ms”这两个门，就不要碰 worker；支持面探测不过，worker 方案必须原样退回分片，这是降级路径，不是可选项。

什么时候不该用 worker

适合的场景，这一年内我自己或同事实际做过的：图像像素级处理（灰度、缩放前的降采样、滤镜）、几兆以上 JSON 的解析与扁平化、地图应用里的地理围栏与路径粗算、前端本地检索的索引构建与排序、表单引擎里的复杂规则校验。共同特征是：输入输出一句话能说清，中间不需要问页面任何事。

不适合的清单同样要背下来：一切 DOM 操作——worker 根本摸不到文档树，为了”算完顺便改 DOM”还得把数据传回来二次搬运，不如别拆；十毫秒级的日常小计算——序列化成本倒挂；需要与页面状态高频双向同步的任务——每帧都要对账的状态机，消息往返会把 CPU 耗在克隆上；依赖 Cookie 的 XHR——worker 里的 XMLHttpRequest 不发页面 Cookie，鉴权接口走不通，要跨域就老老实实用 CORS 头；需要严格一致性的共享状态——两个线程读写同一份数据，当时既没有规范的跨线程共享内存原语，也没有可靠的加锁手段可依赖，别用 worker 碰这件事。

坑与复盘

按我们项目里真实踩中的顺序复盘六个坑。

第一个，把带回调的”配置对象”传给 worker。有人想把排序函数本身传进去：postMessage({ fn: myComparator })，直接抛 DataCloneError——结构化克隆不搬函数，闭包、原型链一概传不过去。函数和 DOM 节点都不能传，这是协议红线。正确姿势是主线程只传数据和一个任务名，比较逻辑在 worker 脚本里自带。

第二个，习惯性写 window.xxx。worker 里没有 window，第一行就 ReferenceError，而且这个错误发生在 worker 线程内，主线程看不到堆栈，只表现为”消息发出去没有回音”。全局对象统一用 self，共享库要在 worker 环境里跑一遍冒烟，别只在页面里测。

第三个，IE10 的结构化克隆比别家严格。循环引用的对象在所有浏览器都传不了；但在 IE10 上还有额外的坑：值为 undefined 的字段会整个丢失，Date 倒能保持类型，函数属性则变成没有行为的普通对象。跨浏览器共用的消息格式，宁可先 JSON.stringify 检查一遍字段，也别赌各家实现对齐。

第四个，本地双击 HTML 文件用 file:// 打开，new Worker 直接抛 SecurityError——同源策略在本地协议下同样成立。必须起一个 http 服务来开发，这一点坑过不止一个人，排查时先看 URL 协议。

第五个，worker 出错后界面永远转圈。计算里一个空指针异常，worker 内的错误如果没被 onerror 接住，主线程的回调就永远不会被调用。所以 runInWorker 里超时兜底和 onerror 处理不是锦上添花，是必须项：宁可误杀一个慢任务，也不能让用户对着转圈等到天荒地老。

第六个，worker 崩溃后不恢复。某些内核在 worker 异常终止后不会自动复活，后续所有消息石沉大海。onerror 里必须 terminate() 并把 worker 引用置空，下次调用时重建，同时把未决回调全部以错误出清，否则 pending 表会越积越大。

小结

worker 的本质是一笔交易：用序列化、拷贝和唤醒延迟这些实打实的成本，换回主线程的帧率与响应性。交易做不做，用前文的对照实验说话；怎么做，三条路线按数据形态选。上线前有四条检查我要求每次都过一遍：支持面探测与分片降级路径是否齐全；单条消息体积是否量过，超过几百 KB 的二进制是否走了 Transferable；超时与 onerror 重建是否真正覆盖所有未决回调；DevTools 里能否切到 worker 线程断点调试。最后留一条纪律给大家共勉：先测量，再上 worker——任何性能优化都从证据开始，到收益复测结束，工具不是信仰，账算得过来才用。
