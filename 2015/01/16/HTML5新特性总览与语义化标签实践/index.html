HTML5 新特性总览与语义化标签实践

本文属于《HTML 与 CSS》第 1/62 篇
上一篇系列目录下一篇

写页面时最常被问的一句话是”这个 HTML5 特性能不能用”。2015 年初的真实答案是：有的立刻能用，有的要补一层兜底，有的只有一家内核实现，还有一堆只是草案。本文做两件事，一是给一张”特性 × 内核”的判断地图，让读者自己也会查；二是把语义化标签里旧文没写透的几个（main、time、figure、header/footer 的作用域）写成能直接照做的规范。适合刚入行、写页面时纠结”这标签浏览器认不认”的同学。

先把”H5”这个词收窄：本文只谈规范

“H5”在中文前端圈已经被用坏了，它至少同时指三样东西：HTML5 这份规范本身；移动端里那种带翻页、CSS3 动效、摇一摇的推广页；泛指一切”比较新的网页效果”，连 Flexbox 也算进去。三层含义混在一起，谈可用性就变成鸡同鸭讲——有人说”H5 视频早就没问题了”，指自家移动端页面能放；有人回”IE 不支持 H5”，说的是某几个新标签。

本文只谈第一层：规范给标记语言新增了哪些元素与属性，各家内核实现到什么程度。之所以先划这条线，是因为规范里的东西有明确的实现状态可查，而”H5 页面”是营销词，没有状态可查。

另外，从 HTML4 迁过来的那些事（doctype、<meta charset> 的位置、废弃标签、属性布尔化）《从 HTML4 迁移到 HTML5 的 checklist》已经列过，本文只引用结论；section、article、nav、aside 的定义与判别依据也在《section、article、nav、aside 语义化标签的合理使用》里讲透了，本文只在示范里直接使用，不重复判据。

判断可用性的唯一标准

一条纪律先立住：一个特性能不能用，唯一标准是你的目标浏览器集合里那个内核是否实现。不是”规范定稿了没有”，不是”文档写着支持”，更不是”我本机 Chrome 里能跑”。

由此有三条推论，都是当下踩过的坑。第一，规范状态与实现状态是两条独立的线：W3C 那份 HTML5 快照 2014 年 10 月才进入候选推荐阶段，同期 WHATWG 的生活标准还在改，hgroup 就是一边还留着、一边已经在删。第二，本机可用不等于目标可用：按我们站点 2014 年 12 月的流量日志，IE 9 到 11 仍有可观占比，Android 2.3 与 4.x 自带浏览器没清干净。第三，”可用”要再拆三层：能不能解析出节点、能不能被 CSS 命中、能不能被辅助技术和爬虫读到；main 就是三层不一致的典型，较新内核能解析，但部分内核把它当未知元素、不给默认块级样式，读屏软件当时也未必报成地标。

判断流程可以固定成一张图：

flowchart TD
  A[想用某个特性] --> B{查目标内核实现情况}
  B -->|全部实现| C[直接用]
  B -->|部分实现| D{不支持的用户看到什么}
  D -->|静默忽略且内容仍完整| E[用并补兜底样式]
  D -->|功能缺失| F[写降级方案或不用]

特性地图：五块内容各给三档

下面按五块给出”能立刻用 / 谨慎用 / 别用”的档位与一句理由，理由都落回同一件事：不支持的用户看到什么。

语义与结构标签

能立刻用：header、footer、nav、section、article、aside、time、address、abbr、figure、figcaption、mark。老内核最多不认得节点，补一层 shiv 和块级样式就能收平，内容不受影响，成本可算。谨慎用：main，IE 全系与 Android 2.3 当时仍按未知元素处理，写它就得补 display: block 并保留 role="main"；ruby 只有 WebKit 系完整支持，Firefox 要等当年的春季版本，别为它设计依赖排版；hgroup 各家能渲染，但标准一侧已经不鼓励，它只解决主副标题的字号问题。别用：把 dialog 当业务弹窗。

表单增强

input 新类型（email、url、tel、number、date、range、search）、placeholder、required、pattern、autocomplete 能立刻用，不支持的内核会退化成 type="text"，用户照样能填；但原生校验气泡的样式与文案各家不一致，Android 2.3 干脆全不认。date 系列在 iOS 上弹原生选择器、在部分安卓自带浏览器里是裸文本框，这个反差必须实测。datalist 谨慎用：Firefox、Chrome、IE 11 可用，iOS Safari 完全不支持。新类型怎么兼容、校验怎么降级、日期控件要不要拉一份 JS 库，下一篇（1 月 18 日）专讲，这里不展开。

多媒体与图形

audio/video 一句：标签各家都认，难的是编码与移动端自动播放限制，坑在《HTML5 多媒体标签 audio 与 video 的坑》里讲过，别把”能用标签”当”能上线”。canvas 一句：2D 上下文在 IE 9 以上、Android 4.x、iOS 都稳，IE 8 只有 excanvas 那种覆盖面很窄的兼容层。WebGL 一句：桌面三家可用，IE 要到 11 才进，移动端只有较新系统能跑。

存储与离线

localStorage/sessionStorage 各内核都可用，但 Safari 私密模式写入会抛异常，见《localStorage 与 sessionStorage 本地存储实战》；IndexedDB 按上表，别把它当唯一存储；ApplicationCache 坑太多，结论见《Application Cache 离线缓存机制与陷阱》，移动端口径见《移动端离线存储与缓存》。这三块一句带过，不重讲。

设备与通信

Geolocation 能立刻用，各内核都实现，要处理的是用户拒绝授权与 watchPosition 的回调频率、耗电。DeviceOrientation 谨慎用，各内核坐标系和”是否要用户先动一下”的口径不一致。postMessage 一句：IE 8 的实现只能传字符串且有缺陷，IE 9 以上才可用，origin 校验照《postMessage 实现跨窗口安全通信》写。补一句网络口径：当下仍是 XMLHttpRequest 的天下，更简洁的 fetch 类接口在主流内核里还没落地，别按它设计架构。

草案区：看着眼熟但别上线

这四样热度很高，但状态必须写清楚，否则会被当成既有能力排进项目。

<dialog>：只有 Chrome 一家实现，IE 全系与 Firefox 都没有，样式还是 WebKit 那套。要弹窗就用 div 加遮罩；即使要用，也必须写完整的降级。

<template>：Chrome 与 IE 11 可用，Safari 7.1 起可用，Firefox 不支持。它把一段不渲染的标记留在文档里供脚本克隆，价值是真的，但在 Firefox 的占比面前不能裸用；先用 script type="text/x-template" 那种老办法存内容，两边都能跑。

srcset 与 <picture>：前者 Chrome 34、Safari 7.1 已支持，但 2015 年 1 月还不是标准、语法仍在改，各家实现互不覆盖；<picture> 只是草案，只有 polyfill 可用，而 polyfill 会带来重复下载与首屏时间问题。响应式图片当下仍要靠服务端裁剪加 CSS 背景图。

自定义元素、Shadow DOM 与 Web Components：概念在铺开，Chrome 有部分实验实现，其余内核为零，封装规范仍在吵。这一批只能算前瞻，写进技术规划可以，写进需求排期是事故。

语义化实践：六条能直接照做的规范

下面讲写法，只讲旧文没细讲的标签与几个普遍误解。

标题层级：先纠一个错

纪律是 h1 到 h6 按内容层级顺序写、不跳级、一个页面主标题只有一个。要纠的错是”用了 HTML5 就能靠 section 嵌套自动决定标题级别”——那个大纲算法没有任何浏览器实现，到 2015 年初规范一侧也已经不推荐它，section 里的 h1 不会自动降级。所以层级由标题标签名手工排干净，section 只承担分组职责、且要写得出标题。算法来龙去脉见《HTML5 文档大纲与标题层级的正确用法》。

main：一个页面一个，配样式兜底

main 标页面唯一的主体内容，即去掉页头、页脚、主导航与侧栏之后剩下的那块。三条约束：一个页面只有一个；它不能是 header、footer、nav、aside 的后代；里面不放全站重复的内容。老内核要补块级样式，IE 9 以下还要 shiv 才能命中，同时保留 ARIA 地标：

header/footer 的作用域

这两个标签不创建大纲节点，含义随所在区块变化：写在页面顶层是站点页头页脚，写在 article 内部就是这篇文章的头与尾。发布时间、来源、免责这类元信息不该平铺在正文里，该收进 article 级的 header 与 footer。下面这份新闻列表页可直接照抄结构，用到了 time、address、abbr、figure 与 figcaption：

日期用 - 分隔，日期与时间之间可用 T 或空格，时区偏移写 +08:00 或 Z。为什么不把那串直接写进文本？读者看不懂；界面语言会切换，同一篇可能显示”16 Jan 2015”；还有时区——面向多时区时展示文本按访问者本地时区渲染，而 datetime 里的偏移量是绝对时刻，爬虫与结构化数据抽取要的是后者。文本随便换，机器时间不动，这才是 time 的价值。列表页只精确到日就写日期，别硬凑一个零点。顺带说 <data>：语义是”机器可读的值”，但内核对它没有任何特殊行为，写它只能算自我安慰，要挂数据用 span 加 data-* 更实际。

无障碍：role 该补就补

role="main"、role="navigation"、role="contentinfo"、role="complementary" 这几个地标角色在 2015 年初支持还不完整，JAWS 与 NVDA 行为不一，旧版读屏对 HTML5 标签的隐式角色还没学会。补显式 role 的代价只是几个属性，收益是把契约写给还没认识新标签的朗读器，建议保留；地标数量要控制，别为每个小卡片补一个。

常见误用与纠偏

复盘视角看几条高频错误。

为了”语义”把导航写成结构废墟。导航本质是链接列表，nav > ul > li > a 就是最正确的结构，有人为了”看起来语义化”在中间塞几层 div 加类名，反而把列表语义切断了。反过来把没有主题的东西包成 section 是同一类错误：写不出标题的分组就是布局容器，诚实写 div 加 class。

<br> 与 <p> 混用。段落用 p，只在诗文、地址、表单说明这种”必须换行但不是新段落”处用 br；用 br 模拟段落间距等于放弃段落语义，爬虫读不出段落边界。

<hr> 当视觉分割线。它的语义是主题转换处的分割，话题换了才写；纯装饰的线该用 CSS 边框，列表项之间每条插 hr 属于误用。

<small> 的两种误传。一种说它只能写版权，另一种说它不语义别用。HTML5 里 small 的定义是附属信息、免责与法律条款那类小字，版权声明正好落在定义内，这么用是对的；错的是把它当字号工具，或反过来把正文小注塞进 p class="small"。字号交给 CSS。

<b> 与 <i> 不是”不语义”。HTML5 重新定义过它们：b 是视觉上突出但不承担额外重要性的片段（关键词、产品名、手写批注），i 是一段不同语气或语域的文本（学名、外来语、思想活动）。与 strong/em 的分工在于是否加重语义强度，真正该避免的是把它们当 span 的别名挂样式。

最后一个认知误区：因为某内核不认就认定这标签不能用。未知元素的代价只是节点与样式，shiv 加块级声明就能收平；反过来因为 Chrome 能用就直接上 dialog，代价是功能缺失。前者可控，后者不可控，两类要分开评估。

小结：取舍清单与一条纪律

新增语义标签值不值得用，笔者给一份四问清单：这块内容通不通得过旧文那套语义测试？老内核不认时补 shiv 与块级样式能不能收平？辅助技术和爬虫能不能因此读到结构？团队里其他人能不能一致按这条规则写？四问都过就值得用；第三、四问过不了，div 加语义化 class 反而更好——一个一致的 .news-item 比十个理解各异的 section 有用。dialog、picture、srcset、Web Components 这一批，正确处置是写进观察清单而不是排期。

一条纪律收束全文：先看目标内核的支持情况，再谈语义和优雅。语义是内容与工具之间的契约，另一端没上线，签得再漂亮也不生效；另一端已经能读时，也别用 div 假装没有更诚实的写法。想用一个新特性先花五分钟查表、翻一次自家流量日志，这一步做了，关于”要不要用 HTML5”的争论会自己消解。
