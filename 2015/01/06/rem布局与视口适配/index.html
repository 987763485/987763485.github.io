rem 布局与视口适配

去年年底，我们把一个跑了大半年的签到活动页从「固定宽度加 viewport 缩放」迁移到了 rem 弹性布局。方案的骨架、三条适配路线的对比、根字号脚本的雏形与构建期换算任务，我在三个月前的《移动端适配方案：流式与弹性》里已经摊开写过，本文不再重复那张对比表，也不重新论证为什么选弹性。这篇只记录迁移过程中真实踩到的八个坑：字号下限、横屏时序、行高继承、基准漂移、像素漏改、第三方组件隔离、可访问性和调试成本，每个坑都按「现象、根因、修法」复盘，最后给出根字号脚本修好之后的最终版本、可直接投产的构建任务，以及一张「什么项目该用 rem、什么项目别用」的决策表。适合已经把 rem 跑起来、或者正准备把整个团队推向 rem 的同学，尤其是被「明明按方案做了，真机上一跑就出问题」折磨的人。

为什么还是 rem：一个换算式和基准值取法

一句话回顾选型理由：em 相对的是父元素字号，层级一深就互相放大，组件套组件时尺寸不可预测；百分比管得了宽度却管不了以 px 标注的间距直觉，还要逐个换算上下文；px 干脆不等比；rem 相对根字号，意味着全页所有度量都挂在一个可计算的数上，运行时脚本只改这一个数，整页等比缩放。三条路线的完整对比在旧文里，这里不展开。

整套方案的数学就两条式子。运行时：根字号 = clientWidth / 设计稿宽 × BASE；编写期：rem 值 = 设计稿标注 px / BASE。两条式子里的 BASE 必须同出一个来源，这是旧文反复强调的单一数据源，迁移期间我们仍然在这里栽过一次（见后文坑四），所以本文把「构建任务与运行时脚本共享同一份配置」直接做进了代码结构里。

真正值得重新想清楚的是基准怎么取。设计稿常见三种口径，对应的取法并不相同：

设计稿宽 取法 375 设备上根字号 换算除数 特点
375（一倍稿） clientWidth / 375 × 16 16 px 16 除数是整数，1rem 恰等于浏览器默认字号
640（老二倍稿） clientWidth / 640 × 100 58.59 px 100 心算最快（小数点左移两位），但根字号数字很大
750（二倍稿） clientWidth / 750 × 75 37.5 px 75 等价于社区在流传的「根字号钉成屏宽十分之一」做法

整数基准和 clientWidth / 10 两种思路各有明确的利弊。取整数基准（比如统一 1rem 等于 16px 口径）的好处是换算除数永远整数、心算友好，而且 px 兜底版本与浏览器默认字号衔接自然，脚本失效时页面不至于全塌；取 clientWidth / 10（也就是 750 稿配 BASE 75）的好处是根字号与设计稿解耦，1rem 恒等于屏宽的十分之一，在任一设备上估读尺寸都很直观，缺点是除数随稿宽变化（375 稿是 37.5、640 稿是 64、750 稿是 75），37.5 这种非整数除法必须由构建任务统一舍入规则，绝不能靠人手算。我们最终选了 750 稿加 75 这一档，原因很实际：设计侧已经全面交二倍稿，而 75 是三者里最少见的踩坑样本数——它既避开了 100 基准在 iOS 6 上暴露出的「rem 数值太小触发舍入抖动」，又让 data-fz 属性里的读数保持在 30 到 44 这个人类容易核对的区间。

viewport 一行仍是标准写法 width=device-width, initial-scale=1.0，target-densitydpi 早在 2013 年底随 Android 4.4 换内核就已经彻底失效，旧模板里的要删干净，其余参数语义在《HTML5 meta viewport 与移动端适配基础》里讲透了，本文不再碰。

根字号脚本的最终版本：比三个月前多了五处防护

旧文里的雏形脚本已经具备上下限夹取和一次性延时重算，但迁移项目上线两周后，真机反馈逼着我们又加了五处防护：双次校正、变化才回写、旧版旋转连发清理、Android 2.3 整体走 px 覆盖表、以及把基准值本身写进 data-fz 属性供 CSS 与调试对齐。下面是修好之后的最终版本，逐行注释，可以直接抄走改配置。

有一处与旧文的路线差异要说明：雏形脚本对 Android 2.3 的处理是在手写 CSS 里保留 px 兜底声明，靠 data-rem="off" 加属性选择器救回来。这个方案在迁移中暴露了两个问题——手写双声明漏一处就崩一处，而 2.3 对属性选择器与后代组合器的解析在个别定制 ROM 上不稳。最终版把兜底彻底挪到构建期自动生成（下一节的 legacy 覆盖表），业务同学写 CSS 时完全不用管这件事，只需要保证脚本里那行 data-fz 写对。

脚本的位置与执行时机同样是拿事故换来的。它必须内联在 head 顶部、排在任何样式表之前：根字号晚一帧写入，首屏就会先按 CSS 里兜底的 37.5px 排版、再被脚本改成真实值重排一次，长页面上肉眼可见是一次整页跳动。兜底值选 37.5px 也有讲究——它是 750 稿口径下 375 设备（当年 iPhone 6 的主力宽度）的真实读数，把兜底钉在存量最大的那一档，脚本失效或迟滞时的观感损失最小。整段脚本压到 1KB 以内、除一个属性读取外不做任何多余的 DOM 查询，才配占用同步阻塞的预算；哪天有人往里加首屏埋点或者设备探测，就是要把它拆出去重新审视执行时机的信号。data-fz 在脚本位的第一次同步执行里就写入，联调时用 Elements 面板直接看 html 节点，任何人报「字号不对」，第一步都是先看这个属性，而不是先翻 CSS。

构建期换算：Grunt 0.4 任务与 gulp 3.8 等价流

写 CSS 时照抄设计稿标注的 px，构建期换算成 rem，这件事旧文做过一个最小任务，但它的正则在三个地方会失手：-1px 这种带负号的值被截成 -.0133rem 加残留、0.5px 的小数部分匹配不全、以及最要命的 @media (max-width: 540px)——媒体查询里的长度值参照的是初始包含块和初始字号，跟根字号无关，被换算进去整组断点直接失效（CSS Values 3 与 Media Queries 3 对这两个单位的解析基准写得很清楚，rem 在媒体查询里当时根本没有定义）。迁移期我们给换算任务补了结构化的边界规则，全部收进一个 Node 模块，Grunt 与 gulp 共用。

规则的优先级是这样的。先看行：落在 @media 块内的整段不碰；含 url( 的行整行不碰（banner-640px.png 这种文件名会被裸正则咬掉）；行尾注释里写了 no-rem 的不碰，这是留给三个白名单场景的人工豁免通道——1px 边框、字号下限相关声明、图标物理尺寸，这三类值要么本来就该钉死物理像素，要么豁免理由只有人知道，机器不该猜。再看值：绝对值不超过 keep（我们配 2）的不换算，这一条自动兜住了 1px 边框和 0px（值为 0 的另外单独短路，0 和 0rem 虽然等价但 0rem 会在某些老内核上多一次解析分歧）。负值保留符号一起换算，-24px 的偏移量该缩放就该缩放，但 -1px 会命中 keep 白名单留下。

页面模板里两个样式表按顺序挂：mobile.rem.css 正常引，mobile.legacy.css 也正常引——认得 rem 的浏览器里 data-fz 永远不会等于 off，覆盖表里的选择器匹配不到任何元素，代价只是一次额外的样式表下载；2.3 上脚本挂出 data-fz="off"，覆盖表用 html[data-fz="off"] 的权重（属性选择器加元素选择器，高于一切单类）把尺寸逐项钉回设计 px。当时 gulp 3.8 已经可用，但 px 转 rem 这类贴合自家构建的活儿社区插件不如 Grunt 生态齐全（主流自动化插件是这一年之后才流行起来的），自己包流反而更短：

三条纪律沿用旧文：输入必须是编译产物 CSS 而不是源码（源码里只出现 px，标注与代码永不脱钩）；base 从配置 JSON 里读，与运行时脚本同源；报告文件每天构建都产出，谁写的 px 没进换算链，清单里见。

legacy 覆盖表的代价要说清楚：它让认得 rem 的浏览器也白白下载了一份用不上的样式表，活动页每多一档布局就 multiply 出一份 html[data-fz="off"] 前缀的规则，文件体积大约是主表的三分之一。我们权衡后接受了这个浪费，因为另两条路更糟——按 UA 动态插 link 会把首屏样式的应用时机推迟到脚本之后，闪烁窗口比现在大得多；把覆盖逻辑塞进主表尾部则依赖声明顺序与权重压制，正是旧文雏形方案在定制 ROM 上翻过的车。2.3 的存量曲线当时还在往下掉，这份体积债预计一年内就能还清，事实上也是第二年随最低内核上调一起删掉的。

图片与倍图在 rem 里的单位陷阱

容器用 rem 定宽高、背景图用 background-size: 100% 100% 收拢，是唯一不会互相打架的组合：

@2x 图的单位陷阱在于很多人会把 background-size 按设计稿标注写成 750px 320px。这条值一旦写死 px 又逃过了构建（比如整行走 no-rem 豁免），容器在缩、图不缩，375 设备上一切正常，414 设备上头图右下缺出一块。写成百分比则容器与图永远同比例，构建链根本不参与，最稳。srcset 当时还没标准化、各内核支持残缺，倍图依旧只能靠 dpr 媒体查询在构建期分档或像这里一样直接上 2x 素材缩回逻辑尺寸。图标尺寸若要跟页面等比缩放，同一段写法把宽高换算成 rem 即可；若要钉死物理尺寸，宽高加 no-rem 豁免、background-size 写回逻辑 px。1px 边框在 rem 页面会被视觉放大这一问题更精细，处理方案在《移动端 1px 边框问题》里已经讲透，一句带过，不重复。

八个坑逐条复盘：现象、根因、修法

坑一：字号下限被浏览器夹住，正文突然「不缩放」

现象：iPhone 6 一切正常，iPhone 4（320 宽）上正文小得像脚注，但标题间距却按预期缩了；更怪的是同一页面在桌面 Chrome 里把窗口拉到 300px 宽，正文反而「卡住」不再变小。根因有三层。其一，桌面 Chrome 对中文页面有最小字号夹取（实测约 12px 一线，视语言与版本略有出入），低于它的 rem 计算值被强制抬回去，而间距、宽高不受此限制，于是文字与度量脱钩；其二，Android 2.3 原生浏览器对过小字号直接忽略或触发自己的字号膨胀逻辑，rem 算出来的 9px、10px 根本不被采纳；其三，-webkit-text-size-adjust 的取值——iOS 8 上写 none 与写 100% 的行为差别这一年被讨论得很多：none 是完全关闭字号调整，iOS 8 上实测连双指缩放时的文字同步放大都被取消，可读性问题很大；100% 是把自动调整锁定在一倍，既挡住横屏时 Safari 自作主张放大正文，又不影响用户缩放文字。所以我们的结论是：字号照样用 rem 走，但正文必须有下限，text-size-adjust 统一写 100%。

.417rem 这个数是反推出来的：脚本的 MIN_FONT 夹在 30px，正文要在最夹死的情况下仍不小于 12.5px，12.5 / 30 ≈ .417。也就是说字号下限不是 CSS 单方面能保证的，它是「根字号下限乘 rem 值」的联合不等式，下限策略必须同时写进脚本（本文最终版脚本里的 MIN_FONT）和排版规范（正文 rem 值不得低于 .333rem，即 12px 除以 36 的中间档读数）。这一条当时花了三天才想明白，因为所有人都只盯着 CSS 找原因。后来我们把验证方法也固化成一条：怀疑字号被夹取，就用 getComputedStyle 读元素实际渲染值，和设计稿换算值一比，差值出现在哪一档设备上、是否恰好落在 12px 一线，两分钟就有结论，不用再靠肉眼在真机上「觉得字小」。

坑二：横屏之后布局错乱，脚本明明监听了旋转

现象：iPad 与部分 Android 4.x 横屏后页面右侧留出一条约 40px 的空白，手动捏合一下才恢复。根因是时序：orientationchange 回调触发的那一帧，document.documentElement.clientWidth 往往还是旋转前的旧值，此时算出的根字号是旧方向的，而布局已经按新方向重排；iOS 上地址栏的收起、Android 上旋转动画的收尾还会再晚几百毫秒。修法就是最终版脚本里的双次校正：事件回调里立刻算一次保证不长时间错版，再排 100ms 与 300ms 两次延时复核，配合「值变了才回写」避免三次重排；pageshow 再兜住 bfcache 回退不重跑 head 脚本的场景。输入法收起时部分内核也发 resize，宽度其实没变，靠同一道回写判断挡住；键盘弹出对布局的完整影响面在《移动端输入法弹出与布局问题》里另有专文，本文按下不表。顺带一提，IE Mobile 在旋转时是否同样存在读数滞后，我们没有真机，标注为需实测。

坑三：line-height 用 rem，嵌套行高越套越乱

现象：标题区行高正常，嵌了一级小字说明后，说明与下一行的间距「显得」比设计稿大一截，层级越深越松散。根因：line-height: 1.4rem 这类写法把行高钉成了一个与字号无关的绝对值，子元素字号改小时，继承来的行高纹丝不动，行框相对字面越拉越开——当时组内管这叫「累积」，严格说是失配而非累乘；真正会累乘的是 em 写法（父 1.5em 折算成 px 后被子元素再乘）。正确写法是用无单位数值，让每个元素按自己的字号重新解析倍率：

无单位数值还有个副作用正好是我们想要的：它不参与 px 转 rem 的换算链，也不会被最小字号夹取搅乱比例。规范里从此多了一条：行高只许写无单位倍率，构建任务对 line-height 带单位的声明一律进人工清单。

坑四：组件里的 em 与页面的 rem 混用，换个页面基准就漂

现象：一套用旧组件库改的活动组件，在 A 页尺寸严丝合缝，挪到 B 页整体胖了 18%。根因：组件内边距写的是 em，相对的是自身字号，而组件的字号在设计时被默认 16px 基准调过；B 页根字号 41.4px（414 设备），组件字号随之变，padding 跟着字号放大，等于被缩放了两次。复盘结论有两条：组件内部一律统一用 rem，禁止 em 参与度量；确实要同时活在 px 体系和 rem 体系里的组件，必须在组件文档头一行写明「当前基准」——我们的做法是要求这类组件把根读数声明成 data-rem-base: 750 稿 / BASE 75，并在集成时用 data-fz 属性做一次运行时对账，读数与声明对不上直接报警。data-fz 写进属性这一处防护，最初就是为这个坑加的。

坑五：绝对定位与 background-position 的 px 漏改

现象：页面整体正常，只有角标气泡偏出 12px、分享图背景定位在小屏上往右下跑。根因：这两类声明的值经常是「两个以上数字」的列表（background-position: 12px 20px、box-shadow: 0 2px 6px rgba(...)），而漏改往往发生在后来手工追加的样式里——它们没走 Less 主链，直接写进了页面的 style 块，构建任务根本看不见。修法一半靠纪律（禁止页内手写带 px 的定位与背景声明），一半靠工具：构建任务每天输出的 px-report.txt 里，「请人工确认」那一段就是为此准备的——未进入换算链的行会连同行号列出来，review 只筛这一节，五分钟看完。上线前那两周，这份清单替我们抓出过十七条漏网声明，其中十一条正是各类偏移与背景定位。

坑六：第三方组件内部是 px，被根字号衬托得不协调

现象：页面换 rem 后，同页的轮播（当时用的 Swiper，接法见《Swiper 轮播图组件实战》）指示器圆点和地图控件明显比周围小一圈。根因：rem 只缩放自己参与换算的声明，第三方 CSS 里的 px 是钉死的物理值，周围一切放大 1.1 倍后，它们自然显得缩了水。当时的隔离做法分三层：第三方样式文件绝不进构建换算链（它的 url() 与像素级声明经不起正则扫）；组件外面包一层 .no-rem 容器，容器自身宽高用 rem 定、内部区域交给组件按 px 自管，接受「组件区不缩放」这个视觉差；实在要求同步放大的，才用 JS 读 data-fz 当前读数、给容器加 -webkit-transform: scale() 的临时方案，代价是文字发虚与触点坐标偏移，只在头图区用过一次。

社区当时还流传一种更巧的说法：把第三方 CSS 按 1rem 等于 10px 的口径转成 rem，再用 .no-rem 容器把「字号基准钉回 10px」——思路方向是对的（给组件一个独立的度量宇宙），但落地有个绕不开的死结：rem 的定义只认根元素，容器上的 font-size 无论钉成多少，都改变不了组件里 rem 值相对 html 的解析结果，能钉回的只有 em 口径，而 em 一进嵌套继承又会把坑四的漂移带回来。我们试过半途（组件内文字用 em 换算、度量仍留 px），两周后回滚。这套取舍在 2.3 覆盖表与第三方容器之间还牵出过一次样式权重对撞：legacy 表的前缀选择器把 Swiper 容器内的兜底规则也盖住了，最后靠覆盖表只限定自身业务选择器、绝不生成组件库内部的规则解决。

坑七：rem 让系统字号设置失效，可访问性的账要认

现象：测试同事把浏览器「字体大小」调到最大再开我们的页面，毫无反应。根因：rem 体系里所有文字尺寸都相对根字号，而根字号被内联脚本按视口宽度写死在 style 上，用户在浏览器或系统层设置的字号偏好，到不了这个被覆盖的根。中间我们试过一条看起来两全的歪路：布局与间距走 rem、正文文字保持 px 并允许系统设置影响它。结果两周后灰度回来是双输——文字不随屏幕缩放，在 320 窄屏上挤成三行、在 414 宽屏上小得像未适配；而「布局等比、文字固定」的组合让设计稿对不上了，改版沟通成本比纯 rem 还高。这条路线的教训是：rem 方案里文字与度量必须同一宇宙，把文字单独摘出去等于同时放弃两种方案的好处。这不是 bug，是方案的结构性代价：等比缩放与尊重用户字号偏好，二者只能取其一。我们的取舍是：活动型、强还原度的页面取等比，但保住双指缩放（viewport 不写 maximum-scale，text-size-adjust 用 100% 不用 none，理由见坑一）；内容型页面反过来，宁可放弃根字号脚本走流式加 px，也不能让用户「调大字体」的设置变成摆设。
这个分界线后来写进了团队的立项检查表，一句话概括：文字必须可读优先，缩放方案服务谁，要先问清楚。最低内核与厂商差异层面的完整清单，见《移动端浏览器兼容问题汇总》，不展开。

坑八：调试一个「字号为什么跳」，成本比修 bug 还高

现象：联调期最频繁的问题不是样式写错，而是「当前基准到底是多少」说不清——CSS 里 0.427rem，设计师问这是几 px，脚本此刻算出的根字号是多少，三方各说各话。修法是把读数变成一等公民，最终版脚本的 data-fz 属性加一段调试快照：

.debug-probe 是排版规范里规定的一个探针元素：高度写死 1rem，藏在页面角落。任何人报「字号跳了」，先让他控制台敲 __ADAPT_DEBUG()，三个读数（视口宽、属性基准、计算根字号）一对，是脚本算错、夹取生效、还是 CSS 换算除数不同源，五分钟定性。线上必须移除这段的原因有三：真机连不上调试台时老内核访问 console 直接抛错（所以上面加了守卫，但守卫挡不住 setInterval 白耗的性能）；基准读数对竞争对手是白送的情报；以及最重要的——留着它，团队就永远不会把「读数可查」当成构建期的责任。

决策：什么样的项目该用 rem，什么项目别用

八个坑爬完，最大的收获其实是学会了拒绝。迁移后期我们立了一张准入表：

判断维度 适合 rem 别用 rem
设计稿宽度口径 全线统一二倍稿，标注即尺寸 每档屏幕各出一稿，缩放解决不了结构差异
iPad 与桌面端 不需要，或接受定宽居中 必须认真适配大屏（夹取之后等比就断了）
第三方内容 可控组件，能走隔离容器 富文本、编辑器输出内联 px，缩放管不住
构建链就绪 Grunt/gulp 任务与同源配置已建好 靠人手换算，两周后必漂
最低支持内核 Android 4.1 以上为主 2.3 存量显著的机型盘子（覆盖表能兜但体验打折）
页面性质 活动页、App 内嵌 H5、强还原度 长图文、阅读为主、字号偏好必须尊重

两个返工案例各自验证了表里的一行。第一个是 iPad 版：750 稿脚本线性外推，768 宽的 iPad 上根字号冲到 76.8px，正文合到 30px 开外，整页像被拉大的手机截图，运营的第一反应是「你们把网站做老气了」。这正是等比直线上限不设防的下场，补救是 MAX_FONT 夹取加超过 480 后容器定宽居中、两侧留白——夹住之后页面不再严格等比，这层「失真」要提前跟设计侧讲明白，别等人来找你。第二个是春节活动页：同事为了「保证所有机型一致」，把根字号写死 37.5px 再给 body 加 min-width: 375px，小米 2 与一批 360 宽机型一进微信内置浏览器就横向溢出，滚动条拖出一块空白底。排查时我们在那台小米 2 上挂了这个项目的调试快照，读数一眼看穿：clientWidth 是 360，布局视口没被 min-width 绑架，是 body 自己以 375 的下限横穿了屏幕——浏览器不会替你兜住 CSS 层面的自我矛盾。微信的 UA 里带 MicroMessenger，内嵌 X5 对 viewport 的处理与系统 Safari 本就有出入，「写死基准加 min-width」等于同时赌内核缩放兜底与赌屏宽下限，两头都赌输了。修法回归动态基准加 MIN_FONT 下限、删掉 min-width 让窄屏真实缩排——基准必须是个函数，不是常量，这是我们用一次线上事故换来的结论。

如果今天重做，这三条我会先定下来

回看整个迁移，真正省事的决定都在第一批：第一条，基准取 clientWidth / 10 口径、上下限写进脚本而不是文档里，任何「保证某机型上基准是 X」的诉求一律翻译成夹取参数，绝不允许写死；第二条，px 兜底产物与人工清单从第一天就是构建任务的固定输出，而不是出了 2.3 事故之后补的补丁——旧文方案里手写的双声明兜底，就是在用人力偿还工具欠的债；第三条，rem 的适用面白纸黑字限定在活动页与内嵌 H5，内容型页面走流式加 px，两套规范并行，别让一个团队只有一种锤子。这三条都不涉及任何高深技术，全是流程与边界，但八个坑里有六个的根源能追溯到它们没在第一天定下来。

小结：一张迁移 checklist

抄一份贴工位，迁移前逐项打勾：基准取值定了吗（设计稿宽、BASE、与运行时同源的配置在哪）；三条白名单划了吗（1px 边框、字号下限、图标物理尺寸，no-rem 注释纪律宣贯了吗）；构建任务三份产物都出吗（rem 双写、legacy 覆盖表、px 报告）；根字号上下限是多少、夹取后的失真边界和设计侧对齐了吗；真机清单含 320 与 360 两档窄屏、iPad、Android 2.3/4.x、微信与 QQ 内嵌浏览器吗；调试快照与 setInterval 上线前移除了吗；第三方组件走「不进换算链加隔离容器」了吗；行高、偏移、背景定位的无单位与豁免规范写进 CSS 守则了吗。rem 适配从来不是「用了这个单位就自适应了」，它是把全页缩放压到一个数上的杠杆——杠杆本身很短，支点（基准）、限位（夹取）和配重（兜底与白名单）才是这套方案的全部工程含量。
