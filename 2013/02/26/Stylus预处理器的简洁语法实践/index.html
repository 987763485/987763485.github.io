Stylus 预处理器的简洁语法实践

本文属于《HTML 与 CSS》第 58/62 篇
上一篇系列目录下一篇

CSS 写长了总会遇到一些让人烦躁的重复：同一个主色要抄十几遍，圆角要写三行浏览器前缀，改一次字号得全局搜索替换。预处理器就是为解决这类问题而生的。本文以入门视角梳理 Stylus 的核心语法与常用写法，适合已有 CSS 基础、正打算换一个更顺手的预处理器的前端开发者。读完本文，你应该能看懂一份 Stylus 源码，会写常用的 mixin，并能把一个小项目的样式从纯 CSS 迁移过来。

CSS 预处理器的三家与 Stylus 的位置

Less 在 2009 年发布，走”尽量贴近 CSS”的路线，分号、冒号、大括号全保留，只额外加了变量和 mixin，学习成本最低。Sass 诞生于 2006 年，2010 年的 Sass 3 引入大括号形式的 SCSS，功能最全，Compass 生态也最厚，是当时最主流的选择。

Stylus 由 TJ Holowaychuk 在 2010 年底创建，他也是 Express 与 Jade 的作者。Stylus 的态度相当激进：分号、冒号、大括号、变量符号，能省的全省。它直接跑在 Node.js 上，和当时已经铺开的 Node 工具链衔接得很自然，2012 年已经足够可用，Hexo 默认主题 landscape 就大量使用它写样式。

三者的本质是同一条流水线：源文件编译后产出标准 CSS。选型只看团队更喜欢哪种书写风格。

flowchart TD
    A[编写 .styl 源文件] --> B[stylus 命令行或 Node 模块编译]
    B --> C[输出标准 .css]
    C --> D[浏览器渲染]

之所以强调”编译后产出标准 CSS”，是因为它意味着预处理器不引入任何运行时依赖。浏览器不会因为你在用 Stylus 而多加载一个脚本，老项目里混着纯 CSS 和 Stylus 源码也完全没问题。这也是它和 2010 年前后出现的 less.js（可以在浏览器端实时编译）在思路上的分岔：后者把编译成本转嫁到了用户机器上，适合本地演示，不适合线上部署。

mixin 与普通函数的边界

Stylus 里 mixin 和函数其实是同一种东西。带参数的可以返回值，不带参数的更像是插入一段声明。判断依据很简单：定义体里最后是不是一条属性声明。

一次小型迁移

如果想把现有项目搬过来，可以按下面三步走，风险最低：

第一步，装好命令行工具，把现有 CSS 原样复制成 .styl。Stylus 完全兼容标准 CSS 语法，这一步应该零报错。

第二步，把重复出现的色值、字号、间距抽成变量，集中在文件头部或单独的 variables.styl 里。

第三步，把带浏览器前缀的片段（圆角、阴影、渐变、过渡）逐个换成 nib 的函数或自己写的 mixin。

不要一开始就重写样式。迁移的目的是先跑起来，再逐步替换。每完成一批就用编译产物和源文件对比一下，确认输出符合预期。

坑与注意事项

第一，缩进敏感。编辑器必须统一用空格缩进，tab 和空格混用时 Stylus 的报错常常只给一个不准确的行号，团队协作前先在 .editorconfig 里约定好。

第二，嵌套层级不要太深。预处理器的嵌套是给人看的，编译出来全是后代选择器。三层以上就该停下来想想是不是该抽成类。

第三，@import 默认按 .styl 解析并把内容内联，想让编译器原样保留一条 CSS 的 @import，要用 @require，或把文件命名成 .css 后缀。

第三，@extend 会拉长选择器。一个基类被十几个选择器继承后，编译产物里选择器会有十几项，IE 6/7 下解析开销明显增加，别滥用。

第四，预处理器不兜底兼容性。Stylus 不会替你把 CSS3 属性加上所有前缀，该用 nib 就用 nib；IE 8/9 的 Flexbox 也仍要靠老语法或回退方案。

小结

Stylus 的吸引力是”少写字”：缩进代替大括号、= 定义变量、冒号可省、mixin 不需要声明关键字，同样一份样式它的源码量通常比 Less 和 SCSS 少三成左右。优先掌握 mixin 与内置颜色函数，它们直接决定复用主题和统一视觉规范的效率。@extend 能减少重复声明，但别把选择器拉得过长。落地时先装命令行工具挂 watch，需要控制流程再走 Node 模块的 render。至于坑，记住缩进统一、报错看上一行、前缀自己管这三条，就能平滑上手。
