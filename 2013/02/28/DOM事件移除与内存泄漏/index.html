DOM 事件移除与内存泄漏

页面越写越久，不少人遇到过这种现象：一个单页操作来来回回几十次，浏览器内存从几十 MB 一路爬到几百 MB，标签页最后直接卡死或崩溃。问题往往不在业务逻辑，而在被遗忘的事件监听器。本文讲清楚事件绑定在底层是怎么被记录的、为什么会泄漏、怎么用 jQuery 1.9 之后的 API 干净地移除，以及如何自己动手验证。适合已有 jQuery 使用经验、开始关心页面长跑表现的读者。

事件监听器在底层是什么

addEventListener 给某个 DOM 节点注册监听器，浏览器内部会为这个节点维护一张监听器表。只要节点还活着、表里还有记录，与监听器关联的回调函数以及回调闭包引用的所有对象都不会被垃圾回收。

关键在第二句话：移除节点不等于移除监听器带来的影响。把一个节点从文档树上 detach 掉，只是把它从父节点的子节点列表里摘掉，浏览器并不会主动清空这张表，节点本身连同它的监听器仍留在内存里，直到没有任何路径能引用到它。

更隐蔽的是 jQuery 这类库自己维护的一份缓存。jQuery 把数据存在 $.cache 里，给节点分配一个内部 id 关联过去。也就是说你 .on() 绑的东西，不只是浏览器的一张表，还有库自己的一份账。

flowchart TD
    A[DOM 节点] --> B[浏览器监听器表]
    A --> C[jQuery 数据缓存]
    B --> D[回调函数]
    C --> D
    D --> E[闭包引用的外部对象]
    E --> F[只要回调可达 这些对象就不可回收]

循环引用：IE 6/7/8 的经典老账

在 IE 6/7/8 的回收器里，DOM 节点不是纯粹的 JS 对象，而是 COM 对象，JS 对象与 DOM 对象各自用引用计数管理，两边计数器互不相通。于是一旦形成环，引用计数永远归不了零：

DOM 节点 el 通过 onclick 属性引用匿名函数，匿名函数又通过闭包引用 el，形成环。IE 解不开它，节点和函数一起留在内存里。当年这是 IE 下”页面开着不走、内存只涨不掉”的头号嫌疑。

规避手段当时有三条：把引用置空、用事件委托代替逐节点绑定、或者不用闭包捕获节点。

Firefox、Chrome 20、IE 9 及以后的回收器用标记清除，能正确处理这类环。但监听器本身导致的泄漏跟回收算法无关，那是下一节的内容。

重灾区：动态节点重复绑定

实际项目里最常见的模式是这样的：列表数据刷新一次，就往新渲染出来的节点上绑一次事件，旧节点被整体替换，但绑定时传入的回调里引用着一些长生命周期的对象，这些节点连带回调全都出不去。

html() 替换掉旧节点后，旧 li 上的监听器仍挂在 jQuery 缓存里，回调闭包引用的对象也跟着留下。刷新一百次就攒下一百份，Chrome 开发者工具里能看到 DOM 节点数单调上涨。

用事件委托绕开它

如果业务允许，最彻底的办法是不往动态节点上逐个绑，而是把监听器挂在稳定的父容器上，靠事件冒泡处理：

on 的第二个参数是选择器，只有点击落在匹配 li 的后代上时才触发，回调里的 this 指向那个 li。这样列表刷新多少次，监听器始终只有一个。这个委托写法在 jQuery 1.7 引入，之前要写 .delegate()，1.9 里 .delegate() 仍可用但已标记过时。

用 jQuery 移除事件

jQuery 1.7 把绑定统一收敛到 .on() / .off()，1.9 又彻底删掉了 .live()。所以现在只有一条正路。

on 与 off 必须成对

最关键的细节：匿名函数绑上去就摘不掉了，只能整体清空。想精确移除，必须先把函数存下来。

命名空间管理一批事件

给同一模块的事件加统一命名空间，销毁时一次性摘除，是比较工程化的做法：

.off('.dialog') 把三种事件全部移除，而不碰别人绑在同一节点上的事件。多个模块共用一个节点时这个区分很重要。

代理事件的移除

委托绑定的事件同样能精确移除，参数结构保持一致：

选择器不传的话，.off('click') 会清掉 #list 上所有 click 处理器，包括其他模块委托上来的，这点要小心。

一张表看清绑定与移除的对应

目的 写法 说明
绑定单个元素 $el.on('click', fn) 最常用
绑定并委托 $el.on('click', 'li', fn) 子节点动态增删不必重绑
精确移除 $el.off('click', fn) 必须传同一个函数引用
移除委托 $el.off('click', 'li', fn) 三个参数都要对上
按命名空间移除 $el.off('.mod') 模块销毁时批量清理
移除某类型全部 $el.off('click') 会清掉别人绑的，慎用

jQuery 1.9 起 .bind()、.unbind()、.delegate()、.undelegate()、.live()、.die() 全部进入过时或已删除状态。写新代码一律用 .on() / .off()，读老代码时看到那六个方法要知道它们是同一件事的旧写法。

原生 API 的对应关系

脱离 jQuery 时，removeEventListener 语义一致：类型、函数引用、capture 三个参数必须与添加时完全相同。

IE 8 及以下没有标准 API，要用 attachEvent / detachEvent，且回调里 this 指向 window 而非触发元素。用 jQuery 的一大好处就是把这层差异和 this 指向都替你抹平了。

怎么验证自己没泄漏

第一，查 jQuery 内部缓存。jQuery 1.9 之后可以这样看还有多少节点挂着数据：

操作完再查，数字不往下掉，说明节点和数据都没释放。

第二，Chrome 的堆快照。Chrome 20 的 Profiles 面板选 “Heap snapshot”，操作前后各拍一张，用对比视图筛选 “Detached DOM tree”。正常情况下这里应该是空的，出现成百上千个游离节点就是泄漏的铁证。

sequenceDiagram
    participant 用户 as 用户
    participant 页面 as 页面
    participant 堆 as 堆内存
    用户->>页面: 执行一次列表增删
    页面->>堆: 拍第一张快照
    用户->>页面: 反复增删 100 次
    页面->>堆: 拍第二张快照
    页面->>堆: 对比两次快照
    堆-->>页面: Detached DOM tree 数量
    页面->>用户: 持续增长即为泄漏

第三，人工观察。任务管理器盯着标签页内存，反复操作同一功能，看曲线是回落还是只涨不跌。方法粗糙但直观，适合先定位到是哪个操作触发的。

两个高频场景的写法

场景一：弹窗打开时绑事件，关闭时摘掉。这是最容易忘的一处，因为关闭的路径往往不止一个——点确定、点取消、按 Esc、点遮罩，四条路都要走到同一段清理代码。

场景二：给 window 或 document 绑 resize、scroll。这类事件触发极其频繁，处理函数如果引用着某个已经被销毁的组件，泄漏会更明显。

小结

事件泄漏的本质不是”忘了移除监听器”这一句话，而是监听器让节点、回调函数、闭包引用的对象形成了一条摘不断的可达链。IE 6/7/8 的循环引用是这条链的经典形态，现代浏览器虽能解环，但链本身依然成立。应对上优先用事件委托减少绑定总量，需要显式绑定时务必保存函数引用，销毁时用命名空间批量 .off()。验证靠 jQuery 的 $._data、Chrome 的堆快照对比和 Detached DOM tree 过滤。养成”绑定与移除成对、销毁模块时清命名空间”的习惯，比事后调试省力得多。
