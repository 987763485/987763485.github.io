Sass 与 Less 预处理器入门对比

本文属于《HTML 与 CSS》第 59/62 篇
上一篇系列目录下一篇

刚接触 CSS 预处理器的人常问的第一个问题是：Sass 和 Less 到底选哪个？两者都能写变量、嵌套、混入，看起来只是符号不同，实际用下来才发现它们在语法哲学、编译环境、生态成熟度上的差异相当大。本文以一个真实选型过程为线索，从语法、功能、工具链三个层面做一次入门对比。

两者的出身与运行环境

Sass 由 Hampton Catlin 在 2006 年设计，2007 年发布，最初只有缩进式语法。2010 年 5 月 Sass 3 引入了 .scss 语法，也就是今天绝大多数人使用的带大括号的写法，并且完全兼容 CSS 3。Less 由 Alexis Sellier 在 2009 年创建，语法从一开始就是 CSS 的超集，大括号加逗号分号，一眼看上去和原生 CSS 没什么区别。

语法风格与变量

Sass 同时支持缩进式 .sass 与大括号式 .scss，Less 只支持大括号式。对比一下同一段代码：

肉眼可见的差别是变量符号：Sass 用 $，Less 用 @。这个差别带来一个很实际的麻烦——Less 的 @ 和 CSS 原生的 @import、@media、@keyframes 挤在同一个命名空间里。在 Less 里写 @media (max-width: 600px) 时，解析器要区分这是原生规则还是变量引用，早期版本偶尔会出现误判；Sass 的 $ 则完全没有这个歧义。

Less 还有一个特性：变量是”惰性求值”的，声明顺序不影响使用，甚至可以后置声明。Sass 的变量则要求先声明后使用，未定义直接报错。初学者常常觉得 Less 更宽松，但在大型样式表里，这种宽松反而让人难以追踪一个变量到底在哪里被定下来。

Less 早期几乎没有控制指令，条件判断要靠”守卫”（guard）这种曲线方式实现，2013 年前后才陆续补齐。这也是当时选型时偏向 Sass 的一个重要原因：做设计系统，循环和颜色函数是刚需。

另外值得一提的是源码地图。2013 年 Sass 3.3 开始支持 source maps，配合 Chrome DevTools 可以直接调试到 .scss 源文件的行号；Less 稍晚也提供了 --source-map 选项。在此之前，只能对着压缩后的 CSS 猜，改一个样式要找半天。

我们的选型结论

那次选型的背景是：一个偏展示型的中台项目，设计规范已经定稿，需要把主题色、间距、字号抽成变量，并要支持一套响应式网格。团队成员更熟 Node，但没人写过 Sass。

最终我们选了 Less，理由很朴素：不需要 Compass 那些重功能，构建链路已经是 Node，lessc 一条命令就能跑起来，团队上手只花了半天。后来这个项目要扩展出多主题，Less 在循环和颜色运算上的短板才开始疼，第二批页面我们又迁回了 Sass。

所以选型不该问”哪个更好”，而该问三个问题：

flowchart TD
    A[选型起点] --> B{构建环境是什么?}
    B -->|Ruby / 静态站| C[Sass 优先]
    B -->|Node / 前端工程化| D[Less 上手更快]
    C --> E{需要主题/网格/复杂运算?}
    D --> E
    E -->|是| F[Sass 更合适]
    E -->|否| G[Less 足够]

一是环境匹配，Ruby 项目用 Sass、Node 项目用 Less，摩擦最小；二是功能需求，需要大量颜色运算、循环生成、设计系统，Sass 的能力储备更足；三是团队惯性，大家都会用的那个才是能长期维护的那个。若三者冲突，优先保团队惯性，语法可以学，维护成本降不下来。

小结

Sass 与 Less 的入门门槛都不高，一天就能写出能用的样式表，真正的差异在后面：@extend 与复制式混入导致的体积差异、颜色函数与控制结构的完备度、Compass 级别的框架生态，以及 Ruby 与 Node 两条工具链的融合成本。2013 年的社区共识基本是”Sass 更强，Less 更轻”，这个判断至今变化不大。对个人项目，选顺手的那个；对要长期演进的团队项目，建议从一开始就选功能上限更高的那个，因为预处理器一旦铺开到上百个文件，迁移成本会高到让人放弃。
