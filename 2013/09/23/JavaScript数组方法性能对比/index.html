JavaScript 数组方法性能对比

写数据处理的代码时，我们常常凭手感挑一个数组方法：要过滤就 filter，要转换就 map，看起来都一样。可一旦数据量上来，或者在低端安卓机上跑，不同写法之间能差出好几倍。更危险的是有些方法不只是慢，还会静默给出错误结果。本文以一次表格渲染优化的过程为例，把 ES5 里可用的数组方法逐个过一遍。

先建立坐标系：复杂度与适用面

ES5 时代我们手里的原生方法并不多，主要就是 forEach、map、filter、reduce、some、every、indexOf、join、concat、slice、splice、reverse、sort，加上 Array.prototype 上少数几个辅助方法。先把它们按”复杂度”和”是否返回新数组”分个类，心里有个谱：

方法 时间复杂度 返回值 原地修改
forEach O(n) undefined 否
map O(n) 等长新数组 否
filter O(n) 长度不大于原数组的新数组 否
reduce O(n) 任意累计值 否
some / every O(n)，可提前退出 布尔值 否
indexOf O(n) 下标或 -1 否
join O(n) 字符串 否
concat / slice O(n) 新数组 否
splice O(n) 被删除元素组成的数组 是
reverse O(n) 原数组 是
sort O(n log n) 原数组 是

这张表最有价值的其实是最后一列。原地修改的方法会在你不知不觉间改变原数组，而函数式方法不会。团队里绝大多数”数据莫名其妙变了”的 bug，源头都是有人在一个共享数组上调了 sort 或 reverse。

变换类方法：map、filter 与 reduce

map 和 filter 都是”返回新数组”的纯变换，语义清晰，是替代手写循环的首选。它们都能链式调用，读起来像一条流水线：

性能上，map 与 filter 各是一次完整遍历，链式调用就是两次。如果数据量很大，一次 forEach 或 for 同时完成过滤和转换会更快，代价是代码可读性下降。实践中我的判断线是：数据量超过五千条且这段代码在滚动或输入时反复执行，就合并成一次循环。

reduce 是这批方法里最被低估的一个。它能把”遍历加累计”的所有模式统一起来，包括求和、分组、展平、甚至实现自己的 map：

reduce 的坑在于不传初始值：此时第一个元素会被当作初始值，循环从第二个开始。空数组不传初始值会直接抛 TypeError。因此团队规范里要求 reduce 必须显式传第二个参数。

some 与 every 的价值在短路：some 找到第一个满足条件的元素就停，every 找到第一个不满足的就停。这在”只需要知道是否存在”的场景里比 filter 高效得多：

查询与拼接：indexOf、join、slice、concat

join 的性能常常被高估。很多人以为拼字符串一定要用数组加 join，实际上在现代浏览器里 += 字符串拼接已经被优化得很好，两者差距很小，只有在拼接上千段时 join 才稳定占优。更值得关注的是分隔符的默认值：join() 不传参数时用逗号，join("") 才是无缝拼接，漏掉参数的 bug 很常见。

小结

回到那次表格渲染优化，最终改动只有三处：把 filter 加 map 的链式调用合并成一次 for 循环，把排序前的 slice 拷贝补上并传入数值比较函数，把类数组转换从 slice.call 换成了带兜底的版本。首屏渲染时间从 900 毫秒降到 300 毫秒，代码反而更短了。方法本身没有优劣，只有匹配不匹配场景：for 争速度，forEach 争可读，map/filter/reduce 争表达力，some/every/indexOf 争短路，sort 永远记得传比较函数。真正拖慢项目的往往不是选错方法，而是对”原地修改””默认字符串排序””原型污染”这三件事缺乏警惕。
