微信 JS-SDK 接入实践

2013 年做微信里的网页，”分享到朋友圈”是躲不掉的需求。那时没有今天这套规范的 wx.config 加 wx.onMenuShareTimeline，大家操作的是 WeixinJSBridge 这个私有桥接对象。本文按 2013 年 9 月的真实情况，把一次微信网页接入的完整过程、签名流程和踩过的坑记录下来。

先认清环境：WeixinJSBridge 是什么

微信内置的 WebView 会往页面里注入一个名为 WeixinJSBridge 的全局对象，它是 JavaScript 与原生客户端之间的桥。页面通过它调用客户端能力，也通过它监听客户端事件。判断自己是否运行在微信环境里，最通用的办法是查 UA：

分享的实现与那个不可靠的回调

分享的核心是监听右上角菜单的点击事件，然后调用 invoke 把内容推给客户端：

注意事件名与 invoke 的方法名不是一一对应的：事件是 menu:share:timeline，动作是 shareTimeline；事件是 menu:share:appmessage，动作是 sendAppMessage。这种不对称在当年踩过不少人，写错一边的表现是”点击菜单没反应”而不是报错，很难排查。

最大的坑是分享成功回调不可靠。用户点了分享但最终取消，客户端也可能返回成功；有些版本的 invoke 回调压根不执行；还有些版本 res.err_msg 的取值五花八门（send_app_message:ok、share_timeline:ok、ok、cancel）。因此任何依赖”分享成功”的业务逻辑都不能建在这个回调上。要做分享激励，正确做法是后端统计：为每次分享生成带参数的链接，从落地页 URL 上识别来源，在页面加载时上报一次。这样即便回调丢了，也能统计到真实的分享打开次数。

还有一点：img_url 必须是公网可访问的绝对地址，且图片要先下载到本地。用相对路径、用 data:、或放在需要登录才能访问的域名下，都会出现”分享出去没有缩略图”。微信对图片尺寸也有要求，超过一定大小会被压缩或拒收。

签名流程：jsapi_ticket 与 SHA1

调用涉及用户信息与支付的能力前，必须先完成签名鉴权。2013 年的流程是这样的：前端把当前页面 URL 传给后端，后端用 jsapi_ticket、noncestr、timestamp、url 四个参数按字典序拼接后 SHA1 算出 signature，前端拿这个签名去初始化配置。

后端那侧的算法要严格按文档来，四个参数名固定，按字典序排序，拼接成 key=value&key=value 的形式，整体做 SHA1，然后转小写十六进制：

其中 jsapi_ticket 的获取又依赖 access_token，两者都要缓存：access_token 有效期 7200 秒，jsapi_ticket 同样 7200 秒。每次页面加载都去取新 ticket 会被接口频率限制打挂，所以必须加本地缓存并提前刷新。

签名失败时 config 的回调会返回 invalid signature 之类的错误。当年的排障经验是，失败原因九成出在 url 上：

具体来说：URL 必须与微信公众平台后台”JS 安全域名”下配置的域名一致；必须去掉 # 及其后的片段；http 与 https 要与后台配置匹配；不能带端口差异；安卓上 location.href 有时是 SPA 路由变化后的地址，而后端签名用的是后台登记的地址，二者不一致就必然失败。最稳的做法是后端只取 location.origin + location.pathname 做签名，并确保页面没有用会改变 URL 的路由方案。

网页授权与用户信息

分享之外的另一类需求是”我是谁”。2013 年的标准做法是 OAuth2 网页授权，流程分两步，全部由后端主导：

flowchart TD
    A[用户点击页面按钮] --> B[跳转授权页]
    B --> C[用户同意]
    C --> D[微信回调 redirect_uri]
    D --> E[后端用 code 换 access_token 与 openid]
    E --> F{scope 是 snsapi_userinfo?}
    F -->|是| G[再用 token 拉取用户资料]
    F -->|否| H[仅得到 openid]
    G --> I[建立登录态并跳回原页面]
    H --> I

snsapi_base 只拿 openid，静默授权不弹窗，适合”仅需识别用户”的场景；snsapi_userinfo 会弹出授权页，能拿到昵称、头像、性别、地区，但用户拒绝后就只能拿到 openid。redirect_uri 要 URL 编码，且域名需在后台配置为”网页授权域名”。

拿到 openid 只是身份标识，要落到自己的账号体系，还需要一次绑定。当时的通用设计是：后端维护 openid 到站内用户的映射表，首次授权时走”微信资料预填 + 手机号验证”的绑定流程，之后凭 openid 直接登录。不要试图把 openid 当密码用，它只是一个第三方发的稳定 ID。

那些跨平台不一致的坑

最后集中记录踩过的坑，按出现频率排序。

一是 iOS 与 Android 行为不一致。 同一段 WeixinJSBridge.invoke 代码，在 iOS 上参数名大小写不敏感，安卓上严格按文档传；iOS 的分享菜单图标出现时机与安卓不同，WeixinJSBridgeReady 触发时间也有早晚。处理办法只有一个：在两台真机上分别验证，不要只在模拟器或一台手机上测。

二是必须在 WeixinJSBridgeReady 之后调用。 在桥就绪前调用 invoke，部分版本静默失败，部分直接抛错。所有桥调用统一走 onBridgeReady 入口，这条纪律必须写进团队的代码规范。

三是 URL 与后台配置不一致。 JS 安全域名、网页授权域名、分享后的 link 三者是独立配置的，改任何一个都要去后台改并等待生效。开发时最容易漏的是本地调试：127.0.0.1 和公司测试域名都要单独加进白名单，否则永远签名失败。

四是缓存导致签名失败。 后端缓存了 jsapi_ticket 但缓存时间超过 7200 秒，或者缓存了整段签名结果；页面被 CDN 或浏览器缓存，导致前端拿到的是别人页面的签名。规避办法是签名接口加 Cache-Control: no-cache，ticket 缓存设置 7000 秒主动过期，且签名结果本身不缓存。

五是支付流程的时序。 2013 年微信支付刚上线，JS 侧的调用同样走 WeixinJSBridge.invoke("getBrandWXPayRequest", ...)，但必须由后端统一下单拿到 prepayid，前端拿到的参数中 timeStamp 是小写、nonceStr 大小写与签名阶段保持一致、package 值形如 prepay_id=*。任何一个字段写错，客户端只会提示”支付参数错误”，不给细节。

六是版本兼容要有退路。 灰度版本可能临时关闭某个接口。所有 invoke 外层包一层探测与 try-catch，失败时给出可读的提示，不要让页面白屏：

顺带说一句前瞻：官方正在把 WeixinJSBridge 这套私有接口整理成规范的 JS-SDK，用 wx.config 统一鉴权、wx.onMenuShareTimeline 之类的方法监听分享。2014 年底正式发布后，签名流程与能力调用都会标准化，本文里关于事件名不对称、invoke 参数拼装的细节会被封装掉。在新接口铺开前，私有桥接仍是唯一可用方案，做一层薄封装把差异隔离掉，是当时最务实的工程选择。

小结

2013 年 9 月的微信网页开发，本质是在与一个私有桥接对象打交道：用 WeixinJSBridgeReady 就绪信号保证调用时机，用 on 监听菜单事件、invoke 触发客户端动作，用 jsapi_ticket 加 SHA1 完成鉴权，用 OAuth2 拿到 openid 与用户资料。这四件事没有一件有友好的报错机制，所有问题都表现为”没反应”，只能靠 UA 判断、能力探测、真机双端验证和后台域名配置逐项排除。把桥调用收敛到统一入口、把签名与 ticket 收进后端缓存、把分享统计交给落地页参数，这三条纪律能让微信页面的可维护性提升一个量级。
