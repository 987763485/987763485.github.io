CDN 加速原理与接入实践

接手一个加载缓慢的站点时，第一反应往往是”图片太大了”。但真正压垮首屏的常常不是体积，而是距离：服务器在广州，用户在东北，一个 20 KB 的 CSS 也可能走上 200 毫秒。CDN 就是为了解决这个问题而存在的。本文从原理讲到接入实践，把一次完整的静态资源 CDN 改造复盘清楚。

CDN 到底做了什么

CDN（Content Delivery Network，内容分发网络）的核心思路只有一句话：把内容缓存到离用户最近的节点，让请求就近被响应，只有缓存未命中时才回到源站取。

它由三部分组成：负责调度的智能 DNS（也叫 GSLB，全局负载均衡）、分布各地的边缘节点、以及节点与源站之间的回源链路。用户的一次请求大致是这样流转的：

flowchart TD
    A[用户访问 static.example.com] --> B[智能 DNS 解析]
    B --> C{调度策略}
    C -->|就近/健康| D[北京边缘节点]
    C -->|就近/健康| E[上海边缘节点]
    D --> F{节点是否有缓存?}
    E --> F
    F -->|命中| G[直接返回缓存内容]
    F -->|未命中| H[回源站取内容]
    H --> I[源站响应并回填节点]
    I --> G

调度的依据通常包括用户本地 DNS 的出口位置、节点的负载与健康状态、以及各线路的连通质量。2013 年的国内环境还有个特殊因素：运营商之间的互联质量参差不齐，能不能让联通用户落到联通线路的节点，往往比单纯的地理距离更影响体验。

对静态资源来说，加速收益来自三处：物理距离缩短带来的延迟下降、节点带宽替代源站带宽带来的并发能力提升、以及 TCP 连接可以复用更近的对端。第三点常被忽略，但它对 HTTPS 站点尤其关键——握手次数的减少能直接改善首屏。

接入方式：一条 CNAME 的事

接入 CDN 的标准动作是域名拆分加 CNAME。源站域名不动，给静态资源单独配一个域名，再把这个域名委托给 CDN 厂商：

这条 CNAME 就是”委托”的凭证。解析请求到达 CDN 的智能 DNS 后，由它返回边缘节点 IP，之后的请求都不再经过源站的 DNS。所以接入 CDN 后，源站对外的可见性下降，排障时需要额外关注 CDN 侧的解析链路。

域名拆分还有一层历史原因：浏览器对同一域名的并发连接数有限制（当年主流浏览器是 6 个），把静态资源放到独立域名，可以与主站并行下载，等于绕开了这个上限。不过也有代价：多一个域名就多一轮 DNS 查询，还要多一次 TCP 连接。所以域名不是拆得越多越好，2013 年的常见实践是拆 2 到 3 个静态域名，其余资源通过合并与精灵图来控制请求数。

配套一定要做的是 Cookie 隔离。如果静态域名和主站同域，浏览器会把主站的 Cookie 一并带给静态请求，白白增加每个请求的头部体积；更糟的是 CDN 节点如果按 URL 加 Cookie 维度做缓存，命中率会被打穿。做法很简单：静态域名完全不写 Cookie，页面里的静态引用全部走独立域名，主站域名另设一个只用于接口与页面的地址。

缓存头：命中的前提

CDN 不是”接上就自动加速”，它只会缓存你允许它缓存的响应。控制权在源站的响应头里。

Cache-Control 的取值决定了节点与浏览器的行为，需要分清两层：节点缓存由 max-age、s-maxage、must-revalidate 等控制，浏览器缓存由 max-age、no-cache、no-store 控制。只给浏览器加缓存头而不让 CDN 缓存，或者反过来，都是常见误配。

与缓存头配套的是”内容寻址”。文件名不带版本号时，更新文件后节点不会主动重新拉取，用户可能长时间拿到旧文件。2013 年的标准做法是在文件名上打指纹：

发布新版本后如果必须让旧 URL 立即失效，就要用 CDN 的刷新接口（不同厂商叫 purge 或 refresh）：

刷新通常有数量限制和生效延迟，分钟级算正常。所以”发布顺序”很重要：先刷新 CDN，再切流量；或者先上线新文件名，再改页面引用。反过来操作就会出现一部分用户拿到新旧混合的资源。

防盗链与鉴权

静态域名暴露在外，很容易被别的站点直接引用，把带宽算在你头上。CDN 一般提供两种防护。

它的弱点也明显：Referer 可以伪造，且部分浏览器与安全软件会剥离 Referer，误伤真实用户。因此”none”要放行，否则直接输入图片地址访问会被拒绝。

Token 鉴权更可靠，适合下载类与计费内容。原理是服务端按约定规则把 URL、过期时间与密钥算出签名，拼在 URL 后面；CDN 节点校验签名合法且未过期才放行：

签名在服务端生成，前端只负责拼接。要注意过期时间不能太短，否则用户下载大文件到一半链接就失效；也不能太长，否则链接外泄后长期有效。

常见坑与实践清单

第一个坑是动态内容上了 CDN。带用户信息的接口、个性化页面一律不能缓存，否则会出现”用户 A 看到用户 B 的数据”这种严重事故。判断标准很简单：响应是否因人而异、是否依赖 Cookie 或请求参数。命中任何一条，就该走动态加速或者干脆回源。

第二个坑是缓存策略一刀切。整站给 30 天，结果后台改个文案三天不生效，运维只能全站刷新。合理做法是按文件类型分层：HTML 与接口短缓存或不缓存，CSS/JS 长缓存加文件名指纹，图片超长缓存。

第三个坑是HTTPS。2013 年 HTTPS 的 CDN 支持还不普及，部分厂商需要额外开通，且 SNI（服务器名称指示）刚刚兴起，老旧客户端与部分移动设备会握手失败。如果站点要上 HTTPS，务必提前确认 CDN 侧的证书部署方式与客户端兼容性，并做好回退到源站的方案。

第四个坑是SEO 顾虑。早期有说法认为静态资源换域名会影响收录，实际上搜索引擎关心的是页面 HTML 的地址与内容，静态资源域名不参与收录判断。真正要保证的是：HTML 始终由源站或可控链路返回，状态码正确，不要在 CDN 侧对 HTML 做强缓存。

第五个坑是日志断层。接入 CDN 后，源站日志里看到的请求量会大幅下降，因为大部分流量在节点就被消化了。做访问分析时，要么用 CDN 提供的日志下载与统计，要么在页面里保留统计打点，不能只看源站日志得出”流量下滑”的错误结论。

一份可以直接照着做的接入清单：

flowchart TD
    A[准备接入 CDN] --> B[拆分静态域名]
    B --> C[配置 CNAME 与回源]
    C --> D[源站设置缓存头]
    D --> E[文件名加版本指纹]
    E --> F[配置防盗链]
    F --> G[验证命中率]
    G --> H{命中率是否达标?}
    H -->|否| I[检查缓存头与 Cookie]
    I --> D
    H -->|是| J[监控与日志归档]

小结

CDN 的本质是”用空间换时间”，靠智能 DNS 把用户调度到最近的边缘节点，靠缓存头决定哪些内容可以被共享，靠回源链路保证内容的一致性。接入动作本身只是一条 CNAME，但真正决定效果的是后续的缓存策略、域名拆分、Cookie 隔离、防盗链与发布顺序。对静态资源而言，这套组合是当年性价比最高的一项优化：改动集中在运维与构建层，不动业务代码，却能同时改善首屏时间、源站负载和跨运营商访问质量。如果只做一项性能优化，我会选它。
