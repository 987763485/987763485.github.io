表单元素操作与表单验证实战

表单是前端里最”重”的一块：既要操作大量控件，又要在提交前把数据拦住。HTML5 给表单加了一大批新类型和验证属性，本意是让浏览器接管校验，但 2013 年的现实是各浏览器支持程度参差不齐，IE 10 之前几乎什么都不认。本文把当时项目里能落地的一套做法写下来：用 form.elements 统一操作控件，用 Constraint Validation API 做原生校验，再用一层传统 JS 校验兜住老浏览器。

HTML5 带来的新类型与新属性

HTML5 给 input 增加了十几个 type 值，并引入了一批与验证相关的属性。先看类型这一侧：

type 值 用途 2013 年 5 月支持情况
email 邮箱地址，提交时校验格式 Chrome 20+、Firefox 部分支持，IE 10 起支持
tel 电话号码，只做键盘优化 Chrome 20+、Firefox 部分支持，IE 10 起支持
url 网址，提交时校验格式 Chrome 20+、Firefox 部分支持，IE 10 起支持
number 数字，带上下箭头与范围限制 Chrome 20+、Firefox 部分支持，IE 10 起支持
date 日期选择器 仅 Chrome 20+ 有初步实现，其余基本没有
color 取色器 仅 Chrome 20+ 有初步实现
search 搜索框，样式与清除行为不同 Chrome 20+、Firefox 部分支持
range 滑块 Chrome 20+、Firefox 部分支持

再看属性这一侧，它们大多与验证直接相关：

属性 作用 备注
required 必填，空值时阻止提交 支持度最好，但仍不完整
pattern 用正则校验输入内容 Chrome 20+ 支持，写法锚定整段
placeholder 输入框内的提示文字 支持度较好，IE 9 起支持
autofocus 页面加载后自动获得焦点 部分浏览器支持，一页只宜用一个
multiple 允许输入多个值（逗号分隔） 支持有限
min / max number 与 date 的取值范围 依赖类型本身被支持
step 数值递增步长 依赖类型本身被支持

把这些一次性堆到代码里是不现实的。当时的务实做法是：能用原生的地方用原生，但绝不让校验逻辑只依赖原生。原因很简单，IE 9 及以下的用户量在 2013 年仍然可观，而它们的表现是所有新类型都退化成 text，所有新属性被静默忽略——不报错，但也不校验。

form.elements：操作控件的统一入口

form.elements 是 HTML4 时代就有的集合，但在 HTML5 语境下它的价值更高，因为它把 input、select、textarea、button 放在同一个容器里，且支持用控件 name 直接索引。这是批量操作表单时最省事的入口。

有三个细节值得留意。第一，form.elements 不含 type 为 image 之外被排除的控件，实际上 input[type=image] 在 HTML5 里是被排除的，历史上有过争议，用的时候最好实测。第二，同名控件（例如一组单选或多个同名 checkbox）用 namedItem 取到的是 RadioNodeList 或集合，需要遍历。第三，form.elements 是动态集合，页面运行期往表单里插控件，它会跟着变，不像 querySelectorAll 返回静态快照。

两种校验如何共存

这是整篇文章最实际的部分。原生校验的优点是提示文案与交互由浏览器提供，本地化、无障碍支持都好；缺点是 2013 年支持残缺，且样式难以定制。传统 JS 校验的优点是行为完全可控、跨浏览器一致；缺点是要自己写提示、自己处理焦点。当时的策略是分层：

flowchart TD
    A[用户点击提交] --> B[拦截 submit 默认行为]
    B --> C{浏览器支持
checkValidity?}
    C -- 是 --> D[调用 form.checkValidity 走原生校验]
    C -- 否 --> E[执行自定义 JS 校验函数]
    D --> F{结果合法?}
    E --> F
    F -- 是 --> G[序列化并提交]
    F -- 否 --> H[聚焦第一个非法控件并提示]

坑在哪

第一，pattern 的正则是整段锚定的。写 pattern="\d+" 匹配的是整个值必须是数字，等价于 ^\d+$。很多人按 search 的语义写，结果发现 "12a" 也能通过，那是因为它确实匹配到了数字子串——实际上规范要求锚定整段，不同浏览器在早期的实现并不统一，Chrome 20 与 Firefox 的表现就有差异。稳妥做法是在 pattern 之外再用 required，并靠 JS 校验兜底。

第二，type="number" 在部分浏览器里允许输入字母，只在提交时校验。用户输入 e（科学计数法前缀）在很多实现里是合法的，直接 parseFloat 可能得到 NaN。取值时先判 el.validity.badInput 或 isNaN(+el.value)。

第三，type="date" 这类控件在 Chrome 里返回的值格式是 yyyy-mm-dd，在不支持的浏览器里退化成 text 后，用户可能输入 2013/05/23 或 05/23/2013。不要假设格式，提交前统一格式化一次。

第四，required 对 type="number" 的空值处理不一致。有些浏览器空字符串算值缺失，有些算合法。用 required 时最好同时校验一次空值。

第五，form.elements 的 name 与控件 id 是两套东西。form.elements['x'] 按 name 找，document.getElementById('x') 按 id 找，两者恰好同名时行为相同，但只要有一处不一致就会踩空。团队约定”name 与 id 同名”能省掉这类问题。

第六，序列化时要跳过 disabled 与无 name 的控件。另外 type="submit"、type="button"、type="reset"、type="image" 没有值，遍历时要排除，否则会得到一堆 undefined。

小结

HTML5 的表单新类型与验证属性方向是对的，但 2013 年的支持度决定了它只能作为增强层：Chrome 20+ 与 Firefox 有部分支持，IE 10 之前完全不支持，所有新属性在老浏览器里都是静默失效。落地时要抓住三个抓手——form.elements 作为操作控件的统一入口，Constraint Validation API 的 checkValidity 与 setCustomValidity 作为原生校验的开关，以及一层规则集中的传统 JS 校验兜住老浏览器。提交逻辑统一走”拦截默认提交、校验、序列化、再提交”这条路径，preventDefault 与 returnValue 都要写。最后记住 setCustomValidity 设置的错误不会自动消失，输入变化时必须显式清空。
