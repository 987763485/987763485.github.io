AJAX 与跨域请求实践

同一个页面要从三个不同域取数据：自己域下的接口、合作伙伴提供的数据服务、还有一个第三方的统计脚本。浏览器同源策略把这三件事分成了三六九等，第一件理所当然，后两件都要想办法绕。本文把当时项目里实际用到的几种方案梳理一遍，包括原生 XMLHttpRequest、jQuery 的 $.ajax、JSONP、XDomainRequest、iframe 加 document.domain 等，说清楚各自适合什么场景、坑在哪里。文中的代码都可以直接跑，接口地址请按自己的实际情况替换。

同源策略与跨域的本质

同源策略规定，协议、域名、端口三者全部相同才算同源。http://a.com 与 https://a.com 协议不同，a.com 与 www.a.com 域名不同，a.com:80 与 a.com:8080 端口不同，都会被视为跨域。浏览器出于安全考虑禁止跨域的 XHR 读取响应内容，这是所有跨域方案的起点。

要注意的是，请求其实是发出去了，服务端也返回了，只是浏览器在拿到响应后把它拦住了。这一点在调试时很关键：你看到的”请求失败”，网络面板里往往有完整的响应体。

2013 年这个时间点上，方案选择有一个基本判断顺序：能不能推动服务端配合？能，就优先走 CORS；不能，就走 JSONP；完全无法通信的场景，才考虑 iframe、window.name 这类折中手段。

JSONP：当时的主流方案

JSONP 的原理是利用 <script> 标签不受同源策略限制的特性。页面动态创建一个 script，src 指向目标地址并带上一个回调函数名，服务端返回一段 JavaScript 代码，内容是”调用你指定的那个函数，并把数据作为参数传进去”。

它的优点很突出：兼容性好，从老 IE 到各种移动浏览器都能用，实现也就十几行。缺点同样明显：只能发 GET 请求；服务端必须改造以支持回调；回调是全局函数，有全局污染风险；错误处理弱，超时只能靠自己兜；还有被注入脚本的安全隐患，服务端返回的内容是直接当代码执行的。用 JSONP 时务必只对可信的域使用。

CORS：跨域资源共享

CORS 是 W3C 的标准方案，2006 年前后开始推进，到 2010 年前后主流浏览器已陆续落地。它的思路是让服务端通过响应头声明”允许哪些域来访问我”，浏览器校验通过后放行。

浏览器会把请求分成两类。简单请求是 GET、HEAD 或 POST，且只使用有限的几个头，Content-Type 限于 application/x-www-form-urlencoded、multipart/form-data、text/plain。简单请求直接发出，浏览器检查响应头里的 Access-Control-Allow-Origin，如果包含当前页面域就放行。

带自定义头、Content-Type 为 application/json，或者用了 PUT、DELETE 方法，浏览器会先发一个 OPTIONS 预检请求，服务端返回允许的方法和头之后才发真正的请求。这意味着每次非简单请求都有两次往返，移动端弱网下延迟感知明显。

IE 8 和 IE 9 有自己的一套实现，叫 XDomainRequest。它的接口和标准 XHR 不一样，只能发 GET 和 POST，不支持自定义头，不能带 Cookie，响应只能是 text/plain，而且 onprogress 等事件名也有差别。jQuery 1.9 内部对 IE 的 CORS 做了封装，但 withCredentials 在 XDomainRequest 下是不支持的。

反向代理：最省事的办法

如果跨域的目标接口是你自己控制的服务，最优解往往不是前端技巧，而是在自己域下加一层代理。Nginx 上几行配置就能做到，前端完全按同源接口访问，不用关心任何跨域细节。

这样做的好处是彻底消灭跨域问题，同时可以在代理层做缓存、合并请求、鉴权。代价是增加一跳网络，以及要维护代理配置。我们的实践中，凡是能谈下来的服务都走了这条路，剩下的才用 JSONP。

其他历史方案

在 CORS 普及之前，开发者们还想出了不少办法，了解它们有助于理解跨域的本质。

document.domain 适合主域相同、子域不同的场景。两个页面都把 document.domain 设成共同的主域，就能互相访问对方的 DOM。

它的限制很死：只能用于 iframe 之间，端口必须一致，改完之后就不能再改回去。

window.name 是另一个技巧。window.name 在页面跳转后依然保留，且容量很大（几 MB 级别），可以先把 iframe 指向跨域页面，让目标页面把数据写进 window.name，再把 iframe 切回同域页面读取。缺点是流程绕、要多次跳转，还得处理加载时序。

location.hash 传递数据则是利用 URL 片段不参与请求的特性，跨域页面通过修改 hash 把数据传给父页面，父页面轮询或监听 hashchange 来读取。数据量受 URL 长度限制，而且不同浏览器对 hash 变更的事件支持在 2013 年还不统一。

  A[需要跨域取数据] --> B{能否让服务端配合?}
  B -- 是, 可控服务 --> C[反向代理到本域]
  B -- 是, 第三方服务 --> D[CORS / XDomainRequest]

方案对比与选型

把几种方案放在一起看，选型就不难了：

方案 支持方法 兼容性 服务端改造 错误处理 适用场景
反向代理 全部 最好 不需要 完整 自有服务
CORS 全部 IE10+，Chrome/Firefox 好 需要加响应头 完整 可配合的第三方
XDomainRequest GET/POST 仅 IE8/9 需要 较弱 IE 老版本兜底
JSONP 仅 GET 最好 需要支持回调 弱，靠超时 不可改造的第三方
document.domain 不涉及请求 好 不需要 完整 同主域 iframe
window.name GET 好 需要 弱 极端场景

实践中我们的顺序是：能加代理就加代理；必须直连第三方时先问对方支不支持 CORS；只支持 GET 且不能改造的才上 JSONP；IE8/9 用 XDomainRequest 兜底 CORS。document.domain 只在老系统的 iframe 通信里用过一次，window.name 和 location.hash 基本没有进过生产代码，它们更像是特定历史条件下的技巧，理解即可。

小结

跨域不是前端单方面能解决的问题，它涉及浏览器策略和服务端配合，选型时先判断能不能推动服务端改造，再决定技术路线。JSONP 胜在兼容和简单，但只能 GET、错误处理弱、有安全风险；CORS 是标准方向，能力完整但老 IE 要单独处理，且预检请求会增加延迟；反向代理最省心，也是自有服务下的首选。用 jQuery 的 $.ajax 可以屏蔽大部分差异，但理解底层依然是必要的，否则遇到预检失败、Allow-Origin 与 Allow-Credentials 冲突这类问题时无从下手。无论哪种方案，超时兜底和错误提示都要自己做，跨域请求失败时的用户体验最容易被忽略。
