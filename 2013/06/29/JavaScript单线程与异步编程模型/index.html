JavaScript 单线程与异步编程模型

很多人第一次被 JavaScript 问到哑口无言，都是被同一个问题：「既然是单线程，为什么 setTimeout 里的回调不会阻塞后面的代码？」要回答这个问题，只背一句「事件循环」是不够的，必须把线程模型、调用栈、任务队列这三者的关系真正连起来。本文从浏览器的 UI 线程模型讲起，一路推到 Node 的事件循环，最后讨论这个模型带来的错误处理困境。需要说明的是，本文写于 2013 年，Promise 还只是 ES6 草案里的提案，文中提到的内容全部基于当时已发布的环境（ES5、Node 0.10）。

为什么 JavaScript 是单线程

这个决定是 1995 年 Brendan Eich 用十天创造这门语言时定下的，后来没有改。原因说起来很朴素：JavaScript 从诞生起就是浏览器的脚本语言，而它最主要的操作对象是 DOM。

假设 JavaScript 是多线程的，一个线程在修改某个 DOM 节点的文本，另一个线程同时删除这个节点，浏览器该听谁的？这类「DOM 竞争」问题在多线程环境下极其普遍，而浏览器没有一套细粒度的 DOM 锁机制。更麻烦的是，浏览器还要处理用户的输入、渲染、布局，如果脚本线程和渲染线程同时操作同一棵文档树，结果将完全不可预测。

所以设计者做了一个极其务实的选择：让 JavaScript 运行在一个线程里，把「并发」这个烫手山芋推给宿主环境（浏览器或 Node）去调度。脚本一次只做一件事，做完一件取下一件，DOM 的读写天然串行，竞争问题从根源上消失。

这个代价是：任何耗时的同步操作都会阻塞整个线程，页面表现为「卡死」。 setTimeout、AJAX 回调这些机制的存在，本质上就是为了把「等待」这件事从脚本线程里摘出去。

用一个类比：浏览器就像一个只有一名员工的柜台，客户（任务）排成一队，员工一次只服务一个人。异步 API 相当于告诉客户「你的事情要去后台办，办好了回来重新排队」。这名员工从不分身，但队伍不会因为有人去后台办事而停摆。

浏览器 UI 线程模型

浏览器里与 JavaScript 直接相关的线程不止一个，但 JavaScript 只跑在其中一个上面，通常被称为 UI 线程或主线程。其他线程包括渲染线程、定时器触发线程、事件触发线程等，它们之间通过消息机制协作。

关键点在于：JavaScript 线程与渲染线程是互斥的。脚本执行期间浏览器不会重绘，这是为什么一个长时间运行的同步循环会让页面「冻结」——不是渲染线程忙，而是它拿不到执行机会。反过来，一旦脚本执行完毕，浏览器会在合适的时机（通常是一个任务结束）触发布局与绘制。

这个互斥关系解释了很多现象。比如在一个大循环里连续修改元素的样式，用户看不到中间过程，只看到最终结果；又比如 alert 会阻塞整个线程，因为它是一个同步的系统调用，在用户点掉之前，渲染线程和后续脚本全部停摆。

浏览器的这一设计还带来一个常被忽视的工程约束：不要把耗时逻辑直接写在事件处理函数里。一次 click 回调如果跑了 500 毫秒，这期间用户的第二次点击不会被响应，看起来就像页面卡了一下。惯例做法是能交给 CSS transition 的效果不要用 JS 逐帧计算，能延后的统计上报放到空闲时再做，实在躲不掉的纯计算扔进 Web Worker。

顺带解释一个相关问题：为什么「先改 DOM 再读尺寸」会比反过来慢。读 offsetWidth、getComputedStyle 这类属性会强制浏览器执行同步布局（layout flushing），因为它必须给出当前最新的几何信息。在一段代码里反复交替写样式和读尺寸，每次读都会触发一次重排，性能急剧下降。这不是事件循环的问题，但同样源于「脚本执行期间渲染线程被阻塞」这个前提。

任务队列与事件循环

现在回答开头的问题。浏览器为 JavaScript 准备了两样东西：一个调用栈，一个任务队列（task queue）。

调用栈就是函数调用的栈，后进先出。每当一个函数被调用就入栈，执行完就出栈。这是同步代码的执行场所。

任务队列是一条先进先出的消息队列，存放的是「待执行的任务」，每个任务在浏览器里通常对应一个事件对象（点击、定时器到期、AJAX 响应等）。当调用栈清空时，事件循环（event loop）会从任务队列里取出第一个任务，压入调用栈执行，执行期间新产生的同步调用继续入栈，直到栈再次清空，再取下一个任务。

    D -->|栈为空时取出一个任务| A
    E[定时器线程] --> C
    F[事件触发线程] --> C
    G[IO 线程] --> C

执行顺序可以这样理解：同步代码在栈里跑，遇到异步 API 时注册一个回调并把「等待」交给宿主，宿主在条件满足时把回调包装成任务放进队列。栈空了，循环就把队列头的任务拿来跑。整个过程反复进行，直到队列耗尽。

三者的分工需要说清楚，因为这是后续所有推理的基础。堆（heap）是对象的内存区域，函数执行时创建的对象都在这里分配，由垃圾回收器管理，它不参与执行顺序。调用栈（stack）保存函数调用的上下文——局部变量、返回地址、作用域链，函数返回时栈帧弹出。任务队列（queue）保存的是待执行的回调任务，与栈的区别是顺序：栈是后进先出，队列是先进先出。

一个关键推论是：异步回调永远不可能在当前同步任务执行期间运行，即使它等待的条件已经满足。原因是事件循环只在「调用栈为空」这个条件下才会去取任务。用序列图表示一次点击事件的投递过程：

为什么定时器回调在最后？因为 setTimeout 只是向定时器线程登记了一个「0 毫秒后触发」的请求，脚本线程并不会停下等待。它继续执行后面的 console.log('2') 和 console.log('3')，等整个脚本的任务执行完、栈空了，事件循环才从队列里取出定时器回调。即使延迟是 0，也不可能插队到同步代码之前。

这里还有一个容易混淆的细节：setTimeout 注册的回调一定会在同一轮脚本之后执行，但两个 setTimeout 之间的顺序只保证「先到期先入队」，不保证执行时长精确。若第一个回调执行了 100 毫秒，第二个到期时间早已过去的回调会被排在它后面。也就是说，定时器队列本身也是先进先出的，不会因为到期时间早就抢跑。

任务、宏任务与微任务的边界

2013 年讨论「任务」时，主流语境里只有 task queue 这一个概念，对应后来规范里的 macrotask（宏任务）。宏任务包括定时器回调、DOM 事件回调、AJAX 回调、MessageChannel 消息等，每个宏任务执行完后，事件循环才有机会去队列里取下一个。

微任务（microtask）的概念在当时尚未成型，Promise 草案里虽然有 thenable 的调度讨论，但浏览器实现的规范程度不一，实际项目里不能依赖。所以本文不展开微任务，读者在 2013 年的代码里也不需要关心它。这里特意说明一句，是因为后来的文章讲事件循环时会把两者混在一起，容易让回看这段历史的人产生时间线上的错乱。

回调函数的本质

把上面所有机制抽象一层，回调函数只是一个「被当作参数传递、在特定时机由别人调用的函数」。它的本质不是异步，异步只是它最常见的舞台。

Node 约定俗成的「错误优先」回调签名 callback(err, result) 在这个例子里已经体现出来：第一个参数保留给错误，后续参数承载数据。这个约定在 2013 年的 Node 生态里已经非常普及，它解决的问题是「如何在不支持异常跨越异步边界的情况下传递错误」——同步代码可以用 try/catch，异步回调抛出的异常没有任何上层能捕获，只能通过参数传递。

错误优先签名有一个细节值得单独说明：err 为真时必须立即返回，不能再继续执行后续逻辑，否则会在错误状态下访问未定义的数据。Node 的风格检查工具（如早期的 JSHint 配置）甚至会把「回调第一个参数未检查」列为警告。实践中衍生出一个小技巧：在开发阶段给每个未处理的 err 加一句 throw err，强制自己看见它，上线前再换成日志上报。

回调真正的价值在于控制反转（inversion of control）：你把「拿到数据之后要做什么」交给别人，别人在合适的时机调用它。这带来了灵活性，也埋下了后面要讲的地狱。

还有一个概念与回调常被一起提到，容易混淆：事件监听。addEventListener 注册的回调同样是控制反转，但它是一对多的——同一个事件可以触发多个监听器，而普通回调通常是「一次任务一次调用」。区别的意义在于：用回调表达「接下来做什么」，用事件表达「发生了某事时通知所有关心的人」。jQuery 的 .on()、.trigger() 正是在这两个语义之间提供了统一接口。

定时器的准确性与细节

setTimeout 和 setInterval 是早期最重要的两个异步原语，但它们的语义远比表面复杂。

第一，延迟参数不是精确的。HTML5 规范明确说明，setTimeout 的第二个参数是最小延迟，不是保证延迟。浏览器会在「至少等待这么久之后，且调用栈为空时」才执行回调。所以一个 setTimeout(fn, 100) 在页面繁忙时可能 300 毫秒后才跑。

第二，嵌套层级会受惩罚。HTML5 规定：当 setTimeout 的嵌套调用超过 5 层，最小延迟会被强制提升到 4 毫秒。这是为了防止递归调用 setTimeout 造成空转消耗 CPU。

第五，setTimeout(fn, 0) 的真实含义。它不等于「立即执行」，而是「尽快执行，但要排到当前任务队列的末尾」。它的两个常见用途：一是把耗时操作从当前执行流里让出去，让浏览器有机会先渲染一帧；二是改变代码的执行顺序，让某些依赖初始化的逻辑延后。把它当成同步代码来推理，是新手最常见的错误。

第六，定时器标识与取消。setTimeout 与 setInterval 都返回一个数值标识（在浏览器里是整数，在 Node 里是一个对象），clearTimeout 与 clearInterval 需要传入对应的标识才能取消。常见错误是把两个调用的返回值搞混，导致定时器取消不掉。另外，页面卸载时如果有未取消的定时器，回调可能在不完整的上下文里执行，单页应用里这是内存泄漏的常见来源之一。

还有一类阻塞来自网络请求本身。如果用了同步的 XMLHttpRequest（open 的第三个参数传 false），在响应返回之前整个页面完全停摆，用户既不能滚动也不能点击，这是浏览器规范允许但强烈不建议的用法。2013 年仍有不少老旧代码这么写，迁移时的第一步就是把第三个参数改成 true 并补上回调。同样的逻辑适用于所有「看起来是同步」的浏览器 API：showModalDialog、早期的 localStorage 在某些浏览器上的实现也可能有同步开销，使用前要评估量级。

一个常被问到的问题是：既然单线程，动画怎么做？答案是动画不需要 JS 参与也能跑，因为 CSS transition 与 animation 由浏览器的合成线程驱动，不完全依赖主线程。只有用 setInterval 逐帧改样式的 JS 动画才会被主线程阻塞拖累。这也是 2013 年移动端优化反复强调「能用 CSS 动画就不要用 JS 动画」的原因。

Node.js 的单线程事件循环

Node 在 2009 年出现时把同一套模型搬到了服务端，但场景不同：浏览器等的是用户事件，Node 等的是 IO。2013 年 Node 0.10 的事件循环大致分为几个阶段：timers（定时器回调）、pending callbacks、idle/prepare、poll（IO 事件）、check（setImmediate）、close。

核心差异在于 IO 模型。Node 通过 libuv 把文件系统、网络这些阻塞式操作委托给线程池或操作系统的异步接口，主线程只负责在回调里处理结果。所以 Node 也是单线程执行 JavaScript，但 IO 是异步的，这是它能用少量进程承载高并发连接的原因。

Node 的单线程有一个必须说清的边界：它只保证 JavaScript 代码在同一个线程执行，CPU 密集型的计算依然会阻塞整个进程，一个慢的正则就能拖垮所有请求。这也是当时 Node 不适合做计算密集型服务的原因，集群（cluster）模块可以开多进程，但共享状态要用消息传递。

Node 与浏览器在异步来源上还有一个差异：浏览器的 IO 主要来自用户交互与网络请求，Node 的 IO 主要来自文件系统与网络套接字。同样是事件循环，两者的「任务生产者」不同，这也导致 Node 更强调吞吐量而非响应延迟——一个 Express 应用里，一次慢查询影响的是排在它后面的所有请求，而浏览器里一次慢计算影响的是当前页面的交互。

错误处理与回调地狱的雏形

与后续规范的关系

写到这里必须回到时间线。2013 年年中，ECMAScript 第 6 版（ES6）还处在草案阶段，其中包含了 Promise。当时的现实是：V8 与部分浏览器开始提供 Promise 的实验性实现，Firefox 的 Promise 实现也已出现，但它带 moz 前缀、语义与后来的标准有差异，跨浏览器完全不可用。

因此，2013 年的生产代码不能使用 Promise，也不能使用它的链式写法。本文介绍的异步手段——回调、错误优先约定、定时器、命名函数、async.js——就是这个时期的正确答案。Promise 以及后来的 async/await 解决的问题，正是上面讲的控制反转与错误传播，但它们是下一代工具，属于另一篇文章的主题。

同样值得说明的是，window.onerror、unhandledrejection 这类全局兜底在 2013 年只有前者可用；Node 的 uncaughtException 事件可以捕获未处理异常，但官方文档明确警告它只是兜底、不是流程控制手段，捕获后进程状态已不可信。

小结

JavaScript 的单线程不是历史包袱，而是为避免 DOM 竞争做出的务实选择，浏览器 UI 线程与渲染线程互斥进一步放大了同步阻塞的代价。异步的实现依赖三层结构：调用栈执行同步代码，宿主环境（定时器线程、事件线程、IO 线程）负责等待，任务队列与事件循环负责在栈空时按序投递回调。回调的本质是控制反转，错误优先签名是异步世界里的错误传递方案，而层层嵌套的编排困难就是回调地狱的根源。2013 年的工程答案是命名函数、并行控制与 async.js，Promise 仍是草案中的提案，不能用于生产。理解这个模型的价值在于：所有「为什么这里不执行」「为什么顺序反了」的疑问，最终都能追溯到「栈空了吗」这一个问题上。
