YSlow 与 PageSpeed 评分优化

接手一个上线半年多的老站点，老板只给了一句需求：「把首页加载再快一点」。听起来很虚，但如果不能量化，这句话就没法验收。本文记录当时怎么用 YSlow 和 PageSpeed 这两个工具把「快一点」拆成可执行的清单，以及两个工具规则打架时怎么取舍。结论先说：两者都是优秀的诊断工具，但定位不同，YSlow 偏规则清单与权重评分，PageSpeed 偏具体资源与可立即套用的优化项，实践中最稳的做法是「YSlow 定方向、PageSpeed 找细节、Network 面板做验证」。

两个工具的出身与形态

YSlow 是 Yahoo 2007 年开源的一个浏览器插件，最早跑在 Firefox 的 Firebug 上，后来也有 Chrome 版本。它背后是 Yahoo 前端团队总结的 23 条性能优化规则（The Yahoo Performance Rules），从减少 HTTP 请求、使用 CDN、把脚本放页面底部，一直到避免 CSS 表达式、减少 DNS 查询。YSlow 把这些规则做成一张清单，逐项打勾或打叉，最后按权重算出一个总分。

PageSpeed 是 Google 的产品，2009 年以插件形态出现，2011 年开源。它的形态演进比较快，一开始同样是浏览器插件，后来有了在线版，2013 年这个时间点还有独立的 PageSpeed Insights 页面，Chrome 的 DevTools 里也开始能看到一些网络与性能面板的数据。PageSpeed 给的诊断同样是一组规则，但它更愿意直接告诉你「这个文件可以再小多少 KB」「这个图片可以换成 JPEG 格式节省百分之多少」。

两者都是「规则 + 权重 = 分数」的思路，且都提供浏览器插件形式，覆盖 Firefox 的 Firebug 与 Chrome 的 DevTools 生态。差别在规则的选取与权重分配上。

规则重合度：哪些是两个工具都在喊的

把两份规则清单并排放，重合的部分相当高，这恰恰说明它们是真正的性能瓶颈。按当时实践的收益排序，重合度最高的有这么几类。

第一类是 HTTP 请求数量。YSlow 的规则 1 是「减少 HTTP 请求」，PageSpeed 里也有对应的「Minimize request size」与合并建议。背景是 2009 年到 2012 年 HTTP/1.1 时代浏览器对同一域名的并发连接数有限制，每个请求都有建连、等待、下载的固定开销。合并脚本与样式表、使用 CSS Sprite 把小图标拼成一张图，收益立竿见影。

第二类是压缩与缓存。两者都强调开启 gzip、配置 Expires 或 Cache-Control、使用 ETag。YSlow 有一条专门讲「配置 ETag」甚至建议在分布式部署下去掉 ETag，因为不同服务器的 ETag 格式不一致会让缓存判断失效；PageSpeed 则直接把「Enable gzip compression」「Leverage browser caching」列为核心规则。

第三类是资源体积。YSlow 讲「Minimize JS and CSS」「Avoid empty src or href」，PageSpeed 讲「Minify JavaScript」「Minify CSS」「Optimize images」。YSlow 的「Optimize images」讲得比较概括，PageSpeed 在这一条上做得更细，会针对单张图片给出格式建议和预估收益。

第四类是渲染阻塞。两者都指出 CSS 放头部、JS 放底部，避免阻塞首屏渲染。PageSpeed 有一条「Put CSS in the document head」，YSlow 的对应规则是「Put Stylesheets at the Top」和「Put Scripts at the Bottom」。

下面的表格概括了两者的规则侧重。

权重与评分的差异，以及怎么用

YSlow 的默认权重把「减少 HTTP 请求」和「使用 CDN」看得比较重，权重一改，同一页面的分数能差出十几分。PageSpeed 的评分更偏向「按当前页面实际数据算出的可优化空间」，同样的代码，如果图片特别大，PageSpeed 分数会被图片拖得很惨；如果请求数多但每个都小，YSlow 可能扣得更多。

这个差异直接影响了使用方式。笔者认为正确的工作流是这样的：先用 YSlow 跑一遍，看哪几条规则被标红，把清单里能立刻改的先改掉，这决定的是整体架构方向；再用 PageSpeed 跑一遍，逐条看它给出的具体文件和具体字节数，这决定的是落地细节；最后用 Chrome DevTools 的 Network 面板和 Timeline 反复验证，因为前两者算的是「规则命中情况」，Network 面板给的才是真实的瀑布流与耗时。

举个当时的真实例子。有个首页接了三个域名的静态资源，没有合并，合计 47 个请求。YSlow 直接给了很低的分数，规则 1 大红。PageSpeed 也扣分，但它额外提示「有 12 个小图标可以用 CSS Sprite 合并」。我们先把 12 个图标合成一张，请求降到 35 个；再把三个 CSS 合成一个、两个 JS 合成一个，请求降到 22 个；最后加缓存与 gzip，二次访问的瀑布流几乎只剩一个 HTML 文档。这个过程中 YSlow 的分数变化是渐进的，PageSpeed 的分数变化则有明显的台阶感，因为单点优化带来的收益更集中。

落地建议与常见误区

第一条建议：先量后改。没有基线数据就动手，改完也不知道有没有效果。当时我们的做法是把 YSlow 与 PageSpeed 的分数、Network 面板的请求数与总体积、首屏时间四项记在一张表里，每次发版前后各跑一次，趋势比绝对值更有说服力。

第二条建议：分清「评分低」和「体验差」。评分是规则命中度的代理指标，不等于用户感知。YSlow 重度惩罚 CSS 表达式这类规则，但现代浏览器早已不支持；反过来，一个满分的页面如果首屏关键路径上有一个同步脚本阻塞渲染，用户依然觉得慢。2013 年前后 WebPageTest 这类工具开始流行，它提供真实浏览器在指定地点、指定网络条件下的多次运行结果，能看到首次渲染时间与完全加载时间的分布，正好补上「评分高但体验差」的盲区。

第三条建议：警惕为了分数而分数。见过有人为了凑 YSlow 的「减少 HTTP 请求」，把一个几十 KB 的整站 CSS 全塞进一个文件，结果首屏被无关样式拖慢；也见过为了让 PageSpeed 的图片规则变绿，把清晰的产品图压成满是噪点的模糊图。规则是参考，不是目标。

常见的误区还有几个。一是以为装了插件性能就会变好，插件只是诊断，改动要落在代码和服务端配置上。二是只优化首页。内页的列表页、详情页往往才是访问大头，批量跑一遍比死磕首页收益更高。三是忽略移动端。2013 年用桌面插件跑出来的分数，放到 2G 或弱网环境下参考价值有限，高延迟下请求数量的权重会被进一步放大。

小结

YSlow 与 PageSpeed 的定位可以概括为：YSlow 用 Yahoo 的 23 条规则给你一张带权重的体检表，适合定方向、做架构决策；PageSpeed 更愿意下钻到单个文件，给出字节级的优化建议，适合做落地执行。两者规则重合度高，说明HTTP 请求数、压缩、缓存、资源体积、渲染阻塞这五件事是真正的瓶颈。实践中最稳的组合是 YSlow 定方向、PageSpeed 找细节、DevTools 的 Network 与 Timeline 做验证，有条件再用 WebPageTest 补上真实网络条件下的首屏与完全加载时间。最后提醒一句：分数是手段不是目的，所有优化都要以真实的加载瀑布流和用户感知为准。
