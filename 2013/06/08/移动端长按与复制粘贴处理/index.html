移动端长按与复制粘贴处理

移动端页面和桌面最大的差别之一是「长按」。桌面上一次点击就是一个动作，移动端的长按却被系统占用着：iOS Safari 会弹出链接预览和保存图片的菜单，Android 4.x 会进入文本选中状态并弹出放大镜。很多 Hybrid 页面想自己定义长按行为，第一关就是把这些默认动作关掉。这篇把当年处理这类需求的常用手段和踩过的坑整理一遍。

系统默认行为：先认清对手

不同平台的长按默认行为差别很大，处理方案也不同。

iOS Safari 上，长按一个链接会弹出「预览/打开/拷贝」的菜单，长按图片会弹出「存储图像/拷贝」，长按带 tel: 或邮箱地址的文本同样有系统菜单。Android 4.x 的 WebKit 内核在长按文本时进入选中模式，出现两个选择手柄和一个放大镜，可以拖动选区。这些行为都由浏览器接管，页面上的 click 事件根本不会触发。

所以做自定义长按之前，先明确要对抗的是哪一个：要弹自己的菜单，就得先抑制系统菜单；要禁止用户复制，就得关掉文本选中。

这里还有一个前提：自定义长按永远替代不了系统菜单的全部功能。用户长按一段文字，可能想复制，也可能想查词典、翻译、分享。如果页面一刀切关掉所有系统行为，就要自己提供这些替代路径，否则就是剥夺用户已有的能力。做 Hybrid 页面时这条边界要和产品确认清楚，不要为了交互统一把系统能力全砍掉。

关掉系统菜单与文本选中

最常用的三个 CSS 属性都带 -webkit- 前缀，2013 年必须写前缀，无前缀的 user-select 在部分浏览器还不识别。

三者的作用范围要说清。-webkit-touch-callout 只影响 iOS Safari 长按链接和图片时弹出的那个菜单，不影响文本选中。-webkit-user-select 控制文本能否被选中，对图片、链接的菜单无效。想让一个区域彻底不响应任何系统长按，两个都要写。

onselectstart 是这条路线上的另一件武器。它是 IE 时代就有的属性，返回 false 可以阻止选中开始，移动端浏览器同样遵守。当年为了兼容，会把 CSS 和事件两路都堵上：

还有一个隐蔽的连带影响：设为 none 的元素内部如果包着可点击的按钮，在某些 Android 版本上点击会变得不灵敏，因为浏览器把长按判定逻辑和选中绑定在一起。遇到这种问题只能缩小题设范围，不要整个页面一刀切。

最后一路是 oncontextmenu。它对应桌面浏览器的右键菜单事件，在移动端的作用是间接的：部分 Android 浏览器的长按菜单由这个事件触发，阻止它就能连带抑制菜单。

但它的兼容情况并不乐观。iOS Safari 的长按菜单不吃这一套，必须靠 -webkit-touch-callout。所以现实做法是三路并用：oncontextmenu 处理桌面和部分 Android，-webkit-touch-callout 处理 iOS，-webkit-user-select 处理文本选中。写全三处不是冗余，是各管一段。

用 touch 事件模拟长按

系统行为压下去之后，接下来是定义自己的长按。思路很直接：监听 touchstart 记下时间和坐标，启动一个定时器，touchend 或 touchmove 时取消；定时器触发即视为长按。

这段代码有几个细节值得说。

第一，必须有位移容差。手机上很难保证手指完全不动，几十毫秒内的微小抖动很常见，不设容差会导致每次触摸都触发长按。

第二，touchcancel 不能漏。系统打断触摸（来电、通知栏下拉、手势冲突）时只会派发 touchcancel，漏掉它会让定时器继续跑，用户在页面别处操作时莫名弹出菜单。

第三，长按与点击要互斥。上面的 triggered 标记就是这个作用：长按触发后，touchend 里不再执行点击逻辑。反过来，一旦定时器取消，也不能留下半激活状态。

第四，touchstart 里不要做重活。触摸到事件派发之间有延迟预算，这时候操作 DOM 会直接表现为「点下去没反应」。

用手势库区分单击与长按

自己写定时器能跑，但项目里手势一多（点击、长按、滑动、缩放）就会纠缠不清。当年 Hybrid 项目常用 Hammer.js 这类的轻量手势库，它把原始触摸事件封装成语义化的手势事件，长按只是其中之一。

用手势库的好处是互斥逻辑已经处理好：press 触发后 tap 不会跟着触发，滑动时 press 自动取消。坏处是引入一个依赖，且库的默认阈值不一定符合产品预期，需要按场景调。笔者的取舍是：单个元素的长按自己写，一整套手势交互才上库。

复制粘贴：execCommand 的现实

页面内选中文本后，用户只能靠系统菜单复制。如果产品要求「一键复制」按钮，就要用到 document.execCommand。

这段代码在 2013 年的兼容情况可以说是「能用但难用」。

document.execCommand('copy') 本身早在 IE 时代就存在，Chrome 与 Safari 也逐渐支持，但触发条件苛刻：必须由用户手势直接调用，不能在定时器或异步回调里调用；必须真正选中文本，select() 对 <input> 有效，对 <div> 的选中在很多浏览器里不被认可。上面的临时 input 就是为了绕过「不能选中任意元素」的限制。

iOS 的坑更多。setSelectionRange 在 iOS 上必须调用，否则选区为空，复制出来的是空字符串；调用时页面不能滚动，否则选区会被重置。Android 4.x 的表现取决于内核版本，有的能复制成功，有的静默失败。

失败提示很重要。复制失败时不要静默，要引导用户长按选中文本手动复制——这正是系统菜单还没被完全禁用的场景。实践中还有一种折中：页面保留文本可选，按钮只做「全选」，把最后一步交给用户确认。

粘贴比复制更麻烦。浏览器没有统一的「读取剪贴板」接口，paste 事件能拿到数据，但只在用户真正执行粘贴动作时触发，且各家的事件数据结构不一致：

移动端浏览器对 paste 事件的支持更是参差，iOS Safari 在某些版本里根本不派发。所以粘贴逻辑只能做增强，不能做依赖，输入框的默认行为必须保留。

输入框与平台差异

-webkit-user-select: none 一刀切的页面里，最常踩的坑是输入框也无法长按弹出「粘贴/替换」菜单，用户没法往输入框里贴内容。前面说过要给 input、textarea 单独放开，这里再强调一次，因为它出现在太多 Hybrid 项目里。

另一个相关问题是 iOS 上输入框获得焦点时会自动缩放页面。这通常不是长按引起的，而是 font-size 小于 16 像素时 iOS 的自动放大行为，但现象类似，都表现为「点一下输入框界面就变了」。处理办法是给输入框设 font-size: 16px，或者在 viewport 里限制缩放。

把上面的手段按平台整理成一张表，排查问题时直接对照，比逐个试快得多。

平台 长按默认行为 抑制手段 复制支持
iOS Safari 6 链接预览、保存图片菜单 -webkit-touch-callout: none execCommand 可用但需 setSelectionRange
Android 4.x 内置浏览器 文本选中加放大镜 -webkit-user-select: none 取决于内核版本，部分静默失败
Android 4.x Chrome 文本选中加系统菜单 user-select 加 oncontextmenu 支持较好
桌面 Chrome/Firefox 右键菜单 oncontextmenu 返回 false execCommand 可用

需要说明的是，Android 4.x 的「内置浏览器」和 Chrome 是两个东西。Android 4.1 之前系统自带的是旧版 WebKit，4.1 之后 Chrome 才成为默认但内核版本分裂严重，同一套代码在 4.0 和 4.3 上表现不同是常态。做兼容测试时至少要覆盖一个 4.0 设备，否则容易漏掉最早期的坑。

iOS 上还有一个和长按相关的经典问题：click 事件有约 300 毫秒延迟，这是浏览器在等待判断用户是否要双击缩放。这个延迟不是长按造成的，但常和长按一起被提及。当年的处理方式是用 touchstart 加定时器模拟即时响应，或者在 viewport 里禁止缩放后依赖浏览器自身的优化：

禁止缩放会影响可访问性，视障用户无法放大页面，正式站点要慎用。折中做法是保留缩放，用 touchstart 做即时反馈，把 300 毫秒的体感延迟藏在视觉反馈里。

小结

移动端长按的本质是「系统默认行为」与「页面自定义行为」的争夺，处理顺序是先抑制、再定义。抑制用 -webkit-touch-callout 关 iOS 菜单、-webkit-user-select 关文本选中、oncontextmenu 关桌面与部分 Android 菜单，三路各管一段，缺一不可。自定义长按用 touchstart 加定时器实现，关键是位移容差、touchcancel 清理和长按与点击的互斥；手势复杂时交给 Hammer.js。复制用 document.execCommand('copy') 加临时 input，在 2013 年兼容很差，必须做失败兜底，引导用户长按手动复制；粘贴只能监听 paste 事件做增强，不能作为唯一通路。Android 4.x 内置浏览器与 Chrome 的行为分裂是兼容测试的重点，至少要覆盖一个早期设备。最后别忘了给 input、textarea 单独放开选中限制并把字号设到 16 像素，这是长按处理里最高频的两个回归点。
