JavaScript 严格模式 strict 的作用

最近给一个老项目做代码体检，发现一个尴尬的事实：同一个变量名拼错，在开发环境安静地变成 undefined，线上某个分支里却突然抛了异常。查到最后，差异只在于那段代码被包在一个声明了 "use strict" 的函数里。严格模式并不是新语法，它是 ECMA-262 第 5 版（2009 年 12 月定稿）带进来的一个”更严格的子集”，目的是把 JavaScript 里一些历史上将错就错的设计堵上。本文从源码层面把它做的事、带来的收益和落地时的取舍讲清楚。

严格模式是什么

严格模式（strict mode）是 ES5 引入的一个可选执行模式。它没有引入新语法，只是在既有语法上收紧规则：一部分原来”静默失败”的操作改为抛出异常，一部分危险的写法被直接禁用，还有一部分隐式类型转换被取消。它对开发者是编译期（准确说是解析期）的提示，对用户则常常是一次访存到报错的差别。

严格模式的作用域只有一层，且是函数级作用域，不是块级。这一点在 ES5 时代尤其重要，因为那时候还没有 let 和 const：

它到底改了什么

把 ES5 规范里的条目归类，实际影响日常开发的主要是下面几组。

静默失败改为抛错

非严格模式下，给一个只读属性赋值、给一个 delete 不掉的东西执行 delete，都是”什么都不发生”。严格模式下它们抛 TypeError。这类改动收益最大，因为它把 bug 从”悄悄扩散”变成”当场报错”。

配套的是八进制字面量被禁用。010 在非严格模式里是 8，这种隐式转换正是无数”日期算错一天”的源头，严格模式下直接是语法错误。同理，with 语句被禁用，因为它让作用域链在运行期才确定，压缩工具无法安全处理，可读性也极差。

隐式 this 不再转对象

这是对库作者影响最大的一条。非严格模式下，函数里的 this 如果是 null 或 undefined，会被强制替换成全局对象，原始值则被包装成对象。严格模式取消了这个”兜底”：

好处是构造函数忘写 new 时能立刻发现：this 变成 undefined，访问属性直接抛错，而不是把属性静默挂到 window 上。jQuery 在 1.9 之后对事件回调的调用就受益于此——回调里 this 是触发元素，不存在被意外包装的情况。

参数与属性的重复被禁止

非严格模式允许同一个函数声明两个同名参数，后一个覆盖前一个；也允许对象字面量写两个同名属性。严格模式下两者都是语法错误。ES5 规范把它列为语法错误，是为了让”哪一个生效”不再依赖实现细节。

arguments 被钉死

arguments.callee 与 arguments.caller 被禁用，前者会让引擎无法做内联优化，后者直接暴露调用栈。同时，arguments 不再与形参联动：修改形参不会改变 arguments 里对应位置的值。这让 arguments 变成一个纯粹的”调用时快照”。

eval 作用域隔离

严格模式下 eval 不能再向所在作用域声明变量。这一点对安全有实际意义：一段拼接出来的 JSON 或表达式如果被 eval，它无法借机污染闭包内的变量。

为未来关键字让路

implements、interface、let、package、private、protected、public、static、yield 被保留为关键字，不能用作变量名。ES5 之后这些位置确实陆续被新特性占用，先占位是必要的。

写不写严格模式：文件级还是函数级

这是落地时真正要做的决定。先看收益与代价。

严格模式的收益集中在三处。一是把 typo 变成显式错误，减少 undefiend 这类拼写错误活到线上；二是禁用危险写法，相当于强制团队不碰 with、arguments.callee；三是让引擎少做一些兼容老代码的兜底，对 this 的包装、八进制的处理都可以省掉，理论上对性能有小幅帮助。

需要说明的是，关于性能要诚实：主流引擎对非严格代码的优化已经很成熟，严格模式带来的性能差在多数场景下测不出来，它真正的价值在”早报错”而不是”跑得快”。把严格模式当性能手段宣传是不合适的。

它的代价是”连带伤害”。如果你的文件被别的文件以普通脚本方式拼接、或者你的函数会被第三方代码以 call(null) 调用，行为就会变。因此推荐的顺序是这样的：

flowchart TD
    A[新写的代码] --> B[是否会被第三方拼接或调用]
    B -- 否 --> C[文件级 use strict]
    B -- 是 --> D[函数级 use strict]
    C --> E[保证它处在文件第一条语句]
    D --> E
    E --> F[跑一遍现有测试]

实际项目里最稳的做法是新文件默认开严格模式，老文件不开。混合状态下要特别小心一件事：严格与非严格的代码可以共存于同一文件的不同函数，但只要一个函数是严格的，它调用的函数未必是严格的，this 的兜底行为可能不一致。jQuery 的处理方式值得借鉴——库自身全严格，但绝不替宿主页面开严格。

还有一个务实建议：用 JSHint 或 JSLint 的 strict 选项做静态检查，比在代码里写指令更早发现问题。工具能在提交前就报出”这里在严格模式下会抛错”，而不是等用户点出来。

常见的坑

第一，字符串指令的位置。放在 'use strict' 之前的任何语句都会让它失效，包括注释之外的代码，也包括看似无关的 var。第二条语句之后写就晚了。

第二，函数级严格不会影响嵌套的非严格函数。上面的 outer/inner 例子已经说明这一点。如果担心团队有人漏写，用构建工具统一在文件头部注入比依赖每个人的记性可靠。

第三，合并压缩时的顺序。多个文件拼成一个时，中间文件的 'use strict' 会跑到第二条语句之后而失效，还可能把后面文件一起拖进严格模式。UglifyJS 处理这类场景时不会自动修正位置，需要在构建配置里显式开启”保留第一条语句”或改用函数包裹。

第四，跨文件的 call/apply。严格函数被别处以 call(null) 调用时 this 为 null，而非严格函数里是全局对象，同一段代码两种行为。封装公共方法时，如果需要容忍两种调用方，不要假设 this 一定是对象。

第五，浏览器控制台的直接粘贴。在 Chrome 或 Firefox 的控制台里粘贴一段没有 'use strict' 的代码，默认是非严格模式；而同样的代码在严格模式的文件里运行结果可能不同。调试时如果结果对不上，先确认执行环境是不是严格模式。

小结

严格模式是 ES5 给 JavaScript 加的一道静态安全栏：它不新增能力，只把原本静默失败的写法推到抛错，把 this 的隐式包装、arguments 的联动、eval 的作用域泄漏这些历史包袱收掉。收益是把 bug 暴露在开发期，代价是会改变被第三方代码调用的函数的行为，所以新文件默认开、老文件保持原样、被拼接的文件优先用函数级指令，是比较平衡的落地策略。性能上不要抱不切实际的期待，它的价值在正确性而非速度。写的时候注意指令必须是第一条语句，合并压缩时注意顺序别把它挤到中间。
