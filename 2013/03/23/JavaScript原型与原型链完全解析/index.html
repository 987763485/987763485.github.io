JavaScript 原型与原型链完全解析

前面两篇分别谈了资源加载和 DOM 操作，这篇回到语言本身。原型与原型链是 JavaScript 里最容易被「用得很熟却说不出原理」的知识点，笔者当年也是靠死记硬背过了面试，直到真正踩了几次坑才把整条链路串起来。本文按「是什么、为什么、怎么做、坑在哪」的顺序完整梳理一遍，力求讲清到规范层面。

prototype 与 proto 是两个东西

混乱几乎都从这里开始：prototype 与 __proto__ 名字太像，指向却完全不同。

  • prototype 是函数独有的属性。每一个普通函数被创建时，都会自动获得一个 prototype 属性，它指向一个对象，这个对象就是「用这个函数 new 出来的实例的原型」。
  • __proto__ 是对象实例上的内部槽位在部分浏览器上的暴露形式。按照 ECMA-262 第 5 版，对象内部有一个 [[Prototype]] 内部属性，它指向该对象的原型。__proto__ 并非规范属性，但 2013 年前后的主流浏览器都已支持它，方便调试时观察。

原型链查找的完整过程

现在把链条拉长。Person.prototype 本身也是一个普通对象，它是怎么来的？默认情况下它由 Object 构造函数创建，因此它的 __proto__ 指向 Object.prototype。而 Object.prototype.__proto__ 指向 null，链条到此终止。

flowchart TD
    A[p 实例] -->|__proto__| B[Person.prototype]
    B -->|__proto__| C[Object.prototype]
    C -->|__proto__| D[null]
    E[hasOwnProperty 等内置方法] --> C
    F[toString / valueOf] --> C

访问 p.sayHello 时，引擎做的事可以精确描述为：

  1. 检查 p 自身有没有名为 sayHello 的属性，有则返回。
  2. 没有，则取 p 的 [[Prototype]]，也就是 Person.prototype，在它身上找。
  3. 还没有，则继续取 Person.prototype 的 [[Prototype]]，也就是 Object.prototype，在它身上找。
  4. 还没有，取到 null，查找结束，返回 undefined。

写入操作遵循另一套规则，这一点极其重要：给 p.name = '王五' 赋值时，引擎不会去改原型上的 name，而是在 p 自身创建一个新属性，把原型上的那个「遮住」。这就是属性的遮蔽（shadowing）。delete p.name 之后，原型上的值会重新露出来。

但有一个例外：如果原型上的同名属性带有写入器（setter），赋值就会调用那个 setter，而不是创建自身属性。ES5 的 Object.defineProperty 可以构造出这种行为，它也是理解属性描述符的最佳入口。

继承的三种实现

原型链的核心用途是继承。从 ES3 到 ES5，常见写法有三种，各有代价。

构造函数绑定的组合继承

选择继承写法时，判断标准只有三条：实例属性是否各自独立、方法是否共享一份、instanceof 与 constructor 是否正确。三条都满足的写法，在 ES5 时代就是 Object.create 方案。

还有一类需求要单独提：混入（mixin）。JavaScript 只有单继承，一个对象只能有一条原型链，但业务上常需要「既能当事件目标，又能当可观察对象」。当年的做法是把多个对象的方法逐个拷到目标原型上，形成一个逻辑上的多继承：

常见坑逐个数

坑一：引用类型属性被所有实例共享

前面已经讲过，这里补充一条判断标准：原型上适合放方法和常量，不适合放对象、数组、函数这类引用值。凡是每个实例应该有独立副本的数据，一律放在构造函数里。

复盘结论有两条，都可以直接复用：

  • 永远不要往 Object.prototype 上加可枚举属性。当年那些「为了兼容打补丁」的写法，代价会在很久以后以完全不相干的形式出现。必须加时用 Object.defineProperty 把 enumerable 设为 false。
  • 遍历对象属性时，for...in 必须搭配 hasOwnProperty，或者直接用 Object.keys。

如果要把这个案例的排查过程写成可复用的方法，大致是四步：先用 console.log 打出可疑对象的原型链，确认每一环是什么；再确认出问题的方法定义在哪一环；然后检查那一环上的属性是否可枚举；最后看调用方是 for...in 还是 JSON.stringify，两者触发的规则不同。这个顺序比盲目打断点快得多，因为原型问题几乎都发生在「查找」和「枚举」两个动作上，而不是赋值本身。

注意 while 循环里加了深度上限。正常情况下原型链长度是固定的几环，但如果有人给原型设置了循环引用，查找会变成死循环，这种写法至少能在调试时发现问题，而不是让浏览器直接卡死。

小结

原型链的本质是一条由 [[Prototype]] 串起来的对象链，prototype 是函数声明继承的入口，__proto__ 是实例指回原型的指针，查找时按「自身、父原型、父父原型，直到 null」的顺序逐级向上。读取会走完整条链并在命中处停止，写入则默认在实例自身创建属性并遮蔽原型上的同名值，只有遇到 setter 才会写入原型。方法应该放在原型上共享，引用类型的实例数据必须放在构造函数里各自一份；用 Object.create 加 Object.defineProperty 修正 constructor，是 ES5 时代最干净的继承写法。最容易出问题的三处是共享引用属性、重写原型后丢失的 constructor，以及被无意识污染的原型链顶端。把这三处和 for...in 的自身判断固定成代码习惯，绝大部分原型相关的 bug 都可以避免。

如果只记一句话，那就是：原型链上的东西是所有实例共享的，构造函数里的东西是每个实例独有的。判断一个成员该放哪，只看它需不需要独立副本，剩下的边界情况——constructor 修正、不可枚举属性、原型污染——都从这一条推导得出来。写代码时多花一秒想清楚成员的位置，比事后对着压缩过的代码猜要划算得多。
