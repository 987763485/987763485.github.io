DOM 增删改查与文档碎片 DocumentFragment

上一篇谈了资源的合并与压缩，解决的是「资源怎么送得快」。这一篇换个方向，谈资源到了浏览器之后，代码怎么把内容写进页面：DOM 的增删改查，以及被很多人忽略的 DocumentFragment。同一个需求，写法不同，在 IE 8 上可能差出十几倍。

DOM 增删改查的最小集合

DOM 的操作说到底就是四件事：查（找到节点）、增（插入节点）、删（摘掉节点）、改（改属性或内容）。把常用的接口列一遍，后面的讨论都基于这些：

insertBefore 是整个插入操作的核心，appendChild 在规范里就是「插到 null 之前」的特例。removeChild 则要求先拿到父节点，这一点和 jQuery 封装好的 remove() 体验不同，原生 API 没有「我把自己删掉」这种说法。

IE 的兼容问题主要集中在 className 与 class 的差异、setAttribute('class', ...) 在部分版本不生效，以及事件绑定的 addEventListener 与 attachEvent 之分。本文的例子统一用 setAttribute 设置类名，是为了让代码在 IE 8 下也能直接跑。IE 8 同样支持 createDocumentFragment，这一点可以放心，文档碎片并不是新特性，DOM Level 1 时代就已经在规范里了。

把这些差异说清楚，是想提醒一件事：性能数据没有普适性。同样一段批量插入代码，在 IE 8 上碎片的收益可能是十倍，在 Chrome 20 上可能只有三倍。做优化之前先在自己的目标浏览器上量一遍，别人的结论只能当参考。

为什么批量插入会慢

单独插入十个节点不会有任何问题，问题是当循环次数变成一千、一万。原因在于，每一次对文档树的修改，都可能触发浏览器的重排（reflow）与重绘（repaint）：浏览器需要重新计算受影响元素的几何信息，再决定哪些像素要重画。

flowchart TD
    A[appendChild 插入节点] --> B[文档树被标记为脏]
    B --> C[重排计算几何与位置]
    C --> D[重绘画布]
    D --> E[下一次插入继续触发]

浏览器实现上有一定的批量优化：如果脚本在同一个任务里连续改了很多次 DOM，渲染引擎通常会推迟到脚本执行完再统一重排。但这不意味着可以无限插入，两个成本依然存在：一是每次插入都要走一遍节点查找与树结构调整，节点数大了之后开销线性增长；二是脚本执行时间本身在变长，主线程被占住，页面既不能响应点击也不能滚动。

重排为什么贵，可以拆开看：浏览器要重新计算受影响元素及其相邻元素的盒模型信息，也就是位置和尺寸，然后在布局树里重新排列，最后才决定哪些区域要重绘。读布局属性的操作（比如 offsetTop、scrollHeight）会强制浏览器提前把未完成的重排算完，因此「读一次、写一次、再读一次」的交错写法比「全部写完再一次读」要慢得多。这个规律在当年就已经是调优常识，如今常被叫做读写分离。

所以优化的方向很明确：减少插入次数，或者把插入的中间过程放在文档树之外。后者正是 DocumentFragment 的用途。

DocumentFragment 是什么

document.createDocumentFragment() 创建一个文档片段。它在接口上就是一个轻量的文档节点，可以 appendChild、insertBefore、querySelector，但它不在文档树里。

关键特性有两条：

  • 它是一个「临时容器」。把节点插进片段，不会触发任何重排，因为屏幕上没有任何变化。
  • 把片段本身插进文档时，插进去的不是这个容器，而是它的所有子节点，容器自身不会留在文档里。
flowchart TD
    A[createDocumentFragment 建立临时容器] --> B[在容器内 appendChild 一百次]
    B --> C[容器不在文档树中]
    C --> D[无重排 无重绘]
    D --> E[一次性 appendChild 容器到文档]
    E --> F[浏览器只做一次重排]

三种批量写法的对比

同样是插入一千个列表项，当年至少有三种主流写法。我用 Chrome 20 和 IE 8 各跑了一次，数据大致如下（多次运行取中位数，仅供比较量级）：

写法 Chrome 20 IE 8 说明
循环 appendChild 到文档 约 120 毫秒 约 900 毫秒 每次都动文档树
循环拼 innerHTML 字符串后一次赋值 约 25 毫秒 约 110 毫秒 需要一次完整解析
createDocumentFragment 后一次插入 约 30 毫秒 约 150 毫秒 保留节点对象与事件

三种写法怎么选，取决于你的需求：

  • 如果只是渲染一段静态列表，innerHTML 拼接通常最快，代码也最短。
  • 如果新节点上要绑定事件、保存引用、或者后续还要逐个操作，必须用 DocumentFragment，因为 innerHTML 赋值后原节点上的监听全部丢失。
  • 如果插入的节点本来就已经在文档里（比如调整顺序），既不能用 innerHTML，也不能用把节点搬进碎片再搬回来的办法，只能用 insertBefore 重排，或者用 removeChild 加 insertBefore 的组合。

表格里的数字要说明来源，否则容易变成玄学。测法是新建一个含 1000 个空 li 的列表，清空后用三种写法分别灌入 1000 个带文本的节点，用 Date 对象取前后差值，重复十次去掉最高最低取平均。这种粗测法误差不小，但足以区分量级，真正的对比还是应该结合业务场景做。另外 DOM 操作的耗时和机器性能关系很大，我给出的 IE 8 数据来自一台旧的办公台式机，读者在自己的环境里复现，绝对值大概率不一样。

删除的两种思路

删节点看起来简单，实际有两种语义不同的思路。

第一种是逐个删除，removeChild 每次摘一个。一千次删除就是一千次树结构调整。

第二种是一次性清空：把父节点的 innerHTML 设为空字符串，或者循环 removeChild(firstChild) 直到没有子节点。

如果父节点上绑了事件委托，第一种写法要注意事件是否已经派发完；第二种 innerHTML = '' 会连同子节点上的所有监听一起销毁。如果删完之后还要复用这些节点（比如做撤销），就必须用 removeChild 把节点取出来另存，innerHTML 是拿不回来的。

删除操作还有一个内存层面的细节：节点从文档里摘掉之后，如果没有其他引用指向它，它就可以被垃圾回收；但如果代码里存了这个节点的引用，或者节点上挂着闭包，它就一整棵子树都留在内存里。长生命周期的单页应用尤其要注意，反复增删的列表如果不主动清理引用，内存会持续上涨。

getElementById 有哈希表索引，单次查询不算贵，但循环一千次仍然是白做工。如果用的是 querySelectorAll，代价更高，因为它要走完整的选择器匹配。凡是循环里不变化的查询结果，都应该提到循环外面。

查询的另一个成本来源是选择器的写法。querySelectorAll 是从右往左匹配的，#list li.item span 这种后代选择器，会先把文档里所有 span 找出来再逐级验证祖先。写得更具体一些，比如限定父级 id，匹配范围就能小很多。在 IE 8 上这个差异尤其明显，因为它没有原生 querySelectorAll 的优化实现，jQuery 的选择器引擎本身就是用 JS 模拟的，写宽泛的选择器等于让引擎多遍历几轮。

另外要注意 getElementsByClassName 和 getElementsByTagName 的实时性。它们返回的是活的集合，文档一变集合就变，把这样的集合存起来长期使用，读到的东西可能和你预期不一致。需要快照就用 querySelectorAll，它返回的是静态 NodeList。

jQuery 在这一层帮我们做了缓冲，所以很多人没有意识到原生 API 的差异。jQuery 1.9 的 $() 内部就是先 querySelectorAll 再包装成静态数组，之后链式操作都基于这个快照。这带来一个可以观察到的现象：先用 jQuery 查到一批元素，再用原生代码往文档里插入新节点，之前那批 jQuery 对象不会自动包含新节点；反过来，用 getElementsByTagName 拿到的集合会。写原生代码时如果心里没这个概念，就会出现「加了新节点却选中不到」的困惑。

小结

DOM 操作的成本主要在「改文档树」这个动作上，而不是创建节点本身。批量插入时把节点先放进 DocumentFragment，再一次性插入文档，可以让重排从多次降为一次，在 IE 8 这类重排代价高的引擎上收益尤其明显。innerHTML 拼字符串在纯渲染场景下更快，但它会销毁节点上的事件，也拿不回被替换的旧节点。遍历时还要小心 getElementsByTagName 返回的动态集合，边遍历边删除会漏数据。把这些细节固定成团队的编码习惯，比事后再用工具 profiling 要划算得多。
