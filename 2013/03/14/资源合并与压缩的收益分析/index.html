资源合并与压缩的收益分析

上个月把一个运营活动的落地页做了一次瘦身，动作只有两个：把散落的 JS 和 CSS 合并成少数几个文件，再对产物做 minify 和 gzip。事后 YSlow 评分从 D 升到 B。这篇文章把当时的思路、数据和踩过的坑摊开来讲，重点回答一个问题：资源合并与压缩到底赚到了什么，又在哪些地方不赚。

前端资源的开销模型

浏览器渲染一个页面，成本并不只发生在下载 HTML 那一刻。每一个 JS 或 CSS 文件都要单独走一遍 DNS 查询、TCP 三次握手、发送请求、等待响应、下载内容这几步。2013 年前后的主流浏览器对同一个域名的并发连接数一般限制在 6 个左右，多出来的请求只能在队列里等位。这些步骤里，除了最后一步之外，都与文件大小无关。

flowchart TD
    A[解析到资源引用] --> B{并发连接是否已满}
    B -->|已满| C[排队等待]
    B -->|未满| D[TCP 三次握手]
    C --> D
    D --> E[发送请求]
    E --> F[等待响应 RTT]
    F --> G[下载并解析执行]

这里最容易被忽略的是固定开销。假设服务器在广州，用户在北京，RTT 约 60 毫秒，那么一个请求光是握手加等待就吃掉 60 毫秒以上，而这跟文件大小几乎没有关系：一个 1 KB 的 JS 和一个 100 KB 的 JS，在握手这一项上的花费是一样的。业界经验也支持这个判断：Yahoo 早年发布的性能规则里，「减少 HTTP 请求数」常年排在第一位，终端用户感受到的响应时间里大约有 80% 花在前端。

还有一个细节常被问到：既然浏览器会缓存，那请求多也无所谓吧？这个说法只对了一半。缓存解决的是「第二次之后不再下载」，但浏览器在复用本地副本之前，仍然可能向服务器发一次条件请求（带 If-Modified-Since 或 If-None-Match），等服务器回一个 304 Not Modified 才算确认。这一次确认同样要占一个连接、等一个 RTT。所以请求数多不光影响冷启动，也会持续拖累热访问，只是代价小一些。

所以前端优化要盯的是两个互相独立的变量：请求数量和传输体积。合并主要作用于前者，压缩主要作用于后者，两者的收益算法完全不同，下面分开说。

合并：把请求数压下来

先说合并，也就是把多个小文件拼成少数几个大文件。当时这个页面一共有 23 个请求，其中 JS 14 个、CSS 6 个、图片 2 个。14 个 JS 里有 9 个是各业务方自己带上来的小插件，每个只有几 KB，加起来不到 60 KB，却要占掉 9 个请求位。

我的处理办法是先分类再合并：

  • 按加载时机分：首屏必须用的合成一个文件，可以延迟的比如浮层交互、日志上报单独放一个文件，页面 onload 后再加载。
  • 按稳定性分：jQuery 这类第三方库改动极少，单独成文件，让它的缓存尽量长期有效；业务代码经常改，单独成文件。
  • CSS 合并成一个文件，同时清理掉里面的 @import。@import 看起来是「在 CSS 里引 CSS」，实际上它会把请求串行化，比用 <link> 并排写更慢。
  • JS 统一放到 </body> 前。放在 <head> 里时，浏览器必须把它下载并执行完才会继续解析后面的 DOM，首屏会被直接堵住。

这四条里，第四条性价比最高，也最容易被忽视。很多时候页面慢不是因为文件太大，而是因为一个几十 KB 的脚本堵在 <head> 里，把后面整页的解析都挡住了。把脚本挪到页面底部，往往不花一分钟就能拿到立竿见影的改善。

合并之后请求数从 23 降到 8。这里要强调一点：合并的顺序必须手工确认。依赖 jQuery 的插件一定要排在 jQuery 之后，否则压缩产物语法是对的，运行时会直接报 undefined is not a function，而这种错误在压缩文件里几乎没法定位。

压缩：把字节数压下来

  • 已经压缩过的格式不要指望 gzip。JPEG、PNG 本身就是压缩格式，gzip 之后通常只小 1% 到 2%，有时反而会因为头部体积略微变大。这类文件该做的是换更好的编码参数，或者改用更合适的格式。WebP 在 2010 年 9 月发布，Chrome 当时已经支持，做渐进增强是可行的。
  • 太小的文件不值得 gzip。几百字节的文本，gzip 头部（约 20 字节）加上分块信息，可能比原文件还大。

判断一个页面该不该上 CDN，标准也很朴素：静态资源多、用户地域分散、峰值流量有规律的页面，收益最明显；反过来，一个全部走同域内嵌样式的后台页面，上了 CDN 也只是多一层缓存管理成本。CDN 真正的价值不只是「加速」，还包括把静态流量从应用服务器上摘下来，让应用服务器的连接数留给动态请求。

    C --> D[文件名加时间戳]
    D --> E[上传 CDN]
    E --> F[服务端开启 gzip]
    F --> G[浏览器请求]
    G --> H[命中缓存则直接复用]

收益到底怎么算

把两个变量拆开算，才能判断一个页面值不值得做。估算模型很朴素：传输时间等于体积除以下行带宽，排队与握手时间等于批次数乘以 RTT。这个页面按 2 Mbps（约每秒 250 KB）带宽、60 毫秒 RTT 测算：

项目 优化前 合并后 再 minify 再 gzip
JS 请求数 14 3 3 3
CSS 请求数 6 2 2 2
总请求数 23 8 8 8
JS 体积 486 KB 486 KB 214 KB 62 KB
CSS 体积 126 KB 126 KB 88 KB 19 KB
传输耗时估算 2.8 秒 2.8 秒 1.2 秒 0.7 秒
排队握手估算 0.24 秒 0.12 秒 0.12 秒 0.12 秒

表格里「再 minify」一列的字节数完全没变，变的只有请求数。合并本身一点字节都没省，它省的是那 0.12 秒的排队和握手，以及浏览器解析更多标签的开销；真正把 2.8 秒打到 1.2 秒的是 minify，486 KB 的 JS 压到 214 KB，主要来自删注释和缩短变量名；最后 gzip 把文本再砍掉七成以上。图片有 96 KB，全程没参与压缩，这也是为什么优化后总量还有 0.7 秒左右。

反过来看更直观：一个只有 3 KB 的小插件，下载时间几乎全是固定开销，砍掉它的请求位就是纯粹的收益。这正是合并的收益来源，它消灭的是那些不产生任何有用字节的握手与等待。

如果换到弱网环境，收益结构会明显不同。3G 网络下 RTT 常到 300 毫秒，带宽也只有每秒几十 KB，此时合并省下的排队时间会从 0.12 秒放大到 0.6 秒，甚至超过压缩的收益。所以不能拿一个固定结论套所有页面，移动端页面要更重视请求数，桌面端则可以放松一些。

还有一个容易被忽略的变量是缓存命中率。上面的表算的是冷启动场景，也就是缓存全空。真实用户里老客占比很高，第二次访问时那 8 个文件可能一个都不下载，页面时间只取决于 HTML 本身。这意味着优化收益在不同用户群体间的分布极不均匀：首次访问的用户拿到了全部收益，回访用户几乎没有变化。做汇报的时候要把这两类用户分开统计，否则数据会很难看，也会低估优化的价值。

坑在哪

最后是这次实际踩到的坑，按代价从大到小排。

第一，缓存失效。合并之后业务代码改一个字符，整个文件的缓存就作废了。当时的做法是在文件名后加时间戳，例如 app.20130310.js，让 URL 变化直接对应内容变化。但如果只改查询串而不改文件名，一部分代理服务器和 CDN 节点不会把它当成新资源，缓存刷新会被拖延，这一点后来花了很久才排查出来。

第二，过度合并。我一开始图省事把第三方库和业务代码打成一个文件，结果业务代码每次发版都会让 jQuery 的缓存一起失效。拆开之后，jQuery 那个文件几乎不再下载，这一项就吃掉了总收益里相当大的一块。

第三，minify 的安全边界。JS 里依赖自动分号插入的写法，比如 return 后面直接换行写返回值，压缩时可能被拼成一行导致语义变化；CSS 里针对 IE 的 hack 也可能被误判成注释删掉。压缩产物必须回归测试，不能直接上线。我们后来的做法是在构建脚本里跑一遍单元测试，压缩产物单独起一个静态服务，用抓包工具确认响应头里的 Content-Encoding 和 Content-Length 符合预期，再切换流量。

第四，单文件过大的反效果。把请求数压到极限之后，首页 JS 变成一个 200 KB 的文件，它会长时间占满连接，首屏可交互时间并没有跟着下降。合理的分片比极端合并更实用。

第五，Sprite 的维护成本。改一个图标要重新拼图，拼图位置一变，所有用到这张图的 background-position 都要跟着改。后来我们的约定是只往图末尾追加，不调整已有位置，才把这项成本压住。

第六，忘了发缓存头。文件合并得再好，如果响应里既没有 Expires 也没有 Cache-Control，浏览器每次都要回源验证一次，合并省下的握手时间会被重新吐回去。静态资源至少要给一个未来一年的过期时间，配合文件名变更来主动失效。

小结

资源合并与压缩是两个独立的手段：合并消灭的是请求的固定开销，压缩消灭的是传输体积，两者要分开度量。这次的结论是，minify 拿走了大头，gzip 是稳定的第二级收益，合并在桌面端收益有限但在弱网上会被放大。真正容易翻车的地方不在技术，而在缓存策略和拆分粒度：合并得越激进，缓存失效的代价越大。所以我的建议是先量化再动手，用 YSlow 或 Page Speed 出一份基线，改完再跑一次，让每个决定都有数据支撑，而不是凭感觉合并。最后再补一句：合并与压缩解决的是「把资源送到浏览器」这一段的成本，代码本身的执行效率是另一条战线，那是下一篇要谈的事。
