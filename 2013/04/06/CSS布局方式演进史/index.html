CSS 布局方式演进史

本文属于《HTML 与 CSS》第 16/62 篇
上一篇系列目录下一篇

CSS 的布局方式不是某一天被设计好的，而是一路被”能用就行”的需求推着往前走的。从用表格硬撑页面，到 float 满天飞，再到 Flexbox 让容器第一次真正指挥子元素排列，每一步都在解决上一阶段留下的痛。本文按时间顺序把这段演进史捋一遍，顺带说清每种方式在当时解决了什么问题、留下了什么坑，以及为什么 Flexbox 值得现在就开始学。

没有布局方案的年代：用表格拼页面

上世纪 90 年代中后期，浏览器里的 CSS 支持非常有限，但网页设计师已经需要做出”左边导航、右边正文”的多栏结构。HTML 里恰好有一个现成的表格结构：<table>、<tr>、<td> 天生就能按行列切分区域，而且各个浏览器渲染得相当一致。于是 <table> 从”展示数据”变成了”搭建页面骨架”，<table border="0" cellpadding="0" cellspacing="0"> 一度是每个页面的标配。

表格布局的做法很直接：外层一个大表格定宽居中，内部用嵌套表格或 colspan/rowspan 切出导航区、内容区、页脚。它能工作，而且可预测性极强——在 Netscape 4 和 IE5 上效果几乎一样，这在当年是天大的优点。当时的桌面屏幕分辨率还集中在 800×600 和 1024×768，页面宽度普遍定在 760 像素或 960 像素，用像素写死一切反而让设计师有种掌控感。

但它的代价很快显露出来。

第一，语义彻底崩坏。一个用表格搭的首页，源码里可能一个 <h1> 都没有，取而代之的是几十层嵌套的 <td>。屏幕阅读器按表格顺序朗读，把用户的阅读顺序搅得一团糟。搜索引擎的爬虫同样要在这堆标签里费劲找正文，早期很多站点的收录质量差与此直接相关。

第二，结构僵化。表格的行列是对齐的，想做一个”左边固定 200 像素、右边自适应”的两栏还勉强可行，想做一个不等高的错落布局就得靠嵌套表格反复套娃。一个三栏页面套上七八层表格是常态，源码体积随之膨胀，拨号网络下光是 HTML 就要下载半天。

第三，渲染必须等表格完全解析完。浏览器要读完整个表格的结构才能确定每列宽度，首屏内容只能干等。这一点在拨号上网时代是致命的。更糟的是为了让”看起来更快”，不少人把整页塞进一个大表格，浏览器渲染引擎根本没有机会增量绘制。

第四，改版等于重写。表格布局是”结构即表现”，调一个间距往往要动三四层嵌套，维护成本随着页面复杂度指数上升。一个页面传到第二个人手里，基本只能推倒重来。

第五，可访问性与设备适配无从谈起。表格布局天生定宽定高，换到小屏幕上就是横向滚动条，而 2007 年之后智能机的普及让这个问题越来越刺眼。

值得注意的是，表格布局并没有立刻消失。在需要严格对齐的邮件模板里，它至今仍是主流——因为邮件客户端对 CSS 的支持比 90 年代的浏览器好不了多少。这是布局史上最讽刺的遗产：最被唾弃的方式，在最封闭的场景里活得最久。

Float 时代：从排版附属品到布局主力

float 本来只是为了让文字环绕图片而设计的：把图片浮动到左侧，文字自然排在它旁边。CSS 1 里就这么点野心。但设计师们发现，既然 float: left 能让一个块脱离文档流并靠左，那把它套上宽度，不就是一个”栏”了吗？

于是 float 布局成了 2000 年代的事实标准。它之所以能取代表格，还有一个常被忽略的背景：那一代浏览器的盒模型不统一。IE6 在怪异模式下用的是”边框和内边距算进 width”的旧盒模型，而标准模式按 CSS 2.1 是”width 只算内容”。写一个定宽两栏，IE6 下会比标准浏览器宽出 40 像素，直接错位。当年的解法是给所有元素统一加 box-sizing: border-box，或者干脆用 hack 把 IE 拉回标准模式。这些折腾让”浮动手动算宽度”变成了一门手艺，也让后来的 Flexbox 承诺”空间由容器分配”显得格外诱人。

但它带来了一连串新问题，每一个都是当年前端面试的必考题。

父元素高度塌陷

浮动元素脱离了正常文档流，父元素如果没有其他内容，高度就会塌陷成 0，后面的元素会跑到浮动元素下面去，或者背景、边框直接”消失”。

这是最广为流传的清浮动方案。它的原理是插入一个清除了浮动的伪元素，让父元素把浮动子元素的高度”包”进去。早期的写法要额外加一个空的 <div class="clear">，后来演进成纯 CSS 的 clearfix，再到 2012 年前后配合 ::before 防止外边距折叠的完整版。还有一派主张直接给父元素设 overflow: hidden，原理是触发新的块级格式化上下文，副作用是会裁掉所有溢出的下拉菜单，属于省事但有风险的方案。

需要给兄弟元素让位

浮动元素仍然占据水平空间，后续不浮动的块级元素会感知不到它，直接占据它的位置。所以两栏布局里，右侧内容要么也浮动，要么用 margin-left 手动让出侧栏宽度。这让”改一个栏宽”变成牵一发而动全身的事。

垂直方向的无力

float 只能水平排列，做垂直等高、垂直居中几乎无解。当年”让一个 div 垂直居中”是个能在论坛里吵几十页的问题，解法无非是 line-height 骗、绝对定位加负 margin 骗、表格单元格 vertical-align 骗。等高一栏在表格布局里是天然属性，到了 float 时代反而要靠背景图在视觉上假装等高，CSS 改一行颜色就得重新切图。

元素顺序被绑定

浮动元素在源码里的顺序基本决定了显示顺序，想做”视觉上侧栏在左、源码里侧栏在后”以照顾 SEO 和可访问性，就得上负 margin 之类的手法，代价是代码可读性暴跌。

与 clear 的纠缠

浮动影响的不仅是父元素，还有后面所有不浮动的兄弟元素。clear: left 写在谁身上、清到哪一层、overflow: hidden 和 display: table 哪种清浮动方式副作用更小，都是必须逐案试出来的经验。更隐蔽的是，清浮动常常连带把外边距折叠一起改变，导致间距忽大忽小，只能靠反复调浏览器开发者工具去猜。

float 布局的坑如此深入人心，以至于后来所有的布局方案——Flexbox、Grid——都把”不塌陷、不等高要手动、顺序可调”写进了设计目标。

Position：脱离文档流的三种姿势

position 常被和 float 并列讨论，但它的定位其实不同：float 是排版系统的一部分，position 是坐标系统。CSS 2.1 给了四个值，分工很清楚。

static 是默认值，元素待在正常文档流里，top/left 一律无效。绝大多数元素都是它。

relative 让元素保持原位占位，但可以按 top/left 等属性相对自身偏移。它最常见的用途不是移动元素，而是给绝对定位的子元素当”定位上下文”：

absolute 让元素完全脱离文档流，相对最近一个 position 非 static 的祖先定位，找不到就相对初始包含块（通常是视口）。它是做浮层、角标、模态框的唯一选择，也是”元素被父级裁掉”这类问题的源头——因为绝对定位元素仍然受祖先 overflow 影响。

fixed 相对视口定位，滚动页面时纹丝不动，适合做吸顶导航和回到顶部按钮。在当年的移动端浏览器上，fixed 的支持相当糟糕，iOS Safari 在很长时间里对 position: fixed 的支持都算半残，这是移动端早期绕不开的坑。

position 的局限在于：它是一次性给出坐标，不参与文档流的自动分配。用它做整体布局，等于把每个元素的尺寸和位置都手写死，改一处动全身。所以它始终是布局的补充手段，而不是主力。

display: inline-block：被重新发现的排版模型

inline-block 在 CSS 2.1 里就有，本意是让元素”既能设宽高、又能像行内元素一样排在一行”。float 布局横行的那几年，它一直被忽视，直到有人发现可以用它做多栏布局，而且比 float 更符合直觉：

它相比 float 有几个明显优势：元素仍在文档流内，不会造成父元素塌陷；不需要 clearfix；源码顺序即显示顺序，没有让位问题。在当年做”导航条等距排列”这类需求时，它比 float 干净得多。

但它有一个极其烦人的缺陷：HTML 里行内元素之间的空白会被渲染成一个空格，多个 inline-block 之间会出现几像素的间隙。这个间隙在栅格系统里足以让布局错位。当年的解法包括把标签写成一行不留空白、给父元素设 font-size: 0 再在子元素里重置、用注释填充空白等，全都属于”能用但难看”的范畴。

另一个问题是基线对齐：默认按基线对齐，一行里只要有一个元素文字行高不同，整行就会参差不齐，必须显式写 vertical-align: top。

所以 inline-block 是一个”小需求很好用、大布局不够省心”的方案。它在按钮、标签、导航项这类小部件上非常好用，用它搭整页则要跟空白字符和基线较劲。

Flexbox：从草案到现代语法

现代语法速览

兼容现状与回退方案

2013 年 4 月这个时间点上，Flexbox 的真实处境是这样的。

IE10 支持的是 2011 年的中间语法，display: -ms-flexbox，属性名是 -ms-flex-align 之类，与现代语法不通用。IE9 及以下完全不支持，写 display: flex 会被直接忽略。

Chrome 21 起、Firefox 20 起支持现代语法，但 Android 4.x 内置的旧版浏览器和 iOS 6 之前的 Safari 只认 2009 年的 -webkit-box 语法。

还有一个容易忽略的差异：IE10 那一版语法里，-ms-flex 简写的第三个参数不是 flex-basis，而且 flex-basis 的初始值是 auto 而非 0，min-width 的默认值处理也与标准不同。因此即使给 IE10 挂了前缀，也常常出现”Chrome 里正常、IE10 里子元素被内容撑爆”的情况，需要在 IE10 分支里显式写 min-width: 0。

响应式布局与 Media Queries Level 3

布局方式的演进不只在”怎么排一行元素”，还在”怎么让同一套页面适配不同屏幕”。

2010 年 5 月，Ethan Marcotte 在 A List Apart 上发表了《Responsive Web Design》一文，系统提出响应式网页设计的概念。他当时给出的三个技术支柱是：流式网格（用百分比宽度替代固定宽度）、弹性图片（让图片不超出容器）、Media Queries（按设备特征应用不同样式）。这篇文章后来被扩展成同名书籍，成为移动互联网初期最重要的设计文献之一。

技术上真正让响应式落地的，是 Media Queries Level 3 在 2012 年 6 月成为 W3C 推荐标准。它让 CSS 第一次可以按视口宽度而非设备型号应用规则：

配合 <meta name="viewport" content="width=device-width, initial-scale=1">，网页才能在手机上按设备宽度渲染而不是缩成桌面版。

Media Queries 与流式布局解决了”宽度自适应”，但浮动布局做响应式依然痛苦：栏位一多就要写大量 float 与 clear，换行点稍复杂就失控。Flexbox 的 flex-wrap 和 flex-basis 恰好补上了这一环，让”一行放得下就横排、放不下就换行”变成属性配置。这也是 Flexbox 在 2012 年之后迅速流行的真正原因——它和响应式是同一波需求的两种解法。

断点该怎么设

响应式落地时最实际的问题是断点取多少。当年有两条路线：一条是按流行设备宽度设断点（320、480、768、1024），直观但很快过时；另一条是”内容驱动”，即当布局在小屏幕上开始挤压变形时再设断点。后者的思路更耐久，因为它不依赖设备清单。配合 min-width 写的移动优先样式，也比 max-width 的桌面优先写法更容易维护——先写单栏基线，再逐层加宽，避免大段覆盖。

弹性图片与流式单位

响应式三支柱里，弹性图片那条在当年要靠一行 CSS：img { max-width: 100%; height: auto; }。它解决的问题很直接——定宽图片在窄容器里会溢出并撑出横向滚动条。更细的做法是给图片外包一层按比例设定内边距的容器，用 padding-bottom 百分比模拟固定宽高比，再让图片绝对定位填满。这个技巧在 CSS 没有 aspect-ratio 的年代是唯一方案，今天看依然不过时。流式单位方面，除了百分比，当时也已经可以用 em 定义栅格，让间距随字号缩放，兼顾可访问性。

块级格式化上下文：被低估的机制

清浮动那一节里提到了”给父元素设 overflow: hidden 触发新的块级格式化上下文”，这个机制值得单独展开，因为它是理解浮动与清浮动的钥匙。

块级格式化上下文的英文是 block formatting context，简称 BFC。一个元素满足下列任一条件就会建立 BFC：根元素、float 不为 none、position 为 absolute 或 fixed、display 为 inline-block 或 table-cell、overflow 不为 visible。BFC 有三个对布局至关重要的特性：内部浮动子元素的高度会被计算进来、自身不与外部浮动元素重叠、外边距折叠不会跨出边界。

这正好解释了清浮动为什么有效：overflow: hidden 让父元素成为 BFC，于是浮动子元素的高度被纳入计算，塌陷消失。也解释了它的副作用：因为不与外部浮动重叠，右侧内容如果本来想绕到浮动元素旁边，现在会被整块挤下去；同时 overflow 非 visible 会裁掉溢出的下拉菜单。所以当年的经验法则变成了：只在不含浮层的容器上用 overflow 清浮动，否则还是用伪元素 clearfix。

到了 Flexbox 时代，BFC 依然在起作用。Flex 容器会为它的每一个 Flex 项建立独立的格式化上下文，因此 Flex 容器内部的浮动、外边距折叠都被隔离，不需要再手动清浮动。这是 Flexbox”开箱即整齐”的底层原因之一，也是它比浮动容易调试的根本所在。

多列布局：被跳过的中间路线

在 float 与 Flexbox 之间，还有一条常被忽略的路线：CSS Multi-column Layout。它在 CSS3 里很早就有了实现，column-count 和 column-gap 让文字像报纸一样自动分栏，IE10 与 Chrome、Firefox 的新版本在 2012 年前后都已支持。

它看起来很适合做正文分栏，但当年并没有成为主流布局手段。原因是它按内容高度自动断栏，栏位高度不可控，一旦其中一栏里插入了图片或标题，断点就会漂移；而且它只能做”内容等分栏”，做不了”侧栏加主栏”这种结构。所以它长期只被用在杂志式的文字排版上，没有参与页面骨架的竞争。

把它写进演进史的意义在于：CSS 的每条新能力都会先在最能发挥它的地方落地，而不是全面替代旧方案。inline-block 服务于小部件，多列服务于文字，float 服务于骨架，position 服务于浮层——这种分工一直延续到 Flexbox 出现。

为什么不是 Grid

读到这里可能有人会问：既然 Flexbox 是一维的，那二维的 Grid 呢？

答案是当时它还不存在。CSS Grid Layout 直到 2017 年前后才有相对一致的现代语法和浏览器实现。在 2013 年，IE10 的预览版本里有一个 -ms-grid 的实现，语法是 -ms-grid-columns/-ms-grid-rows 那套，与后来的标准完全不同，只此一家；其他浏览器一概没有。所以 2013 年谈二维布局，谈的仍是表格布局和嵌套浮动的老办法，Grid 只能作为一个远景中的名词存在。

这也是 Flexbox 在当时的定位：它不是布局的终点，而是”终于能优雅解决一维排列”的第一步。一维问题交给 Flexbox，二维问题在 Grid 到来之前继续用回退方案凑，这是那个年代最清醒的判断。

演进脉络与选型

把整段历史画成一张流程图，可以看到每一次迭代都在修正上一代的核心缺陷：

flowchart TD
  A[表格布局 1990s] --> B[浮动加清浮动 2000s]
  B --> C[position 与 inline-block]
  C --> D[Flexbox 现代语法 2012]
  D --> E[Media Queries L3 2012]
  D --> F[Grid 未来方案]

落到 2013 年的实际项目里，选型建议可以概括成几条。

结构骨架用 Flexbox 打底，float 兜底，靠特性检测切换，不要为 IE9 单独维护一整套布局代码。

小部件（按钮、标签、导航项）优先 inline-block，它简单、可预测、没有浮动副作用。

浮层、吸顶、下拉菜单用 position，这是它的本职，别的方案替代不了。

页面级响应式用 Media Queries 划分断点，配合流式宽度；具体到一行内多栏排列，交给 Flexbox 的 flex-wrap。

需要二维对齐的复杂页面（比如仪表盘、等分卡片墙），在 Grid 可用之前只能靠嵌套浮动或表格，接受它的笨重。

还有一条经常被忽视：布局方案的选择会影响团队协作。float 时代，改版要动的是整页结构，设计师和前端之间来回返工成本极高；Flexbox 时代，栏位宽窄交给属性调，沟通成本随之下降。所以从 float 迁移到 Flexbox，收益不只是代码量减少，更是把”布局参数”从结构里剥离成可调配置。

小结

CSS 布局的演进本质上是”把表现从结构里解放出来”的过程：表格布局把结构和表现绑死，float 松开了这层绑定却带来塌陷与让位，position 和 inline-block 各自补上一角但都不成体系，Flexbox 才第一次让容器真正拥有对子元素排列的指挥权。Flexbox 自己走过了 2009 草案、2011 重构、2012 年现代语法定稿三个阶段，2013 年的现实是语法并存、IE10 只认中间语法、IE9 及以下完全没有，因此渐进增强与特性检测是唯一稳妥的姿势。响应式设计的提出与 Media Queries Level 3 成为推荐标准，让”同一套内容适配多种屏幕”成为共识，也反过来加速了 Flexbox 的普及。理解这段历史的价值在于：每一种老方案的坑，都是新方案的设计动机，看清动机比记住语法更重要。
