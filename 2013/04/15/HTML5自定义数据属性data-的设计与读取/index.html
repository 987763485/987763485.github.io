HTML5 自定义数据属性 data-* 的设计与读取

本文属于《HTML 与 CSS》第 6/62 篇
上一篇系列目录下一篇

HTML5 给所有元素加了一条此前被禁止的能力：在标签上写任意以 data- 开头的自定义属性，把少量私有数据挂在 DOM 节点上。以前我们要么把这些数据塞进 class、rel 这类语义不符的属性里，要么靠隐藏的 <input> 或者 data 之类的非标准属性变通。本文从规范设计出发，讲清 data-* 是什么、dataset 接口怎么读、jQuery .data() 的自动转换与缓存陷阱在哪。

data-* 的设计意图

在 HTML4 时代，往元素上附加自定义信息只能借用已有属性：用 class 存状态、用 title 存提示、用 rel 存关系。做多了就会发现这些属性各有语义，硬塞数据会让文档难以维护，还会与样式选择器打架——比如把 class="item active" 当作状态标记，样式表就很难只按样式维度来写。

HTML5 的做法是开辟一个受控的命名空间：任何以 data- 开头、后面至少跟一个字符的属性名都是合法的自定义属性。规范明确它只用于存放与元素相关的私有数据，不承载任何表现或语义职责，页面作者可以随意定义属性名和内容。

命名的限制只有两条：不能包含大写字母，不能出现 data- 之后紧跟 xml 的形式（为避免与 XML 命名空间冲突）。除此之外，属性值只是一个字符串，规范不规定格式，作者自行约定是数字、JSON 片段还是布尔字面量。

顺带一提，当时社区里流行的 JSON 序列化片段——比如 <div data-config='{"theme":"dark","limit":20}'>——正是借助这个”值任意”的特性实现的。用 jQuery .data() 读出来直接就是对象，用 getAttribute 读则要自己 JSON.parse。这种用法在单页应用普及之前非常普遍，也埋下了后来 XSS 的隐患：如果值里出现了单引号又没有正确转义，整段 HTML 结构都会被破坏。服务端渲染时必须做属性值转义，这是使用 data-* 传结构化数据的第一纪律。

这个设计的价值在于”数据跟着节点走”。节点被克隆、移动、序列化时，数据一起走，不需要额外的映射表；服务端渲染时可以直接把数据写进 HTML，前端拿起来就能用。对当年的列表渲染、配置传递来说，这比维护一个 id 到数据 的字典自然得多。

读取方式之二：dataset 接口

HTML5 还为元素定义了一个专门读写 data-* 的接口：element.dataset。它是一个 DOMStringMap，把属性名从连字符风格转换成驼峰风格后作为键暴露出来。

需要特别说明的是，本文写作时 dataset 的支持范围并不完整：Chrome 与 Firefox 早已实现，IE 直到 10 才支持，IE9 及以下没有这个属性，直接访问会得到 undefined。所以在 2013 年写跨浏览器代码，dataset 只能是增强项，getAttribute 才是基线。

读取方式之三：jQuery .data()

jQuery 的 .data() 是当年项目里最常见的入口，因为它顺手做了三件 getAttribute 不做的事：统一读写接口、自动类型转换、跨元素的数据缓存。

自动类型转换

jQuery 在读取 data-* 时会把字符串按 JSON 规则尝试转换："1001" 变数字 1001，"true" 变布尔 true，"null" 变 null，看起来是 "{"a":1}" 的合法 JSON 会变成对象。这个特性很讨喜，写业务代码时省掉了大量 parseInt。

但它的判定是”尽量转，转不成功就保留字符串”。"012" 会被解析成 10（八进制），"1e3" 会变成 1000，而 "Tom" 保持字符串。更麻烦的是长数字串：超过一定位数的数字会被转成科学计数法或者精度丢失。如果属性里存的是订单号、身份证号这类”必须原样保留”的字符串，jQuery 的自动转换就是坑。稳妥做法是存的时候加个前缀，或者干脆用 .attr("data-order-no") 绕开转换。

缓存陷阱

.data() 最大的坑在于它把”标签属性”和”内部缓存”混在了一起。

jQuery 1.9 与 2.0 的行为是：第一次对某个元素调用 .data(key) 时，会去读 data-* 属性并做转换，然后把结果存进内部的数据缓存；之后再用 .data(key) 读，返回的是缓存值，不再回标签取。写 .data(key, value) 则只写缓存，标签上的属性纹丝不动。

这个例子在当年的论坛里被问过无数次。结论是：如果同一份数据可能被别的代码通过 attr 或原生 DOM 修改，就不要用 .data() 读它，改用 .attr("data-*") 保证拿到最新值；反之，如果数据是纯前端状态、不需要反映到标签上，用 .data() 反而更好，因为它不污染 DOM，也不会被 CSS 选择器误伤。

还有一层容易忽略的：.data() 读取时会一次性把所有 data-* 属性扫进缓存。所以哪怕你只 .data("id")，后续 attr("data-role", "x") 的改动也可能让 .data("role") 读到过期值。多来源写入的场景下，统一用一种访问方式才是安全的。

缓存还会带来另一个隐性成本：jQuery 的元素被移除时，绑在上面的 .data() 缓存不会自动清理，长时间高频增删节点的页面（比如长列表滚动加载）会累积内存。这是当年排查内存泄漏时的常规检查项，解决办法是手动调用 .removeData() 或者在移除节点前 .remove()。

与 dataset 的取舍

把三种方式放在一起比，取舍就清楚了。

方式 返回值类型 标签同步 兼容性（2013 年） 适用场景
getAttribute 字符串 是 全部 基线方案、要字面值
element.dataset 字符串 是 Chrome、Firefox、IE10 渐进增强、可读性
jQuery .data() 自动转换 写时不同步 全部 前端状态、便利优先

简单的判断法则：要”标签上是什么就读到什么”，用 getAttribute；代码跑在支持 dataset 的环境里且追求可读，用 dataset；要存纯前端临时状态、且团队都在用 jQuery，用 .data()。

小结

data-* 是 HTML5 为”把私有数据挂在 DOM 节点上”开辟的受控命名空间，好处是数据随节点走、可被服务端直接渲染、不占用既有语义属性。读取有三条路：getAttribute 最通用但只给字符串，element.dataset 语义最清晰但 IE10 才支持，jQuery .data() 最便利却带自动类型转换和缓存。2013 年的现实是 dataset 尚未覆盖 IE9，因此基线必须落在 getAttribute 上，dataset 作为增强。真正容易出问题的点集中在 .data()：缓存导致读了过期值、自动转换把长数字和编号弄丢精度、以及写 .data() 不同步标签。把这些边界想清楚，data-* 就是当年最轻量的前后端数据通道。
