首屏渲染优化手段汇总

首屏时间是从用户输入网址到第一屏内容可见的时长，它是用户对”这个站快不快”最直接的判断依据，也是当年 Google Page Speed 与 YSlow 两条规则体系共同关注的核心。这两年”关键渲染路径”这个概念逐渐普及，让前端第一次能把渲染过程拆解成可分析的阶段，而不是凭感觉猜。本文按”减少请求、提前渲染、压缩体积、善用缓存”四条线，把 2013 年主流且有效的手段汇总一遍。

关键渲染路径：先看清流程再优化

关键渲染路径指的是浏览器把 HTML、CSS、JavaScript 变成屏幕上像素所经过的步骤。大致可以分为：下载 HTML、解析 HTML 构建 DOM、下载并解析 CSS 构建 CSSOM、执行阻塞的 JavaScript、合并 DOM 与 CSSOM 生成渲染树、计算布局、绘制。

flowchart TD
  A[下载 HTML] --> B[解析 HTML 构建 DOM]
  B --> C[遇到 CSS 则下载并构建 CSSOM]
  C --> D[执行阻塞脚本]
  D --> E[生成渲染树]
  E --> F[计算布局]
  F --> G[绘制首屏]

理解这张图的价值在于：它解释了为什么某些改动有效，而另一些只是心理安慰。CSS 会阻塞渲染，因为渲染树的生成需要 CSSOM；放在头部的同步脚本会阻塞解析，因为它可能改写 DOM 与样式。所有首屏优化手段，本质上都是在缩短这条路径上的某一段。

还要注意一个常被误判的现象：HTML 解析完成并不等于首屏渲染完成。解析完只拿到了 DOM，还要等 CSSOM 就绪才能生成渲染树，之后才是布局与绘制。所以”文档加载完了但屏幕还是白的”通常意味着某个 CSS 还在下载，或者某个脚本卡住了执行。反过来，如果 CSS 已经就位、HTML 解析到首屏内容的位置，浏览器就可以增量绘制，用户先看到一部分——这正是把 CSS 放头部、脚本放底部能提前首屏的机理。

一个常用的观察指标是”首屏渲染完成前浏览器必须下载多少字节、发多少个请求”。Google Page Speed 里有一条经典建议：把关键 CSS 直接内联进 HTML 头部，让渲染不等样式表。这样做的代价是 HTML 体积增大、无法被缓存复用，需要按页面权衡。对于样式表很小、首屏紧迫的活动页，这个取舍往往是划算的；对于样式表庞大、依赖长期缓存的站点，则更适合走外链加缓存路线。

减少 HTTP 请求

浏览器对同一域名的并发请求数有限制，每个请求都有握手与往返延迟。减少请求数量是当年收益最直接、争议最少的手段。需要说明的是，这一条在 HTTP/1.1 时代成立；在连接复用更完善的新协议普及之后，合并的收益会下降，甚至拆分成更多小文件反而更利于缓存——但在本文写作的 2013 年，合并仍是第一优先。

合并文件

把多个 CSS 合成一个、多个 JavaScript 合成一个，是最传统的做法。当年用 Ant、Grunt 或简单的 Cat 脚本在构建时合并，线上只留一个 all.css 和一个 all.js。收益来自两方面：请求数下降，重复的请求头与连接开销也下降。

代价是缓存粒度变粗：改一行 JavaScript 就要让整个文件失效。当年的折中做法是”基础库单独一份、业务代码一份”，基础库变动少、长期缓存，业务代码频繁更新但体积小。

还有一层收益容易被忽略：合并后重复的请求头与连接握手被消除。一个请求的往返里，真正传输文件的时间常常只占一小部分，固定开销才是小文件多的站点的瓶颈。所以合并的收益在文件越小、数量越多时越明显；反过来，如果两个文件都很大且缓存策略不同，硬合并反而拖累首次访问之后的更新效率。

CSS Sprite

把多个小图标拼成一张大图，用 background-position 定位。一个页面有二十个社交图标时，二十个请求变成一个大图加若干定位。它的维护成本不低：加一个图标要重排整张图，所有 background-position 都要跟着改。所以它只适合数量多、尺寸小、长期不动的图标集合。

用 CSS 代替图片

能用一个圆角矩形加渐变做出来的按钮，就不要切图。CSS3 的 border-radius、box-shadow、linear-gradient 在 2012 年之后的主流浏览器里已经可用，加前缀即可覆盖大部分环境。这样做既省请求，又能让按钮跟随字号缩放、跟随主题变色。

图标字体与内联小图

对于纯色图标，当年已经开始流行把图标做成字体文件，一次下载全部图标，还能用 color 控制颜色、用 font-size 控制大小。另一条路线是把极小的图片转成 Base64 直接写进 CSS，省掉请求，代价是体积增大约三分之一且无法单独缓存。这两条路线都要按场景权衡，不是所有小图都值得内联。

控制渲染阻塞与解析阻塞

这一节的所有手段都围绕一个目标：让浏览器尽早开始绘制，同时不让脚本拖住解析。它们之间往往有冲突——比如脚本放底部会让依赖脚本的交互变晚，async 会让执行顺序不可控——所以每一条都要结合实际页面结构取舍，而不是照单全收。

CSS 放头部

样式表必须尽早下载，因为渲染树的生成依赖 CSSOM。把 <link> 放在 <head> 里，浏览器才能一边解析 HTML 一边把 CSS 拉下来，拿到后立刻参与渲染。如果把 CSS 挪到页面底部，用户会先看到无样式的裸页面再”闪”一下变样，即白屏或内容跳变。这是硬规则，没有取舍空间。

避免 @import

@import 让浏览器在解析到该语句时才发现还有一份 CSS 要下载，形成串行链路。在样式表顶部写 @import url("a.css")，等价于让 a.css 的下载排在本文件剩余部分之后，白白多出一个往返。合并成一次 <link> 或者用一个构建工具把 @import 展开，是当年最直接的修法。

脚本放底部

同步脚本会阻塞 HTML 解析：解析器遇到 <script src> 就必须停下来，下载并执行完才继续。把脚本挪到 </body> 之前，可以让 HTML 与 CSS 先解析完、先渲染出来，用户更早看到内容。

但底部脚本意味着依赖它的交互要等到最后才可用。更细的做法是拆分：渲染首屏必需的少量代码放头部内联或紧跟样式之后，其余全部后置。

defer 与 async

HTML5 给 <script> 加了两个属性，让脚本下载不阻塞解析。

defer 表示”文档解析完成后、DOMContentLoaded 之前按顺序执行”，多个 defer 脚本之间保持书写顺序，适合有依赖关系的业务代码。

async 表示”下载完立即执行，不看顺序”，适合互不依赖的独立脚本，比如统计代码。

这两个属性在 IE9 及以下对动态插入的脚本支持不完整，但写在标签上时 IE 也能识别 defer，所以当年是”渐进增强写起来、老浏览器降级为同步”的稳妥方案。

减少重排与重绘

首屏绘制完成之前的每次重排都会拉长可见时间。重排的典型诱因是逐个读取布局属性又修改样式，比如在循环里读 offsetHeight 再改 style.width，浏览器被迫反复计算布局。

批量修改样式还有一条更彻底的路子：先把节点从文档流中取出，改完再插回去，或者用 documentFragment 拼装完整片段后一次性插入。当年没有 requestAnimationFrame 之外的节流手段，但”读写分离”这条规则在任何时代都成立。

谨慎使用 CSS 表达式

IE 特有的 expression() 可以在 CSS 里跑 JavaScript，比如 width: expression(document.body.clientWidth > 800 ? "800px" : "auto")。它会在每次样式重算时都执行一遍，鼠标移动、滚动都可能触发， CPU 直接拉满。这是明确的负面清单项，能用 Media Queries 替代就一定要替代。

压缩与减小体积

请求数降下来之后，下一步是让每个请求传更少的字节。这一节的手段几乎都是零风险的：压缩与裁剪不会改变行为，只改变传输量。唯一切记的是”先缩尺寸再压缩”，顺序颠倒会让图片产物体积明显偏大。

Gzip 压缩

文本资源（HTML、CSS、JavaScript、JSON）开启 Gzip 通常能压掉百分之六十到八十的体积。服务端在响应里带上 Content-Encoding: gzip，浏览器发送 Accept-Encoding: gzip 即可协商。这是零成本的收益，唯一要注意的是别对小文件和已经压缩过的格式（图片、字体）重复压缩，那样只会浪费 CPU。

代码压缩

去掉注释、空白、换行，缩短局部变量名，是当年构建流程的标准一步。压缩后的代码不可读，所以源码与产物必须分离，线上只部署产物，同时保留 source map 之前时代的”未压缩版本仅供调试”的约定。

图片优化

首屏图片往往是体积大头。当年的手段包括：按展示尺寸输出，不要把 2000 像素宽的图缩到 200 像素显示；选择正确的格式，照片用 JPEG、纯色图标用 PNG8 或 GIF、需要透明用 PNG24；调低 JPEG 质量到肉眼难辨的档位；能用 CSS 效果替代的坚决不用图片。

还有一个常被漏掉的点：图片的字节数不只看分辨率，还看内容复杂度。一张纯色渐变的 JPEG 可能比同尺寸的照片小十倍，导出时用工具的”针对 web 优化”选项、或者先缩尺寸再压缩，顺序颠倒会让产物体积明显偏大。当年的工作流是在构建阶段跑一遍无损压缩工具，把冗余的元数据剥掉，收益通常在百分之十到百分之三十。

还有一条容易被忽视的：给图片写死 width 与 height。浏览器在拿到尺寸后可以提前占位，避免图片加载完成后触发重排，重排会连带重绘，直接拖慢首屏。

字体与图标

自定义字体文件往往几百 KB，且会阻塞渲染——浏览器在字体下载完成前可能用占位字形显示文字，甚至延迟绘制。当年的做法是只打包实际用到的字形子集，把中文字体从几 MB 裁到几十 KB；或者对首屏标题用系统字体，正文再换自定义字体。图标字体同样只保留用到的图标，服务端按需裁剪。

DNS 预解析与连接优化

页面引用的静态资源如果分布在多个域名下，DNS 解析与 TCP 连接会成为可见的延迟。提前告诉浏览器”待会儿要去这些域名”，让它空闲时就把解析做掉，是最省事的优化。

2013 年前后这条属性已在新版 Chrome 与 Firefox 中可用。它只解决 DNS 一环，不建立连接，但 DNS 在某些网络下要几百毫秒，提前做掉依然划算。

配套的思路是减少域名数量。静态资源分域名是为了突破并发限制，但域名越多，DNS 与连接成本越高。当年的经验做法是控制在两到三个域名：一个主站域名加一个 CDN 域名，既保留一定并行度，又不至于让解析成本失控。

懒加载与首屏无关内容

首屏优化有一条隐蔽的思路：用户看不到的东西，不要抢首屏的资源。

首屏以下的图片用懒加载，滚动到接近视口时再赋值 src。最简做法是先用一个占位图或者把地址存在 data-* 属性里，监听滚动或使用 IntersectionObserver 出现之前的 getBoundingClientRect 判断，进入视口再替换。

getBoundingClientRect 在每次滚动时会对每张图片强制布局，图片多时反而卡。当年更稳妥的做法是用节流函数限制触发频率，或者只在滚动停止后检测一次。

同样的思路适用于第三方脚本：社交分享按钮、评论框、统计代码都不影响首屏内容，应该延后加载，不要放在头部与样式表抢带宽。

还有一类常被忽视的”首屏无关内容”是首屏之下的模块初始化。一个长页面里的轮播、折叠面板、日期控件，如果都在 DOMContentLoaded 时统一初始化，会把主线程占满，把首屏绘制推迟。按需初始化，或者用 setTimeout 把这些初始化任务推到当前任务之后，能让浏览器先喘口气。

服务端渲染与骨架

在单页应用普及之前，服务端直接吐完整 HTML 是默认做法，首屏内容随文档一起到达，不需要等 JavaScript 执行。当年真正的问题出在”先吐一个空壳、再由 JavaScript 拉数据渲染”的模式上：用户要先看白屏，再等接口，再看内容，三段延迟叠加。

对应的优化是让服务端至少把首屏的静态部分吐出来，动态数据用接口补齐；或者给一个轻量骨架，先占住布局。这与后来”骨架屏”的思路一致，但在 2013 年更多是以服务端模板加局部刷新的形式存在。

CDN 与网络路径

把静态资源部署到 CDN，让用户从地理上更近的边缘节点取文件，直接降低往返延迟。CDN 同时能分担源站压力，在活动流量突增时尤其明显。

使用 CDN 时有几个细节会影响首屏。第一，确认边缘节点覆盖了目标用户的主要地域，否则只是多绕一跳。第二，静态资源要带长期缓存头，让 CDN 与浏览器都能长时间复用。第三，避免 CDN 故障时整站样式全丢，可以给 <link> 加 onerror 回退到主站域名，虽然这种做法当年并不普遍。

还有一个反向的教训：不要把首屏关键 CSS 放在 CDN 上却不做缓存。每次访问都回源验证，反而比放到主站更慢。CDN 的正确用法是配合不可变的长缓存，而不是当成一个加速代理随便挂。

连接数的取舍

浏览器对每个域名保留若干条连接，加载大量资源时会排队。把资源分散到多个域名可以提高并行度，这是拆分 CDN 域名的初衷。但每多一个域名就多一次 DNS 解析与 TCP 握手，在移动网络下这两项加起来可能上百毫秒。所以域名数量的合理区间很小：通常主站一个、静态资源一个，最多再加一个图片域名。超过三个域名，解析成本就会开始吃掉并行收益。

缓存策略

缓存是”第二次访问”的首屏优化，但对回访用户来说收益极大。

强缓存用 Expires 与 Cache-Control: max-age 告诉浏览器”在到期前不要问我，直接用本地副本”。协商缓存用 Last-Modified 加 If-Modified-Since、ETag 加 If-None-Match，让浏览器带本地版本信息来问一句”有更新吗”，服务端返回 304 就说明没变，只传一个空响应。

当年的经典组合是：带指纹的静态资源（比如 app.3f2a1b.js）设一年强缓存，因为文件名变了就是新内容，不存在更新问题；HTML 入口文件设协商缓存或不缓存，保证用户总能拿到最新的资源引用。

这个组合解决了”长缓存”与”及时更新”的矛盾，是构建工具加入文件指纹之后的标配做法。

还有一条与缓存直接相关却常被忽略：Service Worker 式的离线缓存当时还不存在，所以”首屏不依赖网络”只能靠 AppCache 或者浏览器自身的 HTTP 缓存。AppCache 的 manifest 机制在 2013 年已经可用，但它行为难以预测，一个清单文件的笔误就可能让站点长时间停留在旧版本，多数团队只在小范围试用。稳妥的离线策略仍然是把入口 HTML 与关键 CSS 交给 HTTP 缓存管理，让回访时根本不发请求。

度量与验证

不测量就不知道优化是否有效。2013 年可用的度量手段主要有三类。

第一类是浏览器自带的开发者工具。Chrome DevTools 的 Network 面板能看每个请求的时序瀑布图，分辨时间是花在 DNS、连接、等待还是下载上；Timeline 面板能看到脚本执行、布局、绘制的耗时。这是定位具体瓶颈最直接的工具。

第二类是 Navigation Timing API。W3C 定稿的这个接口把页面加载的关键时间点暴露给 JavaScript，performance.timing 里的 navigationStart、domContentLoadedEventEnd 等字段可以拿来计算真实用户的加载耗时。

把它上报到日志系统，就能统计真实用户的首屏分布，而不是只测自己电脑。注意 performance.timing 只在页面加载完成后才有完整值，且各浏览器字段的实现略有差异。

第三类是规则检查工具。Google Page Speed 与 YSlow 都会扫描页面，按请求数、压缩、缓存、脚本位置等维度给分。它们的分数不能直接等同于用户体验，但很适合当作上线前的检查清单，防止漏掉某条基础规则。

实际项目里更有效的做法是把三类度量组合起来：先用 DevTools 的瀑布图定位是网络问题还是渲染问题，再用 Navigation Timing 在真实用户上确认优化是否生效，最后用 Page Speed 的清单兜底。三者回答的是不同问题——瀑布图回答”时间花在哪”，真实数据回答”用户到底多快”，清单回答”有没有漏掉常识”。

常见误区

最后列几个当年常见但收益甚微的做法，避免把精力花错地方。

把脚本加 defer 却指望它一定先于首屏执行。defer 的语义是文档解析完之后才跑，依赖它的功能本来就该延后。如果一定要它早执行，应该评估能否把逻辑拆成”渲染必需的一小段内联在头部，其余延后”。

压缩已经压缩过的文件。JPEG 再 Gzip 基本没有收益，反而浪费服务端 CPU。压缩前先判断内容类型，文本类才走 Gzip。

盲目拆分域名。多一个域名多一次 DNS，收益与成本要一起算。只有在单域名的并发确实成为瓶颈、且每个域名的资源量足够大时才值得拆。

只测自己电脑。本地网络好、有缓存，测出来的数字和真实用户相差很远，必须用带查询串的干净请求复测，或者直接看真实用户的统计数据。

追求工具分数而忽略用户感知。首屏时间达标了，但关键按钮要点两下才有反应，体验依然差。优化的目标始终是用户可感知的时间点，不是任何一个工具的读数。

还有一个方向性误区：把首屏优化等同于”把所有资源都提前加载”。预加载一切只会让关键路径更拥挤，判断标准永远是”首屏渲染是否需要它”，不需要的一律后置。

小结

首屏优化的主线是缩短关键渲染路径：减少请求数量，让 CSS 尽早到位、脚本尽量后置，压缩一切可压缩的文本，用 DNS 预解析与 CDN 缩短网络路径，再靠懒加载把首屏无关内容挡在关键路径之外，最后用缓存让回访用户几乎瞬间看到内容。这些手段大多不需要改架构，靠构建流程与模板调整就能落地，但每一条都应该配合度量来验证：Chrome DevTools 看瀑布图、Navigation Timing 收集真实耗时、Page Speed 与 YSlow 做上线前检查。2013 年这套组合已经能覆盖绝大多数场景，真正难的不是知道手段，而是在项目约束下选对优先级。
