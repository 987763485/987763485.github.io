Hybrid App 与 WebView 交互基础

最近在给一个老项目做 Hybrid 改造，WebView 里的白屏、点击迟钝、键盘弹起时页面回不去，一个个坑踩下来，才发现自己过去只是”会用”WebView，并没有真正理解它。本文把这些零散的经验整理成文，从加载方式、JS 与 Native 通信、首屏性能一直讲到输入法与视口，讲清楚 2013 年这个时间点上 Hybrid 页面应该怎么调优。文中的结论来自 Android 4.x 的 WebKit WebView 与 iOS 5/6 的 UIWebView，基本覆盖当时绝大多数需要适配的机型。

Hybrid 与 WebView 的加载方式

所谓 Hybrid，就是原生应用提供一个 WebView 容器，把 H5 页面装进去展示。原生负责壳、权限、推送、支付这些系统能力，H5 负责业务界面，两边各干自己擅长的事。Android 4.x 的 android.webkit.WebView 内核是 WebKit，iOS 5/6 上则是 UIWebView，WAP 时代那种自带内核的第三方浏览器不算，能自己控制的基本就是这两家。PhoneGap 在 2009 年就诞生了，2011 年捐给 Apache 之后改名 Cordova，但它解决的只是”打包和插件”，WebView 里页面该怎么跑，还得自己琢磨。

页面的来源有三种，调优手段完全不同：

  • 远程页面：webView.loadUrl("http://...")。好处是发版即时，坏处是完全依赖网络，弱网下白屏时间长，而且每次都要走 DNS、握手、下载。
  • 本地页面：放在 assets 或沙盒里，用 file:///android_asset/index.html 加载。秒开，不依赖网络，但数据得靠 XHR 或桥接口拉。
  • 本地加远程混合：框架、公共样式、首屏结构放在本地，数据接口走网络，图片按需下载。这是当时性价比最高的方案，也是本文最推荐的一种。

另一个常被忽略的点是 WebView 本身的初始化成本。在 Android 上，new WebView() 以及首次 loadUrl 时才会真正创建内核和渲染进程，冷启动时这一步可能要几百毫秒。实践中的做法是进应用时就预先创建好一个 WebView 实例并加载一个空白页”热身”，等用户真正点进 H5 页面时直接复用，首屏时间能省下一截。

iframe 桥

把 iframe 的 src 指向 about:blank 或一个本地空页面，再通过修改 location.hash、window.name 传递数据。window.name 能存的字符量大，而且跨文档保留，是当时跨域传数据的常用技巧。缺点是写起来啰嗦，调试也不方便，一般只在没有更好选择时使用。

白屏与首屏时间

白屏是 Hybrid 被吐槽最多的问题，但原因往往不在 WebView，而在页面自己。常见的有四类：

  • 脚本报错。一个未定义变量让整个初始化函数中断，页面停留在空白状态。
  • CSS 阻塞渲染。<head> 里放了一个慢速的远程样式表，整个首屏被卡住。
  • 远端资源不可达。字体、首屏大图放在 CDN 上，弱网下直接拉不到。
  • 缓存策略不当。该缓存的没缓存，每次冷启动都重新下载一遍。

对应的调优手段也很直接：首屏结构内联在 HTML 里，首屏样式写成 <style> 直接内联，脚本放到页面底部并加 defer 式的顺序控制，小图标转 base64，非首屏图片延迟加载。同时加一个 loading 占位和超时降级页，请求超过 5 秒就显示”网络不给力，点击重试”，不要让用户盯着一块白屏发呆。

另外，Hybrid 页面一定要减少重排。低端 Android 机上，一次涉及全页布局的样式改动可能耗时几十毫秒，连续几次就能感到明显卡顿。批量改样式时先用字符串拼好再一次性赋值，或者先把元素移出文档流，改完再放回去。

视口、300ms 点击延迟与滚动惯性

移动端 H5 有三个经典问题，2013 年一个都没解决好。

视口必须显式声明，否则 WebView 会按 980px 的默认宽度渲染再整体缩放，字小得没法看：

user-scalable=no 能禁止双击缩放，但也会带来无障碍方面的争议，当时为了体验普遍都加上，现在再回头看这是个不太友好的选择。

300ms 点击延迟源于浏览器要判断用户是否是双击缩放。click 事件在触屏上总是慢半拍，点下去没反应，用户就会连续点，误触率飙升。当时的做法有几种：用 touchend 加自定义 tap 事件模拟点击；或者引入 FastClick 这类库，在 touchstart 时记录坐标，在 touchend 里阻止默认的 click 并手动 dispatchEvent。Zepto 也内置了 tap 事件，但它依赖 Zepto 自己的事件实现，与 jQuery 的习惯不完全一致。

滚动惯性要加 -webkit-overflow-scrolling: touch，否则 iOS 上自定义滚动区域是”一帧一帧”跳的，没有物理减速感。但这个属性在 iOS 5/6 上有个著名副作用：滚动会创建硬件合成层，层级一多就可能导致输入框失焦、页面闪烁，甚至 position: fixed 的元素跟着滚动。position: fixed 在 WebView 里本身就是重灾区，iOS 尤其明显，底部标签栏在键盘弹起时会错位。规避办法是底部栏改用 absolute 定位并手动控制 scrollTop，或者在键盘事件里重新计算位置。

输入法与键盘

键盘问题在 Hybrid 里比在纯 H5 里更麻烦，因为外层还有原生容器。最常见的坑有三个：

  • focus 到输入框时，WebView 不会自动把键盘弹起，需要 Native 调用 showSoftInput，或者让页面在 touchstart 时先 blur() 再 focus() 触发一次。
  • 键盘弹起后 resize 事件不一定触发，页面高度没有变化，底部按钮被键盘盖住。iOS 上要监听 orientationchange 与 resize 双事件，并配合 window.scrollTo(0, 0) 归位。
  • 键盘收起后页面停留在半空中，回不到顶部。收尾时手动 window.scrollTo(0, 0)，或者在 blur 里做一次延迟复位，是比较通用的补救。

Android 上还要注意 setSoftInputMode。如果设为 adjustResize，WebView 会跟随键盘压缩，布局会重排；设为 adjustPan 则整体平移，输入框可能被顶出可视区。Hybrid 页面一般用 adjustResize 再配合页面自己的滚动处理，行为更可控。

小结

WebView 的坑，八成不在技术方案，而在对容器特性的理解不足。加载方式上，本地加远程的混合方案在首屏速度和发版灵活度之间取得了最好的平衡；通信上，scheme 拦截最通用，注入对象最方便但要注意 Android 4.2 之前的安全问题。性能调优的核心是首屏要快、重排要少、异常要有兜底，白屏一定要有超时降级而不是裸奔。视口、300ms 延迟、滚动惯性和键盘这四类问题在 2013 年都没有银弹，只能针对 iOS 与 Android 分别打补丁。把这些零碎的补丁沉淀成项目里的公共层，才是 Hybrid 改造真正的产出。
