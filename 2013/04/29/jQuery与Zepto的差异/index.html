jQuery 与 Zepto 的差异

项目里同时用着 jQuery 和 Zepto 已经半年了：PC 端管理后台走 jQuery，移动端 H5 为了体积走 Zepto。中间因为”同一个页面里两套 API 看起来一样、跑起来不一样”摔过几次跟头，最惨的一次是动画回调在部分 Android 机上不执行，整页交互假死。本文把这些差异按模块梳理一遍，作为一次复盘，也方便后面的人少走弯路。需要说明的是，结论基于 jQuery 1.9/2.0 与 Zepto 1.x，后续版本的行为可能变化。

定位与体积差异

jQuery 1.9 压缩后约 32 KB，2.0 去掉了 IE 6/7/8 的兼容代码，压缩后约 29 KB，但它依然是一个功能完整的库，选择器、动画、事件、AJAX、工具方法一应俱全。Zepto 的定位从一开始就是”移动端的精简 jQuery”，核心压缩后只有 24 KB 左右，而且默认构建只包含核心模块，动画、AJAX、touch、data 这些都要按需引入。

这个差异带来一个直接的工程选择：PC 站点无脑用 jQuery，别为省几 KB 折腾；移动端如果只是简单的 DOM 操作和事件，Zepto 很合适；一旦用到了复杂动画、大量表单处理或者依赖插件生态，还是要认真评估。Zepto 的插件生态和 jQuery 完全不能比，2013 年这个时候很多 jQuery 插件改一改选择器部分能跑在 Zepto 上，但涉及动画内部实现的基本没戏。

选择器引擎的差异

这是最容易踩坑的地方。jQuery 1.9 用的还是自研的 Sizzle 引擎，对 CSS 选择器的支持非常完整，而且做了大量兼容处理。Zepto 的选择器直接复用浏览器原生的 querySelectorAll，好处是实现简洁、性能在支持该方法的浏览器上更快，坏处是选择器能力完全取决于宿主浏览器。

2013 年主流的移动浏览器对 querySelectorAll 的支持已经不错，所以 :first-child、[data-x=y] 这类常见选择器都能用。但以下几个 jQuery 里能写的写法，在 Zepto 上会直接抛异常或者返回空集：

  • :visible、:hidden。Zepto 不实现，jQuery 里也是用样式计算模拟的，性能并不好。
  • 位置伪类如 :first、:eq(2)、:gt(0)。这些是 jQuery 的扩展语法，不是标准 CSS。
  • 部分属性选择器的复杂组合，以及 :contains(text)。

事件系统的差异

两者都支持事件的直接绑定与委托，.on() 的签名也基本一致，这部分代码迁移成本最低。真正的差异在自定义手势和事件触发上。

Zepto 1.0 重构过事件模块，引入了 touch 模块提供 tap、singleTap、doubleTap、longTap、swipe 等手势。但 tap 的实现方式是：在 touchend 时判断滑动距离是否超过阈值，不超过就触发，并用一个约 250ms 到 300ms 的定时器来区分单击与双击。也就是说，Zepto 的 tap 本身是有延迟的，并没有比原生 click 快多少，它的价值在于统一了接口和消除了部分 300ms 延迟带来的误触。

jQuery 侧要自己处理移动事件，通常的写法是同时监听 touchstart 与 touchend 记录坐标和时间差，自己判断手势类型。两套代码并存时，建议把事件绑定统一封装一层，内部判断当前环境走哪套实现，不要让业务代码直接感知。

还有一个容易忽略的细节：trigger() 的行为。jQuery 的 trigger('tap') 会执行默认行为并冒泡，Zepto 对自定义事件的模拟并不完整，某些情况下需要手动 dispatchEvent。写组件时尽量用原生事件驱动，减少对自定义事件 trigger 的依赖。

动画实现的差异

jQuery 的动画基于一个定时器队列，animate() 会把属性变化分解成多帧插值，支持 duration、easing、step 回调、queue、stop()、delay() 等一整套控制。Zepto 的动画模块则是把参数转成 CSS transition，交给浏览器的合成线程去做，CPU 占用更低，在移动端确实更流畅。

代价是能力不对等：

  • Zepto 不支持 easing 自定义，只有 ease、linear 等浏览器内置曲线；jQuery 只有 swing 和 linear，但可以通过插件扩展。
  • Zepto 没有 step 回调，无法在每一帧里拿到中间值做同步计算，比如边移动边高亮当前卡片这类需求就实现不了。
  • Zepto 的 stop() 语义与 jQuery 不同，停止时的位置可能落在 transition 的任意帧，视觉上会有跳变。
  • 队列管理粗糙，多个 animate() 连续调用时，jQuery 有明确的 fx 队列，Zepto 基本是后写的覆盖前一个。

我踩的那个坑就在这里：一个下拉刷新动画用了 step 回调更新提示文字，在 Zepto 上 step 直接不存在，文字永远停在初始值，看起来就是”动画假死”。最后改成在 transitionend 里分阶段更新，才绕过去。

尺寸计算的差异

jQuery 会分别处理 width/height、innerWidth/innerHeight、outerWidth/outerHeight，并且对 display: none 的元素有特殊处理——它会临时把元素显示出来测量完再隐藏回去，所以拿到的数值是可用的，代价是触发重排。

Zepto 的实现简单得多，基本就是读 getBoundingClientRect() 或计算后的样式。对隐藏元素，Zepto 返回的结果没有保证，display: none 的元素量出来是 0。这在做轮播图、九宫格这类需要提前测量尺寸的逻辑里是个大坑，jQuery 迁移过来的代码很可能行为不一致。

还有一个实际差异：Zepto 的 offset() 与 position() 在 iOS 上受 -webkit-overflow-scrolling: touch 滚动容器影响，滚动中的元素取到的坐标可能滞后一帧。如果要做吸顶、吸附这类依赖精确坐标的效果，需要在滚动事件里节流读取，并且避免在 transition 进行中测量。

其他常见差异

剩下这些点单独看都不致命，合起来却能让人debug到半夜：

  • $.Deferred：Zepto 1.x 早期版本没有，或者实现不完整，依赖 $.when() 的代码需要改造。后来 Zepto 加入了基于 callbacks 的精简版，但与 jQuery 的接口仍有出入。
  • data() 的存储：jQuery 内部维护一个 expando 缓存，能存任意对象；Zepto 早期版本是把值转成字符串写进 data-* 属性，存对象会变成 [object Object]。
  • $.ajax：Zepto 的 data 模块提供了一个可用但简化的实现，beforeSend、statusCode、jsonp 的回调参数细节与 jQuery 有差别，跨域时尤其要注意。
  • 动画队列之外，fadeIn()、slideUp() 这类快捷方法在 Zepto 里是别名式的简化实现，duration 参数语义略有不同。
  • $.browser 在 jQuery 1.9 中已被移除，两端都不要再用，统一改成特性检测。

小结

jQuery 与 Zepto 的 API 表面相似度很高，这让迁移看起来只是一次替换，但底层实现思路完全不同：jQuery 是自建引擎加兼容层，Zepto 是尽量复用浏览器原生能力加精简封装。差异集中在选择器扩展语法、自定义手势、动画能力、尺寸测量四个方面，其中动画和尺寸最容易造成难以定位的问题。实践中不要把两套库混在同一页面里做同一件事，公共层按环境分发，业务代码只面对统一封装。选型的判断标准也很简单：PC 和复杂交互用 jQuery，移动端简单操作用 Zepto，一旦需求超出 Zepto 的能力边界就果断换回 jQuery，不要为了省几 KB 把项目拖进坑里。
