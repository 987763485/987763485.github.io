JavaScript 事件循环机制解析

本博客之前那篇《JavaScript 单线程与异步编程模型》讲的是动因与全貌：为什么 JavaScript 选择了单线程，以及异步模型如何让浏览器在等待中不卡死。本文接着往下钻一层，专门讲事件循环（event loop）本身的机制——队列怎么排、任务怎么取、微任务在哪一刻被清空、不同宿主环境的循环有什么差异。这些细节决定了你写出的异步代码到底按什么顺序执行，也解释了那些看起来违反直觉的输出结果。

为什么要抠这个机制？因为异步代码的 bug 有个共同特征：在单机上偶发，在低端设备上必现，在别人的机器上无法复现。它们的根源往往不是逻辑写错，而是作者对执行顺序的假设与真实顺序不一致。事件循环是这套顺序的唯一裁决者，读懂了它，这类问题就从”玄学”变成”可推演”。

调用栈与执行上下文栈

JavaScript 的执行模型建立在两个结构上：执行上下文（execution context）与调用栈（call stack）。

执行上下文是代码运行时的环境记录。按 ECMA-262 第五版的定义，每当进入一段可执行代码，就会创建一个执行上下文，其中包含变量对象（variable object，函数里对应活动对象）、作用域链（scope chain）与 this 的值。全局代码创建全局上下文，每次函数调用创建一个函数上下文，eval 则创建 eval 上下文。这些上下文不是散乱存在的，它们按创建顺序压入一个栈——这个栈就是调用栈，也叫执行上下文栈。

flowchart TD
  A[进入全局代码 压入全局上下文] --> B[调用 foo 压入 foo 上下文]
  B --> C[foo 中调用 bar 压入 bar 上下文]
  C --> D[bar 执行完 出栈]
  D --> E[foo 继续执行]
  E --> F[foo 执行完 出栈]
  F --> G[全局代码结束]

单线程的含义就在这里：整个进程只有一个调用栈，一次只能做一件事。栈顶的上下文没执行完，下面的都得等。这解释了为什么一个死循环会让页面失去响应——定时器、点击事件、网络回调全部排在后面，没人能进栈。

调用栈还有一层与异步的关系：栈空是事件循环推进的前提。同步代码全部执行完、栈被清空之后，事件循环才有机会从队列里取下一个任务。所以”异步回调一定晚于当前同步代码”不是巧合，而是机制决定的必然。

还有两个与栈有关的细节值得补充。其一是栈的深度是有限的，过深的递归会抛 RangeError: Maximum call stack size exceeded。各引擎的上限不固定，2013 年 Chrome 里大致在一万帧上下。这也是 Node 社区用 process.nextTick 或 setImmediate 拆解深递归的原因——把递归改成每轮让出栈再继续，深度就不再受限制。其二是闭包与栈的关系常被误解：函数执行上下文出栈后，它的变量对象如果还被闭包引用，就不会被释放。所谓”内存泄漏”的常见形态之一，就是无意中把大量数据通过闭包留在了已经”结束”的函数作用域里。

宿主环境与事件循环的分工

一个常见的误解是”事件循环是 JavaScript 的一部分”。实际上不是。ECMA-262 只定义了语言：语法、类型、对象、以及执行上下文如何创建与销毁。它完全没有规定任务队列、定时器、事件监听这些概念——这些属于宿主环境。

浏览器是宿主，Node.js 也是宿主，它们各自实现自己的事件循环。这带来一个重要的实践结论：同一段异步代码，在浏览器与 Node 里的执行顺序可能不同，因为两个宿主排队规则不一样。讨论”事件循环”时，必须先说清是在哪个宿主里。

浏览器的事件循环遵循 WHATWG HTML 标准定义的模型。这个模型在 2010 年之后逐步被各浏览器统一，HTML5 规范把”事件循环”写成了实现必须遵循的章节。Node.js 则不遵循 HTML 的循环，它用 libuv 库，有自己的一套阶段划分。本文分别讲这两者，先讲浏览器，因为它是大多数人接触事件循环的第一现场。

任务队列与微任务的引入

浏览器的事件循环围绕一个任务队列（task queue，也叫 macrotask queue）运转。任务就是一段待执行的代码，常见来源包括：定时器到期、用户交互事件、网络请求完成、postMessage 投递的消息、MutationObserver 的回调等。每来一个任务，就排到队尾。

事件循环的基本形态是一个死循环：取队首任务，执行它，执行期间可能产生新任务（排到队尾），当前任务执行完、调用栈清空后，进入下一轮迭代。

微任务（microtask）概念的引入要晚一些。在 2013 年这个时间点，规范层面还没有 microtask 队列——ES6 草案里 Promise 的微任务语义还在讨论中，浏览器也没有实现它。当时最接近微任务的现实技术是 MutationObserver：它把回调延迟到当前任务结束后、渲染之前的一个统一时机批量触发，而不是同步调用。所以 2013 年的开发者理解”微任务”这个思想，最可靠的参照就是 MutationObserver 的行为：不是马上执行，也不是等到下一个定时器，而是在当前任务的尾巴上。

MutationObserver 还有个比它前身 MutationEvent 更关键的优点：它是异步批量触发的。早期的 DOMNodeInserted 之类事件是同步回调，改一次 DOM 就触发一次，嵌套修改时会造成极深的调用栈与严重的性能问题。MutationObserver 把多次修改合并成一次回调，这正是”微任务批处理”思想在 2013 年的落地形态。

ES6 草案里 Promise 的 then 回调被设计成投递到 microtask 队列，这是该思想的正式规范化。前瞻地看，这意味着将来 then 回调会跑在”当前任务结束、渲染之前”，与 MutationObserver 同一时机——比 setTimeout 更早。但在 2013 年，这还只是提案，本文不写相关代码。

宏任务的分类与特性

浏览器模型里，任务队列中的任务按来源可以分成几类，它们共享同一个队列，但有各自的行为特征。

  • setTimeout 与 setInterval：到期后把回调排入队列，属于定时器任务。
  • I/O：网络请求、文件读取（Node）完成后的回调。
  • UI 事件：鼠标、键盘、触摸等交互事件，由用户操作触发。
  • postMessage：跨文档、跨窗口通信，消息到达后排入队列。
  • MutationObserver：按上面的机制在任务边界批量触发。

这些任务之间没有优先级之分，都按到达顺序排队。一个任务执行期间产生的新任务，不会插队到当前任务之前，只会排到队尾。这是事件循环公平性的基础，也是”定时器不准”的根源之一：队列前面排了十个耗时任务，你的定时器回调就得等这十个全跑完。

flowchart LR
  A[定时器到期] --> Q[任务队列]
  B[用户交互] --> Q
  C[网络完成] --> Q
  D[postMessage] --> Q
  Q --> E[事件循环取队首]
  E --> F[执行任务 压栈出栈]
  F --> G[栈空 进入下一轮]

这里要区分”任务队列”与”作业队列”的字面混淆。HTML 标准里 2013 年前后使用 task queue 指代宏任务，早期文档中偶尔出现 event loop 的”task queue”与浏览器内部实现的多个子队列（如鼠标事件一个、定时器一个）混用的情况。普通开发者不必关心引擎内部拆了几个队列，需要记住的规则只有一条：任务按到达顺序被取走，当前任务执行期间产生的新任务排到队尾，不会插队。

setTimeout 的最小延迟与嵌套限制

setTimeout(fn, 0) 并不意味着”立即执行”，这一点值得单独讲，因为它是误解最深的地方。

首先，浏览器对 setTimeout 有一个最小延迟。HTML5 规范规定，当嵌套层级超过 5 层时，最小延迟为 4 毫秒。也就是说，连续嵌套调用 setTimeout 到第 5 次之后，即使写 0，实际也要等至少 4 毫秒。这个规定是为了防止页面用嵌套定时器把 CPU 占满，最早在 Chrome 等浏览器中落地。

其次，setTimeout 的回调必须等当前任务结束、调用栈清空后才能执行。如果当前有一个同步任务跑了 500 毫秒，你的 setTimeout(fn, 0) 回调最早也要在第 500 毫秒之后才开始。所以 setTimeout 的实际延迟是”指定延迟”与”队列等待时间”的较大者。

第三，定时器的精度受节流阀（throttling）影响。Chrome 从 2011 年起对后台标签页的定时器做了限制：不可见标签页中的 setTimeout 与 setInterval 被强制拉到 1000 毫秒以上执行。这个设计的出发点很实际——后台页面还在跑定时器，白白消耗电量与 CPU。但它带来一个常见陷阱：页面从后台切回前台时，可能有一次集中触发的回调堆积，表现像是”定时器突然跳了好几下”。

setInterval 还有一个老问题：如果回调执行时间长于间隔时间，多个回调可能连续触发而没有间隔。规范层面的缓解是把”到期的 interval”合并处理，但更可靠的做法是用 setTimeout 自调用来模拟周期任务，每次执行完再排下一次，天然避免了叠加。

事件循环的一次迭代

把前面的部件拼起来，事件循环的一轮迭代过程是这样的。

第一步，从任务队列取出队首任务。如果队列为空，循环进入等待。

第二步，执行该任务。这会把对应的执行上下文压栈、执行、出栈。任务执行期间可能产生新的定时器任务、I/O 回调、交互事件任务，它们排到队列尾部，不在本轮执行。

第三步，当前任务执行完毕、调用栈清空后，执行微任务检查点（microtask checkpoint）——在 2013 年的现实里，这个位置对应的就是 MutationObserver 回调被批量触发的时机。用后来的规范语言说，就是清空微任务队列：把队列里的微任务依次执行，执行期间新产生的微任务也加入本轮清空，直到队列为空。

第四步，到了渲染机会（rendering opportunity）。浏览器判断是否需要更新屏幕：如果文档有变化、视口尺寸变化、滚动发生等，就执行样式计算、布局、绘制。requestAnimationFrame 的回调正是在这一步之前执行。

sequenceDiagram
  participant Q as 任务队列
  participant S as 调用栈
  participant M as 微任务检查点
  participant R as 渲染阶段
  Q->>S: 取队首任务并执行
  S->>Q: 执行中产生的新任务排到队尾
  S->>M: 栈空 触发微任务
  M->>M: 依次执行 新产生的也并入本轮
  M->>R: 微任务清空后进入渲染机会
  R->>Q: 渲染完成 进入下一轮迭代

理解这个顺序的关键在于微任务的位置：它在一个任务结束后立刻清空，而不是等到所有任务都跑完。所以一个任务执行期间产生的微任务，会在下一个任务开始前全部跑完。这也是 MutationObserver 与 setTimeout 时序差异的根源——前者在任务边界，后者要排到队尾等下一轮。

requestAnimationFrame 与事件循环的关系

requestAnimationFrame 在 2011 年之后逐渐可用，它与事件循环的关系经常被搞错。它不是一个普通任务，它的执行时机被绑在渲染流程上：在浏览器即将进行样式计算与布局之前、绘制之前，把注册的回调执行掉。

这个时机带来两个实用结论。第一，requestAnimationFrame 回调里读取布局信息是安全的——此时上一帧的布局已确定，不会读到中间状态；反过来，在回调里频繁改样式又读样式，仍可能触发强制同步布局。第二，它比 setTimeout 更适合做动画，因为它与浏览器刷新节奏对齐，不会出现”画了一帧没人看”的浪费，也不会像 16 毫秒的 setInterval 那样因为负载高而与刷新错位。

需要注意的是，requestAnimationFrame 在页面不可见时通常不会触发，这与后台标签页定时器被限制是同一思路：不为看不见的绘制工作。

阻塞事件循环的后果与 Web Worker

事件循环是单线程的，这意味着任何长时间占用调用栈的代码都会阻塞一切：定时器不到期、点击不响应、网络回调不执行、页面不渲染。用户看到的就是”卡住了”。

阻塞的来源通常是三类：大量同步计算（复杂排序、大循环、大字符串拼接）、频繁的 DOM 读写引发的强制同步布局、以及同步的网络请求（2013 年还有少数场景在用 XMLHttpRequest 的同步模式，这是明确应当避免的）。

解法是把计算搬出主线程，这就是 Web Worker 的意义。Worker 在浏览器里可用大约从 2009 年开始，到 2012 年主流浏览器已支持得比较完整。它创建一个独立的执行环境，有自己的全局作用域与事件循环，与主线程通过消息通信。

Worker 有几个限制必须知道：它不能访问 DOM，不能访问 window 与 document，与主线程只能通过可结构化克隆的数据通信（不能传函数）。所以它只适合纯计算，不适合操作界面。但对于大数据排序、图像像素处理、加解密这类任务，Worker 是当年最有效的解卡手段。

如果不便引入 Worker，退而求其次的做法是把长任务切片：把一个大循环拆成若干批，每批之间用 setTimeout 让出主线程，让事件循环有机会处理交互与渲染。这是一种协作式的让渡，代价是总耗时略增，但页面不会假死。

Node.js 0.10 的 libuv 事件循环

Node.js 的事件循环由 libuv 实现，与浏览器有显著差异。在 2013 年 10 月发布的 Node 0.10 这一代，libuv 的循环被划分为若干阶段，按固定顺序推进：

  • timers：setTimeout 与 setInterval 到期回调。
  • pending callbacks：上一轮延迟到本轮的 I/O 回调。
  • idle / prepare：内部使用，供 libuv 自身处理。
  • poll：获取新的 I/O 事件，执行相关回调；该阶段可能阻塞以等待事件。
  • check：setImmediate 回调。
  • close callbacks：关闭事件的回调，如 socket.on('close')。
flowchart LR
  A[timers] --> B[pending callbacks]
  B --> C[idle prepare]
  C --> D[poll]
  D --> E[check]
  E --> F[close callbacks]
  F --> A

与浏览器最直观的差异是 setImmediate。它注册的回调在 poll 阶段之后、check 阶段执行，同一个 I/O 周期内就能跑，不必等下一个定时器周期。所以 Node 里 setTimeout(fn, 0) 与 setImmediate(fn) 的顺序在主模块里并不固定，但在 I/O 回调内部，setImmediate 总是先于 setTimeout 执行——这是浏览器里不存在的概念。

另一个差异是 Node 没有”渲染”这一步。浏览器的循环里有渲染机会，Node 的循环只关心 I/O 与定时器，没有屏幕要更新。这也意味着 Node 里不存在”为了不掉帧而让出主线程”的说法，让出的理由是让其他 I/O 回调有机会执行。

process.nextTick 与微任务

Node 0.10 提供了 process.nextTick，它的语义是：注册的回调不在当前阶段执行，而是在当前操作结束后、事件循环进入下一阶段之前执行。它不是定时器，也不受循环阶段顺序约束。

它与后来 Promise 微任务的关系是这样的：ES6 规范把 Promise 的 then 回调归入 microtask 队列，而 Node 在实现上很早就用 nextTick 队列承担类似角色，两个队列在同一时机被清空。在 Node 0.10 里讨论”微任务”，process.nextTick 就是当时最贴近的现实参照。需要注意 nextTick 队列有递归风险：如果在 nextTick 回调里再注册 nextTick，且永远不停，事件循环会被饿死，永远推进不到 timers 阶段。这是 Node 里真实存在过的坑。

常见误区

最后集中清理几个流传很广的误解。

第一个误区是”setTimeout 0 就是异步执行”。它确实是异步的——不会在当前同步代码里执行——但它的延迟不是 0。它至少要等当前任务结束、栈清空、队列前面的任务跑完，嵌套超过 5 层还有 4 毫秒下限。所以它不是”立即”，只是”不阻塞当前代码”。

第二个误区是”Promise 是宏任务”。这个说法在 2013 年还不成立，因为 ES6 的 microtask 语义尚未落地；即使在后来的规范里，Promise 的 then 回调也属于微任务，执行时机早于 setTimeout。2013 年可以确定的是：与它行为最接近的既有技术是 MutationObserver，而它明显早于定时器。

第三个误区是”定时器时间到了就一定准时执行”。定时器只是登记了到期时间，能否准时执行取决于队列状态。前面排着耗时任务，定时器就只能等。这也是为什么用定时器做精确计时不可靠——要测量时间差应该用 Date.now()，要控制执行节奏应该考虑渲染对齐的 requestAnimationFrame。

第四个误区是”Node 与浏览器的事件循环一样，只是 API 不同”。两者都由事件循环驱动、都有任务队列，这是相同点；但循环阶段的划分、setImmediate 的存在、有无渲染步骤，都是实质差异。跨环境复用异步代码时，这些差异会暴露出来。

小结

事件循环的本质是一个”取任务、执行到栈空、清空微任务、再取下一个”的循环，它的驱动力是单线程的调用栈与排队的任务队列。微任务在 2013 年还没有进入规范，但 MutationObserver 的批量异步回调已经把这个思想的形态带到了浏览器里，Node 0.10 的 process.nextTick 则是另一侧的对应物。浏览器循环里有渲染机会，requestAnimationFrame 卡在渲染之前；Node 循环按 libuv 的阶段推进，有 setImmediate 而没有渲染。定时器的 4 毫秒嵌套下限、后台标签页的 1000 毫秒节流、setTimeout 0 不立即执行，都是这套机制的直接后果。推演异步顺序的方法很朴素：同步进栈、任务排队、任务边界清空微任务、下一个任务之前先看渲染。把这条线索记住，绝大多数看似诡异的输出顺序都能自己推出来。
