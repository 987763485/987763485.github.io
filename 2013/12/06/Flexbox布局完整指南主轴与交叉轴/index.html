Flexbox 布局完整指南：主轴与交叉轴

本文属于《HTML 与 CSS》第 29/62 篇
上一篇系列目录下一篇

2013 年写 Flexbox 是一件需要耐心的事。规范本身几经修订，浏览器各自实现了不同阶段的草案语法，IE10 用的是中间版本，Chrome 与 Firefox 还要带前缀。很多人写完发现代码在自己机器上生效、在别人机器上不生效，多半是前缀或语法版本的问题。但抛开这些工程细节，Flexbox 解决问题的思路本身是清晰而优雅的：用两根轴重新定义对齐。本文把 2013 年前缀现状下的 Flexbox 完整讲一遍，重点放在那两根让人困惑的轴上。

为什么需要 Flexbox？因为 float 布局从来没有为”对齐”这件事设计过。用 float 做多列等高、垂直居中、等分剩余空间，都要靠各种技巧弥补，而且这些技巧各有各的坑：display: table 失去语义、inline-block 受空白字符影响、绝对定位脱离文档流。Flexbox 第一次把”沿一个方向排列”和”沿垂直方向对齐”变成了一等公民。

2013 年的兼容现状与前缀写法

动手之前必须先看清地形。2013 年的 Flexbox 有三个历史版本，语法互不兼容：

  • 2009 年的旧草案（display: box），Chrome 与 Safari 早期实现，如今已完全淘汰。
  • 2011 年的中间草案（display: flexbox），IE10 采用的就是这一套。
  • 2012 年的标准草案（display: flex），这是今天语法的前身，Chrome 21+、Firefox 18+ 之后逐步实现。

2013 年底的实际支持情况是这样的：Chrome 21 及以上需要 -webkit- 前缀；Firefox 18 及以上基本无需前缀（更早的版本需要 -moz-）；Safari 需要 -webkit- 前缀且长期停留在旧语法上；IE10 使用 -ms- 前缀的中间语法；IE9 及以下完全不支持。

主轴与交叉轴：Flexbox 的心脏

如果只从本文带走一个知识点，那就是这两根轴。Flexbox 的所有对齐属性，作用的对象不是”上下左右”，而是”主轴”与”交叉轴”。

主轴（main axis）由 flex-direction 决定。默认值是 row，此时主轴是水平方向、起点在左端。交叉轴（cross axis）与主轴垂直。当 flex-direction 变成 column，主轴旋转九十度变成竖直方向，交叉轴随之变成水平方向。

记住这条对应关系，后面所有属性都不会记混：

  • justify-content 控制项目在主轴上的排列与间距。
  • align-items 控制项目在单行交叉轴上的对齐。
  • align-content 控制多行在交叉轴上的整体分布。

初学者最大的困惑正在于此：学了浮动布局的人默认”水平”由 justify 管、”竖直”由 align 管，这个直觉只在 flex-direction: row 时成立。一旦方向改为 column，两者立即互换。所以记属性名没有用，记”justify 管主轴、align 管交叉轴”才有用。

还有一个连带的概念需要建立：方向改变了，属性作用的物理方向改变，但属性的语义不变。flex-start 永远是主轴的起点，flex-end 永远是主轴的终点。在 row-reverse 下，flex-start 在右侧；在 column-reverse 下，flex-start 在底部。所以写 Flexbox 时心里想的应该是”起点、终点、居中、间距”，而不是”左、右、上、下”。这个转换一开始别扭，习惯之后读代码会快很多——因为方向只是配置，语义才是本质。

还有一个容易忽略的事实：justify-content 分配的是”剩余空间”，而剩余空间为负时它不起作用。也就是说，当项目总宽度已经超过容器（nowrap 且不收缩），center 不会把项目往回拉，溢出方向由书写模式决定。这也是溢出问题常被误判成”justify-content 失效”的原因。

容器属性：align-items 与 align-content

这两个是最容易混淆的一对，区别在于作用对象。

align-items 作用于交叉轴，设定每一行内项目的对齐方式：

baseline 的价值在一行里项目字号不同、希望文字底部对齐时体现，比 flex-end 更符合视觉习惯。stretch 是默认值，这是很多人意外的：不写 align-items，项目就会沿交叉轴拉伸。所以想看到项目”自然高度”而不是被拉高，往往需要显式写 align-items: flex-start。

align-content 只在多行时起作用——即 flex-wrap: wrap 且实际发生了换行。它决定的是这些行本身在交叉轴上如何分布：

如果只有一行，align-content 不起作用——因为此时控制这一行位置的是 align-items。这个”单行用 align-items、多行用 align-content”的区分，是理解这两个属性的关键。

项目属性：order 与 align-self

order 改变项目的视觉排列顺序，默认值是 0，数值越小越靠前：

它只影响视觉顺序，不影响 DOM 顺序，也不影响键盘 Tab 顺序。用负数可以让某个项目排到最前面。这个属性在 2013 年的主要用途是响应式重排——桌面端左主右辅，移动端把辅助内容提前。

align-self 让单个项目脱离容器 align-items 设定的对齐方式，取值与 align-items 相同，多一个 auto（继承父级的 align-items）：

它的实际价值在于一行里大多数项目用一种对齐、个别项目需要例外时，不必给每个项目单独包一层。

baseline 与 stretch 的两个坑

align-items: baseline 值得多说两句。它按项目内第一行文字的基线对齐，这在一行里混合了不同字号的元素时比 flex-end 更自然——比如价格数字大、货币符号小，按基线排才能让它们站在同一条线上。但 baseline 对齐有个限制：如果项目内根本没有文字，或者文字被绝对定位移除，基线就无从计算，浏览器会退回到按 flex-start 处理。

stretch 的坑在于它只在项目没有显式设置交叉轴尺寸时才生效。一旦给项目写了 height（交叉轴是竖直时）或 width（交叉轴是水平时），stretch 就不再拉伸它。很多人遇到”我明明写了 stretch，项目却没有撑满容器高度”，原因就是这个——检查一下是不是项目上带了固定高度。

项目属性：flex-basis 的取值细节

flex-basis 接受的取值比看上去更丰富，理解这些差别对算准尺寸很有帮助：

flex: 1 与 flex: 1 1 0 是等价的，这里的 0 会被解析成 0%。而 flex: 1 1 auto 的基准是内容尺寸，所以 flex: 1 与 flex: auto 的行为差异全在这一个基准值上。这个差别在列表项文字长短不一时表现得最明显：用 flex: auto 时文字长的项最终更宽，用 flex: 1 时所有项严格等宽——代价是文字长的项可能换行更多。

另一个容易忽略的细节是自动最小尺寸。Flexbox 规定，当 flex-basis 为 0 且项目内容有最小宽度需求时，浏览器会为项目应用一个自动的最小尺寸（大致是内容的最小宽度）。这意味着 flex: 1 并不总是能无限压缩一个项目：如果它里面放了一张 300 像素宽的图片，容器再窄，这个项目也小不到 300 像素以下。遇到这种情况，需要显式写 min-width: 0 来解除这个保护。

尺寸计算：flex-grow、flex-shrink 与 flex-basis

这三个属性共同决定项目最终尺寸，也是 Flexbox 里最需要算一笔账的部分。先把三个角色的分工说清楚：

  • flex-basis 是项目的初始基准尺寸，即”在分配剩余空间之前，我有多大”。
  • flex-grow 决定有剩余空间时，项目按什么比例放大。
  • flex-shrink 决定空间不足时，项目按什么比例缩小。

负空间与正空间

分配的是两种空间。容器主轴尺寸减去所有项目基准尺寸之和，得到剩余空间，也就是自由空间（free space）。自由空间为正时，按 flex-grow 分配；为负时，按 flex-shrink 分配。Flexbox 的一次布局，本质上就是先确定基准，再分配这份自由空间。

flowchart TD
  A[容器主轴尺寸] --> B[减去各项目 flex-basis 之和]
  B --> C{自由空间为正}
  C -->|是| D[按 flex-grow 比例放大]
  C -->|否| E[按 flex-shrink 比例缩小]
  D --> F[最终尺寸]
  E --> F

一个完整的计算示例

设容器宽 600 像素，三个项目的 flex-basis 都是 100 像素，flex-grow 分别是 1、2、1。三个基准之和是 300，剩余空间是 300。按比例分配，第二项拿到 300 的一半即 150，第一、三项各拿 75。最终宽度是 175、250、175 像素。

收缩的情形稍微复杂，因为规范规定 flex-shrink 要与基准尺寸相乘后再归一化。设容器宽 200 像素，两个项目基准分别是 150 与 50，flex-shrink 都是 1。总基准 200，恰好等于容器，无剩余。若容器改为 150，则超载 50。按 2012 草案的算法，收缩权重是基准乘收缩系数：150 乘 1 与 50 乘 1，权重比是三比一，于是第一项收缩 37.5、第二项收缩 12.5，最终为 112.5 与 37.5 像素。这个”大项目缩得多”的设计是为了避免小项目被压到无法容纳内容。

flex 简写的默认值

flex 是三个属性的简写，写法有几种等价形式：

flex: 1 与 flex: auto 的差别常常被忽视，而它直接决定等分列的效果。flex: 1 的基准是 0，所以容器空间被完全等分，与项目内容多少无关；flex: auto 的基准是内容尺寸，分配完剩余空间后，内容多的项目最终仍然更大。要做严格的等分列，用 flex: 1；要”内容撑开后再平分剩余”，用 flex: auto。

flex: initial 是”什么都不做”的显式写法，与不写 flex 属性的默认行为一致。它存在的意义是当项目继承了容器的 flex 简写时，可以显式重置回默认。

flex-basis 与 width 的优先级

flex-basis 与 width 都描述项目尺寸，冲突时以 flex-basis 为准。这是因为 flex-basis 在规范里就是主轴方向的尺寸设定，而 width 是主轴为水平时的等价物。更准确地说：flex-basis 未设置时，容器会回退读取 width（主轴水平时）或 height（主轴竖直时）；一旦 flex-basis 有值，width 就不再影响主轴基准。所以 2013 年的建议是：做 Flexbox 布局就用 flex-basis，不要混用 width 与 flex-basis，否则基准来源会变得难以预测。

margin 在 flex 项目中的行为

Flexbox 里的 margin 有一条特殊规则：不会发生外边距折叠（margin collapsing）。折叠是常规文档流里的行为——相邻块级元素的上下 margin 会合并取较大值。在 flex 容器里，项目由 Flexbox 布局而非块级文档流布局，折叠规则不适用。

这条规则有重要的实用价值：用 margin 做间距时，间距是确定的累加值，不会出现”本以为 20 像素实际只有 20 像素（折叠）”的意外。做等分网格时，可以直接给项目加 margin-right 并用 flex-basis 扣掉对应宽度：

还有一个不该忽略的对比对象是当年最常见的”绝对定位加负 margin”方案。它在两栏定宽场景下写起来很短，但它要求父级有明确高度、内容溢出时不会自适应、且一旦文案变长就会破版。Flexbox 的 flex: 1 让剩余空间的分配交给浏览器，这类破版从源头消失。这也是判断该不该上 Flexbox 的实用标准：如果你的布局里出现了”算出来的宽度”，大概率就该用 flex-basis 加 flex-grow 重写一遍。

常见坑与调试方法

2013 年用 Flexbox，一半时间花在排查问题上。把常见坑列出来，能省不少事。

第一个坑是 flex-basis 与 width 并存。前面说过 flex-basis 优先，但很多人是从旧代码改起的，项目上留着 width: 32%，又新加了 flex: 1，结果宽度表现完全不符合预期。规则很简单：上了 flex 的项目，把交叉轴方向的固定尺寸以外的 width 清掉。

第二个坑是 flex-wrap: nowrap 的默认值。做九宫格忘了写 wrap，所有卡片被压在一行里挤成条状。检查方法是看容器高度是否异常矮、项目宽度是否远小于预期。

第三个坑是项目内容撑破容器。flex: 1 的项目里放一段不可断行的长文本或一张大图，项目会超出容器，因为它有自动最小尺寸保护。解法是给项目加 min-width: 0，并让内部元素自己处理溢出（overflow: hidden 或 word-break）。

第四个坑是 order 与 Tab 顺序不一致。视觉上把第一个项目用 order: -1 挪到了最后，键盘用户按 Tab 却先聚焦它。涉及表单与可交互元素的布局，不要用 order 做重排，应该调整 DOM 顺序或用媒体查询分场景输出。

调试上，2013 年 Chrome 的 DevTools 已经能在 Elements 面板里显示 flex 容器的徽标，点开可以看到每个项目的基准尺寸、最终尺寸与放大缩小系数；Firefox 稍晚也提供了类似的盒模型可视化。这些工具比反复改 CSS 猜要高效得多。另外建议临时给容器加一个醒目的背景色、给项目加边框，肉眼确认轴方向是否符合预期——大多数”Flexbox 不生效”的问题，最后都发现是轴方向搞反了。

渐进增强策略

2013 年用 Flexbox 的正确姿势是渐进增强：基础布局用兼容性最好的方案，Flexbox 作为增强叠加其上。典型的写法是先给容器一个 display: block 或 float 的形态，再用特性检测或媒体查询切到 flex。

Modernizr 当时已经提供了 Flexbox 检测，检测通过会给根元素加 flexbox 类，对应上面的 .flexbox 选择器。如果不想引入 Modernizr，也可以用 CSS 的条件注释对 IE9 及以下单独输出 float 版本。

需要提醒的是，2013 年前缀的混乱让这套方案写起来很痛苦：同一套属性要为 -webkit-、-ms-、标准写法各写一遍，且 IE10 的中间语法部分属性名不同。那时常见的工程做法是用 Autoprefixer 或 Stylus 的 nib 插件自动生成前缀，手写只适合小页面。到了 2013 年底，Safari 6 与 iOS 6 上的旧语法残留仍是线上事故的高发区，跨设备实测不可省略。

渐进增强还有一层取舍要讲清楚：回退方案与增强方案的视觉不必完全一致。当年的稳妥做法是让回退版本可用但不完美——float 回退下两栏不等高、间距略不一致，都是可以接受的；真正不能接受的是布局破版。为了追求两套方案视觉完全一致而写大量 hack，维护成本会迅速超过收益。另一个实践是特性检测只做一次并缓存结果，不要每次查询都跑一遍 Modernizr。

小结

Flexbox 的核心不是那十几个属性，而是主轴与交叉轴这对坐标系：方向由 flex-direction 决定，justify-content 永远作用于主轴，align-items 作用于交叉轴，align-content 管多行分布。抓住这一点，属性就不用死记。尺寸由 flex-basis、flex-grow、flex-shrink 三者共同决定，flex 简写的几种形式差别全在基准值上，flex: 1 等分、flex: auto 按内容分配剩余。margin 在 flex 项目里不折叠，这让间距计算变得可靠。2013 年用它必须面对前缀与语法分裂，工程上靠渐进增强兜底。它的真正价值在于第一次让”对齐”成为布局系统的一等能力，等高、居中、等分这些曾需要技巧的需求，从此有了直接答案。
