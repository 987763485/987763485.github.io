移动端性能优化特殊点

桌面端的性能优化套路搬到手机上经常失效，原因很直接：网络环境完全不同，CPU 与内存差一个量级，交互方式从鼠标变成了手指。本文从踩坑复盘的角度，把 2013 年移动端优化里那些”和桌面不一样”的点单独列出来。结论先放在前面：移动端优化的第一顺位不是代码执行速度，而是请求数、首屏体积和触控响应。

弱网与高延迟：请求数是第一指标

桌面用户基本在宽带上，而 2013 年的移动端主力网络是 2G、3G 和不太稳定的 Wi-Fi。这里的关键认知是：延迟比带宽更致命。一个 4KB 的 CSS 在带宽上不值得一提，但一次 RTT 就可能吃掉 300ms 以上，而 3G 网络下握手加往返的代价远超下载本身。

一个典型的页面加载可以拆成下面几步，每一步都可能是一次完整往返：

sequenceDiagram
  participant U as 用户设备
  participant D as DNS
  participant S as 服务器
  U->>D: DNS 查询
  D-->>U: 返回 IP
  U->>S: TCP 三次握手
  S-->>U: 连接建立
  U->>S: 请求 HTML
  S-->>U: 返回 HTML
  U->>S: 请求 CSS/JS/图片（多个）
  S-->>U: 逐个返回
  U->>U: 解析、渲染、执行脚本

在 3G 网络下，一次 DNS 查询加一次 TCP 握手就可能接近一秒。这意味着桌面端”能容忍的小请求”在移动端完全不能容忍。当年的优化手段很朴素但有效：

  • 合并请求。CSS 和 JS 各自合并成一个文件，图标用雪碧图，这是移动端最划算的一招。
  • 减少重定向。每次 301/302 都是一次额外往返，www 跳转、URL 规范化这些桌面端无所谓的事情，在移动端都要重新评估。
  • 域名收敛。桌面端常用多域名并行下载，但每个新域名都要 DNS 查询和握手，移动端反而应该控制域名数。2 到 4 个是当年的经验值。
  • 首屏最小化。首屏只加载必需的 CSS 和 JS，其余延迟或者按需加载。

一个容易忽略的点是请求瀑布。浏览器的预解析扫描器在当年还不成熟，页面中间插入的样式表和脚本会阻塞后续解析，形成一条漫长的瀑布链。把关键 CSS 内联到 head、把脚本放页面底部，是移动端比桌面端收益更明显的做法。

CPU、GPU 与内存的真实限制

2013 年的中低端 Android 手机，CPU 大致相当于 2010 年前后的桌面水平，内存普遍在 512MB 到 1GB 之间，而系统本身和浏览器就要占掉相当一部分。这带来三个后果。

第一，JavaScript 执行慢。 桌面端可以忽略的小循环，在手机上可能造成明显掉帧。减少 DOM 操作、避免在滚动回调里做复杂计算，比微优化语法更有效。

第二，动画必须走合成层。 2013 年的共识已经形成：动画只动 transform 和 opacity，不要动 width、height、top、left。前者可以交给 GPU 合成，后者会触发布局计算，在主线程上跑。

第三，图片解码是内存杀手。 一张 1000×1000 的 PNG，解码后就是 4MB 左右的位图。列表页一口气加载几十张大图，低端机直接 OOM 崩溃。图片必须按需加载、按显示尺寸裁剪，而不是把原图缩着用。

首屏渲染顺序在移动端的重要性高于桌面端，因为首屏时间直接决定用户是否等待。原则是：先出结构，再出样式，最后出交互。CSS 放在 head（阻塞渲染但避免白屏和样式闪烁），JS 放在底部，大图用占位尺寸撑住高度防止布局抖动。

WebView 与 Hybrid 的特殊性

2013 年大量”移动端页面”实际跑在 App 的 WebView 里，这带来桌面浏览器不存在的问题。

WebView 的缓存策略与独立浏览器不同：部分 Android WebView 默认不开磁盘缓存，或者缓存策略由宿主 App 控制。资源如果放在本地 file 协议或者 App 内置目录，加载速度远快于网络。Hybrid 方案的常规做法是把框架性资源打包进安装包，数据类内容走网络。

WebView 还意味着你可能无法控制缓存和 Cookie 策略，也无法升级浏览器内核。iOS 上 WebView 的 JavaScript 引擎性能长期落后于 Safari，Android 上不同机型的 WebView 版本可能是 Chrome 18 到 Chrome 30 之间的任意一个。测试时必须覆盖目标机型的真实 WebView。

真机测试：模拟器骗人

最后一条也是最重要的复盘结论：模拟器的性能数据完全不可信。iOS 模拟器跑的是 x86 代码，用的是桌面 CPU，性能比真机快数倍；Android 模拟器的 GPU 是软件渲染，与真机的 Mali 或 Adreno 完全不同。

真实的性能测试必须覆盖：

  • 不同代际的机型，至少包含一款当年的中低端 Android 机。
  • 真实的网络环境。桌面开发时用 Chrome 的限速可以模拟带宽，但模拟不了丢包和信号切换。
  • 弱网场景，包括 2G 和电梯、地铁里的信号切换。
  • 长时间运行后的内存状态，低端机上的内存泄漏比桌面端更快致命。

不同 Android 机型之间的差异大到惊人：同一段动画在三星旗舰上流畅，在国产中低端机上可能直接卡成幻灯片。这种差异无法通过”兼容写法”消除，只能通过真机测试定位，再决定降级方案。

上面的 navigator.deviceMemory 在 2013 年并不存在，这里只是示意思路；当年的实际做法是按 UA 里的系统版本和机型关键字做分级，粗糙但有效。

小结

移动端性能优化的核心差异在于：网络以延迟而非带宽为主导，所以请求数比文件体积更优先；CPU 和内存的约束让动画必须限制在 transform 和 opacity，图片必须按需解码；触控交互带来了 300ms 点击延迟和滚动回调性能这两个桌面端不存在的坑；WebView 环境下缓存和内核都不可控，Hybrid 场景要把资源本地化。而所有优化手段生效的前提是真机测试——模拟器的数据在移动端几乎没有参考价值。先量请求数和首屏时间，再量帧率和内存，这个顺序不能颠倒。
