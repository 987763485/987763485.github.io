CSS 精灵图与图文混排排版技巧

本文属于《HTML 与 CSS》第 40/62 篇
上一篇系列目录下一篇

CSS Sprite 曾经是前端优化的必修课，2013 年的页面上图标几乎清一色来自雪碧图。本文从对比与选型的角度，讲清精灵图的原理与制作方法、background-position 的定位技巧、高 DPI 适配方案，以及它与 Base64 内联、iconfont 之间的取舍。结论先给出：请求数敏感的页面用精灵图，图标需要多色和动态控制时用 iconfont，两者在 2013 年长期并存。

精灵图的原理与收益量化

HTTP 请求的成本在 2013 年被普遍低估。每个请求都有握手、DNS、请求头、响应头的固定开销，一个 1KB 的小图标和一个 100KB 的大图，请求耗时可能差不多。精灵图（CSS Sprite）的思路就是把几十个小背景图拼成一张大图，用一次请求换掉几十次请求。

收益可以粗略量化：假设 3G 网络下一次请求的固定开销约 200ms，8 个图标合并成 1 个，就能省下约 1.4 秒。Steve Souders 在《High Performance Web Sites》里把”减少 DNS 查询”和”减少请求数”列为最靠前的规则，正是这个道理。反过来，精灵图的代价也清晰：整张大图都要下载，某个图标更新会导致整图缓存失效，以及维护一份坐标映射表的心智负担。

制作方法与命名规范

2013 年制作雪碧图的主流方式有两种。

Photoshop 手动拼。 新建一个透明背景的画布，把各图标按网格排列，图标之间留 2 到 4px 间距防止相互渗透，导出为 PNG-24 或 PNG-8。导出时用切片工具逐块切，再生成坐标表。这种方式可控性最强，适合图标数量少、需要精调的场景。

工具自动拼。 比较流行的有 CSS Sprite Generator、SpriteMe（Steve Souders 团队做的）、以及国内的各种在线拼图工具。它们读入一批小图，自动排列并生成带 background-position 的 CSS。好处是不会算错坐标，坏处是排列策略可能不是最优，图片顺序也未必符合逻辑。

不管用哪种方式，命名规范都是维护的关键。当年比较被认可的做法是按模块分文件，而不是把所有图标堆成一张巨图：

按模块拆分是一个权衡：全部合并请求数最少，但单文件体积大、缓存粒度粗；按模块拆分缓存更合理，代价是多几个请求。项目大了之后，通常走到”公共图标一张图、业务图标各自一张图”这个中间态。

background-position 的定位技巧

background-position 的取值形式比多数人以为的更丰富，理解它能让雪碧图的写法更健壮。

百分比定位是常被忽略的利器。它的计算方式是：偏移量 = (元素尺寸 - 图片尺寸) × 百分比。这意味着当元素尺寸固定而背景图比元素大时，50% 50% 就是精确居中；而 center center 关键字与之等价。

雪碧图场景下最常见的坑是只写了一个值。此时第二个值默认为 center，于是本来想左上角对齐的图标跑到了垂直居中位置：

另一个坑是雪碧图缩放后坐标错位。一旦给图标设了 width/height 让背景图被压缩或拉伸，background-position 的百分比语义会跟着变，而像素值则保持原样。所以雪碧图上的图标必须按原尺寸使用，不能缩放；需要不同尺寸就导出两份。

高 DPI 与 Retina 适配

iPhone 4 之后 Retina 屏迅速普及，2013 年适配高 DPI 已经是标配工作。原理是准备一张 2 倍尺寸的雪碧图，用 media query 按设备像素比切换，再用 background-size 把大图缩回原始尺寸，坐标相应除以 2。

background-size 在现代浏览器已经不需要前缀，但 2013 年为了兼容旧版 WebKit 仍要写 -webkit-background-size。媒体查询的 -webkit-min-device-pixel-ratio 与标准 min-resolution 并存，也是当年的常态。

这套方案的代价是 2 倍图的体积。PNG 的 2 倍图往往接近 4 倍字节数，因此高 DPI 图标要严格控制数量，只对确实需要锐利显示的图标（导航、按钮、Logo）提供倍图，装饰性大图仍用 1 倍。

与 Base64 内联的取舍

Base64 内联是另一条减少请求数的路线：把小图转成 Base64 字符串直接写进 CSS。

两者的取舍很清晰，可以对照着选：

维度 精灵图 Base64 内联
请求数 一次请求承载全部 零额外请求
体积 略大于原图总和 增大约 33%
缓存 可被浏览器缓存复用 随 CSS 缓存，更新即失效
首屏 CSS 体积 小 大，阻塞渲染
维护 需维护坐标 需重新生成字符串
渐进加载 背景图后到，有闪烁 与 CSS 同时到达

实践上的分界线是：极小且首屏必需的图标用 Base64，其余用精灵图。Base64 增大体积且拖慢 CSS 解析，放一大串进去会让首屏渲染明显变慢。另外 Base64 字符串无法被 gzip 高效压缩（它是随机字节的编码），所以”gzip 会压小它”这个假设不成立。

与 iconfont 的对比

2013 年 iconfont 已经相当流行，阿里图标库这类平台也在那前后兴起。它把图标做成字体文件，用 content 配合 @font-face 渲染：

iconfont 的优势非常突出：矢量、任意缩放不失真、可以用 CSS 控制颜色和大小、一套字体文件多端复用、体积通常远小于雪碧图。它在高 DPI 适配上天然占优——不需要倍图。

但它也有雪碧图不存在的短板：字体渲染受抗锯齿算法影响，边缘不如位图锐利；单色图标无法表达复杂颜色；不同浏览器下字体渲染有细微差异；字体文件跨域加载需要服务端配置 CORS；老版本 IE 的 @font-face 兼容需要额外格式。此外，图标字体在某些场景下会被屏幕阅读器读出乱码，需要加 aria-hidden 处理。

所以 2013 年的实际选择通常是：多色、复杂的 Logo 和插图用精灵图，单色线性图标用 iconfont。两者并存而不是互相取代。

图文混排中的背景定位

最后把话题拉回图文混排。精灵图最常见的载体是带图标的文本行，这里有几个和混排直接相关的细节。

基线对齐。 背景图标与文字默认按元素底部对齐，视觉上会偏低。用 padding-left 留出图标位置，再用 background-position 的百分比特性做微调：

文字换行时的图标。 如果文字可能折行，background 会随元素高度变化而保持左上角，看起来图标和文字脱节。解决方法是把图标放到伪元素或 float 的独立元素上：

与文字大小的联动。 图标尺寸固定，文字大小变化时对齐关系会被打破。把图标放在固定宽度的容器里，文字用 padding-left 避开，比直接依赖背景定位更稳。

这个”图片加文字”的两栏结构在 2013 年被反复使用，靠 float 加 overflow: hidden 就能稳定工作，不需要后续才出现的现代布局方案。

小结

CSS Sprite 的本质是用一次请求的固定成本，换掉多次请求的重复成本，在 2013 年的网络环境下收益显著。制作上 Photoshop 手动拼和工具自动拼各有适用场景，按模块拆分加坐标注释是维护的关键。background-position 的百分比语义、单值默认 center 的陷阱、倍图切换时的坐标减半，都是实际项目里反复出现的坑。与 Base64 内联的取舍看体积与首屏影响，与 iconfont 的取舍看单色与多色、锐利度与矢量需求——2013 年的常态是三者按场景混用。图文混排中，图标与文字的基线对齐和换行处理，用浮动元素或伪元素比纯背景定位更可靠。
