JavaScript 中的循环与迭代方式

写 JavaScript 的人几乎没有一天不写循环，但”随手抓一个 for 就上”和”清楚每种迭代方式的代价”之间，隔着一整个性能与正确性问题。本文从工程实践出发，把 ES5 时代可用的循环方式摆在一起，比较它们的语义边界、速度量级和真实项目里最容易踩的坑。读完你应该能回答：什么时候必须用 for...in，为什么它最慢，以及迭代中修改数组会发生什么。

五种基本循环的语义边界

ES5 之前 JavaScript 只有命令式循环，ES5 给数组补上了函数式迭代的入口。先把各自的位置划清楚。

一句话分工：数组用 for 或 forEach，对象用 for...in 加 hasOwnProperty 过滤。混淆这两条界线是新手最常见的问题。

for 与 for…in 的关键差异

for...in 的语义是”枚举属性名”，不是”按下标访问元素”。这个区别在纯数组上看不出来，一旦有人往数组对象上挂了属性、或者往 Array.prototype 上扩展了方法，行为就会变形。

所以遍历数组要的是下标语义，遍历对象要的是键名语义，两者不能互相替换。另一个 for...in 的坑是遍历顺序不保证：规范只说”对象的属性枚举顺序由实现决定”，不同浏览器、不同插入方式下的顺序可能不同。依赖 for...in 的顺序做业务逻辑，等于把命运交给引擎。

for...in 还有一个只在数组上暴露的问题：它会遍历数组的自定义属性，于是”稀疏”与”非下标键”的元素都会被访问到。判断一个数组是否真的有”洞”、以及只想遍历真实存在的下标时，for...in 会给出错误答案。jQuery 内部遍历类数组对象时用的是 for 加 length，而不是 for...in，正是为了避开属性枚举这条慢路径。

性能对比：for 最快，for…in 最慢

循环本身的开销在数据量小的时候可以忽略，但列表渲染、批量数据处理这类场景动辄上万次迭代，差异就会被放大。当年各浏览器上的实测结论相当一致，量级大致如下：

循环方式 相对开销 说明
for 缓存长度 基准（最快） 一次取 length，纯下标访问
for 不缓存长度 略慢 每轮重新读 length
forEach 明显慢于 for 多一层函数调用与回调
for...in 最慢 需枚举属性名、查原型链

实测的方法也值得一提。当年没有统一的基准工具，常见的做法是取一个上万元素的数组，循环执行取对数或者求和，用 Date.now() 或 performance.now()（后者 2013 年部分浏览器已支持）取差值。需要注意的是必须做多轮取平均，单次结果受 GC 影响极大；也要注意引擎的 JIT 预热，第一轮往往明显慢于后续轮次。

除了循环体本身，还有两类开销经常被算到循环账上：一类是循环体内的 DOM 读写（每次读写都可能触发重排），一类是循环体内创建闭包（每次迭代都新建函数对象）。前者应该合并到循环外批量处理，后者在有性能要求的场景下应避免在循环里 return function。

迭代中修改数组：一个隐蔽的坑

在遍历过程中增删数组元素，结果往往和直觉不符，因为下标是动态变化的。

jQuery 的 each：另一套遍历体系

jQuery 提供了 .each() 与 $.each()，与原生循环是两套东西。它们在 DOM 集合遍历上有便利性（this 指向当前元素、内部做了兼容处理），但代价是函数调用开销和无法 break（只能 return false）。

值得强调的是：.each() 里 return false 才能中断，break 关键字写在回调里只会跳出回调自身，这是高频错误。至于 $.each() 与 $().each() 的定位差异、实现细节和性能取舍，本文只做引用式对比，已在《jQuery 的 each 与 $.each 的区别》里单独展开，这里不重复。

另外补充一句 jQuery 遍历与原生循环的关系：jQuery 1.9 的 jQuery.each 内部就是 for 循环加回调，所以它在 DOM 集合上的便利不等于性能优势。批量处理几千个节点时，先取原生数组再走原生循环往往更快——把 jQuery 集合转成原生数组在当年用 $.makeArray() 或者直接遍历 this 都可以做到。选型的依据应该是代码可读性与团队习惯，性能只在明确的热点路径上才成为理由。

一个综合的选型判断

把上面的讨论收拢成一张表，工程上直接对照着用：

场景 首选 理由
遍历数组，需要中断 for 缓存长度 支持 break/continue，开销最小
遍历数组，纯读取 forEach 无下标噪声，回调签名清晰
遍历对象自身属性 for...in 加 hasOwnProperty 唯一直接可用手段
遍历 jQuery DOM 集合 .each() this 指向元素，链式便利
遍历任意数据（对象或类数组） $.each() 类型自适应
遍历中需要删除元素 for 倒序 删除不影响未访问下标
需要拿到跳出时的索引 for 加标签或抽函数 forEach 无法中断

最后提醒一个与循环无关但经常一起出现的写法：arguments 对象是类数组不是数组，它没有 forEach。ES5 时代想对 arguments 用数组方法，只能 Array.prototype.slice.call(arguments) 转成真数组，或者老老实实写 for。

小结

ES5 时代的循环选型可以压缩成几条规则：数组遍历首选缓存长度的 for，热路径和大数据量下它的开销最小；for...in 只服务于对象，且必须加 hasOwnProperty 过滤，同时不能依赖它的枚举顺序；forEach 换来的是无副作用的表达力，代价是回调开销和无法中断。迭代中修改数组要倒序或先筛选再删除，splice 混用正序索引几乎必然漏元素；多层嵌套优先抽函数返回，标签 break 能用但别滥用。把这些边界想清楚，循环就只是工具而不是 bug 来源。
