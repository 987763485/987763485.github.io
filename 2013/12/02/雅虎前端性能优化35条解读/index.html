雅虎前端性能优化 35 条解读

2007 年 Steve Souders 在雅虎内部总结出 14 条前端性能规则，次年整理成书《High Performance Web Sites》（中文版《高性能网站建设指南》），配套的 YSlow 插件把这些规则变成可打分的清单。2009 年《Even Faster Web Sites》出版，规则扩充到 23 条，之后社区把两本书的内容合并整理，才有了今天常说的”雅虎 35 条”。三十几条规则听起来像一本厚厚的经书，但如果按主题归类，其实只有七八个核心思想。本文按主题把这 35 条重新组织一遍，每条讲清原理、做法、2013 年的实际价值与注意事项，最后再给一条批判性的视角。

需要先说明的是，这 35 条不是平权的。有些是 2013 年依然收益巨大的主干手段，有些在 HTTP/1.1 时代有效但在新协议普及后会失效，还有些从提出那天起就只对极少数场景成立。如果不分轻重地照单全收，很容易做出”分数很高、体验很差”的页面。YSlow 的评分是加权平均，它本身不告诉你该先做什么——本文想补的正是这个判断。

减少 HTTP 请求

这是整张清单的第一条，也是收益最大、争议最少的一条。背后的机理很直接：每个请求都有固定开销——DNS 查询、TCP 握手、发送请求头、等待响应头、下载、关闭或复用连接。在 2013 年的宽带环境下，一个请求的固定开销常常在几十到几百毫秒，而一个几 KB 的小文件传输只要几毫秒。也就是说，小文件的数量本身就是瓶颈，而不是文件的总大小。

合并文件与 CSS Sprite

做法是把多个 CSS 合成一个、多个 JavaScript 合成一个，把多个小图标拼成一张大图用 background-position 定位。一个页面有二十个社交图标时，二十个请求变成一张图加若干定位，收益立竿见影。

代价是缓存粒度变粗：改一行 JavaScript 就要让整个合并文件失效，用户重新下载全部内容。当年的折中是”基础库单独一份、业务代码一份”，基础库变动少、长期缓存，业务代码频繁更新但体积小。精灵图还有维护成本：加一个图标要重排整张图，所有 background-position 都要跟着改，所以它只适合数量多、尺寸小、长期不动的图标集合。

内联图片与 Data URI

另一个方向是把小图片转成 Base64 直接写进 CSS 或 HTML，省掉请求。Data URI 的代价是体积增大约三分之一，而且无法单独缓存——内联在样式表里的图片，样式表一更新它就得重新传输。所以它只适合极小、极少变化的图片，比如一像素的占位图或几个装饰性圆点。

空 src 与空 href

这一条容易被忽略：<img src=""> 或 <script src=""> 在部分浏览器里会触发一次指向当前页面 URL 的请求。它既浪费请求，又可能造成意外的重复加载。2013 年的实践是在模板渲染时对空值做判断，宁可不输出标签也不要输出空属性。

使用 CDN

CDN 是这条清单里少数”花钱就能见效”的手段。用户与服务器之间的物理距离决定了往返延迟，把资源部署到离用户更近的节点，TTFB 与握手时间都会下降。此外 CDN 还能分担连接建立成本、提供更高的并发能力。

2013 年的实际情况是，国内访问海外 CDN 的收益受运营商线路影响很大，有时并不明显；反过来，静态资源走国内的云存储或 CDN，收益相当稳定。CDN 的收益要用数据说话，不能默认”用了就快”。另一个常被忽略的代价是缓存一致性：CDN 节点上的旧文件需要刷新或指纹化文件名来解决，否则更新后用户拿到的还是旧版本。

缓存：Expires、Cache-Control、ETag

这三条都在解决同一个问题：让二次访问的请求根本不发出去。

Expires 与 Cache-Control

给响应加上 Expires 或 Cache-Control: max-age，浏览器在有效期内直接读本地缓存，零请求零延迟。这是所有手段里性价比最高的一条，因为它把成本转移到了”根本不发请求”。

注意 Expires 是绝对时间，依赖客户端时钟准确；Cache-Control 的 max-age 是相对时间，更可靠。2013 年的通行做法是对带指纹的文件名用超长 max-age，对入口 HTML 用 no-cache 或短 max-age——让”可能变的东西”快速失效，让”不会变的东西”永久缓存。

配置 ETag

ETag 的作用是缓存失效后做一次条件请求，资源没变就返回 304。问题在于，在集群部署下不同服务器算出的 ETag 可能不一致（inode 与时间戳不同），导致同一文件在不同节点上 ETag 不同，缓存判断反复失败。Souders 的建议是在多机部署时统一 ETag 的生成方式，或者干脆去掉 ETag、只靠 Last-Modified。这一条在今天看依然成立，是 35 条里少有的”完全没过时”的条目。

Gzip 压缩

服务器对文本类资源做 gzip，通常能减少 60% 到 80% 的体积。HTML、CSS、JavaScript、JSON、SVG 都是文本，压缩收益极高；而 JPEG、PNG 本身已经是压缩格式，再 gzip 收益甚微，只是白白消耗 CPU。

2013 年的注意点是压缩级别与 CPU 的权衡：级别 1 已经能拿到大部分收益，级别 9 多花几倍 CPU 只多省几个百分点。另外要确认代理与 CDN 没有把压缩后的内容解压再转发，否则用户端拿到的是未压缩版本。

渲染位置：样式表放头部，脚本放底部

这两条是清单里最容易被误读的。它们不是玄学，而是由浏览器的阻塞机制决定的。

外链 CSS 是渲染阻塞资源：没有完整的 CSSOM 就建不出渲染树，建不出渲染树就不能布局绘制。把样式表放在头部，浏览器在解析 HTML 的过程中就把它下载完了，HTML 解析结束时 CSSOM 也已就绪，可以立刻渲染。放到尾部则可能出现”DOM 早解析完了，屏幕还是白的”——浏览器在等一份它本该早就拿到的样式表。

同步脚本则是解析阻塞资源：文档流中的 <script> 会暂停 HTML 解析，因为脚本可能通过 document.write() 改写后续内容。把脚本放到 </body> 之前，脚本执行时首屏 DOM 已经建好，首屏能更早绘制。更好的做法是给脚本加 defer，让它提前下载、DOM 就绪后按顺序执行，既不阻塞解析又保序。

避免 CSS 表达式

这是 35 条里唯一一条今天可以彻底划掉的。CSS 表达式是 IE 特有的私有特性，允许在 CSS 里写 JavaScript 表达式，表达式会在每次重绘时重新求值。

它的性能问题是结构性的：每次重排重绘都要执行一段脚本，页面一复杂就成了死循环。2013 年 IE10 已经不再支持，IE9 也不推荐。现在的做法是用 calc() 或媒体查询完成同样的事。这条规则在今天只剩历史价值，但它留下一个教训至今有效：任何”在样式计算路径上执行脚本”的设计都是危险的。

外链 JS 与 CSS

这条与”减少 HTTP 请求”看似矛盾，其实针对的是不同场景。合并文件减少的是请求数，但它牺牲了缓存复用：一段被三个页面共用的 jQuery 内联进页面，用户访问第二个页面要重新下载一遍。外链的好处是这份文件被缓存后，跨页面零成本。

Souders 的结论是分层的：首页为了首屏速度可以适当内联，但跨页面复用、更新频率低的代码应该外链并配长效缓存。2013 年现实的折中方案是”外链 + 指纹 + 长缓存”，兼顾两者。这一条的坑在于内联的临界值：内联内容多到一定程度，HTML 变大导致缓存失效代价升高，反而不划算。

精简 JS 与 CSS

精简（minify）指去掉注释、空白、换行，缩短局部变量名，在保持语义不变的前提下减小体积。它与 gzip 是叠加关系：gzip 压缩的是重复字符，精简减少了这些重复字符的绝对数量，两者同时做的收益大于单独做任何一个。

2013 年的注意点有两个。第一，精简必须在构建阶段做，线上不要出现未压缩版本；第二，精简会破坏行号与错误堆栈，需要 source map——但 source map 在 2013 年还不普及，所以当年的做法是压缩版与未压缩版并存，调试时临时切回。

避免重定向与移除重复脚本

避免重定向

重定向多一次完整的请求往返。常见诱因包括：域名不带 www 的访问被 301 到带 www、URL 末尾斜杠统一、追踪链接跳转、旧站迁移。有些重定向不可避免，但要控制层数——连续两次以上的重定向会让用户多等几百毫秒。

移除重复脚本

同一份脚本被引入两次，浏览器会下载并执行两遍。执行两遍的后果不只是浪费带宽：绑定一次事件变两次、初始化代码跑两回，可能出现难以排查的重复行为。2013 年的检查手段是在 Network 面板按名称排序看有没有重复项，或者在构建阶段加一个重复检测的规则。IE 有个特殊行为——重复的脚本在某些情况下不会重新执行，但依赖它不可靠，正确做法是根本不要重复引入。

AJAX 缓存与 GET 请求

AJAX 请求同样占用连接、同样有延迟，也应该被缓存。可缓存的 AJAX 响应需要正确的响应头：对确定不变的数据给长 max-age，对可能变化的用 Last-Modified 或 ETag 做条件请求。2013 年常见错误是给动态接口一律加 no-store，结果同一个数据被反复请求。

用 GET 而不是 POST 发 AJAX 也有缓存层面的理由：POST 在语义上是非幂等的，浏览器与中间代理一般不会缓存它。Souders 的建议是，只要不修改数据就用 GET。但要注意 URL 长度限制与不要把敏感数据放查询串里。

DOM 相关：数量、访问、iframe

减少 DOM 元素数量

DOM 节点数直接影响样式匹配与布局的开销。一千个节点和一万个节点不是十倍的差别——影响范围会扩散，某些布局计算可能涉及整棵树。2013 年的经验值是单页 DOM 控制在 1000 到 1500 个以内比较安全，超过就要考虑分页或虚拟列表。

减少 DOM 访问

每次访问 DOM 都有跨引擎的成本。原则是把引用缓存到局部变量，避免在循环里反复查询；把多次修改合并，避免读写交替触发强制同步布局。

减少 iframe

iframe 的代价是双重的：它本身是一次额外请求，而且它是一个独立的文档，有自己的解析与加载流程，即使内容为空也要付出创建成本。2013 年 iframe 的合理用途主要是跨域隔离（如第三方挂件）与沙箱，用它来做普通的内容切分是负优化。

拆分域名与 Cookie

拆分域名

把静态资源放到与主站不同的域名下，好处是请求可以并行（浏览器对同一域名的并发有限制）、请求不带主站的 Cookie。代价同样明确：多一次 DNS 解析，且连接无法复用。2013 年的经验是拆 2 到 4 个域名，再多收益就被 DNS 成本吃掉。

这一条是 35 条里最需要重新审视的。当浏览器对同一域名的并发上限提升、连接复用更充分之后，拆分域名带来的并行收益会下降，而多域名带来的额外 DNS 与连接开销依然存在。到了更晚的多路复用协议普及之后，拆分域名的收益进一步缩小，甚至拆成更多小文件反而更利于缓存粒度。所以这条规则的正确态度是：在它成立的环境里用，并随时准备在新的网络条件下重新评估。

减小 Cookie 与无 Cookie 域名

Cookie 会附加在同域名的每个请求上，包括图片与样式表。一个 4KB 的 Cookie 在一百个静态请求上就是 400KB 的无效传输。做法是保持 Cookie 精简，只存必要信息，并把静态资源放到无 Cookie 的独立域名下。2013 年的检查方法很朴素：在 Network 面板看静态资源的请求头里有没有 Cookie。

图片优化

图片通常是页面里最大的资源，这一组的收益往往最直接。

优化图片

选对格式比压缩更重要：照片用 JPEG，纯色与线条图形用 PNG-8 或 GIF，需要透明用 PNG-24 或 PNG-8。去掉图片里冗余的元数据、用工具重新压缩，常常能在不损失可见质量的前提下减少 20% 以上。2013 年的工具链有 ImageOptim、jpegoptim、pngcrush 等。

优化 CSS Sprite

精灵图本身已经是合并请求的手段，”优化”指的是横向排列而非纵向排列（横向的文件体积更小）、把颜色相近的图标放在一起（调色板更小）、只把真正需要合并的小图放进去。不要把不需要合并的大图硬塞进精灵图，那会让首屏被迫下载一张大图。

不要在 HTML 中缩放图片

用 width 与 height 属性把一张 500 像素的图显示成 100 像素，浏览器下载的是完整尺寸，显示时再缩小。这既浪费带宽又浪费解码与缩放的计算。正确做法是让图片的原始尺寸接近显示尺寸。

但这条规则在响应式设计兴起后需要修正。2013 年正是响应式布局快速普及的阶段，同一张图可能在不同屏幕上显示成不同大小，服务端无法预知。当年的解法是：为最常见的显示尺寸输出图片，其余情况接受一定缩放；或者准备多套尺寸按屏幕密度选择。把”绝不缩放”当成铁律，在响应式场景下会导致要么下载过大图片，要么输出过多尺寸。这条的正确理解是”避免无意义的大幅缩放”，而不是”任何缩放都禁止”。

favicon.ico 小且可缓存

favicon.ico 有个特殊的坑：即使页面没有引用它，浏览器也会请求 /favicon.ico。如果这个文件不存在，会多一次 404；如果它很大，就白白多下载一次。做法是放一个几 KB 的 ico，并配长缓存。

保持组件小于 25KB

这条与 iOS 的 Packet Capture 有关：某些旧版 Safari 会缓存小于 25KB 的响应。在今天看这条基本失效，但它背后的思想仍然有效——小响应更容易被缓存与快速传输。25K 这个具体数字不必遵守。

打包组件为复合请求

这是 2013 年比较边缘的一条，指用 multipart/x-mixed-replace 之类的技术把多个组件打成一个响应。它的兼容性与调试成本都很高，实际项目里极少采用。列在这里主要是为了完整性。

尽早刷新缓冲区与 POST

尽早刷新缓冲区

服务器不要等整个页面渲染完再输出。先输出 HTML 头部并 flush，浏览器就能立刻开始解析、下载样式表与脚本。这样做的收益在头部资源较多时很明显，因为它把”等待服务器渲染”与”浏览器解析”变成了并行的两件事。实现上要求模板引擎支持分段输出，或者至少把静态头部先吐出来。

POST 请求

这条来自 Souders 的观察：POST 请求分两段发送，先发请求头，等服务器确认 100 Continue 后再发请求体，多一个往返。所以页面加载阶段要发的请求尽量用 GET。这一条对图片与样式表这类加载期请求尤其适用，它们天然就该是 GET。

按需加载与预加载组件

这两条是《Even Faster Web Sites》里最重要的补充，目标是把”首屏必需的”和”其余一切”分开。

预加载组件

利用浏览器空闲时间提前下载将来会用到的资源。2013 年的实现思路是在页面加载完成后，用 JavaScript 触发一次隐藏的请求，把下一屏需要的图片或脚本先拉进缓存。

它的坑是不要过早、过多地预加载，否则会与首屏资源争抢带宽，反而拖慢当前页面。

按需加载组件

与预加载相对，按需加载是”用到了才取”。折叠面板的内容、弹窗里的表单、第二屏之后的图片，都可以等用户交互或滚动到位再加载。2013 年的典型做法是用 data-src 占位，页面就绪后替换真实地址。

这两条合起来就是后来”首屏优先”思想的雏形，也是 35 条里最有生命力的部分之一。

避免 404

404 响应本身不大，但它是一次完整的请求往返，还会伴随错误处理成本。更麻烦的是 404 页面通常不带缓存头，每次访问都要重新请求。2013 年的检查手段是在 Network 面板筛选状态码，把 404 的资源从页面里清掉。常见来源是失效的图片地址、拼错的路径、被移除却仍被引用的脚本。

小结与批判性视角

把 35 条按 2013 年的实际收益排序，大致是这样：缓存相关（Expires、ETag、AJAX 缓存）几乎零成本且收益稳定；减少请求与压缩在小文件多的页面上收益巨大；渲染位置（CSS 头部、JS 底部）是理解型优化，做对了一次性受益；图片优化收益直接但需要工具与流程配合；CDN 花钱就能见效但需按线路实测。

需要警惕的是，有几条在 2013 年已经显露出局限。”不要在 HTML 中缩放图片”在响应式设计普及后需要重新解释，绝对化执行会导致下载过大图片或输出过多尺寸。”拆分域名”的收益受浏览器并发策略与协议演进影响，多域名带来的额外 DNS 与连接开销是确定存在的成本，一旦并行收益下降，这条就从正优化变成负优化。”保持组件小于 25KB”依赖特定旧版浏览器的缓存行为，在今天已经失效。”打包组件为复合请求”兼容性与调试成本过高，极少被采用。CSS 表达式则已经被标准与浏览器双双淘汰，只剩历史价值。

这些”过时”的条目并不影响整张清单的价值。它们共同的问题不是”错了”，而是”被当成了不需要判断的铁律”。性能规则全部是有前提的：它成立的条件写在第 N 条旁边的小字里。YSlow 给的是 checklist，不是答案；分数是体检报告，不是治疗方案。真正该记住的是背后那几条不随时代变化的原理——减少往返、减少字节、缩短阻塞、让缓存生效、把带宽让给首屏。

小结

雅虎 35 条的本质是把浏览器加载页面的过程拆成可干预的环节，再对每个环节给出手段。它们跨越了近十年依然大部分有效，说明底层机理——网络往返、固定开销、阻塞关系、缓存复用——并没有变。变的是各项收益的权重：协议演进改变了合并与拆分的平衡，响应式设计改变了图片策略，缓存成熟度改变了 ETag 一类规则的必要性。读这份清单的正确方式是先理解机理，再看它在自己项目里是否成立，而不是照着清单打勾。把 YSlow 当成体检报告，把 DevTools 与 WebPageTest 当成诊断依据，优化才走得远。
