CSS3 box-sizing 与全局重置样式

本文属于《HTML 与 CSS》第 17/62 篇
上一篇系列目录下一篇

刚学 CSS 那会儿，我一度坚信 width 就是”这个盒子有多大”。直到某次给一个定宽 div 加了 10 像素内边距，整个布局横向错位、右侧元素被挤下去，才明白这个信念在 IE 和非 IE 浏览器里各对一半。这篇复盘 box-sizing 是什么、它怎么改变了我写样式的方式，以及全局 border-box 重置到底该不该上。

一个真实的错位现场

那次的需求很普通：内容区定宽 960 像素居中，里面左右两个子容器各占一半，各自加 16 像素内边距让文字不贴边。我按 CSS 2.1 的标准写下：

标准浏览器里，width: 480px 只算内容宽，加上左右各 16 像素的 padding，每个子容器实际占 512 像素，两个就是 1024 像素，比父容器还宽，第二列被挤到下面去了。而在 IE6 的怪异模式下，width 把 padding 和 border 一起算进去，每个子容器实打实占 480 像素，两个正好 960 像素，布局反而是”对的”。

同一个样式表，两种浏览器给出两种结果，而 IE 那个结果恰好更符合我的直觉。这件事让我郁闷了很久，后来才搞清根源：盒模型本来就有两套。

两套盒模型与 box-sizing 的由来

W3C 标准（CSS 2.1）规定，width 和 height 只作用于内容区（content）。你设置的 width: 480px 之外，还要再加上 padding 和 border，才得到元素在页面上实际占据的宽度。这套模型叫 content-box，即”内容盒”。

IE 在怪异模式（quirks mode）下用的是另一套：width 和 height 包含内容、内边距和边框，称为 border-box，”边框盒”。这套模型其实是 IE5.5 及更早版本的实现，IE 的渲染引擎在标准出现之前就已经这么工作了很久，为了不破坏存量页面，就保留给了没有 doctype 或使用旧 doctype 触发的怪异模式。

为什么有人想要 border-box

border-box 最大的吸引力是”所见即所得”。设置 width: 50% 的两个子元素，不管各自加了多少内边距，加起来永远正好是父容器的 100%，不会出现”百分比加像素导致溢出”的尴尬。

这对响应式布局是质变。content-box 下，width: 50% 的列只要加一点 padding 就溢出，你必须么改用 calc()、么把 padding 挪到子元素上、么手动扣宽度，怎么都不如 border-box 自然。

第二个场景是表单控件。input、textarea、select 这些元素，浏览器默认给了一套自己的 padding 和 border，而且不同浏览器的默认值还不一样。用 content-box 给它们统一 width: 200px，实际宽度每个浏览器都不一样；改成 border-box 并显式设定宽高，各浏览器就一致了。

全局重置：从 * { margin: 0; padding: 0 } 说起

既然 border-box 这么好，很自然会想到：干脆全局都设上。这就是 * { box-sizing: border-box; } 的由来。但它和另一个更古老的重置——* { margin: 0; padding: 0 } ——是同一条思路的延伸，所以踩的坑也差不多。

那条古老的重置写法简单粗暴：把所有元素的内外边距清零，消除浏览器默认样式的差异。它的好处确实存在：各个浏览器的 body 默认 margin: 8px、h1 到 h6 各有各的上下边距、ul 有左缩进，清零之后所有元素都站在同一起跑线上，写起布局来心里有数。

但它的问题在项目一大就暴露：

第一，杀伤面太大。* 匹配所有元素，包括你不会去设置样式的那些。表单控件被清零 padding 之后高度变得难以预测，button 的内边距没了之后文字几乎贴边，每次都得手动补回去。

第二，可访问性受损。outline 有时也会被顺手清零，键盘导航的焦点框消失， Tab 遍历时完全看不到焦点在哪。这是最该被批评的一点。

第三，影响性能。* 是通配选择器，浏览器要从最右侧开始匹配，遍历所有元素做判断。页面元素上千时，这个开销并非为零，尽管绝对值不大。

第四，语义丢失。ul 的左缩进不只是为了好看，它承担了”这是列表”的视觉暗示。清零之后所有列表都变成一条条平铺的文字，用户根本看不出结构。

于是有了两个改进方向。一是 Eric Meyer 的 reset.css，他在 2007 年到 2008 年间整理的这份重置表针对具体元素逐条清零，比 * 精准得多，一度是业界标配。二是 Normalize.css，2012 年 6 月 Nicolas Gallagher 和 Jonathan Neal 发布，它换了个思路：不清零，而是把各个浏览器的默认样式统一成一套合理的中间值，同时保留有用的默认语义。比如它会保留 button 可点击的外观，会修正 sub/sup 不影响行高的老问题。

box-sizing 的全局重置和上述争议有个关键区别：它不改任何视觉默认值，只改盒子的计算方式。所以它比 * { margin: 0; padding: 0 } 温和得多，这也是它当年能被迅速推广的原因。

全局 border-box 的利与弊

把它作为项目默认方案的收益是实打实的：

  • 写百分比宽度时不用心算 padding，两栏、三栏、栅格都变直观。
  • 表单控件尺寸可控，跨浏览器一致。
  • 配合固定高度的容器，内容不会因为加了 padding 而被撑高——这是很常见的”为什么我的盒子变高了”的答案。

但它并非没有代价，有几条必须提前知道。

第一，它和”某些依赖 content-box 的组件”会冲突。当年的一些第三方插件、老的栅格框架（比如 Bootstrap 2 的某些部分）默认按 content-box 计算，全局 border-box 之后它们的宽度可能对不上。所以全局重置最好写在最前面，让后续组件有机会覆盖，或者给特定容器单独设回 content-box。

第二，min-width/max-width 与 border-box 的交互要留意。max-width 限制的是边框盒的总宽，如果内容本身需要的最小宽度超过这个上限，在 border-box 下内容区会被挤压，可能比 content-box 下更早出现内容溢出。

第三，绝对定位元素的包含块计算会受影响。绝对定位元素的 left/right/top/bottom 定位和 padding 有关，border-box 下包含块是父容器的 padding 盒内侧还是 border 盒内侧，行为有差异，做覆盖层、弹层时要实测。

第四，可读性的隐性成本。新人接手一个全局 border-box 的项目，看到 width: 100% 加 padding: 20px 时，如果不知道全局重置，会误以为内容区变窄是 bug。所以要么在项目文档里写明，要么用一个专门的 class 表达意图，而不是全靠全局。

小结

box-sizing 不是新语法糖，它给了你选择盒模型的权利：content-box 忠于 CSS 2.1，border-box 更接近直觉也更适合响应式。当年 IE 的怪异模式让 border-box 背上过”非标准”的名声，但标准模式下的 IE6/7 早已遵循 content-box，把两者混为一谈是常见的误解。全局 border-box 重置比 * { margin: 0; padding: 0 } 温和得多，值得作为默认，但要注意与旧组件的冲突、min/max-width 的交互以及绝对定位包含块的变化。选全局还是按需，取决于项目里第三方代码的比例——笔者的经验是：自己的代码占主导，就全局；要集成一堆老插件，就按需。
