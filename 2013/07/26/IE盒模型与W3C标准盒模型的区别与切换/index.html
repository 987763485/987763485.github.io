IE 盒模型与 W3C 标准盒模型的区别与切换

本文属于《HTML 与 CSS》第 18/62 篇
上一篇系列目录下一篇

盒模型是 CSS 里第一个必须弄明白的概念，也是当年最容易讲错的一个。很多人笼统地说”IE 用 IE 盒模型，其他浏览器用标准盒模型”，这句话在 2013 年已经过时了大半。这篇把两种盒模型的区别、一个流传甚广的误解、box-sizing 的用法与切换、以及百分比布局下的实际差异逐个讲清，全部配可复现的例子。

两种盒模型到底差在哪

一个元素在页面上占据的空间，可以拆成四层，从里到外依次是：内容区（content）、内边距（padding）、边框（border）、外边距（margin）。两种盒模型的分歧只在于：你写的 width 和 height，算到哪一层为止。

W3C 标准盒模型（CSS 2.1 规定），对应 box-sizing: content-box：width 与 height 只描述内容区的尺寸。元素实际占据的宽度是内容宽加上左右 padding，再加上左右 border。

IE 盒模型，对应 box-sizing: border-box：width 与 height 描述的是从内容区外沿到边框外沿的整个区域，padding 和 border 都被包含在内，超出部分由内容区向内压缩。

模型 width 的含义 内容区宽度 实际占据宽度
content-box（W3C 标准） 仅内容区 200px 200 + 20 + 10 = 230px
border-box（IE 怪异模式） 含 padding 与 border 200 - 20 - 10 = 170px 200px

注意 border-box 下内容区被压到了 170px——这就是”加了 padding 之后文字变挤”的原因。反过来说，如果你希望内容区保持 200px 不变，在 border-box 下就得把 width 写成 230px。

margin 不参与这个计算，两种模型下 margin 都加在盒子外面，所以上表的”实际占据宽度”不含 margin，元素在布局里占用的总空间还要再加上左右 margin。把这条链路画出来更直观：

    C --> D[实际宽度 = width + padding + border]
    B -->|border-box| E[width 圈住内容区加 padding 加 border]
    E --> F[实际宽度 = width]
    F --> G[内容区被向内挤压]

    G --> H

一个必须澄清的误解

流传最广的错误说法是：”IE 用 IE 盒模型，Firefox 和 Chrome 用标准盒模型。”这句话在 2003 年前后基本成立，但放到 2013 年是完全错的。真实情况要按渲染模式分开说。

IE 从 6 代开始引入”渲染模式”（rendering mode）的概念，由文档首行的 doctype 决定：

  • 写了标准的 doctype（如 HTML4 Strict、XHTML 1.0 Transitional）或 HTML5 的 <!DOCTYPE html>，IE6/7/8 进入 standards mode（标准模式），此时它们遵循的已经是 W3C 标准盒模型，width 只算内容区。
  • 没有 doctype，或者使用 IE5 时代那种旧 doctype（比如 <!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 4.01 Transitional//EN"> 之前不带 URI 的写法），IE 退到 quirks mode（怪异模式），此时才使用 IE 盒模型。

IE9 及其后更进一步，document.documentMode 可以反映当前渲染模式版本号，标准模式下为 9，怪异模式下为 5；document.compatMode 则是更通用的判断，'CSS1Compat' 表示标准模式，'BackCompat' 表示怪异模式。

所以”IE 等于 IE 盒模型”这个说法的错误在于：它把”渲染模式的选择”错安成了”浏览器的品牌”。同一个 IE8，在标准模式下是 content-box，在怪异模式下是 border-box；而 IE6/7 在标准模式下同样遵循 W3C 规范。真正决定用哪套模型的，是文档的 doctype。

这个误解的代价是实打实的。当年最常见的 bug 是：本地开发时 HTML 文件漏写了 doctype，在 IE 下调样式一切正常（怪异模式，border-box，宽度直觉符合）；发布时模板头部补上了 doctype，IE 立刻切到标准模式，所有定宽盒子集体变宽 20 到 40 像素，两栏布局直接错位。开发环境查不出来，因为本地文件恰好没有 doctype。规避方法很简单也很重要：任何 HTML 页面第一行必须是 <!DOCTYPE html>，让所有浏览器统一走标准模式。

全局重置 border-box：利弊与边界

既然 border-box 更符合直觉，很自然的想法是全局重置：

这条规则的好处在百分比布局里体现得最充分。content-box 下，两个 width: 50% 的列只要其中一列加了 padding 就会溢出父容器，你只能改用 calc()、把 padding 移到子元素，或者手动把宽度扣成 48%。border-box 下完全不需要这些周折，width: 50% 就是实实在在的半宽，padding 向内挤压内容。

但全局重置有几处必须留神。

第一，与第三方组件的冲突。2013 年不少现成的栅格和 UI 组件默认按 content-box 设计，全局切到 border-box 后，它们内部按”宽度加 padding”推算的逻辑会失效。稳妥做法是把全局重置放在样式表最前面，让后续组件有机会覆盖；或者只对自有布局类启用。

第二，绝对定位的包含块计算受影响。绝对定位元素相对最近的定位祖先定位时，left/top 的参照与祖先的 padding 边界有关，border-box 下的表现与 content-box 有差异。做下拉菜单、浮层这类覆盖元素时，必须实测而不是凭推理。

第三，min-width、max-width 的行为。这两个属性限制的是边框盒的外沿尺寸，border-box 下如果内容本身需要的最小宽度超出限制，内容区会被压缩，可能比 content-box 更早出现内容溢出。

第四，与图片的交互。img 元素设置 width: 100% 时，content-box 下图片可能因 padding 溢出容器，border-box 下则会被压扁或裁剪，视觉表现不同，需要配合 max-width: 100% 一起处理。

小结

两种盒模型的差别只在 width/height 算到哪一层：content-box 只算内容，border-box 把 padding 与 border 一起算进去。请记住”IE 等于 IE 盒模型”是误解——IE6/7/8 在标准模式下早已遵循 W3C 规范，只有怪异模式才用 IE 盒模型，而触发怪异模式的钥匙是 doctype 的写法。box-sizing 让我们可以主动选择模型，全局 border-box 在百分比布局和响应式场景收益明显，但要留意第三方组件、绝对定位包含块和 min/max-width 三处边界。实践中更稳妥的是先全局写 <!DOCTYPE html> 统一渲染模式，再按项目情况选择全局切换或按需切换。
