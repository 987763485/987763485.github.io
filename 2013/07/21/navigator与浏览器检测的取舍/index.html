navigator 与浏览器检测的取舍

判断”用户用的是什么浏览器”这件事，看起来是入门第一课，实际做起来却处处是坑：UA 字符串会骗人，版本号语义混乱，同一款浏览器在不同平台上的标识还不一样。更麻烦的是，你真正想知道的其实不是浏览器名字，而是”它支持不支持某个特性”。这篇把 navigator 的各个属性、UA 的伪装史、特性检测的原则以及当年的几种实践方案一次讲清。

navigator 对象有哪些属性

window.navigator 挂着一组与浏览器本身相关的只读属性。在 Chrome 28 的控制台里把它们打印出来，大致是下面这样：

逐个说明它们的含义和不可靠之处。

userAgent 是最长也最常被解析的那个字符串，里面塞了浏览器名、渲染引擎、版本号和操作系统信息。它的问题不是信息不全，而是信息太”礼貌”——为了不被网站挡在门外，几乎所有浏览器都在里面冒充别人，下面单独讲。

appName 在几乎所有现代浏览器里都返回 Netscape，包括 IE11 之前的 IE、Chrome、Firefox、Safari、Opera。这个属性已经彻底失去意义，不要用它做任何判断。

appVersion 名义上是浏览器版本号，实际上各浏览器的取值规则各不相同，多数只返回一个类似 5.0 (Macintosh) 的字符串，数字部分和真实版本对不上。真正要拿版本号，应该从 userAgent 里正则提取。

platform 返回操作系统平台，常见值有 Win32、MacIntel、Linux x86_64、iPhone、iPad 等。它比前两个属性靠谱一些，做平台相关的判断（比如提示用户下载对应客户端）时可用，但同样可以被伪造，而且 32 位与 64 位系统的 Win32 是同一个值，粒度很粗。

language 返回浏览器界面的首选语言，通常是 zh-CN、en-US 这样的 BCP 47 标签。注意它反映的是用户设置的界面语言，不是页面内容的语言——页面语言要看 document.documentElement.lang。做多语言切换时，这个属性适合作为初始默认值，之后应该交给用户选择并持久化。

除此之外还有几个当时可用的属性：cookieEnabled 判断 cookie 是否启用；onLine 反映网络状态，但这个值只表示”浏览器是否处于离线模式”，不代表网络真的通；plugins 是已安装插件的数组，在检测 Flash 版本时用过，2013 年正逐渐失去意义。

UA 字符串的伪装史

UA 字符串之所以长成现在这副模样，完全是一段”谁都不肯认输”的历史。

最早 Netscape Navigator 的用户代理是 Mozilla/2.0，后来加上了平台和加密强度信息。微软的 Internet Explorer 出现后，用自己的格式 Mozilla/2.0 (compatible; MSIE 3.0; Windows 95)——注意它仍然以 Mozilla/ 开头，这是 IE 冒充 Netscape 的起点。原因是当时不少网站只给 Mozilla 开头的浏览器提供完整内容，IE 为了不被当成二等公民，主动戴上了 Mozilla 的面具。

这个面具一戴就是十几年，而且越传越复杂。Netscape 开源成 Mozilla 项目后，Gecko 渲染引擎诞生，Firefox 的 UA 是 Mozilla/5.0 (Windows; U; Windows NT 5.1; rv:1.8) Gecko/20051109 Firefox/1.5，里面明确声明自己是 Firefox。

苹果推出 Safari 时，UA 长这样：Mozilla/5.0 (Macintosh; U; PPC Mac OS X; en) AppleWebKit/418 (KHTML, like Gecko) Safari/417.8。它基于 KHTML 分支出来的 WebKit，但因为太多网站用”含 Gecko 就高级特性全开”的方式做判断，Safari 只能写上 KHTML, like Gecko 来冒充分友人。

Google Chrome 2008 年发布，UA 同样以 WebKit 为核心，于是它把 Safari 的那套结构照抄了一遍：Mozilla/5.0 (Windows NT 6.1) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/28.0.1500.71 Safari/537.36。这就是 Chrome 冒充 Safari 的由来——为了通过那些”检测到 Safari 就给新特性”的站点。

Opera 最有意思。它长期使用自己的 Opera/9.80 (...) 格式，但同样遭遇了”不是 Mozilla 就被降级对待”的问题。Opera 的应对是提供可切换的 UA 身份，菜单里可以让它自称 IE 或 Firefox。到了移动端的 UC 浏览器（UCBrowser），为了在只认 WebKit 的站点上拿到完整功能，它的 UA 里既写了 UCBrowser/8.x，又保留了 Safari 的 AppleWebKit ... Safari 尾巴，形成”UA 里出现多个浏览器名”的混合形态。

把这段历史抽象一下，就是一条层层套娃的链：

flowchart TD
    A[Netscape 自称 Mozilla] --> B[IE 冒充 Mozilla]
    B --> C[网站按 Mozilla 分支放行]
    C --> D[Firefox 表明真实身份 Gecko]
    D --> E[Safari 冒充 KHTML like Gecko]
    E --> F[Chrome 冒充 Safari]
    F --> G[UC 等移动浏览器同时保留多份身份]
    G --> H[解析 UA 变成猜谜游戏]

结论很直白：UA 字符串是一个历史遗留的协商机制，不是一份可信的规格说明。任何解析它的代码，都是在赌对方这次还愿意继续伪装。

UA 检测为什么不可靠

除了伪装，UA 检测还有几个结构性的问题。

第一，粒度错位。你想知道的是”支不支持 border-radius“，UA 给你的却是”Chrome 28”。同一个 Chrome 28，桌面版和 Android 版能力并不完全一致；而版本号 28 在不同产品线里也毫无可比性。

第二，维护成本随时间线性上升。每出一个新浏览器、新版本、新平台（2013 年前后正是 iOS 6、Android 4.x、Windows Phone 8 集中涌现的时期），UA 规则就要补一条。更糟的是 UA 格式本身会变：IE11 之后微软调整了 UA 的构造方式，大量按老格式写的正则直接失效，而那时项目已经上线，谁也不敢随便动这段代码。

第三，伪装是双向的。不仅浏览器会伪装，用户和运营商也会。UC 浏览器的”极速模式”与”兼容模式”UA 不同，某些运营商还会在 UA 后面追加自己的标识。按 UA 判错的成本，最终都落在用户侧。

Modernizr：把特性检测做成基建

手写检测函数可行，但每个项目都写一遍、还容易漏掉前缀变体，于是 Modernizr 应运而生。它 2009 年创建，到 2013 年已经成为最常用的特性检测库之一，Bootstrap 3 等主流框架直接把它作为依赖。

需要提醒的是，Modernizr 检测的是”特性是否存在”，不是”行为是否正确”，前面说的问题它同样存在。

条件注释的局限要记住：它从 IE10 起被彻底废弃，微软明确宣布不再支持。所以在 2013 年的项目里，条件注释只能作为兼容 IE9 及以下的临时通道，代码里要给它的失效留好退路。另外它是 HTML 层的机制，JS 里无法直接读取条件注释的结果。

JS 侧判断 IE 版本，还有一个比解析 UA 更可靠的属性：document.documentMode。它在 IE8 及以上返回当前文档实际使用的渲染模式版本号（5 表示怪异模式，8、9、10 分别对应 IE8/9/10 的标准模式），非 IE 浏览器里是 undefined。

它比 UA 解析准的地方在于：用户可能把 IE9 的文档模式切成 IE8，UA 仍然是 IE9，而 documentMode 会如实反映成 8。做能力规避时，你关心的正是”这个页面实际按什么模式渲染”，所以 documentMode 更贴近事实。当然，它依然只能用于 IE，且同样只回答身份不回答能力。

适合能力检测的场景——判断单个特性的有无，如 border-radius、canvas、placeholder、localStorage。这是绝大多数情况，应该占代码里判断逻辑的九成以上。

适合浏览器检测的场景——只有三类。

第一，规避已知的浏览器缺陷。比如旧版 Android 浏览器的 position: fixed bug、IE8 的 getComputedStyle 个别属性返回空值。这些缺陷特性检测测不出来，只能按版本规避，并且要写清注释和规避的版本范围。

第二，版本号本身是业务信息。比如统计报表里要区分客户端分布，或者提示”您的浏览器版本过低，建议升级”，这时要的就是版本，不是能力。

第三，兜底兼容整个渲染模式。比如确认是否处于 IE 怪异模式（无 doctype 或旧 doctype 触发），用 document.documentMode === 5 或 document.compatMode === 'BackCompat' 判断，比解析 UA 直接得多。

小结

navigator 的各个属性里，userAgent 信息最全也最不可信，appName、appVersion 基本已废，platform 和 language 粒度粗但可作默认值。UA 字符串是一部浏览器互相冒充的历史，IE 冒充 Netscape、Chrome 冒充 Safari、UC 同时保留多份身份，解析它本质是在赌伪装规则不变。因此默认应该做特性检测，Modernizr 把这件事做成了基建，条件注释和 documentMode 则是 IE 专属的辅助通道，且条件注释自 IE10 起已废弃。浏览器检测只留给规避已知缺陷、统计版本和判断渲染模式这三类场景。jQuery 1.9 移除 $.browser 正是这条原则的官方背书，升级时优先把 UA 判断改写成能力判断，而不是急着找回一个替代的 UA 解析库。
