jQuery 性能优化实践

jQuery 把 DOM 操作简化成一行链式调用，代价是把一堆看不见的工作藏了起来。项目小的时候感受不到，等页面上的元素多起来、交互密起来，某些操作明显卡顿，才回头审视自己写的 jQuery。这篇从选择器、DOM 读写、事件绑定三个层面，把当年实际项目中见效最快的几条优化做法整理出来，也顺带说清什么时候该退回原生写法。

优化的前提：知道 jQuery 替你做了什么

每写一次 $('.item')，jQuery 内部大致走这几步：解析选择器字符串，如果带 class 或标签名就调用浏览器原生的 querySelectorAll，拿到节点列表后包成 jQuery 对象，还要做去重和顺序处理。如果选择器里用了 :visible、:eq()、:first 这类 jQuery 扩展伪类，就没法走原生接口，得先在 jQuery 内部用 Sizzle 引擎逐节点过滤，开销陡增。

flowchart TD
    A[调用 $ 选择器] --> B{是否原生可解析}
    B -->|是| C[走 querySelectorAll]
    B -->|否| D[先用原生取出候选集]
    D --> E[Sizzle 逐节点过滤]
    C --> F[包装为 jQuery 对象]
    E --> F
    F --> G[返回可链式操作的对象]

理解了这条链路，优化方向就明确了：让每一次 $() 都尽量短、尽量少、尽量复用。

选择器：能用 ID 就别用 class

jQuery 官方文档当年就把选择器性能写成了一条经验法则：$('#id') 最快，因为它内部直接映射到 document.getElementById，复杂度是 O(1)。$('.class') 和 $('tag') 在支持的浏览器里最终都落到 querySelectorAll，属于浏览器优化的原生查询，也不慢。真正慢的是 $('.a div.b input') 这类多层后代选择器，尤其是右端是标签名加 class 的组合，浏览器要从右往左匹配，逐个候选节点回溯父链。

DOM 读写：合并写入，减少回流

jQuery 的 .css()、.attr()、.addClass()、.html() 这些方法，单次调用都可能触发样式或布局的重新计算。连续调用十次，浏览器未必会合并成一次回流，尤其是中间夹着读取操作时。

append() 接受数组，这是 jQuery 批量插入的标准姿势。如果要插入的内容是原生 DOM 节点，用 document.createDocumentFragment() 作为中转容器，原理和效果一致。

这里值得多说一句 jQuery 的 .html() 与 .append() 的选择。.html(str) 会把容器内容整体替换，内部先清空再一次性写入，在”整块重绘”的场景下反而最快；.append() 适合增量追加。但 .html() 会丢掉容器上原有的子节点所绑定的事件和 jQuery 数据，如果这个容器下有会复用的交互元素，清空重写就得重新绑定。所以更稳的做法是构建字符串时把事件需要的上下文信息写进 data-* 属性，插入后用事件委托接管，这样无论 .html() 重写多少次，交互都不丢。

另一个容易忽略的点是读取布局属性。jQuery 的 .width()、.height()、.offset()、.scrollTop() 背后都要读浏览器的布局盒数据。读一次就可能把之前所有排队的写操作强制执行掉。所以循环里”写一点、读一点”的写法要避免，改成”先全部写完，最后统一读”。

事件绑定：委托优于逐个绑

但列表是会增删的。每加一行新数据，就要给新的删除按钮再绑一次；删掉一行，jQuery 1.9 里用 .off() 解绑，早于 1.7 的版本还在用 .unbind()。事情一多，绑定和解绑的逻辑散落各处，还容易重复绑定——同一个按钮绑两次 click，点一下执行两遍。

事件委托把这件事简化了：把监听器绑在不会消失的祖先容器上，靠事件冒泡判断真实的目标。

这条写法在 jQuery 1.7 及以上才是标准形式。当年从 1.6 迁移过来的代码要特别注意：.live() 和 .die() 在 jQuery 1.9 里已经被彻底移除，过去用 .live() 实现的委托必须改成 .on(event, selector, handler) 的形式；.delegate() 虽然还能用，但文档已建议统一迁移到 .on()。链式里想回到上一个集合，.andSelf() 同样在 1.9 被移除，取而代之的是 .addBack()。

委托的额外收益是绑定数量下降。一个 200 行的表格，直接绑定要 200 个监听器，委托只需要 1 个。内存和初始化时间都省下来了。代价是事件路径变长，冒泡到容器才能触发，深层节点上这点延迟通常可以忽略。

数据存储与集合遍历

$.data() 和 .data() 存在 jQuery 内部的缓存对象里，而 .attr('data-x') 每次都要读 DOM 属性。频繁读同一份数据时，.data() 更快；但要注意 .data() 只在元素首次读取时从 data-* 属性同步一次，之后改了 DOM 属性，.data() 读到的仍是旧值。

另外，jQuery 对象是类数组，可以直接用 [index] 取原生节点，不必 .eq(index) 再包一层。

什么时候干脆别用 jQuery

这一节是选型问题，也是本文最想说的：jQuery 的优势在”批量 DOM 操作 + 兼容性兜底”，而不是所有场景都赢。

场景 建议 理由
按 ID 取单个元素 document.getElementById 省掉选择器解析与包装
简单类名查询 原生 querySelectorAll 现代浏览器都已支持
大量同类操作 jQuery 集合方法 链式与隐式遍历省代码
旧 IE 兼容兜底 jQuery 自己抹平差异成本更高
动画、队列 jQuery 内置实现完善

2013 年的现实是：项目还要兼容 IE8 甚至 IE7，jQuery 依然是性价比最高的选择；但如果某个热路径上只做一次 ID 查询，直接写 document.getElementById('id') 再包成 jQuery 或干脆操作原生属性，都比 $('#id') 更直接。把 jQuery 用在真正复杂的操作上，简单的查询交还原生，是当年项目里最实用的一条混合策略。

和原生 API 的对比也值得量化看一眼。一次 $('#app') 调用，jQuery 要做选择器解析、原生查询、结果包装，还要挂上内部的数据缓存结构；一次 document.getElementById('app') 只有一步。在页面初始化这种一次性操作上，这点差异可以忽略；但如果写在了 scroll 或 resize 的处理器里，每次滚动都触发，累积起来就不是小数。所以混合策略的一个具体执行标准是：进入高频回调的查询，尽量在初始化时查好并缓存，回调里只碰缓存。

另一个选型参考是当时与 jQuery 同台的轻量库。Zepto 用几乎相同的 API 覆盖了 jQuery 的常用子集，体积小得多，但它对旧 IE 基本放弃，面向的是移动端 WebKit。所以 2013 年做 PC 端项目 jQuery 仍是默认答案，做移动端页面才有理由认真考虑 Zepto。这个判断和上面的性能讨论并不矛盾：先看兼容目标，再看代码体积，最后才是微观的执行效率。

小结

jQuery 优化的核心就三句话：少查询、少回流、少绑定。查询上优先 ID 与 find()，远离扩展伪类，缓存复用 jQuery 对象；DOM 上把写入攒成批量操作，读取放到最后统一做；事件上用委托代替逐个绑定，顺手完成从 .live()/.unbind() 到 .on()/.off()、从 .andSelf() 到 .addBack() 的迁移。最后别忘了选型：jQuery 不是每个场景都该用，混合使用才能在兼容与性能之间拿到平衡。
