减少重排与重绘的实践清单

页面卡顿的原因往往不在 JavaScript 算得慢，而在浏览器一次次重新计算布局。重排（reflow）与重绘（repaint）这两个词，面试题里常考，实际项目里更常被忽视——很多卡顿只要把读写顺序调一下就能消失。这篇把当年项目中真实见效的做法整理成一份清单，按”先认清代价、再动手改”的顺序讲清楚每一条为什么有效。

先说两个名词的来历。Firefox 与 IE 早年的文档里管它叫 reflow，Chrome 团队则习惯叫 layout；repaint 这个名字三家倒是统一。所以看到”布局抖动””回流””重排””layout thrashing”，说的都是同一件事：元素的位置或尺寸信息失效，浏览器必须重新算一遍几何，再重新画出来。

重排与重绘到底差在哪

浏览器把 DOM 与 CSSOM 合成渲染树后，要做两件事：算出每个盒子在屏幕上的位置和大小（布局 / layout，即 reflow），再把像素填上去（绘制 / repaint）。

  • 只改颜色、背景、阴影这类不改变几何的属性，浏览器可以跳过布局，直接重绘。重绘比重排便宜得多。
  • 一旦改了会影响几何的信息——宽高、内外边距、边框粗细、位置、字体大小、显示与隐藏——浏览器必须先重新布局，再重绘，受影响子树大的话整页都要重算。
flowchart TD
  A[修改 DOM 或样式] --> B{是否影响几何信息}
  B -->|否| C[跳过布局 直接重绘]
  B -->|是| D[重新计算布局 即 reflow]
  D --> E[重新绘制 即 repaint]
  C --> F[屏幕更新]
  E --> F

哪些操作会触发重排

触发因素可以分成三类。

第一类是改 DOM 结构：增删节点、移动节点、改文本内容。注意改文本也算——一段文字变长可能把容器撑高，进而推动后面的内容。

第二类是改盒模型与位置相关样式：width、height、padding、margin、border-width、top/left/right/bottom、position、float、font-size、line-height、display。

第三类最隐蔽：读取布局信息。读 offsetTop、offsetLeft、offsetWidth、offsetHeight、scrollTop、scrollLeft、scrollWidth、scrollHeight、clientTop、clientLeft、clientWidth、clientHeight，以及 getComputedStyle() 的几乎所有属性，都会让浏览器交出最新的、准确的值。

准确意味着：如果此前有未应用的样式修改，浏览器必须立刻执行一次同步布局，把值算出来再返回。这个”为了回答你的问题而临时补做一次布局”的行为，就是强制同步布局（forced synchronous layout）。

这段循环每转一圈都触发一次同步布局，圈数就是重排次数。元素一多，主线程被布局计算占满，滚动和点击都会跟着卡。

核心手法：先批量读，再批量写

解法很朴素：把读操作集中在一小段里做完，把结果存下来；把写操作集中在另一段里做完。这样浏览器只需要在写完并 flush 时做一次布局。

这就是所谓”避免布局抖动”（layout thrashing）的标准做法。它的前提是你的逻辑确实允许分离——有些算法必须先知道上一个元素改完后的高度才能决定下一个怎么改，这种情况下要么接受多次布局，要么把计算搬到文档外进行（见下一节）。

一次改多个样式：优先改 class

逐条写 style.width = ...; style.height = ...; style.margin = ...，每条都是一次样式失效。如果这几个属性总是一起变，就把它们写成一个 class，一次切类名搞定。

class 方案还有两个附带好处：样式集中在一处，便于审查与复用；名字有语义，JavaScript 里读起来也清楚。要注意的是，改 class 会触发样式重算，如果新 class 影响的规则很多，样式重算本身也不便宜——但相比逐条触发布局，通常还是划算的。

把影响范围关小：position 与 display:none

重排的代价取决于”失效范围有多大”。浏览器一般只需重算受影响元素的子树，但有些属性会让影响扩散到整页：比如改 body 的字体大小，页面上所有用相对单位的盒子都要重算。

缩小影响范围的两个实用手段：

  • 需要做一连串改动的复杂部件，先 position: absolute 让它脱离文档流。它在布局里是独立的一层，改它不会推动兄弟节点，重排范围被限制在自己身上。改完再视情况恢复。
  • 要做大量改动且不需要让用户看到中间过程时，先 display: none，改完再显示。display: none 之后该元素从渲染树移除，期间的修改完全不触发布局。代价是两次重排（隐藏一次、显示一次），但中间几十步全免费。

注意 display: none 与 visibility: hidden 的区别：visibility: hidden 的元素仍然占据布局空间，盒子照旧参与布局计算，只是不画出来。所以它省的是重绘，不省重排；而 display: none 是连布局一起省掉。想”看不见但仍占位”用前者，想”彻底不参与”用后者。

动画：用 transform 与 opacity

这是当年性价比最高的一条。transform 与 opacity 的动画可以不触发重排，由合成器（compositor）单独处理。

原因在于：top 是布局属性，改它就要重算几何；transform 是在元素已经布局完成之后做的变换，浏览器可以直接把这一层挪个位置、缩放一下，重绘都能省掉大半。Chrome 从某个版本起对 transform 与 opacity 的动画有专门的硬件加速路径，帧率明显更稳。

不过别滥用硬件加速。给大量元素无脑加 translateZ(0) 会把它们都提到独立层，每个层都占显存，层数过多反而掉帧。只在真正需要动画的元素上加。

用 Chrome DevTools 的 Timeline 验证

以上都是规则，落地前最好让数据说话。Chrome 20 之后的 DevTools 里有 Timeline 面板，打开后操作页面，会按帧列出 Layout、Paint、Recalculate Style、Event 等记录。

看两个指标：一是单帧内 Layout 记录多不多，一条记录意味一次重排；二是 Layout 紫色的那段占帧时长比例。如果一次滚动或一次点击出现十几次 Layout，基本就是读写交错的锅。把 Timeline 的柱子拉到最细，定位到触发的脚本堆栈，比猜要快得多。

sequenceDiagram
  participant U as 用户操作
  participant JS as 脚本
  participant B as 浏览器
  U->>JS: 触发事件回调
  JS->>B: 读取 offsetHeight
  B-->>JS: 立即执行同步布局并返回
  JS->>B: 修改 style 属性
  B-->>JS: 标记布局失效
  JS->>B: 再次读取 offsetHeight
  B-->>JS: 再执行一次同步布局
  Note over B: 一帧内多次 Layout

小结

重排的成本来自”失效范围乘触发次数”，优化的全部思路就是缩小范围、减少次数。读写分离、批量插入、改 class、把元素拿出文档流，都是在压次数；关绝对定位、收窄影响子树，都是在压范围；动画改用 transform 与 opacity，是干脆绕开布局这一环。这些规则都不复杂，难的是养成习惯——写循环时先问一句”我在这里读了布局属性吗”。最后提醒一句，所有改动都要以 Timeline 的实际记录为准，感觉不可靠，帧时间才可靠。
