jQuery 插件开发模式与实战

项目里零散的 jQuery 代码攒到一定规模，就会发现「复制粘贴一段 $('#box').click(...)」这条路走不通了：同一个组件要在三个页面用，改一处要翻三处。写插件是唯一的出路。本文以 jQuery 1.9/2.0 为准，把一个插件从最简写法一路演进到可发布的状态，中间涉及的每个模式都说明「为什么需要它」，而不是只给代码。文末会给出一个完整的 tooltip 插件源码。

$.fn.extend 与 $.extend 的区别

这是第一个必须分清的问题，搞错了整个插件的写法就歪了。

$ 是 jQuery 构造函数，$.fn 是它的原型对象，等同于 jQuery.prototype。所以 $.fn.extend 扩展的是 jQuery 实例的方法，也就是能用 $('#id').myPlugin() 这样调用的东西。

$.extend 扩展的是 jQuery 构造函数本身的静态方法，调用方式是 $.myUtil()。jQuery 内置的 $.ajax、$.each、$.data 都在这一层。

立即执行函数与作用域隔离

插件代码不能直接写在全局作用域里，否则变量会污染 window，多个插件之间可能互相覆盖。标准做法是用立即执行函数（IIFE）包起来，并把 jQuery 作为参数传入。

this 与 .each() 迭代

插件方法被调用时，this 指向调用它的 jQuery 对象，里面可能包含零个、一个或多个 DOM 元素。所以插件内部必须用 .each() 遍历，逐个处理。

在 .each() 的回调里，this 是原生 DOM 元素，需要包一层 $(this) 才能用 jQuery 方法。这个坑几乎每个人都踩过。

支持链式调用

链式是 jQuery 的标志性体验，插件必须遵守的约定是：除非插件本身的作用就是「获取数据」，否则一律 return this。

如果插件需要返回值（比如获取输入框内容），就返回那个值，此时不能再链式调用。jQuery 自身的 width() 就是这种「读写双模式」：有参数时设置并返回 this，无参数时读取并返回值。插件也可以照此设计，通过 arguments.length 区分：

参数默认值与 options 合并

插件几乎一定要有配置项。标准模式是定义一个默认配置对象，再用 $.extend 把用户传入的对象覆盖上去。关键点是第一参数传 {}，避免修改到默认对象本身。

为什么必须传 {}？如果写成 $.extend(defaults, options)，defaults 会被直接改掉，第二次调用插件时默认值已经变成上次用户传的值，形成跨实例的状态污染。这是插件开发里最隐蔽的 bug 之一。

用户也可能传入 null 或不传，$.extend({}, defaults, null) 是安全的， jQuery 会忽略 null。但要注意传入数组时 $.extend 的行为与预期不符，配置项不建议用数组。

调用方式变成 $('#btn').tooltip({...}) 初始化，$('#btn').tooltip('show') 调用方法。这个模式在 2013 年的 jQuery 插件里极其普遍，好处是不增加 API 表面积，缺点是字符串参数没有编译期检查，拼错方法名只会静默失败。

私有函数定义在 IIFE 内部，外部拿不到引用，这是封装。如果确实需要暴露调试接口，可以挂到 $.fn.tooltip 上作为静态成员，但不宜滥用。

还有一个细节：trigger() 会同时触发命名空间匹配的事件与不带命名空间的同名事件。如果插件的 trigger('change.myPlugin') 会连带触发外部监听的 change，通常这是期望行为，但有时会造成循环触发，需要在处理函数里判断事件来源。

用 data 存储实例

同一个元素可能被多次初始化插件，或者初始化之后要读取它的配置与状态。把实例数据挂在元素上，jQuery 提供了 .data() 方法，底层用的是 HTML5 的 data- 属性机制（内存中存取，不一定写回 DOM）。

注意 .data() 的键名会自动做驼峰转换：$el.data('my-plugin', 1) 存，$el.data('myPlugin') 取。如果键名带横线，两种写法都能访问到同一个值，但代码里最好统一。

数据存在元素上意味着元素被移除时，引用会随之断开，这是 jQuery 推荐的内存管理方式。但要注意：如果实例里闭包引用了外部的大对象（比如缓存的 DOM 列表），元素删除后这些对象仍可能被引用，销毁方法里应显式清理。

销毁方法

一个完整的插件必须提供销毁。销毁通常包括：解绑事件、删除 data、移除插件添加的 DOM 与样式类、必要时恢复原始内容。

与 jQuery UI widget factory 的对比

如果插件需要管理状态、提供公开方法、支持事件回调，手写 IIFE 的模式很快会变得重复。jQuery UI 1.10 的 widget factory（$.widget）就是为这个场景设计的，2013 年已经成熟可用。

widget factory 的核心约定是：用 $.widget('namespace.widgetname', { ... }) 定义，实例方法写在原型里，this 自动指向当前元素（已包装成 jQuery 对象），this.options 是合并后的配置，this._on() 与 this._trigger() 是内置的事件与回调机制。

widget factory 自带的好处：实例方法自动可用（不需要自己写字符串路由）、配置自动合并、_create 与 _destroy 生命周期明确、事件与回调机制统一、避免重复初始化。代价是引入了 jQuery UI 依赖（约几十 KB），以及一层约定上的学习成本。

选型建议：零依赖、体积敏感、逻辑简单的插件（十几行到几十行）用 IIFE 手写；需要公开方法、复杂状态、多个可复用组件的项目直接上 widget factory，省下的维护时间远大于依赖体积。

小结

jQuery 插件的完整形态由若干独立的小模式叠加而成：IIFE 隔离作用域并固定 $ 引用，$.fn.extend 挂载实例方法，.each() 遍历集合，return this 维持链式，$.extend({}, defaults, options) 安全合并配置，字符串参数路由公开方法，闭包定义私有函数，.on('event.namespace') 与 off('.namespace') 管理事件，.data() 存取实例，destroy() 负责清理。复杂度上升之后换用 jQuery UI 1.10 的 widget factory，用 UMD 模板兼容 AMD，最后补齐压缩、文档、示例与测试。写插件的过程本质上是在回答一个问题：这份代码三年后还有人接手，它是否还能被安全地修改？
