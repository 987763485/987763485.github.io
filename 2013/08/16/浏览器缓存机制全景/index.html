浏览器缓存机制全景

浏览器缓存是前端性能优化里性价比最高的一环：一次正确的配置，能让回访用户的静态资源请求几乎归零；一次错误的配置，能让用户拿着旧版本的 CSS 抱怨样式错乱，而你在本地怎么刷新都复现不了。它横跨 HTTP 协议、服务器配置与前端工程三个层面，任何一环理解不到位，都会以”改了文件不生效”的形式还回来。

这篇按”缓存在哪、由谁决定、按什么规则走”的顺序，把 2013 年主流浏览器与 HTTP/1.1 框架下的缓存机制完整梳理一遍：强缓存、协商缓存、缓存位置、启发式缓存、用户操作的影响、Vary 头、策略设计与服务器配置，最后是那些反复出现的坑。文中所有结论都可以在当年的 Chrome 与 Firefox 上复现。

缓存的两大分类：强缓存与协商缓存

所有 HTTP 缓存手段，最终都归到两类里。

强缓存是”浏览器自己说了算”：响应头里给一个有效期，有效期内浏览器直接用本地副本，一个请求都不发。决定强缓存的头是 Expires 与 Cache-Control。

协商缓存是”浏览器问服务器要结论”：浏览器带上本地副本的标识问服务器”我这副本还能用吗”，服务器说能用就返回 304 Not Modified（不带 body），不能用就返回 200 带新内容。决定协商缓存的头是 Last-Modified/If-Modified-Since 与 ETag/If-None-Match。

flowchart TD
  A[浏览器请求资源] --> B{本地有缓存副本吗}
  B -->|没有| C[正常请求 拿到 200]
  B -->|有| D{强缓存是否仍在有效期}
  D -->|是| E[直接用本地副本 不发请求]
  D -->|否| F[带协商标识请求]
  F --> G{服务器判断副本是否最新}
  G -->|最新| H[返回 304 不传 body]
  G -->|过期| I[返回 200 传新内容]

一次请求可能同时涉及两类：先看强缓存，命中就直接结束；未命中才进入协商。所以调优的第一顺位是把强缓存配置好，协商缓存是强缓存的兜底，不是替代品。

强缓存：Expires 与 Cache-Control

Expires 的绝对时间陷阱

HTTP/1.0 时代的产物，写法是一个绝对的 GMT 时间：

意思是”到这个时刻之前，都可以用本地副本”。它的致命问题在于依赖双方时钟一致。用户把系统时间往前调一年，浏览器就认为缓存早已过期，每次都重新请求；往后调，则会在真正过期后继续使用旧副本。服务器与客户端时钟不同步时，这个头的语义完全不可靠。

2013 年的主流做法是仍然保留 Expires 以兼容只认 HTTP/1.0 的老代理，但真正生效的判定交给 Cache-Control。

Cache-Control 的完整指令集

HTTP/1.1 用 Cache-Control 取代 Expires 成为主力，它用相对时长（max-age 以秒计）规避时钟问题，并提供了一组指令控制缓存行为：

各指令的语义如下：

指令 作用对象 含义
max-age=秒 浏览器与中间代理 响应在多少秒内视为新鲜，优先级高于 Expires
no-cache 浏览器与中间代理 每次使用前都必须向服务器验证，不是”不缓存”
no-store 浏览器与中间代理 根本不存，任何副本都不保留
public 中间代理 响应可被共享缓存（如 CDN、代理）存储
private 中间代理 仅终端浏览器可缓存，共享缓存不得存储
must-revalidate 浏览器 过期后必须向源服务器验证，不得在离线时用旧副本

no-cache 这个名字极具误导性：它表示”可以存，但每次用之前都要问服务器”，走的是协商缓存路线。真正”不要存”的是 no-store。这个混淆在面试与实际配置里都高频出现。

public 与 private 的区别只在有中间代理（CDN、公司网关）时才体现。如果响应里带用户相关数据（比如拼接了用户名的一段 JSON），必须标 private，否则 CDN 可能把 A 用户的内容缓存给 B 用户。

must-revalidate 常与 max-age 搭配，用在”过期后宁可报错也不许用旧数据”的场景，比如价格、库存类接口。

优先级上，Cache-Control 优于 Expires；两者同时存在且冲突时，浏览器按 Cache-Control 走。no-store 与 no-cache 之间，no-store 更强。

expires 1y 是 Nginx 的简写，它会同时输出 Expires 与 Cache-Control: max-age=31536000，比手写两个头更稳妥。

协商缓存：Last-Modified 与 ETag

强缓存未命中时，浏览器发起一次带条件的请求。服务器有两种方式判断副本是否最新。

Last-Modified 与 If-Modified-Since

最直观的一种：服务器在响应头里告诉浏览器文件最后修改时间，浏览器下次请求时把这个时间放在 If-Modified-Since 里回传。服务器拿它与文件的当前修改时间比对，一致就返回 304。

它的短板有三个。其一，精度只到秒，一秒内多次修改会被误判为未修改。其二，它只看修改时间不看内容：文件被还原、被替换成同样时间戳的旧版本，都会误判。其三，某些服务器上生成时间不等于内容变化时间（比如动态拼接但模板没变的页面）。

ETag 与 If-None-Match

ETag 是文件内容的唯一标识（通常由内容哈希或 inode 加时间戳加大小生成），服务器把标识放在响应头，浏览器下次请求时放在 If-None-Match 里回传。服务器比对标识，一致返回 304。

强校验要求实体字节完全一致；弱校验只要求语义等价，允许内容有细微差异（比如尾部多一个换行）。强校验可以用于范围请求等场景，弱校验不行。第三种形态其实是无引号形式，不合规范但某些服务器会输出。

当响应同时带 Last-Modified 与 ETag 时，浏览器会把两个都带上，但服务器必须优先用 ETag 判断。原因是 ETag 的精度与准确性都高于 Last-Modified，后者只是兼容性兜底。

两者的对比与选型

维度 Last-Modified ETag
依据 文件修改时间 内容计算出的标识
精度 秒级 内容级
误判 时间不变但内容变会漏判 基本无
计算开销 查文件系统元数据 可能需读文件算哈希
多服务器 时间戳一致即可 需保证各节点算法一致

结论是两者都要开，Last-Modified 作为不支持 ETag 的老代理的降级。但 ETag 在多机部署时有个坑：如果 ETag 由 inode 生成，同一份文件在不同服务器上的 inode 不同，用户请求落到不同机器会被判定为”不匹配”而反复返回 200。解决办法是让 ETag 只基于内容计算（Nginx 默认只用大小加时间戳，是安全的选择）。

304 省了流量，没省往返

协商缓存常被形容为”几乎免费”，这个说法只对了一半。304 响应的 body 确实是空的，带宽几乎不花，但它仍然是一个完整的请求响应周期：DNS 查询（可能被缓存）、TCP 连接、发送请求、等待服务器处理、接收响应头。在国内的网络环境下，这一来一回的 RTT 常常在几十到几百毫秒之间。

这带来两个实践结论。第一，协商缓存是兜底不是主力，能用强缓存覆盖的资源就不要指望 304。第二，控制 304 的数量比控制单个 304 的体积更重要——一个页面引用了三十个需要协商的资源，就是三十个往返，哪怕每个都命中 304，累计延迟也相当可观。

所以完整的优化思路是分层递进的：能用内容指纹加永久强缓存的，一个请求都不发；必须协商的（HTML），控制数量与体积；既不能强缓存又频繁变化的接口数据，考虑在客户端做短期内存缓存，避免短时间内重复请求同一个 URL。

另一个容易被忽略的点是，协商缓存依赖请求头里的条件字段。如果请求因为某些原因没有带上 If-None-Match（比如用户按了 Ctrl+F5），服务器就无法判断，只能返回完整内容。这也是前面”用户行为”一节重要性的延伸。

如何验证协商缓存真的生效

浏览器开发者工具的 Network 面板会显示每个请求的状态码，304 会明确标注。但更有说服气的验证是用命令行直接看响应头，排除浏览器行为的干扰：

curl -I 只发 HEAD 请求，输出响应头。如果第二次返回 304 Not Modified 且没有 body，说明协商链路是通的。这个方法的优势是完全可控——想带什么条件字段就带什么，不受浏览器刷新策略影响，是确认服务器配置是否生效的最直接手段。

缓存位置：memory cache 与 disk cache

强缓存命中的副本放在哪，浏览器有两级存储。

memory cache 是内存缓存，读取最快，但生命周期与渲染进程绑定——标签页关闭、进程被回收，缓存即消失。disk cache 是磁盘缓存，持久化，可跨标签页与跨会话复用，但读取要经过磁盘 IO。

Chrome 的分配策略大致是：渲染过程中用到的资源（当前页面的 CSS、JS、图片）优先放 memory cache，以便二次引用零成本；体积较大或当前页面用不到的资源倾向放 disk cache，避免撑爆内存。这也解释了一个常被误认作 bug 的现象：同一个 URL，在当前页刷新命中 memory cache 极快，关掉标签页重新打开则明显慢一些——前者读内存，后者读磁盘。

判断缓存来自哪一层，可以在 Chrome DevTools 的 Network 面板看 Size 列：标注 from memory cache 与 from disk cache 的请求没有实际网络往返。当年调试缓存问题时，这一列是第一个要看的地方。

flowchart TD
  A[请求资源] --> B{memory cache 有且新鲜吗}
  B -->|是| C[从内存读 无网络请求]
  B -->|否| D{disk cache 有且新鲜吗}
  D -->|是| E[从磁盘读 无网络请求]
  D -->|否| F[走网络请求]

启发式缓存：没有缓存头时的默认行为

如果响应既没有 Cache-Control 也没有 Expires，浏览器并不会认为”不能缓存”，而是进入启发式缓存（heuristic caching）：按 Last-Modified 的值推算一个新鲜期。

RFC 2616 给出的常见算法是取”当前时间与 Last-Modified 之差的一个比例”（实现里常用 10%）。例如文件最后修改于 10 天前，浏览器可能在接下来 1 天内把它当作新鲜副本直接使用。

这个行为是很多”改了文件不更新”的隐形元凶：服务器没配缓存头，只带了 Last-Modified，用户在一个未知时长的窗口内拿到旧文件，而你这边毫不知情。所以配置缓存时的第一条原则是：不要依赖启发式缓存，所有响应都显式给出 Cache-Control。

启发式缓存还有一层连带影响：它让”未配置缓存头的站点”表现出看似正常的缓存行为，从而掩盖了配置缺失。测试时一切正常，直到某次更新后部分用户反馈样式错乱，才回头查响应头。反过来，如果你的本意是”这个响应完全不要缓存”，就必须显式写 no-store——留空不等于不缓存，这是 RFC 2616 与后来所有浏览器实现的既定行为。

另外要注意启发式缓存不适用于没有 Last-Modified 的响应（比如某些动态生成的 200 响应）。这种情况下浏览器通常直接按不可缓存处理，每次重新请求。这种”有时缓存有时不缓存”的不确定性，正是必须显式配置的又一个理由。

用户行为对缓存的影响

这是高频面试题，也是日常排查最实用的知识。同样是刷新页面，不同操作触发的缓存策略完全不同。

用户操作 强缓存 协商缓存
地址栏回车 / 点击链接打开 生效 生效
F5 或常规刷新按钮 不生效 生效
Ctrl+F5 强制刷新 不生效 不生效

逐个解释背后的机制。

地址栏回车或点开链接 是一次普通导航请求，请求头里不带任何条件字段，浏览器完全按缓存规则走：强缓存命中就直接用本地副本，未命中才带条件字段问服务器。这是正常用户访问的状态，也是缓存配置要服务的对象。

F5 刷新 时浏览器会清空当前页面的 memory cache，并在请求头里加上 Cache-Control: no-cache（注意这是请求头，语义是”我不要用强缓存副本”）。资源会重新走网络，但请求仍带 If-Modified-Since 与 If-None-Match，所以协商缓存照样生效，未修改的资源依然返回 304。这个设计的意图是”我要最新的页面，但别浪费带宽重传没变的东西”。

Ctrl+F5 强制刷新 时浏览器连协商缓存一并跳过：请求头带 Cache-Control: no-cache，且不带 If-Modified-Since 与 If-None-Match，同时可能带 Pragma: no-cache。服务器收不到任何条件字段，只能返回完整 200 响应。

掌握这三行的差异，排查问题时的第一句话就能问对：”你是 Ctrl+F5 刷的吗？”很多”改了没生效”的报告，真相只是用户按了强制刷新，或者反过来——用户一直按 F5，而服务器给的是无协商头的纯静态响应。

sequenceDiagram
  participant U as 用户
  participant B as 浏览器
  participant S as 服务器
  U->>B: 地址栏回车
  B->>S: GET /app.js
  S-->>B: 200 + Cache-Control: max-age=31536000
  U->>B: F5 刷新
  B->>S: GET /app.js (Cache-Control: no-cache, If-None-Match)
  S-->>B: 304 Not Modified
  U->>B: Ctrl+F5 强制刷新
  B->>S: GET /app.js (不带任何协商字段)
  S-->>B: 200 + 完整内容

Vary 头：缓存也要看请求

Vary 解决的是”同一个 URL，响应内容却不同”的问题。最常见的是内容协商：服务器根据 Accept-Encoding 返回 gzip 压缩版或原文，根据 Accept-Language 返回不同语言版本。

它的含义是：缓存这个响应时，要把 Accept-Encoding 请求头一起作为 key。之后浏览器带不同 Accept-Encoding 请求同一 URL，不能直接复用这份缓存。

多个字段用逗号分隔。这个头是双刃剑：写对了能防止压缩版被当成原文发给不支持 gzip 的客户端，写错了（比如无脑 Vary: User-Agent）会让缓存命中率崩塌——每种 User-Agent 都各存一份，等于没缓存。

调试时可以在 Network 面板里查看响应头，如果发现同一资源被反复下载，Vary 的字段是否过宽是常见原因之一。

Cookie 与 Storage 不是 HTTP 缓存

一个必须澄清的边界：Cookie、localStorage、sessionStorage 属于客户端存储，不走 HTTP 缓存那套规则。

HTTP 缓存由响应头驱动，由浏览器自动管理，目的是减少网络请求。Cookie 由 Set-Cookie 写入，随每次同源请求自动带回，目的是携带身份与会话状态。localStorage 则完全由 JavaScript 读写，不参与任何请求过程。

把三者混为一谈会导致错误的设计决策。典型的错误是想”用 localStorage 缓存接口数据来减少请求”——localStorage 的读写是同步的，且容量通常只有 5 MB 左右，存放大块数据会阻塞主线程；它也没有过期机制，需要自己维护失效逻辑。2013 年的实践中，localStorage 适合存少量配置与状态，不适合当接口缓存层用。

CDN 缓存

CDN 在链路上多了一跳，规则大体一致但有几个注意点。

CDN 节点会按源站的缓存头决定自己的存储行为，所以源站配置错了，CDN 会忠实地把错误行为复制到所有节点。private 在 CDN 场景下尤其重要：带用户数据的响应必须标 private，否则会被缓存在共享节点上分发给所有用户。

CDN 也提供主动刷新（purge）能力，可以指定 URL 让所有节点立刻回源站拉新内容。对于来不及做文件指纹的历史资源，这是紧急更新的手段，但有生效延迟，且频繁 purge 会增加回源压力。

API 响应标 private 是防止 CDN 缓存用户私有数据的关键一行。

常见坑与排查

坑一：改了文件不更新。 资源没有指纹，且强缓存时间设得过长，用户拿着旧副本。排查方法是看 Network 面板的 Size 列，如果是 from memory cache 或 from disk cache 且没有网络请求，说明强缓存还在有效期。修复方式要么上文件指纹，要么缩短 max-age 改用协商缓存。

坑二：本地永远是新的，线上是旧的。 本地开发环境通常没有配缓存头，或者你习惯按 Ctrl+F5，问题被掩盖。上线后配置了长缓存，用户侧立刻暴露。修复方式是测试时用干净的浏览器 profile，并明确区分 F5 与 Ctrl+F5 的预期行为。

坑三：HTML 被强缓存，新版本永远下不来。 这是最严重的组合：HTML 配了一年 max-age，同时静态资源又用了新指纹。用户永远停留在第一次访问时的那份 HTML，引用的永远是最初那批 CSS/JS。HTML 必须协商缓存，这条没有例外。

坑四：Vary 过宽导致命中率归零。 Vary: User-Agent 会让每种 UA 各存一份。多数场景只需要 Vary: Accept-Encoding。

坑五：集群 ETag 不一致。 多台服务器 ETag 算法不同，用户请求在不同机器间跳转时反复 304 失败、返回完整内容。修复是统一 ETag 生成规则，或直接用 Nginx 默认的”大小加时间戳”方案。

坑六：HTTPS 与 HTTP 混用缓存。 不同协议、不同端口、带不带查询串，在浏览器看来都可能是不同资源。调试时确认 URL 完全一致，包括尾部的 ?v=1。

坑七：缓存与回退按钮行为不一致。 用户点浏览器的后退按钮时，某些浏览器会直接从内存缓存里恢复页面而不重新请求，于是看到一个”上一个版本”的页面。这与缓存头无关，是浏览器的历史记录策略，但排查时容易被误判为缓存未失效。规避方式是给页面加一段检测脚本，在页面从缓存恢复时强制刷新。

坑八：CDN 节点缓存了错误内容却无从察觉。 CDN 回源拉到的内容本身是错的（比如源站配置错误、回源时刚好遇到异常响应），之后这个错误内容被分发到所有节点，且因为缓存头有效而长期存在。此时刷新源站无用，必须走 CDN 的 purge 或刷新接口。这类问题的排查难点在于用户与开发者在不同网络位置，看到的可能是不同节点的内容。

坑九：接口数据被中间代理缓存。 内网代理、公司网关有时会按自己的规则缓存响应，尤其是没带 Cache-Control 的 JSON 接口。用户看到的数据是几分钟前的，而服务器日志显示没有任何新请求。给 API 响应显式加上 Cache-Control: private, no-cache 或 no-store，能避免大多数代理自作主张。

坑十：调试时开启了 Disable cache。 Chrome DevTools 的 Network 面板有一个 Disable cache 复选框，勾选后所有缓存逻辑被跳过。排查完忘记取消，之后的所有观察都不真实。这个小复选框造成的时间浪费，累计起来相当可观。

排查的顺序建议固定为：先看 Network 面板的状态码与 Size 列（是 200 还是 304，是网络还是缓存），再看响应头确认缓存策略，最后对比请求头判断是哪种用户行为触发。三步下来，绝大多数缓存问题都能定位。

小结

浏览器缓存的全部规则可以用两条主线概括：强缓存决定”发不发请求”，由 Expires 与 Cache-Control 驱动，max-age 是主力、no-cache 与 no-store 的差别必须分清；协商缓存决定”要不要重传内容”，由 Last-Modified 与 ETag 驱动，ETag 优先级更高但要注意集群一致性。缓存分 memory 与 disk 两层，无缓存头时会按 Last-Modified 做启发式缓存，这也是隐性故障的来源。策略上遵循”内容不变的资源上指纹加永久强缓存，HTML 走协商缓存”，配合 Vary 头防止缓存错投，并始终记住 Cookie 与 Storage 不属于 HTTP 缓存。最后把三种用户行为的差异记牢：地址栏回车全走缓存，F5 跳过强缓存保留协商，Ctrl+F5 两者都跳过——排查问题时先问清用户按的是哪个键，能省一半时间。
