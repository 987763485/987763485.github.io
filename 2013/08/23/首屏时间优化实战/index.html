首屏时间优化实战

上一类讲”有哪些手段”的文章很容易读爽，照着做一遍却发现收益不如预期。原因很简单：首屏慢的瓶颈往往不在你改的那个文件里。这篇换一个角度，完整记录一次真实的优化过程，从怎么量、到怎么定位、再到按什么顺序动手，最后是哪些改动有效、哪些白忙一场。文中的项目是一个 2013 年的活动落地页，jQuery 1.9 加若干第三方脚本，PC 和移动端共用一套代码。

先量再改：没有数据的优化是猜

动手之前只做一件事，把现状钉死。当年可用的指标来源主要有三个：浏览器的 Network 面板、performance.timing，以及 YSlow 和 PageSpeed 的评分。三者用途不同，Network 面板看单次请求的细节，performance.timing 看整体阶段耗时，YSlow 看规则覆盖。

performance.timing 在 2012 年已经成为标准，Chrome、IE 9+、Firefox 都支持，它的价值是把”白屏时间”拆成一段段可归因的数字：

我在项目里加了一段只上报不显示的统计脚本，连续收集了三天。数字很难看：WiFi 下首屏可见约 2.6 秒，2G 模拟下超过 9 秒，onload 在 3G 下普遍 8 秒以上。更重要的是分布很散，说明有部分用户被某个特定资源拖住，而不是整体网络差。

这里要强调一点：window.onload 和”首屏可见”是两个指标。当年优化容易陷入把 onload 从 9 秒压到 6 秒，但用户早在 3 秒时就看到了主要内容。真正该看的是首屏内容渲染完成的时刻，手工量可以用”首屏最后一个元素出现的时间”，工具上就用 Chrome 的 Timeline 录一次，找到 First Meaningful Paint 附近的帧。两个指标一起看，才知道自己优化的是体验还是评分。

请求瀑布：问题都藏在图里

有了数字，下一步是打开 Network 面板看瀑布图。不要按时间排序，要看请求的并行关系和阻塞关系。这个页面的瀑布图有四个明显特征，我按影响从大到小排了个序。

第一，CSS 在 <head> 里以阻塞方式加载，这没问题；但它上面还压了三个第三方脚本——一段统计代码、一个分享按钮、一个字体服务。这三个都是同步 <script src>，浏览器必须下载并执行完它们才能开始解析 HTML。瀑布图上体现为一长串空白，然后才出现 CSS 请求。

第二，首屏有 12 张图片，其中 4 张是活动头图，尺寸都在 300KB 以上，且没有做渐进式。它们在文档解析到 <img> 标签时才发起请求，全部堆在瀑布图中后段。

第三，jQuery 和两个插件各自独立请求，没有合并也没有走 CDN，DNS 解析就花了将近 400 毫秒。

第四，底部还有一段”滚动到可视区再加载”的逻辑没生效，实际所有图片都在首屏发起。

flowchart TD
    A[HTML 请求] --> B[解析 head]
    B --> C[同步第三方脚本 1]
    C --> D[同步第三方脚本 2]
    D --> E[同步第三方脚本 3]
    E --> F[CSS 阻塞下载]
    F --> G[继续解析 DOM]
    G --> H[jQuery]
    G --> I[插件 1]
    G --> J[插件 2]
    H --> K[执行内联脚本]
    K --> L[解析到 img 标签]
    L --> M[12 张图片并发请求]

这张图就是优化顺序的依据：越靠前、越阻塞的资源，单位改动收益越大。顶部那三个同步脚本，哪怕每个只花 100 毫秒，加起来也是净白的 300 毫秒，而且它们挡着后面所有东西。

动手顺序：先诊断再治疗

我的顺序是四步，每一步做完都重新量一次，避免改动之间互相掩盖效果。这一步很关键，不重新量就不知道哪个改动真的有用。

第一步治理阻塞脚本。三个同步脚本全部改成异步，统计代码用官方提供的异步片段，分享按钮改成点击时才加载，字体服务改成等首屏渲染完再下载字体文件。只这一步，首屏可见时间从 2.6 秒降到 2.1 秒。

第二步合并并压缩 CSS 与 JS。三个 JS 文件合并成一个，CSS 两个合成一个，都过压缩。同时把 jQuery 换到公共 CDN，利用其他站点已经建立的连接和缓存。DNS 的 400 毫秒基本消掉了。

第三步处理图片。这是收益最大的一步。头图切成 WebP 和 JPEG 两套（当年 Chrome 26 以上支持 WebP，iOS 不支持，用 <picture> 或者 JS 判断做降级），分辨率按移动端 DPR 出两档，质量压到 75 左右。四张 300KB 的头图变成平均 45KB。同时把首屏之外的图片加上真正的懒加载——判断依据是 getBoundingClientRect().top 小于视口高度再加 src。

第四步才是那些”看起来高级”的手段：dns-prefetch 预解析几个后续页面要用的域名，把关键的 CSS 内联进 <head> 让首屏样式不必等一个往返。这两步各贡献了 100 到 200 毫秒，属于锦上添花。

改动前后的数据，同一台 Android 4.2 机器、WiFi 与限速 400Kbps 各跑五次取中位数：

指标 优化前 WiFi 优化后 WiFi 优化前限速 优化后限速
首屏可见 2.6 s 1.4 s 9.1 s 4.3 s
onload 4.8 s 2.2 s 15 s 以上 7.6 s
请求数 34 21 34 21
传输体积 1.9 MB 610 KB 1.9 MB 610 KB

限速那一列更能说明问题：绝对时间的降幅比 WiFi 下大得多。优化请求数和体积，收益在网络差的时候被放大，这也是移动端优化优先级高于桌面端的原因。

关键资源优先级与阻塞处理

“哪些资源挡着首屏”是可以逐个判断的。规则很朴素：出现在 <head> 里的 CSS 挡首屏渲染，出现在文档流前面的同步 <script> 挡 DOM 构建，@import 引入的 CSS 挡得更多一层（它要先下载引入它的文件才能发现目标地址）。

处理手段按推荐程度排：

  • 同步 <script> 全部加 async 或 defer，或者移到 </body> 前。有依赖关系的用 defer 保持顺序，无依赖的用 async。
  • CSS 尽量合并成一个文件，减少往返；首屏关键样式可以内联，其余异步加载。
  • 不用 @import，全部改成 <link>。
  • 字体文件体积要盯住。中文字体全量动辄几 MB，活动页一般只用十几个字，2013 年的常见做法是让设计切图，或者用字体子集化工具只保留用到的字。那次我把一个 3.2MB 的字体换成了图标字体加系统字体，请求数少一个，体积少 3MB。

第三方脚本是重灾区。它们的共同特点是不受你控制，随时可能变慢。治理办法不是不用，而是隔离：统计和客服类脚本全部异步，并且加超时兜底——如果某个脚本 2 秒还没回来，后续依赖它的逻辑直接走降级分支。分享按钮这类纯增强功能，改成用户点击后才加载。

监控与持续观测

优化最大的敌人是回退。上线两周后有人加了一个新的统计脚本、一张没压缩的运营图，指标就悄悄回去了。所以那次之后我在项目里固化了两件事。

一是把性能统计做成常规上报。用 performance.timing 采集，onload 之后通过一个 1x1 的图片请求把数据发出去，样本量不用大，1% 的采样就够看趋势。重点是看 P75 而不是平均值，平均值会被快的那部分用户拉平。

二是把规则检查搬进提测流程。YSlow 和 PageSpeed 当年都能离线跑，CI 里挂一条：压缩关闭时报错，图片超过 200KB 告警。这条规则拦下过好几次无意识的回退。

小结

首屏优化是一次诊断过程，不是一堆手段的堆叠：先用 performance.timing 把阶段耗时量化，再看瀑布图找出最靠前、最阻塞的资源，然后按”阻塞脚本、合并压缩、图片、预解析”的顺序逐个改，每步都重新测量。那次实战里收益排序是图片最大、阻塞脚本次之、合并与 CDN 再次，预解析只是补充。限速网络下的绝对收益远大于 WiFi，说明请求数和体积才是移动端的核心矛盾。最后别忘了监控和流程约束，否则所有成果都会在几次无意识的迭代里流失。
