移动端调试工具与实践

桌面浏览器上按 F12 就能看到一切，移动端却完全不是一回事：没有控制台，没有 Network 面板，甚至看不到报错信息。2013 年做移动端页面，排查一个”安卓上白屏”的问题可能要反复加 alert 试位置。这篇把当年真机调试的几种主流方案、抓包限速手段，以及常见问题的排查套路整理一遍，重点说清每个工具的平台限制和适用场景。

真机调试的三种主流方案

2013 年的真机调试方案按原理分三类：远程连接原生调试器、注入远程调试脚本、以及借助 PC 端代理抓包看日志。第一类体验最好但有平台和版本门槛，第二类跨平台但功能弱，第三类严格说不算”调试”但使用频率最高。

Chrome DevTools 远程调试 Android

这是当年 Android 上最好用的方案。原理是 PC 上的 Chrome 通过 USB 连接手机上的 Chrome，把页面和调试器连起来，能看 DOM、执行 JS、断点、看 Network 和时间线，基本等于桌面版 DevTools。

前提条件有三条：手机 Android 4.0 以上，PC 端 Chrome 32 以上，以及手机开启 USB 调试。手机上的 Chrome 还要在设置里打开”启用 USB 调试”（Developer Options）。连接后地址栏输入 chrome://inspect，能看到已连接设备上打开的标签页，点 Inspect 就弹出调试窗口。

常见失败原因是设备显示为 unauthorized，需要在手机上确认 RSA 密钥弹窗；另一个是 Windows 上缺 USB 驱动，装对应机型的驱动即可。Mac 和 Linux 基本免驱。

这个方案的价值不只是控制台。Network 面板能看到每个请求的耗时和瀑布，Timeline 能看到帧率，对定位”安卓上动画卡”特别有用——手机上肉眼看不出是掉帧还是本身动画就慢，时间线上一眼能看出来。

Safari Web Inspector 调试 iOS

iOS 6 起，Safari 支持通过 Web Inspector 远程调试，前提是必须有一台 Mac，以及一根数据线。iOS 5 及以下没有这个能力，只能靠别的手段。

开启方式分三处：手机上进”设置 > Safari > 高级”，打开 Web 检查器；Mac 的 Safari 偏好设置里打开”在菜单栏中显示开发菜单”；连上手机后用手机 Safari 打开页面，Mac Safari 的开发菜单里就会出现这台设备和页面，选一个就进入检查器。

它的功能比 Android 的远程调试更接近原生调试体验，资源面板、时间线、控制台都有，还能直接看 WebCore 的渲染信息。限制是只能调试 Safari，不能调试 App 内嵌的 UIWebView，也不支持 Windows。

iOS 上最麻烦的其实是模拟器。Xcode 自带的 iOS Simulator 可以跑 Safari，配合 Mac 版 Safari 的开发菜单调试，但它和真机在性能上差异巨大——模拟器跑得飞快，真机上卡成狗的动画在模拟器里完全看不出来。iOS 6 的模拟器也没有 WebGL 和部分硬件加速路径。所以模拟器只适合快速验证布局和逻辑，性能问题必须回真机。

weinre 与 Adobe Edge Inspect

前两个方案都要求设备和调试机在同一个”能被连接”的状态，而且各管一家。weinre 是当年覆盖最广的跨平台方案，2011 年由 Patrick Mueller 创建，思路是往页面里注入一段脚本，让它连上一个跑在 PC 上的调试服务器，浏览器打开一个地址就能远程查看和控制页面。

Adobe Edge Inspect 走的是另一条路，它的前身是 2012 年的 Adobe Shadow。原理是 PC 上装一个 Chrome 扩展，手机装 App，两者配对后 PC 上输入的地址会同步推到所有配对设备上，每台设备的截图和 DOM 信息回传到 PC。它解决的是”多机型同时看效果”而不是”调试”——一次改完代码，五台手机上同时刷新，这个能力在当年是独一份的。缺点是对中文网络环境的服务器同步不太稳定，且需要 Adobe ID。

抓包、代理与弱网模拟

移动端调试另一半工作是网络。Charles 和 Fiddler 是当年的主力，功能高度重叠：设置手机代理指向 PC，所有请求就经过 PC，能看到请求响应详情、改请求、改响应。

Fiddler 在 Windows 上更顺手，Charles 跨平台且界面更清爽，移动端开发者里两个用户群都很多。常用能力有四个。

第一是看请求详情。手机上看到的”接口返回 200 但数据是错的”，到 PC 上一看响应体就明白了。很多跨域问题的真实原因（比如返回了 HTML 错误页而不是 JSON）只有在抓包工具里才看得见。

第二是断点改请求改响应。Fiddler 里设一个断点，请求发出去前可以改参数，响应回来时可以改内容，用来模拟服务端异常特别方便。Charles 的 Map 功能可以把远程请求映射到本地文件，改前端页面不用发版。

第三是 Host 映射和域名指向。测试环境经常需要让手机访问测试机域名，一条 Host 映射就解决，比改手机系统 Host 简单得多。

第四是限速。Charles 和 Fiddler 都能模拟弱网，Throttle 设置里选一个预设（比如 2G、3G）或者自定义带宽。这个能力对移动端调优是刚需：本地 WiFi 下秒开的页面，限速到 400Kbps 才知道首屏到底要几秒。

常见问题排查

把当年反复遇到的几类问题和排查顺序列一下，基本能覆盖大部分情况。

白屏。先抓包确认 HTML 和关键 CSS 有没有正确返回、有没有 404 或者返回了错误页。再看控制台有没有 JS 报错——input、classList、addEventListener 这些 API 在低端 Android 2.x 上不支持，一个报错就能让后面的初始化全不执行。最后看是不是某个同步脚本卡住导致 DOM 没解析完。经验上白屏九成是资源加载或脚本报错，纯布局问题很少导致完全白屏。

点击无效。先确认元素有没有被遮挡，用 Web Inspector 的选取工具看命中区域是不是预期元素。iOS 上 click 事件有 300 毫秒左右的延迟，快速点击时会感觉”没反应”，用 touchstart 替代或者引入 fastclick 类方案。Android 上点击穿透比较典型：弹层关闭后点击事件传到了下层元素，用 touchstart 的 preventDefault 或者关闭时加一个短暂的点击拦截层。

键盘遮挡。iOS 上键盘弹起会改变视口，正在输入的框被盖住，处理方式是 focus 时 scrollIntoView()。Android 4.x 上部分机型键盘弹出后 window.innerHeight 不变，页面也不会自动调整，只能用 position: fixed 的底部表单布局绕开。还要注意键盘弹出和收起时 resize 事件的触发时机不一致，做防抖处理。

滚动异常。overflow: scroll 在 iOS 5/6 上没有惯性，需要 -webkit-overflow-scrolling: touch；但它和 position: fixed 混用时定位会错乱，这个组合在 2013 年是无解的，只能改结构。Android 4.x 上部分机型滚动容器内的点击事件会延迟到滚动停止才触发，影响列表项的响应速度。

界面错位。最常见的原因是 viewport 没写或者写错，width=device-width 加 initial-scale=1 是底线；其次是没考虑 DPR，用 CSS 像素写的尺寸在 DPR 2 的屏幕上物理尺寸翻倍。还有 flexbox 的老语法问题，2012 年前的 display: box 和后来的 display: flex 并存，漏写 -webkit- 前缀在 iOS 6 上直接失效。

小结

2013 年的移动端调试方案里，Android 4.0 以上用 Chrome 32+ 的 chrome://inspect 体验最完整，iOS 6 以上配一台 Mac 用 Safari Web Inspector，跨平台兜底用 weinre 注入脚本，多机型同步看效果用 Adobe Edge Inspect，条件极端时自建 vConsole 式日志窗口。网络侧靠 Charles 和 Fiddler 抓包、断点、Host 映射和限速模拟弱网，这一套的使用频率甚至高于控制台。排查问题时按资源加载、脚本报错、事件命中、视口与滚动的顺序走，比盲目试错快得多。
