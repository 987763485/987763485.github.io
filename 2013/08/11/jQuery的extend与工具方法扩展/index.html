jQuery 的 extend 与工具方法扩展

jQuery 只有一百多 KB，却能变成无数形状迥异的”框架”，靠的就是 $.extend 这个不起眼的合并函数。插件作者用它扩展工具方法，业务代码用它做选项合并，团队里用它统一公共函数。用法一句话能说完，坑却能踩一串：浅拷贝把嵌套对象共享了出去、深拷贝遇到循环引用直接栈溢出、多个脚本抢同一个命名空间互相覆盖。这篇从源码入手，把 extend 的两种模式、扩展实例方法的 $.fn.extend，以及实际项目里的合并惯用法和坑一次讲清。

先分清两个入口。$.extend 扩展的是 jQuery 这个对象本身的方法，比如 $.ajax、$.each，调用时写 $.xxx()。$.fn.extend 扩展的是 jQuery.prototype，也就是所有 jQuery 实例的方法，比如 $.fn.hide，调用时写 $('div').hide()。两者底层走的是同一段合并逻辑，只是挂载的目标不同。

三个设计点值得单独说。

target 默认是第一个参数。 所以 $.extend({}, defaults, options) 这种写法才是安全的——第一个参数是一个空对象，作为接收方，后两个只作为数据源，不会被修改。如果写成 $.extend(defaults, options)，defaults 本身就被改掉了，下次再用默认值时已经被污染。

深拷贝用递归实现。 只在 deep 为 true 且值是纯对象或数组时才递归，且递归时会判断目标上已有的同key值是不是同类型，是则复用它作为容器继续填，否则新建。这就是 $.extend(true, {}, a, b) 的完整语义。

if (target === copy) continue; 这行防的是自引用，也是深拷贝不死循环的关键之一。另一处防护在 for (name in options) 里的 jQuery.isPlainObject 判断——它排除了 Date、RegExp 这类对象，遇到它们直接走 copy !== undefined 的赋值分支，保持引用。

深合并也有不能解决的问题，主要有三类。

数组是整体替换，不是逐项合并。 上面例子里如果 options 给 tags: ['c']，深合并的结果是 ['c']，而不是 ['a','b','c']。这是 jQuery 的既定行为，因为”用户给了新数组”通常意味着”我要这个列表”，逐项合并反而难以预测。需要拼接就自己在合并后处理。

Date 与 RegExp 不被递归。 jQuery.isPlainObject 判断的是”用对象字面量或 new Object 创建的对象”，Date 实例会被判为否，于是走直接赋值，复制引用。这意味着深合并后两个对象共享同一个 Date，改一个另一个跟着变。需要真正独立副本时要手动 new Date(src.getTime())。

循环引用会让递归无限进行。 jQuery 1.9 的 extend 对循环引用没有防护（target === copy 只挡同一对象直接自引用，挡不住 A.b = B、B.a = A 这种间接环）。合并这类结构会栈溢出。绕开方式是合并前手动打破环，或者只用浅合并。

坑在哪：一次真实的覆盖事故

把上面的点串成一个场景。团队里 A 同学给公共库加了 $.fn.serializeObject，B 同学在自己的业务脚本里也写了一个同名方法，只是字段处理略有差别。两个文件都按惯例放在页面底部，加载顺序取决于构建工具的输出。结果有时表单能正确提交，有时丢字段——因为谁的脚本后加载，谁的方法就生效，而两个构建产物的顺序并不稳定。

复盘的教训有两条。第一，跨团队共享的方法必须挂命名空间（$.utils.form.serialize），用足够长的路径把碰撞概率降到零。第二，判断存在再扩展，至少在控制台留个警告，而不是静默覆盖：

小结

$.extend 是一段不到四十行的合并逻辑，读懂它比记住它的行为清单更有用：target 取第一个参数、深拷贝靠递归、纯对象与数组才下钻、Date 与 RegExp 保持引用。浅合并适合扁平配置，一旦出现嵌套就必须深合并，否则部分覆盖会静默丢字段；数组是整体替换，循环引用会栈溢出，这两条是深合并的天花板。扩展工具方法优先挂命名空间而非直接压 $，扩展实例方法守住 return this 与 each 两条约定。选项合并永远写成 $.extend(true, {}, defaults, options)，让每次调用都从干净的默认值出发。
