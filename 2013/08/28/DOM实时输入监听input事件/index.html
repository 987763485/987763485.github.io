DOM 实时输入监听 input 事件

实时搜索框、金额千分位格式化、手机号自动加空格，这些需求的共同点是”用户每敲一下键盘就要有反馈”。2013 年做这类需求，第一反应是用 keyup，但很快就发现 keyup 漏掉了粘贴、拖拽和中文输入法上屏这些情况。这篇把 input 事件的适用边界、和键盘事件的分工、中文输入法的处理，以及光标位置保存这些细节讲清楚。

为什么不用 keyup

keyup 在按下并松开一个键之后触发，它有几个绕不过去的漏洞。第一，右键粘贴不触发任何键盘事件，但输入框内容确实变了。第二，用鼠标拖动一段文本到输入框，同样没有键盘事件。第三，中文输入法上屏的时机和 keyup 并不对应，具体行为各浏览器还不一致。第四，长按删除键在部分系统上是连续触发，在另一些系统上只在松手时触发一次。

input 事件解决的就是这些问题。它是 HTML5 规范里定义的事件，语义是”元素的值被用户改变”，不关心是怎么改变的。IE 9 开始支持，Chrome、Firefox、Safari 在 2013 年都已支持，可以说除了 IE 8 及以下没有兼容障碍。

需要说明的是，用 JS 代码给 value 赋值时不会触发 input 事件。这一点有时是好事（避免格式化时自己触发死循环），有时是坏事（别处改了值，监听方收不到通知）。需要触发时手动 dispatchEvent。

和 change 的区别也要讲清楚。change 在输入框失焦且值发生变化时才触发，它的定位是”值确认”，不是”值变化”。实时搜索里 change 一点用都没有，但提交表单前的最终校验用 change 反而更好，不会在用户输入中途频繁打断。

事件对照表

把几个相关事件放在一起对比，才知道该用哪个：

事件 触发时机 粘贴时 输入法上屏 IE 支持
keydown 按下任意键 否 部分 是
keypress 按下字符键 否 部分 是
keyup 松开按键 否 否 是
input 值被改变 是 是 IE 9+
change 失焦且值改变 是 是 是
propertychange 属性改变 是 是 IE 专有

实际项目里的分工是这样的：需要按下的物理键做操作（比如回车提交、方向键选择候选项）用 keydown；只关心最终文本内容一律用 input；失焦校验用 change。

keydown 和 keypress 的差异也顺手记一下：keydown 对所有键都触发，包括功能键、方向键；keypress 只在产生字符的键上触发，IE 和 Firefox 对功能键的处理一直不太一致。判断回车一般用 keyCode === 13，但要阻止默认行为必须在 keydown 里做，keyup 时行为已经发生了。

中文输入法与 composition 事件

这是 input 事件最麻烦的部分。中文输入法的工作方式是：按下字母键时输入法进入组词阶段，用户选词后才把最终的汉字写进输入框。组词期间的中间状态（比如拼音字母）算不算一次 input？

浏览器的实际行为不一致。WebKit 内核在组词期间会触发 input，value 里是拼音串；IE 则在组词期间不触发，只在最终确认时触发一次。如果实时搜索直接监听 input，WebKit 上会在用户打 “zhong” 的时候就去查数据库，返回一堆无意义结果。

防抖与节流：实时但不每一下都发请求

input 解决了”能监听到”，但实时搜索不能每敲一个字母就发一次请求。两个思路：防抖（debounce）和节流（throttle）。防抖是停止输入一段时间后才执行，适合搜索联想；节流是固定间隔内最多执行一次，适合滚动加载和输入统计。

防抖还有一个必须处理的边界：请求是异步的，返回顺序不保证。用户输入 “a” 再输入 “ab”，”a” 的响应可能比 “ab” 的晚到，界面上就会显示过期的结果。当年的做法是维护一个请求序号，只接受最新序号的结果：

移动端 input 的特殊性

移动端的 input 还要多考虑三件事。

一是输入法占用屏幕空间。iOS 上键盘弹起会压缩视口，页面被顶起来，正在输入的框可能被键盘盖住。当年的处理是监听 focus 事件，把输入框 scrollIntoView()，或者用 position: fixed 的底部表单绕开。Android 4.x 上行为更乱，有的机型键盘弹出后 window.innerHeight 变小，有的不变，只能靠实测。

二是输入类型和键盘布局。type="email"、type="tel"、type="number" 会唤出对应的虚拟键盘，pattern 和 inputmode 当时部分支持。注意 type="number" 在部分 Android 浏览器上会在失焦时清掉非数字内容，做金额输入时用 type="text" 加自己校验更稳。

三是输入延迟。input 事件在移动端低端机上可能明显滞后于视觉上的字符出现，因为事件派发在主线程上，主线程被别的任务占住就会推迟。如果要做”跟手”效果（比如输入时实时预览），不要依赖 input 的实时性，可以配合 requestAnimationFrame 读取 value，或者接受这点延迟。

小结

实时监听从 keyup 换成 input，漏掉的粘贴、拖拽和输入法场景就都覆盖了，但 input 在中文组词期间的行为各浏览器不一致，需要 compositionstart、compositionend 配一个标志位屏蔽，IE 全系列不支持则降级为直接监听。实时搜索必须加防抖，并且要处理异步响应乱序返回的问题。格式化输入要保存和恢复 selectionStart、selectionEnd，严谨做法是按光标前的数字个数重新定位。移动端还要额外处理键盘遮挡和输入类型对虚拟键盘的影响。分清”按键”用键盘事件、”内容”用 input、”确认”用 change，这个分工能省掉大部分兼容代码。
