移动端页面切换动画

移动端页面切换动画是 2013 年最让人纠结的一件事：桌面浏览器上一个 transition 就能糊过去，到了手机上同样的代码在低端 Android 上就是满屏掉帧。更麻烦的是移动端的”切换”其实有两种完全不同的场景，一种在单页应用内部换视图，一种是在多个页面或者 WebView 之间跳转，两者的实现手段和坑几乎不重叠。本文按入门角度把这条线捋一遍，说清楚每种场景该用什么方案、动画该动哪些属性，以及当年常见的卡顿是怎么来的。

两类场景先分清楚

移动端的页面切换，第一件事不是写动画，而是先问自己：切换前后是不是同一个页面文档。

  • 单页内切换：始终是一个 HTML 文档，靠显示隐藏不同区块来完成，也就是常说的 SPA 式多视图。用 hash 路由或者自己维护一个视图栈都可以。
  • 多页切换：每个视图一个 HTML 文件，跳转就是 location.href 的赋值，或者在 Hybrid 壳子里由原生代码切换 WebView。
  • WebView 转场：多页切换的原生版本，由 iOS 的 UINavigationController 或 Android 的 Activity 动画完成，前端只能配合。

单页内切换的好处是切换瞬间没有网络请求，动画可以做得很完整，代价是要自己处理历史记录、后退键、页面状态保持。多页切换的优点是每个页面独立、刷新即是最新，代价是每次切换都有白屏和重新执行脚本的成本。

flowchart TD
    A[用户触发切换] --> B{是否同一文档}
    B -->|是 单页内| C[隐藏旧视图]
    C --> D[显示新视图]
    D --> E[class 切换触发 CSS 动画]
    B -->|否 多页| F[location.href 跳转]
    F --> G[白屏等待新文档]
    G --> H[新页面 onload 后再补入场动画]

一个偷懒但实用的判断标准：如果两个视图共享大量状态（比如表单里填了一半的数据），走单页内切换；如果两个视图几乎独立（比如从列表进详情），多页切换更省心。当年很多项目一开始全用单页，最后被后退键和状态恢复折磨，又改回多页。

单页内切换：class 切换加 CSS3

单页内切换的核心是”切换一个 class，让 CSS 去算动画”。JS 只负责改 class 和监听 transitionend，不碰具体的样式值，这样动画的调整就留在 CSS 里。

多页切换与 WebView 转场

多页切换在纯 Web 里能做的事很有限：location.href 一跳，当前文档就被卸载了，动画只能做在”跳出去之前”和”新页面加载完之后”。当年的做法是点击后先播一段离场动画，动画结束再真正跳转：

新页面那一侧则在 DOMContentLoaded 里播入场动画，同时把内容用本地存储或者 URL 参数带过来，减少”跳过去先白一下”的观感。这种做法的体验上限不高，但实现简单，兼容性最好。

Hybrid 页面里这段就交给原生了。iOS 上 UINavigationController 的 push/pop 自带平滑的横向推入动画，前端需要做的只是别在动画期间做重活，并且给 WebView 一个不透明背景，否则会看到底层内容透过来。Android 4.x 的 Activity 切换可以通过 overridePendingTransition 指定自定义动画：

原生动机会连带把两个 Activity 的界面一起做动画，WebView 里的内容只是被当作一层画面，所以 H5 内部再写一遍一模一样的横向动画就会出现”动画打 twice”的观感。前端和客户端约定好转场由谁负责，是很重要的一条协作规范。

滑动手势跟上手

单页内切换最好再补上手势，用户已经从原生习惯了”右滑返回”。手势的标准写法是 touchstart、touchmove、touchend 三件套，核心是在 touchmove 里用 transform: translateX 跟手，松手时按位移决定是完成切换还是弹回去。

注意 preventDefault 的时机。如果页面本身可以纵向滚动，横向手势和纵向滚动会打架，通常的做法是记录第一个 touchmove 的方向，确定是横向之后才阻止默认行为。2013 年还有一个常用手段是给容器加 -webkit-overflow-scrolling: touch，让 iOS 上获得原生级别的惯性滚动，跟手滑动的顺滑度会好很多；但它本身也有坑，在部分 iOS 版本上和 position: fixed 一起用会出现定位错乱。

如果不想自己写手势，当年有几款现成库可以选：iScroll 主要解决 overflow: scroll 在旧系统上的滚动和回弹，Hammer.js 封装了 tap、swipe、drag 等手势识别，Swiper 则专注轮播和多屏滑动。三者的共同建议是不要全引，按需引，每个库都在监听 touch 事件，叠多了事件处理会互相干扰。

性能：动画该动什么

CSS3 动画和 jQuery 的 animate() 在当年是两条路线。差别不在语法，而在动画跑在哪：transform 和 opacity 可以由合成线程处理，不触发主线程的布局计算；而 left、top、width、height 每一个像素的变化都要重新布局再重绘。

一个直观的对比：

方案 每帧开销 是否触发重排 低端机表现
left / top 高 是 明显卡顿
margin-left 高 是 明显卡顿
transform: translate() 低 否 基本流畅
opacity 低 否 基本流畅

所以结论很简单：动画只动 transform 和 opacity。位移用 translateX/Y，缩放用 scale，旋转用 rotate，都不要写成改变几何尺寸的形式。如果非要做”高度展开”，可以用 scaleY 配合 transform-origin 模拟，或者干脆用 max-height 配合一个足够大的值加 transition，后者虽然触发布局，但元素不多时代价可以接受。

卡顿的原因归纳起来主要是这几个，排查时按顺序看：

  1. 同时改变多个会触发重排的属性，浏览器一帧内要做多次布局。能合并成一个 transform 就合并。
  2. 布局层级过深，一个元素变化导致大片区域重新计算。动画元素尽量靠近合成层，减少祖先层级。
  3. 动画期间加载或解码图片，主线程被图片解码占住。首屏之外的图先别急着加载。
  4. box-shadow、filter、圆角这些效果在低端 GPU 上很贵，动画元素上尽量不要叠。
  5. 触摸事件里频繁读取 offsetTop、scrollTop 这类布局属性，强制同步重排。

最后一个值得单独说：iOS 上给元素加 translate3d(0, 0, 0) 或 translateZ(0) 可以强制提升为合成层，很多时候能救活一个卡顿的动画；但滥用会让内存占用上升，图层过多反而更卡。用它定位问题可以，不要当成默认习惯。

小结

移动端页面切换动画先分场景：同一个文档用 class 切换加 CSS3 transition/animation，跨文档就用原生转场或者跳转前后各补一段短动画。单页内切换要自己处理后退键和状态保持，跟手滑动用 touch 三件套加 translateX 实现，松手按位移决定完成还是回弹。动画只动 transform 和 opacity，避免同时改变多个触发重排的属性，警惕层级过深、图片解码和昂贵视觉效果的叠加。CSS animation 比 transition 更容易处理初始状态，both 关键字能省掉手动补默认值。最后记住 2013 年的兼容底线：Android 2.x 基本放弃动画，iOS 6 以上和 Android 4.0 以上才能放开手脚。
