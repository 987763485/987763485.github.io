jQuery 源码架构：Sizzle 选择器引擎

$('#list li.active') 这样一句代码，每天被写成千上万次，却很少有人想过它内部发生了什么。jQuery 把选择器解析这项工作交给了一个叫 Sizzle 的独立引擎，由 John Resig 在 2009 年创建并从 jQuery 中独立出来，jQuery 1.9 起它作为内置组件随库一起分发。本文复盘 Sizzle 要解决的问题、它编译选择器的完整流程、缓存与匹配策略，以及那些 jQuery 专有扩展伪类是怎么插进去的。

Sizzle 要解决什么问题

在 2009 年前后，浏览器原生的选择器 API 是一片沼泽。document.querySelectorAll 在 CSS3 选择器子集上已经可用，但各家的实现进度和质量差别巨大：IE 8 只支持 CSS 2.1 的一个子集，还有一些实现存在真实 bug——某些属性选择器、兄弟选择器组合在特定文档结构下会漏匹配或误匹配，甚至直接抛异常。写库的人没法信任”原生 API 一定对”。

更要紧的是 jQuery 需要扩展伪类。:visible、:animated、:first、:eq(2) 这些语义在 CSS 规范里根本不存在，只属于 jQuery 自己，原生 API 不可能提供。于是必须有一个自己的引擎，能够解析任意选择器字符串、编译成可执行的匹配函数，并允许注册自定义伪类。

Sizzle 的定位因此很清楚：它是一套可移植的选择器解析与匹配引擎，负责把字符串变成函数；至于从哪个候选集里挑元素，它可以自己走 DOM，也可以优先交给原生的 querySelectorAll。这也解释了为什么 jQuery 要把它独立出来——Sizzle 在 jQuery 里以 Sizzle 这个内部对象存在，同时通过 $.find 暴露给外部使用，两者本质是同一套东西。

编译流程：从字符串到匹配函数

Sizzle 拿到一个选择器字符串，并不是每次都现解析。它把整个过程分成三步：词法分析、生成 token 化结果、编译成匹配函数。

    A[选择器字符串] --> B{缓存命中吗}
    B -->|是| C[取出已有编译结果]
    B -->|否| D[词法分析 正则切分]
    D --> E[生成 token 数组]
    E --> F[按 token 生成匹配函数]
    F --> G[存入缓存]
    G --> H[执行匹配 返回元素集合]
    C --> H

词法分析与 token 化

第一步是把字符串切成一个个 token。这一步几乎完全靠一组精心构造的正则表达式完成：每个正则负责识别一类片段——ID（#id）、类名（.cls）、标签名（div）、属性（[attr=val]）、伪类（:name(arg)）以及关系符（空格、>、+、~）。

以 #list li.active:first 为例，切分后的 token 大致是：ID 为 list、一个后代关系符、标签 li、类名 active、伪类 first 不带参数。这一步同时承担了去空白、把连续空白合并为单个后代关系符的工作。字符转义（比如类名里带点的 .a\.b）也在这层被还原，token 拿到的是真实值而非字面量。

匹配策略：为什么是右到左

Sizzle 的匹配方向是从右往左。以 #list li.active 为例，它先找出所有 .active 的元素，再逐个向上验证其祖先链上是否存在 #list。这个方向不是 jQuery 发明的——浏览器原生的 querySelectorAll 同样是 RTL 实现，因为这是唯一能在不支持 XPath 的 DOM 上高效执行后代选择器的方式：从最具体的右端条件出发，候选集最小，向上回溯的验证成本也低。

Sizzle 内部把这一策略具象化为”块”的处理顺序。块从右往左消费，每个块内部则按 DOM 结构从左往右收缩候选集。对于位置伪类（见下一节），这种顺序还带来一个额外好处：右端的块已经缩小了候选集，位置计算只需要在一个小集合上进行。

如果浏览器原生 API 可用且可靠，Sizzle 会优先走原生路径，只有原生不支持或抛异常时才降级到自己的实现。这个降级逻辑在源码里体现为对 querySelectorAll 的探测与 try/catch 包裹。

原生优先与降级：Sizzle.selectors 与 Sizzle.contains

Sizzle 内部有几个可替换的钩子，用来在不同浏览器间切换实现：

  • Sizzle.selectors：提供各种基础匹配能力的实现集合（按 ID 查找、按标签查找、按类名查找、获取子元素、判断包含关系等）。jQuery 在初始化时会用特性检测的结果挑一套最快的填进去。比如有新 API 的浏览器就走原生，老 IE 只能靠遍历。
  • Sizzle.contains：判断一个节点是否包含另一个节点。没有标准的 compareDocumentPosition 时，用 IE 私有的 contains 方法替代。

querySelectorAll 优先的完整逻辑大致是：先用一个正则判断选择器是否只包含”原生能可靠支持”的部分（没有扩展伪类、没有 jQuery 专有语法），如果满足就直接调原生 API 拿到结果，再用 Sizzle.uniqueSort 去重排序；一旦原生调用抛异常（老版本浏览器的已知 bug），立刻回退到自己的引擎。这就是”为什么 jQuery 不直接用 querySelectorAll“的答案：能用的时候确实在用，但必须留一条自己的路。

jQuery 专有扩展伪类

扩展伪类是 Sizzle 最具 jQuery 色彩的部分。它们通过 Sizzle.selectors.pseudos 注册，编译时被当成普通匹配函数插入到匹配链里。

位置伪类是最特殊的一类，因为它们的语义依赖候选集而非单个元素：:first 不是”某元素的第一个子元素”，而是”当前匹配结果里的第一个”。Sizzle 对这类伪类做了专门处理——它们不参与逐元素的匹配，而是在得到候选集之后再过滤。

实际可用的扩展伪类按用途可以分几组：

  • 可见性：:visible、:hidden。实现依赖 offsetWidth、offsetHeight 或 getClientRects 是否为零，属于”必须靠 JS 判断”的典型，原生 CSS 没有对应物。
  • 动画状态：:animated。匹配当前有 jQuery 动画在跑的元素，直接查询内部的定时器队列。
  • 结构类：:header（h1 到 h6）、:first、:last、:even、:odd、:eq(n)、:nth(n)、:gt(n)、:lt(n)。这一组都是位置或结构语义，全部依赖结果集。
  • 表单类：:input、:text、:checkbox、:radio、:button、:submit、:password、:file、:image、:reset。本质是按 type 属性和标签名分组。

位置伪类的”特殊处理”值得多说一句。因为 :eq()、:gt() 这类需要在结果集上切片，Sizzle 的做法是在编译期把它们标记为位置类，执行时先把右边所有条件跑完拿到候选集，再做一次索引过滤。这也就是为什么 $('li:eq(0)') 拿到的确实是所有 li 里的第一个，而不是每个父元素下的第一个——语义上它更接近”结果索引”而不是”结构位置”。

为什么 jQuery 不直接用 querySelectorAll

把理由集中列一下，逻辑就完整了：

第一，兼容性。IE 8 的 querySelectorAll 只覆盖 CSS 2.1 子集，且存在若干真实 bug；IE 7 及以下干脆没有这个方法。一个要支持到 IE 6/7/8 的库，不可能把正确性押在原生实现上。

第二，扩展伪类。:visible、:animated、:header、:input 这些 jQuery 自己的语义，原生 API 不认。带这些伪类的选择器必须走自己的引擎。

第三，性能反而不一定更好。原生 querySelectorAll 返回的是一个静态 NodeList，而且规范要求结果按文档序去重；当选择器包含 jQuery 专有语法时，jQuery 还要再做一次后处理。在”选择器被反复使用”的场景下，Sizzle 的编译缓存加上对候选集的手动收窄，往往比反复调原生 API 更快——这也是 Sizzle 花大力气做编译缓存的动机。

第四，可控性。库需要一个统一的入口来做去重、排序、uniqueSort，以及在上下文节点上限定查找范围。自己掌握匹配过程，才能保证行为在所有浏览器里一致。

从源码结构看 jQuery 的分层

把镜头拉远一点，Sizzle 在 jQuery 里的位置体现了这个库一贯的分层思路：jQuery 核心只管选择器入口、DOM 操作、事件、Ajax 这些高层能力，选择器匹配这种”与具体业务无关、又与浏览器耦合极深”的活，单独拆成一个可替换的模块。

这几行挂载很能说明问题：$.find 是选择入口，$.expr 把整套匹配器暴露给外部，$.expr[":"] 就是扩展伪类的注册表，写插件时想加自己的伪类（比如 :intable）就往这里塞。这种”核心留接口、实现可替换”的设计，是 jQuery 插件生态能长起来的结构性原因之一。

小结

Sizzle 是 John Resig 2009 年从 jQuery 中独立出来的选择器引擎，jQuery 1.9 起内置，$.find 直接指向它。它要解决的是原生选择器 API 兼容性差、且无法表达 jQuery 扩展伪类这两个问题。内部流程是词法分析切分 token、按块编译成匹配函数、缓存编译结果，匹配时从右往左消费块，位置伪类则在候选集上二次过滤。原生 querySelectorAll 在可用且可靠时会被优先调用（Sizzle.selectors、Sizzle.contains 提供了跨浏览器的底层能力替换），失败时降级到自身实现。对使用者的实用启示有两条：不要在循环里拼接动态选择器，那会让编译缓存无限增长；理解 :eq() 是结果索引而非结构位置，能避开大部分语义误用。
