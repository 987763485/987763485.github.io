JavaScript 数组常用方法详解

数组大概是前端日常打交道最频繁的对象。ES5 在 2009 年定稿时给 Array.prototype 补上了一整组高阶方法，从此”遍历数组”这件事有了统一写法。但方法多不等于用得对：回调里的三个参数分别是什么、第二参数 thisArg 有什么用、reduce 不给初始值会怎样、稀疏数组为什么会被悄悄跳过、排序为什么把 10 排在 9 前面——这些细节不理解，写出来的代码就会在某个边界上莫名其妙出错。本文按”迭代类、归约类、查找类、增删类、排序类、检测类”的顺序，把 ES5 时代可用的数组方法逐个讲清。

先看共性：所有迭代方法都长什么样

forEach、map、filter、some、every、reduce、reduceRight 这一组方法有一个统一的约定：第一个参数是回调函数，回调函数接收三个参数，分别是当前元素的值、当前下标、数组本身。

第三个参数最容易被忽略，但它有一个非常实用的场合：回调里需要”除了当前元素以外的整体信息”时，不必再去外层作用域找变量，直接拿 array 即可。不过要注意它是原数组的引用，不是副本，改它等于改原数组。

这一组方法还有第二个参数 thisArg，用来指定回调函数里的 this。不传时回调里的 this 是 undefined（严格模式）或全局对象（非严格模式），这是 ES5 与 ES3 最大的行为差异之一。

jQuery 的 $.each 没有 thisArg，jQuery 内部是用 call 显式绑定的；原生这一组则是通过第二个参数传递，两者思路不同但目的一致：让回调能安全地访问外部对象。

迭代三兄弟：forEach、map、filter

forEach 是最纯粹的遍历，它的返回值是 undefined。如果循环体里写 return，效果等同于 continue——只是跳过当前这一轮，不会中止整个循环。要中止必须用 for 循环配 break，或者换用 some/every。

map 的回调返回值会被收集成一个等长的新数组，长度与原数组严格一致，回调返回 undefined 也会占位。它适合”结构相同的转换”，比如把一组接口数据转成视图需要的形式：

三者的共同点是都不修改原数组，返回的都是新数组（forEach 除外）。这是函数式写法的好处，也是与 splice/sort/reverse 那一组最本质的区别。

归约：reduce 与初始值

reduce 把数组”折叠”成一个值，回调接收四个参数：累计值、当前元素、当前下标、数组本身。第二个参数是初始值。

初始值给不给，行为差别很大：

  • 给了初始值，reduce 从下标 0 开始遍历，累计值的第一轮就是初始值。
  • 不给初始值，第一轮的累计值取数组的第一个元素，遍历从下标 1 开始。

不给初始值有三个坑。第一，空数组会直接抛 TypeError；第二，只有一个元素时回调根本不会执行；第三，如果第一个元素是字符串、对象之类，后续”加法”行为会和预期完全不同：

工程上的结论是：永远显式传初始值。它让代码的自解释性变强，也顺带消掉了空数组崩溃的风险。

reduceRight 与 reduce 完全相同，只是遍历方向从右往左。它的典型用途是把一个”右结合”的结构展开，或者按相反顺序拼接字符串：

短路判断：some 与 every

some 是”存在即真”，every 是”全部为真”，两者的共同优点是可以提前退出：一旦结果确定就不再遍历剩下的元素。这一点在数据量大、或回调里有副作用时，比 forEach + 标志位高效得多。

它们也常被用来实现”数组是否包含某元素”，虽然语义上绕了一层，但在没有 includes 的年代这是标准做法。需要按下标查找时才用 indexOf。

稀疏数组：被悄悄跳过的空洞

ES5 给数组方法加了一条统一规则：回调不会在稀疏数组的空洞上调用。也就是说，下面这个数组实际只会回调两次：

这条规则适用于 forEach、map、filter、some、every、reduce。它带来两个后果：map 处理稀疏数组时，返回的新数组在相同下标上仍然是空洞；reduce 不给初始值时遇到空洞不会跳过累计值，会直接把空洞的 undefined 传给回调。

稀疏数组通常不是有意构造的，而是 new Array(5)、arr[10] = 1 或者 JSON 解析异常造成的。若业务上不允许空洞，最稳妥的做法是显式填充后再处理：

遍历中修改数组：最常见的自伤行为

forEach 与 map 的规范都要求：遍历过程中访问的下标是递增的，且在回调执行期间会读一次当前数组长度。于是”遍历时删元素”必然出问题。

原因是删掉下标 1 的 2 之后，3 挪到了下标 1，而循环下一轮恰好访问下标 1，于是 3 被处理两遍，5 则彻底漏掉。结论：不要在 forEach/map/filter 的回调里增删原数组。需要删除时，先用 filter 得到新数组，再赋值回原变量；或者倒序用 for 循环配 splice，这样前移不会影响尚未访问的下标。

排序：sort 的默认行为是个陷阱

原因正是字符串比较："10" 的第一个码元 "1" 小于 "2"，于是 10 排在了 2 前面。所有需要按数值排序的场合，都必须传比较函数：

比较函数的返回值只关心正负：负数表示 a 排在 b 前，正数表示在后，0 表示相等（在 ES5 之前各引擎对 0 的处理并不一致，ES5 规范统一了行为）。sort 是原地排序，直接修改并返回原数组，这是共享数组被悄悄改掉的头号来源。

另一个少有人注意的细节：sort 会把 undefined 全部移到数组末尾，且排序过程中回调在下标上的调用顺序取决于引擎实现，规范并未承诺稳定排序。需要稳定排序的年代，通常的做法是自己写”原下标 + 值”的包装比较：

增删改：splice 一家与 concat/slice

splice 是数组方法里唯一”既能删又能插”的原地操作，签名是 splice(start, deleteCount, ...items)，返回被删掉的元素组成的新数组。记不清参数顺序时，记住”第二个参数是个数”就不会把删除写成插入。

slice(start, end) 是浅拷贝，返回新数组，不碰原数组，end 不含；concat 则是把参数逐个拼接，返回新数组，同样不动原数组。两者配合可以做出”不可变”风格的更新：

push/pop 在尾部操作，shift/unshift 在头部操作，都返回有意义的数值或元素，且都是原地操作。要留意 shift 与 unshift 会让后面所有元素的下标平移，在长数组上成本不低。

reverse 原地反转，join 用指定分隔符拼成字符串，toString 等价于不带参数的 join(',')。这一组都是从 ES3 就有的老方法，行为稳定，唯一的共同风险就是”原地修改”。

Array.isArray：typeof 与 instanceof 为什么不够

判断一个值是不是数组，ES5 给出的标准答案是 Array.isArray。为什么不用 typeof？因为数组的 typeof 结果是 'object'，它无法把数组与普通对象、null 区分开。

为什么不用 instanceof Array？因为它依赖原型链，而原型链是跟着执行环境走的。浏览器里每个 window/frame 都有自己的一套全局对象和构造函数，页面 A 里创建的数组，在iframe B 的脚本里 instanceof B.Array 就是 false：

Array.isArray 的实现不依赖构造函数，它检查的是对象内部的 [[Class]] 标记，因此跨 frame、跨 realm 都准确。凡是可能接触到来自 iframe、window.open 或其他全局环境的数据，判断数组就必须用它。

上面这个写法同时兼容真数组和”类数组”（arguments、NodeList、jQuery 对象），是 2013 年写通用组件时的常见防御。

小结

ES5 的数组方法可以分成两大家族：forEach、map、filter、reduce、some、every、indexOf 这一族不碰原数组，回调参数统一是（值，下标，数组）并可传 thisArg；splice、sort、reverse、push、pop、shift、unshift 这一族全部原地修改，用的时候必须意识到原数组已经变了。reduce 要显式传初始值，sort 必须为数值传比较函数，forEach 里不要增删原数组，稀疏数组会被静默跳过，判断数组只用 Array.isArray。把这些边界记牢，比记住方法名更重要——方法名查文档就有，边界只会以 bug 的形式出现。
