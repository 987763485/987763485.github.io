网页性能优化全景：关键渲染路径

前端性能优化这个领域，2010 年之前靠的是经验和零散的技巧，2010 年之后才开始有了一套可解释的理论框架。这个框架就是关键渲染路径（Critical Rendering Path，简称 CRP）。它回答了一个根本问题：浏览器从拿到字节到画出像素，中间到底经历了什么。一旦看清了这条路径，绝大多数优化手段就不再是”据说有效”的偏方，而是”缩短某一段路程”的必然选择。本文把这条路径从网络层到合成层完整走一遍，并给出每一段对应的优化手段与实测方法。

理解关键渲染路径的价值，可以用一个类比：一条工厂流水线，产出是屏幕上的第一屏像素。任何一个工位慢了，整条线都要停下来等它。CSS 没下载完，渲染树就建不起来；头部一个同步脚本没执行完，解析就得停住。所以优化的第一课不是”怎么让它更快”，而是”谁在等谁、等的是哪一段”。

从字节流到 HTML：网络层做了什么

用户在地址栏敲下网址后，浏览器要做的第一件事是把服务器上的字节取回来。这一段常被前端忽略，但它往往是耗时最长的一段。

首先是域名解析。浏览器先查自己的 DNS 缓存，没命中就查操作系统缓存，再没命中才向本地域名服务器发起递归查询。一个域名从零开始解析，常见耗时在几十到几百毫秒之间，跨运营商和国际线路时可能更长。DNS 查询的结果会被缓存一段时间，由域名的 TTL 决定。这就是”减少 DNS 查询”这条老规则的理论依据：解析本身就是一次实打实的网络往返。

解析出 IP 之后是建立连接。HTTP/1.1 时代，每个域名下的并发连接数有限制（浏览器常见是 6 个），每次新建 TCP 连接都要三次握手，如果走 HTTPS 还要加上 TLS 握手与证书校验，这又是两三个往返。TCP 的慢启动（slow start）机制决定了连接初期的发送速率是逐步爬升的，一个新连接传不了多少字节就要等确认。这也是为什么大文件要合并、小文件要压缩——新建连接的固定成本必须靠”一次多传点东西”摊薄。

连接建立后，请求发出，服务器处理，第一个字节到达的时间就是首字节时间（TTFB）。然后是逐段传输，浏览器一边收字节一边做后面的解析工作——这正是 HTML 流式处理的起点。

flowchart TD
  A[输入 URL] --> B[DNS 解析]
  B --> C[TCP 三次握手]
  C --> D[发送 HTTP 请求]
  D --> E[服务器处理与响应]
  E --> F[首字节到达 TTFB]
  F --> G[HTML 字节流持续到达]
  G --> H[解析器边收边解析]

这里要建立一个数字感：一个典型的宽带访问，DNS 加握手可能占去 100~300 毫秒，TTFB 几十到几百毫秒，而 HTML 本身可能只有几十千字节、传输只用几十毫秒。换句话说，在 2013 年的网络条件下，网络层的固定开销常常大于实际传输时间。CDN 之所以有效，是因为它同时缩短了地理距离带来的往返延迟、分担了连接建立成本、并让解析请求落在更近的节点上。

HTML 解析与预加载扫描器

浏览器拿到字节流后并不是等整个文档下载完才动手。HTML 解析器是增量式的：字节到达、分词、构造节点、遇到引用外部资源的标签就把下载任务交给网络层，然后继续往下解析。

这一步里有一个常被低估的组件——预加载扫描器（preloader / speculative parser）。它的作用是：主解析器按文档顺序推进，遇到一段很大的同步脚本时要停下来等它下载执行，此时扫描器会继续往后看，把后面出现的图片、样式表、脚本的下载任务提前派发出去。这样即使主解析器被阻塞，后面的资源也已经在下载中了。

预加载扫描器带来两个很重要的推论。第一，把样式表放在文档靠前的位置是有实际收益的，因为它会更早被发现、更早开始下载，CSSOM 也就更早就绪。第二，用 JavaScript 动态插入的资源，扫描器在解析阶段是看不见的——它只能看到 HTML 文本里的标签。所以 document.createElement('script') 动态插入的脚本，浏览器在初始解析时完全不知道它的存在，必须等脚本跑起来、插入节点后才开始下载。这是动态插入资源比静态引用慢的根因。

还有一个细节与字节效率有关：尽早发送字节比攒一个大响应更好。服务器如果等整个页面渲染完再一次性输出，浏览器就完全没有提前解析的机会；而如果先输出 HTML 头部并 flush，浏览器就能立刻开始解析头部、下载样式表。这解释了为什么模板引擎与服务器端渲染应该尽早 flush，以及为什么”尽早刷新缓冲区”会成为雅虎规则里的一条。

DOM 树构建

HTML 解析的产物是 DOM 树。解析过程由 HTML5 规范精确定义：字节流先经过编码判定（优先看 BOM，再看 meta charset，再看响应头，最后靠启发式），解码成字符流；然后经过分词器（tokenizer）产出标签与文本；再经过树构造阶段（tree construction）按规范的状态机把节点挂到树上。规范之所以把错误恢复行为也逐条定义，是为了让各家浏览器对同一份畸形 HTML 得到相同的 DOM——这也是 HTML5 与 HTML4 在工程上最大的区别之一。

树构造阶段有几个对性能有实际影响的规则：

  • 遇到 <link rel="stylesheet">，解析器不阻塞，但该资源会被加入渲染阻塞集合，后续见下文。
  • 遇到没有 defer 或 async 的 <script>，解析器必须停下来，下载并执行完这个脚本才继续。原因是脚本可能通过 document.write() 往文档流里插入内容，后面的解析结果可能因此改变。
  • 遇到 <img>、<iframe> 等，解析不阻塞，下载任务派发出去就继续走。
  • 表格布局、浮动、display: table-cell 等会让浏览器走一些额外的重算路径，但这些属于布局期，不在解析期。

DOM 树的规模直接影响后面的布局与样式计算。节点数从一千涨到一万，样式匹配与布局的开销不是线性涨十倍，因为影响范围会扩散。所以”减少 DOM 元素数量”这条老规则，本质是在给后面的每一个阶段减负。

CSSOM 树构建

浏览器发现样式表后开始下载，下载完成后由 CSS 解析器处理。CSS 的解析比 HTML 简单——它是可回溯的、规则驱动的词法语法，没有 HTML 那套复杂的状态机。解析的产物是 CSSOM：一棵由规则组成的树，每个节点携带该元素生效的样式信息。

CSSOM 有两个关键特性，都源于 CSS 语言本身的设计。

第一是层叠（cascade）。同一个元素可能被多条规则命中，必须按优先级算出一个最终值。优先级由选择器的特异性（specificity）、来源（作者样式、用户样式、浏览器默认样式）、出现顺序共同决定。这意味着 CSSOM 的构建不是简单的”收集所有规则”，而是要对每条规则做匹配、合并、覆盖计算。选择器写得太复杂、嵌套太深，特异性计算与匹配的成本就上去。

第二是继承（inheritance）。像 color、font-family、line-height、visibility 这类可继承属性，父元素上算出的值要沿树往下传。这决定了 CSSOM 必须按树的层次组织，而不能拍平成一个列表——子节点的最终值可能依赖父节点的计算结果。也正因如此，浏览器不会”部分应用”CSS：必须整棵样式表都处理完，才能保证继承值是正确的。

flowchart TD
  A[HTML 字节流] --> B[DOM 树]
  C[CSS 字节流] --> D[CSS 解析]
  D --> E[层叠计算 特异性 来源 顺序]
  E --> F[继承传递]
  F --> G[CSSOM 树]
  B --> H[合并]
  G --> H
  H --> I[渲染树]

这里藏着一个重要的结论：浏览器无法在 CSS 未全部就绪的情况下安全渲染。因此 CSS 是渲染阻塞（render blocking）资源。任何放在头部的外链样式表，都会把首屏绘制推迟到它下载完成之后。这不是浏览器的保守，而是语言语义决定的——它不知道后面还有没有规则会覆盖当前算出的值。

Render 树构建

DOM 与 CSSOM 都就绪后，浏览器把两者合并成渲染树（render tree）。渲染树的构造规则有两条常被忽略的排除项：

  • display: none 的元素不进入渲染树。注意这与 visibility: hidden 不同——后者元素仍在渲染树中，仍占据布局空间，只是不可见。这也解释了为什么 visibility: hidden 比 display: none 更容易引发重排：前者改了还要重新布局，后者直接把子树从渲染树摘掉。
  • <head> 里的元素不进入渲染树。<meta>、<title>、<link>、<style>、<script> 都不产生可见盒子，自然不在其中。

渲染树的节点不是一一对应 DOM 节点的。一个元素可能对应一个盒子，也可能是多个（行内元素跨行拆分、li 的标记盒子与主盒子）；反过来，某些 DOM 节点（如上述被排除的）在渲染树里根本没有对应物。这个”不一一对应”是理解后面所有布局与绘制行为的基础。

Layout / Reflow

有了渲染树，浏览器开始计算布局，这一步在不同引擎里叫 layout、reflow、formatting。它要解决的是：每个盒子在视口中的确切位置与尺寸。

布局是一个递归过程，从根元素开始，按文档流顺序确定每个盒子的几何信息。有些属性会立刻触发全局重算——比如视口宽度变化导致所有百分比宽度失效；有些则只影响局部子树。浏览器会做一定的优化：把失效的盒子标记为脏（dirty），在下一帧统一重新计算，而不是每次改动都全页重排。但 2013 年的实现并不完美，读写交替导致的强制同步布局仍是主要的性能陷阱。

布局完成后，如果后续有改动需要重新计算，就称为重排（reflow）。触发重排的因素包括：DOM 结构变化、影响几何的样式变化、视口尺寸变化，以及——最隐蔽的——读取布局信息。读取 offsetWidth、getBoundingClientRect()、getComputedStyle() 等属性时，浏览器必须保证返回值是准确的，于是会把之前所有未应用的样式改动立刻结算成一次同步布局。写一行代码读一个属性，交替进行，重排次数就等于循环次数。

Paint 与 Composite

布局算出的只是几何信息，接下来要把像素填上去，这一步叫绘制（paint / repaint）。绘制是按层与盒子的绘制顺序，把背景、边框、文字、阴影、图片等内容画到一系列绘制记录（display list）里。像 background-color、color、box-shadow、border-radius 这类只影响外观、不影响几何的属性，修改后只需要重绘，不需要重新布局——这是重绘比重排便宜的原因。

在绘制之后还有合成（composite）。浏览器可能把页面分成多个合成层（compositing layer），各层分别绘制成位图，最后由合成线程按层级、透明度、变换等合成到屏幕上。触发提升为独立合成层的常见因素有：3D 变换（translate3d、rotate3d）、will-change 之前的时代里大家常用的视频元素、opacity 动画、Canvas 等。合成动画可以由合成线程直接处理，不必每次打扰主线程重排重绘，这是流畅动画的技术基础。

渲染阻塞与解析阻塞：两种不同的”卡住”

初学者最容易混淆的两个概念是渲染阻塞与解析阻塞。它们的受害者不同，后果也不同。

渲染阻塞（render blocking）指资源未就绪时，浏览器不能进行到”绘制”这一步，但解析仍可继续。典型就是外链 CSS。CSS 阻塞的是渲染树之后的整条链路：没有 CSSOM 就没有渲染树，没有渲染树就不能布局与绘制。所以 CSS 没到位，屏幕就是白的，但 HTML 解析其实可以正常往下走，后面的 DOM 照样建得起来。

解析阻塞（parser blocking）指资源未就绪时，HTML 解析器必须停下。典型就是位于文档流中、没有 defer 或 async 的 <script>。它连累的是解析本身：后面的 DOM 都还没建出来，更谈不上首屏。而且它间接阻塞渲染——DOM 不完整，渲染树也不完整。

flowchart TD
  A[HTML 解析] -->|遇到 link stylesheet| B[派发下载 解析继续]
  B --> C[CSS 就绪前 不生成渲染树]
  A -->|遇到同步 script| D[解析暂停]
  D --> E[下载并执行脚本]
  E --> A
  C --> F[可渲染]

为什么 CSS 放头部、JS 放底部，原因就在这里。CSS 放头部，浏览器尽早发现、尽早下载，解析期间就把 CSSOM 建好了，HTML 解析完立刻能渲染；如果 CSS 放底部，浏览器可能已经解析完整个 DOM 却还在等 CSS，白屏时间被无谓拉长。JS 放底部，是为了让脚本执行时不阻塞首屏 DOM 的构建——放在底部的脚本执行时，首屏内容已经解析完毕。

但”JS 放底部”有个替代方案：defer。它让脚本提前开始下载，又不阻塞解析，还能保证在 DOM 构建完成后、DOMContentLoaded 之前按文档顺序执行。相比之下 async 一下载完就执行，顺序不保证，适合无依赖的分析类脚本。

三种脚本加载方式的时序

同步脚本、defer、async 三者的下载与执行时机完全不同。用一个时序图看最清楚。

sequenceDiagram
  participant P as 解析器
  participant N as 网络层
  participant S as 脚本引擎
  P->>N: 遇到 script 派发下载
  N->>S: 同步脚本下载完
  S->>P: 执行 阻塞解析
  Note over P,S: defer 脚本并行下载
  P->>P: 解析继续 不受阻塞
  Note over P,S: async 脚本下载完即执行
  S->>P: 执行时机不固定
  P->>S: DOM 构建完成
  S->>S: 依次执行 defer 脚本
  S->>P: 触发 DOMContentLoaded

三者的行为可以归纳成一张表。

方式 下载时机 执行时机 是否阻塞解析 执行顺序
同步 <script src> 遇到即下载 下载完立即执行 阻塞 按文档顺序

选型上：页面初始化逻辑、依赖 DOM 顺序的代码用 defer；统计、广告这类彼此独立、无依赖的第三方脚本用 async；极少数需要提前执行又必须同步的场景才用同步脚本，且要放到底部。2013 年的现实是 IE9 及以下不支持 defer 与 async，需要做特性检测并提供回退——把脚本动态插入 DOM 在旧 IE 上同样能避免阻塞，这是当年常用的折中。

资源优先级与预加载

浏览器不是同时下载所有资源的，它有内部优先级。2013 年 Chrome 的实现里，优先级大致是：CSS 最高，其次是按文档顺序出现的脚本，再是阻塞渲染的字体与首屏图片，最低是异步脚本、视频、延迟加载的图片。这个优先级解释了若干现象：为什么先出现的图片比后出现的先下载完；为什么一个头部同步脚本能推迟后面图片的下载（解析停了，扫描器虽在派发，但资源竞争会让路给高优先级项）。

基于这个机制，当年的实践有几个直接推论：

  • 把首屏关键样式表放最前面，让它抢占最高优先级。
  • 非首屏图片不要写在 HTML 里等浏览器自动发现，用 JavaScript 在页面加载后按需替换 data-src，这是懒加载的做法，把带宽让给首屏。
  • 脚本合并要适度：一个巨大的 all.js 会让浏览器把带宽长时间花在高优先级脚本上，反而推迟 CSS 之后的图片。分拆成”核心库 + 按需模块”更利于并行。

viewport 与首屏

在桌面时代，首屏几乎不需要讨论；进入移动端时代后，视口（viewport）成了渲染路径上必须单独看待的一环。

如果页面没有写 viewport 的 meta，移动浏览器会用一个较大的虚拟视口（常见 980 像素）布局整页，再缩小到设备宽度显示。后果是文字被等比缩小，用户要双击放大，而且浏览器实际绘制的是一张”大海报”，首屏要绘制的区域远大于用户真正看到的内容，绘制与合成的成本都上去了。

这一行的作用是让布局视口等于设备宽度，首屏内容按真实尺寸布局。它与关键渲染路径的关系在于：布局视口决定了百分比与媒体查询的计算基准，也决定了首屏需要绘制多少内容。viewport 设置不当，等于让浏览器为一个用户根本不放大的页面做大面积绘制。

移动端还有一点与桌面不同：连接更不稳定、CPU 更弱。桌面上一两百毫秒的解析开销在手机上可能被放大数倍，所以移动端对”减少阻塞、减少请求数、减少字节数”的收益比桌面更高。

脚本置底或 defer DOM 构建 不阻塞解析 交互变晚、旧 IE 兼容
精简与压缩 JS 执行阶段 缩短解析与执行时间 构建复杂度
减少 DOM 节点数 Layout + 样式匹配 缩小布局与匹配范围 结构调整成本
读写分离 Layout 减少强制同步布局次数 代码可读性
用 transform / opacity 做动画 Composite 跳过布局与绘制 合成层内存
图片懒加载 网络层 + 资源优先级 把带宽让给首屏 滚动时才加载
内联关键 CSS CSSOM 构建 消除一次请求阻塞 无法缓存、体积增大

一个完整页面的优化前后对比

下面用一个具体案例把前面的手段串起来。这是一个电商活动页，2013 年的真实结构，测试环境为 Chrome 30、宽带网络、三次取中位数。

优化前的页面结构：

问题一眼可见：四个脚本在头部同步加载，阻塞了解析；四个样式表在脚本之后，被推迟发现；30 个小图标的请求排在后面。

优化后的调整与每一项对应的收益：

  1. 四个脚本合并为一个 app.js，加 defer，并移到 </body> 前。解析不再被阻塞，脚本提前开始下载。
  2. 四个样式表合并为一个 all.css，置于头部第一个阻塞位置。CSSOM 更早就绪。
  3. 30 个小图标合成一张 CSS Sprite。请求数从 30 降到 1。
  4. 首屏之外的商品图改为 data-src 占位，页面就绪后懒加载。
  5. jQuery 与插件分别配置长效缓存，业务代码加指纹。

测量方法上，当年没有统一的性能 API 落地那么广，实践中主要靠三种手段结合：Chrome DevTools 的 Network 面板看瀑布图与请求数、Timeline 面板看 Loading / Scripting / Rendering / Painting 各阶段耗时；WebPageTest 看首次渲染时间（start render）与完全加载时间；以及 performance.timing 在页面里打点记录关键节点。

优化前后的数字感大致是这样（三次取中位数）：

指标 优化前 优化后
请求数 38 9
传输字节 1.2 MB 420 KB
首次渲染时间 2.1 s 0.9 s
DOM 可交互时间 3.4 s 1.5 s
YSlow 得分 62 91

首次渲染时间从 2.1 秒降到 0.9 秒，主要贡献来自两处：头部同步脚本不再阻塞解析，CSS 提前就绪。请求数从 38 降到 9，贡献最大的是精灵图与合并。这个案例说明，收益最大的往往不是最”高级”的手段，而是把阻塞关系理顺。

测量工具

优化必须建立在测量之上，否则只是感觉良好。2013 年可用的工具链有以下几类。

Chrome DevTools 是主力。Network 面板看瀑布图，能看出请求的排队、阻塞、下载各阶段；Timeline 面板记录事件，按 Loading、Scripting、Rendering、Painting 分组，可以定位到具体某一段脚本或某次布局占了多少毫秒。这两个面板的组合，基本能回答”时间花在哪”。

WebPageTest 是线上测量的好工具，可以指定地点与浏览器，看 start render、首字节、完全加载等曲线，还能出视频对比。它的价值在于环境可控、可重复，适合做前后对比。

performance.timing（Navigation Timing API）提供了页面加载各阶段的高精度时间戳，2012 年起主流浏览器陆续支持。把它上报到自己的统计系统，就能得到真实用户的分布，而不是只看到自己机器上的一个样本。

YSlow 与 Page Speed 则把规则固化成评分，适合作为 checklist 逐项核对，但分数高不等于体验好，仍需结合实际指标。

小结

关键渲染路径是一条环环相扣的流水线：网络层取字节，解析器建 DOM，CSS 建 CSSOM，二者合成渲染树，再经布局、绘制、合成变成像素。CSS 因为语义上必须整棵就绪才能保证继承与层叠正确，所以是渲染阻塞资源；同步脚本因为可能改写文档流，所以是解析阻塞资源，两者受害者不同，优化手段也不同。把 CSS 放头部、脚本置底或用 defer，本质是重新排列阻塞顺序，让首屏更早开始绘制。所有优化手段都能在这条路径上找到自己作用的阶段，测量则决定了你该先动哪一段。看清链路，优化就从玄学变成了工程。
