DOM 样式操作与 getComputedStyle

给元素改颜色、改尺寸，最直接的办法是 el.style.color = 'red'，但这只对写在行内样式上的属性有效。一旦想知道”这个元素现在实际是什么颜色”，就必须问浏览器要计算后的值，这就用到了 getComputedStyle。它读起来很方便，却藏着两个大坑：一是读回来的格式和你写进去的格式不一样，二是每一次读取都可能触发重排。本文从”指定值”与”计算值”的区别讲起，覆盖 IE 的 currentStyle 兼容、float 的属性名之争、颜色返回格式，最后落到批量读取的布局抖动与 jQuery .css() 的封装思路。

style 与 getComputedStyle：两套完全不同的值

el.style 对应的是 CSS 属性声明块，也就是指定值（specified value）里最朴素的那一层：你在标签或 JS 里写了什么，它就返回什么。它可读可写，但只反映行内样式，样式表里定义的规则一概看不到。

getComputedStyle 返回的是计算值（computed value），是浏览器把样式表层叠、继承、初始值全部结算完之后的结果。它是只读的快照，反映元素”现在实际长什么样”。

两者的差异可以概括成一张表：

对比项 el.style getComputedStyle
数据来源 行内声明 层叠结算后的结果
可读可写 可写 只读
能看到样式表规则 不能 能
能看到继承值 不能 能
跨浏览器差异 小 大

需要注意的是，”计算值”不等于”渲染后的最终像素值”。规范里有些属性（比如 width 的百分比）在计算值这一步仍是百分比，getComputedStyle 早期各浏览器对”解析到哪一步”的实现并不统一，Chrome 返回实际像素而 Firefox 有时返回百分比。2013 年做兼容时，跨浏览器读宽度不能假定格式，测出来的值要先判断是不是百分比再决定是否二次解析。要拿准确的布局尺寸，更可靠的是 el.offsetWidth、el.clientWidth 或 getBoundingClientRect()。

IE 的 currentStyle 与一套兼容封装

IE 独有的对应物是 el.currentStyle，它是 el.style 的一个属性，同样返回计算后的值。它与标准的 getComputedStyle 有几处行为差异，写兼容代码时都要照顾到：

  • 属性名是驼峰形式：currentStyle.width，没有 getPropertyValue。
  • float 属性在 IE 里叫 styleFloat，标准里叫 cssFloat。
  • 颜色值在 IE 老版本可能返回 #ffff00 这种十六进制，而标准浏览器返回 rgb(255, 255, 0)。
  • IE 不会返回继承来的某些值，行为更接近”就近可用的值”。

float 的属性名是当年最经典的一个小坑。CSS 属性名是 float，但它是 JavaScript 的保留字，不能直接作为对象的点号属性名。IE 的方案是加 style 前缀叫 styleFloat，标准方案是加 css 前缀叫 cssFloat。jQuery 1.9 里为此专门做了一个映射表：

颜色与尺寸：读回来的值和你想的不一样

即使找到了正确的接口，拿到的值也常常”格式不对”。最常见的三类：

第一是颜色。写进去可以是 red、#ff0、rgba(255, 255, 0, 0.5)，读出来在标准浏览器里统一是 rgb(255, 255, 0) 或 rgba(255, 255, 0, 0.5)，关键字和十六进制都会被规范化。IE 老版本则可能返回十六进制，跨浏览器比较颜色必须先归一化。

第二是长度。getComputedStyle 回来的长度几乎总是带 px 的绝对像素值，包括你写 em、% 的属性。想拿数值参与计算，得自己 parseFloat；拿不到的地方（比如 display: none 的元素）会返回空字符串。

第三是简写属性。getPropertyValue('margin') 这种简写在早期浏览器里支持很差，Chrome 返回空，Firefox 可能返回拼接值。稳妥做法是拆开读 marginTop、marginRight 等长属性。

性能：读一次，刷一次

这是本文最该记住的部分。浏览器为了减少重排，会把多次样式修改合并成一次批量重排。但读取计算样式会强制打断这个批量过程：调用 getComputedStyle 时，浏览器必须保证返回的是最新值，于是先把所有挂起的样式变更应用掉、重新布局，再返回结果。

后果就是经典的”布局抖动”（layout thrashing）：在一个循环里交替”写样式”和”读样式”，每一次读都会触发一次重排，N 次循环就是 N 次重排。

动画场景下这一点尤其致命：在 setInterval 里先读位置再设位置，每帧都强制同步布局，帧率会直接崩掉。合理的做法是维护一份自己记录的状态，需要的时候从状态里取，不反反复复问浏览器。

jQuery .css() 的封装思路

jQuery 的 .css() 在内部就是上面这些兼容逻辑的集大成者。以 jQuery 1.9 为例，读取一个样式属性时大致走这样的路径：

flowchart TD
    A[调用 .css prop] --> B{存在 cssHook 吗}
    B -->|是| C[调用 hook.get]
    B -->|否| D[原生 el.style 取值]
    D --> E{取到值了吗}
    E -->|是| F[归一化后返回]
    E -->|否| G{有 getComputedStyle 吗}
    G -->|是| H[getPropertyValue]
    G -->|否| I[el.currentStyle 驼峰取值]
    H --> J[处理浏览器私有前缀与单位]
    I --> J
    J --> F

这个流程图里有两个值得注意的设计。第一，jQuery 先读 el.style，读不到才走 getComputedStyle——因为读行内样式没有重排代价，能省则省。第二，cssHooks 是一个可扩展的钩子机制：每个 CSS 属性可以注册自己的 get 和 set，用于处理 opacity 在 IE 里的 filter、float 的属性名差异、以及 background-position 这类在不同浏览器里格式不一致的属性。

jQuery 1.9 里 .css() 还统一了取值与设值的返回行为：读取时返回字符串，设置时返回 jQuery 对象本身以支持链式调用。对使用者的启示是：能用 .css() 就别自己写 getComputedStyle，除非你在意那一点点重排开销，或者需要读伪元素样式——那是 .css() 覆盖不到的地方。

小结

el.style 是行内指定值，可读可写但看不到样式表；getComputedStyle 是层叠结算后的计算值，只读但能反映真实状态，两者的数据来源和可写性完全不同。跨浏览器要处理三件事：IE 只有 currentStyle、float 有 cssFloat 与 styleFloat 之争、颜色与长度的返回格式不统一。读计算样式会强制刷新挂起的样式变更，因此批量读取与批量写入必须分两段做，否则就是布局抖动。工程上优先用 jQuery .css()，它已经把 el.style 到 getComputedStyle/currentStyle 的降级路径和 cssHooks 扩展点都封装好了；只有在需要读伪元素样式或刻意规避重排时，才值得直接调原生接口。
