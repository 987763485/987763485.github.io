HTML5 History API 打造无刷新单页应用

本文属于《HTML 与 CSS》第 57/62 篇
上一篇系列目录下一篇

2013 年是单页应用真正开始威胁传统多页应用的一年。AJAX 早就成熟了，”点击链接不刷新页面”本身不是新东西，难的是刷新页面、分享链接、前进后退这些老问题——而这正是 History API 要解决的。这篇从 API 本身讲起，对比它与此前 hash 路由的差异，说明哪些坑来自浏览器、哪些坑来自服务端，最后给出一套 2013 年真实可用的路由设计。结论先放在这：History API 是更好的方案，但它的使用前提是你能控制服务端的 URL 回退配置。

pushState、replaceState 与 popstate

History API 的核心是 history.pushState，它做三件事：往历史栈里推一条记录、改变地址栏 URL、不触发页面加载。签名是三个参数：

  • state：与这条记录关联的任意对象，稍后通过 popstate 事件拿到。它会被结构化克隆，不是引用。
  • title：页面标题。这个参数在 2013 年被所有主流浏览器忽略，写了不生效，别指望它，标题还得用 document.title 自己改。
  • url：新的地址栏 URL。必须与当前页面同源，可以带查询串和 hash，但不能跨域。

对应的 history.replaceState(state, title, url) 用法完全一致，区别是它替换当前记录而不是新增一条。典型用途是筛选场景：用户在列表页选了多个筛选条件，如果用 pushState 会往历史栈里堆十几条记录，用户连点十几次后退才能离开；用 replaceState 只更新当前记录，更符合直觉。

state 对象大小是有限制的，且各浏览器不一：Firefox 的实测上限约 640KB，Chrome 早期也有类似量级的约束。工程上的常识是只放必要信息——分页号、筛选条件、滚动位置，不要把整个数据集塞进去。结构化克隆意味着它也不能存函数和 DOM 节点。

用户点浏览器后退按钮时触发 popstate 事件，事件对象上带着当前记录的 state。它和前面两个方法合起来，构成了无刷新路由的三个基本件。

这里有一个 2013 年必须知道的坑：popstate 在页面加载时也会触发一次（Chrome 与 Firefox 的行为），此时 state 是 null 或者首次 pushState 之前的状态。如果你把 popstate 当成唯一的渲染入口，会看到页面初始加载时渲染了两次或者渲染了空视图。稳妥做法是在 popstate 回调里判空兜底，同时用 history.state（如果不支持就用初始 state 变量）区分首次进入。

另一个细节：pushState 本身不触发任何事件。所以点击站内链接时，你要自己负责改视图，再调 pushState；而 popstate 负责的是”历史栈变化后同步视图”。两条路径写清楚，代码才不会打架。

与 hash 路由的对比

在 History API 之前，实现”无刷新改 URL”的主流做法是操作 location.hash，配合 hashchange 事件。两者路线不同，选型前必须先看清差异。

维度 hash 方案 History API
URL 形态 /app#/list/2 /app/list/2
兼容性 IE8+ 支持 hashchange IE10 起支持，IE9 及以下完全没有
服务端配置 无需特殊处理 必须配置 fallback，否则刷新 404
分享与 SEO hash 通常不被爬虫抓取 真实路径，可被抓取与收录
state 容量 受 URL 长度限制，几乎存不了 Firefox 约 640KB

hash 方案的本质是把状态编码进 URL 的片段标识符。片段标识符从不发送到服务端，浏览器只把它交给页面自己解析，所以任何路径刷新都是同一个 HTML，服务端零配置。它的代价是 URL 丑陋、状态表达能力弱（只能在 hash 里塞字符串）、SEO 基本放弃。

History API 的 URL 是真实路径，看起来和传统多页应用没有区别，爬虫可以抓，分享出去别人点开就是正确页面。但它把一部分责任推给了服务端——这是下一节的主题。

兼容性是 2013 年选型时绕不开的问题：IE10 才开始支持 History API，IE9 及以下连 pushState 都不存在。如果项目必须照顾 IE9 及以下，结论没有商量余地：用 hash 方案，或者两者并存——检测到不支持时自动降级到 hash。一个常见的折中是把 hash 与 path 统一抽象成路由对象，底层按能力切换。

刷新 404：服务端必须配合

pjax：pushState 加 AJAX 的渐进路线

2013 年由 Chris Wanstrath 提出的 pjax 是这条路上最务实的中间方案。它的思路很简单：拦截站内链接的点击，用 AJAX 拉取目标页面，抽出其中的主体内容替换到当前页面，同时用 pushState 更新地址栏。

pjax 的价值在于”渐进”：它不要求整个站点重写成单页应用，可以一个页面一个页面地接入，老的链接结构完全保留，服务端只需要多吐出一个片段版本。对当年的传统站点来说，这比”全面转向单页应用”的现实可行性高得多。它也有显而易见的局限：只处理站内链接，动态数据、表单状态、第三方脚本都需要额外照顾；页面间的脚本重复执行要靠约定管理。

路由设计：几个必须提前定的规则

无刷新单页应用一旦跑起来，路由就是整个应用的骨架。2013 年的实践里，下面几条是必须先定好的。

URL 与 state 的映射要可逆。 任何视图都要能从一个 URL 完整恢复，这是”分享链接”和”刷新不丢状态”的前提。把视图状态拆成 URL 里的部分和存在 state 里的部分，原则是：值得分享和书签化的进 URL，临时的（滚动位置、输入草稿）进 state。

拦截范围要明确。 只接管站内链接，外链、新窗口打开、带 target 的链接、带修饰键的点击都要放行。漏掉任何一类都会出现”点了链接页面没反应”的投诉。

首次进入的数据复用。 服务器渲染的 HTML 里已经包含了首屏数据，前端路由如果无脑再发一次 AJAX，就是双倍请求。合理做法是首屏直接用服务端输出，后续交互再走前端。

flowchart TD
  A[用户点击站内链接] --> B{是否外链或新窗口}
  B -->|是| C[放行 交给浏览器]
  B -->|否| D[拦截默认行为]
  D --> E[AJAX 拉取目标页面]
  E --> F[抽取主体内容与标题]
  F --> G[替换当前页面主体]
  G --> H[pushState 更新地址栏]
  H --> I[执行页面级初始化脚本]
  J[用户点后退] --> K[popstate 触发]
  K --> L[读取 state 恢复视图]
  L --> I

SEO 与爬虫。 2013 年 Google 对 AJAX 抓取的约定是 _escaped_fragment_：爬虫发现带 hash 的 AJAX 站点时，会把 #! 之后的内容转换成 ?_escaped_fragment_= 参数重新请求，服务器看到这个参数就返回渲染好的 HTML 快照。这个约定主要服务于 hash 方案的抓取，用 History API 的真实路径时，更直接的做法是让服务器对爬虫 User-Agent 返回静态化页面。前提是你的站点值得为 SEO 投入——后台系统类的单页应用，直接配 robots.txt 禁爬更省事。

小结

History API 用 pushState 与 replaceState 让无刷新切换和真实 URL 得以共存，popstate 统一了前进后退的处理入口，但 title 参数被浏览器忽略、state 有容量上限、首次加载会触发一次 popstate 这些细节都要提前知道。它与 hash 方案的核心差别在兼容性与服务端责任：hash 靠 IE8 就支持的 hashchange 换来零服务端配置，History API 用 IE10 起支持换来了真实路径与可抓取性。pjax 提供了渐进接入的中间路线。选型时先回答两个问题——要不要兼容 IE9 及以下，能不能改服务端 fallback 配置；两个答案都肯定，History API 就是正确答案，剩下要做的只是把服务端 try_files 配对、把路由的 URL 映射做可逆。
