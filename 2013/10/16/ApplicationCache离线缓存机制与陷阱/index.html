Application Cache 离线缓存机制与陷阱

本文属于《HTML 与 CSS》第 52/62 篇
上一篇系列目录下一篇

2013 年做”离线可用”的 Web 应用，答案几乎只有一个：HTML5 的 Application Cache。它在当年是个诱人的方案——一份 manifest 文件，几行声明，页面就能在断网时继续打开。但用过的人都知道，这个特性的坑比文档写的多得多。这篇以一次真实的踩坑复盘为线索，把 AppCache 的机制、更新模型、调试方法，以及那些当时反复折磨团队的怪毛病一次讲清。需要说明的是，它今天已经被标准废弃了，而这份”不能移除”的痛点，恰恰是它退出历史舞台的原因。

它是什么：一次声明，整站离线

AppCache 的核心思路是让浏览器把一组资源缓存到本地，之后不再访问网络。使用方式朴素得可爱：写一个 manifest 文件，在 HTML 标签上引用它。

浏览器看到这个属性，会按照 manifest 的规则下载并缓存资源，之后对这个域名的请求会优先命中本地缓存。manifest 文件的 MIME 类型必须是 text/cache-manifest，配置错了浏览器会静默忽略整个文件，页面表现为”时而离线时而不行”——这是新手第一个坑。以 Nginx 为例：

manifest 的三段式语法

manifest 是纯文本文件，第一行固定是 CACHE MANIFEST，之后分三段，段名必须顶格大写：

  • CACHE: 段列出需要离线缓存的资源，默认段，可以省略段名（文件开头到第一个段名之间的内容都算隐式缓存段）。
  • NETWORK: 段列出始终走网络的资源。这个段的资源在线时正常请求，断网时访问它们会失败。
  • FALLBACK: 段给出”访问失败时的替代资源”，格式是”请求路径 替代资源路径”。上面的写法表示：任何网络请求失败时，用 /offline.html 兜底。

还有一个容易忽略的规则：引用 manifest 的那个 HTML 页面自身会被自动加入缓存，不需要在 CACHE 段里重复写。但反过来，只被 manifest 引用、页面里没有出现的资源也会被缓存——AppCache 的缓存集完全由 manifest 决定，与页面实际加载了什么无关。

更新机制：manifest 变了才会更新

AppCache 的更新判断规则简单到粗暴：浏览器只在 manifest 文件内容发生变化时才触发更新。CACHE 段里列的文件内容改了、文件名没改，manifest 一字未动，浏览器就不更新——这是它最反直觉的地方，也是”为什么我改了 CSS 不生效”的标准答案。

工程上的标准做法是在 manifest 里放一行版本注释，每次发版改一下这行：

window.applicationCache 提供了检查与更新的接口，它有一组状态常量和一个 update() 方法：

状态常量依次是：UNCACHED(0)、IDLE(1)、CHECKING(2)、DOWNLOADING(3)、UPDATEREADY(4)、OBSOLETE(5)。对应的事件有 checking、downloading、progress、cached、updateready、obsolete、error，以及一个表示”第一次缓存完成”的 noupdate。

更新流程可以用一张图概括：

flowchart TD
  A[页面加载 引用 manifest] --> B[CHECKING 检查 manifest 是否变化]
  B -->|内容未变| C[IDLE 无事发生]
  B -->|内容已变| D[DOWNLOADING 拉取 CACHE 段资源]
  D --> E[UPDATEREADY 新缓存就绪]
  E --> F{调用 swapCache 了吗}
  F -->|是| G[刷新后使用新缓存]
  F -->|否| H[当前会话继续用旧缓存]

这里有一个关键的行为特性：新缓存下载完成后不会自动生效。已经打开的页面继续使用旧缓存，直到下一次刷新。所以生产上要做”新版本就绪后提示用户刷新”，否则用户会停留在旧版本上。这也是 AppCache 体验差的根源之一——更新从来不是即时的。

那些真实的坑

坑一：manifest 自身必须被缓存且不能被强缓存

manifest 文件本身要能被浏览器正常请求到，不能返回 404。更微妙的是：如果服务器给 manifest 加了长 max-age 的强缓存，浏览器可能几天都不去检查它，更新就彻底失效。所以 manifest 必须配 Cache-Control: no-cache 或者至少让它每次都能协商到最新。而它一旦进入缓存，本身就是缓存集的一部分——这就是”manifest 自身必须被缓存”这条规则的由来，逻辑上有点绕，实践上就是不要给它配任何会导致跳过请求的缓存头。

坑二：manifest 不能带查询串

把 manifest 写成 app.manifest?v=3 是个很自然的想法，想用它来强制更新。但这恰恰会让 AppCache 彻底不更新：浏览器对不同 URL 的 manifest 分别缓存，带查询串的地址每次都命中”新”的检查，缓存判定混乱，实测表现是更新时灵时不灵。正确做法还是改 manifest 文件内容里的版本注释，URL 保持固定。

坑三：被缓存的页面永远以缓存版本呈现

这条杀伤力最大。一旦 HTML 页面进了缓存集，改服务器上的 HTML 文件、改引用的 JS 文件名，用户看到的都还是缓存版本。很多人第一次遇到时的反应是”清缓存也没用”，因为只要 manifest 没变，浏览器就把整个缓存集当成一个不可分割的整体。想”改 HTML 就生效”在 AppCache 里是不可能的，必须走改 manifest 版本号的流程。

坑四：相对路径的基准是 manifest，不是页面

manifest 里的相对路径以 manifest 文件所在目录为基准解析，而不是以引用它的页面为基准。页面在 /app/index.html，manifest 在 /app.manifest，那么 CACHE: css/main.css 指向的是 /css/main.css，不是 /app/css/main.css。这个规则害过不少人：本地目录结构和线上不一致时，缓存集看起来是对的，实际请求全是 404，而 404 的资源会让整个更新失败。

坑五：FALLBACK 的语义与 NETWORK 的通配

NETWORK: * 表示”白名单之外的请求都允许走网络”。注意它的语义不是”全部走网络”——CACHE 段里的资源依然优先走缓存。这条通配声明解决的是”manifest 里没列的请求怎么办”：不加 *，未列出的请求在离线时一律失败；加了 *，未列出的请求在线时正常发，离线时才失败。而 FALLBACK 捕获的正是这些失败，把它们重定向到你指定的替代页面。所以一个完整的降级链路是：未列出请求 → 尝试网络 → 失败 → 命中 FALLBACK。

坑六：缓存大小限制

各浏览器对 AppCache 的容量限制都在 5MB 量级：Chrome 约 5MB，Firefox 约 5MB，Safari 约 5MB。iOS 上的 Safari 限制更敏感一些，超出后可能直接丢弃整个缓存。这意味着”把整个网站的图片都塞进 CACHE 段”这条路走不通，做离线应用必须挑资源——只缓存外壳和首屏必需的少量数据，正文内容走 FALLBACK 或者运行时缓存。

坑七：调试困难

AppCache 的缓存对开发者工具一度几乎不可见，改了 manifest 没反应时，你没有任何界面能看到”当前缓存集里到底有什么”。Chrome 提供了 chrome://appcache-internals 这个内部页面，可以列出每个 origin 的缓存条目、手动删除缓存，是当年唯一能可靠排查问题的手段。更麻烦的是缓存状态会跨会话保留，重开浏览器、重启电脑都不能保证清掉——本地的测试结论和用户机器上的表现常常不一致。

坑八：一旦用了就很难移除

这是压垮 AppCache 的最后一根稻草。页面一旦声明过 manifest，浏览器就为这个域名维护了一份缓存集。想去掉 AppCache，不是删掉 manifest 属性就行——老用户的浏览器仍然持有旧缓存，并且会继续用它。标准做法是保留一个内容为空的 manifest（或者只有 NETWORK: * 的 manifest）让所有资源都”过期”，浏览器把缓存集标记为 OBSOLETE，然后再从页面上移除属性。这个过程要跨越好几个版本，任何一步做错，用户就会永远困在旧版本里。

为什么后来大家都放弃了它

站在 2013 年看，AppCache 的问题已经很明显：更新模型不即时、缓存集与页面耦合过紧、缺乏细粒度控制、无法用代码决定”这个请求要不要走缓存”、容量固定且偏小、调试与移除都困难。开发者真正想要的是”一个可编程的缓存层”——用代码决定缓存什么、何时更新、何时清理，而不是靠一份静态清单文件。

W3C 当时已经把这个规范标记为废弃方向，业界开始讨论新的离线方案，也就是后来的 Service Worker。不过要说清楚：在 2013 年 10 月这个时间点，Service Worker 还不存在，它既没有规范定稿，也没有任何浏览器实现，任何以它为前提的方案设计都是空中楼阁。当年实际可用的仍然是 AppCache，配合 localStorage 存数据、FALLBACK 兜页面，就是离线应用的全部答案。知道它难用，但暂时别无选择，这是那一年真实的处境。

小结

AppCache 用一份 manifest 换来了整站离线能力，代价是一套极难驾驭的规则：只有 manifest 内容变化才触发更新，且新缓存不自动生效；manifest 不能被强缓存、不能带查询串、自身必须被缓存；相对路径以 manifest 为基准；被缓存的 HTML 永远以缓存版本呈现。加上 5MB 量级的容量上限、几乎不可见的调试界面、以及”一旦用了很难移除”的锁定效应，它的体验注定好不起来。如果今天还要维护一个还在用 AppCache 的老项目，务实的路径是把它圈定在最小范围内，同时把”可编程缓存层”作为迁移目标——前提是目标方案真的可用。技术选型最怕的不是方案有缺陷，而是明知缺陷还把它铺到核心路径上。
