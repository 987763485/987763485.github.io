jQuery 与原生 DOM 的性能对比

“jQuery 太慢了，我先用原生写一遍再说”——这话在 2013 年的技术讨论里反复出现，也通常以一句”其实差不多”收场。真相介于两者之间：jQuery 确实比原生 DOM 多做了包装和查找工作，但那点开销在绝大多数交互里根本测不出来；只有在热点路径上，差值才会被循环放大成肉眼可见的卡顿。这篇用可复现的计时数据把话说清：差距在哪、有多大、什么时候值得在意、以及哪些场景压根不该比。

对比的前提：让计时可信

性能对比最容易犯的错误是拿一次运行的结果下结论。2013 年浏览器里可用的高精度计时有两个：performance.now()（IE10 与 Chrome 26 起支持）和 +new Date()（毫秒级，全兼容但精度差）。本文的测试统一用 performance.now()，并垫上一个小型的兼容壳：

两条纪律：一是每个场景先跑一次预热，让 JIT 有机会优化热点代码；二是同一场景跑 1 万次取总时长，单次调用差异会被噪声淹没，量级才有参考价值。测试环境统一用 Chrome 30 与 Firefox 24，jQuery 取 1.10.2。

微观对比：选择器、创建与遍历

这一节集中回答”jQuery 到底慢多少”，把三类最高频的操作逐一量化。共同特征是：它们最终都要落到浏览器原生接口上，jQuery 的额外成本只发生在包装那一步。

选择器：$(‘#id’) 与 $(‘.cls’)

jQuery 的选择器最终都要落到浏览器原生接口上：ID 查找走 getElementById，类查找走 querySelectorAll。理论上限就是浏览器原生的速度，差值只在包装那一步。

结论清晰：ID 查找几乎无差别，$('#list') 内部就是一句 getElementById 加一次包装，1 万次总共 20 毫秒上下，单次 2 微秒，这个数字在真实页面里等于不存在。class 查找的差距会拉大一些，原因是 querySelectorAll 返回的是静态 NodeList，jQuery 还要把它转换、包装成自己的对象；getElementsByClassName 返回的是动态 HTMLCollection，省掉了这次转换，所以最快。即便如此，1 万次 .item 全量查找的总耗时仍在几十毫秒量级——真正的开销大头不是 jQuery，而是”在 1 万个节点里找类名”这件事本身。

这里就引出第一条工程结论：选择器的性能问题，十有八九不在于用没用 jQuery，而在于查找范围太大。同一个 $('.item')，写 $('#list').find('.item') 把范围从整个文档收窄到列表内，收益远大于把 $('.item') 改成原生写法。

DOM 创建：$(‘
‘) 与 createElement

创建一个 detached 元素是纯粹的内存操作，不触发任何布局，所以这里的对比最接近”jQuery 包装开销”的真面目。

量级差距在这里最明显：1 万次 createElement 约 10 毫秒，1 万次 $('<div/>') 可能到 40 毫秒以上，差出数倍。原因不复杂——jQuery 要解析这段”HTML”字符串、判断它是单标签还是复合结构、构建内部节点、再包一层 jQuery 对象，还要把结果塞进对象里附带 length、selector 等属性。字符串解析是其中最贵的一步。

但同样要说清楚：绝对差值只有几十毫秒，而这是 1 万次的总和。一个页面里创建 1 万个元素的情况屈指可数，即使出现，通常也是循环拼 HTML 字符串后一次性 innerHTML 写入，走的是完全不同的路径。真正该改的不是 API 选择，而是写法——如果你正用 jQuery 逐个创建节点，早该换成拼字符串加一次写入了。

遍历：.each() 与 for

.each() 是一个非常方便的方法，代价是每次迭代都要调用一次回调函数，函数调用本身就是开销，还要附带 jQuery 的参数检查。

因为 .each() 迭代 1 万个元素本身就不快，这里改成每个场景跑 100 轮 1 万元素的遍历。原生 for 通常比 .each() 快 2 到 4 倍，而且 jQuery 在遍历时创建一个函数作用域，内部代码量大的时候 JIT 的优化机会更少。差别确实存在，但请把数字放回场景：100 轮 1 万元素遍历的差距常常只有几毫秒到几十毫秒。一次滚动事件里如果要做这个量级的处理，你已经该考虑节流或者把计算挪出滚动回调了——那比换写法重要得多。

顺带一提老一代优化指南强调的缓存数组长度：for (var i = 0, len = arr.length; i < len; i++)。2013 年的现代引擎对 length 读取已经不敏感，但缓存 DOM 查询结果依然有效，因为 DOM 查询的开销远大于一次 length 读取。

事件绑定与样式、类操作

这一类的共同点是：差距不仅来自 API，更多来自”怎么用”。事件和样式恰恰是真实页面里最频繁的两类操作，也是最容易被写法拖垮的两类。

事件绑定：.on() 与 addEventListener

jQuery 1.7 之后，.on() 是统一的事件入口。它的实现是绕一圈的：先规范化事件类型，修复 this 指向，再挂到原生 addEventListener 上，事件触发时还要经过 jQuery 的事件分发层和修复对象。

绑定阶段差距很小，1 万次在几十毫秒量级。触发阶段差距也不显著——jQuery 的分发层只做少量属性修正，真正的成本在早期的 Event 对象修复上，而对不上 originalEvent 属性的浏览器差异处理在 2013 年已经被压缩得很薄。事件绑定的性能让人焦虑，往往不是 .on() 慢，而是绑了太多监听器或者没有用事件委托：给 1 万行列表每行绑一个 mouseover，和你把监听器挂在容器上委托一次，差距是数量级的，和用哪种 API 无关。

样式与类操作：.css() 与 style

.css() 的便利来自它对 CSS 属性名的自动处理（连字符转驼峰、浏览器前缀探测、数值补单位）。这个便利的代价是每写一次都要走一层判断。

原生写法稳赢，因为 .css() 除了设置还要解析属性名。但这里有一个更关键的、与 API 无关的事实：连续写样式不会导致性能问题，读写交替才会。写操作只是排入渲染队列，浏览器可以批量处理；而在连续写之间插入一次读取（比如读 offsetHeight），队列被强制刷新，布局立刻重算。所以真实场景里拖慢页面的从来不是 .css()，而是这样的循环：

缓存与链式：真正该优化的地方

把所有微观对比汇总起来看，jQuery 的额外开销来自三处：对象包装（每个 $() 都创建一个对象）、选择器解析（每次都要重新走一遍）、以及查询结果不缓存（同一节点反复查）。

前两处是框架成本，单次微不足道；第三处完全是我们自己的写法问题，也是最常见、最容易修的一处。

需要提醒的是缓存的失效：如果 .panel 会被动态替换（重新渲染列表、DOM 重建），缓存的对象就指向了已脱离文档的旧节点，后续操作静默失效而不报错。这一类的 bug 比性能问题更难查。判断标准很简单——这个节点在页面的生命周期里会不会被换掉？会，就把查询放进事件委托，或者在重建之后重新查询。

结论：一个公允的判断标准

把上面所有数据放到一张表里看：

操作 1 万次 jQuery 量级 1 万次原生量级 差距性质
按 ID 查找 约 20 ms 约 20 ms 基本无差别
按 class 查找 约 50 ms 约 30 ms 静态列表转换开销
创建 detached 元素 约 40 ms 约 10 ms 字符串解析开销
1 万元素遍历 数次毫秒 数毫秒（快 2-4 倍） 函数调用开销
事件绑定 约 30 ms 约 20 ms 事件分发层开销
单次样式写入 毫秒级 更快 属性名解析开销

这些数字的共同特征是：总量小、差距小、都可被预热和批量摊薄。一次点击绑定的处理如果耗时 1 毫秒，用户毫无感知；用到 100 毫秒，问题大概率不在 jQuery，而在于你在循环里做了上千次 DOM 查询和样式读写。

所以决策依据应该落在三条上：

  1. 调用频次。事件回调里只做几次操作，用 jQuery；一段代码每秒执行几十次甚至上百次（滚动、拖拽、输入补全、动画帧回调），值得核算一下是否该用原生。注意是”核算”，不是”一律原生”。
  2. 是否在循环内。循环体里放任何操作都会被乘上循环次数。循环内的 DOM 查询要先提出去缓存，循环内的样式写入要合并成一次，这跟用 jQuery 还是原生无关。
  3. 是否需要兼容 IE8。jQuery 1.10 的 1.x 分支仍在修补 IE6/7/8 的差异，这个价值无法用性能衡量。业务还要照顾这些浏览器，就没有理由为了百分之几的性能把 jQuery 丢掉；反过来，只面向现代浏览器的移动端页面，Zepto 或者原生都是合理选择。

本文的立场很明确：jQuery 的价值在兼容性与开发效率，它把跨浏览器差异封进了一层薄薄的 API，这笔交易大多数时候划算。性能对比的意义不在于证明”原生更快”，而在于让你知道——当你真的需要那几毫秒时，该往哪里去改，以及改完之后值不值得。

小结

微观基准测试里，原生 DOM 在所有项目上都优于 jQuery，ID 查找几乎打平，元素创建和遍历差距最大，但绝对值都在几十毫秒量级。真实页面的性能瓶颈极少来自 API 选择，更多来自过大的查找范围、循环内不缓存的重复查询、以及读写交替导致的强制布局。笔者几年的经验是：先修写法（缓存查询、合并写入、收窄选择器范围、用事件委托），再考虑换 API，只有热点路径上反复核算之后才值得动用原生。同时别忘了兼容性这笔账——jQuery 挡掉的 IE 差异，自己写原生代码迟早要还回去。
