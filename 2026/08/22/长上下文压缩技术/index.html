长上下文压缩技术

长上下文的账单并不是一个数字，而是三本账：占住显存的缓存字节、随序列长度增长的注意力算力、以及按 token 计价或按时钟计费的首字延迟。所谓压缩，就是决定从哪一本账里扣钱、允许信息在哪个环节失真、再用什么观测手段证明失真没有伤到任务。本文把 2025 年及以前的公开工作整理成四条路径——token 丢弃与显著性选择、KV 缓存压缩与量化、注意力稀疏化与窗口分块、层级摘要与检索替代——逐一讨论它们在保信息、保延迟、保成本这个三角上的站位。最后会回答两个经常被跳过的问题：压缩与前缀缓存复用为什么天然打架，以及什么时候开压缩其实是净损失。

上下文成本的三本账与一个三角

上下文的成本可以拆成三本彼此独立的账。第一本是字节：自回归解码要把每个历史位置的键与值留在显存里，序列越长，占得越稳。KV Cache 本身的机制与显存账怎么算，第 963 篇已经写透，本文只在压缩语境里把它当作代价的中心来引用——它是唯一随长度单调增长、又无法靠计算摊薄的部分。第二本是算力：注意力让每个新位置与全部历史发生交互，预填充与解码的耗时都随长度上翘，这段开销买到的承诺是“任意位置可访问”。第三本是钱与时间：提示 token 按量计价，也直接进首字延迟；多轮对话不修剪，就会把前两本账一起滚大。

三本账对应三个不能同时全部保住的承诺：保信息，要求每个位置的细节都能原样取回；保延迟，要求首字与逐 token 时间稳定；保成本，要求显存字节与计费 token 落在预算内。压缩工程的全部难点在于，任何一条路径都会把三角里的一角切给别人，而收益只有靠观测才能确认——没有观测的压缩，等于蒙眼改管道。

按作用层可以把公开方法归为四类。输入侧的 token 丢弃与显著性选择，在文本进入模型之前或刚进入时做减法；引擎侧的 KV 缓存压缩与量化，直接在字节层面动文章；计算侧的注意力稀疏化与窗口分块，数据全部保留、只少算交互；语义侧的层级摘要与检索替代，把长内容折叠成短内容，或干脆搬到上下文之外。《Agent 上下文工程》一篇讨论单次请求如何构造与分配预算，本文讨论的是当预算仍然不够时，可以在哪些层把已经存在的内容变小。

还要先划清无损与有损的界限。像分页式显存管理这样的结构优化，压缩的是簿记开销，与信息本身无关，可以当作无损手段放心叠加；而丢弃、量化、稀疏化、摘要都直接改变模型能看到的内容，属于有损路径，必须与观测手段配套出现。后文每一类都会给出对应的探针布置方法，只讲怎么测，不讲测出来是多少——任何跨模型通用的数字结论都不该信。

token 丢弃与显著性选择

这一类路径的出发点是一句朴素的观察：不是所有 token 都值得同等对待。输入侧，微软团队 2023 年的 LLMLingua 用一个小型模型的可预测性来估计提示里每个 token 的信息量，再做删除与短语级合并；2024 年的 LongLLMLingua 进一步把问题与文档的关联度纳入重要性估计，并针对长提示里“信息埋在中间”的退化现象做了文档级的重排——同年那项关于中段位置利用能力下降的公开研究说明，位置本身就是显著性的一部分，单纯的分数排序会低估中段的损失。解码侧，H2O 与 Scissorhands 在 2023 年提出了同一类观察：少数位置的键值会持续吸引后续注意力，像重锤一样支撑着上下文，其余位置在预算不足时可以请出去。SnapKV 把打分窗口推迟到提示收尾处，利用问题区段的注意力分布给键值打分再做池化，属于同一思想的精细化版本。

放到三角上看，输入侧丢弃是唯一能同时给三本账减压的路径：计费 token 变少、缓存字节变少、注意力算力也变少。但它的信息风险最直接——被删掉的字符不可能原样取回；而且它天然是个改写器，会把前缀缓存的序列指纹打得七零八落，第六节会展开这个冲突。至于延迟收益，取决于预填充在整条链路里的占比：如果瓶颈本来就在解码步数，删提示并不能让每个 token 出来得更快。

两个坑值得单独点名。第一，注意力得分不等于回答相关性：流失 token 现象说明首 token 一类位置的注意力质量是模板产物而非内容信号，做丢弃时必须给它们留强制保座位。第二，显著性有头间差异：同一层里有的头负责检索事实、有的头负责维持生成流畅度，用一把平均分挑位置，会把两种信号搅在一起。下面的骨架把这两点显式建模，字段与阈值均为本文自拟，不对应任何真实推理框架的接口：

KV 缓存压缩与量化

第二类路径直接对缓存字节下手，操作粒度是块而不是字。三条子路线在三角上各押不同的角。

第一条是驱逐与驻留。它与第二节显著性思想同源，但执行层在缓存管理侧：预算可以按层、按头设置，重锤位置留在显存，边缘位置按块换出。被换出的历史只能靠重算找回——这条路径把“任意位置可访问”的承诺打折，换来的是字节与算力。

第二条是量化。KIVI 在 2024 年给出的免训练路线有代表性：键与值分别做低比特的非对称量化，键沿通道分组、值沿 token 分组。量化不改变可见性，信息名义上还停在原位，取回时却已经带上噪声；公开讨论与团队实践都确认键对比特更敏感、深浅层对位宽的敏感度不均，所以按一个统一位宽切全局基本等于没看误差分布。

第三条是结构与传输。vLLM 项目的 PagedAttention 用分页消除连续预留造成的浪费，属于第一节说的无损手段；CacheGen 在 2024 年把缓存编成可流式传输的表示，跨请求复用同一段前缀时走网络搬运而不是重算，本质上是把字节账换成带宽账。

三角上看，量化是最安静的一种收益：不动输入序列、不改信息可见位置，解码时只多一道反量化；代价以精度形式偿付，复制、计数、算术这类逐字保真的任务最先受伤。下面这段 Rust 骨架示意块级量化的形状，结构、字段与位宽均为本文自拟的伪码，不对应任何真实推理引擎的配置键名或接口签名，数字都是示意值：

注意力稀疏化与窗口分块

前两类砍的是 token 或字节，这一类保留数据、只砍计算：并非每个查询位置都需要和每个键值位置交互。模型侧的窗口扩展与长上下文训练属于第 949 篇的范围，本文谈的全部是推理运行时的取舍。

2023 年的 StreamingLLM 给出了滑窗加注意力锚点的组合：解码只关注最近窗口和开头少数几个 token，窗口外的大段历史被结构性地看不见。2024 年的 MInference 把稀疏化推进到预填充阶段，离线为每个头学习动态稀疏模式，区分竖条、区块、锚点几类形态，让长提示的首字延迟吃到稀疏形状的红利，而不必删任何一个字。Quest 同年提出的思路属于解码阶段：先用每组键的少量通道粗略打分，只让得分最高的若干 KV 块进入精确注意力——它省下的是访问面而不是字节。DuoAttention 的贡献是把头分成检索头与流式头两类：前者必须看全序列，后者只看近邻就够，于是只对后者做稀疏。

服务侧还有一族与内容无关的分块：chunked prefill 把长提示切成段，与其他请求的解码批次穿插调度，抹平的是算力占用的毛刺——这是第一节无损手段在计算侧的镜像。

三角上，稀疏化是押注延迟与成本、把信息押在桌面的路线。稀疏模式学得准，输出可以逼近稠密基线；学得偏，错误以“看不见”的形式出现，是最难归因的一类。风险主要有三个：模式依赖模型与任务，微调、换模板或换语域之后，离线学出来的分类可能整体失效；注意力锚点的存在性并非普适，某些对话模板会把质量摊到别处；top-k 访问筛选一旦选偏，信息明明还在缓存里，注意力却永远够不着它——这种“缓存里有但看不见”的状态，光看显存指标完全无感。

观测方法有三件配套。第一是头级覆盖率矩阵：抽样统计每个头实际投给远距离位置的注意力质量分布，检查稀疏窗口与真实质量是否对得上；第二是与稠密基线的一致率抽样：冻结语料重放，比对可验证字段是否漂移，而不是只看总分；第三是配对扫描曲线：把稀疏度旋钮从松到紧扫一遍，同步记录每个旋钮位的任务打分分布，找拐点——拐点是“这个模型 × 这个语料”的属性，换任何一个都不能直接搬运别人的结论。

层级摘要与检索替代

前三类都在模型内部动手术，这一类在语义上动：把长内容折叠成短内容，或者搬出上下文。先划界：先摘要后原文的渐进披露设计已在第 1028 篇展开，把检索本身作为召回系统的质量与流程讨论已在第 980 篇展开，本节只谈它们作为压缩通道时的工程代价。

摘要式折叠有两种形态。免训练的形态是递归摘要链：周期性地把最旧的对话轮折叠成一段较短的摘要，与最近的原文拼接后继续。可训练的形态是让模型自己学会把长历史内化成更短的缓存——2024 年的 LLoCO 一类工作属于这条线，用模型生成的紧凑表示替换遥远历史，而不是靠外部摘要模型生成文本。前者的优点是即插即用，缺点是折叠发生在模型外，摘要器没见过被摘要内容在下游任务里的用法；后者的优点是折叠行为长在权重里，缺点是要动模型，对调用托管模型的服务完全不可及。

检索替代路线不折叠内容，改的是内容的驻地：全文放进外部存储，上下文里只留索引或短摘要，用到再取。它在成本账上的收益最彻底——上下文长度与历史长度解耦，字节账不再随会话无界增长，代价从显存转移到存储与检索调用。

三角上，这条路径的信息风险最隐蔽。量化噪声与位置删除至少是物理性的错误，摘要是语义性的改写：错误不是“少了”而是“变了”，模型会拿着错误的摘要自信地回答。此外有两个常被忽略的固定成本：摘要本身是一次额外的推理调用，短对话摊不平这笔开销；摘要与后续原文并存时，一旦两者矛盾，模型分不清哪份是当前轮的事实。

观测方法也必须是语义级的。第一是溯源审计：每条摘要记录它来自哪些原文区间，抽样回溯比对，重点检测“摘要里有而原文里没有”的内容——这比“原文里有而摘要里丢了”更危险。第二是反事实提问：构造答案只存在于已归档原文、不存在于摘要中的问题，看系统是承认信息不足、去检索、还是直接编造；系统性编造是摘要链最恶劣的失败模式，一旦在探针里出现就该停止加深摘要链。第三是链长-表现分布：统计摘要链深度与提问距离的联合分布下打分器的条件分布，用它判断链子是否已经长到模型不能可靠利用的程度。

与前缀缓存复用的冲突

前缀缓存是长上下文服务最大的成本对冲：多个请求的 token 序列只要开头一致，引擎就能复用已经算好的缓存，跳过重复预填充。它的全部前提是序列指纹不变——而压缩天生是指纹的改写者。冲突有三个来源，先用一张时序图看清最典型的那条链路：

sequenceDiagram

    participant CP as 压缩前置层
    participant PC as 前缀缓存
    participant EN as 推理引擎
    RT->>CP: 提交原始提示段
    CP->>CP: 按显著性删改 token
    CP->>PC: 用改写后的序列查前缀
    PC-->>RT: 未命中，指纹已变化
    RT->>EN: 全量预填充

第一个来源是输入侧改写：开启显著性丢弃后，同一份逻辑提示在不同查询、不同模型版本下会得到不同的 token 序列，复用无从谈起。第二个来源是每会话摘要：每个会话的摘要链都是独一无二的，共同前缀名存实亡，哪怕摘要结果完全稳定，缓存也只能按会话隔离。第三个来源是引擎侧配置漂移：量化位宽或稀疏配置切换后，缓存的格式与切换前不同，混合部署时实例之间无法互享——这也是量化配置应当进入缓存键维度的原因。

缓解思路不是放弃复用，而是把压缩对齐到复用的粒度上。第一，分层冻结：把系统提示、工具描述这类真正稳定的共同前缀保持原文不动，压缩只作用于其后的可变段。第二，版本化：缓存键纳入压缩策略的版本号，切换策略时按版本显式重建，而不是让新旧结果互相污染。第三，批次一致性：同一批次、同一集群内统一位宽与稀疏配置，让前缀共享只发生在同构实例之间。第四，搬运兜底：缓存的跨实例网络搬运能部分对冲“缓存存在但不在这台机器”的损失，但那是用带宽换时间，还引入新的失败面，需要在容量规划里单独立项观察。

观测在这里是成对指标：前缀命中率曲线与每请求平均缓存字节曲线必须放在一起读。字节曲线在降、命中率曲线降得更快，说明压缩在成本维度上的净效果可能为负；单独看任何一条，都约等于没看。

什么时候压缩反而是净损失

前面的叙述里压缩总带着账单，那就要说清什么时候干脆别压。至少六种典型情形。

其一，输入本来就不长。四类路径都有固定成本：显著性打分要先跑一遍才能出分数，摘要要额外一次推理调用，量化在每步解码都多一道反量化，稀疏模式要离线学习。序列短的时候，省下的是比例项，付出的是固定项，怎么算都摊不平。

其二，瓶颈在解码而非预填充。任务形态若是“短提示、长生成”，输入侧压缩削掉的只是首字时间，用户端在流式逐字阅读，这一头的收益几乎不可见，信息风险却全额支付。

其三，逐字保真的任务。术语表翻译、代码生成、合同条款改写、数字誊写，正确性恰恰落在低显著性的字符上。量化噪声与显著性丢弃对这类需求是正面冲突，聚合指标可能看着无恙，但方差爆炸，用户拿到的是单点致命错误。

其四，前缀复用已是生命线。少样本示例库、多租户共享模板这类场景，成本模型建立在命中率之上，输入侧压缩会打碎指纹；除非第六节的分层冻结已经落地且命中率被观测确认持平，否则开启的那一刻就是倒退的那一刻。

其五，并行分支共享同一前缀。一次采样多路再择优的解码形态里，各分支搭同一份缓存的便车；引擎侧的按分支驱逐与稀疏配置会把共享数据变成多份独占，成本按分支数翻倍。

其六，观测体系还没建。最容易忽略的一条：没有留存审计、没有误差账本、没有质量闸门时，压缩的一切得失都无法归因，此时开启压缩不是稳健，是赌博。

判断的操作办法是记两本账。收益账按长度公式先粗估缓存字节、计费 token 与预填充算力三项；固定成本账登记打分开销、摘要调用与簿记开销。两本账必须等观测链路建立之后再对比，因为收益账里还要扣掉前缀复用被破坏后的实测损失。账算平之前，把“不压缩”这个基线本身当一等答案记录在案。

观测证据链：四类探针怎么布置

先声明分工：“冻结重放加统一打分器”如何证明计算投入有效，是第 1037 篇的论证；本节把前面散落的观测点收拢成压缩场景的布置手册。四类证据分别对应第一节的三本账与一个三角。留存探针回答“信息还在不在”：逐字可校验的探针句按位置与路径两个维度统计存活。账面探针回答“钱去哪了”：每请求缓存字节、前缀命中率、重算率三条曲线。时钟探针回答“省的是谁的时间”：首字时间与逐 token 时间的百分位分布，只看接入前后的对比形态，不记绝对结论。一致探针回答“失真长什么形状”：冻结语料同问重放，比对可验证字段的漂移清单。

布置时有三条纪律。第一条，影子先行：让压缩器对真实流量空跑，结果不投产，只与基线输出比对。它贵，但是唯一不污染生产的对照方式，适合任何有损路径上线前的一次性验收。第二条，逐路径启用：同时开两条以上压缩，失败就无法归因；启用顺序按第十节的路线走。第三条，删改全量登记：压缩器丢掉的 token 区间、每条探针的判定结果、每个缓存块的状态迁移，都落成可回溯的记录——事后排查只能靠这份记录，只报汇总计数的压缩日志等于没有日志。质量闸门的具体判据属于团队约定示例，各团队在自己语料上标定，不存在可以照搬的绝对阈值；探针自身的采样开销，也要计入容量规划而不是免费假设。

两点补充读法。第一，表里的四行彼此正交，但方法同源的现象很常见：显著性打分既服务输入侧丢弃，也服务引擎侧驱逐，换的只是执行层与预算粒度——评估时按执行层归因，不要按论文标题归因。第二，风险列与观测列要成对消化：每一行的风险恰好是首要观测手段设计出来要抓的失败形态，装探针时装不出这个形态的，说明探针与路径没配好。

落地顺序与回滚设计

四条路径的接入次序有讲究，依据是三个工程属性：改造成本、爆炸半径、可逆性。输入侧丢弃改造成本最低——挂在请求组装处即可，但它改变模型看到的每一个字，爆炸半径覆盖整条回答；引擎侧的量化与驱逐不动输入序列，半径限于缓存表示的精度与可达性，可是回滚要付重建代价；计算侧稀疏需要离线学习环节，上线慢，好在失败形态相对孤立；语义侧摘要链半径最大，写错的摘要会长期驻留并持续污染后续轮次，回滚也最不干净。

由此给出一个默认顺序，各团队按自身瓶颈调整。第一步永远不是压缩，是记账：把三本账与第八节四类探针先装起来，取得足够长的不压缩基线。第二步，若瓶颈在计费与首字，先接输入侧丢弃，配合分层冻结保前缀。第三步，若瓶颈在显存驻留，接量化，按层配误差探针，驱逐最后接、且只在重算率被持续监控的前提下接。第四步，若瓶颈在预填充排队，接计算侧稀疏。第五步，只有当会话长度事实上无法用窗口约束时，才接摘要链，并强制原文归档。

回滚设计有三条硬要求。其一，每个路径独立的开关与版本号，开关状态进入日志与缓存键，禁止隐式生效；其二，语义侧必须永久归档原文——摘要不可逆，没有原文档案的摘要链等于把历史交给单次改写；其三，回滚演练纳入例行流程，影子运行期间定期回放“全关”配置，确认基线路径随时可达。压缩体系最危险的状态不是压得狠，而是压完之后没人记得怎么退回不压。

小结

长上下文的成本是三本账——缓存字节、注意力算力、计费与首字时间——它们共享同一个长度变量，却没有共享同一个修法。四类压缩路径各自切入不同的账：输入侧的显著性丢弃三账同减但信息不可逆；引擎侧的量化与驱逐安静地省字节、以精度偿付；计算侧的稀疏化把“看见”变成“抽样看见”，收益大且模式易漂移；语义侧的摘要与检索替代把增长掐断，代价是错误从物理性变成语义性。三角上没有免费的角：保信息、保延迟、保成本，任何路径都只能明牌押注其中两个。

比方法更要紧的是两件事。一是压缩与前缀缓存复用天然冲突，指纹即成本，任何改写输入或切换配置的动作都要按第六节的粒度对齐规则重新核算，净效果必须由命中率与字节两条曲线共同裁决。二是任何有损路径的上线依据只能是观测证据：留存审计、误差分布、重算率、覆盖率矩阵、溯源与反事实探针——先有仪表，再有旋钮；先有影子，再有灰度；先有原文归档和回滚演练，再谈压缩率。本文刻意没有给出任何节省比例与保留率的数字：那些结论属于“这个模型、这份语料、这版配置”，搬回来用，往往正是净损失开始的地方。
