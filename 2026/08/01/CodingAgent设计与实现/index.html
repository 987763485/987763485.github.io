Coding Agent 设计与实现

本文属于《Agent 智能体开发》第 54/55 篇
上一篇系列目录下一篇

自己写一个 Coding Agent，难的不是那个 while 循环，而是循环周围的六个决策：仓库怎么进上下文、改动用什么表示、执行反馈从哪里来、失败之后重试几次、写操作在哪里拦住、预算怎么收口。这篇只走这条工程线，不拆某个产品的内部实现，也不谈评测取数口径，目标是给出一份可以直接改的骨架和每一格的取舍理由。文中阈值均为团队约定示例，出现的数字一律是示意值，不能当实测结论。

本文的口径与边界

本文假设你手上已经有两样东西：一个能调用工具的模型，一台能跑构建与测试、且愿意被套上沙箱的机器。要讨论的是把这两样缝成可靠系统的那层胶水，也就是通常所说的 harness。

这一层的麻烦来自三条硬约束。第一条是模型会自信地编造：它会调用你没注册的工具、引用不存在的符号、把你贴给它的一半代码当成全部真相。第二条是仓库读不完：再怎么大的上下文窗口，面对一个中等规模代码库的全文也只能塞进零头，所以必须有召回与压缩。第三条是执行有副作用：文件会被真的改掉，命令会真的跑，token 会真的花掉，这三件事都比“回答错了”更难撤销。

业界参照只提一句，避免和同批文章重复：Devin 在 2024-03-12 以 early access 形态出现，GitHub Copilot 的 agent mode 在 2025-02-06 进入 Insiders 公开预览、2025-04-04 转为全量并带上 MCP 支持，Claude Code 是 2025 年公开的命令行形态；SWE-bench 这类代码基准早在 2023 年就已存在，但本文不引用任何通过率或名次。产品内部长什么样，见《Claude Code 源码架构解析》；极简框架的取舍，见《PiAgent框架解析》；怎么建任务集、怎么取数，见《AI编码助手深度评测》。这三件事本文一概不复述，只谈“自己实现要做的决策”。

这段里有三个槽位经常被省掉，而它们恰恰决定稳定性。第一个是拒绝回写：权限拦下一个动作时，必须把“为什么被拦、有什么替代”当成一条观测塞回上下文，否则模型会在同一个门槛上撞三五次，白烧预算。第二个是取消点：预算检查和取消标志只放在循环顶部，动作执行中途不要指望能停，长命令要靠外部超时把进程收掉。第三个是回滚锚点：每完成一次校验通过的状态就打一个检查点，失败时回到锚点而不是带着半改的状态继续猜。

在 TypeScript 侧做同样的事，习惯做法是把动作表示成可判别的联合类型，用 kind 字段分支，而不是让模型自由返回一个对象再到处取键。模型输出的键名不稳定，联合类型能把“缺字段”从运行期崩溃变成一次可重试的解析失败。控制流建议保持单线程顺序，并行只放在只读检索那一层；写操作并行会引入合并冲突，收益远小于代价。

仓库上下文构建：索引、依赖图与相关文件召回

上下文构建的决策只有一句话：在有限的窗口里，放什么、不放什么、按什么顺序放。常见做法是分层装配，优先级从高到低大致是任务原文与约束、入口相关文件、依赖图邻居、跨模块检索命中的片段、仓库级摘要与约定。把优先级写成显式的装配清单，比事后调 prompt 可靠得多。

召回手段各有明显的失效场景，选型时按这张表对照：

召回手段 建索引成本 相关性问题 典型失效场景
全文或关键词匹配 很低，可直接扫 命名不一致就漏 大型仓库里噪声爆炸
结构召回：导入与调用图邻居 中，需要解析器 只覆盖显式依赖 反射、动态加载、配置驱动
嵌入向量相似检索 中高，需推理与存储 相似不等于需要 短标识符、模板代码难区分
构建系统给出的目标依赖 中，复用现有构建 粒度偏粗 未纳入构建的脚本与资源

这四路是并联的：只走一路会漏，四路全走会重复，所以召回之后必须去重与裁剪，同一文件的不同区间合并，跨路命中的同一片段只留一份，并按“是否会被本次改动直接触碰”排序。

依赖图这一路的性价比最高。边可以从语言级导入语句抽，也可以从构建配置的目标依赖抽；前者精细但跨语言会断，后者粗糙却天然贴合“改这里要重新编译哪些地方”。图不必常驻上下文，它的正确用法是回答“改这个函数会被谁看到”，把调用点列表塞进去。增量维护比全量重建友好：内容哈希变了才重解析，解析失败就退化成路径近邻，别让一个语法错误打死整条召回链。

修改的表示与应用：补丁还是整文件

改动怎么表示，是 Coding Agent 里最容易被低估的一格。三条主流路线的取舍大致如下：

表示方式 优点 代价 适合的场景
行级统一补丁，带上下文行 便宜、可读、易审计、易回滚 上下文漂移就应用失败 小范围确定性修改
整文件重写 不会因为偏移失败，模型擅长 贵，且极易顺手改掉无关代码 新生成的小文件、模板类文件
区域替换，靠唯一锚点定位 比行号稳，比整文件省 锚点不唯一就歧义 中段插入、配置块修改

真正决定可用性的是应用环节的四道安全检查。第一道是应用前重读：模型看到的是几秒前的快照，文件可能已经被格式化钩子或并发动作改过，落地前要重新取一次内容和内容哈希。第二道是乐观并发：把快照版本号或哈希带进应用请求，不匹配就放弃本次改动并重新规划，而不是强行按行号戳进去。第三道是幂等：同一个补丁因为重试被应用两次，是“重复插入代码块”这个经典故障的根源，应用层要有已应用的标记或做双向检测。第四道是应用后再校验：读回文件确认结果与预期一致，这一步很便宜，却能挡住大部分静默失败。

失败要分级。锚点找不到，降级为区域替换或整文件重写；哈希不匹配，重新读并重新规划；权限不足，走拒绝回写。千万别做成“所有失败都重试三次”，那只会在同一个死结上烧预算。至于撤销，最省心的做法是在会话开始时建立检查点，回滚只回本次会话产生的改动，绝不碰用户已有的未提交工作。

执行反馈回路：测试、构建与 lint

反馈回路是把 Coding Agent 从“生成器”变成“收敛系统”的那一步。没有反馈时，模型的置信度与正确率无关；有了反馈，它至少能在错得离谱时自己发现。四类反馈的性价比差别很大，选型时按“时长、信噪比、能证明什么”三列对照：类型检查与编译最快，能证明接口接得上；单元测试中等，能证明行为符合预期；lint 便宜但噪声多，适合当收尾体检而不是决策依据；端到端与集成测试最慢也最贵，只应该在改动半径真的触及边界时启动。

关键决策有三个。第一，跑什么命令不由模型自由拼，而是从仓库自己声明的地方取：脚本清单、CI 配置、构建目标；让模型现编命令，等于把权限门槛和破坏半径同时放大。第二，回给模型的输出必须做结构化压缩：退出码、失败用例名、第一条错误的文件与行号，再加有限长度的原文片段；整段构建日志塞回上下文只会烧钱，还会稀释真正有用的那一行。第三，反馈粒度要和改动半径匹配，改一行注释去跑全量端到端，等于没有反馈，只是延迟很高的噪声。

一次回路在时序上大致是这样：

sequenceDiagram
    participant M as 模型
    participant P as 权限层
    participant F as 文件层
    participant C as 命令层
    M->>P: 提交动作与理由
    P-->>M: 放行或拒绝并给出替代
    M->>F: 提交补丁与快照哈希
    F-->>M: 应用结果与新哈希
    M->>C: 运行仓库声明的检查命令
    C-->>M: 退出码与截断日志
    M->>F: 失败则回滚到检查点

反馈之后是重试。一个可审计的重试阶梯大致是这样：

stateDiagram-v2
    [*] --> 规划
    规划 --> 应用
    应用 --> 校验
    校验 --> 提交: 通过
    校验 --> 修复: 首次失败
    修复 --> 应用: 同一假设内
    校验 --> 重召回: 二次失败
    重召回 --> 规划
    校验 --> 回滚: 三次失败
    回滚 --> 结束: 交人工
    提交 --> [*]
    结束 --> [*]

阶梯的设计意图是把失败归因区分开：第一次失败默认当成实现细节写错，在同一个假设内修；第二次失败说明假设本身可疑，回到召回层，检查是不是读错了文件、漏了调用点；第三次失败就停止猜测，回滚到锚点，把已知的 diff、失败输出和尝试过的路径整理成一次交代清楚的人工交接。比“重试三次”更重要的是每一次都要有新的信息进来，否则只是复读。

与重试配套的是最小化改动纪律，要写成显式约束而不是指望模型自觉：不顺手重构、不新增无关依赖、不做全局格式化。每一行无关改动都会放大反馈的排查面，也会让权限确认时无法回答“这行为什么要改”。校验通过后再加一轮收缩，逐段确认哪些行是达成目标所必需的，能删则删；格式化工具造成的整文件重排应在应用阶段识别出来单独对待，别混进语义改动。

权限与写操作确认：默认拒绝加人工门槛

任何会改状态的动作，都要走“默认拒绝、命中白名单才放行、越界触发人工确认”这条链。把工具按副作用与可撤销性分档，门槛跟着档位走，比按“看起来危不危险”逐条判断更可维护：

档位 例子 默认策略 确认方式
只读检索 列目录、读文件、查引用 放行 事后审计即可
仓库内写 改文件、加测试、跑构建 白名单目录放行 展示 diff 后确认
外部副作用 装依赖、访问网络、开 PR 默认拒绝 单次逐条确认，不长期授权
破坏性操作 删分支、强推、跑数据迁移 拒绝 本文范围内一律不做，交人工

两个实现细节决定这套东西是否真的有效。其一是确认信息的密度：一次合格的人工确认要能回答“改哪个文件、影响哪些调用点、跑什么命令、失败怎么回滚”，只弹一个“是否允许”是无效的，用户只能盲签。其二是拒绝也要成为反馈：门槛拦下动作时，把替代路径一起写回上下文，例如“这条命令被拦，可改用仓库脚本清单里的哪一个”。

凭据的处理单独说，因为它是最容易在示例代码里出事的地方。原则是 Agent 侧永远拿不到明文：凭据由运行环境注入，模型看到的只是占位符或受控代理；不写进任何明文示例，不进日志，不进缓存键。缓存键的常见错误是把带令牌的东西直接拼进去，正确做法是对一个不含机密的部分做摘要，或者用运行期的会话标识；落盘的审计轨迹里，命令参数要过一遍脱敏，长输出的原文别整体留存。会话结束后，临时产物按保留策略清理，不要指望“反正没人看”。

沙箱与超时属于同一格。写操作限制在仓库根目录之内，路径规范化后再判定，防住越界的相对路径；命令执行有独立的墙钟超时和输出字节上限，两者都要能被外部观察者看到，而不是静默失败。

成本与时长预算

预算要同时管两件事：token 和墙钟。只看 token 会漏掉“跑了一次二十分钟的端到端”，只看时长会漏掉“上下文反复全量重发”。可行的做法是三层预算：会话总额、单轮上限、单条命令上限，每层都能独立触发停止，停止时输出的不是失败而是当前状态。下表数字是团队约定示例，示意值不代表合理值：

层级 团队约定示例 触发后的动作
会话总额 一次任务不超过若干轮工具调用 收口成人工交接，附 diff 与失败摘要
单轮上限 单轮注入上下文有字节上限 触发压缩与截断，不整段塞日志
单命令上限 构建或测试有墙钟与输出双上限 外部超时收进程，记为一次失败

上下文压缩是成本的主体，值得单独设计。增量做法是保留三样：目标原文、已落地的 diff、最近若干条观测；早期轮次折叠成摘要，摘要里留文件与符号名而不是散文。要警惕摘要把约束摘丢，任务里的硬性限制一旦被压缩掉，模型就会去做被明令禁止的事，所以约束原文常驻、不进压缩队列。

可观测性决定这些阈值能不能调对。至少记下：完成任务用的轮数、召回命中率、补丁应用失败率、回滚次数、被权限拦下的动作数、单位任务成本。这几个量能直接指出瓶颈在召回、在表示、还是在反馈，而凭手感通常会误判成“模型不行”。取消与恢复也要有骨架：中断时把当前 diff、检查点标识和未完成的假设写进会话状态，恢复时从状态重放，而不是从头再召回一遍。

小结

自己实现一个 Coding Agent，工作量集中在六个决策上：分层装配上下文、给改动选一个能审计的表示、用仓库自己声明的命令造反馈、按失败次数换假设而不是换措辞、把写操作放进默认拒绝加人工门槛的链里、用三层预算和可观测性给一切收口。骨架本身十几行就够，稳定性全来自拒绝回写、回滚锚点和取消点这些不起眼的槽位。

落地顺序建议反过来：先写最小循环，把权限与预算钉死，宁可它什么也做不成；再补反馈回路，让它能自己发现错误；最后才优化召回质量，因为前三步决定它会不会把事情弄糟，第四步只决定它快不快。
