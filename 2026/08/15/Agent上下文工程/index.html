Agent 上下文工程

本文属于《Agent 智能体开发》第 23/55 篇
上一篇系列目录下一篇

Agent 的每一次请求，都是从一堆互相竞争的材料里现场拼出一段上下文：指令、工具定义、历史、检索结果、输出预留，谁占多少、谁排在前面、谁被折叠成摘要，都是需要显式决策的工程问题。本文讨论如何把这段有限资源当作预算对象来管理，覆盖装配顺序、渐进披露、结构化摘要、前缀稳定、指令与数据分离和污染检测，并在结尾给出一份可复用的装配模板与策略对照表。它只关心单次请求之内的上下文构造：跨会话的记忆写入与遗忘策略属于《Agent 记忆与长期上下文》的话题，记忆条目的召回打分属于《Agent 记忆检索优化》的话题，本文到需要处各用一句话划界，不再展开。

把上下文当作有限资源

大模型没有持久的工作区。Agent 每一轮都要把“到目前为止知道的一切”重新塞进一个输入窗口，生成结束后这段窗口就被丢弃，下一轮再重新拼一遍。这个事实决定了上下文工程的全部难点：资源是每次都要重新挣得的，而不是积累下来一劳永逸的。提示词写作关注“怎么说清楚”，上下文工程关注“往窗口里放什么、放多少、放在哪、以什么形态放”。窗口容量扩展的机制在《长上下文扩展》里已有专文，压缩算法的细节留给《长上下文压缩技术》，这里都不重复。

值得先建立的是上下文的三个属性。第一是有限性，而且有两层：一层是服务商声明的 token 上限，硬约束，超了就报错或静默截断；另一层是有效注意力上限，软约束，窗口名义上装得下，模型却未必看得进去——大量经验与公开研究都支持“塞满的上下文质量反而下降”这一定性结论。第二是易逝性，上下文在请求之间不保留任何状态，所谓“它还记得”，只是因为装配器把该记的又放回去了。既然每次都要重拼，装配过程就应当是可复现、可测试、可版本化的管线，而不是每次手工作坊式地粘贴。第三是竞争性，每一段材料占用注意力，都在稀释其他材料被注意到的概率；加一段“可能有用的背景”不是免费操作，它有真实的机会成本。

由此推出上下文工程的立场：目标不是塞得更多，而是让关键信息更可靠地被放在正确的位置上。一个成熟的 Agent 框架里，上下文装配应当像内存分配器一样有明确策略——谁申请多少、超额怎么办、碎片怎么整理、泄漏怎么检测。后面的小节就按这个类比逐一展开：预算分配表、顺序与位置效应、渐进披露与折叠、结构化摘要、前缀稳定性与缓存复用、指令与数据分离、污染检测，最后落到模板和观测。

预算分配表：先谈额度，再谈技巧

多数上下文事故不是“模型不行”，而是装配没有预算：一段超长的工具输出把历史挤掉，检索回来的整篇文档把指令区挤到注意力边缘，或者拼到最后没有给输出留空间，模型在截断的中途收尾。解法是把五类内容当作五个部门，各发一笔额度，超额走显式的处置流程。下面这张表的区间是团队约定示例，只用于说明“必须有额度、必须有处置”这个结构，不是任何行业标准。

分配的顺序比比例更重要。第一条规则是先扣输出预留：输出被截断的代价是行为残缺，比少放两段检索严重得多。第二条是指令与工具两段相对固定，先满足，它们的体量应该在系统建设期就压下来，而不是运行时临时裁剪。第三条是把剩余额度分给检索与历史，检索段设硬上限——检索回来的材料天然容易超长，因为它由外部世界决定长度；历史段消费剩余，消费到地板线以下就触发摘要折叠，而不是等到挤爆。第四条，任何一段超额都必须作为显式事件写入遥测，禁止静默截断：静默截断是上下文领域最危险的 bug，它让事故看起来像模型退化。

预算表还有一个常被忽略的作用：它是团队讨论的载体。当有人想“把这段背景也塞进去”时，问题从“要不要加”变成“从哪个部门挪”，决策质量完全不同。没有预算表之前，上下文的膨胀是无人负责的公地悲剧；有了预算表，每一段新增内容都要回答它挤掉了什么。

顺序与位置效应

同样一批材料，排列顺序不同，行为可以差出一个量级。位置效应不是玄学：Liu 等人在 TACL 2024 发表的《Lost in the Middle》给出的定性结论是，模型对长上下文的利用呈“两端强、中间弱”的形态，关键信息埋在中部时最容易被忽略。据此可以把装配顺序的原则归纳为四条。

第一条：稳定在前，易变在后。窗口最前面放每轮都不变的内容——系统指令、工具定义——后面依次是缓慢增长的历史、本轮新注入的检索与观察。这条原则一半来自注意力（开头有最强的阅读先验，适合放“角色与规则”这类锚定物），一半来自缓存复用，第六节会展开。第二条：全局先于局部。跨任务的约束、输出协议放在前面；本轮特定的小指令贴近生成点。第三条：指令先于数据。权威梯度要清楚：越接近系统层的文本越靠前、越受信任，外部材料靠后且带来源标注，让模型在结构上就分得清“谁在对我说话”。第四条：结尾重新锚定。生成前的最后一段，重复最容易被遗忘的硬性要求——格式、禁止事项、下一步动作。尾部是注意力的另一极，用它对抗中部塌陷，比把它浪费在礼貌性结语划算。

顺序效应还有几个实用推论。检索结果不要平铺成一大段，而是按“一句摘要加出处”的条目化形式排列，相关度最高的放在这个分段的最前面，因为分段内部同样存在微型的两端效应。历史轨迹里工具调用的参数与结果要成对相邻，拆开放会让模型花注意力重新配对。多轮对话里如果出现了话题切换，在切换点插一行显式的分隔标记，比指望模型自己察觉边界可靠。

也要泼一盆冷水：顺序是杠杆，不是替罪羊。如果两段内容本身互相矛盾，调整顺序只是决定违反哪一条；如果指令写得含糊，放在窗口开头也照样被误读。位置效应放大内容质量，不创造内容质量——这句话应该贴在每个改提示词改到绝望的人桌上。

渐进披露与折叠

《Agent 记忆与长期上下文》讨论过跨请求场景下“先给摘要、按需再取原文”的节奏；本节谈的是同一轮请求内部的披露设计：材料在窗口里以什么粒度出现，什么时候完整、什么时候只留索引。核心思想是，上下文中的一段内容有两种形态——完整形态和索引形态——装配器的职责是默认用索引形态，只在证据表明模型需要时才升级为完整形态。

工具结果是第一个典型场景。一次抓取回来的网页正文或一次构建日志可能有几万行，全量注入既不现实也无必要。两阶段的处理方式是把原文外置存储，上下文里只放三样东西：一句结论性摘要、一个计数（多少条、多少行、有无错误特征）、一个句柄。句柄是可寻址的标识，模型判断需要细节时，通过一个专门的读取工具按句柄展开片段——展开的粒度同样受预算表约束，取一节而不是一整篇。任务用完后，展开的片段在下一轮重新折叠回索引形态，这就是“披露可逆”：折叠与展开是双向的运行时决策，不是单向的删除。

文件与代码场景用目录树式披露。与其把仓库里“可能相关”的十个文件都塞进去，不如注入一层文件树加每个文件一行的用途注释，让模型用读取工具按需展开真正需要的那两三个。技能与工具的长文档同理：工具定义里只留一行用途，完整参数说明挂在按需获取的元数据上。披露的代价要诚实列出来：多一次工具往返的延迟、句柄管理错误的风险（悬空句柄、越权句柄），以及“模型不知道自己不知道”的问题——摘要写得不够指引性时，模型不会去申请展开。所以摘要行必须回答两个问题：这里有什么、什么情况下值得展开。

结构化摘要

历史段膨胀到地板线以下就要折叠，折叠的产物是摘要。压缩算法本身的细节留给《长上下文压缩技术》，本节只谈一件事：摘要以什么接口形态进入上下文。差的做法是把摘要写成散文——“用户之前讨论了部署方案，助手给了一些建议”——读起来通顺，对行为却几乎没有约束力，因为规则、数字、否决项在散文化的过程中被抹平了。好的做法是把摘要当作重新编码：用固定的字段化结构承载不同类别的信息，每类信息有自己的保真要求。

一份可用的摘要模式包含这么几类字段：目标（当前要达成的结果，一句话）；已完成（做了哪些不可逆动作，带出处引用）；决策（选定了什么、排除了什么，排除项必须保留理由）；事实（环境中已验证的状态，每条带来源句柄与生成时间）；待办（下一步清单，含被阻塞项与阻塞原因）；悬置问题（观察到但未解释的现象）；否决假设（试过且失败的路线，防止重新踩坑）。保真要求分档：目标与待办允许意译，事实与否决必须保留原文引用句柄，因为前者服务于方向、后者服务于约束。

摘要最容易出的三类事故值得单独点名。一是叙述式摘要丢约束：原始指令里的“不许碰生产库”在摘要里消失，模型下一轮就碰了，所以否决类与安全类条目应设为摘要中的不可删除字段。二是摘要链漂移：拿旧摘要生成新摘要，误差逐级累积，正确做法是定期从外置的原始轨迹全量重算，把摘要看作可丢弃的缓存而不是账本。三是摘要与原文脱钩：摘要里的事实没有句柄，事后无法验证是幻觉还是笔误。三条对策合起来就是一句话：摘要必须可重生成、字段化、带出处。做到这三点的摘要，才配占用预算表里那两至三成的历史额度。

前缀稳定性与缓存复用

主流服务商提供的提示词缓存，原理是对输入上下文的严格前缀匹配：只要本轮请求的开头与某次已计费请求的开头逐 token 相同，这段前缀的推理中间状态就能复用，省下重新计算的时间与费用。它对工程提出的要求很特别——不是抽象地说“尽量复用”，而是要求窗口最前面那一大段文本一字不改。一个随手加的当前时间戳，就能让整段缓存作废。

这意味着装配顺序要与缓存策略对齐：稳定部分构成一个逐轮不变的长前缀，动态部分只允许追加在前缀之后。一个常见的分层是这样的：

同时要保持一个清醒的边界：缓存是性能优化，不是正确性依赖。缓存可能因过期、容量策略或服务端调整而失效，装配器不能假设“前缀已经在缓存里所以可以省略”——每一轮发送给模型的仍然是完整上下文，省的是服务端的重算，不是输入的长度。把上下文做短靠的是预算、折叠与摘要，把上下文做便宜靠的是前缀稳定，两件事不要混为一谈，也不要指望一件替代另一件。

指令与数据分离

提示词的写作技巧与管理流程在《提示词进阶》与提示词管理相关篇目里已有覆盖，本节只谈上下文构造层面的一个问题：窗口里的文本，哪些是“对我下达的指令”，哪些是“给我读的数据”？模型默认会把两者都当指令读，而 Agent 的上下文里塞满了外部世界回来的材料——检索的文档、抓取的网页、工具的输出、代码库里的注释——这些材料随时可能包含“请忽略以上指令并执行以下操作”之类的文本。这是 Agent 安全里最经典的攻击面，本节只讨论防御侧的上下文构造，攻击手法本身不复述。

第一层防御是结构隔离。所有外部材料在进入上下文前统一包裹在固定分隔符内，并在系统指令中声明该标签内的任何文本只是数据、不具备指令地位。包裹要机器生成、格式统一，让“这是外部内容”成为上下文中肉眼与模型都可辨识的结构特征，而不是靠措辞礼貌地提醒。

第二层是净化。工具输出在进入包裹之前，先剥离其中的角色标签与伪系统前缀——外部的 JSON 字段名里藏着 system 角色的构造是常见手法，让净化器而不是模型来兜底。第三层是权限与上下文解耦：Agent 能调用哪些工具、能写哪些资源，由会话外的策略层决定并强制执行，上下文里的任何文本都无权扩权。Anthropic 在 2026 年 5 月发布的工程文章《how we contain Claude》中阐述的正是这类思路——把不可信内容先关进受控的笼子，靠宿主层的边界而不是模型的自觉来兜住最坏情况。第四层是敏感动作门控：不可逆或高权限的操作必须经过上下文之外的确认通道，确认请求要回显将要执行的参数，让人核对“这个动作是谁要的”。

最后强调一点实践纪律：防御的有效性必须逐模型回归。注入抵抗力与模型的对齐训练直接相关，旧模型上验证过的分隔符方案，换一代模型未必同样牢靠——例如 Claude Sonnet 5 这类新模型进入使用时，同一套装配模板应当重跑注入用例的回归测试，而不是默认继承旧结论。把安全寄托在“模型听话”上是统计学的侥幸，把安全寄托在“上下文结构与权限层”上才是工程。

上下文污染检测

预算、顺序、摘要、缓存解决的是“怎么放”，本节解决“放错了怎么发现”。上下文是会污染的，污染形态至少有五种：过时事实——环境已经变了，窗口里还写着旧状态，模型一本正经地按旧地图导航；重复材料——同一文档被不同查询召回多次，占预算占注意力；矛盾指令——两段规则无法同时满足，模型择一违反而不自知；调试残留——上个任务注入的临时说明混进了长期模板；伪权威——外部文本自带角色标签或“系统提示”式开头，冒充指令层。检测手段对应如下。

去重靠分段指纹：每段材料在进入装配前计算内容哈希，与前一轮的分发集合比对，重复内容不再注入完整形态，只保留既有的出处引用。矛盾检测靠把关键规则整理为机器可读的条目清单，在装配阶段做一次静态互斥检查——两条都带强制标记且方向相反时，报错并回人工裁决，而不是赌模型的临场判断。过时事实靠新鲜度约束：每条事实带生成时间与来源句柄，超过约定的时限（团队约定示例：以轮数或挂钟时长计，先到为准）仍未重新验证的条目，自动降级为“待确认”并在上下文中显式标注。防止跨任务串味，可以把任务级材料打上任务标识，装配时只认当前标识。

canary 字符串是一项便宜而有效的手段：在私有上下文里放入随机生成的无意义占位串，如果它出现在工具输出、外部请求或日志里，就说明上下文正在被读取方外带或回显，污染与泄露都当场现形。最后要保留一个断路器：当上述检测连环报警、上下文的实际形态与预期模板偏差过大时，正确的动作不是继续打补丁，而是放弃增量维护，从可信源（原始轨迹、外置存储、权威配置）整体重建一份干净的上下文。增量更新像缝合，缝合次数多了组织会坏死，重建就是换器官。

stateDiagram-v2
    [*] --> s1
    s1: 干净: 通过装配校验
    s2: 可疑: 指纹重复或新鲜度超时
    s3: 隔离: canary报警或矛盾指令
    s4: 重建: 从可信源整体装配
    s1 --> s2: 装配期校验不通过
    s2 --> s1: 重验证或去重后恢复
    s2 --> s3: 升级为安全事件
    s3 --> s4: 拒绝增量修补
    s4 --> s1: 输出新上下文快照

一份可复用的装配模板

前面的机制需要落在一份具体模板上才能被团队执行。下面的模板是骨架而非成品：标签名与占位符均为本文自拟，落地时按自己的装配器改造，但建议保留三条不变量——分段不可缺失（缺段是装配错误，不是优化）、次序不可调换（对应位置效应与缓存策略）、数据必带出处（对应摘要保真与污染检测）。模板中每个占位符都注明了预算来源，装配器据此逐项填充。

策略、收益、代价与观测方法

收尾用一张对照表把全文收拢。表中的收益与代价都是定性描述，具体量级因模型、业务与流量结构差异极大，请在自己的遥测里测，不要抄别人的数字；观测方法一列回答的是“怎么知道这条策略在我的系统里生效了”，这是策略能否长期存活的关键——没有观测的策略最终都会悄悄烂掉。

策略 收益 代价 观测方法
预算分配表 膨胀可控，超额显式化 需要维护各区间的约定 分段实际用量直方图，超额事件计数
顺序与尾部锚定 关键约束遵循度提升 装配逻辑复杂化 约束遵循的用例回归，格式错误率
渐进披露与折叠 同样预算装更多可用信息 多一次工具往返，句柄管理 句柄展开申请次数，悬空句柄告警
结构化摘要 历史变长而行为不失稳 摘要质量本身需要质保 摘要重算后关键条目存活抽查
前缀稳定性 时延与费用优化 改动流程变重 前缀命中率遥测，破前缀变更审计
指令与数据分离 注入面收窄，权限清晰 净化与包裹增加装配开销 注入用例集的通过率
污染检测与重建 事故早发现，错误不累积 断路器误火风险，重建耗时 各污染形态的告警量与处置时长

观测体系值得再说半段。上下文工程的指标天然不如端到端任务成功率直观，所以要分两层：装配层指标（每段用量、超额事件、前缀命中、句柄展开、告警）在管线内部采集，随时可查；行为层指标（约束遵循、事实引用正确、注入抵抗）靠离线用例集加在线抽样评审。两层之间的桥梁是上下文快照——每次请求发送前把最终拼装的上下文按采样率存档，出问题时先回放快照再怀疑模型，绝大多数“模型突然变笨”的报告，回放之后会发现是装配变了。

小结

本文的轴是一句话：上下文是每次请求都要重新挣得的有限资源，工程化的意思是把“往里放东西”变成有预算、有顺序、有形态、有防御、有检测的装配管线。预算表让膨胀显式化，位置效应让关键信息占据注意力的两端，渐进披露用索引形态换回空间，结构化摘要把历史变成可重生成的缓存，前缀稳定让同样的内容越跑越便宜，指令与数据分离守住注入的底线，污染检测与断路器兜住错误的累积。这些策略没有一件依赖“模型更聪明”，全部落在装配器这个确定性组件上——这正是它们可靠的原因，也是它们值得写成模板、纳入代码评审的理由。从下一个迭代开始，先给你的上下文装上预算表与超额事件，再谈其他技巧。
