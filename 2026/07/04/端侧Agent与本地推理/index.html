端侧 Agent 与本地推理

本文属于《Agent 智能体开发》第 52/55 篇
上一篇系列目录下一篇

把智能体装进随身设备或者本地主机里，工程问题会换一副面貌。本文讨论端侧 Agent 的约束结构：内存、发热、电量、系统权限与更新通道如何成套地出现，并逐项改变架构选择。本文不写具体机型参数、跑分与延迟数字，涉及推理工具与模型格式时只写项目名与定位，能力与兼容性细节请按各官方兼容列表与当期文档核对。

约束是成套出现的，不是”模型偏小”这么简单

端侧智能体最常见的误判，是把难点归结为”模型参数少了”。真实情况是约束成套出现，每一项都会单独否决一种云端理所当然的做法。内存决定同一时刻能驻留多大的模型、能撑住多长的会话；发热决定峰值算力能维持多久，不能把”跑得动峰值”当成”跑得动常态”；电量把等待模型的时间变成用户直接感知的成本；系统权限决定工具能否触达真实数据，而操作系统只认沙箱、权限申请与用户确认这三类机制；更新通道决定新模型如何灰度触达用户、出问题如何退回来。约束还互相咬合：上下文更长要换内存，内存吃紧就得更狠的量化，量化伤指令跟随，调用失败的重试又消耗电量。端侧架构的核心工作是在五类约束之间找自洽的组合。本文对 llama.cpp、Ollama、ExecuTorch、MLX 这类项目只提名称与定位，不写版本号；KV Cache 机制与私有化部署另有专文，边缘侧的部署形态也另有专文，本文只谈端侧后果。

规模档位与量化档位之间换的是什么

端侧能装多大模型由可用内存与量化档位共同决定，两个变量必须一起看：保守量化体积更大但行为稳定，激进量化把体积压下去，代价分摊到质量与稳定性上。以 GGUF 这类量化体系为例，命名中的 K、Q、I 等系列刻画的就是”体积—速度—质量”的不同折中，有的偏重速度，有的偏重同体积下保住质量，选型看的是折中方向而不是数字排名；本文不写困惑度、跑分与内存数值。判断口径：降低量化档位时，最先劣化的通常不是”回答是否聪明”，而是指令跟随与工具调用的稳定性——格式错乱的函数调用、被忽略的系统约束，在端侧尤其致命，因为重试成本远高于云端；长上下文的可用性排在第二波劣化里。由此两条结论：其一，”能否稳定产出格式正确的工具调用”排在”对话是否流畅”之前，宁可模型小一档、量化保守一档；其二，同样内存预算下，中低档位配稳妥量化常优于顶配规模加最低档位，后者看似参数多、可用行为更少。换档之后，提示词模板与工具描述必须重新验证——量化不是无损换壳，它改变的是可信行为边界。

上下文是内存账单，所以端侧要更早检索与摘要

云端可以把”窗口大”当卖点，端侧不行——上下文不是免费的文本空间，而是实打实的内存账单：留在窗口里的每段历史都占用缓存内存，窗口越长，留给权重与其他应用的余量越少；长上下文的持续读写还会把散热受限的设备拖入降频。所以端侧的”窗口大”不是能力，而是风险后置：会话过半时内存耗尽、被系统回收，或者慢到用户放弃。端侧 Agent 要比云端更早引入检索与摘要，把”记住全部原文”换成”记住可复原的索引”：当前任务只保留结构化状态摘要——目标、已确认约束、待办、最近结果——原文放入本地索引按需检索；跨天历史默认不进模型窗口。摘要也要防漂移：每轮保留”哪些事实被删除”的清单，避免压缩把用户明确说过的约束悄悄抹掉。这笔账单还影响系统提示与工具定义的体积：把所有工具说明书塞进系统提示在端侧是奢侈品，工具多时应按任务分组建子集，或用 Agent Skills 这类按需加载能力说明的机制。MCP 在端侧同样适用，其 2025-11-25 修订可稳定使用；官方已给出下一轮修订的 RC，草案方向仍可能变动，接入前以当期文档核对。

设备内动作要有分层的权限模型

端侧 Agent 的价值来自它能真正操作设备——读写文件、发通知、调用系统应用，风险也来自同一处。动作分三类：低敏读取可批量授权；发送、删除、支付等有外部可见后果的动作必须逐次确认；触碰敏感数据入口的默认拒绝，按最小必要逐项申请。这一分层与云端授权设计同源，通用授权模型、危险动作审批门槛、沙箱隔离层次与文件系统策略另有专文，本文只写设备侧的差异。差异有三点：其一，裁决者是操作系统，应用只能在系统提供的机制内登记意图，凡替用户静默执行的动作都应视为设计缺陷；其二，权限要绑定用户在场——前台交互期间的确认可以直接采信，界面不可见时收到确认请求应暂停任务等用户回来，而不是在后台替用户点确认；其三，批量授权必须带过期时间与撤销入口，随时可查、随时可断。授权粒度还要说成用户听得懂的话：”允许访问文档目录”可理解，”允许执行任意文件操作”不可，描述越接近实际后果，确认越有效；幂等读取与有副作用的写入应分别计数、分别留痕。

系统级入口：高价值与高隐私是同一件事

通知、剪贴板、相册、日历、定位这五个系统级入口，几乎同时决定了端侧 Agent 的全部便利与全部隐私风险。通知是最自然的触发器，但通知内容常含验证码与私人对话，合理起点是默认拒绝、仅按应用白名单放行。剪贴板最顺手也最危险，其历史里混杂密码与口令，必须不得默认可读，只在用户明确发起的动作内瞬时读取一次。相册承载人脸、地点与票据，语义检索价值高、泄露代价同样高，应限定到用户圈选的相册或时间段。日历能驱动”帮我准备下午的会”这类场景，但日程本身就是行为画像，授权应只读、限时、不留云端副本。定位让”到家提醒”成为可能，连续定位等于行踪记录，默认单次或粗粒度，精确且连续必须显式申请并展示状态图标。统一做法：默认拒绝、逐项申请、用完可撤销、访问留痕可在界面回看；任何”为了体验先全要了”的权限清单，都是在把产品变成审计风险。本文只讨论授权机制的设计，不示范读取真实个人数据的实现。

离线时任务排队，恢复后按幂等与冲突合并

端侧 Agent 必须在”没网”的前提下设计任务流：任务在本地排队，网络只是可选的下游。排队要解决三件事。失效：任务应带生成时间与前提条件，前提过期就作废而不是硬执行，”帮我回复这条消息”在断网两小时后可能已过时，恢复网络后的正确动作是重新确认而不是补发。幂等：有副作用的动作携带本地生成的幂等标识，重放时服务端与本地都能识别”这个动作已做过”；做不到幂等的重试就只重试读取、不重试写入。冲突：本地修改与云端版本只有元数据与时间戳可判的情形才自动合并，内容级冲突一律交还用户选择，Agent 无权在后台替用户挑一个。另一类任务离线做不完：某些结果必须回传云端才能继续，硬口径是回传要告知——任务创建时就说明哪一步会离开设备、传出去什么内容、对方是谁，用户可选择只做本地部分；事后弹窗补问”是否允许上传”，实际是把架构缺陷转嫁给用户的注意力。

端云分派：预算、能力与授权状态三个闸门

端侧还是云端执行，判定收敛为三个闸门：隐私授权状态、能力（本地模型能否稳定完成这类任务）、预算（当前内存、电量、热状态是否允许现在就跑）。隐私是硬否决，能力与预算只影响路径选择。小模型与大模型协同的形态分类、交接契约与升级判定见《小模型与大模型协同》，路由信号与级联写法另有专文，本文不复述，只给设备这一侧的分派与授权判定流程。

flowchart TD
    A[任务进入本地调度器] --> B{涉及系统级敏感入口}
    B -- 是且未授权 --> C[默认拒绝并告知原因]
    B -- 否或已逐项授权 --> D{数据允许离开设备}
    D -- 否 --> E[仅用本地模型执行]
    D -- 是 --> F{本地模型能力足够}
    F -- 是 --> G{内存与热状态允许}
    F -- 否 --> H{云端调用已获用户授权}
    H -- 否 --> E
    H -- 是 --> I[脱敏后上云并留痕]
    G -- 是 --> J[本地执行]
    G -- 否 --> K[排队等待或提示用户充电降温]
    E --> L{动作有外部副作用}
    I --> L
    J --> L
    L -- 是 --> M[前台逐次确认后执行]

    M --> N
    K --> N

失败回退的方向也要定死：云端回退到本地时，只能降级为本地能稳定完成的部分并明确列出未完成项，不允许本地模型补写没把握的内容冒充完整结果；本地回退到云端时，必须先确认授权仍然有效，不能拿任务创建时的授权当免死金牌。

模型也是一种发布物

模型文件和二进制、提示词模板一样是发布物，要同时管理获取、校验、灰度与回滚。获取：支持断点续传与网络类型约束，默认只在 Wi-Fi 下载、蜂窝网络需用户确认，下载与推理不抢同一份内存。校验：文件带可验证的来源信息与完整性校验，加载前核对，失败的文件直接隔离；模型来自开源渠道时，”谁做的量化转换””权重来自哪个仓库”属于供应链信息，应留在设备元数据里可查。

灰度在端侧有特殊性：一次更新影响的是每台设备上驻留的那一份权重，灰度单位是设备与用户；回滚必须连同提示词与工具定义一起回——模型、模板、工具描述是一个行为整体，只回滚其中一件会让行为落在从未验证过的组合上。新模型下载完成但加载失败时，系统应自动退回旧版本并把原因写进本地日志，而不是反复重试。版本命名策略本文不展开，按所用推理框架与分发渠道的当期文档核对。

观测留在设备内，场景决定要不要端侧

端侧产品天然背着默认数据不出设备的隐私口径，而观测与埋点几乎总想要更多。收敛的办法是把观测分两层：诊断层（崩溃、加载失败、工具调用错误率、热降频是否发生）留在设备本地，仅在用户主动反馈时随附，且随附前展示将要带走的清单；指标层确需上云时，先脱敏、只取最小必要，并明确告知、允许关闭、开关状态留痕。最不能妥协的一条：用户的提问原文与生成文本不是默认埋点，上报它们需要独立于任何”改善体验”总开关的显式同意。上下文准入表与上传前脱敏另有专文，端侧的差异在于：日志的默认归宿是设备内的滚动文件，而不是采集服务的队列。

哪些场景值得把 Agent 放在端侧，可以用一张对照表把能力、做法、约束来源与确认点摆在一起：

能力或动作 端侧做法 约束来源 需要向用户确认的点
读写用户文件 限定目录、只读优先、写入进临时区 系统沙箱与权限机制 目录范围、授权有效期
发送通知 由任务触发、内容本地生成 系统通知权限 是否允许后台触发
读取剪贴板 不得默认可读，仅在用户发起的动作内瞬时读 隐私入口 每次即时确认或短效授权
相册检索 限定圈选范围，特征本地计算 内存与热 相册范围与时间跨度
使用定位 单次或模糊粒度优先 电量与隐私 精确且连续定位须显式申请

调用云端补能力 脱敏后上云、结果回本地校验 授权状态 传什么、给谁、可否关闭

反过来，不值得硬塞端侧的场景也要说清：需要超长上下文的整库分析，内存账单付不起；需要最新知识的任务，知识截止让硬答比拒答更糟；需要强合规审计的重任务，端侧留痕证明力有限，更接近私有化部署的讨论范围。判断标准不是能不能跑起来，而是跑起来之后行为是否可信、失败是否可收拾。

小结

端侧 Agent 的工程本质是同时解五道约束：内存、热、电量、权限、更新。模型规模与量化档位要在同一张预算表里选；上下文长度最终都换算成内存账单，检索与摘要要比云端来得更早；动作权限按后果分层，敏感入口默认拒绝、逐项授权、可撤销、有留痕，剪贴板与通讯录不在默认可读之列；离线任务靠失效规则与幂等标识排队，回传必须先告知。端云分派里隐私是硬否决闸门；模型文件要当发布物管理，灰度与回滚落在每台设备上；观测默认留在设备内，用户原文不做默认埋点。值得端侧的是隐私敏感、离线可用、低延迟交互与批量重复动作，超长上下文、最新知识与强合规审计交给更合适的部署形态。约束不会消失，端侧的功夫就是让它们彼此不再打架。
