Agent 工具协议标准化

本文属于《Agent 智能体开发》第 18/55 篇
上一篇系列目录下一篇

工具协议这两年冒出来不少，争论也多，但评价它们的尺子其实一直没变：第三方能不能安全地扩展，宿主在升级时会不会被打穿。本文把”工具协议标准化”拆成三层——描述与发现、调用与结果、身份与授权——逐层讨论该定什么标准、怎么管版本、迁移节奏怎么排。协议自身的生态与供应链问题另有专文，这里不展开。

立论：竞争不在语法，而在扩展与升级

比较两个工具协议时，工程师习惯先抠表面功夫：schema 用 JSON 还是 YAML，传输走 RPC 还是 REST，字段命名是驼峰还是下划线。这些差异确实影响开发体验，但它们从来不是生死原因。序列化领域的历史早就给过教训：编码方案之争的胜出者，往往不是字节布局最优雅的那一个，而是把生态挂在自己身上、并且升级路径最平滑的那一个。工具协议服从同一条规律。

真正决定一个工具协议成败的问题只有两个。第一个问题是：第三方能不能安全地扩展。协议一旦进入生产环境，它的价值主要由别人贡献的能力来实现——各种连接器、服务器、工具集。如果协议没有给出明确的扩展点、权限边界和版本协商机制，第三方扩展就只能靠猜宿主的实现行为来对接，耦合迟早烂掉；更糟的是，猜错的那部分往往恰好落在安全边界上。第二个问题是：升级时会不会打穿宿主。宿主夹在中间，上面是模型，下面是真实系统，协议来一次破坏性变更，就可能让历史上注册过的全部工具在一夜之间语义漂移。一个协议的升级纪律能不能把影响半径约束在可预期的范围里，是企业敢把资产押上去的根本原因。

围绕这两个问题，本文提出一个三层框架。第一层是描述与发现，解决”这个能力是什么、去哪里找到它”；第二层是调用与结果，解决”怎么把它执行掉、拿回来的东西如何消费”；第三层是身份与授权，解决”谁有权执行这次调用、事后如何追责”。三层的标准化工各不同，互相纠缠正是许多协议失败的共同根源：有的协议在第一层做得很漂亮，结果语义全靠字符串约定；有的协议把授权做成装饰，委托链一长就形同虚设。把三层拆干净，是讨论标准化的第一步。

第一层：描述与发现

描述层的头号误区，是把函数签名当成协议。签名只回答”参数叫什么、类型是什么、返回什么”，而调用方在真实系统里做决策需要的信息远不止这些：这个操作是读还是写，有没有副作用，重试是否安全，一次调用大致消耗多少成本，延迟量级有多大，依赖哪些外部系统。这些信息如果不进 schema，就只能散落在人类撰写的描述文本里、或者宿主的私有配置里，可移植性无从谈起——换一家宿主，这些隐含知识全部丢失。标准化的正确做法，是把它们提升为描述层的正式字段。类型与约束的表达可以直接复用 JSON Schema、OpenAPI 这一层已经成熟的契约技术，本文不再重复它们与 gRPC/Protobuf、AsyncAPI 的基础对比（那是序列化与接口契约专文的范围）；但副作用标注、幂等性提示、成本与延迟分级这类字段，必须由工具协议自己定义，任何通用 schema 语言都替你想不到。

发现层要解决的是”一个客户端怎么知道某个服务器到底实现了协议的哪一部分”。认真的协议不会让客户端靠猜测行事，而是定义一组能力声明：建立连接时双方交换各自支持的可选能力，之后任何一方都只走对方声明过的路径。能力协商的价值在版本演进时才真正显现：协议新增了某个方法，老服务器不支持，能力声明天然构成兼容围栏，客户端自动退回旧行为，不需要为每个小增补都升一次协议大版本。反过来说，没有能力协商机制的协议，版本演进只剩两条路：要么破坏性变更一刀切，要么在文档里写满”某些服务器可能不支持”的免责声明——两条都是灾难。

版本与兼容矩阵是描述层的第三块地基。工具描述一旦发布就不能随意改动：改参数名、增删枚举值、收紧约束，三者的破坏性权重完全不同，标准必须明确哪些改动需要走大版本、哪些允许搭车小版本。还有一个容易被忽视的原则：版本号应该约束协议本身，而不是某个产品的功能进度。把”我们支持了某某版本”当成产品能力宣传，是本篇第 9 节要单独批评的误区。

第二层：调用与结果

调用层标准化的第一件事，是给结果建立类型系统，而不是默认”返回一段文本”。合理的结果类型至少分四种。文本：直接供模型消费的自然语言内容，注意是”供模型读”而不是”供日志看”。结构化：带显式编码并引用某个 schema 的数据，让宿主可以程序化处理而不是再让模型解析一遍。二进制：必须携带媒体类型与规模信息，把图片或者文件编码成长字符串塞进文本结果里，是协议早期实现常见的自毁行为——它同时浪费上下文、破坏缓存键、模糊权限边界。引用：只返回一个句柄，内容物化需要第二次显式拉取。引用型结果在授权上意义特殊：一次调用可以”知道存在”某份数据而不”拿到”它，为下游的最小权限留出操作空间。

第二件事是错误语义。本文主张所有工具协议都应把错误收敛到三态。可重试：请求大概率没有产生副作用，或者副作用本身幂等，换个时间再打一次是安全的。不可重试：语义上失败，参数错了、权限不够、对象不存在，重试只会刷日志。未知：请求可能已经执行、也可能压根没到达——连接断了、超时了、响应丢了，此时调用方对”世界被改了没有”处于无知状态。把三态压扁成一个错误字符串，或者用一个统一的重试循环吞掉所有失败，是 Agent 系统重复扣款、重复发货这类事故的头号来源。标准化的底线是：让调用方有能力区分”确定没发生”和”不知道发没发生”，并且协议鼓励服务器在错误响应里显式声明后者。

第三件事是流式、取消、超时与幂等键。长任务的输出应当可以分段消费：中间进度、部分结果、完成信号各有各的形态，宿主才能决定哪些进上下文、哪些只进监控。取消信号必须沿调用链一致传播——客户端发出取消之后，要么服务器真的停手并确认，要么明确告知”无法停止、已产生的副作用清单如下”，不允许静默忽略。超时是双方共同决定的：宿主有硬超时，服务器可以有自报的预估时长，生效的应该是更严格的那个。幂等键则应该由协议层定义为写操作的正式字段，而不是各家宿主塞在参数里的私有约定；服务器被要求在合理窗口内对相同键返回相同结果。

第三层：身份与授权

工具调用天然是一条跨信任域的委托链：用户授权宿主，宿主驱动客户端，客户端调用服务器，服务器再伸手进入外部系统。每一跳都带着上一跳给不了的上下文，也带着下一跳不该看到的信息。标准化的要求可以浓缩成一句话：权限沿链条只能收窄，不能放大。用图来摆信任边界：

范围与最小权限是授权层第一个要标准化的概念。协议至少要支持”每次调用可以携带比总授权更小的范围声明”，让服务器可以断言这次操作只使用了被授予范围的哪个子集；一个所有调用共享同一枚全局令牌的架构里，”最小权限”只是修辞。令牌的生命周期是第二个：签发在哪里、多久轮换、什么时候必须失效，标准未必能规定具体时长，但必须规定”凭据不得出现在三个位置”——模型的上下文窗口、任何一层的日志、以及缓存键的组成部分。这三个禁区的操作细节在权限控制的专文里已有展开，本文只强调标准化的一面：如果协议文本不写死这条禁令，宿主实现者与服务器实现者会各凭运气，安全审计就没有共同的参照物。第三个要标准化的是审计的可重建性：谁、经由哪条委托链、用什么参数调用了哪个工具、外部系统实际发生了什么、结果是什么——协议层要留足钩子，使得这些事件可以事后重建。可重建，是企业敢把核心系统接入协议生态的前提，也是出事故时定责的唯一依据。

授权侧的标准化目前有一个可引用的动态：官方已给出修订候选稿（RC，2026-05-29），方向包括把异步任务归入扩展、新增发现类方法、去掉会话与初始化握手的强绑定、强化授权侧对签发方的校验、以客户端身份元数据文档取代动态注册、把 HTTP+SSE 传输与 Roots、Sampling 原语列入废弃清单并给出约 12 个月的移除窗口——注意，这一切都是草案，可能变动。本文刻意不写具体端点与字段拼写，因为草案阶段的细节正是最不该被工程团队抄进代码的部分。真正值得现在就开始做的，是把自家实现里对”签发方校验”和”客户端身份注册”的依赖梳理出来，等草案定稿时你才知道自己要动多少地方。

工具层与协作层不是一件事

拆完三层，就能看清一个常被混淆的分界：工具层协议解决”怎么调用一个能力”，协作层协议解决”怎么找到并交接一个任务”。前者的单位是一次调用与一份结果，后者的单位是一个待办从提出方流转到执行方再流回来。两层各有各的标准化难题，硬用一层协议同时回答两个问题，通常两头都做不好。本文通篇讨论的是工具层；协作层这边，可以点名的已核实时间线只有 A2A 一条：2025-04-09 公开宣布，2025-06-23 进入 Linux Foundation，2025-07-30 发布 v0.3.0，2026-03-12 发布 v1.0.0，2026-05-26 发布 v1.0.1——最后两个节点都早于本文写作日，属于可陈述的事实。此外 AGNTCY 于 2025-07-29 对外公布，Agent Skills 于 2025-10-16 发布、其规格放在 anthropics/skills 仓库的 spec 目录里。除这些之外，若干组织各自提出过协议，尚未收敛，本文不为它们编造名字或代号。

回到工具层，真正影响工程决策的是三种封装形态的可移植性边界各不相同。第一种是宿主私有函数调用：模型直接以宿主定义的形式发起调用，链路最短、迭代最快，但它只在一家宿主内生效，换宿主或者换模型供应商就得全部重来。各 agent 框架大体走这条路——就当期版本口径而言，LangChain 已到 1.3、LangGraph 到 1.2，OpenAI Agents SDK 仍处于 0.x 的快节奏阶段，CrewAI、AutoGen、Eino 各有自己的定位与生态位；本文不重复它们的接口细节，只指出共同点：框架内函数调用格式的互换性，从来不是这些工具要解决的问题。第二种是协议工具：走标准的客户端与服务器模型，跨宿主复用的前提是宿主实现了协议、并且工具描述停留在各宿主能力交集之内——你在描述层用了某个只有某家宿主才理解的字段，可移植性立刻归零。第三种是技能包：封装的不是”一个能力入口”，而是”做法”本身——流程说明、脚本、参考资料打包分发，可移植性看着最强，实则最依赖执行环境的文件系统与运行能力，标准化的边界因此落在运行时而不是接口上。三种形态没有优劣之分，只有边界之分；把它们混在一个清单里比较”哪个更标准”，是提问方式错了。

治理主体与变更流程

协议标准化绕不开的一个问题是：谁有权在什么时候改变协议。这决定了工程团队能不能做长期规划。标准由基金会或者联盟托管，与由单一公司维护，差别不在名义而在流程：变更提案谁能提、评审要走多久、决议记录在哪里、弃用政策有没有最低保护窗口、参考实现是否随协议同步演进、有没有一致性测试套件把规范文字钉死成可执行判据。文档可以模糊，测试套件不能模糊——一个协议有没有”符合性测试”，是区分”有治理的标准”与”有站点的库”的最硬指标。

已核实的治理节点是这样。Agentic AI Foundation 在 2025-12-09 发布公告，目前托管 MCP、AGENTS.md 与 goose 三个项目；这为 MCP 的变更流程提供了明确的受理主体，也是把 2026 年中的候选稿视为”有治理的演进”而非”单方改接口”的底气所在。A2A 一侧的治理主体则是 Linux Foundation，时间线见上一节。除此之外的多数协议，治理主体未定，本文不做推断。

发现层的基础设施同样需要治理视角。MCP 的注册表项目目前仍是预览状态，API 冻结在 v0.1，整体仍在演进——这句话的含义是：它可以作为今天试验发现机制的参照，但不能作为明天生产依赖的承诺。注册表标准化的对象是”怎么登记、怎么查询、元数据长什么样”，它天然管不到”登记的东西是否安全”——这一点放到第 9 节的误区里再批评。最后说一句与模型的关系以免跑题：协议标准化与具体模型版本基本无关，本文涉及的模型仅按官方当期口径点名——Claude 侧有 Opus 4.6、4.7、4.8 与 Sonnet 4.6，以及 2026-07-09 起用的 Fable 5 与 Mythos 5；其余厂商的型号与日期一律以官方当期公布为准，本文不做罗列。任何把”该选哪个协议”论证成”某个模型更强所以无所谓”的说法，保质期都不会超过一个季度。

弃用与迁移的节奏

先对齐口径。截至本文写作（2026-07-18），MCP 官方已发布的最新修订是 2025-11-25 版，其把异步 Tasks 与 Extensions 纳入标准的主线方向已被社区反复引用；下一次修订的正式文本尚未发布，本文不猜测其内容。能作为既成事实陈述的，只到 2025-11-25 版为止；2026-05-29 的候选稿（RC）给出的所有方向——包括把 HTTP+SSE 传输与 Roots、Sampling 列入废弃清单、并给出约 12 个月移除窗口——在定稿之前一律按草案对待。这个区分不是学究气：把草案当事实排进迁移计划，和把事实当草案无限拖延，是节奏失控的两个对称方向。

废弃清单加上移除窗口，应该被翻译成一份工程排期而不是新闻。可行的节奏大致五步。第一步在废弃公告当日：盘点自家使用面——哪些工具、哪些宿主路径、哪些集成方踩在将被移除的能力上，产出一张影响清单。第二步在窗口的前三分之一：冻结新增依赖，新代码一律走替代路径，存量代码允许继续运行但挂上监控。第三步在中间三分之一：双轨运行，新旧两条路径同时在线，用契约测试把”同一批调用在两条路径上的语义等价”固化为可重复执行的验证。第四步在窗口末尾三分之一：灰度关闭旧轨道，从最低流量的集成方开始，每关一段观察一个完整业务周期。第五步在移除生效后：保留一层薄薄的适配器和整套测试夹具一段时间，专门用来对付没及时升级的长尾接入方——适配器的寿命以事故回溯的需要为准，而不是以协议文档为准。

双轨期的核心工件是一张兼容矩阵：行是协议版本与传输方式，列是自家宿主的关键能力（发现、调用、流式、取消、授权刷新），单元格只允许三种状态——支持、已废弃、已移除。矩阵的价值不在于穷举，而在于强迫每个单元格有人签字。矩阵里的阈值——比如”旧轨道流量降到多少才允许进入下一步”——用团队约定示例即可，例如”连续两周低于总调用量的 5%（团队约定示例，非行业标准）”；切流比例与回滚条件同理，写清是示意值。验证方法上，三件套缺一不可：一致性测试确认你符合协议文本，流量回放确认历史调用在新轨道上结果可比，金丝雀发布确认真实世界的分布没有暗坑。只做完第一件就宣布迁移成功的团队，通常在第三个月收到回滚请求。

标准化成熟度自评表

下面这张表供读者直接抄进自己的协作空间，逐层回答五个问题，把”你现在的做法”一栏如实填写——本文刻意不预填任何结论或数值，因为差距只有对照自家系统才看得出来。评分口径也建议团队自己约定，不要抄别家的。

层次 问题 你现在的做法 差距 下一步
描述与发现 工具描述里有没有副作用、幂等、成本字段？
描述与发现 有没有能力协商机制，还是靠文档免责声明？
描述与发现 工具描述的变更走什么评审、有没有兼容矩阵？
调用与结果 结果类型是否区分文本、结构化、二进制、引用？
调用与结果 错误是否能区分可重试、不可重试、未知三态？
调用与结果 取消与超时沿调用链是否一致传播？
身份与授权 委托链每一跳能否收窄范围而非放大？
身份与授权 令牌生命周期有无明确规范与轮换证据？
身份与授权 事故后能否重建”谁经何链调用了什么”？
治理与迁移 废弃公告到移除窗口的排期有无负责人签字？
治理与迁移 双轨期验证是否覆盖一致测试、回放、灰度？
治理与迁移 依赖的是已发布修订还是草案？草案有无隔离层？

填表的顺序建议从最后四行倒着来：先确认你依赖的是事实还是草案，再确认迁移有无排期，最后才回头修协议实现本身的层次缺口。多数团队会发现，最难填的不是技术行，而是治理行——因为”谁签字”这个问题往往没有现成答案。

四个常见误区

第一个误区：把注册表当安全审核。注册表索引的是元数据——名称、描述、schema、来源地址；它不签名、不审计、不保证发布者和代码作者的意图。装上注册表里任何一个工具，本质仍然是执行一段第三方代码。发现层的标准化解决”找得到、对得上”，信任的锚点必须建立在发现层之外：来源验证、发布流程、运行隔离，缺一件都不能因为”它是从注册表里装的”而豁免。

第二个误区：把 schema 当权限模型。schema 描述”参数应该长什么样”，权限决定”谁能发起哪类调用”；在字段旁边写一个看似严厉的说明文字，不构成任何执行。真正的执行发生在服务器侧与委托链上——校验范围、核对签发方、拒绝越权调用。一个描述层再精致的协议，如果授权层只有约定没有执行点，它的”安全”二字就是纸糊的。

第三个误区：把协议版本当产品能力。宣称”我们已支持某年某月修订”只说明兼容性契约的立场，不说明用户能多做任何一件事。能力在产品层面是连续光谱——有没有实现某个可选扩展、错误三态做没做全、授权刷新顺不顺滑——这些都与版本号的数字没有对应关系。把版本号印在产品页上，然后让客户按版本号做采购判断，是把工程语言冒充成价值语言。

第四个误区：以为标准化能解决任务的可验证性。协议能保证”调用被正确地发出与回执”，不能保证”事情做对了”。模型选错工具、参数语义正确但意图错误、结果真实但对任务无益——这三类失败都在协议射程之外。评测怎么做，官方工程栏目已有专门文章讨论 agent 评测的方法，结论同样是标准化只能解决评测数据可复现的那一角。三层协议建得再齐整，任务验证仍然是独立的学科，不要指望前者替代后者。

与相邻主题的划界

与 MCP 生态：协议自身的生态、原语用法与供应链问题另有专文，入门视角可参见更早的 MCP 介绍文章，本文只谈三层标准化的议题。与工具调用机制：模型侧如何决定调用哪个工具、调用循环如何编排，是工具调用主题的范畴；本文把”调用已经决定”当作给定，只讨论决定之后的协议约束。与协作协议及经济问题：跨智能体的任务流转与市场机制另有专文，本文只在前面《工具层与协作层不是一件事》一节把两层的边界切清楚，不延伸到交易与计价。与序列化协议对比：JSON Schema、OpenAPI、Protobuf、AsyncAPI 在编码与契约表达上的差异是专门主题，本文只在需要时引用一句，不重开对比。

小结

工具协议之间的竞争，表面在语法，实质在两个更深的位置：第三方能否安全扩展，升级时能否不打穿宿主。把标准化拆成三层来谈——描述与发现负责”说清楚能力是什么”，调用与结果负责”执行得可预期”，身份与授权负责”责任可重建”——每一层都有自己成熟的工程问题与对应的失败模式，混层讨论是多数争论无疾而终的原因。对事实与草案保持口径纪律：已发布修订才是地基，候选稿只配隔离层；废弃公告、移除窗口、双轨矩阵与三件套验证，是把节奏落到排期的最小单元。最后把那张空白的成熟度自评表留给读者：标准化不是选出来的，是按层量出来、再一寸寸补上去的。
