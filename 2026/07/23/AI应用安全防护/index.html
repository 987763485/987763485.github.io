AI 应用安全防护

本文只讲防御与流程，不给可复制的攻击手法，不提供任何注入样例、越狱话术、逃逸步骤或绕过手段。要解决的工程问题是：一个会读外部内容、会调工具、会执行产出、会花钱和改数据的智能体应用，应该把防线摆在哪些层次、每层放什么控制、用什么方法证明这些控制真的生效。

风险来源一律按类别讨论，例如“外部内容携带指令”“工具返回值进入上下文”“模型生成的代码被执行”，不指向任何具体产品，也不引用漏洞编号、受影响版本或事件归因。文中阈值都是团队约定示例，不是行业统计结论；需要举例时用占位符或标注示意值。

传统 Web 防护为什么不够用

把 AI 应用当成“带搜索框的 Web 服务”来做防护，是多数事故的起点。智能体应用在三个地方与传统 Web 结构性不同，这三个不同决定了防线必须重排。

第一个特殊性是指令与数据同通道。传统架构里代码与输入走不同路径，SQL 参数不会被当作语句解析，模板变量不会被当作模板执行，这种分离由解析器强制保证。大模型应用把自然语言既当数据又当指令：用户提问、检索回来的网页片段、工具返回值字段、上传文档页眉，全部混进同一段上下文。分离不再自动成立，必须由设计显式建立——谁有资格影响系统行为，谁只能作为被处理的材料，这个边界要在提示组装、权限判定与输出校验三处同时表达。提示注入主题的专文已展开不可信内容的工程写法，本文只把它当作纵深防御的一层来排位置。

第二个特殊性是产出会被执行。模型生成的代码、命令、脚本、配置、富文本片段，下游往往真的有人消费。传统 Web 假设服务端逻辑是人写的、经过评审的；这里执行对象的文本在运行时生成，评审来不及参与。于是“输出即代码”这条路径只能靠执行隔离、出口策略与依赖供给的信任边界兜住，而不是靠生成质量的好坏来判断。命令执行与反序列化主题的专文处理的是同一条老规矩在新场景里的延续，本文不重复其手法描述。

第三个特殊性是动作有外部副作用。退款、下单、发消息、改权限、删数据、发布内容，一旦执行就消耗真实预算或改变他人状态。传统 Web 的写操作有事务与幂等键，智能体的动作长度、分支与重试次数却由模型在运行时决定。副作用必须分级——只读、可回滚写、需补偿的写、不可逆写，并把后两档放到人工确认之后。这一点与《Agent 安全与权限控制》的授权模型直接衔接，本文不展开权限判定本身，只引用它的结论：先把“能做什么”盘清楚，再谈“怎么做才安全”。

输入侧：把不可信内容当数据处理

输入侧的目标不是识别坏句子，而是让坏句子即使出现也拿不到执行权。这个区别很关键：基于文本特征的拦截永远追不上表述变化，基于来源与权限的边界才是结构性的。

第一层是来源标记。上下文里每段文本都要携带可机读的来源属性：会话内用户输入、系统提示与策略文本、检索库文档、网页抓取、邮件正文、上传文件解析结果、工具返回值、子智能体回传、技能包说明。来源属性不是给人看的注释，而是策略引擎的判定输入：只有被列为可信来源的文本才允许影响系统行为，其余一律作为被处理的材料注入。工程上常见做法是给外部文本套一层固定信封，信封边界与内容分别校验，内容中出现信封结束标记时必须转义或截断，不能被解析成结构。

第二层是信任分级与降权。检索结果与网页内容默认按最低信任处理：不进入系统提示的影响范围，不参与工具选择，不作为必须遵循的规则来源；邮件正文、工单描述、上传文档同样按不可信处理。若某类外部文本确实承载业务规则，例如合同条款抽取，要把它降级为待核对的候选依据，并在输出侧要求可指回原始文档的段落位置。这里与《浏览器 Agent 与 GUI 自动化》的界面内容边界讨论相邻，那篇专文处理页面文本与控件标签的信任问题，本文不复述。

第三层是长度、编码与结构探测。风险信号是形态而不是措辞：接近上下文窗口的超长输入、多层嵌套的转义与编码、同一指令以多种编码重复投递、异常密集的不可见字符、纯文本字段里塞入结构化载荷、解析产物中出现脚本或外部资源引用。这些形态应触发可判定的处理动作：截断并告知、要求分段提交、剥离载荷后再解析、拒绝进入工具链路。探测规则要能灰度与回滚，写成策略配置而不是散落在业务代码里。

第四层是越权指令识别。判定信号写在类别层：请求的操作超出当前会话已授权的工具集合；要求绕过确认、绕过审批或绕过日志；要求使用其他身份或更高权限；试图让系统输出内部凭据或配置；要求在无人参与时完成不可逆动作。命中信号的正确反应是降级并确认，不是解释为什么不行，更不是把内部策略文本回显出去。

工具侧：白名单、参数校验与确认门槛

工具是智能体唯一应当产生副作用的出口，因此这层的控制密度要高于其他层。目标是任何一次外部动作都能回答三个问题：这个工具有没有被授权、参数是不是合法、结果需不需要人点头。

工具白名单按每个智能体角色一套来维护，而不是全局一份。只做客服问答的角色不应持有部署类工具，只做数据汇总的角色不应持有写库工具。白名单条目本身是配置项，纳入变更评审与版本发布，改一条等于改一次权限。此处划一句界：协议层次与能力协商见《Agent 工具协议标准化》，供给生态见《模型上下文协议生态》，本文只关心工具作为攻击面与副作用面怎么管。以 MCP 为例，可引用口径只到已发布的 2025-11-25 修订；官方已给出 2026-05-29 的 RC，方向涉及更清晰的授权与生命周期语义，仍是草案、可能变动，本文不写端点与字段拼写。工具目录与注册中心的供应链风险按类别纳入白名单审核即可；MCP Registry 到本文日期仍是预览状态，预览态目录不适合作为生产唯一信任源。

可逆性分级按四档维护：只读、可回滚写、需补偿的写、不可逆。需补偿这一档最容易出事，例如已发出的通知技术上可撤回，但读者已经看见。分级结果要写进目录元数据作为策略引擎的硬输入，同时作为审计事件的必填字段，让事后回溯能看出当时判成了哪一档。

执行侧：生成代码的隔离与供给的信任边界

只要应用会运行模型生成的代码、命令或脚本，执行侧就是最硬的一层，因为它把文本重新变成行为。此处的分工是：隔离层次选型、文件系统策略与网络出口策略的展开见《Agent 代码执行沙箱设计》，本文不复述其清单；尚未成文的《Agent 沙箱与执行安全》会进一步处理执行时策略，这里也不替它展开。本文只讲应用侧必须自己拍板的三件事。

第一件是默认能力假设。执行环境假设输入不可信、假设代码会尝试访问环境、假设有外联冲动，因此起步能力为零：不注入业务凭据、不挂载生产数据卷、不提供内网路由。需要的能力按任务临时授予，用完即失效。Anthropic 工程栏目自 2026-06-24 起的《how we contain Claude》把隔离、权限最小化、出口控制与人工在环当成一组配套而非单选，这个结构判断与本文一致；同一栏目的《code execution with MCP》讨论把工具调用改写成代码执行以压缩上下文占用，它带来的直接安全后果是执行频次上升，因此执行侧配额要跟着重算——每加一层便利就要补一层约束。

第二件是资源与时长上限的机制层描述。要同时约束墙钟时间、CPU 与内存配额、文件描述符数量、进程与线程数量、磁盘写入量与临时层容量、外联次数与目标数量、输出字节数。这些配额的意义不止于防资源挤兑，更在于把失控循环变成可观测的失败。上限数值属于团队约定示例，但必须有上限，且触达上限时返回结构化错误码，让策略引擎能判定终止、重试还是升级到人工。

第三件是出口策略。网络出口默认拒绝、按需开洞，洞的粒度按目标与路径而不是按端口给；域名解析与直连地址要一致处理，避免解析绕过；元数据服务一类的高敏端点默认不可达。出口策略同时是数据外传的最后一道闸：即便前面几层都被绕过，未登记的目的地也连不出去。它与数据隐私主题的传输面控制互补——那篇专文处理上传前脱敏与字段级最小必要，本文只强调一点：出口策略必须能被审计事件验证，否则它只是一份没人检查的配置。

依赖与镜像供给属于执行侧的上游。构建产物里混入的包、被替换的基础镜像、动态拉取的脚本，都是模型生成代码之外的第二个执行来源。控制手段按类别列：锁定文件与摘要校验、来源白名单、构建与工作流权限分离、镜像最小化与只读根、运行时禁止再次拉包。生产镜像要能在无网络条件下启动核心功能，这一条能挡住大部分运行时取料的形态，供应链清单本身不在本文重复。

平台版本口径放在这一节交代，避免“版本旧所以做不了隔离”这类推辞：编排侧按当期 Kubernetes 1.36 的支持与安全基线口径核对策略能力，Node.js 侧区分 Node 26 Current 与 Node 24 LTS 的落地节奏，Go 侧以 Go 1.26 为工具链口径，推理与训练依赖按 PyTorch 当期 2.x 核对；框架层 LangChain 1.3 与 LangGraph 1.2 提供了图执行与检查点能力，可用来承载挂起等待人工确认这类流程，本文不写接口签名。

输出侧：敏感信息阻断、危险指令过滤与可追溯

输出是最后一道可机检的关口，也是直接面向用户与下游系统的接口。这层要同时处理三类问题：不该出去的内容、不该被下游执行的内容、说不清来源的结论。

第一类是敏感信息检测与阻断。检测对象按形态而非字面匹配组织：凭据形态（长随机串、带算法前缀的签名串、私钥封装块、内网令牌样式）、个人数据形态（联系方式样式、证件样式、账户与地址字段组合）、业务形态（内部工单号、数据库主键、未发布价格、内部接口路径）。文档与示例一律使用占位符，绝不把真实凭据、真实标识或可解密的中间值写进配置、日志、缓存键、测试固件或提示词。命中后的处理分级：阻断并回结构化错误、脱敏后放行、转人工复核，哪类字段走哪条路属于团队约定示例，但必须在配置里显式声明并可被回归测试覆盖。这里与《AI 应用的数据隐私保护》分工明确，那篇专文处理脱敏算法与准入表，本文只补两个输出侧的工程事实：检测必须覆盖流式输出的分片边界，避免跨片拼接绕过；检测结果要可解释，让被阻断方知道是哪一类被拦以及申诉路径，而不是一个含糊的失败。

第二类是危险指令的出站过滤。对象是输出会被下游再次解析的路径：生成的 SQL、脚本、配置、富文本、发往消息系统的正文、写入知识库的条目。控制点是把出站内容按目标消费器的语法再校验一遍：SQL 过解析器与语句类型限制，脚本过语法与能力检查，富文本按白名单标签属性转义，链接与媒体地址过目的地策略。原则是不要假设模型自己会克制，也不要假设上游校验覆盖了下游语法，跨消费器的语法要各自校验一遍。

第三类是引用与可追溯。凡依赖外部知识的事实性结论都应携带能回指证据的结构：来源标识、文档版本、段落或行号定位、抓取时间、检索得分。引用不是装饰，它承担三个安全功能：让复核者能验证，让下游能判断新鲜度，让依据缺失本身成为可机检信号。建议把结论与证据的关系写成结构化伴随数据而非内联正文，校验器据此检查高风险结论是否具备足够证据，缺证据时降级为待核实；低风险对话式输出可按团队约定示例豁免，但豁免清单要在评审里出现过。

身份与授权：委托链、短时凭据与代理身份

授权难点在于链条变长：人类用户授权应用，应用通过智能体委托工具，工具再调用下游服务。每一段都要有可验证的授权表达，不能靠“这个进程一直很有权限”的隐性继承。

委托链要回答三个问题：谁发起、授权范围到哪里、链上是否可验证。发起者身份要一路透传到副作用判定与审计事件，不能在中段被替换成服务账号后丢失。范围表达只能收窄不能放大：下游拿到的权限必须是上游授权集合的子集，任何扩权请求都回到人类授权节点；跨服务跳转用可验证断言而不是共享长期密钥。多智能体协作里父与子是委托而非继承，子智能体拿到本次任务的受限能力包，任务结束即回收；跨组织或跨租户的委托要额外记录被委托方身份与用途。本文不展开委托判定的算法细节，只补一句生态观察：Anthropic 工程栏目的《managed agents》讨论托管式执行体，与 2025-12-09 公告中由 Agentic AI Foundation 托管 MCP、AGENTS.md 与 goose 的思路一致，身份与生命周期需要平台化承接；互操作可参考 A2A v1.0.0 与 v1.0.1 及 AGNTCY 这类社区工作，Agent Skills（2025-10-16）把能力包变成可分发单元后，技能包被授予什么身份就成了新问题。

短时凭据是这层最直接的收益。凭据生命周期要短于任务生命周期，避免任务结束后凭据仍可用。凭据的三个禁区一句带过：上下文窗口、日志、缓存键都不该出现凭据，展开见《Agent 安全与权限控制》。工程上要额外检查的是发放方与轮换机制，以及配置里看起来无害的默认值：默认管理员口令、长期有效的测试令牌、被复制到其他环境的开发凭据，是三类最常见的越权入口，应在发布流水线上做存在性检查。

租户边界要在数据访问层而不是界面层落地。多租户应用里最危险的形态是上下文混装：把租户 A 的文档、模板与历史片段和租户 B 的请求送进同一次推理。控制手段按层次列：检索与索引按租户物理隔离；上下文组装阶段校验每条材料的归属；向量库过滤条件不能仅依赖调用方传入；导出与共享默认关闭并需显式审批；同一会话内角色切换要清空受信任状态。浏览器与界面自动化的登录态边界见《浏览器 Agent 与 GUI 自动化》，本文只保留总则：任何账号相关操作，包括点击、提交、读取页面数据与保存凭据，都仅在用户明确授权的账号与环境内进行，且该授权要作为可审计记录留存。

审计与留痕：记什么、不记什么、能不能重放

审计的目标是可重放与可归因，不是把所有文本存下来。这一点决定采集设计：记判定过程，不记被判定内容的原文。

应当记录的事件字段按四组组织：动作（谁在哪个会话下、对哪个工具、带什么参数摘要、副作用档位、结果状态）、判定依据（命中的策略标识与版本、信任分级结果、参数校验结论、确认走哪条分支）、授权来源（发起者、委托链上游身份、本次能力包标识、确认记录标识）、预算消耗（令牌与调用次数、额度占用、时长与资源触顶）。参数只记散列或经字段白名单过滤的摘要。事件结构示意如下，值均为占位符：

明确不该记的内容：用户提问与回答原文、凭据与令牌、精确地理位置、身份证件号与手机号、剪贴板内容、上传文件原始副本，以及任何“先存下来再说”的字段。采集遵循最小必要与脱敏，口径与《AI 应用的数据隐私保护》一致，本文补充审计侧两个陷阱：调试用的完整上下文快照常被视为临时开关，但只要它能在生产开启，就一定会在某次事故里被开启，因此要从生产配置中物理移除；第三方观测服务的默认采集项常包含请求体，接入前必须逐字段确认关闭或替换为摘要，而不是依赖口头承诺。

证据链要能重放，含义是给定一条事件记录，能重建当时的策略版本、上下文组装的可信摘要、工具目录元数据与权限判定输入，从而回答这个动作在当时是否被允许。重放不要求恢复原文，要求恢复决策条件。为此需要三件基础设施：策略配置版本化并保留历史；上下文组装产出结构化摘要而非只留最终字符串；工具目录与能力包按版本快照存档。重放能力还要被演练检验，按季度挑若干历史事件做重建，把重建失败当作缺陷记录。

事件响应：分级、暂停与对外口径

再完整的防线也会遇到没预料到的形态，因此事件响应是纵深防御最后一层，也是唯一必须平时演练的层。

分级按两条轴走。影响来源分三类：内容型（错误信息被输出、被污染的指令影响了行为）、动作型（不该执行的副作用发生了）、暴露型（不该离开边界的材料离开了）。影响范围按单会话、单租户、跨租户、平台级四档判定。两轴交叉得到处置优先级，不需要给事件起花名。

暂停与降级开关必须提前设计，而不是事故里现编。至少要有四档能力：按工具暂停并保留只读、按副作用档位冻结需补偿与不可逆写、按信任来源降级即停止外部文本进入上下文、整体停摆即会话只读并停止新任务。开关要满足三个条件：可灰度到单个租户或单个智能体角色、可在数分钟内生效、每次拨动都产生审计事件并通知值班与业务方。开关有效性要定期验证，从没被测试过的紧急停止按钮在事故中不可信；这与发布门禁的思路同源，但这里检查的是运行态能力，本文点到为止。

影响面判定沿两条线索同时做。行为线索：从审计事件回溯该策略版本下经过同一判定分支的所有动作，列出可能的误放行集合。数据线索：涉及哪些数据范围、是否外传、目的地是否在出口允许列表内。两线交叉出已确认受影响、疑似受影响、未受影响三档，每档给出对应补救与判定依据。补救要考虑可逆性分级：可回滚的走回滚，需补偿的走补偿与通知，不可逆的走止损与善后，补偿动作本身也要授权。

对外沟通遵循三条纪律：只讲已确认事实与正在采取的措施，未验证的因果不写；不透露绕过路径、规则细节与阈值，避免沟通本身变成第二手教程；给出复查询询方式与时间线承诺。通报时限不编造，一律按当期监管要求与合同约定核对后执行，需法务与合规确认的路径要在预案里写明由谁签。涉及合成内容的场景要核对标识义务：我国《人工智能生成合成内容标识办法》自 2025-09-01 施行，配套强制性国标 GB 45438-2025 同日实施；《网络数据安全管理条例》自 2025-01-01 施行，与《个人信息保护法》《数据安全法》这两部既有法律一起构成核对基线。欧盟侧，一般适用日 2026-08-02 即将到来，通用目的模型的义务自 2025-08-02 起已经适用，而被称为“数字 Omnibus”的调整仍只是欧委会 2025-11-19 提出的提案（COM(2025) 837），三方谈判未确认，不能写成已生效或已推迟。条款编号、罚则金额与解释口径本文一律不写，长文交给《大模型与安全合规》。

红队与回归：只谈流程与验收

红队是验证防线是否真的生效的手段，不是产出震撼报告的手段。本节只写流程与验收，不写具体攻击手法与载荷；手法层描述交给对齐评估与红队主题的专文，本文不重复其清单。

第一步是范围授权，必须书面且有边界。授权内容至少写清：允许触达的环境（只限测试环境，或明确列出的生产子集）、可用账号与数据范围、是否允许对外发送真实消息或产生真实费用、时间窗口与并发强度、以及发现即停的熔断条件。任何需要借用真实账号或真实用户数据的路径，都仅在用户明确授权的账号与环境内进行并保留授权记录。红队成员对生产凭据、客户数据与内部文档的访问权应与业务人员同等约束，不能因为是安全测试就默认放开。

参与角色建议固定五方：红队执行者、应用负责人、平台与基础设施负责人、法务与合规代表、拥有停摆开关使用权的值班负责人。职责在预案里写死，避免事故时才发现没人能拍停。节奏上建议常态化小步演练加季度综合演练，而不是年度一次性大检查。

场景清单按类别组织，条目本身不写载荷。可用的类别包括：外部内容携带指令并影响工具选择；工具返回值进入上下文后影响后续决策；模型生成的代码被执行时试图越出隔离与出口边界；参数与副作用档位被误判；委托链与跨租户边界被混淆；凭据与敏感字段经输出、日志或缓存外泄；确认门槛在无人参与路径上缺失；观测与调试通路成为额外数据出口。每族只给验收目标，即防线应当在哪一层拦住，不给实现细节。OWASP 一类公开风险清单在这里只当类别词汇表使用，例如提示注入、不安全的输出处理、供应链、权限升级这些名称，本文不写条目编号与年份对应关系。

发现分级不看戏剧效果，看四个可核要素：被突破的是哪一层防线、需要什么样的前置授权、影响面落在哪一档范围、是否已有可观测信号。分级结果直接映射修复优先级与是否触发事件响应。每个发现必须写清防线缺口而不是技巧描述，报告以控制缺失为主体，手法细节停留在必要最小。

闭环定义为五步：确认可复现的判定路径、定位应当拦住它的控制点、实现或调整该控制、在同环境与同等授权下复验、把验收断言写成回归用例入库。用例库与场景族分类对齐并保留元数据，即属于哪一层防线、依赖哪一版策略、当前状态，因为下一版模型或工具目录变更时，这批用例就是判断防线是否退化的依据。评测与门禁机制见《AI 应用评测体系》，本文只强调安全回归的两个特殊性：通过标准是控制点拦住而不是回答质量高；用例本身可能包含敏感材料形态，因此存储与访问按敏感数据管理。

落地节奏与度量

安全体系不会一次成型，按季度推进更容易验收，每格都要有可核对的交付物。

按季度推进的起点建议是：第一季度做可观测，结构化事件全量落库、工具目录补齐副作用与确认元数据、上下文组装产出可信摘要，缺这三件后面所有控制都无法验证。第二季度做边界，来源标记与信任分级全量落地、参数校验从字符串改为解析后的树、出口策略改为默认拒绝。第三季度做人与钱，确认门槛与额度包上线、凭据短时化与轮换改造、多租物理隔离核对。第四季度做检验，安全回归用例库成型、停摆开关拨测常态化、历史事件重放演练，此后每年重跑一次元数据与授权链完备性审计。

有效性用覆盖率、时效、闭环、残余四类内部指标衡量，四类阈值均为团队约定示例，重点看趋势与解释；策略、模式、出口允许列表与确认档位这些配置同样要版本化、能回滚，否则事后无法还原当时生效的是哪一版。

小结

防护难点不在某一层做得不够细，而在三条结构性变化：指令与数据同通道、产出会被执行、动作有外部副作用。传统 Web 的前提假设要全部重做，方式是沿数据流动把防线排队：输入侧用来源与信任分级代替措辞识别，工具侧用白名单、解析后树上的模式校验与副作用分级收口动作，执行侧用零起步能力、资源上限与默认拒绝出口承接生成代码，输出侧用形态检测、下游语法再校验与证据回指守住最后关口，授权与审计把整条链变成可验证、可重放的记录，事件响应与红队回归负责证明这些控制确实在工作。

写作与评审时请坚持本文边界：风险只在成因类别层讨论，不写漏洞编号与事件归因；凭据一律用占位符；账号与环境相关操作只在用户明确授权的范围内描述；观测保持最小必要与脱敏；红队只交付流程与验收；所有阈值标注为团队约定示例。防线的价值不体现在它支撑了多少惊人的故事，而体现在它能被检验、被重放、被回归覆盖。
