模型上下文协议生态

模型上下文协议（MCP）从 2024 年底走到 2025-11-25 修订，已经把“宿主如何发现并调用外部能力”这件事固化成一套可协商的接口。但真正决定落地成败的往往不是原语设计得多优雅，而是版本节奏、授权边界与分发信任这三件工程琐事。本文不重复协议入门内容，只讨论它在生态里的位置：一个服务器要承受多少种上游变化，一次工具调用的信任边界到底划在哪一跳，以及该用什么口径判断第三方实现值不值得引入。

协议要解决的三件事

把 MCP 当成“一层 JSON-RPC 包装”是常见误读。它真正要处理的是三件互相牵制的事：工具发现、能力声明、上下文注入。

工具发现回答“这里有什么可以调”。一个宿主接入的服务器可能同时暴露十几项能力，名称、描述、输入形状都由服务器给出；客户端在会话建立时抓取一次快照，之后依靠变更通知感知列表变化。这件事的难点不在请求本身，而在快照的生命周期：宿主侧的提示缓存以工具列表为前缀，一次列表变更会让下游一整段缓存失效，于是“服务器有权随时通知”与“宿主希望列表稳定”之间必须有工程上的节流与灰度约定。

能力声明回答“双方各自支持什么”。声明不是装饰性标签，而是决定后续请求能否成立的开关：对侧没有在声明里出现的能力，不应假定它存在，也不应指望它能应答。这条规则看起来弱，实际是整个协议能持续演化的前提——正因为能力是可选的，修订才可以在不破坏既有部署的前提下加入新形态。

上下文注入回答“这段内容以什么身份进入模型视野”。同样是把一段文本放进对话，作为工具返回值、作为被显式选中的资源内容、作为人手工附上的提示片段，三者的可信度等级、可撤销性与审计要求完全不同。协议把这三条路径分开表达，就是在提醒宿主：不要在拼接阶段把它们抹平成同一种东西。

那为什么“函数调用 schema”不够。第一，函数调用只描述单个函数的形状，不描述提供方是谁、实现到哪一版、语义是否已经变更，跨宿主复用只能靠人工粘贴与口头约定。第二，函数调用不携带授权语义：谁允许这次调用、访问下游用谁的身份、令牌从哪个授权服务器来，在 schema 里根本没有位置。第三，函数调用没有版本协商，双方约定一旦写死，上游改一个字段的必填性就等于破坏性变更，而且变更无法被消费方感知。MCP 把这三件事分别交给了发现类请求、能力声明与握手阶段的版本协商，代价是你从此要长期维护一个协议对等体——这才是真正的成本所在。

三类原语的分工与责任边界

tools、resources、prompts 经常被并列介绍，但三者的失败模式完全不同，选错的后果也不同。

tools 是“可能改变世界的调用”。它有副作用的可能，有明确的输入形状，返回值要参与下一轮推理。适合放在 tools 里的：查询工单系统、创建一次受控的计算、提交一段代码到评审队列。不适合的：把“读一下本机某个已知路径的文件”做成 tool——它没有需要模型现场决定的参数自由度，而且会把一次纯粹的人为选择变成模型自主行为，扩大不可预期执行的面积。

resources 是“可被引用的只读内容”。它有标识符、有内容类型，通常由人或宿主策略选择注入，而不是由模型自由决定。适合的：配置快照、指标看板导出、某次构建的产物清单。不适合的：任何需要写回的东西，以及任何“读了之后还要按调用者身份决定是否给出”的敏感内容——后者往往需要同时具备资源标识与访问控制，实现成本会迅速上升，很多团队在这里退回到 tool。

prompts 是“由人发起的模板”。它的设计意图是用户在宿主界面上点选一次，模板由服务器渲染后交给宿主。把业务能力塞进 prompts 是最常见的架构错误：一段“帮我复盘上周事故”的流程一旦被写成模板，它就会随宿主数量被复制成多份，版本无法协商、灰度无法控制、调用不留痕；等到需要把它接到审批流上时，你只能再写一个 tool，两套实现并存并且开始漂移。

判断口径只有三问：这段逻辑需要在服务器侧独立演进吗？需要按调用者鉴权吗？需要留下可回溯的调用记录吗？三问里有两个“是”，它就该是 tool，或者 resource 与 tool 的组合，而不是 prompt。

客户端与服务器的责任划分，我建议按下面这张表写进内部规范，而不是靠口口相传：

事项 客户端（宿主侧） 服务器
决定调用哪项能力、何时调用 负责 不参与
给出能力的名称、描述与输入形状 只消费 负责
决定结果何时以及以何种身份进入上下文 负责 不参与
访问下游系统并完成实际鉴权 不参与 负责
维护能力语义随版本的向后兼容 无法代劳 负责
控制并发、超时与重试预算 负责 需提供幂等性说明
把结果裁剪到合适长度 兜底 优先负责
对外来文本做边界标记与长度限制 负责 不适用

最后一行值得单独强调：服务器返回的正文、以及工具描述本身，都是外来文本。工具描述会以极高信任度进入模型的上下文，因此它的修改权限等同于一次代码发布。宿主在把任何服务器内容拼进对话之前，应有明确的边界标记与长度上限，这一条不属于可选加固。

传输形态与授权要求的演进

本地 stdio 与远端 HTTP 的差别不在吞吐，而在信任根。

stdio 场景里，服务器进程由宿主用本机配置启动，可执行文件路径、环境变量、工作目录全部来自一份人工维护的本机配置。这里几乎没有协议级的访问控制，边界就是操作系统账号：进程能读到什么、能以谁的身份写什么，取决于启动它的那份配置和那个用户。它的优点极其朴素——没有网络暴露面，也没有令牌生命周期要管；缺点同样朴素——一次更新的生效路径就是“有人改了本机配置并重启了宿主”，无法集中审计。

远端形态把问题换了性质：进程不再由宿主直接拥有，身份必须从令牌来。于是修订序列里授权部分的重量一路增加。2024-11-05 把基于授权码流程的授权正式纳入 HTTP 传输；2025-03-26 把要求提高到 OAuth 2.1 一族（含 PKCE）并要求访问令牌绑定受众，也就是把“这个令牌是给哪个资源服务器用的”写进请求（RFC 8707 的路子）。到本文可写的现行口径 2025-11-25 为止，累积的方向是稳定的四件事：授权必须走标准 OAuth 家族而非自定义头；访问令牌要有明确的受众绑定；受保护资源要能被客户端通过元数据自行发现；客户端注册要能自动化且可校验。更细的逐版本归因请以官方各版本文档的变更记录为准，这里不展开，因为这类细节在草案期仍然会动。

同一版本序列里另外两件值得注意的事：2025-11-25 这一版把异步任务与扩展机制纳入口径——这意味着“一次调用一次返回”不再是唯一合法形状；而这条线之后的变化目前只到草案。

官方已经给出下一个修订的 RC（2026-05-29），方向包括：把异步任务归入扩展；新增发现类方法（server/discover 一类）；去掉会话与初始化握手的强绑定；强化授权服务器侧对 issuer 的校验；以客户端 ID 元数据文档取代动态注册；把 HTTP 加 SSE 的传输形态与 Roots、Sampling 等能力列入废弃，并给出约 12 个月的移除窗口。这是草案，内容可能变动，包括窗口长度、条目取舍与最终发布时点。除上述已核实的方向外，本文不写任何端点名与字段拼写，也不把 2026-07-28 这个尚未发布的修订当已发布来讨论。对工程来说，草案唯一确定的价值是：它给了你一个可以提前排期的信号，而不是可以提前依赖的承诺。

授权落地最常见的事故不是算法错，而是凭据被放在了错误的地方。令牌、含令牌的请求头、以及可以从令牌反推出身份的长标识串，都不应出现在明文配置、日志与缓存键里——配置会被同步进仓库，日志会被采集到集中平台，缓存键会出现在指标标签和故障截图里。这三处的扩散路径不同，但结果一样：一次故障排查就是一次凭据广播。传输层的正确姿势是把令牌留在进程内存里，按受众分次获取，并且只记录令牌的指纹与过期时间这一类不可逆信息。

注册与分发：Registry 解决什么、不解决什么

MCP Registry 目前仍是预览阶段，接口冻结在 v0.1，仍在演进。因此本文不写它的可用性与采用度结论——这两类判断在 v0.1 阶段写下来，三个月后大概率是错的。

它解决的问题是两类。第一类是可发现性：服务器的机器可读描述、命名空间归属与版本信息集中在一处，宿主与工具链不必再去各自的 README 里抓取形状不一致的元数据。第二类是来源核验：包的发布主体与注册条目的归属可以核对，“这个名字确实属于这个组织”第一次变成一个可验证命题而不是社交判断。

它不解决的问题更关键：注册不等于审核。条目存在只说明它被以某种格式收录过，不说明它的权限范围合理、依赖被审过、更新策略可控。任何把“官方注册表里有”直接写成导入理由的流程，都是在把安全决策外包给一个并没有承担这个责任的目录服务。这条边界要写进采购规范，因为它很容易被“来自官方清单”这种语感绕过。

由此可以给出供应链信任边界的真实定义：边界不在协议层，也不在网络层，而在“谁能在什么时候把新代码放进你的进程”。引入一个第三方服务器，你同时引入的是它的依赖树、它的发布习惯、它对下游凭据的处理方式，以及它的维护者流失风险。stdio 形态下这条边界尤其锐利，因为新代码进入进程的路径就是本机配置里那一行启动命令。

与之相邻的分发尝试值得放在同一张地图上：AGNTCY 于 2025-07-29 启动，走的是跨组织的目录与标识路线；A2A 在 2026-03-12 发布 v1.0.0、2026-05-26 发布 v1.0.1，其能力描述与发现机制解决的是“智能体之间”而非“宿主与工具之间”的分发问题。治理侧的一个事实是：2025-12-09 公告的治理主体目前托管 MCP、AGENTS.md 与 goose 三件事。把它们放在同一处，说明这些项目愿意接受统一的变更流程与规范节奏，这本身就是评估生态成熟度时一个比“支持列表长度”更有信息量的信号。

三种能力封装形态的共存

今天要把一段“能力”交给模型使用，实际有三种形态：协议工具（MCP 服务器暴露的 tools）、厂商函数调用（宿主自带模型接口里的工具声明）、技能包（以 Agent Skills 为代表，2025-10-16 发布，规格放在 anthropics/skills 项目的 spec 目录，本文只写到项目层级）。三者不是替代关系，而是三种不同的发布单元。

维度 协议工具 厂商函数调用 技能包
版本管理单元 服务器，一次发布影响所有宿主 随宿主 SDK 与模型接口一起走 一个目录，随内容更新即生效
权限模型 由服务器与授权链路共同决定，可独立鉴权 由宿主的执行器决定，常与宿主同权限 通常继承宿主权限，本身不声明新边界
可移植性 跨宿主复用是设计目标 绑定具体厂商接口形状 取决于宿主是否实现同一目录约定
更新粒度 能力级（一个工具可单独改） 通常要改宿主代码并重发 文件级，最轻
审计可见性 有明确的调用请求与结果 混在宿主日志里 常常只有“被读过”没有“被执行”
协商能力 有版本与能力声明 无协商，靠不兼容报错 无协商

需要说明的是，这里不做优劣排名。三者的差别只在你的约束条件下谁更省心，而约束条件是组织相关的。我建议用四个问题定位：这段能力需要跨宿主复用吗？需要独立的发布周期吗？需要为它单独做授权决策吗？需要留下可回溯的调用记录吗？四个都答“是”，它应该是协议工具；只有前两个是、后两个否，厂商函数调用足够，而且更省；四个都是“否”但内容需要随人评审、随版本沉淀，那更像技能包的活。

一个反复出现的组合陷阱是同一段逻辑在两种形态里各存一份。比如把同一个查询同时实现成服务器工具和宿主内置函数，模型面对两个形状近似但语义不同的入口，行为方差立刻上升。若确实需要并存（迁移期不可避免），至少要做到：两侧描述里显式互相指向、只有一侧允许写操作、并让两侧走同一个下游鉴权主体。

一次调用的完整链路

链路图看起来直观，但工程上真正有用的是把每一跳的日志责任标清楚。下面这张时序图按最常见的远端形态画出，宿主内部的模型循环被单独列成一个参与者，因为多数事故恰好发生在“模型循环与协议客户端之间”。

客户端回宿主 注入路径标识（工具结果还是资源） 未经边界标记的原始正文

关于异步形态多说一句。现行口径允许一次调用先受理、后取结果，这会把上面那条链路从“一跳一次返回”变成“一跳加若干次轮询”，日志关联标识因此必须能跨越时间：受理时的标识要等于后续每次取结果的标识，否则一次长任务在观测面上会碎成一堆无法归因的独立请求，事后排查只能靠时间窗猜。

服务端怎么写才不被上游改版本打穿

协议在两年内走了五个修订：2024-10-07、2024-11-05、2025-03-26、2025-06-18、2025-11-25。每一个都改变过可被依赖的形状。服务端要活下来，靠的不是跟得勤，而是把“跟随上游”这件事结构化。

第一条是版本协商要当成运行时事实，不是编译期常量。握手阶段协商到的版本应该记录在每条日志与每个指标维度上，因为故障最常见形态不是“不支持”，而是同一个部署里不同客户端协商到不同版本、走了不同分支代码。同时要给自己一条纪律：至少同时支持两个修订，一个当前、一个上一个，且新修订的支持以旧修订仍可运行为前提。只支持单一版本的实现在宿主生态里等于把自己绑到最快的宿主发布节奏上。

第二条是能力探测要按声明做，不按版本号推断。“对侧版本不早于某修订，所以它一定支持某能力”是典型的不稳定假设，因为能力从这一族规范起就是声明制的，同一版本完全可以声明不同的能力集合。所有分支判断都应该读声明，读不到就走保守路径。

第三条是把废弃窗口当成排期事件。草案里给出的约 12 个月移除窗口（这是草案，内容可能变动）在工程上的正确读法不是“还有一年可以不动”，而是“从现在起有 12 个月可以在无告警状态下并行支持”。合理的节奏是三段：收到废弃信号的一周内把它变成一条带 owner 与截止日的内部工单，中间用计数器和日志确认还有多少真实流量走旧形态，最后设一个比官方窗口更早的内部停止日期，留出回滚余量。移除窗口一旦被当成“到期再说”，就必然以故障收尾。

第四条是分层。把协议适配层写成薄壳——只做形状转换、版本分派与错误映射；业务能力放在与协议无关的内部接口后面。这样上游改的是壳，不是业务。判断标准很实际：如果新加入一个传输形态需要改动业务代码，分层就是失败的。

    F -->|是| H[内部停止日期前下线旧路径]
    H --> I[保留一个发布周期的回滚开关]

第五条是把契约测试按修订做矩阵。测试对象不是“我们实现了什么”，而是“对每种客户端协商结果，我们的响应形状分别是什么”。矩阵至少覆盖当前修订与上一个修订，草案阶段则额外加一列按草案编写的失败测试，但这一列必须不参与发布判定——草案可以准备，不可以依赖。

还有一类变化容易被忽略：宿主侧模型迭代本身不动协议，但会动上下文预算与提示缓存命中。宿主换到新一代型号（Anthropic 侧可点名的有 Opus 4.6、4.7、4.8 与 Sonnet 4.6，以及 Fable 5、Mythos 5 这一代；具体能力、上下文长度与价目请以官方当期公布为准）时，工具列表前缀的缓存价值会重算，模型对长描述的容忍度也会变。服务端能做的准备是把描述写短、把可选项写成结构而不是散文，这既是给模型看的，也是给缓存看的。

供应链与信任边界

第三方服务器的引入流程，本质是一次小型软件供应链采购。这里只讲防御与流程，不讲攻击手法。

权限审查要前置到引入决策，而不是留到事故复盘。审查清单不必长，但要能判定：这个服务器会写哪些系统、以谁的身份写、能不能只授予只读、它的下游凭据存在哪里、它有没有理由需要长期凭据。判定输出应该是“允许接入 / 降权后接入 / 不接入”三态之一，且三态都要有可追溯依据，否则评审会在两个季度后退化成盖章。

依赖来源钉定是 stdio 形态下最有效的一条。安装方式要固定到可校验的摘要，而不是“跟着 latest 走”；镜像与构建产物的来源要显式声明；升级动作要产生一条与人为改动同级的变更记录。远端形态下这条边界由提供方持有，你无法钉定它的实现，因此对远端服务器要改用另一种约束：把它的行为纳入可观测范围，并对它的权限做更严格的收缩。

更新审批要把“上游发了新版”当成变更事件而不是自动行为。可行的最小流程是：订阅发布通知，内部按周或按迭代窗口集中处理，每次升级前核对能力列表差异与描述差异（描述文本的变化同样是行为变更，因为它直接改变模型的调用倾向），升级后保留一个可快速回退的版本对。禁止的做法是让宿主启动时自动拉取最新版——那等于把发布权交给了外部仓库。

最小权限与出口白名单要在部署层落地：服务器进程只应拿到它这项能力所需的那一点权限，运行账号与宿主账号分离，能访问的外部目标以清单形式给出而不是默认放行。这一层的具体网络策略设计不在本文范围，本文只强调它在 MCP 引入流程里不能被省略：一个只读的工单查询服务器没有任何理由可以访问对象存储的写端点。

最后一件事是维护者风险的可见化。生态里相当一部分服务器由单一维护者支撑，仓库的发布间隔、issue 响应、依赖新鲜度这三项就足以给出一个粗略但有效的健康信号。把它写成采购表里的一栏，比写“社区热度高”要可靠得多。

生态评估口径：一个 server 值不值得引入

评估第三方服务器时，最常见的错误是用“功能覆盖度”这一个维度做决定。下面四个维度是我认为无法互相替代的。

维护活跃度看的是它是否还活着，但“活着”要用可核查的信号表达：最近一次发布的间隔、未关闭问题的处理速度、依赖是否跟得上当期运行时。这里要留意运行时基线本身：Node.js 侧 24 仍在 Active LTS、26 属于 Current 线还不是长期支持选择，Go 侧当期是 1.26，部署到集群上的实现还要对齐 Kubernetes 1.36 的口径。一个把 CI 固定在即将退场运行时上的服务器，其维护状态要比看起来差一档。

权限范围看的是它需要多少才能干活，以及它是否肯说清楚自己要多少。一个只读查询的服务器如果要求写权限或长期凭据，这本身就是评估结论，不需要等到事故来证明。

可观测性看的是出问题时你能不能自己定位。具体信号有三个：调用是否带可传递的关联标识、错误是否有区分度（而不是统一一个内部错误）、慢调用是否能被拆分到“客户端排队、网络、服务器处理、下游访问”四段中的某一段。这三条都缺的服务器，在生产环境里等价于一个黑盒依赖。

退出成本看的是它拿走了什么不可替代的东西。如果它只是转发一组下游 API，替换相对干净；如果它把状态、授权关系或历史结果沉淀在自己的存储里，退出就是一次数据工程。把退出成本写成评估项的最大好处，是它会让“先接一个试试”变成有期限的尝试而不是一段时间后的既成事实。

与相邻主题的划界

本文讨论范围之外但有交叉的几件事，各用一句划清：MCP 的基础概念与最小可运行接入属于协议入门范畴，不在这里重复；模型如何决定调用哪个工具、如何生成参数，是工具调用机制的主题，本文只接住调用发出去之后的部分；消息编码与序列化取舍属于序列化协议对比的讨论，本文不比较 JSON-RPC 与其他编码的优劣；多份工具协议之间的横向对比与标准化走势，由工具协议标准化一文展开；具体服务器怎么写、怎么运维，由工具生态与 MCP Server 实践一文展开；可判定的授权模型、凭据放置与审计留痕的通用设计由 Agent 安全与权限控制一文承担，本文只在协议链路上标注记录字段；网络出口与沙箱隔离的机制设计由 Agent 代码执行沙箱设计一文承担；智能体之间的协商与交接、以及框架选型与编排范式的讨论，与本文的协议生态视角不是同一问题。

小结

MCP 的生态问题可以压缩成三句判断。第一，它的价值不在原语数量，而在把发现、声明与注入三件事放进同一个可协商的会话里，因而能力第一次成为可以被跨宿主复用的发布单元；也正因如此，函数调用 schema 那类静态约定无法替代它。第二，选择 tools、resources 还是 prompts，本质是在选择“这段逻辑归谁演进、按谁鉴权、留不留痕”，把它塞进 prompts 是省了一时的接线，欠下长期的不可观测。第三，真正会打穿实现的是节奏：五个修订走过的两年里，授权要求持续加重，能力改为声明制，异步形态进入现行口径，而草案阶段又给出了约 12 个月的移除窗口——把这些当成带 owner 与截止日的排期事件，而不是到期再看的公告，是唯一稳妥的应对。

对分发与供应链，本文的结论偏保守：注册表仍是预览、接口冻结在 v0.1 且仍在演进，因此它只能作为可发现性与来源核验的手段，不能作为安全审核的依据；治理主体在 2025-12-09 之后同时托管 MCP、AGENTS.md 与 goose，说明规范节奏正在被统一流程约束，这对长期维护预期是正面信号，但任何采用度与规模数字都应该等官方口径稳定后再引用。最后留一句给准备引入服务器的人：先填完那张评估表的证据来源列，再谈接入速度。
