Agent 任务规划与分解

本文属于《Agent 智能体开发》第 28/55 篇
上一篇系列目录下一篇

智能体接到一个复杂任务时，最先要回答的往往不是第一步怎么做，而是这件事该拆成什么。本文只谈三件事：任务分解的粒度与可验证子目标怎么定，计划用什么形式表示，什么时候该触发重规划。它与仓库里的近邻篇目各守边界——《Agent 工作流编排入门》讲编排引擎，《Agent 规划能力提升实践》讲训练与提示侧的能力增强，《Agent 架构设计总览》讲整体架构，《AutoGPT 自主智能体解析》讲历史复盘，本文均不重复。

分解的起点：粒度与可验证子目标

模型给出的任务分解常有两种相反的毛病。一种是过粗：把“调研竞品并写出报告”塞成一个步骤，模型要在同一轮里完成检索、阅读、对比、成文，推理负载超出能力，错了也定位不到错在哪一环。另一种是过细：把“打开浏览器”“点击搜索框”“输入关键词”各写一步，计划退化成一出没有规划含义的脚本。

务实的折中是用两个问题检验粒度。第一问：“它能否依靠现有工具在一轮之内完成？”子任务应当大致对应一次“读入材料、调用工具、产出工件”的闭环；一轮装不下，多半是过粗。第二问：“它有没有非黑即白的成败判据？”判据写不出来的子目标仍然太粗；判据只能写成动作描述（点击某个按钮）而不是结果描述（页面出现某条结果）的，往往又细过了头。

第二问之所以能落地，关键在给子目标配上可验证性。一个可验证的子目标带一份输出契约：数据类任务规定字段结构与取值范围，文档类任务规定必备章节与事实出处，工具调用类任务规定应答形状与失败判据。契约不必复杂，但要能让另一个程序或另一个模型“对表检查”并给出结论，而不是由执行者自己宣布完成。没有契约，后面所有的校验、汇报与重规划都建立在主观印象的流沙上。

还要提醒一句：粒度规则是约束而非紧身衣。团队可以约定“单个子任务不超过 N 个动作”之类的软红线（N 为示意值），但重点不在步调统一，而在逼着分解阶段就思考清楚验收标准。把“怎么算做完”前置到计划里，是分解阶段最有价值的产出。

依赖图与关键路径

拆完得到一堆子任务，把它们之间的依赖组织成图，计划才开始变得可调度。以子任务为节点、以“必须先完成 X 才能开始 Y”为边，得到一张有向图。这张图最好是无环的——即一个 DAG：无环意味着至少存在一个可行的执行顺序，且互不依赖的任务可以并行派发。一旦成环，比如 A 等 B 的数据、B 又等 A 的结论，通常是分解本身出了问题，最常见的解法是拆开其中一个节点，或抽出一个“先约定接口格式”的中间步。

以“从三个数据源生成一份周报并送审”为例：

flowchart TD
    A[采集三源原始数据] --> B[解析与清洗]
    A --> C[抽取关键指标]
    B --> D[横向对比分析]
    C --> D
    D --> E[撰写周报草稿]
    E --> F[审阅与发布]

图的价值在于看得见关键路径——DAG 中最长的那条依赖链。上例里“采集—解析—对比—草稿—审阅”构成一条关键路径，它的长度决定了整个任务在并行条件下的耗时下限。由此有三个实用结论。其一，优化应该优先投向关键路径上的节点，加速旁路任务基本不会缩短全局。其二，关键路径是动态的：某条支路一旦遭遇工具失败或返工，原来的非关键路径可能升级成新关键路径，这本身就是重规划的一个信号。其三，非关键节点上的余量是天然的缓冲，可以用来吸收重试与校验的成本。

至于消费这张图的执行器如何实现，那是编排引擎的地盘，本文不展开。我们只强调一点：无论计划最终用什么形式表示，依赖关系必须显式写出来，不能指望模型从步骤的排列顺序里自行猜测。

计划表示形式对比：线性计划、DAG、状态机

同一个分解结果，可以装进三种差别很大的容器，取舍逻辑各不相同。

线性计划就是一张有序步骤清单。它最大的优点是生成与核对都便宜：模型输出它的最在行，人复查它的最快，重规划时把失败点之后的部分整段截掉重写即可。缺点同样明显：并行关系表达不出来，依赖只能隐式地藏在先后顺序里，一旦任务出现分支汇合或条件跳转，清单就开始别扭。它适合严格顺序的小任务，比如“查资料—汇总—写摘要”这类一条链走到底的工作。

DAG 把依赖显式化为边，于是并行派发、局部修复都成了自然操作：某个子任务失败，只需要重做它的下游子树，上游工件照样复用。代价是模型一次生成一张正确 DAG 比生成清单难得多，漏边、多边、把顺序当依赖都是常见病，需要额外的图校验；而且循环语义——重试、回退、等待人工确认——在纯 DAG 上很难看地表达。它适合多源数据、有扇出扇合的中型以上任务。

状态机用“状态、转移条件、副作用”三元组来承载计划。它的强项是执行语义：超时、重试、补偿、人工介入都有明确的挂靠点，全程可审计、可恢复，崩了重启后从当前状态继续即可。弱点是建模门槛：你得在计划前大致枚举清楚状态集合，而探索型任务恰恰在“接下来可能进入什么局面”上说不准，硬套状态机会遇到状态爆炸。它更适合阶段清晰且会反复跑同类流程的任务，例如订单处理、文档审批。

生态里这些形式都不缺拥趸：LangGraph 1.0 已发布，图与状态两种载体都能落地；LangChain 1.x 主线与仍在 0.x 迭代的 OpenAI Agents SDK 偏清单与交接；CrewAI、AutoGen、Eino 各有自己的计划载体。选型细则属于编排篇，此处按下不表。

重规划的触发条件

重规划不是重启按钮。触发条件应当事先写进计划，否则智能体只能在两种失败模式之间摇摆：要么抱着坏死的路径一条道走到黑，要么一有风吹草动就推翻重来。至少要覆盖三类触发。

其一是环境变化：世界状态与计划假设不符。目标目录结构变了、上游接口的应答与契约对不上、可用工具清单或权限边界被调整——MCP 治理归属的近期公告就属于此类，工具的发现与授权方式变化后，“这个工具随时可调”的假设可能一夜失效。判断标准不是“事情变没变”，而是变化是否落在某个子目标的输出契约之内：契约兜得住，继续执行；兜不住，进入重规划。

其二是工具失败。要把瞬时故障与语义故障分开：网络抖动、限流这类瞬时问题交给重试，重试次数超过团队约定的示例阈值才升级处理；参数不匹配、能力不存在这类语义问题则不能靠蛮力重试，得先做局部修复，修复不了再重规划。最常见的浪费是拿同一个错误参数重试一整轮。

其三是预算越界：轮次、时间或费用触及预先设定的预算线（具体数额为示意值，由团队按任务约定）。越界时哪怕看起来“快做完了”，也应当停下来重新评估，因为沉没成本会诱导执行器不断追加投入，把小超支滚成大事故。

最后是重规划的粒度：变更发生在非关键路径、不动已完成工件的契约，做局部修复——换子树、加节点即可；目标本身不再可达、或计划赖以成立的假设塌了，才做完整重建。重建之后记得重新传播依赖图，并把旧工件标记为失效，否则新旧结论会混在同一份上下文里继续误导下游。

分解过细的代价：上下文膨胀与错误累积

“拆得越细越安全”是规划环节流传最广的迷思。细粒度确实让单步更容易、失败更容易定位，但它有两笔常被忽略的账。

第一笔是上下文膨胀。每执行一个子任务，都要把任务背景、约定规范、上游工件重新注入模型的视野；步数越多，这份“随附材料”就被复制得越多次，加上计划本身在每一步的重复出现，总上下文的膨胀速度会明显快于步数本身的增长。更隐蔽的问题是注意力稀释：当每一步都在阅读大量与自己无关的历史，模型对真正关键约束的遵守率会悄悄下滑。

第二笔是错误累积。上游子结果的瑕疵如果没有在验收时抓住，就会被下游当作既定事实继续加工，一路放大。分解越细，交接次数越多，瑕疵穿行的通道就越多；等最终产物暴露出错误时，根源早已埋进最前几步，回溯成本极高。这也是为什么契约必须挂在每个子目标上——累积的不是错误本身，而是未被拦截的错误。

还有一个容易踩的坑：把同一轮推理的天然闭环拦腰切断。“读完这份材料”和“据此写出对比段落”，本来是一个理解与表达相互校准的过程，硬拆成两个子任务后，第二步只能对着第一步的压缩摘要干活，洞察在交接处流失。判断标准依然是那两问：一轮完得成吗？有独立判据吗？两个都勉强的一步，不值得单独立项。

取舍对照表

规划没有标准答案，只有对着场景做的权衡。下表把本文三条主线上的关键取舍收拢在一起，阈值均为团队约定示例。

决策点 偏左的选择 偏右的选择 判断依据
分解粒度 粗：步少、单步重 细：步多、单步轻 单轮工具能力够不够；验收契约写不写得出来；上下文预算撑不撑得起交接次数
计划表示 线性清单：易生成易核对 DAG 或状态机：并行、循环可表达 有无扇出扇合与重试回退；状态集合能否事先枚举；任务是否探索型
重规划触发 保守：先重试后修复 敏感：契约一破即重排 失败是瞬时还是语义；变化是否落在契约之内；预算线离得多近
修复粒度 局部：换子树、加节点 完整：重建并重传播依赖 假设基础塌没塌；已完成工件是否仍然有效

小结

回到开头那三个问题。分解粒度靠“一轮完得成”与“判据写得实”两问来定，落到每个子目标头上的是一份能被别人对表检查的输出契约。表示形式上，清单、DAG、状态机各有主场，共同的底线是依赖必须显式、关键路径要看得见。重规划则是触发条件的问题：环境变化超出契约、工具语义性失败、预算越界，三类信号事先写进计划，修复才谈得上分层。拆得太细要付上下文膨胀与错误累积的利息，这笔账在计划阶段就该估进去。计划是假设，执行是检验——把“何时承认假设错了”设计进计划本身，才是分解工作的最后一块拼图。
