Agent 与 RPA 的结合

本文属于《Agent 智能体开发》第 43/55 篇
上一篇系列目录下一篇

流程机器人（RPA）在企业里已经跑了很多年，它擅长的是把确定性的步骤按顺序复述一遍；大模型智能体擅长的恰好相反，是在信息不全、页面会变、字段叫法不统一的时候把流程继续推下去。本文想讨论的不是谁取代谁，而是这两类东西怎么在同一条流程里各司其职：哪些步骤必须交给录制式脚本，哪些分支才值得交给模型，以及混合之后要补上哪些原本不需要补的工程课。我们会沿着分工原则、编排形态、幂等与补偿、人工介入、断点续跑、可观测与合规的顺序展开，最后给出一张三者对照表和一组“不值得引入模型”的判断条件。

一、分工原则：把确定性交给脚本，把例外交给模型

混合流程最容易犯的错误，是把模型当成一个“更聪明的点击器”，让它在本来有固定答案的位置上重新发明答案；同样常见的错误，是把智能体当成兜底，让它去补齐脚本本该写清楚的规则。本文只用一条判断标准：这一步的输出能否被预先枚举。能枚举的交给录制式脚本，不能枚举的才值得交给模型。

这里“预先枚举”有两层。一是输入可枚举：页面元素、字段名称、按钮位置在版本之间稳定，脚本就比模型可靠，因为脚本出错会立刻暴露，模型出错往往看起来像成功。二是结果可枚举：结论只有“通过”和“驳回”两种时，规则加少量分支就够，模型只会把一个确定问题变成概率问题。

反过来，有三类步骤确实站在枚举之外。非结构化输入，自由文本的备注、扫描件、客户随手写下的诉求，要归一化成字段才能进入流程；语义对齐，上游叫“发票号码”、下游叫“票据编号”、中间系统叫 invoice id，映射关系写在文档里而不是代码里；例外分支，按规则应当拒绝、但业务上确实存在合理例外的长尾情况。

失败语义也要分开定义：脚本的失败是异常，应当立即中断并告警，因为环境变了；模型的失败是“没拿到可用答案”，应当降级为人工处理，因为不确定性超出了可接受范围。把两类失败混在同一层 try 里，是混合流程最早出现的技术债。

二、两种编排形态：谁掌握控制流

混合流程的分歧点只有一个：控制流握在谁手里。握在机器人手里，就是 RPA 调用智能体服务；握在智能体手里，就是智能体调用 RPA 动作。两种形态的适用边界差别很大，混用而不加说明是事故的主要来源。

形态甲适合“流程已经存在，只是某个环节卡住”的场景。主干仍是确定性的：取任务、登录、按顺序填单、提交。智能体只挂在例外分支上，以同步服务的方式被调用，输入是一段原始材料和明确的输出契约，返回结构化字段而不是操作指令。好处是控制流可预测：智能体的权限被限制在“回答”，它不能推动流程往前走。

形态乙适合“流程本身没有被完整定义过”的场景。规划器负责拆解任务、决定下一步、判断是否结束，RPA 的动作被封装成一组注册过的工具，每个工具都带前置条件、后置校验和超时。自由度更高，代价是所有安全属性都要重新实现一遍：谁允许它打开这个页面、哪个动作会真的写数据、走到第几步需要停下来。

flowchart TD
    S[流程入口] --> D{谁掌握控制流}
    D -->|机器人持有| R1[录制式步骤执行]
    D -->|智能体持有| G1[规划器拆解任务]
    R1 --> E1{命中例外分支}
    E1 -->|是| A1[同步调用智能体服务]
    A1 --> K1[结构化结果回写]
    K1 --> R1
    E1 -->|否| W1[提交并落库]
    G1 --> A2[调用注册过的 RPA 动作]
    A2 --> V1{校验动作前置条件}
    V1 -->|通过| W1
    V1 -->|不通过| G1

一个可操作的判断方式：把形态乙当实验，把形态甲当生产。一条流程被反复跑通、例外分支收敛之后，就该把稳定部分固化回脚本，只留下仍然收敛不了的那一小块。混合流程的正确演进方向是“确定性占比逐步上升”，而不是相反。至于智能体具体怎么驱动浏览器界面、怎么通过协议挂载外部工具，属于另一条轴上的问题，本文不展开。

三、幂等与补偿：重复提交、半完成与对账

流程机器人天然生活在一个“至少一次”的世界里：机器人重启、任务被重新领取、脚本提交后超时但对方系统其实已经收到。传统 RPA 用“整个流程重跑一遍”来对付这些情况，前提是每一步都可重放。混合流程里多了一个会思考的环节，重放就不再免费——模型每次被调用都可能给出略有不同的答案，同一次业务意图于是留下两条路径。

幂等设计因此要先回答一个问题：一次业务意图的唯一标识是什么。本文推荐用“业务主键加流程定义版本”派生幂等键，而不是用任务 ID，因为任务 ID 会因为重新领取而变化。幂等键一旦确立，所有写入都必须带上它，回放时先看状态表再决定是否执行，而不是先看页面。

半完成状态是第二件事。步骤最危险的时刻不是失败，而是“已经下发但没拿到回执”：既不能盲目重试，可能造成重复提交；也不能直接放弃，业务侧已经留下一半痕迹。正确做法是标记为待对账，交给独立的对账任务去查对方系统的结果视图，查到就补写回执，确认查不到才走补偿。补偿动作本身也要幂等，撤销接口必须能安全地重复调用。

骨架里有三个细节值得强调。第一，模型只出现在 step.decide 这个“读”的位置，真正写数据的动作都由确定性步骤执行，这保证了回放时写入序列不变。第二，UNKNOWN 分支直接返回，把重试的决策权交给外层调度。第三，每次推进都连同输入、输出与执行人一起落库，它既是断点续跑的基础，也是留痕的起点。

四、审批链与人工介入点

人工介入不是一个兜底按钮，而是一个需要被设计的位置，它至少区分三种语义：补充信息，模型缺一个只有业务侧才知道的口径，人填一下就能继续；复核决策，模型给出了结论，但结论影响资金、库存或对外承诺，必须由有权限的人确认；接管执行，环境异常，人绕过自动化直接办完，流程记录为人工完成并回填凭证。三者界面相似，权限、留痕和统计口径却完全不同，混在一起会让自动化程度这个指标失去意义。

sequenceDiagram
    participant F as 流程编排器
    participant A as 智能体服务
    participant W as 审批工作台
    participant R as RPA 机器人
    F->>A: 请求例外分支判断
    A-->>F: 返回建议与依据
    F->>W: 挂起任务并推送待办
    W-->>F: 复核人给出批准或驳回
    F->>R: 批准后下发提交动作
    R-->>F: 回执与凭证号

审批链最容易出的问题，是模型的建议在流转中被当成“已经决定了”。如果界面只留下最终结论，时间一长就没人记得结论是复核人给的还是模型给的。正确做法是把建议、依据、复核意见分成三个字段保存，并要求复核意见在建议被采纳时也必须填写，哪怕内容只是“同意建议”。

介入阈值要显式配置，而且要写在流程定义里而不是提示词里。例如“金额超过某个阈值必须双人复核”“建议依据不足时自动转人工”“同一主体在一个周期内被反复例外放行就升级审批”（以上阈值均为团队约定示例，本文不给具体数值）。这些条件用规则表达比用自然语言更安全，因为它们需要被审计。

五、断点续跑与状态持久化

机器人重启、系统维护窗口、审批隔夜才回来，这三件事都要求流程能从中间某一步继续，而不是从头再走。传统 RPA 对断点的常见处理就是重跑整个流程，在纯幂等流程里勉强够用，一旦有模型参与就不成立——重跑意味着重新问一次模型，答案可能不同，流程会走向另一个分支。

可恢复的执行态至少要存下四样东西：流程游标，当前走到哪一步，用步骤名而不是序号记录，避免流程改版后错位；已确认事实，模型输出里被采纳的那部分，它要作为后续步骤的输入被固定下来；外部回执，对方系统返回的凭证号，它是判断做没做成的唯一凭据；等待原因，任务为什么停在这里，是等审批、等对账还是等重试窗口。四样合起来才是一个状态，少任何一样，续跑都只能靠猜。

stateDiagram-v2
    [*] --> Accepted
    Accepted: 已受理
    Accepted --> Running: 领取任务
    Running --> Manual: 命中人工介入点
    Manual --> Running: 复核完成
    Running --> Suspected: 已下发但无回执
    Suspected --> Running: 对账补齐回执
    Suspected --> Compensating: 对账确认未生效
    Compensating --> RolledBack: 补偿完成
    Running --> Done: 全部步骤通过
    Done --> [*]
    RolledBack --> [*]

存储位置要与机器人实例无关：机器人可以多台部署、随时替换，任务被谁领取不应影响它能否继续，把状态写在本地盘上等于把流程绑死在一台机器上。框架层面，LangGraph 与 LangChain 的 1.x（1.0 已发布）都把带检查点的执行态存档放在核心位置；调度层面按 Kubernetes 1.35 口径（2025-12-17 发布，2026-01-17 起用）规划作业形态，也适合承载这种长时间等待、由事件唤醒的流程。恢复时还要区分可重放步骤与不可重放步骤：前者按游标重跑，后者一律先对账再决定。

六、可观测与合规留痕

混合流程的可观测性比纯脚本多一个维度：不仅要记录做了什么，还要记录基于什么判断。本文建议守住三条主线。trace 贯穿，一次业务意图从机器人、智能体服务到审批工作台共用同一标识，否则排障时两边日志无法对齐；输入快照，模型被调用时喂进去的原文要留存，只存提示词的哈希并不能举证结论从何而来，而快照本身可能含敏感信息，必须同时做脱敏与访问控制；决策落点，哪个分支被走过、哪条建议被采纳或被推翻，都要能被查出来。

留痕的边界口径必须提前声明：自动化只在获得授权的系统内操作，登录身份、权限范围、可访问的接口都来自书面授权；遇到访问频率或身份上的限制时停下来转人工，不做任何绕过。合规部门关心的通常不是模型来自哪家，而是这几条能不能举证。

数据分级也别偷懒：原文快照属敏感级，回执与结论属业务记录级，提示词模板属可公开的内部资产级。三类数据放进同一张表、用同一个权限读取，是合规评审阶段最常见的返工点。

七、什么场景不值得引入模型

“要不要上智能体”这个问题，多数团队是在上线之后才第一次认真回答，本文把它提前成五个可以当场判断的条件。

  • 输入已经结构化，缺的只是一份字段映射表——那就把映射表写进代码，不要每次运行都去问模型。
  • 结论空间封闭，规则能写成一棵判断树或者一张决策表——规则引擎的确定性远高于模型，且它的输出天生可审计。
  • 动作不可回滚，一旦提交就构成对外承诺——这类步骤上模型只允许出现在“读”的位置，写权限必须留给确定性步骤或者有权限的人。
  • 对方系统本就不允许程序访问——此时正确的答案是取得授权或者转人工，而不是让模型去模仿人的操作。
  • 量小且变动频繁，一年改几次的流程——为它建幂等键、对账任务和留痕体系的固定成本，通常比模型带来的好处更贵（此处只做定性判断，不引用任何效率数字）。

一句话判据：如果引入模型之后你需要新建的东西（幂等键、对账、审批点、执行态存档、留痕体系）比它替掉的确定性规则还多，那么这条流程就不该引入模型。至于智能体进入企业后的组织与责任安排，以及工具调用本身的底层机制，各自已有专文讨论，本文只停在流程资产这一层。

八、三条路线的对照

把前面的讨论收拢成一张表，供选型时对照参考。

维度 传统 RPA 大模型智能体 混合流程
控制流归属 录制时确定，运行时只走预设分支 规划器逐步决定下一步 脚本持主干，模型只填例外分支
输入适应性 依赖稳定页面与固定字段 容忍非结构化材料与字段漂移 结构化段走脚本，漂移段走模型
失败语义 异常即中断并告警 无可用答案即降级转人工 两类失败分开处理
幂等来源 整条流程可重放 需要外部幂等键与回执 业务主键派生幂等键，加对账兜底
变更成本 页面改版即返工 提示词与契约改版需回归 仅例外分支需要回归
留痕粒度 操作日志与界面截图 输入快照与决策落点 三者并存，共用同一标识
适用场景 高频重复且规则封闭 长尾判断与语义对齐 主干确定、例外长尾

小结

回到那条判断标准：能枚举的交给脚本，不能枚举的才交给模型；而一旦把某一步交给模型，幂等键、对账任务、审批介入点、执行态存档和留痕体系这五件事就从“可选”变成“必须”。存量机器人资产不会因为智能体的出现而贬值，它反而提供了混合流程最稀缺的东西——一条已经跑通、并且知道哪里会坏的主干。真正需要谨慎的，是为了暂时的灵活性把主干拆掉。
