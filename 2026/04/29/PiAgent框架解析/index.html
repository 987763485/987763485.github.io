Pi Agent 框架解析

本文属于《Agent 智能体开发》第 16/55 篇
上一篇系列目录下一篇

本文的研究对象是 Pi Agent 框架，一个由 Mario Zechner 开发的最小可扩展 agent harness。写作依据仅限公开仓库 earendil-works/pi（曾用名 badlogic/pi-mono）与文档站 pi.dev 可见的内容，凡这些材料没有直接证实的结构性判断，都标注为”基于公开信息的推断”。截至本文日期，Pi 仍处于 0.x 阶段，接口仍在变动，所以正文不写具体小版本号，也不给需要实测才能确认的行为细节。

研究对象与口径

Pi 的自我定位是一个 agent harness：不是把模型、界面、策略打包完毕的成品，而是把模型调用循环包出来的最小运行时。仓库于 2025 年 8 月上旬公开，到本文写作时经历了约八个多月的公开迭代，版本仍在 0.x 区间。口径决定了后文每一个判断该怎么读，所以放在最前。

第一层是事实。仓库位置、作者、文档站、公开起始时间、0.x 阶段且接口仍在动，这五点公开仓库与文档可见，可以作为确证事实使用。第二层是推断。正文凡出现”核心循环大致是””扩展点分成三类””配置层面会表达”这类说法，除非另有注明，都是基于公开仓库的目录树、README、文档与测试文件做的归纳，属于基于公开信息的推断，本文作者没有读过任何未公开实现。第三层是纪律。正文不复述未公开的 API 签名与私有模块名，不引用未核实的字段名；示例需要具体键名时一律用占位符，并声明其不代表 Pi 的真实 schema。这也是写 0.x 阶段项目的一种方法：版本离 1.0 越远，对结构的断言越要留出处。

“最小”是什么意思

Pi 的”最小”不是功能少，而是实现与概念之间的路径最短。这类项目的本体是一个循环：读取输入、组装上下文、请求模型、执行工具、把结果并回、判定终止，然后再来一轮；循环之外的抽象，大致只剩”工具””技能””宿主”三类扩展点。没有编排 DSL，没有多层运行时，也没有把每步都包成服务的冲动——这同样是基于公开信息的推断，但目录树与文档的说法彼此印证。

为什么这类项目适合想读懂实现的人。主流 agent 框架习惯把配置、编排、插件机制堆成好几层间接，读者的时间大多花在把文档概念翻译成框架术语上；最小 harness 相反，阅读面小，概念与代码几乎一一对应，读完源码后有望凭记忆复述整个循环。”能复述”是检验是否真懂一个系统的土办法，也只有小项目给得起这种体验。代价同样明确：脚手架不自带，调度、记忆、评估、可观测性要么用不上，要么自建——后文的定位与选型讨论都由这一点派生。

核心循环拆解

先把正文从公开代码与文档里归纳出的骨架拆成六步，注意这是基于公开信息的推断。第一步读取输入：从宿主界面接收用户消息或指令，宿主可以是终端，也可以是程序化调用方。第二步组装上下文：把系统提示词、会话历史、已启用技能的内容拼成一次模型请求，这一步是整个 harness 里唯一称得上复杂的地方。第三步请求模型：用哪个模型由配置决定，文档示例里出现的模型名——比如近期常见的 Claude Opus 4.6 或 Sonnet 4.6——都只是模型字段的取值，本文不讨论价格与参数。第四步执行工具：若响应里带工具调用，循环解析出调用意图并在本地执行；是否叠加权限确认与超时控制由执行层决定，公开仓库只能看出机制存在，具体行为留待实测。第五步把结果并回上下文：每个工具调用的结果以消息形式追加进会话，成为下一轮请求的材料。第六步判定终止：模型返回纯文本答复且宿主不再继续时，本轮循环结束；仍有待处理的调用则回到第二步。

flowchart TD
    A[宿主读取输入] --> B[组装上下文]
    B --> C[请求模型]
    C --> D{含工具调用?}
    D -- 是 --> E[执行工具]
    E --> F[结果并回上下文]
    F --> C
    D -- 否 --> G{判定终止?}
    G -- 否 --> A
    G -- 是 --> H[本轮结束]

这张图想说明的是：全系统只有一个循环，复杂度全部集中在组装上下文这一步；最小 harness 的调试体验正由此而来——出问题时沿一条时间线看上下文怎么被拼出来的即可。另外，循环里没有独立的”规划器”组件，规划被交还给模型与提示词，harness 只负责跑、不负责想，这是 harness 一词在语义上的落点。

扩展点三件套

公开文档可见的扩展点，按被扩展的对象可以分成三类：工具、技能、传输与宿主界面。先划一条界：Claude Code 一类产品的公开结构与扩展点全景，1023《Claude Code 源码架构解析》已有专文，本文只谈 Pi 自己的分类，不复述那套细节。

工具扩展”模型能做什么”。每个工具是一份声明加一个执行函数：声明让模型知道何时调用，执行函数在本地把参数变成副作用。边界在于工具只管进参与出结果，编排属于循环；工具 schema 的设计与执行细节见 950《Agent 工具调用与函数执行》，本文不重复。

技能扩展”模型应该怎么做”。Pi 支持 2025 年 10 月公开的技能扩展格式，把指令、脚本与资源打包成可发现的能力单元。技能与工具的分界是声明式与可执行之别：技能不新增能力，只改变行为方式。外部协议这边，MCP 在 2025-11-25 修订后异步 Tasks 与 Extensions 已可用，但 Registry 仍在预览；该协议族已捐给 Linux Foundation 旗下的 Agentic AI Foundation，它同时托管 MCP、AGENTS.md 与 goose。

传输与宿主界面扩展”谁在用这个循环、从哪儿用”。把循环与具体界面解耦，意味着同一套内核可以接终端、接编辑器、接自家产品的入口。这一类的边界是：宿主的交互逻辑不进循环，循环也不感知自己面对的是哪种界面——此句同样是推断。三件套的分法透露了一个取舍：扩展只沿”能力、行为、入口”三个方向开，其余一律不做，抽象层数因此压得住。

配置驱动

配置层面要解决的事情，本文推断大致分三类。第一类是模型与凭据：用哪个模型、从哪个服务取、密钥从哪里来。第二类是开关：工具是否自动执行、技能是否允许加载。第三类是预算与限制：工具调用最多多少轮、上下文留多大余量、单次请求超时多久。这些内容以什么键名表达，应以使用时所在版本自带的 schema 为准，本文不列举未经核实的字段名。

与同类产品的定位差别

把 Pi 与 Claude Code 一类编码智能体产品放在一起比较，差别可以收成一句：前者是拿来即用的产品，模型、界面、工具集与安全策略都替你定完了；后者是给你改的 harness，这些东西以配置与代码的形式留给使用者本人。再划一句界：编码智能体的通用实现要点，1055《Coding Agent 设计与实现》是专文，本文只谈定位，不复述实现清单。

定位不同，讨论的对象就不同。谈前者时聊的是体验边界与策略默认值——它把哪些事情替你做好了、又在哪些事情上不让你碰；谈后者时聊的是实现是否可读、接口是否可改、变更成本归谁承担。要把循环接进自己的评测环境或产品形态，harness 路线让你不必跟产品的硬边界博弈；只想当下把任务做完，现成产品的总成本通常更低。这两句不构成排名，因为它们回答的本来就不是同一个问题。

“接口仍在动”的工程含义

0.x 不是心理安慰，而是一条工程约束：1.0 之前项目通常不承诺向后兼容，本文日期时的 Pi 正处于这一阶段。它落到日常开发上是三件事。锁版本：把依赖连同其传递依赖一起锁进 lockfile，并在变更记录里同时记下版本号与提交哈希，让”当时跑的是哪一份代码”可以被精确回答；升级走小步，一次只动一个组件。跟随上游的成本：文档往往落后于代码，网上示例可能已经跑不起来，此时以仓库内的测试与自带示例为准，文档只用来说明作者意图。迁移与回退：升级前，把已有的脚本化任务在新版本上先跑一遍并对比输出；升级后保留旧 lockfile，确保随时能退回上一个已知良好的状态。回退的本质是精确复现过去的环境，lockfile 与依赖镜像锁定是最省事的两个手段。

另一条经验是把变化隔离开：给 harness 外面包一层自己的薄接口，只让这层代码直接触碰上游 API。上游接口再动，需要修补的面就只有这一层，而不是散落在业务里的大小调用。

什么时候选它、什么时候不选

框架间的评估维度与对应的验证动作，1020《Agent 框架对比与选型》与 994《CrewAI 多智能体框架实战》已有专文，”为什么不给框架排名”在那两篇里也讲过了，本文不复述，只列与这个项目直接相关的判断维度。先看适合选它的情形：你想端到端读懂并复述智能体循环，学习收益优先于交付收益；你要把同一个循环接进自己的产品形态、评测环境或受限网络，接口可改比功能齐全更重要；你希望提示词、工具与技能的策略完全在自己版本控制之下；团队能承受跟随上游的成本。再看适合绕开它的情形：你需要沙箱、权限体系、企业审计这类现成且要人维护的实现；你指望开箱即用的插件生态；你的业务规模要求可依赖的稳定 API 契约。两组情形背后是同一条轴：要现成能力，还是要可控可改——两者都想要时，先想清楚哪个能自己补，现成能力补起来慢，可控性丢了补不回来。

自学习与验证方法

本文全部判断只建立在公开代码与文档之上，这一节交代怎么在同样条件下验证结构假设。入口文件读四类：包的配置文件与入口声明，看出可执行形态与依赖方向；README 与文档源文件，看出作者的概念解释与示例；配置文件指向的循环与命令行入口模块，验证核心循环六步的拆法是否成立；测试文件，它最可信，因为断言与代码同仓、一起演进。命令也跑四类：按文档装依赖后跑测试，看哪些断言在当前版本是绿的；用最小配置启动命令行，观察启动行为；跑一条固定指令，记录模型调用与工具调用的序列，再换版本对比；在仓库内检索凭据相关关键词，确认示例没有把密钥写进明文。方法上的要点是：结构假设要用行为验证，而不是用文档验证——把两个版本背靠背跑同一条指令，看输出在哪一步分叉，比从说明文字里猜可靠得多。本文未能这样验证的地方，都已标注为推断。

小结

最后用一张表把全文的设计取舍收拢，表中判断均为基于公开信息的归纳：

设计取舍维度 Pi 的选择 得到的收益 付出的代价
抽象层数 只保留循环与三类扩展点 可读、可复述、可修改 脚手架需使用者自备
接口稳定 0.x 阶段不承诺兼容 迭代快、包袱小 升级需锁定与人工迁移
模型接入 配置指定模型，不绑定厂商 换模型成本低 各家兼容性差异自己消化
界面形态 宿主与循环解耦 可接任意入口 没有现成产品体验
凭据与安全 交给外部环境与密钥管理 仓库不落明文密钥 配置错误风险在使用者

Pi 的价值不在于功能多少，而在于把一个智能体循环做得可读、可改、可验证；0.x 的阶段让这份清晰要配上跟随上游的税负。口径不变，判断就留得出余地：等它的接口稳定下来，本文里标了推断的句子，值得逐条再验一遍。
