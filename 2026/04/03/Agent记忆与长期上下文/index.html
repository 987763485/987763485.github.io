Agent 记忆与长期上下文

本文属于《Agent 智能体开发》第 22/55 篇
上一篇系列目录下一篇

Agent 落到真实业务里后，最被低估的一层是记忆。本文不复述检索算法的实现细节，只把上下文窗口、会话记忆、长期记忆这三件事的边界划清楚，再逐条给出写入、遗忘、渐进披露与隐私留存的策略。适合正给智能体加长期记忆的工程同学，读完能拿到一套可落地的判断标准和一张分类表。

先把三件事分清

工程上最容易犯的错，是把“上下文窗口”“会话记忆”“长期记忆”当成同一个东西的三种叫法。它们的载体、生命周期和失效方式完全不同，必须分开对待。

上下文窗口的载体是模型一次调用看到的 token 序列，混着系统指令、工具描述、历史消息、本轮检索片段和留给输出的预算。它的生命周期只有一次调用，返回即蒸发，是一种易失的工作记忆；失效方式是溢出与位置效应——超预算的被截断丢弃，就算没被丢弃，落在窗口中间的内容也更易被模型忽略。窗口本身能开多大是模型侧的事，与本文的记忆边界无关。

会话记忆的载体是编排框架维护的线程或会话状态。LangGraph 1.x 主线用检查点持久化线程状态，OpenAI Agents SDK 的 0.x 用会话对象承载多轮，LangChain 1.2 在其上再封装一层，CrewAI、AutoGen、Eino 也各有会话或运行态概念，此处只提定位、不比版本。它的生命周期是一个会话线程，随会话结束、换设备、换租户而取不到；失效方式是会话过期与跨端不可见——上周在手机上聊的那半截，网页端并不天然接得上。

长期记忆的载体是独立于任何一次会话的外部存储：关系库、文档库，或 pgvector、Milvus、Qdrant、FAISS、HNSWlib 这类向量与近邻索引项目，只写定位、不比版本。它跨会话、跨进程存在，生命周期以月计；失效方式是 TTL 到期、被显式删除或被一条更新过的记录覆盖。

之所以要分开，是因为三者的读写时机、成本、可见范围和合规义务都不一样。把长期记忆直接灌进上下文当会话记忆用，等于把“持久保存”和“此刻在场”混为一谈：前者管存得下、找得到，后者管这一次调用里模型能看到什么。记忆怎么分层，另有一篇《Agent 记忆系统设计》专门讲，本文只管这三层各自的边界与策略。

“记住一切”为什么是负资产

很多团队做记忆的第一冲动是“能存就存、多多益善”，这其实是负资产，四条机制都能说明。

一是噪声召回。写进去的条目越多，被相似度顶上来、却与当前任务无关的也越多，它们挤占上下文、稀释了有用信息的比重，模型反而更容易被带偏。

二是冲突累积。事实会变，新写入不跟历史对齐时，同一个属性会留下多条互相矛盾的记忆，组装时不知该信哪条，行为变得不可预测，而且这类矛盾多半无声累积，出问题才被发现。

三是成本上升。上下文越长，每次调用都要为这些 token 付费、把延迟拉长，收益却不随条数线性增长，存到某个点后边际价值趋近于零、成本却一路涨。

四是隐私与合规风险。留存越多越久，一旦越权访问或被要求响应用户删除，暴露面和整改成本就越大；“记住一切”把风险当成了默认值，而合规要求把风险做成需要论证的例外。

合起来，记忆的价值不在记了多少，而在正确的时机只把正确的一小块放到模型眼前。

写入策略的边界

不是每次交互都值得留下记忆。本文把“值得写”与“必须不写”都做成可判定的条件，而不是凭感觉决定。

值得写有四条判据。稳定性：这条信息在未来多次任务里仍成立，而非一时情境，临时变量和一次性调试输出不该进长期记忆。复用度：能被后续会话或别的任务再次用到，只服务于当下一句话的内容留在窗口里就够，不必落库。用户显式确认：用户明说“记住这个偏好”这类指令最可靠，未经确认的推测只进待确认状态，不直接写成事实。可验证来源：来自用户输入、权威文档或系统内的结构化记录，能追溯出处，模型自己推断的结论在没有外部佐证前不当作用户事实存。

必须不写同样有硬边界。凭据类：密码、令牌、API Key、Cookie、私钥一律不落记忆，它们属于密钥管理系统而非记忆。健康与身份类敏感信息：除非任务明确需要且用户授权，否则不主动记录，更不长期明文留存。未授权的第三方信息：从不可信外部内容里读到的、关于某个人的信息，不能写进与某用户绑定的长期记忆。

一句话：写入判据回答“能不能存”，敏感边界回答“绝不能存什么”，两者都要在任何检索层面优化之前先定下来。

遗忘与过期

记忆不仅要会记，更要会忘。没有遗忘机制的记忆库，几个月后就是一堆没人敢动的考古现场。本文给四种遗忘手段，并澄清一个常被误解的存储事实。

TTL 给不同类别的记忆设不同存活时长，临时上下文很短、用户长期偏好很长，具体数值是团队约定示例，取决于业务与合规要求，到期后不再参与召回。重要性衰减让每条记忆带一个随时间下滑的分量，长期没被再次确认或使用的条目分数走低，最终落到召回阈值之下，这是“用得少就淡出”而非删除。被引用次数是重要性的反向信号，被后续任务真正用到的次数越少，越该优先被压缩或下架。显式删除来自用户的“忘记这条”指令，或系统检测到某条与最新事实矛盾且判定作废时的主动下架。

过期不等于删除，这个存储事实要写清楚：一条记忆停止参与召回，不代表它从物理存储上消失了。很多实现里，过期只是给记录打上“不再检索”的墓碑标记，也就是软删除，底层数据行、索引与备份里都还在。后果有两个：其一，“过期”不能当作合规意义上的删除，被要求彻底清除时不能只靠打标记；其二，误标过期的条目只要留着就有被错误重新激活的风险。真正的删除要同时落到数据、索引与备份三层，并留下可核对的处理记录。

渐进披露：先摘要，后原文

渐进披露是本文的读取策略：不要把每条记忆的原文都塞到模型眼前，先给一行摘要，等模型判断这条确实相关、摘要又不足以支撑决策时再回去取原文。这样一次调用里为记忆付出的预算，主要花在“要不要细看”的判断上，而不是无差别地搬运长文本。

它分两级。摘要层为每条记忆预先或按需生成一句到数行的概括，带标识与写入时间戳，进窗口成本远低于原文。原文层只在摘要不够用时触发，用标识把完整内容取回，全部 token 成本压到最后一步。

flowchart TD
    A[本轮任务] --> B[取候选记忆的摘要层]
    B --> C{摘要是否足够}
    C -->|足够| D[按摘要作答]
    C -->|需要细节| E[按标识回取原文]
    E --> F[原文进入本轮上下文]
    F --> D
    D --> G[输出]

摘要会在三种情况下骗人。一是压缩掉了限定条件：原文是“仅在测试环境用这套配置”，摘要成了“用这套配置”，条件一丢结论就危险。二是固化了旧版本：原文后来更新过，摘要还停在旧措辞上，读到的是过期结论。三是吞掉否定与不确定性：原文是“倾向于 A，但没排除 B”，摘要变成“结论是 A”，把不确定说成了确定。所以摘要层必须始终带一个可回取的标识，任务对精确性敏感时宁可多花预算取原文，也不要信摘要。

跨会话一致性

同一条事实会跨会话被反复更新，问题是更新之后旧版本怎么处理，以及两条记忆互相矛盾时怎么办。这里只谈边界与策略；冲突消解的具体算法属于检索那一层，本文不复述。

版本处理上，更新不覆盖：给事实记版本而不是原地改写，新写入标注生效时间与被哪条取代，旧版本进入不再默认召回的状态。这样当会话被回溯、或某次更新事后被证明是错的，能还原当时到底依据了什么。与之配套的是时点化：把“用户当前住在北京”这类会变的陈述，连同写入时间一起记下来，避免把某个瞬间的状态当成永久事实。

冲突提示要分关键与非关键。当两条都还有效的记忆在一个会影响决策的关键属性上互相矛盾，例如两个不同的收货地址，正确的做法不是让模型私下挑一个，而是把矛盾显式暴露给用户：复述两条各自来自何时、请用户确认以哪条为准。沉默地择一，会把数据质量问题伪装成模型幻觉，事后最难排查。反过来，明显能靠时间顺序判定的非关键冲突，按较新版本处理并记一行审计日志即可，不必打扰用户。

记忆与上下文组装的接口

记忆子系统对上游只暴露一个接口：给定本轮任务，交回一份排好序的候选，摘要层优先，由组装层决定放多少进窗口。窗口预算怎么在指令、工具、历史、检索、输出之间分配，是《Agent 上下文工程》要回答的；这里只定记忆这一侧的两条边界。

第一条，放不进窗口时的取舍：候选超过记忆能占的空间时，先丢摘要层里最不相关、最陈旧、还能重新生成的，保住稳定且经用户确认的，而不是去截断原文尾巴——那恰恰造出上文说的“骗人的摘要”。第二条，压缩的归属：把长历史折成摘要、把 token 压薄，是《长上下文压缩技术》的范围；记忆这一侧只管“选哪些进来”，不管“把进来的压小”。

隐私与留存

记忆是隐私问题的高发区，本节只写能直接落到代码和流程里的动作。

最小必要：写入前先判断这条是否任务必需，能不落库的就只留在窗口里，敏感字段进记忆前做脱敏或降精度。留存与删除落地：给每类记忆定明确留存时长、到期即清，实现一条响应用户删除请求的通路，删除要同时作用于数据、索引与备份并留下可审计记录，只打墓碑标记不算数。不留存明文原文：能存结构化事实或摘要就不整段保存对话，确需保留的落库前加密并限定可读范围，让原文存活期短于它派生的记忆。不跨租户共享：读写以租户为边界，检索作用域绝不跨租户命中，一个用户的偏好不能被当成全局默认值发给别人。不当默认训练数据：记忆内容不因存在于此就自动进训练集，用于训练必须单独再取一次授权，这与“是否开启记忆”是两个不同的同意。

三种失败形态与处置

记忆的失败大多不是“不记”，而是“记错了还一直用”，三种形态各有处置。

错误记忆的自我强化：一条写错的记忆被召回、又被引用进新的输出，就可能再被写回，错误越滚越大。处置是给记忆标来源类别，模型自己推断的绝不与用户确认过的同等对待，重要事实要能追溯出处。

时间混淆：把“曾在北京”当成“现在在北京”，是旧事实被当成新事实用。处置是召回时随条目带上写入时间与失效时间，时效敏感的属性取最新有效版本，把“曾经”和“当前”分开表述，不靠模型去猜。

注入的持久化：网页、工单、工具或 MCP server 返回的文本里可能藏着指令，一旦被当作事实记下来，注入就从一次性变成跨会话常驻。处置是外部来源默认只作数据、不作指令并标记不可信，写入前剥离“转述的第三方指令”，凡外部文本要求系统去记忆或删除什么的，都不自动执行，须用户确认。

怎么验证记忆真的有用

判断记忆有没有价值，诚实的办法是对照，不是盯命中率或召回这类数字。做法是固定同一批任务，一次开长期记忆、一次关掉，其余变量尽量一致，比较任务完成质量、返工次数与人工干预率这些任务口径的结果。特别要盯两类反例：开了记忆反而更差的，多半被陈旧记忆带偏；只在演示任务上变好、换一批就现原形的，多半是记忆没真正起作用。对照要按任务类型分层看，别用一个总分掩盖它在某类任务上的伤害。

小结

本文只做一件事：把记忆的三层边界、写入与遗忘的策略、以及隐私留存的底线划清楚，实现细节留给检索与工程那几篇。可落地的原则是分层要清楚、写入要有判据、遗忘要落到存储、摘要要能回取、矛盾要交给用户，对敏感与外部内容格外克制。下面这张表是全篇的收口。
