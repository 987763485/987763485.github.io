大模型编译与推理引擎

大模型推理的性能账可以拆成三件事：少算一些算子、把每个算子算得更快、让算子更多重叠。编译层负责前两件，引擎的层次决定第三件。本文梳理各环节解决哪类开销、带来什么代价，并给出一个判断框架：什么信号说明值得动编译层，什么信号说明应该先动服务层——一次”编译加速”到底加速了什么，为什么它换一台机器就可能失效。

编译层到底做什么

先破除一个印象：编译层不是”把 Python 翻译成机器码”，而是一串各自独立、各有失败模式的变换，拆开看至少包含五件事，每件对应一类开销。

第一件是图捕获，解决宿主侧决策开销：解释执行形态下，每个算子都要经过语言运行时的分发、参数检查、设备选择，设备却在等这些决策在 CPU 上排完队。图捕获把”这一次前向做了哪些计算”固化成结构，后续执行只需一次提交。第二件是算子融合，解决显存带宽与启动次数的双重开销：多个逐元素算子各自要把中间结果写回显存再读出来，融合后一次读写完成多个计算，算子实例数也随之下降。第三件是内核生成，解决”通用实现打不过特化实现”的问题：为当前形状、当前 dtype、当前架构生成专用的循环与访存模式，比一个照顾所有情形的库算子更贴。第四件是显存规划，解决分配抖动：图级别知道每个张量的生命周期后，可以预先做复用与偏移分配，把执行期的分配器调用压到最低。第五件是调度，解决占用率问题：决定哪些计算放哪个流、哪些通信可以与计算重叠。

这五件事彼此独立：可以只做图捕获不做内核生成，也可以反过来。评估是否引入编译层，应当逐件问”我的负载里有没有这一类开销”，而非整体购买。

三条捕获路线

把执行过程变成图，业内通行三条路，各自的坑不一样。

第一条是追踪式捕获：照着一次真实前向执行，把途经的算子连同形状、数据类型记录下来建图，当时主线的 PyTorch 2.x 一类框架就是这条路线的代表。它的坑来自”记录”这个动作本身：控制流只记录走过的分支，未走的分支要么下一轮以新形状重捕获，要么被静态化为条件节点；随机数状态、日志写入这类副作用容易被误捕，落进图后重放语义与原程序不一致；形状一变整图作废，为后文的动态形状问题埋下伏笔。

第二条是导入既有 IR：先从框架导出一个中间表示，再交给下游编译器处理。好处是图的获得不依赖某一次执行的路径，导出物可审查、可缓存。坑在导出面的完备性：框架的算子语义往往多于 IR 的表达能力，导出器要么把差额展开成原始算子集合（图变得巨大），要么留下不透明的回退块；动态控制流在这一路线上通常被强制降级，要么展开成静态分支，要么干脆导出失败；线上跑编译产物、手里只有导出前源码，调试口径隔着两层翻译。

第三条是编译器后端直出：绕开框架的中间表示，从高层描述直接下降到目标平台的代码。收益是变换空间最大、不受框架 IR 的表达限制；代价是所有语义都要自己实现——自定义算子、动态形状、控制流乃至错误处理，缺一样就有一类模型跑不起来，工程投入与前两条不在一个量级。

选路本质是在捕获保真度、导出完备性、可控性三者间排序：求快速接入走追踪，求产物可离线审查与缓存走 IR 导入，愿意养编译器团队才考虑直出。

动态形状：分桶、guard 与重编译

预编译的收益有一个隐含前提：图是稳定的。真实推理负载里这个前提很难成立，因为形状一直在动——训练的批大小是钉死的，在线服务的批却靠连续批处理一路拼出来，请求输入长度又服从长尾，同一个计算图因此面对无穷多个形状。

编译器的常规对策是分桶：把形状归入若干个离散档位（按批大小、按序列长度取整），每个档位各编译一份图。分桶把无穷问题变成有限问题，但引入两类新代价。其一是覆盖率：落在桶间的形状要么向上取整补 Padding（浪费的算力直接体现在延迟上），要么触发新桶的新编译。其二是 guard：运行时每次进入图之前，要校验实际形状、数据类型、设备是否与编译假设一致，不一致就重捕获重编译。guard 本身是纯 CPU 的逐张量检查，图拆得越碎，其相对成本越高；重编译的代价更棘手——它不是均摊开销，而是精确砸在某一个真实请求的首 token 延迟上，从外部看就是一次无规律的长尾。

由此，”预编译收益”成立的条件可以说清：形状分布高度集中，少数几个桶覆盖绝大多数请求；guard 命中率稳态下接近全部命中；编译产物能持久化，冷启动不必重付编译成本。三个条件缺任何一个，编译层带来的都可能不是加速而是抖动的重新分布——把稳定的宿主开销换成了偶发的巨大重编译开销。

推理引擎的三个层次

“推理引擎”这个词经常一整块地用，但优化点其实分布在三个层次，各层的抓手与预算完全不同。

flowchart TD
    A[服务层：批策略 / 路由 / 并发 / 缓存复用] --> B[运行时层：调度 / 显存管理 / 流与同步]
    B --> C[编译与内核层：图捕获 / 融合 / 内核生成]
    C --> D[GPU 与驱动]

编译与内核层刚讲过，不重复。运行时层解决”资源怎么排队”：请求调度决定谁进批、谁等待；显存管理决定 KV 显存的分配形态，机制细节另篇专讲 KV Cache 与分页；流与同步安排决定 CPU 提交与 GPU 执行能否真正流水线化。服务层解决”喂给引擎的东西长什么样”：批的拼法与等待窗口、请求路由、前缀缓存复用策略。vLLM 这类开源引擎的价值主要在下两层的工程化，其部署跑法另篇有实践文，此处不复述。

三层有个先后规律：服务层的决策决定运行时层的可用空间，运行时层的状态决定编译层的收益上限——批的填充率低时，再快的内核也在空转。这也是后文工程决策一节的伏笔：很多看起来该找编译层的负载，账算下来卡在服务层。

观测口径：看什么、怎么归因

编译层上线前后必须换一套观察方式，否则收益与退化都说不清。本文只给口径与归因路径，不给任何倍数与绝对数字——这类数字离开具体负载就没有意义。

要看的五个量：算子级耗时分布，确认时间集中在哪几类计算；内核启动开销占总时长比例，它是”宿主受限”最直接的证据；CPU 与 GPU 的同步点，即设备等宿主的时刻；显存水位随时间的曲线，看分配抖动与峰值余量；批的填充率，即每次前向的实际计算量与批上限之比。

归因的顺序同样重要。第一步分宿主与设备：把提交侧挪到独立流后总时长几乎不变，问题大概率在设备执行本身；提交很快而设备排队很长，是内核的事。第二步查同步：一次隐式同步能把整条流水线串行化，在时间线上表现为周期性空洞。第三步查形状：耗时分布里若存在与请求长度相关的成组漂移，说明命中了不同的编译桶。第四步才轮到融合与内核质量——它排最后，因为前三步的病灶它一概治不了。

内核自动生成类工具的位置

这一类工具常被当成一个整体讨论，实际定位差别很大，本文只写定位与适用面，不做版本与性能对比。

Triton 一类 DSL 面向懂 GPU 内存模型、想把特定子计算交给代码生成的开发者：你描述分块与访存，编译器负责寄存器与调度细节；适用面是已有明确热点且库算子确实覆盖不到的场合，它不替你决定该融合什么。XLA 是绑定框架的图级编译路线，长处在全图视角下的融合与布局传播，适合形状相对稳定、愿意接受编译时延换执行收益的场景。TVM 一类是可编程的端到端编译器栈，lowering 路径自己可控，适合自建后端与异构硬件，代价是工程量以年计。ONNX Runtime 则是”导入既有 IR”路线的代表，价值在跨框架分发与成熟硬件上的开箱覆盖。端侧的 ExecuTorch、MLX 与端侧推理专篇分轴，本文不展开。

选型时最该核对的一件事：候选栈的算子覆盖是否包含你的模型结构。覆盖不全的代价不是报错，而是静默回退——图被切碎，收益在你看不见的地方漏光。

量化与编译的交互

低比特量化与编译层各自都常被宣传，工程问题却多出在两者相遇的交互处。

第一处是内核可用性：量化引入的新数据类型，要有对应的低比特内核才能吃到收益。新位宽、新排布、新形状组合往往没有现成实现，此时编译器面对的不是”慢一点”，而是这个节点根本编译不出目标代码。第二处是回退链：当某个算子没有低比特实现，栈可能把张量反量化回高精度再走原始算子——单次看没问题，但如果这个反量化没有提到循环外或干脆被融合掉，每一次访问权重都要重复反量化，带宽收益被计算开销吃掉大半，时间分布上表现为”量化了反而某些算子变慢”。第三处是精度与形状的耦合：不少低比特内核只为特定的分块尺寸存在，一次形状变化会同时触发重编译与精度路径切换两类事件，叠加在时间线上，归因极易混乱。

因此量化与编译分开验证是纪律：先在基线精度下跑稳图捕获与融合的收益，再单独引入量化，把图里的反量化与转换回退点显式数一遍——它们的位置比精度报告诚实。

为什么”编译一次到处最快”不成立

编译产物本质上是”对当前环境假设的一次性押注”，而假设的每一项都可能变。

GPU 架构与代际变了，指令集、共享内存容量、调度器形态都变了，为旧架构生成的内核在新架构上只能算能用；驱动与运行时版本变了，库算子实现与默认流行为都可能调整，同一份图在不同驱动上不是同一件事；线上的形状分布随业务漂移，原先集中的桶不再集中，guard 失效率悄悄上升；批策略一改——比如调整等待窗口或最大并发——每一步的形状与并发粒度全变，之前的特化多半特化错了对象。

结论不是”编译无用”，而是产物连同其环境指纹应当被当成需要持续验证的整体，护城河挖不了一次。

冷启动与首次编译的处置

编译是重活，首笔账在冷启动：实例上线后头一批请求要么等编译，要么走回退。处置手段无非三种。预热是在接流量之前先按典型形状跑一轮，把编译成本挪到部署阶段，代价是启动时间变长与形状清单要维护。产物缓存是把编译结果连同环境指纹持久化、新实例直接加载，前提是失效判定足够谨慎——指纹少了维度，就会加载一份对不上环境的产物。按需与全量的取舍本质是分布问题：形状桶少且集中时全量编译一次做完更稳，长尾宽时按需编译产物面小、却把重编译留给了线上。端侧的冷启动账另篇细算，本文只标位置。

工程决策：先动哪一层

值得引入编译层的信号是结构性的：时间分布显示宿主侧启动与同步占大头；算子模式化程度高，融合有明确的靶子；形状分布集中，分桶与 guard 稳得住；团队能看懂产物、担得起调试口径分裂的成本。反过来，该先动服务层的信号同样清楚：批的填充率长期偏低，设备在等请求——先改批策略与并发，再谈内核；前缀缓存复用稀疏、路由不均——这是服务层的账，编译层帮不上；显存频繁触顶——先改运行时层的显存管理，它的收益通常比融合来得干净。llama.cpp 一类端侧跑法与 Rust 在基础设施里的落位各有专篇，此处只作分轴声明。

回滚成本评估看三件事：编译入口是否保留解释执行的开关且线上验证过；产物缓存是否与代码版本隔离、可整体作废；监控里能否用 guard 与回退计数在分钟级定位到”退化来自编译层”。三件事做齐，编译层是一个可关掉的优化；做不齐，它是一次不可逆的架构承诺。

小结

本文把编译层拆成五件独立的事、把捕获路线拆成三条、把引擎拆成三层，核心立场只有一个：编译收益是环境假设的函数，不是常数。最后一张表把主要技术项的收益与代价并列，供决策时逐行核对。
