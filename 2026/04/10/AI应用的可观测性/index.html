AI 应用的可观测性

传统后端服务生病，我们看 QPS、延迟、错误率就够了；AI 应用生病，很多老信号还在，但最要命的那部分往往没有 HTTP 状态码可查。本文讲怎么给 AI 应用铺观测面：一次交互的追踪怎么切层、关联键怎么定、日志怎么脱敏与采样、成本怎么归因、面板与告警怎么分层。适合正准备给智能体应用埋点、或者埋了点却发现面板说明不了问题的工程师。

为什么 AI 应用的观测难点不同

第一处不同，输出非确定。同样的输入，两次运行可以给出不同回复：采样温度、模型版本、上下文缓存命中与否、流式分块的边界，都会改变结果。传统服务里请求相同而响应不同就是缺陷，这里”不同”是常态，观测因此必须允许统计视角，并为复现留够依据——记录模型标识与关键配置参数，而不是只记一句”调用成功”。

第二处不同，成本是一级指标。传统系统单次请求的边际成本近似为零，很少进面板；AI 应用每一步消耗的 token 直接等于钱，重试、长上下文、工具级联都在烧预算。观测体系若不带用量维度，就回答不了”钱被谁、在哪个功能上花掉了”。

第三处不同，语义失败没有状态码。模型客气地答非所问，HTTP 返回 200，追踪一片绿色，可答案就是错的，或者幻觉出一个不存在的工具参数名。这类”一切正常但结果不行”要专门采集点：用户反馈、重新提问、切换问法、转人工，都是它的代理信号。指标本身的定义与阈值口径，《大模型监控指标体系》已详述，本文只谈采集与埋点实现，不重述。

一次交互的 trace 结构

本文建议把观测粒度切成四级：会话 → 步骤 → 模型调用 → 工具调用。会话是最外层容器，对应一次对话；步骤是循环里的一轮”决策—行动—观察”；模型调用记录每一次对模型的原生请求，含流式响应的等待与生成段；工具调用把检索、代码执行、MCP 工具（协议口径按 2025-11-25 修订）这些外部动作各包成一个 span。

flowchart TD
    A[会话: 会话标识] --> B[步骤 1: 规划]
    A --> C[步骤 2: 行动]
    B --> D[模型调用: 意图识别]
    C --> E[模型调用: 生成回答]
    C --> F[工具调用: 检索知识库]
    F --> G[工具结果: 成功]

四级的好处在于：异常与成本都发生在最底层，但人排查问题时看的是步骤层的上下文，父子关系定死了，才不会”知道一次请求很贵，却不知道贵在哪一步”。编排框架大多提供开箱即用的插桩，LangChain 1.x 的回调整机制可直接挂接；LangGraph 1.1 刚满一月，其插桩的成熟度本文仍在跟进，接入前先在小流量上验证 span 的层级是否符合预期。

关联键与命名约定

一次交互的数据可能散落在网关、编排服务、模型提供方 SDK、异步 worker 乃至子智能体里，要靠关联键拼回完整链路。本文建议至少三层标识：全局唯一的追踪标识贯穿所有服务，跨进程传播用 W3C traceparent 头；会话标识属于业务域，出现在每个 span 的属性里；步骤序号给出轮次次序。异步任务要在消息体里显式携带会话标识与步骤序号，worker 起子 span 时回链到父追踪，别指望上下文自动传播。子智能体自起追踪时，跨智能体的因果链与传播细节另见《多 Agent 系统可观测性》，本文只要求父侧留好钩子。

同样要紧的是基数控制。会话标识适合在追踪与日志里做精确查找，但绝不能当指标的维度——用户与会话无量级上限，塞进指标标签后基数爆炸，先垮的是存储与查询。命名也要在项目层面一次定死：会话标识用哪个字段、模型调用的 span 叫什么、工具结果状态取哪些枚举值。命名松一个季度，面板就要重写一个季度。

日志、指标、追踪的分工

三者各回答一类问题，谁也替代不了谁。指标回答”总体形态变没变”：错误率、成本走势、延迟分布，告警由它触发，必须全量采集，否则连分母都不可信。追踪回答”这一次请求的哪一步慢、哪一步贵、哪一步断了”，可以采样。日志回答”事件发生那一刻的上下文与原因”，按层级留存。

常见的退化有两种：拿日志当指标，靠 grep 日志算比率，日志本身被采样过，比率全是假的；拿追踪当日志，把诊断细节塞满 span 属性，追踪通道被撑爆。工具层面，OpenTelemetry 统一采集，Prometheus 管指标、Loki 管日志、Tempo 管追踪、Grafana 汇成面板，定位都是老的；通用观测体系怎么搭，此前几篇通用可观测的文章已经讲过，本文只谈落到 AI 场景的差异；端侧怎么埋点，前端埋点那篇也有过交代，不复述。

语义约定：gen_ai 属性注册表怎么用

OpenTelemetry 为生成式 AI 立了语义约定，即 gen_ai.* 属性注册表，覆盖操作类型的划分与若干概念字段：会话标识、操作名、模型名、输入与输出 token 用量、工具名等。必须强调，该注册表当前状态标注为 Development，属于未稳定规范，仍在演进、属性名与语义都可能变动，不能把今天的清单当契约写死。

本文的立场是：词汇应当借用，因为它让不同厂商的工具之间可比；但要隔一层内部属性——埋点代码只写内部字段，导出器再映射成 gen_ai.*，注册表变动时只改映射层。除注册表已列出的之外，不硬造属性键，剩下的用概念表述即可：会话标识、步骤序号、模型与用量、工具名与结果状态。概念不过时，键名的具体拼写交给映射层去追。

脱敏与采样

先定采集哲学：最小必要。提示词与回复要不要落盘、以什么形态落盘，取决于调试是否需要，而不是默认”全量存了再说”。把用户提问原文完整留存既放大隐私暴露面，也让留存与删除变成空话，不是正面做法。

落盘策略分三档。默认档只存摘要、截断片段或哈希指纹，哈希能判断”两次输入是否相同”，却不还原内容；升级档按租户或功能按需开启原文调试开关，开启要有时间上限、操作留审计；禁区档则是手机号、精确地理位置、身份证件号、通讯录内容、剪贴板内容——这些从一开始就不允许进入观测管道，是必须避免的采集对象，而不是事后脱敏的字段。凭据与密钥绝不进日志、追踪属性与缓存键，是硬约束。PII 处理宜在 SDK 侧用规则加模型混合检测、以占位符替换，并把替换次数本身做成指标，别等数据落进消息队列再补救。

采样上有个误区：只靠尾部采样。尾部采样要等整条追踪上报到收集器才能决策，带宽与处理成本已经花掉，而 AI 应用 span 密集，这个代价恰好承受不起。合理的是混合：头部采样控制总量，尾部采样保全稀有样本——出错的全部保、超预算的全部保；且按会话标识哈希采样，保证被选中的会话是完整的一整条，而不是零散几步。

成本归因

成本要成为观测对象，先得有稳定的计量口径：每个模型调用 span 记录输入 token、输出 token、结果状态，并在调用时刻就带上归属维度——业务线、租户、功能入口。别指望事后从账单倒推，账单里没有功能入口这一层。聚合至少按业务线、租户、功能三条轴走，才答得上”这个月超支超在哪个功能上”。

两个容易漏的采集细节。其一，流式响应的用量字段通常在终止帧才出现，包装层要等正常终止才落账，客户端中断或连接异常时把该次调用标记为不完整，单独对账，否则系统性少记。其二，上下文缓存命中显著影响归因：同一段长前缀，命中与否的消耗差异很大，若不把缓存命中记成那次调用的属性，同功能成本的波动看起来像缺陷，其实只是命中率变了。预算告警分两路：事件式的”单租户突破配额”走工单，趋势式的”按当前速率月底将超预算”走告警渠道，阈值都是团队约定示例，没有放之四海皆准的数字。

面板与告警分层

SLI 建议分三层：服务层看可用性、首 token 延迟、端到端延迟；质量层看错误率、拒答率、工具失败率；成本层看单次调用成本与每日消耗。每层各定 SLO 与错误预算，所有阈值一律标”团队约定示例”——抄来的数字既不贴合业务，也会很快过时。

难点是质量层，语义失败读不出直接指标，用三类信号拼近似：人工抽检按固定份数持续做，结论记进统一存储；自动判定用规则查格式与红线词，再让更强的模型给回复打分——比如用 Claude Opus 4.6 或 Sonnet 4.6 做裁判，打分提示词本身也要版本化管理；用户反馈信号——点踩、重新提问、转人工——样本最大但噪声也最大。三条曲线并排看，才勉强算”语义质量在被监控”。告警按预算燃尽率、单功能异常、长周期劣化分优先级，分别对应呼叫、工单与仅看板。至于告警该落在哪个部署形态、由谁认领，《Agent 生产部署架构》已讲过部署侧的落位，本文不重复。

观测与评测的打通

观测是评测集的水源。定期从线上追踪里抽样案例——先脱敏再导出——把带失败信号的（点踩、转人工、自动判定不过）排进候选，人工复核后进评测集，评测集才能跟上线上真实分布的漂移。回归门禁挂在发布流水线上：新版本在抽出来的线上案例集上不过线，就不允许切换默认路由。评测体系本身、门禁挂哪一层，《AI 应用评测体系》已讲过；本文只要求观测侧预留”从 trace 一键导出为案例”的能力与脱敏通道。

常见误区

误区一，把日志当指标。用 grep 日志算比率，日志被采样过、被延迟落盘过，比率连分母都不可信；指标必须走自己的聚合管道。

误区二，维度爆炸。把会话标识、用户标识、完整 URL 塞进指标标签，基数无上限，存储和查询先于业务崩溃。高基数字段属于追踪和日志，用来点查，不用来聚合。

误区三，凭据与原文入日志。为方便调试全量转储请求体，用户手机号、证件号乃至接口密钥一起落进日志库；密钥进了追踪属性或缓存键同样算泄漏。先脱敏再出口，凭据只进密钥管理系统。

误区四，只看平均值。AI 应用的分布长尾极重，平均首 token 延迟好看，尾部体验可能糟糕透顶；月均成本平稳，不妨碍某次失控循环一天烧掉预算。至少同时看分位数与峰值。

小结

AI 应用观测的特殊性可以归结为三点：输出非确定，排查要从单点检查转向统计与复现依据；成本是质量之外的第一变量，用量与归属维度必须和延迟同权重进链路；语义失败没有状态码，人工抽检、自动判定与用户反馈就是它的采集面。落地上守住两条纪律：最小必要采集，手机号、精确地理位置、身份证件号、通讯录、剪贴板一律不进管道；先脱敏再落盘，默认摘要、截断与哈希，原文只作为按需开启、带审计、会自动过期的例外。gen_ai.* 语义约定仍在 Development，借它的词汇、隔一层内部属性去抗变动。埋点、脱敏、归因、告警四个环节咬合成一圈，面板才算真正开口说话。
