Agent 记忆检索优化

本文属于《Agent 智能体开发》第 21/55 篇
上一篇系列目录下一篇

智能体的记忆系统里，写入只是把事实放进仓库，检索才决定它能否在正确的时刻回到上下文。本文把记忆检索当作一个检索问题拆开：条目怎么表示、写入时怎么为召回让路、几条召回路径各自治理什么、矛盾怎么消解、预算与反馈怎么闭环。文中不重复通用文档检索与索引参数调优的既有结论，只聚焦智能体自有记忆条目这条链路。

先把问题收窄

本文讨论的对象，是智能体在长期运行中自己积累下来的记忆条目：用户明示过的偏好、反复观察得到的习惯、执行过程中沉淀的过程性知识、发生过的事件与结论。它看起来和普通文档检索是同一个动作，实际面对的是一份很不一样的语料。

文档库是外部资料，条目之间彼此独立、时间性弱、归属模糊；记忆条目是交互的产物，每一条都有明确的来源链，有强时间性——同一个偏好在不同时间可能是两个样子，也有硬作用域——某个项目里的约定不该出现在另一个项目的回答里，而且往往含个人信息。条目规模也小得多，一个用户级记忆库常见在数百到数万条的量级（示意值）。这个规模直接改变了设计的目标函数。

在小语料上，索引结构的收益会被召回逻辑的失误掩盖。图索引调得再漂亮，也救不回一条把“偏好简洁的周报”和“偏好简洁的会议”合并写入的错误条目。所以本文把工程重心放在三件事上：召回相关性，即该出现的是否出现、不该出现的是否不出现；时效正确性，即新旧事实谁胜出；成本可控，即单次检索在会话热路径上占多少预算。

先把边界划清楚，避免与同批文章重复。《Agent 记忆系统设计》讲记忆的分层与生命周期，本文不重述它的层级划分；《Agent 记忆与长期上下文》讲上下文窗口与持久记忆之间的分工，本文不讨论写入触发与窗口挤出；《RAG 混合检索与重排序》讲通用文档的混合召回与重排，本文只把它的融合口径当作可复用组件；《向量索引算法 HNSW 与 IVF》讲索引结构与参数取舍，本文不涉及这些调参；《RAG 检索质量评估》讲指标定义与评估方法，本文只把评估落到记忆场景的闭环上；《Agent 上下文工程》管的是窗口预算怎么分，本文管预算之内该装哪些条目；《GraphRAG》讲图谱增强的文档问答，本文只把图跳转当作记忆条目之间的一跳扩展。

在这条边界内，记忆检索可以拆成五个工程环节：表示、写入、召回、消解、反馈。前两个决定“库里有什么、能不能被找到”，中间两个决定“这次找到的是不是对的”，最后一个决定“下一次会不会更好”。本文按这个顺序展开。

记忆条目的表示与元数据设计

一条可检索的记忆本质上是一个多视图对象：一段自然语言陈述、一个压缩摘要、若干关键词与实体、一个向量、一组结构化字段。视图越多，能接住的查询形态就越多；但每个视图都要在写入时生成，这就是延迟和成本的来源。因此第一个设计决策不是选哪个 embedding 模型，而是决定给条目配哪几个视图、每个视图承担什么召回职责。

字段设计里，有五个元数据维度直接参与检索决策，缺一个就会在某类查询上系统性失效。

类型维度回答“这是一条什么性质的记忆”。常见取值是事实、偏好、过程、事件、计划、引用、纠正。类型的作用有两层：一层是过滤，涉及风格与口味的查询应当优先取偏好与纠正类，涉及“上次怎么做的”应当优先取过程与事件类；另一层是加权口径，偏好类可以随时间温和衰减，事实类不该衰减——“这个项目用 pnpm”不会因为没有最近被提到就变得可疑。把类型只当作展示标签，是记忆库里最常见的浪费。

时间维度至少要拆成三个字段：事件发生或用户表述的时间、条目被写入的时间、条目的有效期。再加一个修订时间用于审计。新近度打分必须用前者，去重与回溯必须用中者。把“用户什么时候说的”和“系统什么时候记下的”混成一个时间戳，会导致重新导入历史会话时全部条目的新近度被打乱，旧偏好瞬间变成最新偏好。有效期字段则决定条目是恒常的还是临时的：临时条目到期后应当退出召回而不是删除，因为它还要参与历史解释。

来源维度是可信度的地基。取值区分用户明示、工具结果、模型推断、外部导入四类，并保留一个可回溯的定位符，指向会话或工具调用，而不是把原文长期留在条目里。来源在检索时的用法是分层而非一票否决：模型推断的条目可以与用户明示的条目同场竞争，但在冲突消解时永远让位。

置信维度建议存两个数：写入先验与观察次数。先验由来源类型与表述强度决定，观察次数由后续命中累加。打分时置信只做温和加成，不设硬门限——早期一次错误判低，可能让一条真实偏好永久不可召回，这种不可逆代价远大于偶尔召回噪声。

作用域维度是最容易被低估、也最容易出丑的字段。它包含归属主体与层级：全局、某个项目或工作区、某个会话。作用域必须是硬过滤条件，不能只当加权项。串味是记忆检索里最难看的错误，用户会立刻察觉智能体把另一个场景里的约定搬了过来。

写入侧的可检索性设计

检索质量的相当一部分在写入那一刻就定了下来。把记忆写入看成“把话存下来”是误区，它其实是“为未来的模糊查询预先构造可命中的靶面”：靶面太小，召回漏；靶面太大或者形状不对，召回噪声；一条里塞多个断言，任何单一查询都只能拿到部分匹配，打分被稀释到排名之外。

第一条纪律是一条一断言。用户在同一段话里说“周报只写结论，另外以后周五再讨论排期”，应当拆成两条条目：一条是格式偏好，一条是时间安排。拆分之后，问格式只命中前者，问日程只命中后者，两条各自的时间、作用域、置信也才能独立演化。复合条目除了打分吃亏，还会在冲突消解时制造假矛盾：新消息否定了其中的排期部分，旧条目整体被误判为失效。

第二条纪律是陈述句化。条目正文应当写成脱离上下文仍然可读的第三人称陈述，而不是保留对话原话。“半页以内别写太多”这种表述依赖当时语境，换个查询场景就失去含义，而且它把用户原文留在库里，与隐私口径冲突。写入时做一次轻量改写，把语气、指代、时间状语补全，是收益最高的一个环节。摘要视图再压一层，只保留可被关键词通道命中的名词与术语。

第三条纪律是命名与切片。结构化键要用谓词化的稳定命名空间，形如“对象.属性”的点分路径，而不是自由文本；自由键无法做结构化过滤，也会在条目累积后出现同义键爆炸。切片则按断言边界切，不按固定字符数硬切：把一段执行记录切成三句、每句自足，远好过切成两个半句。稀有 token（文件名、配置项、命令、标识符）要在写入时抽进关键词字段，因为语义向量对这类符号最不敏感，而它们在记忆查询里出现频率很高。

四条召回路径与其自治理范围

记忆库的查询分布很宽：有语义问法，有术语问法，有时间问法，有关联问法。单条路径接不住，所以召回是多路并行、各自负责一段失效空间。下面四条路径的分工要写进设计文档，因为它们最常被混用，混用之后无法归因。

向量通道治理语义相似与表述差异。它负责“用户换了一种说法”“中文问、英文记”“查询短、条目长”这几类情况，也负责别名与同义改写。它不负责时间，不负责作用域，也不负责精确符号：一条距离很近的旧偏好会挤掉一条距离稍远的新偏好，这是它的结构性缺陷，必须由其他通道与后置打分补。

关键词通道治理精确符号与稀有词。项目名、命令、配置键、函数名、标识符这类 token 在向量空间里区分度不足，却是记忆查询里最常见的定位手段。它的实现是经典 BM25 一类的稀疏打分，与中文分词策略强相关；把写入侧抽出的术语字段单独建索引，比整条长陈述效果更好，因为陈述里的通用词会稀释命中。

时间通道治理“新的覆盖旧的”。它不是独立召回器，而是对候选集合的新近度重排：按 occurred_at 做衰减，衰减尺度按类型区分——偏好与计划衰减快，事实与过程几乎不衰减。这一路必须与向量通道同时开启，否则最常见的事故是记忆库里存在一条同主题旧条目、语义更贴切、于是永远压住新条目。时间通道还负责有效期过滤：过期的临时条目直接不进候选。

图跳转通道治理实体与关联。记忆条目之间的边很自然：同一实体、同一别名、同一作用域、相邻会话、显式的取代关系。它负责“关于某个人的所有记忆”“这条结论从哪些观察得来”这类需要多跳聚合的查询，也是召回覆盖不足时的补位手段。它必须被严格限跳：一跳做扩展、两跳做聚合，更多跳在小图上会迅速把整个库捞进候选，代价与噪声一起失控。

四路之外还有第五类，不是相似度通道而是结构化过滤：作用域、类型、敏感标记、删除标记。它在候选生成阶段就做硬过滤，绝不进入打分环节商量。把它列在这里，是因为多数“串味”事故都源于设计者把作用域当成加权项。

多路结果的融合，本文直接沿用混合检索与重排序那篇的口径：先按通道做排名倒数一类的融合，再进入记忆特有的后置逻辑（有效期、作用域复核、冲突消解、类型加权与置信加成）。需要强调的是融合权重不是全局常量：偏好类查询给时间与置信更高权重，符号类查询给关键词通道更高权重。具体数值属于团队约定示例，应当由离线评估集校准，而不是抄别人的配置。

召回链路全景

把前面的环节串起来，一次记忆检索的完整链路如下。这里的关键结构有三个：查询理解在最前面决定走哪几路、过滤在候选生成阶段就做硬边界、消解与整形在打分之后再做。

链路里有几处工程上容易写错。其一，硬过滤要在候选生成阶段生效，而不是等打分完再筛：先取回一批跨作用域的条目再过滤，既浪费算力，又会在过滤条件出 bug 时把别人的条目送进模型上下文。其二，图跳转的输入应当是已过滤的实体，否则别名边会把范围外条目带回来，等于绕过作用域。其三，融合排序与后置治理要分开：前者解决“谁排得高”，后者解决“谁已经不作数”，顺序颠倒会让被取代的旧事实靠语义距离重新冒头。

链路末尾那条回流是本文与纯检索文章最大的区别：记忆检索的输出会被智能体引用、被用户纠正、被下一次对话追问，这些信号是天然标注源，不利用就等于放弃了唯一免费的反馈。

去重与冲突消解

记忆库会自我污染。同一件事被反复表述、重新导入历史会话、模型把推断当事实写入，都会产生近似重复；用户改了主意、项目换了工具链、同一条偏好在不同作用域下确实不同，都会产生真冲突。不去重，召回集合里就塞满同义条目，预算被吃掉；不消解，模型就会拿到互相矛盾的两条事实，输出摇摆。

近似重复的识别用三层签名叠加：归一化文本签名（去空白与标点后的短哈希）、结构化键签名（同一组谓词键）、向量近邻阈值（阈值属于团队约定示例）。三层里任意两层命中就判为疑似重复，再决定合并还是并存。合并时保留信息量更大的那条为主条目，把其余条目的时间、来源、观察次数累积上去——观察次数累加这件事很重要，它是置信随重复表述自然增长的合法路径。

真冲突分三类，处理方式完全不同。

取代关系要用双向指针：新条目记 supersedes，旧条目记 superseded_by，旧条目不删除。这样历史解释与溯源仍然可查，同时召回阶段能用一条布尔条件把被取代者排除。要注意取代是按键与作用域判定的，不能只按语义相似度：两条语义很近但讲不同对象的条目，被自动合并就是一次真实信息的丢失。这也是为什么谓词化命名空间值得维护——它给了消解逻辑一个可靠的锚。

作用域串味有专门的治理动作。第一层是硬过滤，已在召回链路里；第二层是继承与提升规则：工作区条目的可见范围默认不向上提升为全局，全局条目可以向内继承；第三层是同名键的就近覆盖——全局有一条、项目有一条时，项目级胜出，但必须在日志里记录这次覆盖，因为它常是用户困惑的来源。第四层是删除的级联：某条目被遗忘后，指向它的取代链、图边、缓存片段都要跟着处理，否则被删条目会以“覆盖了它的那条”的形态继续起作用。

消解放在读取时还是写入时，是一个明确的取舍。写入时消解好处是检索便宜、一致性容易解释，代价是写入昂贵且早期误判难回收；读取时消解好处是策略可随规则演进立刻生效，代价是每次检索都付一遍消解成本，且热路径预算紧张。实践中的稳妥配比是重活放写入侧（近似重复合并、明确取代关系落库）、轻活放读取侧（就近覆盖、有效期复核、置信微调）。规则升级后，用一次离线重建把写入侧的旧判定刷新掉，而不是指望读取侧的补丁永远兜住。

召回打分的伪码骨架

把前面的规则落成代码，骨架应当是三段式：候选生成、打分治理、整形输出。三段职责不混，才能在做坏样本归因时一眼看出是哪一段的问题。下面这份伪码只表达结构与不变式，函数体留空或用注释示意。

这段骨架里有四条不变式值得单独强调。第一，任何通道都不允许绕过 ScopeFilter：图跳转的输入已被过滤，回退策略也只放宽层级的严格程度而不放宽主体归属。第二，被取代与过期条目在打分之前就被排除，避免它们靠语义优势冒头。第三，命中日志是必需项而不是可选项——没有通道与因子明细，坏样本归因只能靠猜。第四，空结果要有显式回退而不是静默返回空：静默空结果会让上游智能体以为“用户没提过任何相关偏好”，进而自由发挥，这类幻觉比召回噪声更难发现。

延迟预算与缓存协同

记忆检索在会话热路径上，一次检索的等待会直接转成用户可感知的停顿，所以它的工程约束是延迟预算而不是吞吐。预算的思路是把一次检索切成有明确上限的阶段，并为每个阶段准备可跳过的降级项。

四条路径并行的价值就在于此：串行会把四段延迟相加，任何一段抖动都直接顶到用户脸上。并行之后总延迟取决于最慢一路，因此需要给每一路设硬超时而不是等它自然返回。图跳转最容易超时——小图上的一次全邻居扫描可能捞出上千条候选——它也是第一个该被弃掉的，因为它的召回贡献通常是补位而不是主力。

缓存有三层，命中条件各不相同，混用是正确性事故的来源。

第一层是 embedding 缓存，键为查询文本归一化后的哈希加视图类型。它绕过的是重复表述带来的重复编码，缓存的是向量而不是结果，因此条目更新不会污染它。第二层是查询级结果缓存，键必须包含作用域、过滤条件哈希、时间桶与规则版本。时间桶与规则版本这两个字段很关键：新近度打分随时间变化，冲突消解规则随发布变化，缺任一个字段，缓存就会返回一份当时正确、现在错误的结果。第三层是会话级热集——当前会话刚写入或刚被引用的条目常驻内存，直接参与候选合并，不等索引刷新。记忆系统里有一类高频查询恰好命中最新写入，而向量索引与搜索引擎通常存在可见性延迟，热集就是补这个窗口的。

冷热分层与本地小索引也值得提一句。用户级记忆库规模小，可以把活跃主体的条目放进程内近似图索引（HNSWlib 一类是这类结构的定位，本文不谈参数），把长尾主体放服务端向量库（Milvus、Qdrant、Weaviate、pgvector 各有适用定位，此处只引用既有结论），冷启动按主体预热而不是全量预热。隐私与删除必须在这三层缓存上都能立刻生效：结果缓存按主体失效、热集直接移除、embedding 缓存不含条目正文可以保留。删除级联清单要写进设计文档，不能靠运维记忆。

离线评估与线上反馈闭环

记忆检索的评估口径与指标定义沿用检索质量评估那篇，本文只讲它怎么在记忆场景里闭环。难点在于记忆库没有现成的答案集：条目是私有交互产物，外部基准无法照搬，所以标注必须自建、并且要能持续生长。

离线侧的起点是历史执行记录。从会话轨迹里抽出真实查询（包括用户原话与智能体的内部检索意图），对每个查询标注候选集中的相关条目及其类型：强相关、弱相关、时间或作用域不适用、应被取代。标注不必全人工，先用规则预筛——同键、同实体、同作用域的条目由程序给出建议标签，人只做确认与修正，效率差别很大。评估集要按通道分层抽样，保证符号类查询、时间类查询、关联类查询都有一份，否则离线分数只反映以语义问法为主的那部分分布。

比分数更有用的是坏样本队列。检索出问题从来不是笼统的“不准”，而是四类性质完全不同的失效，混在一个看板里就修不动。

四类的修复位置不同，串味是正确性问题而不是质量问题，应当按事故处理而不是按权重调优处理。每条坏样本都要带上命中通道与因子日志，否则归因只能靠猜，这也是前面把命中日志列为必需项的原因。

线上信号是免费的标注源，别浪费。可采集的有这几类：条目是否被最终回答引用、用户是否纠正（“我没说过这个”“我改主意了”）、用户是否重复表述同一件事、智能体是否因缺信息而反问。引用与被纠正这两类信号可信度最高，重复表述则同时是置信累加与近似重复的信号。回流路径要把这些事件写成结构化反馈，进入坏样本队列或写入侧的更新流程，而不是只留在日志里。

最后一条是把评估与写入侧连起来：条目库发生变更（批量导入、去重合并、规则升级重建）之后，用固定查询集跑一次回归，比较结果集合的差异并把新增条目送人工抽检。这样做的价值在于，写入侧的改动对检索的影响通常滞后暴露，等到用户在会话里抱怨才发现，回收成本要高一个量级。变更前的回归门禁清单建议固定下来，包括硬过滤不可绕过、被取代条目不出现在结果中、删除级联后查询不报错这三条底线，它们都属于正确性而不是质量。

小结

本文把智能体自有记忆的检索链路当作一个独立问题处理，得到的结论可以归为六条。

  • 表示先于算法：类型、双时间、来源、置信、作用域这五个元数据维度，决定了后面所有环节能不能成立，缺一维就有一类查询系统性失效。
  • 可检索性是写入侧的责任：一条一断言、陈述句化、谓词化命名、术语进关键词字段，这几次改写换来的是整条链路的简单。
  • 四条召回路径各有明确治理范围，不要用一条去补另一条的结构性缺陷；作用域必须是硬过滤而不是加权项。
  • 冲突分取代、条件化、并存三类，重活放写入侧、轻活放读取侧，被取代的旧事实在打分前就退出。
  • 延迟预算决定架构：并行加硬超时加降级阶梯，缓存分三层且键里必须带时间桶与规则版本。
  • 闭环靠坏样本队列：漏召、错召、过期召、串味召分开归因，线上反馈当作免费标注回收，库变更跑回归门禁。

这套链路里没有哪一环是通用检索算法的最新结论，但它决定了智能体是否“真的记得用户说过什么”。记忆系统的口碑通常坏在串味和旧事实复述这两件事上，而它们都是检索设计与消解设计的问题，不是存储的问题。
