Agent 代码执行沙箱设计

本文属于《Agent 智能体开发》第 31/55 篇
上一篇系列目录下一篇

模型现写出来的那段代码，是整条 Agent 链路里唯一一份“运行之前没有人读过”的指令：它可能被上游的提示注入操纵，可能引用一个并不存在的依赖，可能在第 37 行埋一个死循环，也可能顺手把宿主上的某个文件打印到标准输出。本文只讨论一件事——这段代码要安全地跑一次，应该怎么把它关进一个足够小、又不至于让正常任务跑不起来的笼子里。我们不谈模型能力，不谈任务编排，只谈笼子本身：门怎么关、窗口怎么留、拆掉之后留下什么痕迹。

本文的边界：只谈一次执行

先把讨论对象钉死。一次代码执行动作，在实现上就是一个函数调用：输入是四元组——待执行的代码、随附的输入数据、墙钟时限、产物约定；输出是三件套——标准输出与标准错误、退出状态、代码主动写出的产物文件。本文只管中间那一段：从环境构造到环境销毁。上游要不要执行由编排层决定，下游结果怎么用由模型消费，都在本文之外。

还有一点要先钉住：一次执行对应一个一次性环境——每个动作从零构建、用完立即销毁、任何残留都不进入下一次。这和“给每个会话配一个长期工作区”是两种东西：会话级工作区里，前一轮留下的进程、文件与缓存会影响后一轮，隔离目标就从挡住恶意变成挡住互相污染，语义复杂得多。这个选择的成本，也就是启动延迟与无法增量，在第七节讨论依赖供给时正面算账。

从编年的视角看，这段代码的宿主换过好几茬。十年前它跑在 Web 后端的脚本解释器里，隔离靠语言级约定加一个目录根切换；容器普及之后，工程界一度把“扔进容器”当成终局答案。大模型 Agent 把它推到了另一个极端：一天要创建几十万个生命周期只有几秒到几十秒的执行环境，于是容器那份原本可以摊薄的固定开销，突然变成了每笔都要付的成本，而“跑的是别人现写的代码”又把内核攻击面的权重抬了上去。微虚拟机和 WebAssembly 运行时因此重新回到工程视野。这条线索上每一步选型变化的根因都不是性能，而是信任对象变了。

为了避免和同一批文章重复，这里用一句话划清分工：《Agent 工具调用与函数执行》谈的是调用在协议层怎么发起和派发，本文假定派发已经完成，只看落地；《Agent 沙箱与执行安全》谈沙箱在整体体系中的位置与治理，本文只下沉到单个动作的实现细节；《Agent 安全与权限控制》谈谁被允许做什么，本文谈允许之后怎么把它关住；《大模型安全与提示注入防护》在模型与提示侧设防，本文的前提恰恰是注入已经得手；《Agent 生产部署架构》谈服务形态与容量，本文谈单个执行环境内部。

两条自律：本文只写防御与边界设计，不提供逃逸路径、不描述任何漏洞原理，凡涉及“绕过”的讨论止步于“这一层挡不住什么”；开销不给对比数字，个别为说明形状而写的数值一律标注示意值或团队约定示例。

威胁模型：四份不可信

设计沙箱之前要先承认一个不舒服的事实：这一次执行里有四份东西是不可信的，而且它们不可信的原因各不相同。把它们混成一句“代码不可信”，就会漏掉后三份。

代码不可信：把注入当作已发生

模型现写的代码有两个来源风险叠加。一是它本来就是概率生成的产物：调用一个不存在的接口、写下一个平方复杂度的循环、在没有终端的环境里等待输入，这些都不需要恶意，模型的能力边界就足够制造事故。二是它可能被操纵：如果上下文里混进了外部数据——网页正文、工具返回、文件名——而模型把其中的指示当成了指令，那么落到执行层的代码就已经不是“用户想要的代码”了。本文的口径是：假设提示防护全部失效，假设这段代码的作者带着意图。只有这么定，设计动作才不变形——按“代码大概率是好意”来设计，所有约束都会写成“建议”。

在这个前提下，代码能伤害宿主的方向就那么几类：读走不该读的文件、把内容送到外部、耗尽某项资源、修改宿主状态、留下可以再被触发的东西、横向移动到编排层。这六类是后面所有策略条目的索引——每一层约束都该能回答“它挡的是第几类”，答不上来的约束通常是给人看的装饰。

输入不可信：数据也是攻击面

执行不只带代码，还带输入：用户上传的附件、上一次工具调用的返回、代码从指定位置读到的数据。很多人把输入当哑数据，但它至少能造成三件事。一是体积冲击——由上千个小文件组成的归档，解压后能膨胀几个数量级，而解压若发生在沙箱外的工作区准备阶段，受害者就是宿主。二是路径语义——文件名里的相对片段、归档里的目录结构、符号链接，都能把“读一个输入文件”变成“读宿主上任意文件”，所以链接解析之后仍在白名单内必须做成硬检查，不能指望代码自觉。三是格式陷阱——超深嵌套的结构化文本、非法字节序列、畸形编码，会让沙箱外部的预处理程序先于沙箱崩溃。

由此得到一条原则：不可信数据的处理顺序本身就是边界。凡是解析不可信输入的环节，都要放在与代码执行同等强度的约束之下；校验在沙箱外、执行在沙箱内，等于把最脆弱的部分留给自己。

依赖不可信：取件动作发生在执行期间

模型写代码时会随手引入一个包，而包的取得动作常常就发生在执行期间——一句安装命令背后是一次仓库交互。于是依赖引入三类问题：一是供给完整性，你拿到的包未必是你以为的那个包，仓库里同名的、拼写相近的、刚被别人注册掉的包都可能出现在依赖树里；二是供给可用性，仓库慢、镜像缺、网络被策略挡掉，都会让一次正常执行以失败收场，而且失败形态和“代码写错了”混在一起难以区分；三是缓存把一次性变成长期——为了快一点而缓存复用的依赖，一旦被写入恶意内容或者被上一次执行的产物污染，投毒就会跨过执行边界，把选择一次性环境省下的麻烦重新请回来。

时长不可预期：这是最容易被漏掉的一份

人写代码时会本能地估计“这大概跑几秒”，模型不会，它的输出里没有复杂度承诺。要跑三天的代码和要跑三毫秒的代码，语法形状完全可以一样：无界循环、每次递归复制自身的调用、等待一个永远不会到来的网络响应、或者两层循环各开一个线程。更麻烦的是纯计算型失控既不读文件也不联网，前面几类策略一条都拦不住。所以时长要独立成一份不可信，配一套独立机制：绝对上限、空闲上限，以及在系统层面真的会把资源掐断的强制动作，而不是只在编排层记一笔超时日志。

边界之外：这一层挡不住什么

还要说清楚这套设计不解决什么。内核与虚拟化管理层自身的缺陷不在本文范围内，我们只把暴露给代码的内核接口面收窄，不声称消除。同宿主其他执行环境之间的资源干扰与侧信道，只能靠密度控制缓解。供应链上游投毒，只能靠固定来源、完整性校验和缓存治理压缩窗口。至于模型被操纵之后写出完全在策略允许范围内的坏代码——把用户数据整理成一段文本，发给一个白名单内的域名——这属于语义层，边界策略拦不住，只能靠出口名单收窄与人工复核。

知道边界在哪里，才知道出了事该往哪里查——这也是最后那一节留痕设计的出发点。

隔离层次选型：从进程到微虚拟机

选型之前先把“隔离强度”拆开。代码与宿主之间总共享某些东西，值得问的只有三个：共享不共享内核；能看到宿主上的谁和什么；能调用哪些系统能力。层次的区别不在“更安全一些”，而在边界画在哪条线上，以及画在那里要付什么。

进程与用户隔离：把边界画在权限位上

最轻的做法是每次执行一个独立进程：独立的 uid 与 gid、独立工作目录，CPU 时间、内存、文件尺寸与进程数由资源上限约束。系统调用面基本全开，宿主上其他进程的可见部分也照样看得见。

它确实挡住了不少东西：权限位成了真正的门，不同 uid 的执行环境读不到对方的临时目录，记账粒度落到进程组上。但它的成立条件是宿主纪律极好——不能留下任何对这个 uid 可读的敏感文件，不能留下可写的共享目录，而这两条在多团队共用的机器上几乎守不住。好处是它几乎没有启动开销，也没有镜像与内核维护负担，因而是所有更重方案的对照组，适合内网可信脚本、开发调试，以及嵌在更重环境里充当内层。

容器：把边界画在视图与能力上

容器多做了三件事。用命名空间把挂载点视图、进程视图、网络栈、主机名与进程间通信的可见范围收窄成一份副本，于是代码看见的文件系统树、进程表和网络接口都是它自己那一份。用控制组把 CPU、内存、进程数量、块设备吞吐变成有硬上限的配额，而不是事后统计。用系统调用过滤和 capability 收敛把“能做的动作”从全量减到一个列表，同时把 root 名义上保留着但把特权动作逐条摘掉。

这里要点破一句常被误读的话：容器不是安全边界，指的是所有容器共用宿主内核，内核的代码仍在那条路径上；命名空间和过滤缩的是接口面，不是把接口换掉。它挡的是“看见”和“随手动”，挡不住“内核本身被推到异常状态”。代价是实打实的：镜像的构建与分发、宿主上的容器运行时维护、rootless 形态带来的额外配置面，以及当执行密度上去之后每笔执行的固定开销。

微虚拟机：把边界画在虚拟化接口上

微虚拟机的思路是不共享内核：给每次执行（或者每小批执行）一个自己的内核，代码与宿主之间隔的是虚拟机管理接口而不是系统调用。这条线比上一条远得多，因此它把“内核缺陷”这一整类问题从共享面里挪了出去。

代价同样具体：启动路径比容器长，因为要加载一个内核；内存要预留而非按需回收，密度上不去；guest 内核本身成了一个需要维护与加固的组件，补丁负担从宿主一侧挪到镜像一侧；设备直通与加速器接入更麻烦。还有一条常被忽略的纪律：虚拟化了不等于放开里面——guest 内部仍然要做用户隔离、收窄系统调用面、不要把宿主块设备或目录直接挂进去，否则边界退化成“多了一层但什么都能碰”。

WASM 运行时：把边界画在能力授予上

WebAssembly 类运行时的隔离模型和前三者不同向。前三者是“默认什么都能做，然后逐项关掉”，它是“默认什么都不能做，然后逐项授予”：实例天生只有一段线性内存和一组由宿主注入的导入函数，没有文件、没有网络、没有进程，想要就得宿主给它接口，而宿主给它接口的那一刻正好是做授权判断的那一刻。这个性质对 Agent 场景非常友好，因为它把“要不要允许这次打开这个文件”变成了宿主必须显式回答的问题，而不是代码自己去碰运气。

代价集中在生态。不是所有代码都能进去：依赖原生扩展、需要完整 POSIX 语义、要起子进程或监听套接字的库，都得运行时或宿主先提供对应能力面。Python、TypeScript 这类任务通常靠把解释器编译进去、或者在能力接口上重新实现一部分标准库来跑，行为与原生环境有差异，模型的先验知识会在这里踩坑——它会写出语法正确却在这个环境里跑不通的代码。调试与观测的手段也和操作系统那一套不通约；能力接口一旦做宽，前面那点优势就还回去了。

层次可以叠加，选择看最坏情况

这几层不是单选题。常见组合是微虚拟机做外壳、内部再给一次执行独立的视图与配额，或者 WASM 做内层、外面套一层轻量虚拟机兜底。选择依据只有一个问题：这段代码最坏情况下能碰到什么。答案是“宿主内核的系统调用全集”时，不管它叫容器还是叫沙箱，都不该用来跑模型现写的代码；答案是“只有宿主显式授予的几个能力”时，里面是进程级隔离也够用。

下面这张决策表是我们内部评审时逐条对着填的，阈值与列名都是团队约定示例。

文件系统策略：只读根、临时层与白名单

文件系统是代码最先摸到的东西，也是最容易在一句“简单点”里被放弃的地方。做法是把所有路径划成三块，划分依据不是目录名，而是“这块内容在下一轮执行里该不该还在”。

只读根是镜像那一套：解释器、标准库、预置依赖、运行时工具，全部以只读方式呈现。这一条的价值不在防读取，而在防写入——代码改不动自己的运行环境，就没法把“下一次执行会加载的东西”变成攻击载荷，也就堵住了持久化那一类里最省事的一种。要让根只读，就必须承认有些任务确实需要写：临时可写层因此是只读根的配套，不是它的例外。

临时层承载代码自己的写入：中间文件、下载解压的垃圾、日志、崩溃转储。它有三条必须同时成立的约束。一是容量上限，而且要按字节与文件数两个维度限——只限容量，一个造千万个空文件的循环照样能把 inode 耗尽。二是明确的失效边界，执行结束即销毁，任何路径都不进下一轮，否则第七节说的缓存投毒会以另一种形式回来。三是介质选择：内存式文件系统快、销毁彻底，但写入直接计入内存账，和内存上限是同一笔预算；放磁盘则要把容量、写入吞吐与宿主磁盘保护一起考虑。别用一个不限额的临时目录，那是把宿主磁盘当产物。

白名单挂载是唯一被允许进入执行环境的“外部内容”。我们只留三个位置：一个只读的输入位、一个只写的产出位、一个受控的缓存位。所谓只写，是指代码可以往那里写，但代码读不到上一轮留下的东西——产出通过一条独立的取回通道被外部拿走，而不是让代码把工作目录当成检索库。

白名单的难点不在名单，在展开。四件事必须做：路径在解析之后仍在名单内，符号链接与硬链接都能让一个看着在名单里的名字指向名单外，所以检查要放在解析之后；挂载传播要关掉，否则环境里的挂载动作可能反向影响宿主；uid 与 gid 的映射要想清楚，同 uid 直挂会让代码写出的文件在宿主上属于另一个服务的用户；设备节点与伪文件系统按最小集合给，不要为了“有些库需要”就把整棵宿主目录树挂进去。

还有一条常被当作细节：输入数据的展开要在这套文件策略之内做。把归档解压到宿主上的临时目录再挂进去，等于让解压跑在边界外，而解压恰恰是最容易出体积与路径事故的那一步。

网络出口策略：默认拒绝，按需开洞

网络是外泄与横向移动最近的路，也是任务真实需求最常撞上的墙。我们的默认值很硬：拒绝一切出站，代码不会拿到一个“能连通外部”的网络栈；要访问外部，走一条明确授予的路径。

授予的方式不是给代码加权限，而是让它面对一个代理。执行环境里只放一个受控转发入口，域名解析与连接建立都由代理侧完成，代码只能说出“我要去这个主机名这个端口”，说不出“我要去这个地址”。这个差别很关键：按域名授权却不接管解析，代码就能用一个写死的 IP 绕过名单；代理拿到域名之后先解析、再对结果判一次，名单才算落到实处。判定里必须有一条：解析结果落在环回、私有段、链路本地段等内部保留段时一律拒绝。这一条挡的是借沙箱的手去够沙箱本不该够到的地址，其中最要挡的是链路本地的元数据服务地址——模型写出的代码里出现“取一下当前实例信息”这种无辜动作的概率，比任何人以为的都高。

域名与端口白名单要按任务模板给，而不是按全局给。全局名单只会随需求增，两年后你得到的是一个什么都能访问的名单和一份没人读的配置文件。更好的做法是每个任务模板声明它需要的最小出口集合，全局配置只做上限裁剪。端口也要限：只放行约定的几个传输端口，就能把合法域名背后那些奇怪协议挡掉。配额也别忘——并发连接数、新建速率、总字节数，任一项不限，一段失控的抓取循环就能同时打爆出口和别人的预算。

资源与时长上限

第三节的控制组和第四节的容量约束解决的是“看得见”，这一节要把它们变成一组具体维度。值得单独设上限的资源有六项。

CPU 要分两种形态：算力配额决定它多快、抢别人多少，绝对 CPU 时间上限决定它最多算多久。只配前者，一段死循环会以低优先级跑满墙钟，把执行池占死。内存要给整个执行组设上限，并留意计入口径——只盯常驻集合容易低估，写进内存式临时文件系统的量也算同一笔预算。进程与线程数上限防的是失控繁殖：复制进程与创建线程没有显式成本，不设数字就是不设限；打开文件数与套接字数是同一张脸上的另外两个孔。文件尺寸在第四节说过，只补一句：限额要按组而不是按目录，否则换个路径就绕开。最后是墙钟，它和 CPU 时间是两件事——卡在未被放行的连接上的代码几乎不耗 CPU，却会一直占着执行池。

空闲超时是墙钟之外容易被忽略的一维。它的判据不是“没有输出”——安静地算五分钟完全合法——而是“没有任何进展”。可用的进展信号是系统调用统计、文件写入增量、网络字节增量、子进程存活变化这一类量的组合；把“无标准输出”当判据会误杀大量正常任务。这套判据一定有误判率，所以它的定位是提前收割明显僵死的执行，而不是替代墙钟硬上限。

阈值只能来自历史分布。做法是先把限制放到最松，跑一段真实任务，按执行类型看分布，把上限设在覆盖绝大多数正常执行的位置，接受少量误杀，并在失败原因里把“因上限终止”与“代码报错”分清楚——混成一个执行失败返给模型，模型就会回头去修一段本来没问题的代码。配置里的数字一律标注团队约定示例，因为把某个团队调出的经验值直接抄给另一批任务、结果一半执行被误杀，这种事故我们见过不止一次。

依赖与镜像供给：预置与现拉之间

模型写的代码会引用库，而库从哪来这件事会决定沙箱一半的形状。两条路各有账。

预置是把可能用到的东西装进镜像。优点是执行时长不出任何网络动作，启动路径可预期，供给完整性在构建那一刻就固化；缺点是组合爆炸——镜像要么厚到没人维护，要么薄到模型随手写的库不在里面，后一种失败在用户看来就是“这系统老说找不到包”。现拉相反：什么都能装上，代价是执行时长里混进一段你完全不控制的时间，以及下面那点投毒面。

我们的取舍是按任务模板分：高频模板走预置，长尾走现拉，而现拉必须过一道受控的安装代理——来源固定在少数允许的仓库（示例里写成占位符），安装动作发生在沙箱内但出口走代理，落点只有缓存目录，代码可见的目录里不写任何东西。绝对不要让代码自己带着凭据去访问仓库：凭据放在监督者一侧，代码只提交“我要这个包”这个意图。如果配置里出现一段明文的令牌，那它已经不是秘密了。

缓存是这里唯一的长期状态，必须单独设防。缓存键要包含来源与内容摘要，只按包名建键等于允许同名换芯；缓存要可撤销，撤销之后不依赖任何残留即可重建；呈现给代码的缓存目录只读，写入由监督者做，否则一次执行就能往缓存里放东西并影响后续所有执行——那正是把一次性省下的麻烦重新请回来；共享缓存要有明确的失效与重解策略，不能永久有效。

还有一点关于冷启动：为了压延迟，可以预先构造好一批环境放在池子里，但池子里的环境必须是空白的——没有上一轮的输入、产物、临时文件和任何身份凭据。预热的是机制，不是状态。

端到端执行链路

把前面几层串起来，一次执行的动作序列大致如下。图里的分支不是异常路径，而是设计里必须预先想好的三条正常结局：正常完成、超限终止、被策略挡住。

flowchart TD
    A[编排层提交代码与输入四元组] --> B[按任务模板装配策略]
    B --> C[构造环境：只读根、临时层、白名单挂载]
    C --> D[在边界内展开输入并做路径校验]
    D --> E[启动执行：配额与出口策略同时生效]
    E --> F[监督者监视：墙钟、空闲、配额、被拒动作]
    F -->|正常退出| G[从产出位取回文件并做体积与类型校验]
    F -->|超限| H[分级强制终止]
    F -->|策略拒绝| I[记录意图并终止]
    G --> J[输出截断、过滤与结构化封装]
    H --> J
    I --> J
    J --> K[销毁环境：临时层、身份、租约全部回收]
    K --> L[把结果与原因码交回编排层]

图里有两处刻意设计。一是策略在启动之前就已生效，而不是启动之后再限制它——环境构造完成那一刻起，出口和配额就该是收紧状态，任何“先放开再收紧”的窗口都会被最短命的执行撞上。二是三种结局走同一条收尾路径：销毁、留痕、返回。失败执行不留尾巴，是这套链路能长期跑下去的前提，也是第十节取消语义能干净实现的原因。

执行结果回传：截断、格式与过滤

一次执行的产物有三类：标准输出与标准错误、退出状态、代码主动写出的文件。它们都要被压缩成模型能消化的东西，而消化这一步本身就是安全边界的一部分。

体积是第一道。标准输出要有硬上限，而且要字节与行数双限——不设行限，一行两千万字节的输出照样撑爆下游。截断上，保头加保尾加中间省略比只保头有用，因为错误信息常在末尾、输入回显常在开头。更要把截断本身告诉模型：原始多长、丢掉多少。不加声明的截断会让模型以为它看到了全部，进而基于一个不存在的完整输出做下一步推理，这比执行失败更难查。文件产物默认只回传清单——路径、大小、类型、摘要——需要内容时按授权取回，不要把整个目录灌进上下文。

格式上，回传给模型的应该是结构化文本而不是原始日志流。要做的处理是去掉终端控制序列、限制栈深、把依赖库内部的帧折叠成一句摘要。这不是为了好看：原始栈里既有大量无意义的重复，也有宿主绝对路径和依赖目录结构，而后者本身就是一种信息泄露。

过滤是最容易被推迟的一步，而推迟到展示层就等于没做。默认不该出现在回传里的有：宿主绝对路径与环境标识、环境变量的值、凭据形态的字符串、不属于本次任务输入的文件内容。判定要走两路——按内容形态匹配，加上按来源与访问路径匹配——只做其一都会漏。过滤要计入留痕——拦了几条、拦在哪一类——但不保留被拦下的原文，否则过滤只是把敏感数据换个地方存。还有一条纪律：失败信息也是产物，同样要过截断与过滤，不要把未处理的堆栈原样塞回模型。

超时与取消语义：和上层循环怎么配合

终止一次执行有三种原因，它们必须是三个不同的值：代码自己结束了、被上限收割了、被上层取消了。把后两种混成一个超时，上层就分不清该重试还是该放弃。

取消要真的传得下来，实现纪律只有一条：不可信代码不会配合你的取消协议，所以取消要由监督者执行，不能指望代码响应协作式信号。收尾是分级的——先对整个执行组发终止请求，给一个很短的宽限期，再按组强制回收；只按单个进程回收会留下孤儿进程继续消耗配额。回收后还要复查资源真的释放了：内存式临时文件系统的残留、仍然占着的套接字、没关掉的挂载，都属于环境已销毁但账没清。

重试语义要单独立一条规则：超时不等于可重试。判断依据不是等了多久，而是这次执行有没有留下外部效应——写过产出位、发起过被放行的出站连接、动过共享缓存，都属于不可盲目重放。重放必须新建环境，绝不复用上一个被终止环境的残骸。

和上层循环的配合才是这套语义的价值。模型不知道自己的代码要跑多久，但看到“第四分钟被墙钟收割，此前已处理约一千二百个文件”这样的返回，它有可能把下一轮改成增量式写法。所以取消与超时的返回值要携带可推理的线索：终止于哪个阶段、撞上哪个上限、哪一类动作被挡，而不是一个空壳错误码。上限数值要按任务模板可调——全局设一个 60 秒，结果就是所有稍重的任务都在稳定失败，而仪表盘上看起来一切正常。

日志与取证留痕：记什么，不记什么

留痕的目的只有一个：让三个月后的某个人能回答两个问题——这次执行当时生效的是什么策略，它实际做了什么。绝大多数系统只回答第二个，而策略会变：没有策略快照的审计日志，事后读起来像拿今天的规则评判昨天的行为。

该记的是元数据与事件，不是数据。执行标识与关联链要完整：哪次会话、哪个任务模板、代码由哪个生成侧产出、代码的摘要与长度。环境摘要记隔离层次与镜像标识。资源维度记实际用量的分布而不只是终值，它是第六节那些阈值的唯一校准来源。结局要落到可区分的原因码上，与第十节三种终止原因对齐。事件里最有价值的一类是被拒动作：被挡下的打开、被挡下的出站、被顶到的配额上限——它们平时一行都不好看，出事之后是唯一能回答“它本来想去哪”的数据。

不该记的要说得同样硬。输入与输出的正文不属于留痕，它们是数据——把数据塞进审计日志，等于为方便排查新建一份敏感数据湖，而且是一份没人做权限的数据湖。环境变量值、凭据形态的字符串、产物文件内容都不进留痕。代码全文默认也不留：只留摘要、长度与语言标识，需要复盘时按授权单独取回，并对取回动作本身留痕。

有一条纪律最容易在第一天被破：审计通道要独立于沙箱，代码不能写自己的留痕。把审计输出丢进临时层或产出位，等于让被审查者保管审查材料，一次执行就能抹掉自己的痕迹。同理，代码自己打的日志要按不可信来源单独存放与标注，读的人不用猜哪一行是环境写的、哪一行是被约束者写的。

留存期也要分层：策略快照与资源用量这类元数据可以留得久，它没有敏感性；被拦下的原文、代码全文、输入输出的正文，如果一定要留，就要有独立的访问控制和明确的到期清理。

小结

前面十节其实只做一件事：把开头那四份不可信——代码、输入、依赖、时长——压成四条不变量。默认拒绝再逐项授予，而不是默认放开再逐项封堵；策略先于代码生效，环境构造完成时边界已经收紧；一次性优先于复用，临时层、缓存、预热池这类跨执行的长期状态都要单独设防；边界要能复原，出了事能回答“当时允许什么、它试图做什么”。

这套设计没有终局答案。模型写的代码会更长、任务会更重、依赖会更厚，笼子于是只能跟着变厚，启动路径与密度之间的拉扯也会一直在。但变的层次是隔离机制，不变的是那份信任关系：跑在里面的东西，不是人写的，也没人读过。承认这一点，比选哪一种笼子更能决定系统的实际安全水位。
