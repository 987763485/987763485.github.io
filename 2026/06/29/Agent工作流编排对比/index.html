Agent 工作流编排对比

本文属于《Agent 智能体开发》第 17/55 篇
上一篇系列目录下一篇

Agent 的能力上限由模型决定，但能不能上生产，往往由模型外面那层执行外壳决定。本文把常见的编排做法归成三种范式：代码式链、声明式图、状态机加事件，只在机制层面比较差别。对比给的是维度与自家 PoC 里的验证动作，不给排名结论。

编排为什么值得单独谈

一次 Agent 调用看似只有一问一答，真实轨迹里却混着模型推理、工具调用、外部写入和人工等待。模型再强，它只在某一次请求里“活着”，请求一结束就什么都不剩。要持久化、能重放、可审计，靠的都是外面那层执行外壳：把每一步的输入输出落盘，能在进程被杀之后从中间状态接着跑。

这也是编排值得和框架选型分开谈的原因。选型那条线在《Agent 框架对比与选型》里已经展开，本文不重复它的流程与维度清单。编排关心的是另一件事：控制流放在哪里，状态由谁持有，副作用由谁去重。

划界口径：编排的最小闭环由 951 负责，LangGraph 的状态机写法由 771 负责，LangChain 链式用法由 839 与 862 负责，CrewAI 与 Eino 的用法由 994 和 943 负责；本文只谈范式的机制差别，不复述 API 与用法教程，也不给编排层的性能数字——吞吐、延迟、开销都高度依赖自家工具链。时间口径：本文写于 2026 年 6 月末，LangChain 与 LangGraph 都已在 1.x 当期版本线，OpenAI Agents SDK 仍是 0.x，CrewAI 与 AutoGen 偏多智能体协作的表达方式，Eino 更贴近 Go 服务端把编排做成组件管道的思路。

外壳要跑在别人的运行时上：Node.js 26 还是 Current 线、尚未进入 LTS，24 才是 Active LTS；Go 侧当期是 1.26；PyTorch 2.12 可作为当期主线，但本文不把结论绑到它的某个特性上；再往下是 Kubernetes 1.36 的口径。

范式一：代码式链

最朴素也最常见：整条流程就是一段宿主语言代码。Python 或 TypeScript 里写一个异步函数，循环调用模型，用条件判断走分支，用迭代消费工具结果，状态就是函数栈上的局部变量。

优点全在工程熟悉度上。断点可以打在流程中间，异常用普通的捕获语句处理，类型检查器能在编辑期发现“上一步返回字符串、下一步当列表用”这类错误；子函数能在别的业务里复用，单元测试拿 mock 就能跑，任何后端工程师都能读，不需要先学一套图语法。

缺点都集中在“以后才疼”。第一，状态活在内存里：进程一重启，跑了四十分钟的批处理就归零，要续跑得自己把中间变量序列化到外部存储，再自己判断哪些副作用已经做过。第二，可视化弱：给人看的流程图和运行时真正走的路径是两套东西。第三，非作者读不懂：链的形状藏在分支与闭包捕获里，接手的人要通读一遍才知道有几条路径。第四，人工介入要自己搭：停在某点等审批，等于把等待态外置到存储和队列里，本质是在手写一个状态机。

代码式链在当期生态里活得很好：不少 1.x 的链式入口仍是宿主语言的组合子，把函数换成框架提供的可调用对象，检查点与并行的语义就一起继承下来。问题不在代码本身，而在于谁来替你持有状态。

范式二：声明式图与 DAG

第二种做法把节点和边显式写出来：节点是一件可命名的事，边是谁完成后谁才能开始，分支用条件边表达，汇聚用显式的 join 表达。流程的形状不再藏在控制流里，而是一份机器可读的定义。

优点有三条。可检查：图定义能静态校验，孤立节点、不可达分支、意外的环、汇聚点上游不齐，都能在上线前报错。可并行：无依赖的分支可以并发调度，调度器看得到依赖，才谈得上把等待时间重叠起来。拓扑清晰：图本身就是文档，评审时讨论的是这条边该不该存在，而不是这段代码会走到哪一行。

缺点也三条，容易在扩需求时才暴露。循环与动态分支别扭：迭代到满足验收条件为止这种需求，要么把环画进图里，要么在外层反复调用整张图，两者都在削弱“这是一张 DAG”的直觉；分支数量由运行期数据决定时，静态图无从下笔。图爆炸：路径数按组合增长，十几个节点的图还看得完，几十条真实路径就没人能看全。错误语义常被忽略：一个节点抛错时，同时在跑的其他分支是取消还是跑完、部分结果要不要保留，多数图定义里没写清楚。

范式三：状态机加事件

第三种做法用两套词汇描述流程：一个有限的状态集合，加上一张“什么事件把哪个状态推到哪个状态”的迁移表，副作用只挂在迁移上，而不是挂在状态里。

优点正好落在前两种范式的短处上。长时任务语义天然清楚：要等外部回调就停在等待态，进程可以随时退出，因为“现在在哪一步”是一行可落盘的数据，不是内存里的调用栈。人工介入有地方放：暂停态是一等公民，审批人的决定是事件。恢复语义也清楚：重启后读当前状态即可。

暂停-审批-继续这条最常见的路径，用状态机表达是这样的：

stateDiagram-v2
    [*] --> Running
    Running --> Paused: 命中审批门
    Paused --> Reviewing: 审批人领取
    Reviewing --> Running: 通过并注入决定
    Reviewing --> Blocked: 驳回
    Blocked --> Running: 修正输入后重进
    Running --> Done: 全部步骤完成
    Done --> [*]

代价有两条。建模成本高：要把业务讲成状态和事件两套词汇，前期费时，状态划分一粗，迁移表就很难看。事件顺序与幂等要自己保证：消息重复投递、乱序到达，都得在迁移表里写明当前状态与事件不匹配就丢弃并记账，框架不会替你想这件事。

三种范式的三维对照

对照维度 代码式链 声明式图与 DAG 状态机加事件
控制流住在哪 宿主语言的分支与循环 一份图定义 一张迁移表
状态由谁持有 进程内存里的局部变量 运行时持有的共享状态对象 外部存储中的当前状态行
分支与汇聚 自己写并发原语 由依赖关系推导，join 需显式声明 事件到达触发迁移，汇聚靠状态判断
人工介入落点 自己搭等待态 由运行时提供的中断原语承担 暂停本身就是一个状态
停机后接着跑 全部自己实现 取决于运行时是否把每步落盘 读状态行即可继续

这张表只描述机制归谁负责，不含优劣判断。真正的取舍要看下面五个维度，以及在自家 PoC 里能不能验出你要的行为。

五个对比维度与验证动作

第一个维度是检查点与恢复：能不能从中间状态续跑，恢复后副作用会不会重复。代码式链里检查点是一份额外的手工活；图范式里它是运行时的一项能力，能不能到节点粒度各家不同；状态机范式里它几乎等同于状态行，恢复最便宜，前提是状态划得够细。幂等键由编排层生成并随状态一起恢复，比业务代码自己拼键名可靠。验证动作：跑一条含三次外部写入的流程，在第二次写入后强杀进程再拉起，数写入总次数。

第二个维度是并行与汇聚：分支能不能真并发、汇聚点语义是什么、部分失败怎么处理。代码式链自己搭并发，语义完全由你定义；图范式把依赖交给调度器，代价是汇聚规则常常写不清楚；状态机范式没有传统意义的汇聚，只有满足条件才迁移。验证动作：两条并行分支，一条快速失败，另一条按团队约定示例慢十秒，看外壳对慢的那条做了什么——保留、丢弃，还是整体失败，写成可重复的断言。

第三个维度是人工介入：落点在哪一层，决定等待期间要不要占用计算资源。代码式链最省事的做法是阻塞等，代价是进程不能退出；图范式靠运行时的显式中断能力，等待态可以落盘；状态机范式里暂停是状态、审批结果是事件、审批门是迁移的前置条件，表达直白，但每条审批路径都要预先建模。验证动作：让一个审批请求排队一天，中间把服务重启两次，看通过后流程能否自动走下去。

第四个维度是重放与可观测：同输入能不能复现，取决于你记了什么。要记渲染后发给模型的完整提示、工具调用的入参与返回、采样参数与随机性设置、每个分支决策依据的值。不一致分两层：模型调用本身有随机性，两次结果不同可以容忍；分支选择、工具入参、写入次数变了，说明编排层漏了记录。验证动作：留一份轨迹，隔一周用同一输入连跑两遍，逐步骤比对模型调用之外的记录。

第五个维度是取消与超时：取消是不是一条真信号，能不能传播到工具和子任务。代码式链里取消依赖语言自身的机制，能否穿透到工具实现全看运气；图范式要在节点级声明取消与超时的传播规则，否则父流程已退出、远端作业还在跑；状态机范式可以把取消建模成事件，让每个状态回答收到它该去哪个状态。验证动作：给一个会提交远端异步作业的工具发取消，看远端是被撤销还是继续推进，再看归属标识能否穿过重启被找回来；字段名本文自拟，叫它 owner_step。

五个维度都不必参考外部评测，全部能在自家 PoC 里跑出来；一套编排在任意一点上说不清自己的行为，功能清单再长也不必细看。

迁移成本与锁定

锁定不是一句“换框架很麻烦”，而是三样东西各自有多难搬。图定义最不锁定：它描述形状，语言中性，搬出去通常只是换一种表达格式；但分支条件一旦写成某运行时的表达式，或者宿主函数被直接嵌进节点，形状就跟着私有语义走了。状态 schema 最难搬：它带的远超形状，还有检查点的编码方式、历史是覆盖还是累积、并发写入怎么合并，这些语义在文档里常常只有一句话，落到实现里全是细节。工具绑定居中：接口这层被 MCP 标准化了不少，当前可用口径是 2025-11-25 修订；官方已给出下一轮修订的 RC，方向包括把异步任务归入扩展、增加发现类方法、简化会话与初始化握手、强化授权服务器校验、以元数据文档取代动态注册、把旧的 HTTP+SSE 传输与部分能力列入废弃并给出约 12 个月的移除窗口。这是草案，可能变动，本文不把它当作已生效结论，也不写端点拼写与字段名；再往后那一轮修订在本文日期尚未生效，不能当已发布引用。智能体边界另有 A2A v1.0.0 与 v1.0.1 两条已发布规格，能力包这层有 2025-10-16 的 Agent Skills，治理归属写在 2025-12-09 的公告里。

把退出成本当成选型维度，做法是一次反向 PoC：让最小流程把图定义、状态 schema 与工具绑定导出成纯文本，再用另一套宿主代码读回来、跑同一条轨迹并比对结果。导不出来或读回来跑不通的那部分，就是锁定的确切位置。

任务形态 更合适的范式 关键判断点 还要补的东西

小结

三种范式的差别，本质是责任归属的差别：状态归谁持有、并行由谁调度、暂停落在哪一层、取消由谁传播。任务形态决定你更愿意自己扛哪一层责任，这跟用哪个库没有关系。想看外壳的隔离与评测视角，可以读 Anthropic 工程栏目的 how we contain Claude、managed agents 与 agent evals 三篇，本文只给标题与栏目。本文只给维度与验证动作，不给排名：任何一条维度，都能在自家 PoC 里用半天验出来。
