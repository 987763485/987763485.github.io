AI 应用架构演进

很多团队复盘自己的 AI 应用架构时，写出来的是一部工具更替史：哪一年接了哪个框架、哪一年换了哪种检索方案。这种叙述回答不了真正有用的问题——我们上一次架构调整究竟是被什么逼出来的。本文改用阶段划分，每个阶段只问三件事：它替谁解决了问题、它新引入了什么问题、出现什么信号说明你该离开它。判据是问题的形状，不是版本号。

为什么要用阶段划分来叙述演进

编年体加工具名的写法有三个缺陷。第一是因果倒置：它把“当时刚好可用”当成“当时应该采用”，读者带走的是工具清单，不是判断力。第二是不可复盘：当有人问“如果不接检索会怎样”，编年体答不上来，因为它没有记录当时的约束、代价和备选。第三是不可迁移：另一个团队可以照抄同一条工具链，却抄不到触发条件，于是在自己的系统里实现了一个没有问题的解法——这是最常见的架构浪费。

本文的分阶段口径是责任边界的移动。阶段 0 到阶段 4 的编号只表示依赖关系，不表示先进与落后，也不表示某个阶段是“终态”。一个只做阶段 0 且做得干净的客服摘要系统，比一个跳到阶段 4 却说不清收敛判据的系统要健康得多。

判据我使用三条，任何一条为真才考虑阶段迁移：

  • 状态所有权是否改变。如果新阶段要求你把“任务进行到哪”这件事从调用方转移到服务方，那是架构变化；如果只是想换个更好的模型，那不是。
  • 失败是否需要新的语义类别。阶段 0 只有“输出不满意”，阶段 3 会出现“没有报错但没做完”，后者无法用前者的处置代码处理。
  • 错误是否已从输出质量问题变成系统行为问题。当一次故障的表现是“多花了钱、多写了数据”而不只是“答错了”，控制就必须进架构。

还需要划清一条边界：把系统切成层次、各层如何耦合与拆分，属于空间维度的问题，另有专文；本文只处理时间维度的阶段与迁移触发条件。框架的横向对比与选型评分也另有专文，本文提到某个框架只作为时代坐标，不作为推荐。

另一个容易被忽略的事实：阶段是叠加的，不是替换的。阶段 3 的系统里绝大部分调用仍然是阶段 0 的一次请求一次补全。所谓升级，指的是新增一条更难的主干，旧路径继续承担主要流量。理解了这点就明白低阶段的债为什么会拖垮高阶段：主干变难时，没人愿意回头补底层的质量控制。

本文写作时点的坐标只用于说明论证不依赖任何未落地之物：LangChain 1.3 与 LangGraph 1.2 属于刚发布的当期 1.x 更新；MCP 的最新公开修订仍是 2025-11-25 版本，官方修订仍在推进中，Registry 仍是预览；A2A 已有 v1.0.0 的跨实现表征，Agent Skills 自 2025-10-16 起把能力变成可分发单元。这些坐标一条都不构成升级理由。

阶段 0：单点调用

阶段 0 的定义很窄：一次请求换一次补全。输入由调用方在本地拼好，输出被当作一段文本消费，用完即弃，系统不记得上一次说过什么。它常被轻蔑地称为“调个 API”，但它是一个完整的、有适用前提的架构。

它够用的前提有五条，值得逐条写下，因为很多团队是在前提已不成立的情况下继续沿用这个形态：错误表现可被使用者当场识别，无需二次核验；不存在需要跨请求保留的状态；没有外部副作用，或副作用完全由调用方自己兜底；单次调用的延迟与成本稳定落在预算内；提示的正确性可由代码评审保证，即改提示的人就是写这段代码的人。

这一阶段的典型形态是模板化提示加结构化输出解析，价值在于把不确定性关进一个足够小的盒子：盒子有输入、有输出、有超时、有重试，其余都不需要。

但阶段 0 会积累四笔债，利息要到后续阶段才结算。

第一笔是提示词散落在代码里。表现是同一段提示存在于三个仓库的三个变体，改一次措辞要走一次发版，变体之间的差异没人说得清。这笔债在阶段 2 结算：当提示成为流程中一个可替换的步骤，你无法在不改代码的前提下换掉它。

第二笔是没有评测。表现是“看起来更好”成为提示改动唯一的合入理由。阶段 0 时可以接受，因为使用者就是评审者；到了阶段 2，一次提示改动会波及整条链路，你会在没有任何基线可对比的情况下做发布决定。

第三笔是没有成本控制。表现是没有按业务归属拆分的用量归因，账单只能按服务分摊，异常循环要到月底才发现。到了阶段 3，运行时长由任务自身决定，这笔债会直接从超预算变成生产事故。

第四笔是没有输入输出契约。调用方对输出格式做了大量隐式假设却没写成断言。格式漂移在阶段 0 是人看一眼就绕过去的小麻烦，在阶段 2 是下游解析失败、图执行中止的故障。

什么时候该离开阶段 0：使用者开始问“这个结论的依据是什么”；同一个请求需要跨多个信息源或多个步骤；输出不再由人阅读而由另一个程序消费；一个功能的正确性开始取决于“是否记得上一轮”。这四条里出现任意两条，继续停留在阶段 0 就是在用调用方的兜底逻辑掩盖架构缺口。

至于阶段 0 的成本与质量如何分开设定，也就是把便宜模型与强模型的调用组合起来，那是模型路由层面的问题，另有专文，本文不展开。

阶段 1：检索增强

阶段 1 的核心动作是把“依据”从模型权重移到外部语料：先用检索取回候选片段，再把这些片段作为上下文预算的一部分交给模型，让输出可指认。它解决的不是“模型不够聪明”，而是三件具体的事——答案可以给出出处、知识可以不改权重就更新、私有数据不必被训练吸收。

也正因如此，进入阶段 1 的团队从此拥有了一条数据产品线，而这条产品线的负责人往往和模型侧不是同一个团队。这是阶段 1 卡住最多人的真实原因，比任何技术难点都更常见。

它新引入的问题有五个。

第一是数据管道与新鲜度。切块策略、元数据抽取、增量更新、全量重建，每项都要有人负责。最危险的是删除传播：原文已撤回而索引里还在，系统持续输出一个曾经存在的说法——这在多数行业里不是质量问题而是合规问题。

第二是召回质量。错误类别变了：以前是模型答错，现在是该送到的片段没送到。两者修法完全不同，而缺乏归因的团队会去改提示——这几乎从不解决检索问题。分辨二者需要记录每次检索实际返回了什么，而不只记录最终答案。

第三是上下文预算。相关片段之间会互相挤占，塞得越多不一定越好，因为片段之间的注意力是竞争关系。常见失败形态是 top-k 调大之后，模型开始拼接互相矛盾的说法，而答案看起来比之前更充实。

第四是权限泄漏面，本阶段最严重也最容易被推迟的架构问题。检索是外部内容进入上下文的唯一通道，一旦访问控制只在展示层生效，模型就已经看见了不该看见的东西。正确做法是把主体的权限谓词下推到检索层，让“取不到”而不是“取到后不打”成为默认；权限模型的演进必须与检索同步，否则你会得到一个技术上很快、治理上不能用的系统。

第五是引用的工程成本。可点击的出处要求维护片段标识与文档版本的映射，而文档改版会让旧映射失效。

什么时候该离开阶段 1：一个回答需要多轮检索并携带中间结论；任务要求“先确认条件再执行动作”；需要跨多个源做取舍而不是合并；单一检索链路已经变成流程中的一环而不是流程本身。最后这条是主信号——当你发现“检索—生成”之外还有必须固化的步骤，你其实在人肉执行一个工作流。

评测指标怎么分层、发布卡点如何设置，属于评测体系范畴，另有专文；本文只强调一点：阶段 1 引入的“检索质量”与“生成质量”必须能在数据上分开，否则每次架构讨论都会退化成口味之争。

阶段 2：编排工作流

阶段 2 的核心动作是把一次调用变成一张有向的步骤图，步骤之间的数据传递、控制流与失败处置由代码承担而不是由人脑承担。它解决的问题很具体：阶段 1 后期，团队通常在用一份内部文档加几个脚本描述“先查 A、再判断 B、若是则调 C”，这个描述本身已经是架构，只是没有任何运行时来执行它。

编排框架的价值是把状态管理、重放、并行、超时这些通用难题收进库里；LangGraph 与 LangChain 生态都已在 1.x 主线并有当期更新。本文刻意不写其接口，因为接口差异远小于它带来的结构性风险：库的抽象会反过来变成你的业务模型。当“节点”“边”“检查点”开始出现在产品文档和需求评审里，说明你已把实现约束当成领域语言，这会在迁移时成为最大阻力。

阶段 2 新引入的问题有五个。

第一是状态与持久化。图执行的中间状态是一个新的持久层，有保留期、并发写与一致性问题，还有“这份状态算不算用户数据”的定性问题。会话字符串和图状态不是一回事：后者可能包含工具参数、外部返回的原始载荷与中间产物，敏感程度远高于聊天文本。

第二是取消与重试。一旦步骤里出现副作用——写工单、发通知、改配置——“重试”就从技术选项变成业务决策。同一封邮件发两次是可容忍的故障，同一笔退款执行两次不是。取消也一样：停止生成和撤销已发生的动作是两个数量级的问题。取消与副作用安全的设计另有专文，本文只强调它对架构分期的意义：如果你无法回答“运行到第 5 步时取消，世界是什么样”，你还不该进阶段 3。

第三是步骤级评测。端到端指标失去了定位能力。你会遇到“整体通过率降了三个点（示意值）但没人知道降在哪个步骤”的处境，这需要的不是更多指标而是每步的可判定断言。

第四是可观测。跨步骤的关联是硬要求：排查时需要重建“第 3 步的输入为什么是这个”。只有散落的日志行是不够的，因为图的执行顺序本身是动态的。

第五是长时运行的现实约束。步骤可能等人回来才继续，工作流的生命周期开始超过一次 HTTP 请求，于是你必须面对队列、续跑、部署时正在运行的实例怎么处理。这一步做不好，团队会把长任务拆成“人工分段执行”，架构收益被运营成本吃掉。

该离开阶段 2 的信号：分支多到需要人肉维护流程图，且流程图与代码开始不一致；加一个步骤要改三处地方；同一个子图被复制出两份并各自演化；需求开始用条件句描述你无法硬编码的分支。最后一条最关键，它意味着控制流已从可枚举变成不可枚举。

同时要警惕把编排本身当目的的反向停滞：图一直在长却没有新增决策点，这类团队停在阶段 2 且越来越慢，判据见反面清单第一条。

阶段 3：自治智能体

阶段 3 的责任边界移动是本文最需要说清的一件事：从“人定义控制流、模型填充内容”变成“人定义目标、工具与边界，模型在运行期决定控制流”。运行时长与调用次数不再是设计时常量，而是任务自身的属性。这就是它强大和危险的同源原因。

它新引入的问题有五个，每一个都需要新的控制，而不是新的提示词。

第一是不可预测的循环成本。预算必须成为运行期约束而不是事后账单。一个常见的最小守卫形态是这样的（阈值全部为团队约定示例，不构成推荐值）：

第二是工具权限与沙箱。工具从能被调用变成能造成后果；读写分级、参数校验、执行环境隔离是三层不同的东西，多数系统只做了第一层。把模型生成的代码放进执行环境也需要设计：要明确它能触达哪些网络、使用哪些凭据、看见哪个文件系统，以及产物如何回到主循环。Anthropic 工程栏目的《code execution with MCP》讨论的正是这一方向，本文只把它当作该问题已被主流工程实践承认的坐标，不复述结论。

第三是人工介入点设计。这不是加一个确认按钮。真正要回答的是四件事：哪些步骤的确认必须在模型之外完成（模型不能既是执行者又是自己行为的批准者）；介入超时的默认动作是终止还是降级；介入期间外部世界变了怎么办；批准之后的上下文如何续接而不把拒绝理由丢掉。同一时期的 Claude Opus 4.6、4.7 与 Sonnet 4.6 已是可选项，Anthropic 工程栏目的《long-running harnesses》处理的正是长时运行下的续接与恢复，但本文不写任何能力细节，因为介入点的设计质量不由模型档位决定。

第四是失败恢复语义。阶段 2 的失败有明确步骤号，阶段 3 的典型失败是没有报错、只是没做完，或者做完了但绕了很远。恢复的正确单位是任务状态而不是消息历史：从当前目标与已完成事实续跑，比重放对话历史更稳，因为历史里满是已作废的尝试。

第五是评测对象的变化。阶段 0 到 2 评的是输出对不对，阶段 3 还要评过程是否可接受：用了多少步、调了哪些工具、有没有越界尝试、停止得是否合理。《agent evals》这类工程实践值得出现在演进叙述里，正是因为它标志着评测从答案质量扩展到轨迹质量。

该离开阶段 3 的信号：工作流里开始出现无法收回的“让模型自己决定下一步”的分支；固定流程的任务开始需要中途改计划；步骤数在设计时无法枚举。

最后一句提醒：自治度是花钱买的，不是等级。每提高一档，换来的是覆盖面，付出的是可预测性与审计能力。把它当 KPI 的团队，半年后会回过头把自治度调低。

阶段 4：多智能体系统

阶段 4 的定义不是“用了多个模型调用”，而是存在多个各自持有上下文与预算、并能独立行动的智能体，它们通过显式表征协作完成一个任务。这个区别很重要，因为并行发起十次调用仍然是阶段 3 的一次运行。

它新引入的问题有五个。

第一是通信开销。传消息不是免费的：上下文要序列化、要压缩，压缩就有语义衰减，转发就有失真。最常见的失败形态是子智能体做得不错，但主智能体把它的工作摘要成了三段没有依据的话，最终质量低于任何一个环节。控制手段是把交接当契约设计：规定传什么、不传什么、哪些原始产物必须携带引用而不是描述。

第二是共享状态冲突。两个智能体同时修改一份产物，比并发更新一行数据库更难，因为“修改”的表示是自然语言。可行的做法是给共享可写对象指定唯一所有者，或退回到“只有一个写入者、其他人只提建议”，后者常常就够了。

第三是收敛判据。谁判断“够了，可以停”，判据本身由谁核验。多智能体系统里最贵的不是失败，是没有终止条件的成功假象。

第四是跨智能体的追踪与成本归因。一次故障横跨三个智能体，一份账单要归到某个业务；链路标识各用一套就重建不出因果。这是阶段 2 的可观测投资在此结算之处：当初没把关联标识打全，现在只能靠时间戳猜。

协议层在这里给出一份现实约束清单：A2A v1.0.0 提供了跨实现的任务与工件表征；Agent Skills 让能力可以作为单元分发；MCP 的 Registry 仍是预览、官方修订仍在推进。最后一条的含义很明确——跨组织的工具目录还不是可依赖的稳定基础设施，任何把外部工具生态接入押在预览组件上的决策，都该带一个可回退的自建适配层。

什么时候不该进入阶段 4，这四条判据比进入信号更重要：

  • 角色在设计时可静态分配且不需要中途改计划。那是工作流，用阶段 2 表达更便宜也更可测。
  • 单一智能体的瓶颈是模型能力或上下文长度而不是调度。拆分不会让模型变强，只会让每部分拿到更少的上下文。
  • 任务对一致性要求高，例如资金、权限变更。拆分会把审计成本乘以智能体数量。
  • 无法为每个子智能体写出独立的验收判据。局部无法验收，组合结果也无法验收。

该进入的信号只有三种：一个智能体的上下文被非自身职责的材料占满且检索解决不了；子任务需要不同的工具权限与运行环境，放在一起会让权限被迫取并集；并行带来的墙钟收益可以量化。协作模式的种类与拓扑另有专文，本文只回答什么时候值得承担它的开销；编码助手一侧的责任边界迁移同样是一条独立路径，另有专文。

迁移的实际动作

把“迁移”当成一次切换是危险的。更准确的描述是：一部分能力就地增量补齐，一部分结构必须重写，两者并行一段时间。

可以就地增量改的四项，共同点是它们作用在调用的两侧而不是调用内部：

  • 评测：给现有调用建基线不需要改架构，只需要固定输入集与判定方式，这是任何迁移之前的第一件事。
  • 可观测：补关联标识与结构化事件是加法，可逐服务推进。
  • 权限模型：把工具与检索的权限谓词从代码移到统一授权层，是接口收敛而非结构变化；但这一步必须早于更难阶段，否则新阶段会把越权面扩大到写操作。
  • 成本控制：用量归因与预算告警是旁路能力，不影响主链路。

必然重写的三项，共同点是它们改动了数据的形状与生命周期的所有者：

  • 状态存储：从会话字符串到图执行状态再到任务状态，三者的字段、保留期、敏感级别与访问模式都不同。在旧表上加列，通常只会让两套语义混在同一列里。
  • 会话恢复：恢复单位从历史消息变成目标加已完成事实，续跑逻辑无法靠重放旧历史实现。
  • 取消语义：从停止生成变成补偿已发生的副作用，需要为每类动作声明可逆性与补偿动作。这是一张新表，不是一个新分支。

迁移期间建议明确双轨运行，并把它的状态写出来：

stateDiagram-v2
    旧轨独占 --> 双轨并行: 新轨通过影子评估
    双轨并行 --> 新轨承接只读任务: 只读流量验收达标
    新轨承接只读任务 --> 新轨承接可补偿写: 补偿动作演练通过
    新轨承接可补偿写 --> 新轨承接不可逆写: 审计与回退方案签字
    新轨承接不可逆写 --> 旧轨下线: 连续观察期内无回退需求
    双轨并行 --> 旧轨独占: 任一退出条件不达标
    新轨承接只读任务 --> 双轨并行: 指标退化
    新轨承接可补偿写 --> 新轨承接只读任务: 补偿失败

双轨的做法要点有四条。新轨在验收之前不接管任何写操作；两轨共享同一份评测集，否则比较没有意义；切流按任务类型而不是按百分比，因为百分比切流会把难任务均匀撒到新轨上；两轨的观测进同一个面板，任何“只有新轨能看见”的指标都不能当验收依据。

退出条件要预先写死，不能靠感觉。一组团队约定示例：新轨在同一评测集上不劣于旧轨；所有不可逆动作有已演练过的补偿路径；关联标识在链路两端都齐全；成本归因能落到业务单元；有一位明确署名的负责人有权按下回退。缺任何一条，双轨就会永久化。

每一层的新增治理成本

技术债可以偿还，组织债只能重组。这是架构演进的真实代价，也是编年体叙述最常漏掉的一栏。

  • 阶段 1 新增：数据负责人。要有人对切块策略、新鲜度指标、删除传播时效负责，也要有一个评审节点能阻止他在没有版本标注的情况下上线全量重建。缺这个角色时，检索质量退化通常要等到用户投诉才被察觉。
  • 阶段 2 新增：流程所有者与改图权限。谁能改生产环境的图、改完谁复核、图变更是否需要发布窗口，这三个问题必须在有第二条重要流程之前回答。跳过它的团队会把流程改动变成只有原作者敢碰的东西。
  • 阶段 3 新增：工具权限审批链与介入点排班。前者决定新工具接入的速度，后者决定人工介入是不是一个真实可用的能力。如果批准介入的人只有晚上在线，你的介入点在设计上等于自动批准。
  • 阶段 4 新增：能力目录与协议同步机制。谁登记一个可被子智能体使用的能力、跨团队如何同步版本、一个能力的语义变更需要多少人同意。协议层治理正在移出单一厂商（Agentic AI Foundation 2025-12-09 的公告即此趋势），这是好事，但内部目录的所有权问题不会因此自动解决。

评审节奏上，一个可行的做法是把“阶段迁移”当作有独立决策点的架构变更，而不是实现细节：立项时写下触发信号，评审时核对信号是否仍然成立，验收时确认新增角色已有人担任。三个时点缺一个，就会出现“技术上已经在跑、组织上没人认”的架构。

回退设计必须在升级之前写，而且要回答三个具体问题：新阶段持久化的数据在退回旧阶段后是否仍然可读；已经发生的副作用是否可补偿；用户已授予的权限在回退后是否自动收窄。第三条最常被忽略——一旦系统开始持久化用户对某类动作的授权，取消语义就再也回不到阶段 2 的形态，这是本文所说的不可回退升级。

治理侧还有两个外部坐标。其一，欧盟 AI 法案的一般适用时点即将到来，而欧委会 2025-11-19 提出的数字 Omnibus（COM(2025) 837）目前只是一份提案，既未生效也未被推迟，把合规时间表当成确定值的架构计划都还不成熟；它对本文的实际含义是，阶段 1 的权限下推与阶段 3 的介入点，正是合规收紧时最容易被临时补做的两项。其二，运行时与集群层面的更新（Node.js 26 刚进入 Current 线、尚未成为 LTS，24 仍是 Active LTS；Kubernetes 按 1.36 口径讨论；Go 1.26 与 PyTorch 2.11 属当期主线）不改变责任边界，因此不构成一次阶段迁移。把基础设施升级写成架构演进，是治理评审里最常见的注意力错配。

反面清单：五种看起来该升级、实际不该升级的情形

  1. 把编排当目的。症状是图一直在长，但没有新增真正的决策点。核对方法：随机移除两个节点，看输出质量是否可测量地下降。不降则那是仪式，删掉它比给它加评测更划算。
  2. 为了多智能体而多智能体。症状是角色名取自组织架构或演示脚本，而不是任务分解。核对方法：给每个角色写一句独立验收判据，写不出来的角色就是装饰。
  3. 用自治掩盖缺陷。症状是模型答不好就加循环重试，直到“看起来对了”为止。这实质是把质量问题伪装成算力问题，成本上升而根因未动。核对方法：统计重复尝试后成功的比例——若很低，重试只是在制造噪声。
  4. 跳过阶段 1 直接做阶段 3。症状是智能体凭“记忆”给出依据，工具只用来执行不用来查证。这种系统上线初期看不出问题，直到有人问出处。核对方法：随机抽十次运行，检查每个关键结论能否指回一次外部取数。
  5. 把组件替换当阶段迁移。症状是评审材料写的是“换了框架”“升了运行时”“接了某个协议”，通篇没有一句关于责任边界的变化。核对方法：问三个判据（状态所有权、失败语义类别、错误性质）是否有任何一条被触发，都没有就只是一个普通发布。

这五条的共同点是它们都消耗迁移成本而不产生新能力。反面清单的实际用法是在评审现场逐条对照，任何一条命中就把议题退回“先说清触发信号”。

小结

阶段划分的好处是把讨论从“用什么”拉回“被什么逼的”。本文所有分界遵循同一逻辑：一个阶段的价值是它解决了上一阶段解决不了的问题，代价是它新引入的问题，而它是否值得，取决于触发信号是否成立、必备控制是否就位。三条判据——状态所有权是否改变、失败是否需要新的语义类别、错误是否从输出质量变成系统行为——比任何工具清单都耐用，因为它们不随版本失效；三条一条都没被触发的迁移，应当被识别为普通发布，少占用一次架构评审。

两个必须记住的结论。第一，阶段是叠加的，低阶段的债在高阶段结算，所以迁移的正确顺序是先补评测、可观测、成本归因与权限下推，再谈更难的主干。第二，架构演进的真实代价是组织性的：每个阶段都在新增一个角色和一个评审节点，没人担任这些角色时，新架构会在第一次复杂故障时退回“只有原作者敢碰”的状态——你付了演进的代价，却退回了演进前的能力。

留在原地也是一种决定，前提是把它写下来，也就是路线图里那几个“信号不成立就记录理由”的节点。缺这一步的团队，两年后会在一次事故复盘里重新发明这个论证。
