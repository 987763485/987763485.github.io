多 Agent 系统可观测性

本文属于《Agent 智能体开发》第 39/55 篇
上一篇系列目录下一篇

给单个智能体埋点，方法已经相对清楚：会话、步骤、模型调用、工具调用四级 span，关联键定死，日志先脱敏再落盘，成本按归属维度聚合。把三五个智能体放进同一个系统，这套方法就出现结构性缺口——四级 span 默认存在一条”主时间线”，而多智能体系统里没有主时间线：执行是分叉的，消息是乱序的，两个智能体可能在同一秒各自发起模型调用，也可能一个等另一个的回答一等就是四十秒。更麻烦的是，多数故障不是某个智能体报错，而是配合本身失灵：没人认领最后一步、两个智能体重复检索同一份材料、辩论收敛不了却被预算闸门悄悄掐掉。

本文只补这个缺口：拓扑怎么决定埋点形状、并发下 span 层级怎么定、跨智能体因果链怎么不中断、标识体系加哪几层、gen_ai.* 在未稳定状态下怎么用、哪些指标只有群体行为才显形、成本怎么归因、采样怎么改、观测数据怎么回流评测。三支柱怎么搭、单应用怎么埋点、阈值怎么定，此前几篇已讲透；协作形态与仲裁规则见《多智能体协作模式设计》与《多 Agent 分工与协商》，本文假设那套设计已存在，只谈怎么把它看清楚。

难度跳档在哪里

单智能体到多智能体，观测成本不是线性上升，有五个地方发生了性质变化。

第一，时间线从一维变成分支结构。单个循环里”第几步”是整数，天然有序；并发时全局没有一致步序，只有各自的局部序与若干条跨智能体因果关系。人仍然需要一个可读顺序，但它是重建出来的，不是采集到的——把重建当采集就会被乱序事件误导：日志里 B 的回复出现在 A 的提问之前，在异步系统里完全正常，却足以让人误判成逻辑错误。

第二，一次业务失败可以对应零次技术失败。每个智能体都给出合理中间结论，每个工具调用都成功，模型 API 全绿，但整体没有产出：交接消息丢了、仲裁条件永不满足、终止判定被某一句”我这边完成了”触发而另一个还在写。这类失败没有异常可捕获，只能靠结构与进度信号发现——单智能体观测里它是次要问题，这里是主要问题。

第三，成本与上下文开始共享且重复消耗。同一段长上下文被 N 个智能体各读一遍、各记一次输入 token；某个中间产物触发下游三个智能体重做。”总成本多少”好答，”这钱记在谁头上”没有唯一答案，必须事先约定归因规则，否则面板上全是假的精确。

第四，隐私与注入的暴露面被乘以智能体数。内容每多一跳，就多一次落盘、多一条可能进日志的路径、多一个可被污染的接收方。单智能体在出口脱敏一次就够，这里必须先决定：脱敏在每跳出口做、在统一管道入口做，还是两边都做。

第五，可复现性变难。轨迹由调度决定，谁先拿到租约、哪条消息先到，都会改变后续一切。观测数据因此从”排查线索”升级为”复现所需的最小事实”，留存字段要新增调度决策、消息到达顺序、租约授予与到期——传统埋点清单里根本没有这几项。

贯穿全部的一条原则：先假设系统会被问”现在到底进行到哪一步了”，再设计埋点。答不出这句话的系统，面板再漂亮也只是装饰。

拓扑决定观测形状

四种常见协作形态产生的轨迹形状完全不同，埋点方案照抄一定出错。设计取向本身在《多智能体协作模式设计》里已经讨论，本文只做一件事：把每种形态对应的观测难点与必答问题列清楚。

形态 轨迹形状 真正的难点 必须补的信号
监督者—执行者 浅而宽的树，分叉在派发动作 宽度：一次派发起十个执行者，树画得开但没人看得完 派生计数与配对计数——两数不等就是漏，比看任何单条链路都有效
流水线 带分支的线，最像传统微服务链路 排队与背压：某一环慢导致上游堆积，整体延迟涨而每环耗时都”正常” 队列深度与等待时长，不能只采处理时长
交接式 分段链，每段属于不同执行上下文甚至不同语言 因果链在交接点断裂，一次会话被三段独立追踪承接 交接事件与上下文透传，见第四节
辩论与协商 反复收敛的网络，步数事先不可知 看不出”有没有在收敛”：十八轮未收敛与十八轮才收敛的协商在指标上一模一样 轮次数、分歧度量、每轮改动内容、是谁让分歧缩小
共享黑板 前四种都可能叠加的通信底座 写冲突与来源丢失：谁写的、基于哪一版读的、有没有人同时改过 写入者角色、读取版本号、冲突事件

选型上的结论：不要为了”观测统一”把所有形态压成同一种 span 结构。正确做法是共用一套层级与标识骨架，然后每种形态加两三个自己的专用信号。骨架统一、信号分形，这六个字是本文对拓扑问题的全部建议。

span 层级：给并发补一根可读的主轴

单智能体的四级结构要扩成六级，多出来的两级正是本文的核心。

会话（一次端到端业务，最外层容器）→ 智能体运行（某个智能体在某个任务上的一次有始有终的执行）→ 步骤（该次运行内的一轮”决策—行动—观察”）→ 模型调用 → 工具调用 → 交接（跨智能体的边界事件）。

其中”智能体运行”是关键。它不是进程、线程或某个框架的对象实例，而是业务意义上一个角色的一段生命：从接到任务到交回结果。三个好处都很实际——它给出并发可读的分隔（十个执行者同时跑就是十个并列子节点，不必在交错的 span 里靠时间戳猜归属）；它是成本与配额最自然的挂靠点，限定预算和统计总开销都以它为单位才有意义；它还是失败恢复的单位，重试或换人重做时新运行是旧运行的兄弟而非子节点，”同一件事做了几遍”才能被计数。

“交接”这一级最容易被漏掉，也最不该漏。它是显式建模的边界事件，形如”把任务 T 从角色 A 交给角色 B”，本身几乎不耗时，却承载三件事：载荷摘要与字节数、送达与接收的时刻差、接收方的接受结果（接受 / 拒绝 / 超时未响应）。没有它，跨智能体链路只能靠时间戳近似拼接；有它，链路才有真正的因果锚点。交接 span 必须是父侧事件，不能寄生在子侧某个 span 里——下游可能永远不响应，那时子侧一个 span 都没有，父侧必须留下”我确实交出去了”的证据。

    S --> R2[智能体运行: 检索执行者]

图中只有一条实线主轴（会话），虚线是因果链接。层级树的父子关系表达的是”谁归属谁”，不是”谁等谁”——这一区分在下一节展开，混用是本文所知的多智能体埋点第一大坑。

还有一个容易忽略的层级设计：步骤序号按”运行”独立编号，不要用全局自增数。全局步序在并发下既无意义又会互相打架——两个运行同时递增同一计数器，你只会得到一串无法解释的跳号。运行内步序加运行标识才是可解释次序；需要全局顺序时，用事件时间戳与因果链接离线重建，别在采集时假装看得见全局时钟。

因果链：跨智能体的传播、断点与重开

上下文传播的标准做法是把追踪标识放在跨进程调用的载体里——HTTP 用 traceparent 一类的头，消息队列用消息属性。这套在同步调用链上工作得很好，多智能体系统里有四个断点会击穿它。

断点一：异步任务。任务进队列时传播上下文、worker 消费时起 span，多数框架都能做。真正的难点是上下文存活期：worker 里跑了二十分钟，上下文对象早被回收，后续步骤就丢了父链接。做法是把上下文当数据而不是对象——接任务时把父追踪标识与父 span 标识落到运行记录里，之后每个 span 都从这条记录重建，不依赖任何”当前上下文”的隐式状态。下面是 TypeScript 侧的写法，关键是上下文来自任务记录而非 ambient：

断点二：子智能体自己起一条新追踪。这常常是对的——独立采样、独立留存、独立基数，长任务共用一棵大树会把后端压垮。但两边都要留钩子：父侧在交接 span 上写 span link 指向子追踪，子侧根 span 反向 link 回父。link 与父子的区别必须讲清：父子会改变采样与聚合归属（子随父，算进同一棵追踪的时长），link 只声明”两件事有因果”，两边仍各自独立。跨智能体默认用 link；只有确实需要端到端总时长的同步等待场景才用真父子。硬要求一条：父子与 link 不能混用而不声明，否则同一系统里有的成本被算进根追踪、有的没有，成本面板永远对不平。

断点三：恢复与重放。进程崩溃、断点续跑、人工审批后继续，原上下文对象早已消失。恢复流程必须在检查点里存下追踪标识与运行标识，重启后按”同一运行继续”或”新运行成兄弟”两种语义之一接续，并在 span 上显式标注是哪一种。陷阱在于：重新生成追踪标识又不写 link，一次长任务就被切成毫无关系的两段，中间丢失的信号永久无法定位。恢复与重试语义见《Agent 失败恢复与重试》，本文只强调观测侧那条硬约束——检查点必须带追踪上下文，恢复语义要显式打标。

断点四：调度器”代答”。有些系统会在下游超时后由编排层伪造一个结果回给上游，让循环看起来走完了。技术上很优雅，观测上灾难——链路上出现一个没有真实执行者的结果。若保留这种设计，必须给交接 span 打上”合成结果”标记与原因，绝不能让它长得和真实响应一样。否则你把超时降级当成正常完成，质量指标会一路虚高。

最后一条纪律：跨智能体只传标识，不传内容。上下文载体里放追踪标识、任务标识、会话标识与必要的枚举状态，绝不放提示词或中间结论；后者走自己的存储，用标识去点查。这是隐私与成本同时收敛的做法，也是后文”留存与采样”一节里脱敏策略的前提。

标识体系：六类 ID 与它们的用途边界

单智能体的三层标识（追踪、会话、步骤）在多智能体里不够用，缺的都是”归属”类标识。本文建议固定六类，一次定死，全项目共用。

标识 语义 谁生成 必现位置 能否进指标标签
追踪标识 一条技术链路 采样入口 所有 span 否
会话标识 一次端到端业务 接入层 span 属性、日志字段 否
任务标识 一件需要被完成的活 拆解器或监督者 运行、交接、步骤 否（基数无上限）
运行标识 某角色对某任务的一次执行 智能体运行时 该运行下全部 span 否
角色标识 智能体的稳定名字 配置/代码 运行、交接、指标标签 是（有限枚举）
交接标识 一次跨角色事件 派发方 交接 span 否

最关键的两条是任务标识与角色标识，它们共同支撑起多智能体特有的两类问题。

任务标识解决”这件事到底做完没有”。会话是用户视角的容器，一个会话里可能有三个任务；任务是可判定完成的单位——它有明确的成功条件、预算上限与归属者。进度类指标（多少任务在跑、多少停滞超过阈值、多少在等待他人）全部挂在任务标识上。没有任务标识时，你只能观测到”这个会话花了很久”，却答不出”会话里的哪一件事被卡住了”。

角色标识解决”该找谁负责”，并且是这六类里唯一适合做指标标签的高价值维度。前提是它必须来自有限枚举：写在配置里、进版本控制、变更走发布流程，绝不允许由模型即兴生成或从提示词里解析。理由很直白——如果角色名可以动态出现，它就等价于一个无上限标签，基数爆炸先从聚合层开始垮。同理，智能体实例的编号、任务的 UUID、子任务的标题这类字段属于追踪与日志，用于点查，永远不进指标。

命名纪律还有第二条：同名字段跨语言必须同源。Python 侧叫 task_id、TypeScript 侧叫 taskId、Go 侧叫 TaskID，落到后端就是三个字段，聚合查询要写三套。做法是维护一张内部契约表（字段名、类型、必填性、允许取值），由一个共享包在三端各自重新导出，变更走同一次发布。这张表也正是下一节映射到语义约定的输入源。

语义约定：gen_ai 属性注册表的现实用法

OpenTelemetry 的生成式 AI 语义约定（即 gen_ai.* 属性注册表）覆盖了操作类型划分、模型标识、token 用量、工具名与调用标识、会话标识等一组概念。必须先把状态说清：这套约定当前的稳定性标注仍是 Development，属于未稳定规范，仍在演进，属性名、语义与归属都可能变动。本文写作时注册表里已有的名字（如 gen_ai.operation.name、gen_ai.provider.name、gen_ai.request.model、gen_ai.usage.input_tokens、gen_ai.usage.output_tokens、gen_ai.tool.name、gen_ai.conversation.id 等）可以借用，但借的是词汇而不是契约。注册表没列出的东西——尤其是多智能体特有的任务标识、运行标识、角色标识、交接标识——不要硬造属性键，一律走内部命名空间。

落到代码上就是”两段式”：埋点处只写内部字段，导出前由一个映射层翻译成语义约定的名字。借词汇是因为它让不同厂商的工具之间可比，隔离结构是因为规范会动，缺口补在自己的命名空间里是因为它不会短期出现。

映射层同时是隐私与成本的闸门：白名单之外的属性默认丢弃，内容类字段（输入消息、输出消息、工具参数与结果）默认不进 span，需要时以引用标识指向独立存储。语义约定中确实存在描述输入输出内容的条目，但在多智能体场景下，内容在链路里被复制多次，全量落 span 会让追踪通道迅速被撑爆——本文建议把它作为按需开启、带审计、会自动过期的例外，而不是默认。

指标侧同理：注册表覆盖了客户端操作时长与 token 用量这类概念，但”每任务轮次””每角色成本”必须由自己的聚合层产生。命名只守一条——约定已覆盖的走约定名，未覆盖的走内部前缀，不许混着发明第三个拼法。

消息与共享状态的可观测

智能体之间的每一条消息都值得当成一等观测对象，因为它同时是通信记录、状态变更依据和潜在污染载体。本文要求每条交接消息落五个字段：发送方角色、接收方角色、任务标识、载荷摘要（哈希或截断后的短文本，不是原文）、投递状态（待投递 / 已送达 / 已接受 / 被拒绝 / 超时）。投递状态是这里唯一需要状态机来管的部分，也是”进行到哪一步”这个问题的直接答案来源——一个任务的所有消息都停在已送达但未接受，你立刻知道问题出在接收方的接受逻辑，而不是模型质量。

黑板把并发写冲突变成了业务故障，要求因此更严格。三条最低配置：每次写入带写入者角色与读到的版本号；关键字段留追加式历史而不是原地覆盖；读写值不一致时打一条冲突事件。有这三条，”结论为什么和所有输入都不匹配”才有可查路径。租约与序号能挡住过期写入，但本身也要被观测——授予、续期、到期与抢占四类事件各自计数，否则锁死了也没人知道系统在锁上花了多少时间。

污染传播是多智能体特有的新增风险，观测手段是来源标记随内容走。任何被外部材料（检索结果、网页、用户上传、第三方工具返回）影响过的中间结论，都带上来源类型标记，一路传递不清洗。这条标记同时服务两件事：排查时能看出结论从哪一步开始偏，以及注入防护时能识别出”哪一段自主决策是被外部内容推着走的”。防护策略本身见《Agent 安全与权限控制》，本文只要求它可追溯。

指标：只有群体行为才显形的信号

四个黄金信号在这里仍然成立，但它们管的是”某个角色的实例是否健康”，而不是”协作是否成功”。后者需要一批按任务而非按请求聚合的指标。下表是本文认为的最小集，维度一律限制在角色、任务类型、状态与租户，绝不用无上限标签。

派生/配对差 派发数减去回执数，按任务窗口统计 静默丢失的执行者 用请求数当分母，把重试算成回执
交接成功率 已接受 / 已送达 下游拒绝与无人认领 把超时降级算成成功
任务停滞时长 当前时刻减去任务最后一次状态推进 卡死与互相等待 用平均而非分位数，长尾被抹平
收敛轮次 协商类任务的往返次数分布 谈不拢、反复重做 不设上限，分布被极端值拖死
重复工作率 同一任务内相同工具与相近参数的调用占比 分工重叠、职责不清 参数完全等值才算重复，漏掉近似重复
每完成任务成本 总成本除以通过质量判定的任务数 真实经济性 分母含失败任务，越坏越”便宜”
提前终止率 被预算或超时闸门截断的任务占比 闸门在替你做决定 与失败率合并统计，掩盖原因

口径上强调三点。

第一，分母必须是”完成且质量达标”，不是”跑完”。多智能体系统最常见的假繁荣，就是用大量低成本失败任务把平均成本压低，看起来效率提升，实际是什么都没交付。这条在《大模型监控指标体系》里从指标层讲过，本文只把它落到任务粒度。

第二，进度类信号优先于性能类信号。延迟与吞吐回答”快不快”，多智能体首先要在意”有没有在往前走”。最后一次状态推进可以是消息送达、黑板写入或步骤递增，三源之一有更新就算推进。这样定义后，空转的辩论显示为”推进频繁但轮次不收敛”，卡死的流水线显示为”零推进”，两者处置方式完全不同，而在传统指标下都只是”慢”。

第三，群体指标用突变检测而非绝对阈值。角色数、任务类型和业务量都会改变合理区间，固定阈值要么天天误报要么永远不报；起点是按角色与任务类型分别建历史分位带，带外才告警。低频高危事件（写冲突、租约被抢占）不适合比率告警，走单条登记加人工确认。告警分层与抑制机制见《可观测性告警治理》，本文只补一条专属规则：同一任务内的连锁失败必须折叠成一条告警，折叠键就是任务标识——否则一个上游挂掉会让下游七八个一起报错，风暴的结果是所有人屏蔽群消息。

成本归因：分叉执行里”谁花的钱”没有自然答案

成本账单有三类难账：共享上下文重复计费，同一段长材料被 N 个角色各读一遍各记一次输入；重试与重做，第二次执行该记在原任务还是记在故障归因上；孤儿成本，某角色跑了很多步而产物最终没进结论。三类都只能靠事先约定解决，事后从数据里”看出来”是不可能任务。

本文建议的归因规则只有两条，简单到能被写进代码审查清单。第一，成本跟着运行走，运行跟着任务走：每次智能体运行累计自己的模型与工具开销，任务成本是其所有运行之和，包含重试与失败的那几次；会话成本是会话内全部任务之和。不做什么？不做事后按比例分摊共享上下文的”公平算法”——那种算法每季度都会因为架构变化重写一次，且没人能验证它是否算对。第二，重复消耗单独成指标而不是藏进总额：同一任务内对相同检索条件与相近参数的调用打重复标记，报表上”有效成本”与”重做成本”并列显示。把重做藏进总额，你只会看到”这个功能很贵”，看不到”这个功能有一半钱花在重做上”。

归因结果必须和预算闸门闭环，否则它只是记账。闸门四层，任一层被触达都要在链路里显式标记终止原因，这是提前终止率的前提：单次运行上限（防某一步无限生成）、任务上限（防总开销失控）、角色上限（防某角色被反复唤醒）、租户与会话上限（防单个客户吃光共享配额）。最容易漏的是角色上限——监督者不断重派同类子任务时，任务上限还没到，角色已经空转了几十次。至于 token 用量与账单的差额口径，计价细节归《大模型监控指标体系》，本文只留一句：用量解释差值，账单作对账基准，不就地校准。

留存与采样：默认策略会漏掉最贵的那类样本

追踪的默认做法是头部采样——在链路起点按比例决定整棵树要不要。多智能体场景下这个策略有系统性偏差：链路越长、越贵、越可能出问题的样本，恰恰是那些”看起来没报错但跑了几十步”的，而头采样对它们一视同仁。结论是尾采样承担主要职责，头采样只做流量削减：全量先进采集器，按条件决定留不留——总时长超阈值、步数超阈值、总成本超阈值、包含失败或降级、包含写冲突或租约抢占、用户反馈为负，任一命中即保留。其余按时序抽样，保证”每个版本至少留下一条成功样本”，否则新版本出了问题却没有任何对照。

采样还有一条硬保底：一个任务的所有 span 要么整条留，要么明确标记缺失。文中的阈值与留存比例一律是团队约定示例，要按自身预算与合规口径重新校准，本文刻意不给采样率与存储成本数字。留半条链路比不留更糟——半链路会给出错误的因果判断，让排查者顺着不存在的路径找下去。子智能体自起追踪并被独立采样时，父侧的 span link 可能指向一条已被丢弃的追踪，父侧必须能识别”链接指向的追踪未留存”并在面板上标出。

日志的留存哲学与单智能体一致——最小必要、默认摘要、原文按需开启且会自动过期，《AI 应用的可观测性》已讲透，本文只补两条增量。第一，内容每跨一个角色就重新评估一次留存级别：A 的中间结论对调试必要，不代表传给 B 之后仍然必要，跨角色默认只带摘要与标识，原文留在原处。第二，脱敏在进入聚合管道之前完成，而不是在展示层：展示层脱敏挡不住日志库里的原始副本，而路径数量会让”漏一条”变成必然。电话号码、身份证件号、精确地理位置、通讯录内容在任何一层都不该出现，包括 span 属性、指标标签与缓存键。

观测数据回流评测：线上轨迹是任务集的原料

评测体系本身在《AI 应用评测体系》里已经建好，本文只谈多智能体观测数据怎么喂给它，以及喂之前要做什么。

第一层价值是任务集来源。线上任务分布永远比人工用例集宽：哪些类型触发过多角色分工、哪些交接最常超时、哪些协商轮次最多，都能从观测里筛出来，脱敏并标注成功判据后转成回归用例。约束是分层抽样：按角色组合、任务类型与终止原因分层，每层保底若干条，其中”被预算或超时闸门截断”的那批要全量保留——它们缺陷密度最高，也最容易被随机抽样漏掉。

第二层价值是把轨迹变成可判定的对象。Anthropic 在 2026-01-09 那篇讲智能体评测的工程文章里给出的思路值得直接借用：任务要有明确可验证的成功条件，同一条任务要跑多次而不是一次定优劣，判分要同时看结果与过程轨迹。落到多智能体上有个专门陷阱——只判轨迹会奖励”看起来忙碌”：轮次多、工具调用密集、消息频繁的运行，在轨迹打分下分数很好看，实际可能什么都没交付。所以轨迹分数只能当线索，结果判分才是结论；这也是为什么本文前面坚持把终止原因、收敛轮次与有效成本分开统计。

第三层价值是环境一致性：评测沙箱的埋点字段必须与线上同一套内部契约，否则离线指标与线上面板无法对照，回归结论出不了门；同一批用例在新版本重跑时按版本分组、看分布而不是单点——调度差异足以让单次轨迹不同，用单次结果判退化必然误判。反过来也要承认评测替代不了线上观测：只有真实负载才出现的租约竞争、只有真实数据量才暴露的重复检索，只能在线上看见。

采集链路与面板：每段各管什么

链路骨架沿用通用方案：SDK 埋点，采集器（Collector）做归一化、属性白名单、内部字段到语义约定的映射与尾采样，后端按信号分工。项目定位都是老的，本文不写版本号，也不做排名：Prometheus 负责指标存储与查询，Loki 负责日志，Tempo 与 Jaeger 负责追踪，Grafana 把三者拼成可下钻的视图。多智能体场景下唯一需要额外强调的是采集器位置——映射与白名单必须在导出前完成，因为一旦内容进入后端，删掉它的成本就远高于当初不采集它。

面板本文建议严格分四层，每层回答一类问题，混层是常见错误。

层 回答的问题 典型内容 主要消费者
系统层 跑得起吗 队列深度、并发运行数、配额与限流触达、进程健康 值班工程师
流程层 进行到哪了 任务进度、交接状态机分布、停滞时长、终止原因 业务与值班
群体层 配合得好吗 派生配对差、重复工作率、收敛轮次、写冲突 架构与应用团队
经济层 值不值 每完成任务成本、重做成本、按角色与租户归因 产品与负责人

下钻路径必须从任一层到追踪一次直达：看到停滞任务，点开就应是它的交接 span 与运行树，而不是让人去复制标识查另一个系统。跨智能体的链路细节，《云原生可观测性：Metrics、Logging、Tracing》与《可观测性三大支柱落地》已经把三支柱的通用接法讲清，本文不再展开。

eBPF 在这里的位置是补足内核层的观测取证，不替代应用层语义。它适合三类问题：工具执行进程的真实资源占用与文件、网络行为（与《Agent 代码执行沙箱设计》衔接的运行时取证）、短命进程与调度切换造成的时序偏差、埋点缺失时的旁路证据（SDK 崩溃或第三方执行器未接入，仍能在内核层看到调用发生）。它看不到模型语义——不知道哪一步属于哪个运行，也不理解任务与交接。当作第四种信号源，与主链路按进程标识和时间戳对齐即可，别指望它承担因果重建。

常见误区

误区一，用父子关系表达”谁等谁”。层级树表达的是归属，等待与因果要用交接事件加链接表达。混用的后果是并发执行被当成串行累加，端到端延迟凭空翻倍，而真实瓶颈看不见。

误区二，把角色名当成可以自由生成的字符串。角色标识一旦由模型现场生成或从提示词解析，就变成了无上限标签，聚合层最先垮掉。它必须来自配置与版本控制。

误区三，只埋成功路径。交接被拒绝、超时未响应、编排层合成降级这三类都没有异常抛出，不显式建模就永远不会出现在数据里，而它们恰好是协作失灵的主体。

误区四，用总成本代替归因成本。总额平稳而重做占比很高，是多智能体最典型的假效率；没有”有效成本 / 重做成本”这一分法，任何优化都是盲做。

误区五，为省事把原文塞进 span 属性。内容每跨一个角色就被复制一次，追踪通道、留存义务与隐私暴露面同时失控；跨角色只带摘要与标识是硬规则。

误区六，以为框架自带插桩就够了。插桩给出的是单智能体视角的层级，任务、运行、角色与交接这四层协作语义必须自己补，补完还要验证 span 层级确实符合预期。

小结

多智能体把观测从”看清一次请求”变成”看清一场协作”，难点集中在四处：没有主时间线，所以层级按运行切、步序按运行编号；因果会断，所以异步、独立追踪、恢复重开与合成降级四种断点都要显式接续；成本难归属，所以只承认”成本跟运行、运行跟任务”这一条简单规则，并把重复消耗单列；失败常常无声，所以靠派生配对差、交接状态机、停滞时长与收敛轮次这类结构信号，而不是错误率。

落地按四步走：先立内部契约，六类标识与跨语言共享包一次定死；再补层级与因果接续，分清父子与链接，跨进程只传标识不传内容；然后做导出前的白名单与语义约定映射，用映射层对抗 gen_ai.* 仍在 Development 的变动——借词汇、不押契约；最后才动群体指标与告警折叠，并按四层面板组织视图。观测数据接通评测之后，线上轨迹才会持续反哺任务集，闭环才算合上。

一句话收束：检验标准只有一个——任意时刻被问到”进行到哪一步、卡在哪一次交接、这钱记在谁头上”，能不能在三十秒内用数据回答。
