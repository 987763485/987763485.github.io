Token 计费与配额系统

按 token 计费听起来只是”用量乘以一个数”，落地时却是一条要从流式响应里抢数据的管道：费用在请求结束前不可知，重试会重复结算，配额要落在正确的维度上才生效。本文按计量、配额、对账三段展开。纪律有两条：单价一律按当期官方价目核对，不出现任何价格数字；配额与预算阈值均为团队约定示例，估算误差类数字均为示意值。

按 token 计费难在哪

按调用计费是入口可判定的：请求进来时就知道要收一次，计费落在准入位置，上游失败只需一次冲正。按 token 计费把判定推到响应结束，而”结束”本身还不可靠：同一个请求的费用同时取决于输入长度、输出长度、缓存读写命中情况、图像与音频的量，业务方既无法在发起前算准，也无法事后复现。

更麻烦的是输出长度本身不可知。这带来三个后果：预扣与结算必须分开建模；计量点必须放在响应完成路径上，入口只能做额度预检；被中断、超时、客户端主动关闭的请求同样要有费用归属，不能因为没有结果就当零成本。

流式把困难放大一倍：计费用量只在最后一个数据块里出现，而它最容易丢——用户关页面、前端切路由、代理超时、智能体被取消都会让那一帧到不了。必须在”最可靠的数据来得最晚且可能根本不来”的前提下设计，否则账单会系统性偏低，偏低方向恰是被中断的长请求。

成本优化、成本核算、商业定价三件事各有专文；本文假设计价口径已定，只谈实现。

计量口径先把边界定死

实现之前要有一张口径表，把每个计量项的来源与归集规则单独列清；把所有项折算成”总 token 数”是最常见的偷懒做法，代价是后面的对账无从定位。

输入侧包含系统提示词、少样本示例、历史消息、检索注入的上下文、工具声明与参数模式。最容易被低估的是工具与检索带来的隐性膨胀：智能体调用是若干轮”把上一步结果拼进输入再问一次”，每次调用的输入都在增长；检索的召回条数与片段长度同样是输入成本，却常被当成质量参数。两者都应作为独立字段落在调用记录上。

输出侧要区分生成文本与工具调用的结构化参数：算进输出或单列一项都合理，但一个系统只能固定一种并写进口径表，当成”没有输出”会让输出桶长期偏低。

缓存读写是两个独立计量项，命中与否由上游实现决定，并进输入桶就失去了判断缓存策略是否有效的唯一信号；图像与音频也不该折算——不同上游的图像计量单位不同，音频常按时长计，与文本混谈会同时污染两个桶。

分词器口径是硬约束：不同模型分词方式不同，同一句话的 token 数不可跨模型直接比较，也不能拿 A 模型的估算给 B 模型的请求做预算，估算器必须与目标模型绑定。对外口径是以服务端用量字段为准，本地估算只用于准入预检与中断兜底。

MCP 2025-11-25 修订把工具声明放进上下文，隐性输入因此变成可枚举清单，按声明体积记录即可；官方修订仍在推进中，口径表要留出调整空间。

流式取数与重算兜底

取数的姿势是”增量拼内容、终止帧取用量、事后校正”，两条兜底路径要同时存在。第一条是本地估算：用与目标模型绑定的估算器对已到达内容增量计数，随进度写待结算记录，作用不是替代权威数值，而是保证客户端断开后仍有记录。第二条是完成后校正：收到含用量字段的终止帧后以服务端数值覆盖估算值，差值超过约定阈值时（阈值与误差数字均为团队约定示例或示意值）不采信任何一边，把记录标为异常进核对队列；两个数都保留，只留最终值就失去定位线索。

终止帧没到但内容确实流出去一段时，不删记录，保留估算值并标为未校验；按估算结算还是冲正属于团队约定，但要留下痕迹。伪码给出最小结构，四个动作彼此独立：

幂等键与计费记录绑定

重复结算有三个来源。重试让同一个业务请求打到上游两次，两次都有真实消耗，却只应向业务方收一次，账上要同时看到”上游两次”与”业务侧一次”。扇出取先返回的结果，未被使用的记录要么记为候选成本，要么显式丢弃，不能默认消失。异步恢复时回调可能重复投递，结算必须只生效一次。

绑定方式是给计费记录设复合唯一约束：调用幂等键加上游请求标识。它的意义是同一幂等键下可以有多个上游请求，但只有一条记录能进入已结算状态。写入用”不存在则插入、存在则按键更新”，配合待结算、已结算、已冲正三态流转，禁止对金额字段做原地修改；冲正也只新增一条负向记录，账单重跑与审计才都对齐。

这里只讨论计费记录与幂等键的绑定关系。入口层的幂等实现，以及请求怎么在出口处收敛，另有专文，不在此复述。

配额维度与软硬限

配额常用四个维度：租户、应用、模型、接口。租户是账务边界，应用是业务线边界，模型与接口是成本结构边界。最常见的配法是”只按租户限”，失效方式很稳定——一条业务线跑批就能吃满整个租余额度，其他业务线集体饿死，监控上只看到”租户额度耗尽”。要避免它，应用维度必须有独立额度与独立消耗速率，租户维度做总额约束，模型维度约束高消耗模型的可用范围，接口维度约束单次消耗差异极大的入口。

判定顺序固定为”最具体者优先，粗维度做总额兜底”：一个请求要同时通过四道检查，任一不过即拒绝，并说明是哪一维度拒绝的。配额单位不要用请求数，要用量单位并把输入桶与输出桶分开。限流算法怎么推导另有限流相关专文，本文不复述；网关侧的配额落点另有专文。

软限与硬限的差别不在严格程度，而在触发点与体验。软限不拒绝，只告警并降优先级：排队、收缩上下文、把非关键任务推迟到离线队列，感知是”慢一点或短一点”；硬限直接拒绝并返回配额原因标识，感知是”这次没有”。软限在准入时打标、结算时计数，硬限必须在准入时判定，预扣额度要留缓冲。各条线的具体数字全是团队约定示例，要紧的是线间距大于单个请求的消耗量级。

超预算中断与智能体循环

智能体的一次运行由多步组成，每步通常是一次模型调用加若干工具执行，步与步之间靠”把结果拼回输入”衔接。预算判定要落在步骤边界而不是 token 中间：掐断正在生成的调用，已生成内容照样结算却不可用；在步骤边界停下，前一步成果完整可留。

所以正确的中断位置是：让当前调用自然完成，在下一步的准入处拒绝。额度检查要出现在循环入口，落盘的是步骤状态而不是半成品内容——LangGraph 1.0 与 1.1 提供可持久化运行状态，LangChain 1.x 与 1.2 的调用组织也能暴露步骤边界。

费用归属要提前定死：归触发运行的应用与租户，记录在运行标识维度并可下钻到步骤，不摊进公共成本池。被预算中断时，已消耗量照常结算，被拒绝的下一步不产生消耗；中断要写一条结构化事件，说明在哪一步、由哪个维度触发。

重放已完成步骤必须复用原调用幂等键，由上一节的复合约束拦成一条记录。边界也体现在协议层：A2A v1.0.0 与 MCP 2025-11-25 修订描述的任务与工具边界会影响结算点选取，Anthropic 工程栏目中的《agent evals》与《managed agents》只点到标题，不展开结论。

预算自助、预警分级与对账定位

额度看得见，系统才是护栏而不是惊喜。自助视图回答两件事：哪一层在消耗、消耗在哪个计量项上——前者是租户到应用再到接口的下钻，后者是把输入、输出、缓存读写、模态用量、隐性输入分列。视图呈现额度消耗，费用怎么归到业务线口径属于成本归因，另有专文。

预警周期必须明显短于结算周期，否则信号要等账单出来才可见；可行的做法是按天甚至按运行落额度快照。预警至少三档：提示给使用者、升级给应用负责人、限制非关键应用的准入。阈值数字全是团队约定示例，但每一档要对应一个明确动作，只发通知不改优先级或准入，通知就成了噪音。

三方数字对不上是必然的：供应商账单、自有计量、业务归集各有口径，差异按固定顺序定位。第一步时间窗对齐——账单记账时间、计量落库时间、归集跑批窗口往往不同步。第二步计量口径——缓存读写有没有被并进输入、模态用量有没有被折算、工具调用参数归进哪个桶。第三步重试与扇出——同一幂等键下有几条上游记录、几条已结算，这里最容易同时出现多结与漏结。第四步币种与税费——汇率取哪一天、税费是否含在总额里。差异不写成具体比例，把每条归到四类之一比算出一个总数有用。

计费管道的隐私约束

字段纪律只有一条：只记计量必需的字段。用户提问原文不得进入计费明细，也不得出现在账单导出里。它容易被无意破坏——调试时把请求体一起存下来最省事，而计费库是权限最宽、保留最久的通路之一，明细会流向财务、采购甚至外部审计。

可用字段是一个短清单：记录标识、调用幂等键、上游请求标识、租户与应用标识、模型与接口标识、各计量项数量、时间戳、校验状态。清单之外都不该出现在这里：提问与回答原文、工具入参出参、附件名称、检索命中片段属于业务存储，各有保留期与访问控制。做本地估算需要原文长度时算完即弃，会话与运行标识用不可逆形式生成。

“何时可知”决定设计：完成后才可知的项必须先预扣再结算，只能估算的项必须带校验状态参与对账。

小结

难点不在算术而在时机：费用在完成前不可知，最可靠的数据又在最容易丢的那一帧。链路因此围绕时机搭建——口径表定死来源与归集规则，估算器与目标模型绑定；取数靠本地估算与终止帧校正互相兜住；结算靠幂等键与上游请求标识的复合约束去重；配额四维组合、粗维度兜底，软限降优先级、硬限在准入处拒绝；预算中断落在步骤边界。再往外是额度自助与分级预警、固定顺序的三方对账，以及贯穿全程的字段纪律：原文不进计费库。单价一律按当期官方价目核对，文中不含任何价格与账单数字。
