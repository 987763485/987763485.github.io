下一代 Harness：多模型异构 Agent 的开放调度设计

把 Claude Code、Codex、Pi Agent 这类执行器，和 DeepSeek、千问、ChatGLM 这类模型拆开看，会发现一个被单模型绑定掩盖的问题：同一个 Agent 换模型，产出质量会变；同一个模型换执行器，稳定性也会变。本文讨论下一代 Harness 应有的形态，一个不绑定单一模型生态的调度层，用能力画像、成本路由、统一执行器接口和组织化协作，把「谁来做、用什么做、花多少钱」变成可计算、可复盘的决策。适合正在把 Agent 从演示推向生产、同时被效果与成本拉扯的工程师与架构师。

问题不在 Agent，而在绑定关系

在演示环境里，给一个通用 Agent 配上一档强模型，再写几段角色提示词，就能跑出像样的结果。到了生产环境，这套结构很快会遇到四个现象。

第一个现象是同一 Agent 接入不同模型，能力表现不同。系统提示词、工具调用格式、上下文裁剪策略，往往都是围绕某个模型调过的。换一个模型之后，函数调用可能从结构化 JSON 变成夹着解释的自然语言，长上下文里的关键约束被忽略，拒答边界也变了。这种变化不是简单的「更聪明或更笨」，而是能力结构发生了变化：原来擅长的那一类任务可能还凑合，原来不出错的那一类反而开始出错。

第二个现象是同一模型接入不同执行器，能力表现不同。执行器决定工具面、沙箱、重试策略、补丁格式和上下文组织方式。同一个模型在 A 执行器里能连续修改三个文件并跑通测试，在 B 执行器里可能改完一个文件就停下来等指令。因此，能力是「模型 × 执行器 × 任务」三元组的属性，不是模型单点属性。比较模型时如果不固定执行器，结论几乎没有意义；反过来，比较执行器时如果不固定模型，也一样。

第三个现象是领域专精。在笔者维护的评测集里，千问在需求整理、设计说明和中文长文上更稳定；DeepSeek 在代码修改、测试补齐上首轮通过率更高，单位成本也更低；ChatGLM 在中文短文本和结构化抽取上够用。这些差异不会直接出现在公开排行榜上，因为排行榜的任务分布和自己的业务分布并不一致。而且结论会随模型版本变化，今天测出来的优势，下一个版本可能就消失了。

第四个现象是成本梯度明显。高能力档位（如 Claude Fable 5、Codex 的 Astra）与低价档位之间，单位 token 成本往往差一个数量级以上；低价档位多来自 DeepSeek、千问、ChatGLM 这类国内模型。更麻烦的是，账面 token 成本只是总成本的一部分，返工、校验、人工复核、等待时间都要计入。一个便宜模型如果把返工率抬高了一倍，最终账可能比贵的模型还难看。

四个现象指向同一个矛盾：怎样在任务粒度上，把模型能力、调用成本和执行形态匹配起来。单模型多角色的封闭结构做不到这一点。它在设计时就把模型和执行器绑死了，运行时既没有可替换的候选，也没有可比较的账本。所谓「换模型」，只能靠改配置、重启流程，靠人的经验重新调一遍提示词。

本文把 Harness 定义为任务进入执行器之前和之后的那层控制面：拆解任务、选择执行器与模型、分配预算、收集产物、组织协作、记录账本。它不是模型，不是执行器，也不是又一个 Agent 框架。框架解决的是「怎么把一次调用串起来」，Harness 解决的是「这次调用该由谁、用什么、花多少来完成，失败之后怎么办」。

分层：调度层到底管什么

把 Harness 拆开，通常可以分成五层。接入层负责模型 API 的兼容、鉴权、限流、重试和计费口径统一；执行层由 Claude Code、Codex、Pi Agent 这类执行器组成，负责真正的文件操作、命令执行和沙箱隔离；调度层是本文的重点，负责能力画像、路由、预算、升级和熔断；组织层由领导 Agent、执行 Agent 和人工审批构成，决定任务如何流转；观测层用 trace、账本和评测数据，让前面四层的决策可以复盘。

层与层之间靠五个核心对象传递信息。

  • Task：目标、输入、约束、验收标准、预算和截止时间。
  • CapabilityProfile：某个模型在某个执行器上、针对某类任务的历史表现。
  • Executor：统一的执行接口，屏蔽不同执行器的调用差异。
  • Policy：路由规则、升级条件、审批门槛、熔断策略。
  • Ledger：每一次调用的成本、耗时、结果和人工介入记录。

这五个对象里，最容易做错的是 CapabilityProfile。很多团队把它做成了一个静态的「模型能力表」，写着某某模型擅长代码、某某模型擅长写作。这种表在选型阶段有用，在运行阶段几乎没用，因为它没有区分任务类型、执行器和版本，也没有记录方差。真正可用的画像必须是三维的：模型、执行器、任务类型，再加上时间和样本量。

设计调度层时，有四条原则值得先定下来。

第一，控制面与数据面分离。Harness 不直接执行命令，也不直接操作仓库。它只做决策，把执行交给执行器。这样执行器可以替换，沙箱边界也不会被调度逻辑绕过。

第二，配置即代码。路由表、提示词、预算、审批规则都要进版本库。线上出现效果回退时，需要能回答「昨天改了什么」，而不是靠翻聊天记录。

第三，硬约束先过滤，软指标再排序。上下文窗口、工具支持、数据驻留区域、供应商白名单，这些是过滤器，不参与打分。先保证候选可用，再比较谁更合适。

第四，不重复造协议。工具接入优先用 MCP，执行器之间共享同一套工具服务器。Harness 只定义任务和产物的契约，不定义工具协议的另一套方言。

一个常见的误区是把 Harness 做成提示词仓库，里面堆满角色设定和任务模板。提示词当然重要，但它属于执行器或 Agent 的内部实现，不是调度层的核心。调度层真正要回答的是经济问题：这类任务，用哪一档能力、哪一个执行器、在多少预算内完成，才最划算。

模型能力画像：把「擅长」变成可比较的信号

公开排行榜不能直接拿来路由，原因有三个。一是数据污染，训练集和评测集可能有重叠；二是分布不一致，排行榜偏向通用问答和竞赛题，生产任务多是仓库里的缺陷修复和小步重构；三是版本漂移，供应商会在不改变模型名称的情况下更新权重。用自己的任务分布建评测集，是唯一可靠的办法。

评测集不需要很大，两百到五百条真实任务就足以看出差异，关键是分层。按缺陷修复、新功能、重构、补测试、写文档、代码评审这几类分别采样，每类保留一部分作为留出集。验收标准尽量做成可执行的检查：测试是否通过、类型检查是否干净、接口是否符合约定、文档是否包含指定章节。无法自动检查的任务，用双人盲评，记录分歧。评测集本身也要版本化，每季度复核一次，剔除已经失效的任务。

画像至少要记录七个维度。

维度 度量方式 作用
首轮通过率 一次通过验收的比例 直接决定返工成本
工具调用合规率 schema 合法且参数完整的比例 决定能否无人值守
格式稳定性 结构化输出解析失败率 决定流水线能否组合
长上下文保持 关键约束的召回率 决定大仓库任务是否可用
延迟 p50 与 p95 决定交互体验与并发容量
成本 每次被接受任务的总成本 决定经济性
方差 同一任务多次运行的波动 决定是否需要多重采样

方差这一项经常被忽略。同一个模型跑同一个任务三次，有时一次就过，有时三次都不过，这种不稳定性比平均通过率更能说明问题。对高方差的任务，要么增加采样次数再择优，要么换更稳定的模型，要么把任务拆得更小。只看平均值，会把「偶尔能用」误判成「稳定可用」。

这张表的价值不在于把某个模型钉死在某个角色上，而在于把「角色需要什么能力」写清楚。模型版本更新或价格变化时，只需要重跑评测、更新分数，角色映射可以跟着调整，不需要重写整套流程。

成本路由：按「被接受的任务」算账

成本核算最容易犯的错，是只看 token 账单。一次任务的总成本至少包括五部分：模型调用、执行器开销、失败重试、独立校验，以及人工复核的时间。把这些加在一起，再除以被接受的任务数，才是可比较的单位成本。

用公式表达就是：每次被接受任务的成本，等于模型调用、执行器开销、重试、校验和人工时间之和，除以通过验收的任务数。这个口径会把「便宜但常返工」的模型打回原形，也会让「贵但一次过」的模型显出价值。

一个关键的不对称性决定了级联策略是否成立：代码类任务有测试、类型检查和构建可以作为廉价验收器，文档和设计类任务没有。代码可以先让便宜模型生成，再用测试验证，失败再升级；文档如果让便宜模型先写，人工审阅的成本往往高于直接让强模型写一遍。所以级联不是通用策略，它只适用于验收成本低、错误可被判定的任务。

常见的路由策略有四种。

策略 适用场景 主要代价
静态映射 任务类型稳定、模型数量少 无法应对版本波动
级联升级 有可靠且廉价的验收器 延迟叠加，需要独立校验
预算约束 成本敏感、任务可中断 可能提前终止或降级
竞价分配 多供应商、指标稳定 调度开销大，容易过拟合

级联升级是最常用的一种。设计时有几条纪律：最多升级两次，避免无限追高；校验器尽量独立，不要用同一个模型家族做校验，否则盲区会相关；升级时把失败原因带进下一轮上下文，不做无信息重试；每一次升级都要记录原因和成本，否则无法判断级联到底省没省钱。

用一组示意数据可以看清账。假设三档模型的相对单位成本分别是 1、8、40，首轮通过率分别是 0.62、0.81、0.88，校验成本记为 0.5。

方案 期望调用成本 总体通过率 每次被接受任务成本
只用低档 1.00 0.62 1.61
只用中档 8.00 0.81 9.88
只用高档 40.00 0.88 45.45
低档失败后升中档 1.00 + 0.38 × 8.50 0.93 约 4.56

执行器抽象：让不同 Coding Agent 可替换

模型可以换，执行器也要能换。但执行器之间的差异比模型更大，因为它们暴露的是完全不同的交互面。选型时要逐项确认：调用方式是 CLI、SDK 还是 HTTP，是否支持无头运行；工具面覆盖文件、命令、浏览器还是 MCP；沙箱是容器、进程还是远端环境，网络出口是否受限；产物是 diff、patch、测试报告还是日志；事件流是结构化事件还是人类可读文本；计费按 token、按席位还是按调用；是否支持中断、取消和人工确认。

把这些差异收敛成一个统一接口，Harness 才可能做运行时替换。接口不需要很复杂，五件事就够：准备工作区、执行任务、流式返回事件、收集产物、取消执行。

这个接口有三个隐含要求。

第一，产物契约必须结构化。不要让调度层去解析执行器的自然语言输出，那等于把稳定性建立在文案不会变上。diff、变更文件、测试结果、未决问题、token 用量，都应该是独立字段。

第二，执行必须幂等。同一个 taskId 重放时，要么返回已有产物，要么在干净的工作区重跑，不能把两次修改叠在一起。工作区要记录基线 commit 和分支，取消之后能回滚。

第三，取消语义要明确。是停止生成、终止进程，还是等待当前工具调用结束？不同执行器的行为不同，Harness 要在适配器里统一成「尽快停止并保留已产生的产物」，否则超时和预算熔断会失效。

适配器还有几个工程坑。命令行输出格式会随版本变化，必须固定版本并做契约测试；鉴权和限流策略各不相同，要在接入层统一；文件系统不一定共享，远端执行器需要显式上传和下载；并发度受席位和配额限制，调度层要把并发当成资源来分配。最后，执行器与模型的支持关系通常不是全连接，有些执行器只支持自家模型，有些可以通过兼容接口接第三方模型。路由之前要先查兼容矩阵，否则会选出无法执行的组合。

组织化协作：领导角色不是转发消息

当 Agent 数量超过三个，点对点指派任务很快就会失控。沟通路径按平方增长，上下文在多次转述中失真，优先级冲突没有人裁决，预算也被各自为战地消耗。设置领导角色的意义，不是领导更聪明，而是它掌握全局信息：目标、优先级、预算、依赖关系和验收标准。

领导 Agent 的职责可以列成七条：拆解目标，分配任务，裁决冲突，合并产物，控制预算，处理升级，决定哪些事情必须交给人。它不应该做的事同样明确：不亲自写代码，不微调每个执行 Agent 的提示词，不替执行 Agent 做局部技术决策。领导一旦陷入执行，全局视角就没了，整个团队会退化成一条串行流水线。

同级 Agent 之间的协作，靠产物契约而不是自由聊天。它们可以互相提问、请求澄清、共享中间产物，但不能直接把新任务派给同事。需要别人承接时，把请求上报给领导，由领导判断优先级、预算和依赖，再统一分配。这条规则看起来增加了往返，实际上避免了三个问题：任务重复分配、上下文重复传输、紧急任务插队导致的全局失序。

一次交接至少要说清楚八件事：任务标识、目标、输入产物、约束条件、验收标准、预算、截止时间、升级路径。缺一项，承接方就要靠猜，猜错之后返工的成本远高于一次写清楚。上下文包也要克制，只带最小充分信息，产物用路径或哈希引用，不要复制整段对话。把「已经否决的方案」和「关键决策」带上，比带上全部历史更有用。

sequenceDiagram
    participant E as 执行 Agent
    participant L as 领导 Agent
    participant P as 同级 Agent
    participant H as 人工审批
    E->>L: 提交产物、自检结果与未决问题
    L->>L: 校验契约、预算与优先级
    L->>P: 下发联调任务与上下文包
    P-->>L: 返回联调报告
    L->>H: 申请不可逆变更审批
    H-->>L: 批准或驳回
    L-->>E: 合并、返工或关闭

这套结构和真人团队很像，但差异也要说清楚。Agent 不会疲劳，可以并行，但也更容易在上下文里迷路；Agent 不会因为职级而服从，只会因为契约清晰而配合；Agent 之间的「信任」不能靠默契，只能靠校验和账本。把真人团队的隐喻直接照搬，容易忽略这些差异。

组织化协作还有几个反模式。领导变成瓶颈，所有任务都排队等它；同级 Agent 陷入无休止的协商，谁也不肯先产出；两个 Agent 的任务也强行套三层架构，沟通成本高于执行成本；领导只会转发消息，不做裁决，那它就没有存在的价值。判断是否需要多 Agent，标准不是「听起来更先进」，而是任务是否真的可以拆成独立验收的子任务，以及并行带来的收益是否覆盖协调成本。

人机混编：80/20 是结果，不是指标

「八成由 Agent 自主推进，两成由人工引导校验」是一个合理的目标形态，但它只能是结果，不能当成硬性配额。为了凑够 80% 的自动化率而放行未经校验的产物，最后会在事故里把省下的时间连本带利还回去。

真正需要人介入的，通常是这几类：需求本身有歧义，验收标准无法写成可执行检查；动作不可逆，比如生产部署、数据迁移、对外发送；变更涉及安全边界，比如权限、密钥、网络策略；高风险改动的最终验收；以及没有历史数据支撑的新架构决策。把这五类划出来，人工介入点就有了依据，而不是靠感觉。

审批门槛要设计成「人做判断，不做搬运」。审批界面应该给出变更摘要、风险点、测试结果、回滚方案和影响范围，人只需要批准、驳回或要求修改。如果人要在几个 Agent 之间复制粘贴上下文，那说明 Harness 的产物契约没做好。默认拒绝、限时审批、批量复核，是避免人工成为瓶颈的三个常用手段。

衡量人机混编是否健康，可以看五个指标：自动化完成率、首轮验收通过率、返工率、每个被接受任务消耗的人工分钟数、以及事故率。单看自动化率会误导，必须和返工率、事故率一起看。一个团队把自动化率从 60% 提到 85%，但返工率翻倍、事故率上升，这不是进步。

信任要按任务类型逐步校准。缺陷修复和补测试可以先放开，让 Agent 自主推进；数据库迁移和权限变更则长期保留人工闸门。每个任务类型单独积累证据，单独调整门槛，不要用一个全局比例管理所有风险。

观测、账本与落地路径

没有账本的调度系统无法优化，因为它连「上一次为什么选这个模型」都回答不了。一次任务至少要记录一条 trace：任务类型、候选集合、路由决策与理由、执行器、模型、输入输出 token、耗时、重试次数、升级原因、校验结果、人工介入、最终是否被接受。把这些字段落到只追加的账本里，才能做成本归集、回放和离线分析。

如果团队已经在用 OpenTelemetry，可以直接沿用 GenAI 语义约定，把模型、token、操作类型挂到 span 上，不必另造一套埋点体系。关键是字段口径统一：同一个「被接受任务」的定义，路由、财务和复盘要用同一套，否则数字对不上。

上线之前，先用影子路由验证。把一部分真实任务复制一份，用新策略跑，不合并产物，只比较通过率、成本和延迟。等差异稳定，再逐步放量。护栏指标至少要有三个：事故率、p95 延迟、每次被接受任务成本。任何一项恶化，都先回滚策略，再查原因。

落地路径建议分四步。

第一步，选一个任务类型，比如缺陷修复；选一个执行器；接两个模型；建评测集和账本。目标不是全自动，而是把「能力画像」和「单位成本」两个数字跑通。

第二步，加独立校验和级联升级。先用测试和类型检查做验收器，测出级联的真实收益。如果校验成本高于节省的模型成本，就退回静态映射，不要为了架构好看而硬上级联。

第三步，接第二个执行器，统一产物契约。这一步会暴露很多适配问题，也会验证「模型 × 执行器」的组合假设。此时再决定哪些任务需要多 Agent，哪些单 Agent 就够。

第四步，引入领导 Agent 和人工闸门，扩展到更多任务类型。每扩展一类，重新校准能力画像和审批门槛，不要复制上一类的配置。

有几样东西不适合早期做：通用的 Agent 市场、复杂的竞价机制、会自我修改提示词的调度器、以及自研的工具协议。它们都建立在「能力画像稳定、账本可信」的前提上，前提没成立之前，投入大概率打水漂。

最后是组织问题。路由配置要有版本和评审，关键决策要有 ADR，评测集要有明确 owner，Agent 引发的线上问题要进入现有的事故流程。Harness 看起来是一个技术系统，实际约束它的是组织的反馈速度：谁能定义验收标准，谁对成本负责，谁有权批准不可逆动作。这些问题不解决，再精致的调度器也只是一个更贵的演示。

小结

下一代 Harness 的核心不是「让一个 Agent 更聪明」，而是把模型、执行器和任务拆开，在运行时做匹配。能力是「模型 × 执行器 × 任务」三元组的属性，必须用自有评测集测量，不能照搬排行榜。成本要按「被接受的任务」核算，级联只在验收便宜且可靠时成立。执行器要通过统一接口和产物契约变得可替换，领导 Agent 的职责是全局调度而不是转发消息。人机混编的 80/20 是结果，不是配额，审批要基于风险而不是比例。先把一个任务类型、两个模型和一本账跑通，再谈多 Agent 团队。
