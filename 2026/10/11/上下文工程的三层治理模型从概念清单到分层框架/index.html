上下文工程的三层治理模型：从概念清单到分层框架

一个 Agent 给出了看起来完全合理的答案，直到用户发现它引用的是三个月前已经废止的退款规则。排查下来，Memory 里的旧规则盖过了 RAG 检索到的新文档，而 Harness 只检查了权限，没有检查上下文冲突。这类故障不是某个组件坏了，而是组件之间的接缝没有设计。本文用一个三层治理模型，把 RAG、Memory、Skill、MCP、Prompt、Agent 与 Harness 放回它们真正的位置。

一次看似合理的错误回答

事情发生在一个客服 Agent 上。用户问：买了两周的商品还能不能退。Agent 回答得很流畅：按照七天无理由规则，已经超过期限，不能退。语气、结构、引用都像模像样，用户差点就信了。

问题在于，这类商品的政策半个月前刚改过，退货窗口从七天延长到了十五天。新政策写在一份对外公告里，RAG 也检索到了，但它的排序低于 Memory 里那条旧规则。Memory 里的规则来自三个月前的一次人工录入，带着较高的置信度，也没有设置过期时间。Agent 看到两条互相矛盾的信息，选择了它认为更可信的那一条。

Harness 在这一步没有发挥作用。它配置了工具权限、调用了审计日志，也限制了单次任务的 token 预算，唯独没有做上下文冲突检测。于是系统一路放行：检索正常、记忆正常、生成正常、权限正常，最后输出错误。

事后复盘时，团队先怀疑模型，换了更强的模型，问题依旧；又怀疑检索，把 RAG 的召回数量翻倍，错误率反而上升。真正的原因直到有人把三条上下文来源并排打印出来才显现：Memory 里的旧规则、RAG 里的新公告、Prompt 里的「按公司政策回答」，三者互相矛盾，而系统没有任何机制决定谁优先。

这个案例值得反复看，因为每一个组件都在按自己的规则正常工作。RAG 做了召回，Memory 做了持久化，Agent 做了取舍，Harness 做了权限控制。失败发生在它们之间：没有人定义「当记忆和检索结果冲突时，谁说了算」，也没有人规定「这种冲突必须被看见」。

这正是上下文工程真正困难的地方。它不是把七个概念分别讲清楚，而是决定它们在同一个系统里如何分工、如何制衡、冲突时如何收敛。

并列解释为什么不够

把 RAG、Memory、Skill、MCP、Prompt、Agent、Harness 平铺成七个章节，读起来很顺，因为每个概念都能独立成篇。但这种写法回答的是「它是什么」，回答不了「它和别的机制冲突时怎么办」。前者是词典，后者才是架构。

这七个概念并不在同一层。它们控制的对象不同，作用的粒度也不同。RAG 控制外部知识，Memory 控制跨会话状态，Skill 控制流程与标准，MCP 控制工具接入，Prompt 控制单次指令，Agent 控制运行时调度，Harness 控制边界与风险。把它们并列，容易制造三种错误类比。

第一种是把 RAG 和 Memory 都当成「检索」。RAG 检索的是外部事实，Memory 检索的是历史状态；前者的正确性取决于知识库，后者的正确性取决于写入策略。第二种是把 Prompt 和 Skill 都当成「指令」。Prompt 是一次性的，Skill 是可复用的；Prompt 靠措辞起作用，Skill 靠流程和验收标准起作用。第三种是把 MCP 和 Agent 都当成「工具调用」。MCP 解决连接方式，Agent 解决调用决策；协议不负责判断该不该用，编排才负责。

并列清单还会掩盖依赖关系。RAG 的结果可能被写进 Memory，Skill 可能调用 MCP，Agent 的决策又受 Harness 约束；这些关系不是单向的知识点，而是带反馈的供应链。一次错误可能沿着链条放大：检索到旧文档，写进记忆，下一次被当成事实复用，最后固化成团队共识。分层的目的，就是让这些反馈路径可见，并在关键节点设置检查点。

按「谁在控制上下文、控制什么、控制到什么粒度」重新分组，会得到三层：

第一层：上下文的生产与封装

生产层回答的是：上下文从哪里来，以什么形态进入系统。它包含 RAG、Memory 和 Skill，三者都是供给侧。

RAG 负责从外部知识库中检索事实性上下文。它的核心问题不是「能不能检索」，而是「检索回来的东西是否可信、是否过时、是否与当前任务真正相关」。一个能召回十篇文档的 RAG，如果其中三篇是旧版本、两篇是别的产品线，那它带来的不是知识，而是干扰。判断 RAG 是否可靠，至少要回答四个问题：文档来源是谁、最后更新时间是什么、适用范围到哪里、有没有引用可以回溯。

检索本身可以拆成召回、排序、装配三段。召回决定有没有；排序决定先给模型看什么；装配决定以什么形式呈现。三段里任何一段出错，都会表现成「模型胡说」。一个常见的误判是把召回数量当成质量：召回从五条加到二十条，相关文档的排名可能反而下降，模型的注意力被无关内容稀释。更稳妥的做法是保留少量高置信片段，附上来源与时间，并在证据不足时允许系统拒答，而不是硬凑一个答案。

Memory 负责跨会话的持久化状态。短期记忆服务当前任务，长期记忆沉淀项目规范、用户偏好和历史决策。它的关键设计点不是存储容量，而是写入策略与过期机制。什么东西值得记、谁来写、写完谁来复核、多久失效、冲突时如何覆盖，这些决定了记忆是资产还是负债。记忆不是越多越好，错误经验会污染后续判断，而且污染往往比缺失更难发现。

记忆至少可以分成三层：工作记忆保存当前任务的临时状态，会话记忆保存这一轮对话的共识，长期记忆保存跨项目的偏好与决策。三层的写入权限应该不同：工作记忆可以自动写，会话记忆要经过摘要与确认，长期记忆最好由用户显式确认或由系统定期提议。写入来源也要区分：用户亲口说的、模型推断的、系统事件产生的、人工录入的，可信度完全不同。把模型推断直接写成长期事实，是记忆污染最常见的入口。

Skill 负责把团队经验封装成可复用的能力模块。它不同于 Prompt 的单次指令，而是「以后遇到这类任务都这么做」的标准作业程序，包含流程、模板、工具使用方法和质量标准。Skill 的价值在于把分散在个人脑子里的隐性知识结构化，让系统在没有人反复解释的情况下，仍然按团队的方式做事。它的风险也同样明显：流程会过时，封装会变厚，适用范围会被误判。

一个可维护的 Skill 至少包含四部分：触发条件，说明什么任务该用它；步骤与模板，说明怎么做；工具与权限，说明能调用什么；验收标准，说明做完如何判断合格。缺了触发条件，Skill 会被误用；缺了验收标准，Skill 无法迭代。Skill 还需要版本化和组合能力：流程变更要能回滚，多个 Skill 之间要定义清晰的输入输出，而不是互相复制粘贴。一个周报 Skill 如果既管数据收集、又管排版、又管发送，最后会变成无法维护的黑盒，正确做法是拆成收集、写作、发送三个可组合的模块。

三者的共同点是都需要「来源与时效」的元数据。每一条进入上下文的内容，最好都能回答：谁生产的、什么时候生产的、适用于什么范围、置信度多少。没有这四项，生产层就只是一个堆料场，检索、记忆和技能都在往模型面前搬东西，却没有人对这些东西的可靠性负责。

来源 提供什么 可信度取决于 过期信号
RAG 外部事实、制度、文档 来源权威性与更新时间 文档版本、公告日期
Memory 偏好、历史决策、项目状态 写入策略与复核机制 有效期、反例出现
Skill 流程、模板、质量标准 版本管理与实际验收 流程变更、连续失败

第二层：上下文的接入与执行

执行层回答的是：准备好的上下文如何被 Agent 在运行时调用。它包含 MCP、Prompt 和 Agent，三者都是消费侧。

MCP 是工具接入的标准化协议。它解决的是「Agent 如何以统一方式连接外部系统」的问题，而不是「该不该用某个工具」的策略问题。MCP 让工具生态可组合，但它本身不决定上下文的质量。一个接入了二十个系统的 Agent，如果不知道在什么场景该调用哪一个，接口再标准也只是增加了选择困难。MCP 的常见失效包括权限过宽、schema 漂移、服务不可用，以及把「能调用」误当成「应该调用」。

工具描述本身就是上下文。工具名称、参数说明、返回结构，都会影响模型的选择。工具太多、描述太像，模型就会犹豫或选错；工具太少，Agent 又会退回到猜测。MCP 让接入变便宜，但也让工具膨胀变容易，所以治理层要控制工具白名单和可见范围，执行层要根据任务阶段动态暴露工具，而不是一次性把几十个工具全塞给模型。

Prompt 是单次任务中人类对模型的直接指令。在上下文工程的视角下，Prompt 是最窄、最即时的控制手段。它能精确表达这一次的意图，却无法承载跨任务的一致性，也无法管理持久状态。Prompt 的局限性恰恰是其他机制存在的理由：需要跨任务一致，就写进 Skill；需要跨会话记住，就写进 Memory；需要实时事实，就走 RAG 或 MCP。把所有东西都塞进 Prompt，最后会得到一个又长又脆、无法维护的超级提示词。

Prompt 通常承担三种角色：任务说明、约束条件和示例。任务说明告诉模型做什么，约束条件告诉它不能做什么，示例告诉它做到什么程度。三者混在一起，模型容易把示例当成硬性要求，或者把约束当成建议。更稳妥的写法是把指令与数据分开，把稳定约束放进系统层，把可变输入放进用户层，并对可能包含注入内容的数据做隔离。Prompt 不是越长越好，超过一定长度后，新增指令的边际收益会快速下降，反而挤占真正重要的上下文。

Agent 是编排层。它根据任务目标，决定调用哪个 Skill、检索哪类 RAG 结果、写入或读取哪段 Memory、通过 MCP 使用哪个工具。Agent 是上下文的消费者和调度者，而不是生产者。它不拥有知识，也不拥有记忆，它做的是在正确的时间把正确的来源组装起来。用编译器的比喻可能更好理解：Agent 把「目标 + 可用来源 + 约束」编译成一次上下文装配方案。装配方案的质量，决定了模型看到的世界。

执行层的核心矛盾是调度策略如何影响输出质量。取多了，上下文被噪声稀释；取少了，关键约束缺失；取错了，模型会自信地沿着错误前提推理。一个成熟的 Agent，应该能说明自己为什么选了这个来源、为什么排除了那个来源，以及在信息不足时准备问什么。

编排可以拆成四个决策：选源，决定这次任务需要哪些上下文来源；取量，决定每个来源取多少；排序，决定模型先看到什么、后看到什么；刷新，决定哪些信息在任务中途需要重新获取。四个决策都受预算约束，也都需要可解释。Agent 最常见的失败不是不会调用工具，而是过度检索：为了保险把所有相关文档都拉进来，结果关键约束被淹没。另一个常见失败是过早收敛：第一轮拿到一个看似合理的答案就停止，没有验证反例。

机制 运行时角色 控制粒度 不负责什么
MCP 连接工具与环境 单次调用 不判断该不该用、不保证结果可信
Prompt 表达单次意图 单轮或单任务 不承载跨任务一致性、不管理持久状态
Agent 编排来源与工具 任务全流程 不生产知识、不替代治理规则

第三层：上下文的治理与边界

治理层回答的是：谁来保证上下文的使用是可控、安全、可审计的。这一层的核心是 Harness。

业界常把 Harness 描述为围绕基础模型的 wrapper：它不改变模型权重，而是约束模型能做什么、不能做什么、什么时候必须停下来等人。它不生产上下文，也不直接执行任务，而是提供运行时治理：编排策略、权限边界、成本控制、安全确认、冲突检测和审计记录。

把 Harness 放在最高层，不是因为它比 Agent 更聪明，而是因为它处理的是其他所有机制产生的风险的收敛问题。RAG 可能引入错误知识，Memory 可能被污染，Skill 可能过时，MCP 工具可能被滥用，Prompt 可能被注入，Agent 可能规划错误。每一层都有自己的失败模式，而 Harness 是最后一道闸门：它决定哪些动作可以直接执行，哪些必须降级，哪些必须停下来问人。

风险来源 Harness 的控制手段
RAG 召回错误或过时 来源白名单、时效校验、引用回溯、冲突检测
Memory 被污染 写入审批、置信度、有效期、可删除与可回滚
Skill 过时或误用 版本锁定、适用范围校验、连续失败告警
MCP 权限过宽 最小权限、工具白名单、调用配额、沙箱
Prompt 注入 指令与数据分离、输入过滤、敏感动作二次确认
Agent 规划错误 预算上限、步骤上限、关键节点人工审批
成本失控 任务预算、模型档位、熔断与降级

治理层最容易犯的错误，是把它做成一个只会说「不行」的关卡。过度拦截会让 Agent 失去价值，用户开始绕过系统；规则太旧会让治理与现实脱节；审批太频繁会让人变成橡皮图章。好的 Harness 应该像一套交通规则：大多数时候你感觉不到它，但它决定了出事故时谁先停、谁来处理、如何追溯。

治理可以按事前、事中、事后拆开。事前做策略与准入：哪些工具可用、哪些数据可读、哪些动作需要审批；事中做运行时控制：预算、步骤上限、冲突检测、敏感动作拦截；事后做审计与复盘：记录决策依据、保留上下文快照、统计拦截与放行比例。三者缺一不可。只有事前规则，系统会在运行时失控；只有事中拦截，规则会越来越臃肿；只有事后审计，问题只能事后发现。

冲突检测是治理层最容易被忽略、又最该补的能力。它不需要很复杂：同一事实出现多个来源时，比较来源等级、更新时间和适用范围；无法判断时，不要静默选择，而是把冲突暴露给上游或用户。冲突检测的价值不在于自动裁决所有矛盾，而在于让「系统在矛盾信息上做了选择」这件事变得可见。

治理规则本身也需要被治理。谁有权修改规则、修改后如何评审、如何灰度、如何回滚、出问题谁负责，这些必须有明确归属。通常的做法是：平台团队负责运行时策略与工具权限，业务团队负责验收标准与人工确认点，安全与合规团队负责数据边界与审计要求。规则要版本化，关键决策要有记录，指标要能证明规则有效，而不是只证明规则存在。

三个边界问题

分层之后，真正有价值的问题才会浮出来。以下三个边界问题，是这套架构能否落地的关键。

第一，Memory 与 RAG 冲突时信谁。 一个实用的原则是：事实归 RAG 和工具，偏好归 Memory。政策、价格、接口、库存这类会变化的事实，应该以权威来源为准；用户的语气偏好、历史决策、项目习惯，才适合放在 Memory。如果 Memory 里存了事实，它就必须带上来源、时间和适用范围，并在冲突时让位给更新、更权威的来源。冲突不能静默处理，系统要标记出来，必要时向用户确认。

落地时，可以给每条记忆加一个类型字段：事实、偏好、决策。事实型记忆必须带来源和有效期，冲突时让位给权威文档；偏好型记忆可以长期保留，但要有适用范围；决策型记忆要记录当时的理由和被否决的选项，避免下一次只看到结论。这样，Memory 与 RAG 的冲突就从「谁更可信」变成了「这条记忆是什么类型、该不该由它回答」。

flowchart TD
    Q[同一事实出现冲突] --> S{来源等级是否明确}
    S -->|是| A[采用高权威来源]
    S -->|否| T{时效是否明确}
    T -->|是| N[采用更新来源]
    T -->|否| C[标记冲突并向用户确认]
    A --> L[记录决策、来源与时间]
    N --> L
    C --> L

第二，Skill 与 Prompt 的边界在哪。 判断标准不是长度，而是复用性与验收方式。会被反复使用、有明确质量标准的，应该沉淀为 Skill；一次性的、只针对当前任务的，留在 Prompt 里。如果 Skill 越写越厚，正确的做法不是继续加长，而是拆分：流程留在 Skill，模板抽成独立文件，工具调用交给 MCP，判断逻辑交给 Agent。把 Skill 写成超级提示词，等于把可维护的流程重新退化成一坨文本。

一个可操作的厚度阈值是：当一个 Skill 超过十个步骤、需要三份以上模板、或者开始包含条件分支时，就应该考虑拆分，把流程、模板、工具和判断分别交给不同层。Skill 负责「做什么、按什么顺序」，Prompt 负责「这一次的特别要求」，MCP 负责「怎么访问外部系统」。边界清楚了，三者才不会互相吞噬。

第三，Harness 的治理规则由谁维护、如何迭代。 不能让 Agent 自己给自己定规则，也不能让某个业务团队偷偷改权限。治理规则应该像基础设施一样管理：有 owner、有版本、有评审、有灰度、有回滚、有审计。每次线上事故之后，除了修 Prompt 和补测试，还要问一句：这是不是某条治理规则的缺口？如果是，规则要不要更新？更新之后，如何证明它没有把正常任务也拦掉？

诊断清单：Agent 出错时按什么顺序排查

分层框架的最终用途，不是画一张好看的图，而是在故障发生时给出排查顺序。下面这份清单按「成本低、频率高、影响大」排序，建议从前向后查，不要一上来就换模型。

顺序 排查对象 典型症状 检查动作 修复方向
1 Memory 旧规则反复出现、偏好被错误固化 查写入来源、有效期、最近覆盖记录 清理污染、加过期与复核
2 RAG 引用过时、答非所问、来源缺失 查召回文档版本、权威性、相关性 修索引、加时效与引用
3 Skill 流程步骤缺失、连续同类失败 查 Skill 版本、适用范围、验收结果 更新流程、拆分过厚封装
4 Prompt 指令被忽略、数据被当成指令 查注入痕迹、指令与数据是否分离 隔离数据、收紧指令
5 MCP 工具报错、权限不足、结果异常 查 schema、权限、服务状态 修适配器、收权限、加降级
6 Agent 规划绕路、重复调用、取多或取少 查任务分解、来源选择、循环次数 改调度策略、加步骤上限
7 Harness 该拦没拦、该放没放、无法追溯 查规则覆盖、审批记录、冲突检测 补策略、加审计、调阈值

排查顺序的理由很实际：Memory 和 RAG 是最高频的污染源，修复成本也最低；Prompt 和 Skill 次之；Agent 与 Harness 的改动影响面最大，应该放在最后。每次故障复盘后，把新发现的症状补进清单，清单才会越来越贴近真实系统。

这张清单有一个隐含的判断：大多数「模型变笨了」的问题，其实发生在上游。模型看到的上下文已经错了，换一个更强的模型，只会让它更自信地重复错误。先查 Memory 和 RAG，再查 Skill 和 Prompt，最后才怀疑 Agent 和模型，通常能更快定位问题。

诊断清单也不是追责清单。它的目的是让团队在面对一个坏结果时，有共同的排查语言：这是生产层的问题、执行层的问题，还是治理层的问题。分层不是为了让责任更分散，而是为了让修复动作更准确。

小结

七个概念不是七个并列的知识点，而是一条上下文供应链上的不同角色。生产层负责原料的可靠性与时效，执行层负责在正确时机装配正确的来源，治理层负责让前两层产生的风险收敛。Memory 与 RAG 的冲突要靠来源等级和时效规则解决，Skill 与 Prompt 的边界要靠复用性与验收标准划分，Harness 的规则要靠版本化与审计持续迭代。判断一个 Agent 是否成熟，不是看它用了多少概念，而是看它在上下文冲突时有没有明确的裁决机制。先修接缝，再谈能力。
