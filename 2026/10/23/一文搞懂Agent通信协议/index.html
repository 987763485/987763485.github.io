一文搞懂 Agent 通信协议：MCP、A2A 与 ACP

一个客服 Agent 接到退款请求，先要通过 MCP 查订单和物流，再要把需要人工审核的案例交给风控 Agent。前一件事是纵向的工具与数据接入，后一件事是横向的 Agent 协作。很多团队试图用一套协议同时解决两者，最后得到的是一个耦合、难替换、难审计的黑盒。拆开看，这两个动作的失败模式完全不同：查订单失败，通常是工具不可用、参数不对或权限不足；把案例交给风控失败，通常是对方不接、任务超时、产物不符合契约，或者中途需要人补充信息。用同一套超时、重试和错误码处理两类问题，系统会变得既笨重又脆弱。本文把 MCP、A2A 与 ACP 放回各自的问题域，讲清它们的边界、现状与组合方式。

一个 Agent 的两类通信

Agent 的通信可以粗分成两个方向。纵向是 Agent 到工具、数据源和外部系统：查数据库、读文件、调工单、发消息。横向是 Agent 到 Agent：把子任务委托出去、等待结果、处理中途的补充信息、在失败时换一个执行者。两个方向的约束不同，协议也就不同。

纵向通信的关键是「能力描述与调用」。Agent 需要知道有哪些工具、每个工具接受什么参数、返回什么结果、出错如何表示；还需要控制权限、超时、重试和审计。横向通信的关键是「任务与身份」。Agent 需要知道对方是谁、能做什么、如何把任务交出去、任务进行到哪一步、产物如何接收、出问题谁负责。

纵向通信更像远程过程调用，重点是接口稳定、参数校验和幂等；横向通信更像任务委托，重点是状态机、产物和责任人。把两者混在一起，最常见的后果是：工具调用被套上任务生命周期，延迟和复杂度上升；Agent 协作被简化成一次函数调用，失败后无法恢复。

MCP 主要解决纵向问题，A2A 主要解决横向问题。ACP 曾经试图用另一套 REST 风格解决横向问题，但在 2025 年 8 月并入了 A2A。把三者并列成「三个竞争协议」是常见的误读；更准确的说法是：MCP 和 A2A 是两个互补的现行标准，ACP 是一段已经收敛进 A2A 的历史。

    U[用户] --> H[Host / Agent Runtime]

MCP：把工具和数据接进来

MCP 由 Anthropic 在 2024 年 11 月发布，定位是模型与外部数据、工具之间的标准化连接。它采用 JSON-RPC 2.0，角色分为 Host、Client 和 Server。Host 是承载 Agent 的应用，比如 IDE、桌面客户端或服务端运行时；Client 负责与某个 Server 建立一对一的连接；Server 暴露工具、资源和提示词。Host 负责整体体验和安全策略，比如决定哪些 Server 可见、哪些工具需要人工确认；Client 负责协议细节，维护与 Server 的会话；Server 负责能力实现，可以是本地进程，也可以是远程服务。一个 Host 可以同时连接多个 Server，但每个 Client 与 Server 之间是独立的会话，能力声明、授权和错误处理都按连接隔离。

MCP 的服务端原语有三类。Tools 是模型可以主动调用的函数，适合查询、写入、执行动作；Resources 是应用可以读取的上下文数据，适合文档、记录、文件；Prompts 是用户可以选择的结构化提示模板，适合固定工作流。客户端侧还有采样、根目录和补充询问等能力，用来让 Server 在需要时请求模型或用户参与。三类原语的调用方向不同：Tools 由模型发起，Host 执行策略检查；Resources 由应用读取，模型不一定直接看到；Prompts 由用户选择，适合把团队的标准流程固化下来。理解调用方向很重要，不是所有能力都该做成 Tool，读多写少的上下文更适合 Resource，固定模板更适合 Prompt。

传输层有两类常见形态：本地进程用 stdio，远程服务用 Streamable HTTP。早期的 HTTP 加 SSE 方案已经被 Streamable HTTP 取代，后者在同一端点上处理请求与流式响应，部署和网关适配更简单。远程 MCP 的授权通常走 OAuth 2.1，配合作用域和资源指示器，把「这个客户端能访问哪些工具和数据」写进令牌。远程部署还要考虑会话恢复、流式响应的背压、网关的超时设置和审计日志。stdio 适合本地开发和个人工具，但进程生命周期与 Host 绑定，崩溃恢复要靠 Host；Streamable HTTP 适合多租户服务，但要把认证、限流和租户隔离做在网关或 Server 侧。两种形态的安全假设不同，不能直接复用同一套配置。

MCP 的边界也很清楚。它解决「Agent 如何安全、统一地调用工具」，不解决「Agent 如何把任务委托给另一个 Agent」。它没有跨组织的任务生命周期，没有 Agent 身份与委托链，也没有任务级的产物契约。把 MCP 当成多 Agent 协作协议，会缺很多语义，最后只能靠自定义字段补齐。一个具体的判断方法是看「谁对结果负责」：MCP 的工具调用结果由 Host 和用户负责，Server 只提供能力；A2A 的任务结果由服务端 Agent 负责，客户端只负责验收。这个责任边界决定了错误处理、重试和审计应该放在哪一层。

MCP 还有一个容易被忽略的安全面：工具描述和工具返回都是不可信输入。恶意的 MCP Server 可以在工具描述里埋指令，也可以在返回内容里做提示注入。因此 Host 需要做工具白名单、输出隔离、敏感动作确认和审计；远程 Server 还需要来源校验和最小权限。协议只提供通道，不提供信任。以一个工单系统为例：Host 启动时连接 Jira MCP Server，Server 声明 search_issues、create_issue、add_comment 三个工具；模型根据用户问题选择 search_issues，Host 校验参数与权限后转发；Server 返回结构化结果，Host 决定是否把结果放进上下文。整个过程是同步的、工具级的，没有任务状态机，也没有跨 Agent 的产物契约。

A2A：把任务交给另一个 Agent

A2A 由 Google 在 2025 年 4 月发布，同年 6 月捐给 Linux Foundation，2026 年 3 月发布 1.0 版本。它的目标不是让 Agent 共享内部状态，而是让不同厂商、不同框架的 Agent 在不暴露内部工具、记忆和实现的前提下协作。这个原则通常被称为「opaque agent」：对方只需要知道你能做什么，不需要知道你内部怎么做的。这一点对跨组织协作很关键。甲方不需要把内部知识库、工具权限和编排逻辑暴露给乙方，只需要发布一份 Agent Card，说明能承接什么任务、输入输出是什么、如何鉴权；乙方也不需要理解甲方的实现，只按任务契约提交请求、接收状态和产物。

A2A 的发现机制是 Agent Card。每个 Agent 在约定路径暴露一份卡片，描述名称、版本、支持的能力、技能、输入输出模态、服务端点、安全方案和签名。客户端读取卡片，判断这个 Agent 是否能承接任务，再选择对应的传输绑定。1.0 版本支持 JSON-RPC 2.0、gRPC 和 HTTP+JSON 三种绑定，Agent Card 可以用 JWS 签名，降低卡片被篡改的风险。Agent Card 不是简单的宣传页，它同时承担发现、能力协商和安全元数据的职责：客户端根据 supportedInterfaces 选择绑定，根据 skills 判断能否承接，根据 securitySchemes 选择认证方式，根据签名判断卡片是否被篡改。卡片写错，后面的调用再正确也会失败；卡片写得过宽，又会把不该暴露的能力暴露出去。

A2A 的核心对象是 Task、Message、Part 和 Artifact。Task 是长期运行的工作单元，带唯一标识和上下文；Message 是任务中的一轮交流；Part 是消息里的内容片段，可以是文本、文件或结构化数据；Artifact 是任务产物，比如报告、补丁、表格。任务状态通常包括提交、工作中、需要输入、需要授权、完成、失败、取消和拒绝，覆盖了人在回路和权限升级的场景。

通信方式支持同步请求、流式响应和异步推送。流式适合进度反馈和长回答；异步推送适合小时级甚至天级的任务，通过 webhook 通知状态变化；需要输入和需要授权两个状态，则把「Agent 停下来等人」变成协议内的标准动作，而不是靠自定义轮询。任务状态机是 A2A 的核心价值之一，它把「需要用户补充信息」「需要升级授权」「已经完成」「被拒绝」这些现实情况写进协议，让客户端可以据此决定是继续等待、切换执行者，还是转人工。没有状态机，多 Agent 协作只能靠自定义字段和轮询，最后每个团队都实现一套不兼容的语义。

A2A 的边界同样明确。它不规定工具怎么接，工具仍然走 MCP 或厂商自有接口；它不规定 Agent 内部如何规划；它也不替你做授权决策。Agent Card 的签名只能证明卡片来源，不能证明对方一定会按承诺执行；跨组织的身份、委托、计费和责任划分，仍然需要额外的治理设计。还有一个工程细节：A2A 的任务可能很长，客户端要处理断线重连、重复通知和产物幂等。协议定义了状态和操作，但没有替你实现存储、去重和补偿，这些仍然要在服务端和客户端各自完成。以退款审核为例：客服 Agent 读取风控 Agent 的 Agent Card，确认它支持 refund_review 技能和 JSON-RPC 绑定；随后创建 Task，附上订单号和用户诉求；风控 Agent 进入 working，发现缺少凭证时把状态改成 input-required；客服 Agent 补充材料后，任务继续，最终返回一个 Artifact，包含通过、拒绝或转人工的结论与理由。整个过程可以持续几分钟到几天，客户端不需要一直占用连接。

ACP：一个已经并入 A2A 的协议

ACP 由 IBM Research 在 2025 年 3 月推出，用于支撑开源的 BeeAI 平台，定位是 Agent 之间的开放通信协议。它走 REST 路线，用 OpenAPI 描述接口，支持多模态消息、同步与异步、流式交互、有状态与无状态模式、在线与离线发现，以及长任务。它的 Agent Manifest 用来描述 Agent 能力，Run 和 Session 用来管理执行与状态。REST 路线的优势是工具链成熟：OpenAPI 可以生成客户端，网关可以做鉴权限流，日志和追踪可以复用现有体系。异步优先则让长任务不必占住连接，客户端可以提交后离开，稍后回来取结果。离线发现对边缘场景有意义，Agent 可以在没有中心注册表的情况下，通过本地清单找到彼此。

ACP 的设计取向和 A2A 不完全一样。REST 风格更容易接入现有的 HTTP 基础设施、网关和监控体系；异步优先更适合长任务；有状态会话和离线发现，对边缘或受限网络环境更友好。这些想法本身有价值，也是它一度被讨论的原因。

2025 年 8 月，ACP 宣布并入 A2A，归属 Linux Foundation。ACP 官方文档挂出了「ACP is now part of A2A」的公告，仓库进入归档状态，BeeAI 平台提供了迁移到 A2A 的适配路径。ACP 的 REST 优先、异步优先、长任务和离线发现等设计，随后以不同形式影响了 A2A 的演进。合并带来的直接后果是选型收敛：新项目不需要再在 A2A 和 ACP 之间做长期押注，直接选 A2A 即可；已有的 ACP 部署需要评估迁移成本，尤其是 REST 接口、会话模型和发现机制与 A2A 的差异。BeeAI 提供了适配器和迁移指南，但迁移不是改一个 URL，任务状态、产物格式和授权模型都要重新对齐。

这里有一个命名坑。ACP 这个缩写至少还对应另外两个东西：Zed 提出的 Agent Client Protocol，用于编辑器与编码 Agent 之间的通信；Cisco 与 AGNTCY 体系里的 Agent Connect Protocol。本文讨论的是 IBM/BeeAI 的 Agent Communication Protocol。看到「ACP」时，先确认上下文，否则很容易把三套不同的东西混为一谈。从 ACP 的经历还可以得到一个选型教训：协议的价值不只取决于设计，还取决于治理、采用者和迁移成本。REST 风格、异步优先这些设计并不差，但当生态不足以支撑长期演进时，最好的结局往往是被更大的协议吸收。对团队来说，押注一个协议之前，先看它的治理主体、版本节奏和迁移路径，比看功能列表更重要。

这张表最重要的不是逐项对比，而是第一行：问题域不同。MCP 的调用对象是工具，A2A 的调用对象是 Agent，ACP 曾经也是 Agent，但它已经不再独立演进。把 MCP 和 A2A 放在一起比较「谁更好」，就像比较螺丝刀和扳手；它们都重要，但拧的不是同一种螺丝。再补充两个容易混淆的点：MCP 也有 Server 和 Client，但它们是工具提供方与连接方，不是两个对等的 Agent；A2A 的客户端和服务端都是 Agent，只是角色不同。三者都谈「能力发现」，但 MCP 的能力是工具级，A2A 的能力是技能级，ACP 的能力是 Agent 级，粒度不同，治理方式也不同。

怎么组合：同一系统里的分层

一个成熟系统通常会同时用到 MCP 和 A2A。Agent 运行时通过 MCP 连接自己的工具和数据源，通过 A2A 把跨团队、跨厂商的子任务委托出去；内部编排仍然由自己的 Agent 框架负责，不交给协议。协议负责边界上的互操作，框架负责边界内的 planning、memory 和 tool selection。

flowchart TD
    H[Agent 运行时] --> M1[MCP Client]
    M1 --> S1[工单 MCP Server]
    M1 --> S2[数据库 MCP Server]
    H --> A1[A2A Client]
    A1 --> E1[风控 Agent]
    A1 --> E2[法务 Agent]
    E1 --> M2[MCP Client]
    M2 --> S3[风控数据 MCP Server]

选型可以先问三个问题。第一，对方是工具还是 Agent？工具走 MCP，Agent 走 A2A。第二，是否跨组织或跨框架？跨边界优先 A2A，因为 Agent Card、任务生命周期和产物契约就是为这个场景设计的。第三，是否已有 ACP 资产？如果有，优先评估迁移到 A2A，而不是在新项目里继续扩 ACP。组合时还要决定「谁做编排」：如果编排在客户端 Agent，服务端 Agent 只负责执行，任务契约要写清楚输入、输出、超时和失败语义；如果编排在服务端，客户端只提交目标，服务端要返回足够的过程状态，避免变成黑盒。两种模式都能工作，但不能混着来，否则责任边界会模糊。

组合时还要补三件协议之外的事。身份：谁代表谁、委托链有多长、权限如何撤销。授权：A2A 的 Agent Card 能描述安全方案，但具体能不能调用某个技能，仍要由服务端做策略判断。可观测性：跨 Agent 的任务要能串成一条 trace，记录任务 ID、调用方、被调方、状态变化、产物和失败原因。缺了这三件，协议只能保证「能连上」，保证不了「能负责」。身份与授权值得单独展开：跨 Agent 调用通常不是「一个用户对一个 Agent」，而是「用户委托 Agent A，Agent A 再委托 Agent B」。委托链越长，权限越容易失控。至少要记录谁发起、谁转委托、每一跳的范围和有效期；服务端要能验证令牌的受众和范围，客户端要能撤销下游权限。A2A 的 Agent Card 可以声明安全方案，MCP 的 OAuth 作用域可以限制工具访问，但两者都不替你设计委托模型。

常见的误区有六个。第一，把 MCP 和 A2A 当成竞品，重复造一套工具调用或多 Agent 编排。第二，用 A2A 做工具调用，把每个工具包装成一个 Agent，成本和延迟都会上去。第三，用 MCP 做多 Agent 委托，缺少任务状态、产物契约和人工介入语义。第四，以为 ACP 还在独立发展，把新系统建在归档协议上。第五，把协议当成实现，忽略了重试、幂等、超时、审计和版本兼容。第六，双协议重复：同一个能力既通过 MCP 暴露成工具，又通过 A2A 暴露成技能，结果两套权限、两套审计、两套超时，维护成本翻倍。能力应该只在一个地方定义，另一个协议通过适配器引用它；否则协议分层只是把单体拆成了两个更难维护的单体。

版本、生态与选型建议

协议都在快速迭代，版本兼容是落地时必须面对的问题。MCP 的规范按日期版本发布，写本文时最新版本是 2026-07-28；客户端和服务端需要在初始化时协商能力，不能假设对方支持所有原语。A2A 在 2026 年 3 月发布 1.0，但现网仍有不少 0.3 时代的实现，JSON-RPC 方法名、枚举命名和 Agent Card 字段都发生过变化；接入前要确认对方实际支持的版本，而不是只看文档首页。版本兼容要落到测试里：至少准备三组用例，同版本互通、跨小版本互通、跨大版本降级。对 MCP，重点测初始化能力协商和工具 schema 变化；对 A2A，重点测 Agent Card 字段、方法名和任务状态的兼容；对已经归档的 ACP，重点测迁移后的任务语义是否一致。没有互通用例，版本升级只能靠运气。

生态方面，MCP 的工具生态更成熟，适合先落地；A2A 的跨厂商协作生态在基金会治理下扩张，适合处理组织边界；ACP 的生态已经并入 A2A，新项目没有理由再从 ACP 起步。SDK 的成熟度也不一样：有的语言支持完整，有的只覆盖 JSON-RPC 绑定；有的 SDK 同时兼容 0.3 和 1.0，有的只支持单一版本。选型时要把 SDK、网关、监控和身份系统一起评估，不能只看协议规范。还要看治理主体和变更节奏：MCP 与 A2A 都进入了基金会治理，规范变更、弃用和安全响应有公开流程；ACP 已经归档，不再有新的规范演进。选型不只是选技术，也是选一个会持续维护的生态。安全基线也要单独验收：MCP 要测工具描述注入、返回内容注入、越权调用和本地 Server 的沙箱；A2A 要测 Agent Card 篡改、伪造身份、任务重放和产物污染；ACP 迁移后要确认原有的鉴权、会话隔离和审计没有丢失。协议提供的安全机制是积木，不是成品。

一个务实的落地顺序是：先用 MCP 把工具和数据接稳，解决权限、审计和提示注入；当出现跨团队或跨厂商的 Agent 协作需求时，再引入 A2A，先把 Agent Card、任务契约和人工介入点定义清楚；最后补身份、授权和可观测性。不要一上来就搭一个「全能 Agent 网络」，协议能解决互操作，解决不了业务边界和责任划分。还有一个现实建议：把协议封装在适配层后面。业务代码不要直接依赖某个 SDK 的方法名，而是依赖自己定义的 ToolClient、AgentClient 接口；协议升级或更换绑定时，只改适配层。这样既能享受标准生态，又不会被某一个版本的实现锁死。

小结

MCP 解决 Agent 到工具与数据的纵向连接，A2A 解决 Agent 到 Agent 的横向协作，ACP 是曾经尝试用 REST 风格解决横向问题的协议，已于 2025 年 8 月并入 A2A。三者不是三个并列的竞品，而是两个现行标准加一段已经收敛的历史。落地时先分清对方是工具还是 Agent，再选择 MCP 或 A2A；跨组织协作要补身份、授权与可观测性；新项目不要再把 ACP 当独立标准。协议只是边界上的契约，真正决定系统能不能长期运行的，是边界之外的治理与工程。
