大模型能力与速度的两本账：八种手段的适用边界

很多团队把「模型不够好」和「模型太慢太贵」当成同一个问题，结果选错了手段。能力不足，可能需要数据、微调或检索；速度不足，可能需要量化、推理引擎或部署架构。两本账的优化目标不同，混在一起谈，容易得出「换更强的模型」这种正确但昂贵的结论。本文把八类手段拆成三个杠杆，分别算清能力账和速度账，再给出按约束选型的顺序。

先分清两本账

能力账衡量的是「做对多少」。它至少包含任务成功率、事实准确性、指令遵循、长上下文理解、工具调用可靠性，以及特定领域的风格与规范。不同任务对这些维度的权重不同，一个在通用问答上更强的模型，未必在你们的合同审阅或工单分类上更强。

速度账衡量的是「多快、多贵、能扛多少」。它至少包含首 token 延迟、单 token 生成时间、吞吐量、p95 延迟、显存占用，以及每个被接受任务的综合成本。只看平均延迟会掩盖长尾抖动，只看单请求速度会忽略并发吞吐，只看 token 单价会漏掉重试和人工复核。

两本账并不独立。量化能同时降低显存和延迟，但可能损伤长尾精度；RAG 能提升事实性，却增加一次检索往返；蒸馏能加快推理，但能力上限受教师约束；LoRA 能低成本适配领域，却可能带来遗忘；全量微调能抬高能力上限，但成本和风险都高；架构优化可能同时改善能力和速度，却需要重新训练并承担生态适配风险。

所以第一步不是选手段，而是测量：当前瓶颈到底在能力还是速度，具体落在哪个指标上。没有测量，后面的选型都是在猜。

测量的最低要求，是建立一个能重复运行的基线。基线要固定模型版本、推理参数、硬件环境和请求分布；否则今天测出来的提升，可能只是环境变化带来的噪声。能力基线用黄金任务集，速度基线用生产流量的采样回放；两者都要记录 p50 与 p95，而不是只记平均值。

八种手段的分层：三个杠杆

把常见手段按「改什么」归类，会得到三个杠杆：改权重、改上下文、改计算图与部署。八种手段可以对应到这三个杠杆上。

手段 杠杆 改什么 主要收益 主要代价
LoRA 微调 改权重 插入低秩适配矩阵 领域适配、风格对齐 可能遗忘、需要数据
知识蒸馏 改权重 用教师指导小学生 能力下沉、推理变快 上限受教师约束
RAG 改上下文 外挂知识库与检索 事实性、时效性、私有知识 检索延迟与工程质量
全量指令微调 改权重 更新全部参数 通用能力与多任务上限 算力、数据、遗忘风险
架构优化 改权重 注意力、位置编码、结构 长上下文、吞吐与建模 重训成本、生态适配
模型轻量化 改计算图 量化、剪枝、换结构 显存下降、延迟下降 精度损失、硬件限制
推理引擎优化 改执行 KV 缓存、批处理、融合 吞吐提升、首 token 降低 实现复杂、调参成本
部署架构优化 改部署 并行、调度、请求拆分 大模型落地、并发承载 通信开销、运维复杂

这张表里有两点容易被忽略。第一，蒸馏同时出现在能力账和速度账里：它既是能力迁移手段，也是轻量化手段；本文把它归在改权重，速度收益视为派生结果。第二，RAG 不改权重，所以它提升的是「可获得的事实」，不是「模型本身的推理能力」；把 RAG 当成能力升级，会在需要复杂推理时失望。

还有一个隐含前提：三个杠杆的改动成本不同。改上下文最快，通常几天到几周就能上线；改权重需要数据、训练和评测，周期以周或月计；改计算图与部署介于两者之间，但强依赖硬件和推理框架。选型时先考虑低成本杠杆，不是为了省事，而是为了让反馈更快。

八种手段也不是互斥的。RAG 可以和 LoRA 组合，前者补事实，后者补行为；蒸馏之后可以再量化，进一步压缩端侧模型；推理引擎优化和部署架构优化通常一起做。但组合的顺序会影响结果：先蒸馏再量化，学生模型可能同时承受两种损失；先量化再蒸馏，教师和学生的数值精度又可能不一致。组合方案要按「先改能力、再改速度、最后调部署」的顺序验证，避免误差叠加。

能力账：五种提升手段的边界

LoRA 微调冻结主干权重，只在注意力层等位置插入低秩适配矩阵，只训练少量新增参数。它的优势是数据需求小、单卡可跑、可以保留原模型通用能力，适合垂直领域适配、固定对话风格、特定输出格式。它的边界也很清楚：低秩容量有限，复杂推理和大规模知识注入不是它的强项；数据质量差时会过拟合；多个 LoRA 叠加可能互相干扰；部署时要考虑是否合并权重，以及多适配器如何路由。

实际落地时，LoRA 的效果很大程度取决于数据而不是秩。几百条高质量、覆盖边界情况的样本，往往比几万条重复样本更有用；rank 从 8 提到 64，收益可能远小于把标注错误清理一遍。目标模块的选择也很关键：只调注意力层的 q、v，和同时调所有线性层，容量与稳定性不一样。上线前要测合并权重后的推理一致性，避免训练环境和 serving 环境的数值差异。

知识蒸馏用一个高能力教师模型指导小模型，传递输出概率分布、中间特征或生成的训练数据。它适合把能力下沉到端侧、低算力环境，或者把一个昂贵的大模型压缩成可承受的推理服务。蒸馏的边界是教师：教师会的，学生未必学得会；教师错的，学生会学得更像。容量差距过大时，蒸馏会退化成模仿表面措辞；教师数据还涉及授权和合规问题。

蒸馏有两种常见路线：一种传 logits，让学生学习教师的概率分布，信息量更大，但需要教师和学生的词表对齐；另一种传思维链或生成数据，工程上更简单，但容易把教师的错误一起复制。前者适合同架构压缩，后者适合跨架构迁移。无论哪种，都要保留一个独立的学生评测集，不能用教师打过分的数据同时训练和验收。

RAG 在推理时先检索相关文档片段，再交给模型生成回答。它适合实时、私有、专业领域知识，比如企业内部问答、最新政策、产品文档。RAG 的边界不在生成，而在检索：分块是否合理、嵌入是否匹配、召回是否覆盖、重排是否准确、引用是否可回溯。检索质量不行，生成模型再强也只能在错误材料上加工。RAG 还会增加一次检索延迟，并带来权限与数据隔离问题。

RAG 的验收要拆成检索和生成两段。检索看召回率、命中率、排序质量；生成看引用是否支持结论、是否遗漏关键条件、是否在证据不足时拒答。只测最终答案，会把检索错误和生成错误混在一起，无法定位。工程上还要处理文档更新、删除和权限继承，否则知识库会变成新的技术债。

全量指令微调用大规模高质量指令数据更新模型全部权重。它适合有充足算力、希望系统性提升通用能力与多任务表现的团队，也是旗舰模型迭代的核心方式。它的边界是成本和风险：数据清洗与配比要求高，训练不稳定，容易发生灾难性遗忘和安全对齐回退；一次全量训练的代价，往往不是小团队能承担的。

全量微调真正难的是数据配比。通用能力、领域知识、指令遵循、安全对齐，需要按比例混合；某一类数据过多，模型就会在其他维度退化。训练过程中要持续跑回归集，而不是只观察训练损失。对于大多数业务团队，全量微调的投入产出比不如 LoRA 加 RAG；它更适合有明确模型迭代目标的团队。

架构优化改进注意力机制、位置编码或整体结构，比如用更高效的注意力降低长序列的显存与计算，或换用线性复杂度结构。它可能同时改善长上下文能力和推理吞吐。但它的代价最高：通常需要重新训练，甚至重新预训练；新结构需要算子、框架和推理引擎的配套支持；生态不成熟时，纸面收益很难在生产环境兑现。

架构优化的判断标准，不只是论文指标，而是端到端收益：新结构在目标硬件上的实际吞吐、显存、延迟，以及训练稳定性。位置编码的改动尤其容易影响长上下文外推能力，必须用真实长文档验证，而不是只看短序列的损失曲线。没有训练和推理全链路支持时，架构优化应该放在最后考虑。

手段 数据门槛 算力门槛 能力上限 主要风险
LoRA 低到中 低 中 遗忘、适配器冲突
知识蒸馏 中到高 中 受教师约束 教师偏差、容量不足
RAG 中 低 受检索质量约束 召回错误、权限泄露
全量指令微调 高 高 高 成本、遗忘、对齐回退

速度账：三类提速手段的边界

模型轻量化包括 4/8 比特量化、结构化剪枝、知识蒸馏和换线性注意力架构。量化把权重和激活压到更低比特，直接降低显存和带宽压力，是端侧和成本敏感场景的常用手段；它的风险是精度损失，尤其是在长尾任务、数值敏感任务和多语言任务上。结构化剪枝删除整块通道或层，硬件友好，但通常需要再训练恢复精度。蒸馏在前面说过，速度收益来自更小的学生模型。线性注意力把序列交互的复杂度从平方降到线性，长文本场景收益明显，但可能损失一部分建模能力。

推理引擎优化包括 KV 缓存复用、连续批处理、算子融合和动态解码。KV 缓存复用避免重复计算历史 token，前缀缓存还能让相同系统提示词的请求共享计算结果；连续批处理在请求结束时立刻插入新请求，显著提升吞吐；算子融合减少内核启动和显存往返；动态解码根据置信度或投机采样调整生成策略，降低单 token 时间。这些手段的共同点是「不改模型权重」，因此能力损失通常最小，但实现和调参成本不低。

推理引擎的收益高度依赖请求形态。短请求、高并发时，连续批处理收益最大；长上下文、重复系统提示词时，前缀缓存收益最大；小 batch、低延迟场景，算子融合和动态解码更直接。反过来，如果请求长度差异很大，批处理可能拉高 p95；如果缓存命中率低，KV 复用只是增加复杂度。

部署架构优化包括多卡张量并行、流水线并行、动态批处理调度，以及把 RAG 的长问答拆成检索加短生成。张量并行把单层计算切到多卡，降低单卡显存压力，适合大模型低延迟；流水线并行把不同层放到不同卡，吞吐更高，但气泡和通信开销需要调优；动态批处理调度根据请求长度和优先级组批，兼顾吞吐与 p95；RAG 短生成拆分则通过减少输出 token 来降低整体耗时，代价是回答可能更简短。

并行的选择也要看目标：张量并行降低单请求延迟，适合在线交互；流水线并行提升吞吐，适合离线批处理；两者混用时，通信和气泡会吃掉一部分收益。部署架构的调整往往牵动容量规划、故障域和成本模型，不能只按 benchmark 的 tokens/s 决策。

类别 具体手段 主要改善 主要代价
模型轻量化 4/8 比特量化、结构化剪枝、蒸馏、线性注意力 显存、延迟、端侧可行 精度损失、重训、生态限制
推理引擎 KV 缓存复用、连续批处理、算子融合、动态解码 吞吐、首 token、单 token 时间 实现复杂、调参成本

行业里常见的「延迟降 30%—70%」「吞吐提升 2—4 倍」「长问答耗时降 40% 以上」都是量级参考，不是承诺。同样的优化，在不同模型、不同硬件、不同请求分布下，结果可能差很远。验收必须用你们自己的流量和任务集。

两本账互相影响：没有免费的加速

所有提速手段都在某个维度上付费。量化用精度换显存和带宽；剪枝用结构完整性换计算量；蒸馏用能力上限换模型规模；并行用通信开销换单卡显存；批处理用排队时间换吞吐；RAG 短生成用回答完整度换延迟。

能力手段也一样。LoRA 用适配器容量换训练成本，可能牺牲通用能力；RAG 用检索工程换知识更新，可能引入错误材料；全量微调用算力换能力上限，可能牺牲对齐与稳定性；架构优化用重训风险换长期收益。

因此不要问「哪个手段最好」，而要问「在当前约束下，哪个手段的代价我可以接受」。一个团队能接受 1% 的精度损失换取一半的显存，另一个团队可能一分都不能丢；一个团队能接受 200 毫秒的检索延迟换取事实性，另一个团队可能要求首 token 在 100 毫秒内。约束不同，答案就不同。

举一个具体的组合例子：一个团队想把客服问答的首 token 延迟压到 300 毫秒，同时要求政策准确率不下降。单做量化，延迟可能达标但准确率掉两个点；单做 RAG 短生成，准确率保住了但检索延迟又加回来。可行的组合是前缀缓存加连续批处理，先把引擎层的水分挤掉，再对非政策类问题做小范围量化。每一步都单独评测，才能知道收益和代价分别来自哪里。

顺序还会影响可观测性。先做引擎优化，通常不影响模型输出，适合作为第一步；再做量化或蒸馏，能力变化更容易归因；最后动架构或全量微调，风险最高，也最应该单独评估。把改动按「输出不变、输出微变、输出可能大变」排序，能让团队在每一步都有可回退的基线。

怎么选：按约束排序的决策流程

选型可以按五步走。第一步，测量瓶颈：是任务成功率不够，还是首 token、p95、吞吐或成本不达标。第二步，列出硬约束：数据能否出域、算力预算、延迟 SLO、精度红线、知识更新频率。第三步，按约束筛掉不可行的杠杆。第四步，用黄金任务集做小规模验证，同时看两本账。第五步，灰度上线，保留回滚。

验证阶段要设计对照：同一批任务，用基线和新方案各跑一次，固定随机种子和推理参数；能力指标看任务成功率与失败类型，速度指标看 p50、p95 和吞吐，成本指标看每个被接受任务的总成本。灰度阶段先放小流量，观察错误率、降级率和人工介入率，再逐步放量。

有一个常见的错误，是同时上多个手段，然后无法判断收益来自哪里。正确做法是一次只改一个变量，保留基线，记录能力、速度、成本三组指标，再做下一个。另一个错误是只在空载环境测速度，生产环境的请求长度分布、并发模式和缓存命中率，会彻底改变结论。

常见误区与验收指标

第一个误区是用困惑度代替任务成功率。困惑度下降不代表业务指标变好，尤其在分类、抽取、工具调用这类结构化任务上。第二个误区是只看平均延迟，不看 p95 和 p99；用户感知到的卡顿，往往在长尾。第三个误区是忽略输出长度：首 token 很快，但生成很长，整体体验依然差。第四个误区是量化或剪枝后只测通用集，不测长尾、对抗和安全用例。第五个误区是把蒸馏当成免费的能力复制，忽略教师偏差和容量差距。第六个误区是全量微调后不做回归测试，导致安全对齐和格式遵循悄悄退化。

验收指标建议分成四组。能力组：任务成功率、事实准确率、指令遵循率、长上下文召回率。速度组：首 token 延迟、单 token 时间、吞吐、p95 延迟。成本组：每千 token 成本、每个被接受任务成本、显存占用。可靠性组：错误率、重试率、降级率、人工介入率。四组一起看，才能避免「优化了一个数字，恶化了整体体验」。

验收集也要分层：通用能力、领域任务、长尾与对抗、安全与合规。每类保留基线，每次改动都跑同一套。对于生成类任务，自动指标不够时加人工盲评；对于工具调用类任务，重点看 schema 合规与执行成功率，而不是措辞。

还有一个容易忽略的验收维度：稳定性。同一个任务重复运行多次，结果是否一致；模型版本升级后，行为是否漂移；长尾输入是否触发异常。能力提升如果以稳定性为代价，生产环境往往得不偿失。

第七个误区是只看公开 benchmark。公开集的分布和你们的业务分布往往不同，榜单上的提升不一定能复现到生产。用自有任务集做验收，是最低要求。

小结

能力账和速度账是两套目标，不能用同一个手段包打天下。八种手段可以归到改权重、改上下文、改计算图与部署三个杠杆，每个杠杆都有自己的收益和代价。选型的顺序是先测量瓶颈，再列硬约束，然后用黄金任务集小规模验证，最后灰度上线。所有加速都在某个维度上付费，所有能力提升也都有成本；关键是明确当前最不能妥协的指标。一次只改一个变量，两本账一起看，比追逐单点最优更可靠。
