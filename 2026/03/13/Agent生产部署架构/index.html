从能跑通的 demo 到一上线就出的事故

先讲一个示意场景，它是把多类常见故障合并之后的虚构案例，涉及的数字都是示意值。一支团队用 LangGraph 1.0 搭了个客服 Agent：接一个对话模型，读工单系统，再挂几个内部工具。demo 阶段跑得很顺，在笔记本上连续完成三十轮多步推理，演示会上管理者亲眼看到它自己把一张退款工单处理完了。上线之后一周内出了三件事。第一，一次例行的滚动重启把进行中的会话清零——会话状态存在进程内存里，实例一重建，上下文就没了，用户只能从”我刚才说到哪了”重新讲起。第二，一个查询类工具 hang 住将近九十秒，调用方没有超时约束，工作线程被逐个拖死，整个服务在半小时里雪崩成 503。第三，消息队列把一批待办任务重投了一次，Agent 毫不知情地给同一位客户发了五封内容相同的邮件。

这三件事的共性在于：demo 验证的是推理循环能不能转起来，生产验证的是这个循环在一万个并发、随时可能重启、处处会超时的环境里还能不能正确地转起来。智能体负载从演示环境走向线上，中间至少隔着八条差距，本文后面每一节都会对应到其中之一：

  • 状态：会话与任务状态放在哪里，进程重启后能不能续跑；
  • 超时：单步推理、单次工具调用、整棵任务树，各自的预算由谁执行；
  • 并发：长耗时循环占住连接与线程的方式，会不会把宿主拖垮；
  • 凭据：模型密钥与第三方工具的访问凭据如何下发、如何轮换、如何避免泄漏进日志；
  • 出口：模型调用与工具调用是否可以被审计、被限流、被切断；
  • 观测：一次跨分钟甚至跨小时的多步交互，能不能被一条链路串起来回溯；
  • 回滚：提示词、路由表、模型版本这些”软发布物”出了问题是能不能一键退回；
  • 成本：token 与工具调用开销能不能归因到具体业务线，而不是月底一张总账单。

需要划清的是：本文不讲智能体作为编程模型内部的推理循环如何组织，那部分另一篇《Agent 架构设计总览》已经展开；我们只关心这些负载落到机房与集群里之后，需要什么样的部署结构。

把负载切成五层：部署拓扑的骨架

对付上面八条差距，最可靠的起手式是按”有没有状态””失败归谁负责”把智能体应用切成五层。

接入层是无状态的。它承担终端或业务系统的连接、身份认证、配额检查与幂等键登记，不保存任何会话内容。因为无状态，它可以躲在常规负载均衡后面按连接数和请求速率横向扩容，实例随时可杀可补——前提是把上文第一条差距里的教训听进去了：任何”杀掉实例会丢东西”的组件都不能被归进这一层。

编排层是回合推进与工具选择的所在，形态上可以是一个 Python 进程里的图执行器，也可以是按会话片段拉起的一次性 worker。关键在于它的部署属性：编排层进程本身不持有会话数据，每一步从外部状态存储按会话标识读入、算完写回。这样编排层同样具备了”可随意重启”的性质，版本发布时不需要等长会话自然结束。

执行层是工具调用与代码运行的实体，包括直接外呼第三方 API 的短任务，也包括要跑用户提交代码的沙箱。它是安全边界最紧、故障模式最杂的一层，伸缩特性由队列而非请求速率决定——积压深度才是该加机器的信号。

模型与工具出口是所有对外调用的汇聚点。在这个架构里我们不让业务代码直连模型供应商或外部工具，而是全部收敛到统一出口网关，由它执行白名单、超时、重试、去重和审计。后面「出口治理」一节会展开。

状态存储是恢复语义的裁决者。会话、任务、中间产物分别放什么介质，直接决定了重启后哪些能续跑、哪些只能重做。

flowchart TD
    U[客户端或业务系统] --> GW[接入层: 认证 + 配额 + 幂等键]
    GW --> ORCH[编排层: 回合推进与工具选择]
    ORCH --> STORE[(状态存储: 缓存 / 数据库 / 对象存储)]
    ORCH --> Q[任务队列]
    Q --> WORKER[执行层: 工具 worker 与沙箱]
    ORCH --> EGRESS[出口网关]
    WORKER --> EGRESS
    EGRESS --> LLM[模型服务]
    EGRESS --> EXT[外部工具 API]
    ORCH --> OTEL[观测管道]
    WORKER --> OTEL
    STORE --> BAK[备份与归档]

这五层与经典微服务分层并不陌生，关于智能体应用整体架构如何一步步演进成这个样子，《AI 应用架构演进》一篇已有论述；本文只锁定每层在生产部署里的职责与伸缩特性。一个实用的检查方法是：对每一层问一句”这一层的实例现在全部杀掉，用户会感知到什么”，答不上来的层，就是架构里最薄弱的一层。

会话状态放哪：四种介质的取舍

上一节把状态存储称为”恢复语义的裁决者”，这里把裁决做细。智能体的可持久化数据大致分三类：会话状态（对话历史、图执行的检查点、待办中间变量）、任务状态（队列里每个作业的生命周期记录）、产物（工具生成的文件、报表、截图）。三类数据的访问频率与体量差好几个数量级，硬塞进同一种介质一定会别扭。

先看四种候选介质的取舍：

介质 延迟 持久性 容量上限 重启后能否续跑 典型用途
进程内存 最低 无 受单实例内存约束 不能 demo、单测、秒级临时变量
Redis 类缓存 低 弱（配置得当可近似） 受集群内存约束 多数能 会话检查点、锁、幂等键
数据库 中 强 高 能 任务状态、审计记录、长期档案
对象存储 高 很强 几乎无限 能 产物、大附件、脱敏归档

开篇事故里”重启丢会话”的直接修法，就是把图执行器的检查点从内存挪进外部存储。以 LangGraph 1.0 这类带检查点能力的编排框架为例，正确的部署姿势是检查点后端指向 Redis 或数据库，编排进程保持无状态，任何实例拿到会话标识都能接着执行。要警惕的是把缓存当数据库用：Redis 的内存成本决定了它只适合放”最近活跃”的会话窗口，过期策略一旦激进，长周期任务会在最贵的时刻发现状态已经蒸发。我们的经验是给会话状态定义明确的存活期，超期的会话降级到数据库，只保留摘要与索引。

还有一条容易忘的约束，与介质选择同级重要：对话原文不要进缓存键，也不要长期明文留存。缓存键会出现在慢查询日志、监控面板与各类调试输出里，把用户标识甚至会话片段编进键名，等于把敏感数据复制到了所有能看见键的地方。键里只放不透明标识符，这是接入层鉴权之后生成、与内容无关的 ID。留存周期要在设计期就定下来并写进配置：谁定义、多长、到期做什么（删除还是脱敏归档），不能等法务找上门才补。敏感字段的脱敏应发生在写入存储之前，而不是查询时再遮。《Agent 安全与权限控制》对凭据类数据的落点已有更细的规定，本文不重复。

长任务的部署形态：队列、看门狗与超时预算

会话型负载尚可同步应答，一旦单任务耗时以分钟计——多轮调研、批量处理工单、跨系统对账——同步 HTTP 就成了灾难的温床：连接被长期占用、网关按秒级超时机械切断、客户端重连造成重复提交。生产形态应当改为”提交即返回，结果走通知”：接入层收到请求写入任务队列就回作业凭据，编排 worker 从队列领取任务异步执行，进度与终态通过回调或轮询交付。

这套形态里有三个部件。任务队列本身不必发明新东西，成熟的中间件皆可，选型时看的是优先级、延时投递与死信能力这三项是否齐备。心跳与看门狗解决”僵尸任务”：worker 领任务后周期上报心跳，看门狗服务扫描超过约定时间没有心跳的作业，将其判定失效并决定重投还是放弃。这个部件的完整失败语义——重投几次、幂等如何兜底、毒任务如何隔离——属于机制细节，《Agent 失败恢复与重试》一篇已经系统展开，本文只强调它的部署位置：看门狗必须独立于 worker 进程组，否则 worker 群灭时看门狗陪葬，恢复机制形同虚设。

超时预算要分层。单次模型调用有单步预算，单次工具调用有出口预算，整棵任务树有整体预算，三层数字必须递减——整体预算大于各步预算之和是常态，但任何一步的预算都不得超过它所在层的配额，且最内层的超时必须真实传给发起调用的客户端库，而不是只写在文档里。示意值如此设置：单步模型调用六十秒，单个工具调用三十秒，整任务十五分钟，均为团队约定示例，应随业务调整。编排层负责在预算耗尽时走降级路径，而不是让请求在层层等待中自然腐烂。

出口治理：让所有外呼只有一条门缝

智能体应用与常规后端服务在流量形态上最大的差别，是它的出向调用有一半是”运行时才知道要调什么”的：模型决定了这一轮要访问哪个工具的哪个接口。放任这种自由度直接上线，等于把公司的网络出口交给一个不确定行为者。出口治理的第一原则是把出站调用收敛为唯一路径——编排层与执行层所在的工作负载在集群层面禁止直连公网，只允许访问出口网关；模型供应商地址与外部工具域名登记在网关白名单里，白名单之外一律拒绝并留审计记录。这条约束在 Kubernetes 1.35 的网络策略与既有服务网格能力下是常规操作，不展开。

网关收敛之后，三件事才有了统一的落点。其一是超时与重试的归属：重试策略只写在出口网关这一层，编排层与执行层禁止各自藏着退避逻辑——两处都重试会相乘成重试风暴，这个教训在开篇事故的雪崩段落里已经付过学费。各层只保留超时，超时到了把失败如实上抛，由编排层决定业务级降级。其二是请求指纹与去重：网关对每次外呼计算规范化指纹（目标端点、参数摘要、会话标识、时间窗），在短窗口内对指纹重复的请求直接返回上次结果或拒发，挡住编排 bug 造成的同参数死循环轰击供应商接口。指纹计算必须剔除时间戳等易变字段、且不得把凭据纳入摘要输入，否则去重失效或反向泄漏。其三是配额与审计：按业务线维度统计 token 消耗与外呼次数，既是成本归因的数据源，也是异常行为（比如某个会话在十七秒内发起上百次搜索）的告警依据。

模型调用入口的流量整形、路由与降级策略本身是一整套网关设计，那部分《模型服务网关设计》已有专文；本文的边界是：智能体应用必须站在网关后面，且网关的策略由平台团队而不是各业务团队分头维护。

凭据管理：下发、短时化与四条禁区

出口有了门，还得管钥匙。智能体应用的凭据池比常规服务更杂：模型供应商密钥、MCP 服务器的连接凭据、各内部系统的服务账号、沙箱内代码可能需要的临时授权。如果这些凭据以环境变量或明文配置文件的形式预置在每个 worker 里，那么任何一次日志打印、任何一份镜像导出、任何一个被攻破的沙箱都是泄漏面。

生产做法是由平台密钥服务统一下发，随取随用。工作负载启动时不携带长期密钥，只持有一个由集群身份背书的工作负载标识；需要调用某出口时，向密钥服务申请该用途的短时凭据，凭据带使用范围与存活期约束，到期自动作废，轮换因此不需要重启任何进程。密钥服务自身按标准的高可用加密存储形态部署即可，重点在于把它当作出口网关的同级基础设施来对待——它挂了，所有外呼都应显式失败，而不是悄悄回退到镜像里藏的旧密钥，这类回退配置恰恰是审计中最常见的”化石凭据”来源。

幂等与去重：把”至少一次”的世界掰回”恰好一次”

开篇事故里那五封重复邮件值得单独一节。生产消息通道给出的投递语义通常是”至少一次”：队列重投、消费端超时重领、用户看到没反应又点一次提交——每一条路径都可能把同一个意图变成两次执行。对普通 CRUD 服务，重复执行往往被数据库唯一键挡下；对智能体，重复执行意味着重复的模型消费、重复的外呼副作用，以及用户视角下”这个助手疯了”。

防线要设在最外层。接入层对每次写操作要求幂等键：客户端生成、或由网关基于请求要素代生成，键与会话或任务标识绑定，落进缓存与数据库双份存储。同一个幂等键的第二次到达，不再触达编排层，直接返回第一次的受理结果。编排层的检查点进度记录、出口网关的请求指纹，则分别作为第二、第三道防线，作用是把上游漏网的重复在真正花钱之前拦下。

灰度与回滚：模型版本也是一种发布物

智能体应用的发布物清单比常规服务长一倍：容器镜像、提示词模板、工具注册表、路由表、评测集，以及最特殊的——模型版本。把模型版本当作配置字符串里可随手改写的字段，是灰度能力缺失的根源。生产做法是把它纳入与镜像同级的发布管理：每个模型版本有登记条目、有变更记录、有对应的评测通过记录，改路由就是改发布物，走同一套审批与回滚流程。Anthropic 工程栏目那篇《agent evals》讲的就是这类发布前评测怎么搭，此处不展开评测本身。

分桶单位决定灰度粒度。按租户分桶适合 B 端场景——先放三个内部租户，观察一周再扩；按会话分桶适合 C 端场景——新用户的新会话才进实验桶，进行中的会话绝不跨桶迁移，否则同一个对话上下文中途换模型，行为漂移会污染两边的观测数据。实现上就是接入层查一次路由表：桶号由不透明会话标识哈希得出，路由表存放在配置中心并带版本号，路由表本身的回滚因此只是一次配置版本切换，秒级生效。

发布卡点建议至少设三条。其一，评测门禁：候选模型版本或新版提示词必须先通过固定评测集，阈值数值由团队约定、属于团队约定示例，重要的是”不过门禁不进灰度桶”这条流程约束；其二，双桶对照：灰度期间保留一个同规模对照桶，成本与质量指标并列观察，防止”新版本看起来没问题”其实是样本不足；其三，一键退回路径演练：回滚动作本身要在演练里被真实执行过——路由表切回、镜像退版、凭据不受回滚牵连这三件事各验证一遍。回滚最容易踩的坑是”配置退回了旧版，但旧版引用的模型端点已下线”，这正是把模型版本纳入发布物登记的价值：登记表里能看见每个版本的服务期限。镜像层的滚动与版本管理属于通用发布工程，与《Agent 原生应用架构》讨论的应用结构问题交集不大，本文按下不表。

可观测与告警：让一次跨小时的多步交互可以被回溯

传统服务的观测以”一次请求”为单位，智能体负载的天然单位却是”一次会话”或”一个任务”，它扇出成几十次模型调用与工具调用，横跨分钟甚至小时。trace 关联键的设计必须围绕这个天然单位：在接入层为每个会话或任务生成一个贯穿标识，此后每一次模型外呼、每一次工具执行、每一条队列消息都携带它；编排层的检查点记录用同一个标识串起每一步的输入输出摘要。排查时先按会话标识拉出整棵调用树，再下钻到单步，而不是从一堆孤立日志里猜因果。属性命名只讲原则：业务归属、模型版本、桶号、出口端点类别这几类维度必须挂在链路属性上，字段的具体拼写由团队约定示例统一定义即可；本文关心的是”哪些维度缺了就没法做下文两件事”，采集与存储管道的选型属于《AI 应用的可观测性》的范畴，一句划界。

第一件事是成本归因。token 与工具调用开销要能落到业务线而不是月底一张总账单，靠的正是链路与出口审计上的归属维度：每笔消耗都能回答”哪个租户、哪条业务线、哪类任务”烧的。归因粒度到”任务类型 × 模型版本”通常够用，更细的收益递减。推理侧的成本与容量话题另有《大模型推理服务架构》专文处理，本文只认领”归属维度必须在应用侧就打进属性里”这条部署要求。

第二件事是 SLI/SLO 与告警分层。智能体应用的 SLI 至少四类：可用性（会话应答成功率）、时延（首响时间与整任务完成时间，建议分开看）、质量代理（用户追问率、人工接管率、评测门禁通过率）、经济性（单会话平均 token 成本、异常外呼率）。告警按影响面分层：秒级窗口的基础设施告警（队列积压深度、出口错误率）唤值班；小时窗口的质量漂移告警（追问率抬升）唤负责该 Agent 的产品与工程双人组；天窗口的成本告警（单会话成本环比抬升超过团队约定示例阈值）唤预算责任人。三层各配各的升级路径，避免把质量漂移用基础设施的寻呼强度去喊——那是团队疲劳的头号来源。

容量与弹性：按队列与槽位伸缩，而不是按 CPU

智能体 worker 的 CPU 曲线极不可信：一个领到任务的实例可能整分钟挂着网络等待，CPU 低得像闲死，实际并发槽位已满。伸缩信号应当取两类：队列积压深度（滞后指标，触发扩容）与并发槽位占用率（领先指标，逼近满位即扩）。并发槽位在实现上就是 worker 声明的”我能同时养几个进行中任务”，调度器按全局槽位水位做决策，这个水位阈值同样是团队约定示例。

背压必须与伸缩配套，否则积压只是换了个地方堆。位置有三个：接入层按队列深度与槽位水位对新请求排队或快速拒绝，绝不无底线接收；编排层对单会话的在途外呼数设上限；出口网关对各业务线配额设上限。三级数字从外到内递减收敛，任何一级触顶都返回明确的”稍后再试”语义而非静默超时。

冷启动从哪来？按 Kubernetes 1.35 的常规口径审视，智能体 worker 的启动路径上有四段开销：镜像拉取与解包、运行时初始化（Python 依赖装载或 Node.js 24 LTS 运行时的模块解析）、模型与工具的连通性预热（首次 TLS 握手、工具注册表拉取）、以及凭据获取。伸缩响应慢往往不是调度器慢，而是这四段串行且每段都按”新实例”重来。缓解思路是依据可预见的流量曲线提前拉起容量，而不是等积压告警被动追火；这部分属于集群层通用手段，具体规模不在此讨论。GPU 推理侧的容量与调度是模型服务的问题，本文的弹性只覆盖应用层——推理集群的规划细节在《大模型服务化实践》已有论述。

故障演练清单：上线前先把六种坏消息演一遍

前十节的结构是否真的成立，靠读架构图读不出来，只能注入故障验一次。以下六项是我们建议的最小演练集，每项按”注入什么、观察什么、期望表现”三栏执行，演练频率由团队约定示例（可按季度）。

场景 注入什么 观察什么 期望表现
模型超时 出口网关对指定模型端点注入长延迟直至超时 编排层预算消耗路径、会话失败率 预算内快速失败并走降级，连接与槽位按时释放
工具 500 对某外部工具端点返回持续 5xx 网关重试次数、错误是否上抛 仅网关层按策略重试，编排层拿到明确失败并降级，无重试风暴
队列积压 暂停部分 worker 制造积压 积压深度指标、接入层行为 背压触发新请求排队或快速拒绝，恢复后按序消化无丢失
缓存失效 清空会话状态缓存集群 进行中的会话、数据库回源 活跃会话按恢复语义续跑或优雅重开，回源风暴被限流挡住
出口权限收紧 收紧网络策略切断某域名 报错形态、审计日志 白名单拒绝有审计记录，业务收到明确错误码而非静默挂起
凭据轮换 强制吊销在役短时凭据 外呼成功率、密钥服务负载 各层按需重新申请，分钟级自愈，无人工介入

演练的判据要提前写死：每一项的”期望表现”若在演练中不成立，就回改对应节的架构决策，而不是给演练报告打圆场。尤其注意缓存失效一项——它是对本文第三层与第四层接缝（编排层无状态假设）最直接的攻击，跳过这条演练等于没验证过整个状态设计的核心承诺。

一张对照表收尾

把全文的部署对象放进同一张表，作为评审会上的速查页：

组件 是否有状态 失败影响面 缓解手段
接入层 无 入口不可用，新用户全断 多实例负载均衡、健康摘除
编排层 无（外置状态） 新回合停摆，存量可续 检查点外置、随意重启的发布方式
任务队列 有 长任务无法受理 中间件自身高可用、积压告警
执行层 worker 执行中有 单批任务失败 心跳看门狗、重投与死信队列
出口网关 有（指纹窗口） 全部外呼中断 网关多活、降级到备用供应商路由
密钥服务 有 新凭据不可发放 短时凭据缓冲存量会话、显式失败不回退
会话缓存 有 活跃会话需重开 数据库降级回源、恢复语义约定
数据库 有 状态全面不可写 主从与备份、写失败快速拒绝
对象存储 有 产物读写中断 重试与幂等上传、跨区冗余
观测管道 旁路 盲区而非停机 独立于业务集群部署、降级本地日志

小结

本文用一次编造的上线事故开场，把”demo 能跑、线上一触即溃”拆成状态、超时、并发、凭据、出口、观测、回滚、成本八条差距，再用五层拓扑逐一认领：无状态的接入与编排层负责可杀可补，队列与看门狗负责长任务，出口网关统一白名单、重试与指纹去重，密钥服务以短时凭据换掉预置密钥，幂等键加对账把”至少一次”掰回用户期待的”恰好一次”，模型版本升格为发布物使灰度与回滚成立，trace 关联键让成本归因与分层告警有了地基，队列深度与槽位水位取代 CPU 成为伸缩信号。最后一章的故障演练清单与组件对照表是给评审会准备的：架构的说法要能被故障注入证伪，才算数。所有阈值与数字在文中均为团队约定示例或示意值，落地时请按自己的业务重新约定。智能体应用的部署结构没有神秘之处，神秘的部分在循环内部，那不是本文的领地。
