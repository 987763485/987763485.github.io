多模态统一架构

同一张截图，走“OCR 加语言模型”的管线能得到一段文字，走统一模型却可能直接回答“右上角那个红色警告是什么意思”。差别不在模型大小，而在信息有没有在进主干之前就被丢掉。本文要讲的正是这件事：把图像、音频、文本整理进同一个序列空间、共享一套主干，究竟改变了什么，又付出了什么。读完你应当能判断自己的业务该选哪条架构路线，以及为什么换路线之后成本和评测都要重做。读者假定部署过多模态推理服务，或做过视觉语言应用的接口对接。

什么叫“统一”

先把词义钉住。本文所说的统一架构，指图像、音频、文本在进入主干之前都被整理成同一种可索引的符号，拼成一条序列，交给同一套参数、同一种注意力机制、同一个预测目标来处理。它的对立面不是“参数少”或“模态少”，而是多模型拼接的管线：OCR 一个模型、语音识别一个模型、目标检测一个模型，把各自的中间结果序列化成文本，再喂给语言模型。

两者的本质差别有三处。第一处是信息在哪一层被丢弃。管线里每个组件都按自己的目标做压缩：OCR 只留文字与外接框，检测只留类别与坐标，转写只留字符串。主干再聪明，也找不回被上游扔掉的颜色、版式、语气与停顿；统一架构把这些留在同一条序列里，让主干自己在注意力上决定读哪一段、读到什么粒度。第二处是误差怎么传播。管线是前向串接的，上游一次漏检就把错误当成事实往下送；统一架构端到端训练，梯度能一路回到视觉侧参数，被读错的形状有被改回来的机会。第三处是优化目标归谁。管线里每个组件各自对齐自己的指标，很难为“看完三张图再跨图比较”这类复合任务整体优化。

需要立刻划清边界：统一不等于一个模型包打天下，也不意味着管线方案被淘汰。本文后面会给出判定清单，某些场景下“检测加语言模型”仍然更稳、更便宜、更容易审计。

三条路线

第一类是视觉符号化后并入序列。用一个视觉编码器把图像压成一小段符号，经重采样或投影层对齐到文本 embedding 的维度，插进文本序列的某个位置，主干结构完全不动，LLaVA 一系的投影器就是这种形态的典型。它的训练数据以图文对与图文指令为主，推理形态是一次前向加自回归解码，可控性最好：数据侧知道图像占了哪几个位置，日志里能数出这段消耗了多少预算，也能用掩码控制模型看或不看。代价是分辨率上限被编码器的网格锁死，细节在压缩那一步就丢了。

第二类是交错序列训练。文档、网页、字幕、带插标的说明文本，天生就是图与文交替出现的，直接把整份原始顺序排成一条长序列，不做严格的“先图后文”重排。模型因此学到位置关系本身：紧跟某个小标题的那张图，和被挪到段落末尾的同一张图，语义并不相同。这条路线适合多图长上下文与跨模态生成，但它把压力全转移给了长度——序列一长，注意力与显存的问题会在下一节集中出现。

第三类是双塔加投影器做表征对齐。CLIP、SigLIP 一系让两个编码器各自成塔，用对比目标把同一份图文的表征拉到一起；ColPali 一类文档图像检索走得更远，把整页文档当成图像编码成 patch 级表征，让版面本身进入召回。它的优势在数据与成本：图文对噪声大也能用，索引可以离线建好，线上只算一次 embedding。它的劣势同样在对齐发生的位置——两个模态在表征层就见了面，主干根本没机会看原始细节。跨模态召回的工程做法属于《多模态检索实践》的范围，本文不重复。

    B1 --> C1[插入文本序列同一个空间]

    A2[图文交替文档] --> B2[按原始顺序排成一条长序列]

    B3 --> D2[只做检索或只做打分]
    D --> F[解码成文本或符号图像]

三条路线不是优劣排序，而是把“模态在哪一层合并”这件事往前挪还是往后挪。挪得越靠前，训练越省、检索越容易、细节丢得越多；挪得越靠后，主干能用的信息越全，代价全在长度、显存和数据清洗上。

分辨率买的是 token 预算

统一架构一旦成立，图像的“清晰度”就不再是一个视觉概念，而是一个长度概念。视觉编码的基本单位是网格上的一小块，边长固定时，块数随面积增长——这就是高清图更贵的全部原因：不是它“更大”，而是它贡献了更多符号，主干的注意力、KV 缓存、解码步数全都按符号数计费。

理解这一点之后，几种常见处理手段就能统一成一个口径。固定边长缩放并补空白，是拿无效符号换形状规整；把大图切成若干块分别编码，是把一次高成本换成多次中等成本，好处是每块都保细节，坏处是跨块的表格线、被切断的一行字这类接缝信息要么靠位置编码硬拼，要么直接丢；动态分辨率让模型按内容决定用多少块，把预算分配从“写死在预处理里”变成“跟着内容走”，代价是批内长度不齐、排度困难，同一请求两次的开销可能相差很大。

这三件事最终落到设计文档的三条口径上。

至于每档多少钱，按当期官方价目核对即可，本文不列数字。

解码侧：要不要让它生成图像

只输出文本的统一模型，词表就是原来那个词表，图像只进不出，整套解码逻辑与纯文本主干几乎一致。一旦要它也输出图像，三件事同时被改动。

第一是词表。要么给图像 token 开新条目，要么在主干之外挂一个扩散式的头，让主干先出语义、由头补细节。前者把 embedding 与输出投影两层同时扩大，新条目的表示只能靠训练数据喂，冷启动阶段容易吐出无意义块；后者保住了词表，但两段式解码的误差会叠加，主干规划的布局与头实际的落笔经常对不齐。第二是位置编码。文本的位置是一维序号，图像的位置天然是二维的；把图像 token 也排进一维序列，模型学不出平移不变性，同一块图案换个位置就像两个不同符号。这也是交错路线的常见难点：位置编码要么退化成纯顺序，要么改成行列分别编码，而后者与文本位置的组合规则必须一开始就定死，中途改动会让已有表示作废。第三是评测。只出文本时答案可以比对；能出图之后，“对不对”变成“像不像、合规不合规、有没有漏字”，需要引入跨模态判定，而这类判定自身带偏差。

    [*] --> 仅文本解码
    仅文本解码 --> 扩展词表生成: 要端到端出图
    仅文本解码 --> 外挂生成头: 要保住文本能力
    扩展词表生成 --> 跨模态评测: 判定需引入视觉度量
    外挂生成头 --> 跨模态评测: 判定需覆盖两段误差

笔者的倾向很明确：如果业务不需要产出图像，就不要为了“架构完整”去承担这三项改动。生成能力是产品决策，不是架构先进性的证明。

注意力与显存跟着符号数走

统一架构最容易被低估的连锁反应是长度。注意力要在序列内部两两比较，序列越长，单步计算与需要留存的键值状态压力增长越快，而图像恰恰是长度的放大器：一段视觉 token 常常比它要说明的那句提问长得多。

于是显存压力分成两层。第一层在 prefill：图像那一大段必须先完整算过一遍，键值状态一次性分配出来，此时还没有输出可以边生成边释放，请求的首字延迟由这段固定开销决定。第二层在 decode：每吐一个符号都要读一遍已有状态，状态越长读得越慢。图像的麻烦不只是占位，而是它的键值分布与文本很不相同——同一段视觉 token 内容相近、复用率低，却被前缀缓存当作普通前缀参与匹配，让命中率看起来不错、实际省不下多少。显存分页与块化管理的机制细节属于《KV Cache 与 PagedAttention》的范围，本文只借用它的结论：统一架构下决定显存碎片与复用效率的是符号序列的形状，而不是模态标签。

工程上，这意味着三件事被绑在一起。

这类细节在管线方案里由各组件自己承担，在统一方案里全部落在主干这一侧。

成本与评测口径为什么会一起变

只要按符号计费，同一句话换一种形态就是另一笔账。把表格截图发给模型，和把它转成文本再发过去，问的是同一件事，花的却不是同一笔钱——前者多付了视觉段，后者多付了一次上游调用与可能的信息损失。更微妙的是历史轮次：带图的对话被反复回传时，视觉段每轮都要重新算一遍，除非命中缓存。于是“同一个问题怎么送”成了成本问题，而不只是风格问题。预算换准确率的取舍本身属于《推理时计算扩展》的范围，本文只强调一点：统一架构下预算单位变了，原来按调用次数搭的成本模型要重做。

评测口径同样要跟着改。纯文本主干只需比对答案；跨模态以后，判定必须能对齐到视觉证据上，至少要问三类问题：答案里的每个论断能不能指回图中某个区域，指不回的是不是幻觉；同一张图换分辨率或换切块方式，答案稳不稳；图像被截断后，模型有没有老实说“看不清”而不是编。单一准确率不够用，因为它把“看错了”与“理解了但表达错”混成一格。更实际的做法是把指标拆开：一个只测视觉细粒度，一个只测跨模态整合，一个测拒答与不确定性。两个模型总分相近而拆分指标差异明显时，选型结论会完全相反。

失败形态的架构根因

常见事故几乎都能从上面几节推出原因，而不是归咎于“模型不够大”。

小字与密集表格最先丢。视觉编码在网格上取下采样，一行细字的垂直跨度可能不足一个块；一旦跨过块边界，它的能量被摊到相邻几块里，主干拿到的是模糊梯度而不是笔画。切块能救分辨率，却把表格的行列结构切成两段——单元格的归属关系靠的是版式，而版式信息恰好落在接缝上。

坐标不准是第二个必然结果。文本序列只有一维顺序，几何是二维的；模型要么把坐标离散成符号去背诵，要么在文本目标里回归数值，两者都跟预训练时学到的分布不完全合拍。加上视觉段的分辨率已经过一轮压缩，落到坐标上的误差是量化误差与投影误差叠加。

跨图对比退化最隐蔽。多图进同一条序列时，每张图都占一大段，跨图的依赖要拉长程注意力去建立；训练里这种“两图同时出现且必须互相参照”的样本本来就少，模型于是倾向于把后一张当成前一张的重复证据，给出一个折中答案。若请求侧还做了历史截断，被丢掉的正是要对比的那一张。

《多模态 Agent 实践》讲的是怎么接进去、怎么校验回来的结果，那是工程层；本文这几条是架构层的成因，两边不重复。知道成因的价值在于：前两类失败无法靠提示词修复，只能改分辨率口径或退回专用工具。

工程形态选择与数据代价

判定清单值得背下来，本文把它整理成两组条件。

专用识别器在最后一格上仍然更容易做校准，而统一模型在这一格上只能靠加预算硬扛。

数据侧的代价是这条路线最常被忽略的一栏，本文把它列成三项。

因此本文建议：数据能力没有跟上之前，先用可控性好的并入序列形态或干脆用管线，把交错与统一生成当作有意识的中期投入，而不是默认选项。这里不涉及任何数据集条数与规模，那些数字随版本变动太快。

小结

统一架构的定义只有一把尺子：模态在哪一层合并。合并得越晚，主干能用的信息越全，长度、显存、数据清洗三项代价越高；合并得越早，越省也越容易审计，但细节一去不回。分辨率、解码能力、评测口径都是这条主线的延伸——清晰度是长度，生成能力改的是词表与位置编码，评测因此必须拆成细粒度、跨模态整合与拒答三格。选型的实用判据是瓶颈落在哪：读不清小字就交给专用工具，需要跨模态的整体理解才考虑统一模型，只做召回就留在对齐形态。
