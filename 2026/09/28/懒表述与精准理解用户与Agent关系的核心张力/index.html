懒表述与精准理解：用户与 Agent 关系的核心张力

用户对 Agent 的表述正在变短：从一整段需求，变成一句「照上次那样改」。这不是能力退化，而是表达成本与纠错成本被重新计算之后的结果。本文把这种「懒」拆成三层信息损失，讨论 Skill、MCP 与长期记忆为什么最终都落到同一件事上：用上下文工程补全用户没说出口的部分。适合做 Agent 产品、交互设计和上下文系统的工程师。

用户不是变懒，是在算一笔账

「懒」这个词带有道德判断，但在交互系统里，它更像一个理性信号。用户每次开口，都在心里算三笔账：表达成本、认知成本和社交成本。表达成本是把想法组织成语言要花的时间；认知成本是判断哪些信息重要、哪些可以省略；社交成本是担心自己说得太细显得啰嗦，或者说得太粗显得不专业。三笔账加在一起，用户自然会选择「最小可行表述」：能用一句话解决，就不写一段话；能说「老样子」，就不重新列一遍要求。

同一个系统里，专家和新手的「懒」也不一样。专家省略的是自己熟悉的细节，期待系统懂行话、懂默认流程；新手省略的是自己不知道怎么描述的细节，期待系统给方向、给示例。前者需要的是术语和可调整的默认值，后者需要的是选项和渐进式引导。把两者都当成同一种「用户懒」来处理，系统就会在专家面前显得啰嗦，在新手面前显得武断。

模型越强，这个选择越明显。因为多写一句的边际收益在下降：用户发现只给一个模糊指令，模型也能给出七八十分的结果。于是表述继续缩短，直到某一次结果偏离预期，纠错成本突然升高。此时用户很少归因于「我没有说清楚」，更常见的反应是「你不懂我」。这不是用户不讲道理，而是交互系统长期训练出来的预期：既然你能猜对大部分，为什么这一次猜不对？

这里有一个容易被忽略的细节：用户的「懒」并不是均匀分布的。对于低风险、高频次的任务，比如改一段文案、整理一份会议纪要，用户愿意把表述压缩到极简；对于高风险、低频次的任务，比如数据迁移、合同条款、生产发布，用户反而会反复确认。真正决定表述长度的，不是用户的性格，而是错误的代价。Agent 如果只在所有场景里追求「更主动地猜」，就会在低风险场景显得聪明，在高风险场景显得危险。

把这件事翻译成设计语言：不要试图教育用户写更完整的提示词，而要降低「被理解」的成本。前者把责任推回用户，后者才是系统该做的事。一个成熟的 Agent，应该能接住一句含糊的话，把它变成几个可验证的假设，再用最低的交互成本确认其中最关键的那一两个。

用户说出口的 可能的意思 缺失的信息
「帮我写个周报」 汇总本周进展，面向直属上级 格式、篇幅、语气、哪些事不能写
「把这个改得专业一点」 调整措辞与结构，不改变事实 目标读者、行业术语、禁忌表达
「照上次那样做」 复用上一次的流程与参数 哪一次、哪些条件已经变化

表达赤字：说出来的、想说的、真正需要的

用户的一句话里，至少叠着三层信息。最外面是「说出口的表述」，中间是「想完成的任务」，最里面是「真正需要的约束与偏好」。三层之间不是翻译关系，而是持续丢失的关系。

以「帮我写个周报」为例。说出口的只有六个字；想完成的任务是汇总本周工作、暴露风险、让上级快速掌握进度；真正需要的可能还包括：沿用上周的三段式结构，语气克制，不点名批评同事，把尚未解决的问题写成待办而不是结论。后面这些信息，用户往往不会主动说，因为在他的语境里它们是「显然的」。但对一个没有共享语境的模型来说，它们一点都不显然。

模型只能用一个东西去填补这些空白：训练数据里的总体先验。它知道大多数周报长什么样，知道大多数职场表达偏向什么语气，但它不知道你的上级喜欢看结论还是看过程，也不知道你们团队上周刚刚因为一个线上问题被批评过。于是它给出一个「平均正确」的周报：结构完整、语气得体、放在任何公司都不会出错，但放在你这里就是不够用。

本文把这段差距称为「表达赤字」：从用户说出口的表述，到系统真正需要的信息之间，那段没有被说出来的部分。表达赤字不是提示词写得不够好，而是信息根本不在那句话里。继续优化提示词，只是在要求用户多写一点；而用户之所以少写，恰恰是因为他不想承担这部分成本。真正的解法，是让系统自己去获取、推断和验证这段缺失的信息。

    B --> C[模型可见的上下文]

这张图里，每一次箭头都可能丢信息，也都可能加噪声。上下文工程要做的，不是让用户把 A 完整写出来，而是让系统在 B 到 D 之间多几条可靠的获取通道：查一下历史记录、读一下项目文档、调用一次工具、问一个关键问题。每一条通道，都是在替用户补上他懒得说的那部分。

通用模型的极限：越强，越容易「平均正确」

通用大模型的能力，本质上来自对总体分布的压缩。它见过足够多的代码、文档、对话和决策，因此能在缺乏具体信息时给出一个统计上合理的答案。能力越强，这个「合理」的上限越高，但它仍然是总体意义上的合理，不是针对某一个用户的合理。

个性化需求是典型的长尾。你的代码风格、命名习惯、风险偏好、汇报口径、对哪些词敏感、在什么情况下希望被追问，这些都不在总体分布的中心。模型可以用先验去逼近，但逼近得越好，越容易产生一种危险的错觉：它看起来很懂你，实际上只是懂「像你这样的人」。

「平均正确」有四种常见表现。第一种是风格不符：内容没错，但语气、结构、详略不是你要的。第二种是约束遗漏：模型不知道你们有一条「对外文档不写内部代号」的规定，于是写了。第三种是过度泛化：把一个具体场景的建议，套用到另一个约束完全不同的场景。第四种是置信度错配：模型用同样肯定的语气，给出正确和错误的答案，用户无法从语气里判断哪一句该信。

举个具体的例子。让 Agent 改一段 Go 代码，用户只说「优化一下」。模型可能把循环改成并发，性能确实上去了，但引入了竞态；也可能把错误处理简化了，代码短了，可观测性没了。它给出的是通用意义上的「优化」，而用户想要的可能只是少一次内存分配。缺的不是模型能力，而是「优化」这个词在这位用户、这个项目里的定义。

面对这些问题，很多团队的第一反应是微调，训练一个「专属模型」。微调当然有价值，但它不是默认答案。微调需要稳定的数据、明确的评价标准、可承受的训练和推理成本，还要面对版本老化：用户的习惯会变，业务规则会变，模型权重却不会自动跟着变。更现实的问题是隐私：把用户的个人偏好写进权重，删除和纠错都会变得困难。

所以「专属模型」更准确的理解，是一个系统，而不是一份权重。基础模型提供通用能力，上下文层提供用户的世界，工具层提供事实，策略层决定什么时候该猜、什么时候该问。专属感来自这四者的组合，而不一定来自重新训练。把「专属」等同于「微调」，是把一个上下文问题误判成了训练问题。

专属化的三条路径：Skill、记忆与 MCP

当下被讨论最多的三种能力，恰好对应三类缺失的信息。

Skill 补的是「流程性知识」，也就是「这件事在我们这里怎么做」。它不是一段更长的提示词，而是一组可复用的步骤、约束和验收标准。比如一个周报 Skill，会规定先收集哪些数据、按什么结构组织、哪些内容必须标注风险、写完用什么清单自检。用户下一次只需要说「写周报」，系统就能把这一整套流程装进上下文。Skill 的关键是版本化与可组合：流程会变，变了要能回滚；不同 Skill 之间要能拼装，而不是互相覆盖。

长期记忆补的是「稳定偏好与历史决策」，也就是「我是谁、我以前怎么选的」。它至少可以分为三类：偏好记忆，比如语气、格式、禁忌词；事实记忆，比如项目背景、团队结构、长期目标；经验记忆，比如上一次为什么否决了某个方案。记忆的价值不在于存得多，而在于取得准。把所有对话原样塞进上下文，既贵又吵；真正有用的是经过提炼、带时间和来源、可以更新和删除的条目。记忆还需要衰减：三个月前的项目偏好，今天可能已经反转；一次临时决定，不应该变成永久规则。给记忆设置有效期和置信度，比不断增加条目更重要。

MCP 补的是「环境事实」，也就是「现在到底是什么情况」。用户说「把那个失败的构建修一下」，模型不知道「那个」指哪个仓库、哪条流水线、哪次提交。MCP 把文件系统、工单系统、日历、数据库这些真实环境接进来，让模型从「猜」变成「查」。它的价值不只是多几个工具，而是把用户的省略号替换成可验证的事实。

能力 补全的缺失 典型载体 常见失效
Skill 流程、规范、验收标准 版本化的步骤与检查清单 写成超长提示词，无法维护
长期记忆 偏好、历史决策、项目状态 结构化条目加检索 存成聊天记录，噪声淹没信号
MCP 环境事实与实时状态 标准化的工具与资源接口 当成万能插件，权限失控

这三种能力看起来分别属于流程、记忆和工具，但它们的共同点是一样的：决定模型在这一次调用里能看到什么。Skill 改变上下文的结构，记忆改变上下文的内容，MCP 改变上下文的来源。它们都不是模型能力的直接提升，而是上下文工程的不同侧面。

上下文工程：把没说出口的变成可计算的输入

如果把上下文工程压缩成四个问题，大概是：该放什么、该去掉什么、按什么顺序放、什么时候刷新。四个问题都围绕一个约束：模型的上下文窗口有限，用户的耐心也有限。放得越多不一定越好，噪声会稀释信号；放得越久不一定越好，过期的记忆比没有记忆更危险。

具体手段并不神秘。检索负责从大量资料里找出相关片段；摘要负责把长历史压缩成可读的决策记录；结构化画像负责把偏好写成字段，而不是散落在对话里；工具调用负责在需要时获取实时事实；澄清负责在信息不足时向用户要一个关键答案。它们的共同目标，是把「用户没说出口的」变成「模型可以计算的」。

澄清值得单独说。很多系统把「多问一句」当成笨拙，其实问得对，比猜错便宜得多。关键在问法：不要问「你想要什么」，那等于把表达成本又推回给用户；要给选项、给默认值、给可见的假设。比如「我按上周的三段式写，重点放风险和下周计划，可以吗？」用户只需要回「可以」或者改一个点。一次低成本确认，往往比一次高成本返工更划算。追问的次数也要有预算：一次任务最多问一到两个问题，超过这个数量，用户会觉得自己在填表，而不是在委托。

自主程度也应该由置信度决定，而不是由产品经理的偏好决定。高置信、低风险的任务，直接执行；中等置信的任务，执行但把假设写在结果里；低置信或高风险的任务，先给方案再等确认。把这条规则写进系统，比在每个场景里临时判断更稳定。

置信度与风险 系统行为 用户成本
高置信、低风险 直接执行，结果附假设 最低
中置信、低风险 执行并显式标注推断 低
低置信或高风险 给选项或方案，等待确认 中
信息严重不足 只问一个最关键的问题 可控

个性化不是一次性的配置，而是一个闭环：用户修正一次，系统提取一条偏好，存进记忆，下一次检索出来用，再观察是否被接受。闭环的关键是克制：不能因为用户改了一次标点，就认定他讨厌所有标点；也不能因为一次否决，就永久降低某类方案的优先级。偏好要有置信度、有适用范围、有失效时间。

专属化的代价：过度揣测、隐私与依赖

专属化不是免费的。系统越懂用户，越容易越界。

第一重代价是过度揣测。用户一次的偏好，可能被系统固化成长期标签；一个标签一旦进入画像，就会影响后续所有推荐。更糟的是反馈闭环：系统按画像给结果，用户在同一条路上修正，系统又把这个修正当成新证据，最后把用户困在一个越来越窄的假设里。避免这件事的办法，是让画像始终可解释、可反驳、可过期，而不是变成一个黑箱。

第二重代价是隐私。记忆里可能包含项目代号、客户信息、个人习惯，甚至健康和政治倾向。存得越多，泄露的收益和风险同时变大。数据最小化、明确授权、保留期限、删除能力、本地优先，这些不是合规装饰，而是专属化的前提。一个不能忘记的系统，不配拥有长期记忆。一个常见的误区是把「记住用户」当成默认开启的能力；更稳妥的做法是默认不记，只有用户明确授权或任务确实需要时才记，并定期提醒清理。

第三重代价是依赖与能力退化。用户越习惯一句话交付，越不愿意组织自己的需求；越依赖系统补全，越难发现系统补全错了。自动化偏差会让用户在大部分正确的结果里，失去对少数错误的敏感。系统应该主动打破这种惯性：在关键节点展示依据，在不确定时明确说不确定，在用户长期不检查时提醒复核。

透明是这三重代价的共同解药。用户需要知道系统假设了什么、依据是什么、哪些信息来自记忆、哪些来自工具、置信度大概多高。更重要的是，用户要能改：改一条记忆、删一段历史、关掉某类推断、要求下次重新问。专属化的目标，是扩大用户的控制感，而不是替用户做决定。

设计原则：让「懒」变得安全

把前面的讨论收敛成几条可以直接执行的原则。

第一，先补全，再追问。能用记忆、工具和历史补上的，不要问用户；必须问的，只问一个最关键的问题，并且带上选项和默认值。

第二，让假设可见。结果里标出「我假设你希望沿用上周格式」「我没有找到上周的数据，因此用了本周的估算」。可见的假设可以被纠正，隐藏的假设只会变成争吵。

第三，记忆要可查、可改、可忘。每条记忆带来源、时间、适用范围和置信度；提供查看、编辑、删除入口；默认不记录敏感信息。

第四，Skill 要版本化、可组合、可回滚。流程变更要像代码一样评审；不同 Skill 之间定义清晰的输入输出；失效时能退回上一版。

第五，能查就不猜。环境事实优先走 MCP 或等价工具；工具不可用时，明确告诉用户「这是推测」，不要把猜测包装成事实。

第六，用置信度决定自主程度。高置信低风险直接做，中置信标注假设，低置信或高风险先确认；把这条规则写进调度，而不是留给临场判断。

第七，用「被接受的任务」衡量效果，而不是用生成字数或对话轮数。真正有价值的指标是首轮接受率、修正率、每个被接受任务消耗的人工时间，以及出错之后的恢复成本。

这些原则有一个共同方向：把模糊性留在系统内部消化，而不是原样退还给用户。用户的「懒」不会消失，也不应该被指责。它是人对工具的正常期待：我少说一点，你多想一点；但你想错的时候，要让我容易发现、容易纠正。

小结

用户的极简表述不是能力问题，而是在表达成本、认知成本和错误代价之间做出的理性选择。通用模型的「平均正确」来自总体先验，无法自动变成对单个用户的理解，表达赤字只能靠系统补全。Skill 补流程，长期记忆补偏好与历史，MCP 补环境事实，三者本质都是上下文工程。专属化的关键不是训练一份新权重，而是把模型、上下文、工具和策略组合成用户可控制的理解系统。越懂用户的系统，越要克制揣测、保护隐私、保留用户的纠错能力。衡量它是否成功，最终看「被接受的任务」，而不是「生成的内容」。
