Agent 工具生态与 MCP Server

本文属于《Agent 智能体开发》第 19/55 篇
上一篇系列目录下一篇

协议文档读完，真要动手写第一个 MCP Server 的时候，问题会从「它解决什么」变成「每一步怎么定」：工具拆多细，参数怎么校验，长任务怎么取消，凭据放哪，日志留什么，版本怎么废弃，装到别人机器上凭什么被信任。这些内容不在协议正文里，却直接决定这个 server 能不能上线、能不能长期维护。本文按实现的先后顺序走一遍，最后收一份能逐条打勾的自查清单，不铺开协议演进史，也不做生态评估。

本文的位置：从读协议到写实现

先把边界说清楚，避免和几篇相邻文章重复。《MCP 入门》讲过协议的基本概念、消息形态和最小可运行例子；《工具调用机制》关心客户端这一侧，模型如何选择工具、参数如何生成、结果如何回填；《模型上下文协议生态》写协议要解决哪三件事、三类原语的责任边界，以及注册分发解决了什么、没解决什么；《Agent 工具协议标准化》给的是分层描述与治理流程的标准化视角；《LLM 网关与流量治理》站在出口位置，把工具调用当作一条受控门缝处理。本文不复述这些内容，只回答一个问题：作为 server 的作者，实现层要做哪些决策。

还要提前声明：文中的工具名、字段名、阈值和日志样例全部是本文自拟的示意，用来说明写法，不代表任何真实的第三方 server，也不构成对某个公开端点或接口拼写的引用。贯穿全文的立场只有一条：调用方是模型，而模型是概率性的、上下文有限的、会被提示注入影响的，所以实现层的每个选择都要把不可预测的调用方同时当成不可信的调用方。

能力声明与工具粒度设计

第一个要拍板的是粒度，最常见的错误做法是把上游 API 一对一映射成工具：后端有二十个接口，就暴露二十个工具。接口是给工程师看的，工具是给模型在有限注意力里挑选的，两者的组织方式不同。

我常用三条判据来拆或者合。第一，模型能否在一次推理里选对：两个工具若要靠读源码才分得清，就该合并或者改名。第二，参数能否被模型稳定生成：需要它凭空拼出复杂结构、或需要上游内部标识的参数，说明这个工具把不该模型承担的责任推给了它，通常要在前面补一个查询型工具。第三，失败面是否独立：一个动作会写数据、另一个只读，就必须分开，因为重试策略和权限作用域完全不同。

于是有两种形态：「窄工具」是动词清晰的少量工具，每个只做一件事，副作用与返回结构都写在描述里；「宽工具」是一个入口带操作枚举，数量少但分支语义藏在参数里。我的口径是读操作可以适度做宽，写操作一律做窄——宽读减少工具总数、降低选择难度，窄写让权限、幂等和审计按工具粒度对齐。

描述文案要写四件事，缺一个就会出事：前置条件（先调用哪个工具拿到什么）、副作用（改不改数据、多久可见）、返回结构（模型接下来能引用哪个标识）、以及何时不要用。第四件最容易被忽略，明确的负面边界比多加一个工具更能提高选择准确率。同理，能力没实现时要显式拒绝，别静默沉默：模型对「不存在」和「这次失败」的推断完全不同。

输入 schema、校验与错误语义

输入 schema 有两个读者。给模型看时要能被稳定地满足：类型少而明确，枚举列全，必填项只留真正不可缺的那两三个，默认值在描述里写明，格式约束用可自检的形式。给服务端看时它是不可信输入的入口：客户端传来的每个字段都要重新校验，包括那些「模型不可能填错」的字段，因为提示注入可以让它填错。

两类失败要报得不同：校验类错误指出哪个字段、什么约束、期望什么形式，让模型有改参数重来的机会；业务类错误说明为什么在当前状态下不可执行。混成一句「调用失败」，等于把重试和纠错能力都关掉了。

错误语义上我把故障分三层：协议层的问题，比如请求结构不合法，不该由工具去补；工具执行失败，返回一个明确表示失败的标记（这是本文对返回结构的示意说法，不指代任何具体字段拼写），配上可行动的文案；成功但语义为空，也就是「查到了零条」——它必须和失败区分开，否则模型会把空结果理解成服务不可用，进而反复重试或者擅自改条件。

错误文案最重要的品质是「下一步可行动」：该换参数、该先调用哪个工具、还是本来就不该重试。堆栈、内部类名、下游原始错误全文都不该抛给模型：既占上下文又可能泄露拓扑。写操作成功时，返回体要带上被创建或被修改的资源标识，供后续步骤引用。

流式、进度与取消

不是所有工具都值得流式。值得的只有两类：耗时超过一次交互预期的长任务，和结果必须分段交付的查询。判据是模型拿到一半结果能否决定下一步：能就值得流，不能就只是把复杂度从调用侧搬到实现侧。

进度通知的口径是「阶段名加完成量」，不要给假的百分比：排队的任务与卡住的任务在假百分比下长得一样，模型会据此做出错误的等待决策。同样容易踩的坑是把大结果一次性塞进返回体——要么分页，要么写清截断策略和取剩余数据的方式。

取消是最容易只做一半的部分。收到取消信号，实现至少要完成四件事：停止向下游继续发请求、释放占用中的并发额度与连接、把已发生的副作用写进审计、向调用方确认已停止。要小心一个误解：取消不等于回滚，写出去的数据不会消失，所以取消后的返回必须说清「做到哪一步」，让模型或人类决定是否补偿。

  C->>S: 取消（用户中止 / 超时）
  S->>D: 停止后续请求
  S-->>C: 已完成的副作用清单 + 未执行部分

超时与重试放在这一节讲，是因为它们和取消共用一套预算模型。我的习惯是把总预算拆成三层，内层超时严格小于外层（这些数字是团队约定示例，不是任何标准值）：客户端到 server 给 20 秒，server 到单个下游给 6 秒，下游单次内部调用给 2 秒。反过来就会出现「调用方以为失败、实际已经写成功」的窗口，这是非幂等写操作最危险的失效模式。

重试只有同时满足两个条件才允许：操作幂等，且失败原因属于可恢复类（超时、限流、临时不可用）。退避要带抖动，要有次数上限和总时间预算，预算用完就放弃而不是继续按次数磨。还有一点要写进设计文档：重试只能存在于一个层，客户端、server 内部、网关各重试一次，三层相乘就是雪崩式放大。

鉴权、租户隔离与凭据边界

这一节是防御口径，原则四条：认证与授权分离；server 不持有用户长期凭据，确实要持有时放密钥管理系统，绝不落明文配置、不进日志、不作缓存键；权限作用域按工具粒度签发，读工具与写工具不同域；授权状态变化要有失效路径。

第四条最常被漏：令牌到期、用户被撤权、租户被停用之后，已经建立会话的调用什么时候停下来？要么每次执行前做一次作用域校验，要么把令牌有效期压到短于任务时长并在续期时重查，否则就等于把一次授权当成永久授权。

租户隔离的关键决策只有一句话：上下文在会话建立时绑定，绝不从工具入参接收。一旦 schema 里出现让模型填写租户标识的参数，那么模型填错或者被诱导填写，就变成跨租户读取。正确做法是让上下文来自服务端已经验证过的会话，工具描述里也不必解释这个参数，因为它不存在。

同样要限制的是「模型可以指定任意目标」这类自由度。允许它传入 URL 或路径的接口，等于把服务端变成内网探测器：必须做出网白名单、协议限制、重定向逐跳校验，以及对返回内容和大小的限制。任何由模型提供的标识都按不可信输入处理。实操上再加一句：写操作、跨域访问、批量导出这三类默认需要人工确认而不是静默放行，并把确认点留在宿主侧，这比在 server 里自建审批可靠得多。

日志与脱敏

日志为排障而写，却会顺手变成一份敏感数据副本，所以采集口径要先于字段设计定下来：最小必要。默认不记完整提示内容、不记参数原值、不记结果正文，只记能定位问题的派生信息——工具名、耗时、结果码、错误类别、输入输出字节长度与结构哈希前缀。哈希足以判断「同一参数被反复提交」，又不必保存参数本身。

这段是本文自拟样例。注意里面刻意没有的东西：没有联系方式，没有证件样式的编号，没有精确定位，没有从剪贴板或本地文件读来的原文。自由文本一律走掩码，而不是「看起来不像敏感就不处理」：规则按形态匹配，覆盖邮箱样式串、长数字序列、疑似令牌的随机串，命中就替换成类型标记加截断哈希，保留可关联性但不可复原。

关联标识也不能省成用户身份：trace 与 session 用派生的、不可逆的标识串起来，日志里不出现账号、设备或工号这类能直接回溯到个人的键。最后补两条治理项：日志要有显式保留期、到期清理、访问单独授权，一处没人管的日志很快会变成新的泄露面；掩码规则本身要有测试，用一批构造样例验证命中。调试日志的详细程度不能成为审计日志的默认。

版本协商、废弃与分发信任

协商发生在握手阶段，要点三条：能同时服务多个客户端版本，别把版本判断硬编码成等号；对认识不了的可选字段采取「忽略而不是报错」的健壮性原则；能力声明要与实际行为一致，声明了却执行不了比不声明更糟。

废弃节奏最该写进设计文档。以 2026-07-28 的修订为参考，被废弃的协议项会保留一段约 12 个月的移除窗口——这是公开的迁移窗口表述，具体计划仍可能随官方调整，所以实现里任何地方都不该假设它可以更短。据此给自己这一侧定规则：把每个工具的名称和参数形状当作对外契约，改名或删参数要走「新旧双写、公告、观察调用量归零、再下线」四步，绝不可在同一版本里静默改变某个工具返回结构的含义。静默改语义时客户端校验可能仍然通过，故障会以无关的形态出现在别处，是最难排的一类。

分发这一侧，注册与索引服务仍处于预览、演进中的状态，本文不下可用性结论，也不引用采用度数字；只有一条能确定：别绑死在「一定能在索引里搜到」上，私有分发是同等重要的路径。

安装信任是 server 特有的问题，因为它以第三方代码的形态运行在用户机器上，还带着凭据和文件访问。我的口径是：首次运行就列出申请什么权限、连什么网络、写什么位置，默认最小权限，用一项开一项；依赖冻结到可校验的锁定文件与摘要，发布产物与源码之间有可核对的关系，镜像优先于随机源；启动时自检，把缺失的能力直接报出来，而不是等到调用那一刻再失败。私有部署再加一条：版本要能锁死回滚，一次自动升级可能同时改变工具集合和模型的选择结果。

小结

难点不在协议接口本身，而在把「模型是不可预测且可被诱导的调用方」贯彻到每一层：粒度按选择准确率和失败面划分，schema 同时服务生成与校验，错误分三层且必须可行动，流式与取消共享一套超时预算，鉴权不接收模型填写的身份上下文，日志按最小必要采集并掩码，废弃走双写与归零。下面这份清单可在提审前逐条打勾。

  • 每个工具的名字、副作用、返回标识在描述里一眼可读
  • 写操作按窄工具拆分，读操作合并有依据
  • 未实现或不适用的能力显式拒绝，不静默返回空
  • 必填参数只留真正不可缺的，枚举列全
  • 服务端二次校验全部入参，不信任客户端
  • 校验错误、执行失败、成功但空结果三类可区分
  • 错误文案给出下一步，不含堆栈与内部拓扑
  • 长任务有阶段进度无假百分比，大结果有分页或截断策略
  • 取消会停止下游、释放额度、写明已发生的副作用
  • 三层超时内小于外，重试只在一层且要求幂等
  • 凭据不落明文配置、不进日志、不作缓存键
  • 租户上下文来自已验证会话，不从入参接收
  • 模型可指定的目标地址有出网白名单与逐跳校验
  • 日志只记派生信息，掩码有测试，有保留期与独立授权
  • 可选字段不认识时忽略而非报错，可服务多版本
  • 改名或删参数走双写、公告、调用量归零再下线
  • 依赖冻结、产物可核对、首次运行列权限
  • 跨租户读取与撤权失效用例进入自动化测试
