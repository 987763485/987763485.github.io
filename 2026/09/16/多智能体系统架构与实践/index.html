多智能体系统架构与实践

本文属于《Agent 智能体开发》第 40/55 篇
上一篇系列目录下一篇

多个智能体凑在一起做演示，看着总是热闹；真正把它们打倒的，往往是消息风暴、状态漂移、预算失控，还有出事之后无法复现。这篇文章不讨论“要不要协作”，也不重新推导分工与收敛的机理——那些在《多 Agent 分工与协商》里已经讲透——它只做一件事：把多智能体的架构决策落到部署、观测、告警与回放的运维面上，让拓扑成为可以被值守的对象。

从模式到工程

智能体的分层架构——接入、编排、执行、记忆、评测、治理各层怎么切——在《Agent 架构设计总览》里有完整的框架；协作模式怎么分类，则交给《多智能体协作模式》的谱系。本文的轴只有一条：把已经定下来的协作决策，落到部署、观测、告警与回放这四个运维面上，让拓扑不只出现在设计图上，也出现在值班手册里。

工程视角有三个前提。第一，每个能力承诺都要有可验证的接口：一个智能体声称自己能做什么，运维上就是入参校验与出参抽检，写在契约里，不写在提示词里。第二，每个故障都要有可归属的位置：一次链路挂了，要能在几分钟内回答“卡在哪一跳、违反了谁的哪条契约”，这要求拓扑与进程之间有明确的映射。第三，每条成本都要可对账：预算沿拓扑下发，消耗沿拓扑回账，任何一笔说不清归属的花费，都会在下次扩容时变成争议。

口径先约定：本文把一个持有模型调用与工具操作权限的执行单元称为 worker，把掌握任务拆分、汇总与预算的进程称为编排器（orchestrator）。worker 可以是模型驱动的智能体，也可以是固定流程的脚本——运维对二者一视同仁，因为它们都以输入输出契约存在。这个看似平淡的定义，是多智能体运维的起点：能被契约描述的，才能被告警覆盖。

拓扑选型：三种形状与一张图

中心编排。一个编排器持有全部的任务拆分、派发与汇总。它的运维优势是结构性的：预算有唯一落点，副作用有唯一出口，归因链路最短，回放只需要盯住一个进程。它的代价同样结构性：编排器既是单点又是吞吐瓶颈，还天然面临上下文漏斗——每个 worker 把过程全文原样回传的话，最先撑爆的是编排器的上下文窗口。缓解手段只有一个：worker 只回摘要与产物引用，全文一律落共享存储。

对等。智能体之间直接协商，没有常驻中心。好处是局部灵活、不存在全局单点；难处是全局终止条件没人能回答，通信量随参与方数量增长，出了问题要靠因果链路重建现场，复盘成本明显高于中心编排。因此对等结构只应该出现在有明确边界与共同所有者的子问题上，而且这个“区”必须有人负责——运维上，无主的对等区就是事故预定发生地。

层级。树状委托，每一层有自己的子编排器。它在两者之间取得平衡，但引入两个长期问题：信息逐层衰减，根节点写下的意图传到叶子时已经变形；责任链拉长，出问题时叶子声称“在等上游的指令”，归因要走完整棵树。层级深度本身应当是一个被度量的指标——深度每加一层，回放与归因的难度都上一个台阶。

现实里更常见的是混合形态：中心编排做主干，对等只在受管的区内发生。选型判断可以用一张图走一遍：

要强调的是中间那条分支：当子任务还说不清输入输出契约时，选哪种拓扑都是错的——拓扑问题大多是拆分问题没做完。另外，拓扑是部署决策而不是汇报用的组织架构图：哪个编排器对应哪个进程、哪些 worker 共用一条队列、哪些状态落在哪个存储上，这张映射表要写进运维手册，后面几节都围绕它展开。

共享状态与一致性

哪些字段必须唯一、哪些尽可复制，不在这里重新推导；这里只讲落到存储与进程上的做法。第一步是把数据分三类，各给不同的预算。任务事实（工单、状态、归属关系）要强一致，且有唯一写入者；中间产物（代码差异、报告正文、数据集）尽量做成不可变——一次写入、多次读取；派生缓存（摘要、检索索引）允许过期，允许重算。三类混在一个存储里、用同一套一致性策略，是很多多智能体系统慢与乱的共同根源。

状态存储要独立成进程，而不是常驻在编排器的内存里：所有工作状态外置，编排器进程随时可以被替换。这是后文“故障与降级”里恢复手段的前提——进程是壳，状态才是本体。每条状态记录带版本号，写入用比较交换的语义：版本对不上就失败并报冲突，绝不静默覆盖。产物走内容地址化，以内容哈希命名，发布后不可变，移动的只是引用。一条最小的状态记录大概长这样：

第二类不一致来自陈旧：重试、缓存与并发派发，会让某个 worker 读到一份已经被推翻的计划并照着干活。缓解靠两个动作——每次读状态都带版本，版本要出现在下游产物契约里；计划带租约，租约到期自动失效重读。租约时长是团队约定示例，量级上宁短勿长，短租约配续约，比长租约配抢占容易运维得多。

还要正视一类无法用数据库解决的问题：副作用不可回滚。发出邮件、写入订单、占用外部配额，在外部世界里没有“撤销”可言。多智能体系统靠意图日志管副作用——先记录“我打算做什么、幂等键是什么”，再执行，由对账任务回填执行结果。回放时看到“有意图无结果”的跳，用同一幂等键重放；看到“有结果无意图”的跳，交人工核查。工具权限最小化也属于一致性的一部分：每个 worker 的可写面越窄，冲突率越低，脏写的影响半径越小，审计留痕的粒度也越有用。

通信与消息治理

消息先分三类，运维语义完全不同。命令：派任务，点对点，要求回执；询问：要状态或要判断，同步语义、必须有超时；通告：报告已经发生的事，一对多，重点在订阅管理而不是送达确认。很多系统的运维成本源于类别用错——把通告当命令发，发送方要为每个接收方伪造回执；把命令当通告发，任务丢了都没人知道。

交接的第一原则是传指针不传全文：消息体带摘要与产物标识，过程原文存在可寻址的地方。否则原始转录会沿链路逐跳传播，消息体积与各方上下文一起膨胀，这是多智能体消息风暴最常见的物理来源。信封结构不必发明新格式，够用即可：

有序性不追求全局，只追求因果：每条消息携带父消息标识与链路标识，消费方按因果链重排即可，队列乱序不致命，因果链断裂才致命。可靠性走幂等路线：所有派发带投递标识，消费方去重；发送方重试使用指数退避加上限并带抖动，触顶就放弃并上报失败，而不是无限重试掩盖依赖故障。背压要显式设水位：队列深度有上限，触顶时拒绝新派发并报警，绝不静默丢弃——静默丢弃会把一次可诊断的故障变成一处不可复现的悬案。

协议层的位置说清楚：跨进程的互联与任务交接，截至本文时点可以参考 A2A（v1.0.0 发布于 2026 年 3 月、v1.0.1 发布于 2026 年 5 月，规范仍在快速演进，字段与端点以官方当期文本为准）；智能体与工具之间继续走 MCP 的既有形态，其 2026-07-28 修订刚生效不久，对多智能体系统主要意味着客户端鉴权与能力发现要按新口径重新核对，还谈不上长期稳定契约。本文不绑定任何具体签名与字段拼写，只记录一个定位：协议解决“怎么说”，不解决“谁有权说、说完谁负责”，后者永远是拓扑与治理的事。

成本与预算护栏

预算沿拓扑形成一棵树：全局总预算分到各条链路，链路分到各区，区分到每个 worker，worker 分到每一步。下发是决策，回账是义务——每一跳消耗都要能沿树回汇总，否则预算只是装饰。账目分三本记：模型 token、工具调用、人工时间。单价按当期官方价目核对，本文不写任何固定价格；智能体之间怎么计价、怎么结算，那是《多智能体经济与协作协议》的主题，本文只关心护栏本身怎么装、装在哪。

护栏的第一要义是熔断在触顶之前：当单个任务的累计消耗达到团队约定阈值——比如计划额度的七成——编排器立即停止新派发，做出处置决策：降级、砍范围或转人工，并把这次触发记入事件账。等到余额归零才反应，几乎必然已经超支，因为多智能体的消耗有惯性：已经派出去的命令会继续花钱，正在重试的调用会继续花钱。熔断之后还要有恢复语义——是允许降级继续，还是必须人工确认才能重启，事先写死在策略里，别让值班的人临场发明。

降级方案要在护栏之前定好，而不是触发之后再找。常见的降级序列：换更经济的模型档位继续、砍掉非核心子任务、把并行改回串行、最后才是整单转人工。每一档降级的准入条件与产物质量影响都要预先声明，因为降级不是免费的——省下来的预算要用质量损失来付。模型档位的选择随官方当期发布的型号与价目核对即可；近期新发布的系列，比如 Qwen3.8，本文只提名称，不做参数与能力的断言。

归因口径有个必须事先定的问题：重试花的钱记在谁头上？多智能体系统里，一次上游超时可能引发整条链路重跑，账单会同时出现在多个 worker 名下。可行的做法是账目携带因果链标识，把消耗归到“引发这次花费的决策”上，而不是执行者上——否则观测里全是噪声，扩容讨论全是扯皮。跨 agent 的追踪与成本归因口径，《多 Agent 系统可观测性》已专门展开，本文不复述，只强调运维面上的一件事：预算树与账本必须同构，树上有几个节点，账上就要能对出几个节点，对不上的那部分就是治理空洞。

终止与抢占

收敛判据不再重复推导；终止要处理的是执行层面的问题：怎么把一个“该停了”的判断，变成全系统真的停下来。多智能体的终止是四步序列，不是一条广播。第一步，编排器把终止决策连同原因写入状态存储——先落账，后动手；第二步，向所有活跃 worker 发终止命令，命令走正常信封、带因果链；第三步，各 worker 在自己的安全点停下并回执；第四步，编排器汇总回执，未回执者转入强制处置。

安全点必须由每个 worker 自己声明，这是终止语义里最容易被跳过的设计：一个正在写外部系统的事务中间的 worker 被打断，留下的是比不终止更糟的半成品状态。安全点的常见形态是“一次副作用工具调用完成之后、下一次派发之前”。如果 worker 迟迟到不了安全点——比如它卡在一个长工具调用里——编排器要区分“仍在收尾”与“已经失联”，前者等，后者按故障处理，等待要有团队约定的时限。

抢占是带优先级的终止：全局预算被高优先级任务主张，低优先级链路让路。运维上抢占比终止难，因为它要求可恢复——被抢占的 worker 需要能把上下文快照到状态存储，等预算重新下发后从快照继续，而不是从头再来。快照的频率与体积是一对矛盾，频繁快照挤占正常预算，稀疏快照丢失进度；两者都要按链路重要性分级，并用回放来验证恢复语义真的成立。这里有个反直觉的点：抢占必须可回滚到决策点，而不是可回滚到任意步——回滚到任意步意味着承认中间副作用可以撤销，而前文已经说过，它们不能。

最后一类是失控，终止与抢占都要防它：同一对 worker 之间反复交接、消息在环里打转、预算持续消耗但没有产物落账。检测信号不是步数上限——步数会误伤长任务——而是“消耗与产物脱钩”：连续若干个团队约定窗口内有花费、无新增已登记产物，即标记可疑并触发人工检视。自动杀掉可疑链路要慎重，误杀的代价往往高于多等一会儿。

故障与降级

先分类，再给药方。故障按位置分五类：模型侧——超时、内容过滤拦截、速率限制；工具侧——依赖不可用、返回形态变更；同伴侧——有心跳但没有工作推进，也就是活性丢失；状态侧——写冲突率抬升、出现版本回退读；基础设施侧——队列、存储、时钟漂移。五类的告警形态完全不同：前两类看响应曲线与错误率，中间两类看因果链完整度与版本分布，最后一类根本不该由应用报——但多智能体系统常常把它伪装成模型故障，值班手册里要写明鉴别方法。

重试语义按副作用性质分三档：只读操作可以盲目重试；写操作必须带幂等键才能重试；不可逆动作——花钱、发布、对外发送——只允许走确认门槛，禁止一切自动重试。还有一个容易忽略的组合陷阱：编排器重试派发、worker 重试工具调用，两层各自退避，乘起来就是一场对同一依赖的请求风暴。规则是每一层只重试自己发起的那部分，并把“我已经在上游重试过”写进消息上下文，下游见到就换策略而不是叠重试。

影响半径由拓扑决定，运维要按拓扑设计恢复。中心编排下编排器故障等于全局停摆，所以编排器必须做成无本地状态的壳：工作状态全部在外部存储与队列里，备用实例凭状态接管，继续派发。这里不复述单机部署与会话恢复的通用手段——《Agent 部署与运维》已覆盖队列看门狗与灰度回滚——多智能体特有的一层是“接管后的预算一致性”：新编排器上岗第一件事是向账本重放未决意图，把预算水位校准之后再派发，否则要么超额烧钱、要么错误熔断。对等拓扑没有这个清晰单点，它的特色故障是分区：两侧各自产出一版计划，都认为自己有效。治理手段是租约围栏——仲裁权由独立存储上的租约持有，租约过期的参与方自动失去主张有效的资格；没有围栏的对等系统，等于把脑裂写进了日程表。层级拓扑的故障向上表现为“等待上游”，所以每一层子编排器都要有自己的超时，且从根到叶的总超时要在变更层级深度时重新核对，否则一个层内合理的等待，叠四层之后就是一场静默的长尾。

降级按梯子走：重试 → 换工具实现 → 换模型档位 → 砍范围 → 转人工。每个 worker 在契约里声明自己的降级路径与各档准入条件；禁止静默降级——降级本身必须作为事件入账并进指标，否则评估数据会被悄悄污染，回放也会和现场对不上。

最后是安全面：智能体之间传递的内容，对接收方而言一律是外部输入，提示注入会沿链路传播——被污染的 worker 输出的“合理计划”，下游只会更信任它，因为来源是“自己人”。原则只有一条：权限随跳数收敛，高权限动作不接受未经校验的上游产出，链路末端对副作用一律再过一次独立确认。注入与内容边界的细节有专文，本文不展开；但运维面上它落在告警里：同一时间窗内多个 worker 行为同步异常，优先怀疑共同上游被污染，而不是各自故障。

评测与回放

多智能体的不确定性有三个来源：模型采样、并发时序、外部副作用。回放不是消灭不确定性，而是选择冻住哪一层。按成本从低到高分三层。L1 编排回放：模型与工具全部换成固定应答表，只验证路由、预算、终止与状态机——跑得最快、结果最稳，应当进每次合并的必跑门禁，拓扑改动、护栏阈值调整、超时参数变更，都由它兜底。L2 录制回放：在生产消息边界把每个请求标识对应的响应存进档案，回放时模型侧从盘读，工具侧要么从盘读、要么打桩——它验证的是行为逻辑，agent 换了提示词模板之后的回归主要靠它。L3 实跑评测：全真环境、真模型、真工具，只用于评估不承诺复现，波动要靠重复采样与区间口径来压，单次跑分说明不了任何事。

录制内容要有清单：每跳消息的信封与摘要、模型响应（留存须先过脱敏授权）、工具调用参数与返回、状态变更的版本序列、账本增量。默认不进档案的清单同样重要：用户提问原文、手机号、身份证件号、精确地理位置、剪贴板内容——回放需要的是结构与因果，不是明文；确需全文的敏感场景，脱敏之后分级留存，留存期限做成团队约定并写进数据清单。

评测集的设计与指标口径——任务集怎么组、并发档位怎么设、完成质量怎么判——评测类专文已经给了方法；本文只补多智能体特有的三个观察位：该停的时候停了没有（终止正确率）、冲突发生的时候冲突出来没有（一致性可见性）、预算触发的时候降级接住了没有（护栏有效性）。公开基准如 AgentBench、SWE-bench Verified、GAIA、tau-bench、Terminal-Bench 都已存在多年，可以校准单点能力，但“协作质量”没有现成榜单可考；而且业界普遍担心公开基准的污染与刷分问题，外部跑分只作偶发校准，内部回放集与生产录制样本才是日常手段。一个实用的组织法：把每次生产故障转写成一条回放用例，用例库的覆盖度比任何单一分数都更能说明你的系统能被运维到什么程度。

运维面：部署、观测与告警

部署。编排器与 worker 分开部署单元、独立升级：把它们塞进同一个进程，等于同时放弃中心编排的归因收益与独立回滚能力。首发用最小可用拓扑——一个编排器、两个 worker、独立状态存储——先跑通预算下发、消息信封与终止四步，再根据观测决定横向扩展哪一环。凭据一律走密钥管理服务，禁止把凭据或内网令牌写进明文配置与日志；不同权限档的 worker 不共享沙箱，工具面越接近不可信内容，隔离越要往严里配。版本演进走消息契约的加性规则：新字段先让所有消费方上线，再让生产方开始发送，新旧共存要有明确的兼容窗口，这是多智能体灰度发布与单机灰度最不一样的地方——你灰度的不是代码，是拓扑里的对话协议。

观测。指标、日志、追踪三线并行，但字段口径要提前统一。跨智能体的追踪建议以 OpenTelemetry 的 gen_ai.* 语义约定作公共语言；截至本文时点该约定仍在演进、标注为开发状态，属性名以官方注册表为准，升级可能带来变动，所以业务侧再补自有维度——键名做成团队约定并登记在术语表里，例如：

采集口径守最小必要：默认不采用户提问原文、手机号、身份证件号、精确定位与剪贴板；消息内容在指标与日志里只留长度与哈希，全文入档要过脱敏与显式授权，留存期限分级。多智能体特有的一条红线：追踪里会顺带携带上游智能体的推理摘要，它可能已经含有敏感原文——采样点要设在信封边界，设在“摘要写入”之前，让脱敏组件有机会先过一遍。

告警分四族：预算族——消耗速率与剩余额度双阈值，触顶前报警而不是触顶后复盘；活性族——worker 心跳丢失、队列积压越水位、因果链在链路级时限内没有新消息（这个“单跳都没超时、整条链不动”的卡法是多个智能体特有的，单机看门狗看不见它）；一致族——写冲突率、版本回退读、意图与结果错配；终止族——熔断触发、僵尾任务计数。分级原则：单个 worker 故障不叫人名，它是降级的分内事；链路级卡死与预算越界才叫人。同一时间窗内多条告警并发时合并成事件再路由，避免同一个人被同一场故障叫醒五次。值班手册按拓扑逐条回答三个问题：这种故障形态按哪个降级开关、撤销谁的租约、用哪条回放用例复现——三问都答得上来，这份手册才算合格。

表里的“治理成本”是定性判断，没有量化口径——不同团队对同一种故障的容忍度差好几个数量级，硬给数字反而误导。这张表真正的用法是反向自检：对照你当前的拓扑，每一行的“典型故障形态”能否说出它的告警长什么形状、降级按哪个开关、回放用哪条用例；只要有一格答不出来，说明运维设计还没做完，而不是故障还没来。多智能体系统很少死于能力不足，多半死于没有人能对它的故障负责。

小结

这篇文章把多智能体的工程落点收束成一句话：让每一个协作决策都有对应的部署单元、观测字段、告警规则与回放用例。展开来是八件具体的事——拓扑按契约完备度选而不是按组织图选；状态外置、进程成壳，编排器才可替换；消息传指针不传全文，因果链代替全局序；预算沿拓扑成树、熔断在触顶之前；终止是四步序列，抢占要可恢复；回放分三层，先冻住编排再冻住行为；告警按故障侧分四族，单智能体故障不配叫醒人；观测与录制一律最小必要并脱敏。协议与计价交给协作协议的专文，追踪与归因交给可观测性的专文，本文守的是中间这段：拓扑落地之后的可运维性。判断一个系统是否毕业，不需要看它的智能体数量，只需要看最后一个问题：把它最坏的一次故障当面重演一遍，值守的人是否每一步都有据可依。答不出这个问题之前，不要急着加第四个 worker——先把第三个变得可观测、可告警、可回放，这就是多智能体工程与演示之间的分水岭。
