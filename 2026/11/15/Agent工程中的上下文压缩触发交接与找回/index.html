Agent 工程中的上下文压缩：触发、交接与找回

用 Agent 跑长任务，迟早会看到屏幕上跳出一行 Compacting conversation。等它转完，Agent 继续干活，但好像忘了点什么：刚才说好的「别动这个文件」，过一会它又去改了。这类故障通常不是模型变笨，而是压缩把关键约束弄丢了。本文把上下文压缩拆成一次有损的工作交接，讲清什么时候压、留什么、交接文档怎么写、原件放哪，以及如何验证压缩之后任务还能接得上。

压缩不是总结，是一次有损交接

大模型本身是无状态的。每一轮请求，客户端都会把系统提示词、工具定义、历史消息、工具结果重新发一遍；用户感受到的「记忆」，来自这份不断增长的历史。上下文窗口装不下时，系统必须做一次替换：把旧历史压成摘要，保留最近一段原文，然后让模型带着这份摘要继续工作。

这件事看起来像「把聊天记录总结一下」，实际更像一次工作交接。上一个「自己」在上下文快满时，写一份交接文档给下一个「自己」，然后把桌面清空。交接文档写得再认真，也一定有损失：用户当时的语气、被否决的方案、工具返回里的精确路径、某条约束的适用范围，都可能在摘要里变成一句模糊的话。

损失可以分成三类。第一类是约束损失：用户说过「不要改这个文件」「保持接口兼容」「先不要提交」，这些是任务的不变量，一旦丢了，后面的动作就可能越界。第二类是锚点损失：文件路径、函数名、commit SHA、错误码、PR 编号，这些需要逐字准确，模型转述时很容易记错一位。第三类是状态损失：哪些测试跑过、哪些失败、哪一步被阻塞、下一步准备做什么，这些决定任务能否接着往下走。

举个具体的例子。用户在一个重构任务里说过三句话：「不要改 public 接口」「保留旧参数名，内部可以换实现」「提交前跑一次集成测试」。压缩后，摘要只留下「重构登录模块，保持兼容」，前两句约束消失，第三句变成「跑测试」。Agent 接着改了下游调用方，又把旧参数名一起改掉，测试也只跑了单元测试。每一步看起来都在推进任务，合起来却违反了用户最初的边界。

所以压缩的核心问题不是「怎么总结得更短」，而是「哪些东西必须无损地活下来」。把这个问题想清楚，压缩策略才有依据。

为什么 Agent 非压不可

第一笔账是成本。Transformer 的注意力计算随上下文长度增长，token 越多，费用越高、响应越慢。Agent 场景比普通聊天更费上下文：读一个文件几千 token，跑一次测试输出几千 token，搜一次代码又是一大段。工具结果才是大头，几十次调用就能把窗口塞满。

可以把一次 Agent 请求的上下文拆成五块：系统提示与工具定义、项目规则与记忆、技能说明、对话历史、工具结果。前两块相对稳定，适合放在前缀里吃缓存；后两块增长最快，是压缩的主要对象。很多团队一上来就压对话，其实工具结果往往占得更多：一次全量测试日志、一次大文件读取、一次依赖树输出，都可能比几十轮对话还大。先清工具结果，往往比先摘要对话更划算。

第二笔账是效果。长上下文并不等于好上下文。研究早就发现，模型对长上下文中间部分的信息不敏感，常被称为 lost in the middle；工程实践里也常提到 context rot：内容越多，真正重要的约束越容易被淹没。上下文快满时，模型不是「看得更多」，而是「更容易看漏」。

第三笔账是缓存。每轮请求都重复发送历史，服务端可以用 prompt cache 复用前缀计算。但缓存对前缀很敏感：前缀里改一个字，后面的缓存全部失效。压缩恰恰是在改历史，所以每次压缩都要付一次缓存重建的代价。这也解释了一个设计现象：很多系统会把压缩安排在缓存本来就要过期的时候，或者尽量只改尾部、不动前缀。

三笔账合起来，压缩的目标就清楚了：在不丢关键信息的前提下，把上下文降到一个可承受的规模，同时尽量少破坏缓存。压缩不是越早越好，也不是越狠越好；它是一次有成本的交接，时机和内容都要算账。

四个必须回答的问题

第一个问题是何时压。常见做法是设两道阈值：软阈值用于提醒或做轻量清理，硬阈值用于触发正式压缩。触发点最好落在子任务边界，而不是工具调用中途；如果模型提供方直接报上下文溢出，可以压缩一次再重试，但要设上限，避免无限循环。阈值不是越低越好：压得太早，摘要次数多，缓存反复失效，信息也更容易在多次转述中损耗；压得太晚，可能已经触发提供方的硬上限，请求直接失败。比较稳妥的做法是留出「压缩所需 token」的余量，压缩本身也要调用模型，摘要输出也要占空间，不能等窗口 100% 满了才开始。

第二个问题是留什么、丢什么。用户原话通常优先级最高，因为它承载目标和约束；系统提示词、项目规则、当前任务状态必须保留；最近几轮原文要保留，保证对话连贯；旧工具结果可以清理，但要保留路径、命令、退出码和关键错误；思考过程可以丢弃，工具调用与结果的配对不能拆开。保留策略要按「不可再生」排序：用户原话、约束、验收标准、关键锚点不可再生，必须逐字保留；任务进展、决策理由可以结构化重写；工具结果大部分可再生，保留定位信息即可；思考过程通常可以直接丢弃。一个简单的判断是：这条信息丢了之后，能不能通过重新读文件、重新跑命令、重新问用户拿回来？能拿回来的，优先压；拿不回来的，优先保。

第三个问题是交接文档谁来写。可以由主模型在压缩时生成，可以由后台的记忆 Agent 持续维护，可以由服务端返回加密摘要，也可以用确定性模板加正则抽取。不同方案的成本、可读性、可编辑性不同，后面会对比。

第四个问题是原件放哪。压缩后的历史是工作副本，原始记录应该追加到日志或归档存储，支持按会话、任务、消息 ID 找回。没有原件，一旦摘要出错就无法复盘；有了原件，摘要只是索引，不是唯一真相。

还有一个隐含问题：怎么验证。压缩不是写完摘要就结束，必须用任务恢复测试和约束保留测试来验收。否则系统只能证明「压缩成功了」，不能证明「任务还能继续」。

四种实现：Codex、Claude Code、Hermes 与 pi

Codex CLI 是开源的，压缩逻辑在 codex-rs/core/src/compact.rs 等文件里。它区分本地压缩和远程压缩：本地路径在当前历史后追加一条压缩指令，让模型生成一份交接摘要；远程路径在使用自家模型时交给服务端完成，客户端拿到的可能是一段加密内容。本地摘要的提示词明确要求写清当前进展、关键决策、重要上下文、约束与偏好、下一步计划，以及继续工作需要的关键数据。它把压缩定义成「另一个模型做到了这里，你接着干」，而不是「你之前做了什么」。本地路径还会保留一部分用户原话，从新到旧填满预算，而不是把所有历史都交给摘要。这背后的判断是：用户说的话比模型自己的推理过程更重要。远程压缩把摘要变成服务端的不透明数据，好处是客户端无需理解格式，坏处是可读性和可迁移性下降；一旦更换模型或供应商，历史可能无法复用。

Claude Code 的官方文档把上下文窗口讲得比较具体。接近上限时会自动压缩，先清理旧的工具输出，空间还不够再对对话做摘要。压缩后，系统提示词和输出风格不变，项目根目录的 CLAUDE.md 与不带路径范围的规则会从磁盘重新注入；带 paths: 的路径规则、子目录里的嵌套 CLAUDE.md，要等对应文件被重新读取才会回来；调用过的 Skill 内容会重新注入，但有总量上限；最近读写的文件最多重新读取五个。官方也明确提醒：对话早期的细节指令可能丢失，长期规则应该写进 CLAUDE.md，而不是指望历史。用户可以手动 /compact 并指定重点，也可以用 /rewind 做局部摘要，或用 /clear 切换任务。官方文档还提到两个实用开关：/compact 可以指定本次摘要的重点，例如「重点保留接口改动和还没跑通的测试」；PreCompact 和 PostCompact 钩子则允许团队在压缩前后插入自己的逻辑，比如把关键约束重新注入，或把压缩记录写到外部审计系统。

社区对 Claude Code 的拆解还提到一套逐层升级的压缩链：先把超大工具结果落盘，只留预览和路径；再借助服务端缓存删除旧工具结果；缓存本来过期时清理旧结果；后台维护结构化笔记；最后才 fork 一个 Agent 写完整摘要。这套分层思路值得借鉴，但具体阈值和实现会随版本变化，不应当成稳定契约。

Hermes Agent 的官方文档把压缩和缓存写得很细。它支持就地压缩和轮转会话：就地压缩会在同一个会话 ID 下重写消息列表，把压缩前的轮次软归档；轮转模式则通过父会话 ID 保留历史。压缩结构是掐头、留尾、压中间：头部保留系统提示词和最开始的对话，尾部按 token 预算保留最近消息，中间先做不花钱的清理，再交给辅助模型生成结构化摘要。摘要通常覆盖目标、约束与偏好、进展、关键决策、相关文件、下一步和关键上下文；路径、commit SHA、错误信息这类锚点会用规则抽取，避免模型转述出错。原件不会删除，默认可以检索；后续压缩会把上一版摘要传进去，要求更新而不是重写。压缩器本身做成了可替换的 ContextEngine 接口，失败后还有逐级冷却，避免反复调用。就地压缩有一个容易忽略的代价：它重写了当前会话的消息列表，虽然原文被软归档，但会话前缀已经变了，prompt cache 需要重建。轮转模式则通过新会话继承父会话，把「改历史」变成「开新分支」，对缓存更友好，但会增加会话管理的复杂度。两种模式没有绝对优劣，取决于你更在意缓存成本还是会话连续性。

pi 是另一套极简实现。它的触发条件很直接：上下文 token 超过窗口减去预留 token 就压缩，预留默认 16K；检查时机在工具结果写回之后、模型下一次回答之前。保留策略是从最新消息往前累计到约 20K token，切点只能落在消息边界，不能把工具调用和结果拆开。它不会把消息数组直接丢给模型，而是先序列化成纯文本，避免模型把「要总结的材料」当成「要接着聊的对话」；超长工具结果会截断，思考内容会省略。摘要同样采用结构化字段，并额外记录读过和改过哪些文件。最有特点的是，它不重写历史，而是往会话日志里追加一条压缩记录，标明摘要和从哪条消息开始保留，原始消息全部还在；会话本身是树状结构，可以回到任意历史节点开新分支。这种追加式设计把「压缩」变成了「在日志里多一条记录」，原始消息一条不删。这样做的好处是审计和回滚非常直接：任何时候都能回到压缩前的节点，或者从旧分支开新会话。代价是存储会持续增长，检索和重放需要额外的索引；如果会话很长，加载时还要自己做裁剪。

一套可落地的分层压缩设计

把上面的做法抽象出来，可以得到一套不依赖具体厂商的设计。核心原则是：先做便宜的清理，再做昂贵的摘要；先保不变量，再压可丢弃内容；先归档原件，再替换工作副本。

第一步是定义策略。策略至少包含软硬阈值、预留 token、最近保留 token、摘要最大长度、受保护内容、压缩失败重试上限。软阈值可以设在窗口的 60% 到 70%，用于触发轻量清理；硬阈值设在 80% 到 85%，用于正式压缩；预留 token 要覆盖系统提示、工具定义和下一轮输出。触发点优先选在子任务完成、测试跑完、提交完成这类边界上，避免在工具调用中途切断。

第二步是分层清理。先丢弃思考过程、重复的工具输出、已经落盘的大文件内容；把旧工具结果替换成「命令、退出码、关键错误、产物路径」的摘要；保留工具调用与结果的配对，不能只删结果。然后再做结构化摘要。这样可以把最贵的一次模型调用留给真正需要压缩的内容。

第三步是写交接文档。摘要不要写成一篇文章，而是一份可检查的结构化记录。

这份结构里，constraints 和 anchors 是必须逐字保真的字段。前者是任务不变量，后者是后续操作的定位符。decisions 要记录被否决的方案和理由，否则下一个「自己」可能把已经排除的路线重新走一遍。progress 要区分完成、进行中和阻塞，避免把「跑过但失败」写成「已完成」。

第四步是验证与替换。压缩前先保存原始记录，压缩后跑三类检查：约束是否都在、锚点是否准确、任务状态是否自洽。替换历史时，优先保留系统提示和项目规则在前缀里的稳定性；如果服务端支持缓存编辑，可以把旧工具结果从缓存里删掉而不改本地消息；如果不支持，就把压缩安排在缓存本来会过期的时候，减少重建损失。缓存友好还有几个具体手段：把稳定的系统提示、工具定义、项目规则放在最前面，压缩时不要动；尽量只替换历史尾部，保留前缀；如果服务端支持缓存编辑或前缀复用，优先用它删除旧工具结果，而不是重写整段消息；把压缩安排在会话空闲、缓存本来会过期的时候，把重建成本摊到不可避免的时间点上。

第五步是找回。压缩记录要带会话 ID、压缩序号、摘要、切点、原始记录引用和时间戳。用户或运维可以按会话找回原始消息，也可以回到压缩前的节点重新分支。没有找回能力，压缩就是一次不可逆的删除；有了找回能力，压缩才是一次可回滚的交接。

校验最好自动化。把约束和锚点做成结构化字段后，可以用规则检查：摘要里是否包含每条约束的原文或等价表述，锚点是否逐字匹配原始记录，工具调用与结果的数量是否配对，进度字段是否与最近一次工具结果一致。规则检查通过后，再让模型做一次「交接自检」：如果你只能带三样东西到下一个会话，你会带什么？答案应该落在约束、任务状态和下一步上，而不是流水账。

失败模式与验收指标

压缩的失败模式很有规律。第一，约束丢失：摘要只写了「修登录问题」，没写「不要改认证中间件」，后续动作越界。第二，锚点损坏：commit SHA、文件路径、错误码被模型改写，导致命令跑错对象。第三，配对拆散：工具调用被保留，对应的结果被删掉，模型看到一次没有结果的调用。第四，摘要漂移：每次压缩都重写摘要，信息逐轮损耗，最后和最初的目标偏离。第五，缓存抖动：压缩过于频繁，前缀反复失效，成本不降反升。第六，无限压缩：压缩后仍然超限，系统不断重试，任务卡死。第七，原件丢失：只保留摘要，无法复盘和回滚。

对应的验收指标也要成组看。约束保留率：压缩后摘要中仍然包含全部关键约束的比例。任务恢复成功率：从压缩点继续执行，能完成原任务的比例。锚点准确率：路径、SHA、错误码逐字正确的比例。压缩比与成本：压缩前后 token 数、缓存命中率、每个被接受任务的总成本。稳定性：压缩失败率、重试次数、压缩后再次触发的间隔。人工介入率：压缩后需要人补充信息的比例。指标要结合任务长度看。短任务压缩次数少，约束保留率容易做到很高；长任务压缩多次，误差会累积。建议按压缩次数分层统计：第一次压缩后的恢复率、第三次之后的恢复率、以及连续压缩之间的信息损耗。只看一次压缩的结果，会低估长任务的真实风险。

测试方法可以很直接：构造一批长任务，在固定位置注入约束和锚点，执行到触发压缩，然后检查摘要和后续行为；再让 Agent 从压缩点继续，看它是否违反约束、是否找错文件、是否重复已经否决的方案。不要只看摘要「读起来是否合理」，要看任务是否还能跑对。

诊断清单

当 Agent 在压缩后表现异常，可以按下面的顺序排查。

  1. 查摘要里的 constraints 是否完整，特别是用户后来说的补充约束。
  2. 查用户原话是否保留，摘要是否把「不要做」写成了「可以做」。
  3. 查锚点是否逐字准确，路径、SHA、错误码有没有被改写。
  4. 查工具调用与结果是否配对，是否出现只有调用没有结果的消息。
  5. 查最近保留窗口是否太短，压缩点是否切在任务中途。
  6. 查原件是否可找回，能否回到压缩前的节点复现问题。
  7. 查压缩频率与缓存命中率，是否因为压缩过密导致成本上升。
  8. 查长期规则是否放在 CLAUDE.md、AGENTS.md 这类每次重新加载的位置，而不是只靠对话历史。
  9. 查压缩策略是否可替换。如果压缩逻辑写死在主流程里，出了问题只能改代码发版；做成可替换的接口，才能快速试验不同摘要模板和阈值。
  10. 查是否有压缩前后的对照样本。没有基线，就无法判断一次压缩是变好了还是变坏了。

这份清单的顺序，基本对应损失发生的概率：约束和锚点最先坏，工具配对和保留窗口次之，缓存和原件是系统级问题。先修前四项，再谈压缩算法。

小结

上下文压缩不是「把历史总结短一点」，而是一次有损的工作交接。它的设计目标不是摘要漂亮，而是让任务在压缩后还能继续：用户约束不能丢，关键锚点不能错，任务状态要自洽，原始记录要能找回。工程上可以先做便宜的清理，再做结构化摘要，最后才动用完整的模型压缩；触发点尽量落在子任务边界，压缩时机要考虑 prompt cache 的代价。Codex、Claude Code、Hermes 与 pi 给出了不同取舍，但共同点是一致的：用户原话优先、工具结果先清理、摘要结构化、原件可追溯。把长期规则放进每次都会重新加载的配置文件，是比任何摘要技巧都可靠的兜底。
