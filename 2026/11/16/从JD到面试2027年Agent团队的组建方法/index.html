从 JD 到面试：2027 年 Agent 团队的组建方法

2027 年招 Agent 工程师，代价最高的错误是用传统研发的标准筛人。很多 JD 把「熟悉大模型」追加在前后端技能清单后面，面试仍然考八股和算法题。招来的人会调工具，却设计不出一条能交付的工作流。本文从能力模型、JD 重写、面试设计、团队配置到 90 天落地，给出一套可执行的组建方法。

招聘误区：把 Agent 团队当传统研发团队招

第一个误区是把「单领域深度」当成首要标准。传统后端招聘会要求精通 JVM、熟悉 Go 内存模型、能手写并发。Agent 开发也需要工程底子，但日常工作是拆需求、接工具、管上下文、做评测。这些能力横跨前端、后端、数据、模型和产品。单点深度再高，缺了工作流设计，也很难独立交付。

第二个误区是把工具经验当成能力证明。简历上写「熟练使用 Claude Code、Codex」，不等于会设计研发工作流。工具更新很快，工作流设计、上下文工程、评测方法才能带走。面试只问工具怎么用，招来的是操作员。

第三个误区是唯算法背景。多数企业不做基础模型训练。Agent 落地需要模型素养、数据工程、评测和成本控制，不需要发论文。招一个只做预训练的研究者做业务 Agent，双方都痛苦。完全不理解模型边界的纯业务开发，也会在 RAG、微调和上下文策略上反复出错。

第四个误区是 JD 写「全都要」。TypeScript、Python、Go、Rust、Java、K8s、Figma、算法、管理、销售支持，全列成必备。合适的人不敢投，面试官也不知道该考什么。JD 应该用来筛选，不该用来收集愿望。每一项必备能力，都要对应一个面试环节和一条证据。

第五个误区是只招「能写代码的人」，不设计团队。Agent 交付需要互补角色：能定架构的人、能打通数据和检索的人、能做评测和可观测的人、能理解产品与交互的人。五个人的能力结构一样，同一个问题会重复出现。

这些误区叠加，招聘周期变长，薪资被抬高，团队却交付不出生产级 Agent。候选人能演示聊天机器人，说不清任务成功率、Token 成本和失败恢复。团队每天改 Prompt，没人建评测集。上线后一出问题，只能靠人盯。问题通常不在候选人太少，而在筛选标准不清楚。

能力优先级：广度、工作流与一项专长

Agent 团队的前几个人需要广度。这里的广度指能在一条完整链路上做判断。每样技术都浅尝一遍，不算广度。可以把能力分成五层。

第一层是工程基础。TypeScript 和 Python 至少有一门能作为主力，另一门能读能改。Go 与 Rust 至少能读能改，理解适用边界。前端要理解组件化、状态和交互，能配合 React 或 Vue 做 Agent 的调试界面。后端要理解接口、事务、并发和幂等。数据库、Redis、消息队列要懂使用场景和基本运维。Docker 与 Linux 要能独立排查环境问题。CSS 盒模型这类前端基础，考的是能不能和前端对齐，不是能不能手写框架。工程基础的判断标准很朴素：给他一个报错、一条慢查询、一个容器起不来的环境，看他能不能定位到根因，而不是只会重启。

第二层是模型工程。RAG 要懂切分、召回、重排和评测。LoRA 要懂数据构造、训练配置和效果评估。Memory 要懂写入、检索、遗忘和一致性。上下文压缩要懂摘要、裁剪和分层。上下文工程要能把 Prompt、工具描述、状态和失败恢复放在一个系统里设计。这些能力不需要每项都到专家级，但要知道什么时候该用、代价是什么、怎么验收。模型工程的重点在选型与验收，训练只占一小部分。同一个准确率目标，用 RAG、微调、Prompt 还是工具，成本和迭代速度不同。候选人要能说清楚为什么选这一条。

第三层是协议与工具。MCP 解决工具与数据接入，A2A 解决 Agent 之间的任务协作，Skill 把流程做成可复用能力。候选人不需要背协议字段，但要能说清楚什么场景该用 MCP，什么场景该用 A2A，Skill 和 Prompt 的边界在哪里，工具权限和审计怎么做。更好的判断标准是让他画一条调用链。用户请求进来，经过哪些 Agent、哪些工具、哪些权限检查，失败在哪一步降级。

第四层是产品与设计。能分析竞品、能把需求拆成 MVP、能画清楚交互流程，熟悉怎么使用 Figma 或 Pen 等工具处理原型。Agent 的输出经常是一个多步交互，不只是一段文本。不懂交互的人，做出来的 Agent 就是一个只会聊天的输入框。产品能力不要求候选人成为设计师，但要求他能判断这个任务该不该用多步表单，什么时候该展示进度，失败时用户看到什么。这些决定直接影响 Agent 的可用性。

第五层是工作流与团队。能定义需求、设计、编码、评审、测试、发布的流水线，能把 AI 嵌入每个环节，能建立评测标准和复盘机制。负责人要能定这条流水线，高级工程师要能在一个环节里做深。

技术面广有三个实际用处。第一，知道怎么指导模型。熟悉前后端、数据、部署和交互，才能判断模型给的方案哪里不对、该补什么上下文、该换什么工具。很多工作还无法全靠模型完成，人的判断仍然是瓶颈。第二，遇到问题知道往哪查。报错、慢查询、容器、检索、协议，能快速定位是模型问题还是工程问题。第三，知道怎么拆解别人的产品。用过足够多的工具和产品，才能把一个竞品拆成可实现的模块，而不是停留在「它有个聊天框」。

这也是为什么 Agent 工具团队的主栈通常是 TypeScript。Claude Code、OpenCode、WorkBuddy 这类工具以 TypeScript/Node 为主，Codex 也保留了 TypeScript 的 CLI 层。插件、协议适配和前端调试界面大多围绕这个生态。招聘 Agent 工具与工作流岗位时，一个只写 Java、不愿碰 TypeScript 的高级工程师，价值有限。Java、Go、Rust 当然有用，但更适合放在高并发后端、基础设施或性能敏感模块。它们替代不了 Agent 工具的主栈。

团队还需要至少一项明确的专长。广度不等于每项都浅。团队里至少要有一个人能在后端并发、数据一致性、检索质量、评测体系或前端交互中的某一项上做出判断。否则遇到疑难问题，所有人只能一起猜。招聘时可以接受「广度优先、单点中等」，但不能接受「所有点都浅」。让候选人挑一个自己最有把握的领域，连续追问三层「为什么」和「如果失败怎么办」。答得下去，说明确实做过；答不下去，说明只是听过。

能力 必备证据 不需要
工程基础 独立交付过一个前后端或全栈服务 手写 JVM 调优、背 Go 内存模型
模型工程 做过 RAG 或 Memory 的完整链路与评测 从零训练基础模型
协议工具 用过 MCP/A2A，能解释边界与权限 背协议全部字段
产品设计 能拆 MVP、画流程、分析竞品 专业产品经理或 UI 设计师的水准
工作流 定义过团队研发流程并落地 只做过个人效率工具

JD 重写：从技能清单到能力证据

旧 JD 的通病是以名词为中心：熟悉 RAG、熟悉 MCP、熟悉向量数据库。候选人只能回「熟悉」，面试官只能问定义，双方都在表演。新 JD 要以证据为中心：你做过什么，在什么约束下做的，结果如何，失败时怎么处理。

一个可用的 JD 结构是四段。第一段写岗位使命，说明这个角色负责什么业务结果，不要只写「负责 Agent 开发」。第二段写必备能力，每项配一条可验证的证据。比如「有 RAG 从 0 到 1 的落地经验，能说明切分、召回、重排和评测的具体取舍」，比「熟悉 RAG」有用。第三段写加分项，明确它不是筛人门槛。第四段写团队与协作方式：代码评审、评测机制、on-call、文档习惯。

必备能力可以收敛成六类。第一，完整交付过至少一个 Agent 或 LLM 应用，从原型到生产，能讲清楚场景、指标和失败经验。第二，设计过研发工作流，知道 AI 在需求、编码、评审、测试、发布各环节该放在哪里。第三，TypeScript 或 Python 至少一门精通，另一门能协作，有后端或数据工程底子。第四，理解 RAG、Memory、上下文压缩和上下文工程，能设计上下文预算和失败恢复。第五，用过 MCP、A2A 或同类协议，理解工具接入、权限和审计。第六，有评测与可观测意识，能用数据证明效果，不只靠演示。每条必备能力都要绑定一个面试环节：完整交付对工作流复盘，上下文工程对场景实战，工程质量对代码评审，协作对行为面试。JD 上写了却没人考，等于没写。

加分项可以保留设计规范、视觉规范、K8s、Figma/Pen，以及 Java/C# 等存量系统语言。它们只影响加分，不影响是否合格。JD 里要明确写「加分项不作为硬性筛选」，否则招聘系统会把合适的人筛掉。

管理岗的 JD 还要加三条。第一，带过 3 人以上团队，能做目标拆解、任务分配、风险预警。第二，建立过代码规范、评审机制和评测标准，并推动落地。第三，能做跨职能协作，把业务需求翻译成技术方案和排期。只写「有管理经验」不够，要写带团队交付过什么、团队规模、交付周期、人员成长。JD 里不要把学历、年限写成硬门槛。学历和年限说明不了他能不能交付，作品、复盘和现场表现更能说明问题。真要设门槛，就设「能展示一个从原型到生产的项目」。

旧写法 新写法
熟悉 RAG 落地过 RAG 链路，能说明切分、召回、重排与评测取舍
熟悉 MCP 用 MCP 接入过工具，设计过权限、审计与失败降级
精通 TypeScript/Python 一门主力、一门协作，有可展示的生产项目
有管理经验 带过 3 人以上团队，交付过从 0 到 1 的 Agent 应用
熟悉大模型 理解成本、延迟、准确率三角，能做选型与评测

JD 也不要太长。超过两屏，候选人会只扫关键词，面试官也会失去重点。把「必须具备」控制在六到八条，每条一句话加一条证据要求。其余放到加分项或团队介绍里。招聘页面要让合适的人判断「我该不该投」，不用写成能力词典。

面试设计：用场景工作流替代工具经验

面试从复盘开始，不做题。让候选人挑一个真实的 Agent 项目，从需求、方案、实现、评测讲到上线后的故障。重点听四件事：他如何拆问题，如何选择模型与工具，如何设计上下文，如何证明有效。没有真实项目的人，会在这四问里被看出来。有项目但只是「调用 API」的人，讲不清取舍和失败。

第二关是场景实战。给一个业务场景、一份数据、一个 Token 预算和两到三小时，让候选人做一条能跑通的流程：定义目标与验收标准，设计上下文与工具，写出关键代码，跑通演示，说明下一步怎么迭代。观察他如何控制范围、做取舍、做验证，代码量不重要。Token 预算会逼他考虑成本，避免无限堆上下文。

第三关是调试与评审。给一段失败的 Agent 轨迹：检索到错误文档、工具调用参数不对、上下文压缩后约束丢失，或者多 Agent 协作卡住。让候选人定位问题、提出验证方法、说明修复方案。再给一段代码或一个 Skill 定义，让他做 Code Review，重点看可维护性、错误处理和评测接口。

第四关是产品与协作。让候选人分析一个竞品，或者设计一个多步交互流程。问他会怎么和产品、前端、数据团队分工。Figma 不是硬性要求，但能画出清楚的流程和状态，是明显加分。

面试里少考四类题：模型内部原理、框架 API、算法题、工具清单。对应要考的是应用判断、工作流、调试能力和做成的项目。这四类题的共同问题，是把可搜索的知识当成能力，把工具经历当成经验。Agent 领域变化快，去年流行的框架今年可能已经换名。判断力和工作流比记住 API 更有用。

评分卡固定七项：问题定义、工作流设计、上下文工程、工程质量、评测意识、成本意识、沟通协作。每项 1 到 5 分，写清楚 3 分和 5 分的行为标准。面试官先独立打分，再开校准会。分歧超过两分，就回到行为证据。校准两次之后，团队的判断标准会稳定下来。工具名不要放进评分项，它只是候选人的经历。面试官还要提前准备场景包：一份脱敏数据、一段失败轨迹、一个 Token 预算、一张评分卡。所有人用同一套场景和标准，结论才可比。

环节 观察什么 红旗
工作流复盘 拆解、取舍、指标、失败恢复 只会讲工具、讲不出失败
场景实战 范围控制、上下文设计、可运行流程 无限堆功能、没有验收标准
调试评审 定位方法、验证意识、代码质量 靠猜、改 Prompt 了事
产品协作 流程、状态、跨职能沟通 把 Agent 当聊天框

人才选型：不唯算法博士，看三件事

不唯算法博士，不等于不看模型能力。应用型 Agent 团队需要懂模型边界的工程师：知道什么该用 RAG，什么该微调，什么该靠工具，什么该直接拒答。重点看三件事。

第一，成本、延迟、准确率之间的取舍。候选人要能说清楚，同样的任务，用更大模型、更多检索、更长上下文、更多 Agent 回合，分别会把哪个指标推高。反过来，用 Skill 复用、缓存、上下文压缩、模型分级，能省下什么。只会说「换更强的模型」的人，做不了生产。

第二，多 Agent 的协作能力。理解不同 Agent 的能力差异，知道怎么调度、怎么共享记忆、怎么管理文件与产物、怎么处理冲突和失败。多开几个 Agent 不等于协作。要像搭一个跨角色团队一样，定清楚谁负责什么、交接什么、谁做裁决、什么时候转人工。

第三，评测能力。能定义任务成功率、首轮接受率、返工率、单位任务成本，能建黄金任务集，能用数据判断一次改动是变好还是变坏。没有评测，Agent 团队只能靠 Demo 和感觉迭代。

这三条不会因为框架更换而失效。成本意识、协作设计和评测方法，换个模型、换套工具仍然要用。面试时可以这样问。成本取舍给一个具体任务，让他估算 Token、延迟和准确率。多 Agent 让他设计一个「需求、编码、测试」的协作流程，问清楚交接物和失败处理。评测让他现场设计十条验收用例，并说明怎么防止过拟合。

团队配置：前五个人怎么搭

第一个角色是 Agent 负责人或架构师。他要能设计工作流、定上下文工程方案、做协议与工具选型、主持评审，还要能写关键代码。早期不要招纯管理者。没有一线判断力，团队会在技术争论里失去方向。

第二个角色是 Agent 工程师。主力语言 TypeScript 或 Python，能接工具、写 Skill、做 Memory、处理流式与中断，能把一个多步流程跑稳。他不需要会训练模型，但要能和模型侧对齐。

第三个角色是 RAG 与数据工程师。负责文档解析、切分、索引、召回、重排、评测，理解向量数据库的选型与调优，能处理权限、增量更新和删除。RAG 做不好，Agent 的回答质量就上不去。

第四个角色是平台与可观测工程师。负责容器化、CI/CD、日志、trace、成本核算、评测流水线和告警。Agent 的故障往往跨模型、工具和网络。没有可观测性，排障只能靠猜。

第五个角色是懂 AI 的产品或设计师。负责场景选择、交互流程、竞品分析、验收标准，能和工程师一起把 Agent 的能力翻译成用户可理解的界面。这个角色可以兼职，但不能缺。

如果业务需要桌面端或复杂前端，再加一个前端工程师。如果需要高性能网关或基础设施，再加一个 Go/Rust 后端。招聘顺序建议先定负责人，再补 Agent 工程与 RAG，最后补平台与产品。负责人到位之前，不要先招一堆执行者，否则工作流没人定，团队会各写各的。人数不用凑，角色要互补。五个「会写 Prompt 的全栈」，不如三个各有专长的人加两个学习者。

2027 年 Agent 团队的技术栈建议以 TypeScript、Python、Go、Rust 为主。TypeScript 负责 Agent 工具、协议适配、编辑器与前端调试界面。Python 负责模型侧、RAG、数据处理与评测。Go 负责高并发网关、任务调度和服务端基础设施。Rust 负责性能敏感的执行器、沙箱与端侧能力。Java、C#、Kotlin 更适合维护存量系统或作为加分项，不建议作为新团队的主栈。

团队协作机制比角色名单更重要。建议固定四件事：一个共享的 Skill 仓库，所有可复用流程都进版本管理；一套黄金任务集，每次改动都跑回归；一份架构决策记录，关键选型留痕；一次每周 Demo，展示真实任务，不要用 PPT。缺了这四件事，角色再全，团队也会各写各的。

90 天落地与验收指标

前 30 天，选一个高频、低风险、可评测的场景，建黄金任务集，做出一条能跑通的流程，接上日志和成本统计。功能不用多，先把任务成功率、首轮接受率、单位任务成本、p95 延迟这四个数字跑出来。

第 31 到 60 天，做生产化。补权限、审计、失败恢复、人工确认、上下文压缩、缓存和降级。把 RAG 的召回质量、Memory 的写入策略、工具调用的幂等逐个确认。此时要开始做 on-call 和故障复盘，不能等上线后再补。

第 61 到 90 天，复制到第二个场景，验证 Skill 复用和团队协作。第二个场景如果能复用第一个场景的 Skill、评测集和可观测设施，说明团队留下了可复用的东西。如果全部重写，说明之前做的是一个项目，还没有形成平台。

验收指标分四组。交付组看从需求到 MVP 的时间、从 MVP 到生产的时间、版本迭代周期。质量组看任务成功率、首轮接受率、返工率、事故率。成本组看单位任务 Token 成本、人工介入分钟数、缓存命中率。团队组看招聘到岗时间、90 天上手度、评审覆盖率、文档与 Skill 复用率。指标要按场景和版本分组，否则无法判断是模型问题、上下文问题还是人的问题。招聘指标也要看：从 JD 发布到 offer 的时间、面试通过率、offer 接受率、90 天上手度、试用期留存率。面试通过率很高但 90 天上手度很差，说明面试考错了东西。offer 接受率很低，说明 JD 或薪资定位有问题。

小结

2027 年组建 Agent 团队，难的是判断一个人能不能交付 Agent。会写代码的人并不少。JD 要写能力证据，面试要做场景工作流，选型要看成本、协作和评测能力，不要只看学历。前五个人要角色互补，至少有一项拿得出手的专长。90 天先用四个数字证明流程能跑通，再谈平台化。工具和模型都会换。能把需求、上下文、工具、评测和团队组织起来的人，换一套技术栈仍然能用。

岗位定位

负责 Agent 应用从 0→1 与 1→N 的工程化落地：既能设计软件开发工作流与上下文工程体系，也能带队完成 RAG / Memory / 工具调用（MCP、A2A）/ Skill 化的生产级交付。

必备能力（Must-Have）

1. 工程与工作流设计

  • 具备设计软件开发工作流的能力：能定义需求→设计→编码→评审→测试→发布的流水线，并把 AI（Claude Code 等）嵌入为可复用的工程环节。
  • 熟练 TypeScript 与 Python，能作为主力语言进行架构设计与代码评审。
  • 理解 CSS 盒模型等前端基础，能与前端协作定义 Agent 交互层与可视化调试界面。
  • 熟练运用React/vue进行组件化开发

2. 数据与中间件

  • 熟练使用 MySQL / PostgreSQL，理解索引、事务、查询优化。
  • 具备 Redis（缓存、会话、限流）与 MQ（异步任务、事件驱动）的实战经验。
  • 熟悉向量数据库（如 pgvector / Milvus / Qdrant 等）的选型、索引与召回调优。

3. Agent 核心技术

  • 大模型 RAG：检索链路设计、切分策略、召回重排、评测闭环。
  • LoRA：微调数据构造、训练配置、效果评估与上线。
  • Memory：短期/长期记忆设计，写入、检索、遗忘与一致性。
  • 上下文压缩：长对话/长文档的摘要、裁剪、分层记忆策略。
  • 上下文工程：Prompt 结构、工具描述、状态管理、失败恢复的整体设计。
  • MCP：Model Context Protocol 的工具/资源接入与安全边界。
  • A2A：Agent 间协作协议、任务编排与消息契约。
  • Skill 开发 + 编排：将能力沉淀为可复用 Skill（定义、注册、版本、评测）；能让多个原子 Skill 协同工作的工程化方法。

4. 交付与工具链

  • Docker 容器化与本地/CI 环境一致性。
  • Claude Code/Codex 深度使用经验：能将其纳入研发工作流（代码生成、重构、测试、Review）。
  • 具备竞品分析能力：跟踪主流 Agent 产品/框架，输出选型与差异化建议。

5. 团队管理能力

  • 带队经验：有 3 人以上技术团队管理经验，能完成目标拆解、任务分配、进度跟踪与风险预警；能带 5–10 人团队者优先。
  • 人才建设：能识别团队成员能力短板，制定培养计划；具备招聘面试、梯队搭建与关键岗位备份意识。
  • 技术决策与标准制定：能主持技术选型评审，建立代码规范、Review 机制、文档规范与 Agent 评测标准，并推动团队落地。
  • 跨职能协作：能与产品、算法、前端、运维高效对齐，把业务需求翻译成可执行的技术方案与排期。
  • 绩效与激励：能设定可量化的团队目标（交付质量、迭代速度、成本与延迟指标），做绩效反馈与激励设计。
  • 工程文化：推动可维护、可评测、可观测的工程习惯；能以身作则使用 Claude Code 等工具提升团队整体效率。
  • 冲突与向上管理：能处理优先级冲突、资源争夺，向管理层清晰汇报进展与风险。

6. 项目经验

  • 项目经验：存在 Agent 相关的项目开发经历，或参与过相关开源项目；能清晰说明自己在项目中的角色、技术方案、遇到的难点与最终效果（如落地场景、性能/成本指标、用户规模）。
  • 有 Agent 应用从原型到生产的完整交付经验者优先；有可展示的开源贡献（PR、Issue、文档、维护者身份）者加分。

加分项（Nice-to-Have）

  • 设计规范 / 视觉规范：能定义组件与交互规范，提升 Agent 产品一致性。
  • Go / Rust / Java/C#：高性能服务或工具链开发。
  • K8S：Agent 服务的弹性部署与运维。
  • Figma / Pen：能快速产出原型与可视化方案。

我们希望你

  • 有 Agent / LLM 应用从原型到生产的完整落地经验。
  • 能够深入的前瞻的研究大模型的发展方向。
  • 能把”上下文工程”当作一等公民来设计系统，而非堆 Prompt。
  • 具备工程审美：可维护、可评测、可观测。
  • 既能自己写关键代码，也能带团队打硬仗。
