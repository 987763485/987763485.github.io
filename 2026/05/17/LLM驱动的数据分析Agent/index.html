LLM 驱动的数据分析 Agent

本文属于《Agent 智能体开发》第 51/55 篇
上一篇系列目录下一篇

把一句中文提问变成一张可信的图，看起来是最顺理成章的 Agent 场景：数据在仓库里，意图在问题里，中间只差一条 SQL。可真正推进时，多数团队会在一两个月内发现，难点不是让模型写出一条能跑的语句，而是让它在两个同名指标之间选中那一个。本文按“从问数到归因”这条链路，谈指标建模、text2sql 的可行边界、四道护栏、结果复现与人工复核。

落地率低的原因不在语法

演示与生产的差距，通常不在语法能力上。“上周的销售额是多少”这类问题，模型基本能对上一次；换成“上季度华东自营渠道的成交额同比”，失败立刻出现。差别在于后者要求它做四件没有依据去做的事：在多个同名指标里选一个、定时间粒度与对齐方式、把“华东”展开成维度取值、把渠道限定到自营。这四件事的答案都不写在语料里，而写在某个组织的口径约定里。

口径歧义的形态很单调。业务方口中的“成交额”，在仓库里可能对应下单、支付、发货与退款后净额四种实现，四者的差距在促销期尤其明显。时间上的坑同样密集：自然月的月环比在年初出现分母断层；周对齐口径下“上周”与“最近七天”不是同一个区间。维度上的坑是层级——“华东”是一级区域还是三个省，“渠道”指投放渠道还是销售组织，模型只能猜。

所以把“自然语言查数落地率低”归因于模型不够强，是错误诊断。更贴近实际的诊断是：仓库里没有一个程序可读、可查询、可校验的口径定义。语法问题归模型，口径问题归数据治理；后者不解决，前者再强也只是把错误写得更漂亮。

指标与口径要先建模

既然口径是病因，第一件事就是把口径从文档搬进元数据。搬进元数据的标准不是“有个页面写了”，而是“能按标识查到一个结构”。一个可被 Agent 使用的口径定义至少要四块：指标本体、维度与时间粒度、缺省限定条件、归属与状态。

四块里最容易被省略、收益又最大的是别名列表。把“成交额”“支付 GMV”“成交总额”挂到同一个标识上，是 schema linking 真正能起作用的位置。2023 年以来公开方法里那条“把问题中的词对齐到表和列”的线索，如果对齐对象只有物理表名与列名，天花板很低；把指标标识与别名一并纳入，命中质量才有改善余地。值检索与生成后执行反馈修正这些同期技巧，解决的都是“对齐”，不是“业务判断”。第二个不能省的是状态：active、draft、deprecated 三态，deprecated 必须指向替代指标，否则模型会毫无犹豫地用一张已废弃的表。

text2sql 的可行边界

把模型的生成能力看成一个有明确适用域的函数，比看成通用智能有用得多。适用域的形状由三个变量决定：涉及的表数量、时间范围是否已明确、维度取值是否可枚举。至于 Agent 怎么调工具、循环怎么编排，前期讲工具调用的文章已经覆盖，这里只谈取数这一步该交给模型多少。

问题形状 是否交给模型生成 判断依据
单表或两到三张表的星型聚合，时间范围明确 可以 关联路径唯一

有争议的口径之间做选择 不可以 决定取决于这次汇报要回答什么

前三行是安全区，共同点是歧义已被元数据消化掉，模型只剩把结构翻译成语句这一件事。归因值得单独说：模型确实能列出“客单价下滑”“新客占比变化”“某区域促销结束”这样的候选清单，这个清单有价值；但把哪一个认定为解释性原因，是业务判断，不接受模型投票。口径选择同理，用退款后净额还是支付口径，取决于汇报对象关心回款还是成交，答案不在数据里而在约定里。

四道护栏与默认拒绝

护栏要按顺序装：表白名单、只读身份、行数与扫描量上限、费用与超时上限。四条各自独立生效，任何一条不过就不执行，不存在前一条过了后一条就可以放宽这种逻辑。

第一道，表白名单。允许集来自元数据目录里状态为 active 且已登记归属的表，未列出的表、系统目录、临时表一律排除。关键是校验对象要取解析后的语句树——表引用集合、语句类型、函数集合——而不是对原文做正则；正则挡不住公共表表达式里的引用，也挡不住别名与注释拆开的关键词。

第二道，只读身份。执行通道使用与业务写入完全分离的账号，只有查询权限，并按角色限定可见的库与表；要写的东西不多，一张“角色到可见指标、可见表”的映射就够。授权模型另有专文，这里只强调取数场景最容易漏的一点：数据源口令不进提示词、不落日志、不参与缓存键拼接，示例配置里一律用占位符。

第三道，行数与扫描量上限。改写阶段强制注入行数上限，并按预估扫描量拦截。这里有个反直觉的规定：超限要直接失败，不能返回截断结果。截断比拒绝危险得多——模型会把截断样本当全量继续算比率，而图上看不出异常。

第四道，费用与超时上限。单查询超时与会话级预算，执行前用预估成本拦一次；计费与配额体系另一篇专门讨论，这里只把它当作第四道闸门。

默认拒绝必然带来例外，例外要走申请通道而不是走后门。临时申请写明表名、字段范围、使用时窗与用途，由该表归属方审批，授权自动到期回收，审批编号与运行记录关联。有三条不参与审批：只读、行数上限、扫描量上限。护栏被逐层磨薄，通常就是从“这次特殊一点”开始的。至于绕开这套机制的具体写法，本文一个示例都不给。

链路全景与结果可复现

一次问数产出的不是一张图，而是一条有向依赖：问题、口径、语句、数据、图形、结论，六环相扣。链路画全了，才知道每一环都要留东西。

flowchart TD
    Q[用户提问] --> R[问题改写与歧义检测]
    R --> M[指标元数据检索]
    M --> D{口径是否唯一}
    D -->|不唯一| C[回问确认口径]
    C --> M
    D -->|唯一| G[生成查询草案]
    G --> V[语句树白名单校验]
    V -->|未通过| X[拒绝并返回原因码]
    V -->|通过| P[绑定参数与扫描量预估]
    P --> H{是否在上限内}
    H -->|超限| X
    H -->|通过| E[只读通道执行]
    E --> S[结果集与快照版本落盘]
    S --> T[按判定表选图型]
    T --> W[生成结论与数字出处表]
    W --> O[复核签字]
    O -->|驳回| R
    O -->|通过| PUB[交付业务方]

只保存最后那张图，等于把前五环全部丢掉。可复现的底线是：三个月后有人质疑这个数字，我们能原样重跑并拿到同一个结果。每次运行至少要留住下面这些内容。

三个细节最容易漏。其一是快照：支持时间旅行就记快照标识，不支持就退一步记读到的分区清单，别假设数据不会变。其二是参数化：日期与维度取值走参数绑定而非字符串拼接，复现时换一组参数就能跑下一个周期。其三是口径版本：不记版本号，就分不清“重跑结果变了”与“口径被改过”。链路追踪与埋点前期文章已讲，这里只界定分析产物的最小留存集。

图表选择交给判定表

不建议让模型自由决定图表类型。同一份数据两次生成给出两种图，评审无法建立预期；模型的视觉偏好也不中立，双轴、立体、超过五类的饼图这类误导编码出现得不算少。图表选择本质是编码规则问题：类别比较靠长度与位置，部分与整体靠角度，关系靠二维位置，这套排序相当稳定，不必每次现编。

问题形状 首选图型 明确避免 备注

排名与前后对比 表格 装饰图 表格常被低估

模型的正确位置是填槽：判断问题落在哪一行，给出轴字段与聚合方式，渲染层按判定表出图。这样同一数据永远得到同一图，驳回条件也能写成“图型不在判定表内”这种可判定的话；新增业务域时扩充表格，而不是回去改提示词。

四类高频错误

第一类是口径漂移：第一问命中支付口径，第三问的过滤条件被某条改写规则悄悄覆盖，同名不同义却没人察觉。第二类是样本过滤缺失，典型表现是分母不一致——比率型指标的分子按“已支付”过滤，分母却按“全部下单”过滤，算出的比率低得吓人，图上却一切正常。治它要把分子与分母成对写进指标定义并共享同一组限定条件，限定条件不该留在外层过滤里。

第三类是幻觉数字：模型不调工具，直接用上一轮的残留内容给出一个“看起来合理”的数。这条最便宜也最救命——答案里出现的每个数字都必须能追到某个结果集的某个单元格，追不到就判失败，宁可回答“取不到”。第四类是多轮追问里的指标替换：“那华东呢”省略了主语，模型默认沿用第一问的指标，用户此刻想问的其实是另一个。做法是把继承项显式回显并留一个改口径的入口；有歧义时问一句，猜错的代价是一次已经发出去的汇报。

复核环节要有明确的输入输出

“要人审”是口号，不是设计。设计长这样：输入是一份运行记录包，输出是结构化判定——通过或驳回，加一个原因码和一句说明。在群里回一句“看起来没问题”不算复核：那种回复无法统计，也无法在同类错误第二次出现时提醒任何人。

签字的人要拆开。口径由指标归属方签，确认该不该用这个定义；结论由业务复核人签，确认这个数字是否真的回答了最初的问题；护栏由数据平台值班签，确认有没有访问白名单外的表、上限有没有被临时抬过。一个人把三样全签，复核在两三次之后必然退化成盖章。复核人只看三处：指标标识与版本、实际执行的语句与扫描量、结论与结果集的对应表——都在包里，不需要谁重跑查询。

驳回之后要把这一问一答补成别名表或示例集里的一条记录，让同一个坑不掉两次。怎么把它做成体系化的评测集、怎么设发布卡点，另有一篇专门谈评测体系的文章覆盖；厂商工程栏目里关于智能体评测与受管智能体的讨论只作通用参照，此处只取“复核要有明确判定输出”这一点。企业内部流程接入与推广次序，前期文章已有交代。

小结

这条链路上模型真正负责的部分很小：把已消歧的结构翻译成语句，把问题归到判定表的某一行。剩下的都在模型之外——之前是元数据与四道护栏，之后是留存与复核。text2sql 帮的是对齐，业务判断仍是组织的资产，指望模型替我们把资产补齐，是这类项目最常见的起点错误。

可执行的起点只有一条顺序：先把被问得最多的三个指标写成结构化定义，带上别名与状态；再把白名单与两条上限接进执行通道，做成不可绕过的语句树检查；最后给每次问数生成运行记录包，让人在上面签字。这三步走完，能问出来的问题会比换一个大模型多得多。
