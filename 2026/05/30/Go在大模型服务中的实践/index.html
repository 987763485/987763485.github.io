Go 在大模型服务中的实践

Go 在大模型服务里的位置，不是把权重跑起来，而是做编排、网关与长连接服务：推理运行时交给 Python 与 Rust 的生态，Go 负责把请求送出去、把流收回来、把失败与取消传播到底。这句话是全文主线，后面每个环节都是它的具体化。

位置：编排、网关与长连接

大模型链路有三种活：算（矩阵乘、显存调度）、编（规划、工具调用、分支与重试）、通（长连接、流式回传、外部调用）。Go 的舒适区在后两项：标准库把 HTTP/1.1 与 HTTP/2、TLS、超时与取消做成了可直接上线的形状，goroutine 恰好贴合“一个请求一条流”的生命周期；“算”依赖 CUDA 栈与显存生命周期控制，用 Go 重写既不划算也没生态支撑。

相邻内容各划一句界限：Go 写大模型应用的基础形态前期已有专文，本文不复述；Eino 是 Go 语言的 Agent 编排框架定位、eino-ext 提供其周边组件扩展，本文只承认这层能力存在、不假设任何接口；网关层的协议适配与配额路由另有专文，本文只讲服务进程内部。本文是代码级清单，不是框架评测。

SSE 客户端与连接生命周期

http.Client.Timeout 覆盖的是从发起请求到读完响应体的整个过程，而不是首字节。这个语义在普通调用里是好事，在流式调用里是定时炸弹：一次正常的两分钟生成会被它在两分钟处掐断。你真正想要的两件事是“连不上要快失败”与“帧之间不能无限静默”：前者属于传输层，交给拨号超时与响应头超时；后者属于应用层，只能在读循环里自己做空闲检测。

这段的形状比语言细节更重要。超时按层放：建连与响应头在 Transport，静默上限在读循环，整条请求的上限在调用方 context，三者不能互相替代。看门狗只取消 context，不直接关 Body——net/http 会随请求 context 取消打断阻塞中的读，关闭动作仍由 defer 唯一负责。另外两个易错点：onFrame 在读循环里同步执行，业务一阻塞活跃时间就不再刷新，慢消费者会被误判成上游静默；scanner.Err() 之后要区分 context 取消、看门狗超时、上游正常关闭三类结束，混成一类会让“上游真的断了”永远查不出来。

服务端转发流时同样有生命周期：客户端断开后 net/http 取消 r.Context()，这个 context 必须一路传到回源请求；Flush 失败要立刻退出读循环，连接级 deadline 用 http.ResponseController 设置。

context 取消与三层超时预算

大模型调用的耗时分布很宽：一次工具查询是几十毫秒量级，一次长答生成是几十秒量级。单层超时必然失效——设长了挡不住慢工具，设短了打断正常生成。所以预算分三层：请求级（端到端上限，入口中间件按调用方声明与 SLA 设定）、步骤级（一次模型往返或一轮规划）、工具级（一次外部调用，由工具自身性质决定）。三层都用 context 表达，父子关系就是预算包含关系：步骤级不可能超出请求级，工具级又受步骤级约束，这层包含由 context.WithTimeout 天然保证。

那行注释是这条链路上最贵的一课：parent 必须是入口传下来的 context。中途有人图省事写了 context.Background()，取消传播就在那里断掉，上游断开、下游继续生成，代价以 token 计费的形式回来。

“上游断开不等于下游会停”要写成两条检查，而不是一个信念。第一条：客户端断开时 net/http 只取消 r.Context()，任何替换 context 的地方都要证明替换有理由——只有清理动作（落审计、补计费、写指标）允许用 context.WithoutCancel 显式脱离，且它自己必须带一个短 deadline，否则这段清理会在进程退出时变成新的泄漏源。第二条：取消能到达不等于循环会响应，读循环、重试循环、工具批量循环都要在每轮开头检查 ctx.Err()，阻塞点必须可被取消打断。用 context.WithTimeoutCause、context.WithCancelCause 与 context.Cause 记下“为什么结束”，把用户主动断线、预算耗尽、上游错误这三类分开——重试策略与告警路由都依赖这个区分。

重试预算必须挂在请求级 context 上，而不是每次重试新起超时：像 for i := 0; i < 3; i++ { context.WithTimeout(context.Background(), 5*time.Second) } 这样写，三次合计十五秒，请求级预算形同虚设，退避期间还没人看门。正确形状是让退避等待也 select 在 ctx.Done() 上，或用 context.AfterFunc 把取消转成回调。

并发、槽位与背压

流式服务的并发单位不是每秒请求数，而是“一条仍然活着的连接”：背后是一次上游生成、一个读 goroutine、一个看门狗和若干缓冲内存，存在时间与请求速率没有换算关系。所以准入要按活跃槽位设计，而不是照搬按速率的限流器——令牌桶与漏桶的推导前期文章已经写过，本文只谈 Go 里的落地形状。

槽位切两级：租户级防止单个业务方吃光整机，上游或模型级防止一个慢后端把无关请求一起拖死。申请顺序固定、释放顺序相反，任何一步失败都要归还已经拿到的槽。

三点补充。第一，take 的 select 里必须带 ctx.Done()：只写 ch <- struct{}{} 等于把“排队等到天荒地老”设成默认行为，槽位占满时 goroutine 数随排队长度增长，故障表现为内存与调度一起崩。第二，超出排队上限的请求要快速失败，这才是把背压交回调用方；压在进程内排队只是延后故障，还把等待时间计进端到端预算。第三，Agent 内部的多路并行用 errgroup 并显式 SetLimit，任一失败即取消整组，符合“这一步失败就别再花钱”的意图；要保留部分成功就改成收集错误。

还有一条常被跳过的规则：槽位释放点必须在流真正结束处，而不是处理函数返回处。defer release() 写在 handler 上、帧处理丢进异步 goroutine，槽位就在流刚开始时归还了，进程显示并发远低于实际并发，看起来像“没限住”。

流式 JSON：增量解析与延迟解析

流式响应把 JSON 解析从“一次性动作”变成“带状态的协议行为”。三个问题必须显式回答：帧里的内容可能只是半个对象；字段可能在某帧出现某帧缺席，而“缺失”与“显式为 null”业务含义不同；有些字段很大且永远不需要进上下文。对应的三个 Go 手段是截断判定、指针与 omitempty 的取舍、json.RawMessage 延迟解析。

四条硬规则。第一，半截帧只能“等待”，流结束仍不完整才算协议错误；当成脏数据丢弃的后果是用户看到的回答缺一段而日志一切正常。第二，buf.Reset() 只在解析成功时执行，这正是上面那段代码要返回 bool 的原因。第三，大字段（base64 图像、整页 HTML、长数组）不要反序列化进上下文：先在 json.RawMessage 层面判长度与类型，落对象存储或临时缓冲，进上下文的只是引用与摘要。第四，校验自己的配置时可以用 DisallowUnknownFields，解析外部上游响应时绝不能——加字段是常态，严格模式会让你的服务在别人发版那天集体报错。

上游若用换行分隔的 JSON 而非 SSE，同一个 json.Decoder 配 dec.More() 循环读取即可，它自带跨值缓冲；一旦读到截断就要把连接判为已终止，缓冲里已没有可恢复的值边界。

配置分层与密钥注入

配置的正确形状是四层从低到高：编译期默认值、配置文件、环境变量、进程参数，后者覆盖前者，只有运行期要变的项才允许热加载。Go 里不需要框架，规则是结构体上打默认值、显式列举可覆盖项、未知键报错。两个极端都容易出事：全塞进 map[string]any，类型错误要到运行时某个分支才暴露；每项都配一个环境变量覆盖，部署清单就成了没有源可查的第二套配置。

五条要点。第一，密钥从环境变量或平台密钥服务注入进程内存，不落盘、不进命令行参数（ps 与容器 spec 都能看见）、不进配置文件。第二，凭据缺失要在启动期失败并让就绪探针不通过，而不是等第一个请求才报错——静默降级成“未配置”是最难排查的一类故障。第三，结构体标签只描述序列化关系，不要承载业务语义，协议适配放在显式转换函数里。第四，String()、MarshalJSON 与错误包装这三处要主动屏蔽凭据字段：给密钥类型实现返回固定占位串的 MarshalJSON，能挡住绝大多数“日志里出现密钥”的事故。第五，日志与 trace 属性里不得出现凭据，也不得出现用户提问原文；采集、脱敏与留存属于可观测主题的分工，另有专文，本文只要求 Go 侧提供字段级脱敏类型与显式白名单导出。

部署体积、就绪语义与优雅退出

Go 在这一环的优势不是产物体积小，而是交付形态简单：编译出一个可执行文件，启动没有解释器加载与依赖安装阶段，容器里不需要运行时生态；代价是要把构建期与运行期的差异管干净。

三条纪律。第一，CGO_ENABLED=0 得到纯静态产物，镜像里只放二进制与证书 bundle；一旦引入依赖 cgo 的库，静态承诺就作废，这个取舍要在选型时定，不该到构建脚本里救。第二，就绪与存活必须分开：存活探针只回答“进程还在被调度”，就绪探针要回答“配置已加载、密钥已取到、到上游的连接已预热”——启动时做一次轻量握手，把 DNS 与 TLS 摊在启动阶段，否则第一个真实请求同时承担解析、握手与生成，在监控里像上游偶发超时。第三，Shutdown 会等在途请求，但流式请求的结束时间不可控，所以长任务的正确姿势不是“等得更久”，而是先摘流量、再给在途流一个可声明的窗口并与平台终止宽限期对齐；平台侧相关能力仍在演进，本文只依赖长期稳定的语义：超期即强制终止且不可捕获，因此必须完成的收尾要有窗口之外的机制兜底，例如落队列由下一个实例接续。

配套两个细节：用 ConnState 或在排空前统计活跃连接，能给出“还剩多少条流”；所有后台 goroutine 统一挂在同一个根 context 上，退出时用 sync.WaitGroup 显式 join，否则优雅退出只关了一半。

与 Rust 的分工：只看取舍维度

这条链路上 Go 与 Rust 不是替换关系，而是分层关系。选 Go 的场景特征：以 I/O 为主、生命周期与请求一一对应、要管大量并发连接、协议适配频繁变化、团队需要快速交付并读懂别人的代码；标准库直接覆盖 HTTP/2、TLS、context 与超时，不必为“收稳一条流”引入第三方依赖，运维侧也只要一个二进制。选 Rust 的场景特征：需要精确掌控内存布局与分配行为、垃圾回收停顿不可接受的位置、在进程内做靠近运行时的 tokenizer 或张量胶水、FFI 边界要类型级安全保证，以及“宁可编译期复杂也不要线上偶发抖动”的价值取向。

两个维度上取舍方向相反。并发模型：goroutine 让“一个连接一个循环”几乎免费，Rust 的所有权与 async 组合子会把同样的形状变成需要显式处理的生命周期问题——这是设计取向的差别，不是能力缺陷。演进速度：上游协议几个月一改，Go 的适配层是普通结构体加转换函数，心智负担小；Rust 的类型系统能在编译期挡掉更多协议不一致，代价是改动半径更大。于是常见的稳定分法是：推理运行时与需要确定性内存行为的组件用 Rust，编排、网关、BFF 与长连接服务用 Go，两侧以进程边界或 FFI 边界相接，边界上的错误传播、超时与取消由 Go 侧负责到底——用户看到的完整请求只有 Go 这一侧认识。这里不谈性能：两边各有能赢的场景，而赢的不是同一个指标。

小结

回到开头那句：Go 在大模型服务里做的是编排、网关与长连接，不是跑模型。这句判断落到代码上是一串具体动作——超时按层放、取消传到底、槽位按活跃连接计、半截 JSON 只等待不丢弃、密钥与提问原文都不进日志、退出时先摘流量再排空。这些都不靠第三方框架，也不会因为“标准库够用”自动获得，全部体现在谁持有 context、谁负责关闭、在哪里归还槽位这些细节上。模型能不能跑起来由 Python 与 Rust 决定，跑起来之后的可靠性、成本与可运维性由 Go 侧这些形状决定；把上面这张表当评审清单跑一遍，比读十篇选型文章有用。
