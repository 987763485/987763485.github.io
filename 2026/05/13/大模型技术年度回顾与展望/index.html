大模型技术年度回顾与展望

这一年的公开信息里，版本号比洞察多。本文只挑那些真正改变了工程做法的事件，按时间轴串成三条主线，并把每条主线的代价一并记下来。末尾的展望全部标注为推测，每条都给出可证伪的条件。

为什么年度回顾容易写坏

写”年度回顾”最常见的失败，是把罗列当洞察：把一年里发布的版本号、模型名、协议名按日期排一遍，读者读完只知道世界变快了，不知道自己明天该改哪一行代码。第二种失败更隐蔽，是把某项标准化工作写成”某某胜利论”，再反过来用它解释所有工程决策；而真实情况往往是，多数团队只是被迫多维护一套兼容逻辑。

所以本文的切法只有一条：只回顾改变了工程做法的事。”是否改变了做法”我写成一份可操作的清单，三条里至少满足两条才纳入。

先把边界划清。空间维度上的分层与组件总览，《Agent 架构设计总览》已经写过，那是”一个系统有哪几层”；本文写的是”这一年哪一层被动过”。机制细节——偏好优化族、可验证奖励、过程监督与结果监督——不复述，只在它们改变工程形态时一句带过：它们让”模型可以长时间工作”从设想变成工程前提。榜单怎么读、为什么不该用它做选型，另有专文；本文通篇不出现名次、分数、参数量与价格。

主线一：从”一次调用”到”一次任务”

发生了什么。模型侧的代际更替本身不直接改变做法——Claude Opus 4.6 与 Sonnet 4.6、Qwen3.5 这一批的意义，在于把”可以长时间工作”变成可信前提。前提成立，编排层形态跟着变：LangChain 从 1.x 走到 1.2、LangGraph 出现 1.0 与 1.1 口径之后，主流写法从”拼一条提示链”转为”定义一张带状态与重入点的图”，节点之间传的不只是文本，还有结构化中间结果与失败标记，图的边界成了检查点的候选位置。Agent Skills 于 2025-10-16 起用，把”能力包”从散落的提示词文本变成有目录结构与加载语义的东西，”装什么、什么时候装”第一次成了配置问题而不是文案问题。

同一时期，Anthropic 工程栏目给出《code execution with MCP》《long-running harnesses》《agent evals》《managed agents》这几篇标题级文章。不复述其内容，但选题本身就是信号：讨论重心从”怎么问”移到了”怎么让它跑完并且能收回来”。至于”用执行反馈替代模型自评”与”搜索式规划”，机制细节在《Agent 规划能力提升实践》里写过，这里只作为现象记账：它们在今年从论文话题变成周报里的常规条目。

代价是三项一起上移。第一，延迟与成本从”可以优化”变成”必须预算”：一次任务的响应时间不再是单次推理的函数，而是重试次数、检查点落盘开销、子任务并行度三者的函数，彼此纠缠，只能实测。第二，可观测复杂度上移：以前盯请求级 QPS 与 P99 就够，现在还得看任务停留时长、中断后的恢复成功率、半完成状态的残留量，而各家口径都不一样，跨团队对齐很贵。第三，出现了过去不存在的失败模式：任务跑到一半进程被杀、外部工具已改了状态但本地记录没写、恢复后重复执行同一步。幂等与重试的老框架处理得了，只是今年触发频率换了一个量级，老问题必须从”事后加固”提到”设计时约定”。

主线二：协议与工具生态进入修订年代

发生了什么。第一件事，工具层协议出现了修订版本序列。以 MCP 为例，2025-11-25 那一版修订的意义不在新增了哪个方法，而在于”用日期串当版本号”被固化下来：客户端与服务端必须就某个日期串代表的能力集做协商，而不是默认双方看的是同一份文档。版本号一旦需要协商，它就从文档标记变成运行时对象。

第二件事，注册表出现，而且必须说清它是预览状态。Registry 在今年上半年仍是预览口径，它解决”去哪里发现一条集成”，不保证”这条集成能跑”——今年确实有团队把两者当成同一件事，代价到联调阶段才暴露。第三件事，治理关系变动：2025-12-09 的公告把 MCP 的治理交由 Agentic AI Foundation 承接。跨智能体协作这一侧，A2A 于 2026-03-12 发布 v1.0.0，04-12 起用，到本文写作时刚好可用；AGNTCY 代表同一需求上的另一条生态路线。这些事件放在一起不构成”某个协议赢了”的证据，只说明一件事：工具与协作接口开始有兼容性负担。协议清单与结算的讨论在《多智能体经济与协作协议》里写过，本文只记接口形态这一年的变化。

标准化带来的第一份成本就是兼容矩阵。以前只有一条”我们用的版本”，现在有四个维度：协议修订日期串、客户端实现版本、服务端实现版本、传输方式。矩阵一旦存在，最贵的不是实现而是测试——每种组合的降级路径都得有人真的验证过，否则它只在你没测过的那一格失效。

flowchart TD
  A[新修订起用通知] --> B{服务端是否跟上该修订}
  B -->|是| C{客户端是否支持能力协商}
  B -->|否| F[该服务退回手工内联配置]
  C -->|是| D[按协商出的能力集调用工具]
  C -->|否| E[固定单一版本并登记例外]
  D --> G{注册表发现是否命中}
  G -->|命中| H[正常调用]
  G -->|预览期未命中| E
  E --> I[例外进入兼容性测试矩阵]
  F --> I

发现与可用之间隔着授权、传输约束与版本协商三段路，每一段都可能单独失败；把”注册表里有这条记录”当成”这条集成可用”，是今年最容易拖到项目复盘才被发现的错误。

主线三：部署、成本与端侧

发生了什么。降本这一侧，路由与级联从技巧变成默认架构。路由信号的来源、级联的写法与升级判定这三块在《模型路由与级联》里写过，本文不复述；这里只记它进入主流之后的组织后果——一旦”用哪个模型”成为运行时决策，效果归因就再不能按单模型口径汇报，评测集要为每条路由分支单独维护，否则线上劣化无法定位到分支。

运行时这一侧，沙箱与出口治理成了默认要求。代码执行类工具一旦被允许，网络出口范围、文件写入范围、凭据暴露面就从”可选加固”变成上线检查表上的必答题。变化不在原则而在位置：以前这类要求到安全评审才出现，现在架构评审阶段就必须有答案。

基础软件层也在换代：Go 1.26 已起用，Kubernetes 按 1.35 口径讨论，PyTorch 走到 2.10 与 2.11 区间。我刻意不把结论绑到具体特性上，这几版差异主要在工程链路稳定性与构建体验，不在能力边界。端侧推理进入产品叙事，卖点是离线与隐私，而不是算力替代。

合规也在同一年落成工程约束：欧盟 AI 法案的 GPAI 义务自 2025-08-02 起适用；国内标识办法配套 GB 45438-2025 于 2025-09-01 施行，AI 生成内容的标识从此属于交付物本身。它容易被当成法务事项，实际改变的是导出链路：标识信息要在转换、截断、二次分发的每个环节保持完整，这是一项工程验收标准。

代价是团队要多养一套评测与预算治理。这两件事过去属于”上线以后再说”，现在属于”没有就先别上线”。

这一年改变了哪一层

把三条主线按层拆开，更容易看出自己受影响的到底是哪一层。

层 一年前的默认写法 现在不能再这样写 遗留下来的老问题
模型层 选定一个模型，围绕它写提示词 选择变成”一组模型加一条路由策略”，单模型假设一旦写进接口就要返工 能力上限仍然决定任务能拆到多细
协议层 工具用内部函数签名直连，改了同步改 外部接口有修订日期串与协商语义，私有约定不再自足 版本演进带来的兼容测试成本
运行时层 一次请求一次响应，进程可随意重启 长任务需要检查点、可重入与幂等恢复 分布式系统老问题换了位置重现
组织层 算法负责人管效果，运维负责人管可用性 需要评测与预算两类职责，合规进入交付链 权责划分仍然靠人推动，工具不会替你分工

读法很简单：某一行”现在不能再这样写”那栏若是空的，说明这一层今年并没有真的变，相关报道只是噪音；返工集中在哪一层，今年新设的负责人就该在哪一层。

展望：三条可证伪的判断

以下是推测，不是建议。为避免把未来写成事实，三条判断的证伪条件只描述可观察现象，不预设具体日期与事件。

第一条，协议层的成本会显性化。我判断：兼容矩阵会从少数平台的负担变成普遍技术债，降级案例与兼容性声明会公开增多。证伪条件——如果接下来两个修订周期内多数团队仍各自做私有适配、修订日期串实际只剩一个被广泛使用的取值，那么”标准化的第一份成本是兼容矩阵”就错了，我把还没发生的事写成了主线。

第二条，运行时层会独立成一个岗位口径。我判断：长时任务的检查点、恢复与幂等会由专门一层承接，业务代码不再自己保存中间状态。证伪条件——如果托管执行形态在下一个周期里仍把中间状态留给业务方，只是在模型调用外面又包一层，那么”运行时独立成一层”是我判断错了，它只是编排的别名。

第三条，端侧叙事与真实流量之间存在缺口。我判断：设备侧推理短期内主要贡献体验差异而非算力卸载，长任务主力仍在云端。证伪条件——如果设备侧承接长任务的比例在你们自己的可观测口径上持续上升（口径与阈值属团队约定示例，不是行业数据），那么我把端侧写轻了，它本该单列一条主线。

三条判断共享一个弱点：都建立在”今年的变化是结构性的”这一假设上。如果它只是能力快速扩张期的一次工程化补课，模型再强一些就自动消解，那三条会同时失效。

什么没有变

这一节是本文的落点。三条主线读起来像地基被换过，但今年被反复重造的轮子，全都装在同一副旧底盘上。

上下文预算。任务变长以后，预算问题不是被解决，而是被摊到更多地方：系统提示、技能注入、检索片段、工具返回、历史轮次，五处抢同一份窗口。窗口变长只改变了这个问题的刻度，没改变它的形状。今年所有能力包机制最后都要回答同一句话——装进去的东西挤掉了什么；答不上来，说明成本只是挪到了别人看不见的地方。

评测。评测集仍然难做，因为它同时要求覆盖真实任务分布与可自动判分，而这两条天然对立：越真实越难自动判，越容易自动判越像玩具。相关讨论今年标题级地变多，方法没有换代，仍是构造任务、定义判分口径、监控漂移。

幂等。只要一次任务包含外部写操作，重复执行的语义就必须显式定义，这与模型换了几代无关。新增的只是”重复”的来源：中断恢复、超时重试、人工再跑一遍。老框架够用，只是必须更早进入设计评审。

权限最小化。工具、技能、注册表都让可访问面变大，原则一条没变：能不给的权限不给，给了的要有生命周期与回收。出口治理的兴起，本质上是同一件事在网络维度上的版本。

本文不评价”谁赢了”，也不预测哪个接口会取代另一个。榜单与分数决定不了架构该改哪一层，能决定的只有你线上真实出现的失败模式。

小结

今年真正改变工程做法的是三件事：计量单位从一次调用变成一次任务；外部接口开始有版本与兼容负担；运行时约束与合规要求进入默认检查表。共同代价是复杂度整体上移，以及团队凭空多出的两类职责——评测与预算。展望的三条判断都标明推测并附证伪条件，欢迎在下一个修订周期推翻。而上下文预算、评测、幂等、权限最小化这四件事今年一次都没被解决，只是各自换了更好听的名字。如果这份回顾只留一句可执行的话：追任何一个新版本之前，先确认它会改动你的哪一层，以及那一层现在有没有人负责。
