大模型服务化与网关设计

当“一次请求换一次回答”变成“一条长连接挂着一串工具调用与中间推理”，网关的工作性质就变了。本文只谈智能体时代网关与服务化层多出来的职责：粘性、流式、工具通道、配额、归因、留痕；通用网关的老本行与限流算法本身不复述，只一句划界。

老网关为什么不够用

传统 API 网关的假设很干净：请求短、响应短、无状态、错误可用一次重试抹平。智能体把这四条逐一拆掉：一次会话能持续几十分钟并夹着若干轮工具调用；上下文是有位置的，落到哪个实例显著影响命中率；失败不是重放一次就完事，工具可能已经产生外部副作用；响应逐 token 吐出，任一方先撤都留下半截状态。于是网关长出四条长期职责：会话守门人，得把“会话”当一等技术而不是业务方的私事；协议翻译层，上游流式、客户端可能只吃 SSE、中间还要接 gRPC；动作的执行通道，工具要出网、要鉴权、要在危险动作前停下，不能全指望编排层自觉；数据出口，费用、留痕、指纹这些原始事实只有这一层看得全。通用网关设计与服务化流水线前期已讲，本文只算增量。

会话粘性：键选错，后面全白搭

粘性要让同一会话的后续请求回到同一份上下文，难点不在实现而在选键。不要拿用户明文标识当键：用户 ID 一旦进了网关日志、指标标签与连接元数据，就在多个系统里复制了个人身份。做法是网关在会话建立时签发一个不可推导的会话键承载粘性，用租户维度做二级分桶，长任务再引入任务标识——会话键管上下文归属，租户键管配额与故障域，任务键管续传与幂等。形态示意如下，本项目自定义示例，不是任何产品的官方 schema：

粘性做重，扩容与故障域就变疼：会话被钉在实例上，新实例接不到活、老实例迁不走，扩缩容从随手杀掉一个 Pod 变成等会话自然结束；实例重启或跨节点迁移还会让上下文缓存整片丢失，形成同一次故障下的批量重放。缓解靠上下文外置、网关实例可从任意点重建、再平衡时优先迁空闲会话；粘性只保证体验更好，绝不作为正确性依赖。

取消语义要单独设计：客户端断开不等于任务取消，刷新页面、网络抖动、退到后台都可能只是连接断了。显式取消沿“客户端 → 网关 → 编排 → 上游”逐层传，网关即使自己维护着上游连接也必须继续下传；隐式断连先进宽限期再决定回收，宽限时长属团队约定示例。最容易漏的是网关到上游这一段——网关忘了自己才是那条连接的所有者，客户端一断就丢上下文，让上游继续白烧算力。

流式协议转换与半截响应的处置

网关夹在两种流式表达之间：上游常见 SSE 或 gRPC 服务端流，客户端可能是 EventSource 语义、WebSocket，或只会轮询的旧前端。坑不在帧格式，在语义映射：SSE 有事件名与 last-event-id 的续传约定，WebSocket 没有内建的事件标识与重放语义，gRPC 流靠 HTTP/2 流控管背压。对齐三者要网关自造一层“事件序号 + 事件类型 + 终止标记”的中间表示再各自投影，别指望跨协议无损。

背压要显式接住：客户端慢、网络抖、上游快叠加时，无界缓冲先垮的是网关自己。做法是每个活跃流持有一个有界队列，队列满时先向上游施加背压而不是先丢消息。心跳与空闲超时要分开，前者保连接不被中间设备掐掉，后者判死流，数值都属团队约定示例，配太紧会把正常的长思考误杀成超时。半截响应是最需要预先定义的结局，下面把三种中断分开表示。

sequenceDiagram
    participant C as 客户端
    participant G as 网关
    participant O as 编排服务
    participant U as 模型上游
    C->>G: 建立流式请求（带会话键与指纹）
    G->>O: 转发并登记流
    O->>U: 推理请求（流式）
    U-->>O: 增量分片
    O-->>G: 增量分片
    G-->>C: 投影为目标协议的事件
    Note over C,G: 分支一 客户端先行断开
    C--xG: 连接中断
    G->>O: 进入宽限期，保留流与序号
    Note over G,U: 分支二 上游中途断流
    U--xO: 流在非终态处结束
    O-->>G: 返回中断状态与已产出序号
    G-->>C: 下发显式终止事件（不得静默收尾）
    Note over C,O: 分支三 显式取消
    C->>G: 取消指令
    G->>O: 继续下传取消
    O-->>G: 确认停止与终态
    G-->>C: 终态事件后关闭连接

处置原则三条：非终态的流必须让客户端看见一个明确的终止事件，静默关闭等于让对端猜“答完了还是断了”；已产出的部分要落一个可判定的状态标记供续传或重放参考，但别当成完整回答写进长期存储；重放只对无副作用的上游段成立，流里一旦夹了工具执行，续传就让位给幂等与去重。

工具调用中转：把出口做成一条门缝

工具调用若让编排层直连外部，网关就退化成可有可无的前置件：白名单、鉴权与留痕得在每套编排实现里重做一遍。更稳的做法是把“任何工具执行都过网关”当作架构约束——上行它是模型的输出意图，下行它是网关发起的真实外呼，中间由网关完成意图校验、目标解析与凭据替换。白名单因此要落在网关：编排可以被绕过（调试入口、临时脚本、被污染的提示词诱导），网关绕不过去；粒度建议到“工具 + 方法”这一级，只放行某工具名的读操作、写操作需额外条件。

网关在这里承担三道机械动作。一是参数收敛：模型塞进来的超长上下文在出网前截断，规则按工具维度声明，截断事件单独计数。二是结果裁剪：外部返回体可能巨大且夹带无关内容，网关按工具维度设上限并保留结构完整，避免整页原文回灌进下一轮上下文。三是确认门槛的落点：要不要人批、批给谁属授权模型的事，本文不复述；但“暂停执行、等待确认、超时后放弃”这个状态机必须挂在网关上，因为只有它同时握着这条调用的上下文与出网能力。凭据不进上下文窗口、不进日志、不进缓存键这三条禁区安全侧已写清，网关的贡献是让它们机械不可达。

多模型出口、配额与路由表

出口维度的增量是“业务线”这一层：每条线对可用性、数据出境范围与预算的感受完全不同，配额要按租户/业务线切而不是按全局总量切。令牌桶、漏桶这些算法前期限流文章已讲透，本文不复述；网关侧的新活是配额维度的选择——用请求数还是用量单位记账、跨模型怎么折算、超配之后是排队还是降级，折算口径则要由网关统一持有，否则同一业务线在监控和报表里会算出两个数。熔断与失败回退的判定策略、重试放大的成因属路由与级联那篇的结论，本文只确认这些策略的计数器与执行点落在网关。

模型上下线是网关日常。路由表建议做成可热更的数据面配置，而不是随编排发布的常量；表项至少含模型标识、可服务业务线、灰度权重与开关，回滚就是把权重拨回上一个已知良好版本，所以路由表要留版本历史、能整表回放。权重拨到零不等于下线：留一段只进不出的观察窗口让存量会话自然结束。

成本归因：网关侧事实，不是账单侧数字

一次多步任务的费用散落在很多次上游调用里：主推理、工具前的规划调用、被回退的失败调用、为兜底而重复的那一次。账单只给“这个月这个模型花了多少”，给不了“这条业务线的这个任务为什么花了这些”，所以归因必须在请求发生的那一刻于网关侧落数据。

三个抓手。请求指纹把同一任务的所有子调用串成一棵有根调用树，根标识由网关在入口分配、由编排带下来。按步骤计量要求每个 span 记录自己的用量单位与步骤类型，任务总费用是这些步骤的和，而不是最外层那一次的读数。token 口径只取上游回报的用量字段、不自造估算，上游没回报时标记缺失而不是补猜值。归因要能回答三件事：按业务线怎么分布、按步骤类型怎么分布、被回退与重试的占了多少。

请求指纹与去重：三件套各管一件事

网关是链路上唯一能同时看见入参、会话与调用意图的位置，去重放这儿最省力。三件套分工不能混：内容哈希回答“问的是不是同一件事”，把可复用的读型请求收敛到同一份结果；会话维度回答“同一会话里的重复”，把误触与前端重试折叠掉；幂等键回答“同一动作的重复投递”，专治已产生外部副作用的工具调用。前两件可以命中缓存，第三件绝不能——带副作用的动作重到网关时，正确响应是“这个键我见过，回执给你”，而不是再执行一遍。

缓存边界比缓存本身重要。三类内容永不进缓存：凭据与任何可换出凭据的中间物；写操作的结果，它的价值在于唯一一次真实发生；含个人信息或敏感话题的响应体，因为模型回答可能复述出上一轮的个人信息，缓存等于多存一份且跨请求。工具目录侧同理：MCP Registry 仍是预览状态，把它当可信来源做缓存决策并不合适。

可观测与留痕：网关是那条最干净的缝

关联键要从入口一路贯穿网关、编排与工具调用，断在任何一段，一次多步任务就散成几堆互不相干的日志。属性怎么命名、日志指标追踪怎么分工，可观测性那篇已经定过调，本文只补网关特有的两点。其一，字段口径仍跟着上游协议动：MCP 在 2025-11-25 的修订里加入异步任务与扩展相关机制，A2A 规范在 2026-03-12 走到 v1.0.0，跨智能体转发时“谁是发起方、任务处于哪个阶段”由谁承载仍未定型，属性名因此只写概念、标注“仍在演进”，变更交给映射层吸收。其二，留痕与日志是两回事：留痕服务事后审计——这次外呼谁发起、参数是什么、有没有过确认门槛——要不可篡改、留存到位；日志服务排障，可以被采样与轮转。

默认不记录用户提问原文。原文可能夹着个人信息、代码与未公开材料，把它当默认日志内容等于把这些复制到每一套日志后端。取向是默认只记指纹、长度区间与结构摘要，需要原文时显式开启、单独存储、单独授权，并与留痕分开。Agent Skills 这类打包分发的能力，网关只关心一件事：技能声明的工具要在目录里可辨认、调用时归到同一来源，别让它变成一条查不到出处的外呼。

成本归因 请求指纹与按步骤计量 费用只到模型粒度，说不清贵在哪一步

小结

智能体时代没有发明网关，它只是把网关从“搬运请求的位置”推成“承担长期状态与执行权的位置”。四条新职责可以这样记：粘性决定上下文活在哪，取消与续传决定失败长什么样，工具中转决定谁真的能出手，指纹与归因决定事后能不能说清发生了什么——它们都不属于某一次调用的局部逻辑，只能落在同时看得见入参、会话与出口的那一层。

落地顺序建议倒着来：先把关联键与留痕做扎实，否则后面每一步都在盲改；再收工具出口，把绕得过去的路径逐条封掉；然后才谈粘性策略与配额维度。仍在演进的协议口径宜由网关的映射层吸收，不要漏进业务代码，否则上游规范动一次，全链路就得跟着改一次。
