Go 语言大模型应用开发

大模型在工程侧的交付形态很朴素：一个 HTTP 接口，加上一条 SSE（Server-Sent Events）流。本文不谈提示词，只谈把这条链路做成可靠的在线服务时，Go 已经提供了什么、还需要你自己补什么。

1. Go 在大模型应用里的位置

上游以 HTTP 与 SSE 暴露能力，落到服务侧是一道 IO 密集题：转发、聚合、限流、取消、观测。Go 的适配很直接——单个静态二进制部署面小，标准库把 HTTP 客户端、并发调度与超时取消做得顺手，goroutine 廉价。所以它适合编排（orchestration）、网关、工具执行与流式转发，不适合训练与推理内核：算子、GPU 调度与自动求导的母语是 C++ 与 Python。一句话摆正期望：Go 负责把模型调用做成稳定、可运维、可回滚的服务，不负责让模型变聪明。

2. HTTP 客户端的正确姿势

net/http 的默认客户端有个坑：http.DefaultClient 的 Timeout 是 0，即没有整体超时，上游挂住时 goroutine 会一直阻塞在读响应上。默认 Transport 的连接池参数也在版本之间变动过（每主机空闲连接早年是 2 条量级，后来上调到 100 条），把容量寄托在默认值上，等于让并发能力跟着 Go 版本漂移。

这段配置解决三件事。一是两种超时口径：ResponseHeaderTimeout 只约束收到响应头之前，Timeout 覆盖含 body 读满的整个生命周期。二是客户端必须复用：每次新建等于新建一套 Transport 与连接池，TCP 与 TLS 反复握手，文件描述符与 TIME_WAIT 持续上涨，表现为吞吐上不去而 CPU 不忙。三是 MaxIdleConnsPerHost 要与稳态并发同量级，留少了连接建完即关，留多了抬高 fd 与内存。

代价是带 Timeout 的客户端会掐断长流式响应，因为 SSE 的 body 要读几分钟。实践里通常备两个客户端：非流式用带整体超时的，流式克隆一份不设 Timeout 的 Transport，截止时间交给 context 逐请求控制。

3. SSE 与流式消费

最典型的错误写法是 io.ReadAll(resp.Body)：它把“逐字吐出来”退化成“憋完再给”，首字延迟（time to first token）从几百毫秒变成整段生成时间，也丢掉取消能力。正确做法是把 body 当流读，按事件边界切分：一个事件以空行结束，事件内多行 data: 先拼接再解析 JSON。

它解决粘包与半包：一次 Read 可能拿到半个事件也可能拿到三个，把边界交给空行而不是字节数才有确定性。代价是 bufio.Scanner 按行切，上游用裸回车作行尾时会把整段当一行；缓冲上限写死意味着超大事件要么截断要么报错，策略必须显式决定；拼好的 data 仍可能是非法 JSON。

服务端转发时 http.ResponseWriter 自带缓冲，不调 Flush 等于把流式改成整段返回，所以 http.Flusher 是必需的：

代价是每事件一次系统调用、小包变多，且响应头写出后状态码已定，之后出错不能再改成 5xx，只能把错误编码成一个事件。

最常见的事故是中间层把流吃掉：反向代理默认开启响应缓冲、攒满一块才发；网关按整段处理、等上游结束才转发；负载均衡或 CDN 的空闲超时切断长时间无字节流动的长连接；中间层改写 Content-Type。对策是显式声明不缓冲、必要时下发注释行作心跳。最后一条纪律：客户端提前断开时服务端必须停止消耗上游——context 随连接关闭被取消，转发循环要监听它并立即关闭上游响应体，否则 goroutine 继续读、继续按 token 计费，而下游已经没人接收。

4. context 是一等公民

Go 里取消与超时只有一条通路：context。传给 http.NewRequestWithContext 后，net/http 在建连、等响应头、读 body 的每一步都会检查它，取消即关闭底层连接，这正是第 3 节那条纪律的落点；不带 context 的调用都不可取消。预算靠派生表达：入口设一次整体死线，每段下游从剩余时间里切自己的小死线。

收益是整体预算保证服务不被单个请求无限占用，分段预算让重试次数受剩余时间约束而不是凭经验循环，defer cancel() 把 context 泄漏变成静态可查问题。代价是取消语义分层了：不追因时客户端断开、整体超时、分段超时在日志里都长成同一个 context.Canceled，要靠 context.Cause（Go 1.21 起）回溯；后台任务要活过请求得用 context.WithoutCancel 解耦，而不是用 context.Background() 传到底。

另一条常被违反的约定是 context 不传业务参数：值字段只放请求级元数据（trace id、链路标识），UserID、租户配置、提示词一律走显式结构体，否则依赖关系从函数签名里消失。

5. 并发与限流

“每个请求起一个 goroutine 直接打上游”在本地压测很爽，上线是三重事故：上游配额被打穿甚至触发限流与封禁；己方连接与文件描述符耗尽，殃及同进程其他接口；慢上游把并发放大成排队雪崩。goroutine 廉价只意味着创建便宜，不意味着上游容量免费。固定并发度用 golang.org/x/sync 的 errgroup 最直接：

它解决并发有上界、失败能扩散取消：SetLimit 之后 g.Go 在名额满时阻塞，本身就是信号量形态。代价是错误语义为第一个错误赢，可容忍的失败要分类后再决定返回错误还是 nil；自 Go 1.22 起循环变量按迭代新建，旧代码里为闭包捕获写的 q := q 已是冗余。

按租户分片限流的落点在网关入口而不是调用处：以租户标识为键取对应令牌桶（golang.org/x/time/rate 这类标准扩展实现即可），全局桶保底、租户桶防越权抢占；代价是桶所在的映射表本身是无界风险，键基数不可控时必须自带淘汰与上限。背压（backpressure）靠有界 channel 而非无限缓冲：

6. 结构化数据与容错解析

encoding/json 处理模型输出有三个现实问题。超长字符串：几万字的正文解进结构体是合法的，但内存尖峰与日志打印会放大它，必须有长度上限并明确超限是截断还是报错。未知字段策略：默认忽略未知字段让上游加字段不打挂服务，这是想要的行为，但契约测试里要反过来用严格模式（例如 DisallowUnknownFields）暴露结构变化。数字精度：解进 interface{} 时所有数字都是 float64，token 计数与金额这类大整数会静默丢精度，需要 UseNumber() 或显式解进 int64。顺序也很重要：先拿原始字节，再做容错解析。

原始字节先行的收益是解析失败时还能落盘留样、还能二次容错解析。这段分类解决重试决策：可重试、致命、不可解析三类分流，避免对 4xx 做指数退避；代价是这张表要长期维护，上游状态码语义变了而表不更新，可重试错误会被静默归成致命错误。重试次数与超时上限本文一律按团队约定示例处理。

schema 校验与业务校验要分开：前者管字段存在与类型，后者管语义——结束原因是否异常、工具参数是否符合该工具签名、长度是否在业务允许范围内。混写之后的错误无法分级。

7. 配置与密钥

配置分三层：编译期默认值、运行环境（环境变量或凭据服务）、实例级覆盖；每层只写差异、读取顺序固定，出问题时才答得上“这个值从哪来的”。密钥有三条不能越过的线：不进配置文件明文，因为配置会被提交进仓库、打进镜像；不进日志，因为日志会被采集器整份外发；不进缓存键，因为键会出现在指标标签、调试面板与键空间转储里。落点是从运行环境或凭据服务读取，按最小权限只授予进程读取它自己那一个密钥，轮转不改代码也不换镜像。

收益是敏感物与代码解耦，镜像能在环境之间原样搬。代价是启动期必须校验：缺必需项就拒绝启动，而不是撑到第一个请求才失败；模板外置后发布版本与提示词版本可能不一致，两者都要带版本标识。提示词当配置管理是对的——需要灰度、回滚与审计，但含真实用户数据或个人信息的样例不进镜像也不进仓库。

8. 结构化日志与追踪

Go 1.21 起标准库有 log/slog，结构化日志不再是要不要引第三方库的问题。字段规范三条：一是低基数，日志与指标标签里别放用户 ID 明文、URL、错误全文，否则序列数量失控；二是 trace id 贯穿，从入口生成或沿用上游传播头；三是不打印用户提问原文与个人信息，只记长度、类别或哈希，不够用就补埋点而不是补原文。

OpenTelemetry 在 Go 侧有两个接入位置：客户端插桩是在 Transport 层包一次，出站调用自动产生 span（追踪里的一段计时单元），改动小、覆盖全；业务埋点手写在你关心分布的边界上——排队等待、建连、等响应头、首字到达、生成结束、解析、工具执行。指标至少采这几组：每阶段耗时的分布而非均值、输入与输出 token 计数、取消率、重试次数与重试后成功率、上游限流与 5xx 比例；取消率最容易被忽略，它既是体验信号也是成本信号。

分工记一句话：日志记事件、追踪记因果。把因果写进日志文本等于放弃结构化查询，把事件塞进 span 等于给追踪加了成本。

9. 测试策略

模型不可用不代表服务不可测。用 net/http/httptest 起一个假上游，四类场景各覆盖一例：流式（分片与事件边界切分）、超时（处理器故意慢过预算）、断连（提前关连接或客户端取消）、错误码（限流与 5xx 是否走到正确的分类）。

这段测试解决“取消安全”能否被机器验证：只在文档里写要监听 ctx.Done() 没有约束力，断言取消后调用确实返回、goroutine 数回落、假上游的读取确实停止，纪律才是活的；代价是这类用例对时序敏感，断言要落在“取消是否发生”而不是“多久发生”。

契约测试的思路是把真实响应的原始字节留样成固定输入，喂给解析层；单测边界也定在这里——CI 不碰真实模型，否则失败原因会混进上游可用性、配额与网络抖动。

10. 部署形态

一个静态二进制加一层容器镜像，启动路径极短，这是 Go 在这个环节兑现的优势。优雅关闭按顺序做：先让就绪检查转为失败、把流量摘掉，再停止接收新连接，最后给在途请求一个排空窗口。流式请求的排空必须有上限（本文按团队约定示例处理），否则一个正在生成的长回答会拖住发布与回滚。

健康检查要区分两件事：“进程活着”适合做存活探针，“能连上上游”适合做就绪探针；把后者当存活探针，上游一抖动整个集群就被重启，外部故障放大成内部雪崩。

多副本下还有一道容易被忽略的算术：单副本的并发档位乘以副本数就是上游看到的总并发，扩副本而不同步调低配置，配额必然被打穿。内存与 GC 停顿方面，Go 有 GOMEMLIMIT、GOGC 这类环境变量手段，可用于容器内存限额场景，但取值与效果强依赖负载形态，必须实测后再定，本文不给数字。

11. 与生态框架的关系

框架解决的是编排抽象：节点、图、状态、工具注册有了现成模型，业务代码会短很多。Go 侧的 Eino 是本批另外两篇的主题，选型与用法指向它们；Python 侧的 LangChain 与 LangGraph 生态更庞大，本文只当对照，不展开。要强调的是，上面十节的工程地基在任何框架之下都仍是你自己的责任：框架不会替你决定 MaxIdleConnsPerHost，也不会替你挡住把密钥写进日志的那一行。

12. 常见坑清单

这份清单的价值不在“知道”，而在每一条都能被一个测试或一条指标拦住：io.ReadAll 由首字延迟暴露，不关闭 body 由连接复用率暴露，无界并发由上游限流比例暴露。代价是这些拦截手段要长期维护，事故复发往往是因为对应断言被删了。

小结

Go 在大模型应用里是可靠的传输与编排层，不是模型本身，看清这条边界能省掉一半选型争论。剩下的都是工程基本功：显式的超时与连接池、按事件边界消费的流、贯穿全链路的 context、有上界的并发与背压、先字节后结构的容错解析、不进配置不进日志不进缓存键的密钥、低基数且脱敏的可观测性、不依赖真实模型的假上游，以及能摘流量能排空的部署形态。这些不需要新框架，也不能靠默认值凑过去；建议按第 13 节的表逐行自查，先堵住“忘设超时”与“密钥进日志”这两条。
