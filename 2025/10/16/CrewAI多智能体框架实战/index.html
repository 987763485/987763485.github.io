CrewAI 多智能体框架实战

本文属于《Agent 智能体开发》第 13/55 篇
上一篇系列目录下一篇

本文要回答一个具体问题：一项工作天然需要“好几种人”配合时，能不能别再用一堆手写的 for 循环与 if 分支去调度大模型，而用“角色 + 任务 + 流程”这套显式抽象把它组织起来。CrewAI 属于这一类框架。本文是项目实战与边界评估，不是官方文档的复述：代码均为笔者自写的示意骨架，字段名只为表达思路。

它想解决什么问题

朴素写法是一段循环：模型整理一次信息，返回文本塞进第二个提示词，再塞进第三个，中间靠字符串拼接与几个布尔判断决定要不要重来。三步内可用，到第五步集中暴露三类问题：提示词散落各处无法单独评审；某一步失败下一步照样执行；上下文越滚越长，没人说得清这一步需要前面哪些信息。

这一类框架的主张是把“多角色协作”显式建模，把工作拆成五类可声明对象：角色（role，承担什么职责）、目标（goal，要达成什么）、背景（backstory，以什么专业视角工作）、任务（task，这一次交付什么）、流程（process，多个任务按什么次序或什么管理关系推进）。声明化之后，代码里剩下的是编排而不是循环：你描述谁在什么约束下产出什么，提示词组装、调用、交接与重试交给框架补全。

定位一句话：它是低摩擦起步的编排层，不是通用工作流引擎（workflow engine）。它把“角色协作”这种思维模型做成一个足够好用的默认结构，代价是把执行语义的控制权交给了抽象。

角色与任务映射的正确姿势

按产出物定义角色优于按人格定义角色。“你是一位资深分析师，热爱数据、表达犀利”约束的是文风；“你的唯一产出是一份口径可比的竞品价格区间表，缺数据必须标注来源与置信度”约束的才是行为边界。角色只承担职责与标准，“这一次做什么”属于任务。

粒度上只认一条约定：一个任务只产出一个可验收的东西，判定条件要一句话说得清——是“条目数等于用户给定清单的表”，不是“分析得深入一点”。任务之间靠明确的输入输出衔接，不做整段历史往下传的默认。验收标准要写进任务定义而不是角色台词：角色长期复用，验收标准属于这一次交付。示意骨架如下（字段名自拟）：

两种流程形态的差别

两种形态里，顺序式（sequential，按给定顺序把任务一个个交接下去）适合工作本身有流水线形状的场合：取证、成稿、校对，次序就是业务的天然次序。它的失败形态很集中——第一步跑偏会污染后面全部，因为后序角色只拿到上游产出、默认它可信，会把错误口径一路加工成措辞专业、结构完整、结论错误的东西。对策不是加一个复查角色，而是写死第一步的验收标准，并在每个任务结束后做一次形状检查。

分级式（hierarchical，设一个协调角色（coordinator）负责分派与汇总，其余角色只管自己的任务）适合边界事先说不清的场合：需求进来时不知道要拆成几步，需要有人中途决定还缺什么。代价是多出一个同样由模型做的判断点。两种典型失败是越权（协调角色自己去把活干了）与漏派（必要环节没人认领，汇总阶段凭空补一段），根因都是它的职责没被限定成“只分派、只汇总、不产出内容”。

一条心智规则：能画出流程图就用顺序式，画不出来才考虑分级式。

flowchart TD
  T1[任务一 由角色A执行] --> O1[结构化产出A]
  O1 --> T2[任务二 由角色B执行]
  T2 --> O2[结构化产出B]
  O2 --> C[协调角色 汇总]
  C --> Q{验收判定}
  Q -->|通过| DONE[完成]
  Q -->|不通过| R[重跑指定任务]
  R --> T2

验收判定这个节点必须给出布尔结果，而不是一次“请评估质量”的模型调用：前者让重跑有明确目标，后者只会让系统多绕几圈、多花一些钱。

交接与状态传递的坑

最贵的一类错误发生在交接（handoff）处——上一个角色往下传什么。把整段对话往下传最省事也最容易失控：token 消耗按任务数近似平方增长，信噪比随之塌陷，下游需要的三条结论被埋在两千字推理过程里，于是它开始引用本不该有权威的中间草稿。

把中间产出结构化是解法：上游交付的不是“一段分析”，而是给定字段的对象，下游只声明需要哪几个字段。收益有三层——体积可控且可预算；形状本身就是一种验收，缺字段当场暴露；日志可以按字段比对，而不是比对两段散文。契约形状示意（字段名自拟）：

status 与 open_questions 两个键就是这段代码的价值：它们把“上游没做完”变成显式事实，让编排层有机会拦住流程。这正是那个常见判定缺口——前一个角色没产出可验收结论却继续往下流，因为多数实现只检查有没有返回内容，不检查它是否满足验收条件。补救方式很朴素：产出离开任务前跑一次独立检查，能用规则的就别用模型；失败就停在原地并记录原因，让“停”成为一种正常终态。

工具绑定的边界

挂工具是最容易失控的一环，原则是少而正交。两个工具能力重叠——一个通用搜索加一个垂类搜索，或两个都能读文件的不同实现——模型面对“该调哪个”时出现选择歧义，表现为同一件事有时成功、有时反复试错且难以复现；候选越多，提示越长，选错概率越高，合并成一个带参数的工具比让角色自己挑更省事。

工具失败必须有硬上限。放任重试的结局是换着写法把同一个错误请求打十几遍，预算花完而结论仍缺。所以轮次上限与预算要写进每个任务的声明、按任务性质分别给，而不是全局一个默认值；失败后还要有显式出路——标记为 blocked，把缺口写进 open_questions。

敏感动作要有人工确认门槛。凡有外部副作用的动作（写数据、发消息、下单、改配置）都不该由角色自己决定是否执行：在编排层把它们登记为需要人工确认的一类，在产出与执行之间插入一次人的批准，执行侧再核验一次。这与提示注入（prompt injection）的防护是同一件事的两端，判定与常见绕过手法在同期那篇注入防护的文章里有完整讨论。多智能体放大的是未经确认的副作用链条。

可观测与可调试

最难的不是让它跑起来，而是跑坏之后回答“是哪一步坏的”：端到端失败往往只在最后一段输出里露出痕迹，真正的错因在三轮之前。三条约定。其一，每个角色、每个任务都有独立的产出与耗时记录，运行标识、任务名、尝试次数三者齐全，才可能把失败定位到具体一次尝试。其二，日志遵守脱敏最小必要：只记字段名、判定结果、耗时与预算，不把用户原文与工具返回的完整正文写进去。其三，把任务级检查点（checkpoint）做成可重跑的单元：给定运行标识与起点任务只重跑那一段，前提是输入只依赖已记录的产出，不依赖隐藏状态。

show 看形状，diff 看两次运行之间哪个字段变了，rerun 让修复循环只花一次任务的钱而不是整条链的钱。再补一层离线固定样例集回归：十来组输入与期望形状，每次改提示词或换流程形态都跑一遍并比对通过比例。没有这一层，任何调优都只是把生产事故提前到自己身上。

什么时候它会不合适

这套抽象买到的是开发速度，付出的是执行语义的确定性。四类场合本文认为它不合适。任务本身是确定流程：步骤、分支条件与失败处理都能提前写清时，普通编排代码更好维护——可测试、可静态检查、失败栈读得懂；把它改写成给模型看的自然语言，等于把已解决的路径换成每次都要重新赌一遍的路径。需要严格事务语义：一致性、补偿、隔离级别、恰好一次投递不会因为有个协调角色而自动成立，模型的判断不能充当提交点。角色增多使成本与不确定性叠乘：输出方差都参与最终结果，角色从三个加到八个，出错概率与预算都是相乘而不是相加。需要可证明的终止与幂等：循环次数取决于模型自认为“还需要再看一次”时，既无法给出终止性证明，也无法保证重跑同一输入落到同一状态。

与同生态其他框架的分工

同一批问题还有几条路线，本文只谈抽象取舍、不比优劣。偏底层可控的图与状态机式编排把控制权交回给你，代价是协作语义要自己搭；偏单智能体循环的运行时让一个执行体带着工具反复思考与行动，适合路径深度不可预知的探索，代价是过程难以切片验收；自己写循环在两者都不匹配、或者规模只有一两步时最省钱也最清楚。这套抽象的位置在中间：它假设工作可以拆成若干段、每段有明确的职责归属，且这种拆法比状态转移更贴近你对业务的描述——假设成立时省下大量样板，不成立时它就是你要绕开的那层。

落地路径建议

建议顺序是：从单角色加单任务起步；增加第二个角色之前，先证明第一个任务的验收标准真的有效——它能判出通过与否，且失败时你知道自己在改什么；证明成立，再考虑流程形态。跳过这一步，第二个角色只是把不确定性乘以二。分阶段路线（阶段名自拟）：

版本与迁移的现实提醒

本文写作时（2025 年 10 月 16 日），这一类编排框架普遍处于快速变动期，接口文档与实现之间经常不一致，示例能跑与接口稳定是两件事。同期另一个主流编排框架的 1.0 版尚未正式发布，官方已预告即将发布，本文的判断基于当时的 0.x 生态，不对 1.0 的接口做任何假定。所以要害是把框架调用收敛到自己的一层接口后面：角色、任务、验收、交接这些概念用本工程的数据结构表达，框架只在边界处被使用；接口改名、参数调整或整体更换时，改动集中在适配层，评测集还能原样复用。

常见反模式清单

  • 给角色写一大段戏剧化人格：文风稳了，结论没稳。
  • 角色之间靠自然语言传大对象：形状检查被推给了人眼。
  • 没有终态判定：只有跑完，没有成功、部分完成、阻塞三种出口。
  • 任务没有验收标准：最后一段措辞承担了质量判定。
  • 工具无上限：轮次与预算不设限，重试变成烧钱的主要通道。
  • 用更多角色解决质量问题：分工变了，判据没变。
  • 把演示当生产形态：演示里没有失败分支、脱敏约束与回归样例。

小结

这套抽象把“多角色协作”变成可声明、可评审的对象，省掉一批脆弱的字符串拼接与布尔判断；代价是执行语义的确定性，以及方差与成本的叠乘。四件事值得记住：按产出物而不是人格定义角色；一个任务只交付一个可验收的东西；交接必须结构化并带上显式的完成或阻塞状态；工具与重试要有轮次和预算上限、敏感动作要有人确认。先建评测集再谈协作，先证明第一个任务的验收标准有效再加第二个角色。当分支能提前写清、或者需要事务语义与可证明的终止时，请退回工作流——那不是降级，而是换了更合适的工具。
