Rust 在基础设施中的应用

本文属于《Rust 学习路线》第 66/68 篇
上一篇系列目录下一篇

本文只讨论一个窄问题：哪些基础设施类组件值得用 Rust，哪些不值得。读完你会拿到一组可抄的判定问题、一条渐进迁移路径和一份上线门禁清单。文中的判断都是类型化的，不点名具体产品，也不给效果数字——把别人的收益当成自己的预算，正是这类选型最常见的错误。

基础设施类组件的共同特征

这里说的基础设施类组件，指被其他服务依赖的那一层：网关、代理、存储引擎、采集器、内部工具链。它们与业务模块的区别不在代码量，而在五个特征上。

  • 生命周期长：需求按季度重写，组件却要以年为单位运行，还要跨越内核与 TLS 库版本升级，大部分时间在无人照料中度过。
  • 被大量上层依赖：依赖者的数量决定变更的摩擦——你改不动，别人就绕着你写规避逻辑，而绕行代码最终会长成真正的架构。
  • 故障放大：它处在调用链的必经之路上，一次错误会让上游超时、重试、连接堆积，把局部问题放大成雪崩。
  • 性能可预测性要求高：业务关心平均，这层关心尾部。停顿、内存缓涨、锁竞争尖峰都会变成上层的抖动；可预测指”占用有上限、压力下行为不突变”，不是”跑分更高”。
  • 接口窄而稳定：对外能力应当少量、语义明确、多年不变；窄接口给实现留出自由度，也意味着一旦定错就难以收回。

五条合起来，语言选择要回答的就不是”哪种写法让需求落地更快”，而是”哪种实现在两年无人照料之后仍然可预测、在别人手里也读得懂”。业务层可以用迭代频率补偿运行期的不确定性，基础设施层不行——它得把不确定性在编译期和上线前消耗掉。Rust 的强项正对得上这条轴：生命周期、所有权、错误路径都被显式化；弱项也在同一条轴：显式化本身就是成本。

适合用 Rust 的四类组件

网关与代理

网关和代理是典型的连接生命周期复杂体：上下游各有独立的超时、重试、半关闭状态，长连接上复用多路请求。难点不是业务逻辑，而是分支多、路径交错、漏掉一处清理就缓慢泄漏。Rust 的适配点在于连接归属可以显式建模、任务生命周期受所有权链约束、关闭路径在类型层面就必须处理：它写不出正确的状态机，但让你很难忘记某个分支没返回、某个连接没释放——对要求零意外尾延迟的组件，这种”忘记不了”高于性能叙事。

坑有三个：异步运行时的阻塞纪律，一次阻塞调用混进工作线程，整条队列都会感知；取消语义，客户端中断后下游在哪里收尾、任务被 drop 时资源归谁；配置热更新与在途请求的竞争，把配置做成可变共享状态最后只能靠锁续命。反例：网关若实质是路由规则的重排、一周改三次、由非开发角色配置，瓶颈就是表达能力而非确定性，用成熟代理加插件更划算。

存储引擎与数据处理算子

第二类是存储引擎、索引结构、压缩与编码层、流式算子。共同要求是对内存的主动控制：块缓存要有确定的上限与驱逐代价。GC 型语言在这层的困难不是吞吐，而是暂停的时机与时长不完全由你决定，回收压力还常随数据量而非请求量增长。Rust 把这件事变成显式契约：缓存槽位用借用与引用计数表达，上限用 arena 或自定义分配器落实。

坑也是结构性的：自引用结构（B 树父指针、跳表层级）往往要退化成索引式实现；用 Arc<Mutex<_>> 绕开借用检查是常见妥协，代价是把并发正确性交回人肉；崩溃一致性、格式演进、校验和这些语言帮不上。反例：如果你的存储层只是关系模型的增删改查加一层映射劳动，收益撑不起成本。

可观测性代理与采集器

采集器驻留在每台机器上，与业务进程抢同一份 CPU、内存和 fd 配额，所以占用必须封顶：不是”平均很低”，而是最坏情况下也低，上游不可达时不能无界缓冲。常驻加封顶正是 Rust 的舒适区；而它要触碰的进程与系统调用、内核侧事件源这类接口，恰好也是 C 兼容层做得干净的地方，这条边界的坑，同期那篇 eBPF 的文章讲得更合适。

坑在采样与背压：缓冲一旦允许无界排队，最坏后果是把宿主机的内存吃光，让被观测的对象先倒下；为灵活而开放动态加载，会把一次解析异常变成进程级故障；fd 泄漏只在长期运行后才显形。反例：上报量级很小的场合，挂一个成熟 SDK 就够。

CLI 与内部工具

第四类是命令行工具与工具链：迁移脚本、诊断工具、发布器、代码生成器。诉求是分发一个二进制、跨平台行为一致、不依赖目标机上的运行时版本，同时迭代要快。单产物容易带版本与校验；参数与错误的类型表达让工具在两年后还说得清自己做了什么；写对了还能进 CI 当门禁。坑主要在外围：交叉编译矩阵、静态链接与系统库的取舍，以及工具数量失控——每个内部工具都是一份长期承诺。反例：脚本十分钟能解决的一次性需求，做成 crate 加测试加发布流水线，投入产出比不成立。

不适合做什么

选型不写”不适合”，就是营销而不是判断。四类场景本文的结论都是别用 Rust 重写。

一是需求每周大改的业务编排层。它的价值在表达能力与改造速度：抽象还没稳定就被迫重做，在这里把类型系统当护栏，等于每周交一次重构税。

二是需要大量胶水与动态性的脚本场景。插件热加载、动态派发这类需求，通常要靠 trait 对象、嵌入脚本语言或代码生成这层间接实现，而每层间接都是此后归你的维护面积。

三是团队里没人能读懂 unsafe 与生命周期。基础设施代码迟早碰到 FFI、自定义分配器、无锁结构或第三方 crate 里用错的 unsafe，如果出问题只能找最初那位作者，这条依赖线就把组织风险写进了关键路径。能力可以培养，但培养期不该同时是迁移期。

四是已有成熟且稳定的存量实现。重写本身不是收益：存量的可靠性来自它被运行过的那段时间，而不是它的语言。只有当存量卡在结构性问题上——资源占用封不住、契约无法表达、依赖无人维护——才有理由重写。

代价的真实构成

人才供给与上手周期排第一。会写 Rust 不等于写出能被别人接手的 Rust：对 unsafe 的评审能力、对异步取消语义的理解都不充裕，从”能编译”到”能改别人的异步代码”通常以季度计。

编译期心智成本是第二项。借用冲突、泛型边界、trait 约束不满足的报错，让”先试一下”这类探索变贵；它把成本从事故挪到了编译期，但要提前告诉需求方：这里的迭代曲线不是线性的。

生态成熟度差异是第三项。某些组件只有其他语言的成熟实现：小众协议解析、某数据系统的官方客户端、与特定平台绑定的中间层。选 Rust 就要自己维护这一层，而它从此归你。

第四项是节奏与沟通成本：排期、评审、值班响应都要重新对齐，”别人能不能帮你排查线上问题”是硬指标，它决定故障时的恢复时间。

最后是常被漏算的招聘与知识传递：这个组件三年后由谁维护？新人能不能独立定位一次内存缓涨？如果答案是”只有原作者”，运行期省下的成本会以组织成本的形式重新付出去，它就是选型的决定变量之一。

渐进迁移：绞杀者模式与”先包裹再替换”

主线只有一句：不要一次性替换，而是把风险切成可以退回的小步。这里要绞杀的往往不是功能，而是流量路径。

flowchart TD
  A[第 0 步 存量组件加指标与流量镜像] --> B[第 1 步 边缘新组件直接用新实现]
  B --> C[第 2 步 替换无状态中间件按路由切流]
  C --> D[第 3 步 双跑与影子对账]
  D --> E[第 4 步 才碰有状态的存储类组件]
  E --> F[第 5 步 老实现降级为兜底并设定下线期限]
  C -.回滚.-> A
  E -.回滚.-> C

每步都要写清退出条件与回滚方案，否则”渐进”只是”拖着”。

更值得推荐的一步，是把”重写”改成”包裹”：先用 FFI 与 C ABI 把现有 C 组件包起来，让 Rust 只承担调用编排、生命周期与错误传播，验证收益究竟是不是语言能给的。

好处是归因干净、随时可退：同一份内核实现，只换调用层。包完之后问题依旧，说明要改的是设计，不是语言。

与 Go、C 的现实分工

三者不是竞争关系，默认分工如下。

模块类型 默认语言 理由（类型化判断，不做跑分比较）
控制面、编排、管理接口 Go 生态与人力供给最好，需求变动频繁，并发模型够用
长驻数据面、连接与缓冲密集的转发 Rust 资源占用要封顶，尾延迟要可解释
与操作系统或内核最紧的接口 C 抽象层最薄，符号与调用约定最稳定
一次性脚本与临时诊断 脚本语言 用完即弃，不值得维护产物

共存期要投入的是下面三项，缺了它们，多语言只是一堆互相看不懂的东西。

上线门禁：基础设施组件要额外做的事

基础设施组件上线还要看它失败时会不会把别人一起拖下去。下面这份清单逐条签字，缺一项就不该铺开。

两点补充：能区分重启原因的组件，运维价值远高于只知道自己”重启过”的组件；资源上限不要靠读代码确认，要靠把资源打满之后的实际行为验证。

可观测性与供应链治理

指标要求比业务服务更严

常驻组件最有信息量的不是请求数，而是趋势。

最关键的是内存缓涨要能被发现：短时压测看不到它，只有长期曲线的斜率能看出来，所以趋势指标要有足够长的保留窗口和明确的告警口径。这与连接池、网络服务上的实践同源，可对照同期那篇文章。其次是脱敏与最小必要：日志与指标不能出现密钥、令牌与用户内容，缓存键也不能把它们拼进去——这层组件常站在明文与密文的交界处，最容易把敏感字段固化进长命数据结构。

依赖与供应链

依赖要比业务代码更克制，因为它的寿命比上游 crate 的维护热情更长。判断维度是四个：数量（每个依赖都是别人随时可以放弃的东西）、许可证（能否合规分发）、可维护性（上游是否还响应安全问题）、可审计性（能否静态审查、能否在不联网的环境构建）。锁文件与可复现构建是底线：没有锁定的依赖树，昨天的产物今天就重建不出来；产物还要与来源核对，出处不明的二进制不进生产。门禁自动化不在本文范围，同期那篇持续集成的文章负责这块。

决策框架与常见误区

顺序不要打乱：前三问决定值不值得，第四问决定现在做还是先培养人，后三问决定能不能开工。任何一问答不上来，就先做一次实验而不是排一次期；缺第 6 与第 7 问答案的迁移，无论技术上多合理都应推迟。

小结

本文的判断轴只有一条：基础设施组件要的是运行期可信度与可维护性，不是开发速度。Rust 在长驻、资源要封顶、状态机复杂、契约需长期稳定的活上确实对得上；在频繁重排的编排层、动态胶水、无人评审 unsafe 的场合并不合适。代价不是”编译慢一点”，而是人才、心智成本、生态缺口、协作节奏与最常被漏算的知识传递。真要迁移就走绞杀者路径：先加指标，先在边缘试，再换无状态，最后才碰有状态，能包裹就别重写。技术选型最后比拼的通常不是语言优劣，而是你能否把风险切成可以退回的小步。
