大模型监控指标体系

模型应用上线后最难回答的问题不是“服务活着没有”，而是“它今天答得还行不行、贵不贵、有没有漏东西出去”。本文给出大模型应用的四层监控指标体系：质量、性能、成本、安全，逐层讲清定义口径、采集位置、误报来源与告警形态，并给出命名规范、链路追踪与日志的分工、看板与灰度验收的做法。全文有一个前提：监控体系自身也是数据处理者，最小必要采集与脱敏优先不是附加要求，而是设计约束。

从“请求返回 200”到“回答可靠”

传统应用性能监控（Application Performance Monitoring，APM）建立在四个黄金信号（Four Golden Signals）之上：延迟（Latency）、流量（Traffic）、错误（Errors）、饱和度（Saturation）。其隐含假设是：一次调用二值可判，成败由状态码、异常或超时决定；资源消耗与请求量近似线性；错误会留下堆栈。这四条假设在大模型应用里同时松动。

答案的正确性是统计量而不是二值。一次请求可以完整走完流程、返回 200、时延优秀、毫无异常，同时给出一个编造的结论；网关看到的成功与用户感受到的成功之间隔着一次语义判断，而语义判断无法在请求路径上零成本完成，所以质量信号天生依赖抽样与评分。成本也不由 CPU 主导：同一台实例上，短上下文与长上下文请求的耗时与消耗可以差出一个量级，输入长度、缓存命中、工具与检索引入的额外轮次、失败重试都是钱，请求数与饱和度替代不了 token 口径。风险更不进错误率：注入尝试、越权工具调用、外泄拦截在业务语义上是“拦住了所以请求成功”，在监控语义上却必须单独计数，混进 200 就等于没发生。

结论是：质量、性能、成本、安全四层必须同时存在，缺一层就有一类问题不可见；而是否采集用户原文，在四层里都以最小必要为原则。

层 回答什么问题 主要采集位置
质量 用户拿到的答案是否可用、是否可信 抽检与评审流水线、反馈埋点、输出侧校验器、引用一致性检查
性能 用户等了多久、时间花在哪一段 网关埋点、编排层阶段计时、引擎内部计数、客户端首帧观测
成本 这件事值不值这个消耗、消耗归给谁 网关用量字段、引擎 token 计数、轮次记录、缓存层日志
安全 有没有被试图带偏、有没有东西漏出去 输入侧策略检查点、工具权限检查点、输出侧校验、限流组件

后文所有指标都在这三条底线内解释。其一，采集范围按字段白名单声明，未列入的一律不落；需要留存对话内容支撑抽检与排查时，必须同时满足五条：写入独立的对话内容域并与指标存储隔离、只留白名单字段、按角色做访问控制、写清留存期限与到期删除任务、脱敏优先（能只留长度、语言、类别标识就不要留文本）。用户提问原文、手机号、精确地理位置、身份证件号与账号信息都不构成“方便排查”的理由，也不许进任何指标标签。其二，堆快照、密钥、模型权重、用户数据不得写入任何外部服务、日志行或缓存键；缓存键只能由显式设计过的标识符与版本拼成，不能由内容摘要单独决定，否则键本身就成了可反查的数据出口。其三，所有阈值都是团队约定示例；本文不给任何 SLO 数值、告警数量、错误率百分比与时延毫秒数，只说明阈值该由谁依据什么来定。

质量层指标：把“答得不好”变成可观测的信号

离线评测的指标体系与题库构建在往期《大模型应用评估》里已经讲透，本文只谈线上监控这一侧，同一条指标的定义口径以评估篇为准。质量层最容易犯的错误是试图用一个数字回答“答得好不好”，可行做法是把它拆成一组信号，并对每个信号诚实标注证据强度：是结论，还是线索。

抽检评分：按类别分层抽样

均匀随机抽样在真实流量下几乎必然失真：类别分布极不均，短问答型占大头，而真正高风险的场景——涉及资金操作、健康建议、跨部门权限查询——在随机样本里只剩几条，评分被高频低危请求稀释。正确做法先建抽样框，按“功能场景 × 风险等级 × 输出长度分桶”切格子，每格设最小样本量与抽样比例（皆为团队约定示例），格内再随机；输出为每格的评分通过率与按当期流量占比加权后的总分，加权必须显式声明，否则分数会随流量结构自己漂移，看起来像模型退化。抽检评分是本层少数可当结论使用的指标，但结论只覆盖样本足够的格子。误报来源四个：抽样框过期，新功能没有格子而长期落进“其他”桶；重试请求被当新样本重复计入；同一会话多轮被当作彼此独立样本；各格样本量差异过大，加权后被高样本量格压制。

拒答率拆成两条方向相反的指标

把“模型拒绝回答”统计成一个比率是最常见的坑，因为两类处置方向完全相反。一条是“不应拒却拒”（过拒，False Refusal 一类），直接伤可用性：用户问了一件正常的事，模型因措辞触发保守倾向而拒答。另一条是“应拒未拒”（漏放），属安全层，本文只保留计数口径，发现如何登记与定级归同期《对齐评估与红队测试》。过拒率在输出侧策略检查点加编排层兜底话术识别处采集：先按类别维护一组“这算拒答”的判定，再按场景分别出曲线。误报包括把“我无法确定，建议核实”这类合规的谨慎表达误判为拒答、把检索无结果导致的“没有依据可回答”计入主观拒答、模板化回答被正则批量命中；判定本身要按类抽样复核，口径版本作为标签带着走。

幻觉线索：四类可观测代理信号

幻觉没有免费的线上真值，能观测到的是线索；命中线索不等于答案错，未命中也不等于对。一是引用缺失：必须给来源的场景里输出没有可解析的来源标记，误报主要来自解析层——标记格式换一版，正则不认，整批被误判为缺失，看起来像模型突然不引用了。二是引用与原文不一致：引用的段落确实存在，但里面找不到支撑该说法的内容，误报来自片段被截断、引用编号错位、合理的跨段归纳被当成编造。三是工具返回为空却给出确定答案：接口返回空或明确失败，答案却给出肯定结论且无不确定性表述，误报来自答案确实取自模型参数知识这一合法情形——它可能对，但无法证明对，所以仍是要抽检的线索。四是答案中出现具体数字而上下文没有可追溯来源，数字最易误导用户故单独计数，误报来自系统提示中确含常量、格式要求里的示例数字与日期版本号。这四条不进质量总分，用途是驱动抽样：命中任一线索的样本自动进入高优先抽样框。

用户负反馈率与修正轮次比例

可点击负反馈（thumbs down 一类）回收率极低且分布偏斜，是线索不是结论：绝对值不能与抽检评分比大小，只看趋势与结构。误报很具体——按钮在流式渲染未完成时不可点，长答案被系统性少报；前端埋点改版后漏报。客户端采集边界与埋点治理归往期《前端埋点治理》，本文不重讲采集合规基础。修正轮次比例统计同一会话中用户拿到答案后立刻发起否定式、重问式或补充式追问的占比，它是纯代理信号，受语言习惯与业务复杂度影响极大，只适合在版本对照时看相对变化，不适合设绝对阈值告警。

质量指标怎么采出来：离线试验与线上抽检的分工

离线评测试验负责发布前准入：样本可复现、版本可横向比较、失败可重跑，代价是分布人为、题目已知。线上抽检负责对真实分布做稀疏的高成本语义判断，代价是没有真值、样本量永远不够。分工写成一句可执行的规则：离线回答“这个版本有没有资格上”，线上回答“上了之后有没有变坏、坏在哪个格子”；质量波动先用线上抽检定位格子，再用离线样本复现。

自动打分是筛子，不是结论

用模型给模型打分（LLM as a Judge）的偏差是结构性的：偏好更长更工整的答案，即使信息量没变；偏好与自己表达风格相近的文本，从而系统性偏爱某个模型版本；分数随评审提示词措辞漂移；对格式极其敏感，对事实极其迟钝。所以它的职责是把可疑样本捞出来排序，不是给质量下结论。配套三条硬做法：每个评分批次固定抽取一定比例做人工复核，记录“一致／不一致／误判原因”，只用于校准与降级判定，不直接覆盖线上分数；当某批次人工一致率劣化到团队约定示例阈值之外，这批自动分数降级为“仅供排序，不进看板”；评审器版本、评审提示词版本、评分标定文件版本全部与样本绑定，评审器一升级就在曲线上打点，否则分数跳变会被读成模型跳变。一条评分样本若缺以下标签就进“不可比”池，不许出现在趋势图里：模型版本、提示词版本、检索配置版本、抽样框标识、评审器版本、人工复核状态；这套标签同时也是灰度对照与回滚判定的依据。

性能层指标：把一次生成拆到起止点

首 token 时延（Time To First Token，TTFT）的口径：起点取网关完成请求体解析、进入编排之刻，终点取第一个非空内容增量由网关写出之刻。三处最常被含糊过去：起点若取客户端发出请求，就把公网与本地队列算了进来；终点若取引擎产出首 token，就漏掉引擎到网关的返回路径；终点若取客户端看到第一个字符，又混进浏览器渲染。所以同一条 TTFT 至少并存两个计数——引擎侧首 token 与网关侧首字节，二者之差是有意义的量而不是误差。每 token 时延（Time Per Output Token，TPOT）取相邻两个输出 token 之间的间隔，工程上常用生成总耗时减 TTFT、再除以输出 token 数减一来近似；两件事必须写进定义：末尾停止序列的判定耗时算不算、最后一次 flush 与连接关闭算不算，算与不算都会让生成阶段耗时与引擎内部数字对不上。

总耗时是端到端口径，从网关收到请求到流正常结束，含用量帧与连接关闭，它不等于 TTFT 加 TPOT 乘 token 数，因为还有非生成阶段。排队等待与生成时间必须拆开：排队含引擎批次队列等待与并发满时的外部排队，生成拆为预填充（Prefill，读入上下文）与解码（Decode，逐个产出 token）。流式连接中断率与重连率要显式声明分子分母口径：按请求算还是按连接算，一次请求重连三次算几个事件。中断与取消是两件事：取消（Cancellation）是客户端主动断开或用户点了停止，不是失败但真实消耗算力，其上升往往是 TTFT 变长或前端超时过短的先兆，属早期信号。长尾请求占比统计超出约定分位边界的请求比例，边界值由团队约定示例给出。

为什么看分位数而不是均值：输出长度分布重尾，少数超长请求能拉高均值，而均值对应的“平均用户”并不存在，分位数回答的是最差那一档在哪里。为什么 p99 在低流量下不稳：窗口里只有百来个样本时，p99 事实上就是排序后第一个最大值，一次抖动就整点跳变；做法是按窗口样本量决定上报哪一档，样本不足时退到 p95 与窗口最大值，并把样本量作为伴生指标一起看。

指标 起止边界 标签维度 常见误算

采集位置与“两端对不上怎么办”

网关计数与引擎计数最本质的差别是排队算在哪一侧：引擎看不到它在被调度之前已经在网关或队列里等过，网关看不到引擎内部批次队列，两条曲线相加才是用户等的总时间。客户端计数要单独留一路，它包含网关测不到的本地队列、公网、代理与渲染，但它是线索级数据，不能用来做服务侧达标判定，前端采集边界归往期《前端埋点治理》。

时钟与单位是隐蔽重灾区：时延一律用毫秒，时长用单调时钟差值计算，绝对时间戳用墙钟并显式标注单位与时区；跨实例做差时时钟偏移会直接污染分位数，跨机对齐交给链路追踪的相对偏移估计，不许在原始时间戳上硬减。两端对不上时的正确动作是用同一 trace 标识把两侧观测串起来，看差值分布随哪个维度变化，定位差值主要来自排队、网络还是网关自身开销；错误动作是两侧取平均，或“以某侧为准再乘系数”。

成本层指标：归因、方向性与分母

降本的具体动作归同期《大模型成本优化实践》，本文只谈成本该被度量成什么样子，且全文不出现任何金额。

token 消耗必须能归因，归因键是租户、功能、场景三类，来源只能是认证结果与请求上下文里的可信字段，绝不能从模型输出或用户输入推断——后者会让归因被内容本身改写；归因缺失的请求单独计数，其占比上升说明接入层在丢标签，而不是成本在涨。输入与输出必须分开统计：两个方向的单位成本差别很大，输入侧还因缓存读写而不同价，相加成一个“总 token”就再也看不出成本是被冗长上下文推高还是被长回答推高。缓存命中占比要成组看而不是看单个数，至少包含前缀缓存命中率、命中带来的输入 token 减少量、缓存写入所占输入比例；只看命中率会得出越高越省的错误结论，因为缓存本身有写入与占用成本，也可能因键设计不当反复失效，而缓存键只由显式设计的标识符与版本拼成，不写入任何内容或用户数据。

工具与检索引入的额外轮次单独成指标：多轮代理式流程把一次用户请求放大成多次模型调用，指标形态是每任务的模型调用轮次分布，长尾轮次往往集中在一两个工具的失败重试上。失败与重试造成的消耗单独归集：网络重试、超时重试、校验不通过后的重新生成是纯粹的可回收浪费，混进正常成本就掩盖真实趋势。单位成本的分母必须是“成功且有质量的任务”，常用口径是每成功任务、每工单；分母只用请求数，就能靠让模型早点停止把单位成本做小，折中是分母取抽检与线上校验都通过的任务数，并与质量分放在同一张图上看。最后一句提醒：token 数不是成本，两者之间需要一张带版本与生效时间的换算表。

安全层指标：只计数，不搬运内容

安全层是脱敏约束最硬的一层，因为它天然贴着攻击面。本层纪律是：指标里只出现类别、位置、版本与次数，绝不出现载荷，本文也不给任何注入文本样例，示例一律以类别名代替。

注入尝试与拦截计数按“检出机制 × 拦截位置”二维分类，例如指令覆盖类、角色伪装类、工具参数诱导类、格式滥用类，拦截位置区分输入侧策略检查点、编排层约束、输出侧校验；每条计数只带类别、位置、检测器版本、租户类型四个维度，不带原文，也不带长度以外的内容特征。检测器版本必须带，否则升级检测器会让曲线整体跳变，被误读成攻击变多。越权工具调用尝试在工具权限检查点计数，分子是被策略拒绝的调用数，分母是模型发起的调用总数，混在一起会掩盖真问题：分母涨是模型变活跃，分子涨才是权限风险。敏感信息外泄拦截由输出侧检查器计数，类别只到“疑似个人号码／疑似证件或账号／疑似密钥形态／疑似内部标识”这一粒度，记录命中位置与字段名，不记录命中片段；命中样本若需留存复核，独立域存储、字段白名单、访问控制、留存期限四条一起生效，默认脱敏优先，而顺手把片段写进日志行以方便排查是本层最常见的破窗。

输出侧校验失败率统计结构校验（字段齐全、枚举合法、引用结构可解析）的不通过占比，误报主要来自校验器改版而非模型退化，所以它必须与校验器版本标签同时出现。被限流与配额耗尽的次数按租户与原因分别计数，原因至少区分速率闸门、token 预算闸门、并发容量拒绝，三者处置完全不同。这些计数要进告警又不造成噪声，靠三条：对安全类计数用突变检测而非绝对值阈值，因为低频事件的绝对值天然抖；聚合窗口拉长，抑制规则按“同一租户同一类别同一窗口只发一次”写；单条高危事件不走指标通道，走人工登记与分级流程，怎么登记、怎么定级归同期《对齐评估与红队测试》。

指标分层与命名规范

低基数原则：标签集合的笛卡尔积决定序列总量，任何高基数值一旦进标签就再也拿不掉，因此模型输入、文档 ID、用户 ID、会话 ID、请求 ID 一律禁止作为指标标签，它们属于 trace 与日志的检索字段而不属于聚合维度；租户标识只在租户数量本身有界时可用，且用不可反查的内部标识而非手机号或名称。新增标签前先答三问：这个维度取值上界是多少、有没有不加它就定位不了的历史故障、能不能改放到 trace 属性里。

单位与命名约定：时间一律毫秒或一律秒，选定后全局不换；token 数与字节数绝不混用同一个名字；单位写进指标名后缀。版本维度必须互相对上——模型版本、提示词版本、检索配置版本要能在同一张图上作为标签出现，否则“哪个版本变差了”无法回答。本文推荐的注册表形态如下。

最省事的版本对齐做法是由编排层统一装配一个版本包标识，模型、提示词、检索配置各自的版本作为它的字段，任何一处单独热更新都必须产生新的包标识。

Trace 与日志的分工

指标回答“这类请求整体怎么样”，trace 回答“这一次请求的时间花在哪一段”，日志回答“这一步当时为什么这么决定”，三者不能互相替代。

flowchart TD
  A[客户端请求] --> B[网关埋点：TTFT、总耗时、状态]
  B --> C[编排层埋点：阶段计时与轮次]
  C --> D[检索埋点：召回与片段数]
  C --> E[工具埋点：调用与返回状态]
  E --> F[模型引擎埋点：排队、预填充、解码]
  D --> F
  F --> G[指标：计数器与直方图]
  F --> H[链路：span 与阶段耗时]
  F --> I[日志：决策点记录]
  G --> J[看板与告警]
  H --> J
  I --> J

trace 把一次请求的各阶段耗时结构化：网关、编排、检索、工具、模型各成一段，段间是父子关系，排队与生成在模型这一段继续下探；有了这棵树，前文“两端对不上”的问题才有解。日志的规矩是只在处理点记一次：谁做决策谁记录，下游要引用就带 trace 标识去检索，不要把同一条决策在四层里各抄一遍。

span 属性里不写用户原文。需要关联同一段会话时，用会话标识符加内容摘要哈希，并且必须清楚：哈希不能当唯一识别长期留存。摘要是输入空间的压缩，当用户输入较短或模板化程度高时，枚举与撞库在实践里成本很低；一旦某个哈希值被长期留存又与其它数据集并列出现，它就退化成识别码。所以摘要只用于短期排障关联，到期即删，且不进任何外部服务、日志归档或缓存键。“能定位到哪一层坏了”是本节唯一的验收标准，判定关系如下。

现象 第一落点 佐证
TTFT 涨、引擎侧 TTFT 不涨 网关到引擎之间的路径或排队 网关与引擎两段 span 的差值分布
引擎侧 TTFT 涨、排队不变 模型版本、输入长度分布、预填充 版本包标识与输入 token 分桶

语义约定与厂商锁定

生成式 AI 的可观测语义约定正在快速成形。以开放遥测（OpenTelemetry）项目里的生成式 AI 语义约定这一主题为例，到本文写作时（2025 年 10 月）它仍在演进，字段名称与归属随时可能变化，因此本文刻意不写版本号也不抄字段清单。

结论是结构性的而不是版本性的：在自己的系统里立一层内部契约，再在出口做一层导出映射。内部契约定义本文承认的指标名、span 名、属性名与单位，是看板、告警、成本换算唯一允许引用的层；导出映射把内部名字翻译成外部约定或某个后端的字段形状。上游改名时改的是映射层，看板与告警不动；换推理引擎、换可观测后端、换云厂商时也只有映射要重写，历史数据不断档。

告警设计：少而可行动

告警只建立在两类信号上：用户可感知结果，例如端到端总耗时劣化、请求以错误收尾、答案被大量修正；早期信号，即在用户还没受影响时就能预示问题的量，例如取消率抬头、排队时间分布变宽、归因标签缺失比例上升、缓存命中占比下滑。每条告警必须自带四件套，缺一条就不要上线：触发条件写成可判定的表达式，并声明几个连续窗口满足才算；抑制规则声明同源风暴怎么压，至少按租户、按类别、按版本包三条聚合，同一根因在窗口内只发一次；通知分级声明这条走人工即时、走值班工单还是只进日终汇总；响应时限给出预期动作，本文所有分级与时限均为团队约定示例，不给具体分钟数与条数。

为什么不能给每条指标都配告警：序列数量是标签笛卡尔积的产物，给每条序列配阈值等于把统计波动全量转成人声；告警一旦失去意义，真故障就被淹没在自家噪声里。质量类告警还要更保守，三条理由叠加：质量信号多为抽样与评分，样本小方差大，天然抖动就足以触发阈值；质量难以自动定性，分数下滑到底是模型退化、流量结构变了还是评审器改版，机器判不出来；质量类告警的动作是今天必须有人去看二十条样本，做成即时惊动只会逼人把它静音。所以质量类只做日粒度趋势与版本对照，触发后走工单与例会；例外是线索型信号突然全部归零，那不是质量变好而是采集或校验器挂了，按可用性告警处理。

看板与复盘

日常值班看板只放四五个可行动指标，判据是一句话：看到它变红，值班的人今天能做一个具体动作。常用组合是端到端总耗时分位、错误与中断占比、每任务模型调用轮次、归因缺失占比、线索命中样本积压数；质量分与成本趋势不进值班看板而进周会与日终汇总，因为值班同学对它们没有当场可做的动作。发布前后对照看板必须与发布前同一口径：同一指标名、同一分位档、同一抽样框、同一单位，任何“新版本换一套更好看的算法”都会让对照失效。故障复盘的验收标准是看板能还原到分钟级且能按租户切开看：做不到分钟级就说不清故障起点，做不到按租户切就说不清影响面；分钟级不等于永久保留，超过留存期限的高粒度数据要降采样后保留。

看板区块 目的 谁看 出问题时的第一动作
端到端时延分位与样本量 判断用户体验是否劣化 值班 查排队与生成的拆分，确定瓶颈在哪一段
错误、中断与取消占比 区分服务故障与客户端行为 值班 看 SDK 版本与网络区域标签是否集中

抽检格子通过率 定位质量劣化的具体类别 算法负责人 按格子调样本，人工看二十条
版本包对照区 发布后判断是否需要回滚 发布负责人 比对灰度双跑的对照指标

上线前后的指标验收

灰度期只有一条纪律：双跑对照、同一口径。新旧版本在同一时间窗内接同类流量，两侧用完全相同的指标名、分位档、抽样框与单位计算。对照最小集合本文取四条：端到端时延分位、错误与中断占比、每任务模型调用轮次、抽检格子通过率，前三条是硬指标，最后一条按抽样进度看趋势。劣化到什么程度触发回滚，阈值一律是团队约定示例，本文不代各团队决定；但触发条件必须写成“连续几个窗口 + 哪几条指标 + 允许哪一条单独触发”的完整句子，写在发布单里。

必须提前接受：离线通过不等于线上无事。一是分布漂移，离线题库的类别、长度、语言分布是人为配的，线上上下文更长、追问更多、表述更脏，同一版本在两侧分数不可比，只有各自趋势可比。二是上下文里多了检索内容，离线样本常是干净问答对，线上同一道题会被塞进检索片段、工具返回与历史会话，输入分布整体右移，这类退化离线复现不出来，只能靠线上抽检格子发现。三是上游参数被顺手改动，采样参数、重试策略、路由权重、超时配置往往不在发布单上，却直接改变输出分布。

验收结论要落成一句可执行的话：哪几条指标、在连续几个窗口内、劣化超过约定示例幅度就回滚，回滚后由谁确认恢复。灰度期还要额外盯早期信号——取消率、归因缺失占比、线索命中样本积压数。

小结

请求返回 200 与回答可靠之间隔着一次语义判断，而这次判断无法在全路径上零成本完成，所以质量、性能、成本、安全四层必须同时存在。质量层要把信号分成结论与线索两档：抽检评分是结论，但只覆盖样本足够的格子；幻觉线索与负反馈是线索，正确用途是驱动抽样而不是充当分数；自动打分是筛子不是结论，人工复核与版本绑定是它唯一的使用前提。其余三层各有纪律：性能层是边界，TTFT 与 TPOT 精确到起止点，网关侧与引擎侧各是一路，两端对不上用链路串起来解释差值而绝不取平均；成本层是方向与分母，输入与输出分开算，缓存与轮次单独成指标，单位成本的分母必须是成功且有质量的任务；安全层是只计数不搬运内容，指标里出现类别、位置、版本与次数，永远不出现载荷。

贯穿四层的是同一句话：监控体系自己也是数据处理者。最小必要采集、字段白名单、独立域存储、访问控制、留存期限、脱敏优先，不是合规部门加给监控的成本，而是决定它能不能长期跑下去的地基。落地顺序本文建议：先立内部契约与命名规范，再把网关与引擎两路时延打通成一条链路，然后补成本归因与安全计数，最后才动告警——指标可以慢慢加，告警一多就关不掉。
