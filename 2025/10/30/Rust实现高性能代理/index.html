Rust 实现高性能代理

本文属于《Rust 学习路线》第 60/68 篇
上一篇系列目录下一篇

代理是整个后端体系里最少被写清楚、又最多被写错的一类组件：它同时面对下游的不可信客户端和上游的脆弱服务，任何一处的假设错误都会以”偶发的 502””连接挂住””某天下游突然全断”的形式冒出来。本文关心的不是把现成代理配置出来，而是用 Rust 自己实现一层代理时那些必须亲手处理的东西：数据结构的边界、字节怎么流、连接怎么活、什么时候该死。与《Nginx 配置优化》的分工是本文不讲某个具体代理软件的配置项；与《Envoy 服务代理》的分工是本文不讲成熟代理的功能清单；与《Rust 高性能网络服务实践》的分工是通用的监听与并发模型不再重述，只讲代理特有的部分；与《Rust 网络编程》的分工是 socket 与异步 IO 的基础 API 一律假定已掌握；与《API 网关设计》《模型网关》的分工是本文不讨论网关的治理职能与 LLM 语义，只讨论”转发”本身。

代理的位置与两种形态

先把最容易混淆的一件事说清楚：L4 代理与 L7 代理的区别不是”性能高低”，也不是”支持的功能多少”，而是程序在处理一个连接时，手里握住的对象是什么类型。

L4 代理的整个数据通路只认识字节流。它从 accept 拿到一个 TcpStream，与上游再建一个 TcpStream，然后在两者之间搬运字节。它不知道也不该知道自己搬的是 HTTP 请求、MySQL 握手还是随便什么协议。用 Rust 的类型语言表达，就是它的核心函数签名大概是这样：

L7 真正的成本在最后一行：一旦你决定”理解协议”，协议里所有历史包袱都变成你的代码。Content-Length 与 Transfer-Encoding: chunked 同时出现时以谁为准、请求行里的非法空格、头的折叠续行、HTTP/2 的 :protocol 与 HPACK 的动态表——这些不是可选特性，是任何一个愿意乱写的客户端都会踩到的路径。所以实践中常见的组合形态是同一个进程里两种通路并存：SNI 路由走 L4，需要按路径做灰度的流量走 L7。这决定了从第一天起就要把”字节级转发”与”请求级转发”抽象成两个不同的 trait，而不是在同一个函数里用 if 分支区分。

还有一个容易被低估的点：L4 的透明性意味着它对上游暴露的是下游的真实网络行为。下游 TCP 窗口、重传、慢客户端的节奏会原样传导到上游；而 L7 因为把请求解析成了对象，代理与上游之间是一条全新的 TCP 连接，慢客户端被”截断”在下游这一段。这就是所谓的缓冲解耦（buffer decoupling）。它听起来是好事，但代价是代理进程变成了内存的持有者——大 body 在 L7 里要么全量缓冲（内存风险），要么流式转发（失去对 body 的修改能力）。这个取舍必须在写第一行代码之前定下来，不能等到线上出现 OOM 再回头改。

问题 3 与问题 4 合起来是缓冲区与 flush 的关系。这里的心智模型是：write_all 只保证数据进入 Rust 侧的写缓冲（或内核 socket 缓冲），不保证对端已经收到；flush 在 tokio 的 TcpStream 上并不会发送一个 TCP”推送”信号，它的作用是把 BufWriter 层攒着的字节挤进内核。于是三种配置各有明确后果：

第三条是关键：代理不需要理解 HTTP 语义也能找到正确的 flush 时机——在 L7 里是”写完一个响应头/最后一个 chunk”，在 L4 里退化成”源端短暂空闲且缓冲区非空时 flush”。后者可以这样实现：读操作带一个很短的超时（例如示意值 50 毫秒），超时且缓冲非空就 flush 后继续，这样交互式流量不会被攒着，批量流量也不会被拆碎。这个模式在实现 WebSocket 隧道时收益尤其明显，因为一个鼠标移动的帧只有几十字节，等到 64 KB 是不可接受的。

最后一个容易忽略的是背压。用固定大小缓冲区做拷贝，天然就形成了背压：下游写得慢 → 代理的 write_all 挂起 → 代理不再读下游 → 下游的 TCP 窗口收缩 → 客户端被自己操作系统限速。整条链路不需要一行”限流”代码。要警惕的是人为破坏这个机制：给每个方向配一个无界 mpsc::channel 做缓冲（很常见的”解耦读写”重构）、或者把 Vec<u8> 直接 extend_from_slice 进一个不设上限的队列，都会把 TCP 的背压换成内存增长。慢客户端攻击之所以有效，就是因为代理替它把无限的数据吸进了内存。背压一旦要人为打断（例如给慢客户端设上限），打断方式必须是”关闭连接并计数”，而不是”丢弃数据继续跑”——L4 代理丢字节等于篡改数据流，比断开严重得多。

TLS 与 SNI

代理做 TLS 有两种位置，两者的代码复杂度、密钥责任与可见性完全不同，选错了很难事后纠正。

第一种是透传 TCP，只嗅探 ClientHello 拿 SNI。代理从不参与 TLS 握手，它只读取记录层头部与 ClientHello 里的一小段明文，然后把这个已经读走的字节重新交回给上游。TLS 的明文边界是这样的：握手协议本身加密（在 ServerHello 之后），但记录层头部与 ClientHello 是明文。所以嗅探在协议上是完全可行的，且不需要任何私钥——因为代理不试图解密，它只是”提前看了路由所需的那几十个字节”。

三个必须记住的细节：其一，一个 TCP 段里可能塞了 ClientHello 加别的东西，也可能 ClientHello 被拆成两段（TLS 1.3 的 ClientHello 带 key share 时体积不小，加上 IPv6 首包 MTU 的情况，分片确实会发生），所以”读到 5 字节头就以为读完了整个握手”是错的。其二，嗅探到之后，这些字节必须与后续数据严格保序地交给上游，任何一个字节丢失或错位，上游握手直接失败，表现为”只有部分客户端连不上”这类极难复现的故障。其三，嗅探阶段必须有超时。客户端可以只发 1 个字节然后永远不发第二个——这是最常见的慢速探测形态，没有超时的嗅探循环等于给自己加了一类免费的资源耗尽。

第二种位置是终止 TLS（offload）再重新签发到上游。代理此时持有面向该域名的证书，握手在自己这里完成，之后看得见明文，才能做 L7 路由、改写头、按内容灰度。代价全部落在证书管理上：需要按 SNI 动态出证（ACME challenge 只能覆盖固定域名，通配符则要 DNS 权限）、私钥必须放在 KMS 或 HSM 里而绝不出现在配置文件、需要维护吊销与轮换节奏、以及每个新连接都要承担两次完整握手（下游一次、上游一次）的 CPU 与 RTT 成本。还要额外注意：终止 TLS 之后代理与上游之间是否再加密是独立决策，如果为了省事退化成明文回源，那加密边界就终止在了代理，内网链路上任何一跳都能看见明文，这是安全评审时必须单独确认的一项。

    B -->|非 TLS| D[按 L7 HTTP 处理]

最后一点：透传模式下代理日志里不可能也不应该出现任何请求内容。这既是隐私优势也是排障劣势——你能看到”这条连接持续 40 秒、传了 3 MB、以 reset 结束”，但看不到是哪个接口。团队约定示例是把这类连接的全部可观测信息限定为 SNI、上下游地址、字节数与时长，明确禁止为”方便排查”而在透传路径上偷偷加解密。

HTTP/1.1 与 HTTP/2 在代理里的差别

这两个协议在代理里不是”两种格式”，而是两种转发粒度。这句话决定了代码结构。

HTTP/1.1 是”连接即会话”。一条 TCP 连接上的请求与响应严格串行：写完一个请求、读完了它的响应，才能开始下一个。所以对 1.1 而言，代理的复用单位是连接，一条从池子里借出的连接在同一时刻只能服务一个请求，而且必须等响应体完整读完才能归还——早归还一个字节，下一个请求就会读到上一个响应的尾巴，这类”响应错位”故障的表现是随机收到不属于自己请求的 body，比直接报错难查一个数量级。

第 3 条是安全相关的：如果代理把 Content-Length 原样转发给只认长度的上游，而自己按 chunked 判定结束，就会出现请求走私（request smuggling）的一类成因。所以规则是”代理解析用哪个，转发出去就只保留哪个”，绝不能两个都留着。同理 Connection: close 必须被代理消费掉而不能原样透传——它是逐跳头（hop-by-hop），含义是”你我之间这条连接要关”，不是”上游要关”。逐跳头完整清单在实现时应写成一处常量而不是散落各处：

via 头是环路检测最便宜的手段：代理每次转发都追加自己的标识，如果发现请求里已经出现过自己，就直接返回错误而不要转发。没有这一步，一个配置错误的路由规则（上游指回代理自己）会让进程在几秒内被自己的流量打死，而且从外部看像是遭受了攻击。

HTTP/2 把这一切换掉了。它是二进制分帧、一条物理连接上有多个并发流、每个流有自己的流量控制窗口，头部用 HPACK 压缩并共享一张动态表。对代理而言的结构性变化是：转发单位从连接变成流。一条下游连接可能同时有 60 个进行中的请求，它们要各自独立地派发到上游，任何一个慢请求都不能阻塞其它 59 个（这正是 1.1 管线化没能解决的事）。这带来两个具体的实现要求：

其一，HPACK 的动态表不能被无脑复用。如果代理把下游连接的动态表状态原样映射到上游连接，那两条连接上的索引号语义就绑死了，而上游可能因为复用池里的不同连接而完全没有表状态。正确做法是代理在两侧各自维护自己的编解码上下文，中间以”解压后的头列表”为交换格式——多花一次 CPU，换来上下游连接池彻底解耦。

其二，流控窗口要显式传递。下游因为自己的窗口小而发得慢，代理不能因为”上游窗口大”就加速拉取，否则数据全堆积在代理内存里；反过来，代理对上游必须按窗口拆帧写出，不能把一个大 body 塞成一个 DATA 帧。这里最自然的实现是让每个流跑一次与上一节相同的双向拷贝，只不过”读写端”换成了流的抽象对象而不是 socket——这也是把隧道函数写成泛型（AsyncRead + AsyncWrite）的实际收益：同一份拷贝逻辑能同时服务 TCP 隧道、TLS 流、H2 流与 Unix socket。

协议不一致时的降级路径是这类代理最容易出事故的地方。典型形态是下游 H2 多路复用、上游只有 H1.1：一条上游连接一次只能挂一个请求，于是 60 个并发流要占用 60 条上游连接，池子瞬间被打满；此时若再叠加”池满就排队、排队无超时”，表现就是整站请求雪崩式变慢而不是报错。必须做的三件事：池满时快速失败（并单独计数）、把下游流的并发数限制在池容量之内（用 H2 的 SETTINGS_MAX_CONCURRENT_STREAMS 反向告知下游）、以及队列等待一定要有超时。反方向（下游 1.1、上游 2）相对温和，但要留意上游 2 的连接是昂贵的共享资源，任何一次误关会让多条下游连接同时失败，爆炸半径被放大了。

Upgrade/WebSocket 在这两种形态里的表达方式完全不同，值得单独写清。在 1.1 里它是一次请求-响应的特例：客户端发 Connection: upgrade + Upgrade: websocket，服务端回 101 Switching Protocols，之后这条 TCP 连接脱离 HTTP 语义，变成裸字节流。代理在这里的正确行为是：解析完 101 后立刻把两侧连接交给上一节的 tunnel，并且从此不再对这段字节做任何 HTTP 假设。常见的错误实现有三类——继续用 body 解析器去读升级后的字节（WebSocket 帧的第一个字节会被误判）、忘记 Connection/Upgrade 是逐跳头需要特殊保留（这两个头在 101 路径上必须原样送到对端，与前面的剥离规则相反）、以及升级后仍套用 HTTP 空闲超时把长连接杀掉。在 H2 里，RFC 8441 定义了用 extended CONNECT 把流变成隧道的机制，代理要处理的是”一个流升级成了隧道”而非”一条连接升级”，此时隧道两侧的端点是流对象；如果上游不支持该项设置，代理就只能退回到为 WebSocket 单开一条 1.1 通路，这属于容量规划问题而不是代码问题，但要在配置里显式声明，否则运维会以为走的是复用路径。

长连接与背压

上游侧的连接池是 L7 代理最主要的收益来源，也是最多的故障来源。先说收益的量级构成：一次上游连接的成本包括 TCP 三次握手（一个 RTT）、TLS 握手（1.2 是 2 个 RTT，1.3 通常 1 个 RTT）、TLS 的 CPU、以及慢启动——最后这一项常被忽略，新连接的拥塞窗口很小，传一个几十 KB 的响应，前几个 RTT 只能吐出一小部分，因此连接复用的收益不只在省掉握手，更在于跳过慢启动。反过来说，一个每次请求都新建连接的代理，它的额外成本大致等于”至少一个 RTT 加上若干次慢启动往返”，这个描述是定性的，本文不给出压测数字。

“空闲保留时长带抖动”这句要解释一下，因为它是典型的”踩过才知道”的经验：如果代理的每个 worker 都在 60 秒这个相同的时间点淘汰空闲连接，而上游实例也在同一节奏下重启，就会出现周期性的连接建立洪峰。加随机抖动（例如在 60 秒基础上加减若干百分比）把淘汰时刻摊开，代价只是平均复用率略降。

最难缠的问题是池子里的连接被上游悄悄断掉。TCP 是双向的，上游进程崩溃、被容器调度器 SIGKILL、或者中间的负载均衡设备淘汰了会话，都可能让代理手里的连接变成”看起来能写、写完永远等不到响应”的状态。检测手段要组合使用，每个只覆盖一部分：

SO_KEEPALIVE 只能兜住一部分，原因在括号里：它的探测周期是内核级的、默认很长，而且”进程还活着但事件循环卡住”这种最常见的 hang 它完全看不出来——TCP 层一切正常，只是没人读数据。所以真正的兜底必须是应用层超时。另一个实用技巧是”池里的连接只借出、不长期持有”：借出时把连接的”最后使用时间”一并取出，如果超过一个较短的阈值（示意值 5 秒），说明它可能已经死了，先做一次低成本探测或直接退役；同时实现”写失败重试一次到另一条连接”，但这条重试只在请求尚未写出任何字节时才允许，否则会出现同一请求被上游执行两次。

背压在这一层的体现是”池的等待队列”。队列必须满足三个条件才算安全：有上限（超出立即失败）、有超时（等待过久的请求已经没有意义）、并且队列长度本身是一个指标而不是只记平均值。长队列在平均值上看不出来，但它会把整站延迟推向用户超时阈值——这是”没有报错但所有人都在超时”的经典成因。

健康检查与重试放大

先区分两种剔除方式，它们解决的问题不同，不能互相替代。

主动探测是代理按固定节奏向上游发一个专用的检查请求（GET /healthz 之类），失败若干次就把实例摘掉。它的优点是能在流量到达之前发现故障，缺点只有一个但很致命：探测路径与真实路径不等价。/healthz 通常只检查进程活着、端口能连，它不碰数据库、不进业务线程池、不占满文件描述符。于是最常见的事故形态是”实例健康但请求全超时”——探测全绿，摘除逻辑从不触发。缓解办法是让探测带上一点真实代价（例如做一次带超时的一跳依赖查询），并且探测的超时阈值要与真实请求的读头超时同源，否则探测会长期比业务宽松。

被动剔除是以真实请求的结果为依据，只有观察到足够多的失败才摘除。它的判断依据天然真实，代价是”至少要牺牲一批请求”。所以实践中两者并存：主动探测负责摘掉明显死的，被动剔除负责摘掉活着但坏的，且必须有一个恢复路径——被摘掉的实例要定期放一个真实请求过去试探（这就是所谓半开状态），否则一次抖动就永久失去容量，这在弹性伸缩的环境里会放大成雪崩。

“上游返回 5xx 就重试”之所以危险，是因为 5xx 有两类完全不同的成因：一类是代理自己造的（连不上，此时上游根本没收到请求，重试无害）；另一类是上游业务真的失败了（它已经执行了一半，可能已经扣了款）。代理无法从状态码区分这两者。更糟的是重试风暴：上游因为过载而返回 503，代理的每次重试又给它增加一份负载，正反馈下整个上游集群被自己的重试打死。因此重试必须有预算（retry budget），思路是把重试当作一种花费而非动作：

超时与优雅关闭

一个代理进程里最少要区分六种超时，它们约束的是完全不同的失败模式，共用一个总超时等于什么都没约束：

只配一个总超时为什么不够，有两个方向的论证。太短会误杀长请求（文件上传、报表导出），这是显性的；更重要的是它挡不住慢客户端：一个每秒写 10 字节的客户端，在总超时之内可以无限期地把连接保持为”合法活跃”，而每个连接都占着 fd、缓冲区和池里的一条上游连接。这类攻击面必须由”读头超时 + 字节率下限”来堵，因为它们的语义是”进展速度”而不是”总时长”。反过来，空闲超时也不能替代读头超时——一个正在被缓慢写入的连接在空闲判定上是”活跃的”。

超时值之间还有大小关系必须成立，这属于配置校验而不是运维经验：上游连接超时 < 上游响应头超时 < 整体请求超时，而代理的空闲超时应当略短于上游的空闲超时（差值用来吸收时钟与网络抖动）。最后这条经常出错：如果代理的空闲保留比上游长，上游会先关连接，代理则在下一次借出时才发现，于是”每次流量停顿后的第一批请求总有一两个失败”。这个现象的排查成本很高，因为它的概率与流量节奏相关。

优雅关闭的顺序在任何需要滚动发布的代理里都是硬性的，写成状态机最清楚：

sequenceDiagram
    participant Ops as 发布系统
    participant P as 代理进程
    participant D as 下游客户端
    participant U as 上游实例
    Ops->>P: SIGTERM
    P->>P: 状态置 draining，停止 accept 新连接
    P->>D: 已建连接上的新请求正常服务
    Note over P,D: 若做了就绪探针摘除，新连接此时已不再进来
    P->>U: 池停止借出，连接还完在途请求后关闭
    P->>P: 等待活跃连接归零（带上限）
    Ops->>P: 到达优雅上限
    P->>D: 对仍活跃的连接发出关闭信号
    P->>P: 指标落盘后退出

其中真正有技术含量的一步是”在不中断在途请求的前提下把新请求引到别的实例”。L4 代理做不到这件事的完整版本——它只能选”立即 RST”或”等它自己结束”，因为一条 TCP 连接不能搬家。L7 代理则可以：draining 之后在响应里附加 Connection: close，让当前请求正常完成后由客户端自己重连，重连会被负载均衡引到新实例。这是把流量平滑迁走的正确机制，代价是客户端必须真的会重连（很多客户端在这一步的行为不符合预期，需要在灰度里验证）。另外，SIGTERM 之后必须先让健康检查返回失败、再等一个探测周期、然后才停止 accept；顺序颠倒会让负载均衡仍然把新连接送到这个正在关闭的进程上，表现为每次发布都伴随一小段 5xx。

分类计数比直方图更早发挥作用，这条经验值得说明：代理的延迟分布几乎一定被少数长请求污染，P99 高不代表有问题；而”六种超时哪一种在涨”直接指向配置项。指标里不要放的东西同样重要，且必须是硬约束——用户请求内容、URL 查询串、任何头的值都不得成为指标标签。标签是基数，把路径当标签等于给监控系统做了一次拒绝服务攻击；把查询串当标签则会把令牌、手机号这类数据永久留在监控系统里，而监控系统的访问范围通常比业务数据库宽得多。

Rust 侧的实现约定很简单：暴露 /metrics 用的文本格式由 prometheus 或 metrics 生态的 crate 生成，计数器一律用原子类型而不是互斥表；每个连接的统计在 tunnel 返回时一次性提交，避免在拷贝热路径上做带标签的查找——那是唯一会被字节率放大的地方。 tracing 层面则是另一件事：traceparent 这类分布式追踪头属于必须保留、原样透传且不能由下游伪造后直接信任的类别，代理应当在自己这一跳重新派生 span，而不是把下游的采样决策当作既成事实。

安全硬约束

这一节的规则没有一条是性能相关的，但每一条被违反时都会直接导致事故，因此它们的优先级高于任何调优项。

核心事实是：代理的配置文件、启动参数、访问日志、错误日志与指标，权限边界通常比业务代码宽得多。业务服务的凭据只有它自己和运维能看见；代理的访问日志会被采集进集中式日志平台、被排障的人 grep、被贴进工单、被第三方分析系统长期保留；代理的配置会被渲染进编排模板、被镜像构建缓存、被开发人员在本地复现。所以同一条令牌，写在业务配置里是一处风险，写在代理日志里就是几十处复制。基于这个判断，本文所有示例与配套配置遵循同一条禁令：

转发时的头处理规则单独列一遍，因为这是”泄露”最直接的通道。必须剥掉的：全部逐跳头（前一节清单）、代理自身才有的认证头 proxy-authorization、内部服务间鉴权用的自定义头（它们只在代理与内部服务这一跳有意义，继续转发等于把凭据送给不该看的服务）、以及任何 Forwarded/X-Forwarded-* 里由外部客户端伪造的值（应当由代理重写而不是追加信任）。必须保留的：authorization 与 cookie（业务凭据，代理无权消费也不该记录）、content-length/content-type、idempotency-key、traceparent/tracestate、以及上游做校验所依赖的签名头。还有一条常被漏掉的：代理自己往上游加的头，名字必须与下游可能发送的名字错开，否则下游可以预先塞一个同名头，让代理的”我覆盖它”逻辑反而变成”我信任它”。

以及一条关于嗅探路径的：SNI 嗅探阶段看到的域名属于用户可控数据，绝不能直接拼进日志之外的任何地方（尤其是 shell 命令、文件路径、SQL），它经常出现在排障日志里，因此也要按”不可信输入”处理并做长度截断——一个 64 KB 的”域名”写进结构化日志，本身就是一种拒绝服务。

读这张表的方式是：左边的收益右边一定跟着一个风险，任何”只讲收益”的方案在代理这一层都不成立。比如连接池的收益很大，但如果不配套”写失败即弃用 + 池满快速失败 + 空闲时间略短于上游”，它会成为随机 502 的第一嫌疑；再比如 TLS 终止让治理能力上了一个台阶，但私钥管理与证书签发节奏是长期投入，做不好就变成每次证书到期都要人工救火。

小结

本文把”用 Rust 写一个代理”这件事拆成了六个必须各自回答清楚的问题：手里握的是字节流还是解析后的请求对象（决定这是 L4 还是 L7）、两个方向各自怎么关（决定半关闭传播与连接悬挂）、TLS 在哪一层终止（决定谁持有私钥、谁能看见明文）、复用单位是连接还是流（决定池的容量模型与并发上限）、什么错误能重试（决定故障会不会被自己放大）、六种超时分别归谁（决定慢客户端能不能拖死进程）。这六问没有一条是性能优化项，但每一条答错都会以稳定性的形式偿还。

Rust 在这里的帮助是具体而非抽象的：Secret 不派生 Debug，让”令牌进日志”变成编译期与评审期的问题；AsyncRead + AsyncWrite 的泛型拷贝，让 TCP 隧道、TLS 流与 H2 流共用同一份关闭逻辑；BufStream 与 shutdown 的语义区分，让”半关闭”有明确可写的代码而不只是注释里的约定；JoinSet 上显式 abort 则把”一侧出错时另一侧怎么办”变成必须写出来的一行。类型系统不会替你实现协议状态机，但它会把漏掉的那一支留在编译错误或 lint 位置上，而不是留在某个凌晨的告警里。

落地顺序上本文的建议是：先写 L4 隧道，并把关闭语义与双向超时测到没有悬挂连接为止——这一层是所有后续功能的底座，也是最值得投入测试的地方；再写 SNI 嗅探，因为它带来的路由能力最大而风险面最小（不持有私钥、不接触明文）；最后才引入 L7 解析与连接池，因为从这里开始，每一个优化都需要一条对应的保护机制才敢上线，而保护机制的数量会超过优化本身。还有一句值得单独留下的话：代理的性能问题绝大多数不是”Rust 不够快”，而是关闭时机、缓冲策略与重试放大这三件事没想清楚——它们在代码里都是几行，在故障复盘里都是几天。
