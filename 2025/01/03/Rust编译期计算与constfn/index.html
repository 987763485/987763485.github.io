Rust 编译期计算与 const fn

本文属于《Rust 学习路线》第 19/68 篇
上一篇系列目录下一篇

Rust 把”能在编译期算出来的东西就别留到运行时”当成一种设计取向，const 项与 const fn 是这种取向最直接的载体。本文梳理编译期计算的边界在哪、哪些套路在生产代码里真正站得住，以及它和宏、build.rs、优化器折叠之间应该怎么分工。宏的展开机制另文已述，这里只讲与 const 求值的分工。

编译期计算到底发生在哪一步

Rust 源码先进期为 HIR，再降级为 MIR，const 项与 const fn 的求值就发生在一个内建的 MIR 解释器里。这个解释器不是”能跑就赚”的附加部件，它是类型检查的一部分：一个 const 项必须在这一步算出确定的值，算不出来或者算的过程违反了规则，程序就直接编译失败。理解这一点很关键，因为它把编译期计算和”优化器顺手折叠”区分开了。

优化器的常量折叠是一种机会主义行为。let x = 2 + 3; 这样的表达式，优化器多半会折成 5，但你不许依赖它。优化级别不同、函数是否被内联、甚至同一个表达式在循环里的位置变化，都可能让折叠不发生； debug 构建里它往往什么都没做。也就是说，优化器折叠只影响性能，永远不影响程序能不能通过编译，也不影响语义。const 求值相反，它是被语言规范保证的：只要写进了 const 上下文，就必然在编译期完成，并且必然得到同一个结果。

const 项与 const fn 是两种东西，很容易混。const 项是一个编译期就确定的值，它的名字在源码里出现，但求值结果被内联进使用处，所以它没有内存地址，取地址会出问题。static 有地址，const 没有。const fn 则是一个”允许在编译期求值的函数”，它同时可以在运行时被调用，调用点是普通函数调用，编译器不保证任何折叠。这个区别经常被忽略：把 const fn 当成”编译期函数”来写性能注释，然后期待它一定在编译期算完，是一种误用。想让 const fn 真的在编译期出结果，你得把它放进一个 const 上下文里，比如赋给 const 项，或者用在数组长度、const 泛型实参这些位置。

const fn 的能力边界

const fn 今天能做的事情比早年多得多。控制流方面，if、match、loop、while 在 const fn 里都可用，循环支持在 1.46 前后进入稳定版；带 trait bound 的 const 泛型参数等能力也已在当时的稳定版可用。基础运算、数组与元组的构造和索引、部分标准库函数（如一些整数方法）都能在编译期跑。这意味着一个几百次迭代的查表计算完全可以放在编译期。

边界同样清楚，而且每一条都会变成编译错误而不是警告。第一，浮点运算在稳定版的 const 上下文里不可用，1.5 + 2.5 这样的表达式无法在编译期求值，这是长期存在的历史限制，截至本文写作日期仍未解除。第二，不能触发 Drop：常量求值过程里不允许有值走到需要析构的路径，因此任何带资源的类型都进不了 const 上下文。第三，不能堆分配，Vec、String、Box 在 const 上下文里都不可用，能用的只有固定大小的数组、切片和栈上结构体。第四，panic! 在 const 上下文里受限：可以触发 panic 让编译失败，但带格式化参数的 panic!("...{}...", x) 这类形式不支持，能用的是 assert! 这种不带格式化插值的简单形态。第五，不能调用非 const fn 的普通函数，也不能做可能违反 const 求值规则的 unsafe 操作。

实践里最常被低估的是”递归与循环都有步数上限”。求值器对单个 const 项的迭代次数有默认限制，写一个死循环或者超深递归，收到的是达到求值步数上限的错误提示，而不是等来一次卡死的编译。设计上可以把大计算拆成多个 const 项串起来，每项都不触碰上限。

实用套路：查表、断言与保常量

编译期查表是 const fn 最有价值的用法。CRC 表、字符分类位图、hamming 权重表、Unicode 区块的粗粒度索引，都可以用一个 const fn 生成，再绑到 static 数组上。好处不只是省掉运行时初始化：表内容进了只读数据段，没有 OnceLock 分支，也没有”第一次调用才建表”带来的首包延迟抖动。

const _: () = assert!(条件); 这个惯用法值得单独说。它利用匿名常量强制在编译期求值一个断言，条件不成立时编译直接失败，错误信息会指到这个常量声明处。它常用于校验 trait 实现的隐含约束、结构体字段对齐、跨模块约定的常量关系——这些用 debug_assert! 只能在测试里兜底，用运行时断言则有代价，而编译期断言把成本压到了零。另一个常见用途是保证”常量真正常量”：把一个容易被人改成 static 或改成函数返回值的关键数字包进 const 计算链，任何破坏编译期可求值性的修改都会立刻报错，等于给常量加了回归测试。

const generics：把尺寸变成类型的一部分

const N: usize 让类型可以携带一个编译期的整数值，典型签名是 struct Matrix<const N: usize> { data: [[f32; N]; N] } 或 struct RingBuffer<const CAP: usize>。它的核心价值是把”尺寸不匹配”从运行时越界变成类型不匹配：两个不同容量的缓冲区在类型系统里就是不同类型，混用直接编译失败；矩阵乘法要求左右两侧的维度数字一致，不一致时调用点报错，而不是等一个 panic。数组的 .len() 在 const 上下文可用，配合 const 泛型能做维度推导，环形缓冲区的掩码 CAP - 1 这类派生值也可以在 const fn 里算好。

但要在类型层面对 const 参数做算术，情况就没那么乐观。设想 concat_arrays 想要一个返回 [T; M + N] 的签名——在稳定版上这是写不出来的，涉及 const 泛型参数的表达式作为类型出现，依赖 generic_const_exprs 这个特性，它在本文写作日期仍是 nightly 特性、提案中未稳定，生产代码不要依赖。工程上的替代做法是避开加法：把结果缓冲区由调用方传入并断言长度，或者干脆用固定容量加运行时长度。同样要提醒的是，feature(inline_const) 之类把 const { ... } 表达式嵌进普通代码的特性也还停留在 nightly，别把它写进依赖库的兼容承诺里。

const trait 的现实与代偿

trait 方法今天仍然不能声明为 const fn。这意味着你在业务里常见的泛型代码路径，比如 T: Add 的求和循环，无法因为底层运算便宜就整体搬到编译期——约束是 trait bound 决定的，而 trait bound 不携带 const 信息。为 const 上下文引入 const trait 的方案（社区常称 const_trait_impl）截至本文写作日期仍未稳定，标准库内部为此使用了一套只在 nightly 可用的门控机制，普通 crate 用不了。

现状下的代偿有两条路。一条是宏生成：同一份逻辑用 macro_rules! 对每个具体类型展开一遍，展开出来的代码里可以随便用 const fn，代价是每个类型都要列进宏，报错信息也变差。另一条是过程宏生成代码，把编译期可求值的部分由 proc macro 在语法树层面算掉。前文已约定本文不重复宏语法，这里只谈分工：const 求值处理”类型已知、逻辑是纯计算”的场景，宏处理”需要在编译期生成新条目或跨越 trait 系统限制”的场景，两者经常互补而不是竞争。还要坦白一件事：由于 trait 方法不是 const，大量本可以编译期完成初始化的一次性计算，在泛型代码里只能退回到 LazyLock 加运行时分支，这部分重复成本是当下语言现实，只能等特性稳定。

分工对照：五套机制怎么选

机制 适用场景 可调试性 失败时的报错体验
const fn / const 项 纯计算、查表、尺寸与对齐校验 好，逻辑就是普通 Rust 代码 较清楚，定位到具体表达式，但求值器限制有时要读错误全文
macro_rules! 按类型或模式生成重复条目、变参语法 一般，需展开后才能看 展开前报语法错，展开后错误定位到宏内部，噪音较大
过程宏 需要读注解语义、生成完整 impl 或属性派生 差，逻辑在宿主 crate 里 可控但取决于作者水平，常见 syn 报错栈很深
build.rs 需要外部信息：探测平台、代码生成、链接配置 一般，是普通 Rust 程序 编译期之外执行，失败信息散在构建日志里
优化器常量折叠 不需要你选择，编译器自行决定 只能看汇编或 mir 没有报错——它不保证发生，也不保证不发生

工程注意：收益、语法与编译时间

把 const fn 用在热路径上的收益要分两种情况看。第一种是它消灭了真实的运行时工作：一次性建表、启动期校验、每帧都要读的静态数据，这类收益是确定的、可测量的。第二种是它只是把 let x = expensive(a); 挪进了理论上能折叠的位置——如果调用点的参数全是编译期已知的常量，优化器本来大概率也会折叠掉，此时 const fn 的边际收益接近零，它的意义在于把”必须折叠”变成”承诺折叠”，属于语义约束而非性能技巧。反过来，如果参数是运行时值，const fn 标记不产生任何运行时加速，写性能注释时不要把两者混为一谈。具体加速比例取决于表大小与访问模式，这里不给出数字；任何引用本节的基准测试都应标注为示意值。

语法层面，重复初始化数组的稳定写法是 [表达式; N]，其中表达式可以是 const 项或零大小类型；把 const fn 的调用结果作为重复值（形如 [const_fn_call(); N]）的语法在较新的稳定版才可用（社区普遍记为 1.79 起，拿不准工具链版本时以实际编译通过为准），老工具链上要退回手工展开或循环构造。对编译时间的影响要有清醒预期：const 求值占用的是类型检查阶段的串行时间，大表计算从运行时搬到编译期，等于给每次构建都交一遍税；据经验估计（示意值），单个 crate 里堆几十处重计算型 const fn，增量编译时间可能出现可感知的上浮，是否值得取决于该计算在运行时出现的频率。缓存方面，const 求值结果不跨 crate 增量缓存，改一个被大量引用的 const 项，触发重编译的范围由引用图决定，把大表放进独立模块能收窄失效面。

调试手段

const 求值卡住或报错时，第一步永远是读完整错误信息：求值器的错误通常带”evaluation of value failed”之类的总述加上发生错误的函数帧，帧里会指到 const fn 内部具体的那行表达式，多数限制（浮点、Drop、非 const 调用）在这条信息里就能定位。信息量不足的情况集中在宏展开之后——这时需要看展开结果，社区工具 cargo expand 一类可以把宏调用还原成生成的真实代码，再对生成代码逐行排查 const 报错，比在宏体里猜测高效得多。

想看编译期计算究竟算成了什么，有两个正规入口。一是 cargo rustc -- -Zunpretty=mir（nightly）输出 MIR，const 求值的输入正是降级后的 MIR，能直观看到你的 const fn 被降级成了什么控制流；稳定版上可以用 cargo asm 一类的社区工具观察最终代码里常量是否真的被内联成了立即数。二是把怀疑的表达式临时塞进 const _: () = assert!(你的计算 == 期望值);，让编译器在错误信息里把实际求出的值打印出来——这是稳定工具链上最朴素的”编译期打印”，成本几乎为零，值得形成肌肉记忆。

小结

本文的脉络可以收束成几条判断。编译期计算发生在 MIR 解释器里，是语义的一部分，与优化器顺手折叠有本质区别：前者保证发生，后者只是性能机会。const fn 是可进可退的函数，只有放进 const 上下文才真正在编译期出结果；它的边界（浮点、Drop、堆分配、格式化的 panic）在可预见的时期内仍由语言规则硬性划出。查表、const _: () = assert!(...) 断言和 const 泛型尺寸校验，是当下就值得普及的三件套；generic_const_exprs 与 const_trait_impl 仍属 nightly 与提案，生产代码应绕行。机制选择上，const 求值管纯计算，宏管生成条目，build.rs 管外部信息，优化器不归你管。把这套分工想清楚，编译期计算就从炫技变成可维护的工程手段。
