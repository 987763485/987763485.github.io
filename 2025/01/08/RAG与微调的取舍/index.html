RAG 与微调的取舍

过去两年，把大模型落进业务时讨论最多的路线选择，就是 RAG 与微调。本文不复述流水线搭建或训练原理，只谈决策：面对一个具体场景，该选哪条路，或者两条都要。判断依据无非四条——知识变化有多快、要控制什么、怎么评测、怎么回滚。

两条路的本质

一句话把两条路分开：RAG 改的是模型能看到什么，微调改的是模型本身会什么、怎么表现。RAG 在推理时把相关片段塞进上下文，模型的权重一动不动，知识住在外部仓库里，模型只负责阅读与消化；微调则用样本继续训练，把能力写进权重，推理时不依赖外部资料，靠模型的”直觉”完成任务。例子最直观：产品手册、制度文件、历史工单的问答属于前者，因为内容天天在变；让模型稳定输出企业固定话术的客服回复，或者学会行业黑话来给文本打标签，属于后者，因为要改的是行为与风格。定位清楚了，取舍才有得谈。单篇 RAG 的工程落地与分块重排序细节、微调与 LoRA 的训练原理另有专文，本文一律不重讲。

RAG 更合适的信号

出现下面这些信号时，优先考虑 RAG。一是知识更新频率高：文档库按周甚至按天在变，检索侧只需要重灌索引，不用动模型。二是需要引用与可追溯：回答必须给出来源文档与段落，审计时才说得清楚。三是权限与数据隔离：在检索侧做 ACL 过滤，同一套系统里，不同角色看到的资料范围不同，而这个边界不可能靠训练”记”出来。四是要控制幻觉来源：模型对超出知识范围的问题应回答”资料里没有”，检索未命中比凭空编造更容易追查。五是合规要求”能说明依据”。示例：一个内部财务制度问答机器人，每句回答都要挂上制度出处，并且区分总部与子公司口径，RAG 天然贴合。2024-11-25 发布的 MCP 协议把工具与数据源的接入方式标准化，检索侧的工程集成成本有所降低，这进一步放大了 RAG”起步快”的优势。工程上也顺路：检索侧的灌库脚本多用 Python 实现，选 3.12 或 3.13 皆可，3.13 的 free-threaded 构建仍是实验性的，无需追新；对话前端则常见于 TypeScript——这些都落在普通业务团队的能力圈内，不必为此额外配备训练方向的人手。

微调更合适的信号

问题出在模型行为上时，微调才是合适的杠杆。一是稳定的输出格式与文风：JSON 字段顺序、邮件的开头结尾、客服的语气范式，塞进提示词又长又不稳，用样本教更直接。二是领域术语与判别能力：判断设备报修单里的故障描述属于液压还是电气，这种本事很难靠现场阅读现学。三是把能力内化以省钱：长提示词去掉后，单次调用的输入 token 明显下降，高并发场景下这笔账很可观。四是结构化任务：把一段长文改写成五行简报，与其在提示词里反复叮嘱，不如内化成技能。五是延迟敏感：提示词短，首 token 的等待时间就短。2024-12-17 发布的推理模型 o1 说明”想问题的方式”本身也能训进权重，这与微调的方向是呼应的。

两者不是替代关系

真正落地时，两条路经常不是二选一。最常见的混合形态是小模型加检索：小模型训练便宜、部署灵活，微调把它的格式与术语短板补到及格线，知识缺口则交给检索来填。职责切分记住一句话：知识靠检索，行为靠微调——让检索负责”事实是什么”，让微调负责”怎么说话、怎么做”。顺序上，更稳妥的组合是先 RAG 打通：建好仓库、跑通检索、用通用模型原生的能力配少量示例提示词，把端到端基线立起来；当评测里反复出现”提示词和检索都救不回来”的错误，再考虑把这部分问题挪到微调路线上。这个顺序能避免把训练预算花在本质是知识缺失的问题上，也让团队先攒下评测集与归因经验，之后的微调才有验收标准可依。一个示意场景：电商平台的商品问答，商品知识一天变几次，天然该交给检索；但”先安抚情绪、再给退换政策”的话术范式稳定不变，就用几百条样本训一个小模型把它固化下来，两部分各司其职、各走各的更新周期。

粗看这张表：RAG 赢在更新时效与回滚速度，微调赢在推理成本与行为稳定性，混合方案用耦合成本换取能力覆盖面。决策时不必逐行打分，抓住对本场景最敏感的两三行即可——对时效敏感的业务优先看更新与回滚，成本敏感的业务优先看推理与训练两行。把这张表翻译回决策语言：当两条路在关键行上打成平手时，选团队技能那一行更踏实的一条；没有训练经验在手，混合方案就往后排，别用别人的预算表养自己的好奇心。

评测驱动决策

选型不该靠直觉，该靠评测集的归因结果。做法是：先和业务专家一起攒一份离线问答集，每道题标上期望依据与参考答案的判定口径；具体指标的定义另有专文述及，这里只讲方法。把当前系统跑过评测集后，将错误样本归因进四个桶：检索未命中、命中但答错、格式错误、拒答。检索未命中多指向仓库覆盖或检索策略，优先补资料、调检索，而不是急着训练；命中但答错，说明模型读了资料却没消化好，先加示例提示词重试，连续两轮仍无起色再考虑微调；格式错误是典型的行为问题，这类样本交给微调的收益最直接；拒答要拆开看——资料里确实没有依据的拒答是正确行为，有依据却拒答才是问题。归因周期可以按周滚动，做判定的人最好懂业务本身，因为”命中但答错”和”格式错误”的边界，往往只有领域专家能分清。这份归因记录本身就是选型的证据链，也是后续复盘的起点。另有一点要提醒：评测集本身也要版本化管理，业务文档一扩容，”答对”的范围就变了，拿新旧两版混在一起比分数，只会误导选型。

数据治理与合规

两条路都被数据约束着。微调这一侧，第一道关是授权：训练样本是否有权使用、是否混有个人信息——数据集要先做清洗与去重，剔除重复样本与敏感字段，具体操作此处点到为止。RAG 这一侧，重点在数据源本身：权限清单、更新机制与留存策略要当成资产来管，仓库一旦混进过期或越权的文档，检索会把脏数据原样端上来。随着《网络数据安全管理条例》于 2025-01-01 施行，整体的数据合规要求趋严，选型时要把”这条数据从哪来、谁批的、能留多久”的审计证据留在流程里。两条路都有一个共同红线：未获授权采集个人信息从来不是可接受的实现手段，能力再诱人，不能用的数据也只能放弃。合规不是选型的对立面——恰恰因为要说明依据、要管住数据边界，很多场景才更应该先上 RAG。一条实操建议：让微调数据集与检索仓库引用同一份数据台账，两套体系各管各的数据，审计来了必然说不全。

运维复杂度与回滚

运维视角下，两条路的失败模式截然不同。RAG 的典型劣化是召回退化：文档改了版式、仓库规模翻倍、嵌入表示与新内容对不上，答案质量会静悄悄下滑，用户只会觉得”变笨了”却查不出哪一步错了。它的回滚相对轻：换回旧索引、退回上一版检索配置或提示词即可，周期以小时计。微调的典型劣化是灾难性遗忘：新领域能力上去了，通用能力或旧任务表现掉下来，且样本分布会决定模型的偏向。它的回滚是换权重并择期重训，周期以天计，还要重新走一遍验收。灰度方式也因此不同：RAG 可以按查询或按用户分组，让新旧检索策略在线对比；微调只能让新旧权重两套服务并行，把新权重先挂到低风险场景观察。监控上，前者盯检索命中率与引用是否有效，后者盯定期抽样的人工检查与输出分布漂移。回滚成本天差地别这一点，常常是最后拍板时的决定性因素。还有一个容易忽略的差别：RAG 的仓库是全量的，一批不当文档灌进去，所有查询一起遭殃，所以灌库动作本身要能灰度、能重放；微调则是多套权重并存的模型管理问题，版本一多，部署与追踪的复杂度就上来了。

一个最小的判定示例

最后把全文的判断收敛成一段可执行的流程。输入是评测报告里归好桶的错误样本，输出是本周期该做的动作，伪代码式地写就是四行规则：未命中则修检索，命中答错则先改提示词，格式错则进微调候选，无据拒答则视为正常。用流程图表达如下：

flowchart TD
    A[错误样本入桶] --> B{检索未命中?}
    B -->|是| C[补资料或调检索]
    B -->|否| D{命中但答错?}
    D -->|是| E[加示例提示词复测]
    D -->|否| F{格式错误?}
    F -->|是| G[进入微调候选]
    F -->|否| H{有依据仍拒答?}
    H -->|是| C
    H -->|否| I[无据拒答属正常]
    E --> J{两轮后仍集中出错?}
    J -->|是| K[启动微调]
    J -->|否| C
    G --> K

这张图的要点不在分支多精细，而在强制同一套口径：每个动作都要先有归因证据，不允许”感觉该微调了”。示例里”两轮”是团队约定示例，具体次数按业务节奏定。

小结

把本文的决策收拢成五句话。第一句，用”改什么”分路：知识变了走检索，行为变了走微调。第二句，更新频繁、需要引用溯源、要做权限隔离、要控制幻觉来源、合规要讲依据，这五条信号优先 RAG；格式文风稳定、术语判别、成本内化、结构化任务、延迟敏感，这五条信号优先微调。第三句，两者可组合，小模型加检索是常见混合形态，顺序上先 RAG 打通基线，再判断是否需要微调。第四句，让错误归因替直觉发言，每个选型动作都要落在样本证据上。第五句，用更新时效与回滚难度约束运维成本，并守住数据合规这条公共底线。工具会一代一代换，但”这条错误属于哪一路”这个问法不会过时——把问法固定下来，取舍就不再是玄学。最后补一句心态上的话：这条路没有一劳永逸的标准答案，但评测集、数据台账与归因记录这三样家底攒下来，之后无论倒向哪条路、技术怎么换代，都不会亏。
