MoE 混合专家模型解析

稠密模型的账单是按参数量收的：每来一个 token，整个网络的所有参数都要参与一次计算。混合专家（Mixture of Experts，MoE）做的第一件事，就是把这张账单拆成两栏——模型总共有多大，以及每个 token 实际算了多少。本文只谈这一层结构与路由：门控怎么产生权重、专家怎么被选中、负载均衡怎么和路由互相拉扯、它在工程上又以什么方式失败。至于怎么把模型跑起来、怎么微调对齐、应用侧怎么分层，是另一些文章的范围，本文不重讲；量化也不在这里谈。

为什么要稀疏化

结论先说：MoE 的全部动机，是把”参数量”与”每个 token 的实际算量”解耦。其余种种设计，都是这一句话派生出来的代价。

稠密模型的容量与算力是绑死的。我们想让它多记住一些事实、多学会一些风格，通常只能加深加宽，于是每层的矩阵都变大，训练一步和推理一步都变贵。参数越堆越多，边际收益却越来越薄——这是把”模型大小”和”计算量”当成同一件事的必然结果。

MoE 换了一个思路。它把前馈层（部分做法也把它搬到注意力的某些位置上）复制成若干份，每一份叫一个专家，然后规定：一个 token 过来，不必所有专家都算，只挑其中少数几个。这样参数总量可以显著上去，而单个 token 的浮点运算量大致只相当于其中一个专家。GShard、Switch Transformer、Mixtral 这些更早的工作走的都是这条路，只是每次挑几个、怎么挑的取法不同；本文不列它们的具体指标。

代价也很清楚：多出来的参数虽然不用来算力，却要占显存、要跨设备搬运、要有人决定该用哪个专家。参数变成了”库存”，算力变成了”运费”，路由就是那个决定运费的调度器，后面几节讲的都是它。

门控网络与 top-k 路由

结论：门控网络是一个极小的线性打分器，它把 token 的隐状态映成”每个专家多合适”的一组分数，取前 k 个、归一化成权重，再用权重把专家输出加权求和；k 就是每 token 的算量旋钮。

结构上很朴素：一层不加偏置的线性映射，输出维度等于专家数 E。分数一般先过 softmax 变成概率，再按大小切一刀，只保留前 k 个。切完的 k 个权重要在自己内部重新归一化，否则它们加起来小于 1，混合结果的尺度会随路由不确定地漂移，训练里表现为一种很难查的尺度抖动。

k 的含义要说白一点：它是”每 token 算几个专家”，不是”模型里有几个专家”。k 取 1 时最省，路由最脆——一次打分错误就没有第二条路；k 取 2 是常见的折中，两个专家的输出可以互相补台；k 继续往上加，算量近似线性上涨，而容量收益递减，因为专家之间的分工本来就有限。判断一个 MoE 是不是划算，别只看专家个数，要看 k 与专家尺寸的乘积相对稠密基线是多少。

还有一处容易忽略的细节：门控本身也有参数量，虽然小得可以忽略，但它的梯度只经过被选中的专家回传。落选的专家在那一步收不到任何来自本层的梯度——这正是下一节所有麻烦的根源。

路由的可视化其实很短：

flowchart TD
    A[token 隐状态] --> B[门控线性打分]
    B --> C[softmax 概率]
    C --> D[top-k 选取]
    D --> E[权重归一化]
    E --> F[k 个专家前馈]
    F --> G[加权求和回残差流]

负载均衡辅助损失与容量因子

结论：门控只从”被选中的专家”那里拿到梯度，于是它会自发走向两个坏终点——一批专家长期饿死，另一批专家过载；负载均衡辅助损失负责把分布摊平，容量因子负责把过载硬截断，两者会互相拉扯。

先说两种失败长什么样。专家饥饿（expert starvation）指一部分专家在整个训练过程里几乎从未被选中：它们的权重停留在初始化附近，梯度长期为零，等于参数被白白占着显存却不干活。热点专家（hot expert）是反面：某几个专家吸收了远超平均的 token，它们所在的设备成为整步的短板，其它设备都在等它。前者浪费容量，后者浪费时间，而且在同一个模型里往往同时出现。

辅助损失的做法很直白：统计这一步里每个专家被选中的比例，和门控给它的平均概率一起，压向”均匀分布”。当某个专家分到的比例偏离 1/E 越远，惩罚越大；权重通常是个可调系数，并且要随训练衰减。要提醒的是，这个系数是把模型往”平均主义”方向拽，而路由本来是往”专精分工”方向走的——两者目标相反。拽得太紧，专家学不出差异，MoE 退化成一组互相稀释的同质前馈层；拽得太松，饥饿和热点一起回来。实践中最常见的观察方式是打印每个专家被选中次数的直方图，看它是否随训练越来越平或越来越尖。

容量因子（capacity factor）解决另一半问题。分布式实现里每个专家能处理的 token 数必须提前定死，否则显存无法静态分配，收发也无法对齐。于是给每个专家一个容量上限，常见做法是”平均 token 数 × 一个略大于 1 的系数”，示意值常在 1.0 到 1.5 之间。超过上限的 token 会被丢弃——它的路由结果不进入该专家，输出往往直接落回残差流或置零。

这就带来一个不体面但重要的事实：容量因子是”丢弃率”开关。系数偏小，省显存但一部分 token 的信息被静默扔掉，训练损失出现和路由相关的毛刺；系数偏大，几乎不丢，代价是显存和通信都按最坏情况预留。辅助损失想把分布摊平，摊平之后热点变少、需要的容量自然下降；反过来，如果容量给足、丢弃几乎不发生，辅助损失的存在感也就变弱。两者是同一个问题的两种写法，调参时别把它们当成互不相干的独立项。

专家并行与 all-to-all 通信代价

结论：MoE 的瓶颈常常不在算力而在互连——一次路由要把 token 按目标专家重新分发，这在全互联设备之间就是一次 all-to-all，而它的成本随专家数与 hidden 维度增长，和浮点收益不成比例。

稠密层做张量并行时，各设备持有同一个矩阵的不同切片，处理的是同一批 token，通信模式规整。MoE 层不同：设备 A 上的 token 可能要去设备 F 的专家。数据必须先按路由结果重排，才能喂给对应专家；算完再按原顺序换回来。这两个方向各是一次全交换，合称 all-to-all。

sequenceDiagram
    participant D0 as 设备0 持有batch前半
    participant R as 路由与容量分桶
    participant D1 as 设备1 持专家k
    participant D2 as 设备2 持专家m
    D0->>R: 计算 idx 与 w
    R->>D1: 分桶后发往专家k 的 token
    R->>D2: 分桶后发往专家m 的 token
    D1->>D0: 专家输出换回原顺序
    D2->>D0: 专家输出换回原顺序
    D0->>D0: 按 w 加权求和

为什么它比想象中贵：all-to-all 的字节数由”要搬运的激活总量”决定，而不是由专家的浮点运算量决定。token 越多、hidden 越宽、被路由的层越密，交换就越频繁；而每步计算量并没有同比增长。同一时间，最忙的那台设备决定了整步耗时，负载不均直接变成互连等待。这也是为什么许多做法在往两个方向走：要么把若干专家放到同一设备上、把跨设备交换降为设备内查表（专家分组），要么复制少数热门专家到多台设备以摊平它入向的流量（代价是多份权重和梯度同步）。DeepSeek-V3 在 2024 年 12 月底刚开源，本文没有条件复现验证，只把它当作同期公开材料看待，不作为成熟实践引用。

训练与推理两侧的不对称

结论：稀疏是算量的性质，不是显存的性质。推理时你依然要把全部专家权重装进显存——“激活参数少”绝不等于”显存省”。

训练侧的图景是分片的：专家并行把不同专家放到不同设备，每张卡只常驻一部分权重，靠 all-to-all 把它们串成一个逻辑上的大层。所以训练一个 MoE 所需的单卡权重占用，可以比同总参数的稠密模型低得多。

推理侧没有这个巧合。请求的 token 会路由到哪个专家，事先不知道；同一次长生成里，几乎所有专家都会被轮到几次。于是任何”只加载被激活的那几个专家”的想法，都变成把互连瓶颈换成磁盘读取延迟：要么每一步都在等权重从主机内存甚至磁盘搬上来，要么就得提前预热整套专家。多数实现因此选择整份常驻，显存占用按”总参数”算，而算力按”激活参数”算。

这带来两个直接判断。第一，评估一个 MoE 是否适合某个部署环境，要分别问两句话：它的每 token 算量是否够低（这决定吞吐和延迟），它的总参数是否能装下（这决定能不能跑）。第二，MoE 在批量小、单次前向的延迟敏感场景里收益有限——省下的算力被固定权重和路由开销摊薄；反而在吞吐充足、能把同批 token 按专家分桶合并计算的场景里最划算。至于把权重压小、把格式换掉以省下那点常驻显存，那是量化那条线的事，本文不展开。

工程判断与失败模式

结论：MoE 最难查的问题通常不在数值精度，而在路由——它不稳定、随批量变化，而且评测集可能在偏袒它。

其一，路由不稳定。门控是线性打分器，softmax 之后 top-k 又是一刀硬切。当两个专家的分数非常接近，输入的一个微小扰动就足以把选中集合换掉，输出随之跳变。表现为同一段输入换个批次、换个长度，答案风格明显变化；也可能表现为微调后期损失反复。常见缓解是在切分之前给分数加一点噪声（示意做法），或在 k 内部用更软的重归一化，但本质上是承认路由边界难以稳定。

其二，小 batch 下路由抖动。容量是按”平均 token 数 × 系数”算的，batch 越小，平均本身越不可靠：某一层的少数几个 token 全撞到同一个专家，就足以触发大面积丢弃。这解释了为什么同一个小模型在批量 1 和批量 32 下表现差距，比稠密模型的同场景差距更突兀。工程上要么放宽容量，要么在推理时改用更稳的路由取法，而不是简单地调低辅助损失系数。

其三，评测集对路由的偏袒。路由会把 token 派给”看起来最熟”的专家，而专家是有偏的好数据来源。如果某类题目恰好落在被反复选中的那几个专家上，分数会好看；换一批分布不同的题，同一模型可能明显下滑。所以只报一个总分会掩盖问题，至少要把每专家被选中次数与分领域得分放在一起看。

其四，两种更朴素的失败：加载顺序出错时表现为”能跑但答案奇怪”；如果路由统计里长期有一列专家计数接近零，那多半不是数据问题，而是权重没被正确装载，或者门控从一开始就没打算用它。

三种形态的对照

结论：稠密模型、共享专家 MoE、多适配器服务解决的是三种不同诉求——分别是”算得起”、”参数多但算得起”、”权重小且换得快”。

维度 稠密模型 共享专家 MoE 多适配器（LoRA 式）服务
参数量 单份权重，全部激活 总参数大，另有常驻的共享专家 一份基座加多份小增量
每 token 算量 与总参数同比例 约为 k 个专属专家加共享专家 与同尺寸基座相当
显存占用 按总参数常驻 按总参数常驻，训练时可分片 基座常驻，增量可按需换入换出
路由复杂度 无 门控、top-k、负载均衡、容量丢弃全都要 由调用方指定任务，不需模型内路由
部署形态 一卡一模型，直观 多设备专家并行，互连是主瓶颈 一基座多租户，切换成本是关键

共享专家那条值得单说：让一个专家无条件参与所有 token，其余专家仍由路由挑选。它把”路由完全失败也不至于空手而归”变成结构保证，同时消化掉大量通用 token，缓解热点。代价是共享专家的算量回到稠密水平，省下的只有专属专家那部分。

小结

MoE 只解决一件事：把参数量和每 token 算量解耦，其余全是它的账单。门控是个小线性器，k 是算量旋钮，top-k 之后要重新归一化；辅助损失与容量因子从两个方向对付同一种病——饥饿与过载，两者互相拉扯，要一起调。真正卡住规模的是互连：all-to-all 让瓶颈从算力挪到通信，这也是分组与复制专家存在的原因。推理侧请把”激活参数少”和”显存省”分开看：容量规划按总参数算，吞吐规划按激活参数算。最后，MoE 的疑难杂症多数长在路由上——不稳定、小 batch 抖动、评测偏袒，先把路由统计和分领域得分放在一起看，再谈调参。
