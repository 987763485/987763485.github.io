Rust 无锁编程与原子操作

本文属于《Rust 学习路线》第 32/68 篇
上一篇系列目录下一篇

写并发时最顺手的心智模型是锁，共享内存还有另一条路：不加锁，靠单指令的原子读写和一套内存顺序规则保证正确性。本文按浅要篇尺度讲四件事：原子类型覆盖什么、各档 Ordering 解决什么、比较并交换循环与内存回收为何必须配套、以及和锁怎么取舍。读完应得到一条判断路径：先量再说，而不是预设无锁更快。

原子类型族覆盖什么

结论：标准库的原子类型只覆盖“单个能整体读写的机器字”，不覆盖复合结构；而 Ordering 不是全局开关，是每次调用都要单独填的参数。

Rust 把原子能力做在一组具体类型上：整型从 8 位到最大位宽各一档，加上跟随指针宽度的 AtomicUsize、AtomicIsize 和 AtomicBool；指针形态另有 AtomicPtr，操作集同构但可用范围更窄，本文不展开。这些类型都实现 Sync，可被多线程以共享引用访问——无锁的入口就是“共享内存加原子访问”，与《Rust 并发：线程与消息传递》的“只传消息”是两条路；Arc 与 Mutex 归《Rust 并发原语：Arc 与 Mutex》，所有权归《Rust 借用检查与引用规则》，泛型代价归《Rust 类型系统与零成本抽象》。

覆盖不到的要自己搭：结构体里的两个字段不可能被一条原子指令同时改写，只能编码进同一个字、用版本戳加 CAS 循环，或退回 Mutex；浮点数不在稳定的原子族里，常见做法是按位重解释成整型原子搬运。

另外，Ordering 是这些方法签名的最后一个参数：load、store、swap、fetch_add、compare_exchange 都没有默认值可省。这不是啰嗦，而是把“你想清楚了吗”写进类型系统——内存序是最容易出错的一步，标准库不帮你隐藏它。

Ordering 各档强度解决什么

结论：原子值只被自己读写时 Relaxed 就够；一旦它要“代表”另一批数据已就绪，读端与写端就必须 Acquire、Release 配对；只有需要全体线程看到同一个变化总顺序时才上 SeqCst。

Relaxed：操作本身不可分割、不撕裂，但不保证它和其它访问的相对顺序对外可见。适合统计累加、监控打点、不参与同步的标志位。

Acquire：读端用。读取之后的访问不会重排到它之前；当它读到某个配对写入的值时，那次写入之前的所有写入对当前线程都可见。它解决“看到信号就看到内容”。

Release：写端用。写入之前的访问不会重排到它之后，把先前成果随这一笔交货，解决“别让数据比信号先到”。

AcqRel：同一操作既读又写时用，典型是比较并交换与作同步点的 fetch_add，兼有两档效果。

SeqCst：再加一条——所有 SeqCst 操作对全体线程呈现同一个全局顺序。最好讲清，也通常最贵。

对照成一张表，代价一栏是示意性的相对量级，不是性能数字：

Ordering 保证什么 典型用途 代价与风险
Relaxed 操作原子、不撕裂 纯计数、不同步的标志 无跨线程顺序，当同步点用会错乱
Acquire 后续访问不越过本次读，配对写入前的结果可见 消费端读标志与指针 有开销；写端用 Relaxed 则失效
Release 先前访问不越过本次写，成果随写交货 生产端发布数据 有开销；漏步暴露半初始化
AcqRel 读写两端效果同时成立 比较并交换等读改写 介于两档，不需要时白花
SeqCst 额外的全局一致顺序 跨多变量需统一顺序 通常最贵，常隐含全局栅栏

选型三句：不用它同步别的内存就 Relaxed；要发布与订阅就订阅端 Acquire、发布端 Release；说不出“为什么 acquire 和 release 不够”就别用 SeqCst。

最小可用写法：一对配对的例子

结论：先看一段最短的形状——普通数据先写，再用 Release 把就绪标志放出去；读端用 Acquire 拿到标志之后才允许看那个数据。

三个要点。第一，DATA 用 Relaxed 可以：它不承担同步职责，职责全在 READY 上，可见性靠这条链传过去。第二，两端必须成对——发布端若改成 Relaxed 写标志，读端的 Acquire 就失去配对来源，“看到标志却看不到数据”在弱顺序机器上就可能出现。第三，它保证的只是“标志为真后那笔 42 一定看得到”，不保证两个原子变量在某一瞬间共同构成整体状态。只要统计计数、不含同步含义时写法更简单：fetch_add(1, Ordering::Relaxed) 配 Relaxed 读取，换更强顺序只加开销不加正确性。

比较并交换循环

结论：比较并交换是一次尝试，不是一个操作；它会失败，所以无锁写法的骨架永远是“读—算—试—失败重来”这个循环。

compare_exchange 把原子值与期望值比较：相等就写入新值，不相等就把当前真实值还给你。成功与失败都带回旧值，这个细节很重要——重试要用失败返回的最新值重算，而不是把原期望值再试一遍。

为什么要循环？从读值、本地算新值到尝试写回，中间别人可能已经动过同一个字。CPU 不替你保存中间状态，只能在写回那刻检查“你读时看到的还算数吗”：算数就成功，否则给出当前真实值。所以循环不是防御性写法，而是指令语义的必然配套。

两点细节：失败可能因为值确实变了，也可能来自少数架构上的虚假失败，标准库因此提供弱版本 compare_exchange_weak，更便宜却更易无故失败，只适合放在循环里；循环体里别做重活，每次尝试都要重新构造一大段数据时，重试代价会盖过锁。

ABA 来自这条轨迹：你期望看到 A，别人改成 B 又改回 A，比较照样通过，于是你以为什么都没发生，实际中间过程被跳过。它何时才真实存在？当字段的值是可复用资源时——回收后重新分配的指针、会回绕的环形索引、把版本号与计数挤进同一个字却位宽不够。字段单调递增或永不重复时，ABA 只是理论名字，不值得为它加钱。两条思路：多留几位做版本标签；或把“能否复用”交给回收策略，也就是下一节。

另一半难题：内存回收

结论：无锁数据结构难的地方一半在“怎么改指针”，另一半在“摘下来的那个节点什么时候才能真正释放”。前者靠原子指令，后者靠回收策略。

由来很直接。加锁时“我还在用这个节点”由锁自动记录：有人持锁，别人就进不来。去掉锁后这信息没地方保存——甲刚把节点摘下，乙可能上一瞬才把指针指向它；甲此时释放内存，乙就踩进悬垂引用。于是删除必须回答：“确定没人再拿着这个指针了吗？”

思路之一是分代回收，通常叫 epoch 一类。机制是给时间打代标签：线程访问前先声明自己在当前这一代；节点摘下不立刻释放，而是挂进“摘下时那一代”的待回收清单；只有所有活跃线程都推进到更新的代，才释放旧代清单。代价三笔：内存占用滞后于逻辑删除，高吞吐场景峰值抬高；访问期间线程不能长时间阻塞，否则一个睡着的线程拖住全局回收；活跃线程集合与代数推进本身也要同步。

思路之二是危险指针，hazard 一类。机制是每个线程有一小格公开公告栏，访问指针前先把地址写进自己的格子，意思是“这个我在用，别释放”；释放方回收前扫描所有格子，还有人挂着就推迟。代价同样三笔：每次访问多一次公告栏写入与内存序约束；格子数量有限，单线程同时保护的指针有上限；回收前要扫一轮，成本摊进正常路径。

两类思路都不解决逻辑正确性，只回答“什么时候能把内存还给分配器”——这也是很多看着“就是一个 CAS 栈”的实现大半篇幅在处理回收的原因。本文只讲机制与代价，不涉及具体库的接口与版本。

与锁的取舍

结论：无锁不是锁的升级版，而是另一种约束下的解。它在少数负载形状上明显更合适，在多数负载上更慢、更难验证；判断路径是先量，再决定要不要换。

什么时候锁更合适？一是临界区要同时改多个字段并保持不变式，原子类型只覆盖单个字，多字段一致性靠 CAS 拼成本高且易错；二是有分配、系统调用、日志落盘这类会阻塞或耗时不确定的事，塞进重试循环等于反复重做重活；三是要等待条件（队列空了就睡着），这不是“一步改完”的形态，硬做无锁只能自旋烧 CPU；四是争抢不激烈、核数不多时，锁的开销本在噪声级别，换无锁量不出收益。

临界区怎么收缩，不换方案也值得做：把不参与共享的工作搬到同步之外，先在本地构造、校验、复制，最后只用一步挂上去；能拆的热字段拆成多个独立原子，别为“看着整齐”绑在同一把锁下；一次 fetch_add 能解决的不用 CAS 循环；读快照只在末尾做一次 Acquire 确认。收缩临界区的收益通常比换算法大。

然后是“无锁但活锁”。lock-free 只保证系统整体有人前进，不保证你这个线程前进。热点字段强争抢下，多个核反复读旧值、算新值、交换失败、再读，每次刚好被插队，局部看就是谁都没推进；多核同时打同一个计数器、或单次 CAS 很贵时最容易出现。缓解靠退避、弱版本交换、按核或分片分散热点再汇总、把多次尝试并成一次，共性是不消除争抢，只让重试不再互相踩。

判断路径四步：以锁的实现做基线，压出目标负载的吞吐与尾延迟；确认瓶颈真在同步上，看争抢程度、上下文切换、临界区长度，而非凭直觉；再看负载形状是否落在无锁优势区——高争抢、极短临界区、需要非阻塞前进保证；最后把回收与验证成本算进工期。四步走完仍值得才动手，否则一把收缩过的锁通常是更好的答案；“无锁一定更快”本文不成立，其他语言的习惯做法也不展开。

怎么验证

结论：无锁代码要靠“检测并发内存访问的工具类别”加“小状态空间上的模型检查”来验证；单元测试只能证明逻辑走通，证明不了内存序选对了。本文只讲工具类别与定位，不绑定具体版本。

第一类是数据竞争检测：编译器后端做运行期插桩，记录每次原子与普通访问，抓出两个线程非同步地碰同一块内存。定位是报了基本就是真问题，不报不等于没问题——它只覆盖这次跑到的轨迹，关心“有没有同步”，对“方向选错、顺序选弱”不一定敏感。

第二类是模型检查：枚举原子程序可线性化的执行交错，找反例并给出可复现的调度。定位是线程数与取值不大时能翻出某种 Ordering 组合的漏洞，但状态空间迅速膨胀，只适合抽出的核心片段。

第三类是静态提示加人工评审：linter 能标记可疑模式，比如跨函数依赖的同步关系、同一数据混用不同顺序，但证明不了正确性，仍要人按“哪一笔写代表哪一批数据已就绪”过一遍。

为什么单元测试测不出内存序错误？一次执行只是一条轨迹，而这种错误表现为某种少见的交错才出错；测试机常偏强顺序，很多在弱顺序机器上出错的写法在它看来永远正确，于是全绿只说明这个调度没炸；单测多断言最终值，问题却常在中间可见性——别的线程读到半更新状态，随后又被覆盖，最终值仍然对；发布产物里编译器与 CPU 的重排空间也比调试构建大。做法是把关键片段放进“多线程加随机扰动加长时压测加检测器”的组合里跑。

小结

本文把无锁编程拆成四块可独立判断的东西：原子类型族只覆盖单个机器字，复合一致性要自己编码或退回锁；Ordering 决定一次访问是否承担同步含义，Relaxed 与 Acquire、Release 的配对是多数场景的分界线；CAS 循环处理“尝试会失败”，ABA 只在值会被复用时才真实；回收策略解决“何时能安全释放”，是无锁结构的另一半成本。锁的取舍与验证难度共同决定它值不值得上线。建议动手顺序：先问临界区能不能收缩、这个字段是否真需要承担同步职责；内存序按 Relaxed、Acquire 与 Release、SeqCst 逐级加码，每加一级都要说清为什么低一级不够；性能结论以实测为准——先量再说。
