Rust 异步取消与取消安全

本文属于《Rust 学习路线》第 35/68 篇
上一篇系列目录下一篇

异步后端服务里，”把一个还没跑完的任务停掉”每天都会发生：上游超时、客户端断开、进程要退出。本文要把 Rust 中这件事的确切语义钉死——取消是什么、不是什么、哪些代码被取消后会留下烂摊子，工程上又该怎么把风险收敛。读完你应该能回答：手里这段代码 cancel-safe 吗，依据是什么。

取消在 Rust 里到底是什么

结论先说：Rust 的取消就是这个 Future 被 drop 了，从此不再有人 poll 它，仅此而已。它不是给任务发一个停止信号，不是抛一个异常把执行打断，也不是那种需要任务自己反复检查中断标志位的协作式取消。

要理解这一点，得回到 Rust 异步代码的执行单位。一个 async 块或 async fn 的调用结果会被编译成一个实现 Future 的状态机，它只有在被 poll 的时候才前进：poll 一次，状态机跑到下一个 await 点就返回 Poll::Pending，同时把唤醒自己的凭证 Waker 交出去，等事件就绪再被 poll 下一次。反过来，只要没人再 poll 它，它就永远停在原地。所谓”取消”，就是那个负责 poll 的东西——spawn 的调度循环、block_on 的等待、select! 里落选的分支——决定不再 poll 这个状态机，于是它连同捕获的全部局部变量一起被 drop。由此有三条常被忽视的推论。

第一，取消是”不再继续”而不是”中途被打断”。它只能发生在 await 点这类状态机主动交还控制权的边界上，不存在”某一行执行到一半被劈开”；也正因如此，两次 poll 之间的代码对自己的状态有完全掌控，这是 Rust 的取消语义显得干净的根本原因。

第二，没有任何机制通知正在跑的代码”你即将被取消”。状态机被 drop 时不会回头补执行中间那段逻辑，也不会把这件事广播给 await 链的每一层；代码对取消是无感的，只能在构造自己时安排好 drop 该干什么。

第三，取消默认发生且无法捕获：没有 catch Cancelled 这样的语法，也不需要在每个循环里手工检查中断标志。收益是不存在”忘了检查所以停不下来”的故障模式，代价是清理责任全部推给 drop 语义与调用方的设计。至于任务怎么跑起来，本文不重复《Rust 异步编程与 tokio 入门》讲过的 spawn 用法。

poll 与 Waker 的契约：清理只能挂在 Drop 上

结论：在取消这条路径上，你唯一能挂清理逻辑的地方是类型的 Drop 实现，语言没有提供 finally。

理解契约的最好方式是把自己写成 poller 的一方。一个手写的 poll 函数拿到 &mut Context，从中取出 Waker，在返回 Poll::Pending 之前必须确保”将来会有人调用这个 waker 的 wake”。这条约定本身不含取消语义：即使你已决定不再 poll 这个 Future，先前注册的 waker 仍可能随时被触发，而对一个已销毁的任务调用 wake 不是错误，只是浪费一次唤醒。真正要留意的是相反的坑：在自己的 poll 实现里把 waker 吞掉却没注册任何唤醒来源，任务不会崩溃，而是永久挂起，这比被取消糟糕得多。顺带一提，Pin 只保证状态机不再被移动，drop 一个被 Pin 住的 Future 完全合法——语言在类型层面就承认任何 Future 随时可以被丢掉，所以”可被安全 drop”是实现 Future 的硬性义务。

那么清理该放哪。既然没有 finally，工程上只有三种位置。其一，把资源包成 RAII 类型让 drop 自动归还，比如连接池的 guard 一析构就把连接还回去。其二，把”必须做完”的部分放进一个不会被同一个 select! 牵连的独立子任务，用消息通道把结果传回来。其三，让关键改动不跨 await，把”半完成”的窗口窄到能用不变量证明它不存在。另外容易搞反的一点：JoinHandle 被 drop 并不会让它 spawn 的任务停下来，句柄只是放弃了读结果的权力。

什么样的代码叫 cancel-safe

结论：cancel-safe 的定义是”在任意 await 点被 drop 都不会破坏程序其余部分依赖的不变量”；判定它的方法不是背清单，而是问”被取消的那一刻，世界留下了什么”。

这个术语在文档里通常写作 cancel safety，含义比”不会 panic”强得多：一个被取消的 Future 可以不 panic、不泄漏、不违反类型规则，却依然不安全，因为它把外部世界改成了调用方无法接受的中间态。判断的基准不在 Future 内部，而在它对外暴露的那份约定上。

读文档时按这个顺序看。先看函数或宏的文档里有没有专门的 “Cancel safety” 小节：有取消风险的 API 一般会写明三个档位之一——可安全取消、越过某个 await 之后不再可安全取消、不可取消。没有这一节不代表安全，只代表作者没做承诺，得由你自己判断。再看返回值给的是”完成的结果”还是”进度”：若一个读操作返回”这次读到了多少字节”，它天生就在暗示半途而废是可观测的，取消一次等于制造一次短读。

自己判定时，把 Future 想象成随时可能在任何一个 await 点被抽掉，然后逐点问四个问题。第一，有没有跨 await 持有已被改动的状态——取走了半块缓冲区、推进了一个游标、拿着锁准备改共享字段。第二，有没有”发出即不可撤回”的对外副作用——网络写、消息入队、扣库存都算。第三，有没有一个不变量需要两步操作才能维持，取消落在两步之间就会破坏它。第四，下游是不是把”没收到结果”当成”没发生”，这个假设不成立时，取消就会伪装成一次静默的成功或失败。只要有一问答”是且没有兜底”，这段代码就不该出现在可能被 select! 丢弃的位置；反过来，纯粹的计算、只在末尾产生一次副作用的写、用临时文件加 rename 收尾的落盘，通常都能过关。

select! 的真实危险：落选分支是被当场丢弃的

结论：select! 不是”等两个都回来再挑一个”，而是谁先完成就取谁的结果，其余分支的 Future 在这一刻被 drop。危险不在宏本身，而在于人们习惯性地把有副作用的写操作放进分支里。

这跟 Go 的 select 不是一回事：那边被放弃的 case 只是没执行接收，这边落选的是一个执行到一半的异步状态机。

看最常见的两种事故形状。第一种是”写了一半的文件”：分支里是 write_all(&bytes)，内部循环每轮只把缓冲区的一部分交给内核；另一个分支先完成时这个循环被从中间抽走，磁盘上的文件长度停在某个不上不下的位置，而且不会有任何错误返回给你——压根没发生错误，只是没人继续推进它。第二种是”发了一半的请求”：请求可能完整送达、响应也到了内核缓冲区、只是还没被解析，服务端已经做完业务并成功响应，而客户端把结果丢掉了。这等于”钱扣了，订单页没显示”。

还有一个容易漏掉的细节：select! 每轮都会把分支表达式重新求值，构造全新的 Future，所以”会自己重试”的写法其实每次都从头开始，累积进度全部作废。想让进度跨轮保留就得把 Future 提到循环外持有，而一旦这么做，你就得自己回答”它在这一轮被丢弃时留下了什么”。

timeout 与 retry 这两层包装，本质上都是同一个取消机制的语法糖，值得拆开看它们到底取消了什么。

结论先给：timeout 取消的是”等待”，不是”已经发生的事”。它把内层 Future 包起来，到点仍未完成就丢弃内层状态机并返回一个超时错误。请注意这个错误的含义边界：它只说明”我没等到结果”，绝不说明”那件事没做成”。因此把超时直接翻译成”失败”的代码，都在偷偷假设一个通常不成立的事实——远端没有收到请求。

retry 的前提更苛刻。朴素的重试是在说”上一次没成，再来一遍”，而它真正依赖的是”上一次的状态我能够安全地当作没发生”，这个前提只有幂等才给得起。一次读取、一次按唯一键 upsert、一次带幂等键且服务端做了去重的下单，可以重试；一次没有幂等保护的扣款、一次追加型写入，重试就是放大故障。正确顺序是：先让操作本身可重入，再在它外面包 timeout，最后才包 retry；顺序反过来，重试就是在赌博。至于退避多久属于策略问题，本文按下不表，只强调一点：退避期间那个 sleep 同样可能被上层取消，而这通常无害——sleep 是可安全取消的典型，它的 drop 就是把定时器注销。

工程做法：把取消变成可设计的东西

结论：既然语言层的取消是粗暴的，就在它下面铺一层协作机制、在它上面定一条停机纪律。

第一件是协作式的停止信号。做法很朴素：造一个所有子任务都能读到的令牌，内部是”是否已取消”的状态加一组等待者，任务在每轮循环开头和长 await 之前主动查一次，一旦置位就带着当前进度干净收尾。这与 Rust 内建取消并不矛盾——内建取消负责”不再给你运行机会”，令牌负责”让你有机会好好收尾”；要通知很多等待者时，用 Watch 一类一次写多处读的原语比逐个通知省事。

第二件是优雅停机的顺序。反例是一收到退出信号就拆运行器，于是所有在途任务同时被 drop，请求停在未定义状态。正确顺序分三步：先停止接收——关闭监听、健康检查转为不健康、不再 spawn 新任务；再 drain——给在途任务一个有限的宽限期，让已经跑到可提交点的任务把提交走完；最后才强制，超过宽限期的接受被取消。关键在”有限”二字，drain 无限等待会被一个挂死的任务拖垮。

第三件是给长任务配独立子任务与消息通道。当一件事必须”要么完整做完，要么明确没做”，就不要把它写在可能被 select! 丢弃的分支里，而是 spawn 成独立任务，父任务只通过通道收结果：父任务被取消时子任务并不会跟着消失，它能把这件事做完；若你确实希望父死子死，就让子任务去读那个协作令牌。一句口诀：副作用放在不会被丢弃的地方，等待放在随便丢弃的地方。

取消安全性对照表

操作类型 是否可安全取消 被取消后的状态 建议处理方式
纯计算、无副作用的 await 链 是 什么都不留下 无需特殊处理
定时器 sleep 是 定时器注销，无残留 可直接放进会被丢弃的分支
幂等读请求 基本是 远端可能已完成，本地丢弃结果 可重试，超时按”未知”处理
非幂等写请求 否 可能已完整送达并被执行 携带业务幂等键，先查后决
本地文件写入 否 半完成文件，长度与内容不一致 写临时文件后 rename 收尾
跨 await 持锁改共享状态 否 不变量停在半途，锁已自动释放 把改动收敛为单步可回滚
channel 发送 部分 消息可能已入队也可能没有 接收端做去重与幂等消费
子进程 / 外部命令 否 Future 消失，子进程仍在运行 单独持有句柄并显式终止
drain 阶段的在途任务 取决于设计 宽限期内收尾或接受被取消 停接收、限时 drain、再强拆

小结

本文的核心只有一个换法：把”取消”从”让任务停下来”换成”这个任务不再被运行”。想清楚这一点，多数困惑会自动消失——清理只能靠 Drop，所以资源要包成 RAII；通知不存在，所以要停就自己造协作令牌；落选分支会被当场销毁，所以有副作用的写不该放进 select!；超时只证明没等到、不证明没发生，所以重试的前提是幂等。实践上记三条：让每个可能被丢弃的 Future 都能回答”我留下了什么”；让必须做完的事待在不会被丢弃的子任务里；让停机按停接收、限时 drain、再强拆的顺序走。
