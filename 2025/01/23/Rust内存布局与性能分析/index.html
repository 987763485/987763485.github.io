Rust 内存布局与性能分析

本文属于《Rust 学习路线》第 49/68 篇
上一篇系列目录下一篇

导读：本文要回答三个问题：Rust 里一个类型到底占多少字节、为什么占这么多、怎么把它看清楚。适合开始关心“逻辑等价的两种写法为什么性能不同”的后端读者。读完你应该能解释结构体的空洞与补齐、枚举的判别标记与 niche 优化，并用标准库工具和断言把布局事实固定下来。

为什么值得单独谈布局

结论先行：Rust 承诺的是“可预测的内存表示”，而不是“源码里的字段顺序等于内存里的字段顺序”。这两句话的差别，正是本文要谈的东西。

不少后端同学第一次接触 Rust 时，会把布局当成编译器的内部细节：代码能跑，一个结构体怎么摆似乎与业务无关。这个判断在功能层面成立，在性能与边界层面不成立，原因有三个。

其一，Rust 没有把布局写进语言规范。字段声明顺序只决定访问语法，偏移由编译器按对齐重排，换一个 target 甚至换一次优化级别，偏移都可能不同。其二，布局直接决定“一个缓存行装得下多少个你正要访问的对象”，逻辑等价的两种写法跑出明显差距，来源常在密度与局部性而不是算法复杂度。其三，数据一旦跨过语言边界，布局就从实现细节升级为接口契约，靠默认规则是危险的。

顺带划一句界：本文只谈 Rust 自身的内存布局，Go、Java、Node.js 各自的内存模型与回收机制属于别的文章。

结构体：对齐、重排与 padding

结论先行：一个结构体的大小，约等于“重排后的字段占用 + 为满足对齐插入的空洞 + 末尾补齐”。字段顺序写得紧凑，不保证内存紧凑，但确实影响空洞的多少。

先说对齐。每个类型有一个对齐要求，可用 align_of 读到：它是 2 的幂，表示该类型首地址必须是这个值的整数倍。未对齐访问在某些架构上直接触发硬件异常，在另一些上要拆成两次读取再拼接。Rust 把对齐交给编译器保证，字段偏移与总大小都会被调整到满足所有成员。

再说重排。假设依次声明 u8、u32、u64：严格按声明顺序摆放时，u32 前垫 3 字节、u64 前垫 4 字节；而编译器会把对齐要求高的字段挪到前面，让它落在自然边界上，总大小可能小一档（示意值，取决于 target）。动机很直接——把低对齐字段聚拢，减少空洞。后果是：源码顺序没有任何偏移含义，“第 n 个字段一定在第 m 个字节”这类推断都不成立。

padding 有三个来源：字段之间的对齐空洞；末尾的补齐，因为数组里下一个元素同样要满足该结构体中最严的对齐；带数据枚举的判别标记填充，留到下一节。

可操作的判断方法是：把字段按对齐要求从大到小书写，通常能让总大小更紧。但这只是“通常”，不是保证，真要确定就用断言钉住。另外 repr(C) 会关闭重排、严格按声明顺序摆放，代价是体积可能更大，这点在 FFI 一节细说。

枚举：判别标记与 niche 优化

结论先行：带数据枚举的大小等于“判别标记 + 最宽变体的载荷 + 空洞”；niche 优化能把判别标记塞进本来就不合法的位模式，让“多一个分支”不多占一个字节。

先看没有 niche 可用的情形。带数据的枚举必须告诉运行时“当前是哪个变体”，这份信息就是判别标记。Rust 不保证标记的位置——它是首字节还是尾字节、和载荷怎么交错，由编译器决定并随 target 变化。能确定的只有两件事：判别信息一定存在，总大小一定不小于最宽变体。

于是有了那条推论：枚举的体积由最宽变体决定。哪怕只有一个变体携带 u64，其余变体全是空的，整个枚举也至少从 8 字节起（示意值，取决于 target）。这就是“给结果加一个错误分支”在热循环里被放大成成倍内存的来源：偶尔一次的失败，让每次成功都背着错误载荷的宽度。

再看 niche。很多类型自带“保留值”：引用和函数指针保证非空，非零类型（如 NonZeroU32）保证不是全零，bool 只取 0 与 1，但一个字节能表示 256 种位模式。这些“类型保证不会出现”的位模式，编译器可以拿去编码别的信息。于是 Option<&T> 和 &T 一样大：全零这个非法位模式被用来表示 None，不需要额外的标记字节。同理 Option<bool> 仍是 1 字节，None 塞进原本无意义的 2 到 255 之间。

niche 的实际意义是：它让“用 Option 表达可能没有”这种最自然的写法几乎没有存储代价，不必退回“返回哨兵值”的老路。但边界要认清——niche 只在保留值够用、且类型保证该位模式非法时才生效，一旦载荷里没有可用保留值，标记就要实打实地占地。同一个枚举的不同变体里，也可能出现“这个吃得下 niche、那个吃不下”的情况，所以仍回到本文主张：布局不要靠推断，要靠看。

把布局“看”出来：size_of 与 align_of

结论先行：size_of 与 align_of 能读到大小与对齐，size_of_val 能对值读取大小，但三者都读不到字段偏移；实践里靠“打印加断言”两条腿走路。

std::mem::size_of::<T>() 返回 T 占用的字节数，std::mem::align_of::<T>() 返回对齐要求，两者都不产生运行时开销，可直接写进比较与断言。size_of_val(&v) 接收一个值，好处是不必写类型参数，泛型里更顺手。

局限要说清楚。第一，它们只给聚合结果、不给分布：从这几个函数里看不出某个字段落在哪个偏移，也就无法直接验证“改了字段顺序，空洞是不是真的少了”。取偏移要靠别的机制，而拿到的是当前 target 上的数字，换 target 同样要重验。第二，size_of 对零大小类型返回 0，对 trait 对象只返回胖指针自身的宽度（示意值为 2 个机器字），管不了所指载荷。第三，结果随 target 变化，同一份断言在不同架构上一个通过一个失败，这恰恰是它作为回归检测的价值。

另外，若干更细的布局控制属性仍处于实验阶段、尚未稳定，不该写进主干代码。因此最划算的做法，是把当前 target 上验证过的大小与对齐写成单元测试里的断言而不是注释：断言失败说明布局假设不再成立，比线上性能回退后回头考古便宜得多。编译期求值的机制本身有专门文章，本文只把它当现成的工具用。

与性能的联动：缓存行、局部性与 SoA/AoS

结论先行：布局影响性能，主要不是通过“少几个字节”，而是通过“一次缓存行搬运能带进多少个你正要访问的对象”。判断方向靠局部性分析，不靠背倍数。

CPU 以缓存行为单位搬运数据：一次访问会把它所在的整行拉进缓存，同一行里的后续访问近乎免费，跨行则要到下级缓存找。后端服务里工作集大、访问密集，“同一批对象是否落在相邻地址”往往比“算法少几次比较”更值钱，这也是 Vec<T> 通常快于指针式链表的原因。

由此有三个方向值得逐个检查。

第一，Vec<T> 中 T 的密度。T 越小、空洞越少，一个缓存行装下的元素越多，遍历同样多元素时触碰的行数就按同样比例减少。所以在容器场景里，“把 T 的宽度压下来”经常比“给循环做微优化”更有效。

第二，Vec<Option<T>>。如果 T 本身没有可用保留值，每个元素都要额外背一个判别标记，数组里穿插着从未真正用上的标记字节，遍历读到的是“载荷与标记混在一起”的流。若“绝大多数元素都有值”，用 Vec<T> 加一个显式缺失记录，或把可选字段拆成“位图加紧凑载荷”，通常更省、也更适合顺序读。反之若稀疏度很高、访问又集中在“这里有没有值”，把 Option 留在同一列反而让“有没有”和“是什么”落在同一行，省一次跳转。这是必须先量稀疏度再决定的取舍，方向比结论重要。

第三，AoS 与 SoA。数组结构体（Vec<Record>）一次行加载会带进一条记录的所有字段，热循环只读其中一两个字段时，其余字节就是纯浪费；结构体数组（每个字段一个 Vec）把同一字段连续摆放，流式访问友好，代价是读完一条完整记录要跳到多段内存。选择标准压成一句话：按“热循环读什么”决定“什么连续摆”。本文不给倍数——它取决于工作集大小、访问模式和 target，只能用自己的负载去测。

FFI 与跨语言边界

结论先行：只要数据要跨过 Rust 的边界，布局就必须由你显式声明，#[repr(C)] 与 #[repr(transparent)] 是两种最常用的声明方式。

默认布局允许编译器自由重排，这在边界处不可接受：对端按自己的规则算偏移，两边算不出来就会静默读错字节，而且不报错。#[repr(C)] 把规则换成 C 的规则——按声明顺序摆放，用 C 的对齐与补齐算法。代价是放弃重排带来的收益：前面 u8、u32、u64 那个例子在 #[repr(C)] 下会明显变大（示意值，取决于 target）。也就是说，repr(C) 换来的是“对端能读懂”，不是“更省”。

#[repr(transparent)] 用在新类型包装上：它保证包装类型与内部那个唯一的非零大小字段有完全相同的表示。典型用法是把 C 侧句柄包成 Rust 类型以便挂上 Drop 回收资源，同时保证传出去时不需要重新解释。

还有几个必须显式处理的点。跨边界的枚举要加 #[repr(C)]，但带数据枚举的判别标记位置仍未定义，跨语言传它属于高风险区，一般只在边界上暴露无数据的 C 风格枚举。变长数据不要按值传，通常传指针加长度两个参数，让长度显式写进契约。C 的布尔类型、位域与 Rust 的 bool 含义不完全一致，别想当然一一对应。原则一句：边界处的布局要由代码声明，而不是由默认行为推断。

观测方法：从分配量与命中率看布局

结论先行：布局问题有两个可观测口径——分配量和缓存命中行为。前者回答“是不是变大了”，后者回答“变大是否已经影响访问”。本文只给口径与工具类别，不给具体数字。

第一个口径是分配量：进程常驻内存、每请求分配的字节数。做法上用能按类型或调用栈归因的分配剖析工具，关键是固定输入做改动前后对比，而不是盯绝对值。若一次结构调整让每请求常驻明显上升，方向就算对上了。

第二个口径是命中率：各级缓存的缺失次数与缺失率，以及内存带宽利用率。硬件计数器剖析工具能给出这些。判断方法与上一节呼应——改动只影响布局而不影响算法时，若指令数基本不变、缺失次数却明显变化，基本是密度或局部性变了；若缺失率上升而带宽已经打满，说明连续的访问模式被拆散了。

第三个口径最朴素也最有用：断言。把当前 target 上成立的大小写进测试，等于把“性能回归”提前变成“CI 失败”。顺序建议是先用 size_of 断言排除意外膨胀，再看分配量判断值不值得继续投入，最后才上计数器看命中率。

一张对照表

结论先行：布局问题基本落在下面几类表现里，可以直接当排查清单用。

布局问题 典型表现 检查方法 处理手段
字段顺序产生空洞 size_of 比手算大 打印大小与对齐，调整顺序后重测 按对齐从大到小书写
依赖声明顺序推算偏移 换 target 后行为错乱 在多个 target 上分别跑断言 用 repr(C) 显式固定
枚举被最宽变体撑大 结果类型体积远超实际需要 对比各变体载荷宽度 拆分枚举，或把大载荷挪到堆上
Option 标记进入数组 每请求常驻上升 分配剖析做前后对比 位图加紧凑载荷，或确认 niche
AoS 读到的字段用不上 指令数不变、缺失次数上升 用计数器看命中率 让热字段连续摆放
跨语言读出乱码 字段值明显不对 两侧各打印大小与偏移 repr(C) 与 repr(transparent)

小结

本文的脉络可以压成四条。

第一，Rust 给的是可预测的内存表示，不是可预测的字段顺序：偏移由编译器按对齐决定，靠声明顺序推断内存的做法不成立。第二，结构体体积来自“重排后的字段、对齐空洞、末尾补齐”，枚举体积来自“判别标记、最宽变体、空洞”，niche 让 Option<&T> 几乎不增大，但只在保留值够用且有保证时生效。第三，看得见的工具是 size_of、align_of 与断言，逐字段偏移要靠别的机制且随 target 变化，若干更细的布局属性尚未稳定；把布局事实变成 CI 失败，是成本最低的一道防线。第四，性能联动看缓存行与局部性，跨语言联动看显式声明的布局，共同的判断方法是：先确定“谁被一起访问”“谁必须读懂这段字节”，再决定字段怎么摆。

最后留一句方法论：布局不是需要背诵的字节表，而是一组可以随时用断言和剖析验证的事实。能测的，就不要猜。
