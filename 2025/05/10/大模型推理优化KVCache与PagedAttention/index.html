大模型推理优化：KV Cache 与 PagedAttention

问题起点：解码卡在访存而不是算力

大模型的生成是自回归（autoregressive）的：一次前向只产出词表上的一个分布，采样得到下一个 token，再把它接回输入序列继续算下一步。这个循环带来一个不对称——单步的产出极小，单步要读的数据却随历史长度线性增长。要理解推理优化为什么大多围绕键值缓存展开，得先把这个不对称讲清楚。

假设序列已经走到长度 S。第 S+1 步的前向要穿过 L 层，每一层的注意力都要拿新位置的 query 与此前 S 个位置的 key 做一次点积，再对这 S 个位置的 value 做加权求和。也就是说，历史部分的 K、V 每一步都被完整读一遍。如果不缓存，第 S+1 步还得把前 S 个位置的 K、V 重新投影出来：S 次投影乘 L 层，产出却只有 1 个 token。把每一步都这样重算，整个生成过程的计算量按 S 的平方增长。

为什么不重算是正确的？因为因果掩码（causal mask）保证第 i 个位置的隐状态只看得到它自己和它之前的 token，看不见之后生成的内容。只要模型权重固定、前缀 token 固定，第 i 个位置在每一层投影出的 K、V 就是一个常量，算一次即可长期复用。这就是键值缓存（KV Cache）的立足点：用一块显存，把每步 O(S) 的重复投影换成 O(1) 的读取。同一个理由也解释了为什么只缓存 K、V 而不去缓存 Q——历史位置的 query 在它自己那一步用完之后，再也不会被任何后续步骤读到。

省下了计算，却把成本搬到了访存上。单步解码里，权重矩阵被整个批次共享，读一次可以服务批次内所有请求；而 KV Cache 是每请求一份、每步全读。于是一个批次单步要搬运的字节数大致等于「每个序列的 KV 占用乘并发数」，它随并发数和上下文长度同时增长，不像权重那样能被摊薄。更麻烦的是这些读的算术强度（arithmetic intensity，每读入一字节所对应的浮点运算数）很低：注意力里历史部分的形式接近矩阵乘向量，运算数与字节数的比值只有个位数到十几的量级，远低于现代 GPU 由峰值算力与显存带宽之比给出的拐点。结果就是算力单元大量空转，卡在执行内存指令——我们称这种状态为访存受限（memory-bound），而不是算力受限（compute-bound）。

这也解释了两件看起来矛盾的事。其一，训练时一个大批次的前向能吃满 GPU，推理时同样的模型在单步解码上却常常只用掉一小部分算力，区别就在算术强度。其二，推理引擎最重要的优化往往不是把矩阵乘写得更快，而是想办法让更多请求在同一轮前向里排队，把每一份被读进来的 KV 都用满。FlashAttention 一类工作消掉了注意力内部中间矩阵的显存往返，让长上下文的注意力不再按 S 的平方占用显存，属于同一层的带宽优化；但它管的是注意力的计算内核，和历史 K、V 常驻显存这件事是两码事——后者由 KV Cache 的容量管理与调度决定，也正是本文后半部分的主线。至于把上下文本身做稀疏化或线性化改造，那是《上下文窗口扩展技术》的话题，本文不展开。

至于服务怎么部署、参数怎么调，往期《vLLM 大模型推理引擎实践》已经写过，本文只谈 KV 显存与调度的机制，实操指向那篇。

显存怎么算：一条能自己推的式子

关于「一个模型能开多大上下文、能扛多少并发」的争论，多半源于没有先把账算清楚。这里给一条可以自洽推算的估算式，字段名直接对齐训练配置，读者可以拿自己手上的权重去套。

各个符号在训练配置里都有对应字段，不必记住抽象定义：

  • L：Transformer 层数，对应 num_hidden_layers。层与层之间的 KV 互不通用，所以是乘法而不是加法。
  • H_kv：这一层实际存几份 K、V，对应 num_key_value_heads。在标准多头注意力里它等于 num_attention_heads；一旦引入共享，它就可能远小于头数，这正是第 3 节的内容。
  • d_head：每个头的向量长度，对应 head_dim，或者按 hidden_size ÷ num_attention_heads 推出来。RoPE 之类的旋转位置编码作用在这些向量的写法上，不额外增加每 token 的字节数。
  • b：每个元素占几字节。bf16、fp16 记 2，int8、fp8 记 1，四比特量化记 0.5 上下。
  • 最前面的 2：K 与 V 各一份。
  • S_cached：当前已经落进缓存的长度，等于提示词长度加已生成步数，而不是配置里的最大位置编码长度。这两个数差别很大，后面讲预留时会回来。
  • B：同时在飞的序列数，也就是并发。

下面三组配置都是示意值，取的都是好算的整数，跟任何模型的公开规格无关，只用来验证式子能推：

配置（示意值） 结构特征 L H_kv 每头维度 每 token KV 单序列 S=8192 单批次 B=32
A 多头不共享 32 32 128 512 KiB 4 GiB 128 GiB
B 分组共享 32 8 128 128 KiB 1 GiB 32 GiB
C 低秩隐式 32 不适用 576 维隐式 36 KiB 288 MiB 9 GiB

三行的差别全部来自 H_kv 与缓存对象本身，式子没有任何暗箱。有了这张表，访存受限这件事也有了量感：配置 B 在并发 32、长度 8192 时单步要读约 32 GiB 缓存，在一台显存带宽按 2 TB/s 记的机器上（同样是示意值），单步光读缓存的下限约 17 毫秒，逐 token 延迟的上限就在几十 token/s 附近——这是纯带宽推出的天花板，还没算采样、通信与调度开销。真要压这个数，能动的只有三件事：把 H_kv 或 b 变小、把 B 变大以提高每次读取的复用率、把 S_cached 里没用的部分删掉。后面每一节讲的技术，都能落到这三条上。

最后提醒账外项目。上面的式子只覆盖 KV 本体，实际占用还要加上块表与元数据、每步的激活与中间缓冲、图捕获所用的固定缓冲区，以及权重和优化器之外的常驻显存；这些都不是可以忽略的零头。反过来，B 也不能拿单批次占用去除以可用显存的商直接当作答案，因为预留策略与碎片会吃掉一部分——这正是分页那一节要解决的问题。

少存几份 K 和 V：从 MHA 到 GQA，再到低秩隐式

回看估算式，H_kv 是一个纯粹的乘数。这就给结构层面留出了一个非常朴素的方向：让多个 query 头共用同一份 K、V，占用就按共用的倍数线性下降。

多头注意力（Multi-Head Attention，MHA）里每个 query 头都有自己的 key 头和 value 头，H_kv 等于头数。多查询注意力（Multi-Query Attention，MQA）把它压到极致：所有 query 头共用同一份 K、V，H_kv 变成 1，KV 字节数直接除以头数，单步解码要搬运的历史数据同比例下降，访存受限的天花板被显著抬高。分组查询注意力（Grouped-Query Attention，GQA）取中间值，把 query 头分成若干部组，每组共享一份 K、V，H_kv 等于组数。它是目前开源权重里最常见的形态：Llama 3.x、Qwen2.5 这类模型的配置文件中都直接写着 num_key_value_heads，与 num_attention_heads 是两个字段，读者可以从 Hugging Face 的 config.json 里读到真实取值再回去套第 2 节的式子。共享得越狠，H_kv 越小，缓存与带宽越省。

代价要诚实地说清楚三点。第一，质量不是免费的：K、V 是模型对上下文的表征，让多个头共用一份表征，等于减少了它们各自“看历史”的角度，模型需要为此重新训练或做补偿性微调才能收敛到可用水平。公开论文说明了机制与方向，但没有一个可以照抄的质量结论；本文也因此不给压缩比和精度损失的数字，只给出结论性判断：结构改动必须由自己目标任务上的评测来验收。第二，这是训练期决策。对一个已经发布的 MHA 权重做“事后共享”，本质是把若干份 K、V 投影强行合并，属于近似改写，效果和风险都不可控；反过来，GQA 化通常要从头训练或长周期继续训练。第三，实现复杂度会转移而非消失：内核要处理头与 KV 的映射关系，缓存要按 KV 组而不是按头组织，早期一批推理代码为此重写过索引逻辑。

再往前走一步，就不只是“少存几份”，而是“换一个东西存”。以 DeepSeek-V2、DeepSeek-V3（2024 年 12 月发布）与其上的 DeepSeek-R1（2025 年 1 月发布）为代表的路线，把每层每 token 的 K、V 投影压到一个共享的低维隐式向量（常称低秩键值压缩或多头潜在注意力），缓存里放的是这个隐向量加上一小段与位置相关的维度，解码时再借助投影矩阵在需要时把它还原或吸收进计算。这样每 token 的缓存宽度就和头数解耦：H_kv 这个字段在这类配置里不再决定占用，决定占用的是隐式维度。第 2 节示意表里的配置 C 就是照这个形状写的——把 512 维隐式与 64 维位置相关维度记成 576，层数仍取 32。收益很可观，代价是推理侧必须专门支持：还原路径要重写注意力内核，缓存布局与常见实现不兼容，调度器、块管理都得跟着改。一个工程现实是：这类布局必须由推理引擎专门实现支持，否则权重虽在手上，缓存路径却根本接不起来。

顺带划一条轴：本节动的是 K、V 的“形状与份数”，和权重侧的量化（可参考《模型量化与 GGUF 格式》）是两件事。权重压缩减少的是每步读入的参数体积，KV 压缩减少的是每步读入的历史体积，两者可以叠加，但评测与排查时要分开归因。

连续批处理：跑完一个就补一个

结构改动改变的是每一份请求的体积，调度决定的是同一时刻有多少份请求在共享那一次读取。第 1 节说过，单步解码的开销里权重可以被批次摊薄而 KV 不能，所以提高“每次读入 KV 所产生的有效 token 数”是第二根主要杠杆。

最朴素的做法是按请求批处理（request-level batching）：凑齐若干个请求，一起进前向，直到这一批全部生成结束才收工、再放下一批进来。问题在于生成长度天然不齐。一个批次里的短请求早就吐完了结束符，却还要占着批次槽位、占着已经分配好的 KV 空间空转，等最长的请求跑完。更糟的是为了不把批次撑爆，预留必须按“最长可能长度”来，于是大量显存被尚未写满的缓存占着。结果是显存看着满了，实际有效并发很低。

连续批处理（continuous batching，也写作 iteration-level batching，即逐步批处理）把调度粒度从“一个请求的生命周期”缩小到“一次前向”。每完成一步，调度器检查哪些序列已经生成结束，立刻把它们移出活跃批次并把显存还给池子；然后从等待队列里取新请求补位，只要剩余缓存够它跑一步。这样活跃批次始终维持在能维持的最大并发上，被读进显存的 KV 几乎每一份都在产出 token。

它与 KV 占用是互相制约的，这层关系比“提并发就是省”要微妙。并发上得越高，单位时间的产出越划算，但缓存占用线性上涨，很快就撞上显存上限；一旦撞顶，调度器要么停止收新请求（吞吐被限流），要么对已经在跑的序列动手（抢占，下一节讲）。所以真实的引擎里并发数不是一个静态配置，而是被可用缓存块数动态决定的准入结果。一个可用的准入判据大致如下：

分页式 KV 管理：块表、碎片与两种抢占

有了连续批处理，显存分配器就成了瓶颈。原始做法是按请求预留：每个序列进来时，一次性圈出一段连续显存，长度按“最大上下文”算，也就是 max_model_len 乘每 token 字节数。这个策略有两个致命浪费。其一，绝大多数请求远没有跑到最大长度，预留而没用满的部分是内部碎片，别人不能用；其二，请求长度各不相同，池子里被反复切分后剩下的空洞大小不一，而新请求要的是一整块足够大的连续区间，于是明明总空闲量够，却分配不出来——这是典型的外部碎片。显存占用率很高、有效并发很低，两个数字同时出现，基本就能断定分配策略在漏气。

解决思路直接借自操作系统的分页（Paging）。在虚拟内存里，程序看到的是连续的虚拟地址，物理内存却是零散的页框，中间靠页表把虚拟页号翻译成物理页框号。KV Cache 的对应关系是这样的：一个序列的逻辑 token 位置序列相当于虚拟地址空间；把连续若干个 token 的 KV 打包成一个固定大小的物理块（KV block，块大小常取 16 或 32 个 token 每块）相当于页框；每个序列持有一张块表（block table），把逻辑块号映射到物理块号，相当于页表；注意力内核在第 l 层要读历史 K、V 时，先按逻辑位置算出逻辑块号，再查这张表得到真实显存地址。因为物理块尺寸统一，任何空闲块都可以服务任何序列，外部碎片被消掉了，浪费只剩最后一个未写满块的尾部，上界是一个块。

代价同样要摆出来。多了一层间接寻址，内核从一段连续拷贝变成按块表聚合读取（gather），访存不如纯连续布局友好；块表本身要占显存与主机内存，序列数一多就是可观的一笔；每块装多少个 token 是一个要权衡的参数——块太小则映射表长、内核碎片化，块太大则尾部浪费大、也让前缀共享的粒度变粗。这些代价换回来的，是分配器可以“按需增长”：解码一步只写当前块的剩余位置，写满才申请下一个块，于是预留策略从“按最大长度”变成“按实际用量”，第 4 节里 output_reserve 的两难才被真正缓解。

资源仍然会不够。当 admit 一个新请求或给老请求续块而无空闲块时，调度器必须抢占（preemption）某个在跑的序列，把它腾出显存。两条路子恰好互补。换出（swap）是把它的 KV 块整批拷贝到主机内存（CPU RAM），等轮到它时再拷回显存继续跑：不损失任何计算成果，代价是占用主存、消耗 PCIe 带宽，恢复时还有一段不可忽略的数据搬运。重算（recompute by preemption，抢占后重计算）是直接把块丢掉、记下它当时已经生成到哪一步，恢复时把这段序列重新做一次前向：不占主存，代价是要重付一份计算，而重算量与该序列已缓存的长度成正比——上下文越长，重算越贵。取舍框架因此很清楚：主机内存富裕、模型算子昂贵、序列很长时偏向换出；显存余量小而主存紧张、序列短、重算快时偏向重算。工程上两者常常共存，按被抢占序列的长度选边。顺带说一句，这套机制出自 PagedAttention 的论文（SOSP 2023）并在 vLLM 中落地，如今已是主流引擎的公共做法；本文侧重机制本身，具体引擎的参数与部署细节请回看《vLLM 大模型推理引擎实践》。

把上面几节串起来，一个请求在显存里的生命周期是这样的：

  A[请求进入队列] --> B{前缀块表能否命中}
  B -->|命中| C[复用共享物理块并引用计数加一]

  H -->|重算| J[丢弃块记录已生成步数]

  J --> L[重新前向补算历史后续跑]

前缀缓存复用：把同一段历史算一次

分页把显存切成了可共享的块，于是同一份内容在显存里只可能有一份；前缀缓存复用（prefix caching，也叫自动前缀缓存）就是把这句话用上：如果两个请求的开头若干 token 完全相同，那它们在这段前缀上的 K、V 值也完全相同（第 1 节的因果性论证在这里第二次生效），第二个请求没必要重跑这段预填充。引擎按块计算内容的键，命中就把共享物理块挂到新的块表上并给引用计数加一；只有当某个序列需要在共享块的中间位置写入时，才复制出一个新块改写，这正是写时复制（copy-on-write）的思路。省下来的是预填充的算力与时间，同时也少占一批块。

能稳定命中的场景有几类。固定的系统提示词（system prompt）是最典型的一类，只要它一字不动地排在请求最前面就能命中。少样本示例（few-shot）同理：把示例集合放在系统提示之后、用户输入之前，且每次顺序与文本完全一致。多轮对话是天然的重叠结构——每一轮请求都把此前的对话历史原样带上，只要拼接模板不变，前面若干轮的 KV 就是可复用的长前缀。工具调用密集的智能体（agent）负载也受益：同一份工具描述、同一份被反复引用的长文档，都会被重复送进模型。

命中判定要看三件事，缺一不可。第一是分块对齐：只有写满的整块才能被哈希与共享，序列尾部那个未满的块通常不参与复用，需要重新算，所以前缀长度越接近块大小的整数倍越划算。第二是逐 token 相等：共享的粒度是 token 而不是语义，任何一处 token 级差异都会让差异点之后的前缀全部落空。这意味着模板里的时间戳、请求标识、随机化的推荐语、每次变化的“当前日期”都是杀手；更隐蔽的是分词与模板层的变化——换分词器、改聊天模板、调整特殊 token 的拼接方式，等于给整个缓存池清零。第三是缓存键不能含用户敏感原文：键要用内容哈希或受控的键标识，而不是把提示词明文当索引；即便只存哈希，也要考虑长度、公共前缀带来的可推断性，并对键做隔离与生命周期管理。把隐私风险关在键设计这一环里，是前缀缓存能不能进生产的分水岭。

失效与淘汰要提前想好。引用计数归零的块不会立刻消失，而是进入按最近使用淘汰（LRU）的候选队列，在显存压力下被回收；这带来一个直接后果——冷前缀会在热度不够时被淘汰，下一次又得重算，于是池子大小与前缀热度分布之间需要一个容量决策，指标见第 8 节。必须做到整池失效的情况有：权重换版本或做继续训练、分词器与模板变更、以及键的盐值轮换。另外，llama.cpp 那类本地引擎也有各自的会话缓存机制，细节归《llama.cpp 源码解析》，本文不重复。

KV 量化与淘汰：省下的体积要用评测换回来

第 2 节的式子里还剩两个可以动的量：数据类型 b 与实际保留的历史长度。前者是 KV 量化（KV quantization），后者是淘汰类优化（eviction）。

KV 量化的机制与权重量化同类但对象不同：把 K、V 张量从 2 字节降到 1 字节甚至更低，按通道、按 token 或按块做分组，为每组维护缩放系数与零点。难点在于 KV 的数值分布不是一开始就知道的——它由输入决定，随层、随位置、随话题漂移，因此缩放系数往往要在线统计或分阶段校准，写入时同步更新。压缩的收益直接：每 token 字节数按 b 同比例下降，可容纳的并发或上下文随之上升。风险则来自注意力的数学形式：量化的 K 进入点积，误差被 softmax 的非线性放大，误差在长序列上还要跨很多项累积。因此精度风险有明显的形态特征——上下文越长越容易受影响，因为读取的历史项更多；检索式任务（在很长的材料里找出一处关键片段并复述）比概括式任务更容易受影响，因为它依赖个别 token 的精确匹配，而这些恰好可能落在被粗糙量化的位置上；同理，位置相关与首尾 token 常被认为值得单独保留高精度。这些是判断“该往哪儿测”的方向，不是可以直接引用的结论。

淘汰类优化更激进：不再把全部历史留在缓存里，而是按某种重要性判断丢弃一部分。常见形状有滑动窗口加保留开头若干 token、按累积注意力分数保留所谓重要 token、按层分配缓存预算等。它们的共同点是让注意力只看一份近似的历史，于是省的既有显存也有带宽。代价也更大：丢了哪些 token 取决于输入内容，同一个请求重跑可能不一致，归因困难；对需要回溯早期细节的任务，风险高于量化。这里要与第 6 节的“淘汰”划清界限：那里的淘汰是缓存块回收策略，块还在、内容还在，只是不再优先保留；这里的淘汰是把历史 token 从模型视野里删掉，是算法近似的决定。

因此两类优化的上线门槛是同一条：必须自建评测。我们的做法是固定一套覆盖三类能力的评测集——长上下文检索、多轮一致性、格式严格的工具调用或结构化输出；先在 bf16 基线上跑通并保存输入，再用同一份输入、同一套模板与聊天格式、同一套采样参数跑量化或淘汰版本，逐条比对而不是只看总分，因为总分常常掩盖了检索类的局部塌陷。工程上还要保留一条随时可切换的高精度回退路径，并让变更按请求灰度放量。第 10 节的对照表把这一列写成了“代价与风险”，读起来像形式，但它实际是这类优化唯一可靠的入场券。

观测与容量规划：先定口径，再谈数字

没有指标就没法判断上述任何一项优化值不值得做。要采的东西与口径可以这样定：

压测要在没有现成数据时自己搭一次，方法是把变量摆成阶梯而不是找一个“最优值”。并发按倍增档位推进，从很低一直到明显过载；输入长度与输出长度分别控制，因为它们压力方向不同——长输入考验预填充算力与一次性块分配，长输出考验驻留时长与块增长。每个档位至少跑两组：一组是固定长度的干净组，用来看得失是否线性；一组是带长尾的混合组，因为抢占几乎总是在长尾出现时才被触发。跑正式统计前先预热，让缓存池、图捕获与前缀块进入稳定状态，丢弃预热批次的结果。限额必须提前设好：最大并发、最大输出长度、显存水位告警线，触线就停止加压而不是继续冲；判停条件写成可执行的形式，例如 p99 首 token 延迟超出目标或抢占率超出阈值。

判读框架比数字更有用。占用率随并发上升而逐 token 延迟基本不动，说明还在带宽摊薄区，加并发是划算的。占用率上升同时延迟同步恶化、抢占从零星变成常态，说明已经触顶，此时要么缩小每 token 字节数（走结构或量化那条路），要么限制驻留（淘汰或缩短最大长度），要么承认容量就是不够。吞吐不再随并发增长而排队时间暴涨，说明瓶颈已经从前向移到了准入控制。最后这一种现象很容易被误读成“模型变慢了”，而指标上要区分得很干净：分配失败与限流排队是两回事，第 9 节的清单第一条就是它。

常见误用与排查清单

第一个误用最贵：把长上下文当免费。上下文长度在估算式里是乘数，双倍的长度意味着双倍的每步读取与双倍的驻留显存，它同时压低可容纳的并发并抬高每步耗时，绝不会因为“模型支持一百二十万”而变成装饰性数字。第二个误用是忽略最大输出长度对预留的影响：在还没有分页的栈上，预留按 max_model_len 或按“提示加最大输出”圈地，把最大输出长度设成远大于实际需求，等于凭空造出大量未写满的预留，有效并发被腰斩；即便上了分页，调度器的准入判据里那个 output_reserve 仍然沿用这个上限。第三个误用发生在提示词工程一侧：改一个标点、调整一个空格、往系统提示里塞进当前时间，都会让原本可复用的整块前缀全部落空，表现为块表未命中率突然跳高而模型与配置没动。第四个是把 OOM 与抢占混为一谈：分配失败是池子真的没有可用块（或碎片化、或被预留吃掉），症状是报错或请求被拒；抢占是可恢复的调度动作，症状是延迟毛刺与重算量上升，请求最终还能完成。处理路径完全不同，前者调容量与碎片，后者调水位与优先级。第五个是缓存键里含用户敏感原文：图一时方便用提示词明文或其可逆编码做键，等于在服务内部保留了一份可被侧信道推断的索引，风险远大于它省下的算力。

小结

本文把 KV Cache 相关的优化收敛到一条式子上：每 token 字节数由层数、KV 头数、每头维度与数据类型相乘得到，占用再由驻留长度与并发放大。所有能做的事要么在缩小这个乘积，要么在提高每次读取里有效产出的比例，要么在给这个乘积腾地方。这三条路彼此不冲突，但它们的失效模式很不一样，所以一次只动一条轴、一次只归因一件事，是这类优化能持续下去的前提。

调度侧的连续批处理与分页是收益最确定、风险最低的一层，因为它不改变模型的数学行为，只改变显存的组织方式；代价都付在内核间接寻址与调度器复杂度上，可以靠指标直接验收。结构侧的共享与低秩压缩收益最大，却必须付训练期的决策成本，事后改写不是工程问题而是模型能力问题。量化与淘汰处在中间：改动很轻，验收很重，因为误差以长度和任务形态为函数出现，总分看不出局部塌陷。前缀缓存则把工程与合规绑在了一起——省的是预填充，赌的是模板稳定与键设计干净。

如果要给一个落地次序，我们会按“先把账算清楚，再把碎片消掉，再把重复的读取省掉，最后才动数值精度”推进：用第 2 节的式子对照配置文件复核每 token 成本，把长度分布与预留策略摆平；上分页与连续批处理，把块水位、抢占计数与命中率纳入常规采集；然后审视前缀是否稳定可复用；只有在容量确实撞顶且自建评测通过时，才把 KV 的位宽降下来。至于长上下文算法本身、集群拓扑与私有化成本，属于另几篇的分工范围，本文不越界。
