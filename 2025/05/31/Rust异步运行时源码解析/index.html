Rust 异步运行时源码解析

本文属于《Rust 学习路线》第 37/68 篇
上一篇系列目录下一篇

Rust 的异步编程常常被误解为”加了 async 关键字就快了”。实际上，async fn 编译出来的是一个实现了 Future（未来） trait 的状态机，它自己不会跑。真正让它跑起来的，是运行在下面的异步运行时（async runtime）：它决定任务什么时候被 poll（轮询）、被谁 poll、IO 就绪了去唤醒谁、定时器到期了谁该继续执行。本文以”当时主线实现的常见形态”为口径，把一台异步运行时拆成任务、调度、定时、IO 驱动、阻塞池、关停六个子系统，逐个讲清楚它内部的机制与取舍。往期《Rust 异步编程入门》讲的是怎么”用”，本文讲的是它怎么”实现”；横向对比 tokio 与 async-std 的生态差异另有专文，本文不做比较。

由于各运行时版本迭代很快，本文不锚定具体小版本号与源码行号；涉及默认值的地方，一律以”通过运行时构建参数配置，默认值随版本调整，以当期文档为准”的口径表述。读者可以把手头任意一个主流多线程运行时的源码摊开对照，本文描述的是这些实现共同收敛到的结构。

任务与 Future：运行时到底在调度什么

先把边界划清。Rust 语言本身关于异步只提供了三个契约：Future、Poll 和 Waker（唤醒器）。Future 只有一个核心方法，签名大意是”给我一个 Context（上下文，内含 Waker），我还你一个 Poll 结果”；Poll 是个两态枚举，要么 Ready（就绪）携带完成值，要么 Pending（待处理）表示”还没好，别再来烦我，等我唤醒你”；Waker 则是一个可以被克隆、可以被调用的句柄，调用它的效果是”让对应的 future 重新变得可 poll”。语言标准库提供了一个 poll_once 之类的手动驱动工具和一个用于测试的简易阻塞执行器，但没有任何”同时跑一千个任务”的能力。

于是运行时接管了剩下的一切，职责清单大致五项：

其一，任务存储。spawn（生成）一个 future 之后，运行时要在堆上为它找一块能长期存活的内存，因为 future 可能是被 async fn 生成的、生命周期不定的状态机，不能借用调用栈上的空间。其二，调度。哪个 worker（工作线程）在什么时候执行哪个任务的 poll，是运行时的核心策略问题。其三，IO 驱动。把 socket（套接字）的可读可写事件翻译成对应任务的唤醒动作。其四，定时器。维护成千上万个 sleep 的到期时间，到期时唤醒对应任务。其五，阻塞池。把注定会占住线程的同步调用挪到专用线程上去。

为什么”不写运行时，async fn 就不动”？因为编译器把 async fn foo() { ... } Desugar（语法脱糖）成一个匿名状态机：每个 .await 点都是状态机的一个状态，局部变量在状态间存活。这个状态机实现了 Future，但实现 Future 不等于有人调用它的 poll。没有执行器去 poll，它就是躺在栈上一块没人碰的字节。这与 Go 的 goroutine 或 Erlang 的进程根本不同——后两者语言运行时自带调度器，而 Rust 把调度器留给了库。

理解了这一点，就能理解运行时里最核心的数据结构为什么长成那样：一个 spawn 出来的任务，通常被包装成”任务头 + 原始 future + 调度元数据”的复合体。任务头里放着引用计数、状态位图、所属调度队列的链接指针；原始 future 以某种类型擦除的形式存着，因为调度器需要一个统一的入口去 poll 不同 async fn 产生的不同类型；调度元数据记录它当前在哪个队列、是否正在被执行。类型擦除常见有两种做法：一是把任务塞进 trait 对象，通过 vtable（虚函数表）间接调用 poll；二是利用构造时已知类型的”函数指针表”，把 poll、drop、release 等操作在创建任务时就固化成一组成对保存的指针。后者的好处是任务体可以保持具体类型，省掉对象大小的间接开销，代价是每类任务要生成一组胶水代码。

任务的状态位图与引用计数

任务头的引用计数与状态位合在同一个原子字（或同一组原子字）里，是主流实现反复收敛的设计。原因很实际：任务生命周期上的每一次状态迁移，几乎都伴随一次引用计数的变化；如果计数与状态分两处存，就需要两次原子操作甚至一把锁才能保证一致性，而在高并发调度路径上，这几乎翻倍了同步开销。合并之后，一次 CAS（比较并交换）就能同时表达”我拿到了这个任务的执行权，并且它从等待态转入运行态”。

逐位解释一下这段清单。RUNNABLE 与 BLOCKING 互斥：前者表示”可以跑”，后者表示”这个任务在等一个不经过调度器的信号”，典型场景是同步上下文里等待某个异步结果。SCHEDULING 位的作用是保证同一个任务不会被两个 worker 同时 poll——这是运行时的安全底线，poll 必须对同一任务串行。COMPLETED 与 CANCELLED 决定了 future 析构的时机。REMOTE/LOCAL 这类来源标记看似多余，实则关键：当计数降到零需要释放任务时，如果最后一个持有者是远端线程，释放路径要做跨线程的所有权移交，把内存送回创建它的线程去回收，从而避免分配器内部的全局锁竞争。这也解释了为什么许多实现宁愿在原子字里多塞几个比特，也不引入独立锁。顺带一提，任务头字段在缓存线上的排布确实会影响性能，但布局优化与伪共享分析属于内存布局的专门话题，本文只在位段合并这一处点到为止。

值得强调的是”合并位段”的动机不是为了炫技，而是因为任务生命周期上的合法迁移组合是少量且可枚举的。调度器在入队、出队、开始 poll、poll 返回、结果被取走、Drop（丢弃）这几处做状态转换，每一次转换都是对同一个原子字的读-改-写。位段拆得越细，非法状态组合就越多，实现就越容易在边界上出错；把强相关的比特合并，本质是在用状态机约束换正确性。

Waker 协议：唤醒的三动作与引用配平

Waker 是运行时的神经末梢。它的契约只有三个动作：clone 复制一份句柄、wake 唤醒并消耗自己、wake_by_ref 唤醒但保留自己。语义上，调用任意一个 wake 的效果是”让与我绑定的任务重新可调度”，且契约允许唤醒被合并——一个任务在入队后尚未被 poll 之前被多次 wake，运行时只需保证它最终会被再 poll 一次，无需一次 wake 一次 poll。这个合并语义是调度器能安全地”只看队列不看 wake 次数”的前提。

实现上，Waker 内部是一个裸指针加一张 vtable，指针指向任务头，vtable 里的 wake 函数从这个裸指针出发做两件事：把任务标记为 RUNNABLE，并把它推进某个调度队列。关键在于裸指针必须保证任务在它存活期间不被释放——这就引出运行时里最精妙的一段配合：waker 计数与任务引用计数的配平。

每当要构造一个 Waker 交给 future（进而可能被 future 存进某个 IO 驱动、定时器或 channel 的内部），运行时对任务引用计数施加一次”加 waker”性质的增量。于是形成一条铁律：只要世界上还有一个存活的 waker，任务本体就不会被释放。反过来，当 future 已经返回 Ready、外部 JoinHandle（加入句柄）也已取走结果或已 Drop，任务引用降到只剩”那些还没被消费、也没被调用的 waker”，任务会进入一种”已死但还被引用”的状态：future 已析构，内存还在，等最后一个 waker drop 或被调用，运行时才知道”再也没人等这个任务了”，才做最终释放。如果被调用的那个 waker 发现任务早已完成，wake 路径就是空操作——只把引用配平减掉，不入队。

为什么非要等最后一个 waker drop 才算”彻底没人等”？因为 waker 的裸指针随时可能被解引用。如果任务在完成的那一刻就释放，而某个定时器里还存着它的 waker，到期时解引用就是悬垂指针，程序会以极难复现的方式崩溃。用”waker 持有一份强引用”换来的是：唤醒路径永远安全，代价只是内存晚一点回收。这一段的另一面是取消：任务被 drop 之后 future 何时析构、.await 点上的取消安全语义，另有一篇《Rust 异步取消与取消安全》专门处理，本文只在生命周期层面与之衔接一句。

还有一个容易被忽视的细节：waker 的”可唤醒”性质是 once 的。契约不保证一次 wake 之后任务一定会跑到哪一步，只保证会再 poll。因此 future 内部的写法必须是”每次返回 Pending 前，确认已经有某个持有者答应在未来 wake 我”。这句话的分量，我们在下一节讲 poll 路径时展开。

poll 一次任务的完整路径

把镜头拉到一个 worker 线程上，看它取到一个任务后的完整旅程。

第一步，从队列取出任务句柄，对任务头做状态检查：尝试把”已在队列、未被执行”迁移为”正在执行”。这次原子操作如果失败，说明任务被并发改写（比如刚被取消，或已被别的线程抢走执行权），直接放弃、回到取任务循环。这次检查就是前面 SCHEDULING 位的价值：它保证了每个任务的 poll 串行性。

第二步，构造 Context。Context 本身很薄，主要就装一个指向任务头的 waker。运行时会在这里按需生成一个 waker 并计数（或复用任务上缓存的 waker，视实现策略而定）。然后把这个 Context 的引用交给那个类型擦除后的 poll 入口。

第三步，真正调用 future 的 poll。控制权回到用户代码：状态机从上次的 .await 点继续，可能读一段 buffer（缓冲区）、可能检查定时器、可能向 IO 驱动登记兴趣、可能返回 Ready。整个过程不阻塞线程——除非用户代码里藏了同步阻塞调用，那是另一种错误，我们放到阻塞池一节再谈。

第四步，根据返回值决定任务去向。Ready 意味着 future 彻底完成：把结果搬进任务头的结果槽，置 COMPLETED，唤醒还在等 JoinHandle 的一方（如果有），然后走释放路径——但如前所述，任务内存不一定此刻回收，它可能还要等那些悬挂的 waker。Pending 则把任务交还给调度器：不重新入队。对，Pending 不排回队列，因为契约规定：返回 Pending 的那一刻，future 必须已经保证会有 wake。如果 Pending 之后没有任何持有者承诺唤醒，任务就永远躺在”已 poll 完、不再可调度”的状态里。

这条契约值得单独说透，因为违反它的症状极具迷惑性。它不会报错、不会 panic、不会有任何日志——程序只是在那里”不动了”。一个 tick 循环少注册了一个 waker，表现为界面卡在某帧；一个自旋条件判断里”如果没就绪就返回 Pending”却没先把兴趣登记给被等待方，表现为某个任务永远等待。调试这类挂死，唯一可靠的线索是”这个任务最后一次 poll 返回了 Pending，而此刻 IO 驱动、定时器、channel 里都没有它的登记”。所以实现 future 的铁律是：返回 Pending 之前，唤醒责任必须已经转移出去——要么转移给了 reactor（反应堆）的就绪登记表，要么转移给定时器，要么转移给某个 channel 的等待队列。

契约的另一半同样重要：wake 之后 future 必须可被再次 poll，且实现要能在”被虚假唤醒”（spurious wakeup）下保持正确——事件到达未必意味着你等的条件成立。主流库之所以把注册唤醒责任封装在 AsyncRead/AsyncWrite 或 select! 宏里，就是为了让人少有机会写错这一层。

调度队列与工作窃取

任务被 wake 之后要进队列，队列策略决定了这台运行时的性格。主流多线程实现普遍采用”全局队列 + 每 worker 本地队列”的多级结构，思路近似操作系统里的多级反馈队列：短任务在本地快速周转，长任务与积压任务在全局层面重新分配。

本地队列常见实现是一个 LIFO（后进先出）的槽式栈而非 FIFO（先进先出）队列。为什么？局部性。刚 wake 的任务往往是当前任务链的下一环——它复用的缓存行、它要读的 buffer 大概率还在同一个核的缓存里。LIFO 让这类”热”任务第一时间被同一线程接手。代价是公平性：持续自我 wake 的任务会霸占栈顶，让栈底的冷任务饿死。成熟实现于是引入交替机制：本地栈消费到一定深度或发现积压后，转而按 FIFO 顺序批量喂给某个 worker；也有实现周期性地把本地积压的一半整体挂到全局队列，让别的线程来分担。无论哪种形态，本质都是”LIFO 保吞吐、FIFO 保公平”的折中。

工作窃取（work stealing）解决”有线程闲、有线程忙”的失衡。空闲 worker 先翻自己的本地队列，再翻全局队列，最后随机挑一个别的 worker 试图从其队列尾部偷任务。随机化是关键：如果所有空闲线程都按固定顺序偷同一个”最忙”的线程，它们会排成一队争抢同一批任务，彼此制造同步竞争，这就是操作系统领域的 convoy（护航队）效应——一群人堵在同一扇门后，而别的门开着。随机采样把争抢摊开。窃取还要处理另一个问题：被偷走的任务原本的数据分布在这个线程的缓存里，跨线程执行必然冷启动。所以窃取粒度通常是”一批”而不是”一个”，摊薄迁移成本。

队列之外还有”任务间插队”的语义。协作式调度里，没有抢占点，一个持续返回 Pending 且不断自我 wake 的长任务能把 worker 榨干。yield_now 一类原语给的答案是”主动让位”：它 poll 时不完成任何事，只把自己重新排回队列的合适位置（常见是本地积压那一侧），从而把执行权交还给调度器。它不是睡眠、不涉及定时器，纯粹是队列纪律。理解了这一点，也就理解了为什么它不能救那些”一个 poll 里跑了两毫秒纯计算”的任务——那种情况下任务从未 Pending，让位无从谈起。

定时器：时间轮与最小堆的取舍

运行时如何管理”三万年后（误）在 50 毫秒后醒来”的三万个 sleep？只有两条主流路线：最小堆（或最小堆变体）与分层时间轮（hierarchical timing wheel）。

最小堆的做法是把所有待到期定时器按绝对到期时间放进一棵堆，worker 只需看堆顶：还没到期就带超时地等事件，到期就批量弹出到期集合、逐个唤醒。优势是实现简单、精确度高、条目数少时开销低；劣势是每次插入与弹出都是 O(log n)，当负载是”大量短定时器”时，日志因子和堆数组的随机访问模式会让缓存表现变差，且到期检查的抖动相对明显。

分层时间轮把时间轴切成一格一格的槽，每槽挂一串到期于该时间窗的定时器；轮子按 tick（滴答）前进，指针走到哪一格就唤醒那一格的条目；超过本层跨度的定时器交给更高一层的轮子，低层绕完一圈就把高层的条目”降级”灌下来。优势是插入与到期摊到 O(1)，海量短定时器下吞吐优秀；劣势是精度受限于 tick 粒度，且降级与跨层管理带来实现复杂度。工程上常见混合策略：把定时器按剩余时间分成”近期集”（排序的小窗口，精度敏感）与”远期集”（粗粒度时间轮），近期集逐条检查、远期集批量降级，兼顾抖动与吞吐。

这段清单的要点不在复杂度记号本身，而在”抖动特征”四个字。堆的到期时刻由条目自身时间决定，误差小；时间轮的到期时刻被量化到格点上，误差在 [0, tick)。如果你的应用对定时精度敏感（比如令牌桶限速），tick 选大了会造成可观测的批量脉冲；如果你的应用是海量超时检测（比如连接空闲回收），量化误差无所谓，吞吐才是主角。

timer 与 waker 的结合路径值得走一遍：sleep 对象的 future 第一次被 poll 时，检查截止时间，若未到期就向运行时登记”到期时请用这个 waker 唤醒我”，然后返回 Pending；到期唤醒路径把任务重新入队；第二次 poll 时再看时间，已过期，返回 Ready。这里有个容易被忽略的并发细节：如果 poll 检查时间与登记唤醒之间，定时器恰好到期，唤醒会丢失吗？成熟实现会在登记后再核对一次状态，或者让登记函数在”已到期”时直接同步完成唤醒责任——这正是前面那条”返回 Pending 前唤醒责任必须已转移”契约的具体落地。至于时钟粒度：worker 对 OS 等待的超时、时间轮的 tick、sleep 内部是否合并唤醒（多个 sleep 指向同一轮检查），都会影响”很多短 sleep”的实际开销，这些参数一般通过运行时构建参数暴露，默认值随版本调整，以当期文档为准。

IO 驱动：reactor 如何把事件变成唤醒

本节只讲到”IO 驱动如何唤醒任务”这一层；reactor 与 AsyncRead/AsyncWrite 的契约细节归同期的《Rust 异步 IO 模型解析》，本文不展开。

运行时的 IO 侧通常由一个 reactor 统管：它持有所有注册过的 fd（文件描述符），底层对应 OS 的多路复用机制（Linux 上是 epoll，其他平台有 kqueue、io_uring 或 WSAPoll 一类的等价物），并维护”fd → 哪些任务在等它的可读/可写”的映射。路径大致是：任务 poll 时向 socket 状态对象登记”我关心可读”，socket 状态对象再向 reactor 登记兴趣，登记时把自己的 waker 交出去；worker 线程之一（或每 worker 各自，视形态）阻塞在事件获取上；内核报告某 fd 可读，reactor 在映射里找到该兴趣条目，取出 waker 调用 wake；任务重新入队，下一次 poll 时读取数据。

为什么运行时要把”socket 就绪状态”与”future 的等待状态”分成两层各存一份？因为就绪是边沿或水平事件，等待是一次任务关系。一个 fd 可读时，可能同时有多个任务在等它，也可能一个任务同时关心可读与可写，事件与任务不是简单一一对应。把”这个 fd 现在 ready 与否”缓存为 socket 状态上的比特，把”谁在等”缓存为注册记录，reactor 收到事件时只需置比特、唤醒登记持有者，具体 future 醒来后从状态比特判断自己是否真能动。这层分离还让”ready 事件不等于读完写完”这个缝隙有了归属：事件到来可能只表示”可以读”，实际读出来可能是部分数据、可能是 WouldBlock（本会阻塞）——这个差距由 socket 状态层消化，而不是让 reactor 去猜。

顺带一句与线程模型相关的细节：有些运行时的实现里事件获取在每个 worker 上各做一次并共享内核就绪视图，有些则集中一个驱动线程。前者的唤醒更贴近消费任务的线程、少一次跨线程移交，后者事件循环简单。这是工程取舍，没有普适的对错，本文不给数字结论。

阻塞池：为什么 spawn_blocking 必须存在

协作式调度有一个死穴：worker 线程数量有限且被假定为”永不长时间占用”。一个 future 里如果调用了同步的文件读、阻塞的数据库客户端、或一段耗时纯计算，这个 worker 就被吃掉了——它不返回 Pending，调度器无从把执行权拿走。轻则其他任务延迟，重则整个运行时饿死。spawn_blocking（生成阻塞任务）是对这个死穴的制度性回答：把注定阻塞的闭包丢给一组专职线程，future 那边只持有一个”等待结果”的挂起点，不占 worker。

阻塞池的经典结构是”线程数上限 + 无界或有界队列”。上限的意义是给 OS 的线程资源一个边界，超出上限的提交排进队列；队列的形态决定背压：有界队列在满载时拒绝提交，让调用方感知压力；无界队列则把压力藏起来，直到内存告警。具体上限与策略都通过运行时构建参数配置，默认值随版本调整，以当期文档为准——本文不对任何默认数字下断言。与它相邻的是 block_in_place 一类的取舍：当”当前 worker 上只剩这一个任务、且任务本身已经等不及”时，允许就地阻塞、并把该 worker 的剩余队列委托给其他线程接管。这条路避免了把大数组搬进闭包的成本，代价是实现要在调度层做线程接管，语义复杂，只适合”明确知道没有别的任务会饿”的场景。

阻塞池还有一项不起眼的价值是可观测性：线程命名。当池里的线程叫得出”block-in-place worker”之类的名字时，top、htop、perf 采样和 OS 级监控一眼能分辨 worker 与阻塞线程；反之如果全是匿名线程，故障排查时”CPU 卡在哪个池里”要靠猜。同理，某些平台上的 CPU 亲和性配置能把 worker 钉在指定核上换取缓存局部性，但这是拿调优自由换稳定性，默认实现通常不做硬性绑核——本文只描述这一取舍的存在，不推荐任何具体数值。

单线程运行时与多线程运行时

同一套任务结构可以跑在两种形态上：单 worker 的多级队列形态与多 worker 的窃取形态。它们在任务布局上的差别比想象中小，但语义差别很大。

单线程运行时的任务集就是本地那一个队列，没有窃取、没有全局队列的争抢、没有跨线程移交计数的复杂度——任务头的原子操作可以退化，waker 的跨线程唤醒则必须通过”把任务塞回那个唯一队列”的方式安全移交。因为不存在并发 poll，Future 无需 Send（可发送）：任何借用非线程安全上下文（Rc（引用计数指针）、RefCell（借用检查的单元格）、OS 句柄借用）的 future 都能 spawn。这也是为什么测试里偏爱单线程形态——.await 点上的 !Send 值不再让编译器报错，且执行是完全确定的：没有窃取、没有乱序、没有竞态，挂死与逻辑错误的复现极其稳定。代价当然只有一个核。

多线程运行时的任务布局则要为”任务可能在不同线程间迁移”做准备：future 必须 Send + 'static（借用不能跨线程逃逸），任务头要带上前面说的来源标记与远程计数字段，调度路径要处理”在别的线程上被 wake”的移交。两种形态的任务体结构其实一致——差别在于哪些字段会被真的用到、哪些原子操作可以省。也因此有些运行时在单线程模式下会走一条几乎无锁的快速路径：waker 克隆与计数走”本地廉价”分支，定时器集中在轮询点检查，队列就是一个 Vec（动态数组）当栈用。

选择口径不需要性能数字：如果你的并发单元是大量短任务且吃满多核，用多线程形态；如果你要写的是带 !Send 借用状态的流程、或者要的是可复现的测试执行序，单线程形态是正解。两种形态都正确，别用形态差异来掩盖策略差异。

关停语义：为什么优雅关停这么难

关停一台异步运行时的目标看似简单：”不再接受新任务，把在途任务跑完，回收资源。”实现过它的都知道这是整台机器上最难的部分。难点来自三处。

第一，正在 poll 的任务不可打断。协作式调度没有抢占点，关停信号到达时某线程可能正处于用户 future 的 poll 中间，你不能在这一刻 drop 它的 future——那会把用户代码在 .await 点上的所有不变量撕碎。正确做法是等这次 poll 自然返回。于是关停必须分两阶段：先进入”拒收”状态，所有 spawn 返回失败，调度器停止接受入队；再排空——已入队的任务照常执行完，执行完后发现队列空且全员空闲，才真正拆掉资源。

第二，悬挂的 waker。前面讲过，只要还有一个 waker 存活，任务就不会释放。排空阶段所有 future 都已进入终态，但 IO 驱动的登记表、定时器的轮槽里可能还存着它们的 waker。这些登记关系本身也是运行时资源，拆它们的顺序与排空必须协同：先停 IO 驱动与定时器、让它们把持有的唤醒责任就地兑现或作废，再检查任务集合是否清零。顺序错了，要么泄漏内存，要么在已经拆了一半的结构上触发唤醒。

第三，shutdown 之后的 wake 行为。任务已经全部结束、运行时已经拒收时，一个迟到的 wake 应该发生什么？正确答案是”什么都不能发生”：唤醒路径必须在检查到终态后只把引用计数配平减掉，不入队、不重建任何东西。成熟实现会专门对这条路径做断言测试——故意让某个 timer 或 channel 持有 waker 活到关停之后，再触发它，验证进程不崩、计数归零。

给生产环境的建议由此推出：不要把关停当成设计的一部分。具体口径是：给每个任务一个”关停信号 + 超时”的模式，任务内部自己处理退出；让关停超时显著小于编排系统发给你的宽限期，否则 SIGTERM 之后等不来的是内核的 SIGKILL（强杀信号），它不给运行时任何拆结构的机会。

观测与调试：怎么看出运行时坏了

前十一节的机制最终都要落到”出了问题怎么看”。运行时的可观测性与它的调度模型一样是协作式的：它不主动报错，只把状态摆在那里等你查。本节只给方法与判读口径，不给任何数字结论。

先看任务泄漏。判据不是内存曲线而是”账目差值”：运行时通常能报出累计 spawn 成功数与累计完成数（含正常完成与取消），两者的差值就是当前在途任务数。健康服务的在途数应该在负载波动后回落到基线；如果它单调爬升，每一段爬升都对应一批”进去就没出来”的任务。把在途任务按 spawn 点或任务名分桶，爬升基本会收敛到一两个桶，那桶里的 future 十有八九违反了前面讲的契约——返回 Pending 却没把唤醒责任转移出去。第二个信号是这些任务对应的内存不回收：因为 future 还活着，它 .await 点上暂存的所有中间数据都活着，一个挂着十万个僵尸任务的接口能把 RSS（常驻内存集）慢慢顶穿。

再看长 poll。协作式调度下，单个任务在一次 poll 里霸占 worker 太久，不会被抢走，症状链条是：某 worker 的本地队列积压开始增长，全局队列开始被其他 worker 偷空，但它自己始终有活干不完。排查方法与内存剖析同构——周期性采样 worker 线程的栈，看有没有线程长时间停在用户 future 的计算里而不是 poll 入口附近；也可以在自己的代码里给可疑的 poll 段加计时日志。判读口径是”队列积压与单线程占用同涨”：如果只是总量高，那是容量问题；如果积压集中在个别 worker 且它们的 CPU 占用饱和，才怀疑任务独占。此时解法要么把纯计算挪进阻塞池，要么在循环里补 yield_now 一类的让位点，而不是加 worker 数量——加线程只会让更多队列排队。

任务命名与结构化日志的落点也值得说。多数运行时允许给任务挂一个调试名（或从 #[tokio::main] 之类入口的字段派生），运行时 dump 在途任务时会带上它。好的命名粒度是”每种 spawn 一个静态名字”，坏的做法是把请求 ID 塞进名字——那会让 dump 的聚合统计碎成一万个小桶。日志侧，把”任务被 wake””任务 poll 返回 Pending”这类事件留在 trace 级并按任务 ID 结构化，才有办法事后重建某任务的唤醒履历，回答”它到底是被谁唤醒的、最后一次为什么没醒”。所有观测都有观察者效应，高频事件日志在生产上默认关，压测与故障复现时再开。

小结

回到开头那句话：async fn 不会自己跑。把它跑起来的机器，拆开看是一套围绕 Poll::Pending 的严肃簿记——任务头用合并位段维护状态与计数，waker 用一份强引用给唤醒路径买保险，”返回 Pending 前转移唤醒责任”是全系统最硬的一条契约，调度器用本地 LIFO 与随机窃取在吞吐与公平之间走钢丝，定时器在堆与时间轮之间按负载画像选边，reactor 把内核事件翻译成同一条 wake 路径，阻塞池为协作式调度无法抢占的死穴兜底，关停用两阶段状态机体面地收摊。诊断一台运行时坏了，方法也早已蕴含在这些机制里：数在途任务的差值、看单 worker 的积压、重建某个任务的唤醒履历。机制讲到这里，剩下的篇幅在源码里——建议读者挑一个主流运行时，从它的任务结构体定义开始读，把本文每个小节与它逐一对照。
