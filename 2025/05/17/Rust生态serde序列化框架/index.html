Rust 生态：serde 序列化框架

本文属于《Rust 学习路线》第 43/68 篇
上一篇系列目录下一篇

本文面向已经写过 Rust 结构体、正在与接口 JSON 或配置文件打交道的读者，回答三个问题：serde 为什么拆成框架与格式适配器两层，derive 属性各自解决什么，格式切换与解析报错时按什么顺序排查。读完应能设计一组跟随前后端演进的数据结构，并知道何时停止用属性、开始手写实现。

两层结构：框架与格式适配器

serde 这个名字取自 serialization 与 deserialization。它把一次转换拆成两段：框架侧定义数据模型（data model），也就是结构体有哪些具名字段、枚举是哪个变体带着什么内容、一个值是可选的还是 null；格式侧的适配器（format）把这套抽象落成字节或文本，反向亦然。

Serialize 只管一个方向：按数据模型的顺序告诉对方“我要写一个有若干字段的结构体”，它不关心自己在写 JSON 还是二进制。Deserialize 管另一个方向，并多出一个生命周期参数 'de，因为结果可能直接借用输入缓冲区的字节而不拷贝。

flowchart LR
    A[你的 Rust 类型] --> B[derive 生成的实现]
    B --> C[serde 数据模型]
    C --> D[JSON 适配器]
    C --> E[配置文件适配器]
    C --> F[二进制适配器]

解耦的好处是类型定义只写一次：任何格式只要能表达结构体、可选值、映射、枚举，就能挂进这个体系。序列化真正难的地方不是转义引号，而是同一份语义要在多种表示之间保持一致——接口 JSON、内部二进制、人手维护的 TOML 都得对上同一个类型。类型一旦混进格式知识，每次换格式都得改类型。

协议之间的横向比较另有专文，本文只讲 Rust 侧的类型建模；Go 的结构体标签（struct tag）是另一种语言里同类问题的解法，本文只作一句对照。

derive 属性族总览

起点是这一行 derive：

#[serde(...)] 属性分两种作用域：容器属性写在结构体或枚举上，影响整个类型的行为；字段属性写在某一条字段上，只影响这一条边。deny_unknown_fields 是容器属性，flatten 是字段属性，同名属性未必两种作用域都支持。

另有三个属性值得单说。transparent 让新类型（newtype）包装在数据里回到裸值，bound 用于收紧泛型边界，with 把一条边委托出去、其余仍交给 derive，是性价比最高的一个。derive 宏本身怎么造出来属于另一篇，本文只讲怎么用。

与外部契约对齐

字段命名要先做全局决策。Rust 字段习惯 snake case，Web 接口主流用 camel case。省事的做法不是逐字段写 rename，而是在容器上声明一次策略；要兼容旧拼法时用 alias 登记旧名，输出仍只用主名。策略必须全项目统一，否则批量策略与手写改名并存，可读性就退化成人肉记忆。

可选字段有三种必须区分开的语义，把它们混成一谈是很多线上故障的根因。下面三个对象分别代表缺失、显式 null 与空值。

缺失是这条边没出现在映射里，显式 null 是对方明确表达了无值，空值是有值但内容为空。Option<T> 只分有与无，默认行为下缺失和 null 都得到 None；要区分“没传”与“传了空”就让类型套两层。对方从不发 null 时配上 skip_serializing_if。

deny_unknown_fields 在契约演进里是一把双刃剑。它把拼错的字段名、放错层级的对象立刻变成一次失败，在人维护的配置里价值极高；代价是把“对方加字段”从兼容变更变成破坏性变更，上游先发新字段，开了开关的下游就全量报错。分工建议：消费外部接口时默认不加，读自己维护的配置时开启严格模式。

枚举的四种表示形态

Rust 枚举的表达能力远强于多数数据格式，serde 为此提供四种映射方式。

外部标签（externally tagged）是默认形态，枚举值被包成只含一个键的对象，键就是变体名：

内部标签（internally tagged）用 tag 切换，变体名进入表示内部，成为映射里的普通字段：

它的硬约束是表示本身必须是映射，所以单元变体和只有一个新类型字段的变体会在编译期直接报出来，对策是每个变体都带具名字段。相邻标签（adjacently tagged）用 tag 加 content，标签与内容做兄弟，它绕开了形状要求，代价是多出一层 content：

无标签（untagged）只写 untagged，序列化时直接写内层值：

它最贴近历史接口，也最容易出问题：反序列化按变体顺序逐个尝试，第一个形状吻合的就赢，排在前面的宽变体会吃掉后面的准变体；全部尝试失败时只说没有变体匹配，不说在哪个字段失败，排查时只能临时换回外部标签。建议默认形态不动，契约明确要求才切换。

自定义序列化与新类型模式

属性覆盖不到才手写实现。骨架是一段固定对话：序列化方向告诉对方要写一个有 k 个字段的结构体并逐条报值；反序列化方向建一个访问者（visitor），在回调里把键值攒起来。

两个方向的生命周期问题性质不同。Serialize 的方法只有一个类型参数，&self 在调用期间存在即可，实现可以任意借用字段；Deserialize 的 'de 是数据来源的存活期，把缓冲区字节直接交给结果对象，结果就借用了输入，想让值自己拥有数据、能跨线程移动，用 DeserializeOwned。

取舍标准是：改动只在一条边上就用 with 委托一个导出 serialize 与 deserialize 的模块，所有边都要改才手写 trait，且手写之后 rename、default、deny_unknown_fields 得在访问者里手工补。

孤儿规则（orphan rule）是另一种必须手写的情形：类型和 trait 都不属于你，就不能在别人的 crate 里为别人的类型实现别人的 trait，此时包一层新类型。

transparent 让包装类型在数据里完全隐形，而 Rust 侧仍有独立类型可以挂实现与校验，一步绕开孤儿规则与多出一层对象。

换格式不动类型定义

换格式只需换调用侧的适配器，这是两层结构最直接的回报。

差异不在写法，而在各自能表达数据模型的哪一部分。JSON 与多数文本格式以字段名为键，rename、alias、deny_unknown_fields 只在它们身上有意义。TOML 与 YAML 对映射支持很好，但表达 null 和混合形状数组不如 JSON 自由；人写的配置里数字写法就可能改变推断，所以配置类型要显式标注字段类型。二进制不做名字映射，按字段顺序写字节：改名不改变字节，调整顺序直接破坏兼容性，真正影响布局的是 skip。

因此与格式无关的语义写进属性，与格式有关的约束（顺序是否敏感、null 怎么表达）记在注释里。框架与各适配器当时都在自己的主线上，选型看格式对枚举与可选值的支持程度而非版本号，库的评估口径不在本文展开。

配置解析时的错误定位

解析失败的信息质量决定运维成本。只有一句 invalid type: string, expected a sequence 的报错，在几百行配置面前几乎无法定位。路径要自己拼：serde 的错误属于数据模型层，它知道当前在处理哪个键，但适配器不保证把嵌套路径传上来，server.tls.port 这种点号路径要由读配置的一层组装。错误类型怎么定义与传播另有专文，本文只谈解析错误该带什么信息。

第一步是把格式层的定位翻成人话：文本适配器通常在错误对象上给出行列号，可以直接和文件名拼在一起。

这一版只有行列、给不出字段路径，因为路径在默认 derive 实现里已被丢掉。拿回路径有两条路：嵌套结构逐层解析，每层只负责自己那一段，失败时把段名插到 path 前面再往上抛；或者在手写访问者里把当前键记进状态，类型不符时用 de::Error::custom 生成带键名的错误。原则只有一个：错误必须能回答“改哪一行”。

第二步是把解析、校验、缺省分三层，不要搅在一起。

形状解析层里出现业务判断，是配置报错难读的头号原因；判断挪到第二层，第一层的错误才能长得一样、可被工具解析。

性能与取舍的正确姿势

先说最常见的误用：把整份数据先解析成通用值（serde_json::Value 这类运行时树），再逐行手工取字段。代价有三层。一是临时对象，每个字符串、每个数字都要先装箱成一棵堆上的树再取出转换，直接反序列化到结构体时一个都不需要。二是失败发现时机被推迟，形状不合法的地方要到取用时才炸。三是类型丢失，编译器不再检查字段名拼错这类问题，而让错误停在编译期恰恰是 serde 最大的价值。

方向性取舍比数字重要。决定一次解析快慢的因素依次是：要不要拷贝字节、要不要为字段名做字符串比较、要不要分配。二进制省掉字段名查找，文本必须在映射里比对键；借用输入省掉拷贝，但缓冲区要活得更久。

大文件的思路有三档。逐条记录：把一份文件看成同一个类型重复出现，用适配器的流式解析逐个产出值，内存里始终只有一条。延迟解析：外层类型先定好，把体积最大、多数请求不需要的那段用原始片段接住，等下游需要时再解析。借用：结果直接引用输入缓冲区，代价是生命周期要一路传下去。

属性层的对应工具是 deserialize_with，可以把某一条边的解析推迟、或换成只接原始片段，对字段很大但很少访问的形状很有效。反过来先解析成 Value 再交给 from_value 转成结构体，是让数据在运行时树上过一遍又重新反序列化一次，属于最不该写的组合。本文不列对比数字：离开具体格式与数据形状，任何倍数都没有参考价值。

常见坑清单

读错误信息是第一个技能。serde 的报错句式基本固定：invalid type: X, expected Y，或者 invalid length。X 是数据里实际出现的形状，Y 是 Rust 类型要求的形状。看到 invalid type: string, expected u64，先怀疑对方把数字序列化成了字符串；看到 missing field，先想这条边是不是被 skip_deserializing 吃掉了。

第二个坑是 skip 与 default 混用导致往返（round trip）不等。

被 skip 的字段在数据里消失，反序列化时字段无法构造就直接编译不过，于是很多代码顺手补上 default，结果读回的值与原值不相等：内存里曾有过的内容从未进入数据，在配置回写与消息重放里就是静默丢失。原则是：skip 只用于本可重建的派生状态；要保留但允许缺省就用 default；只读输出用 skip_deserializing 并声明它不可回写。

第三类坑是数值边界。数据里写 1.0、字段是 u32 就是 invalid type: floating point，反过来写 1 给 f64 通常被接受。大整数更麻烦：JSON 数字在 JavaScript 侧按双精度浮点存储，超出精确范围会静默失真，所以 u64 与前端交互要么约定用字符串传，要么显式用一个转换模块处理这条边。

第四个坑是空字符串与缺字段：表单把没填发成空字符串，Option<String> 的 None 判断永远不成立，要么在入口把空串归一为 None，要么让类型本身区分三态。第五个坑是 flatten 与 deny_unknown_fields 冲突：摊平的映射就是其余全部字段的容器，严格模式又要拒绝任何未定义的键，两者同时声明会让代码报错，只能取其一。

小结

本文的主线是两层结构：数据模型与字节表示解耦，类型定义只写一次，格式细节留给适配器。derive 属性按容器与字段两种作用域组织，枚举的四种标签形态决定数据里的形状；超出属性能力时先试 with 模块与新类型包装，再考虑手写 trait。配置场景要把字段路径与行列号补进错误，并把解析、校验、缺省分三层。
