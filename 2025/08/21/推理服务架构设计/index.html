推理服务架构设计

为什么需要分层

大模型推理服务的特殊现实是内部引擎变化极快。引擎实现、模型版本、并行策略几乎每季度都在换，而调用方——业务前端、智能体（Agent）编排器、批处理作业——发出的请求形态却应当多年保持稳定。分层的意义就是把”对外契约稳定”与”对内快速变化”拆开，把变化关在靠下的层里：一层换实现时，上层仍遵守同一份契约。不分层，一次引擎升级会拖着请求参数、错误语义、流式格式全链条改，最后没人敢升级。

本文讨论的五层结构如下：接入与网关管对外契约；调度与路由回答”这次请求交给谁”；引擎实例负责算出 token；模型与权重存储把正确的权重送到正确的实例上；观测与计量横跨各层，把内部状态翻译成可核对的信号。

flowchart TD
    A[调用方] --> B[接入与网关层]
    B --> C[调度与路由层]
    C --> D[引擎实例层]
    D --> E[模型与权重存储层]
    F[观测与计量] -.采集.-> B
    F -.采集.-> C
    F -.采集.-> D
    F -.采集.-> E

层与层之间靠契约说话：请求模式、错误语义、取消传播、流式帧格式、就绪状态。边界画错的代价是具体的——把路由决策塞进引擎，它就成了谁都不敢动的黑盒；把计费逻辑散在两层，对账永远对不平。兼容层差异、断连处置、计费对账等落地细节归《大模型推理服务化实践》，本文只画层与契约。

网关层：只做可预期的控制

网关（Gateway）是对外契约的唯一持有者，职责清单应当克制：鉴权与租户识别，把令牌换算成内部身份与租户标识；协议归一（Protocol Normalization），把各家引擎 API 在参数命名、流式帧、错误码上的差异收敛到一套内部契约；限流与配额，按租户与接口控制进入系统的请求量；请求改写，做长度截断与结构化输出（Structured Output）的参数映射；以及把调用方的取消信号正确下传，而不是等引擎算完了才发现没人要结果。

网关有一条必须钉死的红线：不做推理决策。选哪个实例、排队还是拒绝、是否切换备用模型，都属于调度的领域；网关只做可预期的控制——给定同样的输入，必然得到同样的放行或拒绝结果。一旦网关开始”看情况转发”，排查问题就要跨越两层假设，定位成本成倍增加。其内部如何设计归《模型服务网关设计》，本文只确定它在分层中的位置：契约的守门人，而不是大脑。

调度与路由层：这次交给谁

调度与路由（Router / Scheduler）回答：这个请求现在给哪个实例。职责有四组。其一，按模型与版本选择实例池——同一套服务常同时存在多个模型与版本，池子要先选对。其二，按请求特征分桶：输入长度、是否带工具调用（Tool Call）、能否命中缓存、在线还是离线，混在一起会互相拖累。其三，排队与优先级，明确谁是交互式请求、谁可以让路。其四，抢占与重试的边界：什么情况下允许腾出低优先级请求、重试由谁发起，这些决策必须发生在这一层并被记录。

路由必须知道实例当前能不能接，这就是就绪四态：进程存活、模型已加载、预热完成、可接流量。只检查”进程活着”的健康检查是事故源头——刚加载完权重、第一批请求还在触发内核编译与缓存初始化的实例，看着健康，实际第一波全慢；预热完成应作为健康检查里的显式状态。伸缩信号与排水归《推理服务的弹性伸缩》，本文只衔接一句：就绪四态同时是伸缩决策的输入。

引擎层的边界

引擎（Inference Engine）管的是单实例内部的事：连续批处理（Continuous Batching）如何组织、显存如何分配、采样如何执行。它不该管的两件事同样明确：租户与计费。引擎看到的应当是”一批已分给它的请求”，这批请求来自哪个租户、值多少钱是上层的事；让引擎认识租户，等于把商业策略编译进一个每季度更换的实现里。

跨层最容易画错的两条边界都在这里。其一，把排队策略放进引擎：引擎内部悄悄维护私有等待队列，上层以为请求已在处理，实际排在引擎里——这段等待不可观测，超时归因全部失真，策略藏在没人负责的地方；排队应当显式留在调度层，引擎只接收准入后的请求。其二，把 KV 相关参数散落在网关配置里：网关的作者不懂参数语义，引擎的作者改不动它们，最后无人负责。机制的公式与原理本文不重讲，以《大模型推理优化：KV Cache 与 PagedAttention》为准。

存储与模型分发层

存储层回答两个问题：权重从哪里来、怎么到达实例。来源应当是单一可审计的仓库，分发要么由实例按需拉取，要么在启动前预热同步。最难设计的是扩容瞬间：上百个实例同时拉取同一份权重时，源站被雪崩式请求打垮，扩容反而比故障更慢。常见做法有两种：镜像化，把权重烘进容器镜像或只读缓存层，随镜像分发天然分摊；共享缓存，在节点层建权重缓存，把同一节点的百次拉取收敛为一次。关键是让”重复拉取”收敛为”一次拉取”。

版本与校验不能省：每份权重记录按内容计算的哈希摘要（Digest）与来源，由实例加载前核对，数值由流水线生成，绝不能手抄进文档。权重属于敏感资产：不进日志、不进外部缓存、临时副本用完即清理。配置文件与密钥要分域：配置域放泄漏了尚可公开的项，密钥域放泄漏了必须立即轮换的项，混放是密钥进日志的最常见原因。

流式协议的选择

推理服务要持续吐 token，常见的四种承载各有所适。SSE（Server-Sent Events，服务器发送事件）基于 HTTP 单向推送，贴合服务端连续产出，穿透大多数代理，是稳妥默认。WebSocket 双向，适合持续回传工具结果或中间状态的场景，但带来一套连接管理义务。分块 HTTP（Transfer-Encoding: chunked）最简单，却没有事件帧边界，客户端解析容易出错。RPC 流（例如 gRPC streaming）适合内部服务间的层间调用，跨浏览器生态时要费劲。

流式让两件事变难。一是幂等：流已被对端消费一部分，不能简单重放整个响应；断连之后”重试”与”续传”是两种语义，契约必须写明支持哪一种。二是背压（Backpressure）：客户端不收时，服务端要不要继续生成？生成就是计算成本，生产没人接收的流就是白付成本，契约应写明”持续不收则停止生成并释放资源”。中间代理是现实约束：负载均衡、API 网关、企业代理都可能因空闲超时切断长连接，表现为”流戛然而止且没有报错”，这是常见事故源，心跳与空闲超时的逐层配置是架构层义务；断连后的具体处置是运维议题，本文只登记为契约项。

幂等、超时与预算的分层

请求级幂等（Idempotency）键用来判断”这是不是同一个请求的重试”。设计有一条红线：键里不能含用户敏感原文。标识一旦由原文派生，日志、缓存、监控都会顺着键把它扩散出去，脱敏永远追不上复制；应使用内容摘要值，或调用方独立发放、本身不携带语义的标识。

超时要作为预算逐层下发，而不是各层各自拍一个数字。粗粒度关系是：总预算 = 排队 + 首 token + 生成 + 重试余量。若每层只有固定超时，一定会出现网关已断开、引擎还在为无人接收的连接继续生成。下面的分配数值为团队约定示例，不是行业标准：

多模型与灰度

一套服务承载多模型与版本有三种形态。按请求指定：调用方显式传模型名，灵活，但把版本选择的知识压给业务方。按租户绑定：路由表决定哪个租户用哪个模型，集中，但租户迁移要走变更流程。按策略路由：按流量比例、请求特征或成本约束在候选模型间选择，最强也最容易失控——无论哪种，规则都必须存放在可集中审计的地方。

灰度（Canary Release）按两种单位切：按租户，试点范围清晰、反馈容易归因；按流量分桶，用一致性哈希让同一会话稳定落在同一版本。灰度开关唯一的硬性要求是能一键回退：切换必须是集中路由规则的一次修改，而不是”手工慢慢降量”。AB 的观测口径必须与离线评测一致，否则灰度结论无法使用。模型退役最易漏掉的是衍生资产一致性：嵌入（Embedding）与索引不与模型同步换代，就会出现旧索引配新模型的错配。

可观测点清单

可观测性（Observability）是把每层的内部状态翻译成可核对的信号，三条原则先于任何工具选型。命名统一：同一概念在每层用同一字段名，别一层叫 queue 另一层叫 pending。trace 贯穿：链路标识（Trace ID）由网关生成并必须传到引擎，任取一个请求都能看到排队、首 token、生成的完整时间线。指标低基数（Cardinality）：不要把模型的完整输入输出当标签，长度分桶或哈希分桶已经够用。以下清单可直接抄，字段名为约定示例：

失败模式与降级路径

每类故障都该有写进契约的默认行为，而不是靠值班同学临场判断。引擎全忙：交互式请求在预算内排队并暴露深度，超预算快速失败，离线流量走独立的池。目标模型不可用：降级顺序是同池换版本、备用模型、纯检索式回答或致歉，换模型是调度层的决策。上游取消：立即停止生成并释放。缓存不可用：必须有穿透保护。下表按场景、现象、期望、禁忌整理：

引擎全忙 排队变长、首 token 变慢 预算内排队并暴露深度，超预算快速失败 静默无限排队
模型不可用 指定模型名持续报错 路由层降级到备用版本或模型 让网关临场猜模型

安全与合规边界

以下每层一句，展开各归其文。网关层：请求携带的外部内容——网页抓取、工具返回、上下文引用——一律按不可信输入（Untrusted Input）对待，边界划定与注入防护机制详见注入防护专文。检索与调度链路：越权召回的防线必须设在检索阶段，无权限的内容根本不能进入提示词，靠生成层”别说出来”不算边界。存储层：权重与密钥分域、审计可查。观测层：脱敏、留存期与访问控制前置设计。合规时间线上：EU AI Act 对通用人工智能（General-Purpose AI）的义务自 2025 年 8 月已经适用；国内《人工智能生成合成内容标识办法》已公布、即将施行，生成内容加标识的义务即将到来，架构上先预留元数据字段是稳妥做法，条款解读不在本文范围。

小结

本文的立场可以压缩成三句话。第一，分层不是为了优雅，而是为了把”引擎每季度都在变”与”调用方多年不该变”解耦，契约是变化的缓冲区。第二，每层的价值大半体现在它拒绝做什么：网关不做推理决策，引擎不认识租户，排队不许藏进私有队列，KV 参数不许散落在网关配置。第三，就绪四态、预算下发、取消传播、脱敏与最小必要，都是写进契约的架构义务，而不是运维阶段再补的经验。把层画清、把边界守住，之后换成什么引擎、什么模型，服务都还是同一个服务。
