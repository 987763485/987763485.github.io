推理服务的弹性伸缩

本文面向已经用熟了 Kubernetes 水平伸缩、如今要为大模型推理服务做弹性伸缩（Auto Scaling）的工程师与平台团队。它要解决的问题只有一个：为什么把 CPU 或内存水位当成伸缩信号在推理服务上会失效，该换成什么信号，以及伸缩这个动作本身要付出哪些代价。读完之后，你会得到一套从就绪判定、指标选择、缩容排水到演练验证的落地视角，而不是一句”照抄 Web 服务的配置”。

普通 HPA 的三个前提，为什么在推理服务上集体失效

水平伸缩（Horizontal Pod Autoscaling，HPA）这套机制我们用了多年，默认它可靠，是因为它建立在三个几乎从不被拿出来审视的前提之上。通用的伸缩原理与 HPA、垂直伸缩（Vertical Pod Autoscaling，VPA）的机制在往期《HPA 与 VPA 实战》一文里已经讲透，本文只讨论大模型推理服务给这三条前提带来的冲击。

第一个前提：负载指标与容量近似线性。Web 服务里，一个实例每秒处理的请求数大致是个常数，中央处理器（Central Processing Unit，CPU）打到某个水位就代表快满了，于是”利用率翻倍、实例数翻倍”是成立的。推理服务的处理时间却由输出长度主导：同样一条请求，生成几十个 token 和生成上千个 token 占用的时长能差一个数量级，而且这个差别在伸缩那一刻是不可知的。请求数与容量之间不是一条直线，而是一团跟着长度分布来回摆动的云。

第二个前提：扩容出来的新实例几乎立刻可以服务。Web 进程从启动到接流量通常以秒计，就绪探针（readiness probe）亮绿灯的速度远快于伸缩循环的周期。推理服务要把体量巨大的权重从存储读进来、把显存（GPU memory / VRAM）分配到位、把计算图编译并预热，然后才谈得上接第一个真实请求。伸缩”决定扩容”和”新实例真正可用”之间，隔着一段不可忽略的冷启动（cold start）过程。

第三个前提：缩容丢掉的只是少量在途请求，无关紧要。Web 请求短，删一个容器组（Pod）顶多掐断几个正在处理的连接，客户端重试即可。推理服务的一个请求可能是一条持续很久的流式生成，直接删 Pod 会把这条已经吐了一半的流生生切断，用户侧看到的是回答戛然而止。缩容的代价因此从”丢几个请求”升级成”打断一批长连接”。

把这三条失效摆在一起，就得到本文要一路回答的问题清单。

冷启动：起一个 Pod 不等于能接流量

编排器把一个 Pod 调度到节点上、进程跑起来、健康检查（liveness probe）通过，这些都只说明”进程活着”，离”能接流量”还差着一整段路。对推理服务来说，这段路主要由四件事构成。

其一是权重读取。模型参数通常体量很大，从本地盘、对象存储或分布式缓存里把它拉到内存、再搬到显存，是整个冷启动里最重的一块，快慢取决于权重体积、存储带宽和节点缓存是否命中。同一个节点第二次加载往往快得多，因为权重已在本地缓存——这一点会直接影响伸缩时把新实例往哪些节点放。

其二是显存分配与常驻结构搭建。推理引擎要在显存里为模型参数、运行时缓冲和 KV 缓存（KV Cache）预留空间；预留是一次性完成还是按需增长、按什么策略增长，决定了实例是”开起来就能满负荷”，还是”边服务边扩张、扩张时抖动”。

其三是图编译与内核准备。不少引擎在真正服务前要做算子融合、编译或内核选择。这一步不做完，第一批请求会又慢又不稳，把它们放到流量里，等于让线上最早的用户替我们编译。

其四是预热本身。即便前三步完成，第一批真实请求仍然偏慢：形状各异的输入第一次走到某条执行路径上，会触发惰性初始化。预热的意义，就是把这些”第一次”的代价用可控的假请求提前付掉。

所以一个负责任的预热要主动走完服务里会出现的主要输入形状：覆盖几档典型长度、跑够足以触发各分支的条数、把编译产物与缓存填满，并观察内部指标稳定下来之后，才对外亮绿灯。下面这份就绪条件清单，把”进程活着”到”可接流量”拆成四个必须分别判定的状态。

把这四个态分开，价值在于伸缩决策可以只对接流量这一态负责：伸缩在统计可用副本时，应当只计入 ReadyToServe 通过的实例，否则会把还在预热的实例误算进容量，得出”已经够了”的错误结论，进而少扩。反过来，预热完成前的实例必须被流量入口挡在外面，避免刚起来的慢请求污染首 token 等待时间这类尾部指标。这里要提醒的是，”起新实例”这件事在多机分片场景里会进一步复杂化——一个实例可能不再是一个 Pod，而是一组 Pod 整体就绪，这一点放到后面单独讲。

容量不由 CPU 决定：显存、并发与长度分布

推理服务能同时接多少请求，不由 CPU 或内存水位说了算。真正决定容量的是两个量的乘积：同时驻留在实例里的序列数，乘以每条序列占用的状态。前者是并发在跑的请求个数，后者主要是 KV 缓存占用，而它随序列长度增长。把这两者相乘，得到的是一副”以显存为墙”的容量画像：墙不是固定的，序列越长、每块砖越大，能在墙里站下的人就越少。

于是输入与输出长度分布，成了容量最大的扰动源。同样标称”能跑若干条并发”的实例，当来的是短问短答时可能绰绰有余，当来的是长上下文检索或长篇生成时，显存很快见底。这就解释了一个反直觉现象：两个时段观测到的请求数几乎相同，并发压力却天差地别——因为请求数只数了”进来几条”，没数”每条占多久的墙”。用请求数或每秒请求数（Queries Per Second，QPS）当伸缩信号，等于用”进了多少人”去判断”旅馆还住得住吗”，而真正要紧的是”有多少张床被长期占用”。

正因为容量画像长这样，我们该盯的信号也从 CPU 转向三类：显存水位与 KV 占用率（墙还剩多少）、等待队列深度（门外排了多长一队）、以及抢占次数（为了腾地方，把在跑的序列中途踢出去了多少回）。抢占是一个特别值得单独告警的信号——它意味着系统已经在用牺牲已完成工作的代价换容量，是容量见底之后才会出现的现象。KV 缓存本身如何分页管理、占用率怎么算，是同期《大模型推理优化：KV Cache 与 PagedAttention》那篇的主题，本文只把它的占用率当作一个伸缩信号来用，不重讲机制。

伸缩信号的选择与防抖

选定了信号，还得规定每个信号在什么时候该升、升了怎么判、以及怎么防止它骗人。下面逐个说清楚”该升的时候升、误报来自哪里、要怎么平滑”。

队列深度：该升的时候升，是当实例已经满负荷、新请求开始排队而不是被立即接受时，队列随负载增长是健康的扩容前兆。它的误报来自瞬时尖峰——一阵突发流量把队列顶起来又迅速回落，如果伸缩跟着这个尖峰扩容，多半会扩多。平滑办法是看一段时间的队列趋势或移动平均，而不是单点值。

首 token 等待时间（Time To First Token，TTFT）：一个新请求从进入到吐出第一个 token 的等待。它升高，说明请求在系统里等待资源的时间变长，是容量吃紧的领先信号。误报来自个别超长输入的请求把单次测量拉高，以及冷启动实例还没预热就接到了流量。建议用分位数而非均值（下面单独讲），并且只统计已经过预热的实例。

单位时间完成 token 数：整个服务在一秒里吐出的 token 总量，是真实的产出吞吐。当它逼近平台期、再加实例也不再上升，而延迟却持续恶化，说明瓶颈已经从容量转到了别处。误报来自输出长度分布漂移——完成 token 数上升，可能只是因为大家这次要的答案更长，并不代表实例更忙。用它当信号时，要和请求数、长度分布一起看。

显存水位与 KV 占用率：衡量离容量之墙还有多远。它升高意味着快满，是扩容的直接依据；它的下限则指导缩容——占用长期很低才敢减副本。误报来自预留策略：一次性预留一大块的实例，空闲时水位看着也高。要在读数里区分”已用”和”已预留未用”两部分。

超时率：请求因等待过久而被判定失败的比例。它升高是容量已经追不上需求的确认信号，属于该立刻响应的类型；但它同时是最该谨慎对待的信号——低超时不代表可以缩容，只代表还没到悬崖边。

为什么一律用分位数而不是均值。均值会被长尾拉平：一批发短的请求可以把一个卡住的长请求的等待，从统计里稀释掉，让服务看起来”平均没问题”，而真实体验是尾部一片哀嚎。伸缩要看的是 P90、P95 这一档的恶化，因为容量吃紧最先体现在尾部。把均值当阈值，等于亲手把最该报警的信号抹平。

缩容排水：最容易被写坏的一步

缩容是这篇里动作最危险的一步，也是最常被写成”直接删 Pod”的一步。前面说过，推理服务的一个请求可能是一条持续很久的流式生成，如果在它还在吐 token 时把承载它的实例删掉，用户侧看到的就是回答毫无征兆地断在半路。这不是丢一两个请求的问题，而是把”正在给你答案”变成”答案没了”，体验上是硬伤。所以缩容必须排水（draining），而且要按正确的顺序排。

顺序是这样四步。第一步，先把这个实例从流量入口摘出去：关闭它的就绪状态，让路由层不再把新请求分给它。这里有个容易忽略的细节——摘出流量不是瞬时的，服务发现与转发规则的收敛有延迟，所以要在真正开始排空之前，留出一小段等待，让”不再进新请求”这件事在所有链路上生效。第二步，停止接受新请求，让已经在途的流式请求自然跑到结束，一条生成都别打断。第三步，给排水设一个最长等待上限：不能无限等，否则一两个超长生成会把整个缩容卡死，伸缩循环里堆积一堆”正在排空中”的实例，反而制造抖动。第四步，只有当在途清空、或触及最长上限之后，才允许发出终止信号。

这里要把两个 Kubernetes 语义说清楚。preStop 钩子是在容器被终止之前执行的一段逻辑，前面这套”摘流量、等路由收敛、排空在途”的动作就应当放在它里面做，让编排器替我们把”终止前先排水”这件事变成声明式。优雅终止时长（terminationGracePeriodSeconds）则是一个实例从收到终止信号到被强制终止之间的宽限上限。二者的关系要配套：优雅终止时长必须比我们的排水上限留得更宽裕一些，否则编排器会在我们还没排完在途请求时，就先越过排水逻辑把进程强制收掉，前面一切都白做。

现实里最棘手的是”长生成请求让排水迟迟不结束”。有些请求就是会跑到很久，如果坚持”等它自然结束”，缩容可能永远收不了尾。可行的处理是给上限设一个足够覆盖典型生成分布、但又不至于无限的值；到点仍有残留时，不是放任，而是主动做一次优雅收尾——通知客户端、把可续的状态落到检查点或降级返回，然后才终止。核心取舍是：宁可牺牲极少数超长请求的完整性，也不能让整个缩容停摆。下面这段伪代码把上面的顺序固化下来。

伸缩粒度、最小副本与”0 副本”陷阱

伸缩的第一个设计决定是”一次动几个副本”和”最少留几个副本”。很多从 Web 服务迁移过来的团队会顺手把最小副本设成 0，指望靠缩到零来省成本。对推理服务来说，这几乎总是坏主意，原因有二。其一是冷启动代价：缩到零意味着下一个请求要重新付一遍权重读取、显存分配与预热的钱，第一个用户等的是一个完整的冷启动，这在延迟上是不可接受的。其二是依赖抖动放大：冷启动期实例既占存储带宽又占节点资源，一旦流量稍有起伏就反复”缩到零—再拉起”，会把这种重加载的抖动放大到整个集群，反而制造更差的可观测曲线。

至于模型该落在哪种机房、哪类硬件上，属于同期《大模型私有化部署方案》那篇的部署议题，本文只在伸缩信号层面承接它给出的结果，不展开机房选型。

最小副本该定多少，正确的思路不是”最少要几个才够跑”，而是”我愿意承担多大的冷启动风险”。最小副本本质上是一份”随时待命的容量保险”：留得越少越省，但遭遇突发时要付出冷启动的等待。这里给一份团队约定示例，数值需按自己的冷启动时长与流量波动实测确定。

多模型、多版本共存时，副本分配还要再加一层考虑。每个模型都有自己独立的显存墙和长度分布，把它们混在同一个伸缩池里用一个全局信号调节，会让最”重”的模型长期霸占容量、把轻模型饿死。合理做法是按模型或版本切分独立的伸缩单元，各自用自己的队列与水位做决策，再在顶层设一个共享资源上限，防止某一路把总盘子吃干。灰度发布时新旧版本并存的这段时间，两套副本都要保住排水能力，别让”给新版本腾地方”变成”把老版本的在途请求一刀切”。

预测式扩容与节奏控制

被动地等信号超标再扩，对推理服务往往太晚——因为扩容要付预热这段时间。等到队列已经堆起来才触发扩容，新实例还在加载权重，等它能接流量时，那波请求早就超时了。于是我们需要预测式与定时手段，把扩容决策提前到负载真正到来之前。

按业务日历做定时扩容，是最朴素也最可靠的一种。如果流量每天在固定时段抬升——比如工作日白天，或某个定时批处理任务之后——就让伸缩在抬升点之前提前把热实例备好。这类”形状可预知”的负载，定时扩容比任何算法都稳。

纯预测则容易翻车。预测模型学的是历史规律，而推理服务的负载常被不可预期的因素打破：一次外部事件、一段突然流行的长文本、一个上游把调用方接了进来。预测一旦偏低，因为要付冷启动，实际容量会更长时间落后于需求；预测偏高，则长期空置、成本白白挂着。所以合理架构是定时或预测打底、实时信号纠偏——预测负责把基线抬高，实时队列与水位负责在预测出错时把多余的扩掉、把不足的补上，两者互为保险。

节奏控制解决的是”抖动连环扩缩”问题。伸缩最怕在阈值附近反复横跳：负载在临界点上下小幅波动，就触发一次扩、回落触发一次缩、再波动再扩……每一次动作都要付预热的代价，最后系统忙于伸缩而无暇服务。两个手段专治此症。滞回（hysteresis）让扩容阈值和缩容阈值之间留一段空白带：越过上沿才扩，跌破下沿才缩，落在带里则保持不动，避免临界抖动被放大。冷却窗口（cooldown）规定两次同向动作之间的最小间隔，给刚扩出来的实例留出预热与观察的时间，不让策略在上一次动作还没见效时就急着做下一次。

最后是把”伸缩动作代价”计入策略。既然一次扩容要付一段预热时间，那阈值就不能卡在”刚好满”的位置，而要提前——在容量真正见底之前若干身位就触发，给预热留出处置时间。同理，缩容也留缓冲，别贴着一瞬间的低谷就砍副本。一句话：推理服务的伸缩，是要把”动作本身有延迟”这件事，反推回阈值设定里的。

多机分片：伸缩单元从 Pod 变成一个组

当单张设备装不下一个模型，就要把它切开分散到多张卡、甚至多台机器上。常见的两种切法：张量并行（Tensor Parallelism）把每一层的计算矩阵横向分给多张卡在同一步里协同完成，流水线并行（Pipeline Parallelism）把不同的层串成几段、像流水线一样接力。无论哪种，一个逻辑上的”推理实例”从此不再等于一个 Pod，而是一组必须协同工作的 Pod。伸缩单元从”个”变成”组”，带来一连串后果。

第一是整体就绪。这一组里只要还有一块分片没加载完、没预热完，整个实例就不能接流量——它是”与”的关系，不是”或”。所以前面那套四态就绪判定，要在组的维度上再做一次”全组都 ReadyToServe 才算数”的汇总，任何一个分片拖后腿，整组都不许进流量。第二是整体排水。缩容时不能拆着排：只排掉某一分片，剩下的分片会立刻失去协作对象，崩断在途请求。排水要以组为单位，先把整组摘出流量，再等整组在途跑完。第三是故障域变大。一个 Pod 挂掉，过去只损失一个实例；现在损失的是它所属的整组，一个分片的故障会连累一组。副本的容错预算，因此要按”组”来算。

分片还带来一个只需讲方向、不必给定值的开销：分得越细，单卡上的计算压力越小，但分片之间为同步与传递中间结果付出的通信越多。张量并行尤其敏感，因为它要求多卡在每一步里频繁交换数据，一旦交换的相对成本压过计算收益，继续加分片就是负收益。这也是为什么分片数不是越大越好，而要按自己的模型与硬件实测找拐点。

跨机分片把这个矛盾进一步放大到网络层面。当分片分布在不同机器上，分片间通信就要走机间网络，此时伸缩的前提变成一组网络假设：带宽要足够、延迟要足够低且稳定、拓扑上要尽量让同一组的分片落在彼此靠近的位置。运维上这意味着跨机分片的实例更该绑在一起调度、共享同一条网络与故障边界，也要把机间链路当作伸缩里最该盯的隐性瓶颈——很多”容量明明够、延迟却恶化”的现象，根子就在分片通信上。

调度约束：把伸缩落到放得下的地方

伸缩决定”要几个实例”，但能不能真的扩出来，还要看调度器有没有地方放它们。推理服务对”放在哪”远比 Web 服务挑剔，这构成对伸缩的一组硬约束；而调度器内部如何打分、如何绑定节点这些机制，属于往期《Kubernetes 调度器》那篇的主题，本文只讲伸缩侧需要向它提的要求与要做的取舍。

第一类约束是设备类型。模型往往对加速器有硬性偏好：显存容量够不够装下这副权重与 KV 缓存、是不是所需的型号、有没有对应的运行时支持，都是”放不放得下”的前提。伸缩必须把这些当作筛选条件，否则会出现”副本数想扩、但集群里没有满足条件的空位”，扩了个寂寞。

第二类约束是拓扑。多机分片的实例要求它的几块分片彼此靠近——同机、同交换机下或同可用区内，因为分片间通信对延迟和带宽敏感。NUMA 亲和（Non-Uniform Memory Access，非一致内存访问）则是机内层面的同类问题：让进程与其常驻内存落在靠近的处理单元上，能减少跨节点的访存代价。伸缩一旦把一组分片散放到拓扑远端，性能会悄悄劣化却不报错，是最难排查的一类问题。

第三类是抢占与配额。加速器是稀缺资源，当高优先级服务容量告紧要扩容、而集群已满，就需要抢占：把低优先级负载腾出去给在线服务让路。抢占对伸缩是把双刃剑——它保证在线扩容能被满足，但也意味着你的实例可能被更高优先级的东西抢走。配额则划定了每个团队或每个模型最多能占用的资源上界，是伸缩不能突破的天花板，也是成本治理的抓手。

还有一条容易被滥用的捷径是共享设备：把多张卡或一块卡切给多个实例共用，想靠它提高利用率。它适用的边界很窄——只适合负载轻、对延迟不敏感、彼此干扰可控的场景。一旦在线服务对尾延迟敏感，共享带来的隔离不足会让首 token 等待时间的尾部剧烈抖动，因为邻居实例的突发会挤占同一块设备的显存带宽与算力。这种”平时没事、一忙就崩”的行为，恰恰是伸缩最难调的信号来源。所以共享设备在推理服务的在线通路上要格外克制，宁可留独占，把共享留给确实能容忍干扰的负载。

混部与潮汐：用离线任务填谷

加速器贵，而在线推理的负载是有峰谷的——白天挤、深夜闲。于是有了一个自然的想法：把离线批任务（比如批量重跑、数据生成、离线索引构建）和在线服务混布在同一批设备上，在线低谷时用闲着的容量跑离线，等在线起来再把容量还给在线。这就是所谓的填谷，或潮汐式混部。离线任务与在线服务在同一资源池里如何编排、离线队列如何调度，是同期《大模型批处理与调度》那篇的主题，本文只谈它对伸缩提出的三点风险。

第一点是抢占代价要算清。填谷的前提是”在线一起来，离线就让路”，而让路靠抢占离线任务实现。可如果一个离线批任务跑了很久才被抢占、之前的算力全打了水漂，那填谷省下的那点容量，可能不够赔被浪费的离线工作。所以只有可中断、能断点续跑的离线任务才适合拿来填谷，一跑到底不能停的反而添乱。

第二点是在线延迟保障。混部里最凶的坑，是离线任务在在线毫不知情时把设备带宽或显存吃满，让在线请求的首 token 等待悄悄恶化。要填谷，就得给在线留一条”无论离线多忙都抢得回来”的资源底线，并把在线信号（队列、水位、首 token 等待分位数）当成压制离线的闸门：在线一告紧，立刻限住或踢掉离线，而不是等在线超时了才反应。

第三点是显存碎片。在线与离线交替占用同一块显存，容易把可用空间切得七零八落——总量看着够，却凑不出一块能服务下一个长序列的连续空间，触发不必要的抢占或扩容。混部的容量水位评估要把碎片算进去，别只看”已用总量”这一个数。填谷是好事，但它把两种截然不同的负载绑进了同一个伸缩决策，任何一路信号失真，都会让混部从”省钱”变成”互相拖累”。

成本与责任的治理

弹性伸缩最容易带来的副作用，是把成本问题藏起来。它给人一种”系统会自己调节、不必我操心”的安全感，于是没有人再去看账单背后的形状。但对推理服务来说，成本的大头往往不在单张设备的单价，而在峰谷的形状：为了扛住一天里那几个小时的峰值，你得让一整批实例要么热着待命、要么随时能在冷启动之后拉起；低谷时它们闲置，成本却持续发生。自动伸缩会把这种”为峰值买单”的结构忠实地放大——它按信号把副本数顶到峰值水位，却不负责回答”这个峰值值不值得为它常备这么多热实例”。

所以伸缩策略必须和一套治理绑在一起，至少包含三件东西。其一是预算护栏：给伸缩能达到的资源上界设一条不能自动突破的红线，越过它就停止扩容并转为告警，而不是任由信号把集群一路撑大。这条红线通常由配额承载。其二是审批：当某个服务要调整最小副本、扩容上限或阈值这类会显著改变成本曲线的参数时，要有一个明确的人来批准，而不是谁都能随手改一行配置就把常驻容量翻倍。其三是触发上限：对单位时间内的伸缩动作次数设上限，防止失控的策略在故障或异常信号下连环扩容，把成本在一次抖动里推到离谱的位置。

责任也要落到人。每个走自动伸缩的服务，都该有一个看得懂它的伸缩曲线、并对它的成本与延迟同时负责的归属方；否则就会出现”只管扩不管钱、只管省不管炸”的三不管地带。把护栏、审批、上限这三件连同归属一起写进策略，伸缩才既自动又可控。

上线之前：观测、回放与演练

一套伸缩策略在纸面上看着合理，上线却常常翻车，因为它的行为只在”负载×信号×动作延迟”三者耦合时才暴露。要验证它，不必拿真实流量冒险，可以分三层递进。

第一层是离线回放。把历史的负载曲线——请求到达与长度分布随时间的变化——喂给一个能模拟副本数、冷启动延迟与排水过程的模型，看策略在这条曲线上会产生多少次伸缩、每次动作是否来得及、排水会不会拖太久。回放的目的是先排掉明显的”抖成一团”和”永远追不上”的策略，成本最低。

第二层是影子环境。用与生产同构但相互隔离的环境，接上被镜像的真实流量做只读验证，观察伸缩决策与排水行为，而不影响线上用户。它能暴露回放模型没建模到的东西，比如调度器到底放不放得下、机间网络的真实抖动。

第三层是主动演练。在可控窗口里人为触发一次扩容和一次缩容，专门检验”排水是不是真的无损”：缩容时在途流式请求有没有被硬切断、有没有请求触到排水上限被优雅收尾、冷启动的新实例有没有把首 token 等待拖高。演练是唯一能证实”无损排水”这件事真实存在的手段，不能省。

下面是必须长期盯的四个伸缩侧指标，它们直接刻画策略健康度。伸缩动作次数：单位时间内扩与缩各发生了几回，次数异常偏高几乎总是抖动。误扩率：扩出来后很快又缩掉的占比，衡量信号有多少在骗你。排水超时次数：缩容时因触及最长等待上限而不得不优雅收尾的频次，偏高说明负载里长生成太多、排水窗口设得不合适。冷启动请求占比：有多少请求被还没预热的实例接到，它直接对应”用户替我们付冷启动代价”的比例。

配合一张流程图，把从采集到终止的闭环画清楚，演练时照着它核对每一步是否被触发即可。

  B --> C{扩容还是缩容}
  C -->|扩容| D[申请新实例]

  E --> F[置为可接流量]

演练前用一份 checklist 逐项确认，能避免”演练当天才发现缺东西”。

信号适用性对照总表

把前面散落的判断收成一张表，方便选型时一眼对照。它回答三个问题：这个信号能不能用作推理服务的伸缩依据、它在什么时候会骗人、以及用它的同时必须配哪道防抖。

信号 是否适用于推理服务 误报来源 建议用法 必须配套的防抖
CPU / 内存 基本不适用，仅旁证 计算压在加速器上时 CPU 很低，内存反映不了显存墙 只用来排除”卡在 CPU 或主存”这类非容量问题 不进伸缩主决策
请求数 / QPS 有限适用 不反映输出长度与并发占用 结合长度分布做粗判 分位数化 + 移动平均
队列深度 适用，扩容领先信号 瞬时突发顶起又迅速回落 看移动平均趋势而非单点 移动平均 + 冷却窗口
首 token 等待 适用，容量吃紧领先信号 个别超长请求、未预热实例污染 取 P95，只统计已就绪实例 只计就绪 + 窗口平滑

读这张表要抓一个要点：真正适合当主信号的是队列深度、首 token 等待、显存/KV 占用、完成 token 速率这一组”贴着容量走”的指标；CPU、内存和裸请求数只能退居旁证。而每一个主信号都必须自带防抖，否则推理服务特有的长尾与尖峰，会把自动伸缩变成一台抖动发生器。

小结

本文的出发点是：大模型推理服务的伸缩和普通 Web 服务不是一回事。水平伸缩赖以成立的三条前提——指标与容量线性、新实例即刻可服务、缩容只丢少量请求——在推理服务上集体失效，因为容量由”同时驻留序列数×每序列状态占用”决定、起一个 Pod 离能接流量之间隔着权重加载与预热、而一次缩容打断的是一条条长流式生成。这三条失效，就是全文一路回答的问题清单。

沿着这张清单，我们给出了对应的落地姿态：用四态就绪把”能接流量”和”进程活着”分开，只让已过预热的实例计入可用容量；用队列深度、首 token 等待分位数、显存/KV 占用、完成 token 速率替代 CPU 水位做信号，并给每个信号配好误报来源与防抖；缩容务必先摘流量、再等排空、设最长上限、才允许终止，并把 preStop 与优雅终止时长配套；最小副本按”可容忍的冷启动风险”来定、慎用缩到零；用定时与预测打底、滞回与冷却窗口控节奏，并把”动作本身要付预热”这件事反推回阈值。多机分片让伸缩单元从 Pod 变成一个组，要整体就绪、整体排水；调度、配额与共享设备划定了伸缩能否落地的边界；混部填谷能省钱，却把两路负载绑进同一个决策，任何一路信号失真都会互相拖累。

还有两件事贯穿始终。其一，伸缩不是纯技术动作，它需要预算护栏、审批与触发上限的治理来兜底，把成本从被藏起来的状态拽回台面——真正要治理的不是单价，而是峰谷形状。其二，任何策略上线前都应经过离线回放、影子环境和主动演练三层验证，再用伸缩动作次数、误扩率、排水超时次数、冷启动请求占比这四个指标去证伪它。本文所有量级都写成示意值或”你要自己测的口径”，因为推理服务的伸缩参数没有普适数字，只能在你的负载形状上标定。
