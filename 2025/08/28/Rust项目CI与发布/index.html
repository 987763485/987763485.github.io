Rust 项目 CI 与发布

本文属于《Rust 学习路线》第 26/68 篇
上一篇系列目录下一篇

仓库长大之后，最先失控的往往不是代码，而是”改一处、坏三处”的隐性成本。本文面向要给 Rust 项目立流水线的维护者：按问题类别给持续集成（Continuous Integration，下称 CI）分层，用最低支持版本与目标矩阵把兼容性变成可验证的承诺，并说明发布为什么必须保留人工约束。

先定目标：CI 不是”全跑一遍”

流水线的第一个设计决定不是用哪台主机，而是要回答哪几类问题。正确性（correctness）问给定输入下逻辑是否给出期望结果，由单元测试（unit test）、集成测试（integration test）与属性测试（property-based testing）回答；兼容性与可编译性（compatibility 与 buildability）问在公开承诺的 Rust 版本与系统组合上是否还编得出来，由双版本编译、多目标构建与配置组合（feature）矩阵回答；分发可安装性（installability）问产物能否真的装上、跑起来，且在法律与安全上是否可接受，由产物构建、许可证门禁与安全通告（security advisory）扫描回答。

分层的依据是每一类问题能在多短的时间内被回答：反馈周期由关键路径上最慢的作业决定，所以成本最低的检查不该塞进需要完整编译的作业。代价是分层带来重复，判断重复值不值得的标准是失败归因是否更清晰。

工具链与目标矩阵

工具链层面最重要的一条实践，是在仓库里放一份工具链声明文件，让本地开发、CI 与文档构建取到同一套编译器与组件。它把通道、组件与目标从口头约定变成受版本控制的资产，解决的正是”我本地能编”这类最难查的失败：编译器版本、组件缺失、目标未安装的表现完全相同。代价是每次改通道都要显式提交并触发完整回归。

稳定通道（stable）与每夜通道（nightly）要提前分工：主体跑在稳定通道，nightly 只用于确实依赖未稳定能力的场景。理由是它的失败经常来自上游变动而不是你的代码，全仓库被反复染红后团队就学会忽略红色信号。折中办法是保留一个 nightly 作业，只提示、不阻断合并。

目标矩阵（target matrix）的原则只有一条：只覆盖真实用户平台。做法是从下载统计与主动给你打包的发行版维护者那里收集组合，让每一条都能回答”它服务谁”。代价是矩阵宽度直接乘以编译次数，各平台在链接器与系统库上的差异还会引入偶发失败。交叉编译（cross compilation）只讲方向：某些平台必须由厂商工具链或容器化环境补齐链接环境，把”准备环境”与”执行编译”拆成两步，能让这类失败先暴露。

MSRV：把兼容性写成可验证的承诺

最低支持 Rust 版本（MSRV，Minimum Supported Rust Version）是”这个版本及以上的编译器我能编”的公开承诺，必须显式写进文档与配置，而不是”最新版能编就行”。理由有三：用户因合规审查或发行版冻结长期停在旧版本，节奏与作者天然解耦；不声明等于把决策权交给”这台机器恰好装了什么”，问题只在下游暴露；只有声明了才能被验证并在被破坏时报警。

CI 要同时回答”用 MSRV 能编吗”与”用当前稳定版能编吗”，所以这是两个作业，而不是一个作业跑两遍全量。

这样设的原因是 MSRV 作业的结论只关乎能否编译，把测试塞进去会让兼容性问题伪装成测试失败。代价是两个作业都触达依赖解析，此时要分清是自己的代码不兼容还是依赖的兼容窗口变了。edition（版本口径）同属 MSRV 的一部分，例如 2024 edition 随 1.85 于 2025 年 2 月 20 日进入稳定通道，切换它会同时抬高下限。

依赖升级与 MSRV 是连带关系：上游某个 crate 抬高它的下限，你在锁文件（lockfile）保护下暂时感觉不到，重新解析时就会被顶上去。稳妥做法是把”忽略锁文件、解析到最新可用版本再编译”设成一个允许失败、不阻断合并的独立作业，用来提前发现上游兼容窗口的变化；代价是它会因无关的传递依赖变化而偶尔变红。

判定口径要说清：MSRV 变更是破坏性变更（breaking change）的一种。只要公开声明里写了 MSRV，抬高它就让原本能够构建你这个 crate 的用户不再能够构建，这是用户可感知的能力损失，语义化版本（Semantic Versioning）意义上的处理是随主版本一起走，而不是塞进一次补丁发布。唯一值得宽容的例外是为了修复必须升级依赖才能解决的安全问题，此时仍要在变更日志里显著标注。

格式与静态检查门禁

格式检查与 lint（静态检查）应该单列在最前面，理由不是它们重要而是它们便宜：cargo fmt --check 与静态检查不需要产出可执行产物，失败原因又与业务逻辑无关，放在关键路径入口能挡住一批本不该进入昂贵作业的提交。

这张清单的价值在于每一项都能独立重跑，失败归因不与其他作业混淆。代价是它们都要触达编译器前端，重复劳动会占用主机时长；配置组合只能抽样，抽哪几种必须由人显式决定。

规则的严格程度要用时间换：新规则先以警告（warn）落地，给出整改期，期限内只报告不阻断，到期后升级为阻断（deny）。一刀切全部阻断的后果是历史违规让每个 PR 都变红，于是作者学会的第一件事是在文件顶部加一行豁免注释——门禁还在跑，却不再传达任何信息。

测试分层

四类测试各抓不同的东西。单元测试抓函数内部的边界与漏支；集成测试抓序列化与并发这类只有组合起来才暴露的问题；属性测试（property-based testing）抓作者没想到的输入，适合解析器、编码转换这类有明确不变量的代码；文档测试（doc test）抓示例是不是已经过期，它是唯一能验证对外用法的机制。

并行与分片的必要性来自单作业时长。测试默认按 CPU 并行，但总量增长到拖慢反馈时，应按用例耗时分片横向铺开。慢测试要显式标记并隔离到独立作业：关键作业里混进一个很长的用例之后，所有人都相信这个作业本该跑这么久，新引入的慢测试就此被掩盖。

内存检查手段（例如 miri 一类的动态检查工具）只用于不安全代码的正确性检查，代价很高，因此只在特定作业里跑。它检查未定义行为而非逻辑对错，覆盖面取决于测试是否走到那条路径，当作通用门禁容易给出虚假安全感。

覆盖率只当参考、不当门禁：它衡量的是代码被执行过，不衡量断言是否有效；一旦把百分比设成门槛，团队第一反应就是补没有断言的调用。可行的做法是看趋势与缺口位置，把低覆盖模块当作评审提示。

依赖治理与审计门禁

依赖数量要当成 CI 检查项，因为它不是风格问题而是风险敞口：每个直接依赖都带来一份传递依赖树、一组许可证。可以设一个只做计数的作业，让”这次 PR 又加了一批 crate”这个事实在评审里被看见。

工具分工比选哪个工具更重要。cargo tree 回答依赖图长什么样，用来找重复依赖与同一 crate 的多版本共存；cargo deny 类工具回答许可证与来源是否符合政策；cargo audit 类工具回答有没有已公开的安全通告。三者结论不同，混用就会出现拿安全扫描器管许可证的事。选库阶段的评估归同期《Rust 生态 crates 推荐》一文，本篇只讲引入之后的门禁：

这五个问题没有自动答案，只要求出现在提交说明或评审记录里；代价是引入变慢，换来依赖图不至于失控。

许可证与安全审计要写成一等公民的策略。结构通常是三份：允许列表、禁用列表、例外记录。例外要逐条记录理由，并把这条理由当作一份架构决策记录（Architecture Decision Record，ADR）提交进仓库，注明涉及依赖与复审时点——审计的红与绿本身不含上下文，半年后没人记得某个例外为何被批准。代价是维护成本落在人身上，例外一多就像没有策略。

通告检查会因为数据库更新而误报。处理办法不是关掉它，而是给它单独的通知渠道，让它进入待办而不阻塞合并；同时保留一个阻断性质，即新增或升级依赖时引入的通告不允许带病合入。至于”CI 红了却不知道是谁引入的”，要靠锁文件定位：把失败的提交与上一次解析结果做差集，就能把范围压到少数几个 crate。

作业顺序与缓存键

把 lint、check、测试、产物构建排成一张有向图，收益不在省时间而在失败归因：上游节点不过，下游根本不启动，一次红色只对应一个结论。

flowchart TD
  PR[提交 PR] --> Lint[格式与静态检查]
  Lint --> Check[双版本与多目标编译]
  Check --> Test[测试 多工具链分片]
  Test --> Audit[依赖与许可证审计]
  Audit --> Build[产物构建]
  Build --> Tag[打标签]
  Tag --> Publish[发布]
  Publish --> Note[变更日志归档]

缓存键至少要包含工具链版本与配置组合，否则会出现缓存命中却用错编译器或错开关组合的脏数据。代价是键越细命中率越低；编译耗时归同期《Rust 编译加速实践》一文。

产物与发布流程

库 crate 与二进制 crate 的发布差别决定流水线形状。库的产物是源码与文档，风险集中在兼容性与依赖解析；二进制的产物是平台相关的可执行文件，风险集中在构建环境与系统库。所以二进制项目必须先让多平台产物构建稳定。

这五条的成本很低，代价是每次发布前要等一轮作业；但版本号一旦发出去就收不回来，自检是唯一还能反悔的时刻。版本号语义按既有三段式约定使用，具体递增数字本文一律不写；预发布（pre-release）标记表达”能力尚未定型”，默认解析不会选中它。发布失败怎么恢复各生态规则不同，一律以官方发布流程文档为准。

变更日志与破坏性变更沟通

变更日志要按用户能感知的行为分组，而不是按提交或按模块分组。分组标题建议固定成新增、变更、废弃、移除、修复，外加安全一档。最低支持版本变化归入变更并要求显著标注；依赖升级只在影响公开行为时才写入；公开接口变化按其破坏性进废弃或变更。

模板的价值是把”要不要标记破坏性”变成一个填表动作，代价是条目变长。

发布的自动化与权限边界

自动发布必须绑定约束：由标签触发而不是由分支推送触发，只接受受保护分支上的标签，标签创建要有第二人复核。这三条把”谁能发布”从”知道密码的人”收敛成”有权限且有记录的人”。

凭据的纪律是作用域最小化：发布令牌只授予发布所需的最小权限，绝不写进配置明文、构建日志或缓存键——缓存键会被其他作业读到，等于把凭据扩散到共享存储。发布作业与测试作业要分开，不复用缓存与主机：一次测试污染不该影响产物内容，产物构建主机的出网权限本就该更受约束。

最后是现实问题：多数生态里已经发布的版本不能被真正删除，所谓回滚其实是发布一个修复版本，或在下游锁在旧版本上，而已发生的解析无法撤回。后果是破坏性变更的成本被后置到所有用户身上，这也正是前面那些门禁值得存在的理由。

小结

本文的主线是把 CI 当成三类问题的答案机器，每一类只在最便宜的位置被回答。最低支持版本是公开契约，抬高它就是破坏性变更，必须用双版本编译才算验证；目标矩阵要克制，只承诺真正服务的平台。格式、静态检查、许可证与通告审计适合做门控，但策略要留整改期和例外记录，否则门禁会退化成豁免注释。发布不可逆，所以它要由标签触发、受保护分支约束、双人复核，并与测试作业隔离。抄走清单之后的第一件事不是全部打开，而是先让每一项失败都能单独重跑、单独解释。
