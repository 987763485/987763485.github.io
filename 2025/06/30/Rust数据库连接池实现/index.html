Rust 数据库连接池实现

本文属于《Rust 学习路线》第 42/68 篇
上一篇系列目录下一篇

连接池（Connection Pool）在 Rust 服务里不是“参数调好就完事”的组件：所有权模型要求“归还”由类型系统兜住，异步取消又让“连接被拿走时干不干净”必须写清。本文按一个可自研的最小骨架，讲上限与下限、超时与公平、回收与失效、事务绑定、取消安全与指标暴露。

为什么要有连接池

建一条连接贵在四段：TCP 三次握手；TLS 再加一轮握手、证书链校验与密钥协商；认证要查账号、校验口令、加载权限；会话初始化（Session Initialization）要设字符集、时区、隔离级别与语句超时，服务端还得分配线程或进程与会话内存。这些开销每建一次付一遍，认证与初始化又常落在服务端的串行路径上，集中新建时要排队。本文数字均为示意值。

复用也不免费，风险是状态残留（State Leakage）：上一个使用者的事务没提交也没回滚，连接带着一个打开的事务回池，下一个人发出的第一条语句就被卷进别人的事务，更糟是长时间持有行锁；临时表、会话变量、服务端按连接缓存的预备语句（Prepared Statement）句柄都跨请求存活。复位因此必须是归还流程的一环。

两个极端都不对。每请求自建连接，尾延迟由握手和认证决定，连接数随并发线性膨胀。上限形同无限，则撞上数据库侧的全局上限，新建被拒绝，空闲连接白占内存。池的职责不是“缓存连接”，而是配额管理、排队调度与复用安全检查三件事的合体。语言与总论往期已写，本文只谈 Rust 侧实现细节。

池的最小骨架

池里只需要三份状态：空闲容器（栈或队列）、使用中计数、等待队列。获取分三条路径：从空闲取一条；总数未触顶时新建；否则挂进等待队列，等唤醒或等超时。归还先复位再处置：成功就放回空闲并唤醒队首，失败就丢弃、总数减一，把名额交给等待者。

难点是归还必须由类型系统保证。get 若返回裸连接，“还回去”就退化成口头约定——提前返回、用 ? 传播错误、分支里漏还都会漏掉连接。惯用做法是对外暴露守卫对象（Guard）：解引用后像连接一样用，归还绑在作用域结束上：

这段骨架解决“漏还”与“并发超卖”：占名额和归还同处闭环，出错路径绕不过 Drop。代价是多一层间接，连接不能跨请求持有，Drop 里又做不了可能失败的异步清理，复位失败只能丢弃。状态流转见下图：

上限与下限的语义

max 不是“想要多少连接”，而是必须与数据库侧对齐的配额。服务端上限是全局的，还要给运维与批处理留余量，所以各实例的池上限之和要明显小于它，并按发布期实例数临时翻倍来分摊。单实例算法很朴素：（数据库上限 − 预留）÷ 预计最大实例数。每请求取连接的写法归往期 Web 服务那篇，本文只谈池这一侧。

min 的意义是预热，让首请求不付建连代价，但它与空闲回收互相拉扯：下限过激时池里长期躺着一批连接，会被服务端按空闲超时踢成死连接，要么配一条轻量保活，要么把 min 设为 0 接受冷启动。

池的个数按三层划分：按库最硬，不同实例、不同物理库不能互换；按角色服务读写分离，主库池与只读副本池各设上限，免得报表吃光主库配额；按租户要谨慎，每租户一池会让连接总数随租户数爆炸，通常共享一池再叠加每租户并发配额，把隔离做在排队层。

获取超时与等待公平性

等待必须可取消。请求有截止时间，上游可能已经断开，任务可能被整批放弃；不可中断的队列会留下早已没必要等却仍占着名额的僵尸等待。所以 get 要么与请求超时赛跑，要么暴露取消，两条路径都要能从队列里把自己摘出去，且不能浪费已经发给它的唤醒。

两个顺序常被混淆。空闲容器用栈（LIFO），复用最热的连接，网络与会话缓存是暖的，但长尾连接一直没被摸到，更易被服务端踢掉；等待队列要严格先来先服务（FIFO），否则队首会在一次次归还中被插队到饿死。公平性在等待侧，复用效率在空闲侧，分开设计就不冲突。

获取超时与查询超时也要分开：前者只覆盖排队与建连，后者覆盖语句执行。可降级路径（审计日志、能用缓存兜底的读接口）用 try_get 立即失败、不排队，宁可快速失败让上层降级。

空闲回收与最大生命周期

这是两条各自独立的规则，别合并成一个参数。空闲回收（Idle Reaping）看“多久没被用过”，用来释放配额、退还按连接累积的会话内存，并赶在被踢掉之前关闭；最大生命周期（Max Lifetime）看“活了多久”，不管多热门，到期一律换新。

两者解决的问题不重叠。只设空闲回收，高频接口的热连接永不过期，而只有时间能带出来的问题会持续积累：会话内存上涨、元数据缓存过期、旧连接仍按调整前的参数运行。只设最大生命周期，长尾空闲连接照样占配额。强制换新还把损失封顶：一条坏连接最坏只影响它被使用的那段时间。

回收与使用中不冲突：回收器只遍历空闲容器，使用中的连接不在里面。容易出错的是另一种时序——等待者拿到一条刚判定健康的连接，开始使用的瞬间服务端已经断开，所以最终判据只能是“用的时候失败”，回收只降低概率。兜底是给使用中时长也设上限，超时视为泄漏、丢弃并记一次指标，否则漏还一条就永久少一条。

服务端先断开是常态而不是异常：空闲超时清理、NAT 静默丢包、数据库重启、主备切换，池没有先验信息，只能靠错误分类——连接类错误丢弃不归还，语义类错误正常归还。

失效检测与重连

最直觉的做法是取出连接后先跑一条便宜语句验证，例如 SELECT 1。代价是一次完整网络往返：绝大多数连接本来是好的，为极少数坏连接付全员验证的成本并不划算。

更省的三条组合是：按空闲时长决定是否验证，把验证从每次获取降到每次冷获取；失败即丢弃，在同一次请求里新建一条并重试一次；只对读语句重试，写语句一律上抛。骨架大致如此：

事务与连接的绑定

事务必须独占一条连接，原因不在业务而在协议：事务是连接级的会话状态，BEGIN 之后的语句只有沿同一条连接发出才属于同一个事务；换一条连接看到的是全新会话，原子性与隔离级别无从谈起。类型设计上，事务对象在生命周期内持有自己的守卫，只暴露“用我这条连接执行”的方法。

典型事故是嵌套取连接：工具函数签名要连接，事务中的代码就顺手 pool.get() 拿第二条。并发事务数一接近池上限，每个事务握着一条连接等第二条，释放渠道又被自己占着——池被自己占满，全部卡在获取上直到超时。修法是把连接沿调用链往下传，约定禁止事务内部再取连接，再配一个“等待者已持有连接数”的指标。

生态里 r2d2、bb8、deadpool 都有现成实现，选型只看两件事：是否支持异步、是否取消安全。sqlx 自带池且与它的语句类型耦合更紧，一般用它就够；自研的价值出现在跨库路由、按租户配额这类场景。

取消安全：本篇最容易踩的点

异步任务的取消在 Rust 里不是信号，而是“这个 future 被 drop 了”。父任务用超时或 select 放弃等待时，来不及写的清理代码不会执行，执行流直接从 .await 处消失。此时查询大概率已经发给服务端，它不知道客户端放弃了，会继续执行甚至把事务提交掉。

所以不能假定 Drop 会干净收尾。Drop 是同步的，等不了一次网络往返，既没法确认服务端停了，也没法做需要往返的回滚或会话清理。更危险的是协议残留：一条中途被取消的连接留着上一个响应的半个包，归还后下一个人发出的第一条语句会读到别人的结果。

守则四条：只有完整读完响应后才归还的连接允许回空闲，在 .await 处被取消或超时的连接一律判脏、随 socket 关闭丢弃；Drop 里只做内存操作与标记，需要往返的复位交给异步显式路径或后台回收任务；取消与失败在归还接口里合成同一类处置，别给“取消但可复用”留口子；等待者被取消时要把自己从队列摘干净并处理唤醒丢失（wakeup lost）。代价是复用退化成只复用干净连接，丢弃与新建都变多，但比串数据划算。

指标怎么暴露

没有指标的池猜不出问题。以下名字都是本文骨架的自定义示例。核心六个量：获取等待时长分布（必须是直方图，池的问题全在尾巴上）、空闲与使用中与总数三条曲线、获取超时计数、丢弃计数、重建计数、验证失败计数。使用中贴顶而吞吐归零，多半是自我死锁或漏还；重建与丢弃同涨，是服务端在踢连接。

基数控制是唯一会让人后悔的决定。标签只放取值有限且稳定的维度：池名、读写角色、丢弃原因枚举。不要把 SQL 文本、语句指纹、连接串、租户标识原值做成标签——一条慢 SQL 的指纹就能把时间序列撑爆，把监控系统本身打挂。采集口径守最小必要：不记参数值与用户数据，定位交给数据库侧的慢查询日志，池只报类别。

与既有实现的差别

一句对照：Go 的 database/sql 是“连接抽象加驱动重连”的模型，标准库自带池与排队，出错时由驱动透明重建，使用者很少关心归还。本文只说 Rust 不同在哪。

第一处是归还的归属：没有垃圾回收兜住忘记关闭的对象，漏还就是永久少一条连接，所以归还必须绑在类型生命周期上，由守卫和 Drop 完成。第二处是取消：半途放弃是正常控制流，而放弃就发生在 .await 那一点，连接干不干净要额外判断，透明重连并不安全——残留的响应字节会把脏连接交到下一个人手里。

参数 取值（团队约定示例） 设错会怎样
min 0 起步 太大就长期占配额，还被服务端空闲超时踢成死连接
max 按实例分摊 偏大被数据库侧拒绝新建，偏小则高峰期卡在获取超时
acquire_timeout_ms 很短 太长拖长整条链路，太短把可用容量误判为故障

max_lifetime_ms 数小时 不设则热连接永不过期，太短则无谓重建推高负载
验证开关 仅冷获取开 全量验证等于每次多一次往返，关掉则坏连接砸到业务

落地前先确认三件事：分摊算过没有、事务内部不再取连接、使用中时长有兜底。

小结

连接池在 Rust 里的难点不是数据结构，而是三件事的类型化表达：归还交给守卫与 Drop，复用交给“干不干净”的判定，容量交给与数据库侧对齐的配额。上限与下限、空闲回收与最大生命周期、获取超时与查询超时都各自独立，合并任何一对都会埋下故障。指标至少要守住等待时长分布、空闲与使用中、超时与丢弃与重建、验证失败这六项。先按本文骨架写一个最小可用的池，把 checklist 逐项验证过，再考虑是否换成生态里的现成实现。
