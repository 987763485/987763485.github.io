大模型成本优化实践

本文要解决的是一个很具体的问题：线上大模型（Large Language Model）应用怎么在不降低质量的前提下少花钱——先归因，再逐项施加上裁剪、缓存、路由、护栏等降本动作，最后用对照实验证明“省到了”。适合为推理调用与预算负责的工程团队阅读。本文不引用任何真实单价、卡数与金额，涉及数字之处一律按当期官方价目核对，示例数字均显式标注示意值。

先把成本结构摆出来

谈降本，第一步不是找工具，而是把“一次调用到底花了什么”摊开。最显眼的是 token：输入与输出两类，输出的单价比输入贵得多——这个方向性事实贯穿全文。本文不引用任何具体价目，需要数字的地方一律按当期官方价目核对，示例数字均显式标注示意值。方向比数字更重要：模型每多说一个 token 都按更贵的单价计费，所以“让模型少说、少绕路”通常排在“把 prompt 写短”之前。

账面上的 token 之外还有几笔隐性开销：工具调用与检索会带来额外轮次，每一轮都要把不断变长的上下文重新走一遍；超时或限流引发的重试，让同一个请求付费两次；观测里存的提示词与补全原文，随流量与保留期增长成为一笔存储成本；微调、评测与评测集的人工构造，是不出现在推理账单里却同属一个预算池的离线成本。

削减任何一项之前，先让上面每一项都能对应到“哪个功能、哪个租户、哪个模型版本”。归因是所有动作的前提：没有归因，就没有降本。

归因先行：盯单位成本，不盯总花费

总花费是最没用的指标——钱多可能只是因为用得多。要在请求入口把标签打全：场景、功能、租户、模型版本、路由层级、来源端。任何一个标签缺失，都会让一部分消费无处归属；标签缺失的调用单列“未归因”，并限期清零。

然后看单位成本：选一个业务分母，比如每次成功回答、每个完结工单、每个转化。两个注意点——“成功”必须定义为通过质量校验，否则单位成本会奖励放弃质量；分母的统计口径要冻结，口径变了就不许再谈趋势。

预算护栏分三层：日预算、每分钟花费速率、单会话消费上限。越线先告警，持续越线则降级或止损；具体阈值都是团队约定的示例值，例如“花费速率超过约定基线的 1.5 倍即告警”属示意值。算法本身很简单：单位成本等于总花费除以成功量，按月复算，按周看差值。至于核算模型与单位经济学本身，往期《大模型推理成本核算》已经建立，本文不重复，只谈降本动作与治理。

上下文裁剪与缓存：省的是输入和轮次

裁剪类动作的第一步，是把固定部分与可变部分分离：系统指令、输出约束、示例放在上下文（Context）前部并保持稳定，业务变量只放尾部——既少花输入 token（Token），又为前缀缓存（Cache）复用创造条件。历史消息不必全量携带：较早轮次做摘要压缩或槽位化，只保留结论与约束；最近轮次保留原文。检索侧只把推理必需的字段给模型，表格与 JSON 去掉无帮助字段；文档片段做截断与要点化，发送最相关的几段而不是整篇。

要清醒认识风险边界：裁剪省的是输入 token，赔的可能是正确率。最容易被裁丢的信息有三类——罕见例外条款、否定式约束（“不得做某事”）、精确的数字与日期，它们恰恰是模型无法凭常识补全的部分。证明办法是离线对照实验：固定一份覆盖真实流量分布的评测集，在同一提示词版本、同一解码参数下跑“完整上下文与裁剪上下文”两组，比较通过率、升级率与输入 token 均值；质量持平且输入显著下降才合入，否则收缩裁剪范围。不要凭几个自测题下结论。

缓存让同一笔钱只花一次。两层做法：前缀与系统提示复用压低固定部分的实际计费，机制层的 KV 缓存与分页注意力归本批《大模型推理优化：KV Cache 与 PagedAttention》，本文只把它们的收益落到钱上；同题答案缓存则让语义相同的请求命中后直接返回。能否同题缓存先按类别判定：可缓存——事实问答、规格参数、模板化生成、无个人数据、无时效敏感；不可缓存——涉及实时数据、依赖用户身份个性化、依赖多轮上下文、内容有即时下架要求。缓存键设计不能含隐私原文，参考骨架如下：

批处理与错峰：能等的活儿不占高峰

大量任务不需要即时结果：历史工单打标、语料清洗、内容回填改写、离线评测。把它们统一排队到低峰时段执行，平台支持调度时走低优先级，失败用带抖动的退避重试。批量类接口的适用条件是三条——能等、顺序无关、可重试，此外还要加幂等键防止重复付费。与在线延迟的协调靠双队列：在线请求永远不排在批量任务之后，批量任务在高峰主动让路；错峰等待省下的调用费有限，在线响应变慢伤掉的业务却无上限。通用云资源的错峰与超售归往期《云成本优化》与《K8s 成本治理》，本文只算 token 与轮次这两笔大模型特有的账。

模型路由：把强模型留给难题

模型路由（Model Routing）按任务难度分层：简单任务交给便宜的小模型，困难任务才动用强模型。可用的路由信号包括：输入长度与结构、是否包含工具调用、任务类型、相似请求的历史通过率、小模型首次输出后的置信度与校验结果、重试次数。与之配套的是失败升级链：弱模型先试，质量校验不过再升级到强模型，仍不过再升一级并设升级上限，最后兜底到固定话术。要警惕路由自身的成本：路由器要么是一段规则，要么是一次最小模型的调用，判错一次就可能多付一整次强模型调用，所以路由收益只在稳定大流量上成立——先用小流量灰度，盯升级率与端到端延迟，再逐步放量。请求从进来到入账的完整链路如下：

换小模型、蒸馏与微调：先证明质量，再谈省钱

直接换小模型（开源或轻量商用版本）是确定性最高的降本，但它只在几个条件同时成立时划算：任务单一、指令清晰、错误容忍度较高、调用量大且持续、有私有化条件把推理摊出去。2025 年上半年，Qwen2.5 与 4 月底发布的 Qwen3、Llama 3.x 与 4 月初发布的 Llama 4 系列持续补齐中小尺寸档位，DeepSeek-R1 与 3 月的 V3-0324 让长链路推理能力出现在更低成本的模型上，“小模型也能干”的任务面正好在扩大。但两类场景必须保留强模型：一是长链路多步推理与复杂工具编排，错误会在链条里放大；二是医疗、法律初稿这类错误代价极高的场景，5 月下旬新推出的旗舰档位仍应是默认选择。蒸馏（Distillation）只是让小模型达到接近质量的一条路径，方法细节归本批《模型蒸馏与知识迁移》，本文不展开。微调（Fine-tuning）适合“小模型加领域语料”去接固定格式任务，但它先花训练与评测的钱再省调用钱，回不回本要放进下一节的测算表里算。无论选哪条路，验证证据一项都不能少：同一评测集上的通过率差值、升级率差值、人工抽检一致率、灰度流量的线上对照与回滚阈值。四件套没跑齐就说“换小模型省钱”，只是把成本转移成了质量事故。

私有化还是按量调用：只给决策轴，不给答案

自持算力更划算通常是一个条件判断题，不是普适答案。值得往私有化（Private Deployment）方向测算的条件：调用量呈持续高水位而非脉冲、峰谷比可规划从而利用率撑得住、数据合规要求“不出域”、延迟服务等级协议很紧、团队有能长期值守的 GPU 与推理栈运维人力。反过来，量小或波动大、模型迭代快（自研栈的版本落后本身就是隐性成本）、没有专职运维，都是留在按量调用一侧的理由。这一节刻意不写卡数、金额与总拥有成本数字——这类数字过期极快，做决策时应按当期官方价目与内部实测重新核对后填入下表。部署架构与选型细节归本批《大模型私有化部署方案》，本文只保留决策轴；下表数值一律“待填”，凡给出示例均注明示意值：

护栏与观测：止损阀与复盘节奏

护栏（Guardrail）看起来是稳定性话题，实际上全是成本阀门：最大输出 token、单会话最大轮次、工具循环上限、并发与队列上限，再加上带次数上限和退避的重试预算。机制讲清楚就知道没有护栏的成本为什么会失控：工具型智能体（Agent）每一轮都要把不断变长的上下文重新计费，没有循环上限时一个任务可以自触发几十轮，花费随轮次近似平方地增长；没有重试预算时，下游故障会按错误率把花费放大一个量级；没有单会话消费上限时，一个失控会话就足以吃掉当日预算。取值按场景约定后固化为配置，例如“单次请求最多八轮、单会话消费超过日预算的约定比例即熔断”是团队约定示例阈值，不是行业结论。

观测看板至少要有这些字段：分标签的单位成本、总花费、缓存命中率、升级率、轮次分布、重试率、输入 token 的分布与截断率、租户消费排行。每周复盘看差值而不是绝对值——哪个标签的单位成本环比涨了超过阈值（一成属示意值），总花费的增量归因到谁；每次发布做同一评测集的前后对照，质量差值与成本差值一起看，防止功能变好的同时悄悄变贵。异常成本按固定顺序定位：先看是不是重试风暴（重试率与限流状态码），再看是不是历史消息或检索片段变长（输入 token 的 P95），再看是不是新工具让轮次增加，然后查模型版本与路由配置的变更，最后才看流量结构本身。

小结

降本不是一个按键，而是一个循环：先归因，知道钱进了哪个桶；再选动作，每个动作都带着前提条件与副作用；然后验证，用同一评测集的对照实验证明质量没有变差；最后用护栏和观测兜底，防止省下来的钱被重试风暴、变长的历史和增加的轮次吃回去。方向上记住三件事就不会太离谱：控输出比控输入更值钱，因为输出单价在方向上贵得多；缓存与路由的收益最大，也最容易把失败藏进看不见的地方，所以命中率与升级率必须上看板；一切账单数字都会过期，用“按当期官方价目核对”的纪律代替对具体价格的记忆。把每个省下的动作写回同一本账，成本优化才是工程，而不是记账。
