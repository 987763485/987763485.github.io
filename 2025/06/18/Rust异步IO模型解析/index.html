Rust 异步 IO 模型解析

本文属于《Rust 学习路线》第 38/68 篇
上一篇系列目录下一篇

网络服务端开发里，最容易让人产生”我懂了”错觉的，恰恰是异步 IO 这层地基。语法层面的 async/await 只是入口，真正决定一个服务能不能扛住并发、会不会在深夜把内存吃满、会不会偶发地把某个连接永久挂起的，是底层 IO 模型与运行时契约之间的配合方式。本文不重复《Rust 异步编程入门》里的语法与基本用法，也不展开任务调度、定时器内部实现或运行时横向对比，而是把镜头对准”数据怎么从内核流到 future”这一条路径：从操作系统的三种 IO 形态讲起，落到 Rust 的 AsyncRead/AsyncWrite 契约，再逐一拆解反应器如何唤醒任务、边缘触发为什么必须循环读、写方向的部分写与半包、超时与取消对 IO 的真实影响、就绪模型与完成模型的取舍、vectored 与零拷贝的方向、TLS 这类包装层带来的状态机，最后给出一份工程守则与观测验证方法。适合已经会写 async fn、但想弄明白”为什么我的服务偶发卡死”的读者。读完你应当能够判断一个 IO 相关的疑难问题出在哪一层，并知道只改一层去验证它。

操作系统层的三种 IO 形态

要理解 Rust 的异步契约为什么长成那个样子，得先回到内核。抛开具体系统调用的参数细节，只看”内核到底告诉你什么”，阻塞 IO、就绪通知、完成驱动这三种形态给出的信息是逐层递进的。

第一种是阻塞 IO（blocking IO）。线程调用一次读，如果此刻没有数据到达，内核就把这个线程挂起，直到有数据可取才让它继续，然后返回已经拷贝到用户缓冲区的数据。它的语义最直白：这次调用要么拿到数据、要么拿到错误，调用返回的那一刻事情就”办完了”。代价是一个连接占一个线程，几万个空闲连接会把线程栈和调度开销全部摊在你头上。这就是本文不推荐的形态，但它是理解”办完了”这三个字的基准。

第二种是就绪通知（readiness notification），也就是 select、poll、epoll、kqueue 这一类事件机制共同提供的形态。它们共性在于：内核不替你把数据读完，而是回答”你现在可以去试一下了”。线程先向内核登记”我关心这个 fd 的读事件”，然后要么在这批 fd 上等待、要么带超时地等待；当内核认为某个 fd “准备好了”，就把这个 fd 报告给你。关键点在于，”准备好了”是一句承诺而非结果——它告诉你”这次去读大概率不会阻塞”，但数据究竟有多少、是否真的到齐，仍要你自己发起读操作去确认。所以就绪通知回答的是”可以试了”，而不是”办完了”。Rust 的异步 trait 正是围绕这个语义设计的。

第三种是完成驱动（completion-driven），以 io_uring 一类接口为代表。你把读请求连同缓冲区、长度一起提交进队列，内核在你指定的时刻把”这次读实际拿到多少字节、是否出错”写回完成队列。它回答的是”办完了”：完成事件里带着结果本身，而不是一个”你去试试”的暗示。这一形态省掉了”先等就绪、再发起读”的两段式，但把新的责任转移给了调用方——缓冲区的生命周期、提交队列的深度与背压，这些都得自己管。关于 io_uring 的更细取舍本文放在后面章节，此处只确立”内核告诉你的是暗示还是结果”这条分界线。

Rust 异步 IO 的契约：就绪驱动的味道

Rust 标准库里描述异步读写的核心 trait，读方向是 AsyncRead，写方向是 AsyncWrite。它们的灵魂方法是 poll_read 与 poll_write，返回类型统一是 Poll<io::Result<usize>>。这个返回类型把上一节的形态划分原样搬进了类型系统，值得逐层拆开看。

外层 Poll<T> 只有两个变体：Poll::Ready(T) 表示”这次尝试有了结论”，Poll::Pending 表示”这次没能推进，稍后会唤醒你再来一次”。注意 Pending 不是错误，也不是超时，它是一个明确的信号：现在没结果，别 spins，等通知。内层的 io::Result<usize> 才是结论本体，Ok(n) 里的 n 是”这次实际读了或写了多少字节”，这个 n 可以小于你请求的长度。把两层合起来读，poll_read 的语义就是：”如果准备好了，就把当下能拿到的数据拷进缓冲区，告诉你拿了几字节；如果现在拿不到，就返回 Pending，并在将来唤醒你。”这正是就绪驱动的味道——内核（经运行时转述）给的是”此刻能不能推进”，而”数据够不够、是否读完”完全由调用方通过返回值自己判断。

这里有个初学者极易踩坑的点：read 返回 Ok(0) 与 EOF 的关系。在语义上，读到 0 字节且不是错误，通常表示”对端已经关闭了写方向，流结束”。但 0 并不总等于 EOF——某些实现里返回 0 也可能表示”请求的长度本来就是 0”。所以判断结束要依赖流的语义约定，而不是把”0”当成万能终止符。写方向同理，poll_write 返回 Ok(n) 且 n 小于请求长度，是”部分写”，绝不是失败。

正因为 poll_read/poll_write 只保证”当下的一次推进”，标准库在更上层提供了组合子式的读方法做分层。Read trait（同步世界里）的 read 是”读到当前 available 为止，可能一次都不够”，而 read_exact 是”必须填满整个缓冲区，否则要么 EOF 要么出错”。异步侧对应的是 AsyncReadExt::read 与 AsyncReadExt::read_exact。分层的意义在于：底层 poll 方法表达”一次尝试”，上层 read_exact 这类方法用循环把多次尝试拼成”完整读满一个结构体”的语义。你在写协议解析时，绝大多数时候应当站在这层抽象上，而不是手撸 poll。

还有一个当时绕不开的现实：Rust 标准库里的这些异步 IO trait，在本文写作口径下仍未稳定，长期停留在需要 nightly 工具链才能引用的状态。稳定不了不影响生态运转，因为生态并没有等它，而是用一组扩展 trait 来描述同一套契约——读方向、写方向、以及把它们拆成独立持有句柄的辅助 trait，都由生态各自提供并约定接口形状。本文不写具体 crate 的小版本号，也不写”自某个 x.y 起支持某特性”这类无法在目标环境验证的断言；只需要你记住一件事：你在代码里 use 进来的 AsyncReadExt、AsyncWriteExt、ReadBuf 这些名字，是生态对”就绪驱动契约”的具体实现与扩展，它们与标准库方向一致、语义一致，替换运行时通常不改你的读写逻辑。至于任务如何被调度、定时器如何到期，是另一条主线，归《Rust 异步运行时源码解析》讨论，本文只把 IO 这一路讲透。

Poll::Pending 的硬约束与违约症状

就绪驱动契约里最致命的一条规则，往往在第一次读到文档时才被重视：一个 poll 方法在返回 Poll::Pending 之前，必须已经确保”将来会有人唤醒我”。这句话不是建议，是硬约束，而且违反它不会有任何编译错误或运行时报错——它会安静地制造一个永久挂起的任务。

为什么这么严？因为 Poll::Pending 的含义是”我现在推不动，请你（运行时）先把我从执行队列里拿出来，别再空转地反复 poll 我，等条件满足时再唤醒我”。而”条件满足时再唤醒我”这件事，运行时并不知道条件是什么，只有你这个 poll 的实现者知道。所以约定是：poll 在返回 Pending 的那一刻之前，必须已经把自己挂到某个唤醒源上——通常是向反应器登记对这个 fd 的读/写兴趣，并保证当内核报告事件时，反应器会调用这次 poll 里保存下来的 Waker。只要这一步没做，future 就睡在一个没有人会叫醒的位置上：调度器看到 Pending，把它移出就绪队列；没有 Waker 被触发，它永远不会被放回队列；连接对端源源不断地发数据，这个任务却一动不动。进程不崩、不报错、CPU 占用为 0，只是那个连接”卡住”了。

还有一点常被忽略：Waker 是可以被反复调用、也可以在多任务间克隆的，但每次 poll 用的 Waker 都要更新到你这次想被唤醒到的那个 future 实例。取消与 IO 交织时的 Waker 处理，语义总论归《Rust 异步取消与取消安全》，本文只在后面讨论”drop 一个正在读的 future 之后数据去哪了”时涉及它的 IO 后果。

反应器与任务如何连接

上一节说”必须已经登记好唤醒”，这一节就把这条链路的形状画出来：一次 socket 可读事件，究竟是怎么变成对应任务的一次重新执行的。

链路大致是这样五步。第一步，任务在 poll 它的 socket 时，发现当下读不到数据，于是向运行时内部的反应器（reactor）登记”我对这个 fd 的读事件感兴趣，请事件到了用这个 Waker 叫我”，然后返回 Pending。反应器底层对接的正是 select/poll/epoll/kqueue 这一类就绪机制。第二步，调度器看到这个任务返回 Pending，就把它移出就绪队列、挂起，转去执行别的任务，线程不会被这个连接拖住。第三步，内核侧数据到达，反应器在下一轮事件收集时从这个 fd 上读到一个就绪事件。第四步，反应器取出该 fd 关联的那个 Waker，调用它的 wake，把对应任务重新放回就绪队列。第五步，调度器再次 poll 这个任务，任务再次调用 poll_read，这次能读到数据，继续往下推进。把它画成时序图：

sequenceDiagram

  participant R as 反应器 reactor
  participant K as 内核事件机制
  participant S as 调度器
  T->>R: poll 读不到，登记 fd 读兴趣并保存 Waker
  T-->>S: 返回 Poll::Pending
  S->>S: 把任务移出就绪队列，执行其它任务
  K-->>R: 数据到达，fd 报告可读事件
  R->>T: 调用保存的 Waker 触发 wake
  S->>T: 重新 poll 该任务
  T->>K: 发起读，循环读到 WouldBlock 为止

这里有一个设计要点值得单独讲：为什么要把”fd 的状态”和”future 的状态”分开持有。反应器为每个被关注的 fd 维护一份状态（兴趣集合、上一次就绪位图、以及当前挂在它上面的 Waker），这份状态的生命周期跟 fd 走；而 future 的生命周期跟那次 await 走，它随时可能被取消、被重建。如果强行把两者合成一个，就会遇到”future 被 drop 了但 fd 还活着””fd 复用给了新连接但旧 Waker 还挂在上面”这类悬垂引用。把它们分开——fd 状态放在反应器、future 状态放在任务里、中间用 Waker 这个可克隆可失效的把手连接——正是异步运行时能安全处理取消与复用的关键。

于是自然的下一个问题是：同一个 fd 被多个任务同时等待会发生什么？如果两个任务都对这个 socket 调 poll_read，就出现两个 Waker 争一个 fd。就绪事件只能唤醒其中一个（谁先读到数据谁推进），另一个的 Waker 要么被覆盖丢失、要么被唤醒后读不到东西又返回 Pending——处理不当就是上面”现象二”那种随机挂起，或者两个任务反复互相抢。运行时的防护思路通常是：让 fd 的读写各自只允许被一个”当前持有者”关注，用一把内部锁或原子槽位记录”现在挂在这个 fd 上的是哪个 Waker”，后来的等待者要么排队、要么根本不允许（这正是为什么要用 split 把读写拆开各归一个任务，或用一个专职任务持有连接句柄、其余任务通过 channel 转发的原因）。TcpStream 这类裸句柄本身不天然支持”多任务并发读同一个流”，要并发读写就得显式地拆分所有权，这点归到工程守则里再讲。

最后补一个直接决定实现形态的机制差异：水平触发（level-triggered）与边缘触发（edge-triggered）。水平触发是说，只要 fd 上还”有数据可读”，每一轮事件收集都会重复报告这个就绪事件，你漏读了它下次还会再提醒你。边缘触发是说，只有当 fd 的可读状态发生变化（从不可读到可读、或新数据使缓冲从空变非空）时才报告一次，如果你这次没读干净，内核不会再提醒你。两者的直接影响是：水平触发下，一次事件对应一次读、读不干净下次还会再被叫醒，实现简单但可能多几轮空转的系统调用；边缘触发下，一次事件是”一次性通知”，你必须在这次通知里循环把内核缓冲区读到”读不动为止”，否则会永久漏数据。生态里更偏向边缘触发，因为它在高吞吐下能显著减少重复事件上报，代价就是把”读干净”的责任压到了调用方——这就是下一节的主题。

边缘触发下的重复读与读到空

边缘触发把”读干净”变成了调用方的义务，而”读干净”在代码里的判据只有一个：一直读，直到读到”内核缓冲区此刻空了”的那个错误为止。这个错误在 POSIX 语义里就是 WouldBlock（EWOULDBLOCK/EAGAIN），非阻塞 fd 上没有数据可取时返回它。所以一个正确的边缘触发读循环，形状是”读到 WouldBlock 才算完”，而不是”读到一次返回 0 或读到一次成功就停”。

为什么必须循环到错误为止？因为边缘触发的通知是边沿信号，不反映”还剩多少”。假设一次事件到达时内核缓冲区里堆了 8 KB 数据，而你只 read 了一次拿走 4 KB 就 return，那么缓冲区还剩 4 KB；等对端再发新数据时，如果这 4 KB 一直躺在缓冲区里、缓冲始终非空，fd 的可读状态没有发生”从未就绪到就绪”的跃迁，内核可能不再产生新的边缘事件——那 4 KB 就永久卡在缓冲区里，直到下一次真正让缓冲从空变非空的写入才被动被带到。这就是经典的”漏数据”事故。用 WouldBlock 收尾，是为了确认”我真的把此刻能取的全取干了”，从而让边缘事件与缓冲区状态保持一致。

这里有个反直觉但很重要的细节：为什么”读到空”不能作为终止条件。在就绪驱动 + 边缘触发下，一次 poll_read 返回 Poll::Pending（内部对应 fd 暂时没有数据），并不意味着流结束，它只是”这一刻读不动”。而”这一刻读不动”正是边缘触发循环该停的信号——不是 EOF，而是”这一轮我读干净了，回去等下一次事件”。EOF 的判据是另一回事：对端有序关闭、读方向拿到 Ok(0)。把”读到 WouldBlock”和”读到 EOF”混为一谈，是新人最常见的逻辑错误，会导致把正常的读干净误判成连接结束。

每次多读一轮的代价也要摊开说。因为判据是”读到错误为止”，所以每一轮边缘事件后，除了真正拿到数据的那几次读，你还必然多做一次注定返回 WouldBlock 的读调用。这一次空转的 read 系统调用就是成本：它不进内核数据路径但确实是一次陷出。低流量时这笔开销几乎无所谓；高 QPS、每条消息都很短、事件极其频繁时，”每个事件多一次空读”会累积成可见的系统调用数量。实现上常见的缓解办法是配合 read_vect（一次读多个缓冲区把能拿的尽量一次拿干）或者维护一个足够大的用户缓冲减少循环次数，但”必须至少多试一次”这个下界是边缘触发模型给的，去不掉。

对照说明就清楚了：如果底层用的是水平触发，你就不必循环到 WouldBlock。因为只要缓冲区还有数据，下一轮事件收集会再次报告这个 fd 可读，你漏下的那 4 KB 下次照样会被提醒去取。水平触发的代价换成了”可能反复被唤醒去读同一批数据、事件上报数量上升”，实现简单、不容易漏数据，但在连接数巨大、就绪风暴频发时，重复上报本身就成为开销来源。所以这是”漏数据风险 + 空读一次”（边缘）与”重复事件上报”（水平）之间的取舍，不是谁绝对更好。Rust 生态默认走边缘触发这条路，因此你在自定义 IO 适配层时，把”循环读到 WouldBlock“当成一条必须守住的纪律。

写方向的坑：Pending、部分写与半包

读方向讲”能不能读干净”，写方向讲”能不能写干净”，而写干净比读干净更容易被写错，因为它同时包含两个独立的坑：写缓冲满导致的 Pending，和部分写导致的多字节游标推进。

先说 Pending。非阻塞 socket 的发送缓冲区是有容量的，当你写的数据超过内核此刻能接收的量，poll_write 就会返回 Pending——含义是”发送缓冲此刻满了，等你登记唤醒、将来可写了再叫我”。这跟读方向的 Pending 是同一套契约，也必须遵守”返回 Pending 前登记好对写事件的兴趣”。工程上更隐蔽的问题是：如果写路径没有做好背压，客户端读得慢、服务端一直往一个已经满的 socket 上堆数据，那么 Pending 会让写任务挂起等待对端把数据消费掉——这本应是好事（自然背压），但如果你为了避免挂起而在内存里自建了一个无界发送队列，就等于把”该由 TCP 缓冲区承担的等待”搬进了堆，直接把慢客户端的压力变成了自己的内存压力。这一点归到工程守则里详述。

再说部分写，这才是写方向的头号坑。poll_write 返回 Ok(n)，而这个 n 完全可以小于你请求写入的长度——内核只保证”这 n 字节进了发送缓冲”，剩下的一律没管。所以任何一次写之后，你都必须自己维护一个游标，把没写完的尾部继续写完，直到全部写完为止。上层用 write_all 之类的组合子就是帮你把”循环推进游标直到写完”这件事封装好了；但当你自己手写 poll 或者在协议帧边界上拼接多段数据时，”部分写”必须显式处理，否则会静默丢字节。

超时与取消如何作用于 IO

取消语义的总论归《Rust 异步取消与取消安全》，本节只谈当取消与超时落到 IO 这条路上时，会产生哪些资源和数据层面的后果。这层区别很关键：语法上的 select! 或 timeout 让一个 future 停下来很容易，但”停下来的那一刻，内核侧发生了什么”不是语法能替你回答的。

第一个认知：超时不能只靠把 future drop 掉。很多人以为给一次 read 套个超时、时间到了 future 被 drop，连接就”释放”了。事实是 drop 一个 future 只是让 Rust 侧不再推进这个状态机，它不会自动关闭底层的 socket，更不会把已经登记在反应器里的兴趣注销掉——除非你显式地让持有 fd 的那个对象也一并被 drop（也就是把整个连接句柄的所有权一起丢弃）。更麻烦的是 fd 归属：如果一个 future 借用了某个连接、而连接句柄被别的任务持有，你 drop 这个借用 future 时连接还活得好好的，fd 还在被反应器关注；此时你以为”这条请求超时放弃了”，其实底层连接、内核缓冲区、以及可能已经排队的数据都还在。所以正确的超时做法，是让超时分支去触发”关掉整个连接”这个动作，或者把连接的生命周期跟这次请求严格绑定，让 drop 传播到 fd 本身。

第二个认知，也是本篇最重要的一个：drop 一个正在读的 future 之后，数据会不会丢？答案是——那些”已经到达内核缓冲区、但你还没读走”的数据，不归这个 future 管，也不会因为 future 被 drop 就凭空消失或补发给你。就绪驱动模型下，内核的接收缓冲区属于 fd/socket，不属于某个 future。future 只是”去读的动作”，它被 drop，读的动作停止了，但数据仍然安静地躺在内核缓冲区里，等着下一个持有同一个 fd 的读者去取。这就引出两个工程后果：其一，如果你在超时后 drop 了读任务、却复用同一个连接去处理下一个请求，那么上一请求没读完的残留字节会被下一个请求读到，造成协议错乱——这也是为什么 HTTP 这类严格帧化的协议在超时后通常选择关闭连接而不是复用；其二，如果你 drop 的是整个连接句柄，那么缓冲区连同 fd 一起被内核回收，数据随连接消失，反而是干净的。理解”到达但未读的数据不归 future 管”这一条，能解释很多”超时之后连接串包”的诡异现象。

第三个认知：优雅关闭为什么要分写半边和读半边。TCP 连接是全双工的，有两个独立的方向。当你想让一次交互干净收尾时，”关闭连接”不是一个原子决定。常见正确姿势是先做完写方向：把最后一帧写完、把发送缓冲排空，然后 shutdown 写半边，向对端发出”我这边不会再发数据了”（对端读到 EOF）。这一步之后你仍然可以接着读对端可能还没发完的数据或它对你关闭信号的回应，直到对端也关闭或达到某个上限，再放弃读、彻底丢弃连接句柄。如果你不分半边、直接整个句柄一 drop 了事，那么在途的响应字节可能随 socket 关闭而被丢弃，对端会看到连接被重置而非优雅结束。写半边先关、读半边后收，就是把”我说完了”和”你也说完了”这两件事分开确认。

把超时、取消、优雅关闭放一起看，它们的共同教训是：Rust 侧的 future 状态和内核侧的 socket/fd 状态是两套生命周期，取消只保证前者停止，后者需要你在设计时显式安排归属与关闭时机。

就绪模型与完成模型的差别

把视角从”怎么把就绪模型用好”抬到”就绪模型和完成模型到底谁更合适”，能帮你在选型和读源码时不被表象迷惑。取消语义的通用讨论在《Rust 异步取消与取消安全》，运行时内部如何在两者之间调度归《Rust 异步运行时源码解析》，本节只做模型层面的对照。

最直观的差别前面已经铺垫：完成模型（io_uring 一类）能省掉”循环读到 WouldBlock”这件事。因为在就绪模型里，内核只说”可以试了”，你必须自己反复读直到读到”没数据了”才能确认干净；而在完成模型里，你提交一个”读最多 N 字节到这块缓冲”的请求，完成事件会直接告诉你”实际读到了 M 字节”，M 就是结果本身，你不需要再用一次注定失败的读去试探边界。同样在写方向，完成模型把”部分写、推进游标、续写”的循环交给了内核侧的多次完成事件，而不是让你在用户态手写那个 while。省掉这些空转系统调用，是完成模型在高频小包场景下的主要吸引力。

但完成模型不是免费的午餐，它把两类新问题交给你。第一类是缓冲区生命周期。就绪模型里你 poll 时才借用一块栈上或堆上的缓冲，读完这一轮就还回去；完成模型里你在提交请求时就得把缓冲区指针交给内核，并保证”一直到对应完成事件回来之前，这块内存不会被移动、不会被释放、内容不被别的代码改”。这意味着缓冲区往往要进堆、要有一个跟随请求 ID 的归属管理，异步的”提交—完成”两阶段之间的这段时间必须被妥善持有。稍有不慎就是 use-after-free 或数据竞争。第二类是队列背压。就绪模型是”来一个事件处理一个”，压力天然由事件到达速率决定；完成模型有提交队列（SQ）和完成队列（CQ）两个环，如果你的提交速度快过内核消费速度，SQ 会满，你要么阻塞提交要么丢失请求；如果完成事件产生快过你收割，CQ 会积压。两个环的深度、以及”什么时候收割 CQ、什么时候再提交 SQ”的节奏，都是你要自己权衡的背压控制，处理不好就是内存被在途请求撑爆。

那为什么 Rust 生态里，同一套上层 trait 可以把这两种底层都包住？因为 AsyncRead/AsyncWrite 这套契约描述的是”就绪驱动的语义”（poll 一下、给个 Pending 或给个 n），而上层组合子（read_exact、write_all、copy 等）只依赖这套语义。要接一个完成模型后端，就在中间做一层适配：把一次”提交读请求”翻译成 poll_read——第一次 poll 时提交请求并登记唤醒、返回 Pending，完成事件回来后唤醒、再次 poll 时从完成队列取出结果返回 Ok(M)。这样上层代码看到的仍是熟悉的 poll 语义，底层到底是 epoll 边缘触发还是 io_uring 完成队列，被这层适配挡住了。代价是完成模型的部分优势（省掉空读）在”套进 poll 语义”时被重新引入了一点阻抗——不过整体仍是划算的。

关于 io_uring，本文只给方向与设计权衡，不断言任何具体内核版本的可用性、也不罗列它在某个版本支持哪些特性集合。事实是：它的能力边界、可用特性、以及是否能安全地和其它机制共存，强依赖目标环境的内核配置与构建选项，必须在你要部署的那个环境里实测验证，不能凭文章或记忆断言”某能力只有内核某版本才有”。选型时的正确姿势是：如果你的负载是海量长连接、小包高频、且你愿意承担缓冲区生命周期与队列背压的复杂度，完成模型的收益更明显；如果你的负载是少量大流量读写、或你更看重实现简单与可移植，成熟就绪模型加边缘触发已经足够，且生态支持面更广。横向比较各运行时对这两条路的落地程度，归《Rust 异步运行时对比》，本文不重复。

vectored IO 与零拷贝的方向

read_vectored 与 write_vectored 这一类接口，名字里的 “vectored”（向量式，或称散布/聚集）解决的是一个很具体的效率问题：把多次系统调用合成一次、并减少中间拷贝。

普通的 read/write 一次只对接一块连续缓冲区。但很多协议天然是”非连续的一段数据”：一个响应可能是”头部若干字节 + 正文若干字节”分散在不同内存里，或者你要把一个结构体解析成”几个字段各自独立缓冲”再一次读入。用单缓冲 API 的话，你要么先把它们拼到一块连续内存里（多一次 memcpy），要么分多次系统调用读写（多次陷出）。vectored 接口接受一组缓冲区切片，一次 write_vectored 就把这几段按序发出去、一次 read_vectored 就把读到的数据按序灌进这几段。收益有两个：系统调用次数下降（陷出开销、上下文切换减少），以及中间拷贝减少（不必为了连续而临时拼接）。在高吞吐路径上，”一次网络写要发 header 加 body 两段”用 write_vectored 而不是 write(header) 紧跟 write(body)，是常见且值得的优化。

TLS 与压缩等包装层

裸 socket 之上套一层 TLS、套一层压缩、再套一层应用协议帧，是每个真实服务端都会遇到的形态。写服务本身归《Rust 网络编程实战》与《Rust Web 服务实践》，本节只讲一件事：包装层为什么把”一次 poll 就能读完”这件事，变成了一个必须显式维护的状态机。

在裸 socket 上，”我要读 N 字节”和”内核给我 N 字节”之间只隔着一个”数据到了没有”的问题；一次 read_exact 循环 poll 到凑够为止就完事。加上 TLS 之后，多出来一整层”记录”（record）的概念：对端发来的是加密的 TLS 记录，你要先攒够一条完整记录的头、按头里的长度攒够记录体、解密、校验，才能拿到明文字节；而一条 TLS 记录解出来的明文字节数，和你上层想要的 N 字节之间没有对齐关系。于是”读 N 字节明文”变成了一串可能跨多个 TCP 段、每条记录又可能只解出部分明文的状态推进。压缩层类似：压缩流是分块吐明文的，你没法假设一次 poll 到内核数据就等价于一次能解出一个完整可用块。把这些叠在一起，poll_read 的内部就不再是”读一下就走”，而是”处于握手态还是数据态、有没有攒够一条记录、解密缓冲里还剩多少没交给上层”这样一组状态。

半包与协议帧的边界在这里被放大。TCP 本身不保留消息边界，你收到的字节流随时可能把一条 TLS 记录或一个应用帧切在中间。包装层的职责之一就是维护”帧边界”：把零散到达的字节先存进内部缓冲，直到攒够一个完整帧再向上交付一帧，攒不够就返回 Pending 等下一次数据。这就是为什么握手未完成时读写都会返回 Pending：TLS 握手本身是”发几条消息、收几条消息”交替进行的状态机，握手没走完，加密通道还没建立，此时任何 poll_read/poll_write 都无从进行，实现只能把握手当成当前正在推进的读/写目标——握手数据没到就 Pending，握手数据到了一部分就推进握手状态再 Pending，直到握手完成才切换到真正的用户数据读写。

IO 任务的工程守则

前面各节讲的是机制，这一节把它们收敛成能在 code review 里逐条对照的守则。怎么写一个服务归《Rust 网络编程实战》《Rust Web 服务实践》，这里只固化与 IO 模型直接相关的工程纪律。

守则一：每连接一个任务的所有权模型。最省心也最常见的结构，是为每个连接 spawn 一个专属任务，让它独占持有这个连接句柄（读写都在同一个任务里顺序推进）。好处直接对应前几节：一个 fd 只被一个任务关注，不存在多 Waker 争一个 fd 的竞态；连接的 fd 归属清晰，drop 这个任务就 drop 连接、缓冲区随 fd 回收，超时与清理都落在同一个所有权上。代价是读写被串行化，所以引出守则二。

守则二：读写要么并发地拆分所有权，要么接受串行。如果一条连接需要”同时能读、同时能写”（比如双向流、或读到一个请求后要边处理边能继续读下一个），就要用 split 一类手段把读写句柄拆成两个可独立持有的半边，分别交给不同任务，让读写互不阻塞。但拆开的代价是把”谁持有 fd”变成了”两个半边共同背靠一个连接”，于是守则一的”一个 fd 一个 Waker”约束要由拆分实现来保证安全。反过来，如果你不拆分、读写挤在一个任务里顺序做，那么一次没写完的写（Pending 挂起写任务）会顺带把读也卡住，读方向的慢也会拖累写方向——这就是”不并发的后果”。要不要拆，取决于你的协议是否真的需要全双工并发，而不是”别人都拆所以我也拆”。

守则三：背压必须在应用层做，别指望内核替你兜底。内核的 TCP 发送缓冲是有界的，写满就 Pending，这本身是一种天然背压。但很多实现为了”不阻塞”，在应用里塞了一个无界队列去缓冲待发数据——慢客户端读得越慢，这个队列就堆得越长，最终把内存耗尽，触发 OOM 或让 GC/分配器抖动。正确做法是显式设一个有界缓冲，队列满时让生产侧要么阻塞在带超时的发送上、要么按策略丢弃并回压给上游（降速、返回 429 一类）。”有界缓冲 + 满了怎么办”这个决策，必须由应用层来做，因为只有应用知道”丢了这条数据”和”让上游慢下来”哪个更可接受。慢客户端耗尽内存这个事故，根因十有八九就是这一条没做。

守则四：连接池与超时要成套出现。复用连接能省握手与 fd 开销，但池里的空闲连接也有代价：占 fd、占对端资源、可能已被对端悄悄关闭。所以连接池必须配三类时间——获取连接的超时、单次 IO 的读写超时、空闲连接的回收时间。缺了 IO 超时，一个卡死的对端能把池里一条连接连同上面的任务一起永久挂起（呼应 Pending 违约那节：如果唤醒没登记好，连超时兜底都可能被绕过）；缺了空闲回收，池会越攒越多僵尸连接。把这些时间和守则一的”每连接一任务、drop 即清理”配合起来，才能让一条坏连接的影响被限制在它自己那一个任务和 fd 上，而不是扩散。

把四条守则收束成一句可执行的检查：每个 fd 是否只有一个明确持有者、读写并发是否真的必要且安全、待发队列是否有界且定义了满时行为、连接是否有配平的超时与回收。这四点过不了，前面所有机制讲得再透也会在深夜报警里还债。

观测与自建验证

机制和守则讲完，最后给一套”怎么在出问题时看、怎么设计验证”的方法。本文全程不给编造的吞吐或延迟数字——这类数字换个环境就不成立，反而是误导。这里只给”要看什么指标”和”怎么一次只改一层地验证”，数值口径一律标注为”示意值”，代表”这个量在涨还是在跌”的方向，而非绝对性能。

先看要观测的量。第一组是资源侧：打开的 fd 数（是不是接近进程上限、是不是只增不减——只增不减往往说明连接没被真正回收）、任务数与就绪队列长度（是不是某个阶段之后任务永久挂起导致活跃任务堆积）。第二组是 IO 健康侧：读写错误分类——把 WouldBlock（正常空读/背压）、真正的连接错误、超时分别计数，混在一起看等于没看；Pending 比例，即一次读请求里返回 Pending 的占比，它异常升高通常指向登记唤醒出问题或底层真慢。第三组是生命周期侧：连接从建立到关闭的存活时间分布，双峰（一堆秒开秒关 + 一堆超长）往往意味着一类连接没走优雅关闭。把这些指标做成随时间曲线，比看单点数值有用得多。

关于”Pending 比例”要特别强调它是排查前面那些违约症状的主线索：一个健康连接在无数据时应大量返回 Pending 又被正常唤醒，但如果某类请求的 Pending 之后再也没有对应的 wake 计数上升，就高度怀疑”返回 Pending 前没登记唤醒”。把”每类 fd 的兴趣登记次数”和”对应 wake 次数”做成两个 counter 对照，是让这类隐性 bug 现形的最直接办法。

再谈验证方法，核心纪律是”一次只改一层”，否则你无法归因。本文各节正好给出了几条可独立拨动的”层”，验证时每次只动一条、其余冻结，观察指标往哪个方向变：

做这类验证时要控制变量、重复多轮取趋势，并且清楚它的天花板：本地压测环境复现不了生产的连接时长分布与突发模式，所以这里的结论只用来定位”改动影响的方向”，不用来给绝对性能背书。任何”改完吞吐翻倍”的说法，在没有可复现方法与口径之前，本文不予采纳，也建议你在自己的复盘里不予采纳。把观测做细、把验证做成单变量，是把 IO 疑难问题从”玄学”变成”工程”的关键一步。

四种模型对照表

把全文收敛成一张可贴在工位上的表。四列语义要认清：内核告诉你什么（暗示还是结果）、代码要自己处理什么、典型失败模式、以及 Rust 里靠什么表达这一形态。

读这张表时对照前文各节：就绪驱动两行的”可以试了”，就是第 1 节说的”内核给的是暗示不是结果”，它派生出”循环读到 WouldBlock””部分写要自己推游标”这些义务；而完成驱动那行”办完了带结果”省掉了空读，却把责任搬到了”缓冲区生命周期”和”队列背压”。”典型失败模式”那一列几乎每一格都能在前文找到对应的排查条目——Pending 违约对应永久挂起，边缘没读干净对应漏数据，无界队列对应内存耗尽，完成模型持缓冲不当对应 use-after-free。最后一列想强调的是：Rust 上层代码基本只认 poll_* 这套就绪语义，完成模型也是被适配成这套语义后才进入视野，所以掌握这套契约，比记住某个后端的名字更耐用。

小结

本文沿着”内核到底告诉你什么”这条主线，把 Rust 异步 IO 从操作系统形态一路讲到工程守则。核心可以浓缩成三句话。第一，Rust 的 AsyncRead/AsyncWrite 契约是就绪驱动味道：poll 给的是”此刻能不能推进”，”数据够不够、写没写干净”由你自己靠返回值判断，于是催生了”循环读到 WouldBlock””部分写要推进游标””返回 Pending 前必须登记唤醒”这几条硬纪律。第二，Rust 侧 future 的生命周期和内核侧 fd/socket 的生命周期是两套，取消只停前者——“到达但未读的数据不归 future 管”，这是理解超时串包与优雅关闭为什么要分写半边读半边的钥匙。第三，完成模型能省掉空读，但把复杂度转移到缓冲区生命周期与队列背压，而同一套上层 trait 能把两种底层都包住，掌握契约比记住后端名字更耐用。

给读者的落地建议：优先采用每连接一个任务、所有权清晰的结构；只有协议确实需要全双工时才用 split 拆读写；任何待发路径都要有界并定义满时行为；连接池配平获取超时、IO 超时与空闲回收；把”兴趣登记次数”和”wake 次数”两个 counter 长期挂着，让 Pending 违约这类静默 bug 无处藏身。验证问题时坚持”一次只改一层”，只看方向不认绝对数字。把这些做扎实，绝大多数深夜的”连接卡住””内存涨爆””偶发串包”都能被归到本文明确列出的某一层，而不是留给运气。
