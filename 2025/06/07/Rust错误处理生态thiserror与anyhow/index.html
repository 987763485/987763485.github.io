Rust 错误处理生态：thiserror 与 anyhow

本文属于《Rust 学习路线》第 23/68 篇
上一篇系列目录下一篇

本文讲 Rust 错误处理的生态库与工程策略：什么时候用 thiserror、什么时候用 anyhow，错误链里该放什么，调用方又该如何凭错误决定重试、降级、报警还是失败。

错误是值，但组合没人管

Rust 没有异常（exception）机制，错误像普通数据一样被当作值返回、被当作值传递，最常见的落点是标准库的 Result<T, E>：成功携带 T，失败携带 E，向上传播靠 ? 运算符——成功取出值继续走，失败立刻作为当前函数的返回值交回调用方。好处是每个函数可能败在哪里都写在签名里；直接的代价是错误类型必须自己可组合：一个函数调用三个库、各有一套错误枚举时，它的 E 没法同时是三种类型，总要有人把不同来源的错误转换、收敛成一个。语言层只给 std::error::Error 这个 trait 和 From 转换做接口，把样板压到最低是生态库的事，语言底座的部分往期《Rust 错误处理》已经讲透，本文只讲站在它上面的两个库与工程策略。生态分工是：thiserror 帮库快速生成精确的错误类型，anyhow 帮应用抹平类型细节、只留下发生了什么。

库要精确可判别，应用要省事可聚合

先给出本文的核心结论：库要错误精确、可判别，走 thiserror 路线；应用要写得省事、可聚合，走 anyhow 路线。库的价值在 API 契约上，调用方常要按失败的种类做分支——超时重试、权限拒绝重新授权、数据损坏降级，都得 match 到具体变体；应用的价值在把流程跑完，多数失败在顶层只有一个处置：把整条链记进日志然后终止。让应用为每个模块维护一棵完整错误树，是纯粹的开销。同一个配置文件读失败，在两处的写法是：

thiserror：把错误类型的样板交给派生宏

thiserror 定位是实现 std::error::Error 的辅助库，用来定义公开错误类型，不参与运行时。日常用到三样：#[derive(Error)] 生成 trait 实现骨架；#[error("...")] 里的字符串是 Display 模板，花括号直接内嵌字段值；#[from] 与 #[source] 负责错误链（error chain）的挂接。

Timeout 不包装下层，只是把字段带够、让 Display 说人话。BadResponse 用 #[source] 存住 serde_json::Error，链展开时可见原始错误，构造点要自己写；Transport 用 #[from]，自动获得从 io 错误到本变体的 From 转换，io 操作后面可以直接打 ?。取舍在于：#[from] 省掉手写转换，却把一个外部错误类型钉死在固定变体上；#[source] 多写几行构造代码，换来选变体的自由。多种来源要落进同一个语义变体时 #[source] 更稳，因为 From 无法按字段值重载。

另有一条工程纪律：库不该把三方错误原样公开成自己 enum 的变体，公开变体直接包装三方错误类型，三方一改就成了你这个库的破坏性变更——那个 enum 是你公开 API 的一部分。正确姿势是包成自己的语义变体，三方类型靠 #[source] 只沿链可见；确需透传单一错误时才用 #[error(transparent)]，那等于把三方的展示口径也纳入契约。派生宏（derive macro）本身怎么写，本批另有《Rust 派生宏实现》专讲，本文只谈用法。

anyhow：一路兜底，代价是失去静态判别

anyhow 解决反方向的问题：让应用尽量不写具体错误类型。核心是 anyhow::Error，内部是一个特征对象（trait object），装下任何满足 Send、Sync、’static 的 std::error::Error；类型细节在这里被擦除（type erasure），编译器不再知道错误来自 io、解析还是业务规则，也就无法在编译期 match 判别。anyhow::Result 是 Result<T, anyhow::Error> 的别名，main 可以直接返回 anyhow::Result<()>，失败时运行时打印整条链。混合返回类型靠 ? 背后的 From 通路统一：外层返回 anyhow::Result 时，内部任何 Result<T, E> 遇到 ? 都被自动转成内部的 trait object，所以应用几乎不需要手写转换。加语境用 context 与 with_context：

context 适合固定短语，with_context 适合要带局部变量的延迟拼接，闭包只在失败分支执行。要找回具体类型时用 downcast 试探已知的库错误，代价是耦合：上层名义上类型擦除，实际私下认识下层的每个具体类型，绕开了 trait object 的设计初衷，而且是运行时判定、编译期拦不住。所以把它限制在两处：顶层把少数已知错误映射成退出码或状态码，测试里断言失败原因。中层出现要 downcast 的信号，说明这条链路该换 thiserror 路线。

错误链怎么读、怎么打印

std::error::Error 的 source 方法返回下一层错误的引用，一路取到 None，链就展开完了。thiserror 路线的链每环都是语义变体，读链就是在读失败过程；anyhow 路线的链由 ? 的自动包装加逐层 context 构成。书写纪律一致：每层只补这一层知道的事实——什么操作在哪一层失败——不复读下层原文，不替下层猜原因。链里只放事实、不放建议，因为日志里的链是证据不是操作手册：把“请稍后重试或联系管理员”写进链，会污染按消息聚合与检索，措辞一改下游匹配就断；建议归各入口的输出层，CLI 在链之后单独打指引，HTTP 把建议放进错误码字典的说明字段。打印口径因入口而异：CLI 的 main 返回 anyhow::Result，默认逐层缩进输出整条链，给人看终端，信息越全越好；HTTP 相反，链绝不进响应体，对外只有错误码、一句安全文案和一个追踪标识，全链写内部日志；库测试断言变体身份与字段值，不断言 Display 的字面串，因为模板措辞是展示口径不是契约。

用错误分类驱动处置策略

这是错误处理里最值得花设计力气的一节。调用方的处置其实只有四种：重试、降级、报警、直接失败并把原因告诉用户。网络抖动重试，缓存数据损坏降级到副本，不变量破坏报警，用户输入错误直接失败。于是什么信息值得进错误类型有了判据：会不会改变处置。会改变的——是否可重试、是否超时、是否权限、是否数据问题——进类型或变体；不会的——给人看的描述——留在 Display 里，不污染类型系统。分类枚举的骨架可以这样立：

退出码与状态码：把错误翻译成外部契约

粒度看外部脚本是否消费，没人区分的类别就合并；码值一旦发布就是契约，收不回来。常见的坑是深层代码直接调 process::exit：绕过清理，还会把测试进程一起带走；纪律是函数只返回错误，映射统一发生在 main 层。HTTP 服务做同构而反向的映射：内部链换成状态码加响应体，红线是不泄漏内部链——对外只有错误码、安全文案和追踪标识，堆栈细节、下层服务地址、SQL 片段只进内部日志。状态码表达 HTTP 语义，错误码表达业务语义，两者独立演化，所以要维护错误码字典，让后端枚举与前端常量文件同源生成，禁止随手加码。跨语言的错误码治理往期《业务错误码组织》已有讨论，本文只在出口映射这一处与它对照。

错误与日志、追踪的衔接

错误日志最坏的姿势是层层都打。错误既然已通过 ? 往上带、顶层会连链一起输出，中间每层再记一遍，一次失败就复制出十几行日志，淹死真正的信号。口径是：错误只在处理点记录一次——决定重试、降级、报警的那一层，或服务顶层中间件——其余各层只负责让链继续生长。用 tracing 这类结构化记录框架时，处理点的错误事件应带低基数（low cardinality）字段：操作名、阶段、目标（哪个下游服务、哪张表），取值集合有限，适合聚合与告警规则。反过来，禁止进日志的是：令牌与其他凭据字段、堆转储内容、用户手机号与精确地理位置、请求体原文。尤其要记住错误的 Display 本身也是日志内容——下层可能把连接串拼进消息，上日志前要过白名单或脱敏。跨请求的关联交给追踪标识（trace ID），由顶层连同链打一次，中间层不要各自发明。日志本身的写路径与 sink 实现归本批《Rust 高性能日志库实现》，本文只谈错误一侧的衔接口径。

panic 的边界

Rust 用 panic 表达的是程序不变量破了，不是操作失败。数组下标越界、match 走进不可达分支、对 None 强行 unwrap，意味着代码对世界的前提假设已经不成立，继续走下去比停下来错得更远；查不到记录、连接被对端重置、JSON 不合法都在正常可能性集合内，属于 Result 的辖区。库默认不 panic，因为库无法知道宿主进程能不能接受整个终止：解析库被畸形输入触发 panic，等于任何外部数据包都能杀死宿主。公开 API 要把一切可恢复失败做成 Err，确有不可恢复的内部断言就写进文档。catch_unwind 的适用面很窄：把代码交给无法返回错误的边界（例如传入 C 侧的回调）时防止跨语言展开，或测试框架隔离用例崩溃；能否 catch 到取决于 panic 策略与栈，2024 edition 起展开穿过 extern “C” 边界还会直接转为 abort，而且 catch 之后程序状态是否可用没有任何保证，所以它是止损手段而非错误处理机制。crate 顶部挂 #[forbid(unsafe_code)] 这类策略与错误处理的关系间接但实在：禁掉 unsafe，内存类灾难失去来源，错误面收敛到 I/O、解析、权限这些可枚举的种类，上一节的分类枚举才立得住。

什么时候仍然要手写 Display 与 Error

thiserror 存在的理由是手写实现的重复度太难看：一个 enum 八个变体，Display 要八个分支的措辞，source 又要八个分支的映射，两段 match 必须永远同步，新增变体漏掉任何一段都是隐性 bug。派生宏生成的正是这两个 trait 方法的骨架——Display 的格式化实现按每个 #[error] 模板填好，source 的逐层返回按 #[from]、#[source] 标注的字段接好——本文描述到这个行为层面即可，不猜测生成代码的细节。仍有三种场合要回到手写：其一，泛型 bound 复杂，例如给任意实现 Error 的 E 做包装器、展示行为要依赖内层错误；其二，展示格式要动态组装，多行报告、字段对齐、按条件取舍的段落，超出字符串模板的能力；其三，携带不实现 Debug 的上下文或非常规生命周期，手写才能精确控制 bound。手写换来的是义务：Display 文本从此当契约维护，日志检索和下游脚本可能依赖它，公开 crate 里改措辞就是破坏性变更。

迁移与混用：边界 anyhow，内部 thiserror

常见的两种滑坡：库 crate 里到处 anyhow，公开 API 成了无法判别的黑盒；或者应用里也维护完整错误树，每个新调用点都要补 From 实现。迁移口径一句话：边界 anyhow、内部 thiserror——跨 crate 的公开 API 与模块间传递用精确类型，应用主流程与 CLI、服务的顶层收敛到 anyhow。多 crate 的 workspace 里，错误类型跟着语义走：存储层定义存储错误，业务层包成业务错误变体并用 #[source] 保留下层，展示层只见业务错误，谁都不该越层直接 match 三层的类型。动手之前过一遍这份清单：

公开 API 的稳定性要单独权衡：公开 thiserror enum 加变体、删字段、调整语义都会打断下游的 match，全是破坏性变更；对没把握长期冻结的错误集合，不如从第一天就把公开面做成不透明错误类型加几个判别方法，具体 enum 圈在 crate 内。这两个库本身值不值得选，评估口径归本批《Rust 生态 crates 推荐》，本文只讲它们怎么用、怎么混用。

场景对照表

把全文的分工收进一张表，遇到具体工程问题先对号入座：

场景 推荐做法 不该做什么 理由
写库 公开 thiserror 语义 enum，三方错误进 #[source] 公开变体直接透传三方错误 错误类型是 API 契约
写应用主流程 anyhow::Result，逐层 context 补语境 为每个模块手写错误树 主流程只要聚合与终止
写 CLI main 返回 anyhow::Result，顶层映射退出码 深层调用点直接 process::exit 绕过清理，测试遭殃
写 HTTP 服务 处理点记全链，对外只给错误码与状态码 把内部链写进响应体 外部契约不含内部信息
内部模块间传递 包进上层语义变体并保留 source 用字符串拼接吞掉类型 链可读，类型可判别
需要重试判别 可重试性做进变体或谓词 靠 match Display 文本 文本是展示口径非契约

表里列的多半不是语法错误，而是评审时容易被放过的债，越早拦越便宜。

小结

本文的主干还是那句分工：库要精确可判别，走 thiserror；应用要省事可聚合，走 anyhow；边界处混用。thiserror 把定义公开错误类型的样板压进几行属性，#[error] 管展示、#[from] 与 #[source] 管链；anyhow 用特征对象抹平类型、用 context 逐层补语境，downcast 只留给顶层出口和测试。两个库之上是一套工程纪律：分类决定重试、降级、报警还是失败，不改变处置的信息不进类型；链里只放事实，日志只在处理点打一次，敏感与高基数字段禁入日志；出口把链翻译成退出码或状态码，不泄漏内部；panic 只留给不变量破坏，库默认不 panic。错误类型一旦公开就最难改，每加一个变体都先问它会不会改变调用方的处置，会的才配进类型。
