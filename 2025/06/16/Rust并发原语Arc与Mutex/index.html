Rust 并发原语：Arc 与 Mutex

本文属于《Rust 学习路线》第 31/68 篇
上一篇系列目录下一篇

本文面向第一次面对多线程共享状态的读者：Rc 为什么递不出线程、Arc 与 Mutex 各自买来了什么、代价在哪里。读完应能回答三个问题——状态归谁所有、临界区该多短、什么时候换别的共享形态。文中代码按 2024 edition（随 Rust 1.85 于 2025-02-20 发布）后的标准库书写。

问题：共享可变状态必须写进类型

多数语言里，多线程共享可变内存是”运行时约定”：文档写着”这里要加锁”，代码忘了也不报错。Rust 走了另一条路——共享与可变必须在类型上同时成立才放行，互斥锁（Mutex，互斥量）、引用计数、消息传递这些选择会被写进函数签名和结构体字段，一眼可见。

编译器会给出类似 the trait Send is not implemented for Rc<Vec<_>> 的报错，说的是 Send 与 Sync 这两个标记特质的边界：Send 表示所有权可以安全转移到另一个线程，Sync 表示多线程可以同时持有它的引用。Rc 的计数是普通加减而非原子操作，并发增减会丢次数，对象会被提前释放或永远泄漏，所以标准库让 Rc 不满足这两个约束。借用检查基础归往期《Rust 借用与生命周期》，本文只把 Send/Sync 当语义边界使用。

Arc：把计数交给原子操作

Arc（原子引用计数，Atomic Reference Counting）与 Rc 的区别只在计数方式：句柄的每次诞生与析构都是一次原子加减，最后一个强句柄释放时才回收数据。Arc::clone 克隆的只是句柄，不是数据本身；标准库风格鼓励写 Arc::clone(&x) 而非 x.clone()，就是为了让这种廉价但并非免费的克隆在代码里显眼。

强计数之外还有弱计数：Weak 不保证数据存活，只能经 upgrade 尝试换回 Arc，换不回即数据已释放。父子互持强引用构成循环引用，强计数永不归零；惯例是父指子用强引用、子指父用 Weak。

什么时候不该用 Arc：状态若能归单一所有者，把变更请求经 channel 递进去更安全；数据若在编译期确定长存（常量表、静态配置），共享 &'static 不可变引用即可，不需要计数。Arc 适合”多线程共享、谁最后用完谁负责释放”这类生命周期不确定的场景。

引用计数的真实代价

每次 Arc::clone 与句柄析构都是一次原子加减。原子操作意味着要把对应的缓存行（cache line）在多个核心之间搬运并保持独占。几十个线程频繁生灭句柄时，所有核心都在争用存放计数的那一个缓存行，计数本身成了热点。它与锁开销是两笔账：锁争用在数据访问路径上，计数争用在句柄生灭路径上，从不进锁却频繁克隆的程序照样可能被计数拖住。本文不引具体倍数或纳秒数（这类数字强依赖硬件与访问模式），只讲方向：句柄生灭越频繁、线程越跨核，计数争用越明显。

缓解方向是减少句柄的生灭，而不是给数据加更多锁：

能传 &Arc<T> 借用就不要克隆；进入线程前克隆一次，好过线程内反复克隆；用到才取句柄、用完就放，好过处处持有。句柄长期驻留各线程、只在共享数据上动计数时，开销自然回落。

Mutex：数据被锁在类型里

多数语言里锁与数据是两样东西，忘没忘锁全靠自觉——Go 的 sync.Mutex 与 Java 的 synchronized 对同一问题就是这个不同表达。Rust 的 Mutex<T> 把数据 T 直接包进锁类型：想碰数据必须先 lock 拿到守卫（MutexGuard），守卫像引用一样访问数据，离开作用域自动解锁。”忘记加锁”在这里不靠纪律避免，而是类型上根本拿不到数据。

收缩临界区的具体手法

先读后写（copy-on-read）：临界区只拷出决策所需的最小数据，计算与构造在锁外做，最后再进锁写回，并用版本号或 compare_exchange 校验期间有没有被插队；原子替换的内存序细节只此一句对照，归《Rust 无锁编程与原子操作》。

批量提交：不要”来一条改一次锁”，线程本地攒一批再一次性进锁合并，进锁次数从每条一次降到每批一次。

把计数累加挪到线程本地：统计类写入（计数、直方图）最耗锁。给每个线程或分片一份本地计数，定期合并进全局，就把”一把全局锁的频繁争用”换成”若干几乎不争用的锁加一次低成本合并”——这正是分片思想在计数上的应用。

临界区里绝对不放的东西，一份清单：阻塞 IO 与任何可能久睡的系统调用；等待另一把锁（嵌套加锁是死锁的温床）；回调用户代码或 trait 对象方法（它可能反手再拿这把锁）；把日志刷到远端（网络一抖，等锁线程跟着卡）。原则只有一句话：临界区里只放”不做就会坏”的那几行。

中毒与错误传播

Mutex::lock 返回 Result 而不是直接返回守卫，是别的语言没有的设计：持锁线程若在临界区里 panic，锁最终会释放，但数据可能停在”改了一半”的中间态，后续线程不设防就会在坏数据上继续操作。标准库把这样的锁标记为中毒（poisoning），之后的 lock 返回 Err(PoisonError)，提醒数据状态可疑。

PoisonError 包裹着守卫，into_inner 依然能拿到数据——决定权交回使用方。很多服务的实际选择是另外两条路：要么约定临界区里不允许 panic，把可失败操作写成返回 Result 并尽早返回；要么在 Mutex 之外建立恢复策略，中毒后重建该状态域。生态里也有不提供中毒语义的第三方锁，默认 panic 后数据仍可用，把判断彻底交给开发者——少一层保护，也少一层 unwrap 噪音，引入与否看你自己的容忍设计。标准库 RwLock 同样有中毒语义。

RwLock：读多写少才值得考虑

RwLock（读写锁）允许多个读者同时持有 read 守卫，写者独占 write 守卫。它只在读远多于写、读者真的同时到来且读临界区够长时才明显划算。常见误判是”把 Mutex 换成 RwLock 一定更快”——读者之间虽不互斥，但”当前有几个读者”这个计数是所有读者都要原子修改的共享写点；读临界区极短时，它可能比 Mutex 的直接互斥更贵。

写者饥饿也是真实问题：源源不断的新读者可以永远排在等待中的写者前面。标准库对写者优先不作承诺；要求写者及时落地时，用批次或闸门控制读者进入，别指望锁本身公平。

什么时候宁可回到分片 Mutex：当”读多”其实读的是不同数据（按 key 分片后各片各自读写）、或写占比并不低时，一组小 Mutex 往往比一把全局 RwLock 更可预测——前者把争用点打散，后者只是改变了争用的形式。

替代方案谱系

Arc + Mutex 不是唯一解，按”状态归谁、冲突多不多”往下选，各说机制与边界：

原子类型加比较并交换（Compare-And-Swap，CAS）循环：单个计数器、标志位、小状态字，用 AtomicUsize 这类类型的 compare_exchange 做”读—算—写回，失败就重试”。边界是状态能压进一个字且冲突率低，用它维护多字段不变量就是误用。

不可变快照加原子替换：读多写少的配置表、路由表、插件清单的惯解。写者构造一份全新的完整快照，原子地把指针换过去；读者拿到的永远是某一刻的完整版本。与上一项的对照只有一句：CAS 改的是一个字，快照换的是整个指针。

channel 消息传递：与其共享可变状态，不如把状态收敛给单一线程所有，其余参与者发消息请求变更；锁离开数据路径，代价是协议自己设计。channel 与线程模型归往期《Rust 线程与消息传递》，此处不展开。

锁分片（striped lock，条纹锁）：按 key 哈希把大表切成若干片，每片一把小 Mutex；读写只碰自己那片，只有热点 key 才退化回争同一把锁。适合”操作天然可分区、跨分区原子性可放弃”的场景。

无锁队列：只在并发结构的最底层（任务队列、就绪队列）出现。正确的通用无锁队列远难于加锁版本，除非确切知道在解决哪类争用，否则别当日常选项。

死锁形态与预防

死锁（deadlock）常见四种形态。一是锁顺序不成文：甲模块先锁 A 再锁 B，乙模块反着来，两个线程各持一半互等——标准库不替你对齐顺序，只能靠约定。二是重入：标准库的 Mutex 不可重入，同一线程二次 lock 同一把锁会当场自锁，最常见踩法是持锁函数再调用另一个也要拿这把锁的方法。三是持锁回调：临界区里调用 trait 对象方法或用户闭包，对方反手来拿这把锁，制造反向依赖。四是守卫跨模块传递：把 MutexGuard 塞进返回值或存进结构体，锁的生命周期脱离当前作用域，谁解锁、何时解锁变成猜谜。

排查思路：卡住时先抓各线程栈，看是否两个线程分别停在 lock，而各自持有的锁恰是对方的等待对象；再审计所有锁内还会调用的函数。预防清单：给全局锁集合定固定加锁顺序并写进注释；临界区尽量短；能不嵌套就不嵌套，必须组合时用 Mutex::try_lock 加退避——拿不到就换条路，代价是要写重试策略；绝不在持锁时调用不特定的回调；守卫不过函数边界。

与异步的交界

在 async 函数里调用阻塞的 Mutex::lock，等锁期间会占住当前线程：worker 数量远少于任务数，一个 worker 睡在锁上，挂在它上面的任务全部停摆，锁一热便是全局卡。worker 周转与调度归本批《Rust 异步运行时源码解析》，本文只此一句衔接：async 里的阻塞调用应视为例外，必要时挪进专用线程。

另一类问题是守卫跨 await：

拿着 MutexGuard 进入 .await，任务将来可能换线程恢复，而守卫绑定了线程纪律；异步运行时的任务要求 Send，编译器于是直接报错——这是好事，它提醒你把临界区收在两个 await 之间，或改用异步锁（如 tokio::sync::Mutex）。标准库 Mutex 配同步线程与短临界区，异步 Mutex 配确实需要跨 await 持锁的场景；混用前先问：这次等待该不该让出线程。细节留给异步篇。

小结

Rust 的并发原语把别的语言里靠纪律的事搬进了类型：Arc 让共享的生命周期可见，Mutex 让”拿到守卫才能碰数据”成为编译期事实，中毒语义让 panic 后的可疑状态必须被显式表态。选型不看哪种锁更高级，只看三个问题：状态归谁所有、读写比例长什么样、临界区能不能再短一点。计数开销与锁开销是两本账——减少句柄克隆、收缩临界区，通常比换一种锁更有效。无锁结构与内存序、channel 与线程模型、异步运行时调度，本文都只在边界处一句带过，深水区别有专文。把 Send/Sync 当语义来读、把锁当类型来写，共享可变状态就从事故源头变成可审查的设计。
