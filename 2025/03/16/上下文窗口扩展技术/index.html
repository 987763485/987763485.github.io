上下文窗口扩展技术

破题：窗口变大不等于记忆变好

本文的第一个结论：上下文窗口是容量指标，不是能力指标。材料塞得进窗口，只说明模型在数学上看得见它，不说明推理时用得上它。可以把窗口理解成一张工作台：台面变大，能摊开的纸变多了，但读纸的人还是同一个人，他的注意力并没有变多；新的问题不是放不放得下，而是该摊开哪些、哪些另存到抽屉里。

第二个结论：长上下文的利用率是衰减的，且不均匀。同样的信息放在开头、中间、结尾，被召回的概率并不相等，所以扩窗口的真实收益往往低于容量数字暗示的收益。稳妥的默认假设是：窗口里每一个 token 都要为自己争取被用到的机会。

第三个结论：一段材料如果永远只需要部分被用到，把它整段常驻就是浪费。检索链路与分块召回归《RAG 检索增强生成实战》《RAG 工程化落地》《RAG 分块策略与召回优化》三篇，本文不重讲；本文只看窗口这一侧——它能长到多大、代价如何分布、什么条件下值得扩。

模型答错长文档里的问题，先怀疑注意力被稀释或者约束位置不利，而不是窗口不够大。

两条成本线：注意力计算与键值缓存

本文的结论：序列变长时模型要付两笔性质不同的钱——一笔是解码阶段的缓存，近似线性；另一笔是注意力计算与显存访问，更陡。分开看才理解为什么长窗口比大参数更难伺候。

第一条线是键值缓存。自回归解码时每一步都要让当前查询比对历史所有 token 的键与值，这些键值对被缓存下来，长度每加一个 token 就按固定比例变胖。直觉到这里为止：键值缓存随长度线性增长。显存分配与分页机制归《大模型推理优化：KV Cache 与 PagedAttention》，本文不展开。线性增长的好处是可预测：并发数、单请求长度、显存上限之间是干净的乘法关系。

第二条线是注意力本身。标准实现里每个查询要看见每个键，成对交互随长度按平方趋势增长。即便解码阶段常以”一个查询对很多键”把单步计算拉回线性，预填充阶段的成对结构仍让成本显著抬升。某个模型在某段长度上的延迟与吞吐数值，本文一律不给，请以当期官方文档核对。

两笔钱叠起来有个推论：长上下文的成本主要花在每次请求都要重读一遍，而不是窗口开大了占地方——窗口不收费，读它才收费。让读更快是推理引擎的事，让读得更少是应用层的事。

位置编码这条线：为什么要外推

本文的结论：模型能读多长，很大程度取决于它如何知道谁在谁后面，位置编码正是”训练短、用得长”得以成立的根因。

为什么要外推。位置编码把序号映射成可感知信号，训练时模型只见过某个范围内的序号。超范围的输入落在从未出现过的编码分布上，距离感就失真：远处引用对不上，同指关系错乱。突破范围有两条路：把新序号映射回见过的分布，或者改造映射本身。

位置插值走第一条。它把超范围的序号按比例压缩回训练取值，等于把位置轴整体缩放后再喂给模型；改动极小，代价是相邻位置变密，通常要配合一段短期继续训练来校准注意力。旋转位置编码走第二条。它把位置表示成作用在查询与键上的旋转角度，相对关系由角度差体现：只要频率分量足够丰富，角度差在很大距离上都保持可分辨；粗的分量看长程结构，细的分量看邻居关系。本文只讲机制，不写任何具体 token 上限数字，请以当期官方文档核对。

边界要划清：位置编码决定能不能对齐，不决定对齐之后用得好不好，外推不修复注意力稀释。

工程上的替代路线

本文的结论：多数长文档场景不需要把全部材料常驻窗口，四条替代路线各自把”长”这个问题削掉。

第一条是滑动或分块处理。把输入切成窗口能舒适承载的片段逐段处理，只留一小段重叠区衔接。它适合结构弱、顺序强的任务，例如逐段翻译；前提是每个片段的输出能独立成立，重叠区太短会切断指代，太长又抬回成本。

第二条是层次化摘要。先对小块做摘要再逐级向上合并，常驻窗口的是各层摘要而不是原文。价值是把总量压下来，代价是压缩单向，细节一旦丢掉就取不回来，因此适合趋势判断，不适合条款核对。

第三条是检索式外部存储。这里只作划界，链路与召回归前述三篇 RAG 文章。它与扩窗口互补：检索决定哪些内容进来，窗口决定能同时看见多少。

第四条是把长文档切成可寻址单元。它与分块不同：分块是为了流过窗口，可寻址切分是为了引用。做法是给文档建立章节号、条款号、行号这样的内部坐标系，提示里只放目录与清单，需要哪一块就按坐标取哪一块，模型因此能输出”依据第几条”这类可核验的指针。

中间遗忘：位置比内容更影响命中率

本文的结论：长上下文里一条信息被用到的概率，很大程度由位置决定。开头与结尾命中率较高，中间容易被忽略——业界常以”中间遗忘”（lost in the middle）描述这一现象。本文不给具体百分比，这类数字随模型与任务大幅波动，请以当期官方文档核对。

机制上有两种解释。其一是训练分布的偏置：指令与结论常在开头，答案与终止信号常在结尾，模型自然学到两端更值得分配注意力。其二是实现结构：因果掩码、位置分辨率与缓存访问方式，共同让中段且距离较远的键更容易被摊薄。两者指向同一个动作——别假设模型会均匀扫描输入。

由此推出四条写法。硬约束在开头和结尾各写一次：开头给角色、任务与格式，结尾复述最关键的禁令，这是把信息挪出低利用率区域最便宜的办法。关键约束不要穿过中间：中段适合可以粗读的背景材料，不适合必须逐条满足的规则；模型漏掉规则时先检查位置而不是措辞。警惕结尾被污染：塞满客套话或无关日志就会抵消收益，结尾应当短、硬、结构化。多文档混排要标注归属与优先级，否则示例会被当成规范。

把长对话压缩成分层存储归《Agent 记忆系统设计》；本文停在输入构造这一层：位置是免费的变量，先调好它再谈别的。

缓存与成本的联动

本文的结论：前缀稳定就是省钱。多数服务在推理侧提供提示前缀缓存，命中的部分不必重算、计费更低；前缀里某个字节一变，从那个点往后的缓存全部作废。

为什么按前缀而不是按内容块？因为自回归计算有严格的依赖顺序，某个位置的中间结果取决于它之前的全部 token，把两个”内容相同但前缀不同”的请求视为可复用在数学上不成立。缓存友好的结构是：最前面放完全静态的系统指令与工具定义，其次放变化极少的上下文，最后放每次都不同的用户输入。

常见的失效写法有三种：时间戳放在开头，等于每次重建前缀；随机化示例顺序放在开头，同样致命；系统指令里嵌入请求 id 或用户名，让所有请求的开头都不一样。修正方式很朴素——动态字段挪到最后。

选型判断表：扩窗口、上检索、还是做摘要

本文的结论：选哪条路线取决于两个轴——是否需要逐字精确，总量是否远超窗口。两轴交叉，答案基本唯一。

先看纵轴。条款核对、法规引用、日志字段值、真实函数签名要逐字精确，不接受”语义接近但表述走样”，有损摘要尤其危险；主题归纳、跨章节问答这类不要求逐字的，摘要与检索都够用。再看横轴。装得进窗口就别引入额外链路，链路本身就是复杂度；远超窗口就得在窗口之外有存储，区别只在存可寻址原文还是存摘要。

据此给结论。装得下且要精确：直接扩窗口，把关键约束放到两端、把前缀做稳，这类最常见也最容易被过度设计。装得下但不要求精确：仍然扩窗口，摘要只是可选优化。装不下但要精确：扩窗口配合可寻址切分，目录先行、按需展开。装不下也不要精确：层次化摘要，必要时用检索补细节。

另有三条硬约束。要跨多段比对差异的，被比较对象必须同时在窗口里。顺序高度敏感的，扩窗口比逐段流过更安全。成本按请求数放大的，日请求上万时线性成本就成了硬顶。推理预算归《推理模型与思维链》，多智能体分工归《多智能体协作模式设计》，本文只谈单请求输入构造。

小结

本文把窗口扩展拆成三层。机制层，位置编码决定模型能否在超出训练范围的长度上保持距离感，插值靠缩放、旋转式靠角度差，它们只让长窗口可用。成本层，键值缓存随长度线性增长，注意力的成对结构抬升更快，真正贵的是每一次重读，所以前缀要稳、变量留在末尾。使用层，长上下文的利用不均匀，关键约束的位置比措辞更重要。

最常见的错误是装得下还偏上检索链路，以及装不下却硬塞有损摘要；其次是把所有材料一视同仁地摊开，不做目录也不标优先级，然后抱怨模型记不住。

最后留一个可执行顺序：先删无关材料，再把关键约束排布到两端，再检查前缀是否稳定，再决定要不要扩窗口，最后才考虑外部存储或摘要层次。窗口不是记忆，容量不是理解；具体模型的长度上限、延迟与价格，一律以当期官方文档核对。
