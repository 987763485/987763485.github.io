大模型私有化部署方案

本文谈的是方案层面：把一个通用大模型放进自己可控的环境里运行，事先要问清什么、有哪些路线、容量怎么估、成本怎么归因、什么情况下应该反过来选择买 API。引擎内部的调度与显存管理机制、单机量化工具链的操作步骤、训练路线的取舍，各自都有专门的文章覆盖，本文只做一句必要的划界，把同一套操作细节再讲一遍对读者没有价值。

私有化部署项目最常见的返工原因，是把一个部署问题当成了选型问题：先讨论用哪个模型，再补约束条件。顺序反了之后，选型结论会在第一次容量评审时被整体推翻，而且推翻的往往不是模型那一栏，是路线那一栏。所以本文的顺序是固定的：约束、路线、容量、并行边界、许可证、服务化、合规、运维、成本归因，最后才是决策树。

约束先于选型

结论：私有化部署的方案空间由约束决定，而不是由模型决定。约束问不全，任何方案都是猜测。

约束要问七类：数据边界、延迟红线、并发量级、可用性要求、审计与留存期限、预算周期、以及组织内是否已经有人在采购同一件事。最后一条听起来像行政问题，但它是真实的约束：如果集团里已经有一个云上专属环境正在采购周期内，重复自建会让成本归因彻底混乱，方案评审也会从技术比较滑向部门博弈。

数据能不能出内网，要问到人，不要问到部门。答案是”完全不能”的项目，路线空间立刻收缩到机房自建或者专线内的专属环境；答案是”某些字段不能”的项目，才有混合路线的余地。这两个答案的区别不在措辞，在于后面每一个环节要不要多一套数据分级与拦截机制。

延迟红线要拆成三个数字：首 token 延迟、完整响应延迟、超时之后业务侧的行为。只写”要快”的需求无法验收。首 token 延迟约束预填充阶段的并发预算，完整响应延迟约束生成长度上限，超时行为决定要不要流式输出、要不要降级文案。这三个数字不能取平均，方案必须分别满足。

并发量级问的是分布而不是峰值：请求数在一天里的小时分布、单个请求的平均输入长度与输出长度、长上下文请求的占比。私有化项目最典型的容量估算错误，是拿日均每秒请求数去推硬件，然后在早晚高峰被排队时间拖垮。长上下文占比尤其关键，因为缓存占用是长度乘以并发，不是长度加并发，一个占比很小但长度极大的请求类别，就能把整机的并发上限按住。

可用性要求要问清楚降级形态。模型不可用的时候，业务是硬失败、退回旧的规则系统、还是退回公有云 API？三种答案对应三种完全不同的成本结构：硬失败要求多副本和跨机房；退回旧系统意味着要长期维护一条可预测的兜底链路；退回公有云 API 则把数据边界问题重新打开，必须先在合规面上闭环，否则这条链路会成为审计时的第一个问题。

审计与留存期限决定日志粒度和存储量，也决定脱敏要在哪一层做。留存期越长，日志里能留下的字段就越少，二者要一起谈，不能分开谈。

预算周期最容易被忽略，但杀伤力最大。硬件采购通常是资本性支出，走年度审批；云上专属环境通常是运营性支出，按周期结算。两种支出模式对交付节奏的影响不一样：前者要求容量估算一次做对，追加周期太长；后者允许按季度调整，但要预先想清楚长期成本挂在谁头上。

下面这份清单可以直接拿去和业务方、安全方、财务方逐条过。括号里的目的是提示这一条会在后面哪个环节兑现成约束，不要收上来一堆没有归属的答案。

三条路线的适用条件

结论：三条路线的差别不在性能上限，在隐性成本和交付速度。绝大多数争论发生在性能上，而真正决定项目成败的是这两项。

第一条是完全自建，在自有机房采购加速卡并自己搭建服务。适用条件很清楚：数据完全不能出内网、延迟红线严格、并发量级已经稳定到可以一次性算准、组织内有人具备长期运维加速卡集群的能力。它的交付速度最慢，因为硬件采购、机房改造、网络布线、系统镜像准备是一串串行环节，任何一个环节卡住都会整体延后。隐性成本集中在三处：闲置期成本（模型换代和硬件采购周期错配，硬件到手时最好的开源模型可能已经换了一轮）、运维人力（加速卡的故障率和普通服务器不在一个量级，需要专门的人）、以及电力与制冷的长期账单。好处是成本结构可预测、数据边界干净、容量上限自己说了算。

第二条是云上专属环境，即在公有云厂商的隔离资源池里独占一套计算与网络。适用条件是：数据允许离开自己的机房但不允许混用公共资源、需要快速拿到较大容量、并发量级还在变化。它把交付速度提到最快的一档，因为资源是租的、扩容是按流程走的。隐性成本集中在长期账单和迁移锁定的可能性上：权重、镜像、日志格式如果和云上专属环境的托管服务绑得太深，之后回迁机房的代价会显著上升。此外还要注意，云上专属并不自动等于合规，隔离级别的描述要看合同原文和产品文档原文，不能靠”专属”两个字推断。

第三条是混合路线：敏感数据相关的部分自建，通用能力外呼到公有云 API。适用条件是数据分级能力成熟、能把”哪些请求可以出门”写成可执行的规则并拦住例外。它的首期成本最低，交付最快，因为敏感部分只需要承载一部分流量。隐性成本最高的一项是被低估的数据分级工作：分级规则需要维护、需要审计、需要有例外上报通道，而这些工作量在项目立项时通常不会出现在排期里。第二类隐性成本是行为不一致，自建模型和外部 API 的输出风格、拒答策略、长度习惯都不一样，用户会感到服务”人格分裂”，这需要在提示层或路由层做统一，又是一份长期成本。

混合路线还有一类常见的滑坡：一开始只外呼通用问答，后来发现自建模型在某类任务上表现差，于是外呼比例逐渐上升，最后敏感数据边界被业务方以”这一类不敏感”为由反复重新解释。判断一个混合方案能不能守住，关键不在技术而在决策权归属：数据分级判定权如果留在安全方手里，方案稳定；如果下放到业务方自证，方案会慢慢漂成纯外呼。

三条路线之外还有一个常被提出来但不该当作独立路线的选项：用现有一台机器先跑起来。它属于服务化的第一个台阶，不是路线，因为它没有回答数据边界和可用性问题，只是把延迟问题暂时隐藏起来。容量估算和服务化台阶分别放在后面的小节处理。

容量估算与并行边界

结论：私有化的硬件量级是估出来的，不是试出来的。估算要做两件事——把显存拆成随权重、随长度、随并发变化的三个部分，再把算力拆成预填充与解码两个瓶颈方向。至于单机工具链怎么把模型跑起来、量化格式怎么组织、引擎内部怎么管理缓存，分别属于专门文章的范围，本文一句带过：单机引擎与工具链实践见《ollama 本地大模型部署》《vLLM 推理加速实践》，量化格式细节见《模型量化与 GGUF 格式》，本文只需要”量化按比例压缩权重体积、并以精度损失为代价”这个方向性结论。

把三部分合起来，得到一个可以带进评审的不等式：单机可用显存乘以卡数，要大于权重占用加峰值缓存占用加常驻开销，再加约定的余量。任何一项被省略，都会以线上排队或请求被拒绝的形式回来。

算力的两个方向

单次前向的计算量可以按 FLOPs ≈ 2 × N × t 估算，其中 t 是本次前向处理的 token 数。这个近似式在方案层面足够用，它说明两件方向性的事。

第一件是预填充与解码的瓶颈方向不同。预填充一次性处理 t 个输入 token，计算量随 t 增长，通常是算力受限；解码每生成一个 token 只处理一个新 token，但要把整个权重和全部缓存从显存搬运一遍，通常是带宽受限。所以两者的容量估算不能共用一个数字：预填充预算决定同样算力下能吃下多少输入 token，解码预算决定并发序列数。批量里参与解码的序列越多，同一份权重被复用次数越多，带宽利用越充分——这也解释了为什么”把并发拉高一点，吞吐提升明显而延迟恶化有限”在解码阶段成立。至于引擎靠什么机制把这个性质工程化，是缓存管理类专门文章的主题，本文不展开。

第二件是长度与并发的权衡是显式的，不是靠调参消失的。方案评审时应该把”允许的上下文长度、允许的并发数、首 token 延迟上限”三者中固定两个、求第三个，而不是三个都当需求。

什么时候必须切，切完付什么代价

结论：切分只有一个理由——单个设备的显存或算力装不下、跑不快到满足约束。不是为了”看起来更工程化”。

张量并行把同一层内部的矩阵乘法切到多个设备，每层都要在设备间做一次归约通信。它的收益是能把一层的显存与算力摊薄，代价是通信频率与层数和调用次数成正比，因此只在同一台机器内部、走设备间高速互联时才可行；跨机器做张量并行，通信开销通常会把收益吃掉。它的适用边界是”单卡装不下，或者单卡算不到首 token 延迟红线”。

流水线并行按层把模型切成若干段，段与段之间只传递边界激活，通信量小，跨机器也能做。它的代价是气泡：任何一个时刻总有段在等待，段数越多、批次越小，空转比例越高。所以流水线并行要求并发足够大来把气泡填满——这意味着它天然与”在线小流量低并发”的场景冲突，却与离线批处理很合拍。

专家并行针对稀疏激活的模型结构，把不同专家分放到不同设备，每次前向只激活其中一部分。它的收益是权重总量可以超出单设备容量，代价是路由带来的不均衡与专家激活的跨设备搬运：某个专家被集中命中时会出现热点，负载方差远大于稠密模型。适用边界是模型本身为稀疏结构且并发流量足以把各专家填平。若流量稀疏且集中在少数专家，切分反而制造长尾延迟。

序列维度上的切分与注意力计算的重排也有专门手段，但那是引擎机制层面的内容，本文划一句为止：容量估算阶段只需要知道”切分不减少缓存总量，只把它摊到更多设备上”，长上下文的绝对压力仍然存在。

一句话汇总这一节：切分解决的是”装不下”和”算不动”，不解决”用不起”。如果单卡装得下、延迟也达标，多设备方案的隐性成本就是净增项——互联带宽、故障面变大、版本与权重分发复杂度上升，这些都会在后面的运维小节里回来收账。

模型选择与许可证核对

结论：私有化选型的第一道门槛不是能力，是权重来源可核验和许可证可承受。能力排序要等到这一道过了再做，否则会出现更糟的情形：模型上线后被合规要求下架，前面所有容量工作作废。

权重来源核验要做三件事。第一是只从模型发布方自己的官方仓库取权重，不从聚合站或转手镜像取；转手副本的常见风险不是恶意篡改（虽然这是最严重的一类），而是版本混乱——同一个模型名在不同仓库里对应不同检查点，效果差异会被误读成部署问题。第二是落地时把文件清单与校验和记进制品库，让”线上跑的到底是哪一份权重”在半年后仍可回答。第三是检查配套件的一致性：分片是否齐全、词表与对话模板是否与权重版本配套、配置文件里的注意力与键值头结构是否与估算脚本读到的相同。这一类不一致造成的现象是输出乱码或格式崩坏，排查成本远高于一次核对。

许可证要核对的要点，按风险从高到低排：是否允许商用；是否允许把模型用于对外服务而不只是内部使用——这两个面经常被混为一谈，但很多许可证对它们的约定并不相同；微调之后得到的权重是否继承原许可证的约束、是否允许再分发；是否对使用规模达到某个阈值的主体另有授权要求；对模型名称、商标与署名的使用限制；以及对生成内容是否要求标识或附加声明。这些条款的文字每期都不同，所以本文不引用任何条款编号，也不复述具体门槛数字——一切以当期官方许可证原文为准，把原文存档进项目仓库并在评审记录里注明版本号。当时主流的开放权重模型许可证在商用与再分发上的取向差别很大，有的带明确的使用限制条款，有的更接近宽松许可，这属于选型时必须逐份阅读的事，不能靠社区转述。

有一类隐性风险值得单独提：把”我们微调过，所以是新模型”当作许可证豁免。微调通常不改变原许可证对衍生模型的约束，而且如果微调语料本身有保密协议，产出权重就同时受两层限制。训练路线的取舍与微调方法的细节属于《RAG 与微调的取舍》《大模型微调 Fine-tuning 实践》《LoRA 低秩适配微调》的范围，本文只需要一句结论：微调改变了法务风险的形状，通常不减轻它。

核对完许可证，能力排序才有意义。私有化场景的排序方法和公开榜单差别很大：一是必须用自己的真实任务样本，公榜分数与内部文档问答之间的相关性并不可靠；二是小参数模型加检索的组合，在封闭领域的表现常常优于大参数模型裸跑，而这会直接改变上一节的容量结论；三是拒答与格式遵循这类”服务性格”特征要一起测，否则会出现分数达标、上线后被业务方判定不可用的情况。就 2025 年 3 月这个时点而言，可选择的开放权重面已经足够宽：Qwen2.5 系列、Llama 3.x 系列、Mixtral 一类的稀疏结构模型都在盘上可用，DeepSeek-R1 也在今年 1 月下旬放出并提供了可自部署的权重；同时期各家闭源 API 的更新节奏很快，个别厂商的接口刚放出预览版本、未经充分验证，这类候选在进入排序表之前应当标注状态而不是直接排名。

服务化形态与运维现实

结论：私有化不是一次交付而是一个长期状态。方案层面要选的不是”最强的架构”，而是”能爬上去的台阶”。

四个台阶

第一台阶是单机单模型加一个薄薄的服务层。它的作用是把延迟分布、长度分布、失败模式这些真实数据拿到手，通常只要几周就能给出第二台阶所需的输入。单机怎么用工具链把模型跑起来，归《ollama 本地大模型部署》《vLLM 推理加速实践》，本文不重复操作。

第二台阶是多副本加显式队列。多副本本身没有难度，难的是两件事。第一件是准入控制：请求必须在队列里被判定”有没有可能达标”，超过长度上限的请求要么拒绝要么降级，否则它会在生成阶段长时间占住缓存，把整台机器的并发上限拖穿。第二件是分桶：把输入长度相近、输出长度相近的请求放到同一个实例上，能显著减少缓存浪费与排队方差。这一层还有个现实约束——队列长度本身就是用户可感知的延迟，私有化没有公有云那种弹性池可以掩盖排队，所以容量与排队必须一起设计。服务拆分、协议层与多租户治理的具体架构归《推理服务架构设计》《大模型推理服务化实践》，本文只保留”台阶”这个视角。

第三台阶是灰度与回滚。私有化环境里模型版本变更是最高危的操作，因为一次变更同时改变权重、模板和行为。可行做法是两个版本在同一时间都在线，按流量比例分流，用一组可自动判定的门禁指标决定继续放量还是回滚：首 token 延迟分位数、请求拒绝率、超长响应比例、格式解析失败率、单位请求耗时。指标集合里至少要有一个来自业务侧的质量信号，否则会把”延迟达标但答得更差”的版本放上去。

第四台阶是离线交付与升级窗口。当环境本身不能联网时，权重、镜像、依赖都要作为可校验的制品离线搬运，升级窗口要提前和业务约定，并且明确”窗口内只做版本切换，不做配置变更”——把两件事混在一起的升级，失败时无法判断该回滚哪一半。

服务层的伸缩策略——什么时候按队列深度扩、什么时候按延迟扩、缩容时正在生成的长请求怎么办——属于《推理服务的弹性伸缩》的范围，本文只划一句：私有化的伸缩上限由硬件存量决定，所以伸缩问题的主体是”什么时候允许把存量给出去”，不是”从哪里拿到增量”。

运维现实

加速卡的故障率显著高于普通 CPU 服务器节点，这是私有化项目上线后最先撞到的现实。要做的是三件事：卡级健康检查（能起一个最小推理请求并校验输出的那种，而不是只看进程活着）、故障后主动摘除而不是等超时、以及预先算清楚”少一张卡时容量降到多少、需要哪些降级动作”。最后这一项经常被省略，结果是一次单卡故障就触发全站排队。温度、显存纠错计数这类指标的告警阈值请按当期硬件厂商的运维文档设定，本文给的任何具体数字都只能靠不住；示例口径是”团队约定”，不是通用标准。

权重分发要按不可变制品管理：一次发布对应一个带校验和的权重目录，实例启动时校验后才接流量，保留最近一到两个版本的回滚能力，并在元数据里记录该版本的许可证文件名与来源仓库地址——把许可证存档和制品放在一起，是半年后自证合规的关键。编排层面，当时的 Kubernetes 主线版本配合设备插件已能覆盖常见的调度与探针需求；把多卡切分与拓扑感知调度当成默认能力去设计之前，要先确认当期集群与设备插件的实际支持范围，不要假设某个尚未验证的特性可用。镜像与依赖必须冻结：驱动、加速卡运行时、深度学习框架三者之间存在版本兼容关系，本文写作时可用的框架版本落在 2.6 到 2.7 这一区间，但具体选哪一个要按当期官方兼容表核对，且不应把方案结论绑定到某个未发布的特性上。冻结的做法是把三者版本一起写进锁文件，构建产物打标签，禁止在测试环境之外的临时安装。

演练清单建议按季度跑一次，且必须在业务可见的窗口内跑——只在隔离环境里跑的演练不算演练。

第 6 项尤其重要。私有化系统的冷启动时间由权重搬运与加载主导，如果从未测过，故障升级时就会把它当成”随时能恢复”，而真实值可能长到改变可用性结论。

数据与合规面

结论：私有化解决的是”数据不出门”，不解决”数据被记录”。合规成本主要落在最小必要和标识义务两条线上，而这两条线都会改变架构——它们决定拦截发生在哪一层。

先说最小必要。推理侧的数据最小必要意味着只传任务必需的字段，并且这个约束要写进调用方的接口契约而不是靠自觉：一旦某段原文被粘进提示词，它就同时进入了模型上下文、可能的服务端日志、以及运维排障时的截图。想守住这条线，靠的不是提醒，是把”内部文档问答”这类需求改造成受控检索通道——从知识库里按需取片段，而不是让业务方自由拼接上下文。检索与训练路线的取舍本身属于《RAG 与微调的取舍》的范围，本文只需要它的合规性质：受控通道让数据访问有边界，自由上下文没有。若这些语料还要用于模型改进，那是另一条独立的授权链路，不能借用”提供服务”的同意；私有化环境里常见的错误恰恰是”数据都在自己机房，所以可以随便拿去微调”。

日志脱敏与留存要一起设计，顺序是先定留存再定字段。推荐的分级是三档：元数据档（请求标识、模型版本、长度、耗时、结果状态，留存期可以按审计要求放长）、内容摘要档（只留脱敏后的任务类型与长度分布，短留存）、原文档（完整提示与生成结果，仅在明确授权且最短留存下开启）。脱敏必须发生在入口层，用结构化字段白名单实现，而不是落盘之后再清洗——落盘后的清洗拦不住已经进入文件系统的原文，也拦不住备份副本。谁能查询原文档，这件事本身要留审计记录。

生成内容的标识义务是这一节里最容易被漏掉的一项。国内对生成合成内容的标识已有规范要求，具体条文、适用范围与实施方式请以发布机构原文核对，本文不复述条款编号也不解释条文细节。方案层面只需要接受一个事实：面向用户的界面通常需要有可感知的标识，而服务侧通常需要保留可溯源的元数据——这两类落点分别对应展示层与制品管理层，属于架构决策而不是文案决策。如果业务形态是把生成结果再分发给公众，还要确认自己在这条链条里属于哪一类主体，这与”只是内部使用”是完全不同的合规面。

跨境限制最容易被误判的情形是区域选择。云上专属环境如果部署在境外区域，即使隔离级别写得再高，数据离开境内这件事本身就已经构成跨境传输，需要走对应流程；反过来，”选国内区域”也不自动等于合规，还要看日志、备份、监控指标这些副产物落在哪里。实践上推荐的检查方法是把一次请求的完整数据足迹列成表——输入、上下文片段、日志、备份、指标标签、故障转储文件——逐项标注存储地域与留存期，而不是只标注主链路。

成本归因的做法

结论：私有化的钱必须按业务线和功能拆开归因，否则一年内一定会在”这台机器到底为谁服务”的争论里失去预算支持。通用云成本治理与集群层面的分摊方法归《云成本优化实践》《Kubernetes 成本治理》，本文只谈模型推理这一侧特有的归因单位与口径。

模型侧有三个可用的计价单位，适用场景不同。token 数（输入与输出必须分开统计，因为它们的瓶颈方向不同，成本结构也不同）适合按用量向业务线计价。GPU 秒（一次请求实际占用设备的时长）适合做内部成本还原，因为它能把长请求的真实代价暴露出来。请求次数只适合做行为分析，不适合做计价——用请求数计价会系统性低估长上下文与长生成的调用方，而这些调用方正是把容量拖穿的那一批。

内部单价可以从设备小时成本反推。设备小时成本等于硬件折旧加电力制冷加运维人力加网络与存储，除以可售小时数；可售小时数要扣掉闲置、演练、故障和升级窗口。这一步是所有成本口径里最容易自欺的地方——按理论满负荷摊出来的单价，永远会在下一次预算评审时被现实推翻。

归因键要由调用方在请求里显式声明业务线与功能，并在网关处校验，不接受缺省值——大量”未知调用方”的成本最终都会沉进公共池，然后在下一次扩容争论里被放大。归因结果建议按周产出两张表：一张给财务，按业务线汇总金额；一张给架构，按功能汇总时长分布与长度分布，后者才是决定要不要单独扩容或者换路线的依据。

三个常见陷阱值得点名。第一个是把闲置成本摊给当下唯一的调用方：调用方越少、单价越高、越倾向不用，最后形成死亡螺旋。正确做法是把闲置单独列成一栏，让决策者看到”整台机器空着”的真实代价。第二个是把前缀复用或缓存命中省下的成本记成业务线的效率成果，导致缓存策略优化之后账单变化无法解释；计价口径应当基于实际占用时长，而不是名义 token 数乘理论单价。第三个是把降级、重试、超时后重发的请求算成两次成本却只报一次用量，这会让质量指标的分子分母对不上；重试必须在元数据里标注父子关系。

阈值与目标值也要有口径。建议做法是团队先约定一组示例阈值——例如”某业务线月用量低于门槛就不单独占卡，改为共享池加配额”——写进成本治理文档，并注明这是团队约定示例而非通用标准。私有化项目里最危险的不是单价算错，而是把示意值当承诺写进年度预算。

决策树与一票否决门禁

结论：买 API 与自建之间没有立场问题，只有条件问题。把反向条件写清楚，比把正向条件写好更有用，因为大多数项目是”在错误的路线上坚持太久”而不是”没有开始”。

什么情况下应该买 API 而不是自建

下列条件中，满足三条以上就应该把自建方案退回讨论。

数据”不想出门”但从未被合规判定过。这是最常见的一类：所谓敏感是业务方的直觉而不是安全方的结论。真正做完数据分级之后，多数项目会发现可以外呼的比例远高于预期，自建的那部分需求反而撑不起一条独立产线。这种情况下正确顺序是先做分级，再谈路线。

并发量级还在剧烈变化，或者稳定后的量级明显低于团队约定的独占门槛。自建的本质是把闲置风险转移到自己身上，量级不稳时这个风险无法定价。

延迟红线宽松，能接受秒级首 token 和公网抖动；同时业务不需要严格控制生成长度分布。

组织内没有能长期承担加速卡集群运维的人，短期内也招不到或培养不出。缺这一条时，私有化会退化成一个只有作者能维护的系统，其风险高于任何成本节约。

预算走的是运营性支出，审批周期短于硬件采购周期，需求方又要求按季度看到效果。

任务价值本身还没被验证。这一条是反向条件里最强的：如果连”用公有云 API 跑通了这个场景”都还没有证据，自建就只是在为一个未验证的假设采购固定资产。正确做法是用 API 做价值验证，把真实流量与长度分布拿到手，再回到本文第三节做容量估算。

反过来，自建的充分条件是同时成立的那一组：数据不出内网是明确判定过的结论；延迟红线严格且已拆成三个数字；并发量级已经连续数月稳定；有明确的运维责任人和可考核的可用性目标；预算是年度资本性支出；成本归因口径已经谈好。这六项里缺两项以上时，混合路线或者继续用 API 才是负责的答案。

一票否决门禁

评审时不要做加权打分，加权打分会让”合规未闭环”这种硬缺陷被”性能好”稀释掉。下面这份清单用否决制，任何一项未通过就不进入实施阶段。

这十一项看起来像流程形式主义，但每一项都对应一个曾经真实发生过的返工类型。第 5 项与第 6 项尤其值得强调：它们不是要求评审者相信你的数字，而是要求你的数字能被别人用同样的输入复算出来——方案层面唯一可辩护的东西是可复算性。

小结

本文的立场可以压缩成四句话。第一句：约束决定路线，模型只在路线确定之后才有意义，所以那份问句清单值得逐条问到具体的人。第二句：容量估算靠式子而不是靠传闻，权重占用随参数量与位宽线性变化，键值缓存随上下文长度与并发序列数相乘增长，两个瓶颈方向不同，任何一条被省略都会在高峰或长请求上兑现成排队。第三句：切分只解决”装不下”和”算不动”，不解决”用不起”，单设备能满足约束时不要引入多设备。第四句：私有化是长期状态，交付只是第一天，运维现实与成本归因决定它能不能活过第二年。

方案里所有具体数字都要有出处：硬件与模型参数按当期官方规格与配置文件核对，阈值按团队约定标注为示例，示意值不允许进入预算文件。本文刻意不给卡数、单价与总拥有成本，因为这类数字的可信度和当期硬件与合同绑定，写进文章就会变成误导。如果只带走一条操作建议，本文推荐这一条：先用公有云 API 把场景的价值和真实流量分布跑出来，再回来走本文第三节到第九节。顺序颠倒的项目，返工率明显更高。
