多智能体协作模式设计

本文属于《Agent 智能体开发》第 36/55 篇
上一篇系列目录下一篇

本文讨论“多智能体协作”这一层的设计判断：什么时候真要把任务拆给多个智能体，四种常见形态各省掉什么、又新增什么风险，以及消息契约、仲裁规则、终止条件与人工介入点。本文只谈设计取向，不落到某个框架的 API；框架与工具执行的细节交给《CrewAI 多智能体框架实战》《Agent 工具调用与函数执行》。

先给一个判定

结论先行：看起来“需要一个团队”的任务，先用一个智能体加一组工具去跑，跑不动再考虑多智能体。多智能体只解决 3 个具体问题。

一、上下文隔离。检索资料、对话历史、中间产物与提示词挤进同一次调用，有效注意力被稀释、指令遵守度下降。把长上下文切段，每段只让负责它的角色看到，是让模型回到舒适区的直接办法；记忆的分层与检索归《Agent 记忆系统设计》。

二、职责与权限分离。同一个智能体既能读文件又能调外部接口又能改配置时，幻觉的破坏面很大；拆成多个角色、每个只拿最小工具集，出错可控，也便于审计。

三、并行。子任务没有依赖时，比如同时检索 3 个来源，能压低总耗时；但并行只是让等待时间重叠，不降低总 token 消耗。

反过来，单智能体加工具就够了的三条判据：上下文装得下且不损害指令遵守度；决策链里没有需要被隔离的权限差异；任务没有明显并行分支。三条都成立时，硬拆的收益抵不上通信开销。还有一条前提：你能写出每个角色看到什么、产出什么、谁来裁决，拆才成立。

四种常见协作形态

结论先行：常见协作形态归成 4 类——顺序流水线、主管-执行者、并行专家再汇总、评审-修订循环。它们各引入一种新风险，选型不是“哪个更聪明”，而是“你能承受哪一种风险”。把它们用状态机或编排 DSL 实现出来，交给《LangGraph 状态机工作流》《Agent 工作流编排入门》。

顺序流水线

把任务切成有向无环的几步，每步一个角色，前一步产出是后一步输入。省掉全局协调；新增风险是错误沿链条放大——上游误解只要输出合契约就被下游照单全收，末端发现时中间产物已被引用多次。适合步骤明确的链路，如文档翻译加术语对齐。

主管-执行者

主管拿到总目标，拆成子任务分派给执行者，回收后决定继续、返工还是结束。省掉人工规划；新增风险是主管自身会漂移，以及分派退化成昂贵的自由文本——描述含糊执行者就做偏，描述过细又失去用意。成败几乎全取决于通信契约。适合目标清楚但步骤不明、需要中途改道的任务。

并行专家再汇总

若干视角同时跑，再由汇总者综合。价值在覆盖度——同一份代码从性能、可读性、安全三种视角分别看，比让一个智能体综合考虑更全，省掉视角互相遮蔽；新增风险是表面分歧，不同措辞描述同一件事看似冲突，几条同源建议又造成虚假一致感。成本按分支数相乘，要有预算上限。适合代码评审与多维度打分。

评审-修订循环

一个执行者写、一个评审者挑问题、执行者再改。省掉自我审视不可靠——同一个模型在生成模式与检查模式下的表现并不一致，拆开确实提升检出；新增风险是死循环，改进方向与挑问题方向并不总是一致，必须绑定轮次上限、预算上限与终止条件。适合文稿润色、接口设计的两轮反馈。

形态对照一览

结论先行：四类形态放一张表对照，选型的直觉更清楚。预算量级是相对同一任务在单智能体下消耗的示意档位，不是实测数字，落地以团队约定示例为准。

读表抓两点：预算量级不线性，并行看分支数、循环看轮次上限；新增风险这一列没有一个能靠“再加一个智能体”消掉。

角色划分原则

结论先行：按权限边界与上下文边界切，不按人设切。给角色起名字叫产品经理、架构师、程序员都可以，但如果可见上下文和可用工具完全一样，那只是换了个提示词，不是真的分工。

第一条是权限边界。工具集有交集但风险等级不同的角色就该分开：能读代码又能发布的，与只能读代码做静态分析的，前者爆炸半径明显更大；两个角色工具集完全重合，就没有拆开的必要。

第二条是上下文边界。一个角色只应看到它做决定所需的信息：给评审者塞入用户全部历史，只会让它把注意力花在背景上而不是稿件上。划分要基于“这个角色看到什么就更可能做错什么”反推。

第三条是产出边界。每个角色至少产出一个可命名的中间物，一段带出处的摘录、一条评审意见列表都算；产不出可命名物，通常意味着它和相邻角色在做同一件事。

拆分检查问句，设计评审时逐条回答，任何一条含糊就重新划分：哪一个工具一旦被误用会造成不可逆影响？把它看不到的上下文补上，判断结果会不会改变？两个角色输出矛盾时谁来裁决？只留一个角色时要截断哪些上下文才装得进同一份提示？答不清三条以上再拆。

通信契约

结论先行：智能体之间传递的不能是一段自由文本转述，必须是一条结构化消息。结构化不是为了好看，而是让下游能校验、能重放、能追责；工具层的细节归《Agent 工具调用与函数执行》，这里只谈跨角色的消息形状。

一条任务消息至少携带 5 类字段。任务标识：稳定 id 与所属会话或轮次；输入引用：不复制上游正文，只给可寻址的引用；期望输出形状：要字段列表还是散文段落、条目上限多少；预算与截止：留多少 token、允许多少次工具往返、何时必须返回；权限声明：本次允许调用哪些工具、禁止访问哪些上下文。

为什么用 schema 而不让上游转述？可校验，schema 越紧越能在链路早期把不合形的输出拦下来，转述的错误要到下游拿它做决定时才暴露；可重放，有了任务 id 与输入引用，一次分派才能被完整重跑，只有转述文本时重跑会引入新的转述；可追责，schema 化让“上游就没要求这个字段”这类结论能被证明。

字段不是越多越好，一条 5 个字段但稳定的消息，好过 20 个每次都要重新解释含义的字段。优先固定任务标识、输入引用、期望输出形状、预算与截止四类。

仲裁与终止

结论先行：必须有明确的最终决策者，也必须有一份白纸黑字的完成定义。这两件事不事先约定，运行时会以极不体面的方式暴露——两个智能体互相打回，或者一份产物被循环修了十几轮。

谁是最终决策者？主管-执行者里主管天然是仲裁者，前提是它的裁决动作显式：要么接受产出并结束分派，要么连同具体理由退回，而不是用自由文本含糊地“再想想”。并行汇总里汇总者就是仲裁者，需要一份冲突规则，比如同一处两位专家意见相反时以带出处的优先。评审-修订循环里仲裁者既不能是执行者也不能是评审者，通常是外部一层完成定义检查或人工。完成定义本身至少写清 3 件事：产物落到哪些可命名字段、字段值的合形校验规则、验收看的是产物本身还是它引用的证据；它是链路外部的一份规格，不属于任何一个智能体的记忆。

轮次与预算上限不是用来防极端情况，而是把分歧成本锁在团队事先能接受的范围内：循环的轮次上限设 2 至 3 轮即可覆盖大多数真实改进，子任务上限按人力审阅带宽倒推，并行分支数由汇总者可容纳的输入长度决定。这些数字都是团队约定示例，不是实测阈值。MCP 初版规范（2024-11）已把工具调用的上下文协商纳入进来，官方在推进传输层与鉴权演进，但截止本文写作日期，链路层的成本上限仍需业务侧自己声明。

防止互相打回的死循环，推荐 3 条硬约束：每条打回消息必须引用上一轮的具体字段名，禁止“再检查一下”式空返；每轮挑出的问题必须严格多于上一轮已经关闭的问题，否则视为原地打转；链路维护一张“已否决方案”清单，分派落回清单即触发终止并升级人工。

失败与成本放大

结论先行：多智能体最直观的失败不是崩溃，而是分歧把一次调用变成两次、把两次变成四次。理解放大机制，比理解任何单点错误都重要。

一次分歧让 token 与延迟翻倍的典型路径是：主管把子任务派给执行者 A，A 产出后主管觉得不合格又派给 B，最后合并 A 与 B。多花的钱不只是 B 那一次，而是整条链路上被重复消费的上游内容——检索片段被两次带进上下文，合并还要再一次；延迟同理翻倍，因为 A 与 B 往往并不真并行，只是看起来可以并行但其实串行重试。

误差沿引用链扩散是第二个问题。上游对一段材料的概括偏了一个限定词，下游看不到原文，就沿着这个限定词继续推，另一个下游再引用这份产物，误差被继续放大。单智能体里不明显，因为模型看得到原始上下文；上下文被有意隔离之后，误差失去了自我纠正的机会。

最后是幂等与副作用隔离。同一条任务消息因超时或校验失败被重发，接收方如果是先做完副作用再返回，重发就带来重复扣款、重复发布、重复写文件。给每条消息带一个幂等键，处理前先查这个键是否已消耗过，“至少一次”投递才不会变成“至少多次”执行；跨角色写权限推荐“只有指定角色能改指定资源，其它角色只能读”。

人工介入点

结论先行：必须留人的动作有 4 类——对外发送、花钱、删数据、写权限。这 4 类之外，其余环节尽量不打断流程。设计原则是确认的粒度与不可逆性挂钩，而不是与“智能体有多不确定”挂钩。

对外发送包括邮件、消息、公开发布；花钱包括调用按次计费的外部服务、下单、转账；删数据包括任何从持久层抹掉记录的动作；写权限包括改配置文件、变更密钥、开关某条自动化。共同性质是“错了不好收回”，建议统一收拢到一个确认网关之后：网关输入完整任务消息与上游产物，输出放行、拒绝或退回。

怎么做到不打断流程？三个做法。异步审批：把待确认消息挂起而不是阻塞整条链，其它分支继续跑，人批复之后再回到那条分支；批量确认：一次分派里多个同类动作合并成一次确认，避免人被同一类问题反复打断；分级审批：低风险走白名单，中风险单次确认，高风险双人复核，规则写在网关的静态配置里而不是智能体提示里，避免模型说服自己跳过。

留人不是增加摩擦，而是让模型再自信也不该独自决定的动作有明确归属：谁被叫来、多久内回应、超时走什么默认分支。

小结

本文的判定是：多智能体只在上下文隔离、职责与权限分离、并行这 3 个具体问题上真正有价值，其它“像团队”的动机都不成立。四类形态各有各的省与各有各的坑，选型优先看你能承受哪一种风险。角色按权限与上下文边界切，不按人设切；契约必须 schema 化，才能校验、重放与追责；仲裁者、完成定义、轮次上限、终止分支这四件套是防止死循环的最低门槛；人工介入点收窄到对外发送、花钱、删数据、写权限四类。设计取向定下来，再去看具体框架与状态机实现。
