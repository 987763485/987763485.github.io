Rust 生态 crates 推荐

先立规矩：这不是一份清单

本文不打算给出”十个必用 crate”。这类清单的失败方式是确定的：它把一个团队在特定约束下得出的结论，包装成对所有团队都成立的结论。读者读完不会更会选，只会更会抄。

本文只交付三件东西：按场景给候选类别、把评估维度定义清楚、给退出成本。三件缺一不可。只给候选名，读者无法判断这些名字在自己的约束下是否成立；只给维度，读者知道该看什么却不知道从哪里看起；不给退出成本，读者会把一次引入当作永久承诺，结果是要么不敢引入，要么引入了就再也拿不掉。

任何一条推荐在本文里都必须带上适用条件与替代项。如果某段文字只写”用某某”，没有写什么时候不该用某某、不用它时退到哪里，这段文字就是不合格的。

通用技术选型的方法论另有专文，本文不复述那套框架。本文落到 Rust 生态的具体维度与具体场景，讨论”在 Rust 里怎么看这些事”。同样，错误处理在业务代码里怎么组织、Result 与 Option 怎么流转，是另外两篇的主题，本文只在需要区分候选层次时点名它们的边界，不讲写法。crate 与模块怎么组织、怎么划边界，也是专文内容，本文假定读者已经有把依赖收在模块后面的习惯。

评估维度：先统一口径

结论：八个维度里，真正决定”能不能进核心链路”的是维护状态、feature 面积、编译时间影响与退出成本四项；其余四项决定”能进多远、多久要还债”。下面逐条给口径与测法。

维护状态与 bus factor。 结论是：单维护者项目不是不能用，而是不能放在你无法替换的位置上。判据见后文专门一节，这里只强调一点——bus factor 是”关键路径上有几个人能发布这个 crate”，与维护者人数不是一回事。一个五人维护、但代码只有一个人真正读得懂的库，bus factor 仍然接近一。测法很朴素：挑两处你觉得将来可能要改的代码，看除作者之外有没有人提交过、有没有人 review 过。

MSRV 与 edition 兼容。 结论：把 MSRV 当作约束来读，而不是当作说明来读。Rust 2024 edition 已经发布，但许多 crate 尚未跟进切换，这中间的落差就是真实的工程成本：一个依赖停在旧 edition、旧 MSRV，会让整个 workspace 的升级节奏被它拖住。测法是在 workspace 里把 rust-version 收紧到团队基线，看 cargo build 在哪一层报错；报错点比 README 上的声明可靠。需要顺带说明的是，本文涉及的几个偏底层的能力，例如 std::simd、const_trait_impl、generic_const_exprs，截至本文写作时仍未稳定，因此任何以它们为默认前提的方案都不能进入生产选型，只能作为实验分支。

feature 面积与默认特性。 结论：默认特性打开了什么，比这个 crate 总共有多少特性重要得多。默认开启的特性会顺着依赖图传染，你看不见它，但编译时间和体积看得见。测法是把同一份代码分别用默认特性与关闭默认特性构建一次，记录干净的构建时间与产物体积差值。这个差值决定该 crate 能出现在应用层还是必须被推到边缘。

编译时间影响。 结论：Rust 后端项目的成本大头常常不是运行期而是编译期，而 proc-macro 与重型泛型是编译时间的两个主要来源。测法是增量构建与非增量构建各测一次，重点看”改一行业务代码之后要等多久”，不是首次冷启动。冷启动时间长但增量好的依赖是可以共处的；冷启动长且增量也长的依赖应该远离业务 crate。

体积。 结论：只有当同一个二进制里堆了很多功能重叠的依赖时，体积才成为强约束。CLI 工具、边端程序、嵌入式产物要当回事；服务端二进制多几 MB 通常不值得为此牺牲维护性。测法用 cargo bloat 这类工具，按依赖归因看谁贡献了多少。

许可证。 结论：许可证风险不在”是不是开源”，而在传染性条款与多许可叠加。一个依赖同时给了两种许可、而另一种带 copyleft 时，你要看的是你实际使用的路径落在哪一份条款下。做法是把许可证扫描放进 CI，把允许清单写成配置，而不是靠人记。

文档与错误信息质量。 结论：文档质量是可测试的，不要凭观感。三项硬测：一是把文档里的示例原样粘进新 crate，能不能编译通过；二是故意写错一次调用，编译器给出的错误信息能不能把你指向正确方向；三是 trait bound 报错里出现的是你自己的类型还是三层层层包装的类型名。第三项最能预测半年后排查的痛苦程度。

是否提供 no_std 或异步无关的核心。 结论：这条维度衡量的是设计自洽性，而不是能不能跑在嵌入式上。一个库如果能把纯逻辑与运行时解耦，说明它的核心数据结构不依赖执行环境，这类库更容易替换、更容易测试、也更容易在你换运行时时活下来。反过来说，不需要 no_std 不代表它做得差；但”核心逻辑必须挂着异步运行时才能跑”是一个应当被记录下来的坏味道。

场景一：Web 服务的三条线

结论：Web 服务选型真正的分界线不是”哪个框架更好”，而是”你要不要自己拥有请求生命周期”。下面把三条线分开谈，因为它们的替换成本完全不在一个量级上。

路由与中间件层

候选可以分成三类，取舍按”抽象归谁”来看。

第一类是全家桶框架，代表是 actix-web、rocket、poem。它们把路由、参数提取、状态注入、错误转换都接管了。适用条件是内部系统、后台工具、需求还在快速变动的服务——开发速度是它们唯一但真实的优势。代价是抽象归框架：当你需要”所有请求都过一层自定义的租户解析”这种需求时，往往要学一套框架专属的钩子；替换时整个 handler 层要重写。

第二类是路由器加服务抽象的组合，代表是 axum 与它下面的 tower。定位要写清楚：axum 只做路由与提取器，handler 本质是实现了若干 trait 的函数；tower 不是 Web 框架，它是服务组合与中间件层的抽象。这条路线的适用条件是长期维护的核心服务，因为退出成本最低——你要换掉的是最外面那层壳，业务 handler 与传输细节隔得开。代价体现在编译错误上：trait bound 不满足时报错链长，文档质量在这条路线里的权重远高于其他路线。

第三类是薄路由器直接坐在 HTTP 实现之上，底座是 hyper 一类的项目。适用条件是对延迟、连接管理、优雅关闭有非常规要求的服务，或者你在写网关。代价是超时、请求体大小限制、慢客户端处理这些容易写错的细节全部归你。

一句提醒：某些早年相当流行的 HTTP 框架今天已经归档或停止演进，这不是笑话，而是把框架写进核心链路的现实风险——它说明”框架层也会变成遗产代码”。

序列化与校验

序列化层的事实标准是 serde，它同时是库层的抽象和框架层的接口，因此它几乎不可替换；也正因为如此，评估它的 feature 面积比评估别的项目更重要——derive 特性带来的编译时间成本是全团队承担的。承载格式的选择放到场景五谈。

校验有三条候选路线，各自的适用边界不同。

  • derive 式规则校验，代表是 validator：在结构体字段上声明规则，写起来快。顶不住的情况是跨字段依赖、需要查库的唯一性校验，以及”同一个 DTO 在不同接口规则不同”。
  • schema 驱动校验，代表是 jsonschema：契约与代码分离，适合对外暴露的 API 与多语言客户端共存场景。代价是 schema 与 Rust 类型的双向一致性要靠工具或 CI 维护，出错时定位比 derive 慢。
  • 领域构造内校验：把非法状态直接消灭在类型里，用构造函数返回结果。前期成本最高，退出成本最低，因为不引入任何依赖。

替代项建议：三条路线不互斥，常见的稳定组合是”入口 schema 或 derive 做形状校验，领域构造做业务校验”。校验层是三条线里最容易替换的，不要为它设计抽象。

错误处理的层次

只交代候选类别，写法归错误处理专文。可观测到的层次有三类：应用顶层的聚合式错误处理（anyhow 一类）、库层自定义错误类型（thiserror 一类）、框架内的错误到响应的转换。选型时本文关心的只有一件事：错误类型能不能带着足够上下文跨层传递，并且到最外层还能还原成结构化响应。如果你的领域 crate 与 HTTP crate 在同一层，那说明层次已经塌了。

场景二：数据与存储

结论：数据访问层是唯一一处”必须自己包一层再进业务”的依赖位置，因为它一旦渗进 handler，退出成本就从”改一个 crate”变成”改所有 SQL”。

客户端与连接管理

候选按两个轴分：同步与异步、贴 SQL 与 DSL。

  • 编译期校验的 SQL 集成路线，代表是 sqlx：SQL 写在宏里，编译时向数据库问结构。适用条件是 schema 稳定、团队接受”编译依赖数据库”这件事。它把数据库结构变成编译依赖，CI 里要么提供真实实例，要么走离线 prepared 语句的缓存文件——无论哪条，都是流程成本。这也是它的退出成本：一旦 handler 里到处是宏，替换要全量搜索。
  • 驱动级路线，代表是 tokio-postgres：自己拼语句、自己做行到结构的映射，没有魔法。适用条件是需要精确控制预处理语句、事务与复制协议的服务。替换最容易，因为它不改变你的代码形状。
  • 同步客户端，代表是 rusqlite 与同步的 postgres 驱动。选择依据不是”异步一定更快”，而是并发模型：如果服务本身是每请求一线程，或者访问的是本地嵌入式数据库，同步模型更好推理、更好测试；如果是高并发远程 IO，异步客户端才有意义。
  • ORM 与对象映射，代表是 diesel（编译期查询 DSL，schema 由代码生成）与 SeaORM（异步、ActiveRecord 风格）。取舍规律是 DSL 越聪明，写复杂查询越省力，迁移与调试越难，退出越贵。

对象映射的思路本文只给一条：把”行到领域对象”当作纯函数来写，输入是行、输出是结果，不依赖运行时也不依赖连接。做到这一点，上面四种客户端的替换代价都能被压在一层之内。

连接池候选是 r2d2、bb8、deadpool 三类。选择依据是它与运行时的耦合：deadpool 同时覆盖同步与异步管理口径，bb8 更贴 tokio，r2d2 是同步世界里的老选择。池的问题九成不在池本身而在超时与泄漏参数，选型时把”能否观测到等待时间与借用时长”作为硬指标。

迁移工具

候选是 diesel 自带迁移、sqlx-cli、refinery 一类。它们的差异其实只有一处：迁移记录表归谁管、迁移文件是否参与编译。思路应当是——迁移脚本本身是产物，工具只负责顺序与幂等记录，所以选择标准是”脚本能不能被别的工具或人工重放”。能用纯 SQL 表达的迁移就不要写进 DSL，这是退出成本最低的做法。

键值与缓存

Redis 客户端候选是 redis 与 fred 两类，后者把集群与路由作为一等能力。本文只谈客户端选择，集群拓扑与哨兵行为是运维话题，另有一篇专门讲。选型上的建议是：如果代码里出现”按 key 前缀决定连哪个节点”的自研逻辑，说明客户端能力已经不够，应该先换客户端而不是先加抽象。

场景三：并发与运行时

结论：运行时决定调度模型，但决定可迁移性的是”任务归谁管、锁在哪跨 await”。异步运行时本身的细节与横向对比另有专文，本文只回答选型层面的三件事。

运行时选择

候选是 tokio、smol 与 async-std 三种，但口径要写明白：async-std 已进入维护/收敛状态，不应作为新项目的首选，在存量项目里它可以继续活着，只是不要再把新的抽象押在它身上。smol 的定位是小、与 futures 生态直接组合，适合工具类程序与你对调度器有明确取舍的场合。tokio 是当前生态的默认答案，理由不是它最优雅，而是它的周边最厚：驱动、池、超时、测试工具都以它为中心。

选择依据应当是周边而不是调度器性能：先列出你需要的数据访问客户端、可观测导出器、内部库，看它们中有没有已经绑死某个运行时的，那一个基本就是你的选择。反过来的路径——先选运行时再等生态——只在你要写的是一个不依赖任何第三方 IO 的纯计算服务时才成立。

一句必要的提醒：绑运行时绑得最深的往往不是你的业务代码，而是 proc-macro 生成的代码与测试宏。评估 feature 面积时，把”测试是否需要运行时宏”记进去。

结构化并发

候选类别是”任务组与作用域 spawn”，形态上有官方的 JoinSet、第三方结构化并发库，以及自己用 JoinHandle 收集的手写路线。要点不在用哪个，而在三个问题有没有清晰答案：子任务失败时谁负责取消兄弟任务；进程退出时未完成的句柄去哪里；一个请求的生命周期结束时，后台任务由谁兜底取消。三个问题里有任何一个回答不了，就该先补一层任务管理再谈 crate。

手写路线的适用条件常常比想象中宽：任务组逻辑不超过几十行时，自己写的退出成本为零。

通道与共享状态的搭配

候选按用途分层，不要按”哪个更快”来选。

  • 跨任务传所有权：tokio 的 mpsc、oneshot、broadcast、watch 系列。选择依据是语义而不是性能——watch 用于配置与状态广播，oneshot 用于一次性回执，broadcast 要小心滞后丢消息。
  • 同步世界里的无锁队列与并发原语：crossbeam。它是”不引入运行时也能并发”的那条退路，也是把核心逻辑做成运行时无关的那块砖。
  • 需要多生产者多消费者且同步异步两侧都要用：flume 一类。
  • 共享状态：parking_lot 补同步原语的缺口，arc-swap 处理读多写少的整体替换，dashmap 用于分片键值。

搭配原则写成三条可检查的规则：能用所有权传递解决的不要共享；只读快照用整体替换而不是原地改；任何锁的临界区里不要出现 await。最后一条是审查项，不是建议。

取消安全这个话题本文只划界：任何可能被超时或选择打断的 future，都要回答”被打断时我手上的东西是否已经交出去”，具体写法与判定归异步专文。

场景四：可观测

结论：日志与结构化追踪是两类数据，用同一条通道打是后期排查困难的主要来源；指标要么走门面要么直绑后端，不要两头下注。

日志与结构化追踪的分工

候选分三层。门面层是 log，提供 info! 一类宏与后端无关的接口。结构化层是 tracing 与 tracing-subscriber：tracing 的核心是 span，span 有层级、有字段、可以跨 await 传递；tracing-subscriber 负责把事件与 span 组装成输出、过滤与格式。落盘/转发层是具体的 writer 与订阅器实现。

分工的口径应当明确：日志承载”发生了什么事”的单行事实，追踪承载”这件事在哪个请求、哪一层、花了多久”的因果结构。用 span 去打单行业务日志，或者用日志去模拟调用链，都是把两类数据塞进一条通道。与别的语言对照一句：Go 生态的日志库讨论集中在线程安全、结构化字段与采样，那套结论不能直接搬过来，因为 Rust 这边 span 与 async 上下文的绑定是语言层面要处理的问题。

日志后端候选还包括 env_logger、fern 一类。它们的适用条件是本地开发与小型服务；生产核心服务里，把过滤策略交给订阅器而不是环境变量，更容易做统一的字段规范。

指标导出

两条路线。门面路线是 metrics 加 exporter，好处是业务代码不认识后端，代价是多一层抽象与它的 feature 面积。直绑路线是直接用 prometheus 客户端类型注册指标，好处是行为完全可见、少一个依赖，代价是换后端要改代码。选择依据是组织内后端是否已经确定：已经确定就直绑，未确定就走门面。跨语言的 OpenTelemetry 生态在 Rust 侧的候选是 opentelemetry 一族，走 OTLP 出口，适合追踪与指标都要统一收集的团队，代价是 API 层的抽象层次多、学习成本明显高于前两条。

采样与脱敏口径

采样分两处：头部采样在请求入口决定这条链路要不要留，成本低但会丢异常链路；尾部采样先全收再按条件保留，能保住慢请求与错误请求，代价是要有缓冲与内存上限。后端服务的常见口径是入口全收、出口按条件丢弃。

脱敏口径本文给一条硬规定：不得把用户数据写进 span 属性。属性里只能出现标识符、枚举值、长度与计数这类派生量。原因是 span 属性会进索引、会进采样副本、会跨团队可见，而业务代码里的字段名是会被人顺手加进去的。

配套做法是把字段白名单写成 lint 或 code review 检查项，而不是靠文档口头约定——文档在字段新增那天就失效了。

场景五：序列化与协议

结论：选 JSON 看生态兼容，选二进制看 schema 演进能力，选自定义文本看解析错误的可诊断性；跨语言风险的大小几乎只取决于一个问题——格式定义归谁。

JSON

候选是 serde_json 与若干以性能为卖点的实现。serde_json 的定位是事实标准：绝大多数 Web 框架、配置库、测试断言都以它的类型与 trait 为接口，因此它的退出成本极低而性能上限一般。性能实现的适用条件是明确的热点路径：JSON 解析占 CPU 的大头、且数据结构以强类型 Deserialize 为主。代价要自己测两类：一是非 ASCII 文本与 Unicode 转义的处理是否与预期一致；二是与动态 Value 类型互操作的边界——一旦业务代码需要拿到未预先建模的字段，性能路线的实现往往要转成标准类型，收益当场消失。

选型建议是把这句话写进评审记录：性能优化只允许发生在边界清晰的热点上，不允许因为”更快”就把整个服务的 DTO 层换掉。

二进制协议

候选类别按”有没有 schema”分成两组，这是取舍的第一分界。

  • 有 schema、可跨语言：prost 一类（protobuf 代码生成）、flatbuffers 与 flexbuffers、Apache Arrow 生态里的 Rust 实现。特征是格式定义是产物，演进规则明确，未知字段与枚举变体的处理有标准答案。代价是构建期多一步代码生成，以及你要接受类型映射的限制。
  • 无 schema、Rust 内部自用：bincode、postcard、ciborium、rmp 一类。特征是零类型定义、用起来轻，代价是格式变更就是破坏性变更——没有 schema 意味着没有演进规则。ciborium 与 rmp 属于 CBOR、MessagePack 这类有跨语言标准的自描述格式，可以当作中间态；postcard 的定位偏向 no_std 与嵌入式。

选择依据写成三条问句：这个格式会不会有两个非 Rust 的实现方？这个结构以后会不会加字段？旧版本要不要能读新版本写的字节？三问里任何一问是”是”，就应该走有 schema 的那组。

自定义文本协议

候选是解析器组合子与解析器生成器两条路线。组合子一侧是 nom 与 winnow，特点是可以零拷贝切片、控制递归与内存表现，代价是错误信息天生难读，需要自己包装一层诊断。生成器一侧是 pest（PEG 文法生成 AST）与 chumsky（面向错误信息优化的组合子式解析器），特点是文法与代码分离、报错友好，代价是多一层生成与运行时结构。

适用条件划分：DSL、配置格式、需要给用户看的报错——走生成器；网络报文、日志行、性能敏感且格式由你独控——走组合子。跨语言兼容风险的口径是：文本协议必须有独立的测试向量文件，让别的语言实现方读同一批用例，否则”协议”只存在于你的解析代码里。

跨语言兼容的三条检查项

无论选哪种格式，这三条决定了事故概率：时间类型怎么表达（是否有偏移、精度截断在哪一侧）；大整数与浮点怎么表达（会不会静默降精）；未知枚举变体在反序列化时是报错、忽略还是落成兜底分支。第三条最危险，因为”忽略”看起来总是最省事的那个选项。

反面清单：把推荐变成负债的五种做法

结论：这五种做法的共同点是都用”生态优势”这个词掩盖了一个具体成本。评审时把它们当检查项逐条对照。

把 crate 数量当生态优势。 crate 多说明可选项多，不说明可组合性好。真正要看的是数量集中的地方：如果某个领域有十几个可选实现，通常意味着没有哪一个把接口做稳。替代做法是只在该领域里找有”被别人依赖”证据的项目——被依赖比自己发了多少个版本更能说明稳定性。

为一个小函数引入大依赖。 表现是”为了拿当前时间戳加了一个 crate”。成本不是运行时，而是它带进来的整棵依赖树、它的许可证、它的维护状态从此进入你的审计范围。替代做法是先写二十行内联实现，只有当这个函数需要被测试、被跨平台修正、被多个 crate 复用时，才把它升级成依赖。

feature 全开导致编译爆炸。 表现是图省事写 features = ["full"]。代价是编译时间与体积直接失控，且默认特性变化会静默影响你。替代做法是显式列 feature，并在 CI 里把 feature 变更当作需要 review 的改动。这条要配合前面说的口径：full 类特性的含义由项目自己定义，升级时它可能悄悄扩大。

把不维护的项目写进核心链路。 表现是内部工具里一个跑得很好的小库被顺手搬进支付路径。核心链路的判据不是流量，而是”这个 crate 停更三年，你还在不在”。替代做法是给核心链路单独设一道门槛：只允许进入维护活跃度判定表里”可依赖”档的项目。

只看不维护风险的”推荐”。 表现是文章与内部 wiki 只写”用某某”，不写适用条件、替代项与退出成本，于是推荐变成了不可讨论的规定。替代做法是任何推荐必须带三行：什么时候不该用它、不用它时退到哪里、换掉它要动几个文件。缺任何一行，评审直接退回。

从判断活跃度到安全引入

结论：维护活跃度是可以被定性判断的，不需要下载量与关注度这些容易被操纵的数字；引入是可以被流程约束的，关键在”一次只替换一层”。

维护活跃度怎么判断

先划掉两类噪声：下载量与 star 数不能进入判据。前者反映的是历史传播而不是当前维护，后者反映的是兴趣而不是责任。能用的判据只有五项，全部是定性观察。

第一项是提交节奏与最近发布间隔。看的不是提交数量，而是”最近一次有意义的改动离现在多久”，以及改动是不是只由依赖升级机器人贡献。一个仓库如果只剩下自动化的版本号提交，它实际上已经停更。

第二项是 issue 响应。判据不是响应快慢，而是维护者是否复现、是否给出可执行的绕过办法。响应里出现”欢迎提 PR”但没有任何分析，是负信号。

第三项是发布说明质量。能看出维护者是否理解自己的用户：破坏性变更有没有单独列出、有没有迁移提示。只写一句”若干修复”的发布，出问题时你无从判断影响面。

第四项是维护者数量与分布。看的是发布权限与代码理解的分布，而不是署名数量。判断方法在前面的维度一节给过：找两处将来可能要改的代码，看除作者之外有没有人提交过。

第五项是”个人项目加无 CI”这个组合。没有持续集成不等于代码有问题，但它意味着你无法验证自己在文档里读到的承诺，也意味着维护者休假时这个项目在功能上就停摆了。

档位口径是：核心链路只允许”可依赖”档；外围与一次性脚本可以用”谨慎使用”档，但要在依赖清单里标注责任人；”不引入”档不因为”只是用一下没关系”而破例——这是反面清单第四条的来源。

引入流程：四步与一次一层

第一步是试用，时间盒控制在一到两天。产出不是”能用”，而是一份记录：文档示例是否编译通过、故意写错时编译器是否给出方向、关掉默认特性后能否满足需求、干净构建与增量构建各慢了多少。这一步要允许得出”不引入”的结论，而且要鼓励。

第二步是 PoC，只在一条真实链路上做，不上线。产出是把候选封装进一层你自己的抽象，并写一个失败注入测试。之所以限定一条链路，是因为同时改两层会让失败无法归因。一次只替换一层，是这条流程的全部纪律：换路由不换序列化，换客户端不换 ORM，换解析器不换协议。

第三步是锁定策略。三件事同时做：依赖声明收在 workspace 层，避免各处出现不同口径；锁文件进版本库，让构建可复现；把许可证扫描、安全通告扫描、未使用依赖检测这三类工具放进 CI，而不是等出事再跑。版本区间的写法属于团队约定，但约定要写成文档并能被机器检查——允许自动升到小版本，就同时要求破坏性变更必须人工确认。

第四步是退出策略，写进引入记录里，不写就不算完成。内容是三行：这个依赖被谁封装、替换它要动哪些文件、下一次升级窗口是什么时候。回滚杠杆按有效性排序有三个：封装层之后可以只换实现不动调用点；配置开关可以让新旧实现并存一段时间；数据类依赖还可以影子读——新路径读结果但不返回，比对一致后再切。三个都没有的引入，本质上是一次不可逆决定，必须在评审里单独说明。

评估打分表模板

模板本身可以直接抄进团队 wiki，权重与阈值是团队约定示例，不要照抄数值。

模板里两个设计有意为之。退出成本不参与加权而是做一票门槛，因为它衡量的是”以后能不能撤”，与其他维度不在同一个方向上。编译时间权重给到与 feature 面积同级，因为在 Rust 后端项目里，这两项才是团队每天付的账。

场景与退出成本对照表

场景 候选类别 选择要点 风险与退出成本
Web 服务·路由层 全家桶框架 / 路由器加服务抽象 / 薄路由器加 HTTP 底座 抽象归谁；长期服务选后者，原型选前者 框架层会变成遗产代码；换框架需重写 handler 层
Web 服务·校验 derive 规则 / schema 驱动 / 领域构造内校验 是否需要跨字段与异步规则；是否对外契约 最低；三条路线可并存，不要为它设计抽象

小结

本文没有给出必用清单，给的是三件东西：八个可测试的评估维度、五个场景下的候选类别与适用条件、一套把引入变成可撤销动作的流程。如果你只打算记住三句话，本文建议是这三句：任何推荐都要带替代项与退出成本，否则它不是推荐而是规定；一次只替换一层，否则失败无法归因；核心链路只允许进入维护活跃度”可依赖”档的项目，下载量与关注度不能作为豁免理由。

Rust 生态当下最需要的不是更多选择，而是把选择条件写清楚。新 edition 已经发布而许多 crate 尚未跟进，编译时间与 feature 面积仍然是团队每天付的账，这些成本不会因为某个项目名字出现在清单上就消失。把评估表抄进 wiki、把权重改成你们团队的约定值、把每一次引入记录补上退出策略那一行，这篇文章就算落地了。
