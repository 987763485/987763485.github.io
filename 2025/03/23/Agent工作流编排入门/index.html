Agent 工作流编排入门

本文属于《Agent 智能体开发》第 11/55 篇
上一篇系列目录下一篇

把大模型调用串成一条能上线的流程，难点通常不在单次调用质量，而在流程本身：跑一半崩了怎么办，重复扣费怎么办，等人审批等到第二天怎么办。本文讨论的就是这件事——用与框架无关的抽象，把不确定的模型调用组织成可复现、可恢复、可观测的流程。适合准备把原型推向生产的后端与全栈工程师，读完能拿到一套编排要素清单、两种抽象的取舍依据，以及检查点、汇聚、人工介入、补偿、护栏的具体做法。

编排到底是什么

结论先行：编排是把不确定的模型调用组织成可复现、可恢复、可观测的流程的工程手段；它解决的是流程问题，不是模型能力问题。

这句话里三个词各自有明确验收口径，缺一不可。可复现，指的是同样的输入重跑两次，走的步骤序列一致，或者至少不一致的部分被显式记录并可解释；如果一次跑三步、一次跑七步，而且没人说得清为什么，那就没有可复现性。可恢复，指的是流程在任何一步中断之后，能从中间状态继续，而不是从头再来；进程崩溃、网络超时、人工审批隔夜才回来、上游服务当天维护，都是恢复语义要覆盖的正常场景而不是异常场景。可观测，指的是每一步的输入输出、耗时与花费都能被追溯，出错时人能立刻定位是哪一步的哪一次调用给出的结果不符合预期。

把这三条摆在一起，就能看清编排的真实定位：模型能力不足时，编排不会让答案变正确；模型能力足够但流程散乱时，编排才会体现出价值。很多团队把编排当成“让智能体更聪明”的手段，这是误解。编排是让已经具备能力的模型调用被安全地串起来、放出去、收得回。判断自己需不需要编排，本文后面会给出问句清单。

顺带划清几块相邻领地。某个具体框架里状态机怎么落地，由那篇专门的状态机工作流文章负责，本文只谈抽象与通用做法。多智能体的协作形态与角色划分属于协作篇，本文只处理一条流程内部的机制，哪怕流程里出现多个模型角色也是同一条流程的先后步骤。工具的契约、参数校验与执行结果回收由工具调用篇负责，本文不重讲。应用的分层架构那一篇讲的是系统层次划分，不涉及步骤间转移；更早的工作流与任务编排类旧文已经把“为什么要编排作业”讲过一遍，本文把同一套问题精确落到模型调用上。

两种抽象：固定图与转移表

结论先行：可用的抽象只有两类，有向无环图（DAG）与状态机。DAG 表达“预先固定的步骤”，状态机表达“按结果转移的步骤”；两者能表达的东西互有覆盖不了的地方，选型要按流程性质决定而不是按偏好决定。

DAG 的能力边界很清楚。它的节点是一次步骤，边是执行依赖，无环意味着流程必然终止。这套约束带来的好处极其值钱：可静态校验（图没有环、没有孤立节点、依赖不缺失，在部署前就能查出来），可提前排程（能一次性算出哪些节点可并行、关键路径多长、预算上限多少），可解释（跑完之后给出一张实际执行的子图，人一眼看懂）。DAG 不能表达的东西同样清楚：它无法表达“根据这一步的输出决定回到前面某一步重来”，也无法表达“等待外部信号再决定下一步”。重试在 DAG 里通常被建模为节点内部的循环，从外部不可见，这就让“这次是第几次重试”变成了隐藏状态，观测时会失真。

状态机的能力刚好互补。它显式持有状态对象，转移由条件决定：当前状态加上这一步的结果，算出下一个状态。循环、回退、等待、并发分支的汇合都能自然表达。代价是三条：静态可分析性变差（一个状态机是否必然终止，一般不可判定，需要额外规则约束），排程能力变差（无法提前知道会走几步，预算只能是运行时累加而不是预先算出），调试成本变高（要复现一个 bug 得复现整条状态轨迹）。

还有一类需求落在两者之间：整体骨架固定，但个别位置允许有限次回退。工程上常见的处理办法是分层——外层用状态机持有全局状态与终止条件，内层若干段用 DAG 跑固定步骤。这样既保住了大部分静态可校验性，又把循环限制在显式声明的位置。

两者对照如下，落地注意点比抽象本身更容易踩坑。

两种框架中立的表达方式都能承担这套抽象：一种把节点、边、检查点做成声明式配置，一种把它们做成代码里的类型与转移函数。具体某个 Go 框架怎么声明编排与工具调用，那篇实战文章已经写过；某个 Python 框架里链与智能体两个模块怎么用，也由对应入门文章覆盖，本文不重复它们的接口。

什么时候不该用自由 Agent

结论先行：能写成固定流程就别放开循环。自由 Agent 指的是“给模型一组工具，让它自己决定下一步做什么、什么时候停”，它的可变成本与不可复现性都很高，只在流程真的无法预先枚举时才值得付出这个代价。

原因有三条。第一，放开循环以后步数不再由设计决定，而由模型当场的判断决定，同一输入的两次执行可能差好几倍花费，预算无法预估。第二，停止条件变成隐式的，模型认为“任务完成了”就停，而它认为完成不代表真的完成，于是要额外做一层校验，这层校验本身又是一次不确定调用。第三，出问题时排查路径长，因为决策依据散落在提示词与历史对话里，没有一处能指着说“这一步是这里决定的”。

选型时把下面这些问句逐条回答，答案是“是”越多，越应该固定流程；反过来，如果前三条里有任何一条答“是”，才考虑在局部放开循环。

  • 步骤序列能不能在需求评审时全部列出来？列得出来就不要让模型现场决定。
  • 单步失败是否可以用一个确定动作补救，例如重试、降级到缓存、改用更小的模型？可以补救就不要引入反思循环。
  • 这条流程一天跑多少次？次数越大，越要把不确定性压缩到最少的步骤里，因为方差会被放大。
  • 结果错误会不会直接进入对外动作，例如发消息、下单、改生产数据？会的话必须固定校验步骤，不能只靠模型自觉。
  • 输入的空间是不是开放的，例如任意自然语言诉求需要现场规划？是的话才需要模型来选下一步。
  • 是否存在合法的中间态需要外部信号才能推进，例如等客户回复、等审批？是的话状态机比图更合适。
  • 团队能不能接受一次执行的步数在合理区间内浮动？不能接受就先不要放开循环。
  • 有没有一个便宜且可靠的判定函数，能确认最终输出达标？没有的话，自由 Agent 的质量无法验收。

最后一条问句经常被忽略，但它其实是整份清单的闸门：判定函数存在，放开循环才有意义，因为循环可以“试到判定通过为止”；判定函数不存在，放开循环只是把不确定性从输入端搬到了输出端，没有增加任何可控性。

状态与数据形状

结论先行：每一步的输入输出都要 schema 化，状态对象要显式且可序列化，上下文要随步骤收缩而不是随步骤膨胀。这三条决定了编排能不能做检查点、能不能做汇聚、能不能被观测。

为什么要 schema 化。模型输出是文本，而流程控制需要的是结构化事实，例如“这单要不要人工看”“抽取到的日期是哪天”“分类结果属于哪一类”。如果每步之间靠自由文本传递，下游必须再次解析这段文本，而解析本身又是一次不确定调用，错误会顺着链条放大且无法归因。给每一步定义输出 schema，等于把“不确定的生成”收敛成“确定的字段”，之后所有的转移条件、校验、统计都能建立在字段上。schema 至少要有类型与必填约束，最好带上一个明确的“无法判定”取值，避免模型被逼在两个都不对的选项里选一个。

状态对象怎么设计。经验是把状态分成三类字段：事实类，来自输入且流程中不再变化；派生类，每一步写入自己的产物；控制类，记录轮次、重试次数、已消耗预算、审批结果、终止原因。三类字段混在一起是常见的坏味道，会让重放和并发更新都变得危险。控制类字段尤其要单调或可合并，因为并行分支汇聚时需要合并它们。命名空间前缀与显式的写入者约定，能避免两个分支同时改同一个键。

上下文怎么收缩。很多人把编排写成“历史越滚越长”的对话，步骤越多，每步的输入越大，成本与干扰同时上升。正确做法是让每一步只看见它需要的字段：上游产物先经过裁剪或摘要，再进入下游输入；早期步骤的细节在完成职责之后就退出上下文，只留下结论字段。收缩不是丢信息，而是把信息放在合适的层——原始产物留在检查点存储里供人回看，进入模型的只有当前步骤用得上的部分。

检查点与重放

结论先行：检查点不是日志，是可执行的状态快照；重放的边界由副作用决定，凡是不可幂等又无法补偿的步骤，都不能被重放跨越。

为什么要持久化中间状态。模型调用贵且慢，一条流程跑十几步很常见，第 11 步因为下游超时失败，如果没有中间状态，只能从第 1 步重跑，等于把已经付过费的十步再付一次。更硬的场景是人工介入：流程停在确认点过夜，进程早就重启了，状态必须从存储里恢复而不是存在内存里。还有质量场景：线上出问题时需要拿到“当时的输入与当时的中间产物”，只有日志里的最终回复是不够的，因为你无法判断错误发生在哪一步。

检查点设在哪里。有三个判断标准。第一，产物已成型：这一步的输出通过了 schema 校验，是完整对象而不是流式碎片。第二，尚未跨界：后面紧接着的如果是外部动作，那么检查点要设在动作之前，这样重放时最多重复一次“准备做但没做成”，而不会重复“已经做成”。第三，成本值得：每步都存等于把编排变成数据库写入密集任务，通常的做法是只在昂贵的步骤之后存，以及在每个分支点之前存。

可重放边界怎么定。把步骤分成两类，纯计算与外部副作用。纯计算步骤随便重放，成本只是时间与 token。外部副作用步骤——发消息、写库、下单、扣款——必须满足两个条件之一才允许被重放跨越：要么它天然幂等或者接受幂等键，重复调用返回同一结果；要么它有配对的补偿动作，重放前先执行补偿或确认补偿已完成。两者都不满足的步骤，只能设计成“人工确认后才能重放”，或者把它的执行结果先落到检查点、由后续步骤消费，永远不再重跑。副作用标识要写进检查点，重放时按标识跳过，这是避免重复花钱最直接的一招。

重放时避免重复付费还有三件具体事项。第一，重放以步骤为单位而不是以流程为单位，运行时先比较检查点里的步骤序号与当前要执行的步骤，已完成的直接取快照产物，不重新调用模型。第二，给每次流程执行一个稳定的执行标识，模型调用与工具调用都带上它和步骤序号作为幂等键，这样即便程序崩溃在“调用已发出、结果未落盘”的窗口里，重试也不会被上游当成新请求二次计费；上游不支持幂等键时，就在落盘前做一次查询确认。第三，重放要区分“接着跑”和“从头跑”两种意图：前者是故障恢复，复用已有花费；后者是版本升级或输入变更，需要显式声明并重新计算预算上限。

重放最容易踩的坑是隐式依赖：某步骤除了状态里的字段，还偷偷读了当前时间、随机数或某个全局配置，重放时环境变了，输出就变了，于是同一条流程出现两份互相矛盾的中间产物。解决办法是把这些隐式输入在首次执行时就固化进事实类字段，重放只读状态，不读环境。

并行与汇聚

结论先行：并行分支必须有显式的汇聚点与合并规则；部分失败默认不阻塞汇聚，但要按分支的关键性分级；超时后已经花费的预算要计入总账并决定是放弃还是继续等。

分支并行的收益是把串行等待时间折叠起来，代价是状态合并的复杂度。合并规则要先想清楚三件事。第一个是产物冲突：两个分支写出同名字段怎么办。稳妥做法是分支产物各写各的命名空间，汇聚节点显式声明怎么合并，取交集、取优先分支、要求一致否则报错，三种里选一种，不要靠“后写的覆盖先写的”这种隐式行为。第二个是部分失败：四个分支回来三个，是继续还是重跑失败的那个。判据是该汇聚点后面是否还需要失败分支的产物——不需要就按“尽力而为”继续，并在状态里记录缺失；需要就重试或整条失败。第三个是终止性：任何一个分支挂住，汇聚点就永远不到。所以每个并行分支都要有独立超时，汇聚点也要有等待上限，两者是不同参数，只设前者会漏掉“分支都在但迟迟不齐”的情况，只设后者会漏掉“单分支卡死”。

汇聚还有两种常见形态需要分开处理。一种是“全齐才走”，用于所有分支都是必需输入的场合。另一种是“先到先得，取第一个满足质量条件的结果”，用于同一任务的多个候选实现，例如同时用两种策略抽取再取更可信的一份；这种形态必须在汇聚点取消其余分支，否则成本翻倍而收益为零。取消要能真的取消，把分支放进可中断的执行单元，别只靠“结果不再读取”来假装取消。

超时后的预算处理是本文想单独强调的一点。分支超时的时候，钱已经花了，这笔花费不能因为结果被丢弃就从账上消失。正确做法是超时分支的消耗照常计入总预算与成本归因，同时把它的产物标记为“不可用但已付费”，让人看得见沉没成本；否则下一次的容量规划会系统性低估。是否继续等待要有规则而不是临场判断，例如按分支关键性与剩余预算比较，或者对同一步骤设置“首次超时重试、二次超时降级”这样的显式策略，降级路径必须在流程定义里存在，不能靠异常兜底悄悄跳过校验。

人工介入

结论先行：确认点只放在三类动作之前——对外动作、不可逆动作、超过阈值的动作；其余地方加人工介入，只会让流程变慢并稀释人的注意力。等待期间流程状态必须落盘为等待态，且必须有超时策略。

为什么是这三类。对外动作的影响范围超出系统边界，例如把结论发给客户、把内容发布出去，错了无法在系统内悄悄修好。不可逆动作的关键在于补偿成本，写一条可以覆盖的记录不需要审批，发起一笔转账需要。超阈值动作是数量意义上的风险控制，单笔小金额自动放行、累计超过某个额度转人工，阈值本身是业务决定；本文出现的阈值都属于团队约定示例，读者要按自己的风险承受力重新定标，不能照抄。

确认点怎么放还有两条实操细节。第一，人要看的不是全部产物而是差异与依据：把待确认项列成“结论、支撑字段、模型不确定之处”三段，人才能真正做出判断；把几十屏原始文本甩给人，等于把决策又推回模型。第二，确认点要在副作用之前而不是之后，这一步听起来显然，实际实现里经常出错，因为开发者习惯在动作函数返回后再问一句“要不要发通知”，那时已经不可撤销了。

等待期间的状态保存要有三条约定。状态必须持久化成等待态而不是靠线程阻塞，否则进程重启就丢；等待态要写明在等什么（哪个确认点、等谁）与等什么条件（批准、驳回、超时）；恢复执行时要把等待期间可能发生的变化考虑进来，例如输入对象在等待的两天里被别的流程改了，那么批准后再执行前要重新校验一次前置条件，这一条在检查点章节里属于隐式依赖问题的人工版。

超时策略要区分三种含义清楚的超时：人没响应、消息没送达、系统重启后忘了去提醒。前两种都要有升级路径（换审批人、走代理规则）与默认动作（默认驳回比默认放行安全，但要显式写在流程定义里），第三种靠提醒任务与等待态一起持久化来避免。最不该出现的默认动作是“超时即自动批准”，除非这个确认点只是走形式，而那说明它本就不该存在。

失败补偿与终止

结论先行：重试要有上限并且上限写在流程定义里；防死循环靠单调递增的进展度量，不靠模型自觉；终止条件必须显式声明为图上的边；失败后要留下人能直接读的证据链。

重试上限。单步失败最常见的原因是瞬时问题，重试有效；但模型调用的失败经常是持续性的，同样的提示词再问三次还是同样的错误。区分两者靠失败分类：传输层与限流类错误可以按退避重试，schema 校验不通过、语义明显不对这类结果性错误重试无意义，应该走降级或转人工。每次重试都要把尝试次数写进状态，作为可观测字段，别让它藏在执行器内部。退避要有上限与抖动，否则一条流程在下游故障时会把重试压力放大。

死循环防护。自由 Agent 与带回退边的状态机都可能陷入两个状态互转而不产出新东西。防护办法不是设一个全局最大步数了事，而是要求每轮循环都必须推进某个单调量：已确认字段数增加、待补项减少、总分提高、尝试次数增加。循环条件里显式检查这个量，两轮没有推进就强制终止。全局步数上限作为最后一道保险仍要保留，它的角色是兜住“单调量本身写错了”这种实现 bug。

终止条件怎么显式写。本文主张一条流程至少声明四类终态：成功完成、校验不通过后放弃、预算耗尽而中断、人工驳回或超时。四类都要是图上的真实节点而不是异常抛出，理由是终态决定状态里写什么、给人看什么、要不要发通知。预算耗尽这一类特别容易被漏，因为它的触发点在循环中间而不是某步的返回值里；正确做法是每步开始前先比较已花费与上限，超了就转入预算终态，把当前产物封存。

失败后的证据链要按“人能在两分钟内明白发生了什么”来组织。至少包含：流程实际走过的步骤序列、每步的输入摘要与输出（脱敏，见下一节）、终止于哪个终态以及触发它的条件值、失败步骤的尝试次数与每次的失败分类、如果停在人工确认点则写明等给谁、等什么、等了多久。这份证据链应该由流程运行本身产出，不是靠事后翻日志拼出来——只有运行时有状态，才知道“这一步实际读了哪几个字段”。

可观测性与成本护栏

结论先行：观测的最小单位是步骤而不是请求；留痕要脱敏，不留用户原文；耗时与 token 要能归因到步骤和分支；成本护栏的触发口径必须在流程外也能被读懂。本文给出的所有阈值都是团队约定示例，不是推荐值。

步骤级输入输出留痕。传统服务观测到接口调用为止，编排还需要记录“这一步喂给模型的字段是什么、模型回来的结构化对象是什么”。留痕的字段名清单要固定，便于批量分析；内容要脱敏：用户原文不进观测存储，进的是摘要、长度分布、命中的实体类别这类可判断问题的派生信息。这么做不是形式主义，而是因为编排产物里经常出现敏感字段被下游步骤原样搬运的情况，如果观测层照单记录，等于把数据保留策略绕开了。观测还要记录“这次执行读了状态里的哪几个键”，这是排查上下文膨胀与隐式依赖的唯一线索。与外部工具和上下文系统的对接协议仍在演进，官方在推进传输层与鉴权方面的改动，本文不落到任何具体条目，只强调一条：外部调用的留痕里要带上调用标识，用于对账与重放跳过。

耗时与 token 归因。三个口径最容易漏。第一，等待时间要与计算时间分开统计，人工确认或上游排队占掉的时长如果混进步骤耗时，优化方向会被彻底误导。第二，重试的消耗要显式归因到“重试”这个标签，否则单步成本看起来正常，总账却不正常。第三，多分支并行的成本要在汇聚时按分支汇总，并记录哪个分支的产物最终被采用——被取消或被丢弃的分支照样花钱，这部分成本如果没有归属，就会变成无法解释的固定开销。模型侧计费与流程侧计数是两套数字，两者都留，比对它们的差值能发现漏记的步骤。

成本护栏。护栏要有硬阈值与软阈值两层，软阈值触发降级与告警，例如后续步骤改用小模型、跳过增强环节；硬阈值触发中断并进入预算终态。触发口径要写成流程级别的累计量，不能只看单次调用，因为自由循环的风险恰恰体现在累计上。护栏还应该有第二维度：单条流程的步数上限与同一输入的重入次数上限。后者用来防一类隐蔽故障——上游把同一份输入重复投递，流程每次都正常完成，成本却成倍增长。护栏触发的记录要与证据链合并，让看的人立刻明白是“哪条阈值在哪个步骤被触发”。阈值取值口径请团队自己定标并在文档里标注为约定示例，本文不给数字。

一条完整流程的编排形状

结论先行：把前面所有要素落到一张图上，就是分支、汇聚、回退、人工确认、四类终态与副作用点各自位置分明。

这条流程处理需要人把关的材料审核场景，刻意不使用任何框架的术语与接口，因为这套形状与具体库无关；某个多智能体框架的实战写法由它的专文负责，Go 侧的编排与工具调用细节也有对应文章，本文只保证这张图在任何一个执行器里都能被表达。

flowchart TD
  A[开始] --> B[意图分类]
  B --> C{分类结果可用}
  C -->|可用| D[并行分支起点]
  C -->|不可用| Z1[终态 提前结束]
  D --> E[抽取主体字段]
  D --> F[抽取金额字段]
  D --> G[规则命中扫描]
  E --> H[汇聚合并并写检查点]
  F --> H
  G --> H
  H --> I{校验结果}
  I -->|待补且轮次未达上限| J[定向补抽取]
  J --> H
  I -->|不通过| Z2[终态 校验失败]
  I -->|通过| K[风险分档]
  K --> BG{累计花费超硬阈值}
  BG -->|是| Z3[终态 预算中断]
  BG -->|否| L{风险需要人工确认}
  L -->|低| M[生成幂等键]
  L -->|中高| N[等待人工确认并持久化状态]
  N --> O{确认结果}
  O -->|批准| M
  O -->|驳回或超时| Z4[终态 人工未放行]
  M --> P[对外提交 唯一副作用步骤]
  P --> Q[封存证据链]
  Q --> R[终态 成功完成]

读这张图有五个要点。汇聚点 H 是唯一的合并位置，三个分支的产物只在这里合，合并规则写在定义里。回退边 J 到 H 带着轮次条件，所以循环有界。人工确认点 N 位于副作用步骤 P 之前，且节点名里写明要持久化状态。硬阈值检查 BG 放在风险分档之后、确认之前，这样预算中断不会把已经提交的动作退回一半。P 被标为唯一副作用步骤，整张图里只有一处不可逆动作，重放边界因此非常清楚：P 之前任何位置失败都可以从检查点续跑，P 之后失败只能靠查询外部受理结果来判断要不要补偿。

对照前面的表格看，这张图用状态机表达比用 DAG 更自然，原因就在回退边与等待态这两处；而它的绝大部分骨架其实仍然是固定的，这也印证了第 2 节的建议：外层状态机加内层固定片段，是实践中最常见的混合形态。

小结

本文把编排定义为把不确定的模型调用组织成可复现、可恢复、可观测的流程，它解决流程问题而不是模型能力问题。可用的抽象只有两类，DAG 保证可静态校验与预算可预估，状态机保证循环、等待与转移可表达，实践中用外层状态机套内层固定片段。能写成固定流程就别放开循环，选型前先回答那串问句，尤其是有没有可靠的达标判定函数。每一步输入输出 schema 化、状态按事实与派生与控制三类分字段、上下文随步骤收缩，检查点与汇聚才有可依赖的数据形状。重放边界由副作用决定，不可幂等又无补偿的步骤不许被跨越，花费要计入总账。确认点只放在对外、不可逆、超阈值三类动作之前，等待期间状态落盘且必须有超时升级路径。重试有上限、循环有单调进展度量、四类终态显式声明，失败才谈得上补偿与证据链。最后，观测以步骤为最小单位，脱敏留痕，耗时与 token 分口径归因，护栏阈值一律标注为团队约定示例。上手顺序本文建议是：先固定流程加检查点，再加工具与人工确认，最后才考虑放开循环。
