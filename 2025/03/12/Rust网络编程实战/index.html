Rust 网络编程实战

本文属于《Rust 学习路线》第 58/68 篇
上一篇系列目录下一篇

网络代码的故障很少出在语法上，多数出在“字节流没有消息边界”“超时不是断开”这类语义细节上。本文从标准库的阻塞式接口讲起，把 framing、缓冲、超时、重连、DNS 串成一条线，适合写过 Rust 但没处理过裸 socket 的后端读者。

从阻塞式 socket 讲起

结论先行：std::net 的 TcpStream、TcpListener、UdpSocket 只是操作系统套接字的薄封装，错误统一塞进 io::Result，剩下的协议语义全靠调用方补。

TcpListener 负责被动打开：bind 一个本地地址得到监听句柄，accept 阻塞等到一条已建立的连接并返回新的 TcpStream 与对端地址。TcpStream 是主动打开的那一端，connect 之后就是一条双向字节流。UdpSocket 没有必然的“连接”含义，send_to 与 recv_from 每次调用都带地址，一次发送对应一个完整数据报。

错误模型是 io::Result<T>，也就是 Result<T, io::Error>。Error 里要分开对待的是 kind() 返回的 ErrorKind 与 raw_os_error() 返回的系统 errno：前者是给控制流用的粗分类，本文常打交到的成员是 WouldBlock、TimedOut、ConnectionRefused、BrokenPipe、UnexpectedEof；后者是给日志和定位用的细节。决定要不要重试看 kind()，弄清到底发生了什么看 errno，写反了会让分支匹配不完备。还有一点容易被忽略：ErrorKind 是不完备枚举，匹配时必须带兜底分支。

地址解析与连接建立

结论：把解析和连接分开处理，是因为两者的失败原因、重试价值、超时口径完全不同。

TcpStream::connect("127.0.0.1:8085") 这类一步写法看着省事，代价是把 DNS 解析和 TCP 握手绑成了同一个错误：从 io::Error 里分辨不出“域名解析不出来”还是“端口没人监听”，也就没法决定该重试还是该报错。分开写的做法是先用 ToSocketAddrs 的 to_socket_addrs 拿到地址列表，再逐个尝试，中间失败只记录不抛出。

超时是第二个坑。2021 edition 的标准库里，主动连接有 TcpStream::connect_timeout，它接受一个 Duration；bind 出来的监听句柄和 UdpSocket 没有构造期超时参数，只有创建之后的 set_read_timeout 与 set_write_timeout，且 accept 并不吃读超时，别指望套接字选项在所有系统上行为一致。现实做法是：建连阶段的短超时交给 connect_timeout，长会话的静默检测交给应用层心跳。

地址类型上，SocketAddr 统一表示 IPv4 与 IPv6，端口是 u16；bind 时写端口 0 表示让系统分配临时端口，真实端口要再调 local_addr() 才拿得到。

拆包与粘包

结论：TCP 是字节流，没有消息边界。任何“调用一次读就拿到一个完整请求”的代码都是巧合，不是正确。

发送端写两次、各 100 字节，接收端完全可能先读到 37 字节再读到 163 字节；反过来两次写也可能被合并成一段。这是流语义本身，不是 bug，所以必须在应用层定义 framing，常见三种做法。

长度前缀：帧头放一个固定宽度的无符号整数，表示紧跟的负载字节数，本文示例统一用 4 字节大端。优点是解析便宜，能在分配之前拒绝异常大的帧。坑在“读满”：read 允许返回少于请求的数量，必须循环直到读够或者对端关闭。read_exact 是这个循环的标准库版本，但它遇到 EOF 直接返回 UnexpectedEof，此时帧头已消费一半且无法退回，只能把这条连接判为不可用。

分隔符：像换行结尾那样切分，适合文本协议。代价是负载里出现同一字节序列时必须转义，忘了转义就会切出畸形帧。

固定长度：实现最简单也最脆弱，字段变化即不兼容变更，小消息还要填充浪费带宽，只适合严格定长的记录格式。

三者的真正区别在错误恢复能力：长度前缀可以先校验长度再断开，分隔符可以扫描下一个分隔符重新对齐，固定长度一旦错位就追不回来。

读写缓冲

结论：逐字节的系统调用是性能问题的第一现场，但缓冲带来的收益必须和它的边界一起记住。

read(&mut buf[..1]) 每次都要进一次内核。解析代码如果按字节推进，读 1 KB 就是 1024 次调用，用户态与内核态切换的固定开销远大于解析本身。读侧的标准库解法是 BufReader<R>：它内部有一块默认 8 KB 的缓冲（with_capacity 可自定义），把小读合并成一次大块读，同时提供 fill_buf 与 consume 这套“先看一眼再决定吃多少”的能力。

适用边界有两类。其一，BufReader 会预读，缓冲里可能已经装着下一个请求的字节。如果连接是一问一答模型，处理完响应就把底层 TcpStream 还给池子或交给别的线程，剩余字节就永远丢了——这是连接复用最常见的数据错乱来源。正确做法是把 BufReader 当成连接状态的一部分，和 socket 成对存放、成对取回。其二，BufReader 只管读侧，写侧要单独用 BufWriter。

写侧更要紧的是刷新时机。BufWriter 在 Drop 时刷新，而 Drop 里的错误会被忽略：写进缓冲不等于写进网络，只在正常路径显式 flush 的话，提前返回或 panic 时最后一段数据会静默消失。所以每处理完一个响应必须显式 flush 并检查它返回的 io::Result，把 Drop 只当兜底。

半包与超时

结论：要区分“暂时没数据”和“对端已关”，只看 read 的返回值不够，必须把超时设置与 ErrorKind 放在一起判断。

阻塞式的 read 返回 Ok(0) 表示对端正常关闭了写方向，这是 EOF 唯一可靠的信号；返回 Err 且 kind() 为 WouldBlock 表示暂时没有数据可读；返回 Err 且 kind() 为 TimedOut 表示 set_read_timeout 的时间到了。第三种情况最要记住：超时不是断开，连接还活着，已消费的字节位置依然有效，可以从上次进度继续读。因此 framing 循环应写成“状态加剩余待读字节数”，超时返回时不重置状态，只累加等待时长，超过阈值才主动关闭；心跳间隔必须明显小于这个阈值，否则会在正常空闲时把对端踢掉。

读超时和写超时不等价：读超时是“我在等对方发字节”，触发条件是对端不发；写超时是“内核发送缓冲满了塞不进去”，触发条件往往是对端不收或链路断。写侧的典型过程是 write 先返回少于请求的字节数（部分写），随后才出现 WouldBlock 或 TimedOut。所以不能假设一次 write(&buf) 就送走 buf.len() 个字节；标准库提供 write_all，但阻塞模式下它解决不了“对端永久不收”的悬挂，除非配合 set_write_timeout。

异步形态对照

结论：同一段 framing 逻辑换到异步下，改的是“等待”这个动作，不是解析规则；所以解析代码要保持运行时无关。

tokio 当时的 1.x 主线上，AsyncReadExt::read 的返回语义与标准库一致：Ok(0) 仍然是 EOF，而 WouldBlock 由运行时内部消化成一次挂起，不需要手写轮询。于是“读满”循环要么变成 read_exact，要么变成带状态的增量喂入，下面示例的前半部分就是与运行时无关的帧状态机。

为什么切成这样：FrameReader::push 只接受 &[u8]，不认识任何 IO 类型，阻塞版本可以把 fill_buf 与 consume 拿到的字节喂进去，异步版本可以把 read 拿到的字节喂进去，两端共用同一套边界判定和长度校验，单元测试不需要造 socket。本文的口径是：字节到消息的转换写成运行时无关，等待与唤醒留给 IO 层。运行时调度与 spawn 属于《Rust 异步编程与 tokio 入门》，reactor 与 epoll 那一层的机制属于《Rust 异步 IO 模型解析》，服务层与代理转发分别见《Rust 高性能网络服务实践》和《Rust 实现高性能代理》，本文都不展开。

重连与连接复用

结论：重连必须退避加抖动，池化必须先证明收益，证明不了就别加。

固定间隔重连在单个进程里看没问题，一千个客户端同时断连就变成每秒上千次的集中尖峰，这叫重连风暴。指数退避把间隔按 2 的幂推上去，示意值取初始 100 ms、上限 30 s，再叠加随机抖动让不同进程的唤醒时刻错开。抖动不是装饰：只退避不抖动时，失败时刻与退避序列都同步，尖峰只是被推后而不是被摊平。超过一定次数应当放弃并上报，不要无限重试把错误埋掉。

健康探测要分清层次。TCP 层的 set_keepalive 只能证明对端主机可达，探测不到“进程活着但不处理请求”这种半死状态，默认周期也长到没有实用价值。可靠的做法是应用层心跳配合读超时：心跳间隔小于上一节的空闲断开阈值，连续几次没有回应就断开重建。空闲连接要自己先关，因为服务端往往先踢掉它；复用一条刚被踢的连接，第一次写就会撞上 BrokenPipe。

什么时候不该池化：连接绑定了服务端会话状态（认证上下文、未完成事务、游标）时，协议允许乱序响应时，调用频率本来就低时。池化换回来的是缓冲残留、健康检测、池满排队这三套复杂度，收益只有省掉建连开销，两者不成比例时不如每次新建。（Go 侧的池化取舍见《Go 连接 Redis 与缓存设计》，产品层治理见《Nginx 反向代理与负载均衡》，本文只覆盖 Rust 这一侧。）

DNS 与地址列表

结论：解析返回的是一串地址而不是一个地址，只尝试第一个是典型的可用性 bug。

to_socket_addrs 返回的是一个迭代器，里面可能混排 IPv6 与 IPv4 的多个地址，顺序由解析器和系统配置决定，同一域名两次解析的结果顺序可能不同。如果代码取第一个地址、连一次就抛错，等于把可用性押在解析器的排序策略上。正确做法是遍历列表逐个尝试直到成功，每失败一次记下它的 kind()，列表耗尽再返回错误。诊断时要区分两种情况：整个列表为空是解析失败，重试有意义；列表非空但每个地址都被拒是 ConnectionRefused，重试没有意义，该查服务是否起来、端口和地址是否写错。

双栈主机上更麻烦的是 IPv6 路由配了但通不出去：SYN 发出去没有回音，于是连接卡在超时上，把用户的第一次请求拖成秒级等待，而这一刻 IPv4 其实完全可用。Happy Eyeballs 这个思路的定位就是交错甚至并发地尝试两类地址，谁先成功就用谁，本文只提名字与作用，不展开算法细节。标准库的解析是同步阻塞调用，高并发下会占住调用线程；解析结果可按 TTL 做进程内缓存，但负缓存时间不要放太长，否则临时故障会被放大。

问题对照表

结论：各节故障在线上有共同特征，先对齐“表现”与“定位方法”，再谈处理手段。

问题 表现 定位方法 处理手段
粘包与半包 单次读到的字节数与预期不符，解出畸形帧 打印每次读的返回长度与累计偏移，对比发送端写次数 统一长度前缀 framing，用状态机循环读满

读缓冲残留 连接归还复用后，响应错位一个请求 检查归还前 BufReader 内部未消费的字节 socket 与缓冲器成对存放，取回时校验状态

小结

本文的主线只有一条：标准库给你的是一条字节流和一个 io::Result，消息边界、超时语义、地址列表都要自己补。framing 要在长度前缀、分隔符、固定长度里明确选一种并让两端共用；读写缓冲能解决逐字节调用的开销，但预读与延迟刷新会带来新问题，缓冲器要和 socket 一起管理并显式刷新。超时不等于断开，Ok(0) 才是断开，写侧还要处理部分写。异步只是把等待换成挂起，解析逻辑保持运行时无关。重连要退避加抖动，池化要先证明收益，DNS 要按地址列表逐个尝试并考虑双栈回退。把表里的定位手段固化下来，多数故障在第一次复现时就能归类。
