Rust 实现分布式限流器

本文属于《Rust 学习路线》第 61/68 篇
上一篇系列目录下一篇

限流算法的教科书定义——令牌桶、漏桶、固定窗口、滑动窗口各自是什么、彼此怎么取舍，以及在体系设计的哪一层挂限流，本项目已经有若干篇文章写过，本文不重讲。本文只谈一件更窄的事：当算法和挂载点都已经定下来，你准备用 Rust 落地一个跨进程共享状态的限流器时，代码会在哪些地方出问题。

这些问题的根源可以收敛成三句话：状态存在共享存储里，判定同时发生在多个节点上，时间是在各节点本地读出来的。这三件事一旦分离，很多在单进程里”顺手写一下”就正确的代码会变成缺陷。下面按这个框架逐项展开实现细节。

三个分离：本文的问题框架

一个进程内的限流器很好写。所有状态都在自己的地址空间里，判定和更新发生在同一段临界区中，时间戳来自同一个单调时钟源。此时一个 Mutex 或者一个原子计数器就足够：把配额装进一个整数，每次请求做一次带边界检查的递减，正确性由内存模型直接保证。我们不需要担心”另一个进程也在改它”，也不需要担心”我看到的现在和你看到的现在是两个时刻”。

把它改成分布式的，上述三个前提同时失效：

  • 状态外置。窗口计数、令牌余额这些数字被搬到了一个共享存储里。它不再是你内存里的字段，而是一次网络往返的目标。你无法用 Mutex 保护它——Mutex 只锁得住本进程。
  • 判定多点化。同一份配额在十几个甚至上百个节点上被并发读取。任意一个节点看到的”当前剩余量”从它读出来那一刻起就已经过期了，因为别的节点正在同时消费它。
  • 时间本地化。如果你在 Rust 侧调用系统时钟来划窗口，那么”当前落在哪个窗口里”这个结论是每个节点各自算出来的。进程启动时间不同、虚拟机的时间再同步周期不同、跨可用区部署，都会让同一毫秒在两个节点上被归进不同的窗口。

本文后面每一节都在处理这三条中的一条或几条。为了避免跑题，这里先明确几条与兄弟文章的分工：与限流算法原理和体系设计层面文章的分工是，本文假定算法选型已经完成，只谈实现；与《Rust 高性能网络服务实践》的分工是，本文不讲限流器作为中间件挂在服务层的哪个位置，只讲限流器本体；与《Rust 数据库连接池实现》的分工是，本文只在”共享存储客户端复用同一个连接池”这一点上提一句，不展开池化；与《Rust 实现 Redis 协议解析》的分工是，本文把共享存储客户端当作已经能发命令的黑盒，不讲协议帧的编解码。

原子性的来源：把三步压进共享存储端

“读计数 → 比较 → 写回”这三步在多个节点并发下必然超发，原因不是竞态窗口小不小，而是根本没有窗口能把它关起来。假想配额是 100，两个节点在计数为 99 时同时读到 current = 99，两边都比较出”还能放”，两边都执行自增，最终计数变成 101。放行量比配额多出 1。这个例子只有两个节点，把节点数换成 N、把并发度换成真实流量，超发的规模就是 N 倍量级的，而且随负载上升。

关键点是：这三个步骤之间的间隙，你不可能在客户端侧用锁去填。Rust 的 Mutex、RwLock、原子操作、SeqCst 排序，作用域全都限定在单个进程的地址空间内。跨进程的互斥必须由持有状态的那一方来提供。也就是说，判定逻辑必须搬到共享存储那一侧去执行。

在 Rust 侧，一个限流器的正确形态是：它只负责把参数送进原子操作，并解释返回的结论；判定逻辑不在 Rust 里。这条约束值得写成接口层面的强约束，让人没法误用：

这段接口里有三个刻意的设计决定，它们都是踩坑之后的产物。

第一，AtomicGate 上没有 get 也没有 incr。如果 trait 允许调用方单独读计数，就一定会有人在别处写 if read() < limit { consume() }，把原子性拆碎。接口不提供这种可能性，比文档里写”请不要这样用”有效得多。

第二，GateError::BackendUnavailable 和 Decision::Rejected 是两个不同的类型，绝不能合并。”存储告诉我拒绝”和”存储没告诉我任何事”在产品行为上完全不同：前者应该返回 429 并携带重试时间，后者要走降级路径。把它们混成一个 Ok(false)，等于把可用性故障伪装成业务限流命中，监控上完全看不出来。

第三，BackendError::MaybeApplied 单独列出来。请求已经发出、超时没收到响应，这时候配额可能已经被扣掉也可能没有，而你无法区分。这个不确定性是后面”退还”路径必须设计的根本原因——你不能盲目退还一个不确定是否被扣的量，也不能假设它一定没被扣。

正常路径的一次完整判定，时序是这样的：

sequenceDiagram
    participant C as 调用方
    participant R as 本地限流器
    participant L as 本地兜底桶
    participant S as 共享存储原子操作
    C->>R: allow(key, cost)
    R->>S: consume(参数: limit, window, cost)
    Note over S: 读旧值、比较、写回在同一步内完成
    S-->>R: Allowed 或 Rejected
    alt 存储正常返回
        R-->>C: 放行或拒绝
    else 存储失败或超时
        R->>L: try_consume(保守配额)
        L-->>R: 本地结论
        R-->>C: 降级结论并记录兜底启用
    end

顺带一句连接池的事：AtomicGate 的实现内部复用同一个共享存储客户端连接池，与《Rust 数据库连接池实现》里讨论的池化问题是同一套，本文不重复。只提醒一点——池的获取超时应当短于调用方的整体超时，否则限流器自己会变成排队的地方，一个存储抖动会把上游的 worker 全部占住。

时钟偏移：窗口边界为什么会错位

固定窗口和滑动窗口类实现都需要一个”现在”。如果这个”现在”来自 Rust 进程本地时钟，会发生下面的事。

节点 A 的本地时间是 12:00:00.980，节点 B 因为再同步周期和虚拟化开销，本地时间是 12:00:01.020。窗口长度 1 秒、按秒对齐时，A 算出的窗口标识是”第 0 号窗口”，B 算出的是”第 1 号窗口”。这两个键在共享存储里是两条完全独立的状态，各自有各自的配额。逻辑上只有一个窗口的流量，物理上被切成了两个桶，于是这一个真实时间段里的总放行量接近配额的 2 倍。偏移量只有 40 毫秒，超发比例却是 100%——窗口边界附近的偏移放大效应和窗口长度成反比，这是它最反直觉的地方。

更糟的是这个错误不需要”两个节点时钟正好跨过边界”才发生。偏移是一个连续分布的量，只要两个节点的时钟差在窗口长度的一定比例内，它们就会以某个概率落到不同窗口里。偏移越大，落在边界附近的概率密度越高（因为边界两侧的状态是”粘性”的：偏移恒定偏正的节点，总是倾向于比参考时间早一秒进入新窗口）。

三种应对手段，各自都要付代价：

其一，以服务端时间为唯一真源。 窗口标识不由客户端计算，而由执行原子操作那一侧的时钟计算，或者干脆让原子操作自己去维护”当前窗口”的状态（内部存一个窗口起点，请求进来时由存储端判断是否翻页）。这样所有节点看到的是同一个”现在”，边界错位从根上消失。

代价有三层。第一，存储端时钟本身也不完美，只是它的偏移从”N 个应用节点两两不同”收敛成了”1 个存储节点的时钟”，问题的方差变小但没有归零。第二，如果你的原子实现是”客户端传窗口标识、存储只做加法”这种形态，改造成服务端时间源意味着把窗口计算搬进脚本，脚本变复杂、可移植性变差。第三，也是实践中最麻烦的：单元测试里你没法再靠”sleep 一秒”来翻页，必须把时间做成可注入的（这一点在验证一节会展开）。

其二，窗口边界做抖动容忍。 承认偏移存在，在边界附近放宽判定：比如把窗口长度设为 W，但允许”上一个窗口的剩余配额”在下一个窗口开始后的一个抖动带内继续被消费（或反过来，在带内提前扣减下一个窗口的配额）。实现上通常是让原子操作同时看两个相邻窗口的计数，按比例加权。

代价是它把”限流”变成了”软限流”。抖动带内的放行量是可以超过单窗口配额的，如果你的下游对峰值不是平滑容忍而是硬顶（例如某第三方接口按秒计费、超了就封），带内的超出就是真实损失。另外加权逻辑让原子操作从一次整数比较变成两次读加一次算术，脚本复杂度和出错面积都上升。

其三，把窗口拉长以降低偏移占比。 这条最朴素：偏移 40 毫秒在 1 秒窗口里是 4% 的时间占比，在 60 秒窗口里是 0.07%。窗口越长，边界错位的相对影响越小。

代价是配额粒度变粗。60 秒窗口允许 60000 次，恶意流量可以在窗口刚翻页时一次性打满 60000，下游在那一瞬承受的峰值远高于平均值。长窗口保护的是”总量”而不是”节奏”，这是两种不同的需求。另外，窗口越长、状态过期时间就得设得越长，存储里同时存活的键数量上升，被限流键的基数也会更长时间地驻留。

关于 NTP，必须说清楚：用 NTP 对齐不是根治。 NTP 能把时钟收敛到几十毫秒量级，但收敛本身有再同步周期，两次同步之间漂移在累积；虚拟化环境里的时钟是宿主模拟的，guest 的 NTP 客户端看到的”时间”可能整体跳跃；跨可用区、跨机房、混合云里的时钟源本来就不是同一个。更根本的问题是：NTP 让你的时钟平均更准，但分布式限流的正确性要求的是”所有节点对同一个毫秒落在同一个窗口有一致结论”，这是一个最坏情况性质，而 NTP 给的是统计意义上的保证。把 NTP 当成解决方案，等于把正确性寄托在”偏移碰巧没有跨边界”上。

一个务实的组合是：以服务端时间为唯一真源（其一是默认选择），在没法改造成服务端时间源的存量实现上，用其三（拉长窗口）把偏移占比压到可以接受，并且显式接受”窗口边界附近放行量可能超出单窗口配额”这一事实——把它写进设计文档，而不是等到事故复盘时才发现。

共享存储失败时的本地兜底配额

共享存储不可用时，限流器只有两种基本行为：失效（全放过，等价于限流器此刻不存在）或拒绝（全拒，等价于把存储故障升级成业务不可用）。这不是技术问题，是产品决策。核心交易链路上的支付接口，宁可放大流量也不能拒绝合法用户，选失效；对下游有硬保护要求的批处理任务、外呼接口，宁可拒绝也不能打爆下游，选拒绝。这个选择必须由业务方签字，实现侧只负责把两种策略都做成可配置，而不是替业务做决定。

两种极端之间有一个可用的中间态：每个节点持有一个保守的本地令牌桶作为二级闸门。它不查共享存储、不联网、纯内存，因此存储故障时它仍然工作。

参数写法（以下是我们团队内部约定的示例值，不是行业推荐数字）：全局配额 1000/秒、集群 20 个节点时，单节点本地兜底配额取 全局配额 / 节点数 × 保守系数，保守系数在约定里取 0.5，即每节点 25/秒。容量（突发）取 2 秒配额即 50。这个例子里的 1000、20、0.5、50 都是示意值，需要按你自己的流量形状重新谈。

必须直说这个方案的后果：本地兜底配额会把总配额放大成”N 倍本地配额”。存储故障时 20 个节点各自独立地按每节点 25/秒放行，集群总放行量是 500/秒，恰好是全局配额的一半——这是保守系数 0.5 的直接效果。如果你把保守系数取 1.0，故障期间总量就等于全局配额，看起来”无损”，但没有任何机制保证流量在各节点间是均匀分布的：负载均衡抖动、长连接粘性、某个租户的请求集中打到少数节点，都会让”每节点都用满本地配额”变成”少数节点用满、多数节点空转”，最终总量超过配额。保守系数就是对这种不均匀的折扣。

多窗口一致性：预扣、确认与配额泄漏

真实场景里一个接口常常同时受两个约束：既要”每秒不超过 X”，又要”每分钟不超过 Y”。这两个约束对应共享存储里的两份状态。危险在于它们必须一起判定、一起提交。

如果分开判定，会泄漏配额。走一遍失败时序：先判秒窗口，通过；再判分钟窗口，不通过，于是这次请求被拒绝。可是第一步的判定已经把秒窗口的计数加上了 1——一个被拒绝的请求消耗了秒配额。反过来先判分钟再判秒也一样。在流量密集时这个泄漏是显著的：大量请求因为分钟约束被拒，却持续侵蚀秒窗口的额度，导致合法流量在秒维度上提前被卡住，而实际放行量远低于配置意图。

如果分开提交（即先原子地扣第一个窗口，再原子地扣第二个窗口），还多出一类问题：两次提交之间进程崩溃、连接被切断、存储第一次成功第二次返回不可用，此时状态不一致且没人知道该回滚哪一边。

两条实现路线：

路线一：一次原子操作里同时更新两个窗口。 如果共享存储提供的原子能力允许在一个执行单元里读写多个键，这是最干净的方案——判定即提交，不存在中间态。工程上有两个坑。第一，多键操作在很多存储形态里要求这些键落在同一个分片/槽位上，你的键设计必须为此服务（把窗口标识做成 hash tag 的一部分，或者给同一 gate 的多窗口状态放在同一个键里，见键设计一节）。第二，两个窗口的过期时间不同（秒窗口 TTL 短、分钟窗口 TTL 长），一次操作里要分别设置，脚本稍微复杂。

路线二：先预扣，再确认或退还。 适用于原子能力只能覆盖单键、或者两次约束落在不同存储服务上的情况。状态机是：

stateDiagram-v2
    [*] --> Idle
    Idle --> Reserved: 预扣成功（占用配额，未确认）
    Reserved --> Committed: 下游执行完成，确认扣减
    Reserved --> Refunded: 请求取消或失败，退还
    Reserved --> Unknown: 确认/退还调用丢失（超时、进程退出）
    Committed --> [*]
    Refunded --> [*]
    Unknown --> [*]: 依赖 TTL 自然过期回收

路线二的真正难点是预扣在请求被取消时如何回收。Reserved 状态的每一次进入，都必须有一条必然执行的退出路径。而 Rust 异步代码里”必然执行”这件事，恰恰是最容易写错的。下一节专门讲它。

取消安全：配额不能丢在 .await 两侧

这一节是本文区别于泛泛而谈的地方，也是 Rust 写分布式限流器最容易埋雷的一处。

先看一个看起来完全正常的写法：

Rust 的异步取消语义是：Future 在被 drop 时不再继续执行，控制权立刻交还执行器，没有任何”收尾机会”。上游超时、客户端断开连接、select! 的另一条分支先完成、整个请求任务被 JoinHandle::abort——这些都会让正在 await 的 future 被就地 drop。上面的函数在 downstream.await 这一行被 drop 时，consume 已经成功执行、配额已经扣掉，而”扣了配额之后要做的事”一行都没跑。这就是配额永久丢失的路径：它不是泄漏内存，而是泄漏额度，会持续侵蚀你的限流阈值直到窗口翻页。

更隐蔽的是这个 bug 在测试里几乎看不见。正常流量下 future 都跑到底，取消路径占比很小；只有在客户端大量断开的生产环境里，才会表现为”明明没那么多请求，却一直被限流”。

键设计与热点

限流键里放什么，直接决定了共享存储的键基数和热点分布。这是实现里最”廉价”却最容易做错的一项，因为它在写的时候完全没有反馈——功能全对，压测也过，出问题是数月之后存储的内存和某个分片的 CPU。

先看一个常见做法的后果。假设键形态是 rl:{接口}:{租户}:{用户}:{窗口}，把用户标识直接拼进去。用户是天然高基数：注册用户百万级、活跃用户每天几十万。那么一天内产生的键数量是”接口数 × 活跃用户数”这个量级，而限流器需要的状态只跟”当前有流量的 (接口, 用户, 窗口)”三元组有关。窗口翻页后旧键靠 TTL 过期，但 TTL 通常设成窗口长度的 2 倍以保安全，于是存储里同时存活的键数量是”每秒活跃组合数 × TTL 秒数”。这个乘积很容易到千万级。

这就是”把限流器变成存储压力源”的确切机制：

三类负载里第 3 类最难处理，因为它不是”多做容量”能解决的——分片是键哈希决定的，你无法把一个热键的流量分给别的分片。可行的做法是把单键拆成 N 个子键、请求随机选一个子键去消费自己那份配额（配额 = 总配额 / N）。这叫键分裂。代价是每个请求变成 N 分之一配额粒度，精度损失随 N 增大（某子键提前耗尽而另一个子键有余量时，整体是超发还是欠发取决于随机选择的分布，实践上是欠发居多，因为”提前耗尽”更容易发生）；另外当 N 很大时，一次判定要读写 N 个键，反而放大负载。所以键分裂只对”单个热键确实打到分片上限”这一种情况做，不要预先给所有键分裂。

反过来，减少基数的正确做法是只对已知租户集合限流。

如果确实需要按个体区分（例如”每个用户每分钟最多 20 次创建订单”这种反滥用需求），键里也不能放明文标识。硬约束是：键与日志里不得出现凭据、手机号、身份证、邮箱、token、session id 等标识的明文。原因是限流键会被完整记录在共享存储的键空间里、会出现在慢日志里、会被监控系统的采样记录抓走、会被各种运维工具 dump 出来——这些通道的安全等级都远低于业务数据库。把手机号写进键，等于把手机号复制进了一个没有访问控制的数据面。

选摘要算法时要想清楚两件事。第一，DefaultHasher 不保证跨进程、跨版本的稳定性，它甚至可能在同一进程内被随机化——如果你的限流键需要跨节点一致（必须一致），DefaultHasher 是不能用的，要选一个稳定的哈希。第二，摘要空间不足以覆盖键基数时会碰撞，不同用户共用一份配额。截断到 12 个十六进制字符是 48 位空间，按生日界估算，在活跃个体数量到千万级时碰撞概率仍然很低，但这个数字要按你自己的规模重新算，不要照抄。

多窗口场景下键设计还有一个额外约束：如果走”一次原子操作里同时更新两个窗口”的路线，两个窗口的状态往往必须在同一个分片上，所以键前缀里要带上一个让哈希结果一致的分组标识（很多存储形态支持在键里声明”以这一段决定路由”的机制）。这属于”取决于所选共享存储提供的原子操作能力”的范畴——先看文档，再定键形态，不要反过来。

最后一条：不要为了观测把请求内容埋进日志。限流器最容易出现的过度埋点是”把每次拒绝的完整请求参数打出来”，理由是”方便排查”。它会带来三个后果——日志里出现敏感标识（违反前面的硬约束）、日志量随攻击流量线性放大（一次恶意刷量把磁盘打满，而恶意流量恰恰是最不该放大日志的时候）、日志本身成为性能开销。需要排查时，打 gate_key（已归一化、已摘要）加拒绝原因加剩余配额，通常就够了；确实需要原始请求时，用采样或单独的 debug 开关，而不是常规路径。

验证思路：确定性实验与不变量断言

先把话说清楚：本节不给性能数字，本文也不给。QPS、P99、偏移容差、超发比例这些结论全部依赖你的共享存储形态、部署拓扑、键基数和流量形状，任何从别人机器上抄来的数字对你的环境都是噪音。下面给的是实验设计和可断言的性质，你照着做，数字自己出。

三类场景要分别做成确定性测试，”确定性”的意思是：不 sleep、不依赖真实时间、不依赖调度顺序。

其一，多节点并发。 做法是在测试里用多个任务共享同一个 AtomicGate 实现，但把”共享存储”换成一个进程内的参考实现——它用互斥锁保证自身串行执行，等价于一个”绝对正确且零延迟的存储”。

这个测试的价值在于它的精确性：如果原子性有任何一处被拆到客户端，allow 计数就会超过 limit，而且超过的量随并发度上升。它不需要跑很多次才显现，一次就能抓到。

其二，共享存储抖动。 做法是给 AtomicGate 再包一层可编排的故障注入实现：前 K 次调用返回错误、第 M 次调用延迟、某些调用返回 MaybeApplied。

LossAfterApply 是最值得单独测的一类，因为它测试的不是”限流器怎么报错”，而是”限流器在事实不确定时的收敛性”。断言写法是：注入一批 LossAfterApply，然后推进到窗口翻页，验证下一窗口的配额是完整的——如果预扣依赖 TTL 回收，这里能验出回收是否真的发生。

其三，请求被取消。 这是唯一必须由 Rust 侧单测覆盖的一类，因为取消语义是语言与运行时层面的。

注意 flush_refunds_for_test() 这个钩子：退还走后台队列以后，测试就不能通过”函数返回”来判断退还完成了，必须有一个显式的、可等待的排空点。没有它，你的取消测试会退化成一个 sleep 竞态测试，看起来通过率高但抓不到东西。

用可控时钟测窗口边界。 直接把 SystemTime::now() 散布在代码里，窗口边界就无法测试。时间必须从外部注入。

有了注入点，就能写出这类断言：”把时间推进到窗口最后 1 毫秒，让两个节点分别用带 ±40 毫秒偏移的时钟请求，断言结论仍然一致”。如果走服务端时间源路线，这个断言应当恒成立；如果走客户端时间路线，它就是那条能暴露前面”同一个逻辑窗口被切成两个桶”问题的测试。这类测试的写法是把时钟偏移也做成注入参数，而不是靠改系统时间。

最后是关于性质断言还是数值断言。生产限流器的测试里，不要写”这一批请求放行 950 到 1050 之间”这种带容差的断言——容差是给不确定性开的后门，它会掩盖真 bug。能写成不变量的就写成不变量：

小结

本文把分布式限流器的实现难点收敛到三个分离上：状态外置、判定多点、时间本地。围绕它们，可以带走的结论是这几条。

原子性只能由持有状态的一方提供。Rust 侧的 Mutex、原子类型、内存序全都只在单进程内有效，所以”读-比较-写”必须压进共享存储端的原子操作，Rust 只负责送参数和解释返回值。接口层面要刻意不提供单独读和单独写的方法，让误用在编译期就写不出来。

时钟偏移是窗口类实现最容易被低估的问题。客户端本地时间会把同一个逻辑窗口在不同节点上算成两个桶，边界附近的放大效应和窗口长度成反比。唯一有效的处理是以服务端时间为真源；抖动容忍和拉长窗口是缓解，NTP 是运维基线而不是方案。

共享存储不可用时的行为是产品决策。本地兜底配额是可行的中间态，但要说清它的代价：集群总配额被放大成”N 倍本地配额”，保守系数是对流量不均匀的折扣，弹性伸缩会让这个含义漂移。兜底启用的次数必须是独立指标。

多窗口必须一起判定、一起提交，否则被拒绝的请求会持续侵蚀短窗口配额。跨服务或单键原子能力受限时用预扣加确认/退还，但它引入了 Unknown 状态，最稳妥的收敛是让预扣本身带 TTL。

取消安全是 Rust 特有的雷。future 在 await 处被 drop 时没有任何收尾机会，扣减与下游调用分处两侧就是配额永久丢失的路径。解法是把退还绑进 Drop，但 drop 是同步函数，绝对不能在里头 block_on 或起线程做 IO——只能投递到有界后台队列或 spawn 一个脱离当前任务的任务，并且接受”尽力而为”的语义与进程退出时的丢失。select! 里裸写扣减是危险形态，因为未选中分支的 drop 正好落在”已扣、结果未知”的区间。

键设计与指标是长期的问题。限流键里的每个自由字符串都是存储的账单；个体维度需要区分时用带盐不可逆摘要并截断，键和日志里不得出现凭据或手机号等明文。指标要能回答放行比例、拒绝分布、后端失败与延迟、兜底启用次数、退还触发次数这五个问题，而且标签必须是有限集合。

验证上，不要写带容差的数值断言，写成不变量断言；把时间做成注入而不是直接读系统时钟，把存储失败做成可编排的故障脚本，把取消做成显式 drop 加一个可等待的排空钩子。本文不给性能数字，因为性能结论必须由你自己的环境实测得出。
