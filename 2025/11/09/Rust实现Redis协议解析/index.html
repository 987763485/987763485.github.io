Rust 实现 Redis 协议解析

本文属于《Rust 学习路线》第 44/68 篇
上一篇系列目录下一篇

Redis 的协议叫 RESP，本质上是一条 TCP 连接上的少量标记字符加分隔符。写一个解析器不难，难的是让它在半包、粘包、错误帧、流水线与订阅推送同时出现时仍然可推理。

本文的范围是协议编解码加状态机：拿到字节缓冲能还原出帧，能把帧写回字节流，并且知道自己在流里的位置。目标不是做一个能替换生产客户端的库。

协议的两副面孔

RESP 在一条连接上同时允许两种写法。第一种是 inline command，直接把命令当一行文本发过去，以回车换行结束；第二种是序列化协议，用首字节标记这一帧的类型，再按类型规定的结构展开。

inline 形式看起来像这样：

它的好处是人拿 nc 就能敲，调试时直觉；代价是把参数切分语义交给了实现，空格与引号的处理容易和正规帧不一致。生产链路不该依赖 inline，但解析器要能识别它，因为线上偶发地真有客户端这么发。

序列化协议用首字节区分类型，本文只使用以下几类确定存在的标记：

各标记的用途要记牢，状态机就是靠首字节分派的：+ 与 - 一行到底，长度由分隔符决定；: 同样一行到底，内容是 ASCII 数字；$ 与 * 先声明长度再按长度消费，$ 的长度按字节算而非按字符算，* 的长度是元素个数；$-1 是批量字符串的专用负长度，用来表达 nil。数组可以嵌套，元素类型不必一致。

后续版本的协议还引入了更多帧类型，比如更丰富的错误编码与更大的批量长度形式。本文不展开这些细节，实现时以协议规范为准，分派表按首字节留出可扩展的位置即可。

为什么要自己解析

理由很直接：客户端库已经够用了。业务代码要读写 Redis，选一个成熟的 Rust 客户端就行，没必要自己造。

半包与粘包

TCP 不保证一次 read 正好读到一帧：可能只有半帧，可能是一帧加下一帧的开头，也可能一次到很多帧。所以接口必须是「部分消费」语义，而不是「给我一段字节我保证返回一帧」。

最常见的偷懒是按行迭代：

它坏在两处。第一，批量字符串的内容是任意字节，本身就能包含 \r\n，按行切会把一个值劈成两行，声明长度与实际读到的字节数对不上。第二，lines() 把「读到分隔符」当成一次完整交付，它不知道 $6\r\na\r\nb\r\n 里第一个 \r\n 只是头部结束、后面 6 个字节属于值。协议里的 \r\n 有两种身份：结构分隔符，以及数据里的普通字节。只有先拿到长度字段，才知道后面按长度消费还是按分隔符消费。

缓冲区必须有硬上限，因为长度字段完全由对端给出。一个声称巨大长度的帧会让实现立刻照它分配内存，反复发送就能把内存撑爆。做法是解析出长度字段后立即校验「声明长度加已有缓冲」是否超预算，超限就判协议错误并断开，而不是等对端真把那么多字节发完。

错误帧与协议错误的区分

-ERR unknown command 'FOO'\r\n 是一条完全合法的帧。首字节 -，中间错误文本，结尾分隔符，解析器读完了它、消费了确定的字节数，流边界仍然清晰。这是协议内错误：服务端拒绝了命令，但连接照旧可用。

解析失败是另一件事。比如头部写着 $5\r\n 后面跟了不该出现的字符，或者数组声明 3 个元素但第 2 个首字节不是任何已知标记。此时「帧在哪里结束」已无答案，字节偏移不再可信：后面看起来像一帧的字节，可能只是被错误解释的半个值。

两者的处理必须彻底分开：

把解析错误当普通错误吞掉，是这类实现里最贵的 bug。设想流水线里发了 GET a、SET b 1、GET c 三条命令，第二条的响应因某个分支误判而被跳过。于是 SET 的 +OK 被当成 GET a 的响应，GET c 的值被当成 SET b 1 的响应，整条连接从此错位一格，业务侧表现为「读到的值属于另一个键」。它需要恰好一个解析分支出错，测试里几乎复现不了，在生产里却伪装成偶发的数据串台，比崩溃难查得多。

正确做法是把解析失败定性为不可恢复错误，直接判死连接，让上层看到「这条连接已作废」。宁可多一次重连，也不要让错位的响应流继续服务。

请求-响应配对与流水线

Redis 按发送顺序返回响应，请求不必带 id，也没有相关 id 可供匹配。这带来了流水线：一次写出 N 条命令，只等一次往返，读回 N 个响应，省掉 N-1 次往返等待。

sequenceDiagram
    participant C as 客户端
    participant S as 服务端
    C->>S: GET a
    C->>S: GET b
    C->>S: INCR c
    S-->>C: $1\r\nx\r\n
    S-->>C: $1\r\ny\r\n
    S-->>C: :7\r\n

配对靠一个严格先进先出的有序队列：写命令时把 waiter 压入队尾，读到响应时从队首弹出一个并把帧交给它。队首通常放 oneshot::Sender<Frame>，解析循环只负责取队首投递，业务侧只负责 await。

这套假设会在两种情况下崩掉。「少一条」：某个响应被吞，或某条命令根本没被执行。「多一条」：最常见来源是流水线里混进了进入推送模式的命令。SUBSCRIBE 一旦发出，这条连接就不再是一问一答，服务端会在任意时刻主动推送帧。这些 push 帧没有对应 waiter，会接连把 pop_front 弹空，再把真正的响应错配给后续命令。

所以流水线里不能混入订阅类命令：要么给订阅单独开一条连接，要么在连接状态里显式记住「当前是推送模式」，此时不取 waiter 而是交给订阅回调。后者还要处理订阅命令自身的确认帧，也就是形如 *3\r\n$9\r\nsubscribe\r\n... 的数组，它是对请求的答复而不是推送。

发布订阅的模式切换

模式必须写进解析器状态，因为同一批字节在两种模式下的含义不同：请求/响应模式下它是「某个等待者的答复」，推送模式下它是「服务端决定要告诉你的事」。不知道当前模式就只能一律按队列配对，第一条 push 就会吃掉队首等待者，把订阅消息当成某次 GET 的结果交给业务。

stateDiagram-v2
    [*] --> Normal
    Normal --> Subscribed: 发出 SUBSCRIBE 且收到确认帧
    Subscribed --> Subscribed: 收到 push 消息，交给订阅回调
    Subscribed --> Normal: 发出 UNSUBSCRIBE 且已退订全部频道
    Normal --> Broken: 解析失败
    Subscribed --> Broken: 解析失败
    Normal --> [*]: 连接关闭
    Broken --> [*]: 丢弃未决请求后断开

把这些都判成故障，实现就会在高峰或低峰随机断开。做法是让超时取决于当前挂起的是什么命令：阻塞命令的读超时在它自带超时之上再加一段余量，订阅连接不设「空闲即断」而是靠周期心跳探活。取值都是示意值，按自己环境的命令分布来定，集中写在配置里。

超时之后做什么，比超时本身更容易出错。请求超时后，那条命令在服务端可能仍在执行并迟早产生响应；简单摘掉 waiter，迟到响应就会落给下一个 waiter，又回到前一节的错配。安全做法是请求超时就判定这条连接不可再用，关闭重建，而不是「取消这一条然后继续用」。

重连后必须丢弃旧连接的整个未决队列，并把失败明确回传给调用方。不能假装自动恢复：新连接没有旧会话状态，那些请求执行过没有是未知数。幂等读可重试，非幂等写只能交给调用方决定；把不确定性做成内部悄悄重试，最终会在业务侧演变成重复写入。

服务端主动断开在解析层表现为读到 0 字节，也就是 EOF。它和对端复位不同：EOF 说明对方按流程关掉了写端，缓冲里剩下的字节要照常解析完再判定结束，否则最后一个完整响应会被丢掉。实现里要区分「缓冲还有成帧数据」与「连接再没有数据」，前者先交付，后者才报关闭。

集群重定向

只提方向，不展开。集群部署下一条命令可能被当前节点拒绝，回一个 -MOVED <slot> <addr> 或 -ASK <slot> <addr> 形式的错误帧：它仍是协议内错误，流可以继续用，语义却是「这条请求该送到另一个节点」。

对解析层的要求只有两点：错误文本完整保留给上层，做错误码归一化时不要把后面的槽号与地址截掉；重路由决策不要写进编解码模块。槽位表维护、节点发现与迁移期处理是集群客户端的活，本文不做。

安全硬约束

解析器要防的从来不只是崩溃。最容易被忽略的一条是：不要把键和值原样打进日志。

缓存键里常常拼了用户标识、会话标识或订单号，值更可能是业务敏感数据。调试期一行 debug!("resp: {:?}", frame) 看着无害，一旦开在 info 级别就等于把全量读写内容抄进日志，而日志的访问范围通常比 Redis 大得多，还会被采集、索引、长期留存。约定是三件事：日志只打帧类型、字节长度与错误码；必须展示内容时做长度截断；截断前先脱敏，键名保留结构前缀、抹掉疑似标识的部分。

describe 只输出类型与长度；head 只用于错误文本这种本就不含业务值的内容，且截断按字符边界走，避免把多字节字符切成半个。协议异常日志恰恰出现在最需要看内容的时候，所以这套约束要在第一行日志之前就定下来。

同样重要的是数据去向：内存中的响应体、连接串里的凭据，绝不外发到不受控的第三方服务。这包括以「上报指标」名义把键名当标签发送、把完整命令塞进链路追踪的 span 属性、在崩溃报告里附带整段缓冲。连接串一律从环境变量读取，示例与文档写成占位：

小结

本文把 Redis 协议解析拆成四件事：用 enum 建模帧类型与标记字符；用「字节缓冲加消费长度」写出可重入的解码器，同时吃下半包与粘包；用严格 FIFO 队列加显式的连接模式状态，保住请求与响应的对应关系；用两类错误分别处理，避免一次解析失误演变成整条连接串台。

三条纪律值得单独记住。解析失败就等于连接作废，不要试图在同一字节流上恢复；缓冲区上限与超时都是团队约定，必须集中一处配置；日志只输出帧类型与长度，键值截断脱敏，响应体与凭据不出本机。守住这几条，协议层的正确性才是可推理的。
