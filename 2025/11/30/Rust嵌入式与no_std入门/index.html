Rust 嵌入式与 no_std 入门

本文属于《Rust 学习路线》第 48/68 篇
上一篇系列目录下一篇

很多人第一次把嵌入式 Rust 理解为少用一点标准库，实际要接受的是一组不同的约束：没有内核可以调用，没有进程可以崩溃，时间来自外设寄存器，内存布局要自己写进链接脚本。本文按这条线走一遍，看原本由操作系统兜住的责任分别落到了谁手上。

no_std 到底去掉的是什么

std 的绝大部分内容不是语法糖，而是对操作系统承诺的封装。线程与调度、文件系统、网络套接字、进程间通信、Instant 与墙钟这类时间源，实现它们要么发起系统调用，要么依赖内核提供的数据结构与全局状态。裸机上没有内核可以被问话，这些能力连同类型定义一起消失。

留下来的 core 覆盖语言本身与硬件直接相关的基础件：Option 与 Result、迭代器及其适配器、切片与裸指针、fmt 的格式化框架、原子操作、cell、marker、cmp 与 mem。core 里没有需要分配器的容器，也没有任何”现在几点”的概念。判断一条 API 能否进入 core，标准是它要不要一个自己无法提供的运行环境，而不是它看起来够不够基础。与 Rust 原子与内存序那篇的分工是：内存模型与 Ordering 语义在那边讲，本文只在主循环与中断共享状态这一处引用它。

alloc 的位置与前提

如果设备有足够的 RAM，我们可以把堆请回来。alloc 本身是一层很薄的壳：它提供 Vec、Box、String、Rc 这些熟悉的类型，但每一次构造最终都落到一个全局分配器上。启用它有两个动作，声明 extern crate alloc，以及提供一个实现了 GlobalAlloc 的 #[global_allocator] 静态项。只做前一步的报错出现在链接阶段，抱怨的是分配符号找不到而非类型不匹配。

真正的代价在安全契约上。GlobalAlloc 的实现者必须自己保证内存池的并发正确性，因为分配和释放可能来自主循环，也可能来自任意一个中断上下文。单核裸机上常见的保守做法是把整个分配器包在临界区里，进入时掩蔽中断、退出时恢复。代价是最坏中断延迟取决于池元数据遍历的规模；如果在中断里调用 Vec::push 恰好触发扩容，你就把一段不可预期的耗时搬进了中断响应路径。所以在裸机上，”用堆还是用静态缓冲”是时延问题，不是容量问题。与 Rust 分配器一文的分工是：实现细节与通用选型归那边，本文只谈它在临界区里的后果。

启动路径与运行时提供的属性

在 main 的第一行 Rust 代码执行之前，硬件已经提了一串要求。上电或复位后，处理器从向量表取初始栈指针，再从复位向量取入口地址跳过去；这段最早执行的代码要把 .data 段从 Flash 里的初始化镜像搬到 RAM，把 .bss 段按长度清零，把中断向量表摆到硬件约定的位置，最后才把控制权交给 Rust 侧的入口。这几步做错都不会有编译错误：栈指针偏了表现为随机 HardFault，.data 忘了搬表现为全局变量初值全是 0，.bss 忘了清表现为随机脏值。

传统 C 项目里这一段写在启动文件（startup file）中，通常是厂商给的汇编加一段链接说明。嵌入式 Rust 把它挪到了运行时（runtime crate）这一层：由它提供启动序、向量表布局和入口约定。这类属性由你所选运行时 crate 提供，形态上大致三类：把函数标记为程序入口的属性、按异常种类注册处理器的属性、按中断号注册外设中断处理器的属性。具体属性名、参数写法与能否重复标注，一律以所用运行时的文档为准，跨运行时迁移时这一段几乎总要重写。与 Rust FFI 一文的分工是：与 C 互操作及 ABI 的话题不在本文展开。

链接脚本与内存布局

Flash 与 RAM 是两段物理与特性都不同的地址区间：前者掉电不丢、通常按页擦除、可以直接取指；后者小、快、掉电即失。链接脚本只回答两个问题，每一段放在哪个区间的哪个位置，每段最多允许多大。示意布局如下，地址一律用符号名或占位表示。

布局越界有两种完全不同的失败。超出某段允许的容量时链接器直接报区域溢出，问题在构建期暴露，这是好事。更麻烦的是堆与栈之间没有明确边界：启动时没给堆预留区间，或预留太小而分配器不检查就返回一个看似合法的指针，程序会一路正常运行，直到某个后续操作踩到栈帧或踩到别处当作有效的静态缓冲，表现为换个优化等级就换个死法的随机故障。所以”忘了留堆”不是编译错误，是一颗延后引爆的雷。把栈大小、堆大小与向量表位置写成显式且集中的一处配置，收益很高。

中断、临界区与共享状态

在服务器编程里，异步往往意味着任务调度器与线程池；在裸机上，异步的现实形态就是中断。外设完成一件事就拉一条线，处理器在当前指令边界打断你正在跑的代码，压栈跳进另一段逻辑，事后恢复现场。它不由你选择何时发生，也不能被 await。这决定了中断路径的两条纪律：短，且不阻塞。

临界区是最小的一致性工具，机制上是一颗可以整体开与关的全局中断掩蔽位（Cortex-M 一类架构通常由 PRIMASK 承担这个职责，具体指令本文不展开）。它必须严格配对：一次提前返回，或一次从临界区内部抛出的 panic，都会留下一个永远不再响应中断的程序，测试里表现为跑了几分钟就死掉。所以临界区的范围要压到几条复制指令的量级，里面不打印、不等待、不循环。

sequenceDiagram
    participant H as 定时器中断
    participant S as 定长缓冲与标志位
    participant M as 主循环
    H->>S: 写入本帧数据，置 ready 标志
    Note over H,S: 只在掩蔽中断的窗口内完成
    H-->>M: 返回被打断处
    M->>S: 读标志并取走帧
    M->>S: 清标志
    M->>M: 处理耗时逻辑，不阻塞下一次中断

这张图里唯一的通信手段是标志加缓冲，因为中断上下文没有地方可以等。也正因为读写来自两个执行流，共享状态需要真正的互斥：要么用原子类型，要么用显式的临界区封装。static mut 的裸写法之所以危险，是因为它把”访问要互斥”完全交给人的自觉：编译器既不检查主循环与中断是否同时访问，也不阻止你在临界区外取出的引用被中断再次改写，多个并存引用带来的后果不保证停留在”值不对”这一层。

硬件抽象的分层思路

裸机代码的可移植性来自分层，而不是来自某一层做得足够好。从上往下看通常四层。

PAC 的输入是芯片厂商发布的寄存器描述，输出是”每一位都对应一个类型化的读改写方法”。它的价值是忠实，代价是完全不能跨型号复用：换个封装或改个外设实例名，生成结果就面目全非，所以它由工具生成、由版本号锁定，几乎不手写。HAL 的工作是把这些寄存器动作翻译成有语义的能力，让”这是一个能发字节的串口”这件事与具体型号脱钩。真正让驱动生态成立的是接口规范这一层：由一个独立的 crate 只定义 trait，比如带错误类型的收发、延迟、数字输入输出这几类能力，器件驱动只依赖 trait 写实现。同一个驱动因此能工作在不同厂商的板子上，换芯片时改动集中在 HAL 那一处。本文只描述这一分层理念，不声称任何具体 crate 的 API 形态。

体积、静态分配与编译期求值

嵌入式里常避免运行期分配，理由不是省内存，而是三件让人睡不好的事：碎片让剩余可用块的最坏大小无法预先界定，一次 push 的耗时可能是常数也可能是遍历整个池，以及分配失败之后的行为要你自己定义。替代做法是把容量写进类型：以固定容量的结构替代堆分配这一类做法，缓冲长度是类型参数的一部分，装不下就是编译期错误或者显式的 Err，而不是一次悄悄发生的扩容。对象池是同一思路的另一种形态，所有可能被并发使用的节点在启动时一次性成形，运行期只在空闲与在用两个集合之间搬动。

.bss 的清零代价常被低估。这一段在镜像里不占 Flash，但启动时必须逐字节写零，容量越大启动越慢，而静态分配的容器几乎全部落在 .bss 或 .data 里。这就是把缓冲做大之后功能没变、上电到第一条日志之间的空白却变长了的原因。

const fn 与编译期求值在这里格外有用，因为查找表是嵌入式代码里最常见的静态数据。把 CRC 表、分频系数的组合枚举、ADC 的非线性修正点这类计算放进 const 上下文，运行时读到的就是已经算好的 .rodata，既省去启动时填表的循环，也让错误在编译期暴露。要留意 const fn 能做的事仍然有限：需要大量控制流或运行期才能确定的输入时，把它整个塞进编译期往往不划算，甚至写不出来。某些能力仍属不稳定，需要用 nightly 才能碰，量产项目不建议把架构决策押在尚未定型的写法上。

调试手段的几个方向

裸机调试第一个要回答的问题是：有没有输出通道可用。没有 SWD 或 JTAG 一类的调试探针，semihosting 与故障时的寄存器读数都无从谈起；而 panic 消息能不能落到人眼看得见的地方，决定了后面所有手段的价值。

选型要看你在哪一档：调试台上可以放任 semihosting 与送出型 panic，量产固件更可能需要真实串口加锁死型，把复现留给下一次连接。

稳定版写驱动的现实约束

先说不顺的部分。有些别扭来自语言与硬件的接缝，有些只是生态还没长齐。

这些变化不是把嵌入式变简单，而是把一部分隐性约定变成可检查的东西，剩下那部分仍然要人负责。

这份清单里出现频率最高的三类原因值得单列：目标三元组与链接没配好，项目从一开始就编不出可烧写的产物；内存布局约定缺失，编译通过但运行随机故障；运行时版本与 HAL 版本不匹配，表现为 trait 实现了却”不满足边界”，因为上层期望的能力来自另一个版本的定义。这三类都不是 Rust 语言问题，是配置问题，却最消耗新手的时间。

三层能力对照

三层的关系是包含关系，也是最容易被误用的地方。

flowchart TD
    A[std 依赖操作系统] --> B[alloc 依赖全局分配器]
    B --> C[core 语言与硬件基础件]
    C --> D[裸机可用的全部]

core 的代价是功能面窄，但它不需要任何前提，这是它成为地基的原因。alloc 看似只是多几个容器，实际是把一整份内存管理的责任接了过来。std 则默认了一个会替你调度、隔离和计时的操作系统；没有这个假设时，上面这些能力要一项一项自己造，造之前先问一句：它需要的运行环境在我这里存在吗。

小结

本文的线索只有一条：no_std 不是裁剪标准库，而是把操作系统原本兜住的责任分给具体的人。core 给出语言与硬件相关的基础件，alloc 要求你先提供一个并发正确的分配器，std 的那些能力在没有内核的地方只能逐项自己实现。启动序列、链接布局、中断与临界区、分层抽象、静态容器、panic 策略和调试通道，每一层都在回答同一个问题：这件事原本谁做，现在谁做。稳定 Rust 写驱动的收获在于把一部分隐性约定变成编译期可检查的东西，成本在于并发模型的心智负担和分散的文档。从一个目标三元组、一个运行时、一行串口输出、一个定时器中断开始走通，比一开始就设计漂亮的抽象层更能建立正确的直觉。
