Rust 宏进阶：派生宏实现

本文属于《Rust 学习路线》第 28/68 篇
上一篇系列目录下一篇

声明宏解决”复制一段代码并做少量替换”的问题，派生宏解决的则是”根据类型定义自动生成 trait 实现”的问题。本文聚焦派生宏本身的实现工程：从 proc-macro crate 的拆分，到用 syn 解析语法树、用 quote 拼装生成代码，再到属性解析、错误质量与可调试性。与《Rust 宏体系解析》的分工是：那篇讲宏的整体分类与语法概览，本文只讲派生宏怎么写；serde、thiserror 等库的用法不在本文范围，只在需要时作为”别人怎么写派生宏”的例子提及。

三类宏的分工与派生宏的边界

Rust 的宏体系里有三类成员：声明宏（macro_rules! 与 2.0 版宏语法）、属性宏、派生宏。声明宏在表达式、类型、模式等位置做令牌级替换；属性宏接收条目的令牌并返回替换后的条目，理论上可以把被标注的结构体整个换掉；派生宏则被语言规范限定了使用面——它只能出现在 #[derive(...)] 里，输入是一个类型定义的语法结构，输出只能是若干 impl 块，不能替换或删改被标注的类型本身。

这个限制不是实现上的偷懒，而是语义上的必要约束。如果派生宏可以重写类型本体，同一类型上多个派生宏之间就没有可预测的组合语义——A 宏重写了结构体，B 宏看到的还是不是用户写的那个类型就成了问题。所以规则是清晰的：派生宏只做加法，生成的实现与手写实现一样进入 trait 求解；属性宏才承担”改写条目”的责任，代价是更容易破坏可读性。机械可重复、随字段变化而变化的实现适合派生宏；需要类型之外上下文的逻辑则超出它的能力，它只在编译期看到那一个类型定义。

proc-macro crate 的拆分与重导出

过程宏在 Rust 里有一个硬性的工程约束：它必须住在独立的 proc-macro crate 中。这类 crate 在 Cargo.toml 里声明如下：

一旦某个 crate 声明了 proc-macro = true，它的公开接口就被限制为只能导出宏：普通函数、结构体、trait 都不允许出现在它的 pub 表面。这意味着如果把宏实现、辅助工具、文档塞进同一个 crate，用户既会被内部结构淹没，又拿不到非宏的配套设施。

所以生态里的主流做法是拆成两个 crate。内部一个叫 foo_derive 之类的名字，proc-macro = true，只放宏本身；外部一个叫 foo，是普通 crate，做三件事：用 pub use foo_derive::Foo; 把宏重导出到根路径、写非宏的运行时辅助类型与函数、承载面向用户的文档。用户只需要 use foo::Foo;，完全感知不到背后有两个 crate。

这样拆分还有一个常被忽略的收益：目标 trait 必须定义在普通 crate 里，而派生宏生成的 impl 展开发生在用户 crate 的模块树中，所以生成代码必须用全路径引用它（如 ::foo::Foo）——后文讲卫生时会回到这一点。重导出层同时给了发布节奏的自由：宏实现可以大改，只要 pub use 的接口不变，用户无感。

从语法树到生成代码

派生宏的实现主体是一条固定流水线：把输入的令牌流解析成语法树，按类型形状分支处理，再把结果拼装回令牌流。syn 库提供的 DeriveInput 是这条流水线的入口，它对应一个类型定义的全貌：标识符、泛型参数、where 子句，以及一个 Data 枚举——Data::Struct、Data::Enum、Data::Union 三个分支。绝大多数 trait 派生只处理结构体分支，其余分支要么显式报错，要么按语义支持。

属性解析：容器、字段、变体三个层级

派生宏的表达能力很大程度上来自自定义属性。#[derive(Foo)] 只开了入口，真正让每个字段行为可配置的是伴随属性，比如 #[foo(rename = "user_id", skip)]。这些属性按挂载位置分三个层级：容器级挂在类型本身、字段级挂在结构体字段上、变体级挂在枚举 variant 上。三个层级的解析逻辑要分开建模，因为合法键名集合通常不同——容器级接受 crate = "path"，字段级接受 skip，混用就是错误。

属性在语法树里是 syn::Attribute，解析它的规范做法是使用 syn 提供的属性解析接口（以当前版本官方文档为准），而不是从令牌的原始文本里做字符串匹配。成熟的写法是先按路径首段匹配自己的助记符（本例是 foo），再把括号内的令牌交给解析器处理成键值对或标志位。syn 的 meta 相关类型（如 ParseNestedMeta 一类的迭代器接口）允许逐个取出 name = value、裸 name 和嵌套 (...)，并保留每个位置的 span——这直接决定下一节的错误质量。

这里最要紧的是 else 分支：未知属性名必须报错，绝不能静默忽略。静默忽略让拼写错误变成沉默的默认行为——用户把 rename 写成 renmae，编译通过但改名没生效，这类 bug 往往到线上输出对不上时才暴露。报错则让同一个错误在编译期带着精确的 span 指回那个词。另外，#[proc_macro_derive(Foo, attributes(foo))] 的 attributes 参数声明了本宏认领的属性名，未注册的属性会被编译器直接拒绝，你不需要也不应该去猜别人的属性。

错误信息质量

派生宏和用户之间唯一的沟通渠道就是编译错误。宏内部 unwrap 一个 syn::Error，或者对解析失败直接 panic!，用户看到的是一段与自己的代码毫无关系的内部回溯；用 to_compile_error() 把错误落到调用点，用户看到的是带波浪线的正常编译错误。质量差距就在这两者之间。

syn::Error::new_spanned 接受任何实现了 ToTokens 的语法树节点，把错误锚定到那个节点对应的源码位置。给字段报错就传字段的 Ident，给属性键报错就用解析接口提供的 meta.error(...)，它天然带着那个键的 span。错误文案本身也有讲究：说清楚”哪里不合法、为什么、可以怎么办”，比一句”解析失败”有用得多。

另一个决定性的设计是错误聚合。解析阶段可能同时发现多处问题：两个字段写了未知属性名、一个字段把 rename 的值写成了整数。如果实现是”遇到第一个错误就 unwrap“，用户每修一处就要重新编译一次。规范做法是让每个解析函数返回 syn::Result，在驱动层用 syn 提供的错误合并接口（以官方文档为准）把多个错误合并成一个，最后一次性 to_compile_error()。两种写法的编译输出对照如下：

生成代码的可调试性

派生宏最让新手不适的点是：展开出来的实现不在源码里，调试器停不进去。解决这个问题有三个方向。

第一是展开工具。cargo expand（以该工具当前文档为准）会把宏展开后的代码写成可阅读的形式，按包与模块过滤可只看关心的部分。展开结果不是合法的原始源码——宏卫生信息会丢失、名字会被重排——但它是理解”宏到底生成了什么”的最快途径，排查”生成的 impl 为什么没被解析到””路径引用为什么错”这类问题，先 expand 再决策。

第二是给编译器留标记。派生宏生成的实现应当带上 #[automatically_derived]，它不影响语义，但让 rustdoc 和后续工具能把”派生实现”与”手写实现”区分开。命名上保持可预测的规律：为字段生成的中间变量就叫 __字段名_value 一类的前缀形态，用户 expand 之后一眼能对上原文。

第三是生成结构可读的实现体。与其拼一个巨大的嵌套表达式，不如生成若干小而直的函数体，每个字段一条语句：

宏卫生与路径引用

宏展开发生在用户的模块树里，生成代码看到的是用户的名字空间。用户可以在自己的模块里定义 struct Vec、写 use core as std;、或一个恰好叫 format 的本地宏——生成代码如果裸写 Vec、format!、std::vec::Vec，就全部可能被劫持。规则只有一条：引用标准库和依赖 crate 一律写绝对全路径，::core::fmt、::std::vec::Vec、::foo::Foo，开头的 :: 从 crate 根解析，绕开局部作用域的名字遮蔽。

quote! 基于 proc-macro2 的 hygiene 机制会为生成的标识符打上语法上下文标记，用户作用域里的同名变量一般不会与宏引入的变量冲突。但 hygiene 有边界：通过 quote_spanned! 或从输入语法树复用的标识符（字段名、类型名）会带着原始 span 进入输出，解析行为跟随原代码作用域；trait 方法名必须与声明一致，卫生更帮不上忙。实践中仍给中间变量加 __ 前缀（如 __logline_parts）以降低撞名与人眼混淆，但这只是降低风险，真正可靠的仍是两条：路径写全，名字不复用用户的。

枚举、嵌套形状与泛型

很多 trait 的派生在枚举上要么不支持、要么必须自定义语义：Clone 能派生是因为每个 variant 的克隆规则机械明确，而”把字段拼成一行日志”在枚举上就要回答”variant 名要不要输出、匿名字段标签从哪来”这类设计问题。没有清晰语义时，宁可在枚举分支返回明确的 syn::Error。处理匿名结构体字段与嵌套元组的思路是递归下降：具名形状用字段名做标签，Fields::Unnamed 用索引生成 field_0 式占位标签，单元形状直接跳过，三种形状共用一个”标签加值的序列”中间表示。

泛型是派生宏最经典的坑。impl_generics、ty_generics、where_clause 三段必须从 input.generics.split_for_impl() 拆出来各用各位：impl 关键字后跟 impl_generics，类型名后跟 ty_generics，条件约束沿用原 where_clause。第二个坑是 bound 的推导：语法树里的泛型参数带着用户写的约束，但生成实现常常需要”每个类型参数都满足被派生的 trait”这种附加条件。手写形态大致是这样：

测试与工程约束

派生宏的测试分三层。纯解析逻辑（属性字符串进、配置结构体出）可写成普通单元测试，用 syn 的解析入口直接喂源码片段文本。生成结果的正确性靠正常编译的集成测试：真的 derive 一次、断言方法输出。错误信息的质量则要靠编译失败类测试——方向是用 trybuild 一类的工具，把故意写坏的用户代码（错误属性名、不支持的类型形状）放进独立目录，连同编译器输出快照一起纳入版本控制，每次改动宏实现就重跑比对。这是唯一能防住”重构时把 span 弄丢、报错变模糊”这种退化的机制。与《Rust 宏实现 ORM》的分工是：那篇展示宏搭 DSL 的应用面，本节只谈实现宏自身要背的工程账。

两条硬约束必须记牢。其一，派生宏里不能有 IO 和全局可变状态：宏运行在编译器的请求处理路径上，可能跨 crate 并行执行、结果被缓存复用，读文件、发网络请求、依赖环境变量都会破坏构建的确定性与可复现性；需要外部配置时应改用属性显式传入。其二，派生宏会放大编译耗时：每个使用它的类型都要走一遍”令牌进、解析、令牌出”，宏 crate 本身还必须早于依赖它的代码完成编译，容易形成串行的构建瓶颈。所以解析路径上的克隆、大字符串拼接、重复的属性扫描都值得省，但省的方式应是数据结构层面的，而不是牺牲错误质量换速度。

手段对照总表

小结

派生宏的实现工程可以压缩成几句话：接受它”只能加实现、不能改类型”的边界；用双 crate 结构把宏与门面分开；沿 DeriveInput 到 Data 再到字段的流水线解析语法树；属性按容器、字段、变体分层解析且未知名必报错；用 span 化错误与聚合上报替用户省下几轮编译；用全路径、__ 前缀和展开工具守住卫生与可调试性；泛型三段拆开、约束从字段类型推出；最后用编译失败测试把错误质量钉死在版本控制里。至于 serde 这个库本身怎么用、thiserror 与 anyhow 各自的定位，是另两篇文章的主题。把这份清单执行到位，你的宏就与”能跑的原型”拉开了生产级的距离。
