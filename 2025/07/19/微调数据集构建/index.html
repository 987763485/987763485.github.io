微调数据集构建

本文要解决的问题很具体：怎样把散落在工单、对话日志、内部文档里的原始信息，变成一批能稳定改变模型行为、又全程可追溯、可回滚的微调数据集。适合正在准备第一份自建指令数据，或已经被”数据很脏、分数虚高、线上出问题时查不回是哪一条样本”困扰的读者。读完你应该能搭出一条带硬门禁的数据流水线。先划清边界：训练方法、损失与超参本身不在本文范围，那是《大模型微调实践》与《LoRA》的主题，本文只谈数据这一侧。

一、先把目标定清楚：数据集为”行为改变”服务

微调数据集不是”越多越好的资料堆”，而是一份用来改变模型行为的配方。动手收集之前，先回答一个判定问题：你希望模型发生的改变属于哪一种——是改风格（语气、称谓、排版习惯），改格式（固定输出结构、字段顺序、停止方式），改任务能力（分类、抽取、改写、多步推理），还是改知识范围（让它知道某些新事实）？

这里必须先画一条线：知识和事实类的需求，绝大多数应该走检索（retrieval），而不是塞进权重。把”某个产品参数是多少””某条规章原文长什么样”写进训练集，模型学到的是一个脆弱且会过期的记忆，既容易被同族问题带偏，又无法随原文更新而自动更新。正确的分工是把事实放进可更新的知识库、由检索在推理时提供，微调只负责”怎么用这些事实、以什么格式和语气去用”。知识入库这条工程线归《本地知识库问答系统实践》，本文不展开。

目标一旦确定，数据集的形态就被倒推出来。改风格，需要的是同一类任务下”改前 / 改后”的成对样本，靠对比把差异放大；改格式，需要字段完备、角色标签一致的严格结构化样本，格式契约比样本数量更重要；改任务能力，需要覆盖输入分布各段的题目与答案，并且要留一批边界样本；至于改知识范围，多半意味着你真正需要的是检索而不是微调。目标含糊，后面所有环节都会摇摆：清洗标准无从判断、标注规范写不出正例反例、配比没有依据、评估集不知道该测什么。

因此本文建议的第一步不是”抓数据”，而是写一页纸的目标声明，把上面四选一（或哪几个的组合）连同”我们明确不通过微调解决的部分”写下来。这页纸会成为后续所有门禁的裁决依据：当某条样本”看起来能用但不确定该不该用”时，回到这页纸问它服务的是哪一类行为改变，答案立判。

二、来源与授权：先问能不能用，再问好不好用

五类来源各有授权与合规风险。逐条落库前，对每条样本至少问四个问题：数据主体是否同意把它用于训练、供应商或平台的当期条款是否允许抓取与再分发、这段内容的许可证是什么、一旦主体撤回或条款变化我们能否把它从数据集里干净地移除。对”能不能用”的判断，本文一律只写”核对当期条款”，绝不引用具体条款编号、法条解释或罚则——这些随版本变化，交由法务与合规同事按当期文本确认。

  • 自有工单与对话日志：主体是客户或员工，通常默认并没有”用于模型训练”的同意。风险在同意范围与可撤回；落地做法是把”用途”写进采集时的告知，并把撤回通道与样本级 ID 打通。已施行的《个人信息保护法》《数据安全法》与 2025 年 1 月 1 日起施行的《网络数据安全管理条例》要求对个人信息处理有明确依据，具体条款以当期文本为准。
  • 内部文档：授权相对清晰，风险在权限边界——一份跨部门文档可能含当前标注者无权限可见的内容，落库前要按访问域过滤，越权内容不得进入数据集。
  • 公开语料：许可证五花八门，逐条核对数据卡的许可字段，不臆测某个模型或数据集”大概可以商用”；许可为”未知”即视同不可用。
  • 教师模型生成：用 DeepSeek-R1（其公开的推理数据路线把”先造数据再蒸馏”讲得很直白）、GPT-4.1、o3 / o4-mini、Claude Opus 4 / Sonnet 4 这类当期可得的模型产出候选样本。此处先划界：teacher 造数据的方法论归《模型蒸馏与知识迁移》，本文只关心这类来源的授权与治理——上游模型的服务条款常对”用其输出去训练竞品”有约定，须核对当期条款；合成样本没有任何真实主体的同意，用于生产前要单独评估其事实性与偏见。
  • 众包标注：授权链条经由标注方，须确认标注者对产出内容的权利已转让给委托方，且任务说明里没有夹带真实个人信息。

三、脱敏与最小必要：入库前必须做完的处理

脱敏不是”给评估打个码”，而是决定这份数据能不能安全进入训练域的前提。本节列的都是入库前的必做处理，做完才算通过门禁，没做完就是阻断，而不是”记个警告继续跑”。

第一，身份字段要么替换要么丢弃。姓名、手机号、邮箱、证件号、住址、卡号这类直接标识符，凡是不承载任务语义的，一律丢弃；承载语义又必须保留结构的，用可逆性极低的占位符替换（例如把具体号码换成 <<PHONE_1>> 这种带序号的稳定令牌，同一篇文档内同号同令牌，方便保留指代关系）。要点是替换后的令牌不可从训练样本反查回原值，映射表单独存放、单独授权。

第二，自由文本里的标识符要做识别与替换。工单正文、对话口语里会散落手机号、邮箱、身份证号、地址、银行卡号，光靠”字段名是 phone”是不够的，必须对文本本身做模式识别再替换。这里要特别警惕”打码后仍可反查”的伪脱敏：只保留前几位、或者用一个可预测的偏移量替换，攻击者或内部越权者能靠上下文复原——这种做法视同没脱敏。

第三，原始样本与训练样本分域存储并限制访问。原始日志（含明文标识符）放在一个高权限域，训练域只存放脱敏后的产物，两者物理或权限隔离，训练流水线只允许读训练域。这样即便训练集被内部误用，也不至于把带明文的原始库一起暴露。

第四，留存期与删除流程。给每个域写明确切留存期（示意值，具体按你的合规口径定），到期自动清理；当主体撤回同意时，凭样本级 ID 在两个域里定位并删除，删除动作本身要有审计记录，重训计划里要能说明”受影响数据集版本将被废弃”。

四、清洗：把”能训”和”该训”分开

清洗解决的是质量，不是合规。目标是让留下的样本真正代表你想要的行为，而不是把噪声也学进去。

结构化噪声最常见：模板残留（邮件签名、工单固定话术）、HTML 或 Markdown 表格被拆碎后的残屑、复制粘贴带进来的界面文本（按钮名、菜单路径、”点击这里”）、以及系统提示泄漏——线上对话里那句”你是某某助手，请遵循以下规则……”如果原样进入训练集，模型会学到”输出应当以系统口吻开头”这种坏行为。系统提示作为资产本身有它的管理线（归《提示词管理 / 版本化》），本文只处理它在数据里的清除，不展开。

语言混排与编码要统一：同一批里中英混排、全半角混排、繁简混排会让格式契约变得含糊；先确定目标语言分布，把不合语言的样本要么剔除要么单独归档。编码问题（乱码、私有区字符、零宽字符、异常控制字符）要在归一化阶段清掉。

长度异常要设上下限：超长样本多半是把整篇文档误当回复，超短样本多半是没信息。注意这两个阈值是”团队约定示例”，应按你自己数据的分布来定（先统计长度分位，再决定切点），不要照搬别处的数字。

重复与近重复是本节的重点，要分两层处理。文档级去重针对整篇来源（同一份 FAQ、同一篇公告被反复切进来），避免某来源在训练集里被隐性上采样；片段级去重针对样本内的近似段落，去掉模板化的相似句。两层缺一不可：只做片段级会漏掉”同一文档的不同片段”，只做文档级会漏掉”跨文档抄同一段”。去重对评测泄漏同样关键——训练集与评估集之间的近重复，本质就是泄漏（详见第九节）。判断”近似”用什么口径（如按归一化后的 shingle、或按语义向量距离加阈值）应由你自己选定并记录在配方里，本文不规定阈值。

低质量判定信号列几条可直接机检的：长度超出约定区间、非汉字 / 非目标字符占比异常（大量乱码或标点堆叠）、自我循环引用（输入与输出几乎互为改写、没有新增信息）、无信息回答（”好的””收到””无法回答”这类既不推进任务又不承担拒答语义的空样本）。这些信号命中的样本，要么剔除，要么进入待复核队列，不能带着标记直接进训练。

五、标注规范怎么写才不空

标注规范最容易写成”要准确、要自然、要符合业务”这类正确的废话。一份能落地的规范，至少要有六块内容，缺一不可。

第一，任务定义。用一段话说清”给什么输入、期望模型产出什么、这个能力上线后用在哪个场景”，把范围边界写出来（哪些不在这个任务里）。

第二，输入输出契约。明确输入字段的含义、输出必须满足的结构与约束，与第七节的格式契约对齐：如果输出要是 JSON，规范里就写清键名、类型、必填项与”缺失时填什么”。

第三，正例与反例的描述。注意这里要写的是对样例的描述与判定要点，而不是可直接复制进数据集的真实敏感样例。例如”正例：用户问退款进度，回复应给出所需凭证而不承诺具体到账时间；反例：回复里出现真实订单号或承诺了未经授权的补偿”。描述足以让人判断，又不泄漏隐私。

第四，拒答与”不确定”的正确处理。什么情况下模型应当拒答、什么情况下应当表达不确定、拒答时的措辞边界是什么，这三件事要分开写清楚。把”不确定”和”拒答”混为一谈，会让模型学会一律推诿或一律硬答两种坏行为。

第五，边界案例裁定流程与仲裁。规范一定覆盖不全，遇到新边界的样本时，标注者上报、由谁裁定、裁定结论如何回写规范，要有明确流程与仲裁人，避免各标各的。

第六，”谁有权改规范”。规范是活文档，必须写死修改权限与生效方式：谁可以提修订、谁批准、批准后从哪个版本起对哪些样本生效。

最后，把规范当成可测试的对象。检验标准很直接：把规范交给一位新人，让他只读规范去标一批已定标的样本，看他的结论与团队既定结论的符合程度。如果新人只看规范标不对，那是规范有洞，不是新人不行——回到规范补条款，而不是口头纠正个人。这份”新人可独立复现判定”的能力，是衡量规范写得好不好的唯一硬尺子。

六、一致性检验：分歧是规范的漏洞，不是投票的素材

有规范不等于有一致结果。要检验规范是否真的可执行，办法是让多位标注者对同一批样本独立标注，互不可见，再比对结论。

比看总一致率更有用的是按类别拆开看：某些高频类别一致得很好，而边界类别、拒答类、多解类往往一致率塌陷。先定位到底是哪一类在崩，再去修那一类的条款。具体的一致率怎么算、用什么指标（是按简单比例还是做机会校正），口径要写进配方并全程统一，本文不给任何示意百分比——你的数值应由你自己的样本与标注者算出，别人给的百分比对你毫无意义。

最关键的是分歧样本怎么处理。错误做法是”投票取多数”：多数把少数压下去，规范里那个真正的模糊点被藏住了，下一批同样分歧还会再来。正确做法是把每一条分歧当成规范缺陷的信号，回到规范里补一条能裁定该情形的条款，必要时用仲裁流程定标，然后把受影响批次按新条款重标。这样一致性是靠补规范爬上去的，而不是靠投票掩盖出来的。

规范迭代必须有版本记录。每份标注产物都要能回答”我是按规范第几版标的”。一旦规范升版，旧版标的样本要么显式标记为旧版、要么按新版重标，绝不能把两版结论混进同一批却不加区分——这正是第十二节要复盘的”前后混标”事故。版本记录与样本级 ID 配合，才能让一次规范修订追溯到它改动了哪些样本、又重训成哪个数据集版本。

一致性检验还有一层现实约束：它必须在切分之前做。若一批样本一致性极差、需要回炉重标，就不要让其中任何一条过早流进评估集，否则你在用一批自己都判定不稳的样本去当尺子量模型。

七、格式契约：让每一次停止都是被规定的

样本结构大致三种，各有取舍。纯指令式（一条输入对应一条输出）最简单，适合改风格、改单轮任务，代价是学不到多步与工具行为；对话式（多轮 user / assistant 交替）更贴近真实交互，能教会模型承接上下文，代价是轮次边界和”什么时候该停”必须严格一致；带工具调用的多轮样本（模型先发起调用、拿到结果再继续）能训练最复杂的行为，但字段结构最重、也最容易在格式上出错，2025 年 3 月修订的 MCP 规范让工具调用的结构有了公开的参考骨架，可以借它的思路，但字段名要用你自己的契约、别照搬。

无论选哪种，字段命名与角色标签必须全局一致。同一个含义不要一处叫 user 另一处叫 customer，同一个”期望回复”不要一处放 response 一处放 answer。角色标签错位（该是 assistant 的轮次标成了 user）会让模型学到颠倒的说话人归属。

为什么格式不统一后果那么重：模型极其敏感于”输出到哪里算结束”这件事。如果一批样本里，有的回复末尾带句号、有的带特殊标记、有的靠换行结束、有的被截断，模型不会认为”这些都不重要”，它会从统计里提炼出一个隐式的停止条件——于是线上表现为莫名提前结束、或该停不停、或在没有约定标记的位置乱加结束符。停止条件本应是你规定的，却因为数据格式漂移被模型自己”猜”了出来。

因此格式校验要做成流水线里的硬门禁，而不是事后建议。两道：先做 schema 校验——每条样本必须能通过结构校验（必填键、类型、角色序列合法、结束标记符合约定），不通过即整批阻断；再做抽样人工复核——按配方从通过 schema 的样本里抽一小部分人看，专门盯 schema 抓不到的语义级格式问题（如把整段文档塞进答案字段）。抽样比例是团队约定示例，按你的风险容忍定。

八、配比与难度分布：一次只动一个轴

数据配比是行为配方的核心旋钮。至少要沿四个轴分别看分布：任务维度（分类 / 抽取 / 改写 / 推理各占多少）、难度维度（简单、中等、难，以及边界情形）、长度维度（短输入长输出、长上下文压缩等各段是否覆盖）、以及拒答与”我不确定”样本的比例。最后这一项尤其要主动控制：真实业务里”该拒答”和”该表达不确定”的场景占比往往被工程师低估，如果训练集里这类样本太少，模型上线就会过度自信；反之太多，又会变得事事推诿。目标比例是团队约定示例，应从线上真实分布反推，而不是拍一个数。

上采样是把双刃剑。想强化某种风格，把该风格样本上采样，行为确实会变——这正是微调想要的。但代价是泛化：模型会把这个被上采样的模式当成”通用正确姿势”，在风格之外的任务上退化，比如为了礼貌语气而上采样客套样本，结果抽取类任务也开始先寒暄再答题。上采样改变的是分布的重心，重心偏移会溢出到你不希望它影响的任务上。

坏样本的杀伤力远大于它的数量。歧义题（同一输入可有多种合理理解、答案却只咬定一种）教模型在模糊处乱猜；错误答案（标注本身是错的）直接把坏习惯写进权重，且一条就够毒；多解但只给一解的题，教模型把”恰好这一个”当成唯一正确，遇到其它合法解时失配。这三类样本在配比里不是”占比小就无所谓”，它们会不成比例地影响模型在对应区间的行为，所以要在清洗与一致性两节就尽量拦下。

配比调整的铁律：一次只动一个轴，并能归因。如果你同时改了任务配比、又改了风格上采样、还换了基座模型，那么效果变化你无法归到任何一处，下一次调整只能靠运气。正确做法是固定其它轴、只动一个，配一份同口径评估集（见第九节）测前后差异，把”这次动了什么、带来什么变化”写进版本记录（见第十节），让配比成为可解释、可回滚的实验序列，而不是玄学调参。

九、评估集切分与泄漏检测：分数虚高的根子在这里

这一节决定你的评估分数可不可信。先说结论：评估集不能和训练集来自同一批标注、同一时段、同一来源。若两者同源，模型在训练时见过的近似模式会在评估时被”认出来”，测的是记忆而不是泛化，分数虚高且无法解释线上表现。

切分单位必须是文档 / 会话 / 用户，而不是样本行。按行随机切分是新手最常见的致命错误：同一篇 FAQ 被切成多条近似样本、同一通对话的相邻轮次、同一个用户的相似提问，会被随机分到训练侧和评估侧两边。模型在训练侧见过 A 的近亲，评估侧再问 A，它当然答得好——这叫泄漏。正确做法是先按”来源实体”分组（一份文档、一通会话、一个用户归为一组），整组要么进训练要么进评估，绝不拆组跨侧。

在此之上还要做近重复检测。即便分了组，跨来源仍可能有近似样本（不同人抄了同一段模板）。思路是对两侧样本做归一化（去标点、统一空白、必要时统一大小写），用重叠片段集合或语义向量比对，把与评估侧高度相似的训练侧样本揪出来——剔除或移入评估侧，并把这个检测写进切分流程本身。检测口径与阈值记进配方，由你自己的数据定，本文不规定数字。

时间切分是另一条防线：未来数据不进训练。凡采集时间晚于评估基准时点的样本，只能进评估或留待下一版，不能进训练，否则模型用”未来才知道的信息”回答”过去时点该知道的问题”，线上必然对不上。对有时效的业务（价格、政策、库存），时间切分比随机切分更能反映真实表现。

值得专门构造一个小而准的评估集，来自业务真实分布：按线上流量的任务占比、难度占比、拒答场景占比抽样，人工复核到”你信它当尺子”。它不必大，但要覆盖你最怕出错的那几类。检索增强那一侧的检索质量评测归《RAG 检索质量评估》，本文只负责把微调评估集的切分与防泄漏做到位，两者是不同尺子、各测各的。

十、版本化与可追溯：每个数都能追回一条样本

数据集不是”一个文件夹”，而是”一系列不可变版本”。版本命名要能读出来龙去脉，建议形如 ds-<基座>-<日期>-v<序号>-<一句改动摘要>，每次冻结生成新版本、绝不就地覆盖旧版本。命名里带基座，是因为同一批数据在不同基座上行为不同——当期可选的公开基座如 Qwen2.5、Qwen3、Llama 3.x / Llama 4、DeepSeek-V3-0324 等；对刚发布、尚未在生产验证的（如 o3-pro 一类），要在记录里如实标注”未验证”，不当既成事实用。

每次训练记录一个四元组：数据集版本 + 配方 + 基座模型版本 + 评测结果。配方就是第八节说的配比与清洗口径的快照（各轴比例、去重阈值、上采样规则、schema 版本）；评测结果是第九节那把尺子上的数字。四元组齐了，任何一次效果变化你都能回答”是哪一版数据、哪份配方、哪个基座、测出了什么”，而不是事后无从对证。

样本级 ID 要贯穿到线上问题回溯。线上模型答错了一条，你要能：定位是哪个训练样本（或哪一类）把它带偏的 → 在版本记录里找到含该样本的数据集版本 → 判断是”样本本身坏”（回清洗 / 标注）还是”配比或格式问题”（回配方）。ID 追不回去，你只能重训碰运气；ID 追得回，才能精准地把坏样本从下一版里剔除并只重跑受影响的阶段。

数据变更走评审与回滚。任何影响训练分布的改动（新增来源、调整脱敏规则、修订标注规范、改配比）都应作为一次带记录的变更：说明动机、影响面、由谁批准；一旦新版本评估退化，能按版本记录干净地回滚到上一个可信版本，并把”为什么回退”写进账。版本化把数据工程从”改文件”升级成”可审计的实验管理”。

十一、流水线工程：把前面十节串成带门禁的机器

前面每一节都是一道门禁，流水线要做的就是把它们连成”失败即阻断、而不是警告”的机器。从原始数据到可训数据集的阶段图如下：

flowchart TD
  A[来源接入] --> B[授权台账校验]
  B --> C[脱敏与最小必要]
  C --> D[清洗与两层去重]
  D --> E[标注与一致性检验]
  E --> F[格式契约与schema校验]
  F --> G[配比与难度分布]
  G --> H[切分与泄漏检测]
  H --> I[版本冻结]
  I --> J[交付训练]
  B -.未过.-> X[阻断并要求回查]
  C -.未过.-> X
  F -.未过.-> X
  H -.未过.-> X

每个阶段都有明确的产出门禁，过不了就不许进下一阶段：授权台账齐全（每条样本 review_status 为 approved、许可非未知、同意含 train）；脱敏校验通过（白名单字段、无任何密钥 / 堆转储 / 用户原文残留、标识符全部替换或丢弃）；清洗完成（结构化噪声、语言与编码、长度、低质量信号处理完）；两层去重完成；格式校验通过（schema 全绿、抽样人工复核无系统性问题）；切分完成（无跨组、无近重复、无未来数据）。

这里要强调”阻断而不是警告”。流水线最常见的溃败是：脱敏脚本对某条样本没把握，于是”打个 warning 继续跑”，那条样本就混进了训练域；schema 校验把不合规的样本”跳过”，跳过日志没人看，最后数据集里就有一小撮畸形样本教模型学出隐式停止条件。硬门禁的写法是：任一阶段有未清除的失败项，整个批次停止、不产出、不进入版本冻结，逼着人去回查而不是绕过。

工具形态按团队规模选，不必一步到位。小团队用”脚本 + 任务编排”就够：每个阶段一个可独立重跑的脚本，用编排器（make 风格或轻量 DAG）串起来，门禁以退出码表示（非零即阻断），产物落盘带版本目录。规模化以后再考虑平台化（数据版本、血缘、审计做成服务）。无论哪种，都不要在文档里写死某个具体工具的版本号——本文明确不规定 PyTorch、Transformers、peft、trl 等的小版本，工具选型的重点是门禁语义清晰、阶段可重跑、产物可追溯。

十二、常见失败模式复盘：症状、根因、防线

下面四个是反复出现的事故，按”症状 → 根因 → 防线”复盘，不点名任何真实事件，只讲机制。

一，直接把线上日志转成训练集。症状：模型上线后开始复读客服系统的固定话术、把”点击下方按钮””提交工单编号 XXX”当自己该说的话，甚至冒出别的客户的姓名或单号；排查还发现输出里带系统提示。根因：线上原始日志含模板残留、界面文本、系统提示和明文标识符，未脱敏未清洗就直接投喂。防线：来源必须过授权台账与脱敏门禁（第二、三节）、清洗必须处理模板泄漏与系统提示残留（第四节），日志到训练集之间隔着一整条流水线，而不是一个复制粘贴。

二，评估集与训练集同源。症状：离线分数很高、每次改动都”涨点”，一上线就掉链子，且分数无法解释线上表现。根因：按行随机切分、同一文档 / 会话 / 用户的近亲样本分处两侧，评估测的是记忆；合成样本没标来源、也没做时间切分。防线：切分以文档 / 会话 / 用户为组、整组不跨侧，加近重复检测与时间切分，泄漏报告非空即阻断（第九节）。

三，标注规范中途改了却没重标。症状：模型在同类任务上表现忽好忽坏、输出风格前后不一，一致性指标也说不清到底按哪版规范算的。根因：规范升版后旧样本按旧标准标、新样本按新标准标，两版结论混进同一批却不加区分。防线：规范版本写进每条样本、升版即触发受影响批次重标、混标批次不得进版本冻结（第五、六、十节）。

四，上采样某种风格导致风格外任务退化。症状：目标风格的任务确实变好了，但抽取、分类等其它任务明显变差，模型开始”先客套再干活”。根因：只盯着”让某风格更突出”，把该风格样本大幅上采样，重心偏移溢出到别的任务；而且同时动了多个配比轴，无法归因。防线：配比一次只动一个轴、配同口径评估集做前后对照、对退化任务设最低护栏指标（第八节）。

小结

本文把微调数据集的构建拆成一条有硬门禁的流水线：先定清楚要改变的是风格、格式、任务能力还是知识范围，并坚决把事实类需求交给检索而不是塞进权重；随后依次过来源与授权、脱敏与最小必要、清洗与两层去重、标注规范、一致性检验、格式契约、配比与难度、切分与防泄漏、版本化九道关，最后以”失败即阻断”的姿态交付训练。训练方法与超参不在本文范围，那是《大模型微调实践》与《LoRA》的主题；本文只把数据这一侧讲透。

三个反复出现的主线值得再强调。第一，隐私与授权是前提不是补救：任何密钥、堆转储、用户原文不得进入数据集或缓存键，伪脱敏等于没脱敏，撤回通道要靠样本级 ID 打通。第二，可信的分数来自可信的切分：按文档 / 会话 / 用户整组切、做近重复检测、用时间切分挡住未来数据，泄漏报告非空就不许冻结——否则一切涨点都是自欺。第三，质量靠规范与一致性爬上去：把规范当成”新人可独立复现判定”的可测试对象，把每一条分歧当成规范的漏洞去补条款，而不是靠投票掩盖。

落地建议是渐进的：不必一上来就平台化，先用”脚本 + 编排 + 退出码当门禁”把阶段跑通，把每一次训练的四元组（数据集版本 + 配方 + 基座版本 + 评测结果）记全，让配比一次只动一个轴、可归因、可回滚。数字（条数、比例、阈值、一致率）一律由你自己的数据与团队约定统计得出，本文刻意不给任何示意值——因为别人的百分比对你毫无意义，你要学会的是”自己怎么统计这些量”的口径。合规口径也请按当期文本核对，本文只标名称与生效时点、绝不解释条款或引用编号。
