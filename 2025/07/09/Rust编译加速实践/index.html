Rust 编译加速实践

本文属于《Rust 学习路线》第 55/68 篇
上一篇系列目录下一篇

本文面向被 Rust 编译时间拖慢节奏的后端开发者与基础库维护者，讨论的不是“某个开关一开就快多少”，而是一套可复用的归因方法：先把编译拆成可测量的阶段，再让每一类手段去对应它真正改善的阶段，最后用你自己的机器和仓库把收益量级测出来。读完你应该能回答三个问题：慢在哪一段、这段该用什么手段、换手段之后如何验证有效。

慢在哪一段：先把体感拆成可归因的四段

“编译慢”是一个体感，不是一个诊断。rustc（Rust 编译器）把一份源码变成可执行产物，中间经过几段性质完全不同的工作，每段慢的原因不同，能用的手段也不同。

第一段是前端（frontend），负责把文本变成类型良好的中间表示。它包含解析（parsing）、宏展开（macro expansion）、类型检查与借用检查（type check 与 borrow check）。解析基本跟代码行数成正比，不容易成为问题；真正容易拖慢这一段的是宏——过程宏（proc macro）要在编译期运行一段 Rust 代码，声明宏的展开会成倍放大后续要处理的语法树；类型检查与借用检查的代价则与函数体复杂度、泛型约束的深浅、生命周期推理的数量相关，而不是简单的行数。凡是“改了一处却看到大量 crate 重新做类型检查”的现象，几乎都在这一段。

第二段是中端（middle-end），主要工作是把泛型代码变成具体代码，也就是单态化（monomorphization），并做与目标机器无关的优化、把任务切成 codegen 单元（codegen unit）。单态化的机制是：同一个泛型函数会为每个实际用到的具体类型生成一份独立代码，调用点多、类型参数组合多时，这里的产物数量会明显膨胀。codegen 单元的划分方式决定了后端有多少可以并行的工作，也决定了单个单元有多大。

第三段是后端（back-end），即 LLVM 的优化管线与机器码生成（machine code generation）。它的工作量与“要生成的函数体积与数量”成正比，对优化档位（opt-level）、调试信息档位（debug information level）、跨 crate 内联的可用性都敏感。这是典型的 CPU 与内存密集型阶段。

第四段是链接与产物处理（linking 与 artifact handling）。链接要在一处汇集所有目标文件的符号表、做重定位、合并调试信息，往往是整个流程里并行度最低、内存占用最尖峰的一环；产物处理还包括二进制体积相关的工作与后续打包。

除了这四段“纵切”，还有一条“横切”的维度值得单独讲：依赖图（crate graph）上的重复劳动。Cargo 按依赖拓扑顺序构建，上游 crate 没产出元数据（metadata）之前下游无法开始，因此端到端时间不等于总工作量，而更接近一条最长关键路径（critical path）。更麻烦的是重复劳动：每次某个上游 crate 的指纹（fingerprint）发生变化，所有依赖它的下游都要重新做前端检查、重新单态化、重新生成代码，哪怕你只改了上游一行注释以外的东西。一个内部大 crate 处在依赖图中游位置时，它的改动会把整片下游一起拖下水。这也是本文反复强调“看最慢的那条链，而不是看总耗时”的原因。

先测量：把“感觉慢”变成可比较的数据

顺序很重要：先会测，再谈改。没有测量就调参，等于把编译器当黑盒抽奖。

第一步拿分阶段与分 crate 的数据。构建工具侧最直观的是带计时与可视化的产物输出：把一次构建的时间按 crate 摊开，你就能看到“时间被少数几个 crate 吃掉”还是“被一条长链吃掉”；cargo build --timings 会生成一份 HTML 报告，横轴是时间、每行是一个 crate、依赖边标出谁在等谁（本文第 10 节再讲它的读法）。编译器侧还有分阶段计时（per-pass 或 per-phase 的计时输出）这类调试用途的选项，用来看单 crate 内部的时间落在前端、中端还是后端；这类选项的名称与可用性跟工具链渠道相关，本文不逐一罗列精确拼写，只提醒读者：这类输出是给自己看的诊断，不适合放进 CI 的门禁。

第二步分场景计时。三种场景的答案互不通用：冷编译（clean 之后从零开始，反映 CI 与新人首次构建）、热增量（改一个文件后的重建，反映日常开发手感）、CI 全新（带缓存与并发的构建，反映流水线）。三个场景各设一个可重复的动作，例如“改一个内部实现文件”“改一个公共类型签名”“改一个宏”，分别记录三场景下的等待，你会得到一张按场景与按改动类型交叉的表，而不是一个笼统的均值。

第三步控制变量。同一份代码（固定在某个提交上）、clean 后再测冷编译；同一块磁盘（网络盘与本地盘的差别足以掩盖所有优化）；同一并发档位；同一工具链版本；关掉编辑器后台检查再测终端构建，或者反过来。测量时至少跑两次取第二次，把第一次当作磁盘缓存与预热成本。

增量编译的真实边界

增量编译（incremental compilation）是收益最直接的手段，也是最容易被误解的一个。它的前提是“构建产物能复用上一次的成果”，而复用与否由指纹决定，不由你改了多少行决定。

先说哪些改动容易引发大范围重建。改动公共 API（public API）——尤其是那些被下游直接引用的条目——会让下游的元数据视图失效；改动一个被广泛使用的类型签名，包括结构体字段、trait 的方法签名、泛型参数或约束，会让所有用到它的 crate 重新做类型检查并重新生成代码，这是范围最大的一类；改动宏定义，下游要重新展开并重新检查展开结果，等于把前端工作重做一遍；改动 feature 组合则会让所有受影响 crate 的编译选项集合变化，指纹一起变，连产物内容都可能不同。此外还有几条“隐形失效”来源：构建脚本（build script）的输出变化、环境变量进入编译命令行、依赖版本被更新（哪怕是小版本）、以及路径变化——同一份仓库换个目录 checkout，缓存过的元数据里的路径就对不上。另一类一次性打散指纹的改动是批量语法迁移，例如把整个项目从旧 edition 迁到 2024 edition（该 edition 已随当时的稳定版工具链在 2025 年初进入稳定渠道）：它同时改动大量文件的语法与预设，几乎必然带来一次全量重建，因此应当安排在专门的窗口并提前告知团队，而不是随手合进某个功能分支。

再说那个最常见的困惑：为什么我只改了一行，整个 workspace 都重编了。原因通常不在那一行，而在被改的那个 crate 的下游有多少、它是不是位于依赖图上游。Cargo 的复用单位是 crate，一个上游 crate 一旦要重新编译，它的所有下游都要重新读取新的元数据并重新走一遍检查与生成；如果你的公共类型恰好住在一个“人人依赖”的基础 crate 里，一行改动就等于全工程重做。另一个常见原因是 target 目录（构建产物目录）没被复用：不同的 target、不同的 feature 集合、不同的构建配置 profile 都会产出互不复用的结果。

分支切换（branch switching）是这个问题的现实版本。切分支时上游 crate 的指纹变了（代码内容变了、依赖解析变了、feature 变了），你感受到的“切分支必全量重编”就是这么来的。可行的缓解方式按方向排序：把频繁切换的分支放在不同的 target 目录里复用（代价是磁盘占用翻倍）、把公共 API 的改动集中在少量“边界 crate”里让破坏范围可预测、把重构做成向后兼容的追加而不是原地修改签名。这里不承诺任何具体比例，只提示一个必做的验证：切换前后各测一次热增量，看你的改动是否真的收敛了。

最后是 cargo check、cargo build、cargo clippy 三者的关系与代价方向。cargo check 只做到“类型检查与借用检查通过、元数据产出”这一层，不进入后端与链接，因此它的代价主要落在前端；它能让下游继续检查，但不能产出可运行产物，测试也跑不了。cargo build 是完整链路，四段都要走，代价最高也最接近 CI。cargo clippy 本质上是一次带 lint 引擎的检查工作，代价方向接近 check 但要多做一遍分析，且它自己的诊断有额外成本。三者产物的复用关系并不像想象的那样自由：不同工具与不同 profile 下的检查产物未必互相顶替，把它们混用来“省时间”常常换来的是反复重建。把方向记住就够：日常反馈优先用 check，需要跑测试时才 build，clippy 属于门禁与定时任务而不是每次保存都跑。

crate 拆分与依赖图：把关键路径切短

一个内部巨型 crate 是编译时间问题的常见根因：它自己很大（前端与后端都要做很多工作），又处在依赖图上游（一改就波及全工程），还阻塞并行（拆不开就只能串行等它）。把它拆成“接口薄、实现内”的小 crate 之所以能同时改善增量与并行，机制有三条。

第一是元数据视图变小。下游只依赖薄接口 crate，编译器读到的类型与签名数量少了，类型检查与单态化的搜索空间随之收敛；实现 crate 内部怎么改，只要薄接口不变，下游就不必重建。第二是并行度变高。拆开的 crate 之间如果没有依赖边，构建调度可以把它们放在同一层并发跑，关键路径从“一个大块”变成“若干小块加一条薄链”。第三是破坏范围可预测。公共 API 的变更必须显式发生在薄接口 crate 上，你在 review 时就能看到“这次改动会波及哪些下游”，而不是等到 CI 全量重编才发现。

拆得过碎同样有反作用，需要正视三件事。契约面变多：每个新 crate 边界都意味着一批 pub 条目、一套需要维护的错误类型与版本兼容承诺，接口设计的成本从“内部约定”升级为“跨 crate 承诺”。编译单元固定开销：每次进入编译都要读取上游元数据、建立 crate 上下文，边数与节点数上升后，这部分固定成本会累积，甚至抵消并行收益；依赖图碎成一串长链时，并行度反而下降，因为关键路径变长了。版本管理成本：workspace 内部 crate 可以用路径依赖统一管理，一旦有外部消费者，版本对齐与发布节奏就成了额外负担。

feature 与单态化：被组合放大与被复制放大的工作量

feature（Cargo 的条件编译开关）本身不慢，慢的是它的组合。每个 feature 集合都对应一份独立的编译结果与独立的指纹：本地开发常用一套组合，CI 矩阵里还要跑若干套，测试里又有“只在某 feature 下存在”的代码路径。矩阵里 feature 维度一加，CI 的任务数按乘积增长，而这些任务彼此还不能复用产物，等于把冷编译重复做了若干遍。治理方向不是“少测”，而是“只测真实支持的组合”：把没有消费者的组合从矩阵里删掉，把只在极端组合下才有的代码收敛进独立 crate 或独立测试作业，让组合数与真实承诺对齐。这一条会在第 9 节的 CI 裁剪里再落到操作层面。

第二个放大器是优化档位（opt-level）与调试信息档位（debug 信息的详细程度）。它们的方向性关系值得记住：优化档位越高，后端要做的分析与变换越多，单位代码的编译代价越大；调试信息越多，前端与后端要为每个定义与行号维护额外元数据，产物体积与链接工作量同时上升，时间也随之上去。反之把调试信息降到较少甚至关闭，能省下体积与链接相关的工作，代价是线上问题难以定位。这两项没有“永远最优”的取值，只有“按场景选档”：日常热增量与检查用低成本档，需要跑性能验证或产出发布物时用高成本档，CI 里把两者分开而不是所有作业共用一个昂贵的 profile。

第三个放大器是单态化，机制在第 1 节已经提过：泛型代码不为“抽象的 T”生成一次，而是为每个实际用到的具体类型各生成一份。于是一个被 40 种类型参数实例化的函数就会产生 40 份独立代码，中端要复制 40 遍、后端要生成 40 遍、链接要处理 40 份符号（这处份数是示意值，只用于说明乘积关系，不是任何实测结果）。放大效应的强度取决于调用点数量与类型参数个数的乘积，而不是泛型本身有多复杂。取舍也随之明确：当某个泛型接口只在少数几处被使用、却被塞进很多类型参数组合时，改成动态分发（用 trait 对象在运行时选择实现）可以让代码只生成一份，把编译期工作量换成一次运行时间接调用与一层装箱；收敛类型参数（把多个泛型参数合并成一个配置结构、把不必要的泛型改成具体类型）则往往更划算，因为它同时降低接口复杂度。这类取舍改变的是运行期成本与编译期成本的分配，本文只谈编译期一侧的收益，编译期计算能带来什么、抽象到底“零成本”在哪，本批另有两篇专门讨论，此处不重复。

最后要把“依赖 feature 穿透”列为需要长期盯的项目：当一个依赖 crate 的 feature 被你间接打开（多个上游各自要求不同组合，或某个默认 feature 顺带拉进一大片代码），实际参与编译的代码量可能远超你的预期，而它在依赖树里并不显眼。判断方法是把“我声明的 feature”与“实际生效的 feature 全集”分开看，前者在 manifest 里，后者要通过依赖树工具去查（见第 6 节）。至于产物体积的裁剪手段，属于另一篇的主题，本文只关心体积背后的编译工作量。

依赖本身的成本：那些不属于你的代码也要编译

第三方依赖不是免费的外部能力，它们在每一次冷编译里都要走完整链路，而且经常比你的业务代码更占时间。有两类依赖值得单独认识。

第一类是过程宏（proc macro）依赖。它的成本结构与普通 crate 不同：过程宏本质上一段在编译期被运行的程序，构建系统必须先把这个 crate 用宿主工具链完整编译成一个可加载的动态库，然后才能开始编译任何使用它的下游 crate；这意味着它在依赖图上是一个“必须先完成”的前置节点，处在关键路径的起点附近。更要紧的是现象层面的一个事实：过程宏 crate 自身通常享受不到增量优化带来的好处，改动它往往触发把它整个重新编译一遍，而它一重编，所有用了它的 crate 都要重新展开宏、重新检查展开结果。于是“动一下宏实现、全工程回到起点”在带大量派生宏（derive macro）的项目里是常态。围绕它的治理方向是把宏数量与宏展开体积当作指标来管：能用普通代码或 const 上下文表达的就不上宏；能合并的派生入口合并成一个；把宏 crate 的接口保持稳定，把实现细节关在私有模块里；避免让业务 crate 直接依赖语法树处理类基础设施 crate，那类 crate 体量不小、又几乎只为宏服务。这里只讲方向，不写任何“某版本之后如何”的断言——这类结论必须用你锁定的工具链自己验证。

第二类是体积大的通用 crate 被全工程间接引入。它的代价有四个来源：一是元数据视图变大，每个下游 crate 读到的类型与签名数量增加，前端检查更贵；二是单态化在多个下游各做一遍，同一个泛型接口在你的每个 crate 里都会实例化它实际用到的类型；三是它常常带一堆默认打开的 feature，顺地把 TLS 实现、命令行解析、异步运行时之类的子树一起拉进构建；四是链接阶段要处理更多符号。治理方向是把“谁引入了它”查清楚：依赖树工具（例如 Cargo 自带的 cargo tree）能把某个 crate 从哪个依赖的哪个 feature 间接进入你的构建说明白，配合检查未使用依赖的社区工具（例如 cargo-udeps）能找出“已经在编译却没人用”的节点。本文只写工具名与用途，不写版本，也不承诺任何一次清理的收益比例；你要做的是把清理前后的冷编译时间按第 2 节的方法各测一次，把量级差异写进自己的记录表。

一条容易漏的习惯：把依赖清单当作性能资产来 review。新增一个依赖时问三件事——它带来多少编译单元、它的默认 feature 是什么、能否用已有依赖或几十行代码替代。这三个问题在功能评审里常被忽略，但它们直接决定一年后你的 CI 有多长。

并行与链接：调度、内存与那条串行尾巴

并行度不是越高越好，方向比数值重要。构建工具的并发参数（例如并发生成任务数）应与机器的物理核数与内存容量同时匹配：每个并行任务都要占据一份内存工作集，编译器后端与链接器又都是内存大户，并发档拉高到工作集总和超过可用物理内存时，系统开始换页，磁盘与内存带宽成为瓶颈，整体等待反而变长，严重时任务被杀死还得重跑。这就是“并发档明显高于核数、内存跟不上时整体反而更慢”的机理。正确做法是把并发当作一个待测变量：在冷编译与热增量两个场景下，各测一档“接近核数”的设置与一档“明显低于核数”的设置，观察哪个在你的内存约束下更稳；CI 上要注意并发档应与 runner 的 CPU 配额与内存配额一致，而不是照抄本地配置。

链接（linking）之所以单独成为瓶颈，是因为它的性质与其他阶段相反：其他阶段可以按 crate、按 codegen 单元高度并行，链接却天然是汇聚点——它必须等所有输入就绪，然后把散落的符号表、重定位信息、调试信息在一处合并。参与链接的目标文件越多、符号越多、调试信息越厚，这一段越长；一个 workspace 里可执行入口多、每个入口都各链接一遍时，链接成本还会乘以入口数量。这也是为什么在“依赖图重复劳动”之后，链接常常是那条谁也躲不掉的串行尾巴。

链接段的环境相关项要用正确的方式表述：社区里常见做法是换更快的链接器，或者减少调试信息的量来缩短链接与产物处理。你可能会听到 lld、mold 这类名字被作为“更快的链接器”提到，也可能听到调试信息格式与档位被讨论，但本文刻意不给具体配置细节与效果数字：链接器是否可用、以何种方式启用、在你这个平台与工具链渠道上表现如何，都依赖当时的实际组合，换一台机器结论就可能变化。可迁移的做法只有一条——把这类环境项当作“每次只改一个因素”的实验：固定代码与工具链，只动一个环境项，测冷编译与热增量两个场景的等待量级，并把结果记进那张表；同时在 CI 里为它留一个可以关闭的开关，方便出问题时回退定位。顺带记住一个副作用：调试信息减少会让本地与线上的问题定位变难，这是拿可观测性换时间，收益与代价要放在一起权衡。

构建缓存：把它当开关，不要当魔法

缓存至少分四层，越往下越通用、也越容易出问题。第一层是本地 target 目录复用，它按 feature 集合、profile、工具链把产物分开放，收益最大也最直观：只要这些条件不变，第二次构建就能跳过已完成的部分。第二层是本地跨工作区复用，做法是把 target 指到统一的存储位置、或用同一份依赖版本锁让不同分支共享产物，代价是磁盘占用与路径相关问题。第三层是编译缓存（把“输入完全一致的编译任务”的产物与诊断缓存到可共享的地方，社区里常见的是这类缓存代理工具），它能让不同机器、不同分支上的相同任务只编一次。第四层是 CI 侧的缓存：把 target 目录或缓存内容随流水线保存与恢复，让下一次运行不从零开始。这套“分层缓存加按阶段拆门禁”的方法论在前端工具链的编译优化里已经被讲过一轮，本文不重复那些工具细节，只谈 Rust 侧的翻车点。

最容易翻车的一点是：缓存命中依赖工具链版本、feature 组合、环境变量三者的一致性，而这三者常常在你没意识到的时候变化。缓存的键本质上是“这次编译的全部输入签名”，其中包含编译器版本与渠道、生效的 feature 集合、进入编译命令行的环境变量、构建配置的完整内容、乃至源码路径。你在本地把某个变量导出用于构建脚本、CI 上加了一个影响编译命令行的开关、或者升级了工具链，键就变了；表现是“缓存明明配了却全 miss”。更麻烦的是反向情况：键的粒度不够细时，缓存会给出“看起来命中、实际与全新构建结果不一致”的产物，这类问题定位成本极高。因此缓存必须被设计成能关掉的开关：保留一条明确的路径，可以在一次流水线运行里完全绕过所有缓存层跑一次全新构建，用它验证“缓存没有欺骗我”。这条 no-cache 路径要么定时跑，要么在改动构建配置、升级工具链、调整 feature 之后必跑一次。

CI 里缓存 target 目录的收益与风险要成对评估。收益方向：重复依赖构建被跳过，冷编译里属于“依赖那部分”的工作不再每次付。风险方向：target 目录体积大，保存与恢复本身要时间与磁盘 IO，可能吃掉一部分收益；跨运行复用的产物里混着旧工具链的输出，指纹判定负担变重；缓存把同一个错误反复带回流水线，让“这真是新引入的问题吗”变得难以判断。可行的做法是按分支与按构建配置把缓存分开，宁可比预期少命中，也不要跨配置共享。下面这份 CI 分层骨架可以直接改成本仓库的作业名，它的要点是“每层只做该层的事、失败时能立刻定位是哪一层”：

CI 分层与裁剪：把不该一起跑的东西拆开

为什么把格式与静态检查和测试分到不同作业，理由有三条。一是它们回答的问题不同：前者回答“这段代码是否符合规范”，后者回答“行为是否正确”，把它们混在一个作业里，任何一条 lint 违规都会连带让测试结论不可用。二是失败定位：独立作业能直接告诉你“只有 clippy 红了”，而不是在一堆构建输出里找。三是成本结构不同：静态检查不产出可运行产物，测试要构建链接再跑，两者放在一起会人为拉长门禁反馈链条。分层以后，你还能只对最便宜的那层设置“每次都跑”，对昂贵的那层设置“按条件跑”。

按改动路径做受影响范围构建（affected-range build）是第二根杠杆。思路是把“改了哪些目录”映射到“哪些 crate 受影响”，再只对这些 crate 以及依赖它们的下游做检查与测试——工具层面就表现为按包选择要构建与测试的目标，而映射关系来自你对 workspace 依赖图的了解。它的收益集中在增量类场景：改一个叶子 crate 的内部实现时，全工程其余部分没有理由再跑一遍测试。风险也要说清：如果影响范围判定漏掉了间接依赖（比如通过共享类型 crate 或构建脚本传递的依赖），你会得到“CI 绿了但主干坏了”的结果，所以必须保留一个每日或每周的全量作业作为兜底，并让受影响范围算法偏向保守（宁可多跑）。

矩阵裁剪是最容易省却最少被做的一项。真实支持的 feature 组合往往比矩阵里的格子少：把没有用户、没有承诺的组合删掉；把只在极端组合下才编译的代码路径挪到单独的可选验证作业；把“必须通过”和“尽力保障”分成两档，后者失败不阻塞主干。判定依据是产品承诺而不是“反正能配上”。

失败重试与缓存失效要划清边界。测试不稳定（flaky test）该重跑的是测试本身，不应该顺手清缓存；缓存可疑（同一错误跨多次运行、全新构建不复现）该做的是清缓存重跑而不是无限重试。两者混在一起的结果是你永远不知道问题出在代码还是在环境。建议的规则写成一句话：先按“重跑是否改变结论”分类，再决定动作。

开发体验侧的杠杆：反馈环才是真成本

日常开发里，等待发生在编辑器与终端之间，而它们其实在抢同一份资源。语言服务器（例如 rust-analyzer 这类编辑器侧检查工具）会在后台持续做大量 check 级别的工作：加载依赖图、构建项目模型、随文件变化重新分析，这些工作既吃 CPU 也吃内存。你在终端里手动发起一次完整构建时，两者同时运行，谁都不会快；更糟的是磁盘与产物目录的争用，以及多个 checkout 各自在后台索引带来的叠乘效应。可行的方向是错开重活：确定“这段时间由编辑器负责反馈、还是由终端负责构建”，避免在同一台机器上并行开多个大项目的后台分析，把 target 目录放在本地磁盘而不要放在网络盘或被同步工具监看的目录（同步工具会因产物高频变化而反复扫描，代价以另一种形式回到你身上）。

第二个杠杆是把默认动作设成 check 而不是 build。编辑循环里多数问题的答案是“类型过不过、借用对不对”，这些 check 就够；只有要跑二进制、跑集成测试、复现运行时行为时才需要完整构建。把它变成习惯的形式很具体：编辑器里保存时触发的是检查类动作；终端里第一反应敲的是检查；把“完整构建”留给明确需要的时刻。方向上的收益在第 3 节已经解释过——省掉的是中端与后端以及链接，不是前端。

第三个杠杆是大项目的分层测试（layered testing）。把测试按代价分层：单元级（改哪测哪，属于最快的一档）、crate 级集成、跨 crate 的端到端。改动落在哪个 crate，就先只跑那个包以及它的直接下游；端到端与全量测试交给 CI 的对应作业与定时任务，而不是每次手工等待。配合第 4 节的依赖分层，“哪测”这件事才有明确依据。

第四个杠杆是把已有的可视化产物读对。cargo build --timings 生成的报告是一份按 crate 展开的时间轴：每行是一个 crate，条形显示它什么时候开始、什么时候结束，依赖边显示谁在等谁，另有整体并发占用的视图。读它的时候不要问“总共多少秒”，而是问三个结构性问题：最长的那条依赖链是哪几个 crate 串起来的（这是关键路径，只有拆它才缩短端到端等待）；图里有没有大片空白（空白说明并发没被填满，往往是依赖链串行而非机器不够快）；有没有一两个 crate 的条块明显长于同层其他块（那是单点，值得单独看它内部在做什么，比如宏展开、单态化还是它自身体量巨大）。这三问的答案决定你下一步用哪一类手段；本文不给任何“看这张图应该读到多少秒”的结论，因为那张图只在你的机器上成立。

一次诊断复盘：从“改一行等太久”开始

这个案例是我见过的项目形态里最典型的一种，为方便叙述做了脱敏，下面所有量级都用相对描述，个别处标注“示意值”，请读者替换成自己仓库的实测记录。

起点是一句抱怨：某个服务组的同学说，“改一行要等太久，久到思路被打断”。第一轮我们没有动任何配置，只做第 2 节的测量：固定在同一个提交上，分别记录冷编译、改一个内部实现文件的热增量、改一个公共类型签名的热增量这三类动作的等待量级，并把当时的并发档、target 状态、编辑器是否开着都记进表。一轮下来得到三个事实：内部实现改动的等待已经属于“可以接受”量级；公共类型签名的改动等待是“极高”量级；冷编译与 CI 全新构建同为“极高”量级，且彼此不相上下。

第二轮定位结构。用时间轴报告看关键路径，发现最长的链条穿过一个基础 crate，而示意值上有大半的 workspace 成员直接或间接依赖它——处在“人人依赖”的位置，意味着它的签名变更会波及全工程；再往依赖树里查，发现这个基础 crate 顺带把两个体量不小的通用 crate 透传给了所有下游，其中一个还是带着默认 feature 进来的，于是每个下游 crate 的元数据视图里都塞着一堆用不到的类型。第三轮看阶段：把那次公共签名改动重做一遍，确认时间大头落在前端（大量 crate 重复做类型检查）而不是链接，于是排除了“先动环境项”的思路。第四轮看缓存：CI 每次运行都从零开始，流水线各作业之间不共享产物，本地与 CI 之间没有任何一致性约束，工具链版本靠镜像默认值漂移。

诊断结论是三条叠在一起：一个公共类型签名改动触发全 workspace 重编；依赖 feature 穿透把无关代码带进每个 crate；没有共享缓存让每次冷编译都付全额。改造分四步做，每步之间都留了测量。第一步拆边界：把基础 crate 里真正需要被广泛引用的类型抽到一个薄接口 crate，实现留在原处，让“公共签名改动”必须发生在薄接口上；同时把透传的通用 crate 收回到只在必要的能力层 crate 出现。第二步收敛 feature：把依赖 crate 的默认 feature 关掉、按需显式打开，并删掉矩阵里没有承诺的组合。第三步给 CI 加分层与复用：检查、静态门禁、按影响范围的测试、发布构建拆成不同作业，并引入一条绕过所有缓存的全新构建路径用于定期验证。第四步处理环境与习惯：并发档按 runner 配额校准，编辑器后台检查与终端构建错开，把 check 定为默认动作。

验证方式不是“感觉快了些”，而是一份观测计划：改造后重跑同一批固定动作，与第一轮那张表逐行对比同一改动类型的等待量级；观察时间轴报告里最长链是否变短、同层是否出现更多并发；故意做一次公共签名改动，看受影响的 crate 集合是否真的收敛（示意值：从“几乎全仓”收敛到“薄接口的直接下游那一层”）；跑一次绕过缓存的全新构建，确认结果与带缓存的构建一致，以证明缓存没有给出假象。这些观测里唯一有意义的数字是你自己前后的对比，任何跨机器的绝对耗时都不成立——这也正是本文通篇拒绝写死耗时数字的原因。

增量编译 前端为主，连带减少下游重复劳动 增量 产物体积增大；指纹判定有额外开销；失效时收益归零 构建本来就极短；或磁盘吃紧且几乎每次都是全新构建
crate 拆分 前端（元数据视图变小）、依赖图（关键路径变短、并行变高） 增量与冷编译都受益 契约面变多、版本管理成本、每个编译单元的固定开销 拆分问题序列里有两三条答“否”；团队小、无人维护边界
feature 收敛 全链路（参与编译的代码总量变少） 冷编译与 CI 需要维护“支持哪些组合”的承诺；漏测真实组合会引入隐患 项目本来就只有一两种组合；feature 是对外 API 的一部分且用户确实在用
泛型改动态分发 中端与后端（单态化产物数量减少） 冷编译 多一层运行时间接与装箱，损失部分运行期性能；接口表达力下降 泛型只被少数类型实例化；或该路径本身就是性能热点
依赖瘦身 全链路，尤其是前端与链接 冷编译与增量 需要持续审查新增依赖；自研替代部分要自己维护 依赖体量小且无 feature 穿透；替换成本高于收益
并行度调整 后端与整体的墙钟时间 冷编译与 CI 内存压力上升可能反而变慢；配置需与机器配额绑定 机器内存本就紧张；任务间依赖已把并发填满，调了也没空间
构建缓存 依赖图重复劳动与链接（跳过已完成任务） 冷编译与 CI 键不一致就全 miss；错误产物难定位；归档保存与恢复本身要成本 构建输入签名极不稳定（频繁换工具链或路径）；无法保留一条绕过缓存的验证路径
CI 分层与裁剪 依赖图重复劳动与墙钟反馈时间 CI 作业编排复杂度上升；影响范围判定漏判会造成假绿 项目本身就一个 crate 一套测试；无全量兜底作业时不要贸然裁剪
编辑器与本地习惯 前端为主的日常反馈 增量 需要改变个人工作流；偶尔要手动触发一次完整构建 单人小项目、构建本来就快；或工作内容高度依赖运行结果

这张表最右一列比中间几列更重要。编译优化最容易犯的错，是不看条件地把所有手段都上一层，结果换来一堆难维护的配置与无法解释的现象。判断标准始终是前面测出来的那张表：你的等待到底落在哪一段，值不值得为它付这份维护成本。

定位顺序：一张可以直接贴的清单

最后把全文收敛成一份可贴在工位或 wiki 上的定位顺序。它的作用是防止“跳过归因直接调参”。

这份清单里“第 7 步才谈并行”和“第 8 步要回测”是最容易被略过、却最能避免折腾的两条。绝大多数“配了半天没变化”的经历，都是因为从第 7 步开始动手。

小结

本文的主线只有一条：把“编译慢”拆成可归因的阶段，再让每类手段去对应它真正改善的那一段。前端慢，看宏、看元数据视图、看增量边界；中端慢，看单态化与 feature 组合；后端慢，看优化档位、调试信息档位与并发；链接慢，看符号量与产物处理；而依赖图上的重复劳动，只能靠 crate 拆分、缓存与 CI 分层来消。

第二件事是把测量放在手段之前。冷编译、热增量、CI 全新三种场景要分别计时，控制变量、每次只改一个因素、把结果记进一张固定的表——没有这套动作，任何优化都只是在黑盒里试参数。本文通篇不给具体耗时数字，正因为绝对数值只在你的机器、你的仓库上成立；能迁移的只有方法与判断标准。

第三件事是对“优化”本身保持警惕。增量编译会让产物膨胀、crate 拆分会带来契约成本、动态分发会牺牲运行期性能、缓存会造成难定位的不一致、并行度过高反而更慢。每一项收益旁边都写着账单，而本文反复强调的做法是：留一条绕过所有缓存的全新构建路径，定期用它证明优化没有骗你。若你只能记住一件可立即执行的事，那就是把下一次要改的编译配置当作实验对象——先测、再改一个变量、然后回测。
