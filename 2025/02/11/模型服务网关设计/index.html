模型服务网关设计

本文讨论的是模型服务网关：一个把大模型推理接口当作后端服务来治理的入口层。它和通用 API 网关共享同一套工程骨架——鉴权、路由、限流、可观测、灰度——但在每一个环节上都因为“生成”这件事本身而改变了口径。本文不重复通用网关的实现细节，那些内容在《API 网关设计与实现》里已经写透；也不重复限流算法与配额体系本身，那部分归《限流与配额体系设计》；本文只把镜头对准模型服务特有的那一面，讲清楚每一处口径为什么变、变了之后网关要做哪些新的决定。

先给一个总体判断：模型服务网关的难点不在于它多转发了一种协议，而在于它必须把“成本”和“质量”变成一等公民的路由维度。传统网关眼里一次请求近似免费，区别只在字节数和耗时；模型网关眼里一次请求是一笔可计量、可预测、可追责的花费，而且这笔花费在请求发出之前就能估出大概。这个差别会一路传导到重试策略、排队策略、日志格式与审计要求上，本文就按这条传导链依次展开。

一、它到底和传统 API 网关差在哪

结论先行：差别集中在四个维度的替换上——请求维度换成 token 维度、短连接换成长连接流式、路由决策里加入上下文长度、成本与质量同时成为可路由目标。

第一，计量单位从“次”换成“token”。传统网关做限流时，一次 GET 与一次导出千行 CSV 的报表接口在计数上是等价的，最多再按响应字节数补一个次级维度。模型服务不是这样：同一条 chat 调用，输入 200 token 与输入 90 000 token 的上游开销可能差两个数量级，而输出写到哪停并不由调用方决定。于是网关必须估算本次请求的 token 消耗，并在响应回来后校准它——配额、限流、账单、告警阈值全都挂在这个数字上。算法本身不必重讲，计数器、漏桶、令牌桶的行为在《限流算法：计数器、漏桶与令牌桶》里已经说清；变的是被扣减的那个数：不再是 1，而是一个带方差的估算值。

第二，连接形态从“一问一答”变成长连接持续吐字。流式的客户端实现与分块解析在《大模型流式输出实践》里有专文，本文只关心网关作为中继时的责任：不能无意中缓冲掉整个响应，否则首字节延迟的优势全部作废；必须能把上游的取消信号向下游传递、把下游的断连向上游传递。这里最容易出的事故，是网关为了统一响应体而在内存里攒完整段文本，把流式接口做成伪流式。

第三，上下文长度进入路由决策。传统路由按路径、方法、Header、权重选后端；模型网关要多加几个输入：本次请求的输入 token 规模能不能塞进候选模型的窗口、这个模型在长输入下的有效利用率如何、任务是否需要更长的思考预算。上下文长度不只是参数校验，它直接决定候选集合。

第四，成本与质量同时可路由。传统网关的“质量”近似二值：可用与不可用。模型网关面对的是一个连续谱——同一个提示词交给不同模型，价格差数倍，风格与错误分布也不同。于是路由层第一次要处理“没有唯一正确答案”的后端选择，其风险在第二节展开。

把上面的差别整理成对照表：

能力项 传统 API 网关 模型服务网关特有考虑
计量单位 请求次数、字节数 输入与输出 token，需要预估与事后校准
后端选择 按路径与权重，结果等价 按任务、成本、延迟、合规选择，结果不等价
重试 幂等读操作可安全重试 生成结果不可复现，重试烧预算且可能重复副作用

这张表就是后文每一节的目录，逐个展开。

二、路由层：把“选哪个模型”变成可解释的决定

结论先行：路由层要输出的是一个排序后的候选列表加一条明确的降级链路，而不是一次随机挑选；同时必须承认“同一请求换模型”存在语义风险，结果不可复现是这一层的固有属性，不是缺陷。

先看路由的输入。本文建议网关把决策输入固定为四组：任务描述（由调用方声明或网关侧的分类规则推导）、成本约束（本次调用的预算上限、当月剩余配额）、延迟目标（同步交互还是后台批处理）、合规约束（数据能不能出境、能不能进第三方）。这四组不是并列打分项，前两组是过滤条件，后两组是排序权重——把合规当成权重是可以导致事故的做法。

过滤之后得到候选集合，排序要有可解释性。一种常见的做法是把每个候选表示为若干个可估计量的加权组合：预计成本、预计首 token 延迟、该任务类型上的历史表现分、剩余配额充裕度。历史表现分从哪来？从离线评测集与在线抽样反馈来。指标定义与评测方法属于评估实践，本文不展开，只强调一点：这个分数必须带样本量与时间窗，否则网关会在一个小样本的高分模型上稳定翻车。

降级链路要显式写出来，形如“主候选 → 同类替代 → 兜底小模型 → 拒绝并返回可重试错误”。这里有一个常被忽略的设计取舍：兜底不是无成本的。当主模型因为配额耗尽而降级到一个便宜模型，业务侧拿到的回答质量分布会发生漂移；如果这个漂移无人知晓，事故会以“最近怎么变笨了”的模糊反馈形式出现，排查极其困难。所以每一次降级都要在响应元数据与审计日志里留下痕迹，包括被跳过的候选与跳过原因。更进一步，把降级次数与降级深度做成告警指标，而不是只告警错误率——错误率在这类事故里是零。

关于拒绝。网关需要一个明确的“没有合格候选”出口。粗暴返回 503 会让调用方盲目重试；更好的做法是返回结构化的拒绝原因，附带可重试性与建议的重试间隔，让调用方的退避策略有据可依。本文认为，模型网关的拒绝路径值得花心思设计，因为它比传统网关更频繁地发生——配额是有限资源，而模型可用性并不等于业务可用性。

还有一个细节：路由决策要不要缓存？可以缓存的是“任务到候选集合”的映射与模型元数据，不应该缓存的是“这条具体请求的回答”。后者是语义缓存的范畴，它带来的收益与风险都不小，本文不主张在网关默认开启——如果开启，缓存键必须只由模型可见的输入内容派生，绝不包含任何上游凭据（第七节会再回到这一点）。

三、故障转移与重试放大：最贵的一类事故

结论先行：对生成接口做无条件自动重试，是模型网关最典型的预算泄漏源。重试策略必须同时解决两个问题——钱花在哪了，以及副作用会不会重复发生。

先看失败形态的差异。传统服务的失败大多是“整段失败”：连接拒绝、超时、5xx，重试的期望成本近似一次调用。模型服务里有一类中间态：流已经吐了两千 token，上游因资源不足断掉了。这算成功还是失败？协议上是失败，计费上钱已花掉，语义上那半段回答往往已包含业务需要的信息。本文建议默认把已收到的部分连同显式截断标记透传给调用方，由它决定是否接受；同时如实记账已消耗的 token，不能因为“这次是失败”就从统计里抹掉，否则成本归因会长期偏小。

再看重试放大。假设链路是客户端到网关到上游，三层各带三次重试，最坏情况一次用户操作会打出二十七笔上游调用，每笔都是真金白银的推理费用。更糟的是退避窗口重叠：客户端在 t 时刻重试、网关在 t 加 0.2 秒重试，两股流量打到同一个上游账户，瞬时并发被平方级抬高，反而更容易触发上游限流，形成正反馈。本文把这种情形称为重试放大——它在模型网关比在传统网关危险得多，因为每次放大的单位成本高几个数量级。

对策之一是重试预算。做法和普通服务里的思路一致，但预算的度量要落在 token 上而不是请求数上：为每个主体设置一个“重试消耗上限”，比如重试产生的额外开销不超过该主体正常开销的一定比例（具体比例是团队约定示例，不宜写成普适常数）。预算耗尽后，网关不再自行重试，只把错误透传给调用方，并把“本次未重试因为预算耗尽”写进响应元数据。这样做的价值在于把最贵的行为变成了一个可观测、可调参的资源，而不是藏在框架默认值里的黑盒。

对策之二是幂等键。要分两种情形讨论。纯补全类调用没有副作用，重复只是重复花钱，幂等键的作用是去重与合账，把同一逻辑请求的多条物理记录归并成一条可核对的账。带工具调用则完全不同：一旦模型触发下单、退款、发消息这类外部动作，重复执行就是生产事故。网关侧的写法是要求调用方在请求头带上由业务生成的幂等键，并在两个位置使用它——一是发起上游调用前查一次该键是否已有确认执行，有则直接返回既有结果或明确的冲突状态；二是把键透传给工具执行层，由执行层做真正的去重。要强调一点：网关不能凭“提示词相同”就判定幂等，内容相同不等于意图相同，两个用户问出同一句话是完全可能的。

故障转移的顺序也有讲究。上游返回限流类错误时，立刻切到同一供应商的另一个项目密钥几乎没有意义，因为配额通常是账户级或区域级共享的；跨供应商切换才有真实收益，但会连带触发合规检查与价格跳变。所以转移表要标注“等价转移”与“跨域转移”两类，跨域转移必须受第二节的过滤条件约束。还有一点：对 429 类错误做转移比对超时类错误做转移更安全——后者不确定上游是否已经开始执行，转移可能造成双份消费。

四、配额与限流：算法不变，口径全变

结论先行：这一层的算法在《分布式限流设计与实现》里已经讲清，本文只讲在模型场景里必须改的三个口径——计量单位改成 token、池的划分按主体而不是按接口、突发与长期要分成两套窗口。

第一，计量单位。把限流的扣减额从 1 改成“预估 token 消耗”，会带来一个必须处理的问题：预估不准。输入侧可以本地分词估算，误差可控；输出侧无法预知，只能用一个上界（比如请求体里的最大生成 token 数，或者任务级默认值）先预扣，响应后按实际值多退少补。这里有个陷阱：如果调用方在请求里能自报最大 token，那它就掌握了自我放行的手段——自报一个很大或很小的数字会直接影响扣减额。所以这个字段在网关侧要按任务类型重新钳制，取“调用方声明”与“策略上限”的较小值，而不是无条件采信。另外，预扣的额度在连接异常中断时必须能被回收，否则一段时间内会出现额度泄漏，表现是配额莫名其妙耗尽。

第二，池的划分。按接口路径分池对模型服务没什么意义，因为路径通常只有一个。有效的划分维度是主体：业务方、团队、最终用户、任务类型。本文建议至少支持两层——主体层保证公平性与账单归属，全局层保护上游账户不至于被自己打爆。两层之间还需要一个可解释的优先级：紧急修复类任务在资源紧张时能不能插队，这件事最好写成显式策略而不是靠“它的池子还空着”这种巧合。

第三，突发与长期。模型的调用形态天然不均批：交互式场景是持续小流量，批处理与夜间回灌是短时间大流量。只用一个短窗口会让批处理任务永远排队，只用长窗口会让交互式场景在批处理启动时被饿死。所以至少两套窗口并存，并且批处理类流量要有独立的突发许可——它延迟不敏感，可以排队，但要有明确的排队长上限。

最后说排队与拒绝的取舍。本文的判断是：同步交互流量优先快速拒绝，异步批处理流量优先排队。理由是同步场景里用户已经感知到等待，再多排三十秒不如直接返回可重试错误让上层降级；异步场景里拒绝意味着整批任务要人工重放，成本远高于等待。这个决定应写成路由配置里的一个字段（后文示意配置中的 admission.mode），而不是散落在各服务代码里。排队还要有可见性：返回已入队状态与位置估计，比静默挂住连接好得多——挂住的长连接本身也在占用网关的连接资源与流式缓冲。

五、流式透传：中继不是缓冲

结论先行：网关在流式链路上的第一职责是“别添乱”——不聚合、不打乱、能把取消信号双向传导；第二职责才是把断连与超时这两类边界情形算清楚。

先说不聚合。服务端事件（SSE）是按分块到达的文本增量，网关若为了统一响应结构而把整段内容攒在内存里再一次性返回，用户看到的就是“转圈很久然后突然出现全文”，这比不用流式还糟——延迟没省，内存还多占了。正确姿势是逐块转发，同时把每块到达时间记进指标（首块时间尤其重要），只在必要处做轻量改写，比如替换事件里的模型名字段以屏蔽上游的字段差异。改写要谨慎：一旦开始逐块解析再序列化，就把字节流问题变成了结构化问题，出错概率与开销都会上升。本文倾向的做法是——能不解析就不解析，需要统计长度时用一个增量式的估算器。

再说断连。客户端收到一半时断开，是流式链路最常见的“非异常异常”：刷新页面、切后台、网络抖动都会造成断连，网关不能把它当成上游故障。这里要算清楚三件事。第一，向下游停止写入、向上游发送取消，避免上游继续生成白烧钱。第二，已完成部分怎么记账——按上游实际报告的消耗记账，落一条独立于“请求成功”的账目，状态标注为客户端提前终止。第三，已完成部分要不要保留——“重新问就接着说”属于会话状态管理，网关不该自己发明续写语义，只需把这次断在哪、说了多少写清楚，交给上层决定。还有个容易忽略的点：断连时网关持有的上游长连接必须被真正释放而不是等超时，否则并发一高网关自己先耗尽连接池，表现出“上游明明正常但整体变慢”的诡异症状。

超时要分层，三层缺一不可：连接超时（多久连不上上游就放弃）、首 token 超时（连上了但迟迟不吐字，通常意味着排队或上游资源紧张）、整体超时（一条流最多允许持续多久）。三层的处置动作也不同：连接超时是可安全转移的信号；首 token 超时值得转移但要考虑上游可能已经在计费；整体超时通常意味着生成跑飞，应当直接切断并按已消耗记账。把这三层写成三个独立可配的阈值（示意配置中的 timeouts.connect、timeouts.firstToken、timeouts.total），并且明确禁止把它们合成一个“总超时”——合并后的一个数字无法区分上述三种情况，运维时无法定位。

流式链路还带来一个传统网关没有的可观测问题：什么时候算“完成”。没有响应码意义上的完成信号，就要求网关自己定义——本文建议以收到上游的终止事件或上游主动关闭流为完成，两者都没发生而连接断了就是异常终止，两条路径的指标要分开统计，否则错误率会因用户刷新页面而虚高。

六、上下文长度与裁剪：网关要不要动刀

结论先行：本文的立场是网关默认不裁剪，只做校验、度量与记录；如果确实要在网关侧裁剪，必须留下可审计的裁剪声明，因为它改变了模型看到的内容，而模型看到的内容就是证据。

先解释为什么“要不要截断”是个真问题。请求输入已经超过候选模型窗口时，最省事的办法是尾巴截一刀让它进去，但这个动作有三个恶果。第一，语义被悄悄改写：调用方以为模型读了全文，实际读到的是被裁过的一段，回答的偏差无从解释。第二，缓存与评测口径失真：离线评测用完整输入、线上用裁剪输入，两边分数不可比。第三，也是最实在的一条——这是审计问题：回答造成业务影响后，复盘需要知道模型当时到底看到了什么，而“网关裁了一段且没记录”会让复盘直接断线。

所以网关该做的是：把输入 token 度量清楚，把候选模型的窗口当硬约束参与路由（窗口不够就选窗口够的模型，或返回结构化的“输入过长”错误让调用方自己决定怎么缩减），并且把每一次实际发生的裁剪记录成一条审计事件，内容至少包括裁剪前后的 token 数、裁剪策略标识与被移除片段的哈希摘要（不记录原文，理由见下一节）。哈希摘要的作用是让“当时确实少了这些内容”可验证，而不泄露内容本身。

如果业务确实需要一个“网关代劳”的裁剪能力，本文建议只允许两种保守形态：一是按明确规则的元数据剥离，比如去掉调用方声明为可丢弃的历史附件块；二是显式声明的尾部保留策略，即固定保留最近若干轮，并且必须在响应元数据里回传“本次发生了裁剪，保留了最后多少 token”。无论哪种，策略版本要写进日志。策略在没有版本标识的情况下被修改，是事后无法解释行为变化的头号原因。

还要处理一个技术性细节：token 的度量口径。不同模型的分词器不同，同一段文本在两个模型上算出的长度不一样，窗口判断必须以目标模型的口径为准。网关若用一个通用的估算器（例如按字符数除以一个经验系数）来做硬约束，会出现边界误判——恰好卡在窗口边的请求被错误放行，上游直接报错。本文建议：估算器用于计费与限流（容忍误差），精确计数用于窗口校验（不容忍误差），两者分开实现，不要图省事共用一个。

七、密钥与审计：把凭据和内容都当成敏感数据

结论先行：模型网关同时持有两类敏感物——上游凭据和用户写的原文。前者泄露直接造成经济损失与冒用，后者泄露是隐私事故。两者都要有明确的边界，且都要在网关这一层做，因为这是唯一同时看得见两条流的组件。关于应用层安全的更完整讨论在《大模型应用安全》里，本文只讲网关侧该承担的三件事。

第一件，上游凭据集中托管。凭据只存在于网关的密钥服务里，业务侧拿不到，日志里看不到，配置文件中不出现。本文强调四个容易失守的角落。一是调试接口：为方便而支持的“临时换一个密钥试一下”，若不过审计、不留痕，就是最省事的越权通道。二是缓存键：绝不要把凭据、密钥指纹或其任何可逆片段拼进缓存键或指标标签——标签一旦基数化就会在多个系统里复制留存。三是错误响应：上游的认证失败信息常常回显被拒凭据的前缀，透传前必须清洗。四是重试与转移日志：跨账户转移时顺手记下两个账户的标识，等于交出密钥归属关系的完整地图。凭据轮换还要支持无损：同一时刻存在两把有效密钥的窗口期内，配额归集要按密钥而不是按账户，否则轮换会短暂把配额池劈成两半，表现为莫名其妙的限流。

第二件，日志脱敏。模型服务的日志天然包含提问原文，而原文里可能夹带个人信息、内部代码与客户数据。本文建议“默认不记内容，按需分级记录”：常规访问日志只记结构化元数据（主体、任务类型、模型、token 消耗、时延分位、决策结果、被裁剪声明）；内容级日志走单独的采样通道，采样出的条目必须做字段级脱敏，包括正则化常见标识、剥离疑似密钥串、对手机号类形态做掩码。下面这段 Python 表达的就是这个思路——它处理的是已决定记录的结构化副本而非主访问日志，并且绝不接触任何凭据。

第三件，留存期限与访问边界。内容级日志与元数据级日志的留存期不该相同：元数据要支撑对账与容量规划，留得久；内容级日志风险高，留得短，且访问它需要单独授权与二次审计。本文建议把“谁在什么时间看过哪条内容日志”也记成日志——这类访问在事后调查里往往比内容本身更关键。同时要预留合规例外：某业务方要求完全不落内容时，网关必须能在主体维度关掉采样通道；这件事在架构上很便宜，在没有预留它的架构上很贵。

八、灰度与 A/B：按主体分桶，别按随机数分桶

结论先行：模型变更的灰度单位应该是主体而不是请求，因为同一用户在同一会话里被分到不同模型会造成可感知的风格跳变；同时影子流量要用独立预算，回滚必须是一个不需要发布的开关。

为什么按主体分桶。请求级随机分流在 Web 服务里很常见，因为同一后端返回的语义是等价的。模型不等价：一个用户这轮对话用模型甲、下轮切到模型乙，语气、格式、拒答边界都会变，用户会感知为“产品不稳定”。按主体（用户、租户、会话）哈希分桶保证同一主体在实验期内落到同一组配置，跳变只发生在实验边界。下面这段 TypeScript 表达的是分桶的实现要点：输入是稳定主体标识，输出是桶号；注意它只做分桶，不参与任何鉴权，也不要把凭据混进哈希输入。

灰度比例要小步、可停、可回。本文建议把一次模型切换拆成若干台阶，每级都有明确的最短观察时长——短于一个业务周期的观察只能看到噪声。回滚杠杆指“改一个配置值就能把流量整体拉回”，它必须独立于代码发布通道；如果回滚需要重新部署，实际上就没有回滚。还要提防一种隐蔽耦合：候选模型的配额被实验消耗光了，此时“回滚”会变成“降级到第三个模型”，实验结论与降级结论混在一起，两边都不可信。所以实验启动前给候选模型划一份专属预算、用完即停实验，这条纪律比任何统计方法都更能保住实验的有效性。

影子流量是另一件必须花钱的事：把生产请求复制一份发给候选模型、结果不回给调用方，只用于比对。它的价值是零用户风险地拿到真实分布的输入；代价是双份成本，以及一个安全坑——影子副本必须走同样的脱敏与合规检查，不能因为“反正用户看不见”就绕过数据出境限制。本文建议按抽样比例开启，比例小但覆盖长尾任务类型，且影子请求要在所有日志里打显式标记，否则实验开销会被算到业务头上。

评估口径一句话带过：在线看用户可感知的行为指标、离线看评测集上的任务表现，两套口径的指标定义与统计方法属于评估实践，本文不重复；这里只强调灰度配置里必须写明“用哪个离线集与哪个在线信号做判据”，没有预先声明判据的实验，事后总能找到支持结论的那个数。

九、整体链路

结论先行：把前八节串起来，模型服务网关的主干就是七步——准入、鉴权、配额、路由、上游调用、流式回传、计量与审计；其中计量与审计不是收尾动作，它同时给路由与配额回灌数据。

至于通用代理与数据面怎么实现高并发连接、转发与负载均衡，属于《高并发网关设计》《Envoy 代理原理与实践》《Nginx 反向代理与负载均衡》的范围，本文不重复；降级与熔断在企业内的落地流程见《服务限流降级落地》；模型推理服务怎么部署、在整体分层中如何定位，见《大模型应用架构分层》。本文关心的是这七步在模型场景下的口径。近一年生态也在朝这个方向走：MCP 在 2024 年 11 月给出了初版规范，官方至今在推进传输层与鉴权的演进；模型侧的候选项本身在快速增加，比如 2025 年 1 月下旬公开的 DeepSeek-R1 就成了不少团队路由表里的新候选——本文不引用任何产品的性能或价格数字，容量与阈值一律按团队约定示例处理。

flowchart TD

  B -->|未通过| X[结构化拒绝]
  B --> C[配额预扣：按 token 计量]
  C -->|预算不足| Q[排队或拒绝]
  C --> D[路由决策：任务、成本、延迟、合规]
  D -->|无合格候选| X
  D --> E[上游调用：凭据集中托管]
  E -->|连接或首 token 超时| F[故障转移：等价或跨域]
  F --> E
  E --> G[流式回传：逐块中继不缓冲]
  G --> H[客户端断连处理]
  H --> I[实际消耗校准与预算退还]
  G --> I
  I --> J[计量与审计：元数据、裁剪声明、脱敏采样]
  J --> K[指标回灌路由与配额]
  K --> D

这张图里有两条线容易被漏画。第一条是从回传走向校准再回到配额的回路：预扣与实际消耗的差额必须在同一条请求的生命周期内结清，异步补记会让配额短期失真。第二条是故障转移回到上游调用的回路：转移后要重跑一次合规过滤，不能因为“只是换个后端”就跳过检查。

小结

本文的骨架是一个替换关系：请求维度换成 token 维度，短请求换成长连接流式，路由决策里加入上下文与合规，成本与质量同时成为可路由目标。由此推出几条实践纪律。重试要有以 token 度量的预算，幂等键由业务生成、网关只做归集与透传，带副作用的执行绝不能靠内容相似来判等。配额预扣按估算、结算按实际，异常路径也要把额度结清。流式链路的第一职责是不缓冲、能传导取消，超时要分成连接、首 token、整体三层各管一件事。上下文裁剪默认禁止，发生了就必须留下可核对的声明与摘要。凭据只存在于密钥服务，内容日志默认不落原文、分级留存、访问本身也被审计。灰度按主体分桶，影子流量走独立预算，回滚是一个配置值而不是一次发布。最后，模型服务网关的价值不在于它挡住多少请求，而在于它让“花了多少钱、由哪个模型回答、依据什么做的决定”这三件事在任何时刻都能被回答出来。
