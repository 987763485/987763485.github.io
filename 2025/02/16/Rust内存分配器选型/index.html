Rust 内存分配器选型

本文属于《Rust 学习路线》第 50/68 篇
上一篇系列目录下一篇

后端服务里最容易讨论、也最容易被误用的一次改动，就是把全局内存分配器换掉。讨论很多、可复用结论很少，原因很实在：分配器的表现同时依赖负载形状与运行环境，跨环境比较几乎必然得出错误结论。本文把这件事讲到足以支撑决策的程度——先讲接管机制与契约，再讲三类分配器的设计取向、什么现象会暴露差异、容器如何扭曲观测，最后给实验搭建方法、工程做法与反模式清单。全文以 2021 edition 的代码与语义书写；只做类别与机制层面的比较，不比较具体项目实现的版本能力，也不给任何未经环境锚定的性能倍数。

一、接管机制与 GlobalAlloc 契约

结论先行：Rust 程序里所有走标准库的堆分配，最终汇聚到一个可替换的单点；这个替换点的语义是一份 unsafe 契约，而不是一个配置项。

标准库不把分配逻辑内联进你的代码。Box::new、Vec 的增长、String 的拼接，都经由 std::alloc 这层薄封装进入全局分配器实现。语言层提供 #[global_allocator] 属性，作用在一个实现了 GlobalAlloc 的静态项上；一旦声明，它就取代默认实现，成为整个链接产物里所有 Rust 分配请求的入口。这个事实带来两个工程后果。第一，该属性只能出现一次，多处声明直接编译失败，说明全局分配器不具备”按模块切换”的语义。第二，它是编译期的静态决策，不是运行期的开关，这一点在第七节会变成回滚设计的核心约束。想做局部切换，只能靠 arena 之类的作用域容器，不能靠这个属性。

GlobalAlloc 的契约里有四条方法：两条必须实现，两条有默认实现、可以覆盖。

  • alloc：入参是 Layout（大小与对齐），返回满足对齐要求的起始地址；申请失败必须返回空指针，不能 panic，不能在自身内部递归触发分配。
  • dealloc：必须传入与分配时完全一致的 Layout。实现要么靠它定位块元数据，要么靠 size class 反查；传入不一致的 Layout 属于未定义行为。
  • realloc：默认实现是”新分配、复制、再释放”。只有覆盖它，原地扩展才有可能；Vec 增长时是否搬迁数据，取决于这条方法的行为。
  • alloc_zeroed：默认实现是分配后清零。若底层能直接给出已清零的地址区间，覆盖它可以省一次显式清零，但语义要求不变：返回的必须是全零内存。

为什么这是一条 unsafe 边界：契约里最硬的几条，编译器一条都不检查——不能 panic、必须支持任意线程并发调用、dealloc 的 Layout 必须匹配、返回地址必须满足对齐。它同时跨越语言边界：当 C 侧库与 Rust 侧共用同一套底层实现，或者更糟、两套实现的边界不清，任何一侧破坏不变量，都会在另一侧以静默内存损坏的形式呈现。所以选型时真正要问的是”这个实现能否在我这类调用模式下守住契约”，而不是”它快不快”。本文只谈契约对选型的约束；裸指针的使用规则与 unsafe 块内的写法交由 unsafe 专题讨论，这里不展开。

结构体与枚举自身的排布、字段顺序带来的浪费、空值优化这类事，属于《Rust 内存布局与性能分析》的范围，本文只假设”大小与对齐已经定了”。至于借用检查与引用规则，本文假定读者已经把生命周期理顺，只补一句视角：借用检查决定一个对象活多久，分配器决定这段”活多久”要花多少钱。

二、三类分配器的思路差别

结论：类别差异的本质是”复杂度放在哪里”。放在线程本地，就换来低竞争、付出内存足迹；放在全局结构，就换来紧凑与可归还、付出锁；放在生命周期假设上，就换来近乎零成本的分配、付出通用性。

（一）系统 malloc。取向是通用性与兼容性：由 libc 提供，进程内所有语言共享同一份，跨语言边界的分配与释放天然安全，启动时不需要额外建立结构。优势场景是低频大对象、跨边界调用密集、生命周期复杂的常驻服务；行为可预测度低，但”不容易做错”。代价集中在并发上：中心化的空闲管理与 arena 竞争在高线程数下会成为热点，块头与档位的固定开销无法回避。还有一个容易被忽略的事实：不同发行版、不同 libc 的实现可能不同，同一份代码换机器就换行为。这不是优点也不是缺点，而是必须进入实验变量的事实。

（二）带线程缓存的通用分配器。取向是把复杂度推到线程本地：每个线程持有若干尺寸档的小块缓存，命中缓存的分配与释放不触碰全局结构，多线程扩展性因此更好；释放路径上，同线程归还近乎是栈操作，跨线程归还才走慢路径。优势场景很具体：小对象高频、分配风暴、核数多且活跃线程数与核数同量级。代价有三件：线程缓存本身是常驻内存，线程数多时总和不会自然收敛，容易被 cgroup 记成高 RSS；跨线程释放路径更长，且源线程的缓存无法复用，这在异步运行时里非常常见；缓存中的空闲块不会主动归还内核，外部看起来像”占着不用”。这一类是最常被讨论的类别，也是最常在没有证据时被换上的类别。

（三）池化、bump 与固定块的专用分配器。取向是做假设：bump 只推进指针，释放基本是整块重置；固定块把内存切成等大槽位，分配是取一个空槽。优势场景是生命周期整齐、尺寸集中、可以整体作废的阶段——解析、编译、图遍历、单请求内的临时缓冲、批处理的一轮迭代。碎片在这里几乎不构成问题，局部性好，成本可以逐笔解释。代价是硬边界：任意粒度的部分释放不支持或代价很高；超出预置尺寸的请求必须回退到别的分配器；生命周期一旦跨越阶段边界就需要额外协调；它的优势来自”用得对”，而不是”实现好”。

负载与类别的方向性对应（本文只给方向，不给数值）：短连接且每请求产生大量小对象，先评估第二类；阶段清晰、能整批作废，看第三类；跨语言边界密集、尺寸大且低频、运维要求内存足迹最小，先确认第一类是否真的已经是瓶颈。还有第四个方向最常被跳过：很多负载上第一类并没有明显短板，此时换分配器只改变结论的来源，不改变结论本身。本节只描述类别与设计取向，不比较同名项目的实现细节与版本能力。

三、什么现象会暴露分配器差异

结论：分配器的问题很少以”CPU 慢”这一种形态单独出现，更多是以内存形态异常先露头。识别现象比识别分配器更重要，因为现象决定你要不要动分配器。

（一）分配风暴。特征是 QPS 抖动伴随分配调用次数飙升，性能剖析里热点栈停在分配器内部而不是业务代码。常见成因都在业务侧：循环里反复构造 String 与 Vec、每个请求重新创建大缓冲区、序列化框架产生过多中间对象、把一次性容器当作共享容器。这里的正确反应顺序是：先减少分配次数，再考虑换分配器。换分配器只是把同一个错误用更高的吞吐重复出来。

（二）碎片导致 RSS 爬升。分配与释放在多个尺寸档上交错发生时，块会被”占住半满”，空闲空间无法拼成可归还的页。外部表现是 RSS 阶梯式上升且不随负载回落。与真实泄漏的区别有两处：一是曲线是否随负载形状波动后至少部分回落，二是分配计数与释放计数是否回到基线。碎片场景下，次数差值稳定但持有字节数上涨；泄漏场景下，次数差值本身单调上涨。这个判据第五节会给出可执行的口径。GC 语言里同样的现象常被称为”内存不归还”，在 Rust 里成因一致：分配器把页留在自己的缓存或空闲链里，内核无从回收。

（三）跨线程释放。在一个线程分配、在另一个线程释放——通过 channel 传递所有权、线程池回收任务、异步运行时把 future 从一个工作线程迁移到另一个——会让带线程缓存的实现走转发或全局慢路径，同时源线程的缓存无法复用。表现为 CPU 花在分配器内部、且随线程数增长而非线性变差。结构体内部字段怎么排布会造成对齐浪费，那是《Rust 内存布局与性能分析》的范围；本节关心的是”这块内存由哪个线程归还”。

（四）小对象高频。每元素只有几十字节的集合、大量引用计数包装，会让块头与档位上取整的占比放大：逻辑尺寸与实占尺寸之间会出现稳定差值。此时最有效的往往是改容器形态（合并为连续缓冲、减少包装层数），而不是换分配器。

（五）内存对齐与大块申请。当 Layout 指定较大对齐（例如按缓存行对齐的 SIMD 缓冲），分配路径要走对齐调整，实占可能远大于逻辑尺寸。大块申请则经常走另一条代码路径：直接映射匿名内存、释放即归还，行为与小对象完全不同。分界阈值是实现私有细节，不同类别甚至不同平台都不同，选型时不要假设它存在某个固定值，也不要在文章里抄一个”典型阈值”当事实使用。

四、容器与运行时交互

结论：容器里看到的”分配器表现”，大部分其实是环境表现。不先固定环境，任何对比都不成立。

（一）CPU 配额与线程缓存数量。多数实现会按”可见 CPU 数”决定 arena 数量或线程缓存规模，而可见 CPU 数在容器里未必等于配额。当 CPU 以配额方式限制、而拓扑信息仍来自宿主机时，进程会按远多于实际配额的线程数建立缓存：结果是 CPU 上被限流、内存上超配，两边同时变差，且原因看起来互不相关。核对方法不是猜，而是把三个数字放在一起看：cgroup 的 CPU 配额、进程内实际活跃线程数、分配器对外可观测的缓存或 arena 数量（有些实现提供查询入口，没有的话就只能从 RSS 台阶数推断）。三者不一致时，先修环境认知，再谈分配器。标准库提供的可见并行度查询也依赖同一份环境信息，把它当作”需要核对的输入”而不是”可信的事实”，是本节唯一要求的态度。

（二）cgroup 内存限制下”看起来泄漏”。分配器持有的线程缓存、空闲链与页级缓存，在 kernel 眼里都是已分配、尚未使用的常驻内存，全部计入 RSS。限制越紧，这类保留越容易在峰值时触发 OOM，而 OOM 记录里只写”内存超限”，读起来非常像泄漏。再叠加两个常见条件：容器关闭 swap，内核无法把压力转储出去；内核的后台回收不会主动深入用户态缓存。于是同一个实现在宽限制下表现良好、紧限制下反复被杀，很容易被误判成”这个分配器有泄漏”。区分办法仍是第五节的口径：分配与释放计数是否回到基线，以及释放全部临时对象后 RSS 是否出现平台期下降。

（三）为什么基准必须在同一环境里跑。分配器的决策至少依赖这些环境量：可见核数、内存上限与是否触发限制、透明大页开关、NUMA 拓扑、是否发生页迁移、镜像里的 libc 形态。换一台机器、换一次配额、甚至同一机器上换一次并发档位，结论都可能翻转。可复现的做法是：对比组必须在同一镜像、同一节点规格、同一配额下交替运行，且把上述环境量作为记录的字段而不是默认假设。只在压测环境跑赢、没在带内存上限的环境跑过，等于没跑过。

五、观测手段：先把口径写清楚，再谈结论

结论：分配器相关的观测，价值不在”看到内存曲线”，而在”两个口径能对上的证据链”。本节只给方法与口径，不给任何倍数结论——同一份曲线在不同采样口径下可以支持相反的决策。

（一）RSS 与 VSZ 的时间序列。做法是按固定间隔（例如每秒一次，示意值）采样进程的常驻内存与虚拟内存，同时把 QPS、在途请求数、CPU 配额被限流的次数记在同一时间轴上。数据来源是内核暴露的进程状态与 cgroup 计数，两者都要采，因为进程级数字看不到被限制的峰值。口径必须写清三点：RSS 包含分配器内部缓存与已映射但未使用的页；VSZ 包含只是保留、尚未落地的地址区间；两者之间没有稳定的换算关系，也不能互相佐证。判读方式看形状而不是绝对值：是否随负载形状波动、波动后是否回到同一平台、每个周期的谷底是否逐轮抬高。谷底抬高是”要么泄漏要么保留不归还”的强信号，谷底平稳说明保留量已到稳态。

（二）分配计数与释放计数的对齐检查。做法是在自定义全局分配器里按 Layout 分桶计数，口径固定为四个量：按大小档统计的分配次数、释放次数、累计申请字节、当前持有字节。这条手段的价值在于它能区分第三节里两种最容易混淆的现象。判据如下：负载形状稳定时，若分配次数与释放次数之差单调增长，怀疑对象生命周期问题；若次数之差稳定但持有字节持续上涨，怀疑档位上取整与碎片；若两者都回到基线而 RSS 不回落，怀疑保留策略而非分配器本身。实现上的注意点是计数只能给趋势：用宽松顺序的原子累加，接受并发下的少量误差，不要在分配路径里加锁或做精确同步；否则你观测的行为会改变被观测的对象。还要记住这条手段要求你自己实现或包装全局分配器，它带来的开销使其只适合诊断构建，不适合常驻生产。采样与聚合的示意实现见第七节的骨架代码。

（三）分配火焰图的读法。采样式剖析工具记录的是分配调用栈，图上横条宽度是采样占比，不是耗时也不是字节数——这句话决定了读法。要同时看两张视图：按次数聚合的图回答”谁在频繁分配”，按字节聚合的图回答”谁在占内存”，只看一张会得出片面结论。看帧的相对位置：分配器内部帧停在业务帧之上说明问题在调用次数，业务帧之下出现深栈说明中间对象层级过多。跨线程释放会让分配栈与释放栈分叉，此时只看分配图会低估问题规模，必须配合第二项的次数差值。最后一条纪律：火焰图适合排除与定位，不适合证明收益，收益判断只能回到第四节的同环境对照。

（四）交叉验证。存活对象剖析给出的只是”当前存活字节”，它不解释页内碎片，也不解释分配器保留；把存活剖析与 RSS 曲线放在一起，两者的差值本身就是信息量，不要只挑其中一条汇报。

六、选型实验怎么搭

结论：实验设计的质量先于实验次数。变量清单不完整的对比，跑得再多也只是把噪声量化了。

（一）固定变量清单。四组变量必须显式记录，不允许”和上次一样”这种默认：负载形态——读写比例、对象大小分布、生命周期是否整齐、是否跨线程释放；并发档位——线程数、在途请求数、CPU 配额与可见核数；数据规模——数据集大小与是否触及页级行为；环境——节点规格、镜像与 libc 形态、内存上限、透明大页设置、NUMA 拓扑。清单里每一项都必须在结果表里成为字段，否则复现时无从对齐。这里刻意不写具体实现版本号：一旦把版本写进结论，结论就只对该版本成立。

（二）预热与重复次数。预热要覆盖分配器的扩张期，也就是线程缓存建立、arena 增长、档位分布收敛所对应的那段时间；预热时长应当由业务到达曲线决定，而不是拍一个固定秒数。冷启动样本单独记录，不要混入稳态统计——很多”换分配器后启动变慢”的印象，来自把建立期算进了稳态。每组配置重复多次运行，取中位数而不是均值，并同时记录散布；多次运行要交替排列而不是连续跑完一组再跑下一组，以抵消节点漂移与温度影响。

（三）结果记录表模板。下表字段是最低要求，列值留空由实测填充；表中出现的任何阈值都是团队约定示例，不是通用标准。

（四）显著性怎么判断。在没有统计工具的场合，最低标准是三条：先看同配置重复运行的散布，把它当作噪声底；组间差小于噪声底时判为无差异，不写进结论；需要更强判断时，比较两组分布的重叠程度而不是单点数值，非参数思路（看中位数与整体分布是否重叠）比假想的正态检验更贴近实际，因为基准数据通常明显偏态。还有一条常被忽略的判据：如果结论只在某一个并发档位或某一个内存上限下成立，那它就是条件结论，必须在表里注明适用范围，不能写成通用建议。

七、工程做法与最小骨架示例

结论：全局分配器是”最后一次修改”，不是”第一次优化”。真正难的地方不在换，而在换完之后能不能退回来。

（一）只在明确瓶颈处替换。证据要同时过三道门槛：热点栈明确落在分配路径；已确认分配次数无法再降；现象已与环境量核对过（第四节）。三门槛缺其一，替换就是下注而不是决策。优先级永远排在前面的是少分配——复用缓冲、合并容器、消除中间对象、把每请求分配改为每工作线程分配。这些改动收益可解释、可局部回滚、不动全局，也不会给运维新增未知量。

（二）灰度与回滚杠杆。既然全局分配器是编译期决策，那么”改回来”就等于重新发版，杠杆太长，与故障时间尺度不匹配。可行做法有两类。第一类是把分配器选择上升为构建产物的一个维度：同时产出两个二进制，切换与回滚发生在流量入口，而不是配置中心——因为这里根本没有运行期配置可切。第二类更省心：不把决策放在全局，而是把专用分配器的作用域限制在阶段内，出问题时回滚的只是那个阶段的实现方式。判断标准很简单：回滚粒度是否小于故障影响面。做不到就不要在全局层面动手。

（三）把分配器写进构建产物的风险。跨语言边界是第一条：C 侧依赖用 malloc 分配、由 Rust 侧释放（或反之），一旦两侧落到不同实现，就是真正的内存损坏，而且常常只在少数路径上偶发。第二条是工具链假设：剖析器、调试器与内存审计工具对分配符号有各自预期，换了实现就要重新配对，否则采到的数据不可解释。第三条是环境漂移：镜像基础层或 libc 变更会连带改变行为，而你的代码一行都没动。第四条最隐蔽：依赖图或构建配置变化可能让实际生效的全局实现静默改变，现象是”什么都没改但曲线变了”。因此提出一条硬性工程要求——把”当前生效的全局分配器”打进启动日志，并作为环境指纹的一部分留存。

（四）专用分配器与无分配路径比换全局更常见。只读快照型做法是数据段一次装载后不再分配，读取时以映射视图或字节切片提供，热路径上只有读、没有分配。无分配路径型做法是把高频接口改造成借用与复用：切片视图、预分配的环形缓冲、按线程的对象复用。这两类的收益来自缩小契约面，不依赖任何分配器的实现质量；代价是需要重新设计接口，但改完就是永久收益，不会被下一次环境变更抹掉。自研存储里”自己管理一整块内存”的分配策略细节属于《Rust 实现简单 KV 存储》的内容，本文不重复。作一句横向对照：Go、Java、Node.js 的堆分配与回收由各自运行时和垃圾回收器统一负责，不存在”替换全局分配器”这个动作，那几篇讲的是另一套问题。

下面的决策流可以作为团队内的讨论底图。

flowchart TD
    A[内存或CPU形态异常] --> B{热点是否落在分配路径}
    B -- 否 --> C[回到业务代码继续定位]
    B -- 是 --> D{分配次数还能不能减少}

    I -- 否 --> C
    I -- 是 --> J[双构建产物灰度并确认回滚粒度]

最小骨架示意

骨架只演示两件事：契约长什么样，计数口径挂在哪里。它委托到系统分配器，因此行为与默认实现一致，差别只在多了一层计数。

读这段骨架要注意四点。第一，计数使用宽松顺序，只保证趋势可读，不保证跨计数器一致快照，负载重时会出现短暂的次数不匹配，这是设计取舍而不是 bug。第二，realloc 走默认实现时一次扩容会被记成”一次分配加一次释放”，看次数差值时要把扩容路径单独想清楚。第三，计数统计的是 Layout 的逻辑尺寸，不是实占字节，档位上取整与块头不在这里体现——这正是第五节里”次数差值稳定但 RSS 不回落”能成立的原因。第四，加一层计数就给每条分配路径加了成本，因此它属于诊断构建，不能常驻生产；真要长期观测，应该走采样或内核侧手段。若把这里换成 arena 实现，接口形状不变、语义要求变重：dealloc 必须自己判断这块内存是否属于本 arena，否则就退化成跨实现释放的错误。

八、反模式清单与对照表

反模式清单

结论：以下每一条都曾在真实项目里被当作”优化”提交，判断标准是它缺少证据链或缺少回滚杠杆。

  • 为了”性能玄学”换分配器：没有观测数据，只有传闻与”听说它快”。这类改动的典型结局是曲线波动一轮，无人能解释，也无人敢删。
  • 在生产环境一次性全量替换：没有双产物灰度、没有回滚杠杆、没有重新核对内存上限与 OOM 行为，把所有实例同时置于未验证状态。
  • 用分配器掩盖结构体的过度分配：本可以把每请求新建的缓冲改为复用，却选择换一个”更能扛浪费”的实现，把设计债务转交给运行时。
  • 基准环境不一致就下结论：压测机与线上节点规格不同、一个有内存上限一个没有，然后写进选型报告。
  • 把容器可见核数当作事实接受：不核对配额与实际线程数，缓存规模按宿主机核数铺开。
  • 只看吞吐不看内存形态：吞吐达标但 RSS 谷底逐轮抬高，属于延迟爆发的故障。
  • 跨语言边界的分配释放不做校验：混用两套实现的边界路径没有测试覆盖，只在特定分支上偶发。
  • 把分配器当作缓存机制使用：指望它替数据结构做驻留与复用，结果既不可解释也不可调试。
  • 在选型报告里写未经环境锚定的倍数：数字失去上下文之后，它就变成了谣言。

对照表

结论：这张表是本文的收敛点——类别之间不是优劣关系，而是假设关系。选类别等于选一组你愿意长期维持的假设。

分配器类别 设计取向 优势场景 代价与风险
系统 malloc 通用性与兼容性，进程内所有语言共享一份实现 低频大对象、跨语言边界密集、生命周期复杂、要求内存足迹可归还 高线程数下中心结构竞争；行为随发行版与 libc 变化，跨机器不可假设

小结

本文的骨干是三句话。第一，全局分配器是一份 unsafe 契约而不是配置项：alloc 与 dealloc 的 Layout 必须匹配、不能 panic、必须支持并发，编译器一条都不检查，而它是编译期单点决策，天然缺少运行期回滚杠杆。第二，三类分配器的区别在于把复杂度放在哪里——放在全局结构换取紧凑与可归还，放在线程本地换取低竞争并付出常驻缓存，放在生命周期假设上换取近乎零成本并放弃通用性；因此”哪个更好”永远取决于负载形态与环境量，特别是可见核数、线程数与内存上限三者是否一致。第三，动手顺序不可颠倒：先减少分配次数，再用同环境对照实验把差异与噪声底分开，最后才考虑全局替换，并且用双构建产物把回滚粒度压到故障影响面之下。观测上请记住两个口径：RSS 与 VSZ 不可互相换算，分配与释放的差值稳定但持有字节持续上涨，指向的是取整与碎片而非泄漏。全文没有给出任何性能倍数，也没有列举实现版本号——这类数字一旦脱离环境就失去意义，而环境是可以被记录、被核对、被复现的。本文以 2021 edition 的语义书写，读者在做具体决策前，应当把参考资料里的契约文档与内核接口逐条核对一遍，再按第六节的模板把变量固定下来。
