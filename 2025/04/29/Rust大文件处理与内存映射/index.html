Rust 大文件处理与内存映射

本文属于《Rust 学习路线》第 53/68 篇
上一篇系列目录下一篇

文件大小决定不了读法，访问模式才可以。本文梳理整体读入、流式读与内存映射三条路，讲清映射的机制代价、生命周期契约、写侧语义与内存压力口径，并给出对照表与两段骨架，适合要写日志分析、批量导入或格式读取逻辑的 Rust 后端读者。

先把选择说清

处理大文件时有一个容易被默认接受的结论：内存映射比读文件快。这不成立。分界线不是文件多大，而是访问模式：会不会反复访问、顺序还是随机、要不要跨进程共享、能否接受峰值驻留不受控。

  • 整体读入：内容一次性放进 Vec<u8>。只适用于长度确定、远小于可用内存且之后反复随机索引；代价是峰值内存等于文件大小，中途失败即重来。
  • 流式读：带缓冲的迭代读取，缓冲区与文件大小解耦。适合日志、CSV 这类过一遍就走的扫描；驻留可控、没有缺页，代价是要拷进自己的缓冲区并处理短读与半条记录。
  • 内存映射：给文件的一段窗口建虚拟地址区间，靠按需缺页搬页。适合随机访问、工作集远小于文件或需跨进程共享；可以只碰用到的部分，代价是把访存变成可失败、可回收、难预算的内核操作。

“更快”要拆开看：映射省下的那次拷贝在顺序大块读里已被预读摊薄，而每个页面的首次访问都要多付一次缺页处理；收益来自少碰页与共享页，不来自读得快。

流式读的工程做法

结论：把缓冲区分配移出循环，剩下的都在切分策略和短读处理上。

  1. 缓冲区只分配一次。用带容量的缓冲读取器或手写字节向量，都要在循环外建立、循环内复用；太小则系统调用次数淹没解析逻辑，太大只是浪费驻留（团队约定示例：从 1 MiB 起步，按压到设备上限来定）。
  2. 短读是常态。返回少于请求量完全正常，只有返回零才表示到了文件末尾；把短读当错误处理是最常见的缺陷来源。
  3. 切分不等于分配。按行解析复用同一个字符串变量，读完一条清一次；按变长记录维护游标，把残余挪到头部再补读。跨迭代新建缓冲区会把成本请回来，抵消流式方案的全部优势。

一句划界：这里的记录是磁盘上的定界或带前缀长度的记录，网络分帧归《Rust 网络编程实战》。

内存映射的机制

结论：建立映射只是登记一个虚拟地址窗口，真正的成本在第一次碰到每一页时才发生。

  • 虚拟地址窗口。内核只记录这段地址对应文件的哪段范围，不读数据也不复制：创建很快，也不会立刻占用等量物理内存，花的是虚拟地址预算。
  • 按需缺页。第一次读某页内地址时触发缺页：页已在缓存就挂进页表，不在就先做磁盘读取与预读。这解释了首次遍历慢、之后快，也是只碰用到的部分能成立的机制。
  • 页缓存与写回。映射页与普通读同一文件命中的是同一批物理页，这就是省掉一次拷贝的真实原因；写映射页改的也是这批共享页，由内核在内存压力、定时回写或显式同步时写回设备。

省下的拷贝是真的，代价也是真的，这才是映射不是总是更快的理由：

  1. 缺页是同步的。一次普通下标访问可能变成一次磁盘等待，时机不可预测，延迟分布因此变成双峰。
  2. 页会被回收；工作集超限就反复缺页，出现逻辑上读一遍、物理上读几遍的抖动，而预读按顺序假设工作，稀疏访问时只碰 8 个字节也要搬一整页。
  3. 预算不可见：自己的缓冲区知道占了多少，映射只能问内核。全局分配器不在本文范围，见《Rust 内存分配器选型》。

机制与语言版本无关，新 edition 已发布也不改变上面的结论。

生命周期与危险边界

结论：映射是否还在有效期内，取决于文件在映射期间有没有保持原样，而这件事类型系统兜不住。

按 POSIX 语义，映射建立后不依赖文件句柄存活，它绑定的是那个 inode，不是路径名：句柄关掉不等于映射失效，句柄还在也不代表路径上的内容仍是映射时那一份。

两种破坏方式：

  • 被截断。窗口超出文件新长度后，访问超出部分不是越出窗口，而是落在窗口内一个没有后备数据的偏移上，进程收到总线错误直接终止：它不是 panic，也不经过错误返回值，Result 接不住。
  • 被替换。先写临时文件再重命名覆盖是很常见的更新手段，而旧映射仍指向旧 inode，路径上的新文件与内存里的旧内容长期并存，结果是静默的数据错乱：每一步都看起来成功，比崩溃难查。映射之后被追加同样只能重建窗口。

为什么必须是契约而不是类型：所有权和生命周期能挡住同进程内的悬垂引用，却看不见进程外的一次截断或另一个线程的一次重命名，编译器无从校验这条边。所以这类 API 把建立映射的入口做成不安全入口，把文件在映射期间不被截断、不被替换、长度不变交回调用方保证，并让调用方在建映射前记下文件身份、用完再核对。怎么把契约包成安全接口归《Rust unsafe 与裸指针实践》，本文只到为什么需要契约这一步。

写侧：脏页、刷新与并发

结论：写映射省掉的是拷贝和系统调用，省不掉的是持久化语义。

  • 脏页与刷新时机。写映射页把页标记为脏，内核在内存压力、定时回写或显式同步时才交给设备：写合并归内核掌控，代价是真正下盘的时机你说了不算。
  • 写回不等于落盘。回写只表示数据交给了设备；要崩溃后仍可见就需显式同步，文件新建或刚扩展时还牵涉元数据，部分系统上同步返回也不等价于介质已确认。可靠性有要求时，同步点是协议的一部分，不是可选优化。
  • 崩溃一致性。页与页之间写入顺序不保证，可能出现记录新而索引旧；恢复要靠应用层的顺序约定、校验字段和原子替换。自研引擎怎么落盘、怎么建索引归《Rust 实现简单 KV 存储》。
  • 并发与锁。同进程多线程共享同一批页，但字节重叠写仍是数据竞争；跨进程只有共享映射互相可见，私有映射是写时复制，改动既不回落文件也对别人不可见。文件锁保护的是访问意图，拦不住已在内存里的那一页被改掉。

内存压力怎么表现

结论：映射大量文件时的占用要分三个口径看，混在一起就会得出内存不够的错误结论。

  • 驻留集：当前真正在内存里的映射页，随缺页上升、随回收下降。它高不表示不可释放，用它反推自己映射了多大必然失真。
  • 页缓存：文件页属于可回收内存，压力下先被淘汰。典型误判就在这里——监控显示可用见底，但真有分配需求时内核很快腾出空间。
  • 匿名内存：自己的缓冲区与堆数据，不可回收，只能换出或在超限时被终止；这正是流式读要负责的部分，优点是数值可控。

观察口径只讲方法：把分配多少、驻留多少、可回收多少三条曲线分开看；用缺页与回收页数的增量判断趋势；判断还能不能再多映射一个文件时看淘汰速率，不看当前空闲值。划界一句：结构体排布与缓存行归《Rust 内存布局与性能分析》，Node.js 与 Go 的内存统计是各自语言的问题。

什么时候必须回到流式

结论：四类负载下流式读或整体读入更稳，映射只是看起来方便。

  1. 跨机文件系统与网络存储。缺页变成同步网络往返，随机访问把一次顺序读拆成一串小请求，吞吐塌陷得很突然；这类挂载点还有陈旧句柄、语义弱化、超时后页读不上来等更糟的失败模式。
  2. 需要严格顺序写。映射不保证页之间的写入顺序，落盘时机也不由你控制；要表达前一条落盘成功、后一条才可见，顺序写加显式同步更直接。
  3. 容器内存限额吃紧。限额计的是驻留总量，映射页被淘汰会引发重复缺页和吞吐雪崩；解释这些其实是可回收的页缓存，救不了已被终止的进程。
  4. 随机访问比例低。整份文件只过一遍，映射剩下的只有缺页开销与预算不透明。

另有两种情况也该选流式：文件持续被追加、需要跟着读；在线路径对延迟有硬指标。

常见坑清单

结论：映射的问题几乎都出在边界换算和以为不会失败。

  • 把 4 KiB 当成唯一的页大小。页大小由平台和内核决定，而映射的文件偏移必须是页大小的整数倍：从文件中间建映射时要把偏移向下取整到页边界，再把页内偏移加回指针，算错一位就读到整条错位的数据。
  • 基址换算遗漏。记录起点不在窗口开头时，所有下标都必须带同一个基址；这类错误常藏在深层调用里，只在大文件上暴露。
  • 把映射当无上限缓存。映射一百 GiB 不会立刻占一百 GiB，但完整遍历一次就等于把它塞进回收队列：窗口是虚拟地址预算，不是内存预算。
  • 忽略部分映射失败。建映射成功不代表一路访问都成功：中途可能因截断、坏块或网络存储不可用而终止进程，所以要把访问限制在已知长度内；空文件与零长度窗口同理。
  • 混淆两类错误信号：地址越出窗口与窗口内没有后备数据原因不同，别按同一条线索排查。

三种方式对照

小结

本文的结论是把选择建立在访问模式上：顺序全量扫描优先流式读，映射的价值在随机访问、工作集小和跨进程共享，而不在文件大小。流式读的要点只有一条——缓冲区在循环外分配并复用，把短读当常态。映射要记住三件事：它把访存变成可失败、可回收、不可预算的操作；它的生命周期是编译器看不见的契约，文件被截断或替换就是危险边界；写回不等于落盘，顺序与崩溃一致性要应用层自己表达。落地建议也是三条：按文件长度和随机访问比例分派，把映射窗口限制在已知长度内并在用完时核对文件身份，把驻留、可回收与匿名三类内存分开观测。
