RAG 文档解析实践

本文只管 RAG 语料入库之前的解析层：把磁盘上那一堆原始文件，变成检索系统能够消费的”带结构的文本单元”。分块怎么切、召回怎么排、答案怎么生成，都不在本文范围内。这一层平时没人提，坏起来却到处显形，所以值得单独拆开讲清楚：每一类文档能期望什么、不能期望什么、坏了怎么发现、发现了怎么修、修完怎么重跑。

解析层的边界

结论先说：解析层的产出物是”带结构的文本单元”，到这一步为止，后面的一切都不归它管。

什么叫”带结构”。一个合格的文本单元至少要能回答五个问题：这段文字自己是不是说完整了；它在原文里是什么层级位置；它属于哪份文件哪个版本第几页；它的内容是从哪种版式元素来的（正文、表格、列表、脚注还是图注）；以及它有多可信。这五样齐了才叫带结构的单元，缺任何一样都只是字符串。把它们补齐是解析层的责任，而不是下游的补救手段。

边界之外的事情，本文只划一句，不展开：

  • 分块粒度与召回优化归《RAG 分块策略与召回优化》，本文只保证交出去的单元带结构。
  • 端到端链路与工程化落地归《RAG 检索增强生成实战》和《RAG 工程化落地》。
  • 检索层的质量指标定义归《RAG 检索质量评估》，本文只讲解析层自己的度量口径。
  • 图表与图片以原图形态参与检索的部分归《多模态检索实践》，本文只负责判断”这块内容该转成文字还是保留原图”。
  • 从文本单元里抽实体与关系建图谱归《GraphRAG 知识图谱增强》。
  • 密级与可见范围的判定和风险处置归《大模型应用安全》，本文只负责把字段带下来并留出校验位。
  • 单元入库之后的混合检索与重排序归《RAG 进阶：混合检索与重排序》。

为什么要把边界划得这么硬：解析层最典型的失败模式，是它顺手把下游的事情做了。为了凑长度把整张表格压成一行，为了”读起来通顺”把脚注合并进正文，为了减少条目数把跨页内容粘成一段。每一步看着像在帮忙，实际是提前把版式信息烧掉了，等下游想恢复时已经无从下手。本文反复出现的建议都是这一条：宁可能力不足而保留原始结构，也不要自作聪明地替下游做决定。

解析错误为什么总在下游冒充模型问题

结论先说：解析错误是 RAG 里最靠上游的故障源，它同时污染索引、召回和生成三处，而且在下游看起来一律像模型问题。

索引侧。错序的段落把两个不相干的主题焊在一个单元里，向量表示被平均成一个”谁都不太像”的语义中心；单元入库时就坏了，后面用多好的嵌入模型都只是把坏结构忠实编码下来。更隐蔽的是重复污染：每页重复出现的页眉页脚形成一批高度相似的单元，彼此距离很近，会把同主题的正文单元挤开。

召回侧。召回为空时，团队第一反应通常是”嵌入不行”或”用户问法太口语”，而真实原因经常是原文被拆得太碎：答案需要的条件分散在三个单元里，任何单单元检索都凑不齐。召回非空但答错，也常常是命中单元本身残缺——标题与正文错位，看着命中了主题，实际拿到的是目录页。

生成侧。模型面对残缺文本不会承认残缺，它按语言规律把缺失部分补全，这正好是”幻觉”的表象；原文是表格拆散后的散字时，模型给出错误数字，看着像算术不行，其实是行列对应关系在入库前就丢了。

三种典型现象值得单独记下来：答案里的章节编号和真实文档对不上（像是瞎编编号，其实是层级还原失败）；引用页码存在但翻过去找不到那段话（像是幻觉引用，其实是单元与页码绑定错位）；同一份文档同类问题时有时无（像是温度问题，其实是解析对某个版式不稳定）。

怎么把它们区分开，我的习惯是一条固定顺序：**先查语料，再查召回，最后才查模型。**具体三步：把答案引用的单元原文打印出来，看它是否自洽、是否残缺、有没有版式噪声，这一步不需要模型参与；回源文件同一页目视比对，看差在少内容、错顺序，还是多了不该有的东西；前两步都干净了，才值得怀疑分块、检索或生成参数。把这条顺序写进工单模板，比争论”是不是模型不行”有效率得多。

回应一个常见反驳：模型越来越强、上下文越来越长、还能直接看图，解析层是不是可以省了。这些进步只让解析错误更容易被”蒙对”，而不是被修好——DeepSeek-R1、二月发布的 Claude 3.7、三月底进入预览的 Gemini 2.5 Pro 把可读输入与视觉能力又往前推了一步，但蒙对的结果无法追溯、无法复现、无法引用，而 RAG 的全部价值恰恰落在可引用上。解析层的活儿不会消失，只是从”必须做”变成”必须做好并证明自己做了”。

每一层文档能给什么：分层与降级方案

结论先说：文档类型分三层——结构化、半结构化、无结构；每层的可期望产出完全不同，解析策略必须按层设定，不要用处理结构化文档的期待去处理扫描件。

结构化文档包括 Markdown、HTML、XML 这一类，层级关系写在语法里：标题靠标记，列表靠缩进和序号，表格靠单元格边界，代码块靠围栏。对这一层可以期望完整章节路径、准确块类型、可靠的表格二维关系与可回链行号，也几乎没有降级空间，做不好只能归因于解析器或写文档的人。真正的坑是”看起来结构化实际不结构化”：Markdown 表格列数不齐，HTML 标题层级被排版牵着走（H3 当大字、H2 当小标签），XML 字段名与业务含义无关。语法合法但语义骗人，只能靠后面的质量度量把假结构化筛出来。

半结构化文档包括 Word、PPT、Excel，也就是 OOXML 这一族。它们的层级不写在语法里，而写在样式里：标题靠段落样式或字号字重，列表靠编号定义，表格靠边框线。可以期望中等产出——标题层级能还原大半、表格二维关系能保住，但要注意样式名五花八门、正文里手打的”目录”和真实大纲无关、PPT 的信息大量在备注页与文本框和 SmartArt 图形里。降级方案：样式聚类失败时退到”段落纯文本加文件名加位置”，层级字段留空并打降级标记；图形内文字拿不到时把整张幻灯片标为低置信单元，同时保留缩略图让多模态那条路去补。

无结构文档包括扫描件 PDF、图片、录音转写。它们没有可依赖的层级表达，标题靠视觉（居中、字号、加粗）或靠约定（编号”3.2.1”）出现，段落边界靠空白而不是标记，因此只能期望弱产出：页级文本、模糊边界、需人工确认的层级。降级方案按代价从低到高排：第一档，保留页级单元不硬拆段落；第二档，只保留”标题层骨架加页级正文”，层级关系标为猜测；第三档，正文完全不可信时只入库文件名、目录位置和可见范围，让系统明确回答”这份文件存在但我读不了”，而不是给出错误答案。录音转写属于同层特殊情况，要额外处理说话人分离、时间戳和同音术语错误。

分层之后有个很实用的判断：同一批语料里，不同层的文档要走不同的质量口径。把结构化文档的标准和扫描件的混在一起算一定失真——扫描件拉低数字，团队就去过度优化；结构化文档里藏的假结构化，混在噪声里看不出来。下一节 PDF 之所以是重灾区，正是因为它同时横跨三层里的两种形态。

PDF：重灾区的六种坏法

结论先说：PDF 的问题不是解析器不够好，而是它的内部表示和读者的阅读顺序天然不一致；六种坏法都要有各自的处置，不能指望一个通用参数解决。

版式还原：先问段落边界靠什么表达

结论先说：动手选解析策略之前，先回答一个问题——这份文档的段落边界靠什么表达。边界线索决定了可用手段，线索判断错了，后面所有优化都是白费。

一份文档不会只用一种方式表达”这里是一段结束、那里换了一段”。可能的载体有七种：空行、首行缩进、编号、字号字重、块级标记、页面坐标、内容流顺序。结构化文档主要靠前三种加块级标记，半结构化文档靠前四种加样式，无结构文档只剩坐标和空白。所以”边界靠什么表达”实际是在问”我能拿到多强的证据”。

下面这张表是本文最想让读者带走的东西之一：把线索和手段一一对上，遇到具体文档时先辨认线索，再挑手段。

两条使用原则值得单独强调。

第一条，双通道校验。任何依赖几何或样式的判断都要有一条独立证据交叉验证：列分组用字号一致性检查，层级判断用编号模式检查，段落合并用行距检查。两个通道一致时把置信标为高；不一致时保留两种候选结构、标为低置信并进入人工抽检池。让解析器单通道硬猜是扫描件质量问题里最难查的一类，因为每次猜的结果都不一样。

第二条，推断不出来的时候不要造边界。这一条反直觉，因为更粗的输出看着像失败。正确做法是降级到上一层结构：段落定不出来就交页级单元，层级定不出来就只交”标题层骨架加页级正文”，连标题都定不出来就交文件级占位并标注读不了。粗结构只是召回粒度变差，猜错的结构让引用回链失效——前一种是能力问题，后一种是事故。

表格、图片与转写的处置

表格三档：转文本、转二维、转行级描述

结论先说：表格处理只有三档——原样转文本、转 Markdown 或 CSV、转行级自然语言描述；三档对召回与生成的影响不同，选择条件是”用户会问单行事实还是会问聚合”。

选择条件一句话：列数少且行独立用第一档，需要人工核对或表格规整用第二档，提问以单行事实为主用第三档；聚合频繁出现的表格，无论哪档都要额外保留表级单元。跨页表格先合并再处理，判据是表头行重复加列宽一致；合并失败时按页保留并标注”表格不完整”。

图片与 OCR 的边界

结论先说：判断标准只有一条——这段视觉内容是不是读者会直接引用的文字；会被引用的就 OCR 入库，不会被引用的就保留原图走多模态检索（图片以原图参与检索的部分归《多模态检索实践》，本文不展开）。

一个高频踩坑点：图注和图片正文要分开。图注本身就是有效的可检索文本，即使图片走多模态，图注也该作为独立单元入库并带上”所属图”的关联字段。只在 OCR 成功时才留下内容，会造成大量”图片有图注却检索不到”的空白。

低置信度内容的处理原则是打标记而不是直接入库，也不是直接丢弃，分三步：给单元写解析置信与原因（OCR 分数低、几何冲突、字体映射可疑、整页噪声）；低置信单元正常参与索引，但生成侧引用它时必须在提示里显式警示”此处原文识别不确定”，并且不把两个低置信单元组合成看起来互相印证的证据；同一区域反复被抽检出问题，整份文档退回人工并从可回答集合里摘出。这套标记就是下一节元数据契约的一部分。

录音转写的坑同类：转写文本天然没有段落边界，靠停顿和时间戳分段；说话人分离错误会把两个人的话并成一句；术语同音字错误在专业文档里很集中。处置是转写单元必须带时间戳与说话人字段，术语用词表定向校正，置信按句存储——整段高置信不等于每句都对。

元数据契约：每条都要能被引用回来

结论先说：元数据不是日志装饰，它的唯一验收标准是”从答案里的任意一条引用出发，能机械地定位回原文那一段那一页”；定位不回来的字段等于没有。

三条契约规则必须写进实现，否则字段清单会变成形式。

第一条，允许值为空，不允许键缺失。缺键的后果是所有消费方各自处理”字段不存在”，同一个空值在不同代码分支里被解释成不同含义。空值统一用显式 null 或约定哨兵，并把”哪些字段可以为空”写清楚。

第二条，位置字段要成对且说明优先级。页码、行号、字符偏移三种定位适用文档不同，但必须至少有一种能定位到块：PDF 用页加几何框，纯文本用行或字符偏移，转写用起止时间。要写清”有页时以页为准，无页时以偏移为准”，否则回链校验会误报。

第三条，pipeline_version 与 degraded_reason 是重跑的依据。没有流水线版本，无法回答”哪些单元是修复前的产物”；没有降级原因，无法在质检时把降级单元单独筛出来复核。这两个字段在实际项目里最容易被省略，因为写的时候看不出用途，出事故时才想起。

失败样本回收闭环

结论先说：解析质量靠抽检和反馈闭环提升，不靠一次写好解析器；闭环要能发现、能归因、能进回归集、能在修复后精确重跑。

发现入口有三个，覆盖面互补，缺一个都会漏一大类问题。

抽检：按版式特征分层抽样（是否多栏、是否扫描、有无表格与跨页表），人工比对源文件与解析产物。分层比随机重要，因为解析问题几乎总是版式相关的，随机抽样会让少数版式永远抽不到。同批样本还要跑”回链可达性”自动校验：把每条引用按定位字段解回原文，解不回就是事故，不需要人看。

召回为空：一类被低估的信号。某类问题反复出现却从未命中，除了问法不匹配，常见原因是那部分内容压根没以可检索形态存在（在图片里、在域代码里、在备注页里）。把零命中查询按主题聚类去重后人工看一遍，是很便宜的缺陷探测器。

用户点”没答案”与引用点开就走：前者显式、后者隐式——用户点进引用发现原文不是那么回事，是典型的解析错位。两类信号要落到同一张问题记录表，按 doc_id 与版式特征聚合。

归因要有固定标签体系，否则讨论无法收敛。建议至少记下面几类，标签的意义在于统计：某一类占比持续偏高，说明问题在解析策略而不在某份文档。

进回归集这一步决定闭环是不是真的闭上。做法是把出过问题的原始文件保留一份不可变副本，连同”这份文件期望产出什么结构”的快照（关键段落数、章节层级、表格数量与形状、回链可达性）固化成用例。解析代码改动必须跑全量回归集，并把与上一版的产出差异列出来看。没有回归集的解析层永远处于”修一个坏三个”的状态，因为版式种类之间的处理规则互相牵制，改一处坏一片的概率极高。

修复后重跑索引要精确而不是全量。按 pipeline_version 与 degraded_reason 筛出受影响单元集合，重跑这批文件的解析与入库，新旧单元共存一段时间做对比，确认回链与覆盖率达标后再把旧 revision 标为 retired 并下线。重跑窗口里的”新旧并存”是下一个主题。

增量与版本：别让新旧并存

结论先说：更新的最小单位是”文档版本”，不是”文件”；只要按文件路径判断增量，就一定会出现同一文档两个版本同时可召回的污染。

同一份文档更新后如何避免新旧并存，靠三个动作。第一，覆盖写以 doc_id 与 revision 为键，不以文件路径或文件名为键——改名、移动目录、重新导出都只该产生同一 doc_id 的新 revision，而不是另一份”文档”。第二，content_hash 一致的直接短路，不重复解析也不重复入库，但要更新扫描时间，否则无法区分”没变”和”没检查”。第三，新 revision 入库成功后立刻把旧 revision 的单元标记为不可召回，再异步清理；”立刻标记、稍后删除”的顺序很重要，先删索引再标记会在删除过程中留下半份可召回状态。

删除的传导要显式建模。源文件被删而索引单元还在，是引用失效最直接来源：答案引用了一个打不开的文档，用户点开是空白。做法是写入墓碑记录（doc_id、删除时间、原因），索引侧按 doc_id 批量下线对应单元，同时保留墓碑供审计与后续”文件回来了”的重挂。没有墓碑的下线无法区分”删了”和”解析失败没入库”。

权限变更常常不需要重新解析，只需要重写元数据：受影响的是 acl_class 与 visible_scope 两个字段，走”读旧单元、更新字段、验证过滤生效”的轻路径比重解析便宜得多。要注意权限收紧的下线时效必须显著短于内容更新时效——内容旧了只是答案不够新，权限没下线是泄露风险。本文只负责把字段带下来并保证检索期读得到，过滤实现与越权处置归《大模型应用安全》。

文档拆分与合并是最容易被漏掉的情况：一份大手册拆成十章、几份规范并成一份汇编，历史引用会断链。处理办法是维护映射（旧 doc_id 指向新 doc_id 加区间），让旧引用仍能解析到新位置；同时给旧文档设 version_status 为废止并保留可查，别在用户还在引用它时物理删除。

质量度量口径：解析成功率怎么定才不自欺

结论先说：不要用”文件解析成功率”作为口径——一份 300 页文档坏 40 页仍然算成功；要用”可引用段落覆盖率”，并配人工抽检记录表。

文件数口径为什么自欺，原因有三层：分母不按重要性加权，一份核心业务规范和一份过期通知在计数里等权；粒度太粗，长文档的内部失败被折叠成一个成功；结果不可归因，知道”文件层面大多成功”对下一步做什么没有任何指导。

覆盖率口径至少包含四个观测量，本文出现的数字一律是示意值、阈值只算团队约定示例，不构成任何基准：

解析产物的中间结构、降级路径与整条流水线的形状，用下面三段来收束。代码是伪接口示意，不代表任何具体库的 API，也不绑定版本。

小结

本文只讲了一件事：解析层的产出物是”带结构的文本单元”，结构没保住，后面检索与生成做得再好，也只是把坏输入编码得更精致。三条结论带走。第一，解析错误一定在下游伪装成模型问题，所以排查顺序必须是先查语料、再查召回、最后查模型。第二，动手之前先回答”这份文档的段落边界靠什么表达”，按线索挑手段、双通道校验，判不清就降级到更粗但引用可靠的结构，宁可不猜。第三，元数据只有一条验收标准——从答案的任意一条引用出发能机械回到原文那一段，回不去的字段等于没写；覆盖率按可引用段落算而不是按文件数算，坏样本进回归集，修完按流水线版本精确重跑。落地顺序建议：先把回链可达性做成自动校验，再补低置信标记与降级路径，最后才逐版式优化解析规则。
