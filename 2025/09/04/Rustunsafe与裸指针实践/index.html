Rust unsafe 与裸指针实践

本文属于《Rust 学习路线》第 54/68 篇
上一篇系列目录下一篇

本文面向已经写过一些安全 Rust、第一次要往代码里落下 unsafe 的读者。读完应能回答三件事：unsafe 把哪部分责任从编译器转移到人身上，一段不安全代码要写下哪些前提才算交代完整，什么时候不该写它。示例都是说明性骨架，不涉及绕过借用检查的技巧。

unsafe 到底改变了什么

unsafe 常被误解成“关掉安全检查的开关”。更准确的说法是：它把一部分原本由编译器承担的验证责任，转移到写下这行代码的人身上。只能在不安全上下文（unsafe context）里书写的东西有两类，不安全操作（unsafe operation）——例如裸指针解引用、调用不安全函数、访问可变静态变量、实现不安全 trait——以及 unsafe fn 本身。前者编译器从“替你证明它成立”改成“你说成立，我照办”，后者要求你向调用方说清条件。换句话说，unsafe 让你表达编译器无法验证的不变量（invariant）：检查没有被删除，只是搬到一处由人负责、且能写进文档的地方。

责任既然转移了，unsafe 的核心用途就是实现安全抽象：用一小块被论证过的不安全代码，换回一大片可被编译器检查的安全接口。性能常常只是某些结构正确实现之后顺带得到的结果，把它当作 unsafe 的意义是本末倒置。

2021 与 2024 edition 有一处口径不同。2021 edition 里 unsafe fn 的整个函数体默认就是不安全上下文，内部的裸指针解引用等操作不必再套一层 unsafe 块；2024 edition 取消了这个默认，unsafe fn 体内的不安全操作必须显式包在 unsafe 块中才能通过编译。该口径随 Rust 1.85 于 2025-02-20 发布生效，不是 1.86 之后新增的东西。改动不改变任何一段代码的安全性质，只是让“这里正在做不安全的事”逐行可见。

未定义行为的类别

unsafe 要严肃对待，是因为前提一旦没被保证，程序进入的是未定义行为（undefined behavior，常写作 UB），而不是抛出一个错。UB 不是一条错误信息，它的后果是：从那一刻起，编译器此前基于“这段代码合法”所做的一切推理全部失效，读到旧值、跳过你以为一定会走的分支、优化掉你以为一定会执行的清理，都可能发生：

  • 解引用空指针：那个地址上没有任何对象。
  • 解引用悬垂指针：所指对象已经被释放或移动走。
  • 解引用未对齐指针：地址不满足对齐要求，某些架构直接陷入。
  • 读写已释放的内存：那段字节已归还分配器，此刻属于别人。
  • 制造多重可变别名：同一对象同时有两个可写入口。
  • 构造非法值：超出枚举取值范围的整数变成枚举，match 走进不存在的分支。
  • 数据竞争（data race）：两个执行流访问同一内存，至少一个是写入，中间没有同步关系。
  • 违反函数前提：把重叠区域传给要求不重叠的接口。
  • 违反 panic 路径上的额外约束：约定不会展开（unwind）的边界上真的展开了。

把它看成前提失守时的几种失效方式即可，后文每段示例紧跟的前提清单就在替其中几项把关；借用检查为何能挡住大半问题，往期《Rust 借用与生命周期》已讲，不展开。

裸指针、引用与 NonNull

裸指针（raw pointer）有 *const T 与 *mut T 两种形式。它们和引用的差别不在写法而在承诺：&T 与 &mut T 各自带着编译器已经证明过的三件事——对象此刻有效、生命周期内不会被释放或移动、&mut T 还保证这段时间只有它一个可写入口。裸指针三件都不保证：它只是一个地址加一个类型标签，不保证所指对象存在、不保证独占、也不参与生命周期推导。

关键在于：裸指针本身并不是问题。创建、复制、比较、存进结构体、传给别的函数都不需要 unsafe。真正要担责的是两件事，一是解引用，二是你围绕别名做出的假设，例如“这段时间没有人会改写这块内存”；前者编译器要你显式声明，后者编译器完全无从得知。

这段骨架要成立，需要同时满足：same 所说的地址上此刻确实有一个 u64；该地址满足 u64 的对齐；从借出到读取这段时间里原对象没有被释放、没有移动、也没有别的可变入口写入过它；读出的位模式对目标类型是合法值，这对 u64 总成立，换成枚举或引用就不一定。顺带划界：Go 的 unsafe.Pointer 允许与整数来回转换但有一套明文规则，Rust 裸指针背后没有垃圾回收器，把地址存成整数再转回来时没有机制替你保住那块内存，两者规则不同，本文不比优劣。

NonNull<T> 要解决的正是非空与协变这一组组合：它保证地址不是零，同时按文档口径对内部类型保持协变，因此在安全代码里足以表达“这里一定指向一个有效对象”，常见于自行实现拥有内存的类型时替代裸的 *mut T。注意它只保证非空这一件事，不保证对齐、不保证对象存活、也不保证独占，那些仍是外层类型要负责的前提。

MaybeUninit：有效但未初始化

分段构造一个对象时，很自然的想法是先用零值占位再逐字段填。这个做法不成立，因为某些类型的零位模式本身就是非法值：引用不能是空地址，枚举判别式必须落在声明过的取值里，Box 不能为空。用一串零字节假装它们是合法实例，从构造那刻起就已经是未定义行为，哪怕马上就把它覆盖掉。

MaybeUninit<T> 表达的是另一种状态：这块内存有效、大小和对齐都按 T 准备好了，但里面还不是一个 T。它不要求内容有合法值，也不会在自己离开作用域时替内部值调用 drop。

骨架背后是三步：把值写入这块内存；确认 T 的每一个字节都已经被写过，没有留空；最后调用 assume_init 交出一个 T 并接管所有权。前提是：assume_init 只能在三步都完成之后调用；初始化路径若中途提前返回或发生 panic，该路径绝不能调用它，也不能把这块内存当成完整的值交给下游；交出之后原来的 slot 不该再被使用。

谁负责 drop 最容易漏。assume_init 成功之后，释放由那个 T 正常完成；若没有调用它，MaybeUninit<T> 不会自己去 drop 内部内容，值已经写进去却当作未初始化丢掉，结果就是资源泄漏而不是双重释放。抽象代价归往期《Rust 类型系统与零成本抽象》，本文只说 MaybeUninit 这一点边界。

从裸指针到引用的前提

把裸指针变成引用，是日常不安全代码里频率最高也最容易写错的一步。造出引用之后，它立刻按引用的规则被借用检查使用，编译器不再质疑它——因为是你替它作了保。可核对的前提恰好五条：指针非空；地址满足该类型的对齐；所指内存足够放下一个 T 且内容已是合法的 T；在造出的引用的整个存活期内不存在第二个可变入口；期间那块内存不被释放也不被移动。

模板的价值在于它写的是必须被保证的前提，而不是“这段没问题”：前者别人可以核对、可以反驳、可以在调用点检查，后者只是作者的自我安慰，读者无法对它做任何事。SIMD intrinsic 那一类依赖本机指令集的不安全操作，其前提怎么写归往期《Rust 与 SIMD 优化》，本文只强调它遵守同一套“前提必须可核对”的规矩。

把 unsafe 收在边界内

健康的形态是公开 API 安全、内部使用 unsafe：签名不带 unsafe，调用方按普通规则使用，不安全操作压在实现里，前提由类型的内部逻辑保证。相反的形态是 unsafe fn 满天飞，把前提甩给每个调用点。所以每写一个 unsafe fn 都该问：能不能改成普通函数加内部 unsafe 块？能改，说明前提在本函数内就能核实，没理由让调用方替你承担；改不了，说明你真的在要求调用方提供某种全局知识，那就必须写进文档。

比文档更耐用的做法是把不变量固化进类型：构造时校验、字段私有、只暴露安全方法。这样前提只在构造点检查一次，之后每个方法体都能直接依赖它。

骨架省略了 Drop：真实实现里这条不变量要靠它兑现，否则漏掉的是资源泄漏，类型名也会开始说谎。文档上的配套规矩是：有调用前提的 unsafe 函数和宏、不安全 trait 的实现都该写 Safety: 段落，写清调用方必须保证什么——指针要非空还是要对齐、闭包能否重入、会不会展开，而不是笼统的“请谨慎使用”。不变量写进类型名和模块说明，比散落在函数体里的注释更难在一次重构后变成假话。

校验工具各自能查什么

没有一种工具能替你判定一段 unsafe 是否正确，它们只是把某几类错误变成会响的警报，盲区就写在下面这张表里。值得单独记住：静态分析类只看程序文本，覆盖受限于对控制流与跨函数关系的建模深度；运行时检测类只报告被执行到的部分，没跑到等于没检查；模糊测试（fuzzing）靠随机性，一次通过既不是证明也不算承诺。解释执行式的 UB 检查与 unsafe 语义贴得最近，代价是慢，所以只在小范围跑。

并发边界与外部交来的内存

数据竞争最难查，原因不在工具不够，而在它需要两个执行流恰好在同一段时间窗口里撞上。跑上很多次也可能一次都没碰上，所以“跑过没问题”对并发 unsafe 几乎没有说服力：它只说明那一次调度顺序没触发问题，而调度顺序并不在程序承诺的范围里。真要同步，先选原子与锁这类语义明确的东西，而不是先手写裸指针再加标志位；原子与内存序归往期《Rust 无锁编程与原子操作》，共享所有权与临界区的用法，同期讲 Arc 与 Mutex 的那篇已经讲过，本文只划这条界。

手工实现 Send 与 Sync 是另一处被低估的责任。平时这两个标记 trait 由编译器按字段推导，一旦手写，你实际是在向整个语言承诺：经由这个类型跨线程传递或共享那块内存不会有数据竞争，也不会让同一对象出现两个可变入口。承诺没有配套检查，编译器此后照它办事。

外部交来一块内存时，长度、对齐、所有权、生命周期四件事都要在边界上显式约定，缺一条就超出可推理范围。对方声称保证非空不能直接采信，要转成本侧的显式判空与校验。回调方向要防的是 panic 跨过这道边界，带着外部栈与资源状态离开，本文只说要防什么。

复核与治理

治理 unsafe 常用的度量是面积：不安全代码占多少行、集中在哪几个模块、这一季度是涨是跌。面积本身不说明对错，它的作用是把“要不要再添一块”变成一个能被讨论的数字。更实用的做法是把 unsafe 集中到单独模块，让边界只剩一处：外层模块说明写清这一族类型共同遵守的不变量，评审只需守一个入口，新代码想混进来也得先在这里露出来。

两条规矩值得变成硬性要求：每块 unsafe 挂一条 SAFETY 注释，并至少配一个针对它的最小测试——测试不为凑覆盖率，而是让“前提被破坏时会怎样”有一个可复现的地方。评审读 unsafe 的顺序同样应当固定：

小结

本文的主线只有一条：unsafe 不是把检查关掉，而是把责任挪到人这一侧，它的价值取决于你能否把前提写成可核对、可测试、可评审的东西。裸指针与 NonNull、MaybeUninit、从指针到引用的五条前提、把不安全收在类型边界之内，都是为了让这份责任有个明确落点。工具各有盲区，并发与外部内存各有约定，最后落回同一句话：写 unsafe 之前先把前提写出来，写不出前提就先别写。
