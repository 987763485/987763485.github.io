大模型推理服务化实践

本文聚焦大模型推理服务在生产环境中的真实运维问题：兼容层的边界与差异形态、流式响应的断连处理、超时与重试的指数级放大、队列优先级设计、计量对账口径、灰度回滚与故障演练。适合已落地推理服务但尚未处理层间耦合细节的工程团队。读完本文，你应当能建立一份可执行的运维清单，把”架构上能跑”推进到”日常不出事故”。架构分层与职责边界的定义见同期《推理服务架构设计》（idx 984），网关内部实现见《模型服务网关设计》（idx 941），本文只讨论层间出问题的地方。

兼容层的边界

大模型推理服务通常对接多种引擎与上游 API（DeepSeek-V3.1、Qwen3、Llama 4、Claude Sonnet 4、GPT-5 等）。兼容层（compatibility layer）的核心职责是在网关与引擎之间维护一个”内部统一契约”——让调度、队列、计量模块不必感知底层差异。为什么要这层抽象：引擎升级换代的窗口极短，如果业务侧代码直接绑定某家参数命名，换代时所有调用方都要改，变更面不可控。兼容层把”改一处”变成运维配置变更，发布风险从代码层降到配置层。

差异形态可归纳为五类。第一，参数命名差异：同一语义（如最大生成长度、温度、采样方式）在不同引擎中拼写与嵌套层级完全不同，兼容层只做映射，不发明语义。第二，流式终止标记：部分引擎通过一个特定标记表示生成结束，另一些通过关闭连接或发送空对象来表示；兼容层负责把终止信号归一，上层不应判断”是哪种标记”。第三，错误体形状：HTTP 状态码与 JSON 错误结构在不同引擎之间没有统一 schema，兼容层把上游错误翻译成内部错误码加人类可读信息，但不吞掉上游原始错误码。第四，stop token 处理：有的引擎支持多个停止序列，有的只接受单个；有的停止序列需要转义，有的不需要——兼容层统一为列表语义，转换逻辑按引擎路由。第五，工具调用字段：MCP 协议在 2025-03-26 和 2025-06-18 有修订，不同引擎对工具调用的返回格式、参数嵌套方式有出入；兼容层把工具调用归一为内部结构，不做业务决策、不做结果缓存、不改写权限判断。

兼容层不该承担什么：它不做业务路由（该用哪个模型是调度策略的事），不做响应缓存（缓存一致性应由上层业务保证），不改写鉴权信息（权限校验在网关完成），不拼装提示词（提示词是应用层职责）。一旦兼容层承担了这些，它就从映射器变成了隐式业务组件，灰度和回滚的爆炸半径会失控。与《模型服务网关设计》的衔接：网关负责鉴权、限流与协议终止，兼容层在网关之后、调度之前，是网关的下游插件而非独立进程。

流式响应的真实工程问题

大模型生成天然是逐 token 输出的，客户端通过 SSE（Server-Sent Events）或 chunked transfer 接收增量结果。看似简单的”持续推流”在生产中会暴露出四个工程问题。

首字节前的等待。从请求到达引擎到第一个 token 产出，GPU 需要做 KV 缓存分配、前缀计算与首次推理，这段时间可能达到数百毫秒到数秒（具体取决于模型规模与硬件，此处不写具体数字）。在等待期间连接处于静默状态，中间的代理或网关如果配置了空闲超时（idle timeout），会在”无数据”达到阈值时切断连接。应对方式有两种：在首 token 之前发送 SSE 注释行（以冒号开头的 payload）作为心跳；或者把代理的空闲超时设为大于首 token 等待上限。团队约定示例中，心跳间隔设为 5 秒，代理空闲超时不低于 60 秒。

客户端提前断开。用户在生成中途关闭浏览器或切换页面时，TCP 连接断开，但引擎不知道客户端已走。如果服务端不做取消操作，引擎会继续消耗 GPU 算力生成剩余 token——这部分成本完全浪费。正确的处理链路是：网关检测到连接断开后，向下发送取消信号；取消信号经过调度层到达引擎实例；引擎停止解码并释放该请求占用的 KV 缓存。如果取消信号在中间丢失（例如兼容层没有转发），引擎会按最大长度生成完毕后才发现无人接收。

断点续传不可行。普通 HTTP 下载支持 Range 请求实现断点续传，但大模型生成不可重复——相同的 prompt 在不同时刻、不同引擎实例上可能产出不同 token 序列（取决于采样温度与并发批处理中的邻居请求）。因此流式响应中断后不能靠”重连补发”恢复，只能从头重新生成或接受已丢失部分。这一约束决定了取消信号必须一路传到引擎，而不是仅仅在网关侧丢弃响应。

取消信号传递。完整的取消链路覆盖网关、兼容层、调度器、队列和引擎五段。任何一段没有实现取消传播，下游都会做”无用功”。引擎侧需要支持协作式取消：在解码循环的每一步检查取消标记，发现取消后安全释放显存。批处理引擎（如 vLLM）中取消一个请求需要从正在排队的 batch 中移除，否则该 batch 的其他请求也会受影响。

超时与重试放大

一个用户请求从入口到结果需要经过网关、兼容层与调度、引擎、工具调用四段（或更多段）。每段都有自己的超时配置。如果配置不当，最坏情况是上游超时是下游超时的两倍甚至更高，导致上游在下游尚未放弃时已经返回错误，客户端看到”服务不可用”但引擎还在消耗算力。

超时预算分配的原则是”上游 > 下游之和”。下面给一张预算表骨架，数值全部为团队约定示例，不代表任何生产数据。

重试放大问题。假设客户端配置 3 次重试，网关配置 2 次重试，引擎内部对单 batch 的异常实例配置 2 次重试，那么一个请求最坏情况会触发生成 3 × 2 × 2 = 12 次实际推理。GPU 时间不是无成本的资源，12 倍放大意味着同一个故障可能消耗 12 倍的算力配额。应对方式有三层。第一，幂等键（idempotency key）：客户端在首次请求时生成一个随机标识符（UUID 或请求序列号），所有重试携带同一个键；网关和调度层对同一幂等键的并发请求做去重，只放行一个到引擎。第二，重试预算（retry budget）：对每个租户或每条上游通道设定单位时间内允许的重试次数上限，超过后直接快速失败而不是继续重试。第三，熔断（circuit breaker）：连续 N 次超时或错误后打开熔断，跳过所有请求，N 次成功探测后恢复。

幂等键设计注意事项。绝对不要把用户的 prompt 原文或任何个人标识写入幂等键——幂等键会出现在日志、缓存索引和分布式追踪中。正确做法是用客户端生成的随机标识符或对其做哈希。如果必须关联用户会话，使用脱敏后的会话 ID，确保不反查原文。

只对哪类失败重试。连接类失败（TCP 握手超时、连接被重置、DNS 解析失败）可安全重试，因为请求尚未进入引擎。引擎内部的 batch 异常（GPU 显存不足导致 batch 被驱逐）在引擎支持重新调度时可重试。但生成类失败——即请求已经在解码中、产出部分 token 后因某种原因终止——默认不重试。原因：重试意味着重新生成，已经消耗了一半的 GPU 时间作废，且第二次生成结果可能不同。如果业务确实需要”必须拿到完整结果”，应该在应用层用”请求新一次生成”的语义重新发起，而不是让底层框架自动重放。

队列与优先级

在线推理服务必须把请求分成三类：在线（interactive）、近线（near-line）、离线（batch）。为什么要显式分类：在线请求（用户对话、实时补全）对首 token 延迟敏感，等待超过用户感知阈值就会流失；近线请求（内容生成、文档摘要）可以容忍数秒排队但不能超过分钟级 SLA；离线请求（批量评估、数据标注）对延迟无要求但要保证吞吐和最终完成。如果三类混在一条队列里，离线请求在 GPU 显存中排长队，在线请求被迫等待前面的离线 batch 释放资源。批处理调度算法细节见《大模型批处理与调度》（idx 990），本文只讨论在线服务的队列优先级策略。

优先级饥饿的防范。在线请求优先级高于近线、近线高于离线。但长期高优先级流量可能把低优先级完全饿死。两种防范手段：老化提升（aging boost），低优先级请求等待时间超过阈值后优先级自动升一级，确保不会无限等待；分层配额（hierarchical quota），每类流量分配独立的 GPU 时间片比例（示意值：在线 60%、近线 25%、离线 15%），配额内互不抢占。团队约定示例中，老化提升阈值设为：近线请求等待超过 30 秒后提升为在线优先级，离线请求等待超过 5 分钟后提升为近线优先级。

抢占与截断语义。高优先级请求到达时是否抢占正在生成的低优先级请求？答案取决于”抢占后怎么处理”。如果直接从中间截断生成中的请求，客户端收到的是半截结果——这在对话场景中不可接受。可接受的做法是：抢占调度器不切断已在解码的请求，而是把新请求排入下一个 batch 的空位；只有在 GPU 显存真正不足时，才从 batch 中驱逐”尚未开始解码”的请求（而非已在输出的）。被驱逐的请求重新入队，携带”重试”标记，客户端侧看到的效果等同于排队时间变长而非请求失败。

按租户配额与快速失败。多租户共享推理池时，每个租户有独立的并发数上限与队列深度上限。当某租户的队列达到长度上限时，新请求直接返回”服务暂时不可用，请稍后重试”而非无限排队。无界排队的问题：请求在队列中等待时间不确定，最终超时后客户端已放弃但引擎仍在消耗算力，形成”幽灵请求”浪费。有界队列配合快速失败让资源释放及时。

计量与对账

推理服务的计量维度比传统 HTTP 服务复杂。需要计量的对象包括：输入 token 数、输出 token 数、工具调用产生的额外轮次（一次用户提问可能触发多轮工具调用与检索）、缓存命中与否（前缀缓存命中时输入侧实际消耗大幅降低）、失败请求是否计费（引擎在产出第一个 token 前崩溃的请求应免费）。

为什么按”成功产出的 token”计量最不容易起纠纷。如果按”分配给该请求的 GPU 时间片”计量，客户端无法验证这个数字；如果按”请求数”计量，长文本和短文本成本差几十倍，公平性无法保证。按”成功产出的 token 数量”计量有三个好处：客户端可以用自己的 tokenizer 独立验证（或至少估算）、不同引擎之间可横向比较、缓存命中的节省可以直接体现为”输入侧 token 数减少”而不需要额外的”折扣”字段。

对账口径。网关侧计数与引擎侧计数不一致是常态而非异常。原因包括：网关在发出请求后立即记录了”预期 token 数”但引擎实际生成的数量不同；重试导致同一请求在引擎侧计数两次但网关侧只记一次；客户端断开后引擎已生成的 token 是否计入——如果不计入，引擎侧计数大于网关侧。对账做法：每日从引擎导出”实际成功完成的 request_id 与 token 数”清单，与网关的”已入账 request_id 与 token 数”做 join，差异记录进入待核清单。待核清单按 request_id 追踪：网关有记录但引擎无完成记录——通常是引擎崩溃或取消后未入账；引擎有完成但网关无记录——通常是网络回包丢失或计量模块异常。

单位成本归因。推理成本需要归因到三个维度：功能（哪个产品功能消耗了多少）、租户（哪个客户用了多少）、模型（换代前后的单位 token 成本变化）。归因链路要求每条计量记录携带请求的功能标签、租户标识与模型版本，这些信息在兼容层归一后由计量模块直接读取。定价策略不在本文范围——定价一律按当期官方价目核对，本文只关注”计量准确、可追溯”。

计量数据留存与脱敏边界。计量明细需要包含 request_id、token 数、功能标签、租户标识、时间戳——但绝不包含用户 prompt 原文或模型生成内容。原因：计量系统通常与账单系统对接，账单可能被多人访问；token 数与 request_id 足以对账，原文没有计量意义。如果出于调试目的需要关联原文，应通过 request_id 去日志系统查询，而不是把原文写进计量记录。日志系统本身也有脱敏要求，见本文”可观测”一节。

灰度与回滚

模型换代（如从 DeepSeek-V3.1 升级到后续版本、从 Qwen2.5 切到 Qwen3）是推理服务最高频的变更类型。灰度切法通常分三步：按租户灰度、按流量比例灰度、按场景灰度。

按租户灰度：选取内部测试租户或低敏感租户全量切到新版本。此阶段覆盖面小但深度全，能发现权限、计费格式等”全链路”问题。按流量比例灰度：对选定租户组按比例分流（示意值：先 1%、再 10%、再 50%、最后 100%），每档观察足够时间确认无异常。按场景灰度：同一租户内不同功能场景（对话、摘要、代码生成）分阶段切换——某些场景对模型行为更敏感，先切不敏感的场景。

双跑对照的评估口径。灰度期间同一输入在新旧模型上各跑一次，对比质量指标。指标口径沿用同期《模型质量评估》一文的定义（输出准确率、有害内容率、拒答率、格式合规率），本文不重讲评估方法。双跑的目的是在真实流量上验证质量，而不是只看离线评测集。

回滚条件与一键退回。回滚触发条件：错误率突增超出基线、质量指标下降超过团队约定阈值、延迟或吞吐劣化影响在线 SLA。”一键退回旧版本”的实现要求：旧模型的权重文件必须在线（已加载或在共享存储可直接挂载），配置文件中旧版本的条目不能被删除（只标为”当前未启用”）。如果回滚需要先下载权重，冷启动时间会让回滚变成”等待恢复”而非”退回”。兼容层的引擎适配器也要保持旧版本可用——灰度期间两套适配器同时在位，回滚只是切路由。

灰度期间成本翻倍窗口。双跑阶段同一请求消耗两份 GPU 时间，成本在灰度窗口内接近翻倍。预算护栏：灰度持续时长上限设为团队约定值（示意值：不超过 7 天），超时必须做决策（全量或回滚）；灰度期间如果成本超出预算上限，自动停止双跑只保留比例切换的”单跑”模式。

契约测试与容量信号

契约测试（contract test）是在推理服务与所有下游消费方之间建立的一层固定样例验证。一组精心设计的请求样例集覆盖正常生成、多轮工具调用、长上下文、stop token 终止、异常输入等场景。每次引擎升级、兼容层变更或网关规则调整时自动运行这组样例，检查四件事：响应 JSON 的字段形状（哪些字段存在、类型是否正确）、流式事件的顺序与终止方式（是否以约定的结束事件终止）、错误体结构（异常场景返回的内部错误码与可读信息是否完整）、工具调用格式（多轮工具调用的嵌套结构是否符合内部统一契约）。

为什么这是最便宜的防事故手段。上游引擎的 API 变更（字段增删、默认值改变、错误码调整）通常不会通知下游。没有契约测试时，变更会静默传入生产——直到客户端报格式错误或解析失败才被发现。有契约测试时，上游一升级 CI 就报红，发布被拦住。样例集必须覆盖所有兼容层路由到的引擎，每个引擎至少 5 到 10 条核心场景样例。

测试样例不得含真实用户数据。样例中的 prompt 应该是合成文本或团队构造的公开场景描述，绝不能用线上请求的 prompt 原文做测试。原因：样例文件会进版本控制、测试报告和日志，真实用户数据一旦混入就变成数据泄露事件。

容量与伸缩的接口。弹性伸缩的信号采集、排水与冷启动处理见《推理服务的弹性伸缩》（idx 982），本文不重讲。服务侧需要暴露给伸缩控制器的信号有四组：队列深度（当前等待中的请求数，反映”处理能力不够”的即时信号）、首 token 等待分位（P50 和 P99，反映排队是否恶化）、显存水位（已分配 KV 缓存占总显存比例，反映批处理还有没有空间）、就绪四态（实例状态为 启动中、就绪、排水中、已关闭，伸缩控制器必须只向”就绪”实例派发新请求，”排水中”的实例处理完已有请求后退出）。

故障演练清单

推理服务的故障演练必须定期执行（团队约定频率，不低于每季度一次），覆盖以下八个场景。每个场景写明注入方式（描述即可）、期望行为、通过判定标准、恢复动作和需要在场的人员角色。

演练执行注意事项。每个场景必须在预发环境至少演练两次后才可写”已验证”；生产演练需要变更审批（见”组织与流程”一节）。”需要谁在场”列出的角色必须实际到场，远程观察不算”在场”。演练结果写入”评估记录”，作为交付物存档。安全测试相关内容见同期红队评估一文。

可观测与告警落点

监控系统的实现细节与部署见《Rust 服务可观测性》（idx 993）或同期监控篇，本文只列推理服务侧必须采集的信号与判定方法。

阶段耗时拆分。每个请求的全链路耗时必须拆成四个阶段分别上报：排队时间（从入队到分配到 batch）、首 token 时间（从分配到产出第一个 token）、生成时间（从首 token 到末 token 或终止）、工具调用时间（多轮工具调用的总往返时间）。四段独立上报意味着：排队时间长说明并发超限或实例不够，首 token 时间长说明引擎调度或显存分配有瓶颈，生成时间长说明 batch size 过大或上下文过长，工具调用时间长说明检索或外部服务降级。

错误分类。所有失败必须归入有限类别：超时（网关侧、引擎侧、工具侧分别标记）、取消（客户端断开导致的主动终止）、限流（租户配额或全局过载）、引擎内部错误（显存不足、CUDA 异常、batch 驱逐）、兼容层转换错误（上游响应不符合契约格式）。类别有限是低基数原则的前提——如果错误类型无限增长，告警规则和仪表盘会变成噪声。

取消率与重试次数分布。取消率突增通常意味着客户端超时配置过短（用户等不到结果主动关闭）或网络链路劣化。重试次数分布突增意味着上游实例不稳定或熔断器处于半开状态。两个指标结合能区分”客户端问题”和”服务端问题”。

队列等待分位。每类请求的队列等待 P50、P95、P99 单独上报。在线请求 P99 等待超过团队约定阈值（示意值）时触发告警。近线和离线的告警阈值不同——近线容忍更长等待。

租户维度成本。每个租户每日 token 消耗与请求数作为成本归因的基础数据。成本突增自动关联到具体功能标签与模型版本，帮助快速定位”哪个新功能上线导致成本翻倍”。

脱敏原则。用户提问原文与任何可识别个人信息不得写入日志、不得作为缓存键组成部分、不得外发到不受控的第三方观测服务。具体约束：日志中只记录 request_id、token 计数、模型版本、错误码——不记录 prompt 内容和生成内容；分布式追踪的 span 属性中不附带原文；如果排查问题需要关联原文，走审批后的”按 request_id 查询”路径而非全文检索日志。低基数原则要求标签数量有上限——不要把 request_id 作为指标标签（基数无界），只放在结构化日志中。

周边系统耦合与组织流程

与检索和工具服务的耦合。推理服务调用外部检索或工具时共用的超时预算和配额容易配错。工具调用的超时不能设得比推理总超时还长——否则工具还没返回推理侧已超时，导致工具”白跑”。配额共享：如果检索服务和推理服务共享同一组 GPU 资源（如 embedding 模型与生成模型部署在同一张卡上），推理高峰时检索排队延迟增加，反过来拖慢推理的工具调用环节。容量规划时需要把”推理高峰导致检索延迟增加”这个耦合因素考虑进去。

SDK 版本碎片化。客户端 SDK 版本不一致是静默行为差异的常见来源。旧版本 SDK 可能不发送新字段（如幂等键、流式偏好设置），导致服务端走默认路径——默认路径可能不是新策略期望的路径。应对：服务端按请求头中的 SDK 版本标识选择处理逻辑；兼容层对缺失字段填充安全默认值；契约测试样例中保留旧版 SDK 格式的请求验证不会 crash。

时区与时间戳单位。计量系统和日志系统使用 UTC 时间戳，而运维面板可能对不同团队展示本地时间。时间戳单位混用秒与毫秒是最常见的低级事故——计量模块写入毫秒、对账脚本按秒读取，结果 token 归属到错误日期。全链路统一使用 Unix 毫秒时间戳（或秒，选一个写死），在接口文档中注明。

“上游限流被当成业务错误”的误判。上游引擎的限流返回（对应内部错误码”请求被限流”）如果被兼容层翻译为”引擎内部错误”，调度器会触发重试（按内部错误可重试的逻辑），进一步加剧上游压力。正确做法：限流类错误映射为”不可重试”语义，同时向上传播限流信号让调度器降速。这是兼容层的职责之一。

组织与流程。推理服务的运维职责划分需要明确三个角色：引擎负责人（管模型加载、显存分配、引擎版本升级、batch 策略）、网关负责人（管鉴权限流、超时配置、协议转换、健康探测）、应用负责人（管提示词、配置变更、功能标签、成本预算归属）。一次模型换代需要的签字链路：评测团队（质量指标确认）、安全团队（红队测试通过）、成本审批（预算覆盖灰度窗口）、合规（标识方案覆盖——《人工智能生成合成内容标识办法》自 2025-09-01 已施行，需按要求标识）。EU AI Act 中 GPAI 义务自 2025-08-02 已适用，模型换代时需同步核对义务覆盖。评估记录作为交付物持久化存档，事后复盘必须落到”哪条演练场景没覆盖、为什么没覆盖”，而不是笼统写”加强测试”。

问题对照速查

下表把本文讨论的核心问题汇总为速查参考。列为”问题域、必须做的动作、最容易漏的点、坏了的症状、用什么指标预警”。

小结

大模型推理服务从”架构能跑通”到”日常稳定运转”之间隔着大量层间耦合细节。兼容层必须守住边界只做映射；流式链路取消信号要一路传到引擎；超时预算要逐段对齐防指数放大；队列必须显式分类并设老化防饿死；计量按成功 token 走最公平且可验证；灰度回滚要求旧权重和旧适配器同时在线；契约测试是防上游静默变更的最便宜手段；故障演练不能走过场。本文列出的清单、预算表和演练场景可直接作为团队运维手册起点。
