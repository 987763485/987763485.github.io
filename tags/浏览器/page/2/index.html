Web Workers 把耗时计算移出主线程

页面上一次点击要等六七百毫秒才有反应，排查半天发现是前端自己在算东西——这类问题在 2015 年已经不算罕见。Web Worker 给了我们第二个线程来跑纯计算，但它不是免费的：消息要序列化、数据要拷贝、结果要配对，用错了反而更慢。本文站在性能与调优的角度，讲清三件事：怎么判断”该不该上 worker”、上 worker 的三条落地路线（整体搬迁、分片协作、零拷贝传输），以及围绕它的工程约束和踩过的坑。代码全部 ES5，支持面按 2015 年 1 月的真实浏览器情况来谈。事件循环与单线程模型在旧文《JavaScript 单线程与异步编程模型》里已经讲透，本文不重讲；大列表的渲染瓶颈则是另一回事，参见《大列表渲染优化思路》，那是”画不过来”，本文谈的是”算不过来”。

DOM 查询与遍历的性能优化

查询与遍历是脚本碰 DOM 的两个最基本动作，也是最容易藏进热路径的两个：一次按键触发几百次全表扫描、一段递归把调用栈吃穿，事故现场往往就出在这两件“看起来不花钱”的事上。《DOM 查询缓存与批量操作》和《DOM 节点类型与节点关系梳理》已经把“查询结果要缓存”“活集合边删边遍历会漏”讲过，本文不重复这些结论，而是把主线换成成本模型与集合语义：一次查询的开销由哪几段构成、live 与静态集合在规范层面差在哪、老 IE 缺失的 Element 系列怎么补、深树遍历在调用栈与显式栈之间怎么选，最后用一张后台表格页的热路径重构把全部方法走一遍。适合维护列表、表格、树类页面的同学，也适合被“IE6-8 到底缺了什么 API”困扰、准备手写兼容层的读者。文中所有数字都按同一把手工计时口径测得，只给相对量级，不编权威数据。

selection 与 range 实现文本选区

postMessage 实现跨窗口安全通信

页面里嵌一个不同源的第三方组件，或者弹一个对方域下的登录窗口，两边谁也没法直接读谁的东西。postMessage 是浏览器为这种情况留的正式通道：把一条消息投递到另一个窗口的 message 事件上，不经过服务器，也不进地址栏。本文按入门的顺序讲三件事：最少几行代码跑通收发、消息什么时候发才不会丢、以及怎么把这道门守住不让它变成漏洞。适合准备嵌入第三方内容或做跨窗口登录回传的同事读，代码全是 ES5，可以直接落到老项目里。
