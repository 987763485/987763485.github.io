消息队列削峰填谷实战

大促、整点秒杀、批量导入这类流量有一个共同点：峰值只持续几分钟，平均值往往只有峰值的几分之一。按峰值准备容量，大部分时间都在浪费；不按峰值准备，系统又会在最关键的那几分钟里崩掉。本文讲消息队列在中间充当缓冲池的工程做法：什么条件下才适合削峰，链路怎么搭，容量怎么算，消费端怎么治理，以及那些上线之后才会暴露的坑。读者应已了解消息队列的基本模型，本文不涉及产品选型。

缓存设计与缓存一致性

缓存是后端系统里性价比最高的性能手段，也是最容易留下隐患的地方。加一个 Redis 只需要半天，但要让它在流量高峰、发布回滚、主从延迟和机房故障下都不出问题，需要一套完整的设计。本文不讨论某个命令怎么用，而是把缓存设计拆成四个必须回答的问题：缓存放在哪、缓存什么、何时失效、失效之后怎么办。沿着这条主线，我们会依次看读写模式、一致性方案的失败窗口、穿透与雪崩的应对、热点与容量治理，最后用商品详情页做一次完整推演，并给出一份可落地的取舍清单。本文适合已经用过 Redis、准备把缓存做成基础设施的后端工程师阅读。

限流与配额体系设计

一个接口每秒能承受多少次请求，和一个月允许某个客户用掉多少额度，是两件不同的事。前者是保护系统不被瞬时流量打垮，后者是商业合同里的数字，要计量、要对账、要能被审计。本文把这两件事放在同一张设计图上：先厘清限流与配额的边界，再讨论租户分层、计量与账期、分布式下的额度共享、公平性、429 的体验以及配额治理，最后给出一条可以分阶段落地的路径。读者应熟悉 HTTP 与 Redis 的基本用法；令牌桶、漏桶的算法推导留给同系列的其他篇目，本文只在额度共享的语境下讨论分布式取舍。

高并发下的连接池设计

服务一旦扛起高并发，最先出问题的往往不是业务逻辑，而是连接。每次请求都新建 TCP 连接、重新做一次数据库认证，延迟会被握手与权限检查吃掉，下游也会被瞬间涌入的连接数压垮。连接池就是把“建连”这件昂贵的事提前做、反复用，但池子的大小、排队的方式、超时的分层，决定了它是稳定器还是放大器。本文从容量估算讲起，拆开池的内部结构，再讨论超时体系、泄漏排查与多路复用带来的变化，适合已经会写连接池配置、但还说不清每个参数为何取这个值的前后端工程师。

服务自保护与过载保护

一个服务在流量正常时表现得体，接口响应几十毫秒，错误率接近零；一旦流量翻了几倍，或者某个下游突然变慢，它的表现会迅速失控：延迟从几十毫秒涨到几秒，超时开始出现，客户端重试涌入，线程池被占满，连健康检查都开始失败，最后整个实例被摘除，压力转移给剩下的实例，雪崩由此发生。过载不是某个组件的故障，而是一种系统性状态，它以正反馈的方式自我放大，如果不加干预，服务很难靠自己走出泥潭。
