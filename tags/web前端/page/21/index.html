前端路由实现原理

写单页应用绕不开路由，但很多文章把路由讲成了”改一下地址栏”的小技巧，低估了它的分量。路由真正难的地方不在”怎么把 URL 换掉”，而在”换掉之后这一切换要花多少代价”：一次点击背后是匹配、取数、建 DOM、重排重绘，还有一整套卸载旧视图、恢复滚动、补发埋点的收尾工作。这篇文章就从性能与调优的角度，把 Hash 路由和 History API 路由这两条实现路线拆开讲清楚，再讨论路由表的匹配算法、分发渲染的开销构成、频繁触发时的节流、埋点统计的补发，以及落到工程上的选型结论。凡是涉及 location、history 这些对象本身的属性清单，以及 pushState、replaceState 三个参数逐个怎么填，我在《location 与 history 对象详解》和《HTML5 History API 打造无刷新单页应用》里已经写过，这里不重复，只把笔墨放在路由的实现与代价上。文中的代码全部用 ES5 语法书写，块级绑定、箭头函数、异步编排原语这些眼下还没进标准的东西，一个都不碰。

2014 年 11 月，我把一个内部表单控件的继承写法从 Dog.prototype = new Animal() 换成了 Dog.prototype = Object.create(Animal.prototype)。改动不到二十行，测试环境一片绿灯，上线三天却陆续收到四个 bug：有一个键死活查不出来、有一个方法无论怎么覆盖都不生效、有一个把用户的参数写进了原型、还有一个在 IE8 用户的机器上直接白屏。回滚之后我拿 ECMA-262 第 5 版 15.2.3.5 那一条对着各家浏览器逐个参数实测了一遍，才发现我之前是把 Object.create 当成「不用写 new 的构造函数」在用，而它的语义其实只有一句话：造一个对象，把它内部的原型接上你给的那个东西，仅此而已。
