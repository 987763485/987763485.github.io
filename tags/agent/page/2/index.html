多 Agent 系统可观测性

给单个智能体埋点，方法已经相对清楚：会话、步骤、模型调用、工具调用四级 span，关联键定死，日志先脱敏再落盘，成本按归属维度聚合。把三五个智能体放进同一个系统，这套方法就出现结构性缺口——四级 span 默认存在一条”主时间线”，而多智能体系统里没有主时间线：执行是分叉的，消息是乱序的，两个智能体可能在同一秒各自发起模型调用，也可能一个等另一个的回答一等就是四十秒。更麻烦的是，多数故障不是某个智能体报错，而是配合本身失灵：没人认领最后一步、两个智能体重复检索同一份材料、辩论收敛不了却被预算闸门悄悄掐掉。

Agent 长任务执行稳定性

一个只跑几十秒的智能体调用，和一个跑到跨小时、跨进程重启的智能体作业，面对的不是同一个问题。前者的失败通常是“这一次没答好”，后者的失败通常是“这一次没答完，而且没人说得清它答到哪了”。本文只谈执行侧的稳定性机制：进度怎么落、心跳怎么判、预算怎么分层、上下文怎么瘦身、冲突怎么加锁、超支怎么降级、崩了怎么接手。重试与失败恢复的调用级语义不在本文展开，只在必要处划界。

多 Agent 分工与协商

多智能体的困难常常被归因成”模型不够聪明”，但工程上真正咬人的是协作本身：消息会迟到，状态会被两个人同时改，预算会在没人负责的地方烧完，而系统始终回答不出”现在到底进行到哪一步”。本文把这套问题当作一次分布式系统的重演来处理——谁拥有哪份状态、交接消息该带什么、什么时候算做完、什么时候必须熔断、以及最重要的，什么时候根本不该拆。机制层尽量写透，示例一律用角色命名与伪码，不绑定任何具体产品。

Agent 失败恢复与重试
