大模型与安全合规

长上下文压缩技术

长上下文的账单并不是一个数字，而是三本账：占住显存的缓存字节、随序列长度增长的注意力算力、以及按 token 计价或按时钟计费的首字延迟。所谓压缩，就是决定从哪一本账里扣钱、允许信息在哪个环节失真、再用什么观测手段证明失真没有伤到任务。本文把 2025 年及以前的公开工作整理成四条路径——token 丢弃与显著性选择、KV 缓存压缩与量化、注意力稀疏化与窗口分块、层级摘要与检索替代——逐一讨论它们在保信息、保延迟、保成本这个三角上的站位。最后会回答两个经常被跳过的问题：压缩与前缀缓存复用为什么天然打架，以及什么时候开压缩其实是净损失。

Agent 上下文工程

Agent 的每一次请求，都是从一堆互相竞争的材料里现场拼出一段上下文：指令、工具定义、历史、检索结果、输出预留，谁占多少、谁排在前面、谁被折叠成摘要，都是需要显式决策的工程问题。本文讨论如何把这段有限资源当作预算对象来管理，覆盖装配顺序、渐进披露、结构化摘要、前缀稳定、指令与数据分离和污染检测，并在结尾给出一份可复用的装配模板与策略对照表。它只关心单次请求之内的上下文构造：跨会话的记忆写入与遗忘策略属于《Agent 记忆与长期上下文》的话题，记忆条目的召回打分属于《Agent 记忆检索优化》的话题，本文到需要处各用一句话划界，不再展开。
