RAG 检索重排序实践

很多检索增强生成（RAG）系统的质量波动，第一跳的检索链路往往负有相当责任：双塔向量检索捞回来的 top-k 文本块，主题相近却答不上问题的居多，直接塞进提示词，大模型再强也无米下锅。重排序（rerank）的思路是在召回与生成之间插入第二个打分器：用更贵但更强的模型只对召回候选做精排，把“相关”与“能回答”区分开。本文面向已跑通向量检索链路的工程师，讨论重排环节的模型选择、参数决定、评测归因与上线运维。

大模型提示词管理

不少团队的大模型应用做到第二个迭代时，会发现最脆弱的环节不是模型选型，也不是向量检索，而是一段几百字的中文提示词：它被复制进五个文件，改一处忘四处，出了问题没人说得清当初为什么这样写。本文要做的就是把提示词从“文案”升级为“工程资产”：依次讨论分层结构、模板与变量注入、渲染期的注入防护、归属与评审、评测集与回归、灰度与回滚，以及按业务线组织的注册表与检索。适合正在维护多个大模型功能的工程师，读完应能把现有硬编码字符串改造成可评审、可回归、可回滚的形态。版本标识与发布通道这类版本化机制细节另有专文，本文只谈整体实践与取舍。

RAG 工程化落地

RAG（检索增强生成）的原型很好做：把文档切开、算 embedding、塞进向量库，再接一个问答提示词，一个周末就能跑通 demo。但让它服务于真实用户——几十万名员工或者外部客户——问题才会真正暴露：文档每天在变、权限模型复杂、答错了没人能追责、成本随流量线性上涨。本文面向跑通过 RAG 原型、准备推向生产的读者，梳理从数据接入到运维监控的工程链路。检索与 embedding 的原理、分块策略选型、重排序模型细节，本博客另有专文（《Embedding 与语义检索》《RAG 分块策略与召回优化》《RAG 检索重排序实践》），本文不重复，专注工程化与运维这一层。

TypeScript 5 装饰器迁移

TypeScript 5.0 于 2023 年 3 月 16 日发布，这是第一个把 TC39 标准装饰器作为默认语义的稳定版本。对多数项目而言，升级编译器本身并不难，难的是接受“同一个 @ 符号背后换了一套规则”：参数从三个变成两个，字段装饰器从打标记变成返回初始化函数，元数据不再自动发射。本文按“差异、影响、迁移”三层展开，先逐条对比新旧语义，再讨论依赖注入与 ORM 框架为什么暂时不能跟着走，最后给出一份可以分阶段执行的迁移清单。读者应当已经用过 experimentalDecorators，或者正在维护一个被装饰器深度绑定的代码库。

Embedding 模型评测
