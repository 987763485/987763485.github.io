库存扣减的三种方案

库存扣减看起来只是一条减法语句，真正难的是让它在并发、重试和故障下依然成立。本文只讨论“扣减”这一个动作，把常见实现归纳为三条路线：数据库扣减、Redis 预扣后异步落库、消息队列串行化，逐条拆开讲清原子性从哪里来、一致性边界在哪里、失败之后怎么补，最后给出按业务形态选型的判断依据。

go-micro 微服务框架实战

Go 生态里做微服务，可选的路子不少：有的直接在 gRPC 上加一层封装，有的用 HTTP 加 JSON 约定接口，go-micro 走的是第三条路——把服务发现、异步消息、传输、负载均衡这些横切能力抽成接口，再让插件去填。本文从一段 protobuf 定义出发，依次讲清服务定义、组件替换、中间件与 Kubernetes 落地，适合已经写过 Go 服务、正准备引入框架的读者。读完之后，你应该能判断它是否适合你的团队，也能避开版本混用带来的坑。

高并发架构设计原则

高并发不是引入某个中间件就能获得的能力，而是一连串权衡之后留下的设计选择。本文把散落在缓存、消息队列、分库分表、限流熔断中的经验收敛为七条原则，每条原则都配一个反例、一段后果推演与可落地的做法，并用一条电商下单链路贯穿说明：同一个系统在流量增长的不同阶段，取舍为什么会变。本文面向已经写过业务代码、准备接手流量压力的后端工程师。

限流与配额体系设计

一个接口每秒能承受多少次请求，和一个月允许某个客户用掉多少额度，是两件不同的事。前者是保护系统不被瞬时流量打垮，后者是商业合同里的数字，要计量、要对账、要能被审计。本文把这两件事放在同一张设计图上：先厘清限流与配额的边界，再讨论租户分层、计量与账期、分布式下的额度共享、公平性、429 的体验以及配额治理，最后给出一条可以分阶段落地的路径。读者应熟悉 HTTP 与 Redis 的基本用法；令牌桶、漏桶的算法推导留给同系列的其他篇目，本文只在额度共享的语境下讨论分布式取舍。

Rust 迭代器与闭包
